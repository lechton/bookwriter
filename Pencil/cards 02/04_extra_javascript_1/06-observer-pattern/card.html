Line by Line
1—running is a hidden marker holding the computation running right now (or null) — how an otherwise-anonymous read knows who is asking.
2—get(signal) is the intercepted read: every read of a reactive value goes through it.
3—TRACK: if a computation is running, add it to this signal's deps (its set of dependents). The subscription records itself, automatically, on every read.
4—Then return the signal's value to the caller, exactly as an ordinary read would.
6—set(signal, next) is the intercepted write: every change goes through it.
7—Store the new value on the signal.
8—TRIGGER: walk the signal's deps and run each one again. The change notifies everyone who had read this value.
Explanation
A reactive value keeps a list of every computation that depends on it. A hidden marker names the computation currently running, so every intercepted read records it (track) and every intercepted write re-runs the recorded ones (trigger) — the subscribe-and-notify you never wrote.
A read records its reader; a write re-runs them:
reads reader.name TRACK name.deps += masthead
reader.name = "" TRIGGER re-run masthead
✓ read reader.name (while masthead runs) → get records masthead in deps (track)
✓ write reader.name = "" → set re-runs every computation in deps (trigger)
you wrote a plain read and a plain writesubscribe & notify happened for you
signal — a reactive value bundled with the computations that depend on it
track — on a read, record the currently-running computation as a dependent
trigger — on a write, re-run every recorded dependent
Track on read, trigger on write: a value records its readers and re-runs them when it changes — the whole engine of reactivity, performed automatically through an intercepted get and set.
