What React does... under the hood.
The React docs have a challenge that writes this kind of page in plain JavaScript, in a better way. It does not give a command for each change. Instead, it keeps the look in variables, and it has one function, update DOM. That function sets every element from those variables... every time anything changes. The docs say this function "shows what React does under the hood when you set the state".
There is one difference, and it matters for the next mistake. Update DOM writes every property of every element, on every change. React does not. In the words of the docs, React "also avoids touching the DOM for properties that have not changed since the last time they were set." So React compares the new render with the last render. Then it changes only what differs between the two.
Here's a mistake. Changing the page by hand, inside a React component.
A developer who is used to plain JavaScript might turn Apply off the old way, inside the React handler. The button gets an id, and the handler finds it.
Watch line fourteen in this version of handle submit. Line thirteen still calls prevent default. But line fourteen calls document dot get element by id, with the string apply button, and sets its disabled to true. The note marks it as wrong... our code changes the button behind React's back. The rest is the same as before. The try, the await on check code, success on line seventeen, and error in the catch.
The button still has its condition from state.
Only three lines this time, thirty-two to thirty-four. The button now has an id, apply button. And it's still disabled when the code is empty, or when status is checking. The word on it is still Apply.
The shopper types Welcom, and clicks Apply. This handler never asks for the checking look. So during the wait, the page shows no Checking... line, and the box keeps working. Only Apply is off. Then the server says no, and the page looks like this.
Figure thirty-one. At first glance, it looks right... the box says Welcom, and the red line says This code is not valid. But Apply is still disabled. That's the handler that turned Apply off by hand.
Now the shopper fixes the code to Welcome... but Apply stays off. The shopper cannot try again. Here is what happened, in order.
Let's start before the click. On the last render, status was typing, and the box was not empty. So the JSX said disabled equals false, in curly braces, for Apply. The click ran our line, which set disabled to true directly on the button. React knows nothing about this. The server said no, and catch asked for the error look. React drew the component again. In the new render, the JSX again says disabled is false for Apply. The look is now error, and the box is still not empty. React compares the two renders. Apply's disabled was false last time... and it is false again. Nothing changed, so React does not touch the button. The button keeps the true that our code wrote. Apply stays off. And then the shopper types the E. React draws again, and disabled is still false in both renders. So React still does not touch the button.
The fix is to name the next look, and nothing else. Replace our line with the setter call for the checking look, as in the handler of the previous section. Then the checking render says disabled is true, and the error render says disabled is false. The two renders differ... so React turns the button back on.
Two ways to turn Apply off during the check, that's figure thirty-two. By hand, with get element by id and disabled set to true, React's last render said false, and the error render also says false. React sees no change, so Apply stays off. With state, calling set status with checking, the checking render says true, and the error render says false. React sees a change... and turns Apply on again.
