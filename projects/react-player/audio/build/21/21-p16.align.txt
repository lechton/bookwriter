And that brings us to interview prep. For the interview.
Here's the interview question again. How do you design a component that reacts to input with state... instead of touching the DOM?
How to answer it clearly, in thirty seconds.
In plain JavaScript, the code is imperative. Every handler commands each element: disable this button, show that message. With many looks, one forgotten command leaves the page in a look nobody designed... like an error message and a success message on screen together. In React, I write declarative code instead, in five steps. First, I list every visual state the user can see, and I mock each one with a status prop, often all on one page, like a living styleguide. Second, I find what triggers each change. There are human inputs, like clicks and typing, and computer inputs, like a server's answer. Both must set state, and every look needs a way out, including the error path. Third, I represent the look with as little state as possible, usually one status string instead of several booleans. Four booleans allow sixteen combinations, while a string with four allowed values allows exactly four. Fourth, I remove any state that causes a paradox, repeats other state, or can be computed... such as whether the text is empty. Fifth, I connect the event handlers so they only call setters. The JSX decides what is disabled, shown, or styled, and React changes only the parts of the page that differ from the last render. That is also why I never edit the DOM by hand inside a component. React will not undo a change it did not make.
Then, three classic follow up questions interviewers ask.
The first one. Why use one status string, instead of several booleans like is loading and is error? Well, every boolean doubles the number of possible combinations. Four booleans give sixteen, but a form like a promo code box has only four or five real looks. So most combinations are impossible states... and they do happen in practice. Say the error branch sets is error to true, and forgets to set is loading to false. Then the page shows an error while the input is still disabled, and the user cannot fix it. One status holds exactly one value, so setting the string error replaces the string checking by itself. When you need a boolean in the JSX, compute it. For example, a constant is checking, equal to whether status is the string checking. The second question. What goes wrong if you change the DOM directly inside a React component? React does not read the page to decide what to change. It compares its new render with its last render, and it only touches properties that differ. Say a handler sets disabled on a button with get element by id. The JSX may say disabled equals false, in curly braces, both before and after... so React sees no change, and never turns the button back on. The page and React's picture of it no longer match. The fix is to call a setter for the next look, and let the JSX compute disabled, class name, and which elements appear. And the third question. How does a network response change the page, if no one clicks anything? A network response is a computer input. In an async handler, the code before await runs on the click. React draws that state, such as checking, while the handler waits. When the promise has its answer, the handler goes on and calls the setter for the next look: success after await, or error inside catch. Then React draws again. There are two traps. Without catch, a refused request leaves the page stuck on its waiting look. And after await, the status variable still holds the value from the render that created the handler. So the handler should set the next look directly, instead of reading status.
One last picture, figure thirty-four, the comparison to keep in mind for the interview. It's titled, Two ways to make a form react to input, and it branches into three. The first branch is imperative: class list, and disabled set to true. Each handler commands every element, and one forgotten command leaves an old line on screen. The second is many booleans, like is checking and is error. The looks are described, but sixteen combinations are possible... and a forgotten reset shows an error on a box that is still off. The third is one status, and declarative JSX: status, and set status. Each handler only names the next look. React changes only what differs, and old lines cannot stay behind. So, commanding the page by hand... versus describing each look and setting state. That's the whole lecture.
