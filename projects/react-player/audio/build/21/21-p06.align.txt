The mistake. Forgetting to hide one element.
This bug is easy to write, and easy to miss. Here's how it usually goes.
The developer writes the handler, and tests a wrong code. The error line appears. It works. Then the developer reloads the page, and tests a right code. The success line appears. It works. But a real shopper tries a wrong code first, then a right code... exactly like ours. Both lines are on screen.

Now the developer must go through every handler again. And for every element, they must ask... should it be shown, or hidden, after this change?
The React docs say it plainly. Imperative code for a page, quote, gets exponentially more difficult to manage in more complex systems. Adding a new element or a new interaction, quote, would require carefully checking all existing code to make sure you haven't introduced a bug.

In React, we never write commands like these. Instead, we say how the page looks in each case... and React changes the page. The next four principles build the promo code box that way, one step at a time.
And that brings us to principle one, in a single card. Imperative code... one forgotten command breaks the page. Describe each look of the page once, and let the handler change only state, instead of commanding every element in every handler. This one bites every developer who writes forms by hand. Your error line works. Your success line works. Then a real user tries a wrong code, and then a right one... and both lines sit on the screen together. You see, each handler only shows or hides what you remembered to write in it, and nothing checks the rest of the page. In React, the handler changes one value. The JSX already says what the page looks like for that value... so a line from an old look cannot stay behind. The do this example has three short lines. Section two. Principle two. List every look first.
One prop... that picks the look.
Before we write any logic for the promo code box, let's look at a much smaller component. It just shows whether a light is on... or off.
Here, Light dot jsx. Three lines. Line one exports a function called Light, and it unpacks one prop, status, with a default of off. The note there says it plainly: no status from the parent? Use off. Line two does the real work. If status is on, it returns a paragraph that says Light is on... otherwise, a paragraph that says Light is off. And line three just closes the function.
The parent renders Light, and passes nothing. So the default value from Lesson nine gives status the value off. The ternary from Lesson ten checks whether status is on. It is not... so the page shows the second paragraph.
That's what figure nine shows. A browser at localhost five one seven three, and one line on the page: Light is off. The parent passed no status, so status is off.
Now change one word. The default, from off to on... and save the file.
And in figure ten, the same browser, the same Light component... but now the page says Light is on. Only the default changed.
Here is what happened, in order.
First, the parent still passes nothing, so the default gives status the value on. Then the ternary checks whether status is on. It is, so the function returns the first paragraph. And last, React puts that paragraph on the page.
We changed no logic at all. One value picked the look. And the name status is our own choice. The React docs say about this prop... you could call that prop anything you like, the naming is not important.
Drawing every look... before any logic.
Designers work this way. Before anyone writes code, a designer draws one picture for every screen the user can see. There's a picture of the empty form, one of the form while it is sending, one of the form with an error... and so on. Such a picture is called a mock.
The React docs ask us to do the same in code. In their words: just like a designer, you'll want to mock up, or create mocks, for the different states before you add logic. In code, a mock is a version of the component with no logic. It only draws a look.
Each look has a name in React. One look of the component that the user can see is called a visual state. So the light has two visual states... on, and off.
Our promo code box has five visual states.
Five looks, then. Empty: the box is empty, and Apply is off. Typing: the box has text, and Apply works. Checking: the box and Apply are both off, and the word Checking is shown. Error: the same as typing, plus the red line, This code is not valid. And success: the form is gone, and instead the page shows, Code applied! You get free delivery.
Error and typing show the same form. The only difference is one red line. Still, they are two looks... because the user sees the difference.
