Let's list what moves our promo code box. Each row names the look before, the trigger, who causes it... and the look after.
What moves the box, then? Let's go row by row. From empty, the shopper types a letter. That's a human, and the box goes to typing. From typing, the shopper clears the box, also human, and we're back to empty. Still in typing, the shopper clicks Apply. Human again, and the box goes to checking. Now from checking, two rows. The server accepts the code, that's the computer, and we go to success. Or the server refuses the code, the computer again, and we go to error. And last, from error, the shopper fixes the code and clicks Apply. A human... and we're back in checking.

How the server's answer sets state.
Our mock still gets status from a prop. In Principle four, we will move status into state, with the setter, set status. We will also keep the text of the box in state, as code. For now, just picture that both are already there.
Here is a first look at the handler that Apply will run. It uses the same four JavaScript words as the plain handler of Principle one, from async to catch. But it only calls setters.
Notice what's missing, compared with the plain version. No element is touched at all. This is Promo Code dot jsx, in the components folder. Line one starts an async function, handle submit, that takes the event, e. Line two calls e dot prevent default. Line three calls set status with checking, and the note says, human input, the click. Then a try. Line five awaits check code, with our code. Line six sets status to success, and the note says, computer input, the server said yes. And in the catch, line eight sets status to error. Computer input again... the server said no.
The click and the server's answer are very different events. For React, though, they end the same way. Each one calls a setter, and each setter call asks React to draw the component again.
There's one surprise here. The last two setter calls sit inside the click handler... but they do not run during the click. They run one and a half seconds later. To see why, we need one more fact about async functions. When an async function reaches await, it steps aside, and the browser goes on with other work. The rest of the function waits for the answer.
Let's go through it, in order.
The shopper clicks Apply, and React calls handle submit. Calling set status with checking asks for the checking look. The handler reaches await, and steps aside. The part of the handler that runs on the click is now over. As we saw with batching in Lesson sixteen, React handles state changes after the handler's code has run. So React now draws the checking look... while the rest of the handler is still waiting. One and a half seconds later, the server answers. Nobody clicked anything. On a yes, the handler goes on after await, and asks for the success look. On a no, it jumps into catch, and asks for the error look. And React draws the new look.
So the code after await belongs to a computer input, not to the click. It runs when the answer arrives.
One small trap follows from this. After await, the variable status inside the handler still holds the value from the render that created the handler. We saw this with state snapshots, in Lesson fifteen. So status does not say checking there... even though the page does. After waiting, never read status to decide what to do next. Call the setter for the next look directly, as the handler above does.
A mistake. Planning only for the server's yes.
Say we think only of the happy path. Then we write the handler without try and catch.
The handler again, and shorter now. Prevent default on line two, then set status with checking on line three. Line four awaits check code with our code, and this is the line marked wrong. The note says, a no from the server stops the handler here... and nothing sets the next look. Line five, set status with success, only ever runs on a yes.
The shopper types Welcom, with the E missing, and clicks Apply. One and a half seconds later, the page is still waiting. And it waits... forever.
And there it is, stuck, in figure twenty. The promo code box still holds Welcom, and under it, Checking... The box and the Apply button are both disabled. Below the page, the Console shows a red error. Uncaught, in promise. Error, this code is not valid. That's the page after the server refuses Welcom, with no catch in the handler.
So what went wrong? Step by step.
The click asked for the checking look, and React drew it. The box and Apply turned off. Then the server said no, so the promise failed at await. There was no catch to jump to. So the handler stopped at that line... and the line that asks for the success look never ran. Nothing called a setter, so React never drew another look. The page stays on checking, with the box and Apply off. And because nothing caught the failed promise, the browser reports it in the Console, as an error.
The shopper cannot even fix the typo... because the box is off. The arrow drawing shows the gap at once. The checking look has two arrows out, but this handler builds only one of them. Adding try and catch builds the second arrow, as in the handler of the previous section.
Time for the card of principle three. Triggers, human inputs and computer inputs, both set state. List every trigger that moves the component, both what the user does and what the computer does... and make each one call a setter. We think of clicks and typing first, because we do them ourselves. But the server's answer moves the page too. And a server can say no. If your handler only plans for yes, the first wrong code leaves the page stuck on Checking... The box stays off, so the user cannot even fix the typo. Draw each look as a circle, and each trigger as an arrow, and make sure every look except the last has a way out. The card shows both versions. The one to do wraps the await of check code and set status with success in a try. Then a catch, marked as the second way out of checking, sets status to error. The one not to do just sets checking, awaits check code, and sets success. A refused code stops it right there... and the page stays on checking forever.
