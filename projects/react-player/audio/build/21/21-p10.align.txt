Section four. Principle four. One status... instead of many switches.
Two switches... and four combinations.
Our mock picks its look with one prop, called status. But now the looks have to change while the page runs... so the look has to move into state. Many developers first reach for true or false values, one for each look. A true or false value is also called a boolean. Here's the smallest case, with two of them.
Two lines, two switches. Line one calls use state with false, and gets back is checking, along with its setter, set is checking. Line two does the same for is success, and it starts out false too. One true or false value for each look.
Each value can be true, or false. So together... they can be in four combinations.
Let's walk through all four, one row at a time. Both false? That's the typing look. Is checking true, is success false... that's the checking look. Is checking false, is success true... the success look. And then the last row. Both true. Still checking... and already accepted. Nobody designed this look.
So only three of the four combinations are real looks. The last one matches no look that anyone designed. A combination like that is called an impossible state... and the React docs call it a paradox. Nothing in JavaScript, or in React, stops our code from reaching it. React accepts any values in state... and it prints no warning.
Now compare that with one value... that can hold one of three strings.
Here, there's just one line. Use state starts status at the string typing, and set status is how we change it. The note beside it lists the three strings status may hold: typing, checking, or success.
Status holds exactly one string at a time. So it can be in exactly three looks, one for each string. The fourth combination... cannot even be written down.
Think of a traffic light. It has three lamps, but only one of them is lit at a time. Now picture a light with three separate switches, one for each lamp. Someone could turn on red and green together... and the drivers would not know what to do. One status is the traffic light. Many true or false values... are the three separate switches.
Four switches give sixteen combinations.
And the problem grows fast. Here's the count for our promo code box, step by step.
Take one true or false value. It has two possible values. Each extra true or false value doubles the number of combinations. Our box would need four of them... one each for typing, checking, success, and error. That gives two, times two, times two, times two... which is sixteen combinations. Only four of them are real looks. The other twelve are impossible states. And one status string, with four allowed values? That gives exactly four combinations, one for each look.
The React docs put the goal like this. Each piece of state is a moving piece, and you want as few moving pieces as possible. More complexity leads to more bugs!
Now, a mistake. An error line, on a box that is still off.
Here's how an impossible state reaches a real page. The developer keeps a separate true or false value for checking, for the error, and for success.
Four lines of state, in PromoCode dot jsx, inside the components folder. Line five is code, the text in the box, and it starts as an empty string. Then come three switches, all starting at false: is checking on line six, is error on line seven, and is success on line eight.
The handler turns checking on at the click. And it turns the error on when the server says no.
Now look at line ten. That's the handler, handle submit, an async function that gets the event, e. Line eleven calls e dot prevent default. Line twelve sets is checking to true. Then comes a try. And the note on that line is marked wrong: is checking stays true... so the box stays off.
And the form reads each value on its own.

The shopper types Welcom... welcome with the last E missing, and clicks Apply. After the server's answer... the page looks like this.
Figure twenty-one, and something is off here. In the browser, under the heading Promo code, the box still holds Welcom, with Apply next to it. Under them, Checking... and right below that, the error line, This code is not valid. Both at once. Checking and error are two separate true or false values here, so they show together... and the box and Apply both stay disabled.
Here's what happened, in order.
First, the click set is checking to true, and React drew the checking look. The box and Apply turned off, and Checking appeared under them. Then the server said no, and JavaScript jumped into the catch. The catch set is error to true. But nothing set is checking back to false. So now both values are true. And React draws exactly what the JSX says for that pair... the box off, Apply off, Checking, and the error line.
So the page tells the shopper to fix the code... and at the same time, it does not let the shopper type. The React docs warn about exactly this case. They say: you never want to show an error message and disable the input at the same time, or the user won't be able to correct the error!
With one status, this combination cannot happen. Here's the same moment, with status.
This time, the click sets status to the string checking. The server says no, and the catch part sets status to the string error. The new string replaces the old one. So status now holds error, and nothing else. React draws the error look... and the box works again.
We never have to remember to turn checking off. Setting the next look turns the old one off, by itself.
