The React version is longer than the plain one. The React docs admit it. The React code "is longer than the original imperative example"... but it is "much less fragile".
Here is what less fragile means in practice. Suppose the shop's server could later answer that a code has expired. In React, we add one more value to the list, the string expired. We add one more line of JSX. It shows This code has expired, when status is expired. The other looks do not change at all. The docs say this way of working "lets you later introduce new visual states without breaking existing ones". In the plain version... every handler would need one more hide command for the new line.
Three later lessons go further. Lesson twenty-two covers in full which values should not be state at all. Lesson twenty-seven moves the logic of many looks into a reducer. And Lessons forty-one to forty-four show React nineteen form actions, which give you a waiting flag... without a hand-made status.
And here's the last card. Principle five. Handlers set state. The handler names the next look, and React changes the page. Make each handler call a setter, and nothing else on the page. Let the JSX decide what is turned off, shown, hidden, or styled, for each look. Old habits die hard. You reach for get element by id inside a React handler, because it is quicker, and it seems to work. Then the server says no... and the button stays off forever. You see, React only changes what is different between its last render and its new one, and your hand-made change is not in either of them. So never edit the page behind React's back. Call the setter for the next look, and React will turn things on and off for you. The box shows it in two tiny handlers. The one to follow calls prevent default, then set status with checking, and its note says the JSX for checking turns the box and Apply off. The one to avoid calls prevent default, then get element by id on apply button, and sets disabled to true. Its note says it is wrong... React never turns this button back on.
