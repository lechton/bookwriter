## Authorized Scope
Lesson 05 teaches the component tree. It works on a news page in one file. `App` returns `NewsHeader` and `EditorialFeed`. `EditorialFeed` returns two `ArticleCard` tags. Each `ArticleCard` returns an `EditorialByline`. A component becomes a child of the component whose JSX names it. The file order decides nothing. React starts at `App` and calls each component its parent names, from the top down. One long `App` becomes small components, each with one job. Data can only travel down this tree. A sibling cannot read another sibling's variables. So a value that two siblings need lives in their closest common parent. The parent writes it on each child's tag. The lesson builds on Q02, where a component is a capitalized function used as a tag. It also builds on Q03, where a Fragment groups siblings, and on Q04, where curly braces show a value.

## Principles

### Principle 1: The JSX each component returns builds the tree
- **Handle**: `nesting-makes-tree`
- **Kind**: Model
- **Reader Question**: "I wrote five components in one file. How does React know which goes where?"
- **Reader Expects**: the order of the functions in the file, or of the files in the folder, as a flat list of parts
- **React Does**: `root.render` hands React `<App />`; React calls `App`; `App` returns `<NewsHeader />` and `<EditorialFeed />`, so they become its children; React calls each one; `EditorialFeed` returns two `<ArticleCard />`, two separate nodes; each returns an `<EditorialByline />`, a leaf; React walks down until only HTML tags remain; the order of the function definitions plays no part
- **Placement**: a component goes where a parent's JSX names it; to move a part of the page, move its tag, not its function
- **Real Mistake**: none; the reader's flat picture breaks no code here, and `data-flows-down` shows where it misleads
- **Importance**: interviewers open with it; Q15 and Q24 rest on the tree
- **Prediction**: with one `console.log` per component, and the functions defined in the order `EditorialByline`, `App`, `EditorialFeed`, `NewsHeader`, `ArticleCard`, the console prints `App`, `NewsHeader`, `EditorialFeed`, `ArticleCard`, `EditorialByline`, `ArticleCard`, `EditorialByline`.
- **Required Lesson Proof**: the news page with a log in each component and the functions in a shuffled order: the console order above; the tree drawn beside it, `App` at the top and the two `EditorialByline` leaves at the bottom.

### Principle 2: Split the page into components with one job each
- **Handle**: `split-by-concern`
- **Kind**: Decision
- **Reader Question**: "Why not keep the whole page in `App`? It works."
- **Reader Expects**: one function is simpler; HTML pages are one long file
- **React Does**: the DOM is the same either way, since component tags leave no element of their own; the split changes only the code: each part gets a name, a place in the tree, and one job; a card written once can appear twice
- **Placement**: `App` holds the page's regions; branches such as `EditorialFeed` group parts; leaves such as `EditorialByline` show one piece; a small piece stays inside its parent until it has a job of its own
- **Real Mistake**: none; the long `App` renders the same page, and the cost shows in review and in the next change
- **Importance**: the card's Code Experiment; reviewers flag a 500-line component, and the opposite, a component for every tag
- **Review Point**: Prefer
- **Required Lesson Proof**: the long `App` with the header and two copied article blocks, then the split into `App`, `NewsHeader`, `EditorialFeed`, `ArticleCard`, and `EditorialByline`: the HTML of the page is the same, and the article markup now exists once.

### Principle 3: Data travels down the tree, so a shared value lives in the closest common parent
- **Handle**: `data-flows-down`
- **Kind**: Model
- **Reader Question**: "`NewsHeader` needs the reader's name, and `EditorialFeed` already has it. Can it just read it?"
- **Reader Expects**: yes; the two functions sit in the same file, so a variable in one should be visible in the other; or the header can read the name from the page, as plain JavaScript does
- **React Does**: a variable declared inside a component exists only inside that function; siblings never call each other, so no path links them; React calls every component before it puts any of them on the page, so a DOM lookup during the call finds nothing; the only path runs from a parent to the children its JSX names
- **Placement**: the value in `App`, the closest parent of both; `App` writes it on each child's tag, `<NewsHeader readerName={readerName} />`; the child reads `props.readerName`
- **Real Mistake**: `NewsHeader` shows `{readerName}`, declared inside `EditorialFeed`; the page goes blank, and the console shows "readerName is not defined" (`ReferenceError`); the DOM version, `document.getElementById('reader-name').textContent`, fails with "Cannot read properties of null (reading 'textContent')"; verified in React 19.3.0
- **Fix In**: this principle
- **Importance**: the second half of the interview question; the card's Friction; every later lesson on props, lifting state, and context starts here
- **Prediction**: with `readerName` declared in `App` and written on both tags, both "Welcome back, Elena" and "Picked for Elena" appear; declared inside `EditorialFeed`, the page goes blank.
- **Required Lesson Proof**: the news page with `readerName` inside `EditorialFeed` and `NewsHeader` showing it: the blank page and the `ReferenceError`; the tree shows that the only path between the siblings runs through `App`; the value moves to `App`, which writes it on both tags, and both lines show "Elena".

## Senior Answer
React builds a tree from the JSX each component returns. `App` is the root. Any component that `App` names in its JSX becomes its child, and so on down to the leaves. The order of the functions in the file plays no part. React calls `App` first, then each component its parent names, until only HTML tags remain. So I split a long page into small components, each with one job. Regions sit at the top, groups in the middle, and small pieces at the leaves. Hierarchy dictates data flow because data can only travel down this tree. A parent hands values to the children it names, on their tags. Siblings never call each other, so one sibling cannot read another's variables. Reading the page does not work either, because React calls every component before it shows any of them. So a value two siblings need lives in their closest common parent, and travels down to each of them.
