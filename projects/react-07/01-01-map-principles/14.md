## Authorized Scope
Lesson 14 teaches how a component remembers a value. It works on one component, `StoryCard`, which shows a like count and a Save button. Changing a local variable tells React nothing, so the screen stays the same. `useState` keeps a value inside React. It returns the value and a setter function. The setter stores the next value and asks React to render the component again. Each render calls the component function from the top. So a local variable starts over every time. `useState` hands back the stored value instead of the start value. A component can keep several values, and React tells them apart by the order of the calls. Each `StoryCard` on the page keeps its own values. The start value counts only on the first render. A start value that is slow to compute goes in as a function. The lesson builds on Q04, curly braces in JSX, Q12, pure rendering, and Q13, event handlers.

## Theme and Options
- **Theme**: How does a component remember something the user did, such as a like count, and show it on the screen?
- **Options**: none (starting point: the component shows values from local variables and props, Q04 and Q06, and a click runs a handler, Q13)
- **This lesson teaches**: state, a value React keeps for the component between renders, declared with `useState`

## Principles

### Principle 1: Changing a variable does not ask React to update the screen
- **Handle**: `assignment-renders-nothing`
- **Kind**: Model
- **Reader Question**: "I add 1 to `likes` on every click, and the console counts 1, 2, 3. Why does the screen still say 0 likes?"
- **Reader Expects**: changing the variable changes the screen, since `{likes}` in the JSX shows the variable; a habit from spreadsheets, where a cell follows the value, and from Svelte and Vue, where an assignment updates the page
- **React Does**: the click runs the handler; `likes` becomes 1 in memory; React is not told; React updates the screen only when it renders the component again, and nothing asked for a render; the screen keeps the JSX of the first render, `0 likes`, while the console shows 1, 2, 3
- **Placement**: a value that must change the screen when it changes cannot live in a plain local variable
- **Real Mistake**: `let likes = 0` in `StoryCard`, and `likes = likes + 1` in the Like handler with a log; three clicks log `clicked, likes = 1`, `2`, `3` while the screen shows `0 likes`; verified in React 19.3.0
- **Fix In**: `state-pair`
- **Importance**: the bank row's scenario and the card's Friction; the stuck counter every newcomer ships
- **Prediction**: with `let likes = 0` and a log in the body and in the handler, the body logs once on load, each click logs a higher number, the body never logs again, and the screen stays at `0 likes`.
- **Required Lesson Proof**: `StoryCard` with `let likes = 0`, a body log, and a Like handler that adds one and logs it; three clicks log `1`, `2`, `3`, no second body log appears, and the screen shows `0 likes`.

### Principle 2: Keep the value in state and change it with its setter
- **Handle**: `state-pair`
- **Kind**: Decision
- **Reader Question**: "How do I keep the like count, and get the screen to show the new number when it changes?"
- **Reader Expects**: there must be a way to tell React the value changed; once `likes` comes from `useState`, writing `likes = likes + 1` should still work, as it does for any variable
- **React Does**: `useState(0)` returns a pair, the value for this render and a setter; `setLikes(likes + 1)` stores the next value inside React and asks React to render `StoryCard` again; on that render `useState` returns `1`, and the screen shows `1 likes`; assigning to `likes` changes only the local copy, and with `const` it throws
- **Placement**: `import { useState } from 'react'`; `const [likes, setLikes] = useState(0)` at the top of `StoryCard`; the handler calls `setLikes(likes + 1)`; never assign to `likes`; a value used only inside one handler stays a plain variable
- **Real Mistake**: `const [likes, setLikes] = useState(0)` with `likes = likes + 1` in the handler, out of the habit of changing variables directly; the click throws "Assignment to constant variable." and the screen stays at `0 likes`; with `let [likes, setLikes]` there is no error and the screen still stays at `0 likes`; verified in React 19.3.0
- **Importance**: the card's main subject; every later state lesson starts from this pair
- **Review Point**: Do
- **Required Lesson Proof**: `StoryCard` with `const [likes, setLikes] = useState(0)` and a Like button that calls `setLikes(likes + 1)`; three clicks show `3 likes`, and a body log prints `0`, `1`, `2`, `3`; the same card with `likes = likes + 1` throws "Assignment to constant variable." on the click.

### Principle 3: Every render runs the component from the top, so local variables start over
- **Handle**: `fresh-each-render`
- **Kind**: Model
- **Reader Question**: "The Save button is state now, but the like count is still a `let`. After I click Save, why does the next Like start from 1 again?"
- **Reader Expects**: the component is like an object that keeps its variables between uses; a habit from class fields, and from a closure that keeps a counter alive
- **React Does**: `setIsBookmarked` asks for a render; React calls `StoryCard` again, from its first line; `let likes = 0` runs again and makes a new variable; the count from the earlier clicks belonged to the earlier call and is gone; the body logs `likes = 0`, and the next Like logs `1`
- **Placement**: a value that must outlive one render goes in state; a local variable holds only what this render computes, such as text built from props and state
- **Real Mistake**: `StoryCard` with `const [isBookmarked, setIsBookmarked] = useState(false)` for Save and `let likes = 0` for the count, out of the habit that a variable keeps its value; two Likes log `1` and `2`, Save logs `StoryCard renders, likes = 0`, and the next Like logs `1`; verified in React 19.3.0
- **Fix In**: this principle
- **Importance**: the first half of the interview question: why ordinary variables forget
- **Prediction**: with a body log, every Save click prints `StoryCard renders, likes = 0`, whatever the earlier Like clicks counted.
- **Required Lesson Proof**: `StoryCard` with `isBookmarked` in state and `let likes = 0`; Like, Like, Save, Like logs `1`, `2`, the body log with `likes = 0`, then `1`; the fix moves `likes` into `useState(0)`, and the count survives the Save click.

### Principle 4: React keeps the state and hands it back on every render, in call order
- **Handle**: `state-lives-in-react`
- **Kind**: Model
- **Reader Question**: "`useState(0)` runs again on every render. Why does `likes` not go back to 0 like `let likes = 0` does?"
- **Reader Expects**: `useState(0)` sets `likes` to 0 each time it runs, as a plain assignment would
- **React Does**: on the first render React stores `0` for this card; on each later render the `0` is ignored, and `useState` returns the value React stored last; with two calls, `likes` first and `isBookmarked` second, React matches each call to its stored value by its place in the order; the body logs `likes = 0`, `1`, `2`, and `isBookmarked` changes only when Save is clicked
- **Placement**: state lives in React, not in the function; each `useState` call gets its own value, matched by call order
- **Real Mistake**: none; the wrong guess leads to no code a reader writes here, and breaking the order is Q37's
- **Importance**: the second half of the interview question: how `useState` remembers; Q37 builds on the call order
- **Prediction**: with `useState(0)` for `likes`, `useState(false)` for `isBookmarked`, and a body log of both, Like, Like, Save logs `0 false`, `1 false`, `2 false`, `2 true`.
- **Required Lesson Proof**: `StoryCard` with both `useState` calls and one body log of both values; Like, Like, Save logs `likes = 0, isBookmarked = false`, then `1 false`, `2 false`, `2 true`, and the screen shows `2 likes` and `Saved`.

### Principle 5: Each card on the page keeps its own state
- **Handle**: `state-per-instance`
- **Kind**: Model
- **Reader Question**: "I show two `StoryCard`s. If I click Like on the first one, does the second one count up too?"
- **Reader Expects**: one function means one count, so both cards share it; a habit from module-level variables (Q12), which every use shares; or a beginner moves `let likes` above the component so it stops starting over
- **React Does**: React keeps state for each card rendered on the page, not for the function in the code; two `<StoryCard />` elements get two separate counts; two Likes on the first show `2 likes` beside `0 likes`; the parent `App` does not render again and cannot read either count
- **Placement**: `useState` inside `StoryCard` gives each card its own count; a variable above the component is shared by every card and still asks for no render
- **Real Mistake**: `let likes = 0` moved above `StoryCard` so that it survives renders; three Likes on the first card leave both cards at `0 likes`; a Save click on the second card renders it, and it shows `3 likes` while the first still shows `0 likes`; verified in React 19.3.0
- **Fix In**: this principle
- **Importance**: the card's second `StoryCard`; interviewers ask why two cards do not share a count; the module-level fix is the workaround reviewers flag
- **Prediction**: two `StoryCard`s with their own `useState(0)`; two Likes on the first show `2 likes` and `0 likes`, and a log in `App` prints only on load.
- **Required Lesson Proof**: `App` renders two `StoryCard`s with different titles; two Likes on the first show `2 likes` beside `0 likes`, and the `App` log prints once; the module-level version shows `0 likes` on both, then `3 likes` on the second after its Save.

### Principle 6: Pass a slow start value as a function, so React runs it once
- **Handle**: `initial-value-once`
- **Kind**: Decision
- **Reader Question**: "I read the saved like count with `useState(readSavedLikes(story.id))`. Why does `readSavedLikes` run again on every click?"
- **Reader Expects**: React uses the start value only once, so the code inside the parentheses runs only once
- **React Does**: the body runs on every render, so JavaScript calls `readSavedLikes(story.id)` every time, before `useState` sees the result; React ignores that result after the first render; given a function, `useState(() => readSavedLikes(story.id))`, React calls it only on the first render; under `StrictMode`, in development, React calls it twice on that render and keeps one result
- **Placement**: a plain value or a quick expression goes in directly, `useState(0)`; a start value that reads saved data or builds a large list goes in as a function, `useState(() => readSavedLikes(story.id))` or `useState(createInitialItems)`; to keep a function itself in state, wrap it, `useState(() => formatLikes)`
- **Real Mistake**: `useState(readSavedLikes(story.id))`; a log inside `readSavedLikes` prints on load and again on every Like click, while the count still starts from the saved `12`; verified in React 19.3.0
- **Importance**: named in the card's Mechanism; reviewers flag a slow start value computed on every render
- **Review Point**: Prefer
- **Required Lesson Proof**: `StoryCard` whose start value comes from `readSavedLikes`, which logs; with the call, three Likes give four logs and `15 likes`; with the function, one log and the same `15 likes`.

### Principle 7: Call the setter in a handler, never while the component renders
- **Handle**: `setter-in-handler`
- **Kind**: Decision
- **Reader Question**: "I wrote `onClick={setLikes(likes + 1)}`. Why does the page crash with 'Too many re-renders' before I click anything?"
- **Reader Expects**: `onClick` holds code to run later, as `onclick="..."` does in HTML
- **React Does**: braces run their code during render (Q04 `runs-during-render`), so `setLikes(likes + 1)` runs right then; it asks for another render; that render calls the setter again; React stops after many rounds and throws "Too many re-renders. React limits the number of renders to prevent an infinite loop."; the card never appears
- **Placement**: pass a function that calls the setter: `onClick={() => setLikes(likes + 1)}`, or `onClick={handleLike}` with the setter inside `handleLike`; never a setter call, and never `handleLike()`, in the braces
- **Real Mistake**: `<button onClick={setLikes(likes + 1)}>Like</button>`; the page throws "Too many re-renders. React limits the number of renders to prevent an infinite loop." on load and shows nothing; `onClick={handleLike()}` with the setter inside throws the same; verified in React 19.3.0
- **Importance**: Q13 recalls passing against calling; with a setter the same slip crashes the page, the most common useState error
- **Review Point**: Do not
- **Required Lesson Proof**: `StoryCard` with `onClick={setLikes(likes + 1)}`: the body log counts up during load and the error above stops it, with an empty page; with `onClick={() => setLikes(likes + 1)}`: the card shows `0 likes`, and each click adds one.

## Senior Answer
A local variable lives for one call of the component function. React calls that function again on every render, so the variable starts over each time. Changing it also tells React nothing, so the screen does not change. `useState` fixes both problems. React keeps the value outside the function, for this component on the page. On each render, `useState` hands back the stored value, not the start value. The setter stores the next value and asks React to render again. A component can have several state variables, and React tells them apart by the order of the calls. Each copy of the component keeps its own state. The start value counts only on the first render, so a slow one goes in as a function. And I call the setter from an event handler, never while rendering, or React throws "Too many re-renders".
