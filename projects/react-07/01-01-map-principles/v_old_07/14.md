## Authorized Scope
Lesson 14 teaches component memory with `useState`. It works on one component, `StoryCard`, which shows a like count and a bookmark button. Assigning a local variable tells React nothing, so the screen stays the same. React calls the component function again for every render. Each call starts its local variables over. `useState` keeps a value inside React between renders. It returns that value and a setter. The setter stores the next value and asks React to render again. React tells the `useState` calls apart by their order. Each rendered `StoryCard` keeps its own state. The argument of `useState` counts only on the first render. An expensive start value goes in as an initializer function. The lesson builds on Q04, curly braces in JSX, and Q13, event handlers.

## Principles

### Principle 1: Assigning a variable asks React for nothing
- **Handle**: `assignment-renders-nothing`
- **Kind**: Model
- **Placement**: the screen changes only after React renders again; an assignment alone never causes that
- **Mechanism**: React renders when it is asked to; a plain assignment changes memory React does not watch
- **Tempting Belief**: changing the variable changes the screen; a habit from Svelte and Vue, where an assignment updates the page, and from spreadsheets
- **Defect**: the Like button logs `clicked, likes = 1`, `2`, `3`, while the screen still shows `0 likes`
- **Importance**: the card's Friction; the stuck counter every newcomer ships
- **Prediction**: with `let likes = 0` and `likes = likes + 1` in the Like handler, the console counts up on each click and the screen never changes.
- **Required Lesson Proof**: `StoryCard` with `let likes = 0` and a Like button whose handler adds one and logs it; three clicks log `1`, `2`, `3` while the screen shows `0 likes`.

### Principle 2: Each render calls the function again, and local variables start over
- **Handle**: `fresh-each-render`
- **Kind**: Model
- **Placement**: nothing declared in the body survives to the next render
- **Mechanism**: a component is a function; every call runs the body from the top, so `let likes = 0` runs again
- **Tempting Belief**: a component is an object that keeps its fields between uses; a habit from classes, and from closures that keep a counter alive
- **Defect**: after the Save button re-renders the card, the console logs `render, likes = 0`, and the next Like click logs `clicked, likes = 1` again
- **Importance**: the first half of the interview question; without it, the reader cannot see why state must live elsewhere
- **Prediction**: a `console.log` in the body prints `render, likes = 0` on every render, whatever the Like clicks did before.
- **Required Lesson Proof**: the `StoryCard` of Principle 1 also has a Save button backed by `isBookmarked` state; the lesson supplies it ready-made and explains it in Principle 3; three Like clicks, then Save, then Like log `1`, `2`, `3`, `render, likes = 0`, `1`.

### Principle 3: Keep what must survive and show on screen in state, and change it with the setter
- **Handle**: `state-pair`
- **Kind**: Decision
- **Placement**: `const [likes, setLikes] = useState(0)` at the top of `StoryCard`; `setLikes(likes + 1)` in the Like handler; a value used only inside one handler stays a regular variable
- **Mechanism**: the setter writes the value into React's memory for this component and queues a render, in which `useState` returns the new value
- **Tempting Belief**: the state variable is a variable like any other, so `likes = likes + 1` updates it; or a variable moved above the component keeps its value, so it is enough
- **Defect**: `likes = likes + 1` on the state variable throws "Assignment to constant variable."; a module-level `let likes` shows `3 likes` on one card only after something re-renders it, while the other card still shows `0 likes`
- **Importance**: the card's main subject; reviewers flag a module-level variable used as component memory
- **Review Point**: Do
- **Required Lesson Proof**: `StoryCard` with `const [likes, setLikes] = useState(0)` and `onClick={() => setLikes(likes + 1)}`; two clicks show `1 likes`, then `2 likes`, and the body logs `render, likes = 0`, `1`, `2`; the module-level version shows two cards out of step.

### Principle 4: React keeps state outside the function and returns it by call order
- **Handle**: `state-lives-in-react`
- **Kind**: Model
- **Placement**: every `useState` call at the top level of the body, in the same order on every render
- **Mechanism**: on the first render, React stores each initial value; on later renders, each `useState` call takes the next stored value, matched by its position in the order
- **Tempting Belief**: `useState(0)` sets `likes` to `0` every time it runs, as a plain assignment would
- **Defect**: the body passes `0` on every render, yet the screen shows `2 likes`
- **Importance**: the second half of the interview question: how `useState` remembers
- **Prediction**: logging the results of `useState(0)` and `useState(false)` in `StoryCard` prints `0, false`, then `1, false` after Like, then `1, true` after Save; each call keeps its own value.
- **Required Lesson Proof**: `StoryCard` with `likes` and `isBookmarked`, logging both values in the body; Like, then Save, gives the three log lines above.

### Principle 5: Each rendered StoryCard keeps its own state
- **Handle**: `state-per-instance`
- **Kind**: Model
- **Placement**: two `<StoryCard />` elements side by side, each with its own `likes`
- **Mechanism**: React stores state for each rendered component in the tree, not for the function in the code
- **Tempting Belief**: state belongs to the function, so every card that uses it shares one count; a habit from module-level variables, which are shared
- **Defect**: two clicks on the first card show `2 likes` beside `0 likes`
- **Importance**: the card's Code Experiment; interviewers ask why two instances do not share state
- **Prediction**: clicking Like on one `StoryCard` changes only that card; the other stays `0 likes`, and the parent cannot read either count.
- **Required Lesson Proof**: an `App` renders two `StoryCard` elements; two clicks on the first show `2 likes` and `0 likes`; the module-level version of Principle 3 is the contrast.

### Principle 6: The useState argument counts once, so pass an expensive start value as a function
- **Handle**: `initial-value-once`
- **Kind**: Decision
- **Placement**: `useState(createInitialLikes)`, the function itself, not `useState(createInitialLikes())`, its result; a plain value is fine when it is cheap
- **Mechanism**: the argument expression is evaluated on every render, because the body runs every time; React ignores the result after the first render, but only a function reference lets it skip the work
- **Tempting Belief**: the argument runs only once, because React uses it only once
- **Defect**: a log in `createInitialLikes` prints on every Like click with `useState(createInitialLikes())`, and once with `useState(createInitialLikes)`
- **Importance**: named in the card's Mechanism; reviewers flag an expensive call in the argument
- **Review Point**: Prefer
- **Required Lesson Proof**: `StoryCard` with `createInitialLikes` returning `10` and logging; two Like clicks print the log three times with the call and once with the function; under `StrictMode` the initializer logs twice on the first render.

### Principle 7: Call the setter from a handler, never while the component renders
- **Handle**: `setter-in-handler`
- **Kind**: Decision
- **Placement**: `onClick={() => setLikes(likes + 1)}` or `onClick={handleLike}`; not `onClick={setLikes(likes + 1)}`, and not a setter call in the body
- **Mechanism**: code in braces runs during render (Q04 `runs-during-render`); a setter called there asks for another render, which calls it again, and React stops the loop
- **Tempting Belief**: `onClick={setLikes(likes + 1)}` hands the update to the button for later; a habit from HTML, where `onclick="..."` stores code that runs on the click
- **Defect**: the render throws "Too many re-renders. React limits the number of renders to prevent an infinite loop." and the card never appears
- **Importance**: the first Troubleshooting entry on the useState page; a crash newcomers ship and interviewers ask about; Q13 cannot show it, because it has no setter
- **Review Point**: Do not
- **Required Lesson Proof**: the Like button of `StoryCard` written as `onClick={setLikes(likes + 1)}`; the render throws "Too many re-renders..." and nothing appears; the arrow function version shows `0 likes` and counts on each click.

## Senior Answer
A component is a function, and React calls it again for every render. Each call starts its local variables over. Assigning one also tells React nothing, so the screen stays the same. `useState` fixes both problems. It keeps the value inside React, outside the function. It returns that value with a setter. Calling the setter stores the next value and asks React to render again. On that render, `useState` returns the new value, even though the code still passes the old initial value. React tells several `useState` calls apart by their order, so they stay at the top level. State belongs to each rendered instance. Two cards side by side keep separate counts, and their parent cannot read them. The argument matters only on the first render. If the start value is expensive, I pass a function, and React calls it once. I call the setter only from a handler. Called during render, it throws "Too many re-renders."
