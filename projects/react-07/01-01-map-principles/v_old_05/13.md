# Q13: Responding to Events and Callback Props — Operational Principle Map
- **Source Map**: `01-01-map/13.md`
- **Topic Tag**: `#event_handling` | `❱ CORE`
- **Interview Question**: *How do you respond to user events like clicks and typing, and how do callback props communicate back to parents?*

## Authorized Scope
Q13 teaches attaching event handlers in JSX and passing them through props: a handler is a function passed (not called) to a camelCase event prop such as `onClick`, an inline arrow function supplies arguments (`onClick={() => handleSelect(article.id)}`), a parent hands behavior to a child through an `on`-prefixed prop such as `onSelect`, the child wires that prop to a real browser element, and clickable controls are real `<button>` elements; handlers only log or call functions, because state is not available yet; it builds on Q04 curly braces, Q06 props, and Q12 (handlers do not run during render), and it excludes callback contract design across deep trees (Q47), state (Q14), and root-level event delegation (Q79); the event object, propagation, and default actions are named in this lesson's card and are explained here as support.

## Principles

### Principle 1: Pass the handler, never call it
- **Kind**: Decision
- **Rule**: Give an event prop a function value (`onClick={handlePublish}`) so React can call it when the user clicks, and when the handler needs arguments, pass a new function that makes the call (`onClick={() => openArticle(article.id)}`), because anything written inside JSX curly braces runs immediately during render.
- **Importance**: `onClick={handlePublish()}` publishes on page load and then does nothing on click, `onClick={openArticle(id)}` opens every article while the list renders, and a string such as `onClick="handlePublish()"` logs "Expected `onClick` listener to be a function, instead got a value of `string` type."
- **Review Point — Do not**: Do not put parentheses after a handler in an event prop or pass a string; pass the function, or wrap the call in an arrow function when it needs arguments.
- **Required Lesson Proof**: Render the Publish button with `onClick={handlePublish()}` and show "PUBLISH ran" in the console on load with no log on click, then remove the parentheses and show the log only on click; repeat with `openArticle('a1')` and the arrow form.
- **Sources**: Friction, Under the Hood, and Code Experiment of `01-01-map/13.md`; responding-to-events Pitfall, Recap bullet 2, and Challenge "Fix an event handler"; the merged candidates, verified in React 19.3.

### Principle 2: Hand behavior to a child through an `on` prop and wire it to a real element
- **Kind**: Decision
- **Rule**: When the parent decides what a click means, pass a function through a prop named for the app action (`<ArticleCard onSelect={handleSelect} />`) and, inside the child, pass that prop to a built-in element's event prop (`<button onClick={() => onSelect(id)}>`), because only built-in elements turn browser events into handler calls; a custom component ignores props it does not use.
- **Importance**: `<ArticleCard onClick={...} />` looks wired but does nothing when `ArticleCard` never passes `onClick` to an element, and components that hardcode their behavior cannot be reused on another page.
- **Review Point — Do**: Check that every handler prop starts with `on` followed by a capital letter, is named for what it means in the app, and reaches a built-in element's event prop inside the child.
- **Required Lesson Proof**: Pass `onClick` to an `ArticleCard` that ignores it and show that a click logs nothing, then rename it `onSelect`, wire it to the card's `<button>`, and show `NewsFeed`'s handler logging the selected article's ID.
- **Sources**: Core Truth and Code Experiment of `01-01-map/13.md`; responding-to-events "Passing event handlers as props" and "Naming event handler props", Recap bullets 5 and 6; the merged ignored-prop candidate, verified in React 19.3; the merged inverse-data-flow candidate.

### Principle 3: Make click targets real buttons
- **Kind**: Decision
- **Rule**: Attach click handlers to `<button>` elements (or links for navigation), not to `<div>` or `<span>`, because the browser gives a button keyboard focus and activation with Enter and Space, while a clickable `<div>` responds only to a mouse.
- **Importance**: A "Bookmark" control built as `<div onClick>` cannot be reached with Tab or triggered from the keyboard, a failure every accessibility review flags and many users hit.
- **Review Point — Do**: Check that every element with an `onClick` handler is a `<button>` (restyled if needed) or a link, and never a plain `<div>` or `<span>`.
- **Required Lesson Proof**: Render the Bookmark control once as `<div onClick>` and once as `<button onClick>`, press Tab and Enter, and show that only the button receives focus and runs the handler.
- **Sources**: responding-to-events Note on appropriate HTML tags, merged with its restyling advice.

## Senior Answer
I respond to events by passing a function to a camelCase event prop, `onClick={handlePublish}`, never calling it there, because anything inside JSX braces runs during render: `onClick={handlePublish()}` would publish on page load and do nothing on click. When the handler needs an argument, I pass a new function that makes the call, `onClick={() => openArticle(article.id)}`. To let a parent decide what a child's click means, I pass a function through a prop named for the app action, such as `<ArticleCard onSelect={handleSelect} />`, and the child wires it to a built-in element with `<button onClick={() => onSelect(id)}>`; that callback is how a child reports back to the parent without touching the parent's data, and the parent keeps the authority to decide what happens. I attach click handlers to real buttons so keyboard users can reach them, and when a click inside a child must not also reach the parent, or must not trigger the browser's default action, I call `e.stopPropagation()` or `e.preventDefault()` on the event object React passes to the handler.
