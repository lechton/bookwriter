## Authorized Scope
Lesson 12 works on `ArticleCard` in the homepage feed. A pure component is like a formula. For the same props it returns the same JSX, and it changes nothing that existed before it ran. React may call a component on every render, twice in development under `StrictMode`, and in any order. So a component that writes to a variable outside itself shows different numbers each time it runs. Values the component creates during this render are its own, and it may change them freely. Changes to the outside world, such as the DOM, timers, and analytics, do not belong in the render. They go in event handlers, which Q13 teaches. Calls that give a new result each time, such as `Math.random()` and `new Date()`, break the formula too. The lesson builds on Q06, where props were read-only, and on Q04, where `StrictMode` first called a component twice.

## Principles

### Principle 1: React may call a component any number of times, so the same props must give the same JSX
- **Handle**: `same-props-same-jsx`
- **Kind**: Model
- **Reader Question**: "My cards show reader #1, #2, #3 at first, then #4, #5, #6. Why?"
- **Reader Expects**: the component runs once per card, like a template filled in once
- **React Does**: React calls the component function every time it renders the card: on the first render, on every later render, and twice in development under `StrictMode`; it does not promise an order; a component that changes a module-level variable gets a different result on every call, and the page shows the last one
- **Placement**: everything the card shows comes from its props and from values it creates while it runs: `function ArticleCard({ title, position })` returning `<li>{title}, reader #{position}</li>`
- **Real Mistake**: `let readCount = 0` at the top of the file and `readCount = readCount + 1` in `ArticleCard`; the first render shows #1, #2, #3, a second `root.render` shows #4, #5, #6, and under `StrictMode` the first render already shows #2, #4, #6; verified in React 19.3.0
- **Fix In**: `change-only-local`
- **Importance**: the first part of the interview question; the bank row's scenario; Q14 to Q18 recall it
- **Prediction**: a `console.log('render ArticleCard')` in the body prints twice per card under `StrictMode`; the version with a `position` prop shows #1, #2, #3 on every render, however often React calls it.
- **Required Lesson Proof**: the three cards with the module-level counter, rendered twice without `StrictMode`, then once with it; the log printed twice; the `position` version, with the same output every time.

### Principle 2: Change only what this render created
- **Handle**: `change-only-local`
- **Kind**: Decision
- **Reader Question**: "Can I push into an array, or change an object, during render?"
- **Reader Expects**: changing data is normal JavaScript, and the component owns whatever it can reach
- **React Does**: a value that existed before the render, a module-level array, a prop, or an object shared with another card, keeps every change, so the next call starts from changed data and adds again; a value created inside the component is new on every call, so changing it before the `return` is safe; a value passed to JSX and changed afterward still shows the change
- **Placement**: create the array or object inside the component, then fill it: `const items = []; items.push(...)`; or build a new one with `map`, `filter`, or `slice`; leave props and shared data as they are
- **Real Mistake**: `headlines.push('Editor picks')` in the component, on an array declared at the top of the file; under `StrictMode` the list shows "Editor picks" twice on the first render, and without it one more copy after each render; verified in React 19.3.0
- **Importance**: the second part of the interview question; reviewers flag `push` and `sort` on shared data; map 18 recalls it
- **Review Point**: Do not
- **Required Lesson Proof**: the editor's picks with the module-level array: the doubled item; the array created inside the component: one item on every render; `styles.size = 'small'` after `<Header styles={styles} />`: the header shows `class="small"`.

### Principle 3: Keep changes to the outside world out of the render
- **Handle**: `effects-outside-render`
- **Kind**: Decision
- **Reader Question**: "Where do I set the page title, or put a class on an element?"
- **Reader Expects**: in the component, since it runs whenever the article shows, as a script would after loading
- **React Does**: the component runs before its elements exist in the page, and may run again without any change on screen; DOM writes, timers, network requests, and analytics in the body run on every call, or fail because their target is missing; event handlers do not run during render, so they are where such changes go
- **Placement**: what the user sees goes in the returned JSX, as in `className={isNight ? 'night' : 'day'}`; changes caused by an action go in an event handler (Q13); `useEffect` is a last resort (Q31)
- **Real Mistake**: `document.getElementById('time').className = 'night'` in the component; the first render throws "Cannot set properties of null (setting 'className')", and the page is blank; verified in React 19.3.0
- **Importance**: Recap bullet 4; reviewers flag DOM writes in a component; maps 15 and 17 recall it
- **Review Point**: Do not
- **Required Lesson Proof**: the clock with the `className` line: the error; with the class in JSX: the page; `document.title = article.title` in the body: the title changes during render, against the same line in a click handler.

### Principle 4: Do not compute what you show from `Math.random()` or `new Date()` during render
- **Handle**: `no-random-in-render`
- **Kind**: Decision
- **Reader Question**: "Can I show a random 'editor's pick', or the current time?"
- **Reader Expects**: each render picks a fresh value, and that is the point
- **React Does**: each call gives a new result, so two calls of the same component disagree; under `StrictMode` React calls the component twice and shows the second result; a time read during render stays fixed at that render
- **Placement**: pick the value in an event handler, or receive it as a prop from data that already holds it; never call `Math.random()` or `new Date()` for output in the body
- **Real Mistake**: `const pick = Math.random()` in the body; under `StrictMode` the two calls log `0.133` and `0.123`, and the screen shows `0.123`, not the first value logged; verified in React 19.3.0
- **Importance**: the "same output" half of the definition; a key or a pick that changes on every render
- **Review Point**: Avoid
- **Required Lesson Proof**: the editor's pick with `Math.random()` under `StrictMode`: two different logged values and the second one on screen; the pick passed in as a prop: one value everywhere.

## Senior Answer
A pure component works like a formula. For the same props it returns the same JSX, and it changes nothing that existed before it ran. React may call a component many times, in any order, and in development `StrictMode` calls it twice on purpose. So a component that bumps a module-level counter shows different numbers on each render. Pushing into a shared array duplicates items. Values I create inside the component are mine, so changing them before the `return` is fine. Changes to the outside world, like the DOM, timers, or analytics, do not belong in the render. I express what the user sees in JSX, and I put actions in event handlers. I also avoid `Math.random()` and `new Date()` in output, because two calls give two answers. Purity is what lets React re-run, skip, or restart a render safely.
