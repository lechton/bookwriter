## Authorized Scope
Lesson 11 builds the homepage feed of The National Times: an array of stories becomes a row for each. The array method `map()` turns each story object into a JSX element. Braces place the resulting array in the `<ul>`. React renders the array in order. Every element made directly inside `map()` needs a `key`, unique among its siblings. React uses the key to match each row with the same story on the next render. Without keys, or with the array index, it matches rows by position. Then an urgent story added at the top takes over the first row, along with any text typed into it. A stable ID from the data, `key={story.id}`, keeps each row with its story. The key is for React only, so the row never receives it as a prop. The lesson builds on Q04, where braces held an array of elements. It also builds on Q06, where each row receives its story through props.

## Principles

### Principle 1: `map()` turns an array of stories into an array of elements
- **Handle**: `map-to-elements`
- **Kind**: Model
- **Reader Question**: "I have thirty headlines in an array. How do I get a row for each?"
- **Reader Expects**: a loop inside the JSX, like the `for` of a template language
- **React Does**: `stories.map(story => <li>{story.title}</li>)` calls the arrow function once per story and collects what it returns into a new array of elements; braces place that array in the `<ul>`; React renders the elements in array order; an arrow function whose body starts with `{` returns nothing unless it says `return`
- **Placement**: `<ul>{stories.map(story => <li key={story.id}>{story.title}</li>)}</ul>`, or the array built in a variable above the `return`; with a block body, `stories.map(story => { return <li ...>; })`
- **Real Mistake**: `stories.map(story => { <li>{story.title}</li> })`; the arrow function returns `undefined` for every story, and the `<ul>` renders empty with no warning; verified in React 19.3.0
- **Fix In**: this principle
- **Importance**: the first part of the interview question; an empty list with a clean console is the hardest bug to find here
- **Prediction**: `console.log(items[0])` for the mapped array shows a plain object with `type: 'li'`, `key: 's1'`, and `props: { children: 'Budget passes' }`.
- **Required Lesson Proof**: the feed with a block body and no `return`: the empty `<ul>`, and nothing in the console; with `return`, or with no braces: three rows; the logged first element.

### Principle 2: Put the key on the element written inside `map()`
- **Handle**: `key-on-mapped-element`
- **Kind**: Decision
- **Reader Question**: "The console says each child needs a key. Where does it go?"
- **Reader Expects**: on the outer HTML element of each row, such as the `<li>`, wherever it is written
- **React Does**: React checks the keys of the elements in the array, the ones `map()` returns; when `map()` returns `<StoryRow />`, the key must be on `<StoryRow />`; a key on the `<li>` inside `StoryRow` sits in a different place and does not count; keys must be unique among siblings
- **Placement**: `stories.map(story => <StoryRow key={story.id} story={story} />)`; for a story with several nodes, `<Fragment key={story.id}>`; the key written directly on the element, never inside a spread object
- **Real Mistake**: `StoryRow` returns `<li key={story.id}>`, and `Feed` maps to `<StoryRow story={story} />`; the console shows "Each child in a list should have a unique "key" prop." with "Check the render method of `Feed`."; verified in React 19.3.0
- **Importance**: the warning in the bank row's scenario; reviewers flag misplaced keys
- **Review Point**: Do
- **Required Lesson Proof**: the feed with no key: the warning; the key on the inner `<li>`: the same warning, naming `Feed`; the key on `<StoryRow>`: a clean console; two stories with the same id: the duplicate-key error.

### Principle 3: The key is how React finds the same row on the next render
- **Handle**: `keys-are-identity`
- **Kind**: Model
- **Reader Question**: "The list looks right without keys. What does the key do?"
- **Reader Expects**: nothing visible; keys are a rule to silence the console
- **React Does**: on the next render, React matches each new element to an old one with the same key and keeps its DOM node, with whatever the reader typed in it; without keys, or with `key={index}`, it matches by position, so the first new element reuses the first old row; a story prepended at the top takes over the first row and its typed text, while every other row gets new text
- **Placement**: the key comes from the story itself, so it travels with the story wherever it moves in the array
- **Real Mistake**: `stories.map((story, index) => <li key={index}>{story.title} <input /></li>)`; the reader types "fix typo in Budget" into the Budget row, an urgent story is prepended, and the page shows `URGENT: Election called [fix typo in Budget]`; verified in React 19.3.0
- **Fix In**: `stable-id-key`
- **Importance**: the second part of the interview question; the card's Friction: corrections land on the wrong story
- **Prediction**: with `key={story.id}`, the same steps show `URGENT: Election called []` and `Budget passes [fix typo in Budget]`; with no key, they show the same result as `key={index}`.
- **Required Lesson Proof**: the feed with an `<input>` in each row, rendered, typed into, and rendered again by `root.render` with the urgent story first; the rows with index keys against the rows with id keys.

### Principle 4: Use a stable ID from the data as the key
- **Handle**: `stable-id-key`
- **Kind**: Decision
- **Reader Question**: "The stories have no field I like. Can I use the index, or `Math.random()`?"
- **Reader Expects**: any unique value works, and `Math.random()` is always unique
- **React Does**: a key must be the same for the same story on every render; the index changes when a story is inserted, deleted, or moved; `Math.random()` changes on every render, so no key ever matches, and React recreates every row
- **Placement**: `key={story.id}` from the database; for data made in the browser, an id made once when the item is created, with a counter or `crypto.randomUUID()`; the index only for a list that never reorders, inserts, or deletes, such as the lines of a printed poem
- **Real Mistake**: `key={Math.random()}`; after the second render every `<input>` is empty, and the typed correction is gone; verified in React 19.3.0
- **Importance**: interviewers ask why not the index; reviewers flag `key={index}` on any list that changes
- **Review Point**: Condition
- **Required Lesson Proof**: the same typed-text steps with `key={Math.random()}`: every input empty; with `key={story.id}`: the text with its story; a static list of section names with index keys: no difference.

### Principle 5: The key is not a prop, so pass the id again
- **Handle**: `key-not-a-prop`
- **Kind**: Decision
- **Reader Question**: "`StoryRow` needs the story's id. Can it read `props.key`?"
- **Reader Expects**: `key` is written like an attribute, so it arrives with the other props
- **React Does**: React takes `key` out of the props for itself; `props.key` is `undefined` inside the row, and React prints an error that says so
- **Placement**: `<StoryRow key={story.id} storyId={story.id} story={story} />`, or read `story.id` from the story prop
- **Real Mistake**: `StoryRow` renders `data-story-id={props.key}`; the attribute is missing from the DOM, and the console shows "StoryRow: `key` is not a prop. Trying to access it will result in `undefined` being returned. If you need to access the same value within the child component, you should pass it as a different prop."; verified in React 19.3.0
- **Importance**: a react.dev Pitfall; an analytics id that never reaches the page
- **Review Point**: Do
- **Required Lesson Proof**: `StoryRow` reading `props.key`: the error and no attribute; with `storyId`: the attribute on each row.

## Senior Answer
I keep the data in an array and call `map()` on it. Each call returns a JSX element, and React renders the resulting array in order. If the arrow function has a block body, I must write `return`, or the list is empty. Every element made directly inside `map()` needs a `key`, unique among its siblings. When I map to a component, the key goes on the component, not on the `<li>` inside it. React uses keys to match each row with the same item on the next render. Without keys, or with the index, it matches by position. Then an item added at the top takes over the first row, along with anything typed in it. So I use a stable ID from the data, like a database id. I never use `Math.random()`, which changes on every render and recreates every row. The index is fine only for a list that never changes order. The key is not a prop, so when the row needs the id, I pass it again.
