# Q16: Component Memory with useState — Operational Principle Map
- **Source Map**: `01-01-map/16.md`
- **Topic Tag**: `#use_state` | `❱ CORE`
- **Interview Question**: *Why do ordinary variables forget their values between renders, and how does useState remember?*

## Authorized Scope
Q16 teaches the core purpose of `useState` in a `StoryCard` like button: a local variable such as `let likes = 0` belongs to one call of the component, so changing it neither survives the next render nor tells React to render again, while `const [likes, setLikes] = useState(0)` returns a value React keeps outside the function together with a setter that stores the next value and triggers a re-render; the lesson covers array destructuring of the pair, the initial value being used only on the first render, changing state only through its setter from event handlers, each rendered instance having its own state, and keeping in state only what must survive a re-render; it builds on Q06 (props are read-only), Q09 (components update through state instead of repeated `root.render` calls), Q12 (render is pure and StrictMode calls it twice), Q13 (handlers are passed, not called), and Q14 (handlers are the home of side effects), and it excludes the render and commit phases (Q17), snapshot closures and reading state right after setting it (Q18), updater functions and batching (Q19), the StrictMode component (Q20), object and array state (Q21, Q22), controlled inputs (Q23), lifting state (Q26), state position and `key` resets (Q27), the Rules of Hooks (Q46), and Fiber internals (Q78).

## Principles

### Principle 1: Expect a local variable to forget, and to change nothing on screen
- **Kind**: Model
- **Rule**: Every render is a new call of the component function, so a local variable such as `let likes = 0` is created fresh by each call; assigning to it inside a handler changes only that call's copy, React is never told that anything changed, and the next render, whatever triggers it, starts the variable again at `0`.
- **Importance**: This is the first half of the interview question and the card's Friction; a developer without it keeps adding `console.log` lines that prove the number goes up and cannot explain why the screen does not.
- **Prediction**: Three clicks on a `StoryCard` whose button increments `let likes` log "likes is now 1", "likes is now 2", and "likes is now 3" while the button keeps showing "Like (0)"; after an unrelated Save toggle (which uses state) re-renders the card, the next Like click logs "likes is now 1" again.
- **Required Lesson Proof**: Render the `let likes` card with a working Save toggle, click Like three times and show the logs beside "Like (0)", click Save, click Like again, and show the count restart at 1.
- **Sources**: Core Truth, Friction, and Code Experiment Naive of `01-01-map/16.md`; state-a-components-memory "When a regular variable isn't enough"; the merged click and reset candidates, verified in React 19.3.

### Principle 2: Store in state exactly what must survive a re-render
- **Kind**: Decision
- **Rule**: Use `useState` for information the component must remember between renders because it changes what the component shows (a like count, a bookmark flag, an open or closed panel), and keep values that are computed and used inside one handler, such as a share URL, as ordinary local variables, because every setter call costs a render.
- **Importance**: Too little state gives the frozen screen of Principle 1; too much state adds renders that change nothing and, as the "Remove unnecessary state" Challenge shows, values that lag one click behind; reviewers flag both.
- **Review Point — Condition**: If a value must be remembered after the handler returns and affects the output, keep it in state; if it is used only while one handler runs, keep it in a local variable.
- **Required Lesson Proof**: Convert the like count to `useState` and show "Like (1)" after one click; then click a Share button that stores its URL in state and show two `render StoryCard` lines per click with nothing on screen changing, and a second Share button that uses a local `const url` and logs no render.
- **Sources**: Core Truth of `01-01-map/16.md`; state-a-components-memory Recap bullet 1 and Challenge "Remove unnecessary state" Solution; the Q06, Q10, Q12, and Q14 rows routed here; the share output verified in React 19.3.

### Principle 3: Expect React to hand back the stored value on every render
- **Kind**: Model
- **Rule**: `useState` keeps the value outside your function, in a cell React attaches to this component on the screen; on the first render it stores the initial value and returns it, the setter stores the next value and asks React to render again, and on every later render `useState(0)` returns the stored value, so the initial argument matters only once.
- **Importance**: This is the second half of the interview question; a developer who believes `useState(0)` resets the count on each render, or that state is saved somewhere permanent, cannot predict the next screen or explain a lost value after a reload.
- **Prediction**: After one click, the render log reads "render StoryCard a likes = 1" (twice under StrictMode) although the code still says `useState(0)`; editing the component file keeps the count through Fast Refresh ("Likes (2)"), and reloading the page brings back the initial value ("Likes (0)").
- **Required Lesson Proof**: Log `likes` in the component body, click once and show the log with `1` beside the unchanged `useState(0)` line, then change the button label in the editor and show the count survive, then reload and show it return to `0`.
- **Sources**: Mechanism and Under the Hood of `01-01-map/16.md`; state-a-components-memory "Anatomy of `useState`"; useState Parameters and Returns; state-as-a-snapshot "shelf" paragraph; the merged log and Fast Refresh candidates, verified in React 19.3 with Vite 8.3.1.

### Principle 4: Change state only by calling its setter
- **Kind**: Decision
- **Rule**: The state variable is a read-only value for the current render and the setter is the only way to change it: `setLikes(likes + 1)` stores the next value and triggers a re-render, while `likes = likes + 1` either throws, because the destructured variable is a `const`, or, with `let`, changes a local copy that React never sees.
- **Importance**: Assigning to a state variable is the most direct carry-over from Principle 1's habit; with `const` it crashes the handler with "Assignment to constant variable.", and the button stays at "Like (0)".
- **Review Point — Do not**: Do not assign to a state variable; call its setter with the next value.
- **Required Lesson Proof**: Write `likes = likes + 1` in the handler, click, and show "Assignment to constant variable." with the button still at "Like (0)"; replace it with `setLikes(likes + 1)` and show "Like (1)".
- **Sources**: Mechanism of `01-01-map/16.md`; useState "`set` functions"; state-a-components-memory Challenge "Fix stuck form inputs" Solution; the assignment error verified in React 19.3.

### Principle 5: Expect each rendered instance to keep its own state
- **Kind**: Model
- **Rule**: State belongs to one instance of a component on the screen, not to the component function or its file, so rendering `<StoryCard />` twice gives two separate counts, and the parent that renders them cannot read or change either one.
- **Importance**: A developer who thinks of state as a shared module variable expects every card to show the same count, and a developer who expects the parent to see the count cannot understand why Q26 must move state up.
- **Prediction**: With two `StoryCard`s on the page, clicking Like on the first shows "Like (1)" on the first card and "Like (0)" on the second, and only the first card logs a render.
- **Required Lesson Proof**: Render two cards, click the first once, and show the two button texts and the render log naming only the first card; state in one sentence that sharing the count needs lifting state (Preview of Q26).
- **Sources**: state-a-components-memory "State is isolated and private" and Recap bullet 7; the two-card output verified in React 19.3; the Preview row for lifting state (Q26).

### Principle 6: Call setters from handlers, never unconditionally during render
- **Kind**: Decision
- **Rule**: A setter call triggers a render, so a setter that runs during render triggers another render, which calls it again; React stops the loop with an error, and the usual cause is a handler called instead of passed, as in `onClick={setLikes(likes + 1)}`, so setters belong inside event handlers.
- **Importance**: One pair of misplaced parentheses crashes the page with "Too many re-renders. React limits the number of renders to prevent an infinite loop." and leaves the root empty; Q13 deferred this failure to the first lesson with state.
- **Review Point — Do not**: Do not call a setter in the component body or in an event prop expression; call it inside a handler function, such as `onClick={() => setLikes(likes + 1)}`.
- **Required Lesson Proof**: Render `<button onClick={setLikes(likes + 1)}>`, show the error and the empty page, then wrap the call in an arrow function and show one render per click.
- **Sources**: useState Troubleshooting "Too many re-renders"; tutorial `handleClick(0)` trap; the Q13 Deferred row; the error verified in React 19.3.

## Senior Answer
An ordinary local variable belongs to one call of the component: every render calls the function again and creates the variable fresh, and assigning to it in a handler changes that call's copy without telling React, so a `let likes` counter logs 1, 2, 3 while the button still shows 0, and the next render resets it. `useState` fixes both problems: React keeps the value outside the function, in a cell attached to that component instance on the screen, returns the stored value on every render (the initial argument is used only on the first one), and gives me a setter that stores the next value and triggers a re-render. So I change state only through the setter, from event handlers, never by assignment and never during render, where it would loop into "Too many re-renders"; I keep in state only what must survive a re-render to affect the output, and I use a local variable for anything used inside a single handler. Each rendered instance keeps its own state, which its parent cannot see, so two cards count independently and sharing a value means lifting it into their parent.
