# Q17: Trigger, Render, and Commit — Operational Principle Map
- **Source Map**: `01-01-map/17.md`
- **Topic Tag**: `#render_and_commit` | `❱ CORE`
- **Interview Question**: *What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?*

## Authorized Scope
Q17 traces one `LikeCounter` click through the three phases: a render is triggered only by the initial `root.render` or by a state update, and a setter call queues that render instead of performing it, so the rest of the handler still runs against the old DOM; in the render phase React calls the component whose state changed and every component it returns, computing new JSX without touching the DOM; in the commit phase React writes only the differences to the DOM (the initial render appends the whole tree, a re-render changes one text node and leaves an input's typed text alone, and a render with identical output changes nothing), after which the browser paints; it builds on Q01 (the screen is a projection of data), Q05 (rendering walks from the root down), Q09 (`root.render` finishes after your code continues), Q12 (render is a pure calculation, doubled by StrictMode), and Q16 (the setter stores the next value and triggers a re-render), and it excludes the state snapshot inside the running handler (Q18), batching and updater functions (Q19), `Object.is` bail-outs (Q21), Effects (Q35), re-render causes and performance fears (Q56, Q57), `flushSync` (Q65), concurrent rendering (Q66), reconciliation internals (Q77), and the Fiber work loop (Q78).

## Principles

### Principle 1: Treat a setter call as a trigger that queues a render
- **Kind**: Model
- **Rule**: Only two things start a render: the initial `root.render(<App />)` and a state update, whether in the component itself or in an ancestor; calling a setter records the next value and asks for a render, then returns, so the rest of the handler runs before React renders anything and before the DOM changes.
- **Importance**: The card's Friction is the belief that `setState` changes the DOM on the spot; a developer who holds it writes handlers that read or depend on a DOM that has not been updated yet.
- **Prediction**: Clicking Like, whose handler logs, calls `setLikes(likes + 1)`, reads the count's `textContent`, and logs again, prints "handler start", "DOM after setLikes: 0", and "handler end", and only then "render LikeCounter 1"; the screen then shows 1.
- **Required Lesson Proof**: Add the three logs and a render log to `LikeCounter`, click Like, and show the console order, with the screen showing 1 afterwards; state in one sentence that React waits for the whole handler before rendering (Preview of Q19).
- **Sources**: Core Truth and Mechanism of `01-01-map/17.md`; render-and-commit "Step 1: Trigger a render"; state-as-a-snapshot "Setting state triggers renders"; the merged order candidate, verified in React 19.3.

### Principle 2: Treat rendering as React calling your components, not as drawing
- **Kind**: Model
- **Rule**: In the render phase React calls the component whose state changed, then every component that component returns, each with a new props object, and collects the JSX they return; this is a calculation in memory, the DOM stays untouched, and components above the one that changed are not called at all.
- **Importance**: Developers who think "rendering" means painting pixels fear every render and cannot predict which component functions run after a click; an interviewer expects "rendering is React calling your components" as the definition.
- **Prediction**: A Like click inside `LikeCounter` logs "render LikeCounter 1" and "render LikeLabel 1" (each twice under StrictMode) and never logs "render StoryPage", the parent that holds no state.
- **Required Lesson Proof**: Add render logs to `StoryPage`, `LikeCounter`, and `LikeLabel`, show all three on page load, click Like, and show that only the counter and its child log.
- **Sources**: Core Truth and Mechanism of `01-01-map/17.md`; render-and-commit "Step 2"; rules "How does React run your code?"; the Q06 Deferred row on new props per render; the render logs verified in React 19.3.

### Principle 3: Expect the commit to write only what changed
- **Kind**: Model
- **Rule**: In the commit phase React compares the new JSX with the previous render and applies only the necessary DOM operations: the initial commit inserts the whole tree at once, a re-render updates only the nodes whose output differs, and a render whose output matches the previous one changes nothing; the browser then paints the updated DOM, which the docs call painting to keep it apart from React rendering.
- **Importance**: The card's Friction includes the fear that frequent renders cause expensive reflows; without this model a developer cannot explain why typed text survives a re-render or why a render can cost no DOM work at all.
- **Prediction**: The initial load records one insertion of the whole tree into `#root`; after typing "draft" into an input beside the counter, a Like click records exactly one DOM change, the count's text node, and the input still holds "draft"; clicking a button that updates a state the JSX never displays logs both render lines and records no DOM change.
- **Required Lesson Proof**: Type into the input, click Like, and show the Elements panel highlighting only the count's text while the input keeps "draft"; then click the hidden-state button and show the render logs with no highlight in the Elements panel.
- **Sources**: Core Truth, Mechanism, and Under the Hood of `01-01-map/17.md`; render-and-commit "Step 3" (the `Clock` example), "Epilogue: Browser paint", and Recap bullet 3; the two Q01 Deferred rows; the DOM changes recorded with a `MutationObserver` in React 19.3.

### Principle 4: Use the next value you computed, not the DOM, in the rest of the handler
- **Kind**: Decision
- **Rule**: Because the commit happens after the handler returns, any DOM read on the lines after a setter (`textContent`, an element's height, a scroll position) still sees the previous render, so compute the next value into a variable, pass it to the setter, and use that variable for the rest of the handler.
- **Importance**: A handler that calls `setLikes(likes + 1)` and then sends `document.getElementById('likes').textContent` to analytics reports the old number on every click, and the same mistake with element sizes produces layout jumps that are hard to trace.
- **Review Point — Do not**: Do not read the DOM after a setter expecting the new content; keep the next value in a variable, and treat code that truly needs the committed DOM as a case for the tools of later lessons (Preview of Q65).
- **Required Lesson Proof**: Log `textContent` after `setLikes` and show "DOM after setLikes: 0", then write `const nextLikes = likes + 1; setLikes(nextLikes);` and log `nextLikes`, showing 1 on the first click.
- **Sources**: Code Experiment Naive and Friction of `01-01-map/17.md`; useState Troubleshooting "logging gives me the old value" (its save-in-a-variable correction); the DOM read verified in React 19.3; the Preview rows for Q18 and Q65.

## Senior Answer
Every screen update in React goes through three phases. A render is triggered either by the initial `root.render` or by a state update, and a setter call only queues that render, so the rest of the handler runs first and still sees the old DOM. In the render phase React calls the component whose state changed and every component it returns, each with new props, and collects their JSX; that is a pure calculation in memory, nothing touches the DOM, and components above the change are not called. In the commit phase React compares the result with the previous render and applies only the necessary DOM operations: the first commit inserts the whole tree, a re-render changes only the nodes whose output differs, so a like count updates one text node and an input keeps its typed text, and identical output changes nothing; then the browser paints. So I never read the DOM right after a setter to get the new value; I compute the next value into a variable and use it.
