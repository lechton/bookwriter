# Q21: Updating Objects in State — Operational Principle Map
- **Source Map**: `01-01-map/21.md`
- **Topic Tag**: `#state_objects` | `❱ CORE`
- **Interview Question**: *How do you update an object in state without mutating it?*

## Authorized Scope
Q21 teaches object updates inside the National Times dashboard's author profile editor (`ProfileEditor` holding a `profile` with top-level fields such as `bio` and nested objects such as `author` and `settings`): React notices a change only when the setter receives a different object, because it compares the next state with the current one using `Object.is`, so assigning to a field and passing the same object back is ignored and the edit appears only when some unrelated update re-renders; the setter replaces the whole value rather than merging it, so the next object is built from a copy (`{ ...profile, bio: nextBio }`) with the overrides written after the spread; the spread copies one level, nested objects are separate objects shared by reference, and a nested update copies every object from the changed field up to the root while reusing the untouched branches; it builds on Q06 (read-only inputs), Q12 (local mutation of values just created), Q16 (change state only through its setter), Q17 (the commit writes only what changed), Q18 (each render reads its own snapshot), Q19 (the updater form and its purity), and Q20 (updaters are called twice in development), and it excludes arrays (Q22), multi-field handlers with computed names (Q23), flattening deep state (Q25), reducers (Q29), `React.memo` (Q57), lint and compiler checks (Q94, Q63), and Immer.

## Principles

### Principle 1: Replace a state object instead of mutating it
- **Kind**: Decision
- **Rule**: React notices a change only when the setter receives a different object: it compares the next state with the current one using `Object.is`, so assigning to a field (including `+=`, `delete`, and `Object.assign(profile, changes)`) and passing the same object back is ignored, and without a setter call nothing is requested at all; the mutated value then sits hidden in the object until an unrelated update re-renders the component, when it suddenly appears, and it has already rewritten the snapshot that earlier logs and handlers were reading.
- **Importance**: The card's Friction is exactly this bug (the editor's bio never appears), react.dev's Troubleshooting entry calls the setter call "Doesn't do anything", and the delayed "catch-up" makes the bug look random in review and in QA.
- **Review Point — Do not**: Do not mutate an object that is in state and pass it to the setter; create a new object and pass that.
- **Required Lesson Proof**: In `ProfileEditor`, run `profile.bio = nextBio; setProfile(profile)` and show the screen unchanged; then change the name field through a correct setter and show the bio jump to the mutated value; finally write `setProfile({ ...profile, bio: nextBio })` and show the bio update on the first try.
- **Sources**: Core Truth, Friction, and Under the Hood of `01-01-map/21.md`; updating-objects "Treat state as read-only", Recap bullets 1 to 3, and both Challenge Solutions; useState `set` Caveat 2 and Troubleshooting; lint `immutability`; the merged no-setter, same-reference, catch-up, hidden-mutation, bail-out, and snapshot candidates.

### Principle 2: Expect the setter to replace the whole object, not merge it
- **Kind**: Model
- **Rule**: The value passed to a `useState` setter becomes the entire next state, so a partial object does not update "just that field": every field it leaves out is gone from the next render.
- **Importance**: Developers who learned `this.setState` in class components expect a merge, and the Scoreboard challenge shows the result in production terms: editing one field silently erases the others.
- **Prediction**: In a `player` object with `firstName`, `lastName`, and `score`, calling `setPlayer({ lastName: e.target.value })` keeps the typed last name but empties the first-name input and removes the score from the screen.
- **Required Lesson Proof**: Run the partial setter in the Scoreboard form, show the vanished fields and log the next state object, then add `...player` and show every field preserved.
- **Sources**: updating-objects Challenge "Fix incorrect state updates" and its Solution; general engineering knowledge (class component merge habit); the merged vanished-fields candidate.

### Principle 3: Spread the old object first, then write the changed fields
- **Kind**: Decision
- **Rule**: Build the next object as `{ ...profile, bio: nextBio }`: the spread copies every existing field into a new object, and the properties written after it override those copies, so order matters, and `{ bio: nextBio, ...profile }` puts the old bio back on top of the new one; the same object can be returned from an updater as `setProfile(prev => ({ ...prev, bio: nextBio }))`.
- **Importance**: This is the card's Mechanism and the answer a reviewer and an interviewer expect, and the reversed order is a quiet bug: the code looks like an update and changes nothing.
- **Review Point — Do**: Spread the previous object first and write the changed fields after it.
- **Required Lesson Proof**: Update the bio with the spread first and show the change; swap the order and show the old bio returning; then use the updater form from the card's React experiment and show the same result.
- **Sources**: Mechanism and Code Experiment of `01-01-map/21.md`; updating-objects "Copying objects with the spread syntax" and Recap bullet 4; useState "Form (object)"; the merged ordering, longhand, and updater-form candidates.

### Principle 4: Treat nested objects as separate objects shared by reference
- **Kind**: Model
- **Rule**: An object "inside" another is a separate object that the outer one points at, and the spread copies only those pointers, so after `const next = { ...profile }` the new object and the old one share the same `author` object, and any other variable that points at it (such as the `initialProfile` used to create the state) shares it too.
- **Importance**: The card's Friction mutates `profile.author.bio`, and the "Find and fix the mutation" challenge shows the result: a change made through one holder moves something that was never supposed to move.
- **Prediction**: After `const next = { ...profile }`, `next.author === profile.author` logs `true`; setting `next.author.bio = nextBio` and calling `setProfile(next)` does re-render, but `initialProfile.author.bio` now holds the edit too, so a Reset button that calls `setProfile(initialProfile)` shows the edited bio instead of the original.
- **Required Lesson Proof**: Log the identity check, run the shallow update, and press Reset to show the leaked edit.
- **Sources**: Friction of `01-01-map/21.md`; updating-objects closing note of "Copying objects with the spread syntax", Deep Dive "Objects are not really nested", Recap bullet 5, and Challenge "Find and fix the mutation"; the merged `Background` and shared-artwork candidates.

### Principle 5: Copy every level from the changed field up to the root
- **Kind**: Decision
- **Rule**: To change a nested field, create a new object at each level on the path to it and keep every other branch as it is: `setProfile({ ...profile, author: { ...profile.author, bio: nextBio } })`, optionally written as named steps (`nextAuthor`, then `nextProfile`); a full deep clone is not a safer substitute, because `JSON.parse(JSON.stringify(profile))` turns a `Date` into a string and gives every untouched branch a new reference.
- **Importance**: This is the second half of the card's Mechanism, the fix for the Reset leak, and the pattern a reviewer checks in every nested update; the deep-clone habit is a common over-correction that breaks data and, later, memoization (Preview of Q57).
- **Review Point — Do**: Copy each object on the path to the changed field and reuse the untouched branches as they are.
- **Required Lesson Proof**: Rewrite the nested update with copies at both levels, show the bio update and Reset restoring the original, and log `next.author === profile.author` as `false` while an untouched branch such as `next.settings === profile.settings` stays `true`; then show a JSON round trip turning `publishedAt` into a string, so a later `publishedAt.toLocaleDateString()` call throws a TypeError.
- **Sources**: Mechanism and Friction of `01-01-map/21.md`; updating-objects "Updating a nested object" and Recap bullet 6; useState "Form (nested object)"; lint `immutability` Troubleshooting "I need to update nested objects"; the merged deep-clone and named-steps candidates.

## Senior Answer
I treat every object in state as read-only. React decides whether anything changed by comparing the next state with the current one using `Object.is`, so if I assign to a field and pass the same object back, React ignores the update and the edit only shows up later, when some unrelated update re-renders the component. Instead I give the setter a new object. Because the setter replaces the whole value instead of merging it, I build that object from a copy: `{ ...profile, bio: nextBio }`, with the spread first and the changed fields after it, or the same thing returned from an updater when the change depends on the previous value. The spread copies only one level, and a nested object is a separate object shared by reference, so changing `profile.author.bio` through a shallow copy would also change every other holder of that author object. For nested data I copy each object on the path to the changed field, `{ ...profile, author: { ...profile.author, bio: nextBio } }`, and leave the untouched branches as they are rather than deep cloning the whole state.
