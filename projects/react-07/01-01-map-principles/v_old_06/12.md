# Q12: Keeping Components Pure — Operational Principle Map
- **Source Map**: `01-01-map/12.md`
- **Topic Tag**: `#purity` | `❱ CORE`
- **Interview Question**: *What does it mean for a component to be pure, and what breaks when it is not?*

## Authorized Scope
Q12 teaches purity during render with static props: a component is a formula that returns the same JSX for the same inputs and changes nothing that existed before it was called, React may call it any number of times and in any order, the `<StrictMode>` wrapper that the Vite template already places in `main.jsx` calls it twice in development to expose violations, local mutation of values created during the same render is allowed, and side effects (DOM writes, timers, network, analytics) and non-idempotent calls stay out of the render path; it builds on Q05 (render order between siblings is not a contract), Q06 (props are read-only), Q09 (`main.jsx` and the root), and Q11 (keys generated during render), and it excludes state setters (Q14), event handlers as the home of side effects (Q13), the StrictMode component itself (Q46), `useEffect` (Q31), concurrent rendering (Q66), memoization (Q55), and the React Compiler (Q63).

## Principles

### Principle 1: Treat a component as a formula React may run any number of times
- **Kind**: Model
- **Rule**: A pure component returns the same JSX for the same props and changes nothing outside itself, because React decides when and how often to call it: twice per render under StrictMode in development, again whenever its inputs change, in no guaranteed order between siblings, and sometimes without using the result.
- **Importance**: Without this model a developer treats the double console log as a React bug and removes StrictMode, and every impure component then produces numbers that depend on how often it happened to run.
- **Prediction**: A `console.log` in the `Masthead` body prints `render Masthead 1` and `render Masthead 2` on a single page load under StrictMode, while the screen shows one masthead; in a production build it prints once.
- **Required Lesson Proof**: Add the log, load the page in development and show the two lines, then run `vite build` with `vite preview` and show a single line.
- **Sources**: Core Truth and Under the Hood of `01-01-map/12.md`; keeping-components-pure "Purity" and Deep Dive on StrictMode; rules "Why does purity matter?"; the merged double-log, dimming, and render-order candidates, verified in React 19.3.

### Principle 2: Change nothing that existed before the render
- **Kind**: Decision
- **Rule**: During render, never write to module-level variables or mutate objects and arrays created before the component was called, including arrays received as props; creating a fresh array or object inside the component and mutating it is fine, as long as the mutation happens before the value is passed to JSX.
- **Importance**: A global counter incremented in the body renders "Tea cup for guest #2", "#4", "#6" under StrictMode, a pushed placeholder appears twice as "Create Story", and a value changed after being passed to `<Header>` makes the header show the later value.
- **Review Point — Condition**: If the value was created during this render, mutate it freely until it is passed to JSX; if it existed before the call (a module variable, a received array, a shared object), compute a new value instead of changing it.
- **Required Lesson Proof**: Show the `guest` counter, the doubled "Create Story", and the `small` header in development, then fix each: pass the number as a prop, copy with `[...stories, placeholder]` or render the placeholder separately, and build a new styles object; finally show a local `cups` array built with `push` rendering 1, 2, 3.
- **Sources**: Friction and Code Experiment of `01-01-map/12.md`; keeping-components-pure "Side Effects", "Local mutation", and Challenges "Fix a broken profile" and "Fix a broken story tray"; rules "Local mutation" and "Values are immutable after being passed to JSX"; outputs verified in React 19.3.

### Principle 3: Keep side effects out of the render path
- **Kind**: Decision
- **Rule**: The component body only calculates JSX, so DOM writes (`document.title`, `className` through `getElementById`), timers, network requests, and analytics calls do not belong at its top level; express the result in the returned JSX when possible, and otherwise move the effect into an event handler (Preview of Q13).
- **Importance**: A class set with `document.getElementById('time').className` in the body crashes the first render with "Cannot set properties of null (setting 'className')" because the element does not exist yet, and an analytics call in the body fires twice per render in development and again on every re-render.
- **Review Point — Do not**: Do not write to the DOM, start timers, send requests, or log analytics from the component body; compute the output in JSX or move the effect out of render.
- **Required Lesson Proof**: Render the `Clock` that sets its class in the body and show the error, then compute `className={hour < 6 ? 'night' : 'day'}` in the JSX and show the working clock.
- **Sources**: Mechanism of `01-01-map/12.md`; keeping-components-pure "Where you _can_ cause side effects" and Challenge "Fix a broken clock"; rules "Side effects must run outside of render", "Changing the DOM", and the Deep Dive "How to tell if code runs in render"; the error verified in React 19.3.

### Principle 4: Avoid non-idempotent calls in render output
- **Kind**: Decision
- **Rule**: `Math.random()`, `new Date()`, and similar calls return a different value each time, so output computed from them breaks "same inputs, same output"; pass such values in from outside the render (as props or, later, as state) instead of producing them in the body.
- **Importance**: Under StrictMode the two calls of the same render disagree, and the screen shows whichever ran last; the time shown by a `new Date()` in the body stays frozen at the moment of rendering.
- **Review Point — Avoid**: Avoid calling non-idempotent functions while rendering output; compute the value where it is created and pass it in.
- **Required Lesson Proof**: Log `Math.random()` in the body and show two different numbers in the console with only the second on screen, then pass the number in as a prop and show the two logs agreeing.
- **Sources**: rules "Components and Hooks must be idempotent"; the merged random and date candidates, the random output verified in React 19.3.

## Senior Answer
A pure component behaves like a formula: for the same props it returns the same JSX, and it changes nothing that existed before it was called. React relies on that because it decides when and how often to render: it may call a component again, in any order relative to its siblings, or discard a render, and `<StrictMode>` calls every component twice in development precisely to expose code that breaks the rule, which is why a log in the body prints twice. What breaks when a component is impure is predictability: a global counter incremented during render shows guests #2, #4, #6, a placeholder pushed into a received array appears twice, a value changed after being passed to JSX leaks into the earlier element, a DOM write in the body crashes because the element does not exist yet, and `Math.random()` gives each render call a different answer. So I mutate only what I created during the same render and only before passing it to JSX, compute everything else as new values, keep DOM writes, timers, requests, and analytics out of the body, and move those side effects into event handlers.
