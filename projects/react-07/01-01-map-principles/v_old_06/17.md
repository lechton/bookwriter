## Authorized Scope
Q17 teaches batching and the update queue inside one event: React runs all the code in an event handler before it renders, so several setter calls produce one render, and each click is its own batch; during the next render React walks the queue in order, where a value entry replaces the running result and an updater function (`p => p + 1`) receives it; we pass an updater when the next value is computed from the previous one and other updates may be queued before ours is applied; and an updater only computes and returns the next value, because React calls it while rendering (twice in development under StrictMode). It builds on Q12 (rendering is pure), Q14 (the setter asks for a render), Q15 (the render follows the handler), and Q16 (state is fixed within a render), and it leaves `flushSync` to Q65, batching across timeouts and promises and the React 17 comparison to Q75, StrictMode itself to Q46, and reducers to Q26.

## Principles

### Principle 1: Expect one render per event, however many setters it calls
- **Kind**: Model
- **Roles**: event handler: our code, runs to the end first; setter call: adds an entry to the queue for its state variable and returns; batch: every update queued during one event, processed in one render; separate click: a new event and a new batch.
- **Placement**: all setter calls of one interaction inside one handler; the screen changes once the handler has finished, never halfway through it.
- **Mechanism**: React waits until all code in the event handler has run, then renders once with every queued update applied; it does not batch across separate intentional events, so a click that disables a form takes effect before the next click.
- **Defect**: A reader who expects one render per setter call adds workarounds against "flicker" that cannot happen, or expects the screen to show an intermediate value between two setter calls.
- **Importance**: The first half of the interview question; the senior answer names batching and its boundary.
- **Prediction**: With a render counter in the body, a handler that calls `setPasses` three times and `setLabel` once renders once; two separate clicks render twice.
- **Required Lesson Proof**: Log each render, click "+3 Free Passes" once and show one render log, then click twice and show two.
- **Sources**: Core Truth and Scope Boundary of `01-01-map/17.md`; queueing "React batches state updates" and Recap bullet 2; `set` Caveat 3; the merged one-render, two-click, half-finished, and waiter candidates, verified in React 19.3.

### Principle 2: Read the queue in order: a value replaces, an updater receives
- **Kind**: Model
- **Roles**: value entry (`setNumber(5)`): "replace with 5", ignores what came before; updater entry (`setNumber(n => n + 1)`): function React calls with the running result; running result: starts at the current state and passes from entry to entry; final result: what `useState` returns on the next render.
- **Placement**: reasoning about any handler that calls the same setter more than once.
- **Mechanism**: during the next render React walks the queue for that state variable in the order the calls were made; a value entry sets the running result; an updater entry is called with it and its return value becomes the running result.
- **Defect**: Without the model the mixed queue's result looks arbitrary, and a reader guesses 5, 6, or 47 for the same handler.
- **Importance**: Interviewers pose exactly this puzzle, and the model is what the updater decision rests on.
- **Prediction**: From 0, `setNumber(number + 5); setNumber(n => n + 1)` renders 6, and `setNumber(number + 5); setNumber(n => n + 1); setNumber(42)` renders 42.
- **Required Lesson Proof**: Click each handler and show 6 and 42 on screen, then trace each queue in a three-column table (queued update, `n`, returns) as react.dev does.
- **Sources**: Under the Hood and Code Experiment React of `01-01-map/17.md`; queueing "What happens if you update state after replacing it", "What happens if you replace state after updating it", its Note, and the Challenge "Implement the state queue yourself"; the merged 6-and-42 candidate, verified in React 19.3.

### Principle 3: Pass an updater when the next value comes from the previous one and other updates can come first
- **Kind**: Decision
- **Roles**: `setPasses(passes + 1)`: value form, computed from this render's snapshot; `setPasses(p => p + 1)`: updater form, computed from the running result; `p`: the result of every update queued before this one.
- **Placement**: the updater form wherever the next value is computed from the previous one and more than one update can be queued before it is applied: several calls in one handler, or a call made after an `await` or a timer while other clicks may have queued updates.
- **Mechanism**: the value form freezes the snapshot's number into the entry; the updater form defers the computation to the queue walk, where it sees every earlier entry.
- **Defect**: three `setPasses(passes + 1)` calls add 1 instead of 3; in the Buy counter, a delayed `setPending(pending - 1)` after one click ends at `pending -1`, and two fast clicks end at `completed 1` instead of 2 (verified in React 19.3).
- **Importance**: The second half of the interview question and a shipped bug in any counter fed by fast clicks or delayed responses.
- **Review Point — Condition**: When the next value is computed from the previous value and another update can be queued before it is applied, use the updater form; when a handler makes one update per event, the value form is equally correct, and using the updater everywhere is a valid style choice.
- **Required Lesson Proof**: Show "+3 Free Passes" adding 1 with the value form and 3 with the updater form; then show the Buy counter at `pending -1` after one click with the value form, and at `pending 0 completed 2` after two fast clicks with updaters.
- **Sources**: Core Truth, Friction, Mechanism, and Code Experiment of `01-01-map/17.md`; queueing "Updating the same state multiple times" and Recap bullet 3; the Challenge "Fix a request counter"; the useState Deep Dive "Is using an updater always preferred?" and its Recipes; the merged "+3" and Buy candidates, verified in React 19.3.

### Principle 4: Keep updaters pure: compute and return, nothing else
- **Kind**: Decision
- **Roles**: updater (`x => x + 1`): function React calls during render; its argument: the running result; its return value: the next running result.
- **Placement**: side effects (an API call, an analytics event, another setter call) in the event handler beside the setter call, never inside the updater.
- **Mechanism**: React calls updaters while rendering, not when the setter is called; under StrictMode in development it calls each updater twice and keeps one result.
- **Defect**: under StrictMode a single click calls the updater twice while the screen rises by 1, so an analytics call or a log inside the updater fires twice in development (verified in React 19.3).
- **Importance**: A reviewer flags any updater with a side effect, and the double call is the first symptom developers report as a React bug.
- **Review Point — Do not**: Do not call setters, APIs, or other side effects inside an updater; compute the next value from the argument and return it.
- **Required Lesson Proof**: Put a `console.log` inside an updater under `<StrictMode>`, click once, show two logs and a rise of 1, then move the log into the handler and show one.
- **Sources**: Mechanism of `01-01-map/17.md`; queueing purity rule; `set` Caveat 6 and Troubleshooting "My initializer or updater function runs twice"; the merged StrictMode candidate, verified in React 19.3; the Preview row for Q46.

## Senior Answer
React batches state updates: it runs all the code in an event handler first, then renders once with every queued update applied, so three setter calls in one click cause one render and the screen never shows a half-finished state. Each separate click is its own batch. During that render React walks the queue for each state variable in order. A plain value means "replace with this value", and an updater function such as `p => p + 1` receives the result of everything queued before it. That is why three `setPasses(passes + 1)` calls add 1, since each one says "replace with 1", while three `setPasses(p => p + 1)` calls add 3. From 0, `setNumber(number + 5)` followed by `setNumber(n => n + 1)` renders 6. So I pass an updater when the next value is computed from the previous one and other updates can be queued first, which includes code that runs after an `await` while the user keeps clicking. For a single update per event, the plain value is just as correct. React calls updaters while rendering, and twice in development under StrictMode, so an updater only computes and returns; side effects go in the handler.
