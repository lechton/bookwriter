# Q18: Updating Objects in State — Operational Principle Map

- **Interview Question**: *How do you update an object in state without mutating it?*

## Authorized Scope
Q18 teaches that we treat every object in state as read-only: to change it we create a new object and pass it to the setter, because the setter compares the new value with the current one using `Object.is` and skips the render when it receives the same object; a one-level copy with spread syntax (`{ ...profile, title }`) keeps the unchanged fields; a nested change needs a fresh copy of every object on the path from the root to the changed property, because spread copies one level and a nested object is a separate object the parent only points to; and one change handler can serve many fields with a computed property name (`[e.target.name]`). It builds on Q14 (the setter asks for a render), Q16 (each render keeps its own snapshot), and Q17 (the updater form), and it leaves arrays to Q19, flattening deeply nested state to Q22, skipping renders with `memo` to Q55, and external state libraries to Q60; Immer may be named as an optional helper without teaching its API.

## Principles

### Principle 1: Treat a state object as read-only and hand the setter a new one
- **Kind**: Decision
- **Roles**: `profile`: object React holds as this render's state; mutation (`profile.author.bio = newBio`): a change to that same object; new object (`{ ...profile, title }`): a different object our code creates; `setProfile`: setter React provides, which compares old and new with `Object.is`.
- **Placement**: every change to a state object goes through a new object passed to the setter; changing an object our code created a moment ago, before it reaches the setter, is fine.
- **Mechanism**: `Object.is` checks identity, not contents; a mutated object is still the same object, so the setter sees no change and skips the render; without the setter, React is never told at all.
- **Defect**: `profile.author.bio = 'New bio'; setProfile(profile)` causes no render and the screen keeps "Old bio"; the new bio appears only when an unrelated state change re-renders the page (verified in React 19.3).
- **Importance**: The card's Friction and the interview question; a reviewer rejects any assignment to a state object's field.
- **Review Point — Do not**: Do not assign to a field of a state object or pass the same object back to its setter; build a new object and pass that.
- **Required Lesson Proof**: Mutate `profile.author.bio`, call `setProfile(profile)`, and show the old bio with no render log; change an unrelated state value and show the new bio appearing; then pass a new object and show the immediate update.
- **Sources**: Core Truth, Friction, Under the Hood, and Code Experiment Naive of `01-01-map/18.md`; objects "What's a mutation?", "Treat state as read-only", Deep Dives "Local mutation is fine" and "Why is mutating state not recommended in React?", Recap bullets 1 to 3, and the Challenges "Fix incorrect state updates" and "Find and fix the mutation"; `set` Caveat 2 and Troubleshooting "the screen doesn't update"; the merged candidates, verified in React 19.3.

### Principle 2: Spread the old fields into the new object
- **Kind**: Decision
- **Roles**: `...profile`: spread syntax JavaScript provides, copies every field of the old object; `title: newTitle`: the field that changes, written after the spread so it wins.
- **Placement**: `setProfile({ ...profile, title: newTitle })`, with the spread first and the changed field after it; not `setProfile({ title: newTitle })`.
- **Mechanism**: the setter replaces the whole state value with the object it receives; React does not merge it with the previous object.
- **Defect**: `setProfile({ title: 'Chief' })` renders "Chief" and loses `author` entirely, so every field the handler did not mention disappears from the screen (verified in React 19.3).
- **Importance**: A shipped bug in every multi-field form, and a common confusion for developers used to class components' merging `setState`.
- **Review Point — Do**: Check that every new state object built for a partial change starts with a spread of the current object.
- **Required Lesson Proof**: Edit the title with `setProfile({ title: 'Chief' })` and show the author line vanishing, then add `...profile` and show both fields kept.
- **Sources**: Mechanism of `01-01-map/18.md`; objects "Copying objects with the spread syntax", Recap bullet 4, and the Challenge "Fix incorrect state updates" (last name); the merged lost-fields candidate, verified in React 19.3.

### Principle 3: Copy every object on the path to a nested change
- **Kind**: Decision
- **Roles**: `profile`: outer object; `profile.author`: a separate object that `profile` points to; `{ ...profile, author: { ...profile.author, bio } }`: a new outer object pointing to a new author object.
- **Placement**: one spread per level, from the root down to the object that holds the changed property; not a one-level copy followed by an assignment to a nested field.
- **Mechanism**: spread copies one level; the copy's `author` still points at the same author object the previous render holds; changing it changes that render's snapshot too.
- **Defect**: `const next = { ...profile }; next.author.bio = 'New bio'; setProfile(next)` renders the new bio, but the first render's `profile.author.bio` also reads "New bio", so earlier snapshots, past logs, and any comparison of old and new author objects are wrong; the nested spread leaves it "Old bio" (verified in React 19.3).
- **Importance**: The bug looks fixed because the screen updates, which is why reviewers and interviewers probe it; Q55's `memo` comparisons depend on it.
- **Review Point — Do**: Check that a nested change creates a new object at every level between the state root and the changed property.
- **Required Lesson Proof**: Keep a reference to the first render's `profile`, apply the one-level copy plus assignment, and show the screen updating while the old reference's `author.bio` also changed; then apply the nested spread and show the old reference unchanged.
- **Sources**: Mechanism, Under the Hood, and Code Experiment React of `01-01-map/18.md`; objects "Updating a nested object", Deep Dive "Objects are not really nested", and Recap bullets 2, 5, and 6; the merged shallow-copy candidate, verified in React 19.3.

## Senior Answer
I treat every object in state as read-only. The setter compares the new value with the current one using `Object.is`, which checks identity, not contents. So if I write `profile.author.bio = newBio` and call `setProfile(profile)`, React sees the same object and skips the render, and the new bio shows up only when some unrelated update happens to re-render the page. Instead, I create a new object and pass that. The setter replaces the whole value and doesn't merge, so I spread the old fields first, `{ ...profile, title: newTitle }`; otherwise every field I didn't mention disappears. Spread copies only one level, and a nested object is a separate object the parent only points to. So for a nested change I copy each level on the path, `{ ...profile, author: { ...profile.author, bio: newBio } }`. A one-level copy followed by an assignment would update the screen but also change the object the previous render still holds. Changing an object I have just created is fine. For many fields, one handler can use a computed property name, `[e.target.name]: e.target.value`. When the nesting gets deep, a helper such as Immer can produce the copies.
