How do you use JavaScript expressions inside JSX with curly braces?

Imagine this scenario:

  1. A developer builds an article card for a content website with local story data.
  2. The developer places variable identifiers directly between HTML tags and inside attribute quotes.
  3. The developer starts the local development build and inspects the rendered card layout.
  4. Why does the browser print the literal text string while the author photo link breaks?
  5. Visitors see the literal word headline on screen while a broken image icon shows in the browser.
  6. The compiler treated markup as static text where unbracketed identifiers and quoted attributes never execute.
  7. Today we master curly braces in JSX to evaluate JavaScript expressions, dynamic attributes, and values in rendered markup.

Placing raw variable identifiers inside markup renders literal text

In traditional template engines, developers declare local variables and place their names directly into template placeholders, expecting the runtime engine to substitute values automatically. In React, a component is a JavaScript function returning JSX markup that compiles into in-memory element descriptors. When developers transition to React, they often assume that JSX scans text nodes for matching variable names in scope. You declare a local variable const headline = "Night Trains Return to Europe"; and an image path const avatarUrl = "/img/anna.jpg"; type their names directly between heading tags and attribute quotes, and save the file.

When the browser renders the card, the screen displays the literal word "headline" instead of the story title. Beneath it, the author photo displays an empty broken-image icon while the browser console reports an HTTP network failure GET http://localhost:5173/avatarUrl 404 (Not Found) The browser treated "avatarUrl" as a static relative URL path rather than reading the variable from JavaScript memory. Furthermore, when the developer tries to place a control-flow statement like if directly inside the markup to conditionally label long articles, the build compiler halts immediately with a fatal syntax error. Static JSX cannot read runtime variables without an explicit evaluation bridge.

To see this failure in concrete code, examine how a developer attempts to use local variables directly inside markup:

2 const headline = "Night Trains Return";

Notice what happened under the hood. This failure occurs because JSX operates in markup mode by default. In markup mode, every character between tags and within attribute quotes is treated as literal character content. The JSX compiler does not inspect text nodes for matching JavaScript identifiers. It simply passes the characters straight through into string arguments of element descriptor function calls.

To step out of static markup and run live JavaScript, React provides an evaluation window marked by curly braces ({}). Placing curly braces in text content or directly after an attribute equals sign switches the compiler into JavaScript mode. The compiler evaluates the expression inside the braces and passes the resulting value to the element descriptor.

Curly braces step out of static markup into JavaScript

Curly braces ({}) open an inline window from static JSX markup into live JavaScript execution. This evaluation window works in exactly two places: between tag content (such as <h2>{headline}</h2>), and directly after the equals sign in an attribute (such as src={avatarUrl}). Outside these two positions, curly braces cannot be used to name tags (writing <{tag}> halts compilation). Any text outside curly braces remains static literal characters.

When constructing attribute strings from multiple dynamic pieces, developers cannot mix quotes and braces like src="/img/{photoId}.jpg". In JSX, quotes treat everything inside as static text. To combine dynamic variables with static text, developers use a template literal enclosed in backticks inside a single pair of braces, such as ` src={/img/${photoId}-${size}.jpg} , or JavaScript string concatenation with the plus operator +`. Inside the braces, standard JavaScript string rules apply.

In standard JavaScript files, developers write single-line comments with double slashes //. However, between JSX tags, characters outside curly braces are treated as literal text nodes. If a developer writes // note between tags, the browser renders the characters "// note" directly onto the page. To write a comment between JSX tags, the comment must be enclosed inside curly braces as {/* note */}, instructing the compiler to evaluate a JavaScript comment that emits zero output.

Expressions produce values while statements perform actions

In JavaScript grammar, code divides into expressions and statements. An expression is any piece of code that resolves to a single discrete value in memory. Numbers (4 + 2), variables (headline), template literals, ternary conditions, and function calls are all expressions. In contrast, a statement performs an action or controls execution flow without producing a value. Language statements include if, for, while, switch, and variable declarations (const x = 1).

Because every JSX tag compiles into a _jsx(type, props) function call, any children or attributes written in curly braces become arguments passed into that function call. In JavaScript, function call arguments can only accept expressions. Attempting to pass a control-flow statement like if into a function argument, as in _jsx("p", { children: if (admin) ... }) is a fatal syntax error. To choose between values inside JSX braces, developers use the ternary conditional operator (condition ? a : b). When statements like if or for are necessary, they must be executed above the return statement, storing their result in a local variable that is passed into JSX.

React converts types to text nodes or invisible slots

When React renders JSX expressions to the DOM, it evaluates the runtime type of each expression to determine its screen representation. Strings and numbers evaluate directly into browser DOM text nodes ({readTime} prints "4", and {0} prints "0"). In contrast, the primitive values true, false, null, and undefined are treated as empty slots. React renders nothing to the DOM for these values. This design allows conditional rendering expressions without printing unwanted words like "false" or "undefined" onto the page.

Numbers always print on screen, including zero (0). If an arithmetic operation produces NaN, React prints the characters "NaN" into the DOM and emits a console warning when NaN is a sole child. When an array of strings or numbers is passed as content, such as {['Rail', 'Travel']}, React flattens the array and renders the items concatenated side by side into the DOM without automatic spacing.

Objects and functions require explicit conversion for content

In JavaScript, plain objects and Date instances are non-primitive data structures. If a developer attempts to place a raw object or Date instance directly into JSX content, such as <p>{publishedAt}</p> React throws a fatal runtime exception: "Objects are not valid as a React child (found: [object Date])". React does not guess how an object should be formatted. To display data from an object or date, the developer must explicitly read a primitive property (person.name), call a formatting method (publishedAt.toLocaleDateString('en-GB')), or invoke a helper function.

A function reference represents the function definition itself, while a function call invokes the code and returns its resulting value. If a developer places a bare function reference into JSX content, such as <p>{formatReadTime}</p> React renders an empty paragraph and logs a console error: "Functions are not valid as a React child". To render the output of a function, the developer must call the function with parentheses, as in <p>{formatReadTime(readTime)}</p> passing its return value to the JSX window.

In attributes like style, developers frequently encounter double curly braces: <div style={{ color: 'pink', fontSize: 20 }}> The double curlies are not a special React operator. The outer pair of braces is the standard JSX evaluation window, stepping out of markup into JavaScript. The inner pair of braces is a standard JavaScript object literal { color: 'pink', fontSize: 20 } Writing style={theme} with an object variable const theme = { color: 'pink' } produces the exact same DOM styles. Lecture 83 explores HTML components and inline style object properties in full detail. In content, double curlies like <h2>{{headline}}</h2> create an object literal { headline }, which stops the render with an invalid child error.

The JSX compiler trims whitespace that includes line breaks at the start and end of text lines. If an expression and following text are split across separate lines, such as placing {readTime} on one line and min read on the next, the compiler strips the leading space, rendering 4min read with words joined together. To preserve a space across line breaks, developers keep text and expressions on a single line or insert an explicit string space expression {' '}.

QUESTION 1

Curly braces evaluate variables while static tags print text

A developer creates an article card component and declares a local variable for the headline, then writes the tag name directly in markup:

ArticleCard (Unbracketed Identifier)
1export default function ArticleCard() {
2 const headline = "Night Trains Return to Europe";

3 return (
4 <article className="card">
5 <h2>headline</h2>

6 </article>
Check the read time later
7 );
8}

The developer inspects the browser expecting to see the story title. Instead, the screen displays the word "headline", and beneath it the raw characters "// check the read time later" appear directly on the page.

How do you display the value of a variable inside JSX markup instead of its literal name?

ANSWER

The code does not work. The compiler treats unbracketed text between tags as static character content.

At build time, the JSX compiler translates <h2>headline</h2> into _jsx("h2", { children: "headline" }) passing the literal string "headline" into the element descriptor. The compiler does not inspect the identifier against variables in scope. Likewise, the characters // check the read time later sit outside curly braces, so the compiler treats the slashes as plain text and paints them onto the screen.

To evaluate JavaScript variables and expressions, you must enclose them in curly braces: <h2>{headline}</h2> When the compiler encounters an opening curly brace {, it steps into JavaScript evaluation mode, translating the tag into _jsx("h2", { children: headline }) During render, React reads the variable from memory and paints "Night Trains Return to Europe" into the DOM text node. To write a comment between tags that does not emit visible text, wrap the comment in curly braces as {/* check the read time later */}

Static markup text mode versus evaluated JavaScript window
Static markup:   <h2>headline</h2>      --> _jsx("h2", { children: "headline" })
Evaluated JSX:   <h2>{headline}</h2>    --> _jsx("h2", { children: headline })
PRINCIPLE 1

Curly braces open JavaScript in two places, and everything else is text

Text outside curly braces is treated as static character content. The compiler translates unbracketed words directly into string literals, rendering the literal identifier name to the screen. To evaluate a JavaScript variable or expression, wrap the code in curly braces. Curly braces open an evaluation window in exactly two places: between tag content and immediately after an attribute equals sign.

We should do this:
const title = "Night Trains";
<h2>{title}</h2>
renders variable value
We should not do this:
const title = "Night Trains";
<h2>title</h2>
renders literal text "title"

The developer saves the file and opens the browser. Instead of the author's photo, the card shows a broken-image icon, and the network console reports GET http://localhost:5173/avatarUrl 404 (Not Found)

Why does quoting a variable name in an attribute break resource loading?

ANSWER

The code does not work. Quoting an attribute forces the compiler to treat the value as a static string literal.

In JSX, attribute values enclosed in double quotes are emitted directly as static string values. Writing src="avatarUrl" causes the compiler to generate _jsx("img", { src: "avatarUrl" }) When the browser parses the resulting DOM element <img src="avatarUrl">, its network engine resolves avatarUrl as a relative path against the current origin, dispatching a request to http://localhost:5173/avatarUrl which fails with a 404 error. Placing curly braces inside quotes, as in src="{avatarUrl}", also fails because the braces remain literal string characters. Lecture 48 explores how React blocks dangerous javascript URLs in href and src attributes.

To pass a dynamic variable into an attribute, remove the quotes and enclose the expression in curly braces immediately after the equals sign: src={avatarUrl}. The compiler compiles this to _jsx("img", { src: avatarUrl }) resolving the variable to /img/anna.jpg in memory. If you need to construct a dynamic path from several variables, use a template literal inside a single pair of braces: ` src={/img/${photoId}-${size}.jpg} `.

Attribute string literal versus unquoted expression binding
Quoted attribute:    src="avatarUrl"    --> requests /avatarUrl (404 Not Found)
Unquoted expression: src={avatarUrl}    --> resolves /img/anna.jpg (200 OK)
PRINCIPLE 2

An attribute takes a quoted string or one braced expression

In JSX, double quotes instruct the compiler to create a static string literal. Writing quotes around an attribute name passes that exact text to the DOM, causing the browser to request non-existent paths. To bind an attribute to a dynamic variable or expression, omit the quotes and wrap the expression in a single pair of curly braces directly after the equals sign.

QUESTION 3

Braces evaluate expressions while statements belong above return

The developer wants to display a label indicating whether an article requires a long read, and writes an if statement inside the paragraph:

ArticleCard (Statement in Braces)
1export default function ArticleCard() {
2 const readTime = 4;
Reading duration in minutes
3 return (
4 <article className="card">
5 <p>{if (readTime > 10) 'Long read'}</p>
Control statement
6 </article>
7 );
8}

The developer saves the file and the development server halts. The terminal reports a fatal build error: SyntaxError: Unexpected token 'if'

Why does embedding a JavaScript control statement inside JSX fail the build?

ANSWER

The code does not work. Function call argument slots in JavaScript cannot accept control-flow statements.

Every JSX tag compiles into a _jsx() function call where child content becomes argument expressions: _jsx("p", { children: ... }) In ECMAScript grammar, an argument passed into a function call must be an expression, a unit of code that evaluates to a value. A control-flow statement like if, for, while, or const controls program flow or performs actions, but it produces no value. Placing an if statement into a function argument slot violates language grammar, halting the compiler.

To evaluate conditional choices inside JSX curly braces, use a ternary conditional expression (condition ? a : b), which evaluates to a single value. Writing <p>{readTime > 10 ? 'Long read' : 'Quick read'}</p> compiles into valid JavaScript and evaluates to "Quick read" when readTime is 4. When complex branching requires multiple statements, execute the if statement above the return statement and store the resulting string in a local variable before passing it into JSX.

Function argument slots accept expressions and reject statements
Statement in args:  _jsx("p", { children: if (...) }) --> SyntaxError
Expression in args: _jsx("p", { children: test ? a : b }) --> Valid value
PRINCIPLE 3

Braces hold one expression, and statements go above the return

JSX tags compile directly into JavaScript function calls where children become argument values. In ECMAScript grammar, function call argument slots accept only expressions that produce a value. Control-flow statements like if, for, or while produce no value and halt compilation. Use an inline ternary expression inside braces, or compute the value using statements above the return.

We should do this:
const minutes = 4;
<p>{minutes > 10 ? "Long" : "Quick"}</p>
ternary
We should not do this:
const minutes = 4;
<p>{if (minutes > 10) "Long"}</p>
syntax error
QUESTION 4

Embedded expressions run each time React renders the component

The developer creates an article element and reassigns the local variable on the following line to see if the element updates:

ArticleCard (Render Timing Log)
1export default function ArticleCard() {
2 let headline = "Night Trains Return to Europe";
3 const card = <h2>{headline}</h2>;
Creates element descriptor
4 headline = "Alps Sleeper Routes Reopen";
5 return card;
6}

The developer expects the heading on screen to display "Alps Sleeper Routes Reopen". Instead, the screen continues to show "Night Trains Return to Europe".

When does code inside JSX curly braces execute, and does reassigning a variable update the screen?

ANSWER

The code works. Expressions inside curly braces evaluate synchronously at the moment the JSX line runs, producing an immutable element descriptor.

When React renders ArticleCard, it invokes the function from top to bottom. When execution reaches const card = <h2>{headline}</h2> the JavaScript engine evaluates the expression {headline} using the value in scope at that instant ("Night Trains Return to Europe"). The compiler creates a plain JavaScript object { type: 'h2', props: { children: 'Night Trains Return to Europe' } } This object holds the evaluated string value, not a live reference to the headline variable. Reassigning headline on the subsequent line changes the local variable, but it does not alter the already-created element descriptor.

Calling a helper function such as {formatReadTime(readTime)} demonstrates the exact execution timing. Each time React calls ArticleCard, the function call in curly braces executes, logging its output to the console during render. In development with StrictMode enabled, React invokes the component twice to check for side effects, logging twice. Because expressions execute on each render, values must be computed before the JSX line that consumes them. Dynamic values that change over time in response to user interaction require React state hooks, introduced in Lecture 14.

Synchronous expression evaluation into immutable element descriptors
1. let headline = "Night Trains";
2. const card = <h2>{headline}</h2>; --> descriptor captures "Night Trains"
3. headline = "Alps Reopen";         --> variable changes; descriptor unchanged
PRINCIPLE 4

The code in braces runs each time React renders the component

When React renders a component, it invokes the function from top to bottom. Each expression inside curly braces executes synchronously during that run, computing its value and storing it directly into the in-memory element descriptor. The rendered descriptor captures the value at that moment in time. Reassigning a local variable after creating an element does not update the screen.

We should do this:

const card = <h2>{title}</h2>;
evaluates "Night Trains"
return card;
descriptor holds frozen value

Why does rendering a boolean variable produce an empty slot instead of visible text?

ANSWER

The code does not work. React's primitive render matrix treats booleans as invisible empty slots that emit zero DOM nodes.

When React reconciles JSX child expressions, it routes values according to their runtime data types. Strings and numbers evaluate directly into visible DOM text nodes ({readTime} prints "4", and {0} prints "0"). In contrast, the primitive values true, false, null, and undefined are classified as empty slots. React skips these values entirely, appending nothing to the DOM tree. Because undefined renders as an empty slot, typographical errors in property names fail silently. If a developer writes {article.titel} instead of {article.title}, JavaScript evaluates the missing property to undefined, and React renders an empty heading without throwing an error. When a boolean flag must appear as literal text on screen, convert it explicitly using a ternary expression ({isFeatured ? 'Featured' : 'Regular'}) or the String() function.

Why does splitting an expression and adjacent text across separate lines delete the separating space?

ANSWER

The code does not work. The JSX compiler strips whitespace that contains line breaks at the boundaries of text lines.

In native HTML, browsers collapse whitespace containing newlines into a single horizontal space. In contrast, the JSX compiler optimizes string output by trimming leading and trailing whitespace that includes a line break. When {readTime} sits at the end of one line and min read begins on the next, the compiler strips the newline and the indentation spaces preceding min read. The text node renders directly adjacent to the evaluated number, producing the joined string 4min read.

The JSX compiler strips whitespace that contains line breaks at the beginning and end of text lines. For the interview

The Interview Question: How do you use JavaScript expressions inside JSX with curly braces?

1. The Hidden Signal

The interviewer is not merely checking if you know where to type curly braces. They are probing your understanding of ECMAScript compiler grammar, the difference between expressions and statements, and how React processes different data types during render. A junior developer says curly braces are "for inserting variables into HTML." A senior engineer explains that curly braces establish an evaluation window in content and attributes where expressions become arguments to _jsx() function calls, evaluating synchronously during render.

2. The Classic Trap

The classic trap is attempting to write control-flow statements like if or for inside curly braces ({if (active) ...}). Candidates often forget that JSX compiles into JavaScript function arguments, which grammatically reject control statements. Another frequent trap is quoting dynamic attributes (src="{avatarUrl}"), which emits literal strings and triggers network 404 errors, or passing raw objects and Date instances into content, causing fatal runtime crashes.

3. What is Actually Going On

Under the hood, the JSX compiler treats everything outside curly braces as static text. When it encounters {, it steps into JavaScript evaluation mode. The expression inside is evaluated once when the component function executes, and its result is placed into the React element descriptor. React's primitive render matrix translates strings and numbers into DOM text nodes, while treating booleans, null, and undefined as empty slots that emit zero DOM nodes. Non-primitive objects and Date instances stop the render with an error, requiring explicit formatting. Double curlies (style={{}}) are simply an outer JSX evaluation window enclosing an inner JavaScript object literal.

4. Where It Gets Tricky

Where this gets tricky in production is whitespace handling and boolean zeros. In JSX, line breaks strip surrounding whitespace, causing {readTime} and min read on separate lines to render as 4min read unless an explicit {' '} token is added. Additionally, while false renders nothing, the number 0 renders visibly, meaning {count && <Badge />} displays a visible "0" when count is zero, a common defect explored further in Lecture 10.

Glossary

  • JSX Evaluation Window: The syntactic zone opened by curly braces ({}) in content or attributes that switches the compiler from static markup to live JavaScript execution.
  • Expression: An ECMAScript code unit that evaluates to a discrete value in memory (such as variables, math operations, ternaries, and function calls) and can be passed into JSX braces.
  • Statement: An ECMAScript code unit that controls execution flow or performs actions without producing a value (such as if, for, while, or const) and is forbidden inside JSX braces.
  • Primitive Render Matrix: React's internal type-routing rules that paint strings and numbers as DOM text nodes while rendering booleans, null, and undefined as empty slots.
  • Empty Slot: An invisible DOM placeholder emitted when React encounters booleans, null, or undefined in child content, emitting zero DOM nodes.
  • Double Curlies: A syntactic combination where an outer pair of JSX curly braces encloses an inner JavaScript object literal, commonly used in inline style props.

Summary

Architectural Takeaways & Decision Matrix

❒ The JSX Evaluation Window Invariant

➔ IF projecting dynamic values into content or attribute positions, THEN wrap variables and expressions in curly braces ({}) to open the evaluation window.

➔ IF authoring text outside curly braces, THEN treat it as static character content because the compiler does not evaluate unbracketed identifiers.

❒ Dynamic Attribute Binding

➔ IF binding an attribute to a dynamic JavaScript value, THEN use unquoted curly braces (src={avatarUrl}).

➔ IF passing a static, unchanging string literal, THEN use quotes (alt="Author"), avoiding curly braces inside quotes which remain literal characters.

❒ Expressions Versus Statements

➔ IF evaluating logic inside JSX curly braces, THEN use value-producing expressions (variables, math, ternaries, function calls).

➔ IF control flow requires statements (if, for, while), THEN execute them above the return statement and pass the resulting value into JSX.

❒ Primitive Render Matrix and Object Content

➔ IF displaying dates or objects in JSX child content, THEN format them into primitive strings or numbers before placing them inside curly braces.

➔ IF passing an object to an element, THEN do so only for attributes that accept objects (such as style), avoiding objects in content which crash the render.
