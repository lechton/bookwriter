Lecture 7: Container Composition with Children and Prop Spreading

Interview Question

CORE

How do the children prop, spread attributes, and default values work?

Imagine this scenario:

  1. You built a component that shows a news story with its title and author.
  2. One story has no author, but the page still shows the word "By" with nothing after it.
  3. How can one component keep the same design for every story and let each story choose its content?

One design, different content for every story

On a news site, every story is shown with the same design: the same border, the same spacing, the same layout. Only the content changes. One story has a title and an author's name, another a title and a photo, another only a title.

In this chapter, we write one React component that keeps the design the same and lets each story decide its own content. In React, this approach is enabled by a prop named children.

Before we get there, let's see why the props from Lecture 6 are not enough. With props alone, we would write a NewsCard component that receives one prop for each piece of text it shows, here a title and an author:

One prop for each piece of text
1function NewsCard({ title, author }) {
2 return (
3 <article className="card">
4 <h2>{title}</h2>
5 <p>By {author}</p>
Shown even when there is no author
6 </article>
7 );
8}

This works while every story has a title and an author. Now a story arrives without an author. The component still draws the paragraph, and the reader sees the word "By" with nothing after it. A story with a photo has no place for the photo at all, unless we add one more prop for it. Every new kind of story means one more prop and one more change to NewsCard.

This lesson answers three questions:

  • How does content written between a component's tags reach the component?
  • How do we pass attributes like id and aria-label through a component without listing each one?
  • What does a component do when the caller leaves a prop out?

The questions stand on four earlier lessons:

  • Lecture 3 (JSX): JSX compiles every tag into a _jsx call that returns an object describing the element. Attributes such as aria-label and data-story-id keep their dashes, and class is written className.
  • Lecture 4 (Values in JSX): Curly braces put a JavaScript value into the markup. null, undefined, and false show nothing on the screen, and + joins two strings into one.
  • Lecture 5 (The component tree): Writing one tag inside another builds the tree of components and elements on the page.
  • Lecture 6 (Props): The attributes on a component's tag arrive as one props object, and braces in the parameter list unpack its keys. A default such as author = 'Staff' fills a prop the caller left out.

Content between a component's tags arrives as the children prop

To keep the design in one place, we create a component called CardContainer. Its only job is to draw the shared design. The story's content goes between its opening and closing tags, the same way you nest an <h2> inside an <article>:

Content between the tags
1<CardContainer>
2 <h2>New Park Opens Today</h2>
This whole line goes to CardContainer
3</CardContainer>

Look at what sits between <CardContainer> and </CardContainer>: the whole line <h2>New Park Opens Today</h2> React does not throw it away. It takes everything written between the opening tag and the closing tag and hands it to CardContainer as a prop. That prop is always called children; you do not choose the name. You can picture it like this: <CardContainer> the children are here </CardContainer>.

So inside CardContainer, the variable children holds the <h2>New Park Opens Today</h2> the caller wrote. If the caller writes three elements between the tags, children holds all three.

The _jsx call from Lecture 3 shows the same thing. The nested element is passed as one more prop, named children:

Compiled call
1_jsx(CardContainer, {
2 children: _jsx("h2", { children: "New Park Opens Today" }),
The nested h2
3});

To show that content, CardContainer unpacks children from its props, as Lecture 6 taught for any prop, and writes {children} in its markup at the place where the content should appear:

Where the container places children
1function CardContainer({ children }) {
2 return <div className="card">{children}</div>;
The h2 lands in the div
3}

Because the content comes from the caller, the same CardContainer works for a different story. Here the caller writes a photo and a headline between the tags:

A photo and a headline as children
1<CardContainer>
2 <img src="/school.jpg" alt="Children walking to school" />
First child
3 <h2>School Starts on Monday</h2>
Second child
4</CardContainer>

Now children holds both elements, and they appear inside the shared design in the order the caller wrote them. Whatever you write between a component's tags reaches that component as its children prop.

A component like CardContainer, which draws a shared design and shows whatever it receives as children, is called a container component. The caller decides the content, and the container decides the design around it. Lecture 10 shows how a container can show nothing at all when it receives no content.

Rest syntax collects the props you did not name

A container often receives more props than it uses itself, such as an id or an aria-label that belong on its outer element. To collect them, we use rest syntax, a plain JavaScript feature. In destructuring, you name the keys you want, and three dots before a last name collect every other key into a new object. Here it is on a simple object:

Rest syntax on a plain object
1const story = { title: 'New Park', id: 'top', date: 'May 3' };
2const { title, ...rest } = story;
Title is 'New Park'
3console.log(rest);
{ id: 'top', date: 'May 3' }

title leaves the object by name, and rest holds the keys that are left. The story object itself does not change.

The props object is an ordinary object, so the same syntax works in a component's parameter list. Say the caller writes <CardContainer id="top" aria-label="Main story">

Rest syntax on props
1function CardContainer({ children, ...rest }) {
2 console.log(rest);
{ id: 'top', 'aria-label': 'Main story' }
3 return <div className="card">{children}</div>;
4}

children takes the nested content by name, and rest collects id and aria-label. Rest syntax takes out the keys you name and gathers all the others into one object.

Spread writes every key of an object as an attribute

Once the remaining props sit together in one object, we need a way to write them onto an element. JSX has a form for this: {...object} inside a tag writes each key of the object as an attribute. To see it, compare two links, one written with spread and one written by hand:

Spread attributes
1const link = { href: '/sport', title: 'Sport news' };
2const first = <a {...link}>Sport</a>;
Link gives href and title
3const second = <a href="/sport" title="Sport news">Sport</a>;
Written by hand

The two links are the same. React reads the object and writes href and title on the <a>, so the browser gets <a href="/sport" title="Sport news">Sport</a> This is called JSX spread attributes.

It works with any object, including keys with dashes:

Spread attributes with dashes
1const ids = { id: 'top', 'data-story-id': '42' };
2const section = <section {...ids}>Top story</section>;
Id and data-story-id

The browser gets <section id="top" data-story-id="42"> Rest syntax gathers keys into an object, and spread writes an object's keys back out as attributes.

QUESTION 1

Content placed between tags arrives as the children prop

A developer writes a CardContainer component to give every story on a news site the same design. In the parent component, the developer writes a headline between the container's opening and closing tags:

A headline between the container tags
1function Feed() {

3 <CardContainer>
4 <h2>New Park Opens Today</h2>

Inside CardContainer, the component returns its <div> but never writes {children}:

A container that forgets children

3}

When the browser renders the page, DevTools shows an empty <div class="card"></div>. The headline is missing from the screen, and the browser console shows no error.

Why does content written between a component's tags disappear from the screen?

ANSWER

The code does not do what we wanted. React did hand the headline to CardContainer as children, but the component never put it anywhere.

As the first section showed, everything written between <CardContainer> and </CardContainer> reaches the component as a prop named children. Here that is the whole line <h2>New Park Opens Today</h2> Receiving the prop is only half of the work. The component decides where the content appears by writing {children} in its markup. This CardContainer returns <div className="card" /> and never mentions children, so React draws the empty <div> and the headline goes nowhere. React gives no warning, because a component is free to ignore any prop it receives.

The fix is to unpack children and write it inside the <div>:

The container places children

Receives the content
2 return <div className="card">{children}</div>;
The headline goes here
3}

PRINCIPLE 1

Content between the tags arrives as the children prop

children prop the prop that holds everything written between a component's opening and closing tags

Everything you write between a component's opening and closing tags reaches that component as a prop named children. The content appears on the screen only where the component writes {children} in its returned JSX. If the component never writes {children}, React draws the rest of the component and the content is missing, with no warning.

We should do this:
function Card({ children }) {
return <div className="card">{children}</div>;
shows the content
}
We should not do this:
function Card({ children }) {
return <div className="card" />;
content never appears
}

In our runtime test, rendering <CardContainer><h2>New Park Opens Today</h2></CardContainer> with {children} inside the <div> showed the headline inside the card.

QUESTION 2

Let the caller fill the container instead of adding a prop for every piece

The first section showed NewsCard, which receives one prop for each piece of text. A page renders two stories with it, one with an author and one without:

Two stories through NewsCard
1function StoryFeed() {
Renders stories through NewsCard
2 return (
3 <div className="feed">
4 <NewsCard title="New Park Opens Today" author="Anna Lyon" />
5 <NewsCard title="Rain Expected This Weekend" />

The first story shows "By Anna Lyon". The second story shows the word "By" with nothing after it, because NewsCard draws <p>By {author}</p> for every story, and author is undefined here. Then a third story arrives with a photo, and NewsCard has no place for it.

Do we add a new prop to NewsCard for every piece a story might have?

ANSWER

The code does not do what we wanted. Every optional piece becomes one more prop, and NewsCard draws each piece for every story, even when the story has none.

To support the photo, NewsCard would need an imageUrl prop, then a check for stories without a photo, then another prop for the next kind of story. Each change edits the same shared file, and the order of the pieces stays fixed inside it: a caller cannot put the author above the title without yet another prop.

CardContainer turns this around. It draws only the shared design and writes {children} where the content goes. Each caller writes the elements its story has, in the order it wants. The story with an author writes the title and the author line. The story without an author writes only the title, so no empty "By" appears. The photo story writes an <img>, and CardContainer does not change at all. A named prop stays only for something every story must show in the same place, such as a title.

One prop per piece versus content from the caller
NewsCard({ title, author }):
+---------------------------------------+
| <h2>Rain Expected This Weekend</h2>   |
| <p>By </p>   (no author!)             |
+---------------------------------------+

CardContainer({ children }):
+---------------------------------------+
| {children}                            |
|   <h2>Rain Expected This Weekend</h2> |

PRINCIPLE 2

Let the caller fill the container instead of adding a prop for every piece

composition building a component's content from elements the caller writes between its tags

When stories need different content inside the same design, let each caller write its content between the container's tags. This is called composition. Adding a prop for each optional piece makes the component draw that piece for every story, even when the story has none, and every new kind of story changes the shared file. Keep a named prop only for something every story must show in the same place.

It is best practice to do this:
<CardContainer>
<h2>Rain Expected This Weekend</h2>
no author, no empty line
</CardContainer>
Instead of doing this:
<NewsCard
title="Rain Expected This Weekend"
shows "By" with no author
/>

In our test, the story without an author showed "By" with nothing after it through NewsCard. Through CardContainer, the same story showed only its title, and a third story with a photo needed no change to CardContainer.jsx.

QUESTION 3

Spread only the props the container does not use

Callers need to put an id or an aria-label on the card. To pass them all at once, a developer spreads the whole props object onto the container's <div>:

Spreading the whole props object
1function CardContainer(props) {
Receives the full props object
2 return (
3 <div className="card" {...props}>
Every prop lands on the div
4 {props.children}
5 </div>
6 );
7}

A caller renders a story with two props that are meant for the component, not for the browser: <CardContainer isFeatured={true} date="May 3"><h2>New Park Opens Today</h2></CardContainer> When the page loads, the console warns: Warning: React does not recognize the isFeatured prop on a DOM element In DevTools, the element reads <div class="card" date="May 3">

Can we pass the whole props object onto the container element with spread?

ANSWER

The code does not do what we wanted. Spreading the whole props object writes the component's own props onto the browser element too.

{...props} writes every key of the object as an attribute, and props holds everything the caller passed, including props that only the component should read. React checks the attributes it writes on a browser element such as <div>. For a camelCase name like isFeatured, it warns that the browser does not recognize it. A lowercase name like date passes the check, so React writes date="May 3" straight into the page. If a component reads a title prop for its heading and also spreads everything onto a <div>, the same title becomes a tooltip when the mouse rests on the card.

The fix uses the two tools from the first sections. Rest syntax takes out the props the component reads, { children, isFeatured, ...rest } and leaves only the others in rest, such as id, aria-label, and data-story-id. Then spread writes only {...rest} on the <div>.

Rest syntax keeps the component's props off the div
Props object from the caller:
{ children: <h2>, isFeatured: true, id: "top", aria-label: "Main story" }

Read by CardContainer:          Collected into rest:
children, isFeatured            { id: "top", aria-label: "Main story" }

<div className="card" {...rest}>
Browser DOM: <div class="card" id="top" aria-label="Main story">
PRINCIPLE 3

Spread only the props the container does not use

rest syntax collecting the keys you did not name into a new object with ...rest
JSX spread attributes writing each key of an object as an attribute with {...rest}

When a container passes extra attributes on to a browser element, unpack the props it reads and collect the others with rest syntax: { children, isFeatured, ...rest }. Then write only those others on the element with JSX spread attributes: {...rest}. Spreading the whole props object also writes the component's own props on the element: React warns about camelCase names and writes lowercase ones into the page.

We should do this:
function Card({ isFeatured, children, ...rest }) {
return <div className="card" {...rest}>{children}</div>;
only rest
}
We should not do this:
function Card(props) {
return <div className="card" {...props}>{props.children}</div>;
all props
}

In our runtime test, spreading props with isFeatured={true} and date="May 3" wrote date="May 3" on the <div> and logged a console warning. After the change to { children, isFeatured, ...rest } the console stayed clean, and id and aria-label reached the <div> as intended.

QUESTION 4

Around a spread, the last attribute wins

The card container defines its base styling with className="card". To allow callers to forward extra attributes, the developer writes <div className="card" {...rest}>{children}</div> A caller passes a custom highlight class:

Caller Passing Custom Class
1function FeaturedStory() {
Caller highlights story
2 return (
3 <CardContainer className="featured">
Passes custom class
4 <h2>New Park Opens Today</h2>
5 </CardContainer>
6 );
7}

When the page loads, the card loses its rounded border and padding. Inspecting the element in DevTools reveals class="featured". The base class "card" has completely disappeared from the DOM element.

Why does a caller class name overwrite the container base class?

ANSWER

The code does not do what we wanted. JSX applies attributes from left to right, so an attribute in rest replaces any attribute written before the spread.

JSX applies attributes strictly in the order they are written. When an attribute appears more than once on the same tag, the last attribute evaluated wins. In <div className="card" {...rest}> the spread attribute appears after className="card". Because rest contains className: "featured", that incoming value completely replaces "card". The component loses its foundational styles.

If the developer places className="card" after {...rest} (<div {...rest} className="card">), the container's base class overwrites the caller's class completely, preventing callers from adding custom utility styles. Attributes in JSX never merge automatically. To preserve both classes, unpack className in the parameter list and join both strings explicitly using string concatenation: className={'card ' + className}

Left-to-right attribute evaluation order
Case 1: Attribute before spread:
<div className="card" {...rest} />
rest has { className: "featured" }   --> class="featured" (base lost!)

Case 2: Attribute after spread:
<div {...rest} className="card" />
rest has { className: "featured" }   --> class="card" (caller lost!)

Case 3: Explicitly joined in JavaScript:
<div className={'card ' + className} {...rest} />
both classes joined                  --> class="card featured" (both kept!)
PRINCIPLE 4

Around a spread, the last attribute wins

attribute precedence the left-to-right order where later JSX attributes overwrite earlier ones

JSX evaluates attributes from left to right through attribute precedence. When the same attribute appears more than once on an element, the last one written wins. An attribute placed before {...rest} serves as an overridable default that caller props replace. An attribute placed after {...rest} is an enforced value that replaces caller props. When both sides must contribute a class name, extract className and join both strings explicitly.

It is best practice to do this:
function Card({ className, children, ...rest }) {
const fullClass = 'card ' + className;
joins base with caller
return <div className={fullClass} {...rest}>{children}</div>;
}
Instead of doing this:
function Card({ children, ...rest }) {
return <div className="card" {...rest}>{children}</div>;
caller overwrites
}

In our test, placing className="card" before {...rest} when the caller passed className="featured" rendered class="featured". Placing className="card" after {...rest} rendered class="card". When className was unpacked and joined with className={'card ' + className} the browser DOM rendered class="card featured", preserving both base borders and custom highlights.

QUESTION 5

A default fills a prop the caller left out

The developer merges class names using className={'card ' + className} But when a standard story renders without passing a custom class (<CardContainer><h2>Rain Expected This Weekend</h2></CardContainer>), inspecting the DOM in DevTools reveals a surprising attribute: class="card undefined". Furthermore, when a container renders without nested content (<CardContainer />), the page shows an empty card with no notice.

Missing Class Name Call Site
1function StandardFeed() {

2 return (
3 <CardContainer>

4 <h2>Rain Expected This Weekend</h2>

How do we prevent undefined appearing in merged classes when a prop is missing?

ANSWER

The code does not do what we wanted. A missing prop evaluates to undefined, so concatenating it with a string produces the word undefined in the class attribute.

When a caller omits an attribute, that property evaluates to undefined. Inside JSX content, {undefined} shows nothing on the screen. But inside JavaScript string concatenation, 'card ' + undefined coerces undefined into the string "undefined", producing "card undefined" in the DOM.

To fix this, assign a default parameter value in the destructuring list: className = ''. When the caller omits className or passes undefined, the variable receives '', producing the clean string 'card '. Similarly, assigning children = <p>No story yet</p> provides a fallback element when no children are nested. Remember the rule established in Lecture 6: default parameters engage strictly when a value is missing or undefined; they do not engage when a caller passes null or false.

Evaluating missing prop against default parameter fallback
Caller Passes:          Parameter Result:         DOM Output:
className="featured"    className = "featured"    class="card featured"
className={undefined}   className = "" (default)  class="card " (clean!)
className omitted       className = "" (default)  class="card " (clean!)
className={null}        className = null          class="card null" (no default)
PRINCIPLE 5

A default fills a prop the caller left out

default parameter value a fallback value assigned in destructuring when a prop is missing or undefined

A missing prop evaluates to undefined. In JSX content, undefined shows nothing. But in string concatenation, 'card ' + undefined coerces undefined into the text 'card undefined'. Assign a default parameter value in the destructuring list to fill a missing prop: className = ''. Default parameter values engage only when a prop is missing or strictly undefined; they do not engage when a caller passes null or false.

We should do this:

Component Summary

App

The root component places the news page inside a main element. Notice it passes no props to StoryList. Why? It only decides where the page sits, not what the stories say.

StoryList

The caller component writes the content of each story between CardContainer tags. Notice the three stories have different content, and one passes aria-label and className. Why? Each story decides its own content, while the design stays in one place.

CardContainercolor="..." className="..." aria-label="..."

The container component draws the shared design and places children inside its div. Notice it fills color and className with defaults and spreads the remaining props onto the div. Why? Callers can leave props out or add attributes without changing this file.

Without children, one component would need a prop for every piece a story might have, and it would draw those pieces even for stories that do not have them. With children, CardContainer keeps the design and each caller writes its own content. Because CardContainer unpacks the props it reads and spreads only ...rest, callers can add attributes such as aria-label without the component's own props reaching the page.

Where you will meet this

  1. Dialogs: A dialog component draws the window, the backdrop, and the close button, and each caller writes its own text or form fields between the tags as children.
  2. News and product cards: A card component keeps the same border and spacing for every item, while each item writes its own title, author, date, or photo.
  3. Form fields: A field component draws the label and the error message, and spreads attributes such as id, aria-describedby, and disabled onto the <input> with {...rest}.

For the interview

The Interview Question: How do the children prop, spread attributes, and default values work?

1. The Hidden Signal

The interviewer wants to know whether you understand where these values come from. A weak answer treats props as HTML attributes. A strong answer explains that JSX compiles the content between a component's tags into the children prop (_jsx(CardContainer, { children: ... })), that a component which passes attributes on should unpack the props it reads and spread only ...rest, that JSX applies attributes from left to right, and that a default parameter fills a prop the caller left out.

2. The Classic Trap

Assuming children is always an array. With one nested element, children is a single element object. With two or more, it is an array. With plain text, it is a string. Calling children.map() when there is only one child crashes with TypeError: children.map is not a function Another trap is writing <div {...props} /> which writes the component's own props onto the browser element and triggers React warnings.

3. What is Actually Going On

At compile time, the nested JSX becomes the children key of the props object. The container receives element objects that describe the content, not finished HTML. Spread copies the keys of an object as attributes from left to right, and whichever value comes last wins. A default value applies only when a prop is undefined or left out, never when it is null or false.

4. Where It Gets Tricky

If a caller passes a children attribute and also writes content between the tags, <Card children="attr">nested</Card> the content between the tags wins, because the compiler adds it after the attributes. Also, if a container never writes {children}, the components written between its tags never run at all.

Glossary

  • children prop: The prop that holds everything written between a component's opening and closing tags.
  • container component: A component that draws a shared design and shows whatever it receives as children.
  • composition: Building a component's content from elements the caller writes between its tags, instead of adding a prop for every piece.
  • rest syntax: The JavaScript ...rest form in destructuring that collects the keys you did not name into a new object.
  • JSX spread attributes: The {...rest} form in a JSX tag that writes each key of an object as an attribute.
  • default parameter value: A value written in the parameter list, such as className = '', that fills a prop when it is undefined or left out.

Summary

Container Composition and Prop Spreading Rules for keeping one design and passing attributes on

❒ Content Through Children

➔ IF stories need different content inside the same design, THEN write {children} in the container and let each caller write its content between the tags, instead of adding a prop for every piece.

➔ IF every story must show something in the same place, such as a title, THEN make it a named prop and place {children} next to it.

❒ Passing Attributes On

➔ IF a container passes extra attributes to a browser element, THEN unpack the props it reads and spread only ...rest onto the element.

➔ IF a component receives its own props, such as isFeatured, THEN never spread the whole props object onto a browser element.

❒ Attribute Order and Defaults

➔ IF an attribute should be a default the caller can replace, THEN write it before {...rest}; IF it must always win, THEN write it after {...rest}.

➔ IF a container joins its own class with the caller's class, THEN give className the default '' and join the two strings yourself.
