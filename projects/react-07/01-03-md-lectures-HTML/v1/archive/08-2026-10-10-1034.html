Lecture 8: Splitting Components with ES Module Imports and Exports

Interview Question

CORE

How do you split components across files, and how do default and named imports differ?

Imagine this scenario:

  1. Julian opens the morning edition codebase for The National Times to add a breaking news banner.
  2. The editorial desk needs an article card and status badges shared across three different page layouts.
  3. A developer attempts to share the markup by copying and pasting the card function across multiple files.
  4. Why does every minor update to the card design trigger merge conflicts and duplicated bug fixes?
  5. Duplicated code drifts out of sync, displaying inconsistent article cards and broken badge colors in production.
  6. The team traps multiple components inside one giant file instead of organizing them into dedicated modules.
  7. Today, we organize components into clean modules, master default and named imports, and prevent silent import errors.

The Friction of Monolithic Files and Copy-Paste Components

Every web application grows from a single starter file into dozens of user interface sections. In static websites, developers often wrote all their markup inside one long document, copying chunks of HTML whenever they needed the same card on another page. In modern applications, keeping multiple components inside a single monolithic file makes code hard to read and impossible to share cleanly across pages. To solve this, JavaScript and React use modules: independent files that export components so other parts of your application can import and reuse them.

To see this in action on The National Times, you open your editor to build the article feed. At first, you write the ArticleCard component directly inside App.jsx. Then you write the Badge component in that same file. Before long, App.jsx stretches over twelve hundred lines of code. When another engineer wants to use ArticleCard on the search page, they cannot import it without importing the entire App component and all its unrelated layout logic.

It is possible that a developer may fall into the copy-paste trap when facing this limitation. They may copy the entire card function into the new search page file, thinking this avoids file refactoring. Now two identical copies of ArticleCard exist in the codebase. When a designer updates the card spacing or changes a CSS class, one copy gets updated while the other is forgotten. The two cards drift apart, creating visual bugs and confusing readers.

Notice what went wrong. The ArticleCard and Badge components are trapped inside the local scope of App.jsx. Other pages cannot reach them. If the editorial desk creates a new archive section, engineers must either duplicate the functions or cram the new section directly into App.jsx. As more features arrive, merge conflicts multiply, and finding a specific component becomes exhausting.

To resolve this architectural bottleneck, modern JavaScript and React rely on ES modules to organize components into dedicated files. You create a new file named ArticleCard.jsx under src/components/, export the card component, and import it wherever it is needed. Each component lives in its own file with its own clear responsibilities. When a design update occurs, you edit the component in one place, and every page that imports it automatically reflects the change.

⚡ IN THE WILD

Why do monolithic files create team friction?

Teams keeping multiple components inside one giant file suffer frequent git merge conflicts and code duplication. When two developers edit App.jsx simultaneously—one updating the article card while the other adjusts the primary layout—git reports a massive conflict because both touched the same giant file. If a developer copies the card to another page to bypass the file, bug fixes applied to one copy never reach the other. Organizing components into dedicated ES modules under src/components/ solves this by giving each component its own isolated file. Teams edit components independently, share them cleanly across pages, and eliminate duplicated code.

What Are ES Modules and How Does React Use Imports?

In modern web development, every JavaScript file is an isolated module. Variables, functions, and objects defined inside a module are private by default. Other files cannot access or modify them unless the file explicitly shares them using the export keyword. This isolation prevents global namespace collisions and keeps your codebase modular and predictable.

React components are standard JavaScript functions, so they use the official ECMAScript Module (ES Module) system built into the language. JavaScript provides two primary ways to export values from a module: default exports and named exports. A default export represents the primary value or component that a file provides, declared with export default A file can have at most one default export. In contrast, named exports allow a module to share multiple values or helper components, declared with export function Name()

When importing a named export, you place its exact name inside curly braces: import { Badge } from './ArticleCard.jsx' Notice the curly braces {}. In JavaScript, these braces look similar to object destructuring, but in module syntax they are a static language construct. They tell the JavaScript engine to link directly to the specific named export binding declared in that module. Unlike runtime object destructuring, ES module import bindings are evaluated and linked statically before any component function executes.

Under the hood, modern build tools like Vite use the ES module dependency tree to resolve files and package code for the browser. When you write an import statement, the bundler checks that the target file exists on disk and verifies that the requested export name matches an exported binding. If you import a named export with default syntax, or misspell the exported name, the build tool halts immediately with an explicit error before invalid code reaches the browser.

Principles of React: Splitting Components with Imports and Exports

When preparing for technical interviews, candidates must explain how components are organized across files, how default and named imports differ in mechanics and trade-offs, why exported functions must carry explicit names, and how the module dependency tree operates. To master these concepts, we formalize the six governing principles of component imports and exports:

PRINCIPLE 1

Give Each Shared Component Its Own Module

module boundary an isolated file that encapsulates internal logic and exposes explicit exports

Move a component into its own file under src/components/ when another file needs it or when its current file becomes hard to scan. Export the component from that file, and keep private helpers used by only one component unexported in that same file.

It is best practice to do this:
export default function ArticleCard() {
Dedicated module export
return <article className="card" />;
}
Instead of doing this:
function ArticleCard() {}
Monolithic file dumps everything
function Badge() {}
export default function App() {}

Moving a component into its own module takes three steps: (1) create a new file such as src/components/ArticleCard.jsx (2) export the component function from that file, and (3) import it in every file that renders it.

Top-level variables and helper functions defined in a module remain completely private unless you add the export keyword. If a helper function like formatDate is only used inside ArticleCard, keeping it unexported protects it from outside interference and keeps your module contract clean.

Private Module Encapsulation
1function formatDate(date) {
Private helper: NOT exported
2 return `Published on ${date}`;
3}
4export default function ArticleCard({ date }) {
5 return (
6 <article className="card">
7 <p>{formatDate(date)}</p>
8 </article>
9 );
10}

Notice what happens if another file attempts to import an unexported helper: import { formatDate } from './ArticleCard.jsx' The build immediately stops with an explicit error: [MISSING_EXPORT] "formatDate" is not exported by "src/components/ArticleCard.jsx" Unexported code remains strictly private to the module.

PRINCIPLE 2

Import Each Component in the Form It Was Exported

module linking the process where the JavaScript engine connects import statements to corresponding export declarations

Every file that renders a component must import it using the exact syntax matching its export. Use import Component from 'module-path' for a default export and import { Component } from 'module-path' for a named export. ES modules link imports to exports by kind and name before any component runs.

We should do this:
import ArticleCard from './ArticleCard.jsx';
Default import
import { Badge } from './ArticleCard.jsx';
Named import
We should not do this:
import { ArticleCard } from './ArticleCard.jsx';
Wrong: default
import Badge from './ArticleCard.jsx';
Wrong: named export

When you import a default export with curly braces (import { ArticleCard }), or import a named export without curly braces (import Badge), the syntax violates the module contract.

Watch how different tools report this error:

If you forget to write an import statement entirely, JavaScript throws a runtime error when executing the component: "ReferenceError: ArticleCard is not defined"

PRINCIPLE 3

Choose the Export Style by What the File Provides

name drift an inconsistency where different files import the same default export under different local names

Use a default export when a file exists to provide one primary component, and use named exports when a file provides multiple components or utilities. A default import can take any local variable name, while a named import must match the exported name character for character.

It is best practice to do this:
export default function ArticleCard() {}
Primary card export
export function Badge({ text }) {}
Secondary utility export
Instead of doing this:
import AuthorTag from './ArticleCard.jsx';
Silently renames card

The fundamental mechanical difference between default and named exports lies in name binding. Because a default export is the single fallback value of a module, the importing file can assign it any local variable name.

Look at how a default import permits arbitrary naming:

Arbitrary Default Import Naming
1import AuthorTag from './components/ArticleCard.jsx';
Misleading name
2
3export default function App() {
4 return (
5 <AuthorTag title="City News" />
Silently renders card
6 );
7}

The code above compiles and renders the article card with zero errors. However, it creates severe confusion: an engineer reading App.jsx thinks <AuthorTag /> is a small label, unaware that it renders an entire article card. Furthermore, searching the codebase for <ArticleCard /> will never find this usage.

In contrast, named exports strictly enforce that the import identifier inside curly braces matches the exported identifier. If you rename the named export Badge to StatusBadge in the source file, any file still importing { Badge } immediately fails to build with an explicit missing export error. Named exports make refactoring predictable and safe.

PRINCIPLE 4

Name Every Exported Component Function

anonymous component a component function declared without a name identifier in its definition

Always write exported components as named function declarations, such as export default function ArticleCard() {}. If you export an anonymous arrow function without a name, the JavaScript engine assigns it the fallback identifier default, and React prints <default> in its error callstacks and warnings.

We should do this:
export default function ArticleCard() {
Named function in error stacks
return <article>Latest News</article>;
}
We should not do this:
export default () => {
Anonymous export appears as <default>
return <article>Latest News</article>;
};

Official React documentation strongly discourages anonymous default exports like export default () => {} When a component function has no name, the JavaScript runtime assigns it the name of the export key, which is the literal string "default".

Look at what happens in the console when an anonymous component encounters a runtime error:

Error Stack: Anonymous Component Crash
1Uncaught Error: Failed to load article data

Anonymous function lacks name
3The above error occurred in the <default> component:
4 at default (ArticleCard.jsx:2:1)
5 at App (App.jsx:5:3)

In a production codebase containing dozens of default-exported components, an error naming <default> provides zero clue about which component actually failed. You have to hunt through stack line numbers to find the file.

When you declare a named function, React displays the exact component name:

Error Stack: Named Component Crash
1Uncaught Error: Failed to load article data
2 at ArticleCard (ArticleCard.jsx:3:11)
Named function identified
3The above error occurred in the <ArticleCard> component:
4 at ArticleCard (ArticleCard.jsx:2:1)
5 at App (App.jsx:5:3)

Writing export default function ArticleCard() {} takes two seconds, guarantees clear React error stacks, and makes components easy to identify in React DevTools.

PRINCIPLE 5

Match Import Paths to Filenames Exactly, Including Case

case-sensitive file system an operating system storage model where uppercase and lowercase letters represent distinct files

Write every import path with the exact capitalization of the file on disk. The default macOS file system ignores letter casing and resolves ./components/articleCard.jsx to ArticleCard.jsx, while Linux build servers enforce strict case sensitivity and fail the build.

We should do this:
import ArticleCard from './components/ArticleCard.jsx';
Exact casing
We should not do this:
import ArticleCard from './components/articleCard.jsx';
Lowercase breaks

On macOS, the standard APFS file system is case-preserving but case-insensitive. If a file on disk is named ArticleCard.jsx, writing an import path with lowercase articleCard.jsx resolves and compiles with zero warnings on a developer's Mac laptop.

However, production build servers and continuous integration (CI) environments typically run Linux, where file systems are strictly case-sensitive. On Linux, articleCard.jsx and ArticleCard.jsx are completely different files. When your pull request runs in CI, the build crashes:

Linux CI Build Failure
1[UNRESOLVED_IMPORT] Could not resolve
Case mismatch fails Linux build
2 'components/articleCard.jsx' in src/App.jsx
3file: /home/runner/work/project/src/App.jsx:1:24
41: import ArticleCard from 'components/articleCard.jsx';
5 ^

This is one of the most frustrating "works on my machine" bugs in frontend engineering. Even worse, Git on macOS defaults to core.ignorecase = true. If you rename articleCard.jsx to ArticleCard.jsx in the Mac Finder, Git does not register the change. To fix the casing in Git, you must run an explicit rename command:

Terminal: Case-Sensitive Git Rename
1git mv src/components/articleCard.jsx \
2 src/components/ArticleCard.jsx
Forces Git to record casing

Always match the capitalization of your import paths to the exact filename on disk.

PRINCIPLE 6

Separate What Runs on Import from What Runs on Render

module evaluation the one-time execution of top-level code when a file is first imported
render execution the invocation of a component function by React to produce JSX markup

Importing a module executes its top-level code once when the module loads, regardless of how many files import it. In contrast, code placed inside a component function runs only when React actively renders that component in the user interface.

It is best practice to do this:
export default function ArticleCard() {
console.log("Render");
Runs on each component render
}
Instead of doing this:
console.log("Module");
Top-level code executes once on import
export default function ArticleCard() {}

In JavaScript, ES modules are singletons: when a file is imported for the first time, the JavaScript runtime evaluates all code written at the file's top level. If that same file is imported by five other components across your application, the top-level code does not execute again; the runtime returns the cached module export.

Look at how top-level module code compares to component render execution:

Module Evaluation vs Render Execution
1console.log('1. Module loaded');
Runs once on import
2
3export default function ArticleCard({ title }) {
4 console.log('2. Rendering component', title);
Runs on each render
5 return <article className="card">{title}</article>;
6}

Notice that "1. Module loaded: ArticleCard.jsx" prints exactly once when the file is imported. In contrast, "2. Rendering component:" prints twice because React rendered two card instances.

If App.jsx imports ArticleCard but never renders <ArticleCard /> on screen, the module still loads and prints "1. Module loaded", but the component function never executes. Bundlers include every imported module in the application package, so never put heavy calculations or unintended side effects at the module's top level.

In legacy web applications, keeping all components in a single monolithic file resulted in severe maintenance friction, frequent git merge conflicts, and copy-paste duplication. In React, splitting components into standard ES modules establishes clean architectural boundaries. ArticleCard.jsx acts as a dedicated module, exporting its primary component as a default export and secondary utilities as named exports. Because import syntax strictly dictates how values are consumed, developers enjoy build-time verification, clear stack traces, and seamless code reuse across the entire application.

Where you will meet this

  1. Design System Component Libraries: Enterprise UI libraries export primary components (like <Modal />) as default exports, while exposing sub-components (like { ModalHeader, ModalFooter }) as named exports.
  2. File-Based Routing Frameworks: Modern frameworks like Next.js and Remix require each page route file to export a single default React component to represent the page view.
  3. Utility and Icon Packages: Icon libraries package hundreds of SVG icons as individual named exports (import { SearchIcon, CloseIcon }), allowing bundlers to tree-shake unused icons from production bundles.

Glossary

  • Default Export: The primary value or component exported by a module, declared with export default and imported without curly braces under any local name.
  • Named Export: A specific value or component exported by a module using its declared name, imported inside curly braces matching the export identifier.
  • Module Dependency Tree: The hierarchical graph of file relationships formed by import and export statements, used by bundlers to package application code.
  • Render Tree: The runtime hierarchy of React component elements mounted on screen, evaluated by React during application rendering.
  • Name Drift: An inconsistency where different files import the same default export under different local names, making codebase searches difficult.
