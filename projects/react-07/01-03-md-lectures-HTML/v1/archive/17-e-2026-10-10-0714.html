Lecture 17: Batching and Updater Functions

Interview Question

CORE

How does React queue multiple state updates, and when do you need an updater function?

Imagine this scenario:

  1. A concert website sells tickets, and customers add seats with one button.
  2. A customer clicks '+3 Tickets' once to add three seats to the order.
  3. The click handler asks for one more ticket three times in a row.
  4. Why does the ticket counter show 1 instead of 3?
  5. The customer reaches checkout with one seat and loses the other two.
  6. No error appears, and none of the three requests was ignored.
  7. Today we learn exactly how React handles several changes in one click.

One click, several setter calls, and a number that does not add up

Until now, one click changed one piece of state. In real apps, a single click does more. One button might update a counter several times in a row. Another might turn on a loading indicator, wait for the server, and turn it back off.

When a single click triggers multiple state updates, two questions decide what ends up on screen:

  1. How many times does React update the screen during that click?
  2. Which starting value does each setter call actually read?

If you guess wrong, React will not throw an error. Your code will pass a quick glance, and still put the wrong numbers on the screen.

Before looking at the code, five earlier rules govern what happens during a single click:

  • Event Handlers (Lecture 13): You respond to user actions by attaching a function to an element, such as <button onClick={handleClick}> You pass the function without calling it. React runs that event handler every time the user clicks.
  • State and Setters (Lecture 14): Any value that changes on the screen must live in state. Writing const [tickets, setTickets] = useState(0) gives you two things. First, tickets is the state variable holding the current value, which starts at 0. Second, setTickets is the setter function, which is the only valid way to request a new value.
  • Render Timing (Lecture 15): Calling setTickets does not update the screen on that line of code. Instead, React waits until the entire event handler has finished running. Only then does React run your component function again to build the updated screen, a step called a render.
  • Fixed Snapshots (Lecture 16): During a render and its handlers, the value of tickets never changes in place. It remains locked as a fixed number called a snapshot.
  • Render Purity (Lecture 12): Any code that runs during a render must be pure. Given the same inputs, it must return the same output. It must never alter external variables or trigger popups.

Let's trace how these five rules behave when a single click calls multiple state setters.

How React processes multiple requests: batching and the update queue

When an event handler runs, it can call several state setters in sequence. How does React handle these requests?

In browser programming, modifying multiple elements forces repeated layout calculations and repaints. Running multiple screen updates for a single user action wastes computing resources.

React prevents unnecessary work by grouping state updates together. When a click handler calls several setters, React does not recalculate the screen after each call.

Instead, React waits until the entire event handler finishes executing. Only then does React recalculate the interface and paint the screen a single time.

We call this grouping process batching. Batching ensures that all state changes from a single event appear on the screen together.

Browser Layout Repaints vs. React Batched Commit
WITHOUT BATCHING (Traditional DOM - Costly Layout Repaints):
  Call setter 1 ──► [Calculate Layout] ──► [Repaint Screen]
  Call setter 2 ──► [Calculate Layout] ──► [Repaint Screen]
  Call setter 3 ──► [Calculate Layout] ──► [Repaint Screen] (Wasted passes)

WITH BATCHING (React Engine - Single Unified Paint):
  Call setter 1 ──┐
  Call setter 2 ──┼──► [Update Queue] ──► (Handler Done) ──► [Single Paint]
  Call setter 3 ──┘

Behind the scenes, React stores update requests in an internal update queue. Each setter call adds an instruction to this queue.

When you pass a raw number like setTickets(1), you queue a replacement instruction. You instruct React to replace the current state with 1.

When you pass a calculation function like setTickets(t => t + 1) you queue a calculation rule. This function is called an updater function.

Instead of storing a fixed number, React records the rule to compute the next value. When React processes the queue during render, it chains these functions in sequence.

Principles of React: Batching and Updater Functions

Each question below starts from code you could write today. The answer shows what React does with it. The principle turns that behavior into a rule for production code.

QUESTION 1

State Batching

Suppose you have two state variables, tickets and status. Inside the component function, above the return, the line console.log('render') prints render every time React runs the component. You run two state updates inside a single click handler:

App.jsx
1setTickets(1);
Updates tickets in memory
2setStatus('Confirmed');
3console.log('handler done');
Last line of the handler
  • First, you call a setter to update one state variable: setTickets(1)
  • Right below it, you call a second setter to update another state variable: setStatus('Confirmed')
  • On the last line, you log handler done to the console.

After one click, the console shows handler done first, and then render only once. Why does React update the screen once, instead of once for each setter?

ANSWER

The code worked properly. This is an example of proper usage of state batching.

React groups multiple state updates together into a single batch:

  • It does not update line by line: React does not update the screen immediately after each line of code runs.
  • It waits for the handler to finish: React waits until the entire click handler has finished running.
  • It updates the screen once: Finally, React updates the screen a single time and displays all new values at once.

This grouping is called batching. It saves work: React builds the new screen once, with both new values. A second click is a separate event. It gets its own handler run and its own screen update.

PRINCIPLE 1

Update related state together in the same handler

setTimeout a browser function that runs code later, after the click handler has finished

Call all your state setters directly inside the event handler. Trust React to batch them into a single screen update instead of attempting manual delays.

We should do this:
function handleConfirm() {
setTickets(1);
updates tickets directly
setStatus('Confirmed');
updates status message
}
QUESTION 2

The Frozen State Snapshot

Starting with tickets = 0, you want to add three tickets. You call the setter three times in a row inside a single click handler:

App.jsx
1setTickets(tickets + 1);
Queues replace with 0 + 1
2setTickets(tickets + 1);
3setTickets(tickets + 1);
Replaces with 1 three times
  • First, you call setTickets(tickets + 1) expecting to add the first ticket.
  • Right below it, you call setTickets(tickets + 1) expecting to add a second ticket.
  • On the third line, you call setTickets(tickets + 1) expecting to add a third ticket.

Why does the ticket counter on screen advance to 1 instead of 3?

ANSWER

The code did not work as intended. This is a failure from using plain values with a frozen snapshot.

React calculates state updates using a frozen snapshot:

  • The snapshot never changes during a handler: Throughout the entire click handler, the variable tickets stays frozen at 0.
  • Every line computes the same number: Each line calculates 0 + 1 = 1. This queues three replacement instructions.

To fix this, React allows you to pass an updater function (t => t + 1) to the setter. Instead of a fixed number, React records this calculation rule in an internal update queue. During render, it chains them sequentially. It passes each result into the next, advancing the counter to three.

Replacement Values vs. Updater Calculation Pipeline
REPLACEMENT INSTRUCTIONS (setTickets(tickets + 1)):
Snapshot: tickets = 0
  ├─ Call 1: setTickets(0 + 1) ──► Queue: [ Replace with 1 ]
  ├─ Call 2: setTickets(0 + 1) ──► Queue: [ Replace with 1 ]
  └─ Call 3: setTickets(0 + 1) ──► Queue: [ Replace with 1 ] ──► Screen: 1

CALCULATION PIPELINE (setTickets(t => t + 1)):
Snapshot: tickets = 0
  ├─ Call 1: setTickets(t => t+1) ──► Queue: [ 0 ──► +1 ──► 1 ]
  ├─ Call 2: setTickets(t => t+1) ──► Queue: [ 1 ──► +1 ──► 2 ]
  └─ Call 3: setTickets(t => t+1) ──► Queue: [ 2 ──► +1 ──► 3 ] ──► Screen: 3
PRINCIPLE 2

Never rely on state variables updating immediately in a handler

Treat state as a fixed snapshot during the entire event handler. When queuing multiple updates in one handler, pass updater functions instead of plain values.

We should do this:
setTickets(t => t + 1);
receives running total
setTickets(t => t + 1);
setTickets(t => t + 1);
advances total count by three
We should not do this:
setTickets(tickets + 1);
reads frozen snapshot 0
setTickets(tickets + 1);
setTickets(tickets + 1);
replaces total with 1 repeatedly
QUESTION 3

Updating State After an Asynchronous Pause

Sometimes a click handler needs to pause. For example, you might increment a pending count. Then you wait for a network request, and finally decrement the count. In JavaScript, async marks a function that can pause, and await delay(100) pauses execution for 100 milliseconds.

App.jsx
1async function handleReserve() {
2 setPending(pending + 1);
3 await delay(100);
Pauses execution
4 setPending(pending - 1);
Reads from old snapshot
5}

If multiple clicks happen quickly during that pause, why does the pending counter get corrupted and show the wrong number?

ANSWER

The code did not work as intended. This is a failure from reading a frozen snapshot across an asynchronous pause.

When the function resumes after await delay(100), it does not pull fresh values from React. It continues using the frozen snapshot from the exact moment the click happened:

  • The snapshot remains stale: If pending was 0 at the start, pending - 1 evaluates to -1. It ignores clicks that arrived during the wait.
  • The fix requires an updater function: An updater function always reads the live queued total instead of the snapshot. It never calculates using stale data.
PRINCIPLE 3

Use updater functions whenever state depends on previous queued calculations

Never read a frozen variable across an asynchronous pause. Pass an updater function when calculating a new state after an await.

We should do this:
async function handleReserve() {
setPending(p => p + 1);
queues pending increment
await delay(100);
setPending(p => p - 1);
decrements live queued total
}
We should not do this:
async function handleReserve() {
setPending(pending + 1);
reads frozen snapshot
await delay(100);
setPending(pending - 1);
reads stale snapshot again
}
QUESTION 4

Updater Purity & StrictMode

Starting with tickets = 0, you want to add a ticket and show a popup inside an updater. The browser function alert(t) shows a popup message and waits until the user clicks OK.

App.jsx
1setTickets(t => {
2 alert(t);
Popup shows 0
3 return t + 1;
Calculates 0 + 1
4});
  • Inside the updater function, you trigger a popup dialog: alert(t)
  • Right below the alert, you return the calculated number: return t + 1

Why does the alert window pop up two times in development mode before the screen updates to 1?

ANSWER

The code did not work as intended. This failure comes from placing a side effect inside a calculation function.

A side effect is anything a function does besides returning a value: a popup, a console log, a network request. StrictMode is a development check that wraps your app in main.jsx, and Vite adds it by default. Development mode means running the app on your own machine with npm run dev, not for real users.

React runs updater functions under StrictMode in development to verify that calculations are pure:

  • Updaters run during the render: React runs your updater while calculating the render, not inside the event handler.
  • StrictMode calls calculations twice: In development mode, React deliberately executes each updater function twice to check for side effects.
  • Side effects trigger twice on screen: Because an alert was inside the calculation, the popup appeared twice.

Lecture 46 explains why StrictMode runs these functions twice.

StrictMode Double Execution Check
PURE UPDATER (Calculation only):
  Run 1 (StrictMode check): (0) => 0 + 1 = 1  (Discarded)
  Run 2 (Commit pass):      (0) => 0 + 1 = 1  (Committed) ──► Screen shows 1

IMPURE UPDATER (Side effect inside calculation):
  Run 1 (StrictMode check): alert(0) ──► [Popup 1 appears on screen]
  Run 2 (Commit pass):      alert(0) ──► [Popup 2 appears on screen] (Bug!)
PRINCIPLE 4

Keep updater functions strictly pure and free of side effects

Only calculate and return the next value inside an updater function. Always place side effects like alerts, logs, and network requests inside the event handler.

We should do this:
function handleClick() {
setTickets(t => t + 1);
pure state calculation
alert('Ticket added');
side effect runs in handler
}
We should not do this:
setTickets(t => {
alert('Ticket added');
runs twice in StrictMode
return t + 1;
});

For the interview

The Interview Question: How does React queue multiple state updates, and when do you need an updater function?

1. The Hidden Signal

The interviewer is not testing whether you know arrow function syntax. They are probing whether you understand React's render loop and batching pipeline. A junior developer assumes each setter call causes an immediate render. A senior engineer steps to the whiteboard and draws the update queue. They explain that setters do not compute state inside the click handler. Instead, setters add instructions to a first-in, first-out (FIFO) queue. React waits until the handler finishes, starts the render, and works through that queue from first to last.

2. The Classic Trap

The classic trap appears when an interviewer writes three consecutive setter calls on the board. Candidates often guess the count increments by three. When told it only increments by one, they claim React debounced (merged) or ignored two calls. That explanation fails the interview. React never ignores a setter call. All three calls reach the queue, and all three carry the same instruction. A strong candidate says this out loud before the interviewer has to ask.

3. What is Actually Going On

React queues state updates during event execution. It does not update state variables immediately on each line of code.

Calling setCount(count + 1) three times queues three identical replacement instructions based on the frozen snapshot. React executes the queue sequentially, setting state to the same number repeatedly.

Passing an updater function c => c + 1 queues a calculation rule instead of a fixed value. React passes the result of each calculation directly into the next function in line.

4. Where It Gets Tricky

What does React render if you call setCount(count + 5), then setCount(c => c + 1), then setCount(42) from zero?

The final rendered count is 42. React evaluates the queue in strict sequential order during the next render pass. First, count + 5 queues a replacement with 5. Next, the updater receives 5 and returns 6. Finally, 42 replaces the running calculation completely, discarding earlier results.

What happens if you pass a function you want to store, such as setFormatter(formatPrice)?

React treats every function passed to a setter as an updater. It calls formatPrice with the current state and stores the result, not the function. To store the function itself, wrap it in another one: setFormatter(() => formatPrice) The outer arrow is the updater, and it returns formatPrice unchanged.

TicketOrder

This is the stateful boundary component. It owns the ticket count and pending reservations. Notice it uses updater functions for repeated increments and asynchronous reservation completion. Why? To ensure every queued update computes from the latest total without race conditions.

A beginner expects variables to update immediately after each setter call. React instead batches updates per handler and walks the update queue during render, providing consistent snapshots and high performance.

Glossary

  • Batching: The React mechanism that groups multiple state setter calls into a single render after an event handler completes.
  • Update Queue: The internal list of instructions that React processes in order during the next render to calculate state.
  • Updater Function: A function passed to a state setter that receives the pending state and returns the next value.
  • async and await: JavaScript keywords where async marks a pauseable function, and await pauses until a promise finishes.
  • Side Effect: Anything a function does besides returning a value, such as a popup or a network request.
  • StrictMode: A React development tool that runs updater functions twice to help developers catch impure side effects.
