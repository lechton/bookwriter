Lecture 12: Keeping Components Pure

Interview Question

CORE

What does it mean for a component to be pure, and what breaks when it is not?

Imagine this scenario:

  1. You build an article feed where cards display their position number and reading status.
  2. You increment a variable outside the component, but the numbers double on initial page load under StrictMode.
  3. What does it mean for a component to be pure, and what breaks when it is not?

Every web application calculates user interfaces from dynamic data

Every web application calculates user interfaces from underlying data. An online store calculates cart summaries, a dashboard computes live metrics, and a content feed transforms arrays of articles into visual cards. In standard JavaScript scripting, developers frequently declare outside variables and write step-by-step instructions that modify those variables or reach into the browser document. In React, a component is a function that calculates what the interface should look like: UI = f(props). To ensure that user interfaces render reliably without visual corruption or race conditions, React assumes that every component function you write is a pure function.

In traditional imperative programming, functions freely read and write global variables, mutate shared lists, or modify the document with document.getElementById(). If a developer numbers list items by incrementing an outside counter variable inside a component, the application quickly breaks. In development mode, the counter increments twice per render, jumping from #1 to #2 and #4. In React, a component treats rendering as a mathematical formula: given the same inputs, it must return the exact same JSX, and it must never change any variable or system that existed before the function ran.

This chapter answers four core questions. What does it mean for a React component to be a pure function? Why does modifying an outside variable double numbers under StrictMode in development? How does local mutation differ from external mutation? Where do side effects and DOM changes belong if they cannot run during render?

Later in this track, Lecture 13 introduces event handlers as the primary home for user-triggered side effects like network requests and notifications. Lecture 14 teaches how state hooks provide components with memory to update the screen over time without breaking render purity. Lecture 46 dives deep into <StrictMode>, exploring how double-invoking updaters and Effects protects applications against concurrency bugs.

What makes a function pure: identical inputs, identical output, and zero side effects

In Lecture 2 and Lecture 4, we saw that React components are JavaScript functions that accept props and return JSX element descriptions. In computer science and functional programming, a pure function is a function that satisfies two strict rules: first, it minds its own business, meaning it never modifies any variable, object, or system that existed before it was called; second, same inputs always produce the exact same output. A classic example is a math formula such as y = 2x. If x is 2, y is always 4. If x is 3, y is always 6. The answer never changes based on the time of day or what other formulas were calculated earlier.

Pure Calculation
1function PureDouble({ number }) {
Pure: returns exact same JSX for given prop
2 const result = number * 2;
3 return <p>Result: {result}</p>;
Deterministic
4}

React is built directly on this mathematical foundation. React assumes that every component function is a pure calculation. Given the same props, a component must always return the exact same JSX tree. When a component only calculates markup from its inputs without touching outside systems, React can run that component at any time, run sibling components in any order, or run the function multiple times without corrupting application data.

How React runs components during render and why StrictMode double-calls in development

In Lecture 4, we learned that development environments wrap the root application in <StrictMode>. To understand why StrictMode behaves the way it does, we must understand the render phase. Rendering refers to the process where React calls your component function to find out what the next screen description should look like. Code written at the top level of your component function body executes during this render phase. Because React may need to recalculate the interface when data changes, React does not promise to call your component exactly once per screen change.

A module-level variable is a variable declared at the top of a file, outside of any component function. While local variables declared inside a component are recreated fresh on every call, a module-level variable lives in module scope and survives for the entire lifetime of the browser tab. If a component modifies a module-level variable during render, that mutation persists across calls.

Module Variable Mutation

4 renderPass = renderPass + 1;
Mutates outside variable
5 return <div>Render pass #{renderPass}</div>;
6}

In development, <StrictMode> intentionally calls every component function twice during every render pass. If a component is pure, calling it twice produces identical JSX and causes zero harm. But if a component mutates an outside module variable, that mutation executes twice on page load, immediately exposing the bug.

The difference between local mutation and external mutation

In Lecture 6, we established that props are strictly read-only. In JavaScript, mutation means modifying the contents or properties of an existing object or array in place without creating a new reference. Developers often wonder whether React forbids all JavaScript mutation. The answer is no: React explicitly allows local mutation. Local mutation means changing variables, arrays, or objects that were created inside that exact same render call.

If you create a brand-new array inside a component function body using const items = []; and call items.push(...) inside a loop to assemble list items, that code is completely pure. Because the array was born inside that specific render call, no other component or function in the application can see it. When the component finishes executing, the local array is encapsulated in the returned JSX.

Local Array Mutation
1function ItemList({ count }) {
Safe local mutation: array created in this render
2 const items = [];
Fresh local array
3 for (let i = 0; i < count; i++) {
4 items.push(<li key={i}>Item {i + 1}</li>);
5 }
6 return <ul>{items}</ul>;
Pure return
7}

However, calling array.push() on an array received as a prop or declared at the module level modifies data that existed before the render. Under StrictMode, that push() runs twice, duplicating items in memory. Furthermore, mutating a local object after passing it into a JSX element modifies the element because both share the same reference.

What belongs in render versus what belongs in event handlers

In Lecture 1, we saw that scripts interact with the DOM using document.getElementById(). In Lecture 10, we saw that reading properties on null throws a TypeError. A side effect is any operation that modifies state outside the current function or interacts with outside systems during execution. Examples include writing to document.getElementById(), modifying document.title, starting a timer with setInterval, making a network request, or logging analytics. Top-level component execution must remain free of side effects because React calls components before their DOM elements exist.

When a component runs for the first time, its HTML tags have not yet been created or mounted in the browser document. Calling document.getElementById('badge').className = 'active' during render fails immediately: document.getElementById() returns null, and assigning a property on null throws an unhandled TypeError that crashes the page. Even on later renders, directly mutating DOM nodes bypasses React's reconciliation engine.

Declarative Ternary Expression
1function StatusIndicator({ isActive }) {
Declarative: evaluates ternary expression during render
2 const statusClass = isActive ? 'online' : 'offline';
3 return <span className={statusClass}>Status</span>;
4}

The pure React approach is declarative: calculate dynamic styles and text directly in the returned JSX using JavaScript expressions like ternary conditional operators (condition ? 'active' : 'inactive'). Changes caused by user actions (like button clicks) belong in event handlers, which run outside of render.

A function is idempotent if running it multiple times with the same inputs always produces the exact same result. Functions like Math.random() and new Date() are non-idempotent: every single invocation returns a different number or timestamp. When a component calls Math.random() in its body, StrictMode runs the function twice and produces two disagreeing numbers. The screen shows the second number, while earlier logs or child components hold the first. To keep components pure, dynamic values and timestamps should be passed downward as props from data that already holds them.

Principles of React: Keeping Components Pure

QUESTION 1

An outside counter variable doubles its numbers on page load

A developer wants three cards in an article list to display sequential numbers. They declare a counter variable at the top of the file outside the component. Inside the card component, they increment that outside variable during render:

Impure Counter Mutation
1let count = 0;
Module-level variable
2
3export default function ArticleCard({ title }) {
4 count = count + 1;
Mutates outside variable
5 return <li>#{count}: {title}</li>;
6}

When the page loads, the developer expects to see three cards numbered #1, #2, and #3. Instead, the screen displays #2, #4, and #6. When the root renders again, the numbers jump to #8, #10, and #12.

Why does the counter display doubled numbers on initial page load?

ANSWER

The code does not do what we wanted. The component mutates an external variable during development double-rendering.

In development mode, React wraps components in <StrictMode>. StrictMode deliberately runs every component function twice during each render pass to detect accidental side effects. Because count is a module-level variable that lives outside the function, the first card increments count to 1 on its first call and to 2 on its second call. The browser displays #2 for the first item on screen.

When the second card renders, it starts from 2. The first call increments count to 3, and the second call increments it to 4. The third card increments count to 5 and 6. If another component reads count, its output depends entirely on which component React decided to call first. On any later render, count never resets; it keeps climbing without bound.

To fix this defect, remove the outside variable completely and pass the item position downward as an explicit prop. Because the card calculates its markup strictly from its props, React can call it once, twice, or ten times, and the output is always #1, #2, and #3.

StrictMode double-invoking an impure counter versus pure props
Impure: let count = 0                Pure: position={index + 1}
Call 1: count = 0 + 1 -> 1           Call 1: reads prop position (1) -> #1
Call 2: count = 1 + 1 -> 2 (shows)   Call 2: position (1) -> #1 (shows)
Next render: count climbs to 8...    Next render: reads prop position (1) -> #1
PRINCIPLE 1

A component must return the same JSX for the same props

pure function a function that produces identical output for identical inputs and causes zero outside side effects
StrictMode double-rendering a development check where React calls component functions twice to catch side effects

React calls a component function to calculate what to show on screen. In development, StrictMode double-rendering calls every component twice to detect unexpected side effects. When a component reads or writes a variable outside itself, each run sees a different value and numbers drift. Treat every component as a pure function: compute output strictly from props and local variables so every run returns identical markup.

}

}

When the page loads under <StrictMode>, the list displays two identical copies of the bonus story on the very first render. The browser console prints a warning: Encountered two children with the same key

Can I push an item into an array, or change an object, during render?

ANSWER

The code does not do what we wanted. Calling push mutates data that existed before the render started.

Data that existed before the component was called (such as an array received as a prop or declared at module level) survives across render passes. Calling stories.push() mutates that preexisting array in place in the caller's memory. Because <StrictMode> calls the component twice during development, stories.push() runs twice on initial load, appending two duplicate items into the array.

Similarly, if you mutate a local object after passing it into a JSX element (such as writing styles.color = 'red' after <Header styles={styles} />), the element displays the modified color because both share the exact same object reference in memory. Once an object is handed to JSX, it must be treated as immutable.

To modify collections safely during render, use local mutation. Create a fresh array inside the component function using array spread syntax ([...stories, bonusStory]) or push into an array created inside that specific render call. Because the new array was born inside that function call, no outside component can see it, and each render pass starts with a clean copy.

external mutation changing a variable, array, or object that existed before the current render call

Never mutate variables, objects, or arrays that existed before the component was called. Calling push() or reassigning properties on shared data changes memory that other components and later renders rely on. To modify data during render, use local mutation: create a brand-new array or object inside the function body and fill it before passing it to JSX.

QUESTION 3

Modifying the document during render throws an error on initial load

A developer wants to set a dark mode class on a clock widget when it renders at night. Remembering traditional JavaScript DOM manipulation, they query the element directly inside the component body:

Imperative DOM Query
1export default function ClockWidget({ isNight }) {
2 if (isNight) {
3 document.getElementById('clock').className = 'night';
DOM write
4 }
5 return <div id="clock">Current Time</div>;
6}

When the page loads, the screen goes completely white. Opening the browser developer console reveals an unhandled runtime exception: TypeError: Cannot set properties of null (setting 'className')

Where do I set document properties, or add a CSS class to an element?

ANSWER

The code does not do what we wanted. The component queries the browser document before DOM nodes are mounted.

Component functions execute during the render phase, strictly to calculate what the next user interface should look like. During this calculation, React has not yet created or mounted the corresponding browser DOM nodes. When document.getElementById('clock') executes on the initial render, the DOM element does not exist in the document, returning null. Attempting to assign className on null throws an immediate TypeError that halts execution.

Even if the DOM node existed from an earlier render pass, directly modifying DOM nodes by hand bypasses React's declarative reconciliation engine and desynchronizes the user interface. Similarly, writing document.title = title inside the component body alters the browser tab during render, which is a side effect.

The solution is to express visual attributes declaratively directly in the returned JSX. Use a JavaScript ternary conditional operator to calculate the desired class name during render: <div id="clock" className={isNight ? 'night' : 'day'}> React evaluates this expression cleanly and updates the browser DOM node during the commit phase. Side effects that interact with outside systems belong in event handlers, which run in response to user actions outside the render path.

The render phase executes before browser DOM nodes exist
1. Render Phase (Component Body)    2. Commit Phase (DOM Update)
   React calls component function ->   React creates & updates DOM nodes
   document.getElementById returns null -> DOM nodes now exist in page
   TypeError: Cannot set className ->  Event handlers can safely run

Modifying the DOM during render throws errors because elements do not exist yet. Express visual changes declaratively in JSX, and place outside changes into event handlers.

QUESTION 4

Calling Math.random or new Date during render produces disagreeing values

A developer wants each article card in a news feed to pick a random visual badge or display the time it was viewed. They call Math.random() directly inside the component body:

Non-Idempotent Random Pick
1export default function ArticleCard({ title }) {
2 const pick = Math.random();
Non-idempotent calculation
3 console.log('Generated pick:', pick);
4 return <h3>Pick {pick}: {title}</h3>;
5}

When the page loads under <StrictMode>, the browser console displays two different numbers for the same card: Generated pick: 0.133 followed by Generated pick: 0.123. The screen displays Pick 0.123.

Can I pick a random highlight, or show the current time, by calling Math.random or new Date inside the component?

ANSWER

The code does not do what we wanted. Non-idempotent calls produce different results on every invocation.

A pure component must produce idempotent rendering: executing it multiple times with identical inputs must always return the exact same JSX output. Functions like Math.random() and new Date() are non-idempotent because each invocation produces a different number or timestamp. Under <StrictMode>, React deliberately renders the component twice during development. Because Math.random() runs on both passes, the two calls calculate disagreeing values. The browser console displays two different numbers, and the screen shows the result of the second call.

Similarly, calling new Date() in the render body freezes the timestamp at the exact millisecond the component happened to render. The displayed time remains frozen and never advances unless a re-render is triggered.

To preserve component purity, avoid calling non-idempotent functions in the component body. Pass random values or timestamps downward as explicit props from data that already holds them. If a new random value or timestamp must be generated when a user interacts with the page, perform that calculation inside an event handler before passing the result to state.

Non-idempotent call drift under development double-rendering
Call 1 (StrictMode): Math.random() produces 0.133
Call 2 (StrictMode): Math.random() produces 0.123
Screen displays: 0.123 (earlier logs or calculations disagree)
Pure alternative: <Card pick={pick} /> ensures identical values on every run

Where you will meet this

  1. Server-Side Rendering and Static Generation: Server frameworks render components on a web server to generate HTML for thousands of concurrent requests; because pure components never touch global variables or shared memory, concurrent visitor requests never contaminate each other's data.
  2. Performance Optimization with Memoization: When a component is pure, React can safely skip re-rendering it if its props have not changed, reusing the previous JSX calculation because a pure formula is guaranteed to return the exact same markup.
  3. Concurrent and Interrupted Rendering: When React prioritizes urgent user inputs over background updates, it can pause or discard a component render in memory and restart it later; pure components guarantee that discarded renders leave zero corrupted traces behind.
  4. Automated Unit Testing: Testing pure components is simple and reliable because you do not need to mock browser DOM globals, reset external counter variables, or clean up leaked side effects between test runs.

For the interview

The Interview Question: What does it mean for a component to be pure, and what breaks when it is not?

1. The Hidden Signal

The interviewer is probing whether you understand React's declarative execution loop and the contract of pure rendering, or whether you still write React like traditional imperative jQuery scripts. A junior developer mentions that functions should not change variables. A senior engineer explains that pure components act as mathematical formulas where UI = f(props). They explain that React reserves the right to call components multiple times, in any order, and twice in development under StrictMode. They explain how external mutation causes state drift across renders and how imperative DOM queries during render crash because nodes do not exist yet.

2. The Classic Trap

The classic trap appears when an interviewer asks why a console.log() inside a component prints twice on page load. Candidates often assume React has an infinite render bug or a double-mount defect, and some admit to deleting <StrictMode> from their root file to silence the logs. In reality, StrictMode deliberately double-invokes components in development as an intentional stress test to expose hidden mutations. Another trap is assuming purity means you cannot use JavaScript arrays or objects; local mutation on fresh data created inside the current render call is 100% pure.

3. What is Actually Going On

In React, component execution is an on-demand calculation. React takes your props and calls your component function to obtain a tree of element descriptors. If your component is pure, calling it once, twice, or ten times produces identical JSX. If your component modifies a module-level variable during render, StrictMode double-rendering executes that mutation twice on the initial page load, causing numbers to double immediately. If a component writes to the DOM during render, the operation fails with a TypeError because React has not created the DOM nodes yet.

4. Where It Gets Tricky

What happens if you mutate a local object after passing it into a JSX element, such as styles.color = 'red' after writing <Header styles={styles} />? The element receives the modified value because both share the same reference in memory; values must be treated as immutable once passed to JSX. Why are Math.random() and new Date() forbidden in render output? Both are non-idempotent: they return different values on every call, causing the two StrictMode calls to disagree and freezing timestamps at render time. How do you handle real side effects like network requests or timers? Place them inside event handlers, which execute in response to user actions outside the render path.

Glossary

  • Pure Function: A function that always returns the exact same result given the same inputs and produces zero side effects on outside systems.
  • Side Effect: Any operation that modifies state outside the current function or interacts with outside systems during execution.
  • StrictMode: A React development-only wrapper component that deliberately calls component functions twice to expose unintended side effects.
  • Local Mutation: Modifying variables, arrays, or objects created within the current render execution before they are passed into JSX.
  • Idempotence: The property of a function where running it multiple times with identical inputs produces the exact same outcome without state drift.
