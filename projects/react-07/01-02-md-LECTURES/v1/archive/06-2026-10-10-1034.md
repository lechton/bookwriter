### The Duplicate Card Dilemma and the Parameter Mutation Trap

In our previous lessons, we learned that a React component is a JavaScript function that returns markup describing a piece of the user interface. We also discovered in Lecture 5 how components fit together into a top-down render tree, where parent components render children and data flows strictly along parent-child branches. When first building feeds with multiple cards, it is possible that a student of React may fall into the hardcoded copy trap. A junior developer may naturally assume that because three story cards share the same visual structure, the quickest path is to duplicate the component function or copy-paste identical HTML markup three times.

Marcus sits at the newsroom desk to render three morning news stories: a transit agreement, a clean energy project, and a city park renovation. Because Marcus has not yet parameterized the card, Marcus copies the component function three times as `ArticleCardOne`, `ArticleCardTwo`, and `ArticleCardThree`. When the editor asks to change the card layout from rounded corners to square borders, Marcus must manually update all three files. Even worse, before copying the functions, rendering `<ArticleCard />` three times displayed the exact same headline on every single card.

To see this naive approach in runnable code, examine how Marcus initially duplicates identical markup inside three separate card declarations:

```jsx title="Naive Duplicate Cards"
function ArticleCardOne() {
  return (
    <article className="card">
      <h2 className="card-title">Transit Accord Reached</h2> // Hardcoded headline in first card
      <p>By Clara Foster</p>
    </article>
  );
}
```

When Marcus realizes that copying functions creates unmaintainable sprawl, Marcus tries to pass an input argument and reassign it inside the component. Marcus writes `function ArticleCard(props)` and adds `props.title = 'Breaking News'` at the top of the function body. The development server immediately halts execution with a fatal runtime error: `TypeError: Cannot assign to read only property 'title' of object '#<Object>'`. A developer may fall into this trap, expecting props to behave like regular mutable JavaScript function arguments. React explicitly freezes incoming props in development mode to enforce the read-only contract.

```jsx title="Naive Prop Mutation"
function ArticleCard(props) {
  props.title = 'Breaking News'; // **WRONG:** throws TypeError on frozen props
  return (
    <article className="card">
      <h2>{props.title}</h2>
    </article>
  );
}
```

> [!WILD]
> **Why does React freeze props in development?**
> React freezes props in development to enforce component purity and unidirectional data flow. When a newsroom engineer tries to reassign `props.title`, JavaScript throws a fatal **TypeError** because React runs `Object.freeze()` on the incoming object. In React, a component must be a **pure function** that never modifies its inputs. If components could mutate their own **props**, changes made by one child would silently corrupt data in the parent and cause **state drift** across sibling cards. To update what appears on screen, a parent must pass new props, or the component must hold local state.

### What Are Props and How Does React Pass Data Downward?

In standard JavaScript, functions accept arguments so that a single calculation can run on different inputs. For example, a function `double(x)` returns `x * 2` for any number you provide. React components are JavaScript functions that return user interface markup. If a component could only return hardcoded text, you would need a new component for every sentence on your website. React solves this through **props**, which is short for properties. Props allow a parent component to pass custom data down to child components, letting one single component layout render hundreds of different stories.

When you render a component tag in JSX, any attributes you write become properties on a single JavaScript object. For instance, writing `<ArticleCard title="Clean Energy Accord" readTime={5} />` tells React to create an object: `{ title: "Clean Energy Accord", readTime: 5 }`. React passes this object as the first and only argument to your `ArticleCard` component function. In React terminology, the location where you render the tag is called the **call site**, the attributes are called **props**, and the component receiving the data is the **child component**.

When working with props, modern JavaScript provides a concise syntax called **destructuring**. Instead of writing `function ArticleCard(props)` and repeating `props.title` and `props.readTime` throughout your markup, you can write `function ArticleCard({ title, readTime })`. In JavaScript, placing curly braces `{ }` inside the parameter list tells the runtime to automatically unpack specific keys from the incoming object into local variables. This syntax is standard ECMAScript, but it is the universal convention in React because it makes a component's required inputs immediately visible at the top of the function.

Under the hood, the JSX compiler converts every component tag into a function call. As we learned in Lecture 4, writing `<ArticleCard title="Transit Accord" readTime={5} />` transforms into `_jsx(ArticleCard, { title: "Transit Accord", readTime: 5 })`. Notice that the second argument to `_jsx` is a standard JavaScript object literal. React instantiates this object, freezes it shallowly in development mode using `Object.freeze()`, and provides it to your component when invoking the function. This mechanical reality proves why components receive exactly one object argument.

Recall from Lecture 2 that components must always be pure functions that return UI descriptors. Recall also from Lecture 4 that quoted attributes pass string literals while curly braces evaluate live JavaScript expressions. In future lessons, we will explore passing components as the `children` prop (see Lecture 7), passing interactive callback functions (see Lecture 13 and Lecture 15), managing dynamic state that changes over time (see Lecture 16), protecting required props with TypeScript interfaces (see Lecture 89), and understanding why React 19 dropped legacy `defaultProps` (see Lecture 100).

### Principles of React: Passing Data with Props

In technical interviews, engineering candidates are closely evaluated on their understanding of data flow, component parameterization, fallback defaults, and the immutability guarantees of React. To master these concepts, we formalize the six governing principles of props:

> [!PRINCIPLE]
> **Principle 1: Read Props as One Object Created by the Parent**
> Every attribute you write on a JSX tag becomes a property in a single **props** object created by the parent. React passes this object to your component function as its only argument, giving the child access to incoming data. Because the parent creates the object, the parent chooses the values and the child only reads them.
> 
> >> props : a single JavaScript object containing all attributes passed from parent to child
> >> call site : the place in JSX markup where a component tag is rendered with attributes

An interviewer expects the candidate to state clearly that props are the single input argument of a component function. A parent component builds this object at the JSX call site by specifying attributes. When a parent renders `<ArticleCard title="City Transit Expands" readTime={5} />`, React collects those attributes into one object and passes it to `ArticleCard`. If you render `ArticleCard` three times with different attributes, React invokes the function three times, passing a distinct object on each call. The child never decides its own prop values; it receives what the parent provides.

```jsx title="Logging Received Props Object"
function ArticleCard(props) {
  console.log('Received props:', props); // Logs parent attributes as single object
  return (
    <article className="card">
      <h2>{props.title}</h2>
    </article>
  );
}
```

When this component renders from three call sites, the browser console prints three distinct objects: `{ title: 'City Transit Expands', readTime: 5 }`, `{ title: 'Clean Energy Accord', readTime: 3 }`, and `{ title: 'Public Park Renovations', readTime: 4 }`. This proves that props are simply JavaScript objects passed from parent to child.

> [!PRINCIPLE]
> **Principle 2: Turn Differing Values into Props and Derive Redundant Data**
> When several parts of your interface share the same layout but display different text, keep one component and pass the changing values as **props**. Never pass extra props for numbers or labels that the child can calculate on its own, such as passing a topic count alongside a topics array. Calculating values inside the child keeps your code clean and prevents conflicting data on screen.
> 
> >> derived value : data calculated directly from existing props during render without adding extra props
> >> redundant props : passing separate values that can already be computed from other incoming data
> 
> *It is best practice to do this:*
> `function Feed() {`
> `  return (`
> `    <ArticleCard`
> `      title="Transit Accord"`
> `      topics={['Bus', 'Train']} // Child computes length from array`
> `    />`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function Feed() {`
> `  return (`
> `    <ArticleCard`
> `      title="Transit Accord"`
> `      topics={['Bus', 'Train']}`
> `      topicCount={5} // Redundant count can disagree with array`
> `    />`
> `  );`
> `}`

When reviewing pull requests, senior engineers check whether new props carry genuinely independent information. It is possible that a developer may pass both a list of items and a separate counter, such as `topics={['Bus', 'Train']}` alongside `topicCount={2}`. This creates a severe risk of data desynchronization: if the parent updates the array to three items but forgets to update the counter, the child displays conflicting information. Instead, pass only the array and calculate `const count = topics.length` directly inside the child during render. Derive everything you can from existing props.

```jsx title="Deriving Values During Render"
function ArticleCard({ title, topics }) {
  const topicCount = topics.length; // Calculates count directly from array prop
  return (
    <article className="card">
      <h2>{title}</h2>
      <p>Covering {topicCount} related topics</p>
    </article>
  );
}
```

By computing `topics.length` inside `ArticleCard`, the count and the list can never disagree. If the parent adds a third topic to the array, the rendered count updates automatically on the next render pass without any extra props.

> [!PRINCIPLE]
> **Principle 3: Destructure Props Inside Braces in the Parameter List**
> Always unpack incoming properties by wrapping parameter names in curly braces: `function ArticleCard({ title, readTime })`. This syntax is called **destructuring**, and it extracts properties directly into local variables. If you omit the curly braces, React binds the entire props object to your first parameter name, crashing the application when you try to render the object in JSX.
> 
> >> destructuring : extracting specific properties from an object into local variables using curly braces
> >> object child crash : a runtime error thrown when trying to render a raw JavaScript object directly inside JSX
> 
> *We should do this:*
> `function ArticleCard({ title }) { // Destructuring extracts title property`
> `  return <h2>{title}</h2>;`
> `}`
> 
> *We should not do this:*
> `function ArticleCard(title) { // Binds entire props object to title variable`
> `  return <h2>{title}</h2>; // Crash: Objects are not valid as a React child`
> `}`

The official React documentation highlights forgetting destructuring curly braces as a major pitfall. If you declare `function ArticleCard(title)` without braces, the variable `title` does not hold a headline string. It holds the entire props object: `{ title: "Transit Accord", readTime: 5 }`. When you write `<h2>{title}</h2>`, React tries to render a raw JavaScript object into the DOM and throws an immediate exception: `Error: Objects are not valid as a React child (found: object with keys {title, readTime})`. Wrapping the parameters in braces `({ title })` tells JavaScript to extract the `title` property, ensuring `title` holds the actual string value.

```jsx title="Destructuring vs Props Object"
function ArticleCard({ title, readTime }) { // Unpacks properties into named variables
  return <h2>{title} ({readTime} min)</h2>;
}
function ArticleCardAlternate(props) {
  return <h2>{props.title} ({props.readTime} min)</h2>; // Reads directly from props object
}
```

Notice that writing `function ArticleCard({ title, readTime })` produces the exact same result as accepting `props` and writing `props.title` and `props.readTime`. Destructuring is preferred across the community because it avoids repetitive typing and serves as self-documenting code.

> [!PRINCIPLE]
> **Principle 4: Provide Parameter Defaults for Optional Props in Destructuring**
> Assign fallback values to optional props directly in your function signature using an equals sign, like `{ readTime = 3 }`. If a parent omits an optional prop or passes `undefined`, React uses your fallback so the screen never displays an empty gap. Never rely on legacy `defaultProps` or `propTypes`, because modern React 19 silently ignores both on function components.
> 
> >> parameter default : a fallback value assigned with = that applies when a prop is missing or undefined
> >> silent omission : React rendering an empty blank space without warning when an optional prop is missing
> 
> *It is best practice to do this:*
> `function ArticleCard({`
> `  title,`
> `  readTime = 3 // Default provides fallback when prop is omitted`
> `}) {`
> `  return <span>{readTime} min read</span>;`
> `}`
> 
> *Instead of doing this:*
> `function ArticleCard({ title, readTime }) { // Missing prop leaves empty space`
> `  return <span>{readTime} min read</span>; // Renders blank space before min read`
> `}`

In real-world applications, some props are mandatory (like a story headline) while others are optional (like reading time or an author tag). If a parent renders `<ArticleCard title="Transit Accord" />` without `readTime`, `readTime` evaluates to `undefined`. Because React renders nothing for `undefined`, writing `<span>{readTime} min read</span>` renders `" min read"` on screen with an awkward blank space. Adding `readTime = 3` in the destructuring provides a reliable fallback. In React 19, legacy `ArticleCard.defaultProps` and `ArticleCard.propTypes` are completely ignored on function components, so parameter defaults are the sole native mechanism for default values.

```jsx title="Parameter Defaults in Action"
function ArticleCard({ title, readTime = 3 }) { // Fallback default applied if undefined
  return (
    <article className="card">
      <h3>{title}</h3>
      <p>{readTime} min read</p>
    </article>
  );
}
```

If a parent provides `<ArticleCard title="Transit Accord" readTime={7} />`, the component displays `7 min read`. But if the parent omits `readTime`, the parameter default cleanly substitutes `3`, ensuring the UI always renders complete, professional copy.

> [!PRINCIPLE]
> **Principle 5: Handle Null and Zero Explicitly Because Defaults Only Catch Undefined**
> Parameter defaults trigger only when a prop is missing or explicitly passed as `undefined`. If a parent passes `null` or `0`, JavaScript treats those as deliberate values, so the fallback default never runs. When dealing with database records where missing authors arrive as `null`, use the nullish coalescing operator `author ?? 'Staff Reporter'` to display a safe fallback.
> 
> >> nullish coalescing : the ?? operator that returns the right-hand value only if the left is null or undefined
> >> deliberate value : a value like 0 or null that JavaScript treats as real data, bypassing parameter defaults
> 
> *It is best practice to do this:*
> `function ArticleCard({ author = 'Staff Reporter' }) {`
> `  const reporter = author ?? 'Staff Reporter'; // Catches both null and undefined`
> `  return <span>By {reporter}</span>;`
> `}`
> 
> *Instead of doing this:*
> `function ArticleCard({ author = 'Staff Reporter' }) { // Default triggers only for undefined`
> `  return <span>By {author}</span>; // Renders empty name when parent passes null`
> `}`

A frequent source of bugs in production applications is assuming that parameter defaults catch `null`. When an API backend returns article records from a database, an article without an author often arrives as `{ title: "Stock Market Rally", author: null }`. If a parent writes `<ArticleCard author={data.author} />`, JavaScript sees that `author` is present and holds the value `null`. Because `null` is not `undefined`, the parameter default `author = 'Staff Reporter'` does not fire. React renders nothing for `null`, leaving the screen showing `"By "`.

To catch `null`, use the JavaScript **nullish coalescing operator** (`??`). In JavaScript, `a ?? b` evaluates to `b` only if `a` is strictly `null` or `undefined`. Writing `const reporter = author ?? 'Staff Reporter'` safely catches both cases. Notice also how JavaScript handles `0`: if a parent passes `readTime={0}`, `0` is a deliberate number. The default does not override `0`, which is crucial when displaying numeric statistics like zero comments or zero likes.

```jsx title="Null and Zero Default Bypass"
function ValueDisplay({ value = 100 }) { // Default triggers only for undefined
  return <span>{value === null ? 'null' : value}</span>;
}
export default function Preview() {
  return <ValueDisplay value={null} />; // Passes null directly bypassing default 100
}
```

This mechanical behavior demonstrates why parameter defaults alone are not enough when consuming raw JSON data from backends where missing values arrive as `null`.

> [!PRINCIPLE]
> **Principle 6: Treat Props as Read-Only and Derive Display Values During Render**
> Components must never reassign props or modify objects passed into them, because props are strictly **read-only**. React freezes the props object in development, causing direct assignments like `props.title = 'Breaking News'` to throw a TypeError. Calculate formatted values as fresh local constants during render, and if a value must change over time in response to user actions, ask the parent or use component state.
> 
> >> read-only contract : the platform rule stating components cannot alter incoming props
> >> shallow freeze : React freezing top-level props in development while nested objects remain mutable in memory
> 
> *We should do this:*
> `function ArticleCard({ title }) {`
> `  const headline = title.toUpperCase(); // Pure derived calculation preserves props`
> `  return <h2>{headline}</h2>;`
> `}`
> 
> *We should not do this:*
> `function ArticleCard(props) {`
> `  props.title = props.title.toUpperCase(); // Crash: Cannot assign to read only property`
> `  return <h2>{props.title}</h2>;`
> `}`

Why can a component never change its own props? In React, data flows in one direction from parent to child. The props object belongs to the parent that created it. If a child component could mutate its props, it would destroy the pure function contract where the same inputs always produce the same UI output. Even worse, React's development freeze is shallow: if a parent passes a nested object (like `story={{ title: 'Transit Accord' }}`), mutating `story.title` directly will silently modify the parent's object in memory! If another sibling component also receives that `story` object, the mutation unexpectedly corrupts the sibling's display.

```jsx title="Safe Derivation vs Object Mutation"
function ArticleCard({ title, story }) {
  const headline = title.toUpperCase(); // Pure local derivation preserves input props
  return (
    <article className="card">
      <h2>{headline}</h2>
      <p>{story.summary}</p>
    </article>
  );
}
```

Never mutate props. Instead, derive whatever formatted text you need by creating a new constant during render (`const headline = title.toUpperCase()`). If data must change in response to a user clicking a button or typing in an input, the component must ask the parent to pass new props or store the changing data in component state.

### Glossary

- **Props**: The single, read-only JavaScript object passed into a component function containing all attributes specified at its JSX call site.
- **Destructuring**: A JavaScript syntax that extracts individual properties from an object directly into named local variables inside parameter parentheses.
- **Parameter Default**: A fallback value assigned with an equals sign in destructuring that takes effect only when a prop is omitted or passed as undefined.
- **Nullish Coalescing Operator**: The JavaScript ?? operator that returns its right-hand operand when the left-hand operand is strictly null or undefined.
- **Read-Only Contract**: The fundamental architectural rule requiring React components to treat incoming props as immutable and never modify them.
- **Derived Value**: A new constant or formatted string calculated locally during render from existing props without mutating the original input data.

### Summary

**Passing Props and Read-Only Contract Decision Matrix**

❒ Call Sites and Parameterization

➔ ALWAYS pass data downward by declaring attributes at the JSX call site, allowing React to bundle them into one props object.

➔ ALWAYS turn values that differ between component instances into props rather than duplicating component functions.

➔ NEVER pass redundant props for values that the child can calculate on its own, such as passing an item count next to an array.

❒ Destructuring and Default Values

➔ ALWAYS destructure props using curly braces in the parameter list to unpack properties directly into named local variables.

➔ ALWAYS provide parameter defaults for optional props using an equals sign inside destructuring to prevent empty holes on screen.

➔ ALWAYS use the nullish coalescing operator ?? when data from an API may arrive as null, because parameter defaults catch only undefined.

❒ Component Purity and Immutability

➔ ALWAYS treat incoming props as strictly read-only and calculate formatted text as fresh local constants during render.

➔ NEVER assign new values to props or mutate objects received as props, which causes fatal errors in development and state drift in production.

**DO THIS:** Destructure props with fallback defaults and derive values pure in render

```jsx right
function ArticleCard({ title, readTime = 3 }) {
  const headline = title.toUpperCase();
  return (
    <article className="card">
      <h2>{headline}</h2>
      <p>{readTime} min read</p>
    </article>
  );
}
```

**DO NOT DO THIS:** Reassign incoming props directly or mutate input objects during render

```jsx wrong
function ArticleCard(props) {
  props.title = props.title.toUpperCase();
  return (
    <article className="card">
      <h2>{props.title}</h2>
      <p>{props.readTime} min read</p>
    </article>
  );
}
```

| | **HARDCODED REPETITION & MUTATION**<br>(Fragile Anti-Pattern) | **PARAMETERIZED READ-ONLY PROPS**<br>(Pure React 19 Architecture) |
| ---: | :--- | :--- |
| **Data Mechanism** | Duplicated component functions or hardcoded text in JSX | Attributes declared at call site bundled into single object |
| **Component Inputs** | None; functions hardcode copy or read external scope | Parameter list receives single props object from parent |
| **Unpacking Syntax** | Bare parameter binds whole object; crashes on render | Parameter destructuring unpacks properties into variables |
| **Optional Fallbacks** | Missing props leave blank holes or throw null errors | Parameter defaults provide fallbacks for missing values |
| **Null API Handling** | Unhandled null values pass through and render blank | Nullish coalescing (`??`) provides explicit safe fallback |
| **Immutability Contract** | Mutating props throws TypeError or corrupts siblings | Props are strictly read-only; child derives new values |
| **State Drift Risk** | High; duplicated cards or mutated objects drift out of sync | Zero; parent acts as single source of truth for instances |
