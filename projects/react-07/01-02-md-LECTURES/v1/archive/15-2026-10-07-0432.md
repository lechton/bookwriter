# Lecture 15: Trigger, Render, and Commit
> INTERVIEW QUESTION | ❱ CORE | What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?

1. Leo builds the reader statistics for The National Times.
2. He adds one line to the Like button: read the number on the page and send it.
3. A reader clicks Like once, and the page shows 1.
4. Why does the statistics server receive 0?
5. Every report is one like behind, and the editors plan the front page on wrong numbers.
6. The page had not changed yet when Leo's line read it.
7. Today we follow one click from the button to the screen, step by step.

### A Like Report That Is Always One Behind

Leo's `LikeCounter` keeps `likes` in state, as Lecture 14 taught. A click calls the setter, which stores the next value and asks React to run the component again. Leo wants every like reported to the newsroom's statistics server. So right after the setter, his handler reads the number from the page and sends it.

```jsx title="LikeCounter.jsx, first attempt" startLine="1" continues="bottom"
import { useState } from 'react';
function sendLikeEvent(count) {
  console.log('sent to statistics:', count); // stands in for a network request
}
export default function LikeCounter() {
  const [likes, setLikes] = useState(0);
  console.log('LikeCounter runs, likes =', likes); // each time React calls it
  function handleLike() {
    setLikes(likes + 1); // stores the next value
    const shown = document.querySelector('.like-count').textContent;
```

The function `document.querySelector` is the browser's way to find the first element that matches a CSS selector, here the class `like-count`. Its property `textContent` is the text inside that element.

```jsx title="LikeCounter.jsx, first attempt" startLine="11" continues="top"
    sendLikeEvent(shown); // reports what the page shows
  }
  return (
    <section>
      <p className="like-count">{likes}</p>
      <button type="button" onClick={handleLike}>Like</button>
    </section>
  );
}
```

When the counter first appears, the console prints `LikeCounter runs, likes = 0`. Leo clicks Like. The console prints `sent to statistics: 0`, and only then `LikeCounter runs, likes = 1`. The page shows `1`. He clicks again: the server receives `1`, and the page shows `2`. Every report is one behind, and the report line always prints before the line from the new run.

A colleague, Mia, has a second question. She wants a comment field beside the Like button. If React runs the counter again on every like, will it wipe what the reader is typing? Both questions have the same answer: React updates the screen in separate steps, and each step runs different code.

### Three Steps Behind Every Screen Update

In plain JavaScript, `element.textContent = 1` changes the page on that line. The next line already reads `1`. React does not work like that. It splits every screen update into three steps, which the React docs call **trigger**, **render**, and **commit**.

The first step is the **trigger**: something asks React for a render. There are only two triggers. The first one is the call to `root.render(<App />)` in `main.jsx`, which Lecture 9 showed. The second one is a setter call, as Lecture 14 showed.

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import App from './App.jsx';
const root = createRoot(document.getElementById('root'));
root.render(<App />); // the first trigger
```

The second step is the **render**. Lecture 14 used this word for one run of a component. Rendering means React calls our component functions to get their JSX. On the first render, React calls the root component, `App`, and then each component it returns. Our code never calls them itself, as Lecture 2 showed. Nothing on the page changes during a render. The functions only calculate, which is why they must be pure, as Lecture 12 taught.

The console lines in this lesson come from a project without `StrictMode`. A new Vite project turns it on, and then each `runs` line prints twice in development. Lecture 46 explains why.

The third step is the **commit**, where React changes the page. The page is made of **DOM nodes**. Every element and every piece of text on the page is a DOM node, an object the browser keeps for it. On the first render, React creates all the nodes and adds them to the root element with the browser function `appendChild()`. This replaces whatever the root element held before, such as a `Loading...` text. On later renders, React changes only the nodes that differ, the smallest change Lecture 1 promised.

After the commit, the browser draws the new page on the screen. The browser calls this drawing "rendering" too. The React docs call it **painting**, to keep the two words apart: React renders, then commits, and the browser paints.

So where does Leo's handler fit? When does the commit happen, compared with the next line of his handler? Which components does a click make React call? And what happens to text a reader is typing when the commit changes the page? The four principles answer these questions in order.

### Principles of React: Trigger, Render, and Commit

An interviewer who asks this question wants each step and what runs in it. The first principle covers the render. The second covers which components a render calls. The third covers the commit. The last one is the decision Leo needs in his handler.

> [!PRINCIPLE]
> **Principle 1: A Render Is React Calling the Component, and the Page Stays as It Was**
> A component is a function that returns JSX. To render a component, React calls that function and takes the JSX it returns. That is the whole render. The page on the screen does not change during it. React changes the page in the next step, the commit, after the function has returned. So code inside the component that reads the page finds the old page. On the first render there is no `<p>` yet. In the render where `count` is 1, the page still shows 0.
>
> *We should do this:*
> `function Counter() {`
> `  const [count, setCount] = useState(0);`
> `  return <p>{count}</p>; // the value of this render`
> `}`
>
> *We should not do this:*
> `function Counter() {`
> `  const [count, setCount] = useState(0);`
> `  const p = document.querySelector('p'); // null on the first render`
> `  return <p>{p.textContent}</p>; // TypeError, nothing appears`
> `}`

To watch this on Leo's counter, we let the component look at the page while it runs. The ternary from Lecture 4 covers the first render, when there is no `<p>` yet.

```jsx title="LikeCounter.jsx, looking at the page during a render" startLine="5"
export default function LikeCounter() {
  const [likes, setLikes] = useState(0);
  const shown = document.querySelector('.like-count'); // the page right now
  const pageText = shown ? shown.textContent : 'nothing yet';
  console.log('likes =', likes, '| page shows', pageText);
```

The first render prints `likes = 0 | page shows nothing yet`. A click prints `likes = 1 | page shows 0`, and a moment later the page shows `1`. The whole run of `LikeCounter` happened while the page still showed the old number. The new text arrived in the commit, after the function had returned. This is also why the wrong card in the box fails: on the first render, `document.querySelector('p')` returns `null`, and reading `textContent` from `null` throws a `TypeError`.

> [!PRINCIPLE]
> **Principle 2: A State Change Renders Its Own Component and Everything Inside It**
> Components return other components, so together they form a tree, with `App` at the top. On the first render, React calls `App` and then every component below it. After that, a setter asks for a render of its own component. React calls that component again, then each component it returns, and so on to the bottom of the tree. We might expect a change to run the whole app again, as a page reload does. It does not. The parent and the components beside it do not run again.
>
> *It is best practice to do this:*
> `function Counter() {`
> `  const [count, setCount] = useState(0); // setCount runs Counter`
> `  return <p>{count}</p>;`
> `}`
>
> *Instead of doing this:*
> `function Page() {`
> `  const [count, setCount] = useState(0); // setCount runs Page`
> `  return <main><Title /><p>{count}</p></main>; // and Title`
> `}`

Leo's page has a headline above the counter, and the counter shows its number through a small child component. We put a log in every component of the tree from Lecture 5.

```jsx title="The page, with a log in every component"
function StoryTitle() {
  console.log('StoryTitle runs'); // the sibling of LikeCounter
  return <h1>City Library Opens Late on Fridays</h1>;
}
export default function App() {
  console.log('App runs');
  return <main><StoryTitle /><LikeCounter /></main>; // the parent
}
```

Inside `LikeCounter`, the JSX now returns `<LikeLabel count={likes} />`, a child that logs `LikeLabel runs` and shows the number. The first render prints four lines: `App runs`, `StoryTitle runs`, `LikeCounter runs, likes = 0`, and `LikeLabel runs`. A click on Like prints two: `LikeCounter runs, likes = 1` and `LikeLabel runs`. `App` and `StoryTitle` stay silent, and React never touches the headline. React also does not check first whether a child's output will change. A child that always shows the same text runs on every click too, and the commit then finds nothing to change in it. Lecture 54 adds the other reasons a component renders.

> [!PRINCIPLE]
> **Principle 3: The Commit Changes Only What Is Different**
> After a render, React has two sets of JSX: the new one and the one from the last render. In the commit, React changes the page only where they differ. An element that stays in the same place in the JSX keeps the same DOM node on the page. If only `{count}` changed, only that number changes. So an `<input>` beside it keeps the text the user typed. We might expect a render to rebuild the page, as setting `innerHTML` does. It does not. When the commit is done, the browser paints the screen.
>
> *It is best practice to do this:*
> `return (`
> `  <div>`
> `    <p>{count}</p> // only this number changes`
> `    <input />`
> `  </div>`
> `);`
>
> *Instead of doing this:*
> `box.innerHTML = '<p>' + count + '</p><input>'; // the input is new`

This answers Mia. The finished counter has a comment field, an `<input>` beside the number, and `LikeLabel` shows the text `Likes: 0`. A reader types `great post` and clicks Like. React renders `LikeCounter` and `LikeLabel` again, and the page shows `Likes: 1`. The input still holds `great post`. It is the same DOM node as before the click, and so is the `<p>`. Inside the `<p>`, the words `Likes: ` and the number are two separate text nodes, and the commit changed only the number. With `innerHTML`, as in the second card, the same update builds a new, empty input, and the typed text is gone. Lecture 24 explains how React decides that an element is still in the same place.

> [!PRINCIPLE]
> **Principle 4: The Page Changes Only After the Event Handler Finishes**
> In plain JavaScript, `p.textContent = 1` changes the page on that line. We might expect `setCount(1)` to do the same. It does not. A setter only asks React for a render. React renders and commits after the event handler has finished. So on the line after `setCount(count + 1)`, the page still shows the old number. When the handler needs the new number, compute it once, as `const next = count + 1`, and pass `next` to the setter and to any other code.
>
> *We should do this:*
> `const [count, setCount] = useState(0);`
> `const next = count + 1;`
> `setCount(next);`
> `report(next); // reports the new number`
>
> *We should not do this:*
> `const [count, setCount] = useState(0);`
> `setCount(count + 1);`
> `const shown = document.querySelector('p').textContent;`
> `report(shown); // reports the old number`

Now Leo's console makes sense. His report line printed `sent to statistics: 0` before `LikeCounter runs, likes = 1`. The handler ran to its end first, while the page still showed `0`. Only then did React render the counter and commit the new number. The fix computes the next number once and gives it to both the setter and the report.

```jsx title="LikeCounter.jsx, the fixed handler" startLine="8"
  function handleLike() {
    const next = likes + 1; // the new number, computed once
    setLikes(next);
    sendLikeEvent(next); // reports 1 after the first click
  }
```

The first click now prints `sent to statistics: 1`, and the page shows `1`. One more surprise waits here. The variable `likes` itself also still holds the old value on the line after the setter. Lecture 16 explains why.

> [!WILD]
> **Why does code after root.render find an empty page?**
>
> Mia adds a line to `main.jsx`, right after `root.render(<App />)`, to count the stories on the page. It finds none, and the root element still holds `Loading...`. The call to `root.render` is a **trigger**: it asks for the first render and returns at once. React calls the components and makes the **commit** a moment later, after the code in `main.jsx` has finished. That first commit is also what replaces `Loading...` with the app.

Now we assemble the finished story page. It shows a headline, a like count, a comment field, and a Like button that reports the right number.

### Step 1: First, we show the story and its like counter <src/App.jsx>

`App` returns the headline and the counter. It declares no state, because nothing on the page belongs to the page as a whole.

```jsx title="App.jsx"
import LikeCounter from './components/LikeCounter.jsx';
export default function App() {
  console.log('App runs'); // prints on the first render only
  return (
    <main>
      <h1>City Library Opens Late on Fridays</h1>
      <LikeCounter />
    </main>
  );
}
```

Because the like count lives in `LikeCounter`, a click never makes React call `App` again. Its log prints once, and the commit never touches the `<h1>`. Where the state lives decides how much of the tree a click renders, as Principle 2 showed.

### Step 2: Next, we give the counter its state and its report <src/components/LikeCounter.jsx>

`LikeCounter` owns the like count. Its handler computes the next number once, before anything else.

```jsx title="LikeCounter.jsx" startLine="1" continues="bottom"
import { useState } from 'react';
import LikeLabel from './LikeLabel.jsx';
function sendLikeEvent(count) {
  console.log('sent to statistics:', count); // stands in for a network request
}
export default function LikeCounter() {
  const [likes, setLikes] = useState(0);
  function handleLike() {
    const next = likes + 1; // the new number, computed once
    setLikes(next); // asks React for a render after this handler
```

The report gets the same `next` as the setter, so it never depends on when the page changes. The JSX returns the label, the comment field, and the button. The attribute `placeholder` sets the grey hint text that an empty input shows.

```jsx title="LikeCounter.jsx" startLine="11" continues="top"
    sendLikeEvent(next); // reports 1 after the first click
  }
  return (
    <section>
      <LikeLabel count={likes} /> // runs again on every like
      <input placeholder="Say why you like it" /> // keeps typed text
      <button type="button" onClick={handleLike}>Like</button>
    </section>
  );
}
```

The input has no state and no props. The browser keeps the text the reader types, and the commit leaves the input alone, because it stays in the same place in the JSX. Mia's comment field needs no protection from renders.

### Step 3: Finally, we show the count <src/components/LikeLabel.jsx>

`LikeLabel` receives the count as a prop and shows it. It keeps no state.

```jsx title="LikeLabel.jsx"
export default function LikeLabel({ count }) {
  console.log('LikeLabel runs'); // runs whenever LikeCounter runs
  return <p className="like-count">Likes: {count}</p>; // one text node changes
}
```

Now we can follow one click through all three steps. The click calls `handleLike`, and the setter is the trigger. The console prints `sent to statistics: 1`, because the handler runs to its end first. Then React renders `LikeCounter` and `LikeLabel`, and the console prints `LikeLabel runs`. In the commit, React changes only the number inside `Likes: 1`. Last, the browser paints the screen, and the reader sees the new count with their comment still in the field.

### Component Summary

```component-code title="Summary: The Logic of Nested Components"
App.jsx | none | parent | [role: The **parent component** shows the headline and the counter. It keeps **no state**, so a like never makes React call it again. Its log prints once, on the **first render**, and the commit never touches its `<h1>`.]
  LikeCounter.jsx | none | counter | [role: The **state owner** keeps **`likes`** and handles the click. Its handler computes **`next`** once and gives it to both the setter and the report. Why? The page changes only after the handler finishes, so reading the page would report the old number.]
    LikeLabel.jsx | count={likes} | generic | [role: The **child component** shows the count it receives. React calls it on every like, because it sits inside `LikeCounter`. Its **number text node** is the only part of the page the commit changes.]
```

A newcomer expects React to work like plain DOM code: the page changes on the line that asks for it, and a change rebuilds everything. The finished page shows the three steps instead. The setter triggers, React renders the counter and its child, and the commit changes one number while the comment field keeps its text.

### Where you will meet this

1. **Click statistics**: a report sent from a handler must use the value the code computed, not the page.
2. **Forms on busy pages**: an input keeps the user's text while the components around it render again.
3. **Scrolling to a new item**: a new message or comment exists on the page only after the commit.
4. **Debugging with the console**: the order of the log lines shows which code ran in which step.

### Glossary

- **Trigger**: The request that starts a render, either the first `root.render` call or a setter call.
- **Render**: React calling component functions to get their JSX; the page does not change during it.
- **Commit**: The step where React changes the DOM nodes that differ from the last render.
- **DOM Node**: The browser's object for one element or one piece of text on the page.
- **Paint**: The browser drawing the page on the screen after the commit.

## Beyond the basics

- The React docs walk through the three steps with their own examples (see [react.dev/learn/render-and-commit](https://react.dev/learn/render-and-commit)).
- Several setter calls in one handler lead to a single render (see [react.dev/learn/queueing-a-series-of-state-updates](https://react.dev/learn/queueing-a-series-of-state-updates)).
- `flushSync` makes React render and commit before the next line runs, for rare cases such as scrolling (see [react.dev/reference/react-dom/flushSync](https://react.dev/reference/react-dom/flushSync)).
- `StrictMode` calls components twice in development to find code that is not pure (see [react.dev/reference/react/StrictMode](https://react.dev/reference/react/StrictMode)).
- `memo` lets React skip a child's render when its props did not change (see [react.dev/reference/react/memo](https://react.dev/reference/react/memo)).

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Reading Values After a Change

➔ ALWAYS compute the new value once and pass it to the setter and to any other code.

➔ NEVER read the page right after a setter to learn the new value; it still shows the old one.

❒ Trusting the Commit

➔ IF a component renders often THEN let React change the page; the commit changes only what differs.

➔ ALWAYS keep state in the component that shows it, so a change renders only that part of the tree.

➔ NEVER rebuild part of a React page with `innerHTML`; it replaces the nodes and wipes typed text.

**DO THIS:** compute the next number once and report it

```jsx right
function handleLike() {
  const next = likes + 1;
  setLikes(next);
  sendLikeEvent(next);
}
```

**DO NOT DO THIS:** read the number from the page after the setter

```jsx wrong
function handleLike() {
  setLikes(likes + 1);
  const shown = document.querySelector('.like-count').textContent;
  sendLikeEvent(shown);
}
```

| | **PLAIN DOM CODE**<br>(`textContent = 1`) | **REACT**<br>(`setLikes(1)`) |
| ---: | :--- | :--- |
| **When the page changes** | On the line that sets it | In the commit,<br>after the handler finishes |
| **What a change runs** | Only the line you wrote | The component that owns the state<br>and every component inside it |
| **Typed text in an input** | Wiped if the HTML is rebuilt<br>with `innerHTML` | Kept; the commit changes<br>only the nodes that differ |
| **What the next line reads** | The new value | The old value;<br>compute the new one first |
