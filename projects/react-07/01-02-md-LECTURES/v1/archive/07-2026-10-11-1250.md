### Rigid layout cards sprawl when every design needs a prop

Every web interface relies on shared visual frames, such as cards, dialogs, and panels, that wrap different pieces of content across feeds and dashboards. In Lecture 6, we learned that props pass data strictly downward from parent to child, and every React component function receives a single read-only props object. When a component presents a fixed set of fields, explicit props establish a clean, predictable contract. But as an application grows, different pages demand different visual arrangements inside the exact same container frame.

To accommodate layout permutations inside a single card, a developer may add specialized props like `hasBadge`, `badgeText`, `hasAuthor`, `author`, and `buttonText`. As design requests multiply, the parameter list swells and the return statement fills with nested conditional checks. When an article omits a badge, the component still renders `<span className="badge">{badgeText}</span>`. Because the stylesheet styles `.badge` with a background color and padding, the card displays an ugly, empty colored pill on screen. Even worse, if reviewers ask to place the author above the headline on opinion pieces, the component cannot accommodate them because its internal markup order is hardcoded.

To see this naive approach in runnable code, examine how a developer initially attempts to support multiple visual layouts through specialized string and boolean props:

```jsx title="Naive Layout Prop Bloat"
function NewsCard({ title, badgeText, author }) { // rigid prop list
  return (
    <article className="card">
      <span className="badge">{badgeText}</span> {/* renders empty tag */}
      <h2>{title}</h2>
      <p>By {author}</p>
    </article>
  );
}
```

We wonder what rules govern container components, attribute forwarding, and default values in React:
- **How does markup placed between a component's tags reach the container?**
- **How do we let callers compose custom inner layouts without adding a prop for every piece?**
- **How do we pass HTML attributes like aria-label and id through a container without listing each one?**
- **Why does the order of attributes around a spread decide which class name wins?**
- **How do default values in destructuring protect against undefined classes and missing slots?**

In Lecture 10, we will see how a container whose slot is empty can evaluate conditional expressions to decide whether to render its outer frame or render nothing at all. This lesson builds on what earlier lessons established across our curriculum:
- **Lecture 3 (JSX Syntax and Compilation)**: JSX compiles tags into `_jsx()` function calls returning element objects, attributes like `aria-*` and `data-*` keep their hyphens, and the HTML `class` attribute is written as `className`.
- **Lecture 4 (JavaScript Expressions in JSX)**: Curly braces (`{}`) open an inline evaluation window, `null`, `undefined`, and booleans render empty slots on screen, string concatenation with `+` joins text, and objects cannot be rendered directly as children.
- **Lecture 5 (UI as a Tree and Component Hierarchy)**: Components organize into a top-down execution tree where data flows strictly downward along parent-child branches, and nesting elements in JSX builds the render tree.
- **Lecture 6 (Props and Parameter Destructuring)**: Attributes bundle into a single read-only props object, parameter destructuring unpacks specific keys in parameter lists, and default parameters assign fallbacks for missing values.
- **Native Browser Foundations**: We build on standard HTML semantic tags (`<div>`, `<span>`, `<h2>`, `<p>`), JavaScript object destructuring, and the browser development console.

### Content between component tags is called children

You can put content between the opening and closing tags of a component, just as you do with HTML tags:

```jsx title="Nesting Elements in a Card"
// nests headline between component tags
<Card>
  <h2>Night Trains</h2>
</Card>
```

React takes everything between `<Card>` and `</Card>` and hands it to the `Card` component as a prop called `children`. You do not choose this name: React always uses `children`. Inside `Card`, you place `{children}` where the content should appear:

```jsx title="Card Component Slot"
function Card({ children }) { // receives nested content
  return <div className="card">{children}</div>; // places content in frame
}
```

The same `Card` works with any content. Here `children` is a paragraph:

```jsx title="Nesting a Paragraph in a Card"
// nests paragraph between component tags
<Card>
  <p>Hello!</p>
</Card>
```

Whatever you write between a component's tags reaches that component as its `children` prop.

### Rest syntax gathers the keys you did not name

```js
const story = { title: 'Transit Accord', id: 'top', tone: 'quiet' };
const { title, ...rest } = story; // extracts title and gathers rest
console.log(rest); // { id: 'top', tone: 'quiet' }
```

The console prints an object with `id` and `tone`. Line 2 takes `title` out by name, and the three dots before `rest` collect every key that was not named into a new object. This is rest syntax in destructuring. It is plain JavaScript, so it works on any object, including the props object a component receives.

### Principles of React: Container Composition and Prop Spreading

### Question 1: Content placed between tags arrives as the children prop

A developer creates a card container to frame articles on a website. In the parent component, the developer places a headline element between the container opening and closing tags:

```jsx title="Card Call Site"
function Feed() { // parent component nests markup
  return (
    <CardContainer>
      <h2>Transit Accord Reached</h2> {/* headline nested in slot */}
    </CardContainer>
  );
}
```

However, inside `CardContainer`, the component returns a wrapper `<div>` but omits `{children}`:

```jsx title="Omitted Children Slot"
function CardContainer() { // wrapper component
  return <div className="card" />; // drops children silently
}
```

When the browser renders the page, DevTools shows an empty `<div class="card"></div>`. The headline text is missing from the screen, and the browser console prints zero errors.

**Why does content nested between a component's tags disappear from the screen?**

---

**ANSWER**

**The code does not do what we wanted.** React places nested content in a prop named children, but the container must place {children} in its returned markup to display it.

To display nested markup, `CardContainer` accepts the reserved prop named `children`:

```jsx title="CardContainer Slot"
function CardContainer({ children }) { // receives nested elements
  return <div className="card">{children}</div>; // places children in the frame
}
```

React delivers whatever sits between a component's opening and closing tags on the props object under the key `children`. The headline `<h2>Transit Accord Reached</h2>` arrives inside `CardContainer` as `children`, and line 2 places it inside the `<div>`.

The JSX compiler transforms nested markup into the `children` key of the props object: `_jsx(CardContainer, { children: _jsx("h2", { children: "Transit Accord Reached" }) })`. React invokes `CardContainer` with that props object. Because `CardContainer` returned `<div className="card" />` and never wrote `{children}` in its JSX, React renders only the outer `<div>` and silently discards the nested element. Crucially, components nested as children never execute if the container drops them. To display the content, the container must place `{children}` whole inside its returned markup.

```ascii title="Nested JSX compiling into props.children"
JSX Call Site:                       Compiled Output:
<CardContainer>             -->       _jsx(CardContainer, {
  <h2>Transit Accord</h2>               children: _jsx("h2", {
</CardContainer>                          children: "Transit Accord"
                                        })
                                      })
Container Return:                     Browser DOM:
<div className="card">      -->       <div class="card">
  {children}                            <h2>Transit Accord</h2>
</div>                                </div>
```

> [!PRINCIPLE]
> **Principle 1: Nested JSX arrives as the children prop**
> When you nest elements or text between a component's opening and closing tags, React delivers that content in the **children prop**. React passes it to the component function on its props object, like an attribute. The content appears on the screen only where the component writes **{children}** in its returned JSX. If the component never writes `{children}`, React renders the outer frame and drops the nested content without a warning.
>
> >> children prop : a reserved prop that receives elements or text nested between component tags
>
> *We should do this:*
> `function Card({ children }) {`
> `  return <div className="card">{children}</div>; // places children in the card`
> `}`
>
> *We should not do this:*
> `function Card({ children }) {`
> `  return <div className="card" />; // drops children without an error`
> `}`

In our runtime test, rendering `<CardContainer><h2>Transit Accord Reached</h2></CardContainer>` with `{children}` inside the `<div>` displays the headline inside the card frame.

### Question 2: Let the caller fill the container instead of adding a prop for every piece

A team maintains an article feed using `NewsCard` from our earlier Naive Layout Prop Bloat component. The editorial team requests three distinct visual layouts: an urgent bulletin with an alert badge, a standard story with an author, and an event notice with an action button. When the parent feed renders a standard story without a badge alongside an alert story:

```jsx title="StoryFeed Call Site"
function StoryFeed() { // renders stories through NewsCard
  return (
    <div className="feed">
      <NewsCard title="Transit Accord" badgeText="New" author="Anna" />
      <NewsCard title="Budget Debate" author="Clara" /> {/* omits badgeText */}
    </div>
  );
}
```

When a standard article renders without a badge (`<NewsCard title="Budget Debate" author="Clara" />`), DevTools reveals an empty element: `<span class="badge"></span>`. Because the CSS stylesheet styles `.badge` with a background color and padding, the card displays an ugly, empty colored pill on screen.

**Do we add a new prop to the container for every optional piece of layout?**

---

**ANSWER**

**The code does not do what we wanted.** Adding a prop for every piece bloats the component and leaves empty DOM elements on items that omit the prop.

Every new layout request forces developers to edit `NewsCard.jsx`, adding more props like `hasBadge`, `buttonText`, or `imageUrl`. The function body fills with nested ternary operators and conditional branches. Worse, the internal layout order is completely rigid: callers cannot place the author above the headline or put a badge below the title without adding even more boolean flags like `isAuthorTop`.

The solution is slot composition through `CardContainer`. The container renders only the outer visual frame and exposes an open slot with `{children}`. Each caller nests the exact elements it requires in the exact order it chooses. A story with a badge nests `<span className="badge">New</span>` alongside its headline. A story without a badge nests only the headline. A named prop stays only for a fixed requirement that every card must guarantee in a specific position, such as `title` on an article card.

```ascii title="Rigid layout props versus composable slot"
Rigid Props (NewsCard):             Composable Slot (CardContainer):
+------------------------------+    +------------------------------+
| NewsCard({ badgeText })      |    | CardContainer({ children })  |
|   <span class="badge"></span>|    |                              |
|   (empty pill if omitted!)   |    |   {children}                 |
|   <h2>Morning Dispatch</h2>  |    |   (caller nests what fits!)  |
+------------------------------+    +------------------------------+
```

> [!PRINCIPLE]
> **Principle 2: Let the caller fill the container instead of adding a prop for every piece**
> When different instances of a component need different inner layouts, let callers nest the elements they need through **slot composition**. Adding a prop for each optional piece forces the container to manage layout flags and leaves empty elements on items that omit the prop. Keep a named prop only for a value every instance must show in a fixed place, and let callers nest the rest through the open slot.
>
> >> slot composition : letting callers compose inner elements freely inside an open container slot
>
> *It is best practice to do this:*
> `<Card>`
> `  <span className="badge">New</span> {/* caller nests badge */}`
> `  <h2>Title</h2>`
> `</Card>`
>
> *Instead of doing this:*
> `<Card`
> `  badgeText="New" // adds prop to container for layout variation`
> `  title="Title"`
> `/>`

In our test, rendering two stories through `NewsCard` produced an empty `<span class="badge"></span>` on the second story. When rewritten using `CardContainer`, the first story nested `<span className="badge">New</span>`, while the second story omitted the badge entirely. A third story nested an action button without modifying a single line of `CardContainer.jsx`.

### Question 3: Spread only the props the container does not use

Callers need to attach accessibility labels, identifiers, and test IDs to the card. A developer decides to forward all props by spreading the incoming `props` object directly onto the container element:

```jsx title="Spreading Entire Props Object"
function CardContainer(props) { // receives full props object
  return (
    <div className="card" {...props}> {/* spreads all props onto native tag */}
      {props.children}
    </div>
  );
}
```

A caller renders the card with custom component data: `<CardContainer isFeatured={true} badgeText="New"><h2>Alert</h2></CardContainer>`. When the browser loads, the development console warns: `Warning: React does not recognize the isFeatured prop on a DOM element`. Inspecting the browser DOM reveals `<div class="card" badgetext="New">`.

**Can we pass the whole props object directly onto the container element with spread?**

---

**ANSWER**

**The code does not do what we wanted.** Spreading the whole props object leaks component props onto the native DOM element and triggers console warnings.

React validates attributes passed to native browser elements like `<div>`. When React encounters a non-standard camelCase prop like `isFeatured`, it warns that HTML does not recognize the attribute. When it receives a lowercase prop like `badgeText`, React writes `badgetext="New"` directly into the browser DOM. If a boolean prop like `featured={true}` is spread, React warns: `Warning: Received true for a non-boolean attribute featured`. Worse, if a component consumes a custom `title` prop and spreads everything onto a `<div>`, that title becomes an unintended browser hover tooltip.

To prevent DOM attribute leakage, unpack the props the component consumes and collect the remaining properties using JavaScript rest syntax: `{ children, isFeatured, ...rest }`. The consumed props stay in local variables, while `rest` gathers only unconsumed attributes like `id`, `aria-label`, and `data-story-id`. The component then writes `{...rest}` using JSX spread syntax on the underlying element.

```ascii title="Rest syntax isolating pass-through attributes"
Incoming Props Object:
{ children: [...], isFeatured: true, id: "top", aria-label: "Alert" }
     |                       \_____________________________________/
     v                                          v
Consumed by Container:                Collected into ...rest:
children, isFeatured                  { id: "top", aria-label: "Alert" }
                                                v
Forwarded with {...rest}:   <div className="card" {...rest}>
Browser DOM:               <div class="card" id="top" aria-label="Alert">
```

> [!PRINCIPLE]
> **Principle 3: Spread only the props the container does not use**
> When a container forwards extra attributes to a native DOM element, unpack the props it uses and collect the remaining properties with **rest syntax**: `{ children, isFeatured, ...rest }`. Then write only those remaining properties on the element with **JSX spread syntax**: `{...rest}`. Spreading the whole `props` object forwards component props too, causing **DOM attribute leakage** and development console warnings.
>
> >> rest syntax : gathering unpicked properties into a separate object with ...rest
> >> JSX spread syntax : writing each property of an object as a JSX attribute with {...rest}
> >> DOM attribute leakage : writing non-standard component props onto native browser DOM elements
>
> *We should do this:*
> `function Card({ isFeatured, children, ...rest }) {`
> `  return <div className="card" {...rest}>{children}</div>; // forwards rest`
> `}`
>
> *We should not do this:*
> `function Card(props) {`
> `  return <div className="card" {...props}>{props.children}</div>; // leaks props`
> `}`

In our runtime test, spreading `props` with `isFeatured={true}` and `badgeText="New"` produced the invalid attribute `badgetext="New"` in DevTools and logged console warnings. When rewritten to destructure `{ children, isFeatured, ...rest }`, the console remained completely clean, and attributes like `id` and `aria-label` reached the DOM `<div>` as intended.

### Question 4: Around a spread, the last attribute wins

The card container defines its base styling with `className="card"`. To allow callers to forward extra attributes, the developer writes `<div className="card" {...rest}>{children}</div>`. A caller passes a custom highlight class:

```jsx title="Caller Passing Custom Class"
function FeaturedStory() { // caller highlights story
  return (
    <CardContainer className="featured"> {/* passes custom class */}
      <h2>Transit Accord Reached</h2>
    </CardContainer>
  );
}
```

When the page loads, the card loses its rounded border and padding. Inspecting the element in DevTools reveals `class="featured"`. The base class `"card"` has completely disappeared from the DOM element.

**Why does a caller class name overwrite the container base class?**

---

**ANSWER**

**The code does not do what we wanted.** JSX applies attributes from left to right, so an attribute in rest replaces any attribute written before the spread.

JSX applies attributes strictly in the order they are written. When an attribute appears more than once on the same tag, the last attribute evaluated wins. In `<div className="card" {...rest}>`, the spread attribute appears after `className="card"`. Because `rest` contains `className: "featured"`, that incoming value completely replaces `"card"`. The component loses its foundational styles.

If the developer places `className="card"` after `{...rest}` (`<div {...rest} className="card">`), the container's base class overwrites the caller's class completely, preventing callers from adding custom utility styles. Attributes in JSX never merge automatically. To preserve both classes, unpack `className` in the parameter list and join both strings explicitly using string concatenation: `className={'card ' + className}`.

```ascii title="Left-to-right attribute evaluation order"
Case 1: Attribute before spread:
<div className="card" {...rest} />
rest has { className: "featured" }   --> class="featured" (base lost!)

Case 2: Attribute after spread:
<div {...rest} className="card" />
rest has { className: "featured" }   --> class="card" (caller lost!)

Case 3: Explicitly joined in JavaScript:
<div className={'card ' + className} {...rest} />
both classes joined                  --> class="card featured" (both kept!)
```

> [!PRINCIPLE]
> **Principle 4: Around a spread, the last attribute wins**
> JSX evaluates attributes from left to right through **attribute precedence**. When the same attribute appears more than once on an element, the last one written wins. An attribute placed before `{...rest}` serves as an overridable default that caller props replace. An attribute placed after `{...rest}` is an enforced value that replaces caller props. When both sides must contribute a class name, extract `className` and join both strings explicitly.
>
> >> attribute precedence : the left-to-right order where later JSX attributes overwrite earlier ones
>
> *It is best practice to do this:*
> `function Card({ className, children, ...rest }) {`
> `  const fullClass = 'card ' + className; // joins base with caller`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`
>
> *Instead of doing this:*
> `function Card({ children, ...rest }) {`
> `  return <div className="card" {...rest}>{children}</div>; // caller overwrites`
> `}`

In our test, placing `className="card"` before `{...rest}` when the caller passed `className="featured"` rendered `class="featured"`. Placing `className="card"` after `{...rest}` rendered `class="card"`. When `className` was unpacked and joined with `className={'card ' + className}`, the browser DOM rendered `class="card featured"`, preserving both base borders and custom highlights.

### Question 5: A default fills a prop the caller left out

The developer merges class names using `className={'card ' + className}`. But when a standard story renders without passing a custom class (`<CardContainer><h2>Budget Debate</h2></CardContainer>`), inspecting the DOM in DevTools reveals a surprising attribute: `class="card undefined"`. Furthermore, when a container renders without nested content (`<CardContainer />`), the page displays an empty card frame with no placeholder notice.

```jsx title="Missing Class Name Call Site"
function StandardFeed() { // caller omits className
  return (
    <CardContainer> {/* omits className prop */}
      <h2>Municipal Budget Debate</h2>
    </CardContainer>
  );
}
```

**How do we prevent undefined appearing in merged classes when a prop is missing?**

---

**ANSWER**

**The code does not do what we wanted.** A missing prop evaluates to undefined, so concatenating it with a string produces the word undefined in the class attribute.

When a caller omits an attribute, that property evaluates to `undefined`. Inside JSX content, `{undefined}` renders as an empty slot without printing characters. But inside JavaScript string concatenation, `'card ' + undefined` coerces `undefined` into the string `"undefined"`, producing `"card undefined"` in the DOM.

To fix this, assign a default parameter value in the destructuring list: `className = ''`. When the caller omits `className` or passes `undefined`, the variable receives `''`, producing the clean string `'card '`. Similarly, assigning `children = <p>No story yet</p>` provides a fallback element when no children are nested. Remember the rule established in Lecture 6: default parameters engage strictly when a value is missing or `undefined`; they do not engage when a caller passes `null` or `false`.

```ascii title="Evaluating missing prop against default parameter fallback"
Caller Passes:          Parameter Result:         DOM Output:
className="featured"    className = "featured"    class="card featured"
className={undefined}   className = "" (default)  class="card " (clean!)
className omitted       className = "" (default)  class="card " (clean!)
className={null}        className = null          class="card null" (no default)
```

> [!PRINCIPLE]
> **Principle 5: A default fills a prop the caller left out**
> A missing prop evaluates to `undefined`. In JSX content, `undefined` renders an empty slot without printing text. But in string concatenation, `'card ' + undefined` coerces `undefined` into the text `'card undefined'`. Assign a **default parameter value** in the destructuring list to fill a missing prop: `className = ''`. Default parameter values engage only when a prop is missing or strictly `undefined`; they do not engage when a caller passes `null` or `false`.
>
> >> default parameter value : a fallback value assigned in destructuring when a prop is missing or undefined
>
> *We should do this:*
> `function Card({ className = '', children, ...rest }) {`
> `  const fullClass = 'card ' + className; // fallback prevents undefined`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`
>
> *We should not do this:*
> `function Card({ className, children, ...rest }) {`
> `  const fullClass = 'card ' + className; // produces card undefined`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`

In our runtime test, rendering `<CardContainer>` with no `className` produced `class="card undefined"` in the DOM. Adding `className = ''` changed the DOM output to `class="card "`, which cleanly matched the `.card` CSS selector. Rendering `<CardContainer />` with no children displayed the fallback notice `"No story yet"`. Passing `<CardContainer>{null}</CardContainer>` bypassed the default and rendered an empty frame.

### Let's Design a Practical Example

### Step 1: First, we construct the slot-based container component <CardContainer.jsx>

We author the foundational container component `CardContainer.jsx` to establish the reusable visual frame for dispatches. Instead of accepting specialized layout flags that dictate inner elements, `CardContainer` exposes an open slot by destructuring `children` from its parameter list. Notice how the parameter signature also unpacks `color = 'gray'` and `className = ''` with explicit default parameter values, while collecting all remaining pass-through attributes into `...rest`. The component calculates a merged CSS class string and forwards `...rest` onto the root `<div>`.

```jsx title="CardContainer.jsx"
export default function CardContainer({
  children, color = 'gray', className = '', ...rest // unpacks slot
}) {
  const cls = `card card-${color} ${className}`.trim();
  return (
    <div className={cls} {...rest}> {/* forwards props to wrapper */}
      {children}
    </div>
  );
}
```

Reviewing `CardContainer.jsx` highlights the power of container components. The container remains completely decoupled from the specific elements it wraps. It manages border styles, background themes, and attribute forwarding, while leaving the interior layout completely open for callers to fill.

### Step 2: Next, we assemble the composable editorial grid <EditorialGrid.jsx>

We construct the caller component `EditorialGrid.jsx` to organize three morning dispatches. When designing feeds that support multiple visual permutations, developers face an architectural crossroad: whether to use a monolithic card component loaded with specialized boolean flags, or use slot composition with `children` to let each call site compose its own markup. In `EditorialGrid`, we import `CardContainer` once and nest three entirely different layouts without touching `CardContainer.jsx`. One card nests an alert badge, headline, and summary; the second nests a headline and author; the third relies on default props while nesting a headline and notice.

```jsx title="EditorialGrid.jsx" startLine="1" continues="bottom"
import CardContainer from './CardContainer.jsx';

export default function EditorialGrid() { // caller composes dispatches
  return (
    <section className="editorial-grid">
      <h2 className="section-heading">Front Page Dispatches</h2>
      <CardContainer color="red" className="featured-alert">
        <span className="alert-badge">ALERT</span>
        <h3 className="headline">Transit Accord Reached</h3>
      </CardContainer>
```

```jsx title="EditorialGrid.jsx" startLine="11" continues="top"
      <CardContainer color="gray">
        <h3 className="headline">Municipal Budget</h3>
        <span className="author">By Clara Foster</span>
      </CardContainer>
      <CardContainer>
        <h3 className="headline">Weekend Gallery</h3>
      </CardContainer>
    </section>
  ); // closes editorial grid
}
```

Reviewing `EditorialGrid.jsx` proves that slot composition accommodates infinite layout permutations without modifying container code. Each call site controls its own inner hierarchy while inheriting identical card framing, padding, and elevation.

### Step 3: Finally, we mount the editorial layout inside <App.jsx>

To complete our application hierarchy, we mount `EditorialGrid.jsx` inside the root container `App.jsx`. In standard web development, layout wrappers often required complex script queries to locate containers and inject fragments. In React, the entire interface organizes into a clean component hierarchy. `App.jsx` acts as the top-level application shell, hosting the editorial grid within the primary layout. When React renders `App`, the mounting engine evaluates the full tree in memory and paints the resulting DOM nodes in a single, predictable operation.

```jsx title="App.jsx"
import EditorialGrid from './components/EditorialGrid.jsx'; // grid layout

export default function App() {
  return (
    <main className="feed-layout"> {/* top-level layout shell */}
      <EditorialGrid />
    </main>
  );
}
```

Reviewing `App.jsx` completes the top-down render pipeline. Data originates in the feed container, flows downward as props into individual card components, and terminates in native HTML elements. At no point does a child component reach upward or horizontally to alter surrounding state.

In legacy web applications, supporting diverse card layouts resulted in bloated, fragile components weighed down by dozens of boolean parameters and conditional branches. In React, container composition with the `children` prop cleanly separates outer visual styling from inner content. `CardContainer` manages borders, color styling, and attribute forwarding, while callers nest whatever headlines, badges, or summaries each dispatch requires. Because `CardContainer` destructures what it consumes and forwards `...rest`, callers can safely attach accessibility labels and custom utility classes without leaking component-only props to the DOM.

### For the interview

> **The Interview Question:** How do the children prop, spread attributes, and default values work?

**1. The Hidden Signal**

The interviewer is probing your mastery of component composition architecture, compiler transformations, JavaScript rest and spread syntax, attribute precedence, and DOM attribute leakage. Junior developers explain props as HTML attributes. Senior engineers explain that JSX compiles nested tags into `props.children` (`_jsx(CardContainer, { children: [...] })`), implementing inversion of control. They explain that pass-through wrappers destructure consumed props and forward `...rest` to prevent unknown-prop console warnings, that JSX evaluates attributes left to right, and that default parameters protect against `undefined` string coercion.

**2. The Classic Trap**

Assuming `children` is always an array. In React, `children` is an opaque data structure: if a caller nests one element, `children` is an element object (`children.type === 'h2'`); if a caller nests two elements, `children` is an array; if a caller nests text, `children` is a string. Calling `children.map()` directly on an unverified child will crash with `TypeError: children.map is not a function`. Another trap is blindly writing `<div {...props} />`, which dumps component props into the DOM and triggers React warnings.

**3. What is Actually Going On**

At compile time, nested JSX compiles into `_jsx(Card, { children: [...] })`. The container receives lightweight element descriptors, not rendered HTML output. Spreading attributes copies object keys from left to right; whichever attribute evaluates last wins. Destructuring default values trigger exclusively when incoming properties are `undefined` or omitted, never when they are `null` or `false`.

**4. Where It Gets Tricky**

Edge cases in JSX compilation: if a caller passes both an attribute named `children` and nested elements inside the tags, `<Card children="attr">nested</Card>`, the nested content wins because the compiler evaluates nested elements into `children` after opening tag attributes. Furthermore, a container's function body executes before child component functions execute; if a container omits `{children}`, child component functions never run at all.

### Glossary

- **children prop**: The reserved React property that captures whatever markup sits between a component's opening and closing tags.
- **container component**: A component that provides a reusable outer visual frame while leaving its inner content open for callers to supply through slots.
- **slot composition**: The architectural pattern of structuring user interfaces by nesting components inside container placeholders rather than passing monolithic layout configuration flags.
- **rest syntax**: The JavaScript `...rest` pattern in destructuring that gathers unextracted object properties into a fresh object.
- **JSX spread syntax**: The `{...rest}` JSX notation that unpacks an object's properties as attributes on an element tag.
- **default parameter value**: A fallback value assigned during destructuring that applies when an incoming property is `undefined` or omitted.

### Summary

**Container Composition and Prop Spreading Architecture**  
*Essential rules for building reusable frames and forwarding attributes*

❒ Inversion of Control with Slots

➔ IF a component wraps diverse layout variations across pages, THEN expose an open slot with `{children}` rather than adding boolean flags for every permutation.

➔ IF a card requires fixed layout fields in guaranteed positions, THEN declare dedicated named props like `title` and place `{children}` around them.

❒ Controlled Prop Spreading

➔ IF a wrapper component forwards extra attributes to a native DOM element, THEN destructure consumed props and spread only `...rest` onto the element.

➔ IF a component accepts custom data props, THEN never spread the entire `props` object onto native DOM elements to prevent attribute leakage and console warnings.

❒ Attribute Precedence and Defaults

➔ IF specifying overridable defaults on a wrapper element, THEN place default attributes before `{...rest}` and enforced attributes after `{...rest}`.

➔ IF merging class names on a wrapper component, THEN assign a default parameter `className = ''` and combine the strings explicitly.

**DO THIS:** Compose inner layout with children and merge class names explicitly

```jsx right
function CardContainer({
  children,
  color = "gray",
  className = "",
  ...rest
}) {
  const cls = `card card-${color} ${className}`.trim();
  return (
    <div className={cls} {...rest}>
      {children}
    </div>
  );
}
```

**DO NOT DO THIS:** Bloat containers with layout flags and spread unconsumed props

```jsx wrong
function CardContainer(props) {
  return (
    <div className="card" {...props}>
      {props.children}
    </div>
  );
}
```
