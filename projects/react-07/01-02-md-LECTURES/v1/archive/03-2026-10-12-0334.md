### Pasting raw HTML tags into a component fails the build

In traditional web development, authors write static HTML tags freely across template files. When creating an article card, you place an image, a heading, and a paragraph side by side in markup. Web browsers parse raw HTML through a forgiving algorithm that accepts unclosed tags and multiple sibling elements at the document level. When moving to React, developers naturally assume that JSX is identical to HTML written inside JavaScript files. You create a component named `ArticleCard()`, paste your approved HTML markup directly after `return (`, and run your build command.

When the build runs, the compiler halts immediately and emits multiple fatal syntax errors. The terminal reports that adjacent JSX elements must be wrapped in an enclosing tag, pointing directly between your heading and paragraph. On the next line, the parser reports that an unclosed image tag was found where a matching closing tag was expected. Zero JavaScript bundles are emitted to disk, the development server halts, and the browser displays a blank screen. Raw markup that rendered cleanly in a static browser file completely fails to compile inside a React component.

To see this failure in concrete code, examine how a developer attempts to return adjacent, unclosed HTML tags from an article card component:

```jsx title="Naive HTML Paste Anti-Pattern"
export default function ArticleCard() { // returns adjacent raw tags
  return (
    <h2>Night Trains Return</h2>
    <img src="/img/train.jpg">
    <p>Sleeper routes reopen.</p>
  );
}
```

Notice what happened under the hood. This fatal crash occurs because JSX is not an HTML template language. JSX is a syntax extension for JavaScript that compiles each tag into a `_jsx` function call. When the compiler encounters adjacent tags without an enclosing parent, it attempts to return multiple expressions from a single return statement, which ECMAScript grammar forbids. Furthermore, while browser HTML parsers maintain a hardcoded dictionary of void tags that close automatically, the JSX parser enforces strict XML grammar where every opened tag must be explicitly terminated.

When the browser encounters unclosed tags in standard HTML markup, it activates forgiving error-recovery algorithms defined by the HTML5 specification. If an `<img>` or `<input>` tag lacks a closing slash, the browser creates the element and continues parsing subsequent siblings without interruption. In contrast, the JSX compiler builds a formal Abstract Syntax Tree before any browser sees the code. Because the compiler enforces strict token boundaries, an unclosed tag leaves the AST node open, causing the parser to treat downstream tags as illegal children and aborting bundle generation.

### The compiler transforms JSX tags into function calls and element objects

JSX stands for JavaScript XML. It is a syntax extension that allows developers to write HTML-like markup directly inside JavaScript files. While JSX looks like HTML, the browser engine never executes JSX directly. Before code reaches the browser, a build compiler parses the markup and transforms every tag into a JavaScript function call named `_jsx()`.

When the compiler processes `<h2 className="headline">Night Trains Return</h2>`, it transforms that tag into `_jsx("h2", { className: "headline", children: "Night Trains Return" })`. At runtime, calling `_jsx()` produces a lightweight JavaScript object called a React element. A React element is an in-memory descriptor with properties such as `type: 'h2'` and `props`. React reads these descriptor objects during render and calls `document.createElement()` to create the real browser DOM nodes.

Because JSX tags compile into standard JavaScript function calls, JSX expressions are first-class JavaScript values. You can assign a JSX tag to a local variable, pass it as an argument, or return it from a function. Furthermore, any attributes written on a JSX tag become key-value pairs on the second argument of `_jsx()`. Understanding that JSX is JavaScript provides the foundation for all syntax rules that follow.

### JavaScript functions return one expression unless wrapped in a root or a Fragment

In JavaScript, a `return` statement can only return a single value or expression. When you write `return 42;`, the engine returns that single number. If you attempt to write two expressions side by side without an operator, such as `return a b;`, the JavaScript parser halts with a fatal syntax error. Even if you separate them with the comma operator, as in `return (a, b);`, the comma operator evaluates both but returns only the second expression `b`, discarding `a`.

Because every JSX tag compiles into a distinct `_jsx()` function call, writing two adjacent tags side by side after `return` is equivalent to writing two function calls without an operator: `return _jsx("h2", ...) _jsx("p", ...);`. This syntax is invalid JavaScript. To return multiple elements from a component, you must wrap them inside a single enclosing root element, such as an `<article>` container or a `<main>` shell.

Wrapping adjacent elements in an extra `<div>` satisfies the compiler, but it inserts a real DOM element into the page. Intermediate `<div>` nodes pollute the DOM tree and break CSS rules that rely on direct parent-child relationships, such as child selectors (`.stories > li`) or flexbox and grid layouts. To group siblings without adding an extra DOM node, React provides a virtual container called a Fragment, written `<>...</>`. React unpacks Fragments in memory and mounts child elements directly into the parent container.

### JSX requires closed tags and JavaScript property names

In native HTML, elements fall into two distinct categories: container elements that enclose content, and void elements that cannot contain children. The HTML specification defines a fixed dictionary of void elements, including `<img>`, `<input>`, `<br>`, and `<hr>`. In HTML, these tags never require closing tags. In contrast, JSX enforces strict XML grammar where every opening tag must be explicitly terminated, either with a matching closing tag or with a trailing self-closing slash (`<img />` or `<br />`).

In raw HTML markup, developers write `class="headline"` and `<label for="email">`. However, in JavaScript, `class` and `for` are reserved keywords used for declaring ES6 classes and writing loops. Decades ago, the browser DOM specification resolved this collision by naming element object properties `element.className` and `element.htmlFor`. Because JSX attributes become keys on a JavaScript props object, React aligns with these DOM property names, using `className` and `htmlFor` to prevent reserved keyword collisions.

Beyond `className` and `htmlFor`, React writes multi-word HTML attributes in camelCase, such as `tabIndex` instead of `tabindex` and `strokeWidth` instead of `stroke-width`. If a developer writes raw HTML attribute names, React still sets the property on the element but prints clear warning messages in the browser development console. As an explicit exception to the camelCase rule, accessibility attributes (`aria-*`) and custom data attributes (`data-*`) keep their hyphens to match standard HTML specifications.

### Question 1: A component returns descriptor objects rather than HTML strings

A developer creates an article headline and assigns the JSX markup to a local variable before returning it from `ArticleCard`:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() {
  const headline = <h2 className="headline">Night Trains</h2>; // in memory
  console.log(headline); // prints JavaScript object, not HTML string
  return headline;
}
```

The developer inspects the browser console expecting to see a rendered HTML string such as `<h2 class="headline">Night Trains</h2>`. Instead, the console prints a plain JavaScript object with properties `type: "h2"` and `props: { className: "headline", children: "Night Trains" }`.

**Is the markup returned by a component genuine HTML?**

---

**ANSWER**

**The code works as React intended.** JSX is a syntax extension that produces plain JavaScript objects.

At build time, the compiler translates `<h2 className="headline">Night Trains</h2>` into `_jsx("h2", { className: "headline", children: "Night Trains" })`. At runtime, calling `_jsx()` evaluates to a plain JavaScript object called a React element. React evaluates these in-memory descriptors during render and calls `document.createElement("h2")` to paint real DOM nodes on the page. The browser engine never encounters JSX directly.

```ascii title="How JSX transforms into DOM elements"
JSX Source:     <h2 className="headline">Night Trains</h2>
                      |
                      v  (Compiler Transform)
Function Call:  _jsx("h2", { className: "headline", children: "Night Trains" })
                      |
                      v  (Runtime Evaluation)
React Element:  { type: "h2", props: { className: "headline", ... } }
                      |
                      v  (Commit)
Browser DOM:    <h2 class="headline">Night Trains</h2>
```

> [!PRINCIPLE]
> **Principle 1: JSX is JavaScript that describes elements**
> Markup inside a component is not an HTML template string. The build compiles each tag into a `_jsx` function call that evaluates to a plain JavaScript object called a React element. React reads these descriptor objects during render and constructs the corresponding browser DOM nodes. Because JSX is JavaScript, you can place element expressions anywhere a JavaScript value is valid, such as inside variables or return statements.
>
> *We should do this:*
> `const element = <h2 className="title">Night Trains</h2>;`
> `// compiles to _jsx("h2", { className: "title", children: "..." })`

In our `ArticleCard` component, logging a JSX tag proves what exists in JavaScript memory. When you declare `const headline = <h2 className="headline">Night Trains</h2>;` and pass it to `console.log(headline)`, the console does not display a string of angle brackets. Instead, it displays a plain JavaScript object with properties `type: "h2"` and `props: { className: "headline", children: "Night Trains" }`. The browser DOM is never touched during this assignment; React evaluates these descriptor objects during its render pass and coordinates the creation of physical DOM elements.

### Question 2: A component must return a single root element

A developer attempts to return a story headline and a summary paragraph side by side from `ArticleCard`:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() { // adjacent tags violate return grammar
  return (
    <h2>Night Trains Return</h2>
    <p>Sleeper routes reopen.</p>
  );
}
```

When the developer executes the build command, compilation halts instantly with a fatal syntax error. The Babel compiler reports: `SyntaxError: Adjacent JSX elements must be wrapped in an enclosing tag. Did you want a JSX fragment <>...</>?`. The esbuild bundler emits an unexpected token error, and zero code executes in the browser.

**Why does placing two sibling tags after return cause the compiler to fail?**

---

**ANSWER**

**The code does not do what we wanted.** A JavaScript function can only return a single value.

Each JSX tag compiles into an independent `_jsx()` function call expression. In JavaScript, a `return` statement can only return a single value. Placing two function calls side by side after `return` is invalid language grammar. Even if wrapped in parentheses with the comma operator, JavaScript evaluates both expressions but returns only the second value, discarding the first. To satisfy ECMAScript function return grammar, all sibling elements must be enclosed inside a single root container element, such as an `<article className="card">`.

To fix this failure, enclose the adjacent sibling tags inside a single root container:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() {
  return ( // single root container satisfies return grammar
    <article className="card">
      <h2>Night Trains Return</h2>
      <p>Sleeper routes reopen.</p>
    </article>
  );
}
```

```ascii title="JavaScript function return grammar with JSX"
Adjacent Sibling Tags (Syntax Error):
  return _jsx("h2", ...) _jsx("p", ...);  <-- Multiple return values forbidden!

Single Root Container (Valid JavaScript):
  return _jsx("article", {
    className: "card",
    children: [ _jsx("h2", ...), _jsx("p", ...) ]  <-- Single return value!
  });
```

> [!PRINCIPLE]
> **Principle 2: A component returns one root because a function returns one value**
> Every JSX tag compiles into an independent `_jsx` function call expression. In JavaScript, a `return` statement can only return a single value. Placing two adjacent tags side by side without an enclosing container attempts to return two separate expressions, which violates JavaScript language grammar and halts compilation. To return multiple elements, enclose them inside a single root container.
>
> *We should do this:*
> `return (`
> `  <article className="card"> {/* single root container */} `
> `    <h2>Night Trains Return</h2>`
> `    <p>Sleeper routes reopen.</p>`
> `  </article>`
> `);`
>
> *We should not do this:*
> `return (`
> `  <h2>Night Trains Return</h2> {/* adjacent floating tag */} `
> `  <p>Sleeper routes reopen.</p> {/* cannot return two values */} `
> `);`

In our `ArticleCard` component, returning `<h2>` and `<p>` side by side demonstrates the physical return limit of JavaScript. The compiler attempts to transpile the code into `return _jsx("h2", ...), _jsx("p", ...);`. In JavaScript, returning multiple bare expressions is a fatal grammar error. Even with parentheses, the comma operator would discard the heading and return only the paragraph. Wrapping both tags in an `<article className="card">` container produces a single outer `_jsx("article", ...)` call with the heading and paragraph packaged as an array inside its `children` prop, satisfying ECMAScript return grammar.

### Question 3: Grouping siblings with a div can break list and layout styling

A developer creates a component named `TopStories` that returns two story items. To satisfy the single-root rule, the developer wraps both list items in a `<div>`:

```jsx title="TopStories.jsx"
export default function TopStories() {
  return ( // wrapper div creates unnecessary intermediate DOM node
    <div>
      <li>Night trains return</li>
      <li>High-speed rail opens</li>
    </div>
  );
}
```

In `App.jsx`, the developer mounts `TopStories` inside a styled unordered list: `<ul className="stories"><TopStories /></ul>`. The stylesheet defines `.stories > li { color: #0f766e; }`. When the page renders, the list items appear with standard black text, completely unstyled.

**Why should you group siblings with a Fragment when no wrapper element is needed?**

---

**ANSWER**

**The code does not do what we wanted.** An intermediate div creates a real DOM element that interrupts direct parent-child relationships.

A `<div>` tag compiles to `_jsx("div", ...)` and creates a real DOM node in the browser. In HTML5, the only permitted direct children of a `<ul>` element are `<li>` elements. When `TopStories` wraps items in a `<div>`, the living DOM structure becomes `<ul><div><li></li><li></li></div></ul>`. CSS child combinators (`.stories > li`) require direct parent-child relationships, so the selector matches zero items. Furthermore, intermediate divs break CSS flexbox and grid alignments that format direct child tags.

The fix is using a React Fragment, written `<>...</>`. A Fragment satisfies JavaScript's single return requirement in memory without emitting any DOM element:

```jsx title="TopStories.jsx"
export default function TopStories() {
  return ( // Fragment groups siblings without creating a DOM node
    <>
      <li>Night trains return</li>
      <li>High-speed rail opens</li>
    </>
  );
}
```

With a Fragment, the DOM becomes `<ul><li>...</li><li>...</li></ul>`, and `document.querySelectorAll('.stories > li').length` evaluates to 2.

```ascii title="DOM structure with wrapper div versus React Fragment"
With Intermediate <div>:            With React Fragment <>...</>:
  <ul>                                 <ul>
    <div>  <-- Interrupts styling!       <li>Night trains return</li>
      <li>Night trains return</li>       <li>High-speed rail opens</li>
      <li>High-speed rail opens</li>   </ul>  (Direct child elements)
    </div>
  </ul>
```

> [!PRINCIPLE]
> **Principle 3: Group with a Fragment when the page needs no extra element**
> Wrapping elements in a `<div>` creates a real DOM element that can disrupt CSS child selectors, flexbox hierarchies, and grid layouts. When elements must be grouped solely to satisfy the single-root rule, wrap them in a **Fragment**, written `<>...</>`. A Fragment satisfies the single-return requirement in JavaScript without adding any node to the browser DOM. Use an element like `<article>` only when the page requires a semantic container or styling box.
>
> >> Fragment : a virtual JSX container that groups children without rendering a DOM node
>
> *We should do this:*
> `<ul className="stories">`
> `  <>`
> `    <li>Night trains return</li> {/* mounts directly in ul */} `
> `    <li>High-speed rail opens</li>`
> `  </>`
> `</ul>`
>
> *We should not do this:*
> `<ul className="stories">`
> `  <div> {/* extra div breaks child selectors and list semantics */} `
> `    <li>Night trains return</li>`
> `    <li>High-speed rail opens</li>`
> `  </div>`
> `</ul>`

In our `TopStories` component, returning list items wrapped in a `<div>` reveals the architectural cost of unneeded DOM nodes. The HTML specification dictates that the only permitted direct children of a `<ul>` element are `<li>` elements. When `TopStories` wraps items in a `<div>`, the living DOM structure becomes `<ul><div><li></li></div></ul>`. Styles defined for `.stories > li` fail to match because `div` is not an `li`. Replacing `<div>` with `<>...</>` produces a clean flat hierarchy where the list items mount directly inside `<ul>`, allowing child selectors and CSS grid alignments to apply cleanly.

### Question 4: Every tag in JSX must be explicitly closed

A developer pastes an image element into `ArticleCard` following standard HTML void element syntax:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() { // unclosed void tag breaks parser
  return (
    <article className="card">
      <img src="/img/train.jpg" alt="Night train">
      <h2>Night Trains Return</h2>
    </article>
  );
}
```

The terminal compiler halts immediately with a fatal syntax error. The esbuild bundler reports: `SyntaxError: Unexpected closing "article" tag does not match opening "img" tag`.

**Why does JSX reject unclosed HTML void tags like img and br?**

---

**ANSWER**

**The code does not do what we wanted.** The JSX parser requires explicit closing boundaries for every tag.

In native HTML, the browser parser maintains a hardcoded dictionary of void elements (`<img>`, `<input>`, `<br>`, `<hr>`) that cannot contain child content and never require closing tags. In contrast, JSX enforces strict XML grammar with zero tag dictionaries. When the parser encounters `<img`, it expects either a matching closing tag `</img>` or an explicit self-closing slash `/>`. Without a closing slash, the parser assumes that downstream tags (`<h2>`, `</article>`) are inner children of the image. When it encounters `</article>`, the open tag stack mismatches and compilation fails.

The fix is adding an explicit self-closing trailing slash to the image tag:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() {
  return ( // trailing slash closes void tag explicitly
    <article className="card">
      <img src="/img/train.jpg" alt="Night train" />
      <h2>Night Trains Return</h2>
    </article>
  );
}
```

```ascii title="AST parser tag stack for unclosed versus closed tags"
Unclosed HTML Void Tag:              Explicitly Terminated JSX Tag:
  <article>                            <article>
    <img src="...">  (stays open!)       <img src="..." />  (closed!)
      <h2>...</h2>   (child error)       <h2>...</h2>
  </article>         (stack mismatch!) </article>  (tree matches!)
```

> [!PRINCIPLE]
> **Principle 4: Close every tag, including <img /> and <br />**
> While standard HTML allows **void elements** like `<img>` and `<br>` to remain open, JSX enforces strict XML syntax where every tag must be explicitly terminated. Without a closing tag or a trailing self-closing slash, the compiler treats all subsequent markup as child content of that tag. Always terminate self-contained tags with a trailing slash, such as `<img />` or `<br />`, so the parser can resolve the element boundary.
>
> >> void elements : HTML tags that cannot contain children and have no closing tags in HTML
>
> *We should do this:*
> `<article className="card">`
> `  <img src="/img/train.jpg" alt="Train" /> {/* closed slash */} `
> `  <h2>Night Trains Return</h2>`
> `</article>`
>
> *We should not do this:*
> `<article className="card">`
> `  <img src="/img/train.jpg" alt="Train"> {/* unclosed tag */} `
> `  <h2>Night Trains Return</h2>`
> `</article>`

In our `ArticleCard` component, pasting raw `<img src="/img/train.jpg" alt="Night train">` breaks the compiler because the JSX lexer cannot infer where the image element ends. Because the tag lacks a self-closing slash, the parser treats the subsequent `<h2>` tag as an inner child of the image. When the parser eventually encounters `</article>`, it finds an open `<img` node on its parsing stack that was never closed. Adding the trailing slash `<img ... />` informs the parser that the element terminates immediately and possesses zero children, emitting a clean `_jsx("img", { ... })` call.

### Question 5: JSX attributes map to JavaScript property names

A developer adds a newsletter subscription form to `ArticleCard` using standard HTML attribute names:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() { // raw HTML attributes trigger warnings
  return (
    <form className="newsletter-form">
      <label class="label" for="email">Newsletter</label>
      <input id="email" />
    </form>
  );
}
```

The application compiles and renders the form controls on screen. However, when the developer opens the browser development console, two red warnings appear: `Warning: Invalid DOM property 'class'. Did you mean 'className'?` and `Warning: Invalid DOM property 'for'. Did you mean 'htmlFor'?`.

**Why does React warn against writing class and for attributes?**

---

**ANSWER**

**The code does not do what we wanted.** Raw HTML attribute names trigger development console warnings and collide with JavaScript reserved keywords.

JSX attributes become keys of a JavaScript object passed to `_jsx()`. In JavaScript, `class` and `for` are reserved language keywords used for class definitions and loops. Decades ago, the W3C DOM Level 1 specification resolved this collision by naming element object properties `element.className` and `element.htmlFor`. React aligns with these DOM properties so attributes map directly to JavaScript object keys. Multi-word attributes use camelCase (`tabIndex`, `strokeWidth`). Hyphenated accessibility attributes (`aria-*`) and custom data attributes (`data-*`) keep their hyphens to match HTML standards.

The fix is renaming `class` to `className` and `for` to `htmlFor`:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() {
  return ( // DOM property names className and htmlFor silence warnings
    <form className="newsletter-form">
      <label className="label" htmlFor="email">Newsletter</label>
      <input id="email" />
    </form>
  );
}
```

```ascii title="Mapping JSX attributes to JavaScript DOM properties"
JSX Attribute:        Props Object:            DOM Property / Method:
  className="title"    --> { className: "title" }    --> element.className
  htmlFor="email"      --> { htmlFor: "email" }      --> element.htmlFor
  aria-label="Close"   --> { "aria-label": "Close" } --> element.setAttribute
```

> [!PRINCIPLE]
> **Principle 5: Write attributes as JavaScript names**
> Attributes in JSX become keys of a JavaScript props object. Because `class` and `for` are reserved keywords in JavaScript, React uses the corresponding browser DOM property names `className` and `htmlFor`. Multi-word attributes use camelCase, such as `tabIndex` and `strokeWidth`. As an exception, accessibility attributes starting with `aria-` and custom attributes starting with `data-` keep their hyphens to match HTML standards.
>
> *We should do this:*
> `<label className="label" htmlFor="email">Email</label>`
> `// maps cleanly to DOM properties and silences console warnings`
>
> *We should not do this:*
> `<label class="label" for="email">Email</label>`
> `// prints console warnings for invalid properties class and for`

In our `ArticleCard` component, adding a newsletter signup form with `<label class="label" for="email">` demonstrates how React enforces DOM property naming. While modern bundlers allow reserved words as object keys, React inspects incoming props during render. When it detects `class` or `for`, it logs prominent warnings in the development console because the underlying DOM nodes expect `className` and `htmlFor`. Renaming attributes to `className` and `htmlFor` aligns directly with `element.className` and `element.htmlFor`, leaving the console clean while preserving accessibility and CSS styling.

### Step 2: Next, we group list items with a Fragment <TopStories.jsx>

When returning multiple sibling elements that belong inside an external container like a `<ul>`, you encounter a foundational architectural crossroads:
- **Option 1 (The Bloated DOM Way)**: Wrap the sibling list items in an intermediate `<div>`, polluting the DOM tree and breaking CSS child selectors.
- **Option 2 (The Modern Idiomatic Way)**: Group the sibling list items with a React Fragment `<>...</>`, preserving direct parent-child relationships with zero DOM overhead.

First, examine Option 1 with an intermediate `<div>` wrapper:

```jsx title="Option 1: The Bloated DOM Way (Intermediate Div Wrapper)"
export default function TopStories() {
  return ( // intermediate div creates extra node inside ul
    <div>
      <li className="story-item">High-speed alpine rail opens</li>
      <li className="story-item">Sleeper booking platform launches</li>
    </div>
  );
}
```

In Option 1, the intermediate `<div>` satisfies JavaScript's single return requirement. However, when mounted inside a parent `<ul className="stories">`, the living DOM structure becomes `<ul><div><li></li><li></li></div></ul>`. This structure violates HTML5 list specifications, increases browser node count, and breaks CSS rules like `.stories > li` because the list items are no longer direct children of the list container.

Now, examine Option 2 using a clean React Fragment:

```jsx title="TopStories.jsx"
export default function TopStories() {
  return ( // Fragment mounts items directly into host ul
    <>
      <li className="story-item">High-speed alpine rail opens</li>
      <li className="story-item">Sleeper booking platform launches</li>
    </>
  );
}
```

In Option 2, the compiler wraps the siblings inside `_jsx(Fragment, { children: [...] })`. This satisfies JavaScript's single return value requirement at compile time. At runtime, React unpacks the Fragment and appends both `<li>` nodes directly into the host `<ul>` container. The living DOM tree remains clean and flat, allowing CSS child selectors and list styling rules to apply without obstruction.

Notice how `TopStories.jsx` establishes clean grouping:
1. It returns multiple sibling `<li>` tags without introducing extra DOM nodes.
2. It satisfies JavaScript return grammar by enclosing siblings in a virtual Fragment container.
3. It preserves parent CSS child selectors like `.stories > li`.

### Step 3: Finally, we assemble the layout shell inside <App.jsx>

To complete our application layout, we import and compose `ArticleCard.jsx` and `TopStories.jsx` inside the primary page shell `App.jsx`. In standard JavaScript, assembling this layout required querying container elements and appending nodes imperatively. In React, the entire document organizes into a declarative hierarchy. Notice that `App.jsx` wraps `TopStories` inside a semantic `<ul className="stories">` list, providing the proper host container for the Fragment's child items.

```jsx title="App.jsx"
import ArticleCard from './components/ArticleCard.jsx';
import TopStories from './components/TopStories.jsx';
export default function App() {
  return ( // primary shell mounts card and stories list
    <main className="app-shell">
      <ArticleCard />
      <ul className="stories"><TopStories /></ul>
    </main>
  );
}
```

When React evaluates `App`, the JSX compiler transforms `<ArticleCard />` and `<TopStories />` into function calls. React reconciles the tree in memory and paints the returned `<main>`, `<article>`, and `<ul className="stories">` nodes in a single atomic pass. Because `TopStories` returns a Fragment, the browser DOM receives `<ul><li>...</li><li>...</li></ul>` without any intermediate wrapper node. CSS rules such as `.stories > li` match both items directly, producing an accessible layout.

Notice how `App.jsx` establishes clean declarative boundaries:
1. It imports child components as first-class function identifiers.
2. It embeds `TopStories` inside an authentic semantic `<ul>` element.
3. It performs zero manual DOM querying or element manipulation, delegating page mounting to React.

### For the interview

> **The Interview Question:** What is JSX, what syntax rules must every snippet follow, and how do Fragments group elements without wrapper nodes?

**1. The Hidden Signal**

The interviewer is not merely testing whether you know how to write angle brackets inside a JavaScript file. They are probing whether you understand how JSX transpiles into function calls and why React enforces strict XML-like grammar. A junior candidate answers that JSX is simply "HTML in React." A senior engineer steps to the whiteboard and explains that JSX is syntactic sugar for `_jsx()` function calls that return plain JavaScript element descriptors. They explain that the single-root rule is an inescapable consequence of JavaScript function return grammar, not an arbitrary framework preference.

**2. The Classic Trap**

The classic trap is claiming that you can wrap adjacent siblings in a `<div>` anywhere without architectural consequences. Candidates often say "just put a div around it" whenever the single-root error appears. While adding a `<div>` silences the compiler, it pollutes the DOM tree with redundant nodes, breaks HTML5 list semantics (`<ul><div><li>`), and destroys CSS flexbox and grid layouts that depend on direct parent-child relationships. Another fatal trap is assuming that JSX attributes are identical to HTML attributes, forgetting that `class` and `for` collide with JavaScript reserved keywords and trigger console warnings.

**3. What is Actually Going On**

Under the hood, the build compiler transforms each JSX tag into a `_jsx(type, props)` function call. In JavaScript, a function can only return a single expression value. When you return two adjacent tags without an enclosing root, the compiler attempts to emit two separate function calls in a single return slot, which violates language grammar. Every component must therefore return a single root element or a Fragment. Furthermore, while browser HTML parsers have a hardcoded whitelist of void elements that never require closing tags, the JSX parser enforces strict XML grammar where every tag must be explicitly terminated with a closing tag or a self-closing slash (`<img />`). Finally, JSX attributes become keys on a JavaScript props object, so React uses DOM property names like `className` and `htmlFor` to prevent keyword collisions.

**4. Where It Gets Tricky**

Where this gets tricky in production is understanding how React Fragments work in memory. When you write `<>...</>`, the compiler emits `_jsx(Fragment, { children: [...] })`. React detects the internal Fragment symbol during reconciliation and treats it as a virtual container. When committing to the DOM, React completely skips creating a wrapper DOM node; it unpacks the child array and appends the child elements directly into the parent container. However, the shorthand `<>...</>` cannot accept attributes or keys. When rendering collections of grouped elements inside a loop, you must explicitly import `Fragment` from `'react'` and write `<Fragment key={item.id}>...</Fragment>`, as explored in Lecture 11.

### Glossary

- **JSX**: A syntax extension for JavaScript that allows developers to write declarative, HTML-like markup inside JavaScript files, compiling into nested `_jsx()` function calls.
- **React Element**: A lightweight, plain JavaScript object created by `_jsx()` that describes a DOM element's tag name, attributes, and children in memory.
- **Fragment**: A virtual JSX container, written `<>...</>`, that groups multiple sibling elements to satisfy the single-root rule without rendering any node in the browser DOM.
- **Void Element**: An HTML element that cannot contain child nodes or text content (such as `<img>`, `<input>`, or `<br>`) and must be self-closed in JSX.
- **className and htmlFor**: JavaScript DOM property names used in JSX instead of HTML's `class` and `for` attributes to avoid colliding with ECMAScript reserved keywords.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ The Single-Root Return Invariant

➔ ALWAYS return a single root element or Fragment from every component function because JavaScript functions can only return a single expression value.

➔ NEVER return adjacent sibling tags without an enclosing container because two floating expressions violate ECMAScript function return grammar.

❒ Sibling Grouping and DOM Fidelity

➔ ALWAYS use a React Fragment (`<>...</>`) when grouping sibling elements solely to satisfy the single-root rule without adding DOM overhead.

➔ NEVER wrap sibling elements in an unnecessary `<div>` when an extra container breaks CSS child selectors, flexbox hierarchies, or list semantics.

❒ Tag Closure and XML Strictness

➔ ALWAYS explicitly terminate every JSX tag with a closing tag or a self-closing trailing slash (`<img />`, `<br />`).

➔ NEVER leave HTML void elements unclosed because the JSX parser enforces strict XML grammar and halts compilation.

❒ Attribute Mapping and Reserved Keywords

➔ ALWAYS write JSX attributes using DOM property names like `className` and `htmlFor` to prevent collisions with JavaScript reserved keywords.

➔ NEVER write raw HTML `class` and `for` attributes in JSX because they trigger browser development console warnings.

**DO THIS:** return a single root or Fragment, close every tag, and use JavaScript DOM property names

```jsx right
function ArticleCard() {
  return (
    <article className="card">
      <img src="/img/train.jpg" alt="Train" className="thumb" />
      <h2 className="title">Night Trains Return</h2>
      <p className="summary">Sleeper routes reopen.</p>
    </article>
  );
}
```

**DO NOT DO THIS:** return adjacent floating tags, leave void elements unclosed, or use raw class attributes

```jsx wrong
function ArticleCard() {
  return (
    <h2>Night Trains Return</h2>
    <img src="/img/train.jpg" class="thumb">
    <p class="summary">Sleeper routes reopen.</p>
  );
}
```
