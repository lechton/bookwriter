### The Mystery of the Dual Click and the Vanishing Form

Think back to how you connected interactive controls in earlier lessons. In Lecture 13, you learned that React event handlers are functions passed as values to props like `onClick`. You saw that passing a bare function reference (`onClick={handleClick}`) defers execution until the user clicks, whereas invoking a function inside JSX braces runs it immediately during render. You also learned that child components use callback props to notify parents of user interactions.

However, real-world user interfaces rarely feature isolated, single-level buttons. In modern web applications, interactive buttons often live inside larger clickable containers, such as an action button nested inside an article card. Furthermore, users type continuous text into input fields and submit forms to filter content. In traditional browser scripting, developers attached event listeners directly to DOM elements and relied on browser events bubbling up the document tree.

On The National Times, Leo sits down to connect reader controls across the morning reading desk. Leo opens `SearchForm.jsx` and writes a search bar inside a standard form:

```jsx title="Naive Form Reload Attempt"
function SearchForm() {
  function handleSearch() {
    console.log("Searching news..."); // Lost on reload
  }
  return (
    <form onSubmit={handleSearch}>
      <button type="submit">Search News</button>
    </form>
  );
}
```

Leo types a query into the field and presses Enter to search. Instead of filtering the articles on the screen, the browser window flashes white and reloads the entire page. The address bar displays a trailing question mark: `http://localhost:5173/?query=transit`. All local JavaScript memory is wiped clean, and the search input resets to an empty string. The console log vanishes before Leo can read it.

Leo then turns to the article cards. Each card represents a news story. Clicking the card opens the full story in the reader. Inside each card, Leo places a small Bookmark button so readers can save articles for later reading. Leo clicks the Bookmark button. First, the console logs "Bookmarked story". But immediately afterward, the card's click handler fires and opens the story reader. The user wanted only to bookmark the item, but the application forced a page transition.

Why did these failures occur? In both cases, Leo hit fundamental browser mechanics that operate underneath React's declarative markup. In HTML, form submissions trigger native navigation by default, requesting a new document from the server. Simultaneously, user clicks bubble up the DOM tree, notifying every ancestor element in turn. To build modern interactive applications, we must understand how React wraps browser events and how to control event flow.

> [!WILD]
> **Why does clicking a nested button open the parent card?**
>
> In the browser DOM, events do not stay confined to the single element you clicked. Instead, the click event bubbles upward through every parent element in the document tree. When an article card contains a nested Bookmark button, clicking the button dispatches a click event that executes the button's handler first, and then travels upward to trigger the card's click listener. To keep nested button actions strictly local, you must intercept the event object and call `e.stopPropagation()`.

### The React Event Object and the Native DOM Boundary

To master user interaction in React, we must understand the object that arrives in our handlers. When a user clicks, types, or submits, the browser generates a native DOM event. Different browsers historically implemented event properties with subtle inconsistencies. React normalizes these differences by wrapping the browser event in a **React event object**, also known in the React community as a synthetic event.

This event object conforms to the W3C DOM standard. It exposes standard properties like `target`, `currentTarget`, `bubbles`, and `timeStamp`, providing identical behavior across all browsers. When you declare an event handler in React, the function receives this event object as its first argument: `function handleClick(e) { ... }`. By convention, developers name this parameter `e` or `event`. If you ever need to inspect the underlying native browser event directly, React exposes it through `e.nativeEvent`.

A frequent source of subtle bugs is confusing `e.target` with `e.currentTarget`. Imagine an article card containing an `<h3>` headline and a `<span>` icon. You attach an `onClick` handler to the outer `<article>` tag and store the article identifier in `data-id`. If the user clicks directly on the icon, `e.target` points to the `<span>` element. If your handler reads `e.target.dataset.id`, it returns `undefined` because the `<span>` does not have that dataset attribute. In contrast, `e.currentTarget` always points to the element that owns the running handler, which is the `<article>` tag. To read attributes reliably from the element that registered the listener, you must always read `e.currentTarget`.

Text inputs introduce a second critical operational difference: the timing of value updates. In native HTML, an `<input>` dispatches two separate events: `input` fires on every keystroke, while `change` fires only after the user unfocuses or tabs away from the field. React simplifies this model. In React, the `onChange` prop fires immediately on every character typed or deleted, mirroring the native `input` event. The current text is always available through `e.target.value`. If you need an event that waits until the user leaves the input, attach your handler to `onBlur` instead.

Finally, events follow a three-phase lifecycle: the **capture phase** (descending from the document root), the **target phase** (reaching the touched element), and the **bubble phase** (ascending back through ancestors). In React, standard JSX props like `onClick` listen during the bubble phase. All events bubble upward through ancestor handlers, with one notable exception: the `onScroll` event does not bubble, firing strictly on the element being scrolled.

### Principles of React: Event Handlers, Propagation, and Default Actions

In technical interviews, senior candidates must articulate where side effects belong, how the React event object resolves targets, why onChange fires on every keystroke, how event bubbling travels through ancestor components, and how to stop bubbling and browser defaults cleanly. To master these concepts, we formalize the six governing principles of event handling:

> [!PRINCIPLE]
> **Principle 1: Put Side Effects in Event Handlers, Never in the Component Body**
> Event handlers provide a safe home for side effects, keeping them out of the pure component rendering calculation:
>
> - **The Component Body (`ArticleCard`):** runs synchronously during render to calculate and return JSX markup.
> - **The Event Handler (`handleBookmark`):** runs asynchronously only when the user triggers an interaction, such as clicking a button.
>
> Placing side effects such as network requests, analytics logging, or storage writes in the component body causes them to execute on every render before the user has touched anything.
>
> >> side effect : work that changes something outside the component, such as a network request, storage write, or log entry
> >> component body : the top-level function scope executed synchronously during render to calculate JSX

In Lecture 12, you learned that React components must remain pure calculations that return JSX without modifying external variables. The component body executes every time React renders, and in development under StrictMode, React invokes the function body twice to detect unintended side effects. If you place a network request, analytics log, or storage write directly inside the component body, that operation fires twice on page load and repeats every time the component re-renders.

Event handlers exist specifically to house side effects. Because an event handler is stored as a function reference during render and called only when the user physically clicks, types, or submits, it is completely free from the purity restrictions of the render phase. An event handler may safely log analytics, send HTTP requests, write to browser storage, and later update application state without disrupting component rendering.

```jsx title="Side Effects in Event Handlers"
export default function ArticleCard({ title }) {
  console.log("Render card:", title); // Double-called in StrictMode
  function handleBookmark() {
    console.log("Saved bookmark:", title); // Runs strictly on click
  }
  return <button onClick={handleBookmark}>Save {title}</button>;
}
```

Notice the operational timing in the console. When the page loads, `Render card:` prints twice under StrictMode. The handler log `Saved bookmark:` does not print at all. When the user clicks the button twice, `Saved bookmark:` prints exactly two times, while the render log remains completely silent.

> [!PRINCIPLE]
> **Principle 2: Read CurrentTarget for the Listening Element and Target for What Was Touched**
> When a user interacts with your interface, the React event object gives you two different element references:
>
> - **`e.currentTarget` (The Listener):** the element to which the active event handler is attached, such as the parent `<article>` card.
> - **`e.target` (The Trigger):** the innermost element where the user interaction physically started, such as a nested `<span>` label or `<svg>` star icon.
>
> Reading dataset identifiers or attributes from `e.target` instead of `e.currentTarget` returns undefined whenever the user clicks an icon or nested label inside your listening container.
>
> >> e.currentTarget : the element to which the running event handler is attached
> >> e.target : the deepest element where the user interaction physically started

When a user clicks an element, the browser hit-testing algorithm determines the deepest element under the pointer and assigns it to `e.target`. The event then bubbles upward until it reaches an element with a registered listener, which React assigns to `e.currentTarget`.

If you attach an `onClick` handler to an `<article data-id="101">` container, clicking the card's nested `<span>★</span>` sets `e.target` to the `<span>` and `e.currentTarget` to the `<article>`. An engineer who writes `e.target.dataset.id` receives `undefined` because the `<span>` holds no `data-id`. In contrast, `e.currentTarget.dataset.id` reliably returns `"101"`. Whenever you need properties of the element that owns the handler, read `e.currentTarget`.

```jsx title="CurrentTarget vs Target Resolution"
export default function ArticleCard({ id }) {
  function handleClick(e) {
    console.log("target:", e.target.tagName); // Innermost touched element
    console.log("currentTarget:", e.currentTarget.tagName); // Listening node
  }
  return <article onClick={handleClick} data-id={id}>★ Story</article>;
}
```

When you click directly on the star icon, the console logs `target: SPAN` followed by `currentTarget: ARTICLE`. When you click on the headline text, the console logs `target: H3` followed by `currentTarget: ARTICLE`. While `target` changes depending on where the pointer lands, `currentTarget` always points to the listening container.

> [!PRINCIPLE]
> **Principle 3: Expect OnChange to Fire on Every Keystroke Rather Than on Blur**
> React normalizes input events so that the `onChange` prop reports every value change immediately rather than waiting for the field to lose focus:
>
> - **React's `onChange` (Per Keystroke):** fires on every character typed, pasted, or deleted, providing the current input value in `e.target.value`.
> - **Native DOM `change` (On Blur):** fires only after the user commits a change by unfocusing or tabbing away from the input field.
>
> Assuming `onChange` waits for the user to leave the field causes validation, filtering, or network searches to run on every single keystroke.
>
> >> onChange : a React event prop that fires immediately on every user keystroke or input value change
> >> onBlur : a React event prop that fires only when a form element loses keyboard focus

In the native browser DOM, the `change` event on an `<input>` element does not fire while the user is typing; it waits until the user presses Enter or clicks outside the field to commit the change. To capture keystrokes live, native DOM developers had to listen to the `input` event.

React unifies this behavior. On React `<input>`, `<textarea>`, and `<select>` elements, the `onChange` prop is wired to the browser's live input dispatch. Typing the letters "a" then "b" into a search box triggers `onChange` twice: first with `e.target.value` equal to `"a"`, and second with `e.target.value` equal to `"ab"`. Inspecting `e.nativeEvent.type` confirms that the underlying browser event is an `input` event. If an engineer designs an expensive search filter assuming `onChange` runs once after the user finishes typing, the search fires on every keystroke. To execute logic only after the user leaves the input, attach your handler to `onBlur` instead.

```jsx title="Typing with OnChange"
export default function SearchInput() {
  function handleType(e) {
    console.log("Typed text:", e.target.value); // Value on every keystroke
    console.log("Event type:", e.nativeEvent.type); // Native browser input
  }
  return (
    <input type="text" placeholder="Search..." onChange={handleType} />
  );
}
```

Typing "news" into this input produces four distinct console logs in immediate succession: "n", "ne", "new", and "news". In every log, `e.nativeEvent.type` reports `input`, proving that React's `onChange` tracks live text entry.

> [!PRINCIPLE]
> **Principle 4: Expect Events to Bubble Up Through Every Ancestor Handler**
> Browser events travel through the component tree, running handlers on nested elements before bubbling upward to their parent containers:
>
> - **Child Click Handler (`BookmarkButton`):** runs first at the element where the user initiated the click.
> - **Ancestor Click Handler (`ArticleCard`):** runs subsequently as the event bubbles up the DOM hierarchy toward the document root.
>
> Placing an action button inside a clickable card without stopping bubbling causes the card's navigation handler to execute right after the button's action fires.
>
> >> event bubbling : the upward propagation of an event from the innermost target through every ancestor handler
> >> capture phase : the downward travel of an event through capture handlers before reaching the target element

When a user clicks an element, the browser does not notify only that single element. Instead, the event begins at the document root, descends through ancestor elements during the capture phase, reaches the target, and then ascends back up through every ancestor during the bubble phase.

In React, JSX event props like `onClick` listen during the bubble phase. If you render a `<button>` inside an `<article onClick={openCard}>`, clicking the button runs the button's `onClick` handler first, and then immediately runs the `<article>`'s `onClick` handler. If the `<article>` is wrapped in a `<main onClick={trackSection}>`, the section handler runs third. All events in React bubble up the tree, with the single exception of `onScroll`, which fires only on the specific JSX tag being scrolled. If you ever need to intercept an event before child handlers run, you can attach a capture listener like `onClickCapture`, which executes on the downward descent.

```jsx title="Click Event Bubbling Order"
export default function ClickableCard() {
  const logCard = () => console.log("Card bubble"); // Ancestor runs second
  const logBtn = () => console.log("Button clicked"); // Target runs first
  return (
    <article onClick={logCard}>
      <button type="button" onClick={logBtn}>Read</button>
    </article>
  );
}
```

Clicking the "Read" button produces two sequential logs in exact order: first `Button clicked` at the target button, and then `Card bubble` as the event ascends upward into the parent article.

> [!PRINCIPLE]
> **Principle 5: Stop Event Propagation Where a Child Action Must Stay Local**
> When an action inside a container has its own independent purpose, stop the event from continuing up the component tree:
>
> - **`e.stopPropagation()` (Local Containment):** halts the event's upward journey immediately, preventing parent ancestor handlers from running.
> - **Explicit Callback Call (`onBookmark(id)`):** invokes a specific parent handler directly through props when the parent still needs to be notified.
>
> Failing to call `e.stopPropagation()` inside nested action buttons allows clicks to bubble up, triggering unintended container selections or unwanted page transitions.
>
> >> e.stopPropagation : a method on the event object that prevents ancestor handlers from receiving the event
> >> explicit callback invocation : directly calling a parent prop function inside a child handler rather than relying on automatic event bubbling

In complex user interfaces, nested controls often have completely different meanings from their surrounding containers. An article card may navigate to the full story when clicked, while a Bookmark button inside that card saves the story to local reading lists. Because clicks bubble up by default, clicking Bookmark opens the story unless propagation is explicitly halted.

Calling `e.stopPropagation()` on the React event object tells React to stop walking up the component tree. No ancestor click handlers will run for that event. However, what if the parent component still needs to know that a bookmark action occurred? The solution is not to let the click bubble up blindly; the professional pattern is to call `e.stopPropagation()` to stop raw DOM bubbling, and then explicitly invoke a callback prop passed down from the parent: `onBookmark(article.id)`. This pattern keeps event propagation contained while making the line of communication between child and parent explicit, readable, and easy to trace.

```jsx title="Stopping Event Propagation"
export default function ActionButtons({ onShare }) {
  const handleShare = (e) => {
    e.stopPropagation(); // Halts bubbling before reaching card
    onShare(); // Explicitly notifies parent
  };
  return (
    <button type="button" onClick={handleShare}>Share</button>
  );
}
```

By calling `e.stopPropagation()`, clicking the Share button prevents the surrounding card's handler from firing. At the same time, invoking `onShare()` passes the action cleanly upward through React's prop system.

> [!PRINCIPLE]
> **Principle 6: Prevent the Browser Default Action When React Handles the Event**
> Certain native HTML elements trigger built-in browser actions that must be intercepted when your JavaScript handles the interaction:
>
> - **`e.preventDefault()` (Browser Action Cancel):** cancels native browser behaviors, such as form submissions reloading the page or link clicks navigating to a URL.
> - **`e.stopPropagation()` (Ancestor Handler Cancel):** halts event bubbling to parent containers without affecting the browser's default action.
>
> Submitting a search form without calling `e.preventDefault()` causes the browser to reload the entire page, clearing all client memory and erasing what the user typed.
>
> >> e.preventDefault : a method on the event object that halts native browser actions like page reloads
> >> browser default action : native browser behavior triggered by an event, such as navigation or form submission

HTML elements were designed decades before single-page JavaScript applications existed. Built-in elements carry native behaviors: submitting a `<form>` issues a network request and reloads the page; clicking an `<a href="/story">` navigates to a new document; right-clicking opens a context menu. When building React applications, you want JavaScript to handle user interactions on the current page without the browser performing a full-page reload that destroys client memory.

Calling `e.preventDefault()` instructs the browser to suppress its built-in default behavior. A common mistake among junior developers is confusing `e.stopPropagation()` with `e.preventDefault()`. Calling `e.stopPropagation()` stops parent handlers from receiving the event, but it does nothing to prevent the browser from reloading the page. Conversely, calling `e.preventDefault()` prevents the page from reloading, but allows the event to continue bubbling up to ancestor components. Whenever React handles form submission or custom navigation, call `e.preventDefault()` at the start of your handler.

```jsx title="Preventing Default Form Submission"
export default function SearchBar() {
  function handleSubmit(e) {
    e.preventDefault(); // Prevents browser page reload
  }
  return (
    <form onSubmit={handleSubmit}>
      <button type="submit">Search</button>
    </form>
  );
}
```

Submitting this form executes `handleSubmit` safely without triggering a page reload. The browser URL stays unchanged, client state remains in memory, and the window never flashes white.

### Step 1: First, we declare the reading desk container <src/App.jsx>

In `src/App.jsx`, we assemble the overarching editorial environment that hosts both the search form and article cards. This root container orchestrates high-level application events: intercepting global form submissions, tracking live input text, and logging story selections.

Notice how `handleSearch` receives the React event object `e` and immediately invokes `e.preventDefault()`. This single line halts the browser's default form navigation. Without it, submitting the search query triggers a full-page GET reload that wipes all client state and clears the input field.

```jsx title="src/App.jsx" startLine="1" continues="bottom"
import ArticleCard from "./components/ArticleCard.jsx";

export default function App() {
  function handleSearch(e) {
    e.preventDefault(); // Halts browser page reload on submit
    console.log("Search query submitted");
  }
  function handleSelect(id) {
    console.log("Active story selected:", id);
  }
```

Next, we complete the container markup. Inside the return statement, we mount a `<form>` wired to `handleSearch`. On the search input, we attach an inline `onChange` handler that reads `e.target.value` on every keystroke. Because React normalizes `onChange` to the native input event, the search text updates synchronously with each typed character.

```jsx title="src/App.jsx" startLine="10" continues="top"
  return (
    <main className="desk">
      <form onSubmit={handleSearch}>
        <input onChange={(e) => console.log(e.target.value)} />
        <button type="submit">Search</button>
      </form>
      <ArticleCard id="101" title="Transit" onSelect={handleSelect} /> // Child
    </main>
  );
}
```

The parent passes `handleSelect` downward to `ArticleCard` as a callback prop. The container retains full authority over application data, while delegating the presentation and click handling to child components.

### Step 2: Next, we construct the clickable article card <src/components/ArticleCard.jsx>

In `src/components/ArticleCard.jsx`, we build an interactive card boundary that responds to reader clicks. When the reader clicks the card, `handleClick` executes and inspects both `e.target` and `e.currentTarget`.

This inspection demonstrates the critical difference between the listener and the trigger. If the reader clicks on the nested star icon or story headline, `e.target` references the specific child tag (`<span>` or `<h3>`). In contrast, `e.currentTarget` consistently references the outer `<article>` element holding the event listener.

```jsx title="src/components/ArticleCard.jsx" startLine="1" continues="bottom"
import ArticleActions from "./ArticleActions.jsx";

export default function ArticleCard({ id, title, onSelect }) {
  function handleClick(e) {
    console.log("Target tag:", e.target.tagName); // Innermost touched element
    console.log("CurrentTarget tag:", e.currentTarget.tagName);
    onSelect(id); // Opens story in parent desk
  }
```

Now we complete the card markup. We return an `<article>` tag wired with `onClick={handleClick}`. Inside the card, we render the story headline, a star badge, and mount the nested `ArticleActions` toolbar.

```jsx title="src/components/ArticleCard.jsx" startLine="9" continues="top"
  return (
    <article className="card" onClick={handleClick}> // Captures clicks
      <h3>{title}</h3>
      <span>★ Star Story</span>
      <ArticleActions articleId={id} />
    </article>
  );
}
```

Notice that because the card listens for clicks on the outer container, any click inside its boundaries will bubble up to `handleClick` unless a child explicitly stops propagation. This sets up the exact architectural challenge resolved in Step 3.

### Step 3: Finally, we build the action toolbar <src/components/ArticleActions.jsx>

In `src/components/ArticleActions.jsx`, we construct the nested Bookmark and Share buttons. These controls live inside the clickable article card, but represent completely separate user actions. Clicking Bookmark or Share must perform its dedicated task without opening the story reader.

To isolate these interactions, both `handleBookmark` and `handleShare` take the React event object `e` and immediately call `e.stopPropagation()`. This halts event bubbling on the spot, preventing the click event from ascending to the parent `<article>` tag.

```jsx title="src/components/ArticleActions.jsx" startLine="1" continues="bottom"
export default function ArticleActions({ articleId }) {
  function handleBookmark(e) {
    e.stopPropagation(); // Prevents click from bubbling to card
    console.log("Saved bookmark for:", articleId);
  }
  function handleShare(e) {
    e.stopPropagation(); // Halts bubbling to isolate share action
    console.log("Shared story link for:", articleId);
  }
```

Finally, we return the action buttons wrapped in a semantic container. Each action uses a native `<button type="button">` element, ensuring full keyboard accessibility and native focus outlines.

```jsx title="src/components/ArticleActions.jsx" startLine="10" continues="top"
  return (
    <div className="actions">
      <button type="button" onClick={handleBookmark}>Bookmark</button> // Local
      <button type="button" onClick={handleShare}>Share</button>
    </div>
  );
}
```

Because each button handler invokes `e.stopPropagation()`, clicking Bookmark or Share executes only the button's action. The parent card's `handleClick` remains completely silent. The card's selection logic fires strictly when the reader clicks the card body itself, establishing clean, predictable component boundaries.

### Where you will meet this

- Interactive feeds and cards where clicking the card navigates to an item, but clicking nested buttons (like Like, Save, or Share) must perform local actions without opening the card.
- Live search inputs and filtering toolbars where `onChange` captures text keystroke by keystroke to filter results instantly in client memory.
- Single-page application forms where `onSubmit` calls `e.preventDefault()` to submit data asynchronously via fetch without reloading the browser window.
- Analytics and logging systems where capture-phase listeners (`onClickCapture`) track user engagement across all child elements regardless of local propagation logic.

### Glossary

- **React Event Object**: A normalized cross-browser wrapper around native browser events that provides standard properties like target and currentTarget across all platforms.
- **Event Bubbling**: The natural upward propagation of a DOM event starting at the innermost clicked element and ascending through every ancestor component handler.
- **e.currentTarget**: The DOM element to which the currently executing event handler is attached in the React component tree.
- **e.target**: The deepest DOM element where the user interaction physically occurred, which may be a child of currentTarget.
- **e.stopPropagation**: A method on the React event object that halts upward event bubbling, preventing ancestor handlers from receiving the event.
- **e.preventDefault**: A method on the React event object that cancels native browser default actions, such as form submit reloads and link navigation.

**Architectural Takeaways & Decision Matrix**

❒ Side Effects and Render Purity

➔ ALWAYS place side effects like network requests, storage writes, and analytics logging inside event handlers, never in the component body.

➔ IF you need live text input updates THEN use React's `onChange` prop to read `e.target.value` on every keystroke.

❒ Event Target Resolution

➔ ALWAYS read `e.currentTarget` when you need attributes or datasets from the element holding the event handler.

➔ NEVER assume `e.target` is the container holding the handler, because users often click nested child icons or labels.

❒ Event Propagation & Browser Defaults

➔ ALWAYS call `e.stopPropagation()` inside nested action buttons when their click must not trigger parent card navigation.

➔ ALWAYS call `e.preventDefault()` on form submit handlers to prevent the browser from reloading the page and clearing client memory.

```jsx right title="Explicit Event Containment"
function ActionControl({ onSave }) {
  function handleClick(e) {
    e.stopPropagation();
    onSave();
  }
  return (
    <button type="button" onClick={handleClick}>
      Save
    </button>
  );
}
```

**DO NOT DO THIS:** allow clicks to bubble into parent container handlers

```jsx wrong title="Unstopped Bubble Cascade"
function ActionControl({ onSave }) {
  return (
    <button type="button" onClick={onSave}>
      Save
    </button>
  );
}
```

| | **EVENT BUBBLING**<br>(propagation) | **DEFAULT ACTIONS**<br>(browser navigation) |
| ---: | :--- | :--- |
| **Trigger Mechanism** | Event travels upward through parent component hierarchy | Browser executes built-in behaviors like form page reloads |
| **Cancellation Method** | Call `e.stopPropagation()` on the React event object | Call `e.preventDefault()` on the React event object |
| **Failure Consequence** | Parent container handlers execute unexpectedly | Whole page reloads and clears client memory |
| **Primary Target** | Nested action buttons inside clickable cards | Form submission and navigation links |
| **Component Benefit** | Keeps child interactions strictly local | Preserves single-page state and form text |
