### The form field keeps its own text, but React state stays out of sync

Today we learn how React form fields bind directly to component memory, why native HTML habits cause fields to freeze or refuse to clear, and how to control text inputs, textareas, selects, and checkboxes cleanly with state.

In modern frontend web applications, user interfaces collect information through interactive forms. Users type search queries, submit feedback comments, choose options from dropdown menus, and toggle confirmation checkboxes. In plain HTML, form fields own their internal text, and scripts inspect the DOM only after submission. In React, this imperative model causes state and the screen to drift out of sync. When an application needs to clear fields after submission, validate text length on the fly, or populate defaults dynamically, the component must become the single source of truth. By binding the field's displayed value to a React state variable through `value` and updating that state synchronously on every keystroke through `onChange`, the form control becomes fully controlled. State drives what appears on screen, and clearing state immediately flushes the field.

When engineers transition from vanilla HTML scripting to React, they naturally carry over habits from native form elements. In HTML, a developer writes `<textarea>Starting text</textarea>` or `<input value="Default">`, expecting the browser to manage user keystrokes independently while JavaScript reads the field value on submit. In React, passing `defaultValue` sets the initial text once at mount, after which the DOM node retains its own independent memory. When an event handler later updates a state variable with `setText('')`, a `defaultValue` field completely ignores the new state, leaving stale text on screen while counters reset to zero. Conversely, developers who hear that React needs `value={text}` often supply `value` without an `onChange` handler, inadvertently locking the field so it refuses every keystroke while the console logs a read-only warning. Furthermore, checkboxes require `checked` rather than `value`, dropdowns require `value` on the `<select>` rather than `selected` on an `<option>`, and text state must never start as `undefined`.

This chapter investigates six core questions. **Why does calling a state setter fail to clear an input that uses defaultValue?** **Why does assigning value without an onChange handler freeze the field completely?** **Why must the onChange handler store exactly what was typed synchronously, rather than modifying or delaying the text?** **Why does a checkbox require the checked prop and e.target.checked rather than value and e.target.value?** **Where must the value prop be declared when controlling a select dropdown or textarea?** **Why does initializing a state variable with useState() trigger an uncontrolled-to-controlled warning on the first keystroke?**

### Controlled versus uncontrolled form inputs

In Lecture 13, we learned how event handlers capture user interactions, and in Lecture 14, we learned how `useState` provides a setter that schedules a future render. In Lecture 18, we saw a preview of form inputs where `value` and `onChange` were wired to state properties. Today we unpack the exact mechanics of that binding.

In React, form elements operate in one of two distinct modes: uncontrolled or controlled. An uncontrolled field uses `defaultValue="initial"` (or `defaultChecked` for checkboxes). React populates the DOM element once when it mounts, after which the browser's internal DOM node manages all subsequent typing and state. If your component updates a state variable later, the uncontrolled DOM node ignores it. In contrast, a controlled field explicitly binds its displayed text to React state via `value={text}`. On every keystroke, React's synthetic `onChange` event fires immediately, behaving like the native browser `input` event rather than the native `change` event, which only fires after the user leaves the field. The handler calls `setText(e.target.value)`, React re-renders the component, and the commit phase writes the new state value back into the DOM element. Because React drives the field on every render, state is the single source of truth. Clearing state programmatically with `setText('')` immediately flushes the visible text from the screen.

```jsx title="Uncontrolled Versus Controlled Form Fields"
// Uncontrolled: browser keeps text; setting state does not clear it
<textarea defaultValue="Initial note" /> {/* Uncontrolled field */}

// Controlled: React state drives field; setting state flushes DOM
<textarea
  value={text} // State is single source of truth
  onChange={e => setText(e.target.value)} // Synchronous state write
/>
```

The difference between uncontrolled and controlled form fields centers on three core concepts:
1. `uncontrolled input`: a form element whose value is managed internally by the browser DOM node.
2. `defaultValue`: a prop that sets the initial field value once at mount without controlling subsequent renders.
3. `controlled input`: an input driven by React state via `value` and updated on every keystroke via `onChange`.
4. `single source of truth`: an architectural invariant where component state dictates exactly what appears on screen.

### Synchronous input updates and the text caret

In Lecture 16, we saw that calling a state setter queues a render rather than mutating variables in place, and that `setTimeout` defers execution until the browser's event loop clears. When managing text inputs, timing and value fidelity become critical to cursor stability.

When a user types into a text input, the browser places the new character at the active cursor position and advances the text caret immediately. In a controlled field, React must synchronize this DOM mutation with component state. If your `onChange` handler stores an altered string, such as calling `e.target.value.toUpperCase()`, the text that React renders back into the DOM differs from what the browser natively inserted. When React overwrites the element's `value` with a modified string, the browser loses track of the user's cursor position and jumps the caret to the very end of the input. If the user was editing text in the middle of a word, their next keystroke lands erroneously at the end of the line. Similarly, if a developer attempts to defer `setText` inside a `setTimeout`, React writes the old state back to the DOM before the timer fires, causing fast typing to scramble characters. To preserve seamless caret navigation, `onChange` must update state synchronously with the exact, unmodified string from `e.target.value`. Formatting should occur during render display or upon final submission.

```jsx title="Synchronous Event Handling and Caret Stability"
// Correct: stores raw typed text synchronously; cursor position stays stable
function handleTitleChange(e) {
  setTitle(e.target.value); // Caret remains at current edit position
}

// Broken: uppercasing during typing forces the caret to jump to the end
function handleBrokenTitleChange(e) {
  setTitle(e.target.value.toUpperCase()); // Caret jumps to end on keystroke
}
```

Managing the text caret during controlled typing introduces three essential concepts:
1. `text caret`: the blinking cursor indicating where typed characters appear in an editable field.
2. `synchronous state update`: calling the state setter immediately inside the event handler without delay.
3. `caret jump`: cursor displacement to the end of a field caused by overwriting DOM text with an altered string.

### Checkbox boolean bindings and select value props

In Lecture 4, we learned that JSX expressions evaluate JavaScript variables directly, and in Lecture 6, we learned that passing `undefined` causes React to fall back to default behavior. When dealing with form elements, `undefined` carries a specific structural consequence.

Different HTML form elements require specialized prop pairings. A checkbox does not track state through `value`; in native HTML, an input checkbox has a default `value="on"`. If you write `onChange={e => setAgreed(e.target.value)}`, `e.target.value` evaluates to the string `"on"` regardless of whether the box was ticked or unticked. Because `"on"` is a non-empty string, JavaScript evaluates it as truthy. Passing `e.target.value` to `setAgreed` stores `"on"` on the first click and stores `"on"` again on the second click. The checkbox remains checked permanently. Checkboxes and radio buttons must pair the `checked` boolean prop with `e.target.checked`. Similarly, dropdown menus in React do not set `selected` on individual `<option>` elements. Setting `<option selected>` logs a console error; instead, React declares `value={selectedOption}` directly on the parent `<select>` element. Finally, text inputs must never initialize with `useState()` or `undefined`. When an input receives `value={undefined}`, React treats it as an uncontrolled field. When the user types their first letter and state becomes a string, React suddenly switches the input to controlled, logging an error: "A component is changing an uncontrolled input to be controlled." Always initialize text fields with an empty string `useState('')` or provide a fallback `value={text ?? ''}`.

```jsx title="Form Field Bindings and String Initialization"
// Checkbox: binds checked and reads boolean e.target.checked
<input type="checkbox" checked={on} onChange={e => setOn(e.target.checked)} />

// Select: declares value on select element
<select value={topic} onChange={e => setTopic(e.target.value)}>
  <option value="billing">Billing</option>
</select>

const [title, setTitle] = useState(''); // Starts with empty string
```

Form element specialization requires understanding four foundational concepts:
1. `checked`: a boolean prop governing the visual checkmark state of checkboxes and radio buttons.
2. `e.target.checked`: the boolean property reporting whether an input element is currently ticked.
3. `select value`: the container prop on `<select>` matching the active option's value.
4. `uncontrolled-to-controlled warning`: a console error triggered when an input switches from `undefined` to a string.

### Principles of React: Controlled Inputs

### Question 1: Calling a state setter fails to clear a textarea with defaultValue

A developer builds a feedback submission component called `FeedbackForm`. To collect suggestions, the developer declares a textarea initialized with `defaultValue=""` and updates a local state variable `text` on each keystroke to display a live character counter:

```jsx title="FeedbackForm.jsx, defaultValue attempt" startLine="12"
  function handleClear() {
    setText(''); // Re-renders character counter to 0/280
  }
  return (
    <form onSubmit={handleClear}>
      <textarea defaultValue="" onChange={e => setText(e.target.value)} />
      <span>{text.length}/280 characters</span>
    </form>
  );
```

The user types "Fix the date" into the box. The counter displays "12/280 characters". When the user clicks the submit button, `handleClear` runs, calling `setText('')`. The character counter updates to "0/280 characters", but the textarea on screen continues displaying "Fix the date".

**After Send, I call setText(''). The counter says 0/280, but the old text stays in the box. Why?**

---

**ANSWER**

**The code does not do what we wanted.** A field with `defaultValue` sets its text only once at mount, after which the browser DOM manages its text independently of React state.

When you pass `defaultValue=""` to a form element, React instructs the browser to populate the initial DOM node with that value when the element mounts. After mount, the DOM node maintains its own internal text memory. Each keystroke triggers `onChange`, which calls `setText(e.target.value)`. That state setter writes the string into React state, allowing the counter to read `text.length` during rendering.

When the submit handler calls `setText('')`, React schedules a re-render. During the render pass, the counter evaluates `text.length` as zero, so the screen renders "0/280 characters". However, because the textarea uses `defaultValue`, nothing instructs React to synchronize the DOM element with the new state value. React compares the JSX element, notices `defaultValue` is an initial-mount instruction, and leaves the existing DOM node completely untouched.

```ascii title="Uncontrolled DefaultValue Versus Controlled Value"
[setText('')] -> React schedules render
      |
      v
Counter renders 0/280 from state
      |
      v
Textarea uses defaultValue="" (mount only)
      |
      v
[DOM node untouched] -> Screen keeps showing "Fix the date"
```

To make state drive the textarea after every render, you must replace `defaultValue` with `value={text}`. When `value` is present, React's commit phase writes the state string back into the DOM element on every render, ensuring that calling `setText('')` empties the box immediately.

> [!PRINCIPLE]
> **Principle 1: A controlled field shows what is in state, after every render**
> A field with `defaultValue` sets its initial text once at mount; after that, the browser keeps the field's own text, so setting state does not change it. A controlled field takes its displayed text directly from React state through `value`. Each keystroke calls `onChange`, the handler writes the new text into state, and React writes state back into the field after every render. Because state is the single source of truth, whatever is in state is what the field shows, and clearing state clears the field.
>
> >> defaultValue : sets only the initial text when the field mounts; the browser keeps subsequent edits
>
> *We should do this:*
> ```jsx right
> // value drives the textarea from state; setText('') empties it
> <textarea value={text} onChange={e => setText(e.target.value)} />
> ```
>
> *We should not do this:*
> ```jsx wrong
> // defaultValue leaves field uncontrolled; setText('') does not clear it
> <textarea defaultValue="" onChange={e => setText(e.target.value)} />
> ```

### Question 2: Assigning value without an onChange handler freezes the input

Having learned that `value` binds the textarea to state, the developer changes the input to `value={text}`, but removes the `onChange` handler, assuming that the browser will let the user type naturally while React reads the value on submit:

```jsx title="FeedbackForm.jsx, missing onChange" startLine="10"
  const [text, setText] = useState('');
  return (
    <form>
      <textarea value={text} /> {/* Missing onChange handler */}
    </form>
  );
```

The user clicks into the textarea and attempts to type "Hello". No letters appear in the box, the field appears completely frozen, and the browser console logs an error warning that a `value` prop without `onChange` renders a read-only field.

**I wrote value={text} and the box no longer takes any typing. What broke?**

---

**ANSWER**

**The code does not do what we wanted.** Supplying a `value` prop makes an input controlled, so without an `onChange` handler to update state, React overwrites every keystroke with the existing state string.

In React, passing a string to the `value` prop transforms the input into a controlled component. When the user presses a key on their keyboard, the browser's native engine inserts the typed character into the DOM node for a fraction of a millisecond.

However, because there is no `onChange` handler to capture the event and call `setText`, component state remains fixed at its initial value (`''`). React immediately reconciles the DOM element against the JSX `value={text}`, notices that the DOM node contains a character while state specifies `''`, and writes `''` back into the DOM element. The typed character vanishes instantly before the user can see it.

```ascii title="Read-Only Reversion on Missing OnChange"
User presses key -> Browser DOM receives character
      |
      v
No onChange handler -> Component state remains ''
      |
      v
React reconciles: state ('') !== DOM (char)
      |
      v
[React writes '' back to DOM] -> Character disappears instantly
```

React detects this contradiction and prints an explicit diagnostic error: "You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`." To keep the field editable, you must supply an `onChange` handler that writes `e.target.value` into state.

> [!PRINCIPLE]
> **Principle 2: Pair every value with an onChange that sets state**
> Passing a string `value` makes a form field controlled. Each keystroke changes the field for a moment, but with no `onChange` handler, nothing stores the new text into state. React writes the existing state value back into the field on render, causing the keystroke to disappear while logging an error advising to set `readOnly`. If a field should accept user edits, pair its `value` with an `onChange` handler that updates state.
>
> >> readOnly : marks a field as intentionally immutable without an onChange handler
>
> *We should do this:*
> ```jsx right
> // onChange updates state on each keystroke, keeping the field editable
> <input value={name} onChange={e => setName(e.target.value)} />
> ```
>
> *We should not do this:*
> ```jsx wrong
> // value without onChange freezes the field and logs a console error
> <input value={name} />
> ```

### Question 3: Modifying text inside onChange causes the cursor caret to jump

The developer wants headline titles to always appear in uppercase letters. Rather than applying a styling rule, the developer uppercases the text directly inside the `onChange` event handler:

```jsx title="FeedbackForm.jsx, uppercase in onChange" startLine="14"
  function handleTitleChange(e) {
    setTitle(e.target.value.toUpperCase()); // Stores uppercased text
  }
  return <input value={title} onChange={handleTitleChange} />;
```

The user types "fix the date". Then the user clicks between "fix " and "the" to insert "xy". As soon as the user presses "x", the cursor unexpectedly jumps to the end of the input, and pressing "y" lands at the end of the string, producing "FIX XTHE DATEY".

**Headlines are all caps. Can my onChange store e.target.value.toUpperCase()?**

---

**ANSWER**

**The code does not do what we wanted.** Overwriting an input with a modified string causes the browser to lose the user's cursor position, jumping the text caret to the end of the field.

When a user types a letter into an input field, the browser native engine inserts the character at the active cursor position and advances the caret one space forward. When `handleTitleChange` executes, it receives `e.target.value` (for example, `"fix xthe date"`). The handler calls `toUpperCase()`, storing `"FIX XTHE DATE"` in React state.

When React re-renders the component and commits the changes, it writes `"FIX XTHE DATE"` into the input's `value` property. Because this string does not match what the browser natively placed in the input (lowercase "x" replaced by uppercase "X"), the browser cannot preserve the cursor position within the modified text. The browser defaults to placing the caret at the very end of the input string. When the user types the next character ("y"), that character is inserted at the end of the line.

```ascii title="Caret Jump Displacement on Modified String"
User types 'x' in middle: "fix xthe date"
      |
      v
onChange stores uppercased: "FIX XTHE DATE"
      |
      v
React writes modified string -> Browser caret jumps to end
      |
      v
Next letter 'y' typed at end -> "FIX XTHE DATEY"
```

A similar bug occurs if you wrap state updates in `setTimeout`. React writes the old state back to the DOM before the timer fires, causing fast typing to drop or scramble characters. You must store `e.target.value` synchronously and without transformation. If you want uppercase presentation, use CSS `text-transform: uppercase`, or transform the string upon form submission.

> [!PRINCIPLE]
> **Principle 3: Store exactly what was typed, right away**
> When a user types, the browser advances the cursor to the next character position. If `onChange` stores a transformed string or defers state inside a timer, React writes a value back to the DOM that differs from what the browser received. Overwriting the input resets the cursor position, sending the text caret to the end of the field and scrambling subsequent keystrokes. Always store `e.target.value` synchronously and unmodified; format text during display or upon submission.
>
> >> caret : the blinking cursor that indicates where the next typed letter lands
>
> *We should do this:*
> ```jsx right
> // store raw typed string synchronously; format when displaying or saving
> onChange={e => setName(e.target.value)}
> ```
>
> *We should not do this:*
> ```jsx wrong
> // transforming or delaying the typed value moves the caret to the end
> onChange={e => setName(e.target.value.toUpperCase())}
> ```

### Question 4: Reading e.target.value on a checkbox permanently locks it to checked

The developer adds an "urgent" checkbox to flag priority feedback. State variable `isUrgent` starts as `false`. The developer binds `checked` to `isUrgent` but reads `e.target.value` in `onChange`:

```jsx title="FeedbackForm.jsx, checkbox reading value" startLine="20"
  return (
    <label>
      <input
        type="checkbox"
        checked={isUrgent}
        onChange={e => setIsUrgent(e.target.value)} // Reads string value
      />
      Mark as urgent ({String(isUrgent)})
    </label>
  );
```

The user clicks the checkbox once. The checkbox becomes ticked, and the label displays "Mark as urgent (on)". The user clicks the checkbox a second time to uncheck it, but the checkbox remains stubbornly ticked and the label still displays "Mark as urgent (on)".

**For the urgent checkbox, do I write value and e.target.value, like the text fields?**

---

**ANSWER**

**The code does not do what we wanted.** A checkbox does not report boolean status through `value`; `e.target.value` returns the string `"on"`, which is truthy, so the checkbox can never be unchecked.

In native HTML, a checkbox's `value` attribute specifies the data value submitted with the form when the checkbox is checked. If no `value` attribute is explicitly assigned, the browser assigns it a default value of `"on"`. Crucially, clicking a checkbox does not change its `value` property; `e.target.value` returns `"on"` on every single click, whether the user is checking or unchecking the box.

Because `"on"` is a non-empty string, JavaScript evaluates it as truthy. When the user clicks the checkbox the first time, `setIsUrgent("on")` stores `"on"` in state, rendering `checked={true}`. When the user clicks the checkbox a second time, `e.target.value` is still `"on"`. React receives `"on"`, evaluates it as truthy, and renders `checked={true}` again. The checkbox becomes permanently locked in the checked state.

```ascii title="Checkbox Target Value Versus Target Checked"
[First Click: Tick Box]
e.target.value === "on"      ---> setIsUrgent("on")     ---> checked={true}
      |
      v
[Second Click: Untick Box]
e.target.value === "on"      ---> setIsUrgent("on")     ---> checked={true}
      |
      v
e.target.checked === false   ---> setIsUrgent(false)    ---> checked={false}
```

To control a checkbox or a radio button, you must bind the `checked` boolean prop and read the boolean property `e.target.checked`. The property `e.target.checked` accurately returns `true` when the box is checked and `false` when it is unticked.

> [!PRINCIPLE]
> **Principle 4: A checkbox uses checked, and its handler reads e.target.checked**
> A checkbox displays its visual state through the boolean `checked` prop. In HTML, a checkbox's `value` attribute defaults to the string `"on"`, so reading `e.target.value` yields `"on"` on every click. Because non-empty strings are truthy, storing `e.target.value` permanently locks the checkbox to checked. Always bind `checked` to state and read `e.target.checked`, which provides a clean boolean `true` or `false` on every toggle.
>
> >> e.target.checked : the boolean property indicating whether a checkbox is ticked
>
> *We should do this:*
> ```jsx right
> // checked prop with e.target.checked stores true or false accurately
> <input
>   type="checkbox"
>   checked={agree}
>   onChange={e => setAgree(e.target.checked)}
> />
> ```
>
> *We should not do this:*
> ```jsx wrong
> // e.target.value returns "on" every time, so the box never unchecks
> <input
>   type="checkbox"
>   checked={agree}
>   onChange={e => setAgree(e.target.value)}
> />
> ```

### Question 5: Setting selected on an option triggers a console warning

The developer adds a category selection dropdown. Relying on standard HTML syntax, the developer marks the default option with the boolean `selected` attribute:

```jsx title="FeedbackForm.jsx, option selected" startLine="22"
  const [category, setCategory] = useState('support');
  return (
    <select onChange={e => setCategory(e.target.value)}>
      <option value="general">General</option>
      <option value="support" selected>Support</option> {/* HTML habit */}
    </select>
  );
```

When the page loads, the browser console prints an error warning: "Use the `defaultValue` or `value` props on <select> instead of setting `selected` on <option>." Furthermore, when the user clicks a reset button that calls `setCategory('general')`, the dropdown fails to switch to "General Feedback".

**In HTML I mark the default section with selected on its <option>. Do I do the same here?**

---

**ANSWER**

**The code does not do what we wanted.** React does not support `selected` on an `<option>`; dropdown values must be controlled via `value` on the parent `<select>` element.

In native HTML, setting `<option selected>` indicates which item should be initially chosen in a dropdown menu. In React's declarative architecture, form state belongs on the container element that manages user selection, rather than scattered across child option tags.

When React encounters `selected` on an `<option>`, it rejects the attribute and prints a console error. Because the `<select>` tag itself has no `value` prop, React treats the dropdown as an uncontrolled element. When an event handler calls `setCategory('general')`, React updates component state, but the `<select>` DOM element ignores the update and remains stuck on whatever option the user previously picked.

```ascii title="Option Selected Versus Select Value Container"
<option selected>           ---> Rejected by React; logs console error
      |
      v
<select> lacks value prop   ---> Dropdown is uncontrolled; ignores state updates
      |
      v
<select value={category}>   ---> React selects matching option automatically
```

To control a dropdown menu in React, declare `value={category}` directly on the `<select>` element, along with an `onChange` handler that updates state with `e.target.value`. React inspects the child options and automatically highlights whichever `<option>` has a `value` matching the state variable. Similarly, a `<textarea>` must not place text between opening and closing tags; its content belongs in `value`.

> [!PRINCIPLE]
> **Principle 5: Put value on the field itself, not on an option or between tags**
> In React, dropdown selection is controlled on the container `<select>` element, not on individual `<option>` tags. Setting `selected` on an `<option>` logs a console error and breaks state control. Declare `value={choice}` on the `<select>` tag, and React automatically selects the matching option. Similarly, write a `<textarea>` as a self-closing tag with `value`, never placing child text between `<textarea>` tags.
>
> >> select value : selects the matching option declaratively from state
>
> *We should do this:*
> ```jsx right
> // select value matches the active option value without touching options
> <select value={choice} onChange={e => setChoice(e.target.value)}>
>   <option value="one">First Option</option>
>   <option value="two">Second Option</option>
> </select>
> ```
>
> *We should not do this:*
> ```jsx wrong
> // selected on an option logs a console error and breaks state control
> <select onChange={e => setChoice(e.target.value)}>
>   <option value="one">First Option</option>
>   <option value="two" selected>Second Option</option>
> </select>
> ```

### Question 6: Starting state with useState() triggers an uncontrolled-to-controlled warning

The developer prepares the form to receive an initial title asynchronously from a remote server. Because the title is not available immediately when the component mounts, the developer initializes state without an argument:

```jsx title="FeedbackForm.jsx, undefined initial state" startLine="8"
  const [title, setTitle] = useState(); // Initializes state to undefined
  return (
    <input
      value={title}
      onChange={e => setTitle(e.target.value)}
    />
  );
```

When the form first renders, the input appears empty. When the user clicks into the field and types the letter "F", the console logs an error warning: "A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen."

**The headline will come from the server later, so I wrote useState(). Is that fine?**

---

**ANSWER**

**The code does not do what we wanted.** Initializing state with `useState()` sets the variable to `undefined`, causing the input to mount uncontrolled before switching to controlled on the first keystroke.

In JavaScript, declaring `useState()` without an initial value sets the state variable to `undefined`. When React evaluates `<input value={title} />` during initial mount, `value={undefined}` tells React that no controlled value is being supplied. React concludes that this input is uncontrolled, and lets the browser manage the field.

When the user types the first character, `onChange` fires and calls `setTitle("F")`. On the next render, `title` is now a string. When React reconciles the element, it finds that an input that mounted as uncontrolled now has a defined string `value`. In React's architecture, an input element must remain either strictly controlled or strictly uncontrolled throughout its entire lifecycle.

```ascii title="Lifecycle Shift from Uncontrolled to Controlled"
useState() initializes title = undefined
      |
      v
Initial render: <input value={undefined} /> mounts UNCONTROLLED
      |
      v
User types 'F' -> setTitle("F") schedules render
      |
      v
Next render: <input value="F" /> switches to CONTROLLED (LOGS ERROR)
```

Switching control mode mid-lifecycle can cause subtle rendering bugs where browser DOM state conflicts with React state. Always initialize text input state with an empty string: `useState('')`. If the value might arrive asynchronously as `null` or `undefined`, provide a safe fallback using nullish coalescing: `value={title ?? ''}`.

> [!PRINCIPLE]
> **Principle 6: Start every value as a string**
> Passing `value={undefined}` makes React mount the element as an uncontrolled input. When the user types the first letter, state updates to a string, causing the input to switch suddenly from uncontrolled to controlled. React logs a console error because an input must maintain a stable control mode throughout its lifecycle. Always initialize text state with an empty string `useState('')`, or provide a nullish coalescing fallback with `value={text ?? ''}`.
>
> >> nullish coalescing : ?? falls back to empty string when state is null or undefined
>
> *We should do this:*
> ```jsx right
> // initialize with empty string so the field stays controlled from mount
> const [title, setTitle] = useState('');
> // or provide a fallback: value={title ?? ''}
> ```
>
> *We should not do this:*
> ```jsx wrong
> // undefined makes field uncontrolled; subsequent typing triggers warning
> const [title, setTitle] = useState();
> ```

### Where you will meet this

In production frontend applications, controlled form inputs are universal across user authentication screens, search filters, checkout forms, and profile editors. A frequent production bug occurs when an engineer implements a "Clear Form" button that resets component state, only to discover that uncontrolled fields retaining `defaultValue` stubbornly hold user text on screen. Adopting `value` paired with `onChange` guarantees programmatic synchronization.

Another common production bug occurs when teams connect forms to asynchronous APIs where initial user data loads after the component mounts. Initializing state with `useState()` leaves the field `undefined`, triggering uncontrolled-to-controlled console warnings that degrade test suites and user experience. Initializing with `useState('')` or using `value={data?.title ?? ''}` eliminates this issue permanently.

In technical interviews, candidates are routinely asked how controlled components work under the hood. Interviewers specifically probe whether candidates understand why React's `onChange` fires on every single keystroke rather than on blur, why checkboxes require `e.target.checked` instead of `e.target.value`, and how transforming strings inside `onChange` disrupts the browser text caret.

### For the interview

> **The Interview Question:** How do you make an input, textarea, or select fully controlled by React state?

A senior response breaks the explanation into four architectural beats:

**1. The Single Source of Truth**

In React, a controlled component derives its displayed value entirely from state via props: `value` for text inputs, textareas, and selects, or `checked` for checkboxes and radio buttons. The component pairs this prop with an `onChange` handler that captures user interaction and writes the new value into state. State becomes the single source of truth: whatever exists in state is what the DOM renders, and setting state to an empty string programmatically flushes the field.

**2. Synchronous Keystroke Updates**

React synthetic `onChange` events fire on every single keystroke, behaving like the native browser `input` event rather than the native `change` event, which waits until blur. The `onChange` handler must store `e.target.value` synchronously and without transformation. If a handler attempts to uppercase text or delay updates inside `setTimeout`, React writes a modified string back to the DOM, causing the browser to lose cursor tracking and jump the text caret to the end of the line.

**3. Element Specialization: Checkboxes and Selects**

Different HTML form elements require specialized property bindings. A checkbox displays its visual state via `checked={boolean}` and reports changes through `e.target.checked`; reading `e.target.value` yields the static string `"on"`, which is truthy and locks the checkbox permanently. Dropdown menus declare `value={choice}` directly on the parent `<select>` container rather than setting `selected` on an `<option>`, allowing React to match the active option declaratively.

**4. Initial Value Guarantees**

A controlled text input must maintain a stable control mode throughout its entire lifecycle. Initializing state with `useState()` sets the variable to `undefined`, mounting the input as uncontrolled. When the user types their first character, state becomes a string, triggering an uncontrolled-to-controlled console warning. Always initialize text inputs with an empty string `useState('')` or provide a nullish fallback `value={text ?? ''}`.

### Glossary

- **Controlled Input**: A form element whose displayed value is driven by React state and whose changes update that state.
- **Uncontrolled Input**: A form element whose value is managed internally by the browser DOM node.
- **Single Source of Truth**: The architectural model where one state variable determines what appears on screen.
- **Synthetic `onChange`**: React's cross-browser event firing synchronously on every keystroke like native `input`.
- **Text Caret**: The blinking cursor that indicates where the next typed letter lands in an editable field.
- **`defaultValue`**: A React prop that sets the initial text once at mount without controlling subsequent renders.
- **`e.target.checked`**: The boolean property on a synthetic event reporting whether a checkbox is ticked.

### Summary

**Architectural Takeaways & Decision Matrix**

➔ ALWAYS pair every `value` prop with an `onChange` handler that updates state synchronously.

➔ ALWAYS initialize text input state with an empty string `useState('')` to prevent uncontrolled warnings.

➔ IF controlling a checkbox or radio button THEN bind `checked` to boolean state and read `e.target.checked`.

➔ IF controlling a dropdown selection THEN declare `value` directly on `<select>` rather than `selected` on `<option>`.

➔ NEVER transform text inside `onChange` or defer updates in timers; format during display or upon submission.

**DO THIS:**

```jsx right
function handleTitleChange(e) {
  setTitle(e.target.value);
}
return (
  <form onSubmit={handleSubmit}>
    <input value={title} onChange={handleTitleChange} />
    <select value={topic} onChange={e => setTopic(e.target.value)}>
      <option value="billing">Billing</option>
    </select>
    <input
      type="checkbox"
      checked={isUrgent}
      onChange={e => setIsUrgent(e.target.checked)}
    />
  </form>
);
```

**DO NOT DO THIS:**

```jsx wrong
function handleTitleChange(e) {
  setTitle(e.target.value.toUpperCase());
}
return (
  <form onSubmit={handleSubmit}>
    <input value={title} />
    <select onChange={e => setTopic(e.target.value)}>
      <option value="billing" selected>Billing</option>
    </select>
    <input
      type="checkbox"
      checked={isUrgent}
      onChange={e => setIsUrgent(e.target.value)}
    />
  </form>
);
```

| ---: | :--- | :--- |
| **State authority** | Browser DOM node retains text internally | React state variable is single source of truth |
| **Initial mounting** | Sets starting text with `defaultValue` | Binds active state to `value` prop |
