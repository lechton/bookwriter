### Props let one component show different content

Every web application displays repeated visual structures: news feeds, product listings, and user comments. In earlier lessons, our components returned fixed markup or read local variables declared inside their own function bodies. When multiple cards share the same frame but display different data, every developer meets the same question: how does each component display its own unique content?

A component that writes its text inside its own function body is a **hardcoded component**:

```jsx title="Hardcoded component: fixed text inside component body"
function ArticleCard() {
  return (
    <article className="card">
      <h2>Transit Accord Reached</h2> {/* fixed headline in component body */}
      <p>5 min read</p>
    </article>
  );
}
```

All values sit hardcoded inside the function body: the card always displays "Transit Accord Reached" and "5 min read". If the feed renders `<ArticleCard />` three times, every card displays identical copy; to show three different stories, a developer must duplicate the function three times. That is why it is called a hardcoded component: the data is fixed directly in code.

React's answer is **props**: the parent passes attributes on the component tag, and React hands them to the child as an input object.

```jsx title="Props: dynamic attributes configured by parent"
function EditorialFeed() {
  return (
    <main className="feed">
      <ArticleCard title="Rail Strike Ends" readTime={3} /> {/* first card */}
      <ArticleCard title="Clean Energy Project" readTime={5} /> {/* card two */}
    </main>
  );
}
```

The parent component writes attributes on each `<ArticleCard />` tag: `title="Rail Strike Ends"` and `readTime={3}`. React collects those attributes into a single object and passes it to `ArticleCard` as its argument. Inside `ArticleCard`, the component unpacks `{ title, readTime }` and renders those values. One single component layout now renders hundreds of distinct stories. That is why they are called props: properties passed from parent to child.

```jsx title="Props: unpacking inputs in the parameter list"
function ArticleCard({ title, readTime }) {
  return (
    <article className="card">
      <h2>{title}</h2> {/* renders title prop */}
      <p>{readTime} min read</p> {/* renders readTime prop */}
    </article>
  );
}
```

The child component function shows the other side of the contract: placing `{ title, readTime }` in the parameter list unpacks the incoming properties directly into local variables.

Later, we will see that nested markup passed between a component's opening and closing tags arrives as a special prop named `children` (Lecture 7).

In this chapter, we learn how props work on our `ArticleCard` component: how tag attributes compile into a single props object, why we unpack properties in the parameter list with curly braces, why numbers must be passed in curly braces, how default parameter values handle missing data, and why props are strictly read-only. At the end, we compare hardcoded components against props.

In this lesson, props are passed down from a parent with static values. ### What props are and how React passes them as a single object

In standard JavaScript, functions accept arguments so that a single calculation can run on different inputs. For example, a function `double(x)` returns `x * 2` for any number you provide. React components are JavaScript functions that return user interface markup. If a component could only return hardcoded text, you would need a new component function for every distinct item in your application. React solves this through **props**, which is short for properties. Props allow a parent component to pass custom data down to child components, letting one single component layout render hundreds of different stories or products.

When you render a custom component tag in JSX, any attributes you write become properties on a single JavaScript object. For instance, writing `<ArticleCard title="Rail Strike Ends" readTime={3} />` tells React to create an object: `{ title: "Rail Strike Ends", readTime: 3 }`. React passes this object as the first and only argument to your `ArticleCard` component function. In React terminology, the location where you render the tag is called the **call site**, the attributes are called **props**, and the component receiving the data is the **child component**. The attributes on the tag do not reach the browser DOM directly; React hands them exclusively to the component function.

When working with props, modern JavaScript provides a concise syntax called **object destructuring**. Instead of writing `function ArticleCard(props)` and repeating `props.title` and `props.readTime` throughout your markup, you can write `function ArticleCard({ title, readTime })`. In JavaScript, placing curly braces `{ }` inside the parameter list tells the runtime to automatically unpack specific keys from the incoming object into local variables. This syntax is standard ECMAScript, but it is the universal convention in React because it makes a component's required inputs immediately visible at the top of the function. If a destructured parameter name does not match any attribute on the tag (such as writing `{ headline }` when the tag passed `title=`), the local variable receives `undefined`.

Under the hood, the JSX compiler converts every component tag into a function call. As we learned in Lecture 4, writing `<ArticleCard title="Rail Strike Ends" readTime={3} />` transforms into `_jsx(ArticleCard, { title: "Rail Strike Ends", readTime: 3 })`. Notice that the second argument to `_jsx` is a standard JavaScript object literal. React instantiates this object, freezes it shallowly in development mode using `Object.freeze()`, and provides it to your component when invoking the function. This mechanical reality proves why components receive exactly one object argument rather than a list of separate parameters.

### How JavaScript handles prop types, string concatenation, and default values

In JSX, how you wrap an attribute value determines its JavaScript data type. As established in Lecture 4, quotes pass a static string literal (`readTime="5"`), while curly braces evaluate a live JavaScript expression (`readTime={5}`). When a child component receives a prop, the runtime respects that exact type. If a component receives `"5"` as a string and performs addition (`{readTime + 1}`), JavaScript performs string concatenation via **type coercion**, converting `1` to `"1"` and producing `"51"`. By contrast, multiplication (`{readTime * 60}`) coerces the string to a number and yields `300`. This discrepancy can hide bugs during initial testing until an addition operation reveals the error.

When designing components, some props are optional. If a parent component omits an attribute or passes `readTime={undefined}`, the incoming property is `undefined`. To prevent blank slots on screen, JavaScript allows you to specify a **default parameter value** directly inside the destructuring braces: `function ArticleCard({ title, readTime = 5 })`. If the parent does not provide `readTime`, the local variable automatically takes the fallback value `5`. However, default parameter values only trigger when a value is strictly `undefined` or missing; they do not trigger when a parent passes `null` or `0`.

When working with external API data, database records often contain `null` for unmeasured fields. If a parent passes `readTime={null}`, the default parameter `readTime = 5` does not engage because `null` is a defined value. In JSX, `{null}` renders as an empty string, producing ` min read`. In older JavaScript codebases, developers wrote `readTime || 5` using the **logical OR** operator. However, `||` treats any falsy value as missing, which replaces a valid `0` (such as a 0-minute quick read) with `5`. Modern codebases use the **nullish coalescing** operator (`??`): `const time = readTime ?? 5;`. Nullish coalescing checks strictly for `null` and `undefined`, preserving valid `0` values while providing a resilient fallback.

### The read-only contract, frozen objects, and why mutating inputs corrupts the tree

In React, components must be pure functions with respect to their inputs. A pure function is one that does not alter any objects or variables that existed before it was called, and returns the exact same JSX description given the same inputs. Props represent data owned by the parent component. If a child component were allowed to perform a **mutation** by directly reassigning `props.title = 'Breaking News'`, it would modify memory owned by the parent. React enforces an immutability contract: props are strictly read-only.

To protect developers from accidental mutations, React shallowly freezes the props object in development mode using `Object.freeze()`. When code runs inside an ES module, JavaScript automatically executes in **strict mode**. In strict mode, attempting to assign a property on a frozen object immediately throws a fatal exception: `TypeError: Cannot assign to read only property 'title' of object '#<Object>'`. In older non-strict scripts, the assignment is silently ignored without updating the object.

It is critical to understand that React's development freeze is a diagnostic alarm, not a runtime security sandbox. In production builds, React skips `Object.freeze()` to maximize rendering performance. Furthermore, `Object.freeze()` is shallow: if a parent passes an object prop like `article={{ title: 'Rail Strike', readTime: 3 }}`, React freezes only the outer container, leaving nested properties mutable. If a child executes `article.title = article.title.toUpperCase()`, the assignment succeeds in both development and production. This mutation silently corrupts data in the parent and across sibling components showing the same article (such as a sidebar), causing state drift.

Instead of mutating incoming props, a component that needs an altered display format calculates a new local variable during render: `const headline = title.toUpperCase();`. The component renders `{headline}` in its JSX while leaving the incoming prop completely untouched. If data must change dynamically over time in response to user events, the component does not modify props; instead, the owner component manages that value using React state (introduced in Lecture 14).

### Principles of React: Passing Data with Props

### Question 1: Attributes on a tag become the component's one props object

A developer renders three article cards inside an editorial feed container to display morning news dispatches. The developer writes attributes on each JSX tag, providing distinct titles and reading estimates:

```jsx title="Feed Call Sites"
function EditorialFeed() { // parent container passes attributes
  return (
    <main>
      <ArticleCard title="Rail Strike Ends" readTime={3} />
      <ArticleCard title="Clean Energy Project" readTime={5} />
      <ArticleCard title="City Park Renovations" readTime={4} />
    </main>
  );
}
```

However, inside `ArticleCard`, the component still returns hardcoded text:

```jsx title="ArticleCard Hardcoded Heading"
function ArticleCard() {
  return <h2>Night Trains Return to Europe</h2>; // ignores incoming attributes
}
```

When the browser renders the page, all three cards display `Night Trains Return to Europe`. The developer checks the browser console, expecting a warning about unused attributes, but the console stays silent.

**How do individual cards display their own headlines when rendered from the same component?**

---

**ANSWER**

**The code does not do what we wanted.** React packages attributes into a props object, but the component must read values from that object to display them.

When React evaluates `EditorialFeed`, it encounters three `<ArticleCard />` tags. For each tag, React collects all attributes into a single JavaScript object: `{ title: "Rail Strike Ends", readTime: 3 }` for the first card, and `{ title: "Clean Energy Project", readTime: 5 }` for the second. React then invokes `ArticleCard` three times, passing that tag's specific object as the sole argument. If you add `console.log(props)` inside `ArticleCard`, the console prints three distinct objects in the exact order the tags appear.

Because `ArticleCard` returned hardcoded text, it completely ignored its incoming argument. React does not automatically project tag attributes into child markup; attributes never reach the browser DOM by themselves. To display the parent's data, the component must accept its props object and interpolate values into returned JSX, such as `function ArticleCard({ title })` returning `<h2>{title}</h2>`.

```ascii title="JSX attributes compiling into a single props object argument"
JSX Call Site:                               Function Call:
<ArticleCard                         -->     ArticleCard({
  title="Rail Strike Ends"                     title: "Rail Strike Ends",
  readTime={3}                                 readTime: 3
/>                                           })
```

> [!PRINCIPLE]
> **Principle 1: The attributes on a tag become the component's one argument, the props**
> When you write attributes on a custom component tag in JSX, React collects them into a single **props** object. React calls your component function with that object as its only argument. Each tag gets its own props object, giving each rendered card its own values. Nothing appears on screen until the component reads from that object.
>
> >> props : a single JavaScript object collecting all attributes passed from parent to child
>
> *We should do this:*
> `function ArticleCard({ title }) {`
> `  return <h2>{title}</h2>; // reads incoming prop`
> `}`
>
> *We should not do this:*
> `function ArticleCard() {`
> `  return <h2>Night Trains Return</h2>; // ignores tag attributes`
> `}`

In our feed test, rendering `<ArticleCard title="Rail Strike Ends" readTime={3} />` and `<ArticleCard title="Clean Energy Project" readTime={5} />` produces two separate calls to `ArticleCard`. Inside `ArticleCard`, adding `console.log(props)` logs `{"title":"Rail Strike Ends","readTime":3}` and `{"title":"Clean Energy Project","readTime":5}` in the browser console. When the component returned hardcoded text, both calls returned identical markup. Once the component reads from props, each card displays its own headline and reading time.

### Question 2: Unpack the props in the parameter list inside braces

A developer wants to read `title` and `readTime` inside `ArticleCard`. In standard JavaScript functions, passing two pieces of data typically means declaring two parameters. The developer declares both names in the parameter list without braces:

```jsx title="Missing Parameter Braces"
function ArticleCard(title, readTime) { // binds object to title parameter
  return (
    <article className="card">
      <h2>{title}</h2> {/* crashes attempting to render raw object */}
      <p>{readTime} min read</p>
    </article>
  );
}
```

When the application loads, the browser screen goes blank. The developer opens the browser console and discovers a fatal runtime crash: `Error: Objects are not valid as a React child (found: object with keys {title, readTime})`. Furthermore, when testing with `{ headline }` instead of `{ title }`, the heading renders completely blank without an error message.

**How do we extract title and readTime from incoming props without causing runtime errors?**

---

**ANSWER**

**The code does not do what we wanted.** React passes exactly one argument to components, so parameters must be wrapped in curly braces to destructure properties.

In JavaScript, function parameters bind sequentially to incoming arguments. When React renders `<ArticleCard title="Rail Strike Ends" readTime={3} />`, it invokes `ArticleCard({ title: "Rail Strike Ends", readTime: 3 })` with exactly one argument. When you declare `function ArticleCard(title, readTime)` without braces, JavaScript binds the first parameter `title` to the entire props object, while the second parameter `readTime` receives `undefined`.

When React attempts to evaluate `<h2>{title}</h2>`, it encounters a raw JavaScript object inside JSX children. Because objects cannot be converted into DOM text nodes, React halts execution with `Objects are not valid as a React child`. To unpack properties into local variables, wrap the parameter names in curly braces: `function ArticleCard({ title, readTime })`. This triggers object destructuring, creating local variables matching the object keys. If you write `{ headline }` when the tag passed `title=`, destructuring assigns `undefined`, leaving an empty slot.

```ascii title="Parameter destructuring unpacking properties versus raw object binding"
With Braces:   ({ title, readTime })  --> title = "Rail Strike", readTime = 3
Without:       (title, readTime)      --> title = { title: "...", readTime: 3 }
                                          readTime = undefined
```

> [!PRINCIPLE]
> **Principle 2: Unpack the props in the parameter list, inside braces**
> React passes only one argument to a component function, the props object. Wrapping parameter names in curly braces uses **destructuring** to unpack specific properties into local variables. If you omit the braces, the first parameter receives the entire object, causing a runtime crash if rendered directly in JSX.
>
> >> destructuring : unpacking properties from an object into local variables with braces
>
> *We should do this:*
> `function ArticleCard({ title }) {`
> `  return <h2>{title}</h2>; // unpacks title property`
> `}`
>
> *We should not do this:*
> `function ArticleCard(title) {`
> `  return <h2>{title}</h2>; // crashes: objects are not valid as children`
> `}`

When we write `function ArticleCard(title, readTime)`, JavaScript assigns the first argument (the props object) to `title`, while `readTime` remains `undefined`. When React evaluates `<h2>{title}</h2>`, it attempts to render a raw JavaScript object into the DOM and throws: `Error: Objects are not valid as a React child (found: object with keys {title, readTime})`. Wrapping the parameters in braces (`{ title, readTime }`) tells JavaScript to extract those exact properties into local variables. If you type `{ headline }` instead of `{ title }`, the variable receives `undefined`, and the heading renders blank without throwing an error.

### Question 3: Pass numbers in curly braces or they arrive as strings

A developer writes an article card that displays reading estimates in multiple formats. The card displays reading time plus an estimated summary time (`{readTime + 1} min with the summary`), as well as the total seconds (`{readTime * 60} seconds`). At the JSX call site, the developer writes `readTime="5"` in quotes:

```jsx title="Quoted Number Attribute"
<ArticleCard
  title="Rail Strike Ends"
  readTime="5" // passes string "5" rather than numerical value
/>
```

Inside `ArticleCard`, the component performs arithmetic on the incoming prop:

```jsx title="Reading Time Calculations"
function ArticleCard({ title, readTime }) { // unpacks parameters
  return (
    <article className="card">
      <h2>{title}</h2>
      <p>{readTime + 1} min with the summary</p> {/* evaluates "5" + 1 */}
      <p>{readTime * 60} seconds</p> {/* evaluates "5" * 60 */}
    </article>
  );
}
```

On screen, the seconds calculation displays `300 seconds`, which looks correct. However, the first line displays `51 min with the summary` instead of `6 min`.

**Why does passing a number in quotes result in 51 min on screen instead of 6 min?**

---

**ANSWER**

**The code does not do what the reader expected.** Quoted attributes pass strings, causing JavaScript addition to perform string concatenation rather than mathematical addition.

In JSX, quotes enclose string literals. Writing `readTime="5"` passes the string `"5"` to the component. In JavaScript, the addition operator (`+`) has dual behavior: it adds numbers together, but when either operand is a string, it converts the other operand to a string and concatenates them via type coercion. Therefore, `"5" + 1` becomes `"5" + "1"`, which evaluates to `"51"`.

The bug is deceptive because the multiplication line (`{readTime * 60}`) displays `300 seconds`. In JavaScript, the multiplication operator (`*`) does not exist for strings; the runtime coerces `"5"` into the number `5` and performs arithmetic. To pass genuine numbers, wrap them in curly braces: `<ArticleCard readTime={5} />`. Curly braces evaluate the enclosed expression as JavaScript, delivering a number type where `5 + 1` evaluates to `6`.

```ascii title="String concatenation versus numerical addition in JavaScript"
Quoted Prop:  readTime="5"  --> "5" + 1 === "51"  (String Concatenation)
Brace Prop:   readTime={5}  -->  5  + 1 === 6     (Numerical Addition)
```

> [!PRINCIPLE]
> **Principle 3: Pass numbers in curly braces, or they arrive as strings**
> An attribute written in quotes always passes a string literal. If your component performs addition on a quoted number, JavaScript uses **type coercion** to concatenate the values as text, turning `"5" + 1` into `"51"`. Pass numbers inside curly braces so they arrive as numbers.
>
> >> type coercion : automatic conversion of a value from one data type to another by JavaScript
>
> *We should do this:*
> `function Card() {`
> `  return <ArticleCard readTime={5} />; // passes number 5`
> `}`
>
> *We should not do this:*
> `function Card() {`
> `  return <ArticleCard readTime="5" />; // passes string '5'`
> `}`

Testing both call sites reveals why this defect slips past casual checks. In the first card with `readTime="5"`, `{readTime * 60}` computes `300` because the multiplication operator coerces strings to numbers in JavaScript. However, `{readTime + 1}` outputs `51` because the plus operator prioritizes string concatenation when either operand is a string. When we change the call site to `readTime={5}`, `{readTime + 1}` evaluates to `6`, and `{readTime * 60}` evaluates to `300`. Reviewers flag quoted numbers on sight because arithmetic errors surface as soon as a feature adds numbers together.

### Question 4: A default fills a missing prop and only a missing one

A developer designs `ArticleCard` so that `readTime` is optional. If an article record lacks a reading time estimate, the developer wants the card to display a default estimate of 5 minutes. The developer configures a default parameter in destructuring:

```jsx title="Default Parameter Configuration"
function ArticleCard({ title, readTime = 5 }) { // sets default parameter
  return (
    <article className="card">
      <h2>{title}</h2>
      <p>{readTime} min read</p> {/* renders empty slot for null */}
    </article>
  );
}
```

When rendering `<ArticleCard title="Park Renovations" />` with no `readTime` attribute, the card displays `5 min read`. When rendering `<ArticleCard readTime={0} />` for a brief bulletin, the card displays `0 min read`. However, when data arrives from an API where unmeasured articles have `readTime: null`, the card renders ` min read` with an empty slot.

**How do default parameter values behave when an incoming prop is undefined, null, or zero?**

---

**ANSWER**

**The code does not do what the reader wanted.** Default parameters only engage when a prop is missing or undefined; they pass null through unchanged.

In JavaScript, default parameter values trigger strictly when an incoming argument is `undefined`. When a parent omits an attribute or explicitly passes `readTime={undefined}`, JavaScript substitutes the fallback value `5`. However, `null` is a valid primitive object in JavaScript representing the intentional absence of a value. Because `null !== undefined`, the default parameter does not engage. In JSX, `{null}` produces an empty text slot, rendering ` min read`.

To handle `null`, some developers write `readTime || 5`. However, the logical OR operator (`||`) checks for falsiness. Because `0` is falsy in JavaScript, `<ArticleCard readTime={0} />` replaces `0` with `5`, corrupting valid zero-minute bulletins. The robust solution is the nullish coalescing operator (`??`): `const time = readTime ?? 5;`. Nullish coalescing replaces only `null` and `undefined`, preserving valid `0` values. Furthermore, React 19 does not validate legacy `propTypes` on function components, so fallback logic must be handled in JavaScript.

```ascii title="Default parameter evaluation across undefined, null, and zero"
Input Value:       readTime = 5:      readTime || 5:     readTime ?? 5:
undefined (missing) -> 5 (Default)        -> 5               -> 5
null                -> null (Pass-through)-> 5 (Overridden!) -> 5
0                   -> 0 (Preserved)      -> 5 (Overridden!) -> 0 (Preserved)
```

> [!PRINCIPLE]
> **Principle 4: A default fills a missing prop, and only a missing one**
> An assignment after `=` sets a **default parameter** that fills in when a prop is missing or `undefined`. A default parameter does not replace `null` or `0`. When data can hold `null`, compute a fallback with `??` during render, and avoid `||` because it overwrites valid zero values.
>
> >> default parameter : a fallback value assigned when an incoming argument is undefined
>
> *We should do this:*
> `function ArticleCard({ readTime = 5 }) {`
> `  return <p>{readTime} min</p>; // fills missing or undefined`
> `}`
>
> *We should not do this:*
> `function ArticleCard({ readTime }) {`
> `  return <p>{readTime || 5} min</p>; // overrides valid 0 with 5`
> `}`

We test four cards against `readTime = 5`: an omitted prop displays `5 min read`, `readTime={undefined}` displays `5 min read`, `readTime={0}` displays `0 min read`, and `readTime={null}` displays ` min read`. Because `null` passes through default parameters, the label renders blank. When developers attempt to fix this with `readTime || 5`, passing `0` produces `5 min read`, corrupting valid zero-minute reads. Replacing the expression with `readTime ?? 5` preserves `0 min read` for zero while supplying `5 min read` for both `null` and `undefined`.

### Question 5: Props are read-only so make a new variable instead

A developer wants every article headline to appear in uppercase letters. Because `props` is a JavaScript object, the developer attempts to mutate the incoming title directly inside the component body before returning markup:

```jsx title="Direct Prop Reassignment"
function ArticleCard(props) {
  props.title = props.title.toUpperCase(); // attempts in-place mutation
  return (
    <article className="card">
      <h2>{props.title}</h2>
    </article>
  );
}
```

In the local development environment, the browser crashes immediately with `TypeError: Cannot assign to read only property 'title' of object '#<Object>'`. However, in a production build, the assignment succeeds without an error. Furthermore, when an article object is passed as a prop, mutating `article.title` succeeds in both builds and turns a sidebar's "Most Read" list into uppercase as well.

**Why does reassigning props crash in development, and how should formatted values be calculated?**

---

**ANSWER**

**The code does not do what the reader wanted.** Props belong to the parent component and are strictly read-only; components must calculate new variables during render instead of mutating inputs.

In React, components must operate as pure functions. A component should never modify any data that existed prior to its execution. Props represent input data owned and managed by the parent component. To enforce this contract, React shallowly freezes the props object in development using `Object.freeze()`. Because modern Vite and ES module files execute in JavaScript strict mode, any attempt to assign a property on a frozen object throws a runtime `TypeError`.

In production builds, React skips `Object.freeze()` to maximize render speed, meaning mutations fail silently or execute without warning, allowing dangerous bugs to ship. Even worse, `Object.freeze()` is shallow: if a prop contains a nested object (`article={{ title: 'Rail Strike' }}`), mutating `article.title` succeeds in all environments. This mutation modifies shared memory in the parent, causing sibling components that read the same object (such as a sidebar) to unexpectedly display uppercase text. To format data, declare a new local constant during render: `const headline = title.toUpperCase()`.

```ascii title="Direct prop mutation versus pure local derivation during render"
Mutation (Corrupts):  props.title = "NEW"  --> Modifies shared parent object
Derivation (Pure):    const headline = ... --> Creates fresh local constant
```

> [!PRINCIPLE]
> **Principle 5: Props are read-only, so make a new variable instead**
> Props belong to the parent component and are strictly read-only. A direct **mutation** like `props.title = ...` corrupts data across the component tree. In development, React freezes props so an assignment throws an error. When you need an altered form of a prop, calculate a new variable during render.
>
> >> mutation : modifying the properties of an existing object directly in memory
>
> *We should do this:*
> `function ArticleCard({ title }) {`
> `  const headline = title.toUpperCase(); // pure local derivation`
> `  return <h2>{headline}</h2>;`
> `}`
>
> *We should not do this:*
> `function ArticleCard(props) {`
> `  props.title = props.title.toUpperCase(); // crashes: mutating frozen props`
> `}`

In our development server, running `props.title = props.title.toUpperCase()` immediately halts execution with a fatal `TypeError` because React ran `Object.freeze()` on the props object. In a production build, `Object.isFrozen(props)` evaluates to `false`, allowing the mutation to proceed without error. Furthermore, when `article` is passed as an object prop, mutating `article.title = article.title.toUpperCase()` succeeds in both development and production because `Object.freeze()` is shallow. A sidebar component displaying the same article object suddenly renders uppercase titles as well, causing severe state drift. Calculating `const headline = title.toUpperCase()` during render protects the parent's data and keeps sibling components completely isolated.

Next, we implement `ArticleCard.jsx`. The component unpacks `title` and `readTime` directly in its parameter list using object destructuring. Inspecting `ArticleCard.jsx` highlights two critical architectural patterns. First, parameter destructuring with default values makes the component interface robust: consumers can supply a custom reading time or rely on the 5-minute fallback without writing conditional checks. Second, constructing `badgeText` as a local string literal during render satisfies React's purity contract. The component receives read-only inputs, derives its presentation values locally, and returns UI markup without altering parent memory.

### For the interview

> **The Interview Question:** How do you pass data into a component, and why can a component never change its own props?

**1. The Hidden Signal**

The interviewer is testing your grasp of React's component execution model, unidirectional data flow, functional purity, and JavaScript runtime mechanics. A junior candidate says props are "passed like HTML attributes." A senior engineer explains that JSX attributes bundle into a single frozen object passed as the sole argument to the component function, and that props must remain immutable because components must be pure functions with respect to their inputs. Mutating props destroys pure render guarantees, breaks memoization, and causes parent-child state drift across sibling elements.

**2. The Classic Trap**

The classic trap is assuming that props behave like regular mutable JavaScript function arguments, or attempting to write `props.title = props.title.toUpperCase()` to clean up display text. Candidates often fail to realize that React freezes props in development, causing fatal `TypeError` crashes in strict mode. Another frequent trap is forgetting destructuring braces (`function Card(title)` instead of `function Card({ title })`), which binds the entire props object to the first parameter and crashes with `Objects are not valid as a React child` when rendered.

**3. What is Actually Going On**

Under the hood, the JSX compiler translates component tags into `_jsx(Component, propsObject)`. React instantiates the props object, calls `Object.freeze()` on it in development, and passes it to the component. Because ES modules execute in JavaScript strict mode, any attempt to assign a property on a frozen object throws a runtime `TypeError`. In production builds, React skips `Object.freeze()` to optimize performance, meaning mutations succeed silently in production while failing in development. Furthermore, `Object.freeze()` is shallow: mutating nested object properties succeeds in all environments, corrupting shared memory in the parent and across sibling components.

**4. Where It Gets Tricky**

Where this gets tricky in production is handling optional props and fallback values. While default parameter syntax (`{ readTime = 5 }`) cleanly fills in for missing or `undefined` props, it does not trigger for `null` or `0`. If an API returns `null` for an uncalculated field, default parameters leave the value as `null`, rendering an empty slot. Using logical OR (`readTime || 5`) replaces valid `0` values because `0` is falsy. Senior engineers use nullish coalescing (`readTime ?? 5`) during render to preserve valid zeros while providing resilient fallbacks. When data must change over time, state management (Lecture 14) is used instead of prop mutation.

### Glossary

- **Props**: The single read-only JavaScript object containing all attributes passed from a parent component to a child component.
- **Object Destructuring**: The JavaScript syntax using curly braces to unpack specific properties from an object into local variables within a parameter list.
- **Type Coercion**: The automatic conversion of values from one data type to another by JavaScript, such as concatenating numbers as strings during addition.
- **Default Parameter**: A fallback value specified in a function parameter list that assigns automatically when an incoming argument is missing or undefined.
- **Mutation**: The direct modification of an existing object's properties in memory, strictly forbidden on props in React.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Prop Passing and Parameter Destructuring

➔ IF passing data to a child component, THEN write attributes on the custom component tag at the JSX call site.

➔ IF unpacking incoming props, THEN wrap parameter names in curly braces matching attribute names to avoid raw object binding crashes.

❒ Prop Types and Fallback Defaults

➔ IF passing numbers, booleans, or JavaScript expressions, THEN wrap values in curly braces to prevent string type coercion bugs.

➔ IF specifying fallback values for optional props, THEN assign default parameters after `=` in destructuring, using `??` during render if data can contain null.

❒ Immutability Contract and Component Purity

➔ IF formatting or altering incoming prop values for display, THEN calculate a new local variable during render rather than mutating props.

➔ IF data must change dynamically over time in response to user input, THEN manage that data in state rather than modifying props.

**DO THIS:** Unpack props with destructuring, pass numbers in braces, and calculate derived values pure in render

```jsx right
function ArticleCard({ title, readTime = 5 }) {
  const badge = `${readTime} MIN READ`;
  return (
    <article className="card">
      <span>{badge}</span>
      <h2>{title}</h2>
    </article>
  );
}
```

**DO NOT DO THIS:** Omit destructuring braces, pass numbers in quotes, or mutate frozen props directly

```jsx wrong
function ArticleCard(props) {
  props.title = props.title.toUpperCase();
  return (
    <article className="card">
      <h2>{props.title}</h2>
      <p>{props.readTime + 1}</p>
    </article>
  );
}
```
