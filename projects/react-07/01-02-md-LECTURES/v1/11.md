### Every web application needs to display collections of items

Every web application displays dynamic collections of items. An online shop displays a grid of products, a social feed shows a list of posts, and a news portal presents breaking articles. In static HTML, each item is hardcoded into the markup one tag at a time. If the collection changes from twenty items to twenty-five, an engineer must edit the template and redeploy the code. In modern applications, collections change constantly: items are added, removed, filtered, and reordered. Modern web frameworks transform raw arrays of data into living user interfaces.

In basic HTML and early templates, developers repeated tags by hand or wrote imperative loops that manually created DOM elements and appended them to the page. In React, a component is a function that returns a description of what the interface should look like. You store your data in standard JavaScript arrays of objects. Instead of repeating JSX tags or writing manual append loops, you project that array of data into an array of JSX elements. React unpacks that array and paints the corresponding DOM nodes in order.

This chapter answers five core questions. **How does JavaScript's map method turn an array of data into a list of elements?** **Where must the key prop be placed when extracting a child component?** **How do keys give elements persistent identity across re-renders?** **Why do array indices and random numbers create dangerous keys?** **Why is props.key undefined inside a child component?**

### How JavaScript transforms data arrays with map and arrow functions

In Lecture 4, we saw that curly braces `{}` inside JSX open an evaluation window for JavaScript expressions. JavaScript represents collections of structured data as arrays of objects, such as `const stories = [{ id: 's1', title: 'City Transit Plan' }, { id: 's2', title: 'Clean Energy Accord' }]`. Each item in the array has properties we can access with dot notation, like `story.title`. To display every story, we need a way to convert each object in the data array into a corresponding JSX element.

The standard JavaScript array method `map()` transforms an array into a new array. It takes a callback function as an argument, calls that function once on each item in the original array, and collects the return values into a brand-new array. The original array remains completely untouched. For example, `[1, 2, 3].map(n => n * 2)` produces `[2, 4, 6]`. In React, our callback takes a data object and returns a JSX element, such as `stories.map(story => <li>{story.title}</li>)`. When you place `{stories.map(...)}` inside a `<ul>`, React unpacks the resulting array of elements and renders each `<li>` in order.

In JavaScript, an arrow function can be written with an **implicit return** or a **block body**. In an arrow function without curly braces on the right side of the arrow, like `story => <li>{story.title}</li>`, JavaScript uses an implicit return: it automatically returns the single expression following the arrow. However, if you place curly braces after the arrow, like `story => { <li>{story.title}</li> }`, you create a block body. A block body executes code statements line by line, but it returns `undefined` unless you explicitly write the `return` keyword. If you omit `return`, `map()` returns an array filled with `undefined`, and React renders zero DOM nodes.

Often, an interface needs to display only a subset of items from an array, such as only featured stories. The standard JavaScript `filter()` method takes a test predicate function that returns `true` or `false` for each item. It produces a new, shorter array containing only the items that returned `true`. You can chain `filter()` directly into `map()`, writing `stories.filter(story => story.isFeatured).map(story => <li key={story.id}>{story.title}</li>)`. This separates filtering logic from markup projection.

The callback function passed to `map()` receives three arguments: the current item, the item's numerical **array index** (starting from 0), and the array itself. Writing `stories.map((story, index) => ...)` exposes the sequential position of each item. While the index tells you where an item currently sits in the array, that index changes whenever items are prepended, inserted, or reordered.

```jsx title="Transforming Arrays with Map"
const items = [{ id: '1', title: 'First' }, { id: '2', title: 'Second' }];
const elements = items.map(item => (
  <li key={item.id}>{item.title}</li> {/* Implicit return */}
));
const blockList = items.map(item => {
  return <li key={item.id}>{item.title}</li>; // Explicit return
});
const active = items.filter(item => item.id !== '1');
```

### How React reconciles element arrays using persistent keys

In Lecture 3, we learned that JSX tags compile into plain JavaScript objects called React elements. When you write `stories.map(story => <li key={story.id}>{story.title}</li>)`, the `map()` method creates an array of these lightweight element descriptors in memory. Inspecting one of these elements in the console reveals a plain object: `{ type: 'li', key: 's1', props: { children: 'City Transit Plan' } }`. Notice that `key` sits on the element object itself, alongside `type` and `props`.

When an application updates, React creates a new tree of element descriptions and compares it to the previous tree to determine what needs to change in the real DOM. When comparing lists of child elements, React must figure out which element in the new list corresponds to which element in the old list. Without keys, React falls back to **positional matching**: it assumes the first new item matches the first old item, the second matches the second, and so on. If an item is added to the top of the array, every subsequent item shifts down one position, causing React to rewrite existing DOM nodes in place and break internal element state.

A **key** is a special string or number passed to JSX elements in an array that gives each item a permanent **element identity**. React uses the key to track each item throughout its lifecycle across renders. When a key is present, React does not pair elements by their index position; instead, it matches old and new elements that share the exact same key. If an item moves from the first position to the fifth position, React reuses the existing DOM node and moves it in the page, preserving input values, focus, and scroll position.

```jsx title="Inspecting Keyed Element Objects"
const stories = [{ id: 's1', title: 'Transit Plan' }];
const elements = stories.map(story => (
  <li key={story.id}>{story.title}</li> {/* Assigns stable key */}
));
console.log(elements[0]); // Logs element object
```

### Principles of React: Rendering Lists and Keys

### Question 1: An arrow function with braces renders an empty list

You receive an array of thirty breaking stories from the server. You want to display each headline as a row in a list. Inside your feed component, you call `stories.map()`. Because you want to add console logging or variable declarations later, you write curly braces around the callback function body:

```jsx title="Feed Without Return Keyword"
function Feed({ stories }) {
  return (
    <ul>
      {stories.map(story => {
        <li key={story.id}>{story.title}</li>; // Missing return keyword
      })}
    </ul>
  );
}
```

You open the browser. The data array contains thirty stories, but the unordered list renders completely empty. You open the developer console, expecting an error or warning, but the console is clean.

**Why does the list render completely blank when the array has thirty stories?**

---

**ANSWER**

**The code does not work.** The arrow function callback has a block body but omits the return keyword.

In JavaScript, when an arrow function body begins with a curly brace, it becomes a block body. A block body executes statements sequentially, but it produces no return value unless you write the `return` keyword. Without `return`, the function returns `undefined`.

When `stories.map()` executes over an array of thirty items, it collects thirty `undefined` return values into a new array. As Lecture 4 explained, React's suppression whitelist renders zero DOM nodes for `undefined`. The component returns an array of `undefined`, so React paints nothing into the browser DOM. The console shows no error because returning `undefined` is valid JavaScript and valid JSX.

To fix this issue, you must write an explicit `return` keyword inside the curly braces. Alternatively, remove the curly braces and wrap the JSX tag in parentheses to use an implicit return. When written with a proper return, `console.log(storyElements[0])` shows a valid element object with `type: 'li'`, `key: 's1'`, and `props: { children: 'City Transit Plan' }`.

```ascii title="Mapping data objects to React element objects"
Data Array              map() Callback          React Elements
----------------------------------------------------------------------
[                       (story) =>              [
  { id: '1', title: 'A' }  <li key="1">A</li>  ->  { type: 'li', ... }
]                                               ]
```

> [!PRINCIPLE]
> **Principle 1: The map method turns an array of data into an array of elements**
> To build a list of elements from an array, call `map()` on the data. Each call runs the function on one item and collects what it returns into a new array. When the function uses curly braces, write **return**, or the call returns undefined and the list renders completely empty with no error.
>
> >> array transformation : converting an array of data objects into a new array of element descriptions using map
> >> explicit return : writing the return keyword inside a block body so a function outputs a value
>
> *We should do this:*
> `items.map(item => (`
> `  <li key={item.id}>{item.title}</li> {/* returns element */}`
> `))`
>
> *We should not do this:*
> `items.map(item => {`
> `  <li key={item.id}>{item.title}</li>; // returns undefined`
> `})`

### Question 2: The console warns that each child needs a key

To keep your code modular, you extract the markup for each story row into a separate component named `StoryItem`. You remember that React requires a key on list items, so you place `key={story.id}` on the root `<li>` tag inside `StoryItem.jsx`:

```jsx title="Key Placed Inside Child Component"
function Feed({ stories }) {
  return (
    <ul>
      {stories.map(story => (
        <StoryItem story={story} /> {/* Missing key on child */}
      ))}
    </ul>
  );
}
```

Inside `StoryItem.jsx`, you return `<li key={story.id}>{story.title}</li>;`. The thirty stories appear on screen correctly, but the browser console prints a red warning: *"Warning: Each child in a list should have a unique 'key' prop. Check the render method of `Feed`."*

**Why does React print a missing key warning when the list item already has a key?**

---

**ANSWER**

**The code does not do what we wanted.** The key is placed on an inner tag instead of the outermost element returned by map.

React reconciles arrays at the exact level where the array is created. In `Feed.jsx`, the `map()` method creates an array of `<StoryItem />` elements. React inspects that array to verify that each item in the collection carries a `key` prop.

When you place `key={story.id}` on the `<li>` tag inside `StoryItem`, that key is attached to an internal element created inside `StoryItem`'s own render pass. React cannot see into `StoryItem` while it reconciles the child array in `Feed`. To React, the array contains thirty `<StoryItem />` elements, and none of them have a key.

To fix this warning, place `key={story.id}` directly on the outermost element returned by the `map()` callback: `<StoryItem key={story.id} story={story} />`. Keys must be unique among **siblings** within that specific array; using the same key in a completely different list is valid. If a single item must return multiple adjacent tags without adding a wrapper `<div>`, use `<Fragment key={story.id}>` because shorthand `<>...</>` cannot accept attributes. Furthermore, never put a key inside an object and spread it (`<StoryItem {...story} />` where story contains `key`), because React warns that a key is being spread into JSX.

```ascii title="Key placement at the array boundary"
Array Level (Feed)                 Component Internal (StoryItem)
-----------------------------------------------------------------
stories.map(story => (             function StoryItem({ story }) {
  <StoryItem                         return (
    key={story.id}  <-- REQUIRED       <li>...</li>  <-- INEFFECTIVE
    story={story}                    );
  />                               }
))
```

> [!PRINCIPLE]
> **Principle 2: Put the key on the element written inside map**
> React checks keys on the elements in the array returned directly by `map()`. When you map to a component, put the key on that component, not on an HTML element inside it. A key on an inner tag does not identify the item in the array. Keys must be unique among sibling elements in that array.
>
> >> outermost element : the top-level JSX element returned directly by the map callback
> >> sibling uniqueness : the rule that keys must be distinct within the same array
>
> *We should do this:*
> `items.map(item => (`
> `  <ItemRow key={item.id} item={item} /> {/* key on mapped item */}`
> `))`
>
> *We should not do this:*
> `items.map(item => (`
> `  <ItemRow item={item} /> {/* missing key on component */}`
> `))`

### Question 3: Text typed into a row jumps when a story is added at the top

You want each story row to include an uncontrolled `<input>` field where editors can type editorial notes. To satisfy the key requirement quickly, you use the array index as the key:

```jsx title="Feed Using Index Keys"
function Feed({ stories }) {
  const items = stories.map((story, index) => (
    <li key={index}> {/* Index key causes state drift */}
      {story.title} <input placeholder="Add note..." />
    </li>
  ));
  return <ul>{items}</ul>;
}
```

The list renders cleanly, and the console produces zero warnings. An editor clicks the first input box ("City Transit Accord Finalized") and types "verify transit numbers". A breaking headline arrives, and the application prepends an urgent story ("Urgent Alert: Flash Flood") to the top of the array at index 0. The application re-renders with `root.render`.

Suddenly, the note "verify transit numbers" appears inside the input box for "Urgent Alert: Flash Flood"! Meanwhile, the input box for "City Transit Accord Finalized" is now empty.

**Why does typed text jump to the new story when using array indices as keys?**

---

**ANSWER**

**The code does not do what we wanted.** Array index keys force React to match elements by numerical position rather than data identity.

When a component re-renders, React reconciles the new element tree with the previous element tree. To do this efficiently, React pairs elements between renders. When you provide `key={index}` (or omit keys entirely), React uses **positional matching**. It pairs the old item at index 0 with the new item at index 0.

Before the update, index 0 was "City Transit Accord Finalized". When the editor typed into the input, the browser stored that text directly in the physical DOM `<input>` element. When the urgent story was prepended at index 0, the transit story shifted to index 1.

React compares the old tree with the new tree:
1. At index 0, React sees that the title text changed from "City Transit Accord Finalized" to "Urgent Alert: Flash Flood". It updates the headline text inside the existing DOM node in place.
2. Because React mutates the existing DOM node at index 0 instead of moving it, the browser's internal input buffer is left untouched. The typed text remains inside the first physical DOM box.
3. At index 1, React creates a new DOM node or updates an old one, leaving its input empty.

To the user, their typed text appears to jump from the transit story to the urgent headline. The fix is to use a stable ID from the data (`key={story.id}`). With stable keys, React matches the old `s1` element with the new `s1` element. It physically moves the existing DOM node down to index 1, carrying the input text, focus, and scroll position with it.

```ascii title="Positional matching vs identity matching on prepend"
Index Keys (Positional):             Stable Keys (Identity):
Old Slot 0: Transit [verify]         Old s1: Transit [verify]
New Slot 0: Urgent  [verify] (WRONG) New s9: Urgent  []       (FRESH)
New Slot 1: Transit []               New s1: Transit [verify] (MOVED)
```

> [!WILD]
> **Why do user inputs jump when using index keys?** When you use array indices as keys, React tracks elements purely by their numerical order rather than their data identity. When an item is prepended at index 0, every existing item shifts down by one position. React looks at index 0, sees that the title text changed, and mutates the existing DOM node in place. However, the browser's internal input buffer lives directly inside the physical DOM node. Because React reuses the existing node at index 0 instead of moving it, whatever text the user typed stays in that first box. To the user, their typed input appears to jump to the wrong story. To prevent this, you must always provide a permanent database ID (`key={story.id}`) so React can move the actual DOM node to its new position.

> [!PRINCIPLE]
> **Principle 3: The key is how React finds the same row on the next render**
> On the next render, React pairs each new element with an old one that shares the same key. When keys match, React keeps the existing browser DOM node, along with whatever the user typed into it. Without keys, or with array indices, React matches items by position. Adding an item at the top forces the new item into the first DOM node, leaving old typed text attached to the wrong content.
>
> >> element identity : a persistent identifier that ties an element to its physical DOM node across renders
> >> positional diffing : matching items by index order when keys are missing or based on index
>
> *We should do this:*
> `items.map(item => (`
> `  <li key={item.id}><input /></li> {/* node moves with id */}`
> `))`
>
> *We should not do this:*
> `items.map((item, index) => (`
> `  <li key={index}><input /></li> {/* text jumps to wrong row */}`
> `))`

### Question 4: A random key makes every input lose its focus and text

You have an array of stories that do not have an `id` field. Knowing that array indices cause input text to jump, you decide to generate a unique key on the fly using `Math.random()`:

```jsx title="Feed Using Math.random Keys"
function Feed({ stories }) {
  const items = stories.map(story => (
    <li key={Math.random()}> {/* Random key forces recreation */}
      {story.title} <input placeholder="Add note..." />
    </li>
  ));
  return <ul>{items}</ul>;
}
```

An editor begins typing a note into the first input box. As soon as the application updates, the input box suddenly loses focus. The editor's cursor vanishes, and all typed text disappears.

**Why does generating keys with Math.random clear all inputs and lose focus on every render?**

---

**ANSWER**

**The code does not do what we wanted.** Math.random generates fresh keys on every render pass, destroying and rebuilding all DOM nodes.

A key must remain constant for the same data entity across renders. Because `Math.random()` executes during render, every item receives a completely new random number each time the component runs.

When React compares the new element tree with the previous tree, it finds that none of the keys match. React assumes that all previous elements were deleted and that completely new elements were created. It destroys every existing DOM node in the list and mounts new nodes from scratch.

This teardown destroys user inputs:
1. Any active cursor focus is lost because the focused DOM element was removed from the document.
2. Any uncontrolled input values, text selections, or scroll positions are erased.
3. Application performance suffers because the browser must recalculate styles and rebuild layout on every update.

A key must come from the data. If the data comes from a database, use its permanent database ID (`story.id`). If data is created locally in the browser, generate an ID once at creation time using `crypto.randomUUID()` and store it on the object. The array index is acceptable only when a list is completely static: items are never inserted, deleted, filtered, or reordered, such as lines of a printed poem.

```ascii title="Random key churn vs stable data identity"
Render 1: key=0.1824 -> DOM Node A created [focused, text="note"]
Render 2: key=0.7491 -> Keys mismatch! Node A destroyed, Node B created
Result: text lost, focus dropped, full DOM teardown
```

> [!PRINCIPLE]
> **Principle 4: Use a stable ID from the data as the key**
> A key must remain the same for the same item across renders. Generating keys with Math.random runs on every render, so no keys ever match and React tears down and rebuilds every DOM node from scratch. Use a permanent ID from the data, such as a database ID or an ID made once with crypto.randomUUID. The array index is safe only for a static list that never inserts, deletes, or changes order.
>
> >> stable identifier : a permanent ID that remains identical for the same data entity across renders
> >> random key churn : generating keys during render, forcing React to destroy and rebuild all DOM nodes
>
> *We should do this:*
> `items.map(item => (`
> `  <li key={item.id}><input /></li> {/* stable database ID */}`
> `))`
>
> *We should not do this:*
> `items.map(item => (`
> `  <li key={Math.random()}><input /></li> {/* rebuilds DOM */}`
> `))`

### Question 5: Reading props.key inside a row returns undefined

In your extracted `StoryItem` component, you want to render an HTML data attribute `data-id` for analytics tracking. Because you already passed `key={story.id}` to `<StoryItem />`, you attempt to read `props.key` inside the component:

```jsx title="Attempting to Read Key from Props"
function StoryItem(props) {
  return (
    <li data-id={props.key}> {/* Reading props.key yields undefined */}
      {props.story.title}
    </li>
  );
}
```

When you inspect the rendered HTML in developer tools, the `data-id` attribute is missing. In the console, React prints a warning: *"Warning: StoryItem: `key` is not a prop. Trying to access it will result in `undefined` being returned. If you need to access the same value within the child component, you should pass it as a different prop."*

**Why does reading props.key return undefined and print a console warning?**

---

**ANSWER**

**The code does not do what we wanted.** React reserves key for internal reconciliation and strips it from component props.

React treats `key` (and `ref`) as special reserved attributes. When JSX compiles into a React element object, React extracts `key` and stores it directly on the element descriptor (`element.key`). React intentionally excludes `key` from the `props` object.

React does this because `key` belongs to the parent list reconciler, not to the child component. The child component should not need to know where it sits in a list or what key was assigned to it. As a result, accessing `props.key` inside `StoryItem` evaluates to `undefined`.

If your child component needs the story's ID, you must pass it under a different, explicitly named prop such as `storyId={story.id}` or `id={story.id}`. Alternatively, pass the entire `story` object and read `story.id` directly from `props.story`.

```ascii title="React element object property separation"
React Element Object
-----------------------------------------------------------
{
  type: StoryItem,
  key: "story-101",        <-- Consumed by React reconciler
  props: {
    story: { ... },        <-- Passed to component function
    storyId: "story-101"   <-- Accessible as props.storyId
  }
}
```

> [!PRINCIPLE]
> **Principle 5: The key is not a prop, so pass the id again**
> React reserves the key prop for itself and excludes it from the component's props object. Reading props.key inside a component yields undefined and prints a console warning. When a component needs the item's identifier for links, attributes, or handlers, pass that identifier under a different prop name or read it from the data object.
>
> >> reserved prop : a prop like key that React consumes internally and excludes from component props
> >> explicit prop passing : passing an identifier under its own prop name so child components can read it
>
> *We should do this:*
> `function Item({ item, id }) {`
> `  return <li data-id={id}>{item.name}</li>; // reads id prop`
> `}`
>
> *We should not do this:*
> `function Item(props) {`
> `  return <li data-id={props.key}>{props.name}</li>; // undefined`
> `}`

### Step 1: First, we construct the parent feed container <src/App.jsx>

Step 1 constructs the parent application container: We declare our initial story collection as an array of structured objects, each carrying a permanent database `id` string (`'s1'`), a `title`, and a `category`. In `App.jsx`, we define our story collection and render a list of cards by calling `stories.map()`. Notice how we place the reserved `key={story.id}` prop directly on the outermost element returned by the callback: `<StoryItem key={story.id} story={story} />`. By passing the data object via `story={story}`, we establish a clear downward data flow while giving React the stable identity it requires for reconciliation.

```jsx title="App.jsx" startLine="1" continues="bottom"
export default function App() {
  const stories = [
    { id: 's1', title: 'Transit Accord Finalized', category: 'Politics' },
    { id: 's2', title: 'Clean Energy Approved', category: 'Environment' }
  ]; // Initial data collection

  return (
    <main className="feed-container">
```

Inside the main container, we render the header and embed our array transformation inside JSX curly braces. Notice that we use an expression body with an implicit return (`stories.map(story => <StoryItem ... />)`), guaranteeing that every story returns an element rather than `undefined`. Furthermore, each `<StoryItem />` receives two distinct props: the reserved `key={story.id}` prop consumed exclusively by React for reconciliation, and the `story={story}` prop containing the data object that the component displays.

```jsx title="App.jsx" startLine="11" continues="top"
      <header className="feed-header"><h1>Today's Dispatch</h1></header>
```

### Step 2: Next, we build the story item component <src/components/StoryItem.jsx>

Step 2 constructs the list item component: `StoryItem` is responsible for presenting a single story from the feed; it receives the `story` object through props. Notice that `StoryItem` does not attempt to read `props.key`, because React excludes `key` from props during element creation. Instead, `StoryItem` reads `story.title` and passes `story.category` to the child category label. To illustrate DOM node preservation, `StoryItem` renders an uncontrolled `<input placeholder="Add editor note..." />`. Because the input's value lives directly inside the browser DOM node, our stable key ensures that this physical node moves with its corresponding story when the list reorders.

### Step 3: Finally, we extract the category label <src/components/CategoryLabel.jsx>

Step 3 extracts the category label component: In newsroom interfaces, different categories require distinct styling, such as crimson for politics, emerald for environment, and slate for culture. By extracting this formatting into `CategoryLabel.jsx`, `StoryItem` remains focused on article layout while `CategoryLabel` manages category appearance. `CategoryLabel` receives the category string prop and applies a lowercase CSS class. Notice that `CategoryLabel` is a pure presentation component with zero local state and zero knowledge of list keys; list keys belong strictly at the collection level where array mapping occurs.

```jsx title="CategoryLabel.jsx" startLine="1"
export default function CategoryLabel({ category }) {
  const cls = category ? category.toLowerCase() : 'general'; // Tag modifier
  return (
    <span className={`tag tag-${cls}`}>
      {category}
    </span>
  );
}
```

### Where you will meet this

1. **Dynamic Content Feeds and Catalogs**: In news portals, social media feeds, and e-commerce catalogs, you map arrays of database records into card components, using permanent entity database IDs as keys to allow smooth insertion and sorting.
2. **Interactive Form Repeaters**: In invoice builders, survey creators, or recipe ingredient lists where users can add, remove, and reorder input rows, stable keys ensure that typed text and active focus never jump to the wrong row when an item is deleted.

### For the interview

> **The Interview Question:** How do you render a list from an array, and why does React demand a key on every item?

**1. The Hidden Signal**

The interviewer is probing whether you understand React's reconciliation engine and DOM node preservation, or merely memorized syntax to silence a console warning. A junior developer recites map syntax and claims keys make React faster. A senior engineer explains that keys establish persistent element identity across renders. They contrast positional diffing against key-based matching, explaining that keys allow React to move existing DOM nodes and preserve uncontrolled state during insertions and reordering.

**2. The Classic Trap**

The classic trap is reaching for the array index as a convenient key (`key={index}`). Candidates assume index keys are safe because they silence the console warning. But when an item is prepended at index 0, every existing item's index shifts by one. React compares index 0 to index 0, mutating the existing DOM node in place while leaving internal input text, focus, and audio playback attached to the wrong item. Another trap is generating keys on the fly with `key={Math.random()}`, which forces React to destroy and recreate the entire DOM tree on every single render.

**3. What is Actually Going On**

In React, you call `map()` on an array of data. Each call returns a JSX element descriptor, and React unpacks the resulting array in order. If the arrow function has a block body with curly braces, you must write an explicit `return`, or the list renders empty. React needs a unique, stable `key` on every element directly returned by `map()`. React uses that key to pair new elements with old elements on subsequent renders. When keys match, React moves the existing DOM node in place. Without keys, React compares items by array position, overwriting content and scrambling user inputs.

**4. Where It Gets Tricky**

What happens if a list row component tries to read `props.key`? React reserves `key` for its own reconciler and strips it from props; `props.key` evaluates to `undefined` and triggers a console warning. If the child needs the ID, pass it under a separate prop like `id={story.id}`. What happens if you need to render multiple sibling tags from a single mapped item without an extra wrapper `<div>`? You cannot use shorthand `<>...</>` because shorthand fragments cannot accept attributes; you must import `Fragment` from `'react'` and write `<Fragment key={story.id}>`. When is the array index safe to use? The index is safe only when the list is completely static: items are never inserted, deleted, filtered, or reordered.

### Glossary

- **Array Transformation**: Using methods like map to project an array of raw data objects into a new array of JSX element descriptors.
- **Key Prop**: A special string or number attribute passed to list elements that React uses to identify items across renders.
- **Positional Diffing**: React's fallback reconciliation behavior when keys are absent or based on array index, comparing elements purely by sequential position.
- **Element Identity**: The association between a React virtual element and its persistent browser DOM node established by a stable key.
- **Key Churn**: An antipattern where keys change on every render (such as from Math.random), forcing React to destroy and recreate all DOM nodes.
- **Reserved Prop**: A prop such as key or ref that React consumes internally for reconciliation and does not pass down to the component.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Array Transformation & Return Syntax

➔ ALWAYS use `array.map()` to project data arrays into JSX element arrays inside curly braces.

➔ IF using a block body (`=> { ... }`) in a `map` callback THEN write an explicit `return` statement to prevent rendering an empty list.

❒ Key Placement & Multi-Node Grouping

➔ ALWAYS place the `key` prop on the outermost element directly returned by the `map()` callback.

➔ IF an item returns multiple sibling nodes without a wrapper tag THEN use `<Fragment key={item.id}>` instead of shorthand `<>...</>`.

❒ Key Source & Reconciliation Safety

➔ ALWAYS use permanent, stable entity IDs from your data (such as database IDs) as list keys.

➔ NEVER use `Math.random()` to generate keys during render, which causes complete DOM teardown on every update.

➔ IF a list is dynamic THEN avoid array indices as keys to prevent state drift and input bugs.

**DO THIS:** use stable entity IDs as keys on the outermost element returned by map

```jsx right
{stories.map(story => (
  <StoryItem key={story.id} story={story} />
))}
```

**DO NOT DO THIS:** use array indices as keys for dynamic lists

```jsx wrong
{stories.map((story, index) => (
  <StoryItem key={index} story={story} />
))}
```
