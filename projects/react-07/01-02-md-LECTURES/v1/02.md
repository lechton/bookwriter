### The lowercase tag creates an unknown element and leaves the card blank

In standard JavaScript, developers follow camelCase conventions for almost every identifier. Helper functions are named `calculateTotal()`, variables are named `activeArticle`, and event handlers are named `handleClick()`. When starting out with React, developers naturally carry this muscle memory forward. You write a standard function named `articleCard()`, assemble headline and summary markup inside its body, and mount it in your layout as `<articleCard />`. The syntax looks clean, the code editor shows no red squiggles, and the terminal build finishes with zero errors.

When you refresh the browser page, the article card is completely missing. The terminal reports no errors, and the browser displays an empty white space. When you inspect the living page in browser Developer Tools, you find a bizarre custom tag: `<articlecard></articlecard>`. The browser treated your component tag as a native HTML element instead of executing your JavaScript function. Because the browser does not recognize this custom tag and your function was never invoked, the browser creates an empty unstyled DOM node, leaving the user with an empty screen.

To see this failure in concrete code, examine how a developer attempts to declare and mount an article card using standard JavaScript naming conventions:

```jsx title="Naive Lowercase Component Declaration"
function articleCard() {
  return (
    <article className="article-card">
      <h2>Morning Dispatch</h2> {/* headline never renders */}
    </article>
  );
}
export default function App() {
  return <articleCard />; // compiles to native HTML string literal
}
```

Notice what happened under the hood. When the JSX compiler parsed `<articleCard />`, it looked at the very first letter of the tag. Because the letter `a` is lowercase, the compiler assumed `<articleCard />` was a native HTML tag like `<article>`. It compiled the tag into `_jsx("articlecard", {})`. At runtime, React passed this string literal directly to `document.createElement("articlecard")`. The browser instantiated a generic, unstyled `HTMLUnknownElement` and appended it to the DOM. Your component function `articleCard()` sat completely idle in JavaScript memory.

When the browser encounters an unknown tag in markup, it does not throw an exception. The HTML specification dictates that unrecognized tag names instantiate a generic `HTMLUnknownElement` DOM node. Because the JSX compiler converted `<articleCard />` into a string literal request for an HTML element named `"articlecard"`, React instructed the browser to create that element directly. Your function `articleCard()` remained idle in JavaScript memory, completely untouched by React's rendering pipeline.

### Passing a component tag hands React a function reference

A React component is a regular JavaScript function that returns JSX markup describing a slice of the user interface. We use `export default` to mark the main component function of a file so that other files can import and reuse it. Unlike monolithic HTML files where markup and behavior live in separate documents, a component packages structure and presentation into a single cohesive unit.

In standard JavaScript, when we want a function to run immediately, we write parentheses after its name, such as `ArticleCard()`. Calling a function evaluates its lines right away and produces its return value synchronously. In React, our code does not call component functions directly. When we write `<ArticleCard />` in markup, we do not call `ArticleCard()`. Instead, JSX passes the function itself, known as a function reference, to React.

React takes custody of the function reference and enters its render phase. React decides when to call the component function based on what is happening in the application. When React renders the parent layout, it calls `ArticleCard`, inspects the JSX markup it returns, and builds the corresponding DOM elements on the screen. Because React orchestrates rendering, it can optimize screen updates, coordinate child lifecycles, and skip unnecessary work.

### Capital letters tell the compiler to build a component

Browsers natively recognize a fixed catalog of HTML tags, such as `<article>`, `<h2>`, `<p>`, and `<button>`. A web application combines these native building blocks with custom components created by developers. When a compiler parses markup containing both native tags and custom components, it must determine whether each tag represents a built-in browser element or a JavaScript function.

React resolves this distinction using a strict casing rule: PascalCase. Under PascalCase, the first letter of each compound word is capitalized, such as `ArticleCard`. When the JSX compiler converts markup into JavaScript code, it checks the casing of the tag name. If the tag begins with a lowercase letter, the compiler emits a string literal: `_jsx("article")`. If the tag begins with an uppercase letter, the compiler emits an unquoted variable identifier: `_jsx(ArticleCard)`.

If a developer accidentally names a component with a lowercase letter and mounts `<articleCard />`, the compiler treats it as a native HTML tag. React instructs the browser to create an element named `articlecard`, which the browser appends as an empty, unstyled DOM node. Because this is a frequent developer mistake, React prints two clear warning messages in the browser development console: one warning that the tag uses incorrect casing and should use PascalCase, and a second warning that the tag is unrecognized in the browser.

### JavaScript inserts semicolons after isolated return keywords

JavaScript includes a language mechanism called automatic semicolon insertion, or ASI. When the JavaScript parser reaches the end of a line, it checks whether the statement is complete. If the keyword `return` stands completely alone on its line, the parser treats the return statement as finished and automatically inserts an invisible semicolon immediately after it: `return;`.

If a developer writes `return` on one line and places multi-line JSX markup on the next line, the function immediately terminates and returns `undefined`. The JSX markup below the return statement is unreachable and never executes. React receives `undefined` for the component, paints nothing on the screen, and reports no error in the browser window. Bundlers such as esbuild emit a build warning alerting the developer that an expression is unreachable due to an automatically inserted semicolon.

To prevent automatic semicolon insertion when returning multi-line markup, developers open a parenthesis `(` on the exact same line as the `return` keyword. The opening parenthesis signals to the ECMAScript parser that the return expression is incomplete and continues across multiple lines. The parser waits until it encounters the matching closing parenthesis `);` before ending the statement, allowing the complete JSX tree to evaluate reliably.

### Defining a function inside another creates a new function on every run

In JavaScript, developers frequently declare helper functions inside other functions. A function declared inside the body of an outer function is called a nested function. Every time the outer function executes, JavaScript creates and allocates a brand-new inner function in memory with a distinct object reference.

When a developer defines a React component inside the body of another component, this allocation becomes an architectural bug. Every time the outer component renders, it defines a completely new component function. When React compares the new render with the previous one, it sees a different function reference at that position in the tree. React concludes that the old component was removed and an entirely new component was mounted in its place.

Because React treats different component functions as completely different elements, it destroys the existing DOM subtree and constructs new DOM nodes from scratch. If the component contains an interactive `<input>`, any text the user typed is immediately destroyed, and keyboard cursor focus is lost. To preserve component identity across renders, developers define every component at the top level of the file, outside and alongside other components.

### Question 1: Writing a component does not run it until markup uses it

A developer creates a new article card component and adds a logging statement to track when the function executes:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() {
  console.log('ArticleCard runs'); // logs each component execution
  return <article className="card">Morning Dispatch</article>;
}
```

In `App.jsx`, the developer defines the layout container without mounting the card. The browser renders the shell, and the console displays nothing. Next, the developer adds `<ArticleCard />` twice inside `App.jsx`. The browser displays two article cards, and the console logs "ArticleCard runs" twice.

**Who calls ArticleCard, and when does it run?**

---

**ANSWER**

**The code works as React intended.** React calls the function when another component renders markup that names it.

Declaring a component function does not execute it. In plain JavaScript, declaring `function ArticleCard()` allocates the function in memory, but nothing runs until code invokes it. In React, our application code never writes `ArticleCard()`. Instead, `App` returns markup containing `<ArticleCard />`. Writing the tag hands React a function reference.

While React renders `App`, it encounters the tag, invokes `ArticleCard()`, and takes custody of the returned `<article>` description. If `<ArticleCard />` is written twice, React calls the function twice, producing two separate `<article>` elements. If no markup references the component, React never executes the function. When inspecting the browser DOM in Developer Tools, the elements panel shows `<main>` and two `<article>` tags; the custom tag `<ArticleCard>` never exists in the DOM.

```ascii title="Function reference passed in markup compared to execution during render"
Markup in App:  <ArticleCard />  ---> Passes function reference to React
Render Phase:   React runs App   ---> React calls ArticleCard()
                                 ---> Receives <article> description
Browser DOM:    <main> contains <article>, never <ArticleCard>
```

> [!PRINCIPLE]
> **Principle 1: React calls a component when markup names its tag**
> When we write a component, our code does not call its function. We write its name as a tag, such as `<Card />`, inside another component's markup. The tag hands React a reference to the function. While React renders the parent, it calls the component function and places the returned HTML elements into the DOM. The browser DOM shows the HTML tags the function returned, never the component tag.
>
> *We should do this:*
> `function App() {`
> `  return <Card />; // React calls Card when rendering App`
> `}`

In our `ArticleCard` component, adding `console.log('ArticleCard runs')` proves who controls execution. When `App` returns an empty `<main>` container without `<ArticleCard />`, the function never runs, and the console stays silent. When `App` mounts `<ArticleCard />` twice, React evaluates `ArticleCard` twice, printing two log messages and placing two separate `<article>` elements into the DOM. In browser Developer Tools, the living tree displays two `<article>` nodes; the custom tag `<ArticleCard>` never exists in the browser DOM.

### Question 2: A lowercase component tag leaves an empty element in the DOM

A developer writes an article card using standard JavaScript camelCase conventions, naming the function `articleCard` and mounting it as `<articleCard />`:

```jsx title="articleCard (Naive Lowercase Declaration)"
function articleCard() {
  return (
    <article className="article-card">
      <h2>Morning Dispatch</h2> {/* headline never renders */}
    </article>
  );
}
export default function App() {
  return <articleCard />; // compiles to native HTML string literal
}
```

The build compiles cleanly, but the browser displays an empty space. When the developer inspects the DOM in Developer Tools, the elements panel shows `<articlecard></articlecard>`, and the development console displays two warnings about incorrect casing and an unrecognized tag.

**Why does articleCard compile cleanly while displaying nothing on the screen?**

---

**ANSWER**

**The code does not do what we wanted.** Lowercase tags instruct React to create native HTML elements rather than calling component functions.

When the JSX compiler parses `<articleCard />`, it inspects the first character of the tag name. Because `a` is lowercase, the compiler assumes it is a built-in browser element, compiling it to `_jsx("articlecard", {})`. At runtime, React passes that string to `document.createElement("articlecard")`. Because HTML allows custom elements, the browser instantiates an empty `HTMLUnknownElement` with no styles and no children. The JavaScript function `articleCard()` is never executed. React detects the mismatched casing and logs two warning messages to the development console.

The fix is capitalizing the first letter of the component name in both the function declaration and the JSX tag:

```jsx title="ArticleCard (PascalCase Correction)"
function ArticleCard() {
  return (
    <article className="article-card">
      <h2>Morning Dispatch</h2> {/* headline displays reliably */}
    </article>
  );
}
export default function App() {
  return <ArticleCard />; // emits unquoted function identifier
}
```

The uppercase initial letter tells the JSX compiler to emit an unquoted function identifier `_jsx(ArticleCard, {})`. React receives the function reference from memory, executes `ArticleCard()`, and paints the headline and summary to the screen.

```ascii title="Compiler AST branch on tag casing"
Lowercase 'a':
  <articleCard /> ---> _jsx("articlecard")
                  ---> document.createElement("articlecard")
                  ---> empty unknown DOM element

Uppercase 'A':
  <ArticleCard /> ---> _jsx(ArticleCard)
                  ---> React calls ArticleCard()
                  ---> living article DOM element
```

> [!PRINCIPLE]
> **Principle 2: Start every component name with a capital letter**
> In JSX, the first letter of a tag tells the compiler what to create. A lowercase tag tells the compiler to request a native HTML element from the browser, so the function never runs and the browser creates an empty unknown element. A capitalized name in **PascalCase** tells the compiler to reference our function, allowing React to run it and put its markup on the screen.
>
> >> PascalCase : a naming convention where the first letter of each word is capitalized
>
> *We should do this:*
> `function Card() {`
> `  return <article>Content</article>;`
> `}`
> `<Card />; // React runs capitalized component function`
>
> *We should not do this:*
> `function card() {`
> `  return <article>Content</article>;`
> `}`
> `<card />; // lowercase tag creates empty HTML element`

In `ArticleCard`, writing `function articleCard()` and rendering `<articleCard />` produced a silent failure on screen. The terminal reported no build errors, but the browser DOM contained an empty `<articlecard>` node with zero styles and zero child elements. Inspecting the browser console revealed two diagnostic warnings: one explaining that `<articleCard />` uses incorrect casing and should use PascalCase, and another noting that `<articleCard>` is unrecognized. Changing the name to `ArticleCard` in both the function declaration and the JSX tag allowed React to execute the function and display the headline and summary.

### Question 3: Starting markup on the line after return returns nothing

A developer formats `ArticleCard` by placing the `<article>` tag on a new line below `return` for visual clarity:

```jsx title="ArticleCard (Naked Multi-Line Return)"
export default function ArticleCard() {
  return // automatic semicolon inserted here
    <article className="article-card">
      <h2>Morning Dispatch</h2> {/* unreachable markup */}
    </article>;
}
```

In the browser, the article card is completely missing, with zero errors on the page or in the console. In the terminal build output, the bundler emits a warning that the following expression is not returned because of an automatically inserted semicolon.

**Why does placing markup on the line below return leave the card blank?**

---

**ANSWER**

**The code does not do what we wanted.** Automatic semicolon insertion causes the function to return undefined before reaching the markup.

JavaScript features automatic semicolon insertion. When the engine encounters a line break directly after `return` without an expression on that same line, it inserts a semicolon. The function evaluates `return;`, immediately terminating and returning `undefined`. The multi-line JSX expression below it is never evaluated. React receives `undefined` for `ArticleCard` and renders an empty slot, displaying nothing on the screen without throwing an error in the browser.

The fix is opening a parenthesis `(` on the exact same line as the `return` keyword:

```jsx title="ArticleCard (Parenthesized Return Fix)"
export default function ArticleCard() {
  return ( // opening parenthesis connects expression across lines
    <article className="article-card">
      <h2>Morning Dispatch</h2> {/* evaluates reliably */}
    </article>
  );
}
```

The opening parenthesis signals to the JavaScript engine that the return statement continues across multiple lines until the closing parenthesis `);`. Automatic semicolon insertion is prevented, and the component function evaluates the entire JSX tree.

```ascii title="Automatic semicolon insertion on isolated return"
return             ---> JavaScript inserts semicolon: return;
                        (terminates early and evaluates to undefined)
  <article> ...    ---> Unreachable code never evaluated

return (           ---> Parenthesis signals expression continuation
  <article> ...    ---> Evaluates complete JSX tree reliably
```

> [!PRINCIPLE]
> **Principle 3: Open parentheses on the same line as return for multi-line markup**
> When the `return` keyword stands alone on its line, JavaScript automatically inserts a semicolon after it. The function returns `undefined`, ignoring any markup written on following lines and leaving the screen completely blank. To return multi-line markup, open a parenthesis on the same line as `return` so JavaScript knows the expression continues.
>
> >> automatic semicolon insertion : JavaScript inserting a semicolon after an isolated return keyword
>
> *We should do this:*
> `return (`
> `  <article>Content</article> {/* evaluated as return expression */}`
> `);`
>
> *We should not do this:*
> `return // semicolon inserted here, returns undefined`
> `  <article>Content</article>; // unreachable code never evaluated`

In `ArticleCard`, formatting the component with `return` on line 2 and `<article>` on line 3 triggered automatic semicolon insertion. The JavaScript runtime inserted a semicolon after `return;`, causing `ArticleCard` to return `undefined` immediately. In the browser, the article card disappeared with zero console errors, while the terminal build warned that the following expression was unreachable. Adding opening and closing parentheses around the markup connected the return statement across lines, restoring the article card to the browser view.

### Question 4: Defining a component inside another component recreates it on every render

A developer notices that `ArticleCard` is only used inside `App.jsx`, so they define `function ArticleCard()` inside the body of `function App()`:

```jsx title="App.jsx (Nested Component Anti-Pattern)"
export default function App() {
  function ArticleCard() { // reallocated on every render of App
    return (
      <article className="article-card">
        <input placeholder="Feedback..." /> {/* input text wiped on render */}
      </article>
    );
  }
  return <ArticleCard />; // React destroys and rebuilds DOM subtree
}
```

On initial page load, the article card renders normally. But when `App` re-renders, any text typed into the `<input>` field vanishes, and keyboard cursor focus resets.

**Why does defining ArticleCard inside App cause its DOM elements to reset on subsequent renders?**

---

**ANSWER**

**The code does not do what we wanted.** Defining a component inside another creates a brand-new function identity on every parent render.

In JavaScript, declaring a function inside another creates a new function object in memory every time the outer function runs. When `App` renders again, it executes from the first line, allocating a fresh `ArticleCard` function with a different memory reference. React compares the previous element descriptor with the new element descriptor. Because the component function references differ, React concludes that an entirely different component type has replaced the old one.

React destroys the existing DOM subtree and constructs brand-new elements from scratch. Any internal DOM state, such as text typed into an `<input>` or active cursor focus, is immediately wiped out. In addition, rebuilding DOM nodes on every render is substantially slower than surgical property patching.

The fix is moving `function ArticleCard()` to the top level of the module file, outside and alongside `function App()`:

```jsx title="Top-Level Component Declaration"
function ArticleCard() { // single stable function identity
  return (
    <article className="article-card">
      <input placeholder="Feedback..." /> {/* input text retained */}
    </article>
  );
}
export default function App() {
  return <ArticleCard />; // preserves living DOM elements
}
```

When declared at the top level, `ArticleCard` retains a stable function reference across every render of `App`. React recognizes that the component type is identical, updates only what changed, and preserves existing DOM elements, user input text, and cursor focus.

```ascii title="Nested component definition compared to top-level declaration"
Nested:
  App() render 1 ---> creates ArticleCard_A
  App() render 2 ---> creates ArticleCard_B (new identity -> destroys DOM)

Top-level:
  Module loads   ---> creates ArticleCard once
  App() render 1 ---> uses ArticleCard
  App() render 2 ---> uses ArticleCard (stable identity -> preserves DOM)
```

> [!PRINCIPLE]
> **Principle 4: Define every component at the top level of the file**
> Defining a component inside another component creates a new function object every time the outer component runs. Because React sees a different component type on every render, it destroys the existing DOM elements and builds new ones from scratch, wiping out typed input text and resetting focus. Always declare components at the top level of the file so their identity remains stable.
>
> >> nested function : a function defined inside the body of another function
>
> *We should do this:*
> `function Child() {`
> `  return <p>Content</p>; // stable function identity`
> `}`
> `function Parent() {`
> `  return <Child />; // reuses existing DOM across renders`
> `}`
>
> *We should not do this:*
> `function Parent() {`
> `  function Child() { return <p>Content</p>; } // recreated every run`
> `  return <Child />; // React destroys and rebuilds DOM`
> `}`

When `ArticleCard` was defined inside `App`, the initial mount looked identical to a top-level component. But when `App` rendered a second time, React evaluated `App` from the top, allocating a fresh `ArticleCard` function in memory. React compared the previous element descriptor with the new one and observed two different function references. React concluded that a different component type had replaced the old one, destroying the existing `<article>` node and constructing a new one. Moving `ArticleCard` to the top level gave the component a permanent function identity, allowing React to update the DOM surgically without rebuilding elements.

### Step 1: First, we construct the article card component <ArticleCard.jsx>

We construct the standalone article card component `ArticleCard.jsx` to encapsulate headline and summary copy into an isolated, reusable function. Notice that the function name begins with an uppercase letter: `ArticleCard`. This PascalCase naming guarantees that the JSX compiler treats `<ArticleCard />` as a custom component rather than an unknown HTML tag. The component function contains no hardcoded DOM queries, mutates no external variables, and returns semantic HTML elements wrapped in a single root `<article>` tag.

When returning multi-line JSX markup from a component function, you encounter a foundational JavaScript syntax crossroad:
- **Option 1 (The Foundational Way)**: Write a naked multi-line return without wrapping parentheses, exposing the code to automatic semicolon insertion.
- **Option 2 (The Modern Idiomatic Way)**: Wrap the multi-line JSX expression in parentheses, signaling to the parser that the return expression continues across lines.

First, examine Option 1 with a naked multi-line return:

```jsx title="Option 1: The Foundational Way (Naked Multi-Line Return)"
export default function ArticleCard() {
  return // parser automatically inserts semicolon here
    <article className="article-card">
      <h2>Morning Dispatch</h2> {/* unreachable code never evaluated */}
    </article>;
}
```

In Option 1, the JavaScript engine encounters a newline immediately after the `return` keyword. Under the rules of automatic semicolon insertion, the parser inserts a semicolon after `return;`. The function immediately terminates and returns `undefined`. The JSX markup on the following line is never evaluated, and the browser displays a blank card with zero errors.

Now, examine Option 2 with defensive parenthesized return wrapping:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() {
  return ( // parentheses prevent automatic semicolon insertion
    <article className="article-card">
      <h2 className="headline">Morning Dispatch</h2> {/* story headline text */}
      <p className="summary">Civic updates.</p> {/* story summary */}
    </article>
  );
}
```

In Option 2, the opening parenthesis `(` tells the ECMAScript parser that the return expression continues across multiple lines. Semicolon insertion is prevented, and the component function reliably evaluates the entire JSX tree. Notice how `ArticleCard.jsx` functions as a pure presentation component: it owns zero state, requires no external DOM lookups, and cleanly packages the news card into a predictable, reusable unit.

Notice how `ArticleCard.jsx` satisfies the core architectural rules of component anatomy:
1. It uses PascalCase naming (`ArticleCard`) so the compiler treats it as a custom component.
2. It returns a single root container element (`<article>`) satisfying JavaScript expression return grammar.
3. It encloses its multi-line return inside parentheses to neutralize automatic semicolon insertion traps.
4. It is declared at the top level of the file so its component identity remains stable across renders.

### Step 2: Finally, we mount the card declaratively inside <App.jsx>

To complete our application layout, we mount `ArticleCard.jsx` inside the root container `App.jsx`. In standard JavaScript development, inserting a new widget required querying an existing container with `document.querySelector` and appending elements imperatively. In React, the entire document organizes into a declarative hierarchy. Notice that `App.jsx` imports `ArticleCard` as an unquoted JavaScript identifier and mounts it using the self-closing tag `<ArticleCard />`. We do not call `ArticleCard()` directly with parentheses; writing `<ArticleCard />` tells React's mounting engine to register an independent element in the render tree and execute the component during the render pass.

```jsx title="App.jsx"
import ArticleCard from './components/ArticleCard.jsx'; // imports component

export default function App() {
  return (
    <main className="app-shell">
      <ArticleCard /> {/* mounts component declaratively as tag */}
    </main>
  );
}
```

When React evaluates `App`, the JSX compiler transforms `<ArticleCard />` into `_jsx(ArticleCard, {})`. React attaches the component to its virtual tree, executes `ArticleCard()` in memory, and paints the returned `<article>` node inside `<main>` in a single atomic operation. Because the component follows PascalCase naming and declarative invocation, the browser receives living, semantic DOM elements without manual query scripts or silent lowercase failures.

Notice how `App.jsx` establishes clean declarative boundaries:
1. It imports `ArticleCard` as a first-class function identifier from its module path.
2. It mounts `<ArticleCard />` as a declarative JSX element, registering an independent component boundary.
3. It performs zero manual DOM querying or element manipulation, delegating page mounting to React.

### Where you will meet this

1. **Design System Component Libraries**: When authoring buttons, modals, input cards, and layout grids in a shared component library, every component must enforce PascalCase naming to ensure downstream consuming applications can mount them as standard JSX tags without compiler confusion.

### For the interview

> **The Interview Question:** What is a React component, and what rules govern how you write and name one?

**1. The Hidden Signal**

The interviewer is not merely testing whether you know how to write a function keyword. They are probing whether you understand how JSX transpiles into function calls and why React insists on orchestrating execution. A junior candidate answers that capitalization is just an aesthetic style convention. A senior engineer explains that the JSX compiler branches on Unicode casing: lowercase tags compile to string literals for native elements, while uppercase tags compile to unquoted function references that React invokes during render.

**2. The Classic Trap**

The classic trap is claiming that you can call component functions directly inside curly braces `{ArticleCard()}` to save typing. While executing the function returns markup in simple examples, calling a component directly strips its component boundary, inlining child markup into the parent and breaking React's ability to isolate updates or manage Hooks. Another frequent trap is defining helper components inside parent render functions, which causes React to destroy and rebuild DOM trees on every render pass.

**3. What is Actually Going On**

A React component is a standard JavaScript function that returns JSX markup. We never invoke it directly; we write it as a tag, like `<ArticleCard />`, inside another component. That tag passes a function reference to React. When React renders the parent, it executes the function and commits the resulting elements to the DOM. Four concrete rules govern component authoring: (1) start names with a capital letter in PascalCase so the compiler emits function references, (2) open parentheses on the same line as return so automatic semicolon insertion does not return undefined, (3) declare components at module top level so function identity remains stable across renders, and (4) return a valid single root element or Fragment.

**4. Where It Gets Tricky**

Where this gets tricky in production is diagnosing subtle silent bugs. A lowercase tag compiles cleanly without terminal syntax errors; the only clues are an empty custom tag in DevTools and two development console warnings. Similarly, an unparenthesized multi-line return renders a blank component without throwing a browser runtime error, though modern bundlers emit build warnings. Finally, defining components inside parent render functions works deceptively on initial mount, only to destroy user input text and reset focus rings the moment parent state triggers a second render.

### Glossary

- **Component**: A self-contained JavaScript function whose name starts with a capital letter and returns a description of user interface markup in JSX.
- **PascalCase**: A naming convention where the first letter of each compound word is capitalized, used by the JSX compiler to distinguish custom component functions from native HTML elements.
- **Function Reference**: An unquoted reference to a JavaScript function in memory, passed to React so the runtime can execute the function during render.
- **Automatic Semicolon Insertion**: A JavaScript language feature that inserts an invisible semicolon after an isolated return keyword, causing functions to return undefined if markup starts on the next line.
- **Nested Component**: A component function defined inside the body of another component, causing React to treat it as a brand-new component type and rebuild its DOM on every render.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Component Naming and Compiler Casing

➔ ALWAYS name custom components in PascalCase so the JSX compiler emits an unquoted function identifier rather than an HTML string literal.

➔ NEVER define component functions in lowercase or camelCase because the browser treats lowercase tags as native elements and fails silently.

❒ Return Statement Layout

➔ ALWAYS wrap multi-line JSX return statements in parentheses with the opening parenthesis on the same line as the return keyword.

➔ NEVER place multi-line JSX markup on the line after return without an opening parenthesis because automatic semicolon insertion will return undefined.

❒ Component Declaration Scope

➔ ALWAYS declare component functions at the top level of the file so their function identity remains stable across renders.

➔ NEVER define component functions inside the body of another component because React will destroy and reconstruct its DOM elements on every render.

**DO THIS:** name custom components in PascalCase, open parentheses on the return line, and declare at module top level

```jsx right
function ArticleCard() {
  return (
    <article className="article-card">
      <h2>Morning Dispatch</h2>
    </article>
  );
}
export default function App() {
  return <ArticleCard />;
}
```

**DO NOT DO THIS:** name components in lowercase, place markup below bare return, or nest component definitions

```jsx wrong
export default function App() {
  function articleCard() {
    return
      <article className="article-card">
        <h2>Morning Dispatch</h2>
      </article>;
  }
  return <articleCard />;
}
```
