# Lecture 1: What is React and the Declarative Model
> INTERVIEW QUESTION | ❱ CORE | What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

1. You built a page header that shows the reader's name in a greeting and in a badge.
2. The reader changes the name, your script updates the greeting, and the badge keeps the old name.
3. How do we make every place on the page show the new name?

### Plain JavaScript is imperative, React is declarative

Every website shows values that change: the reader's name after they edit their profile, the number of items in a shopping cart, the temperature in a city. When a value changes, the page must show the new value everywhere it appears. So every web developer meets the same question: when a value changes, how does the page change with it?

The browser does not show your HTML file directly. It reads the file, builds an object in memory for every tag, and draws the screen from those objects. Together they are called the **DOM** (Document Object Model). HTML is the text you write; the DOM is what the browser builds from it and keeps while the page is open. So changing the page always means updating the DOM.

There are two ways to update the DOM when a value changes.

**The first way is imperative programming**, which you know from plain JavaScript: you give the browser commands. You find the element, then you set its text:

```js title="Imperative: find the element, set its text"
const greeting = document.getElementById('greeting'); // find it
greeting.textContent = 'Welcome back, Elena Ruiz'; // set its text
```

The first line asks the browser for the element whose `id` is `greeting`. The second line replaces the text inside that element. The browser does exactly what each line says and nothing more, so every other element on the page stays as it was. That is why it is called imperative programming: you give the browser every command yourself. The word comes from the Latin *imperare*, "to command", the same root as *emperor*. Like an emperor, your code orders every step: find this element, set that text. It fits well when one element changes in one place, like a clock in a corner of the page. It fits badly when the same value appears in many places. If the name also appears in a badge, the badge needs its own two lines, and if you forget them, the badge keeps the old name.

**The second way is declarative programming**, which this chapter teaches: instead of commands, you declare what the element should show:

```jsx title="Declarative: what the greeting shows"
<p>Welcome back, {readerName}</p>
```

This looks like HTML, but one part is new: `{readerName}`. The curly braces mark a place in the markup where a JavaScript value goes, and here that place holds the variable `readerName` (Lecture 4 shows everything such a place can hold). Notice what is missing: there is no line that finds the `<p>`, and no line that sets its text. React reads the description, builds the `<p>` on the page, and puts the current value of `readerName` inside it. When `readerName` holds "Elena Ruiz", the page shows "Welcome back, Elena Ruiz". That is why it is called declarative programming: you declare the result, and React updates the DOM to match it. The word comes from the Latin *declarare*, "to make clear, to announce": you announce what the page should show, and React works out the steps.

The badge works the same way:

```jsx title="Declarative: what the badge shows"
<span>Subscriber: {readerName}</span>
```

The greeting and the badge read the same `readerName`. There is no second command to forget, so the two places cannot show different names.

> [!WAYS] Two ways to update the DOM when a value changes
>
> (1) Update the DOM with **imperative programming** (plain JavaScript): you give the browser every command yourself, finding each element and setting its text.
>
> (2) Update the DOM with **declarative programming** (this chapter): you declare what each element should show, and React updates the DOM to match.

React still lets you reach one element directly for the few jobs declarative code cannot do, such as moving the cursor into a search box. Lecture 30 covers that.

React is a JavaScript library for building pages out of components. In this chapter, we write our first component, `SiteHeader`, which describes the whole header from one value, `readerName`. We will see why imperative code misses an element, why a value must live in one variable, and what React changes on the page when the value changes. At the end, we compare the two ways again.

In this lesson the name stays fixed in the code. Lecture 14 shows how a value changes while the page is open, and Lecture 15 follows, step by step, how React then updates the page. Other lessons grow this one component: Lecture 5 splits a page into many components, Lecture 6 passes values from one component to another, and Lecture 12 explains why a component must only describe the page and never change it.

This lesson answers three questions:

- **In plain JavaScript I find each element and change its text. What do I write instead in React?**
- **The name shows in two places. Do I write it twice?**
- **When the name changes, does React rebuild the whole header and wipe what the reader typed?**

You need only HTML and plain JavaScript:

- **HTML**: Tags such as `<p>` and `<span>` describe the page, and an `id` such as `id="greeting"` gives one tag a name.
- **Plain JavaScript**: `const` and `let` store a value in a variable, and `+` joins two strings into one.

### The browser keeps the page as a tree of objects

The DOM from the opening is a tree: its objects nest the same way the tags nest in the HTML file. Each object in it is called a **DOM node**. What you see on the screen is drawn from the DOM, so changing a node changes the page.

Plain JavaScript changes the page through these nodes. Here are the three tools the questions use:

```js title="Three plain JavaScript tools"
const greeting = document.getElementById('greeting'); // find one node
greeting.textContent = 'Welcome back, Elena'; // replace its text
const header = document.getElementById('header');
header.innerHTML = '<p>Welcome back, Elena</p>'; // replace all inside
```

`document.getElementById` searches the DOM for the node with that `id` and gives it back. `textContent` replaces the text inside one node. `innerHTML` is bigger: it takes a string of HTML, throws away every node inside the element, and builds new nodes from the string. The browser does each of these at the moment the line runs.

### A component is a function that returns a description

In React, the description of the page lives in a **component**: a JavaScript function whose name starts with a capital letter and which returns markup. Lecture 2 gives the full rules. Here is the header as a component:

```jsx title="SiteHeader returns a description"
export default function SiteHeader() {
  const readerName = 'Elena'; // the name, stored once
  return (
    <header className="site-header">
      <p>Welcome back, {readerName}</p>
      <span>Subscriber: {readerName}</span>
    </header>
  );
}
```

`SiteHeader` is an ordinary function. The two words in front of it, export default, let another file use it (Lecture 8). Inside it, `readerName` holds the name. The function returns markup that looks like HTML: a `<header>` with a greeting and a badge, and `{readerName}` in both. This markup is called **JSX**. It is JavaScript, not HTML, so a few names differ: the HTML attribute `class` is written `className`. Lecture 3 shows what JSX becomes and why.

Our code never calls `SiteHeader` and never touches the DOM. React calls the function, reads the description it returns, and builds the DOM nodes from it: a `<header>`, a `<p>` with "Welcome back, Elena", and a `<span>` with "Subscriber: Elena". React builds them inside one element of the HTML page that we hand to it, and Lecture 9 shows how. A component returns what the page should show, and React builds the page from it.

### Principles of React: Declarative Synchronization

### Question 1: Finding elements by identifier misses unqueried widgets

The site header displays a personalized greeting and a subscriber status badge. In plain JavaScript, an update script searches for elements by string identifier and updates their text content directly:

```js title="updateHeaderUser (Naive Script)"
function updateHeaderUser(name) {
  const greeting = document.getElementById('greeting');
  if (greeting) {
    greeting.textContent = 'Welcome back, ' + name; // updates greeting
  }
  // The badge query was omitted from the script
}
```

When we run `updateHeaderUser('Elena Ruiz')`, the greeting updates to "Welcome back, Elena Ruiz", while the badge remains stuck on "Subscriber: Elena".

**Why does updating the name update the greeting while leaving the badge on the old text?**

---

**ANSWER**

**The code does not do what we wanted.** The imperative script updated one queried element and skipped the badge.

In plain JavaScript, our code must query every matching DOM node by hand. If a script searches for `greeting` but forgets `badge`, the browser leaves the unqueried element unchanged. The greeting displays the new name while the badge displays the old name, creating immediate state drift between memory and the screen.

In React, we do not query elements by identifier. Instead, we write `SiteHeader`, a component function that returns markup describing the entire header for the current data:

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const readerName = 'Elena Ruiz'; // authoritative value in memory
  return (
    <header className="site-header">
      <p id="greeting">Welcome back, {readerName}</p>
      <span id="badge">Subscriber: {readerName}</span>
    </header>
  );
}
```

React calls `SiteHeader`, reads the returned description, and builds the real DOM elements on the page. Both the greeting and the badge display "Elena Ruiz". Because our code never queries the DOM, no element can be skipped or left behind.

```ascii title="Imperative hunting compared to declarative description"
Imperative DOM Scripting:
App Code  --- document.getElementById('greeting') ---> [ DOM: Greeting ] updated
App Code  - - - (forgot badge query) - - - - - - - - > [ DOM: Badge ]    STALE

Declarative React Component:
Data ('Elena Ruiz') ---> SiteHeader() ---> [ Description Tree ] ---> DOM updated
```

> [!PRINCIPLE]
> **Principle 1: Describe what the page shows for the data instead of changing elements by hand**
> In plain JavaScript, code searches the document for each element and changes its text directly. If an update misses one element, the screen shows old data. In React, a component function returns a description of the markup for the current data, and React builds the page from that description. We describe what the interface shows instead of writing commands to find and change elements.
>
> *We should do this:*
> `function Header() {`
> `  const name = 'Elena';`
> `  return <h1>Welcome, {name}</h1>; // React builds element`
> `}`
>
> *We should not do this:*
> `function updateHeader(name) {`
> `  const el = document.getElementById('name');`
> `  if (el) el.textContent = name; // misses unqueried elements`
> `}`

In our `SiteHeader` component, writing plain JavaScript required `updateHeaderUser` to search for `greeting` and `badge` by their string identifiers. Forgetting `badge` left the screen showing "Elena" in the badge alongside "Elena Ruiz" in the greeting. In React, we write `SiteHeader` as a function that returns the complete header markup. React calls `SiteHeader`, reads the returned description, and constructs the DOM elements on the screen. Because our code never queries the DOM, no element can be skipped or left behind.

### Question 2: The name shows in two places across the header

The reader's name appears inside both the greeting paragraph and the subscriber badge. A developer pastes static markup into the component and hardcodes the initial name into the badge:

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const readerName = 'Elena Ruiz'; // updated local variable
  return (
    <header className="site-header">
      <p id="greeting">Welcome back, {readerName}</p>
      <span id="badge">Subscriber: Elena</span> {/* hardcoded text */}
    </header>
  );
}
```

When React renders this component, the greeting paragraph displays "Welcome back, Elena Ruiz", but the badge displays "Subscriber: Elena".

**Why does the badge still display Elena after the variable was changed to Elena Ruiz?**

---

**ANSWER**

**The code does not do what we wanted.** The badge markup contains a hardcoded string instead of reading the variable.

Typing static text into markup duplicates data. The greeting paragraph reads the variable `readerName`, so it displays "Elena Ruiz". But the badge contains the literal text "Subscriber: Elena", completely detached from the variable. When the variable updates, the hardcoded string remains frozen.

The fix is to store the name in one local variable and read that variable in every place that displays it using curly braces `{readerName}`:

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const readerName = 'Elena Ruiz'; // single source of truth
  return (
    <header className="site-header">
      <p id="greeting">Welcome back, {readerName}</p>
      <span id="badge">Subscriber: {readerName}</span>
    </header>
  );
}
```

The variable `readerName` serves as a single source of truth. Both the greeting and the badge derive their text from that single variable. When `readerName` changes to "Elena Ruiz", both elements update together because both are built from the same value.

```ascii title="Single variable read in multiple elements"
Duplicate static text:
Variable ('Elena Ruiz') ---> [ Greeting: Elena Ruiz ]
Hardcoded String        ---> [ Badge: Elena ] (state drift)

Single source of truth:
Variable ('Elena Ruiz') ----+---> [ Greeting: {readerName} ] (Elena Ruiz)
                            |
                            +---> [ Badge: {readerName} ]    (Elena Ruiz)
```

> [!PRINCIPLE]
> **Principle 2: Keep each value in one variable and read it everywhere it appears**
> When a value appears in more than one place on the screen, do not type it into the markup more than once. Store the value in a single local variable and read that variable in every place that shows it using curly braces. Because every part of the markup reads from this single source of truth, all parts update together and can never disagree.
>
> *We should do this:*
> `function Header() {`
> `  const name = 'Elena'; // single source of truth`
> `  return (`
> `    <div>`
> `      <h1>Welcome, {name}</h1>`
> `      <span>Subscriber: {name}</span>`
> `    </div>`
> `  );`
> `}`
>
> *We should not do this:*
> `function Header() {`
> `  const name = 'Elena';`
> `  return (`
> `    <div>`
> `      <h1>Welcome, {name}</h1>`
> `      <span>Subscriber: Elena</span> {/* fixed text drifts */}`
> `    </div>`
> `  );`
> `}`

In `SiteHeader`, pasting the static text "Subscriber: Elena" directly into the badge markup caused state drift the moment `readerName` changed to "Elena Ruiz". The greeting read the updated variable, while the badge stayed frozen on the old literal string. Replacing the fixed text with `{readerName}` ensures that both elements read the exact same variable. When `readerName` is updated in our code, both the greeting and the badge reflect the new name simultaneously.

### Question 3: Rebuilding the header wipes the search box

The site header contains a search input alongside the user greeting. The user types "elections" into the search box. To update the user name, an imperative script replaces the container HTML with a template string:

```js title="updateHeaderWithInput (Naive Script)"
function updateHeaderWithInput(name) {
  const header = document.getElementById('header'); // finds container node
  const html = '<p>Welcome, ' + name + '</p><input placeholder="Search..." />';
  header.innerHTML = html; // wipes living input element
}
```

The script runs, and the name updates to "Elena Ruiz". But the text "elections" disappears from the search box, and keyboard focus drops back to the document body.

**Why does updating the name wipe out the search text and lose keyboard cursor focus?**

---

**ANSWER**

**The code does not do what we wanted.** Assigning to `innerHTML` destroyed the input element and created a brand-new one.

When JavaScript assigns a new string to `innerHTML`, the browser engine throws away all existing DOM nodes inside that container. Even though the new HTML string includes an `<input>` tag, the browser constructs a brand-new DOM element from scratch. The typed text belonged to the destroyed element, and the active cursor belonged to that destroyed node. As a result, the search query is lost and keyboard focus is reset to the page body.

In React, we describe the entire header from data, including the input element:

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const readerName = 'Elena Ruiz'; // authoritative value in memory
  return (
    <header className="site-header">
      <p id="greeting">Welcome back, {readerName}</p>
      <span id="badge">Subscriber: {readerName}</span>
      <input placeholder="Search..." /> {/* node identity preserved */}
    </header>
  );
}
```

When data changes, React does not rebuild the container with `innerHTML`. Instead, React compares the new description with the previous one. React sees that the `<input>` element has not changed. It applies the minimal necessary operations: it updates only the text nodes containing the reader name. The `<input>` element remains the exact same DOM node on the page, so the typed query and active cursor focus stay completely intact.

```ascii title="innerHTML compared to React update"
Destructive innerHTML:
Old: [ <p>Elena</p> ] [ <input> "elections" (focused) ]
      | container.innerHTML replaces nodes
New: [ <p>Elena Ruiz</p> ] [ <input> "" (focus lost) ] (new DOM nodes)

React surgical update:
Old: [ <p>Elena</p> ] [ <input> "elections" (focused) ]
      | React diffs descriptions and patches text node only
New: [ <p>Elena Ruiz</p> ] [ <input> "elections" (focused) ] (same input node)
```

> [!PRINCIPLE]
> **Principle 3: When data changes, React updates only the text that differs**
> When data updates, React does not destroy and recreate elements on the page. Replacing containers with `innerHTML` destroys living elements, wiping typed input text and losing cursor focus. Instead, React compares the new description with the previous one and applies the minimal changes needed. Unchanged elements remain in place, so an input field keeps what the user typed and keeps its focus.
>
> *We should do this:*
> `function Header() {`
> `  const name = 'Elena';`
> `  return (`
> `    <div>`
> `      <h1>Welcome, {name}</h1> {/* updates text */}`
> `      <input placeholder="Search..." /> {/* keeps focus */}`
> `    </div>`
> `  );`
> `}`
>
> *We should not do this:*
> `function updateHeader(name) {`
> `  const container = document.getElementById('header');`
> `  const html = '<h1>Welcome, ' + name + '</h1><input>';`
> `  container.innerHTML = html; // wipes input text and focus`
> `}`

In plain JavaScript, assigning a new string to `header.innerHTML` tore down the existing search box. The user's typed search query "elections" vanished, and the active cursor was thrown out of the input. In React, changing `readerName` from "Elena" to "Elena Ruiz" causes React to compare the new description with the old one. React observes that the `<input>` element and the layout container are unchanged. It mutates only the text nodes containing the name. The search box keeps its text, its event listeners, and its active cursor focus.

### Step 1: First, we declare the site header component <SiteHeader.jsx>

We construct `SiteHeader.jsx` to establish the declarative foundation for our header. Instead of writing separate HTML tags and later writing scripts to query them, we define a component function that returns our layout description.

We store the reader's name in a single local variable, `readerName`, and project it into both the greeting paragraph and the subscriber badge using curly braces. Notice that our code contains zero calls to `document.getElementById` and zero calls to `textContent`.

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const readerName = 'Elena Ruiz'; // authoritative value in memory
  return (
    <header className="site-header">
      <p id="greeting">Welcome back, {readerName}</p>
      <span id="badge">Subscriber: {readerName}</span>
    </header>
  );
}
```

Because `SiteHeader` describes its output directly from `readerName`, state drift is eliminated at the architectural level. If a developer changes `readerName` in memory, both widgets update simultaneously during the next render.

### Step 2: Next, we add the interactive search input <SiteHeader.jsx>

We enhance `SiteHeader.jsx` by adding a search input `<input placeholder="Search articles..." />` alongside our greeting and badge. In naive JavaScript updates using `innerHTML`, appending or modifying text inside the header destroys all living input elements, clearing whatever the reader typed and resetting cursor focus.

In React, the input is declared directly as part of the component description. When reader data updates, React keeps the exact same `<input>` DOM node on the screen, preserving user text and keyboard focus without manual intervention.

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const readerName = 'Elena Ruiz'; // authoritative value in memory
  return (
    <header className="site-header">
      <p id="greeting">Welcome back, {readerName}</p>
      <span id="badge">Subscriber: {readerName}</span>
      <input placeholder="Search..." /> {/* focus preserved */}
    </header>
  );
}
```

Notice that static elements, dynamic text, and interactive inputs coexist cleanly within a single component. React manages the boundary between unchanging nodes and dynamic text nodes automatically.

### Step 3: Finally, we mount the site header inside <App.jsx>

To complete our application, we mount `SiteHeader` inside the root component `App.jsx`. In standard JavaScript applications, assembling a page often required separate initialization scripts to locate root containers and inject HTML strings.

In React, the entire user interface organizes into a unified component hierarchy. `App.jsx` acts as the primary root container, embedding `SiteHeader` into the application layout. When React renders `App`, it evaluates the component tree in memory and constructs the resulting DOM elements in a single, predictable operation.

```jsx title="App.jsx"
import SiteHeader from './components/SiteHeader.jsx'; // header component

export default function App() { // renders application root
  return (
    <main className="app-container">
      <SiteHeader /> {/* mounts declarative header at root */}
    </main>
  );
}
```

The application now runs as a cohesive declarative tree. React mounts the component into the browser document and manages all future updates through description diffing rather than manual DOM manipulation.

### Where you will meet this

1. **Multi-Widget Navigation Bars**: When a user logs in, their display name, notification count, and account status must appear synchronously across desktop navigation bars, sidebar drawers, and profile banners. Declarative components ensure that every element reflects the exact same data without manual element queries.
2. **E-Commerce Shopping Carts**: The number of items in a user's cart appears in the header cart pill, the checkout button badge, and the order summary sidebar. Reading cart count from a single variable guarantees that item totals match across the entire screen.
3. **Search Filters and Form Headers**: Live search bars, active filter pills, and result counters all display aspects of the current query. Declarative rendering ensures that updating the filter count never wipes the user's active search input or interrupts cursor focus.

### For the interview

> **The Interview Question:** What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

**1. The Hidden Signal**

The interviewer is not merely testing whether you know how to write a component function. They are probing whether you understand the fundamental architectural shift from imperative DOM mutation to declarative state synchronization. A junior developer talks about convenience or shorter syntax. A senior engineer explains that imperative DOM scripting couples application logic directly to fragile document queries, creating inevitable state drift when data appears in multiple widgets. They articulate that React models the user interface as a pure projection of data, computing minimal necessary DOM mutations in memory to preserve element identity and input focus.

**2. The Classic Trap**

The classic trap is claiming that "React is faster than the real DOM because the Virtual DOM has zero performance cost." That claim fails the interview. A well-written, hand-optimized DOM script targeting a single node can execute faster than React's component evaluation and diffing passes. React's true value is predictable synchronization, not raw micro-benchmark speed. Another dangerous trap is telling the interviewer that React throws away and rebuilds the DOM on every render. If React rebuilt the DOM tree, every active text input would lose focus and unsubmitted form state would vanish. React diffs descriptions in memory and surgically mutates only changed text nodes.

**3. What is Actually Going On**

In plain JavaScript, we write imperative commands that find specific elements by identifier and mutate them step by step. If our code misses one element, the screen shows stale data.

In React, we write component functions that return JSX describing what the screen should look like for the current data. React calls our component, evaluates the returned description, and constructs the real DOM elements.

When a value like `readerName` updates, React calls the component again, compares the new description with the previous one, and applies the minimal necessary operations. It changes only the specific text that differs, leaving living DOM nodes and active keyboard focus completely intact.

**4. Where It Gets Tricky**

Where this model gets tricky in production is when developers carry old imperative habits into React applications. Attempting to query DOM nodes directly with `document.getElementById` inside a React component bypasses React's synchronization pipeline, creating severe conflicts between React's in-memory model and physical browser pixels. Similarly, using `innerHTML` or destructive container updates inside a component destroys living DOM node identity, wiping input selections and breaking accessibility focus rings. Embracing React means fully trusting declarative data projection and delegating physical DOM mutations entirely to the library.

### Glossary

- **DOM** (Document Object Model): The objects the browser builds in memory from the HTML, one for every tag, arranged as a tree. The screen is drawn from the DOM, so changing the page means updating the DOM.
- **Imperative programming**: Code that gives the browser every command itself, such as finding an element and setting its text. From the Latin *imperare*, "to command".
- **Declarative programming**: Code that declares what the page should show for the current data, while React updates the DOM to match. From the Latin *declarare*, "to make clear, to announce".
- **State Drift**: A defect where two or more elements on the screen show conflicting or out-of-date information because manual updates failed to synchronize every matching node.
- **Component**: A JavaScript function whose name starts with an uppercase letter that returns a description of user interface markup in JSX.
- **Single Source of Truth**: The architectural practice of storing a piece of data in one place and reading that exact value everywhere it is displayed to prevent disagreement.
- **Minimal Necessary Operations**: React's strategy of comparing new interface descriptions with previous ones and updating only the specific text nodes or attributes that changed.

➔ IF multiple elements display the same reader identity THEN read the value via JSX curly braces so that widgets can never drift out of sync.

❒ DOM Node Identity and Input Focus

➔ ALWAYS delegate DOM mutation to React's diffing engine to preserve living node identity, active text selections, and keyboard focus.

➔ NEVER use `innerHTML` to rebuild containers holding input fields because destroying living DOM elements wipes typed text and resets focus to the document body.

**DO THIS:** derive all interface markup from a single variable in memory

```jsx right
function SiteHeader() {
  const readerName = 'Elena Ruiz';
  return (
    <header className="site-header">
      <p>Welcome back, {readerName}</p>
      <span>Subscriber: {readerName}</span>
      <input placeholder="Search articles..." />
    </header>
  );
}
```

**DO NOT DO THIS:** query elements by identifier to mutate them by hand

```jsx wrong
function updateHeader(name) {
  const greeting = document.getElementById('greeting');
  if (greeting) greeting.textContent = 'Welcome back, ' + name;
  const badge = document.getElementById('badge');
  if (badge) badge.textContent = 'Subscriber: ' + name;
}
```

| | **MANUAL DOM SCRIPTING**<br>(imperative) | **REACT COMPONENT MODEL**<br>(declarative) |
| ---: | :--- | :--- |
| **Interface Construction** | Step-by-step imperative commands:<br>`document.`<br>`getElementById('id')`<br>`.textContent = name` | Declarative markup description:<br>`<p>`<br>`{readerName}</p>`<br>derived directly from data |
| **Multi-Widget Synchronization** | Independent queries per element;<br>missing one element causes<br>immediate state drift | Single source of truth variable;<br>all elements read the same value<br>and update simultaneously |
| **DOM Update Strategy** | Destructive container replacement<br>via `innerHTML` or manual<br>property assignments | In-memory description comparison;<br>applies minimal necessary operations<br>to changed text nodes only |
| **Input Focus & State** | Active cursor focus lost and typed<br>text wiped when container elements<br>are reconstructed | Living DOM node identity and active<br>cursor focus preserved across<br>data updates |
| **Prevented Bug Class** | State drift, missing element exceptions,<br>and lost user input during<br>container resets | Inconsistent multi-widget data and<br>accidental focus loss during<br>interface updates |
| **When it fits** | One element changes in one place,<br>such as a clock in a corner<br>of the page | The same value appears in several<br>places, or many parts of the<br>page change |
