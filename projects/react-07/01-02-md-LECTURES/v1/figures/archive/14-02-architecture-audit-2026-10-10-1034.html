LESSONS FROM THE CODE
Where a Story Card Keeps Its Memory

What each part of the front page expected, and what React did each time it ran the card

Component Layer File and Role Naive Expectation A Plain Variable Invisible to React, erased each time the card runs What Happened State in React Kept per card, changed through a setter
App.jsx Parent ✕ The page holds the counts
A count declared above StoryCard is shared by both cards and never asks React to run the cards again. 		✓ Each card owns its count
App returns two instances and keeps no state; two clicks on one card leave the other at Like (0).
StoryCard.jsx Like count ✕ Adding one updates the button
likes = likes + 1 raised the number to 3 while the button stayed at Like (0). 		✓ The setter asks React to run the card
setLikes(likes + 1) stores the next value, and React runs the card again: Like (1), then Like (2).
StoryCard.jsx Second run ✕ Variables last between runs
Clicking Save made React run the card again, which ran let likes = 0, and erased three clicks. 		✓ React returns the stored value
useState(0) ignores its argument after the first run; the count stays at Like (2) after Save.
StoryCard.jsx Bookmark ✕ The name finds the value
React does not know the names likes and isBookmarked; a call inside an if throws on the next run. 		✓ The order finds the value
The first call is always the count and the second the bookmark, so each returns its own value.
SaveButton.jsx Display button ✕ The button keeps the bookmark
A second copy of the bookmark in the button could disagree with the card. 		✓ The card keeps it, the button shows it
SaveButton shows isBookmarked and calls onToggle; the card stores the result.
Verdict A stuck and forgetful counter
The screen never shows the clicks, and the next run of the card loses them. 		A counter React remembers
Each card keeps its own values in React, and every setter call makes React run the card and show the change.
