State as a Snapshot in Practice

Why React treats state as a fixed constant for the whole render

Component Layer Architecture Naive Expectation Mutable Memory Assumes variables change in place What Happened Snapshot Reality State is fixed for each render
App.jsx Root Shell ✕ Global state propagation
Parent must hold state so rating changes trigger a full tree refresh. 		✓ Isolated boundary memory
StoryFeedback encapsulates its own state; parent App never re-renders on clicks.
StoryFeedback.jsx Setter Call ✕ Immediate variable update
Calling setRating(5) changes the variable on the very next line. 		✓ Fixed constant in running code
The running function still holds 0; setter only requests the next render.
StoryFeedback.jsx API Dispatch ✕ Read state after setting
Passing rating to sendRating delivers the new rating to the server. 		✓ Compute once in a local variable
Passing rating sent 0; const nextRating = 5 sends the true value.
StoryFeedback.jsx Timer Alert ✕ Delayed code reads newest data
A delayed timer fires and reads whatever rating the user chose later. 		✓ Closures capture their own render
The timer callback closes over its render's rating and reports the rating from that click.
RatingControls.jsx Repeated Calls ✕ Three calls increment by three
Calling setRating(rating + 1) three times adds three in one click. 		✓ All calls read the same snapshot
Each call evaluates 0 + 1, so React schedules a single render with 1.
Verdict Mutable variable mental model
Treating state as a live mutable pointer produces subtle timing bugs and stale dispatches. 		Immutable snapshot mental model
Each render receives a fixed snapshot, protecting delayed code and ensuring predictable UI.
