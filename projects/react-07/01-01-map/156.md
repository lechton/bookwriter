# Q156: The Cost of SSR: When Server-Side Rendering Is the Wrong Choice
* **Topic Tag**: #ssr | ❱❱ MORE (Server)
* **Interview Question**: *What does SSR cost, and when is rendering on the server the wrong choice?*
* **Core Truth**: Server-side rendering imposes significant server compute costs, latency overhead, and hydration costs; for authenticated, highly dynamic, or offline-capable apps with no SEO requirements, pure Client-Side Rendering (CSR) delivers superior responsiveness and lower infrastructure cost.
* **The Friction**: The internal newsroom CMS editor at The National Times is built with SSR; rendering complex interactive rich-text editors on the server adds 400ms of TTFB latency and consumes 80% of server CPU, while providing zero SEO benefit.
* **The Mechanism**: Cost analysis: SSR adds server CPU rendering overhead, memory buffering, TTFB latency, and client hydration CPU churn; CSR serves an empty static shell instantly from a CDN cache, delegating all rendering and state management to the client browser.
* **Under the Hood**: TTI degradation: in complex dashboard applications, SSR renders HTML that cannot be interacted with until massive JavaScript bundles execute hydrateRoot; because the user cannot interact during the hydration phase, SSR can actually delay Time to Interactive compared to an optimized client-only app.
* **The Code Experiment**:
  * *Naive*: Forcing an internal, authenticated real-time stock-trading dashboard to use SSR, burning server compute on pages search crawlers cannot even visit.
  * *React*: Choosing a pure CSR model with static CDN hosting and client-side data fetching for internal tools, reserving SSR strictly for public editorial pages.
* **Scope Boundary**: Focus on the trade-offs, compute costs, and counter-indications for SSR. Contrast when CSR outperforms SSR.
