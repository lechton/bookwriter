# Q160: Streaming Runtimes: Node Streams vs Web Streams Across Environments
* **Topic Tag**: #streaming | ❱❱ MORE (Server)
* **Interview Question**: *renderToPipeableStream versus renderToReadableStream: which environment needs which?*
* **Core Truth**: renderToPipeableStream is designed for Node.js using legacy stream.Writable streams and backpressure handling, while renderToReadableStream is built for modern Web Standards runtimes that communicate via ReadableStream.
* **The Friction**: The infrastructure team attempts to deploy The National Times application to Cloudflare Workers using renderToPipeableStream; the deployment fails with runtime errors like stream.Writable is not defined, because Edge runtimes do not support Node's legacy stream module.
* **The Mechanism**: Runtime choice: (1) Node.js (Express, Fastify, standard Node HTTP): use renderToPipeableStream(jsx, options) and call pipe(res); (2) Edge Runtimes (Cloudflare Workers, Deno, Vercel Edge, Bun): use const stream = await renderToReadableStream(jsx, options) and return new Response(stream, { headers: { 'content-type': 'text/html' } }).
* **Under the Hood**: Stream protocol differences: Node pipeable streams rely on EventEmitter events (data, drain, finish) and require manual backpressure handling; Web Streams rely on standard UnderlyingSource, ReadableStreamDefaultController, and asynchronous iterators native to the Fetch standard.
* **The Code Experiment**:
  * *Naive*: Attempting to use Node's renderToPipeableStream inside a Cloudflare Worker or Edge function, causing crashes due to missing Node built-ins.
  * *React*: Implementing an Edge handler using renderToReadableStream(jsx) and returning a native web Response(stream) with appropriate streaming headers.
* **Scope Boundary**: Focus on environment selection (Node.js vs Web Streams / Edge), stream mechanics, and runtime response formatting.
