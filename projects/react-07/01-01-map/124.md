# Q124: The RSC Payload: Wire Format and Streaming UI Trees
* **Topic Tag**: #rsc_payload | ❱ CORE (Server)
* **Interview Question**: *What is the RSC payload, and what ships to the browser instead of component code?*
* **Core Truth**: The RSC payload is a compact, streaming, line-delimited JSON representation of the rendered UI tree containing HTML element tags, props, data, and Client Component module references, allowing the client to reconstruct the DOM without downloading Server Component JavaScript.
* **The Friction**: A security auditor at The National Times inspects network traffic and worries that proprietary server-side rendering algorithms are being downloaded by readers; the engineering lead must explain that the browser never receives the server component code—only a serialized stream of UI instructions and data.
* **The Mechanism**: The RSC stream structure: lines starting with IDs (M for module references, J for JSON element trees, S for Suspense boundaries, H for hints); Server Components render to J rows, Client Components render as M references with props.
* **Under the Hood**: Flight protocol serialization: React's Flight server serializes the virtual DOM tree; when it encounters a Client Component, it emits a module reference pointing to the client chunk URL and serializes its props; the browser's Flight client streams these chunks, resolves module references, and updates the Fiber tree incrementally.
* **The Code Experiment**:
  * *Naive*: Assuming Server Components ship compiled JavaScript code to the client that runs in a hidden browser sandbox.
  * *React*: Inspecting the actual RSC payload response in DevTools (0:["$","div",null,{"children":["$","$L1",null,{...}]}]) to see how client references and server data serialize into a lightweight stream.
* **Scope Boundary**: Focus on what the RSC payload contains, how it streams, and why it replaces component code. Do not implement custom flight parsers.
