# Q36: Auditing and Stabilizing Effect Dependencies
* **Topic Tag**: `#effect_dependencies` | `❱ CORE`
* **Interview Question**: *How do you remove unnecessary effect dependencies, and when must a dependency stay?*
* **Core Truth**: Every reactive value read inside an effect must be declared in its dependency array; unnecessary re-executions should be solved by moving non-reactive logic outside, calculating values during render, or using updater functions, never by lying to the linter.
* **The Friction**: An engineer needs to log an article view: `useEffect(() => { logView(article.id, options); }, [article.id, options])`. Because `options = { theme: 'dark' }` is created as an object literal in the component body, it gets a new memory reference every render, causing the effect to run in an infinite loop and flooding the analytics server.
* **The Mechanism**: Dependency stabilization techniques: move static objects/functions outside the component, move dynamic objects inside the effect, use primitive dependencies (`options.theme`), use updater functions (`setCount(c => c + 1)`) to eliminate state dependencies, or move non-reactive reads into an Effect Event.
* **Under the Hood**: Shallow dependency comparison: React compares dependencies using `Object.is`; recreating object or function references on every render causes `Object.is(prev, next)` to return `false`, even if the contents are identical.
* **The Code Experiment**:
  * *Naive*: Silencing the ESLint `react-hooks/exhaustive-deps` warning by omitting dependencies, trapping stale closure bugs.
  * *React*: An `ArticleTracker` stabilizing dependencies by declaring config objects inside the effect and passing primitive IDs, preventing infinite logging loops without disabling linter checks.
* **Scope Boundary**: Focus on dependency auditing, object reference stabilization, and eliminating unnecessary dependencies. Use `useEffectEvent` (Q35) only as one removal technique without re-teaching it, and do not introduce `useCallback`/`useMemo` (Q56, Q57).
