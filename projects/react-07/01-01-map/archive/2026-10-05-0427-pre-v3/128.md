# Q128: Data Fetching Architecture: Server Components vs Server Functions vs Client
* **Topic Tag**: #data_fetching | ❱ CORE (Server)
* **Interview Question**: *Where should data fetching live: Server Components, Server Functions, or client effects?*
* **Core Truth**: Data fetching architecture depends on data lifecycle: Server Components fetch initial read-only data with zero client JS, Server Functions fetch or mutate on user interaction, and client effects fetch real-time polling or client-state-dependent data.
* **The Friction**: Developers at The National Times build three features using inconsistent patterns: an article view fetches via client useEffect, a live stock ticker queries the database inside an async Server Component, and a search box calls a REST API; the resulting architecture suffers from waterfalls, stale data, and excessive client bundles.
* **The Mechanism**: The 3 fetching paradigms: (1) Server Components: await db.query() for initial page load and SEO; (2) Server Functions: invoked on demand for mutations and user-triggered reads (e.g. pagination, search); (3) Client fetching (use / SWR): for polling, subscriptions, and offline cache updates.
* **Under the Hood**: Network waterfall elimination: Server Components run co-located with the database (sub-millisecond latency), eliminating multi-hop client-to-server waterfalls; Server Functions execute as atomic RPCs; client fetching incurs high round-trip latency over mobile networks.
* **The Code Experiment**:
  * *Naive*: Fetching initial article data on the client via useEffect, causing a blank screen, loading spinner, and slow mobile round-trips.
  * *React*: Fetching article data directly in an async Server Component, while using a Server Function for pagination and a client hook for a live breaking news alert websocket.
* **Scope Boundary**: Focus on architectural decision-making: comparing when to use Server Components vs Server Functions vs Client-side fetching.
