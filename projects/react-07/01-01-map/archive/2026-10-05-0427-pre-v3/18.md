# Q18: State as a Snapshot
* **Topic Tag**: `#state_snapshots` | `❱ CORE`
* **Interview Question**: *Why does state appear frozen inside a render, even right after you set it?*
* **Core Truth**: State variables are not live mutable variables; they are immutable snapshots captured by JavaScript closures for a specific render pass, remaining completely frozen for the entire duration of that execution.
* **The Friction**: A developer writes a `handlePublish` handler: `setEdition('Evening'); console.log(edition); sendAlert(edition);`. The console prints `'Morning'`, and the alert sends `'Morning'`, even though `setEdition('Evening')` was just called. Frustrated, the developer assumes React's setter is broken or has a timing bug.
* **The Mechanism**: Snapshot mental model. Each render pass calls your component with a specific, constant snapshot of state. Inside that execution, the state variable is a `const` captured in the event handler's closure and never changes, regardless of asynchronous delays (`setTimeout`) or subsequent state setter calls.
* **Under the Hood**: JavaScript closure semantics: when `ArticleView` renders with `edition = 'Morning'`, all handlers created during that render close over that specific value. The setter requests a *new* render with a *new* snapshot, but cannot retroactively mutate the variable in the running frame.
* **The Code Experiment**:
  * *Naive*: Calling `setCount(count + 1)` and immediately attempting to read `count` or pass it to an API call, expecting the updated number within the same function execution.
  * *React*: A `StoryFeedback` form demonstrating that calling `setRating(5)` retains the snapshot value in the current handler, showing how to use a local variable or wait for the next render snapshot.
* **Scope Boundary**: Focus strictly on the snapshot concept and closure capture within a single render. Do not introduce `useRef` for mutable storage (Q33) or updater functions (Q19).
