# Q117: Streaming SSR with Suspense: Shells, Fallbacks, and Out-of-Order Flushes
* **Topic Tag**: #suspense_streaming | ❱ CORE (Server)
* **Interview Question**: *How does streaming SSR work with Suspense: the shell, fallbacks, and out-of-order flushes?*
* **Core Truth**: Streaming SSR with <Suspense> allows the server to flush the initial HTML shell and lightweight components immediately, while streaming slow data-dependent subtrees as out-of-order HTML chunks that the browser scripts swap into place.
* **The Friction**: The National Times homepage features instant breaking news headlines and a slow, AI-generated "Trending Reader Discussions" widget that takes 1.8 seconds to query; under traditional SSR, the entire homepage hangs for 1.8 seconds before sending a single byte, tanking Time to First Byte (TTFB).
* **The Mechanism**: <Suspense fallback={<Skeleton />}>: the server sends the document head, navigation, and fallback placeholder in the initial chunk; when the slow async component finishes, the server streams the rendered HTML along with an inline <script> that replaces the fallback DOM node.
* **Under the Hood**: Out-of-order HTML streaming: React assigns a unique template ID to the Suspense boundary; when the deferred chunk resolves, it streams <div hidden id="S:1">...</div><script>$RC("B:1", "S:1")</script>, which executes in the browser to swap the fallback with the real content before client hydration even begins.
* **The Code Experiment**:
  * *Naive*: Blocking the entire server render until all slow database queries resolve, resulting in a 2-second TTFB and poor reader experience.
  * *React*: Wrapping the slow TrendingDiscussions component in <Suspense fallback={<DiscussionsSkeleton />}>, allowing the main news shell to stream to the browser in under 100ms.
* **Scope Boundary**: Focus on conceptual mechanics of Suspense streaming, shell vs fallback, and out-of-order flushes. Low-level Node/Web stream APIs (renderToPipeableStream) are covered in Q118.
