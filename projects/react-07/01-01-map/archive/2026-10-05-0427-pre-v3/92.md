# Q92: Generic Components and Flexible Collections in TypeScript
* **Topic Tag**: `#typescript_generics` | `❱❱❱ ADVANCED`
* **Interview Question**: *How do you type generic components and flexible data collections in React?*
* **Core Truth**: Generic components use TypeScript type parameters (`<T,>`) on component functions to preserve the exact type of passed collections across items, render callbacks, and selection handlers without requiring unsafe type assertions.
* **The Friction**: A team creates a reusable `DataTable` or `ArticleFeed` component. If typed as `items: any[]` or `items: Record<string, unknown>[]`, consumers must write ugly type assertions (`(item as Article).headline`) inside every row render callback, hiding type errors if data models change.
* **The Mechanism**: Generic function components (`function DataTable<T extends { id: string }>({ items, renderRow }: DataTableProps<T>)`). Callers pass `items={articles}` and TypeScript automatically infers `T` as `Article`, providing autocomplete and compile-time safety inside `renderRow={(article) => ...}`.
* **Under the Hood**: TypeScript JSX generic grammar: in `.tsx` files, arrow function generics require a trailing comma (`<T,>`) to avoid parser ambiguity with JSX tags, whereas standard `function Component<T>()` declarations parse cleanly and infer types from passed props.
* **The Code Experiment**:
  * *Naive*: Building a table component with `items: object[]` requiring callers to cast item types in every child callback.
  * *React*: An `EditorialTable<T extends Entity>` component inferring row data types dynamically and guaranteeing that `onSelectRow={(row) => ...}` receives the exact typed record.
* **Scope Boundary**: Focus on generic components, type constraints (`extends`), and generic prop types. Do not cover polymorphic `as` prop implementations (Q93).
