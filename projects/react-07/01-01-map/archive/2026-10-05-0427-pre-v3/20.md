# Q20: StrictMode and Double Rendering
* **Topic Tag**: `#strict_mode` | `❱ CORE`
* **Interview Question**: *Why does React render your components twice in development?*
* **Core Truth**: `<StrictMode>` intentionally executes component functions and state updaters twice in development to uncover impure side effects, memory leaks, and non-idempotent code before they reach production.
* **The Friction**: A developer inspects their terminal and browser console and sees `console.log('Rendering Article')` printing twice on every state change. Believing React is broken or running a catastrophic performance bug, they waste hours trying to "fix" the double render or consider removing StrictMode.
* **The Mechanism**: `<React.StrictMode>`. A development-only wrapper component that enforces React's purity contract by double-invoking render functions, state updaters, and effect setup/cleanup cycles. It is completely inert in production builds.
* **Under the Hood**: How React verifies idempotence: if a component is pure, calling `f(props)` twice produces identical output with zero side effects; if calling it twice alters UI, duplicates items, or increments global variables, StrictMode immediately exposes the impurity in development where it is easy to diagnose.
* **The Code Experiment**:
  * *Naive*: An impure component pushing an item into a global array or mutating an external object on render, causing double entries in StrictMode.
  * *React*: Wrapping `<App />` in `<StrictMode>` in `main.jsx`, demonstrating how a pure component renders cleanly without observable side effects despite double execution.
* **Scope Boundary**: Focus strictly on why StrictMode double-renders in development, what it detects (impure render side effects), and confirming that it has zero runtime overhead in production. Do not detail effect cleanup double-runs (Q35) or legacy lifecycle deprecation warnings.
