# Q53: Accessible and Hydration-Safe IDs with useId
* **Topic Tag**: `#use_id` | `❱❱ MORE`
* **Interview Question**: *How do you generate IDs that are unique, stable, and safe across server and client?*
* **Core Truth**: `useId` generates unique, deterministic IDs based on a component's position in the React tree, guaranteeing identical values between server-rendered HTML and client hydration to prevent accessibility mismatches.
* **The Friction**: An accessible form pairs `<label htmlFor="email">` with `<input id="email">`. When the component is rendered twice on the same page (e.g. in header and footer), duplicate IDs break screen readers; using `Math.random()` produces different IDs on server and client, causing hydration crashes.
* **The Mechanism**: The `useId` hook (`const id = useId()`). It produces stable IDs like `:r0:` that are unique per component instance and match seamlessly between server rendering and client hydration.
* **Under the Hood**: Tree-position hashing: React generates `useId` strings by encoding the component's hierarchical path within the fiber tree; because the tree structure is identical on server and client, the generated ID string is guaranteed to be 100% deterministic.
* **The Code Experiment**:
  * *Naive*: Using a global counter `let id = 0` or `Math.random()`, which causes SSR hydration mismatch errors and clobbers duplicate IDs when components re-render.
  * *React*: An `AccessibleTextField` component using `const id = useId()` to connect `<label htmlFor={id}>` and `<input id={id}>` safely across multiple instances.
* **Scope Boundary**: Focus on `useId` for accessibility wiring (`htmlFor`, `aria-describedby`) and hydration safety. Do not use `useId` for generating keys in lists (keys belong to data).
