# Q49: Synchronous Layout Calculations with useLayoutEffect
* **Topic Tag**: `#use_layout_effect` | `❱❱ MORE`
* **Interview Question**: *When must code run after DOM updates but before the browser paints?*
* **Core Truth**: `useLayoutEffect` runs synchronously immediately after React mutates the physical DOM but before the browser paints pixels to the screen, preventing visual layout shifts and flickering when measuring and adjusting DOM geometry.
* **The Friction**: An editorial tooltip calculates its position relative to an article button. If placed in `useEffect`, the tooltip first renders at `top: 0, left: 0`, paints to the screen, measures the button, and jumps to `top: 140px, left: 200px` 16ms later. The reader sees a jarring visual flicker on every hover.
* **The Mechanism**: The `useLayoutEffect` hook (`useLayoutEffect(() => { const rect = el.getBoundingClientRect(); setCoords(rect); }, [])`). React executes `useLayoutEffect` synchronously in the commit phase before handing control back to the browser paint engine.
* **Under the Hood**: Browser rendering pipeline: React DOM mutations -> `useLayoutEffect` -> browser reflow/layout -> browser paint -> `useEffect`. By updating state inside `useLayoutEffect`, React performs a synchronous re-render pass before the browser ever paints, hiding intermediate positions from the user.
* **The Code Experiment**:
  * *Naive*: Positioning a floating tooltip inside `useEffect`, causing visible flicker on every initial render.
  * *React*: A `Tooltip` component using `useLayoutEffect` to measure DOM bounds and apply positioning offsets synchronously before the initial paint.
* **Scope Boundary**: Focus on when to use `useLayoutEffect` (DOM measurements, preventing flicker) vs `useEffect` (standard async synchronization). Do not use for data fetching. Do not cover `useInsertionEffect` (Q50).
