### The browser starts at index.html and needs an explicit mounting bridge

- [p] ◇ {theme: the browser entry point} Every web application begins with an HTML document. When you build a traditional website, you write tags like `<header>`, `<h1>`, and `<p>` directly inside HTML files, and the browser displays them immediately. In React, your components return descriptions of markup written in JSX. The browser cannot run JSX on its own, and it cannot guess which HTML element your components belong to. To display components on screen, React requires an explicit mounting bridge that connects your virtual component tree to a real, living HTML element on the page. ◼ Educational objective: introduce the universal problem of connecting virtual component trees to the browser DOM.

- [p] ◇ {starting point: index.html has only an empty div} When you inspect a new React project, the root `index.html` file contains almost nothing: just an HTML shell with an empty `<div id="root"></div>` tag and a module script. Looking at this empty container, a developer wonders how component code ever makes its way onto the screen. ◼ Educational objective: ground the starting point in the visible HTML document structure.

- [files] Project folders: File Explorer

```files title="Project folders: File Explorer"
index.html | boundary | Host HTML document containing the physical container div#root
src/

  App.jsx | parent | Root application shell composing the interface layout

    StatusCard.jsx | child | Modular child component displaying pending item count
```

- [p] ◇ {the three files} The mounting pipeline connects three files. First, `index.html` provides the host HTML container and loads the entry script. Second, `src/main.jsx` finds that container and initializes React. Third, `src/App.jsx` provides the root component that renders the application interface. ◼ Educational objective: identify the three load-bearing files before showing their code.

- [code] Host HTML shell in index.html:

```html title="index.html"
<!DOCTYPE html>
<html lang="en">
  <head>
    <title>Item Tracker</title>
  </head>
  <body>
    <div id="root">Loading...</div> <!-- Physical DOM container -->
    <script type="module" src="/src/main.jsx"></script> <!-- Module entry -->
  </body>
</html>
```

◼ **The what-this-introduces list:** 1. `<div id="root">`: the host container element React controls. 2. `Loading...`: placeholder text cleared when React mounts. 3. `<script type="module">`: the module script loading the application entry point.

- [code] Entry point mounting in main.jsx:

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client'; // Browser mounting renderer
import App from './App.jsx'; // Root component import

const container = document.getElementById('root'); // Finds container node
const root = createRoot(container); // Creates React root

root.render(<App />); // Mounts component tree into container
```

◼ **The what-this-introduces list:** 1. `createRoot`: client renderer function from `react-dom/client`. 2. `container`: DOM element reference returned by `getElementById`. 3. `root.render`: schedules the component tree to display inside the container.

### How index.html loads main.jsx through a module script

- [runway] The host HTML document and module scripts, used by Question 1 and Question 2.

- [p] ★ {preknowledge: script tags load JavaScript into HTML pages} We know that HTML documents load external scripts using `<script>` tags. Traditionally, a classic script ran synchronously and treated all code as a single global scope. In modern web development, adding `type="module"` to a `<script>` tag tells the browser that the file is an **ES module** that uses `import` and `export` statements. ◼ Educational objective: establish the technical definition and purpose of `<script type="module">`.

- [p] ★ {mechanism: deferred execution of module scripts} Modern browser engines automatically **defer** module scripts. While the browser downloads `main.jsx` across the network, it continues parsing the rest of the HTML document without pausing. The module script executes only after the entire HTML document has been parsed into memory. Because of this deferred timing, a `<script type="module">` tag placed in the `<head>` of your document can safely find `<div id="root">` even though the `<div>` tag appears further down in the `<body>`. ◼ Educational objective: explain why module scripts avoid traditional DOM ready listener boilerplate.

- [code] Script placement in index.html:

```html title="index.html"
<head>
  <title>Item Tracker</title>
  <!-- Module scripts are deferred until HTML parsing completes -->
  <script type="module" src="/src/main.jsx"></script> <!-- Safe in head -->
</head>
<body>
  <div id="root">Loading...</div> <!-- Found safely by getElementById -->
</body>
```

◼ **The what-this-introduces list:** 1. `type="module"` in `<head>`: deferred execution timing. 2. `<div id="root">` in `<body>`: guaranteed to exist when `main.jsx` runs.

### How createRoot and root.render attach components to the page

- [runway] The mounting API from react-dom/client, used by Question 1, Question 3, Question 4, and Question 5.

- [p] ★ {preknowledge: React separates core logic from DOM rendering} React separates its core component architecture from browser rendering. The core package, `react`, manages element descriptions, component logic, and component trees. The browser renderer, `react-dom/client`, provides the bridge that turns those element descriptions into physical browser DOM nodes. Only the application entry file (`main.jsx`) imports from `react-dom/client`; all your component files import purely from `react`. ◼ Educational objective: explain the architectural boundary between `react` and `react-dom/client`.

- [p] ★ {mechanism: createRoot container ownership and clearing} Calling `createRoot(domNode)` creates a React root object for that specific DOM element and gives React exclusive ownership of the HTML inside it. When `root.render(<App />)` runs for the first time, React wipes whatever placeholder HTML originally lived inside that element (such as `"Loading..."`) and replaces it with the rendered output of `<App />`. Any HTML written outside that container, such as a static navigation bar or footer in `index.html`, remains completely untouched. ◼ Educational objective: explain container ownership and placeholder clearing on initial mount.

- [p] ★ {mechanism: root.render asynchronous scheduling} Calling `root.render` does not block the browser thread to update the DOM synchronously on the spot. Instead, `root.render` schedules a render task in React's queue and returns immediately. If you read `container.textContent` on the line directly following `root.render(<App />)`, the console still prints `"Loading..."` because React has not painted the DOM yet. The browser paints the updated DOM tree only after the current JavaScript execution frame finishes and yields control back to the browser event loop. ◼ Educational objective: explain why `root.render` is asynchronous and returns before the DOM paints.

- [code] Asynchronous render scheduling in main.jsx:

```jsx title="main.jsx"
const container = document.getElementById('root');
const root = createRoot(container); // Creates concurrent root

root.render(<App />); // Schedules render task asynchronously

// The next line executes before React paints the DOM:
console.log(container.textContent); // Still prints: "Loading..."
```

◼ **The what-this-introduces list:** 1. `root.render(<App />)`: non-blocking render queue dispatch. 2. `console.log(container.textContent)`: proves DOM updates happen after the current execution frame.

### Why Vite transforms JSX and serves modules over HTTP

- [runway] Vite dev server, file protocol restrictions, and build output, used by Question 2.

- [p] ◇ {the problem: browsers cannot read raw JSX or bare package names} Web browsers understand ECMAScript, but they do not understand JSX syntax like `<App />`. If a browser encounters a raw `<` token inside a JavaScript file, it halts with a syntax error. Furthermore, browsers cannot resolve bare package specifiers like `import { createRoot } from 'react-dom/client'` because browsers only know how to load files from explicit paths starting with `/`, `./`, or `../`. ◼ Educational objective: identify the two physical limitations that necessitate a build tool.

- [p] ◇ {mechanism: Vite development server and production build} To solve these limitations, modern projects use **Vite**. During development, running `npm run dev` starts a local HTTP **dev server** at `http://localhost:5173`. When the browser requests `/src/main.jsx`, Vite intercepts the request, transforms the JSX into standard function calls (`_jsxDEV`), rewrites package imports into browser-accessible URLs, and serves the files over HTTP. When you are ready to deploy, running `npm run build` compiles your application into static HTML, JavaScript, and CSS bundles inside a `dist/` directory. ◼ Educational objective: describe Vite's on-demand development transform and production bundling.

- [p] ★ {the file protocol trap} If you double-click `index.html` from your desktop folder, the browser opens it using the `file://` protocol. For security reasons, modern browsers treat the local disk origin as `null` and block all `<script type="module">` tags under cross-origin security rules. To run a modern React application, you must always serve your files over HTTP using the Vite development server. ◼ Educational objective: explain why double-clicking `index.html` fails with CORS errors.

- [code] Starting the Vite development server:

```bash title="Terminal"
$ npm run dev # Starts local development server

  VITE v6.0.0  ready in 180 ms

  ➜  Local:   http://localhost:5173/ # Serves modules over HTTP
  ➜  Network: use --host to expose
```

◼ **The what-this-introduces list:** 1. `npm run dev`: CLI command starting the Vite server. 2. `http://localhost:5173/`: local HTTP origin enabling ES module execution.

### Principles of React: Mounting the Root with createRoot

- [question-cycle] Question 1: An empty div in HTML receives the component tree
    - Question: "My index.html has only an empty div. How does App get there?"
    - Code and result: The reader inspects `index.html` containing `<div id="root">Loading...</div>` and `<script type="module" src="/src/main.jsx"></script>`. In `main.jsx`, they write `createRoot(document.getElementById('app')).render(<App />);` with an ID typo `'app'`. When the browser loads, the screen remains completely blank, and the console throws `Target container is not a DOM element.`
    - Verdict: does not do what the reader wanted.
    - Answer: `document.getElementById('app')` searches the active document for an element with an id matching `'app'`. Because `index.html` defines `<div id="root">`, the lookup finds nothing and returns `null`. `createRoot` requires a living DOM node; when it receives `null`, it halts and throws `Target container is not a DOM element.` When the identifier matches (`'root'`), `createRoot` receives the verified DOM node and creates a root object. Calling `root.render(<App />)` instructs React to execute `App` and replace the placeholder text inside `<div id="root">` with the rendered component output.
    - Fix: Pass `document.getElementById('root')` matching the container id in `index.html`.
    - Rule with boundary: Always pass `createRoot` a verified DOM element whose identifier matches the `id` in `index.html` character for character.
    - Needs: `document.getElementById` (recall Lecture 1), `createRoot` (runway), `root.render` (runway), placeholder text clearing (runway).
    - Diagram: ASCII diagram tracing the chain from `index.html` `<div id="root">` through `document.getElementById('root')`, `createRoot`, and `root.render(<App />)`.

> [!PRINCIPLE]
> **Principle 1: index.html loads main.jsx, and main.jsx hands the root element to React**
> When the browser loads index.html, the module script requests main.jsx. In that file, document.getElementById finds the physical container element, and createRoot hands that container to React. Calling root.render replaces any initial content inside the container with your component tree. If the identifier in getElementById does not match the id attribute in index.html, the method returns null, causing createRoot to throw a fatal error that leaves the page blank.
>
> >> root container : the physical HTML element that React takes over to display and manage components
>
> *We should do this:*
> `const element = document.getElementById('root');`
> `const root = createRoot(element);`
> `root.render(<App />); // replaces placeholder content`
>
> *We should not do this:*
> `const element = document.getElementById('app'); // returns null`
> `const root = createRoot(element); // throws on null container`

- [question-cycle] Question 2: Double-clicking index.html blocks the module script
    - Question: "Can I just open index.html from disk, or link App.jsx in a plain script tag?"
    - Code and result: The developer double-clicks `index.html` from their local file manager, opening `file:///Users/dev/project/index.html`. The page remains stuck showing `"Loading..."`, and Chrome logs: `Access to script at 'file:///...' from origin 'null' has been blocked by CORS policy`. Linking `App.jsx` directly via `<script src="/src/App.jsx">` halts with `Cannot use import statement outside a module` and `Unexpected token '<'`.
    - Verdict: does not do what the reader wanted.
    - Answer: Web browsers do not understand raw JSX syntax and cannot resolve bare package names like `react-dom/client`. Furthermore, modern browsers enforce strict security boundaries around ES modules: opening an HTML file directly from disk via the `file://` protocol assigns it a `null` origin, causing the browser to block all `<script type="module">` tags with CORS errors. Vite resolves both issues: running `npm run dev` starts a local HTTP development server that compiles JSX on demand and serves modules over HTTP. For production, `npm run build` compiles your application into static bundles in `dist/`.
    - Fix: Start the Vite development server with `npm run dev` and open the local HTTP address in your browser.
    - Rule with boundary: Always serve a modern React application through Vite over HTTP during development (`npm run dev`) and test production builds on a local HTTP server (`vite preview`). Never open React projects directly over the `file://` protocol.
    - Needs: `file://` page (runway), Vite dev server (runway), CORS policy (runway), `npm run build` (runway).
    - Diagram: ASCII diagram contrasting `file://` (blocks CORS, raw JSX) vs `http://localhost:5173` (HTTP headers, transformed JSX).

> [!PRINCIPLE]
> **Principle 2: Serve the app through Vite, never as raw files**
> Web browsers do not understand JSX syntax and cannot resolve package imports like react-dom/client directly from disk. Furthermore, modern browsers treat local disk files loaded over file:// as having a null origin, blocking all module scripts with security errors. Running the Vite development server transforms JSX into standard JavaScript on the fly and serves your application over HTTP. For deployment, Vite bundles your project into static files inside dist.
>
> >> dev server : a local HTTP server that transforms JSX and serves modules on demand during development
>
> *It is best practice to do this:*
> `// Run Vite dev server: npm run dev`
> `// Local server URL: http://localhost:5173/`
> `<script type="module" src="/src/main.jsx"></script> {/* HTTP */}`
>
> *Instead of doing this:*
> `// Double-clicking file:///project/index.html`
> `<script type="module" src="/src/main.jsx"></script> {/* CORS */}`

- [question-cycle] Question 3: Passing the bare function App leaves the page empty
    - Question: "Do I pass App or <App /> to root.render?"
    - Code and result: In `main.jsx`, the reader writes `root.render(App);` passing the raw function identifier without JSX angle brackets. The browser screen remains empty, and the console logs: `Functions are not valid as a React child. This may happen if you return a Component instead of <Component /> from render.`
    - Verdict: does not do what the reader wanted.
    - Answer: A React component is a JavaScript function. Passing `App` hands React the raw function reference itself, which React cannot draw onto the screen. Writing `<App />` creates a React element descriptor that instructs React to call the component function and render its returned markup. `root.render` accepts React elements, strings, numbers, `null`, or `undefined`, but rejects bare component functions. If a helper function returns JSX, call it first so `root.render` receives the returned element: `root.render(createApp())`.
    - Fix: Wrap the component in JSX tags: `root.render(<App />)`.
    - Rule with boundary: Always pass `root.render` a React element, such as `<App />`, rather than a bare component function reference. Boundary: If passing a helper function that returns an element, call the helper so `root.render` receives the resulting element.
    - Needs: bare function vs JSX element (recall Lecture 2), React element descriptor (recall Lecture 3), helper function returning JSX (runway).
    - Diagram: ASCII diagram comparing `App` (bare function reference) vs `<App />` (`{ type: App, props: {} }` React element descriptor).

> [!PRINCIPLE]
> **Principle 3: Pass root.render an element, <App />**
> A React component is a JavaScript function, but root.render requires a **React element** to mount. Writing the bare name App passes a function reference, which React cannot display on the page. Writing <App /> creates an element descriptor that instructs React to call the component function and render its returned markup. When rendering a helper function that returns JSX, call the function first so root.render receives the resulting element.
>
> >> React element : an object descriptor created with JSX that instructs React what markup to mount
>
> *We should do this:*
> `const root = createRoot(document.getElementById('root'));`
> `root.render(<App />); // passes a React element descriptor`
>
> *We should not do this:*
> `const root = createRoot(document.getElementById('root'));`
> `root.render(App); // error: Functions are not valid child`

- [question-cycle] Question 4: Older tutorials that call `ReactDOM.render` fail in React 19
    - Question: "A tutorial writes ReactDOM.render(<App />, root). Why does it fail?"
    - Code and result: Following an older tutorial, the developer writes `import ReactDOM from 'react-dom';` and calls `ReactDOM.render(<App />, document.getElementById('root'));`. The browser halts with `TypeError: ReactDOM.render is not a function`, leaving the screen blank. If they try `root.render(<App />, container)`, React logs: `Warning: You passed a second argument to root.render(...) but it only accepts one argument.`
    - Verdict: does not do what the reader wanted.
    - Answer: React 19 permanently removed legacy mounting functions, including `ReactDOM.render`, `ReactDOM.hydrate`, and `unmountComponentAtNode`. Applications must import `createRoot` from the client renderer subpath `'react-dom/client'`. You initialize the root once with `createRoot(container)`, and call `root.render` with exactly one argument: the React element. Root configuration options, such as `onUncaughtError`, must be passed as the second argument to `createRoot(container, options)`, not to `root.render`.
    - Fix: Import `createRoot` from `'react-dom/client'`, create the root with `createRoot(container)`, and call `root.render(<App />)`.
    - Rule with boundary: Always mount React applications using `createRoot` from `react-dom/client`. Never call `ReactDOM.render` or pass a container as a second argument to `root.render`.
    - Needs: `ReactDOM.render` removal in React 19 (runway), client subpath `react-dom/client` (runway), root options object (runway).
    - Diagram: ASCII diagram contrasting legacy `ReactDOM.render(element, container)` vs modern `createRoot(container).render(element)`.

> [!PRINCIPLE]
> **Principle 4: Start the app with createRoot, not with ReactDOM.render**
> React 19 completely removed the legacy ReactDOM.render function. Applications must import createRoot from react-dom/client, initialize the root container once, and call root.render with a single React element argument. The render method accepts only one parameter; passing the DOM container or configuration options as a second argument to root.render triggers a console warning. Pass root options directly to createRoot as its second argument.
>
> >> client subpath : the react-dom/client import path providing browser-specific root creation functions
>
> *We should do this:*
> `import { createRoot } from 'react-dom/client';`
> `const root = createRoot(document.getElementById('root'));`
> `root.render(<App />); // modern client root mounting`
>
> *We should not do this:*
> `import ReactDOM from 'react-dom'; // removed in React 19`
> `ReactDOM.render(<App />, document.getElementById('root'));`

- [question-cycle] Question 5: Calling createRoot twice on the same container triggers a warning
    - Question: "The header and the cards both need to update. Do I call createRoot for each?"
    - Code and result: A developer calls `createRoot` twice on `<div id="root"></div>`: first `createRoot(container).render(<App />);` and then `createRoot(container).render(<StatusCard />);`. The browser console logs: `Warning: You are calling ReactDOMClient.createRoot() on a container that has already been passed to createRoot() before. Instead, call root.render() on the existing root to update it.`
    - Verdict: does not do what the reader wanted.
    - Answer: When you call `createRoot(container)`, React establishes exclusive ownership over the DOM inside that container. Calling `createRoot` a second time on the same container creates competing root records that attempt to control the same physical DOM nodes, creating memory leaks and breaking component lifecycle guarantees. In an application built fully with React, you call `createRoot` once at startup in `main.jsx`. All user interface sections should be composed as child components nested inside `App`. Components update the page using state, not by creating additional roots. (Boundary: When embedding React widgets into an existing multi-page website that is only partially built with React, you create one root for each separate physical DOM container).
    - Fix: Call `createRoot` once for `<App />`, and nest child components inside `App`.
    - Rule with boundary: Create one root container per application, and nest all interface sections as components inside `App`. Boundary: When embedding React into a page built only partially with React, create one root for each separate HTML container element.
    - Needs: single root architecture (runway), state update preview (Lecture 14), multiple roots on separate containers boundary (runway).
    - Diagram: ASCII diagram contrasting single root owning `<App />` with nested children vs conflicting duplicate roots on the same container.

> [!PRINCIPLE]
> **Principle 5: Create one root, and nest everything else inside App**
> In an application built fully with React, create a single root container at startup in main.jsx. That root manages the entire DOM tree inside its container. Calling createRoot multiple times on the same DOM element causes conflicting update cycles and logs a warning. Add new interface sections by nesting child components inside App rather than creating additional roots. When embedding React into an existing multi-page website, create one root for each separate physical container element.
>
> >> single root : an application architecture where one root container manages the complete component hierarchy
>
> *It is best practice to do this:*
> `const root = createRoot(document.getElementById('root'));`
> `root.render(<App />); // one root: all components nest inside App`
>
> *Instead of doing this:*
> `const container = document.getElementById('root');`
> `createRoot(container).render(<App />);`
> `createRoot(container).render(<StatusCard />); // duplicate root`

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client'; // React 19 client
import App from './App.jsx'; // Root component

const container = document.getElementById('root'); // Finds container

if (container) {
  const root = createRoot(container); // Connects to DOM
  root.render(<App />); // Mounts tree into container
}
```

### For the interview

- [interview] > **The Interview Question:** How does your root component attach to the browser DOM with createRoot, and how do build tools assemble it?
- [interview] **1. The Hidden Signal**: The interviewer is not asking whether you can memorize three lines of boilerplate. They are probing whether you understand the fundamental boundary between the declarative React component model (`react`) and the imperative browser DOM mounting renderer (`react-dom/client`). A junior developer treats `main.jsx` as magic syntax; a senior engineer explains that React needs an explicit mounting bridge to bind virtual element descriptor trees to physical HTML containers, and that build tools transform JSX into browser-compatible modules because native browser engines cannot parse JSX or resolve bare package specifiers.
- [interview] **2. The Classic Trap**: The classic trap is assuming that `root.render` updates the browser DOM synchronously on the spot, or reciting legacy methods from older tutorials. Candidates often claim that `ReactDOM.render` is still supported, unaware that React 19 completely removed legacy mounting functions. Another fatal trap is writing `root.render(App)` without JSX angle brackets, passing a raw function reference that causes React to crash with `Functions are not valid as a React child`.
- [interview] **3. What is Actually Going On**: The mounting pipeline follows four distinct steps. First, `index.html` loads `main.jsx` using a deferred `<script type="module">` tag. Second, `document.getElementById('root')` finds the physical container element in memory. Third, `createRoot(container)` creates a React root object that takes exclusive ownership of that container. Fourth, `root.render(<App />)` schedules the mounting of the `<App />` element tree into the container. React clears any placeholder content inside the container and paints the component output. In development, Vite intercepts requests, transforms JSX into `_jsxDEV` calls, and serves native modules over HTTP. For production, `vite build` bundles everything into static files inside `dist/`.
- [interview] **4. Where It Gets Tricky**: What happens if you inspect `container.textContent` immediately after calling `root.render(<App />)`? It still contains the old placeholder text because `root.render` schedules updates asynchronously rather than blocking the JavaScript thread synchronously. What happens if you call `createRoot` twice on the same container? React logs a warning because duplicate roots create competing ownership of the same DOM tree; you should always create one root per application and nest all UI inside `App`. What happens if you double-click `index.html` from your desktop? Modern browsers block module scripts over the `file://` protocol with CORS errors, requiring files to be served over HTTP via Vite.

### Glossary

- [glossary] createRoot ◼ The modern React DOM client method that creates a root container for a physical browser element.
- [glossary] root.render ◼ The root method that schedules the rendering of a React element tree into the designated DOM container.
- [glossary] root container ◼ The physical HTML element, typically `<div id="root">`, that React takes over to manage its user interface.
- [glossary] module script ◼ An HTML `<script type="module">` tag that loads ES modules and automatically defers execution until HTML parsing completes.
- [glossary] dev server ◼ A local development HTTP server that compiles JSX on demand and serves native ES modules with instant updates.
- [glossary] single root ◼ An application architecture where one root container manages the complete component hierarchy from a single top-level component.

### Summary

- [review-title] **Architectural Takeaways & Decision Matrix**
- [review-subtitle] ❒ Root Initialization & Container Ownership
- [always-rule] ➔ ALWAYS pass an existing DOM element to `createRoot` and let React take exclusive ownership of that container.
- [never-rule] ➔ NEVER call `createRoot` multiple times on the same container; nest all interface sections as child components inside `App`.
- [if-then-rule] ➔ IF you are embedding React into an existing multi-page website with separate widgets, THEN create one root for each separate physical DOM container.
- [review-subtitle] ❒ Tooling & Mounting APIs
- [always-rule] ➔ ALWAYS import `createRoot` from `react-dom/client` in your entry file, and pass `root.render` a React element like `<App />`.
- [never-rule] ➔ NEVER open React projects over the `file://` protocol; always serve them over HTTP using the Vite development server.
- [never-rule] ➔ NEVER call the removed `ReactDOM.render` method or pass a second argument to `root.render`.

- [p] **DO THIS:** import createRoot from react-dom/client and render a React element

```jsx right
import { createRoot } from 'react-dom/client';
```

- [p] **DO NOT DO THIS:** import removed legacy render or pass raw functions without JSX tags

```jsx wrong

render(App, document.getElementById('root'));
```
