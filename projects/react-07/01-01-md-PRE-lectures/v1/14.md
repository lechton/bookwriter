### How a component remembers data across renders

- [p] ◇ {theme: the challenge of stateful memory in pure component functions} In modern web applications, user interfaces must respond to user actions by remembering choices and displaying updated data. When a user clicks a button to like an article, toggles a bookmark, or types into an input field, the application must store that information and present the new value on the screen. In standard JavaScript programming, developers store changing values in local variables using `let`. In React, components are pure JavaScript functions that execute to return JSX descriptions of the interface. When an interaction occurs, React calls the component function again from the top. A plain local variable declared inside the function body is re-created on every render, discarding any previous value. To remember data across renders and request screen updates, React components use state declared with the `useState` Hook. ◼ Educational objective: introduce component state and contrast it with ordinary local variables.

- [p] ◇ {starting point: local variable assignments versus declarative state updates} Beginners often assume that changing a local variable will automatically update the screen, because the variable appears inside the returned JSX. In plain JavaScript, assigning a new value to a variable mutates memory, but it does not tell React to run the component again. Without a render pass, the browser continues displaying the JSX produced during the initial render. Even if another interaction causes the component to re-render, the function executes from its first line, re-initializing the local variable back to its initial value. Furthermore, moving the variable outside the component creates a module-level variable that is shared by every instance on the page, breaking isolation and still failing to trigger updates. To manage interactive data, React provides the `useState` Hook, which reserves memory outside the component function and returns a setter function that queues a render. ◼ Educational objective: expose the failures of plain local assignments and module variables, motivating the state pair.

- [p] ◇ {core questions: seven governing laws of component state} This chapter investigates seven core questions. **Why does reassigning a local variable fail to update the number on the screen?** **How does `useState` pair a value with a setter function to trigger re-renders?** **Why do ordinary local variables reset back to their initial values when another button re-renders the card?** **How does React remember state values across renders and differentiate multiple `useState` calls?** **Why does each rendered component card keep its own isolated state rather than sharing counts?** **How do we pass an expensive initial calculation so React runs it only once on mount?** **Why does calling a state setter directly inside JSX trigger an infinite render loop, and how do we wire handlers correctly?** ◼ Educational objective: outline the seven roadmap questions for the chapter.

### Why local variable assignment fails to update the display

- [runway] Plain local variables, memory mutation, and render requests, used by Question 1.

- [p] ★ {preknowledge: local variables and JSX expression evaluation} In Lecture 1, we learned that user interfaces reflect application data. In Lecture 4, we saw that placing a JavaScript variable inside JSX curly braces like `{likes}` outputs its value into the rendered HTML. When a component loads, JavaScript initializes local variables declared with `let` or `const` and evaluates JSX expressions during that initial execution. ◼ Educational objective: recall local variable initialization and JSX embedding.

- [p] ★ {mechanism: assignments do not notify the React runtime} When a user clicks a button and an event handler executes `likes = likes + 1`, JavaScript updates the number stored in local memory. However, React has no mechanism to watch plain variable reassignments. React updates the screen only when it executes the component function again to compute a new JSX element tree. Because a plain assignment does not notify React or schedule a render, React never re-runs the component. The DOM continues to display the JSX generated during the very first render pass, leaving the count stuck at `0` on screen while the console logs higher numbers. ◼ Educational objective: demonstrate why variable reassignments fail to trigger UI updates.

- [code] Plain local variable mutation:

```jsx title="Local Variable Assignment"
function StoryCard() {
  let likes = 0; // Local variable React does not track
  function handleLike() {
    likes = likes + 1; // Mutates local variable in memory
    console.log('likes:', likes); // Logs 1, 2, 3 in console
  }
  return <button onClick={handleLike}>Likes: {likes}</button>;
}
```

- [code] Declarative state pair introduction:

```jsx title="Declarative State Introduction"
import { useState } from 'react'; // Named import from React
function StoryCard() {
  const [likes, setLikes] = useState(0); // State reserved in React
  function handleLike() {
    setLikes(likes + 1); // Queues a re-render with next value
  }
  return <button onClick={handleLike}>Likes: {likes}</button>;
}
```

◼ **The what-this-introduces list:** 1. `local variable`: function-scoped variable that React does not watch. 2. `render trigger`: an explicit request that tells React to re-execute a component.

### The state pair and the setter function

- [runway] `useState`, Hook definition, array destructuring, state variable, and setter function, used by Question 2.

- [p] ★ {preknowledge: named imports and array destructuring} In Lecture 8, we learned to import named utilities using curly braces. In JavaScript, array destructuring `const [first, second] = array` allows unpacking values from an array into distinct variable names. ◼ Educational objective: recall named imports and array destructuring syntax.

- [p] ★ {mechanism: declaring state and scheduling updates via setters} A **Hook** is a specialized function starting with `use` that is available only while React renders components. The `useState` Hook is React's built-in tool for giving a component memory. When called as `useState(initialValue)`, it returns an array with exactly two elements: the current **state variable** for this render, and a **setter function**. The state variable is declared with `const` because its value represents a static snapshot for the current render. To change the value, application code must invoke the setter function: `setLikes(likes + 1)`. Calling the setter writes the new value into React's internal storage and schedules a re-render. Attempting to assign `likes = likes + 1` directly throws a `TypeError: Assignment to constant variable`. ◼ Educational objective: derive the state pair anatomy and explain why setters are required.

- [code] State pair declaration and update:

```jsx title="State Pair Usage"
import { useState } from 'react';
function StoryCard() {
  const [likes, setLikes] = useState(0); // Pair: current value and setter
  function handleLike() {
    setLikes(likes + 1); // Schedules render with updated value
  }
  return <button onClick={handleLike}>Likes: {likes}</button>;
}
```

◼ **The what-this-introduces list:** 1. `useState`: React Hook that reserves stateful memory. 2. `Hook`: function prefixed with `use` available during render. 3. `state variable`: constant holding the current render value. 4. `setter function`: function that stores the next value and schedules a render. 5. `array destructuring`: syntax unpacking the state pair.

### Component function re-execution and local variable reset

- [runway] Component render lifecycle, function execution from top to bottom, and local variable re-initialization, used by Question 3.

- [p] ★ {preknowledge: pure function execution} In Lecture 12, we learned that React components are pure functions. React calls component functions whenever an update is scheduled. ◼ Educational objective: recall pure function calling in React.

- [p] ★ {mechanism: local variables discard state on every invocation} A React component is a plain JavaScript function. When a state setter like `setIsBookmarked` executes, React schedules a re-render and calls `StoryCard` again from the very first line. Every time a function is called in JavaScript, its local scope is created fresh. Any statement such as `let likes = 0` executes again, resetting the variable back to zero. The memory from previous calls is wiped clean. If a developer attempts to store a counter in a local `let` variable alongside a stateful bookmark toggle, clicking Like increases the count in memory, but toggling the bookmark re-executes the function and silently wipes `likes` back to `0`. ◼ Educational objective: prove why local variables cannot survive component re-renders.

- [code] Local variable reset during re-render:

```jsx title="Local Variable Reset Demonstration"
function StoryCard() {
  let likes = 0; // Runs on every render, resetting to 0
  const [saved, setSaved] = useState(false); // State survives renders
  function handleLike() {
    likes = likes + 1; // Changes memory for this render only
  }
  return <button onClick={() => setSaved(!saved)}>Save</button>;
}
```

◼ **The what-this-introduces list:** 1. `function re-execution`: React invoking the component function from line 1 on every render. 2. `local variable reset`: re-initialization of local variables upon every invocation.

### How React stores state and matches calls by order

- [runway] React internal fiber storage, Hook call order, and multiple state variables, used by Question 4.

- [p] ★ {preknowledge: multiple hooks in a single component} Components frequently manage multiple pieces of interactive data, such as a counter and a boolean toggle. ◼ Educational objective: motivate multiple state declarations in one component.

- [p] ★ {mechanism: state lives in React and aligns by call index} If `useState(0)` executes on every render, why does `likes` not reset back to `0` like `let likes = 0` does? The reason is that state does not live inside the component function; it lives outside the function in React's internal storage node (the fiber). On the initial render, React stores the initial argument `0`. On subsequent renders, React ignores the argument `0` and retrieves the value stored in React's memory. When a component calls `useState` multiple times, React keeps an ordered list of state cells for that component instance. React pairs each `useState` call to its stored data by its position in the call sequence: call 1 maps to slot 1, and call 2 maps to slot 2. ◼ Educational objective: explain how React preserves state outside the component and aligns hooks by call order.

- [code] Multiple state variables and call order:

```jsx title="Multiple State Variables"
function StoryCard() {
  const [likes, setLikes] = useState(0); // Hook slot 1: like count
  const [saved, setSaved] = useState(false); // Hook slot 2: bookmark status
  return (
    <article>
      <button onClick={() => setLikes(likes + 1)}>Likes: {likes}</button>
      <button onClick={() => setSaved(!saved)}>{saved ? 'Saved' : 'Save'}</button>
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `React internal storage`: memory structure holding state outside the function. 2. `Hook call order`: deterministic sequence React uses to identify state cells.

### Component instances and state isolation

- [runway] Component instances, independent state trees, and module-level variable pitfalls, used by Question 5.

- [p] ★ {preknowledge: reusable component tags} In Lecture 5, we learned that a component definition can be rendered multiple times as separate elements in JSX, such as `<StoryCard />` rendered twice in `App`. ◼ Educational objective: recall component reuse in the UI tree.

- [p] ★ {mechanism: state belongs to rendered instances, not function definitions} When a component is rendered multiple times, each rendered element is a distinct **component instance**. React allocates a separate, isolated state storage record for each instance on the page. Clicking Like on the first `StoryCard` updates only that card's state; the second card's state remains untouched. If a developer attempts to solve the local variable reset problem by moving `let likes = 0` outside the component to module scope, all card instances share that single variable, corrupting isolation and still failing to trigger renders. ◼ Educational objective: derive component instance isolation and contrast with module variables.

- [code] Instance isolation versus module variable:

```jsx title="Component Instances"
function App() {
  return (
    <div>
      <StoryCard title="Story A" /> {/* Independent state instance 1 */}
      <StoryCard title="Story B" /> {/* Independent state instance 2 */}
    </div>
  );
}
```

◼ **The what-this-introduces list:** 1. `component instance`: a specific mounted occurrence of a component in the tree. 2. `isolated state`: private memory allocated per component instance.

### Initializer functions for expensive initial state

- [runway] Initial state argument evaluation, initializer functions, and `StrictMode` double-invocation, used by Question 6.

- [p] ★ {preknowledge: function arguments and JavaScript execution timing} In JavaScript, expressions passed as function arguments evaluate immediately when the outer function is called. ◼ Educational objective: recall JavaScript argument evaluation.

- [p] ★ {mechanism: passing a function reference defers execution to mount} When passing an initial value to `useState(readSavedLikes(id))`, JavaScript executes `readSavedLikes(id)` on every single render pass, even though React uses the initial value only on the initial mount and discards it thereafter. If the initialization involves reading storage or parsing data, this causes unnecessary performance overhead. To avoid running the calculation on every render, pass an **initializer function**: `useState(() => readSavedLikes(id))`. When passed a function, React invokes it only during the initial mount. In development under `StrictMode`, React calls the initializer twice to check for side-effect purity, but keeps one result. ◼ Educational objective: derive the initializer function pattern for expensive initial state.

- [code] Initializer function pattern:

```jsx title="Expensive Initial State"
function StoryCard({ storyId }) {
  // Pass a function to run only on initial mount
  const [likes, setLikes] = useState(() => readSavedLikes(storyId));
  return <button onClick={() => setLikes(likes + 1)}>Likes: {likes}</button>;
}
```

◼ **The what-this-introduces list:** 1. `initializer function`: function passed to `useState` that React executes only on mount.

### Wiring setters in event handlers to prevent render loops

- [runway] JSX curly brace evaluation, immediate invocation versus callback reference, and infinite render loops, used by Question 7.

- [p] ★ {preknowledge: passing functions to event handlers} In Lecture 13, we learned that event props like `onClick` must be passed a function reference, not an immediate function invocation. ◼ Educational objective: recall event handler wiring rules.

- [p] ★ {mechanism: invoking setters during render triggers infinite loops} When a developer writes `<button onClick={setLikes(likes + 1)}>`, JavaScript executes `setLikes(likes + 1)` immediately during the render pass because curly braces evaluate expressions. Calling the setter requests a new render before the current render finishes. React immediately begins the next render, which executes `setLikes` again, creating an infinite loop. React aborts the loop by throwing `Too many re-renders. React limits the number of renders to prevent an infinite loop`. To wire the setter properly, wrap it in an inline arrow function: `onClick={() => setLikes(likes + 1)}` or pass a handler reference. ◼ Educational objective: explain the cause and fix of the "Too many re-renders" crash.

- [code] Immediate setter call vs arrow wrapper:

```jsx title="Event Handler Setter Wiring"
function StoryCard() {
  const [likes, setLikes] = useState(0);
  // Correct: wrapped in an arrow function that waits for a click
  return <button onClick={() => setLikes(likes + 1)}>Like</button>;
}
```

◼ **The what-this-introduces list:** 1. `render-phase setter call`: invoking a state setter during component rendering. 2. `infinite render loop`: recursive render cascade triggered by render-phase state changes.

### [question-cycle] Plan 1: Plain variable assignment fails to update the display
- **Question**: "I add 1 to `likes` on every click, and the console counts 1, 2, 3. Why does the screen still say 0 likes?"
- **Code and result**: In `StoryCard`, `let likes = 0; function handleLike() { likes = likes + 1; console.log(likes); } return <button onClick={handleLike}>Likes: {likes}</button>;`. Clicking the button three times logs `1`, `2`, `3` in the console, but the screen stays stuck on `Likes: 0`.
- **Verdict**: **The code does not do what we wanted.**
- **Answer**: In JavaScript, assigning `likes = likes + 1` mutates a local variable in memory. However, React has no knowledge of plain variable assignments. React updates the screen only when it executes the component function again to compute a new JSX description, and a plain assignment does not request a render.
- **Fix**: Declare the value with `useState` and update it using its setter function (taught in Principle 2).
- **Rule with boundary**: IF a value must change the screen when updated, THEN store it in React state rather than a plain local variable.
- **Needs**: `local variable`, `render trigger`.
- **Diagram**:
```text
  [ User Click ] ──> [ likes = likes + 1 ] ──> Local Memory: 1, 2, 3
                            │
                            ▼
                    React NOT Notified
                            │
                            ▼
                 Screen Stays at "0 likes"
```

### [question-cycle] Plan 6: Pass expensive start values as initializer functions
- **Question**: "I read the saved like count with `useState(readSavedLikes(story.id))`. Why does `readSavedLikes` run again on every click?"
- **Code and result**: In `StoryCard`, calling `useState(readSavedLikes(story.id))` where `readSavedLikes` logs to console. Clicking Like three times logs four calls to `readSavedLikes`, even though React ignores the start value after mount.

- **Answer**: JavaScript evaluates function arguments before calling `useState`. Passing `readSavedLikes(story.id)` executes the calculation on every render pass. Passing a function reference `useState(() => readSavedLikes(story.id))` instructs React to run the calculation only during the initial mount.
- **Fix**: Wrap the initialization call in an arrow function: `useState(() => readSavedLikes(story.id))`.
- **Rule with boundary**: IF initializing state from an expensive calculation or saved data, THEN pass a function reference or initializer arrow to `useState`.
- **Needs**: `initializer function`.
- **Diagram**:
```text
  Direct Call:   useState(expensive()) ──> Runs expensive() on EVERY render
  Function Ref:  useState(() => expensive()) ──> Runs expensive() on MOUNT ONLY
```

:::principle-box{title="PASS A SLOW START VALUE AS A FUNCTION, SO REACT RUNS IT ONCE" handle="initial-value-once"}
#### PREFER THIS:
```jsx
// Initializer function runs once during initial mount
function StoryCard({ storyId }) {
  const [likes, setLikes] = useState(() => readSavedLikes(storyId));
  return <button onClick={() => setLikes(likes + 1)}>Likes: {likes}</button>;
}
```

#### DO NOT DO THIS:
```jsx
// Evaluates expensive function call on every render pass
function StoryCard({ storyId }) {
  const [likes, setLikes] = useState(readSavedLikes(storyId));
  return <button onClick={() => setLikes(likes + 1)}>Likes: {likes}</button>;
}
```

*Pass an **initializer function** to `useState` so expensive calculations execute only during the initial mount rather than on every render.*

### [question-cycle] Plan 7: Call the setter in a handler, never while rendering
- **Question**: "I wrote `onClick={setLikes(likes + 1)}`. Why does the page crash with 'Too many re-renders' before I click anything?"
- **Code and result**: In `StoryCard`, writing `<button onClick={setLikes(likes + 1)}>Like</button>`. The page crashes during load with `Too many re-renders. React limits the number of renders to prevent an infinite loop.`
- **Verdict**: **The code does not do what we wanted.**
- **Answer**: Curly braces in JSX evaluate expressions immediately during the render pass. Calling `setLikes(likes + 1)` invokes the setter while rendering, queuing another render, which calls `setLikes` again in an infinite loop. Setters must be passed inside an uncalled callback function.
- **Fix**: Wrap the setter call in an arrow function: `onClick={() => setLikes(likes + 1)}`.
- **Rule with boundary**: IF wiring a state setter to an event listener, THEN wrap the call in a function rather than invoking it directly in JSX.
- **Needs**: `render-phase setter call`, `infinite render loop`.
- **Diagram**:
```text
  Render Pass ──> Evaluates onClick={setLikes(...)} ──> Schedules Render
       ▲                                                       │
       └───────────────────────────────────────────────────────┘
                     Infinite Loop (Crash!)
```

:::principle-box{title="CALL THE SETTER IN A HANDLER, NEVER WHILE THE COMPONENT RENDERS" handle="setter-in-handler"}
#### DO THIS:
```jsx
// Defers setter execution until the user clicks
function StoryCard() {
  const [likes, setLikes] = useState(0); {/* State constant */}
  return <button onClick={() => setLikes(likes + 1)}>Like</button>;
}
```

#### DO NOT DO THIS:
```jsx
// Invokes setter during render, causing infinite loop
function StoryCard() {
  const [likes, setLikes] = useState(0); {/* State constant */}
  return <button onClick={setLikes(likes + 1)}>Like</button>;
}
```

*Avoid a **render-phase setter call** in JSX expressions; wrap setter calls in functions to prevent an **infinite render loop**.*
:::
