### The Friction of Ephemeral Variables in Component Functions

- [p] ★ {preknowledge: JSX markup, component functions returning descriptors, event handlers with onClick} In previous lessons, you learned that React components are JavaScript functions that calculate JSX markup. In Lecture 13, you wired user interactions by passing event handler functions to `onClick`. When a user clicks a button, browser events execute JavaScript handlers in memory. However, user interfaces are not static documents; users click buttons, toggle bookmarks, and expect numbers to change on screen. In traditional programming, developers declare a variable like `let count = 0` and increment it with `count = count + 1`. When developers bring this habit into React, they place a local variable inside their component function. But when the user clicks the button, the headline or counter never changes. The number on the screen stays stuck at zero, even though the click handler executes and increments the variable in JavaScript memory. ◼ Educational objective: recall component functions and event handlers while introducing the core friction where local variable assignment fails to update the user interface.
- [p] ★ {problem: local variable assignment fails to trigger a render and resets on every call} It is possible that a developer may declare `let likes = 0` inside an article card component, expecting the variable to hold its value across user interactions. When the user clicks the button, `handleLike` increments the variable: `likes = likes + 1`. In the browser console, `console.log(likes)` prints `1`, `2`, and `3`. But the screen never updates. Two distinct platform facts cause this failure. First, assigning a local variable changes a memory slot that React does not track; an assignment never asks React to render the component again. Second, whenever another interaction causes the component to render, React calls the component function from the first line. Each function call allocates fresh local variables, resetting `likes` back to `0`. ◼ Educational objective: analyze the dual platform failures of local variables: lack of render triggering and complete memory reset on re-render.
- [p] ★ {old solution: imperative DOM mutation or global module-level variables} In traditional browser scripting, developers reached into the DOM directly using `element.textContent = likes` to force the screen to match their variable. In React, components never mutate DOM nodes directly. Seeing local variables reset, some developers try moving `let likes = 0` outside the component function at the module level. A module-level variable survives function calls, but assigning it still never tells React to render. Even worse, if the page mounts two cards, both cards share that single variable, corrupting independent counts. ◼ Educational objective: contrast legacy manual DOM mutation and fragile module-level variables with idiomatic component state.

- [code] Naive Local Variable Counter:

```jsx title="Naive Local Variable Counter"
export default function StoryCard({ title }) {
  let likes = 0; // Local variable resets on every render
  function handleLike() {
    likes = likes + 1; // Assigns new value in local memory
    console.log('clicked, likes =', likes);
  }
  return (
    <article className="story-card">
      <h3>{title}</h3>
      <button type="button" onClick={handleLike}>
        {likes} likes
      </button>
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `let likes = 0`: local variable declared inside component function scope. 2. `likes = likes + 1`: plain JavaScript assignment changing local memory without notifying React. 3. `console.log(...)`: observable console output showing counter advancing in memory while the screen stays unchanged.

- [p] ★ {mechanism: component memory with useState, persistent state records, and setter functions} React solves both problems with the `useState` Hook. When you call `useState`, React gives the component a private memory slot that lives outside the function body. Calling `useState(0)` returns a two-item array: the current state value for this render, and a setter function that updates it. When you call the setter (`setLikes(likes + 1)`), React stores the next value in its internal records and schedules a render. When React calls the component function again, `useState` returns the updated value, and React updates the screen to display the new count. ◼ Educational objective: establish the mechanics of useState, explaining how it preserves data across renders and triggers UI updates through its setter function.

### Component Memory and the Execution Cycle

- [p] ◇ {conceptual grounding: functions as ephemeral calculators versus stateful components} In standard JavaScript, functions are ephemeral calculators. You pass arguments into a function, the function allocates local variables in memory, returns a result, and finishes. When execution ends, the JavaScript engine cleans up local variables. In earlier lessons, you saw that React components follow this exact functional contract: `StoryCard` receives props, executes its body, and returns a JSX descriptor tree. If React treated components strictly as ordinary functions, every interactive feature (like search fields, tabs, or like buttons) would lose its data between interactions. To build interactive user interfaces, components require component memory: private data that survives across renders. ◼ Educational objective: ground the necessity of component memory in standard JavaScript function lifecycle limits.
- [p] ★ {runtime distinction: the render execution cycle and local variable allocation} To understand why ordinary variables forget, we must examine the React execution cycle. When a user interacts with a page, React executes a render pass: it calls your component function again to compute the next visual output. Every call to a function starts from the top. The statement `let likes = 0` runs from scratch on every single execution. Even if a user clicked a button ten times, any new render pass wipes the previous function scope and creates a brand-new `likes` variable initialized to `0`. A local variable belongs strictly to one execution of the function. It cannot survive to the next execution because its scope is destroyed when the function returns. ◼ Educational objective: trace the physical execution path of a component function call to show how local variables are destroyed upon return.
- [p] ★ {architectural model: useState as a portal to external React memory} React provides `useState` to bridge this gap. `useState` is a **Hook**: a special function provided by React that lets your component hook into React features. When you call `useState(0)`, you tell React: "Reserve a memory slot for this component, start it at 0, and give me access to it." `useState` returns an array containing exactly two items: the current state value for this render, and a **setter function**. The setter function is the only way to modify that memory slot. When you call the setter, it updates the stored value inside React and asks React to render the component again. ◼ Educational objective: establish the architectural model of useState as a connection to persistent component records managed outside the component function.
- [p] ◇ When declaring state with `useState`, developers choose how to unpack the returned two-item array:
- [p] ◇ - **Option 1 (The Foundational Way: Direct Array Indexing)**: Store the returned array in a single variable and access items using bracket notation (`result[0]` and `result[1]`).
- [p] ◇ - **Option 2 (The Modern Idiomatic Way: Array Destructuring Assignment)**: Unpack both items directly in a single line using JavaScript array destructuring (`const [likes, setLikes] = useState(0)`).

- [code] Option 1: The Foundational Way (Direct Array Indexing):

```jsx title="Option 1: The Foundational Way (Direct Array Indexing)"
export default function StoryCard({ title }) {
  const likesState = useState(0); // Returns two-item array [value, setter]
  const likes = likesState[0]; // Reads current value at index 0
  const setLikes = likesState[1]; // Reads setter function at index 1
  return (
    <button type="button" onClick={() => setLikes(likes + 1)}>
      {likes} likes
    </button>
  );
}
```

- [p] ★ In Option 1, the variable `likesState` holds the raw two-item array returned by `useState(0)`. Index `0` holds the current value (`0`), and index `1` holds the setter function (`setLikes`). While this exposes the exact data structure React provides, writing index lookups across components creates visual clutter and increases the risk of indexing mistakes. ◼ Educational objective: demonstrate the raw array returned by useState to prove how index 0 and index 1 map to state and setter.

- [code] Option 2: The Modern Idiomatic Way (Array Destructuring):

```jsx title="Option 2: The Modern Idiomatic Way (Array Destructuring)"
export default function StoryCard({ title }) {
  const [likes, setLikes] = useState(0); // Unpacks pair directly in one line
  return (
    <button type="button" onClick={() => setLikes(likes + 1)}>
      {likes} likes
    </button>
  );
}
```

- [p] ★ In Option 2, modern JavaScript **array destructuring** unpacks the two items directly at the point of declaration. The square brackets on the left side of the assignment tell JavaScript to assign item `0` to the identifier `likes` and item `1` to `setLikes`. This is the universal standard in React development. By community convention, developers name the pair `[something, setSomething]` to make state reading and state updating immediately clear. ◼ Meaningful pedagogical commentary: explain array destructuring syntax and the universal naming convention.

> [!PRINCIPLE]
> **Principle 1: Assigning a Local Variable Never Triggers a Render**
> React updates the screen only when it renders a component again to calculate fresh JSX markup. Assigning a new value to a local variable changes memory that React does not track, so React never schedules a render. When you increment a local variable inside an event handler, the variable changes in the background while the screen keeps showing the old value.

- [p] ★ Principle 1 operational derivation: In browser JavaScript, assigning a value to a variable modifies a memory address allocated by the JavaScript engine. When you write `likes = likes + 1`, the CPU increments the integer stored in that local slot. However, React does not wrap local variables in proxies or listen to memory assignments. The React rendering engine operates on a pull model: it only calls a component when an interaction or parent update explicitly requests a render pass. Because a plain assignment sends zero signal to React, the component never re-renders, no fresh JSX is produced, and the browser DOM remains completely untouched. ◼ Educational objective: derive the physical engine reality that variable assignment modifies untracked memory without notifying React.

> [!PRINCIPLE]
> **Principle 2: Component Calls Run from the Top and Reset Local Variables**
> A React component is a JavaScript function that React calls anew every time it renders. Each render executes the component body from the first line, allocating all local variables fresh with their initial values. When a render occurs, previous local variables disappear, so any value stored in a local variable resets back to its starting declaration.

- [p] ★ Principle 2 operational derivation: When a component renders, JavaScript executes the function body from line 1. The statement `let likes = 0` runs every time. Even if another interaction (such as toggling a bookmark) causes React to render the card, the function runs from the top. When the function returns, its execution context closes and its local variables are destroyed. In Lecture 12, you learned that React components must remain pure calculations that can be called repeatedly. Because React may call a component function at any time, local variables cannot preserve state across calls. ◼ Educational objective: derive why function execution lifecycle guarantees that local variables reset to their initial values on every render.

> [!PRINCIPLE]
> **Principle 3: Store Persistent Interactive Data in State and Update It Through the Setter**
> When data must survive between renders and update the screen, declare a **state variable** by calling the `useState` **Hook**. React returns a pair containing the current value and a **setter function**. We update the value exclusively by calling the setter with the next value, which stores the data inside React and requests a fresh render.
> 
> >> state variable : a value held by React that persists across component renders
> >> Hook : a special function starting with use that lets a component tap into React features
> >> setter function : a function returned by useState that updates state and asks React to render
> 
> *We should do this:*
> `const [likes, setLikes] = useState(0);`
> `setLikes(likes + 1); // Updates React memory and requests a fresh render`
> 
> *We should not do this:*
> `const [likes, setLikes] = useState(0);`
> `likes = likes + 1; // Throws TypeError: Assignment to constant variable`

- [p] ★ Principle 3 operational derivation: To preserve data across renders, React stores state values outside the component function in internal memory cells. When you call `useState(0)`, React checks whether an existing value exists for this component cell. If not, it stores `0`. It returns that value and a setter function (`setLikes`). Calling `setLikes(1)` does two things: it stores `1` in React's internal cell, and it queues a render pass. During the next render, React calls `StoryCard` again. This time, `useState(0)` looks at its internal cell, finds `1`, and returns `[1, setLikes]`. The JSX calculates markup using `1`, and the screen updates to display `1 likes`. Notice that state variables are declared as `const`. You cannot assign directly to a state variable; doing so throws `TypeError: Assignment to constant variable.` Calling the setter is the only door to updating state. ◼ Educational objective: trace the two-part operation of setter functions: updating React memory and queueing a render pass.

> [!PRINCIPLE]
> **Principle 4: React Stores State Outside the Function and Matches Calls by Order**
> State does not live inside the component function; React holds state externally in an ordered list tied to that component. On the initial render, React saves the initial value for each `useState` call. On every subsequent render, React ignores the argument and returns the stored value matching that call's position in the execution sequence.
> 
> >> call order : the exact sequential order in which a component invokes its Hooks on each render

- [p] ★ Principle 4 operational derivation: A common mystery for developers is: "If `useState(0)` executes on every render, why doesn't `likes` reset to 0?" The answer lies in where state lives. When React mounts a component, it creates an internal array of state cells for that specific component in the tree. Before rendering, React initializes an internal index pointer to `0`. When your component calls `useState(0)` the first time, React notes index `0`, records `0`, and increments the index to `1`. If your component makes a second call, `useState(false)`, React notes index `1`, records `false`, and increments the index to `2`. On subsequent renders, React resets its internal pointer to `0`. Call 1 asks for state; React checks index `0`, finds the existing value (e.g. `2`), returns it, and advances the pointer. Call 2 asks for state; React checks index `1`, finds `true`, returns it, and advances the pointer. Because React matches state calls strictly by their sequential call order, Hooks must always be called at the top level of the component, never inside conditional branches or loops (a rule explored in Lecture 37). ◼ Educational objective: deconstruct the internal array and call order pointer mechanism that allows React to match useState calls to stored values.

- [code] Multiple State Variables Matched by Order:

```jsx title="Multiple State Variables Matched by Order"

export default function StoryCard({ title }) {
  const [likes, setLikes] = useState(0); // Slot 0 in React memory
  const [isSaved, setIsSaved] = useState(false); // Slot 1 in React memory
  console.log('render values:', likes, isSaved);
  return (
    <div>
      <button type="button" onClick={() => setLikes(likes + 1)}>{likes} likes</button>
      <button type="button" onClick={() => setIsSaved(!isSaved)}>
        {isSaved ? 'Saved' : 'Save'}
      </button>

  );
}
```

> [!PRINCIPLE]
> **Principle 5: State Is Completely Private and Isolated to Each Component Instance**
> State belongs to a specific **component instance** at its exact position in the render tree, not to the component function definition. When you render multiple copies of the same component side by side, React creates an independent memory record for each one. Updating state in one instance re-renders only that instance and leaves all sibling instances untouched.
> 
> >> component instance : a specific copy of a component mounted at a distinct location in the UI tree

- [p] ★ Principle 5 operational derivation: In JavaScript, a module-level variable is shared by all functions in that file. In contrast, React state is tied to the physical component instance in the UI tree. If you render `<StoryCard />` twice inside `App.jsx`, React instantiates two distinct nodes in the tree: Instance A and Instance B. Instance A receives its own private array of state cells (`likes = 0`, `isSaved = false`). Instance B receives a completely separate private array of state cells (`likes = 0`, `isSaved = false`). When a user clicks Like on Instance A, Instance A's setter fires, updating only Instance A's memory and re-rendering only Instance A. Instance B is completely unaware of the interaction and retains its original count. The parent component `App` cannot read or modify the private state of either card directly. In Lecture 23, you will learn how to lift state upward when two components genuinely need to share synchronized data. ◼ Educational objective: analyze the physical isolation of component state records across multiple tree instances.

> [!PRINCIPLE]
> **Principle 6: Pass an Initializer Function for Expensive Initial State**
> React reads the `useState` argument only on the first render and ignores it on all later renders. However, if you pass a function call like `useState(calculateTotal())`, JavaScript runs that function on every render anyway. When computing an initial value is expensive, pass an **initializer function** reference (`useState(calculateTotal)`) so React runs it strictly on the initial render.
> 
> >> initializer function : a function passed to useState that React calls only on the initial render to compute starting state
> 
> *It is best practice to do this:*
> `const [likes, setLikes] = useState(getInitialLikes); // React calls function once on initial render`
> 
> *Instead of doing this:*
> `const [likes, setLikes] = useState(getInitialLikes()); // Runs expensive calculation on every render`

- [p] ★ Principle 6 operational derivation: When JavaScript executes code, it evaluates function arguments before calling the outer function. If you write `useState(getInitialLikes())`, JavaScript executes `getInitialLikes()` first, and passes its return value into `useState`. On the initial render, React uses that return value. On the second and third renders, React already has the stored state in its internal cell, so it completely ignores the argument you passed. However, the calculation already ran and consumed CPU time! If `getInitialLikes` reads from `localStorage` or parses thousands of records, your component suffers unnecessary performance overhead on every click. When you pass the function reference without parentheses (`useState(getInitialLikes)`), you hand the recipe to React. React checks if this is the initial render; if it is, React calls `getInitialLikes()` once. On subsequent renders, React skips calling the function entirely. Note that in development mode under `StrictMode`, React calls initializer functions twice on mount to verify that they are pure calculations with zero side effects. ◼ Educational objective: prove why function calls in useState arguments execute on every render and how initializer function references eliminate wasted computations.

    <button type="button" onClick={() => setLikes(likes + 1)}>
      {likes} likes
    </button>
  );
}
```

◼ **The what-this-introduces list:** 1. `getInitialLikes`: standalone initializer function returning calculated starting state. 2. `useState(getInitialLikes)`: passing function reference uncalled. 3. `console.log(...)`: verification that initializer executes only on initial mount.

- [p] ★ {step 2: interactive story card encapsulates private state and handlers} In `src/components/StoryCard.jsx`, we construct the interactive card component. ```jsx title="src/components/StoryCard.jsx" startLine="1" continues="bottom"
import { useState } from 'react';
export default function StoryCard({ title }) {
  const [likes, setLikes] = useState(0); // State slot 0: like counter
  const [isBookmarked, setIsBookmarked] = useState(false); // State slot 1: toggle
  function handleLike() {
    setLikes(likes + 1); // Queues render with next like total
  }
  function handleBookmark() {
    setIsBookmarked(!isBookmarked); // Inverts boolean bookmark state
  }
```

### Glossary

- **State Variable** ◼ A persistent value managed by React that survives across component renders and drives the user interface.
- **Setter Function** ◼ A function returned by `useState` that stores the next state value inside React and schedules a re-render.
- **Hook** ◼ A special function provided by React whose name starts with `use` that allows components to connect to React runtime features.
- **Array Destructuring** ◼ A JavaScript syntax pattern using square brackets (`const [a, b] = array`) to unpack array elements into distinct local variables.
- **Initializer Function** ◼ A function passed by reference to `useState` that React executes only during initial component mounting to compute starting state.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Local Variables vs Component State

➔ ALWAYS store data that must survive renders and update the screen in a state variable via `useState`.

➔ NEVER rely on local function variables (`let count = 0`) to preserve interactive data across renders.

**DO THIS:** declare persistent interactive data with the useState Hook

```jsx right
function StoryCard() {
  const [likes, setLikes] = useState(0);
  return <button type="button" onClick={() => setLikes(likes + 1)}>{likes} likes</button>;
}
```

**DO NOT DO THIS:** mutate local variables expecting the user interface to update

```jsx wrong
function StoryCard() {
  let likes = 0;
  return <button type="button" onClick={() => { likes = likes + 1; }}>{likes} likes</button>;
}
```

❒ State Update Invariants

➔ ALWAYS update component state by invoking the setter function returned by `useState`.

➔ NEVER assign directly to a state variable (`likes = likes + 1`).

**DO THIS:** invoke setter functions to update state and schedule a render

```jsx right
function BookmarkToggle() {
  const [saved, setSaved] = useState(false);
  return <button type="button" onClick={() => setSaved(!saved)}>Save</button>;
}
```

**DO NOT DO THIS:** attempt direct assignment on state variables

```jsx wrong
function BookmarkToggle() {
  const [saved, setSaved] = useState(false);
  return <button type="button" onClick={() => { saved = !saved; }}>Save</button>;
}
```

❒ Initial State Performance

➔ ALWAYS pass an initializer function reference when calculating starting state requires expensive computations.

➔ NEVER call expensive functions directly inside `useState` arguments on every render.

**DO THIS:** pass initializer function references to execute calculations only on mount

```jsx right
function Feed() {
  const [items, setItems] = useState(loadInitialItems);
  return <div>{items.length} items</div>;
}
```

**DO NOT DO THIS:** invoke expensive functions directly inside the useState call

```jsx wrong
function Feed() {
  const [items, setItems] = useState(loadInitialItems());
  return <div>{items.length} items</div>;
}
```

| | **LOCAL VARIABLE**<br>(Ephemeral Scope) | **USESTATE HOOK**<br>(Component Memory) |
| ---: | :--- | :--- |
| **Persistence** | Destroyed when component function completes; resets to 0 | Preserved by React in external records across renders |
| **Screen updates** | Reassignment sends zero signal; UI never updates | Setter stores next value and schedules a render pass |
| **Instance scope** | Local to single execution context | Strictly private and isolated to each mounted instance |
| **Hook call order** | Unordered; standard JavaScript variable scoping | Matched by stable call order index on every render |
| **Initialization** | Evaluated on every single function execution | Evaluated once on mount; initializer functions run once |
