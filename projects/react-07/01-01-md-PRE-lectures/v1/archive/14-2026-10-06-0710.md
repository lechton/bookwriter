### The Friction of Forgotten Variables and Silent Clicks

- [p] ★ {preknowledge: JSX expressions, pure components, event handlers} In earlier lessons, you learned that React components are functions that turn props into JSX markup. In Lecture 13, you wired button clicks to event handlers using function references. However, web interfaces must also remember user interactions across time. When a reader clicks a like button, bookmarks an article, or types a comment, the screen must display the updated value. In traditional JavaScript, developers assigned values to local variables or modified DOM properties directly. When developers bring that mental model to React, they often write `let likes = 0` inside their component and increment it on click (`likes = likes + 1`). When they test this code in the browser, clicking the button changes nothing on the screen: the count remains stuck at zero. ◼ Educational objective: recall event handlers from Lecture 13 and identify the friction where assigning a local variable fails to update the user interface.
- [p] ★ {problem: local variable assignments fail to trigger renders and reset on every render} It is possible that a junior developer assumes that modifying a variable in memory automatically updates the page. They might think: "I added one to likes, so the paragraph should display one." But React does not observe plain variable assignments. An assignment like `likes = likes + 1` alters a number in JavaScript memory, but it never asks React to calculate new JSX. Even worse, if another interaction re-renders the card, the component function executes from the top, re-running `let likes = 0` and erasing the counter back to zero. ◼ Educational objective: establish the twin failures of local variables: no render request and complete loss of memory across render cycles.
- [p] ★ {old solution: mutating local variables or global module variables} A developer experiencing this friction might try two naive workarounds: reassigning a local `let` variable inside the function, or moving `let likes = 0` outside the component to the module level. Mutating the local variable leaves the screen stuck. Moving the variable to the module level keeps the count in memory, but it still triggers no render, and every card instance on the page shares the exact same number. ◼ Educational objective: contrast naive local mutation and shared module-level state against React component memory.

- [code] Naive Counter Attempt:

```jsx title="Naive Counter Attempt"
export default function StoryCard({ title }) {
  let likes = 0; // Local variable declared inside component
  function handleLike() {
    likes = likes + 1; // Mutates local variable silently
    console.log('clicked, likes =', likes);
  }
  return (
    <article className="story-card">
      <h3>{title}</h3>
      <p>{likes} likes</p>
      <button type="button" onClick={handleLike}>Like</button>
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `let likes = 0`: local variable re-created on every function execution. 2. `likes = likes + 1`: plain assignment that fails to notify React. 3. `console.log('clicked, likes =', likes)`: logs showing memory changing while screen stays stuck.

- [p] ★ {mechanism: useState hook providing durable memory and re-render triggers} React solves both problems through a special function called `useState`. When you declare state with `useState`, React stores that value outside the component function in its own internal memory. Calling `useState` gives you two items: the current value to read during this render, and a setter function that stores the next value and queues a re-render. When the setter runs, React calls the component function again, hands back the updated value, and paints the new count on screen. ◼ Educational objective: introduce the useState hook as the unified solution providing durable memory and declarative render triggers.

### Functions That Run from the Top and React's External Memory

- [p] ◇ {conceptual grounding: components as ephemeral functions} To understand component memory, we must look at how JavaScript functions execute. In standard JavaScript, when a function runs, its local variables exist only for the duration of that function call. When the function finishes and returns its result, all local variables are discarded. Because a React component is a standard JavaScript function, React executes the entire function body from top to bottom on every render. If your component declares `let likes = 0`, that line executes every single time React renders the card. In Lecture 12, we learned that React can call a component function at any time, and in development under StrictMode, it may call it twice to verify purity. Therefore, a component cannot rely on its own function scope to remember values across time. ◼ Educational objective: ground component execution in standard JavaScript function mechanics and recall the purity contract from Lecture 12.
- [p] ★ {runtime distinction: React internal memory slots versus local scope} Because the function body cannot hold memory between calls, React stores component state outside the function. Think of React as maintaining an internal shelf of memory slots for each component mounted on the page. When your component calls `useState(0)`, it asks React: "Give me the value stored in my memory slot; if this is the first time I am rendering, store 0 as my initial value." On the initial render, React stores `0` and returns `0` alongside a setter function. When the user clicks the button, your handler calls the setter: `setLikes(likes + 1)`. The setter does two things: it updates the value in React's external memory slot, and it requests a new render. When React renders the component again, the function runs from the top, calls `useState(0)`, but React returns the stored value `1` instead of `0`. ◼ Educational objective: construct the mental model of React's external memory slots and trace the two actions performed by setter functions.
- [p] ★ {syntactic reminder: array destructuring syntax} To read the value and the setter in one clean line, React developers use JavaScript **array destructuring**. The `useState` hook returns an array containing exactly two items: the current state value at index 0, and the setter function at index 1. Writing `const [likes, setLikes] = useState(0)` unpacks those two items into two distinct local variables. The square brackets on the left side of the assignment tell JavaScript to pull the first item into `likes` and the second item into `setLikes`. By community convention, developers name this pair `[something, setSomething]`, making state variables instantly recognizable across projects. ◼ Educational objective: remind the reader how JavaScript array destructuring works and formalize the universal naming convention for state pairs.

> [!PRINCIPLE]
> **Principle 1: Assigning a Local Variable Does Not Ask React to Render**
> React updates what is on the screen only when it renders a component again. Assigning a new value to a local variable changes memory that React does not watch. Because an assignment alone never requests a render, the screen remains stuck on the old value.
>
> *We should do this:*
> `setLikes(likes + 1); // Asks React to render again with the next number`
>
> *We should not do this:*
> `likes = likes + 1; // Assigns local variable without notifying React`

- [p] ★ Principle 1 operational derivation: In plain JavaScript, developers expect changes to variables to take effect immediately. In React, the screen is a declarative projection of state calculated during the render phase. When a user clicks a button and your code executes `likes = likes + 1`, JavaScript increments the number stored in local variable memory. However, React has no mechanism to observe plain JavaScript variable mutations. Because React does not know the number changed, it never schedules a render. The browser never recalculates JSX, and the screen continues displaying the old markup. ◼ Educational objective: prove that plain assignments do not notify React or trigger render cycles.

> [!PRINCIPLE]
> **Principle 2: Each Render Calls the Function Again and Resets Local Variables**
> A React component is a function that React calls from the top every time it renders. Every local variable declared inside the component body is created fresh during that call and vanishes when the function returns. When a component re-renders, its local variables reset back to their initial values.
>
> *We should do this:*
> `const [likes, setLikes] = useState(0); // State value survives across renders in React`
>
> *We should not do this:*
> `let likes = 0; // Local variable resets to zero on every render`

- [p] ★ Principle 2 operational derivation: In Lecture 12, we established that React components must be pure functions that compute their output from incoming inputs. Whenever a component re-renders, React invokes the function again. Just like any normal JavaScript function, each invocation creates a brand-new execution context. Every `let` and `const` declaration inside the body runs from scratch. Any values calculated or modified during the previous render are completely gone. ◼ Educational objective: derive the ephemeral nature of local variables from JavaScript function execution rules and recall Lecture 12.

- [code] Local Variable Reset Proof:

```jsx title="Local Variable Reset"
import { useState } from 'react';
export default function StoryCard({ title }) {
  let likes = 0; // Resets on every render
  const [isBookmarked, setIsBookmarked] = useState(false);
  console.log('render, likes =', likes); // Logs on every render
  function handleLike() {
    likes = likes + 1;
    console.log('clicked, likes =', likes);
  }
  return (
    <article className="story-card">
      <h3>{title}</h3>
      <p>{likes} likes</p>
      <button type="button" onClick={handleLike}>Like</button>
      <button type="button" onClick={() => setIsBookmarked(!isBookmarked)}>
        {isBookmarked ? 'Saved' : 'Save'}
      </button>
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `console.log('render, likes =', likes)`: proof of variable reset on render. 2. `const [isBookmarked, setIsBookmarked]`: state trigger used to force a clean re-render. 3. `{isBookmarked ? 'Saved' : 'Save'}`: ternary conditional display from Lecture 4.

> [!PRINCIPLE]
> **Principle 3: Store Durable Values in State and Update Them Exclusively with Setters**
> To keep data that survives across renders and updates the screen, store it in a state variable using the `useState` Hook. React returns a pair: the current value to read during this render, and a setter function to request the next value. We update state exclusively by calling the setter; reassigning the state variable directly throws a TypeError: Assignment to constant variable.
>
> >> state variable : a value React retains across renders for a component
> >> Hook : a special function starting with use that lets components tap into React features
> >> setter function : a function returned by useState that stores the next state and requests a render
>
> *We should do this:*
> `onClick={() => setLikes(likes + 1)} // Calls setter to store next count and render`
>
> *We should not do this:*
> `onClick={() => { likes = likes + 1; }} // Assignment to constant variable throws TypeError`

- [p] ★ Principle 3 operational derivation: The `useState` Hook provides the dual capability local variables lack: memory persistence and re-render triggers. When you write `const [likes, setLikes] = useState(0)`, you declare a state variable `likes` and a setter function `setLikes`. Because `likes` is declared with `const`, attempting to write `likes = likes + 1` throws `TypeError: Assignment to constant variable.` in standard JavaScript. Even if declared with `let`, direct assignment would fail to notify React. Calling `setLikes(likes + 1)` hands the new value to React and schedules a render. > [!PRINCIPLE]
> **Principle 4: React Keeps State Outside the Function and Matches It by Call Order**
> React stores state data outside the component function in an internal memory list. On the initial render, React saves each starting value in order. On subsequent renders, React ignores the argument and returns the stored value matching that call's position in the sequence. Calling Hooks conditionally disrupts this call order and corrupts state alignment.
>
> >> call order : the fixed sequence in which a component invokes its Hooks on every render
> >> internal memory list : React's private storage outside the component function that holds state pairs
>
> *We should do this:*
> `const [isBookmarked, setIsBookmarked] = useState(false); // Second call in stable top-level order`
>
> *We should not do this:*
> `if (likes > 0) { useState(false); } // Conditional Hook call corrupts React state order`

- [p] ★ Principle 4 operational derivation: Beginners often ask: "If `useState(0)` runs on every single render, why doesn't likes reset to 0 every time?" The answer is that React does not inspect the argument on re-renders. When React renders a component, it maintains an internal pointer index starting at 0. The first call to `useState` retrieves slot 0 from React's internal list for this component. The second call to `useState` retrieves slot 1. React does not identify state variables by their names (`likes` or `isBookmarked`); it identifies them strictly by their **call order**. Why Hooks must never be placed inside conditions or loops belongs to Lecture 37. ◼ Educational objective: explain how React matches state variables by index order rather than identifier names and preview Lecture 37.

```jsx title="Multiple State Variables"
  return (

      <h3>{title}</h3>
      <p>{likes} likes</p>

```

> [!PRINCIPLE]
> **Principle 6: Pass an Initializer Function When Initial State Is Expensive to Compute**
> React uses the initial state argument on the first render only and ignores it on all later renders. However, calling a function in the argument like `useState(createInitialLikes())` runs on every single render cycle. When computing the start value is expensive, pass an initializer function by reference (`useState(createInitialLikes)`), so React invokes it once during setup and skips the work on subsequent renders.

> >> initial state argument : the value or function passed to useState to seed a state variable
>

- [p] ★ Principle 6 operational derivation: When you pass an expression to `useState`, JavaScript evaluates that expression before calling `useState`. If you write `useState(createInitialLikes())`, JavaScript executes `createInitialLikes()` on every render pass. Even though React discards the return value after the initial render, the CPU still paid the cost of computing it. When initial state requires parsing JSON, reading storage, or iterating over large arrays, this repeated computation causes frame drops. Passing `createInitialLikes` as an initializer function lets React call it only when initializing the component. In development under StrictMode, React calls initializers twice on the initial render to verify purity; why StrictMode does this belongs to Lecture 46. ◼ Educational objective: derive initializer functions and explain why passing a function reference avoids re-computation on re-renders while noting Lecture 46.

- [code] Initializer Function Optimization:

```jsx title="Initializer Function Optimization"
import { useState } from 'react';
function createInitialLikes() {
  console.log('computed initial likes'); // Logs when initializer runs
  return 10; // Starting like count
}
export default function StoryCard({ title }) {
  const [likes, setLikes] = useState(createInitialLikes); // Passes function reference
  return (
    <article className="story-card">
      <h3>{title}</h3>
      <p>{likes} likes</p>

    </article>
  );

```

◼ **The what-this-introduces list:** 1. `createInitialLikes`: pure function computing initial state. 2. `useState(createInitialLikes)`: function reference passed as initializer. 3. `console.log('computed initial likes')`: log proving function runs only during initialization.

- [p] ★ In this component, we pass `createInitialLikes` without parentheses. When the card mounts initially, the console logs `computed initial likes` (or twice under StrictMode in development). When you click the Like button twice, the card re-renders and updates the count to 11 and 12, but `computed initial likes` never logs again! In contrast, if you wrote `useState(createInitialLikes())`, the log would appear on initial mount and on every subsequent click, proving that the calculation ran pointlessly on every render. ◼ Educational objective: verify with observable console output that initializer functions run strictly during component setup.

- [principle-steps] Principle 7:
    - Step 1, the decision: never call a state setter during rendering; call setters exclusively inside event handlers or callbacks.
    - Step 2, the shape: plain sentences: calling a setter during render schedules an immediate re-render, entering an infinite loop that crashes the application.
    - Step 3, the names: `setter call` (`setLikes(likes + 1)`); `unconditional render call` (running setter during render).
    - Step 4, what breaks: React halts the infinite loop and throws: "Too many re-renders. React limits the number of renders to prevent an infinite loop."
    - Step 5, the technical words: `unconditional render call` and `infinite render loop` are new and needed; define them with side notes.
    - Step 6, the title: Call Setters Exclusively Inside Event Handlers and Never During Render.
    - Step 7, the beginner read: clear explanation of how premature setter calls cause crash loops.
    - Step 8, the comparison: matches standard infinite loop prevention exemplar.

> [!PRINCIPLE]
> **Principle 7: Call Setters Exclusively Inside Event Handlers and Never During Render**
> Call a setter function only inside an event handler, never unconditionally in the component body or directly inside JSX evaluation braces. Calling `onClick={setLikes(likes + 1)}` invokes the setter immediately during render, which schedules another render, invoking the setter again in an infinite loop. React halts this cycle by throwing the fatal runtime error: Too many re-renders. React limits the number of renders to prevent an infinite loop.
>
> >> unconditional render call : executing a state setter directly while React is calculating JSX
> >> infinite render loop : a crash where a render triggers a state update that immediately triggers another render
>
> *We should do this:*
> `onClick={() => setLikes(likes + 1)} // Arrow function waits until user clicks button`
>
> *We should not do this:*
> `onClick={setLikes(likes + 1)} // Runs during render and throws Too many re-renders`

- [p] ★ Principle 7 operational derivation: In Lecture 13, we learned that expressions inside JSX curly braces evaluate immediately during the render phase. If you write `onClick={setLikes(likes + 1)}`, JavaScript executes `setLikes` while React is building the element tree. The setter updates state and immediately queues another render. React re-runs the component, hits the JSX braces, and executes `setLikes` again. Without a stopping condition, this creates an infinite render loop. To prevent the browser tab from freezing, React aborts execution and throws: "Too many re-renders. React limits the number of renders to prevent an infinite loop." Wrapping the call in an arrow function (`() => setLikes(likes + 1)`) defers the setter until the user physically clicks. ◼ Educational objective: deconstruct the mechanics of the Too many re-renders crash loop and recall Lecture 13.

- [code] Safe Handler vs Immediate Setter Call:

```jsx title="Safe Handler vs Immediate Setter Call"
export default function StoryCard({ title }) {
  const [likes, setLikes] = useState(0);
  return (
    <article className="story-card">
      <h3>{title}</h3>
      <p>{likes} likes</p>
      <button
        type="button"
        onClick={() => setLikes(likes + 1)} // Defers setter execution until click
      >
        Like Story
      </button>
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `onClick={() => setLikes(likes + 1)}`: arrow function wrapper preventing premature invocation. 2. `setLikes(likes + 1)`: setter safely isolated to user interaction. 3. `button layout`: clean multi-line attribute formatting within line budgets.

- [p] ★ By wrapping `setLikes(likes + 1)` in an arrow function, the setter executes strictly when the user clicks the button. The component mounts cleanly displaying `0 likes`, and each click increments the count without triggering a crash. ◼ Educational objective: confirm the operational resolution preventing infinite re-render loops.

### Glossary

- [glossary] State Variable ◼ A variable retained by React across renders that drives what appears on the screen.
- [glossary] Setter Function ◼ A function returned by useState that updates the state variable and requests a new render.
- [glossary] Hook ◼ A special function provided by React that lets component functions tap into state and lifecycle features.
- [glossary] Component Instance ◼ A single mounted occurrence of a component in the UI tree with its own isolated state memory.
- [glossary] Initializer Function ◼ A function passed to useState that React invokes only once during component setup to compute initial state.
- [glossary] Array Destructuring ◼ A JavaScript syntax that unpacks values from an array into distinct variables in a single assignment.

## Beyond the basics

- [beyond-basics] **State updates are batched**: React groups multiple state setter calls inside the same event handler into a single render pass to prevent unnecessary UI redraws (see [react.dev/learn/queueing-a-series-of-state-updates](https://react.dev/learn/queueing-a-series-of-state-updates)).
- [beyond-basics] **State behaves like a snapshot**: reading a state variable immediately after calling its setter returns the value from the current render, not the upcoming one (see [react.dev/learn/state-as-a-snapshot](https://react.dev/learn/state-as-a-snapshot)).
- [beyond-basics] **Updater functions for sequential updates**: when calculating new state depends directly on the previous state multiple times in one event, pass an updater function like `setCount(prev => prev + 1)` (see [react.dev/reference/react/useState#updating-state-based-on-the-previous-state](https://react.dev/reference/react/useState#updating-state-based-on-the-previous-state)).
- [beyond-basics] **Skipping identical state updates**: if you call a setter with a value identical to the current state by `Object.is` comparison, React skips rendering the component and its children (see [react.dev/reference/react/useState#caveats](https://react.dev/reference/react/useState#caveats)).
- [beyond-basics] **Top-level Hook rules**: Hooks must be called exclusively at the top level of component functions, never inside conditions, loops, or nested functions (see [react.dev/reference/rules/rules-of-hooks](https://react.dev/reference/rules/rules-of-hooks)).

### Summary

[review-title] **Architectural Takeaways & Decision Matrix**

[review-subtitle] ❒ Storing Component Memory

[always-rule] ➔ ALWAYS declare state variables using `useState` when data must survive across renders and update the screen.

[never-rule] ➔ NEVER reassign local variables directly expecting React to detect the change and redraw the user interface.

[if-then-rule] ➔ IF an initial state calculation is computationally expensive THEN pass an initializer function by reference (`useState(computeStart)`) to avoid re-running it on every render.

[review-subtitle] ❒ Setter Invariants

[never-rule] ➔ NEVER call a state setter function unconditionally inside the component render body or JSX braces to prevent fatal infinite render loops.

[always-rule] ➔ ALWAYS wrap parameterized setter calls inside inline arrow functions or event handlers so they execute only upon user interaction.

**DO THIS:** update state exclusively through setter functions inside event handlers

```jsx right
function LikeButton() {
  const [likes, setLikes] = useState(0);
  return (
    <button type="button" onClick={() => setLikes(likes + 1)}>
      Like ({likes})
    </button>
  );
}
```

**DO NOT DO THIS:** reassign local variables or call setters during render

```jsx wrong
function LikeButton() {
  let likes = 0;
  return (
    <button type="button" onClick={setLikes(likes + 1)}>
      Like ({likes})
    </button>
  );
}
```

| | **LOCAL VARIABLES**<br>(Ephemeral Memory) | **REACT USESTATE**<br>(Durable Memory) |
| ---: | :--- | :--- |
| **Persistence** | Discarded when function completes;<br>resets on every render | Retained by React across renders<br>in external memory slots |
| **Screen Updates** | Changing variable triggers zero renders;<br>screen stays stuck | Calling setter requests a new render<br>and updates the screen |
| **Instance Scope** | Shared globally if moved to module;<br>reset locally if in function | Completely private and isolated<br>to each rendered component instance |
| **Initial Value** | Re-evaluated and re-assigned on<br>every single function call | Seeded once on initial render;<br>initializer functions run once |
