### The Friction of Event Bubbling and Default Actions

- [p] ★ {preknowledge: JSX markup, components as functions, callback props, pure rendering} In earlier lessons, you learned that React components are pure functions. They calculate JSX markup from incoming props. You built structured layouts by passing numbers, strings, and objects downward. However, real web applications must respond when users interact with the screen. Users click action buttons, type queries into search fields, and submit forms. In standard HTML, events start at the clicked element and bubble upward through all parent elements. When developers build nested cards with inner buttons, clicking an inner button triggers the parent card unexpectedly. Furthermore, submitting a form causes the browser to reload the whole page, wiping all application state. ◼ Educational objective: recall component rendering and props while identifying the twin frictions of unexpected event bubbling and unwanted page reloads.
- [p] ★ {problem: bubbling triggers parent card click and form submit reloads page} It is common for an engineer to nest a Bookmark button inside a clickable article card. Opening the browser reveals an immediate defect. Clicking Save logs the bookmark, but it also opens the full article. The user triggered two conflicting actions with a single click. A second failure occurs when an engineer submits a search form without halting browser defaults. The browser executes a full-page reload, appends a question mark to the URL, and clears the console log. ◼ Educational objective: analyze the operational failure where event bubbling causes unwanted parent activation and default form submission destroys page state.
- [p] ★ {old solution: imperative addEventListener or inline HTML strings} In traditional web pages, developers attached events imperatively using `addEventListener` in script tags. They wrote `onclick="return false"` inside raw HTML strings. In React, JSX props do not take raw strings. You pass declarative function values, handle events cleanly, and govern propagation through the React event object. ◼ Educational objective: contrast legacy HTML attribute strings and imperative listeners with declarative React event props.

- [code] Naive Bubbling and Submission Attempt:

```jsx title="Naive Execution Attempt"
function ArticleCard({ story, onOpen }) {
  function save() {
    console.log(~'Saved:', story.id~); // Prints bookmark action to console
  }
  return (
    <article onClick=~{onOpen}~> // Enclosing card handler triggers on bubble
      <button onClick=~{save}~>Save</button> // Inner click bubbles to card
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `onOpen`: parent click handler attached to card. 2. `save`: child button handler. 3. `console.log(...)`: observable bookmark log executed alongside card opening.

- [p] ★ {mechanism: event objects, stopPropagation, and preventDefault} React solves these problems by providing a cross-browser SyntheticEvent wrapper. Every handler function receives this event object automatically as its first argument. To stop a click from bubbling up to parent cards, you call `e.stopPropagation()` inside the button handler. To stop a form submission from reloading the browser page, you call `e.preventDefault()`. To capture typed characters as they occur, you pass a handler to `onChange` and read `e.target.value`. ◼ Educational objective: establish the mechanics of synthetic event objects, bubbling prevention via stopPropagation, and page reload prevention via preventDefault.
- [grounding] [!] Grounding card: Why did clicking Save also open my article card? ◼ Opening question: Why did clicking Save also open my article card? ◼ Friction target: Developers nesting buttons inside clickable cards notice that clicking the button also triggers the parent container handler. ◼ Tactile scene: A developer puts a Save button inside a clickable news card; clicking Save logs "Saved article" but also immediately opens the full article reader view; the developer realizes two handlers executed for one click. ◼ Bold key terms: **event bubbling**, **synthetic event**, **stopPropagation**, **preventDefault**, **event target**. ◼ Operational resolution: In the browser DOM and React, click events bubble upward from child to parent; calling `e.stopPropagation()` inside the button handler stops the event from reaching the parent card.

### Synthetic Events, Input Handlers, and Propagation Pathways

- [p] ◇ {conceptual grounding: browser events and React declarative handlers} React wraps native browser events in an object called **SyntheticEvent**. This wrapper conforms to the standard DOM Event interface. It normalizes browser differences so events behave identically across all modern browsers. You attach handlers using camelCase props like `onClick`, `onChange`, and `onSubmit`. Every handler receives the event object `e` as its first argument. ◼ Educational objective: introduce synthetic event wrappers and declarative event prop conventions.
- [p] ★ {runtime distinction: currentTarget versus target} A critical distinction in event handling is the difference between `e.currentTarget` and `e.target`. The property `e.currentTarget` always points to the element that owns the active handler. In contrast, `e.target` points to the innermost element the user physically touched. If a button contains an icon `<span>★</span>`, clicking the star sets `e.target` to that inner span. However, `e.currentTarget` remains the button element. Reading `e.currentTarget` ensures you access the element that declared the handler. ◼ Educational objective: clarify the operational distinction between currentTarget and target during user interactions.
- [p] ★ {architectural model: onChange timing and text inputs} In native DOM, input `change` events wait for blur. They fire only when the user leaves the field. In React, `onChange` behaves differently: it fires on every single keystroke. Under the hood, React listens to the browser `input` event and normalizes it to `onChange`. The property `e.target.value` contains the full text typed so far, providing real-time access to user queries. ◼ Educational objective: establish that React onChange fires on every keystroke, contrasting it with native blur-based change events.
- [p] ★ {syntactic reminder: destructuring and arrow functions} Let us review two JavaScript features used in event handlers: **object destructuring** and **arrow functions**. Object destructuring (`const { value } = e.target`) extracts properties directly from an object into local variables. An inline arrow function (`() => handleOpen(story.id)`) creates a waiting function. It passes custom arguments only when the event occurs, avoiding premature execution during render. ◼ Educational objective: review object destructuring and inline arrow function wrappers for event handling.

### Principles of React: The Core Laws of Event Handling and Propagation

- [p] ◇ Senior interview candidates must clearly explain event handling and propagation. They must distinguish targets, handle keystrokes, and stop bubbling cleanly. To master these concepts, we formalize the six governing principles of event handling: ◼ Educational objective: frame the six principles from the perspective of an engineering candidate preparing for senior technical interviews.

> [!PRINCIPLE]
> **Principle 1: Put Side Effects in Handlers, Never in Render**
> Handlers run strictly when the user interacts, never during the render calculation. This makes event handlers the natural home for side effects like logging, analytics, and network calls. Placing side effects in component bodies causes unwanted executions and crashes pure rendering contracts.
> 
> >> side effect : an operation that interacts with outside systems or modifies external memory
> >> render calculation : the pure step where a component calculates its JSX markup

- [p] ★ Principle 1 operational derivation: React components must remain pure functions during the render phase. In earlier lessons, you learned that React may call your component function multiple times. Under StrictMode in development, React invokes your component twice to detect accidental side effects. Side effects placed in component bodies run on page load. Under StrictMode, they execute twice during development. By contrast, React calls event handlers only when a user physically clicks, types, or submits. An event handler is not part of the pure render formula. It can safely send network requests, write to local storage, and trigger outside systems. ◼ Educational objective: derive why event handlers are the authorized location for side effects while component bodies remain pure.

- [code] Render Phase vs Interaction Phase Logging:

```jsx title="Render vs Handler Execution"
export default function ArticleCard({ story }) {
  console.log(~'Render card:', story.id~); // Executes twice during render phase
  function save() {
    console.log(~'Bookmarked:', story.id~); // Runs exclusively upon user click
  }
  return (
    <button onClick=~{save}~>Save</button> // Passes reference without calling
  );
}
```

◼ **The what-this-introduces list:** 1. `console.log('Render card:', story.id)`: render-phase log executing twice on page load. 2. `save`: event handler function holding user side effects. 3. `console.log('Bookmarked:', story.id)`: interaction log executing only on user click.

> [!PRINCIPLE]
> **Principle 2: Read currentTarget for the Bound Element and target for What Was Touched**
> Every handler receives a React event object that mirrors DOM standards. The currentTarget property refers to the element that owns the handler. The target property refers to the innermost element the user physically touched, such as an icon inside a button.
> 
> >> currentTarget : the element whose event handler is currently executing
> >> target : the innermost DOM element where the event originated

- [p] ★ Principle 2 operational derivation: When an event occurs, the browser creates an event object. React wraps this event in a SyntheticEvent. If you attach an `onClick` handler to an `<article>` card, the card is the `currentTarget`. If the user clicks an icon `<span>★</span>` inside that card, `e.target` is the inner `<span>` tag. A common bug occurs when developers read `e.target.dataset.id` expecting the card ID. If the reader clicks the icon, `e.target` is the span, returning `undefined`. Always inspect `e.currentTarget` to read attributes from the element that declared the handler. ◼ Educational objective: analyze the divergence between target and currentTarget when clicking nested child tags.

- [code] Target vs CurrentTarget Verification:

```jsx title="Target vs CurrentTarget"
export default function ArticleCard() {
  function check(e) {
    console.log(~'target:', e.target.tagName~); // Reads innermost touched tag
    console.log(~'current:', e.currentTarget.tagName~); // Identifies owner tag
  }
  return <article onClick=~{check}~><button>★</button></article>;
}
```

◼ **The what-this-introduces list:** 1. `e.target.tagName`: reveals whether user touched the span, button, or article. 2. `e.currentTarget.tagName`: reliably evaluates to ARTICLE. 3. `check`: card-level handler receiving bubbled events.

> [!PRINCIPLE]
> **Principle 3: Expect onChange to Fire on Every Keystroke**
> React fires the onChange prop on every single keystroke. In the browser DOM, native change events wait until an input loses focus. React wraps the native input event so onChange provides immediate updates as the user types.
> 
> >> onChange event : a synthetic event firing on every text modification in an input
> >> input event : the native browser event dispatched on each individual keystroke

- [p] ★ Principle 3 operational derivation: In traditional JavaScript, developers had to choose between `input` and `change` events. The native `change` event on `<input>` elements dispatches only when the user commits text by pressing Enter or clicking away. In React, `onChange` fires immediately on every keypress. The property `e.target.value` contains the full text typed into the field so far. The underlying native event type is `input`, exposed through `e.nativeEvent.type`. This immediate dispatch allows components to log searches, validate formats, or filter lists in real time. ◼ Educational objective: derive the immediate per-keystroke execution of React onChange and its relationship to native input events.

- [code] Per-Keystroke Input Inspection:

```jsx title="Per Keystroke Input Handling"
export default function SearchBar() {
  function handleChange(e) {
    console.log(~'typed:', e.target.value~); // Fires on every single keystroke
    console.log(~'type:', e.nativeEvent.type~); // Reveals native browser event
  }
  return (
    <input onChange=~{handleChange}~ /> // Fires handler on every keystroke
  );
}
```

◼ **The what-this-introduces list:** 1. `handleChange`: input change handler. 2. `e.target.value`: latest text value inside input buffer. 3. `e.nativeEvent.type`: confirms React wraps the browser input event.

> [!PRINCIPLE]
> **Principle 4: Expect Events to Bubble Up Through Parent Handlers**
> Events start at the innermost element touched and bubble upward through ancestors in order. Each parent handler on the path executes unless explicitly stopped. The onScroll event is the sole exception in React that does not bubble.
> 
> >> event bubbling : the upward propagation of an event through ancestor DOM elements
> >> capture phase : the downward pass where capture handlers execute before bubbling starts

- [p] ★ Principle 4 operational derivation: Event propagation in React follows the DOM event model. When a user clicks an element, the event first travels downward from the root during the capture phase. You can listen to this phase using `onClickCapture`. Once the event reaches the target, it bubbles upward through each parent element. If a button sits inside an `<article>` card, clicking the button invokes the button handler first, then the card handler. All events propagate in React except `onScroll`, which fires strictly on the scrolled element. ◼ Educational objective: establish the order of event propagation from child to parent ancestors.

- [code] Event Bubbling Sequence Demonstration:

```jsx title="Event Bubbling Sequence"
export default function FeedCard() {
  const onCard = () => console.log(~'2. Card ran'~); // Runs second on bubble
  const onBtn = () => console.log(~'1. Button ran'~); // Runs first at target
  return (
    <article onClick=~{onCard}~> // Parent card listening to bubbles
      <button onClick={onBtn}>Read</button>
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `onBtn`: child handler running first. 2. `onCard`: ancestor handler running second. 3. `onClick` on article: demonstrating automatic bubbling.

> [!PRINCIPLE]
> **Principle 5: Stop Propagation Where a Child Action Must Stay Local**
> When clicking an inner control must not trigger the parent container handler, call e.stopPropagation() in the child handler. Stopping propagation keeps the action local and prevents accidental parent activation.
> 
> >> stopPropagation : a method on the event object that prevents further bubbling to parents
> >> child isolation : keeping child button actions from activating enclosing card click handlers
> 
> *It is best practice to do this:*
> `function ActionBtn({ onSave }) {`
> `  function handleClick(e) {`
> `    ~e.stopPropagation()~; // Stops bubbling to parent`
> `    onSave();`
> `  }`
> `  return <button onClick=~{handleClick}~>Save</button>;`
> `}`
> 
> *Instead of doing this:*
> `function ActionBtn({ onSave }) {`
> `  function handleClick(e) {`
> `    ~onSave()~; // Omitting stopPropagation bubbles click to parent`
> `  }`
> `  return <button onClick=~{handleClick}~>Save</button>;`
> `}`

- [p] ★ Principle 5 operational derivation: In modern web applications, clickable cards often contain independent actions like bookmark, like, or share buttons. If a user clicks Bookmark, they intend to save the article, not navigate to the article page. Without calling `e.stopPropagation()`, the event bubbles to the card, triggering both actions. Calling `e.stopPropagation()` halts the event at the button boundary. If the parent needs notification, the child calls a parent callback prop explicitly after stopping propagation. ◼ Educational objective: analyze how stopPropagation isolates child button interactions from parent container click behaviors.

- [code] Propagation Stopping Verification:

```jsx title="Stopped Propagation Pattern"
export default function BookmarkAction({ storyId }) {
  function handleSave(e) {
    ~e.stopPropagation()~; // Halts bubbling before reaching parent
    console.log(~'Saved story:', storyId~); // Runs isolated action in memory
  }
  return (
    <button onClick={handleSave}>Save Story</button>
  );
}
```

◼ **The what-this-introduces list:** 1. `e.stopPropagation()`: cancels upward propagation to ancestors. 2. `handleSave`: isolated child click handler. 3. `console.log(...)`: verified single execution.

> [!PRINCIPLE]
> **Principle 6: Prevent Browser Default Actions on Form Submission**
> Forms natively reload the browser page upon submission. Call e.preventDefault() in your onSubmit handler to cancel the native reload. This allows React to handle the event in memory.
> 
> >> preventDefault : a method that cancels the default browser behavior for an event
> >> full-page reload : native browser form submission that refreshes the page and wipes memory
> 
> *It is best practice to do this:*
> `function SearchForm({ onSearch }) {`
> `  function handleSubmit(e) {`
> `    ~e.preventDefault()~; // Prevents full-page reload on submit`
> `    onSearch();`
> `  }`
> `  return <form onSubmit=~{handleSubmit}~><button>Go</button></form>;`
> `}`
> 
> *Instead of doing this:*
> `function SearchForm({ onSearch }) {`
> `  function handleSubmit(e) {`
> `    ~e.stopPropagation()~; // Does not prevent full-page reload`
> `    onSearch();`
> `  }`
> `  return <form onSubmit=~{handleSubmit}~><button>Go</button></form>;`
> `}`

- [p] ★ Principle 6 operational derivation: HTML form elements carry built-in browser behaviors established decades ago. When a `<form>` is submitted, the browser collects inputs and navigates to its action URL. If no action exists, it reloads the current page with query parameters. In a single-page React application, a full-page reload wipes all client state and clears the browser console. Developers sometimes mistakenly call `e.stopPropagation()` to fix this reload. However, stopping propagation only halts bubbling to parent components; it does nothing to prevent browser default behaviors. To cancel the reload, you must call `e.preventDefault()`. ◼ Educational objective: derive why preventDefault is required for form submissions and clarify the difference between preventDefault and stopPropagation.

- [code] Form Default Action Prevention:

```jsx title="Preventing Form Submission Reload"
export default function SearchForm() {
  function handleSubmit(e) {
    ~e.preventDefault()~; // Cancels native browser full-page reload
    console.log(~'Search submitted'~); // Executes custom submission in memory
  }
  return (
    <form onSubmit={handleSubmit}><button>Go</button></form>
  );
}
```

◼ **The what-this-introduces list:** 1. `e.preventDefault()`: cancels native form navigation. 2. `handleSubmit`: form submit handler. 3. `console.log(...)`: verified client execution without page reload.

### Where you will meet this

1. **E-Commerce Product Cards**: Product cards navigate on click. Nested Add-to-Cart buttons call `e.stopPropagation()` to stay on the page.
2. **Search and Filter Bars**: Search forms call `e.preventDefault()` to prevent page reloads. Input fields use `onChange` for real-time filtering.
3. **Dropdown Menus and Modals**: Modals stop propagation on dialog windows. This prevents clicks inside from triggering backdrop dismissal.
4. **Interactive News Feeds**: Social feeds use nested bookmark controls. These controls isolate click events from full-article view navigation.

### Glossary

- **SyntheticEvent**: A cross-browser wrapper around native DOM events providing identical behavior across all modern browsers.
- **Event Bubbling**: The natural upward propagation of an event through parent DOM elements until it reaches the root.
- **Propagation Stopping**: Calling `e.stopPropagation()` to halt the upward journey of an event, preventing ancestor handlers from executing.
- **Default Action Prevention**: Calling `e.preventDefault()` to cancel the built-in browser behavior for an event, such as form submit reloads.
- **Event Target**: The innermost element the user touched (`e.target`), contrasted with the element owning the handler (`e.currentTarget`).

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Event Propagation & Child Isolation

➔ ALWAYS call `e.stopPropagation()` in child button handlers when nested inside clickable parent containers.

➔ IF a parent needs notification THEN call the parent callback prop explicitly after stopping propagation.

**DO THIS:** stop bubbling in child buttons nested inside clickable cards

```jsx right
function SaveButton({ onSave }) {
  function handleClick(e) {
    e.stopPropagation();
    onSave();
  }
  return <button type="button" onClick={handleClick}>Save</button>;
}
```

**DO NOT DO THIS:** allow child button clicks to bubble to parent containers

```jsx wrong
function SaveButton({ onSave }) {
  function handleClick(e) {
    onSave();
  }
  return <button type="button" onClick={handleClick}>Save</button>;
}
```

❒ Preventing Browser Default Actions

➔ ALWAYS call `e.preventDefault()` inside `onSubmit` handlers to prevent full-page browser reloads.

➔ NEVER substitute `e.stopPropagation()` for `e.preventDefault()` when attempting to prevent form reloads.

**DO THIS:** prevent default browser navigation on form submission

```jsx right
function SearchBox({ onSearch }) {
  function handleSubmit(e) {
    e.preventDefault();
    onSearch();
  }
  return <form onSubmit={handleSubmit}><button type="submit">Search</button></form>;
}
```

**DO NOT DO THIS:** rely on stopPropagation to halt browser form submission reloads

```jsx wrong
function SearchBox({ onSearch }) {
  function handleSubmit(e) {
    e.stopPropagation();
    onSearch();
  }
  return <form onSubmit={handleSubmit}><button type="submit">Search</button></form>;
}
```

❒ Keystrokes & Element Targets

➔ ALWAYS expect React `onChange` to fire on every single keystroke.

➔ ALWAYS read `e.currentTarget` to access the element that owns the active handler.

| | **NAIVE ASSUMPTION**<br>(Fragile Event Handling) | **REACT DISPATCH REALITY**<br>(Robust Event Architecture) |
| ---: | :--- | :--- |
| **Nested button clicks** | Child clicks stay isolated inside the clicked button automatically | Clicks bubble upward through all parent container handlers |
| **Stopping bubbling** | Developers assume bubbling is harmless or cannot be stopped | Calling `e.stopPropagation()` isolates child actions cleanly |
| **Form submissions** | Submitting a form keeps the single-page application alive | Browser executes full-page reload unless `e.preventDefault()` runs |
| **Input change timing** | Text input change event waits until the user leaves the field | React `onChange` fires immediately on every single keystroke |
| **Touched element target** | Property `e.target` always points to the element owning the handler | Property `e.target` points to inner icon; `e.currentTarget` owns handler |
