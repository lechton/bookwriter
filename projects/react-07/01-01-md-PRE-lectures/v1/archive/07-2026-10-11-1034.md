### What the children prop is and how JSX compiles slots

- [p] ◇ {runway: physical nesting syntax in HTML versus React} In standard HTML, nesting elements inside one another is the universal way to structure documents: you place an `<img>` and an `<h2>` inside an `<article>`, or an `<a>` inside a `<nav>`. In React, custom components support that exact same physical nesting syntax. When you write `<CardContainer><Headline /></CardContainer>`, you are passing `<Headline />` into `CardContainer` as an input. React automatically captures whatever markup appears between a component's opening and closing tags and delivers it to the component function under a reserved property name: `children`. ◼ Educational objective: ground the children prop in standard HTML nesting and define its role as an input property.
- [p] ★ {runway: JSX compilation to _jsx calls with children property} Under the hood, the JSX compiler converts every component tag into a `_jsx()` function call. As established in Lecture 3, writing opening and closing tags with nested content transforms into `_jsx(CardContainer, { children: [...] })`. The compiler places nested markup into the `children` key of the props object alongside any regular attributes. Because `children` is an ordinary property on the props object, a component reads it using `props.children` or unpacks it directly in its parameter list using object destructuring: `function CardContainer({ children })`. If a caller mistakenly passes both an attribute named `children` and nested elements inside the tags, `<CardContainer children="attr">nested</CardContainer>`, the nested content wins because the compiler writes nested JSX into `children` after evaluating opening tag attributes. ◼ Educational objective: trace compiler transformation of nested JSX into the children prop object.

- [code] Compiler Slot Translation (verified in React 19.3.0: compiler packages nested JSX into props.children):

```jsx title="Compiler Slot Translation"
// JSX call site:
<CardContainer className="featured">
  <h2>Morning Dispatch</h2> {/* nested headline element */}
</CardContainer>

// Compiled output:
_jsx(CardContainer, {
  className: "featured",
  children: _jsx("h2", { children: "Morning Dispatch" }) // slot in props
})
```

◼ **The what-this-introduces list:** 1. `CardContainer`: target component receiving attributes and nested markup. 2. `children` property: compiler-generated key on the props object holding nested element descriptors. 3. Nested `_jsx` calls: inner elements transform into descriptor objects before reaching the container.

- [p] ★ {runway: opaque data structure of children and array mapping pitfalls} It is critical to understand that `children` is an opaque data structure whose internal shape shifts depending on what the caller nests. If a caller nests two elements `<CardContainer><h2 /><p /></CardContainer>`, React sets `children` to an array, and `Array.isArray(children)` evaluates to `true`. But if a caller nests a single element `<CardContainer><h2 /></CardContainer>`, React sets `children` directly to that single element object to avoid memory allocation overhead, and `Array.isArray(children)` evaluates to `false`. If a caller nests text, `children` is a string. If code attempts to call `children.map(...)` on a single child, JavaScript immediately throws a fatal runtime error: `TypeError: children.map is not a function`. Containers must render `{children}` whole or accept an explicit array prop when list mapping is required. ◼ Educational objective: explain the variable internal shape of children and warn against calling array methods on single elements.
- [p] ★ {runway: execution order: container runs before children, and children are descriptors} The `children` prop contains lightweight element descriptors created by the caller, not rendered DOM output. The container component function executes before child component functions execute. Inside `CardContainer`, logging `children.type` points to the child component function itself, not rendered HTML nodes. If a container omits `{children}` from its return statement, the child component function never runs, and its console logs remain completely silent. The container acts as a conduit for element descriptors, never an inspector of rendered DOM output. ◼ Educational objective: establish the execution timing between container and children and clarify that children are descriptors.

### Container components and slot composition

- [p] ◇ {runway: container components and inversion of control} A container component is a component that provides a reusable visual frame (such as borders, background colors, shadows, and padding) while leaving its inner content open for callers to supply. This architectural pattern is called slot composition, and it implements the computer science principle of inversion of control. In rigid monolithic components, the child component dictates both the outer styling and every inner element. With slot composition, responsibility splits cleanly: the container owns the outer boundary, while the caller chooses what content belongs inside. ◼ Educational objective: define container components, slot composition, and inversion of control.
- [p] ★ {runway: dividing responsibilities: named props for fixed requirements, children for variable content} When designing container components, developers must decide what belongs in named props and what belongs in `{children}`. A named prop stays for something every card must guarantee in a fixed position, format, or layout role, such as the `title` on an article card or the `isOpen` state on a dialog. Everything that varies across callers (such as alert badges, author bylines, thumbnail images, or action buttons) belongs in `{children}`. This rule keeps the container parameter list lean while giving callers complete freedom over their markup. ◼ Educational objective: formulate the architectural heuristic for separating named props from slot children.

- [grounding] Architectural rot in design system cards:
  - Opening Question: Why do layout-flag props cause architectural rot in design systems?
  - Friction Target: Parameter explosion and rigid conditional branches in monolithic card components.
  - Tactile Scene: Teams building design systems watch card parameter lists explode with dozens of boolean flags that fight each other. When an editor asks to move an author above the headline on an opinion card, engineers add an `isAuthorTop` prop because layout order is hardcoded. Next week, another section needs two buttons instead of one, prompting `hasSecondaryButton` and `secondaryButtonText`. Within months, the card file becomes a tangled web of conflicting conditionals.
  - Bold Key Terms: **slot composition**, **container component**, **inversion of control**.
  - Concrete Operational Resolution: Replace specialized layout flags with an open slot using `{children}`. The container owns the outer visual frame and styling, allowing callers to compose inner elements freely without editing the shared container file.

### Forwarding attributes with rest syntax and JSX spread

- [p] ◇ {runway: need for forwarding arbitrary HTML attributes on wrapper tags} Reusable container components often wrap native HTML elements like `<div>` or `<article>`. Callers frequently need to attach standard browser attributes to that underlying element, such as `id="main-card"`, `aria-label="Breaking Bulletin"`, `data-story-id="102"`, or mouse event handlers. If a container only accepts explicit props, developers would have to add every possible HTML attribute to the component parameter list by hand. To avoid this boilerplate, React allows wrappers to pass extra attributes through to the underlying element. ◼ Educational objective: motivate attribute forwarding for accessible, identifiable container elements.
- [p] ★ {runway: rest syntax in destructuring gathers unconsumed properties} In JavaScript, placing three dots (`...`) before the final identifier in an object destructuring pattern activates rest syntax: `function CardContainer({ children, isFeatured, ...rest })`. The runtime extracts `children` and `isFeatured` into local variables, and gathers all remaining properties from the incoming props object into a new object named `rest`. If a caller passes `id="top"`, `aria-label="Alert"`, and `data-card-id="42"`, all three properties land cleanly inside `rest`. This allows the component to consume the props it needs for its own logic while isolating pass-through attributes in a clean object. ◼ Educational objective: explain JavaScript rest syntax in destructuring parameter lists.
- [p] ★ {runway: JSX spread attributes forwarding properties to DOM tags} To write the gathered attributes onto a JSX element, React provides JSX spread syntax: `<div className="card" {...rest}>{children}</div>`. Inside JSX tags, wrapping an object in curly braces with three dots (`{...rest}`) tells React to copy every key-value pair from that object as an attribute on the tag. Writing `{...rest}` when `rest` contains `{ id: "top", aria-label: "Alert" }` produces `<div className="card" id="top" aria-label="Alert">` in the browser DOM. The React documentation warns developers to use spread with restraint: frequent spread across business components obscures data requirements, so spread belongs specifically in generic pass-through wrappers. ◼ Educational objective: explain JSX spread syntax and cite official documentation advice on spread restraint.

- [code] Rest and Spread Attributes (verified in React 19.3.0: isolates component props and forwards rest to DOM):

```jsx title="Rest and Spread Attributes"
function CardContainer({ children, isFeatured, ...rest }) { // gathers rest
  return (
    <div className="card" {...rest}> {/* spreads rest onto native tag */}
      {children}
    </div>
  );
}
```

◼ **The what-this-introduces list:** 1. `{ children, isFeatured, ...rest }`: destructuring pattern separating consumed props from pass-through attributes. 2. `rest`: a new JavaScript object containing all unconsumed props. 3. `{...rest}`: JSX spread syntax writing collected attributes onto the root `<div>`.

### Principles of React: Container Composition and Prop Spreading

- [p] ◇ In technical interviews, engineering candidates are closely evaluated on container composition, the opaque structure of `children`, clean attribute forwarding with rest and spread, attribute evaluation order, and fallback defaults in destructuring. In each question cycle below, the scenario presents concrete code, the bold question names the developer's uncertainty, the answer traces what the runtime executes, and the principle box formalizes that answer into an engineering rule. ◼ Educational objective: frame the upcoming five question cycles and principle boxes.

- [question-cycle] Question 1: Content placed between tags arrives as the children prop
    - Question: "I put a headline between `<CardContainer>` and `</CardContainer>`. Where does it go?"
    - Code and result: `Feed` renders `<CardContainer><h2>Transit Accord Reached</h2></CardContainer>`, but `CardContainer` returns `<div className="card" />` without `{children}`; DevTools displays an empty `<div class="card"></div>`, the headline is completely missing from the screen, and the console stays silent with zero warnings (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: The JSX compiler transforms nested markup into the `children` key of the props object: `_jsx(CardContainer, { children: _jsx("h2", { children: "Transit Accord Reached" }) })`; React invokes `CardContainer` with that props object; because `CardContainer` returned `<div className="card" />` and never wrote `{children}` in its JSX, React renders only the outer `<div>` and silently discards the nested element; components passed as children never execute if dropped.
    - Fix: Place `{children}` inside the returned JSX, `function CardContainer({ children }) { return <div className="card">{children}</div>; }`, taught in the runway section "What the children prop is and how JSX compiles slots".
    - Rule: Place `{children}` inside the container markup where the nested content belongs. Boundary: React never places nested JSX by itself; if the container omits `{children}`, the content disappears without an error.
    - Needs: children prop (runway), _jsx call (recall, Lecture 3), props object (recall, Lecture 6), object destructuring (recall, Lecture 6).
    - Diagram: Nested JSX compiling into props.children and mapping to DOM.

> [!PRINCIPLE]
> **Principle 1: Nested JSX arrives as the children prop**
> When you nest elements or text between a component's opening and closing tags, React delivers that content in the **children prop**. React passes it to the component function on its props object, like an attribute. The content appears on the screen only where the component writes **{children}** in its returned JSX. If the component never writes `{children}`, React renders the outer frame and drops the nested content without a warning.
>
> >> children prop : a reserved prop that receives elements or text nested between component tags
>
> *We should do this:*
> `function Card({ children }) {`
> `  return <div className="card">{children}</div>; // places children in the card`
> `}`
>
> *We should not do this:*
> `function Card({ children }) {`
> `  return <div className="card" />; // drops children without an error`
> `}`

- [question-cycle] Question 2: Let the caller fill the container instead of adding a prop for every piece
    - Question: "One card needs a badge, another an author, and a third a button. Do I add a prop for each?"
    - Code and result: `NewsCard({ title, badgeText, author })` with `<span className="badge">{badgeText}</span>`; rendering a standard story without a badge (`<NewsCard title="Budget Debate" author="Clara" />`) renders an empty `<span class="badge"></span>`, which displays as an empty colored pill on screen because `.badge` has padding and a background (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: Adding a prop for every optional piece forces the container to predict every layout variation and render empty elements when props are omitted; in slot composition, the container owns only the outer frame and provides `{children}`; each caller nests the exact elements it needs in the order it wants; a story with a badge nests the badge, while a story without a badge omits it completely.
    - Fix: Refactor `NewsCard` into `CardContainer` taking `{children}` and let each call site nest its own elements, keeping a named prop only for values every card must show in a fixed place, taught in the runway section "Container components and slot composition".
    - Rule: Let callers nest variable elements through the open slot instead of adding a prop per variation. Boundary: Keep a named prop for a value every instance must display in a fixed format or location (such as `title`), while variable inner content goes into `children`.
    - Needs: container component (runway), slot composition (runway), inversion of control (runway), className (recall, Lecture 3).
    - Diagram: Rigid props versus composable slot.

> [!PRINCIPLE]
> **Principle 2: Let the caller fill the container instead of adding a prop for every piece**
> When different instances of a component need different inner layouts, let callers nest the elements they need through **slot composition**. Adding a prop for each optional piece forces the container to manage layout flags and leaves empty elements on items that omit the prop. Keep a named prop only for a value every instance must show in a fixed place, and let callers nest the rest through the open slot.
>
> >> slot composition : letting callers compose inner elements freely inside an open container slot
>
> *It is best practice to do this:*
> `<Card>`
> `  <span className="badge">New</span> {/* caller nests badge */}`
> `  <h2>Title</h2>`
> `</Card>`
>
> *Instead of doing this:*
> `<Card`
> `  badgeText="New" // adds prop to container for layout variation`
> `  title="Title"`
> `/>`

- [question-cycle] Question 3: Spread only the props the container does not use
    - Question: "Callers want to add `id`, `aria-label`, and `data-story-id` to the card. Do I list each one?"
    - Code and result: `CardContainer` spreads all props onto the container element, `<div className="card" {...props}>{props.children}</div>`, with `isFeatured={true}` and `badgeText="New"` passed by a caller; the console warns "React does not recognize the `isFeatured` prop on a DOM element", and DevTools shows `badgetext="New"` on the DOM `<div>` (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: Native DOM elements like `<div>` only accept valid HTML attributes; spreading the entire `props` object forwards component-only props like `isFeatured` and `badgeText` to the DOM node, triggering React console warnings and invalid attributes; rest syntax `{ children, isFeatured, ...rest }` extracts consumed props into local variables and gathers unconsumed props into `rest`; `{...rest}` writes only those remaining attributes onto the `<div>`.
    - Fix: Unpack consumed props and spread only `...rest` onto the element, `function CardContainer({ isFeatured, children, ...rest }) { return <div className="card" {...rest}>{children}</div>; }`, taught in the runway section "Forwarding attributes with rest syntax and JSX spread".
    - Rule: Unpack props the container uses and spread only unconsumed props with `...rest`. Boundary: Spread only in generic pass-through wrapper elements; business components should list their required props explicitly.
    - Needs: rest syntax in destructuring (runway), JSX spread attributes (runway), DOM attribute leakage (runway), aria-* and data-* attributes (recall, Lecture 3).
    - Diagram: Props destructuring separating consumed props from rest for spread.

> [!PRINCIPLE]
> **Principle 3: Spread only the props the container does not use**
> When a container forwards extra attributes to a native DOM element, unpack the props it uses and collect the remaining properties with **rest syntax**: `{ children, isFeatured, ...rest }`. Then write only those remaining properties on the element with **JSX spread syntax**: `{...rest}`. Spreading the whole `props` object forwards component props too, causing **DOM attribute leakage** and development console warnings.
>
> >> rest syntax : gathering unpicked properties into a separate object with ...rest
> >> JSX spread syntax : writing each property of an object as a JSX attribute with {...rest}
> >> DOM attribute leakage : writing non-standard component props onto native browser DOM elements
>
> *We should do this:*
> `function Card({ isFeatured, children, ...rest }) {`
> `  return <div className="card" {...rest}>{children}</div>; // forwards rest`
> `}`
>
> *We should not do this:*
> `function Card(props) {`
> `  return <div className="card" {...props}>{props.children}</div>; // leaks props`
> `}`

- [question-cycle] Question 4: Around a spread, the last attribute wins
    - Question: "The caller passed `className="featured"`. Why did my card lose its frame?"
    - Code and result: `CardContainer` places its base class before the spread, `<div className="card" {...rest}>{children}</div>`, and the caller passes `className="featured"`; DevTools reveals `class="featured"`, and the card loses its base border and padding styles (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: JSX evaluates attributes from left to right; when the same attribute appears multiple times, the last one evaluated overwrites earlier ones; because `rest` contains `className: "featured"` and appears after `className="card"`, the caller's class completely replaces `"card"`; if `className="card"` were placed after the spread, the container would overwrite the caller's class; JSX never merges attributes automatically.
    - Fix: Extract `className` in the parameter list and join both strings explicitly using string concatenation, `const fullClass = 'card ' + className; return <div className={fullClass} {...rest}>{children}</div>;`, taught in earlier string concatenation (Lecture 4) and expanded here.
    - Rule: Attributes written around a spread follow left-to-right precedence; overridable defaults go before `{...rest}`, and enforced attributes go after `{...rest}`. Boundary: When both the container and caller must contribute a class name, destructure `className` and concatenate both strings.
    - Needs: attribute precedence (runway), string concatenation with + (recall, Lecture 4), className (recall, Lecture 3).
    - Diagram: Left-to-right attribute evaluation comparison (before spread, after spread, joined).

> [!PRINCIPLE]
> **Principle 4: Around a spread, the last attribute wins**
> JSX evaluates attributes from left to right through **attribute precedence**. When the same attribute appears more than once on an element, the last one written wins. An attribute placed before `{...rest}` serves as an overridable default that caller props replace. An attribute placed after `{...rest}` is an enforced value that replaces caller props. When both sides must contribute a class name, extract `className` and join both strings explicitly.
>
> >> attribute precedence : the left-to-right order where later JSX attributes overwrite earlier ones
>
> *It is best practice to do this:*
> `function Card({ className, children, ...rest }) {`
> `  const fullClass = 'card ' + className; // joins base with caller`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`
>
> *Instead of doing this:*
> `function Card({ children, ...rest }) {`
> `  return <div className="card" {...rest}>{children}</div>; // caller overwrites`
> `}`

- [question-cycle] Question 5: A default fills a prop the caller left out
    - Question: "What if the caller passes no `className`, or nothing between the tags?"
    - Code and result: `CardContainer` joins class names with `'card ' + className`, but a caller passes no `className`; DevTools reveals `class="card undefined"`; when rendered without children (`<CardContainer />`), an empty frame renders with no fallback (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: A missing prop evaluates to `undefined`; in JSX content `{undefined}` renders empty, but in JavaScript string concatenation `'card ' + undefined` coerces `undefined` into the string `"undefined"`, producing `"card undefined"` in the DOM; assigning a default parameter value in the destructuring list (`className = ''`) replaces `undefined` with `''`, producing a clean `"card "` class; similarly, `children = <p>No items yet</p>` fills an empty slot.
    - Fix: Assign default parameter values in the destructuring list, `function CardContainer({ className = '', children = <p>No items yet</p>, ...rest })`, taught in Lecture 6 default parameters and expanded here.
    - Rule: Assign default parameter values in destructuring to provide fallbacks for missing props. Boundary: Default parameters engage strictly when a prop is missing or `undefined`; they do not engage when a caller passes `null` or `false`.
    - Needs: default parameter value (recall, Lecture 6), null and undefined (recall, Lecture 4), string concatenation (recall, Lecture 4).
    - Diagram: Missing prop versus default parameter fallback evaluation.

> [!PRINCIPLE]
> **Principle 5: A default fills a prop the caller left out**
> A missing prop evaluates to `undefined`. In JSX content, `undefined` renders an empty slot without printing text. But in string concatenation, `'card ' + undefined` coerces `undefined` into the text `'card undefined'`. Assign a **default parameter value** in the destructuring list to fill a missing prop: `className = ''`. Default parameter values engage only when a prop is missing or strictly `undefined`; they do not engage when a caller passes `null` or `false`.
>
> >> default parameter value : a fallback value assigned in destructuring when a prop is missing or undefined
>
> *We should do this:*
> `function Card({ className = '', children, ...rest }) {`
> `  const fullClass = 'card ' + className; // fallback prevents undefined`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`
>
> *We should not do this:*
> `function Card({ className, children, ...rest }) {`
> `  const fullClass = 'card ' + className; // produces card undefined`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`

### Step 1: First, we construct the slot-based container component <CardContainer.jsx>

- [p] ★ We author the foundational container component `CardContainer.jsx` to establish the reusable visual frame for dispatches. Instead of accepting specialized layout flags that dictate inner elements, `CardContainer` exposes an open slot by destructuring `children` from its parameter list. Notice how the parameter signature also unpacks `color = 'gray'` and `className = ''` with explicit default parameter values, while collecting all remaining pass-through attributes into `...rest`. The component calculates a merged CSS class string and forwards `...rest` onto the root `<div>`. ◼ Meaningful pedagogical commentary: architectural motivation of slot container, default parameters, rest forwarding.

- [code] CardContainer.jsx (verified in React 19.3.0: renders slot container with merged classes and rest props):

```jsx title="CardContainer.jsx"
export default function CardContainer({
  children, color = 'gray', className = '', ...rest // unpacks slot
}) {
  const cls = `card card-${color} ${className}`.trim();
  return (
    <div className={cls} {...rest}> {/* forwards props to wrapper */}
      {children}
    </div>
  );
}
```

◼ **The what-this-introduces list:** 1. `CardContainer`: the reusable slot container component. 2. `children`: destructured prop receiving caller-nested elements. 3. `color = 'gray'`: default theme parameter. 4. `className = ''`: default parameter preventing `undefined` in class string. 5. `{...rest}`: JSX spread forwarding unconsumed props to the root `<div>`.

### For the interview

- [interview] The Interview Question and 4 beats:

> **The Interview Question:** How do the children prop, spread attributes, and default values work?

- [p] ◇ **1. The Hidden Signal** ◼ The interviewer is probing your mastery of component composition architecture, compiler transformations, JavaScript rest and spread syntax, attribute precedence, and DOM attribute leakage. Junior developers explain props as HTML attributes. Senior engineers explain that JSX compiles nested tags into `props.children` (`_jsx(Card, { children: [...] })`), implementing inversion of control. They explain that pass-through wrappers destructure consumed props and forward `...rest` to prevent unknown-prop console warnings, that JSX evaluates attributes left to right, and that default parameters protect against `undefined` string coercion.
- [p] ◇ **2. The Classic Trap** ◼ One classic trap is assuming `children` is always an array. In React, `children` is an opaque data structure: a single child is an element object, multiple children form an array, and plain text is a string. Calling `children.map()` on a single nested child crashes with `TypeError: children.map is not a function`. Another trap is spreading full `props` onto a native element (`<div {...props}>`), which leaks component props to the DOM and triggers React warnings. A third trap is merging classes without default parameter fallbacks (`'card ' + className`), which renders `"card undefined"` in the DOM when the prop is omitted.
- [p] ◇ **3. What is Actually Going On** ◼ Under the hood, JSX converts nested tags into `props.children`. When React executes `CardContainer`, it passes this object as the first argument. If the container omits `{children}`, React renders the outer frame and drops the children; child functions never run, and their console logs remain silent. Around `{...rest}`, JSX applies attributes left to right: an attribute before `{...rest}` serves as an overridable default, while an attribute after `{...rest}` enforces a value. In destructuring, `className = ''` assigns an empty string when the prop is missing or `undefined`, preventing string coercion bugs while preserving valid values.
- [p] ◇ **4. Where It Gets Tricky** ◼ Where this gets tricky is handling collisions between custom props and native HTML attributes. If a component accepts `title="Night Trains"` as a data prop but blindly spreads all props onto a container `<div>`, that title becomes an unintended browser hover tooltip. If a boolean prop like `isFeatured={true}` spreads onto a `<div>`, React logs unknown attribute warnings. Another tricky nuance is that default parameters trigger strictly for `undefined` or omitted props; if a caller passes `className={null}` or `children={null}`, default parameter values do not engage, and `{null}` renders as an empty slot.

### Glossary

- [glossary] Children Prop ◼ A reserved React property that automatically receives any JSX elements or text passed between a component's opening and closing tags.
- [glossary] Container Component ◼ A reusable component that provides an outer visual frame while exposing an open slot for caller-provided content.
- [glossary] Slot Composition ◼ An architectural design pattern where a container component defines visual boundaries and leaves open slots for caller-provided content.
- [glossary] Inversion of Control ◼ A design principle where the calling component chooses what inner content to render, while the container decides where and how that content is framed.
- [glossary] Rest Syntax ◼ The JavaScript syntax using three dots in destructuring to collect unconsumed properties into a separate object.
- [glossary] JSX Spread Syntax ◼ A JSX syntax pattern using `{...props}` or `{...rest}` to forward an object of properties onto an underlying element.
- [glossary] DOM Attribute Leakage ◼ The unintended forwarding of non-standard component props onto native browser DOM elements, causing warnings and invalid attributes.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Slot Composition with Children

➔ IF a component acts as a reusable visual container, THEN place `{children}` in its return statement to allow callers to compose inner content freely.

➔ IF rendering received children, THEN treat `children` as an opaque descriptor and render it whole rather than calling array methods like `children.map()`.

❒ Controlled Prop Spreading

➔ IF a wrapper component forwards extra attributes to a native DOM element, THEN destructure consumed props and spread only `...rest` onto the element.

➔ IF a component accepts custom data props, THEN never spread the entire `props` object onto native DOM elements to prevent attribute leakage and console warnings.

❒ Attribute Precedence and Defaults

➔ IF specifying overridable defaults on a wrapper element, THEN place default attributes before `{...rest}` and enforced attributes after `{...rest}`.

➔ IF merging class names on a wrapper component, THEN assign a default parameter `className = ''` and combine the strings explicitly.

**DO THIS:** Compose inner layout with children and merge class names explicitly

```jsx right
function CardContainer({
  children,
  color = "gray",
  className = "",
  ...rest
}) {
  const cls = `card card-${color} ${className}`.trim();
  return (
    <div className={cls} {...rest}>
      {children}
    </div>
  );
}
```

**DO NOT DO THIS:** Bloat containers with layout flags and spread unconsumed props

```jsx wrong
function CardContainer(props) {
  return (
    <div className="card" {...props}>
      {props.children}
    </div>
  );
}
```
