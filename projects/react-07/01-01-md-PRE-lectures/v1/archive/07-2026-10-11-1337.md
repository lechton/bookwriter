# Pre-Lecture Blueprint: Q07 — Container Composition with Children and Prop Spreading

- [ladder-1] You built a news card component that shows a title, a badge, and an author. ◼ Educational objective: name what the reader is building.
- [ladder-2] One story has no badge, but the card still draws an empty badge on the screen. ◼ Educational objective: show the failure the reader can see.
- [ladder-3] How can one card frame hold different content for each story without a prop for every piece? ◼ Educational objective: ask the lesson's question plainly.

### One card component cannot predict every story

- [p] ◇ {problem: one prop per piece} With what Lecture 6 taught, the reader writes the news card with one prop for each piece it shows. ◼ Educational objective: start from code the reader can already write.

- [code] A news card with one prop per piece:

```jsx title="A news card with one prop per piece"
function NewsCard({ title, badgeText, author }) {
  return (
    <article className="card">
      <span className="badge">{badgeText}</span> {/* drawn for every story */}
      <h2>{title}</h2>
      <p>By {author}</p>
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `NewsCard`: one prop for each piece of the card. 2. `badgeText`: a prop whose `<span>` is drawn for every story.

- [p] ◇ {problem: the empty badge} This works while every story looks the same. Stories differ: one has a badge, one has an image, one has a button. Each new piece adds one more prop, and the card draws that piece for every story, even when the story passes nothing. A story without a badge gets an empty `<span class="badge">`, and once the badge has a background color, the reader sees an empty pill. ◼ Educational objective: name the visible defect without teaching the fix.

- [p] ◇ {question} This lesson answers three questions, in bold, one per line: How does content written between a component's tags reach the component? How do we pass attributes like `id` and `aria-label` through a component without listing each one? What does a component do when the caller leaves a prop out? ◼ Educational objective: the three parts of the interview question, in the reader's words.

- [recall] Lecture 3 (JSX) ◼ JSX compiles every tag into a `_jsx` call that returns an object describing the element. Attributes such as `aria-label` and `data-story-id` keep their dashes, and `class` is written `className`.
- [recall] Lecture 4 (Values in JSX) ◼ Curly braces put a JavaScript value into the markup. `null`, `undefined`, and `false` show nothing on the screen, and `+` joins two strings into one.
- [recall] Lecture 5 (The component tree) ◼ Writing one tag inside another builds the tree of components and elements on the page.
- [recall] Lecture 6 (Props) ◼ The attributes on a component's tag arrive as one props object, and braces in the parameter list unpack its keys. A default such as `author = 'Staff'` fills a prop the caller left out.

### Content between a component's tags arrives as the children prop

- [runway] The `children` prop, used by Questions 1, 2, 3, and 5.

- [p] ◇ {runway: name it and show it} The reader can write content between the opening and closing tags of their own component, as with `<article>` or `<div>`. ◼ Educational objective: start from HTML nesting the reader knows.

- [code] Content between the tags:

```jsx title="Content between the tags"
<CardContainer>
  <h2>Transit Accord</h2> {/* this element goes to CardContainer */}
</CardContainer>
```

- [p] ◇ {runway: who does what} React puts that `<h2>` into the props object of `CardContainer`, under the key `children`. The reader does not choose this name: React always uses `children`. In the `_jsx` call from Lecture 3, the nested element is one more prop. ◼ Educational objective: say who acts, and tie the name to the compiled call.

- [code] Compiled call:

```js title="Compiled call"
_jsx(CardContainer, {
  children: _jsx("h2", { children: "Transit Accord" }), // the nested h2
});
```

- [p] ◇ {runway: the receiving side} Inside `CardContainer`, the reader unpacks `children` like any other prop and writes `{children}` where the content should appear. ◼ Educational objective: show the receiving side in its own fence.

- [code] Where the container places children:

```jsx title="Where the container places children"
function CardContainer({ children }) {
  return <div className="card">{children}</div>; // the h2 lands in the div
}
```

- [p] ◇ {runway: second tiny example} The same `CardContainer` frames different content for each story: the caller nests an image and a headline. `children` holds both elements, and the card shows them in the order the caller wrote them. Closing rule: whatever you write between a component's tags reaches that component as its `children` prop. ◼ Educational objective: confirm the idea with different content.

- [code] An image and a headline as children:

```jsx title="An image and a headline as children"
<CardContainer>
  <img src="/budget.jpg" alt="City hall at night" /> {/* first child */}
  <h2>Budget Debate</h2> {/* second child */}
</CardContainer>
```

- [p] ◇ {runway: container component} A component that draws a frame and places whatever it receives as `children` is called a **container component**. The caller decides what goes inside, and the container decides where it goes. Preview, one sentence: Lecture 10 shows how a container can skip its frame when nothing is nested. ◼ Educational objective: name the term from the map's Terms table; the map's Preview row.

### Rest syntax collects the props you did not name

- [runway] Rest syntax in destructuring, used by Questions 3, 4, and 5.

- [p] ◇ {runway: plain JavaScript first} Rest syntax is plain JavaScript. In destructuring, the reader names the keys they want, and three dots before a last name collect every other key into a new object. ◼ Educational objective: the refresher the Terms table asks for.

- [code] Rest syntax on a plain object:

```js title="Rest syntax on a plain object"
const story = { title: 'Accord', id: 'top', tone: 'quiet' };
const { title, ...rest } = story; // title is 'Accord'
console.log(rest); // { id: 'top', tone: 'quiet' }
```

- [p] ◇ {runway: on props} `title` leaves the object by name, and `rest` holds the keys that are left; `story` does not change. The props object is an ordinary object, so the same syntax works in a parameter list. The caller writes `<CardContainer id="top" aria-label="Lead story">`. ◼ Educational objective: carry the same syntax onto props.

- [code] Rest syntax on props:

```jsx title="Rest syntax on props"
function CardContainer({ children, ...rest }) {
  console.log(rest); // { id: 'top', 'aria-label': 'Lead story' }
  return <div className="card">{children}</div>;
}
```

- [p] ◇ {runway: closing rule} `children` takes the nested content by name, and `rest` collects `id` and `aria-label`. Rest syntax takes out the keys you name and gathers all the others into one object. ◼ Educational objective: close with the rule.

### Spread writes every key of an object as an attribute

- [runway] JSX spread attributes, used by Questions 3 and 4.

- [p] ◇ {runway: name it and show it} In JSX, `{...object}` inside a tag writes each key of the object as an attribute. Two elements, one spread and one written by hand, are the same. ◼ Educational objective: name the form next to its code.

- [code] Spread attributes:

```jsx title="Spread attributes"
const link = { href: '/sport', title: 'Sport news' };
const first = <a {...link}>Sport</a>; // link gives href and title
const second = <a href="/sport" title="Sport news">Sport</a>; // written by hand
```

- [p] ◇ {runway: who does what} React reads the object and writes `href` and `title` on the `<a>`, so the browser gets `<a href="/sport" title="Sport news">Sport</a>`. This is called **JSX spread attributes**. ◼ Educational objective: say who acts and what the browser gets.

- [code] Spread attributes with dashes:

```jsx title="Spread attributes with dashes"
const ids = { id: 'top', 'data-story-id': '42' };
const section = <section {...ids}>Top story</section>; // id and data-story-id
```

- [p] ◇ {runway: closing rule} The browser gets `<section id="top" data-story-id="42">`. Rest syntax gathers keys into an object, and spread writes an object's keys back out as attributes. ◼ Educational objective: confirm with a second example and close. The order of attributes around a spread and spreading the whole props object stay with Questions 3 and 4.

### Principles of React: Container Composition and Prop Spreading

[question-cycle]
- Question: Why does content nested between a component's tags disappear from the screen?
- Code and result: Caller writes `<CardContainer><h2>Transit Accord Reached</h2></CardContainer>`, but `CardContainer` returns `<div className="card" />`. Screen shows an empty `<div class="card"></div>`, the headline text vanishes, and the console shows 0 errors.
- Verdict: does not work
- Answer: React compiles nested markup into the `children` key of props: `_jsx(CardContainer, { children: [...] })`. React invokes `CardContainer` with that props object. Because `CardContainer` omits `{children}` in its return statement, React renders only the outer `<div>` and silently discards the nested elements. Dropped child components never execute.
- Fix: Accept `{ children }` in the parameter list and place `{children}` inside the returned JSX markup.
- Rule with boundary: Always render `{children}` whole inside container markup to display nested caller content; never omit the slot or attempt to call array methods on `children` without verifying its type.
- Needs: `children` prop, `_jsx` call, development console
- Example: Caller nests a headline in `CardContainer`, and `CardContainer` renders `{children}` inside its wrapper `<div>`.
- Diagram: ASCII diagram showing JSX call site compiling into `_jsx(CardContainer, { children: [...] })`, passing into `CardContainer`, and embedding in `<div className="card">{children}</div>`.

> [!PRINCIPLE]
> **Principle 1: Content placed between tags arrives as the children prop**
>
> React places whatever sits between a component's opening and closing tags into `props.children`. The container decides where it goes by writing `{children}` in its JSX. The caller decides what it is.
>
> *We should do this:*
> ```jsx
> function CardContainer({ children }) {
>   return <div className="card">{children}</div>; // places children in slot
> }
> ```
> *Instead of doing this:*
> ```jsx
> function CardContainer({ children }) {
>   return <div className="card" />; // drops children without an error
> }
> ```
> >> `children` prop : The property on the props object that receives whatever markup sits between a component's opening and closing tags.

[question-cycle]
- Question: Should a card component add a separate prop for every badge, image, and button that callers need?
- Code and result: Developer adds `badgeText`, `author`, `hasImage` to `NewsCard`. Stories without a badge still render `<span className="badge">{badgeText}</span>`, displaying an empty colored pill with background styling on screen.
- Verdict: does not work
- Answer: Adding a prop for every optional visual element bloats the component parameter list and renders empty tags when values are omitted. Inverting control with slot composition allows callers to pass custom inner markup as `children`, while the container provides only the shared frame. Named props are reserved for fixed requirements that every card must guarantee.
- Fix: Replace specialized layout flags with an open `{children}` slot, keeping named props only for invariant card data.
- Rule with boundary: Use `{children}` for variable inner layouts and reserved named props for values every container instance must enforce; never multiply boolean layout flags for caller-specific markup.
- Needs: container component, props, `children` prop
- Example: `StoryFeed` passes custom headline, badge, and byline directly between `<CardContainer>` tags.
- Diagram: ASCII diagram contrasting monolithic prop bloat with slot composition.

> [!PRINCIPLE]
> **Principle 2: Put variable layout in children and fixed requirements in named props**
>
> A container component owns the outer visual frame, such as borders, shadows, and padding. The caller owns the inner content. Reserve named props for data every card must show, and use `{children}` for everything that varies.
>
> *We should do this:*
> ```jsx
> function CardContainer({ title, children }) {
>   return (
>     <div className="card">
>       <h2>{title}</h2> {/* fixed requirement */}
>       {children} {/* variable inner layout */}
>     </div>
>   );
> }
> ```
> *Instead of doing this:*
> ```jsx
> function NewsCard({ title, badgeText, author }) {
>   return (
>     <div className="card">
>       <span className="badge">{badgeText}</span> {/* renders empty pill */}
>       <h2>{title}</h2>
>     </div>
>   );
> }
> ```
> >> Container component : A component that provides a reusable outer frame while leaving its inner content open for callers to supply through slots.

[question-cycle]
- Question: Can a container forward all incoming attributes by spreading the entire props object onto its native element?
- Code and result: Component writes `<div className="card" {...props} />` when caller passes `isFeatured={true}` and `badgeText="Breaking"`. React prints console warning: "React does not recognize the `isFeatured` prop on a DOM element", and `badgetext="Breaking"` leaks into the live DOM attributes.
- Verdict: does not work
- Answer: The incoming `props` object contains both DOM attributes and component-specific props. Spreading `props` whole copies non-standard attributes onto the native DOM node, causing browser warnings, invalid HTML attributes, and unintended behavior like `title` becoming a tooltip. Rest syntax isolates consumed props and leaves only valid pass-through attributes in `rest`.
- Fix: Destructure component-specific props and collect unconsumed attributes with `...rest`, spreading only `{...rest}` onto the native element.
- Rule with boundary: Always gather unconsumed attributes with rest syntax `{ consumed, ...rest }` and spread only `{...rest}` onto underlying native elements; never spread the entire `props` object onto a DOM element.
- Needs: rest syntax, JSX spread attributes, DOM attribute leakage
- Example: `CardContainer` unpacks `{ children, ...rest }` and writes `<div className="card" {...rest}>{children}</div>`.
- Diagram: ASCII diagram showing `props` splitting into consumed variables and `rest`, forwarding only `rest` to the `<div>`.

> [!PRINCIPLE]
> **Principle 3: Unpack consumed props and spread only the rest on native elements**
>
> Spreading the entire props object onto a native DOM element leaks component-specific props into the HTML tree, producing invalid attributes and browser console warnings. Extract the props the container needs and spread only the remaining attributes.
>
> *We should do this:*
> ```jsx
> function CardContainer({ children, ...rest }) {
>   return (
>     <div className="card" {...rest}> {/* spreads only unconsumed props */}
>       {children}
>     </div>
>   );
> }
> ```
> *Instead of doing this:*
> ```jsx
> function CardContainer(props) {
>   return (
>     <div className="card" {...props}> {/* leaks custom props to DOM */}
>       {props.children}
>     </div>
>   );
> }
> ```
> >> Rest syntax : The `...rest` syntax in destructuring that gathers all unextracted object keys into a single object.
> >> JSX spread syntax : The `{...rest}` syntax in JSX that expands every key-value pair of an object as tag attributes.

[question-cycle]
- Question: Why does passing a custom className to a container wipe out its default styling?
- Code and result: Container renders `<div className="card" {...rest}>{children}</div>`. Caller passes `className="featured"`. In the browser DOM, the element displays `<div class="featured">`, completely losing the base `.card` border, padding, and layout styles.
- Verdict: does not work
- Answer: React evaluates JSX attributes from left to right. When `{...rest}` appears after `className="card"`, the caller's `className="featured"` inside `rest` overrides the earlier `className`. If both classes are needed, destructure `className` explicitly and concatenate strings: `className={'card ' + className}`.
- Fix: Destructure `className` out of `rest` and concatenate it with the base class: `className={'card ' + className}`.
- Rule with boundary: Place overridable defaults before `{...rest}`, place mandatory values after `{...rest}`, and concatenate classes when both caller and container must contribute styling.
- Needs: JSX spread attributes, `className`, string concatenation
- Example: Container concatenates `'card ' + className` and spreads `{...rest}`.
- Diagram: ASCII diagram demonstrating left-to-right evaluation precedence in JSX tags.

> [!PRINCIPLE]
> **Principle 4: Order around the spread decides which attribute wins**
>
> React evaluates attributes from left to right. Attributes written before the spread act as overridable defaults; attributes written after the spread override whatever the caller passed. When both sides must contribute classes, combine them explicitly.
>
> *We should do this:*
> ```jsx
> function CardContainer({ className, children, ...rest }) {
>   return (
>     <div className={'card ' + className} {...rest}>
>       {children}
>     </div>
>   );
> }
> ```
> *Instead of doing this:*
> ```jsx
> function CardContainer({ children, ...rest }) {
>   return (
>     <div className="card" {...rest}> {/* caller className overwrites card */}
>       {children}
>     </div>
>   );
> }
> ```
> >> Attribute precedence : The rule that when the same attribute appears multiple times in JSX, the rightmost evaluation wins.

[question-cycle]
- Question: Why does string concatenation produce class="card undefined" when a caller omits className?
- Code and result: Container uses `className={'card ' + className}`. Caller renders `<CardContainer><p>Story</p></CardContainer>` without passing `className`. DOM renders `<div class="card undefined">`, polluting the DOM with an invalid class name string.
- Verdict: does not work
- Answer: When a caller omits `className`, the destructured variable evaluates to `undefined`. In JavaScript, `'card ' + undefined` converts `undefined` to the literal string `"undefined"`. Assigning a default parameter `className = ''` ensures an omitted prop falls back to an empty string, yielding clean class names.
- Fix: Provide a default fallback in the destructuring parameter list: `className = ''`.
- Rule with boundary: Always assign default parameter values for optional props used in string concatenation or calculations; remember that defaults trigger strictly on `undefined` and missing props, never on `null` or `false`.
- Needs: default parameter value, `null` and `undefined`
- Example: Parameter list declares `{ className = '', children, ...rest }`.
- Diagram: ASCII diagram showing missing prop evaluating to `undefined`, triggering default parameter fallback `''`.

> [!PRINCIPLE]
> **Principle 5: Default parameter values protect missing props from undefined**
>
> When a caller omits a prop, its value is `undefined`. Concatenating an unassigned prop into a string coerces it to the literal text `"undefined"`. Assign a default parameter value in destructuring to provide a safe fallback.
>
> *We should do this:*
> ```jsx
> function CardContainer({ className = '', children, ...rest }) {
>   return (
>     <div className={'card ' + className} {...rest}>
>       {children}
>     </div>
>   );
> }
> ```
> *Instead of doing this:*
> ```jsx
> function CardContainer({ className, children, ...rest }) {
>   return (
>     <div className={'card ' + className} {...rest}> {/* renders card undefined */}
>       {children}
>     </div>
>   );
> }
> ```
> >> Default parameter value : A fallback value assigned in a destructuring pattern that applies when the incoming property is `undefined` or omitted.

### Let's Design a Practical Example

- [p] ◇ {practical: newsroom editorial grid case study} We assemble a production article feed demonstrating container composition with `children`, prop forwarding with rest and spread, and clean default parameters across three distinct card layouts. ◼ Educational objective: apply all 5 principles in a multi-file architecture.

- [assembly-step] Step 1: CardContainer Component
- [code] CardContainer.jsx:

```jsx title="CardContainer.jsx"
export function CardContainer({ // generic card frame
  className = '', // default empty string prevents undefined
  children, // open slot for caller content
  ...rest // collects pass-through attributes
}) {
  return (
    <article className={'card ' + className} {...rest}>
      {children} {/* renders caller elements */}
    </article>
  );
}
```

- [assembly-step] Step 2: EditorialGrid Component
- [code] EditorialGrid.jsx:

```jsx title="EditorialGrid.jsx"
import { CardContainer } from './CardContainer';

export function EditorialGrid({ stories }) { // renders card variants
  return (
    <div className="grid">
      {stories.map((story) => (
        <CardContainer
          key={story.id}
          className={story.isFeatured ? 'featured' : ''}
          aria-label={story.title}
        >
          <span className="badge">{story.badge}</span>
          <h2>{story.title}</h2>
          <p>{story.summary}</p>
        </CardContainer>
      ))}
    </div>
  );
}
```

- [assembly-step] Step 3: App Component
- [code] App.jsx:

```jsx title="App.jsx"
import { EditorialGrid } from './EditorialGrid';

const STORIES = [ // news feed data

```

### For the interview

> **The Interview Question:** How do the children prop, spread attributes, and default values work?

- [interview] The Hidden Signal ◼ Interviewers test whether you understand the fundamental distinction between configuration-driven components and slot-driven composition. Junior candidates add a prop for every minor visual requirement; senior engineers invert control using `children` to provide flexible containment. They also verify that you understand the perils of spreading entire prop objects onto native DOM nodes and know how JSX evaluates attribute precedence.
- [interview] The Classic Trap ◼ Assuming `children` is always an array. If a container receives a single child, `children` is a single element object, and calling `children.map()` throws `TypeError: children.map is not a function`. Assuming `{...props}` is harmless on native elements; spreading unconsumed props leaks non-standard attributes to the DOM and triggers React console warnings.
- [interview] What is Actually Going On ◼ JSX compiles nested tags into the `children` key of the props object: `_jsx(Card, { children: [...] })`. The container receives lightweight element descriptors, not rendered HTML. Spread attributes are evaluated from left to right; the last attribute evaluated wins. Default parameter values trigger exclusively on `undefined` and missing properties, never on `null` or `false`.
- [interview] Where It Gets Tricky ◼ Edge cases in `children` and spread: passing `<Card children="attr">nested</Card>` causes the nested content to win because the compiler evaluates nested elements after opening tag attributes. Spreading `key` props triggers special React warnings. The container function body runs before child component function bodies execute, but child components never execute if the container drops `{children}`.

### Glossary

- [glossary] children prop ◼ The reserved React property that captures all markup nested between a component's opening and closing tags.
- [glossary] container component ◼ A component that provides a reusable outer visual frame while exposing open slots for callers to supply inner content.
- [glossary] slot composition ◼ The architectural pattern of structuring user interfaces by nesting components inside container placeholders rather than passing monolithic layout configuration flags.
- [glossary] rest syntax ◼ The JavaScript `...rest` pattern in destructuring that gathers unextracted object properties into a fresh object.
- [glossary] JSX spread syntax ◼ The `{...rest}` JSX notation that unpacks an object's properties as attributes on an element tag.
- [glossary] default parameter value ◼ A fallback value assigned during destructuring that applies when an incoming property is `undefined` or omitted.

### Summary

- [review-title] Container Composition and Prop Spreading Architecture
- [review-subtitle] Essential rules for building reusable frames and forwarding attributes
- [numbered-review-point] 1. Content placed between tags arrives as `props.children`: the container decides where it goes, while the caller decides what it is.
- [numbered-review-point] 2. Slot composition inverts control: reserve named props for fixed requirements and use `{children}` for variable content.
- [numbered-review-point] 3. Rest syntax `{ children, ...rest }` extracts consumed props and isolates unconsumed attributes for safe forwarding.
- [numbered-review-point] 4. Attributes evaluate from left to right: overridable defaults precede `{...rest}`, while enforced values follow it.
- [numbered-review-point] 5. Default parameters `className = ''` prevent string coercion of `undefined` into `"card undefined"`.
- [if-then-rule] IF a component provides a reusable frame for variable content, THEN use `{children}` rather than multiplying layout props.
- [if-then-rule] IF passing extra attributes to an underlying DOM node, THEN unpack consumed props and spread only `{...rest}`.
- [if-then-rule] IF an optional prop is concatenated into a string, THEN assign a default parameter value in destructuring.

| Pattern | Mechanism | Operational Benefit |
|---|---|---|
| Slot Composition | `function Card({ children })` | Inverts control, eliminating layout prop explosion |
| Attribute Forwarding | `<div {...rest} />` | Passes accessibility and DOM attributes cleanly |
| Parameter Defaults | `{ className = '' }` | Prevents `undefined` coercion in string joins |
