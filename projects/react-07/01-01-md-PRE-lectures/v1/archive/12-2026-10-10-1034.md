### The Friction of Impure Rendering and Shared Variables

- [p] ★ {preknowledge: JSX markup, components as functions, props passing, DOM tree rendering} In earlier lessons, you learned that React components are JavaScript functions that return JSX markup descriptors. You passed data downward from parent components to child components through props, treating each component as a modular building block. However, many developers carry habits from traditional scripting, where functions freely read and write global variables, mutate shared lists, or reach directly into the browser document with `document.getElementById()`. If a developer attempts to number items by incrementing an outside counter variable inside a component function body, the application state quickly corrupts. In development mode, the counter increments twice per render, displaying `#2` and `#4` instead of `#1` and `#2`. When a user interacts with the page and triggers a re-render, the numbers drift higher on every render cycle. ◼ Educational objective: recall functional components and props while exposing how mutating external variables during render causes unpredictable output.
- [p] ★ {problem: mutating outside variables breaks predictability under development double-rendering} It is possible that a developer may declare a variable `let articleCount = 0` outside their component and increment it inside the function body with `articleCount = articleCount + 1`, expecting each rendered card to receive the next consecutive integer. On initial inspection in simple scripts, this looks like a quick way to number items. However, React does not guarantee that a component will run only once, in a specific order, or at a predictable time. In development, React StrictMode intentionally calls every component function twice to expose hidden side effects. Because the outside variable survives across calls, the first card increments the counter to `1` on the first call and to `2` on the second call. The browser displays "Article #2" for the very first item on screen. If another component reads `articleCount`, its output changes depending on which component React decided to call first. ◼ Educational objective: analyze why mutating module-scoped variables produces corrupted numbers under StrictMode double-rendering.
- [p] ★ {old solution: tracking render order through global counters or mutating shared arrays} In traditional imperative scripts, developers frequently used global counters to number elements or called `array.push()` directly on shared data arrays to append banners. In React, mutating variables that existed before the render creates race conditions, duplicate list items, and unstable user interfaces. ◼ Educational objective: contrast legacy mutable tracking patterns with React's pure render requirements.

- [code] Naive External Counter Mutation Attempt:

```jsx title="Naive Counter Attempt"
let ~articleCount~ = 0; // External module variable
function Article({ title }) {
  ~articleCount = articleCount + 1~; // Mutates outside variable
  return (
    <article className="card">
      <h3>#{articleCount}: {title}</h3>
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `let articleCount = 0`: module-level variable that persists across render calls. 2. `articleCount = articleCount + 1`: side effect executed directly in the render body. 3. `#{articleCount}`: render output that changes based on how many times React calls the function.

- [p] ★ {mechanism: pure functions, same inputs same output, and props passing} React eliminates this unpredictability by demanding that every component behave as a **pure function**. A pure function is like a mathematical formula: given the same inputs, it always returns the exact same result, and it changes nothing that existed before it was called. Instead of incrementing an outside counter, the parent component calculates the item number (such as the array index) and passes it downward as an explicit prop: `<Article itemNumber={index + 1} title={title} />`. Because the component only reads its props and calculates JSX, React can call it once, twice, or ten times, and the output never drifts. ◼ Educational objective: establish the pure component contract where output depends strictly on props and produces zero external mutations.
- [grounding] [!] Grounding card: Why does my component log twice on page load? ◼ Opening question: Why does my component log twice on page load? ◼ Friction target: Developers adding a `console.log()` to their component body observe duplicate messages in the browser console on every single page load. ◼ Tactile scene: A developer opens their browser developer tools, refreshes the page, and sees `render Article` printed two consecutive times for a single card; assuming their code has an infinite loop or a duplicate mount bug, they remove `<StrictMode>` from `main.jsx` to silence the log. ◼ Bold key terms: **pure function**, **side effect**, **StrictMode double-rendering**, **idempotence**, **developer tooling**. ◼ Operational resolution: In development, React wraps the root tree in `<StrictMode>`, which deliberately invokes every component function twice during each render pass; if a component is pure, the second invocation produces the exact same JSX and causes zero harm; if a component mutates external state or performs side effects, the second call immediately breaks the output on screen, alerting the developer to the defect before shipping to production.

### Components as Mathematical Formulas and the Render Contract

- [p] ◇ {conceptual grounding: mathematical purity and the formula model} To understand why React requires pure components, we must examine what purity means in computer programming. In mathematics, consider the formula `y = 2x`. If `x` equals `2`, then `y` is always `4`. If `x` equals `3`, then `y` is always `6`. The answer never becomes `9` or `-1` depending on what time of day it is or which formula was calculated first. A pure function obeys two simple laws: first, it minds its own business, never modifying any variable or object that existed before it was called; second, same inputs always produce the same output. React components are designed around this exact mathematical foundation: `UI = f(props)`. A component takes props as inputs and calculates a tree of JSX elements as output. ◼ Educational objective: ground the concept of component purity in standard mathematical formulas and the two core rules of pure functions.
- [p] ★ {runtime distinction: what code runs in render versus outside render} A critical skill for every React developer is understanding when code runs. Code written directly at the top level of your component function body runs during the **render phase**. During rendering, React calculates what the next user interface should look like. Because React can pause, restart, or run this calculation multiple times, the render phase must remain completely free of **side effects**. A side effect is any operation that changes the outside world or produces an observable consequence beyond returning JSX (such as changing `document.title`, writing to the DOM with `document.getElementById()`, starting a timer, or sending an analytics report). Code inside event handlers (like button clicks) runs outside of the render phase, in response to direct user actions. Event handlers do not need to be pure, but code at the top level of a component body must always be pure. ◼ Educational objective: distinguish between render-phase code and event handlers, explaining why the top level of a component body must remain side-effect free.
- [p] ★ {syntactic reminder: local mutation versus external mutation} Developers often ask whether they are forbidden from using any JavaScript mutation in React. The answer is that **local mutation** is completely valid and idiomatic. Local mutation means modifying variables, arrays, or objects that you created inside the current render pass. For example, if you create a local array `const items = [];` inside your component body and populate it using `items.push(<li key={id}>{title}</li>)` inside a loop, that mutation is 100% pure. Because the array was created inside that specific function call, no code outside the component knows that the array was modified. However, mutating a variable declared outside the function, mutating a prop, or mutating an object after it has been passed into JSX violates purity and corrupts application state. ◼ Educational objective: clarify the boundary of local mutation, explaining why mutating newly created local values is safe while mutating external values is prohibited.
- [p] ★ {syntactic reminder: destructuring and the ternary conditional operator} Let us review two JavaScript features used frequently when writing pure components: **object destructuring** and the **ternary conditional operator**. Object destructuring (`function Article({ title, minutes })`) unpacks specific properties directly from the incoming props object into local variables, eliminating repetitive `props.title` syntax. The ternary conditional operator (`condition ? valueIfTrue : valueIfFalse`) is JavaScript's inline decision expression. It evaluates the test before the question mark: if the test is true, it evaluates the expression before the colon; otherwise, it evaluates the expression after the colon. Because a ternary operator is an expression that produces a value, it can sit safely inside JSX curly braces to calculate dynamic classes and text purely during render. ◼ Educational objective: provide a clear, junior-friendly reminder of object destructuring and ternary conditional operators in JavaScript.

### Principles of React: The Core Laws of Pure Rendering

- [p] ◇ When preparing for senior technical interviews, candidates must clearly explain what makes a component pure, why React uses development double-rendering, how local mutation differs from external mutation, why direct DOM writes fail during render, and why non-idempotent functions break the render contract. To master these concepts, we formalize the four governing principles of pure rendering: ◼ Educational objective: frame the four principles from the perspective of an engineering candidate preparing for senior technical interviews.

> [!PRINCIPLE]
> **Principle 1: Treat a Component as a Formula React May Run Any Number of Times**
> A pure component returns the same JSX for the same props and changes nothing outside itself. React decides when and how often to call your component function: twice per render under StrictMode in development, again whenever its inputs change, and in no guaranteed order between siblings.
> 
> >> pure component : a component function that produces identical JSX for identical inputs and causes zero outside side effects
> >> StrictMode double-rendering : a development-only check where React calls component functions twice to detect unexpected side effects

- [p] ★ Principle 1 operational derivation: In React, component execution is an on-demand calculation. React does not sign a contract promising to run your component function exactly once per screen update. Under `<StrictMode>` in development, React intentionally renders your component twice. If you place `console.log('render Article:', itemNumber)` inside the component body, you will see two log lines in the browser console on a single page load. If you use React DevTools, the second log line appears slightly dimmed to indicate that it came from the development check. In a production build, the check is completely stripped, and the component renders once. If your component is a pure formula, calling it once, twice, or ten times produces the exact same JSX tree and changes nothing in memory. What breaks when developers forget this model is that they treat the double call as a bug, remove StrictMode, and leave hidden mutation bugs that explode later in production. ◼ Educational objective: derive how React's rendering model relies on mathematical purity and why StrictMode double-calls components in development.

- [code] StrictMode Double Call Verification:

```jsx title="StrictMode Double Call Verification"
export default function Article({ title, itemNumber }) {
  ~console.log~('render Article:', itemNumber); // Double-invoked by StrictMode
  return (
    <article className="card">
      <h3>#{itemNumber}: {title}</h3>
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `console.log('render Article:', itemNumber)`: observable print demonstrating the two StrictMode development passes. 2. `itemNumber`: explicit prop passed from parent, guaranteeing deterministic output. 3. `return (<article ...>)`: pure declarative JSX description produced from inputs.

> [!PRINCIPLE]
> **Principle 2: Change Nothing That Existed Before the Render**
> During render, never write to variables declared outside the component or mutate objects received as props. You may create fresh arrays or objects inside the function body and mutate them locally, provided that mutation finishes before the value is passed to JSX.
> 
> >> external mutation : changing a variable, array, or object that existed before the current component render call
> >> local mutation : modifying a fresh variable or array created inside the current render call before passing it to JSX
> 
> *It is best practice to do this:*
> `function ArticleList({ stories }) {`
> `  const list = ~[...stories, { id: 'ad' }]~; // Fresh local array`
> `  return <Feed stories={list} />;`
> `}`
> 
> *Instead of doing this:*
> `function ArticleList({ stories }) {`
> `  ~stories.push({ id: 'ad' })~; // Mutating props in place`
> `  return <Feed stories={stories} />;`
> `}`

- [p] ★ Principle 2 operational derivation: When a component runs, anything created before that function call is off-limits for mutation. This includes variables declared at the module level, global window properties, and objects or arrays passed in as props. If you call `stories.push(...)` on an array received as a prop, you mutate the caller's memory. Under StrictMode, that `push()` executes twice, resulting in two identical ad items in the list and triggering React's "Encountered two children with the same key" warning. Similarly, if you mutate a local object after passing it into a JSX element—such as setting `styles.color = 'red'` after writing `<Header styles={styles} />`—the earlier element receives the modified value because both share the same object reference in memory. In contrast, creating a new array inside the function and mutating it is completely safe: `const cards = []; for (let i = 0; i < 3; i++) cards.push(<Card key={i} />);`. Because `cards` was created in that render call, no other component can see it. ◼ Educational objective: analyze the operational difference between mutating external values versus mutating fresh local values.

- [code] Safe Array Copy Pattern:

```jsx title="Safe Array Copy Pattern"
export default function ArticleList({ articles, featured }) {
  const fullList = ~[...articles, featured]~; // Creates fresh local array
  return (
    <section className="feed">
      {fullList.map((story) => (
        <p key={story.id}>{story.title}</p>
      ))}
    </section>
  );
}
```

◼ **The what-this-introduces list:** 1. `[...articles, featured]`: array spread syntax that creates a shallow copy with the new item appended. 2. `fullList`: new local array reference that leaves `articles` untouched. 3. `fullList.map(...)`: pure transformation of the copied array into JSX elements.

> [!PRINCIPLE]
> **Principle 3: Keep Side Effects Out of the Render Path**
> The component body exists strictly to calculate JSX. Never modify DOM nodes, start timers, send network requests, or trigger analytics from the top level of your component function. Express dynamic visual changes in the returned JSX, and move side effects into event handlers.
> 
> >> side effect : any operation that modifies state outside the current function or interacts with outside systems
> >> render path : the synchronous code executed at the top level of a component function to calculate markup
> 
> *It is best practice to do this:*
> `function Badge({ isUrgent }) {`
> `  const cls = ~isUrgent ? 'urgent' : 'normal'~; // Pure JSX class`
> `  return <span className={cls}>News</span>;`
> `}`
> 
> *Instead of doing this:*
> `function Badge({ isUrgent }) {`
> `  const badge = document.getElementById('badge');`
> `  ~badge.className = 'urgent'~; // Mutating DOM directly`
> `  return <span id="badge">News</span>;`
> `}`

- [p] ★ Principle 3 operational derivation: A frequent pitfall for developers transitioning to React is trying to change the page imperatively during render. For example, if you write `document.getElementById('badge').className = 'urgent'` directly in the component body, the code fails with a fatal error on the initial render: `TypeError: Cannot set properties of null (setting 'className')`. The error occurs because the component function runs *before* React creates or mounts the browser DOM elements. The element `#badge` does not exist in the document yet. Even if the element already existed from an earlier render, modifying DOM properties by hand bypasses React's reconciliation engine and creates desynchronized interfaces. The pure React solution is to express the desired class directly in the returned markup using a ternary operator: `<span className={isUrgent ? 'urgent' : 'normal'}>`. When you need to perform real side effects—such as sending an HTTP request or updating analytics—place that code inside an event handler (which runs on user interaction) rather than in the render path. ◼ Educational objective: derive why imperative DOM queries crash during initial render and how declarative JSX properties replace imperative mutations.

- [code] Declarative Class Computation:

```jsx title="Declarative Class Computation"
export default function StatusBadge({ isUrgent, label }) {
  const badgeClass = isUrgent
    ? ~'badge-urgent'~ // Urgent status styling
    : 'badge-standard';
  return (
    <span className={badgeClass}>
      {label}
    </span>
  );
}
```

◼ **The what-this-introduces list:** 1. `isUrgent ? 'badge-urgent' : 'badge-standard'`: pure ternary calculation stored in a local variable. 2. `badgeClass`: local string variable that causes zero external side effects. 3. `className={badgeClass}`: declarative binding that lets React update the DOM node safely.

> [!PRINCIPLE]
> **Principle 4: Avoid Non-Idempotent Calls in Render Output**
> Calling non-idempotent functions like Math.random() or new Date() directly in the component body produces different values on every call, breaking the guarantee that identical inputs yield identical JSX. Pass dynamic numbers and timestamps in as props from outside the render.
> 
> >> non-idempotent function : a function that produces a different return value each time it is invoked, even with identical arguments
> >> idempotent rendering : running a component with the same inputs always produces the exact same JSX output
> 
> *It is best practice to do this:*
> `function TimeDisplay({ publishedAt }) {`
> `  return <span>~{publishedAt}~</span>; // Deterministic prop`
> `}`
> 
> *Instead of doing this:*
> `function TimeDisplay() {`
> `  const now = ~new Date().toISOString()~; // Impure clock call`
> `  return <span>{now}</span>;`
> `}`

- [p] ★ Principle 4 operational derivation: A function is idempotent if executing it multiple times with the same inputs produces the exact same result. When you write `const id = Math.random()` or `const time = new Date()` inside your component body, you introduce non-idempotent code into the render path. Under StrictMode in development, the first call generates one random number (such as `0.791`), and the second call generates a completely different number (such as `0.029`). The browser console displays two disagreeing values, and the screen displays whichever happened to run last. Furthermore, calling `new Date()` in the render body freezes the time at the exact millisecond the component rendered, meaning the clock never ticks forward unless something triggers a re-render. To preserve purity, generate random identifiers or capture the current timestamp outside of the component render—such as passing it downward as a prop from an event handler or data store. ◼ Educational objective: demonstrate how non-idempotent calls like Math.random() cause disagreeing values under StrictMode and freeze time displays.

- [code] Idempotent Prop Timestamp:

```jsx title="Idempotent Prop Timestamp"
export default function ArticleTime({ timestamp }) {
  return (
    <time className="published-date">
      ~{timestamp}~ // Prop timestamp passed downward from parent
    </time>
  );
}
```

◼ **The what-this-introduces list:** 1. `timestamp`: prop passed from the parent, ensuring the component remains an idempotent formula. 2. `<time className="published-date">`: semantic HTML element wrapping the text. 3. `{timestamp}`: pure evaluation of the incoming prop without generating dynamic dates during render.

### Where you will meet this

- [p] ★ 1. **Server-Side Rendering and Static Site Generation**: Because pure components produce identical markup for identical inputs, server frameworks like Next.js can safely run your component tree on a server to generate HTML for thousands of concurrent reader requests without cross-request state contamination.
- [p] ★ 2. **Performance Caching with Memoization**: When a component is pure, React can safely skip re-rendering it if its props have not changed (`React.memo`), caching the previous output because a pure formula is guaranteed to return the exact same JSX.
- [p] ★ 3. **Interrupted Concurrent Rendering**: When React prioritizes urgent user inputs over background updates, it can pause or abort a component render halfway through and restart it later; pure components guarantee that aborted renders leave zero corrupted traces behind.
- [p] ★ 4. **Automated Unit Testing**: Testing pure components is straightforward and reliable because you do not need to mock global document properties, reset external counter variables, or clean up leaked side effects between test cases.

### Glossary

- **Pure Function** ◼ A function that always returns the exact same result given the same inputs and produces zero side effects on preexisting variables or outside systems.
- **Side Effect** ◼ Any operation that modifies state outside the current function or interacts with outside systems (such as DOM mutations, timers, network requests, or analytics) during execution.
- **StrictMode** ◼ A React development-only wrapper component that deliberately executes component functions twice to expose unintended side effects and impure rendering logic.
- **Local Mutation** ◼ Modifying variables, arrays, or objects created within the current render execution before they are passed into JSX, which remains 100% pure.
- **Idempotence** ◼ The property of a code block or function where executing it multiple times with identical inputs produces the exact same outcome without state drift.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Pure Render Calculations

➔ ALWAYS treat your component function as a pure mathematical formula: `UI = f(props)`.

➔ ALWAYS pass dynamic values like item numbers, timestamps, and counters downward as explicit props rather than incrementing external variables.

❒ Managing Mutation and Data Flow

➔ NEVER mutate variables, arrays, or objects that existed before the component was called.

➔ IF you need to accumulate or format items during render THEN use local mutation on fresh arrays created within the same function call.

➔ NEVER mutate a local object after it has been passed into a JSX element.

❒ Side Effects and Browser Interaction

➔ NEVER write to DOM nodes, start timers, or trigger network analytics directly inside the component body.

➔ IF you need visual class changes based on data THEN calculate them declaratively in JSX using ternary conditional operators.

➔ ALWAYS place interactive side effects inside event handlers that run outside of the render phase.

| | **IMPURE COMPONENT**<br>(Shared Outside State) | **PURE COMPONENT**<br>(Mathematical Formula) |
| ---: | :--- | :--- |
| **Formula contract** | Output changes based on outside variables and call counts | Same inputs always return identical JSX: `UI = f(props)` |
| **StrictMode behavior** | Corrupts data: counters double (`#2`, `#4`) and logs desynchronize | Fully resilient: calling twice produces identical output |
| **Mutation boundary** | Modifies external variables, props, or preexisting arrays | Mutates only fresh local variables created in current render |
| **Side effects handling** | Imperative DOM writes crash on initial load (`null` selector) | Declarative JSX ternary expressions resolve cleanly in markup |
| **Caching & Optimization** | Unsafe to cache: skipping renders leads to stale visual state | Safe to cache and optimize with `memo` or concurrent restarts |
