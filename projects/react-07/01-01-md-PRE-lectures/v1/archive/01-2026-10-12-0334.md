### The script updates the greeting and forgets the badge

- [p] ★ {preknowledge: HTML markup, element identifiers, document.getElementById, manual textContent mutation} In standard browser scripting, we write HTML tags with identifiers, such as `<p id="greeting">Welcome back, Elena</p>` and `<span id="badge">Subscriber: Elena</span>`. When data changes, JavaScript reaches into the browser document with `document.getElementById('greeting')` and changes its `textContent` property by hand. For a single tag on a small page, this imperative approach feels direct and manageable. ◼ Educational objective: establish the familiar browser DOM baseline grounded in concrete markup before introducing framework synchronization.
- [p] ★ {problem: manual DOM queries cause state drift across multiple widgets} On modern websites, a user's name appears in multiple places across the header, such as the greeting message, the subscriber badge, and an account avatar. To change the name in plain JavaScript, our code must query every matching element one by one and push the new text into each living DOM node. If our script queries the greeting but forgets the badge, the page displays two conflicting names at the same time. This bug is called state drift: application data in memory disagrees with the pixels on the screen. ◼ Educational objective: define state drift as the core architectural flaw of imperative element hunting.

- [code] Naive DOM Scripting (verified in jsdom 30.1.2: updates greeting, leaves badge stale):

```js title="Naive DOM Scripting"
function updateHeaderUser(name) {
  const greeting = document.getElementById('greeting');
  if (greeting) greeting.textContent = 'Welcome back, ' + name; // updates greeting
  // The badge query was forgotten, so the badge keeps the old name
}
```

◼ **The what-this-introduces list:** 1. `document.getElementById`: native DOM method that searches the document tree for an element by string identifier. 2. `textContent`: property that directly overwrites the text inside a living DOM node. 3. Omitted element query: concrete proof of how manual imperative scripting causes state drift across user interface widgets.

- [p] ◇ {question} We wonder what we should write instead in React. How does describing markup from data replace searching for elements with identifiers? What stops two widgets from showing conflicting information? And does updating the header rebuild the whole layout and discard text typed into an input field? ◼ Educational objective: raise the central questions that declarative components and surgical patching resolve.

### Finding elements by hand causes state drift across the page

- [p] ◇ {runway: imperative against declarative} Traditional JavaScript DOM scripting is imperative: our code specifies every single step required to find elements, read properties, and mutate nodes. Imperative code gives orders: find this element, change this text, and find that next element. Declarative programming flips this habit completely: our code describes the final result we want for our data, and the library determines how to update the browser. ◼ Educational objective: teach the distinction between imperative step-by-step commands and declarative target descriptions.
- [p] ★ {runway: the DOM tree} The browser translates an HTML document into an internal tree of objects called the Document Object Model, or DOM. Every HTML tag becomes a DOM node with properties such as `id` and `textContent`. In plain JavaScript, our code manipulates these nodes directly. If our script fails to find a node or skips an element, the DOM stays frozen on old data. ◼ Educational objective: ground the physical role of DOM nodes and their relationship to browser rendering.

### A component describes the interface in JSX from data

- [p] ◇ {runway: the React component} React replaces manual DOM hunting with components. A component is a plain JavaScript function whose name begins with an uppercase letter, such as `SiteHeader`. Instead of querying the document to push text into elements, `SiteHeader` returns a description of what the header should look like. React calls our component function, reads the returned description, and constructs the real DOM elements on the page. ◼ Educational objective: define the React component as a capitalized JavaScript function returning markup descriptions.
- [p] ★ {runway: JSX and curly braces} The markup returned by a component looks like HTML, but it is actually JSX, an extension of JavaScript that describes user interface structure. In plain HTML, typing text inside a tag creates fixed characters that never change. In JSX, placing curly braces `{}` inside a tag creates an evaluation window where JavaScript variables are read. Writing `<p>Welcome back, {readerName}</p>` places the value of the local variable `readerName` directly into the rendered text. ◼ Educational objective: explain JSX markup syntax and the role of curly braces in projecting variable values into content.

### Updating only what differs preserves typed text and focus

- [p] ★ {runway: innerHTML destruction} In plain JavaScript, developers often try to avoid querying multiple elements by replacing a whole container using `header.innerHTML = '<p>Welcome back, ' + name + '</p><input ... />'`. This assignment causes an immediate browser defect: the browser engine destroys every existing DOM node inside that container and creates brand-new elements from the string. If the user was typing inside a search `<input>`, that input node is destroyed. The typed characters vanish, and keyboard cursor focus drops back to the document body. ◼ Educational objective: demonstrate why destructive innerHTML container replacements fail and lose active user input focus.
- [p] ★ {runway: minimal necessary operations} React takes a fundamentally different path. When data changes, React does not wipe the container with `innerHTML`. Instead, React calls the component function again, receives a fresh description of the interface, and compares the new description with the previous one. React calculates the minimal necessary operations required to bring the page up to date. It updates only the specific text nodes that changed, leaving unchanged DOM elements, active text selections, and keyboard input focus completely intact. ◼ Educational objective: teach how in-memory description comparison enables surgical DOM patching and preserves input focus.

### Principles of React: Declarative Synchronization

- [p] ◇ When preparing for engineering interviews, candidates must explain why React adopted the declarative component architecture instead of imperative DOM scripting. To master this paradigm, we study three core principles: describing the page from data, maintaining a single source of truth, and updating only what differs. ◼ Educational objective: frame the upcoming question cycles and principle boxes.

> [!PRINCIPLE]
> **Principle 1: Describe what the page shows for the data instead of changing elements by hand**
> In plain JavaScript, code searches the document for each element and changes its text directly. If an update misses one element, the screen shows old data. In React, a component function returns a description of the markup for the current data, and React builds the page from that description. We describe what the interface shows instead of writing commands to find and change elements.
>
> *We should do this:*
> `function Header() {`
> `  const name = 'Elena';`
> `  return <h1>Welcome, {name}</h1>; // React builds element`
> `}`
>
> *We should not do this:*
> `function updateHeader(name) {`
> `  const el = document.getElementById('name');`
> `  if (el) el.textContent = name; // misses unqueried elements`
> `}`

- [p] ★ In our `SiteHeader` example, writing plain JavaScript required `updateHeaderUser` to search for `greeting` and `badge` by their string identifiers. Forgetting `badge` left the screen showing "Elena" in the badge alongside "Elena Ruiz" in the greeting. In React, we write `SiteHeader` as a function that returns the complete header markup. React calls `SiteHeader`, reads the returned description, and constructs the DOM elements on the screen. Because our code never queries the DOM, no element can be skipped or left behind. ◼ Educational objective: prove Principle 1 on the lesson's code, demonstrating how component descriptions eliminate manual element hunting.

- [question-cycle] Question 2: The name shows in two places across the header
    - Question: "The reader's name shows in the greeting and in the badge. Do I write it in both places?"

    - Verdict: does not do what the reader wanted.
    - Answer: copying text into markup duplicates data; when the variable changes, the copied text remains frozen; storing the name in one local variable `const readerName = 'Elena'` and reading `{readerName}` in both places makes both derive from that single value; updating the variable updates both places together.
    - Fix: read `{readerName}` in both the greeting and the badge from one local variable. The curly brace syntax is taught in the runway section "A component describes the interface in JSX from data".
    - Rule: keep each value in one variable and read it everywhere it appears. Boundary: data stays static in this lesson; changing data over time with state is owned by Lecture 14.

    - Diagram: two elements reading from one central variable box.

> [!PRINCIPLE]
> **Principle 2: Keep each value in one variable and read it everywhere it appears**
> When a value appears in more than one place on the screen, do not type it into the markup more than once. Store the value in a single local variable and read that variable in every place that shows it using curly braces. Because every part of the markup reads from this single source of truth, all parts update together and can never disagree.
>
> *We should do this:*
> `function Header() {`
> `  const name = 'Elena'; // single source of truth`
> `  return (`
> `    <div>`
> `      <h1>Welcome, {name}</h1>`
> `      <span>Subscriber: {name}</span>`
> `    </div>`
> `  );`
> `}`
>
> *We should not do this:*
> `function Header() {`
> `  const name = 'Elena';`
> `  return (`
> `    <div>`
> `      <h1>Welcome, {name}</h1>`
> `      <span>Subscriber: Elena</span> {/* fixed text drifts */}`
> `    </div>`
> `  );`
> `}`

- [p] ★ In `SiteHeader`, pasting the static text "Subscriber: Elena" directly into the badge markup caused state drift the moment `readerName` changed to "Elena Ruiz". The greeting read the updated variable, while the badge stayed frozen on the old literal string. Replacing the fixed text with `{readerName}` ensures that both elements read the exact same variable. When `readerName` is updated in our code, both the greeting and the badge reflect the new name simultaneously. ◼ Educational objective: prove Principle 2 on the lesson's code, demonstrating how a single source of truth eliminates state drift.

- [question-cycle] Question 3: Rebuilding the header wipes the search box
    - Question: "If React builds the header from my description, does it rebuild the whole header when the name changes, and wipe what the reader typed in the search box?"
    - Code and result: plain JavaScript `header.innerHTML = '<p>Welcome back, ' + name + '</p><input placeholder="Search..." />'`; with "elections" typed into the search box, running the update wipes the text and resets cursor focus to the document body (verified in jsdom 30.1.2).
    - Verdict: does not do what the reader wanted.
    - Answer: `innerHTML` destroys living C++ DOM nodes and parses HTML strings from scratch, wiping input buffers and cursor focus; React compares the new description to the previous one in memory and updates only the two text pieces that hold the name; the `<input>` element remains the exact same DOM node on the page, so the typed text and cursor focus stay.
    - Fix: describe the header in React and let React update the page; React applies the minimal necessary operations to patch changed text nodes without rebuilding unchanged elements. The diffing mechanism is taught in the runway section "Updating only what differs preserves typed text and focus".
    - Rule: let React update only the text that differs instead of rebuilding elements with innerHTML. Boundary: Lecture 15 (`render_and_commit`) traces the complete commit phase when state updates occur.
    - Needs: `innerHTML` (runway), input cursor focus (runway), minimal necessary operations (runway).
    - Diagram: DOM tree comparison showing unchanged `<input>` node retained while text nodes are updated.

> [!PRINCIPLE]
> **Principle 3: When data changes, React updates only the text that differs**
> When data updates, React does not destroy and recreate elements on the page. Replacing containers with `innerHTML` destroys living elements, wiping typed input text and losing cursor focus. Instead, React compares the new description with the previous one and applies the minimal changes needed. Unchanged elements remain in place, so an input field keeps what the user typed and keeps its focus.
>
> *We should do this:*
> `function Header() {`
> `  const name = 'Elena';`
> `  return (`
> `    <div>`
> `      <h1>Welcome, {name}</h1> {/* updates text */}`
> `      <input placeholder="Search..." /> {/* keeps focus */}`
> `    </div>`
> `  );`
> `}`
>
> *We should not do this:*
> `function updateHeader(name) {`
> `  const container = document.getElementById('header');`
> `  const html = '<h1>Welcome, ' + name + '</h1><input>';`
> `  container.innerHTML = html; // wipes input text and focus`
> `}`

- [p] ★ In plain JavaScript, assigning a new string to `header.innerHTML` tore down the existing search box. The user's typed search query "elections" vanished, and the active cursor was thrown out of the input. In React, changing `readerName` from "Elena" to "Elena Ruiz" causes React to compare the new description with the old one. React observes that the `<input>` element and the layout container are unchanged. It mutates only the text nodes containing the name. The search box keeps its text, its event listeners, and its active cursor focus. ◼ Educational objective: prove Principle 3 on the lesson's code, proving surgical node patching and focus preservation.

### Step 1: First, we declare the site header component <SiteHeader.jsx>

- [p] ★ We construct `SiteHeader.jsx` to establish the declarative foundation for our header. Instead of writing separate HTML tags and later writing scripts to query them, we define a component function that returns our layout description. We store the reader's name in a single local variable, `readerName`, and project it into both the greeting paragraph and the subscriber badge using curly braces. Notice that our code contains zero calls to `document.getElementById` and zero calls to `textContent`. ◼ Meaningful pedagogical commentary: declarative markup description, single source of truth, total absence of manual DOM queries.

- [code] SiteHeader.jsx, declaring the header component:

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const readerName = 'Elena Ruiz'; // authoritative value in memory
  return (
    <header className="site-header">
      <p id="greeting">Welcome back, {readerName}</p>
      <span id="badge">Subscriber: {readerName}</span>
    </header>
  );
}
```

◼ **The what-this-introduces list:** 1. `SiteHeader`: component function returning markup descriptions. 2. `readerName`: single source of truth variable. 3. `{readerName}`: JSX curly brace projection embedding variable data into two separate elements simultaneously.

### Step 2: Next, we add the interactive search input <SiteHeader.jsx>

- [p] ★ We enhance `SiteHeader.jsx` by adding a search input `<input placeholder="Search articles..." />` alongside our greeting and badge. In naive JavaScript updates using `innerHTML`, appending or modifying text inside the header destroys all living input elements, clearing whatever the reader typed and resetting cursor focus. In React, the input is declared directly as part of the component description. When reader data updates, React keeps the exact same `<input>` DOM node on the screen, preserving user text and keyboard focus without manual intervention. ◼ Meaningful pedagogical commentary: input element integration, cursor focus preservation, contrasting declarative stability against destructive innerHTML replacements.

### Step 3: Finally, we mount the site header inside <App.jsx>

- [p] ★ To complete our application, we mount `SiteHeader` inside the root component `App.jsx`. In standard JavaScript applications, assembling a page often required separate initialization scripts to locate root containers and inject HTML strings. In React, the entire user interface organizes into a unified component hierarchy. `App.jsx` acts as the primary root container, embedding `SiteHeader` into the application layout. When React renders `App`, it evaluates the component tree in memory and constructs the resulting DOM elements in a single, predictable operation. ◼ Meaningful pedagogical commentary: root container composition, component hierarchy, declarative rendering.

### For the interview

> **The Interview Question:** What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

**1. The Hidden Signal**

The interviewer is not merely testing whether you know how to write a component function. They are probing whether you understand the fundamental architectural shift from imperative DOM mutation to declarative state synchronization. A junior developer talks about convenience or shorter syntax. A senior engineer explains that imperative DOM scripting couples application logic directly to fragile document queries, creating inevitable state drift when data appears in multiple widgets. They articulate that React models the user interface as a pure projection of data, computing minimal necessary DOM mutations in memory to preserve element identity and input focus.

**2. The Classic Trap**

The classic trap is claiming that "React is faster than the real DOM because the Virtual DOM has zero performance cost." That claim fails the interview. A well-written, hand-optimized DOM script targeting a single node can execute faster than React's component evaluation and diffing passes. React's true value is predictable synchronization, not raw micro-benchmark speed. Another dangerous trap is telling the interviewer that React throws away and rebuilds the DOM on every render. If React rebuilt the DOM tree, every active text input would lose focus and unsubmitted form state would vanish. React diffs descriptions in memory and surgically mutates only changed text nodes.

**3. What is Actually Going On**

In plain JavaScript, we write imperative commands that find specific elements by identifier and mutate them step by step. If our code misses one element, the screen shows stale data.

In React, we write component functions that return JSX describing what the screen should look like for the current data. React calls our component, evaluates the returned description, and constructs the real DOM elements.

When a value like `readerName` updates, React calls the component again, compares the new description with the previous one, and applies the minimal necessary operations. It changes only the specific text that differs, leaving living DOM nodes and active keyboard focus completely intact.

**4. Where It Gets Tricky**

Where this model gets tricky in production is when developers carry old imperative habits into React applications. Attempting to query DOM nodes directly with `document.getElementById` inside a React component bypasses React's synchronization pipeline, creating severe conflicts between React's in-memory model and physical browser pixels. Similarly, using `innerHTML` or destructive container updates inside a component destroys living DOM node identity, wiping input selections and breaking accessibility focus rings. Embracing React means fully trusting declarative data projection and delegating physical DOM mutations entirely to the library.

### Glossary

- **Declarative UI**: A programming approach where code describes what the interface should show for the current data rather than specifying step-by-step commands to mutate elements.
- **State Drift**: A defect where two or more elements on the screen show conflicting or out-of-date information because manual updates failed to synchronize every matching node.
- **Component**: A JavaScript function whose name starts with an uppercase letter that returns a description of user interface markup in JSX.
- **Single Source of Truth**: The architectural practice of storing a piece of data in one place and reading that exact value everywhere it is displayed to prevent disagreement.
- **Minimal Necessary Operations**: React's strategy of comparing new interface descriptions with previous ones and updating only the specific text nodes or attributes that changed.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Declarative Interface Projection

➔ ALWAYS describe what the page shows for the current data instead of writing imperative commands to find and mutate elements.

➔ IF data updates across the screen THEN let React compute the minimal necessary operations instead of replacing containers with `innerHTML`.

❒ Multi-Widget Data Consistency

➔ ALWAYS store shared values in a single local variable and read that variable in every place that displays it.

➔ IF multiple elements display the same reader identity THEN read the value via JSX curly braces so that widgets can never drift out of sync.

❒ DOM Node Identity and Input Focus

➔ ALWAYS delegate DOM mutation to React's diffing engine to preserve living node identity, active text selections, and keyboard focus.

➔ NEVER use `innerHTML` to rebuild containers holding input fields because destroying living DOM elements wipes typed text and resets focus to the document body.

**DO THIS:** derive all interface markup from a single variable in memory
