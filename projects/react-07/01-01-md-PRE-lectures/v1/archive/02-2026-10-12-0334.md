### The lowercase tag creates an unknown element and leaves the card blank

- [p] ★ {preknowledge: HTML markup, JavaScript function declarations, camelCase naming conventions} In standard JavaScript, developers follow camelCase conventions for almost every identifier: helper functions are named `calculateTotal()`, variables are named `activeArticle`, and event handlers are named `handleClick()`. When starting out with React, developers naturally carry this muscle memory forward. You write a standard function named `articleCard()`, assemble headline and summary markup inside its body, and mount it in your layout as `<articleCard />`. The syntax looks clean, the code editor shows no red squiggles, and the terminal build finishes with zero errors. ◼ Educational objective: establish the familiar developer baseline and explain why muscle memory pushes developers toward camelCase.
- [p] ★ {problem: lowercase custom tags compile to native HTML string literals, causing silent render failures} When you refresh the browser page, the article card is completely missing. The terminal reports no errors, and the browser displays a blank white space. When you inspect the living page in browser Developer Tools, you find a bizarre custom tag: `<articlecard></articlecard>`. The browser treated your component tag as a native HTML element instead of executing your JavaScript function. Because the browser does not recognize this custom tag and your function was never invoked, the browser creates an empty unstyled DOM node, leaving the user with an empty screen. ◼ Educational objective: identify the silent failure mode of lowercase component tags in the DOM.
- [p] ★ {old solution: naive lowercase component declaration} To see this failure in concrete code, examine how a developer attempts to declare and mount an article card using standard JavaScript naming conventions:

- [code] Naive Lowercase Component Declaration (verified in React 19.3.0: creates empty DOM tag, skips function):

```jsx title="Naive Lowercase Component Declaration"
function articleCard() {
  return (
    <article className="article-card">
      <h2>Morning Dispatch</h2> {/* headline never renders */}
    </article>
  );
}
export default function App() {
  return <articleCard />; // compiles to native HTML string literal
}
```

◼ **The what-this-introduces list:** 1. `articleCard`: naive lowercase function declaration following standard JavaScript camelCase. 2. `<articleCard />`: lowercase JSX tag compiling to an HTML string literal. 3. Silent failure: complete bypass of the component function during render.

- [p] ★ {mechanism: the browser engine instantiates unknown HTML tags without executing the JavaScript function} When the browser encounters an unknown tag in markup, it does not throw an exception. The HTML specification dictates that unrecognized tag names instantiate a generic `HTMLUnknownElement` DOM node. Because the JSX compiler converted `<articleCard />` into a string literal request for an HTML element named `"articlecard"`, React instructed the browser to create that element directly. Your function `articleCard()` remained idle in JavaScript memory, completely untouched by React's rendering pipeline. ◼ Educational objective: deconstruct the browser HTML parser and DOM instantiation behavior for unrecognized tags.

### Passing a component tag hands React a function reference

- [p] ◇ {runway: component definition and module export} A React component is a regular JavaScript function that returns JSX markup describing a slice of the user interface. We use `export default` to mark the main component function of a file so that other files can import and reuse it. Unlike monolithic HTML files where markup and behavior live in separate documents, a component packages structure and presentation into a single cohesive unit. ◼ Educational objective: define the component function and establish the role of default module exports.
- [p] ★ {runway: function call against function reference} In standard JavaScript, when we want a function to run immediately, we write parentheses after its name, such as `ArticleCard()`. Calling a function evaluates its lines right away and produces its return value synchronously. In React, our code does not call component functions directly. When we write `<ArticleCard />` in markup, we do not call `ArticleCard()`. Instead, JSX passes the function itself, known as a function reference, to React. ◼ Educational objective: contrast synchronous function calls with passing function references.
- [p] ★ {runway: render phase orchestration} React takes custody of the function reference and enters its render phase. React decides when to call the component function based on what is happening in the application. When React renders the parent layout, it calls `ArticleCard`, inspects the JSX markup it returns, and builds the corresponding DOM elements on the screen. Because React orchestrates rendering, it can optimize screen updates, coordinate child lifecycles, and skip unnecessary work. ◼ Educational objective: explain how passing function references enables React to orchestrate rendering.

### Capital letters tell the compiler to build a component

- [p] ◇ {runway: native tags versus custom components} Browsers natively recognize a fixed catalog of HTML tags, such as `<article>`, `<h2>`, `<p>`, and `<button>`. A web application combines these native building blocks with custom components created by developers. When a compiler parses markup containing both native tags and custom components, it must determine whether each tag represents a built-in browser element or a JavaScript function. ◼ Educational objective: frame the compiler distinction between native browser tags and developer components.
- [p] ★ {runway: PascalCase convention and AST branching} React resolves this distinction using a strict casing rule: PascalCase. Under PascalCase, the first letter of each compound word is capitalized, such as `ArticleCard`. When the JSX compiler converts markup into JavaScript code, it checks the casing of the tag name. If the tag begins with a lowercase letter, the compiler emits a string literal: `_jsx("article")`. If the tag begins with an uppercase letter, the compiler emits an unquoted variable identifier: `_jsx(ArticleCard)`. ◼ Educational objective: explain the AST compiler branch that converts uppercase tags into function identifiers.
- [p] ★ {runway: development console warnings} If a developer accidentally names a component with a lowercase letter and mounts `<articleCard />`, the compiler treats it as a native HTML tag. React instructs the browser to create an element named `articlecard`, which the browser appends as an empty, unstyled DOM node. Because this is a frequent developer mistake, React prints two clear warning messages in the browser development console: one warning that the tag uses incorrect casing and should use PascalCase, and a second warning that the tag is unrecognized in the browser. ◼ Educational objective: describe the console feedback React provides when a component uses lowercase casing.

### JavaScript inserts semicolons after isolated return keywords

- [p] ★ {runway: automatic semicolon insertion} JavaScript includes a language mechanism called automatic semicolon insertion, or ASI. When the JavaScript parser reaches the end of a line, it checks whether the statement is complete. If the keyword `return` stands completely alone on its line, the parser treats the return statement as finished and automatically inserts an invisible semicolon immediately after it: `return;`. ◼ Educational objective: explain how automatic semicolon insertion affects isolated return statements.
- [p] ★ {runway: unreachable multi-line markup} If a developer writes `return` on one line and places multi-line JSX markup on the next line, the function immediately terminates and returns `undefined`. The JSX markup below the return statement is unreachable and never executes. React receives `undefined` for the component, paints nothing on the screen, and reports no error in the browser window. Bundlers such as esbuild emit a build warning alerting the developer that an expression is unreachable due to an automatically inserted semicolon. ◼ Educational objective: trace how ASI produces undefined return values and blank component output.
- [p] ◇ {runway: defensive parenthesized return wrapping} To prevent automatic semicolon insertion when returning multi-line markup, developers open a parenthesis `(` on the exact same line as the `return` keyword. The opening parenthesis signals to the ECMAScript parser that the return expression is incomplete and continues across multiple lines. The parser waits until it encounters the matching closing parenthesis `);` before ending the statement, allowing the complete JSX tree to evaluate reliably. ◼ Educational objective: teach parenthesized return syntax as the defensive defense against ASI.

### Defining a function inside another creates a new function on every run

- [p] ◇ {runway: nested functions in JavaScript} In JavaScript, developers frequently declare helper functions inside other functions. A function declared inside the body of an outer function is called a nested function. Every time the outer function executes, JavaScript creates and allocates a brand-new inner function in memory with a distinct object reference. ◼ Educational objective: ground the plain JavaScript mechanics of nested function allocation.
- [p] ★ {runway: the cost of nested component declarations} When a developer defines a React component inside the body of another component, this allocation becomes an architectural bug. Every time the outer component renders, it defines a completely new component function. When React compares the new render with the previous one, it sees a different function reference at that position in the tree. React concludes that the old component was removed and an entirely new component was mounted in its place. ◼ Educational objective: explain why nested component definitions change function identity on every render.
- [p] ★ {runway: DOM destruction and top-level declaration} Because React treats different component functions as completely different elements, it destroys the existing DOM subtree and constructs new DOM nodes from scratch. If the component contains an interactive `<input>`, any text the user typed is immediately destroyed, and keyboard cursor focus is lost. To preserve component identity across renders, developers define every component at the top level of the file, outside and alongside other components. ◼ Educational objective: prove why components must be declared at module top level to preserve living DOM nodes.

### Principles of React: Component Anatomy

- [p] ◇ When preparing for engineering interviews, candidates must explain the rules governing component anatomy, naming, and placement. In each question cycle below, the scenario starts with concrete code, the bold question names the beginner's doubt, the answer traces what React does, and the principle box turns that answer into an engineering rule. ◼ Educational objective: frame the upcoming question cycles and principle boxes.

- [question-cycle] Question 1: Writing a component does not run it until markup uses it
    - Question: "I wrote `function ArticleCard()`. Who calls it, and when?"
    - Code and result: `ArticleCard` with `console.log('ArticleCard runs')` in its body; when `App` omits the tag, the console is silent; when `App` renders `<ArticleCard />` twice, the console logs "ArticleCard runs" twice, and the page renders two articles (verified in React 19.3.0).
    - Verdict: works as React intended.
    - Answer: declaring a component function does not execute it; our code never calls `ArticleCard()`; instead, `App` returns markup containing `<ArticleCard />`; the tag hands React a function reference; while React renders `App`, it calls `ArticleCard`, reads the returned `<article>`, and inserts it into the DOM; if `<ArticleCard />` is written twice, React calls it twice; the browser DOM contains two `<article>` tags and zero `<ArticleCard>` tags.
    - Fix: none.
    - Rule: React calls our component function when another component's markup names it as a tag. Boundary: Calling a component function directly as plain JavaScript `{ArticleCard()}` bypasses element tracking, as explored in Lecture 37.
    - Needs: render phase (runway), function reference (runway), component definition (runway).
    - Diagram: markup tag handing function reference to React, which executes the function during render.

> [!PRINCIPLE]
> **Principle 1: React calls a component when markup names its tag**
> When we write a component, our code does not call its function. We write its name as a tag, such as `<Card />`, inside another component's markup. The tag hands React a reference to the function. While React renders the parent, it calls the component function and places the returned HTML elements into the DOM. The browser DOM shows the HTML tags the function returned, never the component tag.
>
> *We should do this:*
> `function App() {`
> `  return <Card />; // React calls Card when rendering App`
> `}`

- [p] ★ In our `ArticleCard` component, adding `console.log('ArticleCard runs')` proves who controls execution. When `App` returns an empty `<main>` container without `<ArticleCard />`, the function never runs, and the console stays silent. When `App` mounts `<ArticleCard />` twice, React evaluates `ArticleCard` twice, printing two log messages and placing two separate `<article>` elements into the DOM. In browser Developer Tools, the living tree displays two `<article>` nodes; the custom tag `<ArticleCard>` never exists in the browser DOM. ◼ Educational objective: prove Principle 1 on the lesson's code, showing how markup tags trigger component execution.

- [question-cycle] Question 2: A lowercase component tag leaves an empty element in the DOM
    - Question: "Does it matter whether I call it `articleCard` or `ArticleCard`?"
    - Code and result: `function articleCard()` mounted as `<articleCard />`; the build compiles cleanly, the DOM holds `<articlecard></articlecard>`, the headline never appears, and the development console logs two warnings about incorrect casing and an unrecognized tag (verified in React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: a tag that starts with a lowercase letter is treated as a native HTML element; the compiler emits a string literal `_jsx("articlecard")`, and React passes `'articlecard'` to `document.createElement`; the browser creates an empty `HTMLUnknownElement`; the function `articleCard()` is never invoked; React prints two warnings in the development console.
    - Fix: rename both the function and the tag to PascalCase starting with an uppercase letter: `function ArticleCard()` and `<ArticleCard />`. The uppercase initial letter tells the JSX compiler to emit an unquoted function identifier `_jsx(ArticleCard)`, allowing React to run the function.
    - Rule: start every component name with an uppercase letter in PascalCase. Boundary: native HTML elements must remain in lowercase so the browser recognizes standard tags.
    - Needs: PascalCase (runway), development console (runway), AST compiler branching (runway).
    - Diagram: compiler branching on casing: lowercase emitting string literal versus uppercase emitting function identifier.

> [!PRINCIPLE]
> **Principle 2: Start every component name with a capital letter**
> In JSX, the first letter of a tag tells the compiler what to create. A lowercase tag tells the compiler to request a native HTML element from the browser, so the function never runs and the browser creates an empty unknown element. A capitalized name in **PascalCase** tells the compiler to reference our function, allowing React to run it and put its markup on the screen.
>
> >> PascalCase : a naming convention where the first letter of each word is capitalized
>
> *We should do this:*
> `function Card() {`
> `  return <article>Content</article>;`
> `}`
> `<Card />; // React runs capitalized component function`
>
> *We should not do this:*
> `function card() {`
> `  return <article>Content</article>;`
> `}`
> `<card />; // lowercase tag creates empty HTML element`

- [p] ★ In `ArticleCard`, writing `function articleCard()` and rendering `<articleCard />` produced a silent failure on screen. The terminal reported no build errors, but the browser DOM contained an empty `<articlecard>` node with zero styles and zero child elements. Inspecting the browser console revealed two diagnostic warnings: one explaining that `<articleCard />` uses incorrect casing and should use PascalCase, and another noting that `<articleCard>` is unrecognized. Changing the name to `ArticleCard` in both the function declaration and the JSX tag allowed React to execute the function and display the headline and summary. ◼ Educational objective: prove Principle 2 on the lesson's code, demonstrating how PascalCase activates component execution.

- [question-cycle] Question 3: Starting markup on the line after return returns nothing
    - Question: "My markup is long. Can I start it on the line after `return`?"
    - Code and result: `return` placed alone on its line with `<article>` starting on the line below; the card renders completely blank with zero runtime errors on the page, and esbuild emits a build warning that the expression is not returned due to an automatically inserted semicolon (verified in React 19.3.0 and esbuild 0.28.2).
    - Verdict: does not do what the reader wanted.
    - Answer: JavaScript automatically inserts a semicolon after an isolated `return` keyword; the function terminates immediately and returns `undefined`; the multi-line markup on subsequent lines is never evaluated; React receives `undefined` and paints an empty slot without crashing.
    - Fix: open parentheses `(` on the same line as `return`, enclosing the multi-line markup inside `return (...)`. The opening parenthesis prevents automatic semicolon insertion and evaluates the entire JSX tree.
    - Rule: open parentheses on the same line as `return` whenever markup spans multiple lines. Boundary: single-line return expressions starting on the `return` line do not require parentheses.
    - Needs: automatic semicolon insertion (runway), parenthesized return expressions (runway).
    - Diagram: isolated return triggering automatic semicolon insertion versus opening parenthesis extending the expression.

> [!PRINCIPLE]
> **Principle 3: Open parentheses on the same line as return for multi-line markup**
> When the `return` keyword stands alone on its line, JavaScript automatically inserts a semicolon after it. The function returns `undefined`, ignoring any markup written on following lines and leaving the screen completely blank. To return multi-line markup, open a parenthesis on the same line as `return` so JavaScript knows the expression continues.
>
> >> automatic semicolon insertion : JavaScript inserting a semicolon after an isolated return keyword
>
> *We should do this:*
> `return (`
> `  <article>Content</article> {/* evaluated as return expression */}`
> `);`
>
> *We should not do this:*
> `return // semicolon inserted here, returns undefined`
> `  <article>Content</article>; // unreachable code never evaluated`

- [p] ★ In `ArticleCard`, formatting the component with `return` on line 2 and `<article>` on line 3 triggered automatic semicolon insertion. The JavaScript runtime inserted a semicolon after `return;`, causing `ArticleCard` to return `undefined` immediately. In the browser, the article card disappeared with zero console errors, while the terminal build warned that the following expression was unreachable. Adding opening and closing parentheses around the markup connected the return statement across lines, restoring the article card to the browser view. ◼ Educational objective: prove Principle 3 on the lesson's code, showing how parenthesized returns defeat ASI bugs.

- [question-cycle] Question 4: Defining a component inside another component recreates it on every render
    - Question: "`ArticleCard` is only used inside `App`. Can I define it inside `App`?"
    - Code and result: `function ArticleCard()` defined inside `function App()`; on initial mount the card renders normally; on a second render of `App`, an `<input>` inside the card is recreated as a new element and its typed text is wiped out (verified in React 19.3.0 with re-render).
    - Verdict: does not do what the reader wanted.
    - Answer: defining a component inside another creates a new function in memory on every render of the parent; React sees a different component function at that position in the tree; React destroys the existing DOM subtree and constructs brand-new elements; any living DOM state, such as typed input text or cursor focus, is immediately wiped out.
    - Fix: declare `function ArticleCard()` at the top level of the module file, outside and alongside `function App()`. When declared at the top level, the function retains a single stable identity across all renders of `App`.
    - Rule: define every component at the top level of the file, never inside another component. Boundary: passing props down from parent to child handles data sharing without nesting function definitions (explored in Lecture 6).
    - Needs: nested functions (runway), component identity across renders (runway).
    - Diagram: nested definition allocating new function pointers on each render versus top-level definition preserving stable function identity.

> [!PRINCIPLE]
> **Principle 4: Define every component at the top level of the file**
> Defining a component inside another component creates a new function object every time the outer component runs. Because React sees a different component type on every render, it destroys the existing DOM elements and builds new ones from scratch, wiping out typed input text and resetting focus. Always declare components at the top level of the file so their identity remains stable.
>
> >> nested function : a function defined inside the body of another function
>
> *We should do this:*
> `function Child() {`
> `  return <p>Content</p>; // stable function identity`
> `}`
> `function Parent() {`
> `  return <Child />; // reuses existing DOM across renders`
> `}`
>
> *We should not do this:*
> `function Parent() {`
> `  function Child() { return <p>Content</p>; } // recreated every run`
> `  return <Child />; // React destroys and rebuilds DOM`
> `}`

- [p] ★ When `ArticleCard` was defined inside `App`, the initial mount looked identical to a top-level component. But when `App` rendered a second time, React evaluated `App` from the top, allocating a fresh `ArticleCard` function in memory. React compared the previous element descriptor with the new one and observed two different function references. React concluded that a different component type had replaced the old one, destroying the existing `<article>` node and constructing a new one. Moving `ArticleCard` to the top level gave the component a permanent function identity, allowing React to update the DOM surgically without rebuilding elements. ◼ Educational objective: prove Principle 4 on the lesson's code, showing how top-level declarations preserve DOM identity.

### Step 1: First, we construct the article card component <ArticleCard.jsx>

- [p] ★ We construct the standalone article card component `ArticleCard.jsx` to package headline and summary markup into an isolated, reusable function. Notice that the function name begins with an uppercase letter: `ArticleCard`. This PascalCase naming guarantees that the JSX compiler treats `<ArticleCard />` as a custom component rather than an unknown HTML tag. The component function contains no hardcoded DOM queries, mutates no external variables, and returns semantic HTML elements wrapped in a single root `<article>` tag. ◼ Meaningful pedagogical commentary: component function anatomy, PascalCase compiler contract, single root container encapsulation.
- [p] ◇ When returning multi-line JSX markup from a component function, you encounter a foundational JavaScript syntax crossroad:
  - **Option 1 (The Foundational Way)**: Write a naked multi-line return without wrapping parentheses, exposing the code to automatic semicolon insertion.
  - **Option 2 (The Modern Idiomatic Way)**: Wrap the multi-line JSX expression in parentheses, signaling to the parser that the return expression continues across lines.
- [code] Option 1: The Foundational Way (Naked Multi-Line Return):

```jsx title="Option 1: The Foundational Way (Naked Multi-Line Return)"
export default function ArticleCard() {
  return // parser automatically inserts semicolon here
    <article className="article-card">
      <h2>Morning Dispatch</h2> {/* unreachable code never evaluated */}
    </article>;
}
```

- [p] ★ In Option 1, the JavaScript engine encounters a newline immediately after the `return` keyword. Under the rules of automatic semicolon insertion, the parser inserts a semicolon after `return;`. The function immediately terminates and returns `undefined`. The JSX markup on the following line is never evaluated, and the browser displays a blank card with zero errors. ◼ Educational objective: explain the mechanical failure mode of automatic semicolon insertion on naked multi-line return statements.
- [code] ArticleCard.jsx:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() {
  return ( // parentheses prevent automatic semicolon insertion
    <article className="article-card">
      <h2 className="headline">Morning Dispatch</h2> {/* story headline text */}
      <p className="summary">Local civic updates.</p> {/* descriptive summary text */}
    </article>
  );
}
```

- [p] ★ In Option 2, the opening parenthesis `(` tells the ECMAScript parser that the return expression continues across multiple lines. Semicolon insertion is prevented, and the component function reliably evaluates the entire JSX tree. Notice how `ArticleCard.jsx` functions as a pure presentation component: it owns zero state, requires no external DOM lookups, and cleanly packages the news card into a predictable, reusable unit. ◼ Meaningful pedagogical commentary: parenthesized return protection, pure presentation contract, satisfying single root invariant.

◼ **The what-this-introduces list:** 1. `ArticleCard`: the standalone custom component function. 2. PascalCase identifier: uppercase naming signaling custom component to JSX compiler. 3. Parenthesized JSX return: defensive multi-line expression wrapping.

### Step 2: Finally, we mount the card declaratively inside <App.jsx>

- [p] ★ To complete our application layout, we mount `ArticleCard.jsx` inside the root container `App.jsx`. In standard JavaScript development, inserting a new widget required querying an existing container with `document.querySelector` and appending elements imperatively. In React, the entire document organizes into a declarative hierarchy. Notice that `App.jsx` imports `ArticleCard` as an unquoted JavaScript identifier and mounts it using the self-closing tag `<ArticleCard />`. We do not call `ArticleCard()` directly with parentheses; writing `<ArticleCard />` tells React's mounting engine to register an independent element in the render tree and execute the component during the render pass. ◼ Meaningful pedagogical commentary: declarative mounting, unquoted identifier import, element registration.

- [code] App.jsx:

```jsx title="App.jsx"
import ArticleCard from './components/ArticleCard.jsx'; // imports component function

export default function App() {
  return (
    <main className="app-shell">
      <ArticleCard /> {/* mounts component declaratively as tag */}
    </main>
  );
}
```

- [p] ★ When React evaluates `App`, the JSX compiler transforms `<ArticleCard />` into `_jsx(ArticleCard, {})`. React attaches the component to its virtual tree, executes `ArticleCard()` in memory, and paints the returned `<article>` node inside `<main>` in a single atomic operation. Because the component follows PascalCase naming and declarative invocation, the browser receives living, semantic DOM elements without manual query scripts or silent lowercase failures. ◼ Meaningful pedagogical commentary: AST transformation to _jsx function identifier, atomic mounting, complete component tree resolution.

◼ **The what-this-introduces list:** 1. `App`: the top-level application root container. 2. Component import: importing `ArticleCard` as an unquoted identifier. 3. Declarative JSX mount: `<ArticleCard />` tag creating a managed element.

A junior candidate answers that capitalization is just an aesthetic style convention. A senior engineer explains that the JSX compiler branches on Unicode casing: lowercase tags compile to string literals for native elements, while uppercase tags compile to unquoted function references that React invokes during render.
- [interview] 2. The Classic Trap ◼ The classic trap is claiming that you can call component functions directly inside curly braces `{ArticleCard()}` to save typing. While executing the function returns markup in simple examples, calling a component directly strips its component boundary, inlining child markup into the parent and breaking React's ability to isolate updates or manage Hooks. Another frequent trap is defining helper components inside parent render functions, which causes React to destroy and rebuild DOM trees on every render pass.
- [interview] 3. What is Actually Going On ◼ A React component is a standard JavaScript function that returns JSX markup. We never invoke it directly; we write it as a tag, like `<ArticleCard />`, inside another component. That tag passes a function reference to React. When React renders the parent, it executes the function and commits the resulting elements to the DOM. Four concrete rules govern component authoring: (1) start names with a capital letter in PascalCase so the compiler emits function references, (2) open parentheses on the same line as return so automatic semicolon insertion does not return undefined, (3) declare components at module top level so function identity remains stable across renders, and (4) return a valid single root element or Fragment.
- [interview] 4. Where It Gets Tricky ◼ Where this gets tricky in production is diagnosing subtle silent bugs. A lowercase tag compiles cleanly without terminal syntax errors; the only clues are an empty custom tag in DevTools and two development console warnings. Similarly, an unparenthesized multi-line return renders a blank component without throwing a browser runtime error, though modern bundlers emit build warnings. Finally, defining components inside parent render functions works deceptively on initial mount, only to destroy user input text and reset focus rings the moment parent state triggers a second render.

### Glossary

- [glossary] Component ◼ A self-contained JavaScript function whose name starts with a capital letter and returns a description of user interface markup in JSX.
- [glossary] PascalCase ◼ A naming convention where the first letter of each compound word is capitalized, used by the JSX compiler to distinguish custom component functions from native HTML elements.
- [glossary] Function Reference ◼ An unquoted reference to a JavaScript function in memory, passed to React so the runtime can execute the function during render.
- [glossary] Automatic Semicolon Insertion ◼ A JavaScript language feature that inserts an invisible semicolon after an isolated return keyword, causing functions to return undefined if markup starts on the next line.
- [glossary] Nested Component ◼ A component function defined inside the body of another component, causing React to treat it as a brand-new component type and rebuild its DOM on every render.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Component Naming and Compiler Casing

➔ ALWAYS name custom components in PascalCase so the JSX compiler emits an unquoted function identifier rather than an HTML string literal.

➔ NEVER define component functions in lowercase or camelCase because the browser treats lowercase tags as native elements and fails silently.

❒ Return Statement Layout

➔ ALWAYS wrap multi-line JSX return statements in parentheses with the opening parenthesis on the same line as the return keyword.

➔ NEVER place multi-line JSX markup on the line after return without an opening parenthesis because automatic semicolon insertion will return undefined.

❒ Component Declaration Scope

➔ ALWAYS declare component functions at the top level of the file so their function identity remains stable across renders.

➔ NEVER define component functions inside the body of another component because React will destroy and reconstruct its DOM elements on every render.

**DO THIS:** name custom components in PascalCase, open parentheses on the return line, and declare at module top level

```jsx right
function ArticleCard() {
  return (
    <article className="article-card">
      <h2>Morning Dispatch</h2>
    </article>
  );
}
export default function App() {
  return <ArticleCard />;
}
```

**DO NOT DO THIS:** name components in lowercase, place markup below bare return, or nest component definitions

```jsx wrong
export default function App() {
  function articleCard() {
    return
      <article className="article-card">
        <h2>Morning Dispatch</h2>
      </article>;
  }
  return <articleCard />;
}
```
