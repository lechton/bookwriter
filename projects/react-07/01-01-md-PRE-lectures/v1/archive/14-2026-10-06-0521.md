### The Friction of Ephemeral Local Variables

- [p] ★ {preknowledge: function components, pure render calculations, JSX return markup, event handlers} In earlier lessons, you learned that React components are functions that run to compute JSX markup from incoming props (see Lecture 2 and Lecture 6). When users interact with the page, event handlers fire to perform actions outside the render pass (see Lecture 13). However, modern web applications must not only respond to clicks; they must also remember what the user did. When an engineer needs to track an interactive counter, such as an article reaction tally or a bookmark toggle, the natural instinct from traditional scripting is to declare a local variable: `let likes = 0`. Inside the click handler, the engineer writes `likes = likes + 1`, expecting the updated count to appear on screen. But when the user clicks the button, the rendered text remains frozen at its initial value, even while `console.log` proves the variable is incrementing in memory. ◼ Educational objective: recall pure component execution and event handling while identifying the core friction where local variable increments fail to update the rendered screen.
- [p] ★ {problem: local variables vanish on return and changes never trigger re-renders} It is possible that a developer may assume a component function behaves like a persistent class instance or a living database that maintains its local variables across time. In reality, JavaScript functions are ephemeral: their local variables are allocated on the call stack when invoked and discarded the moment the function returns. A local variable declared as `let likes = 0` exists only for that single call. When a user clicks a button and triggers an event handler that increments `likes`, two fatal disconnects occur. First, changing a local variable does not notify React that anything happened, so React schedules no re-render and the browser never redraws. Second, whenever the component does re-render (because an ancestor updated or another component triggered a change), React executes the component function from the very first line, resetting `likes` back to `0`. ◼ Educational objective: analyze the dual runtime failure where local variables discard their values between calls and local mutations fail to trigger re-renders.
- [p] ★ {old solution: imperative DOM element mutation or global window storage} In legacy JavaScript scripting, developers bypassed function scopes by storing counts on global objects like `window.likes` or by directly mutating DOM text nodes with `document.getElementById('likes-count').textContent = likes`. In React, mutating external variables breaks component purity (see Lecture 12), and directly touching the DOM bypasses virtual DOM reconciliation (see Lecture 1). React components must remain pure projections of data, which means persistent interactive memory requires a dedicated framework mechanism that preserves values across calls and tells React when to redraw the screen. ◼ Educational objective: contrast fragile imperative DOM mutation and global variable leakage with declarative state management.

- [code] Naive Local Variable Increment Attempt:

```jsx title="Naive Local Variable Attempt"
export default function StoryCard() {
  let likes = 0; // Local variable allocated on each call
  function handleLike() {
    likes = likes + 1; // Modifies local variable in memory
    console.log('Likes:', likes); // Prints incremented number
  }
  return (
    <button type="button" onClick={handleLike}>Likes ({likes})</button>
  );
}
```

◼ **The what-this-introduces list:** 1. `let likes = 0`: ephemeral local variable created fresh on every function execution. 2. `handleLike`: click handler mutating a local variable without notifying React. 3. `<button ...>`: interactive button displaying a frozen count that never updates on screen.

- [p] ★ {mechanism: useState hook provides persistent memory and re-render triggers} React resolves both limitations through the `useState` hook. When you write `const [likes, setLikes] = useState(0)`, you request two linked capabilities from React: a state variable that retains its value across renders, and a state setter function that updates the value and schedules React to re-render the component. Unlike local variables, state does not live inside the component function scope; React stores the state value externally in an internal memory record tied to the component instance in the UI tree. When `setLikes(likes + 1)` is called, React updates the stored value and schedules a new render pass. During that next render pass, React invokes the component function again, but instead of using the initial argument `0`, `useState` hands back the updated value. The component returns fresh JSX reflecting the new count, and React reconciles the browser DOM accordingly. ◼ Educational objective: establish the dual mechanism of useState as external persistent storage and a trigger for scheduled re-renders.

### Component Execution and the Need for Persistent Memory

- [p] ◇ {conceptual grounding: function components as repeated executions} To understand why React needs `useState`, we must examine what happens when a function component renders. In standard JavaScript, calling a function creates a fresh execution context: local variables are allocated, code runs line by line, the return value is handed to the caller, and the stack frame is cleaned up. A React component is invoked not once, but repeatedly throughout the lifecycle of an application. Every time data changes or a parent updates, React calls the component function again to compute a fresh tree of UI descriptors. Because every render is a brand-new function call, any variable declared with `let` or `const` inside the component body is re-created from scratch.
- [p] ★ {runtime architecture: React state shelf outside function execution} If local variables are discarded on every render, where does state actually live? React stores component state outside the component function, in an internal memory cell associated with that component's position in the UI tree. You can picture this as a shelf of memory slots maintained by React in the background. When your component function runs, calling `useState` reaches out to React's internal shelf and asks for the current value assigned to this specific slot. On the very first render (the initial mount), React initializes the slot with the argument you passed (`0`). On all subsequent renders, React ignores that initial argument and hands back whatever value is currently stored in the slot.
- [p] ★ {syntactic deconstruction: array destructuring of value and setter} The `useState` hook returns a JavaScript array containing exactly two items, which developers unpack using **array destructuring**: `const [likes, setLikes] = useState(0)`. The first element (`likes`) is the current state value for this render pass; it is treated as a read-only constant during the execution of the component. The second element (`setLikes`) is a setter function that allows you to change the state. When you invoke `setLikes(nextValue)`, React updates the value stored on its internal shelf and queues a re-render for this component instance.
- [p] ★ {behavioral invariant: state persistence across renders versus page reloads} It is critical to distinguish between re-renders and page reloads. A re-render occurs within the living JavaScript application: React re-executes the component function in memory, preserves internal state cells, and updates only the changed DOM nodes. In contrast, a full browser page reload (or navigation) destroys the entire JavaScript runtime environment, clearing all memory cells and resetting all components back to their initial state. `useState` provides persistent memory across renders within a living session, not persistent storage across browser restarts.

> [!PRINCIPLE]
> **Principle 1: Expect a Local Variable to Forget and to Change Nothing on Screen**
> An ordinary local variable belongs exclusively to a single function execution. When we modify a local variable inside an event handler, React receives zero notification that data changed and schedules no update, leaving the screen unchanged. Whenever the component renders again, the function executes from the top and resets the local variable to its initial starting value.
> 
> >> ephemeral variable : a local variable created inside a function that disappears when execution finishes
> >> render pass : a single complete call of a component function to calculate its return markup

- [p] ★ Principle 1 operational derivation: When a component renders, JavaScript executes the function body from the top down. Declaring `let likes = 0` allocates a slot on the call stack for that invocation only. If an event handler reassigns `likes = likes + 1`, the change takes place purely within that closure's local scope. React has no knowledge that a JavaScript variable was modified because variables do not dispatch notifications. Furthermore, when an unrelated event (such as a parent re-render or timer) prompts React to redraw the component, React invokes the function again. That new call allocates a brand-new `likes` variable initialized to `0`. A local variable is completely ephemeral: it cannot persist data between calls, and modifying it cannot update the browser screen. ◼ Educational objective: derive why local variables are discarded on each render pass and why variable mutation fails to trigger DOM reconciliation.

    - Step 5, the technical words: `state variable` (new and needed: a persistent value preserved by React across renders), `transient calculation` (new and needed: an intermediate value computed and discarded within a single handler run).

> [!PRINCIPLE]
> **Principle 2: Store in State Exactly What Must Survive a Re-Render**
> We store in state only data that must survive between renders and directly affects what the component displays on screen. Values calculated and consumed entirely inside a single event handler, such as a formatted sharing link or temporary math result, belong in ordinary local variables because every state setter call requests a full re-render.
> 
> >> state variable : a persistent value preserved by React across component function executions
> >> transient calculation : an intermediate value computed and discarded within a single handler run
> 
> *It is best practice to do this:*
> `const [likes, setLikes] = useState(0); // State preserves counter`
> `const shareUrl = `/stories/${id}`; // Local transient calculation`
> 
> *Instead of doing this:*
> `const [shareUrl, setShareUrl] = useState(''); // Redundant state`

- [p] ★ Principle 2 operational derivation: Novice engineers often swing between two extremes: using zero state (leaving the UI unresponsive) or placing every variable into `useState`. Every call to a state setter instructs React to schedule a re-render of the component and its children. If an event handler formats a string to send to an analytics server or calculates a temporary URL for clipboard copying, that value does not need to survive beyond the handler's execution, nor does it alter the JSX structure. Storing transient calculations in state forces React to re-render the component tree unnecessarily, wasting CPU cycles and introducing subtle race conditions. We reserve state strictly for values that the component must remember across renders to decide what to paint on screen. ◼ Educational objective: analyze the boundary between persistent UI state and transient handler calculations to prevent unnecessary re-renders.

- [code] State vs Local Variable:

```jsx title="State vs Local Variable"
import { useState } from 'react';
export default function ArticleCard({ id }) {
  const [likes, setLikes] = useState(0); // State preserves counter
  function handleShare() {
    const shareUrl = `/stories/${id}`; // Transient calculation
    navigator.clipboard.writeText(shareUrl); // Copies url to clipboard
  }
  return <button onClick={() => setLikes(likes + 1)}>Likes ({likes})</button>;
}
```

> **Principle 3: Expect React to Hand Back the Stored Value on Every Render**
> React stores component state outside our function in an internal memory cell tied to the component's position in the UI tree. On the initial render, `useState(initialValue)` registers the initial value in that cell and returns it. On every subsequent render, React ignores the initial argument and returns the latest value from its internal cell.
> 
> >> initial render : the first time React calls a component function to create and insert its DOM nodes
> >> internal state cell : an isolated memory record kept by React outside the component function

- [p] ★ Principle 3 operational derivation: When beginners look at `const [likes, setLikes] = useState(0)`, they frequently wonder: "If the component executes again, why doesn't `useState(0)` reset `likes` to `0` every single time?" The answer lies in how React tracks hook execution. State does not reside within the function scope; it resides on an internal Fiber record that React preserves between calls. When React renders a component for the first time, it creates an internal state cell and initializes it with the argument `0`. On all subsequent renders, React recognizes that a state cell already exists for this hook call. It ignores the argument `0` entirely and retrieves the latest value stored in that cell. The initial argument acts strictly as a one-time seed value during initial mounting. ◼ Educational objective: derive how React ignores the initial state argument on subsequent renders and retrieves stored data from internal Fiber cells.

> **Principle 4: Change State Only by Calling Its Setter**
> The state variable returned by `useState` is a read-only snapshot for the current render. We never assign a new value directly to the state variable. Calling the setter function (`setLikes`) is the only way to update React's internal state cell and schedule a fresh render to redraw the screen.
> 
> >> state setter : the update function returned by useState that requests a new render with a new value
> >> direct mutation : attempting to reassign or modify a state variable in place without using its setter
> 
> *We should do this:*
> `setLikes(likes + 1); // Updates React memory and schedules re-render`
> 
> *We should not do this:*
> `likes = likes + 1; // Throws TypeError on const or fails to update UI`

- [p] ★ Principle 4 operational derivation: In React, state variables are meant to be treated as immutable snapshots of data for the current execution frame. When you destructure `const [likes, setLikes] = useState(0)`, declaring `likes` as a `const` enforces this contract at the JavaScript language level: writing `likes = likes + 1` immediately crashes with `TypeError: Assignment to constant variable`. Even if you deliberately declared it with `let [likes, setLikes]`, assigning to `likes` changes only a local identifier in that single closure. React is not a proxy engine; it does not intercept assignments to local variables. The setter function (`setLikes`) is the sole communication mechanism provided by React to record a new state value and place this component into the re-render queue. ◼ Educational objective: demonstrate why direct variable assignment fails to trigger updates and why invoking the setter function is required.

> State belongs to a specific rendered instance of a component on screen, not to the component function or its source file. If we render `<StoryCard />` three times, React creates three separate state cells in memory. > >> component instance : a distinct mounted occurrence of a component placed in the UI tree
> >> isolated state : private memory allocated to one component instance that siblings cannot see

- [p] ★ Principle 5 operational derivation: In object-oriented programming, a class definition is separate from its instantiated objects; similarly, in React, a component definition is separate from its mounted component instances. If you define a `StoryCard` component that holds `const [likes, setLikes] = useState(0)` and render `<StoryCard />` twice inside `App.jsx`, React tracks each card by its unique location in the UI tree. It creates two completely independent state cells in memory. Clicking "Like" on the first card invokes the first card's setter, incrementing its internal cell to `1` and scheduling a re-render strictly for that first card. The second card remains at `0`, and its function does not even run. Furthermore, state is completely private: `App` cannot read or modify the `likes` state of either child card. If two sibling cards ever need to share a synchronized count, that state must be lifted into their common parent (a pattern explored in Lecture 23). ◼ Educational objective: establish state isolation across component instances and preview lifting state when shared synchronization is required.

> [!PRINCIPLE]
> **Principle 6: Call Setters from Handlers, Never Unconditionally During Render**
> A state setter requests a new render, so we must invoke setters exclusively inside event handlers when a user interacts with the page. Calling a setter directly in the component body or invoking it inside JSX curly braces runs the setter during render, causing React to abort with a fatal "Too many re-renders" infinite loop error.
> 
> >> infinite render loop : a crash where setting state during render immediately triggers another render
> 
> *We should do this:*
> `<button onClick={() => setLikes(likes + 1)}> // Defers setter to click`
> `  Like`
> `</button>`
>

> `<button onClick={setLikes(likes + 1)}> // Invokes setter during render`

- [p] ★ Principle 6 operational derivation: In Lecture 13, you learned that expressions inside JSX curly braces evaluate immediately during the render pass. If you write `onClick={setLikes(likes + 1)}`, JavaScript calls `setLikes` right away while constructing the element tree. Calling a setter instructs React to schedule a new render. React attempts to render the component again, but during that second render, JavaScript encounters `onClick={setLikes(likes + 1)}` again, calling the setter once more. This creates an unconstrained recursive loop: render calls setter, setter calls render. To prevent the browser tab from freezing completely, React halts execution and throws an unrecoverable runtime crash: `Error: Too many re-renders. React limits the number of renders to prevent an infinite loop.` To prevent this failure, always wrap parameterized setter calls in an arrow function (`onClick={() => setLikes(likes + 1)}`), ensuring the setter executes strictly when the user physically clicks. ◼ Educational objective: analyze the operational failure of calling state setters during render and demonstrate how arrow functions guarantee deferred execution.

- [p] ★ {step 3: leaf reaction button maintains isolated numeric upvote state} In `src/components/ReactionButton.jsx`, we build the terminal reaction button. ### Glossary

- **Component State** ◼ Persistent memory maintained by React across render passes that stores data affecting what appears on the screen.
- **State Setter Function** ◼ The updater function returned by `useState` that updates React's internal state record and schedules a component re-render.
- **Render Pass** ◼ A single complete execution of a component function by React to calculate its tree of UI descriptors.
- **Internal State Cell** ◼ An isolated data structure maintained by React outside the component function, mapped to the component's position in the UI tree.
- **Infinite Render Loop** ◼ A runtime crash caused by invoking a state setter unconditionally during the render pass, repeatedly triggering new renders without stopping.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Ephemeral Variables vs Persistent State

➔ ALWAYS use `useState` for data that must survive between renders and directly affects the user interface.

➔ NEVER rely on local variables (`let count = 0`) to track data across user interactions.

**DO THIS:** Store interactive data in React state

```jsx right
function LikeButton() {
  const [likes, setLikes] = useState(0);
  return <button onClick={() => setLikes(likes + 1)}>Likes: {likes}</button>;
}
```

**DO NOT DO THIS:** Increment local variables inside click handlers

```jsx wrong
function LikeButton() {
  let likes = 0;
  return <button onClick={() => { likes = likes + 1; }}>Likes: {likes}</button>;
}
```

❒ State Modification and Setters

➔ ALWAYS call the state setter function (`setCount`) to update state and schedule a re-render.

➔ NEVER mutate a state variable directly (`count = count + 1`).

**DO THIS:** Pass the next value to the setter function

```jsx right
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Next</button>;
}
```

**DO NOT DO THIS:** Directly reassign the state variable

```jsx wrong
function Counter() {
  let [count, setCount] = useState(0);
  return <button onClick={() => { count = count + 1; }}>Next</button>;
}
```

❒ Execution Timing and Infinite Loops

➔ ALWAYS invoke state setters inside event handlers or delayed callback wrappers.

➔ NEVER invoke a state setter directly during the render pass or in naked JSX braces.

**DO THIS:** Wrap parameterized setter calls in an arrow function

```jsx right
function UpvoteAction({ onUpvote }) {
  return <button onClick={() => onUpvote(1)}>Upvote</button>;
}
```

**DO NOT DO THIS:** Call the setter immediately in JSX curly braces

```jsx wrong
function UpvoteAction({ onUpvote }) {
  return <button onClick={onUpvote(1)}>Upvote</button>;
}
```

| | **EPHEMERAL LOCAL VARIABLE**<br>(Naive Function Scope) | **REACT USESTATE MEMORY**<br>(Persistent State Engine) |
| ---: | :--- | :--- |
| **Storage Location** | Allocated on temporary JavaScript call stack frame | Maintained externally in React internal Fiber state cells |
| **Render Persistence** | Discarded on return; reset to initial value on each call | Preserved across render passes for the lifetime of component |
| **Re-render Trigger** | None: React is unaware that local variables changed | Setter call queues a re-render and updates browser DOM |
| **Update Mechanism** | Direct assignment (`count = count + 1`) | Invoking setter function (`setCount(count + 1)`) |
| **Instance Isolation** | Scoped to individual function call execution | Private to specific component instance in UI tree |
| **Initial Value Role** | Evaluated on every call, repeatedly resetting value | Used once on initial mount; ignored on later renders |
