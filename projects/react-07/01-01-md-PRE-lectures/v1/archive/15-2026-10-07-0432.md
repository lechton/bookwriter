### Three Steps Behind Every Screen Update

- [p] ◇ {native default: plain DOM code} In plain JavaScript, `element.textContent = 1` changes the page on that line, and the next line reads `1`. React splits the work into three steps, which the React docs call trigger, render, and commit. ◼ Educational objective: name the three steps from the reader's known habit.

- [p] ◇ {trigger} A **trigger** asks React for a render. There are two: the first `root.render(<App />)` call in `main.jsx` (Lecture 9), and a setter call (Lecture 14). ◼ Educational objective: Prerequisite Q09 and Q14 as one-line recalls; Merged row "two triggers".

- [code] main.jsx: `createRoot(document.getElementById('root'))` and `root.render(<App />); // the first trigger`. ◼ **The what-this-introduces list:** nothing new; recalled from Lecture 9.

- [p] ◇ {render} Lecture 14 called each run of a component a **render**. Rendering means React calls our component functions to get their JSX. On the first render React calls the root component and then each component it returns. Nothing on the page changes during a render. Because a render only calculates, it must be pure, as Lecture 12 taught. ◼ Educational objective: Recall Q02/Q14 "render", Prerequisite Q12 purity in one sentence.

- [p] {StrictMode note} The console lines in this lesson come from a project without `StrictMode`. A new Vite project turns it on, and then each `runs` line prints twice in development. Lecture 46 explains why. ◼ Educational objective: Preview Q46 in one sentence, and an honest note so the reader's console matches.

- [p] ★ {commit and DOM node} Every element and every piece of text on the page is a **DOM node**, an object the browser keeps for it. In the **commit**, React changes the DOM nodes. On the first render it creates them all and adds them with `appendChild()`, which replaces whatever the root element held, such as a `Loading...` text. On later renders it changes only what differs. ◼ Educational objective: New terms DOM node and commit; Supporting rows `appendChild()` and "first render clears the container".

- [p] ◇ {paint} After the commit, the browser draws the new page on the screen. The browser calls this drawing "rendering" too, so the React docs call it **painting** to keep the two apart. ◼ Educational objective: render against paint, from card Under the Hood.

### Principles of React: Trigger, Render, and Commit

- [p] ◇ An interviewer who asks this question wants each step and what runs in it. The first principle covers the render. The second covers which components a render calls. The third covers the commit. The last is the decision Leo needs in his handler. ◼ Educational objective: map order `render-is-a-call`, `update-renders-below`, `commit-only-differences`, `dom-after-handler`.

- [principle-notes] Principle 1: The reader knows from Lecture 14 that React runs the component, and believes "render" means drawing on the page (the browser's word). Basics first: a component is a function that returns JSX, and a render is React calling it. Then what happens: the page does not change until the commit, after the function returns. The proof: the body log reads `likes = 1 | page shows 0`, and on the first render finds no `<p>` yet. Code pair: reading the number from state against reading it from the page, where the first render throws because there is no `<p>`. Moves from casebook Cases 1 and 2.

> [!PRINCIPLE]
> **Principle 1: A Render Is React Calling the Component, and the Page Stays as It Was**
> A component is a function that returns JSX. To render a component, React calls that function and takes the JSX it returns. That is the whole render. The page on the screen does not change during it. React changes the page in the next step, the commit, after the function has returned. So code inside the component that reads the page finds the old page. On the first render there is no `<p>` yet. In the render where `count` is 1, the page still shows 0.
>
> *We should do this:*
> `function Counter() {`
> `  const [count, setCount] = useState(0);`
> `  return <p>{count}</p>; // the value of this render`
> `}`
>
> *We should not do this:*
> `function Counter() {`
> `  const [count, setCount] = useState(0);`
> `  const p = document.querySelector('p'); // null on the first render`
> `  return <p>{p.textContent}</p>; // TypeError, nothing appears`
> `}`

- [code] LikeCounter.jsx, looking at the page during a render: `const shown = document.querySelector('.like-count'); // the page right now`, `const pageText = shown ? shown.textContent : 'nothing yet';`, `console.log('likes =', likes, '| page shows', pageText);`. ◼ **The what-this-introduces list:** 1. the ternary from Lecture 4 guards the first render, when there is no `<p>` yet.

- [p] ★ Verified output: the first render prints `likes = 0 | page shows nothing yet`. A click prints `likes = 1 | page shows 0`, and then the page shows `1`. The component's whole run happened before the page changed. ◼ Educational objective: the paragraph under the box shows the rule on Leo's card with real values.

- [principle-notes] Principle 2: The reader believes a change runs the whole app again, from page reloads and from the first `root.render(<App />)`. Basics first: components return components and form a tree (Lecture 5). Then the order: first render from `App` down; a setter renders its own component and everything below it. The proof: `App runs`, `StoryTitle runs`, `LikeCounter runs`, `LikeLabel runs` on the first render; a click prints only `LikeCounter runs` and `LikeLabel runs`. Code pair: state in the component that shows it, against the same state in the page, where a setter call runs the page and its title too; both run, so "best practice". Moves from Cases 2 and 5.

> [!PRINCIPLE]
> **Principle 2: A State Change Renders Its Own Component and Everything Inside It**
> Components return other components, so together they form a tree, with `App` at the top. On the first render, React calls `App` and then every component below it. After that, a setter asks for a render of its own component. React calls that component again, then each component it returns, and so on to the bottom of the tree. We might expect a change to run the whole app again, as a page reload does. It does not. The parent and the components beside it do not run again.
>
> *It is best practice to do this:*
> `function Counter() {`
> `  const [count, setCount] = useState(0); // setCount runs Counter`
> `  return <p>{count}</p>;`
> `}`
>
> *Instead of doing this:*
> `function Page() {`
> `  const [count, setCount] = useState(0); // setCount runs Page`
> `  return <main><Title /><p>{count}</p></main>; // and Title`
> `}`

- [code] The page, with a log in every component: `StoryTitle` returns the headline `<h1>` and logs `StoryTitle runs`; `App` logs `App runs` and returns `<main><StoryTitle /><LikeCounter /></main>`; `LikeCounter` returns `<LikeLabel count={likes} />`, which logs `LikeLabel runs`. ◼ **The what-this-introduces list:** 1. `StoryTitle`: a sibling of `LikeCounter`. 2. `LikeLabel`: a child of `LikeCounter`.

- [p] ★ Verified output: first render `App runs`, `StoryTitle runs`, `LikeCounter runs, likes = 0`, `LikeLabel runs`. A click: `LikeCounter runs, likes = 1`, `LikeLabel runs`. React does not check first whether a child's output will change: a child that always shows the same text also runs on every click, and the commit then finds nothing to change in it. Lecture 54 adds the other reasons a component renders. ◼ Educational objective: Merged rows on the first render walk and the child that runs with the same output; Preview Q54 in one sentence.

- [principle-notes] Principle 3: Mia's question. The reader believes a render rebuilds the page, from full reloads and from `innerHTML`. Basics first: after a render React has the new JSX and the last JSX. Then: the commit changes only where they differ; an element in the same place keeps its DOM node. Proof: type `great post`, click Like; the input keeps its text, the `<p>` and its text nodes are the same nodes, only the number changed. Then the paint. Code pair: JSX against `innerHTML` with string concatenation (Lecture 4); both run, so "best practice". Moves from Case 6 (remind the plain JavaScript) and Case 1 (step by step).

> [!PRINCIPLE]
> **Principle 3: The Commit Changes Only What Is Different**
> After a render, React has two sets of JSX: the new one and the one from the last render. In the commit, React changes the page only where they differ. An element that stays in the same place in the JSX keeps the same DOM node on the page. If only `{count}` changed, only that number changes. So an `<input>` beside it keeps the text the user typed. We might expect a render to rebuild the page, as setting `innerHTML` does. It does not. When the commit is done, the browser paints the screen.
>
> *It is best practice to do this:*
> `return (`
> `  <div>`
> `    <p>{count}</p> // only this number changes`
> `    <input />`
> `  </div>`
> `);`
>
> *Instead of doing this:*
> `box.innerHTML = '<p>' + count + '</p><input>'; // the input is new`

- [p] ★ Verified output on the finished `LikeCounter`: type `great post` into the input, click Like. The page shows `Likes: 1`, the input still holds `great post`, and the `<input>` and the `<p>` are the same DOM nodes as before. Inside the `<p>`, `Likes: ` and the number are two text nodes, and only the number node changed. With `innerHTML`, the same update creates a new, empty input. Lecture 24 explains how React decides that an element is in the same place. ◼ Educational objective: Merged rows on typed text and render against paint; Preview Q24 in one sentence.

- [principle-notes] Principle 4: Leo's bug. The reader believes `setCount(1)` changes the page on that line, from `textContent` and jQuery. Basics first: in plain JavaScript an assignment to `textContent` changes the page at once. Then the steps: the setter asks for a render; React renders and commits after the handler finishes; the next line sees the old page. Decision: compute the new number once and pass it on. Proof: `sent to statistics: 0` before `LikeCounter runs, likes = 1`; the fixed handler sends `1`. Moves from Case 4 (answer the question the reader is about to ask) and Case 7 (two moments the reader can picture).

> [!PRINCIPLE]
> **Principle 4: The Page Changes Only After the Event Handler Finishes**
> In plain JavaScript, `p.textContent = 1` changes the page on that line. We might expect `setCount(1)` to do the same. It does not. A setter only asks React for a render. React renders and commits after the event handler has finished. So on the line after `setCount(count + 1)`, the page still shows the old number. When the handler needs the new number, compute it once, as `const next = count + 1`, and pass `next` to the setter and to any other code.
>
> *We should do this:*
> `const [count, setCount] = useState(0);`
> `const next = count + 1;`
> `setCount(next);`
> `report(next); // reports the new number`
>
> *We should not do this:*
> `const [count, setCount] = useState(0);`
> `setCount(count + 1);`
> `const shown = document.querySelector('p').textContent;`
> `report(shown); // reports the old number`

- [p] ★ Leo's report line printed `sent to statistics: 0` before `LikeCounter runs, likes = 1`: the handler finished first, then React rendered and committed. The fix computes `next` once and sends it; the first click now prints `sent to statistics: 1`. The variable `likes` also still holds the old value on the line after the setter; Lecture 16 explains why. ◼ Educational objective: the decision on Leo's handler; Preview Q16 in one sentence; Merged row on batching stated only as "after the handler".

- [grounding] **Why does code after root.render find an empty page?** ◼ Friction target: a line after `root.render(<App />)` in `main.jsx` counts the `<article>` elements and gets 0. ◼ Tactile scene: the root element still holds `Loading...` on that line. ◼ Bold key terms: **trigger**, **commit**. ◼ Resolution: the first `root.render` is a trigger, not a render; React renders and commits after `main.jsx` has finished, and the first commit replaces `Loading...`. Verified and in createRoot `root.render` Caveat 4.

### Glossary

- [glossary] Trigger ◼ The request that starts a render: the first `root.render` call, or a setter call.
- [glossary] Render ◼ React calling component functions to get their JSX; the page does not change.
- [glossary] Commit ◼ The step where React changes the DOM nodes that differ from the last render.
- [glossary] DOM Node ◼ The browser's object for one element or one piece of text on the page.
- [glossary] Paint ◼ The browser drawing the page on the screen after the commit.
