### What the children prop is and how JSX compiles slots

- [p] ◇ {runway: nesting tags in HTML versus React custom components} In standard HTML, nesting elements inside one another is the universal way to structure documents: you place an `<img>` and an `<h2>` inside an `<article>`, or an `<a>` inside a `<nav>`. In React, custom components support that exact same physical nesting syntax. When you write `<CardContainer><Headline /></CardContainer>`, you are passing `<Headline />` into `CardContainer` as an input. React automatically captures whatever markup appears between a component's opening and closing tags and delivers it to the component function under a reserved property name: `children`. ◼ Educational objective: connect component slot nesting to native HTML element containment.
- [p] ★ {runway: JSX compilation maps nested markup to props.children key} Under the hood, the JSX compiler converts every component tag into a `_jsx()` function call. As established in Lecture 3, writing opening and closing tags with nested content transforms into `_jsx(CardContainer, { children: [...] })`. The compiler places nested markup into the `children` key of the props object alongside any regular attributes. Because `children` is an ordinary property on the props object, a component reads it using `props.children` or unpacks it directly in its parameter list using object destructuring: `function CardContainer({ children })`. If a caller mistakenly passes both an attribute named `children` and nested elements inside the tags, `<CardContainer children="attr">nested</CardContainer>`, the nested content wins because the compiler writes nested JSX into `children` after evaluating opening tag attributes. ◼ Educational objective: trace compiler transformation from nested JSX to props.children and verify attribute-versus-nested precedence.

- [code] Compiler Slot Translation (verified in React 19.3.0: compiler places nested tags into props.children):

```jsx title="Compiler Slot Translation"
// JSX call site:
<CardContainer className="featured">
  <h2>Morning Dispatch</h2> {/* nested headline element */}
</CardContainer>

// Compiled output:
_jsx(CardContainer, {
  className: "featured",
  children: _jsx("h2", { children: "Morning Dispatch" }) // slot in props
})
```

◼ **The what-this-introduces list:** 1. `_jsx`: compiler runtime function instantiating element descriptors. 2. `children`: property in props object holding nested element tree. 3. Tag attributes: regular attributes like `className` sitting alongside `children` in the same object.

- [p] ★ {runway: children is an opaque descriptor with shifting shapes} It is critical to understand that `children` is an **opaque data structure** whose internal shape shifts depending on what the caller nests. If a caller nests two elements `<CardContainer><h2 /><p /></CardContainer>`, React sets `children` to an array, and `Array.isArray(children)` evaluates to `true`. But if a caller nests a single element `<CardContainer><h2 /></CardContainer>`, React sets `children` directly to that single element object to avoid memory allocation overhead, and `Array.isArray(children)` evaluates to `false`. If a caller nests text, `children` is a string. If code attempts to call `children.map(...)` on a single child, JavaScript immediately throws a fatal runtime error: `TypeError: children.map is not a function`. Containers must render `{children}` whole or accept an explicit array prop when list mapping is required. ◼ Educational objective: explain why children has no fixed shape and prevent single-child array crashes.
- [p] ★ {runway: child descriptors do not include rendered output} The `children` prop contains lightweight element descriptors created by the caller, not rendered DOM output. The container component function executes before child component functions execute. Inside `CardContainer`, logging `children.type` points to the child component function itself, not rendered HTML nodes. If a container omits `{children}` from its return statement, the child component function never runs, and its console logs remain completely silent. The container acts as a conduit for element descriptors, never an inspector of rendered DOM output. ◼ Educational objective: establish the descriptor model and prove component execution order.

### Container components and slot composition

- [p] ◇ {runway: container component definition and inversion of control} A **container component** is a component that provides a reusable visual frame (such as borders, background colors, shadows, and padding) while leaving its inner content open for callers to supply. This architectural pattern is called **slot composition**, and it implements the computer science principle of **inversion of control**. In rigid monolithic components, the child component dictates both the outer styling and every inner element. With slot composition, responsibility splits cleanly: the container owns the outer boundary, while the caller chooses what content belongs inside. ◼ Educational objective: define container components, slot composition, and inversion of control.
- [p] ★ {runway: named props for fixed requirements versus slots for variable layout} When designing container components, developers must decide what belongs in named props and what belongs in `{children}`. A named prop stays for something every card must guarantee in a fixed position, format, or layout role, such as the `title` on an article card or the `isOpen` state on a dialog. Everything that varies across callers (such as alert badges, author bylines, thumbnail images, or action buttons) belongs in `{children}`. This rule keeps the container parameter list lean while giving callers complete freedom over their markup. ◼ Educational objective: establish the boundary between named data props and composable slots.

- [grounding] [!] Grounding card: Why do layout-flag props cause architectural rot? ◼ Opening question: Why do layout-flag props cause architectural rot? ◼ Friction target: Teams building design-system components watch their parameter lists explode with dozens of boolean flags that fight each other. ◼ Tactile scene: An editor asks to move an author above the headline on an opinion card; because the shared card has a hardcoded layout order, an engineer adds an `isAuthorTop` boolean prop, breaking the layout for standard articles. ◼ Bold key terms: **inversion of control**, **slot composition**, **layout-flag antipattern**, **children prop**. ◼ Operational resolution: Separate the outer container frame from the inner content; let the container own outer chrome and expose an open slot with `{children}`, allowing callers to arrange inner elements freely.

### Forwarding attributes with rest syntax and JSX spread

- [p] ◇ {runway: why pass-through wrappers need to forward attributes} Reusable container components often wrap native HTML elements like `<div>` or `<article>`. Callers frequently need to attach standard browser attributes to that underlying element, such as `id="main-card"`, `aria-label="Breaking Bulletin"`, `data-story-id="102"`, or mouse event handlers. If a container only accepts explicit props, developers would have to add every possible HTML attribute to the component parameter list by hand. To avoid this boilerplate, React allows wrappers to pass extra attributes through to the underlying element. ◼ Educational objective: motivate attribute forwarding in generic container wrappers.
- [p] ★ {runway: rest syntax in destructuring gathers unconsumed properties} In JavaScript, placing three dots (`...`) before the final identifier in an object destructuring pattern activates **rest syntax**: `function CardContainer({ children, isFeatured, ...rest })`. The runtime extracts `children` and `isFeatured` into local variables, and gathers all remaining properties from the incoming props object into a new object named `rest`. If a caller passes `id="top"`, `aria-label="Alert"`, and `data-card-id="42"`, all three properties land cleanly inside `rest`. This allows the component to consume the props it needs for its own logic while isolating pass-through attributes in a clean object. ◼ Educational objective: explain JavaScript rest syntax in destructuring.
- [p] ★ {runway: JSX spread syntax writes properties as tag attributes} To write the gathered attributes onto a JSX element, React provides **JSX spread syntax**: `<div className="card" {...rest}>{children}</div>`. Inside JSX tags, wrapping an object in curly braces with three dots (`{...rest}`) tells React to copy every key-value pair from that object as an attribute on the tag. Writing `{...rest}` when `rest` contains `{ id: "top", aria-label: "Alert" }` produces `<div className="card" id="top" aria-label="Alert">` in the browser DOM. The React documentation warns developers to use spread with restraint: frequent spread across business components obscures data requirements, so spread belongs specifically in generic pass-through wrappers. ◼ Educational objective: explain JSX spread syntax and establish the rule of spread restraint.

- [code] Rest and Spread Attributes (verified in React 19.3.0: forwards remaining attributes to DOM element):

```jsx title="Rest and Spread Attributes"
function CardContainer({ children, isFeatured, ...rest }) { // gathers rest
  return (
    <div className="card" {...rest}> {/* spreads rest onto native tag */}
      {children}
    </div>
  );
}
```

◼ **The what-this-introduces list:** 1. `...rest`: JavaScript rest syntax gathering unconsumed props into a separate object. 2. `{...rest}`: JSX spread syntax expanding object properties into tag attributes. 3. Native DOM target: forwarding attributes directly to the underlying `<div>`.

### Principles of React: Container Composition and Prop Spreading

- [p] ◇ In technical interviews, engineering candidates are closely evaluated on container composition, the opaque structure of `children`, clean attribute forwarding with rest and spread, attribute evaluation order, and fallback defaults in destructuring. In each question cycle below, the scenario presents concrete code, the bold question names the developer's uncertainty, the answer traces what the runtime executes, and the principle box formalizes that answer into an engineering rule. ◼ Educational objective: frame the upcoming five question cycles and principle boxes.

- [question-cycle] Question 1: Content placed between tags arrives as the children prop
    - Question: "I put a headline between `<CardContainer>` and `</CardContainer>`. Where does it go?"
    - Code and result: The caller renders `<CardContainer><h2>Transit Accord</h2></CardContainer>`; `CardContainer` returns `<div className="card" />` without `{children}`; the browser displays an empty card frame, the headline is missing from the page, and the console prints zero errors (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: The JSX compiler transforms nested markup into the `children` key of the props object, `_jsx(CardContainer, { children: _jsx("h2", { children: "Transit Accord" }) })`; React invokes `CardContainer` with that props object; because the container returned `<div className="card" />` and never wrote `{children}` in its JSX, React renders only the outer `<div>` and silently discards the nested element; child components never execute when dropped, and `children` has no fixed shape (an element object for one child, an array for multiple children, a string for text, throwing TypeError if `children.map` is called on a single child); the content appears on screen only where the container explicitly places `{children}`.
    - Fix: Place `{children}` inside the returned JSX, `function CardContainer({ children }) { return <div className="card">{children}</div>; }`, taught in the runway section "What the children prop is and how JSX compiles slots".
    - Rule: When nesting elements inside custom tags, place `{children}` in the returned JSX where the content belongs. Boundary: The container decides where the slot sits; the caller decides what content fills it.
    - Needs: children prop (runway), compiler slot translation (runway), opaque descriptor (runway), destructuring (recall, Lecture 6).
    - Diagram: Nested JSX compiling into props.children and mounting inside returned JSX slot.

> [!PRINCIPLE]
> **Principle 1: Nested JSX arrives as the children prop**
> When you place elements or text between a component's opening and closing tags, React delivers that content in the **children prop**. The container function receives it as a property on its incoming props object, exactly like an attribute. The content appears on screen only where the container places **{children}** inside its returned markup. If the container omits `{children}`, React renders the outer frame and drops the nested content without printing a warning.
>
> >> children prop : a reserved property that receives any JSX elements or text nested between a component's tags
>
> *We should do this:*
> `function CardContainer({ children }) {`
> `  return <div className="card">{children}</div>; // mounts nested children in slot`
> `}`
>
> *We should not do this:*
> `function CardContainer({ children }) {`
> `  return <div className="card" />; // drops nested children silently`
> `}`

- [question-cycle] Question 2: Let the caller compose inner pieces instead of adding a prop for each
    - Question: "One story needs a badge, another an author, a third a button. Do I add a prop for each?"
    - Code and result: `NewsCard({ title, badgeText, author })` renders `<span className="badge">{badgeText}</span>`; for a story without a badge, the DOM still contains `<span class="badge"></span>`, which renders as an empty styled pill on screen (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: Adding a prop for every optional element bloats the component signature with dozens of parameters and forces the component to manage rigid layout branches; callers cannot reorder elements or add new pieces without editing the shared component; with slot composition, `CardContainer` draws only the outer frame and provides an open hole with `{children}`; each caller nests the exact badges, headlines, or buttons it requires; a story needing a badge nests `<span className="badge">New</span>`, while a story without a badge nests only `<h2>Headline</h2>`; a named prop stays only for a fixed requirement that every card must guarantee in a specific position, such as `title`.
    - Fix: Let callers nest markup inside `<CardContainer>`, keeping named props only for values every card must display in a fixed place, taught in the runway section "Container components and slot composition".
    - Rule: When callers need different inner layouts, let them compose elements inside `{children}` instead of adding layout-flag props. Boundary: Keep a named prop for a fixed value every card must guarantee across every instance.
    - Needs: slot composition (runway), container component (runway), inversion of control (runway), empty element DOM consequence (runway).
    - Diagram: Monolithic layout props versus open slot composition.

> [!PRINCIPLE]
> **Principle 2: Let the caller fill the container instead of adding a prop for every piece**
> When different cards need different inner arrangements, let callers nest the elements they need directly inside the container through **slot composition**. Adding a prop for every optional piece bloats the component signature and forces the container to manage conflicting layout branches. Keep a named prop only for a value every instance must show in a fixed place, and let callers fill the rest through the open slot.
>
> >> slot composition : letting callers compose inner elements freely inside an open container slot
>
> *It is best practice to do this:*
> `<CardContainer>`
> `  <span className="badge">New</span> {/* caller nests badge */}`
> `  <h2>Morning Dispatch</h2>`
> `</CardContainer>`
>
> *Instead of doing this:*
> `<CardContainer`
> `  badgeText="New" // adds prop to container for optional layout piece`
> `  title="Morning Dispatch"`
> `/>`

- [question-cycle] Question 3: Spread only the props the container does not consume
    - Question: "Callers want to add id, aria-label, and data-story-id to the card. Do I list each one?"
    - Code and result: `CardContainer` writes `<div className="card" {...props}>{props.children}</div>`; the caller passes `isFeatured={true}` and `badgeText="New"`; the console prints `Warning: React does not recognize the isFeatured prop on a DOM element`, and the browser DOM receives `<div badgetext="New">` (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: Spreading the entire `props` object onto a native browser tag passes every custom component prop to the DOM element; React does not recognize non-standard camelCase attributes on HTML elements and prints console warnings; non-standard lowercase attributes like `badgeText` leak silently into the DOM as `badgetext="New"`; custom props named like HTML attributes (such as `title`) collide and become unintended hover tooltips; to forward attributes safely, unpack the props the component consumes (`{ children, isFeatured, ...rest }`) with rest syntax, and spread only `{...rest}` onto the element; spreading everything is appropriate only when forwarding all props to a child component that uses them.
    - Fix: Destructure `{ children, isFeatured, ...rest }` and write `<div className="card" {...rest}>{children}</div>`, taught in the runway section "Forwarding attributes with rest syntax and JSX spread".
    - Rule: Destructure the props the component consumes and spread only `...rest` onto native DOM elements. Boundary: Spread is reserved for pass-through wrappers forwarding unconsumed attributes to a single element.
    - Needs: rest syntax (runway), JSX spread syntax (runway), DOM attribute leakage (runway), console warning (recall, Lecture 6).
    - Diagram: Separating consumed props from pass-through attributes using rest syntax.

> [!PRINCIPLE]
> **Principle 3: Spread only the props the container does not use**
> When a container forwards extra attributes to a native DOM element, unpack the props it uses and collect the remaining properties with **rest syntax**: `{ children, isFeatured, ...rest }`. Then forward only those remaining properties onto the element using **JSX spread syntax**: `{...rest}`. Spreading the whole `props` object forwards component props too, causing **DOM attribute leakage** and development console warnings.
>
> >> rest syntax : gathering unpicked properties into a separate object with ...rest`
> >> JSX spread syntax : writing each property of an object as a JSX attribute with {...rest}`
> >> DOM attribute leakage : writing non-standard component props onto native browser DOM elements`
>
> *We should do this:*
> `function CardContainer({ isFeatured, children, ...rest }) {`
> `  return <div className="card" {...rest}>{children}</div>; // forwards rest`
> `}`
>
> *We should not do this:*
> `function CardContainer(props) {`
> `  return <div className="card" {...props}>{props.children}</div>; // leaks props`
> `}`

- [question-cycle] Question 4: Around a spread, the last attribute wins
    - Question: "The caller passed className=\"featured\". Why did my card lose its frame?"
    - Code and result: `CardContainer` writes `<div className="card" {...rest}>{children}</div>`; the caller passes `className="featured"`; the DOM renders `<div class="featured">`, completely replacing `"card"` and stripping border and padding styles (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: JSX evaluates attributes from left to right; when the same attribute name appears before and after, the last one evaluated overwrites earlier values; because `className="card"` was written before `{...rest}`, the caller's incoming `className` inside `rest` overwrote `"card"`; if the container places `className="card"` after `{...rest}`, the container overwrites the caller's class completely and prevents custom styling; attributes never merge by themselves in JSX; when both sides need to contribute classes, extract `className` in the parameter list and join both strings explicitly using string concatenation: `className={'card ' + className}`.
    - Fix: Extract `className` and join both strings with `className={'card ' + className}`, taught in the runway section "Forwarding attributes with rest syntax and JSX spread".
    - Rule: Around a spread, place overridable defaults before `{...rest}` and enforced values after it; when both sides provide classes, join them explicitly. Boundary: Overwriting is desirable only when establishing a default that callers are explicitly intended to replace.
    - Needs: attribute precedence (runway), string concatenation with + (recall, Lecture 4), className attribute (recall, Lecture 3).
    - Diagram: Left-to-right attribute evaluation order and explicit class merging.

> [!PRINCIPLE]
> **Principle 4: Around a spread, the last attribute wins**
> JSX evaluates attributes from left to right. When the same attribute appears more than once, the last one written wins. An attribute placed before `{...rest}` serves as an overridable default that caller props replace. An attribute placed after `{...rest}` is an enforced rule that overrides caller props. When both sides need to contribute a class name, extract `className` and join both strings explicitly.
>
> >> attribute precedence : the left-to-right order where later JSX attributes overwrite earlier ones
>
> *It is best practice to do this:*
> `function CardContainer({ className, children, ...rest }) {`
> `  const fullClass = 'card ' + className; // joins base with caller`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`
>
> *Instead of doing this:*
> `function CardContainer({ children, ...rest }) {`
> `  return <div className="card" {...rest}>{children}</div>; // caller overwrites`
> `}`

- [question-cycle] Question 5: A default fills a prop the caller left out
    - Question: "What if the caller passes no className, or nothing between the tags?"
    - Code and result: `CardContainer` writes `className={'card ' + className}`; when the caller omits `className`, the DOM renders `<div class="card undefined">`; when the caller nests nothing between tags (`<CardContainer />`), the container renders an empty frame with no placeholder (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: A missing prop evaluates to `undefined`; inside JSX content, `{undefined}` renders as an empty slot without printing text; but inside JavaScript string concatenation, `'card ' + undefined` coerces `undefined` into the string `"undefined"`, producing `"card undefined"` in the DOM; to prevent this, assign a default parameter value in destructuring: `className = ''`; when the prop is omitted or passed as `undefined`, the variable receives `''`, producing `'card '`; similarly, `children = <p>No items yet</p>` provides a fallback element when no children are nested; default parameters engage only for missing or `undefined` values; they do not engage for `null` or `false`.
    - Fix: Assign default parameter values in destructuring, `function CardContainer({ children = <p>No items yet</p>, className = '', ...rest })`, taught in Lecture 6 and applied here to container slots.
    - Rule: Assign default parameter values in destructuring to provide fallbacks for missing props or empty slots. Boundary: Default parameters engage strictly when a value is missing or undefined, never for null or false.
    - Needs: default parameter value (recall, Lecture 6), undefined coercion (recall, Lecture 4), null and false handling (recall, Lecture 4).
    - Diagram: Missing prop versus undefined versus null and fallback engagement.

> [!PRINCIPLE]
> **Principle 5: A default fills a prop the caller left out**
> A missing prop evaluates to `undefined`. In content, `undefined` renders nothing, but in string concatenation it becomes the literal text `"undefined"`. Assign a **default parameter value** in the destructuring list to provide a fallback whenever a prop is omitted: `className = ''`. Default parameter values engage only when a prop is missing or strictly `undefined`; they do not engage when a caller passes `null` or `false`.
>
> >> default parameter value : a fallback value assigned in destructuring when an argument is missing or undefined
>
> *We should do this:*
> `function CardContainer({ className = '', children, ...rest }) {`
> `  const fullClass = 'card ' + className; // clean fallback`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`
>
> *We should not do this:*
> `function CardContainer({ className, children, ...rest }) {`
> `  const fullClass = 'card ' + className; // produces undefined`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`

### Step 1: First, we construct the slot-based container component <CardContainer.jsx>

- [p] ★ We author the foundational container component `CardContainer.jsx` to establish the reusable visual frame for dispatches. Instead of accepting specialized layout flags that dictate inner elements, `CardContainer` exposes an open slot by destructuring `children` from its parameter list. Notice how the parameter signature also unpacks `color = 'gray'` and `className = ''` with explicit default parameter values, while collecting all remaining pass-through attributes into `...rest`. The component calculates a merged CSS class string and forwards `...rest` onto the root `<div>`. ◼ Meaningful pedagogical commentary: slot container definition, parameter destructuring with defaults, rest collection, and safe class merging.

- [code] CardContainer.jsx:

```jsx title="CardContainer.jsx"
export default function CardContainer({
  children, color = 'gray', className = '', ...rest // unpacks slot
}) {
  const cls = `card card-${color} ${className}`.trim();
  return (
    <div className={cls} {...rest}> {/* forwards props to wrapper */}
      {children}
    </div>
  );
}
```

◼ **The what-this-introduces list:** 1. `CardContainer`: reusable slot container component. 2. `{ children, color = 'gray', className = '', ...rest }`: parameter destructuring isolating consumed props from pass-through attributes. 3. `cls`: pure local derivation merging base styles, color styles, and caller classes without `"undefined"` leakage. 4. `{...rest}`: attribute forwarding to the native DOM element. 5. `{children}`: the slot mounting caller-provided element descriptors.

### For the interview

- [interview] > **The Interview Question:** How do the children prop, spread attributes, and default values work?
- [interview] **1. The Hidden Signal**: The interviewer is probing your mastery of component composition architecture, compiler transformations, JavaScript rest and spread syntax, attribute precedence, and DOM attribute leakage. Junior developers explain props as HTML attributes. Senior engineers explain that JSX compiles nested tags into `props.children` (`_jsx(Card, { children: [...] })`), implementing inversion of control. They explain that pass-through wrappers destructure consumed props and forward `...rest` to prevent unknown-prop console warnings, that JSX evaluates attributes left to right, and that default parameters protect against `undefined` string coercion.
- [interview] **2. The Classic Trap**: One classic trap is assuming `children` is always an array. In React, `children` is an opaque data structure: a single child is an element object, multiple children form an array, and plain text is a string. Calling `children.map()` on a single nested child crashes with `TypeError: children.map is not a function`. Another trap is spreading full `props` onto a native element (`<div {...props}>`), which leaks component props to the DOM and triggers React warnings. A third trap is merging classes without default parameter fallbacks (`'card ' + className`), which renders `"card undefined"` in the DOM when the prop is omitted.
- [interview] **3. What is Actually Going On**: Under the hood, JSX converts nested tags into `props.children`. When React executes `CardContainer`, it passes this object as the first argument. If the container omits `{children}`, React renders the outer frame and drops the children; child functions never run, and their console logs remain silent. Around `{...rest}`, JSX applies attributes left to right: an attribute before `{...rest}` serves as an overridable default, while an attribute after `{...rest}` enforces a value. In destructuring, `className = ''` assigns an empty string when the prop is missing or `undefined`, preventing string coercion bugs while preserving valid values.
- [interview] **4. Where It Gets Tricky**: Where this gets tricky is handling collisions between custom props and native HTML attributes. If a component accepts `title="Night Trains"` as a data prop but blindly spreads all props onto a container `<div>`, that title becomes an unintended browser hover tooltip. If a boolean prop like `isFeatured={true}` spreads onto a `<div>`, React logs unknown attribute warnings. Another tricky nuance is that default parameters trigger strictly for `undefined` or omitted props; if a caller passes `className={null}` or `children={null}`, default parameter values do not engage, and `{null}` renders as an empty slot.

### Glossary

- [glossary] Children Prop ◼ A reserved React property that automatically receives any JSX elements or text passed between a component's opening and closing tags.
- [glossary] Slot Composition ◼ An architectural design pattern where a container component defines visual boundaries and leaves open slots for caller-provided content.
- [glossary] Inversion of Control ◼ A design principle where the calling component chooses what inner content to render, while the container decides where and how that content is framed.
- [glossary] Rest Syntax ◼ The JavaScript syntax using three dots in destructuring to collect unconsumed properties into a separate object.
- [glossary] JSX Spread Syntax ◼ A JSX syntax pattern using `{...props}` or `{...rest}` to forward an object of properties onto an underlying element.
- [glossary] DOM Attribute Leakage ◼ The unintended forwarding of non-standard component props onto native browser DOM elements, causing warnings and invalid attributes.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Slot Composition with Children

➔ IF a component acts as a reusable visual container, THEN place `{children}` in its return statement to allow callers to compose inner content freely.

➔ IF rendering received children, THEN treat `children` as an opaque descriptor and render it whole rather than calling array methods like `children.map()`.

❒ Controlled Prop Spreading

➔ IF a wrapper component forwards extra attributes to a native DOM element, THEN destructure consumed props and spread only `...rest` onto the element.

➔ IF a component accepts custom data props, THEN never spread the entire `props` object onto native DOM elements to prevent attribute leakage and console warnings.

❒ Attribute Precedence and Defaults

➔ IF specifying overridable defaults on a wrapper element, THEN place default attributes before `{...rest}` and enforced attributes after `{...rest}`.

➔ IF merging class names on a wrapper component, THEN assign a default parameter `className = ''` and combine the strings explicitly.

**DO THIS:** Compose inner layout with children and merge class names explicitly

```jsx right
function CardContainer({
  children,
  color = "gray",
  className = "",
  ...rest
}) {
  const cls = `card card-${color} ${className}`.trim();
  return (
    <div className={cls} {...rest}>
      {children}
    </div>
  );
}
```

**DO NOT DO THIS:** Bloat containers with layout flags and spread unconsumed props

```jsx wrong
function CardContainer(props) {
  return (
    <div className="card" {...props}>
      {props.children}
    </div>
  );
}
```
