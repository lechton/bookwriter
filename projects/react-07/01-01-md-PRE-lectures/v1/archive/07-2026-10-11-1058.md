### Rest syntax gathers the keys you did not name

- [code] Rest Syntax in Object Destructuring:

```js
const props = { title: 'Transit Accord', id: 'top', tone: 'quiet' };
const { title, ...rest } = props; // extracts title and gathers rest
console.log(rest); // { id: 'top', tone: 'quiet' }
```

◼ **The what-this-introduces list:** 1. `title`: extracted property variable. 2. `...rest`: rest syntax collecting unextracted properties. 3. `rest`: new plain JavaScript object containing `{ id: 'top', tone: 'quiet' }`.

- [p] ★ {runway: rest syntax in destructuring} The console prints an object with `id` and `tone`. Line 2 takes `title` out by name, and the three dots before `rest` collect every key that was not named into a new object. This is rest syntax in destructuring. It is plain JavaScript, so it works on any object, including the props object a component receives. It leaves Question 3 completely open, because it says nothing about spreading `rest` onto a JSX tag. ◼ Educational objective: teach the rest syntax tool in isolation before Question 3 uses it.

### Principles of React: Container Composition and Prop Spreading

- [p] ◇ In technical interviews, engineering candidates are closely evaluated on container composition, the opaque structure of `children`, clean attribute forwarding with rest and spread, attribute evaluation order, and fallback defaults in destructuring. In each question cycle below, the scenario presents concrete code, the bold question names the developer's uncertainty, the answer traces what the runtime executes, and the principle box formalizes that answer into an engineering rule. ◼ Educational objective: frame the upcoming five question cycles and principle boxes.

- [question-cycle] Question 1: Content placed between tags arrives as the children prop
    - Question: "I put a headline between `<CardContainer>` and `</CardContainer>`. Where does it go?"
    - Code and result: `Feed` renders `<CardContainer><h2>Transit Accord Reached</h2></CardContainer>`, but `CardContainer` returns `<div className="card" />` without `{children}`; DevTools displays an empty `<div class="card"></div>`, the headline is completely missing from the screen, and the console stays silent with zero warnings (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: The JSX compiler transforms nested markup into the `children` key of the props object: `_jsx(CardContainer, { children: _jsx("h2", { children: "Transit Accord Reached" }) })`; React invokes `CardContainer` with that props object; because `CardContainer` returned `<div className="card" />` and never wrote `{children}` in its JSX, React renders only the outer `<div>` and silently discards the nested element; components passed as children never execute if dropped.
    - Fix: Place `{children}` inside the returned JSX, `function CardContainer({ children }) { return <div className="card">{children}</div>; }`, taught in this answer.
    - Rule: Place `{children}` inside the container markup where the nested content belongs. Boundary: React never places nested JSX by itself; if the container omits `{children}`, the content disappears without an error.
    - Needs: children prop (this answer), _jsx call (recall, Lecture 3), props object (recall, Lecture 6), object destructuring (recall, Lecture 6).
    - Diagram: Nested JSX compiling into props.children and mapping to DOM.
    - First sight: The two-component snippet showing `Card` with `{children}` and `<Card><h2>Transit Accord</h2></Card>`, pointing at the line that links them, then naming `children prop`.

> [!PRINCIPLE]
> **Principle 1: Nested JSX arrives as the children prop**
> When you nest elements or text between a component's opening and closing tags, React delivers that content in the **children prop**. React passes it to the component function on its props object, like an attribute. The content appears on the screen only where the component writes **{children}** in its returned JSX. If the component never writes `{children}`, React renders the outer frame and drops the nested content without a warning.
>
> >> children prop : a reserved prop that receives elements or text nested between component tags
>
> *We should do this:*
> `function Card({ children }) {`
> `  return <div className="card">{children}</div>; // places children in the card`
> `}`
>
> *We should not do this:*
> `function Card({ children }) {`
> `  return <div className="card" />; // drops children without an error`
> `}`

- [question-cycle] Question 2: Let the caller fill the container instead of adding a prop for every piece
    - Question: "One card needs a badge, another an author, and a third a button. Do I add a prop for each?"
    - Code and result: `StoryFeed` calls `NewsCard({ title, badgeText, author })` from our earlier Naive Layout Prop Bloat component; rendering a standard story without a badge (`<NewsCard title="Budget Debate" author="Clara" />`) renders an empty `<span class="badge"></span>`, which displays as an empty colored pill on screen because `.badge` has padding and a background (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: Adding a prop for every optional piece forces the container to predict every layout variation and render empty elements when props are omitted; in slot composition, the container owns only the outer frame and provides `{children}`; each caller nests the exact elements it needs in the order it wants; a story with a badge nests the badge, while a story without a badge omits it completely.
    - Fix: Refactor `NewsCard` into `CardContainer` taking `{children}` and let each call site nest its own elements, keeping a named prop only for values every card must show in a fixed place, taught in this answer.
    - Rule: Let callers nest variable elements through the open slot instead of adding a prop per variation. Boundary: Keep a named prop for a value every instance must display in a fixed format or location (such as `title`), while variable inner content goes into `children`.
    - Needs: container component (this answer), slot composition (this answer), className (recall, Lecture 3).
    - Diagram: Rigid props versus composable slot.
    - First sight: The scenario's code.

> [!PRINCIPLE]
> **Principle 2: Let the caller fill the container instead of adding a prop for every piece**
> When different instances of a component need different inner layouts, let callers nest the elements they need through **slot composition**. Adding a prop for each optional piece forces the container to manage layout flags and leaves empty elements on items that omit the prop. Keep a named prop only for a value every instance must show in a fixed place, and let callers nest the rest through the open slot.
>
> >> slot composition : letting callers compose inner elements freely inside an open container slot
>
> *It is best practice to do this:*
> `<Card>`
> `  <span className="badge">New</span> {/* caller nests badge */}`
> `  <h2>Title</h2>`
> `</Card>`
>
> *Instead of doing this:*
> `<Card`
> `  badgeText="New" // adds prop to container for layout variation`
> `  title="Title"`
> `/>`

- [question-cycle] Question 3: Spread only the props the container does not use
    - Question: "Callers want to add `id`, `aria-label`, and `data-story-id` to the card. Do I list each one?"
    - Code and result: `CardContainer` spreads all props onto the container element, `<div className="card" {...props}>{props.children}</div>`, with `isFeatured={true}` and `badgeText="New"` passed by a caller; the console warns "React does not recognize the `isFeatured` prop on a DOM element", and DevTools shows `badgetext="New"` on the DOM `<div>` (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: Native DOM elements like `<div>` only accept valid HTML attributes; spreading the entire `props` object forwards component-only props like `isFeatured` and `badgeText` to the DOM node, triggering React console warnings and invalid attributes; rest syntax `{ children, isFeatured, ...rest }` extracts consumed props into local variables and gathers unconsumed props into `rest`; `{...rest}` writes only those remaining attributes onto the `<div>`.
    - Fix: Unpack consumed props and spread only `...rest` onto the element, `function CardContainer({ isFeatured, children, ...rest }) { return <div className="card" {...rest}>{children}</div>; }`, taught in this answer.
    - Rule: Spread only the props the container does not use. Boundary: Spread attributes only in generic wrapper components that pass attributes through; a component that reads its data lists its props by name.
    - Needs: rest syntax (runway), JSX spread attributes (this answer), DOM attribute leakage (this answer), aria-* and data-* attributes (recall, Lecture 3).
    - Diagram: ASCII diagram comparing `{...props}` leaking to DOM against `{...rest}` forwarding clean attributes.
    - First sight: The scenario's code.

> [!PRINCIPLE]
> **Principle 3: Spread only the props the container does not use**
> When a container forwards extra attributes to a native DOM element, unpack the props it uses and collect the remaining properties with **rest syntax**: `{ children, isFeatured, ...rest }`. Then write only those remaining properties on the element with **JSX spread syntax**: `{...rest}`. Spreading the whole `props` object forwards component props too, causing **DOM attribute leakage** and development console warnings.
>
> >> rest syntax : gathering unpicked properties into a separate object with ...rest
> >> JSX spread syntax : writing each property of an object as a JSX attribute with {...rest}
> >> DOM attribute leakage : writing non-standard component props onto native browser DOM elements
>
> *We should do this:*
> `function Card({ isFeatured, children, ...rest }) {`
> `  return <div className="card" {...rest}>{children}</div>; // forwards rest`
> `}`
>
> *We should not do this:*
> `function Card(props) {`
> `  return <div className="card" {...props}>{props.children}</div>; // leaks props`
> `}`

- [question-cycle] Question 4: Around a spread, the last attribute wins
    - Question: "The caller passed `className="featured"`. Why did my card lose its frame?"
    - Code and result: The container writes `<div className="card" {...rest}>{children}</div>`; a caller passes `className="featured"`; DevTools displays `class="featured"`, and the card loses its base border and padding because `.card` was completely replaced (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: JSX applies attributes strictly from left to right; an attribute in `rest` appears after `className="card"` and overwrites it; placing `className="card"` after `{...rest}` overwrites the caller's class instead; attributes never merge automatically in React; to combine both classes, destructure `className` explicitly and join them using string concatenation: `className={'card ' + className}`.
    - Fix: Unpack `className` and join both strings explicitly, `className={'card ' + className}`, taught in this answer.
    - Rule: Attributes evaluate from left to right, so the last attribute wins. Boundary: Place overridable defaults before the spread; place locked values after the spread; when both must combine, extract the prop and concatenate.
    - Needs: attribute precedence (this answer), string concatenation with + (recall, Lecture 4), className (recall, Lecture 3).
    - Diagram: Attribute precedence: left to right overwrite order.
    - First sight: The scenario's code.

> [!PRINCIPLE]
> **Principle 4: Around a spread, the last attribute wins**
> JSX evaluates attributes from left to right through **attribute precedence**. When the same attribute appears more than once on an element, the last one written wins. An attribute placed before `{...rest}` serves as an overridable default that caller props replace. An attribute placed after `{...rest}` is an enforced value that replaces caller props. When both sides must contribute a class name, extract `className` and join both strings explicitly.
>
> >> attribute precedence : the left-to-right order where later JSX attributes overwrite earlier ones
>
> *It is best practice to do this:*
> `function Card({ className, children, ...rest }) {`
> `  const fullClass = 'card ' + className; // joins base with caller`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`
>
> *Instead of doing this:*
> `function Card({ children, ...rest }) {`
> `  return <div className="card" {...rest}>{children}</div>; // caller overwrites`
> `}`

- [question-cycle] Question 5: A default fills a prop the caller left out
    - Question: "What if the caller passes no `className`, or nothing between the tags?"
    - Code and result: With `className={'card ' + className}`, a caller omits `className`; DevTools displays `class="card undefined"`; when `<CardContainer />` renders with no children, the page shows an empty card frame with no content (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: Missing props evaluate to `undefined`; in JSX content, `{undefined}` renders an empty slot, but in string concatenation, `'card ' + undefined` produces the literal string `'card undefined'`; assigning a default parameter value in destructuring (`className = ''` and `children = <p>No items yet</p>`) replaces missing or `undefined` values with clean fallbacks.
    - Fix: Assign default parameter values in the parameter list: `function CardContainer({ children = <p>No items yet</p>, className = '', ...rest })`, taught in this answer.
    - Rule: Use default parameter values to fill missing props or slots. Boundary: Defaults engage strictly for `undefined` or omitted props, not for `null` or `false`.
    - Needs: default parameter value (recall, Lecture 6), null and undefined rendering (recall, Lecture 4).
    - Diagram: Parameter evaluation table showing default fallback engagement.
    - First sight: The scenario's code.

> [!PRINCIPLE]
> **Principle 5: A default fills a prop the caller left out**
> A missing prop evaluates to `undefined`. In JSX content, `undefined` renders an empty slot without printing text. But in string concatenation, `'card ' + undefined` coerces `undefined` into the text `'card undefined'`. Assign a **default parameter value** in the destructuring list to fill a missing prop: `className = ''`. Default parameter values engage only when a prop is missing or strictly `undefined`; they do not engage when a caller passes `null` or `false`.
>
> >> default parameter value : a fallback value assigned in destructuring when a prop is missing or undefined
>
> *We should do this:*
> `function Card({ className = '', children, ...rest }) {`
> `  const fullClass = 'card ' + className; // fallback prevents undefined`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`
>
> *We should not do this:*
> `function Card({ className, children, ...rest }) {`
> `  const fullClass = 'card ' + className; // produces card undefined`
> `  return <div className={fullClass} {...rest}>{children}</div>;`
> `}`

### Step 1: First, we construct the slot-based container component <CardContainer.jsx>

- [p] ★ Step 1 authors the foundational container component `CardContainer.jsx`: Instead of accepting specialized layout flags that dictate inner elements, `CardContainer` exposes an open slot by destructuring `children` from its parameter list. Notice how the parameter signature also unpacks `color = 'gray'` and `className = ''` with explicit default parameter values, while collecting all remaining pass-through attributes into `...rest`. The component calculates a merged CSS class string and forwards `...rest` onto the root `<div>`. ◼ Meaningful pedagogical commentary: architectural motivation of container slots, fallback defaults preventing undefined classes, safe attribute forwarding.

- [code] CardContainer.jsx:

```jsx title="CardContainer.jsx"
export default function CardContainer({
  children, color = 'gray', className = '', ...rest // unpacks slot
}) {
  const cls = `card card-${color} ${className}`.trim();
  return (
    <div className={cls} {...rest}> {/* forwards props to wrapper */}
      {children}
    </div>
  );
}
```

◼ **The what-this-introduces list:** 1. `children`: destructured prop receiving caller markup. 2. `color = 'gray'`: default theme parameter. 3. `className = ''`: default fallback preventing undefined string concatenation. 4. `...rest`: rest parameter gathering unconsumed attributes. 5. `{...rest}`: spread attribute forwarding remaining properties to the root `<div>`.

- [p] ★ Step 2 constructs the caller component `EditorialGrid.jsx`: When designing feeds that support multiple visual permutations, developers face an architectural crossroad: whether to use a monolithic card component loaded with specialized boolean flags, or use slot composition with `children` to let each call site compose its own markup. In `EditorialGrid`, we import `CardContainer` once and nest three entirely different layouts without touching `CardContainer.jsx`. One card nests an alert badge, headline, and summary; the second nests a headline and author; the third relies on default props while nesting a headline and notice. ◼ Meaningful pedagogical commentary: caller-driven slot composition, elimination of layout flags, inversion of control.

> **The Interview Question:** How do the children prop, spread attributes, and default values work?

- [interview] 1. The Hidden Signal ◼ The interviewer is probing your mastery of component composition architecture, compiler transformations, JavaScript rest and spread syntax, attribute precedence, and DOM attribute leakage. Junior developers explain props as HTML attributes. Senior engineers explain that JSX compiles nested tags into `props.children` (`_jsx(Card, { children: [...] })`), implementing inversion of control. They explain that pass-through wrappers destructure consumed props and forward `...rest` to prevent unknown-prop console warnings, that JSX evaluates attributes left to right, and that default parameters protect against `undefined` string coercion.
- [interview] 2. The Classic Trap ◼ One classic trap is assuming `children` is always an array. In React, `children` is an opaque data structure: a single child is an element object, multiple children form an array, and plain text is a string. Calling `children.map()` on a single nested child crashes with `TypeError: children.map is not a function`. Another trap is spreading full `props` onto a native element (`<div {...props}>`), which leaks component props to the DOM and triggers React warnings. A third trap is merging classes without default parameter fallbacks (`'card ' + className`), which renders `"card undefined"` in the DOM when the prop is omitted.
- [interview] 3. What is Actually Going On ◼ Under the hood, JSX converts nested tags into `props.children`. When React executes `CardContainer`, it passes this object as the first argument. If the container omits `{children}`, React renders the outer frame and drops the children; child functions never run, and their console logs remain silent. Around `{...rest}`, JSX applies attributes left to right: an attribute before `{...rest}` serves as an overridable default, while an attribute after `{...rest}` enforces a value. In destructuring, `className = ''` assigns an empty string when the prop is missing or `undefined`, preventing string coercion bugs while preserving valid values.
- [interview] 4. Where It Gets Tricky ◼ Where this gets tricky is handling collisions between custom props and native HTML attributes. If a component accepts `title="Night Trains"` as a data prop but blindly spreads all props onto a container `<div>`, that title becomes an unintended browser hover tooltip. If a boolean prop like `isFeatured={true}` spreads onto a `<div>`, React logs unknown attribute warnings. Another tricky nuance is that default parameters trigger strictly for `undefined` or omitted props; if a caller passes `className={null}` or `children={null}`, default parameter values do not engage, and `{null}` renders as an empty slot.

### Glossary

- [glossary] Children Prop ◼ A reserved React property that automatically receives any JSX elements or text passed between a component's opening and closing tags.
- [glossary] Container Component ◼ A reusable component that provides an outer visual frame while exposing an open slot for caller-provided content.
- [glossary] Slot Composition ◼ An architectural design pattern where a container component defines visual boundaries and leaves open slots for caller-provided content.
- [glossary] Inversion of Control ◼ A design principle where the calling component chooses what inner content to render, while the container decides where and how that content is framed.
- [glossary] Rest Syntax ◼ The JavaScript syntax using three dots in destructuring to collect unconsumed properties into a separate object.
- [glossary] JSX Spread Syntax ◼ A JSX syntax pattern using `{...props}` or `{...rest}` to forward an object of properties onto an underlying element.
- [glossary] DOM Attribute Leakage ◼ The unintended forwarding of non-standard component props onto native browser DOM elements, causing warnings and invalid attributes.

### Summary

- [review-title] Architectural Takeaways & Decision Matrix
- [review-subtitle] Slot Composition with Children
- [if-then-rule] IF a component acts as a reusable visual container, THEN place `{children}` in its return statement to allow callers to compose inner content freely.
- [if-then-rule] IF rendering received children, THEN treat `children` as an opaque descriptor and render it whole rather than calling array methods like `children.map()`.
- [review-subtitle] Controlled Prop Spreading
- [if-then-rule] IF a wrapper component forwards extra attributes to a native DOM element, THEN destructure consumed props and spread only `...rest` onto the element.
- [never-rule] IF a component accepts custom data props, THEN never spread the entire `props` object onto native DOM elements to prevent attribute leakage and console warnings.
- [review-subtitle] Attribute Precedence and Defaults
- [if-then-rule] IF specifying overridable defaults on a wrapper element, THEN place default attributes before `{...rest}` and enforced attributes after `{...rest}`.
- [if-then-rule] IF merging class names on a wrapper component, THEN assign a default parameter `className = ''` and combine the strings explicitly.

- [code] DO THIS: Compose inner layout with children and merge class names explicitly:

```jsx right
function CardContainer({
  children,
  color = "gray",
  className = "",
  ...rest
}) {
  const cls = `card card-${color} ${className}`.trim();
  return (
    <div className={cls} {...rest}>
      {children}
    </div>
  );
}
```

- [code] DO NOT DO THIS: Bloat containers with layout flags and spread unconsumed props:

```jsx wrong
function CardContainer(props) {
  return (
    <div className="card" {...props}>
      {props.children}
    </div>
  );
}
```
