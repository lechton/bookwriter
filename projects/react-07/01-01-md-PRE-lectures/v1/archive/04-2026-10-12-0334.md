### Placing raw variable identifiers inside markup renders literal text

- [p] ★ {preknowledge: HTML markup, component return statements, browser DOM} In traditional template engines, developers declare local variables and place their names directly into template placeholders, expecting the runtime engine to substitute values automatically. In React, a component is a JavaScript function returning JSX markup that compiles into in-memory element descriptors. When developers transition to React, they often assume that JSX scans text nodes for matching variable names in scope. You declare a local variable `const headline = "Night Trains Return to Europe";` and an image path `const avatarUrl = "/img/anna.jpg";`, type their names directly between heading tags and attribute quotes, and save the file. ◼ Educational objective: establish the familiar developer baseline and explain why newcomers expect plain identifiers to resolve automatically.

Beneath it, the author photo displays an empty broken-image icon while the browser console reports an HTTP network failure `GET http://localhost:5173/avatarUrl 404 (Not Found)`. The browser treated `"avatarUrl"` as a static relative URL path rather than reading the variable from JavaScript memory. Furthermore, when the developer tries to place a control-flow statement like `if` directly inside the markup to conditionally label long articles, the build compiler halts immediately with a fatal syntax error. Static JSX cannot read runtime variables without an explicit evaluation bridge. ◼ Educational objective: identify the concrete runtime defects (literal text, 404 network failure, compiler syntax error) caused by omitting curly braces.
- [p] ★ {old solution: naive literal text and quoted attribute anti-pattern} To see this failure in concrete code, examine how a developer attempts to use local variables directly inside markup:

- [code] Naive Literal JSX Anti-Pattern (verified in React 19.3.0: renders literal string "headline" and triggers 404 network failure on /avatarUrl):

```jsx title="Naive Literal JSX Anti-Pattern"
export default function ArticleCard() { // returns unbracketed markup
  const headline = "Night Trains Return"; // variable in local scope
  const avatarUrl = "/img/anna.jpg"; // author image path
  return (
    <article className="card">
      <h2>headline</h2> {/* renders literal text string "headline" */}
      <img src="avatarUrl" alt="Author" /> {/* browser requests /avatarUrl */}
    </article>
  );
}
```

Static JSX parsing: compiler mode treating all content outside curly braces as literal characters.

In markup mode, every character between tags and within attribute quotes is treated as literal character content. To step out of static markup and run live JavaScript, React provides an evaluation window marked by curly braces (`{}`). Placing curly braces in text content or directly after an attribute equals sign switches the compiler into JavaScript mode. The compiler evaluates the expression inside the braces and passes the resulting value to the element descriptor. ◼ Educational objective: contrast static markup mode with the inline JavaScript evaluation window provided by curly braces.

### Curly braces step out of static markup into JavaScript

- [p] ◇ {runway: curly braces as the evaluation window} Curly braces (`{}`) open an inline window from static JSX markup into live JavaScript execution. This evaluation window works in exactly two places: between tag content (such as `<h2>{headline}</h2>`), and directly after the equals sign in an attribute (such as `src={avatarUrl}`). Outside these two positions, curly braces cannot be used to name tags (writing `<{tag}>` halts compilation). Any text outside curly braces remains static literal characters. ◼ Educational objective: establish the two valid syntactic positions for curly braces in JSX.
- [p] ★ {runway: template literals and string concatenation} When constructing attribute strings from multiple dynamic pieces, developers cannot mix quotes and braces like `src="/img/{photoId}.jpg"`. In JSX, quotes treat everything inside as static text. To combine dynamic variables with static text, developers use a template literal enclosed in backticks inside a single pair of braces, such as `` src={`/img/${photoId}-${size}.jpg`} ``, or JavaScript string concatenation with the plus operator `+`. Inside the braces, standard JavaScript string rules apply. ◼ Educational objective: explain dynamic string assembly using template literals and concatenation within curly braces.
- [p] ★ {runway: comments in JSX content} In standard JavaScript files, developers write single-line comments with double slashes `//`. However, between JSX tags, characters outside curly braces are treated as literal text nodes. If a developer writes `// note` between tags, the browser renders the characters "// note" directly onto the page. To write a comment between JSX tags, the comment must be enclosed inside curly braces as `{/* note */}`, instructing the compiler to evaluate a JavaScript comment that emits zero output. ◼ Educational objective: explain why single-line comments print to the screen in JSX and demonstrate proper bracketed block comment syntax.

### Expressions produce values while statements perform actions

- [p] ★ {runway: expressions versus statements in ECMAScript grammar} In JavaScript grammar, code divides into expressions and statements. An expression is any piece of code that resolves to a single discrete value in memory. Numbers (`4 + 2`), variables (`headline`), template literals, ternary conditions, and function calls are all expressions. In contrast, a statement performs an action or controls execution flow without producing a value. Language statements include `if`, `for`, `while`, `switch`, and variable declarations (`const x = 1`). ◼ Educational objective: define the grammatical divide between value-producing expressions and control-flow statements.
- [p] ★ {runway: the _jsx function argument constraint} Because every JSX tag compiles into a `_jsx(type, props)` function call, any children or attributes written in curly braces become arguments passed into that function call. In JavaScript, function call arguments can only accept expressions. Attempting to pass a control-flow statement like `if` into a function argument, as in `_jsx("p", { children: if (admin) ... })`, is a fatal syntax error. To choose between values inside JSX braces, developers use the ternary conditional operator (`condition ? a : b`). When statements like `if` or `for` are necessary, they must be executed above the `return` statement, storing their result in a local variable that is passed into JSX. ◼ Educational objective: prove that compiler function argument grammar restricts curly braces to expressions and permits ternaries.

### React converts types to text nodes or invisible slots

- [p] ★ {runway: the primitive render matrix} When React renders JSX expressions to the DOM, it evaluates the runtime type of each expression to determine its screen representation. Strings and numbers evaluate directly into browser DOM text nodes (`{readTime}` prints "4", and `{0}` prints "0"). In contrast, the primitive values `true`, `false`, `null`, and `undefined` are treated as empty slots. React renders nothing to the DOM for these values. This design allows conditional rendering expressions without printing unwanted words like "false" or "undefined" onto the page. ◼ Educational objective: outline React's primitive render matrix and explain why booleans, null, and undefined emit zero DOM nodes.
- [p] ★ {runway: numbers, NaN, and string arrays} Numbers always print on screen, including zero (`0`). If an arithmetic operation produces `NaN`, React prints the characters "NaN" into the DOM and emits a console warning when `NaN` is a sole child. When an array of strings or numbers is passed as content, such as `{['Rail', 'Travel']}`, React flattens the array and renders the items concatenated side by side into the DOM without automatic spacing. ◼ Educational objective: explain the rendering behavior of numbers, zero, NaN, and flattened primitive arrays.

### Objects and functions require explicit conversion for content

- [p] ★ {runway: object literals and Date instances in content} In JavaScript, plain objects and `Date` instances are non-primitive data structures. If a developer attempts to place a raw object or `Date` instance directly into JSX content, such as `<p>{publishedAt}</p>`, React throws a fatal runtime exception: "Objects are not valid as a React child (found: [object Date])". React does not guess how an object should be formatted. To display data from an object or date, the developer must explicitly read a primitive property (`person.name`), call a formatting method (`publishedAt.toLocaleDateString('en-GB')`), or invoke a helper function. ◼ Educational objective: explain why objects and dates throw runtime errors in JSX children and demonstrate explicit string formatting.
- [p] ★ {runway: function references versus function calls} A function reference represents the function definition itself, while a function call invokes the code and returns its resulting value. If a developer places a bare function reference into JSX content, such as `<p>{formatReadTime}</p>`, React renders an empty paragraph and logs a console error: "Functions are not valid as a React child". To render the output of a function, the developer must call the function with parentheses, as in `<p>{formatReadTime(readTime)}</p>`, passing its return value to the JSX window. ◼ Educational objective: contrast bare function references with invoked function calls in JSX content.
- [p] ★ {runway: double curlies as object literals in attributes} In attributes like `style`, developers frequently encounter double curly braces: `<div style={{ color: 'pink', fontSize: 20 }}>`. The double curlies are not a special React operator. The outer pair of braces is the standard JSX evaluation window, stepping out of markup into JavaScript. The inner pair of braces is a standard JavaScript object literal `{ color: 'pink', fontSize: 20 }`. Writing `style={theme}` with an object variable `const theme = { color: 'pink' }` produces the exact same DOM styles. In content, double curlies like `<h2>{{headline}}</h2>` create an object literal `{ headline }`, which stops the render with an invalid child error. ◼ Educational objective: deconstruct double curly brace syntax into an outer JSX window and an inner JavaScript object literal.
- [p] ★ {runway: whitespace trimming across line breaks} The JSX compiler trims whitespace that includes line breaks at the start and end of text lines. If an expression and following text are split across separate lines, such as placing `{readTime}` on one line and `min read` on the next, the compiler strips the leading space, rendering `4min read` with words joined together. To preserve a space across line breaks, developers keep text and expressions on a single line or insert an explicit string space expression `{' '}`. ◼ Educational objective: explain compiler whitespace trimming across line breaks and demonstrate space preservation techniques.

### Principles of React: JavaScript Expressions in JSX with Curly Braces

- [p] ◇ When preparing for technical interviews, candidates must explain how JSX switches between static markup and dynamic JavaScript evaluation. In each question cycle below, the scenario presents concrete code, the bold question names the developer's uncertainty, the answer traces what the compiler and runtime execute, and the principle box formalizes that answer into an engineering rule. ◼ Educational objective: frame the eight upcoming question cycles and principle boxes.

- [question-cycle] Question 1: Curly braces evaluate variables while static tags print text
    - Question: "I wrote `<h2>headline</h2>`, and the card shows the word headline. How do I show what the variable holds?"
    - Code and result: `ArticleCard` renders `<h2>headline</h2>` beside `<h2>{headline}</h2>`; the screen shows "headline" for the first and "Night Trains Return to Europe" for the second; a `// check the read time later` line between tags appears on screen as text, while `{/* check the read time later */}` does not (verified in React 19.3.0).
    - Verdict: does not work.
    - Answer: the JSX compiler reads everything outside curly braces as static character text, translating `<h2>headline</h2>` into `_jsx("h2", { children: "headline" })`; inside curly braces it compiles JavaScript, translating `<h2>{headline}</h2>` into `_jsx("h2", { children: headline })`; curly braces open the evaluation window in content and after `=`; comments in content must be enclosed in `{/* */}`.
    - Fix: enclose the variable identifier in curly braces `<h2>{headline}</h2>`, and enclose comments in `{/* */}`.
    - Rule: Wrap variables in curly braces to open the JavaScript evaluation window. Boundary: Curly braces work only in tag content and attribute values after `=`; they cannot wrap tag names.
    - Needs: curly braces as evaluation window (runway), JSX comments (runway).
    - Diagram: Compiler parsing text mode outside braces versus JavaScript expression evaluation inside braces.

> [!PRINCIPLE]
> **Principle 1: Curly braces open JavaScript in two places, and everything else is text**
> Text outside curly braces is treated as static character content. The compiler translates unbracketed words directly into string literals, rendering the literal identifier name to the screen. To evaluate a JavaScript variable or expression, wrap the code in curly braces. Curly braces open an evaluation window in exactly two places: between tag content and immediately after an attribute equals sign.
>
> *We should do this:*
> `const title = "Night Trains";`
> `<h2>{title}</h2> {/* renders variable value */}`
>
> *We should not do this:*
> `const title = "Night Trains";`
> `<h2>title</h2> {/* renders literal text "title" */}`

- [p] ★ In our `ArticleCard` component, typing `<h2>headline</h2>` renders the literal word "headline" because the compiler parses content outside braces as static character text. Replacing that tag with `<h2>{headline}</h2>` instructs the compiler to emit `_jsx("h2", { children: headline })`, reading the variable from JavaScript memory and painting "Night Trains Return to Europe" into the DOM text node. ◼ Educational objective: prove Principle 1 on the lesson's code by contrasting unbracketed markup with evaluated expressions.

- [question-cycle] Question 2: Attributes take unquoted expressions or static string literals
    - Question: "`avatarUrl` holds the image path, and I wrote `src="avatarUrl"`. Why is the image broken?"
    - Code and result: three `<img>` tags in `ArticleCard` with `src="avatarUrl"`, `src="{avatarUrl}"`, and `src={avatarUrl}`; DevTools shows DOM attributes `src="avatarUrl"`, `src="{avatarUrl}"`, and `src="/img/anna.jpg"`; the first two trigger 404 network failures while the third loads successfully; `disabled="false"` leaves the button disabled and logs a console warning (verified in React 19.3.0).
    - Verdict: does not work.
    - Answer: a quoted attribute compiles to a static string literal, so `src="avatarUrl"` causes the browser to request the relative URL path `/avatarUrl`; curly braces placed inside quotes remain literal character tokens; unquoted curly braces directly following the equals sign (`src={avatarUrl}`) compile to the variable identifier, passing the resolved string `/img/anna.jpg` to the DOM property.
    - Fix: remove the quotes and write `src={avatarUrl}`; when building paths from multiple dynamic parts, use a template literal inside one pair of braces: `` src={`/img/${photoId}-${size}.jpg`} ``.
    - Rule: Pass dynamic attribute values using unquoted curly braces. Boundary: Use quotes only when passing a static, fixed string literal.
    - Needs: template literals in attributes (runway), quoted attribute compilation (runway).
    - Diagram: Quoted attribute emitting static URL string to network stack versus unquoted curly brace binding resolved memory path.

> [!PRINCIPLE]
> **Principle 2: An attribute takes a quoted string or one braced expression**
> In JSX, double quotes instruct the compiler to create a static string literal. Writing quotes around an attribute name passes that exact text to the DOM, causing the browser to request non-existent paths. To bind an attribute to a dynamic variable or expression, omit the quotes and wrap the expression in a single pair of curly braces directly after the equals sign.
>
> *We should do this:*
> `const avatar = "/img/anna.jpg";`
> `<img src={avatar} alt="Author" /> {/* loads image */}`
>
> *We should not do this:*
> `const avatar = "/img/anna.jpg";`
> `<img src="avatar" alt="Author" /> {/* requests 404 URL */}`

- [p] ★ In our `ArticleCard` component, writing `<img src="avatarUrl" />` emits a static string to the DOM, causing the browser to dispatch a network request for the relative path `/avatarUrl` and fail with a 404 error. Writing `<img src={avatarUrl} />` binds the memory variable directly to the `src` attribute, resolving to `/img/anna.jpg` and loading the author photograph cleanly. ◼ Educational objective: prove Principle 2 on the lesson's code by inspecting browser DOM attribute resolution and network requests.

- [question-cycle] Question 3: Braces evaluate expressions while statements belong above return
    - Question: "I want the card to say 'Long read' when `readTime` is over 10. Why does `{if (readTime > 10) 'Long read'}` break the build?"
    - Code and result: `ArticleCard` with `readTime = 4` attempts `<p>{if (readTime > 10) 'Long read'}</p>`; the build halts immediately; esbuild reports `Unexpected "if"`, and Babel reports `Unexpected token` (verified with esbuild 0.28.2 and @babel/parser 7.29.9).
    - Verdict: does not work.
    - Answer: JSX curly braces compile into argument positions of `_jsx()` function calls (`_jsx("p", { children: ... })`); in JavaScript grammar, function arguments can only accept expressions that resolve to values; `if` is a statement that performs control flow without producing a value; statements cannot be passed as function arguments.
    - Fix: use a ternary expression inside braces (`{readTime > 10 ? 'Long read' : 'Quick read'}`), or execute the `if` statement above the `return` statement and assign the resulting value to a local variable.
    - Rule: Place only value-producing expressions inside curly braces. Boundary: When complex branching requires control statements, execute them above the `return` statement.
    - Needs: expressions versus statements (runway), ternary operator (runway), `_jsx` argument grammar (runway).
    - Diagram: Function call argument position rejecting control statement versus accepting ternary expression.

> [!PRINCIPLE]
> **Principle 3: Braces hold one expression, and statements go above the return**
> JSX tags compile directly into JavaScript function calls where children become argument values. In ECMAScript grammar, function call argument slots accept only expressions that produce a value. Control-flow statements like `if`, `for`, or `while` produce no value and halt compilation. Use an inline ternary expression inside braces, or compute the value using statements above the return.
>
> *We should do this:*
> `const minutes = 4;`
> `<p>{minutes > 10 ? "Long" : "Quick"}</p> {/* ternary */}`
>
> *We should not do this:*
> `const minutes = 4;`
> `<p>{if (minutes > 10) "Long"}</p> {/* syntax error */}`

- [p] ★ In our `ArticleCard` component, attempting to write `{if (readTime > 10) 'Long read'}` halts the build compiler because the argument slot of `_jsx()` cannot accept an ECMAScript statement. Replacing the statement with a ternary expression `{readTime > 10 ? 'Long read' : 'Quick read'}` resolves cleanly to the string value "Quick read" when `readTime` is 4, passing the string into the element descriptor. ◼ Educational objective: prove Principle 3 on the lesson's code by contrasting failed statement compilation with working ternary evaluation.

- [question-cycle] Question 4: Embedded expressions run each time React renders the component
    - Question: "When does the code inside the braces run? If `headline` changes later, does the screen follow it?"
    - Code and result: `ArticleCard` calls `{formatReadTime(readTime)}`; the console shows "formatReadTime ran" once on mount without StrictMode and twice with StrictMode; storing `<h2>{headline}</h2>` in `const title` and reassigning `headline = "New Title"` after that line leaves "Night Trains Return to Europe" on screen (verified in React 19.3.0).
    - Verdict: works.
    - Answer: when React calls `ArticleCard`, the component function executes from top to bottom; each expression in curly braces runs once during that function call, evaluating its current value and placing it into the immutable React element descriptor; the element descriptor holds the evaluated value, not a reactive pointer to the variable; reassigning a variable after the JSX line has no effect on already-created descriptors; the next time React calls the component, the entire function runs again.
    - Fix: none.
    - Rule: Expressions evaluate synchronously during the component's render execution. Boundary: In this lesson, components use only local variables; dynamic state that re-executes components on user interaction belongs to Lecture 14 (`useState`).
    - Needs: render execution flow (runway), StrictMode double invocation (runway), immutable element descriptors (Lecture 3).
    - Diagram: Sequential component function execution evaluating expressions into immutable descriptor objects.

> [!PRINCIPLE]
> **Principle 4: The code in braces runs each time React renders the component**
> When React renders a component, it invokes the function from top to bottom. Each expression inside curly braces executes synchronously during that run, computing its value and storing it directly into the in-memory element descriptor. The rendered descriptor captures the value at that moment in time. Reassigning a local variable after creating an element does not update the screen.
>
> *We should do this:*
> `const title = "Night Trains";`
> `const card = <h2>{title}</h2>; {/* evaluates "Night Trains" */}`
> `return card; {/* descriptor holds frozen value */}`

- [p] ★ In our `ArticleCard` component, calling `{formatReadTime(readTime)}` proves that code inside curly braces runs during render. The console logs "formatReadTime ran" during component execution. Furthermore, if we assign `const title = <h2>{headline}</h2>;` and then reassign `headline = "Alps Sleeper Route"`, the screen continues to display "Night Trains Return to Europe" because the element descriptor froze the string value during evaluation. ◼ Educational objective: prove Principle 4 on the lesson's code by tracking render execution logs and testing variable reassignment.

- [question-cycle] Question 5: Content holes render invisible while strings and numbers paint text

> **Principle 5: Predict what content braces print from the value's type**

To display the text of a boolean on screen, convert it explicitly to a string or use a ternary expression.

- [question-cycle] Question 7: Double curly braces pass object literals into the evaluation window
    - Question: "What does `style={{ color: 'pink' }}` mean? Is `{{ }}` a special JSX form?"
    - Code and result: `ArticleCard` renders its headline with `style={{ color: 'pink', fontSize: 20 }}` and with `style={theme}` where `const theme = { color: 'pink', fontSize: 20 }`; DevTools shows both produce the exact same DOM attribute `style="color: pink; font-size: 20px;"`; rendering `<h2>{{headline}}</h2>` in content halts rendering with "Objects are not valid as a React child (found: object with keys {headline})" (verified in React 19.3.0).
    - Verdict: does not work.
    - Answer: double curly braces are not a special React operator or templating syntax; the outer pair of braces is the standard JSX evaluation window, and the inner pair is a standard JavaScript object literal `{ color: 'pink' }`; in attributes like `style` that expect an object, double curlies pass an inline object; in content, double curlies create an object literal, which crashes the render under the invalid child rule.
    - Fix: use a single pair of braces when printing a variable in content (`<h2>{headline}</h2>`); use double curlies only when an attribute explicitly expects a JavaScript object.
    - Rule: Double curlies represent a standard JavaScript object literal inside the JSX evaluation window. Boundary: Use double curlies only for attributes that accept objects (such as `style`), never for text content.
    - Needs: double curlies deconstruction (runway), inline style object properties (runway), object literal syntax (runway).
    - Diagram: Deconstruction of double curlies into outer JSX evaluation window and inner JavaScript object literal.

> [!PRINCIPLE]
> **Principle 7: Double curlies are an object inside the braces**
> The double curly brace syntax is not a special React operator. The outer pair of braces opens the standard JSX evaluation window, while the inner pair defines a standard JavaScript object literal. Attributes like `style` accept an object, making inline object literals convenient. Using double curlies in content creates an object in memory, triggering a fatal invalid child error.
>
> *We should do this:*
> `const title = "Night Trains";`
> `<h2>{title}</h2> {/* one pair prints variable value */}`
>
> *We should not do this:*
> `const title = "Night Trains";`
> `<h2>{{title}}</h2> {/* passes object, stops render */}`

- [p] ★ In our `ArticleCard` component, writing `<h2 style={{ color: 'pink', fontSize: 20 }}>{headline}</h2>` demonstrates how inline styles work. The outer braces step into JavaScript, and the inner braces define a JavaScript object mapping CSS properties in camelCase to values. Furthermore, writing `<h2>{{headline}}</h2>` proves that double curlies simply create an object `{ headline: "Night Trains..." }`, crashing the render because objects cannot be placed directly into content. ◼ Educational objective: prove Principle 7 on the lesson's code by deconstructing double curlies in attributes and content.

- [question-cycle] Question 8: Whitespace with line breaks trims unless protected by space expressions
    - Question: "I put `{readTime}` and `min read` on two lines to keep the code short. Why does the card show `4min read`?"
    - Code and result: `ArticleCard` renders `{readTime} min read` on one line (displays "4 min read"); then split over two lines (displays "4min read"); then with `{' '}` inserted (displays "4 min read") (verified in React 19.3.0).
    - Verdict: does not work.
    - Answer: the JSX compiler removes whitespace that contains a line break at the start and end of each line of text; when text is placed on a new line immediately following an expression, the leading indentation and line break are stripped, causing the text to concatenate directly against the expression value; spaces within a single line are preserved; inserting an explicit space expression `{' '}` preserves the space.
    - Fix: keep the expression and text on a single line (`{readTime} min read`), or add an explicit string space expression `{' '}` at the line break.
    - Rule: Keep expressions and following text on a single line, or use an explicit space expression to prevent word collision across line breaks. Boundary: Whitespace inside a single line is preserved automatically.
    - Needs: JSX whitespace trimming rules (runway), explicit space token `{' '}` (runway).
    - Diagram: Compiler stripping line-break whitespace versus preserving explicit string space tokens.

> [!PRINCIPLE]
> **Principle 8: A line break between text and braces removes the space**
> The JSX compiler strips whitespace that contains line breaks at the beginning and end of text lines. When an expression and following text are placed on separate lines, the separating space is removed, joining the text directly against the evaluated value. To preserve a space across line breaks, keep the text on a single line or insert an explicit string space expression.
>
> *We should do this:*
> `const minutes = 4;`
> `<p>{minutes} min read</p> {/* one line keeps space */}`
>
> *We should not do this:*
> `const minutes = 4;`
> `<p>`
> `  {minutes}`
> `  min read {/* line break removes space: 4min read */}`
> `</p>`

- [p] ★ In our `ArticleCard` component, splitting `{readTime}` and `min read` across separate lines renders as "4min read" because the JSX compiler strips line-break whitespace. Keeping `{readTime} min read` on a single line or writing `{readTime}{' '}min read` guarantees that the separating space survives compilation and renders cleanly in the browser DOM. ◼ Educational objective: prove Principle 8 on the lesson's code by observing line-break whitespace trimming and testing space preservation.

### For the interview

> **The Interview Question:** How do you use JavaScript expressions inside JSX with curly braces?

**1. The Hidden Signal**

The interviewer is not merely checking if you know where to type curly braces. They are probing your understanding of ECMAScript compiler grammar, the difference between expressions and statements, and how React processes different data types during render. A junior developer says curly braces are "for inserting variables into HTML." A senior engineer explains that curly braces establish an evaluation window in content and attributes where expressions become arguments to `_jsx()` function calls, evaluating synchronously during render.

**2. The Classic Trap**

The classic trap is attempting to write control-flow statements like `if` or `for` inside curly braces (`{if (active) ...}`). Candidates often forget that JSX compiles into JavaScript function arguments, which grammatically reject control statements. Another frequent trap is quoting dynamic attributes (`src="{avatarUrl}"`), which emits literal strings and triggers network 404 errors, or passing raw objects and `Date` instances into content, causing fatal runtime crashes.

**3. What is Actually Going On**

Under the hood, the JSX compiler treats everything outside curly braces as static text. When it encounters `{`, it steps into JavaScript evaluation mode. The expression inside is evaluated once when the component function executes, and its result is placed into the React element descriptor. React's primitive render matrix translates strings and numbers into DOM text nodes, while treating booleans, `null`, and `undefined` as empty slots that emit zero DOM nodes. Non-primitive objects and `Date` instances stop the render with an error, requiring explicit formatting. Double curlies (`style={{}}`) are simply an outer JSX evaluation window enclosing an inner JavaScript object literal.

**4. Where It Gets Tricky**

Where this gets tricky in production is whitespace handling and boolean zeros. In JSX, line breaks strip surrounding whitespace, causing `{readTime}` and `min read` on separate lines to render as `4min read` unless an explicit `{' '}` token is added. Additionally, while `false` renders nothing, the number `0` renders visibly, meaning `{count && <Badge />}` displays a visible "0" when `count` is zero, a common defect explored further in Lecture 10.

### Glossary

- **JSX Evaluation Window**: The syntactic zone opened by curly braces (`{}`) in content or attributes that switches the compiler from static markup to live JavaScript execution.
- **Expression**: An ECMAScript code unit that evaluates to a discrete value in memory (such as variables, math operations, ternaries, and function calls) and can be passed into JSX braces.
- **Statement**: An ECMAScript code unit that controls execution flow or performs actions without producing a value (such as `if`, `for`, `while`, or `const`) and is forbidden inside JSX braces.
- **Primitive Render Matrix**: React's internal type-routing rules that paint strings and numbers as DOM text nodes while rendering booleans, `null`, and `undefined` as empty slots.
- **Empty Slot**: An invisible DOM placeholder emitted when React encounters booleans, `null`, or `undefined` in child content, emitting zero DOM nodes.
- **Double Curlies**: A syntactic combination where an outer pair of JSX curly braces encloses an inner JavaScript object literal, commonly used in inline `style` props.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ The JSX Evaluation Window Invariant

➔ IF projecting dynamic values into content or attribute positions, THEN wrap variables and expressions in curly braces (`{}`) to open the evaluation window.

➔ IF authoring text outside curly braces, THEN treat it as static character content because the compiler does not evaluate unbracketed identifiers.

❒ Dynamic Attribute Binding

➔ IF binding an attribute to a dynamic JavaScript value, THEN use unquoted curly braces (`src={avatarUrl}`).

➔ IF passing a static, unchanging string literal, THEN use quotes (`alt="Author"`), avoiding curly braces inside quotes which remain literal characters.

❒ Expressions Versus Statements

➔ IF evaluating logic inside JSX curly braces, THEN use value-producing expressions (variables, math, ternaries, function calls).

➔ IF control flow requires statements (`if`, `for`, `while`), THEN execute them above the `return` statement and pass the resulting value into JSX.

❒ Primitive Render Matrix and Object Content

➔ IF displaying dates or objects in JSX child content, THEN format them into primitive strings or numbers before placing them inside curly braces.

➔ IF passing an object to an element, THEN do so only for attributes that accept objects (such as `style`), avoiding objects in content which crash the render.

**DO THIS:** evaluate variables in curly braces, use unquoted attributes, and format objects into strings

```jsx right
function ArticleCard() {
  const title = "Night Trains";
  const avatar = "/img/anna.jpg";
  const readTime = 4;
  return (
    <article className="card">
      <img src={avatar} alt="Author" />
      <h2>{title}</h2>
      <p>{readTime} min read</p>
    </article>
  );
}
```

**DO NOT DO THIS:** leave identifiers unbracketed, quote dynamic attributes, or put statements in content

```jsx wrong
function ArticleCard() {
  const title = "Night Trains";
  const avatar = "/img/anna.jpg";
  const readTime = 4;
  return (
    <article className="card">
      <img src="avatar" alt="Author" />
      <h2>title</h2>
      <p>{if (readTime > 10) "Long"}</p>
    </article>
  );
}
```
