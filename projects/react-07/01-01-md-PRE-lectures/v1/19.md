### The item list changes in memory, but the screen stays frozen

- [p] ◇ {theme: immutable state arrays in React} In modern web applications, user interfaces frequently manage collections of data. Applications display lists of tasks, shopping cart items, user messages, and incoming notifications. In plain JavaScript, developers modify arrays directly in memory using mutating methods like `push`, `splice`, and `sort`. When an array is stored in React state, this habit breaks application reactivity. In JavaScript, an array is an object, so React compares state values by memory reference using `Object.is`. When an event handler mutates an array in place and hands it back to the setter, React sees the exact same memory address and aborts rendering. To update the screen reliably, every array operation must construct a brand-new array and pass that new container to the setter function. ◼ Educational objective: introduce the immutable state array paradigm and explain why mutating methods fail to trigger screen updates.

- [p] ◇ {starting point: array mutation habits from plain JavaScript versus React reference equality} When engineers transition from plain JavaScript scripting to React, they naturally reach for standard array methods like `arr.splice()` to delete an element or `arr.push()` to append a record. In vanilla scripts, these methods modify memory in place, and the next line of code sees the modified array immediately. In React, application memory lives outside the component function, and state updates occur through declarative reconciliation. Calling `items.splice(1, 1)` deletes the element from computer memory, but calling `setItems(items)` hands React the exact same array reference it already holds. Because `Object.is(previousArray, nextArray)` evaluates to true, React assumes nothing changed and skips the render phase. Furthermore, developers who copy the array using spread syntax often mistakenly assign directly to properties of items inside the copy, unaware that shallow copying shares nested object references with previous render snapshots. ◼ Educational objective: contrast imperative array mutation with declarative reference equality and expose the shallow copy pitfall.

### How mutating array methods skip React re-renders

- [runway] In-place array mutation methods (splice, push, sort, reverse) vs copying methods (slice, filter, map, concat, toSorted), used by Question 1 and Question 4.

- [p] ★ {preknowledge: arrays as objects and Object.is comparison} In Lecture 18, we discovered that JavaScript objects are compared by reference. When an event handler mutates an object's properties directly and calls the setter, `Object.is` finds identical references and React skips the render. Because JavaScript arrays are standard objects under the hood, array state operates under the exact same reference equality invariant. ◼ Educational objective: connect array state behavior directly to Lecture 18's Object.is reference model.

- [p] ★ {mechanism: in-place array mutation vs copying methods} In JavaScript, array methods divide into two distinct categories: mutating methods that alter the array in place, and non-mutating methods that return a fresh array. Mutating methods include `push`, `pop`, `shift`, `unshift`, `splice`, `sort`, and `reverse`, as well as direct index assignment (`arr[0] = value`). When you execute any of these methods on a state array, JavaScript alters the existing array in memory. Passing that mutated array to the state setter gives React the same object reference it already holds. React detects zero reference difference and skips rendering. Conversely, copying methods like `slice`, `filter`, `map`, `concat`, `toSorted`, `toReversed`, and `toSpliced` generate a brand-new array in memory. Passing the new array to the setter allows `Object.is` to detect a distinct reference, scheduling a clean render pass. ◼ Educational objective: categorize JavaScript array methods into mutating vs non-mutating groups and explain the engine rendering consequence.

- [code] In-place mutation versus non-mutating array operations:

```jsx title="Mutating Versus Copying Array Methods"
const items = [{ id: 1, title: 'First' }, { id: 2, title: 'Second' }];

// Mutating in place: modifies array in memory, returns removed elements
const removed = items.splice(1, 1); // items is still same array in memory

// Non-mutating copy: leaves original intact, returns new array
const filtered = items.filter(item => item.id !== 2); // brand-new array
```

◼ **The what-this-introduces list:** 1. `splice`: mutating array method removing elements in place. 2. `filter`: non-mutating array method returning a fresh filtered array. 3. `reference identity`: memory pointer checked by `Object.is`.

### How array spread creates new arrays for additions and insertions

- [runway] Array spread syntax for appending, prepending, and inserting with slice, used by Question 2 and Question 3.

- [p] ★ {preknowledge: spreading objects from Lecture 18} In Lecture 18, we used object spread syntax `{ ...obj }` to create a shallow copy of an object while updating selected properties. JavaScript provides identical spread syntax for arrays: writing `[...arr]` unpacks the elements of an existing array into a fresh array literal. ◼ Educational objective: recall object spread from Lecture 18 and introduce array spread syntax.

- [p] ★ {mechanism: array spread syntax and slicing boundaries} When adding an item to state, developers often intuitively write `setItems(items.push(newItem))`. However, native `push()` mutates the array and returns the array's new length as an integer. Passing this call to the setter stores a number in state, causing the next render pass to crash when it attempts to call `items.map()`. To add items cleanly, use array spread. To append at the end, write `[...items, newItem]`. To prepend at the start, write `[newItem, ...items]`. To insert an item at index `i`, combine spread syntax with native `slice()`: write `[...items.slice(0, i), newItem, ...items.slice(i)]`. The `slice()` method returns a shallow copy of a portion of an array without modifying the original, creating a seamless insertion bridge. ◼ Educational objective: derive array spread addition, explain why push returns a number, and teach the slice insertion pattern.

- [code] Array spread addition and insertion patterns:

```jsx title="Array Spread Addition and Insertion"
const items = [{ id: 1, text: 'A' }, { id: 3, text: 'C' }];
const newItem = { id: 2, text: 'B' };

// Appending at the end
const appended = [...items, newItem]; // [A, C, B]

// Inserting at index 1 between A and C
const inserted = [...items.slice(0, 1), newItem, ...items.slice(1)];
```

◼ **The what-this-introduces list:** 1. `array spread`: unpacks elements into a new array literal. 2. `slice`: non-mutating method extracting an array segment. 3. `insertion recipe`: combining two slice calls with an inserted element.

### Why copying an array leaves its nested objects shared

- [runway] Shallow array copying, shared object references, and mapping with object spread, used by Question 5.

- [p] ★ {preknowledge: nested object references from Lecture 18} In Lecture 18, we learned that copying an object with `{ ...user }` performs a shallow copy: top-level primitive properties are duplicated, but nested objects continue pointing to their original memory addresses. Mutating a nested property on a copied object damages earlier render snapshots and corrupts reset baselines. ◼ Educational objective: recall shallow copy mechanics and shared nested references from Lecture 18.

- [p] ★ {mechanism: shallow array copies and item replacement with map} When an array contains objects, spreading that array with `[...items]` produces a new array container, but the elements inside that new container are identical object references. If a developer writes `const next = [...items]; next[0].done = true;`, the assignment mutates the shared object in memory. While `next` is a new array container that triggers a re-render, the underlying item object was mutated in place. Any earlier render snapshots, cached records, or baseline constants like `initialItems` now reflect the mutation, permanently corrupting the Reset button. To update an item safely, use `map()`: iterate through the array, check if `item.id === targetId`, and return a new object using object spread `{ ...item, done: true }` for the target while returning unchanged items as they are. ◼ Educational objective: deconstruct shallow array copying, demonstrate shared reference corruption, and derive the map replacement recipe.

- [code] Updating nested items using map and object spread:

```jsx title="Replacing Items with Map and Object Spread"
const items = [{ id: 1, title: 'Draft', done: false }];

// SAFE: returns a new array with a new object for item 1
const updated = items.map(item =>
  item.id === 1 ? { ...item, done: true } : item
); // original item in items remains completely unchanged
```

◼ **The what-this-introduces list:** 1. `shallow array copy`: new array containing identical object pointers. 2. `map update`: transforming target item into a fresh object copy. 3. `snapshot preservation`: keeping original item objects immutable.

### Principles of React: Updating Arrays in State

- [question-cycle] Question 1: Calling splice on a state array leaves the screen unchanged
    - Question: "I call `items.splice(1, 1)` and then `setItems(items)`. Why does the deleted item stay on screen?"
    - Code and result: Inside `TaskManager`, a developer attaches a click handler to a "Delete typo" button: `items.splice(1, 1); setItems(items);`. When clicked, the development console logs zero render passes, and the screen continues displaying three items. When the user later clicks an unrelated counter button, the component renders and the second item suddenly vanishes (React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: In plain JavaScript, calling `items.splice(1, 1)` removes one item from the array in place. In React, `items` points to the array instance currently stored in state. Calling `splice` mutates that array in memory. Passing `items` to `setItems(items)` hands React the exact same array reference it already holds. React compares previous state and next state using `Object.is(previous, next)`. Because both variables point to the identical array in memory, `Object.is` returns `true`, and React skips the render. The screen keeps showing three items. When an unrelated button triggers a re-render later, React reads the mutated array and finally displays two items, proving that memory changed while reactivity failed.
    - Fix: Do not mutate the array in place. Replace it with a new array constructed using `filter`: `setItems(items.filter(item => item.id !== id));`. Taught in runway "How mutating array methods skip React re-renders" and Principle 2.
    - Rule with boundary: The setter skips rendering when it receives the same array reference; every state update must provide a newly created array. Boundary: local arrays created inside an event handler may be mutated with `splice` before passing them to the setter.
    - Needs: `Object.is` (recall, Lecture 18), mutating methods (runway), array reference identity (runway).
    - Diagram: ASCII diagram showing `items.splice(1, 1)` mutating the existing array in memory -> `setItems(items)` passing identical reference -> `Object.is` returning `true` -> React skipping render.

> [!PRINCIPLE]
> **Principle 1: The setter skips the render when it gets the same array**
> React checks whether state changed by comparing references with `Object.is`. Methods like `splice`, `push`, and `sort` modify an array in place, so passing the same array back to the setter gives React the exact reference it already holds. Because `Object.is` finds no difference, React skips running the component and the screen keeps showing the old list. To trigger a screen update, your code must provide a newly created array.
>
> >> Object.is : the JavaScript comparison method React uses to check if state changed
>
> *We should do this:*
> `const nextItems = items.filter(item => item.id !== 2); // new array`
> `setItems(nextItems); // React renders the new list`
>
> *We should not do this:*
> `items.splice(1, 1); // modifies array in place`
> `setItems(items); // same array, React skips render`

- [question-cycle] Question 2: Calling slice instead of splice empties the list
    - Question: "How do I delete an item without mutating the array in place?"
    - Code and result: Inside `TaskManager`, a developer replaces `splice(1, 1)` with `slice(1, 1)`: `setItems(items.slice(1, 1));`. When clicked, React executes a render pass, but the entire task list disappears from the screen, leaving an empty container (React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: The developer assumes `slice` is simply the non-mutating version of `splice`. But `slice` accepts a starting index and an ending index, returning elements between them. Calling `slice(1, 1)` asks for elements starting at index 1 up to (but not including) index 1, which extracts zero items. The setter receives an empty array `[]`, causing the entire list to vanish from the screen. To remove an item cleanly, use `filter`. Calling `items.filter(item => item.id !== targetId)` produces a fresh array containing every item whose id does not match. Because `filter` tests items rather than slicing boundaries, it works regardless of array position.
    - Fix: Remove the item using `filter` based on its identifier: `setItems(items.filter(item => item.id !== id));`. Taught in runway "How mutating array methods skip React re-renders".
    - Rule with boundary: Remove elements from a state array using `filter` to generate a new array without the target item. Boundary: if a fresh array was already cloned with `[...items]`, mutating that local clone with `splice` before passing it to the setter is completely safe.
    - Needs: `filter` (recall, Lecture 11), `slice` parameter indexing (runway).
    - Diagram: ASCII diagram contrasting `slice(1, 1)` extracting 0 items resulting in `[]` versus `filter(item => item.id !== 2)` retaining non-matching items in a new array.

> [!PRINCIPLE]
> **Principle 2: Remove with filter, which returns a new array**
> Do not remove items with `splice`, which mutates the array in place, and do not confuse `splice` with `slice`, which extracts a range between two index boundaries. To remove an item from state, call `filter` on the array. The `filter` method evaluates a test function for each element and returns a brand-new array holding only the items that pass.
>
> >> filter : an array method that returns a new array with all elements that pass a test
>
> *We should do this:*
> `const nextItems = items.filter(item => item.id !== 2); // keeps all except id 2`
> `setItems(nextItems); // screen removes item 2`
>
> *We should not do this:*
> `const nextItems = items.slice(1, 1); // returns an empty array []`
> `setItems(nextItems); // empties the entire list on screen`

- [question-cycle] Question 3: Calling push inside the setter crashes the next render
    - Question: "A new item arrives. How do I add it to the end, start, or middle of the list?"
    - Code and result: Inside `TaskManager`, a developer writes `setItems(items.push(newItem));`. When clicked, the application immediately crashes with `TypeError: items.map is not a function`, and React unmounts the component tree from the page (React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: In JavaScript, `push()` mutates the array in place and returns the array's new length as a number. In a 3-item array, `items.push(newItem)` returns the number `4`. Calling `setItems(items.push(newItem))` passes `4` to the setter. React stores `4` as the new state value and initiates a render pass. During render, the JSX executes `items.map(...)`. Because numbers do not possess a `map` method, JavaScript throws a `TypeError` and crashes the application. To add elements safely, use array spread syntax `[...items, newItem]`. To prepend at the beginning, write `[newItem, ...items]`. To insert an item between existing elements at index `i`, combine spread with `slice`: `[...items.slice(0, i), newItem, ...items.slice(i)]`.
    - Fix: Create a new array using spread syntax: `setItems([...items, newItem]);`. Taught in runway "How array spread creates new arrays for additions and insertions".
    - Rule with boundary: Add elements by spreading the existing array into a new array literal with the new item placed at the target position. Boundary: if a handler creates a local array using `const next = [...items]`, calling `next.push(newItem)` on that local variable before calling `setItems(next)` is valid.
    - Needs: array spread syntax (runway), `slice` insertion pattern (runway), `push` return value (runway).
    - Diagram: ASCII diagram illustrating `items.push(item)` returning integer 4 -> crashing `items.map` vs `[...items, newItem]` returning a fresh 4-item array.

> [!PRINCIPLE]
> **Principle 3: Add and insert with spread**
> Calling `push` on an array modifies it in place and returns its new length as a number. Passing `items.push(newItem)` to a setter stores a number in state, crashing the next render when the code calls `items.map`. To add an item, spread the existing array into a new array literal with the new element at the end, at the start, or between two `slice` calls to insert at an index.
>
> >> spread syntax : the ... operator that copies elements from an existing array into a new array
>
> *We should do this:*
> `const nextItems = [...items, newItem]; // copies items and appends new item`
> `setItems(nextItems); // screen shows updated list`
>
> *We should not do this:*
> `setItems(items.push(newItem)); // returns array length number, not array`
> `// next render crashes: items.map is not a function`

- [question-cycle] Question 4: Calling sort directly on state keeps the previous order
    - Question: "I want to sort the list. Can I write `setItems(items.sort(compareFn))`?"
    - Code and result: Inside `TaskManager`, a developer creates a "Sort by time" button: `setItems(items.sort((a, b) => a.time - b.time));`. When clicked, the console logs zero render passes and the task items remain in their original order on screen. Clicking an unrelated counter button causes the list to suddenly reorder on screen (React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: Unlike methods that return numbers, `sort()` reorders the array in place and returns that exact same array reference. Writing `setItems(items.sort(...))` passes the existing state array back to the setter. React compares the previous state reference with the next state reference using `Object.is`. Because the references match identically, React skips rendering. The screen remains frozen in the old order. When an unrelated state update triggers a re-render later, React reads the mutated array and updates the display. Furthermore, because the initial array constant was sorted in place, clicking Reset keeps the sorted order instead of restoring the original order. To sort correctly, create a copy first: `[...items].sort(compareFn)` or use the modern non-mutating method `items.toSorted(compareFn)`.
    - Fix: Sort a copied array or use `toSorted`: `setItems(items.toSorted((a, b) => a.time - b.time));`. Taught in runway "How mutating array methods skip React re-renders".
    - Rule with boundary: Always sort or reverse a copy of the state array, never the array reference held in state. Boundary: if a sorted list is needed solely for display and does not represent independent state, compute the sorted copy during render without storing it in state (deferred to Lecture 22).
    - Needs: `sort` in-place behavior (runway), `toSorted` non-mutating alternative (runway).
    - Diagram: ASCII diagram comparing `items.sort()` mutating the array reference in place vs `items.toSorted()` returning a fresh sorted array container.

> [!PRINCIPLE]
> **Principle 4: Sort a copy, never the array in state**
> The JavaScript `sort` and `reverse` methods reorder elements in place and return the same array reference. Passing `items.sort()` to a setter hands React the array it already holds, so `Object.is` skips the render and the screen keeps the old order. To reorder items in state, sort a fresh copy using `[...items].sort()` or call the non-mutating method `items.toSorted()`.
>
> >> toSorted : a JavaScript method that returns a new array sorted by a comparison function
>
> *We should do this:*
> `const nextItems = items.toSorted((a, b) => a.time - b.time); // new sorted array`
> `setItems(nextItems); // React renders sorted items`
>
> *We should not do this:*
> `setItems(items.sort((a, b) => a.time - b.time)); // reorders in place`
> `// same array reference, React skips render`

- [question-cycle] Question 5: Modifying an item in a copied array corrupts earlier renders
    - Question: "I copied the array first, then updated an item in the copy. Why does Reset fail?"
    - Code and result: Inside `TaskManager`, a developer clones the array with `const next = [...items]` and updates item 2: `next[1].title = 'Corrected'; setItems(next);`. When clicked, React renders and the screen displays "Corrected". However, when the user subsequently clicks a Reset button that calls `setTasks(initialTasks)`, the screen continues displaying "Corrected" instead of restoring the original typo title (React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: Array spread `[...items]` creates a shallow copy: it builds a new array container, but every element inside that container is the identical object reference from the original array. In memory, `next[1]` and `items[1]` point to the exact same object, which is also referenced by the module-level constant `initialTasks[1]`. Writing `next[1].title = 'Corrected'` mutates that shared object directly. Because `next` is a new array container, `Object.is` triggers a render, giving the illusion that the update succeeded. But the mutation permanently altered the object shared by `initialTasks` and past render snapshots. Clicking Reset passes `initialTasks`, but `initialTasks[1]` already holds the mutated title. To update an item safely, use `map()`: return a new object with object spread `{ ...item, title: 'Corrected' }` for the matching item, leaving all other items untouched.
    - Fix: Update the item using `map` and object spread: `setItems(items.map(item => item.id === id ? { ...item, title: 'Corrected' } : item));`. Taught in runway "Why copying an array leaves its nested objects shared".
    - Rule with boundary: When updating an item inside an array, construct a new object for that item using `map` and object spread; never mutate an item reference directly inside a shallow copied array. Boundary: newly created objects that have never been stored in state or rendered may be mutated before passing to the setter.
    - Needs: shallow copy references (runway), `map` item replacement (runway), object spread (recall, Lecture 18).
    - Diagram: ASCII diagram illustrating a shallow array copy pointing to shared item objects in memory vs `map` with `{ ...item }` isolating the edited item in a new object.

> [!PRINCIPLE]
> **Principle 5: To change one item, copy that item too**
> Spreading an array with `[...items]` creates a new array container, but the objects inside remain shared references in memory. To update an item safely, call `map` to produce a new array, and return a new object using object spread for the item you want to change.
>
> >> shallow copy : an array copy where nested objects continue sharing the same memory references
>
> *We should do this:*
> `const nextItems = items.map(item =>`
> `  item.id === 2 ? { ...item, title: 'Fixed' } : item`
> `); // creates a new object for item 2`
> `setItems(nextItems); // screen updates and Reset works`
>
> *We should not do this:*
> `const nextItems = [...items]; // new array container`

```jsx title="TaskManager.jsx" startLine="21" continues="both"
  }
  function handleCorrect(id, title) {
    setTasks(tasks.map(t =>
      t.id === id ? { ...t, title } : t
    )); // Object copy in mapped array
  }
```

◼ **The what-this-introduces list:** 1. `handleSort`: non-mutating reorder handler. 2. `handleCorrect`: item replacement handler using `map`.

### Where you will meet this

- [p] In production frontend applications, updating arrays in state is universal across todo lists, shopping carts, notification feeds, and kanban boards. A frequent production bug arises when an engineer uses `splice` to delete an item from an active cart, causing the UI to freeze until an unrelated state change triggers a re-render. Adopting `filter` permanently prevents this defect.

- [p] Another universal scenario involves sorting tabular data or transaction histories. Developers who call `.sort()` directly on state arrays inadvertently mutate shared memory, scrambling cached datasets and preventing users from restoring original chronological sorting. Using `toSorted()` or `[...items].sort()` guarantees clean reordering without data pollution.

- [p] In technical interviews, engineering candidates are routinely asked how to update arrays in state without mutating them. Interviewers specifically probe whether candidates understand why `push` fails inside setters, why `slice` is not the copying equivalent of `splice`, and why copying an array still requires mapping objects inside it with `{ ...item }`.

### For the interview

- [interview] The Interview Question: How do you add, remove, insert, and reorder items in a state array?

- [p] **1. The Hidden Signal**: The interviewer is evaluating whether you understand JavaScript reference equality and React reconciliation mechanics. Junior developers view arrays as simple lists to be edited with imperative methods like `push` and `splice`. Senior engineers recognize that state arrays are immutable objects compared by reference using `Object.is`, requiring non-mutating operations that generate new array containers.

- [p] **2. The Classic Trap**: The most common trap is assuming that copying an array with spread syntax `const next = [...items]` makes it completely safe to mutate its elements. Candidates write `next[0].title = 'Updated'`, unaware that spreading creates a shallow copy where nested objects remain identical references. When asked why their Reset button no longer works, unprepared candidates cannot identify the shared reference leak.

- [p] **3. What is Actually Going On**: React checks whether state changed by comparing references with `Object.is`. Methods like `splice`, `push`, `sort`, and `reverse` modify the array in place, returning either the same array reference or an unintended value (such as the new length integer returned by `push`). Because the array reference never changes, React skips the render phase. To trigger a render, you must produce a new array container: `filter` for removal, array spread `[...items, newItem]` for additions, `slice` combined with spread for insertions, and `toSorted()` or `[...items].sort()` for reordering.

- [p] **4. Where It Gets Tricky**: What about updating one object inside an array? Because array spread is shallow, updating an item requires calling `items.map()`, checking for the target item identifier, and returning a new object using object spread `{ ...item, prop: value }` while returning untouched items as they are. When nested updates become complex or deeply nested, teams often introduce Immer to write update logic concisely while preserving structural immutability behind the scenes.

### Glossary

- [glossary] Immutable Array ◼ An array treated as read-only in state, updated exclusively by creating fresh array containers rather than altering memory in place.
- [glossary] `filter` ◼ A non-mutating JavaScript array method that returns a new array containing all elements that satisfy a predicate function.
- [glossary] Array Spread ◼ The JavaScript `...` syntax that unpacks elements of an existing array into a fresh array literal, enabling safe additions and shallow copies.
- [glossary] `toSorted` ◼ A modern non-mutating JavaScript array method that returns a brand-new sorted array without modifying the original array in place.
- [glossary] Shallow Copy ◼ A duplicated array container whose internal elements continue pointing to the identical memory references of the original collection.

### Summary

- [review-title] **Architectural Takeaways & Decision Matrix**

- [review-subtitle] ❒ Immutable Array Transitions

- [always-rule] ➔ ALWAYS treat state arrays as read-only collections by constructing fresh array containers for every state transition.

- [never-rule] ➔ NEVER call mutating array methods like `splice`, `push`, `sort`, or `reverse` directly on a state array.

- [if-then-rule] ➔ IF you need to remove an item from an array in state THEN use `filter` with the item identifier instead of `splice`.

- [if-then-rule] ➔ IF you need to add an item to an array in state THEN spread the existing array into a new literal with the new element.

- [if-then-rule] ➔ IF you need to reorder an array in state THEN sort a shallow copy or call `toSorted` to avoid in-place mutation.

- [if-then-rule] ➔ IF you need to update an item inside an array THEN use `map` and return a new object with object spread for the target item.

- [code] DO THIS: remove with filter and add with array spread
```jsx right
function handleRemove(id) {
  setItems(items.filter(item => item.id !== id));
}
function handleAdd(newItem) {
  setItems([...items, newItem]);
}
```

- [code] DO NOT DO THIS: mutate array in place with splice or push
```jsx wrong
function handleRemove(index) {
  items.splice(index, 1);
  setItems(items);
}
function handleAdd(newItem) {
  setItems(items.push(newItem));
}
```

- [comparison-table] Three-column architectural matrix:

| | **IN-PLACE ARRAY MUTATION**<br>(Plain JavaScript Habit) | **IMMUTABLE STATE ARRAY**<br>(React Declarative Architecture) |
| ---: | :--- | :--- |
| **Removal operation** | `splice` modifies array in place | `filter` returns a fresh array |
| **Addition operation** | `push` modifies array and returns length | `[...items, newItem]` unpacks into a brand-new array |
| **Insertion operation** | `splice` inserts elements in place | `slice` with spread creates a combined copy |
| **Reorder operation** | `sort` mutates order of original reference | `toSorted` or `[...items].sort()` on a fresh copy |
| **Item update** | Direct mutation alters shared object | `map` with `{ ...item }` copies changed item |
| **Reconciliation reaction** | `Object.is` finds identical reference; skips render | `Object.is` detects new array reference; triggers render |
| **Baseline data & Reset** | Mutates initial objects; corrupts Reset button | Leaves previous snapshots and initial constants intact |
