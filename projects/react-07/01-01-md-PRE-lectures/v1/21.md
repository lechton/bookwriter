### Imperative DOM commands leave conflicting messages on screen

- [p] ◇ {theme: declarative UI and state machines in React} In modern frontend web applications, user interfaces constantly react to user actions and background network responses. When a customer subscribes to a service, they type payment details, click a submit button, watch a loading indicator appear while the network request is in flight, and finally see either an error notification or a confirmation banner. In plain JavaScript, developers write imperative commands that modify the DOM element by element: disabling buttons, removing hidden classes, and toggling error styles. Each command changes the page step by step and stays there forever until another explicit command undoes it. If a single branch forgets to reset an element, contradictory elements remain visible simultaneously, displaying an error banner right alongside a welcome message. In React, we solve this synchronization breakdown by declaring visual states first, storing the active state in component memory, and letting JSX describe what each state displays. Event handlers never touch the DOM; they only set the next state. ◼ Educational objective: contrast imperative DOM scripting with React's declarative state-driven architecture.

- [p] ◇ {starting point: imperative DOM habits versus declarative visual states} When developers transition from vanilla JavaScript or jQuery to React, they often bring along imperative scripting habits. When an error occurs, an imperative handler queries the DOM to set `errorText.style.display = 'block'`. When the user retries and the request succeeds, the success handler displays the welcome message, but forgets to hide the error container. The user ends up seeing "Payment failed" and "Welcome, subscriber" at the exact same time. The same defect appears when developers represent the form's lifecycle using three separate boolean state variables: `isSubmitting`, `isSuccess`, and `isError`. Three booleans allow eight distinct combinations, most of which represent impossible real-world states. When a retry succeeds and sets `isSuccess` to true without resetting `isError` back to false, the form renders both messages. React replaces both traps with a systematic design process: first, list every visual state; second, identify human and computer triggers; third, store the current state in a single status string. ◼ Educational objective: expose the failure modes of imperative DOM commands and multi-boolean state, previewing the 5-step state-driven design model.

- [p] ◇ {core questions: three governing laws of reacting to input with state} This chapter investigates three core questions. **Why does an imperative handler leave conflicting messages on screen after a retry, and how does JSX driven by status eliminate DOM commands?** **Where should component design begin: with the click handler, or by listing and mocking visual states before wiring triggers?** **Why do separate boolean flags create impossible states, and why does a single status string guarantee mutual exclusivity?** ◼ Educational objective: frame the three roadmap questions the lecture answers.

### A component changes its screen across visual states

- [runway] Visual states (typing, submitting, success, error), disabled button attribute, async and await with try and catch. Used by Question 1.

- [p] ★ {preknowledge: conditional rendering and async handlers from Lectures 10 and 17} In Lecture 10, we learned how conditional rendering with early returns and logical AND operators controls what JSX appears on screen, and in Lecture 17, we learned how asynchronous event handlers use `async` and `await` to coordinate state changes during network operations. Today we combine those mechanics to model complete visual component states. ◼ Educational objective: connect conditional JSX and asynchronous handlers to visual state transitions.

- [p] ★ {mechanism: visual states, button disabled attribute, and try/catch error handling} A visual state represents the complete visual appearance of a component at a specific moment in its lifecycle. A subscription form typically has four visual states: `typing` (the card input is editable and the Subscribe button is active), `submitting` (the input and button are disabled while a loading spinner spins), `success` (the form is replaced by a welcome message), and `error` (the button is active again and an error message is visible). The HTML `disabled` attribute prevents users from clicking buttons or typing into fields. In React, passing a boolean expression like `<button disabled={status === 'submitting'}>` binds button interactivity directly to state. When coordinating network requests, JavaScript provides `try` and `catch` blocks. An `async` handler runs code inside `try`, and if a network Promise rejects, execution immediately transfers to the `catch` block, allowing the component to transition cleanly from `submitting` to `error`. ◼ Educational objective: define visual states, explain the disabled attribute binding, and show how try/catch manages network transitions.

- [code] Visual states and button disabled handling:

```jsx title="Visual States and Disabled Handling"
// Handlers set status; JSX conditionally disables button and shows error
async function handleSubmit(e) {
  e.preventDefault(); // Prevents browser page reload
  setStatus('submitting'); // Transitions to loading visual state
  try {
    await submitPayment(card); // Waits for network Promise
    setStatus('success'); // Transitions to confirmation screen
  } catch (err) {
    setStatus('error'); // Transitions to error visual state
  }
}
```

◼ **The what-this-introduces list:** 1. `visual state`: the complete visual appearance of a component for a given state. 2. `disabled attribute`: a boolean HTML attribute that prevents user interaction on buttons and inputs. 3. `try...catch`: a JavaScript control structure that intercepts errors thrown during asynchronous operations.

### Testing visual states with props before wiring triggers

- [runway] Mocking visual states with a status prop, living styleguide with array map, human inputs (typing, clicking) and computer inputs (network responses). Used by Question 2.

- [p] ★ {preknowledge: props with defaults and list mapping from Lectures 6 and 11} In Lecture 6, we learned that components accept props with default values to configure their output, and in Lecture 11, we saw how array `map()` renders repeated items into an element list. In this section, we apply those mechanics to inspect every visual state before attaching interactive event handlers. ◼ Educational objective: recall prop defaults and list mapping to explain visual state mocking.

- [p] ★ {mechanism: mocking visual states with status props and cataloging triggers} When developing a complex interactive component, writing event handlers first forces you to test screens by manually triggering every step in the browser. A more disciplined approach is to mock each visual state first. By accepting a `status` prop with a default value, such as `function PaywallModal({ status = 'typing' })`, an engineer can change the prop value by hand to verify how `submitting`, `error`, or `success` look without writing any network logic. In fact, rendering an array of statuses side by side with `['typing', 'submitting', 'error', 'success'].map(...)` creates a living styleguide showing all four states simultaneously. Once the visual states are verified, you catalogue the triggers that move the component between them. Triggers divide into two categories: human inputs (such as typing into an input field or clicking a button) and computer inputs (such as an incoming network response or a timer firing). Each trigger becomes a single `setStatus` call in an event handler. ◼ Educational objective: explain visual state mocking, living styleguides, and the taxonomy of human versus computer inputs.

- [code] Mocking visual states with a status prop:

```jsx title="Mocking Visual States with Props"
// Mocking visual states with a prop allows visual verification without logic
export default function PaywallModal({ status = 'typing' }) {
  if (status === 'success') {
    return <p>Welcome, subscriber!</p>; // Visual state: success
  }
  return (
    <form>
      <input disabled={status === 'submitting'} /> {/* Input disabled */}
      <button disabled={status === 'submitting'}>Subscribe</button>
      {status === 'error' && <p>Payment failed</p>} {/* Visual state: error */}
    </form>
  );
}
```

◼ **The what-this-introduces list:** 1. `mock`: a visual preview rendered with static props to verify UI layout before attaching logic. 2. `living styleguide`: rendering multiple visual states simultaneously side by side for visual auditing. 3. `human inputs`: user interactions such as keystrokes, button clicks, and form submissions. 4. `computer inputs`: system events such as network responses resolving, promises rejecting, and timeouts firing.

### One status string prevents impossible states

- [runway] Impossible states (e.g. isError and isSuccess both true), single status string state, independent state for separate data (card text, error message). Used by Question 3.

- [p] ★ {preknowledge: component memory and boolean state from Lecture 14} In Lecture 14, we learned how `useState` stores component values across renders. Developers often create a boolean state variable for each piece of UI they need to toggle, which works well for independent flags but fails when states are mutually exclusive. ◼ Educational objective: recall boolean state variables and identify their combinatorial hazards.

- [p] ★ {mechanism: boolean explosion versus single status string} When a component can exist in only one visual mode at a time, representing those modes with separate boolean flags invites critical bugs. For example, using `isSubmitting`, `isSuccess`, and `isError` creates $2^3 = 8$ possible combinations. A state where `isError === true` and `isSuccess === true` is an impossible state: a screen cannot logically show a payment failure banner and a subscriber welcome message at the same time. If a retry handler sets `setIsSuccess(true)` but forgets to call `setIsError(false)`, the component enters this impossible state. Using a single `status` string state variable with `'typing' | 'submitting' | 'success' | 'error'` makes impossible states mathematically impossible, because a string variable can hold exactly one value at any moment. Values that change independently, such as user input (`card`) or dynamic error messages (`error`), remain separate state variables alongside `status`. ◼ Educational objective: demonstrate boolean state explosion, define impossible states, and mandate single status strings for mutually exclusive modes.

- [code] Single status string versus multiple boolean flags:

```jsx title="Single Status String Versus Multiple Booleans"
// Correct: one string state variable guarantees mutual exclusivity
const [status, setStatus] = useState('typing'); // Holds exactly one mode
const [card, setCard] = useState(''); // Independent user input

// Fragile: multiple booleans allow contradictory combinations
const [isSubmitting, setIsSubmitting] = useState(false); // Can conflict
const [isSuccess, setIsSuccess] = useState(false); // Can conflict
const [isError, setIsError] = useState(false); // Can conflict
```

◼ **The what-this-introduces list:** 1. `impossible state`: a contradictory combination of state values that causes the UI to render broken or conflicting elements. 2. `single status string`: a state variable holding a string enum that guarantees only one visual state is active at a time. 3. `independent state`: state variables that change autonomously, such as input field values or error details, kept separate from status.

### Principles of React: Reacting to Input with State

- [question-cycle] Principle 1 Plan:
    - Question: My Subscribe handler disables the button, shows the spinner, and hides the error. Why does the form end up showing "Payment failed" and "Welcome, subscriber" together?
    - Code and result: Inside `PaywallModal`, a developer queries DOM elements directly: `button.disabled = true`, `errorText.style.display = 'block'` in `catch`. On the first attempt, payment fails and shows "Payment failed". On the retry, payment succeeds and shows "Welcome, subscriber", but the success branch forgot to hide the error text, so both messages show on screen at once (React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: In imperative programming, every DOM mutation remains in place until another line explicitly undoes it. The first attempt fails, so `errorText.style.display = 'block'` displays the error message. The second attempt succeeds, so `welcomeText.style.display = 'block'` displays the welcome message. Because no line commanded the browser to hide the error container, both elements remain visible on screen simultaneously. React has no knowledge of these direct DOM mutations. In React, we describe what each status shows in JSX, reading a `status` state variable. The handlers only call `setStatus('submitting')`, then `setStatus('success')` or `setStatus('error')`. React re-renders the component and updates the DOM to match the JSX for that status, so conflicting messages can never appear together.
    - Fix: Replace imperative DOM queries with declarative JSX driven by `status`, and let handlers only call `setStatus`.
    - Rule with boundary: Describe what each status shows in JSX, and let handlers only set the status. Boundary: handlers change only component state, never the DOM directly; DOM refs for focus or scrolling are introduced in Lecture 30.
    - Needs: visual state (runway), `disabled` attribute (runway), `try`/`catch` (runway), declarative vs imperative (recall, Lecture 1).
    - Diagram: ASCII diagram showing first attempt failing -> imperative DOM edit showing error -> second attempt succeeding -> welcome showing alongside error vs declarative status re-render.

> [!PRINCIPLE]
> **Principle 1: Describe what each status shows, and let handlers only set the status**
> Imperative commands tell the browser how to change the page step by step, and each change stays until another command undoes it. If a success branch forgets to hide an earlier error, both messages remain on screen together. In React, JSX declares what the screen shows for each **visual state**, and event handlers only update state. When state changes, React re-renders the component and updates the DOM to match the JSX, so conflicting elements never share the screen.
>
> >> visual state : a distinct screen appearance determined by component data
>
> *We should do this:*
> `function Form({ status, setStatus }) {`
> `  if (status === 'success') {`
> `    return <p>Action complete</p>; // shows only success message`
> `  }`
> `  return (`
> `    <form onSubmit={() => setStatus('loading')}>`
> `      <button disabled={status === 'loading'}>Submit</button>`
> `      {status === 'error' && <p>Action failed</p>}`
> `    </form>`
> `  );`
> `}`
>
> *We should not do this:*
> `function handleSubmit() {`
> `  document.querySelector('#status').textContent = 'Loading...';`
> `  sendRequest()`
> `    .then(() => {`
> `      document.querySelector('#success').style.display = 'block';`
> `      // forgot to hide #error, so both messages stay visible`
> `    })`
> `    .catch(() => {`
> `      document.querySelector('#error').style.display = 'block';`
> `    });`
> `}`

- [question-cycle] Principle 2 Plan:
    - Question: Where do I start? Do I write the Subscribe handler first?
    - Code and result: A developer starts building `PaywallModal` by writing the `handleSubscribe` function first, attempting to wire button clicks and network requests before defining what screens the form can display.
    - Verdict: works, but starting from event handlers makes it hard to see all visual states.
    - Answer: Starting from event handlers forces you to test screens by manually clicking buttons and waiting for network requests. Listing the visual states first allows you to design and verify each screen before writing any logic. For a subscription paywall modal, the visual states are: typing (button enabled), submitting (button disabled, spinner showing), success (welcome message shown, form hidden), and error (button enabled, error banner shown). You can mock each state by giving the component a `status` prop with a default, such as `status="submitting"`, to view every screen in isolation. You can even render all four mocks side by side in a living styleguide. Next, you identify what triggers each transition: human inputs (typing into the card field, clicking Subscribe) and computer inputs (the network response resolving or rejecting). Finally, each transition becomes a single `setStatus` call in an event handler.
    - Fix: none.
    - Rule with boundary: List the visual states first, then what moves the form between them. Boundary: use this design flow whenever a component switches between distinct screen states based on user or network input; static presentational components that only display props directly do not require state modeling.
    - Needs: `mock` (runway), living styleguide (runway), human and computer inputs (runway), props with defaults (recall, Lecture 6).
    - Diagram: ASCII diagram showing the 4 visual states (typing, submitting, success, error) and the trigger transitions connecting them.

> [!PRINCIPLE]
> **Principle 2: List the visual states first, then what moves the form between them**
> A component that reacts to input is built from the screen inward, not from the handlers outward. First, list every screen the user can see: empty, typing, submitting, success, and error. Second, **mock** each visual state with a `status` prop to verify its markup before writing logic. Third, list the human and computer triggers that cause transitions. Finally, wire event handlers that call `setStatus` to connect those triggers to the visual states.
>
> >> mock : a visual demonstration rendered with static props before adding logic
>
> *We should do this:*
> `function Form({ status = 'empty' }) {`
> `  if (status === 'success') {`
> `    return <p>Success message</p>; // renders success screen`
> `  }`
> `  return (`
> `    <form>`
> `      <input disabled={status === 'submitting'} />`
> `      <button disabled={status === 'submitting'}>Submit</button>`
> `      {status === 'error' && <p>Error message</p>}`
> `    </form>`
> `  );`
> `}`

- [question-cycle] Principle 3 Plan:
    - Question: Can I keep isSubmitting, isSuccess, and isError as three booleans instead?
    - Code and result: Inside `PaywallModal`, a developer creates three separate boolean state variables: `const [isSubmitting, setIsSubmitting] = useState(false);`, `const [isSuccess, setIsSuccess] = useState(false);`, and `const [isError, setIsError] = useState(false);`. On the first attempt, payment fails and the handler calls `setIsError(true)`. The user clicks Subscribe again; payment succeeds and the handler calls `setIsSuccess(true)`. But because nothing set `isError` back to `false`, both `isError` and `isSuccess` are `true` simultaneously, displaying "Payment failed" and "Welcome, subscriber" together (React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: Three separate booleans allow $2^3 = 8$ possible combinations, but only four make real-world visual sense. When state allows combinations that make no sense, it creates impossible states. In this case, setting `isSuccess(true)` leaves `isError` as `true` unless the developer remembers to write `setIsError(false)` in every single success path. Storing the active visual state in a single string variable—such as `status` with values `'typing'`, `'submitting'`, `'success'`, and `'error'`—makes impossible states mathematically impossible, because a string can hold only one value at a time. Values that change independently, like the typed card string (`card`) or an error message text (`error`), keep their own separate state.
    - Fix: Replace the three booleans with a single `status` string state variable: `const [status, setStatus] = useState('typing');`.
    - Rule with boundary: Keep states that exclude each other in one status string. Boundary: values that change independently on their own, such as input text or dynamic error messages, keep their own separate state variables.
    - Needs: impossible state (runway), single status string (runway), boolean state (recall, Lecture 14).
    - Diagram: ASCII diagram showing 3 booleans (8 combinations, impossible states like error+success) versus 1 status string (mutually exclusive states).

> [!PRINCIPLE]
> **Principle 3: Keep states that exclude each other in one status string**
> Representing mutually exclusive visual modes with separate boolean variables allows contradictory flags to be active together, creating an **impossible state** where success and error messages share the screen. A single `status` string holding named states like `'typing'`, `'submitting'`, `'success'`, or `'error'` eliminates impossible combinations because a variable can hold only one string at a time. Keep separate state only for values that change independently, such as typed text.
>
> >> impossible state : a combination of state values that makes no visual sense
>
> *We should do this:*
> `const [status, setStatus] = useState('typing');`
> `const [text, setText] = useState(''); // text changes independently`
> `function handleSuccess() {`
> `  setStatus('success'); // automatically replaces error or typing`
> `}`
>
> *We should not do this:*
> `const [isError, setIsError] = useState(false);`
> `const [isSuccess, setIsSuccess] = useState(false);`
> `function handleSuccess() {`
> `  setIsSuccess(true); // isError stays true, showing both messages`
> `}`

### For the interview
- Blockquote: `> **The Interview Question:** How do you design a component that reacts to input with state instead of touching the DOM?`
- Four beats:
  1. The Hidden Signal: Probing declarative UI architecture, state machine principles, and avoiding imperative DOM anti-patterns.
  2. The Classic Trap: Attempting to patch imperative DOM scripting by querying elements or managing multiple boolean flags.
  3. What is Actually Going On: Listing visual states, mocking with props, identifying human and computer triggers, and driving JSX from a single status string.
  4. Where It Gets Tricky: Handling asynchronous network errors with try/catch, preventing duplicate submissions with the disabled attribute, and keeping independent input state decoupled from status.

### Glossary
- **Visual State**: A distinct visual presentation of a component determined by its underlying data and lifecycle status.
- **Single Status String**: A state variable containing a string enum that guarantees only one mutually exclusive visual mode is active at any time.
- **Impossible State**: A contradictory combination of state values that causes the user interface to display invalid or conflicting elements.
- **Human Input**: User-driven interactions such as typing into form inputs, clicking buttons, or submitting forms.
- **Computer Input**: System-driven interactions such as network responses returning, promises rejecting, or timers completing.
- **Living Styleguide**: Rendering all mocked visual states of a component simultaneously to audit and verify layout across all lifecycle phases.
