### A component tree divides the page into focused jobs

- [p] ◇ {theme} Every web application contains multiple visual sections: headers, article feeds, story cards, and bylines. In earlier lessons, our components were single functions that returned markup for one piece of the interface. When building a full page, every developer meets the same question: how do we organize the markup and functions that create the page? ◼ Educational objective: bird's-eye view; the theme from the map's Theme and Options, from pages the reader knows.

- [p] ◇ {starting point: monolithic layout} A first full page often keeps every region inside one large component function, a **monolithic layout**. ◼ Educational objective: the reader's starting point, named by its exact term; the map lists no options, so it is not a rival way.

- [code] Monolithic layout: all page regions inside one function:

```jsx title="Monolithic layout: all page regions inside one function"
export default function PageLayout() {
  return (
    <div className="content-app">
      <header>Daily Articles</header> {/* inlines site header in monolith */}
      <main>
        <article>Night Trains</article> {/* hardcodes article markup in root */}
      </main>
    </div>
  );
}
```

- [p] ◇ {starting point: point into the code} All regions of the page sit inside one function: the `<header>`, `<main>`, and `<article>` tags are returned in a single return statement. The browser renders the markup without errors. That is why it is called a monolithic layout: one single function contains the entire structure. As the page grows, that function grows to hundreds of lines, and every new card repeats the same markup. ◼ Educational objective: point into the code and say where the starting point stops serving the reader, without inventing a use for it.

- [p] ◇ {the chapter's idea: component tree} React's answer is a **component tree**: split the page into nested components that each manage one focused responsibility. ◼ Educational objective: the chapter's idea, named by its exact term.

- [code] Component tree: nested components with divided responsibilities:

```jsx title="Component tree: nested components with divided responsibilities"
export default function App() {
  return (
    <div className="content-app">
      <NewsHeader /> {/* header component manages banner */}
      <EditorialFeed /> {/* feed component manages article list */}
    </div>
  );
}
```

- [p] ◇ {the chapter's idea: point into the code} Instead of dumping every element into `App`, the top-level component returns `<NewsHeader />` and `<EditorialFeed />`. Inside `EditorialFeed`, the feed returns two `<ArticleCard />` components, and each card returns an `<EditorialByline />`. When React mounts `App`, it walks from `App` down through each child, assembling an in-memory hierarchy called a component tree. The browser DOM receives the exact same HTML elements, but the code divides into modular parts with clear names and focused jobs. That is why it is called a component tree: a top-down hierarchy of components. ◼ Educational objective: the place, what fills it, who acts, and the contrast with a monolithic layout.

- [code] Component tree: feed nesting article cards:

```jsx title="Component tree: feed nesting article cards"
function EditorialFeed() {
  return (
    <main className="feed">
      <ArticleCard /> {/* first article node */}
      <ArticleCard /> {/* second article node */}
    </main>
  );
}
```

### The component tree models your interface from root to leaves

- [p] ◇ {runway: tree structures across computing} In computer science and web development, user interfaces are universally modeled as trees. A tree is a hierarchical data structure composed of connected nodes, starting at a single root node that branches downward into child nodes. Web browsers use tree structures to model HTML documents through the Document Object Model (the DOM) and style hierarchies through the CSS Object Model (the CSSOM). Mobile platforms like iOS and Android represent their view hierarchies as trees. React embraces this exact same model: it organizes your user interface as a **component tree** composed of your custom component functions. ◼ Educational objective: ground React's component tree in universal computing paradigms.
- [p] ◇ {runway: genealogical tree terminology} To discuss component architecture with senior engineers, we use standard genealogical tree terminology. The **root component** is the top-level node where the tree begins (`App`), and it is the very first component React renders. A **branch component** is an intermediate container that groups related sections and renders child components (such as `Header` or `ArticleList`). A **leaf component** is a terminal node at the bottom of the tree that renders native HTML elements directly without nesting further custom components (such as `AuthorBadge`). Within the tree, a component that returns another component is its **parent**, the nested component is its **child**, components sharing the same parent are **siblings**, and components higher up the chain are **ancestors**. ◼ Educational objective: establish the formal genealogical vocabulary of tree positions (root, branch, leaf, parent, child, sibling, ancestor).
- [p] ◇ {runway: component render tree versus browser DOM tree} It is crucial to distinguish between the React component tree and the browser DOM tree. As Lecture 1 demonstrated, custom component tags vanish into plain HTML when rendered to the screen. If you inspect the browser's native Elements tab, you see only native HTML tags like `<header>`, `<main>`, and `<article>`. The browser DOM has zero knowledge of `App`, `Header`, or `ArticleCard`. The React component tree, by contrast, lives in JavaScript memory and consists exclusively of React components. Developers inspect this living component tree using the React DevTools Components tab, which reveals the true architectural hierarchy that drives the application. ◼ Educational objective: contrast the browser DOM tree against the React component tree and introduce React DevTools as the inspection tool.
- [p] ★ {runway: JSX returns compile into element descriptors} How does React build this tree? React does not inspect your file directory or the order in which functions are declared. Instead, React evaluates the JSX returned by each component function. When `App` returns `<Header />` and `<ArticleList />`, the JSX compiler converts those tags into React element descriptors: `_jsx(Header, {})` and `_jsx(ArticleList, {})`. These descriptors form parent-child branches in memory. Because each component function returns element descriptors describing what should appear next, React traverses these descriptors from the root downward, creating the nested component tree for that render pass. ◼ Educational objective: trace how JSX returns compile into element descriptors that form the living component tree.

### Separation of concerns divides a layout by responsibility

- [p] ◇ {runway: separation of concerns} When building web applications, developers face an architectural decision: should a layout live in one large function, or should it be divided across smaller components? In software engineering, **separation of concerns** means assigning each piece of code a single focused responsibility. In a React application, `App` orchestrates high-level page regions, branch components group semantic features, and leaf components manage specific presentation controls. ◼ Educational objective: define separation of concerns and explain why modular boundaries improve code maintainability.
- [p] ★ {runway: DOM equivalence and code review standards} In the browser DOM, a decomposed component tree produces the exact same HTML elements as a monolithic single-function component. Component tags leave zero extra wrapper elements in the browser DOM. The benefits of splitting are architectural: code becomes readable, reusable, and testable. In code reviews, senior engineers flag 500-line monolithic functions because untangling layout bugs in a giant file is painful. However, engineers also avoid the opposite extreme: fragmenting every individual HTML tag into a separate trivial component. ◼ Educational objective: prove DOM equivalence between monoliths and decomposed trees while establishing review standards.
- [p] ◇ {runway: the inline boundary heuristic} As official React documentation teaches in Thinking in React, keep a small piece of markup inline inside its parent until it grows distinct data, styling, or logic of its own. When a section of markup develops an independent concern or needs to be rendered multiple times, extract it into a dedicated component. ◼ Educational objective: establish the practical boundary for when to extract a component versus keeping markup inline.

### Function scope isolates variables between sibling components

- [p] ★ {runway: JavaScript function scope and ReferenceError} In JavaScript, variables declared with `const` or `let` inside a function body belong strictly to that **function scope**. Code executing outside that function cannot access those variables. If a component function attempts to read a variable declared inside another component, JavaScript halts execution and throws a fatal `ReferenceError`. Because sibling components never call each other, no direct horizontal pathway connects them in memory. ◼ Educational objective: explain JavaScript function scope boundaries and why cross-sibling variable access throws a ReferenceError.
- [p] ★ {runway: why DOM lookups fail during render} When developers hit scope boundaries, some attempt to read values from the browser DOM using `document.getElementById('feed-reader').textContent`. In React, this imperative lookup fails with `TypeError: Cannot read properties of null (reading 'textContent')`. As Lecture 15 will explore, React executes all component functions during render to compute the UI description before committing any changes to the browser DOM. At the moment a header component renders, the DOM nodes for sibling components do not exist yet. ◼ Educational objective: prove why imperative DOM lookups fail during component rendering.
- [p] ★ {runway: passing values down via props} Because data cannot flow horizontally between siblings or upward from children, React enforces unidirectional top-down data flow. When two sibling components need the same piece of information, that value must live in their closest common parent. The parent holds the value and passes it downward to each child by writing it as an attribute on the child tag, such as `<Header readerName={readerName} />`. The child receives this value through its **props**, a mechanism Lecture 6 explores in full detail. ◼ Educational objective: introduce unidirectional data flow and props as the vehicle for sharing data through a common parent.

### Principles of React: UI as a Tree and Component Hierarchy

- [question-cycle] Question 1: The order of functions in a file does not decide the tree
    - Question: "I wrote five components in one file. How does React know which goes where?"
    - Code and result: five components defined in shuffled order (`AuthorBadge`, `App`, `ArticleList`, `Header`, `ArticleCard`) with a `console.log` in each; the console logs `App`, `Header`, `ArticleList`, `ArticleCard`, `AuthorBadge`, `ArticleCard`, `AuthorBadge` (verified in React 19.3.0).
    - Verdict: The code works.
    - Answer: `root.render` hands React `<App />`; React calls `App`; `App` returns `<Header />` and `<ArticleList />`, so they become its children; React calls each one; `ArticleList` returns two `<ArticleCard />` tags, two separate nodes; each returns an `<AuthorBadge />`, a leaf; React walks down until only HTML tags remain; the order of the function definitions in the file plays no part.
    - Fix: none.
    - Rule: Read component hierarchy from the JSX returned by each component, never from function declaration order in a file. Boundary: To change where a component appears, move its tag in returned JSX.
    - Needs: component tree (runway), root, branch, and leaf components (runway), DevTools Components tab (runway).
    - Diagram: Shuffled file declaration order versus top-down execution walk and resulting component tree.

> [!PRINCIPLE]
> **Principle 1: The JSX each component returns builds the tree**
> React builds the **component tree** from what each component returns in JSX, not from where functions sit in a file. React starts by calling the root component. When that component returns child tags, React calls those child components next, and continues down until only HTML tags remain. Moving a function up or down in your file changes nothing on screen. To change where a component appears in the hierarchy, move its tag inside the parent component's returned JSX.
>
> >> component tree : the hierarchy of components created by what each function returns in JSX
>
> *We should do this:*
> `function Card() {`
> `  return (`
> `    <article>`
> `      <Badge /> {/* returned JSX makes Badge a child */}`
> `    </article>`
> `  );`
> `}`

- [p] ★ In our single-file test, declaring `function AuthorBadge()` at line 1 and `function App()` at line 20 does not make `AuthorBadge` the root of the page. When the application mounts, React begins execution at `App` because `root.render(<App />)` explicitly designated it as the root. React calls `App`, reads `<Header />` and `<ArticleList />` from its return statement, and visits each child in top-down order. The console logs verify that React visits `ArticleCard` and `AuthorBadge` twice because their tags appear twice in returned JSX, proving that returned markup strictly governs tree topology. ◼ Educational objective: prove Principle 1 on the lesson's code by verifying execution order against returned JSX.

- [question-cycle] Question 2: Splitting a monolith keeps the HTML while dividing responsibilities
    - Question: "Why not keep the whole page in `App`? It works."
    - Code and result: a 500-line monolithic `App` component inlining all header, feed, card, and badge tags versus a decomposed tree with `App`, `Header`, `ArticleList`, `ArticleCard`, and `AuthorBadge`; the browser DOM output is identical in both implementations (verified in React 19.3.0).
    - Verdict: The code works.
    - Answer: the browser DOM is identical either way because custom component tags leave no elements of their own; splitting changes only code architecture: each part receives a name, a place in the tree, and one responsibility; article card markup is written once and reused twice; reviewers reject monoliths because tangled concerns make maintenance risky.
    - Fix: none.
    - Rule: Split monolithic layouts into root, branch, and leaf components by separation of concerns. Boundary: Keep a small piece of markup inline inside its parent until it grows distinct data or logic of its own.
    - Needs: separation of concerns (runway), inline boundary heuristic (runway).
    - Diagram: Monolithic single-function layout versus decomposed modular component hierarchy.

> [!PRINCIPLE]
> **Principle 2: Split the page into components with one job each**
> Writing an entire page in one large component produces the same HTML in the browser DOM, but makes code difficult to read, test, and reuse. Split the page by **separation of concerns** into components that each handle one clear responsibility. The root coordinates high-level regions, intermediate components group related sections, and terminal components render specific content. Keep a small piece of markup inside its parent until it grows distinct data or logic of its own.
>
> >> separation of concerns : giving each component one focused responsibility in the interface
>
> *We should do this:*
> `function App() {`
> `  return (`
> `    <div>`
> `      <Header /> {/* manages top header region */}`
> `      <ArticleList /> {/* manages article feed */}`
> `    </div>`
> `  );`
> `}`

- [p] ★ When we inspect the browser Elements tab for both the monolithic `PageLayout` and the decomposed component tree, the resulting DOM structures are identical. Custom component tags leave zero footprint in the DOM tree, meaning component boundaries introduce zero HTML overhead. Decomposing `App` into `Header`, `ArticleList`, `ArticleCard`, and `AuthorBadge` isolates each visual concern. If the styling of the card changes tomorrow, developers edit `ArticleCard` without touching `App` or risking regressions in `Header`. ◼ Educational objective: prove Principle 2 on the lesson's code by verifying identical DOM outputs and modular isolation.

- [question-cycle] Question 3: Sibling components cannot read each other's local variables
    - Question: "`Header` needs the reader's name, and `ArticleList` already has it. Can it just read it?"
    - Code and result: `ArticleList` declares `const readerName = "Elena"` and `Header` attempts to render `<p>{readerName}</p>`; the browser crashes with `ReferenceError: readerName is not defined`; querying `document.getElementById('feed-reader').textContent` fails with `TypeError: Cannot read properties of null` (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: a variable declared inside a component exists strictly within that function scope; siblings never call each other, so no direct communication path connects them; React calls all components before putting any on the screen, so DOM queries during render return null; data flows strictly downward from parent to child, so the shared value must live in their closest common parent (`App`), which passes it downward on each child's tag.
    - Fix: declare `const readerName = "Elena"` in `App`, pass it to both children as `<Header readerName={readerName} />` and `<ArticleList readerName={readerName} />`, and access it in each child via `props.readerName` (as taught in the runway and previewing Lecture 6).
    - Rule: When two sibling components need the same value, place that value in their closest common parent and pass it downward. Boundary: If only one component needs a value, keep that value local to that component.
    - Needs: function scope (runway), ReferenceError (runway), closest common parent (runway), props attribute binding (runway).
    - Diagram: Horizontal sibling reach crash versus unidirectional data flow from closest common parent.

> [!PRINCIPLE]
> **Principle 3: Data travels down the tree so a shared value lives in their common parent**
> In JavaScript, variables declared inside one function are invisible to other functions. Sibling components never call each other, so no direct communication path connects them. To share a value between siblings, place that value in their **closest common parent**. The parent passes the value downward to each child component by writing it as an attribute on the child tag.
>
> >> closest common parent : the lowest shared component in the tree that sits above all components needing a value
>
> *We should do this:*
> `function App() {`
> `  const user = "Elena"; // declared in common parent`
> `  return (`
> `    <div>`
> `      <Header user={user} />`
> `      <Feed user={user} />`
> `    </div>`
> `  );`
> `}`
>
> *We should not do this:*
> `function Header() {`
> `  return <header>{user}</header>; // ReferenceError: not defined`
> `}`
> `function Feed() {`
> `  const user = "Elena"; // isolated in sibling scope`
> `  return <main>Feed</main>;`
> `}`

- [p] ★ When `readerName` is declared locally inside `ArticleList`, `Header` cannot access it because JavaScript lexical scope isolates function memory. Attempting horizontal variable access crashes the browser with a fatal `ReferenceError`. Furthermore, querying the DOM during render fails because React has not yet committed elements to the document. Moving `readerName` up to `App` resolves the defect completely. `App` sits as the closest common parent above both siblings, projecting the value downward along parent-child branches so both "Welcome back, Elena" and "Picked for Elena" render reliably. ◼ Educational objective: prove Principle 3 on the lesson's code by demonstrating the fatal ReferenceError and resolving it through closest common parent placement.

### Step 1: First, we decompose the application shell <App.jsx>

- [p] ★ {step 1: App.jsx implementation} We construct `App.jsx` as the root coordinator of our component tree. In a monolithic approach, an engineer might dump all header, feed, and card markup directly into this single file. In React, we separate concerns: `App` declares the shared reader name and mounts `Header` and `ArticleList` as direct children in the component tree, passing the shared value downward along both branches. ◼ Meaningful pedagogical commentary: root architectural role, unidirectional data initialization, and branch composition.

- [code] App.jsx (verified in React 19.3.0):

```jsx title="App.jsx"
import Header from "./components/Header.jsx";
import ArticleList from "./components/ArticleList.jsx";
export default function App() {
  const readerName = "Elena"; // shared value in common parent
  return (<div className="content-app">
    <Header readerName={readerName} />
    <ArticleList readerName={readerName} />
  </div>);
}
```

◼ **The what-this-introduces list:** 1. `App`: top-level root component. 2. `readerName`: shared string placed in the closest common parent. 3. `<Header />` and `<ArticleList />`: branch tags establishing parent-child hierarchy in returned JSX.

### Component Summary

- [p] ◇ {component summary panel} We audit the division of labor across our decomposed component tree. `App` coordinates page regions, `Header` and `ArticleList` manage semantic branches, and `ArticleCard` and `AuthorBadge` deliver presentation controls. ◼ Educational objective: deconstruct component responsibilities.

```component-code title="Summary: The Logic of Nested Components"
App.jsx | none | parent | [role: The **root application shell** coordinates top-level page regions. It initializes the shared reader name and mounts the site header and article feed branches. What is its structural role? It provides a stable layout boundary and acts as the closest common parent for the entire component tree.]
  Header.jsx | none | branch | [role: This **branch container** groups site branding and personalized reader greetings. It encapsulates top-level presentation for the header region, keeping header markup completely separate from the article feed.]
  ArticleList.jsx | none | branch | [role: This **branch container** organizes the central story feed. It renders the personalized section title and mounts nested article cards, defining the structural subtree for the feed body.]
    ArticleCard.jsx | none | child | [role: This **presentation component** frames the headline and summary for an individual story. It encapsulates card markup and nests the author badge leaf component.]
      AuthorBadge.jsx | none | generic | [role: This **leaf component** renders author attribution and publication dates directly into native span elements, terminating the bottom of the component tree.]
```

- [p] ★ In legacy web applications, developers built pages by pasting raw HTML markup into monolithic files or manipulating arbitrary DOM nodes across scripts. In React, interfaces are organized as a clean, hierarchical component tree. `App` sits at the root, branching downward into `Header` and `ArticleList`, which terminate in leaf components like `ArticleCard` and `AuthorBadge`. This hierarchy provides immense clarity: each component owns a single responsibility, React walks the tree predictably from the root downward, and data flows reliably along parent-child branches. ◼ Educational objective: contrast monolithic flat sprawl with structured component tree architecture.

### For the interview

> **The Interview Question:** How does React organize nested components into a tree, and why does hierarchy dictate data flow?

**1. The Hidden Signal**

The interviewer is not merely checking if you know what a component is. They are probing your understanding of React's execution model, tree data structures, lexical scope isolation, and why React enforces unidirectional data flow. A junior developer says React "builds a tree from HTML tags." A senior engineer explains that React evaluates JSX element descriptors returned by component functions from the root downward to construct an in-memory component tree, and that hierarchy dictates data flow because functions maintain isolated scopes while React provides zero horizontal communication pathways between siblings.

**2. The Classic Trap**

The classic trap is assuming that function declaration order in a file determines runtime hierarchy, or attempting to share variables horizontally between adjacent sibling components. Candidates often forget that JavaScript lexical scope isolates variables within function bodies, leading to fatal `ReferenceError` crashes when trying to read values across siblings. Another frequent trap is attempting imperative DOM queries like `document.getElementById` during render, which returns null because React executes component calculations before committing elements to the DOM.

**3. What is Actually Going On**

Under the hood, React starts execution at the root component designated by `root.render()`. When a parent component returns JSX, the compiler translates custom tags into element descriptors (`_jsx(Child, {})`). React traverses these descriptors top-down, calling each child component in turn until only native DOM tags remain. Because components are independent functions that never invoke each other directly, no horizontal connections exist between siblings. Data can only flow downward along parent-child branches. When siblings need to coordinate around a shared value, that value must be lifted to their closest common parent, which passes it down to each child via props.

**4. Where It Gets Tricky**

Where this gets tricky in production is understanding that while a parent always executes before its children, React does not guarantee a strict execution order between siblings. Relying on one sibling running before another to set global variables or trigger side effects violates React's pure rendering model, a critical invariant explored in Lecture 12. Furthermore, in deep hierarchies, passing shared values down through multiple intermediate containers creates prop drilling, which motivates architectural patterns like children composition in Lecture 7 and React Context in Lecture 27.

### Glossary

- **Component Tree**: The hierarchical data structure of React element descriptors formed by what components return in JSX, representing the component structure for a single render pass.
- **Root Component**: The top-level component where a React application begins (`App`), acting as the first component React renders and the ancestor of all other components.
- **Branch Component**: An intermediate container in the component tree that groups related UI sections and renders child components.
- **Leaf Component**: A terminal component at the edge of the component tree that has no custom child components and renders native HTML elements directly.
- **Closest Common Parent**: The lowest shared parent component in the hierarchy that sits above two or more components that require the same data.
- **Separation of Concerns**: The software design principle of dividing an application into distinct components, where each component addresses a single, well-defined responsibility.
- **Function Scope**: The JavaScript language boundary where variables declared inside a function body are private to that function and invisible to outside code.
- **ReferenceError**: The JavaScript runtime exception thrown when code attempts to access a variable identifier that does not exist within the current lexical scope.
- **React DevTools**: A browser extension that inspects the living React component tree in memory, contrasting with the browser Elements tab which displays the HTML DOM.
- **Unidirectional Data Flow**: The architectural invariant where data travels strictly downward along parent-child branches from ancestors to descendants.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Tree Structure and JSX Nesting

➔ IF determining component hierarchy, THEN read the nesting of tags inside returned JSX rather than the order of function declarations in a file.

➔ IF moving a component in the UI hierarchy, THEN move its tag within returned JSX, because moving a function definition in a file changes nothing on screen.

❒ Component Decomposition and Separation of Concerns

➔ IF structuring a multi-section layout, THEN decompose it into root, branch, and leaf components with one focused responsibility each.

➔ IF evaluating whether to extract a component, THEN keep small pieces of markup inline until they grow distinct data, styling, or logic of their own.

❒ Execution Order and Unidirectional Data Flow

➔ IF tracing component execution, THEN trace top-down from parent to child, remembering that unmounted child subtrees never execute.

➔ IF sharing a value between sibling components, THEN place that value in their closest common parent and pass it downward, because siblings cannot read each other's local variables.

**DO THIS:** Decompose layouts into parent-child trees and route shared data through common parents

```jsx right
function App() {
  const user = "Elena";
  return (
    <div className="app">
      <Header user={user} />
      <ArticleList user={user} />
    </div>
  );
}
```

**DO NOT DO THIS:** Dump entire layouts into 500-line monoliths or attempt horizontal sibling variable access

```jsx wrong
function Header() {
  return <header>{user}</header>;
}
function ArticleList() {
  const user = "Elena";
  return <main><article><h3>Night Trains</h3></article></main>;
}
```
