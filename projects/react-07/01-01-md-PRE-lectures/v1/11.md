### Every web application needs to display collections of items

- [p] ◇ {theme: displaying collections of items} Every web application displays dynamic collections of items. An online shop displays a grid of products, a social feed shows a list of posts, and a news portal presents breaking articles. In static HTML, each item is hardcoded into the markup one tag at a time. If the collection changes from twenty items to twenty-five, an engineer must edit the template and redeploy the code. In modern applications, collections change constantly: items are added, removed, filtered, and reordered. Modern web frameworks transform raw arrays of data into living user interfaces. ◼ Educational objective: introduce the universal engineering necessity of transforming collections of data into dynamic UI elements.

Instead of repeating JSX tags or writing manual append loops, you project that array of data into an array of JSX elements. React unpacks that array and paints the corresponding DOM nodes in order. ◼ Educational objective: contrast static tag repetition and imperative DOM loops with declarative React array projection.

### How JavaScript transforms data arrays with map and arrow functions

- [runway] Array transformation with map, arrow function return mechanics, and array filtering, used by Question 1, Question 2, and Question 3.

- [p] ★ {preknowledge: JavaScript arrays and object literals} In Lecture 4, we saw that curly braces `{}` inside JSX open an evaluation window for JavaScript expressions. JavaScript represents collections of structured data as arrays of objects, such as `const stories = [{ id: 's1', title: 'City Transit Plan' }, { id: 's2', title: 'Clean Energy Accord' }]`. Each item in the array has properties we can access with dot notation, like `story.title`. To display every story, we need a way to convert each object in the data array into a corresponding JSX element. ◼ Educational objective: re-anchor the reader on arrays of objects and dot notation before introducing transformation methods.

- [p] ★ {mechanism: the array map method} The standard JavaScript array method `map()` transforms an array into a new array. It takes a callback function as an argument, calls that function once on each item in the original array, and collects the return values into a brand-new array. The original array remains completely untouched. For example, `[1, 2, 3].map(n => n * 2)` produces `[2, 4, 6]`. In React, our callback takes a data object and returns a JSX element, such as `stories.map(story => <li>{story.title}</li>)`. When you place `{stories.map(...)}` inside a `<ul>`, React unpacks the resulting array of elements and renders each `<li>` in order. ◼ Educational objective: define the array map method and show how it converts data objects into JSX element arrays.

- [p] ★ {mechanism: arrow functions with implicit returns versus block bodies} In JavaScript, an arrow function can be written with an **implicit return** or a **block body**. In an arrow function without curly braces on the right side of the arrow, like `story => <li>{story.title}</li>`, JavaScript uses an implicit return: it automatically returns the single expression following the arrow. However, if you place curly braces after the arrow, like `story => { <li>{story.title}</li> }`, you create a block body. A block body executes code statements line by line, but it returns `undefined` unless you explicitly write the `return` keyword. If you omit `return`, `map()` returns an array filled with `undefined`, and React renders zero DOM nodes. ◼ Educational objective: contrast implicit arrow returns with block bodies and explain the missing return pitfall.

- [p] ★ {mechanism: filtering data arrays before mapping} Often, an interface needs to display only a subset of items from an array, such as only featured stories. The standard JavaScript `filter()` method takes a test predicate function that returns `true` or `false` for each item. It produces a new, shorter array containing only the items that returned `true`. You can chain `filter()` directly into `map()`, writing `stories.filter(story => story.isFeatured).map(story => <li key={story.id}>{story.title}</li>)`. This separates filtering logic from markup projection. ◼ Educational objective: teach array filter and show how to produce subsets before mapping to JSX.

- [p] ★ {mechanism: array indices as callback arguments} The callback function passed to `map()` receives three arguments: the current item, the item's numerical **array index** (starting from 0), and the array itself. Writing `stories.map((story, index) => ...)` exposes the sequential position of each item. While the index tells you where an item currently sits in the array, that index changes whenever items are prepended, inserted, or reordered. ◼ Educational objective: explain the second index parameter of map callbacks.

- [code] Array map and filter transformations:

```jsx title="Transformations.jsx"
const items = [{ id: '1', title: 'First' }, { id: '2', title: 'Second' }];
const elements = items.map(item => (
  <li key={item.id}>{item.title}</li> {/* Implicit return */}
));
const blockList = items.map(item => {
  return <li key={item.id}>{item.title}</li>; // Explicit return
});
const active = items.filter(item => item.id !== '1');
```

◼ **The what-this-introduces list:** 1. `items.map(item => ...)`: array transformation returning JSX elements. 2. `item => (...)`: implicit arrow return. 3. `item => { return ... }`: explicit return in block body. 4. `items.filter(...)`: array filtering producing matching subset.

### How React reconciles element arrays using persistent keys

- [runway] React element object structure, reconciliation matching, and key requirements, used by Question 2, Question 3, Question 4, and Question 5.

- [p] ★ {preknowledge: React element objects in memory} In Lecture 3, we learned that JSX tags compile into plain JavaScript objects called React elements. When you write `stories.map(story => <li key={story.id}>{story.title}</li>)`, the `map()` method creates an array of these lightweight element descriptors in memory. Inspecting one of these elements in the console reveals a plain object: `{ type: 'li', key: 's1', props: { children: 'City Transit Plan' } }`. Notice that `key` sits on the element object itself, alongside `type` and `props`. ◼ Educational objective: show the physical shape of React element objects in memory and highlight the key property.

- [p] ★ {mechanism: reconciliation and positional matching} When an application updates, React creates a new tree of element descriptions and compares it to the previous tree to determine what needs to change in the real DOM. When comparing lists of child elements, React must figure out which element in the new list corresponds to which element in the old list. Without keys, React falls back to **positional matching**: it assumes the first new item matches the first old item, the second matches the second, and so on. If an item is added to the top of the array, every subsequent item shifts down one position, causing React to rewrite existing DOM nodes in place and break internal element state. ◼ Educational objective: explain React list reconciliation and the failure mode of positional matching.

- [p] ★ {mechanism: element identity through keys} A **key** is a special string or number passed to JSX elements in an array that gives each item a permanent **element identity**. React uses the key to track each item throughout its lifecycle across renders. When a key is present, React does not pair elements by their index position; instead, it matches old and new elements that share the exact same key. If an item moves from the first position to the fifth position, React reuses the existing DOM node and moves it in the page, preserving input values, focus, and scroll position. ◼ Educational objective: define element identity and explain how keys enable node reuse and movement.

- [code] Keyed element array structure:

```jsx title="KeyedElements.jsx"
const stories = [{ id: 's1', title: 'Transit Plan' }];
const elements = stories.map(story => (
  <li key={story.id}>{story.title}</li> {/* Assigns stable key */}
));
console.log(elements[0]); // Logs element object
```

◼ **The what-this-introduces list:** 1. `key={story.id}`: assigns permanent identity to the element. 2. `console.log(elements[0])`: logs plain element descriptor object. 3. `key: 's1'`: key stored on element descriptor alongside type and props.

### Principles of React: Rendering Lists and Keys

- [question-cycle] Question 1: An arrow function with braces renders an empty list
    - Question: "I have thirty headlines in an array. How do I get a row for each?"
    - Code and result: Inside `Feed`, the developer writes `{stories.map(story => { <li key={story.id}>{story.title}</li>; })}`. In React 19.3.0, the `<ul>` renders completely empty, and the browser console displays zero errors and zero warnings.
    - Verdict: does not do what the reader wanted.
    - Answer: In JavaScript, an arrow function followed by a curly brace `{` has a block body. A block body executes statements sequentially and returns `undefined` unless an explicit `return` keyword is written. Calling `stories.map()` with this callback collects thirty `undefined` values, returning `[undefined, undefined, ...]`. Because React's suppression whitelist renders zero DOM nodes for `undefined`, the `<ul>` renders completely empty with no errors. Calling `console.log(storyElements[0])` on a proper return produces a plain React element object with `type: 'li'`, `key: 's1'`, and `props: { children: 'Budget passes' }`.
    - Fix: Add an explicit `return <li key={story.id}>{story.title}</li>;`, or remove the curly braces to use an implicit return: `stories.map(story => <li key={story.id}>{story.title}</li>)`. Taught in runway "How JavaScript transforms data arrays with map and arrow functions".
    - Rule with boundary: Use `map()` to transform an array of data into an array of JSX elements, and ensure the callback returns an element. Boundary: if using a block body with curly braces, always write an explicit `return`.
    - Needs: array `map()` (runway), arrow function implicit return (runway), block body with `return` (runway), React element objects (runway, Lecture 3).
    - Diagram: ASCII diagram showing data array → map callback → array of React element objects → DOM painting.

> [!PRINCIPLE]
> **Principle 1: The map method turns an array of data into an array of elements**
> To build a list of elements from an array, call `map()` on the data. Each call runs the function on one item and collects what it returns into a new array. When the function uses curly braces, write **return**, or the call returns undefined and the list renders completely empty with no error.
>
> >> array transformation : converting an array of data objects into a new array of element descriptions using map
> >> explicit return : writing the return keyword inside a block body so a function outputs a value
>
> *We should do this:*
> `items.map(item => (`
> `  <li key={item.id}>{item.title}</li> {/* returns element */}`
> `))`
>
> *We should not do this:*
> `items.map(item => {`
> `  <li key={item.id}>{item.title}</li>; // returns undefined`
> `})`

- [question-cycle] Question 2: The console warns that each child needs a key
    - Question: "The console says each child needs a key. Where does it go?"
    - Code and result: The row is extracted into a child component `<StoryItem story={story} />`. Inside `StoryItem`, the developer writes `<li key={story.id}>{story.title}</li>`. In `Feed`, they write `stories.map(story => <StoryItem story={story} />)`. In React 19.3.0, the browser console prints: "Warning: Each child in a list should have a unique "key" prop. Check the render method of `Feed`."
    - Verdict: does not do what the reader wanted.
    - Answer: React checks keys on the elements in the array returned directly by the `map()` callback. In `Feed`, `map()` returns an array of `<StoryItem />` elements. Placing `key` on the `<li>` inside `StoryItem` attaches it to a child tag inside `StoryItem`'s own render, not to the element in the mapped array. React cannot look inside `StoryItem` when reconciling the array. The key must be placed on the outermost element directly returned inside `map()`: `<StoryItem key={story.id} story={story} />`. Keys must be unique among siblings in that specific array; the same key in another array is fine. If a row returns multiple sibling nodes, wrap them in `<Fragment key={story.id}>`, because shorthand `<>...</>` cannot take attributes. Never put a key inside a spread object `{...props}`, because React warns that a key prop is being spread into JSX.
    - Fix: Place `key={story.id}` directly on `<StoryItem />` inside the `map()` callback. Taught in runway "How React reconciles element arrays using persistent keys".
    - Rule with boundary: Always place the `key` prop on the outermost element directly returned inside `map()`. Boundary: keys must be unique among sibling elements in that array; identical keys in a different array are completely valid.
    - Needs: `key` prop (runway), outermost element (runway), `<Fragment key={...}>` (recall, Lecture 3), JSX spread warning (recall, Lecture 7).
    - Diagram: ASCII diagram contrasting inner element key inside `StoryItem` (invisible to list reconciliation) vs outer element key on `<StoryItem key={...}>` (visible to array reconciliation).

> [!PRINCIPLE]
> **Principle 2: Put the key on the element written inside map**
> React checks keys on the elements in the array returned directly by `map()`. When you map to a component, put the key on that component, not on an HTML element inside it. A key on an inner tag does not identify the item in the array. Keys must be unique among sibling elements in that array.
>
> >> outermost element : the top-level JSX element returned directly by the map callback
> >> sibling uniqueness : the rule that keys must be distinct within the same array
>
> *We should do this:*
> `items.map(item => (`
> `  <ItemRow key={item.id} item={item} /> {/* key on mapped item */}`
> `))`
>
> *We should not do this:*
> `items.map(item => (`
> `  <ItemRow item={item} /> {/* missing key on component */}`
> `))`

- [question-cycle] Question 3: Text typed into a row jumps when a story is added at the top
    - Question: "The list looks right without keys. What does the key do?"
    - Code and result: The feed maps stories with `key={index}` (or no keys). Each row contains an `<input placeholder="Add note..." />`. The reader types "verify numbers" into the input of the first story ("City Transit Accord"). An urgent story ("Urgent Alert") is prepended to the array at index 0 and rendered with `root.render`. In React 19.3.0, the first row shows "Urgent Alert" with the typed text "verify numbers", while the transit story shows an empty input!
    - Verdict: does not do what the reader wanted.
    - Answer: React uses keys to match each element in a new render with an element from the previous render. Without keys, or when using array indices, React defaults to positional matching: old index 0 matches new index 0, old index 1 matches new index 1. The browser's typed input text lives inside the physical DOM `<input>` element. When the new story enters at index 0, React updates the title text of the existing DOM node at index 0, but leaves the internal input buffer untouched. The typed text stays in the first physical node, now attached to the wrong article. With stable data keys (`key={story.id}`), React matches the old transit element to the new transit element. It moves the existing DOM node and its typed text down to index 1, and inserts a fresh DOM node at index 0.
    - Fix: Use a stable ID from the data (`key={story.id}`). Handed to Principle 4.
    - Rule with boundary: Use keys to give each element an identity that React tracks across renders. Boundary: positional matching occurs whenever keys are omitted or set to array indices.
    - Needs: positional diffing (runway), element identity across renders (runway), typed input buffer in DOM (runway), second `root.render` (recall, Lecture 9).
    - Diagram: ASCII diagram comparing positional diffing (DOM node 0 stays in place, text attaches to wrong story) vs key identity matching (DOM node 0 moves to position 1, input text travels with story).

> [!PRINCIPLE]
> **Principle 3: The key is how React finds the same row on the next render**
> On the next render, React pairs each new element with an old one that shares the same key. When keys match, React keeps the existing browser DOM node, along with whatever the user typed into it. Without keys, or with array indices, React matches items by position. Adding an item at the top forces the new item into the first DOM node, leaving old typed text attached to the wrong content.
>
> >> element identity : a persistent identifier that ties an element to its physical DOM node across renders
> >> positional diffing : matching items by index order when keys are missing or based on index
>
> *We should do this:*
> `items.map(item => (`
> `  <li key={item.id}><input /></li> {/* node moves with id */}`
> `))`
>
> *We should not do this:*
> `items.map((item, index) => (`
> `  <li key={index}><input /></li> {/* text jumps to wrong row */}`
> `))`

- [question-cycle] Question 4: A random key makes every input lose its focus and text
    - Question: "The stories have no field I like. Can I use the index, or Math.random()?"
    - Code and result: Inside `stories.map()`, the developer writes `key={Math.random()}`. The reader types a note into an input. When the component re-renders, the typed text vanishes, and input focus disappears.
    - Verdict: does not do what the reader wanted.
    - Answer: A key must remain constant for the same data entity across renders. Because `Math.random()` executes on every render, every element receives a completely new key on every update. React compares the new keys with the old keys, finds zero matches, and concludes that all previous elements were deleted and completely new elements were created. It tears down all existing DOM nodes and rebuilds them from scratch. This drops keyboard focus, wipes typed input text, and slows down the application. Array indices are also unsafe because inserting or removing an item shifts the index of every subsequent item. A key should come from the data: a database ID (`story.id`), or an ID generated once when the item is created using `crypto.randomUUID()`.
    - Fix: Use a permanent ID from the data (`key={story.id}`) or an ID created once at data inception.
    - Rule with boundary: Always use a stable identifier from your data as the key. Boundary: the array index is acceptable only for a completely static list that never inserts, deletes, or changes order.
    - Needs: `Math.random()` generates new key on every render (runway), `crypto.randomUUID()` (runway), static list boundary (runway).
    - Diagram: ASCII diagram contrasting `key={Math.random()}` (random key churn, full DOM teardown and input loss) vs `key={item.id}` (stable identity, DOM reuse).

> [!PRINCIPLE]
> **Principle 4: Use a stable ID from the data as the key**
> A key must remain the same for the same item across renders. Generating keys with Math.random runs on every render, so no keys ever match and React tears down and rebuilds every DOM node from scratch. Use a permanent ID from the data, such as a database ID or an ID made once with crypto.randomUUID. The array index is safe only for a static list that never inserts, deletes, or changes order.
>
> >> stable identifier : a permanent ID that remains identical for the same data entity across renders
> >> random key churn : generating keys during render, forcing React to destroy and rebuild all DOM nodes
>
> *We should do this:*
> `items.map(item => (`
> `  <li key={item.id}><input /></li> {/* stable database ID */}`
> `))`
>
> *We should not do this:*
> `items.map(item => (`
> `  <li key={Math.random()}><input /></li> {/* rebuilds DOM */}`
> `))`

- [question-cycle] Question 5: Reading props.key inside a row returns undefined
    - Question: "StoryItem needs the story's id. Can it read props.key?"
    - Code and result: Inside `StoryItem`, the component attempts to read `props.key`, rendering `<li data-id={props.key}>{story.title}</li>`. In the rendered DOM, `data-id` is absent, and the browser console prints: "Warning: StoryItem: `key` is not a prop. Trying to access it will result in `undefined` being returned. If you need to access the same value within the child component, you should pass it as a different prop."
    - Verdict: does not do what the reader wanted.
    - Answer: React reserves the `key` prop for its internal reconciliation engine. When React creates an element, it extracts `key` and stores it directly on the element object, intentionally excluding it from `props`. Inside `StoryItem`, `props.key` is `undefined`. If the child component needs the identifier—to construct a URL, set an HTML `data-` attribute, or send an ID to an event handler—pass the ID under an ordinary prop name such as `itemId={story.id}`, or pass the entire `story` object and read `story.id`.
    - Fix: Pass the ID as its own dedicated prop: `<StoryItem key={story.id} storyId={story.id} story={story} />`, or read `story.id` from `props.story`.
    - Rule with boundary: Pass an item's identifier as a dedicated prop when the component needs to read it. Boundary: `key` is reserved for React's reconciler and is never available on `props`.
    - Needs: `props.key` returns `undefined` (runway), reserved prop concept (runway), passing ID as separate prop (recall, Lecture 6).
    - Diagram: ASCII diagram showing React element object structure with `key` stored as an internal element property outside `props`.

> [!PRINCIPLE]
> **Principle 5: The key is not a prop, so pass the id again**
> React reserves the key prop for itself and excludes it from the component's props object. Reading props.key inside a component yields undefined and prints a console warning. When a component needs the item's identifier for links, attributes, or handlers, pass that identifier under a different prop name or read it from the data object.
>
> >> reserved prop : a prop like key that React consumes internally and excludes from component props
> >> explicit prop passing : passing an identifier under its own prop name so child components can read it
>
> *We should do this:*
> `function Item({ item, id }) {`
> `  return <li data-id={id}>{item.name}</li>; // reads id prop`
> `}`
>
> *We should not do this:*
> `function Item(props) {`
> `  return <li data-id={props.key}>{props.name}</li>; // undefined`
> `}`

### For the interview

- [interview] The Interview Question: How do you render a list from an array, and why does React demand a key on every item?
- [interview] 1. The Hidden Signal: The interviewer is probing whether you understand React's reconciliation engine and DOM node preservation, or merely memorized syntax to silence a console warning. A junior developer recites map syntax and claims keys make React faster. A senior engineer explains that keys establish persistent element identity across renders. They contrast positional diffing against key-based matching, explaining that keys allow React to move existing DOM nodes and preserve uncontrolled state during insertions and reordering.
- [interview] 2. The Classic Trap: The classic trap is reaching for the array index as a convenient key (`key={index}`). Candidates assume index keys are safe because they silence the console warning. But when an item is prepended at index 0, every existing item's index shifts by one. React compares index 0 to index 0, mutating the existing DOM node in place while leaving internal input text, focus, and audio playback attached to the wrong item. Another trap is generating keys on the fly with `key={Math.random()}`, which forces React to destroy and recreate the entire DOM tree on every single render.
- [interview] 3. What is Actually Going On: In React, you call `map()` on an array of data. Each call returns a JSX element descriptor, and React unpacks the resulting array in order. If the arrow function has a block body with curly braces, you must write an explicit `return`, or the list renders empty. React needs a unique, stable `key` on every element directly returned by `map()`. React uses that key to pair new elements with old elements on subsequent renders. When keys match, React moves the existing DOM node in place. Without keys, React compares items by array position, overwriting content and scrambling user inputs.
- [interview] 4. Where It Gets Tricky: What happens if a list row component tries to read `props.key`? React reserves `key` for its own reconciler and strips it from props; `props.key` evaluates to `undefined` and triggers a console warning. If the child needs the ID, pass it under a separate prop like `id={story.id}`. What happens if you need to render multiple sibling tags from a single mapped item without an extra wrapper `<div>`? You cannot use shorthand `<>...</>` because shorthand fragments cannot accept attributes; you must import `Fragment` from `'react'` and write `<Fragment key={story.id}>`. When is the array index safe to use? The index is safe only when the list is completely static: items are never inserted, deleted, filtered, or reordered.

### Glossary

- [glossary] Array Transformation ◼ Using methods like map to project an array of raw data objects into a new array of JSX element descriptors.
- [glossary] Key Prop ◼ A special string or number attribute passed to list elements that React uses to identify items across renders.
- [glossary] Positional Diffing ◼ React's fallback reconciliation behavior when keys are absent or based on array index, comparing elements purely by sequential position.
- [glossary] Element Identity ◼ The association between a React virtual element and its persistent browser DOM node established by a stable key.
- [glossary] Key Churn ◼ An antipattern where keys change on every render (such as from Math.random), forcing React to destroy and recreate all DOM nodes.
- [glossary] Reserved Prop ◼ A prop such as key or ref that React consumes internally for reconciliation and does not pass down to the component.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Array Transformation & Return Syntax

➔ ALWAYS use `array.map()` to project data arrays into JSX element arrays inside curly braces.

➔ IF using a block body (`=> { ... }`) in a `map` callback THEN write an explicit `return` statement to prevent rendering an empty list.

❒ Key Placement & Multi-Node Grouping

➔ ALWAYS place the `key` prop on the outermost element directly returned by the `map()` callback.

➔ IF an item returns multiple sibling nodes without a wrapper tag THEN use `<Fragment key={item.id}>` instead of shorthand `<>...</>`.

❒ Key Source & Reconciliation Safety

➔ ALWAYS use permanent, stable entity IDs from your data (such as database IDs) as list keys.

➔ NEVER use `Math.random()` to generate keys during render, which causes complete DOM teardown on every update.

➔ IF a list is dynamic THEN avoid array indices as keys to prevent state drift and input bugs.

**DO THIS:** use stable entity IDs as keys on the outermost element returned by map

```jsx right
{stories.map(story => (
  <StoryItem key={story.id} story={story} />
))}
```

**DO NOT DO THIS:** use array indices as keys for dynamic lists

```jsx wrong
{stories.map((story, index) => (
  <StoryItem key={index} story={story} />
))}
```
