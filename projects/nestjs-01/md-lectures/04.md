### Route Paths versus URL Query Strings

When a web browser or mobile application interacts with an API, the full URL conveys two separate categories of information: the identity of the target resource, and the presentation instructions for that resource.

The URL path (such as `/products`) identifies the specific resource collection. Everything following the `?` delimiter is the **query string** (a series of key-value pairs appended to a URL to specify optional modifiers like filtering, sorting, and pagination without changing the identity of the resource).

In traditional Node.js development, extracting query parameters requires importing the native URL module and manually parsing search parameters from the request stream on every incoming call.

```typescript title="Manual Query Parser"
import http from 'node:http';
import { URL } from 'node:url';

const server = http.createServer((req, res) => {
  const parsedUrl = new URL(req.url, 'http://localhost:3000');
  const sort = parsedUrl.searchParams.get('sort'); // **WRONG:** manually parses URL search strings on each **REQUEST**
  res.writeHead(200, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({ sort: sort || 'name' }));
});
```

This manual parsing creates noisy boilerplate. Across an enterprise platform with dozens of searchable feeds, repeating URL parsing logic invites bugs, complicates testing, and obscures the core business logic of your route handlers.

### Capturing Query Strings with the Query Decorator

To capture query parameters declaratively, NestJS provides the **`@Query()` decorator** (a parameter decorator that extracts parsed URL query string parameters from the incoming HTTP request and injects them as arguments into your route handler).

Under the hood, the underlying HTTP platform automatically splits the URL at the `?` character and parses the key-value pairs into a JavaScript dictionary. The `@Query()` decorator exposes that dictionary directly to your handler.

NestJS allows you to use `@Query()` in two distinct ways:
1. **Named parameter extraction**: passing a string key, such as `@Query('sort') sort: string`, extracts that single property directly from the query string.
2. **Whole query object extraction**: invoking `@Query()` without arguments injects the complete dictionary containing every parameter submitted by the client.

For an endpoint with only one query flag, extracting a named parameter directly is concise. However, real-world catalog endpoints frequently accept multiple options simultaneously, including sorting criteria, sort direction, page numbers, and category filters.

### Structuring Queries with Query DTOs

When an endpoint accepts several query parameters, listing each one as an independent `@Query()` method argument creates bloated and unwieldy method signatures. To maintain clean architecture, NestJS encourages packaging related query parameters into a Data Transfer Object class.

Using a dedicated DTO class for query parameters provides several key benefits: it groups optional parameters into a cohesive schema, enables IDE autocompletion, documents expected search options, and provides a target for runtime validation pipes.

To see this in action on The National Times online store, our product listing endpoint coordinates three files. First, `list-products.dto.ts` defines the accepted query options. Second, `products.controller.ts` exposes `GET /products` and extracts the query options using `@Query()`. Third, `app.module.ts` registers the controller. When a client requests `GET /products?sort=rating`, the controller extracts the sort parameter and returns the products ordered by customer rating.

```components title="national-times-api — Component Explorer"
app.module.ts | mounts application controllers | shell
  products.controller.ts | GET /products?sort=rating | navigation
    list-products.dto.ts | query parameters | form | sort="rating";; [{"id": 401, "name": "Archive Book", "rating": **4.9**}]
```

The component explorer panel above illustrates this structure. On the left, the file hierarchy shows `list-products.dto.ts` in `src/`, `products.controller.ts` in `controllers/`, and `app.module.ts` in `modules/`. On the right, `app.module.ts` mounts `products.controller.ts`, which nests `list-products.dto.ts`. When a request arrives with `?sort=rating`, the controller applies the sort parameter and produces the observable response: a list starting with the highest-rated Archive Book.

Here is `list-products.dto.ts` declaring the query contract:

```ts title="list-products.dto.ts"
export class ListProductsDto {
  sort?: string; // **RIGHT:** declares optional sorting criteria on **DTO**
  limit?: string; // **RIGHT:** captures optional page size limit **PARAMETER**
}
```

Here is `products.controller.ts` consuming the query DTO:

```ts title="products.controller.ts"
import { Controller, Get, Query } from '@nestjs/common';
import { ListProductsDto } from './list-products.dto';

@Controller('products')
export class ProductsController {
  @Get()
  findAll(@Query() query: ListProductsDto) {
    const sort = query.sort || 'name';
    return [
      { id: 401, name: 'Archive Book', rating: 4.9 },
      { id: 402, name: 'Canvas Tote', rating: 4.6 },
    ]; // **RIGHT:** applies query parameter to order catalog **DATA**
  }
}
```

And here is `app.module.ts` registering the controller:

```ts title="app.module.ts"
import { Module } from '@nestjs/common';
import { ProductsController } from './products.controller';

@Module({
  controllers: [ProductsController], // **RIGHT:** mounts products controller to expose query **ROUTING**
})
export class AppModule {}
```

### Route Parameters versus Query Parameters: When to Use Which

A common design challenge for backend developers is deciding whether an incoming value belongs in a route path or in a query string.

To make the right choice, evaluate whether the parameter defines the identity of the resource or merely modifies how a collection is displayed:
- **Use Route Parameters (`@Param`)** when identifying a specific entity. In the URL `/products/401`, the ID `401` is an essential part of the resource's identity. If you omit `401`, the URL changes entirely and points to the whole collection rather than a single product. Route parameters are mandatory for matching the endpoint.
- **Use Query Parameters (`@Query`)** when filtering, sorting, searching, or paginating a collection. In the URL `/products?sort=rating`, the endpoint still targets the general `/products` resource, but asks the server to arrange the result differently. If the client omits the query string entirely, the request still succeeds and returns the default view.

### Query String Parsing and the String Type Reality

Just like route parameters captured by `@Param()`, all query parameters extracted by `@Query()` arrive as JavaScript `string` primitives at runtime.

Even if you declare a property as `limit?: number` in your TypeScript DTO, TypeScript types are completely erased during compilation. When a client requests `/products?limit=25`, the runtime value of `query.limit` is the string `'25'`, not the number `25`.

If your code performs arithmetic like `query.limit + 10`, JavaScript performs string concatenation instead of addition, resulting in the string `'2510'` rather than `35`. In future lectures, you will learn how NestJS transformation pipes automatically parse strings into validated numbers and booleans before your handler runs. Until pipes are applied, treat all incoming query parameters as strings or `undefined`.

> [!KEY]
> Query parameters are optional modifiers used for filtering, sorting, and pagination, and they are always extracted as string primitives by default.

> [!TIP]
> **To impress the interviewer:** Clearly differentiate the semantic roles of `@Param()` versus `@Query()` in REST API design. Explain that `@Param()` captures path tokens that uniquely identify a specific resource (such as `/products/:id`), making the value mandatory for route matching. In contrast, `@Query()` extracts optional modifiers that filter, sort, or paginate a collection (such as `?sort=price&limit=20`) without changing the identity of the underlying endpoint.

### Where you will meet this

- E-commerce product catalogs: parsing `GET /products?category=books&sort=price` to filter and sort inventory for shoppers.
- Editorial archive searches: handling `GET /articles?q=election&author=elena` to power full-text investigative search.
- Paginated subscriber tables: accepting `GET /subscribers?page=3&limit=50` to deliver manageable slices of account records to billing administrators.

### Summary

**URL Query Parameters and Collection Modifiers**

In daily production, providing responsive filtering, sorting, and pagination while maintaining clean route signatures defines whether your API endpoints remain adaptable to client requirements. While manual URL parsing is fragile, NestJS leverages `@Query()` and class-based DTOs to provide structured parameter extraction. Here is your streetwise review.

❒ Query Extraction and DTO Encapsulation

1. Avoid **manually parsing query strings from the raw request URL** inside controller methods.<br>&nbsp;&nbsp;&nbsp;&nbsp;**DO NOT DO THIS:** Using manual string splitting or native URL searchParams instances inside handlers creates clutter.
```typescript wrong
@Get()
findAll(@Req() req: any) {
  const url = new URL(req.url, 'http://localhost');
  return url.searchParams.get('sort');
}
```
&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Use the `@Query()` decorator to inject parsed query parameters directly.
```typescript right
@Get()
findAll(@Query('sort') sort: string) {
  return { sort };
}
```
2. Group multi-parameter query collections inside **dedicated query DTO classes**.<br>&nbsp;&nbsp;&nbsp;&nbsp;**DO NOT DO THIS:** Declaring numerous individual `@Query()` parameters in a method signature degrades readability.
```typescript wrong
@Get()
findAll(
  @Query('sort') sort: string,
  @Query('limit') limit: string,
  @Query('page') page: string
) {
  return [];
}
```
&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Bundle related query parameters into a structured DTO class with optional properties.
```typescript right
@Get()
findAll(@Query() query: ListProductsDto) {
  return [];
}
```

❒ Semantic Boundaries: Route Parameters versus Query Parameters

1. Always use **route parameters for resource identity and query parameters for presentation modifiers**.<br>&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Keep path segments reserved for identifying entities and query parameters for filtering.
```typescript right
@Get(':id')
findOne(
  @Param('id') id: string,
  @Query('includeDetails') includeDetails: string
) {
  return { id, includeDetails };
}
```

➔ NEVER use query parameters to identify a specific, mandatory resource entity.

➔ ALWAYS supply sensible fallback defaults when reading optional query parameters.

➔ IF an endpoint accepts multiple query parameters THEN **package them inside a dedicated class-based DTO**.

| | **ROUTE PARAMETERS**<br>(@Param) | **QUERY PARAMETERS**<br>(@Query) |
| ---: | :--- | :--- |
| **URL location** | Embedded inside path before the `?` delimiter | Appended after the `?` question mark |
| **Cardinality** | Mandatory segment required to match route | Optional modifiers that alter presentation |
| **Primary purpose** | Uniquely identifies a specific resource | Filters, sorts, or paginates collections |
| **Missing value** | Fails route match and returns 404 error | Evaluates to `undefined` if omitted |
| **Syntax pattern** | Declared with `:id` and read with<br>`@Param('id')` | Passed as `k=v` and read with<br>`@Query('k')` |
