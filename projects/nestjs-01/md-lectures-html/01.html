What is a Controller in NestJS?

Imagine this scenario:

  1. A new developer joins the team building the news website server for The National Times.
  2. The mobile app needs a list of staff writers, because readers want to verify who wrote each story.
  3. The developer writes a TypeScript function that returns the names of three staff writers.
  4. The developer starts the server, but every request to /users receives a 404 Not Found error.
  5. Why does the server return a 404 error when the function is already finished?
  6. The server receives the network traffic, but has no map connecting that web address to the function.
  7. Today you will learn how the server connects incoming web addresses to your code.

The Missing Bridge Between Network and Code

When a web client sends an HTTP request over the network to a Node.js server, the incoming packet arrives as raw bytes on a network socket. The operating system hands these bytes to the Node.js process. However, a plain TypeScript class or function sitting inside your application files does not automatically listen to network traffic. Without an explicit routing system, the server has no way of knowing which file or function is supposed to handle a request directed at /users.

In traditional Node.js or Express applications, developers manually wire routes by attaching callback functions to an application instance.

As an enterprise application grows, this manual approach becomes unmanageable. In a production newsroom platform like The National Times, you manage hundreds of endpoints across subscriber accounts, editorial stories, reader comments, and analytics feeds. Scattering procedural conditional statements or loose route callbacks across multiple files leaves routing brittle and disconnected. There is no structured contract for input validation, no separation between network parsing and business logic, and testing an endpoint requires mocking low-level socket streams and response objects.

What is a Controller?

To solve this fragmentation, NestJS organizes the entry point of your application around a dedicated architectural layer. This mechanism is called a controller (a TypeScript class annotated with metadata decorators that receives incoming HTTP requests and returns formatted responses to the client).

Controllers act as the front door for incoming web traffic. When an HTTP request reaches the server, the NestJS routing engine inspects the HTTP method (such as GET, POST, PUT, or DELETE) and the destination URL path (such as /users). The routing engine matches that path against your application controllers and forwards the request to the exact method responsible for handling it. The controller inspects any incoming parameters or payloads, delegates data retrieval to the appropriate services, and returns the result.

In standard TypeScript, classes are simply blueprints for objects. If you write a plain class named UsersController, TypeScript treats it as ordinary data and methods. Nothing inside a standard class instructs Node.js to bind a network port or parse HTTP request headers. To transform a plain TypeScript class into an active web endpoint, NestJS uses decorators (special functions prefixed with an @ symbol that attach routing metadata and configuration instructions to classes and methods).

To see this in action on The National Times, our staff directory endpoint requires two files working together. First, users.controller.ts declares the route and returns the staff roster. Second, app.module.ts registers the controller into the root application module so NestJS knows to mount it. When a client performs a GET /users request, the server executes the controller method, serializes the returned staff array, and sends back an HTTP 200 OK status code.

Anatomy of Route Mapping and Path Prefixes

Let us examine the two decorators that make this controller work:

The @Controller() decorator accepts an optional route path prefix string. In our example, passing 'users' establishes /users as the base route for every method declared inside UsersController. Using a controller-level prefix groups related endpoints together and prevents repeating /users on every individual route handler.

Above the findAll() method, we attach the @Get() HTTP request method decorator. This decorator instructs NestJS to create an endpoint mapping that listens specifically for HTTP GET requests. Because no additional path argument was passed to @Get(), the full route path is simply the controller prefix: GET /users.

If we need an endpoint for active staff members, we can add a second method with @Get('active'). NestJS concatenates the controller prefix with the method path to produce GET /users/active. The method name itself (findAll) is completely arbitrary. NestJS does not infer routing behavior from TypeScript method names, but relies entirely on the decorators you provide.

Notice what the findAll() method returns. It returns a plain JavaScript array containing two user objects. In traditional Express code, you had to call res.status(200).json(...) to set headers and serialize data. NestJS introduces standard response handling (the built-in mechanism where returning a JavaScript object or array automatically serializes it to JSON and defaults the status code to 200 OK, or 201 Created for POST requests). If you return a primitive string or number, NestJS sends the raw value without JSON encoding. You simply return the data, and the framework takes care of network transmission.

Key Takeaway

In NestJS, returning a JavaScript object or array automatically serializes the payload to JSON with an HTTP 200 OK status code.

Activating the Controller in a Module

Writing a controller class and saving users.controller.ts to disk does not immediately start serving requests. NestJS does not crawl your filesystem looking for files ending in .controller.ts. It requires an explicit architectural structure to know which controllers exist and how they fit into the application.

Every controller in NestJS must belong to a module (a class decorated with @Module() that provides metadata NestJS uses to organize the application dependency graph). To expose UsersController to the network, we register it inside the controllers array of our root AppModule.

app.module.ts
1import { Module } from '@nestjs/common';
2import { UsersController } from './users.controller';
3
4@Module({
5 controllers: [UsersController],
RIGHT: registers the controller so NestJS builds its ROUTES
6})
7export class AppModule {}

When the application boots via NestFactory.create(AppModule), NestJS reads the metadata attached to AppModule. It discovers UsersController in the controllers array, instantiates the class, scans its decorated methods, and registers the route GET /users with the underlying HTTP server. Now, when a client sends a request to /users, the server resolves the route, calls findAll(), and returns the staff list.

Standard Response Handling versus the Library-Specific Escape Hatch

While standard response handling covers nearly all real-world requirements, developers coming from Express often reach for the underlying response object. NestJS provides the @Res() decorator to inject the platform-native response object directly into a handler method signature.

However, using @Res() comes with serious architectural drawbacks. When NestJS detects @Res() on a handler, it automatically disables standard response handling for that route. The developer becomes entirely responsible for managing the response lifecycle, including setting HTTP headers, status codes, and manually invoking res.send() or res.json(). If the developer forgets to call res.send(), the HTTP request hangs indefinitely. Furthermore, using @Res() ties your codebase directly to Express, breaking compatibility with alternative HTTP engines like Fastify and bypassing NestJS features such as interceptors and @HttpCode().

Interview Tip

To impress the interviewer: Emphasize that NestJS controllers act strictly as traffic coordinators, not business logic engines. A senior developer keeps controllers thin by delegating data retrieval and complex calculations to injectable providers, while letting the controller focus exclusively on capturing HTTP parameters, validating payloads, and mapping responses. Always favor Nest's standard declarative response model over injecting @Res(), which breaks lifecycle interceptors and couples code to Express.

Where you will meet this

  • Staff directory APIs: mapping GET /users to return active journalists, department designations, and office locations to internal newsroom dashboards.
  • Editorial publication feeds: exposing GET /articles to deliver real-time headline updates and story summaries to reader mobile applications.
  • Subscription billing webhooks: receiving POST /webhooks/stripe payloads to update reader member tiers when monthly renewal payments clear.
  • Account preference endpoints: accepting PATCH /account/preferences requests to update reader newsletter choices and display settings.

Summary

Decorated Controllers and Request Routing

In daily production, choosing between procedural route handlers and declarative NestJS controllers defines how cleanly your backend scales. While manual routing requires wiring callbacks and managing HTTP serialization step by step, NestJS controllers encapsulate route mapping and response handling into structured TypeScript classes. Here is your streetwise review.

❒ Routing Architecture and Separation of Concerns

  1. Avoid manual route dispatching and procedural URL parsing in favor of structured classes.
        DO NOT DO THIS: Parsing URL paths with procedural conditional blocks scatters routing logic and complicates maintenance.
    app.get('/users', (req, res) => {
    res.json({ users: [] });
    });
        DO THIS: Define dedicated controller classes decorated with explicit HTTP method metadata.
    @Controller('users')
    export class UsersController {
    @Get()
    findAll() {
    return { users: [] };
    }
    }
  2. Eliminate manual serialization and header configuration by letting the framework handle responses.
        DO NOT DO THIS: Manually invoking JSON stringification and status code headers creates boilerplate across every route.
    res.writeHead(200, {
    'Content-Type': 'application/json'
    });
    res.end(JSON.stringify(data));
        DO THIS: Return raw JavaScript objects or arrays directly from your controller methods.
    @Get()
    findAll() {
    return this.users;
    }

❒ Module Registration and Response Serialization

  1. Always bind controllers inside cohesive module boundaries.
        DO THIS: Register every controller in its owning module to expose routes to the underlying HTTP server.
    @Module({
    controllers: [UsersController],
    })
    export class AppModule {}

➔ NEVER parse raw request paths with manual procedural switch statements or scattered callbacks.

➔ ALWAYS decorate controller classes and route methods with explicit HTTP metadata.

➔ IF an endpoint returns data THEN return standard objects or arrays for automatic JSON serialization.
