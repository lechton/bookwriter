Lecture 1: Controllers and Incoming HTTP Requests

Interview Question

CORE

What is a Controller in NestJS?

Imagine this scenario:

  1. A new developer joins the team building the news website server for The National Times.
  2. The mobile app needs a list of staff writers, because readers want to verify who wrote each story.
  3. The developer writes a TypeScript function that returns the names of three staff writers.
  4. The developer starts the server, but every request to /users receives a 404 Not Found error.
  5. Why does the server return a 404 error when the function is already finished?
  6. The server receives the network traffic, but has no map connecting that web address to the function.
  7. Today you will learn how the server connects incoming web addresses to your code.

The Missing Bridge Between Network and Code

When a web client sends an HTTP request over the network to a Node.js server, the incoming packet arrives as raw bytes on a network socket. The operating system hands these bytes to the Node.js process. However, a plain TypeScript class or function sitting inside your application files does not automatically listen to network traffic. Without an explicit routing system, the server has no way of knowing which file or function is supposed to handle a request directed at /users.

In traditional Node.js or Express applications, developers manually wire routes by attaching callback functions to an application instance.

Vanilla HTTP Route

4 if (req.url === '/users' && req.method === 'GET') {
5 res.writeHead(200, { 'Content-Type': 'application/json' });
6 res.end(JSON.stringify([{ id: 1, name: 'Elena Rostova' }]));

As an enterprise application grows, this manual approach becomes unmanageable. In a production newsroom platform like The National Times, you manage hundreds of endpoints across subscriber accounts, editorial stories, reader comments, and analytics feeds. Scattering procedural conditional statements or loose route callbacks across multiple files leaves routing brittle and disconnected. There is no structured contract for input validation, no separation between network parsing and business logic, and testing an endpoint requires mocking low-level socket streams and response objects.

What is a Controller?

To solve this fragmentation, NestJS organizes the entry point of your application around a dedicated architectural layer. This mechanism is called a controller (a TypeScript class annotated with metadata decorators that receives incoming HTTP requests and returns formatted responses to the client).

Controllers act as the front door for incoming web traffic. When an HTTP request reaches the server, the NestJS routing engine inspects the HTTP method (such as GET, POST, PUT, or DELETE) and the destination URL path (such as /users). The routing engine matches that path against your application controllers and forwards the request to the exact method responsible for handling it. The controller inspects any incoming parameters or payloads, delegates data retrieval to the appropriate services, and returns the result.

In standard TypeScript, classes are simply blueprints for objects. If you write a plain class named UsersController, TypeScript treats it as ordinary data and methods. Nothing inside a standard class instructs Node.js to bind a network port or parse HTTP request headers. To transform a plain TypeScript class into an active web endpoint, NestJS uses decorators (special functions prefixed with an @ symbol that attach routing metadata and configuration instructions to classes and methods).

To see this in action on The National Times, our staff directory endpoint requires two files working together. First, users.controller.ts declares the route and returns the staff roster. Second, app.module.ts registers the controller into the root application module so NestJS knows to mount it. When a client performs a GET /users request, the server executes the controller method, serializes the returned staff array, and sends back an HTTP 200 OK status code.

Anatomy of Route Mapping and Path Prefixes

Let us examine the two decorators that make this controller work:

The @Controller() decorator accepts an optional route path prefix string. In our example, passing 'users' establishes /users as the base route for every method declared inside UsersController. Using a controller-level prefix groups related endpoints together and prevents repeating /users on every individual route handler.

Above the findAll() method, we attach the @Get() HTTP request method decorator. This decorator instructs NestJS to create an endpoint mapping that listens specifically for HTTP GET requests. Because no additional path argument was passed to @Get(), the full route path is simply the controller prefix: GET /users.

If we need an endpoint for active staff members, we can add a second method with @Get('active'). NestJS concatenates the controller prefix with the method path to produce GET /users/active. The method name itself (findAll) is completely arbitrary. NestJS does not infer routing behavior from TypeScript method names, but relies entirely on the decorators you provide.

Notice what the findAll() method returns. It returns a plain JavaScript array containing two user objects. In traditional Express code, you had to call res.status(200).json(...) to set headers and serialize data. NestJS introduces standard response handling (the built-in mechanism where returning a JavaScript object or array automatically serializes it to JSON and defaults the status code to 200 OK, or 201 Created for POST requests). If you return a primitive string or number, NestJS sends the raw value without JSON encoding. You simply return the data, and the framework takes care of network transmission.

Key Takeaway

In NestJS, returning a JavaScript object or array automatically serializes the payload to JSON with an HTTP 200 OK status code.

Activating the Controller in a Module

Writing a controller class and saving users.controller.ts to disk does not immediately start serving requests. NestJS does not crawl your filesystem looking for files ending in .controller.ts. It requires an explicit architectural structure to know which controllers exist and how they fit into the application.

Every controller in NestJS must belong to a module (a class decorated with @Module() that provides metadata NestJS uses to organize the application dependency graph). To expose UsersController to the network, we register it inside the controllers array of our root AppModule.

app.module.ts
1import { Module } from '@nestjs/common';
2import { UsersController } from './users.controller';
3
4@Module({
5 controllers: [UsersController],
RIGHT: registers the controller so NestJS builds its ROUTES
6})
7export class AppModule {}

When the application boots via NestFactory.create(AppModule), NestJS reads the metadata attached to AppModule. It discovers UsersController in the controllers array, instantiates the class, scans its decorated methods, and registers the route GET /users with the underlying HTTP server. Now, when a client sends a request to /users, the server resolves the route, calls findAll(), and returns the staff list.

Standard Response Handling versus the Library-Specific Escape Hatch

While standard response handling covers nearly all real-world requirements, developers coming from Express often reach for the underlying response object. NestJS provides the @Res() decorator to inject the platform-native response object directly into a handler method signature.

However, using @Res() comes with serious architectural drawbacks. When NestJS detects @Res() on a handler, it automatically disables standard response handling for that route. The developer becomes entirely responsible for managing the response lifecycle, including setting HTTP headers, status codes, and manually invoking res.send() or res.json(). If the developer forgets to call res.send(), the HTTP request hangs indefinitely. Furthermore, using @Res() ties your codebase directly to Express, breaking compatibility with alternative HTTP engines like Fastify and bypassing NestJS features such as interceptors and @HttpCode().

Interview Tip

To impress the interviewer: Emphasize that NestJS controllers act strictly as traffic coordinators, not business logic engines. A senior developer keeps controllers thin by delegating data retrieval and complex calculations to injectable providers, while letting the controller focus exclusively on capturing HTTP parameters, validating payloads, and mapping responses. Always favor Nest's standard declarative response model over injecting @Res(), which breaks lifecycle interceptors and couples code to Express.

Where you will meet this

  • Staff directory APIs: mapping GET /users to return active journalists, department designations, and office locations to internal newsroom dashboards.
  • Editorial publication feeds: exposing GET /articles to deliver real-time headline updates and story summaries to reader mobile applications.
  • Subscription billing webhooks: receiving POST /webhooks/stripe payloads to update reader member tiers when monthly renewal payments clear.
  • Account preference endpoints: accepting PATCH /account/preferences requests to update reader newsletter choices and display settings.

Lecture 2: Extracting Dynamic Route Parameters

Interview Question

CORE

How do you extract a dynamic ID from a route path?

Imagine this scenario:

  1. A developer builds the staff directory for the newsroom dashboard at The National Times.
  2. The dashboard displays author profiles with employee numbers, because payroll tracks journalists by unique employee numbers.
  3. The developer writes an endpoint to display the profile for employee number 123.
  4. When a manager clicks on employee 456, the screen still displays the profile for employee 123.
  5. Why does the server return profile 123 when the request asked for 456?
  6. The server code hardcoded one fixed number into the web address instead of reading the incoming number.
  7. Today you will learn how the server captures dynamic values directly from incoming web addresses.

The Pitfall of Static Route Paths

In Lecture 1, we registered static routes such as @Get() under the @Controller('users') prefix. That static route maps directly to the fixed URL GET /users. Static paths work reliably when an endpoint returns an entire collection, such as the full roster of staff writers across the newspaper.

However, real-world backend applications must also locate and serve individual records. Readers want to view a single journalist's author profile, read one specific breaking news dispatch, or review their personal subscriber settings.

If a developer attempts to serve individual records using static routes, they are forced to hardcode individual identifiers directly into the path strings.

Hardcoded Route Paths
1import { Controller, Get } from '@nestjs/common';
2
3@Controller('users')
4export class UsersController {
5 @Get('123')
6 getElenaProfile() {
7 return { id: '123', name: 'Elena Rostova' };
WRONG: hardcodes a single RECORD identifier
8 }
9}

This manual approach fails the moment a second employee joins the newsroom. You cannot write thousands of separate method handlers to serve thousands of staff members or millions of published articles. The web server needs a flexible mechanism to declare a path pattern once and capture whatever specific identifier the client supplies at runtime.

Dynamic Route Tokens and the Param Decorator

To handle variable path segments, NestJS provides route parameters (dynamic tokens declared in a route path that capture variable values supplied by the incoming request URL).

In NestJS, you define a route parameter by prefixing a segment in the route path with a colon (:). For example, declaring @Get(':id') tells the NestJS routing engine that any value appearing after /users/ represents a dynamic variable named id. If a client sends a request to /users/123, the router matches the route and assigns the string "123" to the id token. If another request arrives for /users/456, the router matches the same handler and assigns "456" to id.

To access this captured value inside your TypeScript code, NestJS provides the @Param() decorator (a parameter decorator that extracts route parameters from the incoming request and injects them as arguments into your method handler).

NestJS supports two ways to use @Param():

  1. Named parameter extraction (recommended): passing a token name to the decorator, such as @Param('id') id: string, extracts that specific route parameter directly as a method argument.
  2. Whole parameter object extraction: invoking @Param() without arguments injects an object containing every captured parameter as key-value pairs, such as params.id.

To see this in action on The National Times, our staff profile endpoint requires two files working together. First, users.controller.ts declares the parameterized route @Get(':id') and extracts the identifier. Second, app.module.ts mounts the controller so NestJS registers the dynamic route pattern. When a manager requests GET /users/123, the controller captures the ID and returns Elena Rostova's profile.

Route Order and Path Conflicts

When combining static endpoints with parameterized routes in the same controller, the order of method declarations becomes critical.

Consider a scenario where the newsroom dashboard needs a special endpoint at /users/me to return the currently logged-in journalist's profile, alongside /users/:id for arbitrary employee lookups. Both methods listen for HTTP GET requests under the /users controller prefix.

In NestJS, the underlying router evaluates routes sequentially in the exact order they are declared within the controller class. The parameter token :id is a wildcard match that accepts any string value. If you place @Get(':id') above @Get('me'), the router encounters :id first. When a request for /users/me arrives, the router interprets the literal word 'me' as the :id parameter, executes findOne('me'), and never reaches your getMe() handler.

To prevent parameterized routes from intercepting static traffic, always declare static routes before dynamic parameterized routes:

Route Declaration Order
1@Controller('users')
2export class UsersController {
3 @Get('me')
4 getMe() {
5 return { id: 'current', name: 'Logged-in User' };
RIGHT: declared first so literal path matches FIRST
6 }
7
8 @Get(':id')
9 findOne(@Param('id') id: string) {
10 return { id, name: 'Specific User' };
RIGHT: declared second so wildcard captures remaining IDS
11 }
12}

The String Type Trap

When a client sends a request to /users/123, the value 123 arrives over the network as part of the URL string. In the HTTP protocol, URL paths are always text. Consequently, NestJS extracts all route parameters as JavaScript string primitives at runtime.

Even if you write TypeScript type annotations like @Param('id') id: number, TypeScript types exist only during development and are completely erased when compiled to JavaScript. At runtime, the variable id holds the string value '123', not the numeric value 123.

If your code attempts a strict equality comparison against a numeric database record, such as author.id === id, the expression 123 === '123' evaluates to false. The query returns null, and the client receives a 404 error even though the record exists.

In upcoming lectures, you will learn how NestJS Pipes automatically parse and validate route parameters before your handler runs. Until you attach a transformation pipe, you must remember that @Param() always delivers raw string values.

Key Takeaway

Route parameters are always extracted as string primitives at runtime, regardless of the TypeScript type annotation on the handler parameter.

Interview Tip

To impress the interviewer: Explain route precedence and parameter collision. Interviewers frequently ask what happens when GET /users/me and GET /users/:id exist in the same controller. Explain that NestJS registers routes in top-down class declaration order by default. Placing :id above me causes the dynamic token to capture the literal string 'me', returning an invalid profile or failing a database lookup. Static routes must always be declared before dynamic token routes.

Where you will meet this

  • Author profile pages: extracting /users/:id to fetch biographical text, assigned department, and published articles for a specific journalist.
  • Article detail endpoints: capturing /articles/:slug to query news content using human-readable URL slugs like election-night-results.
  • Media asset retrieval: handling /photos/:photoId to stream raw image binaries from cloud storage to reader web browsers.
  • Comment moderation feeds: binding /articles/:articleId/comments/:commentId to target an abusive comment for editorial review.

Lecture 3: Reading Request Payloads with Body and DTOs

Interview Question

CORE

How do you read the JSON payload sent in a POST request?

Imagine this scenario:

  1. A developer builds the subscriber signup system for The National Times website.
  2. The server records reader accounts with email addresses, because the paper delivers daily newsletters to verified email addresses.
  3. The developer writes a network endpoint to receive each subscriber signup submission.
  4. A reader submits the signup form, but the server prints undefined for the email address.
  5. Why does the server print undefined when the reader submitted a valid email address?
  6. The incoming network stream sent raw text that the server never extracted into an object.
  7. Today you will learn how the server captures and types incoming data sent in requests.

The Problem of the Empty Request Body

When a client application submits an HTTP POST request containing a JSON payload, that data travels across the network as a continuous stream of raw bytes inside the HTTP message body. Unlike URL query parameters or route path segments, which arrive inside the HTTP request header, payload data requires buffering and parsing before application code can inspect it.

In low-level Node.js development, consuming an HTTP body requires listening to asynchronous chunk events on the request stream and manually assembling the raw string.

Manual Stream Listener
1import http from 'node:http';
2
3const server = http.createServer((req, res) => {
4 if (req.method === 'POST' && req.url === '/users') {
5 let rawData = '';
6 req.on('data', (chunk) => { rawData += chunk; });
WRONG: manually buffers streaming socket CHUNKS
7 req.on('end', () => {
8 const user = JSON.parse(rawData);
9 res.writeHead(201, { 'Content-Type': 'application/json' });
10 res.end(JSON.stringify(user));
11 });
12 }
13});

If a developer neglects this streaming lifecycle and attempts to read req.body directly in vanilla Node.js, the value is undefined. Even in basic Express applications, developers must configure external middleware to parse incoming bodies into memory.

Furthermore, raw JSON parsing offers no architectural guarantee about the structure of incoming data. A client can submit missing fields, unexpected types, or extra malicious properties. Without a clear contract, every route handler becomes cluttered with repetitive manual validation checks.

Capturing Payloads with the Body Decorator

To capture incoming payload data cleanly, NestJS provides the @Body() decorator (a parameter decorator that extracts the parsed HTTP request body from the incoming request and injects it as an argument into your route handler).

When a client issues a request with a Content-Type: application/json header, the underlying HTTP platform automatically parses the raw network stream into a JavaScript object. The @Body() decorator then extracts that parsed object and hands it directly to your method parameter.

To handle creation requests, we pair @Body() with the @Post() HTTP method decorator:

Basic Post Handler
1@Post()
2create(@Body() rawBody: any) {
3 return rawBody;
WRONG: uses un-typed any instead of a structural CONTRACT
4}

By default, NestJS assigns an HTTP status code of 201 Created to successful POST handlers, contrasting with GET handlers which default to 200 OK. This aligns with REST standards, signaling that the incoming request successfully created a new resource.

However, typing @Body() as any reintroduces ambiguity: the editor cannot autocomplete properties, and your code cannot verify what fields the client provided.

Defining Contracts with Data Transfer Objects

To establish a reliable contract for incoming payloads, NestJS relies on Data Transfer Objects. A Data Transfer Object (DTO) (an object that defines the exact structure and schema of data transmitted across the network for a specific operation) formalizes what fields an endpoint expects.

In TypeScript, developers often default to defining contracts with interfaces. However, NestJS strongly recommends defining DTOs using classes.

This introduces a common structural surprise: a DTO class typically contains only property declarations with no methods and no constructor:

app.ts
1export class CreateUserDto {
2 name: string;
3 role: string;
4}

Why write an empty-looking class instead of a TypeScript interface?

The answer lies in how TypeScript compiles to JavaScript. In TypeScript, an interface is a compile-time type that is completely erased during transpilation. At runtime, interfaces do not exist in the JavaScript output.

In contrast, an ES6 class remains intact as a real constructor function and prototype in compiled JavaScript. NestJS relies heavily on runtime metadata reflection. Because classes survive compilation, NestJS can inspect the runtime metatype of method arguments. This capability allows validation pipes to inspect property rules, sanitize payloads, and automatically strip unauthorized properties before the handler executes.

To see this in action on The National Times, our staff creation endpoint requires three files working together. First, create-user.dto.ts defines the required shape for new staff accounts. Second, users.controller.ts exposes POST /users and binds the DTO via @Body(). Third, app.module.ts registers the controller. When a client submits { "name": "Elena Rostova", "role": "Staff Writer" }, the controller captures the payload and returns the created record with an HTTP 201 Created status.

Selective Body Property Extraction

While passing a full DTO to @Body() is the standard approach for complex payloads, the @Body() decorator also supports selective property extraction. By passing a property key string to the decorator, you can extract a single top-level attribute directly:

Single Property Extraction
1@Post('role')
2updateRole(@Body('role') newRole: string) {
3 return { updatedRole: newRole };

4}

Passing a key such as @Body('role') plucks only req.body.role from the incoming payload and assigns it directly to newRole. This pattern is useful for lightweight endpoints that require only one property, such as toggling a flag or updating a single string.

However, for resource creation and update endpoints, whole DTO classes remain superior because they centralize data structure, document expectations, and integrate seamlessly with validation pipes.

Key Takeaway

Defining DTOs as classes rather than interfaces ensures that type metadata survives compilation for runtime validation and pipe transformation.

Route Paths versus URL Query Strings

When a web browser or mobile application interacts with an API, the full URL conveys two separate categories of information: the identity of the target resource, and the presentation instructions for that resource.

The URL path (such as /products) identifies the specific resource collection. Everything following the ? delimiter is the query string (a series of key-value pairs appended to a URL to specify optional modifiers like filtering, sorting, and pagination without changing the identity of the resource).

Capturing Query Strings with the Query Decorator

To capture query parameters declaratively, NestJS provides the @Query() decorator (a parameter decorator that extracts parsed URL query string parameters from the incoming HTTP request and injects them as arguments into your route handler).

Under the hood, the underlying HTTP platform automatically splits the URL at the ? character and parses the key-value pairs into a JavaScript dictionary. The @Query() decorator exposes that dictionary directly to your handler.

NestJS allows you to use @Query() in two distinct ways:

For an endpoint with only one query flag, extracting a named parameter directly is concise. However, real-world catalog endpoints frequently accept multiple options simultaneously, including sorting criteria, sort direction, page numbers, and category filters.

Route Parameters versus Query Parameters: When to Use Which

A common design challenge for backend developers is deciding whether an incoming value belongs in a route path or in a query string.

To make the right choice, evaluate whether the parameter defines the identity of the resource or merely modifies how a collection is displayed:

  • Use Route Parameters (@Param) when identifying a specific entity. In the URL /products/401, the ID 401 is an essential part of the resource's identity. If you omit 401, the URL changes entirely and points to the whole collection rather than a single product. Route parameters are mandatory for matching the endpoint.
  • Use Query Parameters (@Query) when filtering, sorting, searching, or paginating a collection. In the URL /products?sort=rating, the endpoint still targets the general /products resource, but asks the server to arrange the result differently. If the client omits the query string entirely, the request still succeeds and returns the default view.

Query String Parsing and the String Type Reality

Just like route parameters captured by @Param(), all query parameters extracted by @Query() arrive as JavaScript string primitives at runtime.

Even if you declare a property as limit?: number in your TypeScript DTO, TypeScript types are completely erased during compilation. When a client requests /products?limit=25, the runtime value of query.limit is the string '25', not the number 25.

If your code performs arithmetic like query.limit + 10, JavaScript performs string concatenation instead of addition, resulting in the string '2510' rather than 35. In future lectures, you will learn how NestJS transformation pipes automatically parse strings into validated numbers and booleans before your handler runs. Until pipes are applied, treat all incoming query parameters as strings or undefined.

Key Takeaway

Query parameters are optional modifiers used for filtering, sorting, and pagination, and they are always extracted as string primitives by default.

In contrast, @Query() extracts optional modifiers that filter, sort, or paginate a collection (such as ?sort=price&limit=20) without changing the identity of the underlying endpoint.

  • Analytics reporting endpoints: extracting GET /metrics?from=2026-01-01&to=2026-01-31 to filter time-series readership statistics.

The Meaning of HTTP Status Codes

Every HTTP response returned by a web server includes a three-digit numeric status code. This status code acts as the universal communication protocol between backends and clients, informing web browsers, mobile applications, reverse proxies, and monitoring dashboards how the server handled the request.

HTTP status codes follow strict semantic categories:

  • 2xx (Success): indicates that the client request was successfully received, understood, and accepted.
  • 4xx (Client Error): indicates that the request contains bad syntax, missing fields, or invalid authentication.
  • 5xx (Server Error): indicates that the server encountered an unexpected error while processing a valid request.

In NestJS, standard response handling applies sensible default status codes out of the box. Any route decorated with @Get(), @Put(), @Patch(), or @Delete() returns an HTTP status of 200 OK by default. Route handlers decorated with @Post() return an HTTP status of 201 Created by default.

These framework defaults cover standard CRUD operations, but real-world architectures require finer precision. For example, queuing a long-running background export should return 202 Accepted, permanently deleting an article should return 204 No Content, and rejecting an invalid form requires returning 400 Bad Request.

In traditional Express applications, developers manually set status codes by calling library-specific methods on the response stream:

Success Status Overrides versus Exception Throwing

A critical distinction in NestJS architecture is knowing when to use @HttpCode() and when to throw an HTTP Exception.

The @HttpCode() decorator is designed specifically for successful execution paths. When your controller method completes its logic normally and returns a value, NestJS stamps the response with the status code declared in @HttpCode().

However, if a submission is invalid, such as our opening scenario where a reader submits a blank form, you should not attempt to return a 400 status through @HttpCode(). Using @HttpCode(400) on a method means the method will return 400 even when valid data is submitted.

For error conditions, the idiomatic NestJS pattern is to throw an HttpException (a built-in framework error class that halts execution and instructs the exception layer to return a specific HTTP error status).

NestJS exports pre-built exceptions for common HTTP errors, including BadRequestException (400), UnauthorizedException (401), ForbiddenException (403), and NotFoundException (404):

Throwing Validation Exceptions
1import { BadRequestException } from '@nestjs/common';
2
3if (!submitTipDto.content) {
4 throw new BadRequestException('Tip content must not be blank');
RIGHT: halts execution and produces 400 JSON
5}

When you throw BadRequestException, NestJS halts handler execution immediately and delegates to the global exception layer. The server returns an HTTP 400 Bad Request status with a standardized JSON error envelope: {"statusCode": 400, "message": "Tip content must not be blank", "error": "Bad Request"}. This prevents the frontend from displaying an incorrect success message.

Common Status Code Patterns in Production

When designing production APIs for The National Times, four status patterns appear constantly:

  1. HttpStatus.OK (200): The universal standard for successful data retrieval, updates, and non-creation mutations.
  2. HttpStatus.CREATED (201): The default for @Post() handlers. Signals that a new database record or resource was successfully minted.
  3. HttpStatus.ACCEPTED (202): Used when an operation has been accepted into a processing queue, but computation or validation will finish asynchronously in the background.
  4. HttpStatus.NO_CONTENT (204): Standard for successful deletion endpoints. When you apply @HttpCode(HttpStatus.NO_CONTENT), HTTP protocol rules dictate that no response body can be transmitted. Any return value from the controller method is discarded.

Key Takeaway

Use @HttpCode() with the HttpStatus enum to override default success status codes declaratively without sacrificing NestJS response lifecycle features.
