### How a component remembers data across renders

In modern web applications, user interfaces respond to reader interactions by remembering choices and displaying updated data. Readers click buttons to like articles, toggle bookmarks, or submit comments. In standard JavaScript programming, developers store changing values in local variables using `let`. In React, components are pure JavaScript functions that execute to return JSX descriptions of the interface. When an interaction occurs, React calls the component function again from the top. A plain local variable declared inside the function body is re-created on every render, discarding any previous value. To remember data across renders and request screen updates, React components use state declared with the `useState` Hook.

Beginners often assume that changing a local variable will automatically update the screen, because the variable appears inside the returned JSX. In plain JavaScript, assigning a new value to a variable mutates memory, but it does not tell React to run the component again. Without a render pass, the browser continues displaying the JSX produced during the initial render. Even if another interaction causes the component to re-render, the function executes from its first line, re-initializing the local variable back to its initial value. Furthermore, moving the variable outside the component creates a module-level variable that is shared by every instance on the page, breaking isolation and still failing to trigger updates. To manage interactive data, React provides the `useState` Hook, which reserves memory outside the component function and returns a setter function that queues a render.

### Why local variable assignment fails to update the display

In Lecture 1, we learned that user interfaces reflect application data. In Lecture 4, we saw that placing a JavaScript variable inside JSX curly braces like `{likes}` outputs its value into the rendered HTML. When a component loads, JavaScript initializes local variables declared with `let` or `const` and evaluates JSX expressions during that initial execution.

```jsx title="Local Variable Assignment"
function StoryCard() {
  let likes = 0; // Local variable React does not track
  function handleLike() {
    likes = likes + 1; // Mutates local variable in memory
    console.log('likes:', likes); // Logs 1, 2, 3 in console
  }
  return <button onClick={handleLike}>Likes: {likes}</button>;
}
```

When a user clicks a button and an event handler executes `likes = likes + 1`, JavaScript updates the number stored in local memory. However, React has no mechanism to watch plain variable reassignments. React updates the screen only when it executes the component function again to compute a new JSX element tree. Because a plain assignment does not notify React or schedule a render, React never re-runs the component. The DOM continues to display the JSX generated during the very first render pass, leaving the count stuck at `0` on screen while the console logs higher numbers.

```jsx title="Declarative State Introduction"
import { useState } from 'react'; // Named import from React
function StoryCard() {
  const [likes, setLikes] = useState(0); // State reserved in React
  function handleLike() {
    setLikes(likes + 1); // Queues a re-render with next value
  }
  return <button onClick={handleLike}>Likes: {likes}</button>;
}
```

### The state pair and the setter function

In Lecture 8, we learned to import named utilities using curly braces. In JavaScript, array destructuring `const [first, second] = array` allows unpacking values from an array into distinct variable names.

```jsx title="State Pair Usage"
import { useState } from 'react';
function StoryCard() {
  const [likes, setLikes] = useState(0); // Pair: current value and setter
  function handleLike() {
    setLikes(likes + 1); // Schedules render with updated value
  }
  return <button onClick={handleLike}>Likes: {likes}</button>;
}
```

A **Hook** is a specialized function starting with `use` that is available only while React renders components. The `useState` Hook is React's built-in tool for giving a component memory. When called as `useState(initialValue)`, it returns an array with exactly two elements: the current **state variable** for this render, and a **setter function**. The state variable is declared with `const` because its value represents a static snapshot for the current render. To change the value, application code must invoke the setter function: `setLikes(likes + 1)`. Calling the setter writes the new value into React's internal storage and schedules a re-render. Attempting to assign `likes = likes + 1` directly throws a `TypeError: Assignment to constant variable`.

### Component function re-execution and local variable reset

In Lecture 12, we learned that React components are pure functions. React calls component functions whenever an update is scheduled.

```jsx title="Local Variable Reset Demonstration"
function StoryCard() {
  let likes = 0; // Runs on every render, resetting to 0
  const [saved, setSaved] = useState(false); // State survives renders
  function handleLike() {
    likes = likes + 1; // Changes memory for this render only
  }
  return <button onClick={() => setSaved(!saved)}>Save</button>;
}
```

A React component is a plain JavaScript function. When a state setter like `setSaved` executes, React schedules a re-render and calls `StoryCard` again from the very first line. Every time a function is called in JavaScript, its local scope is created fresh. Any statement such as `let likes = 0` executes again, resetting the variable back to zero. The memory from previous calls is wiped clean. If a developer attempts to store a counter in a local `let` variable alongside a stateful bookmark toggle, clicking Like increases the count in memory, but toggling the bookmark re-executes the function and silently wipes `likes` back to `0`.

### How React stores state and matches calls by order

Components frequently manage multiple pieces of interactive data, such as a counter and a boolean toggle.

```jsx title="Multiple State Variables"
function StoryCard() {
  const [likes, setLikes] = useState(0); // Slot 1
  const [saved, setSaved] = useState(false); // Slot 2
  const nextLikes = () => setLikes(likes + 1);
  return (
    <button onClick={nextLikes}>
      Likes: {likes} {saved ? '(Saved)' : ''}
    </button>
  );
}
```

If `useState(0)` executes on every render, why does `likes` not reset back to `0` like `let likes = 0` does? The reason is that state does not live inside the component function; it lives outside the function in React's internal storage node (the fiber). On the initial render, React stores the initial argument `0`. On subsequent renders, React ignores the argument `0` and retrieves the value stored in React's memory. When a component calls `useState` multiple times, React keeps an ordered list of state cells for that component instance. React pairs each `useState` call to its stored data by its position in the call sequence: call 1 maps to slot 1, and call 2 maps to slot 2.

### Component instances and state isolation

In Lecture 5, we learned that a component definition can be rendered multiple times as separate elements in JSX, such as `<StoryCard />` rendered twice in `App`.

```jsx title="Component Instances"
function App() {
  return (
    <div>
      <StoryCard title="Story A" /> {/* Independent state instance 1 */}
      <StoryCard title="Story B" /> {/* Independent state instance 2 */}
    </div>
  );
}
```

When a component is rendered multiple times, each rendered element is a distinct **component instance**. React allocates a separate, isolated state storage record for each instance on the page. Clicking Like on the first `StoryCard` updates only that card's state; the second card's state remains untouched. If a developer attempts to solve the local variable reset problem by moving `let likes = 0` outside the component to module scope, all card instances share that single variable, corrupting isolation and still failing to trigger renders.

### Initializer functions for expensive initial state

In JavaScript, expressions passed as function arguments evaluate immediately when the outer function is called.

```jsx title="Expensive Initial State"
function StoryCard({ storyId }) {
  // Pass a function to run only on initial mount
  const [likes, setLikes] = useState(() => readSavedLikes(storyId));
  return <button onClick={() => setLikes(likes + 1)}>Likes: {likes}</button>;
}
```

When passing an initial value to `useState(readSavedLikes(id))`, JavaScript executes `readSavedLikes(id)` on every single render pass, even though React uses the initial value only on the initial mount and discards it thereafter. If the initialization involves reading storage or parsing data, this causes unnecessary performance overhead. To avoid running the calculation on every render, pass an **initializer function**: `useState(() => readSavedLikes(id))`. When passed a function, React invokes it only during the initial mount. In development under `StrictMode`, React calls the initializer twice to check for side-effect purity, but keeps one result.

### Wiring setters in event handlers to prevent render loops

In Lecture 13, we learned that event props like `onClick` must be passed a function reference, not an immediate function invocation.

```jsx title="Event Handler Setter Wiring"
function StoryCard() {
  const [likes, setLikes] = useState(0);
  // Correct: wrapped in an arrow function that waits for a click
  return <button onClick={() => setLikes(likes + 1)}>Like</button>;
}
```

When a developer writes `<button onClick={setLikes(likes + 1)}>`, JavaScript executes `setLikes(likes + 1)` immediately during the render pass because curly braces evaluate expressions. Calling the setter requests a new render before the current render finishes. React immediately begins the next render, which executes `setLikes` again, creating an infinite loop. React aborts the loop by throwing `Too many re-renders. React limits the number of renders to prevent an infinite loop`. To wire the setter properly, wrap it in an inline arrow function: `onClick={() => setLikes(likes + 1)}` or pass a handler reference.

### Question 1: Changing a variable does not update the screen

A developer builds a like counter inside `StoryCard` using a plain local variable:

```jsx title="Stuck Local Counter"
function StoryCard() {
  let likes = 0; // Local stack variable
  function handleLike() {
    likes = likes + 1; // Mutates local variable
    console.log('likes:', likes); // Prints 1, 2, 3
  }
  return <button onClick={handleLike}>Likes: {likes}</button>;
}
```

Each click logs an increasing number to the console, but the button label remains unchanged.

**I add 1 to likes on every click, and the console counts 1, 2, 3. Why does the screen still say 0 likes?**

---

**ANSWER**

**The code does not do what we wanted.** In JavaScript, reassigning a local variable modifies memory in the current execution context, but React does not observe plain variable reassignments.

React updates the screen only when it calls the component function again to compute a new JSX description. Because a plain assignment does not request a render, React never re-executes `StoryCard`. The screen remains frozen on the initial render output.

```ascii title="Local Assignment vs React Runtime"
[ User Click ] ---> [ likes = likes + 1 ] ---> Memory: 1, 2, 3
                          |
                          v
                  React NOT Notified
                          |
                          v
               Screen Stays at "0 likes"
```

To update the screen, the component must store data in React state and request a render using a setter function.

> [!PRINCIPLE]
> **Principle 1: Changing a variable does not ask React to update the screen**
> In plain JavaScript, assigning a value updates local memory, but React does not track plain variable reassignments. React updates the screen only when it executes the component function again to compute a new JSX description. Because a plain assignment does not request a render, React never re-runs the component, leaving the display frozen on the previous output.
>
> >> plain local variable : a variable declared with let or const inside a function body that React does not watch
> >> render trigger : an explicit request that instructs React to re-execute a component function
>
> *We should do this:*
> `function StoryCard() {`
> `  const [likes, setLikes] = useState(0); // State memory`
> `  function handleLike() {`
> `    setLikes(likes + 1); // Asks React to re-render`
> `  }`
> `  return <button onClick={handleLike}>Likes: {likes}</button>;`
> `}`
>
> *We should not do this:*
> `function StoryCard() {`
> `  let likes = 0; // Local variable React does not track`
> `  function handleLike() {`
> `    likes = likes + 1; // Mutates memory; no render occurs`
> `  }`
> `  return <button onClick={handleLike}>Likes: {likes}</button>;`
> `}`

### Question 2: Keeping the value in state and updating with its setter

A developer declares state with `useState(0)` and attempts to update it directly inside the click handler:

```jsx title="Constant Assignment Error"
function StoryCard() {
  const [likes, setLikes] = useState(0); // State constant
  function handleLike() {
    likes = likes + 1; // Throws TypeError: Assignment to constant
  }
  return <button onClick={handleLike}>Likes: {likes}</button>;
}
```

Clicking the button throws a runtime error in the console.

**How do I keep the like count, and get the screen to show the new number when it changes?**

---

**ANSWER**

**The code does not do what we wanted.** The `useState` Hook returns a pair: the current state value and its setter function.

The state variable is declared with `const` because it represents an immutable snapshot for the current render pass. Directly reassigning `likes` throws a runtime TypeError. Even if declared with `let`, direct reassignment only mutates a local identifier without notifying React. To update state, you must call the setter function `setLikes(likes + 1)`. The setter stores the new value inside React and queues a re-render.

```ascii title="Setter Call and Re-render Cycle"
[ setLikes(1) ] ---> Stores 1 in React ---> Queues Re-render
                          |
                          v
                   StoryCard Re-runs
                          |
                          v
         useState(0) returns 1 ---> Screen shows "1 likes"
```

When React re-runs `StoryCard`, `useState` returns the updated count, and the returned JSX renders the new number to the screen.

> [!PRINCIPLE]
> **Principle 2: Keep the value in state and change it with its setter**
> The useState Hook provides both the current state snapshot and a dedicated setter function. The state variable is a constant for the current render pass and must never be reassigned directly. Calling the setter stores the next value inside React and requests a re-render where the updated value is returned.
>
> >> state variable : a constant representing the component's state value during the current render
> >> setter function : a function provided by useState that updates state and schedules a re-render
>
> *We should do this:*
> `function StoryCard() {`
> `  const [likes, setLikes] = useState(0); // State pair unpacked`
> `  function handleLike() {`
> `    setLikes(likes + 1); // Queues re-render with next value`
> `  }`
> `  return <button onClick={handleLike}>Likes: {likes}</button>;`
> `}`
>
> *We should not do this:*
> `function StoryCard() {`
> `  const [likes, setLikes] = useState(0); // State constant`
> `  function handleLike() {`
> `    likes = likes + 1; // Throws Assignment to constant`
> `  }`

### Question 3: Component function re-execution restarts local variables

A developer pairs a stateful bookmark toggle with a local `let` counter:

```jsx title="Local Variable Reset on Re-render"
function StoryCard() {
  let likes = 0; // Re-created on every render
  const [saved, setSaved] = useState(false); // Survives re-render
  function handleLike() {
    likes = likes + 1; // Count lost when component re-renders
  }
  return <button onClick={() => setSaved(!saved)}>Save</button>;
}
```

The user clicks Like twice, then clicks Save. The next Like click starts from 1 again.

**The Save button is state now, but the like count is still a let. After I click Save, why does the next Like start from 1 again?**

---

**ANSWER**

**The code does not do what we wanted.** A React component is a plain JavaScript function. When `setSaved` triggers a re-render, React calls `StoryCard` again from the very first line.

Every function call in JavaScript establishes a fresh execution context. The line `let likes = 0` runs again, creating a brand new variable initialized to `0`. The count accumulated in the previous render pass is discarded.

```ascii title="Local Variable Reset During Re-render"
Render 1: StoryCard() ---> let likes = 0 ---> Click Like x2 (likes = 2)
                               |
Render 2: StoryCard() ---> let likes = 0 (reset!) ---> Click Like (likes = 1)
```

Values that must survive across re-renders cannot live in plain local variables. They must be managed by React state.

> [!PRINCIPLE]
> **Principle 3: Every render runs the component from the top, so local variables start over**
> Every render executes the component function from line 1. Local variables declared with let or const are re-created on each invocation, discarding any data from previous renders. Values that must persist across renders must be placed in state.
>
> >> function re-execution : React invoking the component function from line 1 on every render pass
> >> local variable reset : the re-initialization of function-scoped variables upon every invocation
>
> *We should do this:*
> `function StoryCard() {`
> `  const [likes, setLikes] = useState(0); // Survives render`
> `  const [saved, setSaved] = useState(false); // Survives render`
> `  return <button onClick={() => setSaved(!saved)}>Save</button>;`
> `}`
>
> *We should not do this:*
> `function StoryCard() {`
> `  let likes = 0; // Re-created and reset on every render`
> `  const [saved, setSaved] = useState(false); // Re-renders card`
> `  return <button onClick={() => setSaved(!saved)}>Save</button>;`
> `}`

### Question 4: React stores state and matches calls by order

A developer inspects a card with multiple `useState` calls:

```jsx title="Multiple State Calls"
function StoryCard() {
  const [likes, setLikes] = useState(0); // Slot 1
  const [saved, setSaved] = useState(false); // Slot 2
  const nextLikes = () => setLikes(likes + 1);
  return (
    <button onClick={nextLikes}>
      Likes: {likes} {saved ? '(Saved)' : ''}
    </button>
  );
}
```

The developer wonders how React avoids resetting `likes` back to `0` when `useState(0)` re-runs.

**useState(0) runs again on every render. Why does likes not go back to 0 like let likes = 0 does?**

---

**ANSWER**

**The code works as expected.** State values do not live inside the component function; they reside outside the function in React's internal storage node for that component instance.

When `useState(0)` executes during the initial render, React initializes slot 1 with `0`. On all subsequent renders, React ignores the argument `0` and hands back the current stored value. React tracks multiple `useState` calls by their exact order in the execution sequence: call 1 retrieves slot 1, and call 2 retrieves slot 2.

```ascii title="Hook Call Order and Storage Slots"
Component Execution:           React Internal Fiber Storage:
1. useState(0)      ------->   Slot 1: [ 2 ] (likes)
2. useState(false)  ------->   Slot 2: [ true ] (saved)
```

Because call order determines slot mapping, `likes` preserves its incremented count while `saved` independently tracks bookmark state.

> [!PRINCIPLE]
> **Principle 4: React keeps the state and hands it back on every render, in call order**
> State memory lives outside the component function in React internal storage. On re-renders, React ignores the initial state argument and returns the latest stored value, differentiating multiple useState calls strictly by their sequential call order.
>
> >> React internal storage : the underlying fiber node structure that retains state across renders
> >> Hook call order : the strict sequential index React uses to match hook calls to state cells
>
> *We should do this:*
> `function StoryCard() {`
> `  const [likes, setLikes] = useState(0); // Slot 1: like count`
> `  const [saved, setSaved] = useState(false); // Slot 2: bookmark`
> `  return (`
> `    <article>`
> `      <button onClick={() => setLikes(likes + 1)}>Like</button>`
> `      <button onClick={() => setSaved(!saved)}>Save</button>`
> `    </article>`
> `  );`
> `}`

let sharedLikes = 0; // Module variable shared across all cards

### Question 6: Pass expensive start values as initializer functions

A developer reads initial counts with an expensive helper function:

```jsx title="Eager Function Evaluation"
function StoryCard({ storyId }) {
  // Evaluates readSavedLikes on every single render

```

Every click logs a storage access, indicating repeated calculation on re-renders.

**I read the saved like count with useState(readSavedLikes(story.id)). Why does readSavedLikes run again on every click?**

---

**ANSWER**

**The code does not do what we wanted.** In JavaScript, arguments passed to a function call are evaluated before the function executes. Writing `useState(readSavedLikes(storyId))` executes `readSavedLikes` on every render pass.

Even though React uses the initial value only on mount and ignores it thereafter, the calculation still runs. To defer execution, pass an initializer function: `useState(() => readSavedLikes(storyId))`. When passed a function, React executes it only during the initial mount.

```ascii title="Direct Argument vs Initializer Function"
Direct Call:   useState(expensive()) ---> Runs expensive() on EVERY render
Function Ref:  useState(() => expensive()) ---> Runs expensive() on MOUNT ONLY
```

Using an initializer function avoids repeated synchronous work on re-renders, preserving interface performance.

> [!PRINCIPLE]
> **Principle 6: Pass a slow start value as a function, so React runs it once**
> Function arguments evaluate on every render pass before useState executes. Passing an initializer function tells React to execute the calculation only during the initial component mount and ignore it on re-renders.
>
> >> initializer function : a callback passed to useState that executes once during initial mount
>
> *We should do this:*
> `function StoryCard({ id }) {`
> `  // Initializer callback executes only on mount`
> `  const [likes, setLikes] = useState(() => getSavedLikes(id));`

> `}`
>
> *We should not do this:*
> `function StoryCard({ id }) {`
> `  // Direct helper call runs on every render pass`

### Question 7: Call the setter in a handler, never while rendering

A developer wires a Like button directly to its setter function:

```jsx title="Render Phase Setter Crash"
function StoryCard() {
  const [likes, setLikes] = useState(0);
  // Invokes setLikes immediately during component render
  return <button onClick={setLikes(likes + 1)}>Like</button>;
}
```

The application crashes on initial page load with a render limit error.

**I wrote onClick={setLikes(likes + 1)}. Why does the page crash with 'Too many re-renders' before I click anything?**

---

**ANSWER**

**The code does not do what we wanted.** Curly braces in JSX evaluate expressions immediately during the render pass. Writing `onClick={setLikes(likes + 1)}` calls the setter function while React is rendering `StoryCard`.

The setter call queues another render before the current render can finish. React immediately starts a new render, which executes `setLikes` again. This creates an infinite loop that crashes the application. Setters must be wrapped in an uncalled function: `onClick={() => setLikes(likes + 1)}` or passed inside a separate handler.

```ascii title="Render Phase Infinite Loop"
Render Pass ---> Evaluates onClick={setLikes(...)} ---> Schedules Render
     ^                                                         |
     +---------------------------------------------------------+
                   Infinite Loop (Crash!)
```

Wrapping the setter call ensures it executes only when the user dispatches an interaction event.

> [!PRINCIPLE]
> **Principle 7: Call the setter in a handler, never while the component renders**
> JSX expressions evaluate immediately during render. Invoking a state setter inside JSX creates an infinite loop of re-renders that crashes the browser. Always wrap state setter calls inside an uncalled event handler callback.
>
> >> render-phase setter call : invoking a state setter during component rendering rather than in a handler
> >> infinite render loop : an unconstrained render cycle triggered by updating state during render
>
> *We should do this:*
> `function StoryCard() {`
> `  const [likes, setLikes] = useState(0); // State constant`
> `  const handleLike = () => setLikes(likes + 1); // Deferred`
> `  return <button onClick={handleLike}>Like</button>;`
> `}`
>
> *We should not do this:*
> `function StoryCard() {`
> `  const [likes, setLikes] = useState(0); // State constant`
> `  return <button onClick={setLikes(likes + 1)}>Like</button>;`
> `}`

### Step 1: First, we lay out the multi-card story feed <src/App.jsx>

In `src/App.jsx`, we establish the top-level application container. `App` renders the overall feed layout by mounting two independent `StoryCard` component instances.

Notice that `App` declares zero state variables. Because state is isolated within individual card instances, user clicks inside one story card will never cause `App` or sibling cards to re-render. `App` executes strictly during the initial page load to mount the component tree.

```jsx title="App.jsx"
import StoryCard from './components/StoryCard.jsx';
export default function App() {
  // Application shell mounts independent card instances
  return (
    <main className="story-feed">
      <StoryCard storyId="art-1" title="Urban Transit Reforms" />
      <StoryCard storyId="art-2" title="Solar Energy Horizons" />
    </main>
  );
}
```

### Step 2: Next, we declare state memory inside the card <src/components/StoryCard.jsx>

In `src/components/StoryCard.jsx`, we construct the interactive state boundary. The card declares private state memory for its like count and bookmark status.

To load the starting like count without running expensive calculations on every subsequent re-render, we pass an initializer function: `useState(() => getInitialLikes(storyId))`. When the reader clicks Like or Save, the setters update React's internal storage and schedule a re-render of this card alone. Notice how `StoryCard` passes the state values and callback functions downward to child presentation buttons.

```jsx title="StoryCard.jsx" startLine="1" continues="bottom"
import { useState } from 'react';
import LikeButton from './LikeButton.jsx';
import SaveButton from './SaveButton.jsx';

function getInitialLikes(id) {
  return id === 'art-1' ? 12 : 5;
}
export default function StoryCard({ storyId, title }) {
  const [likes, setLikes] = useState(() => getInitialLikes(storyId));
  const [saved, setSaved] = useState(false); // Independent bookmark state
```

The card renders the story title and nests the interactive action buttons, passing state snapshots and callback handlers.

```jsx title="StoryCard.jsx" startLine="11" continues="top"
  return (
    <article className="story-card">
      <h3>{title}</h3>
      <div className="card-actions">
        <LikeButton likes={likes} onLike={() => setLikes(likes + 1)} />
        <SaveButton saved={saved} onToggle={() => setSaved(!saved)} />
      </div>
    </article>
  ); // Pass state snapshots and callbacks to buttons
}
```

### Step 3: Then, we wire the interactive like counter button <src/components/LikeButton.jsx>

In `src/components/LikeButton.jsx`, we construct the counter presentation button. It receives the current `likes` count and an `onLike` callback prop from its parent card.

When clicked, the button triggers the incoming `onLike` callback, invoking the parent's state setter and queueing a re-render. Notice that `LikeButton` owns zero state; it acts as a pure presentation leaf that formats the label and triggers upward updates.

```jsx title="LikeButton.jsx"
export default function LikeButton({ likes, onLike }) {
  // Pure presentation button triggers parent state setter
  return (
    <button type="button" className="btn-like" onClick={onLike}>
      Like ({likes})
    </button>
  );
}
```

### Step 4: Finally, we attach the bookmark save toggle <src/components/SaveButton.jsx>

In `src/components/SaveButton.jsx`, we build the bookmark toggle button. It receives the current `saved` boolean flag and an `onToggle` callback function.

Inside the button body, a ternary operator chooses between the strings 'Saved' and 'Save'. Toggling the bookmark updates the boolean state in `StoryCard` and re-renders the card without resetting the like count.

```jsx title="SaveButton.jsx"
export default function SaveButton({ saved, onToggle }) {
  // Displays ternary label and toggles bookmark flag
  return (
    <button type="button" className="btn-save" onClick={onToggle}>
      {saved ? 'Saved' : 'Save'}
    </button>
  );
}
```

Look at how this four-file architecture fulfills idiomatic React state architecture. In a naive implementation, an engineer might have stored like counts in a plain local variable, leaving the screen stuck at `0` because plain assignments provide no render trigger. Or they might have moved the variable to module scope, accidentally sharing one count across every card on the page. Or they might have invoked `setLikes(likes + 1)` directly inside JSX, crashing the application in an infinite render loop.

By declaring state with `useState` inside the component boundary, passing an initializer function for stored data, isolating instance memory across cards, and passing deferred callback handlers to child buttons, our application remains predictable, resilient, and performant.

### Where you will meet this

In production web applications, understanding `useState` is essential when managing counters, form drafts, accordion panels, and interactive toggles. Teams frequently face bugs where local variables reset unexpectedly because an engineer placed mutable state on the function call stack instead of in React memory.

Another common scenario involves performance bottlenecks caused by eager argument evaluation. Passing expensive storage queries or array decoders directly to `useState` slows down every subsequent interaction. Converting those calls to initializer functions ensures initial calculations execute only during the initial component mount.

### For the interview

> **The Interview Question:** Why do ordinary variables forget their values between renders, and how does useState remember?

**1. The Hidden Signal**

The interviewer wants to see whether you understand the fundamental execution model of React: that components are pure functions invoked repeatedly over time. Weak candidates view components as persistent class instances or objects with mutable fields. Strong engineers explain that component functions execute from the top on every render, wiping the JavaScript call stack clean. They explain that `useState` delegates memory retention to React's internal fiber node, which persists data across invocations.

**2. The Classic Trap**

The classic trap is believing that variable reassignment tells React to update the page. Candidates often assume that assigning `likes = likes + 1` automatically syncs the DOM because `{likes}` sits in JSX. Another trap is attempting to avoid the reset by moving variables to module scope, corrupting instance isolation across the page. A third trap is invoking state setters directly inside JSX, causing infinite render loops.

**3. What is Actually Going On**

Every render pass calls the component function from line 1, re-initializing all local `let` and `const` variables. When `useState` executes, React pairs the call to a persistent state cell on the component's internal fiber, determined strictly by Hook call index. Calling a setter queues a re-render and updates the stored value. On subsequent renders, React returns the value from its internal fiber, ignoring the initial state argument.

**4. Where It Gets Tricky**

What if a component has multiple state variables? React differentiates them strictly by the order of `useState` calls, which is why Hooks cannot be placed inside conditions or loops. What about component instances? Each element mounted in the UI tree receives its own isolated fiber record. What about expensive initial values? Passing a function reference defers execution so the computation runs only once during initial mount.

### Glossary

- **State Variable**: An immutable value returned by `useState` representing component memory for the current render.
- **Setter Function**: A function returned by `useState` that updates React internal memory and schedules a re-render.
- **Hook**: A built-in React function prefixed with `use` that gives functional components access to state and lifecycle features.
- **Function Re-execution**: The process of React calling a component function from line 1 on every render pass.
- **Component Instance**: A distinct mounted occurrence of a component in the user interface tree with private state storage.
- **Initializer Function**: A function passed to `useState` that React executes only during initial component mounting.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Declarative State Triggers

➔ ALWAYS store data that affects the visual display in React state using `useState`.

➔ NEVER expect plain variable reassignments to trigger re-renders or update the screen.

➔ IF modifying state THEN call the setter function and never reassign the state variable directly.

**DO THIS:** trigger updates through state setters
```jsx right
const [likes, setLikes] = useState(0);
function handleLike() {
  setLikes(likes + 1);
}
```

**DO NOT DO THIS:** mutate local variables directly
```jsx wrong
let likes = 0;
function handleLike() {
  likes = likes + 1;
}
```

❒ Render Survival & Storage

➔ ALWAYS declare state inside the component function to ensure isolated instance memory.

➔ NEVER place mutable state in module-level variables shared across all instances.

➔ IF initializing state with an expensive calculation THEN pass an initializer function to `useState`.

➔ IF wiring state setters to event listeners THEN wrap the call in a function to prevent infinite render loops.

**DO THIS:** wrap setter in callback to defer execution
```jsx right
<button onClick={() => setLikes(likes + 1)}>Like</button>
```

**DO NOT DO THIS:** invoke setter immediately in JSX
```jsx wrong
<button onClick={setLikes(likes + 1)}>Like</button>
```

| | **IMPERATIVE STACK VARIABLE HABIT**<br>(Plain Local Variable) | **DECLARATIVE REACT MEMORY**<br>(useState Component State) |
| ---: | :--- | :--- |
| **Storage location** | Stored on local JavaScript call stack; inaccessible to React | Preserved in React internal fiber node outside the function |
| **Update trigger** | Reassigning variable mutates memory; screen never updates | Calling setter (`setLikes(next)`) schedules a component re-render |
| **Render survival** | Function runs from top on every render, resetting variable to `0` | React retrieves stored value, ignoring initial argument on re-render |
| **Instance scope** | Moving variable to module scope shares one copy across all cards | React allocates private, isolated memory slots for every card instance |
| **Initial computation** | Evaluates function argument on every single render pass | Initializer arrow (`() => fn()`) runs calculation once on initial mount |
| **Handler wiring** | Direct call in JSX (`onClick=`<br>`{setLikes()}`) crashes in infinite loop | Passing callback (`onClick={`<br>`() => setLikes()}`) waits for click |
