### One card design, different content each time

Every website shows the same kind of card many times. A shop shows each product in the same frame, and an article site shows each story in the same box. The design stays the same; only the content changes. So every React developer meets the same question: how does one card component show different content each time?

React gives two answers. The first one you know from Lecture 6: the card takes a prop and places the value in its own markup.

```jsx title="Option 1: a prop"
<ContentCard name="John Hall" /> {/* passes data through an attribute */}
```

Inside `ContentCard`, the code is `<p>My name is {name}</p>`. The card decides what the content looks like, and the caller only gives the value. This fits when every use has the same shape, such as a price tag that always shows a name and a price.

The second answer is to write the content between the card's tags.

```jsx title="Option 2: content between the tags"
<ContentCard>
  <p>My name is John Hall</p> {/* content placed between tags */}
</ContentCard>
```

Look at what sits between `<ContentCard>` and `</ContentCard>`: the whole element `<p>My name is John Hall</p>`. React takes everything written between the opening tag and the closing tag and hands it to the card as a prop. With a prop from Lecture 6, the information sits in an attribute whose name we choose; here it sits between the tags, and the prop's name is always **`children`**. Inside the card, the code is just `{children}`. Here the caller writes the content, and the card only gives the design around it.

In this chapter, we write one React component that keeps the design the same and lets each article decide its own content. In React, this approach is enabled by a prop named `children`. We will see it with one child, with several, and with none, then when to keep a prop beside it, and how the card passes on the attributes it does not use.

> [!WAYS] Two ways to show different content in one card
>
> (1) Show different content with **props** (Lecture 6): the caller passes values in attributes whose names we choose, and the card decides how they look.
>
> (2) Show different content with **children** (this chapter): the caller writes the content between the card's tags, and the card decides only the design around it.

The idea this chapter follows from the first question to the last: a component can be a frame the caller fills: what the caller writes between its tags arrives as `children`, and the frame decides where it goes. The chapter follows one tag from the inside out: the content between the tags, the choice between content and props, and the attributes on the tag.

This lesson answers three questions:

- **I put a headline between `<CardContainer>` and `</CardContainer>`. Where does it go?**
- **One story has a photo, another a quote, another only text. Do I add a prop for each?**
- **Callers want a `className` and an `aria-label` on the card. Do I list each one?**

The questions stand on what earlier lessons established:

- **Lecture 3 (JSX syntax)**: Each tag becomes a call, and the content inside a tag becomes its **`children`** in the object, as the browser inspect tools reveal. `className` is JSX's name for `class`, and `aria-*` and `data-*` attributes keep their hyphens.
- **Lecture 4 (JavaScript expressions in JSX with curly braces)**: In React rendering, `undefined` displays nothing, and the plus operator (`+`) joins strings together.
- **Lecture 5 (UI as a tree and component hierarchy)**: Nesting component tags creates the component render tree, with `App` at the root.
- **Lecture 6 (Passing data with props and the read-only contract)**: The attributes on a component's tag arrive as one object, the **props**, read by **destructuring** in the parameter list. A **default value**, `className = ''`, fills a prop that is missing or `undefined`. Props are read-only and never mutated.

### An array keeps several values in order

An **array** in JavaScript holds multiple values in an ordered sequence, enclosed in square brackets: `['Rail Strike Ends', 'New Park Opens Today']`. Each item occupies a numeric index, starting at index 0.

```js title="Plain JavaScript: an array of items"
const articles = ['Rail Strike Ends', 'New Park Opens Today'];
console.log(articles[0]); // 'Rail Strike Ends': first item at index 0
console.log(articles.length); // 2: total number of items
```

When a caller nests two or more elements between component tags, React groups those elements into an array and hands that array to the component as `children`. Lecture 11 shows how to transform arrays of dynamic data into elements using `.map()`.

### Three dots collect the rest and spread it out

The three-dot syntax (`...`) performs two distinct jobs in modern JavaScript depending on where it appears.

```js title="Plain JavaScript: rest syntax"
const story = { title: 'Rail Strike Ends', id: 'top', section: 'News' };
const { title, ...rest } = story; // unpacks title and collects remaining
console.log(rest); // { id: 'top', section: 'News' }
```

When used on the left side of an assignment or inside a function's parameter destructuring list, `...rest` is called **rest syntax**. It extracts the named properties and gathers all remaining properties into a new object. When placed on a JSX tag, `{...rest}` is called **spread syntax**. It takes every property from that object and applies it as an attribute on the JSX element.

### Principles of React: A Component Is a Frame the Caller Fills

Everything in this lesson comes down to one idea: a component can be a frame that the caller fills.

First, the children prop, which means the content between a component's tags arrives as one prop: the frame shows it wherever it writes children in braces, and nowhere if it forgets.

Second, composition, which means children when the caller decides the content, props when the frame decides its shape: the body of a story goes between the tags, and its title stays a prop.

Third, prop spreading, which means the attributes the frame does not use pass on to its element: the rest goes on with three dots, the attribute written last wins, and a class both sides set is joined.

### Question 1: The card shows nothing of what sits between its tags

A developer builds a container component named `CardContainer` to wrap article content in a styled card border. In `App.jsx`, `App` places a heading `<h2>New Park Opens Today</h2>` between the opening and closing tags of `<CardContainer>`:

```jsx title="App.jsx" startLine="1" continues="bottom"
function CardContainer(props) {
  return <article className="card" />; // **PROBLEMATIC:** empty container
}
```

In `App`, the heading is nested inside the container:

```jsx title="App.jsx" startLine="4" continues="top"
export default function App() {
  return (
    <CardContainer>
      <h2>New Park Opens Today</h2> {/* nested between tags */}
    </CardContainer>
  );
}
```

Save the file. The browser displays an empty card box on screen with zero text. Furthermore, if a child component like `<AuthorName />` is nested between the tags, its `console.log` never fires; the child component is never even called.

**I put a headline between `<CardContainer>` and `</CardContainer>`. Where does it go?**

---

**ANSWER**

**The code does not do what we wanted.** `CardContainer` ignores its children prop and renders an empty container.

In native HTML, content placed between `<div>` tags appears automatically in the browser. But in React, writing `<CardContainer>` does not render a DOM element directly; it instructs React to call the `CardContainer` component function. As Lecture 3 demonstrated during JSX compilation, React gathers whatever sits between a component's tags into a property on the props object named `children`: `_jsxDEV(CardContainer, { children: ... })`.

A container component displays nothing from between its tags until its return markup explicitly renders `{children}` inside curly braces. Because `CardContainer` never included `{children}`, React dropped the nested content entirely, and the nested `<h2>` was never evaluated.

The fix is to destructure `children` from props and render `{children}` inside the `<article>` tag:

```jsx title="App.jsx" startLine="1"
function CardContainer({ children }) {
  return (
    <article className="card">
      {children} {/* renders nested content */}
    </article>
  );
}
```

The prop `children` can take multiple structural shapes depending on what the caller passes: a single element arrives as an element object, multiple sibling elements arrive as an array of elements, plain text arrives as a string, and omitting inner content leaves `children` as `undefined`. React handles each shape seamlessly when placed in JSX curly braces `{children}`. However, calling `children.map()` directly inside a component crashes with `children.map is not a function` when a single child element is passed, because a single element is not an array.

```ascii title="The four shapes children can take"
CONTENT NESTED BETWEEN TAGS          VALUE OF children IN COMPONENT
<Card><h2>Park</h2></Card>           element object: { type: 'h2', ... }
<Card><h2>Park</h2><p>Text</p></Card> array of 2 elements: [ {..}, {..} ]
<Card>Direct text</Card>             string: "Direct text"
<Card></Card>                        undefined (renders nothing)
```

> [!PRINCIPLE]
> **Principle 1: The children prop: the content between a component's tags arrives as one prop**
> *We read what the caller writes between a component's tags as the prop `children`, and we place `{children}` where the content belongs; a frame that never writes it drops the content without a warning.*
>
> We might expect content placed between a component's opening and closing tags to render automatically like HTML. But a component tag is a function call. React bundles whatever is nested between those tags into a specialized prop named **`children`**. A container component displays nothing from between its tags until its function body explicitly renders `{children}`. If the container omits `{children}`, all nested elements are dropped silently and never execute.
>
> >> children : the prop React automatically populates with content between component tags
>
> *We should do this:*
> `function Panel({ children }) {`
> `  return <section className="panel">{children}</section>; // renders slot`
> `}`
>
> *We should not do this:*
> `function Panel() {`
> `  return <section className="panel"></section>; // **PROBLEMATIC:** drops children`
> `}`

### Question 2: A prop for every piece leaves an empty byline

An article list needs to show multiple story formats: a standard text article with an author byline, a photo article with no author, and a quote article. Following the pattern from Lecture 6, a developer creates a rigid `ArticleCard` that takes individual props for every layout element:

```jsx title="App.jsx" startLine="1" continues="bottom"
function ArticleCard({ title, author }) {
  return (
    <article className="card">
      <h2>{title}</h2>
      <p>By {author}</p> {/* **PROBLEMATIC:** shows 'By ' when omitted */}
    </article>
  );
}
```

`App` renders two article cards, but the photo update has no author:

```jsx title="App.jsx" startLine="9" continues="top"
export default function App() {
  return (
    <>
      <ArticleCard title="Rail Strike Ends" author="James Smith" />
      <ArticleCard title="New Park Opens Today" /> {/* author omitted */}
    </>
  );
}
```

The second card displays "New Park Opens Today" followed by "By " with an empty hole. When designers ask to add photo cards, quote cards, and video badges, the component accumulates twenty optional props, creating brittle, tangled markup.

**One story has a photo, another a quote, another only text. Do I add a prop for each?**

---

**ANSWER**

**The code does not do what we wanted.** A rigid component couples container layout to specific content fields.

When a component accepts a dedicated prop for every piece of content, it must hardcode where and how each piece renders. If a story omits a piece, the hardcoded markup leaves an empty label on screen. If a new content format is introduced, the card must add new props, causing the component to grow uncontrollably.

The solution is **composition**: use props for fixed data that every card shares and that the container positions, and use `children` for variable body content that changes from use to use. Every article requires a title rendered at the top of the card, so `title` remains a prop. But whether the body contains a paragraph, an author byline, an image, or a blockquote is decided by the caller between the tags.

```jsx title="App.jsx" startLine="1"
function CardContainer({ title, children }) {
  return (
    <article className="card">
      <h2>{title}</h2> {/* fixed title slot */}
      {children} {/* flexible content slot */}
    </article>
  );
}
```

Now, the weather update simply places no author between its tags, so no empty byline appears. The photo article nests an `<img>`, and the quote article nests a `<blockquote>`. As react.dev emphasizes, components with a `children` prop act as visual frames with an open slot. Conditional rendering of fallback slots is covered in Lecture 10.

```ascii title="Rigid card with fixed slots vs flexible container frame"
RIGID CARD (prop for every piece)    CONTAINER FRAME (children for content)
+---------------------------------+  +---------------------------------+
| title prop -> <h2>{title}</h2>  |  | title prop -> <h2>{title}</h2>  |
| author prop-> <p>By {author}</p>|  | {children} -> flexible slot for |
| (shows "By " when prop missing) |  |   photo, quote, or author text  |
+---------------------------------+  +---------------------------------+
```

> [!PRINCIPLE]
> **Principle 2: Composition: children when the caller decides the content, props when the frame decides its shape**
> *We pass content that changes from use to use as `children`, and we keep a prop for what every use must have and the frame must place, such as the title.*
>
> Creating dedicated props for every possible variation creates bloated, rigid components that break when designs evolve. When a component hardcodes layout slots, omitting a prop leaves dangling labels on screen. Practice **composition** by using props for fixed values that every instance requires in a standardized location, and use `children` for variable content that changes from instance to instance.
>
> >> composition : combining flexible content slots with fixed container framing
>
> *We should do this:*
> `function ProfileCard({ title, children }) {`
> `  return (`
> `    <article className="card">`
> `      <h2>{title}</h2> {/* title placed by frame */}`
> `      {children}       {/* body provided by caller */}`
> `    </article>`
> `  );`
> `}`
>
> *We should not do this:*
> `function ProfileCard({ title, phone }) {`
> `  return (`
> `    <article className="card">`
> `      <h2>{title}</h2>`
> `      <p>Phone: {phone}</p> {/* **PROBLEMATIC:** shows empty gap */}`
> `    </article>`
> `  );`
> `}`

### Question 3: The caller's class replaces the card's own

The featured top story on the page needs an accessibility label `aria-label="Top story"`, an anchor `id="top-story"`, and an extra highlight class `className="featured"`. A developer collects remaining props using rest syntax and spreads them onto the card:

```jsx title="App.jsx" startLine="1" continues="bottom"
function CardContainer({ children, ...rest }) {
  return (
    <article className="card" {...rest}>
      {children} {/* **PROBLEMATIC:** overrides card class */}
    </article>
  );
}
```

`App` passes the extra attributes to the featured container:

```jsx title="App.jsx" startLine="8" continues="top"
export default function App() {
  return (
    <CardContainer className="featured" id="top-story" aria-label="Top story">
      <h2>Park Opens Today</h2> {/* **PROBLEMATIC:** base style lost */}
    </CardContainer>
  );
}
```

The `id` and `aria-label` reach the `<article>` element. But inspecting the element in the browser Elements panel reveals `class="featured"`: the base `"card"` class disappeared completely, stripping away borders, padding, and layout shadows.

**Callers want a `className` and an `aria-label` on the card. Do I list each one?**

---

**ANSWER**

**The code does not do what we wanted.** Spreading rest after a class attribute overrides it, and joining an undefined class prints "undefined".

In JSX, attributes are evaluated in sequential order from left to right, and whichever attribute is written last wins. In `<article className="card" {...rest}>`, the spread syntax unpacks the caller's `className="featured"` after `className="card"`, completely replacing `"card"` with `"featured"`. If you swap the order to `<article {...rest} className="card">`, the card preserves `"card"` but discards the caller's `"featured"` class entirely.

When both the container and the caller need to apply CSS classes, the container must concatenate them: `className={'card ' + className}`. However, if a caller passes no class, `className` is `undefined`, and string concatenation turns it into `class="card undefined"`. To prevent this bug, provide a default value in the destructuring parameter list: `className = ''`.

```jsx title="App.jsx" startLine="1"
function CardContainer({ children, className = '', ...rest }) {
  return (
    <article className={'card ' + className} {...rest}>
      {children} {/* joined classes with fallback */}
    </article>
  );
}
```

Notice that we unpack `children` and `className` first and spread only `...rest`. If a component spreads all `props` directly with `<article {...props}>`, it accidentally forwards `children` into the DOM as an attribute and leaks non-standard props (like `isFeatured`), causing React to log `React does not recognize the isFeatured prop on a DOM element`. Rest syntax ensures only valid, unconsumed attributes reach the underlying DOM node.

> [!PRINCIPLE]
> **Principle 3: Prop spreading: the attributes the frame does not use pass on to its element**
> *We take out the props the frame uses and pass only the rest to its element with `{...rest}`; the attribute written last wins, so a class the frame and the caller both set is joined, with an empty default for the caller who sets none.*
>
> Extra attributes written on a component tag do not reach underlying HTML elements automatically. Use **rest syntax** in parameter destructuring `({ children, className = '', ...rest })` to extract known container props while capturing remaining attributes in `rest`. Spread `{...rest}` onto the element. Because the last attribute written wins, join container and caller classes explicitly, using an empty default string to prevent `class="card undefined"`.
>
> >> rest syntax : collecting unextracted properties into a single remaining object
>
> *We should do this:*
> `function Panel({ children, className = '', ...rest }) {`
> `  return (`
> `    <section className={'panel ' + className} {...rest}>`
> `      {children} {/* joins classes and spreads rest */}`
> `    </section>`
> `  );`
> `}`
>
> *We should not do this:*
> `function Panel({ children, ...rest }) {`
> `  return (`
> `    <section className="panel" {...rest}>`
> `      {children} {/* **PROBLEMATIC:** overrides base class */}`
> `    </section>`
> `  );`
> `}`

> [!WILD]
> **Is children the same as the children of the render tree in Lecture 5?**
> In Lecture 5, we learned that a component's children in the render tree are the components its own markup returns. With container composition, a parent writes child tags inside a container's JSX call. We might wonder whose child that nested component becomes in the tree.
> In the runtime render tree, content passed as `children` becomes a direct child of the container component that actually renders `{children}`. Even though `App` authored the `<p>` tag, the `<p>` sits underneath `CardContainer` in the render tree because `CardContainer` determines where and when that element renders.

### Where you will meet this

1. **Modal dialog containers**: rendering custom form or alert content inside a standard overlay frame with backdrop styling.
2. **Global layout shells**: wrapping page-level views between shared navigation headers and footers using a `<PageLayout>{children}</PageLayout>` wrapper.
3. **Design system button wrappers**: forwarding standard HTML button attributes (`type`, `disabled`, `onClick`) to underlying `<button>` elements via `{...rest}`.
4. **Card grids and split panes**: creating reusable layout grids that accept arbitrary cards, charts, or tables as children.
5. **Accessibility wrappers**: building focus trap containers that augment nested elements with ARIA attributes without dictating their internal markup.

### For the interview

> **The Interview Question:** How do the children prop, spread attributes, and default values work?

**1. The Hidden Signal**

The interviewer wants to hear how you design reusable, maintainable component interfaces. A junior candidate reaches for dozens of boolean and string props to handle layout variations, creating brittle APIs. A senior engineer explains container composition using the `children` prop, separating layout framing from content presentation. They explain that `children` is an ordinary prop created by JSX compilation, that JSX spread forwards unconsumed attributes to underlying elements, and that default values prevent undefined values from leaking into class names.

**2. The Classic Trap**

The classic trap is spreading all props directly onto native DOM elements using `<article {...props}>`. Spreading `props` forwards `children` into the DOM as an attribute and leaks custom framework flags (like `isFeatured`), triggering React runtime warnings. Another trap is spreading `{...rest}` after `className="card"`, which allows the caller's class to wipe out the base container class instead of joining them.

**3. What is Actually Going On**

When JSX compiles, any content placed between component tags becomes the `children` property of the props object. If one element is nested, `children` is an element descriptor object; if multiple siblings are nested, it is an array of descriptors. A container component renders this content wherever it places `{children}`. Using rest syntax (`...rest`) in parameter destructuring separates known container props from DOM attributes. Spreading `{...rest}` applies remaining properties to the root HTML element, while string concatenation with a default fallback (`className = ''`) combines CSS classes safely.

**4. Where It Gets Tricky**

*Why does `children.map()` throw an error when only one child element is passed?*

Because `children` is not guaranteed to be an array. If a caller nests a single element, `children` is a single React element object, which lacks array methods like `.map()`. To manipulate children safely in legacy code, developers used `React.Children.map`, though modern React recommends container composition over children inspection.

*Why does `<article className="card" {...rest}>` lose its styling when the caller passes a class?*

JSX attributes evaluate from left to right, and whichever attribute is evaluated last overrides previous ones. If `rest` contains `className="featured"`, it replaces `className="card"`. The correct approach is to extract `className` separately and join them: `className={'card ' + className}`.

*What happens if you concatenate `className={'card ' + className}` without a default value?*

If the caller omits `className`, the variable is `undefined`. In JavaScript, `'card ' + undefined` evaluates to the string `"card undefined"`. The browser sets `class="card undefined"`, polluting the DOM. Providing a default `className = ''` ensures omitted classes evaluate to an empty string.

*When should data be passed as a prop instead of children?*

Use props when the container must dictate the layout, styling, and positioning of that specific data point across all instances (such as a card title or icon position). Use `children` when the caller should have complete freedom to choose the structure, tags, and formatting of the inner content.

### Glossary

- **`children`**: The specialized React prop containing elements, strings, or components nested between a component's opening and closing tags.
- **Composition**: The software design pattern of building complex user interfaces by combining simple, flexible container components with nested content.
- **Array**: An ordered, indexed collection of values in JavaScript enclosed in square brackets.
- **Rest syntax**: The `...rest` syntax in destructuring that collects all remaining, unextracted properties into a single object.
- **Spread syntax**: The `{...rest}` JSX syntax that unpacks an object's properties as individual attributes onto an element.

### Summary

**A component can be a frame the caller fills**

❒ The children prop: the content between a component's tags arrives as one prop

➔ ALWAYS read nested markup by destructuring `{ children }` in your container component.

➔ NEVER assume content placed between component tags appears automatically; the frame must render `{children}` explicitly.

❒ Composition: children when the caller decides the content, props when the frame decides its shape

➔ ALWAYS pass variable body content as `children`, while reserving props for fixed values the frame must position.

➔ NEVER create dozens of optional props for layout variations; let callers nest their own markup inside container slots.

❒ Prop spreading: the attributes the frame does not use pass on to its element

➔ ALWAYS extract container props, provide an empty default `className = ''`, and spread `{...rest}` onto the underlying HTML element.

➔ NEVER spread raw `{...props}` onto DOM elements, and never place `{...rest}` after `className` without joining classes.

**Content between the tags, a frame for the shape, and the rest passed on.**

**DO THIS:** wrap content in a container frame, destructure rest props, and join classes

```jsx right
function CardContainer({ title, children, className = '', ...rest }) {
  return (
    <article className={'card ' + className} {...rest}>
      <h2>{title}</h2>
      {children}
    </article>
  );
}
export default function App() {
  return (
    <CardContainer title="New Park Opens Today" className="featured">
      <p>A new park opened this morning.</p>
    </CardContainer>
  );
}
```

**DO NOT DO THIS:** invent props for every layout variation or override base classes with spread

```jsx wrong
function CardContainer({ title, text, photoUrl, ...rest }) {
  return (
    <article className="card" {...rest}>
      <h2>{title}</h2>
      {text && <p>{text}</p>}
      {photoUrl && <img src={photoUrl} alt="" />}
    </article>
  );
}
export default function App() {
  return <CardContainer title="New Park Opens Today" text="A new park opened." />;
}
```
