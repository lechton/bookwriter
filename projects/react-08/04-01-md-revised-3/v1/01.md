# What Is React

## Two different ways to change the page when the data changes

A web page shows data, and when the data changes, the page must change with it. An online shop's cart shows its count in two places: the line "Items: 2" and the button "Buy 2 items". When the shopper adds a third item, both places must show 3. There are two ways to make the page follow the data.

> [!FACT] The browser does not draw the HTML file directly. It builds one object in memory for every tag, nested the way the tags are nested, and draws the screen from these objects. Together they are the **DOM**, the Document Object Model, and each object is a **DOM node**. So to change what the screen shows, something must change the DOM.

```tree caption="Two ways to change the page when the data changes: our code changes each element by hand, or our code describes each element and React changes the DOM."
Two different ways to change the page when the data changes
- Imperative programming: our code changes each element by hand | plain JavaScript: find the element, then set its text, one command per element
- Declarative programming: our code describes what each element shows | React: it changes the DOM to match the description
```

> [!FACT] In plain JavaScript, `document.getElementById('items')` asks the browser for the DOM node whose `id` is `items`. Setting that node's `textContent` replaces the text inside it, and nothing else on the page changes.

> [!FACT] In React, we write the page's markup inside JavaScript, in a form called **JSX**. **Curly braces** in JSX mark a place where a JavaScript value goes: with `count` set to 3, `<p>Items: {count}</p>` shows "Items: 3". A comment inside JSX markup is written in curly braces too, `{/* like this */}`.

We compare the two ways on the cart, after the shopper adds a third item. Both carts show 3 in both places. Only the code differs.

::: row caption="The cart after the third item, changed in two ways. The two pages look the same; compare the code under each."
::: col title="Imperative: plain JavaScript" tag="our code" tone=plain
```shop size=mini
text: Items: 3
button: Buy 3 items
```
```js
items.textContent = 'Items: 3'; // We set the line
buy.textContent = 'Buy 3 items'; // We set the button
```
With 3 items in the cart, our code sets the text of each DOM node, `items` and `buy`, found with `getElementById`: one command per element, on every change.
:::
::: col title="Declarative: React" tag="React" tone=good
```shop size=mini
text: Items: 3
button: Buy 3 items
```
```jsx
<p>Items: {count}</p> {/* We describe the line */}
<button>Buy {count} items</button> {/* We describe the button */}
```
With `count` set to 3, our code only says what each element shows, and React changes the DOM to match. Principle 1 shows how.
:::
:::

Why does the difference matter? Imperative code is fine for one element that changes in one place, such as a clock in a corner of the page. But the count shows in two places, so imperative code needs one command per place on every change. A place with no command keeps the old count, with no error, and the button then offers the shopper the wrong purchase, as Principle 1 shows. Declarative code has no command to forget: each element says what it shows, and React works out the changes.

In **imperative programming**, our code gives the browser each command itself: find this element, set its text. In **declarative programming**, our code declares what each element shows for the current data, and something else makes the DOM match. **React** is a JavaScript library for building user interfaces out of components, and it is declarative.

## Declarative programming: the life of one value

In React, a page is built from **components**. A component is a JavaScript function whose name starts with a capital letter, and it returns the JSX for one part of the page. Our cart is one component, `Cart`. We follow one value of the cart, `count`, through three moments. First the cart is described from `count`. Then two places on the page share it. Then it changes, and React updates the page.

```tree caption="The three moments in the life of count, and the idea each one teaches."
The life of one value, `count`
- `Cart` describes the page | declarative programming: React builds the DOM from what `Cart` returns
- Every place reads `{count}` | a single source of truth: no place keeps a copy of the count
- React changes only the new text | virtual DOM comparison: the new description against the last one
```

We take the three in this order, because each one needs the one before it. Two places can share `count` only once the cart is described from it. And the change can be shown whole only once both places read the same variable. Then one change of `count` reaches both places, and a note box beside them shows what React leaves alone.

# Principles

## 1. Declarative programming: `Cart` describes the page, React builds it

*How? React builds the DOM from what the component returns*

```tree size=mini here="`Cart` describes the page"
The life of one value, `count`
- `Cart` describes the page
- Every place reads `{count}`
- React changes only the new text
```

> [!FACT] `const count = 3;` makes a **local variable**: a name for a value, inside the function. The JSX after `return` can read it in curly braces, `{count}`.

> [!PRINCIPLE]
> **Principle 1: Declarative programming: describing what the page shows, not how to change it**
>
> We control the page by describing what it shows from data.
>
> A component returns JSX that says what each element shows for the current data. React calls the component and builds the DOM from it.
>
> We never find and change the page's elements by hand. Notice: every element our code changes by hand is an element our code can forget.
>
> *We should do this:*
>
> ```jsx
> function Cart() {
>   const count = 3;
>   return (
>     <section> {/* React builds every element from this */}
>       <p>Items: {count}</p>
>       <button>Buy {count} items</button>
>     </section>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```js
> function addItem() {
>   const items = document.getElementById('items');
>   items.textContent = 'Items: 3'; // **PROBLEMATIC:** names only the line: the button keeps 2
> }
> ```

### Example: let's change the cart by hand (the button we never name keeps the old count!)

Here, a script changes the cart by hand, and the button it never names keeps the old count. A script changes exactly the DOM nodes it names, and nothing else. Our shop's old page, from before React, worked this way. Every new place that shows the count needs one more command, and one missing command leaves an old count on the page, with no error.

We want both places to show 3 after the shopper adds a third item. The old page is a plain HTML file, with an `id` on each place that shows the count. Its script runs when the shopper clicks Add to cart. We write one command, for the line.

```html title="old-cart.html"
<section id="cart"> <!-- The old page, from before React -->
  <p id="items">Items: 2</p>
  <button id="buy">Buy 2 items</button>
</section>
```

```js title="old-cart.js" bad="3"
function addItem() { // Runs when the shopper clicks Add to cart
  const items = document.getElementById('items');
  items.textContent = 'Items: 3'; // **PROBLEMATIC:** names only the line
}
```

> [!FACT] `export default` lets another file use a function: `Cart.jsx` exports `Cart`. In another file, `import Cart from './Cart.jsx';` brings it in, and the tag `<Cart />` places it on the page. The project runs with the command `npm run dev`, which starts a **dev server**: a small program on our computer that sends the project to the browser. Each time we save a file, the dev server sends the new code to the open page, and React updates the page without a reload.

In React, we write no such script. The parent, `App.jsx`, places the child, `Cart.jsx`. `Cart` keeps the count in `count` and returns what each element shows. A count that changes on a click needs state, which Lecture 14 teaches. So in this lecture, we play the shopper's click ourselves: we change `2` to `3` in `Cart.jsx` and save.

```jsx title="App.jsx" role=PARENT
import Cart from './Cart.jsx'; // Our component, from its own file

export default function App() {
  return <Cart />;
}
```

```jsx title="Cart.jsx" role=CHILD
export default function Cart() {
  const count = 3; // Changed from 2, then saved
  return (
    <section>
      <p>Items: {count}</p>
      <button>Buy {count} items</button>
    </section>
  );
}
```

## 2. A single source of truth: every place reads `{count}`

*Why? A count typed by hand is fixed text, so it never changes*

```tree size=mini here="Every place reads `{count}`"
The life of one value, `count`
- `Cart` describes the page
- Every place reads `{count}`
- React changes only the new text
```

> [!PRINCIPLE]
> **Principle 2: Single source of truth: describing many places from one value**
>
> When one value appears in many places, we keep it in one variable.
>
> Every place reads that variable in curly braces, so every place is built from it.
>
> We never type a copy of the value into the markup. Notice: a typed copy is fixed text, so it keeps the old value when the variable changes.
>
> *We should do this:*
>
> ```jsx
> function Cart() {
>   const count = 3;
>   return (
>     <section>
>       <p>Items: {count}</p>
>       <button>Buy {count} items</button> {/* Reads count, like the line */}
>     </section>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function Cart() {
>   const count = 3;
>   return (
>     <section>
>       <p>Items: {count}</p>
>       <button>Buy 2 items</button> {/* **PROBLEMATIC:** a 2 typed by hand: it never changes */}
>     </section>
>   );
> }
> ```

### Example: let's copy the button from the old page (a 2 typed by hand never changes!)

Here, a count typed by hand into the JSX keeps the old value, while the line beside it changes. React shows exactly what the JSX describes. A 2 typed by hand is fixed text, so no change of `count` ever reaches it. The slip is easy to miss, because the page looks right for as long as the count is 2.

We want both places to show 3 after the save. When the cart moved from the old page into React, the line got its `{count}`, but the button was copied as it was, with its 2 typed in. `App.jsx` stays as it was: it places `<Cart />`. We change `count` to 3 in `Cart.jsx` and save.

```jsx title="Cart.jsx" bad="6" role=CHILD
export default function Cart() {
  const count = 3; // Changed from 2, then saved
  return (
    <section>
      <p>Items: {count}</p>
      <button>Buy 2 items</button> {/* **PROBLEMATIC:** copied from the old page, 2 typed in */}
    </section>
  );
}
```

### Why does the 2 typed by hand stay?

On every save, React calls `Cart` again and makes each element show exactly what the JSX describes. With the button typed by hand, the JSX describes two different counts.

| element | written in the JSX | the page after the save, with `count` set to 3 |
| --- | --- | --- |
| the line | `Items: {count}` | "Items: 3", read from `count` |
| !the button | `Buy 2 items`, typed by hand | "Buy 2 items", the same text as before |

React did nothing wrong: the button never asked for `count`. Keeping each value in one place, which every part of the page reads, is called a **single source of truth**. A third place that shows the count, such as a number on the cart icon, adds one more `{count}` and no update code. Lecture 23 uses the same idea when two components share a value that changes.

## 3. Virtual DOM comparison: React changes only the new text

*Does React rebuild the cart? No: it changes only the new text*

```tree size=mini here="React changes only the new text"
The life of one value, `count`
- `Cart` describes the page
- Every place reads `{count}`
- React changes only the new text
```

> [!FACT] When we click into a text box and type, the box has the **focus**: it receives the keys we press and shows a blinking cursor.

> [!PRINCIPLE]
> **Principle 3: The virtual DOM: describing the page again when the value changes**
>
> When the value changes, React calls the component again and gets a new description of its whole part of the page.
>
> React compares the new description with the last one, element by element. It changes only the text that is new.
>
> Every other DOM node stays where it is, so a text box keeps what the user typed, and its focus. Notice: React never rebuilds the cart the way `innerHTML` does in plain JavaScript, with new DOM nodes that would lose the typed text.
>
> *We should do this:*
>
> ```jsx
> function Cart() {
>   const count = 3; // Changed from 2, then saved
>   return (
>     <section>
>       <p>Items: {count}</p> {/* Only the 2 becomes 3 */}
>       <input placeholder="Note to the shop" /> {/* The same DOM node: the note stays */}
>     </section>
>   );
> }
> ```

### Example: let's save a new count while a note is typed (only two texts change!)

Here, `Cart` returns a whole new description of the cart, yet React changes only two texts on the page. Each time React calls a component, the component describes its whole part of the page again. So a developer new to React expects the whole cart to be built again, and the note box to come back empty. React does not do that. It compares the new description with the last one, and changes only what differs.

We want the count to change to 3 while a note stays in the note box. `Cart` gets a note box between the line and the button. `App.jsx` stays as it was. On the open page, we type "Please ring the bell" into the note box. Then we change `count` to 3 in `Cart.jsx` and save.

```jsx title="Cart.jsx" good="6" role=CHILD
export default function Cart() {
  const count = 3; // Changed from 2, then saved
  return (
    <section>
      <p>Items: {count}</p>
      <input placeholder="Note to the shop" /> {/* The note box reads no variable */}
      <button>Buy {count} items</button>
    </section>
  );
}
```

```

### Why does the note stay?

React keeps the last description it got from `Cart`. After the save, `Cart` returns a new description, and React compares it with the last one, element by element. Then it changes, in the DOM nodes on the page, only what differs.

| element | the last description | the new description | the DOM node on the page |
| --- | --- | --- | --- |
| `<p>` | Items: 2 | Items: 3 | the text 2 becomes 3 |
| `<input>` | the note box | the note box | the same DOM node stays, with "Please ring the bell" |
| `<button>` | Buy 2 items | Buy 3 items | the text 2 becomes 3 |

So for this save, React makes two text changes and rebuilds nothing. Even "Items:" and "items" stay as they were, because `{count}` is its own piece of text. What the shopper typed lives in the `<input>` DOM node on the page, not in the description. The `<input>` is the same DOM node as before the save, so it still holds the note, and it keeps the focus.

The description is not the DOM. It is kept in memory as plain JavaScript objects that the browser never draws, as Lecture 3 shows. Because it has the shape of the DOM without being it, people often call it the **virtual DOM**. The React documentation describes what React does with it as "the minimal necessary operations": for this save, two text changes. When the new description is the same as the last one, React changes no text at all. Lecture 15 gives each step of an update its name.

### What React does with each element

```tree dir=right caption="What React does with each element of the cart when count changes."

- its text differs from the last description | React changes that text: 2 becomes 3
- it is the same as in the last description | React leaves its DOM node as it is: the note stays
```

## Putting the three together

We want the cart as the three principles built it. `Cart` describes every element, and no line of our code finds or changes one. The line and the button both read `{count}`, the single source of truth. When the file is saved with `count` set to 3, React compares the new description with the last one and changes only the two counts, so the note box keeps what the shopper typed.

## For the interview

- **What is React?** A JavaScript library for building user interfaces out of components. It can run a whole page, or only one part of a page that already exists.
- **How does its model differ from plain JavaScript DOM scripting?** In plain JavaScript, our code finds each element and changes it by hand. That is imperative, and an element the code forgets keeps old data, as the button kept "Buy 2 items" while the cart held 3. In React, a component describes what the page shows for the current data, and React builds and changes the DOM to match. That is declarative. Each value lives in one variable that every place reads, a single source of truth, so no place keeps an old copy.
- **Does React rebuild the page each time the data changes?** No, that is the classic trap. React calls the component again and compares the new description with the last one. On our cart, it changed two texts, 2 to 3, and rebuilt nothing. The note box, the same DOM node as before, kept the shopper's note and the cursor. People call the compared description the virtual DOM.
- **Is React faster than changing the DOM by hand?** No, and that is not its job. React changes the DOM with the same browser methods a script uses, and a script that sets one piece of text does that work with less code to run. React's gain is that our code no longer writes, or forgets, the update steps.
- **Does React stop an old value from showing anywhere?** Only where the JSX reads the variable. A value typed into the markup by hand keeps the old value, even in React.
- **Can I still call `document.getElementById` inside a component?** On the component's first run, its own elements are not on the page yet, so the call returns `null`; Lecture 10 shows the error this causes. For the few jobs that need one particular element, such as moving the cursor into a text box, React gives a way to reach it without changing what it shows (Lecture 30).

## Where you will meet this

- The signed-in user's name, in the greeting at the top and again in the account menu. Both read one variable, so a name change reaches both at once.
- An order total, in the order summary and on the Pay button. Both read one total, so the button never asks for a different amount than the summary shows.
- A comment box under an article. The comment count above it changes while a half-written comment stays in the box, because React changes the count's text and leaves the box as the reader left it.

product: 🧦 | Wool socks | $9
text: Items: 3 | good
typed: Please ring the bell | good
button: Buy 3 items | good
```

The two places agree on the count, and the note is still in its box. No line of our code found an element, and the note box was never rebuilt. Each thing on the page follows one principle of this lecture, and each principle has its tool.

| on the page | the rule behind it | the tool |
| --- | --- | --- |
| "Items: 3" and "Buy 3 items", with no script that sets them | the component says what each element shows, and React builds the DOM | the JSX `Cart` returns (Principle 1) |
| the same 3 in both places | every place reads one variable | `{count}` in the line and in the button (Principle 2) |
| "Please ring the bell" still in the note box after the count changed | React changes only the new text, so the note box stays the same DOM node | the comparison of the new description with the last one (Principle 3) |

With imperative code, the button would need its own command on every change. With declarative code, there is nothing to forget, and React changes only the new text.

## The components behind the page

Two components draw the cart, each in its own file, named after it: `App.jsx` and `Cart.jsx`. The project's `index.html` holds one empty element, `<div id="root"></div>`. `main.jsx`, the file the dev server runs first, puts `App` inside it; Lecture 9 explains how.

```hierarchy caption="The components of this lecture, one file each, and what each holds."
App | holds: the shop page
  Cart | holds: `count`, and the note box | here: describes the line, the note box, and the button
notes:
`App`, in `App.jsx`, imports `Cart` from `Cart.jsx` and places it with `<Cart />`. React calls each function where its tag stands; our code never calls them.
`Cart` keeps the count once, in `count`, and both the line and the button read it.
The note box reads no variable. What it holds comes from the shopper, and React leaves it alone when `count` changes.
```
