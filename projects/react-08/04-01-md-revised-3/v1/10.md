# React Conditional Rendering

## Two different ways to keep a part off the page

A part of the page can stay off the screen in two ways:

```tree caption="Two ways to keep a part off the page: the browser does not draw it, or React does not build it."
Two different ways to keep a part off the page
- Hide it: the element stays in the DOM | React builds it, and the browser does not draw it
- Leave it out: conditional rendering | the component does not return it, and React builds nothing
```

> [!FACT] `!` turns `true` into `false` and `false` into `true`. In a condition, `null`, `undefined`, `0`, and `''` count as false, so `!user` is `true` when `user` is `null`.

We compare the two ways on a New label, with `isNew` set to `false`. Both pages show no label. Only the Elements panel shows the difference:

::: row caption="The New label with isNew set to false. The two pages look the same; compare the Elements panels."
::: col title="Hide it" tag="the browser" tone=plain
```dom title="Elements panel"
<article class="card">
*  <span class="new-label" hidden="">New</span>
  <h2>Rain Expected This Weekend</h2>
</article>
```
```jsx
<span className="new-label" hidden={!isNew}>New</span>
```
React builds the span with `hidden` on it, and the browser does not draw it.
:::
::: col title="Leave it out" tag="React" tone=good
```dom title="Elements panel"
<article class="card">
  <h2>Rain Expected This Weekend</h2>
</article>
```
```jsx
{isNew && <span className="new-label">New</span>}
```
The component returns no span, so React builds nothing. Principle 2 explains how `&&` works.
:::
:::

We leave a part out in almost every case. Hidden JSX still runs: `<h2 hidden={!user}>{user.name}</h2>` still reads `user.name`, and throws when `user` is `null`. JSX that is left out never runs. We hide a part only when it must keep what is inside it while it is gone, such as text the user typed into a field. Hiding keeps that text. Leaving the part out throws it away.

Leaving a part out is **conditional rendering**. Each time React calls a component, the component chooses which JSX to return, with plain JavaScript.

## Conditional rendering: four kinds of choice

We call each part of the JSX that may or may not appear a **piece**: a label, a line of text, or a whole child component. A choice covers either the whole component or one piece inside it. For a piece, the tool depends on how many outcomes the choice has:

```tree caption="The four kinds of choice: first what the choice covers, then how many outcomes it has."
Leave it out: conditional rendering
- The whole component, or nothing | decided at the top of the function
  - Nothing to show | `return null`, or the parent leaves the tag out
- A piece inside the component | decided in the JSX, or above the `return`
  - One piece, or nothing | `&&`
  - One of two pieces | the ternary, `? :`
  - One of three or more | `if` and a variable
```

We learn the four in this order, because each builds on the one before. When the whole component has nothing to show, it returns `null`. When one piece shows or not, we use `&&`. When one of two pieces always shows, we use the ternary. When there are three or more outcomes, we use `if` and a variable.

::: pagebreak

# Principles

## 1. Nothing to show: return null at the top

*Why? Reading a property of `null` throws, and the whole page goes blank*

```tree size=mini here="Nothing to show"
Leave it out: conditional rendering
- The whole component, or nothing
  - Nothing to show
- A piece inside the component
  - One piece, or nothing
  - One of two pieces
  - One of three or more
```

> [!FACT] Reading a property of `null` throws a `TypeError`. Optional chaining, `?.`, reads it safely instead: `null?.name` gives `undefined`.

> [!PRINCIPLE]
> **Principle 1: Nothing to show: return null at the top**
>
> When a component has nothing to show for its props, it returns `null`.
>
> The `if` goes at the very top, before any line reads the missing data. When the parent decides whether the component appears at all, the parent leaves out its tag instead, as Principle 2 shows.
>
> *We should do this:*
>
> ```jsx
> function Profile({ user }) {
>   if (!user) {
>     return null; // No user: nothing shows, and the rest of the page stays
>   }
>   return (
>     <section className="profile">
>       <h2>{user.name}</h2>
>       <p>{user.city}</p>
>     </section>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function Profile({ user }) {
>   return (
>     <section className="profile">
>       <h2>{user.name}</h2> {/* **WRONG:** user is null, so this throws */}
>       <p>{user.city}</p>
>     </section>
>   );
> }
> ```

### Example: let's read the name of a missing user (the page goes blank!)

Here, a component reads data that is missing, and the whole page goes blank. Reading a property of `null` throws a `TypeError`. Nothing catches the error, so React removes the whole page, not only the profile.

We want a page with a heading and the reader's profile. The parent, `App.jsx`, holds the user and places the child, `Profile.jsx`. No one is signed in yet, so the user is `null`. The profile reads `user.name` at once:

```jsx title="App.jsx" role=PARENT
import Profile from './Profile.jsx'; // Our component, from its own file

export default function App() {
  const user = null; // No one is signed in yet
  return (
    <main>
      <h1>News</h1>
      <Profile user={user} />
    </main>
  );
}
```

```jsx title="Profile.jsx" bad="4" role=CHILD
export default function Profile({ user }) {
  return (
    <section className="profile">
      <h2>{user.name}</h2> {/* **WRONG:** user is null, so reading its name throws */}
      <p>{user.city}</p>
    </section>
  );
}
```

```hierarchy
`Profile` receives `null` as its `user`, and its first line of JSX reads `user.name`.
We want: no profile, and the rest of the page still there.
```

### Why does `user.name` blank the whole page?

A read of a property of `null` throws, and React has no place to show the rest of the page. `?.` stops the crash, but React still builds the element with empty tags. Only an `if` at the top stops the function before any line reads `user`:

```chain caption="Why each version gives its page, when user is null."
!`user.name` -> throws a `TypeError` -> nothing catches the error, so React removes the whole page
!`user?.name` -> gives `undefined`, no crash -> React still builds the empty `<section>`
+`if (!user) return null` -> no line reads `user` -> `null` builds nothing, and the page stays
```

We put the `if` at the very top of `Profile`, before the `return` that builds the profile:

```jsx title="Profile.jsx" good="2-4" role=CHILD
export default function Profile({ user }) {
  if (!user) {
    return null; // No user: Profile stops here and builds nothing
  }
  return (
    <section className="profile">
      <h2>{user.name}</h2>
      <p>{user.city}</p>
    </section>
  );
}
```

A `return` inside an `if` ends the function at once, so no later line runs: an **early return**. When `user` is an object, the `if` is skipped, and the profile is built as before.

### Let's check our console log

`Profile` still runs when it returns `null`. It only builds nothing. We log on the first line of `Profile`, before the `if`:

```jsx
console.log('Profile runs', user); // The first line of Profile
```

This project leaves Strict Mode out, so the Console shows one line for one run:

```devconsole source="Profile.jsx:2" caption="Chrome's Console, with user set to null and the early return in place."
Profile runs null
```

### Who decides that nothing shows?

The component itself can decide, as here, or its parent can:

```tree dir=right caption="Who decides that nothing shows, and how."
Nothing to show: who decides?
- The component itself | when nothing outside it has to go: `if (!user) return null`, at its very top
- The parent | when the parent owns markup around it, such as a heading: it leaves the tag out (Principle 2)
```

## 2. One piece, or nothing: a true or false value left of &&

*Why? `&&` gives back one of its sides, and React shows a number*

```tree size=mini here="One piece, or nothing"
Leave it out: conditional rendering
- The whole component, or nothing
  - Nothing to show
- A piece inside the component
  - One piece, or nothing
  - One of two pieces
  - One of three or more
```

> [!FACT] The common **falsy** values, the ones that count as false in a condition, are `false`, `0`, `''`, `null`, `undefined`, and `NaN`. `&&` gives back its left side when that side is falsy, and its right side otherwise. In JSX, React shows nothing for `false`, `null`, and `undefined`, but it shows a number as text.

> [!PRINCIPLE]
> **Principle 2: One piece, or nothing: `&&` with a true or false value on the left**
>
> To show a piece or nothing, we write `condition && <Piece />`.
>
> The left side must be a true or false value, such as `count > 0`. A bare number on the left shows on the page when it is 0.
>
> *We should do this:*
>
> ```jsx
> function Inbox({ count }) {
>   return (
>     <section>
>       <h2>Inbox</h2>
>       {count > 0 && <p>{count} messages</p>} {/* Count is 0: false, nothing */}
>     </section>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function Inbox({ count }) {
>   return (
>     <section>
>       <h2>Inbox</h2>
>       {count && <p>{count} messages</p>} {/* **PROBLEMATIC:** the page shows 0 */}
>     </section>
>   );
> }
> ```

### Example: let's put a number left of `&&` (React shows the 0!)

Here, a number left of `&&` puts a bare 0 on the page. `&&` is not an inline `if`. It gives back one of its two sides, and React shows whatever it gets back. For `false`, React shows nothing, but it shows the number `0` as text.

We want an inbox with a heading, and a line for the messages only when there are some. The parent, `App.jsx`, places the child, `Inbox.jsx`, with a count of 0. We put the count itself left of `&&`:

```jsx title="App.jsx" role=PARENT
import Inbox from './Inbox.jsx'; // Our component, from its own file

export default function App() {
  return <Inbox count={0} />; // No messages yet
}
```

```jsx title="Inbox.jsx" bad="5" role=CHILD
export default function Inbox({ count }) {
  return (
    <section>
      <h2>Inbox</h2>
      {count && <p>{count} messages</p>} {/* **PROBLEMATIC:** count is 0, so the page shows 0 */}
    </section>
  );
}
```

How the two components connect:

```hierarchy
App | holds: the page
  Inbox | gets: `count`, which is `0` | here: shows the line, or nothing
notes:
`App`, in `App.jsx`, imports `Inbox` from `Inbox.jsx` and places it with `<Inbox count={0} />`.
`Inbox` puts `count` itself left of `&&`.
We want: the heading, and a messages line only when there are messages.
```

### Let's check the page

We compare two versions of the left side. With `count`, a bare 0 appears under the heading. With `count > 0`, nothing appears. Each column shows the page, then the code:

### Why does a 0 appear?

> [!FACT] A **comparison** gives `true` or `false`: `count > 0` asks whether `count` is greater than 0, `count === 1` whether it is exactly 1, and `user !== null` whether `user` is anything other than `null`.

`&&` gives back one of its two sides, and the page shows whatever it gave back. A comparison always gives a real `true` or `false`, so it is a safe left side. We follow each left side to the page, for a count of 0 and a count of 3:

| count | left side | `&&` gives back | the page shows |
| --- | --- | --- | --- |
| !0 | `count` | `0` | 0 |
| 3 | `count` | `<p>3 messages</p>` | 3 messages |
| 0 | `count > 0` | `false` | nothing |
| 3 | `count > 0` | `<p>3 messages</p>` | 3 messages |

```tree dir=right caption="What we put left of &&."
What stands left of &&?
- +a true or false value | the piece when true, nothing when false: `isNew`, `count > 0`
- !a number, such as `count` | when it is `0`, the `0` itself appears on the page
```

### Let's leave a whole component out in the parent

A parent uses the same `&&` to leave a whole child out. This is the parent's way to show nothing, from Principle 1. We want a "Your profile" heading above the profile. The heading belongs to `App`, so `Profile`'s `return null` would leave the heading above an empty space. So `App` leaves both out, with a comparison on the left:

```jsx title="App.jsx" good="6" role=PARENT
export default function App() {
  const user = null;
  return (
    <main>
      <h1>News</h1>
      {user !== null && ( /* No user: no heading and no profile */
        <section>
          <h2>Your profile</h2>
          <Profile user={user} />
        </section>
      )}
    </main>
  );
}
```

When `user` is `null`, the comparison gives `false`. Neither the heading nor the profile appears, and `Profile` never runs, so its `console.log` prints nothing:

```devconsole caption="Chrome's Console, with user set to null and the parent leaving Profile out."
= No messages
```

When `user` is an object, the comparison gives `true`, and both appear. `Profile` keeps its own `if (!user) return null`, for any other parent that passes `null`.

## 3. One of two pieces: a ternary around the piece that differs

*Why? The markup both cases share is written once, so a change reaches both*

```tree size=mini here="One of two pieces"
Leave it out: conditional rendering
- The whole component, or nothing
  - Nothing to show
- A piece inside the component
  - One piece, or nothing
  - One of two pieces
  - One of three or more
```

> [!FACT] The ternary `condition ? a : b` gives `a` when the condition is true, and `b` otherwise.

> [!PRINCIPLE]
> **Principle 3: One of two pieces: a ternary around the piece that differs**
>
> To show one of two pieces in the same place, we write `condition ? <A /> : <B />` inside the JSX.
>
> The markup both cases share is written once, outside the ternary. Two whole returns fit only when the two cases share nothing.
>
> *We should do this:*
>
> ```jsx
> function ArticleCard({ article, isSignedIn }) {
>   return (
>     <article>
>       <h2>{article.title}</h2> {/* Both readers see it, so it is written once */}
>       {isSignedIn ? ( /* Only this part differs between readers */
>         <p>{article.summary}</p>
>       ) : (
>         <p>Sign in to read this article.</p>
>       )}
>     </article>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function ArticleCard({ article, isSignedIn }) {
>   if (isSignedIn) {
>     return (
>       <article>
>         <h2>{article.title}</h2>
>         <p>{article.summary}</p>
>       </article>
>     );
>   }
>   return (
>     <article>
>       <h2>{article.title}</h2> {/* **PROBLEMATIC:** the same h2 again */}
>       <p>Sign in to read this article.</p>
>     </article>
>   );
> }
> ```

### Example: let's write one return for each reader (the copies drift apart!)

Here, two returns copy the same markup, and a later change reaches only one copy. Nothing warns us. The build passes, the Console stays clean, and only one reader's card is wrong.

We want an article card with its title and its author for every reader. A signed-in reader sees the summary, and a visitor sees a sign-in prompt in its place. The parent, `App.jsx`, places the child, `ArticleCard.jsx`, once for each kind of reader. We write one return for each reader. Later we add the author's line, and the change reaches only the first return:

```jsx title="App.jsx" role=PARENT
import ArticleCard from './ArticleCard.jsx'; // Our component, from its own file

const park = {
  title: 'New Park Opens Today', author: 'Mary Jones',
  summary: 'The park on Main Street opens at noon.',
};

export default function App() {
  return (
    <main>
      <ArticleCard article={park} isSignedIn={true} /> {/* A signed-in reader */}
      <ArticleCard article={park} isSignedIn={false} /> {/* A visitor */}
    </main>
  );
}
```

```jsx title="ArticleCard.jsx" bad="13" role=CHILD
export default function ArticleCard({ article, isSignedIn }) {
  if (isSignedIn) {
    return (
      <article className="card">
        <h2>{article.title}</h2>
        <p className="author">By {article.author}</p> {/* The new line reached this copy */}
        <p>{article.summary}</p>
      </article>
    );
  }
  return (
    <article className="card">
      <h2>{article.title}</h2> {/* **PROBLEMATIC:** no author line: the change missed this copy */}
      <p>Sign in to read this article.</p>
    </article>
  );
}
```

### Component Hierarchy

How the components connect:

```hierarchy
App | holds: one article, `park`
  ArticleCard | gets: `article`, `isSignedIn={true}` | here: the first return
  ArticleCard | gets: `article`, `isSignedIn={false}` | here: the second return
notes:
`App`, in `App.jsx`, imports `ArticleCard` from `ArticleCard.jsx` and places it twice, once for each kind of reader.
Both cards are the same component. Only `isSignedIn` differs, and it picks the return.
We want: the same title and author line for both readers, and only the summary or the prompt different.
```

### Why do two returns drift apart?

Two returns copy the same markup, so every later change must be made twice. When we miss one copy, the two cards drift apart. Between the two readers, only one paragraph really differs: the summary or the sign-in prompt. So only that paragraph goes inside the choice.

We write one `return`, with the ternary right where the paragraph goes. Every shared part is written once, so the author line reaches both readers:

```jsx title="ArticleCard.jsx" good="6-10" role=CHILD
export default function ArticleCard({ article, isSignedIn }) {
  return (
    <article className="card">
      <h2>{article.title}</h2>
      <p className="author">By {article.author}</p>
      {isSignedIn ? ( /* Signed in: the summary; otherwise the prompt */
        <p>{article.summary}</p>
      ) : (
        <p>Sign in to read this article.</p>
      )}
    </article>
  );
}
```

```tree dir=right caption="When to use one return with a ternary, and when separate returns are fine."
Do the two cases share markup?
- +Yes | one `return`, with a ternary around the part that differs
- No | separate returns are fine: an early `return null` shares nothing with the rest
```

### The ternary needs both sides

A ternary always needs both sides. When we write only the first side, `{isSignedIn ? <p>{article.summary}</p>}`, the build cannot read the file, and Vite covers the page with its **error overlay**:

```overlay size=mini
message: [PARSE_ERROR] Expected ':' but found '}'
file: src/ArticleCard.jsx
```

When one side is "nothing", we use `&&` instead.

## 4. One of three or more: if and a variable above the return

*How? One case per branch, read from top to bottom*

```tree size=mini here="One of three or more"
Leave it out: conditional rendering
- The whole component, or nothing
  - Nothing to show
- A piece inside the component
  - One piece, or nothing
  - One of two pieces
  - One of three or more
```

> [!PRINCIPLE]
> **Principle 4: One of three or more: `if` and a variable above the return**
>
> When a choice has more than two cases, we pick the piece with `if`, `else if`, and `else` above the `return`.
>
> We store it in a variable and place the variable in the JSX. A ternary inside another ternary works, but it is hard to read.
>
> *We should do this:*
>
> ```jsx
> function CommentCount({ count }) {
>   let text;
>   if (count === 0) { // One case per branch, read from top to bottom
>     text = 'No comments yet';
>   } else if (count === 1) {
>     text = '1 comment';
>   } else {
>     text = count + ' comments';
>   }
>   return <p>{text}</p>; // The one wording the if chain picked
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function CommentCount({ count }) {
>   return (
>     <p>
>       {count === 0
>         ? 'No comments yet'
>         : count === 1 // **PROBLEMATIC:** a ternary inside a ternary
>           ? '1 comment'
>           : count + ' comments'}
>     </p>
>   );
> }
> ```

### Example: let's put a ternary inside a ternary (the code is hard to read!)

Here, the code works, but it is hard to read. A ternary chooses between two outcomes. For a third outcome, we put a second ternary inside the first, and the reader must pair each `:` with its `?`. Each new case adds another level.

We want a comment line worded for none, one, or many comments. The parent, `App.jsx`, places the child, `CommentCount.jsx`, three times, with 0, 1, and 5 comments. We choose the wording with a ternary inside a ternary:

```jsx title="App.jsx" role=PARENT
import CommentCount from './CommentCount.jsx'; // Our component, from its own file

export default function App() {
  return (
    <main>
      <CommentCount count={0} /> {/* None, one, and many */}
      <CommentCount count={1} />
      <CommentCount count={5} />
    </main>
  );
}
```

```jsx title="CommentCount.jsx" bad="6" role=CHILD
export default function CommentCount({ count }) {
  return (
    <p>
      {count === 0
        ? 'No comments yet'
        : count === 1 // **PROBLEMATIC:** a second ternary inside the first
          ? '1 comment'
          : count + ' comments'}
    </p>
  );
}
```

### Component Hierarchy

How the components connect:

```hierarchy
App | holds: the page
  CommentCount | gets: `count={0}` | here: picks a wording
  CommentCount | gets: `count={1}` | here: picks a wording
  CommentCount | gets: `count={5}` | here: picks a wording
notes:
`App`, in `App.jsx`, imports `CommentCount` from `CommentCount.jsx` and places it three times.
Each `CommentCount` receives one number and picks one of three wordings.
We want: each case readable on a line of its own.
```

### Let's compare the two versions

To read it, we pair each `:` with its `?`.

### Why is the if chain easier to read?

Each branch of the `if` chain holds one case, and we read the cases from top to bottom. The first branch runs for 0, the second for 1, and the `else` for any other count. The JSX only places the result, `<p>{text}</p>`:

```chain caption="One wording for each count; 5 stands for any count of 2 or more."
`count: 0` -> the first branch -> No comments yet
`count: 1` -> the second branch -> 1 comment
`count: 5` -> the `else` -> 5 comments
```

> [!FACT] Inside JSX braces, only an **expression** can go: code that gives a value, such as `count > 0` or a ternary. An `if` is a **statement**: it does something but gives no value, so it cannot go inside the braces.

The variable can hold JSX as well as text: `text = <em>No comments yet</em>;` works the same way. An `if` is a statement, so it goes above the `return`. `&&` and the ternary are expressions, so they go inside the JSX braces:

```tree dir=right caption="Where each tool goes: expressions inside the braces, statements above the return."
Where does the choice go?
- Inside the JSX braces | expressions only: `&&` and `? :`
- Above the `return` | statements: `if (!user) return null`, and `if` with a variable
```

## Putting the four together

We want an article card that uses all four tools. It returns `null` when there is no article. It shows the New label with `&&` when the article is new. It shows the summary or the sign-in prompt with a ternary. It picks the comment wording with `if` and a variable:

**DO THIS:**

```jsx right
export default function ArticleCard({ article, isSignedIn }) {
  if (!article) {
    return null;
  }
  const count = article.commentCount;
  let commentText;
  if (count === 0) {
    commentText = 'No comments yet';
  } else if (count === 1) {
    commentText = '1 comment';
  } else {
    commentText = count + ' comments';
  }
  return (
    <article className="card">
      {article.isNew && <span className="new-label">New</span>}
      <h2>{article.title}</h2>
      <p className="author">By {article.author}</p>
      {isSignedIn ? <p>{article.summary}</p> : <p>Sign in to read this article.</p>}
      <p className="comments">{commentText}</p>
    </article>
  );
}
```

Here is the same card with four mistakes, marked in red. It reads `article` without checking it first, so the card throws a `TypeError` when `article` is `null` (line 2). It nests one ternary inside another (line 10). It copies the markup into two returns that have already drifted apart, so visitors lose the New label even on a new article (lines 14 to 21). It puts a bare number left of `&&`, so a visitor sees a bare 0 on an article with no comments (line 19):

**DO NOT DO THIS:**

```jsx wrong bad="2,10,14-21"
export default function ArticleCard({ article, isSignedIn }) {
  const count = article.commentCount;
  if (isSignedIn) {
    return (
      <article className="card">
        {article.isNew && <span className="new-label">New</span>}
        <h2>{article.title}</h2>
        <p className="author">By {article.author}</p>
        <p>{article.summary}</p>
        <p>{count === 0 ? 'No comments yet' : count === 1 ? '1 comment' : count + ' comments'}</p>
      </article>
    );
  }
  return (
    <article className="card">
      <h2>{article.title}</h2>
      <p className="author">By {article.author}</p>
      <p>Sign in to read this article.</p>
      {count && <p>{count} comments</p>}
    </article>
  );
}
```

## For the interview

- **Is `&&` an inline `if`?** No. It gives back one of its two sides, so `0 && <Badge />` gives back `0`, and React shows it. We put a true or false value on the left: `count > 0 && <Badge />`.
- **Is returning `null` the same as leaving the tag out in the parent?** The page looks the same when the parent puts nothing around the tag. When the parent has its own markup there, such as a heading, only leaving the tag out removes that too. With `null`, the component still runs every time its parent renders, and a `console.log` inside it still prints. When the parent leaves the tag out, the component never runs.
- **Why not just `display: none`?** Hidden JSX still runs, so `<h2 hidden={!user}>{user.name}</h2>` still throws when `user` is `null`. A hidden element also stays in the DOM with what is inside it, such as typed text. A part that is left out is removed, and when it comes back, React builds it again, empty. So we hide only a part that must keep what is inside it while it is gone.
- **`return null` or `return;` with no value?** `return;` gives `undefined`. Before React 18, returning `undefined` threw an error. Now both show nothing. `null` says that the choice is on purpose.
- **Why would `<ArticleCard article={park} isSignedIn="false" />` show the summary to a visitor?** A prop written in quotes is text, and any non-empty text is **truthy**, the opposite of falsy. So the ternary takes its first side. `isSignedIn={false}`, in braces, passes a real `false`.

## Where you will meet this

- An unread badge, shown only when there are unread messages: we write `unread > 0 && <Badge />`, never `unread && <Badge />`, which shows a 0 when there are none.
- A header that shows "Sign in" to a visitor and an avatar to a signed-in reader: we use a ternary.
- An order status with one wording for each of four stages (placed, packed, shipped, delivered): we pick the wording with an `if` chain into a variable.

## Summary

```tree caption="The whole lecture as one tree."
Two different ways to keep a part off the page
- Hide it: the element stays in the DOM | when the part must keep what is inside it while it is gone
- Leave it out: conditional rendering | when the part only depends on data
  - The whole component, or nothing | decided at the top of the function
    - Nothing to show | `return null` at the top, or the parent leaves the tag out
  - A piece inside the component | decided in the JSX, or above the `return`
    - One piece, or nothing | `&&`, with true or false on the left
    - One of two pieces | the ternary, around the part that differs
    - One of three or more | `if` and a variable, above the `return`
```

**Nothing to show, one piece or nothing, one of two pieces, or one of three or more.**

## Example: article cards on a news site

A news site lists its latest articles, and one component, `ArticleCard`, draws each card. The two cards below do not show the same parts. The park card has a red New label, and the rain card has none. The park card says "3 comments", and the rain card says "No comments yet". The site has no featured article today, so no featured card appears at the top. Here is the page for a signed-in reader:

```page caption="The home page of the news site, for a signed-in reader. One component draws both cards."
heading: Latest Articles
card: title=New Park Opens Today | author=Mary Jones | text=The park on Main Street opens at noon. | label=New | foot=3 comments
card: title=Rain Expected This Weekend | author=Oliver Brooks | text=Heavy rain is expected on Saturday and Sunday. | foot=No comments yet
```

Each difference follows a rule of the form IF something is true, THEN show this part. Each rule uses one of the four tools of this lecture, inside the card from "Putting the four together":

| on the page | the rule behind it | the tool |
| --- | --- | --- |
| no featured card at the top | IF there is no featured article, THEN show nothing | `return null` (Principle 1) |
| a red New label on the park card only | IF the article is new, THEN show the label | `&&` (Principle 2) |
| a summary on both cards, for this reader | IF the reader is signed in, THEN the summary, ELSE a sign-in prompt | the ternary (Principle 3) |
| "3 comments" and "No comments yet" | IF 0, THEN "No comments yet", ELSE IF 1, THEN "1 comment", ELSE the count | `if` and a variable (Principle 4) |

The park article is new and has 3 comments. The rain article is not new and has none. A visitor who is not signed in sees a sign-in prompt in place of each summary. The markup is the same for every card. Only the data differs, and each choice reads it.
