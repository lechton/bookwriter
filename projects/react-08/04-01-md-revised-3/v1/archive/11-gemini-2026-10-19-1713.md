# React Rendering Lists

## Two different ways to render one row per email

A mail application displays dozens or hundreds of messages, and each one appears as a row with identical structure: a selection checkbox, a sender, and a subject line. In the browser DOM, each row is a real HTML element containing form inputs. Only the dynamic data changes from row to row.

Let us be completely candid before we write a single line of code: nobody in their right mind hardcodes three row components by hand in a real production codebase. If you open a pull request with hardcoded array indices, a senior engineer will reject it immediately. So why do we start our architectural review by comparing hardcoded tags with dynamic mapping? Because this baseline isolation reveals React's engine reality: React has zero built-in loop directives. Angular provides ngFor, Vue provides v-for, but React gives you zero special templating syntax for loops. Whether you write three tags manually or map an array of five hundred items, React receives the exact same thing: a flat array of element descriptors. We compare the two approaches to see what happens when the server pushes a new message to your inbox.

```tree caption="Two ways to get one row per email: write each tag by hand, or draw the rows from the array."
Two different ways to render one row per email
- Fixed: written by hand | one tag per email, typed into the JSX
- Dynamic: rendering a list from an **array** | one tag, repeated for every email in the array
```

> [!FACT] An array keeps its values in order and counts them from 0. In `emails`, an array of email objects, `emails[0]` is the first email, `emails[1]` the second, and `emails[2]` the third.

::: pagebreak

> **THE TAKEAWAY**
> Hardcoding elements by hand forces you to know the exact size of your data ahead of time. The moment a fourth email arrives from the backend, your markup is out of sync. With `map()`, you write the template for a single item once, and JavaScript renders three rows or three hundred without you touching the component again.

::: row flow=down caption="A fourth email arrives at the top of the array. The code on top, and under each, the inbox it gives."
::: col title="Fixed: written by hand" tone=bad
```mail size=mini

email: ShopNow | 🔥 FLASH SALE: Extra 15% off | | unread
email: Anna Lee | Team meeting moved
```

```jsx
<form>
  <EmailRow email={emails[0]} /> {/* One tag per email */}
  <EmailRow email={emails[1]} />
  <EmailRow email={emails[2]} />
</form>
```
With four emails in the array, the page still shows only three rows. "Photos from the trip" drops off the screen entirely until a developer manually edits the JSX file to add a fourth tag.
:::
::: col title="Dynamic: from the array" tone=good
```mail size=mini

email: ShopNow | 🔥 FLASH SALE: Extra 15% off | | unread
email: Anna Lee | Team meeting moved
email: Mom | Photos from the trip
```
```jsx

  {emails.map(email => ( /* One tag for every email */
    <EmailRow email={email} />
  ))}
</form>
```
With four emails in the array, the page immediately displays four rows from a single declarative tag. Principle 1 explains how `map()` turns data into elements.
:::

Why does this difference matter in production? When code is written by hand, your component must know the exact count of items ahead of time, turning every data update into a manual code deployment. When rendered from an array, incoming data automatically projects onto the screen with zero component modifications. The same dynamic pipeline also allows us to filter messages by folder or search query on the fly, as Principle 2 shows. Hardcoded elements are acceptable only for fixed navigation links that never change. Every collection that originates from data must be drawn dynamically from that data.

> [!FACT] Each JSX tag, such as `<EmailRow />`, creates a React element: an immutable JavaScript object in memory describing what should appear on screen. It is not a real DOM element. React consumes these element objects and synchronizes them with real browser DOM nodes.

Transforming data collections into UI elements is called **rendering a list**. An array of data objects becomes an array of React element descriptors, and React mounts them into the document in order. Every element in that collection also requires an explicit key, which preserves component identity and user input when items are added, removed, or reordered.

## Rendering a list: four steps in two pairs

Rendering a list follows four architectural steps divided into two logical pairs. The first pair creates the virtual elements from raw data. The second pair maintains element identity and state preservation during updates.

```tree caption="The four steps of rendering a list: first create the rows, then update them correctly when the list changes."
Dynamic: rendering a list from an array
- Create the rows | from the array to the page
  - Rows for every email | `map()`
  - Rows for only some emails | `filter()`, then `map()`
- Update the rows when the list changes | each row stays with its email
  - Key from the email's id | not from its position
  - Key on the tag `map()` returns | not inside the row
```

We review these steps in strict sequence because each step depends directly on the one before it. We master `map()` first, because every subsequent collection pattern operates on the element array it produces. We cover `filter()` next, because filtering runs immediately prior to mapping. Keys come third, because keys name the elements that `map()` produces. Finally, key placement answers where that identifier belongs once you understand what keys accomplish.

# Principles

## 1. Rows for every email: map()

*How? `map()` gives back one element per email, in a new array*

```tree size=mini here="Rows for every email"
Dynamic: rendering a list from an array
- Create the rows
  - Rows for every email
  - Rows for only some emails
- Update the rows when the list changes
  - Key from the email's id
  - Key on the tag `map()` returns
```

> [!FACT] An **arrow function** is a concise way to write a function: the parameter, followed by `=>`, followed by the returned value. `email => email.subject` accepts an email object and returns its subject string.

> [!FACT] **`forEach()`** executes a callback for each item in an array and always returns `undefined`. **`map()`** executes a callback for each item and collects every returned value into a brand new array of identical length. In `email => ...`, the parameter holds the first email on the first invocation, the second on the second, and so on.

> [!PRINCIPLE]
> **Principle 1: Rows for every email: `map()`**
>
> To show one element per item, we call `map()` on the array inside the JSX.
>
> The arrow function can return the element directly using concise parentheses `( )`. If it opens curly braces `{ }`, it has a block body and must use an explicit `return`. Notice: a missing `return` is easy to overlook.
>
> *We should do this:*
>
> ```jsx
> function EmailList() {
>   return (
>     <form>
>       {emails.map(email => ( /* Parentheses: the row is given back */
>         <EmailRow email={email} />
>       ))}
>     </form>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function EmailList() {
>   return (
>     <form>
>       {emails.map(email => { // **PROBLEMATIC:** curly braces open a body with no return
>         <EmailRow email={email} />; // Never given back: no row
>       })}
>     </form>
>   );
> }
> ```

The inbox is completely empty, and the console displays zero errors. Why? Because in JavaScript, curly braces turn an implicit return into a function block body. Without an explicit `return` keyword, the function returns `undefined` on every iteration.

We want one row per message. Our emails live in their own file, `emails.js`, stored as a clean array of objects. Each object carries an `id`, a unique integer that identifies that specific email, along with the sender, subject line, and folder category.

Both files reside in `src/components/`, so `EmailList` imports the data from the parent directory. ### Why does every call give back `undefined`?

> [!FACT] When a curly brace follows `=>`, the arrow function has a **block body**: it returns only what an explicit `return` statement specifies. Without a `return`, it silently returns `undefined`. With parentheses or a bare expression after `=>`, it returns that expression directly.

The `map()` method creates a new array by collecting whatever the callback returns for each item. The delimiter immediately following the arrow dictates the outcome. With parentheses, the arrow returns a React element descriptor. With curly braces and no `return`, it returns `undefined`. Beginners often attempt to use `forEach()` instead, which fails for an even simpler reason: `forEach()` is built for side effects and always returns `undefined` as a whole method.

```chain caption="What each version gives back for the three emails, and so what the page shows."
!`emails.forEach(...)` -> `undefined` -> nothing to place: no rows
!`emails.map(email => { <EmailRow />; })` -> `[undefined, undefined, undefined]` -> no rows
+`emails.map(email => <EmailRow />)` -> `[<EmailRow>, <EmailRow>, <EmailRow>]` -> three rows
```

We use concise parentheses in `EmailList.jsx` so that the arrow returns each element descriptor directly.

```jsx title="EmailList.jsx" good="7-9" role=PARENT
import { emails } from '../emails.js';
import EmailRow from './EmailRow.jsx';

export default function EmailList() {
  return (
    <form>
      {emails.map(email => ( /* Parentheses: the row is given back */
        <EmailRow email={email} />
      ))}
    </form>
  );
}
```

Writing `return <EmailRow email={email} />;` inside explicit curly braces works exactly the same way. When a fourth email arrives in `emails.js`, this exact same expression automatically evaluates to four elements.

## 2. Rows for only some emails: filter(), then map()

*When? A folder shows only its own emails, and a folder can have none*

```tree size=mini here="Rows for only some emails"
Dynamic: rendering a list from an array
- Create the rows
  - Rows for every email
  - Rows for only some emails
- Update the rows when the list changes
  - Key from the email's id
  - Key on the tag `map()` returns
```

> [!FACT] **`filter()`** executes a test function for each item and returns a new array containing only the items that returned `true`. An array's **`length`** property reflects its item count; an empty array has a length of `0`.

> [!PRINCIPLE]
> **Principle 2: Rows for only some emails: `filter()`, then `map()`**
>
> To show only some items, we call `filter()` before `map()`. It keeps only the items that pass a test.
>
> When no item passes, the array is empty, and its length is `0`. Then we show a message, with `length > 0` and the ternary. Notice: a bare `length` on the left of `&&` puts a `0` on the page instead.
>
> *We should do this:*
>
> ```jsx
> function EmailList({ folder }) {
>   const shown = emails.filter(email => email.folder === folder);
>   const rows = shown.map(email => <EmailRow email={email} />);
>   return (
>     <section>
>       <h2>{folder}</h2>
>       {shown.length > 0 ? rows : <p>No emails here.</p>} {/* No emails: the message */}
>     </section>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function EmailList({ folder }) {
>   const shown = emails.filter(email => email.folder === folder);
>   const rows = shown.map(email => <EmailRow email={email} />);
>   return (
>     <section>
>       <h2>{folder}</h2>
>       {shown.length && rows} {/* **PROBLEMATIC:** a bare length shows 0 */}
>     </section>
>   );
> }
> ```

Here is the embarrassing bug that frequently slips past code review and makes websites look broken in front of clients. A junior engineer remembers Lecture 10: "use `&&` for conditional rendering." So they write `{shown.length && rows}`. When testing with an inbox full of emails, it renders perfectly. Then a user clicks on an empty folder, such as Spam. What appears beneath the heading? A stray, naked `0` sitting awkwardly on the screen. Why? Because JavaScript's `&&` operator evaluates falsy numbers directly to `0`, and React renders numbers straight to the browser DOM as text.

We want each folder to show only its own emails, with a message when it has none. The parent component, `EmailList.jsx`, receives the `folder` the reader opened, such as `"Inbox"` or `"Spam"`, from the folder menu, a part of the app left out here. It keeps the emails of that folder with `filter()`, maps them to rows, and renders the result. The child component, `EmailRow.jsx`, is the same row as before. All three sample emails are filed under Inbox, leaving Spam completely empty. We use `&&` to render the rows.

```jsx title="EmailList.jsx" bad="10" role=PARENT
import { emails } from '../emails.js';
import EmailRow from './EmailRow.jsx';

export default function EmailList({ folder }) {
  const shown = emails.filter(email => email.folder === folder); // This folder's emails
  const rows = shown.map(email => <EmailRow email={email} />);
  return (
    <section>
      <h2>{folder}</h2>
      {shown.length && rows} {/* **PROBLEMATIC:** a bare length shows 0 */}
    </section>
  );
}
```

### Why does a 0 appear?

> [!FACT] The logical AND expression `a && b` returns its left operand `a` whenever `a` is falsy (such as `0`, `false`, `null`, or `undefined`), and returns `b` otherwise. In JSX, React treats `false`, `null`, and `undefined` as empty markup, but it renders numeric values directly to the DOM as visible text. A boolean comparison like `length > 0` guarantees a strict `true` or `false`.

The logical `&&` operator does not convert values to booleans; it returns one of its operands. React then renders whatever value it receives. Here is how the same `EmailList` evaluates under the bare length pattern, for each `folder` it receives:

| `folder` | `filter()` gives back | `shown.length` | `shown.length && rows` gives back | the page shows |
| --- | --- | --- | --- | --- |
| `"Inbox"` | three emails | `3` | `rows`, three rows | the three rows |
| !`"Spam"` | `[]` | `0` | `0` | a bare 0 |

The senior developer standard is explicit: write `{shown.length > 0 ? rows : <p>No emails here.</p>}`. The comparison guarantees a genuine boolean `false`, and the ternary gracefully switches between populated rows and an informative empty state.

## 3. Key from the email's id, not its position

*Why? Without a key, React matches the DOM elements on the page to the array by position*

```tree size=mini here="Key from the email's id"
Dynamic: rendering a list from an array
- Create the rows
  - Rows for every email
  - Rows for only some emails
- Update the rows when the list changes
  - Key from the email's id
  - Key on the tag `map()` returns
```

> [!FACT] Form inputs maintain their own internal state in the browser DOM. A checkbox remembers whether it is checked inside its real DOM element, outside of React's JavaScript variables. When a form submits, each checked box sends its `value`, so an input with `value={email.id}` transmits that email's unique ID.

> [!FACT] A **key** is a reserved attribute that React uses to track identity across re-renders: `key={email.id}`. The `map()` method also provides the current iteration index as an optional second parameter: `items.map((item, index) => ...)`, where `index` starts at 0.

> [!PRINCIPLE]
> **Principle 3: Key from the email's id, not its position**
>
> We give each element a `key`, taken from the item's own id. React then keeps each DOM element on the page matched to its own item when the array changes.
>
> The array index works only for a list whose positions never change: items are only added or removed at the end, and never sorted or moved. A key made while rendering, such as a random number, never works.
>
> *We should do this:*
>
> ```jsx
> function EmailList() {
>   return (
>     <form>
>       {emails.map(email => (
>         <EmailRow key={email.id} email={email} /> // The row follows its email
>       ))}
>     </form>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function EmailList() {
>   return (
>     <form>
>       {emails.map((email, index) => (
>         <EmailRow key={index} email={email} /> // **PROBLEMATIC:** the index is the position
>       ))}
>     </form>
>   );
> }
> ```

### Why do we delete the wrong email?

> [!AHA] What is going on
> 1. **The `emails` array and the DOM elements on the page are two different lists.** The `emails` array is a variable in our JavaScript code: an array of objects. The DOM elements are what the browser shows on the page. The `emails` array and the DOM elements should be linked one by one, but they are not the same thing.
> 2. **React builds the DOM elements on the page from the `emails` array.** For each object in the `emails` array, React builds one DOM element on the page, in the same order.
> 3. **So the `emails` array and the DOM elements on the page must match one by one.** When the `emails` array changes, the DOM elements on the page must change with it.
> 4. **The `emails` array and the DOM elements on the page hold different things.** Each object in the `emails` array holds an email's sender, subject, and id. Each DOM element on the page holds what the reader did there: the tick in its checkbox. The tick is in the DOM element on the page, not in the `emails` array.
> 5. **A new object arrives at the top of the `emails` array.** Now "Lunch on Friday?" is the first object in the `emails` array, and "🔥 FLASH SALE: Extra 15% off" is the second.
> 6. **The DOM elements on the page do not move by themselves.** The DOM element with our tick is still the first DOM element on the page. React must decide which DOM element on the page now shows which object of the `emails` array.
> 7. **Without a key, React matches the objects of the `emails` array to the DOM elements on the page by position.** The first object goes into the first DOM element, the second object into the second DOM element, and so on.
> 8. **So the first DOM element on the page, the one with our tick, now shows "Lunch on Friday?".** Its subject and its `value`, `4`, come from the first object of the `emails` array, so they change. The tick is in the DOM element on the page, so it stays.
> 9. **Oops: we press Delete selected.** The form sends `4`. "Lunch on Friday?" is deleted before we read it, and "🔥 FLASH SALE: Extra 15% off" is still there.
>
> **The `emails` array and the DOM elements on the page must match one by one. Without a key, React matches them by position, and the tick stays in the wrong DOM element.**

This architectural defect explains why unique item IDs exist. Supplying `key={email.id}` instructs React's reconciler to match DOM nodes by their persistent database identity rather than transient array positions. We add the key to the tag inside `map()`.

```jsx title="EmailList.jsx" good="2"
{emails.map(email => (
  <EmailRow key={email.id} email={email} /> // Tied to its object by the id
))}
```

With stable keys, step 7 changes completely: React reconciles DOM nodes against array items by ID. When a new item prepends to the collection, React moves the existing DOM node downward to keep it paired with the flash sale email. The checkmark travels safely with its original item, and a brand new unselected DOM node mounts at the top for the lunch invitation.

```chain caption="After a new object arrives at the top of the emails array: where the ticked DOM element goes, and what Delete selected sends."
!no key: matched by position -> the first DOM element, ticked, shows the first object, Lunch on Friday? -> the form sends 4: the wrong email
+`key={email.id}`: matched by id -> the ticked DOM element keeps 🔥 FLASH SALE: Extra 15% off, now second -> the form sends 1: the right email
```

| !the DOM element holds a tick or typed text | fine | the tick stays in its DOM element, and the objects of the array move past it |

### Why does React never read the key inside the row?

React inspects keys on the immediate elements contained within the array it is diffing, and that array holds `<EmailRow>` descriptors. The child component is a black box during list diffing; its internal `<div>` is not a member of the mapped array. Putting a key inside `EmailRow` is like writing a mailing address on the inside of a letter before sealing the envelope: the postal service never sees it. When wrapping row items in structural tags like `<li>`, the key must always move to the outermost mapped tag.

```jsx title="EmailList.jsx" good="3"
<ul className="emails">

    <li key={email.id}> {/* The tag map() returns: the key goes here */}
      <EmailRow email={email} />
    </li>
  ))}
</ul>
```

### Can the row read its own key?

React reserves `key` exclusively for internal reconciliation; it is never forwarded into component props. A child component attempting to access `props.key` receives `undefined` and triggers a console warning.

```devconsole caption="Chrome's Console, when EmailRow reads its key as a prop."
x EmailRow: `key` is not a prop. Trying to access it will result in `undefined` being returned.
```

If a child component needs the ID value for business logic, you must pass it explicitly under a distinct prop name, such as `<EmailRow key={email.id} id={email.id} />`.

### A key hidden inside a spread object

> [!FACT] A **prop spread** `{...props}` on a JSX tag forwards every property of an object as individual attributes.

A key can also be unintentionally obscured by spreading an object onto a tag. This occurs when developers assemble prop bundles ahead of time and include the key property inside the bundle.

```jsx title="EmailList.jsx" bad="2-3"
{emails.map(email => {
  const props = { key: email.id, email: email }; // **PROBLEMATIC:** the key inside the object
  return <EmailRow {...props} />;
})}
```

While earlier versions of React extracted keys from spreads, modern React warns: "A props object containing a "key" prop is being spread into JSX". The senior standard is explicit: write the `key` directly on the JSX tag, and spread only business props.

### A key on a Fragment

> [!FACT] The short fragment syntax `<>` and `</>` groups sibling tags without adding extra nodes to the DOM, but it cannot accept attributes. The formal `<Fragment>` component imported from `'react'` accepts a `key`.

When mapping data where each item requires multiple sibling elements without a wrapper container, wrap each iteration in `<Fragment key={...}>`.

```jsx title="EmailList.jsx" good="2"
{emails.map(email => (
  <Fragment key={email.id}> {/* Several tags per item: the key goes here */}
    <h3>{email.subject}</h3>
    <p>{email.from}</p>
  </Fragment>
))}
```

```tree dir=right caption="The places a key can be written, and what each gives."

- +key on <Fragment key>, the long form | when each item is several tags; <> takes no key
```

## Putting the four together

We assemble all four principles into a production-grade folder component. It filters emails by folder category, projects them into rows using `map()`, mounts each item inside an `<li>` container carrying the persistent key, and displays a clean fallback message when no emails match. The parent renders both folders inside a unified form.

**DO THIS:**

```jsx right
import { emails } from '../emails.js';
import EmailRow from './EmailRow.jsx';

export default function EmailList({ folder }) {
  const shown = emails.filter(email => email.folder === folder);
  const rows = shown.map(email => (
    <li key={email.id}>
      <EmailRow email={email} />
    </li>
  ));
  return (
    <section>
      <h2>{folder}</h2>
      {shown.length > 0 ? <ul>{rows}</ul> : <p>No emails here.</p>}
    </section>
  );
}
```

Here is the exact same component plagued by the two classic junior defects: using `key={index}` which corrupts form state on data mutation (line 7), and using bare length conditional rendering which prints a stray `0` in empty folders (line 14).

**DO NOT DO THIS:**


## For the interview

- **How do you render a list from an array in React?** Store data in an array of objects and call `.map()` within JSX expressions. The callback returns a React element descriptor for each record. To render a subset, chain `.filter()` prior to `.map()`. When collections may be empty, guard with a ternary `collection.length > 0 ? elements : <EmptyState />` rather than a bare logical AND.
- **Why does React require keys on list items?** JavaScript data arrays and browser DOM nodes are two separate entities. When array data changes, React's reconciler must determine which existing DOM nodes to update, move, or remove. Stable keys provide persistent identity across renders, preventing form state corruption and avoiding full DOM teardowns.
- **When is `key={index}` acceptable, and why is it dangerous?** Array indices are safe only when three strict conditions are met: the list is completely static, items are never filtered or sorted, and items never contain local state like inputs or selection checkboxes. In all dynamic lists, index keys cause catastrophic state desynchronization because indices change whenever items prepend or delete.
- **Why is `key={Math.random()}` considered an anti-pattern?** Generating keys during render produces new IDs on every render cycle. React fails to match any existing element, unmounts every single DOM node, wipes out user focus and form input, and destroys rendering performance.
- **Do keys need to be globally unique across the entire page?** No. Keys must be unique only among immediate siblings within the same array mapping. Two separate lists can safely share the same underlying IDs.
- **Can a child component access its own `key` via props?** No. React reserves `key` for internal reconciler mechanics and strips it from `props`. Accessing `props.key` yields `undefined` with a console warning. Pass the identifier as a custom prop like `id={item.id}` if the child requires it.
- **Where exactly must the key prop be placed?** Always on the outermost JSX tag returned directly by the `.map()` callback. If rows are wrapped in `<li>` or `<Fragment>`, the key belongs on that wrapper tag, never on a nested child element.
- **Why does `{items.length && <List />}` render a 0 when empty?** JavaScript's `&&` operator short-circuits on falsy values and returns `0`. Because React treats numbers as valid printable content, it renders a literal `0` into the DOM. Always use `items.length > 0` with a ternary.

## Where you will meet this

- Every data-driven UI feature across the web: feeds, comments, search results, shopping carts, and tables.
- Server-side data fetching: API records always arrive with unique database IDs that serve as natural list keys. When generating client-side records, assign unique IDs at creation time using `crypto.randomUUID()`, never inside render functions.
- Interactive list items containing form inputs, checkboxes, accordions, or animations: omitting stable keys in these components causes immediate, visible UI glitches upon reordering.
- React reconciler diagnostics: console warnings identify the exact parent component whose mapping function is missing keys.

```hierarchy layout=stack caption="The components of this lecture, one file each, and what each holds or receives."
The CHILD (`EmailList`) filters the data collection by `folder` and maps the results into `<li>` elements keyed by `email.id`.
The GRANDCHILD (`EmailRow`) receives one `email` object and renders the row DOM elements containing the selection checkbox.
The data source (`emails.js`) stores the records in a flat array, keeping data independent from component presentation.
```
