# React Rendering Lists

## Two different ways to render one row per email

A mail app shows many emails, and each one appears as a row with the same parts: a tick box, the sender, and the subject. Only the data differs from row to row. There are two ways to get one row per email:

```tree caption="Two ways to get one row per email: write each tag by hand, or draw the rows from the array."
Two different ways to render one row per email
- Fixed: written by hand | one tag per email, typed into the JSX
- Dynamic: rendering a list from an **array** | one tag, repeated for every email in the array
```

> [!FACT] An array keeps its values in order and counts them from 0. In `emails`, an array of email objects, `emails[0]` is the first email, `emails[1]` the second, and `emails[2]` the third.

We compare the two ways inside a component's `return`. `EmailRow` draws one row from the email it receives. With three emails in `emails`, both ways show the same three rows. Then a new email, "Lunch on Friday?", arrives at the top of the array, where a mail app puts new mail. Compare the two inboxes:

::: row caption="A fourth email arrives at the top of the array. Compare the two inboxes."
::: col title="Fixed: written by hand" tone=bad
```mail size=mini
email: Sara Kim | Lunch on Friday? | | unread
email: Bob Smith | Invoice for March | | unread
email: Anna Lee | Team meeting moved
line: Photos from the trip is missing | bad
```
```jsx
<form>
  <EmailRow email={emails[0]} /> {/* One tag per email */}
  <EmailRow email={emails[1]} />
  <EmailRow email={emails[2]} />
</form>
```
With four emails in the array, the page still shows three rows: the first three. "Photos from the trip" is gone from the inbox until someone adds a fourth tag.
:::
::: col title="Dynamic: from the array" tone=good
```mail size=mini
email: Sara Kim | Lunch on Friday? | | unread good
email: Bob Smith | Invoice for March | | unread
email: Anna Lee | Team meeting moved
email: Mom | Photos from the trip
```
```jsx
<form>
  {emails.map(email => ( /* One tag for every email */
    <EmailRow email={email} />
  ))}
</form>
```
With four emails in the array, the page shows four rows, from one tag. Principle 1 explains how `map()` works.
:::
:::

Why does the difference matter? By hand, the component must know how many emails exist and in what order, so every new email is a change to the code. From the array, a new email is one more object in the data, with no change to any component. The same component can also show only the emails it is asked for, such as the emails of one folder, as Principle 2 shows. So by hand fits only a few items that never change, such as two links in a footer. Every list that comes from data is drawn from the data.

> [!FACT] Each JSX tag, such as `<EmailRow />`, makes a React element: React's description of what to show, not yet the row on the page. From each element, React builds the real row on the page.

Drawing the rows from the array is **rendering a list**. An array of data becomes an array of elements, one per item, and React shows them in order. Each element also gets a key, which keeps each row with its own email when the list changes.

## Rendering a list: four steps in two pairs

Rendering a list takes four steps, in two pairs. The first pair creates the rows from the array. The second updates the rows correctly when the list changes, so each row stays with its own email:

```tree caption="The four steps of rendering a list: first create the rows, then update them correctly when the list changes."
Dynamic: rendering a list from an array
- Create the rows | from the array to the page
  - Rows for every email | `map()`
  - Rows for only some emails | `filter()`, then `map()`
- Update the rows when the list changes | each row stays with its email
  - Key from the email's id | not from its position
  - Key on the tag `map()` returns | not inside the row
```

We take the steps in this order because each one needs the one before it. `map()` comes first, because every later step works on the array it gives back. `filter()` runs before `map()`, so it needs `map()` in hand. The key names the elements that `map()` makes, so it comes after them. Where the key goes makes sense only once we know what the key does.

# Principles

## 1. Rows for every email: map()

*How? `map()` gives back one element per email, in a new array*

```tree size=mini here="Rows for every email"
Dynamic: rendering a list from an array
- Create the rows
  - Rows for every email
  - Rows for only some emails
- Update the rows when the list changes
  - Key from the email's id
  - Key on the tag `map()` returns
```

> [!FACT] An **arrow function** is a short way to write a function: the parameter, then `=>`, then what it gives back. `email => email.subject` takes an email and gives back its subject.

> [!FACT] **`forEach()`** calls a function once for each item of an array and gives back `undefined`. **`map()`** calls a function once for each item and collects what the function gives back into a new array, with one entry per item. It passes each item to the function as its parameter: in `email => ...`, the name `email`, which we choose, holds the first email on the first call, the second email on the second, and so on.

> [!PRINCIPLE]
> **Principle 1: Rows for every email: `map()`**
>
> To show one element per item, we call `map()` on the array inside the JSX.
>
> The arrow function can give back the element directly, inside parentheses `( )`. Or it can use curly braces `{ }`, and then it needs an explicit `return`. Notice: a missing `return` is easy to overlook.
>
> *We should do this:*
>
> ```jsx
> function EmailList() {
>   return (
>     <form>
>       {emails.map(email => ( /* Parentheses: the row is given back */
>         <EmailRow email={email} />
>       ))}
>     </form>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function EmailList() {
>   return (
>     <form>
>       {emails.map(email => { // **PROBLEMATIC:** curly braces open a body with no return
>         <EmailRow email={email} />; // Never given back: no row
>       })}
>     </form>
>   );
> }
> ```

### Example: let's open curly braces after the arrow (every call gives back undefined!)

Here, curly braces after the arrow make every call of the function give back `undefined`, so no row appears. Nothing warns us: the inbox is empty, and the Console shows no message. A developer often adds the braces to make room for a second line later, and the rows vanish with no clue.

We want one row per email. The emails live in their own file, `emails.js`, as one array of objects. Each object has an `id`, a number that belongs to that email and to no other, then its sender, its subject, and its folder:

```js title="emails.js"
export const emails = [ // One object per email
  { id: 1, from: 'Bob Smith', subject: 'Invoice for March', folder: 'Inbox' },
  { id: 2, from: 'Anna Lee', subject: 'Team meeting moved', folder: 'Inbox' },
  { id: 3, from: 'Mom', subject: 'Photos from the trip', folder: 'Inbox' },
];
```

The parent, `EmailList.jsx`, imports the array and places one row per email. The child, `EmailRow.jsx`, draws one row: a tick box, the sender, and the subject. Both live in `src/components/`, so `EmailList` imports the array from one folder up. A `for` loop cannot go inside JSX braces, because it is a statement, and braces take only an expression. So we call `map()`, and open curly braces after the arrow:

```jsx title="EmailList.jsx" bad="7-9" role=PARENT
import { emails } from '../emails.js'; // The data, one folder up
import EmailRow from './EmailRow.jsx';

export default function EmailList() {
  return (
    <form>
      {emails.map(email => { // **PROBLEMATIC:** curly braces open a body with no return
        <EmailRow email={email} />;
      })}
    </form>
  );
}
```

```jsx title="EmailRow.jsx" role=CHILD
export default function EmailRow({ email }) {
  return (
    <label className="row">
      <input type="checkbox" name="delete" value={email.id} /> {/* A tick box per row */}
      <span className="from">{email.from}</span>
      <span className="subject">{email.subject}</span>
    </label>
  );
}
```

### Why does every call give back `undefined`?

> [!FACT] When a curly brace follows `=>`, the function has a **block body**: it gives back only what a `return` inside it names, and without `return` it gives back `undefined`. With parentheses, or nothing, after `=>`, the function gives back that expression by itself.

`map()` collects what the function gives back for each email, and the bracket after the arrow decides what that is. With parentheses, the arrow function gives back the element. With curly braces and no `return`, it gives back `undefined`. `forEach()` fails too, for another reason: it gives back `undefined` whatever its function does. What each version gives back for the three emails, and so what the page shows:

```chain caption="What each version gives back for the three emails, and so what the page shows."
!`emails.forEach(...)` -> `undefined` -> nothing to place: no rows
!`emails.map(email => { <EmailRow />; })` -> `[undefined, undefined, undefined]` -> no rows
+`emails.map(email => <EmailRow />)` -> `[<EmailRow>, <EmailRow>, <EmailRow>]` -> three rows
```

We write the parentheses in `EmailList.jsx`, so the arrow gives back each row:

```jsx title="EmailList.jsx" good="7-9" role=PARENT
import { emails } from '../emails.js';
import EmailRow from './EmailRow.jsx';

export default function EmailList() {
  return (
    <form>
      {emails.map(email => ( /* Parentheses: the row is given back */
        <EmailRow email={email} />
      ))}
    </form>
  );
}
```

Writing `return <EmailRow email={email} />;` inside curly braces works the same way. With a fourth email in `emails.js`, this same line gives four rows.

### What turns an array into elements

With all the ways tried inside the JSX braces side by side:

```tree dir=right caption="Every way tried inside JSX braces to turn an array into elements, and what each gives back."
What gives back one element per item?

## 2. Rows for only some emails: filter(), then map()

*When? A folder shows only its own emails, and a folder can have none*

```tree size=mini here="Rows for only some emails"
Dynamic: rendering a list from an array
- Create the rows
  - Rows for every email
  - Rows for only some emails
- Update the rows when the list changes
  - Key from the email's id
  - Key on the tag `map()` returns
```

> [!FACT] **`filter()`** calls a function for each item and gives back a new array of only the items for which the function gave back `true`. An array's **`length`** is its number of items; an empty array has a length of `0`.

> [!PRINCIPLE]
> **Principle 2: Rows for only some emails: `filter()`, then `map()`**
>
> To show only some items, we call `filter()` before `map()`. It keeps only the items that pass a test.
>
> When no item passes, the array is empty, and its length is `0`. Then we show a message, with `length > 0` and the ternary. Notice: a bare `length` on the left of `&&` puts a `0` on the page instead.
>
> *We should do this:*
>
> ```jsx
> function EmailList({ folder }) {
>   const shown = emails.filter(email => email.folder === folder);
>   const rows = shown.map(email => <EmailRow email={email} />);
>   return (
>     <section>
>       <h2>{folder}</h2>
>       {shown.length > 0 ? rows : <p>No emails here.</p>} {/* No emails: the message */}
>     </section>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function EmailList({ folder }) {
>   const shown = emails.filter(email => email.folder === folder);
>   const rows = shown.map(email => <EmailRow email={email} />);
>   return (
>     <section>
>       <h2>{folder}</h2>
>       {shown.length && rows} {/* **PROBLEMATIC:** a bare length shows 0 */}
>     </section>
>   );
> }
> ```

### Example: let's put a bare length left of && (React shows the 0!)

Here, a bare length left of `&&` puts a 0 on the page. For a folder with no emails, `filter()` gives back an empty array, and its length is `0`. `&&` gives back that `0`, and React shows a number as text. Every folder, every search, and every filter can meet an empty list, and the 0 reaches the page with no error.

We want one section per folder, each with only the emails of its own folder, and a message when a folder has none. To keep the example small, the parent, `App.jsx`, places two sections, Inbox and Spam, and passes each its folder. The child, `EmailList.jsx`, keeps the folder's emails with `filter()`, turns them into rows with `map()`, and stores the rows in a variable, `rows`. All three emails are in the Inbox, and none is in Spam. We use `&&`, the usual way to show a piece or nothing:

```jsx title="App.jsx" role=PARENT
import EmailList from './components/EmailList.jsx'; // Our component, from its own file

export default function App() {
  return (
    <main>
      <EmailList folder="Inbox" /> {/* Three emails */}
      <EmailList folder="Spam" /> {/* No email at all */}
    </main>
  );
}
```

```jsx title="EmailList.jsx" bad="10" role=CHILD
import { emails } from '../emails.js';
import EmailRow from './EmailRow.jsx';

export default function EmailList({ folder }) {
  const shown = emails.filter(email => email.folder === folder); // This folder's emails
  const rows = shown.map(email => <EmailRow email={email} />);
  return (
    <section>
      <h2>{folder}</h2>
      {shown.length && rows} {/* **PROBLEMATIC:** a bare length shows 0 */}
    </section>
  );
}
```

`EmailRow.jsx` stays as it was.

### Why does a 0 appear?

> [!FACT] `a && b` gives back `a` when `a` counts as false in a condition, as `0`, `false`, and `null` do, and `b` otherwise. In JSX, React shows nothing for `false` or `null`, but it shows a number as text. A comparison such as `shown.length > 0` always gives a real `true` or `false`, and the ternary `condition ? a : b` gives `a` when the condition is true and `b` otherwise.

`&&` gives back one of its two sides, and React shows whatever it gets back. With the `&&` version and the three emails, what each step gives back for each section:

| section | `filter()` gives back | `shown.length` | `shown.length && rows` gives back | the page shows |
| --- | --- | --- | --- | --- |
| Inbox | three emails | `3` | `rows`, three rows | the three rows |
| !Spam | `[]` | `0` | `0` | a bare 0 |

So the line in the section is `{shown.length > 0 ? rows : <p>No emails here.</p>}`. The comparison gives a real `false` for Spam, and the ternary shows the message. `filter()` runs before `map()`, so `map()` turns only the kept emails into rows.

## 3. Key from the email's id, not its position

*Why? Without a key, React matches rows to emails by order, and a tick stays behind*

```tree size=mini here="Key from the email's id"
Dynamic: rendering a list from an array
- Create the rows
  - Rows for every email
  - Rows for only some emails
- Update the rows when the list changes
  - Key from the email's id
  - Key on the tag `map()` returns
```

> [!FACT] A **key** is an attribute React reserves, written on each element of a list: `key={email.id}`. `map()` also passes each item's position to the function, as a second parameter: `items.map((item, index) => ...)`, where `index` is 0 for the first item; with two parameters, they go in parentheses.

> [!PRINCIPLE]
> **Principle 3: Key from the email's id, not its position**
>
> We give each element a `key`, taken from the item's own id. React then keeps each row with its own item when the list changes.
>
> The array index works only for a list whose positions never change: items are only added or removed at the end, and never sorted or moved. A key made while rendering, such as a random number, never works.
>
> *We should do this:*
>
> ```jsx
> function EmailList() {
>   return (
>     <form>
>       {emails.map(email => (
>         <EmailRow key={email.id} email={email} /> // The row follows its email
>       ))}
>     </form>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function EmailList() {
>   return (
>     <form>
>       {emails.map((email, index) => (
>         <EmailRow key={index} email={email} /> // **PROBLEMATIC:** the index is the position
>       ))}
>     </form>
>   );
> }
> ```

### Example: how to delete the wrong email

Here, a tick we put beside one email ends up beside another, and we delete an email we never read. It happens when a new email arrives at the top of the list while there is no key. The rows look fine without a key, so the key looks like a way to quiet the Console. It is not: without it, React cannot tell which row belongs to which email.

> [!FACT] A checkbox remembers its own tick: the tick lives in the checkbox element on the page. When a form is sent, each ticked box sends its `value`, so a ticked box with `value={email.id}` sends that email's id.

Now the inbox gets a Delete button, so the rows sit in a form that sends the ticked ids to the server. We want to tick "Invoice for March", then press Delete selected and delete that email only. The parent, `EmailList.jsx`, places the rows with no key. The child, `EmailRow.jsx`, holds the tick box. We tick the invoice. Before we press the button, a new email, "Lunch on Friday?", arrives at the top of the array:

```jsx title="EmailList.jsx" bad="9" role=PARENT
import { emails } from '../emails.js';
import EmailRow from './EmailRow.jsx';

export default function EmailList() {
  return (
    <form action="/delete">
      <button>Delete selected</button>
      {emails.map(email => (
        <EmailRow email={email} /> // **PROBLEMATIC:** no key: matched by order
      ))}
    </form>
  );
}
```

```jsx title="EmailRow.jsx" role=CHILD
export default function EmailRow({ email }) {
  return (
    <label className="row">
      <input type="checkbox" name="delete" value={email.id} /> {/* The tick lives here */}
      <span className="from">{email.from}</span>
      <span className="subject">{email.subject}</span>
    </label>
  );
}
```

### Why do we delete the wrong email?

The cause starts with a fact so basic that it is easy to miss:

> [!AHA] What is going on
> 1. **There are two lists.** One is the `emails` array, in our code. The other is the row elements, on the page. React built the rows from the array: one row per email, in the same order.
> 2. **Each list holds its own things.** The array holds each email's sender, subject, and id. A row holds what the reader did in it: the tick.
> 3. **The two orders are separate.** Changing the order of one list does not change the order of the other.
> 4. **A new email arrives at the top of the array.** The array's order changes: "Lunch on Friday?" is now first, and "Invoice for March" moves to second place.
> 5. **The rows on the page do not move by themselves.** React has to decide which row shows which email now.
> 6. **Without a key, React cannot tell which row belongs to which email.** So it matches them by order: the first email goes into the first row, the second email into the second row, and so on.
> 7. **So the first row, the one with our tick, now shows "Lunch on Friday?".** Its text and its `value`, `4`, come from the array, so they change. Its tick belongs to the row, so it stays.
> 8. **Oops: we press Delete selected.** The form sends `4`. "Lunch on Friday?" is deleted before we read it, and "Invoice for March" is still there.
>
> **The text follows the email. The tick stays with the row.**

A key ties each row to one email. We write it on the tag inside `map()`, in `EmailList.jsx`, from the email's own id:

```jsx title="EmailList.jsx" good="2"
{emails.map(email => (
  <EmailRow key={email.id} email={email} /> // Tied to its email by the id
))}
```

With `key={email.id}`, step 6 changes: React matches rows to emails by id, not by order. When the array's order changes, React moves the rows to match it. The ticked row moves down with "Invoice for March", and "Lunch on Friday?" gets a new, empty row at the top:

```chain caption="After the new email arrives at the top: where the ticked row goes, and what Delete selected sends."
!no key: rows matched by order -> the ticked first row takes the first email, Lunch on Friday? -> the form sends 4: the wrong email
+key={email.id}: rows matched by id -> the ticked row keeps Invoice for March, now second -> the form sends 1: the right email
```

### When it breaks

The mistake needs two things at once: the list changes anywhere but the end, and each row holds something of its own, such as a tick or typed text. That is why so many lists seem fine without keys:

| | the list changes only at the end | the list changes at the top or in the middle, or is sorted |
| --- | --- | --- |
| the row holds nothing of its own | fine | fine: nothing can stay behind |
| !the row holds a tick or typed text | fine | the tick stays behind, and the emails slide past it |

### Which key to choose

The four keys side by side:

```tree dir=right caption="The four keys, and what each does after a new email arrives at the top."
Which key?
- +key from the email's id | follows the email: the tick stays beside its email
- !key from the index | is the position: the tick stays at its place when an item is added, removed, or moved above it
- !key from Math.random() | new on every render: every row is rebuilt, the tick is lost
- !no key | matches by order: the tick stays behind the same way, and the Console warns
```

The index fits a list like a fixed row of tabs built from an array that never changes. Adding an item at the end is safe too, since every position stays as it was. But removing an item anywhere else moves every later item up one place, just as adding one at the top moved them down.

## 4. Key on the tag map() returns, not inside the row

*Why? React reads the key only on the elements `map()` gives back*

```tree size=mini here="Key on the tag `map()` returns"
Dynamic: rendering a list from an array
- Create the rows
  - Rows for every email
  - Rows for only some emails
- Update the rows when the list changes
  - Key from the email's id
  - Key on the tag `map()` returns
```

> [!PRINCIPLE]
> **Principle 4: Key on the tag `map()` returns, not inside the row**
>
> We write the `key` directly on the tag that `map()` gives back. That tag is the item of the list React matches.
>
> A key on a tag inside the child component is not an item of the list, so React does not use it, and the warning stays.
>
> *We should do this:*
>
> ```jsx
> function EmailList() {
>   return (
>     <form>
>       {emails.map(email => (
>         <EmailRow key={email.id} email={email} /> // On the tag map() returns
>       ))}
>     </form>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function EmailList() {
>   return (
>     <form>
>       {emails.map(email => (
>         <EmailRow email={email} /> // No key on the tag map() returns
>       ))}
>     </form>
>   );
> }
> function EmailRow({ email }) {
>   return <label key={email.id}>{email.subject}</label>; // **PROBLEMATIC:** inside the child
> }
> ```

### Example: let's move the key onto the `<label>` inside the row (React never reads it!)

Here, a key written on the `<label>` inside the row is never read by React, so the Console's warning stays, and the rows are still matched by order. React reads the key only on the elements `map()` gives back, and those are the `<EmailRow>` elements. The mistake is tempting, because the Elements panel shows the `<label>` tag once per row. So it looks like the tag that repeats, and the place for the key:

```dom title="Elements panel: the inbox with three rows"

*  <label class="row">...</label>
*  <label class="row">...</label>
*  <label class="row">...</label>
</form>

We want the key where React looks for it, so the warning goes. `emails.js` is back to its first three emails, without "Lunch on Friday?". The parent, `EmailList.jsx`, writes `<EmailRow email={email} />` with no key. We move the key onto the `<label>` inside the child, `EmailRow.jsx`:

```jsx title="EmailList.jsx" role=PARENT
import { emails } from '../emails.js';

export default function EmailList() {
  return (

    </form>

}
```

```jsx title="EmailRow.jsx" bad="3" role=CHILD
export default function EmailRow({ email }) {
  return (
    <label key={email.id} className="row"> {/* **PROBLEMATIC:** a key inside the child */}
      <input type="checkbox" name="delete" value={email.id} />

      <span className="subject">{email.subject}</span>

### Why does React never read the key inside the row?

React looks for the key on the items of the array it receives, and that array holds `<EmailRow>` elements. The `<label>` inside a row is not an item of any array, so a key there ties nothing React matches. When `map()` gives back another tag around the row, the key moves to that outer tag. A list is often marked up as a list, so each row sits in an `<li>` inside a `<ul>`, and the key goes on the `<li>`:

```jsx title="EmailList.jsx" good="3"
<ul className="emails">
  {emails.map(email => (
    <li key={email.id}> {/* The tag map() returns: the key goes here */}
      <EmailRow email={email} />
    </li>
  ))}
</ul>
```

### Can the row read its own key?

React keeps the key for itself: the row never receives it as a prop. A row that tries to read it, as in `function EmailRow({ key, email })`, gets `undefined`, and a warning:

```devconsole caption="Chrome's Console, when EmailRow reads its key as a prop."
x EmailRow: `key` is not a prop. Trying to access it will result in `undefined` being returned.
```

Here the row can still read `email.id`, because it receives the whole email. A component that receives only some fields, and needs the id too, gets it as a prop of its own, under another name, such as `<EmailRow key={email.id} emailId={email.id} subject={email.subject} />`.

### A key hidden inside a spread object

> [!FACT] A **spread** `{...props}` on a tag passes every field of the object `props` as its own attribute.

A key can also end up hidden inside an object spread onto the tag. This happens when a row's props are first gathered into one object, key included:

```jsx title="EmailList.jsx" bad="2-3"
{emails.map(email => {
  const props = { key: email.id, email: email }; // **PROBLEMATIC:** the key inside the object
  return <EmailRow {...props} />;
})}
```

React still reads the key from the spread object, but only as a fallback kept for older code, which a future version of React may drop. It warns, "A props object containing a "key" prop is being spread into JSX". So the key comes out of the object and is written directly on the tag, while the other props can still be spread: `const props = { email: email };` then `<EmailRow key={email.id} {...props} />`.

### A key on a Fragment

> [!FACT] `<>` and `</>`, a Fragment, group several tags without adding a tag to the page, but take no attributes. The long form, `<Fragment>`, imported with `import { Fragment } from 'react';`, can take a key.

When each item is several tags with no single tag around them, the key goes on a `Fragment`. This is a different, simpler list, with no row component. With the three emails, it gives each subject followed by its sender, and no warning:

```jsx title="EmailList.jsx" good="2"
{emails.map(email => (
  <Fragment key={email.id}> {/* Several tags per item: the key goes here */}
    <h3>{email.subject}</h3>
    <p>{email.from}</p>
  </Fragment>
))}
```

### Where the key goes

The places a key can be written, side by side:

```tree dir=right caption="The places a key can be written, and what each gives."
Where does the key go?
- +key on the tag map() returns | <EmailRow key>, or <li key> when the row sits in an <li>
- +key on <Fragment key>, the long form | when each item is several tags; <> takes no key
- !key inside the child | the warning stays: the child's <label> is not an array item
- !key inside a spread object | React still reads it for now, but warns: write key on the tag
```

## Putting the four together

We want one folder section that uses all four steps. It keeps the folder's emails with `filter()` and turns them into rows with `map()`. Each row sits in an `<li>` inside a `<ul>`, and the key, from the email's id, is on the `<li>`, the tag `map()` gives back. When the folder has no emails, a ternary on `length > 0` shows a message. `App` places `<EmailList folder="Inbox" />` and `<EmailList folder="Spam" />` inside a form with the Delete selected button. With the three emails, the Inbox shows three rows, and Spam shows "No emails here.":

**DO THIS:**

```jsx right
import { emails } from '../emails.js';
import EmailRow from './EmailRow.jsx';

export default function EmailList({ folder }) {
  const shown = emails.filter(email => email.folder === folder);
  const rows = shown.map(email => (
    <li key={email.id}>
      <EmailRow email={email} />
    </li>
  ));
  return (
    <section>
      <h2>{folder}</h2>
      {shown.length > 0 ? <ul>{rows}</ul> : <p>No emails here.</p>}
    </section>
  );
}
```

Here is the same section with two mistakes, marked in red. It ties each row to its index, so a tick put beside one email stays behind when a new email arrives at the top, and Delete selected deletes the wrong email (line 7). And it puts a bare length left of `&&`, so a folder with no emails, such as Spam, shows a bare 0 instead of a message (line 14):

**DO NOT DO THIS:**

```jsx wrong bad="7,14"
import { emails } from '../emails.js';
import EmailRow from './EmailRow.jsx';

export default function EmailList({ folder }) {
  const shown = emails.filter(email => email.folder === folder);
  const rows = shown.map((email, index) => (
    <li key={index}>
      <EmailRow email={email} />
    </li>
  ));
  return (
    <section>
      <h2>{folder}</h2>
      {shown.length && <ul>{rows}</ul>}
    </section>
  );
}
```

## For the interview

- **How do you render a list from an array?** Keep the data in an array of objects and call `map()` inside the JSX. Its arrow function gives back one element per item, and React shows the array of elements in order. To show only some items, call `filter()` first. When the result can be empty, test its `length` with `> 0` in a ternary: the rows when it is true, a message when it is 0.
- **Why does React need a key?** The array and the elements on the page are two lists with separate orders. When the array changes, React must decide which element now shows which item. With a key, it matches by key. Without one, it matches by order, so what a reader did inside an element, such as a tick or typed text, stays at its place while the items slide past it.
- **Is `key={index}` fine?** Only for a list whose positions never change: no item is ever inserted or removed anywhere but the end, or moved. The index is the position, so it hides the warning, and the tick still stays behind as soon as an item is inserted above it or the list is sorted. Lists whose rows hold nothing of their own hide this bug, which is why many tutorials get away with index keys.
- **Why not `key={Math.random()}`?** It changes on every render, so no key matches the last one: every row is built again from scratch, and every tick or typed text is lost.
- **Must keys be unique on the whole page?** No, only among the items of one array. Two separate lists can use the same ids.
- **Can the child read its key?** No. React keeps the key, so `key` read as a prop is `undefined`, with a warning. When the child needs the id and does not receive the whole item, pass the id again under another name, such as `emailId`.
- **Where does the key go?** On the tag `map()` gives back: on `<EmailRow key>` when `map()` returns the row, on the `<li>` when the row sits in one, and on a `<Fragment key={...}>` when each item is several tags with no tag around them. Never inside the child.
- **Why does an empty list with `length &&` show a 0?** For an empty array, `length` is `0`, and `0 && ...` gives back `0`, which React shows as text. Write `length > 0 ? rows : message`, so an empty list shows the message instead of a 0 or an empty space.

## Where you will meet this

- Every list built from data: emails, comments, search results, cart items. Each comes from an array, goes through `map()`, and takes its key from each item's id.
- Data from a server: each record usually arrives with its own id, ready to be its key. When the data has no id, give each item one once, when it is created, and store it with the item; never while rendering. `crypto.randomUUID()`, a browser function that gives back a new unique string on HTTPS pages and on localhost, can make it.
- Rows that hold input, such as ticks in an inbox, quantities in a cart, or checkboxes in a to-do list: index keys or no keys leave those entries at their places while the items move. This happens when the list is sorted, or an item is added or deleted anywhere but the end.
- A Console warning about keys: it names the component whose `map()` needs the key, so you know which file to open.
