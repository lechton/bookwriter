### A variable lives inside the function that declares it

- [runway] Scope of a variable and `ReferenceError`, used by Question 3 and Step 3.

- [p] ◇ {scope} A variable declared with `const` inside a function exists only while that function runs, and only the code inside that function can see it. This part of the code where a name can be used is called the variable's **scope**. A variable declared at the top level of a file, outside every function, can be seen by every function of that file. ◼ Educational objective: the JavaScript rule Question 3's mistake breaks, before any React is involved.

- [code] Plain JavaScript, a variable another function cannot see:

```js title="Plain JavaScript: a variable stays in its function"
const siteName = 'Town News'; // the whole file sees it
function header() {
  const edition = 'Morning'; // only header sees it
  return siteName + ', ' + edition;
}
function footer() {
  return siteName + ', ' + edition; // edition is not defined
}
```

◼ **The what-this-introduces list:** 1. `siteName` at the top level: a name every function of the file can use. 2. `edition` inside `header`: a name only `header` can use.

- [p] ◇ {point into the code} `header()` gives back "Town News, Morning". `footer()` stops with "edition is not defined": `edition` exists only inside `header`. JavaScript calls this kind of error a **`ReferenceError`**: the code uses a name that does not exist where it is written. `siteName` works in both, because it sits at the top level. ◼ Educational objective: the exact message Question 3 shows, met first in plain JavaScript.

### A tree has a root, branches, and leaves

- [runway] Root, parent, child, sibling, top-level, and leaf, used by Question 1 and every step.

- [p] ◇ {words for a tree} Folders on a computer form a tree: one folder at the top holds others, and they hold more. The same words name any tree. The **root** is the one at the top. Each item is the **parent** of the items directly inside it, and those are its **children**. Children of the same parent are **siblings**. An item near the root is **top-level**, and an item that holds nothing is a **leaf**. ◼ Educational objective: the words the render tree uses, taught on a tree the reader already knows.

### One function, one job

- [runway] Separation of concerns, used by Question 2 and Step 2.

- [p] ◇ {separation of concerns} A long function that does many things is hard to read and hard to change, because every change risks the other things it does. Programmers split it so that each function has one job, and this habit has a name: **separation of concerns**. A function with one job gets a name that says the job, such as `formatDate` or `sendEmail`. ◼ Educational objective: the general programming habit Question 2 applies to components.

### Principles of React: The Page Is a Tree of Components

- [preview] Everything in this lesson comes down to one idea: the page is a tree of components, and React builds it from the root down. First, the render tree, which means each component's markup names its children: App is the root, every component is the parent of the components its markup names, and React calls them branch by branch. Second, component boundaries, which means one branch of the tree for each part of the page with its own job: the header, the feed, and the story each get a component, nested where they sit on the page. Third, data flow, which means a value travels down the tree, never across it: a component cannot read a variable of its parent or of its neighbor, so a value they share starts above them both. ◼ Educational objective: the map's Spoken Preview, word for word, read aloud before Question 1.

### Question 1: React calls the components in the order of the tree

- [question-cycle] Question 1: React calls the components in the order of the tree
    - Question: "I have five components side by side in `App.jsx`. How does React know which goes where?"
    - Code and result: `App.jsx` with six functions, each logging its name, in this file order: `NewsHeader` (returns the masthead), `EditorialByline` (the author line), `ArticleCard` (the headline and `<EditorialByline />`), `MostRead` (the side box), `EditorialFeed` (`<main>` with `<ArticleCard />` and `<MostRead />`), and `App` (a Fragment with `<NewsHeader />` and `<EditorialFeed />`); the page shows the masthead, the story with its byline, and the side box; the Console panel shows "App runs", "NewsHeader runs", "EditorialFeed runs", "ArticleCard runs", "EditorialByline runs", "MostRead runs" (verified in React 19.3.1, Vite 8.3.4, and Chrome).
    - Verdict: the code works as written (Real Mistake none): the page is right, and the console shows the order of the tree, not of the file.
    - Answer: the file starts with `NewsHeader`, but React calls `App` first, because `main.jsx` names `<App />`; `App`'s markup names `NewsHeader` and `EditorialFeed`, so they are `App`'s children; React calls `NewsHeader`, which names no component, so it is a leaf; then `EditorialFeed`, whose markup names `ArticleCard` and `MostRead`; React finishes the whole `ArticleCard` branch, its child `EditorialByline` included, before it calls `MostRead`; this shape is the **render tree**: `App` at the root, top-level components under it, leaves at the ends; React keeps it as real data, and React Developer Tools draws it in its Components tab, which Lecture 64 uses; the render tree holds only components, while the Elements panel shows only the tags they return, `<header>`, `<main>`, `<article>`, `<p>`, `<aside>`, and no `NewsHeader`; a component named twice is two places in the tree, so `<ArticleCard />` written twice prints "ArticleCard runs" twice; a tree can change from one render to the next when a parent chooses its children, which Lecture 10 teaches; files that import each other form another tree, which Lecture 8 shows.
    - Fix: none needed.
    - Rule: we read the components a component's markup names as its children: `App` is the root, each component is the parent of the ones it names, and React calls them from the root down, finishing one branch before the next.
    - Needs: tree words (runway "A tree has a root, branches, and leaves"); React calls a tag's component and the Console panel (recall Lecture 2); Fragment (recall Lecture 3).
    - Window plan: the whole file, its first appearance, as a chain: lines 1 to 8, `NewsHeader` and `EditorialByline` (`startLine="1" continues="bottom"`); lines 9 to 17, `ArticleCard` (`startLine="9" continues="both"`); lines 18 to 21, `MostRead` (`startLine="18" continues="both"`); lines 22 to 30, `EditorialFeed` (`startLine="22" continues="both"`); lines 31 to 39, `App` (`startLine="31" continues="top"`).
    - Diagram: the render tree as an ASCII tree, `App` at the top, with the six calls numbered in the order of the console.

> [!PRINCIPLE] Principle 1: The render tree: each component's markup names its children. Rule word for word; a model card (Real Mistake none), so only the right example: John Hall's profile page, `ProfilePage` returning `<ProfileHeader />` and `<ContactList />` in a Fragment, with comments that name them the first and the second child.

### Question 2: One long App shows the same page

- [question-cycle] Question 2: One long App shows the same page
    - Question: "My `App` now holds the whole front page. Should I cut it up, and where?"
    - Code and result: the same front page written as one `App` that returns the masthead, the story with its byline, and the side box in one block; the Elements panel shows exactly the DOM of Question 1's tree (verified in React 19.3.1 and Chrome).
    - Verdict: the code works as written: React builds the same page from one function or from six.
    - Answer: the page alone cannot tell the two files apart, so the reason to cut is the code, not the screen; one long `App` does five jobs at once, and every change to the byline means reading the masthead and the side box too; react.dev's Thinking in React starts every app the same way: draw a box around each part of the page and name it; **separation of concerns** gives the rule: each part with its own job gets its own component, nested where it sits on the page, so the tree of components matches the page: the masthead in `NewsHeader`, the list of stories in `EditorialFeed`, one story in `ArticleCard`, the author line in `EditorialByline`, the side box in `MostRead`; a part gets a component for its job even when it appears once; a tag that is only part of a job stays in its parent: the story's `<h2>` stays in `ArticleCard`, as react.dev keeps a table's header inside the table until it grows a job of its own; the cost of one long `App` shows in Lecture 6, when each part needs its own data.
    - Fix: none needed; the answer shows the cut as Question 1's tree.
    - Rule: we give each part of the page with its own job its own component, nested where the part sits on the page, and we keep a small piece inside its parent until it grows a job of its own.
    - Needs: separation of concerns (runway "One function, one job"); the render tree (Question 1).
    - Window plan: one long `App` in a chain of two windows, lines 1 to 8 (`startLine="1" continues="bottom"`) and lines 9 to 14 (`startLine="9" continues="top"`); then the Elements panel, which matches Question 1's.
    - Diagram: the front page with a box drawn around each part, each box labeled with its component.

> [!PRINCIPLE] Principle 2: Component boundaries: one branch of the tree for each part of the page with its own job. Rule word for word; a decision with Real Mistake none, so only the right example: John Hall's profile page cut into `ProfileHeader` (his name and photo) and `ContactList` (his email and phone), each nested where it sits.

### Question 3: A child cannot read its parent's variable

- [question-cycle] Question 3: A child cannot read its parent's variable
    - Question: "`ArticleCard` needs the edition that `App` declares. Can it just read it?"
    - Code and result: `App` declares `const edition = 'Morning'` and returns `<main><ArticleCard /></main>`; `ArticleCard` returns `<h2>{edition} edition</h2>`; the page goes empty, and the Console panel shows "edition is not defined" and a note that suggests an error boundary (verified in React 19.3.1 and Chrome).
    - Verdict: does not do what the reader wanted.
    - Answer: `<ArticleCard />` sits inside `App`'s markup, but a tag is not code: it only tells React to call `ArticleCard`; the function `ArticleCard` is defined at the top level of the file, so, as in the runway, it sees only its own variables and the file's; `edition` lives inside `App`, so React's call of `ArticleCard` throws a `ReferenceError`, and with nothing to catch it the page goes empty; a sibling fails the same way: `EditorialFeed` cannot read a variable of `NewsHeader`; the plain JavaScript habit fails too: `NewsHeader` reading `document.getElementById('edition').textContent` finds `null` and throws "Cannot read properties of null (reading 'textContent')", because no part of the page exists yet while React calls the components (Lecture 15 shows why); the tempting fix, defining `ArticleCard` inside `App`, makes it work, and brings back Lecture 2's bug; so a value travels only one way: it starts above every component that needs it and goes down the tree; a fixed value the whole file needs can sit at the top level of the file; a value that belongs to the page starts in the closest common parent and is handed down, which Lecture 6 does with props.
    - Fix: `const edition = 'Morning';` at the top level of the file; `ArticleCard` shows "Morning edition".
    - Rule: we start a value that several components need above all of them and let it travel down the tree; a component never reads a variable of its parent or of its neighbor, and never reads another component's text from the page.
    - Needs: scope and `ReferenceError` (runway "A variable lives inside the function that declares it"); top level of a file and the nested definition (recall Lecture 2); `getElementById` and `textContent` (recall Lecture 1); curly braces (recall Lecture 4); the render tree (Question 1).
    - Diagram: the tree with an arrow that goes down from the top of the file to `ArticleCard`, and a crossed arrow from `App`'s variable into `ArticleCard`.

> [!PRINCIPLE] Principle 3: Data flow: a value travels down the tree, never across it. Right: `const ownerName = 'John Hall';` at the top level, read by `ProfileHeader` and `ContactList`; wrong: `ownerName` declared inside `ProfilePage` and read in `ContactList` ("ownerName is not defined"); verified on the same pattern.

- [grounding] Is the render tree the same as the tree of my files? ◼ Friction target: the map's Preview row on the module dependency tree. Tactile scene: Lecture 8 will move each component into its own file, and the files will import each other; a reader expects the two trees to match. Bold key terms: **module dependency tree**, **bundler**. Concrete operational resolution: the files form a second tree, made by `import` lines, and the build tool uses it to decide which code ships; the two trees can differ, because a component can render a child it does not import, which Lecture 7 shows with `children`. ◼ Educational objective: one `> [!WILD]` card after the principles, adding a fact the cycles did not state.

### Step 1: First, we add the menu and the footer to the tree <App.jsx>

- [p] ★ The render tree. Decision: the menu is part of the masthead, so `MainMenu` is a child of `NewsHeader`; the footer is a part of the whole page, beside the header and the feed, so `SiteFooter` is a child of `App`, after `EditorialFeed`. Prediction, before saving: where do "MainMenu runs" and "SiteFooter runs" appear in the console? Result: "App runs", "NewsHeader runs", "MainMenu runs", "EditorialFeed runs", "ArticleCard runs", "EditorialByline runs", "MostRead runs", "SiteFooter runs": the menu right after its parent, because React finishes the header's branch first, and the footer last (verified). ◼ Meaningful pedagogical commentary: the reader places two new nodes and predicts the order from the tree alone.

- [code] four windows at their real line numbers in the 53-line file: lines 1 to 4, the new `MainMenu` (`startLine="1"`); lines 5 to 13, `NewsHeader` with `<MainMenu />` (`startLine="5"`); lines 40 to 43, the new `SiteFooter` (`startLine="40"`); lines 46 to 52, `App`'s `return` with `<SiteFooter />` (`startLine="46"`). The four lines of `MainMenu` push every component below them down.

### Step 2: Next, we give the sign-up its own component <App.jsx>

- [p] ★ Component boundaries. Decision: the "Most read" box grows a list of three headlines; each `<li>` is only part of the box's job, so the list stays inside `MostRead`; the footer gains a newsletter sign-up, a part with its own job, so it gets its own component, `NewsletterBox`, nested in `SiteFooter`. Result: the page shows the list and "Get the morning edition by email."; the console ends with "SiteFooter runs" and "NewsletterBox runs", one new leaf; `MostRead` still prints once (verified). ◼ Meaningful pedagogical commentary: one piece stays, one piece leaves, and the reason is the job, not the size.

- [code] three windows at their real line numbers in the 71-line file: lines 29 to 38, `MostRead`'s `return` with the list (`startLine="29"`); lines 49 to 52, the new `NewsletterBox` (`startLine="49"`); lines 53 to 61, `SiteFooter` with `<NewsletterBox />` (`startLine="53"`).

### Step 3: Finally, we send the edition down to both ends of the tree <App.jsx>

- [p] ★ Data flow. Decision: the edition must show in the masthead and in the sign-up, two ends of the tree; declaring it inside `NewsHeader` would leave `NewsletterBox` without it; the edition is fixed for the whole page, so it goes to the top level of the file, above every component. Prediction: what happens if it stays inside `NewsHeader`? Result: "Town News, Morning edition" and "Get the Morning edition by email." (verified). When the edition changes from page to page, it will start in `App` and travel down as a prop, which Lecture 6 teaches. ◼ Meaningful pedagogical commentary: the shared value finds the one place both branches can reach.
