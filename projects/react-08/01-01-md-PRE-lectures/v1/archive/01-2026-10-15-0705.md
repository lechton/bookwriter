### Plain JavaScript is imperative, React is declarative

- [p] ◇ {theme} Every website shows values that change (a name after a profile edit, a cart count, a temperature). When a value changes, the page must show it everywhere it appears. The question every web developer meets: when a value changes, how does the page change with it? ◼ Educational objective: bird's-eye view; the theme from the map's Theme and Options, from pages the reader knows.

- [p] ◇ {HTML and the DOM, named first} The browser does not show the HTML file directly: it builds an object in memory for every tag and draws the screen from them, the **DOM** (Document Object Model). HTML is the text we write; the DOM is what the browser builds and keeps. Changing the page means updating the DOM. ◼ Educational objective: the HTML and DOM pair an interviewer expects, named before the ways use it (`lecture-voice` Section 22).

- [p] ◇ {categories: the count} There are two ways to update the DOM when a value changes. ◼ Educational objective: categorical clarity; the count comes first.

- [p] ◇ {way 1: imperative programming, plain JavaScript} The first way is **imperative programming**, which the reader knows from plain JavaScript: give the browser commands; find the element, then set its text. ◼ Educational objective: the habit without React, named by its exact term (React offers no rival way, so this is the first option).

- [code] Imperative: find the element, set its text:

```js title="Imperative: find the element, set its text"
const greeting = document.getElementById('greeting'); // find it
greeting.textContent = 'Welcome back, Elena Ruiz'; // set its text
```

- [p] ◇ {way 1: point into the code, when it fits} The first line asks the browser for the element whose `id` is `greeting`; the second replaces its text; nothing else on the page changes. That is why it is called imperative programming; origin: Latin *imperare*, "to command", the root of *emperor*: like an emperor, the code orders every step. It fits when one element changes in one place (a clock in a corner); it fits badly when the same value appears in many places: the badge needs its own two lines, and if they are forgotten the badge keeps the old name. ◼ Educational objective: a fair account of the first way, pointing into each line, with the term's origin.

- [p] ◇ {way 2: declarative programming, this chapter} The second way is **declarative programming**, which this chapter teaches: instead of commands, declare what the element should show. ◼ Educational objective: the chapter's way, named by its exact term.

- [code] Declarative: what the greeting shows:

```jsx title="Declarative: what the greeting shows"
<p>Welcome back, {readerName}</p>
```

- [p] ◇ {way 2: point into the code} It looks like HTML, but `{readerName}` is new: the curly braces mark a place where a JavaScript value goes (Lecture 4). No line finds the `<p>` and no line sets its text; React reads the description, builds the `<p>`, and puts the current value in it. That is why it is called declarative programming: we declare the result, and React updates the DOM to match; origin: Latin *declarare*, "to make clear, to announce". ◼ Educational objective: the place, what fills it, who acts, the contrast with the commands above, and the term's origin.

- [code] Declarative: what the badge shows:

```jsx title="Declarative: what the badge shows"
<span>Subscriber: {readerName}</span>
```

- [p] ◇ {way 2: second tiny example} The greeting and the badge read the same `readerName`; there is no second command to forget, so the two places cannot show different names. ◼ Educational objective: confirm the idea with a second element.

- [ways] Two ways to update the DOM when a value changes ◼ (1) Update the DOM with **imperative programming** (plain JavaScript): you give the browser every command yourself, finding each element and setting its text. (2) Update the DOM with **declarative programming** (this chapter): you declare what each element should show, and React updates the DOM to match. ◼ Educational objective: the `> [!WAYS]` reminder, repeating the frame "Update the DOM with", each line with the exact term in bold and its plain meaning.

- [p] ◇ {later: refs} React still lets you reach one element directly for the few jobs declarative code cannot do, such as moving the cursor into a search box (Lecture 30). ◼ Educational objective: the senior's caveat, one sentence with its lecture.

- [p] ◇ {this chapter's way} React is a JavaScript library for building pages out of components. In this chapter we write the first one, `SiteHeader`, which describes the whole header from `readerName`; the path: why imperative code misses an element, why a value lives in one variable, what React changes when the value changes, and the two ways compared at the end. ◼ Educational objective: say what React is and where the chapter goes.

- [p] ◇ {book structure} The name stays fixed in this lesson. Lecture 14 changes a value while the page is open, Lecture 15 follows the update; Lecture 5 splits the page into components, Lecture 6 passes values between them, Lecture 12 says a component only describes. ◼ Educational objective: place the lesson in the book; each later lesson in a few words.

- [p] ◇ {questions} This lesson answers three questions: **In plain JavaScript I find each element and change its text. What do I write instead in React?** **The name shows in two places. Do I write it twice?** **When the name changes, does React rebuild the whole header and wipe what the reader typed?** ◼ Educational objective: the map's reader questions, in the reader's words.

### The browser keeps the page as a tree of objects

- [runway] The DOM and the three plain JavaScript tools, used by Questions 1 and 3.

- [p] ◇ {runway: the DOM} The DOM from the opening is a tree: its objects nest the way the tags nest in the HTML file, and each object is a **DOM node**. The screen is drawn from the DOM, so changing a node changes the page. ◼ Educational objective: ground the DOM before the questions use it.

- [code] Three plain JavaScript tools:

```js title="Three plain JavaScript tools"
const greeting = document.getElementById('greeting'); // find one node
greeting.textContent = 'Welcome back, Elena'; // replace its text
const header = document.getElementById('header');
header.innerHTML = '<p>Welcome back, Elena</p>'; // replace all inside
```

- [p] ◇ {runway: point into the code} `document.getElementById` finds the node with that `id`; `textContent` replaces the text inside one node; `innerHTML` throws away every node inside the element and builds new nodes from the string. ◼ Educational objective: teach the forms; the consequence for a typed search box is left to Question 3.

### A component is a function that returns a description

- [runway] The component, JSX, `export default`, and `className`, used by Questions 1, 2, and 3.

- [p] ◇ {runway: the component} A **component** is a JavaScript function whose name starts with a capital letter and which returns markup (Lecture 2 gives the rules). ◼ Educational objective: name it, then show it.

- [code] SiteHeader returns a description:

```jsx title="SiteHeader returns a description"
export default function SiteHeader() {
  const readerName = 'Elena'; // the name, stored once
  return (
    <header className="site-header">
      <p>Welcome back, {readerName}</p>
      <span>Subscriber: {readerName}</span>
    </header>
  );
}
```

- [p] ◇ {runway: the parts of the component} `export default` lets another file use the function (Lecture 8); `readerName` holds the name; the returned markup is **JSX**, JavaScript and not HTML, so `class` is written `className` (Lecture 3). ◼ Educational objective: point into every new form the questions reuse.

- [p] ◇ {runway: who acts} Our code never calls `SiteHeader` and never touches the DOM; React calls it, reads the description, and builds the nodes inside one element of the page that we hand to it (Lecture 9). A component returns what the page should show, and React builds the page from it. ◼ Educational objective: who does what, and the closing rule.

### Principles of React: Declarative Synchronization

- [question-cycle] Question 1: Finding elements by identifier misses unqueried widgets
    - Question: "In plain JavaScript I find each element by its id and change its text. What do I write instead in React?"
    - Code and result: `updateHeaderUser('Elena Ruiz')` sets the greeting by id and forgets the badge; the greeting updates to "Welcome back, Elena Ruiz" while the badge keeps "Subscriber: Elena" (verified in jsdom 30.1.2).
    - Verdict: does not do what the reader wanted.
    - Answer: plain JavaScript requires finding every element by hand; missing one element leaves stale data on screen; in React we write a component function `SiteHeader` that returns markup describing the header from `readerName`; React calls the function and builds the DOM from what it returns; both the greeting and the badge show "Elena", with zero DOM queries in our code.
    - Fix: `SiteHeader` returning the header markup from `readerName`. The component and JSX forms are taught in the runway section "A component describes the interface in JSX from data".
    - Rule: describe what the page shows for the data instead of finding and mutating elements by hand. Boundary: Question 2 (`one-value-every-place`) addresses keeping the value in one variable when multiple places show it.

> [!PRINCIPLE]
> **Principle 1: Describe what the page shows for the data instead of changing elements by hand**
> In plain JavaScript, code searches the document for each element and changes its text directly. If an update misses one element, the screen shows old data. In React, a component function returns a description of the markup for the current data, and React builds the page from that description. We describe what the interface shows instead of writing commands to find and change elements.
>
> *We should do this:*
> `function Header() {`
> `  const name = 'Elena';`
> `  return <h1>Welcome, {name}</h1>; // React builds element`
> `}`
>
> *We should not do this:*
> `function updateHeader(name) {`
> `  const el = document.getElementById('name');`
> `  if (el) el.textContent = name; // misses unqueried elements`
> `}`

- [p] ★ In our `SiteHeader` example, writing plain JavaScript required `updateHeaderUser` to search for `greeting` and `badge` by their string identifiers. Forgetting `badge` left the screen showing "Elena" in the badge alongside "Elena Ruiz" in the greeting. In React, we write `SiteHeader` as a function that returns the complete header markup. React calls `SiteHeader`, reads the returned description, and constructs the DOM elements on the screen. Because our code never queries the DOM, no element can be skipped or left behind. ◼ Educational objective: prove Principle 1 on the lesson's code, demonstrating how component descriptions eliminate manual element hunting.

- [question-cycle] Question 2: The name shows in two places across the header
    - Question: "The reader's name shows in the greeting and in the badge. Do I write it in both places?"
    - Code and result: `SiteHeader` with the badge text typed in by hand as `Subscriber: Elena`; after `readerName` changes to `'Elena Ruiz'`, the greeting shows "Elena Ruiz" but the badge still displays "Elena" (verified in React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: copying text into markup duplicates data; when the variable changes, the copied text remains frozen; storing the name in one local variable `const readerName = 'Elena'` and reading `{readerName}` in both places makes both derive from that single value; updating the variable updates both places together.
    - Fix: read `{readerName}` in both the greeting and the badge from one local variable. The curly brace syntax is taught in the runway section "A component describes the interface in JSX from data".
    - Rule: keep each value in one variable and read it everywhere it appears. Boundary: data stays static in this lesson; changing data over time with state is owned by Lecture 14.
    - Needs: local variable `const` (runway), curly braces `{}` in JSX (runway), single source of truth (runway).
    - Diagram: two elements reading from one central variable box.

> [!PRINCIPLE]
> **Principle 2: Keep each value in one variable and read it everywhere it appears**
> When a value appears in more than one place on the screen, do not type it into the markup more than once. Store the value in a single local variable and read that variable in every place that shows it using curly braces. Because every part of the markup reads from this single source of truth, all parts update together and can never disagree.
>
> *We should do this:*
> `function Header() {`
> `  const name = 'Elena'; // single source of truth`
> `  return (`
> `    <div>`
> `      <h1>Welcome, {name}</h1>`
> `      <span>Subscriber: {name}</span>`
> `    </div>`
> `  );`
> `}`
>
> *We should not do this:*
> `function Header() {`
> `  const name = 'Elena';`
> `  return (`
> `    <div>`
> `      <h1>Welcome, {name}</h1>`
> `      <span>Subscriber: Elena</span> {/* fixed text drifts */}`
> `    </div>`
> `  );`
> `}`

- [p] ★ In `SiteHeader`, pasting the static text "Subscriber: Elena" directly into the badge markup caused state drift the moment `readerName` changed to "Elena Ruiz". The greeting read the updated variable, while the badge stayed frozen on the old literal string. Replacing the fixed text with `{readerName}` ensures that both elements read the exact same variable. When `readerName` is updated in our code, both the greeting and the badge reflect the new name simultaneously. ◼ Educational objective: prove Principle 2 on the lesson's code, demonstrating how a single source of truth eliminates state drift.

- [question-cycle] Question 3: Rebuilding the header wipes the search box
    - Question: "If React builds the header from my description, does it rebuild the whole header when the name changes, and wipe what the reader typed in the search box?"
    - Code and result: plain JavaScript `header.innerHTML = '<p>Welcome back, ' + name + '</p><input placeholder="Search..." />'`; with "elections" typed into the search box, running the update wipes the text and resets cursor focus to the document body (verified in jsdom 30.1.2).
    - Verdict: does not do what the reader wanted.
    - Answer: `innerHTML` destroys living C++ DOM nodes and parses HTML strings from scratch, wiping input buffers and cursor focus; React compares the new description to the previous one in memory and updates only the two text pieces that hold the name; the `<input>` element remains the exact same DOM node on the page, so the typed text and cursor focus stay.
    - Fix: describe the header in React and let React update the page; React applies the minimal necessary operations to patch changed text nodes without rebuilding unchanged elements. The diffing mechanism is taught in the runway section "Updating only what differs preserves typed text and focus".
    - Rule: let React update only the text that differs instead of rebuilding elements with innerHTML. Boundary: Lecture 15 (`render_and_commit`) traces the complete commit phase when state updates occur.
    - Needs: `innerHTML` (runway), input cursor focus (runway), minimal necessary operations (runway).
    - Diagram: DOM tree comparison showing unchanged `<input>` node retained while text nodes are updated.

> [!PRINCIPLE]
> **Principle 3: When data changes, React updates only the text that differs**
> When data updates, React does not destroy and recreate elements on the page. Replacing containers with `innerHTML` destroys living elements, wiping typed input text and losing cursor focus. Instead, React compares the new description with the previous one and applies the minimal changes needed. Unchanged elements remain in place, so an input field keeps what the user typed and keeps its focus.
>
> *We should do this:*
> `function Header() {`
> `  const name = 'Elena';`
> `  return (`
> `    <div>`
> `      <h1>Welcome, {name}</h1> {/* updates text */}`
> `      <input placeholder="Search..." /> {/* keeps focus */}`
> `    </div>`
> `  );`
> `}`
>
> *We should not do this:*
> `function updateHeader(name) {`
> `  const container = document.getElementById('header');`
> `  const html = '<h1>Welcome, ' + name + '</h1><input>';`
> `  container.innerHTML = html; // wipes input text and focus`
> `}`

- [p] ★ In plain JavaScript, assigning a new string to `header.innerHTML` tore down the existing search box. The user's typed search query "elections" vanished, and the active cursor was thrown out of the input. In React, changing `readerName` from "Elena" to "Elena Ruiz" causes React to compare the new description with the old one. React observes that the `<input>` element and the layout container are unchanged. It mutates only the text nodes containing the name. The search box keeps its text, its event listeners, and its active cursor focus. ◼ Educational objective: prove Principle 3 on the lesson's code, proving surgical node patching and focus preservation.

### Step 1: First, we declare the site header component <SiteHeader.jsx>

- [p] ★ We construct `SiteHeader.jsx` to establish the declarative foundation for our header. Instead of writing separate HTML tags and later writing scripts to query them, we define a component function that returns our layout description. We store the reader's name in a single local variable, `readerName`, and project it into both the greeting paragraph and the subscriber badge using curly braces. ### For the interview

> **The Interview Question:** What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

**1. The Hidden Signal**

The interviewer is not merely testing whether you know how to write a component function. They are probing whether you understand the fundamental architectural shift from imperative DOM mutation to declarative state synchronization. A junior developer talks about convenience or shorter syntax. A senior engineer explains that imperative DOM scripting couples application logic directly to fragile document queries, creating inevitable state drift when data appears in multiple widgets. They articulate that React models the user interface as a pure projection of data, computing minimal necessary DOM mutations in memory to preserve element identity and input focus.

**2. The Classic Trap**

The classic trap is claiming that "React is faster than the real DOM because the Virtual DOM has zero performance cost." That claim fails the interview. A well-written, hand-optimized DOM script targeting a single node can execute faster than React's component evaluation and diffing passes. React's true value is predictable synchronization, not raw micro-benchmark speed. Another dangerous trap is telling the interviewer that React throws away and rebuilds the DOM on every render. If React rebuilt the DOM tree, every active text input would lose focus and unsubmitted form state would vanish. React diffs descriptions in memory and surgically mutates only changed text nodes.

**3. What is Actually Going On**

In plain JavaScript, we write imperative commands that find specific elements by identifier and mutate them step by step. If our code misses one element, the screen shows stale data.

In React, we write component functions that return JSX describing what the screen should look like for the current data. React calls our component, evaluates the returned description, and constructs the real DOM elements.

When a value like `readerName` updates, React calls the component again, compares the new description with the previous one, and applies the minimal necessary operations. It changes only the specific text that differs, leaving living DOM nodes and active keyboard focus completely intact.

**4. Where It Gets Tricky**

Where this model gets tricky in production is when developers carry old imperative habits into React applications. Attempting to query DOM nodes directly with `document.getElementById` inside a React component bypasses React's synchronization pipeline, creating severe conflicts between React's in-memory model and physical browser pixels. Similarly, using `innerHTML` or destructive container updates inside a component destroys living DOM node identity, wiping input selections and breaking accessibility focus rings. Embracing React means fully trusting declarative data projection and delegating physical DOM mutations entirely to the library.

### Glossary

- **DOM** (Document Object Model): The objects the browser builds in memory from the HTML, one for every tag, arranged as a tree. The screen is drawn from the DOM, so changing the page means updating the DOM.
- **Imperative programming**: Code that gives the browser every command itself, such as finding an element and setting its text. From the Latin *imperare*, "to command".
- **Declarative programming**: Code that declares what the page should show for the current data, while React updates the DOM to match. From the Latin *declarare*, "to make clear, to announce".
- **State Drift**: A defect where two or more elements on the screen show conflicting or out-of-date information because manual updates failed to synchronize every matching node.
- **Component**: A JavaScript function whose name starts with an uppercase letter that returns a description of user interface markup in JSX.
- **Single Source of Truth**: The architectural practice of storing a piece of data in one place and reading that exact value everywhere it is displayed to prevent disagreement.
- **Minimal Necessary Operations**: React's strategy of comparing new interface descriptions with previous ones and updating only the specific text nodes or attributes that changed.

➔ ALWAYS describe what the page shows for the current data instead of writing imperative commands to find and mutate elements.

| **DOM Update Strategy** | Destructive container replacement<br>via `innerHTML` or manual<br>property assignments | In-memory description comparison;<br>applies minimal necessary operations<br>to changed text nodes only |
