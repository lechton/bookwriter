### Raw HTML is markup, JSX is JavaScript

- [p] ◇ {theme} Every website is built out of markup: headings, paragraphs, images, and lists. In traditional web development, you write HTML directly in markup files. In React, you write markup inside JavaScript functions. The question every web developer meets: when we write markup inside a component, how does that markup differ from plain HTML? ◼ Educational objective: bird's-eye view; the theme from the map's Theme and Options, from pages the reader knows.

- [p] ◇ {starting point: raw HTML} You know markup from **raw HTML**, the plain text of a standard web page: you write the tags as text, and the browser parses them. ◼ Educational objective: the reader's starting point, named by its exact term; the map lists no options, so it is not a rival way.

- [code] Raw HTML: browser parses text markup:

```html title="Raw HTML: browser parses text markup"
<h2 class="title">Night Trains Return</h2>
<img src="/img/train.jpg"> <!-- unclosed void tag -->
<p>Sleeper routes reopen.</p>
```

- [p] ◇ {starting point: point into the code} The browser reads the HTML file as a string of text. Its parser is forgiving: it accepts multiple tags side by side at the document level, allows void tags like `<img>` without a closing slash, and copies attributes like `class` directly to the element. That is why it is called raw HTML: the browser receives markup text directly. Inside a component, the markup no longer sits in an HTML file for the browser to parse: it sits inside a JavaScript function, and the JavaScript engine cannot run markup text. ◼ Educational objective: point into the code and say where the starting point stops serving the reader, without inventing a use for it.

- [p] ◇ {the chapter's idea: JSX} React components write markup in **JSX** instead: you write the tags inside JavaScript, and the build compiles every tag into a function call. ◼ Educational objective: the chapter's idea, named by its exact term.

- [code] JSX: markup compiled to JavaScript expressions:

```jsx title="JSX: markup compiled to JavaScript expressions"
<article className="card">
  <h2 className="title">Night Trains Return</h2>
  <img src="/img/train.jpg" alt="A night train" /> {/* self-closing slash */}
  <p>Sleeper routes reopen.</p>
</article>
```

- [p] ◇ {the chapter's idea: point into the code} All three tags sit inside one enclosing `<article>` container, the `<img>` tag closes itself with `/>`, and the styling attribute is `className`. The build compiles each tag into a `_jsx` call that evaluates to a plain JavaScript object. Because a function returns one value, all tags must sit inside a single root (or a Fragment, `<>...</>`); because JavaScript enforces strict grammar, every tag must close, and attributes use DOM property names. That is why it is called JSX: a JavaScript XML syntax extension that describes elements. ◼ Educational objective: the place, what fills it, who acts, and the contrast with raw HTML.

- [code] JSX: top stories list item:

```jsx title="JSX: top stories list item"
<li className="story-item">
  <span className="bullet" /> {/* self-closing span */}
  Morning Dispatch
</li>
```

- [p] ◇ {the chapter's idea: second tiny example} A second component shows the same rules at work: the `<span />` tag closes itself with a trailing slash, and `className` sets its CSS class without colliding with JavaScript's reserved `class` keyword. ◼ Educational objective: confirm the idea with a second component.

### The compiler transforms JSX tags into function calls and element objects

- [p] ◇ {runway: JSX definition and compile-time transformation} JSX stands for JavaScript XML. It is a syntax extension that allows developers to write HTML-like markup directly inside JavaScript files. While JSX looks like HTML, the browser engine never executes JSX directly. Before code reaches the browser, a build compiler parses the markup and transforms every tag into a JavaScript function call named `_jsx()`. ◼ Educational objective: define JSX and explain that browsers never execute markup tags directly.
- [p] ★ {runway: _jsx call and the React element descriptor} When the compiler processes `<h2 className="headline">Night Trains Return</h2>`, it transforms that tag into `_jsx("h2", { className: "headline", children: "Night Trains Return" })`. At runtime, calling `_jsx()` produces a lightweight JavaScript object called a React element. A React element is an in-memory descriptor with properties such as `type: 'h2'` and `props`. React reads these descriptor objects during render and calls `document.createElement()` to create the real browser DOM nodes. ◼ Educational objective: explain the compilation of JSX into _jsx calls and the creation of React element descriptors.
- [p] ★ {runway: attributes as object properties and first-class JavaScript values} Because JSX tags compile into standard JavaScript function calls, JSX expressions are first-class JavaScript values. You can assign a JSX tag to a local variable, pass it as an argument, or return it from a function. Furthermore, any attributes written on a JSX tag become key-value pairs on the second argument of `_jsx()`. Understanding that JSX is JavaScript provides the foundation for all syntax rules that follow. ◼ Educational objective: establish that JSX tags are first-class JavaScript expressions and attributes become object keys.

### JavaScript functions return one expression unless wrapped in a root or a Fragment

- [p] ★ {runway: JavaScript function return grammar and expressions} In JavaScript, a `return` statement can only return a single value or expression. When you write `return 42;`, the engine returns that single number. If you attempt to write two expressions side by side without an operator, such as `return a b;`, the JavaScript parser halts with a fatal syntax error. Even if you separate them with the comma operator, as in `return (a, b);`, the comma operator evaluates both but returns only the second expression `b`, discarding `a`. ◼ Educational objective: explain JavaScript return grammar and the single expression invariant.
- [p] ★ {runway: the single-root rule as a language invariant} Because every JSX tag compiles into a distinct `_jsx()` function call, writing two adjacent tags side by side after `return` is equivalent to writing two function calls without an operator: `return _jsx("h2", ...) _jsx("p", ...);`. This syntax is invalid JavaScript. To return multiple elements from a component, you must wrap them inside a single enclosing root element, such as an `<article>` container or a `<main>` shell. ◼ Educational objective: prove that the single-root rule is an inescapable requirement of JavaScript return grammar.
- [p] ★ {runway: Fragments and CSS child selectors} Wrapping adjacent elements in an extra `<div>` satisfies the compiler, but it inserts a real DOM element into the page. Intermediate `<div>` nodes pollute the DOM tree and break CSS rules that rely on direct parent-child relationships, such as child selectors (`.stories > li`) or flexbox and grid layouts. To group siblings without adding an extra DOM node, React provides a virtual container called a Fragment, written `<>...</>`. React unpacks Fragments in memory and mounts child elements directly into the parent container. ◼ Educational objective: contrast physical wrapper elements with virtual React Fragments and explain CSS child selector impacts.

### JSX requires closed tags and JavaScript property names

- [p] ◇ {runway: void elements in HTML versus XML tag closure} In native HTML, elements fall into two distinct categories: container elements that enclose content, and void elements that cannot contain children. The HTML specification defines a fixed dictionary of void elements, including `<img>`, `<input>`, `<br>`, and `<hr>`. In HTML, these tags never require closing tags. In contrast, JSX enforces strict XML grammar where every opening tag must be explicitly terminated, either with a matching closing tag or with a trailing self-closing slash (`<img />` or `<br />`). ◼ Educational objective: define HTML void elements and contrast them with strict XML closure in JSX.
- [p] ★ {runway: reserved keyword collisions and DOM property alignment} In raw HTML markup, developers write `class="headline"` and `<label for="email">`. However, in JavaScript, `class` and `for` are reserved keywords used for declaring ES6 classes and writing loops. Decades ago, the browser DOM specification resolved this collision by naming element object properties `element.className` and `element.htmlFor`. Because JSX attributes become keys on a JavaScript props object, React aligns with these DOM property names, using `className` and `htmlFor` to prevent reserved keyword collisions. ◼ Educational objective: explain the history of JavaScript reserved keywords and DOM property alignment for className and htmlFor.
- [p] ★ {runway: camelCase attribute conventions and aria/data exceptions} Beyond `className` and `htmlFor`, React writes multi-word HTML attributes in camelCase, such as `tabIndex` instead of `tabindex` and `strokeWidth` instead of `stroke-width`. If a developer writes raw HTML attribute names, React still sets the property on the element but prints clear warning messages in the browser development console. As an explicit exception to the camelCase rule, accessibility attributes (`aria-*`) and custom data attributes (`data-*`) keep their hyphens to match standard HTML specifications. ◼ Educational objective: outline camelCase attribute conventions, development console warnings, and hyphenated exceptions.

### Principles of React: JSX Syntax and the Single-Root Rule

- [question-cycle] Question 1: A component returns descriptor objects rather than HTML strings
    - Question: "My component returns something that looks like HTML. Is it HTML?"
    - Code and result: `const headline = <h2 className="headline">Night Trains Return</h2>; console.log(headline);` logs a plain JavaScript object with `type: 'h2'` and `props: { className: 'headline', children: 'Night Trains Return' }`, not an HTML string (verified in React 19.3.0).
    - Verdict: works as React intended.
    - Answer: JSX is a syntax extension for JavaScript; the compiler transforms each tag into a `_jsx` function call; calling `_jsx` evaluates to a plain JavaScript object called a React element; React reads these in-memory descriptor objects during render and constructs real DOM nodes; the browser engine never parses JSX directly.
    - Fix: none.
    - Rule: JSX is JavaScript that compiles into function calls returning element descriptors. Boundary: Values from variables stay out of this lesson, as Lecture 4 explores JSX curly brace expressions.
    - Needs: `_jsx` call (runway), React element (runway), attribute (runway).
    - Diagram: JSX tag compiling into _jsx function call producing a JavaScript element descriptor in memory before DOM commitment.

> [!PRINCIPLE]
> **Principle 1: JSX is JavaScript that describes elements**
> Markup inside a component is not an HTML template string. The build compiles each tag into a `_jsx` function call that evaluates to a plain JavaScript object called a React element. React reads these descriptor objects during render and constructs the corresponding browser DOM nodes. Because JSX is JavaScript, you can place element expressions anywhere a JavaScript value is valid, such as inside variables or return statements.
>
> *We should do this:*
> `const element = <h2 className="title">Night Trains</h2>;`
> `// compiles to _jsx("h2", { className: "title", children: "..." })`

- [p] ★ In our `ArticleCard` component, logging a JSX tag proves what exists in JavaScript memory. When you declare `const headline = <h2 className="headline">Night Trains</h2>;` and pass it to `console.log(headline)`, the console does not display a string of angle brackets. Instead, it displays a plain JavaScript object with properties `type: "h2"` and `props: { className: "headline", children: "Night Trains" }`. The browser DOM is never touched during this assignment; React evaluates these descriptor objects during its render pass and coordinates the creation of physical DOM elements. ◼ Educational objective: prove Principle 1 on the lesson's code by inspecting logged React element objects.

- [question-cycle] Question 2: A component must return a single root element
    - Question: "I pasted a heading and a paragraph after return. Why does the build fail?"
    - Code and result: `ArticleCard` returns `<h2>Night Trains Return</h2>` and `<p>Sleeper routes reopen.</p>` side by side; the build fails; Babel reports "Adjacent JSX elements must be wrapped in an enclosing tag. Did you want a JSX fragment <>...</>?"; esbuild reports a syntax parse error (verified with @babel/parser 8.0.7 and esbuild 0.28.2).
    - Verdict: does not do what the reader wanted.
    - Answer: each tag compiles into an independent `_jsx` function call expression; in JavaScript, a `return` statement can only return a single value; two function calls placed side by side without an enclosing container or operator violate JavaScript grammar; the compiler cannot package multiple independent return values into a single return slot.
    - Fix: wrap the adjacent sibling tags inside a single enclosing root element, such as `<article className="card">`.
    - Rule: A component must return a single root element because JavaScript functions can only return a single value. Boundary: When the layout does not require an extra physical DOM container element, use a Fragment as shown in Question 3.
    - Needs: expression (runway), comma operator (runway).
    - Diagram: Adjacent function calls violating return grammar versus single parent function call enclosing child array.

> [!PRINCIPLE]
> **Principle 2: A component returns one root because a function returns one value**
> Every JSX tag compiles into an independent `_jsx` function call expression. In JavaScript, a `return` statement can only return a single value. Placing two adjacent tags side by side without an enclosing container attempts to return two separate expressions, which violates JavaScript language grammar and halts compilation. To return multiple elements, enclose them inside a single root container.
>
> *We should do this:*
> `return (`
> `  <article className="card"> {/* single root container */} `
> `    <h2>Night Trains Return</h2>`
> `    <p>Sleeper routes reopen.</p>`
> `  </article>`
> `);`
>
> *We should not do this:*
> `return (`
> `  <h2>Night Trains Return</h2> {/* adjacent floating tag */} `
> `  <p>Sleeper routes reopen.</p> {/* cannot return two values */} `
> `);`

- [p] ★ In our `ArticleCard` component, returning `<h2>` and `<p>` side by side demonstrates the physical return limit of JavaScript. The compiler attempts to transpile the code into `return _jsx("h2", ...), _jsx("p", ...);`. In JavaScript, returning multiple bare expressions is a fatal grammar error. Even with parentheses, the comma operator would discard the heading and return only the paragraph. Wrapping both tags in an `<article className="card">` container produces a single outer `_jsx("article", ...)` call with the heading and paragraph packaged as an array inside its `children` prop, satisfying ECMAScript return grammar. ◼ Educational objective: prove Principle 2 by deconstructing single-expression return grammar.

- [question-cycle] Question 3: Grouping siblings with a div can break list and layout styling
    - Question: "So I wrap everything in a div?"
    - Code and result: `TopStories` returns two `<li>` items wrapped in a `<div>`, mounted inside `<ul className="stories">`; the DOM renders `<ul><div><li></li><li></li></div></ul>`, and `.stories > li` matches zero items; with `<>...</>` the DOM renders `<ul><li></li><li></li></ul>` and matches 2 items (verified in React 19.3.0).
    - Verdict: does not do what the reader wanted.
    - Answer: a `<div>` tag compiles to `_jsx("div", ...)` and creates a real DOM element between the parent and the children; CSS child combinators (`.stories > li`) and flexbox/grid layout models require direct parent-child relationships; an intermediate `<div>` disrupts these relationships and creates invalid list markup; a Fragment `<>...</>` satisfies the single-root return rule in JavaScript without creating any node in the browser DOM.
    - Fix: replace the outer `<div>` with a React Fragment `<>...</>`.
    - Rule: Group elements with a Fragment when the page needs no extra DOM element. Boundary: Use a physical HTML element like `<article>` or `<section>` when the page needs semantic structure or a styling box.
    - Needs: Fragment (runway), CSS child selector `.stories > li` (runway).
    - Diagram: DOM tree with intermediate div wrapper interrupting child selector versus flat DOM tree with Fragment preserving direct hierarchy.

> [!PRINCIPLE]
> **Principle 3: Group with a Fragment when the page needs no extra element**
> Wrapping elements in a `<div>` creates a real DOM element that can disrupt CSS child selectors, flexbox hierarchies, and grid layouts. When elements must be grouped solely to satisfy the single-root rule, wrap them in a **Fragment**, written `<>...</>`. A Fragment satisfies the single-return requirement in JavaScript without adding any node to the browser DOM. Use an element like `<article>` only when the page requires a semantic container or styling box.
>
> >> Fragment : a virtual JSX container that groups children without rendering a DOM node
>
> *We should do this:*
> `<ul className="stories">`
> `  <>`
> `    <li>Night trains return</li> {/* mounts directly in ul */} `
> `    <li>High-speed rail opens</li>`
> `  </>`
> `</ul>`
>
> *We should not do this:*
> `<ul className="stories">`
> `  <div> {/* extra div breaks child selectors and list semantics */} `
> `    <li>Night trains return</li>`
> `    <li>High-speed rail opens</li>`
> `  </div>`
> `</ul>`

- [p] ★ In our `TopStories` component, returning list items wrapped in a `<div>` reveals the architectural cost of unneeded DOM nodes. The HTML specification dictates that the only permitted direct children of a `<ul>` element are `<li>` elements. When `TopStories` wraps items in a `<div>`, the living DOM structure becomes `<ul><div><li></li></div></ul>`. Styles defined for `.stories > li` fail to match because `div` is not an `li`. Replacing `<div>` with `<>...</>` produces a clean flat hierarchy where the list items mount directly inside `<ul>`, allowing child selectors and CSS grid alignments to apply cleanly. ◼ Educational objective: prove Principle 3 by tracing DOM list item invalidation and CSS child selector failure.

- [question-cycle] Question 4: Every tag in JSX must be explicitly closed
    - Question: "HTML lets me write img and br without closing them. Why does JSX refuse?"
    - Code and result: `ArticleCard` with pasted unclosed `<img src="/img/train.jpg" alt="Night train">`; the build fails with esbuild reporting "Unexpected closing 'article' tag does not match opening 'img' tag"; Babel reports an unexpected token (verified with esbuild 0.28.2 and @babel/parser 8.0.7).
    - Verdict: does not do what the reader wanted.
    - Answer: browser HTML parsers contain a hardcoded dictionary of void elements that cannot contain children and never require closing tags; JSX enforces strict XML grammar with zero tag dictionaries; when the parser encounters `<img`, it expects a matching closing tag or a self-closing slash; without a trailing slash, the parser treats subsequent elements as children of the image, causing closing tag mismatch errors.
    - Fix: terminate the tag with an explicit self-closing slash: `<img src="/img/train.jpg" alt="Night train" />`.
    - Rule: Close every tag in JSX, including void elements like `<img />` and `<br />`. Boundary: Any tag without children may close itself, such as `<div className="spacer" />`.
    - Needs: void elements (runway).
    - Diagram: Unclosed void tag leaving AST branch open versus self-closing slash terminating leaf node immediately.

> [!PRINCIPLE]
> **Principle 4: Close every tag, including <img /> and <br />**
> While standard HTML allows **void elements** like `<img>` and `<br>` to remain open, JSX enforces strict XML syntax where every tag must be explicitly terminated. Without a closing tag or a trailing self-closing slash, the compiler treats all subsequent markup as child content of that tag. Always terminate self-contained tags with a trailing slash, such as `<img />` or `<br />`, so the parser can resolve the element boundary.
>
> >> void elements : HTML tags that cannot contain children and have no closing tags in HTML
>
> *We should do this:*
> `<article className="card">`
> `  <img src="/img/train.jpg" alt="Train" /> {/* closed slash */} `
> `  <h2>Night Trains Return</h2>`
> `</article>`
>
> *We should not do this:*
> `<article className="card">`
> `  <img src="/img/train.jpg" alt="Train"> {/* unclosed tag */} `
> `  <h2>Night Trains Return</h2>`
> `</article>`

- [p] ★ In our `ArticleCard` component, pasting raw `<img src="/img/train.jpg" alt="Night train">` breaks the compiler because the JSX lexer cannot infer where the image element ends. Because the tag lacks a self-closing slash, the parser treats the subsequent `<h2>` tag as an inner child of the image. When the parser eventually encounters `</article>`, it finds an open `<img` node on its parsing stack that was never closed. Adding the trailing slash `<img ... />` informs the parser that the element terminates immediately and possesses zero children, emitting a clean `_jsx("img", { ... })` call. ◼ Educational objective: prove Principle 4 by explaining AST tag stack boundaries.

> `// maps cleanly to DOM properties and silences console warnings`
>
> *We should not do this:*

- [p] ★ In our `ArticleCard` component, adding a newsletter signup form with `<label class="label" for="email">` demonstrates how React enforces DOM property naming. While modern bundlers allow reserved words as object keys, React inspects incoming props during render. When it detects `class` or `for`, it logs prominent warnings in the development console because the underlying DOM nodes expect `className` and `htmlFor`. Renaming attributes to `className` and `htmlFor` aligns directly with `element.className` and `element.htmlFor`, leaving the console clean while preserving accessibility and CSS styling. ◼ Educational objective: prove Principle 5 by tracing DOM property alignment and console warning feedback.

### Step 1: First, we construct the article card component <ArticleCard.jsx>

- [p] ★ {step 1: ArticleCard component construction} We construct the standalone `ArticleCard.jsx` component to encapsulate the story headline, thumbnail image, and summary text into an isolated, reusable unit. Notice that the component encloses its markup inside a single root `<article>` tag, satisfying JavaScript's single expression return grammar. The thumbnail image uses an explicit self-closing slash `<img ... />` to satisfy JSX tag closure rules, and the styling attributes use `className` instead of `class`. ◼ Educational objective: apply the single-root rule, self-closing void tags, and className property alignment in a production card component.

- [code] ArticleCard.jsx:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() {
  return (
    <article className="card"> {/* single root container */}
      <img src="/img/train.jpg" alt="Night train" className="thumbnail" />
      <h2 className="headline">Night Trains Return</h2> {/* story headline */}
      <p className="summary">Sleeper routes reopen.</p> {/* story summary */}
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `<article className="card">`: single semantic root container satisfying function return grammar. 2. `<img ... />`: self-closing void tag satisfying strict XML parsing. 3. `className`: JavaScript DOM property alignment preventing reserved keyword collisions.

- [p] ★ {step 1 commentary: architectural rationale} Notice how `ArticleCard.jsx` functions as a pure presentation component. It owns zero internal state, requires no imperative DOM query scripts, and packages the news story into a predictable, reusable unit. By using a semantic `<article>` element as its root, the component provides accessible meaning to screen readers and a natural styling boundary for layout CSS. ◼ Educational objective: deconstruct the architectural benefits of semantic root elements.

### Step 2: Next, we group list items with a Fragment <TopStories.jsx>

- [p] ★ {step 2: TopStories component construction} When returning multiple sibling elements that belong inside an external container like a `<ul>`, you encounter a foundational architectural crossroads:
- **Option 1 (The Bloated DOM Way)**: Wrap the sibling list items in an intermediate `<div>`, polluting the DOM tree and breaking CSS child selectors.
- **Option 2 (The Modern Idiomatic Way)**: Group the sibling list items with a React Fragment `<>...</>`, preserving direct parent-child relationships with zero DOM overhead. ◼ Educational objective: frame the architectural crossroads between wrapper divs and React Fragments.

- [p] ★ {step 2 crossroads: Option 1 naive implementation} First, examine Option 1 with an intermediate `<div>` wrapper:

- [code] Option 1: The Bloated DOM Way (Intermediate Div Wrapper):

```jsx title="Option 1: The Bloated DOM Way (Intermediate Div Wrapper)"
export default function TopStories() {
  return (
    <div> {/* extra div creates DOM node and breaks list semantics */}
      <li className="story-item">High-speed alpine rail opens</li>
      <li className="story-item">Sleeper booking platform launches</li>
    </div>
  );
}
```

◼ **The what-this-introduces list:** 1. Redundant `<div>`: intermediate DOM node placed inside an external `<ul>`. 2. Broken list semantics: invalid HTML hierarchy where `<div>` is a direct child of `<ul>`.

- [p] ★ {step 2 crossroads: deconstructing Option 1 failure} In Option 1, the intermediate `<div>` satisfies JavaScript's single return requirement. However, when mounted inside a parent `<ul className="stories">`, the living DOM structure becomes `<ul><div><li></li><li></li></div></ul>`. This structure violates HTML5 list specifications, increases browser node count, and breaks CSS rules like `.stories > li` because the list items are no longer direct children of the list container. ◼ Educational objective: deconstruct why wrapper divs break list semantics and CSS child selectors.

- [p] ★ {step 2 crossroads: Option 2 modern idiomatic solution} Now, examine Option 2 using a clean React Fragment:

- [code] TopStories.jsx:

```jsx title="TopStories.jsx"
export default function TopStories() {
  return (
    <> {/* Fragment groups siblings without creating a DOM node */}
      <li className="story-item">High-speed alpine rail opens</li>
      <li className="story-item">Sleeper booking platform launches</li>
    </>
  );
}
```

◼ **The what-this-introduces list:** 1. `<>...</>`: React Fragment syntax grouping multiple siblings in memory. 2. Flat DOM projection: direct mounting of `<li>` items into the parent `<ul>`.

- [p] ★ {step 2 commentary: Fragment mechanics} In Option 2, the compiler wraps the siblings inside `_jsx(Fragment, { children: [...] })`. This satisfies JavaScript's single return value requirement at compile time. At runtime, React unpacks the Fragment and appends both `<li>` nodes directly into the host `<ul>` container. The living DOM tree remains clean and flat, allowing CSS child selectors and list styling rules to apply without obstruction. ◼ Educational objective: explain how Fragments satisfy compiler grammar while preserving flat DOM hierarchies.

### Step 3: Finally, we assemble the layout shell inside <App.jsx>

- [p] ★ {step 3: App component layout assembly} To complete our application layout, we import and compose `ArticleCard.jsx` and `TopStories.jsx` inside the primary page shell `App.jsx`. In standard JavaScript, assembling this layout required querying container elements and appending nodes imperatively. In React, the entire document organizes into a declarative hierarchy. Notice that `App.jsx` wraps `TopStories` inside a semantic `<ul className="stories">` list, providing the proper host container for the Fragment's child items. ◼ Educational objective: assemble the application shell and demonstrate parent-child composition.

- [code] App.jsx:

```jsx title="App.jsx"

import TopStories from './components/TopStories.jsx';

  return ( // primary shell mounts card and stories list
    <main className="app-shell">
```

◼ **The what-this-introduces list:** 1. `<main className="app-shell">`: top-level application container. 2. `<TopStories />` inside `<ul>`: host container receiving unpacked Fragment list items. 3. Declarative composition: combining multiple independent components into a unified interface.

- [p] ★ {step 3 commentary: architectural fidelity} Notice how `App.jsx` establishes clean architectural boundaries. It mounts `ArticleCard` as a self-contained widget and embeds `TopStories` inside a semantic `<ul>` element. Because `TopStories` returns a Fragment, the browser DOM receives `<ul><li>...</li><li>...</li></ul>` without any intermediate wrapper node. CSS rules such as `.stories > li` match both items directly, producing a responsive, accessible layout. ◼ Educational objective: verify DOM fidelity and CSS child selector matching in the completed layout.

### For the interview

> **The Interview Question:** What is JSX, what syntax rules must every snippet follow, and how do Fragments group elements without wrapper nodes?

**1. The Hidden Signal**

- [interview] The interviewer is not merely testing whether you know how to write angle brackets inside a JavaScript file. They are probing whether you understand how JSX transpiles into function calls and why React enforces strict XML-like grammar. A junior candidate answers that JSX is simply "HTML in React." A senior engineer steps to the whiteboard and explains that JSX is syntactic sugar for `_jsx()` function calls that return plain JavaScript element descriptors. They explain that the single-root rule is an inescapable consequence of JavaScript function return grammar, not an arbitrary framework preference.

**2. The Classic Trap**

- [interview] The classic trap is claiming that you can wrap adjacent siblings in a `<div>` anywhere without architectural consequences. Candidates often say "just put a div around it" whenever the single-root error appears. While adding a `<div>` silences the compiler, it pollutes the DOM tree with redundant nodes, breaks HTML5 list semantics (`<ul><div><li>`), and destroys CSS flexbox and grid layouts that depend on direct parent-child relationships. Another fatal trap is assuming that JSX attributes are identical to HTML attributes, forgetting that `class` and `for` collide with JavaScript reserved keywords and trigger console warnings.

**3. What is Actually Going On**

- [interview] Under the hood, the build compiler transforms each JSX tag into a `_jsx(type, props)` function call. In JavaScript, a function can only return a single expression value. When you return two adjacent tags without an enclosing root, the compiler attempts to emit two separate function calls in a single return slot, which violates language grammar. Every component must therefore return a single root element or a Fragment. Furthermore, while browser HTML parsers have a hardcoded whitelist of void elements that never require closing tags, the JSX parser enforces strict XML grammar where every tag must be explicitly terminated with a closing tag or a self-closing slash (`<img />`). Finally, JSX attributes become keys on a JavaScript props object, so React uses DOM property names like `className` and `htmlFor` to prevent keyword collisions.

**4. Where It Gets Tricky**

- [interview] Where this gets tricky in production is understanding how React Fragments work in memory. When you write `<>...</>`, the compiler emits `_jsx(Fragment, { children: [...] })`. React detects the internal Fragment symbol during reconciliation and treats it as a virtual container. When committing to the DOM, React completely skips creating a wrapper DOM node; it unpacks the child array and appends the child elements directly into the parent container. However, the shorthand `<>...</>` cannot accept attributes or keys. When rendering collections of grouped elements inside a loop, you must explicitly import `Fragment` from `'react'` and write `<Fragment key={item.id}>...</Fragment>`, as explored in Lecture 11.

### Glossary

- [glossary] **JSX** ◼ A syntax extension for JavaScript that allows developers to write declarative, HTML-like markup inside JavaScript files, compiling into nested `_jsx()` function calls.
- [glossary] **React element** ◼ A lightweight, plain JavaScript object created by `_jsx()` that describes a DOM element's tag name, attributes, and children in memory.
- [glossary] **Fragment** ◼ A virtual JSX container, written `<>...</>`, that groups multiple sibling elements to satisfy the single-root rule without rendering any node in the browser DOM.
- [glossary] **Void element** ◼ An HTML element that cannot contain child nodes or text content (such as `<img>`, `<input>`, or `<br>`) and must be self-closed in JSX.
- [glossary] **className and htmlFor** ◼ JavaScript DOM property names used in JSX instead of HTML's `class` and `for` attributes to avoid colliding with ECMAScript reserved keywords.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ The Single-Root Return Invariant

➔ ALWAYS return a single root element or Fragment from every component function because JavaScript functions can only return a single expression value.

➔ NEVER return adjacent sibling tags without an enclosing container because two floating expressions violate ECMAScript function return grammar.

❒ Sibling Grouping and DOM Fidelity

➔ ALWAYS use a React Fragment (`<>...</>`) when grouping sibling elements solely to satisfy the single-root rule without adding DOM overhead.

➔ NEVER wrap sibling elements in an unnecessary `<div>` when an extra container breaks CSS child selectors, flexbox hierarchies, or list semantics.

❒ Tag Closure and XML Strictness

➔ ALWAYS explicitly terminate every JSX tag with a closing tag or a self-closing trailing slash (`<img />`, `<br />`).

➔ NEVER leave HTML void elements unclosed because the JSX parser enforces strict XML grammar and halts compilation.

❒ Attribute Mapping and Reserved Keywords

➔ ALWAYS write JSX attributes using DOM property names like `className` and `htmlFor` to prevent collisions with JavaScript reserved keywords.

➔ NEVER write raw HTML `class` and `for` attributes in JSX because they trigger browser development console warnings.

**DO THIS:** return a single root or Fragment, close every tag, and use JavaScript DOM property names

```jsx right
function ArticleCard() {
  return (
    <article className="card">
      <img src="/img/train.jpg" alt="Train" className="thumb" />
      <h2 className="title">Night Trains Return</h2>
      <p className="summary">Sleeper routes reopen.</p>
    </article>
  );
}
```

**DO NOT DO THIS:** return adjacent floating tags, leave void elements unclosed, or use raw class attributes

```jsx wrong
function ArticleCard() {
  return (
    <h2>Night Trains Return</h2>
    <img src="/img/train.jpg" class="thumb">
    <p class="summary">Sleeper routes reopen.</p>
  );
}
```
