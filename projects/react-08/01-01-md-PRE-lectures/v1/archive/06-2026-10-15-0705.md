### Props let one component show different content

- [p] ◇ {theme} Every web application displays repeated visual structures: news feeds, product listings, and user comments. In earlier lessons, our components returned fixed markup or read local variables declared inside their own function bodies. When multiple cards share the same frame but display different data, every developer meets the same question: how does each component display its own unique content? ◼ Educational objective: bird's-eye view; the theme from the map's Theme and Options, from pages the reader knows.

- [p] ◇ {starting point: hardcoded component} A component that writes its text inside its own function body is a **hardcoded component**. ◼ Educational objective: the reader's starting point, named by its exact term; the map lists no options, so it is not a rival way.

- [code] Hardcoded component: fixed text inside component body:

```jsx title="Hardcoded component: fixed text inside component body"
function ArticleCard() {
  return (
    <article className="card">
      <h2>Transit Accord Reached</h2> {/* fixed headline in component body */}
      <p>5 min read</p>
    </article>
  );
}
```

- [p] ◇ {starting point: point into the code} All values sit hardcoded inside the function body: the card always displays "Transit Accord Reached" and "5 min read". If the feed renders `<ArticleCard />` three times, every card displays identical copy; to show three different stories, a developer must duplicate the function three times. That is why it is called a hardcoded component: the data is fixed directly in code. ◼ Educational objective: point into the code and say where the starting point stops serving the reader, without inventing a use for it.

- [p] ◇ {the chapter's idea: props} React's answer is **props**: the parent passes attributes on the component tag, and React hands them to the child as an input object. ◼ Educational objective: the chapter's idea, named by its exact term.

- [code] Props: dynamic attributes configured by parent:

```jsx title="Props: dynamic attributes configured by parent"
function EditorialFeed() {
  return (
    <main className="feed">
      <ArticleCard title="Rail Strike Ends" readTime={3} /> {/* first card */}
      <ArticleCard title="Clean Energy Project" readTime={5} /> {/* card two */}
    </main>
  );
}
```

- [p] ◇ {the chapter's idea: point into the code} The parent component writes attributes on each `<ArticleCard />` tag: `title="Rail Strike Ends"` and `readTime={3}`. React collects those attributes into a single object and passes it to `ArticleCard` as its argument. Inside `ArticleCard`, the component unpacks `{ title, readTime }` and renders those values. One single component layout now renders hundreds of distinct stories. That is why they are called props: properties passed from parent to child. ◼ Educational objective: the place, what fills it, who acts, and the contrast with hardcoded components.

- [code] Props: unpacking inputs in the parameter list:

```jsx title="Props: unpacking inputs in the parameter list"
function ArticleCard({ title, readTime }) {
  return (
    <article className="card">
      <h2>{title}</h2> {/* renders title prop */}
      <p>{readTime} min read</p> {/* renders readTime prop */}
    </article>
  );
}
```

### What props are and how React passes them as a single object

- [p] ◇ {runway: functions accepting arguments to return customized output} In standard JavaScript, functions accept arguments so that a single calculation can run on different inputs. For example, a function `double(x)` returns `x * 2` for any number you provide. React components are JavaScript functions that return user interface markup. If a component could only return hardcoded text, you would need a new component function for every distinct item in your application. React solves this through **props**, which is short for properties. Props allow a parent component to pass custom data down to child components, letting one single component layout render hundreds of different stories or products. ◼ Educational objective: ground props in universal function argument concepts and motivate parameterized rendering.
- [p] ◇ {runway: attributes bundle into a single props object} When you render a custom component tag in JSX, any attributes you write become properties on a single JavaScript object. For instance, writing `<ArticleCard title="Rail Strike Ends" readTime={3} />` tells React to create an object: `{ title: "Rail Strike Ends", readTime: 3 }`. React passes this object as the first and only argument to your `ArticleCard` component function. In React terminology, the location where you render the tag is called the **call site**, the attributes are called **props**, and the component receiving the data is the **child component**. The attributes on the tag do not reach the browser DOM directly; React hands them exclusively to the component function. ◼ Educational objective: establish the core model of attributes at the JSX call site compiling into a single props object.
- [p] ◇ {runway: object destructuring in function parameter lists} When working with props, modern JavaScript provides a concise syntax called **object destructuring**. Instead of writing `function ArticleCard(props)` and repeating `props.title` and `props.readTime` throughout your markup, you can write `function ArticleCard({ title, readTime })`. In JavaScript, placing curly braces `{ }` inside the parameter list tells the runtime to automatically unpack specific keys from the incoming object into local variables. This syntax is standard ECMAScript, but it is the universal convention in React because it makes a component's required inputs immediately visible at the top of the function. If a destructured parameter name does not match any attribute on the tag (such as writing `{ headline }` when the tag passed `title=`), the local variable receives `undefined`. ◼ Educational objective: explain JavaScript object destructuring and contrast destructuring against manual property lookups.
- [p] ★ {runway: JSX compilation to _jsx calls} Under the hood, the JSX compiler converts every component tag into a function call. As we learned in Lecture 4, writing `<ArticleCard title="Rail Strike Ends" readTime={3} />` transforms into `_jsx(ArticleCard, { title: "Rail Strike Ends", readTime: 3 })`. Notice that the second argument to `_jsx` is a standard JavaScript object literal. React instantiates this object, freezes it shallowly in development mode using `Object.freeze()`, and provides it to your component when invoking the function. This mechanical reality proves why components receive exactly one object argument rather than a list of separate parameters. ◼ Educational objective: trace the compiler transformation from JSX attributes to the _jsx props argument.

### How JavaScript handles prop types, string concatenation, and default values

- [p] ★ {runway: quotes versus braces and type coercion} In JSX, how you wrap an attribute value determines its JavaScript data type. As established in Lecture 4, quotes pass a static string literal (`readTime="5"`), while curly braces evaluate a live JavaScript expression (`readTime={5}`). When a child component receives a prop, the runtime respects that exact type. If a component receives `"5"` as a string and performs addition (`{readTime + 1}`), JavaScript performs string concatenation via **type coercion**, converting `1` to `"1"` and producing `"51"`. By contrast, multiplication (`{readTime * 60}`) coerces the string to a number and yields `300`. This discrepancy can hide bugs during initial testing until an addition operation reveals the error. ◼ Educational objective: explain type coercion and demonstrate why numbers must be passed in curly braces.
- [p] ★ {runway: default parameter values in destructuring} When designing components, some props are optional. If a parent component omits an attribute or passes `readTime={undefined}`, the incoming property is `undefined`. To prevent blank slots on screen, JavaScript allows you to specify a **default parameter value** directly inside the destructuring braces: `function ArticleCard({ title, readTime = 5 })`. If the parent does not provide `readTime`, the local variable automatically takes the fallback value `5`. However, default parameter values only trigger when a value is strictly `undefined` or missing; they do not trigger when a parent passes `null` or `0`. ◼ Educational objective: explain how default parameter values operate during destructuring.
- [p] ★ {runway: handling null and zero: logical OR versus nullish coalescing} When working with external API data, database records often contain `null` for unmeasured fields. If a parent passes `readTime={null}`, the default parameter `readTime = 5` does not engage because `null` is a defined value. In JSX, `{null}` renders as an empty string, producing ` min read`. In older JavaScript codebases, developers wrote `readTime || 5` using the **logical OR** operator. However, `||` treats any falsy value as missing, which replaces a valid `0` (such as a 0-minute quick read) with `5`. Modern codebases use the **nullish coalescing** operator (`??`): `const time = readTime ?? 5;`. Nullish coalescing checks strictly for `null` and `undefined`, preserving valid `0` values while providing a resilient fallback. ◼ Educational objective: contrast default parameter behavior against logical OR and nullish coalescing for null and zero.

### The read-only contract, frozen objects, and why mutating inputs corrupts the tree

- [p] ◇ {runway: component purity and the immutability contract} In React, components must be pure functions with respect to their inputs. A pure function is one that does not alter any objects or variables that existed before it was called, and returns the exact same JSX description given the same inputs. Props represent data owned by the parent component. If a child component were allowed to perform a **mutation** by directly reassigning `props.title = 'Breaking News'`, it would modify memory owned by the parent. React enforces an immutability contract: props are strictly read-only. ◼ Educational objective: define component purity and the read-only contract for props.
- [p] ★ {runway: Object.freeze in development and strict mode TypeError} To protect developers from accidental mutations, React shallowly freezes the props object in development mode using `Object.freeze()`. When code runs inside an ES module, JavaScript automatically executes in **strict mode**. In strict mode, attempting to assign a property on a frozen object immediately throws a fatal exception: `TypeError: Cannot assign to read only property 'title' of object '#<Object>'`. In older non-strict scripts, the assignment is silently ignored without updating the object. ◼ Educational objective: trace how Object.freeze and strict mode combine to throw a TypeError on prop assignment.
- [p] ★ {runway: development versus production builds and shallow freeze limits} It is critical to understand that React's development freeze is a diagnostic alarm, not a runtime security sandbox. In production builds, React skips `Object.freeze()` to maximize rendering performance. Furthermore, `Object.freeze()` is shallow: if a parent passes an object prop like `article={{ title: 'Rail Strike', readTime: 3 }}`, React freezes only the outer container, leaving nested properties mutable. If a child executes `article.title = article.title.toUpperCase()`, the assignment succeeds in both development and production. This mutation silently corrupts data in the parent and across sibling components showing the same article (such as a sidebar), causing state drift. ◼ Educational objective: explain why Object.freeze is shallow and compare development versus production build behaviors.
- [p] ★ {runway: pure derivation during render versus future state management} Instead of mutating incoming props, a component that needs an altered display format calculates a new local variable during render: `const headline = title.toUpperCase();`. The component renders `{headline}` in its JSX while leaving the incoming prop completely untouched. If data must change dynamically over time in response to user events, the component does not modify props; instead, the owner component manages that value using React state (introduced in Lecture 14). ◼ Educational objective: show how to derive values pure in render and roadmap state management for dynamic data.

### Principles of React: Passing Data with Props

- [question-cycle] Question 1: Attributes on a tag become the component's one props object
    - Question: "I render three article cards and they all show the same headline. How does each get its own?"
    - Code and result: `EditorialFeed` renders three `<ArticleCard title="..." readTime={...} />` tags with different titles and times; `ArticleCard` still returns hardcoded `<h2>Night Trains Return to Europe</h2>`; all three cards display the exact same headline on screen, and the console stays silent (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: React collects all attributes written on each tag into a single JavaScript object and passes it to `ArticleCard` as its only argument; `console.log(props)` logs three distinct objects in the console; because `ArticleCard` returned hardcoded text, the incoming props were ignored; to display different headlines, the component must read the values from its props object.
    - Fix: Unpack `{ title, readTime }` in the parameter list and render `{title}`, taught in the runway section "What props are and how React passes them as a single object" and expanded in Question 2.
    - Rule: Pass differing values as attributes on the JSX tag, and read them inside the component from its props. Boundary: The attribute values belong to the parent; the child reads what the parent passes.
    - Needs: props (recall, Lecture 5), object literal (recall, Lecture 4), call site (runway), console.log (recall, Lecture 2).
    - Diagram: JSX attributes compiling into a single props object argument.

> [!PRINCIPLE]
> **Principle 1: The attributes on a tag become the component's one argument, the props**
> When you write attributes on a custom component tag in JSX, React collects them into a single **props** object. React calls your component function with that object as its only argument. Each tag gets its own props object, giving each rendered card its own values. Nothing appears on screen until the component reads from that object.
>
> >> props : a single JavaScript object collecting all attributes passed from parent to child
>
> *We should do this:*
> `function ArticleCard({ title }) {`
> `  return <h2>{title}</h2>; // reads incoming prop`
> `}`
>
> *We should not do this:*
> `function ArticleCard() {`
> `  return <h2>Night Trains Return</h2>; // ignores tag attributes`
> `}`

- [p] ★ In our feed test, rendering `<ArticleCard title="Rail Strike Ends" readTime={3} />` and `<ArticleCard title="Clean Energy Project" readTime={5} />` produces two separate calls to `ArticleCard`. Inside `ArticleCard`, adding `console.log(props)` logs `{"title":"Rail Strike Ends","readTime":3}` and `{"title":"Clean Energy Project","readTime":5}` in the browser console. When the component returned hardcoded text, both calls returned identical markup. Once the component reads from props, each card displays its own headline and reading time. ◼ Educational objective: prove Principle 1 on the lesson's code by logging props and verifying distinct object arguments.

- [question-cycle] Question 2: Unpack the props in the parameter list inside braces
    - Question: "How do I get `title` and `readTime` out of the props?"
    - Code and result: `function ArticleCard(title, readTime)` with `<h2>{title}</h2>` in JSX; React crashes with `Error: Objects are not valid as a React child (found: object with keys {title, readTime})`; writing `{ headline }` for `title=` leaves an empty heading with no error (verified in React 19.3.0).
    - Verdict: The code does not do what we wanted.
    - Answer: React passes exactly one argument to the component function: the props object; a parameter list without braces like `(title, readTime)` binds the entire object to `title` and leaves `readTime` as `undefined`; JSX throws when rendering an object; wrapping parameter names in braces `({ title, readTime })` unpacks the keys into local variables with matching names; `props.title` reads the same value.
    - Fix: Write `function ArticleCard({ title, readTime })` and render `<h2>{title}</h2>`, taught in the runway section "What props are and how React passes them as a single object".
    - Rule: Unpack props in the parameter list using curly braces matching the attribute names. Boundary: If a component only needs one or two properties, destructure them directly; to forward the entire bundle, accept `props`.
    - Needs: object destructuring (runway), object child crash (runway).
    - Diagram: Parameter destructuring unpacking properties versus raw object binding.

> [!PRINCIPLE]
> **Principle 2: Unpack the props in the parameter list, inside braces**
> React passes only one argument to a component function, the props object. Wrapping parameter names in curly braces uses **destructuring** to unpack specific properties into local variables. If you omit the braces, the first parameter receives the entire object, causing a runtime crash if rendered directly in JSX.
>
> >> destructuring : unpacking properties from an object into local variables with braces
>
> *We should do this:*
> `function ArticleCard({ title }) {`
> `  return <h2>{title}</h2>; // unpacks title property`
> `}`
>
> *We should not do this:*
> `function ArticleCard(title) {`
> `  return <h2>{title}</h2>; // crashes: objects are not valid as children`
> `}`

- [p] ★ When we write `function ArticleCard(title, readTime)`, JavaScript assigns the first argument (the props object) to `title`, while `readTime` remains `undefined`. When React evaluates `<h2>{title}</h2>`, it attempts to render a raw JavaScript object into the DOM and throws: `Error: Objects are not valid as a React child (found: object with keys {title, readTime})`. Wrapping the parameters in braces (`{ title, readTime }`) tells JavaScript to extract those exact properties into local variables. If you type `{ headline }` instead of `{ title }`, the variable receives `undefined`, and the heading renders blank without throwing an error. ◼ Educational objective: prove Principle 2 on the lesson's code by demonstrating the missing braces crash and mismatched identifier behavior.

- [question-cycle] Question 3: Pass numbers in curly braces or they arrive as strings
    - Question: "I wrote `readTime="5"`. Why does the card say `51 min`?"
    - Code and result: `<ArticleCard readTime="5" />` with `{readTime + 1} min with the summary` and `{readTime * 60} seconds`; the card displays `51 min with the summary` and `300 seconds` (verified in React 19.3.0).
    - Verdict: The code does not do what the reader expected.
    - Answer: Quoted attributes always pass string literals, so `readTime` receives the string `"5"`; in JavaScript, `"5" + 1` performs string concatenation, joining `"5"` and `"1"` into `"51"`; the multiplication `"5" * 60` coerces the string to a number and computes `300`, hiding the bug until addition occurs; curly braces evaluate live JavaScript expressions, so `readTime={5}` passes the actual number `5`.
    - Fix: Write `<ArticleCard readTime={5} />`, taught in the runway section "How JavaScript handles prop types, string concatenation, and default values".
    - Rule: Pass numbers and expressions in curly braces; reserve quotes for static strings. Boundary: Quotes are for fixed text values like `title="Rail Strike Ends"`.
    - Needs: type coercion (runway), string concatenation (runway), curly braces in JSX (recall, Lecture 4).
    - Diagram: String concatenation versus numerical addition in JavaScript.

> [!PRINCIPLE]
> **Principle 3: Pass numbers in curly braces, or they arrive as strings**
> An attribute written in quotes always passes a string literal. If your component performs addition on a quoted number, JavaScript uses **type coercion** to concatenate the values as text, turning `"5" + 1` into `"51"`. Pass numbers inside curly braces so they arrive as numbers.
>
> >> type coercion : automatic conversion of a value from one data type to another by JavaScript
>
> *We should do this:*
> `function Card() {`
> `  return <ArticleCard readTime={5} />; // passes number 5`
> `}`
>
> *We should not do this:*
> `function Card() {`
> `  return <ArticleCard readTime="5" />; // passes string '5'`
> `}`

- [p] ★ Testing both call sites reveals why this defect slips past casual checks. In the first card with `readTime="5"`, `{readTime * 60}` computes `300` because the multiplication operator coerces strings to numbers in JavaScript. However, `{readTime + 1}` outputs `51` because the plus operator prioritizes string concatenation when either operand is a string. When we change the call site to `readTime={5}`, `{readTime + 1}` evaluates to `6`, and `{readTime * 60}` evaluates to `300`. Reviewers flag quoted numbers on sight because arithmetic errors surface as soon as a feature adds numbers together. ◼ Educational objective: prove Principle 3 on the lesson's code by contrasting string concatenation with numerical addition.

- [question-cycle] Question 4: A default fills a missing prop and only a missing one
    - Question: "What if a parent leaves out `readTime`?"
    - Code and result: A card rendered with `readTime: null` against `function ArticleCard({ title, readTime = 5 })`; the card displays ` min read` because `null` passes through unchanged; with missing or `undefined`, the card displays `5 min read`; with `0`, it displays `0 min read` (verified in React 19.3.0).
    - Verdict: The code does not do what the reader wanted.
    - Answer: When an attribute is omitted or passed as `undefined`, JavaScript assigns the default parameter `readTime = 5`; but JavaScript default parameters do not trigger for `null` or `0`; `null` is a valid object representing intentional absence, so it passes into the component, and JSX renders nothing for `null`, leaving an empty space; writing `readTime || 5` replaces `0` because `0` is falsy; writing `readTime ?? 5` fills `null` and `undefined` while preserving `0`.
    - Fix: Use `const time = readTime ?? 5` during render when data may contain `null`, taught in the runway section "How JavaScript handles prop types, string concatenation, and default values".
    - Rule: Use default parameters after `=` to fill missing or `undefined` props. Boundary: When incoming data can hold `null`, use the nullish coalescing operator `??` during render; never use `||` because it replaces valid `0` values.
    - Needs: default parameter value (runway), nullish coalescing (runway), logical OR (runway), null and undefined (recall, Lecture 4).
    - Diagram: Default parameter evaluation across undefined, null, and zero.

> [!PRINCIPLE]
> **Principle 4: A default fills a missing prop, and only a missing one**
> An assignment after `=` sets a **default parameter** that fills in when a prop is missing or `undefined`. A default parameter does not replace `null` or `0`. When data can hold `null`, compute a fallback with `??` during render, and avoid `||` because it overwrites valid zero values.
>
> >> default parameter : a fallback value assigned when an incoming argument is undefined
>
> *We should do this:*
> `function ArticleCard({ readTime = 5 }) {`
> `  return <p>{readTime} min</p>; // fills missing or undefined`
> `}`
>
> *We should not do this:*
> `function ArticleCard({ readTime }) {`
> `  return <p>{readTime || 5} min</p>; // overrides valid 0 with 5`
> `}`

- [p] ★ We test four cards against `readTime = 5`: an omitted prop displays `5 min read`, `readTime={undefined}` displays `5 min read`, `readTime={0}` displays `0 min read`, and `readTime={null}` displays ` min read`. Because `null` passes through default parameters, the label renders blank. When developers attempt to fix this with `readTime || 5`, passing `0` produces `5 min read`, corrupting valid zero-minute reads. Replacing the expression with `readTime ?? 5` preserves `0 min read` for zero while supplying `5 min read` for both `null` and `undefined`. ◼ Educational objective: prove Principle 4 on the lesson's code by testing undefined, null, and zero across default parameters, logical OR, and nullish coalescing.

- [question-cycle] Question 5: Props are read-only so make a new variable instead

> [!PRINCIPLE]
> **Principle 5: Props are read-only, so make a new variable instead**
> Props belong to the parent component and are strictly read-only. A direct **mutation** like `props.title = ...` corrupts data across the component tree. In development, React freezes props so an assignment throws an error. When you need an altered form of a prop, calculate a new variable during render.
>
> >> mutation : modifying the properties of an existing object directly in memory
>
> *We should do this:*
> `function ArticleCard({ title }) {`
> `  const headline = title.toUpperCase(); // pure local derivation`
> `  return <h2>{headline}</h2>;`
> `}`
>
> *We should not do this:*
> `function ArticleCard(props) {`
> `  props.title = props.title.toUpperCase(); // crashes: mutating frozen props`
> `}`

- [p] ★ In our development server, running `props.title = props.title.toUpperCase()` immediately halts execution with a fatal `TypeError` because React ran `Object.freeze()` on the props object. In a production build, `Object.isFrozen(props)` evaluates to `false`, allowing the mutation to proceed without error. Furthermore, when `article` is passed as an object prop, mutating `article.title = article.title.toUpperCase()` succeeds in both development and production because `Object.freeze()` is shallow. A sidebar component displaying the same article object suddenly renders uppercase titles as well, causing severe state drift. Calculating `const headline = title.toUpperCase()` during render protects the parent's data and keeps sibling components completely isolated. ◼ Educational objective: prove Principle 5 on the lesson's code by verifying development TypeError crashes, production silent execution, and nested object corruption.

### Let's Design a Practical Example

- [p] ◇ To solidify our understanding of props, parameter destructuring, fallback defaults, and the immutability contract, we construct a modular article feed for an editorial publication. ### For the interview

> **The Interview Question:** How do you pass data into a component, and why can a component never change its own props?

**1. The Hidden Signal**

The interviewer is testing your grasp of React's component execution model, unidirectional data flow, functional purity, and JavaScript runtime mechanics. A junior candidate says props are "passed like HTML attributes." A senior engineer explains that JSX attributes bundle into a single frozen object passed as the sole argument to the component function, and that props must remain immutable because components must be pure functions with respect to their inputs. Mutating props destroys pure render guarantees, breaks memoization, and causes parent-child state drift across sibling elements.

**2. The Classic Trap**

The classic trap is assuming that props behave like regular mutable JavaScript function arguments, or attempting to write `props.title = props.title.toUpperCase()` to clean up display text. Candidates often fail to realize that React freezes props in development, causing fatal `TypeError` crashes in strict mode. Another frequent trap is forgetting destructuring braces (`function Card(title)` instead of `function Card({ title })`), which binds the entire props object to the first parameter and crashes with `Objects are not valid as a React child` when rendered.

**3. What is Actually Going On**

Under the hood, the JSX compiler translates component tags into `_jsx(Component, propsObject)`. React instantiates the props object, calls `Object.freeze()` on it in development, and passes it to the component. Because ES modules execute in JavaScript strict mode, any attempt to assign a property on a frozen object throws a runtime `TypeError`. In production builds, React skips `Object.freeze()` to optimize performance, meaning mutations succeed silently in production while failing in development. Furthermore, `Object.freeze()` is shallow: mutating nested object properties succeeds in all environments, corrupting shared memory in the parent and across sibling components.

**4. Where It Gets Tricky**

Where this gets tricky in production is handling optional props and fallback values. While default parameter syntax (`{ readTime = 5 }`) cleanly fills in for missing or `undefined` props, it does not trigger for `null` or `0`. If an API returns `null` for an uncalculated field, default parameters leave the value as `null`, rendering an empty slot. Using logical OR (`readTime || 5`) replaces valid `0` values because `0` is falsy. Senior engineers use nullish coalescing (`readTime ?? 5`) during render to preserve valid zeros while providing resilient fallbacks. When data must change over time, state management (Lecture 14) is used instead of prop mutation.

### Glossary

- **Props**: The single read-only JavaScript object containing all attributes passed from a parent component to a child component.
- **Object Destructuring**: The JavaScript syntax using curly braces to unpack specific properties from an object into local variables within a parameter list.
- **Type Coercion**: The automatic conversion of values from one data type to another by JavaScript, such as concatenating numbers as strings during addition.
- **Default Parameter**: A fallback value specified in a function parameter list that assigns automatically when an incoming argument is missing or undefined.
- **Mutation**: The direct modification of an existing object's properties in memory, strictly forbidden on props in React.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Prop Passing and Parameter Destructuring

➔ IF passing data to a child component, THEN write attributes on the custom component tag at the JSX call site.

➔ IF unpacking incoming props, THEN wrap parameter names in curly braces matching attribute names to avoid raw object binding crashes.

❒ Prop Types and Fallback Defaults

➔ IF passing numbers, booleans, or JavaScript expressions, THEN wrap values in curly braces to prevent string type coercion bugs.

➔ IF specifying fallback values for optional props, THEN assign default parameters after `=` in destructuring, using `??` during render if data can contain null.

❒ Immutability Contract and Component Purity

➔ IF formatting or altering incoming prop values for display, THEN calculate a new local variable during render rather than mutating props.

➔ IF data must change dynamically over time in response to user input, THEN manage that data in state rather than modifying props.

**DO THIS:** Unpack props with destructuring, pass numbers in braces, and calculate derived values pure in render

```jsx right
function ArticleCard({ title, readTime = 5 }) {
  const badge = `${readTime} MIN READ`;
  return (
    <article className="card">
      <span>{badge}</span>
      <h2>{title}</h2>
    </article>
  );
}
```

**DO NOT DO THIS:** Omit destructuring braces, pass numbers in quotes, or mutate frozen props directly

```jsx wrong
function ArticleCard(props) {
  props.title = props.title.toUpperCase();
  return (
    <article className="card">
      <h2>{props.title}</h2>
      <p>{props.readTime + 1}</p>
    </article>
  );
}
```
