### Every web page needs to branch its markup

- [p] ◇ {theme: the universal need for branching} Every web page needs to adapt its markup to changing data. A shop shows an 'Out of Stock' note when an item count reaches zero. An article shows an urgent alert when news breaks. A discussion section hides comments when they are turned off. In static HTML, all content is permanent and unchanging. In modern applications, data changes constantly based on user actions and server responses. A developer needs a reliable way to show different elements, switch between two options, or render nothing at all. ◼ Educational objective: introduce the universal engineering reality of conditional user interfaces.

- [p] ◇ {starting point: imperative DOM manipulation vs declarative React} In plain JavaScript, developers changed visibility by searching the page with `document.getElementById`. They added a CSS class like `hidden`, or set `style.display = 'none'`. That approach tells the browser what commands to run step by step. In React, a component is a function. It returns a description of what the user interface should look like for the current props. You never search the page or toggle classes on DOM nodes yourself. Instead, you write plain JavaScript control flow directly in your component to return the JSX for each case. React compares that description to the page and creates, updates, or removes real DOM nodes to match. ◼ Educational objective: contrast imperative DOM queries with declarative React component rendering.

- [p] ◇ {core questions} This chapter answers five core questions. **How does React show or hide elements without manual DOM queries?** **How do you protect a component from crashing when data is missing?** **When should you use a ternary operator instead of logical AND?** **Why does a count of zero print a stray zero on the screen?** **How do you organize complex branching without nesting ternaries inside JSX?** ◼ Educational objective: outline the five roadmap questions.

- [p] ◇ {preview: rendering lists of items} Later in this track, Lecture 11 shows how to render lists of items from arrays. It uses `{tags.length > 0 && <ul>{tags.map(...)}</ul>}` to guard against empty collections. ◼ Educational objective: provide a forward preview for Lecture 11 without teaching lists here.

- [recall] Lecture 3 (JSX is JavaScript) ◼ JSX elements are plain JavaScript object descriptions that React turns into living browser DOM nodes.
- [recall] Lecture 4 (JSX expressions) ◼ Braces inside JSX hold expressions, not statements. Inside braces, booleans, null, and undefined print nothing, while numbers and strings print directly to the screen.
- [recall] Lecture 6 (Passing props) ◼ A parent passes values down to children as props. Quoted strings pass text, while curly braces pass numbers, booleans, and variables.

### How JavaScript evaluates conditions, operators, and falsy values

- [runway] JavaScript expression evaluation and falsy value semantics, used by Question 3, Question 4, and Question 5.

- [p] ★ {preknowledge: statements versus expressions} In Lecture 4, we learned that curly braces inside JSX open a window where JavaScript evaluates code. However, JavaScript strictly separates **statements** from **expressions**. An expression produces a single value that can be passed to a function or assigned to a variable, such as `2 + 2` or `user.name`. A statement performs an action or controls program flow, such as an `if` block, a `for` loop, or a variable declaration. Because JSX tags compile into function calls, you cannot place an `if` statement directly inside JSX curly braces. For inline branching inside JSX markup, you must use JavaScript expressions. ◼ Educational objective: explain the grammatical difference between expressions and statements in JSX.

- [p] ★ {mechanism: ternary operator syntax} The **ternary operator** (`? :`) is an inline JavaScript expression that takes three operands. First comes a condition, followed by a question mark (`?`), an expression to evaluate if the condition is truthy, a colon (`:`), and an expression to evaluate if the condition is falsy. For example, `isLive ? <LiveBadge /> : <StaticDate />` checks `isLive`. If `isLive` is true, the expression evaluates to `<LiveBadge />`. If `isLive` is false, it evaluates to `<StaticDate />`. Because the whole ternary evaluates to a single value, it fits cleanly inside JSX curly braces. ◼ Educational objective: teach the ternary operator syntax and explain its fit for binary choices.

- [p] ★ {mechanism: logical AND operator short-circuiting} The **logical AND operator** (`&&`) evaluates expressions from left to right using **short-circuit evaluation**. If the left side is falsy, JavaScript stops immediately and returns that exact left-hand value without evaluating the right side. If the left side is truthy, JavaScript evaluates and returns the right side. For example, in `isUrgent && <AlertBadge />`, if `isUrgent` is `true`, JavaScript evaluates and returns `<AlertBadge />`. If `isUrgent` is `false`, JavaScript stops and returns `false`. ◼ Educational objective: explain logical AND short-circuit evaluation.

- [p] ★ {mechanism: truthy and falsy values in JavaScript} In JavaScript, values are either **truthy** or **falsy** when tested in a boolean condition. There are six primary falsy values: `false`, `null`, `undefined`, `0`, `NaN`, and the empty string `""`. All other values are truthy, including non-empty strings like `"false"`, objects, and empty arrays `[]`. Because an empty array is truthy, testing `tags && <TagList />` evaluates to true even when `tags` has no items. Testing `tags.length > 0` produces an explicit boolean comparison using `>` that evaluates to `false` when the list is empty. ◼ Educational objective: define truthy and falsy values and show why length checks are required.

- [code] JavaScript conditional operators in action:

```jsx title="Expressions.jsx"
const alert = isUrgent ? <Alert /> : <Normal />; // Ternary picks one of two
const badge = isLive && <LiveBadge />;
const hasTags = tags.length > 0; // Explicit boolean comparison
```

◼ **The what-this-introduces list:** 1. `? :`: ternary operator picking one of two expressions. 2. `&&`: logical AND operator returning right operand when left is truthy. 3. `tags.length > 0`: comparison operator producing a boolean.

### Why React leaves omitted elements out of the browser DOM

- [runway] Component render execution and DOM element omission, used by Question 1 and Question 2.

- [p] ★ {preknowledge: how React processes JSX during render} When React runs a component function, the browser DOM has not been updated yet. The component executes in JavaScript memory to produce a tree of React elements. If a component attempts to find its own markup using `document.getElementById('comments')`, the browser method returns `null` because that element is not in the page yet. Attempting to call `.classList.add('hidden')` on `null` throws an unhandled `TypeError` that halts execution and causes the whole page to go blank. ◼ Educational objective: explain why imperative DOM queries fail during component render execution.

- [p] ★ {mechanism: declarative DOM omission versus CSS hiding} In plain HTML, setting `style={{ display: 'none' }}` hides an element visually, but the physical HTML element remains in the browser DOM and accessibility tree, consuming memory and confusing screen readers. In React, conditional rendering uses **DOM omission**: when a condition is false, the component simply does not include that JSX element in its return value. React compares the returned tree against the real page and removes the corresponding node completely, or never creates it in the first place. ◼ Educational objective: contrast CSS hiding with genuine DOM element omission.

- [p] ★ {mechanism: early returns and property access crashes} When a component receives data through props, that data may be uninitialized or missing. In JavaScript, reading a property on `undefined`, such as `article.title` when `article` is `undefined`, throws a fatal `TypeError: Cannot read properties of undefined (reading 'title')`. In React, an unhandled error during render unmounts the component tree, blanking the application. An **early return** checks for missing data at the very top of the function: `if (!article) return null;`. When a component returns `null`, React renders nothing for that component while leaving the rest of the application intact on screen. ◼ Educational objective: explain defensive early returns with null and contrast them with unhandled property crashes.

- [code] Defensive Early Return Pattern:

```jsx title="StoryHeader.jsx"
export default function StoryHeader({ article }) {
  if (!article) {
    return null; // Exits early before reading missing data
  }
  return <h1>{article.title}</h1>; // Safe property access
}
```

◼ **The what-this-introduces list:** 1. `if (!article) return null`: early return exiting before reading fields. 2. `return null`: tells React to render zero DOM nodes. 3. `article.title`: safe property access guarded by the early return.

### Principles of React: Conditional Rendering

- [question-cycle] Question 1: Calling classList in render throws an error
    - Question: "How do I hide the comments when they are turned off? Do I find the element and hide it?"
    - Code and result: Inside `ArticleHeader`, the developer writes `if (!commentsEnabled) document.getElementById('comments').classList.add('hidden');`. During render, the console logs: `TypeError: Cannot read properties of null (reading 'classList')`, and the whole page goes blank.
    - Verdict: does not do what the reader wanted.
    - Answer: While a component function runs, React is calculating element descriptions in memory. The element has not been mounted to the page yet, so `document.getElementById('comments')` returns `null`. Calling `.classList.add()` on `null` throws a fatal `TypeError` that stops rendering and clears the page. In React, a component does not search or mutate DOM nodes directly. Instead, it branches with plain JavaScript and returns the JSX descriptions for the current case, such as `{commentsEnabled && <CommentList />}`. React inspects the returned JSX and creates or removes real DOM nodes to match. When an element is hidden with CSS (`display: 'none'`), the node remains in the DOM and accessibility tree; when JSX omits it, React creates no DOM node at all.
    - Fix: Return the JSX description for the case using `{commentsEnabled && <CommentList />}` without querying the DOM. Taught in runway "Why React leaves omitted elements out of the browser DOM".
    - Rule with boundary: Return the JSX for the case from your component and let React add or remove DOM nodes. Never query or mutate the DOM directly inside a component.
    - Needs: `classList` (runway), `display: none` (runway), `TypeError` (runway), DOM omission (runway), JSX descriptions (recall, Lecture 3).
    - Diagram: ASCII diagram comparing imperative DOM query (returns null, throws) vs declarative JSX branching (React creates or omits node).

> [!PRINCIPLE]
> **Principle 1: Return the JSX for the case, and let React add or remove the DOM**
> When a component runs, its elements are not in the browser page yet. Searching the document with getElementById finds null, so calling classList throws an error and blanks the page. In React, a component is a function that returns the JSX for the current case. When the JSX includes an element, React creates the DOM node; when the JSX leaves it out, React performs **DOM omission** and creates no node at all.
>
> >> DOM omission : completely leaving an element out of the rendered DOM tree
>
> *We should do this:*
> `function Card({ showDetails }) {`
> `  return <div>{showDetails && <p>Details</p>}</div>; // adds or omits node`
> `}`
>
> *We should not do this:*
> `function Card({ showDetails }) {`
> `  const el = document.getElementById('details');`
> `  el.classList.add('hidden'); // throws on null`
> `  return <div id="details"><p>Details</p></div>;`
> `}`

- [question-cycle] Question 2: Reading properties on missing data blanks the page
    - Question: "The article has not arrived yet. Why is the whole page blank?"
    - Code and result: `ArticleHeader({ article })` runs with `article` as `undefined`, and reads `<h1>{article.title}</h1>`. The browser console logs: `TypeError: Cannot read properties of undefined (reading 'title')`, and every element on the page disappears.
    - Verdict: does not do what the reader wanted.
    - Answer: In Lecture 4, we saw that rendering `{undefined}` alone prints nothing. But reading a property on `undefined`, like `article.title`, is an unhandled JavaScript error that throws an exception. This exception halts rendering and unmounts the application. An early return at the top of the component, `if (!article) return null;`, checks for missing data before any property read occurs. When a component returns `null`, React renders zero DOM nodes for that component, keeping the rest of the application safe and visible on screen. If desired, the component can return fallback placeholder markup like `<p>Loading story...</p>`. When the parent component knows the data is missing, it can omit the child in JSX instead.
    - Fix: Add an early return guard `if (!article) return null;` at the top of the component before reading any properties. Taught in runway "Why React leaves omitted elements out of the browser DOM".
    - Rule with boundary: Guard missing data with an early return before reading any fields. Boundary: when the parent knows the data is missing, the parent can guard or leave the child element out in JSX.
    - Needs: early return (runway), `null` renders nothing (recall, Lecture 4), `TypeError` on property read of undefined (runway).
    - Diagram: ASCII diagram comparing unguarded property read (`article.title` throws, blanks screen) vs early return (`if (!article) return null;` returns empty slot, rest of page stays).

> [!PRINCIPLE]
> **Principle 2: Guard missing data with an early return**
> When a component needs data from a prop, check that the data exists at the start of the function. Reading a property on undefined throws a TypeError that stops rendering and clears the page. Returning **null** or placeholder markup before reading any property lets React finish rendering the rest of the application. When the parent component knows the data is missing, it can omit the child in JSX instead.
>
> >> early return : returning from a component function before reaching the main JSX return
>
> *We should do this:*
> `function Header({ item }) {`
> `  if (!item) return null; // guards before reading property`
> `  return <h1>{item.title}</h1>;`
> `}`
>
> *We should not do this:*
> `function Header({ item }) {`
> `  return <h1>{item.title}</h1>; // throws TypeError on missing item`
> `}`

- [question-cycle] Question 3: Choosing between a ternary and logical AND
    - Question: "Do I use a ternary or &&?"
    - Code and result: In `ArticleHeader`, the reader writes `{isLive ? <LiveBadge /> : <StaticDate />}` to pick between two outputs, and `{isUrgent && <AlertBadge />}` to show a badge or nothing. Both work cleanly.
    - Verdict: works.
    - Answer: A ternary operator `cond ? <A /> : <B />` evaluates to one of two expressions, making it the right tool when you must choose between two visible elements. The logical AND operator `cond && <A />` evaluates to `<A />` when `cond` is true, and to `false` when `cond` is false. Because React renders nothing for `false`, `&&` is the right tool to show an element or nothing at all. Using two inverted `&&` expressions (`{isLive && <A />}{!isLive && <B />}`) duplicates the condition and causes bugs when conditions drift. When both branches share common wrapper markup, branch only the inner part that differs, such as `className={'card ' + (isUrgent ? 'urgent' : '')}`.
    - Fix: none.
    - Rule with boundary: Use a ternary (`? :`) to pick between two outputs, and logical AND (`&&`) to show one output or nothing. When branches share common markup, branch only the changing part. Boundary: when branching exceeds one clean expression or has many cases, move branching above `return` (Principle 5).
    - Needs: ternary operator (recall, Lecture 4), logical AND (runway), string concatenation with `+` (recall, Lecture 4).
    - Diagram: ASCII diagram contrasting binary choice (ternary selects Branch A or Branch B) vs show-or-nothing (`&&` returns element or false).

> [!PRINCIPLE]
> **Principle 3: A ternary picks one of two, and && shows one or nothing**
> Use the ternary operator to choose between two different elements, and use logical AND to show one element or nothing. In JSX, a **ternary operator** evaluates to one of its two branches. The **logical AND** operator evaluates to its right-hand element when true, and to false when false, which React leaves out of the page. When two branches share common markup, branch only the piece that changes.
>
> >> ternary operator : an inline operator that evaluates a condition and chooses between two values
> >> logical AND : an operator that evaluates to the right side when the left side is truthy
>
> *We should do this:*
> `{isLive ? <LiveBadge /> : <StaticDate />} // chooses one of two`
> `{isUrgent && <AlertBadge />} // shows badge or nothing`

- [question-cycle] Question 4: An unread counter of 0 prints a raw 0 on screen
    - Question: "Why is there a 0 on the card?"
    - Code and result: In `ArticleHeader`, the developer writes `{commentCount && <CommentBadge count={commentCount} />}`. When a story has `0` comments, the screen displays an unexpected, raw `"0"` beneath the title.
    - Verdict: does not do what the reader wanted.
    - Answer: In JavaScript, `&&` short-circuits and returns its left side whenever that side is falsy. When `commentCount` is `0`, JavaScript evaluates `0 && <CommentBadge />` to `0`, not `false`. React suppresses booleans (`false`, `true`), `null`, and `undefined`, but it treats numbers as visible user content and renders them as real DOM text nodes. As a result, React creates a text node containing `"0"` and paints it directly on the screen. The exact same issue happens with `NaN`, which renders `"NaN"` on screen with a console warning. Non-empty strings like `"false"` and empty arrays `[]` are truthy in JavaScript, so `isUrgent="false"` and `tags && <TagList />` both display their elements. To prevent this, always put an explicit boolean comparison on the left side of `&&`, such as `commentCount > 0 && <CommentBadge />` or `tags.length > 0 && <TagList />`.
    - Fix: Use an explicit boolean comparison: `{commentCount > 0 && <CommentBadge count={commentCount} />}`. Taught in runway "How JavaScript evaluates conditions, operators, and falsy values".
    - Rule with boundary: Always place an explicit boolean comparison on the left side of `&&`, never a raw number. Boundary: strings and arrays must also be tested as booleans (`tags.length > 0`).
    - Needs: truthy and falsy values (runway), comparison operators `>` and `===` (runway), `NaN` (recall, Lecture 4), quoted string props (recall, Lecture 6), arrays (recall, Lecture 4).
    - Diagram: ASCII diagram tracing `0 && <Badge />` (evaluates to 0 -> renders text node "0") vs `0 > 0 && <Badge />` (evaluates to false -> renders nothing).

> [!PRINCIPLE]
> **Principle 4: Put a boolean on the left of &&, never a number**
> The logical AND operator returns its left side whenever that side is falsy. In JavaScript, 0 is falsy, so 0 on the left evaluates to the number 0. React leaves booleans, null, and undefined out of the page, but it renders numbers as visible text. A condition with 0 prints a **stray zero** on the screen. Compare numbers with zero using a comparison operator so the left side is always a real boolean.
>
> >> stray zero : an unwanted 0 displayed on screen when a numeric zero short-circuits in JSX
>
> *We should do this:*
> `function Card({ count }) {`
> `  const show = count > 0; // explicit boolean`
> `  return <div>{show && <Badge count={count} />}</div>;`
> `}`
>
> *We should not do this:*
> `function Card({ count }) {`
> `  return <div>{count && <Badge count={count} />}</div>; // prints 0`
> `}`

- [question-cycle] Question 5: Branching across multiple states nests ternaries
    - Question: "The header has five cases. Do I nest ternaries?"
    - Code and result: Inside JSX, the reader nests multiple ternaries: `{isUrgent ? <Alert /> : isLive ? <Live /> : isDraft ? <Draft /> : null}`. The code runs and displays the correct badge, but code reviewers flag it as unreadable and fragile.
    - Verdict: works.
    - Answer: Curly braces inside JSX hold only a single expression, so handling several cases inline forces you to nest ternaries. Chained ternaries are hard to read and easy to break when adding new states. Because JSX elements are plain JavaScript objects in memory, you can move branching above the `return` statement using standard `let` variables and `if/else` statements. You assign the calculated JSX element to a local variable like `let badge = null;`, and then place `{badge}` once inside the returned markup.
    - Fix: none (code works, but prefer variable assignment before `return`).
    - Rule with boundary: Move complex branching above the `return` statement into standard `if` statements and a variable holding JSX. Boundary: short, single-case ternaries or `&&` expressions stay inline inside JSX.
    - Needs: statements vs expressions (recall, Lecture 4), local variables `const` and `let` (recall, Lecture 1).
    - Diagram: ASCII diagram comparing nested inline ternaries vs clean variable extraction above `return`.

> [!PRINCIPLE]
> **Principle 5: Move complex branching above the return**
> Braces inside JSX hold a single expression, so handling several cases inline creates nested ternaries that are hard to read. Move multi-case branching above the return statement using standard if statements and a **local variable**. Assign the chosen JSX element to that variable, and place the variable inside your markup once. Simple binary choices and short show-or-nothing checks stay inline.
>
> >> local variable : a variable declared with let or const inside the component function
>
> *It is best practice to do this:*
> `let badge = null;`
> `if (isUrgent) badge = <AlertBadge />;`
> `else if (isLive) badge = <LiveBadge />;`
> `return <header>{badge}<h1>{title}</h1></header>; // clean placement`

```jsx title="LiveIndicator.jsx"
    </span>
  );
}
```

### For the interview

- [interview] The Interview Question Callout:
> **The Interview Question:** How do you show, hide, or switch JSX based on a condition?

- [interview] 1. The Hidden Signal:
The interviewer is not asking whether you know the syntax of an if statement or a question mark. They are probing whether you understand how React manages the browser DOM declaratively. A junior candidate talks about toggling CSS classes with document queries. A senior engineer explains that components are pure functions of props and state: React renders what the returned JSX describes, and omits what the JSX leaves out. They immediately highlight the difference between expressions and statements inside JSX braces, explain how React treats falsy values, and address the stray zero trap.

- [interview] 2. The Classic Trap:
The most famous trap is writing `{count && <Badge />}` with a numeric zero. Candidates assume that because 0 is falsy in JavaScript, React will render nothing. But in JavaScript, `0 && <Component />` returns `0`. React suppresses booleans, null, and undefined, but it treats numbers as visible user content and renders a literal "0" onto the physical screen. Another classic trap is using two separate inverted `&&` expressions (`{isLive && <A />}` and `{!isLive && <B />}`) to simulate an if/else branch, which duplicates the condition and causes visual desynchronization when conditions drift.

- [interview] 3. What is Actually Going On:
In React, conditional rendering uses standard JavaScript control flow. Braces inside JSX open an expression window, so an `if` statement cannot live directly inside markup. For a binary choice between two elements, use a ternary: `{isLive ? <LiveBadge /> : <StaticDate />}`. For a show-or-nothing element, use logical AND: `{isUrgent && <AlertBadge />}`.
When a condition evaluates to false, React leaves that element out of the tree entirely; it produces zero DOM nodes, meaning the element is never created in the browser page. When data may be uninitialized, place an early return `if (!data) return null;` at the top of the component to prevent property read crashes. When logic has three or more cases, move branching above the `return` statement into standard `if` statements and a `let` variable.

- [interview] 4. Where It Gets Tricky:
*What happens if you pass a quoted string like `isUrgent="false"` to a component?*
In JavaScript, all non-empty strings are truthy. Writing `isUrgent="false"` passes the literal string `"false"`, so `{isUrgent && <Alert />}` evaluates to true and shows the alert. To pass a real boolean, you must use curly braces: `isUrgent={false}`.
*What happens if an uninitialized calculation produces NaN?*
In JavaScript, `NaN` is falsy. But like `0`, `NaN && <Component />` returns `NaN`. React prints `"NaN"` directly onto the screen and logs a console warning. Always guard calculations with `!Number.isNaN(val) && val > 0`.
*What happens if you check an empty array with `tags && <TagList />`?*
In JavaScript, an empty array `[]` is an object, and all objects are truthy. Even with zero items, `tags && <TagList />` evaluates to true, mounting `<TagList />` with an empty collection. Always check length: `tags.length > 0 && <TagList />`.

### Glossary

- [glossary] **Conditional Rendering** ◼ The technique of displaying, hiding, or alternating user interface markup based on JavaScript conditions and props.
- [glossary] **Early Return** ◼ Exiting a component function early with null or fallback markup before executing the main JSX return.
- [glossary] **Ternary Operator** ◼ A JavaScript inline operator (`? :`) that evaluates a condition and chooses between two alternative expressions.
- [glossary] **Short-Circuit Evaluation** ◼ The evaluation model where logical AND (`&&`) stops and returns the left operand immediately if it is falsy.
- [glossary] **Suppression Whitelist** ◼ React's built-in rule that renders zero DOM nodes for booleans (`true`, `false`), `null`, and `undefined`.
- [glossary] **Stray Zero** ◼ An unwanted 0 displayed on the screen when a numeric zero short-circuits on the left side of logical AND.

### Summary

- [review-title] **Architectural Takeaways & Decision Matrix**

- [review-subtitle] ❒ Operator Selection & Branch Shape

- [always-rule] ➔ ALWAYS use logical AND (`&&`) for show-or-nothing branches, and use the ternary operator (`? :`) when choosing between two alternate elements.

- [never-rule] ➔ NEVER use two separate inverted `&&` expressions (`{isLive && ...}{!isLive && ...}`) to simulate an if/else choice.

- [review-subtitle] ❒ Numeric Guarding & Falsy Safety

- [always-rule] ➔ ALWAYS convert numbers to explicit booleans (`count > 0 && ...`) before using the `&&` operator to prevent the stray zero bug.

- [never-rule] ➔ NEVER place a raw numeric counter or unverified calculation on the left side of `&&`.

- [review-subtitle] ❒ Complexity Management & DOM Ownership

- [if-then-rule] ➔ IF branching logic exceeds one clean expression THEN move the calculation before the `return` statement using standard `if` statements and a variable.

- [never-rule] ➔ NEVER manipulate CSS classes or styles imperatively using `classList` on DOM elements managed by React.

**DO THIS:** guard numeric values with explicit boolean comparisons

```jsx right
{commentCount > 0 && (
  <span className="comments">{commentCount} Comments</span>
)}
```

**DO NOT DO THIS:** pass raw numeric counters to logical AND operators

```jsx wrong
{commentCount && (
  <span className="comments">{commentCount} Comments</span>
)}
```
