### The button asks for three tickets, but the screen adds one

- [p] ★ {preknowledge: `useState`, setter functions, snapshots, Lecture 14 and Lecture 16} In Lecture 14 we stored component data in state. When a customer books concert seats, adding multiple items should increment the order total predictably. ◼ Educational objective: recall earlier state fundamentals; introduce order booking feature.
- [p] ★ {problem: calling the setter three times only increments by one} In plain JavaScript, adding one to a variable three times increases it by three. In React, calling a setter three times in a row produces a surprise: the number advances by only one. We write `setTickets(tickets + 1)` three times in the same click handler. We also call `setStatus('Updated')` and log a message to the console. When we click "+3 Tickets", the screen updates to 1 instead of 3. The console shows `handler done`, followed by a single render log. ◼ Educational objective: establish the concrete runtime symptom where three calls result in one increment.

### How React groups updates and walks the queue

- [p] ◇ {conceptual grounding: batching and the restaurant waiter} In traditional DOM programming, modifying three elements forces the browser engine to recalculate layout and repaint three separate times. React prevents this waste by waiting until all code in the event handler has finished running. Then it renders the component once for all setter calls made during that event. This grouping behavior is called **batching**. Think of a restaurant waiter taking an order at your table. A waiter does not run to the kitchen after every single dish you name. The waiter listens until you finish your whole order. Then they deliver the complete ticket to the kitchen once. Batching lets your application update multiple state variables without triggering wasteful intermediate renders. React does not batch across separate clicks, so each user click gets its own independent render. ◼ Educational objective: introduce batching using the classic waiter metaphor; explain performance and visual consistency benefits.
- [p] ◇ {mechanism: the update queue} When you call a setter function, React does not modify state on that line. Instead, React places an instruction into an internal **update queue**. During the next render, React walks through this queue in order, starting from the current state. If an entry is a plain value, React replaces the running total with that value. If an entry is an **updater function**, React calls that function with the running total. ◼ Educational objective: define the update queue and distinguish plain values from updater functions.
- [p] ★ {tracing mixed queues} React applies queued instructions with strict sequential order. Suppose we call `setTickets(tickets + 5)` and then `setTickets(t => t + 1)` from 0. The queue sets the total to 5 and then adds 1. The screen displays 6. Appending `setTickets(42)` overwrites that result, leaving 42. Calling `setTickets(5)` works exactly like `setTickets(t => 5)` where the argument is ignored. ◼ Educational objective: explain mixed queues and prove that plain setters act as constant functions.

Lecture 13 showed that functions are passed to event handlers. Lecture 14 introduced `useState`, and Lecture 15 proved that rendering occurs after handlers finish. Lecture 16 taught that state is a snapshot fixed for the entire render. Looking ahead, Lecture 18 will use updaters to update nested objects safely. Lecture 46 will examine why `StrictMode` invokes functions twice in development. ◼ Educational objective: anchor prerequisite mechanics and preview upcoming lessons.

- [code] Mixed queue execution (verified in React 19.3.0: renders 6, then 42):

```jsx title="TicketOrder.jsx, mixed queues" startLine="6"
  function handleMixedQueue() {
    setTickets(tickets + 5); // queues replace with 5

```

### Principles of React: Batching and Updater Functions

- [p] ◇ Interviewers ask this question to verify understanding of batching and the update queue. The first principle explains batching across event handlers. The second principle shows how React walks the queue in order. The third principle identifies when an updater function is necessary. The fourth principle enforces updater purity. ◼ Educational objective: frame the four principles clearly.

- [principle-notes] Principle 1: The reader expects calling setters four times to trigger four separate renders. What actually happens: React batches all setter calls in the event handler and renders once after the handler finishes. Move from casebook Case 1: state the reader's expectation, show that React waits for the whole handler, and explain why one render follows. Real Mistake is none, so the box carries a single right card.

> [!PRINCIPLE]
> **Principle 1: React updates the screen once after the whole click handler runs**
> When a click handler calls several setters, React does not update the screen after each call. Instead, it waits until all code in the handler finishes running. Then it runs the component once, using all the updates from that click. This behavior is called **batching**. A separate click is its own event, and React runs the component again for that second click.
>
> *We should do this:*
> `function handleClick() {`
> `  setCount(count + 1); // queues first update`
> `  setNote('Saved'); // queues second update`
> `} // React runs the component once after this line`

- [p] ★ In the `TicketOrder` component, the click handler calls `setTickets(tickets + 1)` three times and `setStatus('Updated')` once. Even with four setter calls, `TicketOrder` runs only once after the click. In the development console, we see `handler done` first. Then the component logs `render tickets = 1 status = Updated` a single time. When a customer clicks a second time, that click forms an independent event. In that second run, the handler sees `tickets = 1`, and one more render follows. Lecture 15 showed that React renders after the handler, and batching explains why all calls share that render. ◼ Educational objective: prove Principle 1 on the lesson's feature with verified console logs.

- [principle-notes] Principle 2: The reader expects three increment calls to increase the ticket count by three. What actually happens: each call evaluates the constant snapshot 0, queueing "replace with 1" three times. Walking the queue in order produces 1. Move from casebook Case 1 and Case 2: state the reader's expectation, show how React walks the queue, and contrast plain values against updater functions. Real Mistake is calling setCount(count + 1) three times.

> [!PRINCIPLE]
> **Principle 2: React applies queued updates in order, replacing values and running functions**
> When you call a setter, React adds an instruction to an internal **update queue**. During the next run of the component, React walks through that queue in order, starting from the current value. A plain value replaces the running total with that number. An **updater function** receives the running total and returns the next value. Three calls with plain values replace the total three times with the same number.
>
> *We should do this:*
> `setCount(c => c + 1); // queues updater function`
> `setCount(c => c + 1); // receives running result from previous call`
> `setCount(c => c + 1); // advances count by three`
>
> *We should not do this:*
> `setCount(count + 1); // queues replace with 0 + 1`
> `setCount(count + 1); // queues replace with 0 + 1 again`
> `setCount(count + 1); // screen shows 1 instead of 3`

- [p] ★ In `TicketOrder`, calling `setTickets(tickets + 1)` three times queues three replace-with-1 instructions. The state variable `tickets` stays 0 throughout that render (Lecture 16). During the next render, React applies the instructions in order, leaving the total at 1. When we replace them with `t => t + 1`, each function receives the running total from the previous updater. From 0, the functions compute 1, 2, and 3. The screen displays 3. On the first click after page load, React 19 calls the first updater during the setter call. The console prints `t = 0` before `handler done`. ◼ Educational objective: prove Principle 2 on the lesson's example with verified queue transitions.

- [principle-notes] Principle 3: The reader wonders whether they must use an updater function on every setter call from now on. What actually happens: a plain setter is completely fine for a single update per click because React finishes rendering before the next click runs. An updater is needed when multiple updates queue before a render, or when updating state after an await. Move from casebook Case 3 and Case 6: state the boundary clearly and show the asynchronous request counter bug.

> [!PRINCIPLE]
> **Principle 3: Use an updater function when another update can be queued first**
> A setter with a plain value works well for one update per click. React finishes rendering before the next click runs. When a handler queues several updates, or updates state after a network request, the snapshot value falls behind. An **updater function** calculates the next state from the latest queued total.
>
> *We should do this:*
> `setPending(p => p + 1); // queues increment`
> `await delay(100); // waits for request`
> `setPending(p => p - 1); // receives running total, ends at 0`
>
> *We should not do this:*
> `setPending(pending + 1); // queues 0 + 1`
> `await delay(100); // waits for request`
> `setPending(pending - 1); // reads snapshot 0, ends at -1`

- [p] ★ We rewrite the "+3 Tickets" button using three updater calls: `setTickets(t => t + 1)`. When the customer clicks the button, the ticket count rises from 0 to 3. We then test an asynchronous reservation counter on `TicketOrder` to track pending bookings. In JavaScript, `async` marks a function that can pause, and `await` pauses execution until a promise completes. We test plain values with `setPending(pending + 1)`, wait for `await delay(100)`, and call `setPending(pending - 1)`. The second setter reads snapshot `0` (Lecture 16). The counter finishes at `-1`. When we switch to `setPending(p => p - 1)`, the updater receives `1`, returning `0`. Even after two fast clicks, updaters correctly return the pending count to 0. ◼ Educational objective: prove Principle 3 with the asynchronous counter and remind async/await syntax.

- [principle-notes] Principle 4: The reader puts a console.log or alert inside an updater function and notices that it runs twice under StrictMode. What actually happens: updater functions run during render, so they must be pure. Move from casebook Case 4: explain that rendering must be pure, show that StrictMode doubles calls in development, and prohibit side effects in updaters.

> [!PRINCIPLE]
> **Principle 4: An updater function must only calculate and return the next value**
> React calls updater functions while it calculates the next screen, so updaters run during render. Code that runs during render must be pure, calculating its return value without changing outside variables or running side effects. In development with Strict Mode enabled, React calls each **updater function** twice with the same argument. This helps you spot unintended mutations. Putting popups, logs, or API requests inside an updater causes those side effects to run twice.
>
> *We should do this:*
> `setCount(c => c + 1); // updater only calculates next value`
> `alert('Ticket added'); // popup runs once in the click handler`
>
> *We should not do this:*
> `setCount(c => {`
> `  alert('Ticket added'); // popup runs twice under StrictMode`
> `  return c + 1;`
> `});`

- [p] ★ Lecture 16 showed that reading state right after a setter reads the old snapshot. A developer might place side effects inside the updater where the new value is calculated. We test this by placing an `alert` popup inside `setTickets(t => { alert('Ticket added'); return t + 1; })`. In browser JavaScript, `alert` displays a popup message dialog. Because Vite enables `StrictMode` by default, React calls the updater twice during render, displaying the popup twice for every click. We move the `alert` back into the handler and compute the displayed number as `tickets + 1`. The popup appears once. Updaters run during render, so they must obey the purity rules from Lecture 12. Lecture 46 will explore why `StrictMode` doubles function calls. ◼ Educational objective: prove Principle 4 by deconstructing double invocation in StrictMode.

### For the interview

- [interview] > **The Interview Question:** How does React queue multiple state updates, and when do you need an updater function?
- [interview] **1. The Hidden Signal**: Interviewers ask this question to probe whether you understand React's batching model and execution pipeline. A junior candidate often assumes each setter call re-renders immediately. A senior engineer explains that React batches updates within event handlers and resolves queued instructions during render.
- [interview] **2. The Classic Trap**: The most common wrong assumption is that calling `setCount(count + 1)` three times will increment by three. It only increments by one because all three calls read the identical snapshot value. Another trap is putting side effects like API requests inside updater functions, which breaks under StrictMode.
- [interview] **3. What is Actually Going On**: Think of React like a waiter taking your order. React batches updates, waiting until the handler finishes to run down the ticket once. Passing setCount(count + 1) three times asks for the same dish three times. Passing an updater c => c + 1 adds one more to the plate, computing 3. Use an updater when the next value depends on other updates in the same handler or after an async pause.
- [interview] **4. Where It Gets Tricky**: What does React render if you call setCount(count + 5), then setCount(c => c + 1), then setCount(42) from zero? The final rendered count is 42 because 42 replaces the running total. Why are updater functions critical after an await? Because stale closures lose increments if multiple requests finish out of order. Why does StrictMode run updaters twice in development? To surface accidental side effects and external mutations before production.

### Glossary

- [glossary] **Batching** ◼ The React mechanism that groups multiple state setter calls into a single render after an event handler completes.
- [glossary] **Update Queue** ◼ The internal list of instructions that React processes in order during the next render to calculate state.
- [glossary] **Updater Function** ◼ A function passed to a state setter that receives the pending state and returns the next value.
- [glossary] **`async` and `await`** ◼ JavaScript keywords where `async` marks a pauseable function, and `await` pauses until a promise finishes.
- [glossary] **`StrictMode`** ◼ A React development tool that runs updater functions twice to help developers catch impure side effects.

