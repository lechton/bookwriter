### The form field keeps its own text, but React state stays out of sync

- [p] ◇ {theme: declarative form controls in React} In modern web applications, user interfaces collect information through interactive forms. Users type search terms, write comments, pick categories from dropdowns, and toggle agreement checkboxes. In plain HTML, form fields own their internal text, and scripts query the DOM when a user submits the page. In React, this imperative model creates severe synchronization defects. When an application needs to clear fields after submission, validate text length on the fly, or populate defaults dynamically, the component must become the single source of truth. By binding the field's displayed value to a React state variable through `value` and updating that state synchronously on every keystroke through `onChange`, the form control becomes fully controlled. State drives what appears on screen, and clearing state immediately flushes the field. ◼ Educational objective: introduce the controlled component paradigm and contrast it with imperative HTML DOM state.

- [p] ◇ {starting point: HTML form habits versus React controlled fields} When engineers transition from vanilla HTML and JavaScript to React, they naturally carry over habits from native form elements. In HTML, a developer writes `<textarea>Starting text</textarea>` or `<input value="Default">`, expecting the browser to manage user keystrokes independently while JavaScript reads the field value on submit. In React, passing `defaultValue` sets the initial text once at mount, after which the DOM node retains its own independent memory. When an event handler later updates a state variable with `setText('')`, a `defaultValue` field completely ignores the new state, leaving stale text on screen while counters reset to zero. Conversely, developers who hear that React needs `value={text}` often supply `value` without an `onChange` handler, inadvertently locking the field so it refuses every keystroke while the console logs a read-only warning. Furthermore, checkboxes require `checked` rather than `value`, dropdowns require `value` on the `<select>` rather than `selected` on an `<option>`, and text state must never start as `undefined`. ◼ Educational objective: contrast native HTML form habits with React controlled architecture and preview the six core failure modes.

- [p] ◇ {core questions: six governing laws of controlled inputs} This chapter investigates six core questions. **Why does calling a state setter fail to clear an input that uses defaultValue?** **Why does assigning value without an onChange handler freeze the field completely?** **Why must the onChange handler store exactly what was typed synchronously, rather than modifying or delaying the text?** **Why does a checkbox require the checked prop and e.target.checked rather than value and e.target.value?** **Where must the value prop be declared when controlling a select dropdown or textarea?** **Why does initializing a state variable with useState() trigger an uncontrolled-to-controlled warning on the first keystroke?** ◼ Educational objective: frame the six roadmap questions the lecture answers.

### Controlled versus uncontrolled form inputs

- [runway] Controlled inputs (value and onChange), uncontrolled inputs, defaultValue, textarea, select, option, string length, browser input vs change events. Used by Question 1 and Question 2.

- [p] ★ {preknowledge: event handlers and state pairs from Lectures 13 and 14} In Lecture 13, we learned how event handlers capture user interactions, and in Lecture 14, we learned how `useState` provides a setter that schedules a future render. In Lecture 18, we saw a preview of form inputs where `value` and `onChange` were wired to state properties. Today we unpack the exact mechanics of that binding. ◼ Educational objective: anchor form input mechanics in established state and event handling knowledge.

- [p] ★ {mechanism: defaultValue versus value and single source of truth} In React, form elements operate in one of two distinct modes: uncontrolled or controlled. An uncontrolled field uses `defaultValue="initial"` (or `defaultChecked` for checkboxes). React populates the DOM element once when it mounts, after which the browser's internal DOM node manages all subsequent typing and state. If your component updates a state variable later, the uncontrolled DOM node ignores it. In contrast, a controlled field explicitly binds its displayed text to React state via `value={text}`. On every keystroke, React's synthetic `onChange` event fires immediately—behaving like the native browser `input` event rather than the native `change` event, which only fires after the user leaves the field. The handler calls `setText(e.target.value)`, React re-renders the component, and the commit phase writes the new state value back into the DOM element. Because React drives the field on every render, state is the single source of truth. Clearing state programmatically with `setText('')` immediately flushes the visible text from the screen. ◼ Educational objective: contrast defaultValue with value, explain the synthetic onChange keystroke timing, and define the single source of truth.

- [code] Uncontrolled versus controlled form fields:

```jsx title="Uncontrolled Versus Controlled Form Fields"
// Uncontrolled: browser keeps text; setting state later does not clear it
<textarea defaultValue="Initial note" />

// Controlled: React state drives field; setting state flushes the DOM
<textarea value={text} onChange={e => setText(e.target.value)} />
```

◼ **The what-this-introduces list:** 1. `uncontrolled input`: a form element whose value is managed internally by the DOM. 2. `defaultValue`: sets the starting value once without controlling subsequent renders. 3. `controlled input`: an input driven by React state via `value` and updated via `onChange`. 4. `single source of truth`: a single state variable that dictates what appears on screen.

### Synchronous input updates and the text caret

- [runway] Text caret position, string toUpperCase(), synchronous onChange updates, setTimeout delaying state. Used by Question 3.

- [p] ★ {preknowledge: render cycles and asynchronous timers from Lecture 16} In Lecture 16, we saw that calling a state setter queues a render rather than mutating variables in place, and that `setTimeout` defers execution until the browser's event loop clears. When managing text inputs, timing and value fidelity become critical to cursor stability. ◼ Educational objective: connect input event handling to render queue timing and event loop scheduling.

- [p] ★ {mechanism: caret position jumping and synchronous event handling} When a user types into a text input, the browser places the new character at the active cursor position and advances the text caret immediately. In a controlled field, React must synchronize this DOM mutation with component state. If your `onChange` handler stores an altered string—such as calling `e.target.value.toUpperCase()`—the text that React renders back into the DOM differs from what the browser natively inserted. When React overwrites the element's `value` with a modified string, the browser loses track of the user's cursor position and jumps the caret to the very end of the input. If the user was editing text in the middle of a word, their next keystroke lands erroneously at the end of the line. Similarly, if a developer attempts to defer `setText` inside a `setTimeout`, React writes the old state back to the DOM before the timer fires, causing fast typing to scramble characters. To preserve seamless caret navigation, `onChange` must update state synchronously with the exact, unmodified string from `e.target.value`. Formatting should occur during render display or upon final submission. ◼ Educational objective: explain why modifying or deferring text in onChange causes the caret to jump to the end and mandate synchronous updates.

- [code] Synchronous event handling and caret stability:

```jsx title="Synchronous Event Handling and Caret Stability"
// Correct: stores raw typed text synchronously; cursor position stays stable
function handleTitleChange(e) {
  setTitle(e.target.value); // caret stays exactly where the user is typing
}

// Broken: uppercasing during typing forces the caret to jump to the end
function handleBrokenTitleChange(e) {
  setTitle(e.target.value.toUpperCase()); // jumps caret to end of field
}
```

◼ **The what-this-introduces list:** 1. `text caret`: the blinking cursor indicating where typed characters appear. 2. `synchronous state update`: calling the setter immediately in the event handler. 3. `caret jump`: cursor displacement caused by overwriting input text with an altered string.

### Checkbox boolean bindings and select value props

- [runway] Checkbox checked and e.target.checked (vs e.target.value), select value vs option selected, string initialization useState('') vs useState() causing uncontrolled-to-controlled warning. Used by Question 4, Question 5, and Question 6.

- [p] ★ {preknowledge: props, JSX expressions, and nullish coalescing from Lectures 4 and 6} In Lecture 4, we learned that JSX expressions evaluate JavaScript variables directly, and in Lecture 6, we learned that passing `undefined` causes React to fall back to default behavior. When dealing with form elements, `undefined` carries a specific structural consequence. ◼ Educational objective: recall JSX expression evaluation and undefined prop fallbacks.

- [p] ★ {mechanism: checked prop, select containers, and string initialization} Different HTML form elements require specialized prop pairings. A checkbox does not track state through `value`; in native HTML, an input checkbox has a default `value="on"`. If you write `onChange={e => setAgreed(e.target.value)}`, `e.target.value` evaluates to the string `"on"` regardless of whether the box was ticked or unticked. Because `"on"` is truthy, the checkbox becomes permanently checked and cannot be unticked. Checkboxes and radio buttons must pair the `checked` boolean prop with `e.target.checked`. Similarly, dropdown menus in React do not set `selected` on individual `<option>` elements. Setting `<option selected>` logs a console warning; instead, React declares `value={selectedOption}` directly on the parent `<select>` element. Finally, text inputs must never initialize with `useState()` or `undefined`. When an input receives `value={undefined}`, React treats it as an uncontrolled field. When the user types their first letter and state becomes a string, React suddenly switches the input to controlled, logging an error: "A component is changing an uncontrolled input to be controlled." Always initialize text fields with an empty string `useState('')` or provide a fallback `value={text ?? ''}`. ◼ Educational objective: detail checkbox boolean bindings, select value declaration, and string initialization rules.

- [code] Form field bindings and string initialization:

```jsx title="Form Field Bindings and String Initialization"
// Checkbox: binds checked prop and reads boolean e.target.checked
<input type="checkbox" checked={urgent} onChange={e => setUrgent(e.target.checked)} />

// Select: declares value on select element, not selected on option
<select value={topic} onChange={e => setTopic(e.target.value)}>
  <option value="billing">Billing</option>
</select>

// Safe text initialization: starts as empty string, preventing warning
const [title, setTitle] = useState(''); // never useState() without string
```

◼ **The what-this-introduces list:** 1. `checked`: boolean prop governing checkbox and radio button visual state. 2. `e.target.checked`: boolean property reporting whether a checkbox is ticked. 3. `select value`: container prop matching the selected option's value. 4. `uncontrolled-to-controlled warning`: error logged when value switches from undefined to a defined string.

### Principles of React: Controlled Inputs

- [question-cycle] Principle 1 Plan:
    - Question: After Send, I call setText(''). The counter says 0/280, but the old text stays in the box. Why?
    - Code and result: Inside `FeedbackForm`, a developer uses `<textarea defaultValue="" onChange={e => setText(e.target.value)} />`. On submit, the handler calls `setText('')`. The character counter reads `text.length` and displays 0/280, but the textarea on screen still displays "Fix the date".
    - Verdict: does not do what the reader wanted.
    - Answer: `defaultValue=""` sets the starting text of the field once when the component mounts. After mount, the browser's DOM node retains its own independent memory. Calling `setText('')` updates the component's state variable, which causes React to re-render the counter to 0/280. However, because the textarea uses `defaultValue`, nothing instructs React to synchronize the DOM node with the new state. The textarea ignores the state update and keeps displaying the typed text. To make state drive the field, you must switch from `defaultValue` to `value={text}`. After every render, React writes the state value back into the DOM element. Calling `setText('')` then immediately clears the visible text.
    - Fix: Replace `defaultValue=""` with `value={text}`.
    - Rule with boundary: A controlled field shows what is in state after every render; use `value` when state must programmatically update or clear the field. Boundary: use `defaultValue` only for uncontrolled fields whose text our code never changes after initial mount.
    - Needs: controlled input (runway), `defaultValue` (runway), single source of truth (runway).
    - Diagram: ASCII diagram showing submit calling `setText('')` -> `defaultValue` leaving DOM unchanged vs `value={text}` flushing the DOM on render.

> [!PRINCIPLE]
> **Principle 1: A controlled field shows what is in state, after every render**
> A field with `defaultValue` sets its initial text once at mount; after that, the browser keeps the field's own text, so setting state does not change it. A controlled field takes its displayed text directly from React state through `value`. Each keystroke calls `onChange`, the handler writes the new text into state, and React writes state back into the field after every render. Because state is the single source of truth, whatever is in state is what the field shows, and clearing state clears the field.
>
> >> defaultValue : sets only the initial text when the field mounts; the browser keeps subsequent edits
>
> *We should do this:*
> `// value drives the textarea from state; setText('') empties it`
> `<textarea value={text} onChange={e => setText(e.target.value)} />`
>
> *We should not do this:*
> `// defaultValue leaves field uncontrolled; setText('') does not clear it`
> `<textarea defaultValue="" onChange={e => setText(e.target.value)} />`

- [question-cycle] Principle 2 Plan:
    - Question: I wrote value={text} and the box no longer takes any typing. What broke?
    - Code and result: Inside `FeedbackForm`, a developer writes `<textarea value={text} />` without an `onChange` prop. When the user types into the box, no letters appear on screen, and the development console logs an error warning that a `value` prop without `onChange` renders a read-only field.
    - Verdict: does not do what the reader wanted.
    - Answer: Passing a string `value` to a form field makes it a controlled component. When the user presses a key, the browser momentarily updates the native DOM input. However, because there is no `onChange` handler to store the newly typed character in React state, React immediately re-renders the element with its existing `text` state value. The typed character vanishes instantly, freezing the field. React warns you in the console: "You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field." To keep the field editable, you must pair every `value` prop with an `onChange` handler that updates state.
    - Fix: Add an `onChange` handler: `onChange={e => setText(e.target.value)}`.
    - Rule with boundary: Pair every `value` prop with an `onChange` handler that updates state. Boundary: if a field is intentionally non-editable by the user, add the `readOnly` prop; if the field only needs initial text and our code never changes it, use `defaultValue`.

If a field should accept user edits, pair its `value` with an `onChange` handler that updates state.

- [p] Glossary:
  - Controlled Input: A form element whose displayed value is driven by React state and whose changes update that state.
  - Uncontrolled Input: A form element whose value is managed internally by the DOM.
  - Single Source of Truth: The architectural model where one state variable determines what appears on screen.
  - Synthetic `onChange`: React's cross-browser event firing synchronously on every keystroke like native `input`.
  - Caret Stability: The preserved position of the text cursor when input state updates synchronously without modification.
- [p] Beyond the Basics: Links to react.dev docs on input, textarea, select, and form handling.
- [p] Summary Decision Matrix (IF ... THEN):
  - IF a field must be updated or cleared by React state THEN bind `value` to a state variable and pair it with `onChange`.
  - IF a field is a checkbox or radio button THEN bind `checked` to boolean state and read `e.target.checked`.
  - IF controlling a dropdown selection THEN declare `value` directly on the `<select>` tag rather than `selected` on an `<option>`.
  - IF handling text input THEN store `e.target.value` synchronously without modification to preserve caret position.
  - IF declaring state for a controlled text input THEN initialize with an empty string `useState('')` to prevent uncontrolled-to-controlled warnings.
