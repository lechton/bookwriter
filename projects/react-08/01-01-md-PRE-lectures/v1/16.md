### A function remembers where it was made

- [runway] The closure and `setTimeout`, in plain JavaScript first, used by Question 2 and every step.

- [p] ◇ {the closure, named with code} A function can read the variables of the place where it was written, even after that place is gone. Such a function is called a **closure**: it closes over the variables around it and keeps them. ◼ Educational objective: the refresher the map marks `yes`, in plain JavaScript first (`principle-definition` Pass 3).

- [code] A function that keeps its variables:

```js title="A closure"
function makeGreeting(name) {
  return () => console.log('Hello, ' + name); // keeps name
}
const greetMary = makeGreeting('Mary Jones');
greetMary(); // Hello, Mary Jones, long after makeGreeting returned
```

◼ **The what-this-introduces list:** 1. The arrow function returned by `makeGreeting`, which keeps `name`.

- [p] ◇ {setTimeout, named with code} The browser can run a function later: **`setTimeout(fn, ms)`** waits `ms` milliseconds, then calls `fn` once. 3000 milliseconds are three seconds. A function passed to `setTimeout` is often a closure: it reads the variables around it when it finally runs. ◼ Educational objective: the second refresher, joined to the first, because Question 2 uses them together.

- [code] A function run three seconds later:

```js title="setTimeout"
const title = 'New Park Opens Today';
setTimeout(() => {
  console.log(title); // three seconds later: New Park Opens Today
}, 3000);
```

◼ **The what-this-introduces list:** 1. `setTimeout(..., 3000)`: run a function once, three seconds from now.

- [p] ◇ {the rule} A closure keeps the variables of the place it was made, and `setTimeout` runs it later; together, they run old code with old values. ◼ Educational objective: the closing rule, which Question 2's answer recalls in a few words.

### Principles of React: State as a Snapshot

- [preview] Everything in this lesson comes down to one idea: state as a snapshot, which means that each render sees one fixed value of its state. First, snapshots, which means the rest of the handler keeps the old value: a setter asks for a new render and changes nothing in the render we are in, so when the handler needs the new value, it computes it once and uses that. Second, stale closures, which means code that runs later keeps the old value too: a function made during a render remembers that render's values, even when it runs seconds afterwards. ◼ Educational objective: the map's Spoken Preview, word for word, one paragraph for the anchor and one per principle in the lecture, read aloud before Question 1.

> [!PRINCIPLE]
> **Principle 1: Snapshots: the rest of the handler keeps the old value**
> *After a setter, every line of the same handler still reads the old value, so when a handler needs the new value, it computes it once into a constant and uses that constant for the setter and for everything else.*
>
> When React renders a component, it gives that render the current value of each state variable, and the variable is a `const` of that render. The JSX and the handlers of the render are built from it: this fixed value is called a **snapshot**. A setter stores a new value in React and asks for a new render; it cannot change the `const` of the render we are in. So every line after the setter, in the same handler, reads the old value. The new value arrives with the next render. When the handler needs it now, it computes it once and uses that.
>
> *We should do this:*
> `const next = count + 1;`
> `setCount(next);`
> `report(next); // the new value`
>
> *We should not do this:*
> `setCount(count + 1);`
> `report(count); // the old value: this render's snapshot`

> [!PRINCIPLE]
> **Principle 2: Stale closures: code that runs later keeps the old value too**
> *A function made during a render, such as the one we pass to `setTimeout`, keeps that render's values even when it runs later; we never wait for state to change, and when the delayed code needs the new value, we give it the value we computed.*
>
> A function reads the variables of the place where it was made: it is a **closure**. A handler is made by one render, so a function it passes to `setTimeout` closes over that render's state. When the function runs seconds later, React has already rendered again with a new value, but the old function still holds the old one. Waiting changes nothing. This is often what we want: a message scheduled at a click describes the moment of the click. When the delayed code needs the new value, the handler gives it the value it computed.
>
> *We should do this:*
> `const next = count + 1;`
> `setCount(next);`
> `setTimeout(() => report(next), 3000); // the new value`
>
> *We should not do this:*
> `setCount(count + 1);`
> `setTimeout(() => report(count), 3000); // still the old value`

- [grounding] Is `setState` asynchronous? ◼ Friction target: the map's Merged row on the "is setState asynchronous?" framing. Tactile scene: a common answer online says the setter is "asynchronous", so the reader waits for it with a timer, as in Question 2. Bold key terms: **snapshot**, **trigger**. Concrete operational resolution: the word misleads; the setter itself finishes at once, storing the value and asking for a render; what never changes is the `const` of the current render, so no wait of any length could change it; the screen does update after the handler (Lecture 15), but the variable in the old render stays as it was; the honest answer is "the setter schedules a render, and the current render's value is fixed". ◼ Educational objective: one `> [!WILD]` card after the principles, correcting the word that causes Question 2's mistake.

### Where you will meet this

- [p] 1. **Analytics after a click**: the event reports the value the handler computed, never the state variable on the line after its setter.
- [p] 2. **Toasts and undo messages**: a message scheduled with `setTimeout` describes the click that scheduled it, which is usually what the user expects.
- [p] 3. **"+5" and "add several" buttons**: one setter with the total, or the updater of Lecture 17, never several setters with the same expression.

### For the interview

- [interview] > **The Interview Question:** Why does state appear frozen inside a render, even right after you set it?

- [interview] **1. The Hidden Signal** ◼ The interviewer wants to hear "snapshot" and "closure", and why they are the same idea. A junior answer says "setState is asynchronous". A strong answer says that each render gets a fixed value in a `const`, that the setter schedules a new render instead of changing that `const`, and that functions made in a render, timers included, keep that render's values.

- [interview] **2. The Classic Trap** ◼ The classic trap is waiting for the state: on the article card, `setLikes(likes + 1)` followed by a three-second `setTimeout` still logged 0, while the screen had shown "Likes: 1" for three seconds. The setter was not slow; the timer's function was a closure over the render in which `likes` was 0.

- [interview] **3. What is Actually Going On** ◼ React rendered the card with `likes` at 0, and `handleLike` was built in that render. `setLikes(likes + 1)` stored 1 and asked for a new render; the line after it still read 0. Three calls were three `setLikes(0 + 1)` calls, so the count moved by one. The fix computed `const nextLikes = likes + 1` once and used it for the setter, the report, and the timer.

- [interview] **4. Where It Gets Tricky** ◼ *Does a log before the setter differ from one after it?* No: both print this render's value. *Why do three quick clicks with timers log 0, 1, and 2?* Each click ran a different render's handler, and each timer closed over its own render. *Is the stale value ever useful?* Yes: a delayed message keeps describing the click that made it, as react.dev's "Alice" form shows. *How do I read the latest value later?* With an updater (Lecture 17) or a ref (Lecture 29), never with a longer delay. *Does `flushSync` change the variable?* No: it changes the DOM earlier (Lecture 65), and the `const` stays.

### Glossary

- [glossary] Snapshot ◼ The fixed value of a state variable in one render, held in a `const`. The render's JSX and handlers are built from it, and a setter cannot change it.
- [glossary] Closure ◼ A function that keeps the variables of the place where it was made, even after that place is gone. Every handler is a closure over its render.
- [glossary] Stale closure ◼ A closure that reads a value the screen has already replaced, such as a timer reading the state of an earlier render.
- [glossary] `setTimeout` ◼ A browser function that calls a function once after a delay in milliseconds.
- [glossary] Substitution method ◼ Reading a handler with each state variable replaced by its value in that render, as in `setLikes(0 + 1)`, to see what it really does.

```jsx right
  console.log('analytics:', article.title, nextLikes);

    alert(`Thanks! Likes: ${nextLikes}`);
  }, 3000);
}
```

**DO NOT DO THIS:** read the state after its setter, or wait for it

```jsx wrong
function handleLike() {
  setLikes(likes + 1);
  console.log('analytics:', likes);
  setTimeout(() => {
    alert(`Thanks! Likes: ${likes}`);
  }, 3000);
}
```

- [comparison-table]

| | **AN ORDINARY VARIABLE**<br>(`let count`) | **A STATE SNAPSHOT**<br>(`const [count, setCount]`) |
| ---: | :--- | :--- |
| **After it is set** | The next line reads the new value | The next line reads the old value;<br>the new one comes with the next render |
| **Three changes in a row** | Each one adds to the last | Three calls with `count + 1` add one |
| **A timer three seconds later** | Reads the latest value | Reads the value of its own render |
| **How to use the new value now** | Read the variable | Compute it once: `const next = count + 1` |
| **When it helps** | A value only this function uses | A screen and handlers that always agree<br>with one moment in time |
