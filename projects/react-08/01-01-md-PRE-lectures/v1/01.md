### The page must change wherever the data appears

- [p] ◇ {theme} Most pages show the same piece of data in more than one place. A website greets the signed-in user at the top, "Welcome back, Mary", and shows the name again in the corner, "Signed in as Mary". When Mary adds her family name in her profile and becomes Mary Brooks, both places must show the new name. Every web developer meets this question: when the data changes, how does the page change with it? ◼ Educational objective: the theme from the map's `## Theme and Options`, on a page every reader has seen.

- [p] ◇ {the DOM, named first} The browser does not draw the HTML file directly. It reads the file and builds one object in memory for every tag, nested the way the tags are nested, so together they form a tree. Then it draws the screen from that tree. The tree is the **DOM**, the Document Object Model, and each object in it is a **DOM node**. HTML is the text we write; the DOM is what the browser builds from it and keeps. So to change what the screen shows, something must change the DOM. ◼ Educational objective: the HTML and DOM pair an interviewer expects, named before either option uses it (`lecture-voice` Section 22).

- [p] ◇ {option 1: imperative programming} The first answer is the one plain JavaScript taught you: you change the page yourself. You find the element, then you set its text. ◼ Educational objective: say what the code is for before it appears; the reader's own habit comes first.

- [code] Plain JavaScript, finding the greeting and setting its text:

```js title="Plain JavaScript: find the element, set its text"
const greeting = document.getElementById('greeting'); // the <p id="greeting">
greeting.textContent = 'Welcome back, Mary Brooks'; // new text on screen
```

◼ **The what-this-introduces list:** 1. `document.getElementById`: asks the browser for the DOM node with that `id`. 2. `textContent`: the text inside one node, which the second line replaces.

- [p] ◇ {option 1: point into the code, the term, its origin, where it fits} `document.getElementById('greeting')` asks the browser for the DOM node whose `id` is `greeting`, and `textContent` replaces the text inside that node. Nothing else on the page changes. This is called **imperative programming**: you give the browser every command yourself. The word comes from the Latin *imperare*, "to command", the root of *emperor*: like an emperor, the code orders every step. It fits well when one element changes in one place, such as a clock in the corner of a page. ◼ Educational objective: a fair account of the first option, pointing into each line, with the term an interviewer uses and the situation where it is the right choice.

- [p] ◇ {option 2: declarative programming} The second answer is React's: instead of the commands, you write what the element shows. ◼ Educational objective: the chapter's option, introduced by its purpose before its code.

- [code] React, what the greeting shows:

```jsx title="React: what the greeting shows"
<p>Welcome back, {userName}</p>
```

◼ **The what-this-introduces list:** 1. `{userName}`: a place where the current value of the variable `userName` goes.

- [p] ◇ {option 2: point into the code, the term, its origin, where it fits} It looks like HTML, but `{userName}` marks a place where the value of the variable `userName` goes. No line finds the `<p>`, and no line sets its text. React reads this line, builds the `<p>`, and puts the current value in it. This is called **declarative programming**: you declare what the page should show, and React changes the DOM to match. The word comes from the Latin *declarare*, "to make clear, to announce". It fits when the same value shows in several places, or when many parts of the page change. ◼ Educational objective: the place in the code, what fills it, who acts, the contrast with the commands above, and the term's origin.

- [code] React, what the corner shows:

```jsx title="React: what the corner shows"
<span>Signed in as {userName}</span>
```

◼ **The what-this-introduces list:** 1. A second element that reads the same `userName`.

- [p] ◇ {option 2: a second tiny example, then the rule} The corner reads the same `userName` as the greeting. There is no second command to write, so there is no second command to forget. Imperative code tells the browser how to change the page, one command at a time; declarative code says what the page shows, and React does the changing. ◼ Educational objective: confirm the idea on a second element, then state both terms as one contrast.

- [ways] Two ways to update the DOM when the data changes ◼ (1) Update the DOM with **imperative programming** (plain JavaScript): you give the browser every command yourself, finding each element and setting its text. (2) Update the DOM with **declarative programming** (this chapter): you declare what each element should show, and React updates the DOM to match. ◼ Educational objective: the `> [!WAYS]` box in the owner's frame for Lecture 1 (`lecture-structure` Section 12), each line with its exact term in bold and its plain meaning.

- [p] ◇ {the boundary of the commands} Declarative code still leaves room for the few jobs that need one particular element. To move the cursor into a search box, for example, React lets your code reach that one element without changing what it shows. Lecture 30 covers it. ◼ Educational objective: the senior's caveat from the map's Preview row (Q30 `#dom_refs`), one sentence with its lecture, so Principle 1's "never find and change" reads as a rule about changing, not about reaching.

- [p] ◇ {what React is, and the anchor of the chapter} React is a JavaScript library for building user interfaces out of components. It can run a whole page, or only one part of a page that already exists. This chapter follows one idea from its first question to its last: we describe the page from data, and React makes the browser match. ◼ Educational objective: answer "what is React" in one sentence (map Supporting rows), and plant the anchor in the exact words of the map's `## Principle Thread`, so the spoken preview later lands on a phrase the reader has already heard.

- [p] ◇ {the questions} This lesson answers three questions. **I find each element and change its text. What do I write instead in React?** **The name shows in two places. Do I write it twice?** **When the name changes, does React throw the header away and wipe what I typed?** ◼ Educational objective: the map's three Reader Questions, in the reader's words and in thread order.

- [p] {the starting point} Lecture 1 has no earlier lecture to recall. It stands on HTML tags with an `id` attribute and on plain JavaScript you already write: a variable made with `const`, and two strings joined with `+`. ◼ Educational objective: the recall list stays empty, because it names only earlier lectures (`pre-lecture` Section 13C), and the map has no Prerequisite rows; the reader's starting point is named in one sentence instead.

### innerHTML replaces every node inside an element

- [runway] `innerHTML` and focus, used by Question 3. `document.getElementById` and `textContent` come from the first section.

- [p] ◇ {two plain JavaScript tools that look alike} `textContent` changes the text inside one node and leaves the node itself in place. `innerHTML` does much more: it throws away every node inside an element and builds new nodes from a string of HTML. ◼ Educational objective: set the new tool against the one the reader just saw.

- [code] Plain JavaScript, rebuilding the inside of the header:

```js title="Plain JavaScript: rebuild the inside of the header"
const header = document.getElementById('header'); // the <header id="header">
header.innerHTML = '<p>Welcome back, Mary Brooks</p>'; // new nodes inside
```

◼ **The what-this-introduces list:** 1. `innerHTML`: the HTML inside an element; assigning a string to it replaces every node inside.

- [p] ◇ {point into the code} After the second line, the `<header>` holds a new `<p>`, built from the string. The old `<p>` is gone, together with everything else that was inside the header. The screen looks the same, but every node inside the header is a new one. ◼ Educational objective: the physical fact Question 3 stands on (new nodes, old ones gone), without its consequence for a text box, which is Question 3's to show.

- [p] ◇ {focus} When you click into a text box and type, that box has the **focus**: it is the element that receives the keys you press, and it shows a blinking cursor. Only one element on the page has the focus at a time. Click somewhere empty, and the focus goes back to the page itself. ◼ Educational objective: the browser term Question 3 needs, grounded in what the reader does every day.

### A component is a function that returns what the page shows

- [runway] Component, JSX, local variable, curly braces in JSX, and `export default`, used by Questions 1, 2, and 3.

- [p] ◇ {the term, then the code} In React, a page is written as **components**. A component is a JavaScript function whose name starts with a capital letter and which returns the markup for one piece of the page. Lecture 2 gives the rules for writing one. Here is the header from the opening, written as a component: ◼ Educational objective: name the idea first, then show it at once.

- [code] SiteHeader.jsx, the whole header as one component:

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const userName = 'Mary'; // the name, written once
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as {userName}</span>
      <input placeholder="Search" />
    </header>
  );
}
```

◼ **The what-this-introduces list:** 1. `function SiteHeader()`: a component, a function with a capitalized name. 2. `const userName = 'Mary'`: a local variable that holds the name. 3. The markup after `return`: JSX. 4. `{userName}` twice: two places that read one variable. 5. `export default`: lets another file use the function.

- [p] ◇ {point into the code} `const userName = 'Mary'` makes a **local variable**: a name for a value, inside this function. The markup after `return` is **JSX**. It looks like HTML, but it is JavaScript, which Lecture 3 explains. Inside JSX, **curly braces** mark a place where a JavaScript value goes, so `{userName}` shows "Mary" in the greeting and again in the corner; Lecture 4 shows what else braces can hold. `export default` lets another file use this function, as Lecture 8 explains. ◼ Educational objective: decode every symbol the questions reuse, each named next to the line that shows it, with one sentence of preview for each owner lesson.

- [p] ◇ {who does what} Our code never calls `SiteHeader`. React calls it, and React uses the JSX it returns. ◼ Educational objective: who acts, said plainly, while what React does with the JSX stays Question 1's answer.

- [code] A second tiny component:

```jsx title="A second component: SiteFooter"
export default function SiteFooter() {
  const year = 2026; // a number this time
  return <footer>Copyright {year}</footer>;
}
```

◼ **The what-this-introduces list:** 1. A second component: a local variable and one place that reads it.

- [p] ◇ {the second example confirms, then the rule} `SiteFooter` works the same way with a number: `{year}` shows 2026. A component is a function that returns JSX, and curly braces place a value inside that JSX. ◼ Educational objective: confirm the form on a second, different piece of the page; close on the rule.

### Principles of React: Describing the Page from Data

- [preview] Everything in this lesson comes down to one idea: we describe the page from data, and React makes the browser match. First, declarative programming, which means describing what the page shows, not how to change it: we write what each element shows for the data, and React changes the DOM to match, so our code never finds an element by hand. Second, a single source of truth, which means describing many places from one value: when a name appears in many places, every place reads it from one variable, so no place can show an old copy. Third, the virtual DOM, which means describing the page again when the value changes and comparing the two descriptions: React changes only the new text, so whatever the user typed stays where it was. ◼ Educational objective: the map's Spoken Preview, word for word, read aloud before Question 1. It names the anchor once and then each principle by its label and its rule, with no code and no symbols, so a listener hears the whole thread before the first question; each term arrives joined to its plain meaning (`lecture-structure` Section 12C, `lecture-voice` Section 16B).

> **Principle 1: Declarative programming: describing what the page shows, not how to change it**
> *We control the page by describing what it shows from data, and we never find and change its elements by hand.*
>
> In plain JavaScript, the page changes only where our code finds an element and sets its text, so an element the code forgets keeps its old text. > `}`
>

> `function updateHeader(name) {`
> `  const el = document.getElementById('hello');`

> *When one value appears in many places, we describe every place from one variable, and we never type a copy of it.*
>

### Question 3: Rebuilding the header empties the search box

- [question-cycle] Question 3: Rebuilding the header empties the search box
    - Question: "If React builds the header from my description, does it throw the header away when the name changes, and wipe what I typed in the search box?"
    - Code and result: first the plain JavaScript habit: "elections" is typed into the search box, then `header.innerHTML = '<p>Welcome back, ' + name + '</p><span>Signed in as ' + name + '</span><input placeholder="Search">'` runs with `name` set to `'Mary Brooks'`; both names change, the search box is empty, and the focus is on the page itself (verified in jsdom 30.1.2 and in Chrome).     - Verdict: the `innerHTML` code does not do what the reader wanted; React keeps the typed text.
    - Answer: `innerHTML` throws away every node inside the header and builds new ones from the string, as the runway showed; the new `<input>` was never typed into, so it is empty, and the focus had nowhere to stay but the page itself; with React, the save makes React call `SiteHeader` again, and the function returns a whole new description of the header, with the new name in it; React compares it with the last description, element by element: the text of the `<p>` differs, the text of the `<span>` differs, the `<input>` is the same; React changes those two texts in the DOM and leaves every other node where it is; the `<input>` is the same DOM node as before, so it keeps "elections" and the focus; the Elements panel highlights the two names; a description that is the same as last time changes no text at all; people call the description React compares the virtual DOM, while react.dev says React applies "the minimal necessary operations" (two text changes were recorded for this save); Lecture 15 gives the steps of an update their names (one sentence of preview).
    - Fix: describe the whole header in `SiteHeader` and change the data; never rebuild it with `innerHTML`. Nothing new: `SiteHeader` and the save come from the runway.
    - Rule: when the value changes, React compares the new description with the last one and changes only the new text, so whatever the user typed stays where it was. Boundary: it holds while the same element stays in the same place in the description, which is true for every change this lesson makes.
    - Needs: `innerHTML` and focus (runway "innerHTML replaces every node inside an element"); the save and the Elements panel (runway "The dev server shows each saved change of a file"); React builds the DOM from the description (Question 1); one variable in two places (Question 2).

> [!PRINCIPLE]
> **Principle 3: The virtual DOM: describing the page again when the value changes**
> *When the value changes, React compares the new description with the last one and changes only the new text, so whatever the user typed stays where it was.*
>
> When the data changes, React calls the component again, and the component returns a whole new description with the new value in it. React compares it with the last description, element by element. It changes the text that is new and leaves every other node where it is. A text box is still the same node, so it keeps what the user typed and keeps the focus. Rebuilding the elements with `innerHTML` makes new nodes, and the typed text is gone.
>
> *We should do this:*
> `function Header() {`
> `  const name = 'John Hall'; // was 'John'`
> `  return (`
> `    <header>`
> `      <p>Hello, {name}</p> {/* only this text changes */}`
> `      <input /> {/* keeps typed text and focus */}`
> `    </header>`
> `  );`
> `}`
>
> *We should not do this:*
> `const header = document.getElementById('header');`
> `header.innerHTML = '<p>Hello, John Hall</p><input>'; // box is empty`

### Step 1: First, we describe the header from its data <SiteHeader.jsx>

- [p] ★ This step applies the first principle, declarative programming, which means describing what the page shows, not how to change it. The plain JavaScript page kept the name and the count inside its HTML, and a function such as `updateHeaderUser` changed them, one command per element. In React there is no such function to bring over. We start from the data instead: the header depends on two values, who is signed in and how many messages are new, so each gets one variable at the top of the component, and the JSX below says where each value shows. Save the file and look at the Elements panel: the empty `<div id="root">` from `index.html` now holds a `<header>` with "Welcome back, Mary" and "Messages (3)", and the file has no `getElementById` and no `textContent` (verified in React 19.3.1, Vite 8.3.4, and Chrome). Our code describes, and React builds. ◼ Meaningful pedagogical commentary: the decision (no update function, two variables for the two values the header depends on), the result in the Elements panel, and the interview sentence (Principle 1).

- [code] SiteHeader.jsx, the header described from two values:

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const userName = 'Mary'; // who is signed in
  const unreadCount = 3; // how many messages are new
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <a href="/messages">Messages ({unreadCount})</a> {/* Messages (3) */}
    </header>
  );
}
```

◼ **The what-this-introduces list:** 1. `unreadCount`: a second value, a number, read in curly braces the way `SiteFooter` read `year`. 2. `<a href="/messages">`: the Messages link.

### Step 2: Next, we read each value in every place that shows it <SiteHeader.jsx>

- [p] ★ This step applies the second principle, a single source of truth, which means describing many places from one value. The full header adds three places: the corner and the account menu show the name, and a notice repeats the count. The notice is where a copy slips in most easily: it is a whole sentence, and typing "You have 3 new messages" looks finished. That would be Question 2's mistake again, on a number this time. So every place reads its value in curly braces, and the page now shows five places built from two variables, with no update code. Plain JavaScript would need one command for each of the five places on every change, and one more command for each place someone adds later. Why not give the account menu its own component? Without a way to pass the name in, which Lecture 6 teaches, it would need its own copy of the name, and the copy is exactly what this step removes. The last line, the search box, reads no variable at all: what it shows comes from the user, and Step 3 tests whether React leaves it alone. ◼ Meaningful pedagogical commentary: the decision (the notice reads `{unreadCount}`, not a typed number), the scale the hook promised (five places, two variables, zero update lines against five commands per change), the Negative Counterfactual for splitting the header (Lecture 6), and the setup for Step 3 (Principle 2).

- [code] SiteHeader.jsx, lines 5 to 12 after the change: the whole `<header>`, at its real line numbers:

```jsx title="SiteHeader.jsx" startLine="5"

      <p>Welcome back, {userName}</p>
      <span>Signed in as {userName}</span> {/* the corner */}
      <button>{userName}</button> {/* the account menu */}
      <a href="/messages">Messages ({unreadCount})</a>
      <p>You have {unreadCount} new messages</p> {/* not a typed 3 */}
      <input placeholder="Search" /> {/* reads no value */}
    </header>
```

◼ **The what-this-introduces list:** 1. Three places that read `userName` and two that read `unreadCount`. 2. `<button>`: the account menu. 3. The search box, which reads no variable.

### Step 3: Finally, we change both values while the user types <SiteHeader.jsx>

- [p] ★ This step applies the third principle, the virtual DOM, which means describing the page again when the value changes, and it tests everything above. Type "elections" into the search box and leave the cursor in it. Then make both changes the opening promised: Mary becomes Mary Brooks, and a new message arrives, so the count goes from 3 to 4. Save. Before you look, predict what changes. React calls `SiteHeader` again, and it returns a new description with the new values in it. React compares it with the last one, place by place: three places read `userName`, two read `unreadCount`, and the search box is the same as before. So React changes five texts in the DOM (five text changes were recorded for this save in React 19.3.1, Vite 8.3.4, and Chrome). The box still holds "elections", and the cursor still blinks in it, because the `<input>` is the same DOM node it was before the save. The plain JavaScript header rebuilt with `innerHTML` would have emptied the box, and the version that sets each text by hand would have needed five commands, with five chances to forget one. ◼ Meaningful pedagogical commentary: the milestone (a change of both values while the user types), the prediction the reader can now make alone, the verified count, and the contrast with both plain JavaScript habits (Principle 3).

### Component Summary

- [component-code] Summary: The Logic of Nested Components:

```component-code title="Summary: The Logic of Nested Components"
main.jsx | none | boundary | [role: The **entry file** hands the empty `<div id="root">` of `index.html` to React and shows **SiteHeader** inside it. No step changed it.]
  SiteHeader.jsx | none | header | [role: The **header component** holds the data in two variables, **userName** and **unreadCount**, and five places read them. It returns the whole header as one description and calls no DOM method. When both values changed, React changed five texts and kept the search box with what the user typed.]
```

- [p] ★ A developer who comes from plain JavaScript expects the update code to grow with the header: five places mean five commands for every change, and a sixth place means a sixth command that someone must remember. In React 19, the header grew from two places to five, and the update code stayed at zero lines. Each step applied one principle: the header is described from data, every place reads one variable, and a change of the data ends in exactly the texts that changed, while the search box stays as the user left it. ◼ Meaningful pedagogical commentary: the naive expectation against React 19's behavior, told once, with the three principles in thread order.

### Where you will meet this

- [p] 1. **The signed-in name**: a site shows the user's name in a greeting, in the account menu, and next to every comment the user wrote. Each place reads one variable, so a name change reaches all of them at once.
- [p] 2. **The cart count**: a shop shows the number of items in the header and again on the checkout button. Both read the same count, so the button never promises more items than the cart holds.
- [p] 3. **The search results**: a results page shows "Results for elections" above the list while the same word stays in the search box. React changes the heading and leaves the box, with its cursor, as the user left it.
- [p] 4. **The unread messages**: a mail app shows the unread count in the browser tab and again beside the inbox. One variable feeds both, so the tab and the inbox always agree.

### For the interview

- [interview] > **The Interview Question:** What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

- [interview] **1. The Hidden Signal** ◼ The interviewer wants to hear who changes the DOM. A candidate who says "React has nicer syntax" has not answered. A strong candidate names the two models, imperative and declarative, and says what each one costs on a real page: in plain JavaScript every update is a command we write, and every place we forget keeps old data; in React a component describes the page for its data, and React makes the DOM match it. A strong candidate also names the one-variable rule by its common name, a single source of truth.

- [interview] **2. The Classic Trap** ◼ The classic trap is "React renders again, so it rebuilds the page". If that were true, every search box would lose its text each time any data changed. On our header, a saved change of the name left the typed "elections" in the box with its cursor: React changed two text nodes and kept the `<input>`.

- [interview] **3. What is Actually Going On** ◼ In plain JavaScript, the call to `updateHeaderUser` set the greeting and forgot the corner, so the page showed "Welcome back, Mary Brooks" beside "Signed in as Mary". In React, `SiteHeader` keeps the name in one variable, `userName`, and both places read it. When the name changed to Mary Brooks, React called `SiteHeader` again, compared the new description with the last one, and changed exactly two texts. The search box was the same node, so it kept what was typed. People call that description the virtual DOM.

- [interview] **4. Where It Gets Tricky** ◼ *Is React a framework?* React calls itself a library for building user interfaces, and it can run a whole page or only one part of a page that already exists. *Does React stop the old name from showing up anywhere?* Only where the JSX reads the variable: a name typed into the markup as fixed text keeps the old value, even in React. *What does React change when the new description is the same as the last one?* No text at all. *Can I still call `document.getElementById` inside a component?* On the component's first run its own elements are not in the page yet, so the call returns `null`; Lecture 10 shows the error this causes.

### Glossary

- [glossary] DOM ◼ The Document Object Model: the objects the browser builds in memory from the HTML, one for every tag, nested like the tags. The screen is drawn from the DOM, so changing the page means changing the DOM.
- [glossary] Imperative programming ◼ Code that gives the browser every command itself, such as finding an element and setting its text. From the Latin *imperare*, "to command".
- [glossary] Declarative programming ◼ Code that declares what the page should show for the current data, while React changes the DOM to match. From the Latin *declarare*, "to make clear, to announce".
- [glossary] Component ◼ A JavaScript function whose name starts with a capital letter and which returns JSX for one piece of the page. React calls it; our code does not.
- [glossary] JSX ◼ The markup a component returns. It looks like HTML but is JavaScript, and curly braces inside it place the value of a variable.
- [glossary] Virtual DOM ◼ The common name for the description a component returns, which React compares with the last one to change only what is new in the real DOM. react.dev calls the result "the minimal necessary operations".

### Summary

- [review-title] **Describing the page from data**

- [review-subtitle] ❒ Declarative programming: describing what the page shows, not how to change it
- [always-rule] ➔ ALWAYS describe what the page shows in the JSX a component returns, and let React build the DOM from it.
- [never-rule] ➔ NEVER find and change elements by hand with `document.getElementById` and `textContent` in a page that React builds.

- [review-subtitle] ❒ Single source of truth: describing many places from one value
- [always-rule] ➔ ALWAYS keep a value that shows in several places in one variable, and read it with curly braces in every place.
- [never-rule] ➔ NEVER type a copy of the value into the markup; a copy keeps the old value when the variable changes.

- [review-subtitle] ❒ The virtual DOM: describing the page again when the value changes
- [if-then-rule] ➔ IF the data changes THEN describe the page from the new data and let React change only the new text.
- [never-rule] ➔ NEVER rebuild part of the page with `innerHTML`; it makes new nodes, and every text box inside loses what the user typed.

- [closing-line] One description, one value, and the smallest change. ◼ Educational objective: the map's Closing Line, the last spoken sentence of the lesson.
