### What do we pass to the setter?

- [p] ◇ {theme, where the reader stands} Lecture 14 counted Likes with `setLikes(likes + 1)`: the next value came from the current one. Pages are full of such counters: tickets in an order, items in a cart, requests still waiting for the server. So every React developer meets the same question: when the next value of a state comes from its current value, what do we pass to the setter? ◼ Educational objective: the theme from the map's `## Theme and Options`, on counters every reader has seen.

- [p] ◇ {option 1: passing the next state} The first answer you know from Lecture 14: compute the new value and pass it. ◼ Educational objective: say what the first code is for before it appears.

- [code] Passing the next state:

```jsx title="Passing the next state"
setTickets(tickets + 1);
```

◼ **The what-this-introduces list:** 1. `tickets + 1`: computed by our code, then handed to the setter.

- [p] ◇ {option 1: point into the code, who decides what, where it fits} Our code reads `tickets`, the snapshot of this render (Lecture 16), adds 1, and gives React the result. React stores that number as it is. This is **passing the next state**: our code decides the new value. It fits most handlers: one update per click, and every value that does not depend on the old one, such as a message. ◼ Educational objective: a fair account of the first option, with who acts and where it fits.

- [p] ◇ {option 2: passing an updater function} The second answer is React's: give the setter a function instead of a value. ◼ Educational objective: the chapter's option, introduced by its purpose before its code.

- [code] Passing an updater function:

```jsx title="Passing an updater function"
setTickets(t => t + 1);
```

◼ **The what-this-introduces list:** 1. `t => t + 1`: an arrow function (Lecture 11) that takes the current count, `t`, and returns the next one.

- [p] ◇ {option 2: point into the code, who decides what, where it fits} The setter receives an arrow function. React does not store the function. It calls it with the newest value of the state, here named `t`, and stores what the function returns. Read `t => t + 1` as "take the current count and add 1". This is an **updater function**: React supplies the current value, and our function computes the next one from it. The name `t` is the first letter of `tickets`, a common convention; `prevTickets` is another. It fits when another update of the same state can come first, which is what this chapter shows. ◼ Educational objective: the term with its code, who acts (React calls, our function computes), and the naming convention (map Supporting row).

- [ways] Two ways to set a state from its current value ◼ (1) Set a state from its current value by **passing the next state** (Lecture 14): our code computes the new value from this render's snapshot and gives it to the setter. (2) Set a state from its current value by **passing an updater function** (this chapter): we give the setter a function, and React calls it with the newest value and stores what it returns. ◼ Educational objective: the `> [!WAYS]` box in the owner's frame (`lecture-structure` Section 12), each line with its exact term in bold, where it comes from, and its plain meaning.

### A function can wait with await

- [runway] `async` and `await`, in plain JavaScript first, used by Question 3 and Step 3.

- [p] ◇ {async and await, named with code} Buying tickets sends the order to a server, and the answer takes a moment. JavaScript lets a function wait for such a slow task without freezing the page. We mark the function **`async`**, and inside it, **`await`** pauses the function until the task is done. In this lesson the slow task is `sendOrder()`, a ready-made helper in `api.js` that stands for a request to the ticket server; it answers after one second. ◼ Educational objective: the refresher the map marks `yes`, in plain JavaScript first, with what each keyword does.

- [code] A function that waits for the server:

```js title="async and await"
async function buyTickets() {
  console.log('sending the order');
  await sendOrder(); // the function pauses here for one second
  console.log('the server answered');
}
```

◼ **The what-this-introduces list:** 1. `async`: marks a function that may wait. 2. `await sendOrder()`: pause here until the server answers.

- [p] ◇ {the second example: the page keeps working} `await` pauses only its own function. Code after the call runs at once, and the paused function goes on when the answer arrives. ◼ Educational objective: confirm the idea with a second, different snippet: the order of the three lines shows who waits.

- [code] The rest of the code does not wait:

```js title="Who waits"
buyTickets();
console.log('the page keeps working');
// sending the order
// the page keeps working
// the server answered (one second later)
```

◼ **The what-this-introduces list:** 1. The order of the three lines in the Console panel (verified in Node).

- [p] ◇ {the rule} While a function waits at `await`, the page keeps working, so the user can click again, and React can render, before the answer arrives. After the wait, the function goes on with the variables it had: it is a closure over the place it was made (Lecture 16). ◼ Educational objective: the closing rule, which Question 3's answer recalls in a few words.

### Principles of React: Batching and Updater Functions

- [preview] Everything in this lesson comes down to one idea: queued updates, which means that each setter call adds an update to a queue, and React works through the queue in the next render. First, batching, which means the updates wait for the whole handler: React renders once, after the last line of the handler has run. Second, the update queue, which means the updates apply in order: a plain value replaces the result so far, so three calls that read the same old number give that number plus one, three times over. Third, updater functions, which means each update starts from the result before it: a function given to the setter receives the newest value, so we use one when another update can come first. Fourth, pure updaters, which means each updater only computes the next value: React calls it during the next render, twice in development, so a log or a request belongs in the handler. ◼ Educational objective: the map's Spoken Preview, word for word, read aloud before Question 1.

> [!PRINCIPLE]
> **Principle 1: Batching: the updates wait for the whole handler**
> *React renders once, after the whole event handler has run, for every setter call the handler made.*
>
> An event handler is an ordinary function: it runs from its first line to its last. A setter call inside it does not run the component. It adds an update to a queue and asks for a new run. When the handler has returned, React runs the component once, with every update in the queue, and the screen changes once. This is **batching**. Two setters in one click give one run, so the screen never shows one change without the other. A second click is a new event, with its own handler and its own run.
>
> >> batching : React waits for the whole handler, then runs the component once for all its setter calls
>
> *We should do this:*
> `const [count, setCount] = useState(0);`
> `const [message, setMessage] = useState('');`
> `function handleClick() {`
> `  setCount(count + 1); // queued`
> `  setMessage('Added'); // queued`
> `} // one run: the screen shows 1 and Added together`

> [!PRINCIPLE]
> **Principle 2: The update queue: the updates apply in order**
> *The next render starts from the current state and applies the queued updates in the order of the calls; a plain value replaces the result so far, so three plain calls that read the same snapshot give the same number three times.*
>
> Every line of a handler reads the same value of `count`, the snapshot of the render that made it. With `count` at 0, `setCount(count + 1)` three times queues the same step three times: replace with 1. After the handler, React starts from 0 and applies the steps in order: 1, then 1, then 1. The screen shows 1. No update is lost; all three say the same thing. An updater function is a different kind of step: React passes it the result of the step before, so three `c => c + 1` take the value to 1, to 2, and to 3. Principle 3 shows when we need one.
>
> >> update queue : the list of updates one event made to a state, applied in order in the next render
>
> *We should do this:*
> `const [count, setCount] = useState(0);`
> `setCount(c => c + 1); // 0 + 1`
> `setCount(c => c + 1); // 1 + 1`
> `setCount(c => c + 1); // 2 + 1: the screen shows 3`
>
> *We should not do this:*
> `const [count, setCount] = useState(0);`
> `setCount(count + 1); // replace with 1`
> `setCount(count + 1); // replace with 1`
> `setCount(count + 1); // replace with 1: the screen shows 1`

> [!PRINCIPLE]
> **Principle 3: Updater functions: each update starts from the result before it**
> *When the next value comes from the previous one and another update of the same state can come first, we pass an updater function, such as `c => c + 1`, which receives the result so far; for one update per click, a plain value is fine.*
>
> A plain value is computed from the snapshot, the value the handler's render saw. It is right as long as nothing changed the state in between. > `}`

> `const [count, setCount] = useState(0);`

> [!PRINCIPLE]
> **Principle 4: Pure updaters: each updater only computes the next value**
> *An updater receives the result so far and returns the next value, and does nothing else, because React calls it during the next render, twice in development; a log, a request, or another setter goes in the handler.*
>
> Our code never calls an updater. It hands the function to the setter, and React calls it while it works out the next state, which is part of rendering. Rendering must be pure, as Lecture 12 showed, so an updater must be pure too: it receives a value, returns the next one, and changes nothing else. In development, Strict Mode calls every updater twice with the same value and keeps one result. A pure updater gives the same screen either way. A log or a request inside it runs twice. Such code goes in the handler.
>
> *We should do this:*
> `const [count, setCount] = useState(0);`
> `setCount(c => c + 1); // only computes`
> `console.log('added one'); // once per click`
>
> *We should not do this:*
> `const [count, setCount] = useState(0);`
> `setCount(c => {`
> `  console.log('added one'); // twice per click in development`
> `  return c + 1;`
> `});`

### Where you will meet this

- [p] 1. **Quantity buttons in carts and orders**: a "+3" or a helper called several times in one click passes an updater, never the same `count + 1` three times.
- [p] 2. **Requests in flight**: a counter of pending requests, or a list of completed ones, changes after `await` with an updater, because another request may have finished first.
- [p] 3. **Forms that set several fields on submit**: every setter in the handler lands in one render, so the screen never shows half the change.
- [p] 4. **Analytics and logging**: the event is sent from the handler, never from inside an updater, where Strict Mode doubles it.
- [p] 5. **Code review**: an updater on a value that does not depend on the old one, such as `setMessage(() => 'Saved')`, adds nothing; a plain `count + 1` after an `await` is a bug waiting for a second click.

### For the interview

- [interview] > **The Interview Question:** How does React queue multiple state updates, and when do you need an updater function?

- [interview] **1. The Hidden Signal** ◼ The interviewer wants to hear "batching" and "update queue", and when the updater is really needed. A junior answer says "always use the function form" or "setState is asynchronous". A strong answer says that setter calls queue updates, that React applies them in order in one render after the handler, and that an updater receives the result so far, which matters when another update can come first.

- [interview] **2. The Classic Trap** ◼ The classic trap is three `setTickets(tickets + 1)` calls in one click. Candidates guess 3; the screen shows 1. Some say React dropped two calls. It did not: all three read the snapshot 0, so all three queued "replace with 1". A second trap is a log or a request inside an updater: Strict Mode calls the updater twice in development, so the request goes out twice.

- [interview] **3. What is Actually Going On** ◼ Each setter call adds one step to a queue. React does not touch the screen while the click handler runs. When the handler returns, React applies the steps in order and renders once. With `tickets` at 0, `setTickets(tickets + 1)` three times queues the same step three times: replace with 1, and the screen shows 1. An updater like `t => t + 1` is a different kind of step: React passes it the result of the step before, so three updaters take the value from 0 to 1, to 2, and to 3.

- [interview] **4. Where It Gets Tricky** ◼ *What does `setTickets(tickets + 5); setTickets(t => t + 1); setTickets(42)` show from 0?* 42: the last plain value replaces the result so far. *Is an updater needed for one update per click?* No: React renders each click before the next handler runs, so the snapshot is current; an updater does no harm there. *What about an `async` handler?* After `await`, the handler still reads its old snapshot, so a counter set there needs an updater, or it goes to -1. *Why does a log inside an updater print twice?* Strict Mode calls updaters twice in development to expose side effects; the production build calls them once. *How do I store a function in state?* `setFormat(() => formatPrice)`: a function given directly would be called as an updater. *Can I force the screen to update before the next line?* `flushSync` does that (Lecture 65), and batching across timeouts and promises is Lecture 75.

### Glossary

- [glossary] Batching ◼ React's way of waiting until the whole event handler has run, then rendering once for all its setter calls.
- [glossary] Update queue ◼ The list of updates one event made to a state, which React applies in order, starting from the current state, in the next render.
- [glossary] Updater function ◼ A function given to a setter, such as `t => t + 1`, which React calls with the result so far and whose return value becomes the next state.
- [glossary] Passing the next state ◼ Giving the setter a value, such as `tickets + 1`, computed by our code from this render's snapshot.
- [glossary] `async` and `await` ◼ JavaScript keywords: `async` marks a function that may wait, and `await` pauses it until a slow task, such as a request, is done.

### Summary

- [review-title] **Queued updates: each setter call adds an update to a queue, and React works through the queue in the next render**

- [review-subtitle] ❒ Batching: the updates wait for the whole handler
- [always-rule] ➔ ALWAYS expect one render per click, after the handler's last line, however many setters it calls.
- [if-then-rule] ➔ IF one click changes several states THEN set them in any order; the screen shows them together.

- [review-subtitle] ❒ The update queue: the updates apply in order
- [never-rule] ➔ NEVER call `setCount(count + 1)` several times in one click to add several; every call reads the same snapshot.
- [if-then-rule] ➔ IF a queue mixes values and updaters THEN apply it in order from the current state: a value replaces, an updater adds to the result so far.

- [review-subtitle] ❒ Updater functions: each update starts from the result before it
- [if-then-rule] ➔ IF the next value comes from the previous one and another update can come first, in the same handler or after an `await`, THEN pass an updater such as `c => c + 1`.
- [if-then-rule] ➔ IF a click makes one update, or the new value does not come from the old one, THEN a plain value is fine.

- [review-subtitle] ❒ Pure updaters: each updater only computes the next value
- [never-rule] ➔ NEVER log, send a request, or call another setter inside an updater; Strict Mode runs it twice in development.
- [always-rule] ➔ ALWAYS put side effects in the handler, with the value they need computed there.

- [closing-line] The updates wait, apply in order, start from the result before them, and only compute. ◼ Educational objective: the map's Closing Line, the last spoken sentence of the lesson. The four subtitles above are the four thread labels word for word, so the summary repeats the structure the preview announced (`lecture-structure` Section 13).

**DO THIS:** pass updaters where another update can come first, and keep side effects in the handler

```jsx right
async function handleBuy() {
  setPending(p => p + 1);
  await sendOrder();
  setPending(p => p - 1);
  setCompleted(c => c + 1);
  console.log('analytics: order sent');
}
```

**DO NOT DO THIS:** read the snapshot after a wait, or log inside an updater

```jsx wrong
async function handleBuy() {
  setPending(pending + 1);
  await sendOrder();
  setPending(pending - 1);
  setCompleted(c => {
    console.log('analytics: order sent');
    return c + 1;
  });
}
```

| **Who computes the new value** | Our code, from this render's snapshot | React calls our function<br>with the result so far |

| **When it runs** | Our code computes it in the handler | React calls it in the next render,<br>twice in development |
