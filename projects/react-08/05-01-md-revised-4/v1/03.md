## Example: moving an old site's article card into React

The example for this whole lecture is a news site that is moving to React. Its old pages are plain HTML files, and their markup has to move into components. Here is one article card from the old site, first in its HTML file, then pasted as it is into the `return` of a component, `ArticleCard`:

::: row arrows caption="The same five lines of markup: in the old HTML file, the card shows; pasted into a component, an error overlay covers the page. The overlay counts lines in the whole file, where the image is line 4."
::: col title="In `old-site/index.html`" tone=plain
```html bad="2,3"
<article>
  <img src="/library.jpg" ~alt="Library">~ <!-- No end: the browser closes it by itself -->
  <h2 ~class~="title">Library Hours</h2> <!-- HTML's name: it styles the heading -->
  <p>Open until nine.</p>
</article>
```
```page size=mini
card: img=Library | title=Library Hours | text=Open until nine.
```
The browser reads the file as it is, and the card shows.
:::
::: col title="Pasted into `ArticleCard`'s `return`" tone=bad
```jsx bad="2,3"
<article>
  <img src="/library.jpg" ~alt="Library">~ {/* **WRONG:** no end: the build waits for </img> */}
  <h2 ~class~="title">Library Hours</h2> {/* **PROBLEMATIC:** HTML's name: a Console error */}
  <p>Open until nine.</p>
</article>
```
```overlay size=mini
message: [PARSE_ERROR] Expected corresponding JSX closing tag for 'img'.
file: src/App.jsx:4:8
```
The same lines in a component: the `<img>` has no end, so the build stops and an error overlay covers the page.
:::
:::

The browser never reads a component file as we wrote it. The dev server, Vite, first rewrites it into plain JavaScript; this rewrite is the **build**. When the build cannot read a file, nothing in that file runs, and Vite covers the page with a dark panel that names the problem, the **error overlay**. Look closely at the two lines marked in red. Each works in the HTML file. In the component, the image stops the build, and `class` still styles the heading but logs an error in the Console:

| in the pasted markup | in the HTML file | in the component |
| --- | --- | --- |
| `<img src="/library.jpg" alt="Library">`, with no end | the browser closes it by itself | the build stops: the overlay above (section 2) |
| `class="title"` | styles the heading | an error in the Console, once the build gets past the image (section 5) |
| the whole card | shows on the page | an error overlay instead of the card |

The markup is the same, so what changed is where it lives. In a component, markup is written in **JSX**: it looks like HTML, but it is JavaScript. That is the topic of this lecture: what changes when HTML moves into a component, and which rules every piece of JSX must follow?

## The components behind the page

This lecture's components all live in one file, `App.jsx`, so you see them at once; a later lecture gives each its own file. `main.jsx`, the file Vite runs first, shows `App` on the page:

```hierarchy layout=stack caption="The components of this lecture, all in App.jsx."
App | holds: the page | here: names each component with a tag
  ArticleCard | holds: the card pasted from the old site
  FeaturedArticles | holds: two featured articles, as list items
  SignUp | holds: the newsletter form
notes:
Each component is a function that returns JSX, the markup it draws.
`App` places the others with their tags, `<ArticleCard />`, `<FeaturedArticles />`, `<SignUp />`, and React calls each function where its tag stands.
The old site's markup goes into these functions, after `return`. Every problem in this lecture appears when that markup meets JavaScript.
```

## Two ways to put markup on the page

The same markup can reach the page in two ways:

```tree caption="Two places markup can live: an HTML file the browser reads, or a component the build turns into JavaScript."
Put an old page's markup on the page
- In an HTML file | the browser reads it as it is, and forgives open tags
- In a component, as JSX | the build turns it into JavaScript first, and stops at any open tag
```

Why does the difference matter? An HTML file forgives: a tag left open, or two tags side by side at the top of the file, still gives a page. The build does not: one open tag, or two tags side by side directly after `return`, stops the whole file, and nothing in it runs. Of this lecture's mistakes, only wrong attribute names get past it, and they show up as errors in the Console, as section 5 shows. In exchange, markup in a component is part of a function, so the component can be placed anywhere with one tag, and later fill its markup from data. So markup moves into components, and it follows JavaScript's rules.

## JSX in five rules

Pasted markup must follow five rules in a component. Two words first: a **box** here means an extra element on the page, such as a `<div>`, which the interview question calls a wrapper node; and a **root** is the one outermost tag a component returns, which holds all the others.

```tree caption="The five rules of JSX."
Five rules for pasted HTML in a component
- Each tag becomes a call | `<h2>` becomes a function call
- Every tag is closed | `<img />`, `<br />`
- One root per return | one `<article>` around the rest
- A Fragment when no box is wanted | `<>` and `</>`
- Attributes use JavaScript names | `className`, `htmlFor`
```

We take the rules in this order. The first explains all the others: once a tag is a call, the next two rules follow, and the build checks them before anything runs, so they appear as error overlays. The Fragment answers the problem the one-root rule creates. The attribute names come last, because the build accepts the wrong ones; only the Console complains, once the page runs.

## 1. Each tag becomes a call that returns an object

```tree size=mini here="Each tag becomes a call"
Five rules for pasted HTML in a component
- Each tag becomes a call
- Every tag is closed
- One root per return
- A Fragment when no box is wanted
- Attributes use JavaScript names
```

> [!FACT] A JavaScript **object** keeps values under names: `{ title: 'Library Hours', topic: 'City' }`. Each name with its value is a **property**. Stored in a variable, as `const article = { title: 'Library Hours' };`, a property is read with a dot: `article.title` gives `'Library Hours'`. An object can hold other objects, and square brackets hold a list of values, an **array**: `[1, 2, 3]`.

> [!PRINCIPLE]
> **Principle 1: Each tag becomes a call that returns an object**
>
> We read JSX as JavaScript. On the dev server, the build turns each tag into a call of `_jsxDEV`, a function it imports from React.
>
> The call returns an object that describes the element. React builds the DOM, the page's real elements, from those objects.
>
> *We should do this:*
>
> ```jsx
> function Greeting() {
>   const note = ~<p>Hello, John Hall</p>~; // The build turns this tag into a call that returns an object
>   return note;
> }
> ```

So we start with what the build does to one card, then to one of its tags.

```hierarchy
App | holds: the page
  ArticleCard | holds: its card markup, in a variable | here: logs the markup, then returns it
notes:
`App` places the card with `<ArticleCard />`.
`ArticleCard` stores its markup in a variable, `card`, logs it with `console.log`, and returns it.
We want: to see what the markup really is, once the build has rewritten it.
```

The card here already uses `className` instead of `class`; section 5 explains why. Everything else is the old markup, with the image left out for now:

```jsx title="App.jsx" good="8"
function ArticleCard() {
  const card = (
    <article>
      <h2 className="title">Library Hours</h2>
      <p>Open until nine.</p>
    </article>
  );
  console.log(~card~); // Logs the object the tag became, not markup
  return card;
}
```

The card appears on the page, with its title and its text. The Console does not show the markup as text. It shows an object, which we expand by clicking it; here it is shortened. Inside its `props`, `children` holds the tag's content: here an array of two more objects, one for each inner tag. This project leaves Strict Mode out, so the object is logged once:

```js title="Console panel: console.log(card), opened and shortened"
{
  ~type: 'article'~, // The tag's name, kept as text
  props: {
    ~children~: [ // The two inner tags, as objects of the same shape
      { type: 'h2', props: { className: 'title', children: 'Library Hours' } },
      { type: 'p', props: { children: 'Open until nine.' } },
    ],
  },
}
```

> [!FACT] To see a file as the browser received it, after the build: in the developer tools, open the **Network panel**, reload the page, click `App.jsx`, and open its Response. The Sources panel shows our original file by default, because the dev server also sends a source map, a file that links the rewritten code back to our lines.

In that Response, `App.jsx` has no tags at all. One tag, followed from the file to the page:

```stages caption="One tag on its way to the page, and where to see each stage."
We write | App.jsx | <h2 className="title">Library Hours</h2>
The build writes a call | Network panel, shortened | _jsxDEV("h2", { className: "title", children: "Library Hours" })
The call returns an object | Console panel, with console.log | { type: 'h2', props: { className: 'title', children: 'Library Hours' } }
React builds the DOM | Elements panel | <h2 class="title">Library Hours</h2>
```

This rewrite is the **JSX transform**. The tag's name becomes the call's first argument; its attributes and its content become one object, the second, which React keeps under the name `props`, a word a later lecture builds on. The call returns a plain object, a **React element**, and React builds the DOM from those objects, so the browser never receives JSX: it receives calls, and React builds the elements from them. The DOM shows `class`, not `className`: React writes the HTML name into the page, as section 5 explains. The dev server also adds a line at the top of the file that imports `_jsxDEV` from React. A separate command, `npm run build`, is a second rewrite, not the dev server's build: it rewrites every file once to publish the site, and there the call is the shorter `jsx`.

The transform also explains why a component's name starts with a capital letter. A name with a capital is written into the call as it is, as a reference to our function; a name with a small letter is written in quotes, as a string that names an HTML tag. With a small letter, the card does not appear, and the Console shows two errors, `<articleCard /> is using incorrect casing` and `The tag <articleCard> is unrecognized in this browser`:

```chain caption="Two tags and the calls the build writes for them, shortened."
+`<ArticleCard />` -> `_jsxDEV(ArticleCard)` -> the call holds our function: React calls it
!`<articleCard />` -> `_jsxDEV("articleCard")` -> the call holds only a string: an empty <articlecard> in the Elements panel, and two Console errors
```

## 2. Every tag is closed: <img />

```tree size=mini here="Every tag is closed"
Five rules for pasted HTML in a component
- Each tag becomes a call
- Every tag is closed
- One root per return
- A Fragment when no box is wanted
- Attributes use JavaScript names
```

> [!FACT] Inside JSX markup, a comment is written in curly braces, `{/* like this */}`; in plain JavaScript lines, `//` works as usual. The boxes use both. An HTML comment, `<!-- ... -->`, pasted into JSX stops the build with "HTML comments are not allowed in modules".

> [!FACT] Some HTML tags can never hold anything inside them, such as `<img>`, `<br>`, and `<input>`. They are called **void elements**, and HTML lets them stay open, with no closing tag.

> [!PRINCIPLE]
> **Principle 2: Every tag is closed, `<img />` and `<br />` too**
>
> We close every tag, with a closing tag or with a slash. That includes tags that hold nothing, such as `<img />` and `<br />`.
>
> The build must know where each tag ends. A tag left open stops the build, and nothing in the file runs.
>
> *We should do this:*
>
> ```jsx
> function Author() {
>   return (
>     <section>
>       <img src="/john.jpg" ~alt="John Hall" />~ {/* Closed with a slash: the tag ends here */}
>       <p>John Hall<br />Boston</p>
>     </section>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function Author() {
>   return (
>     <section>
>       <img src="/john.jpg" ~alt="John Hall">~ {/* **WRONG:** no slash: the build waits for </img> */}
>       <p>John Hall~<br>~Boston</p> {/* **WRONG:** the br is left open too */}
>     </section>
>   );
> }
> ```

Section 1 showed that each tag becomes a call. To write a call, the build must know where each tag's content ends. Now the card gets its photo back, as the old site wrote it:

```hierarchy
App | holds: the page
  ArticleCard | holds: the pasted card, with its photo | here: returns the card
notes:
`ArticleCard` returns the card from the old site, image included.
The `<img>` is written as HTML allows: open, with no closing tag.
We want: the photo and the title on the page.
```

```jsx title="App.jsx" bad="4"
function ArticleCard() {
  return (
    <article>
      <img src="/library.jpg" ~alt="Library">~ {/* **WRONG:** no end: the build waits for </img> */}
      <h2 className="title">Library Hours</h2>
    </article>
  );
}
```

When `<img>` has no slash, the build stops; with the slash, the card appears. The two versions differ in one line:

::: row caption="The image left open, and the image closed with a slash. Compare the two pages."
::: col title="The image left open" tone=bad
```jsx
<img src="/library.jpg" alt="Library">
```
```overlay size=mini
message: [PARSE_ERROR] Expected corresponding JSX closing tag for 'img'.
 4 │ <img src="/library.jpg" alt="Library">
   │  ─┬─
   │   ╰─── Opened here
 6 │ </article>
   │   ───┬───
   │      ╰───── Expected `</img>`
```
With the image open, the build reads on to line 6, finds `</article>` where it expected `</img>`, and stops; the overlay points back to line 4, where the image opened. Nothing in the file runs.
:::
::: col title="The image closed with a slash" tone=good
```jsx
<img src="/library.jpg" alt="Library" />
```
```page size=mini
card: img=Library | title=Library Hours
```
With the slash, the photo and the title appear.
:::
:::

After an open tag, the build reads everything as that tag's content, until it finds the matching closing tag. HTML makes an exception for void elements; JSX makes none:

```chain caption="What the build reads after the image, in each version."
!`<img ...>` opens -> the `<h2>` becomes the image's content -> at `</article>`, it still waits for `</img>`: the build stops
+`<img ... />` closes at once -> the `<h2>` sits next to the image -> `</article>` closes the card
```

```tree dir=right caption="How each kind of tag is closed in JSX."
How is a tag closed in JSX?
- +a tag with content | a closing tag: <p>...</p>, <li>...</li>
- +a void element, which never holds anything | a slash: <img />, <br />
- +any other tag, when empty | a slash or a closing tag: <div />
- !a tag left open, as HTML allows | the build stops
```

## 3. One root per return

```tree size=mini here="One root per return"
Five rules for pasted HTML in a component
- Each tag becomes a call
- Every tag is closed
- One root per return
- A Fragment when no box is wanted
- Attributes use JavaScript names
```

> [!PRINCIPLE]
> **Principle 3: One root per return**
>
> A component returns one root: one element, or a Fragment as section 4 shows, that holds the rest.
>
> Each tag is one call, and so one value. Two values side by side, with nothing joining them, are not valid JavaScript, so two tags side by side stop the build. This holds wherever JSX stands: after `return`, or in a variable.
>
> *We should do this:*
>
> ```jsx
> function Author() {
>   return (
>     ~<section>~ {/* One root holds both tags */}
>       <h2>John Hall</h2>
>       <p>Author of 12 articles</p>
>     </section>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function Author() {
>   return (
>     <h2>John Hall</h2>
>     ~<p>Author of 12 articles</p>~ {/* **WRONG:** a second root: the build stops */}
>   );
> }
> ```

Every tag is now closed. Another card on the old site has no `<article>` around it, only a heading and a paragraph:

```hierarchy
App | holds: the page
  ArticleCard | holds: a heading and a paragraph | here: returns them
notes:
`ArticleCard` returns the two tags from the old card, as they were.
In the HTML file, the two tags sat side by side, with nothing around them.
We want: the heading and the paragraph on the page.
```

When the two tags stand side by side after `return`, the build stops; with one element around both, the card appears:

::: row caption="Two tags side by side after return, and the same tags inside one article. Compare the two pages."
::: col title="Two tags side by side" tone=bad
```jsx
return (
  <h2>Library Hours</h2>
  ~<p>Open until nine.</p>~ {/* **WRONG:** a second root: the build stops */}
);
```
```overlay size=mini
message: Adjacent JSX elements must be wrapped in an enclosing tag.
help: Did you want a JSX fragment <>...</>?
```
With two tags side by side, the build stops, and nothing in the file runs.
:::
::: col title="One `<article>` around both" tone=good
```jsx
return (
  ~<article>~ {/* One root around both: the build passes */}
    <h2>Library Hours</h2>
    <p>Open until nine.</p>
  </article>
);
```
```page size=mini
card: title=Library Hours | text=Open until nine.
```
With one element around both, the card appears.
:::
:::

```chain caption="Why two tags side by side stop the build."
!two tags after `return` -> two calls, so two values side by side -> nothing joins them, so it is not valid JavaScript: the build stops
+one `<article>` around both -> one call, whose content holds the other two -> one value: the card appears
```

The two inner calls become the content of the outer one, its `children`, just as the `<h2>` and the `<p>` did in the object of section 1. The overlay's help line points at a second way to give one root, which section 4 takes up.

## 4. A Fragment when no box is wanted

```tree size=mini here="A Fragment when no box is wanted"
Five rules for pasted HTML in a component
- Each tag becomes a call
- Every tag is closed
- One root per return
- A Fragment when no box is wanted
- Attributes use JavaScript names
```

> [!FACT] In CSS, `display: flex` on a list makes a **flex layout**: the list's children sit side by side in a row. `.articles > li` is a **child selector**: it styles only an `<li>` that sits directly inside `.articles`, not one deeper down.

> [!PRINCIPLE]
> **Principle 4: A Fragment when the page needs no extra box**
>
> When tags need one root but the page needs no extra box, we group them with a Fragment, `<>` and `</>`. React adds no element for it.
>
> We keep a real element as the root only when the page needs that box, for its meaning or for a style.
>
> *We should do this:*
>
> ```jsx
> function Items() {
>   return (
>     ~<>~ {/* Groups the items, and adds no element to the DOM */}
>       <li>First</li>
>       <li>Second</li>
>     </>
>   );
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function Items() {
>   return (
>     ~<div>~ {/* **PROBLEMATIC:** a box between the list and its items */}
>       <li>First</li>
>       <li>Second</li>
>     </div>
>   );
> }
> ```

Section 3 gave the card one root, an `<article>`, which the page wants anyway. Sometimes the page wants no extra box at all. The home page shows its featured articles in a row, styled by `index.css`, which `main.jsx` imports:

```css title="index.css"
.articles { display: flex; gap: 24px; }
.articles > li { border: 1px solid #999; }
```

```hierarchy
App | holds: the list, `<ul className="articles">` | here: draws the list around the items
  FeaturedArticles | holds: two featured articles | here: returns the two list items
notes:
`App` owns the list, styled as a row, with a border on each item that sits directly inside it.
`FeaturedArticles` returns the two `<li>` items, and `App` places it inside the list: `<ul className="articles"><FeaturedArticles /></ul>`.
Two `<li>` side by side would stop the build, so they need one root.
We want: one root for the two items, and nothing between the list and its items, so the row and the borders still apply.
```

The quickest way to give the two items one root is a `<div>` around them. With the `<div>`, the build passes, and the Console stays clean (React checks some nesting rules, such as a `<div>` inside a table row, but not a `<div>` inside a `<ul>`), yet the row breaks; with a Fragment instead, the row and the borders appear:

::: row caption="The two featured articles, grouped by a div and by a Fragment. Compare the Elements panels and the two rows."
::: col title="Grouped by a `<div>`" tone=bad
```jsx
~<div>~ {/* **PROBLEMATIC:** now the list's only child */}
  <li>Ten easy summer recipes</li>
  <li>New park opens today</li>
</div>
```
```dom title="Elements panel"
<ul class="articles">
!  <div>
    <li>Ten easy summer recipes</li>
    <li>New park opens today</li>
!  </div>
</ul>
```
```page size=mini
stack: Ten easy summer recipes ; New park opens today
```
With the `<div>`, the list's only child is the `<div>`: the items stack, with no border.
:::
::: col title="Grouped by a Fragment, `<>`" tone=good
```jsx
~<>~ {/* No element: the items stay the list's children */}
  <li>Ten easy summer recipes</li>
  <li>New park opens today</li>
</>
```
```dom title="Elements panel"
<ul class="articles">
+  <li>Ten easy summer recipes</li>
+  <li>New park opens today</li>
</ul>
```
```page size=mini
row: Ten easy summer recipes ; New park opens today
```
With the Fragment, the items are the list's own children: a row, each with its border.
:::
:::

A `<div>` is a real element, so React builds it in the DOM, between the list and its items. The flex layout arranges the list's children, and its only child is now the `<div>`; the child selector finds no `<li>` directly inside the list. A **Fragment**, written `<>` and `</>`, is one call too, so it gives one root, but React builds no element for it and puts its children straight into the parent.

```tree dir=right caption="What to group tags with, and what each leaves in the DOM."
What groups the tags into one root?
- +a Fragment, <> and </> | when the page needs no box: nothing added to the DOM
- +an element, such as <article> | when the page needs the box, for its meaning or a style
- !a <div> between a list or a flex row and its items | when a style targets direct children, it misses the items
```

## 5. Attributes use JavaScript names: className, htmlFor

```tree size=mini here="Attributes use JavaScript names"
Five rules for pasted HTML in a component
- Each tag becomes a call
- Every tag is closed
- One root per return
- A Fragment when no box is wanted
- Attributes use JavaScript names
```

> [!FACT] JavaScript keeps some words for itself, such as `return`, `class`, and `for`: they are **reserved words**. HTML's `aria-*` attributes, such as `aria-label`, describe an element to screen readers; `data-*` attributes, such as `data-form-id`, store our own values on an element.

> [!PRINCIPLE]
> **Principle 5: Attributes use JavaScript names**
>
> Each attribute becomes a property of the object the call receives, and React mostly uses the DOM's own property names. So `class` becomes `className`, and `for` becomes `htmlFor`. The DOM chose those names because `class` and `for` are reserved words in JavaScript.
>
> Names of several words use camelCase, where each later word starts with a capital, such as `tabIndex`. Only `aria-*` and `data-*` keep their dashes.
>
> *We should do this:*
>
> ```jsx
> function SignUp() {
>   return <label ~className~="label" htmlFor="name">Name</label>; // JavaScript names: the Console stays clean
> }
> ```
>
> *We should not do this:*
>
> ```jsx
> function SignUp() {
>   return <label ~class~="label" for="name">Name</label>; // **PROBLEMATIC:** HTML names: React logs an error for each
> }
> ```

The build now accepts every pasted tag: each is closed, and each component has one root. One habit gets past the build: HTML's attribute names. The old newsletter form is pasted into `SignUp` with its HTML attributes:

```hierarchy
App | holds: the page
  SignUp | holds: the newsletter form | here: returns the form
notes:
`SignUp` returns the form from the old site, with a label and an email field.
In HTML, `for="email"` ties the label to the field, so a click on the label puts the cursor in the field.
We want: the same form, and a clean Console.
```

```jsx title="App.jsx" bad="4-5"
function SignUp() {
  return (
    <form>
      <label ~class~="label" for="email">Your email</label> {/* **PROBLEMATIC:** HTML names: class and for */}
      <input id="email" type="email" ~tabindex~="0" /> {/* **PROBLEMATIC:** React wants tabIndex */}
    </form>
  );
}
```

With the HTML names, the page looks right, and the label still works, but the Console fills with errors. With the JavaScript names, the same page has a clean Console:

::: row caption="The same form with HTML names and with JavaScript names. The pages look the same; compare the Consoles."
::: col title="HTML names" tone=bad
```jsx
<label class="label" for="email">
<input id="email" tabindex="0" />
```
```page size=mini
form: Your email
error: Invalid DOM property `class`. Did you mean `className`?
error: Invalid DOM property `for`. Did you mean `htmlFor`?
error: Invalid DOM property `tabindex`. Did you mean `tabIndex`?
```
With `class`, `for`, and `tabindex`, three errors fill the Console.
:::
::: col title="JavaScript names" tone=good
```jsx
<label className="label" htmlFor="email">
<input id="email" tabIndex="0" />
```
```page size=mini
form: Your email
quiet: Console: no messages
```
With `className`, `htmlFor`, and `tabIndex`, the Console is clean.
:::
:::

The attributes of a tag become the properties of the object its call receives, as `className` did in section 1, and React mostly names them as the DOM does: in JavaScript, an element's class is `element.className`, and a label's target is `label.htmlFor`. Other names of several words, SVG ones such as `stroke-width` included, simply use camelCase:

| in HTML | in JSX | why |
| --- | --- | --- |
| `class` | `className` | the DOM's name, since `class` is a reserved word |
| `for` | `htmlFor` | the DOM's name, since `for` is a reserved word |
| `tabindex` | `tabIndex` | a name of several words uses camelCase |
| `aria-label`, `data-form-id` | unchanged | `aria-*` and `data-*` keep their dashes |

Given `class` and `for`, React still writes them into the page as attributes, which is why the page looks right and the label still works. Only the Console shows the mistake, and only on the dev server: the site built with `npm run build` logs nothing, so the wrong names ship silently. A Console full of these errors also hides the one error that matters. In the Elements panel, the fixed form still shows `class="label"` and `for="email"`: React writes the HTML names into the DOM itself.

## Putting the five together

The old card, moved into a component the way the five sections showed: every tag a call, the image closed with a slash, one `<article>` as the root that the page needs, and `className` for `class`:

**DO THIS:**

```jsx right
function ArticleCard() {
  return (
    <article>
      <img src="/library.jpg" alt="Library" />
      <h2 className="title">Library Hours</h2>
      <p>Open until nine.</p>
    </article>
  );
}
```

The same card as it would come from an old page with no `<article>` around it, with three mistakes marked in red: the image left open, so the build stops (line 3); three tags side by side after `return`, so the build would stop there next (lines 3 to 5); and `class` instead of `className`, so the Console shows an error once the build passes (line 4):

**DO NOT DO THIS:**

```jsx wrong bad="3,4,5"
function ArticleCard() {
  return (
    <img src="/library.jpg" alt="Library">
    <h2 class="title">Library Hours</h2>
    <p>Open until nine.</p>
  );
}
```

## For the interview

- **What is JSX?** Not HTML. The build turns each tag into a function call; the call returns a plain object, a React element; and React builds the DOM from those objects. The browser never sees JSX, and every rule follows from that.
- **Is JSX just HTML with a few differences?** That is the classic trap. An open `<img>` stops the build, two tags side by side directly after `return` stop it again, and `class` fills the Console with errors. An HTML file accepts all three; in a component, the first two stop the build, and `class` still works but logs an error.
- **Does a Fragment appear in the Elements panel?** No. Its children sit directly inside the parent, as the two `<li>` items did in the list.
- **Can I keep the HTML comments of my old page?** No: `<!-- ... -->` stops the build. Inside the markup, a comment is written `{/* ... */}`.
- **Old tutorials start each file with `import React from 'react'`. Do I need it?** Not for JSX. The old transform turned each tag into `React.createElement`, which needed `React` in the file. React 19 requires the new transform, which adds its own import, as the Network panel's Response shows.

## Where you will meet this

- A designer's HTML mockup, or a snippet copied from a CSS library: every open `<input>` or `<img>`, every group of tags side by side at the top of a `return`, and every `class` needs the five checks of this lecture.
- A component that returns several table cells for one row: when the cells sit side by side with no box around them, a Fragment, because a `<div>` inside a `<tr>` breaks the table, and React logs an error that a `<div>` cannot be a child of a `<tr>`.
- An icon pasted from a design tool as SVG markup: an attribute of several words with a dash, such as `stroke-width`, becomes `strokeWidth`.

## Summary

```tree caption="The whole lecture as one tree."
Put an old page's markup on the page
- In an HTML file | the browser reads it as it is
- In a component, as JSX | the build turns it into JavaScript
  - Each tag becomes a call | a call that returns an object; React builds the DOM
  - Every tag is closed | a closing tag, or a slash: `<img />`
  - One root per return | one element, or a Fragment, around the rest
  - A Fragment when no box is wanted | `<>` and `</>`: no element in the DOM
  - Attributes use JavaScript names | `className`, `htmlFor`, `tabIndex`
```

**One call per tag, every tag closed, one root, a Fragment when the page needs no box, and JavaScript names.**
