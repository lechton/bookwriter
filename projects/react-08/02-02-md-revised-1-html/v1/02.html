Lecture 2: Component Anatomy and the Capitalization Rule

Interview Question

CORE

What is a React component, and what rules govern how you write and name one?

Imagine this scenario:

  1. You wrote a function that returns the markup for an article card, with a title and a short text.
  2. You save the file, and the page shows no card and no error.
  3. How does a function you write become a piece of the page?

A page is made of pieces, and each piece is a function

A site that lists articles shows the same kind of piece many times: a card for each article, a box for comments under each card, and a footer at the bottom of every page. Lecture 1 wrote one piece, the header, as one component, and main.jsx showed it. A real page needs many pieces, and some of them appear more than once. So every developer who starts with React asks the same thing: how does a function I write become a piece of the page, and how do I use it again?

The answer is one idea, and this chapter follows it from the first question to the last: a component is a function React calls. We write the function, and React calls it wherever a tag names it. Each rule of the chapter follows one tag on its way to the page: the tag itself, the first letter of its name, what the function gives back, and what happens on the next run.

This lesson answers four questions:

  • I wrote the function ArticleCard. Who calls it, and when?
  • Does it matter whether I name it articleCard or ArticleCard?
  • My markup is long. Can I start it on the line after return?
  • ArticleCard is used only inside App. Can I define it inside App?

The questions stand on what Lecture 1 established:

  • Lecture 1 (What is React): A component is a JavaScript function that returns JSX, markup that looks like HTML and describes one piece of the page. React builds the DOM, the tree of nodes the browser draws, from that description, and the Elements panel shows those nodes. export default lets another file use the function.
  • Lecture 1 (The dev server and the virtual DOM): The dev server sends each saved change to the open page. On a save, React calls the component again, compares the new description with the last one, and changes only what is new. People call that description the virtual DOM. Because React changes only what is new, a text box keeps what the user typed and keeps the focus.

A function runs only when something calls it

In plain JavaScript, the name of a function can appear in two ways, and they do different things. With parentheses after it, the name is a call: the function runs now and gives back its result. Without parentheses, the name is a reference: it stands for the function itself, which has not run.

Plain JavaScript: a call and a reference
1function sayHello() {
2 console.log('sayHello runs');
A line in the Console panel
3 return 'Hello';
4}
5const text = sayHello();
A call: it runs, text is 'Hello'
6button.addEventListener('click', sayHello);
A reference

console.log('sayHello runs') prints a message each time its line runs. The messages appear in the Console panel, next to the Elements panel in the browser's developer tools. sayHello() on the fifth line runs the function at once, so the Console panel shows "sayHello runs".

On the last line, addEventListener gets sayHello with no parentheses: the function itself. Our code never calls it there. The browser calls it later, once for each click, and each click adds one more message to the Console panel.

JavaScript names and HTML tags use different letters

Plain JavaScript names functions and variables in camelCase. The first word starts with a small letter, and every later word starts with a capital, as in sayHello or formatDate. The capitals in the middle stand up like the humps of a camel.

PascalCase starts every word with a capital, the first one too, as in ArticleCard. The name comes from the Pascal programming language, which used this style.

HTML tags are written in small letters: <article>, <footer>, <input>.

A return with nothing after it gives back undefined

A function gives back what its return names. When return names nothing, the function gives back undefined, JavaScript's value for "no value here":

Plain JavaScript: return with nothing after it
1function getTitle() {
2 return;
Ends the function here
3}
4const title = getTitle();
Title is undefined

JavaScript also lets us leave out the semicolon at the end of a line, so const city = 'Boston' works with or without one. When a line could end a statement, JavaScript ends it there, as if we had typed the semicolon. This is called automatic semicolon insertion. Most of the time it does what we meant. Question 3 shows the one place where it does not.

Many code editors run a tool called ESLint. It reads the code as we type and underlines lines that are probably mistakes, each with a short message. It does not change the code, and it does not stop the page from running.

A function defined inside another one is new on every call

A function written directly in the file, outside every other function, is at the top level of the file. JavaScript runs that line once, when the file loads, so the name stands for one function for as long as the page is open.

A function can also be written inside another function. It is then a nested function, and its line runs each time the outer function runs:

Plain JavaScript: a nested function, made on every call
1function makeGreeter() {
2 function greet() {
Runs each time makeGreeter runs
3 return 'Hello';
4 }
5 return greet;
6}
7makeGreeter() === makeGreeter();
False: two different functions

Each call of makeGreeter runs the line function greet() again and makes a new function. The two greet functions do the same work, but they are two different functions, so ===, which is true only for the very same function, gives false. A function at the top level is made once, and its name gives the same function every time.

The project for this lesson keeps every component in App.jsx

The code of this lesson runs in a small project like the one from Lecture 1. This time main.jsx shows a component called App, and every component of the lesson lives in one file, App.jsx. React allows that: a file can hold several components, and the React documentation keeps small components that work together in one file. A real app usually gives each main component its own file, such as ArticleCard.jsx, so that no file grows to hundreds of lines. This lesson keeps every component in App.jsx so that you can see all of them at once. Lecture 8 shows how to give each component its own file with import and export.

Principles of React: A Component Is a Function React Calls

Everything in this lesson comes down to one idea: a component is a function that React calls, never our code.

First, rendering, which means React calls the component wherever a tag names it: we write the component's name as a tag in another component's markup, and React runs the function and puts what it returns on the page.

Second, PascalCase, which means React calls only the tags that start with a capital letter: a tag that starts with a small letter is read as an HTML tag, so our function never runs.

Third, automatic semicolon insertion, which means React calls the function and gets back only what starts on the return line: markup that starts on the next line is never returned, so we open the parentheses on the return line.

Fourth, top-level components, which means React calls the same function on every run: we define each component at the top level of the file, because a component defined inside another one is a new function every time, and React rebuilds everything it shows.

The code works as written: nothing names the card, so nothing calls it.

PRINCIPLE 1

Rendering: React calls the component wherever a tag names it

We use a component by writing its name as a tag in another component's markup, and React calls the function once for each tag; our code never calls it.

A component is a function, and a function runs only when something calls it. The tag hands React the function itself. While React runs the component that holds the tag, it calls the function once for each tag and builds the DOM from what each call returns. A function that no tag names never runs. The DOM holds only the HTML tags the function returns, never a tag with the component's name.

We should do this:
function Greeting() {
return <p>Hello, John Hall</p>;
}
function Page() {
return <Greeting />;
React calls Greeting
}

10export default function App() {

A small a here too

The page shows no card, and "articleCard runs" never appears. The Elements panel shows an empty element with the name in small letters:

Elements panel
1<main>

Empty, and all small letters

The Console panel shows two errors from React. The first says: "<articleCard /> is using incorrect casing. Use PascalCase for React components, or lowercase for HTML elements." The second says: "The tag <articleCard> is unrecognized in this browser. If you meant to render a React component, start its name with an uppercase letter."

Does it matter whether I name it articleCard or ArticleCard?

ANSWER

The code does not do what we wanted. The card never appears, because React never calls the function.

React looks at the first letter of each tag. A small letter means an HTML tag, like <article>, so React hands the browser the text 'articleCard', not our function. The browser has no such tag, so it makes an empty element, and the Elements panel shows its name in small letters. Our function never runs, so its message never appears. The two errors in the Console panel are the only signal.

A developer who reads the errors may rename only the tag to <ArticleCard />. Then the page throws "ArticleCard is not defined", and the whole page is empty, not only the card, because App itself fails. The fix needs both names. Line 1 names the function with a capital letter:

App.jsx
1function ArticleCard() {
A capital A here
2 console.log('ArticleCard runs');

Line 13, in App, writes the tag the same way:

App.jsx
13 <ArticleCard />
And a capital A here

Now the card appears, and the Console panel shows "ArticleCard runs". This is why component names use PascalCase: one capital letter tells React, and every reader, that the tag is ours and not an HTML tag. Lecture 3 shows that the call for <articleCard /> takes a text, while the call for <ArticleCard /> takes our function.

PRINCIPLE 2

PascalCase: React calls only the tags that start with a capital letter

We start a component's name with a capital letter, in the function and in the tag, because a tag with a small first letter is read as an HTML tag and our function never runs.

React decides what a tag is by its first letter. A capital letter hands React our function, and React calls it. A small letter means an HTML tag, so the browser makes an element with that name. An unknown name gives an empty element, and our function never runs. Renaming the tag without the function leaves the name undefined, and the whole page fails.

We should do this:
function ProfileCard() {
return <p>John Hall</p>;
}
<ProfileCard />
React calls ProfileCard
We should not do this:
function profileCard() {
return <p>John Hall</p>;
}
<profileCard />
PROBLEMATIC: lowercase tag never runs function
QUESTION 3

A return alone on its line gives back nothing

The card's markup grows, and a developer moves it to the line after return, so it lines up neatly:

App.jsx
1function ArticleCard() {
2 return
The statement ends here
3 <article>
4 <h2>New Park Opens Today</h2>
5 <p>The park on Main Street opens at noon.</p>
6 </article>;
7}

App still names <ArticleCard />. The page shows an empty <main>. The Console panel shows no error, and the terminal where the dev server runs shows no warning. Only an editor that runs ESLint underlines the <article> line, with the message "Unreachable code".

My markup is long. Can I start it on the line after return?

ANSWER

The code does not do what we wanted. The function gives back nothing, so React has nothing to show.

return alone on its line can end a statement, so automatic semicolon insertion ends it there, as if we had typed return;. The function gives back undefined, as getTitle did at the start of this lecture, and the markup below is never reached. React called ArticleCard and got nothing back, so it shows nothing in the card's place.

Nothing is wrong in JavaScript's eyes, so no error appears anywhere. ESLint is the one tool that notices: it marks the lines below return as "Unreachable code", code that can never run.

The fix is to open a parenthesis on the return line. The statement cannot end while a parenthesis is open, so it goes on until the markup is closed:

App.jsx
1function ArticleCard() {
2 return (
The parenthesis opens here
3 <article>
4 <h2>New Park Opens Today</h2>
5 <p>The park on Main Street opens at noon.</p>
6 </article>
7 );
8}

The card appears again. Markup that fits on the return line needs no parentheses, such as return <footer>Latest Articles, 2026</footer>; The parentheses are for markup that starts on the next line.

PRINCIPLE 3

Automatic semicolon insertion: React calls the function and gets back only what starts on the return line

When the markup does not fit on the return line, we open the parentheses on the return line, because a return alone on its line gives back nothing.

JavaScript ends a return that stands alone on its line, as if a semicolon followed it. The function gives back undefined, and the markup below it never runs. React gets nothing, so it shows nothing, and no error appears. A parenthesis opened on the return line keeps the statement going until the markup is closed.

We should do this:
function Greeting() {
return (
the statement goes on
<section>
<h2>Hello, John Hall</h2>
</section>
);
}
We should not do this:
function Greeting() {
return
WRONG: returns undefined, crashing render
<section>
<h2>Hello, John Hall</h2>
</section>;
}
QUESTION 4

A card defined inside App loses the typed comment on every save

The card now has a comment box. ArticleCard is used only by App, so a developer writes it inside App, the way plain JavaScript often keeps a helper inside the only function that uses it:

App.jsx
1export default function App() {
2 function ArticleCard() {
Defined inside App
3 return (
4 <article>
5 <h2>New Park Opens Today</h2>
6 <input placeholder="Write a comment" />
7 </article>
8 );
9 }

Below the card, App returns it:

10 return <main><ArticleCard /></main>;
React calls the inner card
11}

The first run looks right. The developer types "See you there" into the comment box, then changes the title in the file to "New Park Opens on Saturday" and saves. The new title shows, but the comment box is empty, and the cursor is gone.

ArticleCard is used only inside App. Can I define it inside App?

ANSWER

The code does not do what we wanted. Every run of App makes a new ArticleCard, and React rebuilds the card from scratch.

As in Lecture 1, the save makes React call App again. This run reaches the line function ArticleCard() and makes a new function, just as each call of makeGreeter made a new greet. React compares the new description with the last one and finds a different function in the card's place.

To React, a different function is a different component. So it removes the old <article>, with its <input>, and builds new nodes. The new box was never typed into, so it is empty, and the old box, which had the focus, is gone.

The fix is to move ArticleCard out of App, to the top level of the file:

App.jsx
1function ArticleCard() {
At the top level, beside App
2 return (
3 <article>
4 <h2>New Park Opens Today</h2>
5 <input placeholder="Write a comment" />
6 </article>
7 );
8}

App keeps only the tag:

9export default function App() {
10 return <main><ArticleCard /></main>;
Only the tag stays here
11}

Now type "See you there" again, change the title, and save. The box still holds "See you there", and the cursor still blinks in it. React found the same ArticleCard in the card's place, so it changed only the title text. On a save, the dev server matches each top-level component of the file to its old version by its name. A nested component has no such match.

What React finds in the card's place on the save
ArticleCard is   last run      this run      in the DOM
inside App       function #1   function #2   new <article>, empty box
at top level     ArticleCard   ArticleCard   same <input>, "See you there" kept

The save is not the only time App runs again. Lecture 14 shows a component running again while the page is open, when its data changes, and a nested card would lose the typed text there too. Lecture 24 explains how React matches components from one run to the next. And a card that needs data from App gets it through props, which Lecture 6 teaches, not by living inside App.

PRINCIPLE 4

Top-level components: React calls the same function on every run

We define every component at the top level of the file, beside the others, and never inside another component.

React compares the new description with the last one, and it knows a component by its function. A component defined inside another one is made again on each run of the outer component, so React finds a different function in the same place. It removes the old elements and builds new ones, and a text box loses what the user typed and the focus. A component at the top level is made once, so React finds the same function and keeps its elements.

We should do this:
function SearchBox() {
return <input placeholder="Search" />;
}
function Profile() {
return <SearchBox />;
the same SearchBox on every run
}
We should not do this:
function Profile() {
function SearchBox() {
PROBLEMATIC: re-created on each run, resetting state
return <input placeholder="Search" />;
}
return <SearchBox />;
}

⚡ IN THE WILD

Can I call ArticleCard() myself instead of writing the tag? It works today, and that is the trap. If App writes {ArticleCard()} inside <main>, the page shows the same card, and the Console panel shows "ArticleCard runs". But our code ran the function while App was running, so React received only the <article> it returned. React never learned that a component was there. The React documentation's rule is short: Never call component functions directly. Use every component as a component tag, so React decides when to call it. The cost of the hand call shows once a component keeps its own data, which Lecture 37 explains.

Component Summary

main

The entry file names <App />, so every run starts with App. No step changed it.

App

Four top-level components. App names <ArticleCard /> and <Footer />, and ArticleCard names <CommentBox />. React called them in the order of their tags, and none of them is called by our code. The footer's markup opens its parentheses on the return line. When the title changed, React changed one text and kept the comment box with what the reader typed.

A developer who comes from plain JavaScript brings four habits: call each function where its markup should go, name it like any other function, start long markup on a fresh line, and keep a helper inside the only function that uses it. Each habit breaks a component in its own way. A call hides the component from React, a small letter turns it into an empty HTML tag, a bare return gives back nothing, and a nested definition empties the comment box on every run. In React 19, the four steps avoided all four: each piece is a tag, each name starts with a capital letter, each long return opens its parentheses on the return line, and each component sits at the top level, so the page kept what the reader typed.

Where you will meet this

  1. A list of cards: a site that lists articles, a shop, or a feed writes one card component and names its tag once for each item. Lecture 6 shows how each card gets its own text.
  2. Names that match HTML tags: most apps have a Header, a Footer, a Button, or a Form component. The capital letter is the only thing that tells React to call ours instead of making the HTML tag.
  3. A card that vanished after a reformat: a teammate moves the markup to the line after return to make it easier to read, and the card is gone with no error. ESLint's "Unreachable code" points at the line.
  4. A chat box that keeps emptying: a message box defined inside the chat window component loses the half-typed message every time the window runs again. Moving it to the top level fixes it.

For the interview

The Interview Question: What is a React component, and what rules govern how you write and name one?

1. The Hidden Signal

The interviewer wants to hear who calls the component. A candidate who says "a component is a function that returns HTML" has given half an answer. A strong candidate says that our code never calls it: we write its name as a tag, React calls it, and that call is called rendering. A strong candidate also treats the capital letter as a rule React acts on, not a matter of style.

2. The Classic Trap

The classic trap is "capitalization is just a naming convention." On our page, <articleCard /> showed no card, the Elements panel held an empty <articlecard> element, and the function never ran. A convention would not change what the browser builds.

3. What is Actually Going On

A tag with a capital letter hands React the function itself. While React renders the parent, it calls the function once for each tag and builds the DOM from what it returns. A return alone on its line gives back undefined, so React shows nothing.

A component defined inside another one is a new function on every run of the outer one. React finds a different function in the same place, removes the old elements, and builds new ones, so a comment box loses what was typed.

4. Where It Gets Tricky

Is <ArticleCard /> the same as ArticleCard()?

The page can look the same, but with the call, React never learns that a component was there. The React documentation says never to call component functions directly, and Lecture 37 shows the cost.

Why does every message appear twice in a new project?

A new Vite project turns on Strict Mode, which runs each component twice while you develop. Lecture 12 explains why.

Can several components live in one file?

Yes. This lesson keeps four in App.jsx, each at the top level. Real apps keep small components that work together in one file too, while each main component usually gets its own. Lecture 8 shows how to split them into files.

Does a component that gives back undefined throw an error?

No. React 19 shows nothing in its place and prints no error, which is why the bare return is hard to find.

Glossary

  • Component: A JavaScript function whose name starts with a capital letter and which returns JSX for one piece of the page. React calls it; our code does not.
  • Component tag: A component's name written as a tag, such as <ArticleCard />, in another component's markup. It hands React the function.
  • Rendering: React calling a component to find out what it shows.
  • camelCase: The usual style for JavaScript names: the first word starts with a small letter, and every later word with a capital, as in formatDate.
  • PascalCase: A style where every word starts with a capital, as in ArticleCard. Component names use it.
  • undefined: JavaScript's value for "no value here". A function whose return names nothing gives it back.
  • Automatic semicolon insertion: JavaScript ending a statement at the end of a line, as if a semicolon were there, when the line could end it.
  • ESLint: A tool that reads code as we write it and underlines likely mistakes, such as "Unreachable code".
  • Top level: The part of a file outside every function. A function written there is made once.
  • Strict Mode: A development check from React that runs each component twice, so every console.log in a component appears twice.

Summary

A component is a function React calls

❒ Rendering: React calls the component wherever a tag names it

➔ ALWAYS use a component by writing its name as a tag, such as <ArticleCard />, in another component's markup.

➔ NEVER call a component function yourself, such as {ArticleCard()}; let React call it.

❒ PascalCase: React calls only the tags that start with a capital letter

➔ ALWAYS start a component's name with a capital letter, in the function and in the tag.

➔ NEVER give a component a name with a small first letter; React reads its tag as an HTML tag, and the function never runs.

❒ Automatic semicolon insertion: React calls the function and gets back only what starts on the return line

➔ IF the markup does not fit on the return line THEN open the parentheses on the return line.

➔ NEVER leave return alone on its line; the function gives back undefined, and nothing shows.

❒ Top-level components: React calls the same function on every run

➔ ALWAYS define every component at the top level of the file, beside the others.

➔ NEVER define a component inside another component; it is new on every run, and its text boxes lose what the user typed.
