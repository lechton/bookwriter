# Q13: Responding to Events and Callback Props
* **Topic Tag**: `#event_handling` | `❱ CORE`
* **Interview Question**: *How do you respond to user events like clicks and typing, and how do callback props communicate back to parents?*
* **Core Truth**: React attaches event handlers declaratively as camelCase function props (like `onClick` and `onChange`); handlers receive synthetic events and execute in response to user actions, while callback props allow children to notify parents without violating unidirectional data flow.
* **The Friction**: An engineer writes `onClick={handleClick()}` instead of `onClick={handleClick}` on a "Publish" button. The function executes immediately on page load before the user ever touches the button, triggering infinite loops or premature actions. Furthermore, child components need to report user clicks up to parent containers without mutating parent data directly.
* **The Mechanism**: Declarative event handlers (`onClick={handleClick}`), inline arrow functions for arguments (`onClick={() => handleSelect(article.id)}`), synthetic event handling (`e.stopPropagation()`, `e.preventDefault()`), and passing callback props from parent to child (inverse data flow).
* **Under the Hood**: Passing a function reference vs calling a function during render; how React wraps native browser events in a cross-browser SyntheticEvent wrapper, delegating events at the root container to maximize performance.
* **The Code Experiment**:
  * *Naive*: Invoking the handler immediately in JSX (`onClick={openArticle(id)}`) causing execution at render time, or child attempting to reassign parent variables.
  * *React*: An `ArticleCard` receiving an `onSelect` callback prop from `ArticleList`, invoking it cleanly on user click with arguments while stopping propagation.
* **Scope Boundary**: Focus strictly on event handler syntax, passing references vs invoking, synthetic event propagation, and callback props for child-to-parent communication. Do not introduce `useState` (reserved for Q14).
