# Q21: Reacting to Input with State
* **Topic Tag**: `#reacting_to_input` | `❱ CORE`
* **Interview Question**: *How do you design a component that reacts to input with state instead of touching the DOM?*
* **Core Truth**: Instead of telling the DOM what to change (disable this button, show that spinner), we list the visual states a component can be in (typing, submitting, success, error), keep the current one in state, and write JSX that describes each state; event handlers only set the next state, and React makes the DOM match.
* **The Friction**: A developer builds a sign-up form for members-only articles with imperative code: `button.disabled = true`, `spinner.classList.remove('hidden')`, `errorText.style.display = 'block'`. After a failed attempt the user retries and succeeds, but the success branch forgets to hide the error text, so the form shows "Sign-up failed" and "Welcome, Mary Jones" at the same time.
* **The Mechanism**: react.dev's five steps: (1) identify the component's visual states; (2) find what triggers each change, both human inputs (typing, clicking Sign Up) and computer inputs (the network response arriving); (3) represent the current state with `useState`, as one `status` string (`'typing' | 'submitting' | 'success' | 'error'`) rather than separate booleans; (4) remove state that adds nothing; (5) connect the event handlers that set `status`.
* **Under the Hood**: Why one `status` string beats separate booleans: four booleans (`isTyping`, `isSubmitting`, `isSuccess`, `isError`) allow sixteen combinations, most of them impossible, while a single string allows only the four listed values. Imperative code must handle the change from every state to every other state, while declarative JSX describes each state once, so adding a fifth state adds one branch instead of a new set of DOM edits.
* **The Code Experiment**:
  * *Naive*: Imperative event handlers querying elements with `document.querySelector` and manually toggling CSS classes and `disabled` properties, leaving the error and success messages visible together.
  * *React*: A `SignUpForm` with one `status` state (`'typing' | 'submitting' | 'success' | 'error'`) whose JSX disables the button while submitting and shows exactly one of the error banner or the welcome message.
* **Scope Boundary**: Focus on listing visual states, finding their triggers, and modeling them with one status value instead of DOM edits. Do not cover the full rules for removing redundant state (Q22), `useReducer` (Q26), state machine libraries such as XState, or React 19 form actions (Q40).
