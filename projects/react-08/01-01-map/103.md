# Q103: The Rendering Spectrum: CSR, SSR, Streaming SSR, Static Prerender, and Resuming
* **Topic Tag**: #rendering_models | ❱ CORE (Server)
* **Interview Question**: *How do CSR, SSR, streaming SSR, static prerendering, and resuming differ?*
* **Core Truth**: Modern web architectures span a spectrum of rendering models defined by when HTML is generated (build time, request time, or in-browser) and how interactivity is activated (client render, full hydration, selective hydration, or resumption).
* **The Friction**: The site needs instant page loads for old articles, sub-second TTFB for articles with a "New" label, and a rich interactive live score page; the developers treat all pages with a single rendering model, causing either stale cached data or sluggish server bottlenecks.
* **The Mechanism**: The 5 models: (1) CSR: browser downloads empty HTML and renders everything; (2) SSR: server renders full HTML string per request; (3) Streaming SSR: server streams HTML chunks with Suspense fallbacks; (4) Static Prerendering (SSG): HTML generated at build time; (5) Resuming: client continues from serialized server state without re-executing component render passes.
* **Under the Hood**: When bytes are emitted and what executes where: comparing the lifecycle timeline (Server Request -> TTFB -> First Chunk / Full HTML -> FCP -> JS Bundle Download -> Hydration / Execution -> TTI) across all five paradigms.
* **The Code Experiment**:
  * *Naive*: Building the entire site using a monolithic CSR setup where old articles and a live score share the exact same runtime rendering cost.
  * *React*: Classifying the site's pages along the spectrum: static prerendering for old articles, streaming SSR for the newest articles, and CSR widgets for personalized user settings.
* **Scope Boundary**: Focus on taxonomy, trade-offs, and comparing the five distinct rendering models. Do not implement deep streaming APIs or prerender internals.
