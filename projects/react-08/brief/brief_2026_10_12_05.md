# Brief 2026-10-12-05: The File-Name Evaluation in the Introduction

## Why

Lecture 8's opening (the first lesson whose code lives in more than one file) named only `App.jsx` in prose, hid the real file names behind conceptual tabs ("Dedicated component export", "Importing the component"), and imported `./components/ArticleCard.jsx` before any folder named `components` was introduced. The intro standards in `lecture-structure` Section 12 said nothing about file names or folders, and `code-blocks` Section 02 prescribed conceptual titles for comparisons, which a writer could read as covering this case.

## Group 1: The file-name evaluation (#2026_10_12_05_group_1)

- `lecture-structure` Section 12: one new check. Before a file name or a path appears in the opening, the writer makes a judgment call, judged by pedagogical clarity: a name that tells the reader where the code lives stays; a name that only decorates goes. When two or more files need to be named, the folder structure comes first in plain words (which folder holds which file), and the file names come after. The owner's correction shaped the rule: the trigger is the evaluation, not the lesson's topic.
- `code-blocks` Section 02: the conceptual-title line is reworded so it covers only code that is not a real project file; a snippet that lives in a real project file keeps the file's name on its tab. This prunes a conflict between two sections instead of stacking a new ban.
- `intro-examples.md`: Example 3, Lecture 8's opening quoted as written (failed) and redone with the evaluation applied (proper): the folder structure leads in plain words and a small tree, then the real file names appear on the tabs. It quotes Lecture 8, so it leaves the file before Lecture 8 is rebuilt from scratch.
