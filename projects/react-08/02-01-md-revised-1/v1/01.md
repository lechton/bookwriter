# Lecture 1: What is React and the Declarative Model
> INTERVIEW QUESTION | ❱ CORE | What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

1. You built a page header that shows the user's name in a greeting and again in the corner.
2. The user changes the name, your script updates the greeting, and the corner still shows the old name.
3. How does every place on the page show the new name?

### The page must change wherever the data appears

Most pages show the same piece of data in more than one place. A website greets the signed-in user at the top, "Welcome back, Mary", and shows the name again in the corner, "Signed in as Mary". When Mary adds her family name in her profile and becomes Mary Brooks, both places must show the new name. Every web developer meets this question: when the data changes, how does the page change with it?

The browser does not draw the HTML file directly. It reads the file and builds one object in memory for every tag, nested the way the tags are nested, so together they form a tree. Then it draws the screen from that tree. The tree is the **DOM**, the Document Object Model, and each object in it is a **DOM node**. HTML is the text we write; the DOM is what the browser builds from it and keeps. So to change what the screen shows, something must change the DOM.

The first answer is the one plain JavaScript taught you: you change the page yourself. You find the element, then you set its text.

```js title="Plain JavaScript: find the element, set its text"
const greeting = document.getElementById(~'greeting'~); // Finds <p> node by ID
greeting.textContent = ~'Welcome back, Mary Brooks'~; // New text on screen
```

`document.getElementById('greeting')` asks the browser for the DOM node whose `id` is `greeting`, and `textContent` replaces the text inside that node. Nothing else on the page changes. This is called **imperative programming**: you give the browser every command yourself. The word comes from the Latin *imperare*, "to command", the root of *emperor*. Like an emperor, the code orders every step. Imperative code fits well when one element changes in one place, such as a clock in the corner of a page.

The second answer is React's. Instead of the commands, you write what the element shows:

```jsx title="React: what the greeting shows"
<p>Welcome back, {userName}</p>
```

It looks like HTML, but `{userName}` marks a place where the value of the variable `userName` goes. No line finds the `<p>`, and no line sets its text. React reads this line, builds the `<p>`, and puts the current value in it. This is called **declarative programming**: you declare what the page should show, and React changes the DOM to match. The word comes from the Latin *declarare*, "to make clear, to announce". Declarative code fits when the same value shows in several places, or when many parts of the page change.

The corner works the same way:

```jsx title="React: what the corner shows"
<span>Signed in as {userName}</span>
```

The corner reads the same `userName` as the greeting. There is no second command to write, so there is no second command to forget. Imperative code tells the browser how to change the page, one command at a time. Declarative code says what the page shows, and React does the changing.

> [!WAYS] Two ways to update the DOM when the data changes
>
> (1) Update the DOM with **imperative programming** (plain JavaScript): you give the browser every command yourself, finding each element and setting its text.
>
> (2) Update the DOM with **declarative programming** (this chapter): you declare what each element should show, and React updates the DOM to match.

Declarative code still leaves room for the few jobs that need one particular element. To move the cursor into a search box, for example, React lets your code reach that one element without changing what it shows. Lecture 30 covers it.

React is a JavaScript library for building user interfaces out of components. It can run a whole page, or only one part of a page that already exists. This chapter follows one idea from its first question to its last: we describe the page from data, and React makes the browser match.

This lesson answers three questions:

- **I find each element and change its text. What do I write instead in React?**
- **The name shows in two places. Do I write it twice?**
- **When the name changes, does React throw the header away and wipe what I typed?**

The lesson builds on what you already know: HTML tags with an `id` attribute, and plain JavaScript, such as a variable made with `const` and two strings joined with `+`.

### innerHTML replaces every node inside an element

`textContent` changes the text inside one node and leaves the node itself in place. `innerHTML` does much more. It throws away every node inside an element and builds new nodes from a string of HTML:

```js title="Plain JavaScript: rebuild the inside of the header"
const header = document.getElementById(~'header'~); // Finds <header> node by ID
header.~innerHTML~ = '<p>Welcome back, Mary Brooks</p>'; // Replaces child nodes
```

After the second line, the `<header>` holds a new `<p>`, built from the string. The old `<p>` is gone, together with everything else that was inside the header. The screen may look the same, but every node inside the header is a new one.

One more browser word belongs here. When you click into a text box and type, that box has the **focus**: it is the element that receives the keys you press, and it shows a blinking cursor. Only one element on the page has the focus at a time. Click somewhere empty, and the focus goes back to the page itself.

### A component is a function that returns what the page shows

In React, a page is written as **components**. A component is a JavaScript function whose name starts with a capital letter and which returns the markup for one piece of the page. Lecture 2 gives the rules for writing one. Here is the header from the opening, written as a component:

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const userName = ~'Mary'~; // The name, written once
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as {userName}</span>
      <input placeholder="Search" />
    </header>
  );
}
```

`const userName = 'Mary'` makes a **local variable**: a name for a value, inside this function. The markup after `return` is **JSX**. It looks like HTML, but it is JavaScript, as Lecture 3 explains. Inside JSX, **curly braces** mark a place where a JavaScript value goes, so `{userName}` shows "Mary" in the greeting and again in the corner. Lecture 4 shows what else the braces can hold. `export default` lets another file use this function, as Lecture 8 explains.

Our code never calls `SiteHeader`. React calls it, and React uses the JSX it returns.

A second component works the same way, this time with a number:

```jsx title="A second component: SiteFooter"
export default function SiteFooter() {
  const year = ~2026~; // Number value placed in JSX
  return <footer>Copyright {year}</footer>;
}
```

Here `{year}` shows 2026. A component is a function that returns JSX, and curly braces place a value inside that JSX.

### The dev server shows each saved change of a file

The code of this lesson runs in a small project prepared for you. Three files matter, and each one holds a different part of the page:

```files title="Lesson 1 project: File Explorer"
index.html | parent | The page the browser loads, with one empty element for React
src/
  main.jsx | boundary | Hands that empty element to React and shows the header in it
  SiteHeader.jsx | child | The header component this lesson writes
```

`index.html` is the page the browser loads, and its body holds one empty element, `<div id="root"></div>`. `main.jsx` hands that element to React and tells React to show `SiteHeader` inside it; Lecture 9 explains how. `SiteHeader.jsx` is the component we write.

```html title="index.html"
<body>
  <div id=~"root"~></div> <!-- Empty container in the file -->
  <script type="module" src="/src/main.jsx"></script>
</body>
```

You start the project with the command `npm run dev`. It starts a **dev server**, a small program on your computer that sends the project to the browser while you work. Each time you save a file, the dev server sends the new code to the open page, and the page shows the change without a reload.

To see the DOM itself, open the browser's developer tools and choose the **Elements panel**. It shows the DOM nodes the page has right now, which is not always what the HTML file holds. When a node changes, the panel highlights it for a moment.

### Principles of React: Describing the Page from Data

Everything in this lesson comes down to one idea: we describe the page from data, and React makes the browser match.

First, declarative programming, which means describing what the page shows, not how to change it: we write what each element shows for the data, and React changes the DOM to match, so our code never finds an element by hand.

Second, a single source of truth, which means describing many places from one value: when a name appears in many places, every place reads it from one variable, so no place can show an old copy.

Third, the virtual DOM, which means describing the page again when the value changes and comparing the two descriptions: React changes only the new text, so whatever the user typed stays where it was.

### Question 1: The script changes the greeting and forgets the corner

The page from the opening, written in plain HTML, has a greeting and a corner, each with its own `id`:

```html title="index.html (plain JavaScript version)"
<p id="greeting">Welcome back, Mary</p>
<span id="account">Signed in as Mary</span>
```

When Mary changes her name, a script updates the header. It finds the greeting by its `id` and sets its text:

```js title="Plain JavaScript: updateHeaderUser"
function updateHeaderUser(name) {
  const greeting = document.getElementById('greeting');
  greeting.textContent = ~'Welcome back, ' + name~; // Updates greeting only
}

updateHeaderUser('Mary Brooks');
```

After the call, the page shows "Welcome back, Mary Brooks" at the top and "Signed in as Mary" in the corner.

**I find each element by its id and change its text. What do I write instead in React?**

---

**ANSWER**

**The code does not do what we wanted.** It changes exactly the nodes it names, and it names only the greeting.

The function has one line for the greeting and none for the corner, so the corner keeps "Mary". Every new place on the page that shows the name needs one more line in this function. One forgotten line is one place on the page with the old name.

In React, we write no such function. We write `SiteHeader`, the component from the start of this lecture, which returns JSX with `{userName}` in the greeting and in the corner. React calls `SiteHeader` and builds the DOM nodes from the JSX it returns.

You can see this in the browser. The file `index.html` still holds only the empty `<div id="root"></div>`, yet the Elements panel shows the whole header inside it:

```html title="Elements panel"
<div id=~"root"~> <!-- Empty element from index.html -->
  <~header~> <!-- Built by React -->
    <p>Welcome back, Mary</p>
    <span>Signed in as ~Mary~</span> <!-- Built from the same name -->
    <input placeholder="Search">
  </header>
</div>
```

Every one of these nodes was built by React from the description. A search of our code finds no `getElementById` and no `textContent`, so there is no line that a new place on the page could be missing. Because the component only describes, the same data always gives the same page; Lecture 12 explains why React counts on that.

> [!PRINCIPLE]
> **Principle 1: Declarative programming: describing what the page shows, not how to change it**
> *We control the page by describing what it shows from data, and we never find and change its elements by hand.*
>
> In plain JavaScript, the page changes only where our code finds an element and sets its text, so an element the code forgets keeps its old text. In React, a component returns JSX that says what each element shows for the current data. React calls the component and builds the DOM from what it returns. Our code has no line that finds or changes an element, so there is no element to forget. Reaching one element to move the cursor into it is a different job, which Lecture 30 shows.
>
> *We should do this:*
> `function Header() {`
> `  const name = 'John';`
> `  return <p>Hello, ~{name}~</p>; // React builds the <p>`
> `}`
>
> *We should not do this:*
> `function updateHeader(name) {`
> `  const el = document.getElementById('hello');`
> `  el.textContent = ~'Hello, ' + name~; // **PROBLEMATIC:** leaves rest of page stale`
> `}`

### Question 2: A name typed into the markup keeps the old value

A developer moves the header into React and copies the corner from the old HTML page, letters and all. The greeting reads the variable, but the corner keeps the name typed into it:

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const userName = ~'Mary Brooks'~; // Changed from 'Mary' and saved
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as ~Mary~</span> {/* Pasted from the HTML page */}
      <input placeholder="Search" />
    </header>
  );
}
```

With the dev server running, the developer changes `'Mary'` to `'Mary Brooks'` and saves. The page now shows "Welcome back, Mary Brooks" at the top and "Signed in as Mary" in the corner.

**The name shows in the greeting and in the corner. Do I write it in both places?**

---

**ANSWER**

**The code does not do what we wanted.** The corner holds a copy of the name, and the copy did not change.

React builds every element exactly as the JSX describes it. The greeting describes its text with `{userName}`, so React builds it from the variable, and it shows the new name. The corner describes its text as fixed letters, "Signed in as Mary", so React builds it from those letters, on this run and on every run after it. React did nothing wrong: the JSX asked for two different names.

The fix is one line, line 6 of the file. The corner reads the same variable as the greeting:

```jsx title="SiteHeader.jsx" startLine="6"
      <span>Signed in as ~{userName}~</span> {/* Signed in as Mary Brooks */}
```

Now both places are built from one variable, and the saved change shows "Mary Brooks" in both. This rule has a common name: a **single source of truth**. Each value lives in one place, and every part of the page reads it from there. Lecture 23 uses the same idea when two components must share a value that changes. A third place that shows the name, such as a line in the account menu, adds one more `{userName}` and no update code. In this lesson the name stays fixed in the code until we edit the file. A value that changes while the page is open needs state, which Lecture 14 teaches.

```ascii title="One variable, two places"
const userName = 'Mary Brooks'
  |
  +--> <p>Welcome back, {userName}</p>
  |      shows: Welcome back, Mary Brooks
  |
  +--> <span>Signed in as {userName}</span>
         shows: Signed in as Mary Brooks

<span>Signed in as Mary</span>
  shows: Signed in as Mary (fixed text, not read from the variable)
```

> [!PRINCIPLE]
> **Principle 2: Single source of truth: describing many places from one value**
> *When one value appears in many places, we describe every place from one variable, and we never type a copy of it.*
>
> A value often shows in more than one place, such as a name in a greeting and again in a corner of the page. A place that reads the variable in curly braces is built from it, so when the variable holds a new name, that place shows the new name. A copy typed into the markup is fixed text: it keeps the old name while the rest of the page shows the new one.
>
> *We should do this:*
> `const name = 'John Hall';`
> `<p>Hello, ~{name}~</p> {/* Hello, John Hall */}`
> `<span>Signed in as ~{name}~</span> {/* Signed in as John Hall */}`
>
> *We should not do this:*
> `const name = 'John Hall';`
> `<p>Hello, {name}</p>`
> `<span>Signed in as ~John~</span> {/* **PROBLEMATIC:** hardcoded text stays old */}`

### Question 3: Rebuilding the header empties the search box

The header now has a search box, and the user has typed "elections" into it. Then the name changes. In plain JavaScript, a common way to update a header is to rebuild its inside from a string with the new name:

```js title="Plain JavaScript: rebuild the header with the new name"
const name = 'Mary Brooks';
const header = document.getElementById('header');
header.innerHTML =
  '<p>Welcome back, ' + name + '</p>' +
  '<span>Signed in as ' + name + '</span>' +
  '<~input~ placeholder="Search">'; // A new empty input node
```

Both names change. But the search box is empty, and the cursor no longer blinks in it: the focus has gone back to the page itself. React also builds the header from a description, so a developer who has seen this may expect React to do the same.

**If React builds the header from my description, does it throw the header away when the name changes, and wipe what I typed in the search box?**

---

**ANSWER**

**The code does not do what we wanted, and React does not repeat its mistake.** `innerHTML` throws away the old search box; React keeps it.

As the start of this lecture showed, `innerHTML` throws away every node inside the header and builds new ones from the string. The new `<input>` was never typed into, so it is empty. The old one, which had the focus, is gone, so the focus has nowhere to stay but the page itself.

Now the same change in React. Type "elections" into the search box of `SiteHeader`, change the name on line 2 of the file, and save:

```jsx title="SiteHeader.jsx" startLine="2"
  const userName = ~'Mary Brooks'~; // Changed from 'Mary'
```

The save makes React call `SiteHeader` again, and the function returns a whole new description of the header, with the new name in it. React compares it with the last description, element by element. The text of the `<p>` is different, the text of the `<span>` is different, and the `<input>` is the same. So React changes those two texts in the DOM and leaves every other node where it is. The `<input>` is the same DOM node as before the save, so it still holds "elections", and the cursor still blinks in it. In the Elements panel, the two names flash as they change.

```ascii title="What React changes when the name changes"
element   last description     new description           in the DOM
<p>       Welcome back, Mary  Welcome back, Mary Brooks  text changed
<span>    Signed in as Mary   Signed in as Mary Brooks   text changed
<input>   search box           search box                same node

the same <input> node keeps "elections" and the blinking cursor
```

When the new description is the same as the last one, React changes no text at all. People often call the description that React compares the **virtual DOM**. The React documentation describes the result as "the minimal necessary operations": for this save, exactly two text changes. Lecture 15 gives each step of an update its name.

> [!PRINCIPLE]
> **Principle 3: The virtual DOM: describing the page again when the value changes**
> *When the value changes, React compares the new description with the last one and changes only the new text, so whatever the user typed stays where it was.*
>
> When the data changes, React calls the component again, and the component returns a whole new description with the new value in it. React compares it with the last description, element by element. It changes the text that is new and leaves every other node where it is. A text box is still the same node, so it keeps what the user typed and keeps the focus. Rebuilding the elements with `innerHTML` makes new nodes, and the typed text is gone.
>
> *We should do this:*
> `function Header() {`
> `  const name = ~'John Hall'~; // Changed from 'John'`
> `  return (`
> `    <header>`
> `      <p>Hello, ~{name}~</p> {/* Only this text changes */}`
> `      ~<input />~ {/* Keeps typed text and focus */}`
> `    </header>`
> `  );`
> `}`
>
> *We should not do this:*
> `const header = document.getElementById('header');`
> `header.~innerHTML~ = '<p>Hello, John Hall</p><input>'; // **PROBLEMATIC:** wipes input and focus`

> [!WILD]
> **Does React make the page faster than plain JavaScript?** No, and that is not its job. React changes the DOM with the same browser methods a script uses. On the first run it adds the nodes with **appendChild()**, and on the save it set the text of two nodes, exactly what a careful script would do by hand. A script that sets one text node does that same work with less code to run. React's gain is that our code no longer writes, or forgets, the update steps: it describes the page, and React works out the **minimal necessary operations**. So the corner is never left on the old name, and the search box is never rebuilt.

### Let's Design a Practical Example

Each question tested one principle on the smallest header that shows it. Now we build the header from the opening at its real size. Mary's name shows in three places: the greeting, the corner, and the account menu. The number of her new messages shows in two: the Messages link, and a notice below it. The header also holds the search box she types into. Each of the three steps applies one principle of this lesson, in the same order, and ends with what the page shows, so keep the dev server running and the Elements panel open.

```components title="site-header - Rendered UI Canvas"
SiteHeader.jsx | none | header | [elem:p: Welcome back, Mary Brooks] ;; [elem:span: Signed in as Mary Brooks] ;; [elem:button: Mary Brooks] ;; [elem:a: Messages (4)] ;; [elem:p: You have 4 new messages] ;; [elem:input: elections]
```

```files title="site-header: File Explorer"
src/

  SiteHeader.jsx | child | The header component: five places read two values, and a search box
```

### Step 1: First, we describe the header from its data <SiteHeader.jsx>

This step applies the first principle, declarative programming, which means describing what the page shows, not how to change it. The plain JavaScript page kept the name and the count inside its HTML, and a function such as `updateHeaderUser` changed them, one command per element. In React, there is no such function to bring over. We start from the data instead. The header depends on two values, who is signed in and how many messages are new, so each one gets a variable at the top of the component, and the JSX below says where each value shows:

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const userName = ~'Mary'~; // Who is signed in
  const unreadCount = ~3~; // How many messages are new
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <a href="/messages">Messages (~{unreadCount}~)</a> {/* Messages (3) */}
    </header>
  );
}
```

`unreadCount` is a number, and curly braces place it the same way `SiteFooter` placed `year`. Save the file and look at the Elements panel. The empty `<div id="root">` from `index.html` now holds a `<header>` with "Welcome back, Mary" and "Messages (3)", and the file has no `getElementById` and no `textContent`. Our code describes, and React builds.

### Step 2: Next, we read each value in every place that shows it <SiteHeader.jsx>

This step applies the second principle, a single source of truth, which means describing many places from one value. The full header adds three places: the corner and the account menu show the name, and a notice repeats the count. The notice is where a copy slips in most easily. It is a whole sentence, and typing "You have 3 new messages" looks finished. That would be Question 2's mistake again, on a number this time. So every place reads its value in curly braces, and the header now runs from line 5 to line 12:

```jsx title="SiteHeader.jsx" startLine="5"
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as ~{userName}~</span> {/* The corner */}
      <button>~{userName}~</button> {/* The account menu */}
      <a href="/messages">Messages ({unreadCount})</a>
      <p>You have ~{unreadCount}~ new messages</p> {/* Not a typed 3 */}
      <~input~ placeholder="Search" /> {/* Reads no value */}
    </header>
```

The page now shows five places built from two variables, and the component still has no update code. Plain JavaScript would need one command for each of the five places on every change, and one more command for each place someone adds later.

Why not give the account menu its own component? The header, greeting, and corner will form a tree of components, as Lecture 5 shows, but without a way to pass the name in, which Lecture 6 teaches, it would need its own copy of the name, and the copy is exactly what this step removes.

The last line, the search box, reads no variable at all. What it shows comes from the user, and Step 3 tests whether React leaves it alone.

### Step 3: Finally, we change both values while the user types <SiteHeader.jsx>

This step applies the third principle, the virtual DOM, which means describing the page again when the value changes, and it tests everything above. Type "elections" into the search box and leave the cursor in it. Then make both changes the opening promised: Mary becomes Mary Brooks, and a new message arrives, so the count goes from 3 to 4. Both values sit at the top of the component, on lines 2 and 3. Save:

```jsx title="SiteHeader.jsx" startLine="2"
  const userName = ~'Mary Brooks'~; // Changed from 'Mary'
  const unreadCount = ~4~; // Updated from 3
```

Before you look, predict what changes. React calls `SiteHeader` again, and it returns a new description with the new values in it. React compares it with the last one, place by place. Three places read `userName`, two read `unreadCount`, and the search box is the same as before. So React changes five texts in the DOM, and in the Elements panel those five values flash:

```ascii title="What React changes when both values change"
place          last description   new description   in the DOM
greeting       Mary               Mary Brooks       text changed
corner         Mary               Mary Brooks       text changed
account menu   Mary               Mary Brooks       text changed
Messages link  3                  4                 text changed
notice         3                  4                 text changed
search box     search box         search box        same node
```

The box still holds "elections", and the cursor still blinks in it, because the `<input>` is the same DOM node it was before the save. The plain JavaScript header rebuilt with `innerHTML` would have emptied the box. The version that sets each text by hand would have needed five commands, with five chances to forget one.

### Component Summary

```component-code title="Summary: The Logic of Nested Components"
main.jsx | none | boundary | [role: The **entry file** hands the empty `<div id="root">` of `index.html` to React and shows **SiteHeader** inside it. No step changed it.]
  SiteHeader.jsx | none | header | [role: The **header component** holds the data in two variables, **userName** and **unreadCount**, and five places read them. It returns the whole header as one description and calls no DOM method. When both values changed, React changed five texts and kept the search box with what the user typed.]
```

A developer who comes from plain JavaScript expects the update code to grow with the header: five places mean five commands for every change, and a sixth place means a sixth command that someone must remember. In React 19, the header grew from two places to five, and the update code stayed at zero lines. Each step applied one principle. The header is described from data, every place reads one variable, and a change of the data ends in exactly the texts that changed, while the search box stays as the user left it.

### Where you will meet this

1. **The signed-in name**: a site shows the user's name in a greeting, in the account menu, and next to every comment the user wrote. Each place reads one variable, so a name change reaches all of them at once.
2. **The cart count**: a shop shows the number of items in the header and again on the checkout button. Both read the same count, so the button never promises more items than the cart holds.
3. **The search results**: a results page shows "Results for elections" above the list while the same word stays in the search box. React changes the heading and leaves the box, with its cursor, as the user left it.
4. **The unread messages**: a mail app shows the unread count in the browser tab and again beside the inbox. One variable feeds both, so the tab and the inbox always agree.

### For the interview

> **The Interview Question:** What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

**1. The Hidden Signal**

The interviewer wants to hear who changes the DOM. A candidate who says "React has nicer syntax" has not answered. A strong candidate names the two models, imperative and declarative, and says what each one costs on a real page. In plain JavaScript, every update is a command we write, and every place we forget keeps old data. In React, a component describes the page for its data, and React makes the DOM match it. A strong candidate also names the one-variable rule by its common name, a single source of truth.

**2. The Classic Trap**

The classic trap is "React renders again, so it rebuilds the page." If that were true, every search box would lose its text each time any data changed. On our header, a saved change of the name left "elections" in the box, with its cursor. React changed two text nodes and kept the `<input>`.

**3. What is Actually Going On**

In plain JavaScript, the call to `updateHeaderUser` set the greeting and forgot the corner, so the page showed "Welcome back, Mary Brooks" beside "Signed in as Mary".

In React, `SiteHeader` keeps the name in one variable, `userName`, and both places read it. When the name changed to Mary Brooks, React called `SiteHeader` again, compared the new description with the last one, and changed exactly two texts.

The search box was the same node before and after, so it kept what was typed. People call the description React compares the virtual DOM.

**4. Where It Gets Tricky**

*Is React a framework?*

React calls itself a library for building user interfaces. It can run a whole page, or only one part of a page that already exists.

*Does React stop the old name from showing up anywhere?*

Only where the JSX reads the variable. A name typed into the markup as fixed text keeps the old value, even in React.

*What does React change when the new description is the same as the last one?*

No text at all.

*Can I still call `document.getElementById` inside a component?*

On the component's first run, its own elements are not in the page yet, so the call returns `null`. Lecture 10 shows the error this causes.

### Glossary

- **DOM**: The Document Object Model: the objects the browser builds in memory from the HTML, one for every tag, nested like the tags. The screen is drawn from the DOM, so changing the page means changing the DOM.
- **Imperative programming**: Code that gives the browser every command itself, such as finding an element and setting its text. From the Latin *imperare*, "to command".
- **Declarative programming**: Code that declares what the page should show for the current data, while React changes the DOM to match. From the Latin *declarare*, "to make clear, to announce".
- **Component**: A JavaScript function whose name starts with a capital letter and which returns JSX for one piece of the page. React calls it; our code does not.
- **JSX**: The markup a component returns. It looks like HTML but is JavaScript, and curly braces inside it place the value of a variable.
- **Virtual DOM**: The common name for the description a component returns, which React compares with the last one to change only what is new in the real DOM. The React documentation calls the result "the minimal necessary operations".

### Summary

**Describing the page from data**

❒ Declarative programming: describing what the page shows, not how to change it

➔ ALWAYS describe what the page shows in the JSX a component returns, and let React build the DOM from it.

➔ NEVER find and change elements by hand with `document.getElementById` and `textContent` in a page that React builds.

❒ Single source of truth: describing many places from one value

➔ ALWAYS keep a value that shows in several places in one variable, and read it with curly braces in every place.

➔ NEVER type a copy of the value into the markup; a copy keeps the old value when the variable changes.

❒ The virtual DOM: describing the page again when the value changes

➔ IF the data changes THEN describe the page from the new data and let React change only the new text.

➔ NEVER rebuild part of the page with `innerHTML`; it makes new nodes, and every text box inside loses what the user typed.

**One description, one value, and the smallest change.**

**DO THIS:** describe every place from one variable

```jsx right
export default function SiteHeader() {
  const userName = 'Mary Brooks';
  return (
    <header>
      <p>Welcome back, {userName}</p>
      <span>Signed in as {userName}</span>
      <input placeholder="Search" />
    </header>
  );
}
```

**DO NOT DO THIS:** find each element and set its text by hand

```js wrong
function updateHeaderUser(name) {
  const greeting = document.getElementById('greeting');
  greeting.textContent = 'Welcome back, ' + name;
}
```

| | **IMPERATIVE**<br>(plain JavaScript) | **DECLARATIVE**<br>(React) |
| ---: | :--- | :--- |
| **Who changes the DOM** | Our code, one command per element:<br>`getElementById(...)`<br>`.textContent = name` | React, from the JSX the component returns:<br>`<p>Welcome back,`<br>`{userName}</p>` |
| **A value in many places** | One command per place;<br>a forgotten place keeps the old value | One variable that every place reads;<br>no place can keep an old copy |
| **When the data changes** | Our code sets each text again,<br>or rebuilds with `innerHTML` | React compares the new description<br>with the last one and changes only the new text |
| **Typed text and focus** | Lost when `innerHTML`<br>builds new nodes | Kept, because the `<input>`<br>stays the same node |
| **When it fits** | One element changes in one place,<br>such as a clock in a corner | The same value shows in several places,<br>or many parts of the page change |
