## Authorized Scope
Lesson 17 teaches what React does with several setter calls. It works on one component, `TicketOrder`, which shows a ticket count and a "+3 Tickets" button. React waits until all the code in an event handler has run. Then it renders once. This is called batching. Each setter call adds one update to a queue. In the next render, React works through the queue in order, starting from the current state. A plain value replaces the result so far. An updater function, such as `t => t + 1`, receives the result so far and returns the next one. So three updaters add three, while three plain values set the same number three times. We need an updater when the next value comes from the previous one and another update can come first. That happens with several calls in one handler, or with a call after an `await`. React calls updaters during the next render, so they must be pure. The lesson builds on Q12, pure rendering, Q15, the render after the handler, and Q16, state as a snapshot.

## Theme and Options
- **Theme**: The next value of a state comes from its current value, as with a counter. What do we pass to the setter?
- **Option**: passing the next state: `setTickets(tickets + 1)` | Q14 `#use_state` | one update per click, or a value that does not depend on the old one, such as `setMessage('1 ticket added')`
- **Option**: passing an updater function: `setTickets(t => t + 1)` | this lesson | the next value comes from the previous one, and another update of the same state can come first in the queue
- **This lesson teaches**: the updater function, and the batching that makes it necessary

## Principle Thread
- **Anchor**: Queued updates: each setter call adds an update to a queue, and React works through the queue in the next render
- **Axis**: the life of the queue: when React works through it, how it treats each update, what we put in it, and what an updater may do
- **Why This Axis**: Each step needs the one before it. The reader must first see that the updates wait for the end of the handler, or a queue makes no sense. Only then can the queue's order show why three plain values give 1: each replaces the result so far. The updater answers that failure, so it comes third. Purity comes last, because it rests on where the updater runs: inside the next render, which the first three steps have shown. Two axes were rejected. "The value form, then the function form" hides why the value fails, which is the queue. "One state variable, then several" splits batching into two lessons for one fact.
- **Spoken Preview**: Everything in this lesson comes down to one idea: queued updates, which means that each setter call adds an update to a queue, and React works through the queue in the next render. First, batching, which means the updates wait for the whole handler: React renders once, after the last line of the handler has run. Second, the update queue, which means the updates apply in order: a plain value replaces the result so far, so three calls that read the same old number give that number plus one, three times over. Third, updater functions, which means each update starts from the result before it: a function given to the setter receives the newest value, so we use one when another update can come first. Fourth, pure updaters, which means each updater only computes the next value: React calls it during the next render, twice in development, so a log or a request belongs in the handler.
- **Closing Line**: The updates wait, apply in order, start from the result before them, and only compute.

## Principles

### Principle 1: Batching: the updates wait for the whole handler
- **Handle**: `one-render-per-event`
- **Thread Step**: when React works through the queue
- **Rule**: React renders once, after the whole event handler has run, for every setter call the handler made.
- **Kind**: Model
- **Reader Question**: "My click handler calls `setTickets` and then `setMessage`. Does `TicketOrder` render twice, once per setter?"
- **Reader Expects**: one render per setter call, because Q15 showed a setter call followed by a render; or a render in the middle of the handler, right at the setter
- **React Does**: each setter call adds its update to a queue and asks for a render; the handler keeps running and logs "handler ends"; when the handler has returned, React renders `TicketOrder` once with every queued update; this is batching; the console shows "handler ends", then the body log with `tickets = 1` (twice under Strict Mode, which calls the component twice, as in Q12); the screen shows "Tickets: 1" and "1 ticket added" together; batching is like a waiter who takes the whole order before going to the kitchen; it also keeps the screen from showing a half-finished state, with the new count and the old message; a second click is its own event: its handler logs `tickets = 1`, and one more render follows
- **Placement**: every setter call in one handler, for one state variable or several, waits for the same render; a separate click gets its own render
- **Real Mistake**: none; expecting two renders breaks no code, and the one surprise, a line after the setter that reads the old value, belongs to Q16 `fixed-in-render`
- **Importance**: interviewers ask for batching by name; it is the ground of the queue in the next principle
- **Prediction**: however many setters one click calls, the body log of `TicketOrder` appears once per click (twice under Strict Mode, with the same value), and after the handler's own last log
- **Required Lesson Proof**: `TicketOrder` with `tickets` and `message` state and a body log; the handler calls `setTickets(tickets + 1)` and `setMessage('1 ticket added')`, then logs "handler ends"; the console shows "handler ends", then the render log with `tickets = 1`; a second click's handler logs `tickets = 1`.

### Principle 2: The update queue: the updates apply in order
- **Handle**: `queue-in-order`
- **Thread Step**: how React treats each update
- **Rule**: The next render starts from the current state and applies the queued updates in the order of the calls; a plain value replaces the result so far, so three plain calls that read the same snapshot give the same number three times.
- **Kind**: Model
- **Reader Question**: "I call `setTickets(tickets + 1)` three times. Why does the screen show 1 and not 3? What happened to the other two updates?"
- **Reader Expects**: each call adds one, so three calls add three, as `count++` three times would
- **React Does**: `tickets` is 0 for the whole handler (Q16 `fixed-in-render`); each call computes `0 + 1` and adds "replace with 1" to the queue; the next render starts from the current state, 0, and applies the updates in order: "replace with 1" three times gives 1; `useState` returns 1, and the screen shows "Tickets: 1"; the other two updates were not lost: they set the same number; the next click reads 1 and shows 2; the queue holds values and functions alike: `setTickets(tickets + 5); setTickets(t => t + 1);` from 0 queues "replace with 5", then "add 1 to the result", and shows 6; a final `setTickets(42)` replaces everything before it and shows 42; `setTickets(5)` acts like an updater that ignores its argument
- **Placement**: the order of the setter calls in the handler is the order of the queue; the queue is applied in the next render, starting from the current state
- **Real Mistake**: the "+3 Tickets" handler written as three `setTickets(tickets + 1)` calls, to add three; from 0, the screen shows 1 after the click and 2 after the next; verified in React 19.3.1, Vite 8.3.4, and Chrome
- **Fix In**: `updater-from-previous`
- **Importance**: the bank hook; the interview question asks how React queues; the mixed queue is a common interview puzzle
- **Prediction**: from 0, a handler with `setTickets(tickets + 5)` and then `setTickets(t => t + 1)` shows 6, and adding `setTickets(42)` after them shows 42
- **Required Lesson Proof**: three plain calls show 1, then 2; the `+5`, updater queue shows 6; the same queue with `42` last shows 42; each traced as a queue table.

### Principle 3: Updater functions: each update starts from the result before it
- **Handle**: `updater-from-previous`
- **Thread Step**: what we put in the queue
- **Rule**: When the next value comes from the previous one and another update of the same state can come first, we pass an updater function, such as `c => c + 1`, which receives the result so far; for one update per click, a plain value is fine.
- **Kind**: Decision
- **Reader Question**: "The updater fixed +3 Tickets. Do I need `t => t + 1` on every setter from now on, to be safe?"
- **Reader Expects**: after the surprise of `queue-in-order`, an updater on every setter, or a rule that says only "several calls in one handler"
- **React Does**: `setTickets(t => t + 1)` adds the function itself to the queue; the next render calls it with 0 and gets 1, then with 1 and gets 2, then with 2 and gets 3; the screen shows "Tickets: 3", and the next click 6; another update can also come first across an `await`: the Buy handler adds 1 to `pending`, waits a second for `sendOrder()`, then subtracts 1; after the wait, `pending` still holds the snapshot 0 (Q16 `handler-keeps-its-render`), so `setPending(pending - 1)` sets -1 and the screen shows "Pending: -1"; two quick Buys both read `completed = 0`, so the screen ends at "Completed: 1" and one order is lost; with `setPending(p => p - 1)` and `setCompleted(c => c + 1)`, each update receives the newest value, and the screen ends at "Pending: 0, Completed: 2"; with one plain setter per click, React has rendered the previous click before the next handler runs, so `setTickets(tickets + 1)` reads the current count and the screen rises 1, 2, 3
- **Placement**: `setTickets(t => t + 1)` when the handler queues more than one update of the same state, or sets it after an `await`; a plain value, such as `setTickets(tickets + 1)` alone or `setMessage('1 ticket added')`, is fine otherwise; an updater there does no harm, but it is not needed
- **Real Mistake**: the react.dev request counter on `TicketOrder`: a Buy handler with `setPending(pending + 1)`, `await sendOrder()`, then `setPending(pending - 1)` and `setCompleted(completed + 1)`; after one Buy the screen shows "Pending: -1, Completed: 1"; after two quick Buys, "Pending: 0, Completed: 1"; verified in React 19.3.1 and Chrome
- **Importance**: the bank hook's "why does `setCount(c => c + 1)` fix it"; counters that skip or go negative after a request reach production
- **Review Point**: Condition
- **Required Lesson Proof**: the "+3 Tickets" handler with three `setTickets(t => t + 1)` calls shows 3, then 6; the Buy counter ends at "Pending: -1, Completed: 1" with plain values and at "Pending: 0, Completed: 2" with updaters after two quick Buys; one plain setter per click rises 1, 2, 3.

### Principle 4: Pure updaters: each updater only computes the next value
- **Handle**: `updater-stays-pure`
- **Thread Step**: what an updater may do
- **Rule**: An updater receives the result so far and returns the next value, and does nothing else, because React calls it during the next render, twice in development; a log, a request, or another setter goes in the handler.
- **Kind**: Decision
- **Reader Question**: "I put a log inside `t => t + 1` to send the new count to our analytics, and it prints twice on every click. Does my updater run twice?"
- **Reader Expects**: an updater runs once, at the moment of the setter call, like any function we call ourselves; a doubled line looks like a double click
- **React Does**: the setter queues the function; React calls it while it computes the next state, during the next render, after "handler ends" (on the first click after the page loads, React calls the first updater at the setter call, so one line prints before "handler ends"); rendering must be pure (Q12); in development, under Strict Mode, React calls each updater twice with the same argument and keeps one result, to show updaters that are not pure; the console shows "updater gets 3" twice, 4 twice, 5 twice, and the screen still shows 6; an analytics log inside the updater prints twice per click, so the analytics would count two tickets for one; without Strict Mode it prints once; moved into the handler as `tickets + 1`, after one updater, it prints once per click
- **Placement**: `t => t + 1` returns a value and does nothing else; the analytics log, a request, or another setter goes in the handler, outside the updater, with the value it needs computed there
- **Real Mistake**: after Q16 showed that a log right after the setter reports the old count, the analytics log moved into the updater, where the new count is: `setTickets(t => { console.log('analytics: ticket added, now', t + 1); return t + 1; })`; under Strict Mode every click prints it twice, with the same number; the screen rises by one per click; verified in React 19.3.1 and Chrome
- **Importance**: reviewers flag side effects inside updaters; every Vite app starts with Strict Mode, so a reader sees the doubled log on day one
- **Review Point**: Do not
- **Required Lesson Proof**: the three-updater handler with a log inside each updater, under Strict Mode: six updater lines, the screen 6; the analytics log inside the updater: twice per click; moved into the handler: once per click.

## Senior Answer
React batches state updates. It waits until all the code in an event handler has run, and then it renders once. Each setter call adds an update to a queue. In the next render, React works through the queue in order, starting from the current state. A plain value replaces the result so far. An updater function receives the result so far and returns the next one. That is why three calls to `setCount(count + 1)` add one. Each call reads the same snapshot, so the queue says "replace with one" three times. Three calls to `setCount(c => c + 1)` add three, because each updater receives the result of the one before. I use an updater when the next value comes from the previous one and another update can come first. That means several calls in one handler, or a call after an `await`. For one update per click, a plain value is fine. Updaters run during rendering, so they must be pure. In development, Strict Mode calls them twice to catch side effects.
