## Authorized Scope
Lesson 20 teaches how a form field shows exactly what is in state. It works on one component, `ArticleCorrectionForm`, with a headline input, a correction textarea, a section select, and an "urgent" checkbox. A field with `defaultValue` keeps its own text, so setting state does not change it. A controlled field takes its text from state through `value`. Each keystroke calls `onChange`, and the handler writes the new text into state. After the render, React writes state back into the field. So the field always shows state, and clearing state clears the field. A `value` without `onChange` freezes the field. The handler must store exactly what was typed, at once. A checkbox uses `checked` and `e.target.checked`. A select takes `value` on the `<select>`, not `selected` on an `<option>`. And `value` must start as a string, never `undefined`. The lesson builds on Q13, event handlers, Q14, `useState`, and Q18, which supplied the `value` and `onChange` pair ready-made.

## Principles

### Principle 1: A controlled field shows what is in state, after every render
- **Handle**: `state-drives-field`
- **Kind**: Model
- **Reader Question**: "After Send, I call `setText('')`. The counter says 0/280, but the old text stays in the box. Why?"
- **Reader Expects**: the box empties; the box and the counter show the same text, and state was just cleared; a habit from Q15, where setting state changed the screen
- **React Does**: `defaultValue=""` gives the textarea its starting text once; after that, the browser keeps the field's own text; each keystroke fires `onChange`, and `setText` copies the text into state; Send calls `setText('')`; React renders; the counter reads `text.length` and shows 0/280; nothing tells the textarea to read state, so it keeps "Fix the date"; with `value={text}`, React writes `text` into the field after every render; after `setText('')` the field is empty
- **Placement**: `<textarea value={text} onChange={e => setText(e.target.value)} />`; then `setText('')` in the submit handler clears it; not `defaultValue` when our code must change the field later
- **Real Mistake**: `<textarea defaultValue="" onChange={e => setText(e.target.value)} />` with `setText('')` after Send, the card's Friction: the counter shows 0/280 and the box still shows "Fix the date" (React 19.3.0)
- **Fix In**: `this principle`
- **Importance**: it is what "controlled" means in the interview question; a form that will not clear is a classic shipped bug
- **Prediction**: with `value={text}`, any setter call that changes `text` changes the field at the next render; with `defaultValue`, the field ignores every later state change.
- **Required Lesson Proof**: `ArticleCorrectionForm` with a correction textarea, a live count, and a Send button whose submit handler calls `e.preventDefault()` and `setText('')`; with `defaultValue`: typing "Fix the date" shows 12/280, and Send shows 0/280 beside the old text; with `value={text}`: Send empties the box.

### Principle 2: Pair every `value` with an `onChange` that sets state
- **Handle**: `value-needs-onchange`
- **Kind**: Decision
- **Reader Question**: "I wrote `value={text}` and the box no longer takes any typing. What broke?"
- **Reader Expects**: `value` only sets the text, like the HTML `value` attribute, and typing still works; a habit from HTML, where `value` is a starting value
- **React Does**: a string `value` makes the field controlled; each keystroke changes the field for a moment; with no `onChange`, nothing stores the new text; React writes `text` back, so the keystroke disappears; the console shows "You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`."; the same happens to a `<select>` and to a checkbox's `checked`
- **Placement**: `value={text}` together with `onChange={e => setText(e.target.value)}`; `readOnly` for a field nobody should edit; `defaultValue` for a field our code never changes
- **Real Mistake**: `<textarea value={text} />`, the card's second Friction: every keystroke vanishes and the console shows the error above (React 19.3.0)
- **Importance**: the error every React beginner meets; the card's Naive code
- **Review Point**: Do
- **Required Lesson Proof**: the correction textarea of `ArticleCorrectionForm` with `value={text}` and no `onChange`: typing "Fix" leaves the box empty, and the console shows the error; with `onChange`: "Fix" appears.

### Principle 3: Store exactly what was typed, right away
- **Handle**: `set-what-was-typed`
- **Kind**: Decision
- **Reader Question**: "Headlines are all caps. Can my `onChange` store `e.target.value.toUpperCase()`?"
- **Reader Expects**: yes; `onChange` is our function, and state is ours to shape; a habit from formatting a value before saving it
- **React Does**: the browser puts the typed letter into the field and the caret after it; `onChange` stores an uppercased copy, which differs from the field's text; React writes that copy into the field; replacing the whole text moves the caret to the end; in Chrome, typing "xy" after "fix " in "fix the date" gives "FIX XTHE DATEY"; a handler that stores the text inside `setTimeout` is late instead of different: React writes the old state back first, and quick typing scrambles the text
- **Placement**: `onChange={e => setHeadline(e.target.value)}`, synchronous and unchanged; format the text where it is shown or when it is sent
- **Real Mistake**: `onChange={e => setHeadline(e.target.value.toUpperCase())}`: typing in the middle of the headline sends the caret to the end, so the next letter lands there (Chrome 154, React 19.3.0)
- **Importance**: the card's synchronous `onChange` rule; a react.dev Troubleshooting entry; the bug appears only when editing in the middle, so it ships
- **Review Point**: Do
- **Required Lesson Proof**: the headline input of `ArticleCorrectionForm` with the uppercased handler: type "fix the date", move the caret after "fix ", type "xy", and the field shows "FIX XTHE DATEY"; with `e.target.value`: "fix xythe date".

### Principle 4: A checkbox uses `checked`, and its handler reads `e.target.checked`
- **Handle**: `checked-for-checkbox`
- **Kind**: Decision
- **Reader Question**: "For the urgent checkbox, do I write `value` and `e.target.value`, like the text fields?"
- **Reader Expects**: yes; it is an input too, so the same pair should work; a habit from the text fields of this lesson
- **React Does**: a checkbox shows its state through `checked`; its `value` is the text it sends with the form, "on" by default; `e.target.value` is "on" on every click; with `checked={isUrgent}` and `setIsUrgent(e.target.value)`, the first click stores "on", which is truthy, so the box is checked; the second click stores "on" again, so it stays checked; `e.target.checked` is `true` or `false`, so the box follows each click
- **Placement**: `<input type="checkbox" checked={isUrgent} onChange={e => setIsUrgent(e.target.checked)} />`; the same for a radio button
- **Real Mistake**: `onChange={e => setIsUrgent(e.target.value)}`: state becomes "on", and the box can never be unchecked (React 19.3.0)
- **Importance**: named in the card's Core Truth and Mechanism; a react.dev Troubleshooting `<Pitfall>`; the bug logs nothing
- **Review Point**: Do
- **Required Lesson Proof**: the urgent checkbox of `ArticleCorrectionForm` with a line that shows `String(isUrgent)`: with `e.target.value`, two clicks show "on" and a checked box; with `e.target.checked`, they show `true`, then `false`.

### Principle 5: Put `value` on the field itself, not on an option or between the tags
- **Handle**: `value-on-the-field`
- **Kind**: Decision
- **Reader Question**: "In HTML I mark the default section with `selected` on its `<option>`. Do I do the same here?"
- **Reader Expects**: yes; JSX looks like HTML, and that is how HTML picks an option; a habit from HTML, where a textarea's starting text also goes between its tags
- **React Does**: React does not support `selected` on an `<option>`; it logs "Use the `defaultValue` or `value` props on <select> instead of setting `selected` on <option>."; `<select value={section}>` picks the option whose `value` matches `section`; a pick fires `onChange`, and `e.target.value` is the picked option's `value`; text between `<textarea>` tags logs "Use the `defaultValue` or `value` props instead of setting children on <textarea>."
- **Placement**: `<select value={section} onChange={e => setSection(e.target.value)}>` with a `value` on each `<option>`; `<textarea value={text} ... />` with nothing between the tags; an array of strings for `<select multiple>`
- **Real Mistake**: `<option value="sports" selected>`: the console shows the error above (React 19.3.0)
- **Importance**: the card's Mechanism names `value` "instead of `selected`"; reviewers flag the HTML habit
- **Review Point**: Do
- **Required Lesson Proof**: the section select of `ArticleCorrectionForm` with `selected` on "Sports": the error; with `value={section}` starting at "metro": a pick of "Sports" shows "sports" in state and in the select.

### Principle 6: Start every `value` as a string
- **Handle**: `start-with-a-string`
- **Kind**: Decision
- **Reader Question**: "The headline will come from the server later, so I wrote `useState()`. Is that fine?"
- **Reader Expects**: yes; `undefined` means nothing yet, and an empty field shows nothing too; a habit from plain JavaScript, where a variable starts as `undefined`
- **React Does**: `value={undefined}` is the same as no `value`, so the input starts uncontrolled; the first keystroke stores a string; `value` is now a string, so the input becomes controlled; React logs "A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen."; `value={null}` logs "`value` prop on `textarea` should not be null."; `useState('')` keeps the field controlled from the first render
- **Placement**: `useState('')` for every text field; `value={headline ?? ''}` when the value may arrive as `null` or `undefined`
- **Real Mistake**: `const [headline, setHeadline] = useState()` behind `<input value={headline}>`: the first keystroke logs the warning above (React 19.3.0)
- **Importance**: the card's third focus; a warning every React developer meets when data arrives later
- **Review Point**: Do
- **Required Lesson Proof**: the headline input of `ArticleCorrectionForm` with `useState()`: typing "F" logs the warning; with `useState('')`: no warning.

## Senior Answer
A controlled field shows whatever is in state. I pass the state as `value`, or as `checked` for a checkbox or a radio. I pass an `onChange` handler that writes the new value into state. React calls `onChange` on every keystroke. After the render, React writes state back into the field. So state is the single source of truth, and clearing state clears the field. With `defaultValue`, the field keeps its own text, and state cannot change it. A `value` without `onChange` freezes the field, and React warns about it. The handler must store `e.target.value` right away and unchanged. Otherwise the caret jumps, or the text scrambles. For a checkbox I read `e.target.checked`. For a select I put `value` on the `<select>`, not `selected` on an option. And I start every value as an empty string, never `undefined`. Otherwise React warns that an uncontrolled input became controlled.

So `start-with-a-string` proves the warning on the headline `<input>`, and keeps the rule for every field. No card changed.
- textarea Troubleshooting says the caret jumps "to the beginning". In Chrome 154 it jumps to the end. The map states the observed behavior.
