## Authorized Scope
Lesson 21 teaches how to design a component whose screen changes with what the user does. It works on one component, `PaywallModal`, a subscription form. It has a card field, a Subscribe button, a spinner, an error banner, and a welcome message. Plain JavaScript changes the page step by step: disable the button, show the spinner, hide the error. Each step stays until another line undoes it, and one forgotten line leaves two messages on screen. In React, we list the visual states first: typing, submitting, success, and error. Then we find what moves the form from one state to the next. A person types or clicks, and a network response arrives. We keep the current state in one `status` string. The JSX describes what each status shows, and the handlers only set the next status. React makes the page match. Separate booleans can be true together, which brings the two-message bug back. The lesson builds on Q01, describing instead of commanding, and on Q10, branches in JSX. It also uses Q14, `useState`, Q17, `async` handlers, and Q20, controlled inputs.

## Principles

### Principle 1: Describe what each status shows, and let handlers only set the status
- **Handle**: `jsx-for-each-status`
- **Kind**: Model
- **Reader Question**: "My Subscribe handler disables the button, shows the spinner, and hides the error. Why does the form end up showing 'Payment failed' and 'Welcome, subscriber' together?"
- **Reader Expects**: one forgotten line; each handler must show and hide the right parts, and the fix is to add `hide(error)` to the success branch; a habit from plain JavaScript and jQuery, where every change to the page is a command
- **React Does**: the handler's DOM edits stay on the page until another line undoes them; the first attempt fails and shows the error; the second succeeds and shows the welcome; no line hid the error, so both show; React never sees these edits; with a `status` state, the JSX says what each status shows: the button is disabled while `status === 'submitting'`, the error shows only when `status === 'error'`, and `status === 'success'` returns only the welcome; the handler calls `setStatus('submitting')`, then `setStatus('success')` or `setStatus('error')`; React renders the JSX for that status and changes the page to match; the error and the welcome never show together
- **Placement**: what the form shows lives in the JSX, read from `status`; the handlers call `setStatus` and nothing else touches the page; no `document.querySelector`, no `style.display`, no `disabled =` in a handler
- **Real Mistake**: the card's imperative `PaywallModal`: `document.querySelector('#error').style.display = 'block'` in the failure branch and no line that hides it in the success branch; after a failure and a success, the form shows "Payment failed" and "Welcome, subscriber" (React 19.3.0)
- **Fix In**: `one-status-string`
- **Importance**: it is the interview question; Q01 taught describing static text, and this is the same model for a form that changes
- **Prediction**: with `status`, every status shows at most one of "Processing...", "Payment failed", and "Welcome, subscriber"; the order of earlier attempts makes no difference.
- **Required Lesson Proof**: `PaywallModal` with a ready-made `submitPayment` that fails once and then succeeds; the imperative handlers: type, Subscribe, Subscribe, and both messages show; the `status` version: "Processing..." with the button disabled while waiting, "Payment failed" after the first attempt, and only "Welcome, subscriber" after the second.

### Principle 2: List the visual states first, then what moves the form between them
- **Handle**: `states-then-triggers`
- **Kind**: Decision
- **Reader Question**: "Where do I start? Do I write the Subscribe handler first?"
- **Reader Expects**: yes; a form is built from what happens on each click, the way a plain JavaScript script starts from its event listeners
- **React Does**: we write down what the user can see: typing, submitting, success, error; we mock each one: `PaywallModal` takes a `status` prop with a default, and editing it shows each screen with no logic; `statuses.map(status => <PaywallModal key={status} status={status} />)` shows all four at once; then we list what changes the status: the reader typing and clicking Subscribe, and the network response arriving; each change becomes one `setStatus` call in one handler
- **Placement**: the states first, as mocks driven by a `status` prop; the triggers second, human and computer; the handlers last, each setting one status
- **Real Mistake**: none; starting from a handler is valid code, and the bug it invites is the one `jsx-for-each-status` shows
- **Importance**: the card's Mechanism steps 1, 2, and 5; interviewers ask for a design process; map 01 deferred the visual states to this lesson
- **Review Point**: Prefer
- **Required Lesson Proof**: the four mocks of `PaywallModal` side by side: typing shows the button; submitting shows "Processing..." and a disabled button; success shows only "Welcome, subscriber"; error shows the button and "Payment failed".

### Principle 3: Keep states that exclude each other in one status string
- **Handle**: `one-status-string`
- **Kind**: Decision
- **Reader Question**: "Can I keep `isSubmitting`, `isSuccess`, and `isError` as three booleans instead?"
- **Reader Expects**: yes; each message is shown or hidden, so each gets a true or false; a habit from the `isBreaking` flags of earlier lessons
- **React Does**: the failure sets `isError` to true; the success sets `isSuccess` to true; nothing sets `isError` back to false, so both are true; the JSX shows both messages, the same bug as the imperative form; three booleans allow eight combinations, and only four make sense; `useState('typing')` with `setStatus('success')` replaces the old status, so the error disappears with no extra line; the typed card number and the error text change on their own, so they keep their own state
- **Placement**: one `status` with the values `'typing'`, `'submitting'`, `'success'`, and `'error'` when only one can be true at a time; separate state for values that change on their own, such as `card`
- **Real Mistake**: `isSubmitting`, `isSuccess`, and `isError`, with `setIsError(true)` on failure and `setIsSuccess(true)` on success: after a failure and a success, "Payment failed" and "Welcome, subscriber" show together (React 19.3.0)
- **Importance**: the card's Under the Hood; booleans are the first thing readers write, and they rebuild the bug the lesson removes
- **Review Point**: Condition
- **Required Lesson Proof**: `PaywallModal` with three booleans: type, Subscribe, Subscribe, and both messages show; with one `status`: only "Welcome, subscriber".

## Senior Answer
I don't change the DOM by hand. I describe what the component shows in each state, and React makes the page match. First I list the visual states. For a payment form, they are typing, submitting, success, and error. I mock each one with a `status` prop, so I can see every screen before any logic. Then I find what moves the form between states. The user types or clicks Subscribe, and the network answers. I keep the current state in one `status` string with `useState`. The JSX reads it: the button is disabled while submitting, and the error shows only in the error state. Each handler only calls `setStatus`. I avoid separate booleans for states that exclude each other. Two booleans can both be true, and then the error and the welcome show together. One string can hold only one value. Values that change on their own, like the typed text, keep their own state.
