## Authorized Scope
Lesson 14 teaches how a component remembers a value that changes while the page is open. A plain variable cannot do it, for two reasons. Changing it puts nothing new on the screen, because the screen shows the value from the component's last run. And each run of the component starts the variable over. `useState`, a Hook React provides, gives a value React keeps between runs and a setter that changes it. Calling the setter makes React run the component again with the new value. A component can keep several values, and React tells them apart by the order of the calls. Each copy of a component on the page keeps its own values. An expensive starting value is passed as a function, so React computes it only once. A setter is called in an event handler, never while the component runs. The lesson builds on Q12, where React calls a component any number of times. It also builds on Q13, where a click runs a handler. The example is the article card's Like button.

## Theme and Options
- **Theme**: A page changes while it is open: a Like count grows, a Save button turns into Saved. Where does a component keep a value that changes?
- **Options**: none (starting point: values written in the code and passed as props, Lectures 1 to 13, which change only when the file is saved)
- **This lesson teaches**: state with `useState`

## Principle Thread
- **Anchor**: Component memory: a value React keeps for one component between its runs
- **Axis**: three stretches of one value's life: why a plain variable cannot keep it (the screen, the next run), how React keeps it (the pair, several values, one copy each), and how it starts and changes (the first run, the user's action)
- **Why This Axis**: Each step needs the one before it. The reader must see a plain variable fail twice before a Hook makes sense: the screen does not follow it, and the next run erases it. `useState` answers both, so it comes third. Once the reader holds one state value, the next questions are how React keeps several apart and whether two copies share them. The start and the change come last, because both are about calling the pair the right way at the right time. Two axes were rejected. "Before, during, and after a click" puts the starting value and the order of the calls in no place. "The code from top to bottom" puts the initializer before the reader knows why the argument is ignored.
- **Spoken Preview**: Everything in this lesson comes down to one idea: component memory, which means a value React keeps for one component between its runs. The first stretch shows why a plain variable cannot be that memory. First, local variables, which means the value changes, but the screen keeps the old one: a value that must change on the screen never lives in a plain variable. Second, re-rendering, which means the value starts over on every run: a plain variable lasts only for one run of the component. The second stretch shows how React keeps the value. Third, state, which means the value React keeps, with a setter that changes it: we read the value, and we change it only through its setter. Fourth, multiple state variables, which means the values React tells apart by the order of the calls: we ask for each value at the top of the component, never inside a condition. Fifth, component instances, which means the value each copy keeps for itself: two copies of one component never share their state. The last stretch shows how the value starts and how it changes. Sixth, initializer functions, which means the starting value computed only once: an expensive start is passed as a function. Seventh, setters in event handlers, which means the value changes only when the user acts: a setter runs in a handler, never while the component runs.
- **Closing Line**: Not a variable but state: kept by React, told apart by order, one per copy, started once, and changed on a click.

## Principles

### Principle 1: Local variables: the value changes, but the screen keeps the old one
- **Handle**: `assignment-renders-nothing`
- **Thread Step**: why a plain variable cannot keep it: the screen
- **Rule**: The screen keeps the value it got when the component ran, so a value that must change on the screen never lives in a plain variable: changing that variable changes nothing on the page.
- **Kind**: Model
- **Reader Question**: "I add 1 to `likes` on every click and the console counts up. Why does the button still say Like (0)?"
- **Reader Expects**: the button shows `likes`, so when `likes` changes, the button changes, as a spreadsheet cell follows the cell it reads
- **React Does**: when React runs `ArticleCard`, `{likes}` in the JSX puts the value `likes` holds at that moment, 0, into the button's text; the click handler then changes `likes` to 1, 2, 3, and the console shows each new value; nothing puts the new value on the screen, because `{likes}` is read again only when React runs the component again, and changing a variable does not make React run it; the setter of `state-pair` does
- **Placement**: no `let` for a value the screen shows and the user changes; `const [likes, setLikes] = useState(0)` instead (`state-pair`)
- **Real Mistake**: `let likes = 0;` in `ArticleCard`, `likes = likes + 1;` and a log in `handleLike`, and `Like ({likes})` on the button; three clicks log "likes is now 1", 2, 3, and the button stays at "Like (0)"; verified in React 19.3.1, Vite 8.3.4, and Chrome
- **Fix In**: `state-pair`
- **Importance**: the bank question's hook; react.dev's first reason a regular variable is not enough; the first wall every reader hits
- **Prediction**: after three clicks, the console shows 1, 2, 3 and the button still shows "Like (0)"
- **Required Lesson Proof**: the `let` counter: three logs, an unchanged button.

### Principle 2: Re-rendering: the value starts over on every run
- **Handle**: `fresh-each-render`
- **Thread Step**: why a plain variable cannot keep it: the next run
- **Rule**: Each run of a component starts its variables over: a plain variable inside a component lasts only until the function returns, so it never holds anything a later run needs.
- **Kind**: Model
- **Reader Question**: "The card ran again, and my `let` counter went back to 0. Why?"
- **Reader Expects**: once React runs the component again, the variable keeps the 3 it reached, as a variable in a running script does
- **React Does**: React runs a component more than once: every time the screen must change, and on every save while the dev server runs; each time, it calls the function from its first line; so `let likes = 0` runs again, and `likes` is 0, whatever the last run left in it; the 3 belonged to the run that is over; the next Like logs "likes is now 1"
- **Placement**: no plain variable for a value a later run needs; `useState` (`state-pair`)
- **Real Mistake**: the `let` counter of `assignment-renders-nothing` after three Likes; `App.jsx` is saved with the dev server running, React runs the card again, and the next Like logs "likes is now 1"; verified in React 19.3.1, Vite 8.3.4, and Chrome
- **Fix In**: `state-pair`
- **Importance**: the bank question's first half; react.dev's second reason; Q16 and Q17 rest on runs that start over
- **Prediction**: after the save, the first Like logs 1 again, not 4
- **Required Lesson Proof**: three Likes, a save, one more Like: the log starts at 1.

### Principle 3: State: the value React keeps, with a setter that changes it
- **Handle**: `state-pair`
- **Thread Step**: how React keeps it: the pair
- **Rule**: `useState` gives a value that lasts and a function that changes it: we read the state variable and never assign to it, and every change goes through its setter.
- **Kind**: Decision
- **Reader Question**: "How do I keep a value and make the screen follow it?"
- **Reader Expects**: the value still behaves like a variable: once it lives in state, `likes = likes + 1` works
- **React Does**: `const [likes, setLikes] = useState(0)` gives two things, unpacked with array destructuring: `likes`, the state variable, which is 0 on the first run and keeps its value between runs, and `setLikes`, the setter; `setLikes(likes + 1)` stores 1 and makes React run the component again, and in that run `likes` is 1, so the button shows "Like (1)"; the value is still a variable in this run: `likes = likes + 1` on a `const` throws "Assignment to constant variable.", and with `let` it changes nothing on screen and throws nothing; a value used only inside one handler needs no state; forgetting the import throws "useState is not defined"
- **Placement**: `import { useState } from 'react';` at the top of `ArticleCard.jsx`; `const [likes, setLikes] = useState(0);` as the first line of the component; `setLikes(likes + 1)` in `handleLike`
- **Real Mistake**: `const [likes, setLikes] = useState(0);` with `likes = likes + 1;` in `handleLike`; the click throws "Assignment to constant variable.", and the button stays at "Like (0)"; `setLikes(likes + 1)` shows "Like (1)", then 2, then 3; verified in React 19.3.1 and Chrome
- **Importance**: the bank question's second half; the card's Core Truth; every later state lesson uses the pair
- **Review Point**: Do not
- **Required Lesson Proof**: the setter: Like (1), (2), (3), and 3 kept after a save; the assignment to `const`: the error; the assignment to `let`: no change; the missing import: the error.

### Principle 4: Multiple state variables: the values React tells apart by the order of the calls
- **Handle**: `state-lives-in-react`
- **Thread Step**: how React keeps it: several values
- **Rule**: React keeps state outside the component and matches it by order: we call `useState` once per value at the top of the component, never inside an `if`.
- **Kind**: Model
- **Reader Question**: "`useState(0)` runs on every run. Why does `likes` not go back to 0, and how does React tell two values apart?"
- **Reader Expects**: `useState(0)` sets the value to 0 each time, as `let likes = 0` does, and React reads the names `likes` and `isSaved` to know which is which
- **React Does**: React keeps each value itself, outside our function; on the first run, `useState(0)` stores 0; on every later run, React ignores the 0 and returns the stored value; a component may call `useState` several times, once per value; React never sees the names `likes` or `isSaved`, so it matches each call to its stored value by its place in the order: first call, second call; two Likes and a Save show "Like (2)" and "Saved", each value kept apart; a `useState` inside `if (likes > 0)` is skipped on the first run and called after the first Like, so the second call finds no value of its own: React warns about "a change in the order of Hooks" and throws "Rendered more hooks than during the previous render."; why the order may never change is Q37's
- **Placement**: `const [likes, setLikes] = useState(0);` and `const [isSaved, setIsSaved] = useState(false);` at the top of `ArticleCard`, before any `if`
- **Real Mistake**: `if (likes > 0) { const [isSaved, setIsSaved] = useState(false); }` in `ArticleCard`; the first Like logs "React has detected a change in the order of Hooks" and throws "Rendered more hooks than during the previous render.", and the page goes blank; both calls at the top keep both values; verified in React 19.3.1 and Chrome
- **Fix In**: this principle
- **Importance**: react.dev's `<DeepDive>`; interviewers ask how React knows which state is which; Q37 builds on it
- **Prediction**: with `likes` and `isSaved` at the top, two Likes and a Save show "Like (2)" and "Saved", and a Like on the second card shows "Like (1)" there
- **Required Lesson Proof**: two values at the top: kept apart; the call inside `if`: the warning, the error, the blank page.

### Principle 5: Component instances: the value each copy keeps for itself
- **Handle**: `state-per-instance`
- **Thread Step**: how React keeps it: one copy each
- **Rule**: Each copy of a component on the screen keeps its own state: a value per copy lives in state inside the component, never in a variable outside it, and the parent cannot read or change it.
- **Kind**: Model
- **Reader Question**: "Does a Like on one card add to every card?"
- **Reader Expects**: the cards run the same function with the same `useState(0)` line, so they share one count; or, to make the count last, it should move outside the component
- **React Does**: one component function can appear on the page many times; the list shows three `ArticleCard`s; React keeps a separate set of stored values for each copy, called a component instance, so three Likes on the first card show "Like (3)" while the others stay at "Like (0)"; a `let likes` moved outside the component, to the top of the file, is one variable for every copy (Q12): four Likes on two cards change nothing on screen, and the next run shows "Like (4)" on all three; the list cannot read a card's state or change it
- **Placement**: `useState` inside `ArticleCard`, so each copy has its own `likes`; nothing outside the component that the cards change
- **Real Mistake**: `let likes = 0;` moved above `export default function ArticleCard`, so the count survives runs; two Likes on the first card and two on the second change nothing on screen, and a save shows "Like (4)" on all three cards; `useState` inside the component keeps a separate count on each card: three Likes on the first and one on the second show "Like (3)", "Like (1)", "Like (0)"; verified in React 19.3.1, Vite 8.3.4, and Chrome
- **Fix In**: this principle
- **Importance**: the card's Code Experiment React; react.dev's "State is isolated and private"; Q23 and Q24 build on it
- **Prediction**: three Likes on the first card leave the second and third at "Like (0)"
- **Required Lesson Proof**: three cards with state: separate counts; the variable outside: one shared number, shown after a save.

### Principle 6: Initializer functions: the starting value computed only once
- **Handle**: `initial-value-once`
- **Thread Step**: how it starts and changes: the first run
- **Rule**: We pass an expensive starting value as a function, `useState(createItems)` or `useState(() => readSaved(id))`, so React computes it only on the first run; a cheap value such as `0` needs no function.
- **Kind**: Decision
- **Reader Question**: "My starting count is read from saved data. Why does that code run on every click?"
- **Reader Expects**: React uses the starting value once, so the code that makes it runs once
- **React Does**: React uses the argument of `useState` only on the first run and ignores it after that; but the whole line runs on every run, so `useState(getSavedLikes(article.id))` calls `getSavedLikes` every time, and React throws the result away: the log "reading saved likes 1" appears on load and again on every Like; `useState(() => getSavedLikes(article.id))` passes a function, an initializer function, and React calls it only on the first run; with Strict Mode it calls it twice on that first run and keeps one result; a function that needs no argument passes by name, `useState(createItems)`; a cheap value needs nothing of the kind
- **Placement**: `const [likes, setLikes] = useState(() => getSavedLikes(article.id));` in `ArticleCard`; `getSavedLikes` above the component, reading `localStorage`
- **Real Mistake**: `useState(getSavedLikes(article.id))` in `ArticleCard`, with a log in `getSavedLikes`; the log shows twice for each card on load and twice more on every Like; `useState(() => getSavedLikes(article.id))` logs only on load; verified in React 19.3.1 and Chrome
- **Importance**: the card's Mechanism and Scope Boundary; react.dev's "Avoiding recreating the initial state"; interviewers ask about lazy initial state
- **Review Point**: Prefer
- **Required Lesson Proof**: the call: logs on every Like; the initializer: logs on load only.

### Principle 7: Setters in event handlers: the value changes only when the user acts
- **Handle**: `setter-in-handler`
- **Thread Step**: how it starts and changes: the user's action
- **Rule**: We call a setter only when the user acts, inside an event handler, never in the component's body and never as a call written in an event prop.
- **Kind**: Decision
- **Reader Question**: "I wrote `onClick={setLikes(likes + 1)}`. Why does the page crash before I click?"
- **Reader Expects**: the setter is stored for the click, as `onclick="..."` stores code in HTML
- **React Does**: the braces run their code while React runs the component (Q13), so the setter runs before anyone clicks; the setter makes React run the component again; that run calls the setter again, and so on; React stops the loop with "Too many re-renders. React limits the number of renders to prevent an infinite loop." and the page goes blank; `onClick={() => setLikes(likes + 1)}`, or `onClick={handleLike}` with the setter inside `handleLike`, runs the setter only on the click
- **Placement**: `setLikes(likes + 1)` inside `handleLike`, passed as `onClick={handleLike}`
- **Real Mistake**: `<button onClick={setLikes(likes + 1)}>` in `ArticleCard`; the page goes blank as it loads, and the console shows "Too many re-renders. React limits the number of renders to prevent an infinite loop."; `onClick={handleLike}` shows the cards and counts on each click; verified in React 19.3.1 and Chrome
- **Importance**: react.dev's Troubleshooting; the most common `useState` crash; map 13 routed it here
- **Review Point**: Do not
- **Required Lesson Proof**: the call in the prop: the blank page and the error; the handler: the counting button.

## Senior Answer
A local variable lives only for one run of the component. React may run that function many times, and each time the variable starts over. Changing it also puts nothing new on the screen, because the screen shows the value from the last run. `useState` solves both. It returns a pair: the current value, and a setter. The setter stores the next value and makes React run the component again. In that run, `useState` returns the new value. React keeps the values outside the function and matches each `useState` call by its order. So the calls must stay at the top of the component. Each copy of a component keeps its own state, and the parent cannot reach it. An expensive starting value goes in as a function, because React uses the argument only once. And a setter runs only in an event handler, because a setter called while rendering asks for another render forever.
