## Authorized Scope
Lesson 18 teaches how to change an object that we keep in state. It works on one component, `ArticleForm`, a form that edits an article. The article is one object in state: a title, a summary, and an author object with a name and a bio. Above the fields, the form shows the article as readers will see it. A variable holds a reference to an object, not the object itself. Changing a property of the object in state changes the object React already holds. The setter compares the next value with the current one using `Object.is`. A changed object is still the same object, so React skips the render. So we never change the object in state. We build a new object and pass it to the setter. The three dots copy the old properties, and the property written after them replaces the copied one. The dots copy only one level. A change inside the author needs a copy of the article and a copy of the author. One handler can serve several fields when each field's `name` equals its property. The lesson builds on Q06, where props were read-only, and Q07, where the three dots first appeared. It also builds on Q12, where a mutation was defined, and Q13, where `e.target.value` held the typed text. Q14 to Q17 taught state, renders, snapshots, and updaters.

## Theme and Options
- **Theme**: A form edits several values that belong together, such as an article's title, summary, and author. How do we keep them in state, and change one of them?
- **Option**: one state variable per value: `const [title, setTitle] = useState('New Park Opens Today')` | Q14 `#use_state` | a few values that change one at a time and are always set whole
- **Option**: one object in state: `const [article, setArticle] = useState(firstArticle)` | this lesson | values that belong together, arrive together as one object, or are sent together, such as the fields of a form
- **Option**: Immer: `updateArticle(draft => { draft.author.bio = bio; })` | named in this lesson; no lesson teaches its API | objects nested several levels deep, where the copies at every level grow long
- **This lesson teaches**: one object in state, changed by building a new object for every change

## Principle Thread
- **Anchor**: A new object for every change: we never change the object React holds; we build a new one and hand it to the setter
- **Axis**: building the new object, one question at a time: why it must be new, what it copies, how deep the copy goes, and which property it changes
- **Why This Axis**: Each step needs the one before it. Until the reader sees that the setter compares objects and not their contents, a copy looks like wasted work, so the reason comes first. The three dots are how we build the copy, so they come second. The depth problem exists only once the reader knows that the dots copy one level, so it comes third. The computed name changes which property the dots' copy replaces, and its boundary (a field inside the author keeps its copy at every level) needs the third step, so it comes last. Three axes were rejected. "The depth of the object, top level and then nested" has no place for the computed name and teaches a copy before the reason for it. "The mistake, then the fix" splits each idea into two questions the reader asks as one. The order of the react.dev page (mutation, spread, nested objects, Immer) ends on a library the card only names.
- **Spoken Preview**: Everything in this lesson comes down to one idea: a new object for every change, which means that we never change the object React holds, and we build a new one and hand it to the setter. First, reference equality, which means a new object, because the setter compares objects, not their contents: a title changed inside the old object leaves the same object, so React skips the render, and the change appears later, when something else renders. Second, object spread, which means a new object that copies the old one and changes one property: the three dots copy every property first, the property written after them wins, and a property we leave out is gone. Third, nested objects, which means a new object at every level down to the change: the three dots copy only one level, so the author inside the article needs its own copy, or the old article changes too. Fourth, computed property names, which means a new object whose changed property comes from the field's name: one handler reads the name of the field that changed and uses it, in square brackets, as the property to replace.
- **Closing Line**: A new object, a copy with one change, a copy at every level, and the field that names the change.

## Principles

### Principle 1: Reference equality: a new object, because the setter compares objects, not their contents
- **Handle**: `same-object-no-render`
- **Thread Step**: why it must be new
- **Rule**: We never change a property of the object in state; we build a new object and pass it to the setter, because the setter skips the render when it gets the same object back; an object we have just built, which nothing else holds yet, is ours to change before we pass it.
- **Kind**: Model
- **Reader Question**: "I wrote `article.title = e.target.value` and then called `setArticle(article)`. The setter ran. Why does the title not change?"
- **Reader Expects**: the property changes the data, and the setter call makes React show it, as every setter call did in Q14 and Q15; a habit from plain JavaScript, where an object is changed in place, and from Vue, whose reactive objects notice every assignment
- **React Does**: a variable holds a reference to an object, not the object itself; `article` and the state React keeps point to one object; the assignment changes that object; `setArticle(article)` hands React the same reference; React compares the current value and the next with `Object.is`, finds the same object, and skips the render; no "ArticleForm runs" line; the Title field gives back the typed "!", because it shows the title of the last render, and the preview keeps "New Park Opens Today"; the console shows no error and no warning; a keystroke in Summary, whose handler is right, renders `ArticleForm`, and the field and the preview now show "New Park Opens Today!", because the object was changed all along; with no setter call at all, nothing renders either; ESLint with the React Hooks plugin marks the assignment "This value cannot be modified"; a new object built with the three dots, `{ ...article, title: e.target.value }`, is a different object, so React renders, and each keystroke shows in the field and the preview; a new object with every property written in full renders too, and so does a fresh object filled line by line before the setter call, because nothing else holds it yet
- **Placement**: every change of the article goes into a new object passed to `setArticle`; never an assignment to `article.title` or to any property of the object React holds; a new object filled before the setter call is fine
- **Real Mistake**: `article.title = e.target.value; setArticle(article);` in `handleTitle`; typing "!" in Title logs no render, and the field and the preview keep "New Park Opens Today"; a "." typed in Summary then renders once (two lines under Strict Mode), and Title shows "New Park Opens Today!" in the field and the preview; ESLint 10.12.0 with `eslint-plugin-react-hooks` 7.1.1 reports `react-hooks/immutability`, "This value cannot be modified"; verified in React 19.3.1, Vite 8.3.4, and Chrome
- **Fix In**: this principle
- **Importance**: the interview question and the bank hook; the card's Friction; useState Troubleshooting "the screen doesn't update"; a change that appears later, with an unrelated update, is a classic production bug
- **Prediction**: after `article.title = 'Park Opens'` and `setArticle(article)`, no render line prints and the preview keeps the old title; the next render for any other reason shows "Park Opens"; `Object.is(article, article)` is still true after the assignment, and `Object.is({ ...article }, article)` is false
- **Required Lesson Proof**: `ArticleForm` with `useState(firstArticle)`, a render log, the preview, and the Summary field, whose handler copies the article with the three dots; the Title field added with the changing `handleTitle`: "!" gives no line and no change, then "." in Summary renders and shows the "!"; the same handler with a new object: each keystroke renders and shows in the field and the preview.

### Principle 2: Object spread: a new object that copies the old one and changes one property
- **Handle**: `new-object-with-spread`
- **Thread Step**: what the new object copies
- **Rule**: We build the new object with the three dots first and the change after them: the dots copy every property, the property written after them replaces the copied one, and the setter stores exactly the object it gets, so a property we leave out is gone.
- **Kind**: Decision
- **Reader Question**: "The fix copies the whole article with the three dots just to change the title. Can I pass only the property that changed, `setArticle({ title: e.target.value })`?"
- **Reader Expects**: yes; React merges the new title into the old article, as `this.setState` does in the class components of older tutorials; or the dots may go anywhere in the object, since they copy the same properties
- **React Does**: the setter stores the object it receives as the whole new state, with no merge; `{ title: e.target.value }` has no `summary` and no `author`; the render reads `article.author.bio` and throws a `TypeError`, "Cannot read properties of undefined (reading 'bio')"; React removes `ArticleForm`, and the page goes blank; `{ ...article, title: e.target.value }` copies `title`, `summary`, and `author` into a new object, then the `title` written after the dots replaces the copied one, the same last-one-wins order as the spread attributes of Q07; the new object is a different object, so React renders, and the preview shows the new title with the old summary and author; `{ title: e.target.value, ...article }` lets the copied old title win: React renders, but the field gives back the "!", and the title stays
- **Placement**: `setArticle({ ...article, title: e.target.value })` in `handleTitle` and `setArticle({ ...article, summary: e.target.value })` in `handleSummary`; the dots first, the change after them
- **Real Mistake**: `setArticle({ title: e.target.value })` in `handleTitle`, the merging habit of `this.setState`: typing "!" throws "Cannot read properties of undefined (reading 'bio')", and the page goes blank; also `setArticle({ title: e.target.value, ...article })`: a render runs, and the title stays "New Park Opens Today"; verified in React 19.3.1 and Chrome
- **Importance**: the card's Mechanism; react.dev's Challenge "Fix incorrect state updates" (the lost score); reviewers flag a lost property; interviewers ask how to change one property of an object in state
- **Review Point**: Do
- **Required Lesson Proof**: `handleTitle` with the dots first: "!" shows in the field and the preview, and the summary and the author stay; without the dots: the error and the blank page; with the dots after the change: the title stays.

### Principle 3: Nested objects: a new object at every level down to the change
- **Handle**: `copy-every-level`
- **Thread Step**: how deep the copy goes
- **Rule**: The three dots make a shallow copy: they copy one level, and an inner object stays shared by the old object and the copy; to change a property inside it, we copy every object on the path from the top to the change, and the objects off the path may stay shared.
- **Kind**: Decision
- **Reader Question**: "The bio sits inside `article.author`. I copied the article with the dots, `const next = { ...article }`, then wrote `next.author.bio = e.target.value`. The new bio shows. Is that fine?"
- **Reader Expects**: yes; the dots made a full copy of the article, so changing the copy is safe, as a copied folder holds its own copy of every file inside; and `same-object-no-render` allowed changing an object we have just built
- **React Does**: `author` holds a reference to a separate object; the dots copy that reference, not the author object, so `next.author`, `article.author`, and `firstArticle.author` are one object; `next` is ours, but `next.author` is not; the assignment changes the shared author; `next` itself is new, so React renders, and the preview shows the new bio; ESLint and oxlint report nothing, because `next` is a new object; but `firstArticle.author.bio` has changed too: after a change in Title, Undo changes, `setArticle(firstArticle)`, brings back the first title and keeps the new bio; the article of every earlier render, its snapshot (Q16), shows the new bio as well; `{ ...article, author: { ...article.author, bio: e.target.value } }` makes a new article and a new author, copying the name; `firstArticle` keeps "Mary writes about the city.", and Undo brings back both; the title and the summary are copied by the outer dots, and nothing else needs a copy; `{ ...article, bio: e.target.value }` adds a `bio` at the top of the article, so the preview, which reads `article.author.bio`, keeps the old bio; `author: { bio: e.target.value }`, without the inner dots, loses the author's name, and the preview shows "By" with nothing after it
- **Placement**: `setArticle({ ...article, author: { ...article.author, bio: e.target.value } })` in `handleBio`; one copy for each object on the path, the article and its author
- **Real Mistake**: `const next = { ...article }; next.author.bio = e.target.value; setArticle(next);` in `handleBio`; typing "!" shows the new bio; after a "!" in Title, Undo changes brings back "New Park Opens Today" and keeps "Mary writes about the city.!"; ESLint 10.12.0 with `eslint-plugin-react-hooks` 7.1.1 and oxlint 1.88.0 report nothing; verified in React 19.3.1 and Chrome
- **Importance**: the card's Code Experiment and Under the Hood; react.dev's Challenge "Find and fix the mutation"; the shallow copy passes a quick review and the lint and still changes old state; interviewers ask what a shallow copy is and how to update a nested property
- **Review Point**: Do
- **Required Lesson Proof**: `handleBio` with the shallow copy and the assignment: the new bio, then a change in Title, then Undo keeps the new bio; with the copy at both levels: Undo brings back the first bio; `{ ...article, bio }`: the preview keeps the old bio; `author: { bio }`: "By" with no name.

### Principle 4: Computed property names: a new object whose changed property comes from the field's name
- **Handle**: `name-matches-key`
- **Thread Step**: which property it changes
- **Rule**: When several fields change the same object the same way, one handler reads the changed field's `name` attribute and uses it, in square brackets, as the property to replace; each field's `name` must equal its property, and a field inside an inner object still needs its copy at every level.
- **Kind**: Decision
- **Reader Question**: "`handleTitle` and `handleSummary` differ in one word. Can one handler serve both fields?"
- **Reader Expects**: one handler per field, as each button got its own handler in Q13, which works and is only repetitive; or a variable written as the property name, `{ ...article, field: e.target.value }`
- **React Does**: typing fires the field's `onChange` with the event object; `e.target` is the field typed in (Q13); `e.target.name` is its `name` attribute, "title" or "summary"; in an object literal, a name in square brackets is computed: `[e.target.name]` uses the string as the property name; `{ ...article, [e.target.name]: e.target.value }` is a new article with that one property replaced; React renders, and the preview shows the typed text in the right place; a plain name is the word itself: `field: e.target.value` adds a property called "field", and the title stays; `e.target.name:` without the brackets does not build, and Vite shows "Expected `,` or `}` but found `.`"; a field named "sumary" adds a property "sumary", and the field gives back the typed key; the Bio field sits inside `author`, so it keeps `handleBio` and its copy at both levels
- **Placement**: one `handleChange` with `setArticle({ ...article, [e.target.name]: e.target.value })`, and `name="title"` and `name="summary"` on the two fields; `handleBio` stays for the author's bio; separate handlers stay right when the fields change the object in different ways
- **Real Mistake**: none; one handler per field is valid code, and the attempts without brackets come from readers who have not met them yet, so the lesson shows them as the reason for the brackets
- **Importance**: the card's Mechanism; react.dev's `<DeepDive>` "Using a single event handler for multiple fields"; interviewers ask what the square brackets do; a form with ten fields otherwise copies one handler ten times
- **Review Point**: Prefer
- **Required Lesson Proof**: `handleChange` on Title and Summary: "!" in each shows in the right place, from one handler, and Undo brings back both; `field:` adds a "field" property and the title stays; `e.target.name:` without brackets stops the build.

## Senior Answer
I treat every object in state as read-only. React does not stop me from changing it in place. But the setter compares the next value with the current one using `Object.is`. That checks whether it is the same object, not what is inside it. A changed object is still the same object. So React skips the render, and the old data stays on the screen until something else renders. To change a property, I build a new object with spread syntax. The spread comes first and copies the old properties. The changed property comes after it and wins. The setter does not merge, so a property I leave out is lost. Spread makes a shallow copy. An inner object is shared by the old object and the copy. So for a nested change, I copy every object on the path: the article, and then its author. Otherwise I also change the old object, and an Undo that goes back to it breaks. For a form, one handler with a computed property name, `[e.target.name]`, can update every top-level field. For deep nesting, Immer can make the copies for me.
