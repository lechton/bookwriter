## Authorized Scope
Lesson 01 teaches one change of habit. In plain JavaScript, we find each element on the page and change it by hand. In React, we write a component, `SiteHeader`, that describes what the header shows for its data. React builds the page from that description. The reader's name lives in one variable, `userName`, and every place that shows the name reads it. So no place can show an old copy. When the name changes, React compares the new description with the last one. It changes only the text that is new, so the search box keeps what the reader typed. The data stays fixed in the code. The lesson changes it by editing the file, and the dev server shows the result.

## Theme and Options
- **Theme**: When the data changes, how does the page change with it?
- **Option**: imperative programming: `document.getElementById('greeting').textContent = 'Welcome back, Mary Brooks'`, and our code finds each element and sets its text | plain JavaScript, no lesson (the reader's habit without React) | one element changes in one place, such as a clock in a corner of the page
- **Option**: declarative programming: `<p>Welcome back, {userName}</p>`, and React makes the page match it | this lesson | the same value shows in several places, or many parts of the page change
- **This lesson teaches**: declarative programming

## Principle Thread
- **Anchor**: describing the page from data: we describe what the page shows, and React makes the browser match
- **Axis**: the path of one value: described, shared, changed
- **Why This Axis**: The three principles are three moments in the life of `userName`. First the header is described from it, then many places read it, then it changes. Each moment needs the one before it, so the axis order and the dependency order are the same. Two axes were rejected. "Who does the work, we or React" splits the first principle in two and has no place for the second. "Before, during, and after an update" has no place for the second either, because sharing one value is not a moment of an update.
- **Spoken Preview**: Everything in this lesson comes down to one idea: we describe the page from data, and React makes the browser match. First, declarative programming, which means describing what the page shows, not how to change it: we write what each element shows for the data, and React changes the DOM to match, so our code never finds an element by hand. Second, a single source of truth, which means describing many places from one value: when a name appears in many places, every place reads it from one variable, so no place can show an old copy. Third, the virtual DOM, which means describing the page again when the value changes and comparing the two descriptions: React changes only the new text, so whatever the user typed stays where it was.
- **Closing Line**: One description, one value, and the smallest change.

## Principles

### Principle 1: Declarative programming: describing what the page shows, not how to change it
- **Handle**: `describe-from-data`
- **Thread Step**: the anchor itself: the value is described
- **Rule**: We control the page by describing what it shows from data, and we never find and change its elements by hand.
- **Kind**: Model
- **Reader Question**: "In plain JavaScript I find each element by its id and change its text. What do I write instead in React?"
- **Reader Expects**: some React way to find elements and change them, like `document.getElementById('greeting').textContent = ...`; a habit from plain JavaScript and jQuery
- **React Does**: we write `SiteHeader`, a function that returns the header's markup with `userName` in it; React calls it and builds the DOM from what it returns; the page shows "Welcome back, Mary" and "Signed in as Mary"; `index.html` still holds only the empty root, and no line of our code finds or changes an element
- **Placement**: what each element shows goes in the markup `SiteHeader` returns; no `getElementById`, `textContent`, or `innerHTML` in our code
- **Real Mistake**: the plain JavaScript `updateHeaderUser('Mary Brooks')` sets the greeting by id and forgets the corner; the page shows "Welcome back, Mary Brooks" beside "Signed in as Mary"; verified in jsdom 30.1.2
- **Fix In**: this principle
- **Importance**: it is the interview question; every later lesson assumes the reader describes instead of commands
- **Prediction**: the served `index.html` holds only `<div id="root"></div>`, yet the Elements panel shows the header with "Welcome back, Mary" and "Signed in as Mary"; a search of our code finds no DOM call.
- **Required Lesson Proof**: the card's plain JavaScript page with a greeting and a corner: `updateHeaderUser('Mary Brooks')` leaves the corner on "Mary"; then `SiteHeader` in the prepared project: the served `index.html` with its empty root beside the Elements panel with the whole header.

### Principle 2: Single source of truth: describing many places from one value
- **Handle**: `one-value-every-place`
- **Thread Step**: the value is shared: one variable, many places
- **Rule**: When one value appears in many places, we describe every place from one variable, and we never type a copy of it.
- **Kind**: Decision
- **Reader Question**: "The reader's name shows in the greeting and in the corner. Do I write it in both places?"
- **Reader Expects**: yes, copy "Mary" into each spot, as in a static HTML page
- **React Does**: `const userName = 'Mary'` holds the name once; the greeting and the corner both read `{userName}`; change the variable to `'Mary Brooks'` and save, and both places show the new name, because both are built from it
- **Placement**: one `userName` variable at the top of `SiteHeader`; every place that shows the name reads it with `{userName}`; no copy of the name typed into the markup
- **Real Mistake**: markup pasted from the old HTML page keeps `Signed in as Mary` as fixed text in the corner; after `userName` becomes `'Mary Brooks'`, the greeting shows "Mary Brooks" and the corner still "Mary"; verified in React 19.3.1
- **Importance**: the card's Friction; reviewers flag a value typed twice; interviewers expect the phrase single source of truth
- **Review Point**: Do
- **Required Lesson Proof**: `SiteHeader` first with the corner text typed in by hand: change `userName` to `'Mary Brooks'`, save, and the corner keeps "Mary"; then with `{userName}` in both places: both show "Mary Brooks".

### Principle 3: The virtual DOM: describing the page again when the value changes
- **Handle**: `smallest-change`
- **Thread Step**: the value changes: a new description, the smallest change
- **Rule**: When the value changes, React compares the new description with the last one and changes only the new text, so whatever the user typed stays where it was.
- **Kind**: Model
- **Reader Question**: "If React builds the header from my description, does it throw the header away when the name changes, and wipe what I typed in the search box?"
- **Reader Expects**: yes, the whole header is thrown away and made again, as with `header.innerHTML = ...`; a habit from template strings and from server pages that reload
- **React Does**: the file is saved with `'Mary Brooks'`; the dev server makes React call `SiteHeader` again, which returns a new description; React compares it with the last one; it changes the two text pieces that hold the name; the `<input>` stays the same element, so "elections" and the focus stay
- **Placement**: describe the whole header from the data and let React change the page; never rebuild part of the page with `innerHTML`
- **Real Mistake**: the plain JavaScript habit of rebuilding the header with a template string, `header.innerHTML = '<p>Welcome back, ' + name + '</p><input>'`; the new `<input>` is empty, "elections" typed into the old one is gone, and focus falls back to the page body; verified in jsdom 30.1.2
- **Fix In**: this principle
- **Importance**: interviewers ask how React updates the page, what the virtual DOM is, and whether React is faster than the DOM; the card's Under the Hood
- **Prediction**: with "elections" typed in the search box, saving the file with `'Mary Brooks'` changes the name in the greeting and in the corner; the search box keeps "elections" and the focus.
- **Required Lesson Proof**: the plain JavaScript header with "elections" typed in the search box: `innerHTML` with the new name empties the box and moves focus to the page body; then `SiteHeader` in the dev server with "elections" typed: the file saved with `'Mary Brooks'`, both names change, and the box keeps "elections" and the focus.

## Senior Answer
React is a JavaScript library for building user interfaces out of components. In plain JavaScript, I find each element and change it by hand. That is imperative code, and one forgotten element leaves old data on the page. React is declarative. A component describes what the page shows for the current data. React builds the DOM from that description. I keep each value in one variable, and every place reads it. So no place can show an old copy. When the data changes, React compares the new description with the last one. It changes only the text that is new. The elements around it stay, so a search box keeps what the user typed. People call that description the virtual DOM. The gain is not raw speed, because React still calls the same DOM methods. The gain is that I no longer write, or forget, the update steps.
