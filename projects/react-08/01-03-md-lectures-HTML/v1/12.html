Lecture 12: Keeping Components Pure

Interview Question

CORE

What does it mean for a component to be pure, and what breaks when it is not?

  • Your article list numbers its cards with a counter that lives outside the card component.
  • The cards show #2, #4, and #6, and after you save a file, #8, #10, and #12.
  • What may a component do while React runs it, and what goes wrong when it does more?

React runs our components, sometimes more often than we expect

Since Lecture 2, React has called our components, and every component so far only returned JSX built from its props. Lecture 2 also noticed something odd: every console.log inside a component printed twice. So every React developer meets the same question sooner or later: React runs our components, sometimes more often than we expect, so what may a component do while it runs?

React's answer has a name from mathematics: a component must be pure. This chapter follows one idea from the first question to the last: pure rendering, which means that each call of a component only calculates its JSX from its inputs. It looks at that idea in three steps: what each call may give back, what each call may change, and how React checks both. The Rules of React, which Lecture 82 explores in detail, begin with this exact requirement.

This lesson answers three questions:

  1. My cards number themselves with a counter outside the component. Why do they show #2, #4, #6?
  2. I want a "See all articles" item at the end of the list. Can I push it into the articles array?
  3. Every console.log in my component prints twice. Should I remove Strict Mode?

A pure function only calculates

A formula from school, y = 2x, gives 6 for 3, every time. A JavaScript function can work the same way:

A pure function
1function double(number) {
2 return 2 * number;
Double(3) is 6, every time
3}

double is a pure function, and it has two properties. It gives the same result for the same inputs, every time: this is called idempotence, from the Latin for "the same power". And it changes nothing that existed before it was called: no outside variable, no object it received, nothing on the page. A change of that kind is called a side effect, because it happens on the side of the result.

Two functions that are not pure
1let total = 0;
2function addToTotal(number) {
3 total = total + number;
Changes an outside variable
4 return total;
5}
6const pick = () => Math.random();
Different result on every call

addToTotal(3) gives 3, then 6, then 9, because each call changes the variable the next call reads. Math.random() gives a new number every time, by design. A pure function only calculates: the same inputs give the same result, and nothing outside it changes.

Some array methods change the array they are called on

Changing an object or an array that already exists is called a mutation. Some array methods mutate: push() adds an item at the end of the array it is called on, reverse() turns it around in place, and sort() reorders it in place. Others, such as map() and filter() from Lecture 11, leave the array alone and give back a new one.

Changing an array, and changing a copy
1const titles = ['New Park', 'Rain'];
2titles.push('Soups');
Titles itself now has three items
3const copy = [...titles];
4copy.reverse();
Copy is reversed, titles is not

The copy is new, so changing it changes nothing anyone else holds. Changing something created a moment ago, inside the same function, is called local mutation, and it is harmless. Mutation changes an array that already exists; a copy turns it into local mutation.

Principles of React: Pure Rendering

Everything in this lesson comes down to one idea: pure rendering, which means that each call of a component only calculates its JSX from its inputs.

First, idempotence, which means each call gives the same JSX for the same inputs: what the component shows depends on its props alone, never on how many times it was called.

Second, no side effects, which means each call changes nothing that existed before it: the component may change only what it created during the same call.

Third, Strict Mode, which means each component is called twice in development, to catch impure calls: we keep it on, because a pure component shows nothing different on the second call.

My cards number themselves with a counter outside the component. Why do they show #2, #4, #6?

ANSWER

The code does not do what we wanted. Reading and writing a module-level variable during render makes component output depend on how many times the function was called.

In plain JavaScript, developers often use an outside counter to count how many times a function runs. Because React renders three <ArticleCard /> tags, it is intuitive to expect three function executions. But React does not guarantee that a component executes only once per tag. In development, <StrictMode> deliberately invokes each component function twice to verify purity, and every saved change in Vite triggers a re-render.

Because cardNumber lives at the top level of the module outside the component function, its value persists across all component calls. When React renders the first card, Strict Mode runs ArticleCard twice. The first execution increments cardNumber from 0 to 1 and discards the result. The second execution increments cardNumber from 1 to 2, rendering #2. The second card runs twice, advancing the counter through 3 and 4 to render #4. The third card advances through 5 and 6 to render #6. When Vite triggers a live reload, cardNumber is already 6, so the next render pass increments it through 7 to 12.

The component is not idempotent: the JSX it returns depends on how many times React executed the function, rather than on the data passed to it. Calling non-deterministic utilities like Math.random() or new Date() inside the render body fails for the exact same reason: each call computes a different value. Furthermore, components must never communicate with each other through shared outside variables, because React promises no fixed execution order between components (Lecture 5). To change what appears on screen interactively over time, components set state (Lecture 14) instead of mutating shared variables.

The fix is to pass the item's position as an input prop. In ArticleList, the map() callback receives the array index as its second parameter. Passing number={index + 1} hands each card a deterministic number:

PRINCIPLE 1

Idempotence: each call gives the same JSX for the same inputs

A component's JSX depends only on its props: we never read and change a variable outside the component while it runs, and never show a value that changes on every call, such as Math.random() or new Date(); a number that depends on an item's place comes in as a prop.

React calls a component whenever it needs its JSX, and it may call it more than once. A variable outside the component is shared by every call, so a component that adds one to it gives a different number on each call: the page then shows how many calls happened, not what the props say. A value that changes by itself, such as Math.random(), does the same. When every value the JSX shows comes from the props, every call gives the same JSX, however many calls there are.

I want a "See all articles" item at the end of the list. Can I push it into the articles array?

ANSWER

The code does not do what we wanted. Calling articles.push() mutates an array that existed before the render call, producing a side effect that corrupts data across render passes.

In standard JavaScript scripts, calling push() appends one item to an array. But in ES modules (Lecture 8), the top level of articles.js runs only once. The articles array exported from that file is a single shared object in memory. Every time React executes ArticleList, the component receives a reference to that exact same array.

Calling articles.push() inside the component body is an impure mutation of existing data. Because Strict Mode executes ArticleList twice in development, articles.push() executes twice. The shared array now contains two identical "See all articles" objects with id: 'all'. When the JSX maps over the array, both items render to the DOM, triggering React's duplicate key warning. If Strict Mode were turned off, the item would appear once on first load, but saving a file would push a second item on the subsequent render pass.

A common junior attempt is writing a conditional guard: if (!articles.some(a => a.id === 'all')) articles.push(...) While this prevents duplicate DOM entries, it still mutates shared application memory during render. Any other component importing articles receives the modified array.

The solution is local mutation. We use spread syntax (Lecture 7) to create a shallow copy of the array inside the render function: const items = [...articles]; Because items is created during the current render execution, it belongs exclusively to this single call:

Calling items.push() mutates only the newly created local array. The original articles array in articles.js remains untouched. Whether React executes ArticleList once, twice, or ten times, each call creates a clean copy and appends exactly one item.

Other mutating methods like reverse() and sort() behave identically: calling articles.reverse() directly during render creates bizarre bugs where Strict Mode's second render reverses the array back to its original order. Mutating external targets like browser tabs (document.title = article.title) or querying the DOM with document.getElementById() inside the render body are also side effects: each card overwrites the tab, leaving only the last card's title. All side effects belong in event handlers (Lecture 13), which execute on user interaction rather than during render.

PRINCIPLE 2

No side effects: each call changes nothing that existed before it

While a component runs, we change only what that call created: a copy of an array or object is ours to change, while props, imported data, outside variables, and the page itself stay as they were; changes to the outside world belong in event handlers.

An array or object that existed before the call, such as a prop or imported data, is shared: every call receives the same one. So a component that pushes into it changes it for every later call and for everyone else who reads it, and a second call pushes again. A copy made inside the call is new each time, so changing it changes nothing outside. The same holds for the page itself: a component that sets the tab's title changes something it did not create.

Every console.log in my component prints twice. Should I remove Strict Mode?

ANSWER

The code does not do what we wanted. Removing <StrictMode> eliminates the diagnostic double-run that exposes impure code, hiding mutations until user interaction or hot reloading triggers the bug in production.

When developers first notice that component functions execute twice, it is natural to assume that React has a bug or is wasting browser resources. But as promised in Lecture 2, the double execution is an intentional development-only mechanism provided by <StrictMode>.

In development, <StrictMode> executes every component function twice and keeps the JSX returned by the second run. When a component is pure, both executions return identical JSX trees and produce no side effects. The browser DOM reflects the exact same markup, and the only observable evidence of the second run is the doubled console output. When React DevTools is installed in Chrome, the browser console automatically dims the log entries produced by the second call.

When a component is impure, however, the second execution produces a different result from the first. The counter from Question 1 exposed this immediately by displaying #2, #4, and #6 on initial mount. Removing <StrictMode> silenced the second execution, temporarily masking the bug by showing #1, #2, and #3. But the underlying defect remained: the next render pass inevitably corrupted the numbers to #4, #5, and #6.

Removing <StrictMode> does not fix impure components; it merely hides the warning signal. Furthermore, <StrictMode> is strictly a development tool. In the production build (npm run build followed by npm run preview), React never invokes components twice. Production builds execute each component once, printing three log lines for three cards. Strict Mode costs your production users zero performance overhead. Lecture 46 explores additional checks that Strict Mode performs on updaters and ref callbacks.

⚡ IN THE WILD

Why does React want components that can be called any number of times?

A beginner might ask why React insists on pure components that tolerate multiple executions rather than guaranteeing exactly one execution per tag. Because pure components are completely decoupled from call counts, React gains extraordinary operational capabilities. React can pre-render components on a backend server before shipping HTML to the client (Lecture 102). React can skip executing components whose props remain unchanged (Lecture 55). And in concurrent rendering, React can pause a long-running background render halfway through, execute an urgent user keystroke, and restart the background render from scratch (Lecture 66). Each of these optimizations relies on one invariant: calling a component produces identical JSX and alters nothing outside itself.

Where you will meet this

  1. Numbered rows and rankings: Leaderboards, search results, and paginated tables calculate item numbers from array index offsets passed as props, never from module-level counter variables.
  2. Sorting and filtering shared collections: Specialized views like "recent stories" or "alphabetical directory" clone arrays via [...items].sort() before reordering, protecting shared data from mutating in place.
  3. Double logging in development: Every new Vite and Next.js project enables Strict Mode by default; understanding the diagnostic double-run prevents developers from prematurely disabling the check.
  4. Code reviews and linter gates: Senior reviewers flag mutations of props, outside variables, and imported datasets during render before code reaches staging environments.
  5. Updating external browser state: Modifying document titles, triggering analytics beacons, or manipulating local storage belong exclusively inside event handlers (Lecture 13) or Effects (Lecture 31), never in render bodies.

For the interview

The Interview Question: What does it mean for a component to be pure, and what breaks when it is not?

1. The Hidden Signal

Interviewers ask this question to probe whether a candidate understands React's functional execution model. A junior developer often recites that pure components "have no side effects" without explaining why React cares. A senior engineer explains both pillars of purity: idempotence (same inputs yield identical JSX output) and zero side effects (render executions mutate nothing that existed prior to invocation). They explain that React components can be executed multiple times, out of order, or on worker threads, making purity a mandatory architectural prerequisite.

2. The Classic Trap

The classic trap is blaming Strict Mode for rendering bugs and proposing to remove <StrictMode> from main.jsx. Candidates often observe doubled counters or duplicated list items and assume Strict Mode is defective. A strong candidate clarifies that Strict Mode intentionally runs components twice in development to surface existing mutations. Removing Strict Mode merely hides the bug until the application is re-rendered by user state changes or hot module reloading in production.

3. What is Actually Going On

When a component alters a variable outside its local scope, that variable acts as shared state across render passes. Because React executes component functions to build virtual DOM trees, any mutation of outside variables makes the resulting JSX dependent on the history of previous executions rather than the current props.

Similarly, calling mutating array methods like push(), splice(), or reverse() on props or imported arrays alters objects in shared memory. Subsequent render calls receive the mutated array, causing duplicate items, reversed layouts, and corrupted keys. Confining mutations to local variables created within the current render execution keeps the function pure.

4. Where It Gets Tricky

Is it illegal to mutate any variable during render? No. Mutating variables, arrays, or objects created entirely within the current render call (local mutation) is completely safe because no outside entity holds a reference to them.

Why does calling articles.reverse() appear to do nothing in development? Strict Mode calls the component twice. The first execution reverses the shared array; the second execution reverses it back to its original order, producing a phantom bug where the code appears ignored.

Can a component render Math.random() or new Date()? Not as values computed inline during render. Because each call yields a different value, the component is not idempotent. Generate random IDs or timestamps during user events or pass them as props.

Does Strict Mode double-render in production? No. Production builds execute component functions exactly once.

Where do unavoidable side effects belong? Changes to the outside world belong inside event handlers (Lecture 13), such as click or submit handlers, or, as a last resort, an Effect (Lecture 31).

Why does React require purity? Purity enables server rendering (Lecture 102), skipping renders via memoization (Lecture 55), and concurrent rendering where React pauses and restarts renders to prioritize user input (Lecture 66).

Glossary

  • Pure function: A function that returns identical output for identical inputs and causes zero side effects on entities outside its scope.
  • Idempotence: The mathematical property where multiple identical invocations produce the exact same result as a single invocation.
  • Side effect: Any modification of state or interaction with the outside world that occurs during function execution, such as mutating outside variables, altering the DOM, or writing to storage.
  • Local mutation: Modifying objects, arrays, or variables that were instantiated entirely within the current function execution.
  • Strict Mode: A React development-only wrapper component (<StrictMode>) that invokes component render functions twice to expose impure calculations and side effects.

Summary

Pure rendering: each call of a component only calculates its JSX from its inputs

❒ Idempotence: each call gives the same JSX for the same inputs
  • ALWAYS build what a component shows from its props, and pass a number that depends on the place as a prop.
  • NEVER read and change a variable outside the component while it runs.
  • NEVER show a value that changes on every call, such as Math.random() or new Date(), computed while the component runs.
❒ No side effects: each call changes nothing that existed before it
  • ALWAYS copy an array or object before you change it, [...items].
  • NEVER call push, sort, or reverse on props or imported data while a component runs.
  • IF something outside the page's JSX must change THEN do it in an event handler, never while the component runs.
❒ Strict Mode: each component is called twice in development, to catch impure calls
  • ALWAYS keep <StrictMode> around the app; the doubled logs are the check at work.
  • IF the second call shows a different page THEN fix the component, not main.jsx.
