Lecture 2: Component Anatomy and the Capitalization Rule

Interview Question

CORE

What is a React component, and what rules govern how you write and name one?

Imagine this scenario:

  1. You built an article card component to display a headline and summary.
  2. You mount it with <articleCard />, but the page stays blank and the function never runs.
  3. What rules govern how we write and name a component?

Calling a function yourself or letting React run it

Every website breaks its interface into reusable pieces: a card for an article, a button for an action, a row for a comment. In JavaScript, we write functions to build these pieces. So every web developer meets the same question: when we write a function that describes a piece of the user interface, how do we run it and put it on the page?

There are two ways to run a function that describes UI.

The first way is a function call, which you know from plain JavaScript: you call the function with parentheses yourself:

Function call: you run the function yourself
1const card = articleCard();
Runs immediately

Inside articleCard(), the code runs right away. Your code calls the function, waits for it to finish, and takes the returned value. The browser evaluates each line synchronously at that exact moment. That is why it is called a function call: our code issues the call and controls when it happens. It fits well for helper functions that compute values, such as calculating a shopping cart total or formatting a date. It fits badly for building a React interface: if you call component functions directly, React cannot track when they run or coordinate updates to the page.

The second way is a component tag, which React uses and this chapter teaches: instead of calling the function with parentheses, you write its name as a capitalized tag in markup:

Component tag: React runs the function
1<ArticleCard />

Notice what is missing: there are no parentheses () after ArticleCard. You do not call the function. Writing <ArticleCard /> hands React a reference to the function itself. React takes custody of that function, decides when the page needs it, and calls ArticleCard() during its render phase. That is why it is called a component tag: you declare where the component belongs in the markup, and React handles the execution.

A second component works the same way:

Component tag: author badge
1<AuthorBadge />

Our code never calls AuthorBadge(). React calls AuthorBadge() when rendering the layout, reads the markup it returns, and builds the HTML elements on the screen.

Two ways to run a function that describes UI

(1) Run a function with a function call (plain JavaScript): you call the function with parentheses yourself, evaluating its lines immediately.

(2) Run a function with a component tag (this chapter): you write its name as a capitalized tag in markup, and React calls the function during render.

Calling a component function directly also bypasses element tracking and breaks the order of Hooks when components hold state. Lecture 37 covers that rule.

We will see who calls it and when, why component names must start with a capital letter, why long markup after return needs parentheses, and why components must be defined at the top level of the file. At the end, we compare the naive JavaScript reflex against React's component rules.

Passing a component tag hands React a function reference

A React component is a regular JavaScript function that returns JSX markup describing a slice of the user interface. We use export default to mark the main component function of a file so that other files can import and reuse it. Unlike monolithic HTML files where markup and behavior live in separate documents, a component packages structure and presentation into a single cohesive unit.

In standard JavaScript, when we want a function to run immediately, we write parentheses after its name, such as ArticleCard(). Calling a function evaluates its lines right away and produces its return value synchronously. In React, our code does not call component functions directly. When we write <ArticleCard /> in markup, we do not call ArticleCard(). Instead, JSX passes the function itself, known as a function reference, to React.

React takes custody of the function reference and enters its render phase. React decides when to call the component function based on what is happening in the application. When React renders the parent layout, it calls ArticleCard, inspects the JSX markup it returns, and builds the corresponding DOM elements on the screen. Because React orchestrates rendering, it can optimize screen updates, coordinate child lifecycles, and skip unnecessary work.

Capital letters tell the compiler to build a component

Browsers natively recognize a fixed catalog of HTML tags, such as <article>, <h2>, <p>, and <button>. A web application combines these native building blocks with custom components created by developers. When a compiler parses markup containing both native tags and custom components, it must determine whether each tag represents a built-in browser element or a JavaScript function.

React resolves this distinction using a strict casing rule: PascalCase. Under PascalCase, the first letter of each compound word is capitalized, such as ArticleCard. When the JSX compiler converts markup into JavaScript code, it checks the casing of the tag name. If the tag begins with a lowercase letter, the compiler emits a string literal: _jsx("article"). If the tag begins with an uppercase letter, the compiler emits an unquoted variable identifier: _jsx(ArticleCard).

If a developer accidentally names a component with a lowercase letter and mounts <articleCard />, the compiler treats it as a native HTML tag. React instructs the browser to create an element named articlecard, which the browser appends as an empty, unstyled DOM node. Because this is a frequent developer mistake, React prints two clear warning messages in the browser development console: one warning that the tag uses incorrect casing and should use PascalCase, and a second warning that the tag is unrecognized in the browser.

JavaScript inserts semicolons after isolated return keywords

JavaScript includes a language mechanism called automatic semicolon insertion, or ASI. When the JavaScript parser reaches the end of a line, it checks whether the statement is complete. If the keyword return stands completely alone on its line, the parser treats the return statement as finished and automatically inserts an invisible semicolon immediately after it: return;.

If a developer writes return on one line and places multi-line JSX markup on the next line, the function immediately terminates and returns undefined. The JSX markup below the return statement is unreachable and never executes. React receives undefined for the component, paints nothing on the screen, and reports no error in the browser window. Bundlers such as esbuild emit a build warning alerting the developer that an expression is unreachable due to an automatically inserted semicolon.

To prevent automatic semicolon insertion when returning multi-line markup, developers open a parenthesis ( on the exact same line as the return keyword. The opening parenthesis signals to the ECMAScript parser that the return expression is incomplete and continues across multiple lines. The parser waits until it encounters the matching closing parenthesis ); before ending the statement, allowing the complete JSX tree to evaluate reliably.

Defining a function inside another creates a new function on every run

In JavaScript, developers frequently declare helper functions inside other functions. A function declared inside the body of an outer function is called a nested function. Every time the outer function executes, JavaScript creates and allocates a brand-new inner function in memory with a distinct object reference.

When a developer defines a React component inside the body of another component, this allocation becomes an architectural bug. Every time the outer component renders, it defines a completely new component function. When React compares the new render with the previous one, it sees a different function reference at that position in the tree. React concludes that the old component was removed and an entirely new component was mounted in its place.

Because React treats different component functions as completely different elements, it destroys the existing DOM subtree and constructs new DOM nodes from scratch. If the component contains an interactive <input>, any text the user typed is immediately destroyed, and keyboard cursor focus is lost. To preserve component identity across renders, developers define every component at the top level of the file, outside and alongside other components.

Who calls ArticleCard, and when does it run?

ANSWER

The code works as React intended. React calls the function when another component renders markup that names it.

Declaring a component function does not execute it. In plain JavaScript, declaring function ArticleCard() allocates the function in memory, but nothing runs until code invokes it. The code does not do what we wanted. Defining a component inside another creates a brand-new function identity on every parent render.

In JavaScript, declaring a function inside another creates a new function object in memory every time the outer function runs. For the interview

The Interview Question: What is a React component, and what rules govern how you write and name one?

1. The Hidden Signal

The interviewer is not merely testing whether you know how to write a function keyword. They are probing whether you understand how JSX transpiles into function calls and why React insists on orchestrating execution. A junior candidate answers that capitalization is just an aesthetic style convention. A senior engineer explains that the JSX compiler branches on Unicode casing: lowercase tags compile to string literals for native elements, while uppercase tags compile to unquoted function references that React invokes during render.

2. The Classic Trap

The classic trap is claiming that you can call component functions directly inside curly braces {ArticleCard()} to save typing. While executing the function returns markup in simple examples, calling a component directly strips its component boundary, inlining child markup into the parent and breaking React's ability to isolate updates or manage Hooks. Another frequent trap is defining helper components inside parent render functions, which causes React to destroy and rebuild DOM trees on every render pass.

3. What is Actually Going On

A React component is a standard JavaScript function that returns JSX markup. We never invoke it directly; we write it as a tag, like <ArticleCard />, inside another component. That tag passes a function reference to React. When React renders the parent, it executes the function and commits the resulting elements to the DOM. Four concrete rules govern component authoring: (1) start names with a capital letter in PascalCase so the compiler emits function references, (2) open parentheses on the same line as return so automatic semicolon insertion does not return undefined, (3) declare components at module top level so function identity remains stable across renders, and (4) return a valid single root element or Fragment.

4. Where It Gets Tricky

Where this gets tricky in production is diagnosing subtle silent bugs. A lowercase tag compiles cleanly without terminal syntax errors; the only clues are an empty custom tag in DevTools and two development console warnings. Similarly, an unparenthesized multi-line return renders a blank component without throwing a browser runtime error, though modern bundlers emit build warnings. Finally, defining components inside parent render functions works deceptively on initial mount, only to destroy user input text and reset focus rings the moment parent state triggers a second render.

Glossary

  • Component: A self-contained JavaScript function whose name starts with a capital letter and returns a description of user interface markup in JSX.
  • PascalCase: A naming convention where the first letter of each compound word is capitalized, used by the JSX compiler to distinguish custom component functions from native HTML elements.
  • Function Reference: An unquoted reference to a JavaScript function in memory, passed to React so the runtime can execute the function during render.
  • Automatic Semicolon Insertion: A JavaScript language feature that inserts an invisible semicolon after an isolated return keyword, causing functions to return undefined if markup starts on the next line.
  • Nested Component: A component function defined inside the body of another component, causing React to treat it as a brand-new component type and rebuild its DOM on every render.

Summary

Architectural Takeaways & Decision Matrix

❒ Component Naming and Compiler Casing

➔ ALWAYS name custom components in PascalCase so the JSX compiler emits an unquoted function identifier rather than an HTML string literal.

➔ NEVER define component functions in lowercase or camelCase because the browser treats lowercase tags as native elements and fails silently.

❒ Return Statement Layout

➔ ALWAYS wrap multi-line JSX return statements in parentheses with the opening parenthesis on the same line as the return keyword.

➔ NEVER place multi-line JSX markup on the line after return without an opening parenthesis because automatic semicolon insertion will return undefined.

❒ Component Declaration Scope

➔ ALWAYS declare component functions at the top level of the file so their function identity remains stable across renders.

➔ NEVER define component functions inside the body of another component because React will destroy and reconstruct its DOM elements on every render.
