Lecture 18: Updating Objects in State

Interview Question

CORE

How do you update an object in state without mutating it?

Imagine this scenario:

  1. A user updates their account profile on a community website settings page.
  2. The user types a new biography into the form and clicks save.
  3. The developer assigns the new biography directly to the profile object and calls the setter.
  4. Why does the screen refuse to update and keep showing the old biography?
  5. The user refreshes the page in confusion, wondering why their changes disappeared.
  6. No error appeared in the console, and React accepted the setter call without complaint.
  7. Today we learn how React checks object identity, why mutation skips rendering, and how spread syntax preserves state.

One click, a mutated property, and a screen that refuses to change

Until now, state held primitive numbers and strings. In real applications, a single state variable often holds an entire data record. One object stores a user profile, account settings, and nested contact details.

When state holds a JavaScript object, two questions decide what appears on the screen:

  1. How does React check whether a state value actually changed?
  2. Why does mutating a nested object corrupt earlier render snapshots?

If you mutate an object in place, React will not throw an error. Your code will pass a quick glance, and still leave stale information on the screen.

Before looking at the code, here are seven rules from earlier lessons that govern state objects:

  • Object Expressions (Lecture 04): Writing object literals inside JSX curly braces creates standard JavaScript objects.
  • Props Read-Only Contract (Lecture 06): Inputs handed to a component are read-only. You never reassign properties on props, and state follows this same rule.
  • Render Purity (Lecture 12): Any code executing during a render pass must be pure. Given the same inputs, it must return the same output without altering external objects.
  • Event Handling (Lecture 13): Handlers receive a browser event object e holding data from the interactive element.
  • State and Setters (Lecture 14): Declaring state with useState gives you a variable and its setter. Calling the setter is the only valid way to request a screen update.
  • Fixed Snapshots (Lecture 16): Every render receives a fixed snapshot of state that never changes in place during that render.
  • Functional Updaters (Lecture 17): Passing an updater like prev => ({ ...prev }) guarantees calculations read the live queue.

Let's trace how these rules behave when updating objects in state.

Plain objects are silent: why React requires setters

A standard JavaScript object is completely silent.

When you assign to user.bio = 'Architect', JavaScript modifies the property in memory. However, it rings no bells and triggers no alarms.

A plain object has no connection to the browser DOM. It cannot notify the browser that text changed, and it cannot trigger a render on its own.

This is the entire reason React provides setter functions.

In React, a variable is not automatically reactive. React does not watch your variables, and it does not monitor properties inside your objects.

The setter function is the single communication channel between your code and React's rendering engine.

Calling the setter is the only action that hooks your data into React's reactive system. It tells React that a value changed and requests a screen update.

Direct mutation operates outside the reactive system

When you assign directly to a property, you operate completely outside the reactive system.

You changed data in computer memory, but you never notified React. The screen remains frozen because React has no idea you touched anything.

Even worse, calling setUser(user) after a direct mutation fails to fix the problem.

React compares the previous state with the next state using a built-in comparison tool named Object.is.

The Object.is tool checks whether two values share the exact same memory address. It does not inspect the properties inside the object.

Because both variables point to the exact same object in memory, Object.is returns true. React concludes that no state change occurred and skips the render completely.

Reactivity through replacement: why we pass new objects

React does not track property mutations. React tracks object replacements.

To participate in React's reactive system, you must never modify an existing state object. Instead, you create a brand new object and pass it through the setter.

Writing curly braces allocates a fresh object at a new memory address.

To retain existing data without typing every property manually, JavaScript provides the spread syntax. Writing { ...user, bio: 'Architect' } allocates a new object, copies all properties, and overwrites the biography.

Because the new object has a different memory address, Object.is returns false. React detects the state change, schedules a render pass, and updates the screen.

Principles of React: Updating Objects in State

Each question below starts from code you could write today. The answer shows what React does with it. The principle turns that behavior into a rule for production code.

QUESTION 1

State Object Identity & The Skipped Render

Suppose you have state holding a user profile object with a nested details record. You update the user bio by assigning to it directly inside a click handler:

App.jsx
1user.details.bio = 'Architect';
Mutates nested value in memory
2setUser(user);
Hands unchanged reference back to setter
3console.log('handler done');

The handler modifies the bio property directly on the existing user object in memory. Next, it hands that same object reference to setUser, expecting React to detect the edit. Finally, it logs to the console to confirm the click finished running.

After one click, the console shows handler done, but no component render occurs and the screen keeps the old bio. Why does React skip updating the screen even though the object property changed?

ANSWER

The code did not work as intended. Mutating an object preserves its memory address without triggering a render.

React checks whether to re-render by comparing object identity:

  • It compares the memory address: The setter compares the next value with the current one using Object.is.
  • It finds the same address: Because the object was modified in place, both variables point to the same location. Object.is(user, user) returns true.
  • It skips the render pass: When the memory address is unchanged, React assumes the state value did not change. It skips the render completely.

The screen stays stale until an unrelated event triggers a render. When a separate click updates an activity counter, React re-renders the component. That render reads the mutated object from memory and finally paints the new biography. This delayed update is a classic production bug.

To request a render, you must pass a newly created object to the setter. Never assign directly to the properties of a state object.

PRINCIPLE 1

Treat state objects as read-only and never mutate them in place

Object.is a JavaScript comparison method that checks whether two values share the exact same reference

Always treat every object stored in state as read-only. Never assign properties directly to a state object, because React requires a new object reference to trigger a render.

We should do this:
function handleUpdateBio() {
setUser({
...user,
bio: 'Architect'
Allocates fresh object reference
});
}
We should not do this:
function handleUpdateBio() {
user.bio = 'Architect';
Mutates existing object in memory
setUser(user);
Identical reference skips render
}
QUESTION 2

Creating New Objects with Object Spread

Starting with a user object that has both a role and details, you want to promote the team member. You call the setter with only the changed field:

App.jsx
1setUser({
2 role: 'Tech Lead'
Supplies only the updated role field
3});

The developer passes a fresh object containing only the new role to setUser. They assume React will merge this role into the existing user profile automatically.

Why does this update cause the component to crash with a TypeError, removing the user profile from the screen?

ANSWER

The code did not work as intended. React replaces the entire state object instead of merging it.

State setters in modern React do not perform automatic shallow merging:

  • It replaces the entire state object: The setter treats the object passed to it as the complete new state.
  • It drops all unmentioned properties: Passing only the role completely discards name, city, details, and all other fields.
  • It causes property lookups to crash: The next render attempts to read user.details.bio, finds undefined, and throws a runtime error.

To preserve existing fields, use object spread syntax (...user). The spread operator copies all existing properties into a brand new object. Always place the spread operator first so your changed property overrides the copied one.

PRINCIPLE 2

Copy existing properties with object spread before applying changes

Always copy existing object fields using spread syntax before writing updated properties. Place the spread operator first so your changed values override the copied properties.

We should do this:
setUser({
...user,
Clones existing fields into new object
role: 'Tech Lead'
Overrides role with updated value
});
We should not do this:
setUser({
role: 'Tech Lead'
Drops other keys and causes crash
});
QUESTION 3

Copying Every Level of Nested Objects

You want to update the nested bio inside user.details. Remembering to copy the user, you make a shallow copy and then mutate the nested details:

App.jsx
1const nextUser = { ...user };
Shallow copy clones only the outer object
2nextUser.details.bio = 'Lead';
Writes to shared details object
3setUser(nextUser);

The developer uses object spread to duplicate the outer user object, believing the entire structure is now safe. They then reassign the nested bio property directly and queue the update.

The screen updates to display the new bio. However, clicking Reset to restore initialUser still shows the new bio instead of the original text. Why did updating a copy corrupt the initial state?

ANSWER

The code did not work as intended. Object spread is shallow and does not duplicate nested objects.

Object spread copies property values only one level deep:

  • It copies primitive fields by value: Top-level fields like name and role get copied as independent values.
  • It copies nested objects by reference: The details property holds an object reference pointing to nested memory.
  • Both copies share nested memory: Both outer containers point to the exact same nested details object.

When you modify nextUser.details.bio, you mutate the shared nested object in memory. Because initialUser points to that same nested object, its data is corrupted. To update nested state, allocate a fresh object at every level along the path.

PRINCIPLE 3

Copy every nested object level along the path to the changed property

Deeply nested state requires copying every object along the path from the root to the target property. Never mutate a nested object on a shallow copy, as it alters historical snapshots and shared references.

We should do this:
setUser(prev => ({
...prev,
Clones outer object container
details: {
...prev.details,
Clones nested details object
bio: 'Lead Architect'
}
}));
We should not do this:
const next = { ...user };
Outer copy shares inner object
next.details.bio = 'Lead';
Mutates shared nested memory
setUser(next);
QUESTION 4

Updating Multiple Fields with Computed Property Names

Your user profile form contains a role input and a city input. You connect both inputs to a single change handler using computed property syntax:

App.jsx
1function handleChange(e) {
2 setUser({
3 ...user,
Retains existing state properties across inputs
4 [e.target.name]: e.target.value
Maps input name directly to state key
5 });
6}

This single handler captures change events from multiple inputs. It preserves existing fields with object spread while reading the input name attribute dynamically to assign the matching property.

Why does this single function successfully update both role and city inputs without requiring separate change handlers for each field?

ANSWER

The code worked properly. This is a proper use of computed property names to handle multiple inputs.

JavaScript allows object keys to be evaluated dynamically using square brackets:

  • It matches input names to state keys: Setting the input name to match the state key links them together.
  • It reads event targets dynamically: The expression reads the input name and uses it as the key.
  • It preserves unedited fields: Spreading user ensures fields not modified by this specific input remain in state.

This pattern eliminates boilerplate code. You can manage forms with many fields using a single handler, as long as input names match keys.

PRINCIPLE 4

Use computed property syntax to update multiple fields from a single event handler

Match input name attributes to state object keys to update multiple fields using one event handler. Use square brackets to compute the property key dynamically while spreading existing state.

We should do this:
function handleChange(e) {
setUser({
...user,
[e.target.name]: e.target.value
Evaluates input name dynamically
});
}

Glossary

  • Object Reference: The memory address where a JavaScript object lives, which React checks using Object.is to detect changes.
  • Mutation: Changing the properties of an existing object in place without creating a new object in memory.
  • Object Spread (...obj): A JavaScript syntax that copies all enumerable properties from an existing object into a new object literal.
  • Shallow Copy: A copy operation that duplicates top-level properties but copies references to nested objects rather than cloning them.
  • Nested Object: An object stored inside another object, requiring explicit copying at every level to prevent shared reference mutation.
  • Computed Property: A JavaScript syntax using square brackets [key] to set an object property dynamically from an evaluated expression.
  • Object.is: The JavaScript comparison algorithm used by React to verify whether a new state value differs from the previous one.
