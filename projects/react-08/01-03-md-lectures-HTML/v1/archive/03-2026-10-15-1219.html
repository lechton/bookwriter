Lecture 3: JSX Syntax and the Single-Root Rule

Interview Question

CORE

What is JSX, what syntax rules must every snippet follow, and how do Fragments group elements without wrapper nodes?

Imagine this scenario:

  1. You copy the markup of a news card from the old Town News site and paste it into a component.
  2. You save, and instead of the card, a dark box with red text covers the page.
  3. What changes when HTML moves into a component?

Most React work starts from HTML that already exists

Most React work does not start from an empty file. It starts from markup that already exists: a page of an old site, a design a teammate wrote in HTML, or an example copied from the web. The Town News site is moving to React, and its old pages are plain HTML files. In Lecture 2, every component we wrote was small and clean. Now the markup comes from somewhere else, and it was written for the browser, not for React. So every developer who moves a site to React asks the same thing: what changes when HTML moves into a component?

The answer is one idea, and this chapter follows it from the first question to the last: JSX looks like HTML, but it is JavaScript: each tag becomes a call that builds an object. Each rule of the chapter follows one block of pasted HTML on its way to the page: the tag, its end, the return, the group, its attributes.

This lesson answers five questions:

  • My component returns something that looks like HTML. Is it HTML?
  • My HTML has <img> with no closing tag. Why does the build stop?
  • I pasted a heading and a paragraph after return. Why does the build fail?
  • So I wrap everything in a <div>?
  • Can I keep class and for from my HTML?

The questions stand on what Lectures 1 and 2 established:

  • Lecture 1 (What is React): A component is a JavaScript function that returns JSX, markup that describes one piece of the page. React builds the DOM, the tree of nodes the browser draws, from that description, and the Elements panel shows those nodes. The dev server sends each saved change to the open page.
  • Lecture 2 (Component anatomy): We write a component's name as a component tag, such as <ArticleCard />, and React calls the function. That call is called rendering. A capital first letter tells React that the tag is ours, and long markup starts on the return line with return ( console.log prints a message in the Console panel, and our projects leave Strict Mode out, so each message appears once.

An object keeps values under names

A JavaScript object keeps several values together, each under a name. Each name with its value is a property. We write an object with curly braces, and we read a property with a dot:

Plain JavaScript: an object and its properties
1const story = {
2 title: 'Rail strike ends',
A property named title
3 section: 'City',
4};
5console.log(story.title);
Rail strike ends

The object holds two properties, title and section. story.title reads the first one, so the Console panel shows "Rail strike ends". A property name is a JavaScript name, so it follows the same rules as the name of a variable.

The dev server changes our files before the browser gets them

The browser does not read App.jsx as we wrote it. When the page asks for the file, the dev server reads it, rewrites it into plain JavaScript, and sends the result. This rewriting is called the build. The command npm run build does the same for every file at once, when the site is ready to publish.

The Sources panel of the browser's developer tools, next to the Elements panel and the Console panel, shows each file the browser received. Opening App.jsx there shows the result of the build, not our file.

When the build cannot read a file, nothing in that file runs. Vite then covers the page with a dark box, the error overlay. It shows the message, the file, and the line where the build stopped. The overlay goes away once we fix the file and save.

HTML lets some tags stay open

Some HTML tags can never hold anything inside them: <img>, <br>, and <input>. They are called void elements, and HTML lets us write them without a closing tag. HTML even lets us leave some other tags open, such as <li> and <p>, because the browser closes them when the next one starts.

CSS can style only the direct children of an element

A new Vite project has a stylesheet, index.css, and main.jsx loads it with one line, so its rules apply to the whole page. Ours styles a list of top stories:

index.css
1.stories {
2 display: flex;
The items sit in a row
3 gap: 24px;
4 padding: 0;
5 list-style: none;
6}
7.stories > li {
Only the direct children
8 border: 1px solid #999;
9 padding: 8px;
10}

display: flex turns the list into a flex layout: its children sit side by side in a row, with 24 pixels between them. The > in .stories > li makes it a child selector. It gives a border only to an <li> that sits directly inside the list, not to one that sits deeper.

Some words belong to JavaScript itself

JavaScript keeps some words for itself, such as return, function, class, and for. They are called reserved words. class starts a class definition, and for starts a loop, so neither can be the name of a variable.

HTML has two families of attributes whose names contain a dash. aria-* attributes, such as aria-label, describe an element to screen readers. data-* attributes, such as data-edition, store our own values on an element.

Principles of React: JSX Is JavaScript

Everything in this lesson comes down to one idea: JSX looks like HTML, but it is JavaScript.

First, the JSX transform, which means each tag becomes a JavaScript call that returns an object: the build rewrites every tag as a call, and React builds the page from the objects.

Second, closed tags, which means JavaScript must know where each tag ends: every tag needs a closing tag or a slash, the image and the line break too.

Third, a single root, which means a JavaScript function returns one value: a component gives back one element that holds the rest.

Fourth, Fragments, which means one JavaScript value that adds no element to the page: when the page needs no extra box, an empty tag groups the elements instead.

Fifth, camelCase attributes, which means each attribute becomes a JavaScript property name: class becomes className, and for becomes htmlFor.

The build rewrote each tag as a call. The tag's name became the first argument, and its attributes and its content became the properties of an object, the second argument. This rewrite is called the JSX transform. The dev server also added an import line at the top of the file, which loads _jsxDEV from React, and it added the file name and the line of each tag, for error messages. When we run npm run build, the calls use a shorter function, jsx, without those extras.

Each call returns a plain object, the one the Console panel showed. React calls it a React element. When React renders the component, it reads these objects and builds the DOM from them, so the browser never receives a tag at all.

PRINCIPLE 1

The JSX transform: each tag becomes a JavaScript call that returns an object

We read JSX as JavaScript: the build turns each tag into a call, the call returns an object that describes the element, and React builds the DOM from those objects.

The browser never reads JSX. The build rewrites each tag as a call of a function from React. The tag's name, its attributes, and its content go into the call, and the call returns a plain object, a React element. React reads these objects and builds the DOM. So JSX can go wherever a JavaScript value can go: after a return, or in a variable.

We should do this:
function Greeting() {
const note = <p className="note">Hello, John Hall</p>;
an object
return note;
}
QUESTION 2

An open img tag stops the build

The card should show a photo of the library. The old site's HTML has it, so a developer pastes it as it is:

App.jsx
1function ArticleCard() {
2 return (
Pasted from the old site
3 <article>
4 <img src="/library.jpg" alt="The city library">
5 <h2>City Library Extends Its Hours</h2>
6 </article>
7 );
8}

The developer saves, and the page stays empty. The error overlay covers it, with two messages. The first one points at two lines:

Vite error overlay: the first message, shortened
[PARSE_ERROR] Expected corresponding JSX closing tag for 'img'.
 4 │       <img src="/library.jpg" alt="The city library">
   │        ─┬─
   │         ╰─── Opened here
 6 │     </article>
   │       ───┬───
   │          ╰───── Expected `</img>`

The second message says "Unexpected token. Did you mean {'}'} or &rbrace;?", and it points at line 8, the closing brace of the function.

My HTML has <img> with no closing tag. Why does the build stop?

ANSWER

The code does not do what we wanted. The build stops at the <img>, so nothing in the file runs.

Each tag becomes a call, and the build must know where the call's content ends. After an open tag, it reads everything as the content of that tag until it finds the closing tag. HTML knows that <img> is a void element, but the build does not make that exception. So the <h2> became the content of the <img>, and at </article> the build was still waiting for </img>. That is what the two marks in the overlay say: the tag was opened here, and its end was expected there.

The second message comes from the same mistake. The build lost its place and reached the closing brace of the function as if it were text inside the markup. That line has no mistake of its own, so we fix the first message and the second one goes away.

The fix is a slash before the >. A tag that closes itself has no content, so the build knows at once where it ends:

App.jsx
1function ArticleCard() {
2 return (
Every tag closed
3 <article>
4 <img src="/library.jpg" alt="The city library" />
5 <h2>City Library Extends Its Hours</h2>
6 </article>
7 );
8}

Save, and the photo and the headline appear. <br> and <input> fail the same way, and so does an <li> or a <p> left open, as HTML allows. Any tag may close itself, such as <div className="spacer" />

PRINCIPLE 2

Closed tags: JavaScript must know where each tag ends

We close every tag, with a closing tag or with a slash, <img /> and <br /> too, because JavaScript must know where each tag ends.

The build reads everything after an open tag as its content, until it finds the closing tag. JSX makes no exception for void elements, so an open image swallows the tags below it, and the build stops at the next closing tag. Nothing in the file runs, and the overlay names the open tag. A slash closes a tag that holds nothing.

We should do this:
<section>
<img src="/john.jpg" alt="John Hall" />
closed with a slash
<p>John Hall<br />Boston</p>
</section>
We should not do this:
<section>
<img src="/john.jpg" alt="John Hall">
waits for </img>
<p>John Hall<br>Boston</p>
</section>

Another card on the old site has no <article> around it, only a heading and a paragraph. A developer pastes both after return:

I pasted a heading and a paragraph after return. Why does the build fail?

ANSWER

The code does not do what we wanted. The function tries to give back two values, and the build stops before anything runs.

Each tag becomes one call, and one call gives one value. A JavaScript function gives back one value with return, so the build cannot turn two calls side by side into one return. HTML allows any number of tags next to each other, but a function's return does not.

One element around both is one call. The two inner calls become its content, its children, exactly as the <h2> and the <p> did in the object of Question 1:

2 return (

3 <article>
4 <h2>City Library Extends Its Hours</h2>
5 <p>The library now stays open until nine.</p>
6 </article>
7 );
8}

Save, and the card appears. The help line in the overlay pointed at a second way to give one root, and Question 4 takes it up.

PRINCIPLE 3

Single root: a JavaScript function returns one value

We return one root from every component, one element that holds the rest, because a JavaScript function returns one value.

Each tag becomes one call, and each call gives one value. A function returns one value, so a component returns one tag, and that tag holds the others as its children. Two tags side by side are two values, and the build stops before anything runs. The root is usually an element the page needs anyway, such as an article or a section.

2 return (

App places the stories inside the styled list:

So I wrap everything in a <div>?

The code does not do what we wanted. The <div> gives one root, but it also lands on the page, between the list and its items.

A <div> is a real element, so React builds it in the DOM. The flex layout arranges the children of the list, and the list now has one child, the <div>. The two items sit inside the <div>, one below the other. The child selector .stories > li looks for an <li> directly inside the list, finds none, and gives no border.

3 <>
4 <li>Rail strike ends</li>
5 <li>New park opens today</li>
6 </>
7 );
8}

A Fragment is one call, like any tag, so the build accepts it as one root. Its type is React's Fragment, and React does not build an element for it. It puts the Fragment's children straight into the parent:

An element is still the right root when the page needs the box, as the <article> was in Question 3. A Fragment cannot take a key, which Lecture 11 explains when it renders lists.

PRINCIPLE 4

Fragments: one JavaScript value that adds no element to the page

When the elements need one root but the page needs no extra box, we group them with a Fragment, <> and </>, and we keep an element only when the page needs the box.

A wrapping element is a real node in the DOM, between the parent and the children. Inside a list, a table, or a flex row, it breaks the layout, because the styles look for direct children. A Fragment is one call, so it gives one root, but React builds no element for it and puts its children straight into the parent. An element stays right when the page needs it, for its meaning or for a style.

return (

no element in the DOM
<td>John</td>
<td>Hall</td>
</>
);
}
We should not do this:

return (
<div>
a div inside the table row
<td>John</td>
<td>Hall</td>
</div>
);
}
QUESTION 5

class and for work, and the console fills with errors

The old site has a newsletter form. A developer pastes it into SignUp, with the attributes it had in HTML:

App.jsx
1function SignUp() {
2 return (
Pasted with its HTML attributes
3 <form>
4 <label class="label" for="email">Your email</label>
5 <input id="email" type="email" tabindex="0" />
6 </form>
7 );
8}

The page looks right, and a click on the label puts the cursor in the box. But the Console panel shows three errors. The first one says: "Invalid DOM property class. Did you mean className?" The other two say the same for for, with htmlFor, and for tabindex, with tabIndex.

Can I keep class and for from my HTML?

ANSWER

The code does not do what we wanted. The page works, but each HTML name is the wrong name in JSX, and each one adds an error to the console.

The attributes of a tag become the properties of an object, as className did in Question 1. A property name is a JavaScript name, and class and for are reserved words in JavaScript. So React uses the names that the DOM itself gives these two properties, className and htmlFor. Other attribute names of several words use camelCase, so tabindex becomes tabIndex.

React 19 still sets the wrong names on the element. That is why the page looks right and the label still works. Only the console shows the mistake, and a console full of these errors hides the one error that matters.

The fix uses the JavaScript names. The aria-* and data-* attributes are the exception: they keep their dashes, as in HTML:

App.jsx
1function SignUp() {
2 return (
Aria-label and data-form-id keep their dashes
3 <form aria-label="Newsletter" data-form-id="7">
4 <label className="label" htmlFor="email">Your email</label>
5 <input id="email" type="email" tabIndex="0" />
6 </form>
7 );
8}

Save, and the Console panel is empty. The Elements panel still shows class="label" and for="email", because React writes the HTML names into the page. Lecture 83 lists the other renamed attributes, and attributes written on the tag of our own component become its props, which Lecture 6 teaches.

PRINCIPLE 5

camelCase attributes: each attribute becomes a JavaScript property name

We write each attribute as a JavaScript property name: className for class, htmlFor for for, camelCase for names of several words, and dashes only in aria-* and data-*.

The attributes of a tag become the properties of the object the call receives, so they follow the rules of JavaScript names. The words class and for are reserved in JavaScript, so React uses className and htmlFor, the names the DOM gives these properties. Names of several words use camelCase. React 19 still sets an HTML name on the element, so the page looks right, and only the console shows an error.

We should do this:
<form className="contact">
className, not class
<label htmlFor="name">Name</label>
<input id="name" placeholder="John Hall" data-user-id="7" />
</form>
We should not do this:
<form class="contact">
an error in the console
<label for="name">Name</label>
<input id="name" placeholder="John Hall" data-user-id="7" />
</form>

⚡ IN THE WILD

Old tutorials import React at the top of every file. Do I need that line? Not for JSX. Older tutorials start each component file with import React from 'react' because the old transform turned every tag into a call of React.createElement, and that call needs React in the file. React 19 requires the new JSX transform, which adds its own import of the JSX functions, as the Sources panel showed in Question 1. That is why our files never import React and still work. A file still imports by name the other things it uses from React, which Lecture 8 shows.

A developer who comes from HTML brings five habits: read the markup as HTML, leave void elements open, put tags side by side, wrap a group in a <div>, and keep the HTML attribute names. Each habit meets JavaScript in its own way. The markup is a list of calls, an open tag hides where a call ends, two tags side by side are two values, a <div> lands on the page and breaks a layout, and class fills the console with errors. In React 19, the five steps followed the build from one message to the next, and the old page now runs as two components with a clean console.

Where you will meet this

  1. A designer's HTML mockup: a design arrives as an HTML file, and every page of it goes through the same five checks as the Town News front page.
  2. A snippet copied from the web: examples from CSS libraries are written in HTML, full of class and open <input> tags. Each one needs className and a slash.
  3. A table row component: a component that returns several <td> cells for a row needs a Fragment, because a <div> inside a <tr> breaks the table.
  4. An old tutorial: a file that starts with import React from 'react' comes from the time before the new JSX transform.
  5. An icon pasted from a design tool: SVG markup brings attributes such as stroke-width, which JSX writes as strokeWidth.

For the interview

The Interview Question: What is JSX, what syntax rules must every snippet follow, and how do Fragments group elements without wrapper nodes?

1. The Hidden Signal

The interviewer wants to hear what JSX turns into. A candidate who says "JSX is HTML inside JavaScript" has described how it looks. A strong candidate says that the build turns each tag into a function call, that the call returns a plain object, and that React builds the DOM from those objects, so the browser never sees JSX. Every rule then follows from that one fact.

2. The Classic Trap

The classic trap is "JSX is just HTML with a few differences." On our page, an open <img> stopped the build, two tags side by side stopped it again, and class filled the console with errors. HTML accepts all three. JavaScript does not.

3. What is Actually Going On

Each tag becomes a call, so the build must know where its content ends, and every tag must be closed. Each call is one value, and a function returns one value, so a component returns one root.

A Fragment is a call with React's Fragment type. It gives one root, and React puts its children straight into the parent, so nothing extra lands in the DOM. The attributes become the properties of an object, so they take JavaScript names: className, htmlFor, and camelCase.

4. Where It Gets Tricky

Does a Fragment appear in the Elements panel?

No. React builds no element for it. Its children sit directly inside the parent, as the two stories did in the list.

Can I keep the HTML comments of my old page?

No. A comment written as in HTML stops the build with "HTML comments are not allowed in modules". A comment in JSX needs curly braces, which Lecture 4 teaches.

Does class break the page?

No. React 19 still sets it on the element, and the page looks right. The Console panel shows an error that asks for className.

Can a Fragment take a key?

The empty tag cannot. The long form, written with the name Fragment, can, and Lecture 11 shows it in a list.

Glossary

  • Object: A JavaScript value that keeps several values together, each under a name.
  • Property: One name and its value inside an object, such as title: 'Rail strike ends'.
  • Build: The rewriting of our files into plain JavaScript, done by the dev server for each file the page asks for, and by npm run build for the whole site.
  • Sources panel: The panel of the browser's developer tools that shows each file the browser received, after the build.
  • Error overlay: The dark box Vite puts over the page when the build cannot read a file. It shows the message, the file, and the line.
  • JSX transform: The step of the build that rewrites each JSX tag as a call of a function from React.
  • React element: The plain object a JSX call returns. It describes one element with a type and props.
  • Void element: An HTML element that can hold nothing, such as <img>, <br>, or <input>. HTML lets it stay open; JSX does not.
  • Fragment: An empty tag, <> and </>, that groups elements into one root and adds no element to the page.
  • Flex layout: A CSS layout, set with display: flex, that puts the children of an element in a row.
  • Child selector: A CSS selector with >, such as .stories > li, that matches only the direct children of an element.
  • Reserved word: A word JavaScript keeps for itself, such as class or for, which cannot be a variable name.
  • className and htmlFor: The JSX names of the HTML attributes class and for.

Summary

JSX looks like HTML, but it is JavaScript

❒ The JSX transform: each tag becomes a JavaScript call that returns an object

➔ ALWAYS read JSX as JavaScript: each tag is a call that returns an object, and React builds the DOM from the objects.

➔ NEVER expect the browser to receive the tags; open the Sources panel to see the calls it got.

❒ Closed tags: JavaScript must know where each tag ends

➔ ALWAYS close every tag, with a closing tag or a slash, such as <img />, <br />, and <input />.

➔ NEVER leave a void element open as HTML allows; the build stops, and nothing in the file runs.

❒ Single root: a JavaScript function returns one value

➔ ALWAYS return one root that holds the rest of the component's markup.

➔ NEVER return two tags side by side; they are two values, and the build stops.

❒ Fragments: one JavaScript value that adds no element to the page

➔ IF the elements need one root but the page needs no extra box THEN group them with <> and </>.

➔ IF the page needs the box, for its meaning or a style, THEN keep an element such as <section> as the root.

❒ camelCase attributes: each attribute becomes a JavaScript property name

➔ ALWAYS write className for class, htmlFor for for, and camelCase for names of several words.

➔ NEVER rename aria-* and data-* attributes; they keep their dashes.
