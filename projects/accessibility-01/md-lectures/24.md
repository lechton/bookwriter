### The Semantic Illusion: Roles Without Behaviors

ARIA attributes act as descriptive metadata for the browser's accessibility tree, modifying what assistive technologies announce to users. However, ARIA does not alter browser functionality, provide keyboard event listeners, or inject interactive mechanics into passive DOM elements. When a developer stamps a switch role onto a generic division, the screen reader announces a switch, but the browser provides zero keyboard or focus support.

```html title="div-switch-vs-button.html"
<div role="switch" aria-checked="true">Alerts</div> <!-- **WRONG:** div lacks keyboard focus and **LISTENERS** -->

<button role="switch" aria-checked="true">Alerts</button> <!-- **RIGHT:** native button provides keyboard **CONTRACT** -->
```

```canvas title="Settings Switch: Passive Div Role vs Native Button Contract" width="2/3" layout="compare"

switch | Breaking News | checked | right="keyboard operable" | focus=1 | note="✓ Operates with Space and Enter"
```

The comparison exposes the critical divide between semantic declaration and mechanical operation. On the left, decorating a generic division with an ARIA role instructs VoiceOver to announce an interactive toggle, yet pressing Spacebar or Enter achieves nothing because divisions do not possess native keyboard bindings. On the right, establishing the role on a native button provides inherent keyboard focusability, standard click propagation, and effortless keyboard triggering.

This disconnect directly violates the First Rule of ARIA. ARIA does not transform a passive division into an interactive control; it merely alters its label in the accessibility tree. Developers who rely on role declarations without implementing underlying keyboard contracts leave assistive technology users completely paralyzed.

### Dynamic States: Keeping DOM and ARIA in Sync

ARIA states represent dynamic conditions that change throughout an element's lifecycle, such as checked, expanded, and disabled states. Because browsers do not automatically synchronize ARIA states when JavaScript modifies internal component variables, developers must update these attributes explicitly upon every user interaction. An out-of-sync ARIA attribute lies to assistive technology operators, reporting false states that contradict visible reality.

```javascript title="toggle-state-sync.js"
button.classList.toggle('is-open'); // **WRONG:** updates visual class but ignores **ARIA**

const isOpen = button.classList.toggle('is-open'); // **RIGHT:** synchronizes aria-expanded with **DOM**
button.setAttribute('aria-expanded', String(isOpen));
```

```canvas title="Accordion Trigger: Desynchronized ARIA vs Synchronized State" width="2/3" layout="compare"
button | Section Topics | wrong="stale aria" | note="✕ Visually open, says collapsed"
button | Section Topics | right="aria synced" | focus=1 | note="✓ Announces expanded state"
```

The layout comparison demonstrates the danger of state desynchronization. On the left, clicking the disclosure trigger expands the section visually, but because the developer neglected to update the expanded state attribute, the screen reader continues to announce collapsed to blind users. On the right, binding the ARIA attribute directly to the reactive boolean state ensures that visual presentation and accessibility metadata remain in perpetual synchronization.

This failure violates WCAG 4.1.2 Name, Role, Value (Level A). Assistive devices rely entirely on accurate accessibility tree states to communicate interactive context to operators.

### The Triad: Roles, States, and Properties

The Accessible Rich Internet Applications specification organizes its taxonomy into three distinct functional categories:

1. **Roles:** Define what an element is and its intended function (such as button, tab, switch, or dialog). Roles are predominantly static and set once during initialization.
2. **States:** Define current operational conditions that change rapidly in response to user action (such as `aria-checked`, `aria-expanded`, `aria-selected`, or `aria-busy`).
3. **Properties:** Define structural characteristics or relationships that remain relatively stable throughout the component's life (such as `aria-labelledby`, `aria-describedby`, `aria-haspopup`, or `aria-required`).

The W3C WAI-ARIA specification establishes this division clearly:

> ARIA is designed to provide semantics to assistive technologies when standard HTML elements do not suffice. It does not provide behavior, styling, or keyboard operation. Developers must implement the expected keyboard interactions using JavaScript.
*W3C, WAI-ARIA 1.2 Specification, `resources/accessibility/aria/aria-1.2.html`*

### Production Svelte 5 Implementation of Alert Settings Switch

Here is the complete Svelte 5 component for the National Times notification switch, demonstrating clean reactive state synchronization and full keyboard operability:

```svelte title="AlertToggle.svelte"
<script>
  let { isEnabled = $bindable(false), label = "Breaking News Alerts" } = $props();

  function toggle() {
    isEnabled = !isEnabled;
  }

  function handleKeydown(event) {
    if (event.key === ' ' || event.key === 'Enter') {
      event.preventDefault();
      toggle();
    }
  }
</script>

<div class="setting-item">
  <span id="setting-label" class="setting-text">{label}</span>
  <button
    type="button"
    role="switch"
    aria-checked={isEnabled}
    aria-labelledby="setting-label"
    class="switch-control"
    onclick={toggle}
    onkeydown={handleKeydown}
  >
    <span class="switch-thumb" class:checked={isEnabled}></span>
  </button>
</div>

<style>
  .setting-item {
    display: flex;
    align-items: center;
    justify-content: space-between;
    padding: 12px 16px;
    background: #ffffff;
    border-bottom: 1px solid #e2e8f0;
  }
  .switch-control {
    position: relative;
    width: 48px;
    height: 28px;
    background: #cbd5e1;
    border: none;
    border-radius: 14px;
    cursor: pointer;
    padding: 2px;
  }
  .switch-control[aria-checked="true"] {
    background: #0284c7;
  }
  .switch-thumb {
    display: block;
    width: 24px;
    height: 24px;
    background: #ffffff;
    border-radius: 50%;
    transition: transform 0.2s ease;
  }
  .switch-thumb.checked {
    transform: translateX(20px);
  }
</style>
```

In this implementation, Zoe encounters zero friction. The native button handles keyboard focus naturally, Svelte 5 binds `aria-checked` reactively to `isEnabled`, and keyboard listeners allow effortless toggling via Spacebar or Enter.

> [!KEY]
> ARIA defines how an element sounds to assistive technology, not how it works. Always pair ARIA roles and states with native keyboard listeners and focus semantics.

### Glossary

- **ARIA Role**: A descriptor establishing what kind of widget an element represents in the accessibility tree.
- **ARIA State**: A dynamic attribute reflecting rapid operational changes, such as checked or expanded status.
- **ARIA Property**: A structural attribute defining relationships or permanent characteristics, such as descriptive labels.
- **First Rule of ARIA**: The fundamental mandate to use native semantic HTML elements before resorting to custom ARIA roles.
- **Accessibility Tree**: The hierarchical browser structure queried by screen readers to announce element names, roles, and values.
- **Keyboard Contract**: The expected set of keyboard keystrokes (such as Space, Enter, or Arrows) required to operate a specific widget pattern.

### Summary

**ARIA Roles, States, and Properties Architecture**

ARIA is descriptive metadata for the browser's accessibility tree, not a programming runtime that provides interactive behavior. Stamping an ARIA role on a generic division alters how screen readers describe the node, but leaves the element completely devoid of keyboard focus, event listeners, and native activation semantics. Furthermore, dynamic states must be strictly synchronized with visible application state to avoid misleading assistive device users. Professional developers rely on native HTML elements first, reserving ARIA for custom composite widgets backed by robust keyboard contracts. Here is your streetwise review.

❒ The Rules of ARIA Engineering

1. Never use ARIA as a substitute for native HTML elements.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) A native button provides focusability, click events, and keyboard support for free.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Adding a role to a generic division creates an inaccessible illusion.
2. Synchronize ARIA states reactively upon every user interaction.<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Attributes like `aria-expanded` must immediately reflect underlying DOM changes.<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Stale ARIA states misinform screen reader users and fail WCAG 4.1.2 at Level A.

❒ The Developer's Levers

1. Never assign interactive roles to passive container divisions.

**DO NOT DO THIS:** Fake a button using a division with an ARIA role.
```html wrong
<div role="button" onclick="save()">Save</div>
```
&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Use the native interactive HTML button element.
```html right
<button type="button" onclick="save()">Save</button>
```
2. Never update visual styling while leaving ARIA states frozen.

**DO NOT DO THIS:** Change visual classes without updating aria-expanded.
```javascript wrong
panel.classList.toggle('visible');
```
&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Update the ARIA state in lockstep with the visual change.
```javascript right
button.setAttribute('aria-expanded', String(isOpen));
```

➔ NEVER assume an ARIA role confers keyboard operability or focus.

➔ ALWAYS build on native HTML interactive elements whenever a semantic tag exists.

➔ IF creating a custom ARIA widget THEN implement its complete WAI-ARIA keyboard contract.
