# Lecture 28: The Accessible Tab Interface
> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How do you implement an accessible tab interface with correct focus management?

1. Sarah opens the National Times election dashboard to review municipal candidate voting records.
2. The dossier features fifteen topic tabs covering transit, housing, energy, and school budgets.
3. She presses the Tab key to skip past the tabs and examine candidate spending in the active panel.
4. Why must Sarah press Tab fifteen consecutive times just to read the first sentence of the panel?
5. Each keystroke lumbers across another inactive tab title while the main story remains stranded below.
6. Treating tab headers as independent tab stops forces exhaustive keyboard traversal and traps motor-impaired readers.
7. Today we wire the roving tab index, bind arrow key navigation, and turn the entire tablist into a single tab stop.

### The Sequential Traversal Trap: Fifteen Tab Stops Versus One Roving Entry

Sarah navigates the candidate dossier using a physical keyboard to audit public budget votes. When developers build tabbed interfaces using standard interactive buttons without roving tab index management, every individual tab registers as an independent stop in the document sequence. Sighted and motor-impaired keyboard operators must tab through every single tab header before their focus ring finally reaches the active panel content below. Implementing a roving tabindex confines the entire tab bar to a single sequential tab stop while arrow keys handle lateral movement:

```html title="tablist-focus.html"
<button class="tab">Transit</button> <!-- **WRONG:** Standalone buttons create 15 tab stops -->

<button tabindex="-1" class="tab">Housing</button> <!-- **RIGHT:** Inactive tabs removed from tab stream -->
```

```canvas title="Election Dossier Tabs: Multiple Tab Stops vs Roving Tabindex" width="2/3" layout="compare"
tab | Transit; Housing; Energy | wrong="tab stops on every tab" | note="✕ 15 tab presses to reach panel"
tab | Transit; Housing; Energy | right="roving tabindex active" | note="✓ 1 tab press jumps to panel"
```

The contrast illustrates the fundamental difference between standard document flow and composite widget navigation. On the left, each tab button possesses a default `tabindex="0"`, forcing the browser's sequential focus algorithm to visit every single header. If an editorial dashboard contains fifteen categories, the reader is subjected to fourteen redundant keystrokes before reaching the panel. On the right, only the currently active tab maintains `tabindex="0"`, while all inactive sister tabs are assigned `tabindex="-1"`. When Sarah presses the Tab key from the preceding paragraph, focus lands immediately on the active tab; pressing Tab a second time exits the tab bar entirely and moves directly into the interactive controls of the visible panel.

### The ARIA Tab Contract: Roles, Selection States, and Panel Associations

Constructing accessible tabs requires explicit semantic bindings between each tab control and its corresponding content container. Without declaring the tablist, tab, and tabpanel roles, screen reader users hear only unassociated buttons without any clue that activating one updates the viewport below. Pairing `aria-selected` with `aria-controls` establishes a bidirectional link that announces tab position and exposes panel relationships:

```html title="tab-semantics.html"
<div class="tabs"><button>Energy</button></div> <!-- **WRONG:** Raw buttons lack tab semantics -->

<div role="tablist" aria-label="Topics">
  <button role="tab" aria-selected="true"
          id="t-1" aria-controls="p-1">Energy</button>
</div> <!-- **RIGHT:** Full ARIA contract binds panel -->
```

```canvas title="Tab Semantics: Unbound Buttons vs Complete ARIA Contract" width="2/3" layout="compare"
tab | Economy; Transit | wrong="unbound raw buttons" | sr="Transit, button" | note="✕ No tab role or selection state"
tab | Economy; Transit | right="tablist and selection" | sr="Transit, tab, selected, 2 of 4" | note="✓ Exposes role, index, and panel binding"
```

Screen readers rely on the parent container's `role="tablist"` to calculate the total set size and communicate navigational context. When Sarah's screen reader moves focus to the accessible tab on the right, it speaks: "Transit, tab, selected, 2 of 4". The user immediately understands the widget type, current selection status, and relative position within the group. Furthermore, linking the tab to its container via `aria-controls="p-1"` allows assistive technology users to jump directly from the header into the referenced panel via platform-specific shortcut commands.

The W3C ARIA Authoring Practices Guide establishes the definitive focus management model for tab interfaces:

> When focus moves into the tab list, places focus on the active tab element. When the tab list contains the focus, moves focus to the next element in the page tab sequence outside the tablist, which is the tabpanel unless the first element containing meaningful content inside the tabpanel is focusable.
*W3C WAI, Tabs Pattern, resources/accessibility/aria-practices/content/patterns/tabs/tabs-pattern.html*

> [!KEY]
> The entire tablist must occupy exactly one tab stop in the sequential navigation order, delegating lateral movement between tabs to the Arrow keys.

> [!TIP]
> **To impress the interviewer:** contrast automatic activation with manual activation. In automatic activation, pressing the Left or Right Arrow immediately activates the tab and displays its panel; in manual activation, arrow keys move focus across tabs without changing panels until the user explicitly presses Space or Enter. Emphasize that manual activation is strictly mandatory when rendering panel content requires expensive network queries or layout reflows, preventing sluggish keystrokes.

### Glossary

- **Roving Tabindex**: A focus management technique where the active widget item holds `tabindex="0"` while all sibling items hold `tabindex="-1"`.
- **Tablist Role**: The composite container role that groups a set of related tab elements and announces overall set size to screen readers.
- **Tabpanel Role**: The structural container role that holds the content associated with an individual tab element.
- **aria-selected**: The state attribute indicating whether a tab is currently activated and displaying its associated panel.
- **aria-controls**: The property identifying the specific DOM element whose contents are managed by the current tab control.

### Summary

**Roving Focus Architecture and Semantic Tab Controls**

In production application engineering, tabs are composite widgets, not loose collections of independent buttons. Forcing keyboard users to tab through every header creates an exhausting navigation barrier that violates basic usability principles. Restrict the tablist to a single sequential tab stop, implement roving tabindex with arrow key listeners, and announce selection state with complete ARIA attributes. Here is your streetwise review.

❒ The Architectural Principles of Accessible Tabs

1. Roving Focus Model
<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Only the selected tab maintains `tabindex="0"` in the DOM stream.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Inactive tabs carry `tabindex="-1"` so the Tab key skips directly to the panel.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(c) Left and Right Arrow keys update focused tabs circularly.

2. Semantic ARIA Attributes
<br>&nbsp;&nbsp;&nbsp;&nbsp;(a) Wrap tab buttons inside a container declaring `role="tablist"`.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(b) Set `role="tab"` and `aria-selected="true"` on the active header.
<br>&nbsp;&nbsp;&nbsp;&nbsp;(c) Point `aria-controls` to the matching container declaring `role="tabpanel"`.

**DO NOT DO THIS:** Render plain buttons without roving focus, forcing users to tab through every header.
```html wrong
<div class="tabs">
  <button class="active">Transit</button>
  <button>Housing</button>
</div>
```
&nbsp;&nbsp;&nbsp;&nbsp;**DO THIS:** Manage roving tabindex and declare full tablist semantics.
```html right
<div role="tablist" aria-label="Election Topics">
  <button role="tab" aria-selected="true" tabindex="0">Transit</button>
  <button role="tab" aria-selected="false" tabindex="-1">Housing</button>
</div>
```

➔ NEVER allow inactive tabs to maintain `tabindex="0"` in the page tab order.

➔ ALWAYS bind `role="tablist"`, `role="tab"`, and `role="tabpanel"` together.

➔ IF panel rendering requires network data THEN use manual activation requiring Space or Enter.
