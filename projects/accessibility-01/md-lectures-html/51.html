The Microtask Drain: Why Chained Promises Starve the Screen

The browser event loop balances JavaScript execution against rendering updates. A macrotask runs, followed immediately by draining the entire microtask queue until empty. If asynchronous handlers continually chain promises, the microtask queue never exhausts, completely blocking the rendering phase:

The difference between queues dictates where work belongs. The engine picks exactly one task from the macrotask queue (such as a timer or input event). Next, it immediately executes every pending microtask queued via Promise.prototype.then(), queueMicrotask(), or MutationObserver. If a microtask schedules another microtask, that new microtask runs in the current drain cycle before any rendering begins. Only after the microtask queue reaches zero does the browser evaluate requestAnimationFrame callbacks, compute CSS styles, calculate layout geometry, and paint pixels to the screen.

MDN Web Docs explains the mechanics of tasks and microtasks in the browser execution model:

The difference between the task queue and the microtask queue is simple but very important: When a new iteration of the event loop begins, the runtime executes the next task from the task queue. Further tasks and tasks added to the queue after the start of the iteration will not run until the next iteration. Whenever a task exits and the execution context stack is empty, all microtasks in the microtask queue are executed in turn. The difference is that execution of microtasks continues until the queue is empty (even if new ones are scheduled in the interim).

Key Takeaway

Microtasks always drain to total exhaustion before the browser can render or process user input; recursive promises create a synchronous freeze disguised as asynchronous code.

Interview Tip

To impress the interviewer: explain why modern frameworks use microtasks for batching. Frameworks like Vue and React batch multiple state mutations within the same tick using queueMicrotask() or resolved promises so the DOM updates only once before the next paint. Contrast this with setTimeout(fn, 0): timer callbacks run in future macrotask turns and cannot prevent intermediate renders.

Where you will meet this

  • Real-time financial dashboards: streaming thousands of WebSocket updates per second without freezing the UI.
  • UI state batching: collapsing multiple consecutive property changes into a single consolidated DOM write.
  • Recursive promise processing: walking large JSON trees or paginated APIs without locking up user input.

Glossary

  • Event Loop: The browser mechanism coordinating JavaScript execution, microtask queues, user inputs, and rendering.
  • Macrotask: An independent unit of work scheduled via timers, I/O, network callbacks, or user input events.
  • Microtask: A short asynchronous callback executed immediately after the current script exits, before any paint.
  • Microtask Starvation: A condition where continuously enqueued microtasks prevent the event loop from ever rendering.
  • requestAnimationFrame: A browser API that schedules a callback immediately before the next display repaint.

The Browser Event Loop: Tasks, Microtasks, and Starvation

The event loop prioritizes microtask queue exhaustion over frame rendering and user interactions.

❒ Scheduling Hierarchy

  1. Queue Ordering Rules
        (a) Task Execution: the engine runs at most one macrotask per event loop turn.
        (b) Microtask Drain: all microtasks are executed to zero before any paint or subsequent task.
  2. Frame Protection
        (a) Yield to Paint: avoid recursive promise chains that starve the compositor.
        (b) Synchronized Updates: use requestAnimationFrame for visual changes and timers for heavy chunking.

DO NOT DO THIS: Chain recursive promises that continuously refill the microtask queue without yielding.

app.js
1function pollData() {
2 fetchChunk().then(chunk => {
3 applyChunk(chunk);
4 Promise.resolve().then(pollData);
5 });
6}

    DO THIS: Yield to the macrotask queue or native scheduler between data processing chunks.

app.js
1function pollData() {
2 fetchChunk().then(async chunk => {
3 applyChunk(chunk);
4 await scheduler.yield();
5 pollData();
6 });
7}

➔ NEVER create unbounded or recursive microtask chains with Promise.resolve().then() or queueMicrotask().

➔ ALWAYS reserve microtasks for lightweight state batching that must complete before the immediate paint.

➔ IF work involves visual DOM layout and animation THEN coordinate execution with requestAnimationFrame().
