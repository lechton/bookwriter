Lecture 40: HTTP Caching: Headers, Revalidation, and Cache Busting

Interview Question

CORE

How do HTTP caching headers work, and what is cache busting?

Imagine this scenario:

  1. Elena deploys a critical hotfix to resolve a broken subscription checkout script.
  2. Returning readers continue reporting checkout crashes because their browsers execute yesterday's cached JavaScript file.
  3. Why does the browser execute stale, broken scripts when updated code exists on the origin server?
  4. Readers cannot complete purchases, and support queues flood with duplicate billing complaints.
  5. The server shipped the asset with a long expiration header using an unversioned file path.
  6. HTTP caching must pair immutable cache lifetimes with content-hashed file URLs to guarantee instant updates.

The Stale Script Trap: Why Unversioned Assets Break Releases

Browsers maintain an HTTP disk and memory cache to prevent redundant network round trips on repeat visits. When an asset response includes a Cache-Control header with a high max-age directive, the browser assumes the file contents will remain valid for that duration. If the server serves a file at an unvarying URL like /js/checkout.js, the browser never contacts the origin server to verify whether newer code exists. Deploying an urgent bug fix to the same URL leaves existing users stranded on broken client logic:

The contrast illustrates why static asset caching requires content-based cache busting. On the left, giving an unversioned asset a one-year cache lifetime instructs the browser to bypass the network completely. Even if Elena restarts origin servers and purges upstream reverse proxies, returning subscribers load the buggy file directly from their local disk. On the right, modern bundlers append a cryptographic hash of the file contents to the filename, yielding /js/checkout.8f3a.js. Because any code modification alters the hash and produces a brand-new URL, the browser treats the asset as an entirely new resource, pulling the hotfix instantly while allowing untouched bundles to remain cached indefinitely.

The Gateway Document: Why HTML Must Never Be Cached Long-Term

Content-hashed static assets depend entirely on the document that references them. If the HTML page itself is cached by the browser, the browser will continue reading the older HTML markup, which still points to the superseded asset URLs. Therefore, HTML documents must always be configured with revalidation directives such as Cache-Control: no-cache. This directive does not prevent caching; instead, it mandates that the browser must validate freshness with the origin server before using the cached response:

1Cache-Control: max-age=86400
WRONG: Caches HTML for 24 hours, locking obsolete script URLs
2
3Cache-Control: no-cache
RIGHT: Mandates ETag revalidation on every single page load

The difference between no-cache and no-store is one of the most widely misunderstood distinctions in web engineering. The directive no-store completely forbids any device or intermediary from saving the response to disk or memory, which is essential for sensitive banking or authentication endpoints. Conversely, no-cache allows the browser to store the HTML response locally, but requires an HTTP conditional request using If-None-Match and an ETag token. If the HTML has not changed, the origin server returns a lightweight 304 Not Modified status with an empty body, consuming zero layout overhead while ensuring new script hashes are discovered the instant they deploy.

Chrome Developers outline the foundational mechanic of client-side HTTP caching in the official audit documentation:

When a browser requests a resource, the server providing the resource can tell the browser how long it should temporarily store or cache the resource. For any subsequent request for that resource, the browser uses its local copy rather than getting it from the network.

Key Takeaway

Pair immutable one-year cache headers on content-hashed static assets with no-cache conditional revalidation on root HTML documents.

Interview Tip

To impress the interviewer: explain the immutable directive introduced in RFC 8246. When a user manually presses the browser reload button, standard browser behavior sends conditional revalidation requests for subresources even if their max-age has not expired. Appending immutable to Cache-Control informs modern browsers that the content will never change across its lifetime, suppressing conditional network requests completely during user reloads.

Where you will meet this

  • Continuous deployment pipelines: pushing code multiple times daily without invalidating untouched vendor libraries.
  • Single-page application shells: ensuring updated route bundles are downloaded immediately while assets stay cached.
  • Content delivery networks: configuring edge TTLs to offload origin servers while respecting client validation tokens.

Glossary

  • Cache-Control: An HTTP header used to specify browser and intermediary caching policies across request-response cycles.
  • Cache Busting: The engineering practice of appending unique content hashes or query tokens to asset URLs to force cache invalidation.
  • no-cache: A caching directive specifying that cached copies must be revalidated with the origin server before every reuse.
  • no-store: A caching directive strictly prohibiting browsers and proxy intermediaries from persisting responses to disk or memory.
  • ETag: An HTTP response header providing a cryptographic validator fingerprint used to determine if a cached entity matches origin state.

Summary

HTTP Caching Headers and Cache Busting

Effective caching pairs long-term static persistence with strict root revalidation.

❒ Caching Directives

  1. Static Asset Strategy
        (a) Hashed Bundles: set max-age=31536000 and immutable on content-hashed file names.
        (b) Content Invalidation: any source code edit changes the filename, bypassing old cache.
  2. Root Document Strategy
        (a) HTML Revalidation: set no-cache to force ETag verification on each page request.
        (b) Sensitive Data: set no-store on authenticated account and billing payloads.
