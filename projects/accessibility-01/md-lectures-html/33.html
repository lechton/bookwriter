Lecture 33: Manual Accessibility Testing

Interview Question

ADVANCED

How do you manually test a page for accessibility using only a keyboard and a screen reader?

Imagine this scenario:

  1. Marcus prepares the National Times investigative store for the annual subscription drive.
  2. The continuous integration pipeline reports zero axe-core violations across the checkout funnel.
  3. Marcus unplugs his mouse and attempts to complete a purchase using only his keyboard.
  4. Why does the active focus ring vanish into an unlabelled payment frame halfway through checkout?
  5. The automated scanner confirmed the iframe existed, but never checked if keystrokes could leave it.
  6. Relying solely on synthetic crawlers blinds teams to devastating keyboard traps and broken user flows.
  7. Today we unplug the mouse, master screen reader rotor commands, and execute rigorous manual testing protocols.

The Unplugged Mouse: Verifying Focus Trails and Keyboard Traps

Marcus begins manual validation by disconnecting his mouse and relying exclusively on physical keystrokes. Sighted keyboard navigators follow a visual focus trail to identify active controls and verify sequential progress through the DOM. When third-party checkout frames or custom payment widgets capture focus without providing an escape key handler, keyboard users become permanently trapped. Conducting manual keyboard passes exposes focus containment flaws that automated DOM linters completely overlook:

The Speech Audit: Testing Rotor Navigation and Acoustic Landmarks

Manual testing requires evaluating how assistive software interprets content through auditory output. Non-sighted users navigate web pages using specialized screen reader shortcut menus, such as the VoiceOver Rotor or the NVDA Elements List. When developers organize content using visual typography without semantic landmark tags or heading levels, screen reader navigation menus display blank screens. Auditing pages with a screen reader ensures structural elements appear cleanly in rotor dialogs:

Key Takeaway

Manual testing begins by unplugging the mouse; if a workflow cannot be completed using Tab, Arrows, and Enter, the feature is broken.

Interview Tip

To impress the interviewer: describe the four-step manual testing protocol: (1) keyboard-only traversal verifying focus visibility and trap dismissal with Escape, (2) screen reader rotor audits verifying heading and landmark hierarchies, (3) 400% zoom reflow checks ensuring zero two-dimensional scrolling at 320 CSS pixels, and (4) high-contrast theme validation ensuring focus rings remain distinct on dark surfaces.

Where you will meet this

  • Subscription checkout funnels: verifying that payment modals, billing fields, and receipt links operate cleanly by keyboard.
  • Multimedia news packages: testing that audio scrubbers, transcripts, and video captions respond to screen reader commands.
  • Account authentication drawers: ensuring password toggles, biometric prompts, and two-factor code fields do not trap focus.
  • Interactive survey forms: testing dynamic multi-step disclosures and validation errors with speech synthesizers.

Glossary

  • Manual Accessibility Testing: The systematic evaluation of a user interface using physical keyboards, screen readers, and zoom controls.
  • Keyboard Trap: A defect where focus enters an interactive component but cannot be moved to another element using the keyboard.
  • Screen Reader Rotor: A dialog menu in VoiceOver and assistive tools listing page landmarks, headings, links, and form controls.
  • Linear Tab Order: The sequential flow of keyboard focus through interactive elements in matching visual reading order.
  • Rotor Menu Audit: A manual testing technique verifying that all page sections are indexed properly in assistive shortcut lists.

Summary

Manual Verification Protocols and Assistive Tool Auditing

Automated testing tools cannot experience an application the way a human does. Unplugging the mouse and launching a screen reader immediately exposes keyboard traps, missing landmarks, and broken conversion funnels. Establish strict manual evaluation routines across every core user path, audit heading rosters, and guarantee universal operability. Here is your streetwise review.

❒ The Core Manual Testing Protocol

  1. Keyboard Operability Checks
        (a) Navigate forward with Tab and backward with Shift+Tab.
        (b) Verify that every interactive control displays an assertive focus ring.
        (c) Ensure modals dismiss and restore focus upon pressing Escape.
  2. Screen Reader Acoustic Checks
        (a) Open the rotor menu (Caps Lock + U or VO + U) to audit headings and landmarks.
        (b) Verify form inputs announce explicit accessible names and invalid states.
        (c) Ensure dynamic status updates are announced without stealing active focus.

DO NOT DO THIS: Rely on mouse clicks during development and ship unverified keyboard traps.

    DO THIS: Build native interactive controls and verify them with physical keystrokes.

➔ NEVER consider a user conversion funnel complete without an unplugged-mouse walkthrough.

➔ ALWAYS test modal dialogs and dropdown menus for Escape key dismissal and focus return.

➔ IF a component appears in visual reading order THEN verify it appears in the screen reader rotor.
