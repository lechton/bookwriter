The Broken Promise: Redundant Tab Role Versus Clean Semantic Button

Tariq added Accessible Rich Internet Applications attributes to the National Times category filter bar, assigning role="tab" to each button to satisfy an audit suggestion. But when screen reader users navigated the archive, the controls announced as tabs while arrow keys produced dead silence because Tariq had not implemented composite keyboard widget scripts. ARIA modifies auditory announcements without granting native keyboard behaviors, making incomplete ARIA worse than plain HTML:

Dynamic State: Visual CSS Class Versus Accessible State Attribute

The First Rule of ARIA does not mean ARIA should never be used; it means ARIA should be used only when native HTML cannot express the required semantic state. In frontend applications, interactive components frequently transition between binary states, such as live investigative filters toggling on and off, or accordion disclosure panels expanding and collapsing. Visual designers typically communicate these active states by adding a CSS class that changes background colors or border highlights.

However, visual class names like .active or .selected are completely invisible to screen readers and assistive devices. When a blind subscriber toggles a live transit alert filter, the browser must explicitly announce whether the filter is currently active or inactive:

The Five Rules of ARIA

The W3C Web Accessibility Initiative codifies five non-negotiable rules governing all ARIA implementations across the web:

  1. Rule 1: Use Native Elements First. If you can use a native HTML element or attribute with the semantics and behavior you require already built in, instead of re-purposing an element and adding an ARIA role, state, or property to make it accessible, then do so.
  2. Rule 2: Do Not Change Native Semantics. Do not override the built-in semantics of native HTML tags unless genuinely necessary. Never assign role="heading" to a button or role="button" to a link.
  3. Rule 3: All Interactive ARIA Controls Must Be Keyboard Operable. If you create a custom widget using ARIA roles (such as a tablist, combobox, or slider), you must manually implement the full keyboard navigation specification outlined in the ARIA Authoring Practices Guide.
  4. Rule 4: Do Not Hide Focusable Elements. Never place role="presentation" or aria-hidden="true" on an element that can receive keyboard focus. Doing so creates ghost focus stops where keyboard users become trapped on invisible elements.
  5. Rule 5: All Interactive Elements Must Have an Accessible Name. Every interactive control must expose a programmatic accessible name via visible text, aria-label, or aria-labelledby so assistive technologies can announce its identity.

The official MDN documentation summarizes the first rule in one succinct directive:

If you can use a native HTML element or attribute with the semantics and behavior you require already built in, instead of re-purposing an element and adding an ARIA role, state or property to make it accessible, then do so.

MDN Web Docs, ARIA: Accessible Rich Internet Applications, resources/web-performance/mdn/files/en-us/web/accessibility/aria/index.md

The W3C Authoring Practices Guide explains why breaking these rules causes widespread disruption:

Functionally, ARIA roles, states, and properties are analogous to a CSS for assistive technologies. For screen reader users, ARIA controls the rendering of their non-visual experience. Incorrect ARIA misrepresents visual experiences, with potentially devastating effects on their corresponding non-visual experiences.

W3C, ARIA Authoring Practices Guide (APG), resources/accessibility/aria-practices/content/practices/read-me-first/read-me-first-practice.html

Key Takeaway

ARIA adjusts the accessibility tree for assistive software, but it never modifies DOM behavior, styling, or keyboard operation; a role is a promise that your JavaScript must manually fulfill.

Where you will meet this

  • Article category filters: using clean buttons with aria-current rather than breaking keyboard navigation with incomplete tablist roles.
  • Dark mode toggle switches: using native buttons with aria-pressed to communicate toggle states to screen readers.
  • Collapsible navigation accordions: employing aria-expanded on button triggers to announce whether drawer menus are open or closed.
  • Form validation error messages: linking error text containers to invalid inputs using aria-describedby.
  • Breaking news ticker banners: declaring aria-live="polite" to notify assistive tech users of real-time journalistic dispatches.

Glossary

  • ARIA (Accessible Rich Internet Applications): A technical specification from the W3C defining HTML attributes to enhance accessibility markup for assistive technologies.
  • First Rule of ARIA: The fundamental design principle stating that developers should always prefer built-in semantic HTML elements over custom ARIA roles whenever possible.
  • aria-current: An ARIA attribute indicating that an element represents the current item within a container or set of related elements (such as the active page).
  • aria-pressed: An ARIA state attribute indicating the current press state (true, false, or mixed) of a toggle button.
  • aria-expanded: An ARIA state attribute indicating whether a collapsible widget or its associated grouping element is currently open or closed.
  • Accessibility Tree: The parallel object model created by browser engines that translates HTML elements, CSS styles, and ARIA attributes into platform accessibility APIs.

Summary

ARIA as a Surgical Accessibility Layer

ARIA is a powerful specification designed to bridge gaps in native HTML, not a decorative paintbrush to sprinkle across stylesheets. Adding ARIA roles creates contractual promises with assistive software; failing to support those promises with JavaScript keyboard logic breaks user interfaces. Use native semantic HTML for structure and controls, and reserve ARIA for dynamic states and live announcements. Here is your streetwise review.

❒ The Rules of ARIA Engagement

  1. Native HTML elements always take precedence over custom ARIA.
        (a) A native button requires zero custom JavaScript to support keyboard navigation and screen reader roles.
        (b) Adding role="tab" requires implementing arrow key roving tabindex logic from scratch.
  2. ARIA communicates state, not visual design.
        (a) CSS active classes are invisible to screen readers; use aria-pressed or aria-expanded for state.
        (b) Never place aria-hidden="true" on focusable elements.

❒ The Developer's Levers

  1. Never assign redundant ARIA roles to native semantic elements.

DO NOT DO THIS: Add redundant or misleading roles to native buttons.

index.html
1<button role="tab" class="active">Politics</button>

DO THIS: Use native elements and express active state with aria-current.

index.html
1<button type="button" aria-current="page">Politics</button>
  1. Never rely on CSS styling alone to convey dynamic toggle state.

DO NOT DO THIS: Change background colors without exposing state to assistive tech.

index.html
1<button type="button" class="btn is-active">Live Feed</button>

DO THIS: Use aria-pressed to announce toggle state to screen readers.

index.html
1<button type="button" aria-pressed="true">Live Feed</button>

➔ NEVER use ARIA when a native HTML element can accomplish the same task.

➔ ALWAYS implement full keyboard navigation whenever assigning custom ARIA widget roles.

➔ IF an interactive component changes state dynamically THEN declare that state with ARIA attributes.
