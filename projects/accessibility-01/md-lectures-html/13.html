Lecture 13: The Chorus of Click Heres

Interview Question

CORE

What distinguishes a good link from a bad one, and when should you use a button instead?

Imagine this scenario:

  1. Maya opens the National Times opinion package on metropolitan rail transit reform.
  2. She opens her screen reader's Links List dialog to jump straight to the cited economic studies.
  3. Maya's headphones fill with an incomprehensible list: "Click here, Click here, Read more, Download, Click here".
  4. Which link opens the high-speed rail study and which link downloads the municipal tax audit?
  5. Maya cannot distinguish a single destination without closing the dialog and reading through three thousand words of text.
  6. She attempts to open the feedback drawer on a link tag, and the spacebar scrolls the page downward instead.
  7. Today you learn to banish ambiguous anchor text, master descriptive context, and enforce the platform divide between links and buttons.

Non-Visual Link Navigation: Ambiguous Action Words Versus Explicit Destination

Maya navigates the National Times transit reform package by opening her screen reader's links dialog. When journalists attach hyperlinks to vague action words like "click here" or "read more", speech synthesizers strip surrounding sentence context and read an identical list of useless phrases. Authoring explicit link text that names the specific destination allows non-visual readers to browse efficiently out of context:

The contrast demonstrates how assistive technology users experience the web outside the traditional visual reading flow. In desktop screen readers like JAWS and NVDA, pressing Insert plus F7 pulls every hyperlink into an alphabetized Links List dialog. In Apple VoiceOver, users open the Rotor and navigate to the Links pane. Inside these menus, links are presented completely isolated from surrounding paragraph prose. A list containing five instances of "click here" forces blind users to close the menu and hunt through the Document Object Model line by line.

What Makes Link Text Accessible?

Under Web Content Accessibility Guidelines 2.2 Success Criterion 2.4.4 (Link Purpose In Context, Level A), the purpose of each link must be determinable from the link text alone, or from the link text together with its programmatically determined context:

The intent of this success criterion is to help users understand the purpose of each link so they can decide whether they want to follow the link. Whenever possible, provide link text that identifies the purpose of the link without needing additional context. Assistive technology has the ability to provide users with a list of links that are on the web page. Link text that is as meaningful as possible will aid users who want to choose from this list of links.

W3C, Understanding WCAG 2.2: Link Purpose (In Context), resources/accessibility/wcag/understanding/20/link-purpose-in-context.html

To satisfy this criterion, senior engineers adhere to three rules:

  1. Front-load keywords: Place the most informative noun near the start of the anchor string (e.g. "Transit subsidy audit" rather than "More details on the transit subsidy audit").
  2. Indicate non-HTML payloads: If a link points to a binary document like a PDF or spreadsheet, append the file format and approximate file size (e.g. "2026 Transit Feasibility Study (PDF, 3.2 MB)").
  3. Warn of new browsing contexts: When a link specifies target="_blank", provide an audible warning or text badge so non-visual readers know a new tab will spawn.

Control Semantics: Navigation Links Versus Action Buttons

Frontend engineers frequently confuse hyperlinks and buttons when constructing interactive components like flyout drawers, tabs, and filter dialogs. Anchors and buttons serve completely different architectural roles across the web platform:

This difference is grounded in platform keyboard behavior:

  1. Keyboard Activation: Native buttons fire click handlers when the user presses either the Enter key or the Spacebar. Native links fire click handlers strictly when the user presses Enter. When a user presses Space on a link tag, the browser engine executes the default page scrolling mechanism, scrolling the user away from their interactive context.
  2. Routing versus State: Links navigate the user to a new location, change the URL address, and push a new entry onto the browser history stack. Buttons trigger client-side scripts, submit forms, toggle dialogs, and mutate interface state without changing URLs.
  3. Accessible Role Announcement: Screen readers announce anchors as "link" and buttons as "button". Announcing an in-page modal trigger as a link misleads assistive technology users into expecting a page transition.

Interview Tip

To impress the interviewer: define the link versus button divide through platform behavior: links change location, update the URL, and activate on Enter; buttons trigger actions, mutate state, and activate on both Enter and Space. Cite WCAG Success Criterion 2.4.4 (Link Purpose In Context) and Criterion 2.4.9 (Link Purpose Link Only). Emphasize that ambiguous phrases like "click here" destroy usability in screen reader Links Lists (Insert+F7 in NVDA), and explain that putting href="#" on an anchor breaks keyboard scrolling contracts.

Where you will meet this

  • Investigative journalism dossiers: linking to downloadable evidence filings with explicit document labels and file size indicators.
  • E-commerce product listings: avoiding repetitive "View details" links by including the product name directly inside the anchor text.
  • Masthead navigation bars: ensuring every category link communicates its destination clearly without relying on parent layout cards.
  • Interactive slide-out panels: replacing imitation <a href="#"> triggers with native <button type="button"> elements.
  • Documentation search results: formatting API references with distinct titles rather than generic "Read more" buttons.

Glossary

  • Link Purpose (In Context): WCAG Success Criterion 2.4.4 requiring that the destination of every hyperlink be determinable from its anchor text or immediate sentence context.
  • Links List Rotor: A screen reader utility (such as Insert+F7 in JAWS/NVDA) extracting all page hyperlinks into an alphabetized menu for rapid keyboard traversal.
  • Anchor Element (<a>): A semantic HTML element designed specifically for hyperlinking and document navigation between Uniform Resource Identifiers.
  • Button Element (<button>): A semantic HTML element designed for triggering in-page scripted behaviors, dialog disclosures, and form submissions.
  • Target Context Warning: An audible or textual notice informing assistive software users that activating a link will spawn a new browser tab.
  • Spacebar Scroll Conflict: The platform interaction bug where pressing Space on an anchor tag scrolls the browser viewport instead of triggering the attached JavaScript click listener.

Summary

Purposeful Links and Semantic Action Controls

In modern frontend architecture, hyperlinks and action buttons are not interchangeable styling targets; they represent the two foundational interaction verbs of the web platform. Links navigate across documents and must declare their destinations with clarity so non-visual readers can evaluate them out of context. Buttons trigger programmatic changes and must support native keyboard contracts. Conflating these roles breaks muscle memory and navigation efficiency for millions of assistive technology users. Here is your streetwise review.

❒ The Two Interaction Verbs

  1. Links navigate across resources.
        (a) Use an anchor element when changing the URL, navigating across pages, or pointing to file payloads.
        (b) Ensure link text identifies the destination without needing surrounding paragraph prose.
  2. Buttons trigger in-page state changes.
        (a) Use a button element when toggling modals, expanding menus, filtering feeds, or submitting forms.
        (b) Guarantee keyboard execution on both Enter and Spacebar keystrokes.

❒ The Developer's Levers

  1. Never author ambiguous hyperlink text.

DO NOT DO THIS: Rely on lazy phrases that become unintelligible inside screen reader links menus.

index.html
1<p>To view the transit audit, <a href="/audit.pdf">click here</a>.</p>

    DO THIS: Embed the descriptive destination directly inside the anchor element.

index.html
1<p>Inspect the <a href="/audit.pdf">2026 Transit Audit Report (PDF)</a>.</p>
  1. Never substitute an anchor tag for an interactive button action.

DO NOT DO THIS: Attach JavaScript click handlers to dummy anchor tags that break spacebar contracts.

index.html
1<a href="#" onclick="openModal()">Open Filter Dialog</a>

    DO THIS: Use a native button element that dispatches on both Space and Enter.

index.html
1<button type="button" onclick="openModal()">Open Filter Dialog</button>

➔ NEVER include the phrases "link to" or "click here" in your anchor text.

➔ ALWAYS append file type and size indicators when linking directly to non-HTML payloads like PDFs.

➔ IF an element triggers an in-page script without changing the URL THEN write a button instead of a link.
