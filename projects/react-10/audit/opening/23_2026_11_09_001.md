## 2. Form of Move 1 Used

The opening uses the **plain-words** form of Move 1 (`### Changing the file yourself vs. calling the owner back` and `### What is at stake`). ## 4. Plan for the New Opening

The owner wrote the approved Lecture 23 opening in `skills/v10.6/opening-essence/SKILL.md` Example 9 (recorded in `brief/brief_2026_11_08_04.md`). The new opening should use the owner's approved checkout cart screen and retain the `tree` figure and core facts that later sections rely on:

- **Real screen and user action (Points 1 and 2):** Open under `## How a Child Asks Its Parent for a Change` and `### The Remove button in the row vs. the total at the top of the cart` on a **checkout cart on Amazon**, where every item sits in its own row with a **Remove** button. The user clicks **Remove** on a pair of headphones, and three things happen on the screen at once:
  1. The **headphones row** vanishes.
  2. The **subtotal** at the bottom drops by $200 (or two hundred dollars).
  3. The **cart badge** at the top ticks down from `3` to `2`.
- **The question and immediate answer (Point 3):** State the puzzle that screen raises: the Remove button sits inside one small row component that does not know the subtotal or the cart badge even exists. Ask: *"How does a click inside a tiny child component update distant parts of the page?"* Answer at once: *"It doesn't. A row never reaches across the screen to edit the total."*
- **The React pieces on that screen and the `tree` figure (Point 4):** Name the React pieces on that checkout cart screen:
  1. The **parent Cart** component owns the single list of products in its **state**, and the rows, the subtotal, and the badge are all calculated from that one list.
  2. Only the parent can change its own state, so the parent hands each row a **function** as a **prop**, named `onRemove`.
  3. Keep the contrast between the two kinds of props written on a child's tag and the `tree` Box-to-Boxes figure (`Two kinds of props on a child's tag: one carries a value to show, the other carries a function to call`): a prop that holds a value (such as `name="John"` or the item's title and price) carries something for the child to show as it travels down from the parent, while a prop that holds a function (such as `onRemove={handleRemove}`) carries something for the child to call when the user acts so the parent's own code changes the state.
- **Everyday image to unlock one word (Point 5):** After the cart screen and its React pieces are in place, use the owner's one-sentence **walkie-talkie** image to unlock the word **callback**: handing the function prop down is like handing the child a walkie-talkie (*"You cannot edit the list yourself. Call me when the user clicks Remove, and tell me your ID."*). When the user clicks the button, the row calls `onRemove` with its `id`, the parent removes that item from its state and triggers a fresh render, and the rows, subtotal, and badge all update together from the same updated list. A function passed down like this is called a **callback** because the child calls the parent back.
- **The broken case on that screen and where readers go wrong (Point 6):** On that same Amazon checkout cart screen (in `### What is at stake` or directly after the callback explanation), show what happens without this pattern: if a row tries to call the parent's setter directly, the Remove button fails; and if a row simply hides itself on click, the headphones row vanishes from the list while the top cart badge still reads `3` and the checkout total still charges `$200`, so the page gives two different answers to the same question. Keep the two places where readers usually go wrong from lines 30 to 32: picturing the child reaching up into the parent to change the parent's list directly, or thinking that data now flows both ways (only a function call goes up; the new list still comes down as props).
- **Bridge sentence to the example page (Point 7):** Close the opening with the owner's bridge sentence into the lesson's example page: *"In this lesson, we will build this exact pattern on a smaller scale: a party guest list. Each guest row gets its own Remove button, while the '3 guests' counter sits up in the parent header."*

## 5. What Must Stay and Later References to Watch

### Facts, Code Names, and Figures in the Start Section That Must Stay

- **Title and interview question (lines 1 to 2):** `# Lecture 23: How a Child Tells Its Parent to Change State` and `> INTERVIEW QUESTION | ❱ CORE | How does a child component notify its parent or trigger state updates using callback props?`
- **The `tree` figure in the opening (lines 20 to 24):** `Two kinds of props on <GuestRow>` (or on a child row tag) comparing `+A prop that holds a value [name="John"]` and `+A prop that holds a function [onRemove={handleRemove}]`.
- **The core rule and misconceptions in the opening (lines 12 to 32):**
  - The definition of a **callback** (a function that one piece of code hands to another piece of code so the other piece can call it back later when something happens).
  - The key idea: the parent owns the state and the only code that changes it; the child never changes that state itself and only calls the function it was given.
  - The two places where readers go wrong: thinking the child reaches up into the parent to change the list directly, or thinking data flows both ways once a child can trigger a change in the parent's state (only a function call goes up; the new list still comes down as props).
- **The four ways section (`### Four ways to let a child change its parent's state`, lines 34 to 40):**
  1. Pass a handler the parent wrote (`onRemove={handleRemove}`) and let the child call it with a value.
