The opening lines read:
> *"When you open the team page of a work app and click a name, the page shows that person's bio under the buttons. The bio is not written in the code of the page. It lives on a server, and the page has to ask the server for it every time the user clicks a name..."*

### Problem 2: Misses the Core Architectural Collision
The text fails to state the physical reason why data fetching in React is tricky:
**React rendering is synchronous and instantaneous; the network wire is asynchronous and high-latency.**

When a component renders, it must return JSX on the current frame. It cannot "pause" to wait for a database across the continent. This synchronous/asynchronous collision creates all three dilemmas of data fetching:
- If you fetch in the component body, it refetches on every render and causes infinite loops.
- If you fetch in an event handler, initial page loads have no data because no click occurred.
- When you fetch in an Effect, you must manage blank screens, silent HTTP errors, and out-of-order response arrivals.

## 3. Principle-by-Principle Pedagogical Audit

### Principle 1: Keep State Synchronized With Remote Data in an Effect
- **Current Defect:** Explains `fetch` mechanics as a generic JavaScript lesson rather than focusing on component synchronization.
- **Pedagogical Cure:** Explain why fetching belongs in an Effect. The Effect does not exist because a button was clicked; it exists because `Bio` is currently mounted on screen and its display must synchronize with the remote resource.
- **Key Visual Contract:** Establish the 3-state state machine:
  - `data === null && error === null` $\rightarrow$ **Loading State**
  - `error !== null` $\rightarrow$ **Error State**
  - `data !== null` $\rightarrow$ **Content State**

### Principle 2: Interrogate response.ok Because fetch Never Rejects on Server Crashes
- **Current Defect:** Mentions that `fetch` only rejects on network errors, but does not sharply contrast developer intuition against browser reality.
- **Pedagogical Cure:** Highlight the "HTTP Deception":
  - *What developers expect:* An HTTP 500 or 404 triggers `.catch()`.
  - *Physical reality:* `fetch` resolves on 500! It hands back a response object where `response.ok` is `false`. Without checking `response.ok`, the response body parses as non-bio JSON, `data.bio` evaluates to `undefined`, and `bio ?? 'Loading...'` traps the UI on `Loading...` forever.
- **Required Missing Angle:** A dedicated tree diagram comparing network transport failure (DNS drops, offline) against application status codes (200 vs 500).

### Principle 3: Stale Payloads: The ignore Flag Drops Out-of-Order Answers
- **Current Defect:** Describes race conditions textually without showing the exact time-slice collision.
- **Pedagogical Cure:** Introduce the time-slice race diagram:
  - Click 1 (Bob, slow): dispatched at 0.0s, completes at 2.0s.
  - Click 2 (Taylor, fast): dispatched at 0.5s, completes at 0.7s.
  - At 0.7s, Taylor renders. At 2.0s, Bob finishes late and clobbers Taylor.
- **The Mechanism:** Walk through closures. Each Effect execution has its own local `let ignore = false`. The cleanup of the previous run flips that run's flag to `true`. When Bob's promise finally settles, its closure checks `if (!ignore)`, sees `true`, and discards the stale payload.

### Principle 4: Socket-Level Cancellation: AbortController Stops Wasted Bandwidth
- **Current Defect:** Frames `AbortController` as merely a variation of the `ignore` flag without clarifying why a team would choose one over the other.
- **Pedagogical Cure:** Contrast software-level discards against hardware/socket-level cancellation:
  - *Ignore Flag:* The request downloads completely across cellular networks, wasting battery and data, but JavaScript ignores it.
  - *AbortController:* The browser closes the TCP socket immediately.
- **The Critical Trap:** Aborting an in-flight fetch causes the promise to reject with a `DOMException` named `AbortError`. If `.catch()` does not filter `err.name === 'AbortError'`, every normal navigation or Strict Mode remount renders a false crash banner.

## 5. Blueprint for the New Opening Section

```markdown
## The Collision Between Synchronous Rendering and the Asynchronous Wire

### React renders in milliseconds; the network answers in seconds

React rendering is instant and synchronous. When a component mounts or receives new props, React executes its function and expects JSX immediately. It cannot wait for a server across the country to respond.

The data your component needs lives on a remote server. That physical distance creates the three problems this lesson solves:
1. **The Blank Screen**: React renders before the server answers, so the component must provide an immediate fallback such as `Loading...`.
2. **The HTTP Deception**: When a server crashes with an HTTP 500 error, `fetch` treats the exchange as a successful resolution, leaving the screen hanging unless code explicitly checks `response.ok`.
3. **The Network Race**: The network has no memory of user intent. A slow request from an earlier click can finish after a fast request from a later click, silently overwriting fresh data with stale content.

### What is at stake: the ghost overwrite

What is at stake is displaying the wrong data with zero errors in the console.

Picture our team directory. The user clicks Bob, whose server lookup is slow and takes two seconds. Realizing their mistake, the user immediately clicks Taylor, whose lookup takes 200 milliseconds. Taylor's bio arrives first and renders. But a moment later, Bob's late response arrives, executes its setter, and overwrites the screen.

The page now displays Taylor's name with Bob's bio underneath. The console stays quiet. On a high-speed fiber connection at the office, the developer never reproduces it. On a customer's phone over cellular data, it happens constantly.
```
