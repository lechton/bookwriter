# Q125: Server Errors: Fatal Shell Crashes vs Recoverable Content Errors
* **Topic Tag**: #server_errors | ❱ CORE (Server)
* **Interview Question**: *How do errors surface during server rendering, and what is a recoverable error?*
* **Core Truth**: Server rendering distinguishes between fatal shell errors (which crash the HTTP response before sending headers) and recoverable content errors inside Suspense boundaries (which fall back to client rendering without breaking the page).
* **The Friction**: A third-party financial stock ticker widget throws an unhandled exception during server rendering at The National Times; on an unpartitioned page, the entire homepage returns a 500 Internal Server Error, taking down breaking news coverage over an optional peripheral widget.
* **The Mechanism**: Shell errors vs Recoverable errors: Errors in the root shell trigger onShellError, allowing the server to send an alternative 500 page; errors inside a <Suspense> boundary trigger onError, but React emits a client fallback and allows client-side recovery via hydrateRoot or client error boundaries.
* **Under the Hood**: Error recovery in streaming SSR: when an async component throws during streaming, React marks the boundary as failed, streams instructions to show the fallback, and instructs the client runtime to retry rendering that component on the client; if the server logs it via onError, it is classified as a "recoverable error".
* **The Code Experiment**:
  * *Naive*: Allowing an optional sidebar widget to throw at the root level during server rendering, crashing the entire HTTP response with a 500 error.
  * *React*: Wrapping the unreliable widget in <Suspense> and an Error Boundary, allowing the server to stream the news shell cleanly while logging the recoverable error.
* **Scope Boundary**: Focus on server error taxonomy (shell errors vs recoverable content errors), streaming error callbacks (onShellError, onError), and client fallback handoff.
