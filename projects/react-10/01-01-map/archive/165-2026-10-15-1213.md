# Q165: Server-to-Client Context: The Sanctioned Provider Bridge Pattern
* **Topic Tag**: #context_server | ❱❱ MORE (Server)
* **Interview Question**: *How do you pass server-fetched values into client providers?*
* **Core Truth**: Server Components provide initial data to client-side Context by fetching data securely on the server and passing it as props to a Client Component Provider wrapper that initializes React Context for downstream client consumers.
* **The Friction**: The editorial team at The National Times needs reader subscription entitlements available across 15 interactive client widgets; an engineer attempts to fetch the user profile inside the client provider via useEffect, resulting in a flash of unauthenticated UI (FOUC) and an unwanted loading spinner.
* **The Mechanism**: The Provider Bridge pattern: // Server: const user = await getSession(); return <UserProvider initialUser={user}>{children}</UserProvider>; — where UserProvider is a 'use client' component that seeds createContext with initialUser.
* **Under the Hood**: Hydration seed without client fetch: the server component renders the client provider with server-fetched props; during SSR/hydration, the provider initializes its context synchronously from props, allowing all client consumers to read valid user data on initial render without a second fetch.
* **The Code Experiment**:
  * *Naive*: Initializing Context with null and fetching user permissions inside a client useEffect, causing client widgets to flash unauthorized states on page load.
  * *React*: Fetching user permissions in the root Server Component and passing them to <AuthProvider initialPermissions={perms}>{children}</AuthProvider>, eliminating client fetch waterfalls.
* **Scope Boundary**: Focus on the sanctioned pattern for bridging server-fetched data into client Context Providers. Concludes the Server MORE tier.
