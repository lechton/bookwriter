# Q15: Trigger, Render, and Commit
* **Topic Tag**: `#render_and_commit` | `❱ CORE`
* **Interview Question**: *What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?*
* **Core Truth**: Every screen update in React happens in three steps: a trigger (the initial `root.render()` call or a state setter) requests a render; rendering is React calling our component functions to compute the JSX that should be on screen; and the commit is React changing only the DOM nodes that differ from the previous render. After the commit, the browser paints.
* **The Friction**: A developer calls `setLikes(likes + 1)` and on the next line reads `document.querySelector('.like-count').textContent` for an analytics event; it still holds the old number, because the DOM changes only in the commit, after the handler has finished. Another developer avoids re-rendering a form for fear it rebuilds the page, not knowing that a re-render leaves alone every DOM node whose output did not change, including the text a reader is typing into an `<input>`.
* **The Mechanism**: Trigger: the initial render through `createRoot(document.getElementById('root')).render(<App />)`, or a state update through a setter, which queues a render. Render: on the initial render React calls the root component; on a re-render it calls the component whose state changed, then every component that one returns, recursively; this step is a pure calculation and changes no DOM. Commit: on the initial render React inserts the DOM nodes it created with `appendChild()`; on a re-render it applies only the changes it calculated while rendering.
* **Under the Hood**: Rendering in React and rendering in the browser are different steps: React's render runs our JavaScript and produces JSX, while the browser's paint computes layout and draws pixels. Because rendering must be pure, React can call a component without touching the screen (StrictMode calls it twice in development, Q46), and because the commit compares the new output with the previous one, a component that renders again with the same result causes no DOM change at all.
* **The Code Experiment**:
  * *Naive*: Assuming `setCount(5)` immediately changes `document.getElementById('count').textContent` on the next line of code.
  * *React*: Tracing a `LikeCounter` button through Trigger (click invokes `setLikes`), Render (`LikeCounter()` executes and returns JSX), and Commit (React updates only the specific text node in the DOM).
* **Scope Boundary**: Focus strictly on the three steps (Trigger, Render, Commit), what runs in each, and the difference between React rendering and browser painting. Do not cover state as a snapshot (Q16), queueing several updates (Q17), or concurrent priority lanes and the Fiber work loop (Q66, Q78).
