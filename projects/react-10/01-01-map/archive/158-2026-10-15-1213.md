# Q158: The Hydration Cost Model: Shrinking the Client Component Graph
* **Topic Tag**: #hydration | ❱❱ MORE (Server)
* **Interview Question**: *What is the hydration cost model, and how do you shrink it?*
* **Core Truth**: Hydration is expensive because React must instantiate Fiber nodes and traverse the DOM tree for every Client Component; minimizing the number and depth of Client Components directly reduces JavaScript parse time, main-thread blocking, and memory usage.
* **The Friction**: On low-end mobile devices, The National Times homepage stutters and freezes reader scrolling for 1.2 seconds after HTML paints; an audit reveals that 350 presentational article cards are marked with 'use client' just to toggle an active CSS hover state, forcing massive hydration overhead.
* **The Mechanism**: Shrinking the graph: (1) Push 'use client' down to the leaves; (2) Replace client state with CSS (:hover, :focus-within) where possible; (3) Pass server components as children to keep intermediate containers server-only.
* **Under the Hood**: Fiber allocation cost: during hydration, React must allocate Fiber nodes for every client component and match them 1:1 against existing DOM elements; Server Components emit zero client Fiber nodes, completely bypassing this allocation and traversal tax.
* **The Code Experiment**:
  * *Naive*: Marking a top-level ArticleFeed with 'use client', forcing hundreds of DOM nodes and cards to be traversed and allocated as client Fiber nodes.
  * *React*: Keeping ArticleFeed and ArticleCard as Server Components, and extracting only the interactive <LikeButton /> as a client leaf component.
* **Scope Boundary**: Focus on the performance cost model of hydration (CPU, memory, main-thread blocking) and techniques to reduce the client component surface area.
