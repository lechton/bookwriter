# Q159: Resuming vs Hydrating: Byte Shipping and Execution Comparisons
* **Topic Tag**: #resume | ❱❱ MORE (Server)
* **Interview Question**: *Resuming versus hydrating: what ships, and what runs?*
* **Core Truth**: Hydration ships component code to the browser and re-executes render functions to reconstruct the virtual DOM and bind event listeners; Resumption ships serialized component state in the HTML and skips re-execution entirely, activating listeners on demand.
* **The Friction**: Readers on limited mobile data plans complain that loading an investigative report at The National Times downloads 800KB of JavaScript just to make two interactive charts clickable; the frontend architect must explain to leadership the fundamental difference between traditional hydration and emerging resumption paradigms.
* **The Mechanism**: Shipping and execution comparison: (1) Hydration: ships full component source code, runs render functions on client, builds Fiber tree, attaches listeners; (2) Resumption: ships serialized execution closures and event listeners in HTML, skips initial render pass, lazily downloads only the code for clicked handlers.
* **Under the Hood**: Closure serialization vs re-execution: Hydration treats server HTML as a passive artifact that must be verified by re-running JavaScript; Resumption treats server HTML as an active serialized program where listeners are mapped to fine-grained lazy chunks invoked directly on user events.
* **The Code Experiment**:
  * *Naive*: Assuming that because server-rendered HTML is visible, client JavaScript does not need to re-run the component functions under standard React hydration.
  * *React*: Understanding that React's hydration requires executing client components to attach listeners, and contrasting this with how resumption architectures eliminate that re-execution.
* **Scope Boundary**: Focus on the deep conceptual and mechanical contrast between hydration and resumption. Do not duplicate API usage from Q120/Q142.
