# Q05: Splitting Components with ES Module Imports and Exports
* **Topic Tag**: `#imports` | `❱ CORE`
* **Interview Question**: *How do you split components across files, and how do default and named imports differ?*
* **Core Truth**: React components are modular JavaScript functions organized via standard ES Module `export` and `import` statements; default exports allow flexible naming for primary components, while named exports enforce strict contractual naming for multi-utility files.
* **The Friction**: A team keeps seven components in a monolithic 1,200-line `App.jsx`. Merging features causes massive git conflicts, code reuse across pages is impossible, and developers accidentally mix up default and named import brackets, causing `Element type is invalid: expected a string or a class/function but got: undefined`.
* **The Mechanism**: Splitting components into dedicated `.jsx` files. Using `export default` for the primary component, `export function` for secondary sub-components or utilities, and matching the import syntax accordingly.
* **Under the Hood**: How JavaScript ES Module bindings resolve at build time: `import Card from './Card'` resolves the `default` export key, while `import { Card } from './Card'` resolves the named property `Card` on the export module namespace object.
* **The Code Experiment**:
  * *Naive*: 1,000-line monolithic file, followed by an import syntax mismatch error (`import ArticleCard from ...` when only named exports exist).
  * *React*: Clean file structure with `src/components/ArticleCard.jsx` exporting the default card and named badge helpers, cleanly consumed by `App.jsx`.
* **Scope Boundary**: Focus strictly on ES module syntax, file organization, default vs named exports, and debugging undefined import errors. Do not introduce dynamic `lazy()` or bundle splitting.
