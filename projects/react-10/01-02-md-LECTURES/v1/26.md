## How We Build a Page in React, One Step at a Time

### Where to start when a designer hands us a mockup

A designer hands us a drawing of a new page for a cafe website. It has a heading, a search box, a tick box that says `Only show drinks in stock`, and a list of drinks with their prices. This drawing of the finished page is called a **mockup**. Nothing on it is code yet. So where do we start?

There are two ways to start:
- **Starting from what the user does:** we open `App.jsx`, add a `useState` for the search text, write a handler for the search box, and grow the page around them, one piece at a time, as each piece comes to mind.
- **The React way:** we follow five steps in a fixed order. React's documentation calls them *Thinking in React*:
   1. We draw boxes on the mockup and turn each box into a component. The docs call the result a **component hierarchy**.
   2. We build the page from the data with props only, so it shows everything and reacts to nothing. The docs call this a **static version**.
   3. We find the few values that change and that nothing else can work out. The docs call them the **minimal state**.
   4. We decide which component keeps each of those values.
   5. We let the boxes the user types in change those values. The docs call this **inverse data flow**.

The five steps bring no new tool. **Yes, it is the exact same toolbox you already know!** Each step uses something an earlier lesson taught: components and the UI tree in Step 1, props in Step 2, the three questions for what is state in Step 3, the closest common parent in Step 4, and a function passed down as a prop in Step 5. Thinking in React is the order in which we use them.

Why does the order matter? Think of building a house. The plan comes first, then the walls. Then we decide which lamps must switch on and off, then where each switch goes, and only then do we run the wires from each switch. Nobody runs wires before the walls stand. React's docs give the same reason in their own words: "Building a static version requires a lot of typing and no thinking, but adding interactivity requires a lot of thinking and not a lot of typing." The order keeps the long typing and the hard thinking apart.

```tree dir=right caption="The five steps of Thinking in React, in the order React's docs give them."
The five steps from a mockup to a working page
- +1. Component hierarchy | Draw boxes on the mockup and **name each box** | No code yet
- +2. Static version | Show the data with **props only** | The page looks finished, but **nothing reacts**
- +3. Minimal state | Keep as state only what **changes and cannot be computed** | No code yet
- +4. Where state lives | Put each state in the **closest common parent** | The boxes show the state, but **refuse input**
- +5. Inverse data flow | Pass the setters down and **call them from `onChange`** | The page **fully works**
```

Lesson 21 also gave five steps from React's docs, for designing the visual states of one form. Those five steps design one component. These five steps build a whole page out of many components.

### What is at stake

The key idea is this: build everything that does not change first, then add the few values that do change, in the component that owns them, and only then let the boxes the user types in change those values.

What is at stake is what the user sees when the steps get mixed up. A developer who starts from `useState` calls and handlers at random often stores the same value twice, once in each component that needs it, and the two copies stop agreeing. On the page, the user ticks `Only show drinks in stock` and a sold-out drink stays on the list. Or the user types in the search box and the list does not move.

Readers usually go wrong in four places. They start from `useState` and handlers. They store the filtered list as state. They put the search text inside the search box component, where the list cannot read it. And they expect `value={filterText}` to update `filterText` by itself. The principles below meet each of these places, one step at a time.

### Five Principles of Thinking in React

**PRINCIPLES:** Each principle is one of the five steps, in order, and after each one we look at what the page shows:
1. **Principle 1: Boxes on the Mockup Become Four Components**: Before any code, we draw a box around every part of the mockup and name each box. A box inside a box becomes a child inside a parent.
2. **Principle 2: The Static Menu Ignores the Typed Search**: We build the whole page from the data with props only. The page looks finished, but the list does not follow what the user types.
3. **Principle 3: Only the Search Text and the Tick Box Become State**: Of the four values the page uses, only two change over time and cannot be computed from anything else. Only those two become state.
4. **Principle 4: State in MenuPage Freezes the Search Box**: We put both pieces of state in the closest common parent of the search box and the list. The page now shows the state, but the boxes refuse the user's input.
5. **Principle 5: onFilterTextChange Lets the Search Box Change MenuPage's State**: Only the owner of the state can call its setter. So the owner passes the setters down, and the boxes call them from `onChange`.

Here is the complete map of the five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Component Hierarchy: Boxes on the Mockup** | A page written as one big component grows with every new part, and none of its parts can be used again on another page. | Draw a box around every part of the mockup, give each box a component name, and nest the names the way the boxes nest. One component does one thing. |
| **Principle 2** | **Static Version: Props Only, No State** | Adding state while the components are still being typed puts the search text where the list cannot read it, and the state has to move later. | Build the whole page from the data with props only. The data enters at the top component and flows down to the rows. |
| **Principle 3** | **Minimal State: Keep Only What Cannot Be Computed** | Storing the filtered list as a second state lets it disagree with the search text and the tick, so a sold-out drink stays on the list. | Keep as state only what changes over time, does not come from a parent, and cannot be computed from other state or props. |
| **Principle 4** | **Where State Lives: The Closest Common Parent** | State kept inside the search box component cannot reach its sibling, the list. A box with `value` but no `onChange` refuses every letter. | Put each piece of state in the closest common parent of every component that renders from it, and pass it down as props. |
| **Principle 5** | **Inverse Data Flow: Pass the Setters Down** | Interviewers ask why typing in a box with `value={filterText}` does not change `filterText`, and how React differs from two-way data binding. | The owner passes its setters down as props, and the boxes deep in the tree call them from `onChange` with the new value. |

## 1. Principle 1: Boxes on the Mockup Become Four Components

### Drawing a box around every part of the mockup

Step 1 writes no code. We print the mockup and take a pen. React's docs say: "Start by drawing boxes around every component and subcomponent in the mockup and naming them."

On our menu, we draw four boxes:
1. A big box around the search part and the list together. We name it `MenuPage`.
2. A box around the search box and the tick box. We name it `SearchBar`.
3. A box around the whole list of drinks. We name it `DrinkList`.
4. A box around one row of the list. We name it `DrinkRow`. The list has five rows, but every row looks the same, so they are five copies of one component.

Then we write the names the way the boxes sit inside each other. A box that sits inside another box goes under it:

```tree caption="The four boxes drawn on the mockup, written as a component hierarchy."
`MenuPage` [the big box] | The search part and the list together
- +`SearchBar` [box inside `MenuPage`] | The search box and the tick box
- +`DrinkList` [box inside `MenuPage`] | The whole list of drinks
  - +`DrinkRow` [box inside `DrinkList`] | One drink, used once for each of the five drinks
```

React's docs call this nested list of names a **component hierarchy**. It is not a new kind of structure. **Yes, it is the exact same thing as the UI tree from Lesson 06!** A box inside another box on the mockup is a child inside a parent in the tree. The docs say it this way: "Components that appear within another component in the mockup should appear as a child in the hierarchy." So `SearchBar` and `DrinkList` are children of `MenuPage` and siblings of each other, and `DrinkRow` is a child of `DrinkList`.

### Where one box ends: one component does one thing

Why does one row get its own box, instead of staying inside the list? React's docs answer with a computer science idea called **separation of concerns**: "a component should ideally only be concerned with one thing. If it ends up growing, it should be decomposed into smaller subcomponents." The search part lets the user type and tick. The list shows the drinks. One row shows one drink. Each of them does one thing, so each gets its own box.

The docs give three habits you can start from when you split a design:
- **Programming:** split it where you would write a new function in plain JavaScript.
- **CSS:** split it where you would write a new CSS class. The docs add that a component is usually a bigger piece than one class.
- **Design:** split it the way the designer grouped the layers in the design tool.

The data helps too. The shape of the data a page shows is called its **data model**. Our data model is the `DRINKS` array. It has the same shape as the boxes: the whole array is the list, `DrinkList`, and each object in it is one row, `DrinkRow`. The docs say that the UI and the data "often have the same information architecture, that is, the same shape." So they advise: "Separate your UI into components, where each component matches one piece of your data model."

Some parts can go either way. The tick box, for example, can stay inside `SearchBar`, or it can get its own component. The docs call a choice like this "a matter of preference, and you could go either way". Both choices give the exact same page. The choice is only about how big that part will grow: if the cafe later adds more filters next to the tick box, they can move into a component of their own.

### Where the four names and `App` come from

We chose the names `MenuPage`, `SearchBar`, `DrinkList`, and `DrinkRow` ourselves. Often the designer has already chosen them. The docs say: "If you work with a designer, they may have already named these components in their design tool. Ask them!"

`App` is not a box on the mockup. It is the root component that `main.jsx` renders, as in Lesson 07. It holds the `DRINKS` array and the heading `Drinks`, and it renders `MenuPage`.

After Step 1, the browser shows nothing new, because this step writes no code at all.

### Mistake: writing the whole page in one component

The habit this step replaces is opening `App.jsx` and writing the search box, the tick box, and the list of drinks all inside one component. That component grows with every part the designer adds. The list cannot be used on another page without bringing the search box along. And splitting the component later means moving state and handlers into new files after the page already works.

> [!PRINCIPLE]
> **Principle 1: Component Hierarchy: Boxes on the Mockup Become Four Components**
>
> *Before writing any code, draw a box around every part of the mockup, name each box as a component, and nest the names the way the boxes nest; one component should do one thing.*
>
> A page written as one component grows with every part the designer adds, and none of its parts can be used again. The boxes on the mockup give us the components before we type a line. A box inside a box becomes a child inside a parent, which is the same UI tree as in Lesson 06. Each component matches one piece of the data: the array is the list, and each object is one row.
>
> **DO THIS:**
> ```jsx
> function MenuPage({ drinks }) {
>   return (
>     <div>
>       ~<SearchBar />~ {/* One box: the search box and the tick box */}
>       <DrinkList drinks={drinks} />
>     </div>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ~App~() { // **WRONG:** the search box, the tick box, and every row in one component
>   return (
>     <main>
>       <input type="text" placeholder="Search..." />
>       <input type="checkbox" />
>       <ul>{DRINKS.map(drink => <li key={drink.id}>{drink.name}</li>)}</ul>
>     </main>
>   );
> }
> ```

## 2. Principle 2: The Static Menu Ignores the Typed Search

### A component that only shows its props

Step 2 turns the boxes into code, with one limit: no state yet. Each component only shows the props it receives:

```jsx title="A component that only shows its props"
function DrinkRow({ ~drink~ }) { // Reads the drink from props: no useState anywhere
  return <li>{drink.name} {drink.price}</li>;
}

<DrinkRow ~drink={{ name: 'Tea', price: '$2' }}~ /> {/* Shows the line Tea $2 */}
```

React's docs call a page built this way a **static version**. Static means it does not move: the page shows the data, "without adding any interactivity... yet!" **Interactivity** is everything the user can change on the page, such as the text in the search box or the tick. The docs keep state for exactly that: state "is reserved only for interactivity, that is, data that changes over time". The search box will need state, but not in this step. The docs' advice is: "It's often easier to build the static version first and add interactivity later."

### Top down and bottom up: two orders, the same four components

With four components to write, which file comes first? The docs give two orders:

```tree caption="Two orders for writing the components of the static version."
Two orders for writing the four components
- +Top down [`MenuPage` first] | Start with the component **at the top** of the hierarchy | The docs: usually easier **in simpler examples**
- +Bottom up [`DrinkRow` first] | Start with the components **at the bottom** of the hierarchy | The docs: easier **on larger projects**
```

The two orders write the files in a different sequence, but they end with the exact same four components. Our page is small, so we go top down.

### Building the static menu, top down

At the top, `App` hands the whole `DRINKS` array to `MenuPage` as a prop:

```jsx title="src/App.jsx"
import MenuPage from './components/MenuPage.jsx';

const DRINKS = [
  { id: 1, name: 'Coffee', price: '$3', inStock: true },
  { id: 2, name: 'Tea', price: '$2', inStock: true },
  { id: 3, name: 'Hot chocolate', price: '$4', inStock: false },
  { id: 4, name: 'Lemonade', price: '$3', inStock: true },
  { id: 5, name: 'Iced tea', price: '$3', inStock: false },
];

export default function App() {
  return (
    <main>
      <h1>Drinks</h1>
      <MenuPage ~drinks={DRINKS}~ /> {/* The data enters the hierarchy here, as a prop */}
    </main>
  );
}
```

`MenuPage` renders its two children and passes the array on to the list:

```jsx title="src/components/MenuPage.jsx"
import SearchBar from './SearchBar.jsx';
import DrinkList from './DrinkList.jsx';

export default function MenuPage({ drinks }) {
  return (
    <div>
      <SearchBar />
      <DrinkList ~drinks={drinks}~ /> {/* Passes the same array one level down */}
    </div>
  );
}
```

`SearchBar` draws the search box and the tick box. Neither of them has a `value`, a `checked`, or an `onChange` prop:

```jsx title="src/components/SearchBar.jsx"
export default function SearchBar() {
  return (
    <form>
      ~<input type="text" placeholder="Search..." />~ {/* No value and no onChange */}
      <label>
        <input type="checkbox" /> Only show drinks in stock
      </label>
    </form>
  );
}
```

`DrinkList` turns the array into rows with `.map`, as in Lesson 18:

```jsx title="src/components/DrinkList.jsx"
import DrinkRow from './DrinkRow.jsx';

export default function DrinkList({ drinks }) {
  return (
    <ul>
      {drinks.map(drink => <DrinkRow key={drink.id} ~drink={drink}~ />)} {/* One row for each drink object */}
    </ul>
  );
}
```

`DrinkRow` shows one drink, and adds `Sold out` only when the drink is not in stock:

```jsx title="src/components/DrinkRow.jsx"
export default function DrinkRow({ drink }) {
  return <li>{drink.name} {drink.price}{~!drink.inStock && ' Sold out'~}</li>; // Sold out only for a drink that is not in stock
}
```

Every component of the static version only returns JSX. After this step, the docs say, "you'll have a library of reusable components that render your data model."

The data enters at the top, in `App`, and each component passes it one level down, until each `DrinkRow` gets one item of the array as `drink`. React's docs call this **one-way data flow**: the data flows down from the top component to the ones at the bottom of the tree, as in Lessons 06 and 23.

### The user types `tea`, and the list still shows all five drinks

When the page opens, the static menu looks exactly like the finished page:

```page caption="The static menu when the page opens: the search box shows its hint Search..., and the page looks exactly like the finished page."
heading: Drinks
form:
  field: | Search...
  check: Only show drinks in stock | off
line: Coffee $3
line: Tea $2
line: Hot chocolate $4 Sold out
line: Lemonade $3
line: Iced tea $3 Sold out
console: quiet
```

Now the user types `tea` in the search box. The box shows `tea`, but the list does not change at all. Why? Well, nothing in our code hears the typing:
1. The search box has no `value` prop, so the browser keeps the typed text inside the input's DOM node, as in Lesson 13.
2. The search box has no `onChange` prop, so no code of ours runs after each keystroke by the user.
3. No state changes, so React does not render `MenuPage` again.
4. `DrinkList` still has the same `drinks` array, so the page still shows all five drinks.

The tick box behaves the same way. The user ticks it, the browser shows the tick, and `Hot chocolate` and `Iced tea` stay on the list although they are sold out:

```page caption="The static menu after the user types tea and ticks the box: the list still shows all five drinks."
heading: Drinks
form:
  field: | tea
  check: Only show drinks in stock | on
line: Coffee $3 | bad
line: Tea $2
line: Hot chocolate $4 Sold out | bad
line: Lemonade $3 | bad
line: Iced tea $3 Sold out | bad
console: quiet
```

The static version and the finished page look the same in the browser, and the search box takes letters in both. **It may look the same, but it is NOT the same thing!** Only the finished page changes the list. That is not a bug of this step. The static version is meant to show the data and nothing more, and the next three steps add what changes.

### Mistake: adding state while the page is still being typed

React's docs warn about this step: "At this point, you should not be using any state values. That's for the next step!" A developer who adds state too early usually writes `SearchBar` first and puts a `useState` for the search text inside it, because the box is there. Then the developer writes the list in `DrinkList`, a sibling of `SearchBar`, and finds that the list cannot read the search text, because a sibling cannot read another component's state, as in Lesson 24. The state has to move, and the handlers with it, after the page is already built.

> [!PRINCIPLE]
> **Principle 2: Static Version: The Static Menu Ignores the Typed Search**
>
> *Build the whole page from the data with components and props only, and no state; the data enters at the top component as a prop and flows down to the rows.*
>
> When state goes in while the components are still being typed, the long typing and the hard thinking happen at the same time, and the state often lands in the wrong component. The static version only shows the data: `App` passes the array down, and each component reads its props. The page looks finished, but typing in the search box changes nothing yet, and that is expected after this step.
>
> **DO THIS:**
> ```jsx
> export default function DrinkList({ ~drinks~ }) { // Reads the array from props only
>   return <ul>{drinks.map(drink => <DrinkRow key={drink.id} drink={drink} />)}</ul>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function SearchBar() {
>   const [filterText, setFilterText] = ~useState('')~; // **WRONG:** state added in Step 2, inside a component the list cannot read
>   return <input value={filterText} onChange={(e) => setFilterText(e.target.value)} />;
> }
> ```

## 3. Principle 3: Only the Search Text and the Tick Box Become State

### The four values of the page

Step 3 also writes no code. We read the page and the data, and we list every value the page uses. React's docs list the same four values for their own example page. On our menu, they are:
1. The list of drinks.
2. The search text the user typed.
3. The tick of the box.
4. The drinks that match the search text and the tick.

The fourth value changes every time the user types or ticks, so it looks like state. **It may look the same, but it is NOT the same thing!** The drinks that match are computed from the other three values. Whenever we know the list, the text, and the tick, we can always work out which drinks match.

The key idea of this step, in the docs' words: "Think of state as the minimal set of changing data that your app needs to remember." The docs' title for this step is **find the minimal but complete representation of UI state**. Minimal means nothing that can be computed. Complete means everything the page needs to remember.

### The three questions, asked once of each value

Lesson 22 taught three questions that tell what is state: Does it remain unchanged over time? Is it passed in from a parent via props? Can you compute it from existing state or props? A "yes" to any of them means it is not state. Here are the answers for the four values of our menu:

```tree caption="The three questions applied to the four values of the drinks menu: only two values become state."
Which of the four values is state?
- !The list of drinks [`drinks`] | Arrives **from a parent** as a prop | **Not state**
- +The search text [`filterText`] | **Changes over time** and **cannot be computed** | **State**
- +The tick of the box [`inStockOnly`] | **Changes over time** and **cannot be computed** | **State**
- !The drinks that match [`visibleDrinks`] | **Computed** from the list, the text, and the tick | **Not state**
```

The docs reach the same answer for their page: "This means only the search text and the value of the checkbox are state!" We name the two pieces of state the way the docs do: `filterText` for the search text and `inStockOnly` for the tick.

### Storing the drinks that match, and computing them

There are two ways to get the drinks that match, and they look alike in the code:

```jsx title="The drinks that match, stored with useState"
const [visibleDrinks, setVisibleDrinks] = ~useState(drinks)~; // **WRONG:** a second copy that every handler must update by hand
```

```jsx title="The drinks that match, computed with filter during rendering"
const visibleDrinks = ~drinks.filter(...)~; // Made again from drinks, filterText, and inStockOnly on every render
```

They are NOT the same thing. With `useState`, the list of matching drinks is a copy that our code must update by hand after every keystroke and every tick by the user. With `filter`, the list is made again on every render from the current text and tick, so it is always right. Principle 4 writes out the full `filter` call.

The docs name the rule behind this DRY, short for Don't Repeat Yourself, and give a shopping list as the example: "don't store the number of items as another state value, instead, read the length of your array."

### Props and state

The list of drinks failed the second question because it is a prop. The docs put the two words side by side: props "are like arguments you pass to a function", and state "is like a component's memory". They also say: "Props and state are different, but they work together." A parent keeps information in state and passes it down to its children as props. That is exactly what Step 4 does with `filterText` and `inStockOnly`.

After Step 3, the browser shows nothing new, because this step writes no code.

### Mistake: storing the drinks that match as a second state

A developer stores the matching drinks in a second state variable, next to the search text, and the `onChange` of the search box updates both. Later the developer adds the tick box and forgets to update the matching drinks from its `onChange`. Now the user ticks the box, `inStockOnly` changes, and `Iced tea` stays on the list although it is sold out, because nothing told the stored copy about the tick.

> [!PRINCIPLE]
> **Principle 3: Minimal State: Only the Search Text and the Tick Box Become State**
>
> *List every value the page uses and keep as state only what changes over time, does not come from a parent, and cannot be computed from other state or props.*
>
> Every value stored as state is one more value that can disagree with the others. The list of drinks comes from a parent. The drinks that match can be computed from the list, the text, and the tick. Only the search text and the tick of the box change over time and cannot be computed, so only they become state.
>
> **DO THIS:**
> ```jsx
> const [filterText, setFilterText] = useState('');
> const [inStockOnly, setInStockOnly] = useState(false);
> const visibleDrinks = ~drinks.filter(...)~; // Computed on every render, never stored
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [filterText, setFilterText] = useState('');
> const [visibleDrinks, setVisibleDrinks] = ~useState(drinks)~; // **WRONG:** a copy that goes out of step when one handler forgets it
> ```

## 4. Principle 4: State in MenuPage Freezes the Search Box

### A parent holds the state, and two parts of the page read it

Step 4 decides where `filterText` and `inStockOnly` live. Here is the shape we are heading for, in its smallest form:

```jsx title="The state in the parent, read by the box and by the list"
function MenuPage() {
  const [filterText, setFilterText] = ~useState('tea')~; // The parent owns the search text
  return (
    <div>
      <input ~value={filterText}~ /> {/* The box shows tea and refuses every letter */}
      <DrinkList ~filterText={filterText}~ /> {/* The list shows only the drinks with tea in their name */}
    </div>
  );
}
```

The box with `value` and no `onChange` refuses every letter the user types. **Yes, it is the exact same frozen box as in Lesson 20!** Here the value comes from state in a parent, and in the project it will reach the box through props, but the box freezes in the same way.

### Finding the owner in three steps

Lesson 24 taught how to find the owner of a piece of state. React's docs list the same three steps, and we apply them once to `filterText` and `inStockOnly`:
1. **Find every component that renders something from that state:** `DrinkList` needs both values to pick the drinks that match. `SearchBar` needs both values to show the text in the box and the tick.
2. **Find their closest common parent:** `SearchBar` and `DrinkList` are siblings, and their closest common parent is `MenuPage`.
3. **Decide where the state lives:** in `MenuPage`.

For the last of these three, the docs give three choices: "Often, you can put the state directly into their common parent." "You can also put the state into some component above their common parent." "If you can't find a component where it makes sense to own the state, create a new component solely for holding the state." Our common parent works, so the state goes into `MenuPage`. Both values go to the same place, and the docs explain why: "they always appear together, so it makes sense to put them into the same place."

The state cannot live in `SearchBar`, even though the boxes are there. `DrinkList` is a sibling of `SearchBar`, and a sibling cannot read another component's state, as in Lesson 24.

### Adding the state to `MenuPage` and passing it down

`MenuPage` gets the two `useState` lines and passes both values down to both children:

```jsx title="src/components/MenuPage.jsx"
import { useState } from 'react';
import SearchBar from './SearchBar.jsx';
import DrinkList from './DrinkList.jsx';

export default function MenuPage({ drinks }) {
  const [filterText, setFilterText] = ~useState('')~; // The search text starts empty
  const [inStockOnly, setInStockOnly] = ~useState(false)~; // The tick box starts empty
  return (
    <div>
      <SearchBar ~filterText={filterText} inStockOnly={inStockOnly}~ /> {/* The boxes show the state */}
      <DrinkList drinks={drinks} ~filterText={filterText} inStockOnly={inStockOnly}~ /> {/* The list uses the state */}
    </div>
  );
}
```

`SearchBar` puts the two props into the two boxes:

```jsx title="src/components/SearchBar.jsx"
export default function SearchBar({ filterText, inStockOnly }) {
  return (
    <form>
      <input type="text" ~value={filterText}~ placeholder="Search..." /> {/* The box always shows filterText */}
      <label>
        <input type="checkbox" ~checked={inStockOnly}~ /> Only show drinks in stock {/* The tick always follows inStockOnly */}
      </label>
    </form>
  );
}
```

`DrinkList` computes the drinks that match during rendering, as Principle 3 decided, and maps over them instead of over all drinks:

```jsx title="src/components/DrinkList.jsx"
import DrinkRow from './DrinkRow.jsx';

export default function DrinkList({ drinks, filterText, inStockOnly }) {
  const visibleDrinks = drinks.filter(drink => {
    if (~inStockOnly && !drink.inStock~) { // With the box ticked, a sold-out drink is dropped
      return false;
    }
    return drink.name.~toLowerCase()~.includes(filterText.toLowerCase()); // Keeps a drink whose name holds the search text
  });
  return (
    <ul>
      {~visibleDrinks~.map(drink => <DrinkRow key={drink.id} drink={drink} />)} {/* Only the drinks that match */}
    </ul>
  );
}
```

One helper is new here: `toLowerCase`. It is a JavaScript method of every string, and it returns the same text in small letters. The names in our data start with a capital letter, such as `Tea` and `Iced tea`, while the user usually types in small letters. With `toLowerCase` on both sides, the search text `tea` finds `Tea` and `Iced tea`. Then `includes`, from Lesson 21, checks whether the name holds the search text. An empty text counts as found inside every name, so while the search box is empty, every drink matches.

### Mistake: keeping the search text in `SearchBar` and copying it into `DrinkList`

This step prevents the same value being stored twice. Here is how that happens:
1. A developer puts the `useState` for the search text inside `SearchBar`, because the box is there.
2. `DrinkList` needs the same text to pick the drinks, and it cannot read it.
3. The developer adds a second `useState` for the same text inside `DrinkList`.
4. The two copies start equal. Then the user types, and only the copy in `SearchBar` changes.
5. The box shows `tea`, and the list still shows all five drinks.

> [!PRINCIPLE]
> **Principle 4: Where State Lives: State in MenuPage Freezes the Search Box**
>
> *Put each piece of state in the closest common parent of every component that renders from it, and pass it down as props; until Step 5, the boxes show the state but refuse the user's input.*
>
> The search box shows the text, so the text seems to belong in `SearchBar`. But the list, a sibling, needs the same text, and a sibling cannot read it. The closest common parent, `MenuPage`, owns both values and passes them down. After this step, a new starting value in the code changes the box and the list together, while the user's typing is refused, because no `onChange` changes the state yet.
>
> **DO THIS:**
> ```jsx
> function MenuPage({ drinks }) {
>   const [filterText, setFilterText] = ~useState('')~; // Owned by the closest common parent
>   return (
>     <div>
>       <SearchBar filterText={filterText} />
>       <DrinkList drinks={drinks} filterText={filterText} />
>     </div>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function SearchBar() {
>   const [filterText, setFilterText] = ~useState('')~; // **WRONG:** the sibling DrinkList can never read this text
>   return <input value={filterText} onChange={(e) => setFilterText(e.target.value)} />;
> }
> ```

## 5. Principle 5: onFilterTextChange Lets the Search Box Change MenuPage's State

### Passing the setter down, and calling it from `onChange`

Only the owner of the state can call its setter, and the owner here is `MenuPage`. React's docs say it about their own example: "The state is owned by `FilterableProductTable`, so only it can call `setFilterText` and `setInStockOnly`." `FilterableProductTable` is the docs' name for the component that plays the part of our `MenuPage`. So `MenuPage` hands its setter down as a prop, and the box calls it:

```jsx title="The parent passes its setter down, and the box in the child calls it"
<SearchBar ~onFilterTextChange={setFilterText}~ /> {/* In MenuPage: the setter travels down as a prop */}

<input onChange={(e) => ~onFilterTextChange(e.target.value)~} /> {/* In SearchBar: the typed text travels back up */}
```

**Yes, it is the exact same thing as the callback prop from Lesson 23, and the setter passed down in Lesson 24!** The docs give it a name for its direction: **inverse data flow**. Inverse means the other way round. Props carry data down the tree, and a function passed down carries the typed text the other way, up the tree to its owner.

### `value` alone and `value` with `onChange`

A reader may expect `value={filterText}` to change `filterText` when the user types, since the box already shows it. Compare the two boxes:

```jsx title="A box with value only, and a box with value and onChange"
<input ~value={filterText}~ /> {/* value only: the state goes down into the box, and the box stays frozen */}
<input value={filterText} ~onChange={(e) => onFilterTextChange(e.target.value)}~ /> {/* value and onChange: every keystroke goes back up */}
```

They look alike, but they are NOT the same thing. `value` only sends the state down into the box. The `onChange` that calls `onFilterTextChange` sends each new text back up to `MenuPage`. Some other tools let a box and a variable update each other with no handler written. That is called **two-way data binding**, and React does not do it. The docs say: "React makes this data flow explicit, but it requires a little more typing than two-way data binding."

### Adding the two setters to the page

`MenuPage` adds the two setters to the `SearchBar` tag:

```jsx title="src/components/MenuPage.jsx" startLine="8"
  return (
    <div>
      <SearchBar
        filterText={filterText}
        inStockOnly={inStockOnly}
        ~onFilterTextChange={setFilterText}~ // Hands down the setter for the search text
        ~onInStockOnlyChange={setInStockOnly}~ // Hands down the setter for the tick
      />
      <DrinkList drinks={drinks} filterText={filterText} inStockOnly={inStockOnly} />
    </div>
  );
```

`SearchBar` unpacks the two new props and calls them from `onChange`. On the text box, `e.target.value` is the text in the box. On the tick box, `e.target.checked` is the tick, as in Lesson 20:

```jsx title="src/components/SearchBar.jsx"
export default function SearchBar({ filterText, inStockOnly, onFilterTextChange, onInStockOnlyChange }) {
  return (
    <form>
      <input
        type="text"
        value={filterText}
        placeholder="Search..."
        ~onChange={(e) => onFilterTextChange(e.target.value)}~ // Sends the new text up to MenuPage
      />
      <label>
        <input type="checkbox" checked={inStockOnly} ~onChange={(e) => onInStockOnlyChange(e.target.checked)}~ /> Only show drinks in stock {/* Sends the new tick up to MenuPage */}
      </label>
    </form>
  );
}
```

`App.jsx`, `DrinkList.jsx`, and `DrinkRow.jsx` do not change. The list already picks the drinks from `filterText` and `inStockOnly`. It only needed those values to change.

We pass the setter itself, as the docs do. A handler in `MenuPage` that calls `setFilterText`, passed down in place of the setter, does the exact same thing on this page, because the box always sends exactly the next text.

### The user types `tea`, and the list follows every letter

After each keystroke by the user, the list changes. Here is the path of the first letter:
1. The user types `t`. React calls the `onChange` arrow function in `SearchBar` with the event object `e`.
2. The arrow function calls `onFilterTextChange` with the text `t`, and `onFilterTextChange` is `setFilterText` from `MenuPage`.
3. React renders `MenuPage` again, now with `filterText` set to `t`.
4. `SearchBar` receives the new `filterText` and shows `t` in the box. `DrinkList` receives it too and computes `visibleDrinks` again: every drink whose name holds a `t`. That is `Tea`, `Hot chocolate`, and `Iced tea`.

The letters `e` and `a` take the same path. With `te`, the list still shows the same three drinks, because the word chocolate ends in the letters t and e. With `tea`, `Hot chocolate` leaves the list, and only `Tea` and `Iced tea` stay. Then the user ticks the box. The tick box calls `onInStockOnlyChange` with `true`, which is `setInStockOnly`. `Iced tea` leaves the list because it is sold out, and only `Tea` stays:

```page caption="The finished menu after the user types tea and ticks the box: only Tea is left, and the Console is clear."
heading: Drinks
form:
  field: | tea | good
  check: Only show drinks in stock | on | good
line: Tea $2 | good
console: quiet
```

If the user now clears the search box and keeps the tick, the list shows the three drinks in stock: `Coffee`, `Tea`, and `Lemonade`. Both boxes have their `onChange` now, so the read-only field errors are gone from the Console. The docs say it after this step: "Now the application fully works!"

### Mistake: expecting `value` to update the state by itself

This is the most common surprise in this lesson, and the docs' own Step 5 starts from it. A developer passes `filterText` down, writes `value={filterText}` on the box, and expects the box to change `filterText` when the user types, as two-way data binding does in other tools. The user types, and the box stays empty, with the read-only field error in the Console. The fix is the one this principle shows: pass `onFilterTextChange` down and call it from `onChange`.

> [!PRINCIPLE]
> **Principle 5: Inverse Data Flow: onFilterTextChange Lets the Search Box Change MenuPage's State**
>
> *Only the owner of the state can call its setter, so the owner passes the setters down as props, and the boxes deep in the tree call them from `onChange`.*
>
> A box with `value={filterText}` shows the state, but it cannot change it, because `filterText` belongs to `MenuPage`. `MenuPage` passes `setFilterText` down as `onFilterTextChange`, and the box calls it with `e.target.value` after each keystroke by the user. React then renders `MenuPage` again, and the box and the list both follow the new text.
>
> **DO THIS:**
> ```jsx
> <input
>   value={filterText}
>   ~onChange={(e) => onFilterTextChange(e.target.value)}~ // The typed text goes up to the owner
> />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input ~value={filterText}~ /> {/* **WRONG:** no onChange, so the box refuses every letter the user types */}
> ```

## For the Interview

> **The Interview Question:** What is the step-by-step process for building a UI in React?

### How to Answer Clearly in 30 Seconds

"React's docs call it Thinking in React, and it has five steps in a fixed order. First, I break the mockup into a component hierarchy: I draw a box around every part, name it, and nest the names, so each component does one thing and matches one piece of the data. Second, I build a static version with props only and no state, so the data flows down from the top component. Third, I find the minimal state: only what changes over time, does not come from a parent, and cannot be computed. Fourth, I put each piece of state in the closest common parent of the components that render from it. Fifth, I add inverse data flow: the owner passes its setters down, and the inputs call them from `onChange`. On a search page, only the search text and the checkbox are state, and the filtered list is computed during rendering."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why build a static version first, without any state?"**
   Because the two jobs are different. React's docs say that building a static version "requires a lot of typing and no thinking, but adding interactivity requires a lot of thinking and not a lot of typing." When state goes in while the components are still being typed, it often lands in the wrong component, such as the search text inside the search box component, where the list cannot read it. After the static version, the data already flows down with props, and the state goes in with one clear question: who needs it? The static version takes its data as a prop at the top, whether the data is written in the file, as in our menu, or fetched from a server, which a later lesson covers.
2. **"On a page with a search box and a filtered list, is the filtered list state?"**
   No. It changes when the user types, but it can be computed from the full list, the search text, and the checkbox, so it is computed during rendering with `filter`. If it were stored as a second state, every handler would have to update it by hand, and a forgotten update would leave a sold-out item on the list. The docs' rule is to find the minimal set of changing data the app needs to remember and compute everything else when it is needed. On their own example, the docs conclude that only the search text and the value of the checkbox are state.
3. **"After you move the state up and pass it down, why does typing in the box do nothing, and how do you fix it?"**
   The box has `value={filterText}`, so React makes it always show `filterText`, but nothing calls `setFilterText` when the user types. React prints the read-only field error in the Console. React has one-way data flow, so the fix is inverse data flow: the owner passes its setter down as a prop, such as `onFilterTextChange={setFilterText}`, and the box calls it from `onChange` with `e.target.value`. React makes this flow explicit, with a little more typing than two-way data binding. When the setters and props passed down grow too many or go too deep, later lessons bring `useReducer` and context.

```tree dir=right caption="Interview summary: the five steps of Thinking in React, and the question each one answers."
The five steps and the question each one answers
- +1. Component hierarchy | Which **components** does the mockup need?
- +2. Static version | How does the **data** reach every component?
- +3. Minimal state | Which values **change and cannot be computed**?
- +4. Where state lives | Which component **owns** each piece of state?
- +5. Inverse data flow | How does a box deep in the tree **change** that state?
```
