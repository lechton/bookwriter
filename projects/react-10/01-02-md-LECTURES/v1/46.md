# Lecture 46: How to Choose Between a Framework and a Build Tool
> INTERVIEW QUESTION | ❱❱ MORE | How do you choose between a full-stack framework and a standalone build tool?

## Why the Choice Comes Before the First Line of Code

### The page the user sees vs. the HTML file the server sends

Picture a product page in an online shop. It shows one product name, `Blue Sneakers`, and one price, `$49`:

```page caption="The product page of the shop, open in the developer's browser."
heading: Blue Sneakers
line: $49
```

A user likes the sneakers. The user copies the link of this page and pastes it into a chat app, to send it to a friend. Two things go wrong:
1. The chat app shows a preview card under the link. The card reads `Shop`, the same title it shows for every product of the shop. The name `Blue Sneakers` is missing.
2. The friend opens the link on a phone with a slow connection. The page stays blank, then shows `Loading...`, and only then shows `Blue Sneakers`.

```page caption="The preview card the chat app shows for the pasted link: the shop title, and no product name."
url: chat.example.com
section: Chat
line: shop.example.com
card: title=Shop | bad
```

::: row caption="What the friend sees on a slow phone: a blank page, then Loading..., then the product."
::: col title="1. While the JavaScript downloads" tone=bad
```page size=mini
url: shop.example.com
blank
```
:::
::: col title="2. While the product data loads" tone=bad
```page size=mini
url: shop.example.com
line: Loading...
```
:::
::: col title="3. At last" tone=good
```page size=mini
url: shop.example.com
heading: Blue Sneakers
line: $49
```
:::
:::

The page looks right on the developer's computer, but the chat app and the phone did not start from that page. They started from the HTML file of the app. In an app made with Vite alone, the way we have built every page so far (as seen in Lesson 07), that file holds only an empty root:

```html title="The file the server sends vs. the page after the JavaScript runs in the browser"
~<div id="root"></div>~ <!-- 1. The file the server sends: the root is empty -->
~<div id="root"><h1>Blue Sneakers</h1><p>$49</p></div>~ <!-- 2. The page after the browser has loaded and run the JavaScript -->
```

The chat app never runs that JavaScript, so it never sees the product. The slow phone does run it, but only after a long download.

**It may look the same, or work the same at first, but it is NOT the same thing!** Build this shop twice: once with Vite alone, and once with a framework. In the developer's browser, the two product pages look the same. The HTML file that leaves the server is different:
- **With Vite alone**, the root in that file is empty. JavaScript adds the product later, in the browser.
- **With a framework that makes the page on the server or at build time**, the file already holds `Blue Sneakers` before any JavaScript runs.

### React draws the components and leaves three questions open

React's home page says it plainly: "React is a library. It lets you put components together, but it doesn't prescribe how to do routing and data fetching."

So every React app must answer three questions that React itself leaves open:
1. **What does the first HTML file hold?** An empty root, or the finished page?
2. **Which URL shows which page?** This question is called **routing**.
3. **When does the data load?** After the page renders, or before?

A **full-stack framework**, or framework for short, answers all three for us. Full-stack means it can also do work on a server, not only in the browser. Next.js and React Router are two of them. A **build tool** such as Vite answers none of them. It leaves all three to our own code.

The two words "library" and "framework" come from everyday life, and they tell us who is in charge. With a **library**, we are in charge: we take the tool we need, the way we take a book from a library shelf, and we decide how the rest of the app is built. A **framework** is a frame, like the frame of a house that already stands: it decides the shape of the app, such as where each page lives and when it loads its data, and we fill in the rooms. React is the library. A framework such as Next.js is the frame built around it.

```tree caption="React draws the components; a framework or our own code decides how the page reaches the user."
Who answers each question in a React app
- +React, a library [`<Product />`] | Puts **components together** and draws them | Does **not** decide routing, data loading, or the first HTML
- +A full-stack framework [`Next.js` `React Router`] | Decides **the first HTML**, **the URL of each page**, and **when data loads** | We follow its way of building pages
- !A build tool alone [`Vite`] | Prepares our files for the browser | Leaves **all three questions** to our own code
```

### What is at stake

The choice shows up on the user's screen in three places:
1. **The shared link shows the wrong title.** A chat app builds its preview card with a **crawler**: a program that downloads a web page to read what it says. Social media crawlers usually do not run JavaScript, so the card can show only what the HTML file holds.
2. **The user waits twice.** First for the whole JavaScript bundle, then again for the product data, before the product appears.
3. **A link to one product opens the home page.** This happens when the app keeps the current page in state instead of in the URL.

### Where readers usually go wrong

1. **They think a framework always needs a server.** react.dev says the opposite: "Full-stack frameworks do not require a server."
2. **They think server rendering is only for search engines.** react.dev: "A common misunderstanding is that server rendering is only for SEO." SEO is the work of making a page easy for search engines to find. Server rendering also shows the content to the user before the JavaScript loads.
3. **They start a new app with `npx create-react-app`.** react.dev has deprecated it.

### The ways to start a React app

When developers start a React app at work, they choose one of these ways. react.dev lists each one with its command:

1. **A full-stack framework.** react.dev recommends this for a new app or website:
   - Next.js, with its App Router.
   - React Router, version 7.
   - Expo, for native apps.
2. **A build tool, starting from scratch:** Vite, Parcel, or Rsbuild. react.dev says this fits when "your app has constraints not well-served by existing frameworks, you prefer to build your own framework, or you just want to learn the basics of a React app".
3. **A build tool such as Vite, for React in part of an existing page,** such as a page made with Rails. The rest of the site already exists in another technology, and React takes over one element of that page.
4. **Not a way: Create React App.** react.dev: "Should I use Create React App? No. Create React App has been deprecated."

```text title="Terminal: the commands react.dev gives for each way"
npx create-next-app@latest
npx create-react-router@latest
npx create-expo-app@latest
npm create vite@latest my-app -- --template react-ts
npm install --save-dev parcel
npx create-rsbuild --template react
```

```tree caption="The ways to start a React app today, and the one way that is no longer a choice."

- +A build tool from scratch [`npm create vite@latest`] | Fits a **client-only app**, a team that **builds its own framework**, or **learning** | Every other decision is **ours**

```

### Our example: the Blue Sneakers product page

In this lesson, we build the product page with Vite alone, the way we built every page so far (as seen in Lesson 07). Then we compare each part with what a framework does for the same page.

```files title="shop: File Explorer" caption="The files of our shop made with Vite alone."
index.html | entry | The one HTML page, with `<title>Shop</title>` and the empty root div
src/
  main.jsx | boundary | Imports `App` and mounts it into `#root`, as in Lesson 07
  App.jsx | page | Exports `App` as default: the product page
  api.js | stand-in server | Exports `getProduct`, which waits one second and gives the product
```

Our shop has no real server, so `api.js` plays its part. Its function `getProduct` waits one second, then gives back `{ name: 'Blue Sneakers', price: 49 }`.

**PRINCIPLES:** A framework and a build tool both run React. They differ in what they decide for us. Six practical rules come up when a team makes this choice, in daily debugging and in React interviews:
1. **Principle 1: A Build Tool Prepares Our Files, and Nothing Else.** Vite turns JSX into JavaScript, packs the files into a bundle, runs a development server, and makes the production files. Routing, data loading, and server rendering are not part of it.
2. **Principle 2: The First HTML Holds Only an Empty Root.** In an app made with a build tool alone, the HTML file the server sends holds no product. The user sees a blank page, and a crawler sees no content, until the JavaScript runs.
3. **Principle 3: A Page Kept in State Has No URL of Its Own.** When the app picks its page with `useState`, every page has the same address. A shared link always opens the first page. A router gives each page its own URL.
4. **Principle 4: A Loader Starts the Fetch Before the Page Renders.** A fetch in an Effect waits for the bundle and the first render. A framework's loader starts the fetch first, while the code is still downloading.
5. **Principle 5: A Framework Can Put the Product into the HTML.** A framework can make a page on the server or at build time, so the file already holds the product. It chooses this for each page, and it does not need a server.
6. **Principle 6: An Admin Tool Behind a Login Can Stay on Vite.** When no page must show its content before the JavaScript runs, and no page needs its own URL, a build tool is enough.

Here is the map of the six principles before we walk through each one:

| :--- | :--- | :--- | :--- |

## 1. Principle 1: A Build Tool Prepares Our Files, and Nothing Else

### One command starts a Vite project

Here is react.dev's own command to start a React app with Vite:

```text title="Terminal: starting a React app with Vite"
npm create vite@latest my-app -- --template react-ts
```

The command creates a new folder named `my-app`, the name we chose, and copies Vite's starting files into it. The option `react-ts` asks for React with TypeScript. The template named `react` gives plain JavaScript files instead, like the `.jsx` files of our shop.

Inside the folder, two commands do the daily work (as seen in Lesson 07 and Lesson 15):

```text title="Terminal: the two daily commands"
npm run dev
npm run build
```

1. `npm run dev` starts the development server while we write code.
2. `npm run build` makes the files we put on a production server.

react.dev calls this path "building a React app from scratch". The name sounds like new and harder work. **Yes, it is the exact same thing** as the project we already know (as seen in Lesson 07): one `index.html`, one `main.jsx`, and Vite. Nothing new is added. This lesson only gives the path its name.

### What a build tool does, and what it leaves to us

A **build tool** is a program that prepares our source files for the browser. react.dev lists its jobs: build tools "provide features to package and run source code, provide a development server for local development and a build command to deploy your app to a production server."

So Vite does four jobs for us:
1. It turns JSX into JavaScript that the browser can run.
2. It packs our files into a bundle.
3. It runs a development server.
4. It makes the production files with a build command.

That is all. react.dev says the build tools "start off with a client-only, single-page app", or SPA for short. Two words in that sentence matter:
- **Single-page app, SPA:** the browser loads one HTML document, and JavaScript changes what that one document shows. Our shop has one `index.html`, and every page of the shop is drawn inside it.
- **Client-only:** the client is the user's browser. All the drawing happens there. Nothing is drawn on the server.

Routing, data fetching, and rendering on the server are not part of a build tool. If the app needs them, our team adds them.

```tree caption="What a build tool such as Vite does for us, and what it leaves to our own code."
What `npm create vite@latest` gives a React app
- +What Vite does [`npm run dev` `npm run build`] | Turns **JSX into JavaScript** and packs a **bundle** | Runs a **development server** and makes the **production files**
- !What Vite leaves to us | **Routing**: which URL shows which page | **Data fetching** and **rendering on the server** are ours to add
```

Vite is one of three build tools react.dev names. The other two are Parcel and Rsbuild, each with its own command in the terminal block of the opening. For React Native, the bundler is Metro.

### `npm create vite` vs. `npx create-react-app`

Many older tutorials start with a different command:

```text title="Terminal: the command of older tutorials"
npx create-react-app my-app
```

To a developer who follows that tutorial, both commands seem to do the same job: each one gives a working page with JSX and a development server. **It may look the same, or work the same at first, but it is NOT the same thing!** Create React App is **deprecated**: react.dev no longer recommends it, and keeps it only so that old apps keep working. In react.dev's words, "Create React App will continue working in maintenance mode." It has no active maintainers.

When a developer runs it, the terminal prints this message:

```text title="Terminal: running npx create-react-app"
create-react-app is deprecated.

You can find a list of up-to-date React frameworks on react.dev
For more info see:https://react.dev/link/cra

This error message will only be shown once per install.
```

A developer who ignores the message starts a new app on a tool that nobody maintains. react.dev's answer is short: start with a framework, or with Vite, Parcel, or Rsbuild.

Create React App was a good answer in its time. In 2016, there was no clear way to build a new React app, and it joined several tools into one recommended setup. Today, frameworks and build tools solve those problems better, so react.dev deprecated it on February 14, 2025.

> [!PRINCIPLE]
> **Principle 1: Build Tool: Vite Prepares Our Files, and Leaves Routing, Data, and Server HTML to Us**
>
> *A build tool such as Vite turns JSX into JavaScript, packs a bundle, runs a development server, and makes production files; it does nothing else for the app.*
>
> A build tool starts us off with a client-only single-page app. It never decides which URL shows which page, when the data loads, or what the first HTML file holds. Create React App once did the same job, but react.dev deprecated it, so a new app starts with a framework or with Vite, Parcel, or Rsbuild.
>
> **DO THIS:**
> ```text
> npm create vite@latest my-app -- --template react-ts
> ```
>
> **DO NOT DO THIS:**
> ```text
> npx create-react-app my-app
> ```

## 2. Principle 2: The First HTML Holds Only an Empty Root

### The page the user sees vs. the file the server sends

**Beware! In an app made with a build tool alone, the file the server sends never holds the product.** The product page on the screen and the HTML file behind it are two different things. JavaScript fills the page later, in the browser.

Let's build the product page with Vite and see where `Blue Sneakers` really lives.

### The product page made with Vite alone

`index.html` is the one HTML page of the shop. Its title is `Shop`, and its root is empty (as seen in Lesson 07):

```html title="index.html"
<!DOCTYPE html>
<html lang="en">
  <head>
    <title>~Shop~</title> <!-- The one title of the whole shop -->
  </head>
  <body>
    ~<div id="root"></div>~ <!-- Empty: no product anywhere in this file -->
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>
```

`main.jsx` mounts `App` into `#root` (as seen in Lesson 07). Our stand-in server lives in `api.js`:

```js title="src/api.js"
export function ~getProduct~() { // Our stand-in server: answers after one second
  return new Promise(resolve => {
    setTimeout(() => resolve({ name: 'Blue Sneakers', price: 49 }), 1000);
  });
}
```

`App` fetches the product in an Effect and shows `Loading...` until it arrives (as seen in Lesson 33):

```jsx title="src/App.jsx"
import { useState, useEffect } from 'react';
import { getProduct } from './api.js';

export default function App() {
  const [product, setProduct] = useState(null);

  useEffect(() => {
    ~getProduct().then(setProduct)~; // Starts after the first render
  }, []);

  if (!product) {
    return <p>Loading...</p>;
  }

  return (
    <>
      ~<h1>{product.name}</h1>~ {/* Blue Sneakers, one second after the first render */}
      <p>${product.price}</p>
    </>
  );
}
```

The developer opens the page. It shows `Loading...`, and one second later the product:

::: row caption="The product page made with Vite alone, in the developer's browser."
::: col title="First render"
```page size=mini
line: Loading...
```
:::
::: col title="One second later" tone=good
```page size=mini
heading: Blue Sneakers
line: $49
```
:::
:::

The developer then opens the Elements panel, and the product is there, inside the root:

```dom caption="The Elements panel after the JavaScript has run: the product sits inside the root."
<div id="root">
+ <h1>Blue Sneakers</h1> | note: Added by JavaScript in the browser
+ <p>$49</p> | note: Added by JavaScript in the browser
</div>
```

This is why the developer never notices the problem. The Elements panel shows the page as it is now, after the JavaScript ran. It does not show the file the server sent.

### What the chat app receives

**The preview card reads `Shop` because the chat app never runs our JavaScript.** Here is what happens when the user pastes the product link, in order:
1. The chat app's crawler downloads the HTML file of the link.
2. The crawler does not run the JavaScript in that file.
3. In that file, the only title is `Shop`, and the root is empty.
4. So the card reads `Shop`. It reads `Shop` for this product and for every other product of the shop, because a single-page app sends the same `index.html` for every page.

After `npm run build`, the file the server sends is still our `index.html`. Vite only replaces our script tag with one in the head that points at the bundle it made, under a file name that Vite chooses:

```html title="The file the server sends after npm run build, shortened"
<title>~Shop~</title> <!-- The same title for every product -->
<div ~id="root"~></div> <!-- Still empty: Blue Sneakers is not in the file -->
```

Search engines have crawlers too. MDN explains the difference between the two kinds: "major search engines are capable of executing JavaScript so pure CSR sites can still be indexed, but social media crawlers usually cannot."

CSR in that sentence stands for **client-side rendering**: JavaScript makes the content of the page in the browser. That is exactly what our shop does. MDN's own example of a CSR page holds only `<div id="root"></div>`, like ours.

### What the friend's slow phone shows

**The friend waits twice: first for the bundle, then for the product.** Here is what the slow phone does, in order:
1. The page is blank while the bundle downloads. react.dev describes it: "the user sees a blank page until the app's JavaScript code loads and runs."
2. React runs and draws `Loading...`, and only then does the Effect ask for the product.
3. One second later, `Blue Sneakers` appears.

On the developer's computer, the bundle arrives in a moment, so the blank page is too short to notice. On a slow phone, it is the first thing the user sees.

### Why this bug ships

This mistake is easy to make, because nobody on the team sees it at first:
1. A team starts a public shop with Vite alone, because the first screen is quick to build.
2. Every page looks right on the developers' computers.
3. Months later, the marketing team shares product links, and every preview card shows the same shop title.
4. The team learns that the HTML of every page is the same empty file.
5. To fix it, someone must make the HTML on the server or at build time. When a team starts from scratch, react.dev says it "will have to implement" this on its own.

react.dev gives the cure in the docs of `createRoot`: "To solve this, you can generate the initial HTML from your components on the server or during the build." And it adds: "We recommend using a framework that does this optimization out of the box." Principle 5 shows what that looks like.

Client-side rendering has a real benefit too. Once the bundle has loaded, the user moves between pages without a full page reload. The cost is the empty first file.

```tree dir=right caption="The same product page, seen by the developer's browser and by the chat app's crawler."
Who sees `Blue Sneakers` on the page made with Vite alone
- +The developer's browser [`App.jsx`] | Downloads the file **and runs the JavaScript** | Shows **Blue Sneakers** one second after **Loading...**
- !The chat app's crawler [`index.html`] | Downloads the file and **does not run the JavaScript** | Finds only the title **Shop** and an **empty root**
```

> [!PRINCIPLE]
> **Principle 2: Client-Side Rendering: The First HTML Holds Only an Empty Root**
>
> *In a client-only app, the HTML file the server sends holds only `<div id="root"></div>`; the content exists only after the JavaScript loads and runs.*
>
> The developer's browser runs the JavaScript, so the page looks complete. A chat app's crawler usually does not run it, so its preview card shows only the title of `index.html`. A user on a slow phone sees a blank page while the bundle downloads. When a page must show its content before the JavaScript runs, its HTML must be made on the server or at build time.
>
> **DO THIS:**
> ```html
> <div id="root">~<h1>Blue Sneakers</h1>~<p>$49</p></div> <!-- Made on the server or at build time: a crawler reads the product -->
> ```
>
> **DO NOT DO THIS:**
> ```html
> ~<div id="root"></div>~ <!-- **WRONG:** for a public product page: the crawler finds no product, and the preview card says Shop -->
> ```

## 3. Principle 3: A Page Kept in State Has No URL of Its Own

### Two ways to show a second page

Our shop now needs a home page. It shows the shop title and one product button, `Blue Sneakers`. The user clicks it, the product page appears, and the user copies the link from the address bar.

```page caption="The home page of the shop, at the shop's address: one product to click."
url: shop.example.com
heading: Shop
line: [Blue Sneakers]
```

There are two ways to switch from the home page to the product page. Both show the product page after the click. They differ in one thing: whether the address in the address bar changes.

```jsx title="With useState: a state variable picks the page"
const [~route~, setRoute] = useState('home'); // The current page lives in state

{route === 'home' && <Home />}
{route === 'product' && <Product />}
```

```jsx title="With a router: each page has its own URL"
const router = createBrowserRouter([
  { ~path: '/'~, element: <Home /> }, // The home page lives at /
  { ~path: '/products/1'~, element: <Product /> }, // The product page lives at /products/1
]);
```

**It may look the same, or work the same at first, but it is NOT the same thing!** With either version, the user clicks `Blue Sneakers` and sees the product page. Only with a router does the link lead back to that product. react.dev says it in one line, in a comment of its own example: "Routing in state does not create URLs".

**Routing** decides which page to show for which URL. react.dev: "Routing determines what content or pages to display when a user visits a particular URL." A **router** is the code that ties each URL to a page, and a **route** is one such pair, such as `/products/1` and the product page.

### The shop with the page kept in `useState`

Let's build the first version. The product page moves into its own file, `Product.jsx`. Its code stays the same, and only its function name changes from `App` to `Product`. A new `Home.jsx` shows the shop title and one button:

```jsx title="src/Home.jsx"
export default function Home({ onOpen }) {
  return (
    <>
      <h1>Shop</h1>
      <button ~onClick={onOpen}~>Blue Sneakers</button> {/* Calls the function App passed in */}
    </>
  );
}
```

`App` keeps the current page in state and shows one page at a time (as seen in Lesson 10 and Lesson 12):

```jsx title="src/App.jsx"
import { useState } from 'react';
import Home from './Home.jsx';
import Product from './Product.jsx';

export default function App() {
  const [route, setRoute] = useState(~'home'~); // Every visit starts on the home page

  return (
    <>
      {route === 'home' && <Home onOpen={() => ~setRoute('product')~} />} {/* Changes state, not the URL */}
      {route === 'product' && <Product />}
    </>
  );
}
```

```files title="shop: File Explorer" caption="The shop gains a home page and moves the product page into its own file."
index.html | entry | The one HTML page, with `<title>Shop</title>` and the empty root div
src/
  main.jsx | boundary | Imports `App` and mounts it into `#root`
  App.jsx | parent | Keeps the current page in `route` and shows `Home` or `Product`
  Home.jsx | page | Shows the shop title and one button for `Blue Sneakers`
  Product.jsx | page | The product page of Principle 2, now named `Product`
  api.js | stand-in server | Exports `getProduct`
```

### What the friend receives

**The click works, but the link does not.** The user sees the product page, and the friend sees the home page. Here is what happens, step by step:
1. The user opens the shop at `shop.example.com` and clicks `Blue Sneakers`.
2. `setRoute('product')` runs, and React shows the product page.
3. The address bar still shows `shop.example.com`. No line of our code changed the URL.
4. The user copies that link and sends it to the friend.
5. The friend's browser loads the app from the start, where `useState('home')` begins on the home page. The friend sees the home page, not the sneakers.

```page size=mini

heading: Blue Sneakers
line: $49
```

```page caption="What the friend sees after opening the link from the version with useState: the home page, not the product."
url: shop.example.com
heading: Shop
line: [Blue Sneakers]
```

A bookmark fails the same way. The user bookmarks the product page and opens the bookmark the next day. The app starts again from `useState('home')`, and the home page appears.

### The same shop with a router

A router library ties each page to its own URL. React Router is one of the routers react.dev suggests for an app made with a build tool, together with TanStack Router. It is a library we install with npm. It is not part of React:

```jsx title="src/App.jsx with a router"
import { ~createBrowserRouter~, RouterProvider } from 'react-router'; // Builds the list of routes, one per URL
import Home from './Home.jsx';
import Product from './Product.jsx';

const router = createBrowserRouter([
  { path: '/', element: <Home /> },
  { ~path: '/products/1'~, element: <Product /> }, // The product has its own address
]);

export default function App() {
  return <RouterProvider router={router} />;
}
```

In this version, `App` no longer passes `onOpen` to `Home`. On the home page, the `Blue Sneakers` button becomes a link to `/products/1`. A router gives its own link component for this, which changes the URL without reloading the page.

Now the click changes the address bar to `shop.example.com/products/1`. The friend opens that link, the router finds the route for `/products/1`, and the friend sees the sneakers.

```tree caption="Switching pages with useState vs. with a router: both show the product after a click, only one gives it a URL."
How the shop switches to the product page
- !With `useState` [`route` `setRoute`] | The click changes **state**; the address bar **stays the same** | A shared link or a bookmark opens **the home page**
- +With a router [`createBrowserRouter` `path`] | The click changes the **URL** to **/products/1** | A shared link or a bookmark opens **the product page**
```

### Why a router pulls in a framework

At work, the router is rarely the end of the story:
1. A developer on a Vite app needs a second page and keeps the current page in state, because `useState` is the tool the developer already knows.
2. Clicks work, so the code ships.
3. A user bookmarks a product, and the bookmark opens the home page.
4. The team installs a router.
5. Now the router must also work together with data loading and with code splitting. react.dev says routers "are usually integrated with data fetching", with code splitting, and with the way each page is rendered (code splitting is taught in Lesson 70).

At that point, the team is writing the parts of a framework by hand. That is why react.dev gives this rule of thumb: "if your app needs routing, you would probably benefit from a framework".

> [!PRINCIPLE]
> **Principle 3: Routing: A Page Kept in State Has No URL of Its Own**
>
> *Give every page that a user can share or bookmark its own URL with a router; `useState` can switch what is shown, but it creates no URL.*
>
> When the app picks its page with `useState`, the click changes state and the address bar stays the same. A friend who opens the shared link starts the app from the first state again and sees the home page. A router ties each URL to a page, so `/products/1` always opens the sneakers. Once an app needs routing, react.dev suggests a framework.
>
> **DO THIS:**
> ```jsx
> const router = createBrowserRouter([
>   { path: '/', element: <Home /> },
>   { ~path: '/products/1'~, element: <Product /> }, // A shared link opens the product
> ]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [route, setRoute] = ~useState('home')~; // **WRONG:** for pages users share: every link opens the home page
> ```

## 4. Principle 4: A Loader Starts the Fetch Before the Page Renders

### Two places to start the same fetch

Both versions below call the same `getProduct` and show the same product. They differ in one thing: when the fetch starts.

```jsx title="With useEffect: the fetch starts after the first render"
useEffect(() => {
  ~getProduct().then(setProduct)~; // Waits for the bundle and the first render
}, []);
```

```jsx title="With loader: the fetch starts before the page renders"
export async function ~loader~() { // The router calls this before the page renders
  return getProduct();
}
```

**It may look the same, or work the same at first, but it is NOT the same thing!** Both show `Blue Sneakers` in the end. With the loader, the user waits less, because the fetch does not wait for the page to render first.

### Counting the waits with `useEffect`

**With `useEffect`, every wait starts only after the one before it has ended.** Here is the friend's first visit to the product page made with Vite alone:
1. The browser downloads the HTML file.
2. The browser finds the script tag and downloads the bundle.
3. React renders `Product` for the first time, and the page shows `Loading...`.
4. Only now does the Effect run and call `getProduct()`.
5. One second later, `Blue Sneakers` appears.

react.dev calls this chain a **network waterfall**: "Network waterfalls are caused by fetching data when your app renders instead of in parallel while the code is downloading." The name is an image: like water falling from one step to the next, each request starts only when the step above it is done.

On a bigger page, the waterfall grows longer. The product renders, then its reviews component renders and fetches its own data, and the user sees one `Loading...` after another.

### The same page with a loader

A framework's router offers a **loader**: a function we export from the same file as the page component. The router calls it to get the page's data. react.dev: "On initial load, the router can fetch the data immediately before the route is rendered."

Here is the product page of the shop with React Router used as a framework, in the shape react.dev shows:

```jsx title="The product route in a framework"
import { getProduct } from './api.js';

export async function ~loader~() { // Runs before Product renders
  return getProduct();
}

export default function Product({ ~loaderData~ }) { // Holds { name: 'Blue Sneakers', price: 49 }
  return (
    <>
      <h1>{loaderData.name}</h1>
      <p>${loaderData.price}</p>
    </>
  );
}
```

Two names here come from the framework, not from our code:
- **`loader`**: our code never calls it. The router finds this exported function in the route file and calls it before it renders `Product`.
- **`loaderData`**: our code never passes it. The router passes it to `Product` as a prop (as seen in Lesson 08), and it holds what `loader` returned.

This is the frame of the opening at work: the framework decides when the data loads, and we only fill in `loader`.

Notice what is gone: there is no `useState`, no `useEffect`, and no `Loading...` branch. When `Product` renders, the product is already there.

```tree dir=right caption="When the fetch starts: after the first render in an Effect, or before the render in a loader."
When `getProduct` starts on the friend's first visit
- !With `useEffect` [`useEffect` `setProduct`] | HTML, then bundle, then **Loading...**, then the fetch | **Each wait starts after the one before**: a network waterfall
- +With `loader` [`loader` `loaderData`] | The router starts the fetch **before the route renders** | The fetch runs **while the code is still downloading**
```

react.dev's own comments on the two versions of its example say the same in two lines: "Fetching data in a component causes network waterfalls" and "Fetching data in parallel while the code is downloading".

### What a loader costs

A loader is not free. react.dev: "this requires correctly configuring the loaders in your app and trades off complexity for performance." A framework sets this up for us. On an app made with Vite alone, the team must connect the router and the data loading by hand.

react.dev also gives advice for code that still fetches in Effects: "If you use a framework, use its built-in data fetching mechanism." Without a framework, react.dev suggests a client-side cache such as TanStack Query, SWR, or RTK Query (taught in Lesson 60).

> [!PRINCIPLE]
> **Principle 4: Loader: The Router Starts the Fetch Before the Page Renders**
>
> *A fetch in an Effect starts only after the bundle has loaded and the page has rendered once; a framework's loader starts it before the route renders, in parallel with the code download.*
>
> With `useEffect`, the user waits for the HTML, then the bundle, then the first render with `Loading...`, and only then for the data. react.dev calls this chain a network waterfall. A framework's router calls `loader` before it renders the route and hands the result to the component as `loaderData`, so the component renders with the product already there.
>
> **DO THIS:**
> ```jsx
> export async function ~loader~() { // The router fetches before Product renders
>   return getProduct();
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   ~getProduct().then(setProduct)~; // **WRONG:** in a framework: waits for the bundle and the first render
> }, []);
> ```

## 5. Principle 5: A Framework Can Put the Product into the HTML

### The file with an empty root vs. the file with the product

**A framework can send the finished page inside the HTML file itself.** Then the product is there before any JavaScript runs. Compare the part that matters in the two files the server sends for the same product page:

```html title="With Vite alone: the file the server sends, shortened"
<body>
  ~<div id="root"></div>~ <!-- Empty: JavaScript adds the product later -->
</body>
```

```html title="With a framework that renders on the server: the file the server sends, shortened"
<body>
  ~<h1>Blue Sneakers</h1>~ <!-- Already in the file before any JavaScript runs -->
  <p>$49</p>
</body>
```

Each framework adds its own wrapper tags and script tags around the page. We leave them out here.

**It may look the same, or work the same at first, but it is NOT the same thing!** Once the JavaScript has loaded, both shops show `Blue Sneakers` in the developer's browser. Only the second file shows it to a crawler, and to a user whose JavaScript has not loaded yet.

### Who made that HTML

Our code did not make it. The framework did. It ran our components with React, together with the data from `loader`, and wrote the result into the file. A framework can do this at two moments:
- **Server-side rendering, SSR:** the framework makes the HTML on the server, for every request. When the friend opens the link, the server runs `loader`, renders `Product`, and sends the finished file.
- **Static site generation, SSG:** the framework makes the HTML files once, during the build. The finished files then sit on a static host or a CDN: servers that only hand out ready files and never run our code.

Both give a file that already holds the product. They differ in when the file is made. react.dev gives an example of each: a Terms of Service page or documentation can be static, "while a page with a content feed might perform best with server-side rendering".

```tree caption="Three ways a framework can make a page, chosen for each route."
How a framework can make each route
- +Server-side rendering [`SSR`] | HTML made **on the server**, for **every request** | Fits a page whose data **changes often**, such as a content feed
- +Static site generation [`SSG`] | HTML made **once, at build time** | Fits a page that **rarely changes**, such as a Terms of Service page
- +In the browser only [`SPA`] | The file holds an **empty root**, as with Vite | Fits a page that **only signed-in users** open
```

A framework makes this choice for each route, not for the whole app. react.dev: "these frameworks allow you to add server-side rendering on a per-route basis, when it makes sense for your use case." The product page can render on the server, while the account page stays in the browser only.

### What the chat app and the slow phone receive now

The team moves the shop to a framework, and the product page becomes the route with a `loader` from Principle 4. Here is what changes:
1. The user pastes the product link into a chat app.
2. The chat app's crawler downloads the HTML file, which now holds `Blue Sneakers`.
3. The crawler can now read the product name without running any JavaScript. To show that name as the title of the preview card, each page also needs its own `<title>` in that file (taught in Lesson 121).
4. The friend opens the link on a slow phone and sees `Blue Sneakers` before the bundle has loaded.
5. The buttons on the page start to work only after the JavaScript loads. react.dev: "The user will spend some time looking at the server-generated HTML before your JavaScript code loads."

That last step has a name. Once the bundle arrives, React attaches itself to the HTML that is already on the page, instead of drawing it again. This is called **hydration** (taught in Lesson 104). In a framework app, we do not even write `createRoot` ourselves. react.dev: "If you use a framework, it might do this call for you."

This is why server rendering is not only about search engines. react.dev: server rendering sends "a full HTML document which produces a faster First Contentful Paint". First Contentful Paint is the moment the user first sees content on the screen.

### A framework does not require a server

**Yes, a framework can run with no server at all.** react.dev: "Full-stack frameworks do not require a server." The recommended frameworks also support client-only apps and static site generation, and they "can be deployed to a CDN or static hosting service without a server". Next.js also supports a static export, which needs no server.

Here is the mistake this clears up:
1. A team building an internal dashboard hears "framework" and thinks "server".
2. The team picks Vite to avoid running a server.
3. Months later, the dashboard gains public pages that must show their content to crawlers.
4. Now the team must add server rendering to a Vite app by hand. react.dev warns that this "can be very complex to set up and maintain".

react.dev describes the other path: frameworks "allow you to start with a client-only app, and if your needs change later, you can opt-in to using server features on individual routes without rewriting your app."

Server rendering has its own cost. react.dev: generating pages on the server "incurs additional cost and takes time to generate", which can increase the Time to First Byte. The Time to First Byte is the wait before the browser receives the first byte of the page (this cost is weighed in Lesson 156).

> [!PRINCIPLE]
> **Principle 5: Server Rendering: A Framework Can Put the Product into the HTML, Route by Route**
>
> *A framework can render a route on the server or at build time, so the file that leaves the server already holds the page's content; it chooses this per route, and it does not require a server.*
>
> With server-side rendering, the framework makes the HTML for every request. With static site generation, it makes the HTML once during the build, and a static host can send it with no server. Either way, a crawler finds the product in the file, and a user on a slow phone sees it before the JavaScript loads. A route that does not need this can stay client-only, as with Vite.
>
> **DO THIS:**
> ```html
> <body>~<h1>Blue Sneakers</h1>~<p>$49</p></body> <!-- Rendered by the framework: the product is in the file -->
> ```
>
> **DO NOT DO THIS:**
> ```html
> <body>~<div id="root"></div>~</body> <!-- **WRONG:** for a shared product page: the file holds no product -->
> ```

## 6. Principle 6: An Admin Tool Behind a Login Can Stay on Vite

### The public shop vs. the internal admin tool

Not every app needs a framework. react.dev's own example of an app that can stay on Vite is an internal admin tool. Only staff who have signed in open it, and its first page reads `Welcome to the Admin Tool!`:

```jsx title="src/App.jsx: react.dev's admin tool"
export default function App() {
  return (
    <div>
      ~<h1>Welcome to the Admin Tool!</h1>~ {/* Seen only by signed-in staff, after the JavaScript runs */}
    </div>
  );
}
```

```page caption="The first page of the internal admin tool."
heading: Welcome to the Admin Tool!
```

Both apps are React apps, and both run fine on Vite at first. They differ in who opens their pages, and how:
- **The public shop:** users share its pages in chat apps, crawlers read them, and people open them on slow phones. Each product needs its own URL and HTML that already holds the product.
- **The internal admin tool:** nobody shares its pages, no crawler reads them, and staff open it after signing in. An empty root and a short `Loading...` hurt nobody here.

So the deciding questions are simple:
1. Must any page show its content before the JavaScript runs?
2. Do the pages need their own URLs, loaders, and code splitting?

When the answer to both is no, Vite is enough.

```tree caption="The one difference between the public shop and the admin tool that decides the tool."
Which tool fits the app
- +The public shop [`Blue Sneakers`] | Links are **shared**, read by **crawlers**, opened on **slow phones** | Needs **URLs per page** and **HTML with content**: a **framework**
- +The internal admin tool [`Welcome to the Admin Tool!`] | Opened only by **signed-in staff**, after the JavaScript runs | Needs none of that: **Vite** is enough
```

### When react.dev says a build tool fits

react.dev gives three reasons to start from scratch with a build tool: "your app has constraints not well-served by existing frameworks, you prefer to build your own framework, or you just want to learn the basics of a React app".

It adds a fourth case on another page: adding React to part of an existing site, such as a page made with Rails. There, Vite builds the React part, and `createRoot` mounts it on one element of that page. Once the whole page is made with React, react.dev recommends moving to a framework.

It also gives a warning: "You should only choose this option if you are comfortable tackling these problems on your own, or if you're confident that you will never need these features."

### What Vite costs on a public site

Here is the mistake behind that warning:
1. A developer picks Vite for a new public site, because react.dev's tutorial and our own earlier lessons used it.
2. The site grows more routes, more data, and more shared links.
3. The team adds a router, then a data library, then code splitting, then tries server rendering.
4. Each fix touches the others. react.dev: "Many limitations you'll hit can be difficult to solve as each problem is interconnected with the others."

react.dev has a name for this result: starting from scratch is "often the same as building your own adhoc framework". **Ad hoc** means made for one case only. The team ends up with its own framework, built one problem at a time, and nobody outside the team maintains it.

A framework has a cost too, and it is not a server bill. react.dev: frameworks "impose some opinions about structuring your app", the same way build tools do. These opinions are rules, such as where each route file goes and how a page loads its data. For the admin tool, those rules buy nothing.

> [!PRINCIPLE]
> **Principle 6: Choosing the Tool: A Client-Only App Behind a Login Can Stay on Vite**
>
> *Start a new app with a framework; choose a build tool when the app is client-only and will never need URLs per page or HTML with content, when React goes into part of an existing page, when the team wants to build its own framework, or when the goal is to learn.*
>
> The tool follows what the pages need. A public shop needs its products in the HTML and a URL for each page, which a framework gives. An internal admin tool opened only by signed-in staff needs neither, so Vite is enough. Picking Vite for a public site means building an ad hoc framework later, one problem at a time.
>
> **DO THIS:**
> ```jsx
> export default function App() {
>   return <h1>~Welcome to the Admin Tool!~</h1>; // Behind a login: Vite alone is enough
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   return <h1>~Blue Sneakers~</h1>; // **WRONG:** a public product page that users share, on Vite alone: its HTML file holds no product
> }
> ```

## Putting All Six Principles Together

### The complete shop made with Vite alone

Here is the complete shop as we built it with Vite alone, with the current page kept in state:

```html title="index.html"
<!DOCTYPE html>
<html lang="en">
  <head>
    <title>~Shop~</title> <!-- One title for every page: the preview card shows Shop -->
  </head>
  <body>
    ~<div id="root"></div>~ <!-- Empty until the JavaScript runs -->
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>
```

```jsx title="src/main.jsx"
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

~createRoot(document.getElementById('root'))~.render(<App />); // Fills the empty root in the browser
```

```js title="src/api.js"
export function ~getProduct~() { // Our stand-in server: answers after one second
  return new Promise(resolve => {
    setTimeout(() => resolve({ name: 'Blue Sneakers', price: 49 }), 1000);
  });
}
```

```jsx title="src/App.jsx"
import { useState } from 'react';
import Home from './Home.jsx';
import Product from './Product.jsx';

export default function App() {
  const [route, setRoute] = ~useState('home')~; // The page lives in state: no URL per page

  return (
    <>
      {route === 'home' && <Home onOpen={() => setRoute('product')} />}
      {route === 'product' && <Product />}
    </>
  );
}
```

```jsx title="src/Home.jsx"
export default function Home({ onOpen }) {
  return (
    <>
      <h1>Shop</h1>
      <button ~onClick={onOpen}~>Blue Sneakers</button> {/* Switches to the product page */}
    </>
  );
}
```

```jsx title="src/Product.jsx"
import { useState, useEffect } from 'react';
import { getProduct } from './api.js';

export default function Product() {
  const [product, setProduct] = useState(null);

  useEffect(() => {
    ~getProduct().then(setProduct)~; // Starts after the bundle and the first render
  }, []);

  if (!product) {
    return <p>Loading...</p>;
  }

  return (
    <>
      <h1>{product.name}</h1>
      <p>${product.price}</p>
    </>
  );
}
```

In a framework, the product page shrinks to the route of Principle 4: a `loader` that the router calls first, and a `Product` that reads `loaderData`.

### What happens on the friend's first visit, in order

When the friend opens the product link, the two shops do their work in a different order:

```tree dir=right caption="The order of work on the first visit: the shop made with Vite alone vs. the shop made with a framework."
The friend opens the product link
- !With Vite alone [`index.html` `main.jsx` `App` `Home` `Product`] | 1. The server sends the file with an **empty root** | 2. The browser downloads the **bundle** | 3. React calls `App`, then `Home`: the link holds no product address, so the friend lands on **the home page** | 4. After a click, React calls `Product`, which shows **Loading...** | 5. The Effect calls `getProduct`, and one second later **Blue Sneakers** appears
- +With a framework rendering on the server [`loader` `Product`] | 1. The server calls `loader`, which calls `getProduct` | 2. The server renders `Product` with `loaderData` | 3. The server sends a file that **already holds Blue Sneakers** | 4. The browser downloads the bundle, and React **hydrates** the page | 5. The address bar shows **/products/1**
```

| Question | With a build tool such as Vite | With a full-stack framework |
| :--- | :--- | :--- |
| **What does the first HTML file hold?** | Only `<div id="root"></div>`; JavaScript adds the content in the browser | The finished page, made on the server or at build time, or an empty root where we choose |
| **Which URL shows which page?** | Our own code; `useState` creates no URL, so we add a router ourselves | The framework's router: each page has its own URL |
| **When does the data load?** | In an Effect, after the bundle and the first render | In a loader, before the route renders |
| **Does it need a server?** | No | No; it can also run client-only or as static files |
| **When does it fit?** | A client-only app such as an admin tool, React in part of an existing page, a team building its own framework, or learning | A new app or website, especially one that needs routing |
| **What does it cost?** | Every missing piece becomes part of our own ad hoc framework | Its rules about how to structure the app |

## For the Interview

> **The Interview Question:** How do you choose between a full-stack framework and a standalone build tool?

### How to Answer Clearly in 30 Seconds

"React is a library. It draws components, but it does not decide what the first HTML holds, which URL shows which page, or when data loads. A build tool such as Vite turns JSX into JavaScript, bundles the code, runs a development server, and builds for production. It starts as a client-only single-page app. So the HTML holds an empty root, social media crawlers usually see no content, and data fetched in an Effect starts only after the bundle and the first render. A full-stack framework such as Next.js or React Router adds routing, loaders that fetch before the route renders, code splitting, and HTML made on the server or at build time, chosen per route. It does not require a server. So for a new app or a public site, I pick a framework, following react.dev's rule of thumb: if the app needs routing, it probably benefits from a framework. I pick Vite for a client-only app such as an internal admin tool, for React inside part of an existing page, or for learning. I never start a new app with Create React App, which is deprecated."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Doesn't a framework force you to pay for and run a server?"**
   **No.** react.dev says it directly: "Full-stack frameworks do not require a server." The recommended frameworks support client-only apps, single-page apps, and static site generation, and they can be deployed to a CDN or a static host. Next.js also supports a static export. A framework lets us start client-only and add server rendering later, on the routes that need it, without rewriting the app. The real cost of a framework is its rules about how to structure the app.
2. **"Isn't server rendering just for SEO?"**
   **No.** react.dev calls that a common misunderstanding. Server rendering sends a full HTML document, so the user sees the content before the JavaScript loads, which gives a faster First Contentful Paint. It also lets chat and social apps read the page from the HTML, because their crawlers usually do not run JavaScript. The cost is server work on every request, which can raise the Time to First Byte. So a framework lets us choose server rendering, static generation, or client-only rendering for each route.
3. **"Why is fetching in `useEffect` slower than fetching in a loader?"**
   An Effect runs only after the component has rendered, and the component renders only after the bundle has downloaded. So the user waits for the HTML, then the bundle, then the first render with `Loading...`, and only then does the fetch start. react.dev calls this a network waterfall. A framework's loader lets the router start the fetch before the route renders, in parallel with downloading the code, and the component receives the result as `loaderData`. Without a framework, react.dev points to a client-side cache such as TanStack Query or SWR.
