## How React Queues State Updates from an Event Handler

### Passing `count + 1` three times vs. passing an updater function

Suppose a counter starts at `0`. When the user clicks a button, the click handler calls `setCount` three times in a row to add three points.

First, look at what happens when the handler passes `count + 1` on all three lines:

```jsx title="Way 1: Passing count + 1 three times in one click handler"
const [count, setCount] = useState(0);

function handleThree() {
  ~setCount(count + 1);~ // 1. count is 0 here, so this passes 0 + 1 -> 1
  ~setCount(count + 1);~ // 2. count is STILL 0 here, so this also passes 0 + 1 -> 1
  ~setCount(count + 1);~ // 3. count is STILL 0 here, so this also passes 0 + 1 -> 1
}
```

Now compare that with passing a small arrow function to `setCount` on all three lines instead:

```jsx title="Way 2: Passing an updater function c => c + 1 three times"
const [count, setCount] = useState(0);

function handleThree() {
  ~setCount(c => c + 1);~ // 1. Queues a function: takes 0 and returns 1
  ~setCount(c => c + 1);~ // 2. Queues a function: takes 1 and returns 2
  ~setCount(c => c + 1);~ // 3. Queues a function: takes 2 and returns 3
}
```

When you click the button in Way 1, the counter on the screen moves from `0` to **`1`**. When you click the button in Way 2, the counter moves from `0` to **`3`**!

Look at the three silent confusions that trip developers up here:
- **First, writing `count + 1` three times looks like three additions, but it is NOT the same thing!** Inside this render's snapshot, `count` stays at `0` from the first line of the handler to the last. Each line calculates `0 + 1` and hands React the finished number `1`. React hears *"make the count one"* three times in a row, so one click leaves the screen at `1`.
- **Second, passing `count + 1` and passing the arrow function in Way 2 are NOT the same thing!** When a button calls `setCount` only once per click, both ways give the same result on screen. Yet passing `count + 1` calculates a single number right now from this render's fixed snapshot. Passing the arrow function hands the function itself to React so React can call it later, feeding each function the result of the update right before it.
- **Third, the screen not changing between two setter lines looks as if React is slow or the first setter failed, but it did NOT fail!** React waits until every line of the event handler has finished before it renders the component once.

Look at the four terms you will hear in every React team and interview:
- **What is "batching"?** In everyday English, a **batch** is a group of items handled together in one go. You bake a whole tray of cookies at once instead of one cookie at a time. Think of a polite **waiter** at a restaurant. A waiter does not run to the kitchen the moment you name your first dish. The waiter listens until you finish your entire order, and even lets you change your mind, before walking to the kitchen once. In React, **batching** means React listens to every setter call in your event handler and then renders once at the end.
- **What is the update "queue"?** In everyday English, a **queue** is a waiting line where items wait their turn in the exact order they arrived. For each state variable, React keeps an update **queue** like a stack of order slips that it reads from top to bottom during the next render.
- **What is an "updater function"?** When you pass a plain value like `1` to a setter, that order slip says *"replace the value with one,"* ignoring earlier slips. When you pass an arrow function like the one in Way 2 to a setter, React calls that function an **updater function**. Its order slip says *"take whatever the running result is by now and add one to it."*
- **What is the "pending state"?** While React walks the queue during the next render, the running result produced by the earlier slips is called the **pending state**. React passes that pending state into the parameter `c` of the next updater function in line:

```tree caption="What sits in React's update queue when you pass count + 1 three times vs. when you pass an updater function three times."
Three setter calls in one click starting from `0`
- !Way 1: Pass the value `count + 1` three times | Every line reads the **same snapshot `0`** and queues **replace with `1`** | React reads all three slips and renders **`1`**
- +Way 2: Pass an updater function three times | Each queued function receives the **pending state** from the slip before it | Steps from `0` to `1`, then `2`, then **`3`** in one render
```

### Why a scoreboard's `+3` button only adds one point

Imagine watching a live basketball game where a digital scoreboard tracks the home team's points. At the start of the game, the board shows a score of zero and says that the game has started. Below the board sit three buttons for the scorekeeper: a one-point free-throw button, a two-point basket button, and a `+3` shot button.

To avoid typing the same score update inside all three buttons, the developer writes one small **helper function**. A helper function is just a shared function inside the component that several handlers can call. This helper adds one point to the score. The first button calls the helper once, the second button calls it twice, and the `+3` button calls it three times.

Yet when a player makes a three-point shot and the scorekeeper clicks `+3`, the score goes up by **one point** instead of three!

```tree caption="What the scorekeeper expects when clicking +3 vs. what happens when the helper queues three value replacements from the same snapshot."
Clicking `+3` on the basketball scoreboard
- +What the scorekeeper expects [`+3` calls the one-point helper three times] | Three calls should add **three points** to the home score | Board should move from `Home: 0` to **`Home: 3`**
- !What happens with value replacement [`setScore` given `score + 1`] | All three calls read the **same snapshot `0`** and queue **replace with `1`** | Board moves from `Home: 0` to **`Home: 1`** on a three-pointer!
```

### Three ways to give a state setter its next value

In React, you have three ways to give a state setter its next value inside an event handler, and each way fits a different job.

Look at all three ways side by side:

```jsx title="Three ways to give setScore the next value"
function ScoreWays() {
  const [score, setScore] = useState(0);

  function handleDirect() {
    ~setScore(score + 3);~ // 1. Direct value: fits when this state is updated once in the click
  }

  function handleVariable() {
    const ~nextScore = score + 3~; // 2. Saved in a variable first: fits when the handler needs nextScore right away
    setScore(nextScore);
    console.log(nextScore);
  }

  function addPoint() {
    ~setScore(s => s + 1);~ // 3. Updater function: fits when several updates of score are queued in one click
  }
}
```

Here is how to choose among those three ways in daily coding:
1. **Way 1, a value calculated directly from the snapshot**: Passing `score + 3` directly to `setScore` fits whenever an event updates that state variable only **once** per click.
2. **Way 2, a value saved in a local variable first**: Storing `score + 3` in a constant named `nextScore` fits when you update that state once and your running handler also needs that new number right away.
3. **Way 3, an updater function**: Passing an updater function to `setScore` fits when the next value builds on the previous value and one click queues several updates. When one state variable must be calculated from a *different* state variable, teams instead combine them into a **reducer**, which a later lesson covers.

```tree caption="The three ways to give a state setter its next value, and when each way fits."
Three ways to pass the next state to `setScore`
- +1. Direct value from the snapshot [`score + 3`] | Best when the handler updates `score` **only once** per click | Simple and direct for single updates
- +2. Value saved in a variable first [`const nextScore = score + 3`] | Best when the **running handler** also needs the new number right away | Passes `nextScore` to both `setScore` and the lines below it
- +3. Updater function [`s => s + 1`] | Best when **multiple updates of `score`** are queued before the next render | Each queued function builds on the **pending state** before it
```

### Short arrow functions and five facts from earlier lessons

Before we write our first updater function, look at a small JavaScript shortcut you will see in every React codebase: the **short arrow function**.

In plain JavaScript, when a function takes **one parameter** and only **returns a single calculation**, you can write it in a short form. You leave out the word `function`, the parameter parentheses, the curly braces, and the word `return`:

```js title="Plain JavaScript: a full function vs. a short arrow function"
const addOneFull = ~function (s) { return s + 1; }~; // 1. Full function syntax: takes s and returns s + 1
const addOneShort = ~s => s + 1~; // 2. Exact same thing: takes s and returns the value after =>!
```

**Yes, those two functions are the exact same thing!** The parameter `s` on the left of the arrow is the input, and the calculation `s + 1` on the right is automatically returned.

Remember too how we pass an event handler to a button tag without parentheses so the browser calls it later. Passing an updater function to `setScore` works the exact same way. You write the arrow function inside `setScore` without calling it yourself, handing the function to React so React can call it during the next render.

This lesson also builds on five facts from earlier lessons:
- **State variables and setters**: Calling `useState` stores a value inside React. It gives back the current state variable and a setter function, such as `score` and `setScore`.
- **Trigger, render, and commit**: Calling a setter queues a render. React calls your component function again to ask for its updated JSX, then commits the changes to the browser DOM.
- **State as a snapshot**: Every render gets its own fixed value for `score`. Calling `setScore` never changes the variable `score` inside the event handler that is currently running.
- **Purity and `<StrictMode>`**: A **pure function** only calculates its result from its inputs and changes nothing outside. In development, `<StrictMode>` calls pure component functions twice and keeps both `console.log` lines in the Console, while it **never** calls event handlers twice.
- **The browser's `alert` box**: Calling the built-in browser function `alert` opens a pop-up message on the screen. It pauses the running JavaScript function on that exact line until the user clicks `OK`.

### Five Principles of Batching and Updater Functions

**PRINCIPLES:** When an event handler calls a state setter, React does not stop the handler and redraw the screen right away. Instead, React adds each update to a queue and processes the whole queue in one render after the handler finishes. Following what goes into that queue and when React runs it gives us five practical rules:
1. **Principle 1: React Batches All Setter Calls in One Handler into One Render**: React runs every line of an event handler first, even code written after the setter calls, and then renders the page once with all state variables updated together. Each separate user click is handled on its own.
2. **Principle 2: A Value Entry Replaces the Queued State**: Passing a calculated value to a setter adds a replacement slip to the queue. Every line in the handler reads the same snapshot, so calling that setter three times queues the same replacement number three times.
3. **Principle 3: An Updater Function Continues from the Pending State**: Passing a function to a setter adds the function itself to the queue. During the next render, React calls each queued updater in order and passes it the pending state from the step before it, so three updater calls add three.
4. **Principle 4: React Walks the Queue in Order**: When a queue holds both value replacements and updater functions for the same state variable, React walks them in the exact order they were called. An updater builds on the running result, whereas a value replacement ignores and wipes out every update queued before it.
5. **Principle 5: Updaters Run During Render and Must Be Pure**: React decides when to call updater functions, mostly during the next render, and calls each one twice in Strict Mode during development. Every updater must be pure with zero side effects or logs inside it, and you need one whenever several updates of the same state stack up.

Here is the complete overview of all five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Batching: One Render After the Whole Handler Finishes** | Developers expect the screen to change between two setter lines or while a pop-up is still open; interviewers ask why updating two state variables does not trigger two renders. | React runs the entire event handler first, batches all its setter calls together, and updates the screen in one single render at the end. |
| **Principle 2** | **Value Updates Replace: Three Snapshot Calls Add One** | Calling a one-point helper three times in one click only raises the score by one point, with zero Console warnings. | Passing a value to a setter queues a replacement; three calls from the same snapshot queue the same number three times. |
| **Principle 3** | **Updater Functions Continue from the Pending State** | An updater function lets multiple updates of the same state in one event build on each other; reading the outer snapshot name inside the updater breaks the fix. | Pass a function to the setter so React calls it during the next render with the pending state from the update before it. |
| **Principle 4** | **Queue Order: A Value Placed After Updaters Wipes Them Out** | Mixing a value helper and an updater helper for the same state gives different totals depending on which line runs first. | React walks the queue from top to bottom: an updater adds to the running result, while a plain value replaces the running result and ignores earlier slips. |
| **Principle 5** | **Keep Updaters Pure and Use Them When Updates Stack Up** | Putting a Console log or side effect inside an updater runs twice per update in Strict Mode development; interviewers ask whether every setter needs an updater. | Keep updaters pure because React decides when they run, mostly during render; use an updater when several updates of the same state can be queued before the next render. |

## 1. Principle 1: Batching: React Runs the Whole Handler First, Then Renders Once

### Why calling two setters in one click does not cause two renders

Before we build our scoreboard, look at a small component with two state variables. The counter `count` starts at zero, and `label` starts with the text *"Not clicked"*. Inside the button's click handler, we call both setters and then open a browser `alert` box on the last line:

```jsx title="Calling two state setters and alert inside one click handler"
function CounterAlert() {
  const [count, setCount] = useState(0);
  const [label, setLabel] = useState('Not clicked');

  function handleClick() {
    ~setCount(count + 1);~ // 1. Queues an update for count: screen does NOT change yet
    ~setLabel('Clicked');~ // 2. Queues an update for label: screen STILL does not change
    ~alert('Done');~ // 3. Pauses handleClick with the old screen still visible behind the pop-up!
  }

  return <button onClick={handleClick}>{label}: {count}</button>;
}
```

Look at two things that surprise beginners when they click that button:
- **First, writing two setter calls one after the other looks like it should update the screen twice, once for `count` and a second time for `label`. It may look like two screen updates, but it is NOT two renders!** React waits until `handleClick` finishes and combines both state changes into **one single render**.
- **Second, while the `'Done'` pop-up box is sitting open on the screen, both `setCount` and `setLabel` have already run, yet the button behind the pop-up still says `'Not clicked: 0'`! It looks as if the setters failed or got stuck, but they did NOT fail!** Because `alert` pauses `handleClick` on line 3, the handler has not finished yet. Like the waiter who stays at your table until you finish your whole order, React waits until you click `OK` and `handleClick` returns before rendering:

```tree dir=right caption="What happens during handleClick while alert is open vs. after the handler finishes."
One click on `CounterAlert`
- +While `alert` is open [lines 1 and 2 have run, line 3 is paused] | Both updates sit waiting in React's queues | Screen behind the pop-up **still shows `Not clicked: 0`**
- +After clicking `OK` [`handleClick` finishes its last line] | React batches both updates into **one render** | Screen updates to **`Clicked: 1` all at once**
```

### Building the scoreboard with two state variables in one click

Now let us build our basketball scoreboard project and watch this exact behavior on the page.

First, our main application file imports the scoreboard component and renders its tag:

```jsx title="src/App.jsx" startLine="1"

  return <Scoreboard />;

```

Next, in the scoreboard file, we store the score and the latest play in state. We also write a three-point handler that updates both values and opens a pop-up:

```jsx title="src/components/Scoreboard.jsx" startLine="1"
export default function Scoreboard() {

    ~setScore(score + 3);~ // 1. Adds "replace score with 3" to the score queue
    ~setLastPlay('Three-pointer');~ // 2. Adds "replace lastPlay with 'Three-pointer'" to the lastPlay queue
    ~alert('Three points for Home!');~ // 3. Opens pop-up and pauses handleThree before React renders!

```

Below the handler, the scoreboard returns the heading, the two text lines, and the three-point button:

```jsx title="src/components/Scoreboard.jsx" startLine="13"
      ~<button onClick={handleThree}>+3</button>~ {/* 4. Clicking +3 runs handleThree */}
    </section>
  );
}
```

Watch what happens in order when the scorekeeper clicks the `+3` button:
1. Before the click, the scoreboard displays `Home: 0` and *"Last play: Game start."*
2. The scorekeeper clicks `+3`. The browser pop-up saying *"Three points for Home!"* opens right away.
3. While that pop-up is open, the scoreboard behind it still says `Home: 0` and *"Last play: Game start"*! Thinking the setters are broken, a beginner often tries moving the `alert` line around.
4. The scorekeeper clicks `OK` to close the pop-up. That lets `handleThree` finish its last line, and the scoreboard changes to `Home: 3` and *"Last play: Three-pointer"* at the exact same moment!

### Why React waits for the handler to return before rendering

Look closely at `handleThree` above. Nothing in our code tells React *"now call `Scoreboard` again and redraw the page."* Who starts the render, and why did it wait until after the pop-up closed?

React starts the render itself, and it always waits for the running event handler to return first. Follow what JavaScript and React do step by step on that click:
1. Clicking the three-point button starts `handleThree` in the render where `score` is zero and the play text says *"Game start."*
2. Line 1 calls `setScore` with `0 + 3`. React places that update in the queue for `score` and leaves the screen untouched.
3. Line 2 calls `setLastPlay` with `'Three-pointer'`. React places that update in the queue for `lastPlay` and still leaves the screen untouched.
4. Line 3 calls `alert`. The browser opens the pop-up box and pauses JavaScript right on line 3 until the user clicks `OK`.
5. When the user clicks `OK`, `handleThree` finishes and returns. React sees that the handler is done, calls `Scoreboard` **once** with the new values, and commits both lines to the DOM together:


### Why React batches inside one click, and never across separate clicks

Waiting until the end of the event handler to process every setter call in one render is called **batching**. Batching solves two problems at once:
- **First, your app runs much faster**: Even if one click handler updates several state variables across multiple components, React re-renders only once at the end instead of re-rendering after every setter call.
- **Second, the user never sees a "half-finished" screen**: Without batching, calling `setScore` before `setLastPlay` would briefly show the new score paired with the old play text. Batching guarantees that both updated lines appear together in the same render.

Does React ever batch two **separate** button clicks together? **No!** React never batches across multiple intentional user events like separate clicks. Every click is handled on its own, and React finishes rendering the first click before the next click runs. If a user's first click disables a submit button on a form, that button is already disabled before a second click can submit the form again. When code must force an earlier DOM update inside a handler, React provides a helper named `flushSync`, which a later lesson covers.

```tree caption="How React batches multiple setter calls inside one click vs. how it handles two separate user clicks."
What React batches vs. what React keeps separate
- +Multiple setter calls in ONE click [`setScore` and `setLastPlay` in `handleThree`] | React waits until the **entire handler finishes** | Processes both updates in **1 single render** with **0 half-finished screens**
- +Two SEPARATE user clicks [1st click, then 2nd click] | React **never** batches across separate intentional clicks | The **1st click finishes its render** before the **2nd click** runs
```

> [!PRINCIPLE]
> **Principle 1: Batching: React Runs the Whole Handler First, Then Renders Once**
>
> *React waits until every line of an event handler has finished before processing its state updates in one single render, and handles each separate click on its own.*
>
> Calling a state setter does not redraw the screen on that line. It only places an update into React's queue while your event handler keeps running. Even if you call several setters for different state variables and run more code after them, the screen stays untouched until the handler returns. Only then does React batch all the queued updates into one render so the page updates once without ever flashing a half-finished mix of old and new values.
>
> **DO THIS:**
> ```jsx
> function handleThree() {
>   ~setScore(score + 3);~ // 1. Queued for the next render
>   ~setLastPlay('Three-pointer');~ // 2. Batched with setScore into ONE render after handleThree finishes
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleThree() {
>   setScore(score + 3);
>   setLastPlay('Three-pointer');
>   ~alert('Three points for Home!');~ // **WRONG:** expecting the screen behind alert to show 3 before handleThree finishes!
> }
> ```

## 2. Principle 2: Value Updates Replace: Three Snapshot Calls Queue the Same Number

### Why passing `number + 1` three times is the exact same thing as passing `1` three times

Now look at what happens when one event handler calls the **same** state setter three times with a calculated value. Suppose `number` starts at `0`, and our button handler runs these three lines:

```jsx title="What you write: three calls with number + 1"
const [number, setNumber] = useState(0);

function handleClick() {
  ~setNumber(number + 1);~ // 1st call in this render where number is 0
  ~setNumber(number + 1);~ // 2nd call in the same render where number is STILL 0
  ~setNumber(number + 1);~ // 3rd call in the same render where number is STILL 0
}
```

Because `number` is locked at zero for this entire render snapshot, substitute `0` on each of those three lines:

```jsx title="What JavaScript actually passes to setNumber when number is 0"
function handleClick() {
  ~setNumber(1);~ // 1st slip added to the queue: "replace number with 1"
  ~setNumber(1);~ // 2nd slip added to the queue: "replace number with 1"
  ~setNumber(1);~ // 3rd slip added to the queue: "replace number with 1"
}
```

Look closely at those two code blocks:
- **Writing `number + 1` inside `setNumber` looks like an instruction to add one, but it is NOT an instruction to add one!** JavaScript calculates `0 + 1` **before** calling `setNumber`, so React never sees a plus sign. React only receives the finished number `1`.
- **In the render where `number` is `0`, passing `number + 1` three times and passing `1` three times are the exact same thing!** Passing any non-function value to a setter adds a slip to the queue that says **"replace with that value,"** ignoring earlier slips. After all three lines run, the queue holds three identical slips that all say *"replace with `1`"*! When React renders after the handler, the screen changes from `0` to `1`:

```tree dir=right caption="How three calls with number + 1 in the render where number is 0 queue three identical replacement slips."
One click when `number` is `0`
- +1. First call [`0 + 1`] | Hands `1` to `setNumber` | Queue slip 1: **replace with `1`**
- +2. Second call [`0 + 1`] | Reads the **same snapshot `0`** and hands `1` to `setNumber` | Queue slip 2: **replace with `1`**
- +3. Third call [`0 + 1`] | Reads the **same snapshot `0`** and hands `1` to `setNumber` | Queue slip 3: **replace with `1`** -> next render shows **`1`!**
```

### Mistake: Calling a value-based helper three times in one click

Let us see how this trap appears in our basketball scoreboard. We remove the pop-up from Principle 1 and add the free-throw button and the two-point button beside `+3`.

To avoid repeating the score update in every button, the developer writes one `addPoint` helper and calls it in the free-throw handler:

```jsx title="src/components/Scoreboard.jsx" startLine="1"
import { useState } from 'react';

export default function Scoreboard() {
  const [score, setScore] = useState(0);
  const [lastPlay, setLastPlay] = useState('Game start');

  function addPoint() {
    ~setScore(score + 1);~ // **WRONG:** calculates score + 1 from the same snapshot every time addPoint runs in one click!
  }

  function handleOne() {
    addPoint();
    setLastPlay('Free throw');
  }
```

Below the free-throw handler, the two-point handler calls `addPoint` twice, and the three-point handler calls `addPoint` three times while logging the score after each call:

```jsx title="src/components/Scoreboard.jsx" startLine="16"
  function handleTwo() {
    addPoint();
    addPoint();
    setLastPlay('Two-pointer');
  }

  function handleThree() {
    ~addPoint();~ // 1st call: queues "replace with score + 1"
    console.log(score);
    ~addPoint();~ // 2nd call: reads the exact same score snapshot and queues the same number again!
    console.log(score);
    ~addPoint();~ // 3rd call: reads the exact same score snapshot a 3rd time!
    console.log(score);
    setLastPlay('Three-pointer');
  }
```

Finally, the scoreboard renders the heading, the two text lines, and all three buttons:

```jsx title="src/components/Scoreboard.jsx" startLine="32"
  return (
    <section>
      <h1>Scoreboard</h1>
      <p className="score">Home: {score}</p>
      <p className="last-play">Last play: {lastPlay}</p>
      <button onClick={handleOne}>+1</button>
      <button onClick={handleTwo}>+2</button>
      <button onClick={handleThree}>+3</button>
    </section>
  );
}
```

Watch what happens when the scorekeeper tests the three buttons during the game:
1. First, the scorekeeper clicks `+1` for a free throw. Because `handleOne` calls the helper only once, the board moves from zero to `Home: 1` with the free-throw label. Everything seems to work!
2. Next, with the board at `Home: 1`, a player hits a three-pointer and the scorekeeper clicks `+3`. The play line updates to three-pointer, **but the score only rises to `Home: 2` instead of `Home: 4`!**
3. Next, the scorekeeper clicks `+2`. The score only rises to `Home: 3` instead of `Home: 5`! Every button on the scoreboard adds only one point, and the Console shows zero warnings.
4. Look at the Console panel after clicking `+3` from a starting score of one. All three `console.log` lines print `1`, the starting score before the click!

### Why three `addPoint` calls only add one point

Look at the scoreboard code above. Our file has no queue array in it, only three calls to `addPoint`. Where is the queue, and why did three calls to `addPoint` only move the score from one to two?

React keeps that update queue internally for `score`. Here, two rules from React work together. First, **state as a snapshot** keeps `score` fixed during the click. Second, **batching** waits until all three `addPoint` calls have finished before rendering.

Follow what happens step by step when the scorekeeper clicks `+3` while `score` is one:
1. Clicking the three-point button starts `handleThree` inside the render snapshot where `score` is one.
2. The first `addPoint` call calculates `1 + 1` and passes two to the setter. React adds *"replace with `2`"* to the queue, and the first log prints `1`.
3. Calling a setter never changes `score` in the running handler, so the second `addPoint` call still reads one. It calculates `1 + 1` again, queues a second replacement with two, and prints `1`.
4. The third `addPoint` call also reads `score` as one. It adds a third *"replace with `2`"* slip to the queue, and the third log prints `1`.
5. After `handleThree` finishes, React runs one render and walks the queue for `score`: replace with two, three times in a row. Every slip sets the score to `2`, so the board shows `Home: 2`!

Notice too that saving a local variable like `nextScore` inside `addPoint` would not fix this helper either. Because `addPoint` reads `score` from the component's snapshot each time it runs, all three calls in one click would still calculate two:

> [!PRINCIPLE]
> **Principle 2: Value Updates Replace: Three Snapshot Calls Queue the Same Number**
>
> *Passing a non-function value to a setter queues a replacement, so three calls from the same snapshot queue the same number three times.*
>
> When you pass an addition directly into a state setter, JavaScript calculates that math right away from this render's fixed snapshot. It hands only the finished number to React. Each call tells React to replace the state with that number, ignoring whatever is already waiting in the queue. If a click handler calls that setter three times, all three calls read the same starting number and queue the same replacement. That raises the score by one instead of three.
>
> **DO THIS:**
> ```jsx
> function handleOne() {
>   ~setScore(score + 1);~ // Safe ONLY when this event queues a single update for score
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleThree() {
>   setScore(score + 1);
>   setScore(score + 1);
>   ~setScore(score + 1);~ // **WRONG:** all 3 lines read the same score snapshot and queue the same number 3 times!
> }
> ```

## 3. Principle 3: Updater Functions Continue from the Pending State

### Why passing a value and passing an updater function are NOT the same thing

How do we tell React *"add one to whatever number is already waiting in the queue"* instead of *"replace the queue with this fixed number"*? Instead of passing the calculated number `number + 1`, you pass an **updater function** to the setter.

Compare both setter calls side by side:

```jsx title="Passing a calculated value vs. passing an updater function"
~setNumber(number + 1);~ // 1. Value update: calculates 0 + 1 right now from the snapshot and queues "replace with 1"
~setNumber(n => n + 1);~ // 2. Updater function: queues the function n => n + 1 so React calls it during the next render!
```

Look at the three distinctions that make updater functions clear right away:
- **First, passing `number + 1` and passing the arrow function on line 2 are NOT the same thing!** When you call a setter only once per click, both produce the same screen, so they seem to work the same at first. Yet passing `number + 1` calculates a number right now from this render's snapshot and tells React to **replace** the state. Passing the arrow function hands the **function itself** to React so it **continues** from the latest value in the queue during the next render.
- **Second, the parameter `n` inside the arrow function and the state variable `number` outside it are NOT the same thing!** They both hold the count, so they look like the same variable at first. Yet the state variable `number` is frozen at `0` for the entire click handler. During the next render, React fills the parameter `n` with the **pending state**, the running result from the update right before it.
- **Third, the short arrow function on line 2 is the exact same thing as a full JavaScript function that takes `n` and returns `n + 1`!** Both take the pending state `n` from React and return `n + 1`.

Now look at what happens when one click handler queues three updater functions in a row starting from `0`:

```jsx title="Queueing three updater functions in one click handler"
const [number, setNumber] = useState(0);

function handleClick() {
  ~setNumber(n => n + 1);~ // 1st updater in queue: React passes n = 0 -> returns 1
  ~setNumber(n => n + 1);~ // 2nd updater in queue: React passes n = 1 -> returns 2
  ~setNumber(n => n + 1);~ // 3rd updater in queue: React passes n = 2 -> returns 3
}
```

During the next render, React walks through the three queued functions in order, passing the return value of each function as the `n` parameter of the next one:

| Queued Update | Value of `n` Passed by React | Return Value Passed to the Next Step |
| :--- | :--- | :--- |
| **1st updater in queue** | `0`, the starting state from this render | `0 + 1` -> **`1`** |
| **2nd updater in queue** | `1`, the pending state from the 1st updater | `1 + 1` -> **`2`** |
| **3rd updater in queue** | `2`, the pending state from the 2nd updater | `2 + 1` -> **`3`**, stored as the final state |

```tree dir=right caption="How three queued updater functions hand their running result, the pending state, from one step to the next."
React walks three updaters starting from `0`
- +1. First updater [receives `n = 0`] | Adds `1` to `0` | Returns pending state **`1`**
- +2. Second updater [receives `n = 1`] | Takes the **`1` from step 1** and adds `1` | Returns pending state **`2`**
- +3. Third updater [receives `n = 2`] | Takes the **`2` from step 2** and adds `1` | Returns **`3`**, which `useState` gives to the page
```

### Mistake: Writing an updater function that still reads the snapshot variable

Let us update `addPoint` in our basketball scoreboard to use an updater function. Watch the easy mistake where a developer writes the arrow parameter `s`, **but still writes the outer snapshot variable `score` on the right side**:

```jsx title="src/components/Scoreboard.jsx" startLine="7"
  function addPoint() {
    ~setScore(s => score + 1);~ // **WRONG:** ignores parameter s and still reads the frozen snapshot variable score!
  }
```

When the developer saves the file and clicks the three-point button from zero, the scoreboard **still rises to `Home: 1` instead of `Home: 3`!**

Why didn't the arrow function fix the bug? Because `score` on the right side of the arrow is still the component's fixed snapshot variable `0`. Even though React passed zero, then one, and then two into `s`, the function body ignored that parameter and returned `0 + 1` all three times!

### Reading the pending state parameter inside the updater function

To make each queued update build on the one before it, the right side of the arrow must calculate its result from the updater's own parameter, `s`:

```jsx title="src/components/Scoreboard.jsx" startLine="7"
  function addPoint() {
    ~setScore(s => s + 1);~ // Uses the pending state parameter s passed in by React!
  }

  function handleOne() {
    addPoint();
    setLastPlay('Free throw');
  }

  function handleTwo() {
    addPoint();
    addPoint();
    setLastPlay('Two-pointer');
  }

  function handleThree() {
    ~addPoint();~ // 1st queued updater: s = 0 -> returns 1
    ~addPoint();~ // 2nd queued updater: s = 1 -> returns 2
    ~addPoint();~ // 3rd queued updater: s = 2 -> returns 3
    setLastPlay('Three-pointer');
  }
```

### How React passes the pending state into each updater

Look closely at `addPoint` above. Our code never writes parentheses after the arrow function to call it, and our code never passes a number into `s`. Who calls that arrow function, and where does `s` come from?

React calls each updater function during the next render and supplies `s` itself! Follow what happens in order when the scorekeeper clicks `+3` from `Home: 0`:
1. Clicking `+3` runs `handleThree`. Each of the three `addPoint` calls hands the updater function to `setScore` without calling it. React places all three functions in the update queue for `score`.
2. Next, `setLastPlay` queues the new play text, and `handleThree` finishes.
3. React starts the next render by calling `Scoreboard`. Inside `useState`, React walks the queue of three updater functions starting from zero.
4. React calls the first updater with `s` set to zero, and gets back `1`.
5. React calls the second updater with `s` set to that pending state one, and gets back `2`.
6. React calls the third updater with `s` set to that pending state two, and gets back `3`. React stores `3` as the new score and commits `Home: 3` and the three-pointer label to the page! If the scorekeeper then clicks `+2`, the two queued updaters step from three to four and five, showing `Home: 5`:

### Naming the updater parameter and two setter rules

When you write an updater function, React lets you give its parameter any valid JavaScript name. Across React teams and interviews, you will see three common naming styles:
- **The first letters of the state variable**: such as `s` for `score`, or a single letter for any state name.
- **The full state variable name**: repeating `score` as the parameter name, which works because the inner parameter name shadows the outer state variable inside the arrow function.
- **A `prev` prefix**: writing `prevScore` or `prevEnabled` to show clearly that the parameter holds the state from the step right before this updater.

```jsx title="The three common naming styles for an updater parameter"
~setScore(s => s + 1);~ // 1. First letter of the state variable name
~setScore(score => score + 1);~ // 2. Full state variable name repeated as the parameter
~setScore(prevScore => prevScore + 1);~ // 3. "prev" prefix before the state variable name
```

Keep two more facts about state setters in mind for debugging and interviews:
- **First, setter functions return `undefined`**: Calling `setScore` only adds an update to React's queue and returns nothing. Assigning the result of `setScore` to a variable always stores `undefined`.
- **Second, React treats any function passed to a setter as an updater function**: To store a function itself inside state, wrap it in an outer arrow function so React calls the wrapper and stores your function:

```jsx title="How to store a function itself in state without React calling it as an updater"
~setFn(someOtherFunction);~ // **WRONG:** React treats someOtherFunction as an updater and calls it during render!
~setFn(() => someOtherFunction);~ // Outer arrow is the updater: React calls () => someOtherFunction and stores someOtherFunction!
```

> [!PRINCIPLE]
> **Principle 3: Updater Functions Continue from the Pending State**
>
> *Pass an updater function to the setter so React calls it during the next render with the pending state from the update before it.*
>
> Instead of handing a finished number to the state setter, an updater function hands React a small calculation. That function takes the pending state as its parameter and returns the next state. During the next render, React walks the queue and feeds the return value of each updater straight into the parameter of the next updater in line. Make sure the right side of the arrow reads the updater's own parameter and not the outer snapshot variable.
>
> **DO THIS:**
> ```jsx
> function addPoint() {
>   ~setScore(s => s + 1);~ // Reads the pending state parameter s supplied by React
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function addPoint() {
>   ~setScore(s => score + 1);~ // **WRONG:** ignores s and reads the frozen snapshot variable score!
> }
> ```

## 4. Principle 4: Queue Order: React Walks Mixed Updates from First to Last

### Combining a value update and an updater on the same state: before vs. after

In Principle 2 our handler queued only plain values, and in Principle 3 our handler queued only updater functions. Can you write a plain value update like `number + 5` **and** a one-point updater function inside the **same click handler** for the same state variable?

Yes! Suppose `number` starts at zero. Inside a click handler, we call the setter with `number + 5` and also call it with a one-point updater.

When you put both calls in the same handler, there are **two ways to order them**:
- **Order 1**: The value update `number + 5` comes **before** the one-point updater. That means the value update is **first** in the queue, and the updater is **second**, at the end.
- **Order 2**: The one-point updater comes **before** the value update `number + 5`. That means the updater is **first** in the queue, and the value update is **second**, at the end.

Look at both orders side by side starting from `number` equal to `0`:

```jsx title="The two ways to order a value update and an updater function in one handler"
const [number, setNumber] = useState(0);

function handleOrderOne() {
  ~setNumber(number + 5);~ // Order 1, slip 1: value update is FIRST -> replaces 0 with 5
  ~setNumber(n => n + 1);~ // Order 1, slip 2: updater is LAST -> takes 5 and returns 6!
}

function handleOrderTwo() {
  ~setNumber(n => n + 1);~ // Order 2, slip 1: updater is FIRST -> takes 0 and returns 1
  ~setNumber(number + 5);~ // Order 2, slip 2: value update is LAST -> ignores 1 and replaces with 5!
}
```

In everyday math, adding five and then adding one gives the same answer as adding one and then adding five. **So Order 1 and Order 2 look like they should produce the same screen, and Order 1 even gives `6`, but they are NOT the same thing!**

Why does Order 1 display **`6`** while Order 2 displays **`5`**? Because during the next render, React walks the update queue in order from top to bottom:
1. **In Order 1**, the value update runs first. In this render `number` is zero, so the first slip says *"replace with `5`"*! The running result becomes five. Next, the updater function runs second. It receives that running result five as `n`, adds one, and produces **`6`**.
2. **In Order 2**, the updater function runs first. It receives the starting state zero as `n`, adds one, and makes the running result `1`. Next, the value update runs second! Because `number` in this render's snapshot is still zero, its slip says *"replace with `5`"*! A value slip **replaces** the running result and ignores earlier slips, so it throws away the `1` and leaves **`5`**!

What if we take Order 1 and place one more value call, `42`, at the very end after the updater?

```jsx title="Placing a plain value update after an updater in the queue"
function handleReplaceAtEnd() {
  setNumber(number + 5);
  setNumber(n => n + 1);
  ~setNumber(42);~ // Slip 3: comes LAST -> ignores the running 6 and replaces the state with 42!
}
```

Look at how React walks those three slips in order starting from `0`:

| Queued Update | Value of `n` Passed by React | Return Value Passed to the Next Step |
| :--- | :--- | :--- |
| **1. Replace with `5`** | `0`, unused because a value slip ignores `n` | **`5`** |
| **2. Updater function `n => n + 1`** | `5`, the pending state from step 1 | `5 + 1` -> **`6`** |
| **3. Replace with `42`** | `6`, unused because a value slip ignores `n` | **`42`**, stored as the final state |

That table also unlocks how React views both kinds of slips internally. Passing a plain value like `5` to a setter is the **exact same thing** in the queue as passing `n => 5`! Both ignore whatever `n` came before them and return `5`:

```tree caption="How the order of value replacements and updater functions in the queue decides the final state from 0."
Three mixed queues starting from `0`
- +Order 1: Value `number + 5` BEFORE updater [`replace with 5`, then `n => n + 1`] | Slip 1 sets running state to `5`; slip 2 adds `1` to `5` | Renders **`6`**
- !Order 2: Updater BEFORE value `number + 5` [`n => n + 1`, then `replace with 5`] | Slip 1 returns `1`, **then slip 2 overwrites `1` with `5`!** | Renders **`5`**, losing the updater's point
- !Value `42` placed AFTER earlier updates [`replace with 5`, `n => n + 1`, then `replace with 42`] | Slip 3 comes last and **ignores the `6` built above it** | Renders **`42`**
```

### How React's queue loop works in plain JavaScript

We can write React's entire queue calculation in ten lines of plain JavaScript. Starting from `baseState`, React loops through each item in the `queue` array from first to last:

```js title="Plain JavaScript: how React calculates the final state from a queue"
function getFinalState(baseState, queue) {
  let finalState = baseState;

  for (const update of queue) {
    if (~typeof update === 'function'~) { // 1. Updater function: call it with the running finalState!
      finalState = update(finalState);
    } else {
      ~finalState = update;~ // 2. Plain value: overwrite finalState and ignore what came before!
    }
  }

  return finalState;
}
```

Look at the two branches inside that `for` loop. When the queue item is a function, React calls `update` with the running `finalState` so it continues from the step before it. When the queue item is any plain value, `finalState = update` overwrites `finalState` completely and forgets every earlier step in the loop!

### Mistake: Mixing a value helper and an updater helper in the same click

Watch how easy it is to trip over that `else` branch in our basketball scoreboard. Suppose the page reloads to zero, and a teammate adds a second helper named `addTwo` for the two-point button using a plain value `score + 2`. When the scorekeeper clicks `+2`, `addTwo` is the only score update in that click, so the two-point button works fine on its own.

Next, the teammate rewrites the three-point handler to combine both helpers by calling `addTwo` first and `addPoint` second:

```jsx title="src/components/Scoreboard.jsx" startLine="7"

    setScore(s => s + 1);
  }

  function addTwo() {
    ~setScore(score + 2);~ // Uses a plain value replacement instead of an updater function
  }

  function handleThree() {
    ~addTwo();~ // Order 1, slip 1: queues "replace with 0 + 2" -> running state is 2
    ~addPoint();~ // Order 1, slip 2: updater s => s + 1 takes 2 -> returns 3, hiding the bug!
    setLastPlay('Three-pointer');
  }
```

When the scorekeeper clicks `+3` from zero, the board shows `Home: 3`! Because the value replacement `addTwo` ran **before** the updater `addPoint`, the bug stays completely hidden.

Later that afternoon, another developer edits the three-point handler and swaps the two lines so `addPoint` runs **before** `addTwo`:

After reloading the page to zero, the scorekeeper clicks `+3` for a three-pointer. Now the scoreboard shows **`Home: 2` instead of `Home: 3`**!

### Why `addTwo` erased the point that `addPoint` queued before it

Look at the swapped `handleThree` above. Nothing in the handler says *"subtract the first point."* Why did putting `addPoint` before `addTwo` lose a point?

Follow what JavaScript and React do in order when `score` starts at `0`:
1. Calling `addPoint` first adds its one-point updater function as the first slip in the queue.
2. Calling `addTwo` second reads this render's fixed snapshot `score`, which is still zero. It calculates `0 + 2` and adds *"replace with `2`"* as the second slip in the queue.
3. When `handleThree` returns, React walks the queue starting from zero: the first slip is the updater, which turns zero into `1`. The second slip is *"replace with `2`,"* which ignores the running one and overwrites the score with `2`!

### Writing both score helpers with updater functions

```jsx title="src/components/Scoreboard.jsx" startLine="7"
  function addPoint() {

  }

  }
```

Now both `addPoint` and `addTwo` build on the pending state. Whether `handleThree` calls `addTwo` first or last, the queue steps cleanly to three:

> **Principle 4: Queue Order: React Walks Mixed Updates from First to Last**
>
> *During the next render, React walks the queue in order: an updater builds on the running result, while a plain value replaces it.*
>
> When you mix plain value updates and updater functions for the same state variable in one event, the order of the lines changes the final number on screen. Any updater function placed after a value update adds to that value, whereas a plain value placed after updater functions ignores their work and overwrites the running state. > **DO NOT DO THIS:**
> ```jsx
> function handleThree() {
>   setScore(s => s + 1);

> }
> ```

## 5. Principle 5: Keep Updater Functions Pure, and Use Them When Updates Stack Up

### Why code inside an updater function is NOT the same thing as code inside the click handler

Where does an updater function actually run, and can you put `console.log`, another state setter, or outside changes inside it?

Compare these two click handlers. Both increase `count` by one and print a message to the Console, but look at **where** the `console.log` line sits in each one:

```jsx title="Logging inside the updater function vs. logging inside the click handler"
function handleImpure() {
  setCount(c => {
    ~console.log('adding');~ // **WRONG:** inside the updater -> React decides when it runs, and runs it twice in StrictMode!
    return c + 1;
  });
}

function handleClean() {
  ~console.log('adding');~ // Inside the click handler -> runs ONCE on the click!
  ~setCount(c => c + 1);~ // Pure updater -> only calculates and returns c + 1
}
```

Look closely at the two confusions that trip developers up here:
- **First, because the updater arrow function is written right inside `handleImpure`, it looks like click-handler code that runs at the moment of the click, but it is NOT the same thing!** Your click handler only hands the updater function to React, and React decides when to call it. React calls most updaters **during the next render**, under the exact same purity rules as your component body! When nothing else waits in the queue yet, React may even call the first updater once right inside the setter call. That early call checks whether the state will change at all. Think of an updater function as a **recipe card** handed to the kitchen. The cook decides when to cook it. In `<StrictMode>` development, the cook cooks every recipe card **twice** to check the calculation and throws one of the two dishes away. Because of that, the recipe card must only calculate and return the next state, and never call another setter or log messages.
- **Second, what if a button handler updates a state variable only once per click? With one update per click, passing `count + 1` and passing `c => c + 1` give the exact same result!** React always finishes rendering the current click before the next click begins, so a single update in a click handler never starts with an old value. You only *need* an updater function when more than one update of the same state variable can be queued before the next render:

```tree caption="Code written inside an updater function vs. code written inside the event handler outside the setter."
Where a line of code runs when you click a button
- !Inside the updater function [inside `c => { ... }`] | **React decides** when it runs, mostly **during the next render** | Must be **100% pure**: `<StrictMode>` calls it **twice** in development and keeps **one** result
- +Inside the event handler [outside `setCount`] | Runs **once at the moment of the click** | Event handlers do **not** need to be pure and are **never called twice** by `<StrictMode>`
```

### Mistake: Putting `console.log` or side effects inside an updater function

Let us watch what happens in our basketball scoreboard when a developer puts a `console.log` line inside the updater function of `addPoint`:

```jsx title="src/components/Scoreboard.jsx" startLine="7"
  function addPoint() {
    setScore(s => {
      ~console.log('Point for Home');~ // **WRONG:** side effect inside an updater function!
      return s + 1;
    });
  }
```

In development, our startup file wraps the app in `<StrictMode>`. Now watch what happens when the scorekeeper clicks `+3` once from `Home: 0`:
1. In Chrome's Console panel, the message does **not** print three times. Because `<StrictMode>` calls each updater function twice in development, the log prints **six times** for a single `+3` click!
2. Startled by seeing six Console messages, the developer looks at the scoreboard expecting to see `Home: 6`.
3. Yet the scoreboard on the page reads **`Home: 3`**, the right score!

### Why `StrictMode` calls each updater twice in development and keeps one result

Look at `addPoint` above. Clicking `+3` called `addPoint` only three times, and each call queued one updater function. Nothing in our scoreboard file called those updaters a second time! Who called them twice, and why did the score still stop at `Home: 3` instead of `Home: 6`?

In development, React's `<StrictMode>` intentionally calls every **component function**, **initializer function**, and **updater function** twice to help you catch accidental side effects early:
1. When the scorekeeper clicks the three-point button, the handler hands three updater functions to the score setter. Nothing else waits in the score queue yet. So React calls the first updater once right away, with `s` set to zero, to check whether the score will change. Then React queues all three updaters, and `handleThree` returns.
2. During the next render of `Scoreboard`, React walks the queue. Under `<StrictMode>`, React calls the first updater one more time, and it calls the second and third updaters **twice** each. So every updater runs twice, and both runs get the same pending state `s`.
3. Both runs call `console.log`, printing the log message twice for each queued updater.
4. For the state itself, React **keeps only one return value** of each pair and throws the other one away! So the running result still steps from zero to one, then two, and finally `3`. In a production build, React calls each updater only once, and the Console shows the message three times.

### Keeping the updater pure and placing logs inside the handler

Only component functions, initializer functions, and updater functions must be pure. Event handlers and the helpers they call run on the click, not during rendering, so `<StrictMode>` **never** calls an event handler twice!

To log once per point, move `console.log` out of the updater function and place it directly inside `addPoint` above the setter:

```jsx title="src/components/Scoreboard.jsx" startLine="7"
  function addPoint() {
    ~console.log('Point for Home');~ // 1. Runs in the handler on the click: logged ONCE per addPoint call
    ~setScore(s => s + 1);~ // 2. Pure updater function: only calculates and returns s + 1
  }
```

Save the file and click `+3` once from `Home: 0`. Now the Console prints the message three times, once for each `addPoint` call, and the scoreboard shows `Home: 3`:

### When to use an updater function vs. a plain value

Now we can answer the second half of our interview question completely: **when do you actually need an updater function?**

Here are the four situations you will meet in real projects and interviews:
- **1. Multiple updates of the same state before the next render**: Whenever one event queues more than one update for the same state variable, **use an updater function** so every update calculates from the latest pending state. That includes calling helpers like `addPoint` several times in one click, or updating a state variable after an asynchronous `await` delay.
- **2. Only one update of that state in the click**: When a click handler updates a state variable only once, passing a plain value like `score + 1` works cleanly without any bug. React always updates the state before the next intentional user click can run. Teams that prefer one consistent style often write an updater every time state builds on its previous value, and doing so is completely fine.
- **3. The running handler itself needs the new value right away**: Remember that neither a plain value nor an updater function changes `score` inside the running handler! When your click handler needs to pass the new number to `alert` or a log right away, save `score + 3` in a local variable first.
- **4. One state variable depends on a different state variable**: Never try to call one state setter from inside another state variable's updater function. When one state update depends on the value of a *different* state variable, combine those states into one object managed by a **reducer**, which a later lesson covers.

```tree caption="How to choose the right state update tool for each situation in React."
Which state update pattern fits your handler?
- +Several updates of the SAME state before the next render [`addPoint` called 3 times, or after `await`] | +**DO** use an updater function | Each queued update receives the **latest pending state** `s`
- +One update of that state per click [`setLastPlay` or a single score change] | +**DO** pass the next value directly, or use an updater by team habit | React finishes the render **before the next click** starts
- +Running handler must read the new number right now [for `console.log` or `alert`] | +**DO** save `const nextScore = score + 3` first | Gives the running handler the new value immediately
- !Next state depends on a DIFFERENT state variable [calling a setter inside an updater] | ~Do **NOT** call setters inside an updater | Keep updaters pure; combine related states in a **reducer**
```

> [!PRINCIPLE]
> **Principle 5: Pure Updaters: Keep Updaters Pure and Use Them When Updates Stack Up**
>
> *React calls updater functions mostly during rendering, so they must be pure. Use an updater whenever multiple updates of the same state can be queued before the next render.*
>
> Your click only hands an updater function to React. React decides when to call it, mostly during the next render, and calls each updater twice in Strict Mode development while keeping only one result. Because of that, an updater must only calculate and return the next value from its parameter. Never put Console logs, other state setters, or outside mutations inside an updater. Put logs and side effects inside the event handler, and reach for an updater whenever multiple updates of the same state can queue up.
>
> **DO THIS:**
> ```jsx
> function addPoint() {
>   ~console.log('Point for Home');~ // 1. Side effects and logs belong in the event handler
>   ~setScore(s => s + 1);~ // 2. Updater is pure: only returns s + 1
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function addPoint() {
>   setScore(s => {
>     ~console.log('Point for Home');~ // **WRONG:** React decides when it runs, and it prints twice per update in StrictMode!
>     return s + 1;
>   });
> }
> ```

```jsx title="src/components/Scoreboard.jsx" startLine="1"
  const [lastPlay, setLastPlay] = useState('Game start');

    ~console.log('Point for Home');~ // Principle 5: log lives in the handler, never inside the updater
    ~setScore(s => s + 1);~ // Principle 3: pure updater continues from the pending state s

  function addTwo() {
    ~setScore(s => s + 2);~ // Principle 4: updater helper composes cleanly in any order
  }

  function handleOne() {
    addPoint();
    ~setLastPlay('Free throw');~ // Principle 1 & 2: single update per click uses a direct value and batches with score
  }

  function handleTwo() {
    addTwo();
    setLastPlay('Two-pointer');
  }

  function handleThree() {
    ~addPoint();~ // Principle 4: queues s => s + 1 first
    ~addTwo();~ // Principle 4: queues s => s + 2 second -> steps 0 -> 1 -> 3!
    setLastPlay('Three-pointer');
  }

      <h1>Scoreboard</h1>
      <p className="score">Home: {score}</p>
      <p className="last-play">Last play: {lastPlay}</p>
      <button onClick={handleOne}>+1</button>
      <button onClick={handleTwo}>+2</button>
      <button onClick={handleThree}>+3</button>
    </section>
  );
```

### How React batches the updates and walks the queue on a `+3` click

When the scorekeeper clicks the three-point button from `Home: 0`, React runs every line of `handleThree` first. First, `addPoint` logs once to the Console and queues its one-point updater. Second, `addTwo` queues its two-point updater, and `setLastPlay` queues the new play text. Once `handleThree` returns, React renders `Scoreboard` once, walks the score queue from zero to one to three, and commits the finished board to the DOM:

| Aspect | The Naive Expectation | The React Rule |
| :--- | :--- | :--- |
| **When setter calls update the screen** | Expects each setter line to re-render the screen immediately before the next line of the handler runs | React **batches** all setter calls in one handler and renders **once** after the entire handler finishes |
| **Separate user clicks** | Wonders if fast button clicks get merged into one batch | React **never** batches across separate intentional clicks; each click renders before the next click runs |
| **Passing a value three times** | Expects three `score + 1` setter calls in one handler to add three points | Each value call reads the **same snapshot** and queues **replace with that number**, so three calls add **one** |
| **Passing an updater function** | Treats `s => s + 1` as just a longer spelling of `score + 1` | React queues the function and calls it during the next render with the **pending state** `s`, so three calls add **three** |
| **Mixing values and updaters** | Assumes adding two and adding one gives the same total in either order | React walks the queue in order: an updater builds on the running result, while a plain value **replaces** and wipes out earlier slips |
| **Side effects inside updaters** | Puts `console.log` or another setter inside `s => { ... }`, thinking it runs once on the click | React decides when updaters run, mostly **during render**, so they must be **pure**; `<StrictMode>` calls each updater twice in development and discards one result |

## For the Interview

> **The Interview Question:** How does React queue multiple state updates, and when do you need an updater function?

### How to Answer Clearly in 30 Seconds

"Calling a state setter does not change the state variable in the running render; it adds an update to React's queue and requests a new render. First, React uses **batching**: it waits until all code in the event handler has finished before processing the queued updates in a single render. That keeps the app fast and prevents half-finished screens when several state variables change together, while each separate user click is still handled on its own.

Second, what happens inside the queue depends on what we pass to the setter:
1. **Passing a next value directly**, like `count + 1`, adds a **replacement** slip to the queue. Every line in a handler reads the same render snapshot, so calling `setCount` with `count + 1` three times queues the same replacement number three times. The count only goes up by one.
2. **Passing an updater function**, like `c => c + 1`, adds the function itself to the queue. During the next render, React walks the queue in order and calls each updater with the **pending state** from the step before it, so three calls add three. If a plain value and an updater are mixed in the same queue, their order matters because a plain value overwrites whatever running result came before it.
3. **Purity and when to use one**: React decides when updater functions run, mostly during rendering. `<StrictMode>` calls each one twice in development and discards one result, so updaters must be pure calculations with no side effects. You need an updater whenever the next state depends on the previous state and multiple updates of that same state can be queued before the next render. For a single update per click, a plain value works fine because React renders before the next click, while cross-state calculations belong in a reducer."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"When `number` starts at `0`, what does a click show after calling `setNumber` with `number + 5` and then `n => n + 1`, or in reverse order?"**
   - When `number + 5` comes **first** and `n => n + 1` comes **second**, the screen shows **`6`**. In the render where `number` is `0`, the first call queues *"replace with `5`,"* and the second call queues `n => n + 1`. During the next render, React sets the running result to `5` and then calls the updater with `n` equal to `5`, returning `6`.
   - When we **swap** the two lines so `n => n + 1` comes **first** and `number + 5` comes **second**, the screen shows **`5`**. The updater runs first and turns `0` into `1`, and then the value slip *"replace with `5`"* ignores that `1` and overwrites the running result with `5`. Similarly, placing a plain value call with `42` at the very end after updaters overwrites everything before it and renders `42`.

2. **"Why must an updater function be pure, and why did a `console.log` inside my updater print twice in development?"**
   - Even though an updater function is written inside an event handler, it is not event handler code. React decides when to call it. React calls most updaters **during the next render**, and it may call the first one once right inside the setter call to check whether the state will change. Because rendering must be pure, an updater must only calculate and return the next state from its parameter, without mutating outside variables, calling setters, or logging. In development under `<StrictMode>`, React calls each updater function **twice** with the same pending state. It keeps only one of the two return values, and the extra call helps expose side effects. Event handlers themselves do not need to be pure and are never called twice by `<StrictMode>`, so logs and side effects belong in the handler.

3. **"Should I always pass an updater function to every state setter, or only in specific cases?"**
   - You do not *have* to use an updater on every setter call. For intentional user clicks, React always finishes rendering the current click before the next click runs, so a single update per click works cleanly with `count + 1`.
   - You **must** use an updater whenever the next state builds on the previous state and **multiple updates of that same state** can queue up before the next render. That happens when a handler calls a helper function several times in one click, or updates state after an asynchronous wait while other updates may have occurred. Writing an updater every time state builds on its own previous value is also a fine team convention, while state calculated from another variable belongs in a reducer.

```tree dir=right caption="Interview comparison: passing a next value directly vs. passing a pure updater function to a state setter."
Two kinds of entries in React's state update queue
- +Direct value [`count + 1`] | Calculated **now** from this render's fixed snapshot | Queues **replace with that value**, ignoring earlier slips; fits **one update per click**
- +Updater function [`c => c + 1`] | Pure function called by React, mostly **during the next render** | Receives the **pending state** from the slip before it; needed when **multiple updates of the same state** are queued
```
