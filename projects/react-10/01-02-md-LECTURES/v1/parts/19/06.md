## 5. Principle 5: A Copied Array Still Holds the Same Songs, So Changing One Song Means a New Song Object

### Why mutating an item inside a copied array and replacing it with `map` are NOT the same thing

In Principle 4, we saw that spreading an array into new square brackets gives us a fresh array copy that we can reorder freely. That leads straight to one of the most common questions in React interviews. **Once you copy an array of objects with spread, can you also change a property inside one of its objects?**

Suppose an array named `people` holds an object for Anna with `seen: false`, and we want to mark Anna as seen. Compare two ways of writing that update in plain JavaScript.

First, look at Way A, which copies the outer array with `[...people]` and then flips `copy[0].seen` in place:

```js title="Way A: Copying the array, then mutating copy[0].seen in place"
const people = [{ id: 1, name: 'Anna', seen: false }];
const copy = ~[...people]~; // 1. New outer array, yet copy[0] === people[0] is still true!
~copy[0].seen = true;~ // 2. Mutates that shared Anna object in place!

console.log(~people[0].seen~); // 3. true -> the original people[0] object was secretly changed too!
```

Now compare Way A with Way B, which uses `people.map` and object spread `{ ...p }` to create a brand-new object for Anna:

```js title="Way B: Using map and object spread to replace only the changed object"
const people = [{ id: 1, name: 'Anna', seen: false }];
const next = ~people.map(p => p.id === 1 ? { ...p, seen: true } : p)~; // Builds a new array AND a new Anna object!

console.log(~next[0].seen~); // true -> the new Anna object in next has seen: true
console.log(~people[0].seen~); // false -> the original Anna object in people is still untouched!
```

Wait: Way A and Way B both build a brand-new outer array whose first person has `seen` set to `true`. In React, both even trigger a re-render on the first click! **It may look the same on the first click, and it may seem to work the same at first, but it is NOT the same thing**. Way A mutates the person object that the old array still holds, while Way B creates a brand-new person object.

Why did changing `copy[0]` on the copied array also change `people[0]` on the original array? Because copying an array with `[...people]` is a **shallow copy**. Objects do not really sit inside an array. They sit separately in memory, and each slot of the array only holds a link pointing at an object.

Think of a photocopy of a party guest list. Making a shallow copy with `[...people]` gives you a brand-new sheet of paper. Yet the first line on both sheets still points at the exact same real Anna standing in the room, so `copy[0] === people[0]` is `true`. If you use the new sheet to put a hat on Anna with `copy[0].seen = true`, Anna on the original sheet is wearing that hat too!

Way B avoids that trap by following the nested-state rule from our object lessons. You must copy every level on the path to the change, all the way up to the top level. Here `people.map` builds a brand-new outer array, and `{ ...p }` builds a brand-new inner object for the one person who changed. Every unchanged person is returned as is.

Compare how Way A and Way B treat the outer array and the inner person object in memory:

```tree caption="Copying the outer array with [...people] and mutating copy[0].seen in place vs. replacing the changed item object with people.map and { ...p }."
Updating one object inside an array of objects [`const people = [{ id: 1, name: 'Anna', seen: false }]`]
- !Way A: Shallow array copy and item mutation [`const copy = [...people]; copy[0].seen = true`] | Builds a new outer array, yet `copy[0] === people[0]` is **`true`** | Mutates the **shared Anna object**, so `people[0].seen` becomes **`true` too**
- +Way B: Replace the changed item with `map` and spread [`people.map` with `{ ...p, seen: true }`] | Builds a **new outer array** and a **brand-new Anna object** | `next[0] === people[0]` is **`false`**, and `people[0].seen` stays **`false`**
```

### Mistake: Mutating a song inside a copied array breaks Undo

Now let's add a **Like** button to every song row in our play queue. Each song starts with `liked: false`, and clicking **Like** switches the button label to **Liked**.

Suppose we write `handleLike` by copying the queue array and then flipping the song's `liked` flag directly on that item:

```jsx title="src/components/PlayQueue.jsx" startLine="38"
  function handleLike(index) {
    const next = [...queue];
    ~next[index].liked = !next[index].liked;~ // **WRONG:** mutates the song object shared with queue!
    setPrevious(queue);
    setQueue(next);
  }
```

Watch what happens on screen when the listener clicks **Like** on Blue Bicycle at index `1` and then clicks **Undo**:
1. **First, the listener clicks Like on Blue Bicycle:** Because `next` is a brand-new outer array, React sees a new array reference, re-renders right away, and switches Blue Bicycle's button to **Liked**! Everything looks fine on the first click.
2. **Next, the listener clicks Undo to take that Like back:** The **Undo** button disappears, yet Blue Bicycle stays stuck on **Liked**!

**Wait: why did Undo fail to revert Blue Bicycle's Like when no line ever wrote to `previous`?** Trace what happened in memory step by step:
1. Spreading `queue` into `next` built a new outer array, yet the second slot of both arrays still pointed at the exact same Blue Bicycle object.
2. Flipping `next[1].liked` walked down that shared link and mutated that shared object's `liked` property in place.
3. Calling `setPrevious` with `queue` saved the old array for **Undo**, and its second slot still pointed at that same mutated Blue Bicycle object!
4. When the listener clicked **Undo**, React restored `previous`, read `song.liked` from that mutated object, and rendered **Liked** all over again!

This exact bug also happens whenever two state arrays, such as `myList` and `yourList` in an art bucket list, start from one shared array of objects. If you shallow-copy `myList` and mutate an item inside it, the matching checkbox in `yourList` flips on screen too. Both arrays still point at the exact same item objects in memory!

### Replacing only the liked song with `map` and object spread

To update one song without touching any earlier array that holds it, we use `queue.map` inside `handleLike`. For the matching song we build a brand-new object with spread, and we return every other song unchanged:

```jsx title="src/components/PlayQueue.jsx" startLine="38"
  function handleLike(id) {
    setPrevious(queue);
    setQueue(
      ~queue.map(s => (s.id === id ? { ...s, liked: !s.liked } : s))~ // Replaces ONLY the matching song with a brand-new object
    );
  }
```

Inside the ordered list of `PlayQueue`, we add a **Like** button to each song row that passes `song.id` when clicked:

```jsx title="src/components/PlayQueue.jsx" startLine="60"
      <ol>
        {queue.map((song, index) => (
          <li key={song.id}>
            <span>{song.title}</span>
            ~<button onClick={() => handleLike(song.id)}>~ {/* Passes song.id so handleLike replaces only this song */}
              {song.liked ? 'Liked' : 'Like'}
            </button>
            <button
              disabled={index === 0}
              onClick={() => handleMoveUp(index)}
            >
              Move up
            </button>
            <button onClick={() => handleRemove(song.id)}>
              Remove
            </button>
          </li>
        ))}
      </ol>
```

**Wait: inside the new song object, where do `id` and `title` come from when we only wrote the new like status?** And why does **Undo** work now? Trace what `queue.map` builds step by step:
1. Calling `queue.map` runs our arrow function once for each song `s`. It also passes the item index as a second argument whenever you need to replace an item by index.
2. For Sunny Road and Night Train, `s.id === id` is `false`, so the ternary returns the existing song object as is. Only the changed song gets a new object!
3. For Blue Bicycle, `s.id === id` is `true`. Object spread `{ ...s }` creates a brand-new object and copies every existing property from `s`, including its id and title. Then `liked: !s.liked` after the spread overwrites that property to `true` on the new object!
4. Now the second slot of `previous` still points at the original Blue Bicycle object with `liked: false`. Meanwhile, the second slot of the new `queue` points at the brand-new Blue Bicycle object with `liked: true`.
5. When the listener clicks **Undo**, React restores `previous`, reads `liked: false` from the untouched original object, and flips the button right back to **Like**!

Notice that `queue.map` is not limited to replacing a single item by `id`. You use the exact same `map` pattern whenever you want to transform several items or every item at once. For instance, an **Unlike all** action can map over `queue` and return a fresh copy of every song with `liked: false`. In the official React documentation's shape editor, `map` moves every circle down by fifty pixels while returning every square unchanged.

Replacing the changed item object also protects more than **Undo**. Mutating a song inside a copied array corrupts earlier render snapshots and breaks child components wrapped in `memo`. A `memo` row compares its previous and next `song` prop, sees the exact same object reference, and skips re-rendering! When state is deeply nested and copying every level by hand feels repetitive, the optional **Immer** library and its `useImmer` hook can help. Inside `useImmer`, you update a temporary `draft` object, and Immer builds the immutable nested copies for you behind the scenes. Moving each song row into its own child component with callback props, or gathering every array update into a reducer, comes in later lessons.

Here is what the second slot of `previous` and the new `queue` point to in memory under both approaches:

```tree dir=right caption="Why mutating next[1].liked inside a shallow array copy corrupts previous[1], while queue.map and { ...s } give the new array its own song object."
Slot `1` for Blue Bicycle inside `previous` vs. the new `queue`
- !Mutate `next[1].liked` inside `[...queue]` | `previous[1]` and `next[1]` point at the **same object** | Both see `liked: true`, so **Undo fails**
- +Replace with `queue.map` and `{ ...s, liked: !s.liked }` | `previous[1]` keeps the **original `liked: false` object** | New `queue[1]` gets a **new `liked: true` object**, so **Undo works**
```

> [!PRINCIPLE]
> **Principle 5: Copy the Changed Item Object Too with `map` and Object Spread**
>
> *To update one object inside a state array, use `map` to return a brand-new copied object for that item and keep every other item unchanged.*
>
> Copying an array with spread, `slice`, or `filter` makes a shallow copy whose slots still point at the exact same item objects in memory. Mutating an item inside a copied array changes that shared object inside the old state array and inside any saved `previous` snapshot too. That hidden mutation breaks **Undo**, corrupts earlier render snapshots, and stops `memo` child components from re-rendering.
>
> **DO THIS:**
> ```jsx
> setQueue(
>   ~queue.map(s => (s.id === id ? { ...s, liked: !s.liked } : s))~ // New array AND a brand-new object for the liked song
> );
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const next = [...queue];
> ~next[index].liked = !next[index].liked;~ // **WRONG:** mutates the song object still shared with queue and previous!
> setQueue(next);
> ```
