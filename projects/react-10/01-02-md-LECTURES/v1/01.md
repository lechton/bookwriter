## Why We Use React Instead of Updating the Page by Hand

### What "imperative" and "declarative" really mean

Why do developers call plain JavaScript **"imperative"** and React **"declarative"**? Both words sound academic at first, but their meaning comes straight from everyday life.

**Imperative** comes from the same root as an **empire** or an **emperor** giving commands: *"Go here! Do this! Now change that!"* In plain JavaScript, you act like a commander guiding the browser step by step for every place on the screen:
1. *"First, go find the paragraph on the page!"*
2. *"Now replace its text with the new count!"*
3. *"Now go find the buy button on the page!"*
4. *"Now replace the button's text too!"*

Here is what those step-by-step commands look like in plain JavaScript:

```js title="Plain JavaScript: giving step-by-step commands for every element"
const count = 3;
const items = document.getElementById('items');
~items.textContent = 'Items: ' + count;~ // Command 1: update the paragraph text
const buyBtn = document.getElementById('buy-btn');
~buyBtn.textContent = 'Buy ' + count + ' items';~ // Command 2: update the button text too
```

Suppose `count` appears in five places on the page. If you forget the command for even one place, that spot stays stuck on the old number!

**Declarative** means you simply **declare** what the finished page should look like, the way you hand a finished blueprint to a builder:

```jsx title="React: declaring where count belongs on the page"
<p>Items: ~{count}~</p> {/* 1. Declare that the paragraph shows count */}
<button>Buy ~{count}~ items</button> {/* 2. Declare that the button also shows count */}
```

You never command the browser to go find the paragraph and then go find the button. You simply place `{count}` in both spots once. Whenever `count` changes, React reads your blueprint and updates every spot on the screen automatically:

```tree caption="Plain JavaScript is imperative like an empire giving step-by-step commands; React is declarative like stating the finished blueprint."
Imperative commands in plain JavaScript vs. declarative code in React
- !Plain JavaScript: Imperative [`items.textContent = ...` `buyBtn.textContent = ...`] | Like an **empire giving step-by-step orders** for every single element | Forget **one command** and that part of the screen stays stuck on the **old value**
- +React: Declarative [`<p>Items: {count}</p>` `<button>Buy {count} items</button>`] | You **declare** where `{count}` belongs on the page **once** | Change `count` once, and React updates **every place automatically**
```

### Keeping a page in sync by hand is easy to get wrong

Now picture an online shop with a small shopping cart box on the side of the page. The cart shows the number of items in **two places**: a line that says `Items: 3` and a button that says `Buy 3 items`. Between them sits a text box where the shopper has typed a delivery note asking the courier to ring the bell:

```shop caption="Our target shopping cart on the page: the item count appears in two places, and the shopper has typed a delivery note."
product: 🧦 | Wool socks | $9
product: ☕ | Ceramic mug | $14
product: 📓 | Pocket notebook | $6
text: Items: 3 | good
typed: Please ring the bell | good
button: Buy 3 items | good
```

When the shopper adds a third item and the count rises from two to `3`, both places must show `3`. At the same time, the typed delivery note must stay right where it is. Developer teams have two ways to keep a page like this in sync when data changes:

```tree caption="Two ways to keep the webpage in sync when data changes: step-by-step DOM instructions in plain JavaScript vs. a component description in React."
Ways to update the webpage when data changes
- !Way 1: Imperative UI in plain JavaScript [`textContent` `innerHTML`] | ~Do **NOT** update each DOM element by hand in growing apps | You write **step-by-step instructions** to find and change each element | Forgetting one element leaves **old numbers on screen**, and replacing HTML wipes out **typed input text**
- +Way 2: Declarative UI in React [`Cart` `<Cart />`] | +**DO** describe what the UI should look like for the current data | You write a **component function** that plugs `{count}` into the markup | React updates **only the changed text** in the browser and keeps **typed input text and focus** alive
```

**React** is a JavaScript library for building user interfaces from small, self-contained functions called **components**. You describe what each piece of the screen should look like for the current data, and React updates the browser page for you.

### HTML tags in your file vs. the live DOM tree in the browser

Before we compare plain JavaScript and React in code, let us separate two things that look alike at first glance. One is the **HTML file** you write, and the other is the **live DOM tree** the browser builds in memory.

- **HTML** is the text file of tags, such as `<section>` and `<button>`, that you save in your editor.
- **The DOM**, short for Document Object Model, is the live tree of element objects that the browser builds in memory after reading your HTML. When JavaScript changes an element in the DOM, the screen changes right away.
- **The Elements panel** in Chrome's developer tools lets you inspect that live DOM tree at any moment:

```dom title="Elements panel" caption="The live DOM tree for our shopping cart inside Chrome's Elements panel."
<section id="cart">
  <p id="items">Items: 2</p>
  <input placeholder="Note to the shop" />
  <button id="buy">Buy 2 items</button>
</section>
```

```tree dir=right caption="How the browser turns static HTML text into the live DOM tree shown on the screen."
From HTML text to the screen
- 1. HTML file [`index.html`] | Static text with `<section>`, `<p>`, `<input>`, and `<button>` tags
- 2. Browser DOM [`document`] | Live tree of element objects in browser memory that you inspect in the **Elements panel**
- 3. Browser screen | Pixels the shopper sees and clicks
```

### Two plain-JavaScript tools for changing the DOM: `textContent` and `innerHTML`

In plain JavaScript, developers usually reach for one of two browser tools to change the DOM when a number changes from `2` to `3`:

1. **`textContent` on each element one by one**: You find each element by its `id` with `document.getElementById` and replace only its text:

```js title="page.js"
const count = 3;
document.getElementById('items').~textContent~ = 'Items: ' + count; // 1. Updates the <p> text to "Items: 3"
document.getElementById('buy').~textContent~ = 'Buy ' + count + ' items'; // 2. Updates the <button> text to "Buy 3 items"
```

2. **`innerHTML` on the outer box**: You replace all the HTML inside the `<section id="cart">` box at once:

```js title="page.js"
const count = 3;
document.getElementById('cart').~innerHTML~ = ` // Replaces every element inside #cart with brand-new DOM elements
  <p>Items: ${count}</p>
  <button>Buy ${count} items</button>
`;
```

Both tools work on a tiny page, and each one fails in a specific way as soon as the cart grows. React's three main characteristics exist to solve those exact failures.

### Three Principles of React

**PRINCIPLES:** React is built around three core ideas that work together to keep the screen in sync without wiping out what the user is doing:
1. **Principle 1: Declarative UI**: Do not write step-by-step commands to find and change each element whenever a number changes. Declare what the markup looks like for the current data, and React updates every place that displays it.
2. **Principle 2: Component-Based Architecture**: Do not scatter a page's HTML in one file and its update commands in another. Bundle each visual piece of the page and its data into a reusable function called a component.
3. **Principle 3: The Virtual DOM**: Do not demolish and rebuild a whole section of the page on every update. React compares lightweight blueprints in memory first and updates only the exact text or attributes that changed.

Here is how all three principles fit together:

| # | Principle | What Question It Answers | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Declarative UI** | How do you keep multiple places on the screen in sync when a piece of data changes? | Plug your data variable into the markup with curly braces and let React update every spot on the page. |
| **Principle 2** | **Component-Based Architecture** | How do you organize the data and markup for each visual piece of a page? | Bundle each visual piece into its own component function and place it on the page with a component tag. |
| **Principle 3** | **Virtual DOM** | How does React update the screen when a component runs again without wiping out what the user typed into an input box? | Return the updated markup from your component; React compares the old and new virtual blueprints in memory and patches only what changed. |

## 1. Principle 1: Declarative UI: Describe What the Screen Should Look Like

### Giving step-by-step DOM instructions vs. describing what the screen should show

To a junior developer, changing a variable from two to `3` and seeing `3` on the screen feel like one automatic step. To a senior developer, there are **two opposite ways** to connect data to the screen:

- **Imperative UI**: You write step-by-step instructions that find each DOM element and overwrite its text whenever data changes.
- **Declarative UI**: You write one description of what the screen should look like for the current data, and the library updates the DOM to match that description.

### What goes wrong in plain JavaScript when you forget one place

Start with the simplest version of our cart: just the item count line and the buy button, with `2` items in the cart:

```html title="index.html"
<section id="cart">
  <p id="items">Items: 2</p>
  <button id="buy">Buy 2 items</button>
</section>
```

Now the shopper adds a third item, so `count` becomes `3`. Our developer writes a `textContent` line to update the paragraph, **but forgets to update the button**. Compare what happens in plain JavaScript against React:

::: row caption="When count changes from 2 to 3: plain JavaScript updates the line and forgets the button, while React updates both places from count."
::: col title="Plain JavaScript" tag="one place forgotten" tone=bad
```shop size=mini
text: Items: 3 | good
button: Buy 2 items | bad | old count
```
```js title="page.js"
const count = 3;
items.~textContent~ = 'Items: ' + count; // **WRONG:** updates the line, but forgets the button!
```
The line says `3`. The button still says `2`.
:::
::: col title="React" tag="both places match" tone=good
```shop size=mini
text: Items: 3 | good
button: Buy 3 items | good
```
```jsx title="Cart.jsx"
export default function Cart() {
  const count = 3;
  return (
    <section>
      <p>Items: {~count~}</p> {/* 1. Reads count and shows 3 */}
      <button>Buy {~count~} items</button> {/* 2. Also reads count and shows 3 */}
    </section>
  );
}
```
Both places read `count`, so both show `3`.
:::
:::

### How JSX curly braces `{count}` keep every place in sync

Look at lines 5 and 6 of `Cart.jsx` above. The HTML-like tags inside the JavaScript function are called **JSX**. Inside JSX, curly braces `{count}` mean: **step into JavaScript, read the value of `count`, and put it right here**.

Because both the paragraph line and the button read `{count}`, you never write `textContent` instructions by hand. When the variable is `3`, both places show `3`:

```tree dir=right caption="Imperative DOM updates by hand vs. declarative UI with JSX curly braces in React."
How count = 3 reaches the screen
- !Imperative plain JavaScript [`items.textContent = ...`] | ~Do **NOT** update each DOM node by hand | You must remember **every id on the page** that shows `count` | Forgetting `buy.textContent` leaves **`Items: 3`** above **`Buy 2 items`**
- +Declarative React JSX [`{count}`] | +**DO** describe the UI from `count` | Both `<p>Items: {count}</p>` and `<button>Buy {count} items</button>` read **`count`** | React updates **every place** to **`3`** automatically
```

> [!PRINCIPLE]
> **Principle 1: Declarative UI: Describe What the Screen Should Show for the Current Data**
>
> *Write JSX that plugs your data variable into every place that displays it, and let React update the browser DOM.*
>
> In plain JavaScript, you must find and update each DOM element by hand whenever a number changes, and forgetting even one element leaves the screen out of sync. In React, you declare what the markup looks like for the current value of your variable, and React updates every matching place on the page together.
>
> **DO THIS:**
> ```jsx
> export default function Cart() {
>   const count = 3;
>   return (
>     <section>
>       <p>Items: {~count~}</p> {/* 1. Reads count and shows 3 */}
>       <button>Buy {~count~} items</button> {/* 2. Also reads count and shows 3 */}
>     </section>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> const count = 3;
> items.~textContent~ = 'Items: ' + count; // **WRONG:** updates the line, but forgets buy.textContent!
> ```

## 2. Principle 2: Component-Based Architecture: Build UIs from Reusable Pieces

### Splitting files by technology vs. bundling each UI piece into a component

In old plain-JavaScript projects, developers split code into files by **technology**: all the HTML markup lived in `index.html`, and all the DOM update lines lived in `page.js`. Whenever you changed the cart, you had to jump between both files and keep their `id` names matched by hand.

React replaces that split with **component-based architecture**. Each visual piece of the page lives in its own **component function** that bundles the piece's data and JSX markup together in one place:

```tree caption="Splitting a page by technology in plain JavaScript vs. bundling each visual piece into a React component."
Two ways to organize the code for a webpage
- !Split by technology [`index.html` + `page.js`] | ~Do **NOT** scatter one UI piece across separate HTML and selector files | Markup sits in **`index.html`** while update logic sits in **`page.js`** | Changing one UI piece forces you to hunt for matching `id` strings across files
- +Component-based architecture [`Cart.jsx` inside `App.jsx`] | +**DO** bundle each UI piece's data and markup into one component function | `Cart` keeps its **`count` data and `<section>` markup** together | Any parent component can place the cart with a single **`<Cart />`** tag
```

### How `App.jsx` places `Cart.jsx` on the page

In a React project, the whole page starts from a parent component named `App` in `App.jsx`. Our shopping cart lives in its own file, `Cart.jsx`. The parent file imports `Cart` and places it inside the main page tag with `<Cart />`:

```jsx title="App.jsx"
import ~Cart~ from './Cart.jsx'; // 1. Import the Cart component from its own file

export default function App() {
  return (
    <main>
      <h1>Shop</h1>
      ~<Cart />~ {/* 2. Place the Cart component inside <main> */}
    </main>
  );
}
```

```tree caption="The component hierarchy: App is the parent component that holds the page heading and places Cart."
App [parent component in `App.jsx`] | Holds the `<h1>Shop</h1>` heading and places `<Cart />`
- +Cart [child component in `Cart.jsx`] | Holds `count = 3` and returns `<section>` with the line and button
```

When React renders the parent component, it sees `<Cart />` and calls the `Cart` function. It then builds the browser DOM from the HTML tags that both functions return. If you open the **Elements panel** in Chrome, you see only lowercase HTML tags such as `<main>` and `<section>`. You never see `<App>` or `<Cart>` in the DOM, because component tags exist only for React:

```dom title="Elements panel" caption="The browser DOM in the Elements panel contains only the HTML tags returned by App and Cart."
<main>
  <h1>Shop</h1>
+ <section>
+   <p>Items: 3</p>
+   <button>Buy 3 items</button>
+ </section>
</main>
```

### What happens when a value is hardcoded inside a component

Putting markup inside `Cart.jsx` only keeps the cart in sync if **every place** that displays the count reads `{count}`. Suppose a developer uses `{count}` on the paragraph line, **but leaves a hardcoded `2` inside the button text**. That component will show two different numbers on the screen:

::: row caption="Inside Cart.jsx with count = 3: a hardcoded 2 on the button stays stuck at 2, whereas reading {count} in both places keeps the component in sync."
::: col title="Hardcoded 2 on the button" tag="out of sync" tone=bad
```shop size=mini
text: Items: 3 | good
button: Buy 2 items | bad | hardcoded 2
```
```jsx title="Cart.jsx"
export default function Cart() {
  const count = 3;
  return (
    <section>
      <p>Items: {count}</p>
      <button>Buy ~2~ items</button> {/* **WRONG:** hardcoded 2 never updates to 3! */}
    </section>
  );
}
```
The button ignores `count` and stays on `2`.
:::
::: col title="`{count}` in both places" tag="single source of truth" tone=good
```shop size=mini
text: Items: 3 | good
button: Buy 3 items | good
```
```jsx title="Cart.jsx"
export default function Cart() {
  const count = 3;
  return (
    <section>
      <p>Items: {~count~}</p> {/* 1. Reads count on the paragraph */}
      <button>Buy {~count~} items</button> {/* 2. Reads count on the button too */}
    </section>
  );
}
```
One variable feeds every place in the component.
:::
:::

> [!PRINCIPLE]
> **Principle 2: Component-Based Architecture: Bundle Markup and Data into Reusable Component Functions**
>
> *Package each piece of the interface into a component function that returns JSX, and read the component's variable in every line that shows that data.*
>
> A component keeps the data and the markup for one part of the page together in one function. Another component can place that piece anywhere with a single tag, and every line inside the component that reads the variable in curly braces stays in sync.
>
> **DO THIS:**
> ```jsx
> export default function Cart() {
>   const count = 3;
>   return (
>     <section>
>       <p>Items: {~count~}</p> {/* 1. Reads count on the paragraph */}
>       <button>Buy {~count~} items</button> {/* 2. Reads count in every place that shows the number */}
>     </section>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function Cart() {
>   const count = 3;
>   return (
>     <section>
>       <p>Items: {count}</p>
>       <button>Buy ~2~ items</button> {/* **WRONG:** hardcoded 2 stays stuck when count is 3! */}
>     </section>
>   );
> }
> ```

## 3. Principle 3: Virtual DOM: Update Only What Changed So State Survives

### Why replacing the whole box with `innerHTML` looks like it works at first, but is NOT the same thing as React

Now let us add a third element inside our shopping cart box. Between the item count paragraph and the buy button, we place an `<input>` text box where the shopper can type a delivery note:

```jsx title="Cart.jsx"
export default function Cart() {
  const count = 3;
  return (
    <section>
      <p>Items: {count}</p>
      ~<input placeholder="Note to the shop" />~ {/* Text box where the shopper types a delivery note */}
      <button>Buy {count} items</button>
    </section>
  );
}
```

Our `<section>` box now holds three elements in order:
1. First, the `<p>` paragraph showing the item count.
2. Second, the `<input>` text box for the shopper's delivery note.
3. Third, the `<button>` showing the item count.

When `count` rises from two to `3`, compare the two ways developers try to update the whole cart box at once:
- **Way 1**: Overwriting the container with `cart.innerHTML = ...` in plain JavaScript.
- **Way 2**: Returning the `<section>` JSX from `Cart` in React.

Before the shopper types anything into the text box, **both ways look the exact same on the screen**. Both update the two numbers to `3` with zero errors in the Console. **It may look the same, and it may seem to work the same at first, but it is NOT the same thing!**

Suppose the shopper starts with `2` items in the cart, clicks inside the `<input>` box, and types a delivery note asking the courier to ring the bell. While the cursor is still blinking inside that box, the shopper adds a third item so `count` rises from two to `3`.

Look at why `innerHTML` and React behave completely differently the moment that update happens:

### Why `cart.innerHTML` wipes out what the shopper typed

In plain JavaScript, some developers try to avoid forgetting `textContent` lines by rewriting the whole cart with `innerHTML` on each update. Watch what happens to the shopper's typed delivery note when `cart.innerHTML` runs:

::: row caption="When count changes from 2 to 3 while 'Please ring the bell' is typed in the input: innerHTML destroys the input and wipes the text, while React's virtual DOM updates only the two numbers."
::: col title="Plain JavaScript with innerHTML" tag="note wiped out" tone=bad
```shop size=mini
text: Items: 3 | good
input: Note to the shop | bad | empty again
button: Buy 3 items | good
```
```dom title="Elements panel"
<section id="cart">
! <p>Items: 3</p>
! <input placeholder="Note to the shop" />
! <button>Buy 3 items</button>
</section>
```
```js title="page.js"
const count = 3;
cart.~innerHTML~ = ` // **WRONG:** destroys all 3 DOM nodes!
  <p>Items: ${count}</p>
  <input placeholder="Note to the shop" />
  <button>Buy ${count} items</button>
`;
```
`innerHTML` throws away the old `<input>` DOM element and builds a brand-new empty one. The shopper's typed note and the cursor focus are gone!
:::
::: col title="React with the Virtual DOM" tag="note stays intact" tone=good
```shop size=mini
text: Items: 3 | good
typed: Please ring the bell | good | still here
button: Buy 3 items | good
```
```dom title="Elements panel"
<section>
+ <p>Items: 3</p>
* <input placeholder="Note to the shop" />
+ <button>Buy 3 items</button>
</section>
```
```jsx title="Cart.jsx"
export default function Cart() {
  const count = 3;
  return (
    <section>
      <p>Items: {~count~}</p> {/* 1. Updates only this number in the DOM */}
      <input placeholder="Note to the shop" />
      <button>Buy {~count~} items</button> {/* 2. And updates only this number in the DOM */}
    </section>
  );
}
```
React touches only the two `2` to `3` text nodes. The existing `<input>` DOM element stays in place with the shopper's typed note and cursor focus intact.
:::
:::

### How the virtual DOM works in three steps

When your `Cart` component returns JSX, it does **not** create real browser DOM elements directly. Instead, JSX creates lightweight JavaScript objects in memory called the **virtual DOM**. When `count` rises from two to `3`, React follows three steps:

1. **Create the new virtual DOM tree in memory**: React calls `Cart` and gets the new lightweight blueprint of the section, where both numbers are `3`.
2. **Compare the new virtual tree against the previous virtual tree**: React lines up the old description for `2` against the new description for `3` in memory. It sees that the outer section and the `<input>` text box did not change at all. Only the text inside the paragraph and the button changed to `3`.
3. **Patch only the changed nodes in the real browser DOM**: React updates only those two text nodes in the real DOM and leaves the `<input>` element untouched.

```tree dir=right caption="How React's virtual DOM updates the screen without destroying the live input element."
What happens when count changes from 2 to 3
- !Plain JS `cart.innerHTML = ...` | ~Do **NOT** replace a live container with `innerHTML` | Destroys the old `<p>`, `<input>`, and `<button>` DOM nodes and creates three new ones | Wipes out **`Please ring the bell`** and removes **cursor focus**
- +React Virtual DOM comparison | +**DO** return JSX and let React diff in memory | Compares old virtual tree [`2`] vs. new virtual tree [`3`] in JavaScript memory | Updates **only the two text nodes** to `3` and keeps **`Please ring the bell`** and **focus**
```

> [!PRINCIPLE]
> **Principle 3: Virtual DOM: Compare in Memory and Update Only the Changed DOM Nodes**
>
> *Return the full JSX description from your component on every update. React compares the new virtual DOM tree against the previous one in memory and patches only the changed DOM nodes.*
>
> Replacing a container with `innerHTML` destroys every real DOM element inside it and builds new ones, which wipes out typed input text and cursor focus. React's virtual DOM compares lightweight JavaScript descriptions in memory first and updates only the changed text nodes, so untouched inputs keep their typed text and focus.
>
> **DO THIS:**
> ```jsx
> export default function Cart() {
>   const count = 3;
>   return (
>     <section>
>       <p>Items: {~count~}</p> {/* 1. Updates only this text node */}
>       <input placeholder="Note to the shop" /> {/* 2. Same DOM node stays alive with typed text and focus */}
>       <button>Buy {~count~} items</button> {/* 3. Updates only this text node */}
>     </section>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> cart.~innerHTML~ = ` // **WRONG:** destroys the live <input> DOM node and erases typed text and focus!
>   <p>Items: ${count}</p>
>   <input placeholder="Note to the shop" />
>   <button>Buy ${count} items</button>
> `;
> ```

## Putting All Three Principles Together

First, here is the complete `Cart.jsx` file bundling the count data, the paragraph, the note input, and the buy button:

```jsx title="Cart.jsx"
export default function ~Cart~() { // Principle 2: Reusable component function bundling data and markup
  const count = 3;

  return (
    <section>
      <p>Items: {~count~}</p> {/* Principle 1: Declarative UI reads count */}
      <input placeholder="Note to the shop" /> {/* Principle 3: Virtual DOM keeps this input alive on update */}
      <button>Buy {~count~} items</button> {/* Principle 1: Second place reading count stays in sync */}
    </section>
  );
}
```

Next, here is `App.jsx` importing that component and placing `<Cart />` inside the page:

```jsx title="App.jsx"
import ~Cart~ from './Cart.jsx'; // 1. Import the Cart component from its file

export default function App() {
  return (
    <main>
      <h1>Shop</h1>
      ~<Cart />~ {/* 2. Principle 2: Place Cart on the page */}
    </main>
  );
}
```

```shop caption="The finished Cart component inside our Shop page: both count places show 3, and the shopper's typed note stays intact."
product: 🧦 | Wool socks | $9
product: ☕ | Ceramic mug | $14
product: 📓 | Pocket notebook | $6
text: Items: 3 | good
typed: Please ring the bell | good
button: Buy 3 items | good
```

| Characteristic | Plain JavaScript Habit | The React Way |
| :--- | :--- | :--- |
| **1. Declarative UI** | Find each DOM node and set `textContent` step by step. | Plug `{count}` into JSX; React updates every place that reads it. |
| **2. Component-Based Architecture** | Keep HTML in `index.html` and DOM selectors in `page.js`. | Bundle data and JSX into `Cart.jsx` and place it with `<Cart />`. |
| **3. Virtual DOM** | Replace the container with `innerHTML`, wiping `<input>` text and focus. | Compare virtual DOM objects in memory and patch only the changed text nodes. |

## For the Interview

> **The Interview Question:** What is React, and what are its main characteristics (declarative UI, component-based architecture, virtual DOM)?

### How to Answer Clearly in 30 Seconds

"React is a JavaScript library for building user interfaces around three main characteristics. First, React is **declarative**: instead of writing step-by-step DOM instructions like `textContent`, you describe what the screen should look like for the current data using JSX. React then updates every place on the screen that reads that data. Second, React is **component-based**: you build the page from small, self-contained functions such as `Cart` inside `App`. Each component bundles its own data and markup and is placed with a tag like `<Cart />`. Third, React uses a **virtual DOM**: when data changes, your component returns a new lightweight JavaScript description of the UI in memory. React compares it against the previous description and patches only the changed real DOM nodes, preserving typed text and cursor focus inside an `<input>`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What is the difference between imperative and declarative UI?"**
   - **Answer**: In an imperative UI, you write step-by-step instructions to find each DOM element and mutate it when data changes. If you update the item count line and forget the buy button, the screen goes out of sync. In a declarative UI, you write one JSX description that reads `{count}` in both places, and React updates the DOM to match that description.
2. **"Why don't component tags like `<App>` and `<Cart>` show up in the browser's Elements panel?"**
   - **Answer**: Because `<App />` and `<Cart />` are React component tags that tell React which JavaScript functions to call. The browser DOM only receives the lowercase HTML tags, such as `<main>`, `<section>`, `<p>`, `<input>`, and `<button>`, that those functions ultimately return.
3. **"Why can't we just re-render a component by setting `innerHTML` on its container?"**
   - **Answer**: Setting `innerHTML` destroys every existing DOM node inside the container and creates brand-new DOM nodes from scratch. That wipes out anything the user typed into an `<input>` and loses cursor focus. React's virtual DOM compares the old and new UI descriptions in memory first and updates only the changed text nodes, leaving the existing `<input>` DOM node intact.
