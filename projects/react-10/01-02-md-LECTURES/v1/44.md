## How a Like Shows Before the Server Confirms

### The heart that turns red before the server answers

Open a photo post on Instagram. Under the photo sit its title, `Sunset at the beach`, and a heart button that reads `🤍 Like`:

```page caption="A photo post with its title and a white heart button, before the user clicks."
line: Sunset at the beach
form:
  submit: 🤍 Like
console: quiet
```

The user clicks the heart, and it turns red at once. It now reads `❤️ Liked`:

```page caption="The same post right after the user clicks the heart, while the server is still saving the like."
line: Sunset at the beach
form:
  submit: ❤️ Liked | | good
console: quiet
```

Behind the screen, the app sends the like to the server, and the server needs about one second to save it. The user never sees that second. As far as the user can tell, the like is already done.

Every app with a like button behaves like this. Now look at the same screen as the developer who builds it. The server has not answered yet, so our code does not know whether the like is saved. Yet the heart is already red.

The page shows the answer it hopes for. While the save runs, React shows the value we expect, a red heart, through a Hook called `useOptimistic`. When the save ends, React shows the real value again, the one the server saved.

### Why it is called "optimistic"

An optimist is a person who expects things to go well. Here, the page is the optimist. It expects the save to succeed, so it shows the result before the server says so. React's docs give the same reason for the name: this state "is called the 'optimistic' because it is used to immediately present the user with the result of performing an Action, even though the Action actually takes time to complete."

So two values sit behind one heart button:
- **The real state** is what the server saved. In our page it is `liked`, and it changes only when the server answers.
- **The optimistic state** is what the page shows while the save runs. In our page it is `optimisticLiked`, and it holds the hoped-for answer during the wait.

What the two share: both are values that React keeps for the component, and the button can draw the heart from either one. The one difference is time. Before the click and after the save, the two hold the same value. Only during the one-second wait can they differ.

```tree caption="The real state and the optimistic state of one like button: the same value, except during the wait."
Two values behind one heart button
- +The real state [`liked`] | Changes **only when the server answers** | Before the click and after the save, it decides what the heart shows
- +The optimistic state [`optimisticLiked`] | Holds the **hoped-for answer** while the save runs | During the wait, the heart shows **this value**
```

### What is at stake

The key idea to remember is this: **the optimistic state is temporary.** React's docs say it in one sentence: "Optimistic state only renders while an Action is in progress, otherwise `value` is rendered." Every principle of this lesson comes from that sentence.

What is at stake is what the user sees during that one second:
1. Without an optimistic state, the heart stays white for one second after the user clicks it.
2. The user thinks the click did not work, and clicks again.
3. If we show the red heart first with a plain `useState` and the save fails, the page keeps a red heart that the server never saved. Only extra code of ours can turn it white again.

Readers usually go wrong in two places:
1. They call the set function of `useOptimistic` in an `onClick` handler. The heart flashes red, turns white again, and the Console shows an error. Principle 2 shows why.
2. They think they must clear the optimistic state after the save. React does that by itself, and the real state decides what stays. Principle 3 shows how.

### Three ways to show the result of a click

Developers choose between three ways for this same job:
1. **Wait for the server, then show the result.** `useActionState` alone does this (as seen in Lesson 42), with `isPending` or `useFormStatus` for a "saving" sign (as seen in Lesson 43). It fits when the result cannot be guessed, such as a payment or a sign-up that the server may refuse.
2. **Show the result first with `useState`, and set it back by hand when the save fails.** This is the old way. React's blog describes it: "In the past, you would need to handle pending states, errors, optimistic updates, and sequential requests manually."
3. **Show the result first with `useOptimistic`.** It fits when the save almost always succeeds and the user expects to see the change at once: a like, a follow, a new message in a chat. React shows the hoped-for value during the save, and shows the real state again when the save ends.

This lesson is about the third way.

```tree caption="Three ways to show the result of a click that the server must save."
Three ways to show the result of a click
- +1. Wait for the server [`useActionState`] | Shows a **saving sign** during the wait | Fits when the result **cannot be guessed**, such as a payment
- !2. Show it first with `useState` | Our code **sets it back by hand** on every failure | Forget one failure, and the page **keeps a value the server never saved**
- +3. Show it first with `useOptimistic` | React shows the **hoped-for value** during the save | When the save ends, React shows the **real state** again by itself
```

```js title="src/api.js"
}
```

### The five principles

**PRINCIPLES:** The page can show the answer before the server gives it, because React keeps a second, temporary value for the wait. Five practical rules follow:
1. **Principle 1: `useOptimistic` Turns the Heart Red at Once.** The form's action puts the hoped-for value into the optimistic state first, and starts the save second. The button must read the optimistic state, or it still waits for the server.
2. **Principle 2: `setOptimisticLiked` in `onClick` Flashes the Heart.** The set function works only inside an Action. Called in `onClick`, it shows the red heart for a moment, then the white heart comes back, and the Console logs an error.
3. **Principle 3: `liked` Keeps the Heart Red After the Save.** No line of our code clears the optimistic state. When the Action ends, the optimistic state equals the value we passed to `useOptimistic` again, so that value must be the real state, not a fixed `false`.
4. **Principle 4: A Failed Save Turns the Heart White Again.** When the server fails, the real state does not change. When the Action ends, the page shows what it showed before the click, and no undo code is needed.
5. **Principle 5: One Reducer Moves the Heart and the Count Together.** When one click changes two values on the page, one reducer computes both, so the heart and the like count never disagree during the wait.

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`useOptimistic` Turns the Heart Red at Once** | A button that still reads `liked` stays white for one second after the click, as if the Hook did nothing. | Call `useOptimistic(liked)`, call the set function first inside the form's action, and render the optimistic state. |
| **Principle 2** | **`setOptimisticLiked` in `onClick` Flashes the Heart** | In `onClick`, the red heart lasts only a moment, and the Console logs "An optimistic state update occurred outside a transition or action." | Call the set function inside an Action, such as the function passed to the form's `action`. |
| **Principle 3** | **`liked` Keeps the Heart Red After the Save** | With `useOptimistic(false)`, the heart turns white again one second after a like that the server saved. | Pass the real state to `useOptimistic`, and let React end the optimistic state when the Action ends. |
| **Principle 4** | **A Failed Save Turns the Heart White Again** | A hand-made `useState` version forgets one failure and keeps a like that the server never saved. | On failure, return the previous state from the reducer action; React shows it when the Action ends. |
| **Principle 5** | **One Reducer Moves the Heart and the Count Together** | A count read from the real state shows `12 likes` next to a red heart for one second. | Pass a reducer as the second argument of `useOptimistic`, and read every value the click changes from the optimistic state. |

## 1. Principle 1: `useOptimistic` Turns the Heart Red at Once

### The Hook in its smallest code

`useOptimistic` is a React Hook that lets you "optimistically update the UI", in the words of React's docs. It comes from `'react'`, like `useState`. Here it is in its fewest lines. The first line keeps the real like with `useActionState` (as seen in Lesson 42):

```jsx title="useOptimistic in its smallest code"
const [liked, likeAction] = useActionState(updateLike, false); // The real state: changes when the save ends
const [optimisticLiked, setOptimisticLiked] = ~useOptimistic(liked)~; // The optimistic state: equals liked until an Action sets it

async function submitAction() {
  ~setOptimisticLiked(true)~; // 1. The heart turns red at once
  return likeAction(true); // 2. Then the save starts, and takes one second
}

<form action={submitAction}>
  <button type="submit">{~optimisticLiked~ ? '❤️ Liked' : '🤍 Like'}</button> {/* The button reads the optimistic state */}
</form>
```

`useOptimistic` gives back a pair, which we name in square brackets, as with `useState` (as seen in Lesson 12):
- **`optimisticLiked` is the optimistic state.** While no Action is pending, it equals the value we pass in. While an Action is pending, it equals the value our code passed to the set function.
- **`setOptimisticLiked` is the set function.** React's docs say it "lets you update the state for the duration of an Action". The words "for the duration" matter: the value lasts as long as the Action, and no longer.

The value we pass in, `liked`, is what React's docs call `value`: "The value returned when there are no pending Actions." So before the click, `optimisticLiked` is `false`, because `liked` is `false`.

`submitAction` is our own function. We pass it to the form's `action`, so React calls it inside a Transition when the user clicks the submit button. That makes it an Action (as seen in Lesson 41). The `true` in `likeAction(true)` is the payload: React passes it to `updateLike` as the second parameter, after the previous state (as seen in Lesson 42).

### The button reads `liked` vs. the button reads `optimisticLiked`

Both buttons below draw the heart from a value that React keeps for the component. The one difference is which value they read:

```jsx title="The heart button that reads liked, and the heart button that reads optimisticLiked"
<button type="submit">{~liked~ ? '❤️ Liked' : '🤍 Like'}</button> {/* White for one second after the click, then red */}
<button type="submit">{~optimisticLiked~ ? '❤️ Liked' : '🤍 Like'}</button> {/* Red at once */}
```

It may look the same, or work the same at first, but it is NOT the same thing! Before the click, both values are `false`, so both buttons show the white heart. During the one-second wait, they split. `liked` is still `false`, because the server has not answered. `optimisticLiked` is already `true`, because the form's action passed `true` to the set function.

::: row caption="During the one-second save, the button that reads liked still shows the white heart; the button that reads optimisticLiked already shows the red one."

```page size=mini

  submit: 🤍 Like | | bad
```
:::
::: col title="The button reads optimisticLiked" tag="red at once" tone=good

Developers really make this mistake. They add the `useOptimistic` line and call the set function in the form's action, but the button still reads `liked`. The user clicks the heart, and it stays white for one second, as if the Hook did nothing. The fix is one word in the button: read `optimisticLiked`.

### What React does during that one second

**The heart turns red before the save starts, and stays red while the save runs.** Here are the steps in the order React takes them:
1. The user clicks the white heart, and React calls `submitAction` inside a Transition, because it is the form's action.
2. `setOptimisticLiked(true)` runs first. React renders at once with `true`, and the heart reads `❤️ Liked`.
3. `likeAction(true)` calls `updateLike`, which waits one second for `saveLike`.
4. During that whole second, `liked` is still `false`, but React keeps showing `true`, so the heart stays red.

React's docs describe the same order: "When `setOptimistic('b')` is called, React immediately renders with `'b'`," and "If you await in the Action, React continues showing `'b'`."

### The like button of our page

Now the whole `LikeButton` file. `updateLike` is the reducer action of `useActionState`: it waits for the save and returns the new like, which becomes `liked`. Its first parameter, `wasLiked`, is the previous state. This version does not use it yet; Principle 4 does. `submitAction` sets the hoped-for value first and starts the save second, the same shape React's docs use for a form with `useOptimistic`:

```jsx title="src/LikeButton.jsx"
import { useActionState, ~useOptimistic~ } from 'react'; // useOptimistic comes from react, like useState
import { saveLike } from './api.js';

async function updateLike(wasLiked, nextLiked) {
  await saveLike(nextLiked);
  return nextLiked;
}

export default function LikeButton() {
  const [liked, likeAction] = useActionState(updateLike, false);
  const [optimisticLiked, setOptimisticLiked] = ~useOptimistic(liked)~; // Equals liked whenever no Action is pending

  async function submitAction() {
    const nextLiked = ~!optimisticLiked~; // A click on the red heart sends false and unlikes the post
    setOptimisticLiked(nextLiked);
    return likeAction(nextLiked);
  }

  return (
    <form action={submitAction}>
      <button type="submit">{optimisticLiked ? '❤️ Liked' : '🤍 Like'}</button>
    </form>
  );
}
```

`nextLiked` comes from `optimisticLiked`, the heart the user sees. So the same button both likes and unlikes the post: a click on the white heart sends `true`, and a click on the red heart sends `false`.

```tree dir=right caption="What the heart shows before the click, during the one-second save, and after the save."
One click by the user on the white heart
- +Before the click | `liked` is **false**; `optimisticLiked` equals it | The heart is **white**
- +During the save | `liked` is still **false**; `optimisticLiked` is **true** | The heart is **red at once**
- +After the save | `liked` is **true**; `optimisticLiked` equals it again | The heart **stays red**
```

> [!PRINCIPLE]
> **Principle 1: useOptimistic: The Button Reads the Optimistic State**
>
> *Call `useOptimistic(liked)`, call its set function first inside the form's action, and let the button read the optimistic state, so the heart turns red while the save is still running.*
>
> When a user clicks a heart, the server needs about one second to save the like. A button that reads the real state waits for that second, and the user thinks the click did not work. `useOptimistic` gives the component a second value for the wait. The form's action puts the hoped-for value into it at once, and the button shows that value until the save ends.
>
> **DO THIS:**
> ```jsx
> const [optimisticLiked, setOptimisticLiked] = useOptimistic(liked);
>
> <button type="submit">{~optimisticLiked~ ? '❤️ Liked' : '🤍 Like'}</button> {/* Red as soon as the form's action calls the set function */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [optimisticLiked, setOptimisticLiked] = useOptimistic(liked);
>
> <button type="submit">{~liked~ ? '❤️ Liked' : '🤍 Like'}</button> {/* **WRONG:** the Hook runs, but the heart stays white until the server answers */}
> ```

## 2. Principle 2: `setOptimisticLiked` in `onClick` Flashes the Heart

### The same line in two places

A developer wants the heart to change "on click", so the `onClick` handler looks like the natural place for the set function. Here is the same call in two places. First, in `onClick` on the button:

```jsx title="setOptimisticLiked in onClick"
<form action={submitAction}>
  <button type="submit" ~onClick~={() => setOptimisticLiked(true)}>🤍 Like</button> {/* A plain event handler, outside any Action */}
</form>
```

Then, inside the form's action:

```jsx title="setOptimisticLiked in the form's action"
async function ~submitAction~() { // The form's action: React calls it inside a Transition
  setOptimisticLiked(true);
  return likeAction(true);
}
```

What the two share: both run when the user clicks the heart. The one difference is how React calls them. React calls the form's action inside a Transition, which makes it an Action. React calls `onClick` as a plain event handler, outside any Action.

It may look the same, or work the same at first, but it is NOT the same thing! The optimistic state lives only as long as an Action. In `onClick`, there is no Action around the call, so nothing holds the red heart.

### What the user sees with the set function in `onClick`

**With the set function in `onClick`, the red heart lasts only a moment. The white heart comes back at once, and the red one returns only when the save ends.**

Here is the broken version of our file. `onClick` sets the optimistic state, and the form's action only starts the save:

```jsx title="src/LikeButton.jsx" startLine="13"
  async function submitAction() {
    return likeAction(!liked);
  }

  return (
    <form action={submitAction}>
      <button
        type="submit"
        ~onClick~={() => setOptimisticLiked(!optimisticLiked)} // **WRONG:** runs outside any Action, so the red heart does not last
      >
        {optimisticLiked ? '❤️ Liked' : '🤍 Like'}
      </button>
    </form>
  );
```

When the user clicks the white heart, this happens:
1. `onClick` runs first, as a plain event handler. The set function logs an error in the Console, and the heart reads `❤️ Liked` for a moment.
2. React shows the white heart again at once. No Action holds the optimistic state, so it equals `liked` again, and `liked` is still `false`.
3. The form's action starts the save. After one second, `liked` becomes `true`, and the heart turns red for good.

React's docs explain step 2: "When you call the setter outside an Action, the optimistic state will briefly appear and then immediately revert back to the original value. This happens because there's no Transition to 'hold' the optimistic state while your Action runs."

```page caption="The post during the one-second save, with the set function in onClick: the white heart is back, and the Console shows React's error."
line: Sunset at the beach
form:
  submit: 🤍 Like | | bad
console: An optimistic state update occurred outside a transition or action. To fix, move the update to an action, or wrap with startTransition.
```

The error names the fix: "move the update to an action". On our page, the Action is `submitAction`. When we move the line back into it, we get the file of Principle 1 again, where the heart turns red at once and stays red.

### Why the form's action needs no `startTransition`

The error names a second fix, `startTransition`, which a later lesson teaches. Our form does not need it. React's docs call a prop like the form's `action` an **Action prop**: a prop whose function React already calls inside a Transition. In the docs' words: "When using Action props, you can call the set function without `startTransition`." "This works because Action props are already called inside `startTransition`."

So the set function belongs in the function we pass to the form's `action`. By React's convention, the name of such a function ends in "Action", and `submitAction` follows it.

```tree caption="The same set function call in onClick and in the form's action: only the form's action is inside an Action."
Where `setOptimisticLiked` runs on the click
- !In `onClick` [`onClick`] | A **plain event handler**, outside any Action | The red heart **flashes**, the white heart comes back, and the Console logs an **error**
- +In the form's action [`submitAction`] | React calls it **inside a Transition** | The red heart **stays** for the whole save
```

> [!PRINCIPLE]
> **Principle 2: Inside an Action: Call the Set Function in the Form's Action**
>
> *Call the set function of `useOptimistic` inside an Action, such as the function passed to the form's `action`, never in a plain `onClick` handler.*
>
> The optimistic state lasts only as long as an Action. The form's `action` is an Action prop: React calls our function inside a Transition, and that Transition holds the red heart until the save ends. A plain `onClick` handler has no Transition around it. The red heart shows for a moment, the white heart comes back, and React logs an error in the Console.
>
> **DO THIS:**
> ```jsx
> async function submitAction() {
>   ~setOptimisticLiked(true)~; // Inside the form's action: the red heart stays until the save ends
>   return likeAction(true);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button type="submit" ~onClick~={() => setOptimisticLiked(true)}>🤍 Like</button> {/* **WRONG:** outside any Action, the heart flashes and React logs an error */}
> ```

## 3. Principle 3: `liked` Keeps the Heart Red After the Save

### No line of our code turns the optimistic state off

Look again at the `LikeButton` file of Principle 1. `submitAction` calls the set function once, at the start. No line calls it again after the save. Yet after the save, the heart stays red.

The heart stays red because of the value we passed to `useOptimistic`, not because of the set function. React's docs title one of their notes "Optimistic state is temporary". When the Action ends, the optimistic state equals the value we passed in again. In our file that value is `liked`, the **real state**: the value the save sets.

**The optimistic state ends by itself when the Action ends, and the real state decides what stays on the page.** Here is what happens after the user clicks the white heart and it turns red:
1. After one second, `updateLike` returns `true`, and `useActionState` stores it as `liked`.
2. The Action ends.
3. React renders once with `liked` as `true`. `optimisticLiked` is `true` again, but now because it equals `liked`.
4. The heart stays red. There is no white moment between the hoped-for heart and the real one.

React's docs say there is no extra render to clear the optimistic state: the optimistic state and the real state meet in the same render, when the Transition ends.

### Passing `liked` vs. passing `false`

The heart starts white, so `false` looks like a fine value to pass to `useOptimistic`. Here are both lines:

```jsx title="Passing the real state, and passing a fixed false"
const [optimisticLiked, setOptimisticLiked] = useOptimistic(~liked~); // After the save, it equals liked, which is true: the heart stays red
const [optimisticLiked, setOptimisticLiked] = useOptimistic(~false~); // After the save, it equals false again: the heart turns white
```

It may look the same, or work the same at first, but it is NOT the same thing! Both turn the heart red at once, because during the Action both show the value our code passed to the set function. After the save, only the first stays red. React's docs: "The `value` argument to `useOptimistic` determines what displays after the Action finishes."

Here is how this mistake reaches a real user:
1. A developer writes `useOptimistic(false)`, since the heart starts white.
2. The user clicks, and the heart turns red at once.
3. The server saves the like.
4. One second after the click, the heart turns white again.
5. The user thinks the like was lost and clicks again. `optimisticLiked` is `false`, so the click sends `true` once more: the same like, saved a second time.

The fix is to pass the real state, `useOptimistic(liked)`. Then, after every save, the page shows what the server saved.

> [!PRINCIPLE]
> **Principle 3: The Real State: Pass liked, and Let React End the Optimistic State**
>
> *Pass the real state to `useOptimistic`, and never clear the optimistic state by hand: when the Action ends, the optimistic state equals that value again.*
>
> The optimistic state is temporary. No line of our code turns it off. React ends it when the Action ends, in the same render that shows the saved value. So what the user sees after the save is the value we passed to `useOptimistic`. A fixed `false` turns the heart white again after a like the server saved.
>
> **DO THIS:**
> ```jsx
> const [optimisticLiked, setOptimisticLiked] = useOptimistic(~liked~); // After the save, the heart shows what the server saved
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [optimisticLiked, setOptimisticLiked] = useOptimistic(~false~); // **WRONG:** after a saved like, the heart turns white again
> ```

## 4. Principle 4: A Failed Save Turns the Heart White Again

### When the server cannot save the like

So far the server always saves the like. Real servers sometimes fail. To see a failure, we change one line in the given `src/api.js`. The fake save now returns `false`, which means the server could not save the like:

```js title="src/api.js" bad="3"
export async function saveLike(liked) {
  await new Promise(resolve => setTimeout(resolve, 1000));
  return ~false~; // The server could not save the like
}
```

The `updateLike` of Principle 1 does not look at what `saveLike` returns. It always returns `nextLiked`, which is `true`, so `liked` becomes `true` although the server saved nothing. The heart stays red after the failure.

So `updateLike` must check the answer. When the save fails, it returns `wasLiked`, the previous state, which `useActionState` passes as the first parameter (as seen in Lesson 42):

```js title="src/LikeButton.jsx" startLine="4"
async function updateLike(wasLiked, nextLiked) {
  const saved = await saveLike(nextLiked);
  return saved ? nextLiked : ~wasLiked~; // On failure, liked stays what it was before the click
}
```

The failure is returned as the state, not thrown, the way a known error is handled (as seen in Lesson 42). With `useActionState`, a thrown error goes to the nearest Error Boundary, which a later lesson teaches.

### What the user sees when the save fails

**When the save fails, the heart turns white again by itself. No line of our code says "undo the like".** Here is what happens after the user clicks the white heart:
1. The heart turns red at once, as in Principle 1.
2. After one second, `saveLike` returns `false`.
3. `updateLike` returns `wasLiked`, which is `false`. So `liked` stays `false`.
4. The Action ends, and the optimistic state equals `liked` again.
5. The heart reads `🤍 Like` again.

This is the same step as in Principle 3: the optimistic state ends, and the real state shows. After a success, the real state is the new like. After a failure, the real state is still the old one. React's docs call this a roll back: "the UI automatically rolls back". React's blog says Actions "revert optimistic updates to their original value automatically".

```page caption="The post during the one-second save that will fail: the heart is red."

  submit: ❤️ Liked
console: quiet
```

```page caption="The same post after the save fails: the heart is white again, as it was before the click."
line: Sunset at the beach
form:
  submit: 🤍 Like | | good
console: quiet
```

### The hand-made way vs. `useOptimistic`

Before `useOptimistic`, developers showed the like first with `useState` and turned it back by hand. What the two ways share: both show the red heart first, and the old heart after a failure. The one difference is who does the second step. Here is the hand-made way:

```jsx title="Showing the like first with useState, and setting it back by hand"
const [liked, setLiked] = useState(false);

async function handleLike() {
  setLiked(true);
  const saved = await saveLike(true);
  if (!saved) ~setLiked(false)~; // Our code turns the heart white again on failure
}
```

And here is the `useOptimistic` way. The set function in the form's action shows the red heart, as before, and on failure the reducer action only keeps the old value:

```js title="Keeping the previous state on failure, with useOptimistic"
async function updateLike(wasLiked, nextLiked) {
  const saved = await saveLike(nextLiked);
  return saved ? nextLiked : ~wasLiked~; // Nothing to undo: liked simply stays as it was
}
```

When the hand-made way is written correctly, yes, it is the exact same thing on the screen! The heart is red at once, and white again after the failure. With `useState`, our code turns it back. With `useOptimistic`, React does.

The hand-made way breaks as soon as one failure is forgotten:
1. A developer shows the like first with `setLiked(true)`, then calls the server.
2. They write `setLiked(false)` for the case where the server answers `false`.
3. They forget the case where the request itself fails, such as a lost connection. Then `saveLike` throws, and the line with `setLiked(false)` never runs.
4. The heart stays red.
5. The next time the user opens the post, the server says it is not liked, and the heart is white.

With `useOptimistic`, the red heart is never stored in state. It lasts only as long as the Action, so there is nothing to turn back.

```tree caption="Who turns the heart white again after a failed save: our code with useState, or React with useOptimistic."
Turning the heart white again after a failed save
- !Show it first with `useState` [`setLiked`] | Our code **sets it back by hand** | Forget one failure, and the heart **stays red** although the server saved nothing
- +Show it first with `useOptimistic` [`wasLiked`] | `liked` **does not change** on failure | When the Action ends, the heart shows **what it showed before the click**
```

From here on, `src/api.js` returns `true` again, and `updateLike` keeps its check of `saved`.

> [!PRINCIPLE]
> **Principle 4: Roll Back: A Failed Save Leaves the Real State Unchanged**
>
> *When the save fails, return the previous state from the reducer action; when the Action ends, the page shows what it showed before the click, with no undo code.*
>
> A hand-made version with `useState` stores the red heart for real, so our code must turn it back on every failure, and a forgotten failure keeps a like that the server never saved. With `useOptimistic`, the red heart lasts only as long as the Action. On failure, `liked` stays as it was, and React shows it again when the Action ends.
>
> **DO THIS:**
> ```js
> async function updateLike(wasLiked, nextLiked) {
>   const saved = await saveLike(nextLiked);
>   return saved ? nextLiked : ~wasLiked~; // On failure, the heart goes back to what it was before the click
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> async function updateLike(wasLiked, nextLiked) {
>   await saveLike(nextLiked);
>   return ~nextLiked~; // **WRONG:** ignores the failure, so the heart stays red although the server saved nothing
> }
> ```

## 5. Principle 5: One Reducer Moves the Heart and the Count Together

### One click, two values on the page

Instagram shows a count under the heart, such as `12 likes`. Now one click by the user changes two things on the page: the heart and the count. So the like becomes one object with two fields, `liked` and `likes`, and the real state is now `post`:

```jsx title="The post as one object in the real state"
const [post, likeAction] = useActionState(updateLike, ~{ liked: false, likes: 12 }~); // The heart and the count, in one object
```

`useOptimistic` takes an optional second argument for this case, a **reducer**. React's docs describe it as "The reducer function that specifies how the optimistic state gets updated. It must be pure, should take the current state and reducer action arguments, and should return the next optimistic state."

```jsx title="useOptimistic with a reducer"
const [optimisticPost, setOptimisticPost] = useOptimistic(
  post,
  ~(current, liked) => ({ liked, likes: current.likes + (liked ? 1 : -1) })~ // The current state and the new like in, the next state out
);
```

The reducer returns a new post. Its `liked` is the new like, and its count goes up by one when the user likes the post, and down by one when the user unlikes it.

It is the same kind of reducer you already know: the current state and an action in, the next state out (as seen in Lesson 27), and it must be pure (as seen in Lesson 14). The one difference is that its result shows only while the Action runs. Its two parameters come from two places:
- **`current`** is supplied by React: the current state, here `post` at the start of the Action.
- **`liked`** is supplied by our code: the value we pass to `setOptimisticPost`. React's docs: "If you provided a `reducer` to `useOptimistic`, this value will be passed as the second argument to your reducer."

### The count from `post` vs. the count from `optimisticPost`

The heart already reads `optimisticPost.liked`. The count line can read the real state or the optimistic state:

```jsx title="The count line that reads post, and the count line that reads optimisticPost"
<p>{~post.likes~} likes</p> {/* 12 likes for one second, then 13 likes */}
<p>{~optimisticPost.likes~} likes</p> {/* 13 likes at once */}
```

It may look the same, or work the same at first, but it is NOT the same thing! Before the click, both lines read `12 likes`. During the wait, the heart is already red. The count that reads `post` still says `12 likes`, because the server has not answered. The user sees a liked post whose count did not change.

::: row caption="During the one-second save: the count from post disagrees with the red heart; the count from optimisticPost agrees with it."
::: col title="The count reads post" tag="12 likes next to a red heart" tone=bad
```page size=mini

form:
  submit: ❤️ Liked
line: 12 likes | bad
```
:::
::: col title="The count reads optimisticPost" tag="13 likes next to a red heart" tone=good
```page size=mini
line: Sunset at the beach
form:
  submit: ❤️ Liked
line: 13 likes | good
```
:::

React's docs give the rule: "When an optimistic update affects multiple related values, use a reducer to update them together." Every value that the user sees change on the click must come from the same optimistic state.

### What one click does to both values

**One call to the set function moves the heart and the count in the same render.** Here is what happens after the user clicks the white heart above `12 likes`:
1. `setOptimisticPost(true)` passes `true` to the reducer as its second argument.
2. The reducer returns `{ liked: true, likes: 13 }`.
3. React renders with that object: the heart turns red and the count reads `13 likes`, together.
4. After the save, the real `post` is `{ liked: true, likes: 13 }`, and the optimistic state equals it. Nothing moves on the screen.

### The final like button

Here is the final `LikeButton` file. The reducer gets a name, `applyLike`, so that `updateLike` can use it too. The first parameter of `updateLike` is now called `previousPost`, because the previous state is the whole post, not only the like:

```jsx title="src/LikeButton.jsx"
import { useActionState, useOptimistic } from 'react';
import { saveLike } from './api.js';

function ~applyLike~(current, liked) { // The reducer: one place that computes the heart and the count
  return { liked, likes: current.likes + (liked ? 1 : -1) };
}

async function updateLike(previousPost, nextLiked) {
  const saved = await saveLike(nextLiked);
  return saved ? ~applyLike(previousPost, nextLiked)~ : previousPost; // The saved post uses the same reducer
}

export default function LikeButton() {
  const [post, likeAction] = useActionState(updateLike, { liked: false, likes: 12 });
  const [optimisticPost, setOptimisticPost] = ~useOptimistic(post, applyLike)~; // The second argument is the reducer

  async function submitAction() {
    const nextLiked = !optimisticPost.liked;
    setOptimisticPost(nextLiked);
    return likeAction(nextLiked);
  }

  return (
    <form action={submitAction}>
      <button type="submit">{optimisticPost.liked ? '❤️ Liked' : '🤍 Like'}</button>
      <p>{~optimisticPost.likes~} likes</p> {/* Reads the optimistic state, like the heart */}
    </form>
  );
}
```

`useOptimistic` and `updateLike` share `applyLike`, so the hoped-for count and the saved count are computed the same way. A real server would send back the saved count. Our fake `saveLike` returns only `true` or `false`.

```page caption="The final page before the user clicks the heart."
line: Sunset at the beach
form:
  submit: 🤍 Like
line: 12 likes
console: quiet
```

```page caption="The final page during the save and after it: the heart and the count change together."
line: Sunset at the beach
form:
  submit: ❤️ Liked | | good
line: 13 likes | good
console: quiet
```

> [!PRINCIPLE]
> **Principle 5: One Reducer: Every Value the Click Changes Comes from the Optimistic State**
>
> *When one click changes several values on the page, pass a reducer as the second argument of `useOptimistic`, and read every one of those values from the optimistic state.*
>
> The heart and the count answer the same question: did the user like this post? If the heart reads the optimistic state and the count reads the real state, the page gives two different answers for one second. A reducer computes the heart and the count from one call to the set function, so both change in the same render.
>
> **DO THIS:**
> ```jsx
> <button type="submit">{optimisticPost.liked ? '❤️ Liked' : '🤍 Like'}</button>
> <p>{~optimisticPost.likes~} likes</p> {/* 13 likes at the same moment as the red heart */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button type="submit">{optimisticPost.liked ? '❤️ Liked' : '🤍 Like'}</button>
> <p>{~post.likes~} likes</p> {/* **WRONG:** 12 likes next to a red heart for one second */}
> ```

```jsx title="src/LikeButton.jsx"
  return saved ? applyLike(previousPost, nextLiked) : ~previousPost~; // Principle 4: a failure leaves the real state unchanged

  const [post, likeAction] = useActionState(updateLike, { liked: false, likes: 12 });
  const [optimisticPost, setOptimisticPost] = useOptimistic(~post~, applyLike); // Principle 3: the real state decides what stays

  return (
    <form action={submitAction}>
```

### How React calls the components, and what one click does

When the page loads, React calls `App`, and inside it, `LikeButton`. When the user clicks the heart, React calls `submitAction`, which sets the hoped-for post first and starts the save second:

```tree caption="The order in which React calls the components when the page loads, and the functions that run after one click by the user."
`App` [1. Called first] | Renders `<article>` with the title and `<LikeButton />`
- +`LikeButton` [2. Called second] | Keeps `post` with `useActionState` and `optimisticPost` with `useOptimistic` | Renders the heart button and the count
  - +`submitAction` [3. Runs when the user clicks] | Calls `setOptimisticPost` first: **red heart and 13 likes at once** | Then calls `likeAction`
  - +`updateLike` [4. Runs during the save] | Waits **one second** for `saveLike` | Returns the saved post, or the **previous post** on failure
```

### The five principles at a glance

| Principle | The mistake | What the user sees | The React rule |
| :--- | :--- | :--- | :--- |
| **1. The button reads the optimistic state** | The button still reads `liked` | The heart stays white for one second | Render `optimisticLiked` |
| **2. Inside an Action** | The set function sits in `onClick` | The heart flashes, and the Console logs an error | Call the set function in the form's action |
| **3. The real state decides what stays** | `useOptimistic(false)` | The heart turns white after a saved like | Pass the real state, `liked` |
| **4. Roll back** | A hand-made `useState` forgets a failure | The heart stays red although nothing was saved | Return the previous state on failure |
| **5. One reducer** | The count reads `post` | `12 likes` next to a red heart | Read every changed value from the optimistic state |

## For the Interview

> **The Interview Question:** How do you show the value the reader expects before the server confirms?

### How to Answer Clearly in 30 Seconds

"I use `useOptimistic`. It takes the real state, such as the `liked` value that `useActionState` keeps, and returns an optimistic state and a set function. Inside the form's action, I call the set function first with the hoped-for value, so the heart turns red at once, and then I start the save. Three rules keep it correct:
1. **Call the set function inside an Action**, such as the form's action. In a plain `onClick`, the value only flashes, and React logs an error.
2. **Never clear the optimistic state by hand.** When the Action ends, it equals the real state again, in the same render.
3. **Let the real state carry the result.** On success, the real state is the new like. On failure, it stays the old one, so the heart rolls back by itself."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"When would you not use `useOptimistic`?"**
   When the result cannot be guessed. A like or a follow almost always succeeds, so showing it first is honest. A payment or a sign-up may be refused, and showing "Paid" before the server agrees would mislead the user. There, I wait for the server with `useActionState` and show a saving sign with `isPending` or `useFormStatus`.
2. **"What happens if the Action throws instead of returning a failure?"**
   The Transition still ends, and React renders with whatever the real state is at that moment, so the optimistic value goes away. With `useActionState`, though, a thrown error goes to the nearest Error Boundary, and React cancels the Actions waiting in its queue. That is why a known failure, such as the server refusing the like, is returned as state: the reducer action returns the previous state.
3. **"Why pass a reducer instead of calling the set function with the next value?"**
   A reducer fits when one click changes several values, such as the heart and the count, because one function computes both and they never disagree. React's docs add a second reason: "Reducers are essential when the base state might change while your Transition is pending." The base state is the real state we passed to `useOptimistic`. If it changes during the wait, React runs the reducer again on the new base state, while a plain value passed to the set function stays fixed.

```tree caption="Interview comparison: three tools that show the user something while a save runs, and what each one shows."
What the page shows while a save runs
- +`isPending` from `useActionState` | Says that **an Action is running** | Fits a **saving sign** on a button
- +`pending` from `useFormStatus` | Says that **the form is submitting** | Fits a sign **inside the form's own components**
- +`useOptimistic` | Shows **the result itself**, before the server confirms | Fits a **like, a follow, or a chat message**
```
