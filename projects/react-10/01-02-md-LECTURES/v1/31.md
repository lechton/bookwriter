# Lecture 31: Reaching a DOM Node with a Ref
> INTERVIEW QUESTION | ❱ CORE | How do you reach a DOM node from React to focus it, scroll it, or measure it?

---

## How Our Code Gets Hold of One Real Element on the Page

### Three jobs the JSX cannot describe

Since Lesson 01, React has written the page for us. We describe the page in JSX, and React creates and updates the real elements in the browser to match. The text in a box, a class, whether a line is shown or hidden: the JSX says all of it, and React does the rest.

Some jobs have no words in JSX. Think of a form where you type one name after another. After each name, the cursor should be back in the box, ready for the next one. The browser calls this **focus**: the element that has focus receives the keys the user presses, and a text box with focus shows the blinking cursor. JSX has no prop that says "this box has the focus now". It has no prop that says "scroll until this picture is visible", and no way to ask how wide an element is on the screen. The docs say it plainly: "There is no built-in way to do those things in React, so you will need a *ref* to the DOM node."

A **DOM node** is the real object the browser keeps for one tag on the page. It is what the Elements panel shows, and what `document.getElementById` returned in Lesson 01. The docs say "DOM node" and "DOM element" for the same thing.

Here is the whole tool, in the three lines the docs use:

```jsx title="Putting the cursor in a box with a ref"
const inputRef = ~useRef(null)~; // 1. In the component: creates the ref, the object { current: null }
<input ~ref={inputRef}~ /> {/* 2. In the JSX: asks React to put this box's DOM node into inputRef.current */}
~inputRef.current.focus();~ // 3. In a click handler: the browser puts the cursor in that box
```

The first line is the ref from Lesson 30. The third line calls `focus`, a method the browser gives every element. Only the second line is new.

### The same ref as in Lesson 30, filled by React

The ref here and the stopwatch's ref in Lesson 30 are made the same way. Yes, it is the exact same thing! Both call `useRef` with `null`, and both get back the same kind of object, whose `current` starts as `null`. React keeps it between renders, and changing `current` renders nothing. In the words of the docs: "Refs are a generic concept, but most often you'll use them to hold DOM elements."

The one difference is who writes `current`:

```jsx title="Our code fills the ref, or React fills the ref"
intervalRef.current = ~setInterval(tick, 1000)~; // Lesson 30: our Start handler writes the interval ID into current
<input ~ref={inputRef}~ /> {/* This lesson: React writes the box's DOM node into current */}
```

In this lesson, no line of our code writes `inputRef.current`. React writes it, because the tag carries the `ref` attribute.

```tree caption="The same ref object from useRef, filled by our code in Lesson 30 and by React in this lesson."
Two ways a ref gets its `current`
- +Our code writes `current` [`intervalRef.current = setInterval`] | Lesson 30: the **Start handler** puts the interval ID in | The **Stop handler** reads it back later
- +React writes `current` [`<input ref={inputRef} />`] | This lesson: the tag carries the **`ref` attribute** | React puts **the box's DOM node** in, and our handler calls `focus` on it
```

Lesson 30 called a ref an escape hatch. The docs use the same word here: a ref to a DOM node is for the moments when you have to "step outside React". Their examples are "managing focus, scroll position, or calling browser APIs that React does not expose". Browser APIs are the methods and properties the browser itself gives every element, such as `focus`.

### Which tool fits which job

The docs remind us that this is the rare case: "React automatically updates the DOM to match your render output, so your components won't often need to manipulate it." Here is the right tool for each job, and the plain JavaScript way that does not fit:
1. **Anything the JSX can say**, such as the text in a box, a class, or whether a line is shown: state and JSX, with no ref.
2. **Focus, scroll, or measure after something the user does**, such as a click: a ref, read in the event handler. The docs say: "Usually, you will access refs from event handlers."
3. **Focus a box the moment it appears on the page**: the `autoFocus` prop. The `<input>` reference says: "If `true`, React will focus the element on mount." With a ref and no event to run code in, the job takes an Effect, which Lesson 32 teaches.
4. **The plain JavaScript way, `document.getElementById`**, from Lesson 01. It searches the whole page, not one copy of the component, and Principle 3 shows where that breaks.

```tree caption="Which tool fits which job when a component needs something on the page."
What the component needs on the page
- +Something the JSX can say [`value={text}` `{show && <p />}`] | Text, a class, a line shown or hidden | **State and JSX**, no ref
- +Focus, scroll, or measure after a click [`inputRef.current.focus`] | The browser keeps these, **not the JSX** | **A ref**, read in the **event handler**
- +Focus a box the moment it appears [`autoFocus`] | There is **no event** to run code in | **`autoFocus`**, or an Effect in Lesson 32
- !Find the element by its id [`document.getElementById`] | Searches **the whole page** | Finds **the wrong box** when a component appears twice
```

### What is at stake

On our example page, the user types guest names one after another. Each mistake of this lesson shows on the page at once:
1. With no ref, the cursor leaves the box each time the user clicks Add, and the user must click the box again before typing the next name.
2. With `document.getElementById` and two lists on the page, the user clicks the Add button of the Dinner list, and the cursor lands in the box of the Lunch list, so the next name the user types appears in the wrong list's box.
3. With the call to `focus` in the body of the component instead of a handler, the page is blank when it opens.

Readers usually go wrong in three ways. First, they reach for `document.getElementById`, the tool they know from plain JavaScript. Second, they read `inputRef.current` while the component renders and expect the box, but on the first render it is still `null`. Third, once they hold the node, they use it to change what React draws, such as removing an element, instead of changing state.

### Five Principles of Reaching a DOM Node with a Ref

**PRINCIPLES:** The `ref` attribute on a tag asks React to put that tag's DOM node into a ref, and our event handlers call the browser's own methods on it. Five principles follow from that:
1. **Principle 1: ref={inputRef} Puts the Box into inputRef.current**: After React creates the box, it puts the box's DOM node into `inputRef.current`. Our code never writes it, and without the attribute it stays `null`.
2. **Principle 2: The Add Click Puts the Cursor Back in the Box**: In an event handler, `inputRef.current` is the real box, so our code calls the browser's `focus` or `scrollIntoView` on it, or reads its `offsetWidth`.
3. **Principle 3: getElementById Puts the Cursor in the Wrong List**: `document.getElementById` searches the whole page and returns the first box with that id, while a ref belongs to one copy of the component.
4. **Principle 4: inputRef.current Is null During the First Render**: React fills the ref during the commit, so the body of the component finds `null` on the first render, and a call to `focus` there blanks the page.
5. **Principle 5: `remove` on React's Node Crashes the Next Toggle**: A ref is for actions that change nothing in the DOM, such as focusing, scrolling, and measuring. Removing a node that React manages crashes the next update.

Here is the complete map of those five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **ref={inputRef} Puts the Box into inputRef.current** | Interviewers ask how a ref gets the element; a ref without the `ref` attribute stays `null`, and the click throws a `TypeError`. | Create the ref by calling `useRef` with `null`, and pass it to a built-in tag as `ref={inputRef}`; React puts the DOM node into `current` after it creates the node. |
| **Principle 2** | **The Add Click Puts the Cursor Back in the Box** | Focus, scroll position, and sizes have no JSX form, so changing state alone never moves the cursor. | In an event handler, call the browser's own methods on `ref.current`: `focus`, `scrollIntoView`, `offsetWidth`, or `getBoundingClientRect`. |
| **Principle 3** | **getElementById Puts the Cursor in the Wrong List** | It works with one copy of the component and breaks as soon as the component appears twice, with no warning in the Console. | Reach a node through a ref, which belongs to one copy of the component, never through an id searched on the whole page. |
| **Principle 4** | **inputRef.current Is null During the First Render** | A call on `ref.current` in the body of the component blanks the page when it opens, and skipping the call with a check still gives no focus. | Read DOM refs in event handlers, or in an Effect when there is no event, never during rendering. |
| **Principle 5** | **`remove` on React's Node Crashes the Next Toggle** | Changing a node React manages looks fine for one click, then the next state change crashes the page or leaves it inconsistent. | Use DOM refs for non-destructive actions such as focusing, scrolling, and measuring; change what React draws through state. |

## 1. Principle 1: ref={inputRef} Puts the Box into inputRef.current

### The first example of the docs: Focus the input

The docs show the whole tool in one small component: a box, and a button that puts the cursor in it.

```jsx title="Focusing a text input, the first example of the docs"
import { ~useRef~ } from 'react'; // The same Hook as in Lesson 30

export default function Form() {
  const inputRef = ~useRef(null)~; // On the first render, React creates { current: null }

  function handleClick() {
    ~inputRef.current.focus();~ // current holds the real box, so the browser's focus works on it
  }

  return (
    <>
      <input ~ref={inputRef}~ /> {/* Asks React to put this box into inputRef.current */}
      <button onClick={handleClick}>Focus the input</button>
    </>
  );
}
```

The attribute, in the words of the docs, "tells React to **put this `<input>`'s DOM node into `inputRef.current`.**"

```page width=text caption="The docs' example when the page opens: an empty box and the Focus the input button."
form:
  field:  | 
  button: Focus the input
console: quiet
```

When the user clicks the button, the cursor appears in the box, and the browser draws a ring around it:

```page width=text caption="After the user clicks Focus the input, the cursor is in the box."
form:
  field:  |  | good
  button: Focus the input
console: quiet
```

### Where the box in inputRef.current comes from

No line of our code writes `inputRef.current`. React does it, in four steps:
1. The first render returns `<input ref={inputRef} />`. At that moment `inputRef.current` is still `null`, because the box does not exist yet.
2. In the commit, React creates the `<input>` DOM node and adds it to the page, as Lesson 13 showed.
3. React then sets `inputRef.current` to that node. The `useRef` reference says: "After React creates the DOM node and puts it on the screen, React will set the `current` property of your ref object to that DOM node."
4. When the box is later removed from the page, React sets `inputRef.current` back to `null`.

```tree dir=right caption="How the box reaches inputRef.current without a line of our code writing it."
How React fills `inputRef.current`
- +1. The first render [`<input ref={inputRef} />`] | The JSX names the ref | `current` is still **`null`**
- +2. The commit | React **creates the `<input>` node** | and adds it to the page
- +3. Right after | React sets **`inputRef.current` to that node** | Our handler can now call `focus`
- +4. The box is removed | React sets **`current` back to `null`**
```

A log in the handler shows what React put there:

```jsx title="Logging inputRef.current in the click handler"
function handleClick() {
  ~console.log(inputRef.current);~ // Logs the <input> element itself
  inputRef.current.focus();
}
```

```page width=text caption="After the click, the Console shows the input element that React put into inputRef.current."
form:
  field:  |  | good
  button: Focus the input
log: <input>
```

The `ref` attribute itself is only for React. React reads it and never writes it into the DOM, so the Elements panel shows a plain box:

```dom caption="The Elements panel: the input carries no ref attribute, because React reads ref and keeps it out of the DOM."
<div id="root">
+ <input> | note: No ref attribute in the DOM
  <button>Focus the input</button>
</div>
```

### The ref attribute fills current on built-in tags

The docs call the browser's own tags, such as `<input>` and `<div>`, built-in components, to tell them apart from the components we write, such as `GuestList`. On a built-in component, the `ref` attribute fills the ref with that element. The reference says: "Your ref will be filled with the DOM element for this node." On a component we write, such as `<GuestList ref={listRef} />`, the attribute does not reach the box inside unless the component passes it on, which Lesson 85 teaches.

### useRef alone leaves current at null

The ref from `useRef` and the `ref` attribute are two separate pieces, and the box lands in the ref only when both are there:

```jsx title="Without the ref attribute on the tag, and with it"
<input /> {/* Without the attribute: inputRef.current stays null forever */}
<input ~ref={inputRef}~ /> {/* With the attribute: React puts this box into inputRef.current */}
```

It looks the same, but it is NOT the same thing! Both tags draw the same box on the page, but React fills the ref only through the attribute.

A developer who forgets the attribute still writes the call to `focus` in the handler. When the user clicks the button, the cursor does not appear, and the Console shows an error:

```page width=text caption="Without ref={inputRef} on the tag, the click leaves the box without the cursor and throws an error."
form:
  field:  |  | bad
  button: Focus the input
console: Uncaught TypeError: Cannot read properties of null (reading 'focus')
```

`inputRef.current` still holds the `null` that the ref started with, and `null` has no `focus` method, so JavaScript throws a `TypeError`. The fix is the missing attribute.

### The guest list gets its ref

In our project, `GuestList` imports `useRef`, creates `inputRef`, and passes it to the box:

```jsx title="src/components/GuestList.jsx" startLine="1"

let nextId = 0;

export default function GuestList() {
  const [text, setText] = useState('');
  const [guests, setGuests] = useState([]);
  const inputRef = ~useRef(null)~; // The ref for the box, empty until the commit
```

```jsx title="src/components/GuestList.jsx" startLine="18"
      <input ~ref={inputRef}~ value={text} onChange={e => setText(e.target.value)} /> {/* React puts this box into inputRef.current */}
```

After the first commit, `inputRef.current` holds the box. The page still behaves as before, because nothing calls `focus` yet. Principle 2 adds the call.

> [!PRINCIPLE]
> **Principle 1: The ref Attribute: React Puts the DOM Node into ref.current**
>
> *Create a ref by calling `useRef` with `null`, and pass it to a built-in tag as `ref={inputRef}`; after React creates the node, it puts the node into `inputRef.current`, and it sets `current` back to `null` when the node is removed.*
>
> `useRef` alone only makes an empty object. The `ref` attribute on the tag asks React to fill it with that tag's DOM node, right after the commit. Our code never writes `current` here. Without the attribute, `current` stays `null`, and a call on it throws a `TypeError`.
>
> **DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> return <input ~ref={inputRef}~ />; // React puts this box into inputRef.current
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> return ~<input />~; // **WRONG:** no ref attribute, so inputRef.current stays null forever
> ```

## 2. Principle 2: The Add Click Puts the Cursor Back in the Box

### Focus, scroll, measure: the same shape three times

The interview question names three jobs: focus, scroll, and measure. With a ref, all three have the same shape: the node in `current`, then a method or a property the browser gives every element:

```jsx title="Three jobs with the same shape: the node in current, then the browser's own method"
inputRef.current.~focus()~; // Focus: puts the cursor in the box
imageRef.current.~scrollIntoView()~; // Scroll: scrolls until the image is visible
setWidth(boxRef.current.~offsetWidth~); // Measure: reads the element's width in pixels
```

Yes, it is the exact same thing! The `focus` we call on `inputRef.current` is the same `focus` that plain JavaScript calls on an element it found with `document.getElementById`. React only hands us the element. The docs put it this way: "You can then access this DOM node from your event handlers and use the built-in browser APIs defined on it."

None of these three jobs has a JSX form. Many developers think every change on the page must go through state. State decides what React draws: the text, the rows, the classes. Focus, the scroll position, and the size of an element belong to the browser, so our code asks the DOM node directly, in an event handler.

### What focus means

MDN describes the method: it "sets focus on the specified element, if it can be focused. The focused element is the element that will receive keyboard and similar events by default." For the user, focus is the blinking cursor in the box: the keys the user presses type there. Only one element on the page has focus at a time. Browsers usually draw a ring around it, which MDN calls the "visible indication of the focused element".

### Why the cursor leaves the box

At the start of the lesson, the cursor leaves the box when the user clicks Add, though no line of our code moves it:
1. While the user types John, the box has focus, and the cursor is in it.
2. The user presses the mouse button on Add. The box loses focus, because the user clicked another element.
3. `handleAdd` runs. It adds John and empties the box, and no line in it brings the cursor back.
4. The user types Mary, and the letters reach no box.

Browsers differ on where focus goes after the user clicks a button. In every browser, it is no longer in the box.

### The fix: focus at the end of handleAdd

`handleAdd` gets one more line:

```jsx title="src/components/GuestList.jsx" startLine="10" good="13"
  function handleAdd() {
    setGuests([...guests, { id: nextId++, name: text }]);
    setText('');
    ~inputRef.current.focus();~ // Puts the cursor back in the box after every click on Add
  }
```

The user types John and clicks Add. John joins the list, the box is empty, and the cursor is already in it:

```page width=text caption="After the click on Add, John is in the list and the cursor is back in the empty box."
section: Lunch guests
form:
  field:  |  | good
  button: Add
line: John
console: quiet
```

The user types Mary at once and clicks Add again, and the list shows both names:

```page width=text caption="The user typed Mary without clicking the box first, and clicked Add again."
section: Lunch guests
form:
  field:  |  | good
  button: Add
line: John
line: Mary
console: quiet
```

The call to `focus` works at once, on the line right after the setter empties the text. Lesson 15 showed that the call to `setText` only asks React for a new render. But the box itself has been on the page since the first commit, so `inputRef.current` already holds it, and the cursor moves into it right away. A moment later, React renders, and the box shows the empty text.

### Scrolling to an element

The docs show scrolling with a carousel, a row of cat pictures that scrolls sideways. Each picture has its own ref, and a button scrolls the first one into view:

```jsx title="Scrolling to the first picture, from the docs' carousel"
const firstCatRef = useRef(null);

function handleScrollToFirstCat() {
  firstCatRef.current.~scrollIntoView~({ behavior: 'smooth', block: 'nearest', inline: 'center' }); // Scrolls until this picture is in view
}

<img ~ref={firstCatRef}~ src="https://placecats.com/neo/300/200" alt="Neo" /> {/* React puts this picture into firstCatRef.current */}
```

MDN says that `scrollIntoView` "scrolls the element's ancestor containers" until the element "is visible to the user." In plain words, the page and every scrolling area around the picture move until the picture is in view. Called with no options, it scrolls just as well. The options in the docs only ask for a smooth motion and choose where the picture ends up in the row.

### Measuring an element

A chart needs to know how wide its area is. The width belongs to the browser, so our code reads it from the node:

```jsx title="Measuring an element after a click"
const boxRef = useRef(null);
const [width, setWidth] = useState(0);

function handleMeasure() {
  ~setWidth(boxRef.current.offsetWidth);~ // Reads the width the browser laid out
}

return (
  <>
    <div ~ref={boxRef}~>Chart area</div> {/* React puts this div into boxRef.current */}
    <button onClick={handleMeasure}>Measure</button>
    <p>Width: {width}</p>
  </>
);
```

MDN says that `offsetWidth` "returns the layout width of an element as an integer". The number is in pixels, "including any borders, padding, and vertical scrollbars". For a hidden element, it is `0`. Our code never sets `offsetWidth`. The browser computes it when it lays out the page. The width goes into state because the page shows it, and Lesson 30 taught that a value the page shows belongs in state.

The browser offers a second way to measure, `getBoundingClientRect`. Both ways count the padding and the border. They differ in what they give back: `offsetWidth` is one whole number, while `getBoundingClientRect` returns an object with, in the words of MDN, "the size of an element and its position relative to the viewport". The viewport is the part of the page the user sees in the browser window.

### Changing state is not enough

A challenge in the docs makes the same point. A video player keeps `isPlaying` in state, and its button switches between Play and Pause. The user clicks Play, and the button now reads Pause, but the video does not move. The docs explain that "toggling state is not enough": our code also has to call the `play` and `pause` methods on the DOM element. State changed the button, which React draws. Playing belongs to the browser's `<video>` element, so the fix is a ref on `<video>` and a call to `play` or `pause` on it in the handler.

> [!PRINCIPLE]
> **Principle 2: Browser APIs: Call focus, scrollIntoView, or offsetWidth on ref.current in a Handler**
>
> *In an event handler, `ref.current` is the real DOM node, so our code calls the browser's own methods on it: `focus` to put the cursor in it, `scrollIntoView` to scroll to it, and `offsetWidth` or `getBoundingClientRect` to measure it.*
>
> Focus, the scroll position, and sizes have no JSX form. State changes what React draws, but it never moves the cursor. The click by the user on Add takes focus away from the box, and only a call to `focus` on the box brings it back, so the user can type the next name at once.
>
> **DO THIS:**
> ```jsx
> function handleAdd() {
>   setText('');
>   ~inputRef.current.focus();~ // The cursor goes back into the box
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleAdd() {
>   ~setText('');~ // **WRONG:** empties the box, but the cursor stays outside it
> }
> ```

## 3. Principle 3: getElementById Puts the Cursor in the Wrong List

### Two ways to reach the box

Plain JavaScript already has a way to reach the box: give it an id and search the page for that id, as in Lesson 01. Here are both ways side by side:

```jsx title="Reaching the box by its id, and through a ref"
<input ~id="guest-input"~ /> {/* With the id: the tag carries a name for the whole page */}
document.~getElementById('guest-input')~.focus(); // Searches the whole page for that name

<input ~ref={inputRef}~ /> {/* With the ref: React puts this box into this copy's ref */}
~inputRef.current~.focus(); // Reads the ref of this copy of GuestList
```

It may look the same, or work the same at first, but it is NOT the same thing! With one list on the page, both give the exact same box, and both put the cursor in it. The difference shows as soon as the page has two lists.

### Two lists: Lunch and Dinner

The page now plans two meals. `App` renders two guest lists, and each gets a `title` prop:

```jsx title="src/App.jsx"
import GuestList from './components/GuestList.jsx';

export default function App() {
  return (
    <main>
      ~<GuestList title="Lunch" />~ {/* The first copy of GuestList */}
      ~<GuestList title="Dinner" />~ {/* The second copy: its own state and its own ref */}
    </main>
  );
}
```

`GuestList` reads `title` and shows it in the heading:

```jsx title="src/components/GuestList.jsx" startLine="5"
export default function GuestList({ ~title~ }) { // Lunch or Dinner, from the tag in App
```


> [!PRINCIPLE]
> **Principle 3: One Ref per Copy: getElementById Searches the Whole Page**
>
> *`document.getElementById` returns the first element on the whole page with that id, so in a component used twice it finds the first copy's box; a ref belongs to one copy, so each list reaches its own box.*
>
> With one list, an id and a ref give the same box. When the component appears twice, the page holds the same id twice, and the handler of every copy finds the first box. A ref is made for each copy of the component, and React fills it with that copy's node.

> ```

> ```jsx
> document.~getElementById('guest-input')~.focus(); // **WRONG:** the first box on the page, even from the Dinner list
> ```

## 4. Principle 4: inputRef.current Is null During the First Render

### The same line in two places

The call to `focus` works in `handleAdd`. Put the exact same line in the body of the component, and the page goes blank:

```jsx title="The same call to focus in the body of the component, and in the handler"
export default function GuestList({ title }) {
  const inputRef = useRef(null);
  ~inputRef.current.focus();~ // In the body: runs while React renders GuestList

  function handleAdd() {
    ~inputRef.current.focus();~ // In the handler: runs when the user clicks Add
  }
}
```

It may look the same, or work the same at first, but it is NOT the same thing! The line in the handler runs after the user clicks, long after the commit. The line in the body runs during rendering, before React has created the box.

### The user opens the page, and it is blank

A developer wants the cursor in the box of the Lunch list as soon as the page opens, and writes the call at the top of the component:

```jsx title="src/components/GuestList.jsx" startLine="5" bad="9"
export default function GuestList({ title }) {
  const [text, setText] = useState('');
  const [guests, setGuests] = useState([]);
  const inputRef = useRef(null);
  ~inputRef.current.focus();~ // **WRONG:** runs during rendering, while current is still null
```

The user opens the page, and it is blank. The Console shows the error:

```page width=text caption="With the call to focus in the body of GuestList, the page is blank when it opens."
blank
console: Uncaught TypeError: Cannot read properties of null (reading 'focus')
  warn: An error occurred in the <GuestList> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

Here is what happens when the page opens:
1. React calls `GuestList` for the first render.
2. `useRef` returns the ref object, with `current` set to `null`.
3. The body reaches the call to `focus` while `inputRef.current` is still `null`.
4. JavaScript throws a `TypeError` before the component reaches its `return`.
5. React removes the whole page. The `Component` reference says: "if your application throws an error during rendering, React will remove its UI from the screen."

The Elements panel shows the root element with nothing inside:

```dom caption="The Elements panel after the error: the root div is empty."
! <div id="root"></div> | note: React removed everything inside it
```

The docs explain why the body is too early: "During the first render, the DOM nodes have not yet been created, so `ref.current` will be `null`. And during the rendering of updates, the DOM nodes haven't been updated yet. So it's too early to read them."

### What inputRef.current holds during each render

A log in the body, without the call to `focus`, shows what each render finds:

```jsx title="src/components/GuestList.jsx" startLine="8"
  const inputRef = useRef(null);
  ~console.log(inputRef.current);~ // During rendering: what the ref holds before this commit
```

When the page opens, the Console shows `null` four times: once for each of the two lists, and each one twice. With `<StrictMode>` in development, React calls every component twice, as Lesson 14 showed, and all four calls come before the commit. After the user adds John to the Lunch list, the Lunch copy renders again and logs the `<input>` element, twice. It is the box from the last commit, which this render has not updated yet.

```page width=text caption="The Console with a log in the body: null on the first render, the input element after the click on Add in the Lunch list."
section: Lunch guests
form:
  field:  |  | good
  button: Add
line: John
section: Dinner guests
form:
  field:  | 
  button: Add
log: null | GuestList.jsx:9
log: null | GuestList.jsx:9
log: null | GuestList.jsx:9
log: null | GuestList.jsx:9
log: <input value=""> | GuestList.jsx:9
log: <input value=""> | GuestList.jsx:9
```

The docs give the order around every commit: "Before updating the DOM, React sets the affected `ref.current` values to `null`. After updating the DOM, React immediately sets them to the corresponding DOM nodes." Lesson 30 gave the rule: do not read or write `ref.current` during rendering. A DOM ref shows why: during rendering, the node is either missing or about to change.

### Skipping the call does not focus the box

To silence the error, the developer may skip the call while the ref is empty. Optional chaining, `?.`, does that: it calls `focus` only when `inputRef.current` is not `null`:

```jsx title="src/components/GuestList.jsx" startLine="8" bad="9"
  const inputRef = useRef(null);
  inputRef.current~?.~focus(); // **WRONG:** no crash, but the first render still finds null, so nothing gets focus
```

The page comes back, but the cursor is still not in the box when the page opens. The first render still finds `null`, so the call is skipped at the one moment it was meant for.

Focusing a box when the page opens has two right tools. The simpler one is the `autoFocus` prop on the box, which tells React to focus the box when it first appears on the page:

```jsx title="Focusing the box when it appears on the page"
<input ref={inputRef} ~autoFocus~ value={text} onChange={e => setText(e.target.value)} /> {/* React focuses the box on mount */}
```

The other is an Effect, which Lesson 32 teaches. The docs say: "If you want to do something with a ref, but there is no particular event to do it in, you might need an Effect." Our page needs focus after a click, so the call stays in `handleAdd`.

> [!PRINCIPLE]
> **Principle 4: Commit: inputRef.current Is null During the First Render**
>
> *React fills a ref during the commit, so during the first render `ref.current` is `null`, and during later renders it still holds the old DOM; read DOM refs in event handlers, never during rendering.*
>
> The component returns its JSX first, and React creates the box later, in the commit. A call on `inputRef.current` in the body finds `null`, throws a `TypeError`, and React removes the whole page. Skipping the call with `?.` hides the crash but still gives no focus. Use the event handler, `autoFocus`, or an Effect.
>
> **DO THIS:**
> ```jsx
> function handleAdd() {
>   ~inputRef.current.focus();~ // After the click: the box is on the page
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> ~inputRef.current.focus();~ // **WRONG:** during rendering, current is null and the page goes blank
> ```

## 5. Principle 5: `remove` on React's Node Crashes the Next Toggle

### Two buttons that both hide a line

A ref hands our code the real node, and the browser lets our code do anything with it, even remove it. The docs show what happens then, with two buttons and one line of text:

```jsx title="The docs' example: hiding a line through state, and removing it through a ref"
import { useState, useRef } from 'react';

export default function Counter() {
  const [show, setShow] = useState(true);
  const ref = useRef(null);

  return (
    <div>
      <button onClick={() => { ~setShow(!show);~ }}>Toggle with setState</button> {/* Changes state: React removes or adds the line */}
      <button onClick={() => { ~ref.current.remove();~ }}>Remove from the DOM</button> {/* Removes the line behind React's back */}
      {show && <p ref={ref}>Hello world</p>}
    </div>
  );
}
```

```page width=text caption="The docs' example when the page opens: two buttons and the line Hello world."
line: [Toggle with setState] [Remove from the DOM]
line: Hello world
console: quiet
```

`remove` is a browser method that takes an element off the page. It may look the same, or work the same at first, but it is NOT the same thing! A click on either button makes Hello world disappear. Only `setShow` tells React.

### The toggle that worked now crashes the page

The user clicks Toggle with setState a few times, and Hello world hides and shows each time. Then this happens:
1. With Hello world on the page, the user clicks Remove from the DOM. The call to `remove` on `ref.current` takes the `<p>` off the page.
2. Nobody tells React. `show` is still `true`, and React still counts its `<p>` as on the page.
3. The user clicks Toggle with setState. `show` becomes `false`, and React goes to take its `<p>` off the page.
4. The `<p>` is no longer there, so the browser throws an error, and the page crashes.

```page width=text caption="After Remove from the DOM, the next click on Toggle with setState crashes the page."
blank
console: Uncaught NotFoundError: Failed to execute 'removeChild' on 'Node': The node to be removed is not a child of this node.
  warn: An error occurred in the <p> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The docs explain: "This is because you've changed the DOM, and React doesn't know how to continue managing it correctly." React updates the DOM it built from our JSX, as Lesson 13 showed. Our code changed that DOM, and the next update by React no longer matches what is there.

### Use refs for non-destructive actions

The docs call the nodes that React created from our JSX and keeps updating "DOM nodes managed by React". Their rule, from the Recap, is: "Avoid changing DOM nodes managed by React." Changing them means changing their text, adding children to them, or removing them. The docs warn that it "can lead to inconsistent visual results or crashes like above."

Reading a node, and asking it to focus, scroll, or report its size, changes nothing that React built. The docs call these non-destructive actions: "If you stick to non-destructive actions like focusing and scrolling, you shouldn't encounter any problems." Our guest list already follows the rule. Its ref only calls `focus`, and the list itself changes through `setGuests`.

The docs allow one exception: "You can safely modify parts of the DOM that React has *no reason* to update." For example, "if some `<div>` is always empty in the JSX, React won't have a reason to touch its children list."

> [!PRINCIPLE]
> **Principle 5: Non-Destructive Actions: Never Change a DOM Node That React Manages**
>
> *Use a DOM ref for non-destructive actions such as focusing, scrolling, and measuring; do not change, add, or remove DOM nodes that React manages, because React keeps updating them from the JSX and does not know about our change.*
>
> Removing a node through a ref looks the same as hiding it through state, for one click. React still counts the node as on the page, so its next update crashes or leaves the page inconsistent. State decides what the page shows; a ref is for the few jobs state cannot say.
>
> **DO THIS:**
> ```jsx
> <button onClick={() => ~setShow(!show)~}>Toggle with setState</button> {/* React removes the line itself */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button onClick={() => ~ref.current.remove()~}>Remove from the DOM</button> {/* **WRONG:** React still counts the line as on the page */}
> ```

### How React calls the components and fills the refs

When the page opens, React calls `App`, then the two copies of `GuestList` in the order of their tags. Each copy gets its own `inputRef`, still `null` during this render. In the commit, React creates the two boxes and puts each one into the ref of its own copy:

```tree caption="The order in which React calls the components, and the box that React puts into each copy's inputRef in the commit."
`App` [1. Called first] | **Root component** | Renders `<GuestList title="Lunch" />` and `<GuestList title="Dinner" />`
- +`GuestList` with `title` Lunch [2. Called second] | Its own **`inputRef`**, `null` during the render | After the commit: **the box of the Lunch list**
- +`GuestList` with `title` Dinner [3. Called third] | Its own **`inputRef`**, `null` during the render | After the commit: **the box of the Dinner list**
```

| How the code reaches the box | What the user sees | Why |
| :--- | :--- | :--- |
| **No ref at all** | The cursor leaves the box each time the user clicks Add | Focus belongs to the browser, and no state or JSX moves it |
| **`useRef` without the `ref` attribute** | The click throws a `TypeError`, and the cursor stays out | React never fills `current`, so it stays `null` |
| **`document.getElementById` with two lists** | Add in the Dinner list puts the cursor in the box of the Lunch list | The search covers the whole page and returns the first box with that id |
| **The call to `focus` in the body** | The page is blank when it opens | During the first render, React has not created the box, so `current` is `null` |
| **`remove` on `ref.current`** | The next toggle crashes the page | React still counts the removed node as on the page |
| **`ref={inputRef}` and `focus` in `handleAdd`** | The cursor goes back into the box of its own list | React fills each copy's ref in the commit, and the handler runs after it |

## For the Interview

> **The Interview Question:** How do you reach a DOM node from React to focus it, scroll it, or measure it?

### How to Answer Clearly in 30 Seconds

"With a ref. React updates the DOM from the JSX, but JSX has no way to say 'put the cursor here', 'scroll to this', or 'how wide is this', so I need the real node. I create a ref by calling `useRef` with `null`, and pass it to a built-in tag as `ref={inputRef}`. After React creates the node in the commit, it puts the node into `inputRef.current`, and when the node is removed, it sets `current` back to `null`. Then, in an event handler, I call the browser's own APIs on it: `focus`, `scrollIntoView`, `offsetWidth`, or `getBoundingClientRect`. Three rules keep it right:
1. **A ref, not `document.getElementById`**: an id is searched on the whole page, so a component used twice finds the first copy's box, while a ref belongs to one copy.
2. **Never read the DOM ref during rendering**: on the first render it is still `null`, so I read it in event handlers, or in an Effect when there is no event.
3. **Only non-destructive actions**: focusing, scrolling, and measuring are safe; removing or changing a node that React manages can crash the next update."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"How do you focus an edit box the moment it appears, for example after a click on Edit?"**
   The call to `focus` in the click handler does not work there, because the box does not exist yet when the handler runs. The setter only asks for a render, so `inputRef.current` is still `null`. The simplest tool is the `autoFocus` prop: "If `true`, React will focus the element on mount." With a ref, the job takes an Effect, which Lesson 32 teaches, since the docs say: "If you want to do something with a ref, but there is no particular event to do it in, you might need an Effect." To make React update the DOM at once inside the handler, there is `flushSync`, which Lesson 65 teaches.
2. **"Can you pass a ref to your own component, such as `<MyInput ref={inputRef} />`?"**
   Only if the component takes `ref` and passes it on to a built-in tag inside. The docs say: "By default, your own components don't expose refs to the DOM nodes inside them." Lesson 85 shows how a component passes `ref` on. With `useImperativeHandle`, which Lesson 50 teaches, the component can give the parent only a few methods, such as `focus`, instead of the whole node. The docs warn that "manually manipulating *another* component's DOM nodes can make your code fragile."
3. **"How do you scroll to a row you just added to a list, and why does it lag?"**
   One `useRef` for each row does not work, because a Hook must be called at the top level of a component, never inside `map`, as Lesson 38 teaches. The docs use a ref callback instead, a function in the `ref` attribute, which Lessons 86 and 99 teach. When the handler adds a row and scrolls in the same click, the new row is not in the DOM yet, because the setter "does not immediately update the DOM". The docs say: "This is why scrolling always 'lags behind' by one item." `flushSync`, from Lesson 65, makes React update the DOM before the scroll.

```tree dir=right caption="Interview comparison: reaching the box by its id vs. through a ref."
`document.getElementById` vs. a ref in an interview
- !By its id [`document.getElementById`] | Searches **the whole page** | With two copies, returns **the first box** every time
- +Through a ref [`ref={inputRef}` `inputRef.current`] | React fills it **in the commit**, **one per copy** | Each copy reaches **its own box**, in the event handler
```
