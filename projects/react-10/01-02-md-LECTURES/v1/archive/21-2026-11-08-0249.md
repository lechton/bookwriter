## How a Form Shows One Answer After Each Click

### Changing the page directly vs. changing it through state

After the user clicks a button on a form, the page has to show something new, such as a red error line. There are two ways to get there. Both change what the page shows after the user acts. The one difference is who edits the page: our code edits it directly through DOM commands, or our code changes a state value and React edits the page.

In the browser without React, a line that starts hidden with display none becomes visible when a script sets its display style to an empty string. Here is the red error line both ways:

```js title="A DOM command: our code shows the hidden red line itself"
~error.style.display = '';~ // Switches on the red line; stays on until another command hides it
```

```jsx title="A state change: our code names the picture, and React edits the page"
~setStatus('error');~ // Names the current picture; touches no DOM element itself
{~status === 'error'~ && <p>Please enter a full email address.</p>} {/* Drawn only while status holds error */}
```

It may look the same, or work the same at first, but it is NOT the same thing! After the user's first wrong try, both show the red line. The difference shows on the next try, when the email is right. The DOM command left the red line switched on, and no command switches it off, so it stays on the page next to the welcome line. The state change only named a picture, and the next picture holds no red line, so React removes it.

That is the key idea of this lesson. A form has a small set of named pictures. A click or a timer only changes which name is current, and the JSX already says what each picture looks like. What is at stake is simple: after each try, the user sees exactly one answer, never an old error next to a new success. Readers usually go wrong by thinking in commands, such as "now show this line, now hide that one", and then forgetting one hide.

```tree caption="Two ways to change what a form shows after the user clicks: editing the page with DOM commands, or changing a state value so React edits the page."
Two ways to show the red error line after a wrong try
- !DOM command [`error.style.display`] | Our code **switches on one line** of the page | The line stays on until some later command **switches it off**
- +State change [`setStatus` `status === 'error'`] | Our code **names the current picture** | React draws that picture and **removes every line it does not hold**
```

### A newsletter box that must give one clear answer

At the bottom of a recipe site sits a small newsletter box: a heading, one email box, and a `Join` button. The user types an email and clicks `Join`. That one box can show four different pictures:
1. While the user types, the box and `Join`.
2. After a wrong email, the box, `Join`, and a red error line asking for a full email address.
3. While the email is being sent, a grey box, a grey `Join`, and the line `Sending...`
4. After a right email, only a welcome line in place of the whole form.

If our code shows and hides these lines one by one, a single forgotten hide leaves the red error line on the page next to the welcome line. The user then reads two answers that say opposite things.

Developers really choose between three ways to build this box:

```tree caption="Three ways developers build the four pictures of the newsletter box."
Three ways to switch the newsletter box between its four pictures
- !1. DOM commands | Find each element and **show or hide it** by command | Fits a page **without React**; one forgotten hide leaves an **old line** on the page
- !2. One true or false state per message [`isError` `isSubmitting` `isSuccess`] | Each message has **its own switch** | Works only while **every handler resets every switch**
- +3. One `status` string [`status`] | One value holds the **name of the current picture** | The way **React's docs recommend**
```

Two stricter tools go further than this lesson: the reducer of Lesson 27, and the form actions of Lessons 41 to 43 with their built-in pending flag.

This lesson builds on a few tools from earlier lessons. In JSX, a component can give a prop a default value, finish early with `return`, and show a line with `&&`. ### Four Principles of Reacting to Input with State

**PRINCIPLES:** A React form does not show and hide its lines one by one. It names the picture the user should see, and React draws that picture. Four practical rules follow from that:
1. **Principle 1: Each `status` Draws One Picture of the Form**: Before writing any handler, list every picture the user can see and give each one a name. Then write the JSX for every picture from one `status` value.
2. **Principle 2: Clicks and a Timer Only Set `status`**: Keep `status` in state. Each click by the user and each timer that finishes calls `setStatus` with the name of the next picture, and the JSX stays the same.
3. **Principle 3: DOM Commands Leave Two Messages on the Page**: When code shows and hides lines by command, every branch must hide every line that should go. Forget one, and the old red line stays next to the welcome line.
4. **Principle 4: One `status` String Rules Out an Error Next to `Sending...`**: One true or false state per message lets two messages show at once when one reset is forgotten. One `status` string can only hold one name at a time.

Here is the complete map of those four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Each `status` Draws One Picture of the Form** | A picture that was never drawn can never show, and interviewers ask for the first step of building a form that reacts to input. | List every visual state, name each one, and draw each one from one `status` value before writing any handler. |
| **Principle 2** | **Clicks and a Timer Only Set `status`** | A handler that shows and hides lines by itself grows with every new message; a handler that names the next picture stays one line. | Keep `status` in state, and let every human input and every computer input call `setStatus` with the next picture's name. |
| **Principle 3** | **DOM Commands Leave Two Messages on the Page** | A forgotten hide leaves the red error line next to the welcome line, with zero Console messages. | Describe each picture once in JSX, so the next picture removes every line it does not hold. |
| **Principle 4** | **One `status` String Rules Out an Error Next to `Sending...`** | Three true or false states allow eight mixes for four pictures, and one forgotten reset shows an error while the box is locked. | Keep pictures that cannot appear together in one `status` string, so every handler sets exactly one name. |

## 1. Principle 1: Each `status` Draws One Picture of the Form

### One component with two pictures, picked by one prop

Start with the smallest component that has two pictures. When its tag gives no `status`, it shows a `Join` button. When its tag says `status="success"`, it shows a welcome line instead. Here are two of its tags on one page:

```page width=text caption="Two Signup tags on one page: the first shows the Join button, the second shows the welcome line."
line: [Join]
line: Welcome to the list!
console: quiet
```

```jsx title="Signup draws one of two pictures, picked by status"
function Signup({ ~status = 'typing'~ }) { // A tag without status gets the name typing
  if (~status === 'success'~) { // The success picture holds only the welcome line
    return <p>Welcome to the list!</p>;
  }
  return <button>Join</button>;
}

<Signup />
<Signup status="success" />
```

Each of these two looks is one complete picture the user can see. React's docs call such a picture a **visual state**. The name `status` is our own choice. React's docs say: "You could call that prop anything you like, the naming is not important." What matters is that one value says which picture is current.

A thing that is always in exactly one of a few named states is what computer scientists call a **state machine**. Think of a traffic light. It shows one light at a time: red, yellow, or green. It is never red and green together. Each light is built in advance, and a timer or the walk button only picks which one is on. `Signup` works the same way: both pictures are written in advance, and `status` picks one.

```tree caption="A state machine is always in exactly one of a few named states, like a traffic light that shows one light at a time."
`Signup` is a small state machine [`status`]
- +`'typing'` [`<button>Join</button>`] | Drawn **in advance** in the JSX | On the page while `status` holds **typing**
- +`'success'` [`<p>Welcome to the list!</p>`] | Drawn **in advance** in the JSX | On the page while `status` holds **success**
```

React's docs take a second image from design. Before writing any logic, a designer draws one mockup for each picture. Our code can do the same: give each name its own tag, and look at every picture on one page before any click works. This drawing of every picture before any logic is called a **mock**. In the docs' words, "Mocking lets you quickly iterate on the UI before you wire up any logic."

### Drawing the four pictures of the newsletter box

Our newsletter box has four pictures, and each one gets a name. While the user edits the address, the name is `'typing'` or `'error'`. Once the form sends, the name is `'submitting'` or `'success'`. These are the names React's docs use for the same kind of form.

The `'submitting'` picture needs one new word: `disabled`. It is a true or false attribute of the browser, and React passes it through to the real element. React's reference for the input says: "A boolean. If `true`, the input will not be interactive and will appear dimmed." So while the email is being sent, the user cannot type in the box or click `Join` a second time.

```jsx title="src/components/NewsletterSignup.jsx"
export default function NewsletterSignup({ ~status = 'typing'~ }) { // App picks the picture on each tag
  if (status === 'success') {
    return <p>Welcome to the list!</p>;
  }

  return (
    <form>
      <h2>Join our newsletter</h2>
      <input ~disabled={status === 'submitting'}~ /> {/* Locks and dims the email box while sending */}
      <button type="submit" ~disabled={status === 'submitting'}~>Join</button> {/* Stops a second click while sending */}
      {status === 'submitting' && <p>Sending...</p>}
      {status === 'error' && <p style={{ color: 'red' }}>Please enter a full email address.</p>}
    </form>
  );
}
```

`App` now renders one tag per picture, each under a small label with its name:

```jsx title="src/App.jsx"
import NewsletterSignup from './components/NewsletterSignup.jsx';

export default function App() {
  return (
    <main>
      <h4>typing</h4>
      <NewsletterSignup ~status="typing"~ /> {/* One tag for each picture */}
      <h4>error</h4>
      <NewsletterSignup status="error" />
      <h4>submitting</h4>
      <NewsletterSignup status="submitting" />
      <h4>success</h4>
      <NewsletterSignup status="success" />
    </main>
  );
}
```

```page width=text caption="The mock: all four pictures of the newsletter box on one page. In the submitting copy, the box and Join are grey."

  field: |
  submit: Join

heading: Join our newsletter

  field: |

  field: |
```

`NewsletterSignup` never sets `status` itself. `App` writes it on each tag, and the default in the parameter list gives `'typing'` to a tag that has none.

In the Elements panel, the grey copy carries the `disabled` attribute, and the success copy holds no form at all:

```dom caption="The Elements panel for the last two copies of the mock: disabled on the box and the button, and no form in the success copy."

```

The mock is for looking, not for clicking. Its form has no `onSubmit` yet, so a click on `Join` in the typing copy reloads the page. Principle 2 gives the form its handler.

> [!PRINCIPLE]
> **Principle 1: Visual States: Each `status` Draws One Picture of the Form**
>
> *Before writing any handler, list every picture the user can see, give each one a name, and write the JSX for every picture from one `status` value.*
>
> A form is not one screen whose bits change after each click. It is a few complete pictures, and a picture that was never drawn can never show. So draw each picture first, from one `status` value, and look at all of them on one page as a mock. The clicks come later, and all they do is pick a name.
>
> **DO THIS:**
> ```jsx
> function NewsletterSignup({ status = 'typing' }) {
>   if (~status === 'success'~) { // One picture per name, drawn before any handler
>     return <p>Welcome to the list!</p>;
>   }
>   return <button disabled={status === 'submitting'}>Join</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function NewsletterSignup() {
>   return <button ~onClick={handleJoin}~>Join</button>; // **WRONG:** starts from the click, and the sending, error, and success pictures are drawn nowhere, so they can never show!
> }
> ```

## 2. Principle 2: Clicks and a Timer Only Set `status`

### `status` from the tag vs. `status` from state

In Principle 1, `App` picked each picture by writing `status` on the tag. A real form has to pick its picture itself, after the user acts. So `status` moves from the tag into state:

```jsx title="status written on the tag"
<Signup ~status="error"~ /> {/* App picks the error picture */}
```

```jsx title="status held in state"
const [status, setStatus] = useState('typing');
<button onClick={() => ~setStatus('error')~}>Join</button> {/* The user's click picks the error picture */}
```

Yes, it is the exact same thing! The JSX that draws each picture does not change at all. Whether that name arrives on the tag or lives in state, `status === 'error'` draws the exact same red line. Only the place where `status` comes from is different.

Here is the smallest form that picks its own picture. When the page opens, it shows `Join`:

```page width=text caption="Signup when the page opens: status starts as typing, so the Join button shows."
line: [Join]
console: quiet
```

```jsx title="Signup keeps status in state"
function Signup() {
  const [status, setStatus] = useState('typing');
  if (status === 'success') {
    return <p>Welcome to the list!</p>;
  }
  return <button onClick={() => ~setStatus('success')~}>Join</button>; // The click only names the next picture
}
```

```page width=text caption="The same page after the user clicks Join: the button is gone, and the welcome line shows."
line: Welcome to the list! | good
console: quiet
```

There is no line in our code that removes the button. React removes it, because the success picture holds no button.

### Human inputs and computer inputs

Two kinds of things can change the picture. React's docs call them human inputs and computer inputs:
- A **human input** is something the user does, such as typing in the box or clicking `Join`.
- A **computer input** is something that happens without the user. The docs give "a network response arriving, a timeout completing, an image loading" as examples.

Think of the traffic light again. The walk button is a human input, and the timer inside the light is a computer input. Both only switch which light is on. It is the same in React: "In both cases, you must set state variables to update the UI."

Our newsletter box has both kinds. The user types and clicks `Join`. A timer of one second stands in for the server's answer, and when it finishes, it moves the form from `'submitting'` to `'success'`. React's docs suggest drawing "each state on paper as a labeled circle, and each change between two states as an arrow". Here are the arrows of our form:

```tree caption="The five arrows between the four pictures of the newsletter box, and the input that causes each one."
What moves the newsletter box from one picture to the next
- +typing to error | **Human input**: the user clicks **Join**, and the email has no `@`
- +typing to submitting | **Human input**: the user clicks **Join**, and the email has an `@`
- +error to error | **Human input**: the user clicks **Join** again, and the email still has no `@`
- +error to submitting | **Human input**: the user clicks **Join**, and the email now has an `@`
- +submitting to success | **Computer input**: the **timer finishes** after one second
```

### The newsletter box with `status` in state

Now `NewsletterSignup` gets its own state. The `status` prop is gone. `email` holds the text of the box, and `status` holds the name of the current picture. The JSX stays the same as in Principle 1, with three additions: the box is controlled, the form has `onSubmit`, and `Join` starts disabled while empty.

```jsx title="src/components/NewsletterSignup.jsx"
import { useState } from 'react';

export default function NewsletterSignup() {
  const [email, setEmail] = useState('');
  const [status, setStatus] = useState('typing');

  function handleSubmit(e) {
    ~e.preventDefault();~ // Without it, the browser reloads the page and the welcome line never shows
    if (email.includes('@')) {
      ~setStatus('submitting');~ // Human input: the user clicked Join with a full email
      setTimeout(() => {
        ~setStatus('success');~ // Computer input: the timer finished, standing in for the server
      }, 1000);
    } else {
      ~setStatus('error');~ // Human input: the user clicked Join without an @
    }
  }

  if (status === 'success') {
    return <p>Welcome to the list!</p>;
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Join our newsletter</h2>
      <input
        value={email}
        onChange={e => setEmail(e.target.value)}
        disabled={status === 'submitting'}
      />
      <button type="submit" ~disabled={email.length === 0 || status === 'submitting'}~> {/* Off while the box is empty or while sending */}
        Join
      </button>
      {status === 'submitting' && <p>Sending...</p>}
      {status === 'error' && <p style={{ color: 'red' }}>Please enter a full email address.</p>}
    </form>
  );
}
```

Calling `email.includes` with `'@'` returns true when the text in the box contains the at sign. `Join` stays off while the box is empty, and that comes straight from `email.length`, so the form needs no fifth picture for an empty box. Lesson 22 covers when a value belongs in state and when it is computed from other values.

`App` now renders one `NewsletterSignup` tag with no prop on it:

```jsx title="src/App.jsx"
import NewsletterSignup from './components/NewsletterSignup.jsx';

export default function App() {
  return (
    <main>
      ~<NewsletterSignup />~ {/* No status on the tag: the form picks its own picture */}
    </main>
  );
}
```

The user types `mary` and clicks `Join`:

### The red line goes away with no line of code hiding it

React removes the red line, and no line of our code does. Why? Well, the handler never touched the red line. It only named the next picture, and that picture has no red line. Here is what happens after the user's second click, in order:
1. `status` holds `'error'`, so the red line is on the page.
2. The user clicks `Join` with `mary@mail.com` in the box.
3. The submit handler calls `setStatus` with `'submitting'` and starts the timer.
4. React calls the component again, and this time `status` holds `'submitting'`.
5. `status === 'error'` is now false, so the returned JSX holds no red line.
6. React compares this JSX with the last one and removes the red paragraph from the page. It does not hide it with a style: the element is gone from the Elements panel.

One second later, the timer finishes and calls `setStatus` with `'success'`. React calls `NewsletterSignup` again, and the early `return` replaces the whole form with the welcome line, although the user did nothing:

```page width=text caption="One second after the second click: the whole form is replaced by the welcome line."
line: Welcome to the list! | good
console: quiet
```

> [!PRINCIPLE]
> **Principle 2: Inputs: Clicks and a Timer Only Set `status`**
>
> *Keep `status` in state, and let every human input and computer input call `setStatus` with the next picture name while the mock JSX stays unchanged.*
>
> A handler that shows the sending line, then hides it, then shows the welcome line has to know every line on the page. A handler that only names the next picture knows nothing about the page. The user's click names `'error'` or `'submitting'`. One second later, the finished timer names `'success'`. React then draws that picture from the JSX already written, and it removes every line the picture does not hold.
>
> **DO THIS:**
> ```jsx
> function handleSubmit(e) {
>   e.preventDefault();
>   ~setStatus('error');~ // Names the next picture; the JSX decides what shows
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleSubmit(e) {
>   e.preventDefault();
>   ~document.getElementById('error').style.display = '';~ // **WRONG:** edits the page by hand instead of naming the next picture, so every other line must be fixed by hand too!
> }
> ```

## 3. Principle 3: DOM Commands Leave Two Messages on the Page

### Switching one line on vs. naming the whole picture

The opening of this lesson put the two ways side by side. Both change what the page shows after the user clicks `Join`. The one difference is who edits the page. In plain JavaScript, two browser commands switch a line on and off:

```js title="Switching a line off and on with DOM commands"
~error.style.display = 'none';~ // The browser hides the red line
~error.style.display = '';~ // The browser shows the red line again
```

```jsx title="Naming the picture with a state change"
~setStatus('error');~ // Picks the error picture; React updates the page
{~status === 'error'~ && <p>Please enter a full email address.</p>} {/* The red line belongs to the error picture */}
```

It may look the same, or work the same at first, but it is NOT the same thing! A DOM command changes one element and leaves every other element as it was. A state change picks a whole picture, and React removes whatever that picture does not hold. You can see the difference only on the second try.

### The newsletter box built with DOM commands

Here is the same newsletter box in `plain-newsletter.html`, with no React. Both message lines start hidden, and the script switches them on by command:

```html title="plain-newsletter.html"
<form id="signup">
  <h2>Join our newsletter</h2>
  <input id="email" />
  <button>Join</button>
</form>
<p id="error" style="display: none; color: red">Please enter a full email address.</p>
<p id="welcome" style="display: none">Welcome to the list!</p>

<script>
  const form = document.getElementById('signup');
  const email = document.getElementById('email');
  const error = document.getElementById('error');
  const welcome = document.getElementById('welcome');

  form.addEventListener('submit', e => {
    e.preventDefault();
    if (email.value.includes('@')) {
      form.style.display = 'none';
      ~welcome.style.display = '';~ // **WRONG:** shows the welcome line, but no line here hides the red one!
    } else {
      ~error.style.display = '';~ // Switches on the red line after a wrong try
    }
  });
</script>
```

The browser supplies `e` to the listener, and `email.value` is the text the user typed, kept on the box element itself.

### The red line stays next to the welcome line

The user tries `mary`, then `mary@mail.com`, as before. The page ends with the red line and the welcome line together. Here is the order of events:
1. The user types `mary` and clicks `Join`.
2. The `else` branch runs `error.style.display = ''`, and the red line shows.
3. The user types `mary@mail.com` and clicks `Join`.
4. The success branch runs `form.style.display = 'none'` and `welcome.style.display = ''`.
5. No line runs `error.style.display = 'none'`, so the red line stays switched on.

The React version gets the same two tries and shows only the welcome line:


The Elements panel of the plain version shows why. The red line is still there, and nothing in its style hides it anymore:

```dom caption="The Elements panel of plain-newsletter.html after the two tries: the form is hidden, and the red line is still visible."
  <form id="signup" style="display: none;">...</form>
! <p id="error" style="color: red;">Please enter a full email address.</p> | note: Switched on by the first try, never switched off
```

The fix in plain JavaScript is one more command, `error.style.display = 'none'`, in the success branch. But every branch has to hide every line that should go, and that list grows. With four pictures, DOM commands must handle the change from each picture to each of the other three, which is up to twelve changes. The JSX describes four pictures. A fifth picture adds one more branch to the JSX, while the commands have to be checked again for every change that touches it. React's docs put it this way: the React version is longer, "but it is much less fragile".

> [!PRINCIPLE]
> **Principle 3: Imperative Pitfall: DOM Commands Leave Two Messages on the Page**
>
> *When code shows and hides lines by command, every branch must hide old lines; with `status`, each picture is described once, so old lines disappear.*
>
> A DOM command switches one element on and leaves everything else as it was. After a wrong try and then a right one, the success branch shows the welcome line while the old red line stays visible. The user reads an error and a welcome at the same time. With `status`, the red line belongs to the error picture only. When the picture changes, React removes the line, and no branch has to remember it.
>
> **DO THIS:**
> ```jsx
> {~status === 'error'~ && <p style={{ color: 'red' }}>Please enter a full email address.</p>} {/* The red line exists only in the error picture */}
> ```
>
> **DO NOT DO THIS:**
> ```js
> if (email.value.includes('@')) {
>   ~welcome.style.display = '';~ // **WRONG:** the red line from the last try stays on the page next to the welcome line!
> } else {
>   error.style.display = '';
> }
> ```

## 4. Principle 4: One `status` String Rules Out an Error Next to `Sending...`

### Two true or false states vs. one string

Both ways below keep in state which picture the user sees. The one difference is how many values hold it. One way gives each message its own true or false state, which developers call a flag, like a small flag that is either up or down. The other way keeps one string with the name of the picture:

```jsx title="One true or false state per message"
const [~isError~, setIsError] = useState(false); // One switch for the red error line
const [~isSubmitting~, setIsSubmitting] = useState(false); // A separate switch for Sending...
```

```jsx title="One status string"
const [~status~, setStatus] = useState('typing'); // Holds one picture name at a time
```

It may look the same, or work the same at first, but it is NOT the same thing! As long as every handler sets every flag, both draw the same pictures. But two true or false values allow four mixes: both false, only the error, only the sending line, and both true. Both true is a picture no one wants: an error and a sending line at once. The string can hold only the names we list, so it can never be in two pictures at once. React's docs: "There are four possible combinations of two booleans, but only three correspond to valid states."

Think of the traffic light one last time. Three separate switches for red, yellow, and green could turn on red and green together. One dial with three positions cannot.

A mix of state values that matches no picture the user should see is called an **impossible state**. React's docs ask you to "prevent the cases where the state in memory doesn't represent any valid UI that you'd want a user to see." The docs also call such a pair a **paradox**, an everyday word for something that says two opposite things at once. Their example is that `isTyping` and `isSubmitting` cannot both be true.

### The newsletter box with three true or false states

Suppose a developer builds `NewsletterSignup` with one true or false state per message. The JSX is the same as before, except that each `status === ...` check becomes a flag. In the branch for a full email, the developer turns on `isSubmitting` and forgets to turn off `isError`:

```jsx title="src/components/NewsletterSignup.jsx"
const [email, setEmail] = useState('');
const [isError, setIsError] = useState(false);
const [isSubmitting, setIsSubmitting] = useState(false);
const [isSuccess, setIsSuccess] = useState(false);

function handleSubmit(e) {
  e.preventDefault();
  if (email.includes('@')) {
    ~setIsSubmitting(true);~ // **WRONG:** turns on Sending..., but never resets isError to false!
    setTimeout(() => {
      setIsSubmitting(false);
      setIsSuccess(true);
    }, 1000);
  } else {
    setIsError(true);
  }
}
```

The JSX reads the three flags:

```jsx title="src/components/NewsletterSignup.jsx"
if (isSuccess) {
  return <p>Welcome to the list!</p>;
}

return (
  <form onSubmit={handleSubmit}>
    <h2>Join our newsletter</h2>
    <input value={email} onChange={e => setEmail(e.target.value)} ~disabled={isSubmitting}~ /> {/* Grey and locked while isSubmitting is true */}
    <button type="submit" disabled={email.length === 0 || isSubmitting}>Join</button>
    {isSubmitting && <p>Sending...</p>}
    {~isError~ && <p style={{ color: 'red' }}>Please enter a full email address.</p>} {/* Still true from the first try */}
  </form>
);
```

### The red line shows next to `Sending...`

The user tries `mary`, then `mary@mail.com`. The page shows the red line and `Sending...` together, and the box is grey, so the user cannot fix what the red line asks to fix:

```page width=text caption="The version with three flags after the second click: the red line shows under Sending..., and the box and Join are grey."
heading: Join our newsletter
form:
  field: | mary@mail.com
  submit: Join
line: Sending...
line: Please enter a full email address. | bad
console: quiet
```

Both messages appear on the page at the same time. Why? Well, `isError` was turned on by the first click and never turned off by the second. Here is the order of events:
1. The user types `mary` and clicks `Join`. The handler sets `isError` to `true`, and the red line shows.
2. The user types `mary@mail.com` and clicks `Join`.
3. The handler sets `isSubmitting` to `true` and starts the timer. Nothing sets `isError` back to `false`.
4. React renders with `isError` true and `isSubmitting` true.
5. The page shows `Sending...` and the red line together, with the box locked.
6. One second later, the timer sets `isSubmitting` to false and `isSuccess` to true. The early `return` then shows the welcome line, while `isError` stays true in memory.

The Console stays quiet the whole time. React has no way to know that these two flags should never be true together. As React's docs note, you must never "show an error message and disable the input at the same time", or the user cannot fix the address.

### Three flags allow eight mixes for four pictures

With three flags, each one true or false, there are two times two times two, which is eight mixes. Our form has only four pictures. The other four mixes are impossible states, and each forgotten reset can land the page in one of them:

```tree caption="Three true or false flags allow eight mixes for four pictures; one status string allows only the four names."
How many mixes can the state of the newsletter box hold?
- !Three flags [`isError` `isSubmitting` `isSuccess`] | **8 mixes** for only **4 pictures** | Every handler must **reset every flag**, or an impossible state renders
- +One string [`status`] | Exactly **4 names**: typing, error, submitting, success | Every handler sets **one name**, so two pictures can **never** show at once
```

The fix is the `status` version of Principle 2, which is our finished page. There, the branch for a full email calls `setStatus` with `'submitting'`. That one call leaves the error picture behind, because one string cannot hold `'error'` and `'submitting'` at the same time. On the same two tries, the red line goes away the moment `Sending...` appears.

When the JSX would read better with a flag, compute a local constant from `status === 'submitting'` right before `return` instead of storing a second state. The flag is then computed on every render and can never disagree with `status`.

> [!PRINCIPLE]
> **Principle 4: Impossible States: One `status` String Rules Out an Error Next to `Sending...`**
>
> *When pictures cannot appear together, keep them in one `status` string instead of separate booleans, so every handler sets one name and prevents impossible mixes.*
>
> Separate flags for the error, the sending line, and the welcome line let the page show a mix that no one drew. Forget one reset, and the red line shows next to `Sending...` while the box is locked, with zero Console messages. One `status` string holds exactly one name. Setting the next name leaves the old picture behind, so the impossible mix cannot render.
>
> **DO THIS:**
> ```jsx
> const [status, setStatus] = useState('typing');
> ~setStatus('submitting');~ // One name: the error picture is left behind
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [isError, setIsError] = useState(false);
> const [isSubmitting, setIsSubmitting] = useState(false);
> ~setIsSubmitting(true);~ // **WRONG:** isError is still true, so the red line shows next to Sending...!
> ```

## Putting All Four Principles Together

### The complete newsletter box

Here is the finished project. The entry file mounts `App` inside `StrictMode`:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

`App` renders one newsletter box:

```jsx title="src/App.jsx"
import NewsletterSignup from './components/NewsletterSignup.jsx';

export default function App() {
  return (
    <main>
      ~<NewsletterSignup />~ {/* The form picks its own picture from state */}
    </main>
  );
}
```

`NewsletterSignup` draws four pictures from one `status` string:

```jsx title="src/components/NewsletterSignup.jsx"
import { useState } from 'react';

export default function NewsletterSignup() {
  const [email, setEmail] = useState('');
  const [~status~, setStatus] = useState('typing'); // Principle 4: one string, one picture at a time

  function handleSubmit(e) {
    e.preventDefault();
    if (email.includes('@')) {
      ~setStatus('submitting');~ // Principle 2: the user's click names the next picture
      setTimeout(() => {
        ~setStatus('success');~ // Principle 2: the finished timer names the next picture
      }, 1000);
    } else {
      setStatus('error');
    }
  }

  if (~status === 'success'~) { // Principle 1: the success picture holds no form
    return <p>Welcome to the list!</p>;
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Join our newsletter</h2>
      <input
        value={email}
        onChange={e => setEmail(e.target.value)}
        disabled={status === 'submitting'}
      />
      <button type="submit" disabled={email.length === 0 || status === 'submitting'}>
        Join
      </button>
      {status === 'submitting' && <p>Sending...</p>}
      {~status === 'error'~ && <p style={{ color: 'red' }}>Please enter a full email address.</p>} {/* Principle 3: the red line lives in one picture only */}
    </form>
  );
}
```

### How React calls the components in order

When the page opens, React calls `App` first. Because that component returns `NewsletterSignup`, React calls `NewsletterSignup` next. After that, every keystroke, every click on `Join`, and the finished timer update state inside `NewsletterSignup`, so React calls only that component again. `App` holds no state and is not called again:

```tree dir=right caption="The order in which React calls the components of the newsletter page: both on page load, then only NewsletterSignup after each state change."
How React calls the components of the newsletter page
- +1. Page load [`App`] | React calls **App** first | App returns `<main>` with one `<NewsletterSignup />`
- +2. Page load [`NewsletterSignup`] | React calls **NewsletterSignup** | `status` holds **typing**, so the empty form shows
- +3. After each keystroke or click [`setEmail` `setStatus`] | React calls **only NewsletterSignup** again | The JSX draws the picture that `status` names
- +4. After the timer [`setStatus`] | React calls **NewsletterSignup** again | `status` holds **success**, so only the welcome line shows
```

| Aspect | The Command Habit | The React Rule |
| :--- | :--- | :--- |
| **The pictures** | Start from the click and decide what it should show and hide | List every visual state, name each one, and draw each one from `status` before any handler |
| **The handlers** | Show the sending line, then hide it, then show the welcome line | Call `setStatus` with the next name, from a human input or a computer input |
| **The old line** | Switch the red line on with `style.display`, and forget to switch it off | The red line lives only in the error picture, so React removes it when the picture changes |
| **The state shape** | One true or false state per message, with eight mixes for four pictures | One `status` string that can hold only one of the four names |

## For the Interview

> **The Interview Question:** How do you design a component that reacts to input with state instead of touching the DOM?

### How to Answer Clearly in 30 Seconds

"I describe the UI for each visual state instead of showing and hiding elements by command. First, I list every picture the user can see, such as typing, error, submitting, and success. I draw each one from a `status` value, often as a mock with every picture on one page. Then I find what changes the picture: human inputs such as typing and clicking, and computer inputs such as a network response or a timer. I keep `status` in `useState`, and each event handler only calls `setStatus` with the next name. React makes the DOM match. I use one `status` string rather than several booleans, because booleans allow impossible mixes, such as an error message next to a locked, sending form."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why one `status` string instead of `isError`, `isSubmitting`, and `isSuccess`?"**
   Three booleans allow eight combinations for only four real pictures. If one handler forgets a reset, the page shows an impossible mix, such as an error line next to `Sending...` on a disabled form, with zero warnings. A string can hold only one of the listed names, so setting the next name always leaves the old picture behind. React's docs put it as moving pieces: "you want as few 'moving pieces' as possible. More complexity leads to more bugs!" When the JSX needs a boolean, I compute it, as in `const isSubmitting = status === 'submitting';`. For a stricter model, there is `useReducer`, or a state machine library such as XState, and React 19 form actions come with a built-in pending state.
2. **"Should an empty email box be its own status, such as `'empty'`?"**
   No. Whether the box is empty is already in `email`, so I compute it: `disabled={email.length === 0 || status === 'submitting'}`. Storing it as a separate state would add one more value that can disagree with the text in the box. React's docs remove `isEmpty` from their own example for the same reason, and keep only the state they cannot remove "without breaking the functionality".
3. **"What does React do to the DOM when `status` changes from `'error'` to `'submitting'`?"**
   React calls the component again, gets the JSX for the submitting picture, and compares it with the JSX of the last render. It then changes only what differs: it removes the red error `<p>`, adds the `Sending...` line, and sets `disabled` on the box and the button. The heading stays as it was, and the box stays the same element, so it keeps the text `mary@mail.com`. React's docs compare this to a single `updateDOM` function that syncs every element from the current state. Under the hood, React does that same sync, except it "avoids touching the DOM for properties that have not changed".

```tree dir=right caption="Interview comparison: showing and hiding elements by command vs. naming the current visual state and letting React draw it."
Commands vs. `status` in an interview
- !DOM commands or one boolean per message [`style.display` `isError`] | Every branch must **reset every element or flag** | One forgotten reset shows **two answers at once**
- +One `status` string [`setStatus`] | Each handler sets **one name** | React draws that picture and **removes everything it does not hold**
```
