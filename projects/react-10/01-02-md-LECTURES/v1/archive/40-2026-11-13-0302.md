# Lecture 40: Choosing Between Controlled State and Uncontrolled FormData
> INTERVIEW QUESTION | ❱ CORE | Should a form use controlled state or uncontrolled FormData, and how do you choose?

---

## Which Boxes of a Form Need State

### The Email box vs. the Password box on a Sign up form

Picture the Sign up form on almost any website. It has an Email box, a Password box, one hint line under the password, and a Sign up button.

```page caption="The Sign up form of our shop when the page opens."
heading: MyShop
section: Sign up
form:
  field: Email
  field: Password
line: Use 8 or more characters
form:
  submit: Sign up
```

Watch what the user does, and what the page does in return:
1. The user types `john@mail.com` into the Email box. Nothing else on the page changes. The site needs the email only once, when the user clicks Sign up.
2. The user types a password. The hint line under it changes while the user types. It reads `Use 8 or more characters` until the password has 8 characters. Then it reads `Looks good`.

```page caption="The same form after the user types john@mail.com and the 8-character password secret12."
heading: MyShop
section: Sign up
form:
  field: Email | john@mail.com
  field: Password | •••••••• | good
line: Looks good | good
form:
  submit: Sign up
```

This screen raises one question for the developer: does every box need a state variable? No. Only the box whose text the page must show or check while the user types needs state. Every other box can keep its text in the browser, and our code reads that text once, when the user clicks Sign up.

So a box in a form can be written in two ways:

```jsx title="Two ways to write a box in a form"
<input ~name="email"~ /> {/* The browser keeps the text until the user clicks Sign up */}
<input ~value={password}~ onChange={e => setPassword(e.target.value)} /> {/* State keeps the text */}
```

1. **The box with `name`** has no `value`, so it is an uncontrolled box (as seen in Lesson 20). The browser keeps what the user types. The `name` is the label our code uses to find that text later. When the user clicks Sign up, our code asks the browser for the text of every box that has a `name`, through a browser object called `FormData`. Principle 1 shows how.
2. **The box with `value` and `onChange`** is a controlled box (as seen in Lesson 20). State keeps the text. After every keystroke by the user, `onChange` saves the new text into state.

The two lines look different in the code. On the screen, though, the two boxes behave the same: both show each letter the moment the user types it. So a developer easily believes they do the same work. It may look the same, or work the same at first, but it is NOT the same thing! After every keystroke by the user, the box with `value` and `onChange` changes state, and React calls the component function again. The box with `name` changes no state, so React calls nothing.

```tree caption="Two ways a form box keeps what the user types: the browser keeps it until submit, or state keeps it and React renders on every keystroke."
Two ways a box keeps what the user types
- +With `name` [`name="email"`] | The **browser** keeps the text | Our code reads it **once, at submit**, with `FormData` | React renders **nothing** while the user types
- +With `value` and `onChange` [`value={password}` `onChange`] | **State** keeps the text | React renders the component **after every keystroke** | The page can **change while the user types**
```

### What is at stake

The key idea to remember: **choose for each box.** Keep a box in state only when the page must change while the user types. Otherwise, let the browser keep the text, and read it when the user submits the form.

What is at stake is how fast the page answers the user's typing. Picture an admin form with forty boxes, where every box has its own state. The user types one letter in any box, and React renders the whole form again, with all forty boxes. React's docs warn that when the component holding the state renders a large tree on every keystroke, "this can get slow". On a low-end laptop or phone, the letters appear late while the user types.

Readers usually go wrong right after Lesson 20. They have just learned controlled boxes, so they put every box in state by habit, even the boxes the page reads only when the user clicks Sign up.

### Four Principles of Choosing Between Controlled State and FormData

**PRINCIPLES:** A box that the page reads only at submit can keep its text in the browser. A box whose text the page must follow while the user types goes into state. Four practical rules follow from that choice:
1. **Principle 1: `name` Puts the Email into FormData**: When the user clicks Sign up, `new FormData(e.currentTarget)` collects the text of every box that has a `name`. Our code reads the email with `formData.get('email')`, and no state is needed.
2. **Principle 2: Typing in the Email Box Skips the Render**: While the user types into the box with `name`, React renders nothing. While the user types into a box with `value` and `onChange`, React renders the whole component after every keystroke.
3. **Principle 3: The Password Hint Follows State**: When the page must change while the user types, as the hint under the password does, that box goes into state. At submit, our code reads the email from `FormData` and the password from state.
4. **Principle 4: State in SignupForm Keeps SiteHeader Still**: Every keystroke renders the component that holds the state, and every component inside it. When the state lives in `SignupForm`, the header does not render while the user types.

Here is the complete map of those four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`name` Puts the Email into FormData** | A box without `name` is missing from the form data, so `formData.get('email')` returns `null` and the sign up code gets no email, with no error on the page. | Give every box that `FormData` reads a `name`, and read it with `formData.get` and that same name. |
| **Principle 2** | **Typing in the Email Box Skips the Render** | A form where every box sits in state renders the whole form after every keystroke, and a large form lags on slow devices. | Keep a box uncontrolled when the page reads it only at submit. |
| **Principle 3** | **The Password Hint Follows State** | A hint that must follow the typing never changes when the box keeps its text in the browser. | Put a box in state with `value` and `onChange` when the page must change on every edit, and read that box from state at submit. |
| **Principle 4** | **State in SignupForm Keeps SiteHeader Still** | The state of a box placed in `App` renders the whole page, header included, after every keystroke. | Keep the state of a box in the component that holds the form, not higher. |

## 1. Principle 1: `name` Puts the Email into FormData

### Reading a box at submit without state

A box does not need state for our code to read it. The browser already keeps the text of every box. When the user submits a form, the browser can hand our code all of that text at once.

Here is the smallest form that reads a box without state:

```jsx title="Reading the Email box at submit with FormData"
function handleSubmit(e) {
  e.preventDefault();
  const formData = ~new FormData(e.currentTarget)~; // Collects the text of every box in the form that has a name
  console.log(~formData.get('email')~); // Logs the text stored under the name email
}

<form onSubmit={handleSubmit}>
  <input ~name="email"~ /> {/* This name becomes the key in the form data */}
  <button type="submit">Sign up</button>
</form>
```

Three new words appear in this code. None of them comes from React. All three come from the browser:
1. **`name`** is an HTML attribute of the box. React passes it on to the box in the DOM. React's docs say that the `name` you write "will be used as a key in the form data".
2. **`FormData`** is a browser object that holds the data of a form: one entry for each box that has a `name`, with the text inside that box. `new FormData(e.currentTarget)` builds that object from our form, at the moment the user submits it.
3. **`formData.get('email')`** is a method of that object. It returns the text stored under the name `email`.

The string `'email'` inside `formData.get('email')` is the same string as `name="email"` on the box. Nothing else links the two.

```tree dir=right caption="How the text in the Email box reaches our code at submit: the name on the box becomes the key in the form data."
How `john@mail.com` reaches `handleSubmit`
- +1. The box [`name="email"`] | The user types **`john@mail.com`** | The **browser** keeps the text
- +2. The form data [`new FormData`] | Built when the user **clicks Sign up** | Holds one entry: **`email`** with **`john@mail.com`**
- +3. Our code [`formData.get`] | Asks for the entry named **`email`** | Gets **`john@mail.com`**
```

Here is the first version of `SignupForm` in our project, with its heading, the Email box, and the Sign up button:

```jsx title="src/components/SignupForm.jsx"
export default function SignupForm() {
  function handleSubmit(e) {
    e.preventDefault();
    const formData = new FormData(e.currentTarget);
    console.log(~formData.get('email')~); // Logs john@mail.com when the user clicks Sign up
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Sign up</h2>
      <label>
        Email
        <input ~name="email"~ /> {/* The browser keeps what the user types */}
      </label>
      <button type="submit">Sign up</button>
    </form>
  );
}
```

The user types `john@mail.com` and clicks Sign up. The page does not reload, because `e.preventDefault()` stops the browser from sending the form (as seen in Lesson 11). The Console shows the email:

```page caption="The Sign up page after the user types john@mail.com and clicks Sign up."
heading: MyShop
section: Sign up
form:
  field: Email | john@mail.com | good
  submit: Sign up
log: john@mail.com | SignupForm.jsx:5
```

### `e.target` vs. `e.currentTarget` inside `onSubmit`

React's docs write `new FormData(e.target)`, and our code writes `new FormData(e.currentTarget)`. In a submit handler on the form, yes, it is the exact same thing! The submit event happens on the `<form>` itself, and the handler sits on that same `<form>`. So `e.target`, the node where the event happened, and `e.currentTarget`, the node whose handler runs, are both the form (as seen in Lesson 11).

### A box without `name` is missing from the form data

Now suppose the developer writes the Email box without `name`. A box in state never needed a `name`, so the habit is easy to keep:

```jsx title="src/components/SignupForm.jsx" startLine="11"
      <label>
        Email
        ~<input />~ {/* **WRONG:** no name, so the form data has no entry called email */}
      </label>
```

**The sign up code now gets no email, and nothing on the screen says so.** Here is what happens, in order:
1. The user types `john@mail.com` and clicks Sign up.
2. The page does not reload, and no error appears.
3. The Console shows `null`. The form data has no entry called `email`, and `formData.get` returns `null` for a name it does not hold.
4. The sign up code receives no email.

::: row caption="The same Email box with and without name: only the box with name reaches the form data."
::: col title="Email box with name" tag="the email reaches our code" tone=good
```page size=mini

  field: Email | john@mail.com | good
  submit: Sign up
log: john@mail.com | SignupForm.jsx:5
```
```jsx title="SignupForm.jsx" good="1"
<input ~name="email"~ /> {/* Stored under the key email */}
```
`formData.get('email')` finds the entry and returns the text.
:::
::: col title="Email box without name" tag="the email is missing" tone=bad
```page size=mini
form:
  field: Email | john@mail.com | bad
  submit: Sign up
log: null | SignupForm.jsx:5
```
```jsx title="SignupForm.jsx" bad="1"
~<input />~ {/* **WRONG:** no name, so no entry in the form data */}
```
The box shows the email, but the form data never holds it.

:::

> [!PRINCIPLE]
> **Principle 1: `name` Puts the Email into FormData: Read Each Box by Its Name at Submit**
>
> *Give every box that the form reads at submit a `name`, build the form data with `new FormData(e.currentTarget)`, and read each box with `formData.get` and that same name.*
>
> You do not need state to read what the user typed. The browser already keeps the text of every box. When the user submits, `FormData` collects the text of every box that has a `name`, and the `name` is the key you ask for. A box without `name` is left out, so your code gets `null`, and the page shows no error.
>
> **DO THIS:**
> ```jsx
> function handleSubmit(e) {
>   e.preventDefault();
>   const formData = new FormData(e.currentTarget);
>   console.log(formData.get('email'));
> }
> <input ~name="email"~ /> {/* formData.get('email') returns the typed email */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleSubmit(e) {
>   e.preventDefault();
>   const formData = new FormData(e.currentTarget);
>   console.log(formData.get('email'));
> }
> ~<input />~ {/* **WRONG:** no name, so formData.get('email') returns null */}
> ```

## 2. Principle 2: Typing in the Email Box Skips the Render

### The same box, two ways, and a log at the top of the component

To see when React renders `SignupForm`, we add one log line at the top of the component. Every time React calls `SignupForm`, the Console prints a line:

```jsx title="A log line that prints on every render"
export default function SignupForm() {
  ~console.log('SignupForm rendered');~ // Prints every time React calls SignupForm
```

Now compare two ways to write the Email box:

```jsx title="Email with name"
<input ~name="email"~ /> {/* The browser keeps the text */}
```

```jsx title="Email with value and onChange"
const [email, setEmail] = useState('');

<input value={email} ~onChange={e => setEmail(e.target.value)}~ /> {/* Every keystroke calls setEmail */}
```

The page loads, and the user types `jo`, the first two letters of the email, into each version. Both boxes show `jo`. The two Consoles do not match:

::: row caption="The same Email box written two ways: both show jo, but only the box with value and onChange renders SignupForm after every keystroke."
::: col title="Email with name" tag="no render while typing" tone=good
```page size=mini
form:
  field: Email | jo | good
```
```devconsole
+ SignupForm rendered
+ SignupForm rendered
```
The two lines come from the page load. Typing `jo` adds none.
:::
::: col title="Email with value and onChange" tag="one render per keystroke" tone=bad
```page size=mini
form:
  field: Email | jo | good
```
```devconsole
+ SignupForm rendered
+ SignupForm rendered
+ SignupForm rendered
+ SignupForm rendered
+ SignupForm rendered
+ SignupForm rendered
```
Two lines come from the page load, then two more after each of the 2 keystrokes.
:::
:::

Each render logs twice because Strict Mode calls the component twice in development (as seen in Lesson 14). With React DevTools installed, the second line of each pair appears slightly dimmed.

It may look the same, or work the same at first, but it is NOT the same thing! On the screen, both boxes show `jo`. In the code, they do different work:
- **With `name`**, the browser keeps the text. No state changes while the user types, so React has no reason to call `SignupForm` again.
- **With `value` and `onChange`**, every keystroke calls `setEmail`. A state change makes React render the component again (as seen in Lesson 13). So React renders `SignupForm` once for every letter the user types.

React's docs say it plainly: "When you use a controlled input, you set the state on every keystroke."

```tree caption="What happens after one keystroke by the user in each version of the Email box."
One keystroke in the Email box
- +With `name` [`name="email"`] | The **browser** writes the letter into the box | **No state** changes, so React **renders nothing**
- !With `value` and `onChange` [`value={email}` `onChange`] | `onChange` calls **`setEmail`** with the new text | React **renders `SignupForm` again**, and the box shows the new text
```

### The cost is the render, not the box

One render per keystroke is fine for a small form. Our form has two boxes, and React renders it in no time. The cost grows with how much React has to render after each keystroke.

**Beware! When every box of a large form sits in state, every keystroke in any box renders the whole form.** Here is how a developer runs into it:
1. After learning controlled boxes, the developer gives every box of a forty-box admin form its own `useState`.
2. The user types one letter in any box.
3. React renders the whole form again, with all forty boxes.
4. On a low-end laptop or phone, the letters appear late while the user types.

Most of those forty boxes are read only when the user clicks Save. They never needed state. As boxes with `name`, read at submit with `FormData`, they would cost no render at all while the user types.

So the Email box of our Sign up form stays the box with `name`, because the page reads the email only when the user clicks Sign up:

```jsx title="src/components/SignupForm.jsx"
export default function SignupForm() {
  ~console.log('SignupForm rendered');~ // Prints on page load, and never while the user types the email
  function handleSubmit(e) {
    e.preventDefault();
    const formData = new FormData(e.currentTarget);
    console.log(formData.get('email'));
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Sign up</h2>
      <label>
        Email
        <input ~name="email"~ /> {/* Uncontrolled: the browser keeps the email until submit */}
      </label>
      <button type="submit">Sign up</button>
    </form>
  );
}
```

> [!PRINCIPLE]
> **Principle 2: Typing in the Email Box Skips the Render: Keep a Box Uncontrolled When the Page Reads It Only at Submit**
>
> *A box with `value` and `onChange` makes React render the component after every keystroke; a box with `name` makes React render nothing while the user types.*
>
> Both boxes show what the user types, so they seem to cost the same. They do not. A controlled box sets state after every keystroke, and every state change renders the component that holds it. When the page needs the text only at submit, that work buys nothing, and in a large form the user feels it as letters that appear late.
>
> **DO THIS:**
> ```jsx
> <input ~name="email"~ /> {/* Read once at submit, no render while the user types */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [email, setEmail] = useState('');
> <input value={email} ~onChange={e => setEmail(e.target.value)}~ /> {/* **WRONG:** renders the form on every keystroke, though the page reads the email only at submit */}
> ```

## 3. Principle 3: The Password Hint Follows State

### A hint that must change while the user types

Now we add the Password box, and the hint line under it. The hint reads `Use 8 or more characters` until the password has 8 characters. Then it reads `Looks good`.

The Password box cannot be a box with `name`, like the Email box. Compare both ways:

```jsx title="Password with name"
<input type="password" ~name="password"~ /> {/* The browser keeps the text, and React renders nothing */}
<p>Use 8 or more characters</p>
```

```jsx title="Password with value and onChange"
const [password, setPassword] = useState('');

<input type="password" ~value={password}~ onChange={e => setPassword(e.target.value)} /> {/* Every keystroke saves the text into password */}
<p>{~password.length < 8~ ? 'Use 8 or more characters' : 'Looks good'}</p> {/* Picks the hint on every render */}
```

The user types the 8-character password `secret12` into each version:

::: row caption="The same Password box written two ways: both show 8 dots, but only the box with value and onChange updates the hint."
::: col title="Password with name" tag="the hint never changes" tone=bad
```page size=mini
form:
  field: Password | •••••••• | bad
line: Use 8 or more characters | bad
```
The password has 8 characters, and the hint still asks for 8.
:::
::: col title="Password with value and onChange" tag="the hint follows the typing" tone=good
```page size=mini
form:
  field: Password | •••••••• | good
line: Looks good | good
```
After the eighth character, the hint reads `Looks good`.
:::
:::

It may look the same, or work the same at first, but it is NOT the same thing! Both boxes show one dot for each letter. But with the box with `name`, the page now gives the wrong hint, for two reasons:
1. **There is no value to check.** The text sits in the browser, so the component has no `password` to measure with `.length`.
2. **There is no render while the user types.** Even with a value, nothing would make React call the component again to pick a new hint.

The box with `value` and `onChange` has both. Every keystroke by the user saves the text into `password`, and React renders the component again with the new `password`.

React's docs give the reason to choose a controlled box: you need state anyway, for example to render the page again on every edit. Here are the cases developers really meet:
1. **The page shows or checks the value on every edit**, such as a password hint, a live character limit, or autocomplete suggestions under the box.
2. **Something other than typing also changes the value**, such as a button that fills or clears the box.
3. **A button stays off until the form is valid**, such as a Sign up button with `disabled` (as seen in Lesson 21).

### One form, two ways: the email from FormData, the password from state

Our Password box goes into state. The Email box stays a box with `name`. One form now holds both ways, and that is fine: you choose for each box, not for the whole form.

At submit, our code reads each box from the place that keeps its text. React's docs say it directly: "If you instead control an input with state, read from that state on submit rather than from `FormData`."

```jsx title="src/components/SignupForm.jsx"
import { useState } from 'react';

export default function SignupForm() {
  const [password, setPassword] = useState('');
  console.log('SignupForm rendered');

  function handleSubmit(e) {
    e.preventDefault();
    const formData = new FormData(e.currentTarget);
    const email = ~formData.get('email')~; // From the browser, read once at submit
    console.log({ email, ~password~ }); // The password comes from state
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Sign up</h2>
      <label>
        Email
        <input ~name="email"~ /> {/* Uncontrolled: read at submit */}
      </label>
      <label>
        Password
        <input
          type="password"
          ~value={password}~ // Controlled: shows only what password holds
          onChange={e => setPassword(e.target.value)}
        />
      </label>
      <p>{~password.length < 8~ ? 'Use 8 or more characters' : 'Looks good'}</p> {/* Changes after the eighth character */}
      <button type="submit">Sign up</button>
    </form>
  );
}
```

The Password box has no `name`, because our code never asks the form data for the password.

The user types `john@mail.com`, then `secret12`. While the user types the email, the Console gets no new line. While the user types the password, two `SignupForm rendered` lines appear after every keystroke, as in Principle 2. Now we clear the Console with its clear button, and the user clicks Sign up. Clicking Sign up changes no state, so React renders nothing, and the Console shows one line, with both values:

```page caption="The Sign up form after the user types john@mail.com and secret12, the Console is cleared, and the user clicks Sign up."
heading: MyShop
section: Sign up
form:
  field: Email | john@mail.com | good
  field: Password | •••••••• | good
line: Looks good | good
form:
  submit: Sign up
log: {email: 'john@mail.com', password: 'secret12'} | SignupForm.jsx:11
```

When you turn a box into a controlled box, start its state with `''` (as seen in Lesson 20). With `useState()` and no starting value, the box starts uncontrolled. When the user types the first letter, the Console shows the warning that begins "A component is changing an uncontrolled input to be controlled".

> [!PRINCIPLE]
> **Principle 3: The Password Hint Follows State: Control a Box When the Page Changes on Every Edit**
>
> *Put a box in state with `value` and `onChange` when the page must change while the user types, and read that box from state at submit.*
>
> A hint under a box needs two things after every keystroke: the current text, and a render to show the new hint. A box with `name` gives neither, because the browser keeps the text and React renders nothing. A controlled box gives both. The rest of the form can stay uncontrolled, because you choose for each box.
>
> **DO THIS:**
> ```jsx
> const [password, setPassword] = useState('');
> <input type="password" ~value={password}~ onChange={e => setPassword(e.target.value)} /> {/* Each keystroke renders the form */}
> <p>{password.length < 8 ? 'Use 8 or more characters' : 'Looks good'}</p>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input type="password" ~name="password"~ /> {/* **WRONG:** no state and no render, so the hint can never change */}
> <p>Use 8 or more characters</p>
> ```

## 4. Principle 4: State in SignupForm Keeps SiteHeader Still

### The same state in two places

Every keystroke in the Password box renders the component that holds `password`. Which component that is depends on where we write `useState`.

To see which components render, we add a log line to the header too:

```jsx title="src/components/SiteHeader.jsx"
export default function SiteHeader() {
  ~console.log('SiteHeader rendered');~ // Prints every time React calls SiteHeader
  return (
    <header>
      <h1>MyShop</h1>
    </header>
  );
}
```

Now compare two places for the `password` state. In the first, `App` holds it and passes it down to the form as props (as seen in Lesson 24):

```jsx title="src/App.jsx with the state in App"
export default function App() {
  const [password, setPassword] = ~useState('')~; // Every keystroke changes state in App
  return (
    <main>
      <SiteHeader />
      <SignupForm password={password} onPasswordChange={setPassword} />
    </main>
  );
}
```

In this version, `SignupForm` has no state of its own. Its Password box shows the `password` it gets from `App`, and calls the function `App` passed down (as seen in Lesson 23):

```jsx title="The Password box inside SignupForm, with the state in App"
<input type="password" value={password} onChange={e => ~onPasswordChange~(e.target.value)} /> {/* Calls setPassword of App, so the state in App changes */}
```

In the second version, `App` holds no state, and `SignupForm` keeps `password` itself, as in Principle 3:

```jsx title="src/App.jsx with the state in SignupForm"
export default function App() {
  return (
    <main>
      <SiteHeader />
      ~<SignupForm />~ {/* SignupForm holds password itself */}
    </main>
  );
}
```

Both versions give the same page, the same hint, and the same submit. The Console tells them apart. **With the state in `App`, every keystroke in the Password box renders the header too, though nothing in the header changed.** Here is what happens when the user types one letter:
1. `onChange` calls `onPasswordChange`, which is the setter of the state in `App`.
2. React renders `App` again.
3. Rendering `App` means React calls every component inside it again: `SiteHeader` and `SignupForm`.
4. The Console shows `SiteHeader rendered` after every keystroke.

The page loads, and the user types the letter `s` into the Password box of each version:

::: row caption="The same password state placed in App or in SignupForm: the page is the same, but only the state in App renders SiteHeader on every keystroke."

```devconsole
+ SignupForm rendered

```
After the four page-load lines, the keystroke renders the header and the form again.

It may look the same, or work the same at first, but it is NOT the same thing! A state change renders the component that holds the state and every component inside it. With the state in `App`, that is the whole page. With the state in `SignupForm`, that is only the form.

```tree caption="Where the password state lives decides which components React renders after every keystroke by the user."
Which components render after one keystroke
- !State in `App` [`App`] | React renders **`App`** again | `SiteHeader` and `SignupForm` **both render**, so the **whole page** renders on every keystroke
- +State in `SignupForm` [`SignupForm`] | React renders **`SignupForm`** again | `SiteHeader` **stays still**; only the **form** renders on every keystroke
```

A developer often ends up with the first version by writing the form straight inside `App`, next to the rest of the page. On a small page like ours, nobody notices. On a big page, every keystroke renders the whole page, and typing becomes slow.

React's docs give the first fix: move the state of the box into the component that holds the box, so only that component renders after every keystroke. Two other cases remain:
1. **The rest of the page really needs the typed value.** Then the state has to live higher (as seen in Lesson 24). React offers `useDeferredValue` to keep the box quick during a large render, and Lesson 68 covers it.
2. **The page does not need the value while the user types.** Then the box can be a box with `name`, read at submit, as in Principle 1.

> [!PRINCIPLE]
> **Principle 4: State in SignupForm Keeps SiteHeader Still: Keep the State of a Box in the Component That Holds the Form**
>
> *Write the `useState` of a controlled box in the component that holds the form, not in `App`, so each keystroke renders only the form.*
>
> A state change renders the component that holds the state and every component inside it. The state of a box at the top of the page renders the whole page after every keystroke, header included. The same state inside the form component gives the same form, and React renders only the form.
>
> **DO THIS:**
> ```jsx
> function SignupForm() {
>   const [password, setPassword] = ~useState('')~; // Each keystroke renders only SignupForm
> }
> export default function App() {
>   return <main><SiteHeader /><SignupForm /></main>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   const [password, setPassword] = ~useState('')~; // **WRONG:** each keystroke renders App, SiteHeader, and SignupForm
>   return <main><SiteHeader /><SignupForm password={password} onPasswordChange={setPassword} /></main>;
> }
> ```

## Putting All 4 Principles Together

### The complete project

Here is the complete Sign up page. The Email box has a `name`, and our code reads it once at submit. The Password box is in state, because the hint follows it. The state lives in `SignupForm`, so the header does not render while the user types.

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  ~<StrictMode>~ {/* In development, React calls each component twice per render */}
    <App />
  </StrictMode>
);
```

```jsx title="src/App.jsx"
import SiteHeader from './components/SiteHeader.jsx';
import SignupForm from './components/SignupForm.jsx';

export default function ~App~() { // 1. Called 1st when the page loads; holds no state
  return (
    <main>
      <SiteHeader />
      <SignupForm />
    </main>
  );
}
```

```jsx title="src/components/SiteHeader.jsx"
export default function ~SiteHeader~() { // 2. Called 2nd on page load, and never while the user types

    <header>
      <h1>MyShop</h1>
    </header>

```

```jsx title="src/components/SignupForm.jsx"

export default function ~SignupForm~() { // 3. Called 3rd on page load, and again after every keystroke in the Password box
  const [password, setPassword] = useState('');
  console.log('SignupForm rendered');

  function handleSubmit(e) {
    e.preventDefault();
    const formData = new FormData(e.currentTarget);
    const email = formData.get('email');
    console.log({ email, password });
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Sign up</h2>
      <label>
        Email
        <input ~name="email"~ /> {/* Uncontrolled: the browser keeps the email until submit */}
      </label>
      <label>
        Password
        <input
          type="password"
          ~value={password}~ // Controlled: the hint below follows every keystroke
          onChange={e => setPassword(e.target.value)}
        />
      </label>
      <p>{password.length < 8 ? 'Use 8 or more characters' : 'Looks good'}</p>
      <button type="submit">Sign up</button>

}
```

### When React calls each component

On page load, React calls `App`, then `SiteHeader`, then `SignupForm`. After that, only one action makes React call a component again: a keystroke in the Password box, which renders `SignupForm` alone. Typing the email and clicking Sign up render nothing:

```tree caption="Which components React calls on page load, on a keystroke in each box, and on submit."
`App` [1. Called on page load] | Holds **no state** | Renders `<SiteHeader />` and `<SignupForm />`
- +`SiteHeader` [2. Called on page load] | Logs `SiteHeader rendered` | **Never** called again while the user types
- +`SignupForm` [3. Called on page load] | Logs `SignupForm rendered` | Called again after **every keystroke in the Password box**
  - +Email box [`name="email"`] | Typing calls **no component** | Read **once** in `handleSubmit` with `FormData`
  - +Password box [`value={password}`] | Typing calls **`SignupForm`** again | The hint changes after the **eighth character**
```

| Aspect | The Habit That Hurts | The React Rule |
| :--- | :--- | :--- |
| **Reading a box at submit** | Put every box in state just to read it once | Give the box a `name` and read it with `new FormData(e.currentTarget)` and `formData.get` |
| **The `name` on the box** | Leave it out, so `formData.get('email')` returns `null` | Write the same name on the box and in `formData.get` |
| **Typing in a box** | Control every box, so every keystroke renders the whole form | Control a box only when the page must change while the user types |
| **Reading a controlled box at submit** | Read it from `FormData` too | Read it from state, and the other boxes from `FormData` |
| **Where the state of a box lives** | In `App`, so every keystroke renders the whole page | In the component that holds the form |

## For the Interview

> **The Interview Question:** Should a form use controlled state or uncontrolled FormData, and how do you choose?

### How to Answer Clearly in 30 Seconds

"I choose for each box, not for the whole form. A controlled box, with `value` and `onChange`, keeps its text in state, so React renders the component after every keystroke. An uncontrolled box keeps its text in the browser, and I read it once at submit with `new FormData(e.currentTarget)` and `formData.get`, using the box's `name` as the key. So:
1. **Uncontrolled with `FormData`** when the page reads the box only at submit: no render while the user types, and less code.
2. **Controlled** when the page must change on every edit, such as a password hint, a character limit, autocomplete, or a button disabled until the form is valid, or when something other than typing changes the value.
3. **Mixed** in one form: I read the controlled boxes from state and the others from `FormData`, and I keep the state of each box in the component that holds the form, so each keystroke renders only that component."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Your `FormData` code returns `null` for a field. What happened?"**
   The box has no `name`, or its `name` differs from the string passed to `formData.get`. `FormData` keys each entry by the box's `name`, so a box without one is left out, and `formData.get` returns `null` for a name it does not hold. Nothing on the page shows an error. To turn the whole form data into a plain object, React's docs use `Object.fromEntries(formData.entries())`, and the same `formData` can be sent with `fetch` as the request body.
2. **"Aren't controlled inputs always slow?"**
   No. The cost is the render, not the box. A small form with a few controlled boxes renders in no time. It gets slow when the component holding the state renders a large tree after every keystroke, such as a forty-box form where every box has its own state, or the state of a box placed in `App`. The fixes, in order:
   1. Make a box uncontrolled when the page reads it only at submit.
   2. Move the state of the box down into the component that holds the box.
   3. When the rest of the page really needs the value, use `useDeferredValue`, which Lesson 68 covers. Unlike debouncing, it waits for no fixed delay.
3. **"Can one box be controlled at first and uncontrolled later, or both at once?"**
   No. React's docs say a box cannot be both controlled and uncontrolled at the same time, and it should not switch during its lifetime. That is why a controlled box starts with `''` and not `undefined`. With `undefined`, the box starts uncontrolled, and the first keystroke by the user makes React warn that "A component is changing an uncontrolled input to be controlled". Different boxes of the same form can still make different choices. In React 19, form actions receive the same `FormData` directly, which makes uncontrolled boxes the natural default for boxes read only at submit. Lesson 41 covers form actions.

```tree dir=right caption="Interview comparison: how to choose between a controlled box and an uncontrolled box read with FormData."
How to choose for each box of a form
- +Uncontrolled, read with `FormData` [`name="email"`] | The page reads the box **only at submit** | **No render** while the user types; needs a **`name`**
- +Controlled, kept in state [`value` `onChange`] | The page **changes on every edit**, or a button also **changes the value** | **One render per keystroke**; keep the state in the **component that holds the form**
```
