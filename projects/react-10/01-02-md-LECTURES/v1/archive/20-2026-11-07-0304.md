# Lecture 20: Controlled Inputs: Letting State Decide What Every Box Shows
> INTERVIEW QUESTION | ❱ CORE | How do you make an input, textarea, or select fully controlled by React state?

---

## Why a Form Needs Its Text in State

### The smallest controlled box: a name, a greeting, and a Clear button

In Lesson 12, a button and a piece of state worked together: the click called the setter, and the page showed the new state. Now we put a text box next to them. Here is a small page with a Name box, a greeting under it, and a Clear button. When the page opens, the Name box is empty:

```page width=text caption="The name page when it opens: an empty Name box, a greeting, and a Clear button."
form:
  field: Name |
line: Hello,
form:
  button: Clear
```

This is the whole component:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [name, setName] = useState('');

  return (
    <main>
      <label>
        Name
        <input value={name} onChange={e => setName(e.target.value)} />
      </label>
      <p>Hello, {name}</p>
      <button ~onClick={() => setName('')}~>Clear</button> {/* Clear changes only the state */}
    </main>
  );
}
```

The user types John into the Name box, and the greeting follows the box letter by letter, until it says Hello, John:

```page width=text caption="The same page after the user types John into the Name box."
form:
  field: Name | John | good
line: Hello, John | good
form:
  button: Clear
```

Then the user clicks the Clear button, and the Name box and the greeting are both empty again:

```page width=text caption="The same page after the user clicks Clear: the box and the greeting are both empty."
form:
  field: Name | | good
line: Hello,
form:
  button: Clear
```

Take another look at the code for the Clear button. As always in React, the story starts with state. We declare a variable, `name`, alongside its inseparable twin, `setName`, the function built to update it. They always travel as a pair, with a strict division of labor: when we want to show the name on the screen, we read `name`; when we need to change it, we call `setName`.

- **`name`**: Use it to read and display the current name.
- **`setName`**: Use it to update the name.

Right out of the gate, `name` holds an empty string. Everywhere the page references `name`, it renders nothing. The Name box is wired directly into this system: because its `value` is bound to `name`, the box starts out completely blank too.

Now, think about how the browser listens to you. Click a button, and `onClick` fires, straightforward enough. Type inside a text box, and `onChange` fires, because every keystroke alters what is inside the box. Press **J**, and `onChange` triggers. Press **o**, and it triggers again, firing on every single letter until you have spelled out *John*.

Our job is to wire those two events directly to our state. Every time you type in the box, that new text needs to land inside `name`. Every time you click the Clear button, `name` needs to be wiped clean. Here is how `onChange` and `onClick` divide the work:

- **Typing updates the state:** Whenever you type in the Name box, `onChange` fires. Inside `onChange`, we pass the text you just typed straight into `setName`.
- **Clicking resets the state:** Whenever you click the Clear button, `onClick` fires. Inside `onClick`, we call `setName` with an empty string.
- **React syncs the screen:** Every time `setName` changes `name`, React renders the page again. The Name box pulls its `value` fresh from `name`, immediately showing whatever `name` holds now.

That is the real secret behind the Clear button. Our code never reaches into the page to erase the Name box directly. It simply empties `name`, and because the Name box is locked to `name` through `value`, the box clears itself automatically.

A classroom whiteboard works the same way. The students call out their answers, but only the teacher writes on the board. On our page, the user calls out letters through `onChange`, our state does the writing, and the Name box shows only what state holds, through `value`. React calls a box like this **controlled**, because React state controls what it shows. The two props work as a team, and Principles 1 and 2 take them apart to show what each one does on its own.

### The real page: a contact form that counts and clears

The name page is tiny, but a real form needs the same two jobs. Think of the contact form of an online shop. Under the message box, a small line counts the characters as the user types, such as 12 / 200, and that one line asks two things of the message box.

First, the count must change on every key. So the text must reach state on every key, not only when the user clicks Send. That is the job `onChange` did for the greeting.

Second, after the user clicks Send, the message box must be empty again, ready for the next message. Our code can empty the state, so the state must also be able to empty the box. That is the job `value` did for the Clear button.

A box that only reports to state can do the first job but not the second, as Principle 2 shows. A box that only reads from state cannot even do the first, as Principle 3 shows. This lecture builds one box that does both.

### Our example page: the Contact Us form

Our page is the **Contact Us** form of an online shop. Besides the Message box and its count, it has a Name box, a Topic menu, a tick box called Email me a reply, and a Send button. When the user ticks Email me a reply, an Email box appears. Here is the finished page when it opens:

```page width=text caption="The finished Contact Us form, as it looks when the page opens."
heading: Contact Us
form:
  field: Name |
  select: Topic | Delivery
  textarea: Message |
line: 0 / 200
form:
  check: Email me a reply | off
  submit: Send
```

The project has four files, and the whole form lives in one component, `ContactForm`:


We start with the Message box and its count, and each principle adds one part until the form is finished.

Along the way, the lecture leans on a few ideas from earlier lessons:
- `useState` keeps a value between renders, and calling its setter makes React render the component again, from Lesson 12.
- React hands every event handler an event object `e`, and `e.target` is the element where the event started, from Lesson 11.
- Inside a handler on a box, `e.target.value` is the text in the box, which you met once in Lesson 17.
- A form's submit handler calls `e.preventDefault` so the browser does not reload the page, from Lesson 11.
- A `<label>` around a box makes its text clickable, and a tick box keeps its own tick inside the browser, from Lesson 18.

### Five Principles of Controlled Inputs

**PRINCIPLES:**
1. **`onChange` sends every key into state.** React calls it on every key, so the count can follow each letter.
2. **`value` sends state back into the box.** Then emptying the state is enough to empty the box after Send. `defaultValue`, which sets only the starting text, cannot do this.
3. **`value` without `onChange` freezes the box.** The browser accepts each new letter, React puts the old text back, and the Console shows an error.
4. **A menu and a tick box use the same pair.** The menu takes its choice from state. The tick box takes its tick from state, and its handler reads the tick, not the text.
5. **A controlled box starts with an empty string.** If its state starts with nothing at all, React warns as soon as the user types.

Here is the map of the five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`onChange` Sends Every Key into State** | A count or a greeting that never moves means the typed text never reached state. Interviewers also ask why React's `onChange` fires on every key. | Give the box `onChange`, and save the new text with the setter on every key. |
| **Principle 2** | **`value` Sends State Back into the Box** | A form that keeps its old text after Send, while the count says zero, is the most common form bug. | Give the box `value` from state, so the box always shows what state holds. |
| **Principle 3** | **`value` Without `onChange` Freezes the Box** | A box that refuses every letter looks broken, and the Console error explains why. | Every box with `value` also needs `onChange` that saves the new text right away. |
| **Principle 4** | **The Same Pair on a Menu and a Tick Box** | A tick box that will not untick, or a menu that ignores its starting choice, comes from the habits of plain HTML. | Put the chosen value on the menu itself. Give the tick box its tick from state, and read the tick back from the browser. |
| **Principle 5** | **A Controlled Box Starts with an Empty String** | A warning about a box changing from uncontrolled to controlled appears on the first key, and confuses many developers. | Start the state behind every box with an empty string, never with nothing. |

## 1. Principle 1: `onChange` Sends Every Key into State

### The smallest version: a greeting that follows each letter

On the name page, the Name box had two props, `value` and `onChange`. To see what `onChange` does by itself, we keep it and take `value` away. When the page opens, the box is empty, and the greeting says only Hello:

```page width=text caption="A Name box and a greeting, when the page opens."
form:
  field: Name |
line: Hello,
```

Here is the same component with `onChange` alone on the Name box:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [name, setName] = useState('');

  return (
    <main>
      <label>
        Name
        <input ~onChange~={e => setName(e.target.value)} /> {/* React calls this arrow on every key */}
      </label>
      <p>Hello, {name}</p>
    </main>
  );
}
```

The user types J, and the greeting says Hello, J. After four keys, it says Hello, John:

```page width=text caption="The same page after the user types John: the greeting has followed every letter."
form:
  field: Name | John | good
line: Hello, John | good
```

So `onChange` alone is enough to bring every letter into state. On a text box, React calls it every time the user changes the text, which means on every key, not when the user leaves the box. Our arrow takes the text from `e.target.value` and saves it with `setName`. Saving new state makes React render again, and the greeting shows the new name.

### The message box and its live count

The greeting followed every letter, and a character count needs exactly the same thing. So we build the first part of the contact form with the same pattern: a heading, the Message box, and the count under it.

```jsx title="src/components/ContactForm.jsx"
import { useState } from 'react';

export default function ContactForm() {
  const [message, setMessage] = useState('');

  function handleMessageChange(e) {
    setMessage(e.target.value);
  }

  return (
    <section>
      <h1>Contact Us</h1>
      <form>
        <label>
          Message
          <textarea ~onChange={handleMessageChange}~ /> {/* React calls the handler on every key */}
        </label>
        <p>{message.length} / 200</p>
      </form>
    </section>
  );
}
```

The count uses `.length`, the number of characters in a string. When the page opens, `message` is an empty string, so the count shows 0 / 200:

```page width=text caption="The first version of the Contact Us form, when the page opens."
heading: Contact Us
form:
  textarea: Message |
line: 0 / 200
```

The user types Where is my parcel? and the count moves with every letter, up to 19 / 200:

```page width=text caption="The same form after the user types Where is my parcel? into the Message box."
heading: Contact Us
form:
  textarea: Message | Where is my parcel?
line: 19 / 200 | good
```

For the count to be right, the new letter must already be in the text when our handler reads it. It is, because of the order inside each key. The browser puts the letter into the Message box first, and only then does React call `handleMessageChange`. So by the time our handler reads `e.target.value`, the new letter is part of the text, and `setMessage` saves the whole new text. This order comes back in every principle that follows.

### React's `onChange` and the browser's `change` event are NOT the same

If you have written plain JavaScript, the name `onChange` should make you suspicious. The browser has its own event called `change`, and on a text box it does not fire on every key. In fact, plain JavaScript offers two different events on a text box:

```js title="page.js"
messageBox.addEventListener(~'change'~, e => console.log(e.target.value)); // Runs only when the user leaves the box
messageBox.addEventListener(~'input'~, e => console.log(e.target.value)); // Runs on every key
```

The browser's `change` event waits until the user leaves the box, while the browser's `input` event fires on every change.

React's `onChange` on a text box behaves like the second one, the `input` event. So React took the name of one browser event and gave it the behavior of the other. React also accepts `onInput`, which does the same job, but its documentation admits that `onChange` is the habit: "For historical reasons, in React it is idiomatic to use `onChange` instead which works similarly." This book follows that habit. Just remember that in React, "on change" means "on every key".

### Mistake: keeping the message in a plain variable

The count works because the text lives in state. To see why state is needed, look at what a developer coming from plain JavaScript might write instead, with the text in a plain variable:

```jsx title="src/components/ContactForm.jsx" bad="2,5"
export default function ContactForm() {
  let message = '';

  function handleMessageChange(e) {
    ~message~ = e.target.value; // **WRONG:** changes a plain variable, so React never renders again
  }

  return (
    <section>
      <h1>Contact Us</h1>
      <form>
        <label>
          Message
          <textarea onChange={handleMessageChange} />
        </label>
        <p>{message.length} / 200</p>
      </form>
    </section>
  );
}
```

The user types Hi into the Message box. The box shows Hi, but the count stays at 0 / 200:

```page width=text caption="The contact form with a plain variable, after the user types Hi."
heading: Contact Us
form:
  textarea: Message | Hi
line: 0 / 200 | bad
```

The Message box and the count disagree, and each one is right about something different. The Message box shows Hi because the browser keeps typed letters inside a box on its own, and a box without `value` needs no help from React to do that. The count shows zero because it is still the count React drew when the page opened. Our handler changed a plain variable, and changing a plain variable never asks React to render again.

Even a render would not save the count. The next time React called `ContactForm`, its first line would run again and set `message` back to an empty string.

So we need something that keeps the text between renders and asks React to render again. That is the state from Lesson 12:

```jsx title="src/components/ContactForm.jsx" good="4,7"
import { useState } from 'react';

export default function ContactForm() {
  const [message, setMessage] = useState('');

  function handleMessageChange(e) {
    ~setMessage~(e.target.value); // Saves the text and asks React to render again
  }
```

Now the count follows every letter, as it did for Where is my parcel? above.

### Inside the handler, `message` is still one letter behind

The handler saves `e.target.value`, and you might wonder why it does not simply use `message`. To see why, suppose we add a log line to the handler for a moment:

```jsx title="src/components/ContactForm.jsx" startLine="6"
  function handleMessageChange(e) {
    console.log(~message~); // Shows the text from before this key
    setMessage(e.target.value);
  }
```

The Message box holds Wher, and the user types e. The box now shows Where, but the Console shows Wher. Why the old text?

Because the handler belongs to a render. In Lesson 15, you saw that each render sees its own fixed state values. The handler that runs on this key was made in the render where `message` was Wher, so inside it, `message` is still Wher. `setMessage` saves Where, but only the next render will see it.

So inside the handler, the new text lives in exactly one place: `e.target.value`. That is why the handler saves `e.target.value` and never builds the new text from `message`. We take the log line out again before we go on.

> [!PRINCIPLE]
> **Principle 1: `onChange`: React Calls It on Every Key**
>
> *When the page must react to what the user types, give the box `onChange` and save `e.target.value` with the setter.*
>
> The count under the Message box must move while the user types, so the text must reach state on every key. React's `onChange` does this. It has the name of the browser's change event, which waits for the user to leave the box, but it behaves like the browser's input event and fires on every key. By the time it runs, the browser has already put the new letter into the box, so `e.target.value` holds the whole new text. The setter saves that text and makes React render again, which changing a plain variable never does.
>
> **DO THIS:**
> ```jsx
> const [message, setMessage] = useState('');
> <textarea ~onChange~={e => setMessage(e.target.value)} /> {/* Saves the whole text on every key */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> let message = '';
> <textarea onChange={e => { ~message~ = e.target.value; }} /> {/* **WRONG:** a plain variable never makes React render again */}
> ```

## 2. Principle 2: `value` Sends State Back into the Box

### The smallest version: one Clear button, two different boxes

Principle 1 showed that `onChange` carries every letter from the box into state. Now we look at the other direction, from state back into the box. We go back to the name page from the start of the lecture and try the Name box with two different props. In both versions, the user types John and then clicks the Clear button:

::: row caption="The same name page with two different props on the box, after the user types John and clicks Clear."
::: col title="defaultValue on the box" tag="box keeps John" tone=bad
```jsx title="src/App.jsx" startLine="10"
<input ~defaultValue=""~ onChange={e => setName(e.target.value)} /> {/* Sets only the starting text */}
```
```page size=mini
form:
  field: Name | John | bad
line: Hello,
form:
  button: Clear
```
The greeting says only Hello, but the box still shows John.
:::
::: col title="value on the box" tag="box empties" tone=good
```jsx title="src/App.jsx" startLine="10"
<input ~value={name}~ onChange={e => setName(e.target.value)} /> {/* Shows whatever name holds */}
```
```page size=mini
form:
  field: Name | | good
line: Hello,
form:
  button: Clear
```
The greeting says only Hello, and the box is empty.
:::
:::

### Why the box with `defaultValue` keeps John

The two versions of the page differ in one prop on the Name box: the first version uses `defaultValue`, and the second uses `value`. In both versions, the user types John, and both boxes show John, so at first there is no difference.

Then the user clicks the Clear button, and its handler calls `setName` with an empty string, which empties `name`. In the version with `defaultValue`, the greeting reads `name`, so it now says only Hello. But the Name box still shows John.

That is strange. `name` is empty, and the greeting shows it. So why does the box still show John?

If you have written plain HTML, the name `defaultValue` may bother you, because HTML has no attribute called that. In HTML, you write `<input value="John">`, and John is only the starting text. The user can type over it, and the attribute in the Elements panel still says John. The browser keeps two things apart: the starting text, which is what the `value` attribute holds, and the text that is in the box right now. In JavaScript, the browser even calls the starting text `input.defaultValue`.

React keeps the same two things apart, but it renames them. What HTML calls the `value` attribute, React calls `defaultValue`. React uses the name `value` for the other thing: the text in the box right now. So the same line, `<input value="John">`, means two different things. In an HTML file, it sets the starting text. In JSX, it tells React that the box must show John after every render.

That explains the Clear button. In the version with `defaultValue`, our code only ever set the starting text. When the user clicks the Clear button and the handler empties `name`, our code has said nothing about the text in the box right now. So the box keeps John. In the version with `value={name}`, our code describes the text in the box right now. So when `name` becomes empty, React empties the box too.

React has a name for each kind of box. A box that gets `value` from state is **controlled**. It is the whiteboard from the start of the lecture, and React's documentation says that "React will force the input to always have the `value` you passed." A box without `value` is **uncontrolled**: after its starting text, the browser keeps the text, and React leaves it alone. So the word does not mean that nobody is in charge of the text. It means the browser is in charge of it, not our state.

### With `value`, why can I still type?

If React makes the Name box show `name` after every render, you might wonder how a new letter gets in at all. The answer is the order from Principle 1. The browser puts the letter into the box first. Then `onChange` saves the new text in `name`, and React renders. By the time React compares the box with `name`, the letter is already in both, so React has nothing to change.

### The Send button that empties the count, but not the Message box

The bug of the Clear button also happens on real pages, so let's go back to our contact form. We add a Send button. When the user clicks Send, the handler logs the message and empties `message`, so the form is ready for the next message:

```jsx title="src/components/ContactForm.jsx" startLine="10"
  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', message);
    ~setMessage('')~; // Empties the state after sending
  }
```

The developer wants the Message box to start empty, so they give it `defaultValue` with an empty string:

```jsx title="src/components/ContactForm.jsx" startLine="16" bad="7"
  return (
    <section>
      <h1>Contact Us</h1>
      <form onSubmit={handleSend}>
        <label>
          Message
          <textarea ~defaultValue=""~ onChange={handleMessageChange} /> {/* **WRONG:** starting text only, so Send cannot empty the box */}
        </label>
        <p>{message.length} / 200</p>
        <button type="submit">Send</button>
      </form>
    </section>
  );
}
```

While the user types Where is my parcel? everything works, and the count says 19 / 200. Then the user clicks Send:

```page width=text caption="The contact form with defaultValue, after the user types Where is my parcel? and clicks Send."
heading: Contact Us
form:
  textarea: Message | Where is my parcel? | bad
line: 0 / 200 | bad
form:
  submit: Send
log: Sent: Where is my parcel? | ContactForm.jsx:12
```

The count says 0 / 200, and the Console shows that the message was sent, yet the Message box still holds the old message. This is the bug of the Clear button again. The Send handler emptied `message`, so the count, which reads `message`, shows zero. The Message box has only a starting text, so React writes nothing into it, and the browser keeps the typed message.

So which one tells the truth, the count or the Message box? The count does, because it reads the state. A second click on Send proves it. The Console now logs an empty message, because `message` holds an empty string, while the old text still sits in the box:

```page width=text caption="The same form after the user clicks Send a second time without typing anything."
heading: Contact Us
form:
  textarea: Message | Where is my parcel? | bad
line: 0 / 200 | bad
form:
  submit: Send
log: Sent: Where is my parcel? | ContactForm.jsx:12
log: Sent: | ContactForm.jsx:12
```

### The fix: `value={message}` on the Message box

The problem is that nothing writes `message` into the Message box, so the fix is one prop on the text area:

```jsx title="src/components/ContactForm.jsx" startLine="20" good="3"
        <label>
          Message
          <textarea ~value={message}~ onChange={handleMessageChange} /> {/* The box always shows what message holds */}
        </label>
```

After a reload, the user types the same message and clicks Send. Now the Message box and the count are both empty:

```page width=text caption="The contact form with value, after the user types Where is my parcel? and clicks Send."
heading: Contact Us
form:
  textarea: Message | | good
line: 0 / 200 | good
form:
  submit: Send
log: Sent: Where is my parcel? | ContactForm.jsx:12
```

Notice that no line of our code empties the box itself. The Send handler empties `message`, React renders the form again, and React writes the new value, an empty string, into the text area.

### State is the single source of truth

After the fix, the page shows the message in two places, the Message box and the count, and both read the same `message`. This is called a **single source of truth**: one place holds the text, and everything on the page reads it. So to change what the Message box shows, we never touch the box. We change the state.

The bug with `defaultValue` was the opposite case. There, the text lived in two places, in the state and inside the box, and nothing kept them in step.

### An empty `defaultValue` and `value={message}` are NOT the same

This bug is easy to write because, when the page opens, the text area with `defaultValue=""` and the text area with `value={message}` draw the exact same empty box. They split only at the first render after the user clicks Send. On that render, React writes the empty string into the text area with `value={message}`. The text area with `defaultValue=""` gets nothing, because its `defaultValue` did its one job when the page opened.

The same idea explains the Message box of Principle 1. It had `onChange` and was still uncontrolled, because `onChange` only reports. Only `value` decides whether a box is controlled.

One last note for readers who know HTML. In HTML, you write the starting text of a text area between its tags. React does not support that. The box still shows the text, but React prints a red error in the Console that tells you to use `defaultValue` or `value` instead. So in React, a text area gets its text from one of these two props, just like an input.

> [!PRINCIPLE]
> **Principle 2: `value`: React Writes State into the Box After Every Render**
>
> *When our code must change what the box shows, such as emptying it after Send, give the box `value` from state.*
>
> In HTML, the `value` attribute is only the starting text. In React, that job belongs to `defaultValue`, and `value` means the text in the box right now. So a box with only `defaultValue` keeps whatever the user typed, and after Send the count says zero while the old message stays in the box. With `value` from state, React makes the box match the state after every render. Then saving an empty string empties the box too, and state becomes the single source of truth.
>
> **DO THIS:**
> ```jsx
> <textarea ~value={message}~ onChange={e => setMessage(e.target.value)} /> {/* Setting message to an empty string now empties the box */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <textarea ~defaultValue=""~ onChange={e => setMessage(e.target.value)} /> {/* **WRONG:** starting text only, so the box keeps its text after Send */}
> ```

## 3. Principle 3: `value` Without `onChange` Freezes the Box

### The smallest version: a box stuck on John

Principles 1 and 2 used `onChange` and `value` together. So what happens to a box that has `value` but no `onChange`? Here is a Name box whose `name` starts as John. When the page opens, the box shows John, and the Console already shows a red error:

```page width=text caption="A Name box with value and no onChange, when the page opens."
form:
  field: Name | John
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

The Name box has `value`, and nothing else:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [name, setName] = useState('John');

  return (
    <label>
      Name
      <input ~value={name}~ /> {/* **WRONG:** value without onChange */}
    </label>
  );
}
```

The user clicks at the end of the box and types ny, but the box still shows John:

```page width=text caption="The same page after the user types ny into the Name box."
form:
  field: Name | John | bad
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

No line of our code removes the letters, and the browser does not refuse them either. The browser accepts each letter, the way it does in any box. So who removes them? React does, in three steps:
1. The user presses n, and the browser puts n into the box.
2. The box has no `onChange`, so no code of ours runs, and `name` stays John.
3. React sees that the box no longer matches `value`, and puts John back.

So this box is not refused by the browser. React reverts it after every key.

Compare a box with `readOnly`, a prop that React passes to the browser as its own read-only attribute. A box with `readOnly` never accepts the letter in the first place: the browser refuses the key, so the text never changes and `onChange` never runs. To the user, both boxes look equally stuck. They are stuck for different reasons, and only one of them is a mistake.

### What the red error tells you

The red error in the first preview knows about both kinds of stuck box. React prints it while you develop, whenever a box has `value` and no `onChange`, and it names three ways out, one for each thing you might have meant:
- If the box should be editable, add `onChange`.
- If you only wanted a starting text, use `defaultValue` instead.
- If the box should really be frozen, say so with `readOnly`. Then React knows you meant it, and the error goes away.

### Mistake: the Name box that refuses Anna

This mistake is easy to make on a real form. Back on our contact form, the developer adds a Name box above the Message box, with its own state:

```jsx title="src/components/ContactForm.jsx" startLine="4"
  const [name, setName] = useState('');
  const [message, setMessage] = useState('');
```

They remember from Principle 2 that `value` lets Send empty the box, but in the markup they forget `onChange`:

```jsx title="src/components/ContactForm.jsx" startLine="20" bad="4"
      <form onSubmit={handleSend}>
        <label>
          Name
          <input ~value={name}~ /> {/* **WRONG:** no onChange, so every letter is put back */}
        </label>
```

The user clicks into the Name box and types Anna. The box stays empty, and the Console has shown the error since the page opened:

```page width=text caption="The contact form after the user types Anna into a Name box that has no onChange."
heading: Contact Us
form:
  field: Name | | bad
  textarea: Message |
line: 0 / 200
form:
  submit: Send
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

These are the same three steps as the box stuck on John. The browser accepts each letter, no code saves it in `name`, and React puts the empty `name` back into the box. So the fix is the same `onChange` the Message box already has:

```jsx title="src/components/ContactForm.jsx" startLine="21" good="3"
        <label>
          Name
          <input value={name} ~onChange={e => setName(e.target.value)}~ /> {/* Each letter now reaches state */}
        </label>
```

With the name in state, the Send handler can log the name too, and empty it together with the message:

```jsx title="src/components/ContactForm.jsx" startLine="11"
  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, message);
    ~setName('')~; // The Name box empties together with the message
    setMessage('');
  }
```

After a reload, Anna appears letter by letter, and the Console is clean:

```page width=text caption="The contact form after the fix, when the user types Anna into the Name box."
heading: Contact Us
form:
  field: Name | Anna | good
  textarea: Message |
line: 0 / 200
form:
  submit: Send
console: quiet
```

The Name box before the fix and the Name box after it differ by one prop, and both show the same empty text when the page opens. But they are NOT the same. Only the Name box with `onChange` saves each letter in `name` before React compares, so only its letters survive.

### Refusing a letter on purpose: the 200 limit

React puts back whatever state says, and that same behavior can be useful. The count under the Message box promises a limit of 200 characters, so let's make the box keep that promise. We add one check to the message handler:

```jsx title="src/components/ContactForm.jsx" startLine="7"
  function handleMessageChange(e) {
    ~if (e.target.value.length <= 200)~ { // Saves the text only while it fits
      setMessage(e.target.value);
    }
  }
```

Suppose the Message box already holds 200 characters, and the user types one more. The browser adds the letter, and React calls `handleMessageChange`. The new text is 201 characters long, so the handler does not call `setMessage`. Because `message` still holds the 200 characters, React puts them back into the box, and the extra letter is gone.

This is what "controlled" means in practice: the user proposes each change, and our handler decides whether it is accepted.

### The handler must save `e.target.value` right away

Because React compares the box with state as soon as the handler ends, the handler has two more rules: it must save the text right away, and it must save exactly `e.target.value`. Here is a Name handler that breaks the first rule, because it saves the text later, inside a timer:

```jsx title="A Name box whose handler saves the text later"
function handleNameChange(e) {
  ~setTimeout~(() => setName(e.target.value), 100); // **WRONG:** the state waits, but React puts the old text back right away
}

<input value={name} onChange={handleNameChange} />
```

The user types into this Name box, and the box refuses every letter, even though the handler runs on every key. Why?

Because React compares the box with `name` as soon as the handler ends, not a moment later:
1. The user presses a key, and the browser puts the letter into the box.
2. React calls `handleNameChange`, which only starts a timer and ends.
3. `name` still holds the old text, so React puts the old text back into the box.
4. When the timer runs, `e.target.value` reads the same box, which holds the old text again. `setName` saves the old text, and nothing changes.

So this box refuses letters just like a box with no `onChange`. This time, though, the Console stays quiet, because the box does have a handler. React's documentation puts the rule plainly: the state update cannot wait. It must happen inside the handler, right away.

A handler breaks the second rule when it saves a changed copy of the text, such as one that turns every letter into a capital with `toUpperCase`. The browser has just put one text into the box, and then React writes a different text into it. React's documentation lists this as a cause of a caret that jumps while the user types.

So keep the handler simple: save exactly `e.target.value`, right away. If you need to refuse a change, refuse the whole change with an `if`, as the 200 limit does.

> [!PRINCIPLE]
> **Principle 3: Read-Only: `value` Without `onChange` Freezes the Box**
>
> *Every box with `value` also needs an `onChange` handler that saves the new text, exactly as typed, right away.*
>
> The browser accepts every letter, even in a box with `value`. After each key, React compares the box with the state and puts the state back. So if no handler has saved the new letter, the state still holds the old text, the letter disappears, and the Console shows the read-only field error. The same freeze happens when the handler saves the text later, inside a timer. A box that should be frozen on purpose says so with `readOnly`, and then the browser refuses the letter itself.
>
> **DO THIS:**
> ```jsx
> <input value={name} ~onChange={e => setName(e.target.value)}~ /> {/* Each letter reaches state, so it stays */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input ~value={name}~ /> {/* **WRONG:** no onChange, so React puts the old text back after every key */}
> ```

## 4. Principle 4: The Same Pair on a Menu and a Tick Box

### The smallest version: a fruit menu and an agree box

So far, every box held text. A drop-down menu and a tick box hold a choice instead, but they can be controlled with the same idea. A drop-down menu is a `<select>`, and a tick box is an `<input type="checkbox" />`. When the page opens, the Fruit menu shows Orange, and the I agree box is not ticked:

```page width=text caption="A fruit menu and an agree box, when the page opens."
form:
  select: Fruit | Orange
  check: I agree | off
```

The Fruit menu takes `value`, just like a text box, and the I agree box takes `checked` instead:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [fruit, setFruit] = useState('orange');
  const [agree, setAgree] = useState(false);

  return (
    <form>
      <label>
        Fruit
        <select ~value={fruit}~ onChange={e => setFruit(e.target.value)}> {/* The chosen option comes from state */}
          <option value="apple">Apple</option>
          <option value="banana">Banana</option>
          <option value="orange">Orange</option>
        </select>
      </label>
      <label>
        <input type="checkbox" ~checked={agree}~ onChange={e => setAgree(e.target.checked)} /> {/* The tick comes from state */}
        I agree
      </label>
    </form>
  );
}
```

The user picks Banana and ticks I agree:

```page width=text caption="The same page after the user picks Banana and ticks I agree."
form:
  select: Fruit | Banana | good
  check: I agree | on | good
```

### HTML has two more starting values, and React renames them too

Principle 2 showed that HTML's `value` attribute is only a starting text, and that React calls that starting text `defaultValue`. HTML does the same thing twice more.

In HTML, you choose the starting option of a menu by writing `selected` on that option, and you tick a box from the start by writing `checked` on it. Both are starting values, just like the `value` attribute on a text box. The browser even names them that way in JavaScript: `option.defaultSelected` and `input.defaultChecked`.

React follows one rule for all of them. A prop whose name starts with default is a starting value, such as `defaultValue` and `defaultChecked`. A prop without default is the value right now, such as `value` and `checked`. With that rule in mind, the two mistakes in this principle are easy to predict.

### What `value` means on a menu

Start with the menu. On a `<select>`, `value` says which option is chosen, so it must match the value of one of its options. That is why each `<option>` has two texts:
- The text between its tags, such as Banana, is what the user reads.
- Its `value`, such as banana with a small b, is the string the menu reports to our code.

So when the user picks Banana in the Fruit menu, the menu's value becomes banana. React calls `onChange`, and the handler saves banana in `fruit`. React then makes the menu match `fruit`, so Banana stays chosen.

### Never mark an option as `selected`

Because the choice lives on the select, the HTML habit of marking an option no longer fits. A developer who knows HTML might still write the starting option the HTML way:

```jsx title="The plain HTML habit on a menu"
<select>
  <option value="delivery">Delivery</option>
  <option value="payment" ~selected~>Payment</option> {/* **WRONG:** the plain HTML habit, not supported in React */}
</select>
```

React does not support `selected` on an option. The menu still opens on Payment, but React prints a red error in the Console that tells you to use `value` or `defaultValue` on the select instead. That fits the rule above: in React, neither the starting choice nor the current choice lives on an option. Both live on the select, as `defaultValue` or `value`:

```jsx title="The React way on a menu"
<select ~value="payment"~ onChange={e => setTopic(e.target.value)}> {/* React chooses the option whose value matches */}
  <option value="delivery">Delivery</option>
  <option value="payment">Payment</option>
</select>
```

React reads `value` on the select and chooses the option whose `value` matches. When the menu only needs a starting choice and no state, use `defaultValue` on the select instead.

### What `checked` means on a tick box

Now the tick box. A tick box has no text to show. It is either ticked or not, so React does not control it with `value`. It uses **`checked`**, a React prop that holds true or false, and after every render, React makes the box ticked or unticked to match.

You met a tick box without `checked` in Lesson 18. It kept its own tick inside the browser, so it was uncontrolled. With `checked` from state, React decides the tick, and the box becomes controlled.

To bring the tick into state, the handler reads **`e.target.checked`**, which the browser supplies: true if the box is ticked right after the click, and false if not.

The rest of the pair carries over from text boxes. For a tick box that only needs a starting tick, React has `defaultChecked`, which works like `defaultValue`. And a tick box with `checked` and no `onChange` freezes, just like the Name box stuck on John in Principle 3. React prints the same read-only error, but this time it names `checked` and `defaultChecked`.

### The Topic menu on the contact form

Back to our contact form, which needs a Topic menu that starts on Delivery. Its state starts with the value of that option:

```jsx title="src/components/ContactForm.jsx" startLine="4"
  const [name, setName] = useState('');
  const [topic, setTopic] = ~useState('delivery')~; // The menu starts on Delivery
  const [message, setMessage] = useState('');
```

The Topic menu sits between the Name box and the Message box:

```jsx title="src/components/ContactForm.jsx"
        <label>
          Topic
          <select ~value={topic}~ onChange={e => setTopic(e.target.value)}> {/* Must match the value of one option */}
            <option value="delivery">Delivery</option>
            <option value="payment">Payment</option>
            <option value="other">Other</option>
          </select>
        </label>
```

The user types Anna and picks Payment, so `topic` now holds payment, and the Topic menu shows Payment:

```page width=text caption="The contact form after the user types Anna and picks Payment."

  field: Name | Anna
  select: Topic | Payment | good
```

### Mistake: reading `e.target.value` on the tick box

Next comes the tick box Email me a reply. Its state starts as false, because the box starts unticked:

```jsx title="src/components/ContactForm.jsx" startLine="7"
  const [wantsReply, setWantsReply] = useState(false);
```

The developer copies the handler from the text boxes, so it reads `e.target.value`:

```jsx title="src/components/ContactForm.jsx" bad="2"
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.value~)} /> {/* **WRONG:** reads a fixed string, not the tick */}
          Email me a reply
        </label>
```

The user ticks Email me a reply, and it looks ticked. Then the user clicks it again to untick it, and it stays ticked:

```page width=text caption="The contact form after the user ticks Email me a reply and then clicks it again to untick it."
heading: Contact Us
form:
  field: Name | Anna
  select: Topic | Payment
  textarea: Message |
line: 0 / 200
form:
  check: Email me a reply | on | bad
  submit: Send
```

The first click seemed to work, and the second click, with the same handler, did nothing. So what does `e.target.value` hold on a tick box?

Not the tick. In HTML, the value of a tick box is the word that a form sends to a server when the box is ticked. When the HTML gives no value, the browser uses the word on, and that word never changes with the tick. Here is what the two clicks do:
1. On the first click, `setWantsReply` saves the string on. React treats any string that is not empty as true for `checked`, so the box is ticked.
2. On the second click, the browser removes the tick, and React calls `onChange` again. `e.target.value` is still on.
3. `wantsReply` still holds on, so React puts the tick back, and the box stays ticked.

So the fix is to read the tick itself:

```jsx title="src/components/ContactForm.jsx" good="2"
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* true or false, right after the click */}
          Email me a reply
        </label>
```

After a reload, the box ticks and unticks with each click.

### Send puts the menu and the tick box back

Now that the menu and the tick box live in state, the Send handler can put every part of the form back to its start:

```jsx title="src/components/ContactForm.jsx" startLine="15"
  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, topic, message, wantsReply);
    setName('');
    ~setTopic('delivery')~; // Back to the first option
    setMessage('');
    ~setWantsReply(false)~; // Back to unticked
  }
```

Again, no line of our code touches the Topic menu or the tick box. When the user clicks Send, the handler saves delivery in `topic` and false in `wantsReply`. React renders `ContactForm` again and makes the Topic menu show Delivery and the tick box unticked. It is the same mechanism as the Message box, with different props.

> [!PRINCIPLE]
> **Principle 4: Menus and Tick Boxes: The Same Pair with Their Own Props**
>
> *Control a menu with `value` on the select itself, never `selected` on an option. Control a tick box with `checked`, and read `e.target.checked` in its handler.*
>
> In HTML, `selected` on an option and `checked` on a tick box are only starting values. React keeps the current value on the element the user changes: `value` on the select, and `checked` on the tick box. A menu reports the `value` of the picked option, so `value` on the select must match one option. On a tick box, `e.target.value` is the word a form would send to a server, such as on, and it never changes with the tick, so the handler reads `e.target.checked` instead.
>
> **DO THIS:**
> ```jsx
> <select ~value={topic}~ onChange={e => setTopic(e.target.value)}> {/* The choice lives on the select */}
> <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* true or false, right after the click */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <option value="payment" ~selected~>Payment</option> {/* **WRONG:** not supported in React */}
> <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.value~)} /> {/* **WRONG:** always 'on', so the box never unticks */}
> ```

## 5. Principle 5: A Controlled Box Starts with an Empty String

### The smallest version: a City box that starts with nothing

Every box so far started with a real value: an empty string, John, or false. Here is a City box whose state starts with nothing at all. When the page opens, it looks like any empty box, and the Console is clean:

```page width=text caption="A City box whose state starts with nothing, when the page opens."
form:
  field: City |
console: quiet
```

The only difference from the boxes before is the empty call to `useState`:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [city, setCity] = ~useState()~; // **WRONG:** no starting value at all

  return (
    <label>
      City
      <input value={city} onChange={e => setCity(e.target.value)} />
    </label>
  );
}
```

The user types a. The letter appears, and a red message appears in the Console too:

```page width=text caption="The same page after the user types a into the City box."
form:
  field: City | a
console: A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen. Decide between using a controlled or uncontrolled input element for the lifetime of the component. More info: https://react.dev/link/controlled-components
```

### Where did `undefined` come from?

The message talks about `undefined`, but our code never writes `undefined`. JavaScript supplies it. `useState` received no starting value, and in JavaScript a missing argument is `undefined`. So `city` starts as `undefined`.

### Why React warns when the box works

The City box works, so what is React complaining about? The answer is in how React decides whether a box is controlled. It looks at the box's `value` on every render. For React, `value={undefined}` is the same as having no value at all. That gives this order:
1. The page opens. `city` is `undefined`, so React treats the City box as uncontrolled.
2. The user types a. `onChange` runs, and `setCity` saves the string a.
3. React renders again. Now the City box has a real `value`, the string a.
4. The same box has switched from uncontrolled to controlled. React cannot tell which one we meant, so it warns.

React's documentation explains it the same way: "React won't know whether you want the component to be uncontrolled or controlled." A box must stay one kind for its whole life.

The warning makes sense once you see what React has to work with. It reads our intention from one value on one render. A missing starting value and a box we meant to leave to the browser look exactly the same to React, so React cannot tell a slip from a choice.

### Starting with nothing and starting with an empty string are NOT the same

When the page opens, a City box whose state starts with nothing and a City box whose state starts with an empty string draw the same empty box. They differ at step 1 of the order above. With an empty string, `value` is a real string from the very first render, so the box is controlled from the start, and it never switches.

### Mistake: the Email box that appears with nothing in it

On the contact form, this mistake hides in the Email box. When the user ticks Email me a reply, an Email box should appear, and the `&&` from Lesson 10 shows it only when `wantsReply` is true:

```jsx title="src/components/ContactForm.jsx"
        {wantsReply && (
          <label>
            Email
            <input value={email} onChange={e => setEmail(e.target.value)} />
          </label>
        )}
```

The email is not needed until the box is ticked, so the developer gives its state no starting value:

```jsx title="src/components/ContactForm.jsx" startLine="8" bad="1"
  const [email, setEmail] = ~useState()~; // **WRONG:** undefined until the first key
```

The user ticks Email me a reply, and an empty Email box appears. Then the user types a, and the warning appears:

```page width=text caption="The contact form after the user ticks Email me a reply and types a into the Email box."
heading: Contact Us
form:
  field: Name | Anna
  select: Topic | Payment
  textarea: Message |
line: 0 / 200
form:
  check: Email me a reply | on
  field: Email | a | bad
  submit: Send
console: A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen. Decide between using a controlled or uncontrolled input element for the lifetime of the component. More info: https://react.dev/link/controlled-components
```

These are the same steps as the City box. `email` starts as `undefined`, the first key turns it into a string, and the Email box switches from uncontrolled to controlled. So the fix is one empty string:

```jsx title="src/components/ContactForm.jsx" startLine="8" good="1"
  const [email, setEmail] = ~useState('')~; // A real string from the first render
```

After a reload, typing into the Email box gives no warning.

### Send clears the whole form

With every part of the form in state, the Send handler empties the email too. Every state goes back to its start, and no line of our code touches a box:

```jsx title="src/components/ContactForm.jsx" startLine="16"
  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, topic, message, wantsReply, email);
    setName('');
    setTopic('delivery');
    setMessage('');
    setWantsReply(false);
    ~setEmail('')~; // An empty string, never undefined
  }
```

The email is cleared with an empty string, the same kind of value it started with. Clearing it with `undefined` or `null` would make the Email box switch the other way, from controlled to uncontrolled.

> [!PRINCIPLE]
> **Principle 5: Starting Value: A Controlled Box Starts with an Empty String**
>
> *The state behind `value` must hold a string from the first render, so the state of an empty box starts as an empty string, never as nothing.*
>
> React decides on every render whether a box is controlled by looking at its `value`, and a value of `undefined` counts as no value at all. A `useState` call with no starting value gives `undefined`, so the box starts uncontrolled. On the first key, the state becomes a string and the box becomes controlled, and React warns, because a box cannot switch over its life. An empty string makes the box controlled from the first render, so start with one, and clear the box with one too.
>
> **DO THIS:**
> ```jsx
> const [email, setEmail] = ~useState('')~; // Controlled from the first render
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [email, setEmail] = ~useState()~; // **WRONG:** undefined first, a string later, so React warns
> ```

## Putting All Five Principles Together

### The complete `ContactForm.jsx` file

Each principle added one part to the form, and here they all are in one file. Every box takes what it shows from state, and every box reports its changes back to state:

```jsx title="src/components/ContactForm.jsx"
import { useState } from 'react';

export default function ContactForm() {
  const [name, setName] = useState('');
  const [topic, setTopic] = useState('delivery');
  const [message, setMessage] = useState('');
  const [wantsReply, setWantsReply] = useState(false);
  const [email, setEmail] = ~useState('')~; // 5. Starts with a string, never undefined

  function handleMessageChange(e) {
    if (e.target.value.length <= 200) {
      setMessage(e.target.value);
    }
  }

  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, topic, message, wantsReply, email);
    setName('');
    setTopic('delivery');
    setMessage('');
    setWantsReply(false);
    setEmail('');
  }

  return (
    <section>
      <h1>Contact Us</h1>
      <form onSubmit={handleSend}>
        <label>
          Name
          <input value={name} ~onChange={e => setName(e.target.value)}~ /> {/* 3. value always comes with onChange */}
        </label>
        <label>
          Topic
          <select ~value={topic}~ onChange={e => setTopic(e.target.value)}> {/* 4. The choice lives on the select */}
            <option value="delivery">Delivery</option>
            <option value="payment">Payment</option>
            <option value="other">Other</option>
          </select>
        </label>
        <label>
          Message
          <textarea ~value={message}~ onChange={handleMessageChange} /> {/* 2. State goes into the box */}
        </label>
        <p>{message.length} / 200</p>
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* 4. The tick, not the text */}
          Email me a reply
        </label>
        {wantsReply && (
          <label>
            Email
            <input value={email} ~onChange~={e => setEmail(e.target.value)} /> {/* 1. Every key goes into state */}
          </label>
        )}
        <button type="submit">Send</button>
      </form>
    </section>
  );
}
```

The user fills in every part of the form:


### How React calls the components, and what one key does

When the page loads, React starts at `App` and follows the tags. `App` has only one tag, so React calls `ContactForm` next:

```tree caption="The component tree of the contact page and the order in which React calls each component."
`main.jsx` mounts `App` inside `<StrictMode>`
- +`App` [1. Called first] | **Root component** | Returns `<ContactForm />`
  - +`ContactForm` [2. Called second] | Holds **five states**, one for each part of the form | Called again after **every key**, every pick, every tick, and every Send
```

Inside `ContactForm`, every controlled box goes around the same loop on every key:

```tree dir=right caption="The loop that one key runs in a controlled box, from the browser to state and back into the box."
One key in a controlled box
- +1. The browser | Shows the new letter in the box for a moment
- +2. `onChange` | React calls our handler with the event object
- +3. The setter [`setMessage`] | Saves the new text in **state**
- +4. React renders again | Writes the state into the box through **`value`** | The letter stays
```

### Summary

| Aspect | The Plain JavaScript Habit | The React Rule |
| :--- | :--- | :--- |
| **Reporting each key** | Listen to the `change` event, which waits until the user leaves the box, or save the text in a plain variable | Use `onChange`, which fires on every key, and save `e.target.value` with the setter |
| **Emptying a box** | Reach into the box and clear its text by hand | Give the box `value` from state, then set the state to an empty string |
| **A box with a value** | Write the value and expect the user can still type | Always pair `value` with `onChange`, or use `defaultValue` or `readOnly` |
| **Menus and tick boxes** | Write `selected` on an option, and read `value` from a tick box | Put `value` on the select, and use `checked` with `e.target.checked` |
| **The starting value** | Leave a variable empty until it is needed | Start every controlled box with an empty string, never `undefined` |

## For the Interview

> **The Interview Question:** How do you make an input, textarea, or select fully controlled by React state?

### How to Answer Clearly in 30 Seconds

"A controlled field takes what it shows from state and reports every change back to state. I give it two props: `value` from state, and `onChange`, which saves `e.target.value` with the setter. React's `onChange` fires on every key, like the browser's `input` event, not like the `change` event. After every render, React makes the field match the state, so state is the single source of truth. To empty the field after Send, I only set the state to an empty string. Four rules keep this working:
1. **`value` always comes with `onChange`.** Without it, React puts the old text back after every key and logs a read-only field error. The handler saves exactly `e.target.value`, right away.
2. **`defaultValue` is not controlled.** It is what HTML calls the `value` attribute, a starting text, and after that the field keeps its own text.
3. **Menus and tick boxes use the same pair.** A `<select>` takes `value` on the select itself, never `selected` on an option. A checkbox takes `checked` and reads `e.target.checked`.
4. **Start with an empty string.** A controlled field must get a string from the first render. If it starts as `undefined`, React warns that an uncontrolled input is changing to controlled."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What is the difference between a controlled and an uncontrolled input, and when would you use each?"**
   A controlled input gets `value` from state, or `checked` for a checkbox, and reports with `onChange`. React makes it show what state holds after every render. An uncontrolled input has no `value`. It may get a starting text from `defaultValue` or `defaultChecked`, and after that the browser keeps its text. A controlled field is worth it in two cases. The page needs the text on every key, such as for a live count. Or our code must change the field, such as emptying it after Send. A field can never be both, and it cannot switch over its life. Choosing between controlled fields and reading an uncontrolled form with `FormData` at submit time is the topic of Lesson 40.

2. **"Why does my input's caret jump, or why does typing feel slow?"**
   A caret jumps when the handler does not save exactly `e.target.value` right away. Two common causes are saving a changed copy, such as with `toUpperCase`, and saving later, inside `setTimeout`. Another cause is a field that React removes and adds again on every key. That happens when a component is defined inside another component, as in Lesson 04, or when its `key` changes, which Lesson 25 covers. Slow typing has a different cause. Every key sets state, and every state change renders the component that holds it. If that component draws a large page, every key makes React render all of it again. The fix is to move the field and its state into a small component of its own, so each key renders only that small part. `useDeferredValue`, from Lesson 68, is another tool for this.

3. **"How do you control a select, a checkbox, and a field whose value comes from an API?"**
   A `<select>` gets `value` on the select, and it must match the `value` of one `<option>`. Writing `selected` on an option is not supported in React. A select with `multiple` takes a list of values instead of one string. A checkbox gets `checked`, which must always be true or false, and its handler reads `e.target.checked`. On a checkbox, `e.target.value` is the word a form would send to a server, on by default, and it never changes with the tick. A value from an API is often `null` or `undefined` until it arrives. So start the state with an empty string, or write `value={someValue ?? ''}`. The `??` uses the empty string whenever the left side is `null` or `undefined`, so the field always gets a string.
