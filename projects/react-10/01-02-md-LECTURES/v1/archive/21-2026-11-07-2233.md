## Why a Component Keeps the Name of the Screen in State

### The smallest version: one `status`, two screens

When the page opens, it shows one button:

```page width=text caption="The page when it opens: one Paris button."
line: [Paris]
console: quiet
```

Here is the whole component behind it. Its state holds the name of the screen the user sees, and we call that state `status`:

```jsx title="One status, two screens"
function Quiz() {
  const [status, setStatus] = useState('asking');

  if (~status === 'right'~) { // After the click: only the heading is left
    return <h1>That's right!</h1>;
  }
  return <button onClick={() => ~setStatus('right')~}>Paris</button>; // Before the click: one Paris button
}
```

The user clicks `Paris`, and the button is gone. Only the heading is left:

```page width=text caption="The same page after the user clicks Paris: the button is gone, and only the heading is left."
heading: That's right!
console: quiet
```

No line of our code removes the button. The click only changes `status` to `'right'`, and React draws the screen for `'right'`, which has no button in it. This lesson builds a whole page in this way.

### The real page: a quiz that shows two answers at once

Everyone has answered a quiz question on a website. Our page asks `What is the capital of France?`. It has a text box, a `Check` button, and two answer lines that wait out of sight: `That's right!` and `Not quite. Try again!`. First we build it in plain JavaScript, with no React, the imperative way of Lesson 01, where our own code changes the page by hand.

Both answer lines sit in the HTML from the start, and each one carries `hidden`. `hidden` is a browser attribute: the browser keeps an element that carries it out of sight, until our code sets the element's `hidden` property to `false`.

```html title="index.html"
<h2>Capital quiz</h2>
<p>What is the capital of France?</p>
<input id="answer" />
<button id="check">Check</button>
<p id="right" ~hidden~>That's right!</p> <!-- In the HTML, but out of sight -->
<p id="wrong" ~hidden~>Not quite. Try again!</p> <!-- In the HTML, but out of sight -->
<script src="src/quiz.js"></script>
```

The script finds the box, the button, and the two lines. When the user clicks `Check`, it shows one of the two lines:

```js title="src/quiz.js"
const box = document.getElementById('answer');
const button = document.getElementById('check');
const rightText = document.getElementById('right');
const wrongText = document.getElementById('wrong');

button.addEventListener('click', () => {
  if (box.value === 'Paris') {
    ~rightText.hidden = false;~ // Shows That's right!
  } else {
    ~wrongText.hidden = false;~ // Shows Not quite. Try again!
  }
});
```

The user types `Lyon` and clicks `Check`. The wrong line appears, as it should:

```page width=text caption="The plain JavaScript quiz after the user types Lyon and clicks Check."
heading: Capital quiz
line: What is the capital of France?
form:
  field:  | Lyon
  button: Check
line: Not quite. Try again!
console: quiet
```

Then the user changes the answer to `Paris` and clicks `Check` again. Now the page tells the user that the answer is right and wrong at the same time:

```page width=text caption="The same quiz after the user changes the answer to Paris and clicks Check: both answer lines are on the page."
heading: Capital quiz
line: What is the capital of France?
form:
  field:  | Paris | good
  button: Check
line: That's right! | good
line: Not quite. Try again! | bad
console: quiet
```

The wrong line stays because no line of the handler ever hides it:
1. On the first click, the box holds `Lyon`, so the `else` branch sets `wrongText.hidden` to `false`.
2. On the second click, the box holds `Paris`, so the `if` branch sets `rightText.hidden` to `false`.
3. The `if` branch never touches `wrongText`, so the wrong line stays where the first click put it.

To fix it, every branch must undo what every other branch did. Each new part of the page makes that harder. A `Checking...` line or a dimmed button adds lines to every branch, and when the developer forgets one of them, the page no longer matches the answer. React.dev names this exact risk: "Adding a new UI element or a new interaction would require carefully checking all existing code to make sure you haven't introduced a bug." Its own example of such a bug is the one on our page: forgetting to show or hide something.

### Four Principles of Reacting to Input with State

**PRINCIPLES:** In React, a handler never shows or hides a part of the page. It changes state, and the JSX already describes the page for every value that state can hold. Four rules follow from that:
1. **Each visual state gets its own mockup.** Before writing any handler, list every screen the user can see, and draw each one as JSX chosen by a `status` prop. A screen that is never drawn can never be shown.
2. **One `status` shows one message at a time.** Screens that exclude each other live in one state variable that holds one string. One boolean per screen allows mixes that match no screen at all.
3. **`answer.length` turns the Check button off.** When the page can read something from state you already have, compute it during render. A stored copy changes only when a handler remembers to change it.
4. **Clicks and timers only set `status`.** Every input, from the user or from the computer, only names the next screen. The JSX for that screen leaves out every other line, so no handler has to hide anything.

Here is the map of the four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Each Visual State Gets Its Own Mockup** | A handler written before the screens are listed forgets one of them, and the user who gives a wrong answer sees nothing happen. | List every visual state first, and draw each one as JSX chosen by a `status` prop. |
| **Principle 2** | **One `status` Shows One Message at a Time** | One boolean per screen lets `Checking...` and `Not quite. Try again!` show together, and the dimmed box locks the user out. | Keep screens that exclude each other in one `status` string, never in several booleans. |
| **Principle 3** | **`answer.length` Turns the Check Button Off** | A stored `isEmpty` falls out of step with the box, so the user can check an empty answer and be told it is wrong. | Compute what you can from existing state during render, such as `answer.length === 0`. |
| **Principle 4** | **Clicks and Timers Only Set `status`** | Showing and hiding parts by hand leaves an old message on the page, and every new screen means editing every branch. | Let every human input and computer input set the next `status`, and let the JSX draw that screen. |

## 1. Principle 1: Each Visual State Gets Its Own Mockup

### The smallest version: a light that draws On or Off

This page shows two lights, one off and one on:

```page width=text caption="A page with two Light components: the first one draws Off, the second one draws On."
line: Off
line: On
console: quiet
```

Both come from the same component. Only the `status` prop differs:

```jsx title="One component, two screens chosen by a status prop"
function Light({ ~status = 'off'~ }) { // No status passed in: status is 'off'
  return status === 'on' ? <p>On</p> : <p>Off</p>;
}

<Light /> {/* Draws Off */}
<Light ~status="on"~ /> {/* Draws On */}
```

`Light` has no handler and no state. It draws the screen that its `status` asks for, and nothing else.

### What a visual state is

Before a single button works, a designer draws one picture of the screen for every moment the user can see: the empty form, the form while it sends, and the thank-you note. React.dev borrows the designer's word for each of those pictures: a *visual state*. A visual state is one screen the user can see.

`Light` has two visual states, and its `status` prop names the one to draw. The name `status` is our own, and React gives it no meaning. React.dev says so plainly: "You could call that prop anything you like, the naming is not important."

JSX that draws one screen with no logic behind it is called a *mockup*. React.dev explains why we start there: "Mocking lets you quickly iterate on the UI before you wire up any logic."

### Mistake: starting from the click and forgetting a screen

A developer who starts from the click thinks of two outcomes only: the answer is right, or nothing happens. The text of the box sits in `answer`, as in Lesson 20, and the screen sits in `status`, as in the Paris button at the start of this lecture. The first handler covers only the right answer:

```jsx title="A handler written before the screens were listed"
function handleCheck() {
  ~if (answer === 'Paris')~ { // **WRONG:** only the right screen exists, so Lyon changes nothing
    setStatus('right');
  }
}
```

The user who types `Lyon` can click `Check` again and again and never gets an answer, because the JSX has no wrong screen for any handler to show.

Listing every screen first finds the missing one before any handler exists. The capital quiz has five:

```tree caption="The five visual states of the capital quiz, listed before any handler is written."
The five screens a user of the capital quiz can see
- +empty [`'empty'`] | The box is empty | The Check button is **dimmed**
- +typing [`'typing'`] | The user has typed an answer | The Check button is **live**
- +checking [`'checking'`] | The box and the button are **dimmed** | The line **Checking...** shows
- !wrong [`'wrong'`] | The box and the button are live again | The line **Not quite. Try again!** shows | !The screen the click-first handler forgot
- +right [`'right'`] | Everything else is gone | Only the heading **That's right!** shows
```

### Drawing the five screens of `CapitalQuiz`

Two of the screens dim a part of the page. The browser does that with the `disabled` attribute: a box or a button with `disabled` set to `true` turns grey and stops reacting to the user. React.dev describes it for the box: "If `true`, the input will not be interactive and will appear dimmed." The Check button must be off in two screens, empty and checking, so we join the two checks with two vertical bars, `||`, which JavaScript reads as "or".

The first version of the quiz is a mockup, like `Light`. It takes a `status` prop and draws the screen that the prop names:

```jsx title="src/components/CapitalQuiz.jsx"
export default function CapitalQuiz({ ~status = 'empty'~ }) { // No status passed in: status is 'empty'
  if (status === 'right') {
    return <h1>That's right!</h1>;
  }

  return (
    <>
      <h2>Capital quiz</h2>
      <p>What is the capital of France?</p>
      <input ~disabled={status === 'checking'}~ /> {/* Dimmed only while checking */}
      <button ~disabled={status === 'empty' || status === 'checking'}~>Check</button> {/* Dimmed when empty or checking */}
      {status === 'checking' && <p>Checking...</p>}
      {status === 'wrong' && <p>Not quite. Try again!</p>}
    </>
  );
}
```

To see all five screens at once, `App` renders the mockup once for each name in a list. Each name in `statuses` reaches the mockup as its `status` prop:

```jsx title="src/App.jsx"
import CapitalQuiz from './components/CapitalQuiz.jsx';

const statuses = ['empty', 'typing', 'checking', 'wrong', 'right'];

export default function App() {
  return (
    <>
      {~statuses.map~(status => ( // One section for each screen
        <section key={status}>
          <h4>CapitalQuiz ({status}):</h4>
          <CapitalQuiz ~status={status}~ /> {/* Passes this screen's name to the mockup */}
        </section>
      ))}
    </>
  );
}
```

### Designers and computer scientists name the same idea

React.dev says that "React stands at the intersection of design and computer science." A designer calls each screen a visual state. A computer scientist calls the whole set of screens, together with the moves between them, a *state machine*. Both words describe the same list.

A page that shows every visual state at once, like the one `App` draws above, is often called a *living styleguide* or a *storybook*. A team can review every screen there before any logic exists. The flow can even be sketched on paper first, with each screen as a labeled circle and each change as an arrow. React.dev: "You can sketch out many flows this way and sort out bugs long before implementation."

> [!PRINCIPLE]
> **Principle 1: Visual States: Draw Every Screen Before Writing Any Handler**
>
> *List every screen the user can see, give each one a name, and draw each one as JSX chosen by a `status` prop.*
>
> A handler written first, starting from the click, covers only the outcome the developer had in mind. The user who gives a wrong answer clicks and sees nothing, because the wrong screen was never drawn. Listing the visual states first, empty, typing, checking, wrong, and right, finds the missing screen before any logic exists. Each mockup draws exactly what its `status` asks for, and a page that renders every mockup at once lets the whole team check every screen.
>
> **DO THIS:**
> ```jsx
> <CapitalQuiz status="empty" />
> <CapitalQuiz status="checking" />
> <CapitalQuiz ~status="wrong"~ /> {/* The wrong screen is drawn before any handler exists */}
> <CapitalQuiz status="right" />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleCheck() {
>   ~if (answer === 'Paris')~ { // **WRONG:** no wrong screen exists, so Lyon changes nothing on the page!
>     setStatus('right');
>   }
> }
> ```

## 2. Principle 2: One `status` Shows One Message at a Time

### The smallest version: two booleans and one `status`

Compare two ways to store the same three screens: typing, checking, and wrong.

```jsx title="With isChecking and isWrong"
const [~isChecking~, setIsChecking] = useState(false); // true or false
const [~isWrong~, setIsWrong] = useState(false); // true or false: four mixes, and both true matches no screen
```

```jsx title="With one status"
const [~status~, setStatus] = useState('typing'); // 'typing', 'checking', or 'wrong': three values, three screens
```

It looks the same, but it is NOT the same thing! Two booleans give four mixes. Both `false` is typing, only `isChecking` is checking, and only `isWrong` is wrong. The fourth mix, both `true`, means checking and wrong at the same moment, a screen no user should ever see. `status` holds one string, so it can only name one screen at a time.

React.dev calls such a mix an *impossible state*, and explains the cure:

> There are four possible combinations of two booleans, but only three correspond to valid states. To remove the "impossible" state, you can combine these into a `status` that must be one of three values.

### Mistake: one boolean for each screen

The mockup becomes a real component now. `CapitalQuiz` stops taking a `status` prop, and `App` renders one real quiz:

```jsx title="src/App.jsx"
import CapitalQuiz from './components/CapitalQuiz.jsx';

export default function App() {
  return ~<CapitalQuiz />~; // One real quiz instead of five mockups
}
```

A developer who thinks one screen at a time gives each screen its own boolean. The box is controlled, as in Lesson 20. The boolean `isEmpty` dims the Check button while the box is empty, and Principle 3 comes back to it. The timer stands in for the server:

```jsx title="src/components/CapitalQuiz.jsx" startLine="1"
import { useState } from 'react';

export default function CapitalQuiz() {
  const [answer, setAnswer] = useState('');
  const [isEmpty, setIsEmpty] = useState(true);
  const [isChecking, setIsChecking] = useState(false);
  const [isWrong, setIsWrong] = useState(false);
  const [isRight, setIsRight] = useState(false);

  function handleChange(e) {
    setAnswer(e.target.value);
    setIsEmpty(false);
  }

  function handleCheck() {
    setIsChecking(true);
    setTimeout(() => {
      if (answer === 'Paris') {
        setIsChecking(false);
        setIsRight(true);
      } else {
        ~setIsWrong(true);~ // **WRONG:** forgets setIsChecking(false), so isChecking stays true!
      }
    }, 1000);
  }

  if (isRight) {
    return <h1>That's right!</h1>;
  }

  return (
    <>
      <h2>Capital quiz</h2>
      <p>What is the capital of France?</p>
      <input value={answer} onChange={handleChange} disabled={isChecking} />
      <button onClick={handleCheck} disabled={isEmpty || isChecking}>Check</button>
      {isChecking && <p>Checking...</p>}
      {isWrong && <p>Not quite. Try again!</p>}
    </>
  );
}
```

The user types `Lyon` and clicks `Check`. One second later, the page shows both lines, and the box and the Check button stay dimmed:

```page width=text caption="The quiz one second after the user types Lyon and clicks Check: Checking... and Not quite. Try again! show together, and the box and the Check button stay dimmed."
heading: Capital quiz
line: What is the capital of France?
form:
  field:  | Lyon | bad
  button: Check
line: Checking... | bad
line: Not quite. Try again! | bad
console: quiet
```

The quiz is stuck because both booleans are now `true`:
1. The click runs `handleCheck`, which sets `isChecking` to `true`, and React dims the box and the button.
2. One second later, the timer runs the `else` branch. It sets `isWrong` to `true`, and no line sets `isChecking` back to `false`.
3. Now `isChecking` and `isWrong` are both `true`, a mix that matches none of our five screens.
4. The JSX draws both lines, and `disabled={isChecking}` keeps the box and the button dimmed.
5. The user can no longer type a new answer or click `Check`, so no handler can ever run again. The quiz stays stuck until the user reloads the page.

React.dev warns about exactly this screen: "you never want to show an error message and disable the input at the same time, or the user won't be able to correct the error!"

### The fix: one `status` that holds one screen

We keep `isEmpty` for now and replace the other three booleans with one `status`. Because `isEmpty` still handles the empty box, `status` starts at `'typing'`. Each pair of setters in the timer becomes one call:

```jsx title="src/components/CapitalQuiz.jsx" startLine="1"
import { useState } from 'react';

export default function CapitalQuiz() {
  const [answer, setAnswer] = useState('');
  const [isEmpty, setIsEmpty] = useState(true);
  const [~status~, setStatus] = useState('typing'); // One string replaces isChecking, isWrong, and isRight

  function handleChange(e) {
    setAnswer(e.target.value);
    setIsEmpty(false);
  }

  function handleCheck() {
    ~setStatus('checking');~ // The box and the button dim, and Checking... appears
    setTimeout(() => {
      if (answer === 'Paris') {
        setStatus('right');
      } else {
        ~setStatus('wrong');~ // 'wrong' is not 'checking': the box and the button come back
      }
    }, 1000);
  }

  if (status === 'right') {
    return <h1>That's right!</h1>;
  }

  return (
    <>
      <h2>Capital quiz</h2>
      <p>What is the capital of France?</p>
      <input value={answer} onChange={handleChange} disabled={status === 'checking'} />
      <button onClick={handleCheck} disabled={isEmpty || status === 'checking'}>Check</button>
      {status === 'checking' && <p>Checking...</p>}
      {status === 'wrong' && <p>Not quite. Try again!</p>}
    </>
  );
}
```

Setting `status` to `'wrong'` now ends the checking screen and starts the wrong screen in the same render, because `status` cannot hold `'checking'` and `'wrong'` at once. The user can type a new answer and try again:

```page width=text caption="The quiz one second after the user types Lyon and clicks Check, with one status: Checking... is gone, and the box and the Check button are live again."
heading: Capital quiz
line: What is the capital of France?
form:
  field:  | Lyon | good
  button: Check
line: Not quite. Try again! | good
console: quiet
```

The strings `'typing'`, `'checking'`, `'wrong'`, and `'right'` are our own. React stores the string and never reads its meaning. Only our `===` checks in the JSX turn each string into a screen.

### Why one string is safer than many booleans

Each new boolean doubles the mixes. Three booleans give eight, and five give thirty-two, while the quiz has only five screens. React.dev: "Simplicity is key: each piece of state is a "moving piece", and you want as few "moving pieces" as possible. More complexity leads to more bugs!"

When the JSX reads better with a name such as `isChecking`, compute that name from `status` during render, with an ordinary constant:

```jsx title="A name computed from status during render"
const ~isChecking~ = status === 'checking'; // A constant, not state: it always agrees with status
```

React.dev says of such names: "they're not state variables, so you don't need to worry about them getting out of sync with each other."

One string removes the impossible mixes inside one state variable. Some mixes can still hide across two variables, such as an error message kept next to a status that says the answer is right. A reducer removes those, and Lesson 27 teaches it.

> [!PRINCIPLE]
> **Principle 2: One Status: Keep Screens That Exclude Each Other in One String**
>
> *When only one screen can be true at a time, store it in one `status` state variable that holds one string, not in one boolean per screen.*
>
> Separate booleans allow mixes that match no screen. When the timer sets `isWrong` and forgets to clear `isChecking`, the page shows `Checking...` and `Not quite. Try again!` together, and the dimmed box locks the user out. One `status` can only hold one name at a time, so setting it to `'wrong'` ends the checking screen in the same render.
>
> **DO THIS:**
> ```jsx
> const [status, setStatus] = useState('typing');
> setTimeout(() => {
>   ~setStatus('wrong');~ // One call: checking ends and the wrong line appears together
> }, 1000);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [isChecking, setIsChecking] = useState(false);
> const [isWrong, setIsWrong] = useState(false);
> setTimeout(() => {
>   ~setIsWrong(true);~ // **WRONG:** isChecking stays true, so both lines show and the box stays dimmed!
> }, 1000);
> ```

## 3. Principle 3: `answer.length` Turns the Check Button Off

### The smallest version: a stored `isEmpty` and a computed one

Compare two ways to turn the Check button off while the box is empty:

```jsx title="With isEmpty in state"
const [isEmpty, setIsEmpty] = useState(true);
<button ~disabled={isEmpty}~>Check</button> {/* Changes only when a handler remembers to call setIsEmpty */}
```

```jsx title="With answer.length === 0"
<button ~disabled={answer.length === 0}~>Check</button> {/* Read from answer on every render */}
```

It looks the same, but it is NOT the same thing! The stored `isEmpty` is a second copy of something `answer` already knows, and it changes only when a handler remembers to change it. `answer.length === 0` is read fresh from `answer` on every render, so it can never disagree with the box.

### Mistake: the Check button stays on for an empty box

Our quiz still carries `isEmpty`. Its handler looks harmless:

```jsx title="src/components/CapitalQuiz.jsx" startLine="8"
  function handleChange(e) {
    setAnswer(e.target.value);
    ~setIsEmpty(false);~ // **WRONG:** sets false on every keystroke, even when the box becomes empty!
  }
```

The user types `Lyon`, then deletes all four letters. The box is empty, and the Check button is still on. The user clicks it, and one second later the quiz calls the empty answer wrong:

```page width=text caption="The quiz after the user types Lyon, deletes all four letters, and clicks Check: the empty answer is marked wrong."
heading: Capital quiz
line: What is the capital of France?
form:
  field:  |  | bad
  button: Check
line: Not quite. Try again! | bad
console: quiet
```

`handleChange` sets `isEmpty` to `false` on every keystroke by the user, even on the keystroke that deletes the last letter:
1. The user types the `L` of `Lyon`. `handleChange` sets `isEmpty` to `false`, and the button turns on.
2. The user presses Backspace four times. Each press runs `handleChange`, and after the last one `answer` is an empty string.
3. Each time, `handleChange` sets `isEmpty` to `false` again, because it never looks at the text.
4. The button reads `isEmpty`, which is still `false`, so the button stays on.
5. The user clicks `Check`. One second later the timer compares the empty string with `'Paris'` and sets `status` to `'wrong'`.

React.dev names this risk: "By making them separate state variables, you risk them going out of sync and causing bugs."

### The fix: read the empty screen from `answer`

React.dev asks three questions about every state variable:
- "Does this state cause a paradox?" That is the impossible state of Principle 2.
- "Is the same information available in another state variable already?"
- "Can you get the same information from the inverse of another state variable?"

`isEmpty` fails the second question, because `answer` already says whether the box is empty. So we delete `isEmpty`, its setter, and `handleChange`. The two state lines that are left look like this:

```jsx title="src/components/CapitalQuiz.jsx" startLine="3"
export default function CapitalQuiz() {
  const [answer, setAnswer] = useState('');
  const [status, setStatus] = useState('typing');
```

The box goes back to the one-line handler of Lesson 20, and the Check button reads `answer` directly:

```jsx title="src/components/CapitalQuiz.jsx" startLine="26"
      <input value={answer} onChange={e => setAnswer(e.target.value)} disabled={status === 'checking'} />
      <button onClick={handleCheck} ~disabled={answer.length === 0 || status === 'checking'}~>Check</button> {/* Off the moment the box is empty again */}
```

The empty screen never needed a name in `status`. It is the typing screen while `answer` is empty, so `status` holds only `'typing'`, `'checking'`, `'wrong'`, or `'right'`. Now, when the user deletes the last letter, the Check button dims again:

```page width=text caption="The quiz after the user types Lyon and deletes all four letters, with answer.length === 0: the Check button is dimmed."
heading: Capital quiz
line: What is the capital of France?
form:
  field:  | 
  button: Check
console: quiet
```

```dom caption="The Elements panel at the same moment: the Check button carries disabled again."
<input value="">
+ <button disabled="">Check</button> | note: answer.length is 0
```

The quiz is left with two state variables, `answer` and `status`, and neither one can be removed without breaking the page. React.dev calls such state *essential*: "You know they are essential, because you can't remove any of them without breaking the functionality."

### From many state variables to the essential ones

The boolean version of the quiz had five state variables: `answer`, `isEmpty`, `isChecking`, `isWrong`, and `isRight`. The clean version has two. React.dev makes the same clean-up on its own form and goes from seven state variables down to three essential ones.

The same move works for an error flag. React.dev: "`isError` is not needed because you can check `error !== null` instead." The full rules for redundant and duplicate state come in Lesson 22.

> [!PRINCIPLE]
> **Principle 3: Essential State: Compute What You Can Read from Existing State**
>
> *When the page can read something from state you already have, compute it during render instead of storing a copy of it.*
>
> A stored `isEmpty` changes only when a handler remembers to change it. A handler that sets it to `false` on every keystroke leaves the Check button on after the user deletes the last letter, and the quiz marks the empty answer wrong. `answer.length === 0` is read from `answer` on every render, so the button can never disagree with the box. What is left, `answer` and `status`, is the essential state.
>
> **DO THIS:**
> ```jsx
> <button ~disabled={answer.length === 0 || status === 'checking'}~>Check</button> {/* Read from answer on every render */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleChange(e) {
>   setAnswer(e.target.value);
>   ~setIsEmpty(false);~ // **WRONG:** stays false after the user deletes the last letter!
> }
> ```

## 4. Principle 4: Clicks and Timers Only Set `status`

### The smallest version: `hidden` and `setStatus`

Compare how plain JavaScript and React answer the same click on `Check`:

```js title="With hidden, in plain JavaScript"
if (box.value === 'Paris') {
  ~rightText.hidden = false;~ // Shows the right line, and leaves the wrong line where it was
} else {
  ~wrongText.hidden = false;~ // Shows the wrong line, and leaves the right line where it was
}
```

```jsx title="With setStatus"
~setStatus(answer === 'Paris' ? 'right' : 'wrong');~ // Names the next screen: its JSX leaves out every other line
```

It looks the same, but it is NOT the same thing! With `hidden`, each branch shows one line and must also hide every line that any other branch showed. With `setStatus`, the branch only names the next screen, and the JSX for that screen already leaves everything else out.

### Human inputs and computer inputs

Something must change `status`, and React.dev sorts those things into two kinds. A *human input* is something the user does: "Human inputs, like clicking a button, typing in a field, navigating a link." A *computer input* happens without the user: "Computer inputs, like a network response arriving, a timeout completing, an image loading." React.dev gives one rule for both: "In both cases, you must set state variables to update the UI."

In the capital quiz, typing in the box and clicking `Check` are human inputs. The timer that ends one second after the click is a computer input. Typing sets `answer`, and clicking and the timer set `status`:

```tree dir=right caption="How each input moves the capital quiz from one status to the next."
The inputs that change `status`
- typing [`'typing'`] | The user clicks **Check** | Moves to **`'checking'`**
- checking [`'checking'`] | The timer ends and `answer` is **Paris** | Moves to **`'right'`**
- checking [`'checking'`] | The timer ends with **another answer** | Moves to **`'wrong'`**
- wrong [`'wrong'`] | The user changes the answer and clicks **Check** | Moves to **`'checking'`** again
```

### The final `handleCheck`

The `if` and the `else` inside the timer now become the one line of the smallest version:

```jsx title="src/components/CapitalQuiz.jsx" startLine="7"
  function handleCheck() {
    ~setStatus('checking');~ // Human input: the click starts the checking screen
    setTimeout(() => {
      ~setStatus(answer === 'Paris' ? 'right' : 'wrong');~ // Computer input: the timer picks the next screen
    }, 1000);
  }
```

The `answer` inside the timer is the one from the render in which the user clicked `Check`, as Lesson 15 showed. The user cannot change it during that second, because the box is dimmed the whole time.

The check is exact. An answer typed as `paris`, with a small letter, is not `'Paris'`, so the quiz calls it wrong.

### Why the wrong line disappears with no line that hides it

The page shows `Not quite. Try again!`. The user changes the answer to `Paris` and clicks `Check`, and the wrong line disappears at once, even though no line in `handleCheck` hides it:

```page width=text caption="The quiz right after the user changes the answer to Paris and clicks Check: the wrong line is gone, and the box and the Check button are dimmed."
heading: Capital quiz
line: What is the capital of France?
form:
  field:  | Paris
  button: Check
line: Checking...
console: quiet
```

React removes the line because the new render has no line in that place:
1. Before the click, `status` is `'wrong'`, so the page shows the wrong line.
2. The click runs `handleCheck`, which sets `status` to `'checking'`.
3. React renders `CapitalQuiz` again. Now `status === 'wrong'` is `false`, so the `&&` on the wrong line gives `false`.
4. React draws nothing for `false`, so the new render has no wrong line, and React removes that `<p>` from the page.
5. One second later, the timer sets `status` to `'right'`, and the early `return` draws only `That's right!`.

React.dev describes the fourth step: "React considers `false` as a "hole" in the JSX tree, just like `null` or `undefined`, and doesn't render anything in its place." The Elements panel shows that the wrong line is gone from the page, not only hidden:

```dom caption="The Elements panel right after the second click on Check: the wrong line is no longer in the DOM."
<h2>Capital quiz</h2>
<p>What is the capital of France?</p>
<input value="Paris" disabled="">
<button disabled="">Check</button>
+ <p>Checking...</p> | note: status is 'checking'
* No <p>Not quite. Try again!</p> | note: status === 'wrong' is false
```

One second later, only the heading is left:

```page width=text caption="The same quiz one second later: only the heading is left."
heading: That's right!
console: quiet
```

### The plain JavaScript fix grows with every new screen

Back in the plain JavaScript quiz, the developer fixes the double answer by hiding the wrong line at the start of every click. Then the quiz needs a `Checking...` line and a dimmed box and button, just like our React version. The HTML page gets a third line that waits out of sight, above the two answer lines:

```html title="index.html" startLine="5"
<p id="checking" ~hidden~>Checking...</p> <!-- A third line that waits out of sight -->
```

The script looks it up next to the others:

```js title="src/quiz.js" startLine="5"
const ~checkingText~ = document.getElementById('checking'); // One more element to show and hide by hand
```

Now the click handler must dim, show, and hide every part by hand, and then undo it when the timer ends:

```js title="src/quiz.js" startLine="7"
button.addEventListener('click', () => {
  box.disabled = true;
  button.disabled = true;
  checkingText.hidden = false;
  ~wrongText.hidden = true;~ // Hides the wrong line left by the last click
  setTimeout(() => {
    ~box.disabled = false;~ // Undoes the first line of the click
    button.disabled = false;
    checkingText.hidden = true;
    if (box.value === 'Paris') {
      rightText.hidden = false;
    } else {
      wrongText.hidden = false;
    }
  }, 1000);
});
```

Every line here undoes a line written somewhere else, and when the developer forgets one of them, a screen that should be gone stays on the page. The React `handleCheck` has two calls to `setStatus` and does not touch a single element. A sixth screen later needs one new branch in the JSX and no change to the other screens. React.dev: "Although this code is longer than the original imperative example, it is much less fragile. Expressing all interactions as state changes lets you later introduce new visual states without breaking existing ones."

### The five steps, and what React does under the hood

React.dev lists the whole method in five steps: identify the visual states, determine what triggers each change, represent the state with `useState`, remove non-essential state, and connect the event handlers. This lecture covered all five. Principle 1 is the first step, Principles 2 and 3 are the third and the fourth, and Principle 4 is the second and the fifth.

One of the React.dev challenges rewrites the plain JavaScript quiz with one function, `updateDOM`, that redraws every part of the page from the current state after each change. React.dev: "The `updateDOM` function you wrote shows what React does under the hood when you set the state." There is one difference: React skips every DOM property that has not changed since the last time it was set. That matches Lesson 13, where React changed only the DOM nodes that differ between two renders.

A second click during checking cannot start a second check, because `disabled={answer.length === 0 || status === 'checking'}` keeps the button off for that whole second. Two more topics touch this one and come later. Returning two separate JSX trees for two screens can reset the state below them, which Lesson 25 explains. React 19 form actions and `useActionState` can track the pending screen for you, which Lessons 41 and 42 teach.

> [!PRINCIPLE]
> **Principle 4: Inputs Set State: Let Every Click and Timer Only Name the Next Screen**
>
> *Every human input and every computer input only sets the next `status`. The JSX already describes every status, so no handler shows, hides, enables, or disables anything.*
>
> With `hidden` in plain JavaScript, each branch must undo what every other branch showed, and forgetting one line leaves `That's right!` and `Not quite. Try again!` on the page together. With `setStatus`, a click or a timer only names the next screen. React renders again, the JSX for the new status leaves every other line out, and React removes the old nodes from the DOM by itself.
>
> **DO THIS:**
> ```jsx
> function handleCheck() {
>   setStatus('checking');
>   setTimeout(() => {
>     ~setStatus(answer === 'Paris' ? 'right' : 'wrong');~ // Names the next screen; the JSX draws it
>   }, 1000);
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> button.addEventListener('click', () => {
>   if (box.value === 'Paris') {
>     ~rightText.hidden = false;~ // **WRONG:** the wrong line from the last click stays on the page!
>   } else {
>     wrongText.hidden = false;
>   }
> });
> ```

And here is the complete quiz. It keeps only the essential state, `answer` and `status`:

```jsx title="src/components/CapitalQuiz.jsx"
import { useState } from 'react';

export default function CapitalQuiz() {
  const [answer, setAnswer] = useState('');
  const [~status~, setStatus] = useState('typing'); // Principle 2: one string names the current screen

  function handleCheck() {
    setStatus('checking');
    setTimeout(() => {
      ~setStatus(answer === 'Paris' ? 'right' : 'wrong');~ // Principle 4: the timer only names the next screen
    }, 1000);
  }

  if (status === 'right') {
    return <h1>That's right!</h1>;
  }

  return (
    <>
      <h2>Capital quiz</h2>
      <p>What is the capital of France?</p>
      <input value={answer} onChange={e => setAnswer(e.target.value)} disabled={status === 'checking'} />
      <button onClick={handleCheck} ~disabled={answer.length === 0 || status === 'checking'}~>Check</button> {/* Principle 3: computed from answer */}
      {~status === 'checking'~ && <p>Checking...</p>} {/* Principle 1: every screen is drawn in the JSX */}
      {status === 'wrong' && <p>Not quite. Try again!</p>}
    </>
  );
}
```

### How React calls the components, and what each input does

When the page opens, React calls `App`, and `App` names `CapitalQuiz`. Each keystroke by the user, each click on `Check`, and the end of each timer makes React call `CapitalQuiz` again with the new state:

```tree caption="How React calls App and CapitalQuiz, and what each input changes in CapitalQuiz."
`App` [`<StrictMode>`] | Mounts inside StrictMode and renders `<CapitalQuiz />`
- +`CapitalQuiz` [`useState`] | Holds `answer` and `status` | Draws the screen that `status` names on every render
  - +Typing in the box [`setAnswer`] | Human input: changes **`answer`** | `answer.length === 0` decides whether **Check** is dimmed
  - +Clicking Check [`setStatus`] | Human input: sets **`'checking'`** and dims the box and the button | Shows **Checking...**
  - +The timer ends [`setStatus`] | Computer input: picks `'right'` or `'wrong'` | Shows **That's right!** or **Not quite. Try again!**
```

### Summary

| Aspect | The Plain JavaScript Habit | The React Rule |
| :--- | :--- | :--- |
| **The screens** | Start from the click and write a branch only for the outcome in mind | List every visual state first and draw each one as JSX chosen by `status` |
| **The state** | Keep one boolean per screen, such as `isChecking` and `isWrong`, which can both be `true` | Keep one `status` string that can only name one screen at a time |
| **The empty box** | Store `isEmpty` and change it by hand in the box handler | Compute `answer.length === 0` during render |
| **The handlers** | Show and hide each line with `hidden` and undo every other branch by hand | Let each click and timer only set the next `status`, and let React update the DOM |

## For the Interview

> **The Interview Question:** How do you design a component that reacts to input with state instead of touching the DOM?

### How to Answer Clearly in 30 Seconds

"Instead of showing and hiding parts of the page by hand, I describe the page for every visual state and let state pick one. I follow five steps. First, I list every screen the user can see, such as typing, checking, wrong, and right, and I can mock each one with a `status` prop. Second, I find what changes the screen: human inputs, such as typing and clicking, and computer inputs, such as a timer or a network response. Third, I store the screen in one `status` string with `useState`, because separate booleans allow impossible mixes, like an error message on a dimmed form. Fourth, I remove state I can compute, such as an empty flag that is just `answer.length === 0`. Fifth, I connect the handlers, and each one only sets the next `status`. The JSX already describes every status, so React updates the DOM, and a new screen adds one branch without breaking the others."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why is one `status` string better than several booleans such as `isChecking` and `isWrong`?"**
   Two booleans allow four mixes, and only three of them are real screens. If a handler sets `isWrong` and forgets to clear `isChecking`, the page shows `Checking...` and `Not quite. Try again!` together, and `disabled={isChecking}` locks the box, so the user can never try again. One `status` can only hold one value, so setting it to `'wrong'` ends the checking screen in the same render. Names such as `isChecking` can still exist as constants computed from `status` during render, because constants cannot fall out of step.
2. **"How do you decide which values belong in state at all?"**
   I ask React's three questions about each variable: does it cause a paradox with another one, is the same information already in another state variable, and can I get it from the inverse of another variable? A stored `isEmpty` fails the second question, because `answer.length === 0` says the same. Storing it anyway risks the button staying on after the user deletes the last letter. What is left after that clean-up is the essential state: in the quiz, `answer` and `status`. Impossible mixes that remain across two variables can be removed with a reducer.
3. **"What does React do when a handler sets the status, if the handler never touches the DOM?"**
   Setting state makes React call the component again. The JSX for the new status describes the whole screen, and React compares the new render with the old one and changes only the DOM nodes that differ. A line written with `&&` gives `false` when its status no longer matches, React draws nothing for `false`, and the old `<p>` is removed from the DOM. It is like an `updateDOM` function that redraws everything from state, except that React skips every node that has not changed.

```tree dir=right caption="Interview comparison: touching the DOM by hand vs. several booleans in state vs. one status string."
Three ways to make the quiz react to input
- !Touch the DOM by hand [`wrongText.hidden = false`] | Every branch must undo every other branch | An old message **stays on the page** when one line is forgotten
- !One boolean per screen [`isChecking` `isWrong`] | Each boolean doubles the mixes | **Impossible states** such as checking and wrong at once
- +One `status` string [`setStatus`] | Each input only names the next screen | React draws that screen and **removes the rest**
```
