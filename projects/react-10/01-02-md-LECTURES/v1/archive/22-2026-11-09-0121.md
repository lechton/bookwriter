> INTERVIEW QUESTION | ❱ CORE | How do you decide which values belong in state and which are derived?

## How We Decide Which Values Go in State

### Remembering a value vs. calculating it again

Think of a shopping list on paper. You write one item per line: bread, milk, eggs. How many items are on the list? You could write the number 3 at the bottom of the page. Or you could count the lines whenever someone asks.

The written number needs fixing every time you add a line or cross one out. You add butter, and you change the 3 to a 4. You cross out milk, and you change the 4 back to a 3. Sooner or later you add a line and forget to change the number, and now the bottom of the page says 3 under a list of 4. Counting the lines never goes wrong, because the count comes from the lines themselves at the moment you need it.

A React component can give the page a value in the same two ways. Both are values the page shows. The one difference is what React keeps between renders:
- **A state value:** React remembers it between renders, and it changes only when our code calls its setter. This is the number written at the bottom of the list.
- **A calculated value:** a `const` in the component body. React keeps nothing of it. Every time React calls the component, the line runs again and makes the value fresh from state. This is counting the lines.

```tree caption="Two ways to give the page a value: React remembers a state value, and a calculated value is made again on every render."
Two ways to give the page a value
- +A state value [`useState`] | React **remembers it** between renders | It changes only when our code **calls its setter**
- +A calculated value [`const`] | React **keeps nothing** of it | It is made again **from state on every render**
```

So here is the key idea of this lesson. State holds only what changes over time and cannot be calculated from anything else. Every other value the page shows is calculated during rendering. React's docs give the goal in one line: make state easy to update without introducing mistakes. Paraphrasing Albert Einstein, they ask us to make our state as simple as it can be, but no simpler.

### What is at stake

What is at stake is a page that shows two answers that disagree. A line says `5 players` above a list of four players. A line says `Captain: Mia` after Mia has left the team. Each time, the page keeps the same fact in two places, once in the list and once in a second state variable, and the user's click updated only one of them. There is no error in the Console. The page is simply wrong.

Readers usually go wrong in one place: they give every value the page shows its own `useState`. Then every event handler must remember to call every setter. The first handler that forgets leaves the page wrong.

### Four ways to keep a value that depends on other values

When a value on the page depends on other values, developers choose among four ways:
1. **Store it in its own state**, and call its setter in every handler that changes what it depends on. It works only while every handler remembers. React's docs, about a packing list that keeps two counters in state, say that you could carefully change each event handler to update the counters correctly, but "the root problem is that these state variables exist at all."
2. **Calculate it during rendering** with a `const` in the component body. This is React's default, and the way this lesson teaches.
3. **Calculate it during rendering, and let `useMemo` keep the result between renders** so the calculation does not run again. This is only for a calculation you have measured as slow. Lesson 56 teaches `useMemo`.
4. **Store it in state and update it from an Effect**, a piece of code that React runs after the page is drawn. React's docs call this "more complicated than necessary" and inefficient too. Lesson 34 shows how to remove such an Effect.

### The five rules on the React docs' page

React's docs page on choosing the state structure gives five rules. This lesson teaches four of them. The second rule was the heart of Lesson 21, where one `status` variable took the place of several true or false variables that could contradict each other.
1. **Group related state**: Principle 5.
2. **Avoid contradictions in state**: Lesson 21.
3. **Avoid redundant state**: Principles 1, 2, and 4.
4. **Avoid duplication in state**: Principle 3.
5. **Avoid deeply nested state**: Principle 6.

### Six Principles of Choosing the State Structure

**PRINCIPLES:** Every value the page shows either lives in state or is calculated from state or props during rendering. Six practical principles follow from that choice:
1. **Principle 1: `players.length` Keeps the Count Right**: A count kept in its own state changes only when a handler calls its setter. A count read from the list during rendering changes whenever the list changes.
2. **Principle 2: `query` Filters the List During Rendering**: Only the full list and the search text are state. The rows that match the search are calculated from those two on every render, so they also follow a click on `Remove`.
3. **Principle 3: `captainId` Finds the Captain in the List**: When the user picks one player, keep the player's id in state, not the player's object, and find the player in the list during rendering.
4. **Principle 4: `useState` Freezes the Captain Line**: The value passed to `useState` is read only on the first render, so a prop copied into state never sees the parent's later values. Use the prop directly.
5. **Principle 5: `position` Holds `x` and `y` Together**: Two values that always change together belong in one object, and every update writes both fields or spreads the old object first.
6. **Principle 6: `childIds` Keeps Nested Places Flat**: Deeply nested data is stored once per item in a flat object keyed by id, where each item lists the ids of its children.

Here is the complete map of those six principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`players.length` Keeps the Count Right** | A count kept in its own state shows `5 players` above four rows after the user clicks `Remove` once, with zero Console errors. | When a value can be calculated from state or props during rendering, write it as a `const` in the component body, not as a state variable. |
| **Principle 2** | **`query` Filters the List During Rendering** | A filtered list kept in state works while the user types, then keeps a removed player on the page. Interviewers ask which values should never have been state. | Keep the full list and the search text in state, and calculate the filtered list from both during rendering. |
| **Principle 3** | **`captainId` Finds the Captain in the List** | A chosen object kept in state still says `Captain: Mia` after Mia is removed from the list. | Keep the id of the chosen item in state, and find the item in the list during rendering. |
| **Principle 4** | **`useState` Freezes the Captain Line** | A prop copied with `useState` keeps showing the first captain after the parent passes a new one. | Use a prop directly. Copy it into state only when later values must be ignored, and then start the prop's name with `initial` or `default`. |
| **Principle 5** | **`position` Holds `x` and `y` Together** | Merging two values into one object and then setting only one field leaves the other field `undefined`. | When two state variables always change together, merge them into one object, and set every field or spread the old object first. |
| **Principle 6** | **`childIds` Keeps Nested Places Flat** | Removing an item deep in a nested object needs a new copy of every level above it. | Store each item once in a flat object keyed by id, and give each item an array of its child ids. |

## 1. Principle 1: `players.length` Keeps the Count Right

### A count in its own state vs. a count read from the list

Here are two ways to show how many names a list holds. Both lists start with three names, and both paragraphs show the same count:

```jsx title="With count in its own state"
const [names, setNames] = useState(['John', 'Mia', 'Sara']);
const [count, setCount] = ~useState(3)~; // A second state variable that holds 3

<p>{count} names</p> {/* Shows 3 names */}
```

```jsx title="With count read from names.length"
const [names, setNames] = useState(['John', 'Mia', 'Sara']);
const count = ~names.length~; // Read from the list every time React calls the component

<p>{count} names</p> {/* Shows 3 names */}
```

Both show `3 names` when the page opens. **It may look the same, or work the same at first, but it is NOT the same thing!** The two part ways as soon as a handler changes `names`:
- **With `count` in its own state**, `count` changes only when some handler calls `setCount`. A handler that removes a name and forgets `setCount` leaves the page saying `3 names` above two names.
- **With `names.length`**, there is nothing to forget. React calls the component again after every change to `names`, the `const` line runs again, and it reads the length of the new list.

This is the shopping list again. A `count` in its own state is the number written at the bottom of the page. `names.length` is counting the lines.

React's docs have a name for a state variable like the first `count`: **redundant state**. In everyday English, something is redundant when it is more than you need, like a second copy of the same note. The count is already inside the list, so keeping it a second time in its own state is more than we need. The docs' name for the second way is to **calculate during rendering**: a `const` in the component body, run again every time React calls the component.

```tree caption="A count kept in its own state vs. a count calculated from the list during rendering."
Two ways to show how many names the list holds
- !With `count` in its own state [`useState`] | **Redundant state**: the count is kept a **second time** | It changes only when a handler **calls `setCount`**
- +With `names.length` [`const count`] | **Calculated during rendering** from the list | It follows **every change** to `names`
```

### The team page with the count in its own state

Now we start our team page. The team list file holds the five players in state, shows a heading and a count line, and gives each player a row with a `Remove` button. The count gets its own state variable:

```jsx title="src/components/TeamList.jsx" bad="13"
import { useState } from 'react';

const initialPlayers = [
  { id: 0, name: 'John' },
  { id: 1, name: 'Mia' },
  { id: 2, name: 'Sara' },
  { id: 3, name: 'Leo' },
  { id: 4, name: 'Anna' },
];

export default function TeamList() {
  const [players, setPlayers] = useState(initialPlayers);
  const [count, setCount] = ~useState(initialPlayers.length)~; // **WRONG:** the number of players is kept a second time

  function handleRemove(id) {
    ~setPlayers(players.filter(player => player.id !== id))~; // Changes players and never calls setCount
  }

  return (
    <section>
      <h1>Team</h1>
      <p>{count} players</p>
      <ul>
        {players.map(player => (
          <li key={player.id}>
            {player.name}
            <button onClick={() => handleRemove(player.id)}>Remove</button>
          </li>
        ))}
      </ul>
    </section>
  );
}
```

Our main file only renders the team list:

```jsx title="src/App.jsx"
import ~TeamList~ from './components/TeamList.jsx'; // The default export of the team list file

export default function App() {
  return <TeamList />;
}
```

When the page opens, the count line and the list agree:

```page width=text caption="The team page when it opens, with count kept in its own state."

line: Mia [Remove]
line: Sara [Remove]
line: Leo [Remove]
line: Anna [Remove]

```

Now the user clicks `Remove` on John. John's row disappears, and the line still says `5 players`:

```page width=text caption="The same page after the user clicks Remove on John: four rows under a line that still says 5 players."
heading: Team
line: 5 players | bad
line: Mia [Remove]
line: Sara [Remove]
line: Leo [Remove]
line: Anna [Remove]
console: quiet
```

The line is wrong because `handleRemove` changes `players` and never asks React to change `count`. The Console stays quiet, because both state variables hold ordinary values and React sees nothing wrong. Here is what React does after the user's click:
1. `setPlayers` receives a new array of four players and asks React to render `TeamList` again.
2. Nothing called `setCount`, so on this render `useState` gives back the old `count`, which is `5`.
3. The list draws four rows from `players`, and the line shows `5 players` from `count`.

React's docs call this being **out of sync**: two values on the page that should agree, and do not. We could make `handleRemove` also call `setCount` with one less than `count`. But then every future handler that adds or removes a player must remember it too. The real fix is to have no second copy at all.

### The fix: reading the count from `players.length`

We delete the state line for `count`, and a `const` takes its place:

```jsx title="src/components/TeamList.jsx" startLine="11" good="13"
export default function TeamList() {
  const [players, setPlayers] = useState(initialPlayers);
  const count = ~players.length~; // Read from players every time React calls TeamList
```

The JSX still writes `{count} players`, even though `count` no longer comes from `useState`. Every time React calls `TeamList`, `useState` hands back the current `players`, and the `const` line reads its length before the JSX runs. After the same click by the user on `Remove`, the line follows the list:

```page width=text caption="The fixed page after the user clicks Remove on John: the line says 4 players above four rows."
heading: Team
line: 4 players | good
line: Mia [Remove]
line: Sara [Remove]
line: Leo [Remove]
line: Anna [Remove]
console: quiet
```

React's docs tell the same story with a packing list. The list keeps its items in state, plus a `total` counter and a `packed` counter as two more state variables. Each handler fixes the counters by hand. The delete handler lowers `total` and forgets `packed`. So when the user packs an item and then deletes it, the footer still counts a packed item that is no longer on the list. The docs' fix is the same as ours: remove both counters from state, and calculate them from the items.

> [!PRINCIPLE]
> **Principle 1: Redundant State: Calculate a Count from the List During Rendering**
>
> *When a value can be calculated from state or props during rendering, write it as a `const` in the component body, not as a state variable.*
>
> A count kept in its own state is redundant state: it holds again what the list already holds. It changes only when a handler remembers to call its setter, so one forgotten setter leaves the page out of sync. A `const` that reads the list runs again on every render, so it always matches the list.
>
> **DO THIS:**
> ```jsx
> const [players, setPlayers] = useState(initialPlayers);
> const count = ~players.length~; // Follows every change to players
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [players, setPlayers] = useState(initialPlayers);
> const [count, setCount] = ~useState(initialPlayers.length)~; // **WRONG:** changes only when a handler remembers setCount
> ```

## 2. Principle 2: `query` Filters the List During Rendering

### Three questions that sort every value

A search box seems to change the list the user sees, so the list of matching rows looks like state. It is not. Here is the smallest code for a list with a search:

```jsx title="Two state variables and one calculated list"
const [names, setNames] = useState(['John', 'Mia', 'Sara']);
const [query, setQuery] = useState('');
const visibleNames = ~names.filter(name => name.includes(query))~; // With query 'a': Mia and Sara
```

Only `names` and `query` are state. `visibleNames` is calculated from both on every render.

React's docs, in the page Thinking in React, give a test for which values belong in state. They describe state as the **minimal set of changing data** the page needs: the fewest values, and only the ones that change. Then they give three questions to ask of each value:
1. Does it stay the same over time? Then it is not state.
2. Is it passed in from a parent through props? Then it is not state.
3. Can it be computed from existing state or props? Then it is definitely not state.

Now ask the three questions of the four values that the finished team page, shown at the start of this lecture, puts on the screen:

```tree caption="The four values of the finished team page sorted by the three questions of Thinking in React."
Which values of the team page are state?
- +The players | Change when the **user clicks Remove** | Cannot be computed from anything else | **State**
- +The search text | Changes as the **user types** | Cannot be computed from anything else | **State**
- The rows that match the search | Computed from **the players and the search text** | **Not state**
- The count line | Computed from **the matching rows and the players** | **Not state**
```

Only the players and the search text are left. React's docs call such values **essential state**: "you can't remove any of them without breaking the functionality." Remove the players, and the page has no team. Remove the search text, and the box forgets what the user typed.

The interview question uses one more word for the other two values: **derived**. In everyday English, one thing derives from another when it comes out of it, the way a river comes out of its spring. A derived value comes out of state or props. A page of React's reference writes "Derive during render". So "a derived value" and "a value calculated during rendering" are **the exact same thing**.

### The team page with the filtered list in its own state

Readers usually go wrong here by filtering inside `onChange`, because typing is the moment the list seems to change. So we add a search box with the hint `placeholder="Search players"`, and we keep the filtered list in its own state, set by the search handler:

```jsx title="src/components/TeamList.jsx" startLine="11" bad="14"
export default function TeamList() {
  const [players, setPlayers] = useState(initialPlayers);
  const [query, setQuery] = useState('');
  const [filteredPlayers, setFilteredPlayers] = ~useState(initialPlayers)~; // **WRONG:** the matching rows are kept a second time

  function handleRemove(id) {
    setPlayers(players.filter(player => player.id !== id)); // Changes players and never touches filteredPlayers
  }

  function handleSearch(e) {
    setQuery(e.target.value);
    ~setFilteredPlayers(players.filter(player => player.name.includes(e.target.value)))~; // Filters only when the user types
  }

  return (
    <section>
      <h1>Team</h1>
      <input value={query} onChange={handleSearch} placeholder="Search players" />
      <p>Showing {filteredPlayers.length} of {players.length} players</p>
      <ul>
        {~filteredPlayers~.map(player => ( // The rows come from the second copy
          <li key={player.id}>
            {player.name}
            <button onClick={() => handleRemove(player.id)}>Remove</button>
          </li>
        ))}
      </ul>
    </section>
  );
}
```

The new count line reads two lengths, so the `count` of Principle 1 is no longer needed.

While the user types, this version looks right. After the user types `a`, the list shows Mia, Sara, and Anna. Anna matches through the small a at the end of her name, because `includes` tells a capital A from a small a:

```page width=text caption="The page with filteredPlayers in state after the user types a into the search box."
heading: Team
form:
  field: | a
line: Showing 3 of 5 players
line: Mia [Remove]
line: Sara [Remove]
line: Anna [Remove]
console: quiet
```

Now start again from a fresh page, with the box empty, and let the user click `Remove` on John. John stays on the list, and the line says `Showing 5 of 4 players`:

```page width=text caption="The page with filteredPlayers in state after the user clicks Remove on John: John stays, and the line says 5 of 4."
heading: Team
form:
  field: | Search players
line: Showing 5 of 4 players | bad
line: John [Remove] | bad
line: Mia [Remove]
line: Sara [Remove]
line: Leo [Remove]
line: Anna [Remove]
console: quiet
```

John stays because the rows come from `filteredPlayers`, and only typing in the search box changes it. Here is what happens, in order:
1. On the first render, `filteredPlayers` starts as `initialPlayers`, all five players.
2. The user clicks `Remove` on John. `handleRemove` calls `setPlayers` with four players and does not touch `filteredPlayers`.
3. React renders `TeamList` again. `players` holds four players, and `filteredPlayers` still holds five.
4. The rows are drawn from `filteredPlayers`, so John's row stays.
5. The line reads `filteredPlayers.length` and `players.length`, so it says `Showing 5 of 4 players`.

The filtered list in state misses every change that does not come through the search box.

### The fix: calculating `visiblePlayers` from `players` and `query`

We delete the state for the filtered list, and a `const` named `visiblePlayers` takes its place. The search box becomes the plain controlled box of Lesson 20:

```jsx title="src/components/TeamList.jsx" startLine="11" good="14"
export default function TeamList() {
  const [players, setPlayers] = useState(initialPlayers);
  const [query, setQuery] = useState('');
  const visiblePlayers = ~players.filter(player => player.name.includes(query))~; // Made again from players and query on every render

  function handleRemove(id) {
    setPlayers(players.filter(player => player.id !== id));
  }

  return (
    <section>
      <h1>Team</h1>
      <input value={query} ~onChange={e => setQuery(e.target.value)}~ placeholder="Search players" /> {/* Typing changes only query */}
      <p>Showing {visiblePlayers.length} of {players.length} players</p>
      <ul>
        {~visiblePlayers~.map(player => ( // The rows come from the calculated list
          <li key={player.id}>
            {player.name}
            <button onClick={() => handleRemove(player.id)}>Remove</button>
          </li>
        ))}
      </ul>
    </section>
  );
}
```

Now typing and removing both change the rows. The user types `a`, then clicks `Remove` on Mia:

```page width=text caption="The fixed page after the user types a and then clicks Remove on Mia."
heading: Team
form:
  field: | a
line: Showing 2 of 4 players | good
line: Sara [Remove]
line: Anna [Remove]
console: quiet
```

The same mistake shows up on a search page for articles. A developer stores the article list, the filter text, the filtered articles, and a result count as four state variables. The search box sets the filter text and the filtered articles. Later a new article arrives through a different handler, which updates only the article list. The counter says 0 results while five articles are on the page. Only the article list and the filter text should ever have been state.

> [!PRINCIPLE]
> **Principle 2: Minimal State: Calculate the Filtered List from the Full List and the Search Text**
>
> *Keep the full list and the search text in state, and calculate the filtered list from both during rendering; never keep the filtered list as its own state.*
>
> State is the minimal set of changing data. The full list changes when the user removes a player, and the search text changes when the user types, so both are state. The filtered list can be computed from those two, so it is not state. Kept in state, it follows only the search box and misses every other change to the list.
>
> **DO THIS:**
> ```jsx
> const [players, setPlayers] = useState(initialPlayers);
> const [query, setQuery] = useState('');
> const visiblePlayers = ~players.filter(player => player.name.includes(query))~; // Follows both typing and Remove
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [query, setQuery] = useState('');
> const [filteredPlayers, setFilteredPlayers] = ~useState(initialPlayers)~; // **WRONG:** misses every change that does not come through the search box
> ```

## 3. Principle 3: `captainId` Finds the Captain in the List

### The chosen object vs. the chosen id

When the user picks one item from a list, we must remember which one. Here are two ways to remember that the user chose Mia:

```jsx title="With the chosen object in state"
const names = [{ id: 0, name: 'John' }, { id: 1, name: 'Mia' }];
const [chosen, setChosen] = ~useState(names[1])~; // Mia's object, kept in a second place apart from the list

<p>{chosen.name}</p> {/* Shows Mia */}
```

```jsx title="With the chosen id in state"
const names = [{ id: 0, name: 'John' }, { id: 1, name: 'Mia' }];
const [chosenId, setChosenId] = ~useState(1)~; // Only Mia's id
const chosen = ~names.find(item => item.id === chosenId)~; // Looks Mia up in the list on every render

<p>{chosen.name}</p> {/* Shows Mia */}
```

The second way uses a new helper, `find`. It is a JavaScript array method. It calls the function we give it once for each item, in order, and returns the first item for which the function returns `true`. When no item matches, it returns `undefined`.

Both paragraphs print `Mia`. **It may look the same, or work the same at first, but it is NOT the same thing!** With the chosen object in state, Mia is now kept in two places: once in the list, and once in `chosen`. With the chosen id in state, Mia is kept only in the list, and `chosenId` only says which item to look up. React's docs call the first way **duplication in state**: the same information kept in two places.

Think of a bookmark and a photocopy of a page. A bookmark points to a page in the book, so if the page is corrected or torn out, you see that at once when you open the book. A photocopy keeps the old page forever, whatever happens to the book. `chosenId` is the bookmark, and `chosen` in state is the photocopy.

```tree caption="Keeping the chosen object in state vs. keeping only its id and finding the item during rendering."
Two ways to remember that the user chose Mia
- !With the chosen object in state [`chosen`] | **Duplication in state**: Mia is kept **in two places** | Changes to the list **never reach** `chosen`
- +With the chosen id in state [`chosenId`] | Mia is kept **only in the list** | `find` looks her up **on every render**
```

### The team page with the captain object in state

Our team page now gets a captain. Each row gets a `Make captain` button, and a line below the list names the captain. First, we keep the chosen player's object in state, starting as `null` before the user picks anyone:

```jsx title="src/components/TeamList.jsx" startLine="11" bad="15"
export default function TeamList() {
  const [players, setPlayers] = useState(initialPlayers);
  const [query, setQuery] = useState('');
  const visiblePlayers = players.filter(player => player.name.includes(query));
```

## 4. Principle 4: `useState` Freezes the Captain Line

### A prop copied into state vs. a prop used directly

A component often shows a prop that its parent passes. Here are two ways for a small greeting to show the `name` it receives:

```jsx title="With name copied into useState"
function Hello({ name }) {
  const [shownName] = ~useState(name)~; // name is read only on the first render
  return <p>Hello, {shownName}</p>;
}
```

```jsx title="With name used directly"
function Hello({ name }) {
  return <p>Hello, ~{name}~</p>; // name is read on every render
}
```

The parent passes John first, and later passes Mia on the same tag:

```jsx title="The parent passes John, and later Mia"
<Hello ~name="John"~ /> {/* On the first render */}
<Hello ~name="Mia"~ /> {/* On a later render, in the same place */}
```

Both show `Hello, John` at first. **It may look the same, or work the same at first, but it is NOT the same thing!** When the parent passes `Mia`, only the version with `name` used directly shows `Hello, Mia`. The version that copies `name` into `useState` keeps showing `Hello, John`. Why? Well, Lesson 12 taught that the value passed to `useState` is used only on the first render. On every later render, `useState` ignores it and gives back what it already holds.

React's docs call this **mirroring props in state**: putting a prop into a state variable with `useState`. The name suggests that the state follows the prop the way a mirror follows your face. It does not. `useState` looks at the prop only once, on the first render, and keeps that first face however much you move.

```tree caption="Copying a prop into state vs. using the prop directly, after the parent passes a new name."
Two ways to show the `name` that the parent passes
- !With `useState` around the prop [`shownName`] | **Mirroring props in state** | Keeps **the first name** after the parent passes a new one
- +With `name` used directly [`{name}`] | Reads the prop **on every render** | Shows **the name of this render**
```

### When a copy of the prop is wanted: `initial` or `default` in its name

Sometimes a component really should take the parent's value once and then ignore it. React's docs give one case: mirroring a prop "only makes sense when you *want* to ignore all updates for a specific prop." Then the docs start the prop's name with `initial` or `default`:

```jsx title="With name and with initialName passed to useState"
const [shownName] = ~useState(name)~; // Keeps the first name, and the prop's name hides that
const [shownName] = ~useState(initialName)~; // Keeps the first name, and the prop's name says so
```

**For React, yes, it is the exact same thing!** Both keep the first value and ignore every later one. The one difference is the prop's name. `initialName` tells the next developer who reads the tag that later values are ignored on purpose, so nobody expects the line to follow the parent.

React's docs show the mistake with a clock. A `Clock` component receives a `color` prop and copies it into state. The parent shows a select box, the user picks a new color, and the parent passes the new `color`. The clock keeps its first color. The docs' fix is to remove the state variable and use the prop directly.

> [!PRINCIPLE]
> **Principle 4: Mirroring Props: Use a Prop Directly Instead of Copying It into State**
>
> *Use a prop directly, or in a `const`; copy a prop into state only when the component should ignore every later value, and then start the prop's name with `initial` or `default`.*
>
> The value passed to `useState` is read only on the first render. A prop copied into state shows the first value forever, even after the parent passes a new one, as long as the component stays in the same place. Reading the prop directly shows the value of every render.
>
> **DO THIS:**
> ```jsx
> function CaptainLine({ name }) {
>   return <p>Captain: ~{name}~</p>; // Shows the name of this render
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function CaptainLine({ name }) {
>   const [shownName] = ~useState(name)~; // **WRONG:** keeps the first captain after the parent passes a new one
>   return <p>Captain: {shownName}</p>;
> }
> ```

## 5. Principle 5: `position` Holds `x` and `y` Together

### Two state variables vs. one object

The first four principles removed values from state. This one changes how the values that stay in state are grouped. Our team page has no values that always change together, so this principle and the next use their own small code, and the team page stays as it is.

Think of a red dot that follows the pointer across the page, as in an example from React's docs. The dot needs two numbers: how far across the page, `x`, and how far down, `y`. Each time the user moves the pointer, the browser runs our handler with an event object, and the event gives the two numbers as `e.clientX` and `e.clientY`. Here are two ways to keep them:

```jsx title="With x and y in two state variables"
const [x, setX] = useState(0);
const [y, setY] = useState(0);

function handleMove(e) {
  ~setX(e.clientX)~; // The first of two setters that must always run together
  ~setY(e.clientY)~; // The second one
}
```

```jsx title="With x and y grouped in one position object"
const [position, setPosition] = ~useState({ x: 0, y: 0 })~; // One state variable for one place on the page

function handleMove(e) {
  ~setPosition({ x: e.clientX, y: e.clientY })~; // One setter moves both together
}
```

Both move the dot. React's docs say so plainly: "Technically, you can use either of these approaches." But `x` and `y` always change together, in the same handler, because together they name one place. A cinema ticket works the same way: it names a row and a seat, and you never choose one without the other. React's docs call this rule **group related state**: when two state variables always change together, merge them into one.

### Changing one field of the grouped object

Once `x` and `y` live in one object, a handler may want to change only `x`. There are two ways to write it:

```jsx title="With { x: 100 } and with { ...position, x: 100 }"
setPosition(~{ x: 100 }~); // **WRONG:** the new object has no y, so position.y is undefined
setPosition(~{ ...position, x: 100 }~); // Copies y from the old object, then sets x to 100
```

**They look alike, but they are NOT the same thing!** A setter replaces the whole object, as Lesson 17 taught. The first object has no `y` at all, so after this call `position.y` is `undefined`. React's docs warn about exactly this: "it would not have the `y` property at all!" The second object spreads the old one first, so `y` is kept, and `x` comes last and wins.

```tree caption="Two state variables vs. one grouped object, and the two ways to change only x."
Keeping and changing the dot's place
- Two state variables [`x` `y`] | Two setters that **must always run together** | Works, but one handler can **call one and forget the other**
- +One object [`position`] | **Group related state**: one setter for one place | Every update writes **both fields**
- !Only `x` written in the new object | The new object has **no `y`** | `position.y` becomes **`undefined`**
- +The old object spread first | `y` is **copied**, then `x` is set | Both fields are **kept**
```

> [!PRINCIPLE]
> **Principle 5: Group Related State: Merge Values That Always Change Together**
>
> *When two state variables always change together, merge them into one object; when you set that object, write every field, or spread the old object first.*
>
> Two values that always change in the same handler describe one thing, such as one place on the page. Kept apart, they need two setters that must always run together. Kept together, one setter changes both. Because a setter replaces the whole object, an update that writes only one field leaves the other one `undefined`.
>
> **DO THIS:**
> ```jsx
> const [position, setPosition] = useState({ x: 0, y: 0 });
> setPosition(~{ ...position, x: 100 }~); // y is kept
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [position, setPosition] = useState({ x: 0, y: 0 });
> setPosition(~{ x: 100 }~); // **WRONG:** the new object has no y, so position.y is undefined
> ```

## 6. Principle 6: `childIds` Keeps Nested Places Flat

### Places nested inside places vs. places stored flat

Some data comes as a tree: places inside places. A travel plan holds Earth, Earth holds Africa, and Africa holds Kenya. The natural way to write it is to nest each place inside its parent:

```js title="With places nested inside childPlaces"
const plan = {
  id: 0,
  title: 'Earth',
  ~childPlaces~: [ // Africa sits inside Earth
    {
      id: 1,
      title: 'Africa',
      ~childPlaces~: [{ id: 2, title: 'Kenya', childPlaces: [] }], // Kenya sits inside Africa
    },
  ],
};
```

React's docs show a second way. Every place is stored once, side by side, under its own id. Instead of holding its children, each place holds a short list of their ids, named `childIds`:

```js title="With places stored flat, by id, in childIds"
const plan = {
  0: { id: 0, title: 'Earth', ~childIds: [1]~ }, // Earth points to Africa by its id
  1: { id: 1, title: 'Africa', ~childIds: [2]~ }, // Africa points to Kenya by its id
  2: { id: 2, title: 'Kenya', childIds: [] },
};
```

For the information, **yes, it is the exact same thing!** Both objects hold the same three places in the same order: Earth, then Africa inside it, then Kenya inside Africa. Only the shape differs. React's docs say this shape "might remind you of seeing a database table": one row per place, and each row points to other rows by id. They call the outer object the "table" object. They call this shape **flat**, also known as **normalized**: every place sits on one level, the way papers lie side by side in one drawer instead of in folders inside folders.

### Removing Kenya from each shape

The work of a change is **NOT the same thing**. Suppose the user removes Kenya, and the plan lives in a state variable named `plan`, with its setter `setPlan`.

In the nested plan, Lesson 17's rule applies: a change deep inside an object needs a new copy of every object on the path to it. Removing Kenya needs a new Africa without Kenya, and then a new Earth that holds the new Africa. That is one copy for each level above Kenya. React's docs: "Deleting a deeply nested place would involve copying its entire parent place chain. Such code can be very verbose."

In the flat plan, the change always takes two steps, however deep Kenya sits:

```js title="Removing Kenya from the flat plan"
const parentId = 1;
const parent = plan[parentId];
const nextParent = { ...parent, ~childIds: parent.childIds.filter(id => id !== 2)~ }; // 1. A new Africa without Kenya's id
setPlan(~{ ...plan, [parentId]: nextParent }~); // 2. A new table object with the new Africa under its own id
```

Inside the new table object, `[parentId]` is a computed property name from Lesson 17: it writes the new Africa under the key `1`, in place of the old one. Kenya's own entry is still in the table, but no place lists its id any more, so the plan no longer reaches it. React's docs also show how to delete such entries from the table to save memory.

```tree caption="The same three places stored nested and stored flat, and the work of removing Kenya from each."
The same travel plan in two shapes
- !Nested in `childPlaces` | Each place **holds its children** | Removing Kenya needs **a new copy of every level** above it
- +Flat by id with `childIds` | Each place is stored **once**, under its id | Removing Kenya changes **two levels**: the parent and the table object
```

> [!PRINCIPLE]
> **Principle 6: Avoid Deeply Nested State: Store Each Item Once, by Id**
>
> *When state is nested so deeply that one change needs copies at every level, store each item once in a flat object keyed by id, and give each item an array of its child ids.*
>
> A nested object holds every child inside its parent, so a change deep inside needs a new copy of every parent above it. A flat object holds every item side by side under its id, and each item lists its children by id. Any change then needs only two new objects: the changed item and the table object.
>
> **DO THIS:**
> ```js
> const plan = {
>   1: { id: 1, title: 'Africa', ~childIds: [2]~ }, // Points to Kenya by its id
>   2: { id: 2, title: 'Kenya', childIds: [] },
> };
> ```
>
> **DO NOT DO THIS:**
> ```js
> const plan = {
>   id: 1,
>   title: 'Africa',
>   ~childPlaces~: [{ id: 2, title: 'Kenya', childPlaces: [] }], // **WRONG:** every level down means one more copy for each change
> };
> ```

## For the Interview

> **The Interview Question:** How do you decide which values belong in state and which are derived?

### How to Answer Clearly in 30 Seconds

"State is the minimal set of changing data a component needs to remember. Everything else is derived, which means calculated during rendering with a plain `const`. I test each value with three questions from React's docs: if it stays the same over time, if it comes from a parent through props, or if it can be computed from existing state or props, it is not state. So for a search with a filtered list and a result count, only the full list and the search text are state. The filtered list and the count are calculated from them on every render, so they can never disagree with the list. I also follow the other structure rules from the docs:
1. **Avoid duplication**: keep the id of a chosen item, not a copy of its object, and find the item during rendering.
2. **Do not mirror props**: `useState` reads a prop passed to it only on the first render. When I really want to ignore later values, I name the prop `initialColor` or `defaultColor`.
3. **Group, avoid contradictions, and flatten**: merge values that always change together, use one `status` instead of booleans that contradict each other, and store deeply nested data flat, by id."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Is it not slow to recalculate the filtered list on every render?"**
   **Usually not.** React's docs say that unless you are creating or looping over thousands of objects, a calculation is probably not expensive, and they suggest measuring it with `console.time`. When a measured calculation really is slow, `useMemo` keeps its result between renders and runs it again only when its inputs change, as Lesson 56 shows. Even then, `useMemo` does not make the first render faster, and the value still stays out of state. The React Compiler, a build tool taught in Lesson 63, can add this for us automatically.
2. **"Why not keep the count in state and update it from an Effect whenever the list changes?"**
   Because it is more work for a worse result. React first renders the page with the old count, then runs the Effect, which sets the new count and makes React render the whole component again. For one render, the page shows a stale value. React's docs call this "more complicated than necessary" and inefficient. A `const` gives the right value in the same render. Lesson 34 shows how to remove such Effects.
3. **"When the user can select several items, what goes in state?"**
   An array of ids, such as `[0, 2]`, or a `Set` of ids, JavaScript's built-in collection that holds each value only once. The number of selected items is `selectedIds.length` or `selectedIds.size`, calculated, never stored. The same rule as for one captain applies: state says which items, and the list holds the items. A `Set` in state is treated like any object: you make a new one instead of changing it, as Lesson 17 taught for objects.

```tree dir=right caption="Interview summary: how to decide whether a value belongs in state."
Deciding whether a value belongs in state
- Does it stay the same over time? | **Not state**: a constant outside the component, such as `initialPlayers`
- Does it come from a parent through props? | **Not state**: use the prop directly, such as `name`
- Can it be computed from state or props? | **Not state**: a `const` during rendering, such as `visiblePlayers`
- +None of the three? | **State**: such as `players`, `query`, and `captainId`
```
