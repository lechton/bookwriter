## How a Chat Stays Connected While the User Mutes It

### Picking a room vs. muting the room

Open a chat app with rooms, such as Slack. A menu at the top lets you pick the room you want to read, and the heading welcomes you to the general room. Next to the menu sits a tick box that reads Mute notifications. While the box is not ticked, every new message in the room shows a notification. When you tick it, the notifications stop.

On this screen, the user does two everyday things and expects two different results:
1. **The user picks `travel` in the menu.** The app leaves the general room and connects to the travel room.
2. **The user ticks the Mute notifications box.** The notifications stop, and nothing else changes. The user is still in the travel room, and the chat stays connected.

This screen raises one question for the developer. The chat connection lives in an Effect that connects to the current room (as seen in Lesson 35). The messages arrive through that connection, so the code that shows a notification runs inside the same Effect. That code reads `muted`, the value of the box. How can the Effect read `muted` without disconnecting and connecting again every time the user ticks the box?

React's answer is a Hook called `useEffectEvent`. We move the one check that reads `muted` out of the Effect and into a function that React's docs call an **Effect Event**. The Effect keeps the connection to the room. The Effect Event reads `muted` at the moment a message arrives, so a change of `muted` never touches the connection. As React's docs put it: "You can think of Effect Events as being very similar to event handlers. The main difference is that event handlers run in response to user interactions, whereas Effect Events are triggered by you from Effects."

**It may look the same, or work the same at first, but it is NOT the same thing!** The room and the Mute setting both reach the chat component as props, `roomId` and `muted`, and the Effect reads both:
1. **To the linter, they are the same thing.** Both are reactive values, so both must go in the dependency array (as seen in Lesson 35).
2. **To the user, they are not.** React's docs say it plainly: "From the user's perspective, a change to the `roomId` does mean that they want to connect to a different room." Ticking the box means something else: the user wants silence, not a new connection.

So one Effect holds two kinds of logic. The connection must follow `roomId`. The decision to show a notification must read `muted` when a message arrives, and must not follow its changes.

```tree caption="One Effect reads two props: roomId must re-synchronize the chat, and muted must only be read when a message arrives."
Two props the chat Effect reads
- +`roomId` [`[roomId]`] | Picking a new room **means a new connection** | The Effect **disconnects and connects again** when it changes
- +`muted` [`useEffectEvent`] | Ticking the box **means silence, not a new room** | Read **only when a message arrives**; the connection stays as it is
```

### What is at stake

What is at stake is a chat that keeps its connection and still obeys the user's Mute setting. The two common fixes each break one of those two things:
1. **With `muted` in the dependency array**, every tick of the box disconnects the chat and connects it again. React's docs describe this exact case, with a prop they call `isMuted`: "every time `isMuted` changes ... the Effect will re-synchronize, and reconnect to the chat. This is not the desired user experience!"
2. **With `muted` left out and the linter suppressed**, the chat stays connected, but the box stops working. In the words of the docs, `isMuted` would get "stuck" with its old value.

In both cases, the app does not do what the user asked. The first drops the connection when the user only wanted silence. The second keeps showing notifications after the user muted the room.

Readers usually go wrong in three places:
1. They silence the linter to stop the reconnect. The React blog notes that "most users just disable the lint rule and exclude the dependency."
2. They wrap too much in `useEffectEvent`, including the connection itself, only to make the dependency array shorter.
3. They call the Effect Event from a click handler, or pass it to a child, as if it were an ordinary function.

### Four ways to handle a value that an Effect reads

There are four ways to handle a value that an Effect reads (as seen in Lesson 35), and this lesson teaches the second one. Here they are for the values of our chat:
1. **Keep it in the dependency array** when a change of the value means the Effect must re-synchronize, such as `roomId`.
2. **Read it in an Effect Event** when the value is only needed at the moment something happens, such as `muted` when a message arrives.
3. **Change the code so the value is no longer a dependency**, for example by moving it outside the component (covered in Lesson 37).
4. **Suppress the linter.** React's docs say: "We recommend never suppressing the linter." Principle 3 shows what goes wrong.

2. **The user picks `travel`.** The heading changes. The app disconnects from the general room and connects to the travel room.

The chat helper is the message version of `createConnection` from React's docs. It keeps `connect` and `disconnect` (as seen in Lesson 35) and adds two things. The `connect` method now starts a timer that delivers a message every three seconds. And a new method, `on`, lets our code hand the connection a function to call with each message:

```js title="src/chat.js"
export function createConnection(serverUrl, roomId) {
  let intervalId;
  let messageCallback;
  return {
    connect() {
      console.log('✅ Connecting to "' + roomId + '" room at ' + serverUrl + '...');
      clearInterval(intervalId);
      intervalId = ~setInterval~(() => { // Every 3 seconds, a message arrives
        if (messageCallback) {
          if (Math.random() > 0.5) {
            messageCallback('hey');
          } else {
            messageCallback('lol');
          }
        }
      }, 3000);
    },
    disconnect() {
      ~clearInterval(intervalId)~; // Stops the messages of this connection
      messageCallback = null;
      console.log('❌ Disconnected from "' + roomId + '" room at ' + serverUrl);
    },
    ~on~(event, callback) { // Keeps the function to call with each message
      if (messageCallback) {
        throw Error('Cannot add the handler twice.');
      }
      if (event !== 'message') {
        throw Error('Only "message" event is supported.');
      }
      messageCallback = callback;
    },
  };
}
```

React's docs show each notification as a small pop-up message from a separate package. Our stand-in prints it to the Console instead, so we can count the notifications:

```js title="src/notifications.js"
export function ~showNotification~(message) { // Prints one notification line in the Console
  console.log('🔔 ' + message);
}
```

### Five Principles of Separating Events from Effects

**PRINCIPLES:** One Effect can hold two kinds of logic: logic that must follow a value, and logic that only reads a value when something happens. Adding the Mute box to our chat gives us five practical rules:
1. **Principle 1: Reading `muted` Inside the Effect Reconnects the Chat**: Every reactive value an Effect reads goes in its dependency array. So when the notification check reads `muted` inside the Effect, every tick of the box disconnects the chat and connects it again.
2. **Principle 2: `onMessage` Reads `muted` Without Reconnecting**: `useEffectEvent` moves the notification check into an Effect Event named `onMessage`. The Effect calls it for each message, it reads the latest `muted`, and neither `muted` nor `onMessage` goes in the array.
3. **Principle 3: Suppressing the Linter Leaves `muted` Stuck**: Leaving `muted` out of the array and silencing the linter also stops the reconnect. But the function the connection holds keeps the `muted` of the render that connected, so the box stops working.
4. **Principle 4: Wrapping the Connection in `onMount` Leaves the Chat in the First Room**: Only logic that should not re-synchronize moves into an Effect Event. The connection to `roomId` stays in the Effect, and the message text reaches `onMessage` as an argument.
5. **Principle 5: `onMessage` Runs Only Inside Its Own Effect**: An Effect Event is called only from an Effect or from another Effect Event. It is never called during rendering, never called from a click handler, and never passed to another component.

Here is the complete map of those five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Reading `muted` Inside the Effect Reconnects the Chat** | The user ticks a box that has nothing to do with the connection, and the Console shows a disconnect and a new connect. | Every reactive value an Effect reads belongs in its dependency array, so a value read only when a message arrives still re-synchronizes the Effect. |
| **Principle 2** | **`onMessage` Reads `muted` Without Reconnecting** | Interviewers ask what `useEffectEvent` is for; it is the documented way to read a value without reacting to it. | Declare an Effect Event with `useEffectEvent` at the top level, call it from the Effect, and leave both the Effect Event and the values it reads out of the array. |
| **Principle 3** | **Suppressing the Linter Leaves `muted` Stuck** | The reconnect disappears, the bug moves to the box, and the linter can no longer warn about the next missing value. | Never suppress the linter; a suppressed Effect keeps the values of the render that set it up. |
| **Principle 4** | **Wrapping the Connection in `onMount` Leaves the Chat in the First Room** | Wrapping the whole connection in an Effect Event quiets the linter, and the heading changes while the chat stays in the first room. | Move only non-reactive logic into an Effect Event, name it after what the user thinks happened, and pass the values of the event as arguments. |
| **Principle 5** | **`onMessage` Runs Only Inside Its Own Effect** | A call during rendering throws an error, and a call from a click or a child breaks a rule the linter checks. | Call an Effect Event only from an Effect or another Effect Event in the same component, and use a regular function for clicks and children. |

## 1. Principle 1: Reading `muted` Inside the Effect Reconnects the Chat

### Logic that follows a value vs. logic that runs when something happens

Code that runs because of one interaction goes in an event handler, and code that keeps the component in sync goes in an Effect (as seen in Lesson 34). Here are the two side by side in React's own chat example:

```jsx title="An event handler and an Effect in the same chat room"
function handleSendClick() {
  ~sendMessage(message)~; // Runs only when the user clicks Send
}

useEffect(() => {
  const connection = ~createConnection(serverUrl, roomId)~; // Runs again for every new roomId
  connection.connect();
  return () => connection.disconnect();
}, [roomId]);
```

React's docs give the two kinds of code a name:
- **Logic inside event handlers is not reactive.** It runs again only when the user does the same thing again. The handler reads `message`, yet typing a new message does not send it. In the words of the docs, "a change to the `message` does not mean that they want to send a message. It only means that the user is typing."
- **Logic inside Effects is reactive.** It runs again whenever a value it reads changes. When `roomId` changes, the Effect disconnects and connects again (as seen in Lesson 35).

The docs then add: "Things get more tricky when you want to mix reactive logic with non-reactive logic." Our notification is exactly such a mix. It must live inside the Effect, because the message comes from the connection. But the check of `muted` should behave like an event handler: read the value when the message arrives, and ignore its changes.

### Adding the notification puts `muted` in the array

Here is the natural first try. `ChatRoom` receives `muted`, and the Effect hands the connection a function that shows a notification unless the user muted the room:

```jsx title="src/components/ChatRoom.jsx"
import { useEffect } from 'react';
import { createConnection } from '../chat.js';
import { showNotification } from '../notifications.js';

const serverUrl = 'https://localhost:1234';

export default function ChatRoom({ roomId, muted }) {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    ~connection.on~('message', msg => { // Hands the connection a function to call with each message
      if (~!muted~) { // Reads the muted prop when a message arrives
        showNotification('New message: ' + msg);
      }
    });
    return () => connection.disconnect();
  }, ~[roomId, muted]~); // The linter asks for muted, so muted joins roomId

  return <h1>Welcome to the {roomId} room!</h1>;
}
```

Two names here come from our own helpers:
- **`connection.on`** comes from our `chat.js`. We hand it a function, and every three seconds the connection calls that function with the text of the new message. JavaScript puts that text, `hey` or `lol`, into `msg`.
- **`showNotification`** comes from our `notifications.js`. It prints the notification line in the Console.

`muted` is in the array because the Effect reads it, and a prop is a reactive value (as seen in Lesson 35). Leave it out, and the linter reports `React Hook useEffect has a missing dependency: 'muted'`.

When the page opens, everything works. The chat connects to the general room, and a notification line appears for each message.

### Ticking the box disconnects the chat and connects it again

**Beware! Ticking the box does stop the notifications, but it also drops the connection and opens a new one.** The user only asked for silence, and the chat reconnects. Here is what happens, in order, when the user ticks the Mute notifications box in the general room:
1. `App` sets `muted` to `true`, and `ChatRoom` renders again with the new prop.
2. React compares the new array with the last one. `roomId` is still `'general'`, but `muted` changed.
3. So React runs the old cleanup, and the Console shows the disconnect line for the general room.
4. Then React runs the new setup, and the Console shows a new connect line for the same room.
5. The heading did not change. The user is still in the general room, on a brand-new connection.

```page width=text caption="The chat right after the user ticks the Mute notifications box: the heading is unchanged, but the Console shows a disconnect and a new connect."
form:
  select: Choose the chat room: | general
  check: Mute notifications | on | bad
heading: Welcome to the general room!
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
log: 🔔 New message: hey
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
```

With `[roomId, muted]`, the Effect treats the two actions of the user the same way:
- **When the user picks `travel`**, `roomId` changes. The Effect disconnects from the general room and connects to the travel room. This is what the user wants.
- **When the user ticks the box**, `muted` changes. The Effect disconnects from the general room and connects to the general room again. Nobody asked for this.

There is a second surprise. **A user who ticks and unticks the box quickly gets no messages at all.** Here is why:
1. Every reconnect runs `disconnect`, which stops the timer of the old connection, and `connect`, which starts a new timer.
2. The new timer delivers its first message three seconds after the connect.
3. If the user ticks the box again before those three seconds pass, the timer stops once more, and no message arrives.

React's docs show the same thing with a timer: "If you keep clearing the interval every time before it has a chance to fire, it will appear as if the timer has stalled."

The array is correct for the code as written, so the linter did its job. What is wrong is the code itself: it puts non-reactive logic, the check of `muted`, inside a reactive block. The fix is to move that logic out of the Effect, not to change the array.

```tree caption="With muted read inside the Effect, picking a room and ticking the Mute box both reconnect the chat."
What the Effect does with `[roomId, muted]`
- +The user picks `travel` [`roomId`] | The user **wants a new room** | Disconnects from general and **connects to travel**
- !The user ticks the Mute box [`muted`] | The user **only wants silence** | Disconnects from general and **connects to general again**
```

## 2. Principle 2: `onMessage` Reads `muted` Without Reconnecting

### `useEffectEvent` in its smallest form

`useEffectEvent` is a Hook provided by React. You give it a function, and it gives you back a new function, an Effect Event:

```jsx title="The smallest useEffectEvent"
import { useEffect, ~useEffectEvent~ } from 'react'; // Imported from React, like useEffect

const onEvent = ~useEffectEvent(callback)~; // Returns an Effect Event that runs callback
```

The name says what it is: a piece of your Effect that behaves like an event. As React's docs put it: "It's a part of your Effect logic, but it behaves a lot more like an event handler. The logic inside it is not reactive, and it always 'sees' the latest values of your props and state."

So an Effect Event and an event handler share one thing: both read the current values at the moment they run, and neither runs again when those values change. The one difference is who calls them. React calls an event handler when the user clicks. Your Effect calls an Effect Event, for example when a message arrives.

### Moving the `muted` check into `onMessage`

Here is `ChatRoom` with the check moved into an Effect Event named `onMessage`:

```jsx title="src/components/ChatRoom.jsx"
import { useEffect, useEffectEvent } from 'react';
import { createConnection } from '../chat.js';
import { showNotification } from '../notifications.js';

const serverUrl = 'https://localhost:1234';

export default function ChatRoom({ roomId, muted }) {
  const onMessage = ~useEffectEvent~(msg => { // Declared at the top level, next to the Effect
    if (!muted) {
      showNotification('New message: ' + msg);
    }
  });

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    connection.on('message', msg => ~onMessage(msg)~); // Calls the Effect Event for each message
    return () => connection.disconnect();
  }, ~[roomId]~); // Only roomId: muted and onMessage stay out

  return <h1>Welcome to the {roomId} room!</h1>;
}
```

Three things changed:
1. The check of `muted` moved out of the Effect into `onMessage`, declared with `useEffectEvent` at the top level of the component.
2. The function handed to the connection no longer checks anything itself. It passes each message on to `onMessage`.
3. The array is back to `[roomId]`. The Effect no longer reads `muted` itself, so `muted` leaves the array. And `onMessage` stays out too, because, as the docs say, "Effect Events are not reactive and must be omitted from dependencies."

React's docs call this move "extracting" an Effect Event: the non-reactive line comes out of the Effect, and the Effect keeps only the logic that must follow `roomId`.

**It may look the same, or work the same at first, but it is NOT the same thing!** When the page opens, the version with `muted` inside the Effect and the version with `onMessage` do exactly the same thing. Both connect to the general room, and both show a notification line for each message. The difference appears only when the user ticks the box. The version with `muted` inside the Effect reconnects. The version with `onMessage` keeps its connection, and still stops the notifications.

```tree caption="The same chat with muted read inside the Effect, and with muted read inside the onMessage Effect Event."
Where the check of `muted` lives
- !Inside the Effect [`[roomId, muted]`] | The Effect **depends on `muted`** | Every tick of the box **disconnects and connects again**
- +Inside `onMessage` [`useEffectEvent` `[roomId]`] | The Effect **depends only on `roomId`** | The next message reads the **latest `muted`**; the connection **stays**
```

### Ticking the box now changes only the notifications

**When the user ticks the Mute notifications box, the notifications stop, and the Console shows no disconnect and no new connect.** That may look surprising, since the connection was set up when `muted` was still `false`. Here is what happens, in order:
1. The user ticks the box, and `ChatRoom` renders again with `muted` as `true`.
2. React compares `[roomId]` with the last array. Nothing changed, so the Effect does not run again.
3. The connection from the first setup keeps running. A few seconds later, it calls its function with the next message.
4. That function calls `onMessage`, which reads the latest `muted`, `true`, and shows nothing.

```page width=text caption="The chat after the user ticks the Mute notifications box: no disconnect, no new connect, and no notification line for the next messages."

  check: Mute notifications | on | good

log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
log: 🔔 New message: hey
```

When the user unticks the box, `onMessage` reads `false` for the next message, and notification lines appear again on the same connection:

```page width=text caption="The same chat after the user unticks the box: notification lines appear again, and the connection was never replaced."

  check: Mute notifications | off | good

log: ✅ Connecting to "general" room at https://localhost:1234...

log: 🔔 New message: lol
```

### Where does `onMessage` get the latest `muted`?

React gives it the latest `muted`. The function the connection holds was created during the first render, yet `onMessage` reads the value of the box as it is now. The docs promise exactly that: "When you call the returned Effect Event function, the `callback` always accesses the latest committed values from render at the time of the call." In plain words, `onMessage` reads the props and state of the latest render that reached the screen. The docs do not describe how React does this inside, and you do not need to know it to use the Hook.

`msg` comes from the Effect. The connection hands the message text to the arrow function, and the arrow function passes it on to `onMessage` as an argument.

React's docs teach the same pattern with a different setting. Their chat helper also reports when the chat has connected, and their notification helper takes the current theme. Put the two side by side:

```jsx title="The docs' version: a theme read in an Effect Event"
const onConnected = ~useEffectEvent~(() => { // Reads the latest theme when the chat connects
  showNotification('Connected!', theme);
});

useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.on('connected', () => {
    onConnected();
  });
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId]~); // ✅ All dependencies declared
```

**Yes, it is the exact same thing!** One line reads a user setting, `theme` there and `muted` here. That line moves into an Effect Event, and the array keeps only `roomId`.

### Listing `onMessage` in the array reconnects on every render

**Beware! An Effect Event in the array brings the reconnect back, and makes it worse: the chat reconnects after every render.** Out of habit, developers add every function the Effect calls to its array:

```jsx title="src/components/ChatRoom.jsx"
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  connection.on('message', msg => onMessage(msg));
  return () => connection.disconnect();
}, ~[roomId, onMessage]~); // **WRONG:** onMessage is new on every render, so the chat reconnects on every render
```

Here is what goes wrong:
1. The linter reports it. React's docs give this message as "Functions returned from useEffectEvent must not be included in the dependency array".
2. If the code runs anyway, the Effect runs again after every render, because "Effect Event functions do not have a stable identity". The identity of a function is which function object it is. React gives `onMessage` a brand-new function object on every render, on purpose, so the comparison of the array always sees a change.
3. So the chat disconnects and connects again on every render of `ChatRoom`, including every tick of the box.

> [!PRINCIPLE]
> **Principle 2: Effect Events: `onMessage` Reads the Latest `muted` Without Reconnecting**
>
> *Move the line that should not be reactive into a function made with `useEffectEvent`, and call it from inside the Effect. Leave both the Effect Event and the values it reads out of the array.*
>
> The user ticks the box and expects silence, not a new connection. An Effect Event lets the Effect read the current `muted` each time a message arrives, while the Effect itself depends only on `roomId`. Picking a room still reconnects. Ticking the box only changes what the next message does.
>
> **DO THIS:**
> ```jsx
> const onMessage = ~useEffectEvent~(msg => { // Reads the latest muted for each message
>   if (!muted) showNotification('New message: ' + msg);
> });
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => onMessage(msg));
>   return () => connection.disconnect();
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => onMessage(msg));
>   return () => connection.disconnect();
> }, ~[roomId, onMessage]~); // **WRONG:** an Effect Event in the array reconnects the chat on every render
> ```

## 3. Principle 3: Suppressing the Linter Leaves `muted` Stuck

### Two Effects with the same `[roomId]`

There is a second way to stop the reconnect, and many developers try it first. They keep the check of `muted` inside the Effect, remove `muted` from the array, and silence the linter with a comment:

```jsx title="With the linter suppressed"
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  connection.on('message', msg => {
    if (~!muted~) { // **WRONG:** reads the muted of the render that connected
      showNotification('New message: ' + msg);
    }
  });
  return () => connection.disconnect();
}, ~[roomId]~); // **WRONG:** eslint-disable-line react-hooks/exhaustive-deps hides muted from the linter
```

The comment `eslint-disable-line react-hooks/exhaustive-deps` at the end of the last line tells the linter to skip that line, so it no longer asks for `muted`. Developers often write the same thing as an `eslint-disable-next-line` comment on the line above. Now look at the version with `onMessage` from Principle 2:

```jsx title="With onMessage"
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  connection.on('message', msg => ~onMessage(msg)~); // Reads the latest muted for each message
  return () => connection.disconnect();
}, [roomId]);
```

**It may look the same, or work the same at first, but it is NOT the same thing!** Both arrays say `[roomId]`, and after a tick of the box, neither version shows a disconnect line. But only the version with `onMessage` stops the notifications.

### Notifications keep coming after the user mutes the room

**Beware! With the linter suppressed, the box no longer works: the user mutes the room, and notifications keep coming.** Here is why, in order:
1. The page opens with `muted` as `false`. The setup runs and hands the connection a function that belongs to this first render, so that function sees `muted` as `false`.
2. The user ticks the box. `ChatRoom` renders again with `muted` as `true`.
3. React compares `[roomId]` with the last array. Nothing changed, so the old setup stays, and so does its function.
4. The next message arrives. The old function checks the old `muted`, which is still `false`.
5. The Console shows a new notification line, after the user muted the room.

The old function never sees the new value, because each render keeps its own values of props and state (as seen in Lesson 15). The function was created during the first render, so it sees the first render's `muted` until React runs a new setup.

```page width=text caption="With the linter suppressed: the first notification line came before the tick, and the next two came after the user ticked the Mute notifications box."
log: 🔔 New message: lol
```

### Picking another room fixes the box for a while

**Changing rooms seems to repair the box, and then it breaks the other way.** Here is what happens, in order:
1. While the box is ticked, the user picks `travel`. `roomId` changed, so React runs a new setup.
2. The new function belongs to this render, and sees `muted` as `true`. No notification lines appear.
3. The user unticks the box. The function still sees `true`, so no notification lines appear until the room changes again.

This bug is hard to find, because the box works or fails depending on when the user last changed rooms. And the linter can no longer help. React's docs warn that after a suppression, "React will no longer warn you when your Effect needs to 'react' to a new reactive dependency you've introduced to your code." And they add: "If you never suppress the linter, you will never see problems with stale values."

```tree caption="Two Effects with the same array: the suppressed one keeps an old muted, and the one with onMessage reads the latest muted."

- +With `onMessage` [`useEffectEvent`] | The function the connection holds **calls the Effect Event** | Reads the **latest `muted`**, so **the notifications stop**
```

> [!PRINCIPLE]
> **Principle 3: Suppressing the Linter: The Effect Keeps an Old `muted`**
>
> *Silencing the linter also stops the reconnect. But the function the connection holds keeps the `muted` of the render that set it up, so the box stops working until the room changes.*
>
> The user mutes the room and still gets notifications. The Effect did not run again, so the function it gave the connection still belongs to the old render and checks the old value. The linter was the only thing that could point to this, and it was silenced. An Effect Event fixes the reconnect without hiding anything.
>
> **DO THIS:**
> ```jsx
> const onMessage = useEffectEvent(msg => {
>   if (~!muted~) showNotification('New message: ' + msg); // Reads the latest muted for each message
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => {
>     if (~!muted~) showNotification('New message: ' + msg); // **WRONG:** muted is stuck at its value from the render that connected
>   });
>   return () => connection.disconnect();
> }, ~[roomId]~); // **WRONG:** eslint-disable-line react-hooks/exhaustive-deps hides muted from the linter
> ```

## 4. Principle 4: Wrapping the Connection in `onMount` Leaves the Chat in the First Room

### Wrapping the whole connection in an Effect Event

Once developers see that `useEffectEvent` quiets the linter, some wrap everything in it. Here the whole connection moves into an Effect Event named `onMount`, and the Effect runs only once:

```jsx title="With the connection inside onMount"
const onMount = ~useEffectEvent~(() => { // **WRONG:** the connection must follow roomId, so it does not belong here
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  connection.on('message', msg => onMessage(msg));
  return connection;
});

useEffect(() => {
  const connection = onMount();
  return () => connection.disconnect();
}, ~[]~); // The linter is quiet: the Effect reads no reactive value
```

In the code from Principle 2, the connection stays in the Effect with `[roomId]`, and only the check of `muted` moved into `onMessage`.

**It may look the same, or work the same at first, but it is NOT the same thing!** Both versions connect to the general room when the page opens, and the linter is quiet for both. The difference appears when the user picks `travel`. Only the version from Principle 2 reconnects.

### The heading says travel, and the chat is still in general

**With the connection inside `onMount`, the heading follows the menu, and the connection does not.** Here is what happens, in order:
1. The page opens. The Effect calls `onMount`, which connects to the general room.
2. The user picks `travel`. The heading changes to welcome the user to the travel room.
3. React compares `[]` with `[]`. Nothing changed, so no cleanup and no setup run.
4. The Console shows no disconnect line and no new connect line. The messages still come from the general room.

`onMount` does read the latest `roomId` when it runs. But nothing calls `onMount` again, so it only ever read the first one.

```page width=text caption="With the connection inside onMount, the heading says travel, but the Console shows only the connection to general."
form:
  select: Choose the chat room: | travel | bad
  check: Mute notifications | off
heading: Welcome to the travel room!
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
log: 🔔 New message: hey
```

React's docs warn against exactly this: "Do not use `useEffectEvent` to avoid specifying dependencies in your Effect's dependency array. This hides bugs and makes your code harder to understand." And they say where the Hook belongs: "You should only apply it to the lines of code that you don't want to be reactive."

### Name the Effect Event after what the user thinks happened

The name `onMount` was the first warning sign. It says when the code runs, not what happened for the user. React's docs ask you to "name your Effect Events after what the user thinks has happened, not when some code happened to run." They add that "`onMount`, `onUpdate`, `onUnmount`, or `onAfterRender` are so generic that it's easy to accidentally put code that should be reactive into them." Good names describe an event the user would recognize, such as `onMessage`, `onTick`, `onVisit`, or `onConnected`.

To decide what moves, ask one question for each piece of logic: does a change of this value mean the user wants this code to run again?
1. **For the connection, the answer is yes.** A new `roomId` means the user wants a new room, so the connection stays in the Effect, with `roomId` in the array.
2. **For the notification check, the answer is no.** A new `muted` does not mean the user wants a new connection, so the check moves into `onMessage`.

### The message text arrives as an argument

`onMessage` gets the message text from the Effect, as an argument, because the component has no message text to read. The text exists only at the moment the connection hands it over, and it belongs to that one message. React's docs allow this: "The function can accept any number of arguments and return any value."

So the two values inside `onMessage` arrive in two different ways:

```jsx title="The two kinds of values inside onMessage"
const onMessage = useEffectEvent(~msg~ => { // Belongs to this one message: passed in by the Effect
  if (!~muted~) { // A setting looked up when the message arrives: always the latest value
    showNotification('New message: ' + msg);
  }
});
```

1. **A value that belongs to the event**, such as the message text, comes in as an argument from the Effect.
2. **A value the event only looks up at that moment**, such as `muted`, is read inside the Effect Event, and it is always the latest one.

```tree caption="Moving the whole connection into an Effect Event vs. moving only the notification check."
What moves into an Effect Event
- !The whole connection in `onMount` [`[]`] | Quiets the linter, **but the connection no longer follows `roomId`** | The heading says travel; the chat **stays in general**
- +Only the check in `onMessage` [`[roomId]`] | The connection **stays in the Effect** | Picking a room **reconnects**; ticking the box **only changes the notifications**
```

> [!PRINCIPLE]
> **Principle 4: Only Non-Reactive Logic: The Connection Stays in the Effect**
>
> *Move into an Effect Event only the logic that should not re-synchronize. Code that must follow a value, such as the connection to `roomId`, stays in the Effect. A value that belongs to the event, such as the message text, reaches the Effect Event as an argument.*
>
> When the user picks a new room, the chat must leave the old one. If the connection hides inside an Effect Event, the linter goes quiet, and the chat stays in the first room while the heading changes. Move only the lines that read a value at the moment something happens, and name the Effect Event after that event.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => ~onMessage(msg)~); // Only the notification check is an Effect Event
>   return () => connection.disconnect();
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const onMount = useEffectEvent(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return connection;
> });
> useEffect(() => {
>   const connection = ~onMount()~; // **WRONG:** runs once, so the chat never leaves the first room
>   return () => connection.disconnect();
> }, []);
> ```

## 5. Principle 5: `onMessage` Runs Only Inside Its Own Effect

### Three places to call the same function

`onMessage` is a function, so it seems you could call it anywhere a function fits. Here are three places a developer might try:

```jsx title="Three places to call onMessage"
connection.on('message', msg => ~onMessage(msg)~); // 1. Inside the Effect: allowed

<button onClick={() => ~onMessage('test')~}>Test notification</button> {/* 2. In a click handler: not allowed */}

<MessageList ~onMessage={onMessage}~ /> {/* 3. Passed to a child as a prop: not allowed */}
```

**It may look the same, but it is NOT the same thing!** All three call the same function, and only the first is allowed. React's docs put it in two rules: "Only call them from inside Effects." And: "Never pass them to other components or Hooks."

The reason is that an Effect Event is a piece of one Effect, not a general tool. In the words of the docs: "This design reinforces that Effect Events conceptually belong to a particular effect, and are not a general purpose API to opt-out of reactivity."

### A call during rendering throws an error

**Calling `onMessage` in the body of `ChatRoom` throws an error, and the page goes blank.** Here is the call:

```jsx title="src/components/ChatRoom.jsx"
export default function ChatRoom({ roomId, muted }) {
  const onMessage = useEffectEvent(msg => {
    if (!muted) {
      showNotification('New message: ' + msg);
    }
  });

  ~onMessage('test')~; // **WRONG:** runs while React renders ChatRoom

  return <h1>Welcome to the {roomId} room!</h1>;
}
```

The body of a component runs while React renders it (as seen in Lesson 13). So this call happens during rendering, before anything reaches the screen. React stops rendering, removes the page, and prints the error:

```devconsole caption="The Console after onMessage is called in the body of ChatRoom."
x Uncaught Error: A function wrapped in useEffectEvent can't be called during rendering.
x An error occurred in the <ChatRoom> component. Consider adding an error boundary to your tree to customize error handling behavior.
```

### A click handler and a child get the linter's warning

When the page runs, the click handler and the child prop show no error. The linter reports them instead. React's docs give its message as "... is a function created with React Hook `useEffectEvent`, and can only be called from Effects and Effect Events".

Each of the two has its own reason:
1. **A click does not need an Effect Event.** A click is already an interaction, so it gets a regular event handler (as seen in Lesson 11).
2. **A child would get a function that changes on every render.** An Effect Event has a new identity after every render. If the child lists it in the array of its own Effect, that Effect runs again after every render.

React's docs show the second case with a timer. A component passes its Effect Event to a custom Hook, `useTimer`, and the timer restarts on every render. The docs' advice: "If you need a callback for event handlers or to pass to children, use a regular function or `useCallback` instead." `useCallback` has its own lesson (covered in Lesson 57), and so do custom Hooks that take a callback (covered in Lesson 39).

For the Test notification button, a regular event handler does the job:

```jsx title="A regular event handler for the Test notification button"
function ~handleTestClick~() { // A regular function: runs only when the user clicks
  showNotification('Test notification');
}

<button onClick={handleTestClick}>Test notification</button>
```

### Declared next to its Effect, at the top level

`useEffectEvent` is a Hook, so it goes where `useState` and `useEffect` go: at the top level of the component, never inside a condition or a loop (covered in Lesson 38). Declare the Effect Event right above the Effect that calls it. React's docs: "Effect Events are non-reactive 'pieces' of your Effect code. They should be next to the Effect using them."

```tree caption="The four places a developer might put a call to onMessage, and which one React allows."
Where `onMessage` can be called
- +Inside its own Effect [`connection.on`] | **Allowed** | Reads the latest `muted` each time a message arrives
- !In the component body [`onMessage`] | Runs **during rendering** | React **throws an error**
- !In a click handler [`onClick`] | The linter **reports it** | Use a **regular event handler** instead
- !Passed to a child [`<MessageList onMessage>`] | A **new identity** on every render | Use a **regular function** or `useCallback` instead
```

> [!PRINCIPLE]
> **Principle 5: Limits: An Effect Event Runs Only Inside Its Own Effect**
>
> *Call an Effect Event only from its own Effect or from another Effect Event. Never call it during rendering or from an event handler, never pass it to another component or Hook, and declare it next to the Effect that uses it.*
>
> An Effect Event looks like any other function, but it is a piece of one Effect. Called during rendering, it throws an error and the page goes blank. Called from a click or passed to a child, it breaks the rule the linter checks, and a child that depends on it runs its Effect after every render. Clicks and children get regular functions.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => ~onMessage(msg)~); // Called from inside its own Effect
>   return () => connection.disconnect();
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button onClick={() => ~onMessage('test')~}> {/* **WRONG:** an Effect Event called from a click handler */}
>   Test notification
> </button>
> ```

## Putting All Five Principles Together

### The complete project files

Here are the four files of our finished chat room. The chat helper creates a connection that delivers a message every three seconds:

```js title="src/chat.js"
export function ~createConnection~(serverUrl, roomId) { // The message version of the helper from React's docs
  let intervalId;
  let messageCallback;
  return {
    connect() {
      console.log('✅ Connecting to "' + roomId + '" room at ' + serverUrl + '...');
      clearInterval(intervalId);
      intervalId = setInterval(() => {
        if (messageCallback) {
          if (Math.random() > 0.5) {
            messageCallback('hey');
          } else {
            messageCallback('lol');
          }
        }
      }, 3000);
    },
    disconnect() {
      clearInterval(intervalId);
      messageCallback = null;
      console.log('❌ Disconnected from "' + roomId + '" room at ' + serverUrl);
    },
    on(event, callback) {
      if (messageCallback) {
        throw Error('Cannot add the handler twice.');
      }
      if (event !== 'message') {
        throw Error('Only "message" event is supported.');
      }
      messageCallback = callback;
    },
  };
}
```

The notification helper prints one line for each notification:

## For the Interview

> **The Interview Question:** How do you keep non-reactive values from re-running an effect?

### How to Answer Clearly in 30 Seconds

"Every reactive value an Effect reads must be in its dependency array. So a value I only need at the moment something happens, such as a Mute setting checked when a chat message arrives, still re-runs the whole synchronization. The fix is `useEffectEvent`, which React 19.2 added:
1. **Extract the non-reactive logic**: I move the lines that read that value into an Effect Event, declared with `useEffectEvent` at the top level of the component, and I call it from inside the Effect.
2. **Leave it out of the array**: the Effect Event always reads the latest props and state when it is called, and neither it nor the values it reads go in the dependency array. The Effect keeps only the values that should re-synchronize it, such as `roomId`.
3. **Respect its limits**: I move only logic that should not be reactive, I never suppress the linter instead, and I call the Effect Event only from its own Effect, never during rendering, from a click handler, or from a child."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why not just suppress the linter and leave the value out of the array?"**
   Because the value gets stuck. The function the Effect hands to the connection belongs to the render that ran the setup, and each render keeps its own props and state. If the Effect does not run again, that function keeps checking the old value. In our chat, the user mutes the room and still gets notifications until the room changes. Worse, the linter stays silent for every new value the Effect reads later. An Effect Event avoids the reconnect without hiding anything from the linter.
2. **"When should a value be passed to the Effect Event as an argument instead of read inside it?"**
   When the value belongs to the event itself. The message text exists only when the connection hands it over, so the Effect passes it to `onMessage`. React's docs give a second case: a log of page visits. For each new `url`, the Effect calls `onVisit` and passes the `url` as an argument, so the log records the page that caused this visit. If `onVisit` read `url` from the component instead, it would get the latest `url`, which may already be a different page. Asking for the value as an argument also keeps `url` in the Effect's array, so nobody can remove it by accident.
3. **"Why does an Effect Event get a new identity on every render, unlike a setter or a ref?"**
   React does it on purpose. The docs say its identity "intentionally changes on every render", and that "the non-stable identity acts as a runtime assertion", which means a built-in check that fails loudly. If someone lists the Effect Event in a dependency array, the Effect runs again after every render, so the mistake shows up at once instead of hiding. It also makes clear that an Effect Event is not a function to pass around. For a function to give a child, you write a regular function, or wrap it in `useCallback` when the child needs the same function between renders.

```tree dir=right caption="Interview summary: how one Effect separates the logic that re-synchronizes from the logic that only reads the latest values."
One Effect, two kinds of logic
- +Reactive logic [`[roomId]`] | Must **follow its value** | Stays in the Effect, and a change **re-synchronizes** the connection
- +Non-reactive logic [`useEffectEvent`] | Only **reads a value when something happens** | Moves into an Effect Event that reads the **latest props and state**
- !Suppressed linter [`eslint-disable-line`] | Stops the re-run **by hiding a dependency** | The value **gets stuck**, and the linter stays silent afterwards
```
