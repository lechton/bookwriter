# Calculating Values During Rendering vs. Storing Them in State

> INTERVIEW QUESTION | ❱ CORE | How do you decide which values belong in state and which are derived?

## Before We Begin

To follow this lesson comfortably, you should already know a few tools from earlier lessons:
- From Lesson 12, how `useState` stores a value for a component, how calling its setter asks React to call the component again, and why the initial value passed to `useState` is used only on the first render.
- From Lesson 06 and Lesson 09, how a parent passes props to a child and how expressions such as `? :` and `&&` pick what JSX to return.
- From Lesson 15, Lesson 17, and Lesson 18, how `map` turns an array into rows with a `key` on each row, how `filter` returns a new array without the removed item, and how `{ ...obj, key: newValue }` copies an object with one changed field.
- From Lesson 20, how a controlled `<input>` reads its text from `value={query}` and updates state in `onChange` through `e.target.value`.

Think of a shopping list on paper. You write one item per line: bread, milk, eggs. How many items are on the list? You could write the number 3 at the bottom of the page. Or you could count the lines whenever someone asks.

If you write 3 at the bottom and then cross out milk, the list now has two items, and the bottom of the page still says 3. Your two notes on the same page disagree. If instead you count the lines whenever someone asks, the answer is always 2, because it comes straight from the lines that are there right now.

A React component faces the same choice every time it shows a number, a filtered list, or a chosen item:

```tree caption="Two ways a component can get a value to show on the page" width=text
The values a component shows on the page
├── 1. Stored in state with useState
│   └── React keeps it between renders, and it changes only when a handler calls its setter
└── 2. Calculated during rendering with const
    └── A plain variable in the component body, computed fresh from state and props on every render
```

Both produce a variable that the JSX can put on the page. The one difference is who keeps it up to date. A state variable stays on its old value until your code calls its setter. A `const` in the component body runs again every time React calls the component, so it cannot lag behind the state and props it reads:
- **A state value** is stored with `useState`. React keeps it between renders, and it changes only when an event handler calls its setter.
- **A calculated value** is a plain `const` inside the component function, computed from state and props while the component runs. React's docs call this **calculating during rendering**.

Interviewers also call a value calculated during rendering **derived**, or sometimes **derived state**. In everyday English, one thing derives from another when it comes out of it, the way a river comes out of its spring. The count of items comes out of the list of items, so the count is derived from the list. Remember that "a derived value" and "a value calculated during rendering" are **the exact same thing**. It is not a special kind of `useState`. It is a plain `const` computed during rendering, with no `useState` at all:

```tree caption="What React keeps between renders, and what the component computes on each render" width=text
Inside one render of a component
├── State from useState: the raw changing facts
│   ├── Kept by React between renders
│   └── Updated only when an event handler calls a setter
└── Derived values with const: calculated during rendering
    ├── Computed fresh from state and props each time the component function runs
    └── Never stored in useState, so they never need their own setter call
```

What is at stake is a page that shows two answers that disagree. A line says `5 players` above a list of four players. A line says `Captain: Mia` after Mia has left the team. React's docs say that two parts of a page like this have fallen **out of sync**: they should agree, and they do not. Each time, the component kept the same fact in two places: once in the list, and once in a second state variable. Then one click by the user updated only one of them. The Console prints no error, even though the two parts of the page disagree.

Readers usually go wrong in one place: they give every value the page shows its own `useState`. Then every event handler must remember to call every setter. The first handler that forgets leaves the page out of sync.

The page shows a search box, a count line `Showing 5 of 5 players`, the list of players with `Make captain` and `Remove` buttons on each row, and a captain line at the bottom. When the search box is empty, it shows the hint `Search players` through the browser's `placeholder` attribute. Six values change on this page as the user types and clicks:
- Which players are still on the team.
- What text is inside the search box.
- Which rows match the search box.
- How many rows match and how many players are on the team in total.
- Which player is the captain, marked on that player's row.
- The captain's name at the bottom of the page.

By the end of the lesson, all six will work together on the page while only **three** of them live in `useState`. The other three will be plain `const` variables calculated during rendering, and we will also see two rules from React's docs on how to shape state itself when values belong together or sit inside nested trees:

```tree caption="Six values on the team page: only three live in useState" width=text
The six changing values on the team page
├── Essential state in useState
│   ├── 1. players: the array of players currently on the team
│   ├── 2. query: the text typed by the user into the search box
│   └── 3. captainId: the numeric id of the chosen captain, or null
└── Derived during rendering with const or props
    ├── 4. visiblePlayers: computed from players and query with filter
    ├── 5. The counts in Showing 5 of 5 players: read from visiblePlayers.length and players.length
    └── 6. captain and the bottom line: looked up with find from players and captainId, then passed as a prop
```

1. **Principle 1: `count` Comes from `players.length`**: A count kept in its own `useState` stays on the old number whenever a handler updates `players` without calling `setCount`. Read `players.length` during rendering instead.
2. **Principle 2: `visiblePlayers` Comes from `players` and `query`**: A filtered list comes from two state variables, the full list and the search text. Keeping the filtered list in a third state variable leaves removed players on screen until the user types again.
3. **Principle 3: Keep `captainId` in State, Not the `captain` Object**: Keeping a chosen player's object in its own state variable duplicates that player, so removing the player from `players` leaves the removed player as captain. Keep only `captainId` in state and find the player in `players` during rendering.
4. **Principle 4: Copying `name` into `useState` Freezes the Captain Line**: The initial value passed to `useState` is read only on the first render, so a prop copied into state ignores every later value from the parent. Read the prop directly instead.
5. **Principle 5: `position` Holds `x` and `y` Together**: Two values that always change together belong in one state object, and every update writes both fields or spreads the old object first.
6. **Principle 6: A Flat `plan` Uses `childIds` Instead of Nested Objects**: When items sit inside items inside items, storing every item at the top level by `id` with an array of `childIds` turns a deep nested copy into updating the parent item and the top object.

| Principle | Rule | Trap | Fix |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Calculate from State During Rendering** | Keeping `count` in its own `useState` leaves `5 players` on screen after a player is removed. | Delete the `count` state and read `const count = players.length;` during rendering. |
| **Principle 2** | **Calculate from Multiple State Values** | Keeping `filteredPlayers` in state and setting it only in `onChange` leaves removed players on the list. | Keep only `players` and `query` in state and compute `visiblePlayers` with `filter` on every render. |
| **Principle 3** | **No Duplication in State** | Storing the full `captain` object in state keeps saying `Captain: Mia` after Mia is removed from `players`. | Store only `captainId` in state and look up `captain` in `players` with `find` during rendering. |
| **Principle 4** | **Do Not Mirror a Prop in State** | Copying a prop into `useState` keeps showing the first captain after the parent passes a new one. | Use a prop directly. Copy it into state only when later values must be ignored, and then start the prop's name with `initial` or `default`. |
| **Principle 5** | **Group Related State** | Merging two values into one object and then setting only one field erases the other field to `undefined`. | When two state variables always change together, merge them into one object, and set every field or spread the old object first. |
| **Principle 6** | **Avoid Deeply Nested State** | Removing a deeply nested item requires copying every parent level above it. | Store a flat table object keyed by `id`, where each item lists its children in `childIds`. |

## Principle 1: `count` Comes from `players.length`

Look at two ways a component can show how many names are in a list:

```jsx title="With count in its own state"
const [names, setNames] = useState(['John', 'Mia', 'Sara']);
const [count, setCount] = ~useState(3)~; // A second state variable that holds 3

<p>{count} names</p>
```

```jsx title="With count read from names.length"
const [names, setNames] = useState(['John', 'Mia', 'Sara']);
const count = ~names.length~; // Read from the list every time React calls the component

<p>{count} names</p>
```

Both show `3 names` when the page opens. **It may look the same, or work the same at first, but it is NOT the same thing!** They part ways as soon as a handler changes `names`:
- **With `count` in its own state**, React keeps two separate values in memory: `names` and `count`. Calling `setNames` updates `names` and leaves `count` at `3` unless the handler also calls `setCount`.
- **With `names.length`**, there is no second state variable to update. Because React calls the component again after every change to `names`, the `const` line runs again and reads the length of the new array.

React's docs have a name for a state variable that holds `count` in its own `useState`: **redundant state**. In everyday English, something is redundant when it is more than you need because it repeats what is already there, like a second copy of the same note. The number of names is already inside the `names` array as its `.length`. Keeping that number a second time in `useState` is redundant state. The docs' name for reading `names.length` in a `const` is to **calculate during rendering**: writing a `const` in the component body that runs again every time React calls the component.

```tree caption="Count in its own state vs. count read from names.length" width=full
How the component gets count
├── !With count in its own state [useState] | **Redundant state**: the count is kept a **second time** | It changes only when a handler **calls setCount**
└── +With names.length [const] | **Calculated during rendering**: read from **names** on each render | It updates automatically whenever **names changes**
```

Now we build the first step of our team page. The team list component keeps the five players in `players`, shows a heading and a count line, and gives each player a row with a `Remove` button. Suppose we also give `count` its own state variable:

```jsx title="src/components/TeamList.jsx" bad="13"
import { useState } from 'react';

const initialPlayers = [
  { id: 0, name: 'John' },
  { id: 1, name: 'Mia' },
  { id: 2, name: 'Sara' },
  { id: 3, name: 'Leo' },
  { id: 4, name: 'Anna' },
];

export default function TeamList() {
  const [players, setPlayers] = useState(initialPlayers);
  const [count, setCount] = ~useState(initialPlayers.length)~; // **WRONG:** stores the number of players a second time in state

  function handleRemove(id) {
    ~setPlayers~(players.filter(player => player.id !== id)); // Updates players to 4 items and never calls setCount
  }

  return (
    <section>
      <h1>Team</h1>
      <p>{count} players</p>
      <ul>
        {players.map(player => (
          <li key={player.id}>
            {player.name}
            <button onClick={() => handleRemove(player.id)}>Remove</button>
          </li>
        ))}
      </ul>
    </section>
  );
}
```

Our main file renders the team list:

```jsx title="src/App.jsx"
import ~TeamList~ from './components/TeamList.jsx'; // Imports the default export of the team list file

export default function App() {
  return <TeamList />;
}
```

When the page opens, the paragraph says `5 players` above five rows. Now the user clicks `Remove` next to John. John's row disappears from the list, and the paragraph above the list still says `5 players`:

```page caption="The count line stays at 5 players after John is removed" width=text
heading: Team

No error appears in the Console, and the page now disagrees with itself: the line says `5 players` right above four players. Here is what happens on that click, in order:
1. On the first render, `players` has 5 items and `count` is `5`. The page shows `5 players` above five rows.
2. The user clicks `Remove` next to John. `handleRemove` runs with `0`.
3. `handleRemove` calls `setPlayers` with a new array of 4 items: Mia, Sara, Leo, and Anna. Nothing in `handleRemove` calls `setCount`.
4. React calls `TeamList` again. `useState` gives back the new `players` array of 4 items, and `useState` for `count` gives back the untouched `5`.
5. The JSX renders `{count} players` as `5 players`, and maps over the 4 remaining players. The count line and the list are now out of sync.

One small fix could be to add a `setCount` call inside `handleRemove`. That would patch this one button, and it would leave the trap in place. Later, when we add a button that adds a player or a button that clears the team, every new handler must also remember `setCount`. The first handler that forgets puts the bug right back on the page.

The real fix is to remove `count` from state altogether, because `players` already knows how many items it has. Before we edit `TeamList.jsx`, compare what happens in both orders when `Remove` runs first and then React calls `TeamList` to render:
- **Order 1, `Remove` runs and `count` is in `useState`**: `handleRemove` updates `players` to 4 items. Then React calls `TeamList`. `useState` returns the old `count` of `5`, so the page says `5 players`.
- **Order 2, `Remove` runs and `count` is a `const` in `TeamList`**: `handleRemove` updates `players` to 4 items. Then React calls `TeamList`. The `const` line reads `players.length` from the new 4-item array, so `count` is `4` and the page says `4 players`.

We delete the state line for `count` and replace it with a `const`:

```jsx title="src/components/TeamList.jsx" startLine="11" good="13"
export default function TeamList() {
  const [players, setPlayers] = useState(initialPlayers);
  const count = ~players.length~; // Read from players every time React calls TeamList

  function handleRemove(id) {
    setPlayers(players.filter(player => player.id !== id));
  }

  return (
    <section>
      <h1>Team</h1>
      <p>{count} players</p>
      <ul>
        {players.map(player => (
          <li key={player.id}>
            {player.name}
            <button onClick={() => handleRemove(player.id)}>Remove</button>
          </li>
        ))}
      </ul>
    </section>
  );
}
```

The JSX still writes `{count} players`, even though `count` no longer comes from `useState`: the `const` line on line 13 supplies it. Every time React calls `TeamList`, `useState` gives back the current `players`, and the `const` line reads `players.length` before the JSX runs. After the same click on `Remove`, the count line follows the list:

```page caption="Calculated from players.length: the count line updates to 4 players" width=text
heading: Team
line: 4 players | good
line: Mia [Remove]
line: Sara [Remove]
line: Leo [Remove]
line: Anna [Remove]
console:
  quiet: No errors or warnings
```

The same rule applies to text and booleans, not only to array counts. In the React docs' check-in form, storing `fullName` in state alongside `firstName` and `lastName` is redundant: `const fullName = firstName + ' ' + lastName;` calculates the full name fresh whenever either setter triggers a re-render. In the tic-tac-toe tutorial, `xIsNext` is removed from state because it can be calculated from `currentMove % 2 === 0`. As the docs sum up in Managing State, "many bugs in React apps are fixed this way."

> **Principle 1: Calculate from State During Rendering**
>
> *When a value can be computed from existing state, calculate it with a `const` during rendering instead of storing it in its own `useState`.*
>
> A count kept in its own state is redundant state: it stores a second time what the list already knows. Because it changes only when a handler remembers to call its setter, one handler that updates the list without calling `setCount` leaves the page out of sync. A `const` that reads `players.length` runs again on every render, so it always agrees with the list.
>
> **DO THIS:**
> ```jsx
> const [players, setPlayers] = useState(initialPlayers);
> const count = ~players.length~; // Recalculated on every render when players changes
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [players, setPlayers] = useState(initialPlayers);
> const [count, setCount] = ~useState(initialPlayers.length)~; // **WRONG:** changes only when every handler remembers setCount
> ```

## Principle 2: `visiblePlayers` Comes from `players` and `query`

In Principle 1, the count came from one state variable, `players`. What when a value on the page depends on **two** state variables at once? Look at the smallest version of a searchable list:

```jsx title="Two state variables and one calculated list"
const [names, setNames] = useState(['John', 'Mia', 'Sara']);
const [query, setQuery] = useState('');
const visibleNames = ~names.filter~(name => name.includes(query)); // With query 'a', holds ['Mia', 'Sara']
```

Only `names` and `query` are in `useState`. `visibleNames` is a `const` calculated from both on every render.

How do we know for sure which values belong in state and which should be calculated? In the page Thinking in React, React's docs call this the **DRY** principle, short for **Don't Repeat Yourself**. They say: "Figure out the absolute minimal representation of the state your application needs and compute everything else on-demand." They describe state as the **minimal set of changing data** that your app needs to remember, meaning the fewest values, and only the ones that change, and they give three questions to test any piece of data:
1. **Does it remain unchanged over time?** If so, it is not state.
2. **Is it passed in from a parent via props?** If so, it is not state.
3. **Can you compute it based on existing state or props in your component?** If so, it is definitely not state.

Let us run the values of our team page through those three questions:

```tree caption="Testing the values of the team page with the three questions from Thinking in React" width=full
Which values of the team page are state?
├── initialPlayers | Question 1: Does it remain unchanged over time? **Yes** | **Not state**: a constant array outside the component
├── players | Unchanged? No. Passed via props? No. Computable from other state? No. | **State**: the players currently on the team
├── query | Unchanged? No. Passed via props? No. Computable from other state? No. | **State**: what the user typed into the search box
├── !visiblePlayers | Question 3: Can you compute it from players and query? **Yes** | **Not state**: derived during rendering with filter
└── !The counts | Question 3: Can you compute them from visiblePlayers.length and players.length? **Yes** | **Not state**: derived during rendering
```

Look at the two values that pass all three questions: `players` and `query`. You cannot compute the current list of players from the search text, and you cannot compute what the user typed from the list of players. React's docs call values like these **essential state**: "Notice that these two state variables are essential, because you can't calculate either of them from the other." If you remove either one, the page can no longer do its job. Everything else in that tree is **derived**: it comes out of `players` and `query`.

Readers usually go wrong here by putting the filtered rows into a third state variable, `filteredPlayers`, and filtering inside `onChange`, because typing in the search box is the first moment they think about filtering. Compare the two ways:
- **With `filteredPlayers` in `useState`, updated inside `onChange`**: the rows on screen come from `filteredPlayers`, which is rebuilt only when the user types in the search box.
- **With `visiblePlayers` in a `const`, calculated during rendering**: the rows on screen are rebuilt from `players` and `query` on every render, whether the render was caused by typing or by clicking `Remove`.

While the user is only typing in the search box, both ways show the same filtered rows. **It may look the same, or work the same at first, but it is NOT the same thing!** Watch what happens in `TeamList.jsx` when `filteredPlayers` is kept in state and updated inside `onChange`:

```jsx title="src/components/TeamList.jsx" startLine="11" bad="14"
export default function TeamList() {
  const [players, setPlayers] = useState(initialPlayers);
  const [query, setQuery] = useState('');
  const [filteredPlayers, setFilteredPlayers] = ~useState(initialPlayers)~; // **WRONG:** stores the filtered rows in state

  function handleRemove(id) {
    ~setPlayers~(players.filter(player => player.id !== id)); // Changes players and never touches filteredPlayers
  }

  return (
    <section>
      <h1>Team</h1>
      <input
        value={query}
        onChange={e => {
          setQuery(e.target.value);
          ~setFilteredPlayers~(players.filter(player => player.name.includes(e.target.value))); // Filters only when the user types
        }}
        placeholder="Search players"
      />
      <p>Showing {filteredPlayers.length} of {players.length} players</p>
      <ul>
        {~filteredPlayers~.map(player => ( // Draws the rows from filteredPlayers in state
          <li key={player.id}>
            {player.name}
            <button onClick={() => handleRemove(player.id)}>Remove</button>
          </li>
        ))}
      </ul>
    </section>
  );
}
```

When the user types `a` into the search box, `onChange` runs and calls both `setQuery` and `setFilteredPlayers`. The list narrows to Mia, Sara, and Anna, and the line says `Showing 3 of 5 players`. So far, everything looks fine.

Now start from the freshly opened page and have the user click `Remove` next to John without typing in the search box. Look at the page after that click:

The user clicked `Remove` on John, and John is still sitting at the top of the list. Even worse, the count line now reads `Showing 5 of 4 players`: five rows shown out of four players in total. Here is what happens on that click, in order:
1. On the first render, `players` has 5 items and `filteredPlayers` has those same 5 items.
2. The user clicks `Remove` next to John. `handleRemove` runs with `0`.
3. `handleRemove` calls `setPlayers` with a 4-item array without John. Because the user did not type in the search box, `onChange` never runs, and nothing calls `setFilteredPlayers`.
4. React calls `TeamList` again. `players` now has 4 items, and `filteredPlayers` still has all 5 items, including John.
5. The paragraph reads `filteredPlayers.length`, which is `5`, and `players.length`, which is `4`, so it prints `Showing 5 of 4 players`.
6. The `<ul>` maps over `filteredPlayers`, so John's row stays on the screen even though John is already gone from `players`.

This is the same failure that hits an article dashboard when a component stores `articles`, `filterText`, `filteredArticles`, and `articleCount` all in separate `useState` hooks. A handler updates `articles` and `filteredArticles` and forgets `articleCount`, so the header says `0 results` right above a list of matching articles. Every extra state variable is one more setter that every handler can forget.

Now compare what happens in both orders when `visiblePlayers` is calculated during rendering instead:
- **Order 1, the user types `a`, then clicks `Remove` on Mia**: typing calls `setQuery` with `'a'`. React calls `TeamList`, and `players.filter` keeps the 3 players whose names contain `a`: Mia, Sara, and Anna. Next, clicking `Remove` on Mia calls `setPlayers` with a 4-item array. React calls `TeamList` again, and the same `players.filter` line runs on the new 4-item `players` array with the existing `query` of `'a'`. It keeps Sara and Anna, and the page says `Showing 2 of 4 players`.
- **Order 2, the user clicks `Remove` on Mia first, then types `a`**: clicking `Remove` calls `setPlayers` with a 4-item array. React calls `TeamList`, and `players.filter` runs with `query` still equal to `''`. Because every string contains the empty string `''`, all 4 remaining players pass the filter, and the page says `Showing 4 of 4 players`. Next, typing `a` calls `setQuery` with `'a'`. React calls `TeamList` again, and `players.filter` runs on the 4-item array with `'a'`. It keeps Sara and Anna, and the page reaches the exact same `Showing 2 of 4 players`.

No matter which action happens first, one `const` line handles both because every setter call triggers a render, and every render runs that `const` line with the latest `players` and the latest `query`.

We delete the state for the filtered list, replace it with a `const`, and return the search box to the plain controlled input of Lesson 20:

```jsx title="src/components/TeamList.jsx" startLine="11" good="14"
export default function TeamList() {
  const [players, setPlayers] = useState(initialPlayers);
  const [query, setQuery] = useState('');
  const visiblePlayers = ~players.filter~(player => player.name.includes(query)); // Rebuilt from players and query on every render

  function handleRemove(id) {
    setPlayers(players.filter(player => player.id !== id));
  }

  return (
    <section>
      <h1>Team</h1>
      <input value={query} ~onChange={e => setQuery(e.target.value)}~ placeholder="Search players" /> {/* Typing updates only query */}
      <p>Showing {visiblePlayers.length} of {players.length} players</p>
      <ul>
        {~visiblePlayers~.map(player => ( // Draws the rows from the calculated list
          <li key={player.id}>
            {player.name}
            <button onClick={() => handleRemove(player.id)}>Remove</button>
          </li>
        ))}
      </ul>
    </section>
  );
}
```

In the JSX, `visiblePlayers` now comes from line 14 right above `handleRemove`. On every render, `players.filter` runs its arrow function once for each player and keeps every player whose `name` contains `query`. Suppose the user types `a` into the search box and then clicks `Remove` on Mia. The search box holds `a`, the list shows Sara and Anna, and the count line says `Showing 2 of 4 players`:

> **Principle 2: Calculate from Multiple State Values**
>
> *Keep only the essential state variables that cannot be computed from each other, and derive every filtered list or combined count from them during rendering.*
>
> `players` and `query` are essential state: neither can be calculated from the other. `visiblePlayers` can be calculated from `players` and `query`, so storing it in a third `useState` is redundant state that updates only when the handler that calculates it runs. Computing `visiblePlayers` in the component body ensures it updates whether `setPlayers` or `setQuery` triggered the render.
>
> **DO THIS:**
> ```jsx
> const [players, setPlayers] = useState(initialPlayers);
> const [query, setQuery] = useState('');
> const visiblePlayers = ~players.filter(player => player.name.includes(query))~; // Updates when either players or query changes
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [players, setPlayers] = useState(initialPlayers);
> const [query, setQuery] = useState('');
> const [filteredPlayers, setFilteredPlayers] = ~useState(initialPlayers)~; // **WRONG:** stays stale when setPlayers runs without setFilteredPlayers
> ```

## Principle 3: Keep `captainId` in State, Not the `captain` Object

Look at two ways a component can remember which item in a list is chosen:

```jsx title="With the chosen object in state"
const names = [{ id: 0, name: 'John' }, { id: 1, name: 'Mia' }];
const [chosen, setChosen] = ~useState(names[1])~; // Stores Mia's object in a second state variable

<p>{chosen.name}</p>
```

```jsx title="With the chosen id in state"
const names = [{ id: 0, name: 'John' }, { id: 1, name: 'Mia' }];
const [chosenId, setChosenId] = ~useState(1)~; // Stores only Mia's id, 1
const chosen = ~names.find~(item => item.id === chosenId); // Looks Mia up in names on every render

<p>{chosen.name}</p>
```

The version with `chosenId` in state uses a new helper: JavaScript's array method `find`. Like `filter`, `find` calls the arrow function we pass it once for each item in the array, in order. Instead of returning an array of matches, `find` stops at the first item for which the function returns `true` and returns that single item. When no item in the array matches, `find` returns `undefined`.

On the first render, both paragraphs print `Mia`. **It may look the same, or work the same at first, but it is NOT the same thing!** Look at what lives in state in each version:
- **With the chosen object in state**, Mia's object `{ id: 1, name: 'Mia' }` is held in two state variables at once: inside the list, and again in `chosen`. React's docs call this **duplication in state**: keeping the same information in two places in state.
- **With the chosen `id` in state**, state holds the list and one number, `1`. Mia's object lives in one place only, inside the list, and `names.find` looks it up on each render.

Think of a book of team recipes. If you photocopy page 12 and tape the photocopy to the fridge, and then someone crosses out an ingredient on page 12 in the book or tears page 12 out, the photocopy on the fridge still shows the old page 12. If instead you put a bookmark at "page 12" and open the book to page 12 whenever you cook, you always see page 12 as it is right now, or you see at once that page 12 is no longer in the book. Storing `captain` as an object is the photocopy. Storing `captainId` is the bookmark.

```tree caption="Storing the chosen object in state vs. storing only chosenId" width=full
How the component remembers the chosen item
├── !With the object in state [chosen] | **Duplication in state**: Mia's object is held in **two state variables** | Removing or editing Mia in the list leaves **chosen holding the old Mia**
└── +With the id in state [chosenId] | **No duplication**: state holds only the number **1**, like a bookmark | **find** looks up item **1** in the current list on every render
```

Storing only the item's `id` and looking the item up with `find` during rendering guarantees that the page always reflects the current list.
>
> **DO THIS:**
> ```jsx
> const [players, setPlayers] = useState(initialPlayers);
> const [captainId, setCaptainId] = ~useState(null)~; // Stores only the chosen id
> const captain = ~players.find(player => player.id === captainId)~; // Looks up the object in players on every render
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [players, setPlayers] = useState(initialPlayers);
> const [captain, setCaptain] = ~useState(null)~; // **WRONG:** duplicates the chosen player object in state
> ```

## Principle 4: Copying `name` into `useState` Freezes the Captain Line

Until now, every value we examined started inside `TeamList`. What when a parent component passes a value down to a child component as a prop? Look at two versions of a tiny `Hello` child component:

```jsx title="Copying the name prop into useState"
function Hello({ name }) {
  const [shownName] = ~useState(name)~; // Reads name only on the first render of Hello
  return <p>Hello, {shownName}</p>;
}
```

```jsx title="Using the name prop directly"
function Hello({ name }) {
  return <p>Hello, ~{name}~</p>; // Reads the latest name prop on every render of Hello
}
```

Suppose the parent renders `Hello` with `"John"` first, and on a later render passes `"Mia"` to that same `Hello`:

```jsx title="The parent passes John first, and later Mia"
<Hello ~name="John"~ /> {/* First render */}
<Hello ~name="Mia"~ /> {/* Later render at the same place in the tree */}
```

On the first render, both versions show `Hello, John`. **It may look the same, or work the same at first, but it is NOT the same thing!** On the later render, the parent passes `"Mia"` as the `name` prop. The version that reads `name` directly updates to `Hello, Mia`. The version that copies `name` into `useState` stays frozen on `Hello, John`. Why? Well, as Lesson 12 taught, `useState` reads its initial value only on the first render and ignores it on every re-render after that.

React's docs call this mistake **mirroring props in state**: copying a prop into a state variable with `useState`. A real mirror reflects whatever stands in front of it right now. Putting a prop inside `useState` is like a mirror that freezes the first person who walks past it and keeps showing that first face even after someone else steps in front.

```tree caption="Copying a prop into useState vs. reading the prop directly" width=full
Inside a child component that receives a name prop
├── !With useState around the prop [shownName] | **Mirroring props in state**: reads name **only on the first render** | Stays frozen on **the first name** when the parent passes a new one
└── +With the prop read directly [name] | **Plain prop**: comes straight from the **function argument** on each render | Always shows **the latest name** the parent passed
```

Now let us move our captain line into a child component, `CaptainLine.jsx`. `TeamList` passes `captain.name` down as the `name` prop, and `CaptainLine` unpacks `{ name }`. First, watch what happens when `CaptainLine` copies `name` into `useState`:

```jsx title="src/components/CaptainLine.jsx" bad="4"

In `TeamList.jsx`, we import `CaptainLine` at the top and pass `captain.name` down as the `name` prop when `captain` exists:

```jsx title="src/components/TeamList.jsx" startLine="1"

```

```jsx title="src/components/TeamList.jsx" startLine="23"

React's docs note that mirroring a prop into state "only makes sense when you *want* to ignore all updates for a specific prop." For example, a component might start an input from a prop when it first mounts and then let the user edit that state locally regardless of what the parent renders later. In that rare case, compare these two lines:

```jsx title="With useState around name vs. around initialName"
const [shownName, setShownName] = ~useState(name)~; // Keeps the first value, and the prop name hides that fact
const [shownName, setShownName] = ~useState(initialName)~; // Keeps the first value, and the prop name states that fact clearly
```

**For React, yes, it is the exact same thing!** Both lines read the prop on the first render and ignore every later prop update. The one difference is for the human reading the code: React's docs say that by convention, you should start the prop name with `initial` or `default`, such as `initialName` or `defaultName`, to make it clear that new values of the prop are ignored on purpose. And when you later want a component with `initialName` to throw away its old state and start fresh for a different item, you change its `key`, which Lesson 25 covers in full.

React's docs illustrate the unintentional mistake with a `Clock` challenge: `Clock` receives a `color` prop from its parent and passes `props.color` into `useState`. The parent shows a `<select>` box, and the user picks a new color. Even when the prop changes from `'lightcoral'` to `'midnightblue'`, the clock stays stuck on its first color. Removing `useState` and reading `color` straight from the prop fixes the clock at once.

> **Principle 4: Do Not Mirror a Prop in State**
>
> *When a child component needs to display or calculate from a prop, read the prop directly instead of copying it into `useState`.*
>
> The initial value passed to `useState` is read only on the component's first render. Copying a prop into `useState` freezes the child component on that first prop value for as long as the component stays at the same position in the tree. Reading the prop directly ensures the child always displays the latest value from its parent.
>
> **DO THIS:**
> ```jsx
> export default function CaptainLine({ name }) {
>   return <p>Captain: ~{name}~</p>; // Updates whenever the parent passes a new name prop
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function CaptainLine({ name }) {
>   const [shownName] = ~useState(name)~; // **WRONG:** ignores every new name prop after the first render
>   return <p>Captain: {shownName}</p>;
> }
> ```

## Principle 5: `position` Holds `x` and `y` Together

Principles 1 through 4 removed values that should not be in state at all. Now look at values that **do** belong in state, and ask how they should be grouped.

When the user moves the pointer across the page, the browser gives the event object two numbers. `e.clientX` is how far the pointer is from the left edge of the browser window, and `e.clientY` is how far it is from the top edge. Every move of the pointer gives a new `clientX` and a new `clientY` at the same instant. Look at two ways to keep a red dot's position in state:

```jsx title="With x and y in two separate state variables"
const [x, setX] = useState(0);
const [y, setY] = useState(0);

~setX(e.clientX)~; // First setter call when the user moves the pointer
~setY(e.clientY)~; // Second setter call that must always run alongside setX
```

```jsx title="With x and y grouped in one position object"
const [position, setPosition] = ~useState({ x: 0, y: 0 })~; // One state object holding both coordinates

~setPosition({ x: e.clientX, y: e.clientY })~; // One setter call updates x and y together
```

Both move the dot when the pointer moves. As React's docs say in Choosing the State Structure, "Technically, you can use either of these approaches. But if some two state variables always change together, it might be a good idea to unify them into a single state variable. Then you won't forget to always keep them in sync." React's docs call this rule **group related state**: if you always update two or more state variables at the same time, merge them into a single state variable. It also applies when a form has custom fields and you do not know ahead of time how many pieces of state you will need: keeping one object in state lets you store all of those fields together.

Think of a cinema seat written as row and seat number. You never move to a new seat on the ticket without both numbers together, so the ticket prints them in one box instead of on two separate slips of paper that can get separated in your pocket.

```tree caption="Two separate state variables vs. one grouped state object" width=full
Two coordinates that always change on the same pointer move
├── With two state variables [x and y] | Every handler that moves the dot must remember **both setX and setY**
└── +With one state object [position] | **Group related state**: one **setPosition** call keeps **x** and **y** together
```

Grouping two values into one object brings one rule from Lesson 17 that you must remember whenever you update only one field of that object. Compare these two calls on `position`:

```jsx title="Passing only { x: 100 } vs. spreading position first"
~setPosition({ x: 100 })~; // **WRONG:** replaces the object with one that has no y property at all
~setPosition({ ...position, x: 100 })~; // Copies position.y over, then overwrites x with 100
```

**They look alike, but they are NOT the same thing!** Calling a state setter replaces the entire state object rather than merging fields into it. Passing `{ x: 100 }` replaces `{ x: 0, y: 0 }` with an object that has only `x`. As React's docs warn in their Pitfall box, "it would not have the `y` property at all!" On the next render, `position.y` is `undefined`. To change `x` alone on a grouped state object, spread `...position` first so `y` is copied over, or keep `x` and `y` as two separate state variables if they usually change on their own:

```tree caption="What lives inside position after each setter call" width=full
Starting from position equal to x: 0, y: 0
├── !Passing only x: 100 to setPosition | Replaces the object with **x: 100** | **position.y is now undefined**
└── +Spreading position first, then x: 100 | Copies **y: 0** from position and sets **x: 100** | **position.y stays 0**
```

In Lesson 21, we also saw the partner rule to grouping related state: **avoid contradictions in state**. When a form kept both `isSending` and `isSent` as separate booleans, forgetting to call one setter left both `true` at once, an **impossible state**, and replacing the two booleans with one `status` string made that impossible state unreachable. Together with Principles 1 through 4, that gives the first five rules of React's Choosing the State Structure page:
1. **Group related state**: merge state variables that always change together into one object or array.
2. **Avoid contradictions in state**: replace booleans that can disagree with one `status` variable, as in Lesson 21.
3. **Avoid redundant state**: do not store in state what you can calculate during rendering, as in Principles 1 and 2.
4. **Avoid duplication in state**: store an item's `id` instead of duplicating the item object, as in Principle 3.
5. **Do not mirror props in state**: read props directly unless you intentionally want only the first value, as in Principle 4.

The sixth rule handles what happens when objects in state are nested inside other objects several levels deep.

> **Principle 5: Group Related State**
>
> *When two state variables always change at the same time, merge them into one state object; when you update only one field of that object, spread the existing object first.*
>
> Keeping two values that always move together in one state object means a single setter call updates both at once. Because a state setter replaces the whole object, updating a single field on a grouped state object requires spreading `...position` first so the other fields are not wiped out to `undefined`.
>
> **DO THIS:**
> ```jsx
> const [position, setPosition] = ~useState({ x: 0, y: 0 })~; // Groups x and y into one state object
> ~setPosition({ x: e.clientX, y: e.clientY })~; // Updates both coordinates together
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [position, setPosition] = useState({ x: 0, y: 0 });
> ~setPosition({ x: 100 })~; // **WRONG:** replaces the object and erases position.y to undefined
> ```

## Principle 6: A Flat `plan` Uses `childIds` Instead of Nested Objects

Suppose a travel checklist stores places to visit: Earth contains Africa, and Africa contains Kenya. Look at the nested way to store those three places in one object:

```js title="Nested state: each place holds an array of full child objects in childPlaces"
const plan = {
  id: 0,
  title: 'Earth',
  ~childPlaces~: [{ // Earth holds the full Africa object inside childPlaces
    id: 1,
    title: 'Africa',
    ~childPlaces~: [{ id: 2, title: 'Kenya', childPlaces: [] }], // Africa holds the full Kenya object inside childPlaces
  }],
};
```

Here Kenya sits inside Africa's `childPlaces` array, and Africa sits inside Earth's `childPlaces` array.

Now compare that nested object with the flat shape from React's docs. Every place sits at the top level of one object under its own numeric `id`, and instead of holding full child objects, each place holds an array of numbers called `childIds`:

```js title="Flat state: every place sits at the top level under its id and lists childIds"
const plan = {
  0: { id: 0, title: 'Earth', ~childIds: [1]~ }, // Earth points to Africa by its id, 1
  1: { id: 1, title: 'Africa', ~childIds: [2]~ }, // Africa points to Kenya by its id, 2
  2: { id: 2, title: 'Kenya', ~childIds: []~ }, // Kenya has no child places
};
```

React's docs call the shape where every place sits at the top level under its `id` **flat** state, also known as **normalized** state. Think of how a database engineer organizes a database table so each record lives in one row under its `id`, and rows point to other rows by `id` instead of stuffing whole tables inside other tables. In computer science, organizing data that way so nothing is nested or duplicated is called **database normalization**. React's docs say this state structure "might remind you of seeing a database table," and they call the outer object keyed by `0`, `1`, and `2` **the "table" object**.

Now compare the two shapes on two questions. First, for the information they hold: **yes, it is the exact same thing!** Both say that Earth has child `1`, Africa, and Africa has child `2`, Kenya. Second, for the work of removing a deeply nested place like Kenya: **it is NOT the same thing!**
- **In the nested `plan`**, Lesson 17's rule of copying every level means that removing Kenya from Africa's `childPlaces` requires making a new Africa object with its new `childPlaces` array, and then making a new Earth object with its new `childPlaces` array, and in a deeper tree every parent level above it as well.
- **In the flat `plan`**, Africa is not stored inside Earth. Africa sits at `plan[1]` at the top of the table object. Removing Kenya `2` from Africa `1` touches only two objects: a new Africa without `2` in its `childIds`, and a new top-level `plan` table object with key `1` pointing to that new Africa.

Here is the whole update in the flat `plan` when the user checks off Kenya `2` under Africa `1`:

```js title="Removing Kenya from the flat plan in state"
const [plan, setPlan] = useState(initialTravelPlan);

const parentId = 1;
const parent = ~plan[parentId]~; // Looks up Africa's object directly at plan[1]
const nextParent = {
  ...parent,
  ~childIds: parent.childIds.filter(id => id !== 2)~, // 1. A new Africa object without Kenya's id 2 in childIds
};
setPlan(~{ ...plan, [parentId]: nextParent }~); // 2. A new table object with key 1 replaced by nextParent
```

Here `parent` comes straight from the table object by its `id` with `plan[parentId]`. Inside `setPlan`, `[parentId]` is a computed property name from Lesson 17: it writes `nextParent` under key `1` in the new table object. Earth at key `0` does not need to be copied at all, because Earth's `childIds` array `[1]` still points to `1`. No matter how many levels deep the checklist grows, removing a child from its parent copies only that one parent object and the top-level `plan` table object:

```tree caption="Removing Kenya under Africa in nested state vs. flat state" width=full
Removing Kenya with id 2 from Africa with id 1
├── !In nested state [childPlaces] | Must copy **Africa**, then copy **Earth**, and **every parent level above it**
└── +In flat state [childIds in the table object] | Copies only **Africa at plan[1]** and **the top-level plan object**
```

React's docs add three practical notes on flat state:
1. Flat state also prevents duplication when the same item appears under more than one parent, because each item object lives once in the table object and parents list only its `id` in `childIds`.
2. In a real checklist, when you remove a place from its parent's `childIds`, you can also delete that place and its children from the table object so removed items do not accumulate in memory. In the DeepDive on improving memory usage, the docs show how the **Immer** library from Lesson 17 lets you write `delete plan[id]` cleanly on a draft of the table object.
3. Sometimes you can also make state less nested by moving a piece of UI state, such as whether a single row is hovered, down into the child component that renders that row.

> **Principle 6: Avoid Deeply Nested State**
>
> *When updating deeply nested objects becomes repetitive because every parent level must be copied, flatten the state into a table object keyed by `id` where each item holds an array of `childIds`.*
>
> In a deeply nested tree, changing one item near the bottom requires copying every parent object on the path back to the root. In a flat table object where each item stores `childIds`, removing or reordering a child updates only that one parent item and the top-level table object.
>
> **DO THIS:**
> ```js
> const nextParent = { ...parent, ~childIds: parent.childIds.filter(id => id !== 2)~ }; // Copies only the direct parent
> setPlan(~{ ...plan, [parentId]: nextParent }~); // Copies only the top-level table object
> ```
>
> **DO NOT DO THIS:**
> ```js
> const plan = {
>   id: 0,
>   title: 'Earth',
>   ~childPlaces: [{ id: 1, title: 'Africa', childPlaces: [{ id: 2, title: 'Kenya', childPlaces: [] }] }]~, // **WRONG:** deep nesting forces every parent level to be copied on each nested update
> };
> ```

## Putting All Six Principles Together

Here is the complete team page in three files, `src/App.jsx`, `src/components/TeamList.jsx`, and `src/components/CaptainLine.jsx`:

```jsx title="src/App.jsx"
import TeamList from './components/TeamList.jsx';

export default function ~App~() { // 1. Called first when the page loads
  return <TeamList />;
}
```

```jsx title="src/components/TeamList.jsx" good="13,14,15,17,18"
import { useState } from 'react';
import CaptainLine from './CaptainLine.jsx';

const initialPlayers = [
  { id: 0, name: 'John' },
  { id: 1, name: 'Mia' },
  { id: 2, name: 'Sara' },
  { id: 3, name: 'Leo' },
  { id: 4, name: 'Anna' },
];

export default function ~TeamList~() { // 2. Called second, rendered by App
  const [players, setPlayers] = ~useState(initialPlayers)~; // Essential state 1: the players on the team
  const [query, setQuery] = ~useState('')~; // Essential state 2: the search text
  const [captainId, setCaptainId] = ~useState(null)~; // Essential state 3, Principle 3: only the captain's id

  const visiblePlayers = ~players.filter~(player => player.name.includes(query)); // Principle 2: derived from players and query
  const captain = ~players.find~(player => player.id === captainId); // Principle 3: derived from players and captainId

  function handleRemove(id) {
    setPlayers(players.filter(player => player.id !== id));
  }

  return (
    <section>
      <h1>Team</h1>
      <input value={query} onChange={e => setQuery(e.target.value)} placeholder="Search players" />
      <p>Showing ~{visiblePlayers.length}~ of {players.length} players</p> {/* Principle 1: counts read from .length */}
      <ul>
        {visiblePlayers.map(player => (
          <li key={player.id}>
            {player.name}
            {player.id === captainId && ' (captain)'}
            <button onClick={() => setCaptainId(player.id)}>Make captain</button>
            <button onClick={() => handleRemove(player.id)}>Remove</button>
          </li>
        ))}
      </ul>
      {captain ? <CaptainLine name={captain.name} /> : <p>No captain yet</p>}
    </section>
  );
}
```

```jsx title="src/components/CaptainLine.jsx" good="2"
export default function ~CaptainLine~({ name }) { // 3. Called third whenever captain is found
  return <p>Captain: ~{name}~</p>; // Principle 4: reads the name prop directly
}
```

When the user types `a` into the search box and clicks `Make captain` next to Mia, the search box, the count line `Showing 3 of 5 players`, the three matching rows, Mia's captain label, and the `Captain: Mia` line at the bottom all stay in sync from those three state variables:

```page caption="The finished team page after typing a and clicking Make captain on Mia" width=text
heading: Team
form:
  field: | a
line: Showing 3 of 5 players | good
line: Mia (captain) [Make captain] [Remove] | good
line: Sara [Make captain] [Remove]

line: Captain: Mia | good
console:
  quiet: No errors or warnings
```

When the page loads, React calls `App` first and `TeamList` second. Whenever `captain` is an object, React calls `CaptainLine` third. On every state change in `TeamList`, `useState` returns the current `players`, `query`, and `captainId` at the top of `TeamList`, and the `const` lines right below them compute `visiblePlayers` and `captain` before the JSX runs:

```tree caption="The three components of the team page and how every value is produced" width=full
`App` [1. Called first] | Renders `TeamList`
└── +`TeamList` [2. Called second] | **State**: `players`, `query`, `captainId` | **Calculated**: `visiblePlayers`, `visiblePlayers.length`, `players.length`, `captain`
    └── +`CaptainLine` [3. Called third when captain exists] | **Prop**: reads `name` directly with no `useState`
```

| Value on the page | Stored in `useState` or derived? | Why |
| :--- | :--- | :--- |
| **`players`** | Stored in `useState` | Essential state: changes when a player is removed, and cannot be computed from anything else |
| **`query`** | Stored in `useState` | Essential state: changes when the user types, and cannot be computed from `players` |
| **`captainId`** | Stored in `useState` | Essential state, Principle 3: stores only the chosen `id` so the player object is never duplicated |
| **`visiblePlayers`** | Derived with `players.filter` | Principle 2: computed from `players` and `query` on every render |
| **The counts `3` and `5`** | Derived from `.length` | Principle 1: read from `visiblePlayers.length` and `players.length` during rendering |
| **`captain`** | Derived with `players.find` | Principle 3: looked up from `players` and `captainId` on every render |
| **The captain line's name** | Read directly from the `name` prop | Principle 4: copying a prop into `useState` would freeze the line on the first captain |
| **`x` and `y` coordinates** | Grouped in one `position` object | Principle 5: two state values that always change on the same event belong in one object |
| **A deep tree of places** | Flattened into a table object with `childIds` | Principle 6: updates only the parent item and the top table object instead of every level |

## Summary & Interview

> **The Interview Question:** How do you decide which values belong in state and which are derived?

### Model Answer

I test every piece of data with the three questions from React's Thinking in React guide: does it stay unchanged over time, is it passed in from a parent via props, or can it be computed from existing state or props in the component? If the answer to any of the three is yes, it does not belong in `useState`. Only the **minimal set of changing data** that cannot be computed from anything else is **essential state**, such as `players`, `query`, and `captainId`. Everything else is **derived**, meaning calculated during rendering with a plain `const`, such as `visiblePlayers` from `players.filter`, `count` from `players.length`, and `captain` from `players.find`.

Keeping derived values out of `useState` prevents three classic synchronization bugs:
1. **Redundant state**: storing `count` or `filteredPlayers` in state leaves the UI out of sync whenever one handler updates `players` and forgets to call the second setter.
2. **Duplication in state**: storing a full `selectedItem` or `captain` object in state duplicates the object inside the array, so editing or removing that item in the array leaves the selected state holding stale data. Storing only `selectedId` avoids the duplicate.
3. **Mirroring props in state**: passing a prop to `useState` reads that prop only on the first render. If I intentionally want to ignore later prop updates, I prefix the prop name with `initial` or `default`, such as `initialColor`.

Finally, for values that do belong in state, I **group related state** into one object when two variables always change together, and I **flatten deeply nested state** into a normalized table object keyed by `id` with `childIds` arrays so updates do not have to copy every parent level.

### Common Follow-Up Questions

1. **"Is it not slow to recalculate a filtered list on every render?"**
   **Usually not.** Unless you are creating or looping over thousands of objects, recalculating a derived array during rendering is fast, and React's docs recommend measuring with `console.time` before optimizing. When a measured calculation is genuinely slow, you still do not move the value into `useState`: you wrap the calculation in `useMemo` so React reuses the previous result when `players` and `query` have not changed, which Lesson 56 covers. Even then, `useMemo` does not make the first render faster. In projects that use the **React Compiler**, covered in Lesson 63, expensive calculations during rendering can be cached automatically.
2. **"Why not store the derived count or filtered list in state and synchronize it inside a `useEffect`?"**
   Because an **Effect** runs **after** React has already rendered the component and put the result on the page. When `players` changes, React first renders the component with the new `players` list and the stale `count`, and then the Effect calls `setCount` and forces a second render right after. React's docs say this is more complicated than necessary, and inefficient too. Calculating `const count = players.length;` during rendering produces the right value in a single render pass. Lesson 34 covers how to replace such Effects with values calculated during rendering.
3. **"When the user can select multiple items in a list, what belongs in state?"**
   An array of selected ids, such as `[0, 2]`, or a JavaScript `Set` of ids, which is a built-in collection of unique values. Just as with a single `captainId`, you never copy the selected item objects into a second array in state. Whether a row is selected and how many rows are selected are derived during rendering from those ids, and when you keep a `Set` in state, you copy it into a new `Set` before adding or deleting an `id` and passing the new `Set` to the setter.

```tree caption="Deciding whether a value belongs in useState or is calculated during rendering" width=full
Test any value in a component
├── Does it stay the same over time? | **Not state**: keep it as a constant outside the component, such as `initialPlayers`
├── Does it come from a parent through props? | **Not state**: read the prop directly, such as `name` in `CaptainLine`
├── Can it be computed from state or props? | **Not state**: calculate it with a `const` during rendering, such as `visiblePlayers` and `captain`
└── +None of the three? | **Essential state**: store it with `useState`, such as `players`, `query`, and `captainId`
    ├── Always changes together with another state value? | **Group related state** into one object, such as `position`
    └── Nested several levels deep inside other objects? | **Flatten state** into a table object keyed by `id` with `childIds`
```
