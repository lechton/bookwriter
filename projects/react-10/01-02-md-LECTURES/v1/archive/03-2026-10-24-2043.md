# Lecture 3: JavaScript Expressions in JSX with Curly Braces
> INTERVIEW QUESTION | ❱ CORE | How do you use JavaScript expressions inside JSX with curly braces?

## Why We Use Curly Braces Inside JSX

### A card needs to show values that live in JavaScript variables

Look at any real news website: an article card shows a headline, an author name, a reading time, and a photo. Those values are almost never typed once inside the markup and left forever. Instead, they come from a database or a calculation and sit inside JavaScript variables at the top of the component.

If we type fixed words directly inside a tag, every card on the page shows the exact same headline. We need a way to keep the card's HTML tags while reading the real headline from a JavaScript variable.

```tree caption="Two ways to put text inside a component's markup: typing fixed words inside the tag vs. reading a JavaScript variable with curly braces."
How a component puts values into its markup
- !Fixed words outside curly braces [`<h2>Library Hours</h2>`] | Every card shows the **exact same text** | Cannot read values stored in **JavaScript variables**
- +Curly braces inside the markup [`<h2>{title}</h2>`] | +**DO** use curly braces to read JavaScript values | Opens a **window to JavaScript** and displays the variable's current value
```

### One variable for the headline, and curly braces to read it

First, look at what happens when a developer stores the headline in a variable, **but writes the variable's name directly inside the heading tag without curly braces**:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const title = 'Library Hours';
  return (
    <article>
      <h2>~title~</h2> {/* **WRONG:** without curly braces, JSX prints the word "title"! */}
    </article>
  );
}
```

When the file saves, the browser does not show `Library Hours`. It prints the literal word `title` on the card! Inside a tag, JSX treats every bare word as ordinary text and never checks whether a variable has that name.

Now we wrap the variable name in **curly braces**:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const title = 'Library Hours';
  return (
    <article>
      <h2>~{title}~</h2> {/* Curly braces read the variable and show "Library Hours" */}
    </article>
  );
}
```

Curly braces open a window from JSX into JavaScript. When React calls the component, JavaScript reads the variable inside the braces and puts its value, `Library Hours`, onto the card:

::: row caption="Writing a variable name as plain text vs. opening the JavaScript window with curly braces."
::: col title="Without Braces" tag="prints the word title" tone=bad
```page size=mini
card: title=title | bad=title
```
```dom title="Elements"
<article>
!  <h2>title</h2> | note: literal word between tags
</article>
```
JSX treats the word as plain text.
:::
::: col title="With Curly Braces" tag="reads the variable" tone=good
```page size=mini
card: title=Library Hours | good=title
```
```dom title="Elements"
<article>
+  <h2>Library Hours</h2> | note: variable value inserted
</article>
```
Curly braces read the variable from JavaScript.
:::
:::

### Two places where the curly-brace window can open

Inside JSX, you can open the curly-brace window in **only two places**:
1. **Between an opening tag and a closing tag**, to show text or numbers inside the element.
2. **Right after the equals sign of an attribute**, to pass a JavaScript value to that attribute.

You can never use curly braces to replace the tag name itself:

```tree caption="Every place inside JSX belongs to one of three spots: two spots where curly braces work, and one spot where they stop the build."
Where can curly braces open a window to JavaScript?
- +Spot 1: Between an opening and closing tag [`<h2>{title}</h2>`] | +**DO** use curly braces for text and numbers inside a tag | Evaluates the JavaScript variable and puts the result **inside the element**
- +Spot 2: Right after an attribute's equals sign [`src={avatarUrl}`] | +**DO** use curly braces right after `=` with no quotes | Passes the JavaScript value **directly to the attribute**
- !Spot 3: Inside the tag name itself [`<{tagName}>`] | ~Do **NOT** put curly braces in a tag name | Stops the build immediately with a **syntax error**
```

### How we inspect our card in the browser

Throughout this lesson, we grow a single `ArticleCard` component inside `src/App.jsx`, testing one rule at a time before combining all six rules at the end. As we test each step, we check three places:
- **The page viewport** shows what the visitor sees on the card.
- **The Elements panel** shows the real HTML nodes in the browser DOM.
- **The Console panel and error overlay** show any runtime or build errors.

### Six Principles of Curly Braces in JSX

**PRINCIPLES:** Every rule in this chapter follows one simple idea. Curly braces open a window from JSX to JavaScript, run the code inside when the component renders, and put the result in that spot. Because of that, six practical rules come up in daily coding and React interviews:
1. **Principle 1 — Braces Between Tags**: Words outside curly braces stay fixed text, while curly braces read JavaScript values. Putting a line break right between a braced number and the next word swallows the space between them.
2. **Principle 2 — Braces in Attributes**: Right after an attribute's equals sign, use quotation marks for fixed text or curly braces for a JavaScript value. Never wrap curly braces inside quotation marks, because the quotes turn the braces into ordinary text.
3. **Principle 3 — Expressions, Not Statements**: The build turns each JSX tag into a function call, so the code inside curly braces sits in a function argument slot. That slot accepts expressions that give back a value, and rejects statements such as `if` or `for`.
4. **Principle 4 — JSX Comments**: Because JSX lives inside JavaScript, an HTML comment stops the build and a bare double-slash line between tags prints on the page. Always wrap a block comment in curly braces: `{/* ... */}`.
5. **Principle 5 — What Values Appear on Screen**: Between tags, React displays strings and numbers, including the number zero. It displays nothing at all for `true`, `false`, `null`, and `undefined`, with zero warnings in the Console.
6. **Principle 6 — Objects and Double Curlies**: React cannot display a plain object or a `Date` object as text between tags and crashes the page if you try. Read a string or number property first, and use double curly braces `{{ ... }}` only when an attribute such as `style` expects an object.

Here is the complete overview of all six principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Braces Between Tags** | Forgetting braces prints the variable's name as text; splitting a braced number and the next word across two lines glues them together as `3min read`. | Wrap dynamic text in curly braces and keep adjacent words on the same line or insert `{' '}`. |
| **Principle 2** | **Braces in Attributes** | Wrapping curly braces in quotes on an image or button passes literal text instead of the JavaScript value and breaks the element. | Put curly braces right after `=` with no quotes, or use a template literal inside curly braces. |
| **Principle 3** | **Expressions, Not Statements** | Writing an `if` block inside curly braces stops the build with a syntax error; interviewers ask why `{}` accepts ternaries and rejects `if`. | Put only value-producing expressions inside `{}`; move `if` statements above `return` or use a ternary. |
| **Principle 4** | **JSX Comments** | Pasting an HTML comment stops the build, and writing `// note` between tags prints the note on the screen for users to see. | Write comments inside JSX as a block comment wrapped in curly braces: `{/* note */}`. |
| **Principle 5** | **What Values Appear on Screen** | Placing a boolean or a misspelled property inside curly braces leaves a silent blank spot on the page with zero Console warnings. | Convert booleans to text with a ternary, and remember that `0` prints `0` while booleans, `null`, and `undefined` print nothing. |
| **Principle 6** | **Objects and Double Curlies** | Putting a plain object, a `Date`, or accidental double braces `{{title}}` between tags crashes the whole page at runtime. | Render string or number properties between tags; use `{{ ... }}` only when passing an object to an attribute like `style`. |

## 1. Principle 1: Braces Between Tags — Open a Window to JavaScript in Text

### Plain text outside curly braces and a JavaScript value inside curly braces are two separate worlds

Between an opening tag and a closing tag, JSX gives you two separate worlds that can sit side by side on the same line:

- **In daily coding**: Words outside curly braces are copied onto the screen character for character. Words inside curly braces are evaluated as JavaScript. If you forget the braces, the variable name itself appears on the page.
- **In an interview**: Interviewers often ask how JSX mixes static words with dynamic data. Explain that curly braces switch JSX from plain text mode into JavaScript mode for that exact spot, and then switch right back after the closing brace.

Let us see how both worlds work together on a single line for the card's author:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~author~ = 'Samantha Robinson';
  return (
    <article>
      <p>By ~{author}~</p> {/* "By " stays plain text; {author} reads the variable */}
    </article>
  );
}
```

Look at the paragraph line from left to right. First, the word `By ` sits outside the curly braces, so JSX keeps it as plain text including the space after `By`. Next, the curly braces open the JavaScript window, read the variable, and put `Samantha Robinson` right after `By `.

### Why a line break next to curly braces swallows the space

Now let us add a reading time of `3` minutes. When a line of JSX gets long, a developer often puts the braced number on one line and the words `min read` on the next line:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~readTime~ = 3;
  return (
    <article>
      <p>
        ~{readTime}~
        ~min read~ {/* **WRONG:** JSX trims the line break and glues 3 to min read! */}
      </p>
    </article>
  );
}
```

When the file saves, the card shows `3min read` with no space between the number and the word! To keep multi-line markup tidy, JSX automatically strips line breaks and leading indentation between lines inside a tag.

To keep the space, place the braced number and the words on the same line:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~readTime~ = 3;
  return (
    <article>
      <p>~{readTime} min read~</p> {/* Same line keeps the space between 3 and min */}
    </article>
  );
}
```

If a line is so long that it truly must wrap across two lines, put an explicit space string inside curly braces, `{' '}`, between the two lines.

::: row caption="Splitting a braced value and plain words across two lines vs. keeping them on the same line."
::: col title="Split Across Two Lines" tag="space swallowed" tone=bad
```page size=mini
card: title=Library Hours | text=3min read | bad=text
```
JSX removes the newline between the two lines, gluing `3` and `min` together.
:::
::: col title="On the Same Line" tag="space preserved" tone=good
```page size=mini
card: title=Library Hours | text=3 min read | good=text
```
Keeping both on one line preserves the space between `3` and `min read`.
:::
:::

> [!PRINCIPLE]
> **Principle 1: Braces Between Tags: Open a Window to JavaScript Inside Text**
>
> *Between an opening tag and a closing tag, wrap any JavaScript variable or calculation in curly braces so React displays its value instead of its name.*
>
> Everything outside curly braces between tags is treated as fixed text. Everything inside curly braces runs as JavaScript when the component renders. Keep a braced value and the words next to it on the same line so JSX does not strip the space between them across a line break.
>
> **DO THIS:**
> ```jsx
> <h2>~{title}~</h2>
> <p>~{readTime} min read~</p>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <h2>~title~</h2> // **WRONG:** prints the word "title" instead of the variable!
> <p>
>   ~{readTime}~
>   ~min read~ // **WRONG:** newline swallows the space and prints "3min read"!
> </p>
> ```

## 2. Principle 2: Braces in Attributes — Use Quotes or Braces, Never Both

### Quotation marks and curly braces after an equals sign do two opposite jobs

In regular HTML, every attribute value sits inside quotation marks. When developers move to React, they often keep those quotation marks and type curly braces inside them.

- **In daily coding**: If you wrap curly braces inside quotation marks on an image or link attribute, the quotation marks win. JSX treats the curly braces as ordinary characters, and the image breaks.
- **In an interview**: State the rule in one clean line. Right after an attribute's equals sign, write **either** quotation marks for a fixed string **or** curly braces for a JavaScript value, never both together.

```tree caption="Two opposite ways to write an attribute value right after the equals sign in JSX."
What comes right after `=` on a JSX attribute?
- !Quotation marks around braces [`src="{avatarUrl}"`] | ~Do **NOT** put quotes around curly braces | The quotes turn `{avatarUrl}` into **literal text characters** | Browser requests a file named **`"{avatarUrl}"`** and shows a **broken image**
- +Curly braces alone after `=` [`src={avatarUrl}`] | +**DO** replace the quotes with curly braces | Opens the **JavaScript window** for the attribute | Passes the variable's string **`'/library.jpg'`** to the browser
```

### What happens when quotation marks wrap the curly braces

First, the developer adds the library photo at the top of the card, **but leaves quotation marks around the curly braces**:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~avatarUrl~ = '/library.jpg';
  return (
    <article>
      <img ~src="{avatarUrl}"~ alt="The city library" /> {/* **WRONG:** quotes turn the braces into text! */}
    </article>
  );
}
```

When the file saves, the photo is broken. Because the value starts with a quotation mark, JSX never opens the JavaScript window. It hands the literal twelve-character text `"{avatarUrl}"` to the browser as the image address!

Now remove the quotation marks so the curly braces sit directly after the equals sign:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~avatarUrl~ = '/library.jpg';
  return (
    <article>
      <img ~src={avatarUrl}~ alt="The city library" /> {/* Braces right after = read the variable */}
    </article>
  );
}
```

::: row caption="Wrapping curly braces in quotes on an attribute vs. placing curly braces directly after the equals sign."
::: col title="With Quotes Around Braces" tag="broken image" tone=bad
```page size=mini
card: img=broken: "{avatarUrl}" | title=Library Hours | bad=img
```
```dom title="Elements"
<article>
!  <img src="{avatarUrl}" alt="The city library"> | note: literal braces in DOM
</article>
```
The quotes turn the curly braces into ordinary characters.
:::
::: col title="With Curly Braces Alone" tag="photo loads" tone=good
```page size=mini
card: img=/library.jpg | title=Library Hours | good=img
```
```dom title="Elements"
<article>
+  <img src="/library.jpg" alt="The city library"> | note: variable value in DOM
</article>
```
Curly braces after `=` read the image address from the variable.
:::

### Joining fixed text and a variable inside an attribute

Sometimes a variable holds only part of an address, such as the file name `library`, and we need to add the folder path `/images/` and the `.jpg` ending.

In plain JavaScript, a **template literal** uses backticks and a dollar sign with curly braces to build one string from pieces:

```js title="Plain JavaScript"
const imageId = 'library';
const path = ~`/images/${imageId}.jpg`~; // Builds the string "/images/library.jpg"
```

To use that inside a JSX attribute, open the JSX curly braces right after the equals sign, and place the backtick template literal inside them:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~imageId~ = 'library';
  return (
    <article>
      <img ~src={`/images/${imageId}.jpg`}~ alt="The city library" /> {/* Builds "/images/library.jpg" */}
    </article>
  );
}
```

The same quote rule matters for on-or-off attributes such as a disabled button. Writing `disabled="false"` in quotes passes the non-empty text `"false"`, which is truthy in JavaScript and **disables** the button! Writing `disabled={false}` in curly braces passes the boolean `false` and keeps the button enabled.

> [!PRINCIPLE]
> **Principle 2: Braces in Attributes: Use Quotes for Fixed Text or Braces for JavaScript, Never Both**
>
> *Right after an attribute's equals sign, write quotation marks for a fixed string or curly braces for a JavaScript value, and never put quotation marks around curly braces.*
>
> Quotation marks tell JSX to treat everything inside them as literal text, including any curly braces. When you want an attribute to read a variable, a boolean, or a template literal, remove the quotation marks and put curly braces directly after the equals sign.
>
> **DO THIS:**
> ```jsx
> <img src=~{avatarUrl}~ alt="The city library" />
> <img src=~{`/images/${imageId}.jpg`}~ alt="The city library" />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <img src=~"{avatarUrl}"~ alt="The city library" /> // **WRONG:** quotes turn {avatarUrl} into literal text!
> <img src=~"/images/{imageId}.jpg"~ alt="The city library" /> // **WRONG:** {imageId} inside quotes is never read!
> ```

## 3. Principle 3: Expressions, Not Statements — What Fits Inside the Braces

### An expression gives back a value, while a statement only controls flow

In JavaScript, not all code does the same job. Every piece of JavaScript belongs to one of two groups:

- **An expression** is code that produces a value, such as a variable, math, a function call, or a ternary choice. Because an expression gives back a value, you can put it on the right side of `const result = ...`.
- **A statement** is code that gives instructions or controls flow, such as `if`, `for`, or `const`. A statement does not give back a value, so you can never write `const result = if ...`.

```js title="Plain JavaScript"
const wordCount = 540;
const readTime = ~Math.ceil(wordCount / 200)~; // 1. Expression: divides 540 by 200 and rounds 2.7 up to 3

const isLive = false;
const badge = ~isLive ? 'Live now' : 'Recorded'~; // 2. Ternary expression: chooses 'Recorded'
```

Look at line 5 above. The **ternary operator** asks a yes-or-no question in one expression. It checks the condition before `?`, gives back the first value when true, and gives back the value after `:` when false.

- **In daily coding**: You can put any expression inside JSX curly braces, **but putting an `if` statement or a `for` loop inside curly braces stops the build immediately**.
- **In an interview**: Interviewers often ask *why* curly braces reject `if`. Vite rewrites each JSX tag into a function call. Whatever sits inside `{ ... }` lands in a **function argument slot**, where JavaScript allows only expressions.

### Why an `if` statement inside curly braces stops the build

Let us check where the code inside curly braces goes when the build rewrites our tag into plain JavaScript:

```js title="After the build"
_jsxDEV("p", {
  children: ~Math.ceil(wordCount / 200)~ // Sits right inside a JavaScript value slot!
});
```

Because that slot is an object property inside a function call, only an expression can sit there. Watch what happens when a developer tries to write an `if` statement inside curly braces for the card's badge:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const isLive = false;
  return (
    <article>
      <span>~{if (isLive) { 'Live now' } else { 'Recorded' }}~</span> {/* **WRONG:** if is a statement! */}
    </article>
  );
}
```

The build stops right away and covers the browser with a syntax error overlay!

### Two clean ways to choose a value for JSX

We have two clean ways to choose between two values in a component.

**Way 1 — Use a ternary expression right inside the curly braces**:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~isLive~ = false;
  return (
    <article>
      <span>~{isLive ? 'Live now' : 'Recorded'}~</span> {/* Ternary expression gives back "Recorded" */}
    </article>
  );
}
```

**Way 2 — Run a normal `if` statement above `return` and put the variable in curly braces**:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const isLive = false;
  let ~badge~ = 'Recorded'; // 1. Run statements above return
  if (isLive) {
    badge = 'Live now';
  }
  return (
    <article>
      <span>~{badge}~</span> {/* 2. Read the variable inside curly braces */}
    </article>
  );
}
```

::: row caption="Writing an if statement inside curly braces stops the build; a ternary expression or an if block above return renders cleanly."
::: col title="Statement Inside `{}`" tag="build error" tone=bad
```overlay size=mini
message: [PARSE_ERROR] Unexpected token: 'if' is a statement, not an expression.
file: src/App.jsx:5:13
```
An `if` statement cannot sit inside a function argument slot.
:::
::: col title="Expression Inside `{}`" tag="renders cleanly" tone=good
```page size=mini
card: label=Recorded | title=Library Hours | good=label
```
The ternary expression evaluates to `'Recorded'` and displays the badge.
:::
:::

```tree caption="What fits inside JSX curly braces vs. what must stay above the return statement."
Code you want to use in a component
- +JavaScript expressions [`title` `wordCount / 200` `isLive ? 'Live' : 'Recorded'`] | +**DO** place inside `{ ... }` | Every expression **produces a value** | Fits cleanly into the **`_jsxDEV` argument slot**
- !JavaScript statements [`if / else` `for` `switch` `const`] | ~Do **NOT** place inside `{ ... }` | Statements **control flow** and produce no value | Run them **above `return`** and put the resulting variable in `{ ... }`
```

> [!PRINCIPLE]
> **Principle 3: Expressions, Not Statements: Put Only Value-Producing Code Inside Curly Braces**
>
> *Inside JSX curly braces, write only JavaScript expressions that produce a value; keep statements such as `if` and `for` above the `return` line.*
>
> During the build, each JSX tag is rewritten into a function call, and the code inside curly braces becomes an argument to that call. Because JavaScript only allows expressions inside function arguments, variables, math, function calls, and ternaries work inside curly braces, while `if` statements and `for` loops stop the build.
>
> **DO THIS:**
> ```jsx
> <span>~{isLive ? 'Live now' : 'Recorded'}~</span>
> <p>~{Math.ceil(wordCount / 200)}~ min read</p>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <span>~{if (isLive) { 'Live now' } else { 'Recorded' }}~</span> // **WRONG:** if statement stops the build!
> ```

## 4. Principle 4: JSX Comments — Wrap Block Comments in `{/* ... */}`

### JSX tags are JavaScript code, not an HTML file

When developers want to leave a reminder note inside a component's markup, they often forget that JSX lives inside a JavaScript file.

- **In daily coding**: If you write an HTML comment inside JSX, the build stops with a syntax error. If you write a bare double-slash comment on a line between tags, JSX treats it as plain text and prints your private developer note right on the webpage!
- **In an interview**: Remember that JSX is plain text outside curly braces. You must first open the JavaScript window with `{ ... }` and then write a JavaScript block comment `/* ... */` inside it.

### What happens with an HTML comment or a bare double-slash line

First, look at what happens when a developer writes an HTML comment inside the card:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  return (
    <article>
      <h2>Library Hours</h2>
      ~<!-- Reminder: check photo credit -->~ {/* **WRONG:** HTML comments stop the build! */}
    </article>
  );
}
```

Because this file is a JavaScript module, the build does not recognize HTML comment arrows and stops immediately.

Second, look at what happens when the developer tries a bare double-slash comment on its own line between the tags:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  return (
    <article>
      <h2>Library Hours</h2>
      ~// Reminder: check photo credit~ {/* **WRONG:** outside curly braces, this prints on the page! */}
    </article>
  );
}
```

Remember Principle 1: between tags, everything outside curly braces is plain text. So JSX prints `// Reminder: check photo credit` right on the card for every visitor to see!

### Opening the curly-brace window for a block comment

To write a real comment inside JSX, open the curly-brace window to JavaScript and place a block comment inside it:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  return (
    <article>
      <h2>Library Hours</h2>
      ~{/* Reminder: check photo credit */}~ {/* Stripped completely during the build */}
    </article>
  );
}
```

Now JavaScript strips the comment during the build, so nothing appears on the page or in the browser's Elements panel:

::: row caption="Three ways developers try to comment inside JSX: only {/* ... */} is stripped cleanly."
::: col title="HTML Comment" tag="stops build" tone=bad
```overlay size=mini
message: [PARSE_ERROR] HTML comments are not allowed in modules.
file: src/App.jsx:5:6
```
JavaScript modules reject HTML comment syntax.
:::
::: col title="Bare Double-Slash" tag="prints on page" tone=bad
```page size=mini
card: title=Library Hours | raw=// Reminder: check photo credit | bad=raw
```
Outside curly braces, the note is treated as visible text.
:::
::: col title="Braced Block Comment" tag="cleanly stripped" tone=good
```page size=mini
card: title=Library Hours | good=title
```
The curly braces open JavaScript so the block comment is removed.
:::
:::

> [!PRINCIPLE]
> **Principle 4: JSX Comments: Wrap a Block Comment Inside Curly Braces**
>
> *To leave a comment inside JSX markup, open curly braces and write a JavaScript block comment inside them: `{/* comment */}`.*
>
> JSX sits inside a JavaScript file, so HTML comments cause a build error. At the same time, text outside curly braces between tags is printed on the screen, so a bare double-slash line appears on the webpage. Wrapping a block comment in curly braces switches into JavaScript and removes the note cleanly during the build.
>
> **DO THIS:**
> ```jsx
> <article>
>   <h2>{title}</h2>
>   ~{/* Reminder: check photo credit */}~
> </article>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <article>
>   <h2>{title}</h2>
>   ~<!-- Reminder: check photo credit -->~ // **WRONG:** stops the build!
>   ~// Reminder: check photo credit~ // **WRONG:** prints on the card as visible text!
> </article>
> ```

## 5. Principle 5: What Values Appear on Screen — Strings and Numbers Show, Booleans and Empty Values Disappear

### Values that exist in JavaScript vs. values that React draws on the screen

A variable can hold a valid value in JavaScript memory and still produce nothing at all when placed between JSX tags.

- **In daily coding**: If you put a boolean variable or a misspelled property inside curly braces between tags, React leaves that spot completely blank and prints **zero warnings** in the Console.
- **In an interview**: Interviewers love to compare `<p>{0}</p>` against `<p>{false}</p>`. State the exact boundary: **strings and numbers, including `0`, always appear on the screen**, while **`true`, `false`, `null`, and `undefined` render nothing at all**.

```tree caption="What React draws on the screen when different JavaScript values sit inside curly braces between tags."
Primitive values inside `{ ... }` between tags
- +Strings and numbers [`'Library Hours'` `540` `0`] | +**Always drawn** on the screen as text | Even the number **`0`** prints **`0`** so a count of zero never disappears
- !Booleans and empty values [`true` `false` `null` `undefined`] | ~Drawn as **nothing at all** on the screen | React leaves the spot **completely blank** and logs **0 Console warnings**
```

### Why a boolean or a misspelled property leaves a silent blank spot

First, look at what happens when a developer places a boolean variable directly inside a paragraph tag to show whether an event is live:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~isLive~ = false;
  return (
    <article>
      <p>Live: ~{isLive}~</p> {/* **WRONG:** false renders nothing, leaving "Live: " blank! */}
    </article>
  );
}
```

The developer expects the card to say `Live: false`. Instead, the card shows `Live:` with nothing after it, and the Console panel stays completely quiet!

Why does React ignore `true`, `false`, `null`, and `undefined` between tags? React treats those four values as intentionally empty slots. That same rule explains why a misspelled property name is so sneaky. If you write `writer.nmae` instead of `writer.name`, JavaScript evaluates the missing property to `undefined`, and React silently draws nothing.

To display a boolean on the screen, convert it into a string with a ternary expression:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~isLive~ = false;
  return (
    <article>
      <p>Live: ~{isLive ? 'Yes' : 'No'}~</p> {/* Converts false into the visible string "No" */}
    </article>
  );
}
```

::: col title="Boolean Directly in Braces" tag="silent blank spot" tone=bad
```page size=mini
card: title=Library Hours | text=Live: | missing=missing: false renders nothing | bad=text
console: quiet
```
React draws nothing for `false` and prints zero Console warnings.
:::
::: col title="Converted to a String" tag="shows Yes or No" tone=good
```page size=mini
card: title=Library Hours | text=Live: No | good=text
console: quiet
```
The ternary turns `false` into the string `'No'`, which React draws on the card.

:::

| Value Inside `{}` Between Tags | Example in JSX | What Appears on the Page | Console Output |
| :--- | :--- | :--- | :--- |
| **String** | `<h2>{'Library Hours'}</h2>` | `Library Hours` | No warnings |
| **Number, including `0`** | `<p>{0}</p>` | `0` | No warnings |
| **Boolean `true` or `false`** | `<p>Live: {false}</p>` | `Live: ` with nothing after it | No warnings |
| **`null` or `undefined`** | `<p>By {writer.nmae}</p>` | `By ` with nothing after it | No warnings |

> [!PRINCIPLE]
> **Principle 5: What Values Appear on Screen: Strings and Numbers Show, Booleans and Empty Values Disappear**
>
> *Between JSX tags, React displays strings and numbers including zero, and displays nothing at all for `true`, `false`, `null`, or `undefined`.*
>
> Never place a boolean variable directly inside curly braces expecting the word true or false to appear on the page. Convert booleans into strings with a ternary expression, and check for property-name typos whenever a value silently disappears with no Console warning.
>
> **DO THIS:**
> ```jsx
> <p>Live: ~{isLive ? 'Yes' : 'No'}~</p>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <p>Live: ~{isLive}~</p> // **WRONG:** booleans render nothing, leaving "Live: " blank!
> ```

## 6. Principle 6: Objects and Double Curlies — Read Object Properties for Text, Use `{{ ... }}` for Object Props

### An object in memory is a container of properties, not a piece of text

In JavaScript, an object groups several named properties inside curly braces, and a `Date` is an object too.

- **In daily coding**: If you put a plain object or a `Date` object directly inside curly braces between tags, React crashes at runtime with `Objects are not valid as a React child` and blanks the whole page.
- **In an interview**: Interviewers ask two connected questions: why `<h2>{{title}}</h2>` crashes with that exact object error, and what double curly braces `{{ ... }}` actually mean on an attribute like `style={{ color: 'gray' }}`.

### Why placing an object between tags crashes the page

Suppose our card stores the author's details in an object with a `name` and a `role`. First, look at what happens when a developer places the whole object inside curly braces between paragraph tags:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~writer~ = { name: 'Samantha Robinson', role: 'Archivist' };
  return (
    <article>
      <p>By ~{writer}~</p> {/* **WRONG:** writer is an object, so React crashes at runtime! */}
    </article>
  );
}
```

As soon as the file saves, the entire page goes blank and the Console prints `Uncaught Error: Objects are not valid as a React child`! React refuses to guess which property of the object you wanted to print.

To fix the crash, read a specific string or number property from the object:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  const ~writer~ = { name: 'Samantha Robinson', role: 'Archivist' };
  return (
    <article>
      <p>By ~{writer.name}~</p> {/* Reads the string property "Samantha Robinson" */}
    </article>
  );
}
```

The exact same rule applies to two related cases:
- **A `Date` object**: Writing `new Date` creates an object, so placing `{publishedAt}` between tags crashes the page too. Call a formatting method such as `publishedAt.toLocaleDateString` inside the braces so it gives back a string.
- **Accidental double braces between tags**: Writing `<h2>{{title}}</h2>` also crashes with `Objects are not valid as a React child`! The outer braces open JavaScript, and the inner `{title}` creates a JavaScript object `{ title: title }` and hands that object to the heading tag.

### Where double curly braces `{{ ... }}` actually belong

When **do** we write double curly braces in React? We write them when an attribute expects a JavaScript object, such as the `style` attribute for inline CSS:

```jsx title="App.jsx" startLine="1"
export default function ArticleCard() {
  return (
    <article>
      <p ~style={{ color: 'gray' }}~>Published 10/15/2026</p> {/* Outer {} opens JS; inner {} is the style object */}
    </article>
  );
}
```

Double curly braces are not a special JSX syntax. They are simply two ordinary pairs of braces nested one inside the other:
1. **The outer braces `style={ ... }`** open the JSX attribute window to JavaScript.
2. **The inner braces `{ color: 'gray' }`** create a normal JavaScript object and hand it to `style`.

```tree caption="Why double curly braces crash between tags yet work on an attribute that expects an object."
What double curly braces `{{ ... }}` do in two different places
- !Between tags [`<h2>{{title}}</h2>`] | ~Do **NOT** put an object between tags | Outer `{}` opens JS, and inner `{title}` creates an **object** | Crashes at runtime with **`Objects are not valid as a React child`**
- +On an object attribute [`style={{ color: 'gray' }}`] | +**DO** use when an attribute expects an object | Outer `{}` opens the **JSX attribute window** | Inner `{ color: 'gray' }` passes the **CSS object** to `style`
```

::: row caption="Placing a raw object between tags crashes the page; reading a string property and passing an object to style={{ ... }} renders cleanly."
::: col title="Object Between Tags" tag="runtime crash" tone=bad
```page size=mini
blank
error: Uncaught Error: Objects are not valid as a React child.
```
React cannot turn a plain object or a `Date` object into text on its own.
:::
::: col title="Property in Text + Object in `style`" tag="renders cleanly" tone=good
```page size=mini
card: title=Library Hours | author=By Samantha Robinson | text=Published 10/15/2026 | good=title,author,text
quiet: Console: no warnings
```
Reading `writer.name` gives a string, and `style={{ color: 'gray' }}` passes an object to `style`.
:::

> [!PRINCIPLE]
> **Principle 6: Objects and Double Curlies: Read Object Properties for Text, Use `{{ ... }}` for Object Props**
>
> *Never place an object or a `Date` between JSX tags; read a string or number property for text, and use `{{ ... }}` only for object attributes like `style`.*
>
> React cannot display an object as text and throws a runtime error that blanks the page if an object or `Date` sits between tags. Double curly braces are simply an object literal sitting inside the JSX attribute window, which is why they belong on attributes like `style` and never around text children.
>
> **DO THIS:**
> ```jsx
> <p>By ~{writer.name}~</p>
> <p style=~{{ color: 'gray' }}~>
>   Published ~{publishedAt.toLocaleDateString('en-US')}~
> </p>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <h2>~{{title}}~</h2> // **WRONG:** inner {title} creates an object and crashes!
> <p>By ~{writer}~</p> // **WRONG:** plain object crashes as a child!
> <p>Published ~{publishedAt}~</p> // **WRONG:** Date object crashes as a child!
> ```

```jsx title="src/App.jsx" startLine="1"
  const imageId = 'library';
```

## For the Interview

> **The Interview Question:** How do you use JavaScript expressions inside JSX with curly braces?

### How to Answer Clearly in 30 Seconds

"In JSX, curly braces open a window to JavaScript in two places: between tags for child content, and right after an attribute's `=` sign for prop values. Anything outside curly braces is treated as fixed text, so wrapping braces in quotes like `src="{url}"` passes the literal string `"{url}"` instead of reading the variable.

Because the build rewrites each JSX tag into a function call, everything inside `{}` lands in a function argument slot. Curly braces therefore accept any JavaScript expression that produces a value, such as a variable, math, a template literal, or a ternary, plus `{/* ... */}` block comments. They cannot hold statements like `if` or `for`, which belong above `return`.

When curly braces sit between tags, React renders strings and numbers including `0`, and renders nothing for `true`, `false`, `null`, and `undefined`. Passing a plain object or a `Date` between tags throws a runtime error. Double curly braces like `style={{ color: 'gray' }}` simply nest a JavaScript object literal inside the JSX attribute window."

### Four Classic Follow-Up Questions Interviewers Ask

1. **"Can you use curly braces to pick a dynamic tag name like `<{tagName}>Hello</{tagName}>`?"**
   **No.** Curly braces only open a JavaScript window between tags or after an attribute's `=` sign. To render a dynamic tag name, store the tag string or component in a capitalized variable such as `const Tag = tagName` above `return`, and render `<Tag>Hello</Tag>`.
2. **"Why does `<p>{0}</p>` print `0` on the screen while `<p>{false}</p>` prints nothing?"**
   `0` is a number, and React renders every number as a text node so quantities like `0` items or a score of `0` never disappear. Booleans `true` and `false`, along with `null` and `undefined`, are treated as empty placeholders that render nothing.
3. **"Why does `<h2>{{title}}</h2>` crash with `Objects are not valid as a React child`?"**
   The outer curly braces open the JavaScript window, and the inner `{title}` uses property shorthand to create a plain object `{ title: title }`. Because that plain object sits between `<h2>` and `</h2>` as a child, React throws a runtime error and blanks the page.
4. **"What is the difference between `disabled="false"` and `disabled={false}` on a `<button>`?"**
   `disabled="false"` uses quotation marks, so it passes the non-empty string `"false"`, which is truthy in JavaScript and disables the button. `disabled={false}` opens the JavaScript window and passes the boolean `false`, which keeps the button enabled.

```tree dir=right caption="Interview summary: what every JavaScript value does when placed inside { ... } between JSX tags."
Values inside `{ ... }` between JSX tags
- +String or Number [`'Library Hours'` `540` `0`] | Rendered on screen as a **DOM text node** | Even **`0`** always prints **`0`**
- ~`true`, `false`, `null`, `undefined` [`{isLive}` `{writer.nmae}`] | Rendered as **nothing at all** with **0 Console warnings** | Convert booleans to strings with a **ternary**
- !Plain Object or `Date` [`{writer}` `{publishedAt}` `{{title}}`] | Crashes with **`Objects are not valid as a React child`** | Read a **primitive property** or format the **`Date`** to a string
```
