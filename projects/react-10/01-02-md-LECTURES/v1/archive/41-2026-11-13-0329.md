> INTERVIEW QUESTION | ❱ CORE | What is the action prop on a form, and how do actions modernize form handling?

## How a Form Hands Its Data to a Function

### `action` with a URL vs. `action` with a function

A `<form>` tag has had an `action` attribute since the first days of HTML. In plain HTML, `action` holds a URL. In React 19, the same `action` can also hold a function:

```jsx title="The same action attribute, holding a URL and holding a function"
<form ~action="/send"~></form> {/* 1. A URL: the browser sends the form data to /send and loads a new page */}
<form ~action={sendMessage}~></form> {/* 2. A function: React calls sendMessage with the form data, and the page stays */}
```

It may look the same, but it is NOT the same thing! Both tags use the same attribute, and both decide what happens when the user clicks Send. The difference is who receives the form data:
- **With a URL**, the browser receives it. The browser sends the data to the server, leaves our page, and shows the server's answer as a brand-new page. Everything React kept in memory is gone.
- **With a function**, React receives it. React calls our function, and the browser never leaves the page. Our component keeps running, with its state in place.

The data itself is nothing new. Yes, it is the exact same thing as in Lesson 40: a `FormData` object, and `formData.get('message')` reads the text of the box named `message`. The only change is who builds it. With `onSubmit`, our code builds it with `new FormData(e.target)`. With `action`, React builds it and passes it in.

React's docs call a function like `sendMessage` an **action**. In everyday English, an action is something you do. Here, it is the function that does the work of the form when the user submits it.

```tree caption="The action attribute on a form, holding a URL in plain HTML and holding a function in React 19."
Two things the `action` attribute on a `<form>` can hold
- !A URL, plain HTML [`action="/send"`] | The **browser** sends the form data to a server address | The browser **loads a new page**, and React state is lost
- +A function, React 19 [`action={sendMessage}`] | **React** calls the function with the form data | The **page stays**, and the component keeps its state
```

The key idea to remember: **the `action` prop takes a function that receives the form data.** There is no event, no `e.preventDefault()`, and no `new FormData(...)`.

### What is at stake

Picture the message box of a chat. The user types `Hi` and clicks Send. Every chat user expects two things: `Hi` appears in the conversation, and the box is empty again.

With `onSubmit`, our code has two jobs on top of adding the message, and each one is easy to miss:
1. **Stopping the reload.** When the developer forgets `e.preventDefault()`, the browser sends the form to the current address and reloads the page. The app starts again from zero, so the conversation goes back to its first message, and `Hi` is gone.
2. **Emptying the box.** When the send works, the box still shows `Hi`. Nothing empties it until our code empties it.

With the `action` prop, the page does not reload, and the box is empty after a successful send. Our code writes neither of those two jobs.

Readers usually go wrong in one place. They read `action` as one more event handler, like `onSubmit`, and write `function sendMessage(e) { e.preventDefault(); }`. The first parameter of an action is not an event. It is the form data.

### Three Principles of the action Prop

**PRINCIPLES:** When a form holds a function in its `action` prop, React takes over the submit. React calls our function with the form data, empties the boxes after the function succeeds, and waits for the function when it needs time. Three practical principles follow:
1. **`action={sendMessage}` Receives the Form Data**: React calls the function with one argument, the form data, and the page does not reload. The function needs no event, no `e.preventDefault()`, and no `new FormData(e.target)`.
2. **The Message Box Empties After Send**: After the action succeeds, React resets every uncontrolled box in the form. A controlled box keeps showing its state.
3. **An `async` Action Empties the Box After `await`**: The action may wait for a server. React waits with it, keeps the page usable, and empties the box only when the action has succeeded.

Here is the complete map of those three principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`action={sendMessage}` Receives the Form Data** | An old `onSubmit` handler moved to `action` unchanged calls `e.preventDefault()` on a `FormData` object. JavaScript throws an error, and the chat disappears from the page. | Pass a function to `<form action>`. Its only parameter is the form data. Read each box with `formData.get` and the box's `name`. |
| **Principle 2** | **The Message Box Empties After Send** | A controlled box keeps the sent text after Send, so the developer writes `setText('')` by hand, work that an uncontrolled box never needs. | Keep the boxes of an action form uncontrolled, with a `name` only. React resets them after the action succeeds. |
| **Principle 3** | **An `async` Action Empties the Box After `await`** | Developers write an `isSending` state by hand next to every form, although React already tracks the wait of every action. | Write `async` in front of the action and `await` the server. React waits for the action and resets the form when it ends without an error. |

## 1. Principle 1: `action={sendMessage}` Receives the Form Data

### The same Send form with `onSubmit` and with `action`

Here is one Send form written two ways. Both read the text of the box and show it in an alert. With `action`, three lines of the `onSubmit` version disappear:

```jsx title="Sending the message with onSubmit"
function handleSubmit(~e~) { // 1. React passes the submit event
  ~e.preventDefault();~ // 2. Our code stops the browser from reloading the page
  const formData = ~new FormData(e.target)~; // 3. Our code builds the form data from the form
  alert(formData.get('message'));
}

<form onSubmit={handleSubmit}>
  <input name="message" />
  <button type="submit">Send</button>
</form>
```

```jsx title="Sending the message with action"
function sendMessage(~formData~) { // React passes the form data itself
  alert(formData.get('message'));
}

<form ~action={sendMessage}~> {/* React calls sendMessage when the user clicks Send */}
  <input name="message" />
  <button type="submit">Send</button>
</form>
```

For the data, yes, it is the exact same thing! When the user types `Hi` and clicks Send, both alerts show `Hi`. For the code, it is NOT the same thing. With `action`, React handles the submit event itself, so our function gets no event and has nothing to call `e.preventDefault()` on.

### Where did `formData` come from?

React creates it. Our code never does. Here is what happens when the user submits the form:
1. The user clicks Send.
2. React collects every box of the form by its `name` into one `FormData` object.
3. React calls `sendMessage` with that object as its only argument.

The page does not reload either, although no line of our code stops the reload. When `action` holds a function, React handles the submit, and the browser never loads a new page.

### Building the chat with `action`

Now we build the chat. The list comes from `messages` in state, and each new message gets its ID from `nextId` above the component (as seen in Lesson 19):

```jsx title="src/components/ChatRoom.jsx" startLine="1"
import { useState } from 'react';

const initialMessages = [{ id: 1, text: 'Hello there!' }];
let nextId = 2;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);

  function sendMessage(~formData~) { // 1. React calls this on Send, with the form data
    setMessages([...messages, { id: nextId++, text: ~formData.get('message')~ }]); // 2. Adds the typed text to the list
  }

  return (
    <section>
      <ul>
        {messages.map(m => <li key={m.id}>{m.text}</li>)}
      </ul>
      <form ~action={sendMessage}~> {/* 3. Hands sendMessage to React, not to the browser */}
        <input name="message" />
        <button type="submit">Send</button>
      </form>
    </section>
  );
}
```

`App` renders the chat:

```jsx title="src/App.jsx" startLine="1"
import ChatRoom from './components/ChatRoom.jsx';

export default function App() {
  return ~<ChatRoom />~; // React calls ChatRoom and puts the list and the form on the page
}
```

The user types `Hi` in the box and clicks Send. `Hi` joins the list, and the page stays:

```page caption="The chat after the user types Hi and clicks Send: Hi joins the list, and the page does not reload."
line: Hello there!
line: Hi | good
form:
  field: |
  submit: Send
console: quiet
```

The box in this preview is already empty again. Principle 2 explains who emptied it.

### The mistake: moving the old `onSubmit` handler into `action`

A developer who knows `onSubmit` well moves the old handler into `action` without changing it:

```jsx title="src/components/ChatRoom.jsx" startLine="9"
function sendMessage(~e~) { // **WRONG:** React passes the form data here, not an event
  ~e.preventDefault();~ // **WRONG:** FormData has no preventDefault, so JavaScript throws a TypeError
  const formData = new FormData(e.target);
  setMessages([...messages, { id: nextId++, text: formData.get('message') }]);
}
```

The user clicks Send, and the whole chat disappears from the page. Here is what happens, in order:
1. React calls `sendMessage` with the form data, so the parameter named `e` holds a `FormData` object, not an event.
2. A `FormData` object has no `preventDefault`, so JavaScript throws an error on the first line of `sendMessage`.
3. React sends an error thrown by an action to the nearest error boundary, the component that catches an error and shows a fallback screen (as seen in Lesson 38).
4. Our page has no error boundary, so React removes the whole page from the screen.

```page caption="The chat after the user clicks Send when the action still calls e.preventDefault: nothing is left on the screen."
blank
console: Uncaught TypeError: e.preventDefault is not a function
  warn: An error occurred in the <form> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The user sees neither the list nor the box, and the message is lost. The fix is to name the parameter for what it is, `formData`, and to delete the lines with `e.preventDefault()` and `new FormData(e.target)`.

> [!PRINCIPLE]
> **Principle 1: The action Prop: React Calls the Function with the Form Data**
>
> *Pass a function to `<form action>`; when the user submits the form, React calls it with one argument, the form data, and the page does not reload.*
>
> A form that sends its data with `onSubmit` must stop the reload and build the form data by hand. With a function in `action`, React handles the submit event, builds the `FormData` object from the `name` of every box, and passes it in. The action never sees an event, so a leftover `e.preventDefault()` throws an error and the page goes blank.
>
> **DO THIS:**
> ```jsx
> function sendMessage(~formData~) { // React passes the form data
>   setMessages([...messages, { id: nextId++, text: formData.get('message') }]);
> }
> <form action={sendMessage}>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function sendMessage(e) {
>   ~e.preventDefault();~ // **WRONG:** e is the form data, and FormData has no preventDefault!
> }
> <form action={sendMessage}>
> ```

## 2. Principle 2: The Message Box Empties After Send

### The box with `onSubmit` vs. the box with `action`

Picture our chat written two ways. The form with `onSubmit` uses `handleSubmit` from Principle 1, with the `alert` line replaced by the same `setMessages` line that `sendMessage` has. The form with `action` uses `sendMessage`. Both forms hold the same box, `<input name="message" />`, with no `value`, so both boxes are uncontrolled (as seen in Lesson 20). The user types `Hi` in each box and clicks Send:

```jsx title="ChatRoom.jsx"
  <input name="message" />

```

::: col title="Form with action" tag="empty again" tone=good

```jsx title="ChatRoom.jsx"
  <input name="message" />
```

It may look the same at first, but it is NOT the same thing! Both forms add `Hi` to the list. But after Send, the form with `onSubmit` still shows `Hi` in the box, and the form with `action` shows an empty box.

For the user, this matters. A chat box that keeps the sent text invites a second click on Send, and the same message goes out twice.

### Who empties the box?

React does. No line of our code empties the box. Here is what happens after the user types `Hi` and clicks Send:
1. React calls `sendMessage` with the form data.
2. `sendMessage` adds `Hi` to `messages` and ends without an error.
3. React **resets** the form: every uncontrolled box goes back to its starting value. Our box started empty, so it is empty again.
4. The list shows `Hi`, and the box is ready for the next message.

React's docs promise it in one sentence: "After the action function succeeds, all uncontrolled field elements in the form are reset." With `onSubmit`, React does no reset, so our code must call the form's own `reset()` method by hand, `e.target.reset()`.

### The mistake: a controlled box inside an action form

A developer makes every box controlled by habit (as seen in Lesson 20), and adds a `text` state to `ChatRoom`:

```jsx title="src/components/ChatRoom.jsx" startLine="8"
const [text, setText] = useState('');
```

```jsx title="src/components/ChatRoom.jsx" startLine="19"
<form action={sendMessage}>
  <input
    name="message"
    ~value={text}~ // **WRONG:** React resets only uncontrolled boxes, so this box keeps showing text
    onChange={e => setText(e.target.value)}
  />
  <button type="submit">Send</button>
</form>
```

The user types `Hi` and clicks Send. `Hi` appears in the list, but the box still shows `Hi`. Why? Well, the box shows only what `text` holds, and nothing changed `text`. React resets only the uncontrolled boxes of the form, and this box is controlled.

```page caption="The chat after Send when the message box is controlled with value and onChange: the box still shows Hi."
line: Hello there!
line: Hi
form:
  field: | Hi | bad
  submit: Send
console: quiet
```

The developer then adds `setText('')` inside `sendMessage`, one more line of work that the uncontrolled box never needed. The simpler fix is to delete `text`, `value`, and `onChange`, and to keep only `name="message"` on the box.

> [!PRINCIPLE]
> **Principle 2: The Automatic Reset: React Empties Uncontrolled Boxes After the Action Succeeds**
>
> *After the function in `action` succeeds, React resets every uncontrolled box in the form; a controlled box keeps showing its state.*
>
> A chat box that still shows the sent text invites the user to send it twice. With `onSubmit`, our code must empty the box itself. With a function in `action`, React resets the form after the action ends without an error, so a box with only a `name` is empty again. A box with `value` shows what state holds, so React's reset cannot empty it.
>
> **DO THIS:**
> ```jsx
> <form action={sendMessage}>
>   ~<input name="message" />~ {/* Uncontrolled: React empties it after Send */}
> </form>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <form action={sendMessage}>
>   <input name="message" ~value={text}~ onChange={e => setText(e.target.value)} /> {/* **WRONG:** controlled, so the box still shows Hi after Send */}
> </form>
> ```

## 3. Principle 3: An `async` Action Empties the Box After `await`

### A function that waits: `async` and `await`

A real chat sends each message to a server first, and the server takes time to answer. We have no real server, so we write the stand-in in a new file, `src/api.js`. It waits one second and then gives the text back:

```js title="src/api.js" startLine="1"
export ~async~ function deliverMessage(text) { // async: this function may wait inside
  ~await~ new Promise(resolve => setTimeout(resolve, 1000)); // await: pauses here for one second
  return text; // Runs only after the wait
}
```

JavaScript gives us two words for a function that waits:
1. **`async`**, written in front of `function`, says that the function may wait inside. Calling such a function always gives back a promise (as seen in Lesson 33).
2. **`await`**, written in front of a promise, pauses the function at that line until the promise is done. Then it gives back the value inside the promise.

A function in `action` may be `async` too. React then waits for it. React counts the action as finished only when the promise it returns is done.

### The chat waits for the server

Now `sendMessage` becomes `async`. It builds the new message, waits for the server, and only then adds the message to the list:

```jsx title="src/components/ChatRoom.jsx" startLine="1"
import { useState } from 'react';
import { deliverMessage } from '../api.js';

const initialMessages = [{ id: 1, text: 'Hello there!' }];
let nextId = 2;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);

  ~async~ function sendMessage(formData) { // 1. React waits for this action until its promise is done
    const message = { id: nextId++, text: formData.get('message') }; // 2. Builds the message once, before the wait
    ~await deliverMessage(message.text)~; // 3. Pauses here for one second
    setMessages(~m => [...m, message]~); // 4. Adds the message to the newest list
  }
```

The rest of `ChatRoom.jsx` stays the same. Two lines change, and each one has a reason:
1. **The updater `m => [...m, message]`.** Inside `sendMessage`, `messages` is the list from the moment of the click (as seen in Lesson 15). Suppose the user sends a second message during the wait. Both calls of `sendMessage` then start from the same old list, and the second message would push the first one out of the list. The updater gets the newest list from React instead (as seen in Lesson 16), so both messages stay.
2. **The message is built before `await`, outside the updater.** `<StrictMode>` calls an updater twice, so `nextId++` inside it would use up two IDs for one message (as seen in Lesson 14).

### What the user sees during the second

For one second after Send, the page seems to do nothing: the box still shows `Hi`, and the list does not show it yet. Here is what happens, in order:
1. The user types `Hi` and clicks Send.
2. React calls `sendMessage` with the form data.
3. `sendMessage` reaches `await deliverMessage(...)` and pauses for one second.
4. The promise is done. `setMessages` adds `Hi` to the list.
5. `sendMessage` ends without an error, so React resets the form, and the box is empty.

::: row caption="The chat during the one second wait after Send, and after the stand-in server answers."
::: col title="During the wait" tag="box still shows Hi"
```page size=mini
line: Hello there!
form:
  field: | Hi
  submit: Send
console: quiet
```
:::
::: col title="After the wait" tag="Hi sent, box empty" tone=good
```page size=mini
line: Hello there!
line: Hi | good
form:
  field: | | good
  submit: Send
console: quiet
```
:::
:::

The box empties only after the action succeeds. So the text stays in front of the user while the server is still working.

During that second, the page stays usable: the user can still scroll, click, and type. React runs every action in a **Transition**, React's word for an update that does not block the page. React also keeps a record that this action has started and has not ended yet. React's docs call it the **pending state** of the action.

### The mistake: tracking the wait by hand

A developer who tracked the state of a form by hand (as seen in Lesson 21) brings the same habit to the action:

```jsx title="src/components/ChatRoom.jsx" startLine="9"
const [isSending, setIsSending] = useState(false);

async function sendMessage(formData) {
  ~setIsSending(true)~; // **WRONG:** React already tracks the pending state of every action
  const message = { id: nextId++, text: formData.get('message') };
  await deliverMessage(message.text);
  setMessages(m => [...m, message]);
  ~setIsSending(false)~; // **WRONG:** the second line to copy next to every form
}
```

This works, but the developer now copies the same state and the same two lines into every form of the app. React already tracks this pending state for every action. Two React Hooks read it in the next lessons: `useActionState` in Lesson 42, and `useFormStatus` in Lesson 43, which lets a Send button show `Sending...`.

> [!PRINCIPLE]
> **Principle 3: The async Action: React Waits, Then Resets the Form**
>
> *The function in `action` may be `async`; React waits for its promise, runs it in a Transition, and resets the form only after it succeeds.*
>
> A real chat must wait for the server before the message counts as sent. With `async` and `await`, the action pauses until the server answers. React waits with it, keeps the page usable, tracks the pending state, and empties the box only after the action ends without an error.
>
> **DO THIS:**
> ```jsx
> ~async~ function sendMessage(formData) { // React waits for this action, then empties the box
>   const message = { id: nextId++, text: formData.get('message') };
>   await deliverMessage(message.text);
>   setMessages(m => [...m, message]);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> async function sendMessage(formData) {
>   ~setIsSending(true)~; // **WRONG:** a hand-written copy of the pending state React already tracks
>   await deliverMessage(formData.get('message'));
>   setIsSending(false);
> }
> ```

## Putting All 3 Principles Together

### The complete project

Here is the finished chat. The stand-in server waits one second, and the chat sends each message through an `async` action:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

```jsx title="src/App.jsx"
import ChatRoom from './components/ChatRoom.jsx';

export default function App() {
  return <ChatRoom />;
}
```

```js title="src/api.js"
export async function deliverMessage(text) {
  await new Promise(resolve => setTimeout(resolve, 1000));
  return text;
}
```

```jsx title="src/components/ChatRoom.jsx"
import { useState } from 'react';
import { deliverMessage } from '../api.js';

const initialMessages = [{ id: 1, text: 'Hello there!' }];
let nextId = 2;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);

  ~async~ function sendMessage(~formData~) { // Principles 1 and 3: React passes the form data and waits
    const message = { id: nextId++, text: formData.get('message') };
    await deliverMessage(message.text);
    setMessages(m => [...m, message]);
  }

  return (
    <section>
      <ul>
        {messages.map(m => <li key={m.id}>{m.text}</li>)}
      </ul>
      <form ~action={sendMessage}~> {/* Principle 1: React handles the submit */}
        ~<input name="message" />~ {/* Principle 2: uncontrolled, so React empties it after Send */}
        <button type="submit">Send</button>
      </form>
    </section>
  );
}
```

### What React does when the user clicks Send

When the page loads, React calls `App`, then `ChatRoom`. When the user clicks Send, React handles the submit, calls the action, waits for it, and resets the form:

```tree dir=right caption="The order of events in our chat, from the first render to the empty box after Send."
From the first render to the empty box
- +1. First render [`App` then `ChatRoom`] | The list shows **`Hello there!`** | The box is **empty**
- +2. The user clicks Send | React builds the **form data** | React calls **`sendMessage`** in a Transition
- +3. The action waits [`await deliverMessage`] | One second **with no change** on the page | The box still shows **`Hi`**
- +4. The action succeeds | `setMessages` adds **`Hi`** to the list | React **resets the form**, and the box is empty
```

| Aspect | The `onSubmit` Way | The `action` Way |
| :--- | :--- | :--- |
| **What the function receives** | The submit event `e`; our code builds `new FormData(e.target)` | The form data itself, a `FormData` object |
| **The page reload** | Our code must call `e.preventDefault()` | React handles the submit, so the page never reloads |
| **The box after Send** | Keeps the sent text until our code empties it | Empty again, because React resets uncontrolled boxes after success |
| **Waiting for a server** | Our code tracks the wait with an `isSending` state | React waits for the `async` action and tracks its pending state |

## For the Interview

> **The Interview Question:** What is the action prop on a form, and how do actions modernize form handling?

### How to Answer Clearly in 30 Seconds

"In plain HTML, a form's `action` holds a URL, and submitting the form loads a new page. In React 19, `action` can hold a function instead. When the user submits the form, React calls that function with one argument, the form data, as a `FormData` object. Actions replace three pieces of manual work:
1. **The submit event**: there is no event, no `e.preventDefault()`, and no `new FormData(e.target)`, and the page does not reload.
2. **The reset**: after the action succeeds, React resets every uncontrolled box in the form, so a chat box is empty after Send.
3. **The waiting**: the action can be `async`. React waits for it in a Transition, keeps the page usable, and tracks its pending state, so we no longer write an `isSending` state by hand."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Should we still use `onSubmit`?"**
   It still works in every version of React, and it gives you the submit event itself. React's docs list what an `action` adds on top of it, which is why, for a new React 19 form, `action` does more of the work:
   1. It runs in a Transition and tracks the pending state.
   2. It sends a thrown error to the nearest error boundary.
   3. It works with `useActionState`, and with `useOptimistic`, which shows a message before the server confirms it, in Lesson 44.
   4. It can be a Server Function, which `onSubmit` cannot be. Lesson 110 covers Server Functions.
2. **"What can an action return?"**
   A plain form action may return a promise, because it may be `async`. React waits for that promise before it resets the form. React gives the returned value no use on a plain `<form action>`. When the page must show a result, such as an error line after a failed send, the action is wrapped in `useActionState`, and the value it returns becomes the new state. Lesson 42 covers it.
3. **"Why did my box not empty after Send, and how do I stop a box from emptying?"**
   React resets only uncontrolled boxes, and only after the action succeeds. A box with `value` and `onChange` shows what state holds, so it keeps the sent text. When a reset is not wanted, such as in a search box, Lesson 45 shows how to keep the text.
