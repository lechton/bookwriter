# Lecture 20: Controlled Inputs: Letting State Decide What Every Box Shows
> INTERVIEW QUESTION | ❱ CORE | How do you make an input, textarea, or select fully controlled by React state?

---

## Why a Form Needs Its Text in State

### The smallest controlled box: a name, a greeting, and a Clear button

In Lesson 12, a button and a piece of state worked together. A click called the setter, the setter changed the state, and the page showed the new state. Now we add a text box to that picture. Here is a small page with a Name box, a greeting under it, and a Clear button. When the page opens, the Name box is empty:

```page width=text caption="The name page when it opens: an empty Name box, a greeting, and a Clear button."
form:
  field: Name |
line: Hello,
form:
  button: Clear
```

This is the whole component:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [name, setName] = useState('');

  return (
    <main>
      <label>
        Name
        <input value={name} onChange={e => setName(e.target.value)} />
      </label>
      <p>Hello, {name}</p>
      <button ~onClick={() => setName('')}~>Clear</button> {/* Clear changes only the state */}
    </main>
  );
}
```

The user types John into the Name box, and the greeting follows the box letter by letter, until it says Hello, John:

```page width=text caption="The same page after the user types John into the Name box."
form:
  field: Name | John | good
line: Hello, John | good
form:
  button: Clear
```

Then the user clicks the Clear button, and the Name box and the greeting are both empty again:

```page width=text caption="The same page after the user clicks Clear: the box and the greeting are both empty."
form:
  field: Name | | good
line: Hello,
form:
  button: Clear
```

Take another look at the code for the Clear button. As always in React, the story starts with state. We declare a variable, `name`, alongside its inseparable twin, `setName`, the function built to update it. They always travel as a pair, with a strict division of labor. When we want to show the name on the screen, we read `name`; when we need to change it, we call `setName`.

- **`name`**: Use it to read and display the current name.
- **`setName`**: Use it to update the name.

Right out of the gate, `name` holds an empty string. Everywhere the page references `name`, it renders nothing. The Name box is wired directly into this system: because its `value` is bound to `name`, the box starts out completely blank too.

Now, think about how the browser listens to you. Click a button, and `onClick` fires, straightforward enough. Type inside a text box, and `onChange` fires, because every keystroke alters what is inside the box. Press **J**, and `onChange` triggers. Press **o**, and it triggers again, firing on every single letter until you have spelled out *John*.

Our job is to wire those two events directly to our state. Every time you type in the box, that new text needs to land inside `name`. Every time you click the Clear button, `name` needs to be wiped clean. Here is how `onChange` and `onClick` divide the work:

- **Typing updates the state:** Whenever you type in the Name box, `onChange` fires. Inside `onChange`, we pass the text you just typed straight into `setName`.
- **Clicking resets the state:** Whenever you click the Clear button, `onClick` fires. Inside `onClick`, we call `setName` with an empty string.
- **React syncs the screen:** Every time `setName` changes `name`, React renders the page again. The Name box pulls its `value` fresh from `name`, immediately showing whatever state holds now.

That is the real secret behind the Clear button. Our code never reaches into the page to erase the Name box directly. It simply empties `name`. Because the Name box is locked to `name` through `value`, the box clears itself automatically.

Think of a classroom whiteboard. The students call out their answers, but only the teacher writes on the board, and the board shows only what the teacher wrote. Our box works the same way. The user calls out letters through `onChange`, only state writes the text, and through `value` the box shows only what state holds. A box that works like this is called a **controlled** box, because React state controls what it shows.

### The real page: a contact form that counts and clears

Now think of the contact form of an online shop. Under the Message box, a small line counts the letters as the user types, such as 12 / 200. This form needs two things from its boxes.

First, the count must change on every key. So the text must reach state on every key, not only when the user clicks Send.

Second, after the user clicks Send, every box must be empty again, ready for the next message. Our code empties the state, so state must be able to reach back into the box and empty it too.

A box that only reports to state fails the second job, as Principle 2 shows. A box that only listens to state fails the first job, as Principle 3 shows. This lecture shows how one box does both jobs.

### Our example page: the Contact Us form

Our page is the **Contact Us** form of an online shop. It has a Name box, a Topic menu, a Message box with its count, a tick box called Email me a reply, and a Send button. When the tick box is ticked, an Email box appears. Here is the finished page:

### Five Principles of Controlled Inputs

**PRINCIPLES:**
1. **`onChange` sends every key into state.** React calls it on every key, so the count can follow each letter.
2. **`value` sends state back into the box.** Then emptying the state is enough to empty the box after Send. `defaultValue`, which sets only the starting text, cannot do this.
3. **`value` without `onChange` freezes the box.** The browser accepts each new letter, React puts the old text back, and the Console shows an error.
4. **A menu and a tick box use the same pair.** The menu takes its choice from state. The tick box takes its tick from state, and its handler reads the tick, not the text.
5. **A controlled box starts with an empty string.** If its state starts with nothing at all, React warns as soon as the user types.

Here is the map of the five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`onChange` Sends Every Key into State** | A count or a greeting that never moves means the typed text never reached state. Interviewers also ask why React's `onChange` fires on every key. | Give the box `onChange`, and save the new text with the setter on every key. |
| **Principle 2** | **`value` Sends State Back into the Box** | A form that keeps its old text after Send, while the count says zero, is the most common form bug. | Give the box `value` from state, so the box always shows what state holds. |
| **Principle 3** | **`value` Without `onChange` Freezes the Box** | A box that refuses every letter looks broken, and the Console error explains why. | Every box with `value` also needs `onChange` that saves the new text right away. |
| **Principle 4** | **The Same Pair on a Menu and a Tick Box** | A tick box that will not untick, or a menu that ignores its starting choice, comes from the habits of plain HTML. | Put the chosen value on the menu itself. Give the tick box its tick from state, and read the tick back from the browser. |
| **Principle 5** | **A Controlled Box Starts with an Empty String** | A warning about a box changing from uncontrolled to controlled appears on the first key, and confuses many developers. | Start the state behind every box with an empty string, never with nothing. |

## 1. Principle 1: `onChange` Sends Every Key into State

### The smallest version: a greeting that follows each letter

Start with a tiny page that has only a Name box and a greeting under it. When the page opens, the box is empty and the greeting says only Hello:

```page width=text caption="A Name box and a greeting, when the page opens."
form:
  field: Name |
line: Hello,
```

To make the greeting follow what the user types, we give the box `onChange`:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [name, setName] = useState('');

  return (
    <main>
      <label>
        Name
        <input ~onChange~={e => setName(e.target.value)} /> {/* React calls this arrow on every key */}
      </label>
      <p>Hello, {name}</p>
    </main>
  );
}
```

The user types J, and the greeting immediately says Hello, J. After four keys, the page looks like this:

```page width=text caption="The same page after the user types John: the greeting has followed every letter."
form:
  field: Name | John | good
line: Hello, John | good
```

Look closely at the function inside `onChange`. How does it grab the letters you type?

Whenever `onChange` fires, React hands your function the event object, `e`. Inside that object, `e.target` is the box the user just typed into. Its `e.target.value` holds the full text inside that box right now, with the newest letter already in it:

- **Press J:** The browser puts J into the box, `onChange` fires, and `e.target.value` is J.
- **Press o:** The browser adds o to the box, `onChange` fires again, and `e.target.value` is Jo.

Our function passes that text straight to `setName`, and the greeting updates on every letter. Think of a student who calls out each letter to the teacher while writing a word on paper. The teacher hears every letter as it is written, not only the finished word.

### The message box and its live count

Now we build the first part of our Contact Us form: a heading, a Message box, and the character count under it:

```jsx title="src/components/ContactForm.jsx"
import { useState } from 'react';

export default function ContactForm() {
  const [message, setMessage] = useState('');

  function handleMessageChange(e) {
    setMessage(e.target.value);
  }

  return (
    <section>
      <h1>Contact Us</h1>
      <form>
        <label>
          Message
          <textarea ~onChange={handleMessageChange}~ /> {/* React calls the handler on every key */}
        </label>
        <p>{message.length} / 200</p>
      </form>
    </section>
  );
}
```

Every string in JavaScript has `.length`, which is the number of characters in it. When the page opens, `message` is empty, so the count shows zero:

```page width=text caption="The first version of the Contact Us form, when the page opens."
heading: Contact Us
form:
  textarea: Message |
line: 0 / 200
```

The user types Where is my parcel?, and the count moves with every letter:

```page width=text caption="The same form after the user types Where is my parcel? into the Message box."
heading: Contact Us
form:
  textarea: Message | Where is my parcel?
line: 19 / 200 | good
```

Notice the order inside a single keystroke. When the user presses a key, the browser puts the new letter into the Message box first, and React calls our handler right after. Because the letter is already inside the box when the handler runs, `e.target.value` already includes it, and the count is never a letter behind. Keep that browser-first order in mind, because Principles 2 and 3 build right on top of it.

### React's `onChange` and the browser's `change` event are NOT the same

If you have written plain JavaScript, the name `onChange` may surprise you. In plain JavaScript, a text box has two different events you can listen to:

```js title="page.js"
messageBox.addEventListener(~'change'~, e => console.log(e.target.value)); // Runs only when the user leaves the box
messageBox.addEventListener(~'input'~, e => console.log(e.target.value)); // Runs on every key
```

The browser's `change` event stays quiet while the user types and waits until the user clicks outside the box. It is the browser's `input` event that fires on every key.

React's `onChange` works like the second line, the `input` event. So the two share a name, but they are NOT the same. The browser's `change` event waits for the user to leave the box, whereas React's `onChange` fires on every keystroke. React also accepts `onInput`, which does the exact same job. As the React documentation notes, "For historical reasons, in React it is idiomatic to use `onChange` instead which works similarly."

### Mistake: keeping the message in a plain variable

A developer new to React might keep the text in a plain variable, the way plain JavaScript does:

```jsx title="src/components/ContactForm.jsx" bad="2,5"
export default function ContactForm() {
  let message = '';

  function handleMessageChange(e) {
    ~message~ = e.target.value; // **WRONG:** changes a plain variable, so React never renders again
  }

  return (
    <section>
      <h1>Contact Us</h1>
      <form>
        <label>
          Message
          <textarea onChange={handleMessageChange} />
        </label>
        <p>{message.length} / 200</p>
      </form>
    </section>
  );
}
```

The user types Hi into the Message box. The box shows Hi, but the count stays at zero:

```page width=text caption="The contact form with a plain variable, after the user types Hi."
heading: Contact Us
form:
  textarea: Message | Hi
line: 0 / 200 | bad
```

Why does Hi appear in the box while the count stays at 0 / 200? The browser puts the letters into the box on its own as the user types. The count, however, is drawn by React. Changing a plain variable never asks React to render again. Even if React did render again, the first line of the function would reset `message` back to an empty string.

Keeping `message` in state fixes both problems:

```jsx title="src/components/ContactForm.jsx" good="4,7"
import { useState } from 'react';

export default function ContactForm() {
  const [message, setMessage] = useState('');

  function handleMessageChange(e) {
    ~setMessage~(e.target.value); // Saves the text and asks React to render again
  }
```

Now the count follows every letter, just as in the preview above.

### Inside the handler, `message` is still one letter behind

There is one more trap inside the handler. Suppose a developer logs `message` inside `handleMessageChange` to check what the user just typed:

```jsx title="src/components/ContactForm.jsx" startLine="6"
  function handleMessageChange(e) {
    console.log(~message~); // Shows the text from before this key
    setMessage(e.target.value);
  }
```

Suppose the box holds Wher, and the user types e. On screen, the box now shows Where, yet the Console prints Wher.

In Lesson 15, you saw that each render has its own fixed snapshot of state. This handler was created during the render when `message` was still Wher, and `setMessage` only asks for the *next* render with Where. Inside the handler that is running right now, the new text lives in `e.target.value`, not in `message`.

> [!PRINCIPLE]
> **Principle 1: `onChange`: React Calls It on Every Key**
>
> *When the page must react to what the user types, give the box `onChange` and save `e.target.value` with the setter.*
>
> The count must move while the user types, so the text must reach state on every key. React's `onChange` is not the browser's `change` event. It fires on every key, like the browser's `input` event. Because the browser puts the new letter into the box before React calls the handler, `e.target.value` already holds the whole text with the new letter. Meanwhile, the state variable still holds the previous render's text. A plain variable cannot do this job, because changing it never makes React render again.
>
> **DO THIS:**
> ```jsx
> const [message, setMessage] = useState('');
> <textarea ~onChange~={e => setMessage(e.target.value)} /> {/* Saves the whole text on every key */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> let message = '';
> <textarea onChange={e => { ~message~ = e.target.value; }} /> {/* **WRONG:** a plain variable never makes React render again */}
> ```

## 2. Principle 2: `value` Sends State Back into the Box

### The smallest version: `defaultValue` and `value`

React gives an input box two different props for its text, and each one does a different job:

- **`defaultValue`** sets **only the starting text** when the box first appears. It is called `defaultValue` because all it holds is an initial default. And that is the catch with a default value: after that first render, its job is over. The box keeps whatever the user types inside the browser, and later changes to state never touch the box again. There is an initial default at the start, and then the connection between state and the box vanishes.
- **`value`** locks the input box to what state holds right now, on every render. Paired with `onChange`, it works in both directions:
  - It **displays** the input box initially with the starting `value` from state.
  - It **updates the display** of the box every time that state changes.
  - And through `onChange`, it does the opposite as well: it **updates the state** itself whenever the user writes something in the box. This creates a complete two-way loop between the screen and state.

It is a win-win situation: state always knows what is in the box, and the box always shows what is in state.

Now look at what happens on our name page when we try each prop, type John, and click the Clear button:

::: row caption="The same name page with two different props on the box, after the user types John and clicks Clear."
::: col title="defaultValue on the box" tag="box keeps John" tone=bad
```jsx title="src/App.jsx" startLine="10"
<input ~defaultValue=""~ onChange={e => setName(e.target.value)} /> {/* Sets only the starting text */}
```
```page size=mini
form:
  field: Name | John | bad
line: Hello,
form:
  button: Clear
```
The greeting says only Hello, but the box still shows John.
:::
::: col title="value on the box" tag="box empties" tone=good
```jsx title="src/App.jsx" startLine="10"
<input ~value={name}~ onChange={e => setName(e.target.value)} /> {/* Shows whatever name holds */}
```
```page size=mini
form:
  field: Name | | good
line: Hello,
form:
  button: Clear
```
The greeting says only Hello, and the box is empty.
:::
:::

- **With `defaultValue`, the box and state live two separate lives.** They meet only once, when the page opens, and then go their own ways. The browser keeps its own copy of *John* inside the box, while React keeps *John* inside `name`. When the Clear button wipes `name`, React clears the greeting, because the greeting belongs to React. But the box is no longer listening to React, so *John* stays right where the browser left it.
- **With `value`, the box has no separate life of its own.** It is a live mirror of `name`. The box never stores its own truth; it only reflects whatever `name` holds at this moment. So the instant the Clear button wipes `name`, the mirror goes blank too, and the box and the greeting clear as one.

### Why HTML's `value` attribute became React's `defaultValue`

If you have written plain HTML, the name `defaultValue` may bother you, because HTML has no attribute called that. In HTML, you write `<input value="John">`, and John is only the starting text. The user can type over it, and the attribute in the Elements panel still says John. The browser keeps two things apart: the starting text, which is what the `value` attribute holds, and the text that is in the box right now. In JavaScript, the browser even calls the starting text `input.defaultValue`.

React keeps the same two things apart, but it renames them. What HTML calls the `value` attribute, React calls **`defaultValue`**. React uses the name **`value`** for the other thing: the text in the box right now. So the same line, `<input value="John">`, means two different things. In an HTML file, it sets the starting text. In JSX, it tells React that the box must show John after every render.

That explains the Clear button. In the version with `defaultValue`, our code only ever set the starting text. When the user clicks the Clear button and `setName` empties `name`, our code says nothing about the text in the box right now, so the box keeps John. In the version with `value={name}`, our code describes the text in the box right now. So when `name` becomes empty, React empties the box too.

Think of a student's own notebook. On the first day, the teacher writes one line on page one. That is `defaultValue`. After that, the student writes freely, and the teacher cannot erase anything from the front of the room. A box like this, without `value`, is called an **uncontrolled** box, because it keeps its own text. A box with `value` from state and `onChange` back into state is the whiteboard from the start of the lecture, a **controlled** box. As React's documentation puts it, "React will force the input to always have the `value` you passed."

### With `value`, why can I still type?

If `value={name}` forces the box to show `name` after every render, how does a new letter stay in the box when you type? Follow one keystroke in order:
1. The user presses a key, and the browser shows the letter in the box.
2. React calls `onChange`, and `setName` saves the new text in state.
3. React renders again, and `value` is now that new text.
4. React writes that same text into the box, so the letter stays.

### The Send button that empties the count, but not the Message box

Back to our Contact Us form. Now we add a Send button. When the form is sent, our code logs the message and empties the state, so the form is ready for the next message:

```jsx title="src/components/ContactForm.jsx" startLine="10"
  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', message);
    ~setMessage('')~; // Empties the state after sending
  }
```

The developer wants the Message box to start empty, so they give it `defaultValue=""`:

```jsx title="src/components/ContactForm.jsx" startLine="16" bad="7"
  return (
    <section>
      <h1>Contact Us</h1>
      <form onSubmit={handleSend}>
        <label>
          Message
          <textarea ~defaultValue=""~ onChange={handleMessageChange} /> {/* **WRONG:** starting text only, so Send cannot empty the box */}
        </label>
        <p>{message.length} / 200</p>
        <button type="submit">Send</button>
      </form>
    </section>
  );
}
```

While the user types Where is my parcel?, everything looks fine, and the count reaches 19 / 200. Then the user clicks Send:

```page width=text caption="The contact form with defaultValue, after the user types Where is my parcel? and clicks Send."
heading: Contact Us
form:
  textarea: Message | Where is my parcel? | bad
line: 0 / 200 | bad
form:
  submit: Send
log: Sent: Where is my parcel? | ContactForm.jsx:12
```

Look at the page after the click on Send. The count says 0 / 200, yet Where is my parcel? is still sitting in the Message box. Why do the count and the box disagree?
1. When the user clicked Send, `handleSend` emptied `message`.
2. React rendered again. The count reads `message.length`, so it dropped to 0 / 200.
3. The Message box uses `defaultValue=""`, which only set the starting text when the page opened. Because the box has no `value` prop, the browser kept the old text inside the box.

So state is empty, and the box on screen is out of date. If the user clicks Send a second time without typing anything, the Console proves it by logging an empty message while Where is my parcel? is still visible in the box:

```page width=text caption="The same form after the user clicks Send a second time without typing anything."
heading: Contact Us
form:
  textarea: Message | Where is my parcel? | bad
line: 0 / 200 | bad
form:
  submit: Send
log: Sent: Where is my parcel? | ContactForm.jsx:12
log: Sent: | ContactForm.jsx:12
```

### The fix: `value={message}` on the Message box

Replacing `defaultValue=""` with `value={message}` ties the Message box to state:

```jsx title="src/components/ContactForm.jsx" startLine="20" good="3"
        <label>
          Message
          <textarea ~value={message}~ onChange={handleMessageChange} /> {/* The box always shows what message holds */}
        </label>
```

Now when the user types Where is my parcel? and clicks Send, the box and the count become empty together:

```page width=text caption="The contact form with value, after the user types Where is my parcel? and clicks Send."
heading: Contact Us
form:
  textarea: Message | | good
line: 0 / 200 | good
form:
  submit: Send
log: Sent: Where is my parcel? | ContactForm.jsx:12
```

### State is the single source of truth

Our page shows the message in two places: inside the Message box and in the character count below it. Think of a train station with one main clock. Every platform screen copies that clock, and when the main clock changes, every screen changes with it. Nobody walks down the platform setting screens by hand.

On our page, `message` is that main clock, and the Message box and the count are the screens. Developers call this a **single source of truth**: one place holds the text, and everything on the page copies it.

### An empty `defaultValue` and `value={message}` are NOT the same

When the page opens and the message state is empty, the Message box with `defaultValue=""` and the Message box with `value={message}` draw the exact same blank box. Even while the user types, they look alike because both have `onChange`. Yet they are NOT the same. They split on the first render after Send, when `value={message}` writes the empty string into the box while `defaultValue=""` leaves the old text behind. Notice too that the Message box in Principle 1 had `onChange` and was still uncontrolled. `onChange` only reports; only `value` makes a box controlled.

One last note for readers who know HTML. In plain HTML, you put the starting text of a text area between its opening and closing tags. React does not support that; in React, a text area takes `value` or `defaultValue`, just like an input.

> [!PRINCIPLE]
> **Principle 2: `value`: React Writes State into the Box After Every Render**
>
> *When our code must change what the box shows, such as emptying it after Send, give the box `value` from state.*
>
> A box without `value` keeps its own text. `defaultValue` only sets the starting text, so after Send the count says zero while the old message stays in the box. With `value={message}`, React writes the state into the box after every render. Then emptying `message` empties the box too, and state becomes the single source of truth.
>
> **DO THIS:**
> ```jsx
> <textarea ~value={message}~ onChange={e => setMessage(e.target.value)} /> {/* Setting message to an empty string now empties the box */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <textarea ~defaultValue=""~ onChange={e => setMessage(e.target.value)} /> {/* **WRONG:** starting text only, so the box keeps its text after Send */}
> ```

## 3. Principle 3: `value` Without `onChange` Freezes the Box

### The smallest version: a box stuck on John

What happens if a box has `value`, but no `onChange`? When the page opens, the Name box shows John, and the Console already shows a red error:

```page width=text caption="A Name box with value and no onChange, when the page opens."
form:
  field: Name | John
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

The box has `value={name}`, and nothing else:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [name, setName] = useState('John');

  return (
    <label>
      Name
      <input ~value={name}~ /> {/* **WRONG:** value without onChange */}
    </label>
  );
}
```

The user clicks at the end of the box and types ny, yet the box still shows John:

```page width=text caption="The same page after the user types ny into the Name box."
form:
  field: Name | John | bad
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

No line of our code deletes those letters, and the browser did not lock the keyboard either. So who removes the letters? React does. Here is what happens when the user presses n, in order:
1. The browser puts n into the box, so for a split second the box holds Johnn.
2. The box has no `onChange`, so no handler runs, and `name` stays John.
3. React sees that the box no longer matches `value={name}` and immediately writes John back into the box.

Remember the classroom whiteboard. A student calls out a letter, but the teacher is not listening, so the board never changes. That also makes this box different from an HTML `readOnly` box. On a `readOnly` box, the browser itself blocks typing at the keyboard. On a box with `value` and no `onChange`, the browser accepts every keystroke and React undoes it right away.

### What the red error tells you

Because a frozen box without `readOnly` is almost always a mistake, React prints this error in development and points to the three valid choices:
- If the user should be able to type into the controlled box, add `onChange`.
- If you only wanted starting text on an uncontrolled box, switch `value` to `defaultValue`.
- If the box should really be uneditable, add `readOnly` so React knows you meant it and silences the error.

### Mistake: the Name box that refuses Anna

Back to our Contact Us form. We add a Name box above the message, with its own state:

```jsx title="src/components/ContactForm.jsx" startLine="4"
  const [name, setName] = useState('');
  const [message, setMessage] = useState('');
```

In the form, the developer gives the Name box `value={name}` so Send can clear it, but forgets `onChange`:

```jsx title="src/components/ContactForm.jsx" startLine="20" bad="4"
      <form onSubmit={handleSend}>
        <label>
          Name
          <input ~value={name}~ /> {/* **WRONG:** no onChange, so every letter is put back */}
        </label>
```

The user clicks into the Name box and types Anna. The box stays empty, and the Console shows the error:

```page width=text caption="The contact form after the user types Anna into a Name box that has no onChange."
heading: Contact Us
form:
  field: Name | | bad
  textarea: Message |
line: 0 / 200
form:
  submit: Send
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

The steps are the same as for John. The browser puts each letter of Anna into the box, no handler saves it, and React puts the empty `name` right back. Adding `onChange` to the Name box completes the pair:

```jsx title="src/components/ContactForm.jsx" startLine="21" good="3"
        <label>
          Name
          <input value={name} ~onChange={e => setName(e.target.value)}~ /> {/* Each letter now reaches state */}
        </label>
```

When the user clicks Send, the form now logs and clears the name together with the message:

```jsx title="src/components/ContactForm.jsx" startLine="11"
  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, message);
    ~setName('')~; // The Name box empties together with the message
    setMessage('');
  }
```

Now Anna appears letter by letter, and the Console stays quiet:

```page width=text caption="The contact form after the fix, when the user types Anna into the Name box."
heading: Contact Us
form:
  field: Name | Anna | good
  textarea: Message |
line: 0 / 200
form:
  submit: Send
console: quiet
```

When the page first opens, the Name box without `onChange` and the Name box with `onChange` draw the exact same empty box. Yet they are NOT the same: without `onChange`, React wipes out every letter the moment you type it.

### Refusing a letter on purpose: the 200 limit

Because React puts back whatever state holds, our code can refuse a letter on purpose just by not saving it. Right now, our count says `/ 200`, so let's make the Message box stop at 200 characters:

```jsx title="src/components/ContactForm.jsx" startLine="7"
  function handleMessageChange(e) {
    ~if (e.target.value.length <= 200)~ { // Saves the text only while it fits
      setMessage(e.target.value);
    }
  }
```

Suppose the box already holds 200 characters, and the user types one more:
1. The browser puts the 201st letter into the box.
2. React calls `handleMessageChange`. The new text is 201 characters long, so the handler skips `setMessage`.
3. `message` still holds the 200 characters, so React writes those 200 characters back into the box, and the extra letter disappears.

This is the freeze from the start of Principle 3, used on purpose. The student can call out a 201st letter, but because the teacher does not write it down, it never stays on the whiteboard.

### The handler must save `e.target.value` right away

Because React checks the box right after your `onChange` handler finishes, the handler cannot wait inside a timer before saving the text:

```jsx title="A Name box whose handler saves the text later"
function handleNameChange(e) {
  ~setTimeout~(() => setName(e.target.value), 100); // **WRONG:** the state waits, but React puts the old text back right away
}

<input value={name} onChange={handleNameChange} />
```

Even though this box has `onChange`, typing into it still fails:
1. The user presses a key, and the browser shows the letter in the box.
2. `handleNameChange` starts a timer and finishes right away without changing `name`.
3. React sees that `name` has not changed yet and puts the old text back into the box.
4. When the timer runs 100 milliseconds later, the box has already been wiped back to the old text.

Changing the letters inside `onChange`, such as turning them into uppercase with `toUpperCase`, also fights the browser. When the user types a small letter inside a word, React overwrites the box with a different string, and the cursor jumps to the end of the box. Keep the handler simple: save `e.target.value` as it is, right away, or skip the setter when refusing a key.

> [!PRINCIPLE]
> **Principle 3: Read-Only: `value` Without `onChange` Freezes the Box**
>
> *Every box with `value` also needs `onChange` that saves the new text right away.*
>
> With `value`, React writes the state into the box after every key. If no handler saves the new letter, state never changes, so React puts the old text back, and the Console shows the read-only field error. The same happens when the handler waits inside a timer. Skipping the setter when the text is too long lets you use that same reset on purpose to enforce a character limit. A box that should stay frozen on purpose says so with `readOnly`.
>
> **DO THIS:**
> ```jsx
> <input value={name} ~onChange={e => setName(e.target.value)}~ /> {/* Each letter reaches state, so it stays */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input ~value={name}~ /> {/* **WRONG:** no onChange, so React puts the old text back after every key */}
> ```

## 4. Principle 4: The Same Pair on a Menu and a Tick Box

### The smallest version: a fruit menu and an agree box

A drop-down menu is a `<select>`, and a tick box is an `<input type="checkbox" />`. Both are controlled with the same two-prop idea. Here is a tiny page where the Fruit menu starts on Orange and the I agree box starts unticked:

```page width=text caption="A fruit menu and an agree box, when the page opens."
form:
  select: Fruit | Orange
  check: I agree | off
```

The menu uses `value` like a text box, while the tick box uses `checked`:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [fruit, setFruit] = useState('orange');
  const [agree, setAgree] = useState(false);

  return (
    <form>
      <label>
        Fruit
        <select ~value={fruit}~ onChange={e => setFruit(e.target.value)}> {/* The chosen option comes from state */}
          <option value="apple">Apple</option>
          <option value="banana">Banana</option>
          <option value="orange">Orange</option>
        </select>
      </label>
      <label>
        <input type="checkbox" ~checked={agree}~ onChange={e => setAgree(e.target.checked)} /> {/* The tick comes from state */}
        I agree
      </label>
    </form>
  );
}
```

The user picks Banana and ticks I agree:

```page width=text caption="The same page after the user picks Banana and ticks I agree."
form:
  select: Fruit | Banana | good
  check: I agree | on | good
```

It is the same whiteboard as before: now the board holds a chosen option and a ticked square, and only state writes them.

### HTML has two more starting values, and React renames them too

In Principle 2, we saw that HTML's `value` attribute sets only the starting text. React renames that starting prop to `defaultValue` and uses `value` for the text right now. Menus and tick boxes follow that exact same pattern:
- In plain HTML, you mark a starting menu choice by writing `selected` on an option, and a starting tick by writing `checked` on the checkbox. In JavaScript, the browser calls those starting values `option.defaultSelected` and `input.defaultChecked`.
- In React, props that start with `default`, such as **`defaultChecked`**, set only the starting choice on an uncontrolled field. Meanwhile, **`value`** and **`checked`** control what the field shows on every render.

### What `value` means on a menu

On a `<select>`, each option has two texts. The user reads the word between its tags, such as Banana, while the menu reports its `value`, such as `'banana'`, to our code. Passing `value={fruit}` to the menu highlights whichever option has a matching `value`. When the user picks a new option, `e.target.value` gives our handler that option's `value` string.

### Never mark an option as `selected`

In plain HTML, you choose the starting option of a menu by writing `selected` on one `<option>`:

```jsx title="The plain HTML habit on a menu"
<select>
  <option value="delivery">Delivery</option>
  <option value="payment" ~selected~>Payment</option> {/* **WRONG:** the plain HTML habit, not supported in React */}
</select>
```

React does not support `selected` on an option. Instead, it prints a Console error pointing you to `value` on the `<select>` itself:

```jsx title="The React way on a menu"
<select ~value="payment"~ onChange={e => setTopic(e.target.value)}> {/* React chooses the option whose value matches */}
  <option value="delivery">Delivery</option>
  <option value="payment">Payment</option>
</select>
```

So in React, the two are NOT the same. Putting `value` on the `<select>` tag lets you control the whole menu from one state variable. You never have to move `selected` from option to option.

### What `checked` means on a tick box

A tick box has no text to show; it is either ticked or not. So instead of `value`, a controlled tick box uses **`checked`**, which holds true or false. Its handler reads **`e.target.checked`**, which is true when the click just ticked the box and false when it unticked it. And just like a text box, giving a tick box `checked` without `onChange` freezes it and prints the same read-only error.

### The Topic menu on the contact form

Back to our Contact Us form. We add a Topic menu that starts on Delivery:

```jsx title="src/components/ContactForm.jsx" startLine="4"

  const [topic, setTopic] = ~useState('delivery')~; // The menu starts on Delivery
  const [message, setMessage] = useState('');
```

The menu sits between the Name box and the Message box:

```jsx title="src/components/ContactForm.jsx"
        <label>
          Topic
          <select ~value={topic}~ onChange={e => setTopic(e.target.value)}> {/* Must match the value of one option */}
            <option value="delivery">Delivery</option>
            <option value="payment">Payment</option>
            <option value="other">Other</option>
          </select>
        </label>
```

The user types Anna and picks Payment from the Topic menu:

### Mistake: reading `e.target.value` on the tick box

Next, we add the tick box Email me a reply, starting unticked:

```jsx title="src/components/ContactForm.jsx" startLine="7"
  const [wantsReply, setWantsReply] = useState(false);
```

Because every other field on the form reads `e.target.value`, the developer copies `e.target.value` into the tick box handler by mistake:

```jsx title="src/components/ContactForm.jsx" bad="2"
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.value~)} /> {/* **WRONG:** reads a fixed string, not the tick */}
          Email me a reply
        </label>
```

The user clicks Email me a reply to tick it, and the tick appears. Then the user clicks it a second time to untick it, and the box stays ticked:

```page width=text caption="The contact form after the user ticks Email me a reply and then clicks it again to untick it."
heading: Contact Us
form:
  field: Name | Anna
  select: Topic | Payment
  textarea: Message |
line: 0 / 200
form:
  check: Email me a reply | on | bad
  submit: Send
```

The first click ticked the box, yet the second click cannot untick it. Why does reading `e.target.value` trap the tick box in the ticked state?
1. Most tick boxes have no `value` attribute of their own. On those boxes, the browser sets `e.target.value` to the fixed string `'on'`, which never changes when you click.
2. On the first click, `setWantsReply` saves `'on'`. Because `'on'` is a non-empty string, React treats `checked={wantsReply}` as ticked.
3. On the second click, the user tries to untick the box, but `e.target.value` is still `'on'`. So `wantsReply` stays `'on'`, and React puts the tick right back.

Reading `e.target.checked` instead gives us the tick after each click:

```jsx title="src/components/ContactForm.jsx" good="2"
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* true or false, right after the click */}
          Email me a reply
        </label>
```

Now the box ticks and unticks cleanly on every click.

### Send puts the menu and the tick box back

When the form is sent, our handler now puts the Topic menu back to Delivery and unticks the box too:

```jsx title="src/components/ContactForm.jsx" startLine="15"
  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, topic, message, wantsReply);
    setName('');
    ~setTopic('delivery')~; // Back to the first option
    setMessage('');
    ~setWantsReply(false)~; // Back to unticked
  }
```

Because both controls read their state on every render, clicking Send resets the menu and the tick box right alongside the text boxes.

> [!PRINCIPLE]
> **Principle 4: Menus and Tick Boxes: The Same Pair with Their Own Props**
>
> *Control a menu with `value` on the `<select>` itself. Never put `selected` on an option. Control a tick box with `checked`, and read `e.target.checked` in its handler.*
>
> A menu reports the `value` of the picked option, so `value` on the select must match one option. Writing `selected` on an option is the plain HTML habit, and React does not support it. A tick box takes `checked` from state and reads `e.target.checked` in its handler. On a tick box, `e.target.value` is the fixed string `'on'`, which never changes with the tick.
>
> **DO THIS:**
> ```jsx
> <select ~value={topic}~ onChange={e => setTopic(e.target.value)}> {/* The choice lives on the select */}
> <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* true or false, right after the click */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <option value="payment" ~selected~>Payment</option> {/* **WRONG:** not supported in React */}
> <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.value~)} /> {/* **WRONG:** always 'on', so the box never unticks */}
> ```

## 5. Principle 5: A Controlled Box Starts with an Empty String

### The smallest version: a City box that starts with nothing

Here is a City box whose state starts with no value inside `useState`. When the page opens, it looks like any empty box, and the Console is quiet:

```page width=text caption="A City box whose state starts with nothing, when the page opens."
form:
  field: City |
console: quiet
```

The only difference is the empty `useState` call:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [city, setCity] = ~useState()~; // **WRONG:** no starting value at all

  return (
    <label>
      City
      <input value={city} onChange={e => setCity(e.target.value)} />
    </label>
  );
}
```

The user types a. The letter appears in the box, and a red warning appears in the Console:

```page width=text caption="The same page after the user types a into the City box."
form:
  field: City | a
console: A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen. Decide between using a controlled or uncontrolled input element for the lifetime of the component. More info: https://react.dev/link/controlled-components
```

### Where did `undefined` come from?

Our code never writes the word `undefined`, yet the Console warning says the value changed from `undefined` to a defined value. JavaScript supplies it: whenever you call a function with nothing between its parentheses, JavaScript passes `undefined`. So calling `useState` with nothing starts our state variable as `undefined`.

### Why React warns when the box works

The letter a appeared in the box, so why is React complaining that an uncontrolled input changed to controlled? Follow what happened from the first render:
1. When the page opened, `city` was `undefined`. To React, `value={undefined}` is the same as giving the box no `value` prop at all, so React created the City box as an **uncontrolled** box.
2. When the user typed a, `setCity` saved the string `'a'`.
3. On the next render, `value={city}` was now the string `'a'`, so the very same box suddenly became a **controlled** box.

As React's documentation explains, if you pass `undefined` first and a string later, "React won't know whether you want the component to be uncontrolled or controlled." A box must stay one kind for its whole life. Think of a student's notebook that is suddenly declared a classroom whiteboard in the middle of the lesson: nobody knows who owns the page any more.

### Starting with nothing and starting with an empty string are NOT the same

When the page opens, calling `useState` with nothing and calling it with an empty string draw the same empty box, but they are NOT the same. With an empty string, `value` is a real string from the very first render, so the box starts controlled and never switches.

### Mistake: the Email box that appears with nothing in it

Back to our Contact Us form. When the user ticks Email me a reply, an Email box appears using `&&` from Lesson 10:

```jsx title="src/components/ContactForm.jsx"
        {wantsReply && (
          <label>
            Email
            <input value={email} onChange={e => setEmail(e.target.value)} />
          </label>
        )}
```

Because the email is not needed until the box is ticked, the developer gives `useState` no starting value:

```jsx title="src/components/ContactForm.jsx" startLine="8" bad="1"
  const [email, setEmail] = ~useState()~; // **WRONG:** undefined until the first key
```

The user ticks Email me a reply, an empty Email box appears, and the user types a:

```page width=text caption="The contact form after the user ticks Email me a reply and types a into the Email box."
heading: Contact Us
form:
  field: Name | Anna
  select: Topic | Payment
  textarea: Message |
line: 0 / 200
form:
  check: Email me a reply | on
  field: Email | a | bad
  submit: Send
console: A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen. Decide between using a controlled or uncontrolled input element for the lifetime of the component. More info: https://react.dev/link/controlled-components
```

When the Email box appeared, `email` was `undefined`, so the box started uncontrolled and switched to controlled on the first key. Starting `email` with an empty string makes the box controlled from the moment it appears:

```jsx title="src/components/ContactForm.jsx" startLine="8" good="1"
  const [email, setEmail] = ~useState('')~; // A real string from the first render
```

### Send clears the whole form

Now `handleSend` empties the email too, putting every part of the form back to its starting state:

```jsx title="src/components/ContactForm.jsx" startLine="16"
  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, topic, message, wantsReply, email);
    setName('');
    setTopic('delivery');
    setMessage('');
    setWantsReply(false);
    ~setEmail('')~; // An empty string, never undefined
  }
```

Notice the empty string passed to `setEmail`. Clearing a box with `undefined` or `null` would make it switch the other way, from controlled back to uncontrolled. So we always clear a text box with an empty string.

> [!PRINCIPLE]
> **Principle 5: Starting Value: A Controlled Box Starts with an Empty String**
>
> *The state behind `value` must hold a string from the first render, so start an empty box with an empty string in `useState`, never with nothing.*
>
> Calling `useState` with no argument gives `undefined`. Passing `undefined` to `value` is the same as giving the box no value at all, so the box starts uncontrolled. On the first key, state becomes a string, the box switches to controlled, and React warns because a box cannot switch over its life. An empty string makes the box controlled from the first render, and we clear it with an empty string too.
>
> **DO THIS:**
> ```jsx
> const [email, setEmail] = ~useState('')~; // Controlled from the first render
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [email, setEmail] = ~useState()~; // **WRONG:** undefined first, a string later, so React warns
> ```

## Putting All Five Principles Together

### The complete `ContactForm.jsx` file

Here is the finished form. Every box takes what it shows from state, and every box reports its changes back to state:

```jsx title="src/components/ContactForm.jsx"
import { useState } from 'react';

export default function ContactForm() {
  const [name, setName] = useState('');
  const [topic, setTopic] = useState('delivery');
  const [message, setMessage] = useState('');
  const [wantsReply, setWantsReply] = useState(false);
  const [email, setEmail] = ~useState('')~; // 5. Starts with a string, never undefined

  function handleMessageChange(e) {
    if (e.target.value.length <= 200) {
      setMessage(e.target.value);
    }
  }

  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, topic, message, wantsReply, email);
    setName('');
    setTopic('delivery');
    setMessage('');
    setWantsReply(false);
    setEmail('');
  }

  return (
    <section>
      <h1>Contact Us</h1>
      <form onSubmit={handleSend}>
        <label>
          Name
          <input value={name} ~onChange={e => setName(e.target.value)}~ /> {/* 3. value always comes with onChange */}
        </label>
        <label>
          Topic
          <select ~value={topic}~ onChange={e => setTopic(e.target.value)}> {/* 4. The choice lives on the select */}
            <option value="delivery">Delivery</option>
            <option value="payment">Payment</option>
            <option value="other">Other</option>
          </select>
        </label>
        <label>
          Message
          <textarea ~value={message}~ onChange={handleMessageChange} /> {/* 2. State goes into the box */}
        </label>
        <p>{message.length} / 200</p>
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* 4. The tick, not the text */}
          Email me a reply
        </label>
        {wantsReply && (
          <label>
            Email
            <input value={email} ~onChange~={e => setEmail(e.target.value)} /> {/* 1. Every key goes into state */}
          </label>
        )}
        <button type="submit">Send</button>
      </form>
    </section>
  );
}
```

The user fills in every part of the form:

  field: Email | anna@example.com
  submit: Send
```

Then the user clicks Send. The Console logs every value, and the whole form returns to its start:

```

### How React calls the components, and what one key does

When the page loads, React starts at `App` and follows the tags. `App` has only one tag, so React calls `ContactForm` next:

```tree caption="The component tree of the contact page and the order in which React calls each component."
`main.jsx` mounts `App` inside `<StrictMode>`
- +`App` [1. Called first] | **Root component** | Returns `<ContactForm />`
  - +`ContactForm` [2. Called second] | Holds **five states**, one for each part of the form | Called again after **every key**, every pick, every tick, and every Send
```

Every controlled box goes around the same loop on every key:

```tree dir=right caption="The loop that one key runs in a controlled box, from the browser to state and back into the box."
One key in a controlled box
- +1. The browser | Shows the new letter in the box for a moment
- +2. `onChange` | React calls our handler with the event object
- +3. The setter [`setMessage`] | Saves the new text in **state**
- +4. React renders again | Writes the state into the box through **`value`** | The letter stays
```

### Summary

| Aspect | The Plain JavaScript Habit | The React Rule |
| :--- | :--- | :--- |
| **Reporting each key** | Listen to the `change` event, which waits until the user leaves the box, or save the text in a plain variable | Use `onChange`, which fires on every key, and save `e.target.value` with the setter |
| **Emptying a box** | Reach into the box and clear its text by hand | Give the box `value` from state, then set the state to an empty string |
| **A box with a value** | Write the value and expect the user can still type | Always pair `value` with `onChange`, or use `defaultValue` or `readOnly` |
| **Menus and tick boxes** | Write `selected` on an option, and read `value` from a tick box | Put `value` on the select, and use `checked` with `e.target.checked` |
| **The starting value** | Leave a variable empty until it is needed | Start every controlled box with an empty string, never `undefined` |

## For the Interview

> **The Interview Question:** How do you make an input, textarea, or select fully controlled by React state?

### How to Answer Clearly in 30 Seconds

"A controlled field takes what it shows from state and reports every change back to state. I give it two props: `value` from state, and `onChange`, which saves `e.target.value` with the setter. React's `onChange` fires on every key, like the browser's `input` event, not like the `change` event. After every render, React writes the state into the field, so state is the single source of truth. To empty the box after Send, I only set the state to an empty string. Four rules keep this working:
1. **`value` always comes with `onChange`.** Without it, React puts the old text back after every key and logs a read-only field error. The handler saves `e.target.value` right away.
2. **`defaultValue` is not controlled.** It sets only the starting text, and the box keeps its own text after that.
3. **Menus and tick boxes use the same pair.** A `<select>` takes `value` on the select itself, never `selected` on an option. A checkbox takes `checked` and reads `e.target.checked`.
4. **Start with an empty string.** A controlled field must get a string from the first render. If it starts as `undefined`, React warns that an uncontrolled input is changing to controlled."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What is the difference between a controlled and an uncontrolled input, and when would you use each?"**
   A controlled input gets `value` from state, or `checked` for a checkbox, and reports changes with `onChange`. React forces it to show what state holds after every render. An uncontrolled input has no `value`; it can get a starting text from `defaultValue` or `defaultChecked`, and after that it keeps its own text inside the browser. A controlled field is worth it in two cases. First, the page needs the text on every key, such as for a live count. Second, our code must change the field, such as emptying it after Send. Choosing between controlled fields and reading an uncontrolled form with `FormData` at submit time is the topic of Lesson 40.

2. **"Why does my input's caret jump, or why does typing feel slow?"**
   A caret jumps when the handler does not save `e.target.value` as it is right away. Two common causes are turning the text into uppercase with `toUpperCase` and delaying the update inside `setTimeout`. Another cause is a field that React removes and mounts again on every key. That happens when a component is defined inside another component, as in Lesson 04, or when its `key` changes, covered in Lesson 25. Slow typing has a different cause: every key updates state and renders the component that holds it. If that component draws a large page, moving the field and its state into a smaller child component, or using `useDeferredValue` from Lesson 68, keeps typing fast.

3. **"How do you control a select, a checkbox, and a field whose value comes from an API?"**
   A `<select>` gets `value` on the select tag itself, matching the `value` of one option, never `selected` on an option. A select with `multiple` takes an array of strings instead of one string. A checkbox gets `checked`, which is `true` or `false`, and its handler reads `e.target.checked`, because `e.target.value` on a checkbox is a fixed string such as `'on'`. A value from an API is often `null` or `undefined` until it arrives, so start the state with an empty string or write `value={someValue ?? ''}` so the field receives a string from its first render.
