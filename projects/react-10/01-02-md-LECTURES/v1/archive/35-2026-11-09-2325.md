## How a Chat Room Switches Rooms Without Leaving the Page

### One component that stays on the page, and a connection that must stop and start

When you open a chat app with rooms, such as Slack or Discord, a menu at the top lets you pick which room to read. The page shows the heading for the general room, and your browser stays connected to the chat server for that room (as seen in Lesson 32).

Now the user opens the menu and picks the travel room. The heading on the screen changes at once to welcome the user to the travel room, while the chat component itself stays on the page.

Because that component never left the page, it did not unmount and it did not mount again. Yet the browser must disconnect from the general room and connect to the travel room. React's `useEffect` handles that switch by running your cleanup function to stop the old connection and your setup function to start the new one. As React's docs state: "Your Effect's body specifies how to start synchronizing, and your cleanup function specifies how to stop synchronizing. All that React needs to do now is to call them in the correct order and with the correct props and state."

Here is the docs' own Effect that connects to `serverUrl` for the current `roomId` prop and disconnects when that Effect is cleaned up:

```jsx title="An Effect that starts and stops synchronizing with roomId"
useEffect(() => {
  const connection = ~createConnection(serverUrl, roomId)~; // 1. Start synchronizing with this render's roomId
  connection.connect();
  return () => {
    ~connection.disconnect()~; // 2. Stop synchronizing when this Effect is cleaned up
  };
}, ~[roomId]~); // 3. Stop the old connection and start a new one whenever roomId changes
```

React's docs use the word **lifecycle** for the stages something goes through over time. They state the core rule of this lesson directly: "Effects have a different lifecycle from components. Components may mount, update, or unmount. An Effect can only do two things: to start synchronizing something, and later to stop synchronizing it."

Compare those two lifecycles:
- **The component's lifecycle** has three stages. A component **mounts** when React adds it to the screen (as seen in Lesson 13). It **updates** when it receives new props or state on a re-render, usually in response to an interaction. Finally, it **unmounts** when React removes it from the screen (as seen in Lesson 32).
- **The Effect's lifecycle** has only two actions. The body of your setup function specifies how to **start synchronizing** with the external system, here by opening the chat connection. The cleanup function returned by your Effect specifies how to **stop synchronizing**, here by closing that exact connection. When a dependency such as `roomId` changes on a re-render, React stops the old synchronization and starts a new one. React's docs call that stop-and-start step **re-synchronizing** the Effect.

**It may look the same, or work the same at first, but it is NOT the same thing!** On the first visit, the component's lifecycle and the Effect's lifecycle happen together, yet the moment the user switches rooms, the two lifecycles split apart:
1. **On the first visit**, the user opens the chat. Here both lifecycles look identical: the component mounts, and the Effect starts synchronizing with the general room.
2. **When the user picks `travel` in the menu**, the two lifecycles split apart. The component only updates in place without unmounting, while the Effect stops synchronizing with the general room and starts synchronizing with the travel room.

```tree caption="A component's lifecycle has mount, update, and unmount; an Effect's lifecycle is a repeatable cycle of start synchronizing and stop synchronizing."
Two different lifecycles on the same chat page
- +The component's lifecycle [`mount -> update -> unmount`] | **Mounts** once, **updates** when `roomId` changes, **unmounts** when closed | Stays **on the page** while the user switches rooms
- +The Effect's lifecycle [`useEffect`] | **Starts synchronizing** in the setup and **stops synchronizing** in the cleanup | Repeats one **stop and start** every time `roomId` changes
```

### What is at stake

What is at stake is that the heading on the screen and the live chat connection behind it must always agree on which room the user is in. When the user switches the menu from `general` to `travel`, the heading on the page welcomes the user to the travel room. Two common mistakes break the connection behind that heading in opposite ways:
1. **Without a cleanup function**, the Effect opens a new connection to the travel room while leaving the old connection to the general room open. You now have two connections active at the same time.
2. **With `roomId` left out of the dependency array**, the Effect never runs again when the user picks `travel`. As React's docs warn: "You will remain connected to the initial `roomId` and `serverUrl` even after the user picks different values in the UI."

In both broken cases, the page and the server connection give two different answers to the question "which room am I in?". The heading on the screen says `travel`, while the connection to `general` is still open. As the docs put it, what your Effect did back then, connecting to the `"general"` room, no longer matches the UI.

Readers usually go wrong in four places:
1. They read the cleanup function as "the unmount code". Then they hit the exact surprise named in the docs' Troubleshooting section: "My cleanup logic runs even though my component didn't unmount".
2. They expect the cleanup function to see the new `roomId` after a switch, when in fact it still holds the old `roomId` from the render that created it.
3. They leave `roomId` out of the dependency array to stop the Effect from re-running, which leaves the chat stuck on the first room.
4. They put unrelated work, such as logging a page visit, inside the connection Effect simply because both happen to run when the user enters a room.

### Four ways to handle a value that an Effect reads

Whenever an Effect reads a value, where that value is declared decides whether it can change on a re-render. Props, state variables, and variables calculated inside the component body can change from one render to the next, so React's docs call them **reactive values**. React's docs give four ways to handle a value that an Effect reads:
1. **List it in the dependency array**: fits when the value is a reactive value in the component body that can change on a re-render. Listing `roomId` tells React to re-synchronize the Effect whenever `roomId` changes.
2. **Move it outside the component**: fits when the value is a fixed constant that never changes, such as a fixed `serverUrl`. Above the component, it cannot change on a re-render, so it is not reactive and does not belong in the array.
3. **Move it inside the Effect**: fits when only the Effect uses the value and it does not depend on props or state. Inside the Effect, it is not calculated during rendering, so it is not reactive and does not belong in the array.
4. **Read it in an Effect Event**: fits when the Effect needs to read the latest value of a prop or state variable without re-synchronizing the connection, which Lesson 36 covers with `useEffectEvent`.

```tree caption="The four places a value read by an Effect can live, and what each one means for the dependency array."
Four ways to handle a value that an Effect reads
- +1. Keep it in the component body and list it [`[roomId]`] | Can change on a **re-render** | React **re-synchronizes** the Effect whenever it changes
- +2. Move a fixed constant outside the component [`const serverUrl` at top of file] | Never changes on a **re-render** | Not reactive, so it **leaves the dependency array**
- +3. Move a helper value inside the Effect [Declared inside `useEffect`] | Created **when the Effect runs**, not during rendering | Not reactive, so it **leaves the dependency array**
- +4. Read it inside an Effect Event [`useEffectEvent` in Lesson 36] | Reads the **latest prop or state** without reconnecting | Covered in **Lesson 36**
```

Our server helper lives in `chat.js`, taken straight from the React docs. As the docs note in their code, "A real implementation would actually connect to the server". Our helper stands in for that server so we can watch every connection start and stop in the Console:

```js title="src/chat.js"
export function ~createConnection~(serverUrl, roomId) { // Stand-in for a real chat server connection
  return {
    ~connect~() { // Prints the connect line with roomId and serverUrl
      console.log('✅ Connecting to "' + roomId + '" room at ' + serverUrl + '...');
    },
    ~disconnect~() { // Prints the disconnect line with roomId and serverUrl
      console.log('❌ Disconnected from "' + roomId + '" room at ' + serverUrl);
    }
  };
}
```

### Five Principles of the Effect Lifecycle

**PRINCIPLES:** An Effect does not mount, update, and unmount like a component; instead, it starts synchronizing and stops synchronizing once for each value of its dependencies. Walking through how React re-synchronizes our chat room as its dependencies change gives us five practical rules:
1. **Principle 1: The Effect Connects to One Room Until It Disconnects**: A component's lifecycle has mount, update, and unmount, while an Effect's lifecycle has only one start and one stop. You write the setup to start synchronizing and the cleanup to stop synchronizing, and React repeats that pair as often as needed.
2. **Principle 2: Picking travel Runs the Cleanup for general First**: When a dependency changes, React first runs the cleanup function from the previous render with that render's old values. Then React runs the new setup function with the new render's values. Without a cleanup function, every room switch leaves an old connection open.
3. **Principle 3: Leaving roomId Out Keeps the Chat on general**: You cannot choose your dependencies. Every reactive value that the Effect reads must go in the dependency array. Silencing the linter with `[]` leaves the Effect stuck on the first render's stale value.
4. **Principle 4: A serverUrl in State Joins the Array**: Props, state, and any variable calculated in the component body are reactive values and must go in the dependency array. Constants outside rendering do not belong in the array, and values that change without a re-render, such as `ref.current`, cannot be dependencies.
5. **Principle 5: Logging the Visit Gets Its Own Effect**: Each Effect in a component must represent one separate synchronization process. Putting `logVisit` inside the connection Effect logs a false room visit every time `serverUrl` changes.

Here is the complete map of those five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **The Effect Connects to One Room Until It Disconnects** | Thinking of an Effect as "mount code" and "unmount code" breaks the moment a prop changes while the component stays on the page. | Write every Effect as a single start and stop cycle: the setup starts synchronizing and the cleanup stops synchronizing. |
| **Principle 2** | **Picking travel Runs the Cleanup for general First** | Expecting the cleanup to read the new prop, or forgetting the cleanup altogether, either misreads the Console or leaves the old connection open on every room switch. | After a commit with changed dependencies, React runs the previous render's cleanup with the old values first, then the new render's setup with the new values, and runs the last cleanup once more on unmount. |
| **Principle 3** | **Leaving roomId Out Keeps the Chat on general** | Shortening the dependency array to `[]` and suppressing the linter leaves the chat connected to `general` after the heading changes to `travel`. | Include every reactive value the Effect reads in its dependency array so React compares each spot with `Object.is` and re-synchronizes when a value changes. |
| **Principle 4** | **A serverUrl in State Joins the Array** | Moving `serverUrl` into state or calculating it in the component body makes it reactive; conversely, putting `ref.current` or `location.pathname` in the array never triggers a re-run. | Put all props, state, and component-body variables read by the Effect into the array; keep constants outside rendering out of the array, and do not use values that change without a re-render as dependencies. |
| **Principle 5** | **Logging the Visit Gets Its Own Effect** | Combining `logVisit` and the server connection in one Effect logs a new room visit for every letter the user types into the `Server URL:` box. | Give each independent synchronization process its own `useEffect` with its own dependency array, so deleting one Effect would never break the other. |

## 1. Principle 1: The Effect Connects to One Room Until It Disconnects

### The component's perspective vs. the Effect's perspective

Suppose the user clicks the Open chat button, picks `travel` in the menu, picks `music` in the menu, and then clicks the Close chat button. React's docs compare two ways of looking at those four actions: **the component's perspective** and **the Effect's perspective**.

From **the component's perspective**, you see four lifecycle moments of `ChatRoom`:
1. `ChatRoom` mounted with `roomId` set to "general".
2. `ChatRoom` updated with `roomId` set to "travel".
3. `ChatRoom` updated with `roomId` set to "music".
4. `ChatRoom` unmounted.

Now read the exact same four actions from **the Effect's perspective**:
1. Your Effect connected to the "general" room, until it disconnected.
2. Your Effect connected to the "travel" room, until it disconnected.
3. Your Effect connected to the "music" room, until it disconnected.

**It may look the same, or work the same at first, but it is NOT the same thing!** Look at the count: the component goes through four lifecycle moments, while the Effect completes three start and stop cycles. React's docs warn against mixing the two up: "**It's a good way to think about components, but _not_ about Effects.**"

Thinking of Effects as callbacks or lifecycle events that fire after a render or before unmount "gets complicated very fast," as the docs put it. Instead, the docs give a simpler rule: "always focus on a single start/stop cycle at a time. It shouldn't matter whether a component is mounting, updating, or unmounting."

```tree caption="The same four user actions seen from the component vs. seen from the Effect: four component lifecycle moments vs. three room connections."
Four user actions across three rooms
- !The component's perspective [`ChatRoom`] | 1. Mounted with `general` | 2. Updated with `travel` | 3. Updated with `music` | 4. Unmounted
- +The Effect's perspective [`useEffect`] | 1. Connected to `general`, until it disconnected | 2. Connected to `travel`, until it disconnected | 3. Connected to `music`, until it disconnected
```

### Writing the Effect in ChatRoom.jsx

Here is the `ChatRoom` component file that holds this Effect:

```jsx title="src/components/ChatRoom.jsx"
import { useEffect } from 'react';
import { createConnection } from '../chat.js';

const ~serverUrl~ = 'https://localhost:1234'; // Fixed server address outside the component

export default function ChatRoom({ ~roomId~ }) { // "general", "travel", or "music" from App
  useEffect(() => {
    const connection = ~createConnection~(serverUrl, roomId); // Builds the connection object for this room
    connection.~connect~(); // Starts synchronizing with this room
    return () => {
      connection.~disconnect~(); // Stops synchronizing with this room
    };
  }, [roomId]);
  return <h1>Welcome to the {roomId} room!</h1>;
}
```

Here `serverUrl` sits outside `ChatRoom` because the server address never changes between renders.

When an Effect does not return a cleanup function at all, the docs state that "React will behave as if you returned an empty cleanup function." Yes, for React's start and stop cycle they are **the exact same thing**: React still runs a stop step, and that step does nothing. For the chat room, returning no cleanup means nothing ever calls `disconnect`, so every room connection stays open.

### One component mount produces three connections

**Beware! Across these four clicks, `ChatRoom` mounts only once, yet the Effect connects three separate times.** Follow the four user actions in order in a production build:
1. **The user clicks the Open chat button.** The parent renders `ChatRoom` for the first time with `roomId` set to the general room. `ChatRoom` mounts, puts the general welcome heading on the page, and runs the Effect's setup function, which connects to the `general` room.
2. **The user picks `travel` in the menu.** The parent passes `roomId` for the travel room to the same `ChatRoom` component. `ChatRoom` does not unmount or mount again; it updates its heading in place to the travel welcome heading. React then calls the previous cleanup function, which disconnects from the `general` room, and runs the new setup function, which connects to the `travel` room.
3. **The user picks `music` in the menu.** `ChatRoom` updates its heading in place to the music welcome heading. React calls the cleanup function from the `travel` render, disconnecting from that room. Then React runs the setup function for the `music` render, connecting to the `music` room.
4. **The user clicks the Close chat button.** `App` stops rendering `ChatRoom`. `ChatRoom` unmounts, and React calls the cleanup function one last time, disconnecting from the `music` room.

Here is the browser and the Console after the first three actions, once the user has opened the chat, picked `travel`, and picked `music`:

```page width=text caption="The browser and Console in a production build after opening the chat, switching to travel, and switching to music."
form:
  select: Choose the chat room: | music | good
  button: Close chat
heading: Welcome to the music room!
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
```

### Why thinking from the component's lifecycle leads to a bug

Thinking from the component's lifecycle instead of the Effect's start and stop cycle leads directly to a broken chat room:
1. A developer looks at `ChatRoom` and thinks: I want to connect when the component mounts, and disconnect when it unmounts.
2. That thought treats setup as "mount code" and cleanup as "unmount code", so the developer writes an empty dependency array `[]` (as seen in Lesson 32).
3. When the user clicks the Open chat button, `ChatRoom` mounts with `roomId` set to the general room. The Effect connects to the `general` room.
4. When the user picks `travel` in the menu, `ChatRoom` does not unmount and does not mount again. It updates in place. Because the developer only thought about mount and unmount, the Effect never disconnects from `general` and never connects to `travel`. Principle 3 fixes the dependency array itself.

The docs summarize the mindset that prevents this bug: "All you need to do is to describe how to start synchronization and how to stop it. If you do it well, your Effect will be resilient to being started and stopped as many times as it's needed." They compare this to writing JSX: when you write the tags a component returns, you do not ask whether the component is mounting or updating. You describe what should be on the screen, and React figures out the rest. As the docs put it: "The Effect is *also* a part of the rendering output." And as the docs conclude: "When your cleanup logic correctly "mirrors" the setup logic, your Effect is resilient to running setup and cleanup as often as needed."

> [!PRINCIPLE]
> **Principle 1: Start and Stop Cycle: The Effect Connects to One Room Until It Disconnects**
>
> *Always focus on a single start and stop cycle at a time. Describe how to start synchronization in the setup function and how to stop it in the cleanup function, whether the component is mounting, updating, or unmounting.*
>
> From the component's perspective, opening the chat, switching rooms twice, and closing the chat is one mount, two updates, and one unmount. From the Effect's perspective, it is three start and stop cycles in a row, one each for the general, travel, and music rooms. When the cleanup mirrors the setup, React can start and stop the Effect whenever the room changes.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   ~return () => connection.disconnect();~ // Stops the room connection that this setup started
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[]~); // **WRONG:** treats the Effect as mount and unmount, so switching rooms never reconnects
> ```

## 2. Principle 2: Picking travel Runs the Cleanup for general First

### Both functions read `roomId`, but not from the same render

Look again at the setup function and the cleanup function inside `ChatRoom`:

```jsx title="The setup and cleanup inside ChatRoom.jsx"
useEffect(() => {
  const connection = createConnection(serverUrl, ~roomId~); // Reads roomId from the render that starts this Effect
  connection.connect();
  return () => {
    ~connection.disconnect()~; // Disconnects the connection created with that same render's roomId
  };
}, [roomId]);
```

The `useEffect` reference states the exact three-step timing for when React calls your setup and cleanup functions:
1. **When the component mounts**: "Your setup code runs when your component is added to the page."
2. **After every commit with changed dependencies**: "First, your cleanup code runs with the old props and state. Then, your setup code runs with the new props and state."
3. **When the component unmounts**: "Your cleanup code runs one final time after your component is removed from the page."

**It may look the same, or work the same at first, but it is NOT the same thing!** The cleanup function and the setup function sit inside the same `useEffect` call and both work with `connection`. When the user switches the menu from the general room to the travel room, the prop `roomId` is now `'travel'`. It is easy to assume both functions see that new value. They do not. First, the cleanup disconnects from `'general'` using the previous render's value. Only then does the new setup connect to `'travel'` using the new render's value. As React's docs state in bold: "**React always cleans up the previous render's Effect before the next render's Effect.**". In the docs' words, "React needs to re-synchronize your Effect to re-connect you to a different room."

```tree dir=right caption="What React runs after a commit where roomId changed from general to travel."
How React re-synchronizes when `roomId` changes from `'general'` to `'travel'`
- +1. Commit the new UI [`Welcome to the travel room!`] | React updates the heading text in the DOM first
- +2. Run the OLD render's cleanup [`roomId` is `'general'`] | Calls `disconnect` from the **`'general'` render**
- +3. Run the NEW render's setup [`roomId` is `'travel'`] | Calls `connect` from the **`'travel'` render**
```

### Why the cleanup still holds `'general'` after the heading says `travel`

**Beware! When the user picks `travel`, the Console prints a disconnect line for `general` after the heading on the page already welcomes the user to the travel room.** Here is what happens in order when the user picks `travel`:
1. The user picks `travel` in the room menu, and `setRoomId` asks React for a re-render.
2. The parent renders and passes the new `roomId` down to `ChatRoom`, and React commits the travel room heading to the DOM.
3. React compares the new dependency array `['travel']` with the previous array using `Object.is` (as seen in Lesson 32). Because `'travel'` and `'general'` are not equal, the docs explain: "The Effect can't be skipped."
4. React calls the cleanup function that the `general` render's setup returned. That cleanup disconnects the connection created for the general room, printing the disconnect line for `general`.
5. React calls the `travel` render's setup function, which creates a new connection and prints the connect line for `travel`.

That cleanup still holds `'general'` because every render of a component keeps its own snapshot of props and state (as seen in Lesson 15). Why? Well, as the docs explain in their Deep Dive, "Each Effect "captures" the `text` value from its corresponding render." During the first render, `roomId` was `'general'`, so the first render's Effect and its cleanup function captured that value:

```jsx title="The first render's Effect with 'general' captured in its snapshot"
() => {
  const connection = createConnection(serverUrl, ~'general'~); // Captured 'general' during the 1st render
  connection.connect();
  return () => ~connection.disconnect()~; // Always disconnects the 1st render's 'general' connection
}
```

Later, when the user clicks the Close chat button while in the `music` room, `ChatRoom` unmounts from the page. React calls the active render's cleanup one final time, printing the disconnect line for `music`.

### Why clicking Open chat in development prints three lines

**Beware! In development with Strict Mode, clicking the Open chat button prints three lines in the Console for a single mount: connect, disconnect, and connect again.** Here is what React runs when the user clicks the Open chat button in development:
1. React runs the first render's setup for `general`, which prints the first connect line for `general`.
2. React immediately calls that setup's cleanup function, which prints the disconnect line for `general`.
3. React runs the setup for `general` once more, which prints the second connect line for `general`.

```page width=text caption="After the user clicks Open chat in development: Strict Mode runs setup, cleanup, and setup to verify that the Effect can re-synchronize."
form:

  button: Close chat
```

As the docs explain: "In development, React always remounts each component once." They compare this check to "opening a door and closing it an extra time to check if the door lock works" (as seen in Lesson 32). Lesson 47 covers this development check in full, along with how saving a file in development also re-synchronizes your Effect.

When `ChatRoom` re-renders while `roomId` is still on the general room, nothing reconnects. React compares the second render's `['general']` array with the first render's array using `Object.is`. As the docs state: "**Because all dependencies are the same, React *ignores* the Effect from the second render.** It never gets called." Suppose a third render later changes `roomId` to `'travel'`. As the docs' Deep Dive notes, before applying the third render's Effect, React "needs to clean up the last Effect that _did_ run." Because the second render's Effect was skipped, React cleans up the first render's Effect before running the third render's Effect.

### What happens when you forget the cleanup function

1. The setup function opens a connection to `roomId` and returns no cleanup function.
2. The user switches the menu from `general` to `travel`. The page now displays the travel room heading, while React has no cleanup function to call for the previous room.
3. React immediately runs the new setup for `travel` and prints its connect line, with no disconnect line for `general` before it.
4. Nothing closed the connection to `general`, so it stays open in the background while the new connection to `travel` is also open. Each new room the user picks adds one more open connection.

> [!PRINCIPLE]
> **Principle 2: Re-Synchronization Order: Old Cleanup Runs with Old Values Before New Setup Runs with New Values**
>
> *After a commit with changed dependencies, React runs the previous render's cleanup with the old values before running the new setup with the new values.*
>
> Each render captures its own snapshot of props and state. When the user switches the room to `'travel'`, the cleanup function that React calls was created during the first render, so it disconnects from `'general'`. Only then does the new setup connect to `'travel'`. Omitting that cleanup leaves `'general'` connected in the background every time the user switches rooms.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();

> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   ~connection.connect();~ // **WRONG:** no cleanup returned, so every room change leaves the old connection open!
> }, [roomId]);
> ```

## 3. Principle 3: Leaving roomId Out Keeps the Chat on general

### `[roomId]` vs. `[]` when the Effect body reads `roomId`

Both Effects below run the exact same setup and cleanup reading `roomId`, and they differ only in the dependency array at the bottom:

```jsx title="Listing roomId in the dependency array: [roomId]"
useEffect(() => {
  const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId]~); // Tells React this Effect depends on roomId
```

```jsx title="Leaving roomId out of the dependency array: []"
useEffect(() => {
  const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
  connection.connect();
  return () => connection.disconnect();
}, ~[]~); // **WRONG:** tells React this Effect depends on nothing, so it never reconnects!
```

**It may look the same, or work the same at first, but it is NOT the same thing!** When the user clicks the Open chat button, both versions connect to the `general` room and show the exact same screen and Console lines. The moment the user picks `travel` in the menu, the version with `[roomId]` disconnects from the old room and connects to the travel room. The version with `[]` does nothing at all and stays connected to `general`.

React knew to re-synchronize the Effect with `[roomId]` because the dependency array included `roomId`. Why? Well, in the docs' words: "It's because *you told React* that its code depends on `roomId` by including it in the list of dependencies." The docs break that down into three steps:
1. "You knew `roomId` is a prop, which means it can change over time."
2. "You knew that your Effect reads `roomId`."
3. "This is why you specified it as your Effect's dependency."

That leads to the rule the docs put in bold: "**You can't "choose" your dependencies.**" Every reactive value your Effect reads must be listed in its dependency array. The `exhaustive-deps` linter rule checks this automatically, as in its reference example:

```jsx title="The exhaustive-deps reference example: missing userId vs. complete array"
useEffect(() => {
  fetchUser(~userId~); // Reads userId inside the Effect
}, ~[]~); // **WRONG:** Missing 'userId' in the dependency array!

useEffect(() => {
  fetchUser(~userId~); // Reads userId inside the Effect
}, ~[userId]~); // Lists userId so the Effect runs again when userId changes
```

Passing `[roomId]` and passing **no dependency array at all** are **NOT the same thing** either. Without a dependency array, the Effect re-synchronizes after every single commit of the component (as seen in Lesson 32). Suppose `ChatRoom` also has a text input for typing a chat message, as in the docs' first Challenge. When you omit the dependency array, typing every letter in the message box "*also* reconnects to the chat".

```tree caption="What happens with [roomId], with [], and with no dependency array at all when the Effect reads roomId."
Three ways to write the end of `useEffect` when the body reads `roomId`
- +With `[roomId]` [`[roomId]`] | Lists the reactive value the Effect reads | Re-synchronizes **only when `roomId` changes**
- !With `[]` [`[]`] | ~Leaves `roomId` out of the array | Never re-synchronizes when `roomId` changes; **stays stuck on `'general'`**
- !With no array at all [no array] | ~Omits the dependency array completely | Re-synchronizes **after every single commit**, even when typing in a message box
```

### What happens when a developer suppresses the linter with `[]`

Sometimes a developer silences that warning by writing an `eslint-disable-next-line` comment for `exhaustive-deps` to **suppress the linter** for that line. React's docs warn against this directly: "Don't fix these problems by suppressing the linter!"

**Beware! When you write `[]` and suppress the linter, the heading on the screen changes to the travel room, while the Console prints nothing and the app remains connected to `general`.** Here is what happens step by step:

2. The user clicks the Open chat button, and the Effect connects to `general`.
3. The user picks `travel` in the menu. The page now displays the travel room heading, while the Effect still holds the connection from the first render.
4. React compares `[]` from the new render with the previous render's `[]`. Because no item in the array changed, React skips the Effect.
5. No disconnect line and no new connect line appear in the Console. The Effect stays stuck on the **stale value** `'general'` from the first render (as seen in Lesson 34). The heading on the screen and the live chat connection no longer match.

### Stale closures and what to do when an Effect runs too often

In interviews, you will hear the `exhaustive-deps` documentation's name for this bug: leaving out a dependency "causes stale closures where the hook uses outdated values." In JavaScript, a **closure** is a function that remembers the variables from the scope where it was created. A **stale closure** is one from an earlier render that still holds outdated props or state. In the docs' Challenge on investigating a stale value bug, a pointer listener `handleMove` inside an Effect reads `canMove` while the linter is suppressed. Because the dependency array is empty, that listener "from the initial render will forever see" `canMove` as `true`, even after the user unticks the checkbox.

Effects re-run whenever a dependency changes because, in the docs' words, "Effects are reactive blocks of code." As the docs contrast them with handlers: "Unlike event handlers, which only run once per interaction, Effects run whenever synchronization is necessary." When you want an Effect to act only when a condition holds, put the condition inside the Effect body rather than wrapping the Hook itself in a condition. As the docs' Hint states: "You can't declare an Effect conditionally. However, the code inside the Effect can use conditions!" That keeps your Hook at the top level of the component, following the rules of Hooks (covered in Lesson 38).

When the linter flags a dependency that makes your Effect re-run too often, do not suppress the linter. Instead, change the code so the Effect no longer needs that reactive dependency. As the docs' Pitfall explains: "The linter only knows when the dependencies are *wrong*. It doesn't know *the best* way to solve each case." Still, "All errors flagged by the linter are legitimate." You can read the latest value inside an Effect Event without reconnecting (covered in Lesson 36). Or you can change the code so the dependency is not an object or function recreated on every render (covered in Lesson 37).

> [!PRINCIPLE]
> **Principle 3: Complete Dependencies: Never Suppress the Linter to Hide a Reactive Value**
>
> *List every reactive value that the Effect reads inside its dependency array, and never suppress the `exhaustive-deps` linter to shorten the array.*
>
> React only knows to re-synchronize an Effect when an item in the dependency array changes between renders according to `Object.is`. Leaving `roomId` out and silencing the linter keeps the first render's setup alive forever, leaving the app connected to a stale `roomId`.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[roomId]~); // Includes roomId so React reconnects when roomId changes
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[]~); // **WRONG:** suppressing exhaustive-deps lies to React about roomId!
> ```

## 4. Principle 4: A serverUrl in State Joins the Array

### `serverUrl` above the component vs. `serverUrl` in state

In Principle 1, `serverUrl` sat above the component as a fixed constant, and the dependency array was `[roomId]`. Now suppose we let the user edit the server address in a text box by moving `serverUrl` into state inside `ChatRoom`. Both versions below pass the server URL and room ID to `createConnection`, and they differ only in where `serverUrl` is declared and whether it joins the dependency array:

```jsx title="serverUrl declared above the component: not reactive"
const ~serverUrl~ = 'https://localhost:1234'; // Outside the component: never changes on a re-render

function ChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId]~); // Only roomId is reactive here
}
```

```jsx title="serverUrl declared in state inside the component: reactive"
function ChatRoom({ roomId }) {
  const [~serverUrl~, setServerUrl] = useState('https://localhost:1234'); // Inside the component: can change on a re-render

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId, serverUrl]~); // Both roomId and serverUrl are reactive and belong in the array
}
```

**It may look the same, or work the same at first, but it is NOT the same thing!** Inside the Effect, the call to `createConnection` is character-for-character identical in both versions, and both start with `'https://localhost:1234'`. With `serverUrl` declared above the component, the URL "never changes due to a re-render", so the array lists only `[roomId]`. With `serverUrl` declared in state inside the component, the URL "may change over time", so it must join the array as `[roomId, serverUrl]`. As the docs explain, "dependencies only do something when they change over time!"

React's docs use four terms to define which values belong in the dependency array:
1. **Reactive values**: React's docs state in bold that "**Props, state, and other values declared inside the component are _reactive_**". They can change on a re-render because they are calculated during rendering and participate in the React data flow.
2. **The rendering data flow**: During rendering, React passes props and context into your component, reads your state snapshots, and calculates the variables in your component body from top to bottom. That calculation during rendering is the React **rendering data flow**, and every value calculated in it is reactive.
3. **Stable values**: Some values returned by React are guaranteed "to not change on a re-render". Two examples are the state setter from `useState` and the ref object from `useRef` (as seen in Lesson 30). As the docs' Note explains: "Stable values aren't reactive, so you may omit them from the list. Including them is allowed." That is why the linter never asks you to put `setServerUrl` or `setRoomId` in the dependency array.
4. **Mutable values and global variables**: A value such as `location.pathname` or `ref.current` that "can change at any time completely outside of the React rendering data flow" is a **mutable value**. Because changing it does not trigger a re-render, it cannot be a dependency.

A regular variable calculated in the component body is also reactive and must go in the dependency array. Why? Well, as the docs explain, "It's a regular variable that you calculate during rendering," so it can change on a re-render just like props and state. Here is the docs' example where `serverUrl` is calculated during rendering from a prop and a context value from `useContext` (as seen in Lesson 28). The nullish coalescing operator `??` falls back to the default URL when the prop is null or undefined:

```jsx title="A regular variable calculated in the component body is also reactive"
function ChatRoom({ roomId, selectedServerUrl }) {
  const settings = useContext(SettingsContext);
  const ~serverUrl~ = selectedServerUrl ?? settings.defaultServerUrl; // Calculated during rendering -> reactive!

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, [roomId, ~serverUrl~]); // Must list serverUrl because it can change on a re-render
}
```

When neither `serverUrl` nor `roomId` depends on props or state, you can declare both fixed constants either above the component or inside the Effect:

```jsx title="Declaring fixed constants above the component"
const ~serverUrl~ = 'https://localhost:1234'; // Declared outside the component: not calculated during rendering
const roomId = 'general';

function ChatRoomOutside() {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[]~); // Empty array: uses zero reactive values
}
```

```jsx title="Declaring fixed constants inside the Effect"
function ChatRoomInside() {
  useEffect(() => {
    const ~serverUrl~ = 'https://localhost:1234'; // Declared inside the Effect: not calculated during rendering
    const roomId = 'general';
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[]~); // Exact same empty array: uses zero reactive values!
}
```

**Yes, it is the exact same thing** for the dependency array! Whether you declare fixed constants above the component or inside the Effect, "They aren't calculated during rendering, so they're not reactive." To remove a dependency honestly, you move it outside the component or inside the Effect. As the `useEffect` reference puts it, "you need to "prove" to the linter that it *doesn't need* to be a dependency." That also shows what `[]` truly means from the Effect's perspective: not "run only on mount", but "your Effect's code does not use *any* reactive values." If `roomId` or `serverUrl` later moves into state, "your Effect's code won't change. You will only need to add them to the dependencies."

```tree caption="Which values read by an Effect are reactive and belong in the dependency array, and which do not."
Four kinds of values an Effect can read, and which ones belong in the dependency array
- +Props, state, and variables in the component body [`roomId` `serverUrl`] | Calculated **during rendering** in the React data flow | **Reactive**: must be listed in `[roomId, serverUrl]`
- +Constants outside the component or inside the Effect [`const serverUrl` at top of file] | Never change due to a **re-render** | **Not reactive**: can be omitted, leaving `[]` when none remain
- +Stable values from React [`setServerUrl` `ref` object] | Guaranteed **not to change** on a re-render | **Stable**: omitting or including them is allowed
- !Mutable values outside rendering [`location.pathname` `ref.current`] | ~Change **outside React's rendering data flow** | **Cannot be dependencies** because changing them never triggers a re-render
```

### Adding the `Server URL:` input box to `ChatRoom.jsx`

Now we update `ChatRoom.jsx` so the server URL lives in state with a controlled input box (as seen in Lesson 20). We also add `serverUrl` to the dependency array:

```jsx title="src/components/ChatRoom.jsx"
import { useState, useEffect } from 'react';
import { createConnection } from '../chat.js';

export default function ChatRoom({ roomId }) {
  const [~serverUrl~, setServerUrl] = useState('https://localhost:1234'); // Reactive state variable

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => {
      connection.disconnect();
    };

  return (

      <label>
        Server URL:{' '}
        <input
          ~value={serverUrl}~ // Shows the current serverUrl in the input box
          ~onChange={e => setServerUrl(e.target.value)}~ // Updates serverUrl on every keystroke by the user

    </section>
  );
}
```

**Beware! Because `serverUrl` is now a reactive dependency in `[roomId, serverUrl]`, every single keystroke by the user in the URL box disconnects from the old URL and connects to the new URL.** Here is what happens when the user types `5` at the end of `https://localhost:1234`:
1. The user types `5` at the end of the `Server URL:` box.
2. `setServerUrl` updates state with the new URL and asks React to re-render `ChatRoom`. The page now shows `https://localhost:12345` in the input box.
3. React compares the new dependency array with the previous render's array using `Object.is`.
4. Because `serverUrl` changed, React calls the previous render's cleanup function, which prints the disconnect line for `https://localhost:1234`.
5. React runs the new render's setup function, which prints the connect line for `https://localhost:12345`.

### Why mutable values like `location.pathname` and `ref.current` cannot be dependencies

**Beware! Putting a mutable value such as `location.pathname` or `ref.current` in the dependency array will not make your Effect re-run when that value mutates.** Walk through the four steps from the docs' Deep Dive "Can global or mutable values be dependencies?":
1. A developer wants an Effect to re-synchronize when `location.pathname` or `ref.current` changes (as seen in Lesson 30). So the developer puts that value in the dependency array.
2. Later, some code outside React mutates `location.pathname` or assigns a new value to `ref.current`.
3. Because mutating an external object or `ref.current` happens completely outside of the React rendering data flow, it does not trigger a re-render of the component.
4. Because the component never re-renders, React never checks the dependency array. The Effect stays on the old value. As the docs explain: "even if you specified it in the dependencies, React *wouldn't know* to re-synchronize the Effect when it changes."

To subscribe to an external mutable value such as `location.pathname`, the docs recommend `useSyncExternalStore` (covered in Lesson 53). By contrast, an object or function created inside the component body during rendering has the opposite problem. It is brand-new on every render, so listing it in the dependency array re-synchronizes the Effect on every render. The docs' Challenge on fixing a connection switch shows this when a component creates a new `createConnection` function during rendering. Passing a simple boolean prop such as `isEncrypted` instead keeps the dependency equal across renders (covered in Lesson 37).

> [!PRINCIPLE]
> **Principle 4: Reactive Values: Everything Calculated in the Component Body Belongs in the Array**
>
> *Props, state, and variables in the component body are reactive and belong in the dependency array; constants outside rendering are not reactive, and mutable values cannot be dependencies.*
>
> A value is reactive when it is calculated during rendering as part of the React data flow. Moving `serverUrl` from a top-level file constant into state or calculating it inside the component means it can change on a re-render, so it must join `[roomId, serverUrl]`. Conversely, mutating `ref.current` or `location.pathname` never triggers a re-render, so listing them in the array will never re-synchronize the Effect.
>
> **DO THIS:**
> ```jsx
> function ChatRoom({ roomId }) {
>   const [~serverUrl~, setServerUrl] = useState('https://localhost:1234'); // Reactive state inside the component
>   useEffect(() => {
>     const connection = createConnection(serverUrl, roomId);
>     connection.connect();
>     return () => connection.disconnect();
>   }, ~[roomId, serverUrl]~); // Lists both reactive values read by the Effect
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ChatRoom({ roomId }) {
>   useEffect(() => {
>     const connection = createConnection(serverUrl, roomId);
>     connection.connect();
>     return () => connection.disconnect();
>   }, [roomId, ~ref.current~]); // **WRONG:** mutating ref.current never triggers a re-render, so it cannot be a dependency!
> }
> ```

## 5. Principle 5: Logging the Visit Gets Its Own Effect

### One Effect for both jobs vs. two separate Effects

Now we want our app to send an analytics visit log by calling `logVisit` whenever the user visits a chat room (as seen in Lesson 34). Both versions below log the room visit and connect to the server, differing only in whether `logVisit` shares the connection Effect or gets its own `useEffect`:

```jsx title="Putting logVisit inside the connection Effect"
useEffect(() => {
  ~logVisit(roomId);~ // **WRONG:** also runs every time serverUrl changes!
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId, serverUrl]~); // Re-runs when either roomId OR serverUrl changes
```

```jsx title="Giving logVisit its own Effect with [roomId]"
useEffect(() => {
  ~logVisit(roomId);~ // 1st process: logs a visit only when roomId changes
}, ~[roomId]~); // Re-runs only when roomId changes

useEffect(() => {
  const connection = ~createConnection(serverUrl, roomId)~; // 2nd process: reconnects when roomId or serverUrl changes
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId, serverUrl]~); // Re-runs when roomId or serverUrl changes
```

**It may look the same, or work the same at first, but it is NOT the same thing!** When the user first opens the chat or switches rooms, both versions call `logVisit` once per room change. The difference appears the moment the user types a character into the `Server URL:` box. With `logVisit` inside the connection Effect, React calls `logVisit` again on every keystroke in the URL box. With `logVisit` in its own Effect, React reconnects to the new URL without re-running the `[roomId]` visit Effect.

Those two jobs must live in two separate Effects because each Effect in your code should represent "**a separate and independent synchronization process**", as React's docs state. For our chat room, the docs explain that logging the visit "**is a separate process** from connecting." One Effect synchronizes the analytics log with `roomId`, and the other synchronizes the chat connection with the room and `serverUrl`.

To test whether two pieces of logic belong in two separate Effects or one, React's docs ask whether "deleting one Effect wouldn't break the other Effect's logic." If you delete the visit Effect, the chat connection still works. If you delete the chat connection Effect, the visit log still works. Because neither breaks when you delete the other, they are two separate synchronization processes and belong in two separate Effects.

Splitting one cohesive synchronization process into two separate Effects just to make each block look shorter is **NOT the same thing**! If two pieces of logic are part of the same synchronization process, deleting one breaks the other. As the docs warn: "if you split up a cohesive piece of logic into separate Effects, the code may look "cleaner" but will be more difficult to maintain." And: "you should think whether the processes are same or separate, not whether the code looks cleaner."

```tree caption="How to decide whether code belongs in one Effect or two separate Effects."
One Effect or two Effects? Ask whether the synchronization processes are separate
- !Two separate processes in one Effect [`logVisit` + `createConnection` in one `useEffect`] | ~Shares `[roomId, serverUrl]` between **both jobs** | Changing `serverUrl` **falsely logs a new visit** for the same room
- +One Effect per synchronization process [`[roomId]` for visit, `[roomId, serverUrl]` for connection] | +Deleting one Effect **does not break** the other | Each Effect re-synchronizes **only when its own dependencies change**
- !One cohesive process split into two Effects for looks | ~Splits one setup across two blocks | Makes the code **harder to maintain** without separating dependencies
```

### Two independent fetches, custom Hooks, and Effect Events

This same principle decides the docs' Challenge with planets and places in two menus. One menu loads the list of planets on mount, and the second menu loads the list of places for the selected `planetId`. Because those two fetches are independent synchronization processes, they belong in two separate Effects. Combining them into one Effect would make "changing the planet ... refetch the list of all planets." As the docs state: "Effects are not a tool for code reuse." When two separate Effects share similar data-fetching code, you extract a custom Hook such as `useSelectOptions` to reuse the logic cleanly (covered in Lesson 39).

Sometimes `logVisit` inside a visit Effect also needs to read the current shopping cart count without logging a new visit when the user adds an item. When one synchronization process needs to read a latest value without re-synchronizing, you extract an Effect Event with `useEffectEvent` (covered in Lesson 36).

> [!PRINCIPLE]
> **Principle 5: Independent Processes: Give Each Synchronization Process Its Own Effect**
>
> *Each Effect in your component should represent one separate and independent synchronization process, with its own dependency array.*
>
> Putting two unrelated jobs in one Effect forces both jobs to re-run whenever any dependency of either job changes. Test whether two pieces of logic belong in separate Effects by asking whether deleting one Effect would break the other. If each works on its own, give each its own `useEffect`.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   ~logVisit(roomId);~ // 1st independent process: runs only when roomId changes
> }, ~[roomId]~); // Re-runs only when roomId changes
>
> useEffect(() => {
>   const connection = ~createConnection(serverUrl, roomId)~; // 2nd independent process: reconnects when roomId or serverUrl changes
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[roomId, serverUrl]~); // Re-runs when roomId or serverUrl changes
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   ~logVisit(roomId);~ // **WRONG:** shares [roomId, serverUrl], so editing serverUrl logs a false room visit!
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, [roomId, serverUrl]);
> ```

| Aspect | The Common Mistake | The React Rule |
| :--- | :--- | :--- |
| **Thinking in component lifecycles** | Treating an Effect as mount and unmount code that runs once and forgets about props | Thinking from the Effect's perspective: a cycle that starts synchronizing in setup and stops synchronizing in cleanup |
| **Cleanup closures** | Expecting the cleanup function to read the new render's `roomId` when a prop changes | Each render's Effect and cleanup close over that render's snapshot of props and state |
| **Comparing dependencies** | Omitting the dependency array, or passing `[]` when the Effect reads a prop | React compares each dependency with `Object.is` and skips re-synchronizing when every item matches the previous render |
| **Choosing dependencies** | Deleting `serverUrl` from the dependency array so typing in the input will not reconnect | The code inside the Effect dictates the dependency array; every reactive value read inside must be listed |
| **Combining unrelated tasks** | Putting `logVisit` and `createConnection` inside the same Effect | Each Effect represents one independent synchronization process; unrelated processes belong in separate `useEffect` calls |

## For the Interview

> **The Interview Question:** What is the lifecycle of a reactive effect as its dependencies change?

### How to Answer Clearly in 30 Seconds

"Unlike a component, which mounts, updates, and unmounts, an Effect only does two things. It starts synchronizing in its setup function and stops synchronizing in its cleanup function. That cycle can repeat many times while the component stays mounted:
1. **How React knows to re-synchronize**: after each render, React compares every item in the Effect's dependency array against the previous render's array using `Object.is`. If every dependency is the same, React skips the Effect.
2. **The exact order when a dependency changes**: if even one dependency changed, React commits the new DOM first. Then it runs the **previous render's cleanup function**, which still closes over the old render's props and state. Right after that, it runs the **new render's setup function** with the new props and state. When the component finally unmounts, React runs the last cleanup one final time.
3. **Reactive values and independent Effects**: you don't choose your dependencies. Every prop, state variable, and value calculated inside the component that the Effect reads is reactive and must be in the dependency array. If a constant doesn't depend on props or state, move it outside the component. And if two tasks inside one Effect shouldn't re-run together, split them into two separate `useEffect` calls."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"When `roomId` changes from `'general'` to `'travel'`, why does the cleanup disconnect from `'general'` instead of `'travel'`?"**
   Because each render creates its own setup function and its own cleanup function, and both close over that render's props and state. When `roomId` was `'general'`, React ran that render's setup and saved the cleanup function it returned. When `roomId` changes to `'travel'`, React invokes that saved cleanup from the `'general'` render before running the new `'travel'` setup. Its closure still holds `'general'` as `roomId`, so it disconnects from the exact room it connected to.
2. **"What counts as a reactive value in React, and can I put `ref.current` or `location.pathname` in the dependency array?"**
   Reactive values are props, state variables, and any variables or functions declared inside the component body, because React re-evaluates them during rendering. Mutable values like `ref.current` or `location.pathname` can change outside of React's rendering data flow without triggering a re-render. Even if you list them in the dependency array, React will not know when they mutate and will not re-run your Effect.
3. **"What happens if I suppress the `exhaustive-deps` linter and pass `[]` so my Effect only runs once?"**
   Your Effect's closure is frozen around the initial render's props and state. When a prop or state variable updates later, React compares `[]` to `[]`, sees zero changes, and never re-synchronizes. The Effect stays connected to the stale initial values, and any timer or listener inside it keeps reading outdated state. As the React docs warn, suppressing the dependency linter leads to very confusing bugs and makes your code harder to maintain.

```tree dir=right caption="Interview summary: the complete lifecycle of a reactive Effect from mount to unmount."
The complete lifecycle of a reactive Effect
- +1. Mount [`useEffect` `[roomId, serverUrl]`] | Component appears on screen and React commits the DOM | React runs **the initial setup**, and in Strict Mode development runs **setup, cleanup, and setup** to verify the cleanup
- +2. Re-render with same dependencies [`Object.is` `true`] | Every item in the dependency array matches the previous render | React **skips the Effect**; the existing connection stays open untouched
- +3. Re-render with changed dependency [`Object.is` `false`] | At least one item in the dependency array changed | React runs **the previous render's cleanup** with the old snapshot, then runs **the new render's setup** with the new snapshot
- +4. Unmount [`cleanup`] | Component leaves the screen | React runs **the latest render's cleanup** one last time so nothing leaks
```
