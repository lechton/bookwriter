## How a Value Chosen at the Top Reaches a Component Far Below

### Passing a prop through every component vs. letting the far component ask for it

A value chosen at the top of the tree often has to reach a component far below. Suppose `App` decides that the theme is dark, and a Share button two components further down must show it. How does the value get there?

The way we already know is props. `App` gives `theme` to `Page`, and `Page` gives it to `ShareButton`:

```jsx title="With props: Page carries theme down to ShareButton"
function App() {
  return <Page ~theme="dark"~ />; // App decides the value
}

function Page({ ~theme~ }) { // Page receives theme and never uses it
  return <ShareButton theme={theme} />;
}

function ShareButton({ theme }) {
  return <button ~className={theme}~>Share</button>; // The button gets the class dark
}
```

React gives us a second way, called **context**. Here is the same tree with it:

```jsx title="With context: Page never mentions theme"
const ThemeContext = ~createContext('light')~; // Creates the context once, outside any component, with the default 'light'

function App() {
  return (
    <ThemeContext ~value="dark"~> {/* App provides the value dark */}
      <Page />
    </ThemeContext>
  );
}

function ~Page~() { // No theme here at all
  return <ShareButton />;
}

function ShareButton() {
  const theme = ~useContext(ThemeContext)~; // ShareButton asks React for the value
  return <button className={theme}>Share</button>; // The button gets the class dark
}
```

Both trees put the same Share button on the page, with the class `dark`. For the user, **yes, it is the exact same thing!** The page cannot tell how the value arrived.

What the two share is the start and the end: `App` decides the value, and `ShareButton` uses it. The one difference is the middle. With props, every component on the way receives the value and passes it on. With context, `Page` does not mention `theme` at all.

Lesson 24 gave the first way its name: **prop drilling**. Think of a note passed hand to hand along a row of people. Everyone in the middle must hold the note and pass it on, though only the last person reads it. `Page` is in the middle: it receives `theme` only to hand it to `ShareButton`. Our tree has one such component. A real page often has three or four.

The second way takes its name from everyday speech. The **context** of something is its surroundings: one word can mean two different things in two sentences, and the words around it decide which. In React, a component reads a value from its surroundings, from the components above it in the tree. React's docs say it like this: "*Context* lets the parent component make some information available to any component in the tree below it, no matter how deep, without passing it explicitly through props."

Three names in the second tree carry the idea. `createContext` creates the context, outside any component. The tag around `Page` in `App` is a **provider**: to provide is to supply, and this tag supplies the value `dark` to every component inside it, at any depth. `useContext` in `ShareButton` asks for the value, and React finds it by searching the tree above `ShareButton`. The `'light'` given to `createContext` is the **default value**: a component gets it only when React finds no provider above it.

```tree caption="Two ways for a value chosen in App to reach ShareButton: props through every component, or context that ShareButton asks for."
Two ways for `theme` to reach `ShareButton`
- +With props [`theme={theme}`] | **Every component on the way** receives `theme` and passes it on | `Page` holds a prop it **never uses**
- +With context [`useContext`] | `App` **provides** the value and `ShareButton` **asks** for it | `Page` **does not mention** `theme`
```

### What is at stake

The key idea to remember is this: context does not pass the value through the components in the middle. The component that reads it asks for it, and React finds the closest provider above that component.

What is at stake is whether the user sees the change. On our page, the user clicks `Toggle theme`, and the Share button must turn dark. With props, a middle component that forgets to pass `theme` on leaves the button with no class at all, so it never turns dark. With context, a tree that has no provider above the button leaves it light, because the button reads the default value.

Readers usually go wrong in four places:
1. They think context is one global variable for the whole app. It is not. Each component that reads it gets the value of the closest provider above it. A provider lower in the tree can give one part of the page another value.
2. They think the value given to `createContext` is the value to change later. React's docs answer: "This value never changes. React only uses this value as a fallback if it can't find a matching provider above."
3. They read the context in the same component that provides it, and get the default value.
4. They reach for context whenever a prop goes two levels down. React's docs warn: "Just because you need to pass some props several levels deep doesn't mean you should put that information into context."

### Six Principles of Context

**PRINCIPLES:** React's docs give context three steps: create it, use it from the component that needs the data, and provide it from the component that specifies the data. Each step has its own place where the page goes wrong. Two more questions follow: which provider a component finds, and when context is the wrong tool. Six principles come from that:
1. **Principle 1: `createContext` Makes `ThemeContext`**: `createContext` with the default `'light'`, called outside any component, returns a context object. The object holds no value of its own. `'light'` is only the default, used when no provider is above.
2. **Principle 2: `useContext` Leaves the Share Button Light**: `useContext` with `ThemeContext` returns the value of the closest provider above the component. With no provider above, it returns the default, so the button stays light after every click by the user.
3. **Principle 3: The `ThemeContext` Provider Turns the Share Button Dark**: Wrapping components in the `ThemeContext` provider with `value={theme}` gives `theme` to every component inside that reads it, no matter how deep. When `theme` changes, React re-renders the components that read it.
4. **Principle 4: `use` Reads the Same Theme**: `use` with `ThemeContext` returns the same value as `useContext`. The one difference is that `use` may also be called inside `if` and loops.
5. **Principle 5: The Closest `ThemeContext` Above Wins**: React searches upward from the component that reads, starting above it. A provider returned by the same component does not count, and a provider lower in the tree overrides the value for its part of the page.
6. **Principle 6: Passing JSX as `children` Skips the Middle Layers**: Before reaching for context, pass props or pass JSX as `children`. Context fits information that many distant components need, such as a theme.

Here is the complete map of those six principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`createContext` Makes `ThemeContext`** | Developers look for a way to change the value given to `createContext`, and there is none. Interviewers ask what a context object holds. | Call `createContext` with a default value outside any component, and export the result from its own file. The value lives in the provider, not in the context object. |
| **Principle 2** | **`useContext` Leaves the Share Button Light** | A component with no provider above it gets the default value on every render, with no warning in the Console, so the page looks right until the first click. | Call `useContext` at the top level of the component that needs the value, and make sure a provider sits above it. |
| **Principle 3** | **The `ThemeContext` Provider Turns the Share Button Dark** | A provider whose prop is not named `value` gives every component that reads it `undefined`, not the default. Interviewers ask how a deep component updates when state changes. | Wrap the tree in `<SomeContext value={state}>`. When the value changes, React re-renders every component inside that reads it. |
| **Principle 4** | **`use` Reads the Same Theme** | Developers think `use` is a new kind of context or a faster `useContext`. Interviewers ask why `use` may sit inside `if`. | `use` reads the same provider as `useContext`. Use it when the reading must sit inside a condition or a loop. |
| **Principle 5** | **The Closest `ThemeContext` Above Wins** | A component that reads the context it provides itself gets the default value. Developers treat context as one global value. | Read a context only in a component below its provider. Nest a provider with another value to override it for one part of the tree. |
| **Principle 6** | **Passing JSX as `children` Skips the Middle Layers** | Overusing context hides which component uses which data. Interviewers ask when not to use context. | Pass props first, then try passing JSX as `children`. Use context when distant components in different parts of the tree need the same information. |

## 1. Principle 1: `createContext` Makes `ThemeContext`

### Two lines create a context, and nothing appears on the page

The first of React's three steps is to create the context. It takes two lines in a new file:

```js title="src/ThemeContext.js"
import { ~createContext~ } from 'react'; // A function that React provides
export const ThemeContext = ~createContext('light')~; // 'light' is the default value
```

Nothing changes on the page. No component reads `ThemeContext` yet, and the other files still pass `theme` as a prop.

`createContext` is a function from React. Its only argument is the **default value**, here `'light'`. It returns a **context object**, which we name `ThemeContext`. React's docs say where to call it: "Call `createContext` outside of any components to create a context."

`ThemeContext` does not hold the theme. React's docs are direct about it: "**The context object itself does not hold any information.** It represents _which_ context other components read or provide." `ThemeContext` is the name that a provider and a reading component share, so React can match them. The value itself lives in the provider, which Principle 3 adds.

It looks like a variable that holds `'light'` and can later be set to `'dark'`, **but it is NOT the same thing!** A component that reads `ThemeContext` gets `'light'` only when no provider sits above it in the tree. React's docs say: "The default value is meant as a 'last resort' fallback. It is static and never changes over time." A fallback is what you fall back on when nothing better is there: here, the value a component gets when React finds no provider above it.

### The default value: `'light'` vs. `null`

The default matters only for a component that reads `ThemeContext` with no provider above it. Two common defaults give that component two different values:

```js title="Two defaults for the same context"
export const ThemeContext = createContext(~'light'~); // A component with no provider above it gets 'light'
export const ThemeContext = createContext(~null~); // A component with no provider above it gets null
```

These two lines are NOT the same thing for that component. With `'light'`, the button still gets a real class and still looks right. React's docs recommend a default that makes sense, because "if you accidentally render some component without a corresponding provider, it won't break. This also helps your components work well in a test environment without setting up a lot of providers in the tests." When there is no default that makes sense, React's docs use `null`, for example as the default of a context for the current user.

A theme has an obvious default, so our page uses `'light'`.

### The context lives in its own file

Our context sits in `ThemeContext.js`, not inside a component file. React's docs say: "it's common to declare contexts in a separate file", and "This works similar to importing and exporting components." Keeping it in a component file would work the exact same way. A file of its own simply lets every file import the same object.

Because `ThemeContext` is a named export, every file that needs it imports it with curly braces:

```jsx title="src/components/ShareButton.jsx" startLine="1"
import { ~ThemeContext~ } from '../ThemeContext.js'; // A named export, so curly braces
```

One file can create several contexts. React's docs show a `Contexts.js` file that exports `ThemeContext` and `AuthContext` side by side. Each one is a separate context.

### There is no way to change the default value

React's docs list this as a common question: "I can't find a way to change the context value". A developer writes `createContext` with `'light'`, reads `ThemeContext` in a component, and then wants the page to turn dark after a click by the user. So the developer looks for a way to change the `'light'` given to `createContext`.

There is none. React's docs say: "This value never changes. React only uses this value as a fallback if it can't find a matching provider above." Their fix is to "add state and wrap components in a context provider." That is Principle 3.

```tree caption="What createContext gives back: a context object that holds no value, and a default used only when no provider is above."
`createContext` with `'light'` in `ThemeContext.js`
- +The context object [`ThemeContext`] | Holds **no value** of its own | The **name** a provider and a reading component share
- +The default value [`'light'`] | Used **only** when no provider is above the reading component | **Never changes** over time
```

> [!PRINCIPLE]
> **Principle 1: createContext: The Context Object Names the Context, the Provider Holds the Value**
>
> *Call `createContext` with a default value outside any component, export the context object from its own file, and never try to change the default value.*
>
> A developer wants the theme to change and looks for a way to set `ThemeContext` to `'dark'`. There is none. `ThemeContext` holds no value. It only names which context a provider gives and a component asks for. The `'light'` given to `createContext` is a fallback for a component with no provider above it, and it never changes.
>
> **DO THIS:**
> ```js
> import { createContext } from 'react';
> export const ThemeContext = ~createContext('light')~; // Outside any component, in its own file
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ShareButton() {
>   const ThemeContext = ~createContext('light')~; // **WRONG:** a brand-new context on every render, which no provider above can match
>   const theme = useContext(ThemeContext);
>   return <button className={theme}>Share</button>;
> }
> ```

## 2. Principle 2: `useContext` Leaves the Share Button Light

### Two ways for `ShareButton` to get `theme`

The second step is to use the context from the component that needs the data. Here are two ways for `ShareButton` to get `theme`:

```jsx title="Two ways for ShareButton to get theme"
function ShareButton(~{ theme }~) { // From the theme prop on its parent's tag
  return <button className={theme}>Share</button>;
}

function ShareButton() {
  const theme = ~useContext(ThemeContext)~; // From the closest ThemeContext provider above
  return <button className={theme}>Share</button>;
}
```

**It may look the same, or work the same at first, but it is NOT the same thing!** Both create a variable named `theme`, and both show a light button when the page opens. The first gets `theme` from the tag its parent writes. The second asks React for the value of the closest `ThemeContext` provider above `ShareButton`.

`useContext` is a React Hook. React's docs say: "`useContext` is a React Hook that lets you read and subscribe to context from your component." To read the context is to get its value now. To subscribe is to ask React to run the component again whenever that value changes later. We pass it the context object, and it returns the **context value**. React's docs say which value comes back: the value "passed to the closest `SomeContext` above the calling component in the tree." With no provider above, `useContext` returns the default value.

React's docs describe what was missing before: "some way for a child to 'ask' for data from somewhere above in the tree." `useContext` is that question. As with `useState`, the call sits at the top level of the component. React's docs say: "you can only call a Hook immediately inside a React component", not inside loops or conditions. Lesson 38 covers that rule.

### The middle components stop passing `theme`

Now `ShareButton` reads the context:

```jsx title="src/components/ShareButton.jsx"
import { useContext } from 'react';
import { ThemeContext } from '../ThemeContext.js';

export default function ShareButton() {
  const theme = ~useContext(ThemeContext)~; // Asks React for the closest ThemeContext above
  return <button className={theme}>Share</button>;
}
```

So `ActionBar` no longer needs `theme`:

```jsx title="src/components/ActionBar.jsx"
import ShareButton from './ShareButton.jsx';

export default function ~ActionBar~() { // No theme in the parameters
  return (
    <div>
      <ShareButton />
    </div>
  );
}
```

`ArticleCard`, `Page`, and `App` drop it too:

```jsx title="src/components/ArticleCard.jsx" startLine="3"
export default function ~ArticleCard~() { // No theme here either
  return (
    <article>
      <h2>New Park Opens</h2>
      <ActionBar />
    </article>
  );
}
```

```jsx title="src/components/Page.jsx" startLine="3"
export default function ~Page~() { // Nor here
  return (
    <main>
      <ArticleCard />
    </main>
  );
}
```

```jsx title="src/App.jsx" startLine="4"
export default function App() {
  const [theme, setTheme] = useState('light');
  return (
    <div>
      <button onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}>
        Toggle theme
      </button>
      ~<Page />~ {/* App still holds theme, but passes it to nobody */}
    </div>
  );
}
```

### The page looks right until the user clicks

When the page opens, it looks exactly as before:

```page width=text caption="The page when it opens, with ShareButton reading ThemeContext and no provider anywhere: the Share button is light."
line: [Toggle theme]
heading: New Park Opens
line: [Share]
console: quiet
```

When the user clicks `Toggle theme`, the Share button stays light. A second click and a third change nothing either:

```page width=text caption="The same page after one click by the user on Toggle theme: the Share button is still light."
line: [Toggle theme]
heading: New Park Opens
line: [Share] | bad
console: quiet
```

```dom width=text caption="The Elements panel after one click by the user on Toggle theme: the Share button still has the class light."
<div>
  <button>Toggle theme</button>
  <main>
    <article>
      <h2>New Park Opens</h2>
      <div>
        ! <button class="light">Share</button> | note: The default value, not the state of `App`
      </div>
    </article>
  </main>
</div>
```

Why? Well, no `ThemeContext` provider exists anywhere in the tree, so `useContext` returns the default `'light'` on every render. `App`'s state changes, but nothing connects it to `ThemeContext`. Here is what happens, in order:
1. When the page opens, React renders `ShareButton`, and `useContext` looks for a `ThemeContext` provider above it. There is none, so it returns the default, `'light'`.
2. The button gets the class `light`. `App`'s state is also `'light'`, so the page looks right by chance.
3. The user clicks `Toggle theme`. `App` sets `theme` to `'dark'`, and React renders `App` again, with `Page` and everything below it.
4. `ShareButton` runs again. It still finds no provider above it, so it gets `'light'` again.

React prints nothing in the Console. Reading a context with no provider above is not an error, because the default value exists exactly for that case.

React's docs show the same moment in their own example, a page of headings: "Notice this example doesn't quite work, yet! All the headings have the same size because **even though you're *using* the context, you have not *provided* it yet.** React doesn't know where to get it!"

Reading a context and providing it are two separate steps. `App` holds `theme` and `ShareButton` reads `ThemeContext`, but a state variable reaches no reading component until some component provides it. React's docs name this case in their troubleshooting list: "You may have forgotten to wrap your component with `<SomeContext>`, or you might have put it in a different part of the tree than you thought." React Developer Tools, Lesson 64, shows which providers sit above a component.

```tree dir=right caption="Why the Share button stays light: useContext searches above ShareButton, finds no provider, and returns the default."
One click by the user on `Toggle theme`, with no provider
- +1. `App` [`setTheme`] | `App`'s state becomes **`'dark'`**
- +2. `ShareButton` runs again [`useContext`] | React searches above it and finds **no provider**
- !3. The Share button | Gets the default **`'light'`** again | The page **stays light**
```

> [!PRINCIPLE]
> **Principle 2: useContext: A Component Gets the Closest Provider Above, or the Default**
>
> *Call `useContext` at the top level of the component that needs the value. It returns the value of the closest provider above, or the default value when there is none.*
>
> The user clicks `Toggle theme`, and the Share button refuses to turn dark. `ShareButton` asks for `ThemeContext`, but no component provides it, so React hands back the default `'light'` on every render. There is no mechanism in place that connects `App`'s state to the context, and React prints no warning about it.
>
> **DO THIS:**
> ```jsx
> function ShareButton() {
>   const theme = ~useContext(ThemeContext)~; // Gets the value of the closest provider above
>   return <button className={theme}>Share</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   const [theme, setTheme] = useState('light');
>   return ~<Page />~; // **WRONG:** no provider, so ShareButton gets 'light' after every click
> }
> ```

## 3. Principle 3: The `ThemeContext` Provider Turns the Share Button Dark

### Wrapping components in the provider

The third step is to provide the context from the component that specifies the data. We write the context object as a tag around the components that should get the value:

```jsx title="Providing ThemeContext"
<ThemeContext ~value="dark"~> {/* Every component inside that reads ThemeContext gets 'dark' */}
  <Page />
</ThemeContext>
```

That tag is a **context provider**. React's docs say: "Wrap your components into a context provider to specify the value of this context for all components inside." Its one prop is `value`: "The value that you want to pass to all the components reading this context inside this provider, no matter how deep. The context value can be of any type."

In plain words, the tag tells React: if any component inside asks for `ThemeContext`, give it this value.

### `App` provides its state

`App` already holds the theme in state. So `App` provides it, with curly braces around `theme` to pass the variable and not the text:

```jsx title="src/App.jsx"
import { useState } from 'react';
import { ~ThemeContext~ } from './ThemeContext.js'; // The same context object that ShareButton reads
import Page from './components/Page.jsx';

export default function App() {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext ~value={theme}~> {/* Every component inside that reads ThemeContext gets the current theme */}
      <div>
        <button onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}>
          Toggle theme
        </button>
        <Page />
      </div>
    </ThemeContext>
  );
}
```

No other file changes. `Page`, `ArticleCard`, and `ActionBar` still have no `theme`. When the page opens, the Share button is light, as before. After one click by the user on `Toggle theme`, it turns dark:

### What happens after one click on `Toggle theme`

The Share button turns dark, although no component in the middle mentions `theme`. Why? Well, when the value of a provider changes, React re-renders the components inside it that read that context. Here is the click, in order:
1. The user clicks `Toggle theme`, and the handler sets `theme` to `'dark'`.
2. React renders `App` again. The provider now has the value `'dark'`.
3. React compares the old value with the new one, using `Object.is` from Lesson 17. `'light'` and `'dark'` are different.
4. React re-renders the components inside the provider that read `ThemeContext`. `ShareButton` calls `useContext` again, and this time it gets `'dark'`.
5. The button gets the class `dark`.

`Page`, `ArticleCard`, and `ActionBar` also run again, because their parent `App` rendered again, as Lesson 13 showed. But they pass nothing on. `ShareButton` gets `'dark'` from the provider, not from them.

This is what "subscribe" means in React's description of `useContext`. React's docs say: "The returned value is always up-to-date. React automatically re-renders components that read some context if it changes." And: "Context is not limited to static values. If you pass a different value on the next render, React will update all the components reading it below! This is why context is often used in combination with state."

```tree dir=right caption="One click by the user on Toggle theme: App's state changes the provider's value, and React re-renders ShareButton, which reads it."
One click by the user on `Toggle theme`, with the provider
- +1. `App` [`setTheme`] | `App` renders again
- +2. The provider [`value={theme}`] | Now has the value **`'dark'`** | React sees a **different value**
- +3. `ShareButton` [`useContext`] | Re-renders and gets **`'dark'`** | The Share button **turns dark**
```

### `<ThemeContext>` and `<ThemeContext.Provider>`

In code written before React 19, you will see the provider written with `.Provider` after the context name:

```jsx title="The React 19 provider and the legacy provider"
<ThemeContext ~value={theme}~> {/* React 19: the context object is the provider */}
<ThemeContext.Provider ~value={theme}~> {/* Before React 19: the legacy way */}
```

**Yes, it is the exact same thing!** React's docs say: "Starting in React 19, you can render `<SomeContext>` as a provider. In older versions of React, use `<SomeContext.Provider>`." The longer form still works, but React's docs call it legacy: an older way that keeps working so that old code does not break. React plans to retire it. The React 19 announcement says: "In future versions we will deprecate `<Context.Provider>`." To deprecate a feature is to mark it as old, before it is removed.

### A provider whose prop is not named `value`

Before this lesson, `theme` always traveled under the prop name `theme`. So a developer may write the provider the same way:

```jsx title="src/App.jsx" startLine="8"
<ThemeContext ~theme={theme}~> {/* **WRONG:** a provider reads only the prop named value */}
```

The Share button is not light. It has no class at all, and it never changes when the user clicks `Toggle theme`. Why? Well, the provider has no `value` prop, and React's docs say: "If you forget to specify `value`, it's like passing `value={undefined}`." So `ShareButton` gets `undefined`, not the default `'light'`. The default is used "**if there is no matching provider above at all**", and here a provider exists. It just provides `undefined`.

React prints one warning in the Console. The message still names the legacy form, but it is about our provider:

```devconsole caption="The Console when the page opens with a ThemeContext provider that has no value prop."
x The `value` prop is required for the `<Context.Provider>`. Did you misspell it or forget to pass it?
```

```dom width=text caption="The Elements panel with a provider that has no value: the Share button has no class."

  <button>Toggle theme</button>
  <main>
    <article>
      <h2>New Park Opens</h2>

        ! <button>Share</button> | note: `className` got `undefined`, so React writes no class
      </div>
    </article>
  </main>

```

The fix is to call the prop `value`. The same `undefined` comes from a provider written with no prop at all.

> [!PRINCIPLE]
> **Principle 3: Provider: Every Component Inside That Reads the Context Gets Its value**
>
> *Wrap the components that need the value in `<SomeContext value={state}>`; every component inside that reads the context gets that value, no matter how deep, and re-renders when it changes.*
>
> Without a provider, the state in `App` never reaches the context, and the button stays light. With the provider, `App` hands its state to React under the name `ThemeContext`. When the user clicks `Toggle theme`, the provider gets a new value, and React re-renders `ShareButton`, which reads it. The components in the middle still mention nothing. The prop must be called `value`, or every component that reads the context gets `undefined`.
>
> **DO THIS:**
> ```jsx
> <ThemeContext ~value={theme}~> {/* ShareButton turns dark after the click */}
>   <Page />
> </ThemeContext>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ThemeContext ~theme={theme}~> {/* **WRONG:** no value prop, so ShareButton gets undefined */}
>   <Page />
> </ThemeContext>
> ```

## 4. Principle 4: `use` Reads the Same Theme

### Two first lines for `ShareButton`

React 19 gives a second way to read a context. Here are two first lines for `ShareButton`:

```jsx title="Two ways to read ThemeContext in ShareButton"
const theme = ~useContext(ThemeContext)~; // The value of the closest ThemeContext provider above
const theme = ~use(ThemeContext)~; // The same value, from the same provider
```

**Yes, it is the exact same thing!** React's docs say: "When a context is passed to `use`, it works similarly to `useContext`." Both search the tree for the closest provider above the component. Both return the same value, and both make React re-render the component when that value changes.

`use` is imported from `'react'`, as `useContext` is. React's docs call it a **React API**, not a Hook: "`use` is a React API that lets you read a resource during rendering, such as a Promise or context." Its name starts with `use`, but React's docs say plainly: "Despite its name, `use` is not a Hook."

### The one difference: `use` may sit inside `if`

React's docs give the one difference: "While `useContext` must be called at the top level of your component, `use` can be called inside conditionals like `if` and loops like `for`." Their own example reads the theme only when a line should be shown:

```jsx title="Reading ThemeContext inside if"
function HorizontalRule({ show }) {
  if (show) {
    const theme = ~use(ThemeContext)~; // Allowed: use may sit inside if
    return <hr className={theme} />;
  }
  return false;
}
```

Write `useContext` in the same place, and it is NOT the same thing. `useContext` is a Hook, and a Hook inside `if` breaks the rule from Principle 2, even when the page seems to work. Lesson 38 covers that rule. `use` has a rule of its own: React's docs say "`use` must be called inside a Component or a Hook."

`use` can also read a Promise and wait for it. That is Lessons 69 and 71. In Server Components, Part Two of this book, reading context with `use` is not supported.

### `ShareButton` with `use`

Our `ShareButton` reads the theme at the top level, so either one works. We switch to `use`, the newer API:

```jsx title="src/components/ShareButton.jsx"
import { ~use~ } from 'react'; // Imported from React, like useContext
import { ThemeContext } from '../ThemeContext.js';

export default function ShareButton() {
  const theme = ~use(ThemeContext)~; // Same provider, same value as useContext
  return <button className={theme}>Share</button>;
}
```

No other file changes. The page behaves exactly as in Principle 3: the Share button is light when the page opens, dark after one click by the user on `Toggle theme`, and light again after a second.

`use` is more flexible about where it sits, but it searches the tree the same way. React's docs warn that, like `useContext`, it "always looks for the closest context provider *above* the component that calls it." A provider in the component that calls `use` does not count. Principle 5 shows what that means on our page.

```tree caption="useContext and use read the same value from the same provider; they differ only in where the call may sit."
Two ways to read `ThemeContext`
- +`useContext` | A **Hook**: only at the **top level** of the component | Gets the value of the **closest provider above**
- +`use` | A **React API**: also inside **`if`** and **loops** | **Exact same value**, from the **same provider**
```

> [!PRINCIPLE]
> **Principle 4: use: The Same Context Value, Allowed Inside if**
>
> *`use` returns the same value as `useContext`, from the closest provider above. Unlike `useContext`, it may be called inside `if` and loops.*
>
> Developers meet `use` and think it is a new kind of context. It is not. It reads the same `ThemeContext` from the same provider, and the page does not change when we switch to it. The one difference is where the call may sit: `useContext` is a Hook and stays at the top level, while `use` may also sit inside a condition or a loop.
>
> **DO THIS:**
> ```jsx
> function HorizontalRule({ show }) {
>   if (show) {
>     const theme = ~use(ThemeContext)~; // use may sit inside if
>     return <hr className={theme} />;
>   }
>   return false;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function HorizontalRule({ show }) {
>   if (show) {
>     const theme = ~useContext(ThemeContext)~; // **WRONG:** a Hook inside if breaks the rules of Hooks
>     return <hr className={theme} />;
>   }
>   return false;
> }
> ```

## 5. Principle 5: The Closest `ThemeContext` Above Wins

### A provider lower in the tree overrides the value for its part of the page

A provider can sit inside another provider of the same context. Then two components that read `ThemeContext` can get two different values:

```jsx title="A provider inside another provider of ThemeContext"
<ThemeContext value="dark">
  <ShareButton /> {/* Gets 'dark' */}
  <ThemeContext ~value="light"~> {/* A nested provider for this part of the tree */}
    <ShareButton /> {/* Gets 'light' */}
  </ThemeContext>
</ThemeContext>
```

The two `ShareButton` components run the same code and show two different themes. Each one gets the value of the closest `ThemeContext` provider above it. React's docs say: "You can override the context for a part of the tree by wrapping that part in a provider with a different value." And: "You can nest and override providers as many times as you need."

That is why context is NOT one global variable for the whole app. The value a component gets depends on where it sits in the tree. React's docs say context lets you write components that "adapt to their surroundings". That is the everyday meaning of the word *context* from the start of this lesson: the surroundings. The same `ShareButton` is light in one place and dark in another, because of where it is rendered.

React's docs compare it with CSS. When a `div` sets `color: blue`, every element inside it, no matter how deep, inherits blue, unless an element in the middle overrides it with `color: green`. React's docs say: "Similarly, in React, the only way to override some context coming from above is to wrap children into a context provider with a different value."

The comparison goes one step further. In CSS, `color` and `background-color` do not override each other. React's docs say: "Similarly, **different React contexts don't override each other.**" A provider of `ThemeContext` never changes what a component reading `AuthContext` gets. Each context made with `createContext` is completely separate from the others.

### `App` provides `'dark'` and reads `'light'`

Now suppose we want the `Toggle theme` button to follow the theme too. `App` already provides `ThemeContext`, so a developer reads it in `App`:

```jsx title="src/App.jsx"
import { useState, useContext } from 'react';
import { ThemeContext } from './ThemeContext.js';
import Page from './components/Page.jsx';

export default function App() {
  const [theme, setTheme] = useState('light');
  const buttonTheme = ~useContext(ThemeContext)~; // **WRONG:** no provider above App, so this is always 'light'
  return (
    <ThemeContext value={theme}>
      <div>
        <button className={buttonTheme} onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}>
          Toggle theme
        </button>
        <Page />
      </div>
    </ThemeContext>
  );
}
```

After one click by the user on `Toggle theme`, the Share button turns dark, and the `Toggle theme` button stays light. It stays light after every click:

```page width=text caption="After one click by the user on Toggle theme, with useContext in App: the Toggle theme button is still light, and the Share button is dark."
line: [Toggle theme] | bad
heading: New Park Opens
line: [Share] | good
console: quiet
```

```dom width=text caption="The Elements panel after the same click: the Toggle theme button keeps the class light, and the Share button has the class dark."
<div>
  ! <button class="light">Toggle theme</button> | note: `App` read the default value
  <main>
    <article>
      <h2>New Park Opens</h2>
      <div>
        + <button class="dark">Share</button> | note: `ShareButton` read the provider in `App`
      </div>
    </article>
  </main>
</div>
```

Why? Well, React starts its search above the component that reads the context, and no provider sits above `App`. The provider `App` returns is below `App`, not above it. Here is what happens, in order:
1. `App` calls `useContext` with `ThemeContext`.
2. React searches for a `ThemeContext` provider above `App`. The provider in `App`'s own JSX does not count, and there is nothing above `App`.
3. `buttonTheme` gets the default, `'light'`, on the first render and after every click.
4. `ShareButton` sits inside the provider, so it gets `App`'s state and turns dark.

React prints nothing in the Console. React's docs state the rule: a `useContext` call "is not affected by providers returned from the *same* component." The provider "**needs to be *above***" the component that reads it. The same is true for `use`, as Principle 4 quoted.

### The fix: `App` already holds the theme

`App` does not need to read the context at all. It holds the theme in state, so the toggle uses `theme` directly:

```jsx title="src/App.jsx" startLine="10"
<button ~className={theme}~ onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}> {/* App's own state */}
  Toggle theme
</button>
```

Now both buttons turn dark after one click by the user:

```page width=text caption="After one click by the user on Toggle theme, with the toggle reading the state of App: both buttons are dark."
line: [Toggle theme] | good
heading: New Park Opens
line: [Share] | good
console: quiet
```

The other fix is the one React's docs give: move the provider "*above and outside*" the component that reads it. That means moving the toggle into its own component, rendered inside the provider, which then reads `ThemeContext` like `ShareButton` does.

```tree caption="Where the reading component sits decides the value: above the provider it gets the default, inside the provider it gets the provider's value."
Who reads `ThemeContext` on our page
- !`App` reads it [`useContext` in `App`] | The provider is **in `App`'s own JSX** | React finds **no provider above** and returns **`'light'`**
- +`ShareButton` reads it [`use` in `ShareButton`] | The provider in `App` is **above** it | Gets **`App`'s state**, `'dark'` after one click
```

> [!PRINCIPLE]
> **Principle 5: Closest Provider: React Searches Upward, Starting Above the Reading Component**
>
> *A component that reads a context gets the value of the closest provider above it. A provider in the same component does not count, and a nested provider overrides the value for its part of the tree.*
>
> The user clicks `Toggle theme`, the Share button turns dark, and the `Toggle theme` button refuses to follow. `App` reads `ThemeContext`, but React looks only above `App`, and the provider sits inside it. There is no provider above `App`, so `App` gets the default. Context is not one global value: what a component reads depends on where it sits in the tree.
>
> **DO THIS:**
> ```jsx
> function App() {
>   const [theme, setTheme] = useState('light');
>   return (
>     <ThemeContext value={theme}>
>       <button ~className={theme}~>Toggle theme</button> {/* App uses its own state */}
>       <Page />
>     </ThemeContext>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function App() {
>   const [theme, setTheme] = useState('light');
>   const buttonTheme = ~useContext(ThemeContext)~; // **WRONG:** the provider is below App, so this is always 'light'
>   return (
>     <ThemeContext value={theme}>
>       <button className={buttonTheme}>Toggle theme</button>
>       <Page />
>     </ThemeContext>
>   );
> }
> ```

## 6. Principle 6: Passing JSX as `children` Skips the Middle Layers

### Two ways to take a prop out of a layout component

Context is not the only way to stop prop drilling. React's docs warn: "Context is very tempting to use! However, this also means it's too easy to overuse it." Their own example is a `Layout` component that receives `posts` only to pass them on to `Posts`. Here are two ways to write it:

```jsx title="Passing posts through Layout, and passing Posts as children"
<Layout ~posts={posts}~ /> {/* Layout receives posts only to pass them on to Posts */}
<Layout>~<Posts posts={posts} />~</Layout> {/* Layout receives the finished Posts tag as children */}
```

Both lines put the same posts on the page. The one difference is who writes the `Posts` tag. With `posts={posts}` on `Layout`, the `Posts` tag sits inside `Layout`'s own code, so `Layout` needs `posts`. With `Posts` as `children`, the top component writes the `Posts` tag between the `Layout` tags, and `Layout` only places its `children`, as Lesson 09 showed. `Layout` never touches `posts`.

React's docs say that when data passes through components that only pass it on, "this often means that you forgot to extract some components along the way." Here, to extract `Posts` is to take its tag out of `Layout`'s code and write it in the top component instead.

Passing `children` takes the data prop out of the middle, as context does. **It may look the same, but it is NOT the same thing as context!** With `children`, the top component still passes `posts` by hand, as a prop on the `Posts` tag, so anyone reading the code sees which component gets the data. With context, no tag shows where the value goes.

### Our page with `children`

The three middle components only lay out the page with plain HTML tags. So each one can take `children` in place of the tag it wrote before:

```jsx title="src/components/Page.jsx"
export default function Page({ ~children~ }) { // Whatever App writes between the Page tags
  return <main>{children}</main>;
}
```

```jsx title="src/components/ArticleCard.jsx"
export default function ArticleCard({ title, ~children~ }) { // The title, and whatever App writes inside
  return (
    <article>
      <h2>{title}</h2>
      {children}
    </article>
  );
}
```

```jsx title="src/components/ActionBar.jsx"
export default function ActionBar({ ~children~ }) { // Whatever App writes between the ActionBar tags
  return <div>{children}</div>;
}
```

Now `App` imports all four components and writes the whole tree itself, down to the Share button's tag. Because `App` writes that tag, `App` passes `theme` to `ShareButton` itself:

```jsx title="src/App.jsx"
import { useState } from 'react';
import Page from './components/Page.jsx';
import ArticleCard from './components/ArticleCard.jsx';
import ActionBar from './components/ActionBar.jsx';
import ShareButton from './components/ShareButton.jsx';

export default function App() {
  const [theme, setTheme] = useState('light');
  return (
    <div>
      <button className={theme} onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}>
        Toggle theme
      </button>
      <Page>
        <ArticleCard title="New Park Opens">
          <ActionBar>
            <ShareButton ~theme={theme}~ /> {/* App writes this tag, so App passes theme itself */}
          </ActionBar>
        </ArticleCard>
      </Page>
    </div>
  );
}
```

`ShareButton` goes back to reading its `theme` prop, as at the start of the lesson:

```jsx title="src/components/ShareButton.jsx"
export default function ShareButton({ ~theme~ }) { // From the tag that App writes
  return <button className={theme}>Share</button>;
}
```

The page shows the same elements as the context version. After one click by the user on `Toggle theme`, both buttons turn dark. No middle component mentions `theme`, and there is no context.

### Three ways, one Share button

We have now written the same page three ways:

```tree caption="Three ways to bring theme from App to ShareButton: they give the same page and differ in what the code shows."
Three ways for `theme` to reach `ShareButton`
- +Props through every layer [`<Page theme={theme} />`] | **Clear** but **verbose** | Every middle component **holds `theme`** and passes it on
- +JSX as `children` [`<ShareButton theme={theme} />` in `App`] | The prop **stays visible** in `App` | The **middle layers drop out** of the path
- +Context [`<ThemeContext value={theme}>`] | **No prop** at all | `ShareButton` **asks** for the value wherever it sits
```

React's docs give an order. First props: "It may feel like a slog, but it makes it very clear which components use which data!" Then `children`: "This reduces the number of layers between the component specifying the data and the one that needs it." And only then: "If neither of these approaches works well for you, consider context."

React's docs give one test for when context fits: "if some information is needed by distant components in different parts of the tree, it's a good indication that context will help you." They list four common cases:
1. **Theming**: an app that lets the user change its look, such as dark mode, puts a provider at the top.
2. **Current account**: many components need to know who is signed in.
3. **Routing**: "Most routing solutions use context internally to hold the current route."
4. **Managing state**: a reducer together with context, which Lesson 29 covers.

Our page keeps context. A theme is the first case in that list: on a real site, buttons, cards, menus, and footers all over the tree read it. On this small page, `children` would work just as well.

> [!PRINCIPLE]
> **Principle 6: Before Context: Try Props, Then children**
>
> *Before you use context, pass props, or extract components and pass JSX as `children`; use context when distant components in different parts of the tree need the same information.*
>
> A prop that passes through three layout components does not always need context. Often a component was not extracted. When the top component writes the tag of the component that needs the data, it passes the prop straight to it, and the layers in the middle take `children`. Context removes the prop entirely, which also hides where the data goes. Keep it for information that many distant components read, such as a theme or the current account.
>
> **DO THIS:**
> ```jsx
> <Layout>
>   ~<Posts posts={posts} />~ {/* The data goes straight to the component that uses it */}
> </Layout>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Layout ~posts={posts}~ /> {/* **WRONG:** Layout never uses posts, it only passes them on */}
> ```

```jsx title="src/components/ShareButton.jsx"
  const theme = ~use(ThemeContext)~; // Principles 2 and 4: the value of the closest provider above
  return <button className={theme}>Share</button>;
```

### How React calls the components and finds the provider

When the page opens, React calls `App` first and follows the tags down. The provider sits between `App` and `Page` in the tree, but it is not a component we wrote, and it adds no element to the page. When `ShareButton` calls `use` with `ThemeContext`, React searches upward from `ShareButton` and stops at that provider:

```tree caption="The tree of our page: the order in which React calls the components, and the provider that ShareButton finds above it."
`main.jsx` mounts `App` inside `<StrictMode>`
- +`App` [1. Called first] | Holds **`theme`** in state | Returns the provider with the toggle and `Page`
  - +The `ThemeContext` provider [`value={theme}`] | Not a component we wrote, and **no element** on the page | Gives its value to **every component inside that reads it**
    - +`Page` [2. Called second] | Renders `<main>` | **No `theme`**
      - +`ArticleCard` [3. Called third] | Renders `<article>` | **No `theme`**
        - +`ActionBar` [4. Called fourth] | Renders `<div>` | **No `theme`**
          - +`ShareButton` [5. Called fifth] | Calls `use`, and React searches **upward** to the provider | Gets **`'light'`**, then **`'dark'`** after one click
```

When the user clicks `Toggle theme`, `App` sets `theme` to `'dark'` and renders again. The provider gets a new value, and React re-renders `ShareButton`, which reads it. The Share button and the `Toggle theme` button both turn dark.

| Aspect | With props through every layer | With context |
| :--- | :--- | :--- |
| **Where the value comes from** | The `theme` prop on the tag the parent writes | The `value` of the closest `ThemeContext` provider above |
| **The components in the middle** | `Page`, `ArticleCard`, and `ActionBar` each receive `theme` and pass it on | They never mention `theme` |
| **When the value does not arrive** | A middle component that forgets to pass it leaves `theme` as `undefined` | The component that reads it gets the default value from `createContext` |
| **After a click on `Toggle theme`** | `App` renders again and passes the new `theme` down every level | The provider gets a new value, and React re-renders every component that reads it |
| **How `ShareButton` gets it** | The `theme` prop in its parameters | `useContext` at the top level, or `use`, which may also sit inside `if` |
| **What the code shows** | Every tag on the way shows where `theme` goes | No tag shows where `theme` goes, so keep it for information many components need |

## For the Interview

> **The Interview Question:** How do you pass data many levels deep without prop drilling, and how does the use() API read it?

### How to Answer Clearly in 30 Seconds

"Prop drilling is passing a prop through components that never use it, only pass it on. Context removes it in three steps:
1. **Create**: `createContext` with a default value, called outside any component, returns a context object. The object holds no value. The default is used only when there is no provider above at all.
2. **Provide**: wrap the tree in `<MyContext value={...}>`. In React 19, the context object itself is the provider, and `MyContext.Provider` is the legacy way. With state as the value, a change re-renders every component that reads the context.
3. **Read**: `useContext` or `use`, given the context object, returns the value of the closest provider above the component. `use` reads the same value, but unlike `useContext` it may sit inside `if` and loops, and it can also read Promises.

A provider in the same component does not count, and a nested provider overrides the value for its part of the tree. Before reaching for context, I try props, or passing JSX as `children`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"A component reads a context and gets the default value, or `undefined`. Why?"**
   The default value comes back when there is no provider above the reading component at all. The provider may be missing or sit in another part of the tree. Or it sits in the same component that reads the context, and React starts its search above that component. `undefined` comes back when a provider exists but has no `value` prop, for example when the prop is misspelled as `theme`. React's docs say: "If you forget to specify `value`, it's like passing `value={undefined}`." In that case React prints the warning that the `value` prop is required. The default never changes while the app runs: to change the value, put state in a provider.
2. **"What is the difference between `use` and `useContext` for reading context?"**
   They return the same value from the same closest provider, and both re-render the component when that value changes. `useContext` is a Hook, so it must sit at the top level of the component. `use` is a React API, and "Despite its name, `use` is not a Hook", so it may be called inside `if` and loops. It must still be called inside a component or a Hook, and it does not see a provider in the same component. Reading context with `use` is not supported in Server Components. `use` can also read a Promise, which `useContext` cannot.
3. **"When a context value changes, which components re-render, and does `memo` stop it?"**
   React re-renders every component that reads that context, starting from the provider that receives a different value. It compares the old and new values with `Object.is`. React's docs say: "Skipping re-renders with `memo` does not prevent the children receiving fresh context values." So a component that reads the context still updates, even deep inside a component wrapped in `memo`, Lesson 55. One trap follows from `Object.is`. An object written right inside `value`, such as an object holding a state and its setter, is a new object on every render of the provider. So every component that reads the context re-renders. Lesson 59 shows how `useMemo` and `useCallback` fix that.

```tree caption="Interview summary: what a component reading a context gets, depending on what sits above it."
What a component reading `ThemeContext` gets
- +A provider with `value` above it [`<ThemeContext value={theme}>`] | Gets **that value** | **Re-renders** when it changes, even inside `memo`
- !No provider above it at all [Provider missing, or in the **same** component] | Gets the **default value** | **No warning** in the Console
- !A provider without `value` above it [`<ThemeContext theme={theme}>`] | Gets **`undefined`**, not the default | React prints **a warning** in the Console
```
