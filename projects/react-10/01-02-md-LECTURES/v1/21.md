## How a Form Shows One Answer After Each Click

### Changing the page directly vs. changing the variable it depends on

How do we change what a page shows? Imagine our website has a light theme, and we want it to turn dark when the user clicks a button. The click is how the user asks for the change. But what actually updates the page?

There are two ways to do it:
- **Changing the element directly:** our code points at the page element and tells it what to become. This is the classic way of plain JavaScript, and it is not how we work in React.
- **The React way:** instead of touching the element, we work in two steps:
   1. **The element depends on a variable:** we say once that the theme of the page comes from a variable, such as `theme`.
   2. **We change only the variable:** when `theme` changes, every element that depends on it updates by itself.

In React, we never change the page element ourselves. We change the variable, and the page follows. The update is indirect: we reach the element through the variable it depends on.

```tree caption="Two ways to change what the page shows: change the element directly, or change the variable it depends on."
Two ways to change what the page shows
- !Change the element directly | Our code **points at the element** and changes it | Every element that must change needs **its own update**
- +Change the variable it depends on | The element **depends on a variable**; our code **changes only the variable** | **Every element that depends on it** updates by itself
```

### What is at stake

In React, this variable is a **state variable**. A theme has only two values, light and dark. A form has more: while the user types, after a wrong email, while the email is being sent, and after a right email goes through. One state variable, `status`, holds whichever of these is true right now, and the form shows only what belongs to that value.

What is at stake is that the user sees one answer at a time. When we change elements directly, we have to remove every old message by hand, and forgetting even one leaves an old error next to a new welcome line. When the form depends on `status`, changing `status` replaces the whole answer at once. Readers usually go wrong by thinking in commands, "now show this line, now hide that one", and then forgetting one hide.

### A newsletter box that must give one clear answer

At the bottom of a recipe site sits a small newsletter box: a heading, one email box, and a `Join` button. The user types an email and clicks `Join`. Depending on what just happened, that one box shows one of four things:
1. While the user types, the box and `Join`.
2. After a wrong email, the box, `Join`, and a red error line asking for a full email address.
3. While the email is being sent, a grey box, a grey `Join`, and the line `Sending...`
4. After a right email, only a welcome line in place of the whole form.

These four are the four values of `status`: `'typing'`, `'error'`, `'submitting'`, and `'success'`. The principles show how the JSX describes each value, how a click by the user or a timer that finishes sets it, and why DOM commands or separate true or false states let two opposite answers show at once.

### Four Principles of Reacting to Input with State

**PRINCIPLES:** A React form does not show and hide its lines one by one. It sets a `status` variable to `'typing'`, `'error'`, `'submitting'`, or `'success'`, and React updates what the form shows. Four practical rules follow from that:
1. **Principle 1: Each `status` Value Describes What the Form Shows**: Before writing any handler, list what the form can show and give each case a `status` value. Then write the JSX for each value from one `status` variable.
2. **Principle 2: Clicks and a Timer Only Set `status`**: Keep `status` in state. Each click by the user and each timer that finishes calls `setStatus` with the next `status` value, and the JSX stays the same.
3. **Principle 3: DOM Commands Leave Two Messages on the Page**: When code shows and hides lines by command, every branch must hide every line that should go. Forget one, and the old red line stays next to the welcome line.
4. **Principle 4: One `status` String Rules Out an Error Next to `Sending...`**: One true or false state per message lets two messages show at once when one reset is forgotten. One `status` string can only hold one value at a time.

Here is the complete map of those four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Each `status` Value Describes What the Form Shows** | A message or button that is not in the JSX for any `status` value can never show, and interviewers ask for the first step of building a form that reacts to input. | List what the form can show, give each case a `status` value, and write the JSX for each value from `status` before writing any handler. |
| **Principle 2** | **Clicks and a Timer Only Set `status`** | A handler that shows and hides lines by itself grows with every new message; a handler that calls `setStatus` stays one line. | Keep `status` in state, and let every human input and every computer input call `setStatus` with the next `status` value. |
| **Principle 3** | **DOM Commands Leave Two Messages on the Page** | A forgotten hide leaves the red error line next to the welcome line, with zero Console messages. | Describe what the form shows for each `status` value once in JSX, so changing `status` removes every line the new value does not include. |
| **Principle 4** | **One `status` String Rules Out an Error Next to `Sending...`** | Three true or false states allow eight mixes for only four `status` values, and one forgotten reset shows an error while the box is locked. | Keep states that cannot appear together in one `status` string, so every handler sets exactly one value. |

## 1. Principle 1: Each `status` Value Describes What the Form Shows

### One component with two `status` values, passed as a prop

Start with the smallest component whose `status` prop takes two values: `'typing'` and `'success'`. When its tag gives no `status`, it shows a `Join` button. When its tag says `status="success"`, it shows a welcome line instead. Here are two of its tags on one page:

```page width=text caption="Two Signup tags on one page: the first shows the Join button, the second shows the welcome line."
line: [Join]
line: Welcome to the list!
console: quiet
```

```jsx title="Signup shows the Join button or the welcome line from status"
function Signup({ ~status = 'typing'~ }) { // A tag without status gets typing
  if (~status === 'success'~) { // When status is success, return only the welcome line
    return <p>Welcome to the list!</p>;
  }
  return <button>Join</button>;
}

<Signup />
<Signup status="success" />
```

The name `status` is our own choice. React's docs say: "You could call that prop anything you like, the naming is not important." What matters is that one value says whether `Signup` shows the `Join` button or the welcome line.

A thing that is always in exactly one of a few named states is what computer scientists call a **state machine**. Think of a traffic light. It shows one light at a time: red, yellow, or green. It is never red and green together. Each light is built in advance, and a timer or the walk button only picks which one is on. `Signup` works the same way: the JSX for `'typing'` and the JSX for `'success'` are written in advance, and `status` picks which one renders.

```tree caption="A state machine is always in exactly one of a few named states, like a traffic light that shows one light at a time."
`Signup` is a small state machine [`status`]
- +`'typing'` [`<button>Join</button>`] | Drawn **in advance** in the JSX | On the page while `status` holds **typing**
- +`'success'` [`<p>Welcome to the list!</p>`] | Drawn **in advance** in the JSX | On the page while `status` holds **success**
```

Before writing any click handler, our code can give each `status` value its own tag so we can check all of them on one page. In the docs' words, "Mocking lets you quickly iterate on the UI before you wire up any logic."

### What the newsletter box shows for each of its four `status` values

Our newsletter box has four `status` values. While the user edits the address, `status` is `'typing'` or `'error'`. Once the form sends, `status` is `'submitting'` or `'success'`. These are the four strings React's docs use for the same kind of form.

When `status` is `'submitting'`, the form needs one new word: `disabled`. It is a true or false attribute of the browser, and React passes it through to the real element. React's reference for the input says: "A boolean. If `true`, the input will not be interactive and will appear dimmed." So while the email is being sent, the user cannot type in the box or click `Join` a second time.

```jsx title="src/components/NewsletterSignup.jsx"
export default function NewsletterSignup({ ~status = 'typing'~ }) { // App passes status on each tag
  if (status === 'success') {
    return <p>Welcome to the list!</p>;
  }

  return (
    <form>
      <h2>Join our newsletter</h2>
      <input ~disabled={status === 'submitting'}~ /> {/* Locks and dims the email box while sending */}
      <button type="submit" ~disabled={status === 'submitting'}~>Join</button> {/* Stops a second click while sending */}
      {status === 'submitting' && <p>Sending...</p>}
      {status === 'error' && <p style={{ color: 'red' }}>Please enter a full email address.</p>}
    </form>
  );
}
```

`App` now renders one tag for each `status` value, each under a small heading with that value:

```jsx title="src/App.jsx"
import NewsletterSignup from './components/NewsletterSignup.jsx';

export default function App() {
  return (
    <main>
      <h4>typing</h4>
      <NewsletterSignup ~status="typing"~ /> {/* One tag for each status value */}
      <h4>error</h4>
      <NewsletterSignup status="error" />
      <h4>submitting</h4>
      <NewsletterSignup status="submitting" />
      <h4>success</h4>
      <NewsletterSignup status="success" />
    </main>
  );
}
```

`NewsletterSignup` never sets `status` itself. `App` writes it on each tag, and the default in the parameter list gives `'typing'` to a tag that has none.

In the Elements panel, the grey copy carries the `disabled` attribute, and the success copy holds no form at all:

> [!PRINCIPLE]
> **Principle 1: `status` Values: Each `status` Value Describes What the Form Shows**
>
> *Before writing any handler, list what the form can show, give each case a `status` value, and write the JSX for each value from `status`.*
>
> A message or a locked button that is never written in the JSX can never appear on the page. Write the JSX for `'typing'`, `'error'`, `'submitting'`, and `'success'` first, driven by one `status` value. The click and timer handlers come later, and all they do is set `status`.
>
> **DO THIS:**
> ```jsx
> function NewsletterSignup({ status = 'typing' }) {
>   if (~status === 'success'~) { // Each status value returns what the form shows, before any handler
>     return <p>Welcome to the list!</p>;
>   }
>   return <button disabled={status === 'submitting'}>Join</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function NewsletterSignup() {
>   return <button ~onClick={handleJoin}~>Join</button>; // **WRONG:** starts from the click, and the JSX for submitting, error, and success is written nowhere, so those messages can never show!
> }
> ```

## 2. Principle 2: Clicks and a Timer Only Set `status`

### `status` from the tag vs. `status` from state

In Principle 1, `App` passed `status` on each tag. On a real page, when the user clicks `Join`, our code calls `setStatus('submitting')`, and React changes the page to show `"Sending..."`. So `status` moves from the tag into state:

```jsx title="status written on the tag"
<Signup ~status="error"~ /> {/* App sets status to error on the tag */}
```

```jsx title="status held in state"
const [status, setStatus] = useState('typing');
<button onClick={() => ~setStatus('error')~}>Join</button> {/* Clicking Join sets status to error */}
```

Yes, it is the exact same thing! The JSX for each `status` value does not change at all. Whether `'error'` arrives on the tag or lives in state, `status === 'error'` shows the exact same red line. Only the place where `status` comes from is different.

Here is the smallest component that keeps `status` in state. When the page opens, it shows `Join`:

```page width=text caption="Signup when the page opens: status starts as typing, so the Join button shows."
line: [Join]
console: quiet
```

```jsx title="Signup keeps status in state"
function Signup() {
  const [status, setStatus] = useState('typing');
  if (status === 'success') {
    return <p>Welcome to the list!</p>;
  }
  return <button onClick={() => ~setStatus('success')~}>Join</button>; // Clicking Join sets status to success
}
```

```page width=text caption="The same page after the user clicks Join: the button is gone, and the welcome line shows."
line: Welcome to the list! | good
console: quiet
```

There is no line in our code that removes the button. React removes it, because when `status` is `'success'`, `Signup` returns only the welcome line and no button.

### Human inputs and computer inputs

Two kinds of things can change `status` and update what the form shows. React's docs call them human inputs and computer inputs:
- A **human input** is something the user does, such as typing in the box or clicking `Join`.
- A **computer input** is something that happens without the user. The docs give "a network response arriving, a timeout completing, an image loading" as examples.

Think of the traffic light again. The walk button is a human input, and the timer inside the light is a computer input. Both only switch which light is on. It is the same in React: "In both cases, you must set state variables to update the UI."

Our newsletter box has both kinds. The user types and clicks `Join`. A timer of one second stands in for the server's answer, and when it finishes, it changes `status` from `'submitting'` to `'success'`. React's docs suggest drawing "each state on paper as a labeled circle, and each change between two states as an arrow". Here are the five changes between the four `status` values of our form:

```tree caption="The five changes between the four status values of the newsletter box, and the input that causes each one."
What changes `status` in the newsletter box
- +typing to error | **Human input**: the user clicks **Join**, and the email has no `@`
- +typing to submitting | **Human input**: the user clicks **Join**, and the email has an `@`
- +error to error | **Human input**: the user clicks **Join** again, and the email still has no `@`
- +error to submitting | **Human input**: the user clicks **Join**, and the email now has an `@`
- +submitting to success | **Computer input**: the **timer finishes** after one second
```

### The newsletter box with `status` in state

Now `NewsletterSignup` gets its own state. The `status` prop is gone. `email` holds the text of the box, and `status` holds `'typing'`, `'error'`, `'submitting'`, or `'success'`. The JSX stays the same as in Principle 1, with three additions: the box is controlled, the form has `onSubmit`, and `Join` starts disabled while empty.

```jsx title="src/components/NewsletterSignup.jsx"
import { useState } from 'react';

export default function NewsletterSignup() {
  const [email, setEmail] = useState('');
  const [status, setStatus] = useState('typing');

  function handleSubmit(e) {
    ~e.preventDefault();~ // Without it, the browser reloads the page and the welcome line never shows
    if (email.includes('@')) {
      ~setStatus('submitting');~ // Human input: the user clicked Join with a full email
      setTimeout(() => {
        ~setStatus('success');~ // Computer input: the timer finished, standing in for the server
      }, 1000);
    } else {
      ~setStatus('error');~ // Human input: the user clicked Join without an @
    }
  }

  if (status === 'success') {
    return <p>Welcome to the list!</p>;
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Join our newsletter</h2>
      <input
        value={email}
        onChange={e => setEmail(e.target.value)}
        disabled={status === 'submitting'}
      />
      <button type="submit" ~disabled={email.length === 0 || status === 'submitting'}~> {/* Off while the box is empty or while sending */}
        Join
      </button>
      {status === 'submitting' && <p>Sending...</p>}
      {status === 'error' && <p style={{ color: 'red' }}>Please enter a full email address.</p>}
    </form>
  );
}
```

Calling `email.includes` with `'@'` returns true when the text in the box contains the at sign. `Join` stays off while the box is empty, and that comes straight from `email.length`, so `status` needs no fifth value such as `'empty'` for an empty box. Lesson 22 covers when a value belongs in state and when it is computed from other values.

`App` now renders one `NewsletterSignup` tag with no prop on it:

```jsx title="src/App.jsx"
import NewsletterSignup from './components/NewsletterSignup.jsx';

export default function App() {
  return (
    <main>
      ~<NewsletterSignup />~ {/* No status prop on the tag: NewsletterSignup keeps status in state */}
    </main>
  );
}
```

### The red line goes away with no line of code hiding it

React removes the red line, and no line of our code does. Why? Well, the handler never touched the red line. It only called `setStatus('submitting')`, and when `status` is `'submitting'`, the JSX holds no red line. Here is what happens after the user's second click, in order:
1. `status` holds `'error'`, so the red line is on the page.
2. The user clicks `Join` with `mary@mail.com` in the box.
3. The submit handler calls `setStatus` with `'submitting'` and starts the timer.
4. React calls the component again, and this time `status` holds `'submitting'`.
5. `status === 'error'` is now false, so the returned JSX holds no red line.
6. React compares this JSX with the last one and removes the red paragraph from the page. It does not hide it with a style: the element is gone from the Elements panel.

One second later, the timer finishes and calls `setStatus` with `'success'`. React calls `NewsletterSignup` again, and the early `return` replaces the whole form with the welcome line, although the user did nothing:

```page width=text caption="One second after the second click: the whole form is replaced by the welcome line."
line: Welcome to the list! | good
console: quiet
```

> [!PRINCIPLE]
> **Principle 2: Inputs: Clicks and a Timer Only Set `status`**
>
> *Keep `status` in state, and let every human input and computer input call `setStatus` with the next `status` value while the JSX stays unchanged.*
>
> A handler that shows the sending line, then hides it, then shows the welcome line has to know every line on the page. A handler that only calls `setStatus` knows nothing about the DOM elements. The user's click sets `status` to `'error'` or `'submitting'`. One second later, the finished timer sets `status` to `'success'`. React then updates the page from the JSX already written, and it removes every line the new `status` value does not include.
>
> **DO THIS:**
> ```jsx
> function handleSubmit(e) {
>   e.preventDefault();
>   ~setStatus('error');~ // Sets status to error; the JSX decides what the form shows
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleSubmit(e) {
>   e.preventDefault();
>   ~document.getElementById('error').style.display = '';~ // **WRONG:** edits the page by hand instead of calling setStatus, so every other line must be hidden by hand too!
> }
> ```

## 3. Principle 3: DOM Commands Leave Two Messages on the Page

### Switching one line on vs. setting `status`

The opening of this lesson put the two ways side by side. Both change what the page shows after the user clicks `Join`. The one difference is who edits the page. In plain JavaScript, two browser commands switch a line on and off:

```js title="Switching a line off and on with DOM commands"
~error.style.display = 'none';~ // The browser hides the red line
~error.style.display = '';~ // The browser shows the red line again
```

```jsx title="Setting status with a state change"
~setStatus('error');~ // Sets status to error; React updates the page
{~status === 'error'~ && <p>Please enter a full email address.</p>} {/* Drawn only while status is error */}
```

It may look the same, or work the same at first, but it is NOT the same thing! A DOM command changes one element and leaves every other element as it was. A state change sets `status` to a new value, and React removes whatever the JSX for that `status` value does not include. You can see the difference only on the second try.

### The newsletter box built with DOM commands

Here is the same newsletter box in `plain-newsletter.html`, with no React. Both message lines start hidden, and the script switches them on by command:

```html title="plain-newsletter.html"
<form id="signup">
  <h2>Join our newsletter</h2>
  <input id="email" />
  <button>Join</button>
</form>
<p id="error" style="display: none; color: red">Please enter a full email address.</p>
<p id="welcome" style="display: none">Welcome to the list!</p>

<script>
  const form = document.getElementById('signup');
  const email = document.getElementById('email');
  const error = document.getElementById('error');
  const welcome = document.getElementById('welcome');

  form.addEventListener('submit', e => {
    e.preventDefault();
    if (email.value.includes('@')) {
      form.style.display = 'none';
      ~welcome.style.display = '';~ // **WRONG:** shows the welcome line, but no line here hides the red one!
    } else {
      ~error.style.display = '';~ // Switches on the red line after a wrong try
    }
  });
</script>
```

The browser supplies `e` to the listener, and `email.value` is the text the user typed, kept on the box element itself.

### The red line stays next to the welcome line

The user tries `mary`, then `mary@mail.com`, as before. The page ends with the red line and the welcome line together. Here is the order of events:
1. The user types `mary` and clicks `Join`.
2. The `else` branch runs `error.style.display = ''`, and the red line shows.
3. The user types `mary@mail.com` and clicks `Join`.
4. The success branch runs `form.style.display = 'none'` and `welcome.style.display = ''`.
5. No line runs `error.style.display = 'none'`, so the red line stays switched on.

The fix in plain JavaScript is one more command, `error.style.display = 'none'`, in the success branch. But every branch has to hide every line that should go, and that list grows. With four `status` values, DOM commands must handle the change from each one to each of the other three, which is up to twelve changes. In React, the JSX describes what the form shows for each of the four `status` values. A fifth `status` value adds one more branch to the JSX, while the DOM commands have to be checked again for every change that touches it. React's docs put it this way: the React version is longer, "but it is much less fragile".

> [!PRINCIPLE]
> **Principle 3: Imperative Pitfall: DOM Commands Leave Two Messages on the Page**
>
> *When code shows and hides lines by command, every branch must hide old lines; with `status`, the JSX describes what the form shows for each value once, so old lines disappear.*
>
> A DOM command switches one element on and leaves everything else as it was. After a wrong try and then a right one, the success branch shows the welcome line while the old red line stays visible. The user reads an error and a welcome at the same time. With `status`, the red line is rendered only when `status === 'error'`. When `status` changes to `'submitting'` or `'success'`, React removes the red line, and no branch has to remember to hide it.
>
> **DO THIS:**
> ```jsx
> {~status === 'error'~ && <p style={{ color: 'red' }}>Please enter a full email address.</p>} {/* The red line exists only when status is error */}
> ```
>
> **DO NOT DO THIS:**
> ```js
> if (email.value.includes('@')) {
>   ~welcome.style.display = '';~ // **WRONG:** the red line from the last try stays on the page next to the welcome line!
> } else {
>   error.style.display = '';
> }
> ```

---

## 4. Principle 4: One `status` String Rules Out an Error Next to `Sending...`

### Two true or false states vs. one string

Both ways below keep in state what the newsletter box shows. The one difference is how many state variables hold it. One way gives each message its own true or false state, which developers call a flag, like a small flag that is either up or down. The other way keeps one `status` string:

```jsx title="One true or false state per message"
const [~isError~, setIsError] = useState(false); // One switch for the red error line
const [~isSubmitting~, setIsSubmitting] = useState(false); // A separate switch for Sending...
```

```jsx title="One status string"
const [~status~, setStatus] = useState('typing'); // Holds one status string at a time
```

It may look the same, or work the same at first, but it is NOT the same thing! As long as every handler sets every flag, both show the same form at each step. But two true or false values allow four mixes: both false, only the error line, only `Sending...`, and both true. Both true shows the error line and `Sending...` at once. The `status` string can hold only one string at a time, such as `'error'` or `'submitting'`, never both at once. React's docs: "There are four possible combinations of two booleans, but only three correspond to valid states."

Think of the traffic light one last time. Three separate switches for red, yellow, and green could turn on red and green together. One dial with three positions cannot.

A mix of state values for things that should never appear on the page together is called an **impossible state**. React's docs ask you to "prevent the cases where the state in memory doesn't represent any valid UI that you'd want a user to see." The docs also call such a pair a **paradox**, an everyday word for something that says two opposite things at once. Their example is that `isTyping` and `isSubmitting` cannot both be true.

### The newsletter box with three true or false states

Suppose a developer builds `NewsletterSignup` with one true or false state per message. The JSX is the same as before, except that each `status === ...` check becomes a flag. In the branch for a full email, the developer turns on `isSubmitting` and forgets to turn off `isError`:

```jsx title="src/components/NewsletterSignup.jsx"
const [email, setEmail] = useState('');
const [isError, setIsError] = useState(false);
const [isSubmitting, setIsSubmitting] = useState(false);
const [isSuccess, setIsSuccess] = useState(false);

function handleSubmit(e) {
  e.preventDefault();
  if (email.includes('@')) {
    ~setIsSubmitting(true);~ // **WRONG:** turns on Sending..., but never resets isError to false!
    setTimeout(() => {
      setIsSubmitting(false);
      setIsSuccess(true);
    }, 1000);
  } else {
    setIsError(true);
  }
}
```

The JSX reads the three flags:

```jsx title="src/components/NewsletterSignup.jsx"
if (isSuccess) {
  return <p>Welcome to the list!</p>;
}

return (
  <form onSubmit={handleSubmit}>
    <h2>Join our newsletter</h2>
    <input value={email} onChange={e => setEmail(e.target.value)} ~disabled={isSubmitting}~ /> {/* Grey and locked while isSubmitting is true */}
    <button type="submit" disabled={email.length === 0 || isSubmitting}>Join</button>
    {isSubmitting && <p>Sending...</p>}
    {~isError~ && <p style={{ color: 'red' }}>Please enter a full email address.</p>} {/* Still true from the first try */}
  </form>
);
```

### The red line shows next to `Sending...`

The user tries `mary`, then `mary@mail.com`. The page shows the red line and `Sending...` together, and the box is grey, so the user cannot fix what the red line asks to fix:

```page width=text caption="The version with three flags after the second click: the red line shows under Sending..., and the box and Join are grey."
heading: Join our newsletter
form:
  field: | mary@mail.com
  submit: Join
line: Sending...
line: Please enter a full email address. | bad
console: quiet
```

Both messages appear on the page at the same time. Why? Well, `isError` was turned on by the first click and never turned off by the second. Here is the order of events:
1. The user types `mary` and clicks `Join`. The handler sets `isError` to `true`, and the red line shows.
2. The user types `mary@mail.com` and clicks `Join`.
3. The handler sets `isSubmitting` to `true` and starts the timer. Nothing sets `isError` back to `false`.
4. React renders with `isError` true and `isSubmitting` true.
5. The page shows `Sending...` and the red line together, with the box locked.
6. One second later, the timer sets `isSubmitting` to false and `isSuccess` to true. The early `return` then shows the welcome line, while `isError` stays true in memory.

The Console stays quiet the whole time. React has no way to know that these two flags should never be true together. As React's docs note, you must never "show an error message and disable the input at the same time", or the user cannot fix the address.

### Three flags allow eight mixes for four `status` values

With three flags, each one true or false, there are two times two times two, which is eight mixes. Our form has only four valid states: `'typing'`, `'error'`, `'submitting'`, and `'success'`. The other four mixes are impossible states, and each forgotten reset can land the page in one of them:

```tree caption="Three true or false flags allow eight mixes; one status string holds only typing, error, submitting, or success."
How many mixes can the state of the newsletter box hold?
- !Three flags [`isError` `isSubmitting` `isSuccess`] | **8 mixes** for only **4 valid states** | Every handler must **reset every flag**, or an impossible state renders
- +One string [`status`] | Exactly **4 values**: typing, error, submitting, success | Every handler sets **one value**, so two messages can **never** clash
```

The fix is the `status` version of Principle 2, which is our finished page. There, the branch for a full email calls `setStatus` with `'submitting'`. That one call leaves `'error'` behind, because one string cannot hold `'error'` and `'submitting'` at the same time. On the same two tries, the red line goes away the moment `Sending...` appears.

When the JSX would read better with a flag, compute a local constant from `status === 'submitting'` right before `return` instead of storing a second state. The flag is then computed on every render and can never disagree with `status`.

> [!PRINCIPLE]
> **Principle 4: Impossible States: One `status` String Rules Out an Error Next to `Sending...`**
>
> *When states such as `'error'`, `'submitting'`, and `'success'` cannot appear together, keep them in one `status` string instead of separate booleans, so every handler sets one value and prevents impossible mixes.*
>
> Separate flags for the error line, `Sending...`, and the welcome line let the page show two of them at once. Forget one reset, and the red line shows next to `Sending...` while the box is locked, with zero Console messages. One `status` string holds only one value at a time. Setting `status` to `'submitting'` replaces `'error'`, so the two messages cannot render together.
>
> **DO THIS:**
> ```jsx
> const [status, setStatus] = useState('typing');
> ~setStatus('submitting');~ // Replaces error with submitting in one call
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [isError, setIsError] = useState(false);
> const [isSubmitting, setIsSubmitting] = useState(false);
> ~setIsSubmitting(true);~ // **WRONG:** isError is still true, so the red line shows next to Sending...!
> ```

## Putting All Four Principles Together

### The complete newsletter box

Here is the finished project. The entry file mounts `App` inside `StrictMode`:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

`App` renders one newsletter box:

```jsx title="src/App.jsx"
import NewsletterSignup from './components/NewsletterSignup.jsx';

export default function App() {
  return (
    <main>
      ~<NewsletterSignup />~ {/* NewsletterSignup keeps status in its own state */}
    </main>
  );
}
```

`NewsletterSignup` renders what the form shows from one `status` string:

```jsx title="src/components/NewsletterSignup.jsx"
import { useState } from 'react';

export default function NewsletterSignup() {
  const [email, setEmail] = useState('');
  const [~status~, setStatus] = useState('typing'); // Principle 4: one string, one status value at a time

  function handleSubmit(e) {
    e.preventDefault();
    if (email.includes('@')) {
      ~setStatus('submitting');~ // Principle 2: the user's click sets status to submitting
      setTimeout(() => {
        ~setStatus('success');~ // Principle 2: the finished timer sets status to success
      }, 1000);
    } else {
      setStatus('error');
    }
  }

  if (~status === 'success'~) { // Principle 1: when status is success, return only the welcome line
    return <p>Welcome to the list!</p>;
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Join our newsletter</h2>
      <input
        value={email}
        onChange={e => setEmail(e.target.value)}
        disabled={status === 'submitting'}
      />
      <button type="submit" disabled={email.length === 0 || status === 'submitting'}>
        Join
      </button>
      {status === 'submitting' && <p>Sending...</p>}
      {~status === 'error'~ && <p style={{ color: 'red' }}>Please enter a full email address.</p>} {/* Principle 3: the red line renders only when status is error */}
    </form>
  );
}
```

### How React calls the components in order

When the page opens, React calls `App` first. Because that component returns `NewsletterSignup`, React calls `NewsletterSignup` next. After that, every keystroke, every click on `Join`, and the finished timer update state inside `NewsletterSignup`, so React calls only that component again. `App` holds no state and is not called again:

```tree dir=right caption="The order in which React calls the components of the newsletter page: both on page load, then only NewsletterSignup after each state change."
How React calls the components of the newsletter page
- +1. Page load [`App`] | React calls **App** first | App returns `<main>` with one `<NewsletterSignup />`
- +2. Page load [`NewsletterSignup`] | React calls **NewsletterSignup** | `status` holds **typing**, so the empty form shows
- +3. After each keystroke or click [`setEmail` `setStatus`] | React calls **only NewsletterSignup** again | The JSX returns what the form shows for the new `status`
- +4. After the timer [`setStatus`] | React calls **NewsletterSignup** again | `status` holds **success**, so only the welcome line shows
```

| Aspect | The Command Habit | The React Rule |
| :--- | :--- | :--- |
| **What the form shows** | Start from the click and decide what it should show and hide | List each `status` value, such as `'typing'`, `'error'`, `'submitting'`, and `'success'`, and write its JSX before any handler |
| **The handlers** | Show the sending line, then hide it, then show the welcome line | Call `setStatus` with the next `status` value, from a human input or a computer input |
| **The old line** | Switch the red line on with `style.display`, and forget to switch it off | The red line renders only when `status === 'error'`, so React removes it when `status` changes |
| **The state shape** | One true or false state per message, with eight mixes for four `status` values | One `status` string that can hold only one of the four values |

## For the Interview

> **The Interview Question:** How do you design a component that reacts to input with state instead of touching the DOM?

### How to Answer Clearly in 30 Seconds

"Instead of showing and hiding DOM elements by command, I keep a `status` variable in state and write the JSX for each value it can hold: `'typing'`, `'error'`, `'submitting'`, and `'success'`. First, I write the JSX for each `status` value so I can see what the form shows in every case before wiring up handlers. Then I find what changes `status`: human inputs such as typing and clicking, and computer inputs such as a network response or a timer. I keep `status` in `useState`, and each handler only calls `setStatus` with the next value. React updates the DOM to match. I use one `status` string rather than several booleans, because booleans allow impossible mixes, such as an error message next to a locked, sending form."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why one `status` string instead of `isError`, `isSubmitting`, and `isSuccess`?"**
   Three booleans allow eight combinations for only four `status` values: `'typing'`, `'error'`, `'submitting'`, and `'success'`. If one handler forgets a reset, the page shows an impossible mix, such as an error line next to `Sending...` on a disabled form, with zero warnings. One `status` string can hold only one value at a time, so calling `setStatus('submitting')` always replaces `'error'`. React's docs put it as moving pieces: "you want as few 'moving pieces' as possible. More complexity leads to more bugs!" When the JSX needs a boolean, I compute it, as in `const isSubmitting = status === 'submitting';`. For a stricter model, there is `useReducer`, or a state machine library such as XState, and React 19 form actions come with a built-in pending state.
2. **"Should an empty email box be its own status, such as `'empty'`?"**
   No. Whether the box is empty is already in `email`, so I compute it: `disabled={email.length === 0 || status === 'submitting'}`. Storing it as a separate state would add one more value that can disagree with the text in the box. React's docs remove `isEmpty` from their own example for the same reason, and keep only the state they cannot remove "without breaking the functionality".
3. **"What does React do to the DOM when `status` changes from `'error'` to `'submitting'`?"**
   React calls the component again with `status` set to `'submitting'`, gets the returned JSX, and compares it with the JSX of the last render. It then changes only what differs: it removes the red error `<p>`, adds the `Sending...` line, and sets `disabled` on the box and the button. The heading stays as it was, and the box stays the same element, so it keeps the text `mary@mail.com`. React's docs compare this to a single `updateDOM` function that syncs every element from the current state. Under the hood, React does that same sync, except it "avoids touching the DOM for properties that have not changed".

```tree dir=right caption="Interview comparison: showing and hiding elements by command vs. setting status and letting React update the form."
Commands vs. `status` in an interview
- !DOM commands or one boolean per message [`style.display` `isError`] | Every branch must **reset every element or flag** | One forgotten reset shows **two answers at once**
- +One `status` string [`setStatus`] | Each handler sets **one `status` value** | React updates the form and **removes every line the new value does not include**
```
