## Why We Describe Each Look Instead of Changing the Page by Hand

### One Subscribe button, written two ways

Many pages have a button that changes the page when you click it. Here is the smallest one we can think of. When the page opens, it shows one Subscribe button:

```page width=text caption="A small page with one Subscribe button, as it looks when the page opens."
line: [Subscribe]
```

One click should change two things. First, the button should turn off, so nobody subscribes twice. Second, a line that says Thanks! should appear under it.

We can build this in two ways. The first way uses plain JavaScript, with no React at all. The HTML file holds the button, and a thank-you line that starts hidden:

```html title="index.html"
<button id="subscribe">Subscribe</button>
<p id="thanks" class="hidden">Thanks!</p>
```

The word `hidden` is our own CSS class. Our stylesheet gives it one rule, `display: none`. That rule tells the browser not to show any element that has this class. So when the page opens, the thank-you line is in the HTML, but the user cannot see it.

Next, a small script tells the button what to do on a click:

```js title="subscribe.js"
const button = document.getElementById('subscribe');
const thanks = document.getElementById('thanks');

button.addEventListener('click', () => {
  ~button.disabled = true~; // Command 1: turn the button off
  ~thanks.classList.remove('hidden')~; // Command 2: take the hidden class off the thank-you line
});
```

We met `document.getElementById` in Lesson 1. The browser gives it to us. It finds the element whose `id` attribute matches the text we pass. We met `addEventListener` in Lesson 4. It hands our function to the browser, and the browser calls that function on every click.

Two words inside the click handler are new. Both come from the browser:
- **`disabled`** is a property of every button and every text box. When our code sets it to `true`, the element ignores clicks and typing, and it looks dimmed. When our code sets it back to `false`, the element works again.
- **`classList`** is the list of CSS classes on an element. Its `remove` method takes a class off, so taking `hidden` off makes the element show again. Its `add` method puts a class on, so putting `hidden` back makes the element hide again.

The second way uses React. The whole page is one small component:

```jsx title="Subscribe.jsx"
import { useState } from 'react';

export default function Subscribe() {
  const [done, setDone] = useState(false);
  return (
    <>
      <button ~disabled={done}~ onClick={() => setDone(true)}>Subscribe</button> {/* Off when done is true */}
      ~{done && <p>Thanks!</p>}~ {/* Shown only when done is true */}
    </>
  );
}
```

Here `done` is a piece of state, and it starts as `false`. The button gets `disabled={done}`. As we saw in Lesson 3, the curly braces pass the value of `done` itself. So at the start, the button gets `disabled={false}`, and it works. The line under the button uses the double ampersand from Lesson 10. At the start, the double ampersand gives `false`, and React creates nothing for it. So there is no thank-you line on the page at all.

Now the user clicks Subscribe once. Both versions give the same page:

```page width=text caption="The same page after one click on Subscribe: the button is now disabled, and the thank-you line is shown."
line: [Subscribe]
line: Thanks! | good
```

The page is the same, but the way we got there is very different. Here is what the plain version does, in order:
1. The user clicks Subscribe, and the browser calls our function.
2. The first line of the function sets `disabled` to `true`, so the button turns off.
3. The second line takes `hidden` off the thank-you line, so the line shows.

And here is what the React version does, in order:
1. The user clicks Subscribe, and React calls the function in `onClick`.
2. That function calls `setDone` with `true`. The setter stores `true` in `done` and asks React to draw the component again.
3. React calls `Subscribe` again. This time `done` is `true`.
4. So the JSX now says `disabled={true}` for the button, and the double ampersand now gives the thank-you paragraph.
5. React compares this result with the last one, as we saw in Lesson 13. It finds two differences. So it turns the button off and adds the paragraph to the page.

Look at what each click handler talks about. The plain handler names both elements and tells each one what to do. If one more element had to change on the click, the plain handler would need one more line. The React handler names no element at all. It changes one value, `done`. The JSX already says how the page looks when `done` is `true`. React does the work of changing the page.

In Lesson 1, we gave these two styles their names:
- **Imperative** code gives a command for every step: turn this off, show that.
- **Declarative** code describes the result: when `done` is true, the button is off and the thank-you line is there.

Think of a car ride across a city. In the imperative style, you sit next to the driver and call out every turn: left here, right at the bakery, straight on to the bridge. In the declarative style, you get into a taxi and say only the address. The taxi driver knows the streets and finds the way. In React, the handler says the address, and React is the driver.

### A promo code box that has five looks

The Subscribe button has only two looks: before the click and after it. Real forms have more. Look at the checkout page of any online shop. Under the cart, there is often a small box called Promo code. You type a code and click Apply. Then the shop's server checks the code.

While the server checks, the page says Checking..., and you cannot click Apply again. If the code is wrong, a red line says the code is not valid. If the code is right, the box goes away, and a line says the discount was applied. So this small box has five looks over time: empty, typed, checking, refused, and accepted.

In plain JavaScript, every change from one look to another needs its own commands: show this line, hide that one, turn the button off, turn it back on. With five looks, there are many changes to cover. If you forget one command, the page ends up in a look that nobody designed.

In this lesson, we build that promo code box twice. First, we build it in plain JavaScript, and we watch one forgotten command break the page. Then we build it in React. There, we describe each look once and let state decide which look is on the screen.

### The promo code box in this lesson

Our page is the Promo code box of an online shop. It has a heading, a text box, and an Apply button. Under them, one of three lines can appear:
- `Checking...` while the server checks the code.
- A red "This code is not valid." when the server says no.
- `Code applied! You get free delivery.` when the server says yes.

We have no real server. Instead, a small function of ours plays the server. It waits 1.5 seconds. Then it says yes to the code `WELCOME` and no to every other code.

Our shopper follows a very normal path. First, the shopper types `WELCOM`, with the last letter missing, and the code is refused. Then the shopper fixes the typo to `WELCOME`, and the code is accepted.

### What this lesson stands on

This lesson uses these facts from earlier lessons:
- **Imperative and declarative**: imperative code commands each element step by step. Declarative code describes the result. From Lesson 1.
- **Fragments**: the empty tags `<>` and `</>` group several elements without adding an extra box to the page. From Lesson 2.
- **Curly braces in an attribute**: they pass a JavaScript value. So `disabled={false}` passes the value `false`, and the button works. From Lesson 3.
- **A default value for a prop**: writing `status = 'empty'` among the props gives the prop the value `'empty'` when the parent passes nothing. From Lesson 9.
- **Choosing what to show**: an `if` with an early `return`, the `? :` ternary, and the double ampersand decide what a component shows. React creates no page element for `null` or `false`. From Lesson 10.
- **Sending a form**: `onSubmit` on a form runs our handler. React passes the handler an event object, `e`. Calling its `preventDefault` method stops the page from reloading. From Lesson 11.
- **State**: `useState` keeps a value between renders. Its setter stores a new value and asks React to draw the component again. From Lesson 12.
- **Render and commit**: after a state change, React draws the component again. Then it changes only the parts of the page that differ from last time. From Lesson 13.
- **Waiting**: `setTimeout` runs a function later, after a wait in milliseconds. From Lesson 15.
- **Batching**: React handles the state changes of a handler after the handler's code has run. From Lesson 16.
- **Lists**: `map` with a `key` draws one element for each item of an array. From Lesson 18.
- **A controlled box**: `value={code}` makes the box show what state holds. An `onChange` handler that calls `setCode` with the new text stores every keystroke in state. From Lesson 20.

### Five Principles of Reacting to Input with State

**PRINCIPLES:** A page that changes in several ways over time is hard to keep right when our code changes each element by hand. React lets us describe every look once and pick the look with state. Five practical rules follow from that:
1. **Principle 1: One Forgotten Command Breaks the Page**: Plain page code needs a command for every change from one look to another. One forgotten command leaves the page in a look nobody designed.
2. **Principle 2: List Every Look First**: Before writing any logic, list every look the user can see. Then draw each look from one value.
3. **Principle 3: Find Every Trigger**: Some changes come from the user. Others come from the computer, such as a server's answer. Both kinds must set state.
4. **Principle 4: One Status Instead of Many Switches**: One value that names the current look cannot be in two looks at once. Several true or false values can.
5. **Principle 5: Handlers Only Set the Next State**: The handler says which look comes next. The JSX already says what each look shows, and React changes the page to match.

Here is the complete map of those five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **One Forgotten Command Breaks the Page** | A refused code and then an accepted code can leave the error line and the success line on screen together, with no message in the Console. | Describe the page for each look once, and let the handler change only state. |
| **Principle 2** | **List Every Look First** | A forgotten waiting look leaves the form working while the server checks, so an impatient shopper sends the code twice. | Write down every look, and draw each one from one value before adding any logic. |
| **Principle 3** | **Find Every Trigger** | A handler that waits for the server but never plans for a no leaves the page stuck on its waiting look. | List what the user does and what the computer does, and make each one set state. |
| **Principle 4** | **One Status Instead of Many Switches** | Two true or false values can both be true, so the page shows an error while the box stays off. | Keep one value that names the look, and compute everything else from it or from other state. |
| **Principle 5** | **Handlers Only Set the Next State** | Changing the page by hand inside a React component can leave a button off forever, because React only changes what differs from its last render. | Let the handler call a setter, and let the JSX decide what is shown, turned off, or styled. |

## 1. Principle 1: One Forgotten Command Breaks the Page

### Every new element means one more command

Let us go back to the Subscribe button for a moment. Suppose the page also has a short note under the button: Get one email a week. The note should go away after the click.

In the plain version, the note gets its own `id` in the HTML. Our script finds it with `document.getElementById` and keeps it in a variable called `note`, the same way it found the button. Then the click handler needs a third command:

```js title="subscribe.js" startLine="5"
button.addEventListener('click', () => {
  button.disabled = true;
  thanks.classList.remove('hidden');
  ~note.classList.add('hidden')~; // New command 3: hide the note
});
```

In the React version, the handler stays exactly as it was. Only the JSX gets one more piece that reads `done`:

```jsx title="Subscribe.jsx" startLine="6"
    <>
      <button disabled={done} onClick={() => ~setDone(true)~}>Subscribe</button> {/* The handler did not change */}
      ~{!done && <p>Get one email a week</p>}~ {/* New: shown only while done is false */}
      {done && <p>Thanks!</p>}
    </>
```

The exclamation mark in `!done` means "not". At the start, `done` is false, so `!done` is true, and the note shows. After the click, `done` becomes true. Then `!done` is `false`, and the note goes away.

So each new element costs the plain handler one more command. It costs the React handler nothing.

With one click and two looks, the plain version is still easy to keep right. Now let us build the promo code box, which has five looks.

### The fake server: a function that answers later

Before we write the plain page, we need our fake server. It lives in its own file:

```js title="src/checkCode.js"
export function checkCode(code) {
  return ~new Promise~((resolve, reject) => { // An answer that is not here yet
    setTimeout(() => {
      if (code === 'WELCOME') {
        ~resolve()~; // The answer is yes
      } else {
        ~reject(new Error('This code is not valid.'))~; // The answer is no
      }
    }, 1500);
  });
}
```

A real server does not answer right away. Its answer comes back a moment later. JavaScript has an object for exactly this case. It is called a **`Promise`**. A promise is a JavaScript object that stands for an answer that is not here yet.

Think of a burger counter that gives you a buzzer when you order. You get the buzzer right away, but the burger comes later. When the buzzer goes off, it tells you one of two things: your order is ready, or sorry, we are sold out. A promise is that buzzer.

When JavaScript creates a new promise, it calls the small function we pass in. It hands that function two other functions, `resolve` and `reject`. Calling `resolve` means the answer is yes. Calling `reject` means the answer is no.

The three equals signs in `code === 'WELCOME'` ask JavaScript whether two values are exactly the same. The answer is `true` or `false`.

Here is what `checkCode` does, step by step:
1. It returns a new promise right away. The answer is not known yet.
2. Inside the promise, `setTimeout` waits 1500 milliseconds, which is 1.5 seconds.
3. If the code is exactly `WELCOME`, it calls `resolve`. The answer is yes.
4. Otherwise, it calls `reject`. The answer is no. We pass `reject` a `new Error`, which is a standard JavaScript error object. Ours carries the message "This code is not valid."

### The plain promo page

Now the plain page. The HTML loads our stylesheet and holds the whole form. Every element has an `id`, so our script can find it:

```html title="plain.html"
<link rel="stylesheet" href="/src/index.css" />
<form id="promo-form">
  <h2>Promo code</h2>
  <input id="code-input" />
  <button id="apply-button" disabled>Apply</button>
  <p id="checking" class="hidden">Checking...</p>
</form>
<p id="error" class="error hidden">This code is not valid.</p>
<p id="success" class="hidden">Code applied! You get free delivery.</p>
<script type="module" src="/src/plain-promo.js"></script>
```

In HTML, writing `disabled` on a tag turns the element off from the start. It is the same switch as the `disabled` property our script can set. So the Apply button starts off, because the box starts empty.

The `Checking...` line, the error line, and the success line all start with the class `hidden`. The error line also has the class `error`, which our stylesheet colors red.

The error line and the success line sit outside the form. There is a reason for that. After a success, we will hide the whole form. If the success line were inside the form, it would hide too.

The script starts by finding every element it will change:

```js title="src/plain-promo.js" startLine="1"
import { checkCode } from './checkCode.js';

const form = document.getElementById('promo-form');
const codeInput = document.getElementById('code-input');
const applyButton = document.getElementById('apply-button');
const checkingText = document.getElementById('checking');
const errorText = document.getElementById('error');
const successText = document.getElementById('success');
```

Each of these six names is our own variable. Each one holds one element of the page, found by the `id` we wrote in the HTML.

While the shopper types, the Apply button should work only when the box has text:

```js title="src/plain-promo.js" startLine="10"
codeInput.addEventListener('input', () => {
  ~applyButton.disabled = codeInput.value.length === 0~; // Off while the box is empty
});
```

The browser fires the `input` event on every keystroke, and it calls our small function each time. Inside it, `codeInput.value` is the text in the box right now. Its `length` is the number of letters in that text.

The highlighted line looks dense, so here it is in order:
1. JavaScript reads the text in the box and counts its letters.
2. It checks whether that count is exactly 0. The answer is `true` or `false`.
3. It stores that answer in `applyButton.disabled`.

So when the box is empty, the answer is `true`, and the button is off. As soon as the box holds one letter, the answer is `false`, and the button works.

### Waiting for the server inside a handler

The last part of the script runs when the shopper clicks Apply. It has to wait for the fake server, so it uses five JavaScript words we have not met yet:

```js title="src/plain-promo.js" startLine="14"
~async~ function handleSubmit(e) { // async: this function may wait
  e.preventDefault();
  codeInput.disabled = true;
  applyButton.disabled = true;
  checkingText.classList.remove('hidden');
  ~try~ { // Run this part; if it fails, jump to catch
    ~await~ checkCode(codeInput.value); // Wait here for the answer
    successText.classList.remove('hidden');
    form.classList.add('hidden');
  } ~catch~ { // The server said no
    errorText.classList.remove('hidden');
  } ~finally~ { // Runs after try or catch, whichever happened
    checkingText.classList.add('hidden');
    codeInput.disabled = false;
    applyButton.disabled = false;
  }
}

form.addEventListener('submit', handleSubmit);
```

All five words come from JavaScript:
- **`async`** in front of a function means the function is allowed to wait. Only an `async` function may use `await`.
- **`await`** pauses the function at that line until the promise has its answer. Here it waits for the promise that `checkCode` returns. While the function waits, the browser keeps the page alive, so the shopper can still scroll. When the answer is yes, the function goes on with the next line.
- **`try`** and **`catch`** work as a pair. JavaScript runs the code inside `try`. If something there fails, JavaScript stops at that point and jumps into `catch`. A promise that says no counts as a failure at its `await`. We write `catch` with no name after it, because this handler does not need the error object.
- **`finally`** runs at the end in both cases: after `try` finished, or after `catch` ran.

On the last line, `addEventListener` hands `handleSubmit` to the browser. The word `'submit'` names the event. The browser fires it when the form is sent, which happens when the shopper clicks Apply. Just like React in Lesson 11, the plain browser passes the handler an event object, `e`. Here too, calling its `preventDefault` method stops the page from reloading.

### The first try: WELCOM is refused

The shopper types `WELCOM` and clicks Apply. For 1.5 seconds, the page looks like this:

```page width=text caption="The plain page while the server checks WELCOM: the box and Apply are disabled, and Checking... is shown."
heading: Promo code
form:
  field:  | WELCOM
  button: Apply
line: Checking...
```

Then the server answers, and the page looks like this:

```page width=text caption="The plain page after the server refuses WELCOM: the box and Apply work again, and the red error line is shown."
heading: Promo code
form:
  field:  | WELCOM
  button: Apply
line: This code is not valid. | bad
```

Here is what happened, in order:
1. The shopper clicked Apply, and the browser called `handleSubmit`.
2. The handler turned off the box and the button. Then it took `hidden` off the `Checking...` line.
3. At `await`, the handler paused for 1.5 seconds. Then the fake server said no.
4. JavaScript jumped into `catch`, which took `hidden` off the error line.
5. `finally` hid the `Checking...` line again. Then it turned the box and the button on again.

So far, everything works. The shopper sees the typo and adds the missing E.

### The second try: WELCOME is accepted, and both lines show

The box now holds `WELCOME`, and the shopper clicks Apply again. During the wait, the old error line is still on the page, under the `Checking...` line:

```page width=text caption="The plain page while the server checks WELCOME on the second try: Checking... and the old error line are on screen together."
heading: Promo code
form:
  field:  | WELCOME
  button: Apply
line: Checking...
line: This code is not valid. | bad
```

After 1.5 seconds, the page looks like this:

```page width=text caption="The plain page after a refused WELCOM and then an accepted WELCOME: the old error line and the success line are both on screen."
line: This code is not valid. | bad
line: Code applied! You get free delivery. | good
```

The shop says the code is not valid, and it also says the code was applied. The Console shows nothing, because no line of code failed. Here is what happened, in order:
1. The shopper clicked Apply, and the browser called `handleSubmit` again.
2. The handler turned off the box and the button, and showed `Checking...`. Nothing in the handler touched the error line, so it was still showing.
3. At `await`, the handler paused. Then the fake server said yes.
4. Inside `try`, the next line took `hidden` off the success line. The line after it put `hidden` on the whole form.
5. `finally` hid `Checking...` and turned the box and the button on. All three are inside the hidden form, so the shopper sees none of them.
6. No line anywhere put `hidden` back on the error line. So the error line stayed.

Look at step 6. The code that runs after a yes never thinks about the error line. The developer tested the yes on a fresh page, where the error line had never been shown.

### Mistake: Forgetting to hide one element

This bug is easy to write and easy to miss. Here is how it usually goes:
1. The developer writes the handler and tests a wrong code. The error line appears. It works.
2. The developer reloads the page and tests a right code. The success line appears. It works.
3. A real shopper tries a wrong code first, then a right code, exactly like ours.
4. Both lines are on screen.

The fix is one more command in the `try` part:

```js title="src/plain-promo.js" startLine="19"
  try {
    await checkCode(codeInput.value);
    ~errorText.classList.add('hidden')~; // New: hide the error line from an earlier try
    successText.classList.remove('hidden');
    form.classList.add('hidden');
  }
```

That fixes today's bug. But the real problem is still there: every handler must remember every element. Say that next month, the shop adds a Remove code button. Now the developer must go through every handler again. For every element, they must ask whether it should be shown or hidden after this change.

The React docs say it plainly. Imperative code for a page "gets exponentially more difficult to manage in more complex systems". Adding a new element or a new interaction "would require carefully checking all existing code to make sure you haven't introduced a bug".

```tree dir=right caption="Why the plain promo page shows two lines at once after a refused code and then an accepted code."
The plain handler after a second, successful try
- +What the developer remembered | Show the success line | Hide the form | Hide `Checking...`
- !What the developer forgot | Hide the error line from the **first try** | No line of code does it | **Both lines** stay on screen
```

In React, we never write commands like these. Instead, we say how the page looks in each case, and React changes the page. The next four principles build the promo code box that way, one step at a time.

> [!PRINCIPLE]
> **Principle 1: Imperative Code: One Forgotten Command Breaks the Page**
>
> *Describe each look of the page once, and let the handler change only state, instead of commanding every element in every handler.*
>
> This one bites every developer who writes forms by hand. Your error line works. Your success line works. Then a real user tries a wrong code and then a right one, and both lines sit on the screen together. You see, each handler only shows or hides what you remembered to write in it, and nothing checks the rest of the page. In React, the handler changes one value. The JSX already says what the page looks like for that value, so a line from an old look cannot stay behind.
>
> **DO THIS:**
> ```jsx
> const [done, setDone] = useState(false);
> <button disabled={done} onClick={() => ~setDone(true)~}>Subscribe</button> {/* The handler changes one value */}
> {done && <p>Thanks!</p>}
> ```
>
> **DO NOT DO THIS:**
> ```js
> button.addEventListener('click', () => {
>   button.disabled = true;
>   ~thanks.classList.remove('hidden')~; // **WRONG:** every element needs its own command, and a forgotten one stays wrong
> });
> ```

## 2. Principle 2: List Every Look First

### One prop that picks the look

Before we write any logic for the promo code box, let us look at a much smaller component. It shows whether a light is on or off:

```jsx title="Light.jsx"
export default function Light({ ~status = 'off'~ }) { // No status from the parent? Use 'off'
  return status === 'on' ? <p>Light is on</p> : <p>Light is off</p>;
}
```

The parent renders `<Light />` and passes nothing. So the default value from Lesson 9 gives `status` the value `'off'`. The ternary from Lesson 10 checks whether `status` is `'on'`. It is not, so the page shows the second paragraph:

```page width=text caption="The Light component when the parent passes no status, so status is off."
line: Light is off
```

Now change one word, the default, from `'off'` to `'on'`, and save the file:

```page width=text caption="The same Light component after the default status is changed to on."
line: Light is on
```

Here is what happened, in order:
1. The parent still passes nothing, so the default gives `status` the value `'on'`.
2. The ternary checks whether `status` is `'on'`. It is, so the function returns the first paragraph.
3. React puts that paragraph on the page.

We changed no logic at all. One value picked the look. The name `status` is our own choice. The React docs say about this prop: "You could call that prop anything you like, the naming is not important."

### Drawing every look before any logic

Designers work this way. Before anyone writes code, a designer draws one picture for every screen the user can see. There is a picture of the empty form, one of the form while it is sending, one of the form with an error, and so on. Such a picture is called a **mock**.

The React docs ask us to do the same in code. In their words: "Just like a designer, you'll want to 'mock up' or create 'mocks' for the different states before you add logic." In code, a mock is a version of the component with no logic. It only draws a look.

Each look has a name in React. One look of the component that the user can see is called a **visual state**. So the light has two visual states, on and off.

Our promo code box has five visual states:
- **empty**: the box is empty, and Apply is off.
- **typing**: the box has text, and Apply works.
- **checking**: the box and Apply are off, and `Checking...` is shown.
- **error**: the same as typing, plus the red line "This code is not valid."
- **success**: the form is gone, and `Code applied! You get free delivery.` is shown instead.

Error and typing show the same form. The only difference is one red line. Still, they are two looks, because the user sees the difference.

```tree caption="The five visual states of the promo code box, listed before writing any logic."
The five looks of the promo code box
- +empty | Box empty | Apply **off**
- +typing | Box has text | Apply **works**
- +checking | Box and Apply **off** | `Checking...` shown
- !error | Like typing | Red line **This code is not valid.**
- +success | Form gone | **Code applied! You get free delivery.**
```

### A mock of the promo code box

Now we write the promo code component as a mock. It has no state and no handler yet. It only draws each look from one prop, `status`, whose default is `'empty'`. The first lines handle the success look:

```jsx title="src/components/PromoCode.jsx" startLine="1"
export default function PromoCode({ ~status = 'empty'~ }) { // The look to draw; empty by default
  if (status === 'success') {
    ~return~ <p>Code applied! You get free delivery.</p>; // Early return: only this line, no form
  }
```

The rest of the function draws the form for the other four looks:

```jsx title="src/components/PromoCode.jsx" startLine="5"
  return (
    <form>
      <h2>Promo code</h2>
      <input ~disabled={status === 'checking'}~ /> {/* Off only while checking */}
      <button ~disabled={status === 'empty' || status === 'checking'}~>Apply</button> {/* Off when empty or checking */}
      {status === 'checking' && <p>Checking...</p>}
      {status === 'error' && <p className="error">This code is not valid.</p>}
    </form>
  );
}
```

The button's condition uses two vertical bars, `||`. In JavaScript, this means "or". The whole condition is true when the left side is true, or the right side is true, or both. So the button is off in the empty look and in the checking look.

The main file renders one promo code box and passes no status:

```jsx title="src/App.jsx"
import PromoCode from './components/PromoCode.jsx';

export default function App() {
  return ~<PromoCode />~; // No status, so the box draws its empty look
}
```

The page shows the empty look:

```page width=text caption="The promo code mock with no status from App, so it draws the empty look with Apply disabled."
heading: Promo code
form:
  field:  |
  button: Apply
```

Here is what happened, in order:
1. `App` renders `<PromoCode />` and passes no status.
2. The default value gives `status` the value `'empty'`.
3. `status === 'success'` is false, so the function skips the early return and goes on to the form.
4. `status === 'checking'` is false, so the box gets `disabled={false}` and works.
5. `status === 'empty'` is true, so the button gets `disabled={true}` and is off.
6. Neither line under the button matches, so React draws neither of them.

Now change the default from `'empty'` to `'success'` and save. The page shows only the success line:

```page width=text caption="The same mock after the default status is changed to success: only the success line is drawn."
line: Code applied! You get free delivery. | good
```

This time `status === 'success'` is true. So the early return gives only the paragraph, and the function never reaches the form. There is no form on the page at all, not even a hidden one.

### Every look on one page

Changing the default by hand shows one look at a time. We can do better and show all five looks at once. `App` keeps a list of every status and draws one promo code box for each:

```jsx title="src/App.jsx"
import PromoCode from './components/PromoCode.jsx';

const statuses = ['empty', 'typing', 'checking', 'error', 'success'];

export default function App() {
  return (
    <>
      {~statuses.map~(status => ( // One section for each look
        <section key={status}>
          <h4>{status}</h4>
          <PromoCode ~status={status}~ /> {/* This box draws this look */}
        </section>
      ))}
    </>
  );
}
```

`statuses` is our own array of the five names. The `map` from Lesson 18 walks it one item at a time. For each name, it draws a section. The section has the name as a small title, and a promo code box that receives that name as its `status`. Each name is different, so it also works as the `key`.

The page shows all five looks, one under the other:

```page width=text caption="Every look of the promo code mock on one page. The box is empty in every section, because the mock gives it no text yet. Apply is disabled under empty and checking, and the box is disabled under checking."
section: empty
heading: Promo code
form:
  field:  |
  button: Apply
section: typing
heading: Promo code
form:
  field:  |
  button: Apply
section: checking
heading: Promo code
form:
  field:  |
  button: Apply

heading: Promo code
form:
  field:  |
  button: Apply

section: success
line: Code applied! You get free delivery. | good
```

The box is empty in every section, even under typing. That is fine. The mock gives the box no text, because text comes from the user, and there is no user yet. What we check here is the rest of each look: which control is off, and which line is shown.

A page like this has a name. The React docs say it is often called a **living styleguide** or a **storybook**. You can see every look at a glance. You can also change the design of one look without clicking through the whole form. As the docs put it, mocking lets you "quickly iterate on the UI before you wire up any logic".

### Mistake: Leaving out the checking look

Listing the looks on paper sounds slow. Many developers skip it and start with the looks they can think of: an empty box, a typed box, and a done message. Here is the mock they write:

```jsx title="src/components/PromoCode.jsx" startLine="5"
  return (
    <form>
      <h2>Promo code</h2>
      <input />
      <button ~disabled={status === 'empty'}~>Apply</button> {/* **WRONG:** no checking look, so Apply stays on while the server checks */}
    </form>
  );
```

Later, when the handler is connected, this page works for a calm shopper. Here is what happens to an impatient one:
1. The shopper types `WELCOME` and clicks Apply.
2. There is no checking look, so nothing turns the box or Apply off.
3. The server needs 1.5 seconds. The shopper sees no change and clicks Apply again.
4. The form is sent a second time, and the code goes to the server twice.

Writing the list of looks first shows the gap. Between typing and success, the shopper waits. The React docs list this waiting look on its own: "Submitting: Form is completely disabled. Spinner is shown." Their page on batching also notes that "if the first button click disables a form, the second click would not submit it again". Once the checking look is on the list, the mock has to say what it looks like. That is why our mock turns off the box and Apply when `status` is `'checking'`.

```tree caption="A list of three looks vs. a list of five looks for the promo code box."
Which looks did the developer list?
- !Three looks [empty, typing, success] | No look for the wait | Apply stays **on** while the server checks | A second click sends the code **twice**
- +Five looks [empty, typing, checking, error, success] | The wait is its **own look** | The box and Apply are **off** while checking | A second click **does nothing**
```

Computer science has a name for something that is always in exactly one of a few states, like our box with its five looks. It is called a **state machine**. You will hear the name in interviews. The React docs say React "stands at the intersection of design and computer science". This method takes one idea from each side: the designer's list of looks, and the state machine.

> [!PRINCIPLE]
> **Principle 2: Visual States: List Every Look Before Any Logic**
>
> *Write down every look the user can see, then draw each one from a single `status` prop, before adding state or handlers.*
>
> It is so tempting to jump straight into handlers. But the look you forget to list is exactly the look you forget to build, and the waiting look is the one everybody forgets. Then the button stays on while the server thinks, and the impatient user clicks twice. With a `status` prop and a default value, you can switch the whole component between its looks by changing one word. With `map`, you can see every look on one page.
>
> **DO THIS:**
> ```jsx
> export default function PromoCode({ ~status = 'empty'~ }) { // One prop picks the look
>   if (status === 'success') {
>     return <p>Code applied! You get free delivery.</p>;
>   }
>   return <button disabled={status === 'empty' || status === 'checking'}>Apply</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function PromoCode({ status = 'empty' }) {
>   return <button ~disabled={status === 'empty'}~>Apply</button>; // **WRONG:** no checking look, so Apply stays on while the server checks
> }
> ```

## 3. Principle 3: Find Every Trigger

### A button that changes back on its own

So far, our looks change only when we edit the code. On a real page, something has to move the component from one look to the next. Here is a small example with two kinds of movement.

A Copy link button shows Copied! for a moment after a click. Then it goes back to Copy link. We leave out the copying itself here, because only the label matters:

```jsx title="CopyButton.jsx"
import { useState } from 'react';

export default function CopyButton() {
  const [status, setStatus] = useState('ready');

  function handleClick() {
    ~setStatus('copied')~; // Moved by the user's click
    ~setTimeout(() => setStatus('ready'), 1500)~; // Moved by a timer, 1.5 seconds later
  }

  return <button onClick={handleClick}>{status === 'copied' ? 'Copied!' : 'Copy link'}</button>;
}
```

When the page opens, `status` is `'ready'`, so the button says Copy link:

```page width=text caption="The Copy link button when the page opens."
line: [Copy link]
```

The user clicks it once:

```page width=text caption="The same button right after the click."
line: [Copied!]
```

Then the user does nothing at all. 1.5 seconds later, the button changes back:

```page width=text caption="The same button 1.5 seconds after the click, with no second click."
line: [Copy link]
```

Here is what happened, in order:
1. The user clicked, and React called `handleClick`.
2. Calling `setStatus` with `'copied'` asked for the copied look.
3. `setTimeout`, from Lesson 15, asked the browser to run a small function after 1500 milliseconds.
4. The handler finished, and React drew the button with the label Copied!
5. 1.5 seconds later, the timer ended, and the browser ran the small function. It called `setStatus` with `'ready'`.
6. React drew the button again, with the label Copy link.

Two different things moved this button. The first was the user's click. The second was a timer, and nobody touched anything for it. The React docs give these two kinds of trigger names:
- A **human input** is something the user does: clicking a button, typing in a box, following a link. The docs note that "human inputs often require event handlers".
- A **computer input** is something that happens without the user: a network answer arriving, a timer ending, an image finishing loading.

The docs draw a finger for human inputs, and a row of ones and zeroes for computer inputs. Then they add the rule that matters most: "In both cases, you must set state variables to update the UI."

### The triggers of the promo code box

Now we list what moves our promo code box. Each row names the look before, the trigger, who causes it, and the look after:

| From | Trigger | Kind | To |
| :--- | :--- | :--- | :--- |
| **empty** | The shopper types a letter | Human | **typing** |
| **typing** | The shopper clears the box | Human | **empty** |
| **typing** | The shopper clicks Apply | Human | **checking** |
| **checking** | The server accepts the code | Computer | **success** |
| **checking** | The server refuses the code | Computer | **error** |
| **error** | The shopper fixes the code and clicks Apply | Human | **checking** |

The React docs suggest drawing this table as a picture. Each look is a circle with a label. Each change is an arrow with its trigger written on it. A drawing like that lets you "sort out bugs long before implementation". Here are the arrows of our box, from left to right:

```tree dir=right caption="The looks of the promo code box and the trigger written on each arrow between them."
How the promo code box moves between its looks
- +empty | **start typing**, human | Goes to **typing**
- +typing | **press Apply**, human | Goes to **checking**
- +checking | **server accepts**, computer | Goes to **success**
- !checking | **server refuses**, computer | Goes to **error**
- +error | **press Apply**, human | Goes to **checking** again
```

Look at the checking look. It has two arrows out, one for yes and one for no. Every look needs at least one way out, except the last one. A look with no way out is a dead end, and the user is stuck there.

### How the server's answer sets state

Our mock still gets `status` from a prop. In Principle 4, we will move `status` into state, with the setter `setStatus`. We will also keep the text of the box in state, as `code`. For now, picture that both are already there.

Here is a first look at the handler that Apply will run. It uses the same four JavaScript words as the plain handler of Principle 1, from `async` to `catch`. But it only calls setters:

```jsx title="src/components/PromoCode.jsx"
async function handleSubmit(e) {
  e.preventDefault();
  ~setStatus('checking')~; // Human input: the click
  try {
    await checkCode(code);
    ~setStatus('success')~; // Computer input: the server said yes
  } catch {
    ~setStatus('error')~; // Computer input: the server said no
  }
}
```

The click and the server's answer are very different events. For React, they end the same way. Each one calls a setter, and each setter call asks React to draw the component again.

There is one surprise here. The last two setter calls sit inside the click handler, but they do not run during the click. They run 1.5 seconds later. To see why, we need one more fact about `async` functions. When an `async` function reaches `await`, it steps aside, and the browser goes on with other work. The rest of the function waits for the answer.

Here is what happens, in order:
1. The shopper clicks Apply, and React calls `handleSubmit`.
2. Calling `setStatus` with `'checking'` asks for the checking look.
3. The handler reaches `await` and steps aside. The part of the handler that runs on the click is now over.
4. As we saw with batching in Lesson 16, React handles state changes after the handler's code has run. So React now draws the checking look, while the rest of the handler is still waiting.
5. 1.5 seconds later, the server answers. Nobody clicked anything.
6. On a yes, the handler goes on after `await` and asks for the success look. On a no, it jumps into `catch` and asks for the error look.
7. React draws the new look.

So the code after `await` belongs to a computer input, not to the click. It runs when the answer arrives.

One small trap follows from this. After `await`, the variable `status` inside the handler still holds the value from the render that created the handler. We saw this with state snapshots in Lesson 15. So `status` does not say `'checking'` there, even though the page does. After waiting, never read `status` to decide what to do next. Call the setter for the next look directly, as the handler above does.

### Mistake: Planning only for the server's yes

A developer who thinks only of the happy path writes the handler without `try` and `catch`:

```jsx title="src/components/PromoCode.jsx"
async function handleSubmit(e) {
  e.preventDefault();
  setStatus('checking');
  ~await checkCode(code)~; // **WRONG:** a no from the server stops the handler here, and nothing sets the next look
  setStatus('success');
}
```

The shopper types `WELCOM` and clicks Apply. 1.5 seconds later, the page is still waiting, and it waits forever:

```page width=text caption="The promo code box after the server refuses WELCOM, when the handler has no catch: stuck on Checking..., with the box and Apply disabled."
heading: Promo code
form:
  field:  | WELCOM | bad
  button: Apply
line: Checking...
console: Uncaught (in promise) Error: This code is not valid.
```

Here is what happened, in order:
1. The click asked for the checking look, and React drew it. The box and Apply turned off.
2. The server said no, so the promise failed at `await`.
3. There was no `catch` to jump to. So the handler stopped at that line, and the line that asks for the success look never ran.
4. Nothing called a setter, so React never drew another look. The page stays on checking, with the box and Apply off.
5. Nothing caught the failed promise, so the browser reports it in the Console as an error.

The shopper cannot even fix the typo, because the box is off. The arrow drawing shows the gap at once. The checking look has two arrows out, but this handler builds only one of them. Adding `try` and `catch` builds the second arrow, as in the handler of the previous section.

> [!PRINCIPLE]
> **Principle 3: Triggers: Human Inputs and Computer Inputs Both Set State**
>
> *List every trigger that moves the component, both what the user does and what the computer does, and make each one call a setter.*
>
> We think of clicks and typing first, because we do them ourselves. But the server's answer moves the page too, and a server can say no. If your handler only plans for yes, the first wrong code leaves the page stuck on Checking... The box stays off, so the user cannot even fix the typo. Draw each look as a circle and each trigger as an arrow, and make sure every look except the last has a way out.
>
> **DO THIS:**
> ```jsx
> try {
>   await checkCode(code);
>   setStatus('success');
> } ~catch~ { // The second way out of checking
>   setStatus('error');
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> setStatus('checking');
> ~await checkCode(code)~; // **WRONG:** a refused code stops here, and the page stays on checking forever
> setStatus('success');
> ```

## 4. Principle 4: One Status Instead of Many Switches

### Two switches, four combinations

Our mock picks its look with one prop, `status`. Now the looks must change while the page runs, so the look must move into state. Many developers first reach for true or false values, one for each look. A true or false value is also called a **boolean**. Here is the smallest case, with two of them:

```jsx title="Two true or false values for two looks"
const [isChecking, setIsChecking] = useState(false);
const [isSuccess, setIsSuccess] = useState(false);
```

Each value can be `true` or `false`. So together, they can be in four combinations:

| `isChecking` | `isSuccess` | What the page shows |
| :--- | :--- | :--- |
| `false` | `false` | The typing look |
| `true` | `false` | The checking look |
| `false` | `true` | The success look |
| `true` | `true` | Still checking, and already accepted. Nobody designed this look |

Only three of the four combinations are real looks. The last one matches no look that anyone designed. Such a combination is called an **impossible state**. The React docs call it "a paradox". Nothing in JavaScript or in React stops our code from reaching it. React accepts any values in state, and it prints no warning.

Now compare that with one value that can hold one of three strings:

```jsx title="One status value for three looks"
const [status, setStatus] = useState('typing'); // 'typing', 'checking', or 'success'
```

`status` holds exactly one string at a time. So it can be in exactly three looks, one for each string. The fourth combination cannot even be written down.

Think of a traffic light. It has three lamps, but only one of them is lit at a time. Now picture a light with three separate switches, one for each lamp. Someone could turn on red and green together, and the drivers would not know what to do. One `status` is the traffic light. Many true or false values are the three separate switches.

### Four switches give sixteen combinations

The problem grows fast. Here is the count for our promo code box, step by step:
1. One true or false value has 2 possible values.
2. Each extra true or false value doubles the number of combinations.
3. Our box would need four of them, one each for typing, checking, success, and error. That gives 2 times 2 times 2 times 2, which is 16 combinations.
4. Only four of them are real looks. The other 12 are impossible states.
5. One `status` string with four allowed values gives exactly four combinations, one for each look.

The React docs put the goal like this: "each piece of state is a 'moving piece', and you want as few 'moving pieces' as possible. More complexity leads to more bugs!"

### Mistake: An error line on a box that is still off

Here is how an impossible state reaches a real page. The developer keeps a separate true or false value for checking, for the error, and for success:

```jsx title="src/components/PromoCode.jsx" startLine="5"
  const [code, setCode] = useState('');
  const [isChecking, setIsChecking] = useState(false);
  const [isError, setIsError] = useState(false);
  const [isSuccess, setIsSuccess] = useState(false);
```

The handler turns checking on at the click. It turns the error on when the server says no:

```jsx title="src/components/PromoCode.jsx" startLine="10"
  async function handleSubmit(e) {
    e.preventDefault();
    setIsChecking(true);
    try {
      await checkCode(code);
      setIsSuccess(true);
    } catch {
      ~setIsError(true)~; // **WRONG:** isChecking stays true, so the box stays off
    }
  }
```

The form reads each value on its own:

```jsx title="src/components/PromoCode.jsx" startLine="28"
      <input value={code} onChange={e => setCode(e.target.value)} ~disabled={isChecking}~ /> {/* Off while isChecking is true */}
      <button disabled={code.length === 0 || isChecking}>Apply</button>
      {isChecking && <p>Checking...</p>}
      {isError && <p className="error">This code is not valid.</p>}
```

The shopper types `WELCOM` and clicks Apply. After the server's answer, the page looks like this:

```page width=text caption="The promo code box after the server refuses WELCOM, when checking and error are two separate true or false values: Checking... and the error line show together, and the box and Apply stay disabled."
heading: Promo code
form:
  field:  | WELCOM | bad
  button: Apply
line: Checking...
line: This code is not valid. | bad
```

Here is what happened, in order:
1. The click set `isChecking` to `true`, and React drew the checking look. The box and Apply turned off, and `Checking...` appeared under them.
2. The server said no, and JavaScript jumped into `catch`.
3. `catch` set `isError` to true. Nothing set `isChecking` back to false.
4. Now both values are `true`. React draws exactly what the JSX says for that pair: the box off, Apply off, `Checking...`, and the error line.

The page tells the shopper to fix the code. At the same time, it does not let the shopper type. The React docs warn about exactly this case. They say: "you never want to show an error message and disable the input at the same time, or the user won't be able to correct the error!"

With one `status`, this combination cannot happen. Here is the same moment with `status`:
1. The click sets `status` to `'checking'`.
2. The server says no, and the catch part sets `status` to `'error'`.
3. The new string replaces the old one. `status` now holds `'error'` and nothing else.
4. React draws the error look, and the box works again.

We never have to remember to turn checking off. Setting the next look turns the old one off by itself.

### Three questions that remove extra state

The React docs ask three questions about every piece of state. Each "yes" means that piece of state can go. Here they are, asked about our promo code box:
1. **Does this state cause a paradox?** `isChecking` and `isError` can both be true, as we just saw. So we merge all the looks into one `status`.
2. **Is the same information already in another state variable?** An `isEmpty` value would repeat what the text of the box already says. So we do not store it. We compute it instead: `code.length === 0` is true exactly when the box is empty.
3. **Can it come from the opposite of another state variable?** The React docs show this on their own quiz form. That form keeps the error message in a state variable called `error`. An `isError` value would only say whether that message is there. So the docs drop `isError` and write `error !== null`. As we saw in Lesson 1, `!==` means "is not equal to". So `error !== null` is true when there is an error message. In our box, `status === 'error'` already says it.

After the three questions, our box needs only two pieces of state:
- **`code`**: the text in the box.
- **`status`**: the current look. It holds one of four strings: typing, checking, error, or success.

The empty look has no string of its own anymore. It is simply a typing look where `code` is empty. A piece of state that you cannot remove without breaking the component is called **essential state**. `code` and `status` are both essential.

You can still use true or false names in your code when they help. Compute them from `status` instead of storing them. The React docs show this in a hotel feedback form:

```js title="A true or false name computed from status"
const ~isSending~ = status === 'sending'; // True only while status is 'sending'
```

The React docs build their own version of a form like ours a little differently. They keep the error message in a separate piece of state. Their `status` has three values: typing, submitting, and success. The docs note that this version can still hold an error message while `status` is `'success'`. Our box puts `'error'` inside `status` instead, so that pair cannot exist at all. Both designs are valid, and this lesson keeps `'error'` inside `status`.

The React docs also say that "your first idea likely won't be the best, but that's ok". Starting with many true or false values and then merging them is a normal part of the work.

### The promo code box with real state

Now the mock prop becomes state. The component no longer receives `status` from its parent. It keeps `code` and `status` itself:

```jsx title="src/components/PromoCode.jsx" startLine="1"
import { useState } from 'react';

export default function PromoCode() {
  const [code, setCode] = ~useState('')~; // The text in the box, empty at the start
  const [status, setStatus] = ~useState('typing')~; // The current look: typing, checking, error, or success

  if (status === 'success') {
    return <p>Code applied! You get free delivery.</p>;
  }
```

The form now reads both pieces of state:

```jsx title="src/components/PromoCode.jsx" startLine="11"
  return (
    <form>
      <h2>Promo code</h2>
      <input ~value={code}~ onChange={e => setCode(e.target.value)} disabled={status === 'checking'} /> {/* A controlled box */}
      <button ~disabled={code.length === 0 || status === 'checking'}~>Apply</button> {/* Off when empty or checking */}
      {status === 'checking' && <p>Checking...</p>}
      {status === 'error' && <p className="error">This code is not valid.</p>}
    </form>
  );
}
```

The box is now a controlled box, as in Lesson 20. `value={code}` makes it show what `code` holds. `onChange` stores every keystroke in `code`. The button's condition no longer asks whether `status` is `'empty'`. It asks whether `code` is empty.

`App` goes back to rendering one promo code box:

```jsx title="src/App.jsx"
import PromoCode from './components/PromoCode.jsx';

export default function App() {
  return ~<PromoCode />~; // One box, which now picks its own look from state
}
```

When the page opens, it shows the empty look:

```page width=text caption="The promo code box with state when the page opens: the box is empty and Apply is disabled."
heading: Promo code
form:
  field:  |
  button: Apply
```

The shopper types `WELCOM`:

```page width=text caption="The same box after the shopper types WELCOM: Apply is now enabled."
heading: Promo code
form:
  field:  | WELCOM | good
  button: Apply
```

Here is what happened, in order:
1. When the page opened, `code` was an empty string. `status` was `'typing'`.
2. `code.length === 0` was true, so React drew Apply turned off.
3. The shopper typed W. React called `onChange`, and `setCode` stored the letter. React drew the component again.
4. Now `code.length === 0` was false, and `status === 'checking'` was false too. So React turned Apply on.
5. The same thing happened for each of the next five letters, until `code` held `WELCOM`.

The empty look and the typing look both come from the same `status`, `'typing'`. The only difference is `code`.

The form has no submit handler yet. So a click on Apply now would only make the browser reload the page, because nothing calls `preventDefault` on the event. Principle 5 connects the handler.

> [!PRINCIPLE]
> **Principle 4: One Status: A Single String Cannot Be in Two Looks at Once**
>
> *Keep the current look in one `status` string, and compute everything else from it or from other state, instead of keeping several true or false values.*
>
> Every true or false value doubles the number of combinations, and most of them are looks nobody designed. With two switches for checking and error, forget to set `isChecking` back to false, and the error shows while the box stays off. The user cannot even fix the typo. One `status` holds exactly one string, so setting the next look turns the old one off by itself. If you want a true or false name, compute it: `status === 'checking'`.
>
> **DO THIS:**
> ```jsx
> const [status, setStatus] = useState('typing');
> ~setStatus('error')~; // Replaces 'checking', so the box works again
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [isChecking, setIsChecking] = useState(false);
> const [isError, setIsError] = useState(false);
> ~setIsError(true)~; // **WRONG:** isChecking is still true, so the error shows on a box that is still off
> ```

## 5. Principle 5: Handlers Only Set the Next State

### Computing a class instead of adding one

In plain JavaScript, we changed the look of an element by adding or removing a CSS class. Here is a small example. A picture should get a blue frame when the user clicks it. Our stylesheet has a class for that, `picture--active`.

The plain way finds the picture element by its `id` and keeps it in a variable called `image`. Then it adds the class on the click:

```js title="picture.js"
image.addEventListener('click', () => {
  ~image.classList.add('picture--active')~; // A command: put the blue frame on this element
});
```

React does not ask us to command the element. Instead, we compute the class name from state on every render:

```jsx title="Picture.jsx"
import { useState } from 'react';

export default function Picture() {
  const [isActive, setIsActive] = useState(false);

  let className = 'picture';
  if (isActive) {
    ~className += ' picture--active'~; // Add the second class to the text when isActive is true
  }

  return <img ~className={className}~ onClick={() => setIsActive(true)} src="/park.jpg" alt="The new park" />; // The class text computed above
}
```

The sign `+=` comes from JavaScript. Used on a string, it adds text to the end of it. So when `isActive` is true, the text grows to `'picture picture--active'`. The space at the start of `' picture--active'` keeps the two class names apart.

The user clicks the picture once. The Elements panel then shows both classes on the image:

```dom caption="The Elements panel after one click on the picture: React wrote both classes into the class attribute."
+ <img class="picture picture--active" alt="The new park" src="/park.jpg"> | note: Both classes, computed from isActive
```

Here is what happened, in order:
1. The user clicked, and the handler set `isActive` to `true`.
2. React drew `Picture` again. This time `isActive` was true, so the class name became `'picture picture--active'`.
3. React compared the new class name with the old one, `'picture'`. They differ, so React wrote the new class name into the image's `class` attribute.

The handler never talks about classes. It only says that the picture is now active. The React docs describe the rule like this: "in React you need to describe what you want to see rather than manipulate the UI elements". This is the taxi again. The handler names the address, and React drives.

### Connecting the handler to the form

Now we finish the promo code box. The handler from Principle 3 goes inside the component, below the success check. It also needs `checkCode`, so the file imports it from our fake server:

```jsx title="src/components/PromoCode.jsx" startLine="1"
import { useState } from 'react';
import { checkCode } from '../checkCode.js';

export default function PromoCode() {
  const [code, setCode] = useState('');
  const [status, setStatus] = useState('typing');

  if (status === 'success') {
    return <p>Code applied! You get free delivery.</p>;
  }

  async function handleSubmit(e) {
    e.preventDefault();
    ~setStatus('checking')~; // Next look: checking
    try {
      await checkCode(code);
      ~setStatus('success')~; // Next look: success
    } catch {
      ~setStatus('error')~; // Next look: error
    }
  }
```

The handler does nothing else to the page. It does not turn the box off. It does not show `Checking...`. It does not hide the error line. It only names the next look.

The form gets the handler through `onSubmit`. The box also gets a class that is computed from `status`, so it has a red border in the error look:

```jsx title="src/components/PromoCode.jsx" startLine="23"
  return (
    <form ~onSubmit={handleSubmit}~> {/* Apply sends the form, and React calls handleSubmit */}
      <h2>Promo code</h2>
      <input
        ~className={status === 'error' ? 'code-box code-box--error' : 'code-box'}~ // Red border only in the error look
        value={code}
        onChange={e => setCode(e.target.value)}
        disabled={status === 'checking'}
      />
      <button disabled={code.length === 0 || status === 'checking'}>
        Apply
      </button>
      {status === 'checking' && <p>Checking...</p>}
      {status === 'error' && <p className="error">This code is not valid.</p>}
    </form>
  );
}
```

The ternary on the box works like the one in `Light`. In the error look, the box gets two classes, `code-box` and `code-box--error`. In every other look, it gets only `code-box`.

The stylesheet holds the classes that both versions of the page use:

```css title="src/index.css"

.error { color: red; }
.code-box--error { border: 2px solid red; }

Now we follow our shopper through the whole story. The shopper has typed `WELCOM` and clicks Apply. For 1.5 seconds, the page shows the checking look:

Then the server says no:

Here is what happened, in order:
1. The shopper clicked Apply. That sent the form, so React called `handleSubmit`.
2. The call to `preventDefault` stopped the page from reloading. Then the handler asked for the checking look.
3. The handler stepped aside at `await`. React drew the checking look. `disabled` became true on the box and on Apply, and the `Checking...` paragraph appeared.
4. 1.5 seconds later, the server said no. JavaScript jumped into `catch`, which asked for the error look.
5. React drew the error look and compared it with the checking look. Four things differ. `disabled` is now false on both controls. The `Checking...` paragraph is gone. The error paragraph is new. And the box has the class `code-box--error`. So React changed exactly those four things.

The shopper adds the missing E and clicks Apply again. For 1.5 seconds, the page shows the checking look once more:

```page width=text caption="The React promo code box while the server checks WELCOME: the error line from the first try is gone."
heading: Promo code
form:
  field:  | WELCOME
  button: Apply
line: Checking...
```

Look at what is missing. The error line from the first try is gone, and no line of our code removed it. Here is why, in order:
1. The handler asked for the checking look. So `'checking'` replaced `'error'` in state.
2. React drew the component again. This time `status === 'error'` was false. So the double ampersand gave `false`, and the JSX had no error paragraph.
3. React compared the new JSX with the last one. The last one had an error paragraph, and the new one does not. So React removed that paragraph from the page.

Then the server says yes:

```page width=text caption="The React promo code box after the server accepts WELCOME: only the success line is on the page."

```

`catch` did not run this time. The line after `await` asked for the success look, and React drew the component again. This time the early return gave only the success paragraph. So React removed the whole form and put the paragraph in its place.

Remember the plain page of Principle 1, which showed the error line and the success line together. That cannot happen here. The error line appears only when `status` is `'error'`. The success line appears only when `status` is `'success'`. One string cannot hold both values at once.

```tree dir=right caption="The plain handler vs. the React handler on the second try, when the error line from the first try is still on screen."
The second try, after a refused code
- !Plain handler | Must **remember** to hide the error line | Forgot it, so **both lines** show
- +React handler | Only calls `setStatus` | The JSX for checking and success has **no error line**, so React **removes it**
```

### What React does under the hood

The React docs have a challenge that writes this kind of page in plain JavaScript, in a better way. It does not give a command for each change. Instead, it keeps the look in variables, and it has one function, `updateDOM`. That function sets every element from those variables, every time anything changes. The docs say this function "shows what React does under the hood when you set the state".

There is one difference, and it matters for the next mistake. `updateDOM` writes every property of every element on every change. React does not. In the words of the docs, React "also avoids touching the DOM for properties that have not changed since the last time they were set." So React compares the new render with the last render. Then it changes only what differs between the two.

### Mistake: Changing the page by hand inside a React component

A developer who is used to plain JavaScript might turn Apply off the old way, inside the React handler. The button gets an `id`, and the handler finds it:

```jsx title="src/components/PromoCode.jsx" startLine="12"
  async function handleSubmit(e) {
    e.preventDefault();
    ~document.getElementById('apply-button').disabled = true~; // **WRONG:** our code changes the button behind React's back
    try {
      await checkCode(code);
      setStatus('success');
    } catch {
      setStatus('error');
    }
  }
```

The button still has its condition from state:

```jsx title="src/components/PromoCode.jsx" startLine="32"
      <button id="apply-button" disabled={code.length === 0 || status === 'checking'}>
        Apply
      </button>
```

The shopper types `WELCOM` and clicks Apply. This handler never asks for the checking look. So during the wait, the page shows no `Checking...` line, and the box keeps working. Only Apply is off. Then the server says no, and the page looks like this:

```page width=text caption="The promo code box after a refused WELCOM, when the handler turned Apply off by hand: the error line shows, but Apply stays disabled."
heading: Promo code
form:
  field:  | WELCOM | bad
  button: Apply
line: This code is not valid. | bad
```

Now the shopper fixes the code to `WELCOME`, but Apply stays off. The shopper cannot try again. Here is what happened, in order:
1. On the last render before the click, `status` was `'typing'`. The box was not empty. So the JSX said `disabled={false}` for Apply.
2. The click ran our line, which set `disabled` to true directly on the button. React knows nothing about this.
3. The server said no, and `catch` asked for the error look. React drew the component again.
4. In the new render, the JSX again says `disabled={false}` for Apply. The look is now error, and the box is still not empty.
5. React compares the two renders. Apply's `disabled` was false last time, and it is false again. Nothing changed, so React does not touch the button.
6. The button keeps the `true` that our code wrote. Apply stays off.
7. The shopper types the E. React draws again, and `disabled` is still `false` in both renders. So React still does not touch the button.

The fix is to name the next look and nothing else. Replace our line with the setter call for the checking look, as in the handler of the previous section. Then the checking render says `disabled={true}`, and the error render says `disabled={false}`. The two renders differ, so React turns the button back on.

```tree dir=right caption="Turning Apply off by hand vs. letting the next look turn it off."
Two ways to turn Apply off during the check
- !By hand [`getElementById` `disabled = true`] | React's last render said **false** | The error render also says **false** | React sees no change, so Apply **stays off**
- +With state [`setStatus` `'checking'`] | The checking render says **true** | The error render says **false** | React sees a change and turns Apply **on again**
```

### Adding a new look later

The React version is longer than the plain one. The React docs admit it: the React code "is longer than the original imperative example", but it is "much less fragile".

Here is what "less fragile" means in practice. Suppose the shop's server could later answer that a code has expired. In React, we add one more value to the list, `'expired'`. We add one more line of JSX. It shows "This code has expired." when `status` is `'expired'`. The other looks do not change at all. The docs say this way of working "lets you later introduce new visual states without breaking existing ones". In the plain version, every handler would need one more hide command for the new line.

Three later lessons go further. Lesson 22 covers in full which values should not be state at all. Lesson 27 moves the logic of many looks into a reducer. And Lessons 41 to 44 show React 19 form actions, which give you a waiting flag without a hand-made `status`.

> [!PRINCIPLE]
> **Principle 5: Handlers Set State: The Handler Names the Next Look, and React Changes the Page**
>
> *Make each handler call a setter and nothing else on the page, and let the JSX decide what is turned off, shown, hidden, or styled for each look.*
>
> Old habits die hard. You reach for `getElementById` inside a React handler, because it is quicker, and it seems to work. Then the server says no, and the button stays off forever. You see, React only changes what is different between its last render and its new one, and your hand-made change is not in either of them. So never edit the page behind React's back. Call the setter for the next look, and React will turn things on and off for you.
>
> **DO THIS:**
> ```jsx
> async function handleSubmit(e) {
>   e.preventDefault();
>   ~setStatus('checking')~; // The JSX for checking turns the box and Apply off
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> async function handleSubmit(e) {
>   e.preventDefault();
>   ~document.getElementById('apply-button').disabled = true~; // **WRONG:** React never turns this button back on
> }
> ```

## For the Interview

> **The Interview Question:** How do you design a component that reacts to input with state instead of touching the DOM?

### How to Answer Clearly in 30 Seconds

"In plain JavaScript, the code is imperative. Every handler commands each element: disable this button, show that message. With many looks, one forgotten command leaves the page in a look nobody designed, like an error message and a success message on screen together. In React, I write declarative code instead, in five steps. First, I list every visual state the user can see, and I mock each one with a `status` prop, often all on one page, like a living styleguide. Second, I find what triggers each change. There are human inputs, like clicks and typing, and computer inputs, like a server's answer. Both must set state, and every look needs a way out, including the error path. Third, I represent the look with as little state as possible, usually one `status` string instead of several booleans. Four booleans allow 16 combinations, while a string with four allowed values allows exactly four. Fourth, I remove any state that causes a paradox, repeats other state, or can be computed, such as whether the text is empty. Fifth, I connect the event handlers so they only call setters. The JSX decides what is disabled, shown, or styled, and React changes only the parts of the page that differ from the last render. That is also why I never edit the DOM by hand inside a component: React will not undo a change it did not make."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why use one `status` string instead of several booleans like `isLoading` and `isError`?"**
   Every boolean doubles the number of possible combinations. Four booleans give 16, but a form like a promo code box has only four or five real looks. So most combinations are impossible states, and they do happen in practice. Say the error branch sets `isError` to true and forgets to set `isLoading` to false. Then the page shows an error while the input is still disabled, and the user cannot fix it. One `status` holds exactly one value, so setting `'error'` replaces `'checking'` by itself. When you need a boolean in the JSX, compute it, for example `const isChecking = status === 'checking';`.
2. **"What goes wrong if you change the DOM directly inside a React component?"**
   React does not read the page to decide what to change. It compares its new render with its last render, and it only touches properties that differ. Say a handler sets `disabled` on a button with `getElementById`. The JSX may say `disabled={false}` both before and after, so React sees no change and never turns the button back on. The page and React's picture of it no longer match. The fix is to call a setter for the next look, and let the JSX compute `disabled`, `className`, and which elements appear.
3. **"How does a network response change the page if no one clicks anything?"**
   A network response is a computer input. In an `async` handler, the code before `await` runs on the click. React draws that state, such as `'checking'`, while the handler waits. When the promise has its answer, the handler goes on and calls the setter for the next look: `'success'` after `await`, or `'error'` inside `catch`. Then React draws again. There are two traps. Without `catch`, a refused request leaves the page stuck on its waiting look. And after `await`, the `status` variable still holds the value from the render that created the handler. So the handler should set the next look directly instead of reading `status`.

```tree dir=right caption="Interview comparison: commanding the page by hand vs. describing each look and setting state."
Two ways to make a form react to input
- !Imperative [`classList` `disabled = true`] | Each handler **commands every element** | One forgotten command leaves an **old line on screen**
- !Many booleans [`isChecking` `isError`] | Looks are described, but **16 combinations** are possible | A forgotten reset shows an error on a box that is **still off**
- +One status and declarative JSX [`status` `setStatus`] | Each handler **only names the next look** | React changes **only what differs**, and old lines **cannot stay behind**
```
