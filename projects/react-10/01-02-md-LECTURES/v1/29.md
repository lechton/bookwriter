# Lecture 29: Combining a Reducer with Context for App-Wide State
> INTERVIEW QUESTION | ❱ CORE | How do you combine a reducer with context for app-wide state?

---

## How Components Far Below Read and Change One Reducer's State

### A reducer and a context on the same page

Lesson 27 gave one component a reducer. Lesson 28 let a component far below read a value without props. This lesson puts the two together. The cart and its `dispatch` function live in one component at the top of the page. How do the components far below read the cart and change it, without every component in between passing them on?

Here are the two pieces we already know:

```jsx title="What Lesson 27 and Lesson 28 gave us"
const [cart, dispatch] = ~useReducer(cartReducer, initialCart)~; // Lesson 27: the cart, and the function that sends actions

<ThemeContext ~value={theme}~>...</ThemeContext> {/* Lesson 28: a provider supplies a value to everything inside it */}
const theme = ~useContext(ThemeContext)~; // Lesson 28: a component below asks React for that value
```

Now put them in the same component. The component that calls `useReducer` puts `cart` in one provider and `dispatch` in another. Each component below asks for the one it needs:

```jsx title="A reducer and two contexts on the same page"
function App() {
  const [cart, dispatch] = useReducer(cartReducer, initialCart);
  return (
    <CartContext ~value={cart}~> {/* Supplies the cart to every component inside */}
      <CartDispatchContext ~value={dispatch}~> {/* Supplies dispatch to every component inside */}
        <Page /> {/* The rest of the page, with Header and DeleteButton somewhere inside */}
      </CartDispatchContext>
    </CartContext>
  );
}

function Header() {
  const cart = ~useContext(CartContext)~; // Gets the cart that App holds
  return <p>Cart: {cart.length} items</p>;
}

function DeleteButton({ id }) {
  const dispatch = ~useContext(CartDispatchContext)~; // Gets the dispatch that App got from useReducer
  return <button onClick={() => dispatch({ type: 'deleted', id: id })}>Delete</button>;
}
```

**Yes, it is the exact same thing!** Combining a reducer with context is not a new tool. It is the reducer of Lesson 27 and the context of Lesson 28, used in the same component. `dispatch` is a value like `theme`. The component that holds it puts it in a provider, and a component below asks for it with `useContext`, exactly as the Share button asked for the theme in Lesson 28.

React's docs say it in three sentences: "Reducers let you consolidate a component's state update logic. Context lets you pass information deep down to other components. You can combine reducers and context together to manage state of a complex screen."

```tree caption="A reducer and a context each do one job; together, a component far below can read the state and send actions."
A reducer and context on the same page
- +The reducer [`useReducer` `cartReducer`] | Keeps **all the update logic** in one function | Gives **`cart`** and **`dispatch`** to the component that calls it
- +The context [`<CartContext value={cart}>` `useContext`] | Carries a value **deep down the tree** | Any component below **asks for it** without props
- +Both together | `App` puts **`cart` and `dispatch`** into two providers | `Header` reads the cart, and a button far below **sends actions**
```

### What the cart and dispatch share, and the one difference

Both values come from the same `useReducer` call in the same component. The one difference is how often they change. `cart` is a new array after every action that changes the cart. `dispatch` stays the very same function for the whole life of the component. React's docs say that `dispatch` "has a stable identity". It means that on every render, React hands back the same function, so `Object.is` finds the old one and the new one equal. That one difference is why the docs give each value its own context. Principle 4 shows what it changes.

### What is at stake

The interview question speaks of app-wide state. That is state that many parts of the app read and change, such as a cart that the header counts and every row changes. It is not a new kind of state. The key idea to remember is this: the state still lives in the component that calls `useReducer`. The context does not store the cart. It only delivers it to the components below. React's docs put the word in quotes: the state still "lives" in the component at the top, managed with `useReducer`.

What is at stake is that one click deep in the page changes two distant places at once. On our page, the user clicks `Delete` on the Bread row. The row must leave the list, and the header at the top must change from `Cart: 3 items` to `Cart: 2 items`. With props, every component on the way down must carry `cart` and four handlers. Suppose one component in the middle forgets to pass `onDelete` on. Then the user clicks `Delete` on the Bread row, the row stays on the page, and the Console shows `Uncaught TypeError: onDelete is not a function`.

Readers usually go wrong in four places:
1. They think the state moved into the context. It did not. Lesson 28 showed that a context holds no value of its own. It carries what the provider gives it, here the cart from the `useReducer` call at the top.
2. They think "app-wide" means one global variable for the whole app. Each component that reads a context gets the value of the closest provider above it. A component outside every provider gets the default value, `null` on our page.
3. They put `cart` and `dispatch` together in one object in one context. Then every component that reads it receives a different object on every render, and React renders all of them again.
4. They remove every prop, including the ones a component really needs, such as the one item each row shows.

### Four ways to share one state with distant components

Developers choose between four ways to let distant components read and change the same state:
1. **Props, as in Lessons 23 and 24.** The state lives in the closest common parent, which passes the state and the handlers down. This fits when few components sit in the middle. React's docs warn that with "tens or hundreds of components in the middle, passing down all state and functions can be quite frustrating!"
2. **Passing JSX as `children`, from Lesson 28.** Fewer components sit in the middle, so fewer props travel.
3. **A reducer together with context, this lesson.** This fits when many distant components read or change the same state. React's docs call it common "to use a reducer together with context to manage complex state and pass it down to distant components without too much hassle."
4. **`useState` together with context.** One context carries an object that holds the state and its setter. Lesson 28 named this way too.

At the start, `App` calls `useReducer` and holds four handlers. Each handler is one line that sends an action, as in Lesson 27. `App` passes the cart to `Header`, and the cart with all four handlers to `CartPage`:

```jsx title="src/App.jsx"
import { useReducer } from 'react';
import cartReducer from './cartReducer.js';
import Header from './components/Header.jsx';
import CartPage from './components/CartPage.jsx';

const initialCart = [
  { id: 0, name: 'Apple', quantity: 1 },
  { id: 1, name: 'Bread', quantity: 2 },
  { id: 2, name: 'Milk', quantity: 1 },
];

export default function App() {
  const [cart, dispatch] = useReducer(cartReducer, initialCart);

  function handleIncrease(id) {
    dispatch({ type: 'increased', id: id });
  }

  function handleDecrease(id) {
    dispatch({ type: 'decreased', id: id });
  }

  function handleDelete(id) {
    dispatch({ type: 'deleted', id: id });
  }

  function handleEmpty() {
    dispatch({ type: 'emptied' });
  }

  return (
    <>
      <Header cart={cart} />
      <CartPage ~cart={cart} onIncrease={handleIncrease} onDecrease={handleDecrease} onDelete={handleDelete} onEmpty={handleEmpty}~ /> {/* Five props for a component that uses none of them */}
    </>
  );
}
```

`Header` uses the cart it receives:

```jsx title="src/components/Header.jsx"
export default function Header({ cart }) {
  return (
    <header>
      <h1>Corner Shop</h1>
      <p>Cart: {cart.length} items</p>
    </header>
  );
}
```

`CartPage` receives five props and only hands them on, four to `CartList` and one to `EmptyCartButton`:

```jsx title="src/components/CartPage.jsx"
import CartList from './CartList.jsx';
import EmptyCartButton from './EmptyCartButton.jsx';

export default function CartPage({ ~cart, onIncrease, onDecrease, onDelete, onEmpty~ }) { // Receives five props, reads none of them
  return (
    <main>
      <h2>Your cart</h2>
      <CartList cart={cart} onIncrease={onIncrease} onDecrease={onDecrease} onDelete={onDelete} />
      <EmptyCartButton onEmpty={onEmpty} />
    </main>
  );
}
```

`CartList` reads the cart and hands the three row handlers on to every row:

```jsx title="src/components/CartList.jsx"
import CartRow from './CartRow.jsx';

export default function CartList({ cart, onIncrease, onDecrease, onDelete }) {
  if (cart.length === 0) {
    return <p>Your cart is empty.</p>;
  }
  return (
    <ul>
      {cart.map(item => (
        <CartRow key={item.id} item={item} ~onIncrease={onIncrease} onDecrease={onDecrease} onDelete={onDelete}~ /> // Passes on three handlers it never calls
      ))}
    </ul>
  );
}
```

At the bottom of the chain, `CartRow` and `EmptyCartButton` finally call the handlers:

```jsx title="src/components/CartRow.jsx"
export default function CartRow({ item, onIncrease, onDecrease, onDelete }) {
  return (
    <li>
      {item.name}: {item.quantity}
      <button onClick={() => onIncrease(item.id)}>Add one</button>
      <button onClick={() => onDecrease(item.id)}>Remove one</button>
      <button onClick={() => ~onDelete(item.id)~}>Delete</button> {/* The handler that came down from App */}
    </li>
  );
}
```

```jsx title="src/components/EmptyCartButton.jsx"
export default function EmptyCartButton({ onEmpty }) {
  return <button onClick={~onEmpty~}>Empty cart</button>; // The handler that came down from App through CartPage
}
```

The page works. But `CartPage` and `CartList` carry handlers they never call, only to pass them on. This is the prop drilling of Lessons 24 and 28. The rest of the lesson removes it, one step at a time, and the page the user sees stays the same at every step.

### Five Principles of Combining a Reducer with Context

**PRINCIPLES:** The state and `dispatch` stay in the component that calls `useReducer`, and two contexts carry them to every component below. Five practical principles follow:
1. **Principle 1: Create two contexts.** One carries the cart and one carries `dispatch`. Each is created by `createContext` with the default value `null`, in a file of their own.
2. **Principle 2: Provide both from the component that calls `useReducer`.** `App` puts `cart` in one provider and `dispatch` in the other, one inside the other. Nothing changes on the page until a component below reads them.
3. **Principle 3: Read the context you need, and drop the props nobody used.** `Header` and `CartList` read the cart. `CartRow` and `EmptyCartButton` read `dispatch` and send their own actions. `CartPage` loses all five props.
4. **Principle 4: Move the reducer and the providers into one provider component.** `CartProvider` calls `useReducer`, provides both contexts, and renders the `children` it receives, so `App` only places it around the page.
5. **Principle 5: Read the two contexts through two small functions.** `useCart` and `useCartDispatch` return the value of each context, so the components never touch the contexts themselves.

Here is the complete map of those five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Two Contexts: One for the State, One for `dispatch`** | Putting `cart` and `dispatch` in one object makes every reader receive a new object on every render; interviewers ask why the docs use two contexts. | Create one context for the state and one for `dispatch`, each by `createContext` with the default value `null`. |
| **Principle 2** | **Two Providers in the Component That Calls `useReducer`** | A provider whose prop is not named `value` gives its readers `undefined`, and the first click on `Delete` fails. | Provide `cart` and `dispatch` with `value`, around everything the component renders. |
| **Principle 3** | **Each Component Reads Only What It Needs** | Components in the middle that carry handlers they never call break the page when one of them forgets to pass a handler on. | Read the state or `dispatch` with `useContext` where it is used, keep the props a component really needs, and drop the rest. |
| **Principle 4** | **A Provider Component That Takes `children`** | A component placed outside the provider reads `null` and blanks the page; with `children`, a component that only sends actions is not rendered again when the cart changes. | Let `CartProvider` call `useReducer`, provide both contexts, and render `children`; place every reader inside it. |
| **Principle 5** | **Two Custom Hooks Read the Two Contexts** | Calling such a function inside a click handler breaks the rules of Hooks; interviewers ask what a custom Hook is. | Export `useCart` and `useCartDispatch` from the context file and call them at the top of each component. |

## 1. Principle 1: createContext Makes CartContext and CartDispatchContext

### Two contexts are two ordinary contexts

The first step is to create the contexts. One `useReducer` call gives two values, so we create two contexts:

```jsx title="src/CartContext.jsx"
import { createContext } from 'react';

export const ~CartContext~ = createContext(null); // Will carry the current cart
export const ~CartDispatchContext~ = createContext(null); // Will carry the dispatch function
```

**Yes, it is the exact same thing!** Each line is the `createContext` of Lesson 28. Nothing in `createContext` knows about reducers. These are two ordinary contexts with two names, and each name says what its context will carry. React's docs build the same pair in their own example, a to-do list: one context provides the current list, and the other "provides the function that lets components dispatch actions."

Both contexts get `null` as the default value. React's docs give the reason: the real values will be provided by the component that calls `useReducer`. On our page, that is `App`, in the next principle. A component reads `null` only when no provider sits above it, and Principle 4 shows what the user sees then.

The contexts sit in a file of their own, so every component file can import them by name with curly braces, as Lesson 05 showed. The file name ends in `.jsx`, because from Principle 4 on the file holds JSX.

```tree caption="The two contexts of the cart: what each one will carry, and where the value will come from."
Two contexts in `src/CartContext.jsx`
- +`CartContext` [`createContext` with `null`] | Will carry **the current cart** | The value will come from `cart`, returned by `useReducer`
- +`CartDispatchContext` [`createContext` with `null`] | Will carry **the `dispatch` function** | The value will come from `dispatch`, returned by the same `useReducer`
```

### Two contexts vs. one context with both values

One `useReducer` call made both values, yet we created two contexts. A junior developer often writes one context instead. Here are the two side by side:

```jsx title="Two contexts, and one context that carries both values"
<CartContext ~value={cart}~> {/* With two contexts: the cart in one, dispatch in the other */}
  <CartDispatchContext value={dispatch}>...</CartDispatchContext>
</CartContext>

<ShopContext ~value={{ cart, dispatch }}~>...</ShopContext> {/* With one context: a new object on every render */}
```

When the page opens, both versions show the same page. **It may look the same, or work the same at first, but it is NOT the same thing!** With one context, the double curly braces build a brand-new object every time the providing component renders. React compares the old value and the new value with `Object.is`, finds two different objects, and renders again every component that reads the context, even one that only uses `dispatch`. With two contexts, the context for `dispatch` always carries the same function, because `dispatch` never changes. Principle 4 shows the difference on our page, once the page has a component that only uses `dispatch`.

The default value matters too. With `null` as the default value, a component placed outside the provider fails loudly when it reads `cart.length`. With an empty array `[]` as the default value, the same header would quietly show `Cart: 0 items`, and the mistake would hide. The docs choose `null` for this pattern.

### Our page after this step

Nothing on the page changes yet. No component imports the contexts, so the page still works through props, and the Console stays quiet.

> [!PRINCIPLE]
> **Principle 1: Two Contexts: One for the State, One for `dispatch`**
>
> *To pass a reducer's state and `dispatch` down the tree, create two separate contexts by `createContext` with the default value `null`, one for the state and one for `dispatch`, in a file of their own.*
>
> A reducer gives two values from one call, and they change at different rates: the cart is new after every action, and `dispatch` never changes. Each value gets its own context, so a component can read only the one it needs. Packing both into one object makes that object new on every render, and every reader renders again.
>
> **DO THIS:**
> ```jsx
> export const CartContext = createContext(null);
> export const ~CartDispatchContext~ = createContext(null); // dispatch gets a context of its own
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ShopContext ~value={{ cart, dispatch }}~> {/* **WRONG:** a new object on every render, so every reader renders again */}
>   <CartPage />
> </ShopContext>
> ```

## 2. Principle 2: App Puts cart and dispatch into Two Providers

### Two providers, one inside the other

The second step is to provide the two values. The component that calls `useReducer` already has `cart` and `dispatch`, so it wraps everything it renders in the two providers:

```jsx title="Providing the cart and dispatch from the component that calls useReducer"
function App() {
  const [cart, dispatch] = useReducer(cartReducer, initialCart);
  return (
    <CartContext ~value={cart}~> {/* The cart, for every component inside */}
      <CartDispatchContext ~value={dispatch}~> {/* The dispatch function, for every component inside */}
        <Page />
      </CartDispatchContext>
    </CartContext>
  );
}
```

React's docs call this step "Put state and dispatch into context". There is no new word here. The provider and its `value` come from Lesson 28, and `cart` and `dispatch` from Lesson 27.

One provider sits inside the other, so they can go in either order:

```jsx title="The two orders of the providers"
<CartContext value={cart}><CartDispatchContext value={dispatch}>...</CartDispatchContext></CartContext> {/* CartContext outside */}
<CartDispatchContext value={dispatch}><CartContext value={cart}>...</CartContext></CartDispatchContext> {/* CartDispatchContext outside */}
```

**Yes, it is the exact same thing!** Each component that reads a context asks for one context by name, and React finds the closest provider of that context above it, as Lesson 28 showed. A provider of the other context does not count. So whichever provider is outside, every reader of `CartContext` gets the cart, and every reader of `CartDispatchContext` gets `dispatch`.

### A provider only makes a value available

A junior developer often expects the buttons to start sending actions through the context as soon as `dispatch` is in a provider. They do not. A provider only makes a value available. Nothing changes until a component below asks for it.

On our page, `App` imports both contexts and wraps its two components in the providers. It keeps every prop, so the page still works through props. React's docs take the same in-between step: "For now, you pass the information both via props and in context".

```jsx title="src/App.jsx" startLine="1"
import { useReducer } from 'react';
import cartReducer from './cartReducer.js';
import { ~CartContext, CartDispatchContext~ } from './CartContext.jsx'; // Named exports, so curly braces
import Header from './components/Header.jsx';
import CartPage from './components/CartPage.jsx';
```

The return of `App` now wraps the same two components in the two providers:

```jsx title="src/App.jsx" startLine="32"
  return (
    <CartContext ~value={cart}~> {/* Makes the cart available below */}
      <CartDispatchContext ~value={dispatch}~> {/* Makes dispatch available below */}
        <Header cart={cart} />
        <CartPage cart={cart} onIncrease={handleIncrease} onDecrease={handleDecrease} onDelete={handleDelete} onEmpty={handleEmpty} />
      </CartDispatchContext>
    </CartContext>
  );
}
```

The page looks the same as before, and every click works the same. The providers add no element to the page: the Elements panel shows the same `<header>` and `<main>` as before. `App` itself cannot read the two contexts it provides, because React's docs say a `useContext` call "is not affected by providers returned from the *same* component". It does not need to read them, because it already has `cart` and `dispatch`.

### A provider without value

A real mistake at this step is to name the prop after the value it carries:

```jsx title="src/App.jsx" startLine="34"
      <CartDispatchContext ~dispatch={dispatch}~> {/* **WRONG:** a provider reads only the prop named value */}
```

React's docs say a provider without `value` is "like passing `value={undefined}`". The page still works for now, because every component still uses props. But React already prints a warning in the Console when the page opens:

```page width=text caption="The shop page when App provides dispatch with a prop named dispatch instead of value: the page works, and the Console shows a warning."
heading: Corner Shop
line: Cart: 3 items
section: Your cart
line: • Apple: 1 [Add one] [Remove one] [Delete]
line: • Bread: 2 [Add one] [Remove one] [Delete]
line: • Milk: 1 [Add one] [Remove one] [Delete]
line: [Empty cart]
console: The `value` prop is required for the `<Context.Provider>`. Did you misspell it or forget to pass it?
```

The mistake shows on the page as soon as a component reads the context, as `CartRow` does in the next principle. `CartRow` asks for `CartDispatchContext` and gets `undefined`, not the default `null`, because a provider does sit above it. When the user clicks `Delete`, the click fails with `TypeError: dispatch is not a function`, and the row stays on the page. The fix is to name the prop `value`.

> [!PRINCIPLE]
> **Principle 2: Two Providers in the Component That Calls `useReducer`**
>
> *The component that calls `useReducer` provides the state in one provider and `dispatch` in the other, one inside the other, around everything it renders.*
>
> The component that calls `useReducer` is the only one that has the cart and `dispatch`, so it is the one that provides them. The order of the two providers does not matter, because each reader looks only for the provider of its own context. A provider only makes a value available: nothing changes on the page until a component below reads it. The prop must be named `value`, or every reader gets `undefined`.
>
> **DO THIS:**
> ```jsx
> <CartContext value={cart}>
>   <CartDispatchContext ~value={dispatch}~> {/* Readers below get the dispatch from useReducer */}
>     <CartPage />
>   </CartDispatchContext>
> </CartContext>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <CartContext value={cart}>
>   <CartDispatchContext ~dispatch={dispatch}~> {/* **WRONG:** no value prop, so readers below get undefined */}
>     <CartPage />
>   </CartDispatchContext>
> </CartContext>
> ```

## 3. Principle 3: CartRow Reads dispatch, and CartPage Loses Its Props

### A handler from the parent vs. dispatch from the context

The third step is to read the contexts where the values are used. Here are two ways for a row to delete its item:

```jsx title="A Delete button with onDelete from the parent, and with dispatch from the context"
function CartRow({ item, ~onDelete~ }) { // With onDelete: the handler came down from App through every parent
  return <button onClick={() => onDelete(item.id)}>Delete</button>;
}

function CartRow({ item }) {
  const dispatch = ~useContext(CartDispatchContext)~; // With useContext: dispatch comes from the closest provider above
  return <button onClick={() => dispatch({ type: 'deleted', id: item.id })}>Delete</button>;
}
```

For the user, **yes, it is the exact same thing!** The same click sends the same action, `{ type: 'deleted', id: item.id }`, to the same `cartReducer`, and the same row leaves the page. The one difference is how the row gets what it calls. With `onDelete`, the handler came down from `App` through `CartPage` and `CartList`, and `App` built the action in `handleDelete`. With `useContext`, the row gets `dispatch` straight from the closest provider above, and it builds the action itself, where the click happens.

React's docs describe the finished step in one sentence: "Each component reads the context that it needs". Any component below the component that calls `useReducer` can now read the state and send actions, without passing them through every component on the way.

### Every component reads only what it needs

On our page, two components read the cart and two read `dispatch`. `Header` reads the cart for its count:

```jsx title="src/components/Header.jsx"
import { useContext } from 'react';
import { CartContext } from '../CartContext.jsx';

export default function Header() {
  const cart = ~useContext(CartContext)~; // The cart that App provides, with no prop
  return (
    <header>
      <h1>Corner Shop</h1>
      <p>Cart: {cart.length} items</p>
    </header>
  );
}
```

`CartList` reads the cart too. It still gives each row its `item` as a prop, and nothing else:

```jsx title="src/components/CartList.jsx"
import { useContext } from 'react';
import { CartContext } from '../CartContext.jsx';
import CartRow from './CartRow.jsx';

export default function CartList() {
  const cart = useContext(CartContext);
  if (cart.length === 0) {
    return <p>Your cart is empty.</p>;
  }
  return (
    <ul>
      {cart.map(item => (
        <CartRow key={item.id} ~item={item}~ /> // The one prop the row really needs
      ))}
    </ul>
  );
}
```

`CartRow` reads `dispatch` and sends its own three actions:

```jsx title="src/components/CartRow.jsx"
import { useContext } from 'react';
import { CartDispatchContext } from '../CartContext.jsx';

export default function CartRow({ item }) {
  const dispatch = ~useContext(CartDispatchContext)~; // The dispatch that App got from useReducer
  return (
    <li>
      {item.name}: {item.quantity}
      <button onClick={() => dispatch({ type: 'increased', id: item.id })}>Add one</button>
      <button onClick={() => dispatch({ type: 'decreased', id: item.id })}>Remove one</button>
      <button onClick={() => dispatch({ type: 'deleted', id: item.id })}>Delete</button>
    </li>
  );
}
```

`EmptyCartButton` reads only `dispatch`:

```jsx title="src/components/EmptyCartButton.jsx"
import { useContext } from 'react';
import { CartDispatchContext } from '../CartContext.jsx';

export default function EmptyCartButton() {
  const dispatch = useContext(CartDispatchContext);
  return <button onClick={() => ~dispatch({ type: 'emptied' })~}>Empty cart</button>; // Sends its own action
}
```

A junior developer often thinks context replaces props, so every prop goes. It does not. Context replaces only the props that components in the middle carried for others. `item` is not one of them. Each row shows a different item, and only `CartList` knows which one, so `item` stays a prop. React's docs keep the same prop in their own example, where each row of the to-do list still gets its task as a prop.

### The components in the middle lose their props

Now compare `CartPage` before and after this step:

```jsx title="CartPage with five props, and CartPage with none"
export default function CartPage({ ~cart, onIncrease, onDecrease, onDelete, onEmpty~ }) { // With five props it never reads
  return (
    <main>
      <h2>Your cart</h2>
      <CartList cart={cart} onIncrease={onIncrease} onDecrease={onDecrease} onDelete={onDelete} />
      <EmptyCartButton onEmpty={onEmpty} />
    </main>
  );
}

export default function ~CartPage~() { // With no props at all
  return (
    <main>
      <h2>Your cart</h2>
      <CartList />
      <EmptyCartButton />
    </main>
  );
}
```

**Yes, it is the exact same page!** The `CartPage` with no props renders the same heading, the same list, and the same button. It simply stops holding values it never used.

`App` loses its four handlers too. The actions are now built in the components where the user clicks, so `App` only calls `useReducer` and provides the two values:

```jsx title="src/App.jsx" startLine="13"
export default function App() {
  const [cart, dispatch] = useReducer(cartReducer, initialCart);
  return (
    <CartContext value={cart}>
      <CartDispatchContext value={dispatch}>
        ~<Header />~ {/* No props */}
        ~<CartPage />~ {/* No props */}
      </CartDispatchContext>
    </CartContext>
  );
}
```

```tree caption="Where each component gets what it uses, before and after it reads the contexts."
How the cart and its actions reach each component
- !With props | `App` passes `cart` and **four handlers** down | `CartPage` and `CartList` **carry handlers they never call**
- +With the two contexts | `Header` and `CartList` **read `CartContext`** | `CartRow` and `EmptyCartButton` **read `CartDispatchContext`**; `CartPage` takes **no props**
```

### One click deep in a row changes the header at the top

The user clicks `Delete` on the Apple row, deep inside `CartList`, and the header at the very top changes from `Cart: 3 items` to `Cart: 2 items`. No line of `CartRow` mentions the header. Here is what happens, in order:
1. React calls the arrow function on the `Delete` button of the Apple row.
2. `CartRow` sends the action `{ type: 'deleted', id: 0 }` to the `dispatch` it read from `CartDispatchContext`.
3. That `dispatch` is the one `App` got from `useReducer`, so React renders `App` again and calls `cartReducer` with the current cart and the action.
4. `useReducer` returns a new array with two items, and `App` passes it to `<CartContext value={cart}>`.
5. `Header` and `CartList` both read `CartContext`, so both show the new array: the header says `Cart: 2 items`, and the list shows two rows.

```page width=text caption="The shop page after the user clicks Delete on the Apple row: the row leaves, and the header shows two items."

section: Your cart
line: • Bread: 2 [Add one] [Remove one] [Delete]
line: • Milk: 1 [Add one] [Remove one] [Delete]

console: quiet
```

The state still lives in `App`, managed with `useReducer`, as React's docs say. This is the lifting state up of Lesson 24, with context in place of the props.

### A context that was never imported

A real mistake at this step is to add the `useContext` line and forget the import:

```jsx title="src/components/EmptyCartButton.jsx"
import { useContext } from 'react';

export default function EmptyCartButton() {
  const dispatch = useContext(~CartDispatchContext~); // **WRONG:** this file never imported CartDispatchContext
  return <button onClick={() => dispatch({ type: 'emptied' })}>Empty cart</button>;
}
```

When the page opens, it goes blank. JavaScript finds no `CartDispatchContext` in this file. It is the same kind of error as a missing component name in Lesson 06:

```page width=text caption="The shop page when EmptyCartButton reads CartDispatchContext without importing it: the page is blank."
blank
console: Uncaught ReferenceError: CartDispatchContext is not defined
console: An error occurred in the <EmptyCartButton> component. Consider adding an error boundary to your tree to customize error handling behavior.
```

The fix is to import the context in every file that reads it, as `CartRow.jsx` does above.

> [!PRINCIPLE]
> **Principle 3: Each Component Reads Only What It Needs**
>
> *Any component below the providers reads the state from `CartContext` or `dispatch` from `CartDispatchContext` with `useContext`, and sends its own action; the components in the middle stop receiving props they never used.*
>
> With props, every component between `App` and the buttons carried handlers it never called, and one forgotten prop broke a button. With the two contexts, a component that shows the cart reads the cart, and a component that changes it reads `dispatch`. One click deep in a row changes the header at the top, because both read the same cart from `App`. A prop that a component really needs, such as the item of one row, stays a prop.
>
> **DO THIS:**
> ```jsx
> function CartRow({ item }) {
>   const dispatch = ~useContext(CartDispatchContext)~; // Reads dispatch from the closest provider above
>   return <button onClick={() => dispatch({ type: 'deleted', id: item.id })}>Delete</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function CartPage({ ~onDelete~ }) { // **WRONG:** carries a handler it never calls, only to pass it down
>   return <CartList onDelete={onDelete} />;
> }
> ```

## 4. Principle 4: CartProvider Wraps children and Holds the Reducer

### A provider component is a component like any other

The page works, but `App` still holds the `useReducer` call, the starting cart, and both providers. React's docs call this code the "wiring": the code that creates the state and connects it to the two contexts. The fourth step moves all of it into one component, next to the contexts:

```jsx title="A provider component that holds the reducer and both providers"
export function ~CartProvider~({ children }) { // Our own component, not a part of React
  const [cart, dispatch] = useReducer(cartReducer, initialCart);
  return (
    <CartContext value={cart}>
      <CartDispatchContext value={dispatch}>
        ~{children}~ {/* Whatever App writes between <CartProvider> and </CartProvider> */}
      </CartDispatchContext>
    </CartContext>
  );
}

export default function App() {
  return (
    <CartProvider>
      <Header />
      <CartPage />
    </CartProvider>
  );
}
```

React's docs list the three jobs of this component: "1. It will manage the state with a reducer. 2. It will provide both contexts to components below. 3. It will take `children` as a prop so you can pass JSX to it."

A junior developer often thinks `CartProvider` is a special provider from React. It is not. **Yes, it is the exact same thing as any other component!** It is our own function, named in `PascalCase`, that calls `useReducer` and renders two of React's providers around its `children`. And `children` is the prop of Lesson 09: React collects `<Header />` and `<CartPage />`, written between `<CartProvider>` and `</CartProvider>` in `App`, into `props.children`. The docs call such a component a provider component. They add that "You don't have to do this": it only keeps the other components tidy.

```tree dir=right caption="How Header and CartPage, written inside CartProvider in App, end up inside both providers."
How `<CartProvider><Header /><CartPage /></CartProvider>` reaches the page
- +1. In `App` [`<CartProvider>...</CartProvider>`] | `Header` and `CartPage` are written **between the tags**
- +2. In `props` [`props.children`] | React collects both into **`children`**
- +3. In `CartProvider` [`{children}`] | Both render **inside the two providers**, so they can read the cart and `dispatch`
```

### Our page after this step

The context file now holds everything about the state of the cart. It imports `useReducer` and the `cartReducer` of Lesson 27, takes `initialCart` from `App`, and exports `CartProvider`:

```jsx title="src/CartContext.jsx"
import { createContext, useReducer } from 'react';
import cartReducer from './cartReducer.js';

const initialCart = [
  { id: 0, name: 'Apple', quantity: 1 },
  { id: 1, name: 'Bread', quantity: 2 },
  { id: 2, name: 'Milk', quantity: 1 },
];

export const CartContext = createContext(null);
export const CartDispatchContext = createContext(null);

export function ~CartProvider~({ children }) { // The state of the cart now lives here
  const [cart, dispatch] = useReducer(cartReducer, initialCart);
  return (
    <CartContext value={cart}>
      <CartDispatchContext value={dispatch}>
        {children}
      </CartDispatchContext>
    </CartContext>
  );
}
```

`App` loses `useReducer`, `initialCart`, and both providers. It only places `CartProvider` around the parts of the page that need the cart:

```jsx title="src/App.jsx"
import { CartProvider } from './CartContext.jsx';
import Header from './components/Header.jsx';
import CartPage from './components/CartPage.jsx';

export default function App() {
  return (
    ~<CartProvider>~ {/* Every component inside can read the cart and dispatch */}
      <Header />
      <CartPage />
    </CartProvider>
  );
}
```

The page looks and works the same as in Principle 3, and `CartProvider` adds no element to the Elements panel. `App` is now free of all the wiring. React's docs suggest thinking of the provider component as a part of the screen that knows how to deal with its data, here with the cart.

### Header inside the provider vs. Header outside it

Where `App` places `Header` matters. Look at two ways to write the return of `App`:

```jsx title="Header inside CartProvider, and Header above it"
<CartProvider><Header /><CartPage /></CartProvider> {/* Header inside: it reads the cart */}
<><Header /><CartProvider><CartPage /></CartProvider></> {/* Header outside: it reads the default null */}
```

**It may look the same, but it is NOT the same thing!** Both place a header above the cart. But when `Header` sits outside, no `CartContext` provider sits above it, so `useContext` returns the default value of `CartContext`, `null`. `Header` then reads `cart.length` on `null`, and the page goes blank when it opens:

```page width=text caption="The shop page when Header sits above CartProvider: Header reads null, and the page is blank."
blank
console: Uncaught TypeError: Cannot read properties of null (reading 'length')
console: An error occurred in the <Header> component. Consider adding an error boundary to your tree to customize error handling behavior.
```

React's docs name this cause: "You may have forgotten to wrap your component with `<SomeContext>`, or you might have put it in a different part of the tree than you thought." The fix is to place every component that reads the cart inside `<CartProvider>`. Here the default value `null` from Principle 1 pays off: the mistake shows at once, instead of a header that quietly says `Cart: 0 items`.

### A component that only sends actions stops rendering again

Moving the reducer into `CartProvider` also changes which components React renders again after a click. To see it, we put one line at the top of `EmptyCartButton`:

```jsx title="src/components/EmptyCartButton.jsx"
import { useContext } from 'react';
import { CartDispatchContext } from '../CartContext.jsx';

export default function EmptyCartButton() {
  ~console.log('EmptyCartButton renders');~ // Prints once for each render of EmptyCartButton
  const dispatch = useContext(CartDispatchContext);
  return <button onClick={() => dispatch({ type: 'emptied' })}>Empty cart</button>;
}
```

Then the user clicks `Add one` on Bread once. The page looks the same with the providers inside `App` and with `CartProvider`, so only the Console shows the difference. In development, `<StrictMode>` calls each component twice, as Lesson 14 showed, so each render prints the line twice:

::: row caption="The Console after the page opens and the user clicks Add one on Bread once, with the providers inside App and with CartProvider."
::: col title="Providers inside App" tag="renders again after the click" tone=bad
```devconsole
+ EmptyCartButton renders | EmptyCartButton.jsx:5
+ EmptyCartButton renders | EmptyCartButton.jsx:5
+ EmptyCartButton renders | EmptyCartButton.jsx:5
+ EmptyCartButton renders | EmptyCartButton.jsx:5
```
Two lines when the page opens, and two more after the click.
:::
::: col title="CartProvider with children" tag="renders only when the page opens" tone=good
```devconsole
+ EmptyCartButton renders | EmptyCartButton.jsx:5
+ EmptyCartButton renders | EmptyCartButton.jsx:5
```
Two lines when the page opens, and none after the click.
:::
:::

This surprises most readers, because the code inside `EmptyCartButton` is the same in both. Here is what happens after the click, first with the providers inside `App`:
1. The click sends an action, and the cart lives in `App`, so React renders `App` again.
2. A render calls the component and the components it returns, and theirs, as Lesson 13 showed. React's docs put it this way: "This process is recursive: if the updated component returns some other component, React will render _that_ component next".
3. So React renders `Header`, `CartPage`, `CartList`, every `CartRow`, and `EmptyCartButton` again, whether they read the cart or not.

Now with `CartProvider`:
1. The click sends an action, and the cart lives in `CartProvider`, so React renders `CartProvider` again, and not `App`.
2. `<Header />` and `<CartPage />` were created by `App`, and `App` did not render again, so `children` holds the very same elements as before. React's docs on `memo` say that when a component takes JSX as `children` and updates its own state, "React knows that its children don't need to re-render."
3. `CartContext` receives a new array, so React renders again the components that read it: `Header`, `CartList`, and the rows that `CartList` returns.
4. `CartDispatchContext` receives the same `dispatch` as before, because `dispatch` has a stable identity. React compares the two with `Object.is`, finds them equal, and renders none of its readers again. `CartPage` reads nothing, so it is not rendered again either, and neither is `EmptyCartButton` inside it.

This is the full answer to the question of Principle 1: two contexts and `children` work together. With one context carrying `{ cart, dispatch }`, the object would be new on every render of `CartProvider`, and `EmptyCartButton` would render again after every click. Without `children`, every render of the component that holds the state renders everything below it anyway. Lesson 59 measures this further.

React's docs end the topic with one more point: "You can have many context-reducer pairs like this in your app." A shop could have one pair for the cart and another for the signed-in user, each with its own provider component.

> [!PRINCIPLE]
> **Principle 4: A Provider Component That Takes `children`**
>
> *A provider component, `CartProvider`, calls `useReducer`, provides both contexts, and renders the `children` it receives; `App` only places `<CartProvider>` around the parts of the page that need the cart.*
>
> `App` no longer holds the reducer or the providers: all of it lives in one component, next to the contexts. `CartProvider` is our own component, and `children` is the prop of Lesson 09. Every component that reads the cart must sit inside it, or it reads `null`. Because the children come from `App`, a click that changes the cart renders again only the components that read the cart, not a component that only sends actions.
>
> **DO THIS:**
> ```jsx
> export default function App() {
>   return (
>     ~<CartProvider>~ {/* Header and CartPage both sit inside the provider */}
>       <Header />
>       <CartPage />
>     </CartProvider>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   return (
>     <>
>       ~<Header />~ {/* **WRONG:** outside CartProvider, so it reads null and the page goes blank */}
>       <CartProvider><CartPage /></CartProvider>
>     </>
>   );
> }
> ```

## 5. Principle 5: useCart and useCartDispatch Read the Two Contexts

### Two small functions that read the contexts

Every component that reads the cart still imports `useContext` and a context, and calls one with the other. The last step puts each of those calls in a small function, in the context file:

```jsx title="Two functions that read the two contexts"
export function ~useCart~() { // Returns the cart from the closest provider above
  return useContext(CartContext);
}

export function ~useCartDispatch~() { // Returns dispatch from the closest provider above
  return useContext(CartDispatchContext);
}
```

A component now calls the function instead of `useContext`:

```jsx title="Reading dispatch with useContext, and with useCartDispatch"
const dispatch = ~useContext(CartDispatchContext)~; // With useContext and the context
const dispatch = ~useCartDispatch()~; // With the function: the same dispatch
```

**Yes, it is the exact same thing!** React's docs say so: "This doesn't change the behavior in any way, but it lets you later split these contexts further or add some logic to these functions."

These functions have a name in React: a **custom Hook**. A custom Hook is our own function that calls a Hook of React, and its name starts with `use`, like the Hooks of Lesson 12. React's docs give the rule: "Your function is considered a custom Hook if its name starts with `use`. This lets you use other Hooks, like `useContext`, inside it." A junior developer often takes `useCart` for a new Hook from React. It is not. It is our own function, one line long. Lesson 39 covers custom Hooks in full.

One more thing surprises readers here. `useCart` sits in `CartContext.jsx`, yet the cart it returns does not depend on that file. A custom Hook runs inside the component that calls it. So when `Header` calls `useCart`, the `useContext` inside it finds the closest `CartContext` provider above `Header`.

### Our page after this step

The context file adds `useContext` to its import and the two custom Hooks at the bottom. The two contexts lose `export`. No other file needs them now, so the only ways in from another file are `CartProvider`, `useCart`, and `useCartDispatch`, as in the last version of the docs' example:

```jsx title="src/CartContext.jsx" startLine="1"
import { createContext, ~useContext~, useReducer } from 'react'; // useContext is now used inside this file
import cartReducer from './cartReducer.js';
```

```jsx title="src/CartContext.jsx" startLine="10"
~const CartContext~ = createContext(null); // No export: other files reach it through useCart
const CartDispatchContext = createContext(null);
```

```jsx title="src/CartContext.jsx" startLine="24"
export function useCart() {
  return useContext(CartContext);
}

export function useCartDispatch() {
  return useContext(CartDispatchContext);
}
```

The four components that read the contexts import the custom Hooks instead. `Header` and `CartList` call `useCart`:

```jsx title="src/components/Header.jsx"
import { useCart } from '../CartContext.jsx';

export default function Header() {
  const cart = ~useCart()~; // The same cart as useContext(CartContext)
  return (
    <header>
      <h1>Corner Shop</h1>
      <p>Cart: {cart.length} items</p>
    </header>
  );
}
```

`CartRow` and `EmptyCartButton` call `useCartDispatch`:

```jsx title="src/components/EmptyCartButton.jsx"
import { useCartDispatch } from '../CartContext.jsx';

export default function EmptyCartButton() {
  const dispatch = ~useCartDispatch()~; // The same dispatch as useContext(CartDispatchContext)
  return <button onClick={() => dispatch({ type: 'emptied' })}>Empty cart</button>;
}
```

The page behaves exactly as in Principle 4. All the wiring of the context and the reducer now sits in `CartContext.jsx`. React's docs describe the gain: the components stay "focused on what they display rather than where they get the data".

### Calling the custom Hook inside the click

A real mistake is to call the custom Hook where `dispatch` is used, inside the click:

```jsx title="src/components/EmptyCartButton.jsx"
export default function EmptyCartButton() {
  return <button onClick={() => ~useCartDispatch()~({ type: 'emptied' })}>Empty cart</button>; // **WRONG:** a Hook called inside a click handler
}
```

The page opens normally. But when the user clicks `Empty cart`, React reports an invalid Hook call in the Console, and the cart stays as it was. Why? Well, `useCartDispatch` calls `useContext`, and a Hook may be called only at the top level of a component or of a custom Hook, while React renders it. A click handler runs later, after the render. Lesson 38 covers these rules. The fix is to call `useCartDispatch` at the top of `EmptyCartButton`, as above, and use `dispatch` inside the arrow function.

> [!PRINCIPLE]
> **Principle 5: Two Custom Hooks Read the Two Contexts**
>
> *The file that holds the contexts exports `useCart` and `useCartDispatch`, which return `useContext` of each context; components call them at their top level instead of importing the contexts.*
>
> Each custom Hook is one line, and it changes nothing on the page. It moves the last piece of the wiring into the context file, so the components only say what they need: the cart, or `dispatch`. The contexts no longer need `export`. A custom Hook runs inside the component that calls it, so it finds the closest provider above that component, and like any Hook it must be called at the top level.
>
> **DO THIS:**
> ```jsx
> function EmptyCartButton() {
>   const dispatch = ~useCartDispatch()~; // Called at the top level of the component
>   return <button onClick={() => dispatch({ type: 'emptied' })}>Empty cart</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function EmptyCartButton() {
>   return <button onClick={() => ~useCartDispatch()~({ type: 'emptied' })}>Empty cart</button>; // **WRONG:** a Hook called inside the click handler
> }
> ```

```jsx title="src/cartReducer.js"
export default function cartReducer(cart, action) {
  switch (action.type) {
    case 'increased': {
      return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity + 1 } : item);
    }
    case 'decreased': {
      return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity - 1 } : item).filter(item => item.quantity > 0);
    }
    case 'deleted': {
      return cart.filter(item => item.id !== action.id);
    }
    case 'emptied': {
      return [];
    }
    default: {
      throw Error('Unknown action: ' + action.type);
    }
  }
}
```

### How React calls the components

When the page opens, React calls `App`, then `CartProvider`, which calls `useReducer` and gets `initialCart`. Then React calls the components inside the providers from top to bottom: `Header`, then `CartPage`, then `CartList` with its three rows, then `EmptyCartButton`. After each click by the user, React renders `CartProvider` again and, of the rest, only the components that read the cart:

```tree caption="The component tree of the finished shop page, the order in which React calls the components when the page opens, and what happens after a click."
`App` | **1. Called first**, only when the page opens | Places `<CartProvider>` around **`Header`** and **`CartPage`**
- +`CartProvider` | **2. Called next**, and again after every click | **Holds `cart`** through `useReducer` and provides **both contexts** around `children`
  - +`Header` | **3. Reads `useCart`** and shows the count | Renders again when the cart changes
  - +`CartPage` | **4. Reads nothing** | **Not rendered again** after a click
```

## For the Interview

> **The Interview Question:** How do you combine a reducer with context for app-wide state?

### How to Answer Clearly in 30 Seconds

"A reducer keeps the update logic of a state in one function, and context passes a value deep into the tree without props. Combined, they let any component below read and change a state that lives at the top. React's docs give three steps:
1. **Create** two contexts by `createContext`, each with the default value `null`: one for the state and one for `dispatch`.
2. **Provide** both from the component that calls `useReducer`, one provider inside the other.
3. **Use** them: a component that shows the state reads the state context, and a component that changes it reads `dispatch` and sends its own action. The components in the middle stop passing props they never used.

The state still lives in the component that calls `useReducer`; context only delivers it. Usually I move the reducer and both providers into a provider component that renders `children`, and I export two custom Hooks, such as `useCart` and `useCartDispatch`, that read the two contexts."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why two contexts, and not one context with `{ state, dispatch }`?"**
   Because the two values change at different rates. The state is new after every action, while `dispatch` "has a stable identity", as React's docs say: it is the same function on every render. React compares the old and the new value of a context with `Object.is`. An object such as `{ cart, dispatch }` written in `value` is a new object on every render of the provider, so every component that reads the context renders again, even one that only sends actions. With two contexts, the context for `dispatch` never changes. So a component that reads only `dispatch` is not rendered again when the state changes, as long as the provider component renders its `children` instead of creating them itself. React's docs fix an object value another way, with `useMemo` and `useCallback`, in Lesson 59. `dispatch` needs no `useCallback`, because it never changes.
2. **"Does 'app-wide state' mean one global variable? Where does the state actually live?"**
   No. The state lives in the component that calls `useReducer`, such as `CartProvider`. Each component that reads a context gets the value of the closest provider above it. So a component outside the provider gets the default value, and with the default value `null`, reading `cart.length` throws a `TypeError`. React's docs suggest checking the tree with React Developer Tools when a component does not see the value of its provider. And an app can have "many context-reducer pairs like this", one for each part of the screen. React's docs call the whole pattern "a powerful way to scale your app and lift state up without too much work whenever you want to access the data deep in the tree."
3. **"When would you use a reducer with context instead of props?"**
   When many distant components read or change the same state, and the components between them only pass props on. With a few components in the middle, props are simpler, and React's docs agree that props work well in a small example. Passing JSX as `children` can also leave fewer components in the middle. Context does not remove every prop: a prop that a component really needs, such as the item of one row, stays a prop. And `memo` does not stop a component that reads a context from rendering again when the value changes. React's docs say: "Skipping re-renders with `memo` does not prevent the children receiving fresh context values."

```tree caption="Interview summary: what each part of a reducer combined with context does."
A reducer combined with context
- +`useReducer` in `CartProvider` | **Holds the state** and gives **`cart`** and **`dispatch`** | The state **still lives here**
- +Two contexts, two providers [`CartContext` `CartDispatchContext`] | Deliver **`cart`** and **`dispatch`** separately | `dispatch` **never changes**, so its readers are not rendered again
- +Two custom Hooks [`useCart` `useCartDispatch`] | Read each context **at the top level** of a component | Components **never import the contexts**
```
