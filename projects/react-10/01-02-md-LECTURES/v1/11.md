## How React Responds to User Events

### Handing a function to `onClick` vs. calling it during render

Before we build an interactive page, look at three ways a developer might wire a function to a button in React:

```jsx title="Three ways developers try to wire sayHello to a button"
function sayHello() {
  console.log('Hello');
}

<button ~onClick={sayHello}~>Say hello</button> // 1. Passes the sayHello function itself to React
<button ~onClick={() => sayHello()}~>Say hello</button> // 2. Passes an arrow function that calls sayHello on click
<button ~onClick={sayHello()}~>Say hello</button> // 3. **WRONG:** calls sayHello right now during render!
```

Compare those three buttons carefully:
- **Look at the first two buttons**: In the first button, we pass the function by name. In the second button, we wrap the call inside an arrow function. **Yes, when clicked, those first two buttons do the exact same thing!** Both hand React a function to save now and call later on click.
- **Now compare the first button with the third button**: The third button adds two tiny parentheses right after the function name inside the curly braces. **It may look almost the same on the tag, but it is NOT the same thing at all!**

**Where did the parentheses go on the first button?**
- **Without parentheses**, passing the function name is like writing your phone number on a sticky note and handing it to a receptionist. The receptionist keeps the note and calls your number only when a visitor walks in and clicks the button.
- **With parentheses**, calling the function inside curly braces is like dialing the phone yourself right at the front desk while the page is still being built. The function runs immediately before anyone touches the mouse. Then it hands its empty return value, `undefined`, to `onClick`, so clicking the button later does nothing!

Now look at the everyday meaning of the words we use whenever a page responds to the user:
- **What is an "event"?** In everyday English, an **event** is something that happens at a specific moment, such as a mouse click, a key press, or a form submission.
- **What is an "event handler"?** A **handler** is the function you write to handle that event when it happens, such as `handleLike` or `handleCommentSubmit`.
- **What is "event propagation", also called "bubbling"?** Imagine a button physically glued onto the front of a cardboard box. When you press the button with your finger, your finger also presses the box behind it. In the browser, a click starts on the inner `<button>` and then rises upward to the parent `<article>` card like an air bubble rising through water. To pop that bubble so the parent card's handler does not run, you call `e.stopPropagation`.
- **What is a "default browser action"?** Certain HTML tags have a built-in browser reflex from the early days of the web. When you submit a `<form>`, the browser's built-in reflex reloads the entire page from scratch. To cancel that built-in reload reflex, you call `e.preventDefault`.

Whenever you work with the event object `e`, you will see two methods that sound alike. **Both `e.stopPropagation` and `e.preventDefault` sound like "stop this event", so they look like they do the same job. Yet they are NOT the same thing!**
- **`e.stopPropagation`** stops the event from climbing up to **parent tags** in your component tree.
- **`e.preventDefault`** stops the **browser's built-in default action** for that HTML tag, such as reloading the page when a `<form>` is submitted:

```tree caption="The four tools for responding to user events in React and what each one controls."
Four tools for responding to events in React
- +1. Function reference [`onClick` with `handleLike`] | Hands the function **by name** to React without parentheses | Runs **only when the user clicks**, never during render
- +2. Inline arrow wrapper [`onClick` with arrow function] | Wraps a call that needs a **custom argument** inside an arrow function | Keeps the call **sealed until the user clicks**
- +3. Stop upward bubbling [`e.stopPropagation`] | Stops a click on an inner `<button>` from **climbing up** to a parent `<article>` | Prevents the parent tag's `onClick` handler from firing too
- +4. Stop browser default [`e.preventDefault`] | Cancels the browser's **built-in reflex** on `<form>` submit | Keeps the browser tab from **reloading the whole page**
```

### Why events on a real page need all four tools

Imagine a compact news reader page with one clickable story card for a park opening and a comment form right below it:
1. Inside the story card, a **like button** lets the reader like the article. That button needs a function reference on `onClick` so it waits for the reader's click instead of running while the page loads.
2. Beside the like button, a **share button** lets the reader share the article by email. That button needs an inline arrow function so it can pass the custom text `'Email'` when clicked while reading the card's `title` prop.
3. The **story card itself** is clickable so clicking the card opens the full article. Both buttons sit physically inside that clickable card. Without `e.stopPropagation`, clicking the like button will also open the card!
4. Below the card, a **comment form** lets the reader type a comment and submit it. Because a form reloads the browser tab on submit by default, the `onSubmit` handler must call `e.preventDefault` to keep the page from reloading.

### Four Principles of Responding to Events

**PRINCIPLES:** Responding to user events in React rests on four rules that connect JavaScript functions, JSX curly braces, and browser DOM behavior:
1. **Principle 1: Pass a Function Reference to an Event Prop**: Write event props in `camelCase`, such as `onClick`, and pass the function itself without parentheses. Writing parentheses after the function name calls the function immediately during render and hands `undefined` to `onClick`.
2. **Principle 2: Wrap Custom Arguments in an Inline Arrow Function**: Declare event handlers inside the component so they can read its props directly. Whenever a handler call needs a custom argument on click, wrap that call in an inline arrow function so it waits for the click.
3. **Principle 3: Stop Upward Bubbling with `e.stopPropagation`**: Clicks and most other DOM events bubble upward from an inner child element to every parent element around it. When a button sits inside a clickable card, accept the event object `e` and call `e.stopPropagation` so clicking the button does not trigger the card too.
4. **Principle 4: Stop the Browser Reload on Form Submit with `e.preventDefault`**: Submitting a `<form>` triggers the browser's built-in page reload reflex. Attach your handler to `onSubmit` on the form tag and call `e.preventDefault` so the browser does not reload the tab.

Here is the overview of all four principles before we build each step:

| # | Principle | The Mistake to Avoid | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Function Reference on `camelCase` Props** | Calling a handler with parentheses inside `onClick` runs it on page load and leaves the button dead; lowercase `onclick` is ignored. | Pass the function reference without parentheses to a `camelCase` prop such as `onClick`. |
| **Principle 2** | **Inline Arrow Wrapper for Arguments** | Calling a handler with an argument bare inside `onClick` fires during render instead of waiting for a click. | Define handlers inside the component to read props in scope, and wrap custom arguments in an inline arrow function. |
| **Principle 3** | **Stopping Bubbling with `e.stopPropagation`** | Clicking a button inside a clickable card fires both the button handler and the parent card handler. | Accept the `SyntheticEvent` parameter `e` in the child handler and call `e.stopPropagation`. |
| **Principle 4** | **Preventing Reload with `e.preventDefault`** | Submitting a `<form>` without cancelling the browser default reloads the whole page and clears client memory. | Attach the handler to `<form>` with `onSubmit` and call `e.preventDefault` inside the handler. |

## 1. Principle 1: Pass a Function Reference to an Event Prop

### Referencing a function vs. calling a function

Compare these two button tags side by side:

```jsx title="Passing sayHello by name vs. calling sayHello with parentheses"
<button ~onClick={sayHello}~>Say hello</button> // 1. No parentheses: hands the sayHello function to React for later
<button ~onClick={sayHello()}~>Say hello</button> // 2. **WRONG:** with parentheses: calls sayHello right now during render!
```

**Those two lines differ by only two tiny parentheses at the end of `sayHello`. They look almost the same on the tag, but they are NOT the same thing at all!**

To see why, look at what happens in plain JavaScript when you write a function name without parentheses versus with parentheses:

```js title="Plain JavaScript: referencing a function vs. calling a function"
function sayHello() {
  console.log('Hello');
}

const ~fn = sayHello~; // 1. No parentheses: stores the function itself in fn; logs nothing yet
const ~result = sayHello()~; // 2. With parentheses: runs sayHello right now and stores its return value, undefined!
```

**Where did the parentheses go on the first line at the bottom?**
1. **Without parentheses**, `sayHello` is a **function reference**. It points to the function in memory without running it, so you can hand that function to React to call later.
2. **With parentheses**, JavaScript **calls** `sayHello` right now. It prints the greeting immediately, and when a function has no `return` statement, the call evaluates to `undefined`.

```tree caption="What a function name without parentheses gives you vs. what a function name with parentheses gives you."
Two ways to write a function name in JavaScript
- +Without parentheses [`sayHello`] | A **function reference** pointing to the function in memory | Does **not** run yet; hands the function to React to call on click
- !With parentheses [`sayHello` followed by parentheses] | A **function call** that runs **right now** | Runs immediately during render and evaluates to **`undefined`**
```

### HTML `onclick` strings vs. React `onClick` props

Why do so many developers accidentally write parentheses inside `onClick`? Because in plain HTML, you write event attributes as a quoted text string with parentheses:

```html title="Plain HTML: onclick holds a quoted string of code"
<button ~onclick="handleLike()"~>Like</button> <!-- In HTML, quotes hold text that the browser saves for later -->
```

In plain HTML, two things are different from React:
1. The attribute name `onclick` is written in **all lowercase letters**.
2. The value sits inside **quotes**, so the browser does not run it while loading the page. Instead, the browser keeps that string of text and runs it only when the user clicks.

In React JSX, you do not pass a string of code in quotes. If you pass a quoted string to `onClick` in JSX, React prints an error in the Console and never runs your code:

```jsx title="Mistake: passing a quoted string to onClick in JSX"
<button ~onClick="handleLike()"~>Like</button> // **WRONG:** passes a text string instead of a function!
```

When that line renders, Chrome's Console panel logs this error:

```devconsole
x Expected `onClick` listener to be a function, instead got a value of `string` type.
```

Instead of quotes, React uses **curly braces `{ }`** to pass a real JavaScript function. And remember our rule for curly braces in JSX: whatever you write inside `{ }` is evaluated **immediately while React renders the component**.

```tree caption="How plain HTML onclick attributes differ from React JSX onClick props."
Plain HTML `onclick` vs. React JSX `onClick`
- !Plain HTML attribute [Lowercase `onclick` with a quoted string] | Holds a **quoted text string** | Browser wraps the string and waits for a click
- !Quoted string in JSX [Quoted string inside `onClick`] | ~Do **NOT** pass a string to `onClick` in JSX | Logs **`Expected onClick listener to be a function`**
- +React JSX prop [`onClick={handleLike}`] | +**DO** use `camelCase` `onClick` with a **function reference** | Evaluates `{handleLike}` to your function and calls it **when clicked**
```

### Mistake 1: Calling the handler with parentheses inside `onClick`

Let us build the first step of our news reader page and see what happens when a developer puts parentheses after the handler name inside `onClick`.

First, in our card file, the developer writes the like handler inside the card component and puts parentheses after its name on the like button:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard() {
  function handleLike() {
    console.log('Liked: New Park Opens Today');
  }

  return (
    <article className="card">
      <h3>New Park Opens Today</h3>
      <p>The park on Main Street opens at noon.</p>
      <button className="like-btn" ~onClick={handleLike()}~>Like</button> {/* **WRONG:** calls handleLike() during render and passes undefined! */}
    </article>
  );
}
```

Next, our main file imports and renders the card:

```jsx title="src/App.jsx" startLine="1"
~import ArticleCard from './components/ArticleCard.jsx';~ // Imports ArticleCard into App.jsx

export default function App() {
  return (
    <main>
      <h1>City Reader</h1>
      <ArticleCard />
    </main>
  );
}
```

Watch what happens in order when you save those two files:
1. **While the page loads**: React calls `ArticleCard` to render the card. Inside the curly braces, the parentheses call `handleLike` immediately. The Console logs the like message before you even touch the mouse!
2. **What `onClick` receives**: Because our like handler has no `return` statement, calling it returns `undefined`. So the button actually receives `onClick={undefined}`.
3. **When you click the like button**: Because `onClick` is `undefined`, clicking the button does nothing at all, and zero new messages appear in the Console.

### Passing the function reference to `onClick`

To make the like button wait for the user's click, we write `onClick` on the button and pass `handleLike` **without parentheses**:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard() {
  function ~handleLike~() { // 1. Declare the event handler inside the component
    console.log('Liked: New Park Opens Today');
  }

  return (
    <article className="card">
      <h3>New Park Opens Today</h3>
      <p>The park on Main Street opens at noon.</p>
      <button className="like-btn" ~onClick={handleLike}~>Like</button> {/* 2. Pass handleLike by name without parentheses */}
    </article>
  );
}
```

Notice the naming habit React teams follow here. The JSX prop on the built-in tag starts with **`on`** followed by the event name, such as `onClick`. Meanwhile, the function you declare inside your component starts with **`handle`** followed by the action, such as `handleLike`.

Now save the file and open Chrome's **Elements panel** to inspect the `<button>` in the live browser DOM:


Look closely at the `<button>` in the Elements panel above. There is **no `onclick` attribute** on that button in the browser DOM! If React did not write `onclick` onto the button, how does clicking the button run `handleLike`?

React uses **root event delegation** instead of putting `onclick` on every DOM element:
1. When React mounts your app into the `#root` container, it attaches one shared click listener at `#root`.
2. While rendering the card, React remembers in memory that this button owns the `handleLike` function.
3. When you click the like button, the click rises to `#root`, and React calls `handleLike`!

## 2. Principle 2: Wrap Custom Arguments in an Inline Arrow Function

### Why parentheses inside an arrow wrapper do NOT run during render

Once you know Principle 1, a natural question comes up right away. *"If putting parentheses after a function name calls it during render, how do I pass a custom argument like `'Email'` when the button is clicked?"*

Look at these three buttons side by side:

```jsx title="Direct reference vs. arrow wrapper vs. bare call with an argument"
<button ~onClick={sayHello}~>Say hello</button> // 1. No arguments needed: pass sayHello directly
<button ~onClick={() => sayHello()}~>Say hello</button> // 2. Arrow wrapper: also waits for a click!
<button ~onClick={() => greet('John')}~>Greet John</button> // 3. Arrow wrapper with argument: passes 'John' on click!
```

Let us clear up two questions that every learner asks when looking at those three lines:
1. **First, compare Button 1 and Button 2**: When no custom argument is needed, Button 1 passes `sayHello` directly, while Button 2 wraps `sayHello` inside an arrow function. **Yes, when clicked, those two buttons do the exact same thing!** Both hand a function to React, and both run `sayHello` only when the user clicks.
2. **Second, look at Button 3**: Wait a moment! In Principle 1 we saw that putting parentheses after a function name runs the function immediately during render. Why are parentheses suddenly allowed after `greet` when an arrow function sits in front of it? **Calling `greet` bare and wrapping the call inside an arrow function with `=>` may both contain parentheses, but they are NOT the same thing!**

Think of the arrow `=>` at the front as **sealing the call inside an envelope**:
- **Without an arrow function in front**, calling `greet` bare inside `{ }` opens and runs the function immediately while React builds the page. Then it hands `undefined` to `onClick`.
- **With an arrow function in front**, JavaScript creates a **brand-new wrapper function** and hands that wrapper function to React **without running the code inside it**. The call to `greet` stays sealed inside the wrapper function until the user clicks the button!

```tree caption="Why a bare call with arguments runs during render, while wrapping it in an arrow function waits for the click."
Three ways to write `onClick` when functions are involved
- +1. Direct function reference [`onClick={sayHello}`] | Best when the handler needs **no custom arguments** | Hands `sayHello` directly to React
- !2. Bare call with an argument [`onClick` with bare `greet` call] | ~Do **NOT** call the function bare inside `{ }` | Runs `greet` **immediately during render** and passes `undefined` to `onClick`
- +3. Inline arrow function [`onClick` with `=>` before `greet`] | +**DO** wrap the call in an arrow function when passing an argument | Hands the **arrow wrapper function** to React; calls `greet` **only on click**
```

### How a handler reads props from scope

Look at how plain JavaScript handles two things: reading variables from an outer function, and storing an arrow function in a variable:

```js title="Plain JavaScript: reading outer parameters and creating an arrow wrapper"
function makeLogger(title) {
  function greet(platform) {
    console.log('Shared ' + ~title~ + ' by ' + platform); // 1. Reads title directly from makeLogger's parameters
  }

  const ~bad = greet('Email')~; // 2. Runs greet right now and stores undefined in bad!
  const ~good = () => greet('Email')~; // 3. Creates a wrapper function; greet does NOT run until good() is called!
}
```

Two plain JavaScript rules are at work here:
1. **Lexical scope**: Because `greet` is declared inside the outer function, it can read the outer `title` parameter directly.
2. **Arrow wrapper**: Assigning the bare call to `bad` runs the inner function right away and stores `undefined`. Putting an arrow function with `=>` in front stores a wrapper function in `good` that waits until someone calls it.

### Mistake: Calling a handler with an argument directly in `onClick`

Now let us grow our news reader project. First, in our main file, we pass `title` and `summary` as props into the card component:

```jsx title="src/App.jsx" startLine="1"
import ArticleCard from './components/ArticleCard.jsx';

export default function App() {
  return (
    <main>
      <h1>City Reader</h1>
      <ArticleCard
        ~title="New Park Opens Today"~ // 1. Passes title prop to ArticleCard
        ~summary="The park on Main Street opens at noon."~ // 2. Passes summary prop to ArticleCard
      />
    </main>
  );
}
```

Inside the card file, we unpack `title` and `summary` in the parameter list and update our like handler to read the card title. We also add a second button for sharing by email that calls `handleShare` with `'Email'`.

Look at what happens when a developer calls `handleShare` directly inside `onClick` without an arrow wrapper:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ ~title, summary~ }) { // 1. Unpacks title and summary from props
  function handleLike() {
    console.log('Liked: ' + title);
  }

  function handleShare(platform) {
    console.log('Shared ' + title + ' by ' + platform);
  }

  return (
    <article className="card">
      <h3>{title}</h3>
      <p>{summary}</p>
      <button className="like-btn" onClick={handleLike}>Like</button>
      <button className="share-btn" ~onClick={handleShare('Email')}~>Share by Email</button> {/* **WRONG:** calls handleShare('Email') during render! */}
    </article>
  );

```

When you save the file, the exact same bug from Principle 1 happens on the second button:
1. While React renders the card on page load, JavaScript evaluates `handleShare` with `'Email'` immediately and logs the share message in the Console before anyone clicks.
2. Because our share handler has no return value, the share button receives `onClick={undefined}`.
3. When the reader clicks the share button, nothing happens.

### Wrapping the call in an inline arrow function

To pass `'Email'` only when the reader clicks the share button, we put an inline arrow function in front of the call inside `onClick`:

```jsx title="src/components/ArticleCard.jsx" startLine="1"
export default function ArticleCard({ title, summary }) {
  function handleLike() {
    console.log('Liked: ' + ~title~); // 1. Reads title directly from ArticleCard's props
  }

  function handleShare(platform) {
    console.log('Shared ' + ~title~ + ' by ' + platform); // 2. Reads title from props and platform from the argument
  }

  return (
    <article className="card">
      <h3>{title}</h3>
      <p>{summary}</p>
      <button className="like-btn" ~onClick={handleLike}~>Like</button> {/* No custom argument: pass handleLike directly */}
      <button className="share-btn" ~onClick={() => handleShare('Email')}~>Share by Email</button> {/* Custom argument: wrap in () => */}
    </article>
  );
}
```

Look closely at both handlers in the code above. Neither button passes `title` inside `onClick`, yet both functions print the park heading when clicked! Where did `title` come from?

Because `handleLike` and `handleShare` sit **inside** the card component, both functions can read the component's props directly:
1. Our main component renders the card with the park heading in `title`.
2. Inside the card component, `title` is already in scope for every function declared inside it.

## 3. Principle 3: Stop Upward Bubbling with `e.stopPropagation`

### Why clicking an inner button also triggers its parent box

Suppose you have an outer box with `onClick={openBox}` and a button inside that box with `onClick={likeItem}`:

```jsx title="A clickable button sitting inside a clickable parent box"
<div ~onClick={openBox}~> {/* Outer parent box has its own onClick handler */}
  <button ~onClick={likeItem}~>Like</button> {/* Inner child button has its own onClick handler */}
</div>
```

Look at those two tags. **In your code, `onClick={openBox}` and `onClick={likeItem}` sit on two separate tags. It looks like clicking the like button should only run `likeItem`, but in the browser DOM it is NOT isolated like that!**

Why do **both** handlers run when you click the button?
- Physically, the `<button>` sits **inside** the `<div>` box. When you click the button, you are also clicking inside the outer box!
- In the browser DOM, an event starts on the innermost tag you clicked and runs its handler first. Then it **bubbles upward** through every parent tag around it, like an air bubble rising through water.
- To pop that bubble at the child button so it never reaches the parent box, you take the event object `e` and call `e.stopPropagation` inside the child's handler:

```jsx title="Calling e.stopPropagation inside the child button's handler"
<div onClick={openBox}>
  <button ~onClick={(e) => { e.stopPropagation(); likeItem(); }}~>Like</button> {/* Stops the click from bubbling up to openBox */}
</div>
```

```tree caption="What happens when you click an inner <button> inside a clickable parent <article> without and with e.stopPropagation."
Clicking an inner `<button>` inside a clickable `<article>`
- !Without `e.stopPropagation` [Default DOM bubbling] | 1st runs the `<button>` handler, then **bubbles up** to `<article>` | Fires **both** the button handler and the parent card handler!
- +With `e.stopPropagation` [Called inside the child handler] | Runs the `<button>` handler and **stops the upward climb** | Parent `<article>` handler **does not run**
```

### How React passes the `SyntheticEvent` object `e`

Before we add `e.stopPropagation` to our card, look at how `e` arrives in a handler function:

```jsx title="Receiving the event object e in an event handler"
function handleLike(~e~) { // 1. React passes the SyntheticEvent object e as the first argument automatically!
  ~e.stopPropagation()~; // 2. Stops the click from bubbling up to parent elements
  console.log(e.target.tagName, e.currentTarget.tagName);
}

<button ~onClick={handleLike}~>Like</button> // Notice: we did NOT write any argument on the tag!
```

Look closely at the button tag above. We did not pass any argument in JSX, yet `handleLike` received `e` as its first parameter! Who supplied `e`?

Whenever an event happens in the browser, React wraps the browser's native event into a cross-browser object called a **`SyntheticEvent`**. React passes that `SyntheticEvent` object `e` automatically as the **first argument** to your event handler, giving you standard methods and properties across every browser:
- **`e.stopPropagation`**: Stops the event from bubbling up to parent elements.
- **`e.preventDefault`**: Stops the browser's built-in default action for that tag, which we will use in Principle 4.
- **`e.target`**, *The Clicked Element*: The inner DOM element where the click actually started, such as `'BUTTON'`.
- **`e.currentTarget`**, *The Listening Element*: The DOM element whose event handler is currently running, such as `'ARTICLE'` when a bubbled click reaches the card.
- **`e.nativeEvent`**: The underlying native browser `MouseEvent` object if you ever need it.

```tree caption="How to tell e.target and e.currentTarget apart when a click on <button> bubbles up to <article>."
Two element properties on the `SyntheticEvent` object `e`
- +`e.target` [*The Clicked Element*] | Points to the inner tag **where the click started** | Inside `<article>`'s handler, `e.target.tagName` is **`'BUTTON'`**
- +`e.currentTarget` [*The Listening Element*] | Points to the tag **whose handler is currently running** | Inside `<article>`'s handler, `e.currentTarget.tagName` is **`'ARTICLE'`**
```

### How capture phase events work with `onClickCapture`

In interviews, senior engineers often ask: *"What if a parent component needs to log every click inside it, even when a child button calls `e.stopPropagation`?"*

Every DOM event actually travels through **three phases** in order:
1. **The Capture phase, traveling downward**: The event starts at the root and travels **down** the tree toward the clicked element. By default, normal `onClick` handlers do not run here. To run a handler during this downward trip, add **`Capture`** to the end of the event prop name, such as **`onClickCapture`**.
2. **The Target phase**: The event reaches the clicked element itself.
3. **The Bubbling phase, traveling upward**: The event rises back **up** from the clicked element toward the root. Normal `onClick` handlers run during this upward trip.

Look at what happens when we add `onClickCapture` to the parent card while our like button still calls `e.stopPropagation`:

```jsx title="Using onClickCapture on the parent <article> to catch a click on the way down"
<article
  className="card"
  ~onClickCapture={() => console.log('Capture: card')}~ // 1. Runs FIRST on the way down, before the button!
  onClick={handleOpenCard}
>
  <button className="like-btn" ~onClick={handleLike}~>Like</button> {/* 2. Runs SECOND and calls e.stopPropagation() */}
</article>
```

When you click the like button, the Console logs `'Capture: card'` first on the way down, and then logs the like message at the button. Because our like handler calls `e.stopPropagation`, the upward bubbling trip stops at the button and the parent card handler never runs!

One more interview detail to remember: **almost every event in React bubbles upward, except `onScroll`**. Scrolling a container fires `onScroll` only on that specific scrolled element and never bubbles up to parent elements.

```tree dir=right caption="The three phases of a DOM click event from top-down capture to the clicked target to bottom-up bubbling."
Three phases of a click event in React
- +1. Capture phase, top-down [`onClickCapture` on `<article>`] | Travels **downward** from the root to the clicked child | Runs **before** the child's `onClick`
- +2. Target phase [`onClick` on `<button>`] | Reaches the **clicked `<button>`** itself | Calling `e.stopPropagation` here cancels the upward climb
- +3. Bubbling phase, bottom-up [`onClick` on `<article>`] | Rises **upward** from the child to parent tags | Skipped when the child called `e.stopPropagation`
```

> [!PRINCIPLE]
> **Principle 3: Event Propagation: Call `e.stopPropagation` When a Child Click Should Not Trigger Its Parent**
>
> *When a button sits inside a clickable parent container, accept the event object `e` and call `e.stopPropagation` so the event does not bubble up to the parent handler.*
>
> In the browser, clicking a button inside a card physically clicks the card behind it too. First React runs the button's `onClick` handler, and then the click bubbles upward to the parent card and runs the card's `onClick` handler right after it. Calling `e.stopPropagation` inside the button handler pops that bubble right at the button so the parent card never fires.
>
> **DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> function handleLike(~e~) { // 1. Receive the SyntheticEvent object e
>   ~e.stopPropagation()~; // 2. Stop the click from bubbling up to the parent <article>
>   console.log('Liked: ' + title);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx title="src/components/ArticleCard.jsx"
> function ~handleLike~() { // **WRONG:** without e.stopPropagation(), clicking Like also fires the parent <article>'s onClick!
>   console.log('Liked: ' + title);
> }
> ```

## 4. Principle 4: Stop the Browser Reload on Form Submit with `e.preventDefault`

### `e.stopPropagation` vs. `e.preventDefault`

Compare these two `<form>` tags when the user clicks the submit button:

```jsx title="Submitting a <form> without e.preventDefault vs. with e.preventDefault"
<form ~onSubmit={handleSubmit}~> {/* 1. If handleSubmit does NOT call e.preventDefault(), the browser reloads the whole page! */}
  <button type="submit">Post</button>
</form>

<form ~onSubmit={(e) => { e.preventDefault(); handleSubmit(); }}~> {/* 2. e.preventDefault() stops the browser reload! */}
  <button type="submit">Post</button>
</form>
```

Why does a `<form>` reload the entire browser tab when you submit it?
- In plain HTML from the early web, a `<form>` packs up its inputs, adds them to the URL bar, and reloads the whole page from the server.
- In a modern React app, a full-page reload destroys your running JavaScript memory and resets the entire screen.
- Calling **`e.preventDefault`** inside `onSubmit` tells the browser: *"Cancel your built-in reload reflex; my React handler will take care of this submission."*

Be careful not to confuse `e.stopPropagation` from Principle 3 with `e.preventDefault` here. **Both methods sit on `e` and both sound like "stop this event", so developers mix them up constantly, but they are NOT the same thing!**
- Calling `e.stopPropagation` inside `onSubmit` does **not** stop the browser from reloading the page; it only stops the submit event from climbing up to parent tags in the tree.
- Calling `e.preventDefault` stops the **browser's built-in default action** for that HTML element. That cancels a `<form>` page reload on submit or stops an `<a>` link from navigating to another URL:

```tree caption="The exact difference between e.stopPropagation and e.preventDefault in React interviews and daily debugging."
`e.stopPropagation` vs. `e.preventDefault`
- +`e.stopPropagation` [Controls **tree bubbling**] | Stops the event from **climbing up to parent tags** in your component tree | Does **NOT** stop a `<form>` from reloading the page
- +`e.preventDefault` [Controls **browser default action**] | Stops the browser's **built-in reflex** for that tag, like `<form>` reload or `<a>` navigation | Does **NOT** stop the event from bubbling to parent tags
```

```tree dir=right caption="What happens on each of the four user interactions in our finished City Reader app."
- +3. Click card heading [`onClick={handleOpenCard}` on `<article>`] | Bubbles from `<h3>` to `<article>` and logs the open message | Opens the card when clicking outside the buttons
- +4. Submit `CommentForm` [`onSubmit={handleCommentSubmit}`] | Calls `e.preventDefault` and logs **`'Comment posted'`** | URL stays at `localhost:5173` with **0 page reloads**
```

| Aspect | The Plain HTML or Beginner Habit | The React Rule |
| :--- | :--- | :--- |
| **Event attribute name** | Lowercase `onclick` or `onsubmit`, which React ignores with a Console error | `camelCase` prop names such as `onClick` and `onSubmit` |
| **Passing the handler** | Calling the function inside `onClick`, which runs during render and passes `undefined` | Pass the function reference without parentheses, such as `onClick={handleLike}` |
| **Passing custom arguments** | Calling `handleShare` with `'Email'` bare inside `onClick`, which fires on page load | Wrap the call inside an inline arrow function so it waits for the click |
| **Nested clickable elements** | Letting a child button click bubble up and trigger a parent card's `onClick` handler | Accept `e` in the child handler and call `e.stopPropagation` |
| **Form submission** | Letting `<form>` reload the whole browser tab or calling `e.stopPropagation` | Attach `onSubmit` to `<form>` and call `e.preventDefault` inside the handler |

## For the Interview

> **The Interview Question:** How do you respond to user events like clicks and form submissions, and how do you control propagation and default browser actions?

### How to Answer Clearly in 30 Seconds

"In React, we respond to user events by passing a function to a `camelCase` event prop such as `onClick` or `onSubmit` on a JSX element. Four rules govern how event handlers work:
1. **Pass a function reference, never a function call**: We write `onClick={handleLike}` without parentheses. Adding parentheses inside the curly braces executes the function immediately while React renders the component and passes its return value, `undefined`, to `onClick`.
2. **Use an inline arrow function for custom arguments**: Event handlers declared inside a component can read its props directly through JavaScript lexical scope. When we also need to pass a custom argument on click, we wrap the call in an inline arrow function so React receives an uncalled function.
3. **Control propagation with `e.stopPropagation`**: React passes a cross-browser `SyntheticEvent` object `e` as the first argument to every handler. Because DOM events bubble upward from a child `<button>` to a parent `<article>`, calling `e.stopPropagation` in the child handler keeps parent handlers from firing. If a parent must intercept an event on the way down before child handlers run, we use a capture prop such as `onClickCapture`.
4. **Prevent default browser actions with `e.preventDefault`**: Submitting a `<form>` triggers the browser's built-in full-page reload. Attaching `onSubmit` to `<form>` and calling `e.preventDefault` cancels that native browser reload, which is completely separate from `e.stopPropagation`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does `onClick={handleLike}` work without parentheses, while wrapping a call in an inline arrow function with `=>` works even though the inner call has parentheses?"**
   Whatever sits directly inside `onClick={...}` is evaluated while React renders the component, and it must evaluate to a function. When you write `handleLike` without parentheses, it evaluates to the `handleLike` function itself. If you write a bare call with parentheses at the top level of `{ }`, JavaScript runs that function during render and hands `undefined` to `onClick`. When you put an arrow function with `=>` in front of `handleShare`, the expression inside `{ }` evaluates to the outer arrow function without running its body. The `handleShare` call inside that arrow body runs only when the user clicks.
2. **"What is the difference between `e.stopPropagation` and `e.preventDefault`?"**
   **They control two completely different things.** `e.stopPropagation` stops an event from bubbling upward through parent elements in your component tree, such as stopping a button click from triggering `onClick` on the parent `<article>`. It does **not** stop a `<form>` from reloading the page. `e.preventDefault` cancels the browser's built-in default behavior for an HTML element, such as stopping a `<form>` from reloading the page or stopping an `<a>` link from navigating. It does **not** stop the event from bubbling up to parent elements.
3. **"Inside a bubbled click handler, what is the difference between `e.target` and `e.currentTarget`, and how does `onClickCapture` differ from `onClick`?"**
   `e.target`, *The Clicked Element*, is the inner DOM element where the click actually started, such as the `<button>`. `e.currentTarget`, *The Listening Element*, is the DOM element whose event handler is currently running, such as the outer `<article>` card when the click bubbles up to it. Normal `onClick` handlers run during the upward bubbling phase from child to parent. Adding `Capture` to the prop name, `onClickCapture`, runs the handler during the downward capture phase from parent to child, before the child's `onClick` runs.

```tree dir=right caption="Interview comparison: controlling upward tree bubbling with e.stopPropagation vs. cancelling native browser behavior with e.preventDefault."
- +`e.preventDefault` [`<form>` with `onSubmit` or `<a href>`] | Cancels the **browser's built-in default action** for that element | Does **not** stop the event from bubbling up to parent handlers
```
