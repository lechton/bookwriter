# Brief 2026-11-07 13: Comparisons as two forms of one thing, a contemplation for future skills

This brief changes no skill. It records an idea of the owner, to inform the skills when they are next written.

## The problem it answers

The openings of Lecture 21 felt staged. The same faults keep coming back when a skill forces a shape on a lesson:
- a false dilemma, two things set up as enemies when they are not;
- a crisis that does not exist, such as a plain JavaScript bug no developer writes;
- examples that are not realistic, such as a light that draws On or Off;
- an angle that means nothing;
- nitpicking over examples;
- text that reads as cringy because it was written to obey a rule.

Not every lesson has a subtle distinction at its heart. A comparison with plain JavaScript is not needed every time, and when it is forced it is boring. The start of a lecture is there to give the key idea the reader must remember, what is at stake, and the place where readers usually go wrong. Back to the basics.

## The idea: name what the two share, then the one difference

Two things are often separated in a brute way, as opposites. It is wiser to explain them as two forms of one thing: first what they have in common, then the one thing that differs.

| Instead of | Say | The pair |
| --- | --- | --- |
| Dark is the opposite of light. | Dark is what happens to a room without light. | Light vs. absence of light |
| A CEO is the opposite of a politician. | A CEO is a leader who is not elected, as a politician is. | Corporate leader vs. elected leader |
| A click changes the situation, not the page. | A click changes the page indirectly, by changing the state. | Changing the DOM directly vs. changing it through state |

This keeps what the reader already knows, names the real difference exactly, and leaves no room for a villain, a staged bug, or a forced verdict.

## The key idea of Lecture 21

> In React, a click never changes the page directly. It changes state, and React changes the page to match.

Heading: *Changing the DOM directly vs. changing it through state*. Both ways end with a new page. In plain JavaScript, the handler changes the page itself. In React, the handler changes state, and React changes the page.

## The same pattern in Lectures 22 to 24

| Lecture | What both are | The one difference | Heading |
| --- | --- | --- | --- |
| 22, which values belong in state | values the component shows on the page | React remembers one between renders; the other is calculated again on every render from it | A value React remembers vs. a value calculated from it |
| 23, how a child tells its parent | props the parent passes down to the child | one carries a value down; the other carries a function down, which the child calls to send a request up | Passing a value down vs. passing a function down |
| 24, how two siblings share one value | state a component keeps with `useState` | it lives in the child that uses it, or in the closest parent of both | State in the child that uses it vs. state in the parent of both |

Lecture 22 has a second pair inside a principle: a prop copied into state vs. a prop read directly. Both start from the parent's value; one stops at the first value, and the other keeps following the parent.

## Lectures 21 to 24 are one family

All four answer one question: where a changing value lives, and who changes it.
- 21: how it changes, through state, not directly.
- 22: what is kept, only what cannot be calculated.
- 23: who changes it, its owner, when a child asks.
- 24: where it lives, in the closest parent of everyone who needs it.

Each opening can name this thread in one sentence, without teaching an earlier lesson again.

## For future skills

- Before an opening is written, name the key idea of the lesson. A comparison belongs there only when the reader really confuses two things.
- When there is a comparison, name what the two share first, then the one difference.
- The owner's three pairs above are the examples to teach it with.
