# Lecture 42: How useActionState Remembers the Last Answer and the Pending Flag
> INTERVIEW QUESTION | ❱ CORE | How does useActionState manage a form's submitted state and pending flag?

## How a Form Remembers the Answer of Its Last Submit

### A newsletter box that answers after every click

Picture the bottom of a news site. A small box reads "Get our weekly news". It has one email box and one Sign up button. Every reader has seen one.

The user types `john@example.com` and clicks Sign up. Two things happen, one after the other:
1. For about one second, the button reads "Signing up..." and the user cannot click it.
2. Then one line appears under the button: "Thanks! john@example.com is signed up."

::: row caption="The newsletter box when the page opens, while the sign-up runs, and after the answer comes back."
::: col title="When the page opens" tag="no line yet"
```page size=mini
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
```
:::
::: col title="While the sign-up runs" tag="Signing up..."
```page size=mini
heading: Get our weekly news
form:
  field: Email | john@example.com
  submit: Signing up... | | disabled
```
:::
::: col title="After the answer comes back" tag="one line" tone=good
```page size=mini
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
line: Thanks! john@example.com is signed up. | good
```
:::
:::

Later, the user signs up with the same email again. This time the line under the button reads "This email is already signed up".

So after every submit, the form must remember two things:
1. **What the last submit answered**: the thanks line or the error line.
2. **Whether a submit is still running**: so the button can read "Signing up..." and refuse a second click.

A plain form action already receives the form data and can send the email to the server (as seen in Lesson 41). But React ignores what that action returns, and our component has no variable that says the action is still running.

React gives both with one Hook: **`useActionState`**. It keeps what the action returned last time as state. It also gives a pending flag, `isPending`, that React turns on when the action starts and off when the answer is on the screen. The name says what it holds: the state that comes out of an action.

### What is at stake

Without `useActionState`, we keep both values by hand. One `useState` holds the message, another holds the pending flag, and our code sets each one at the right moment. One forgotten line, and the user sees it:
1. The button stays on "Signing up..." forever, and the user cannot try again.
2. Or the thanks line of the last email stays on the screen, while the new email was refused.

Readers usually go wrong in one place. They keep the shape of a plain form action, which takes the form data as its only parameter (as seen in Lesson 41). With `useActionState`, React hands the action one more value first, so the form data moves to second place. Principle 2 shows both shapes.

### Three ways to show the answer and the pending state

Developers really choose between three ways for this same job:
1. **`useState` for the message and `useState` for the pending flag**, both set by hand in a submit handler (as seen in Lessons 33 and 40). It fits any React version, and code that does not run as a form action.
2. **`useState` with `useTransition`**, which a later lesson teaches. It fits when several actions must run at the same time. The `useActionState` page of the React docs says: "If you want to perform Actions in parallel, use `useState` and `useTransition` directly."
3. **`useActionState`**. It fits when the screen shows the result of the last submit, and the submits run one after the other.

This lesson teaches the third way, and Principle 4 puts it next to the first.

### Our newsletter project

Our project has three files. `src/main.jsx` mounts the default export of `src/App.jsx`, unchanged (as seen in Lesson 7). `src/App.jsx` holds the `Newsletter` component and its `signup` action. `src/api.js` pretends to be the server:

```files title="newsletter: File Explorer" caption="How the files of our newsletter box sit inside src/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports the default export of `./App.jsx` and mounts it, unchanged
  App.jsx | form | Holds the `signup` action and exports `Newsletter` as default
  api.js | fake server | Exports `signUp`, which answers after one second
```

The fake server is given, not taught. It waits one second, then answers with an error text when the email is already on its list, or with `null` when the sign-up went through:

```js title="src/api.js"
const emails = [];

export async function signUp(email) {
  await new Promise(resolve => setTimeout(resolve, 1000));
  if (emails.includes(email)) {
    return 'This email is already signed up';
  }
  emails.push(email);
  return null;
}
```

The one-second wait exists only so we can see the pending state on the screen.

### Four Principles of useActionState

**PRINCIPLES:** `useActionState` keeps the answer of the last submit as state and tells us whether a submit is still running. Four rules come up in daily debugging and in interviews:
1. **Principle 1: Three Values**: the Hook returns the current state, an action to give to the form, and `isPending`. The form must get that returned action, not our `signup`.
2. **Principle 2: The Second Parameter**: React calls our action with the previous state first and the form data second, so the action must keep both places.
3. **Principle 3: The Returned Text**: whatever our action returns becomes the new state, so a known problem, such as an email already signed up, is returned, not thrown.
4. **Principle 4: The Pending Flag**: `isPending` is `true` while the action runs, so the button can read "Signing up..." with no `useState` and no line to forget.

Here is the complete map of those four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **useActionState Gives the Form Three Values** | Putting `signup` itself on the form runs it, but the line under the button never appears, with zero errors in the Console. | Destructure the three values and give the form the returned action, `signupAction`. |
| **Principle 2** | **formData Moves to the Second Parameter** | Keeping the shape of a plain form action, `signup(formData)`, reads the email from `null` and stops the page with a `TypeError`. | Write the action as `signup(previousState, formData)`, even when it does not use `previousState`. |
| **Principle 3** | **The Returned Text Becomes the Message Line** | Throwing a known error, such as an email already signed up, never reaches the line; it goes to the nearest Error Boundary. | Return known errors as state; throw only for failures you did not expect. |
| **Principle 4** | **isPending Turns the Button into Signing up...** | A hand-written pending flag stays `true` forever when the request throws before `setIsPending(false)` runs. | Read `isPending` from `useActionState`; React turns it on and off around the action. |

## 1. Principle 1: useActionState Gives the Form Three Values

### One line, three values

Here is the whole Hook in one line, and the one place where its second value goes:

```jsx title="useActionState in one line"
const [message, signupAction, isPending] = ~useActionState(signup, null)~; // Returns three values, in this order

<form action={~signupAction~}> {/* The form gets the action that useActionState returned */}
```

`useActionState` takes two arguments:
1. **`signup`**: our action, the function that does the work when the user submits.
2. **`null`**: the initial state, what `message` holds before the first submit.

It returns three values, and array destructuring gives each one a name of our choice, in order (as seen in Lesson 12):
1. **`message`**: the current state. On the first render, it equals the initial state, `null`. After each submit, it equals what `signup` returned.
2. **`signupAction`**: the action to give to the form. The React docs call it the action dispatcher, `dispatchAction`. React builds it around our `signup`.
3. **`isPending`**: `true` while a submit is still running. Principle 4 uses it.

### It looks like useState, but it is NOT the same thing

The first line looks a lot like a `useState` line. Put the two side by side:

```jsx title="With useState and with useActionState"
const [message, ~setMessage~] = useState(null); // Two values: our code calls setMessage with the new message
const [message, ~signupAction~, isPending] = useActionState(signup, null); // Three values: the form calls signupAction
```

It may look the same, but it is NOT the same thing! Both lines give a `message` that starts as `null`. The difference is in the second value:
- **With `useState`**, the second value is a setter. Our code calls it and hands it the new message.
- **With `useActionState`**, the second value is an action. Our code never hands it a message. The form calls it, React calls our `signup`, and React stores what `signup` returns as the new `message`.

```tree caption="The second value of useState is a setter our code calls; the second value of useActionState is an action the form calls."
Where the new `message` comes from
- +With `useState` [`setMessage`] | Our code **calls the setter** with the new message | Two values: **`message`** and **`setMessage`**
- +With `useActionState` [`signupAction`] | The **form calls the action**, and React stores **what `signup` returns** | Three values: **`message`**, **`signupAction`**, and **`isPending`**
```

### The first newsletter box

Now we build the newsletter box. For this first step, `signup` ignores the email and returns one fixed text:

```jsx title="src/App.jsx"
import { useActionState } from 'react';

function signup() {
  return 'Thanks, you are signed up!';
}

export default function Newsletter() {
  const [message, signupAction, isPending] = ~useActionState~(signup, null); // message starts as null

  return (
    <form action={~signupAction~}> {/* The form gets signupAction, not signup */}
      <h2>Get our weekly news</h2>
      <label>
        Email <input name="email" />
      </label>
      <button>Sign up</button>
      {~message &&~ <p>{message}</p>} {/* No line while message is null */}
    </form>
  );
}
```

When the page opens, `message` is `null`, so there is no line under the button:

```page caption="The newsletter box on the first render: message is null, so no line appears."
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
```

The user types `john@example.com` and clicks Sign up. The line appears:

```page caption="The newsletter box after the user clicks Sign up: the text that signup returned is on the screen."
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
line: Thanks, you are signed up! | good
```

React also empties the email box after the submit. That is the automatic reset of a form after its action, and a later lesson covers it.

### React calls signup, not our code

Our code never calls `signup`, and it never calls a setter. Yet the line changed. Here is what React does after the user clicks Sign up:
1. The form calls the action on its `action` prop, `signupAction`.
2. `signupAction` calls our `signup`.
3. `signup` returns `'Thanks, you are signed up!'`.
4. React stores that text as the new `message` and renders `Newsletter` again. This time, `message` is not `null`, so the line appears.

### Mistake: putting signup itself on the form

A developer may write `signup` itself on the form, as with a plain form action (as seen in Lesson 41):

```jsx title="src/App.jsx" startLine="11"
    <form action={~signup~}> {/* **WRONG:** signup runs, but React throws away what it returns */}
```

The user clicks Sign up, `signup` runs, and nothing appears under the button. The Console stays quiet. Only the action that `useActionState` returned stores the answer in `message`. Our own `signup` knows nothing about `message`.

### Mistake: calling the action while the component renders

Another developer wants the form to run once when the page opens, and calls the action in the component body:

```jsx title="src/App.jsx" startLine="7"
export default function Newsletter() {
  const [message, signupAction, isPending] = useActionState(signup, null);
  ~signupAction()~; // **WRONG:** runs on every render, and each call asks for another render
```

Calling the action asks React for a new state, and a new state means a new render. That render calls the action again. React stops and shows the error `Cannot update action state while rendering.` Call the action only in answer to the user, here when the user submits the form.

> [!PRINCIPLE]
> **Principle 1: Three Values: The Form Gets the Action That useActionState Returns**
>
> *Call `useActionState(signup, null)` at the top of the component, destructure the current state, the action, and `isPending`, and give the form the returned action.*
>
> A form needs to show what its last submit answered. `useActionState` keeps that answer as state: on the first render it holds the initial state, and after each submit it holds what our action returned. React stores the answer only when the form calls the action that `useActionState` returned. Our own `signup` on the form runs, but its answer goes nowhere.
>
> **DO THIS:**
> ```jsx
> const [message, signupAction, isPending] = useActionState(signup, null);
>
> <form action={~signupAction~}> {/* React stores what signup returns in message */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [message, signupAction, isPending] = useActionState(signup, null);
>
> <form action={~signup~}> {/* **WRONG:** signup runs, but message stays null and no line appears */}
> ```

## 2. Principle 2: formData Moves to the Second Parameter

### The same line inside two parameter lists

A plain form action is called with one value, the form data (as seen in Lesson 41). Now `signup` must read the email the user typed. Look at two ways to write its parameters:

```jsx title="With signup(formData) and with signup(previousState, formData)"
function signup(~formData~) { // The plain form action shape: one parameter
  const email = formData.get('email');
}

function signup(~previousState, formData~) { // The useActionState shape: two parameters
  const email = formData.get('email');
}
```

It may look the same, but it is NOT the same thing! Both read the email with the same `formData.get('email')`. But who calls the action decides what arrives in each place:
- **A plain form action** is called with the form data first.
- **An action given to `useActionState`** is called through `signupAction`, and `signupAction` puts one more value first: the previous state. The form data moves to second place.

### What previousState holds

`previousState` is what `signup` returned last time:
1. On the first submit, it is the initial state, our `null`.
2. On every later submit, it is the value `signup` returned on the submit before.

That shape should look familiar. A reducer receives the current state first and returns the next state (as seen in Lesson 27). The React docs call the function we give to `useActionState` a `reducerAction` for that reason: it turns the previous state into a new state, like the reducer of `useReducer`. Unlike a reducer, it may send a request to a server, because React calls it as an Action.

Our `signup` does not need `previousState` yet. It must still keep the first place, because React fills the places in order.

### Mistake: keeping the one-parameter shape

A developer had a working plain form action. To show a message, they wrap the action in `useActionState`, but they leave the parameter list as it was:

```jsx title="src/App.jsx" startLine="3"
function signup(~formData~) { // **WRONG:** React puts the previous state here, so formData holds null
  const email = formData.get('email');
  return `Thanks! ${email} is signed up.`;
}
```

**The page opens fine, but the first submit fails before the email reaches the line.** Here is what happens:
1. The user types `john@example.com` and clicks Sign up.
2. React calls `signup` with `null` first and the form data second.
3. The parameter named `formData` holds `null`.
4. `formData.get('email')` fails, because `null` has no `get`.

The thanks line never appears. The Console shows the error:

```devconsole
x Uncaught TypeError: Cannot read properties of null (reading 'get')
```

An Error Boundary is a component that catches an error thrown by the components inside it and shows something else in their place. Our page has none, so React removes the newsletter box from the page. A later lesson teaches Error Boundaries.

### The fix: add previousState in first place

Add `previousState` as the first parameter. Now `formData` holds the form data, and the email reaches the line:

```jsx title="src/App.jsx" startLine="3"
function signup(~previousState, formData~) { // React fills previousState first, then formData
  const email = formData.get('email');
  return `Thanks! ${email} is signed up.`;
}
```

```page caption="The newsletter box after the user signs up with john@example.com: the line now names the email."
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
line: Thanks! john@example.com is signed up. | good
```

```tree caption="What arrives in each parameter when useActionState calls the action on a submit."
What React passes to `signup` through `signupAction`
- !With one parameter, `formData` [`formData`] | The only parameter receives the **previous state**, `null` on the first submit | `formData.get` fails with a **`TypeError`**
- +With two parameters, `previousState` and `formData` [`previousState` `formData`] | First place: the **previous state**; second place: the **form data** | `formData.get` reads **`john@example.com`**
```

> [!PRINCIPLE]
> **Principle 2: Two Parameters: The Previous State First, the Form Data Second**
>
> *Write an action given to `useActionState` as `signup(previousState, formData)`, even when it does not use `previousState`.*
>
> A plain form action receives the form data first. Through `useActionState`, React adds the previous state in front of it: the initial state on the first submit, and what the action returned on every later one. An action that keeps the old one-parameter shape reads the email from the previous state, and the submit fails.
>
> **DO THIS:**
> ```jsx
> function signup(~previousState, formData~) { // formData holds the form data
>   const email = formData.get('email');
>   return `Thanks! ${email} is signed up.`;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function signup(~formData~) { // **WRONG:** formData holds the previous state, null on the first submit
>   const email = formData.get('email');
>   return `Thanks! ${email} is signed up.`;
> }
> ```

## 3. Principle 3: The Returned Text Becomes the Message Line

### Two returns, two lines on the screen

The line under the button changes only one way: through what the action returns. One action can return two different texts:

```jsx title="One action, two returns"
async function signup(previousState, formData) {
  const error = await signUp(formData.get('email'));
  if (error) {
    ~return error;~ // The error text becomes message
  }
  ~return 'Thanks!';~ // The thanks text becomes message
}
```

Whichever text `signup` returns, React stores it as `message`, and the line shows it.

### Calling the fake server

Now `signup` sends the email to our fake server. It becomes `async`, waits for `signUp`, and returns the error text when there is one:

```jsx title="src/App.jsx" startLine="1"
import { useActionState } from 'react';
import { signUp } from './api.js';

async function signup(previousState, formData) {
  const email = formData.get('email');
  const error = await ~signUp(email)~; // null when it went through, the error text otherwise
  if (error) {
    return error;
  }
  return `Thanks! ${email} is signed up.`;
}
```

### The line changes with no setter

**Two submits with the same email give two different lines, and no line of our code sets `message`.** Here is what happens, in order:
1. The user types `john@example.com` and clicks Sign up.
2. React calls `signup` with `null` and the form data.
3. `signUp` waits one second and returns `null`, because the email is new. So `signup` returns `'Thanks! john@example.com is signed up.'`.
4. React stores that text as `message` and renders `Newsletter` again. The thanks line appears.
5. The user types `john@example.com` again and clicks Sign up. This time, `previousState` holds the thanks text.
6. `signUp` finds the email on its list and returns `'This email is already signed up'`. `signup` returns that text, and the line changes to it.

```page caption="The newsletter box after the first sign-up with john@example.com."
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
line: Thanks! john@example.com is signed up. | good
```

```page caption="The same box after the user signs up with john@example.com a second time."
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
line: This email is already signed up | bad
```

### Return a known error, do not throw it

"Already signed up" is a failure, so a developer may want to throw it, as they would inside a `try` block. Put the two side by side:

```jsx title="With return error and with throw new Error"
if (error) {
  ~return error;~ // The text becomes message: the line shows it
}

if (error) {
  ~throw new Error(error);~ // **WRONG:** the text never reaches message
}
```

It may look the same, but it is NOT the same thing! Both stop `signup` at the same moment, with the same text. But only a returned value becomes state:
- **With `return error`**, React stores the text as `message`, and the user reads "This email is already signed up" under the button.
- **With `throw new Error(error)`**, React cancels any other submit still waiting its turn and passes the error to the nearest Error Boundary. With no Error Boundary on the page, the newsletter box disappears, as it did in Principle 2.

The React docs draw the line between the two. A known error, such as an email already signed up, is part of the answer: return it and show it. An error you did not expect, such as a bug in the code, is thrown.

> [!PRINCIPLE]
> **Principle 3: Returned State: What the Action Returns Becomes the Line**
>
> *Return every answer the user should read, including known errors such as an email already signed up; throw only for failures you did not expect.*
>
> `useActionState` has no setter for our code to call. The only way to change the line under the button is to return a new value from the action: React stores it as the new state and renders the form again. A thrown error does not become state. React passes it to the nearest Error Boundary, and the user never reads it under the button.
>
> **DO THIS:**
> ```jsx
> async function signup(previousState, formData) {
>   const error = await signUp(formData.get('email'));
>   if (error) {
>     ~return error;~ // The line shows "This email is already signed up"
>   }
>   return 'Thanks!';
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> async function signup(previousState, formData) {
>   const error = await signUp(formData.get('email'));
>   if (error) {
>     ~throw new Error(error);~ // **WRONG:** the text never reaches the line, and the newsletter box disappears
>   }
>   return 'Thanks!';
> }
> ```

## 4. Principle 4: isPending Turns the Button into Signing up...

### The Signing up... button in three lines

The third value of `useActionState` drives the button:

```jsx title="A button driven by isPending"
<button disabled={~isPending~}> {/* Refuses clicks while a sign-up runs */}
  {~isPending ?~ 'Signing up...' : 'Sign up'} {/* The text while it runs, and the text after */}
</button>
```

`isPending` is `true` from the moment the user submits until React shows the state that the action returned. `disabled` is the HTML attribute that stops a button from being clicked.

### The pending flag by hand and isPending

Before `useActionState`, developers wrote the pending flag themselves, in a submit handler (as seen in Lesson 33). Here is the same newsletter box with the message and the flag written by hand:

```jsx title="With setIsPending by hand"
const [message, setMessage] = useState(null);
const [isPending, setIsPending] = useState(false);

async function handleSubmit(e) {
  e.preventDefault();
  const email = new FormData(e.target).get('email');
  ~setIsPending(true);~ // Our code turns the flag on
  const error = await signUp(email);
  setMessage(error ? error : `Thanks! ${email} is signed up.`);
  ~setIsPending(false);~ // Our code must remember to turn it off
}
```

And here is the same flag with `useActionState`:

```jsx title="With isPending from useActionState"
const [message, signupAction, ~isPending~] = useActionState(signup, null); // React turns isPending on and off
```

Yes, it is the exact same thing on the screen! For one submit, both buttons read "Signing up..." for one second, then "Sign up" again. The difference is in the code. With `useActionState`, there is no `setIsPending(true)` and no `setIsPending(false)`. React already knows when the action starts and when its answer is on the screen, so it sets `isPending` itself.

### Mistake: the flag that never turns off

The hand-written version has one line that is easy to lose:
1. Our handler calls `setIsPending(true)`.
2. The request throws, for example when the network fails.
3. The line `setIsPending(false)` never runs.
4. The button stays on "Signing up..." and disabled. The user cannot try again.

The usual fix is a `try` and `finally` block around the request. With `useActionState`, there is no such line to forget.

### The old line stays until the new answer arrives

The finished button goes into `src/App.jsx`:

```jsx title="src/App.jsx" startLine="22"
      <button disabled={isPending}>
        {isPending ? 'Signing up...' : 'Sign up'}
      </button>
```

Now watch a second sign-up, with a new email. **While the request runs, the button reads Signing up..., but the line still shows the old answer.** Here is why:
1. The line from the last submit reads "Thanks! john@example.com is signed up."
2. The user types `mia@example.com` and clicks Sign up.
3. `isPending` becomes `true`, so the button reads "Signing up..." and cannot be clicked. `message` has not changed, because `signup` has not returned yet, so the old thanks line stays.
4. One second later, `signup` returns. In the same render, React shows the new line and the button reads "Sign up" again.

```page caption="During the one-second wait: the button reads Signing up..., and the line still shows the last answer."
heading: Get our weekly news
form:
  field: Email | mia@example.com
  submit: Signing up... | | disabled
line: Thanks! john@example.com is signed up.
```

```page caption="After the wait: the new line replaces the old one, and the button reads Sign up again."
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
line: Thanks! mia@example.com is signed up. | good
```

```tree caption="Two ways to show the pending state: a flag our code sets by hand, or isPending from useActionState."
Who turns the pending flag on and off
- !With `setIsPending` by hand [`setIsPending`] | Our code turns the flag **on before** the request and **off after** it | If the request throws, the button **stays on Signing up... forever**
- +With `isPending` from `useActionState` [`isPending`] | **React** turns the flag on when the action starts and off when its answer is shown | **No line to forget**: no `useState`, no `setIsPending`, no `finally`
```

> [!PRINCIPLE]
> **Principle 4: isPending: React Turns the Pending Flag On and Off**
>
> *Read `isPending` from `useActionState` to disable the button and change its text while the action runs.*
>
> A button that reads Signing up... needs a flag that is `true` while the request runs and `false` again when the answer is shown. Written by hand, that flag needs two setter calls, and one thrown request skips the second call and freezes the button. `useActionState` gives the flag as its third value, and React sets it, because React already knows when the action starts and ends.
>
> **DO THIS:**
> ```jsx
> <button disabled={~isPending~}> {/* React sets isPending around the action */}
>   {isPending ? 'Signing up...' : 'Sign up'}
> </button>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> setIsPending(true);
> const error = await signUp(email);
> ~setIsPending(false);~ // **WRONG:** skipped when signUp throws, so the button stays on Signing up...
> ```

## Putting All Four Principles Together

### The complete project

Here is the finished `src/App.jsx`. The action keeps both parameters, returns every answer the user should read, and the button reads `isPending`:

```jsx title="src/App.jsx"
import { useActionState } from 'react';
import { signUp } from './api.js';

async function signup(~previousState, formData~) { // 2. React passes the previous state first, the form data second
  const email = formData.get('email');
  const error = await signUp(email);
  if (error) {
    ~return error;~ // 3. A known error is returned and becomes message
  }
  return `Thanks! ${email} is signed up.`;
}

export default function Newsletter() {
  const [message, signupAction, isPending] = ~useActionState~(signup, null); // 1. Three values: state, action, flag

  return (
    <form action={signupAction}>
      <h2>Get our weekly news</h2>
      <label>
        Email <input name="email" />
      </label>
      <button disabled={~isPending~}> {/* 4. React turns isPending on and off around the action */}
        {isPending ? 'Signing up...' : 'Sign up'}
      </button>
      {message && <p>{message}</p>}
    </form>
  );
}
```

And here is the fake server it calls, unchanged:

```js title="src/api.js"
const emails = [];

export async function signUp(email) {
  await new Promise(resolve => setTimeout(resolve, 1000));
  if (emails.includes(email)) {
    return 'This email is already signed up';
  }
  emails.push(email);
  return null;
}
```

### What happens on one submit, in order

When the page opens, React renders `Newsletter` once. `message` is `null` and `isPending` is `false`. Then each submit follows the same four steps:

```tree dir=right caption="What happens, in order, from the click on Sign up to the new line under the button."
One submit of the newsletter box
- +1. The user clicks Sign up [`signupAction`] | The form calls **`signupAction`** with the form data | `isPending` becomes **true**: the button reads **Signing up...**
- +2. `signupAction` calls `signup` [`previousState` `formData`] | React passes the **previous state** first and the **form data** second | `signup` waits **one second** for `signUp`
- +3. `signup` returns a text [`return`] | React stores it as the new **`message`** | The line under the button shows **the new answer**
- +4. The same render [`isPending`] | `isPending` becomes **false** | The button reads **Sign up** again
```

| Aspect | With `useState` by hand | With `useActionState` |
| :--- | :--- | :--- |
| **The values** | Two `useState` calls, one for the message and one for the pending flag | One Hook returns the message, the action, and `isPending` |
| **The form** | An `onSubmit` handler that reads the form data itself | The form gets `signupAction` on its `action` prop |
| **The message** | Our code calls `setMessage` with the new text | React stores what `signup` returns |
| **A known error** | Our code calls `setMessage` with the error text | `signup` returns the error text |
| **The pending flag** | `setIsPending(true)` before the request and `setIsPending(false)` after it, often in `finally` | React sets `isPending` around the action |

## For the Interview

> **The Interview Question:** How does useActionState manage a form's submitted state and pending flag?

### How to Answer Clearly in 30 Seconds

"`useActionState` takes an action and an initial state, and returns three values: the current state, an action to pass to the form, and `isPending`. When the user submits, React calls my action with two arguments: the previous state first and the form data second. Whatever my action returns becomes the new state, so the screen shows the answer of the last submit with no setter in my code. That is why I return known errors, such as an email already signed up, instead of throwing them. `isPending` is `true` while the action runs, so I can disable the button without a second `useState` and without a `finally` block that turns the flag off."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does the action receive the previous state as its first argument?"**
   Because `useActionState` works like a reducer: the action turns the previous state into the next one. On the first submit, the previous state is the initial state; after that, it is what the action returned last time. The difference from `useReducer` is that a reducer must be pure, while the action may send a request to a server. The form data therefore moves to the second place, and an action written in the one-parameter form shape reads the form data from the wrong place.
2. **"What happens if the user submits the form twice before the first answer comes back?"**
   On our form, this cannot happen, because the button is disabled while `isPending` is `true`. Without `disabled`, React puts the second submit in a queue and runs the submits one after the other, so each call receives the result of the one before. The React docs say this is intentional in the design of `useActionState`. `isPending` stays `true` until every queued submit has finished, and then React renders once with the final state. When several actions must run at the same time, the docs recommend `useState` with `useTransition` instead.
3. **"How do you show a server error with useActionState?"**
   A known error, such as an email already signed up, is part of the answer, so the action returns it as state, and the component renders it like any other message. An error the code did not expect is thrown. A thrown error does not become state: React cancels every submit still waiting in the queue and passes the error to the nearest Error Boundary.
