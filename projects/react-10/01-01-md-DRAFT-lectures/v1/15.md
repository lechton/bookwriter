## Why State Keeps Its Old Value Inside the Handler That Sets It

### Why calling `setCount` is NOT the same thing as `count = count + 1`

Before we build a project, look at this small counter component with a click handler that updates the count and logs it on the very next line:

```jsx title="Setting count and logging count on the next line"
import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);

  function handleClick() {
    ~setCount(count + 1);~ // 1. Asks React for a new render with 1; does NOT change count here
    ~console.log(count);~ // 2. Still prints 0 in the Console!
  }

  return <button onClick={handleClick}>Count: {count}</button>;
}
```

When you click the button once, two things happen at the same time: the button on the screen changes to `Count: 1`, while Chrome's Console panel prints `0`!

Two pieces of confusion hit almost every developer the first time they see this:
- **First, calling `setCount` with `count + 1` looks like the plain JavaScript assignment `count = count + 1`, but it is NOT the same thing!** In plain JavaScript, writing `count = count + 1` changes the variable `count` on that very line. In React, calling `setCount` does not touch the variable `count` inside the code that is already running. Instead, it stores `1` inside React and asks React to call `Counter` again for a new render.
- **Second, seeing `0` in the Console makes it look as if `setCount` failed, but it did NOT fail!** Look at the button on the page: it now says `Count: 1`. The setter worked for the next render. The `console.log` line printed `0` because that line was still running inside the old render where `count` was `0`.

To feel why React works this way, unlock the two everyday pictures behind the React documentation:
- **What does "snapshot" mean?** In everyday life, a **snapshot** is a quick photograph taken at one moment in time. If someone walks across the room after you press the camera shutter, the people inside the photograph do not move. In React, each render is one snapshot of your component taken with the state value of that moment.
- **Where does state actually live?** State does not live inside your function. It lives inside React itself, outside your component, as if sitting on a shelf. When React calls your component, it takes the current value off the shelf and hands your function a fixed value for that render. Calling `setCount` puts `1` on React's shelf for the next render, and leaves the `0` in your running function untouched:

```tree caption="Why plain JavaScript assignment changes a variable right away, while a React state setter asks for the next render."
Plain JavaScript assignment vs. React state setter
- !Plain JavaScript assignment [`count = count + 1`] | Changes the variable `count` **on that exact line** | The next line reads the **new value `1`** right away
- +React state setter [`setCount` with `count + 1`] | Puts `1` on React's shelf for the **next render** and leaves `count` untouched | The next line still reads this render's **snapshot value `0`**, while the button updates to **`Count: 1`** on the next render
```

### Why reading a state variable right after setting it calls the wrong customer on a queue screen

Now look at how this exact surprise causes a visible bug on a real page. Picture the number screen above a bakery counter. The screen shows the current ticket number, `Now serving: 12`, an announcement line underneath it, and a button labeled `Next customer`.

When a clerk clicks `Next customer`, the click handler needs to do two jobs at once: move the serving number up to `13`, and update the announcement line underneath to say `Number 13, please come to the counter`.

If the developer calls `setNumber` with `number + 1` and then builds the announcement line using `number`, the top line on the screen moves to `Now serving: 13`, while the announcement line underneath says `Number 12, please come to the counter`! Customer 12, who already bought their bread, walks back to the counter, while customer 13 keeps waiting.

Whenever an event handler needs a state value after calling its setter, you have two ways to write that code:
1. **Read the state variable `number` again**: Because `number` is frozen at this render's snapshot value, reading `number` after calling `setNumber` always gives the old number from before the click.
2. **Calculate the next value once in a local constant such as `nextNumber`**: By storing `const nextNumber = number + 1` first, you can pass `nextNumber` to `setNumber` and to every other line in the handler that needs the new number right away.

```tree caption="The two ways a click handler can read a value after calling a state setter."
Two ways to use a value inside the handler that sets it
- !Way 1: Read the state variable `number` after `setNumber` [Call `setNumber` then read `number`] | `number` still holds **this render's old snapshot value `12`** | Screen shows **`Now serving: 13`**, while the announcement calls **`Number 12`**
- +Way 2: Calculate `nextNumber` once in a constant [`const nextNumber = number + 1`] | Pass `nextNumber` to `setNumber` **and** to the announcement line | Both the screen and the announcement use the **new number `13`**
```

### What happens to local constants, closures, and timers across function calls

Before we walk through our bakery queue page, let us connect five facts we already know from earlier lessons with three plain JavaScript building blocks:
- **Event handler references**: Writing `onClick={handleNext}` on a button hands the `handleNext` function to React without calling it, so React calls it only when the user clicks.
- **`useState` pairs**: Declaring `const [number, setNumber]` with `useState` stores the value inside React outside the component, and returns a two-item array unpacked by position: the current state value first, and the setter function second.
- **Trigger, Render, and Commit**: Calling a setter triggers a render, and React calls the component again and commits the new DOM nodes only after the event handler finishes. That means the browser DOM also still holds the old number while the handler is running.
- **`<StrictMode>` in development**: Wrapping `<App />` in `<StrictMode>` inside `src/main.jsx` calls each component function twice during rendering to check purity, and calls an event handler only once per click.
- **Joining text with `+`**: Writing `'Number ' + number` joins the text string and the number into one string.

Now add three plain JavaScript rules that govern every render:
- **Each function call creates its own local `const` variable**: When a component declares `const [number, setNumber]` with `useState`, the keyword `const` means the name `number` cannot be pointed at a new value inside that call. When React calls the component again on the next render, JavaScript creates a brand-new `const` named `number` for that new call.
- **What a "closure" means in everyday words**: In everyday English, a **closure** means something closed in and sealed, like an envelope. When you define an inner function inside an outer function, the inner function closes over the variables of that specific outer call and seals them inside itself. Even when the inner function runs later, it keeps reading the values from the call that created it.
- **Running code later with `setTimeout`**: In plain JavaScript, `setTimeout` takes a function and a wait time in milliseconds, where `1000` milliseconds is one second. Passing `3000` tells the browser to wait three seconds and then run that function.

### Four Principles of State as a Snapshot

**PRINCIPLES:** Every time React calls your component function, it hands that call a fixed snapshot of the state. Four practical rules explain how that snapshot behaves during a click and how to work with it cleanly:
1. **Principle 1: The Setter Only Updates the Next Render**: Calling a state setter stores the next value inside React and requests a new render. It never changes the state variable inside the event handler that is currently running, so reading that variable on the next line still gives the old value even though the screen updates afterward.
2. **Principle 2: Every Render Creates Its Own Snapshot and Handlers**: Each render call creates its own state constant and its own event handler functions. Because each handler closes over the state constant of the render that created it, reading the state variable before the setter or after the setter produces the exact same value.
3. **Principle 3: Delayed Code Still Reads Its Click's Snapshot**: A state variable never changes within a render, even inside asynchronous code such as a three-second timer started by a click. The timer function stays sealed to the snapshot of the click that started it, which keeps overlapping clicks from scrambling each other's work.
4. **Principle 4: Calculate the Next Value Once in a Local Variable**: When an event handler needs the new state value right away for another setter, a log, or a timer, calculate the next value once in a local constant and pass that constant everywhere instead of reading the state variable again.

Here is the complete overview of all four principles before we build and test each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **The Setter Asks for the Next Render** | Developers call a setter, log the state variable on the next line, see the old value, and think the setter failed or is broken. | A state setter only updates what `useState` returns on the next render; it never mutates the variable in the running handler. |
| **Principle 2** | **Each Render Has Its Own Snapshot** | Moving a read line above the setter changes nothing, and interviewers ask how JavaScript closures tie each handler to one render. | Every render gets its own fixed state constant, and every handler created in that render closes over that render's value. |
| **Principle 3** | **Delayed Code Keeps the Click's Snapshot** | A timer that fires seconds after the screen updated still reads the old click's state value, surprising developers who expected waiting to help. | Even delayed functions such as `setTimeout` read the snapshot of the render whose handler started them. |
| **Principle 4** | **Calculate the Next Value Once** | Reading the state variable again after setting it leaves announcements, logs, and network calls one step behind the screen. | Save the next value in a local constant before calling the setter, and pass that constant to every line that needs the new value. |

## 1. Principle 1: The Setter Asks for the Next Render; It Does Not Change the Variable in the Running Code

### Why calling `setCount` does not change `count` on the next line

Compare what happens when you update a number in plain JavaScript with what happens when you call a state setter in React.

First, look at plain JavaScript with a `let` variable:

```js title="Plain JavaScript: reassigning a variable in place"
let count = 0;
~count = count + 1;~ // 1. Reassigns the variable count in place right now
~console.log(count);~ // 2. Prints 1 immediately
```

Now compare that with calling the state setter inside a React click handler:

```jsx title="React: calling the state setter inside an event handler"
const [count, setCount] = useState(0);

function handleClick() {
  ~setCount(count + 1);~ // 1. Stores 1 in React for the next render; leaves count at 0 here
  ~console.log(count);~ // 2. Prints 0 because count in this render is still 0!
}
```

**Look at those two snippets side by side. Calling `setCount` with `count + 1` and writing `count = count + 1` may look like they do the same job, but they are NOT the same thing!**
- **In plain JavaScript**, `count = count + 1` reaches directly into the variable `count` and replaces `0` with `1` on that line.
- **In React**, `count` is a `const` holding `0` for this render. Calling `setCount` is like handing an order ticket to a restaurant kitchen: handing the ticket to the kitchen does not change the plate already sitting on your table right now. The new dish arrives only when the kitchen brings out the next serving, which is the next render!
- **And why is there no contradiction between the Console printing `0` and the button showing `Count: 1`?** Because `console.log` ran during the old render while `0` was still on the table, and `Count: 1` appeared when React ran the component again for the next render.

```tree caption="Handing a new value to a React state setter is like handing an order ticket to the kitchen: the new value arrives on the next render, not on the current plate."
What happens on the line after `count = count + 1` vs. calling `setCount`
- !Plain JavaScript [`count = count + 1`] | Mutates `count` **in place on that line** | `console.log` on the next line reads **`1`**
- +React setter [`setCount` with `count + 1`] | Stores `1` in React and **asks for the next render** | `console.log` on the next line still reads **`0`**, and the screen updates to **`Count: 1`** after the handler finishes
```

### How React gives `13` to the next render while `number` stays `12` in this click

Look closely at `handleNext` in `QueueBoard.jsx`. Not a single line inside `handleNext` assigns `13` to `number`; the function only calls `setNumber` with `number + 1`. So how did `Now serving: 13` appear on the screen, and why did `number` stay `12` on the lines right below `setNumber`?

Here is what JavaScript and React do in chronological order:
1. **First render**: React calls `QueueBoard`. `useState` returns `12`, and JavaScript creates the constant `number` with the value `12` for this call.
2. **The click runs `handleNext`**: The clerk clicks `Next customer`. Inside `handleNext`, calling `setNumber` with `12 + 1` stores `13` on React's shelf and asks React for a new render.
3. **The rest of `handleNext` finishes with `12`**: The next line calls `setAnnouncement` using `number`. Because `number` in this first render is still the constant `12`, it builds `'Number 12, please come to the counter'`, and `console.log` prints `12` once in the Console. Even if you read the browser DOM on this line, it would also still say `Now serving: 12`, because React has not committed the new render yet.
4. **Second render**: Now that `handleNext` has finished, React calls `QueueBoard` a second time. In this second call, `useState` returns the new value `13` from the shelf into a brand-new constant `number`, and returns `'Number 12, please come to the counter'` into a brand-new constant `announcement`.
5. **Commit to the screen**: React updates the browser DOM so the page displays `Now serving: 13` above `Number 12, please come to the counter`.

```tree dir=right caption="The five chronological steps from the first render with 12 to the second render with 13."
What happens when the clerk clicks `Next customer` once
- +1. Render 1 [`useState` returns `12`] | JavaScript creates constant **`number = 12`** for this call
- +2. `setNumber` runs [`setNumber` receives `13`] | Stores **`13` inside React** and requests a new render
- !3. Next lines in `handleNext` [`setAnnouncement` and `console.log`] | `number` in Render 1 is **still `12`**, so it stores **`"Number 12..."`** and logs **`12`**
- +4. Render 2 [`QueueBoard` runs again] | `useState` returns **`13`** into a **new constant `number`**
- !5. Screen updates [Browser DOM commit] | Top line shows **`Now serving: 13`**, while announcement shows **`Number 12, please come to the counter`**
```

### Why changing `const` to `let` or assigning to `number` directly does not work

When developers notice that `number` stayed `12` after calling `setNumber`, they sometimes wonder if the keyword `const` is what kept `number` at `12`.

What if you change `const` to `let` in the state declaration and still call the setter? Look at what happens:

```jsx title="src/components/QueueBoard.jsx" startLine="4"
  ~let~ [number, setNumber] = useState(12); // Changing const to let changes nothing!
  const [announcement, setAnnouncement] = useState(
    'Welcome! Please take a number.'
  );

  function handleNext() {
    setNumber(number + 1);
    ~console.log(number);~ // Still logs 12! setNumber cannot reassign a local variable
  }
```

Changing `const` to `let` changes nothing at all! The Console still logs `12`, because `setNumber` is a function call. In JavaScript, passing `number + 1` to a function hands over the value `13`; the function `setNumber` has no way to reach back into `QueueBoard` and reassign your local variable `number`.

What if a developer tries to force the state variable to change by reassigning it directly inside the handler?

```jsx title="src/components/QueueBoard.jsx" startLine="9"
  function handleNext() {
    ~number = number + 1;~ // **WRONG:** cannot reassign a const state variable!
    setNumber(number);
  }
```

The moment you save that file, Vite stops the build and shows an error overlay reporting an illegal reassignment of a `const` variable, and in the browser console reassigning a `const` throws `Uncaught TypeError: Assignment to constant variable.`:

```overlay caption="Vite stops the build when code tries to reassign the const state variable number directly."
message: [ILLEGAL_REASSIGNMENT] Unexpected re-assignment of const variable
file: src/components/QueueBoard.jsx:10:4
```

Keeping state variables declared with `const` protects you from thinking you can mutate state in place.

> [!PRINCIPLE]
> **Principle 1: The Setter Asks for the Next Render; It Does Not Change the Variable in the Running Code**
>
> *Calling a state setter stores the next value inside React for the next render; it never changes the state variable in the code that is already running.*
>
> When React renders your component, `useState` gives that render a fixed constant. Calling `setNumber` puts the next number on React's shelf and schedules a new render, leaving `number` at `12` for every remaining line of the running handler. That is why logging `number` on the line after `setNumber` prints `12` even though the screen updates to `13` a moment later.
>
> **DO THIS:**
> ```jsx
> function handleNext() {
>   ~setNumber(number + 1);~ // Stores 13 in React for the next render; number stays 12 in this call
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleNext() {
>   setNumber(number + 1);
>   ~setAnnouncement('Number ' + number + ', please come to the counter');~ // **WRONG:** expects number to be 13 here, but it is still 12!
> }
> ```

## 2. Principle 2: Every Render Gets Its Own Fixed Value, and Every Handler Keeps the Value of the Render That Made It

### Why reading state before or after the setter is the exact same thing, while handlers from two renders are NOT the same thing

After seeing Principle 1, two new questions immediately come up:
1. Does reading `number` **before** calling `setNumber` give a different result from reading `number` **after** calling `setNumber`?
2. Since `function handleNext` is written only once in our file, how can clicking the button a second time read `13` instead of `12`?

Let us answer the first question right away by logging the state variable twice in the same handler, once above the setter and once below it:

```jsx title="Reading number before the setter vs. after the setter in the same handler"
function handleNext() {
  ~console.log(number);~ // 1. Before setNumber: logs 12
  setNumber(number + 1);
  ~console.log(number);~ // 2. After setNumber: ALSO logs 12!
}
```

**Yes, reading `number` before the setter and reading `number` after the setter are the exact same thing!** Both lines sit inside the exact same render snapshot, where `number` is `12` from the first line of `handleNext` to the last.

Now look at the second question in plain JavaScript. Suppose we write an outer function named `render` that receives `number`, creates an inner function named `handleNext`, and returns it:

```js title="Plain JavaScript: each call to render creates its own handleNext closure"
function render(number) {
  function handleNext() {
    console.log(number);
  }
  return handleNext;
}

const first = render(12);
const second = render(13);

~first();~  // 1. Prints 12: first closed over number = 12
~second();~ // 2. Prints 13: second closed over number = 13
~first();~  // 3. Still prints 12!
```

**Look at `first` and `second`. They come from the exact same `function handleNext` lines and both log `number`, so they look like the same function, but they are NOT the same thing!**
- When `render` ran with `12`, JavaScript created a local variable `number` holding `12`, and created the `first` function, which closed over that `12` like sealing `12` inside an envelope.
- When `render` ran with `13`, JavaScript created a second local variable `number` holding `13`, and created a second function `second`, which sealed `13` inside its own envelope.
- Even after the second call to `render` has finished, calling `first` again still opens the first envelope and prints `12`!

The React documentation gives you a simple way to read any render's code, called the **substitution method**: imagine taking a snapshot photo of the component for one render and replacing every word `number` inside that render with its literal number, such as `12` in the first render and `13` in the second render:

```tree caption="Each call to the outer function creates a separate inner handler sealed with that call's snapshot value."
Why `first` and `second` are NOT the same function in memory
- +First call [`const first = render` with `12`] | Creates `handleNext` sealed with **`number = 12`** | Every line inside `first` reads **`12`**, before or after any other call
- +Second call [`const second = render` with `13`] | Creates a **new `handleNext`** sealed with **`number = 13`** | Every line inside `second` reads **`13`**
```

### Mistake: Moving `setAnnouncement` above `setNumber`

In our bakery queue project, suppose the developer thinks `setNumber` somehow delayed or blocked the line after it, and moves the announcement update and the log line **above** the setter call:

```jsx title="src/components/QueueBoard.jsx" startLine="9"
  function handleNext() {
    ~setAnnouncement('Number ' + number + ', please come to the counter');~ // **WRONG:** moved above setNumber, and still reads 12!
    ~console.log(number);~ // **WRONG:** still logs 12 on the first click!
    setNumber(number + 1);
  }
```

Watch what happens when we test this in the browser:
1. The clerk clicks `Next customer` once. The screen still shows `Now serving: 13` and `Number 12, please come to the counter`, and the Console still logs `12`. Moving the read above the setter made zero difference!
2. Next, the developer clicks `Next customer` twice in a row with no pause between clicks, wondering if the second click will get stuck reading the old `12` too.
3. After the two back-to-back clicks, the screen shows `Now serving: 14` and `Number 13, please come to the counter`, and the Console logs `12` followed by `13`. The second click already had `13`!

### How JavaScript creates a fresh `handleNext` for each render and how the substitution method traces it

Look at `QueueBoard.jsx`. The file defines `function handleNext` only once. How did the first click read `12` on every line, while the second click read `13` on every line?

Follow what JavaScript and React do across the two renders using the substitution method:
1. **Render 1 with `12`**: React calls `QueueBoard`. `useState` gives `number` as `12`. JavaScript creates a `handleNext` function for Render 1 that closes over `12`. If we substitute `12` for `number`, Render 1's handler builds `'Number ' + 12 + ', please come to the counter'` and passes `12 + 1` to `setNumber`.
2. **React attaches Render 1's `handleNext` to the button**: Until someone clicks, the button holds Render 1's handler.
3. **Click 1 runs Render 1's `handleNext`**: Whether `setAnnouncement` sits above `setNumber` or below `setNumber`, `number` inside this function is `12`. It logs `12`, sets the announcement to `'Number 12, please come to the counter'`, and asks React to render with `13`.
4. **Render 2 with `13`**: React calls `QueueBoard` again. `useState` gives a new constant `number` as `13`. JavaScript creates a brand-new `handleNext` function for Render 2 that closes over `13`. Substituting `13` for `number`, Render 2's handler builds `'Number ' + 13 + ', please come to the counter'` and passes `13 + 1` to `setNumber`.
5. **React attaches Render 2's `handleNext` before the next click**: React commits the new DOM and connects Render 2's `handleNext` to the button before the next user click can fire. So when the second click happens, even right away, it runs Render 2's handler and reads `13`.

Two extra details often come up in interviews here:
- **Does a click handler ever start with a "stale" state value?** Developers use the word **stale** to describe an old value that no longer matches the screen. Because React processes the state update and attaches the new render's click handler before the next intentional user click, a click handler never starts with a stale value when you click.
- **What happens if you call `setNumber` with `number + 1` three times in the same click handler?** Because all three calls sit inside Render 1's snapshot where `number` is `12`, all three lines substitute `12` and pass `12 + 1` to `setNumber`. The screen moves from `12` to `13`, not `15`! Updating the same state variable multiple times in one click requires an **updater function**, which we cover in the next lecture.

```tree caption="Three snapshots across three renders: each render creates its own number constant and its own handleNext closure."
How each render gets its own snapshot and its own `handleNext`
- +Render 1 [`number` is `12`] | `handleNext` #1 closes over **`12`** | Click 1 runs `handleNext` #1, logs **`12`**, and asks React for **`13`**
- +Render 2 [`number` is `13`] | `handleNext` #2 closes over **`13`** | Click 2 runs `handleNext` #2, logs **`13`**, and asks React for **`14`**
- +Render 3 [`number` is `14`] | `handleNext` #3 closes over **`14`** | Ready on the button for the next click with **`14`**
```

> [!PRINCIPLE]
> **Principle 2: Every Render Gets Its Own Fixed Value, and Every Handler Keeps the Value of the Render That Made It**
>
> *Each render creates its own state constant and its own event handlers, and every handler closes over the state value of the render that created it.*
>
> Because `handleNext` is defined inside `QueueBoard`, each render creates a fresh `handleNext` function that closes over that render's `number`. Inside that handler, `number` is the same fixed value from top to bottom, so reading `number` before the setter or after the setter gives the exact same result. When React re-renders with the new state, it creates a new handler closed over the new value and attaches it to the button for the next click.
>
> **DO THIS:**
> ```jsx
> function handleNext() {
>   ~console.log(number);~ // Reads this render's snapshot: 12
>   ~setNumber(number + 1);~ // Calculates 12 + 1 and asks React for 13 on the next render
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleNext() {
>   ~setAnnouncement('Number ' + number + ', please come to the counter');~ // **WRONG:** moving the read above setNumber still reads 12!
>   setNumber(number + 1);
> }
> ```

## 3. Principle 3: Code That Runs Later Still Reads the Snapshot of the Click That Started It

### Why waiting three seconds in `setTimeout` still reads the old snapshot, and why that protects overlapping clicks

Now suppose a developer says: *"In Principles 1 and 2, we read `number` right away while the handler was still running. What if we use `setTimeout` to wait three seconds, until long after React has finished the new render and updated the screen to `13`? Surely after three seconds, `number` inside the timer will be `13`!"*

Let us test that idea in plain JavaScript first:

```js title="Plain JavaScript: a timer started inside a closure"
function render(number) {
  return function handleNext() {
    ~setTimeout(() => console.log(number), 300);~ // Waits 300ms, then logs the number sealed in this call
  };
}

~render(12)();~ // 1. Starts a timer inside the call where number is 12; prints 12 after 300ms
~render(13)();~ // 2. Immediately runs a second call where number is 13; prints 13 after 300ms
```

Look closely at what that timer does, because two nuances of confusion meet right here:
- **First, waiting three seconds in `setTimeout` looks as if it should give React time to update `number`, so reading `number` inside a timer seems different from reading `number` on the line right after the setter. Yes, it is the exact same thing!** A state variable's value never changes within a render, even when the handler starts asynchronous code like `setTimeout`. The arrow function inside `setTimeout` was created inside the render where `number` was `12`, so it closed over that exact same `12`. Think of it like writing a letter right now and dropping it into a delayed mailbox: when the envelope is opened three seconds later, the paper inside still says what was written when the envelope was sealed.
- **Second, a timer that still reads its click's value after the screen has moved on looks like a bug at first, but it is NOT always a bug!** Imagine two clicks happen one second apart: Click 1 for one customer, and Click 2 for the next customer. Because each timer keeps the snapshot of the click that started it, Click 1's timer remembers the first click's number and Click 2's timer remembers the second click's number, instead of both timers getting mixed up and naming only the newest number on screen!

```tree caption="A function passed to setTimeout is like a sealed letter: when the timer opens it seconds later, it still holds the snapshot of the render that created it."
Does waiting inside `setTimeout` change what `number` holds?
- !What you might expect [`setTimeout` waits 3 seconds] | Screen has already changed to **`Now serving: 13`** | You might expect `number` inside the timer to become **`13`**
- +What actually happens [Arrow function closes over Render 1's `number`] | Sealed with **`number = 12`** when Click 1 ran | Three seconds later, the timer still reads **`12`** from its own click snapshot
```

In our bakery, customers sometimes miss their first announcement while chatting. So the developer adds a three-second timer at the bottom of the click handler in `src/components/QueueBoard.jsx` to display a last-call reminder after three seconds:

### How the timer arrow function closes over its click's `number` across two quick clicks

Look at the arrow function inside `setTimeout` above. Its parameter list is empty; nothing passes `number` into it when the three seconds end. Where did it get `12` three seconds after `QueueBoard` had already rendered with `13`?

Follow the five steps in chronological order:
1. **Click 1 runs Render 1's `handleNext`**: In Render 1, `number` is `12`.
2. **`setTimeout` receives the arrow function**: JavaScript creates the arrow function inside Render 1's `handleNext`. That arrow function closes over Render 1's `number`, sealing `12` inside itself.
3. **`setTimeout` schedules the timer and returns immediately**: The browser starts counting down three seconds, and `handleNext` finishes right away.
4. **Render 2 updates the screen to `13`**: React calls `QueueBoard` for Render 2 with a new constant `number` equal to `13`, and updates the DOM to `Now serving: 13`. Render 1's `number` constant is untouched.
5. **Three seconds later, the browser runs the arrow function**: The arrow function opens its sealed closure from Render 1, reads `12`, sets the announcement to `'Last call for number 12'`, and logs `timer reads 12`.

Now see what happens when the clerk clicks `Next customer` **twice**, with only one second between Click 1 and Click 2:
1. **At 0 seconds, Click 1 runs Render 1's handler**: `number` is `12`. It starts Timer 1 sealed with `12`, and moves the screen to `Now serving: 13`.
2. **At 1 second, Click 2 runs Render 2's handler**: `number` in Render 2 is `13`. It starts Timer 2 sealed with `13`, and moves the screen to `Now serving: 14` and `Number 13, please come to the counter`.
3. **At 3 seconds, Timer 1 fires**: Timer 1 reads its sealed `12`, updates the announcement to `Last call for number 12`, and logs `timer reads 12`.
4. **At 4 seconds, Timer 2 fires**: One second after Timer 1, Timer 2 reads its sealed `13`, updates the announcement to `Last call for number 13`, and logs `timer reads 13`.

Notice why React's snapshot design is a gift here: even though Click 2 happened before Click 1's timer finished, Click 1's timer did not get overwritten by Click 2! Each click kept its own snapshot. In the React documentation's message form example, if you click Send on a message to Alice and then switch the recipient dropdown to Bob before the five-second timer finishes, the snapshot guarantees that the message you sent to Alice still goes to Alice. Our only bug in `QueueBoard` is that both timers are off by one because they read `number` instead of `number + 1`. In the rare case where delayed code truly needs to bypass the snapshot and read whatever latest value is on screen right now, React provides a ref with `useRef`, which we cover in a later lecture.

> [!PRINCIPLE]
> **Principle 3: Code That Runs Later Still Reads the Snapshot of the Click That Started It**
>
> *A state variable's value never changes within a render, even inside delayed code such as `setTimeout` that runs seconds after the screen has updated.*
>
> When an event handler starts a timer with `setTimeout`, the callback function inside `setTimeout` closes over the state snapshot of the render that created the handler. Even if React renders new values onto the screen while the timer is waiting, the timer still reads the value from the click that started it. That keeps each click's delayed work tied to its own click rather than mixing up overlapping clicks.
>
> **DO THIS:**
> ```jsx
> setTimeout(() => {
>   ~console.log('timer reads ' + number);~ // In Render 1 where number is 12, prints "timer reads 12" after 3s
> }, 3000);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleNext() {
>   setNumber(number + 1);
>   setTimeout(() => {

>   }, 3000);
> }
> ```

## 4. Principle 4: To Use the New Value Now, Calculate It Once and Pass the Same Variable Everywhere

### Why saving `const nextCount = count + 1` gives both the setter and the next line the new number right away

In Principles 1, 2, and 3, reading the state variable inside the handler always gave the old number from before the click. How do we use the **new** number right away inside the same click handler, without waiting for the next render?

Look at the official troubleshooting pattern from the React documentation:

```jsx title="Calculating nextCount once in a local constant before calling setCount"
const [count, setCount] = useState(0);

function handleClick() {
  ~const nextCount = count + 1;~ // 1. Calculate the next value once in a local constant
  setCount(nextCount);
  ~console.log(count);~ // 2. Still 0: the old snapshot of this render
  ~console.log(nextCount);~ // 3. Prints 1 right away!
}
```

Look at the two nuances here so nothing feels mysterious:
- **First, passing `nextCount` to `setCount` versus passing `count + 1` to `setCount` gives React the exact same value!** In both cases, `0 + 1` evaluates to `1`, and `setCount` receives `1`. The only difference is that by saving `const nextCount = count + 1` on the line before `setCount`, you keep that `1` in a named constant that every other line in your handler can read right away.
- **Second, creating `nextCount` looks like a way around the snapshot, but it does NOT change `count`!** Look at the two `console.log` lines above: logging `count` still prints `0`, while logging `nextCount` prints `1`. `count` is still the frozen snapshot of this render, and `nextCount` is simply a second constant holding the new number you just calculated.

Think of `nextCount` as writing the new number `13` on a note before handing a copy to the kitchen: because you keep that note in your hand, you can read `13` into the counter microphone right away and also copy `13` onto the three-second reminder timer!

```tree caption="Saving const nextCount = count + 1 gives both setCount and the rest of the handler the new value right away."
Reading `count` again vs. saving `const nextCount = count + 1`
- !Read `count` after `setCount` [Call `setCount` then log `count`] | `count` is still **this render's old snapshot `0`** | Prints **`0`**
- +Save `nextCount` first [`const nextCount = count + 1` then pass `nextCount`] | Both `setCount` and later lines read **`nextCount`** | `count` stays `0`, while `nextCount` prints **`1` right away**
```

### Calculating `nextNumber` once at the top of `handleNext`

Let us apply this fix to `src/components/QueueBoard.jsx`. On the very first line of the click handler, we calculate the next ticket number once in a local constant and pass that constant to the setter, to the immediate announcement, to the Console log, and into the three-second timer:

```jsx title="src/components/QueueBoard.jsx" startLine="9"

    ~const nextNumber = number + 1;~ // 1. Calculate 13 once at the start of the click
    ~setNumber(nextNumber);~ // 2. Pass 13 to React for the next render
    ~setAnnouncement('Number ' + nextNumber + ', please come to the counter');~ // 3. Immediate announcement uses 13
    console.log(number, nextNumber);
    setTimeout(() => {
      setAnnouncement('Last call for number ' + nextNumber);
      console.log('timer reads ' + nextNumber);
    }, 3000);
  }
```

### How `nextNumber` fixes both the immediate announcement and the three-second last call

Look at `handleNext` above. The number `13` is never typed in the file, and `number` is still `12` during the first click. How do both the immediate announcement and the three-second timer now say `13`?

Follow the five steps in chronological order when the clerk clicks `Next customer` once:
1. **First line of `handleNext`**: In Render 1 where `number` is `12`, JavaScript calculates `12 + 1` and creates the local constant `nextNumber` with the value `13`.
2. **Passing `nextNumber` to `setNumber`**: Hands `13` to React so the next render will display `Now serving: 13`.
3. **Immediate `setAnnouncement` and `console.log`**: Reads `nextNumber`, which is `13`, and stores `'Number 13, please come to the counter'`. The Console prints `12 13`, showing `number` as `12` next to `nextNumber` as `13`.
4. **`setTimeout` closes over `nextNumber`**: Because `nextNumber` is a constant created inside this click of `handleNext`, the arrow function inside `setTimeout` closes over `nextNumber` holding `13` the exact same way it previously closed over `number`. Three seconds later, the timer reads `13`, sets `'Last call for number 13'`, and logs `timer reads 13`.
5. **React commits Render 2**: Right after `handleNext` finishes, the screen shows `Now serving: 13` and `Number 13, please come to the counter`. Three seconds later, it shows `Last call for number 13`. Both lines on the board match at every moment!

When a single click needs to queue several updates to the same state variable one after another, we use an updater function, which is the topic of the next lecture.

> [!PRINCIPLE]
> **Principle 4: To Use the New Value Now, Calculate It Once and Pass the Same Variable Everywhere**
>
> *When an event handler needs the next state value right away, calculate it once in a local constant such as `nextNumber`, pass it to the setter, and pass that same constant to every other line.*
>
> You do not need to wait for React to re-render just to know what value you handed to `setNumber`. Your handler already calculated `number + 1`! By storing `const nextNumber = number + 1` at the top of the handler, you can pass `nextNumber` to `setNumber`, build strings with `nextNumber`, and let `setTimeout` close over `nextNumber` so every immediate and delayed step uses the new number.
>
> **DO THIS:**
> ```jsx
> function handleNext() {

>   ~setAnnouncement('Number ' + nextNumber + ', please come to the counter');~ // 3. Reuse nextNumber everywhere
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleNext() {
>   setNumber(number + 1);
>   ~setAnnouncement('Number ' + number + ', please come to the counter');~ // **WRONG:** re-reading number gives the old snapshot 12!
> }
> ```

## For the Interview

> **The Interview Question:** Why does state appear frozen inside a render, even right after you set it?

### How to Answer Clearly in 30 Seconds

"In React, a state variable holds one fixed value for the entire duration of a single render. Each time React calls your component function, it hands that call a snapshot of the state from React's internal storage. Three practical rules follow from that:
1. **The setter does not mutate the local variable**: Calling `setNumber` with `number + 1` does not reassign `number` in the code that is currently running. Instead, it stores the next value inside React and requests a new render. That is why logging `number` on the line right after `setNumber` still prints the old value, while the screen updates after the handler finishes and React calls the component again.
2. **JavaScript closures lock each handler to its render's snapshot**: Every render creates fresh event handlers that close over that render's `const` state variable. Because of that closure, `number` is the same whether you read it before the setter, after the setter, or three seconds later inside a `setTimeout` callback. That closure also keeps overlapping asynchronous actions tied to the values from the moment the user clicked, and React updates the state before the next click so a click handler never starts with a stale value.
3. **How to use the next value immediately**: If an event handler needs the updated value right away, calculate it once in a local constant like `const nextNumber = number + 1` and pass `nextNumber` both to `setNumber` and to any other logic in the handler. If you need to queue multiple updates in a single click, you use an updater function instead."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"If I call `setNumber` with `number + 1` when `number` is `12` and immediately log `number`, why does it print `12`? Would changing `const` to `let` or moving the log line above `setNumber` change anything?"**
   It prints `12` because `setNumber` is a function call that schedules the next render inside React; it cannot reassign the local variable `number` inside the currently running function call. Changing `const [number, setNumber]` to `let [number, setNumber]` changes nothing, because `setNumber` still cannot mutate your local variable, and trying to write `number = number + 1` on a `const` throws `Uncaught TypeError: Assignment to constant variable.`. Moving the log line above `setNumber` also prints the exact same `12`, because `number` holds `12` for the entire render snapshot.
2. **"What happens if you log `number` inside a `setTimeout` callback that runs three seconds after calling `setNumber`, long after the screen already shows `13`? Is that behavior a flaw in React?"**
   Even three seconds later, when the screen already shows `13`, the `setTimeout` callback still prints `12`. That happens because the arrow function passed to `setTimeout` was created inside the first render's click handler and closed over that render's `number` constant, which is `12`. Far from being a flaw, this snapshot behavior prevents timing bugs when actions overlap: if a user clicks twice or changes a form field while a delayed action is still waiting, each click's timer keeps the exact values from the moment it was triggered. When delayed code genuinely needs to read the latest value on screen instead of the click's snapshot, you store that value in a ref with `useRef`.
3. **"How do you use the new state value right away inside the same event handler, and can a click handler ever start with a stale state value?"**
   To use the new value right away in the same handler, calculate it once in a local constant before calling the setter, such as `const nextNumber = number + 1`, and pass `nextNumber` to `setNumber`, to any other setter, and into any `setTimeout` callback. And no, a click handler does not start with a stale value on the next click: React processes the state update, re-renders the component, and attaches the new render's event handler before the next intentional user click runs.

```tree dir=right caption="Interview summary: why reading number after setNumber gives the old snapshot, and how nextNumber gives the new value right away."
How to use the next state value inside the same event handler
- !Read `number` again after `setNumber` [Call `setNumber` then read `number`] | Closure reads **this render's old snapshot `12`**, even inside `setTimeout`
- +Save `const nextNumber = number + 1` first [Pass `nextNumber` to `setNumber` and later lines] | Local constant holds **`13` right away** for setters, logs, and timers in that click
```
