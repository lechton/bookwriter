# Lecture 21: Reacting to Input with State: Letting `status` Pick the Screen
> INTERVIEW QUESTION | ❱ CORE | How do you design a component that reacts to input with state instead of touching the DOM?

---

## Why a Component Describes Its Screens Instead of Changing Them

### Writing each message by hand vs. letting `status` pick the message

In Lesson 01, plain JavaScript changed the page with commands, one line at a time, while React described the finished page. Here is that difference on a sign-up box that can show two messages: an error line when a sign-up fails, and a thank-you line when it works. The user tries twice. The first try fails, and the second try works.

With commands, plain JavaScript writes each message into its own paragraph:

```js title="page.js"
const errorText = document.getElementById('error');
const doneText = document.getElementById('done');

~errorText.textContent~ = 'This email is already subscribed.'; // The first try fails: the error line appears
~doneText.textContent~ = 'You are subscribed!'; // The second try works: the error line is still on the page
```

With `status` in state, React shows each message only while `status` holds its word:

```jsx title="SubscribeBox.jsx"
{~status === 'error'~ && <p>This email is already subscribed.</p>} {/* The first try sets status to 'error': only this line shows */}
{~status === 'success'~ && <p>You are subscribed!</p>} {/* The second try sets status to 'success': only this line shows */}
```

Here is the page after the user's second try, for each way:

::: row caption="The sign-up box after the second try: with commands, both messages stay; with status, only the thank-you line shows."
::: col title="Writing each message by hand" tag="both messages on the page" tone=bad
```page size=mini
line: This email is already subscribed. | bad
line: You are subscribed! | good
```
:::
::: col title="Letting status pick the message" tag="one message at a time" tone=good
```page size=mini
line: You are subscribed! | good
```
:::
:::

It looks the same, but it is NOT the same thing! After the first try, both ways show only the error line. After the second try, the command for the thank-you line adds a line and removes nothing, so the old error stays on the page. `status` holds one word at a time, so when it becomes `'success'`, the condition of the error line is false, and React takes that line off the page.

With commands, every change must also undo the old message by hand. With `status`, our code only says which message is true now, and React makes the page match.

### Why a newsletter box shows two opposite messages

Think of the newsletter box at the bottom of a news site. It says Get our weekly news, and it has an email box and a Subscribe button. When the user clicks Subscribe, the box shows Subscribing... for a moment while a server checks the email, and then it shows either an error line or a thank-you line.

Here is how that box is often written in plain JavaScript. A timer of 1500 milliseconds stands in for the server. Our pretend server says that `john@example.com` is already subscribed, and that any other email is new:

```js title="subscribe.js"
const emailBox = document.getElementById('email');
const statusText = document.getElementById('status');
const errorText = document.getElementById('error');
const doneText = document.getElementById('done');

function handleSubscribe() {
  statusText.textContent = 'Subscribing...';
  setTimeout(() => {
    statusText.textContent = '';
    if (emailBox.value === 'john@example.com') {
      errorText.textContent = 'This email is already subscribed.';
    } else {
      ~doneText.textContent~ = 'You are subscribed!'; // **WRONG:** writes the thank-you line and leaves the error line on the page
    }
  }, 1500);
}

document.getElementById('subscribe').addEventListener('click', handleSubscribe);
```

Here is what the user meets:
1. The user types `john@example.com` and clicks Subscribe.
2. After about a second and a half, the line This email is already subscribed. appears.
3. The user changes the email to `anna@example.com` and clicks Subscribe again.
4. The thank-you line appears, and the error line is still there above it.

```page width=text caption="The plain JavaScript newsletter box after a failed try and a good try: two opposite messages at once."
heading: Get our weekly news
form:
  field: Your email | anna@example.com
  button: Subscribe
line: This email is already subscribed. | bad
line: You are subscribed! | bad
```

This handler starts from the actions: when the user clicks, write this; when the server answers, write that. Each command fixes one part of the page, and it must also remember every other part that the last command left behind. React turns the work around. We first list everything the box can show, and then every input only says which of those pictures is true now.

### Our example page: the newsletter box

Our page is that same newsletter box, built in React. Each picture of the box that the user can see is a **screen**. Our box has four screens:
- **Typing**: the email box and the Subscribe button are on, and the user can type.
- **Sending**: the box and the button are greyed out, and the line Subscribing... shows under them.
- **Success**: the line You are subscribed! shows in place of the whole box.
- **Error**: the same as typing, plus the line This email is already subscribed.

The pretend server stays the same: one timer of 1500 milliseconds that answers with the error for `john@example.com` and with success for any other email. The plain JavaScript version above is only a snippet for comparison. It is not part of the project.

The project has five files:

```files title="newsletter-box: File Explorer" caption="How the files of our newsletter box sit inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` and mounts it inside `<StrictMode>` into `#root`

  App.jsx | parent | Exports `App` as default and renders `SubscribeBox`
  components/
    SubscribeBox.jsx | default export | Exports `SubscribeBox` as default and draws every screen of the box
```

### Four Principles of Reacting to Input with State

**PRINCIPLES:** A React component never shows, hides, turns on, or turns off a part of the page by hand. It describes every screen once, and state picks the screen. Four rules follow:
1. **`status` picks which screen the box shows.** List every screen first, and write each one in JSX, chosen by one value.
2. **A click and a timer only call `setStatus`.** Every input, from the user or from the computer, only sets state, and React draws the new screen.
3. **One `status` replaces three true-or-false flags.** Separate flags can be true together, and then the page shows two screens at once.
4. **The red border follows `status`, not `classList`.** A look that changes with the screen comes from `status` in JSX, because React leaves alone a class that its JSX never set.

Here is the map of the four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`status` Picks Which Screen the Box Shows** | A message that stays on the page after it should be gone means some command forgot to undo it. Interviewers ask how you plan a component before writing its handlers. | List every screen first, and write each one in JSX, chosen by a single `status` value. |
| **Principle 2** | **A Click and a Timer Only Call `setStatus`** | A button that never turns back on after an error comes from code that turns it off and on by hand. | Every human input and every computer input only calls a setter. `disabled` and every message follow from state. |
| **Principle 3** | **One `status` Replaces Three True-or-False Flags** | An error line next to Subscribing... is a mix of flags that matches no real screen, and React prints no warning for it. | Keep the screen in one `status` string with a fixed list of values. |
| **Principle 4** | **The Red Border Follows `status`, Not `classList`** | A red border that stays after the error is gone comes from a class added by hand, which React never takes away. | Compute `className` from `status` in JSX, and never add or remove classes on a DOM node yourself. |

## 1. Principle 1: `status` Picks Which Screen the Box Shows

### `status="error"` vs. `status="success"`

Before any state or handler exists, the same component can already draw two different screens. Here is the newsletter box placed twice, once with each value of a prop named `status`:

::: row caption="The same SubscribeBox component with status set to error, and with status set to success."
::: col title="With status set to error" tag="the box and the error line" tone=good
```page size=mini
heading: Get our weekly news
form:
  field: Your email |
  button: Subscribe
line: This email is already subscribed.
```
```jsx title="App.jsx"
<SubscribeBox ~status="error"~ /> {/* The box, the button, and the error line */}
```
:::
::: col title="With status set to success" tag="only the thank-you line" tone=good
```page size=mini
heading: You are subscribed!
```
```jsx title="App.jsx"
<SubscribeBox ~status="success"~ /> {/* Only the thank-you line, with no box and no button */}
```
:::
:::

It looks the same, but it is NOT the same thing! Both tags name the same component, yet each one draws a different screen, because the component reads `status` and picks the screen from it. No line of the component hides or shows anything by hand.

`status` is our own prop name. The React docs say you could call that prop anything you like.

### Writing the four screens in `SubscribeBox`

Here is the whole component for now. It has no state and no handler yet. It only describes what the box looks like for each value of `status`:

```jsx title="src/components/SubscribeBox.jsx"
export default function SubscribeBox({ ~status = 'typing'~ }) { // A tag with no status gets 'typing'
  if (~status === 'success'~) { // The success screen replaces the whole box
    return <h2>You are subscribed!</h2>;
  }

  return (
    <section>
      <h2>Get our weekly news</h2>
      <label>
        Your email
        <input ~disabled={status === 'sending'}~ /> {/* Greyed out only while sending */}
      </label>
      <button disabled={status === 'sending'}>Subscribe</button>
      {~status === 'sending'~ && <p>Subscribing...</p>} {/* Only on the sending screen */}
      {~status === 'error'~ && <p>This email is already subscribed.</p>} {/* Only on the error screen */}
    </section>
  );
}
```

Each of the four screens is written once, in one place. The success screen has no error line in its JSX, so the bug of the plain JavaScript box has nowhere to come from.

### Every screen on one page

To check every screen before any logic exists, `App` can place the box four times, once for each value of `status`:

```jsx title="src/App.jsx"
import SubscribeBox from './components/SubscribeBox.jsx';

const statuses = ['typing', 'sending', 'success', 'error'];

export default function App() {
  return (
    <main>
      {statuses.map(status => (
        <div ~key={status}~> {/* One copy of the box for each screen */}
          <h3>Screen: {status}</h3>
          <SubscribeBox status={status} />
        </div>
      ))}
    </main>
  );
}
```

A page that shows every screen of a component at once is what teams call a living styleguide or a storybook. It lets a designer and a developer look at every screen before a single handler is written.

### Mistake: starting from the clicks instead of the screens

The plain JavaScript box at the start of this lecture was written from the actions: on click, write Subscribing...; on an error, write the error; on success, write the thank-you line. Each action became a command, and the success command never cleared the error line. The React docs call this mistake forgetting to show or hide something.

Listing the screens first prevents it. The success screen has no error line, so its JSX has none, and no command has to remember to remove it:

```tree caption="Writing a newsletter box from its actions vs. from its screens."
Two ways to start a newsletter box
- !Start from the actions [`textContent`] | One command for each click and each answer | Each command must **undo the last screen by hand** | Forgets the error line: **two messages at once**
- +Start from the screens [`status`] | Four screens: typing, sending, success, error | Each screen is **written once** in JSX | The success screen **has no error line** to forget
```

> [!PRINCIPLE]
> **Principle 1: Screens First: `status` Picks Which Screen the Box Shows**
>
> *Before writing any handler, list every screen the user can see, and write JSX for each one, chosen by a single `status` value.*
>
> A box written from its actions needs one command for each click and each answer, and every command must also undo whatever the last one left on the page. When one command forgets, the user sees two opposite messages at once. When the box is written from its screens, each screen sits in the JSX once, and `status` says which one is on the page. A message that does not belong to the current screen is simply not in the JSX.
>
> **DO THIS:**
> ```jsx
> {~status === 'error'~ && <p>This email is already subscribed.</p>} {/* Only on the error screen */}
> {status === 'success' && <p>You are subscribed!</p>}
> ```
>
> **DO NOT DO THIS:**
> ```js
> ~doneText.textContent~ = 'You are subscribed!'; // **WRONG:** writes the thank-you line and leaves the error line on the page!
> ```

## 2. Principle 2: A Click and a Timer Only Call `setStatus`

### A human input vs. a computer input

Something must change `status` while the page runs. Here are the two kinds of input that change the screen of our box. The first comes from the user, and the second comes from the computer:

```jsx title="When the user clicks Subscribe"
<button onClick={() => ~setStatus('sending')~}>Subscribe</button> {/* The screen becomes sending */}
```

```jsx title="When the timer ends"
setTimeout(() => ~setStatus('success')~, 1500); // The screen becomes success
```

Yes, it is the exact same thing! A click and a timer look like two different kinds of event, but both only call `setStatus`, and React draws the screen that the new `status` picks.

The React docs give the two kinds their own names:
- A **human input** is something the user does, such as typing in a box, clicking a button, or following a link. Human inputs usually need an event handler.
- A **computer input** arrives without the user doing anything, such as an answer from a server, a timer that ends, or an image that finishes loading.

For both kinds, the docs give one rule: to change what the user sees, you set state.

Every screen of our box changes into another one because of one input:

```tree dir=right caption="The four screens of the newsletter box and the input that moves the box from one screen to the next."
How each input moves the box between screens
- +Typing | The user **clicks Subscribe** | Moves to **sending**
- +Sending | The timer ends with `john@example.com` | Moves to **error** | The timer ends with any other email | Moves to **success**
- +Error | The user **types a new letter** | Moves back to **typing**
- +Success | **No input** leaves this screen
```

### Giving the box its state

Now `status` stops being a prop and moves into state. A second state, `email`, holds the text of the box, as in Lesson 20. The click starts the pretend server, and the timer sets the answer:

```jsx title="src/components/SubscribeBox.jsx" startLine="1"
import { useState } from 'react';

export default function SubscribeBox() {
  const [email, setEmail] = useState('');
  const [status, setStatus] = ~useState('typing')~; // The box opens on the typing screen

  function handleEmailChange(e) {
    setEmail(e.target.value);
    ~setStatus('typing')~; // Typing again leaves the error screen
  }

  function handleSubscribe() {
    ~setStatus('sending')~; // Human input: the user clicked Subscribe
    setTimeout(() => {
      if (email === 'john@example.com') {
        ~setStatus('error')~; // Computer input: the pretend server says no
      } else {
        setStatus('success');
      }
    }, 1500);
  }
```

The JSX stays as it was in Principle 1. Only the box gets `value` and `onChange`, and the button gets `onClick`:

```jsx title="src/components/SubscribeBox.jsx" startLine="22"
  if (status === 'success') {
    return <h2>You are subscribed!</h2>;
  }

  return (
    <section>
      <h2>Get our weekly news</h2>
      <label>
        Your email
        <input value={email} onChange={handleEmailChange} disabled={status === 'sending'} />
      </label>
      <button ~onClick={handleSubscribe}~ disabled={status === 'sending'}>Subscribe</button> {/* The handler only sets state */}
      {status === 'sending' && <p>Subscribing...</p>}
      {status === 'error' && <p>This email is already subscribed.</p>}
    </section>
  );
}
```

The `if` with the early `return` sits below both `useState` lines, so the hooks run on every render, as Lesson 12 requires. `App` now places one box:

```jsx title="src/App.jsx"
import SubscribeBox from './components/SubscribeBox.jsx';

export default function App() {
  return ~<SubscribeBox />~; // One newsletter box, which holds its own state
}
```

The user types `john@example.com` and clicks Subscribe. The box moves to the sending screen:

```page width=text caption="Right after the user clicks Subscribe: the box and the button are greyed out while sending."
heading: Get our weekly news
form:
  field: Your email | john@example.com
  button: Subscribe
line: Subscribing...
```

About a second and a half later, the timer ends and the pretend server says no:

```page width=text caption="When the timer ends with john@example.com: the error screen, with the box and the button on again."
heading: Get our weekly news
form:
  field: Your email | john@example.com | good
  button: Subscribe | good
line: This email is already subscribed. | good
```

### The box turns itself back on

On the error screen, the email box and the Subscribe button are on again, and no line of our code turned them on. React turns them on, because `disabled` follows `status`:
1. The timer calls `setStatus('error')`.
2. React calls `SubscribeBox` again, and `status` is now `'error'`.
3. `status === 'sending'` is now false, so the box and the button both get `disabled={false}`.
4. React compares the new JSX with the last one and changes only the `disabled` attribute of the box and of the button in the DOM, as Lesson 13 showed.

The timer reads `email` from the render in which the user clicked Subscribe, as Lesson 15 showed. That is safe here, because the box is greyed out while sending, so the user cannot change the email before the answer arrives.

When the user starts typing a new email on the error screen, the error line goes away. React renders once for the two setters in `handleEmailChange`, as Lesson 16 showed, and in that render the condition of the error line is false.

The user changes the email to `anna@example.com` and clicks Subscribe again. After Subscribing..., the success screen replaces the whole box:

```page width=text caption="When the timer ends with anna@example.com: only the success screen."
heading: You are subscribed! | good
```

### Mistake: the plain JavaScript button that never turns back on

In plain JavaScript, a developer turns the button off by hand when the user clicks, and must remember to turn it on again in every branch that needs it:

```js title="subscribe.js"
function handleSubscribe() {
  button.disabled = true;
  setTimeout(() => {
    if (emailBox.value === 'john@example.com') {
      ~errorText.textContent~ = 'This email is already subscribed.'; // **WRONG:** forgets button.disabled = false
    } else {
      doneText.textContent = 'You are subscribed!';
    }
  }, 1500);
}
```

The success branch leaves the button off, which suits a finished sign-up. The error branch forgets `button.disabled = false`. The user reads the error, fixes the email, and cannot click Subscribe again:

```page width=text caption="The plain JavaScript box after the error: the user fixed the email, but the Subscribe button stays greyed out."
heading: Get our weekly news
form:
  field: Your email | anna@example.com
  button: Subscribe | bad
line: This email is already subscribed.
```

In the React version, `disabled={status === 'sending'}` is the only place that decides whether the button is on. Every screen except sending turns it on, so no branch can forget it.

The React version is longer than the plain JavaScript one, but the React docs call it much less fragile. A new screen, such as a line that says Check your inbox to confirm, adds one value of `status` and one branch in the JSX. The handlers that already work do not change.

> [!PRINCIPLE]
> **Principle 2: Inputs Set State: A Click and a Timer Only Call `setStatus`**
>
> *Find every input that changes the screen, from the user or from the computer, and make each one call a setter; the handler never turns a page part on or off and never writes a message.*
>
> A click by the user and a timer that ends look like two different kinds of event, but in React they do the same job: they set `status`, and React draws the screen that `status` picks. When a handler turns the button off by hand, some other branch must turn it on by hand, and one forgotten line leaves the user stuck. When `disabled` comes from `status` in the JSX, there is exactly one place that decides it, and every screen gets the right answer.
>
> **DO THIS:**
> ```jsx
> <button onClick={() => ~setStatus('sending')~} disabled={status === 'sending'}>Subscribe</button> {/* The click only sets state */}
> ```
>
> **DO NOT DO THIS:**
> ```js
> function handleSubscribe() {
>   ~button.disabled = true~; // **WRONG:** turned off by hand, so every later branch must turn it on by hand!
> }
> ```

## 3. Principle 3: One `status` Replaces Three True-or-False Flags

### Three flags vs. one `status`

There is another way to keep the screen in state: one true-or-false flag for each screen. Here are both, after a failed try and a second click on Subscribe:

```jsx title="Three true-or-false flags"
const [isSending, setIsSending] = useState(false);
const [isError, setIsError] = useState(false);
const [isSuccess, setIsSuccess] = useState(false);

setIsError(true); // The first try fails
~setIsSending(true)~; // The second click: isError is still true, so the error line and Subscribing... show together
```

```jsx title="One status"
const [status, setStatus] = useState('typing');

setStatus('error'); // The first try fails
~setStatus('sending')~; // The second click: status holds only 'sending', so only Subscribing... shows
```

It looks the same, but it is NOT the same thing! Both seem to describe the same four screens. But three flags can be true together, while `status` can only hold one of its four words at a time.

A mix of values that matches no screen you would want the user to see is an **impossible state**. The React docs call it a paradox: a form cannot be typing and sending at the same time. One `status` with a fixed list of values cannot hold such a mix.

Programmers call a thing that is always in exactly one of a fixed list of states a **state machine**. Think of a traffic light: exactly one light is on at a time, and red and green are never on together. Our `status` works the same way. It is always exactly one of `'typing'`, `'sending'`, `'success'`, and `'error'`.

### Mistake: the error line stays while the box is sending

Here is the newsletter box written with three flags. Each flag is set by hand in the place where its screen begins:

```jsx title="src/components/SubscribeBox.jsx" startLine="3"
export default function SubscribeBox() {
  const [email, setEmail] = useState('');
  const [isSending, setIsSending] = useState(false);
  const [isError, setIsError] = useState(false);
  const [isSuccess, setIsSuccess] = useState(false);

  function handleEmailChange(e) {
    setEmail(e.target.value);
  }

  function handleSubscribe() {
    ~setIsSending(true)~; // **WRONG:** turns sending on and leaves isError as it was
    setTimeout(() => {
      setIsSending(false);
      if (email === 'john@example.com') {
        setIsError(true);
      } else {
        setIsSuccess(true);
      }
    }, 1500);
  }
```

The JSX reads each flag on its own:

```jsx title="src/components/SubscribeBox.jsx" startLine="25"
  if (isSuccess) {
    return <h2>You are subscribed!</h2>;
  }

  return (
    <section>
      <h2>Get our weekly news</h2>
      <label>
        Your email
        <input value={email} onChange={handleEmailChange} disabled={isSending} />
      </label>
      <button onClick={handleSubscribe} disabled={isSending}>Subscribe</button>
      {~isSending~ && <p>Subscribing...</p>} {/* Shows whenever isSending is true */}
      {~isError~ && <p>This email is already subscribed.</p>} {/* Shows whenever isError is true, even while sending */}
    </section>
  );
}
```

The user gets the error for `john@example.com`, changes the email to `anna@example.com`, and clicks Subscribe. The box shows Subscribing... and the error line together, with the box greyed out, and the Console stays quiet:

```page width=text caption="The box with three flags on the second try: the error line and Subscribing... at once, with the box and the button greyed out."
heading: Get our weekly news
form:
  field: Your email | anna@example.com
  button: Subscribe
line: Subscribing... | bad
line: This email is already subscribed. | bad
console: quiet
```

This is the exact screen the React docs warn about: you never want to show an error message and disable the box at the same time. Here is how it happens:
1. The first timer set `isError` to true.
2. Typing the new email calls only `setEmail`, and nothing sets `isError` back to false.
3. The second click calls `setIsSending(true)`, so `isSending` and `isError` are both true.
4. Both `&&` lines read a true flag, so both lines are in the JSX, and React puts both on the page.

React prints no warning, because every flag holds a valid true or false. Only the mix is wrong.

### Eight mixes for four screens

Each of the three flags can be true or false, so together they allow two times two times two, which is eight mixes. Only four of them are real screens: all three flags false is typing, and exactly one flag true is sending, error, or success. The other four mixes are impossible states that the code must never reach. Each new flag doubles the number of mixes, while a new screen adds only one word to `status`.

### The fix: back to one `status`

Replace the three flags with the single `status` of Principle 2. The click sets `'sending'`, and that one word replaces `'error'`, so the error line leaves the page in the same render:

```jsx title="src/components/SubscribeBox.jsx" startLine="12"
  function handleSubscribe() {
    ~setStatus('sending')~; // One word replaces 'error': the error line leaves the page
```

```page width=text caption="The box with one status on the second try: only Subscribing..., with the box and the button greyed out."
heading: Get our weekly news
form:
  field: Your email | anna@example.com
  button: Subscribe
line: Subscribing... | good
console: quiet
```

Two more tools take this idea further in later lessons. State that can be worked out from other state, such as an empty box from the length of `email`, needs no flag of its own: Lesson 22. A reducer can rule out the impossible mixes that remain across several state variables: Lesson 27.

> [!PRINCIPLE]
> **Principle 3: One Status: One `status` Replaces Three True-or-False Flags**
>
> *Keep the screen in one `status` string with a fixed list of values, never in one true-or-false flag for each screen.*
>
> Three flags allow eight mixes, and only four of them are real screens. When one handler forgets to switch an old flag off, the page shows two screens at once, such as an error line next to Subscribing..., and React gives no warning. A single `status` works like a traffic light: it holds exactly one of its words, so setting a new word always ends the old screen.
>
> **DO THIS:**
> ```jsx
> const [status, setStatus] = ~useState('typing')~; // 'typing', 'sending', 'success', or 'error'
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [isSending, setIsSending] = useState(false);
> const [isError, setIsError] = ~useState(false)~; // **WRONG:** can be true together with isSending!
> ```

## 4. Principle 4: The Red Border Follows `status`, Not `classList`

### `classList.add` by hand vs. `className` from `status`

On the error screen, the email box should get a red border. The CSS file holds one class for it:

```css title="src/index.css"
.invalid {
  border: 2px solid red;
}
```

There are two ways to put that class on the box. The first adds it by hand with `classList.add`, the browser's way to add one class to an element. The second computes `className` from `status` in the JSX:

```js title="Adding the class by hand"
document.getElementById('email').~classList.add('invalid')~; // The border turns red, and it stays red
```

```jsx title="Computing className from status"
<input ~className={status === 'error' ? 'invalid' : ''}~ /> {/* Red only while status is 'error' */}
```

It looks the same, but it is NOT the same thing! On the error screen, both boxes have a red border. But React leaves alone a class that its JSX never set, so the class added by hand stays after the screen changes. The class computed from `status` leaves as soon as `status` is no longer `'error'`.

### Mistake: the red border that stays after the error

First, `main.jsx` imports the CSS file, so the `invalid` class reaches the page:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import ~'./index.css'~; // Loads the invalid class for the whole page
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

Out of plain JavaScript habit, a developer gives the box an `id` and adds the class by hand inside the timer, when the pretend server says no:

```jsx title="src/components/SubscribeBox.jsx" startLine="12"
  function handleSubscribe() {
    setStatus('sending');
    setTimeout(() => {
      if (email === 'john@example.com') {
        setStatus('error');
        document.getElementById('email').~classList.add('invalid')~; // **WRONG:** a class that no JSX describes
      } else {
        setStatus('success');
      }
    }, 1500);
  }
```

```jsx title="src/components/SubscribeBox.jsx" startLine="32"
        <input ~id="email"~ value={email} onChange={handleEmailChange} disabled={status === 'sending'} /> {/* No className in the JSX */}
```

Here is what the user meets:
1. The user types `john@example.com` and clicks Subscribe.
2. The error screen appears, and the email box has a red border.
3. The user clicks into the box and deletes the last letter to fix the email.
4. `status` becomes `'typing'`, and the error line goes away.
5. The red border stays.

No line of our JSX asks for a red border on the typing screen. Our `classList.add` put the class straight onto the real DOM node, outside React's description of the screen. Here is why React leaves it there:
1. The keystroke by the user calls `setStatus('typing')`, and React calls `SubscribeBox` again.
2. The JSX of the email box has no `className`, now or in the last render.
3. React compares the two and finds no change to `className`, so it does not touch the class of that box.
4. The `invalid` class that our code added by hand is still on the box.

The React docs give the rule behind step 3: React avoids touching the DOM for properties that have not changed since the last time they were set. The Elements panel shows the class still on the box:

```dom caption="The Elements panel after the user deletes one letter, in the version with classList.add."
<section>
  <h2>Get our weekly news</h2>
  <label>
    Your email
!   <input id="email" class="invalid"> | note: Added by hand, so React never takes it away
  </label>
  <button>Subscribe</button>
</section>
```

The developer can add `classList.remove('invalid')` inside `handleEmailChange`. The border then goes away, but now two places must agree again, the same trap as the plain JavaScript box at the start of this lecture.

### The fix: `className` from `status`

Remove the `id` and both hand-written lines, and compute the class from `status` on the box:

```jsx title="src/components/SubscribeBox.jsx" startLine="31"
        <input
          value={email}
          onChange={handleEmailChange}
          disabled={status === 'sending'}
          ~className={status === 'error' ? 'invalid' : ''}~ // Red only on the error screen
        />
```

Now the class follows the screen. Here is the box after the user deletes one letter, in both versions:

::: row caption="The email box after the user deletes one letter on the error screen: with classList.add, the red border stays; with className from status, it goes away."
::: col title="With classList.add" tag="the red border stays" tone=bad
```page size=mini
heading: Get our weekly news
form:
  field: Your email | john@example.co | bad
  button: Subscribe
```
The error line is gone, and the box still has the `invalid` class.
:::
::: col title="With className from status" tag="the red border goes away" tone=good
```page size=mini
heading: Get our weekly news
form:
  field: Your email | john@example.co | good
  button: Subscribe
```
`status` is `'typing'`, so `className` is an empty string, and React removes the class.
:::
:::

> [!PRINCIPLE]
> **Principle 4: Looks Follow State: The Red Border Follows `status`, Not `classList`**
>
> *When a look changes with the screen, such as a red border on the error screen, compute `className` from `status` in JSX; never add or remove classes on the DOM node by hand.*
>
> React changes only the parts of the DOM whose JSX changed since the last render. A class added with `classList.add` is not in the JSX at all, so React never sees it and never takes it away, and the red border stays after the error is gone. When `className` comes from `status`, the class is part of the screen React describes, so it appears on the error screen and leaves with it.
>
> **DO THIS:**
> ```jsx
> <input ~className={status === 'error' ? 'invalid' : ''}~ /> {/* The class follows status */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> document.getElementById('email').~classList.add('invalid')~; // **WRONG:** no JSX sets this class, so React never takes it away!
> ```

```jsx title="src/components/SubscribeBox.jsx"
import { useState } from 'react';

export default function SubscribeBox() {
  const [email, setEmail] = useState('');
  const [status, setStatus] = ~useState('typing')~; // 3. One status, never three flags

  function handleEmailChange(e) {
    setEmail(e.target.value);
    setStatus('typing');
  }

  function handleSubscribe() {
    ~setStatus('sending')~; // 2. Human input: the click only sets state
    setTimeout(() => {
      if (email === 'john@example.com') {
        ~setStatus('error')~; // 2. Computer input: the timer only sets state
      } else {
        setStatus('success');
      }
    }, 1500);
  }

  if (~status === 'success'~) { // 1. Each screen is written once
    return <h2>You are subscribed!</h2>;
  }

  return (
    <section>
      <h2>Get our weekly news</h2>
      <label>
        Your email
        <input
          value={email}
          onChange={handleEmailChange}
          disabled={status === 'sending'}
          ~className={status === 'error' ? 'invalid' : ''}~ // 4. The red border follows status
        />
      </label>
      <button onClick={handleSubscribe} disabled={status === 'sending'}>Subscribe</button>
      {status === 'sending' && <p>Subscribing...</p>}
      {status === 'error' && <p>This email is already subscribed.</p>}
    </section>
  );
}
```

### How React calls the components

When the page loads, React starts at `App` and follows the tags. After every setter call, React calls `SubscribeBox` again and draws the screen that `status` picks:

```tree caption="The component tree of the newsletter page and the order in which React calls each component."
`main.jsx` mounts `App` inside `<StrictMode>`
- +`App` [1. Called first] | **Root component** | Returns `<SubscribeBox />`
  - +`SubscribeBox` [2. Called second] | Holds `email` and **one `status`** | Called again after **every keystroke by the user**, every click on Subscribe, and every timer that ends
```

Every input goes around the same loop:

```tree dir=right caption="The loop that every input runs, from the input to the new screen."
One input in the newsletter box
- +1. An input arrives | The user types or clicks, or the timer ends
- +2. The setter [`setStatus`] | Saves the new word in **state**
- +3. React renders again | Reads `status` and picks **one screen**
- +4. React commits | Changes only the DOM parts that differ: a message, `disabled`, or the class
```

### Summary

| Aspect | The Plain JavaScript Habit | The React Rule |
| :--- | :--- | :--- |
| **Showing a message** | Write each message with `textContent`, and remember to clear every old one by hand | List every screen first, and let `status` pick the one on the page |
| **Turning a button off and on** | Set `button.disabled` by hand in every branch | Every input only calls a setter, and `disabled` follows `status` |
| **Keeping the screen in state** | One true-or-false flag for each screen, which can be true together | One `status` string with a fixed list of values |
| **A look that changes with the screen** | Add and remove classes with `classList` | Compute `className` from `status` in JSX |

## For the Interview

> **The Interview Question:** How do you design a component that reacts to input with state instead of touching the DOM?

### How to Answer Clearly in 30 Seconds

"I never show, hide, enable, or disable a page part by hand. I describe every screen once in JSX and let state pick the screen. The React docs give five steps, and I follow them in this order:
1. **List every screen the user can see.** The docs call them visual states. For a newsletter box: typing, sending, success, and error. I can draw all of them on one page by passing a `status` prop before any logic exists.
2. **Find every input that changes the screen.** Human inputs, such as typing and clicking, and computer inputs, such as a server answer or a timer.
3. **Keep the screen in `useState`.** One `status` string with a fixed list of values, not one true-or-false flag for each screen, because flags can be true together and show an impossible mix.
4. **Remove state that is not needed.** Anything that can be worked out from other state needs no state of its own.
5. **Connect every input to a setter.** Handlers only call `setStatus`. Messages, `disabled`, and class names all come from `status` in JSX. React then changes only the DOM parts that differ, and it leaves alone a class that no JSX set, which is why I never use `classList` on a React node."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why is one `status` string better than several booleans such as `isSending` and `isError`?"**
   Each true-or-false flag doubles the number of possible mixes. Three flags allow eight mixes, and only four of them are real screens. When one handler forgets to switch an old flag off, the page shows an error line next to Subscribing..., and React prints no warning, because every flag holds a valid value. One `status` with a fixed list of values works like a state machine: like a traffic light, it is always in exactly one state, so setting a new word always ends the old screen. If some mixes still make no sense across several state variables, such as an error text while `status` is `'success'`, a reducer can bring them into one place, which is Lesson 27.

2. **"How would you add a new screen to this component, and why is the declarative version safer than the imperative one?"**
   A new screen, such as a Check your inbox to confirm line, adds one value of `status`, one branch in the JSX, and one setter call where the input arrives. The handlers that already work do not change, and no existing screen breaks. In the imperative version, every new screen means new commands, and every existing command must learn to undo it. The React docs admit the declarative version is longer, and they call it much less fragile. Teams often draw every screen on one page, called a living styleguide or a storybook, to check each one before the logic exists.

3. **"Why does a class added with `classList.add` stay on a React element, and what do you write instead?"**
   React compares the new JSX with the last one and changes only the DOM properties that differ. A class added with `classList.add` is not in the JSX, so React never sees it and never removes it. After the error screen ends, the red border stays. Instead, I compute the class from state, such as `className={status === 'error' ? 'invalid' : ''}`, so the class is part of the screen React describes. Another way is to return two separate chunks of JSX, one for each screen. Then their nesting must line up, or switching between them can rebuild the whole tree below and reset what the user typed, which is Lesson 25.
