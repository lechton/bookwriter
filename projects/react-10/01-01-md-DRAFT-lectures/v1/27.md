# Lecture 27: Consolidating State Logic with useReducer
> INTERVIEW QUESTION | ❱ CORE | When does state logic outgrow useState, and how does a reducer consolidate it?

---

## How a Reducer Gathers Every Update Rule in One Place

### Setting the next state in the handler vs. saying what the user did

Every state change so far has worked the same way: an event handler works out the next value and hands it to the setter. That stays easy to read while a component has one or two buttons. When four buttons change the same state, each in its own way, four handlers each carry their own rule for the next state. React gives us a second way to write the same component, where the handlers only say what the user did and one function holds every rule. That function is called a **reducer**, and the Hook that uses it is `useReducer`.

Here is one counter written both ways. First, with `useState`, as in Lesson 12:

```jsx title="A counter with useState"
const [count, setCount] = useState(0);

<button onClick={() => ~setCount(count + 1)~}>Count: {count}</button> {/* The rule add one sits inside the handler */}
```

Now the same counter with `useReducer`:

```jsx title="The same counter with useReducer"
function reducer(count, action) {
  if (action.type === 'incremented') {
    ~return count + 1;~ // The rule add one sits here, outside the handler
  }
}

const [count, dispatch] = useReducer(reducer, 0);

<button onClick={() => ~dispatch({ type: 'incremented' })~}>Count: {count}</button> {/* The handler only says what happened */}
```

On the page, nobody can tell the two counters apart. Each button shows `Count: 0` when the page opens and `Count: 1` after one click by the user. **Yes, it is the exact same thing!** React's docs say it plainly: "You can always convert between `useState` and `useReducer` back and forth: they are equivalent!"

What the two share is everything the user sees: one state variable that React keeps between renders, and a function that React gives back to change it. The one difference is where the rule for the next value lives. With `useState`, the handler holds the rule and passes the finished value to `setCount`. With `useReducer`, the handler only reports what happened, and the function `reducer` holds the rule.

React's docs describe the second way like this: "Instead of telling React 'what to do' by setting state, you specify 'what the user just did' by dispatching 'actions' from your event handlers."

Think of a waiter in a restaurant. The waiter writes down what the customer ordered and hands the order to the kitchen. The waiter never cooks, and only the kitchen knows how each dish is made. An event handler that calls `dispatch` works the same way: it passes on what the user did, and the reducer alone knows how the state changes because of it.

```tree caption="Two ways to change one state variable: the handler works out the next value, or the handler says what the user did and one function works out the value."
Two ways to change the same state
- +With `useState` [`setCount`] | The handler **works out the next value** | Every handler holds **its own rule**
- +With `useReducer` [`dispatch` `reducer`] | The handler **says what the user did** | **One function** holds every rule
```

### What is at stake

The key idea is this: event handlers say what happened, the reducer says how the state changes in response, and React connects the two through `dispatch`.

What is at stake is what the user sees when one rule is wrong. Picture a cart where the Milk row suddenly shows minus one. If four handlers each hold their own rule for the cart, the developer must read all four to find the one that let the quantity drop below zero. React's docs put it this way: "When you have a bug with `useState`, it can be difficult to tell _where_ the state was set incorrectly, and _why_." With a reducer, every rule sits in one function, and one log line inside it shows every action the user caused, in order.

Readers usually go wrong in four places:
1. They think `useReducer` is a new kind of state, or state that the whole app shares. It is the state of one component, exactly as with `useState`. Sharing it with other components is Lesson 29.
2. They think `dispatch` changes the state at once. It asks React for the next render, exactly as a setter does in Lesson 15.
3. They put a side effect, such as an `alert`, inside the reducer, and the user sees it twice in development.
4. They think every component should now use a reducer. The docs answer: "You don't have to use reducers for everything: feel free to mix and match!"

### The page for this lesson: a shopping cart

Our page is the cart of a small food shop. It lists three items, each with its quantity. Every row has three buttons: `Add one`, `Remove one`, and `Delete`. Under the list sits an `Empty cart` button:

```page width=text caption="The cart when the page opens: three items, each with three buttons, and an Empty cart button under the list."
heading: Your cart
line: Apple: 1 [Add one] [Remove one] [Delete]
line: Bread: 2 [Add one] [Remove one] [Delete]
line: Milk: 1 [Add one] [Remove one] [Delete]
line: [Empty cart]
console: quiet
```

Each button changes the same cart in its own way:
1. A click on `Add one` in the Bread row raises Bread to `3`.
2. A click on `Remove one` in the Bread row lowers Bread to `1`. A second click takes the Bread row out of the cart, because a quantity of zero means the item leaves.
3. A click on `Delete` in the Apple row takes the Apple row out at once.
4. A click on `Empty cart` takes every row out and shows `Your cart is empty.`

```page width=text caption="The same cart after the user clicks Empty cart."
heading: Your cart
line: Your cart is empty. | good
line: [Empty cart]
console: quiet
```

The cart is one array of three objects, written above the component. Here is the component as we would write it today, with `useState` and four handlers, one for each button:

```jsx title="src/components/Cart.jsx" startLine="1"
import { useState } from 'react';

const initialCart = [
  { id: 0, name: 'Apple', quantity: 1 },
  { id: 1, name: 'Bread', quantity: 2 },
  { id: 2, name: 'Milk', quantity: 1 },
];

export default function Cart() {
  const [cart, setCart] = useState(initialCart);

  function ~handleIncrease~(id) { // Rule 1: a copy of the item with one more
    setCart(cart.map(item => item.id === id ? { ...item, quantity: item.quantity + 1 } : item));
  }

  function ~handleDecrease~(id) { // Rule 2: one less, and the row leaves at zero
    setCart(cart.map(item => item.id === id ? { ...item, quantity: item.quantity - 1 } : item).filter(item => item.quantity > 0));
  }

  function ~handleDelete~(id) { // Rule 3: every item except this one
    setCart(cart.filter(item => item.id !== id));
  }

  function ~handleEmpty~() { // Rule 4: no items at all
    setCart([]);
  }

  return (
    <section>
      <h1>Your cart</h1>
      {cart.length === 0 && <p>Your cart is empty.</p>}
      <ul>
        {cart.map(item => (
          <li key={item.id}>
            {item.name}: {item.quantity}
            <button onClick={() => handleIncrease(item.id)}>Add one</button>
            <button onClick={() => handleDecrease(item.id)}>Remove one</button>
            <button onClick={() => handleDelete(item.id)}>Delete</button>
          </li>
        ))}
      </ul>
      <button onClick={handleEmpty}>Empty cart</button>
    </section>
  );
}
```

Nothing here is new. Each handler uses `map`, `filter`, and a copy with `{ ...item }`, as Lessons 17 and 19 taught. The page works. But four rules for one array now sit in four handlers, and that is exactly the situation the docs describe: many state updates in many event handlers. Their answer: "For these cases, you can consolidate all the state update logic outside your component in a single function, called a _reducer._" To consolidate means to gather scattered pieces into one place.

By the end of the lesson, the project has these files:

```files title="food-cart: File Explorer" caption="How the files of our cart sit inside src/ and src/components/ at the end of the lesson."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it inside `<StrictMode>`
  App.jsx | parent | Exports `App` as default and renders `<Cart />`
  cartReducer.js | reducer | Exports `cartReducer` as default: every rule for the cart, from Principle 5
  components/

```

### Five Principles of useReducer

**PRINCIPLES:** React's docs move a component from `useState` to `useReducer` in three steps: the handlers dispatch actions, a reducer function holds the rules, and the component uses that reducer. The first three principles are those three steps. The last two say how to write a reducer well:
1. **Principle 1: dispatch Sends What the User Did**: Each handler stops working out the next cart. It calls `dispatch` with an object that says what the user just did.
2. **Principle 2: cartReducer Holds Every Rule for the Cart**: One function, written outside the component, takes the current cart and that object and returns the next cart.
3. **Principle 3: useReducer Hands Back the Cart and dispatch**: One line replaces the `useState` line. React calls the reducer on the next render and gives the component the cart it returned.
4. **Principle 4: An alert Inside cartReducer Pops Up Twice**: React calls the reducer during rendering, and twice in development, so the reducer may only compute the next cart.
5. **Principle 5: One emptied Action Clears the Whole Cart**: Each action is one thing the user did, even when it changes many things in the cart. Then a log in the reducer reads as the list of the user's clicks.

Here is the complete map of the five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Actions: Handlers Say What Happened** | When every handler holds its own rule, a wrong number on the page can come from any of them; interviewers ask what an action is and what goes in it. | In each event handler, call `dispatch` with an action object: a `type` that names what the user did, plus the smallest extra information the reducer needs. |
| **Principle 2** | **The Reducer: Current State and Action In, Next State Out** | A missing `return` or a forgotten field in one branch blanks the row or the whole page; a `default` that throws names a wrongly spelled type at once. | Write the reducer outside the component; give it one `case` for each action type, return the next state from each, and throw in `default`. |
| **Principle 3** | **useReducer: The State and dispatch** | Logging the state right after `dispatch` shows the old value, and many developers decide that `dispatch` failed. | Replace `useState` with `useReducer(reducer, initialState)`; React calls the reducer during the next render, and the running handler keeps the old value. |
| **Principle 4** | **Pure Reducers** | An `alert` or a mutation inside the reducer runs twice in development or leaves the page unchanged. | Keep the reducer pure: no side effects and no mutation. Put messages to the user in the event handler. |
| **Principle 5** | **One Action per User Interaction** | Actions named after data changes make the log unreadable; a reducer in its own file can be tested with no component at all. | Dispatch one action for each thing the user did, and let the reducer make every change that follows from it. |

## 1. Principle 1: `dispatch` Sends What the User Did

### Two handlers for the same button that look alike

Here are two handlers for the `Add one` button. Each one makes a single call:

```jsx title="The handler with setCart"
function handleIncrease(id) {
  ~setCart(cart.map(item => item.id === id ? { ...item, quantity: item.quantity + 1 } : item));~ // The next cart, worked out right here
}
```

```jsx title="The handler with dispatch"
function handleIncrease(id) {
  ~dispatch({ type: 'increased', id: id });~ // Only what the user did: increased the item with this id
}
```

**It may look the same, but it is NOT the same thing!** Both handlers make one call. The handler with `setCart` passes the next cart itself, so the rule for the next cart lives in the handler. The handler with `dispatch` passes a description of the click, and the next cart is worked out somewhere else, in Principle 2.

The word *dispatch* means to send something off to the place where it is handled, as a shop dispatches a parcel to the post office. The handler sends the description off. It does not handle it.

### The action: a plain object that says what happened

The object passed to `dispatch` is called an **action**. React's docs: "It is a regular JavaScript object. You decide what to put in it, but generally it should contain the minimal information about _what happened_." Our code writes it, right inside the handler.

By convention, the action has a `type` field, a string that names what happened. Any other information goes in other fields. In our cart, `type: 'increased'` names the click, and `id: 1` says which row the user clicked:

```jsx title="The action for a click on Add one in the Bread row"
dispatch({ ~type: 'increased'~, ~id: 1~ }); // type names what happened; id is the one extra fact the rule needs
```

The `id` comes from the button, exactly as before. The arrow `() => handleIncrease(item.id)` on each row passes that row's `id` to the handler, as Lesson 11 showed.

`dispatch` itself does not exist yet: nothing we have written creates it. React's docs write the handlers first and add `dispatch` "in a later step". Here that step is Principle 3, where `useReducer` gives `dispatch` to the component. Until then, the page does not run.

### The four handlers, before and after

Here are all four handlers of `Cart` with `dispatch`. Each one sends one action:

```jsx title="src/components/Cart.jsx" startLine="12"
function handleIncrease(id) {
  ~dispatch({ type: 'increased', id: id });~ // The user increased one item
}

function handleDecrease(id) {
  ~dispatch({ type: 'decreased', id: id });~ // The user decreased one item
}

function handleDelete(id) {
  ~dispatch({ type: 'deleted', id: id });~ // The user deleted one item
}

function handleEmpty() {
  ~dispatch({ type: 'emptied' });~ // The user emptied the cart: no id is needed
}
```

No `map`, no `filter`, and no empty array is left in any handler. The four rules have left the handlers. Principle 2 gives them their new home.

```tree caption="The four handlers of Cart: what each one held before, and the action each one sends now."
The handlers of `Cart`
- !Before, with `setCart` | Each handler works out **the next cart** | **Four rules** sit in **four handlers**
- +Now, with `dispatch` | Each handler sends **one action** | The actions are `increased`, `decreased`, `deleted`, and `emptied`
```

### Name the action after what the user did

Two names can produce the same cart and still not be the same thing. Compare these two actions for the `Add one` button:

```jsx title="An action named after the click, and one named after the change"
dispatch({ ~type: 'increased'~, id: 1 }); // Says what the user did
dispatch({ ~type: 'set_quantity'~, id: 1, quantity: 3 }); // Says how the state should change
```

Both can leave `Bread: 3` on the page. **It may look the same, but it is NOT the same thing!** The docs' advice: "action types should ideally describe 'what the user did' rather than 'how you want the state to change'. This makes it easier to later add more features." With `set_quantity`, the rule for the next quantity is back in the handler, which had to work out the `3`.

How long the name is does not matter. The docs: "The `type` is specific to a component, so in this example either `'added'` or `'added_task'` would be fine. Choose a name that says what happened!" In our cart, `'increased'` and `'increased_item'` would be the exact same thing.

The docs' own exercise shows the mistake that a wrong name hides. A chat page has a message box and a Send button. A developer clears the box on Send by reusing the action for typing:

```jsx title="Clearing a chat box on Send"
dispatch({ ~type: 'edited_message'~, message: '' }); // **WRONG:** says the user typed an empty message
dispatch({ ~type: 'sent_message'~ }); // Says the user clicked Send; the reducer empties the box
```

The box empties either way, so the first line seems right. But the action now says the user typed an empty message, when the user clicked Send. As the docs say: "From the user's perspective, sending a message is a different action than editing the field."

> [!PRINCIPLE]
> **Principle 1: Actions: dispatch Sends What the User Did**
>
> *In a component with a reducer, an event handler does not work out the next state; it calls `dispatch` with an action object that says what the user just did, with only the information the reducer needs.*
>
> When every handler holds its own rule for the next state, a wrong number on the page can come from any of them. With actions, the handler only reports the click: a `type` that names it, such as `'increased'`, and the `id` of the row. The rule for the next cart moves out of the handler.
>
> **DO THIS:**
> ```jsx
> function handleIncrease(id) {
>   ~dispatch({ type: 'increased', id: id })~; // Says what the user did
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleIncrease(id) {
>   ~dispatch({ type: 'set_quantity', id: id, quantity: 3 })~; // **WRONG:** the handler worked out the next quantity itself
> }
> ```

## 2. Principle 2: `cartReducer` Holds Every Rule for the Cart

### A reducer is a plain function you can call by hand

A **reducer** is a function that takes two inputs, the current state and an action, and returns the next state. It is plain JavaScript. It does not touch the page, and React is not involved yet. We can call one by hand:

```js title="A reducer called by hand, with no React at all"
function counterReducer(count, action) {
  if (action.type === 'incremented') {
    return count + 1;
  }
}

~counterReducer(0, { type: 'incremented' })~; // Returns 1
~counterReducer(5, { type: 'incremented' })~; // Returns 6
```

The state we pass in is called the **current state**, and the value the reducer returns is the **next state**. React's docs: "React will set the state to what you return from the reducer." That last part happens in Principle 3.

Why is it called a reducer? The name comes from the array method `reduce`, which walks through a list and folds it into one value. Here it adds five numbers:

```js title="The array method reduce adds five numbers"
[1, 2, 3, 4, 5].reduce((result, number) => ~result + number~); // Returns 15
```

The function passed to `reduce` "takes the _result so far_ and the _current item,_ then it returns the _next result._" A React reducer does the same with the state so far and the next action. As the docs put it: "In this way, they accumulate actions over time into state." The name does not mean that a reducer makes the code shorter. The docs: "Although reducers can 'reduce' the amount of code inside your component, they are actually named after the `reduce()` operation."

### The reducer of our cart

Our reducer takes the current cart as its first argument and the action as its second. It is named after its state, as the docs name theirs `tasksReducer`. The four rules that left the handlers in Principle 1 come back here, one for each action type:

```jsx title="src/components/Cart.jsx" startLine="47"
function cartReducer(cart, action) {
  ~switch (action.type)~ { // Compares the type with each case below
    case 'increased': {
      return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity + 1 } : item);
    }
    case 'decreased': {
      return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity - 1 } : item).filter(item => item.quantity > 0);
    }
    case 'deleted': {
      return cart.filter(item => item.id !== action.id);
    }
    case 'emptied': {
      return [];
    }
    ~default~: { // Runs when no case matches
      throw Error('Unknown action: ' + action.type);
    }
  }
}
```

`switch` is plain JavaScript. It takes one value, here `action.type`, compares it with each `case` from top to bottom, and runs the first one that matches. `default` runs when no `case` matches. React's docs give two small habits for each `case`. Wrap it in curly braces, so that variables declared in different cases do not clash. And end it with `return`, because the docs warn: "If you forget to `return`, the code will 'fall through' to the next `case`, which can lead to mistakes!"

`throw` is plain JavaScript too. It stops the function at once and reports an error in the Console. The docs end every reducer with this line, so a type that no `case` knows never passes silently.

`action.id` is the `id` that the handler wrote into the action in Principle 1. `cart` is the first parameter. In Principle 3, React passes the current cart into it, and the action that the handler gave to `dispatch`.

### A `switch` and if/else give the same reducer

The `switch` is only the docs' habit. Here is the same branch written with if/else:

```jsx title="Branching on action.type with switch, and with if/else"
switch (action.type) { case 'emptied': { ~return [];~ } } // switch: the docs' habit
if (action.type === 'emptied') { ~return [];~ } // if/else: the same branch
```

**Yes, it is the exact same thing!** The docs: "The result is the same, but it can be easier to read switch statements at a glance." And: "If you're not yet comfortable with switch statements, using if/else is completely fine."

### Why the reducer sits outside the component

We wrote `cartReducer` below `Cart`, not inside it. The reducer gets the cart as an argument, so it needs nothing from inside the component. The docs: "Because the reducer function takes state as an argument, you can **declare it outside of your component.** This decreases the indentation level and can make your code easier to read." A reducer inside `Cart` would return the exact same carts. Outside, it can later move to its own file, which Principle 5 does.

### The filter in `decreased` keeps the cart sane

The `decreased` rule ends with `.filter(item => item.quantity > 0)`. Compare the rule with it and without it:

```jsx title="The decreased rule with the filter, and without it"
return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity - 1 } : item).~filter(item => item.quantity > 0)~; // Milk at 1: the Milk row leaves the cart
return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity - 1 } : item); // **WRONG:** Milk at 1 shows Milk: 0, then Milk: -1 on the next click
```

Without the filter, the Milk row stays in the cart at zero, and the next click on `Remove one` shows minus one. That is the bug from the start of this lesson, and now there is exactly one place to look for it.

### Calling the reducer by hand changes nothing on the page

Since `cartReducer` is a plain function, we can call it ourselves and log what it returns:

```jsx title="src/components/Cart.jsx"
console.log(~cartReducer(initialCart, { type: 'emptied' })~); // Prints [] in the Console
```

The page still shows Apple, Bread, and Milk. Two facts explain it:
1. Nothing gave the result to React. Our code called the function and logged the answer, and React never saw it. Giving the result to React is Principle 3.
2. `initialCart` still holds three items. The reducer built a new array and changed nothing it was given.

### Two mistakes that a reducer makes easy to find

The first mistake is a branch that forgets to copy the old fields. Here the `increased` rule builds the new item with `quantity` only:

```jsx title="src/components/Cart.jsx" startLine="49"
case 'increased': {
  return cart.map(item => item.id === action.id ? ~{ quantity: item.quantity + 1 }~ : item); // **WRONG:** the new item has no id and no name
}
```

The user clicks `Add one` in the Bread row, and the Bread row loses its name:

```page width=text caption="After one click on Add one in the Bread row, with a rule that forgot to copy the old fields."
heading: Your cart
line: Apple: 1 [Add one] [Remove one] [Delete]
line: : 3 [Add one] [Remove one] [Delete] | bad
line: Milk: 1 [Add one] [Remove one] [Delete]
line: [Empty cart]
console: Each child in a list should have a unique "key" prop.
```

The new Bread object holds only `quantity`, so `item.name` is `undefined` and the row shows nothing before the colon. Its `id` is gone too, so the row's `key` is `undefined`, and React warns about the missing key. The docs' fix: "Make sure that every `case` branch **copies all of the existing fields** when returning the new state." Here that means `{ ...item, quantity: item.quantity + 1 }`.

The second mistake is a type that no `case` knows. A handler dispatches `'increase'`, while the reducer's case says `'increased'`. Without a `default`, no branch runs, the reducer returns `undefined`, and the next render fails when it calls `map` on `undefined`. The page breaks either way, but with the docs' `default`, the Console names the wrong type at once:

```devconsole caption="The Console after a click that dispatches the type increase, which no case of cartReducer knows."
x Uncaught Error: Unknown action: increase
```

```tree caption="What cartReducer does with an action: a known type returns the next cart, and an unknown type throws."
`cartReducer` receives the current cart and an action
- +A `case` matches the type [`increased` `decreased` `deleted` `emptied`] | Runs **one rule** | **Returns the next cart**
- !No `case` matches [`increase`] | `default` runs | **Throws** and names the **unknown type** in the Console
```

> [!PRINCIPLE]
> **Principle 2: The Reducer: cartReducer Holds Every Rule for the Cart**
>
> *A reducer is a function, declared outside the component, that takes the current state and an action and returns the next state, with one `case` for each action type and a `default` that throws for a type it does not know.*
>
> With every rule for the cart in one function, a wrong quantity has only one place to come from. The reducer is plain JavaScript: it gets everything it needs as arguments, so it lives outside the component, and calling it by hand changes nothing on the page. Each branch returns a whole new cart, with every old field copied.
>
> **DO THIS:**
> ```jsx
> function cartReducer(cart, action) {
>   switch (action.type) {
>     case 'emptied': {
>       ~return [];~ // Returns the next cart
>     }
>     default: {
>       throw Error('Unknown action: ' + action.type);
>     }
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function cartReducer(cart, action) {
>   switch (action.type) {
>     case 'emptied': {
>       ~cart = [];~ // **WRONG:** no return, so the reducer returns undefined and the next render breaks
>     }
>   }
> }
> ```

## 3. Principle 3: `useReducer` Hands Back the Cart and `dispatch`

### One line in place of one line

The third step changes a single line. Compare the line we had with the line that replaces it:

```jsx title="The state line with useState, and with useReducer"
const [cart, setCart] = ~useState(initialCart)~; // The current cart and a setter
const [cart, dispatch] = ~useReducer(cartReducer, initialCart)~; // The current cart and dispatch
```

**Yes, it is the exact same thing!** The docs: "The `useReducer` Hook is similar to `useState`: you must pass it an initial state and it returns a stateful value and a way to set state, in this case, the dispatch function."

What the two share: both take the initial cart, both give back the current cart on the left, and both give back a function React made on the right. The one difference: `useReducer` also takes the reducer, and the function it gives back takes an action instead of the next cart.

`useReducer` is a React Hook, imported from `'react'` like `useState`. It takes two arguments:
1. The reducer, here `cartReducer`.
2. The **initial state**, here `initialCart`. React saves it on the first render and ignores it on the next renders.

It returns two values: the current state, here `cart`, and the **`dispatch` function**. This is the `dispatch` that the handlers of Principle 1 have been calling. The reference: "The `dispatch` function returned by `useReducer` lets you update the state to a different value and trigger a re-render. You need to pass the action as the only argument to the `dispatch` function."

### The cart works again

In `Cart.jsx`, the import changes, and the state line changes. The handlers from Principle 1, the reducer from Principle 2, and the JSX stay as they are:

```jsx title="src/components/Cart.jsx" startLine="1"
import { ~useReducer~ } from 'react'; // In place of useState

const initialCart = [
  { id: 0, name: 'Apple', quantity: 1 },
  { id: 1, name: 'Bread', quantity: 2 },
  { id: 2, name: 'Milk', quantity: 1 },
];

export default function Cart() {
  const [cart, dispatch] = ~useReducer(cartReducer, initialCart)~; // cartReducer is the function below Cart
```

The page behaves exactly as it did with `useState`. One click on `Add one` in the Bread row shows `Bread: 3`:

```page width=text caption="The cart with useReducer after one click on Add one in the Bread row."
heading: Your cart
line: Apple: 1 [Add one] [Remove one] [Delete]

line: Milk: 1 [Add one] [Remove one] [Delete]
```

### What happens after one click on `Add one`

Our code never calls `cartReducer`. React calls it, during the next render. Here is the click in the order things happen:
1. The user clicks `Add one` in the Bread row. React runs the arrow on the button, which calls `handleIncrease(1)`.
2. `handleIncrease` calls `dispatch` with `{ type: 'increased', id: 1 }`. React puts the action in a queue. The docs: "Actions are queued until the next render."
3. The handler ends. Inside it, `cart` still holds `Bread: 2`.
4. React renders `Cart` again. During this render, `useReducer` calls `cartReducer` with the current cart and the action.
5. `useReducer` returns the array that `cartReducer` returned, and the Bread row shows `3`.

The reference sums it up: "React will pass the current state and the action to your reducer function. Your reducer will calculate and return the next state. React will store that next state, render your component with it, and update the UI."

```tree dir=right caption="One click on Add one: the handler sends an action, and React calls the reducer during the next render."
From a click to `Bread: 3`
- +1. The handler [`handleIncrease`] | Calls `dispatch` with **one action** | `cart` here still holds **`Bread: 2`**
- +2. React [`dispatch`] | Puts the action **in a queue** | Starts **a new render** of `Cart`
- +3. The reducer [`cartReducer`] | Called **by React** with the current cart and the action | Returns **the next cart**
- +4. The page | `useReducer` returns the next cart | The row shows **`Bread: 3`**
```

### `dispatch` does not change `cart` in the running handler

Suppose a developer wants to check the cart right after emptying it, and adds a log to `handleEmpty`:

```jsx title="src/components/Cart.jsx" startLine="24"
function handleEmpty() {
  dispatch({ type: 'emptied' });
  console.log(~cart.length~); // Prints 3: this render's cart still holds three items
}
```

The user clicks `Empty cart`, and the page shows `Your cart is empty.` Here is the Console:

```devconsole caption="The Console after one click on Empty cart, with a log of cart.length right after dispatch."
3 | Cart.jsx:26
```

`dispatch` did not fail. The reference: "Calling the `dispatch` function **does not change state in the running code**." This is the snapshot from Lesson 15: the handler belongs to the render that showed three items, and its `cart` stays that render's cart. The new cart arrives with the next render.

When the handler really needs the next cart, the docs call the reducer by hand, with the same two arguments React will use:

```jsx title="src/components/Cart.jsx" startLine="24"
function handleEmpty() {
  const action = { type: 'emptied' };
  dispatch(action);
  const nextCart = ~cartReducer(cart, action)~; // The cart the next render will show
  console.log(nextCart.length); // Prints 0
}
```

### `setCart` and `dispatch` take different things

The two functions sit in the same place in the code, but they are NOT the same thing. `setCart` receives the next cart. `dispatch` receives an action. If we passed an action to `setCart`, React would store the action object itself as the new cart, and the next render would call `map` on an object that has no `map`.

> [!PRINCIPLE]
> **Principle 3: useReducer: It Hands Back the Cart and dispatch**
>
> *`useReducer(cartReducer, initialCart)` takes the reducer and the initial state and returns the current state and the `dispatch` function; each call to `dispatch` makes React call the reducer during the next render, store what it returns, and show it.*
>
> The `useReducer` line takes the place of the `useState` line, and the page behaves the same. Our code never calls the reducer: React calls it with the current cart and the action. Because that happens in the next render, the handler that called `dispatch` still sees the old cart.
>
> **DO THIS:**
> ```jsx
> const [cart, dispatch] = ~useReducer(cartReducer, initialCart)~; // React calls cartReducer on the next render
>
> function handleEmpty() {
>   dispatch({ type: 'emptied' });
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleEmpty() {
>   dispatch({ type: 'emptied' });
>   ~if (cart.length > 0)~ { // **WRONG:** cart is still the old cart here, so this logs even though the cart was just emptied
>     console.log('Emptying failed');
>   }
> }
> ```

## 4. Principle 4: An `alert` Inside `cartReducer` Pops Up Twice

### One click, two pop-ups

Suppose we want to tell the user that the cart is empty. All the cart logic lives in the reducer now, so a developer puts the message there:

```jsx title="src/components/Cart.jsx" startLine="58"
case 'emptied': {
  ~alert('Cart emptied');~ // **WRONG:** a side effect inside the reducer
  return [];
}
```

The user clicks `Empty cart` once. In development, the pop-up `Cart emptied` appears, and right after the user closes it, the same pop-up appears again. Here is why, in order:
1. `handleEmpty` calls `dispatch` with `{ type: 'emptied' }`.
2. React renders `Cart` again and calls `cartReducer` with the action.
3. `<StrictMode>` in `src/main.jsx` makes React call `cartReducer` a second time, with the same cart and the same action.
4. Each call runs the `alert`.

The docs say it directly: "React will call your reducers multiple times in Strict Mode. This is why, if you put an alert in a reducer, it fires twice."

**Yes, it is the exact same thing** as Lesson 14 and Lesson 16! A reducer runs during rendering, like a component and like an updater function, so it must be pure. The docs: "Similar to state updater functions, reducers run during rendering! Actions are queued until the next render. This means that reducers must be pure: same inputs always result in the same output." A pure reducer is safe to call twice, because the second call returns the same cart and does nothing else.

### The message goes in the event handler

The handler runs once per click. The reference: "**Only component, initializer, and reducer functions need to be pure.** Event handlers don't need to be pure, so React will never call your event handlers twice." So the `alert` moves to `handleEmpty`, and the reducer only returns the empty cart:

```jsx title="The alert inside the reducer, and inside the event handler"
case 'emptied': { ~alert('Cart emptied');~ return []; } // **WRONG:** runs twice in development
function handleEmpty() { dispatch({ type: 'emptied' }); ~alert('Cart emptied');~ } // Runs once per click
```

It may look the same, since the same line runs after the same click, but it is NOT the same thing! The docs' own answer to this exact case: "The reducer should be a pure function, it should only calculate the next state. It should not 'do' anything, including displaying messages to the user. That should happen in the event handler."

The same goes for every other side effect. The docs' list: reducers "should not send requests, schedule timeouts, or perform any side effects, operations that impact things outside the component. They should update objects and arrays without mutations."

### A mutation inside the reducer

The second call also catches a reducer that changes the cart it was given. Here the `increased` rule changes the Bread object itself instead of copying it:

```jsx title="src/components/Cart.jsx" startLine="49"
case 'increased': {
  return cart.map(item => {
    if (item.id === action.id) {
      ~item.quantity = item.quantity + 1;~ // **WRONG:** changes the Bread object that the current cart holds
    }
    return item;
  });
}
```

The user clicks `Add one` in the Bread row once, and in development the row jumps from `Bread: 2` to `Bread: 4`:

```page width=text caption="After one click on Add one in the Bread row, with a rule that changes the Bread object in place, in development."
heading: Your cart
line: Apple: 1 [Add one] [Remove one] [Delete]
line: Bread: 4 [Add one] [Remove one] [Delete] | bad
line: Milk: 1 [Add one] [Remove one] [Delete]
line: [Empty cart]
console: quiet
```

Both calls of the reducer get the same current cart, which holds the same Bread object. The first call adds one to it, and the second call adds one to the same object again. The docs show the same effect with a list: "Because React calls your reducer function twice, you'll see the todo was added twice, so you'll know that there is a mistake." Strict Mode turns a hidden mistake into one the user can see in development.

A mutation can also freeze the page. Suppose the `deleted` rule removes the row with `splice` and then returns `cart`. The user clicks `Delete`, and the row stays. React compares the next cart with the current one by `Object.is`, as in Lesson 17, finds the very same array, and skips the render. The reference: "You mutated an existing `state` object and returned it, so React ignored the update."

```tree caption="Three kinds of reducer body: only the pure one shows the right cart once per click."
What the reducer does besides returning the next cart
- !A side effect [`alert`] | Runs **twice** in development | The user sees **two pop-ups** for one click
- !A mutation that returns a new array [`item.quantity = ...`] | Both calls change **the same item** | The row jumps **by two**
- !A mutation that returns the same array [`splice`] | `Object.is` finds **the same array** | **No change** on the page
- +Pure: only compute and return [`{ ...item }` `filter`] | Same cart and action give **the same next cart** | The right cart, **once per click**
```

The double call happens only in development. The reference: "This is development-only behavior and does not affect production." React keeps the result of one call and ignores the other. In production, React calls the reducer once per click, so the pop-up appears once and the mutated row moves by one. The mistake is still in the code, only hidden.

> [!PRINCIPLE]
> **Principle 4: Pure Reducers: An alert Inside cartReducer Pops Up Twice**
>
> *A reducer must be pure: the same state and action always give the same next state, with no side effects and no mutation, because React calls it during rendering and, in Strict Mode, twice in development.*
>
> The handler runs once, on the click. The reducer runs later, during rendering, and in development it runs twice. So the reducer may only compute and return the next cart. Messages to the user, requests, and timers belong in the event handler.
>
> **DO THIS:**
> ```jsx
> function handleEmpty() {
>   dispatch({ type: 'emptied' });
>   ~alert('Cart emptied');~ // Runs once per click
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> case 'emptied': {
>   ~alert('Cart emptied');~ // **WRONG:** the reducer runs twice in Strict Mode, so the pop-up appears twice
>   return [];
> }
> ```

## 5. Principle 5: One `emptied` Action Clears the Whole Cart

### Two ways to empty the cart

Here are two `Empty cart` handlers. Each one leaves `Your cart is empty.` on the page:

```jsx title="Emptying the cart with one emptied action, and with one deleted action per item"
dispatch({ ~type: 'emptied'~ }); // One action: the user clicked Empty cart
cart.forEach(item => dispatch({ ~type: 'deleted'~, id: item.id })); // Three actions: three deletes the user never clicked
```

`forEach` is plain JavaScript: it runs the arrow once for each item, so the second line sends three actions. **It may look the same, or work the same at first, but it is NOT the same thing!** The first line says what the user did: one click on `Empty cart`. The second says the user deleted Apple, Bread, and Milk one by one, which never happened.

The docs' rule: "Each action describes a single user interaction, even if that leads to multiple changes in the data." Their example: "if a user presses 'Reset' on a form with five fields managed by a reducer, it makes more sense to dispatch one `reset_form` action rather than five separate `set_field` actions."

### One click, two changes, one action

Our `decreased` rule already follows this. When the user clicks `Remove one` in the Milk row, the cart changes in two ways: Milk drops to zero, and the Milk row leaves. Yet the handler sends one action, and the reducer makes both changes. Compare that with a handler that sends two:

```jsx title="Removing the last Milk with one action, and with two"
dispatch({ ~type: 'decreased'~, id: 2 }); // The reducer lowers Milk and removes the row at zero
dispatch({ type: 'decreased', id: 2 }); ~dispatch({ type: 'deleted', id: 2 });~ // **WRONG:** the handler decides the row must go
```

The page ends up the same, but in the second line the rule "zero means the item leaves" has moved back into a handler. The first keeps the rule in the reducer, and the action says what the user did: one click on `Remove one`.

### A log in the reducer reads as the list of the user's clicks

When each action is one thing the user did, one log line inside the reducer shows every update and its reason. The docs: "With `useReducer`, you can add a console log into your reducer to see every state update, and _why_ it happened, due to which `action`. If each `action` is correct, you'll know that the mistake is in the reducer logic itself."

```jsx title="src/components/Cart.jsx" startLine="47"
function cartReducer(cart, action) {
  ~console.log(action);~ // Logs every action that reaches the reducer
  switch (action.type) {
```

The user clicks `Add one` in the Bread row, then `Empty cart`. In development, Strict Mode calls the reducer twice for each action, so each line appears twice:

```devconsole caption="The Console after a click on Add one in the Bread row and a click on Empty cart, with a log at the top of cartReducer, in development."
> {type: 'increased', id: 1} | Cart.jsx:48
> {type: 'increased', id: 1} | Cart.jsx:48
> {type: 'emptied'} | Cart.jsx:48
> {type: 'emptied'} | Cart.jsx:48
```

The log reads like the user's clicks: one increase, then one empty cart. If the handler had sent three `deleted` actions instead, the log would list three deletes that no one clicked, and the developer would hunt for a bug in the wrong place. The docs: "that log should be clear enough for you to reconstruct what interactions or responses happened in what order." The log line is for finding a bug. We remove it afterwards.

### The reducer in its own file

`cartReducer` needs nothing from `Cart`, so it can live in its own file. The docs: "If you want, you can even move the reducer to a different file." We move it to `src/cartReducer.js`, export it as default, and import it in `Cart.jsx`, as Lesson 05 showed:

```jsx title="src/cartReducer.js"
~export default~ function cartReducer(cart, action) { // Moved here from the bottom of Cart.jsx
  switch (action.type) {
```

```jsx title="src/components/Cart.jsx" startLine="1"
import { useReducer } from 'react';
import ~cartReducer~ from '../cartReducer.js'; // The reducer now comes from its own file
```

The page behaves exactly as before. The move also lets us test the reducer with no component and no click. The docs: "A reducer is a pure function that doesn't depend on your component. This means that you can export and test it separately in isolation." We write the state and the action by hand:

```js title="Testing cartReducer with no component"
import cartReducer from './cartReducer.js';

const result = ~cartReducer([{ id: 2, name: 'Milk', quantity: 1 }], { type: 'decreased', id: 2 })~; // One Milk, one decrease
console.log(result); // Prints []: the Milk row left the cart
```

```tree caption="Two ways to empty the cart: both leave the same empty cart, but only one action says what the user did."
Two ways to empty the cart
- +One `emptied` action [`dispatch` once] | Says **what the user did**: one click on `Empty cart` | The log shows **one line** for **one click**
- !One `deleted` action per item [`forEach` with `dispatch`] | Says the user deleted **three items** | The log shows **three deletes** that **no one clicked**
```

> [!PRINCIPLE]
> **Principle 5: One Action per Interaction: One emptied Action Clears the Whole Cart**
>
> *Each action describes one user interaction, even when the interaction leads to several changes in the data; then a log in the reducer reads as the list of what the user did, and the reducer can be tested on its own.*
>
> One click on `Empty cart` removes three rows, and one click on `Remove one` can lower a quantity and remove a row. Each is still one action. The reducer turns that action into every change it needs, so the rule stays in one place and the log matches the user's clicks.
>
> **DO THIS:**
> ```jsx
> function handleEmpty() {
>   ~dispatch({ type: 'emptied' })~; // One click, one action
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleEmpty() {
>   ~cart.forEach(item => dispatch({ type: 'deleted', id: item.id }))~; // **WRONG:** three actions the user never clicked
> }
> ```

`cartReducer` holds every rule for the cart:

```jsx title="src/cartReducer.js"
export default function cartReducer(cart, action) {
  switch (action.type) {
    case 'increased': {
      return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity + 1 } : item);
    }
    case ~'decreased'~: { // Principle 5: one action, two changes
      return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity - 1 } : item).filter(item => item.quantity > 0);
    }
    case 'deleted': {
      return cart.filter(item => item.id !== action.id);
    }
    case 'emptied': {
      ~return [];~ // Principle 4: only computes, no alert here
    }
    ~default~: { // Principle 2: an unknown type throws
      throw Error('Unknown action: ' + action.type);
    }
  }
}
```

`Cart` holds the state and sends one action from each handler:

```jsx title="src/components/Cart.jsx"
import { useReducer } from 'react';
import cartReducer from '../cartReducer.js';

const initialCart = [
  { id: 0, name: 'Apple', quantity: 1 },
  { id: 1, name: 'Bread', quantity: 2 },
  { id: 2, name: 'Milk', quantity: 1 },
];

export default function Cart() {
  const [cart, dispatch] = ~useReducer(cartReducer, initialCart)~; // Principle 3: the cart and dispatch

  function handleIncrease(id) {
    ~dispatch({ type: 'increased', id: id });~ // Principle 1: says what the user did
  }

  function handleDecrease(id) {
    dispatch({ type: 'decreased', id: id });
  }

  function handleDelete(id) {
    dispatch({ type: 'deleted', id: id });
  }

  function handleEmpty() {
    dispatch({ type: 'emptied' });
    ~alert('Cart emptied');~ // Principle 4: the side effect stays in the handler
  }

  return (
    <section>
      <h1>Your cart</h1>
      {cart.length === 0 && <p>Your cart is empty.</p>}
      <ul>
        {cart.map(item => (
          <li key={item.id}>
            {item.name}: {item.quantity}
            <button onClick={() => handleIncrease(item.id)}>Add one</button>
            <button onClick={() => handleDecrease(item.id)}>Remove one</button>
            <button onClick={() => handleDelete(item.id)}>Delete</button>
          </li>
        ))}
      </ul>
      <button onClick={handleEmpty}>Empty cart</button>

```

### How React calls the components and the reducer

When the page opens, React calls `App`, then `Cart`. On this first render, `useReducer` returns `initialCart` and does not call the reducer, because no action has been sent yet. After each click by the user, the handler sends one action, and React renders `Cart` again. During that render, React calls `cartReducer`, twice in development, and `Cart` returns the rows of the new cart:

```tree caption="The component tree of the cart, and when React calls cartReducer."
`App` [1. Called first] | **Root component** | Renders `<Cart />`
- +`Cart` [2. Called second, and again after every click] | **Owns `cart`** through `useReducer` | Each handler sends **one action** with `dispatch`
  - +`cartReducer` [Called by React during each re-render that has an action] | Gets **the current cart and the action** | Returns **the next cart**; twice in development
```

| Principle | What we write | What the page shows |
| :--- | :--- | :--- |
| **1. Actions** | Each handler calls `dispatch` with a `type` and the `id` | Nothing yet: `dispatch` does not exist until Principle 3 |

## For the Interview

> **The Interview Question:** When does state logic outgrow useState, and how does a reducer consolidate it?

### How to Answer Clearly in 30 Seconds

"State logic outgrows `useState` when many event handlers change the same state in different ways, so the rules for the next state are scattered across the component and a wrong value can come from any handler. A reducer gathers those rules into one function, outside the component. The move has three steps. First, each handler stops setting state and calls `dispatch` with an action, a plain object whose `type` says what the user did. Second, a reducer function takes the current state and the action and returns the next state, usually with a `switch` on `action.type` and a `default` that throws. Third, `useReducer(reducer, initialState)` replaces `useState` and returns the state and `dispatch`. React calls the reducer during the next render, so the reducer must be pure, and Strict Mode calls it twice in development to catch side effects. `useState` and `useReducer` are equivalent; the reducer only changes where the update logic lives, which makes it easier to log and to test on its own."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"When would you pick `useReducer` over `useState`?"**
   React's docs compare them on five points. Code size: "Generally, with `useState` you have to write less code upfront", while `useReducer` "can help cut down on the code if many event handlers modify state in a similar way." Readability: `useState` "is very easy to read when the state updates are simple", and "`useReducer` lets you cleanly separate the _how_ of update logic from the _what happened_ of event handlers." Debugging: one log line in the reducer shows every update and its action, "However, you have to step through more code than with `useState`." Testing: the reducer is a pure function, so you can check that it "returns a particular state for a particular initial state and action." Personal preference: "Some people like reducers, others don't. That's okay." The docs' recommendation: "We recommend using a reducer if you often encounter bugs due to incorrect state updates in some component, and want to introduce more structure to its code." Both can live in the same component. The state behind a reducer still belongs to one component; to share it with components further down, you pass `dispatch` down as a prop, or through context, which Lessons 28 and 29 cover.

2. **"Does `dispatch` change the state right away?"**
   No. "Calling the `dispatch` function **does not change state in the running code**." It puts the action in a queue, and React calls the reducer with the current state and that action during the next render, the same way it processes updater functions. A log of the state right after `dispatch` shows the old value, because the handler belongs to the render that is already on the screen. When you need the next value in the handler, call the reducer yourself: `const nextCart = cartReducer(cart, action)`. If the reducer returns the same object, as `Object.is` decides, React skips the re-render. `dispatch` also has a stable identity, so you will often see it left out of Effect dependencies, which later lessons cover. Like every Hook, `useReducer` must be called at the top level of the component. It also takes an optional third argument, an initializer function such as `createInitialState`, which React calls once to build the initial state; you pass the function itself, not the result of calling it.

3. **"Why must a reducer be pure, and why is it called a reducer?"**
   It must be pure because React calls it during rendering, not during the click. The docs: reducers "should not send requests, schedule timeouts, or perform any side effects", and "should update objects and arrays without mutations." In Strict Mode, React calls the reducer twice in development and keeps one result, so an `alert` inside it appears twice, and a mutation changes the same object twice. That double call happens only in development. Purity is also what lets you test the reducer on its own, with no component and no browser. The name comes from the array method `reduce`: its function takes the result so far and the next item and returns the next result, and a React reducer takes the state so far and the next action and returns the next state. When a reducer works on deeply nested objects, the Immer library offers `useImmerReducer`, which lets the reducer write changes on a `draft` while Immer builds the new copies.

```tree caption="Interview summary: useState and useReducer hold the same state; they differ in where the update logic lives."
`useState` vs. `useReducer` in an interview
- +`useState` [`setCart`] | Each handler **works out the next state** | Best when the **updates are simple**
- +`useReducer` [`dispatch` `cartReducer`] | Handlers **say what the user did**; one pure function **holds every rule** | Best when **many handlers** change one state, or update bugs keep coming back
```
