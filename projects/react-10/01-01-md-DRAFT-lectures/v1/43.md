## How the Post Button Knows the Form Is Submitting

### The comments under a photo post

Picture the comments under a photo post on Instagram. One comment is already there: `Great shot!`. Under it sit a box that says `Add a comment...` and a Post button.

```page caption="The comments under a photo post when the page opens: one comment, an empty box, and a Post button."
card: lines=Great shot! | input=Add a comment...
line: [Post]
```

The user types `Nice photo!` and clicks Post. For about one second, the button reads `Posting...`, and the user cannot click it:

```page caption="The same comments during the one-second wait after the user clicks Post."
card: lines=Great shot! | typed=Nice photo!
line: [Posting...] | good
```

Then `Nice photo!` appears under `Great shot!`. The box is empty again, and the button reads Post:

```page caption="The same comments after the wait: the new comment is in the list, and the box and the button are back to the start."
card: lines=Great shot!; Nice photo! | input=Add a comment...
line: [Post]
```

Every app with a comment box does this. Now look at it as the developer who builds it. In our code, the Post button is its own component. It sits inside another component, and that one sits inside the form. No line of our code tells the button that the form is sending a comment.

So how does the button know that the form is submitting right now? It asks the form. The button calls a Hook named `useFormStatus` and reads one value from it, `pending`. While the form above the button is submitting, `pending` is `true`. The rest of the time, it is `false`.

### What "pending" means

In everyday English, something is **pending** when it has started and is still waiting to finish, like a bank payment that your banking app marks as Pending. A form is pending in the same sense: the user has clicked Post, and the comment is on its way, but the answer has not come back yet.

```tree dir=right caption="The three moments of one comment, and the value of pending in each."
One click on Post, seen by the button
- +Before the click | The form is **not submitting** | `pending` is **`false`**: the button reads **Post**
- +During the one-second wait | The form is **submitting** the comment | `pending` is **`true`**: the button reads **Posting...** and cannot be clicked
- +After the answer comes back | The submission is **over** | `pending` is **`false`** again: the button reads **Post**
```

### What is at stake

The key idea to remember is this: **`useFormStatus` reads the status of the closest `<form>` above the component that calls it.** The form must be a parent of that component. A form in the same component does not count.

What is at stake is what the user sees when `pending` never becomes `true`:
1. The button keeps reading Post during the whole one-second wait, and the user can still click it.
2. The user sees no sign that the first click worked, so the user clicks again.
3. The same comment is posted twice, and the list shows `Nice photo!` two times.

Readers usually go wrong in one place. They call `useFormStatus` in the same component that renders the `<form>` tag, right next to it. There, `pending` stays `false` on every submit, and the Console shows no error. Principle 2 shows this mistake on our page.

### Context vs. useFormStatus: two ways to read a value from far above

You already know one way for a component deep in the tree to read a value without a prop from every component above it: context (as seen in Lesson 28). `useFormStatus` works the same way, with one difference:
- **With context**, our code writes the provider, and the component reads the closest provider above it.
- **With `useFormStatus`**, our code writes no provider. The `<form>` tag plays that part, and the component reads the closest form above it.

React's blog says it in one sentence: "`useFormStatus` reads the status of the parent `<form>` as if the form was a Context provider."

```tree caption="Context and useFormStatus both let a deep component read a value from above; only who provides the value differs."
Two ways a deep component reads a value without props from every layer
- +Context | **Our code** writes the provider | The component reads the **closest provider above it**
- +`useFormStatus` | **The `<form>` tag** plays the provider | The component reads the **closest form above it**
```

### Three ways to tell the button that the form is submitting

Developers choose between three ways to give a submit button the form's pending state:
1. **Pass `isPending` down as a prop.** The component that owns the form already has `isPending` from `useActionState` (as seen in Lesson 42), and it hands that value down. React's own `useActionState` page does this when it writes `<Total quantity={count} isPending={isPending}/>`. This fits when the button sits one level below the form's owner.
2. **Make a context by hand.** Our code creates a context and provides the pending flag (as seen in Lesson 28). This fits a status that is not a form submission.
3. **Call `useFormStatus` in the button component.** This fits a button or a box rendered anywhere inside a `<form>`, at any depth, and a button that many forms reuse.

React's blog explains why the third way exists: "This can be done via Context, but to make the common case easier, we've added a new hook `useFormStatus`."

```tree caption="Three ways to give a submit button the pending state of its form, and when each one fits."
Three ways to tell the button that the form is submitting
- +1. A prop from the form's owner [`isPending={isPending}`] | The owner hands `isPending` down | Fits a button **one level below** the owner
- +2. A context made by hand [`<PendingContext value={isPending}>`] | Our code writes the provider | Fits a status that is **not a form submission**
- +3. `useFormStatus` in the button [`const { pending } = useFormStatus`] | The button asks the **form above it** | Fits a button **at any depth** inside a form
```

The file `src/api.js` stands in for a real server. It waits one second so that the pending state stays on the screen long enough to see it:

```js title="src/api.js"

  await new Promise(resolve => setTimeout(resolve, ~1000~)); // Waits one second, like a slow server
  return { id: nextId++, text };
}
```

The file `src/CommentSection.jsx` owns the list and the form. It stays the same in every principle, except where a principle shows a broken or older version of it:

```jsx title="src/CommentSection.jsx"
import { useActionState } from 'react';
import { saveComment } from './api.js';
import CommentFooter from './CommentFooter.jsx';

  const comment = await saveComment(formData.get('comment'));
  return [...previousComments, comment];

  const [comments, postAction] = useActionState(addComment, [{ id: 0, text: 'Great shot!' }]);

```

The form renders `CommentFooter`, and `CommentFooter` renders `PostButton`. So `CommentFooter` is the component in the middle, between the form and the button.

### Four Principles of useFormStatus

**PRINCIPLES:** A component inside a form can ask that form whether it is submitting. It calls `useFormStatus`, and React DOM, the part of React that works with the browser page, answers from the closest form above it. Four practical rules follow:
1. **Principle 1: `useFormStatus` Gives the Post Button `pending`**: The button calls `useFormStatus` from `'react-dom'` and reads `pending`. Our code never sets `pending`: React DOM makes it `true` while the form submits and `false` after.
2. **Principle 2: `pending` Stays `false` Next to the `form` Tag**: The Hook reads only a form above the component that calls it. In the component that renders the `<form>` tag itself, `pending` never becomes `true`, and nothing warns you.
3. **Principle 3: `CommentFooter` Passes No `pending` Prop**: The Hook reaches the form through any number of components in between, so the components in the middle no longer carry a prop they never use.
4. **Principle 4: `data` Shows the Comment Being Posted**: The same Hook also returns `data`, the form data being submitted right now, so a component inside the form can show what the user just sent. Before the first submit, `data` is `null`.

Here is the complete map of those four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`useFormStatus` Gives the Post Button `pending`** | The import comes from `'react-dom'`, not `'react'`, and interviewers ask where the value of `pending` comes from when no prop brings it. | Call `useFormStatus` in a component rendered inside the form and read `pending` from the object it returns. |
| **Principle 2** | **`pending` Stays `false` Next to the `form` Tag** | The Hook in the form's own component leaves the button clickable during the wait with no error, so the user can post the same comment twice. | Call `useFormStatus` in a component that sits inside the `<form>`, never in the component that renders the `<form>` tag. |
| **Principle 3** | **`CommentFooter` Passes No `pending` Prop** | A `pending` prop must pass through every component in the middle, and one forgotten prop leaves the button stuck on Post. | Let the button read the form's status itself, so the components between the form and the button pass nothing. |
| **Principle 4** | **`data` Shows the Comment Being Posted** | `data` holds the submitted form data only during a submission, and reading it with no check crashes the first render. | Read `data` from the same Hook and check that it is not `null` before calling `data.get`. |

## 1. Principle 1: `useFormStatus` Gives the Post Button `pending`

### The smallest code: a button that asks its form

Here is the whole idea in the fewest lines. A small `Submit` component calls `useFormStatus`, and the form renders it:

```jsx title="A button that asks its form with useFormStatus"
import { useFormStatus } from 'react-dom';

function Submit() {
  const { ~pending~ } = useFormStatus(); // true while the form above is submitting
  return <button type="submit" disabled={pending}>Submit</button>;
}

<form action={action}>
  ~<Submit />~ {/* Submit is inside the form, so this form is its parent */}
</form>
```

Nobody gives `Submit` a value. The form does not pass `pending` as a prop. `Submit` asks the form it sits in, and the form answers.

### What useFormStatus returns

`useFormStatus` is a Hook that gives you "status information of the last form submission", in the words of React's docs. React DOM provides it. It takes no parameters, so there is no way to name a form: it always reads the form above the component.

It returns one object, which the docs call the status object. That object holds four properties: `pending`, `data`, `method`, and `action`. The curly braces in `const { pending } = useFormStatus();` take out `pending` by name (as seen in Lesson 8). This lesson uses two of the four: `pending` here, and `data` in Principle 4.

The docs define `pending` in two sentences: "If `true`, this means the parent `<form>` is pending submission. Otherwise, `false`."

```tree caption="The one object useFormStatus returns, and the four properties inside it."
The status object that `useFormStatus` returns
- +`pending` | `true` while the parent form **is submitting** | `false` the rest of the time
- +`data` | The **form data** the parent form is submitting | `null` when **nothing is being submitted**
- +`method` | The form's method, **`'get'`** or **`'post'`** | Rarely needed in a component
- +`action` | The **function** passed to the form's `action` prop | Rarely needed in a component
```

### Import it from 'react-dom', not from 'react'

Every Hook so far came from `'react'`: `useState`, `useActionState`, and the rest. `useFormStatus` does not. It comes from `'react-dom'`, the package that connects React to the browser page (as seen in Lesson 7):

```jsx title="The two import lines a developer might write"
import { ~useFormStatus~ } from 'react'; // **WRONG:** 'react' has no useFormStatus, so the page fails with an error
import { ~useFormStatus~ } from 'react-dom'; // The right package: React DOM provides this Hook
```

Why does it live in `'react-dom'`? Because a `<form>` exists only on a web page. React's docs list `useFormStatus` among the Form Hooks of React DOM, and they work only in web applications that run in the browser. They are not supported in apps for iOS, Android, or Windows.

### Our Post button reads pending

Now we bring the idea into our comment page. `PostButton` calls `useFormStatus` and reads `pending`:

```jsx title="src/PostButton.jsx"
import { useFormStatus } from 'react-dom';

export default function PostButton() {
  const { ~pending~ } = useFormStatus(); // Comes from the form above, not from a prop
  return (
    <button type="submit" ~disabled={pending}~> {/* The user cannot click while the comment is on its way */}
      {pending ? 'Posting...' : 'Post'}
    </button>
  );
}
```

`CommentFooter`, the component in the middle, renders the button and nothing else:

```jsx title="src/CommentFooter.jsx"
import PostButton from './PostButton.jsx';

export default function CommentFooter() {
  return (
    <div>
      ~<PostButton />~ {/* No pending prop: the button asks the form itself */}
    </div>
  );
}
```

And `App` renders the comment section:

```jsx title="src/App.jsx"
import CommentSection from './CommentSection.jsx';

export default function App() {
  return <CommentSection />;
}
```

### What happens when the user clicks Post

The user types `Nice photo!` and clicks Post. Our code never writes `pending`, and no prop reaches `PostButton`. Still, the button reads `Posting...` for one second and cannot be clicked. Here is what happens, in order:
1. The user clicks Post. The button has `type="submit"`, so the click submits the form (as seen in Lesson 11).
2. React DOM starts the form's action, `postAction`. The form is now pending, so React DOM gives `PostButton` a `pending` of `true`. React renders the button again, and it reads `Posting...` and turns off.
3. `addComment` waits one second for `saveComment`, then returns the list with `Nice photo!` added.
4. The submission is over. `pending` goes back to `false`, the button reads Post again, and React empties the box (as seen in Lesson 41).

```page caption="The comments during the one-second wait: the button reads Posting... and cannot be clicked."
card: lines=Great shot! | typed=Nice photo!
line: [Posting...] | good
console: quiet
```

```page caption="The comments after the wait: Nice photo! is in the list, the box is empty, and the button reads Post."
card: lines=Great shot!; Nice photo! | input=Add a comment...
line: [Post]
console: quiet
```

Open the Elements panel during the wait, and you see the `disabled` attribute that `disabled={pending}` puts on the real button:

```dom caption="The Elements panel during the one-second wait: the button inside the row of CommentFooter carries the disabled attribute."
<div>
+ <button type="submit" disabled>Posting...</button> | note: disabled while pending is true
</div>
```

```tree dir=right caption="Where the value of pending comes from: React DOM fills it from the form, and the button only reads it."
How `pending` reaches `PostButton`
- +1. The user clicks Post [`type="submit"`] | The click **submits the form**
- +2. React DOM marks the form as submitting | The form above `PostButton` is **pending**
- +3. `PostButton` asks the form [`useFormStatus`] | `pending` is **`true`**: the button reads **Posting...** and turns off
- +4. The Action finishes | `pending` is **`false`**: the button reads **Post** again
```

> [!PRINCIPLE]
> **Principle 1: `useFormStatus`: A Component Inside a Form Asks the Form for `pending`**
>
> *Call `useFormStatus` from `'react-dom'` in a component rendered inside a `<form>`, and read `pending`, which is `true` while that form is submitting.*
>
> A submit button often needs to know that its form is sending something, so it can turn off and say so. No prop has to bring that value. The button calls `useFormStatus`, React DOM looks at the form above the button, and `pending` tells the button whether that form is submitting right now. The Hook comes from `'react-dom'`, because forms exist only on a web page.
>
> **DO THIS:**
> ```jsx
> import { useFormStatus } from 'react-dom';
>
> function PostButton() {
>   const { ~pending~ } = useFormStatus(); // true while the form above is submitting
>   return <button type="submit" disabled={pending}>{pending ? 'Posting...' : 'Post'}</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import { ~useFormStatus~ } from 'react'; // **WRONG:** 'react' has no useFormStatus, so the page fails
>
> function PostButton() {
>   const { pending } = useFormStatus();
>   return <button type="submit" disabled={pending}>{pending ? 'Posting...' : 'Post'}</button>;
> }
> ```

## 2. Principle 2: `pending` Stays `false` Next to the `form` Tag

### The same Hook line in two places

Here are two components. Both call `useFormStatus` with the exact same line. The one difference is where the `<form>` tag is: inside the component's own return, or above the component:

```jsx title="The same Hook line, next to the form tag and inside the form"
function Form() {
  const { ~pending~ } = useFormStatus(); // **WRONG:** this component renders the form, so pending is never true
  return <form action={submit}></form>;
}

function Submit() {
  const { ~pending~ } = useFormStatus(); // Submit is rendered inside the form, so pending is true while it submits
  return <button disabled={pending}>Submit</button>;
}
```

It may look the same, but it is NOT the same thing! The Hook line is identical, and both components have a form on the page. But `useFormStatus` looks only **above** the component that calls it:
- **In `Form`**, the `<form>` tag is in the component's own return, so it sits below `Form`, not above it. The Hook finds no form, and `pending` stays `false`.
- **In `Submit`**, the `<form>` tag sits above `Submit`, because the form renders `<Submit />`. The Hook finds that form, and `pending` is `true` while it submits.

React's docs call the form above the component the **parent `<form>`**: "The `useFormStatus` Hook must be called from a component that is rendered inside a `<form>`." And they say exactly what happens otherwise: `useFormStatus` "will only return status information for a parent `<form>`. It will not return status information for any `<form>` rendered in that same component or children components."

```tree caption="useFormStatus next to the form tag vs. inside the form: the same line of code, two different results."
Where the component that calls `useFormStatus` sits
- !Next to the `<form>` tag [`function Form`] | The form is in the component's **own return**, below it | `pending` is **always `false`**
- +Inside the `<form>` [`function Submit`] | The form is **above** the component | `pending` is **`true`** while the form submits
```

### The mistake on our comment page

Suppose a developer learns `useFormStatus` and adds it to the component that already has the form, `CommentSection`. The button is written right inside the form:

```jsx title="src/CommentSection.jsx, with useFormStatus next to the form tag" startLine="10"
export default function CommentSection() {
  const [comments, postAction] = useActionState(addComment, [{ id: 0, text: 'Great shot!' }]);
  const { ~pending~ } = useFormStatus(); // **WRONG:** CommentSection renders the form, so pending stays false
  return (
    <section>
      <ul>
        {comments.map(comment => <li key={comment.id}>{comment.text}</li>)}
      </ul>
      <form action={postAction}>
        <input name="comment" placeholder="Add a comment..." />
        <button type="submit" disabled={pending}>
          {pending ? 'Posting...' : 'Post'}
        </button>
      </form>
    </section>
  );
}
```

**Beware! With the Hook next to the form tag, the button never changes, and the user can post the same comment twice.** Here is what the user meets:
1. The user types `Nice photo!` and clicks Post.
2. The button keeps reading Post, and the user can still click it during the whole second.
3. The user sees no sign that the click worked, so the user clicks Post again. The box still holds `Nice photo!`, because React empties it only after the Action finishes (as seen in Lesson 41).
4. The second click submits the same text again, and `Nice photo!` appears twice in the list.

```page caption="The broken page during the one-second wait: the button still reads Post and can be clicked again."
card: lines=Great shot! | typed=Nice photo!
line: [Post] | bad
console: quiet
```

```page caption="The broken page after the user clicked Post twice: the same comment is posted two times."
card: lines=Great shot!; Nice photo!; Nice photo! | input=Add a comment... | bad=lines
line: [Post]
console: quiet
```

The Console stays quiet. React's docs give no error message for this case. They only warn: "`pending` will never be true". In the Elements panel, the button never gets the `disabled` attribute.

Many developers then give up on the Hook and add a `useState` flag by hand, set before the request and cleared after it. There is no need. The docs give the fix: "call `useFormStatus` from inside a component that is located inside `<form>`". On our page, that component is `PostButton`, exactly as Principle 1 wrote it.

### The form's owner already has its own flag

The component that renders the form has a second option. When `CommentSection` itself needs to know that the form is pending, it does not need `useFormStatus` at all. It already gets `isPending` from `useActionState` (as seen in Lesson 42). The rule for the owner and the rule for the children fit together:
- **The form's owner**, `CommentSection`, reads `isPending` from `useActionState`.
- **A component inside the form**, such as `PostButton`, reads `pending` from `useFormStatus`.

The same rule holds for context: a provider in the same component does not count, only one above it (as seen in Lesson 28).

> [!PRINCIPLE]
> **Principle 2: Parent Form: `useFormStatus` Reads Only a Form Above the Component**
>
> *Call `useFormStatus` in a component rendered inside the `<form>`; in the component that renders the `<form>` tag, `pending` is never `true`.*
>
> The Hook looks only above the component that calls it. A form in the component's own return sits below it, so the Hook does not see that form, and `pending` stays `false` on every submit. Nothing in the Console says why. On the page, the button stays clickable during the wait, and the user can post the same comment twice.
>
> **DO THIS:**
> ```jsx
> function PostButton() {
>   const { ~pending~ } = useFormStatus(); // PostButton sits inside the form, so pending works
>   return <button type="submit" disabled={pending}>Post</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function CommentSection() {
>   const { ~pending~ } = useFormStatus(); // **WRONG:** this component renders the form, so pending stays false
>   return <form action={postAction}><button type="submit" disabled={pending}>Post</button></form>;
> }
> ```

## 3. Principle 3: `CommentFooter` Passes No `pending` Prop

### The middle component with a pending prop vs. without one

Here is `CommentFooter`, the component in the middle, written two ways:

```jsx title="CommentFooter with a pending prop, and CommentFooter with useFormStatus in the button"
function CommentFooter({ ~pending~ }) { // Receives pending only to hand it on
  return <PostButton pending={pending} />;
}

function CommentFooter() { // Mentions no pending at all
  return ~<PostButton />~; // PostButton asks the form itself
}
```

Both versions give the user the same button. In both, the form's submission decides what the button shows. The one difference is in the middle: with the prop, `CommentFooter` receives `pending` and never uses it. With `useFormStatus` in the button, `CommentFooter` does not mention it.

### The whole page with a pending prop

To see the difference on our page, here is the older way, before `useFormStatus`. `CommentSection` takes `isPending` from `useActionState` and passes it down:

```jsx title="src/CommentSection.jsx, with a pending prop" startLine="10"
export default function CommentSection() {
  const [comments, postAction, ~isPending~] = useActionState(addComment, [{ id: 0, text: 'Great shot!' }]); // true while addComment runs
  return (
    <section>
      <ul>
        {comments.map(comment => <li key={comment.id}>{comment.text}</li>)}
      </ul>
      <form action={postAction}>
        <input name="comment" placeholder="Add a comment..." />
        ~<CommentFooter pending={isPending} />~ {/* 1. The owner hands the flag down */}
      </form>
    </section>
  );
}
```

`CommentFooter` receives the prop and hands it on:

```jsx title="src/CommentFooter.jsx, with a pending prop"
import PostButton from './PostButton.jsx';

export default function CommentFooter({ pending }) {
  return (
    <div>
      ~<PostButton pending={pending} />~ {/* 2. The middle component only passes it through */}
    </div>
  );
}
```

And `PostButton` reads it as a prop:

```jsx title="src/PostButton.jsx, with a pending prop"
export default function PostButton({ ~pending~ }) { // 3. The button finally uses it
  return (
    <button type="submit" disabled={pending}>
      {pending ? 'Posting...' : 'Post'}
    </button>
  );
}
```

For the user, "Yes, it is the exact same thing!" The button reads `Posting...` for the same second, turns off in the same way, and reads Post again after the answer. `isPending` from `useActionState` is `true` while the Action runs, and `pending` from `useFormStatus` is `true` while the form submits that same Action.

```tree caption="A pending prop and useFormStatus give the same button; only the component in the middle changes."
Two ways the Post button gets the form's pending state
- +With a `pending` prop [`<CommentFooter pending={isPending} />`] | `CommentFooter` **receives `pending` and only hands it on** | The button reads **Posting...** during the wait
- +With `useFormStatus` [`<CommentFooter />`] | `CommentFooter` **mentions no `pending`** | **Exact same button**: it reads **Posting...** during the wait
```

Passing a value through components that do not use it is **prop drilling** (as seen in Lesson 28). React's docs describe the cost: "passing props can become verbose and inconvenient when you need to pass some prop deeply through the tree". Here the prop is `pending`, and `CommentFooter` carries it only for the button.

### One more component in the middle

The difference shows up the day the page changes. Suppose a developer wraps the Post button in a new row component, `CommentActions`, to place an emoji button next to it later. With the prop version, the new component must also receive `pending` and hand it on. The developer forgets:

```jsx title="src/CommentFooter.jsx, with a pending prop and one more component in the middle"
export default function CommentFooter({ pending }) {
  return (
    <div>
      ~<CommentActions />~ {/* **WRONG:** pending is not handed on, so PostButton reads Post forever */}
    </div>
  );
}

function CommentActions({ pending }) {
  return <PostButton pending={pending} />;
}
```

`PostButton` now receives no `pending`. The button never turns off, and the user can post twice again, as in Principle 2.

With `useFormStatus` in the button, the same change needs nothing else. The button still sits inside the same `<form>`, now two components down, and it still asks that form:

```jsx title="src/CommentFooter.jsx, with useFormStatus in the button and one more component in the middle"
export default function CommentFooter() {
  return (
    <div>
      <CommentActions />
    </div>
  );
}

function CommentActions() {
  return ~<PostButton />~; // Still inside the form, so useFormStatus still finds it
}
```

React's docs ask only that the component is "rendered inside a `<form>`". They set no limit on how many components sit in between.

### Why the button is its own component

Real teams write one submit button and reuse it in every form of the app: the comment box, the sign-up form, the settings page. React's blog calls such a reusable piece a **design component**, and names this exact case: "In design systems, it's common to write design components that need access to information about the `<form>` they're in, without drilling props down to the component."

`useFormStatus` reads only the form's submission. Any other value that many components share still needs props or context (as seen in Lesson 28).

> [!PRINCIPLE]
> **Principle 3: No Prop Drilling: The Components in the Middle Pass Nothing**
>
> *Let the component that needs the form's status call `useFormStatus` itself, so the components between the form and that component pass no `pending` prop.*
>
> With a `pending` prop, every component between the form and the button must receive the prop and hand it on, even though it never uses it. One forgotten prop leaves the button stuck on Post. With `useFormStatus` in the button, the button asks the form directly, through any number of components in the middle, and the user sees the exact same button.
>
> **DO THIS:**
> ```jsx
> function CommentFooter() {
>   return <div>~<PostButton />~</div>; // No pending prop: PostButton calls useFormStatus
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function CommentFooter({ pending }) {
>   return <div>~<CommentActions />~</div>; // **WRONG:** pending is dropped here, so the button never turns off
> }
> ```

## 4. Principle 4: `data` Shows the Comment Being Posted

### The smallest code: reading what the form is sending

The status object holds a second useful property, `data`. A component inside the form reads it the same way:

```jsx title="Reading data from useFormStatus"
const { ~data~ } = useFormStatus(); // The form data being submitted, or null

{~data &&~ <p>Posting "{data.get('comment')}"...</p>} {/* Shows the line only during a submission */}
```

The docs define `data` like this: "An object implementing the `FormData interface` that contains the data the parent `<form>` is submitting. If there is no active submission or no parent `<form>`, it will be `null`."

So `data` is the same kind of object as the `formData` that our action receives (as seen in Lesson 40), and you read it the same way, with `.get` and the box's `name`:
- **With `formData.get('comment')` in `addComment`**, the action reads the text that the user sent.
- **With `data.get('comment')` in a component inside the form**, the screen reads that same text while it is on its way.

Yes, it is the exact same thing! Both read the form data of the same submission, so both give `Nice photo!`. The only difference is the place: one runs inside the action, the other inside a component on the screen.

### A line under the box while the comment is on its way

Now we use `data` on our page. `CommentFooter` shows a line with the text being posted, above the button:

```jsx title="src/CommentFooter.jsx"
import { useFormStatus } from 'react-dom';
import PostButton from './PostButton.jsx';

export default function CommentFooter() {
  const { ~data~ } = useFormStatus(); // CommentFooter is inside the form too
  return (
    <div>
      {~data &&~ <p>Posting "{data.get('comment')}"...</p>} {/* Only while the form submits */}
      <PostButton />
    </div>
  );
}
```

`PostButton`, `CommentSection`, and `api.js` do not change. Here is the page through one comment:
1. Before the first submit, `data` is `null`, so no line shows under the box.
2. The user types `Nice photo!` and clicks Post.
3. During the wait, the line `Posting "Nice photo!"...` appears under the box, and the button reads `Posting...`.
4. When the submission ends, `data` is `null` again, and the line disappears.


```page caption="The finished page during the wait: a line shows the comment being posted, and the button reads Posting..."
card: lines=Great shot! | typed=Nice photo!

console: quiet
```


The line shows only what is being sent. It does not put the new comment in the list early: showing the comment in the list before the server answers is the job of `useOptimistic` (Lesson 44).

### Reading data before the first submit

A developer who sees `data` work during the wait may drop the check and write the line directly:

```jsx title="src/CommentFooter.jsx, reading data with no check" startLine="7"
      <p>Posting "{~data.get('comment')~}"...</p> {/* **WRONG:** data is null on the first render, so this throws */}
```

The page breaks before the user can type a letter. On the first render, nothing is being submitted, so `data` is `null`, and `null` has no `get`. The browser throws an error, and React removes the whole page:

```page caption="The page with data.get and no check: the first render throws, and nothing is left on the page."
blank
console: Uncaught TypeError: Cannot read properties of null (reading 'get')
  error: An error occurred in the <CommentFooter> component. Consider adding an error boundary to your tree to customize error handling behavior.
```

The fix is the check from our finished file: show the line only when `data` is there, with `{data && ...}`. React's docs write the same check as a ternary, `data ? ... : ''`.

> [!PRINCIPLE]
> **Principle 4: `data`: The Form Data Being Submitted, or `null`**
>
> *Read `data` from `useFormStatus` to show what the parent form is submitting, and check that `data` is not `null` before you call `data.get`.*
>
> While the form submits, `data` holds the same form data that the action receives, so a component inside the form can show the user's text on the screen. The rest of the time, `data` is `null`. Calling `data.get` on the first render, before any submit, throws an error and empties the page.
>
> **DO THIS:**
> ```jsx
> const { data } = useFormStatus();
> return <div>{~data &&~ <p>Posting "{data.get('comment')}"...</p>}</div>; // The line shows only during a submission
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const { data } = useFormStatus();
> return <div><p>Posting "{~data.get('comment')~}"...</p></div>; // **WRONG:** data is null before the first submit, so this throws
> ```

## Putting All Four Principles Together

### The complete project

Here are all five files of the finished comment page. The form lives in `CommentSection`. Both `CommentFooter` and `PostButton` sit inside it, and both ask it for its status:

```js title="src/api.js"
let nextId = 1;

export async function saveComment(text) {
  await new Promise(resolve => setTimeout(resolve, 1000));
  return { id: nextId++, text };
}
```

```jsx title="src/App.jsx"
import CommentSection from './CommentSection.jsx';

export default function App() {
  return <CommentSection />;
}
```

```jsx title="src/CommentSection.jsx"
import { useActionState } from 'react';
import { saveComment } from './api.js';
import CommentFooter from './CommentFooter.jsx';

async function addComment(previousComments, formData) {
  const comment = await saveComment(formData.get('comment'));
  return [...previousComments, comment];
}

export default function CommentSection() {
  const [comments, postAction] = useActionState(addComment, [{ id: 0, text: 'Great shot!' }]);
  return (
    <section>
      <ul>
        {comments.map(comment => <li key={comment.id}>{comment.text}</li>)}
      </ul>
      ~<form action={postAction}>~ {/* The parent form of CommentFooter and PostButton */}
        <input name="comment" placeholder="Add a comment..." />
        <CommentFooter />
      </form>
    </section>
  );
}
```

```jsx title="src/CommentFooter.jsx"
import { useFormStatus } from 'react-dom';
import PostButton from './PostButton.jsx';

export default function CommentFooter() {
  const { ~data~ } = useFormStatus(); // Principle 4: the text being posted, or null
  return (
    <div>
      {data && <p>Posting "{data.get('comment')}"...</p>}
      ~<PostButton />~ {/* Principle 3: no pending prop */}
    </div>
  );
}
```

```jsx title="src/PostButton.jsx"
import { ~useFormStatus~ } from 'react-dom'; // Principle 1: from react-dom, not react

export default function PostButton() {
  const { ~pending~ } = useFormStatus(); // Principle 2: called inside the form, so pending works
  return (
    <button type="submit" disabled={pending}>
      {pending ? 'Posting...' : 'Post'}
    </button>
  );
}
```

### How React calls the components in order

When the page loads, React calls `App` first, then `CommentSection`, then `CommentFooter` inside the form, then `PostButton` inside `CommentFooter`. During a submit, React calls `CommentFooter` and `PostButton` again, because the form's status changed:

```tree caption="The component tree of the comment page, the order in which React calls each component, and where each one reads the form's status."
`App` [1. Called first] | Renders `<CommentSection />`
- +`CommentSection` [2. Called second] | **Owns the list and renders the `<form>`** | Does not call `useFormStatus`: the form is in its own return
  - +`CommentFooter` [3. Called third, inside the form] | Calls `useFormStatus` and reads **`data`** | Shows **Posting "Nice photo!"...** during the wait
    - +`PostButton` [4. Called fourth, inside the form] | Calls `useFormStatus` and reads **`pending`** | Reads **Posting...** and turns off during the wait
```

| Aspect | The Habit That Breaks | The React Rule |
| :--- | :--- | :--- |
| **The import** | Import `useFormStatus` from `'react'`, like `useState`, and the page fails | Import `useFormStatus` from `'react-dom'` |
| **The place** | Call the Hook in the component that renders `<form>`, and `pending` stays `false` | Call the Hook in a component rendered inside the `<form>` |
| **The middle** | Pass `pending` through every component in between, and one forgotten prop freezes the button | Let the button ask the form, and pass nothing through the middle |
| **The data** | Call `data.get` with no check, and the first render throws | Show the line only when `data` is not `null` |

## For the Interview

> **The Interview Question:** How does a field nested deep in a form read the form's pending state?

### How to Answer Clearly in 30 Seconds

"The field or the button calls `useFormStatus`, a Hook from `'react-dom'`. It takes no parameters and returns the status of the parent form: `pending`, `data`, `method`, and `action`. `pending` is `true` while that form is submitting, so a Post button can turn off and read `Posting...`. Three rules keep it working:
1. **Call it inside the form**: the Hook reads only a form above the component. In the component that renders the `<form>` tag itself, `pending` is never `true`, with no error.
2. **No prop drilling**: the components between the form and the button pass nothing. The blog says the Hook reads the parent form as if the form was a Context provider.
3. **Check `data`**: `data` holds the form data being submitted, and it is `null` when nothing is being submitted."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"I called `useFormStatus` in my form component, and `pending` is always `false`. Why?"**
   Because the Hook reads only a parent `<form>`, a form above the component that calls it. A form in the component's own return is below it, so the Hook does not see it. Outside any form, the Hook returns `pending` as `false`, and `data` and `action` as `null`. The fix is to move the Hook into a component rendered inside the form, such as the submit button. If the form's owner needs the flag itself, it reads `isPending` from `useActionState`.
2. **"What is the difference between `isPending` from `useActionState` and `pending` from `useFormStatus`?"**
   They answer the same question for two different components. `isPending` goes to the component that calls `useActionState`, which is usually the component that owns the form. `pending` goes to any component inside the form, at any depth, without a prop. On one page, the owner uses `isPending`, and the reusable submit button uses `pending`.
3. **"Why does `useFormStatus` come from `'react-dom'`, and what do `method` and `action` hold?"**
   It is one of the Form Hooks of React DOM, which work only in web applications that run in the browser, because `<form>` is a browser element. `method` is the string `'get'` or `'post'`. React's docs add that when a function is passed to the form's `action` prop, the HTTP method is POST, whatever the `method` prop says. `action` is a reference to the function passed to the form's `action` prop, and it is `null` when the form has a URL there or no `action` prop at all.

```tree caption="Interview comparison: which component reads the form's pending state, and with which tool."
Who reads the pending state of one form
- +The form's owner [`CommentSection`] | Calls `useActionState` | Reads **`isPending`**
- +A component inside the form [`PostButton` `CommentFooter`] | Calls `useFormStatus` | Reads **`pending`** and **`data`**, with no prop
- !The form's owner calling `useFormStatus` | The form is **in its own return**, not above it | `pending` is **always `false`**
```
