# Lecture 38: Calling Hooks Only at the Top Level of React Functions
> INTERVIEW QUESTION | ❱ CORE | Why must hooks be called at the top level, and only from React functions?

---

## Why Every Render Must Call the Same Hooks

### A feedback form: where does the `useState` for the message go?

Many apps end a page with a small feedback form. It has a box with the placeholder `Message` and a `Send` button. When the page opens, the box is empty:

```page width=text caption="The feedback form when the page opens: an empty Message box and a Send button."
form:
  textarea: Message |
  submit: Send
console: quiet
```

Here is what the user does, and what the user expects to see:
1. The user types `Great app` in the box. The letters appear.
2. The user clicks `Send`. The form goes away, and `Thank you!` appears in its place.

```page width=text caption="The same page after the user clicks Send: the form is gone, and the thank-you heading takes its place."
heading: Thank you!
console: quiet
```

This small screen raises a real question for the developer. The component shows one of two screens: the thank-you heading, or the form. So its code has an `if` with two branches. The text the user types lives in a state variable, `message`, and only the form uses it. Where may the `useState` for `message` sit: inside the form's branch, next to the form, or at the top of the component?

At the top, always. React's docs say it in one line: "always use Hooks at the top level of your React function, before any early returns."

Why? Well, React does not know a Hook by its variable name. It knows the Hook by its place in the order of Hook calls (as seen in Lesson 12). So every render of a component must call the same Hooks, in the same order. No `if`, no loop, no early `return`, and no nested function may decide whether a Hook runs.

### Two forms that look the same until the user clicks Send

Compare two ways to write this form:
1. **With `useState` for `message` at the top of the component**, above the `if`.
2. **With `useState` for `message` inside the form's branch**, right next to the form that uses it.

It may look the same, or work the same at first, but it is NOT the same thing! Both versions show the empty box when the page opens. In both, typing works. Only the first one shows `Thank you!` after Send. The second one crashes, and React's docs name the error: "Rendered fewer hooks than expected".

```tree caption="Two places for the useState of message: they look the same while the user types, and only one survives the click on Send."
Where the `useState` for `message` sits
- +At the top of the component, above the `if` | The box opens empty and **typing works** | After Send, the page shows **`Thank you!`**
- !Inside the form's branch, next to the form | The box opens empty and **typing works** | After Send, React stops with **Rendered fewer hooks than expected**
```

### What is at stake

What is at stake is the user's last click. The user writes a message and clicks Send. Instead of `Thank you!`, the whole page goes blank, and the message is gone. React's docs explain the blank page: "By default, if your application throws an error during rendering, React will remove its UI from the screen."

The bug hides well. The page opens without an error, and typing works, so a developer who only types in the box never sees it. The first person to click Send sees it.

Readers usually go wrong in four ways:
1. They think React finds `message` by its name.
2. They move a Hook next to the code that uses it, inside a branch.
3. They silence the linter when it marks that line.
4. They call a Hook inside an event handler, to create state at the moment of the click.

### How our project files are organized

Our project has four files. The whole form lives in one component, `FeedbackForm`:

```files title="feedback-form: File Explorer" caption="How the files of the feedback form sit inside src/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it inside `<StrictMode>`
  App.jsx | parent | Exports `App` as default and imports `FeedbackForm` from `./FeedbackForm.jsx`
  FeedbackForm.jsx | state | Holds `isSent` and `message`, and shows the form or the thank-you heading
```

`App` only places the form on the page:

```jsx title="src/App.jsx"
import FeedbackForm from './FeedbackForm.jsx';

export default function App() {
  return ~<FeedbackForm />~; // React calls FeedbackForm to draw the form
}
```

### Five Principles of the Rules of Hooks

**PRINCIPLES:** React stores the data of every Hook in the order of the calls, and it matches each Hook call to its data by position: the first call gets the first entry, the second call gets the second entry. React's docs give two rules that keep those positions right, and they call them the **Rules of Hooks**: "Only call Hooks at the top level" and "Only call Hooks from React functions". Five practical principles follow from them:
1. **Principle 1: Two `useState` Calls in `FeedbackForm` Run in One Order**: React never sees the names `isSent` and `message`. It sees the first Hook call and the second Hook call, and this holds for every kind of Hook.
2. **Principle 2: Clicking Send Crashes the Form with a Hook Inside `else`**: A Hook inside a branch runs on some renders and not on others. The number of Hook calls changes, and React stops with an error.
3. **Principle 3: `useState` Above the First `return` Brings Back Thank You**: Move every Hook above the first early `return`, and let the `if` decide only what the component returns.
4. **Principle 4: The Condition Moves Inside the Hook**: When a Hook seems to need a condition, keep the Hook at the top and move the condition inside it, into its initial value, or into a new component.
5. **Principle 5: A Hook Inside the `onSubmit` Function Breaks Send**: Hooks work only while React renders a function component or a custom Hook, never in an event handler or a regular JavaScript function.

Here is the complete map of those five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Call Order: React Matches Every Hook by Its Place** | Interviewers ask how React knows which state belongs to which `useState` when no name is passed. | Every render calls the exact same Hooks in the exact same order. |
| **Principle 2** | **A Hook in a Branch Changes the Number of Hook Calls** | The page opens and typing works, so the bug ships; the first user to click Send sees a blank page. | Never call a Hook inside a condition, a loop, or below an early `return`. |
| **Principle 3** | **Every Hook Above the First `return`** | The fix is one line moved, and it is the fix React's docs give for this exact form. | Call every Hook at the top level, before any early `return`. |
| **Principle 4** | **The Condition Moves, Not the Hook** | A developer who needs "a Hook only sometimes" must know the legal ways to say it. | Put the condition inside the Hook, in its initial value, or in a new component. |
| **Principle 5** | **Hooks Only From React Functions** | A Hook in a click handler opens without an error and throws on the first click. | Call Hooks only from function components and custom Hooks. |

## 1. Principle 1: Two useState Calls in FeedbackForm Run in One Order

### Neither Hook call passes a name to React

Look at two state variables at the top of a component:

```jsx title="Two useState calls, one after the other"
const [name, setName] = ~useState('John')~; // 1st Hook call: React matches 'John' to it
const [count, setCount] = ~useState(0)~; // 2nd Hook call: React matches 0 to it
```

The names `name` and `count` exist only inside our function. Neither call hands a name to React: React receives only `'John'` and `0`. React's docs ask the obvious question and answer it: "There is no "identifier" that is passed to `useState`, so how does it know which of the state variables to return? Does it rely on some magic like parsing your functions? The answer is no." Hooks "rely on a stable call order on every render of the same component."

Lesson 12 showed this for `useState`. The new fact of this lesson is that it holds for **every** Hook: `useState`, `useEffect`, `useContext`, `useRef`, `useReducer`, all of them. The docs page for the lint rule `rules-of-hooks`, the lint page from now on, says: "Each time your component renders, React expects the exact same hooks to be called in the exact same order."

### Renaming a state variable changes nothing for React

Suppose we rename `message` to `text`:

```jsx title="The same Hook call under two variable names"
const [~message~, setMessage] = useState(''); // The 2nd Hook call in FeedbackForm
const [~text~, setText] = useState(''); // Still the 2nd Hook call: React sees no difference
```

Yes, it is the exact same thing for React! Both lines are the second `useState` call, and React hands that call the second value it stored.

### Hooks are declarations at the top of the component

React's docs give an image for how to think of a Hook. They say it openly, as a way of thinking, not as a fact about the code: "Hooks are functions, but it's helpful to think of them as unconditional declarations about your component's needs. You "use" React features at the top of your component similar to how you "import" modules at the top of your file."

An `import` line never sits inside an `if`. It sits at the top of the file and runs every time. A Hook belongs in the same kind of place. **Unconditional** means no condition decides whether it runs.

That place has a name in the docs: the **top level of your React function**. It is the body of the component itself:
1. Outside any `if`, loop, or nested function.
2. Above any early `return`.

### The working feedback form

Here is our working form. Both Hooks sit at the top level, and the early `return` comes after them:

```jsx title="src/FeedbackForm.jsx" good="4,5"
import { useState } from 'react';

export default function FeedbackForm() {
  const [isSent, setIsSent] = ~useState(false)~; // 1st Hook call, on every render
  const [message, setMessage] = ~useState('')~; // 2nd Hook call, on every render

  if (isSent) {
    return <h1>Thank you!</h1>; // The early return comes after both Hooks
  }

  return (
    <form onSubmit={e => {
      e.preventDefault();
      setIsSent(true);
    }}>
      <textarea
        placeholder="Message"
        value={message}
        onChange={e => setMessage(e.target.value)}
      />
      <br />
      <button type="submit">Send</button>
    </form>
  );
}
```

Count the Hook calls on each render. The answer is two, every time. On every render after the first, React hands back what it stored, in the order of the calls:

| What the user did | 1st Hook call returns | 2nd Hook call returns | What the page shows |
| :--- | :--- | :--- | :--- |
| Opened the page | `isSent` is `false` | `message` is `''` | The empty box and `Send` |
| Typed `Great app` | `isSent` is `false` | `message` is `'Great app'` | The box with `Great app` |
| Clicked `Send` | `isSent` is `true` | `message` is `'Great app'` | `Thank you!` |

```page width=text caption="The working form after the user types Great app."
form:
  textarea: Message | Great app
  submit: Send
console: quiet
```

```page width=text caption="The working form after the user clicks Send: both Hooks ran, and the thank-you heading appears."
heading: Thank you!
console: quiet
```

What is at stake when the order changes? React gives one Hook's data to another call. The lint page says React then "loses track of which state corresponds to which hook call, leading to bugs like state mismatches". Principle 2 shows the moment the order breaks on our form.

> [!PRINCIPLE]
> **Principle 1: Call Order: React Matches Every Hook by Its Place in the Order**
>
> *Every Hook in a component, of any kind, is matched to its stored data by its place in the order of Hook calls, so every render must call the same Hooks in the same order.*
>
> React never receives the names `isSent` or `message`. It receives a first Hook call and a second Hook call, and it hands each one the data stored at that position. This works only while every render makes the same calls in the same order, which is why every Hook sits at the top level of the component.
>
> **DO THIS:**
> ```jsx
> function FeedbackForm() {
>   const [isSent, setIsSent] = ~useState(false)~; // 1st Hook on every render
>   const [message, setMessage] = ~useState('')~; // 2nd Hook on every render
>   if (isSent) {
>     return <h1>Thank you!</h1>;
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function FeedbackForm() {
>   const [isSent, setIsSent] = useState(false);
>   if (!isSent) {
>     const [message, setMessage] = ~useState('')~; // **WRONG:** the 2nd Hook runs only while isSent is false
>   }
> }
> ```

## 2. Principle 2: Clicking Send Crashes the Form with a Hook Inside else

### The Hook moves next to the form that uses it

A developer may reason that `message` is used only by the form, so its `useState` belongs next to the form. React's docs show this exact form in their Challenge "Fix a crash": the `useState` for `message` sits inside the `else` branch:

```jsx title="src/FeedbackForm.jsx" bad="9"
import { useState } from 'react';

export default function FeedbackForm() {
  const [isSent, setIsSent] = useState(false);

  if (isSent) {
    return <h1>Thank you!</h1>;
  } else {
    const [message, setMessage] = ~useState('')~; // **WRONG:** inside else, so it runs only while isSent is false
    return (
      <form onSubmit={e => {
        e.preventDefault();
        setIsSent(true);
      }}>
        <textarea
          placeholder="Message"
          value={message}
          onChange={e => setMessage(e.target.value)}
        />
        <br />
        <button type="submit">Send</button>
      </form>
    );
  }
}
```

The linter marks that line. In the docs' version, the developer has silenced it with an `eslint-disable-next-line` comment on the line above (as seen in Lesson 35).

### The form opens, the user types, and nothing looks wrong

When the page opens, the box is empty, and the Console is quiet. The user types `Great app`, and the letters appear:

```page width=text caption="The form with the Hook inside else, after the user types Great app: it looks exactly like the working form."
form:
  textarea: Message | Great app
  submit: Send
console: quiet
```

It may look the same, or work the same at first, but it is NOT the same thing! Up to this point, every render of this version also calls two Hooks. The difference waits for one click.

### Clicking Send blanks the page

**Beware! With a Hook inside `else`, the click on Send removes the whole page.** The thank-you render makes one Hook call where the render before it made two, and React stops. Here is what happens, in order:
1. The page opens. `isSent` is `false`. React calls `useState(false)`, goes into `else`, and calls `useState('')`. Two Hook calls.
2. The user types `Great app`. Each letter typed by the user calls `setMessage`, and each render makes the same two calls.
3. The user clicks `Send`. The `onSubmit` function calls `e.preventDefault()` and `setIsSent(true)`.
4. React calls `FeedbackForm` again. The first Hook call now returns `true`.
5. `if (isSent)` returns the thank-you heading. The line with `useState('')` never runs. One Hook call.
6. React expected two Hook calls and got one. It throws an error while rendering `FeedbackForm`.
7. No error boundary sits above the form, so React removes the whole page from the screen. An error boundary is a component that catches a render error and shows a fallback screen instead, and Lesson 72 covers it.

No line of our code throws this error. React throws it, because the count of Hook calls changed between two renders. The Console shows the same message as in Lesson 12:

```page width=text caption="The same page after the user clicks Send with the Hook inside else: nothing is left on the screen."
blank
```

```devconsole
x Uncaught Error: Rendered fewer hooks than expected. This may be caused by an accidental early return statement.
```

The Elements panel shows what is left of the page: the root `<div>`, with nothing inside it.

```dom caption="The Elements panel after the click on Send: React removed everything inside the root div."
<body>
! <div id="root"></div> | note: Empty: React removed the form and never drew the heading
</body>
```

The page now displays nothing at all. The user sees neither the form nor `Thank you!`, and the message is lost.

### The opposite case: a Hook that appears only after Send

The same crash comes in the other direction. Suppose a Hook sits inside `if (isSent)`, so it runs only after Send. The first render calls fewer Hooks than the second, and React stops with "Rendered more hooks than during the previous render." (as seen in Lesson 12).

Fewer or more, the cause is the same: a condition decided whether a Hook ran.

### Where the docs say a Hook must never go

React's docs list every place where calling a Hook is not supported:
1. Inside a condition, such as `if`, a ternary, `&&`, or `||`.
2. Inside a loop, such as `for`. The number of Hook calls would follow the number of items.
3. After a conditional `return` statement.
4. In an event handler.
5. In a class component.
6. Inside a function passed to `useMemo`, `useReducer`, or `useEffect`.
7. Inside a `try`, `catch`, or `finally` block.

The lint page adds two more: an async function, and the module level, outside any component.

The tool that catches all of these is the lint rule `rules-of-hooks`, from the package `eslint-plugin-react-hooks`. It is part of the plugin's `recommended` preset, so every project that uses the preset has it on. It marked our line in the `else` branch. The developer silenced it, and the bug shipped. The docs' hint for this form says to look for comments that disable the linter, because "this is where the bugs often hide!"

> [!PRINCIPLE]
> **Principle 2: Hooks in Branches: A Hook in a Branch Crashes the Render That Skips It**
>
> *A Hook inside a condition, a loop, or below an early `return` runs on some renders and not on others, so the number of Hook calls changes and React stops with an error.*
>
> Where a value is used and where its Hook is called are two separate things. The form uses `message`, but the `useState` for `message` must run on the thank-you render too. When a render skips a Hook, React throws "Rendered fewer hooks than expected", and without an error boundary the whole page goes blank.
>
> **DO THIS:**
> ```jsx
> const [isSent, setIsSent] = useState(false);
> const [message, setMessage] = ~useState('')~; // Runs on the form render and on the thank-you render
> if (isSent) {
>   return <h1>Thank you!</h1>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [isSent, setIsSent] = useState(false);
> if (isSent) {
>   return <h1>Thank you!</h1>;
> } else {
>   const [message, setMessage] = ~useState('')~; // **WRONG:** skipped after Send, so React stops and the page goes blank
> }
> ```

## 3. Principle 3: useState Above the First return Brings Back Thank You

### The same line in two places

The fix is to move one line. Here is the `useState` for `message` in its two possible places:

```jsx title="Below the if, inside else"
if (isSent) {
  return <h1>Thank you!</h1>;
} else {
  const [message, setMessage] = ~useState('')~; // **WRONG:** skipped on the thank-you render
}
```

```jsx title="Above the if, right under the first Hook"
const [isSent, setIsSent] = useState(false);
const [message, setMessage] = ~useState('')~; // Runs on every render, before the first return
if (isSent) {
  return <h1>Thank you!</h1>;
}
```

It looks the same, but it is NOT the same thing! The first place makes one Hook call after Send. The second place makes two Hook calls on every render, so React never loses count.

React's docs give this exact fix for this exact form: "Hooks can only be called at the top level of the component function. Here, the first `isSent` definition follows this rule, but the `message` definition is nested in a condition. Move it out of the condition to fix the issue". And they add: "Remember, Hooks must be called unconditionally and always in the same order!"

### The `else` branch is no longer needed

Once both Hooks sit above the `if`, the `else` around the form has no job left. The `if` already returns early, so the lines below it run only when `isSent` is `false`.

With the `else` and without it, the form behaves the same. Yes, it is the exact same thing! The docs suggest removing it "to reduce the nesting", and they keep one condition: "it's still important that all calls to Hooks happen *before* the first `return`."

### The thank-you screen still has a `message`

The junior worry is: "The thank-you screen does not need `message`, so it should not create it." But creating a value and showing it are two separate things. On the thank-you render, the second Hook call still runs, and React still hands back `'Great app'`. The thank-you screen simply does not show it.

### The fixed form

Here is the final `FeedbackForm`. The suppression comment is gone, the `else` is gone, and both Hooks sit at the top:

```jsx title="src/FeedbackForm.jsx" good="4,5"
import { useState } from 'react';

export default function FeedbackForm() {
  const [isSent, setIsSent] = useState(false);
  const [message, setMessage] = ~useState('')~; // Moved above the first return: two Hook calls on every render

  if (isSent) {
    return <h1>Thank you!</h1>;
  }

  return (
    <form onSubmit={e => {
      e.preventDefault();
      setIsSent(true);
    }}>
      <textarea
        placeholder="Message"
        value={message}
        onChange={e => setMessage(e.target.value)}
      />
      <br />
      <button type="submit">Send</button>
    </form>
  );
}
```

The user types `Great app` and clicks Send. This time, the heading appears, and the Console stays quiet:

```page width=text caption="The fixed form after the user clicks Send: both Hooks ran, and the thank-you heading appears."
heading: Thank you!
console: quiet
```

### The same mistake on a loading screen

Developers meet this rule most often with an early `return` for a screen that is not ready yet: a loading line, an empty list, a done screen. The lint page shows the loading case:

```jsx title="A Hook below a loading return"
if (!data) {
  return <Loading />;
}
const [processed, setProcessed] = ~useState(data)~; // **WRONG:** skipped while data is missing, then called once data arrives
```

While `data` is missing, the component returns early and calls fewer Hooks. When the data arrives, it calls one more. The fix is the same as on our form: the Hook moves above the `return`.

> [!PRINCIPLE]
> **Principle 3: Top Level: Call Every Hook Above the First Early `return`**
>
> *Call every Hook at the top level of the component, above the first early `return`, and let the condition decide only what the component returns.*
>
> An early `return` stops the function, so every Hook written below it is skipped on that render. Moving the Hook above the `return` makes every render call the same Hooks. The component then creates every value on every render, and the `if` decides only which screen the user sees.
>
> **DO THIS:**
> ```jsx
> const [isSent, setIsSent] = useState(false);
> const [message, setMessage] = ~useState('')~; // Above the first return
> if (isSent) {
>   return <h1>Thank you!</h1>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [isSent, setIsSent] = useState(false);
> if (isSent) {
>   return <h1>Thank you!</h1>;
> }
> const [message, setMessage] = ~useState('')~; // **WRONG:** below the first return, skipped after Send
> ```

## 4. Principle 4: The Condition Moves Inside the Hook

### Moving the condition, not the Hook

Sometimes a developer really needs a Hook "only sometimes": an Effect only for a signed-in user, or a starting value that depends on the kind of user. The Hook still stays at the top. **The condition moves instead.** React's docs give four ways to move it:
1. Put the condition inside the Effect.
2. Give `useState` a conditional initial value.
3. Extract a new component and move the state into it.
4. Read context with `use` instead of `useContext`.

### 1. The condition goes inside the Effect

Suppose a developer wants to fetch the user's data only when the user is signed in. The first idea is to wrap the Effect in an `if`:

```jsx title="useEffect inside if"
if (isLoggedIn) {
  ~useEffect~(() => { // **WRONG:** when the user signs in, the next render calls one more Hook
    fetchUserData();
  }, []);
}
```

The lint page's fix keeps the Effect at the top and moves the `if` inside it:

```jsx title="if inside the Effect"
~useEffect~(() => { // Called on every render, so the number of Hook calls never changes
  if (isLoggedIn) {
    fetchUserData();
  }
}, ~[isLoggedIn]~); // The Effect runs again when isLoggedIn changes
```

It looks the same, but it is NOT the same thing! In the first, the `useEffect` call itself comes and goes with `isLoggedIn`. In the second, `useEffect` is called on every render, and the condition decides only what the Effect does. Because `isLoggedIn` is in the dependency array, the Effect runs again when the user signs in (as seen in Lesson 32).

### 2. The condition goes into the initial value

Suppose the starting permissions depend on the kind of user. The first idea is two `useState` calls in two branches:

```jsx title="Two useState calls in two branches"
if (userType === 'admin') {
  const [permissions, setPermissions] = ~useState(adminPerms)~; // **WRONG:** a Hook inside if
} else {
  const [permissions, setPermissions] = ~useState(userPerms)~; // **WRONG:** a Hook inside else
}
```

The lint page's fix is one `useState` with a **conditional initial value**, chosen by a ternary:

```jsx title="One useState with a conditional initial value"
const [permissions, setPermissions] = useState(~userType === 'admin' ? adminPerms : userPerms~); // One Hook call, the condition picks only the starting value
```

Both start `permissions` with the right value, but for React they are NOT the same thing. The second always makes one Hook call at the same place.

### 3. The state moves into a new component

Back on our form. The `message` state belongs to the form branch only. When state belongs to one branch, React's docs give a third way: "extract a new component and move the state into it."

So the form moves into its own component, `MessageForm`, and `message` moves with it:

```jsx title="src/MessageForm.jsx"
import { useState } from 'react';

export default function MessageForm({ onSend }) {
  const [message, setMessage] = ~useState('')~; // The top level of MessageForm: one Hook call on every render of MessageForm

  return (
    <form onSubmit={e => {
      e.preventDefault();
      ~onSend()~; // Tells FeedbackForm that the user clicked Send
    }}>
      <textarea
        placeholder="Message"
        value={message}
        onChange={e => setMessage(e.target.value)}
      />
      <br />
      <button type="submit">Send</button>
    </form>
  );
}
```

`FeedbackForm` keeps only `isSent`, and it chooses which component to show:

```jsx title="src/FeedbackForm.jsx"
import { useState } from 'react';
import MessageForm from './MessageForm.jsx';

export default function FeedbackForm() {
  const [isSent, setIsSent] = useState(false); // FeedbackForm's only Hook

  if (isSent) {
    return <h1>Thank you!</h1>;
  }

  return <MessageForm ~onSend={() => setIsSent(true)}~ />; // A callback prop: the form asks the parent to switch screens
}
```

Now the `if` decides whether `MessageForm` appears, not whether a Hook runs. Each component calls its one Hook at its own top level, on every one of its own renders.

When the user clicks Send, `Thank you!` replaces `MessageForm`, and React discards its `message` (as seen in Lesson 25). The user sees the same page as with the fixed form of Principle 3: the box, `Send`, then `Thank you!`.

Both designs are correct. The fixed form of Principle 3 is shorter, so it stays our final page. Extracting a component pays off when the branch holds several pieces of state of its own.

### 4. Context goes through `use`

The last case is a branch that only reads context. `useContext` is a Hook, so it must stay at the top. But React has an API that may sit inside an `if`: `use` (as seen in Lesson 28).

```jsx title="useContext inside if, and use inside if"
if (isSent) {
  const theme = ~useContext(ThemeContext)~; // **WRONG:** useContext is a Hook inside if
}
if (isSent) {
  const theme = ~use(ThemeContext)~; // use may be called inside if
}
```

It looks the same, but it is NOT the same thing! React's docs: "While `useContext` must be called at the top level of your component, `use` can be called inside conditionals like `if` and loops like `for`." The docs also say: "Despite its name, `use` is not a Hook." Two limits remain: `use` cannot sit inside `try` and `catch`, and it must be called inside a component or a Hook.

> [!PRINCIPLE]
> **Principle 4: Moving the Condition: The Hook Stays, the Condition Moves Inside It**
>
> *When a Hook seems to need a condition, keep the Hook at the top level and put the condition inside it, in its initial value, or in a new component that holds the Hook.*
>
> A condition may decide what a Hook does, never whether it runs. Inside an Effect, the `if` decides what the Effect does. In `useState`, a ternary decides the starting value. When state belongs to one branch only, a new component holds it, and the parent's `if` decides whether that component appears.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   ~if (isLoggedIn)~ { // The condition lives inside the Effect
>     fetchUserData();
>   }
> }, [isLoggedIn]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~if (isLoggedIn)~ { // **WRONG:** the condition decides whether useEffect is called at all
>   useEffect(() => {
>     fetchUserData();
>   }, []);
> }
> ```

## 5. Principle 5: A Hook Inside the onSubmit Function Breaks Send

### A component and a regular function look alike

The second Rule of Hooks says where a Hook may be called from. Both functions below are JavaScript functions with the same Hook call inside. React's docs show them side by side:

```jsx title="The same Hook call in a component and in a regular function"
function FriendList() {
  const [onlineStatus, setOnlineStatus] = ~useOnlineStatus()~; // A function component: the Hook call is allowed
}

function setOnlineStatus() {
  const [onlineStatus, setOnlineStatus] = ~useOnlineStatus()~; // **WRONG:** not a component or a custom Hook
}
```

It may look the same, but it is NOT the same thing! Only `FriendList` is a **React function**. That is the docs' name for the two kinds of functions that may call Hooks:
1. **A function component**, such as `FeedbackForm`. React calls it to render.
2. **A custom Hook**, a function our code writes whose name starts with `use` followed by a capital letter, such as `useOnlineStatus`. A custom Hook may call other Hooks, and our component calls it at its top level. Lesson 39 covers custom Hooks in full.

Every other function is a **regular JavaScript function**, and it may not call Hooks. Why? Well, React's docs say: "You can only call Hooks while React is rendering a function component". React knows which component a Hook call belongs to only while it is rendering that component. A regular function can run at any moment our code chooses, outside any render.

### The Hook moves into the click

On our form, this mistake looks like a shortcut. A developer wants state that exists only after the click, so the developer writes `useState` inside the `onSubmit` function, in place of `setIsSent(true)`:

```jsx title="src/FeedbackForm.jsx" startLine="11" bad="14"
  return (
    <form onSubmit={e => {
      e.preventDefault();
      const [isSent, setIsSent] = ~useState(true)~; // **WRONG:** a Hook inside an event handler, called when the user clicks Send
    }}>
```

**Beware! The page opens without an error, and the error waits for the click.** Here is what happens, in order:
1. The page opens. The box and `Send` appear, because the `onSubmit` function has not run yet.
2. The user types `Great app` and clicks `Send`.
3. React runs the `onSubmit` function for the browser's submit event. No component is rendering at this moment.
4. The function calls `useState`, and React throws an error.
5. The handler never calls `setIsSent`, the setter of the `isSent` at the top of `FeedbackForm`. So the form stays on the page, and `Thank you!` never appears.

The `isSent` inside the `onSubmit` function is a new variable of that function only. It has nothing to do with the `isSent` at the top of `FeedbackForm`, and it never exists, because the line throws first.

```page width=text caption="The form with a Hook inside onSubmit, after the user clicks Send: the form stays, and the thank-you heading never appears."
form:
  textarea: Message | Great app | bad
  submit: Send
console: Uncaught Error: Invalid hook call. Hooks can only be called inside of the body of a function component.
```

The fix is the form of Principle 3. The Hook goes back to the top level, and the event handler calls only its setter, `setIsSent(true)`. The docs' comment for this case says the same: "to fix, move it outside!"

React prints the same error for two other causes that have nothing to do with where our Hooks sit: React and React DOM at mismatching versions, or two copies of React in one app. The docs' check for a second copy is the command `npm ls react`.

### The name says where state may hide

The rule has a purpose beyond the crash. React's docs: "By following this rule, you ensure that all stateful logic in a component is clearly visible from its source code."

The naming convention makes that visible. The docs: "Hook names must start with `use` followed by a capital letter". So a reader of the code can tell at a glance which calls may hold state. The docs: "If you see a `getColor()` function call inside your component, you can be sure that it can't possibly contain React state inside because its name doesn't start with `use`."

The prefix is a promise, so it belongs only on functions that call Hooks. A function named `useSorted` that calls no Hook and a function named `getSorted` with the same body are the exact same code. Yes, it is the exact same thing! The docs: "Functions that don't *call* Hooks don't need to *be* Hooks." Name it `getSorted`, and it may even be called inside an `if`, because it is not a Hook.

> [!PRINCIPLE]
> **Principle 5: React Functions Only: Call Hooks While React Renders a Component or a Custom Hook**
>
> *Call Hooks only while React renders a function component or a custom Hook, and never from an event handler, a regular JavaScript function, or a class component.*
>
> A Hook needs the component that React is rendering at that moment. An event handler runs later, when the user clicks, outside any render, so a Hook inside it throws. Keep every Hook at the top level of a component or a custom Hook, and let event handlers call only setters.
>
> **DO THIS:**
> ```jsx
> const [isSent, setIsSent] = useState(false);
> <form onSubmit={e => {
>   e.preventDefault();
>   ~setIsSent(true)~; // The handler calls only the setter
> }}>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <form onSubmit={e => {
>   e.preventDefault();
>   const [isSent, setIsSent] = ~useState(true)~; // **WRONG:** a Hook in an event handler throws when the user clicks Send
> }}>
> ```

## Putting All 5 Principles Together

### The complete project

`main.jsx` mounts `App` inside `<StrictMode>`:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    ~<App />~ {/* 1. React calls App first */}
  </StrictMode>
);
```

`App` places the form:

```jsx title="src/App.jsx"
import FeedbackForm from './FeedbackForm.jsx';

export default function App() {
  return ~<FeedbackForm />~; // 2. React calls FeedbackForm next
}
```

`FeedbackForm` calls both Hooks at its top level, then decides what to show:

```jsx title="src/FeedbackForm.jsx" good="4,5"
import { useState } from 'react';

export default function FeedbackForm() {
  const [isSent, setIsSent] = ~useState(false)~; // 3. The 1st Hook call, on every render
  const [message, setMessage] = ~useState('')~; // 4. The 2nd Hook call, on every render

  if (~isSent~) { // 5. Only now does the condition choose the screen
    return <h1>Thank you!</h1>;
  }

  return (
    <form onSubmit={e => {
      e.preventDefault();
      ~setIsSent(true)~; // 6. The handler calls only the setter
    }}>
      <textarea
        placeholder="Message"
        value={message}
        onChange={e => setMessage(e.target.value)}
      />
      <br />
      <button type="submit">Send</button>
    </form>
  );
}
```

### The order React follows on every render

On every render, React follows the same path. It calls `App`, then `FeedbackForm`. Inside `FeedbackForm`, it meets the two Hooks first, in the same order, and only then the `if`:

```tree dir=right caption="The order React follows on every render of the feedback form: the components, then the two Hooks, then the condition."
How React renders the feedback form
- +1. `App` [`<FeedbackForm />`] | React calls **`App`**, which returns the form's tag
- +2. `FeedbackForm` | React calls **`FeedbackForm`** on the first render and after every state change
- +3. 1st Hook [`isSent`] | **Always first**: React hands back the stored `isSent`
- +4. 2nd Hook [`message`] | **Always second**: React hands back the stored `message`
- +5. The `if` | Chooses **`Thank you!`** or **the form**; the number of Hook calls stays **two**
```

```page width=text caption="The finished page after the user types Great app and clicks Send."
heading: Thank you!
console: quiet
```

| Where the Hook call sits | What React sees | What the user sees |
| :--- | :--- | :--- |
| **At the top level, above the first `return`** | Two Hook calls on every render | `Thank you!` after Send |
| **Inside `else`, next to the form** | After Send, one Hook call where there were two | A blank page after Send |
| **Inside `if (isSent)`** | After Send, more Hook calls than the render before | A blank page after Send |
| **Inside the Effect, with the `if` inside it** | One `useEffect` call on every render | The Effect does its work only when the condition is true |
| **In a new component, `MessageForm`** | Each component makes the same calls on its own renders | `Thank you!` after Send |
| **Inside the `onSubmit` function** | A Hook call outside any render, when the user clicks Send | The form stays, and `Thank you!` never appears |

## For the Interview

> **The Interview Question:** Why must hooks be called at the top level, and only from React functions?

### How to Answer Clearly in 30 Seconds

"React does not identify a Hook by its variable name, because no Hook call passes a name. It matches each call to its stored data by its place in the order of Hook calls. So every render must call the exact same Hooks in the exact same order. Two rules keep that order safe:
1. **Only call Hooks at the top level**: never inside a condition, a loop, a nested function, or below an early `return`. If a feedback form calls its `useState` for the message inside an `else`, the thank-you render skips it, React throws 'Rendered fewer hooks than expected', and the page goes blank.
2. **Only call Hooks from React functions**: function components and custom Hooks, never event handlers or regular functions. React ties a Hook call to the component it is rendering at that moment, and the `use` prefix shows a reader where state may hide.

When a Hook seems to need a condition, I keep the Hook at the top and move the condition inside it, into its initial value, or into a new component. The `rules-of-hooks` lint rule catches these mistakes, so I never silence it."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does React use call order instead of names?"**
   Order keeps the syntax short: `useState('')` needs no key or label. React's docs say Hooks "rely on a stable call order on every render of the same component", and that this works well in practice because the top-level rule keeps the order the same, while the linter catches most mistakes. The cost is the rule itself: a Hook may never be skipped on one render and called on another.
2. **"How do you run an Effect only when a condition is true?"**
   You call `useEffect` on every render and put the `if` inside the Effect function, such as `if (isLoggedIn) { fetchUserData(); }`. Then you add `isLoggedIn` to the dependency array, so the Effect runs again when the condition changes. Wrapping `useEffect` itself in an `if` changes the number of Hook calls when the user signs in.
3. **"Is there anything like a Hook that may be called inside an `if`?"**
   Yes, `use`. React's docs say `use` "can be called inside conditionals like `if` and loops like `for`", while `useContext` must stay at the top level. `use` is not a Hook, but it still has two limits: it cannot sit inside `try` and `catch`, and it must be called inside a component or a Hook. Regular functions such as `getSorted` can also be called inside an `if`, because they are not Hooks.

```tree caption="Interview summary: where a Hook call may sit and where it may not."
Where a Hook call may sit
- +At the top level of a function component | **Before any early `return`**, outside every `if`, loop, and nested function | Same Hooks, **same order**, every render
- +At the top level of a custom Hook | A function named **`use` plus a capital letter** | Called by a component at **its own top level**
- !Inside a condition, a loop, or below an early `return` | The number of Hook calls **changes between renders** | React throws **Rendered fewer hooks than expected**
- !Inside an event handler or a regular function | Runs **outside any render** | React throws **Invalid hook call**
```
