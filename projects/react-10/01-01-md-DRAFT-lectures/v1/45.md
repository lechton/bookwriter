## How a Form Keeps or Clears What the User Typed

### A refusal for the user vs. a success for React

Picture the Create account form of a website. It has a Username box, an Email box, and a Create account button.

```page caption="The Create account form after the user has typed a username and an email, before the click."
heading: Create account
form:
  field: Username | john
  field: Email | john@mail.com
  submit: Create account
console: quiet
```

The user types `john` and `john@mail.com`, then clicks Create account. About one second later, one line appears under the button. The username is taken. And both boxes are empty:

```page caption="The same form about one second after the click: the refusal line, and two empty boxes."
heading: Create account
form:
  field: Username | | bad
  field: Email | | bad
  submit: Create account
  error: Username john is taken.
console: quiet
```

The email was right. Now the user must type it again.

React emptied the boxes. No line of our code touches them. In React 19, a form whose `action` is a function gets one extra step for free: after the function finishes, React resets every uncontrolled box of that form. This is the **automatic reset**, as the React 19 announcement calls it.

The surprise is the word "finishes". For the user, `Username john is taken.` and `Welcome, john!` are opposites: one is a refusal, the other a success. For React, they are the exact same thing: a value the action returned without throwing an error. React never reads the text you return. It only knows whether your function threw, and a returned error message is not a thrown error, so React counts the refusal as a success:

```tree caption="The same answer from the server, read by the user and by React."
What `Username john is taken.` means
- !For the user | The server **said no** | The user expects to **fix one word** and try again
- +For React | The action **returned a value** and **did not throw** | The action **succeeded**, so React **resets the form**
```

### What is at stake

The reset puts each box back to its **default value**: the text the box starts with, and the text it goes back to when the form is reset. Our boxes have no default value, so the reset leaves them empty. That gives us the key idea of this lesson. To keep what the user typed after a refusal, we do not stop the reset. We make the user's text the new default value, so the reset puts it back.

Two things are at stake for the user:
1. After every refusal from the server, the user types the whole form again, including the parts that were right.
2. On a slow phone, the user may click Create account before the JavaScript of the page has loaded. Whether that click sends anything depends on how the form is built.

Readers usually go wrong by thinking the reset happens only when the account was created. It happens after every action that does not throw.

### Three ways to keep the text after a refusal

Developers really choose between three ways for this job:
1. **Uncontrolled boxes with `defaultValue` from the state the action returned.** This fits forms built on `<form action>` and `useActionState`, the React 19 way. The form stays plain HTML, so it can still work before JavaScript loads.
2. **Controlled boxes with `value` and `onChange`** (as seen in Lesson 20). This fits a form where the page must change on every keystroke anyway, such as a live hint under the box. React does not reset these boxes at all.
3. **`onSubmit` with `e.preventDefault()`** (as seen in Lessons 11 and 40). There is no automatic reset at all, so our code asks for the reset itself, with `requestFormReset`. This fits older forms that a team moves to Actions step by step.

```tree caption="Three ways to keep the user's text after the server says no."
Three ways to keep the text after a refusal
- +1. `defaultValue` from state [`defaultValue={state.email}`] | React **still resets** the form | The reset **puts back** the text the action returned
- +2. `value` and `onChange` [`value={email}`] | React **does not reset** a controlled box | The page **renders on every keystroke**
- +3. `onSubmit` and `requestFormReset` [`e.preventDefault`] | **No automatic reset** happens | Our code **asks for the reset** when the action ends
```

### Five Principles of Form Resets and Progressive Enhancement

**PRINCIPLES:** React resets a form after its action, and the reset sends each box back to its default value. Five practical principles follow from that:
1. **Principle 1: A Successful Action Empties the Form**: When the function passed to `<form action={...}>` finishes without throwing, React resets every uncontrolled box of that form. No line of our code does it.
2. **Principle 2: A Returned Error Still Empties the Form**: An action that returns an error message has succeeded for React. The error line appears, and the boxes are emptied at the same time.
3. **Principle 3: defaultValue From State Brings the Text Back**: Return the submitted text in the action's state, and give each box `defaultValue` from that state. The reset still runs, and it puts that text back.
4. **Principle 4: requestFormReset Asks for the Reset by Hand**: A form submitted through `onSubmit` gets no automatic reset. Call `requestFormReset(form)` inside the Transition to get the same reset, at the same moment.
5. **Principle 5: name and a Submit Button Keep the Form Working Without JavaScript**: A form works before its JavaScript loads only when it is real HTML and its action is one the browser can send by itself.

Here is the complete map of those five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **The Automatic Reset** | A box that empties after Save looks like a page reload, but the page never reloaded; React reset the form. | After a function in `<form action>` succeeds, React resets every uncontrolled box of the form. |
| **Principle 2** | **A Returned Error Is a Success** | The classic bug report: the username was taken, and the email the user typed is gone too. | React resets the form after any action that does not throw, including one that returns an error message. |
| **Principle 3** | **defaultValue From State** | Writing `value` instead of `defaultValue` freezes the box, and stopping the reset is not possible without leaving `<form action>`. | Return the submitted values in state and give each box `defaultValue` from that state, so the reset puts them back. |
| **Principle 4** | **requestFormReset** | A form moved to `onSubmit` keeps old text after success, and `form.reset()` empties it before the server answers. | Call `requestFormReset(form)` from `'react-dom'` inside the Transition, so the reset waits for the action. |
| **Principle 5** | **Progressive Enhancement** | A form that works only after the JavaScript loads does nothing for a user on a slow phone. | Use a real `<form>`, a `name` on every box, a real submit button, and an action the browser can send without JavaScript. |

## 1. Principle 1: A Successful Action Empties the Form

### React resets the box after the action returns

Start with the smallest form that has an action: one box, one button, and a function that only reads the box.

```jsx title="src/App.jsx"
function save(formData) {
  console.log(formData.get('username')); // Prints john
}

export default function App() {
  return (
    <form ~action={save}~> {/* React calls save with the form data on submit */}
      <label>Username <input name="username" /></label>
      <button type="submit">Save</button>
    </form>
  );
}
```

The user types `john` and clicks Save:

```page caption="The small form before the click, with john typed into the box."
form:
  field: Username | john
  submit: Save
console: quiet
```

```page caption="The same form right after the click: the Console shows john, and the box is empty."
form:
  field: Username | | good
  submit: Save
log: john | App.jsx:2
```

The box is empty, though no line of our code emptied it. It is easy to believe that the browser sent the form and loaded a fresh page, as plain HTML forms do. It did not. With a function in `action`, the page stays where it is. Here is what happened, in order:
1. The user clicked Save. React stopped the browser from sending the form, and called `save` with the form data.
2. `save` printed `john` and returned without throwing an error.
3. Because the action succeeded, React **reset** the form: it put every uncontrolled box back to its default value.
4. Our box has no default value, so it is empty.

To **reset** a form is to put every box of it back to its default value. The browser has always had this as a method of every form element, `form.reset()`. What is new in React 19 is that React calls it for us after a successful action. React's docs say it in one sentence: after the `action` function succeeds, all uncontrolled field elements in the form are reset.

```tree dir=right caption="What React does when the user clicks Save on a form whose action is a function."
One click on Save
- +1. React calls `save` [`formData.get`] | The function **reads the box** and returns | The Console shows **john**
- +2. The action succeeded | `save` returned **without throwing** | React decides to **reset the form**
- +3. React resets the form | Every uncontrolled box goes back to its **default value** | The Username box is **empty**
```

### The reset covers only uncontrolled boxes

The word "uncontrolled" in the docs matters. A controlled box, one with `value` and `onChange` (as seen in Lesson 20), shows what its state holds, and the reset does not change state. So a controlled box keeps `john` after Save:

```jsx title="A controlled box inside a form with an action"
const [name, setName] = useState('');

<form action={save}>
  <input name="username" ~value={name}~ onChange={e => setName(e.target.value)} /> {/* Still shows john after Save */}
  <button type="submit">Save</button>
</form>
```

A developer who expects the automatic reset here waits for an empty box that never comes. With a controlled box, our own code empties it, by calling `setName('')` inside the action.

> [!PRINCIPLE]
> **Principle 1: The Automatic Reset: A Successful Action Empties the Form**
>
> *When the function passed to `<form action={...}>` finishes without throwing, React resets every uncontrolled box of that form.*
>
> A form with a function in `action` does not reload the page. React calls the function with the form data, and when the function returns, React resets the form: every uncontrolled box goes back to its default value. A controlled box is not reset, because it shows what its state holds.
>
> **DO THIS:**
> ```jsx
> function save(formData) {
>   console.log(formData.get('username'));
> }
> <form action={save}>
>   <input ~name="username"~ /> {/* Uncontrolled: React empties it after save returns */}
>   <button type="submit">Save</button>
> </form>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <form action={save}>
>   <input name="username" ~value={name}~ onChange={e => setName(e.target.value)} /> {/* **WRONG:** a controlled box is not reset, so john stays after Save */}
>   <button type="submit">Save</button>
> </form>
> ```

## 2. Principle 2: A Returned Error Still Empties the Form

### Returning a message vs. throwing an error

An action can end in two ways when something goes wrong. It can **return** an error message, as we did with `useActionState` (as seen in Lesson 42). Or it can **throw** an error:

```jsx title="Returning the message vs. throwing it"
if (error) {
  ~return error;~ // The message becomes the new state: the line shows, and the form is reset
}

if (error) {
  ~throw new Error(error);~ // React shows the nearest Error Boundary: no line, no form
}
```

It looks the same, but it is NOT the same thing! Both lines carry the same message. But React treats a returned value as a normal answer. It puts the value into state, renders the page, and resets the form. A thrown error is different: React sends it to the nearest Error Boundary (as seen in Lesson 72), and without one, the whole form is gone from the screen. React's docs draw the line clearly: return the errors you expect, such as a taken username, and throw only the errors you do not expect.

So the right way is to return the message. And that is exactly why the boxes empty.

### The Create account form

Now we build the real page. First, the stand-in server. It waits one second, then answers with an error message for `john` and with `null` for any other name:

```js title="src/api.js"
const takenUsernames = ['john'];

export function createAccount(username) {
  return new Promise(resolve => {
    setTimeout(() => {
      if (~takenUsernames.includes(username)~) { // john is taken
        resolve(`Username ${username} is taken.`);
      } else {
        resolve(null); // Any other name is free
      }
    }, 1000);
  });
}
```

Then the form. `signUp` asks the server and returns the message, as Lesson 42 taught:

```jsx title="src/App.jsx"
import { useActionState } from 'react';
import { createAccount } from './api.js';

async function signUp(previousState, formData) {
  const username = formData.get('username');
  const error = await createAccount(username);
  if (error) {
    ~return error;~ // Returned, not thrown: for React, the action succeeded
  }
  return `Welcome, ${username}!`;
}

export default function App() {
  const [message, formAction] = useActionState(signUp, '');

  return (
    <form ~action={formAction}~>
      <h1>Create account</h1>
      <label>Username <input name="username" /></label>
      <label>Email <input name="email" /></label>
      <button type="submit">Create account</button>
      {message && <p>{message}</p>}
    </form>
  );
}
```

Two names here come from earlier lessons. `previousState` is what `signUp` returned the last time, and on the first click it is the initial state `''`. `message` is the first value `useActionState` gives back: whatever `signUp` returned last.

### The error line and the empty boxes arrive together

**React empties the boxes in the same moment the refusal appears.** The user sees "your username is taken" next to a form that has forgotten everything:
1. The user types `john` in Username and `john@mail.com` in Email, then clicks Create account.
2. React calls `signUp` with the previous state `''` and the form data.
3. `createAccount('john')` waits one second and answers `'Username john is taken.'`.
4. `signUp` returns that text. It did not throw, so for React the action succeeded.
5. React renders `App` with the new state, so the line `Username john is taken.` appears.
6. React resets the form, so both boxes are empty.

```page caption="The Create account form one second after the click with the username john."
heading: Create account
form:
  field: Username | | bad
  field: Email | | bad
  submit: Create account
  error: Username john is taken.
console: quiet
```

The Console stays quiet. Nothing is broken in the code. And the bug hides well: a developer who tests with a free name sees `Welcome, mia!` and two empty boxes, which is exactly right after a success. The bug report arrives later, from a real user whose name was taken.

The reset changes only the boxes on the page. It does not touch the state of `useActionState`: `message` still holds the refusal.

> [!PRINCIPLE]
> **Principle 2: A Returned Error Is a Success: React Resets the Form After Any Action That Does Not Throw**
>
> *An action that returns an error message has succeeded for React, so the boxes are emptied while the error line appears.*
>
> React never reads the message an action returns. It only knows whether the action threw. A known error, such as a taken username, is returned as state, as React's docs recommend, so the form is reset, and the user loses every box at the moment the refusal appears. Throwing the error instead does not save the text: it hands the whole form to the nearest Error Boundary.
>
> **DO THIS:**
> ```jsx
> if (error) {
>   ~return error;~ // The refusal line appears; Principle 3 brings the text back
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> if (error) {
>   ~throw new Error(error);~ // **WRONG:** no refusal line: the nearest Error Boundary replaces the form
> }
> ```

## 3. Principle 3: defaultValue From State Brings the Text Back

### The reset goes back to the default value

The reset cannot be switched off for a form with `action`. But it does not have to empty the boxes. It sends each box back to its **default value**, and we decide what that is. We set it with `defaultValue` (as seen in Lesson 20):

```jsx title="A box with no default value vs. a box whose default value comes from state"
<input name="email" /> {/* The reset empties the box */}
<input name="email" ~defaultValue={state.email}~ /> {/* The reset puts back whatever state.email holds */}
```

After a refusal and after a success, it is the exact same reset. Only the default value differs. So the fix has two parts:
1. **The action returns the text the user typed**, together with the message.
2. **Each box reads that text through `defaultValue`.**

Then the reset itself puts the user's text back. A box's default value is something the browser keeps for every box; React's `defaultValue` prop sets it.

### The state becomes one object

The state now holds three things, so it becomes one object. On a refusal, `signUp` returns the message and the two texts it read from the form. On a success, it returns empty texts, because after a success the user wants an empty form:

```jsx title="src/App.jsx" startLine="4"
const initialState = { message: '', username: '', email: '' };

async function signUp(previousState, formData) {
  const username = formData.get('username');
  const email = formData.get('email');
  const error = await createAccount(username);
  if (error) {
    return ~{ message: error, username, email }~; // Keeps what the user typed
  }
  return ~{ message: `Welcome, ${username}!`, username: '', email: '' }~; // Empties both boxes
}
```

`{ message: error, username, email }` is a JavaScript shortcut. When a key has the same name as the variable that holds its value, you write the name once. So `{ username, email }` is the exact same thing as `{ username: username, email: email }`.

Each box now reads its default value from the state:

```jsx title="src/App.jsx" startLine="16"
export default function App() {
  const [state, formAction] = useActionState(signUp, initialState);

  return (
    <form action={formAction}>
      <h1>Create account</h1>
      <label>Username <input name="username" ~defaultValue={state.username}~ /></label>
      <label>Email <input name="email" ~defaultValue={state.email}~ /></label>
      <button type="submit">Create account</button>
      {state.message && <p>{state.message}</p>}
    </form>
  );
}
```

### The refusal keeps the text, and the success empties it

**After a refusal, the same reset that used to empty the boxes now fills them with what the user typed.** Here are both clicks, in order:
1. The user types `john` and `john@mail.com`, then clicks Create account.
2. `signUp` returns `{ message: 'Username john is taken.', username: 'john', email: 'john@mail.com' }`.
3. React renders `App` with this state. Each box gets a new default value: `john` and `john@mail.com`.
4. React resets the form. Each box goes back to its default value, so the boxes show `john` and `john@mail.com` again.
5. The user changes `john` to `john7` and clicks again.
6. `signUp` returns `{ message: 'Welcome, john7!', username: '', email: '' }`.
7. The default values are now empty, so the same reset empties both boxes.

::: col title="After the refusal" tag="text kept" tone=good
```page size=mini
heading: Create account
form:
  field: Username | john | good
  field: Email | john@mail.com | good
  submit: Create account
  error: Username john is taken.
console: quiet
```
The user fixes one word and clicks again.
:::
::: col title="After the success" tag="form emptied" tone=good
```page size=mini
heading: Create account
form:
  field: Username |
  field: Email |
  submit: Create account
line: Welcome, john7! | good
console: quiet
```

### `value` freezes the box

`value` is the prop that shows text in a box, so it is tempting to write `value={state.email}`. It looks the same as `defaultValue={state.email}`, but it is NOT the same thing! `value` without `onChange` freezes the box (as seen in Lesson 20). The user can no longer type a single letter, and React prints a warning:

```page caption="The Create account form with value={state.email} on the Email box: the box refuses every letter."
heading: Create account
form:
  field: Username |
  field: Email | | bad
  submit: Create account
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

A controlled box with both `value` and `onChange` would keep the text too, because React does not reset a controlled box at all. The difference is how often the page renders. The controlled box renders `App` after every keystroke by the user. The box with `defaultValue` renders `App` only when the action returns, and while the user types, the browser alone keeps the text.

```tree caption="Three ways to write the Email box, and what each one does after a refusal."
The Email box after `Username john is taken.`
- !No default value [`name="email"`] | The reset sends the box back to **nothing** | The user must **type the email again**
- +`defaultValue` from state [`defaultValue={state.email}`] | The reset sends the box back to **what the user typed** | `App` renders **only when the action returns**
- !`value` without `onChange` [`value={state.email}`] | The box **freezes** | The user **cannot type**, and React prints a **warning**
```

> [!PRINCIPLE]
> **Principle 3: defaultValue From State: Make the User's Text the Value the Reset Goes Back To**
>
> *To keep the user's text after a refusal, return it in the action's state and give each box `defaultValue` from that state.*
>
> The reset after a refusal cannot be stopped, but it only sends each box back to its default value. When the action returns what the user typed and each box reads it through `defaultValue`, the reset puts that text back. After a success, the action returns empty texts, and the same reset empties the form.
>
> **DO THIS:**
> ```jsx
> <input name="email" ~defaultValue={state.email}~ /> {/* After a refusal, the box shows john@mail.com again */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input name="email" ~value={state.email}~ /> {/* **WRONG:** value without onChange freezes the box, and the user cannot type */}
> ```

## 4. Principle 4: requestFormReset Asks for the Reset by Hand

### `form.reset()` vs. `requestFormReset(form)`

The browser's own way to reset a form is a method on the form element. React DOM adds a second function with almost the same job:

```jsx title="The browser's reset vs. React DOM's reset"
import { requestFormReset } from 'react-dom';

~form.reset();~ // The browser empties the boxes right now
~requestFormReset(form);~ // React empties the boxes when the current Transition ends
```

It looks the same, but it is NOT the same thing! Both put every box back to its default value. They differ in **when**. `form.reset()` belongs to the browser, and it runs at once, even while the action is still waiting for the server. `requestFormReset` belongs to React DOM, and it waits for the Transition it was called in. So the boxes change in the same update as the new state. This is the same reset React does for us after a form `action`. We need to ask for it by hand only when the form is submitted another way.

### A form submitted through `onSubmit` is never reset

Some forms do not pass the action to `<form action>`. A team moving an older form to Actions often keeps its `onSubmit` handler (as seen in Lessons 11 and 40) and calls the dispatcher from it. The dispatcher of `useActionState` must be called inside a Transition, so the handler wraps it in `startTransition`, which a later lesson covers (Lesson 67):

```jsx title="src/App.jsx" startLine="16"
export default function App() {
  const [state, formAction] = useActionState(signUp, initialState);

  function handleSubmit(e) {
    e.preventDefault();
    const form = e.currentTarget;
    startTransition(() => {
      ~formAction(new FormData(form));~ // Runs signUp, but no form action ran, so nothing resets the form
    });
  }

  return (
    <form ~onSubmit={handleSubmit}~> {/* No form action: React never resets this form by itself */}
      <h1>Create account</h1>
      <label>Username <input name="username" defaultValue={state.username} /></label>
      <label>Email <input name="email" defaultValue={state.email} /></label>
      <button type="submit">Create account</button>
      {state.message && <p>{state.message}</p>}
    </form>
  );
}
```

**The welcome line appears, and the box still shows the name the user typed.** The user types `john7` and clicks Create account:
1. `handleSubmit` stops the browser from sending the form, and calls `formAction` inside a Transition.
2. `signUp` returns `{ message: 'Welcome, john7!', username: '', email: '' }`.
3. React renders `App`. The default values become empty.
4. Nothing resets the form, because no form `action` ran. The boxes keep what the user typed.

```page caption="The Create account form submitted through onSubmit, after a success: the welcome line next to the old text."
heading: Create account
form:
  field: Username | john7 | bad
  field: Email | john@mail.com | bad
  submit: Create account
line: Welcome, john7! | good
console: quiet
```

### Asking for the reset inside the Transition

The fix is one line, inside the same `startTransition`:

```jsx title="src/App.jsx" startLine="1"
import { useActionState, startTransition } from 'react';
import { requestFormReset } from 'react-dom';
```

```jsx title="src/App.jsx" startLine="19"
  function handleSubmit(e) {
    e.preventDefault();
    const form = e.currentTarget;
    startTransition(() => {
      formAction(new FormData(form));
      ~requestFormReset(form);~ // The boxes reset when signUp has finished, like a form action
    });
  }
```

Now the onSubmit form behaves for the user exactly like the form with `<form action={formAction}>`. After a success, the boxes are empty. After a refusal, the reset puts back the text from `defaultValue`, as in Principle 3. Yes, it is the exact same thing! The second way only asks by hand for the reset the first way gets from React.

### `form.reset()` empties the boxes too early

`form.reset()` is the method developers already know, so it is tempting to call it in the handler, right after starting the action. But it runs at once. The boxes empty the moment the user clicks, a full second before the server answers. If the answer is `Username john is taken.`, the user has already watched the form clear as if the account was created, and then reads that it was not.

React's own docs do call `reset()` at once in one place: a chat box (as seen in Lesson 44). There the user always wants the box empty right after sending, whatever the server answers. A sign-up form is the opposite case.

> [!PRINCIPLE]
> **Principle 4: requestFormReset: Ask React for the Reset When the Form Has No Action**
>
> *When a form is submitted without the `action` prop, call `requestFormReset(form)` from `'react-dom'` inside the Transition, so the boxes reset when the action ends.*
>
> React resets a form for us only after a function passed to `<form action>`. A form submitted through `onSubmit` keeps its old text after a success. `requestFormReset` asks React for the same reset, and it waits for the Transition, while the browser's `form.reset()` empties the boxes before the server has answered.
>
> **DO THIS:**
> ```jsx
> startTransition(() => {
>   formAction(new FormData(form));
>   ~requestFormReset(form);~ // The boxes reset together with the new state
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> startTransition(() => {
>   formAction(new FormData(form));
> });
> ~form.reset();~ // **WRONG:** the boxes empty at the click, before the server says whether the name is free
> ```

## 5. Principle 5: name and a Submit Button Keep the Form Working Without JavaScript

### A user who clicks before the JavaScript has loaded

Picture the same Create account form on a phone with a slow connection. The page has appeared, but the JavaScript of the app, the **JavaScript bundle** as React's docs call it, is still downloading. The user clicks Create account.

Whether that click sends anything depends on what the form's `action` holds. Compare two forms that look the same on the screen:

```jsx title="An action with a URL vs. an action with a function"
<form ~action="/signup"~ method="post"> {/* The browser sends the form to /signup by itself */}
<form ~action={formAction}~> {/* Only React can call formAction, so React must be running */}
```

They look the same, but they are NOT the same thing! A URL is something the browser understands without any JavaScript. It reads every box that has a `name`, and sends the values to `/signup` with the POST method. A function exists only inside our JavaScript. Until React runs, there is nobody to call it.

### Progressive enhancement

Building a page so that it works at this moment has a name: **progressive enhancement**. MDN describes it as giving a baseline of essential content and functionality to as many users as possible, then adding the richer version for browsers that can run it.

Think of a building with stairs and an elevator. The stairs take everyone to the top floor. The elevator is faster and nicer, and when it is not running yet, the stairs still work. For a form, the stairs are plain HTML that the browser can send by itself. The elevator is React's version: the pending button, the error line without a reload, the reset.

What does a form need so the browser can send it alone? Four parts, all of them HTML:
1. **A real `<form>` element.**
2. **A `name` on every box.** The browser sends only boxes that have a name, and the name becomes the key in the form data.
3. **A real submit button**, a `<button type="submit">`.
4. **An action the browser can send without JavaScript**: a URL, or a Server Function in a framework that renders the page on the server.

Our form already has the first three parts, because `FormData` needs them too (as seen in Lesson 40). The same `name` that `formData.get('username')` reads is the name the browser would send. They cost nothing extra.

```tree caption="The four parts a form needs so the browser can send it before JavaScript loads."
What the browser can use alone
- +A real `<form>` [`<form>`] | The browser knows **how to submit** it
- +A `name` on every box [`name="username"`] | The browser **sends only named boxes**
- +A real submit button [`<button type="submit">`] | A click **submits the form** with no handler
- +An action the browser can send [`action="/signup"`] | A **URL**, or a **Server Function** from a framework
```

### What our Vite app shows before its JavaScript runs

**Our Vite app shows the user nothing at all before its JavaScript runs.** Not a broken form, but an empty page. Here is why, in order:
1. The browser receives `index.html`, which holds only `<div id="root"></div>` (as seen in Lesson 07).
2. `main.jsx` has not run yet, so React has not rendered `App`.
3. There is no form on the page to click.

```page caption="Our Create account app on a phone whose JavaScript has not loaded yet."
blank
```

```dom caption="What the Elements panel shows before main.jsx runs: the root div with nothing inside."
<body>
! <div id="root"></div> | note: Empty until main.jsx runs and React renders App
</body>
```

So in an app that renders only in the browser, progressive enhancement starts later, when the team renders the page on the server (Lesson 102). Then the HTML of the form arrives before the bundle. With a Server Function in its `action`, React's docs say such a form can be submitted before the JavaScript bundle is loaded (Lesson 110), and `useActionState` can replay a submit the user made before React took over the page (Lesson 137). Our lesson keeps the four HTML parts in place, so the form is ready for that step.

### The mistake that breaks it

The classic mistake is building the button or the boxes in a way only JavaScript understands:
1. A developer builds the Create account button as a `<div onClick={...}>`, because a click handler does the job.
2. Another box has no `name`, because the React code reads its value from state.
3. Everything works while the JavaScript runs.
4. Later, the team renders the page on the server so it appears fast on slow phones.
5. A user clicks before the bundle loads. A `<div>` is not a submit button, so nothing is sent. And a box without a `name` is never part of the form data.

> [!PRINCIPLE]
> **Principle 5: Progressive Enhancement: name and a Submit Button Keep the Form Working Without JavaScript**
>
> *A form works before its JavaScript loads only when it is a real `<form>` with a `name` on every box and a real submit button, and its action is one the browser can send by itself.*
>
> Progressive enhancement gives every user a basic version that works, and adds React's richer version when the JavaScript runs. The browser can send a form alone only from HTML: the `<form>`, the named boxes, the submit button, and a URL or a Server Function in `action`. A function from our own code needs React running, and a click on a `<div>` needs a handler that has not loaded yet.
>
> **DO THIS:**
> ```jsx
> <form action={formAction}>
>   <input ~name="email"~ /> {/* The browser and FormData both read this name */}
>   <button ~type="submit"~>Create account</button> {/* A click submits the form, with or without a handler */}
> </form>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <section>
>   <input value={email} onChange={e => setEmail(e.target.value)} />
>   <div ~onClick={handleCreate}~>Create account</div> {/* **WRONG:** no form, no name, no submit button: nothing is sent before JavaScript loads */}
> </section>
> ```

## Putting All Five Principles Together

### The complete project

Here is the finished Create account form. The stand-in server refuses `john`:

```js title="src/api.js"
const takenUsernames = ['john'];

export function createAccount(username) {
  return new Promise(resolve => {
    setTimeout(() => {
      if (takenUsernames.includes(username)) {
        resolve(`Username ${username} is taken.`);
      } else {
        resolve(null);
      }
    }, 1000);
  });
}
```

The form passes `formAction` to `<form action>`, so React resets it after every action. The action returns what the user typed, and the boxes read it through `defaultValue`:

```jsx title="src/App.jsx"
import { useActionState } from 'react';
import { createAccount } from './api.js';

const initialState = { message: '', username: '', email: '' };

async function signUp(previousState, formData) {
  const username = formData.get('username');
  const email = formData.get('email');
  const error = await createAccount(username);
  if (error) {
    return { message: error, username, email }; // Principle 2: returned, not thrown
  }
  return { message: `Welcome, ${username}!`, username: '', email: '' };
}

export default function App() {
  const [state, formAction] = useActionState(signUp, initialState);

  return (
    <form ~action={formAction}~> {/* Principle 1: React resets the form after signUp returns */}
      <h1>Create account</h1>
      <label>Username <input ~name="username"~ defaultValue={state.username} /></label> {/* Principle 5: a name the browser can send */}
      <label>Email <input name="email" ~defaultValue={state.email}~ /></label> {/* Principle 3: the reset puts back the typed email */}
      <button ~type="submit"~>Create account</button> {/* Principle 5: a real submit button */}
      {state.message && <p>{state.message}</p>}
    </form>
  );
}
```

### What React does after one click

`App` is the only component, so React calls it once on every render. What matters here is the order of the steps after the user clicks Create account:

```tree dir=right caption="The order of the steps after the user clicks Create account on the finished form."
One click on Create account
- +1. React builds the form data [`FormData`] | Reads **every named box**
- +2. React calls `signUp` in a Transition [`await createAccount`] | Waits **one second** for the stand-in server
- +3. `signUp` returns the new state [`{ message, username, email }`] | Returned, **not thrown**: the action **succeeded**
- +4. React renders `App` [`defaultValue={state.email}`] | Each box gets its **new default value**
- +5. React resets the form | Each box goes back to its default value | **Text kept** after a refusal, **form empty** after a success
```

| The Situation | The Plain Habit | The React Rule |
| :--- | :--- | :--- |
| **A successful action** | Empty every box by hand at the end of the handler | React resets every uncontrolled box after a function in `<form action>` returns |
| **A refusal from the server** | Expect the boxes to stay, because the server said no | A returned error is a success for React, so the form is reset |
| **Keeping the user's text** | Write `value` so the box shows the text | Return the text in state and read it through `defaultValue`, so the reset puts it back |
| **A form submitted through `onSubmit`** | Call `form.reset()` right after the click | Call `requestFormReset(form)` inside the Transition, so the reset waits for the action |
| **A user whose JavaScript has not loaded** | Build the button as a `<div onClick>` and leave boxes without `name` | Use a real `<form>`, a `name` on every box, a submit button, and an action the browser can send |

## For the Interview

> **The Interview Question:** How do React 19 form actions manage automatic form resets, manual requestFormReset, and progressive enhancement?

### How to Answer Clearly in 30 Seconds

"When a function is passed to `<form action>`, React calls it with the form data, and after it succeeds, React resets every uncontrolled field of the form. Succeeds means it did not throw, so a returned validation error also clears the boxes. Three points follow:
1. **Keeping the text after a refusal**: the reset puts each field back to its default value, so the action returns the submitted values in `useActionState` state, and each field reads them through `defaultValue`.
2. **`requestFormReset`**: when a form is submitted without the `action` prop, for example through `onSubmit`, we call `requestFormReset(form)` from `react-dom` inside a Transition to get the same reset when the action ends.
3. **Progressive enhancement**: a basic version that works for everyone, made richer when JavaScript runs. A form needs a real `<form>`, a `name` on every field, a real submit button, and an action the browser can send without JavaScript, such as a URL or a Server Function in a server-rendered page."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Our sign-up form clears the email after the server says the username is taken. Why, and how do you fix it?"**
   React resets a form after every action that does not throw, and a returned error message is a normal return value. The reset sends each box back to its default value. So the action returns the submitted values together with the message, and each box gets `defaultValue` from that state. After a refusal, the reset puts the text back. After a success, the action returns empty values, and the same reset empties the form. Writing `value` instead freezes the box.
2. **"What is the difference between `form.reset()` and `requestFormReset(form)`?"**
   Both put every box back to its default value. `form.reset()` is the browser's method and runs at once, so the boxes empty before the server has answered. `requestFormReset` comes from React DOM and is called inside a Transition, so the reset happens when the action ends, together with the new state. React does this same reset for us after a function in `<form action>`, so we call it by hand only for a form submitted another way.
3. **"Does a form with a function in `action` work before JavaScript loads?"**
   Not by itself. A function from our own code exists only after React runs, and a Vite app that renders only in the browser has no form on the page at all before `main.jsx` runs. A form with a URL in `action` is sent by the browser alone. In a framework that renders the page on the server, a Server Function in `action` makes the form progressively enhanced: it can be submitted before the bundle loads, and `useActionState` can replay that submit once React takes over.

```tree caption="Interview summary: what decides whether the boxes keep the user's text after a form action."
Does the box keep the text after the action?
- !Uncontrolled box with no default value | The reset sends it back to **nothing** | Text **lost** after a refusal
- +Uncontrolled box with `defaultValue` from state | The reset sends it back to **the returned text** | Text **kept** after a refusal, **emptied** after a success
- +Controlled box with `value` and `onChange` | React **does not reset** it | Our code **clears the state** itself
```
