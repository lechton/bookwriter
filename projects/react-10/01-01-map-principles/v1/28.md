# Q28 Principle Map (River Version v1): Passing Data Deeply with Context and use()

- **Version**: River Version (`v1`), written under `skills/v10.6`
- **Bank Row**: `questions/questions.md` row 28

- **Interview Question**: *How do you pass data many levels deep without prop drilling, and how does the use() API read it?*

## Scope

Covered here:
- Prop drilling: a value passed as a prop through components in the middle that never use it, only pass it further down.
- The docs' three steps: create a context with `createContext(defaultValue)`; use it from the component that needs the data; provide it from the component that specifies the data.
- The context object: it holds no information itself; it names which context components provide or read.
- The default value: used only when there is no provider above at all; it is static and never changes.
- Reading with `useContext(ThemeContext)`: a Hook, called at the top level of a component.
- Providing with `<ThemeContext value={theme}>`, the React 19 way, and `<ThemeContext.Provider value={theme}>`, the legacy way before React 19.
- Context with state: when the provided value changes, React re-renders the components that read it.
- Reading with `use(ThemeContext)`: the same value as `useContext`, and unlike `useContext` it can be called inside `if` and loops.
- The closest provider above wins: a provider in the same component does not count; a nested provider overrides the value for its part of the tree; different contexts do not override each other.
- The docs' "Before you use context": pass props first, or extract components and pass JSX as `children`; the docs' four use cases for context.
- The Troubleshooting entries this page can show: the reader does not see the provider's value; `undefined` from a provider with no `value` or a wrong prop name; looking for a way to change the default value.

## Start of the Lecture

**Opening Essence of the chapter**:
- The question of the lesson: how does a value chosen at the top of the tree reach a component far below, without every component in between passing it on?
- Smallest code, two versions of one three-level tree, with no project files:
  1. With props: `function App() { return <Page theme="dark" />; }`, `function Page({ theme }) { return <ShareButton theme={theme} />; }`, `function ShareButton({ theme }) { return <button className={theme}>Share</button>; }`. `Page` receives `theme` and never uses it.
  2. With context: `const ThemeContext = createContext('light');`, `function App() { return <ThemeContext value="dark"><Page /></ThemeContext>; }`, `function Page() { return <ShareButton />; }`, `function ShareButton() { const theme = useContext(ThemeContext); return <button className={theme}>Share</button>; }`. `Page` has no `theme` at all.
  3. Both pages show the same Share button with the class `dark`. `unconfirmed` until the lab runs it.
- Confusion to say out loud: *"Yes, it is the exact same thing!"* for what the user sees. The docs, after the same change: "It's the same result as the original code, but you did not need to pass the `level` prop to each `Heading` component!" What the two share: `App` decides the value, `ShareButton` uses it. The one difference: with props, every component on the way carries the value; with context, the components in the middle do not mention it.
- The docs' own frame, from the Intro: "*Context* lets the parent component make some information available to any component in the tree below it, no matter how deep, without passing it explicitly through props." The docs join the two parts with a dash; the map writes a comma.
- The docs' image: "Wouldn't it be great if there were a way to 'teleport' data to the components in the tree that need it without passing props?"
- Everyday image for prop drilling, offered once for the opening only: a note passed hand to hand along a row of people, where everyone in the middle must hold it and pass it on, though only the last person reads it. After the opening, the lecture uses React's words only: "note" and "row" never stand for code. See Open Issues.
- Key idea: context does not pass the value through the middle; the reading component asks for it, and React finds the closest provider above.
- What is at stake for the user: the user clicks `Toggle theme` and the Share button must turn dark. With props, a middle component that forgets to pass `theme` on leaves the button light. With context and no provider above, the button also stays light, because it reads the default value.
- Where readers usually go wrong:
  1. They think context is one global variable for the whole app. It is not: each reader gets the value of the closest provider above it, and a nested provider can give one part of the tree another value.
  2. They think the value given to `createContext` is the value to change. The docs: "This value never changes. React only uses this value as a fallback if it can't find a matching provider above."
  3. They read the context in the same component that provides it, and get the default value.
  4. They reach for context whenever a prop goes two levels down. The docs: "Just because you need to pass some props several levels deep doesn't mean you should put that information into context."

**Theme**: a news site lets the user switch between a light and a dark theme at the top, and the Share button inside the article card, four components below `App`, must follow the switch.

**Ways** (developers really choose between these for the same job, from the docs' "Before you use context"):
1. Pass props, even through many components: fits most cases. The docs: "It may feel like a slog, but it makes it very clear which components use which data!"
2. Extract components and pass JSX as `children`: fits when the components in the middle only lay out the page. The docs: "This reduces the number of layers between the component specifying the data and the one that needs it."
3. Context: fits when distant components in different parts of the tree need the same information. The docs: "If neither of these approaches works well for you, consider context."
4. A reducer together with context, for app-wide state: Lesson 29, named only.

**Example page chosen for this lesson**: a news article page with a theme switch.
- Parts of the page: a button `Toggle theme` at the top; under it, one article card with the title `New Park Opens` and, at the bottom of the card, a bar with one button `Share`.
- What the user does: clicks `Toggle theme`. The Share button turns dark, with a dark background and white text. A second click turns it light again.
- State: one string, `theme`, in `App`: `const [theme, setTheme] = useState('light');` The toggle: `onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}`, the docs' own line and label.
- The tree: `App` renders `Page`; `Page` renders `ArticleCard`; `ArticleCard` renders `ActionBar`; `ActionBar` renders `ShareButton`. `ShareButton` renders `<button className={theme}>Share</button>`.
- At the start of the lesson, `theme` travels as a prop: `<Page theme={theme} />`, `<ArticleCard theme={theme} />`, `<ActionBar theme={theme} />`, `<ShareButton theme={theme} />`. `Page`, `ArticleCard`, and `ActionBar` receive `theme` and never use it.
- At the end of the lesson: `src/ThemeContext.js` exports `ThemeContext`; `App` wraps `<Page />` in `<ThemeContext value={theme}>`; `ShareButton` reads `use(ThemeContext)`; no middle component mentions `theme`.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>` and `import './index.css';`, `src/index.css` with two rules, `.light` and `.dark`, `src/App.jsx`, `src/components/Page.jsx`, `src/components/ArticleCard.jsx`, `src/components/ActionBar.jsx`, `src/components/ShareButton.jsx`, and from Principle 1 `src/ThemeContext.js`.
- Names follow the docs' own code: `ThemeContext`, `createContext('light')`, `theme`, `setTheme`, `Toggle theme`, `className={theme}`, a contexts file as the docs' `Contexts.js`.

## Principles

### Principle 1: createContext Makes ThemeContext

- **Rule**: `createContext(defaultValue)`, called outside any component, returns a context object; the object holds no information itself, it only names which context components provide and read; export it from its own file so every file can import the same object.
- **Move**: Smallest code first, because creating a context is two lines and nothing appears on the page yet.
- **Opening Essence**:
  - Smallest code: `import { createContext } from 'react';` and `export const ThemeContext = createContext('light');`
  - Key idea, from the reference: "**The context object itself does not hold any information.** It represents _which_ context other components read or provide."
  - What the default value is, from the reference: "The value that you want the context to have when there is no matching context provider in the tree above the component that reads context." "The default value is meant as a 'last resort' fallback. It is static and never changes over time."
  - Where readers go wrong: they think `ThemeContext` is a box holding `'light'` that they can later set to `'dark'`.
- **Root Distinction**:
  - Junior: "`ThemeContext` holds the theme, so changing the theme means changing `ThemeContext`."
  - Senior: `ThemeContext` is only a name that a provider and a reader share; the value lives in the provider, and the default is used only when no provider is above.
- **Simplest version**:
  - `src/ThemeContext.js`: `import { createContext } from 'react';` and `export const ThemeContext = createContext('light');`
  - The docs' advice when there is no meaningful default: `createContext(null)`.
- **Words to teach**:
  - *context*: the docs' Intro: context lets a parent "make some information available to any component in the tree below it". Provided by React. Needed in the first line of the principle.
  - *`createContext`*: a function from `'react'`. The reference: "Call `createContext` outside of any components to create a context." Needed at the first line of `ThemeContext.js`.
  - *context object*: what `createContext` returns. Provided by React. Needed when the reader asks what `ThemeContext` holds.
  - *default value*: the only argument of `createContext`. Needed at `'light'`.
  - Known: named `export`, `import { ... } from`, Lesson 05. A component declared at the top level, Lesson 04.
  - Helper: none.
- **Side by side**:
  - "with `createContext('light')`" and "with `createContext(null)`": NOT the same result for a component with no provider above. With `'light'`, it gets `'light'`; with `null`, it gets `null`. The docs: with a meaningful default, "if you accidentally render some component without a corresponding provider, it won't break. This also helps your components work well in a test environment without setting up a lot of providers in the tests."
  - "the context in `ThemeContext.js`" and "the context in the same file as its components": the exact same context. The docs: "it's common to declare contexts in a separate file", and "This works similar to importing and exporting components."
- **Surprises**: none. Nothing appears on the page in this step.
- **Where did that come from?**:
  - `createContext`: imported from `'react'`.
  - `ThemeContext` in other files: a named export, so other files import it with curly braces, `import { ThemeContext } from '../ThemeContext.js';`, Lesson 05.
- **Real beginner mistake** (the reference Troubleshooting, "I can't find a way to change the context value"):
  1. A developer writes `createContext('light')` and reads `ThemeContext` in a component.
  2. The developer wants the page to turn dark after a click.
  3. The developer looks for a way to change the `'light'` given to `createContext`.
  4. There is none. The docs: "This value never changes. React only uses this value as a fallback if it can't find a matching provider above."
  5. The docs' fix: "add state and wrap components in a context provider." That is Principle 3.
- **Interview depth**:
  - The context object has a few properties: `SomeContext` provides the value; `SomeContext.Consumer` is "an alternative and rarely used way to read the context value"; `SomeContext.Provider` "is a legacy way to provide the context value before React 19."
  - One file can create many contexts: the docs' `Contexts.js` exports `ThemeContext` and `AuthContext = createContext(null)`.
  - The reference caveat: if the build produces duplicate modules, as can happen with symlinks, context breaks, because the provider's and the reader's `SomeContext` must be "*exactly* the same object, as determined by a `===` comparison."
  - The docs' default can be "any kind of value (even an object)".
- **React does**:
  - Page: nothing new; `ThemeContext.js` is not read by any component yet.
  - Console: nothing.
  - Elements panel: nothing.
- **Example step**:
  - Creates `src/ThemeContext.js` with `import { createContext } from 'react';` and `export const ThemeContext = createContext('light');`
  - The other files still pass `theme` as a prop.
- **Code names**: `src/ThemeContext.js`, `createContext`, `ThemeContext`, `'light'`, `null`, `import { createContext } from 'react'`, `export const ThemeContext = createContext('light')`, `Contexts.js`, `AuthContext`, `SomeContext.Provider`, `SomeContext.Consumer`

### Principle 2: useContext Leaves the Share Button Light

- **Rule**: `useContext(ThemeContext)`, called at the top level of a component, returns the value of the closest `ThemeContext` provider above that component; with no provider above, it returns the default value.
- **Move**: Steps for a surprise, because the page looks right on the first load and the Share button stays light after the user clicks `Toggle theme`.
- **Opening Essence**:
  - Smallest code, two ways for `ShareButton` to get `theme`:
    1. `function ShareButton({ theme }) { return <button className={theme}>Share</button>; }`
    2. `function ShareButton() { const theme = useContext(ThemeContext); return <button className={theme}>Share</button>; }`
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both create a variable named `theme`, and both show a light button on the first load. The first gets `theme` from its parent's tag. The second asks React for the closest `ThemeContext` above, and here none exists yet.
  - The docs: "**`useContext` tells React that the `Heading` component wants to read the `LevelContext`.**" And: "That would require some way for a child to 'ask' for data from somewhere above in the tree."
- **Root Distinction**:
  - Junior: "`App` holds `theme` and `ShareButton` reads `ThemeContext`, so the button gets `App`'s theme."
  - Senior: reading a context and providing it are two separate steps; a state variable in `App` reaches no reader until `App` provides it.
- **Simplest version**:
  - `import { useContext } from 'react';` and `import { ThemeContext } from '../ThemeContext.js';`
  - `const theme = useContext(ThemeContext);` as the first line of `ShareButton`.
- **Words to teach**:
  - *`useContext`*: a React Hook. The reference: "`useContext` is a React Hook that lets you read and subscribe to context from your component." Provided by React. Needed at the first line of `ShareButton`.
  - *read and subscribe*: the reference: "The returned value is always up-to-date. React automatically re-renders components that read some context if it changes." Needed in Principle 3, when the theme changes; named here.
  - *context value*: what `useContext` returns, "determined as the `value` passed to the closest `SomeContext` above the calling component in the tree." Needed when the reader asks which value comes back.
  - Known: Hook, `useState`, Lesson 12. The docs: "Just like `useState` and `useReducer`, you can only call a Hook immediately inside a React component (not inside loops or conditions)." The rule itself: Lesson 38.
  - Helper: none.
- **Side by side**:
  - "with `({ theme })`" and "with `useContext(ThemeContext)`": NOT the same thing. The same variable name; the first comes from the parent's tag, the second from the closest provider above.
- **Surprises**:
  - The user clicks `Toggle theme`, and the Share button stays light:
    1. `ShareButton` calls `useContext(ThemeContext)`. `Page`, `ArticleCard`, and `ActionBar` no longer pass `theme`.
    2. On the first load, React finds no `ThemeContext` provider above `ShareButton` and returns the default, `'light'`.
    3. The button gets `className="light"`, and `App`'s state is also `'light'`, so the page looks right.
    4. The user clicks `Toggle theme`. `App` sets `theme` to `'dark'` and renders again.
    5. `ShareButton` still finds no provider above it and gets `'light'` again.
  - The docs, on the same step: "Notice this example doesn't quite work, yet! All the headings have the same size because **even though you're *using* the context, you have not *provided* it yet.** React doesn't know where to get it!"
- **Where did that come from?**:
  - `'light'` in `ShareButton`: the default value from `createContext('light')` in Principle 1, not `App`'s state.
  - `ThemeContext` in `ShareButton.jsx`: the named import from `../ThemeContext.js`.
- **Real beginner mistake** (the reference Troubleshooting, "My component doesn't see the value from my provider", second case):
  1. A developer adds `useContext(ThemeContext)` in `ShareButton`.
  2. The developer removes `theme` from every middle component.
  3. The developer forgets to wrap any part of the tree in a provider.
  4. The button shows the default on every render. The docs: "You may have forgotten to wrap your component with `<SomeContext>`, or you might have put it in a different part of the tree than you thought."
  5. The docs' way to check the tree: React Developer Tools, Lesson 64.
- **Interview depth**:
  - The reference Parameters: "The context itself does not hold the information, it only represents the kind of information you can provide or read from components."
  - The reference: "To determine the context value, React searches the component tree and finds **the closest context provider above** for that particular context."
  - The docs' Note: context passes "any information needed by the entire subtree: the current color theme, the currently logged in user, and so on."
- **React does**:
  - Page: the Share button is light on the first load and stays light after each click on `Toggle theme`. From the docs; for this page `unconfirmed`.
  - Console: no warning for reading a context with no provider above. `unconfirmed`.
  - Elements panel: `<button class="light">Share</button>` before and after the click. `unconfirmed`.
- **Example step**:

### Principle 3: <ThemeContext value={theme}> Turns the Share Button Dark

- **Rule**: wrapping components in `<ThemeContext value={theme}>` gives `theme` to every component inside that reads `ThemeContext`, no matter how deep; when `theme` is state and changes, React re-renders the components that read it.
- **Move**: Side by side, because the page with the provider and the page of Principle 2 look the same on the first load and are NOT the same thing after one click; and `<ThemeContext>` against `<ThemeContext.Provider>` is the exact same thing.
- **Opening Essence**:
  - Smallest code: `<ThemeContext value="dark"><Page /></ThemeContext>`
  - Key idea, from the docs: this tells React "if any component inside this `<Section>` asks for `LevelContext`, give them this `level`." On this page: any component inside asking for `ThemeContext` gets `theme`.
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* `<ThemeContext value={theme}>` and `<ThemeContext.Provider value={theme}>`. The reference Note: "Starting in React 19, you can render `<SomeContext>` as a provider. In older versions of React, use `<SomeContext.Provider>`."
- **Root Distinction**:
  - Junior: "The provider sends `theme` to its child `Page`, and `Page` passes it on."
  - Senior: `Page`, `ArticleCard`, and `ActionBar` pass nothing; `ShareButton` reads `ThemeContext`, and React finds the provider above it.
- **Simplest version**:
  - `App.jsx`: `import { ThemeContext } from './ThemeContext.js';`
  - `return (<ThemeContext value={theme}><button onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}>Toggle theme</button><Page /></ThemeContext>);` The writer may lay this out on several lines.
- **Words to teach**:
  - *context provider, provider*: the tag `<ThemeContext>` with a `value`. The reference: "Wrap your components into a context provider to specify the value of this context for all components inside." Provided by React, from the context object of Principle 1. Needed at the line that wraps `<Page />`.
  - *`value`*: the provider's prop. The reference: "The value that you want to pass to all the components reading this context inside this provider, no matter how deep. The context value can be of any type." Needed at the same line.
  - *legacy*: the docs' word for `<SomeContext.Provider>`. Needed in the Side by side.
  - Known: state, `useState`, setter, Lesson 12. A setter triggers a re-render, Lesson 13. `value="dark"` against `value={theme}`, Lesson 03. The ternary, Lesson 10.
  - Helper: none.
- **Side by side**:
  - "with `<ThemeContext value={theme}>` around `<Page />`" and "with no provider", as in Principle 2: NOT the same thing. The same light button on the first load; after one click, dark with the provider and light without.
  - "with `<ThemeContext value={theme}>`" and "with `<ThemeContext.Provider value={theme}>`": the exact same thing. The React 19 blog: "New Context providers can use `<Context>` and we will be publishing a codemod to convert existing providers. In future versions we will deprecate `<Context.Provider>`."
  - "with `value=\"dark\"`" and "with `value={theme}`": NOT the same thing. The docs: "`value=\"dark\"` passes the `\"dark\"` string, but `value={theme}` passes the value of the JavaScript `theme` variable with JSX curly braces."
  - "with `value={theme}`" and "with `theme={theme}`" on the provider: NOT the same thing. The docs: "prop should be called 'value'".
- **Surprises**:
  - The user clicks `Toggle theme`, and the Share button turns dark although no middle component mentions `theme`:
    1. `setTheme('dark')` runs in `App`'s handler.
    2. React renders `App` again; the provider now has `value` `'dark'`.
    3. The provider received a different `value`. React compares the old and new values with `Object.is`.
    4. React re-renders the components inside that read `ThemeContext`. `ShareButton` calls `useContext(ThemeContext)` and gets `'dark'`.
    5. The button gets `className="dark"`.
  - The reference: "Now any `Button` inside of the provider will receive the current `theme` value. If you call `setTheme` to update the `theme` value that you pass to the provider, all `Button` components will re-render with the new `'light'` value."
- **Where did that come from?**:
  - `value` on `<ThemeContext>`: the provider's prop, read by React, not by any of our components.
  - `'dark'` in `ShareButton`: `App`'s state, given to the provider as `value`, found by React above `ShareButton`.
  - The `<ThemeContext>` tag itself: the context object from Principle 1 used as a tag, imported in `App.jsx`.
- **Real beginner mistake** (the reference Troubleshooting, "I am always getting `undefined` from my context although the default value is different"):
  1. A developer writes `<ThemeContext theme={theme}>` around `<Page />`, matching the prop name used before.
  2. The provider has no `value`. The docs: "If you forget to specify `value`, it's like passing `value={undefined}`."
  3. `ShareButton` gets `undefined`, not the default `'light'`. The docs: the default "is only used **if there is no matching provider above at all.**"
  4. The button has no class and shows neither theme.
  5. The docs: "In both of these cases you should see a warning from React in the console." The fix: call the prop `value`.
- **Interview depth**:
  - The reference caveat: "React **automatically re-renders** all the children that use a particular context starting from the provider that receives a different `value`. The previous and the next values are compared with the `Object.is` comparison. Skipping re-renders with `memo` does not prevent the children receiving fresh context values." `memo`: Lesson 55.
  - The docs: "Context is not limited to static values. If you pass a different value on the next render, React will update all the components reading it below! This is why context is often used in combination with state."
  - An object value with state and its setter, `value={{ currentUser, setCurrentUser }}`, lets a deep component change the state. Named only; with a reducer, Lesson 29.
  - An object literal as `value` is a new object on each render of the provider, so every reader re-renders; `useMemo` and `useCallback` fix it. Lesson 59, named only.
  - Many providers near the root, a "pyramid" of contexts: "There is nothing wrong with that." They can be moved into one component such as `MyProviders`.
- **React does**:
  - Page: the Share button is light on the first load, dark after one click on `Toggle theme`, light after a second. `unconfirmed`.
  - Console, a provider with no `value` or with `theme={theme}`: a warning from React, exact text `unconfirmed`.
  - Elements panel: `<button class="dark">Share</button>` after the click. The provider adds no element of its own: `unconfirmed`. With `value` missing, `<button>Share</button>` with no `class`: `unconfirmed`.
- **Example step**:
  - `App.jsx`: adds `import { ThemeContext } from './ThemeContext.js';` and wraps the toggle and `<Page />` in `<ThemeContext value={theme}>`.
  - No other file changes. The page works again, with no `theme` prop in `Page`, `ArticleCard`, or `ActionBar`.
- **Code names**: `App.jsx`, `<ThemeContext value={theme}>`, `<ThemeContext.Provider value={theme}>`, `value`, `value="dark"`, `theme={theme}`, `setTheme`, `setTheme(theme === 'dark' ? 'light' : 'dark')`, `Toggle theme`, `'dark'`, `undefined`, `className="dark"`, `<button class="dark">Share</button>`, `Object.is`, `memo`, `currentUser`, `setCurrentUser`, `MyProviders`

### Principle 4: use(ThemeContext) Reads the Same Theme

- **Rule**: `use(ThemeContext)` returns the same value as `useContext(ThemeContext)`, from the closest provider above; unlike `useContext`, it can be called inside `if` and loops; it must be called inside a component or a Hook.
- **Move**: Side by side, because `useContext(ThemeContext)` and `use(ThemeContext)` at the top of `ShareButton` are the exact same thing, and they differ only in where each may be called.
- **Opening Essence**:
  - Smallest code, two first lines for `ShareButton`:
    1. `const theme = useContext(ThemeContext);`
    2. `const theme = use(ThemeContext);`
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* The docs: "When a context is passed to `use`, it works similarly to `useContext`." Both search for "the closest context provider above". The one difference: "While `useContext` must be called at the top level of your component, `use` can be called inside conditionals like `if` and loops like `for`."
  - The docs' smallest code for that difference: `function HorizontalRule({ show }) { if (show) { const theme = use(ThemeContext); return <hr className={theme} />; } return false; }`
- **Root Distinction**:
  - Junior: "`use` is a new kind of context, or a faster `useContext`."
  - Senior: `use` reads the same context from the same provider; it only lifts the top-level limit, and it also reads Promises, Lesson 71.
- **Simplest version**:
  - `import { use } from 'react';` and `const theme = use(ThemeContext);` in `ShareButton`.
- **Words to teach**:
  - *`use`*: the reference: "`use` is a React API that lets you read a resource during rendering, such as a Promise or context." Provided by React, imported from `'react'`. Needed at the changed line in `ShareButton`.
  - *React API*: the docs' word for `use`. The reference, in the Promise section: "Despite its name, `use` is not a Hook. Unlike Hooks, it can be called inside loops and conditional statements like `if`." Needed when the reader asks why the name starts with `use`.
  - Known: `if`, Lesson 10. Hook, Lesson 12. The top-level rule for Hooks: Lesson 38, named only.
  - Helper: `for` loop, named in the docs' sentence only, plain JavaScript.
- **Side by side**:
  - "with `useContext(ThemeContext)`" and "with `use(ThemeContext)`" at the top of `ShareButton`: the exact same thing. Same value, same provider, same re-render after a click.
  - "with `use(ThemeContext)` inside `if (show)`" and "with `useContext(ThemeContext)` inside `if (show)`": NOT the same thing. The first is allowed; the second breaks the docs' rule "you can only call a Hook immediately inside a React component (not inside loops or conditions)". The error itself: Lesson 38, `unconfirmed`.
- **Surprises**: none. After the change, the page behaves exactly as in Principle 3.
- **Where did that come from?**:
  - `use`: imported from `'react'`, as `useContext` was.
  - `show` in the docs' `HorizontalRule`: a prop from its parent, `<Button show={true}>` in the docs' example.
- **Real beginner mistake** (the `use` reference Pitfall, which repeats the `useContext` one):
  1. A developer moves the reading into the component that provides: `App` calls `use(ThemeContext)` and returns `<ThemeContext value={theme}>`.
  2. The developer expects `use` to see the provider, since `use` is more flexible.
  3. `use` returns the default `'light'`. The docs: "Like `useContext`, `use(context)` always looks for the closest context provider *above* the component that calls it. It searches upwards and **does not** consider context providers in the component from which you're calling `use(context)`."
  4. The full case is Principle 5.
- **Interview depth**:
  - The reference Caveats: "`use` must be called inside a Component or a Hook." "Reading context with `use` is not supported in Server Components."
  - `use(promise)` reads a Promise and the component suspends while it is pending: Lessons 69 and 71.
  - The docs' "Reading a Promise from context": `const userPromise = use(UserContext); const user = use(userPromise);` "Reading the value requires two `use` calls because the context value itself isn't awaited." Lesson 71, named only.
  - The syllabus card calls `use` the flexible way to read context in React 19; the docs show both, and `useContext` stays fully supported.
- **React does**:
  - Page: unchanged from Principle 3. `unconfirmed`.
  - Console: nothing. `unconfirmed`.
  - Elements panel: unchanged. `unconfirmed`.
- **Example step**:
  - `ShareButton.jsx`: `import { useContext } from 'react';` becomes `import { use } from 'react';`; `useContext(ThemeContext)` becomes `use(ThemeContext)`.
  - No other file changes.
- **Code names**: `ShareButton.jsx`, `use`, `import { use } from 'react'`, `const theme = use(ThemeContext)`, `useContext(ThemeContext)`, `HorizontalRule`, `show`, `if (show)`, `<hr className={theme} />`, `return false`, `UserContext`, `userPromise`, `use(userPromise)`

### Principle 5: The Closest ThemeContext Above Wins

- **Rule**: a component that reads a context gets the `value` of the closest provider above it in the tree; a provider returned by the same component does not count; a nested provider with another value overrides the value for its part of the tree; different contexts never override each other.
- **Move**: Steps for a surprise, because `App` provides `'dark'` and reads `'light'`.
- **Opening Essence**:
  - Smallest code, the docs' override: `<ThemeContext value="dark"> ... <ThemeContext value="light"><Footer /></ThemeContext> ... </ThemeContext>`. The button inside `Footer` gets `'light'`; the buttons outside get `'dark'`.
  - Key idea, from the docs: "The component will use the value of the nearest `<LevelContext>` in the UI tree above it."
  - The docs' comparison: CSS property inheritance. "In CSS, you can specify `color: blue` for a `<div>`, and any DOM node inside of it, no matter how deep, will inherit that color unless some other DOM node in the middle overrides it with `color: green`. Similarly, in React, the only way to override some context coming from above is to wrap children into a context provider with a different value."
  - The docs' second half of the comparison: "In CSS, different properties like `color` and `background-color` don't override each other." "Similarly, **different React contexts don't override each other.**"
  - Where readers go wrong: they treat context as one global value, and they read a context in the component that provides it.
- **Root Distinction**:
  - Junior: "The value is in context, so any component, anywhere, reads the same value."
  - Senior: the value depends on where the reading component sits; React searches upward from it, and starts above it, not inside it.
- **Simplest version**:
  - Wrong: `function App() { const theme = useContext(ThemeContext); return <ThemeContext value="dark"><Page /></ThemeContext>; }`. `App` gets `'light'`.
  - Right: the reading moves into a component inside the provider, such as `ShareButton`.
- **Words to teach**:
  - *closest provider above*: the reference Returns: the value "passed to the closest `SomeContext` above the calling component in the tree." Provided by React's search. Needed at the first wrong try.
  - *override, nested provider*: the reference: "You can override the context for a part of the tree by wrapping that part in a provider with a different value." "You can nest and override providers as many times as you need." Needed at the docs' `Footer` code.
  - *"adapt to their surroundings"*: the docs: "Context lets you write components that 'adapt to their surroundings' and display themselves differently depending on _where_ (or, in other words, _in which context_) they are being rendered." Needed for the meaning of the word *context*.
  - Known: parent and child in the UI tree, Lesson 06.
  - Helper: CSS inheritance, `color`, from the docs' comparison; MDN wording `unconfirmed`.
- **Side by side**:
  - "reading in `App`, which returns the provider" and "reading in `ShareButton`, inside the provider": NOT the same thing. The first gets the default; the second gets the provider's `value`.
  - "a button inside `<ThemeContext value=\"light\">`" and "a button outside it, under `<ThemeContext value=\"dark\">`": NOT the same value, from the same component code.
  - "`ThemeContext` and `AuthContext` on the same tree": two separate values. The docs: "Each context that you make with `createContext()` is completely separate from other ones."
- **Surprises**:
  - `App` provides `'dark'` and reads `'light'`:
    1. A developer wants the `Toggle theme` button to follow the theme too and adds `const buttonTheme = useContext(ThemeContext);` in `App`, with `className={buttonTheme}` on the toggle.
    2. `App` returns `<ThemeContext value={theme}>`, so the provider sits inside `App`'s own JSX.
    3. React searches for a provider above `App` and finds none.
    4. `buttonTheme` is the default `'light'` after every click, while the Share button turns dark.
    5. The reference caveat: "`useContext()` call in a component is not affected by providers returned from the *same* component. The corresponding `<Context>` **needs to be *above*** the component doing the `useContext()` call."
  - The fix on this page: the toggle uses `theme`, the state `App` already holds; or the toggle becomes its own component inside the provider.
- **Where did that come from?**:
  - `'light'` in `App`: the default value of Principle 1, because no provider is above `App`.
  - `'light'` inside the docs' `Footer`: the nested provider closest above it.
- **Real beginner mistake** (the reference Troubleshooting, "My component doesn't see the value from my provider", first case):
  1. A developer renders `<SomeContext>` in the same component that calls `useContext()`.
  2. The component gets the default value.
  3. The developer thinks the provider is broken.
  4. The docs' fix: "Move `<SomeContext>` *above and outside* the component calling `useContext()`."
- **Interview depth**:
  - The docs' accumulating example: `Section` reads `LevelContext` and provides `level + 1`, so each `Heading` picks `<h1>` to `<h6>` by how many `Section` components it sits in. "Now both `Heading` and `Section` read the `LevelContext` to figure out how 'deep' they are."
  - The docs' use case for a nested provider: "Some apps also let you operate multiple accounts at the same time (e.g. to leave a comment as a different user). In those cases, it can be convenient to wrap a part of the UI into a nested provider with a different current account value."
  - Context passes through built-in components such as `<div>` and through our own components: "You can insert as many components as you like between the component that provides context and the one that uses it."
- **React does**:
  - Page, the wrong try: the `Toggle theme` button stays light after each click while the Share button turns dark. `unconfirmed`.
  - Console: no warning for a reader with no provider above. `unconfirmed`.
  - Elements panel: the toggle keeps `class="light"`. `unconfirmed`.
- **Example step**:
  - `App.jsx`, as a short wrong try and its fix: `const buttonTheme = useContext(ThemeContext);` with `className={buttonTheme}` on the toggle, then `className={theme}` with the state.
  - The final `App.jsx` has no `useContext` call.
- **Code names**: `App.jsx`, `buttonTheme`, `const buttonTheme = useContext(ThemeContext)`, `className={buttonTheme}`, `className={theme}`, `Toggle theme`, `<ThemeContext value="light">`, `<ThemeContext value="dark">`, `Footer`, `AuthContext`, `Section`, `Heading`, `LevelContext`, `level + 1`, `color: blue`, `color: green`, `background-color`

### Principle 6: Passing JSX as children Skips the Middle Layers

- **Rule**: before context, try passing props, or extract components and pass JSX as `children`; use context when distant components in different parts of the tree need the same information.
- **Move**: Side by side, because the `children` version and the context version both remove `theme` from the middle components, and they are NOT the same thing.
- **Opening Essence**:
  - Smallest code, the docs' own pair:
    1. `<Layout posts={posts} />`, where `Layout` only passes `posts` on.
    2. `<Layout><Posts posts={posts} /></Layout>`, where `Layout` takes `children`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both leave the middle component with no data prop. With `children`, `App` still passes `theme` by hand, as a prop, to the one component that uses it, so the data flow stays visible in the code. With context, no tag shows where `theme` goes.
  - The docs: "Context is very tempting to use! However, this also means it's too easy to overuse it."
- **Root Distinction**:
  - Junior: "A prop that goes three levels down is prop drilling, so it needs context."
  - Senior: a prop that passes through layout components often means a component was not extracted; context is for information that many distant components need.
- **Simplest version**:
  - `Page({ children })` returns `<main>{children}</main>`; `ArticleCard({ title, children })` returns `<article><h2>{title}</h2>{children}</article>`; `ActionBar({ children })` returns `<div>{children}</div>`.
  - `App` renders `<Page><ArticleCard title="New Park Opens"><ActionBar><ShareButton theme={theme} /></ActionBar></ArticleCard></Page>`.
- **Words to teach**:
  - No new React word. `children`, passing JSX as children, Lesson 09. Props, Lesson 08.
  - The docs' four use cases, as facts: theming; current account; routing, "Most routing solutions use context internally to hold the current route"; managing state, a reducer with context, Lesson 29.
  - The docs' test: "In general, if some information is needed by distant components in different parts of the tree, it's a good indication that context will help you."
  - Helper: none.
- **Side by side**:
  - "with `theme` passed through `Page`, `ArticleCard`, and `ActionBar`", "with `children` and `<ShareButton theme={theme} />` written in `App`", and "with `ThemeContext`": three ways, the same Share button. The first is clear and verbose; the second keeps the prop and removes the layers; the third removes the prop.
  - The docs on the first way: "If your components are not trivial, it's not unusual to pass a dozen props down through a dozen components." "The person maintaining your code will be glad you've made the data flow explicit with props."
- **Surprises**: none.
- **Where did that come from?**:
  - `children` in `Page`, `ArticleCard`, and `ActionBar`: the JSX written between their tags in `App`, Lesson 09.
  - `theme` on `<ShareButton theme={theme} />`: `App`'s state, now written in `App` itself, because `App` writes the `ShareButton` tag.
- **Real beginner mistake** (the docs' "Before you use context", point 2):
  1. A developer passes data such as `posts` into a layout component that does not use it: `<Layout posts={posts} />`.
  2. The prop goes through several such layers.
  3. The developer reaches for context to remove the props.
  4. The docs: "this often means that you forgot to extract some components along the way." The fix: `<Layout><Posts posts={posts} /></Layout>`.
- **Interview depth**:
  - The docs' order: props first, then `children`, then context. "If neither of these approaches works well for you, consider context."
  - The docs' Recap: "Before you use context, try passing props or passing JSX as `children`."
  - Why the final page keeps context: a theme is read by many components across the tree, the docs' first use case; on this small page, `children` would work as well.
  - Composition with `children` as a performance tool: Lesson 58, named only.
- **React does**:
  - Page, the `children` version: the same Share button, light and dark after each click on `Toggle theme`. `unconfirmed`.
  - Console: nothing. `unconfirmed`.
  - Elements panel: the same `<main>`, `<article>`, `<div>`, and `<button>` as the context version. `unconfirmed`.
- **Example step**:

## Interview Points

- Prop drilling is passing a prop through components that never use it, only pass it on; it happens when the closest common parent is far above the components that need the data.
- Context lets a parent make information available to every component in the tree below it, no matter how deep, without props.
- Three steps: create the context with `createContext(defaultValue)` outside any component; read it with `useContext(MyContext)` or `use(MyContext)`; provide it with `<MyContext value={...}>`.
- The context object holds no information; the value lives in the provider.
- The default value is used only when there is no provider above at all; it never changes; a provider with no `value` gives `undefined`.
- In React 19, `<MyContext>` is the provider; `<MyContext.Provider>` is the legacy way and will be deprecated.
- A reader gets the closest provider above it; a provider in the same component does not count; a nested provider overrides the value for its part of the tree.
- With state as the `value`, a change re-renders every component that reads the context, compared with `Object.is`, and `memo` does not stop it.
- `use(MyContext)` reads the same value as `useContext`; unlike `useContext`, it can be called inside `if` and loops; it also reads Promises.
- Before context, pass props or pass JSX as `children`; use context for information many distant components need: theme, current account, routing, and app state with a reducer.
