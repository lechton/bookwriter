# Q38 Principle Map (River Version v1): Calling Hooks Only at the Top Level of React Functions

- **Version**: River Version (`v1`), written under `skills/v10.6`
- **Bank Row**: `questions/questions.md` row 38
- **Topic Tag**: `#rules_of_hooks` | `❱ CORE`
- **Interview Question**: *Why must hooks be called at the top level, and only from React functions?*

## Scope

Covered here:
- The two Rules of Hooks, as the docs page "Rules of Hooks" names them: "Only call Hooks at the top level" and "Only call Hooks from React functions".
- Every Hook keeps its data by call order, not by name. The `rules-of-hooks` lint page: "Each time your component renders, React expects the exact same hooks to be called in the exact same order." Lesson 12 showed this for two `useState` calls; this lesson applies it to every Hook.
- What top level means, the docs: "always use Hooks at the top level of your React function, before any early returns."
- The places the docs list as not supported: conditions, loops, after a conditional `return`, event handlers, class components, functions passed to `useMemo`, `useReducer`, or `useEffect`, and `try`/`catch`/`finally` blocks. The lint page adds async functions and module level.
- The crash on the docs' feedback form, with the docs' words "Rendered fewer hooks than expected".
- The fixes the docs give: move the Hook above the first `return`; keep the Hook and move the condition inside it; give a conditional initial value; extract a new component and move the state into it.
- Only call Hooks from React functions: function components and custom Hooks, never regular JavaScript functions. The naming convention `use` followed by a capital letter, as the reason a reader can see where state hides.
- The `use` API as the one exception: it can be called inside `if` and loops, but not inside `try`/`catch`.
- The `eslint-plugin-react-hooks` rule `rules-of-hooks` as the tool that catches these mistakes, and a suppression comment as the place the docs say bugs hide.

## Start of the Lecture

**Opening Essence of the chapter**:
- No short code shows the idea with a surprise before the reader knows the screen, because the crash happens only on the second render. So the idea opens in plain words on a real screen, as Examples 8 and 9 of opening-essence open.
- The real screen: a feedback form at the bottom of an app or a website. A box with the placeholder `Message`, and a `Send` button. After Send, the form is replaced by `Thank you!`.
- What the user does, and what the user expects:
  1. Types `Great app` in the box: the letters appear.
  2. Clicks `Send`: the form goes away and `Thank you!` appears.
- The question that screen raises for the developer: the code that shows `Thank you!` and the code that shows the form sit in two branches of one `if`. The `message` state is needed only by the form. Where may the `useState` for `message` sit?
- The answer, the docs: "always use Hooks at the top level of your React function, before any early returns."
- Key idea the reader must remember: React does not know a Hook by its variable name. It knows it by its place in the order of Hook calls. So every render of a component must call the same Hooks in the same order, and no `if`, loop, early `return`, or nested function may decide whether a Hook runs.
- Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"*
  1. The form with `useState('')` inside the `else` branch, next to the form that uses it, and the form with `useState('')` at the top.
  2. Both show the box when the page opens. In both, typing works.
  3. Only the second shows `Thank you!` after Send. The first crashes, with the docs' words "Rendered fewer hooks than expected".
- What is at stake for the user, on the example page:
  1. The user writes a message and clicks Send.
  2. Instead of `Thank you!`, the page goes blank. The docs, `Component.md`: "By default, if your application throws an error during rendering, React will remove its UI from the screen."
  3. On this page the blank page is `unconfirmed`, a lab check.
- Where readers usually go wrong:
  1. They think React finds `message` by its name.
  2. They move a Hook next to the code that uses it, inside a branch.
  3. They silence the linter. The docs' hint: "Check if there are any comments disabling the linter checks--this is where the bugs often hide!"
  4. They call a Hook inside an event handler, to create state at the moment of the click.

**Theme**: a feedback form that must show `Thank you!` after Send, which crashes when one of its two Hooks sits inside a branch.

**Ways** (what to do when a Hook seems to need a condition, from the docs):
1. Move the Hook above the first `return`: when the Hook was inside a branch only because the code that uses it is there. The docs' Solution of "Fix a crash". Principle 3.
2. Keep the Hook at the top and move the condition inside it: for an Effect, `if (isLoggedIn)` inside the Effect function; for state, a conditional initial value. The lint page's Troubleshooting. Principle 4.
3. Extract a new component and move the state into it: when the state belongs to one branch only. The docs, `useState` Caveats: "If you need that, extract a new component and move the state into it." Principle 4.
4. Read context with `use` instead of `useContext`: when the only Hook inside the condition reads context. The docs: "`use` can be called within loops and conditional statements like `if`." Lesson 28, used in Principle 4.

## Principles

### Principle 1: Two useState Calls in FeedbackForm Run in One Order

- **Rule**: Every Hook in a component, of any kind, is matched to its stored data by its place in the order of Hook calls, so every render must call the same Hooks in the same order.
- **Move**: Smallest code first, because the idea is new for every kind of Hook before the form is built; the call order of `useState` is known from Lesson 12 and is only recalled.
- **Opening Essence**:
  - Smallest code: `const [name, setName] = useState('John');` and `const [count, setCount] = useState(0);`, one after the other at the top of a component.
  - Key idea: neither call passes a name to React. The docs: "There is no "identifier" that is passed to `useState`, so how does it know which of the state variables to return? Does it rely on some magic like parsing your functions? The answer is no." Hooks "**rely on a stable call order on every render of the same component.**"
  - New in this lesson: the same holds for every Hook, not only `useState`. The lint page: "React relies on the order in which hooks are called to correctly preserve state between renders. Each time your component renders, React expects the exact same hooks to be called in the exact same order."
  - The docs' everyday image, from the Pitfall: "Hooks are functions, but it's helpful to think of them as unconditional declarations about your component's needs. You "use" React features at the top of your component similar to how you "import" modules at the top of your file."
  - What is at stake: when the order changes, React gives one Hook's data to another call. The lint page: "React loses track of which state corresponds to which hook call, leading to bugs like state mismatches".
- **Root Distinction**:
  - Junior: "React finds `message` because I named it `message`."
  - Senior: the names `isSent` and `message` exist only inside our function; React sees the first Hook call and the second Hook call.
- **Simplest version**: `const [name, setName] = useState('John');` then `const [count, setCount] = useState(0);`. React matches `'John'` to the first call and `0` to the second.
- **Words to teach**:
  - *top level of your React function*: the body of the component, outside any `if`, loop, or nested function, and above any early `return`. Provided by the docs as words. Needed when the reader sees `if (isSent) { return ... }` below the two Hooks.
  - *unconditional declarations*: the docs' words for how to think of Hooks: the component states what it needs on every render, the way a file lists its imports at the top. Needed with the smallest code.
  - *the exact same order*: the lint page's words. Needed when the reader counts the Hooks on two renders.
  - Known: `useState`, Hook, the state pairs and the index, Lesson 12. `import`, Lesson 05. Early `return`, Lesson 10. Render, Lesson 13.
  - Helper: none.
- **Side by side**:
  - "with the variable named `message`" and "with the variable named `text`": Yes, it is the exact same thing for React. React never sees the names; it sees only the second `useState` call.
- **Surprises**: none. With both Hooks at the top, every render calls `useState(false)` first and `useState('')` second.
- **Where did that come from?**:
  - The values `false` and `''` on the second render: React stored them on the first render, in the order of the calls, and returns them in that order. Lesson 12.
- **Real beginner mistake**: none for this principle; the mistake comes in Principle 2.
- **Interview depth**:
  - The docs' sketch of the mechanism: React keeps an array of state pairs for each component and an index set to `0` before rendering; each `useState` call takes the next pair and moves the index. Lesson 12; recall only.

### Principle 4: The Condition Moves Inside the Hook

- **Rule**: When a Hook seems to need a condition, keep the Hook at the top level and put the condition inside it, in its initial value, or in a new component that holds the Hook.
- **Move**: Side by side, because each fix keeps the same behavior as the illegal code it replaces.
- **Opening Essence**:
  - Smallest code, the lint page's two Troubleshooting pairs:
    1. `if (isLoggedIn) { useEffect(() => { fetchUserData(); }, []); }`, then `useEffect(() => { if (isLoggedIn) { fetchUserData(); } }, [isLoggedIn]);`.

### Principle 5: A Hook Inside the onSubmit Function Breaks Send

- **Rule**: Call Hooks only while React renders a function component or a custom Hook, and never from an event handler, a regular JavaScript function, or a class component.
- **Move**: Side by side, because a Hook call looks the same in a component and in a function inside it, and only one of the two runs while React is rendering.
- **Opening Essence**:
  - Smallest code, the docs' pair: `function FriendList() { const [onlineStatus, setOnlineStatus] = useOnlineStatus(); // ✅ }` and `function setOnlineStatus() { // ❌ Not a component or custom Hook! const [onlineStatus, setOnlineStatus] = useOnlineStatus(); }`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both are JavaScript functions with a Hook call inside. Only the first is a React function.
  - Key idea, the docs: "You can only call Hooks while React is rendering a function component". An event handler runs later, when the user clicks, not while React renders.
  - Why the rule exists, the docs: "By following this rule, you ensure that all stateful logic in a component is clearly visible from its source code."
- **Root Distinction**:
  - Junior: "Any function can call `useState`; it is just a function."
  - Senior: a Hook works only during the render of a component that React is calling; a function our code calls at another moment, such as a click handler, is outside any render.

- **Words to teach**:
  - *React function*: the docs' words for a function component or a custom Hook. Provided by the docs. Needed with the `FriendList` pair.
  - *custom Hook*: a function our code writes whose name starts with `use` followed by a capital letter; it may call other Hooks. The docs' Note: "Custom Hooks *may* call other Hooks (that's their whole purpose). This works because custom Hooks are also supposed to only be called while a function component is rendering." Named here; full lesson 39.

Needed when the reader asks how a reader of the code tells a Hook from a regular function.

## Interview Points

- React matches every Hook to its stored data by call order; no Hook passes a name to React.
- Each render must call the exact same Hooks in the exact same order.
- Top level means the body of a function component or a custom Hook, outside conditions, loops, and nested functions, and before any early `return`.
- A Hook in a branch, a loop, or below an early `return` changes the number of Hook calls between renders; React stops with "Rendered fewer hooks than expected" or "more".
- Without an error boundary, React removes the UI from the screen.
- The fixes: move the Hook above the first `return`; put the condition inside the Hook; give a conditional initial value; extract a new component that holds the Hook.
- Hooks are called only from React functions: function components and custom Hooks. Never from event handlers, regular functions, class components, or functions passed to `useMemo`, `useReducer`, or `useEffect`.
- The rule keeps all stateful logic visible in the component's source code; the `use` prefix tells the reader where state may hide.
- `use` is not a Hook and may be called inside `if` and loops, but not inside `try`/`catch`.
- The `rules-of-hooks` lint rule catches these mistakes; a suppression comment is where the bug hides.
