# Q31 Principle Map (River Version v1): Reaching a DOM Node with a Ref

- **Version**: River Version (`v1`), written under `skills/v10.6`
- **Bank Row**: `questions/questions.md` row 31
- **Topic Tag**: `#dom_refs` | `❱ CORE`
- **Interview Question**: *How do you reach a DOM node from React to focus it, scroll it, or measure it?*

## Scope

Covered here:
- Why a ref is needed at all: React updates the DOM from the JSX, but JSX has no way to say "put the cursor in this box", "scroll to this element", or "how wide is this element". The docs: "There is no built-in way to do those things in React, so you will need a *ref* to the DOM node."
- The three steps from the docs: import `useRef`, declare `const inputRef = useRef(null);`, pass it as `<input ref={inputRef} />`.
- What React does with the `ref` attribute: after React creates the DOM node, it puts the node into `inputRef.current`; when the node is removed, React sets `current` back to `null`.
- Using the node in an event handler with the browser's own methods: `focus()`, `scrollIntoView()`, and reading a size with `offsetWidth` or `getBoundingClientRect()`.
- Why a ref beats `document.getElementById` when the same component appears twice on the page.
- When React fills the ref: during the commit, so `ref.current` is `null` during the first render, and reading or writing it during rendering is not allowed.
- The docs' best practice: use refs for non-destructive actions such as focusing, scrolling, and measuring; avoid changing DOM nodes managed by React, as the docs' `remove()` crash shows.

## Start of the Lecture

**Opening Essence of the chapter**:
- The question of the lesson: React writes the DOM for us from the JSX, so how does our code get hold of one real element on the page, the text box, to put the cursor in it?
- Short code shows the idea, the docs' own example:
  1. `const inputRef = useRef(null);`
  2. `<input ref={inputRef} />`
  3. In the click handler: `inputRef.current.focus();`
- What this lesson's ref shares with Lesson 30's ref, then the one difference (Back to the basics):
  - Shared: the same Hook, `useRef`, the same object with one property, `current`, kept between renders, and no re-render when `current` changes.
  - The one difference: in Lesson 30 our code wrote `current`, with an interval ID. Here React writes `current`, with the DOM node, because the tag carries `ref={inputRef}`.
- Confusion to say out loud: *"Yes, it is the exact same thing!"* `useRef(null)` here is exactly Lesson 30's `useRef(null)`. The docs: "Refs are a generic concept, but most often you'll use them to hold DOM elements." Nothing new is created; only the `ref` attribute is new.
- A second confusion, for later: `document.getElementById('guest-input')` and `inputRef.current` may give the exact same box while there is one box on the page, but they are NOT the same thing as soon as there are two. Principle 3.
- The docs' words for what a ref to a DOM node is: "an escape hatch" for when you "step outside React", with the examples "managing focus, scroll position, or calling browser APIs that React does not expose".
- What is at stake for the user, on the example page:
  1. Without a ref: after each click on Add, the cursor is no longer in the box, and the user must click the box again before typing the next name. `unconfirmed`, a lab check.
  2. With `document.getElementById` and two lists on the page: a click on Add under Dinner puts the cursor in the Lunch box, and the next name the user types goes into the wrong list.
  3. With `inputRef.current.focus()` in the body of the component: the page is blank on load.
- Where readers usually go wrong:
  1. They reach for `document.getElementById`, the tool they know from plain JavaScript, Lesson 01.
  2. They read `inputRef.current` during rendering and expect the box, but on the first render it is `null`.
  3. They use the node to change what React draws, such as removing it, instead of changing state.

**Theme**: a guest list where the user types one name after another, and the cursor must go back into the text box after every click on Add.

**Ways** (the jobs the docs name, and the tool each one fits):
1. Anything the JSX can say, such as the text in the box, a class, or whether an element is shown: state and JSX, no ref. The docs: "React automatically updates the DOM to match your render output, so your components won't often need to manipulate it."
2. Focus, scroll, or measure after an event, such as a click: a ref, read in the event handler. The docs: "Usually, you will access refs from event handlers."
3. Focus a box the moment React puts it on the page: the `autoFocus` prop, "If `true`, React will focus the element on mount", from the `<input>` reference; or, with a ref and no event, an Effect, Lesson 32. Named only.
4. Finding the element with `document.getElementById`: the plain JavaScript way from Lesson 01. It reads the whole document, not this copy of the component, Principle 3.

**Example page chosen for this lesson**: a guest list for a lunch.
- Parts of the page:
  1. A heading `Lunch guests`.
  2. A text box and a button `Add`.
  3. A list of the names added so far.
- What the user does, and what each click changes:
  1. Types `John` in the box.
  2. Clicks `Add`: `John` appears in the list, the box is empty, and the cursor is back in the box.
  3. Types `Mary` at once, without touching the mouse, and presses `Add` again.

## Principles

### Principle 1: ref={inputRef} Puts the Box into inputRef.current

- **Rule**: When a tag carries `ref={inputRef}`, React puts that tag's DOM node into `inputRef.current` after it creates the node, and sets `inputRef.current` back to `null` when the node is removed.
- **Move**: Smallest code first, because the whole tool is one Hook call and one attribute, before any project file.
- **Opening Essence**:
  - Smallest code, the docs' three steps: `import { useRef } from 'react';`, `const inputRef = useRef(null);`, `<input ref={inputRef} />`.
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* `useRef(null)` is Lesson 30's Hook with Lesson 30's object `{ current: null }`. The only new piece is the `ref` attribute on the tag.
  - The docs' sentence for what the attribute does: it "tells React to **put this `<input>`'s DOM node into `inputRef.current`.**"
  - Key idea: our code never writes `inputRef.current` here; React does, at the commit.
- **Root Distinction**:
  - Junior: "`useRef` gets the element."
  - Senior: `useRef` only makes an empty object; the `ref` attribute on a tag asks React to fill it with that tag's node after the commit.
- **Simplest version**:
  - The docs' "Focusing a text input": `const inputRef = useRef(null);`, `function handleClick() { inputRef.current.focus(); }`, `<input ref={inputRef} />`, `<button onClick={handleClick}>Focus the input</button>`.
  - A check: `console.log(inputRef.current)` inside `handleClick`.
- **Words to teach**:
  - *`ref` attribute*: an attribute React reads on any built-in tag; its value is a ref object from `useRef`. The `common.md` reference: "Your ref will be filled with the DOM element for this node." Provided by React. Needed at `<input ref={inputRef} />`.
  - *DOM node, DOM element*: the real object the browser keeps for one tag on the page, the one the Elements panel shows and `document.getElementById` returns. The docs say "DOM node" and "DOM element" for the same thing. Provided by the browser. Needed when `inputRef.current` is logged.
  - *built-in component*: the docs' name for browser tags such as `<input>` and `<div>`, as opposed to our own components. Needed because the `ref` attribute fills `current` only on these, Lesson 85 for our own.
  - Known: `useRef`, `current`, Lesson 30. Commit, Lesson 13. `null`, Lesson 08.
  - Helper: none.
- **Side by side**:
  - "with `useRef(null)` alone" and "with `useRef(null)` and `ref={inputRef}` on the tag": NOT the same thing. Without the attribute, `current` stays `null` forever; with it, React fills `current` with the node.
  - "with `inputRef.current`" and "with `document.getElementById('guest-input')`", while one box is on the page: the exact same DOM node. Principle 3 shows when they differ.
- **Surprises**: none. The node appears in `current` after the commit, as the docs say.
- **Where did that come from?**:
  - The DOM node in `inputRef.current`: never assigned by our code. Steps:
    1. The first render returns `<input ref={inputRef} />`; `inputRef.current` is still `null`.
    2. In the commit, React creates the `<input>` DOM node and adds it to the page.
    3. React then sets `inputRef.current` to that node. The `useRef` reference: "After React creates the DOM node and puts it on the screen, React will set the `current` property of your ref object to that DOM node."
    4. When the `<input>` is removed from the page, React sets `inputRef.current` back to `null`.
  - `focus` on `inputRef.current`: a method of the browser's DOM element, not of React. MDN, `HTMLElement.focus()`.
- **Real beginner mistake** (the docs' Troubleshooting entry and the step list of "Focusing a text input"):
  1. A developer declares `const inputRef = useRef(null);` and writes `inputRef.current.focus()` in the handler.
  2. The developer forgets `ref={inputRef}` on the `<input>`.
  3. The user clicks the button.
  4. `inputRef.current` is still `null`, and the click throws a `TypeError`. The exact text `TypeError: Cannot read properties of null (reading 'focus')` is `unconfirmed`, a lab check; the docs give `TypeError: Cannot read properties of null` for the same `null` in their Troubleshooting entry.
- **Interview depth**:
  - The docs: "The `useRef` Hook returns an object with a single property called `current`. Initially, `myRef.current` will be `null`."
  - The `ref` attribute also takes a function, a ref callback, used for a list of nodes: Lessons 86 and 99.
  - A ref passed to our own component, `<MyInput ref={inputRef} />`, does not reach the `<input>` inside unless the component takes `ref` and passes it on. The docs: "By default, your own components don't expose refs to the DOM nodes inside them." Lesson 85.
- **React does**:
  - Page: the docs' example; "clicking the button will focus the input".
  - Console: `console.log(inputRef.current)` in the handler shows the `<input>` element. The exact form of the log is `unconfirmed`, a lab check.
  - Elements panel: `<input>` with no `ref` attribute on it. `unconfirmed`, a lab check.
- **Example step**:
  - `GuestList.jsx`: imports `useRef`; adds `const inputRef = useRef(null);`; adds `ref={inputRef}` to the `<input>`.
- **Code names**: `useRef`, `import { useState, useRef } from 'react'`, `inputRef`, `useRef(null)`, `{ current: null }`, `inputRef.current`, `ref={inputRef}`, `<input ref={inputRef} />`, `handleClick`, `Focus the input`, `console.log(inputRef.current)`, `GuestList.jsx`, `TypeError: Cannot read properties of null`

### Principle 2: The Add Click Puts the Cursor Back in the Box

- **Rule**: In an event handler, `inputRef.current` is the real DOM node, so our code calls the browser's own methods on it: `focus()` to put the cursor in it, `scrollIntoView()` to scroll to it, and `offsetWidth` or `getBoundingClientRect()` to measure it.
- **Move**: Smallest code first, because the three jobs of the interview question are three one-line calls with the same shape.
- **Opening Essence**:
  - Smallest code, the same shape three times:
    1. Focus: `inputRef.current.focus();`
    2. Scroll: `imageRef.current.scrollIntoView();`
    3. Measure: `setWidth(boxRef.current.offsetWidth);`
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* `inputRef.current.focus()` is the same `focus()` that plain JavaScript calls on an element; React only handed us the element. The docs: "You can then access this DOM node from your event handlers and use the built-in browser APIs defined on it."
  - Key idea: these three jobs have no JSX form; there is no prop that says "the cursor is here now".
  - What is at stake for the user: without `focus()`, the user must take the mouse and click the box before every name.
- **Root Distinction**:
  - Junior: "To change the page in React, I always change state."

### Principle 3: getElementById Puts the Cursor in the Wrong List

- **Rule**: `document.getElementById` searches the whole page and returns the first element with that `id`, so in a component used twice it finds the first copy's box; a ref belongs to one copy, so each list gets its own box.
- **Move**: Side by side, because the two ways look alike and give the same box while one list is on the page.
- **Opening Essence**:
  - Smallest code, two ways to reach the box:
    1. `<input id="guest-input" />` and `document.getElementById('guest-input').focus();`
    2. `<input ref={inputRef} />` and `inputRef.current.focus();`
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* With one list, both put the cursor in the right box. With Lunch and Dinner on the page, both lists have a box with `id="guest-input"`.
  - MDN: "If two or more elements in a document have the same ID, this method returns the first element found."
- **Root Distinction**:
  - Junior: "The `id` names my box."
  - Senior: an `id` names one element of the whole page; a component used twice makes the same `id` twice. A ref is made per copy, Lesson 30, and React fills each copy's ref with that copy's node.
- **Simplest version**:
  - `App.jsx`: `<GuestList title="Lunch" />` and `<GuestList title="Dinner" />`.
  - `GuestList.jsx`: `export default function GuestList({ title })`, `<h2>{title} guests</h2>`.
  - Wrong try: `<input id="guest-input" ... />` and `document.getElementById('guest-input').focus();` in `handleAdd`.
  - Fix: `ref={inputRef}` and `inputRef.current.focus();` from Principle 2.
- **Words to teach**:
  - No new React word. `document.getElementById` and `id`, Lesson 01. Props, Lesson 08. One ref per copy, Lesson 30.
  - Helper: none.
- **Side by side**:
  - "with `document.getElementById('guest-input')`" and "with `inputRef.current`": with one list, the exact same node; with two lists, NOT the same thing. The first reads the whole document; the second reads this copy's ref.
  - The syllabus card's friction: `document.getElementById('edit-input')` "fails if multiple edit forms exist".
- **Surprises**:
  - The user adds a dinner guest, and the cursor jumps to the Lunch box:
    1. The page shows `Lunch guests` and `Dinner guests`, each with a box and an `Add` button.
    2. The Elements panel shows two `<input id="guest-input">`.
    3. The user types `Ana` in the Dinner box and clicks the Dinner `Add`.
    4. `Ana` joins the Dinner list, because `guests` is the Dinner copy's state, Lesson 12.
    5. `document.getElementById('guest-input')` returns the first box on the page, the Lunch box, and `focus()` puts the cursor there.
    6. The user types the next dinner guest, `Ben`, and the letters appear in the Lunch box. `unconfirmed`, a lab check.
  - With the ref: each copy of `GuestList` has its own `inputRef`, and the Dinner `Add` focuses the Dinner box.
- **Where did that come from?**:
  - The second `id="guest-input"`: our JSX wrote it once, and React rendered `GuestList` twice, so the page holds it twice.
  - The two refs: each copy of `GuestList` calls `useRef(null)` and gets its own object, Lesson 30.
- **Real beginner mistake** (the syllabus card's friction):
  1. A developer moves from plain JavaScript and writes `document.getElementById('edit-input')` in the edit form.
  2. It works while the page has one form.
  3. The page later shows the form twice.
  4. The click on the second form focuses the first form's box.
  5. The fix: a ref in the component, so each copy reaches its own box.
- **Interview depth**:
  - The `common.md` reference on `id`: "Generate it with `useId` to avoid clashes between multiple instances of the same component." Lesson 52. An `id` is still needed for `<label htmlFor>`; a ref is what our code uses to reach the node.
  - The docs' other plain way, a ref to the parent and `querySelectorAll` to find the children, "is brittle and can break if your DOM structure changes."
  - `getElementById` also returns `null` when the element is not on the page yet, MDN, "or `null` if no matching element was found in the document."
  - A ref also reaches a node inside another component's tree only when that component passes `ref` on: the docs' Pitfall, "Manually manipulating _another_ component's DOM nodes can make your code fragile." Lesson 85.
- **React does**:
  - Page: with `getElementById`, the Dinner `Add` puts the cursor in the Lunch box; with the ref, in the Dinner box. `unconfirmed`, a lab check.
  - Console: no warning for the repeated `id`. `unconfirmed`, a lab check.
  - Elements panel: two `<h2>` headings, `Lunch guests` and `Dinner guests`; with the wrong try, two `<input id="guest-input">`. `unconfirmed`.
- **Example step**:
  - `App.jsx`: renders `<GuestList title="Lunch" />` and `<GuestList title="Dinner" />`.
  - `GuestList.jsx`: takes `title` and shows `<h2>{title} guests</h2>`; a short wrong try with `id="guest-input"` and `getElementById`, then back to the ref.

### Principle 4: inputRef.current Is null During the First Render

- **Rule**: React fills a ref during the commit, so during the first render `ref.current` is `null`, and during later renders it still holds the old DOM; read refs in event handlers, never during rendering.
- **Move**: Steps for a surprise, because one line in the component body blanks the whole page on load.
- **Opening Essence**:
  - Smallest code, two places for the same line:
    1. In the body of `GuestList`, before `return`: `inputRef.current.focus();`
    2. In `handleAdd`: `inputRef.current.focus();`
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* The same line, `inputRef.current.focus()`, works in the handler and crashes in the body.
  - The docs: "During the first render, the DOM nodes have not yet been created, so `ref.current` will be `null`. And during the rendering of updates, the DOM nodes haven't been updated yet. So it's too early to read them."
  - The docs' order: "Before updating the DOM, React sets the affected `ref.current` values to `null`. After updating the DOM, React immediately sets them to the corresponding DOM nodes."
- **Root Distinction**:
  - Junior: "The `<input ref={inputRef}>` is in my JSX, so the box exists when my component runs."
  - Senior: the component returns JSX first; React creates the box later, in the commit, and only then fills the ref.
- **Simplest version**:
  - Wrong try: `inputRef.current.focus();` in the body of `GuestList`.
  - A check: `console.log(inputRef.current);` in the body, then in `handleAdd`.
  - Fix: the call stays in `handleAdd`, from Principle 2.
- **Words to teach**:
  - No new React word. Render and commit, mount, Lesson 13. Pure, Lesson 14. During rendering, and the rule not to read or write `ref.current` there, Lesson 30.
  - Helper: none.
- **Side by side**:
  - "with `inputRef.current.focus()` in the body" and "with `inputRef.current.focus()` in `handleAdd`": NOT the same thing. The body runs during rendering, before the commit; the handler runs after the user clicks, long after the commit.
- **Surprises**:
  - The page is blank on load:
    1. React calls `GuestList` for the first render.
    2. `useRef(null)` returns `{ current: null }`.
    3. The body reaches `inputRef.current.focus()`; `inputRef.current` is `null`.
    4. JavaScript throws a `TypeError` before `return` is reached.
    5. React removes the page. The `Component` reference: "if your application throws an error during rendering, React will remove its UI from the screen."
    6. The Console shows the error. The exact text, such as `Uncaught TypeError: Cannot read properties of null (reading 'focus')`, is `unconfirmed`, a lab check.
  - With `console.log(inputRef.current)` in the body:
    1. The first render logs `null`; with `<StrictMode>` in development, React calls the component twice, Lesson 14, so `null` may appear twice. `unconfirmed`, a lab check.
    2. After a click on `Add`, the next render logs the `<input>` element, the one from the last commit. `unconfirmed`, a lab check.
- **Where did that come from?**:
  - The `null`: the initial value passed to `useRef(null)`, still there because React has not reached the commit.
- **Real beginner mistake** (the bank row's naive experiment, "attempting to read `inputRef.current.focus()` directly during the render phase"):
  1. A developer wants the cursor in the box as soon as the page opens.
  2. The developer writes `inputRef.current.focus()` at the top of the component.
  3. The page is blank, and the Console shows a `TypeError` on `null`.
  4. To silence it, the developer writes `inputRef.current?.focus()` or an `if`.
  5. The crash is gone, but the box still gets no focus on load, because the first render still sees `null`. `unconfirmed`, a lab check.
  6. The docs' ways: `autoFocus` on the `<input>`, or an Effect, Lesson 32. The docs: "If you want to do something with a ref, but there is no particular event to do it in, you might need an Effect."
- **Interview depth**:
  - The `useRef` Pitfall: "Do not write _or read_ `ref.current` during rendering", because React expects the body to "behave like a pure function"; "You can read or write refs **from event handlers or effects instead**."
  - The `refs` lint page lists "Reading `ref.current` during render"; its valid example reads `ref.current.offsetWidth` inside `useEffect`. Lessons 63 and 95.
  - The one exception from Lesson 30, filling an empty ref once, does not apply to DOM refs, because React fills them.
  - After a setter inside a handler, the ref still points to the old DOM until the commit; the docs' `flushSync` Deep Dive, Lesson 65.
- **React does**:
  - Page: blank with the call in the body. `unconfirmed`, a lab check.
  - Console: a `TypeError` on `null`, exact text `unconfirmed`; React may add its own line naming the component, `unconfirmed`.
  - Elements panel: the `#root` element is empty. `unconfirmed`, a lab check.
- **Example step**:
  - `GuestList.jsx`, as a short wrong try and its fix: the call moved into the body, the blank page, then back into `handleAdd`.
- **Code names**: `GuestList`, `inputRef.current.focus()`, `console.log(inputRef.current)`, `null`, `{ current: null }`, `Uncaught TypeError: Cannot read properties of null (reading 'focus')`, `inputRef.current?.focus()`, `autoFocus`, `#root`

### Principle 5: remove() on React's Node Crashes the Next Toggle

- **Rule**: Use a DOM ref for non-destructive actions such as focusing, scrolling, and measuring; do not change, add, or remove DOM nodes that React manages, because React keeps updating them from the JSX and does not know about our change.
- **Move**: Steps for a surprise, because a click that worked a moment before now crashes the page.
- **Opening Essence**:
  - Smallest code, the docs' own example: `const [show, setShow] = useState(true);`, `const ref = useRef(null);`, a button `Toggle with setState` that calls `setShow(!show)`, a button `Remove from the DOM` that calls `ref.current.remove()`, and `{show && <p ref={ref}>Hello world</p>}`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both buttons make `Hello world` disappear from the page. Only `setShow` tells React.
  - The docs: "After you've manually removed the DOM element, trying to use `setState` to show it again will lead to a crash. This is because you've changed the DOM, and React doesn't know how to continue managing it correctly."
  - Key idea, the docs' Recap: "Avoid changing DOM nodes managed by React."
- **Root Distinction**:
  - Junior: "I have the node, so I can do anything plain JavaScript does with it."
  - Senior: the node still belongs to React; reading it and asking it to focus or scroll is safe, changing what it holds or whether it exists is React's job, through state.
- **Simplest version**: the docs' toggle example, unchanged, with the CSS `p, button { display: block; margin: 10px; }` left out.
- **Words to teach**:
  - *managed by React*: the docs' words for DOM nodes that React created from our JSX and keeps updating.
  - *non-destructive actions*: the docs' words for actions that do not change the DOM, "like focusing, scrolling, or measuring".
  - *`remove()`*: a browser method that takes the element off the page. Named by the docs as "the `remove()` DOM API". Needed only in this principle.
  - Known: `useState`, Lesson 12. `&&`, Lesson 10. Imperative DOM changes, Lessons 01 and 21.
  - Helper: none.
- **Side by side**:
  - "with `setShow(!show)`" and "with `ref.current.remove()`": the same page for one click, NOT the same thing after the next toggle. The first changes state, and React removes the `<p>`; the second removes the `<p>` without telling React.
- **Surprises**:
  - The toggle that worked now crashes:
    1. The user clicks `Toggle with setState` a few times; `Hello world` hides and shows each time.
    2. With `Hello world` on the page, the user clicks `Remove from the DOM`; `ref.current.remove()` takes the `<p>` off the page.
    3. React still holds `show` as `true` and still thinks its `<p>` is on the page.
    4. The user clicks `Toggle with setState`; React tries to update a `<p>` that is no longer there.
    5. The page crashes. The docs: "will lead to a crash". The exact Console text is `unconfirmed`, a lab check.
- **Where did that come from?**:
  - The crash on a click that only calls `setShow`: React compares the new JSX with the DOM it built, Lesson 13, and that DOM was changed by our code.
- **Real beginner mistake** (the docs' best practices):
  1. A developer who knows plain JavaScript gets a node through a ref.
  2. The developer hides a message with `ref.current.remove()`, or changes `textContent`, instead of changing state.
  3. The page looks right at first.
  4. A later state change makes React update that part of the page.
  5. The page shows a mix of old and new, or crashes. The docs: "can lead to inconsistent visual results or crashes like above."
- **Interview depth**:
  - The docs' exception: "You can safely modify parts of the DOM that React has _no reason_ to update", such as "some `<div>` is always empty in the JSX".
  - The docs: "Refs are an escape hatch. You should only use them when you have to 'step outside React'."
  - The Lesson 01 and Lesson 21 contrast holds here too: what the page shows is decided by state; the ref is for the few jobs state cannot say.
- **React does**:
  - Page: `Hello world` hides and shows with the toggle; after `Remove from the DOM`, the next toggle crashes the page. The docs say "crash"; what the page shows after it is `unconfirmed`, a lab check.
  - Console: an error from React's update of the DOM; exact text `unconfirmed`, a lab check.
  - Elements panel: after `Remove from the DOM`, the `<p>` is gone while the buttons stay. `unconfirmed`.
- **Example step**:
  - None. The guest list is not changed; it already uses the ref only for `focus()`, a non-destructive action. The docs' toggle example stands alone.

## Interview Points

- React updates the DOM from the JSX, but focusing, scrolling, and measuring have no JSX form, so our code needs a ref to the DOM node.
- `const inputRef = useRef(null);` makes the ref; `<input ref={inputRef} />` asks React to put that tag's DOM node into `inputRef.current`.
- React sets `ref.current` during the commit, after it creates the node, and sets it back to `null` when the node is removed.
- `ref.current` is `null` during the first render, so the component body must not read it; read it in event handlers, or in an Effect when there is no event.
- In a handler, `inputRef.current` is the real element, so the browser's own `focus()`, `scrollIntoView()`, `offsetWidth`, and `getBoundingClientRect()` work on it.
- A ref belongs to one copy of the component; `document.getElementById` reads the whole page and returns the first element with that `id`, the wrong one when a component appears twice.
- Use refs for non-destructive actions; changing or removing DOM nodes that React manages can crash the page or leave it inconsistent.
- A ref to our own component does not reach its inner `<input>` unless the component takes `ref` and passes it on, Lesson 85; `useImperativeHandle` limits what the parent receives, Lesson 50.
- Focusing a box the moment it appears uses `autoFocus` or an Effect; scrolling to a row just added in the same handler needs `flushSync`.
