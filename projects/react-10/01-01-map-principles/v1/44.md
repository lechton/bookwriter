# Q44 Principle Map (River Version v1): How a Like Shows Before the Server Confirms

- **Version**: River Version v1, skills `v10.6`
- **Bank row**: 44 of `questions/questions.md`
- **Topic tag**: `#use_optimistic` | `❱❱ MORE`
- **Interview question**: How do you show the value the reader expects before the server confirms?
- **Bank hook**: The like should turn red the instant it is clicked, not after the round trip. How does useOptimistic render the hoped-for value and roll it back on failure?

## Scope

This lesson covers:
- `useOptimistic(value, reducer?)` from `'react'`: a Hook that returns `[optimisticState, setOptimistic]` (useOptimistic.md, Reference).
- What the optimistic state equals: `value` when no Action is pending; the value passed to the set function, or the value the reducer returns, while an Action is pending (useOptimistic.md, Returns).
- Where the set function may be called: inside an Action, such as the function passed to `<form action={...}>`. Outside an Action, React logs an error and the optimistic state shows only briefly (useOptimistic.md, Caveats and Troubleshooting).
- How the optimistic state ends: no code clears it; when the Action finishes, it equals `value` again, in the same render that commits the real state (useOptimistic.md, Deep Dive "How optimistic state works").
- The roll back on failure: when the save fails and `value` does not change, the page shows what it showed before the click (useOptimistic.md, "What happens when the Action fails"; React 19 blog).
- The optional reducer: one function that updates the heart and the like count together (useOptimistic.md, "Updating multiple values together").
- Only the client form path: the set function called inside a form action, and the real state kept with `useActionState`, as in the docs' "Using with `<form>` Action props" example (useActionState.md).

## Start of the Lecture

- **Opening Essence of the chapter** (a way of working seen on a real screen, so it opens in plain words, then the smallest code):
  1. The screen: a photo post on Instagram, with the title `Sunset at the beach` and a heart button under it that reads `🤍 Like`.
  2. The user clicks the heart.
  3. The heart turns red at once and reads `❤️ Liked`.
  4. The save to the server takes about one second. The user sees no wait.
  5. The question this screen raises for the developer: the server has not answered yet. How can the page already show the answer?
  6. The answer in one line: React shows the value we hope for while the Action runs, with `useOptimistic`, and goes back to the real value when the Action ends.
- **Key idea to remember**: the optimistic state is temporary. It shows only while an Action is in progress. Otherwise the real `value` shows. The docs: "Optimistic state only renders while an Action is in progress, otherwise `value` is rendered."
- **What is at stake for the user**:
  1. Without it, the heart stays gray for one second after the click.
  2. The user thinks the click did not work and clicks again.
  3. With a manual "show it first" in `useState`, a failed save leaves a red heart that the server never saved, unless our code turns it back by hand.
- **Where readers usually go wrong**:
  1. They call the set function in an `onClick` handler, outside an Action. The heart flashes red and goes back to gray, and the Console shows an error (Principle 2).
  2. They think they must clear the optimistic state after the save. React does it; the real state decides what stays (Principle 3).
- **The confusion to say out loud**:
  1. "with `liked`" and "with `optimisticLiked`" in the button: "It may look the same, or work the same at first, but it is NOT the same thing!" Before the click and after the save, both hold the same value. Only during the one-second wait do they differ.
  2. "with `setOptimisticLiked` in `onClick`" and "with `setOptimisticLiked` in the form action": the same line in two places. NOT the same thing: only the second is inside an Action.
- **What the two share, then the one difference** (Back to the basics): `liked` and `optimisticLiked` are both state the page reads. The one difference: `liked` changes only when the server answers; `optimisticLiked` shows the hoped-for answer while the Action runs, then becomes `liked` again.
- **Everyday image for the word "optimistic"**: an optimist is a person who expects things to go well; here, the page expects the save to succeed. The docs: "This state is called the 'optimistic' because it is used to immediately present the user with the result of performing an Action, even though the Action actually takes time to complete."
- **Theme**: a like should show on the screen the instant the user clicks, and go back if the server fails to save it.
- **Ways** (developers really choose between these for the same job):
  1. Wait for the server, then show the result: `useActionState` alone (Lesson 42), with `isPending` or `useFormStatus` (Lesson 43) for a "saving" sign. Fits when the result cannot be guessed, such as a payment or a sign-up that may be refused.
  2. Show the result first with `useState`, and set it back by hand when the save fails. The blog: "In the past, you would need to handle pending states, errors, optimistic updates, and sequential requests manually." Named as the old way.
  3. `useOptimistic`. Fits when the save almost always succeeds and the user expects to see the change at once: a like, a follow, a new message in a chat. form.md: "When a user submits a form, instead of waiting for the server's response to reflect the changes, the interface is immediately updated with the expected outcome."
- **Example page**: the photo post `Sunset at the beach` with one heart button. Principle 5 adds one line under it: `12 likes`.
  - Why chosen:
    1. Everyone has liked a post. A title and a heart need no explanation.
    2. A like is where developers really use optimistic updates, and it is the bank row's own case. The docs show it too: `LikeButton` in useOptimistic.md, "Updating props or state optimistically".
    3. The change is big on the page: a gray heart becomes red. The broken cases are big too: a heart that waits, flashes, or stays red after a failed save.
    4. The action is one click.
    5. The page needs little outside code: `useActionState` from Lesson 42 keeps the real like, and a given `src/api.js` waits one second.
  - Pages considered and rejected:

    2. A chat that shows a new message with `(Sending...)` (form.md, "Optimistically updating form data"): Lesson 41 built a chat, and a list adds `key`, a `pending` flag on each item, and the reducer before the main idea.

    4. The follow button with a follower count (useOptimistic.md): close to the like, but the like is the bank row's case. Its idea, two values in one reducer, is Principle 5 on the like page.
    5. The shopping cart with add and remove (useOptimistic.md, "Handling multiple `action` types"): three kinds of updates, prices, and a total before the idea starts.

## Principles

### Principle 1: useOptimistic Turns the Heart Red at Once

- **Rule**: call `useOptimistic(liked)` and render `optimisticLiked`; when the form action calls `setOptimisticLiked(true)`, the heart shows `❤️ Liked` at once, while the save is still running.
- **Move**: Smallest code first, because the Hook is a new idea and must be seen in a few lines before the whole `LikeButton` file.
- **Opening Essence**:
  - The smallest code: the Hook line, the set function called first inside the form action, and the button that reads the optimistic state.
  - The confusion to say out loud: "with `liked`" and "with `optimisticLiked`" in the button. "It may look the same, or work the same at first, but it is NOT the same thing!" Before the click, both are `false`. During the one-second wait, `liked` is still `false` and `optimisticLiked` is `true`.
  - What the two share, then the one difference: both are values React keeps for the component. `liked` changes when the server answers; `optimisticLiked` shows the hoped-for answer during the Action.
- **Root Distinction**:
  - junior: "The heart can only turn red after the server says yes."
  - senior: what the page shows during the wait and what the server saved are two separate values; the first may be shown before the second arrives.
- **Simplest version**:

```jsx
const [liked, likeAction] = useActionState(updateLike, false);
const [optimisticLiked, setOptimisticLiked] = useOptimistic(liked);

async function submitAction() {
  setOptimisticLiked(true);
  return likeAction(true);
}

<form action={submitAction}>
  <button type="submit">{optimisticLiked ? '❤️ Liked' : '🤍 Like'}</button>
</form>
```

- **Words to teach**:
  - `useOptimistic`: "a React Hook that lets you optimistically update the UI." Provided by React, imported from `'react'`. Needed when the reader writes the second Hook line in `LikeButton`.
  - optimistic state, the first value it returns: "The current optimistic state. It is equal to `value` unless an Action is pending, in which case it is equal to the state returned by `reducer` (or the value passed to the set function if no `reducer` was provided)." Provided by React. Needed when the button reads `optimisticLiked`.
  - `value`, the argument: "The value returned when there are no pending Actions." Provided by our code, here `liked`. Needed when the reader asks what the heart shows before the click.
  - the set function, the second value it returns: it "lets you update the state for the duration of an Action." Provided by React. Needed when the user clicks the heart.
  - Already taught: Hook pair in square brackets (12), `useActionState`, `likeAction`, the reducer action (42), `<form action>` and Action (41), `<button type="submit">` (11), ternary (10), `async` and `await` (33, 41).
  - Helper words: `saveLike`, from the given `src/api.js`.
- **Side by side**:
  - "with `liked`" in the button: the heart reads `🤍 Like` for the whole second, then `❤️ Liked`.
  - "with `optimisticLiked`" in the button: the heart reads `❤️ Liked` at once.
  - Verdict: NOT the same thing.
  - Reason: during the Action, `optimisticLiked` holds the value passed to the set function; `liked` waits for the value the reducer action returns.
- **Surprises**:
  1. The user clicks `🤍 Like`.
  2. React calls `submitAction` inside a Transition, because it is the form's action (Lesson 41).
  3. `setOptimisticLiked(true)` runs first. The docs: "When `setOptimistic('b')` is called, React immediately renders with `'b'`." The heart reads `❤️ Liked`.
  4. `likeAction(true)` calls `updateLike`, which waits one second for `saveLike`. The docs: "If you await in the Action, React continues showing `'b'`."
  5. During that second, `liked` is still `false`, and the heart is still red. That the heart stays red for the full second on this page: `unconfirmed`, checked in the lab.
- **Where did that come from?**:
  - `optimisticLiked` and `setOptimisticLiked`: the two values `useOptimistic` returns; our code names them in square brackets, as with `useState` (Lesson 12).
  - `liked` inside `useOptimistic(liked)`: the state from `useActionState` one line above.
  - `submitAction`: our function, passed to the form's `action`. React calls it when the user clicks the submit button.
  - `true` in `likeAction(true)`: the payload; React passes it to `updateLike` as the second parameter, after the previous state (Lesson 42).
- **Real beginner mistake**:
  1. A developer adds `useOptimistic(liked)` and calls `setOptimisticLiked(true)` in the form action.
  2. The button still reads `{liked ? '❤️ Liked' : '🤍 Like'}`.
  3. The user clicks the heart.
  4. The heart stays gray for one second, as if the Hook did nothing.
  5. The fix: the button reads `optimisticLiked`.
- **Interview depth**:
  - Three ways to show a wait, compared: `isPending` of `useActionState` says an Action runs; `pending` of `useFormStatus` says the form submits; `useOptimistic` shows the result itself.
  - "To know when `useOptimistic` is pending": compare `optimistic !== value`; "If the values are not equal, there's a Transition in progress."
  - The docs' Note: `useTransition` "uses `useOptimistic` for `isPending` under the hood".
  - It works with plain `async` and `await`, "so it works the same whether you're using `fetch` on the client, or a Server Action from the server" (React Labs blog).
  - It is a Hook: top level only (useOptimistic.md, Reference; Lesson 38).
- **React does**:
  - Page before the click: `Sunset at the beach` and the button `🤍 Like`.
  - Page right after the click and during the wait: the button `❤️ Liked`.
  - Page after the wait: the button `❤️ Liked`.
  - Elements panel during the wait: the `<button>` node holds the text `❤️ Liked`; exact serialization `unconfirmed`.
  - Console on a normal click: nothing; `unconfirmed`, checked in the lab.
- **Example step**: the full page appears. `src/App.jsx` renders the title and `<LikeButton />`. `src/api.js` is the given file. `src/LikeButton.jsx`:

```jsx
import { useActionState, useOptimistic } from 'react';
import { saveLike } from './api.js';

async function updateLike(wasLiked, nextLiked) {
  await saveLike(nextLiked);
  return nextLiked;
}

export default function LikeButton() {
  const [liked, likeAction] = useActionState(updateLike, false);
  const [optimisticLiked, setOptimisticLiked] = useOptimistic(liked);

  async function submitAction() {
    const nextLiked = !optimisticLiked;
    setOptimisticLiked(nextLiked);
    return likeAction(nextLiked);
  }

  return (
    <form action={submitAction}>
      <button type="submit">{optimisticLiked ? '❤️ Liked' : '🤍 Like'}</button>
    </form>
  );
}
```

  - The shape follows the docs' Checkout example in useActionState.md, "Using with `<form>` Action props": the set function first, then `return dispatchAction(...)`.
  - A second click on `❤️ Liked` sends `false` and unlikes the post.
- **Code names**: `src/main.jsx`, `src/App.jsx`, `src/LikeButton.jsx`, `src/api.js`, `LikeButton`, `useOptimistic`, `useActionState`, `'react'`, `liked`, `likeAction`, `updateLike`, `wasLiked`, `nextLiked`, `optimisticLiked`, `setOptimisticLiked`, `submitAction`, `saveLike`, `<form action={submitAction}>`, `type="submit"`, `'❤️ Liked'`, `'🤍 Like'`, `Sunset at the beach`

### Principle 2: setOptimisticLiked in onClick Flashes the Heart

- **Rule**: the set function works only inside an Action, such as the form's action; called in an `onClick` handler, the heart turns red for a moment, goes back to gray, and the Console logs an error.
- **Move**: Side by side, because the same line sits in two places on the same button and only one place is inside an Action.
- **Opening Essence**:
  - The smallest code: the same `setOptimisticLiked(...)` line, once in `onClick` on the button, once inside `submitAction`.
  - The confusion to say out loud: "It may look the same, or work the same at first, but it is NOT the same thing!" Both run on the same click. Only the form action runs inside an Action.
  - What the two share, then the one difference: both are functions React calls when the user clicks. The one difference: React calls the form's action inside a Transition, and calls `onClick` as a plain event handler.
- **Root Distinction**:
  - junior: "A click is a click; I can set the optimistic heart in `onClick` and save in the action."
  - senior: the optimistic state lives only as long as an Action; with no Action around it, nothing holds it.
- **Simplest version**:

```jsx
<button type="submit" onClick={() => setOptimisticLiked(true)}>

async function submitAction() {
  setOptimisticLiked(true);
  return likeAction(true);
}
```

- **Words to teach**:
  - Action prop: the docs' words for a prop that React or a component calls inside a Transition. "When using Action props, you can call the set function without `startTransition`." "This works because Action props are already called inside `startTransition`." The form's `action` is one. Needed when the reader asks why `submitAction` needs no `startTransition`.
  - Already taught: `onClick` (11), Action and Transition by name (41).
  - Helper words: `startTransition`, named only, in the Console message (Lesson 67).
- **Side by side**:
  - "with `setOptimisticLiked` in `onClick`": the heart turns red for a moment and goes back to gray; it turns red for good only after the save.
  - "with `setOptimisticLiked` in `submitAction`": the heart turns red at once and stays red.
  - Verdict: NOT the same thing.
  - Reason, the docs: "When you call the setter outside an Action, the optimistic state will briefly appear and then immediately revert back to the original value. This happens because there's no Transition to 'hold' the optimistic state while your Action runs."
- **Surprises**:
  1. The developer writes `onClick={() => setOptimisticLiked(!optimisticLiked)}` on the submit button, and `submitAction` only calls `likeAction(!liked)`.

### Principle 3: liked Keeps the Heart Red After the Save

- **Opening Essence**:

  - senior: the optimistic state ends by itself with the Action; the real state decides what remains.

### Principle 4: A Failed Save Turns the Heart Gray Again

- **Rule**: when the save fails, the reducer action returns the old value, `liked` does not change, and when the Action ends the heart goes back to what it showed before the click; no roll back code is needed.
- **Move**: Steps for a surprise, because the heart turns gray on its own, and no line of our code says "undo the like".
- **Opening Essence**:
  - The key idea: the roll back is the same mechanism as Principle 3. The optimistic state ends, and the real state shows. On failure, the real state is still the old one.
  - What is at stake: with a hand-made "show it first" in `useState`, a failed save leaves a red heart that the server never saved, unless our code sets it back on every failure path.
  - The place where readers go wrong: they think `useOptimistic` needs a `catch` that undoes the change.
- **Root Distinction**:
  - junior: "When the save fails, I have to find the heart and turn it back."
  - senior: the page shows the real state once the Action ends; on failure we leave the real state as it was.
- **Simplest version**:

```js
async function updateLike(wasLiked, nextLiked) {
  const saved = await saveLike(nextLiked);
  return saved ? nextLiked : wasLiked;
}
```

- **Words to teach**:
  - revert, roll back: the docs' words. The blog: Actions "revert optimistic updates to their original value automatically"; "When the update finishes or errors, React will automatically switch back to the `currentName` value." useOptimistic.md: "the UI automatically rolls back to show the item again." Needed when the heart turns gray after the failed save.
  - `wasLiked`: the previous state, the first parameter of the reducer action (42). Here it is the value to keep on failure.
  - Already taught: a known error is returned as state, not thrown (42).
  - Helper words: none.
- **Side by side**:
  - "with `useState` set by hand": `setLiked(true)` before the request, and `setLiked(false)` written by us on failure.
  - "with `useOptimistic`": the set function before the request, and nothing on failure; the reducer action returns `wasLiked`.
  - Verdict: the exact same thing on the screen when the hand-made version is written correctly: red at once, gray after the failure.
  - Reason: in both, the heart shows the hoped-for value first and the old value after the failure. With `useOptimistic`, React does the second step. That the hand-made version gives the same screen: `unconfirmed`, checked in the lab.
- **Surprises**:
  1. `src/api.js` now returns `false`: the server could not save the like.
  2. The user clicks `🤍 Like`, and the heart reads `❤️ Liked` at once.
  3. After one second, `saveLike` returns `false`.
  4. `updateLike` returns `wasLiked`, which is `false`. `liked` stays `false`.
  5. The Action ends. The optimistic state equals `liked` again.
  6. The heart reads `🤍 Like` again. The docs: "Since the parent typically only updates `value` on success, a failure means `value` hasn't changed, so the UI shows what it showed before the optimistic update."
  7. That the heart turns gray after one second on this page: `unconfirmed`, checked in the lab.
- **Where did that come from?**:
  - The gray heart: no line sets it. It is `liked`, unchanged, shown once the Action ends.
  - `false` from `saveLike`: the changed line in the given `src/api.js`, which plays the part of a server that failed.
- **Real beginner mistake** (the manual way the React 19 blog describes: "In the past, you would need to handle pending states, errors, optimistic updates, and sequential requests manually"):
  1. A developer shows the like first with `setLiked(true)`, then calls the server.
  2. They write `setLiked(false)` for the case where the server returns an error.
  3. They forget the case where the request itself fails, such as a lost connection.
  4. The request fails, and the heart stays red.
  5. The next time the user opens the post, the server says it is not liked, and the heart is gray.
- **Interview depth**:
  - When an Action throws, "the Transition still ends, and React renders with whatever `value` currently is"; "You can catch the error to show a message to the user."
  - With `useActionState`, a thrown error goes to the nearest Error Boundary, and React cancels the queued Actions (useActionState.md, Caveats; Lesson 72). So a known failure is returned as state, as in Lesson 42.
  - The docs' "Optimistic delete with error recovery": the item comes back and an error line appears.
  - In a list, each optimistic item can carry its own `pending: true` flag, such as `(Adding...)` or `(Sending...)` (useOptimistic.md; form.md).

### Principle 5: One Reducer Moves the Heart and the Count Together

- **Rule**: when one click changes two values, such as the heart and the like count, pass a reducer as the second argument of `useOptimistic`, so both change in the same optimistic update.
- **Move**: Side by side, because the heart from the optimistic state and the count from the real state look fine before the click and disagree during the wait.
- **Opening Essence**:
  - The smallest code: `useOptimistic(post, (current, liked) => ({ liked, likes: current.likes + (liked ? 1 : -1) }))`.
  - The confusion to say out loud: "with the count from `post`" and "with the count from `optimisticPost`". "It may look the same, or work the same at first, but it is NOT the same thing!" Before the click, both read `12 likes`. During the wait, only the second reads `13 likes`.
  - What the two share, then the one difference: the reducer here is the same kind of function as in Lesson 27, the current state and an action in, the next state out. The one difference: its result shows only while the Action runs.
- **Root Distinction**:
  - junior: "The heart is optimistic, so the count will follow."
  - senior: every value the user sees change on the click must come from the same optimistic state, or the page shows two different answers during the wait.
- **Simplest version**:

```jsx
const [optimisticPost, setOptimisticPost] = useOptimistic(
  post,
  (current, liked) => ({ liked, likes: current.likes + (liked ? 1 : -1) })
);
```

- **Words to teach**:
  - reducer, the optional second argument: "The reducer function that specifies how the optimistic state gets updated. It must be pure, should take the current state and reducer action arguments, and should return the next optimistic state." Provided by our code. Needed when the count line appears.
  - the argument of the set function with a reducer: "If you provided a `reducer` to `useOptimistic`, this value will be passed as the second argument to your reducer." Needed when the reader asks where `liked` in the reducer comes from.

  - Helper words: none.
- **Side by side**:
  - "with the count from `post`": `❤️ Liked` and `12 likes` for one second, then `13 likes`.
  - "with the count from `optimisticPost`": `❤️ Liked` and `13 likes` at once.
  - Verdict: NOT the same thing.
  - Reason, the docs: "When an optimistic update affects multiple related values, use a reducer to update them together. This ensures the UI stays consistent." "This ensures the button text and count always stay in sync."

```jsx
import { useActionState, useOptimistic } from 'react';
import { saveLike } from './api.js';

function applyLike(current, liked) {
  return { liked, likes: current.likes + (liked ? 1 : -1) };
}

async function updateLike(previousPost, nextLiked) {
  const saved = await saveLike(nextLiked);
  return saved ? applyLike(previousPost, nextLiked) : previousPost;
}

export default function LikeButton() {
  const [post, likeAction] = useActionState(updateLike, { liked: false, likes: 12 });
  const [optimisticPost, setOptimisticPost] = useOptimistic(post, applyLike);

  async function submitAction() {
    const nextLiked = !optimisticPost.liked;
    setOptimisticPost(nextLiked);
    return likeAction(nextLiked);
  }

  return (
    <form action={submitAction}>
      <button type="submit">{optimisticPost.liked ? '❤️ Liked' : '🤍 Like'}</button>
      <p>{optimisticPost.likes} likes</p>
    </form>
  );
}
```

  - `applyLike` is the reducer, shared by `useOptimistic` and by `updateLike`, so the hoped-for count and the saved count are computed the same way. A real server would return the saved count; the given `saveLike` returns only `true` or `false`.

## Interview Points

- `useOptimistic(value, reducer?)` from `'react'` returns the optimistic state and a set function.
- The optimistic state equals `value` when no Action is pending; during an Action, it equals what the set function or the reducer gave it.
- The set function must be called inside an Action: a form's `action`, another Action prop, or `startTransition`. Outside one, the state shows briefly and reverts, and React logs "An optimistic state update occurred outside a Transition or Action."
- No code clears the optimistic state. When the Action ends, the optimistic and the real state meet in the same render.
- Pass the real state as `value`; a hardcoded `value` such as `false` comes back after the Action, even after a successful save.
- On failure, the real state does not change, so the page shows what it showed before the click: the roll back is automatic.
- A thrown error from a `useActionState` Action goes to the nearest Error Boundary; a known failure is returned as state.
- When one action changes several values, one reducer updates them together, and it re-runs if the base state changes during the Action.
- Use it when the save almost always succeeds and the user expects instant feedback, such as a like, a follow, or a chat message; wait for the server when the result cannot be guessed.
