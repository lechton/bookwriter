- **Interview Question**: *How do you keep a value between renders without triggering a re-render?*

## Scope

Covered here:
- What `useRef(initialValue)` returns: a plain JavaScript object with one property, `current`, set at first to the initial value.
- That React returns the same object on every later render, and ignores the initial value after the first render.
- That changing `ref.current` does not re-render the component, and that the change is there at once, in the same handler.
- The docs' stopwatch: the interval ID from `setInterval` is kept in a ref so that the Stop click can pass it to `clearInterval`.
- The four places a component can keep a value, compared by the docs' three facts: a local variable resets on every render; state re-renders when it changes; a variable outside the component is shared by every copy; a ref keeps the value, does not re-render, and belongs to one copy.
- The docs' rule for choosing: information used for rendering goes in state; information only event handlers need, whose change needs no re-render, may go in a ref.
- The opposite mistake: a value shown on the page kept in a ref, so the page does not update.
- The docs' rule "Don't read or write `ref.current` during rendering", with its one exception, setting the ref once on the first render.

## Start of the Lecture

**Opening Essence of the chapter**:
- The question of the lesson: the Start click gets a number from `setInterval`; the Stop click, many renders later, needs that same number for `clearInterval`. Where can the number wait between the two clicks?
- When no short code shows the idea, the idea first in plain words. Here short code shows it:
  1. `const intervalRef = useRef(null);` gives `{ current: null }`.
  2. In the Start handler: `intervalRef.current = setInterval(tick, 1000);`
  3. In the Stop handler: `clearInterval(intervalRef.current);`
- What a ref shares with state, then the one difference (Back to the basics):
  - Shared: React keeps both between renders. The docs: "Like state, refs are retained by React between re-renders."
  - The difference: "However, setting state re-renders a component. Changing a ref does not!"
  - The docs' own way to say both at once: "you can think of it as a regular state variable without a setter."
- Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* `useState(0)` and `useRef(0)` both remember a number between renders. Only the setter of state asks React to render again; writing `ref.current` tells React nothing.
- The docs' everyday image: "It's like a secret pocket of your component that React doesn't track." The docs' illustration: "An arrow with 'current' written on it stuffed into a pocket with 'ref' written on it."
- The name: the docs' page is "Referencing Values with Refs"; a ref keeps a reference to a value so that later code can find it.
- What is at stake for the user, three ways:
  1. With a `let` variable, the user clicks Stop and the stopwatch keeps counting.
  2. With one variable outside the component, the user clicks Stop on one stopwatch and the other one stops.
  3. With the shown number in a ref, the user clicks Start and the page stays on `Seconds: 0`.
- Where readers usually go wrong:
  1. They think a `let` inside the component keeps its value between renders.
  2. They think every value a component remembers must be state, and re-render for a number nobody sees.
  3. After learning refs, they keep a shown value in a ref because it "updates faster", and the page stops updating.

**Theme**: a stopwatch page whose Stop button must find the interval that the Start button started, many renders earlier.

**Ways** (the docs compare these four places for the same job, in the `useRef` reference, "By using a ref, you ensure that"):
1. A local variable, `let intervalId`: fits a value computed fresh in each render, as in Lesson 22. It does not survive a re-render: "unlike regular variables, which reset on every render".
2. A variable outside the component, at the top of the file: fits a value shared by every copy that never changes, such as Lesson 27's `initialCart`. It is shared: "unlike the variables outside, which are shared".
3. State, `useState`: fits information used for rendering. Changing it re-renders: "unlike state variables, which trigger a re-render".
4. A ref, `useRef`: fits information that only event handlers need and whose change needs no re-render, such as an interval ID or a timeout ID. The docs: "Refs are an 'escape hatch' you won't need often."

**Example page chosen for this lesson**: a stopwatch.
- Parts of the page:
  1. A line `Seconds: 0`.
  2. Two buttons, `Start` and `Stop`.
- What the user does, and what each click changes:
  1. Clicks `Start`: the line counts up once a second, `Seconds: 1`, `Seconds: 2`, `Seconds: 3`.
  2. Clicks `Stop`: the line stays on its number, such as `Seconds: 3`.
  3. Clicks `Start` again: the count goes on from that number, `Seconds: 4`.
- State: one number, `seconds`, from `useState(0)`.
- The interval: `setInterval(() => { setSeconds(s => s + 1); }, 1000)`. The updater function is Lesson 16's; with `setSeconds(seconds + 1)` the interval would keep the `seconds` of the Start click's render, Lesson 15.
- At the start of the lesson:
  1. `Stopwatch` has `seconds` and `handleStart`, which calls `setInterval` and keeps nothing it returns.
  2. `handleStop` must call `clearInterval`, and has no interval ID to give it.
- At the end of the lesson:
  1. `const intervalRef = useRef(null);` in `Stopwatch`.
  2. `handleStart`: `clearInterval(intervalRef.current);` then `intervalRef.current = setInterval(...)`.
  3. `handleStop`: `clearInterval(intervalRef.current);`
  4. `seconds` stays in state, because the page shows it.
  5. `App` renders two stopwatches, `<Stopwatch label="Tea" />` and `<Stopwatch label="Eggs" />`, each with its own ref.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx`, `src/components/Stopwatch.jsx`.
- Names follow the docs' stopwatch: `Stopwatch`, `intervalRef`, `handleStart`, `handleStop`, the buttons `Start` and `Stop`.

## Principles

### Principle 1: useRef Returns the Same Object on Every Render

- **Rule**: `useRef(initialValue)` returns an object `{ current: initialValue }`; React gives back the same object on every later render, and our code reads and changes `current` freely without a re-render.
- **Move**: Smallest code first, because the whole tool is one call and one property, before any project file.
- **Opening Essence**:
  - Smallest code, the docs' click counter: `const ref = useRef(0);` and in `handleClick`: `ref.current = ref.current + 1;` then `alert('You clicked ' + ref.current + ' times!');` on a button `Click me!`.
  - What `useRef(0)` returns, the docs: `{ current: 0 }`, "The value you passed to useRef".
  - The docs' everyday image: "a secret pocket of your component that React doesn't track".
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* A ref is an ordinary JavaScript object with one property. The docs: "the ref itself is a regular JavaScript object, so it behaves like one." Writing `ref.current = 5` is the same as writing any object property.
  - Key idea: the button text never changes, and the pop-up counts 1, 2, 3. The docs: "the component doesn't re-render with every increment."
- **Root Distinction**:
  - Junior: "`useRef(0)` sets the value to `0` on every render, like `let count = 0`."
  - Senior: the initial value is used only on the first render; every later render gets back the same object with whatever `current` holds now.
- **Simplest version**:
  - `import { useRef } from 'react';`
  - `const ref = useRef(0);`
  - `function handleClick() { ref.current = ref.current + 1; alert('You clicked ' + ref.current + ' times!'); }`
  - `<button onClick={handleClick}>Click me!</button>`
- **Words to teach**:
  - *ref*: the docs, "When you want a component to 'remember' some information, but you don't want that information to trigger new renders, you can use a ref." Provided by React. Needed at the first line, `const ref = useRef(0)`.
  - *`useRef`*: a Hook from `'react'` that takes the initial value as "the only argument" and returns the ref object. Provided by React. Needed at the `import`.
  - *`current`*: the one property of the ref object; "you can both read and write to it". Provided by React, filled by our code. Needed at `ref.current = ref.current + 1`.
  - *mutable*: the docs, "This value is intentionally mutable, meaning you can both read and write to it." Needed when `current` is changed by assignment, not by a setter.
  - *`setInterval`*: a browser function that calls a function again and again, every `delay` milliseconds, and returns "A positive integer ... that uniquely identifies the interval timer". It shares everything with Lesson 15's `setTimeout` except that it repeats. Provided by the browser, MDN. Needed in `handleStart`.
  - *interval ID*: MDN, "This identifier, often referred to as an 'interval ID', can be passed to `clearInterval()`". Needed when `handleStart` stores the number.
  - *`clearInterval`*: a browser function that stops the interval with that ID; "If the parameter provided does not identify a previously established action, this method does nothing." Provided by the browser, MDN. Needed in `handleStop`.
  - Known: Hook, `useState`, Lesson 12. Event handler, Lesson 11. `alert`, Lesson 16. `setTimeout`, Lesson 15.
  - Helper: `setInterval`, interval ID, and `clearInterval` are helper words from the browser; they are new, so each has its line above.
- **Side by side**:
  - "with `useState(0)` and `setCount(count + 1)`" and "with `useRef(0)` and `ref.current = ref.current + 1`": NOT the same thing. Both keep the number between renders; only the setter re-renders. The docs' table: "Doesn't trigger re-render when you change it." against "Triggers re-render when you change it."
  - "`setCount(5)` then `console.log(count)`" and "`ref.current = 5` then `console.log(ref.current)`": NOT the same thing. The first logs the old value, Lesson 15; the second logs `5`. The docs: "when you mutate the current value of a ref, it changes immediately".
  - "`useRef(0)` on the first render" and "`useRef(0)` on a later render": NOT the same thing. The first creates `{ current: 0 }`; the later one returns the same object and ignores `0`. The `useRef` reference: "This argument is ignored after the initial render."
- **Surprises**: none in the counter. The pop-up shows the new count and the button text does not change, as the code says.
- **Where did that come from?**:
  - `current`: never written by our code before `ref.current` is read. `useRef` creates the object with that one property, set to the initial value.
  - The same object on the second render: the docs' Deep Dive, "During the first render, `useRef` returns `{ current: initialValue }`. This object is stored by React, so during the next render the same object will be returned."
  - The interval ID in `handleStart`: the return value of `setInterval`, a number chosen by the browser.
- **Real beginner mistake** (the docs' stopwatch calls `clearInterval(intervalRef.current)` before each new `setInterval`):
  1. A developer writes `handleStart` with only `intervalRef.current = setInterval(...)`.
  2. The user clicks `Start` twice.
  3. Two intervals run, and `intervalRef.current` holds only the second ID.
  4. The line counts two seconds for each real second. `unconfirmed`, a lab check.
  5. The user clicks `Stop`; only the second interval stops, and the line keeps counting one by one. `unconfirmed`, a lab check.
  6. The fix: call `clearInterval(intervalRef.current)` at the top of `handleStart`. On the first click it gets `null` and does nothing, MDN.
- **Interview depth**:
  - The docs' Deep Dive: `useRef` "could be implemented on top of `useState`", as `const [ref, unused] = useState({ current: initialValue }); return ref;`, "a regular state variable without a setter".
  - The docs: refs "might remind you of instance fields", `this.something` in a class, written `somethingRef.current`.
  - A ref can hold any value: "a string, an object, or even a function".
  - The `useRef` caveat: in Strict Mode, "Each ref object will be created twice, but one of the versions will be discarded."
  - `useRef` is called at the top level of the component, like every Hook: Lesson 38.
- **React does**:
  - Page: the counter's button stays `Click me!`; the pop-up says `You clicked 1 times!`, then `You clicked 2 times!`.
  - Page, stopwatch: after `Start`, `Seconds: 1`, `Seconds: 2`; after `Stop`, the number stays. `unconfirmed`, a lab check.
  - Console: nothing.
  - Elements panel: the ref adds no DOM node; `<p>Seconds: 3</p>` changes only through `seconds`. `unconfirmed`.
- **Example step**:
  - `Stopwatch.jsx`: imports `useRef`; adds `const intervalRef = useRef(null);`; `handleStart` calls `clearInterval(intervalRef.current)` and stores `setInterval(...)` in `intervalRef.current`; `handleStop` calls `clearInterval(intervalRef.current)`; the `Stop` button gets `onClick={handleStop}`.
- **Code names**: `useRef`, `import { useState, useRef } from 'react'`, `ref`, `ref.current`, `useRef(0)`, `{ current: 0 }`, `handleClick`, `Click me!`, `'You clicked ' + ref.current + ' times!'`, `You clicked 1 times!`, `Stopwatch.jsx`, `Stopwatch`, `intervalRef`, `useRef(null)`, `intervalRef.current`, `setInterval`, `clearInterval`, `1000`, `setSeconds(s => s + 1)`, `handleStart`, `handleStop`, `Start`, `Stop`, `Seconds: 0`, `Seconds: 3`

### Principle 2: Stop Fails When intervalId Is a let

- **Rule**: A `let` variable inside the component is created again on every render, so the interval ID stored by the Start click is gone by the time the Stop click reads it; a ref keeps it.
- **Move**: Steps for a surprise, because the user clicks `Stop` and the number keeps counting, and no line of code says why.
- **Opening Essence**:
  - Smallest code, two ways to keep the ID:
    1. `let intervalId = null;` in the component, `intervalId = setInterval(...)` in `handleStart`, `clearInterval(intervalId)` in `handleStop`.
    2. `const intervalRef = useRef(null);`, `intervalRef.current = setInterval(...)`, `clearInterval(intervalRef.current)`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both store the number in `handleStart`. Only the ref still holds it after the next render.
  - The docs' Hint: "Regular variables like `let timeoutID` don't 'survive' between re-renders because every render runs your component (and initializes its variables) from scratch."
- **Root Distinction**:
  - Junior: "I stored the ID in a variable, so `handleStop` can read it later."
  - Senior: each render makes its own `intervalId`, and the `Stop` button holds the `handleStop` of the latest render, which sees a new `null`.
- **Simplest version**:
  - Wrong try: `let intervalId = null;` and `function handleStop() { clearInterval(intervalId); }`
  - Fix: `const intervalRef = useRef(null);` and `function handleStop() { clearInterval(intervalRef.current); }`
- **Words to teach**:
  - No new React word. Local variable reset on each render: Lesson 12. Re-render: Lesson 13. `clearInterval` doing nothing for an unknown ID: Principle 1.
  - Helper: none.
- **Side by side**:
  - "with `let intervalId`" and "with `intervalRef.current`": NOT the same thing. The `useRef` reference: a ref lets you "store information between re-renders (unlike regular variables, which reset on every render)".
- **Surprises**:
  - The user clicks `Start`, waits, clicks `Stop`, and the line keeps counting:
    1. The user clicks `Start`. `handleStart` stores the new ID, such as `7`, in this render's `intervalId`. The ID value is `unconfirmed`.
    2. One second later, the interval calls `setSeconds(s => s + 1)`.
    3. React renders `Stopwatch` again. The new render runs `let intervalId = null;` and makes a new variable.
    4. The new render also makes a new `handleStop`, and React puts it on the `Stop` button. That `handleStop` reads the new `intervalId`, which is `null`.
    5. The user clicks `Stop`. `clearInterval(null)` does nothing, MDN.
    6. The interval still runs. The line goes on: `Seconds: 4`, `Seconds: 5`. `unconfirmed`, a lab check.
  - A click on `Stop` before the first tick, within one second, may still work, because no re-render has happened yet. `unconfirmed`, a lab check.
- **Where did that come from?**:
  - The `null` in step 4: the line `let intervalId = null;`, run again by React's new call of `Stopwatch`, Lesson 13.
  - The new `handleStop` in step 4: every render defines the handlers again, and the button gets the latest one, Lesson 15.
- **Real beginner mistake** (the docs' Challenge "Fix a broken chat input"):
  1. A chat stores `let timeoutID = null;` and starts a three second `setTimeout` on Send.
  2. Send also calls `setIsSending(true)`, which re-renders the component.
  3. The user clicks Undo, which calls `clearTimeout(timeoutID)` with the new `null`.
  4. The "Sent!" pop-up still appears. The docs: "even after 'Undo' is clicked, the 'Sent!' message still appears."
  5. The docs' fix: "store it in a ref, which React will preserve between renders."
- **Interview depth**:
  - The docs' Solution: "Whenever your component re-renders (such as when you set state), all local variables get initialized from scratch."

### Principle 3: useState for the Interval ID Renders the Stopwatch Again

- **Rule**: A value the page never shows does not belong in state; storing the interval ID with a setter works, but every change re-renders the component for nothing, and the new ID is not there until the next render.
- **Move**: Side by side, because state and a ref both make `Stop` work, and only one of them renders again.
- **Opening Essence**:
  - Smallest code, two ways that both work on the page:
    1. `const [intervalId, setIntervalId] = useState(null);`, `setIntervalId(setInterval(...))`, `clearInterval(intervalId)`.
    2. `const intervalRef = useRef(null);`, `intervalRef.current = setInterval(...)`, `clearInterval(intervalRef.current)`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* The user sees the same stopwatch. With state, React renders `Stopwatch` again each time the ID changes, though nothing on the page shows it.
  - The docs' rule: "When a piece of information is used for rendering, keep it in state. When a piece of information is only needed by event handlers and changing it doesn't require a re-render, using a ref may be more efficient."
  - The docs on the stopwatch: "Since the interval ID is not used for rendering, you can keep it in a ref".
- **Root Distinction**:
  - Junior: "Anything a component must remember goes in `useState`."
  - Senior: state is for what the page shows; a value only the handlers need goes in a ref.
- **Simplest version**:
  - With state: `const [intervalId, setIntervalId] = useState(null);`, in `handleStart` `setIntervalId(setInterval(() => { setSeconds(s => s + 1); }, 1000));`, in `handleStop` `clearInterval(intervalId); setIntervalId(null);`
  - With a ref: the code of Principle 1.
  - A `console.log('Stopwatch rendered')` in the body of `Stopwatch` shows the renders.
- **Words to teach**:
  - *"used for rendering"*: the docs' test for state; the value appears in the JSX or is needed to compute it. Needed at the comparison of `seconds` and the ID.
  - Known: `useState`, setter, Lesson 12. Snapshot, Lesson 15.
  - Helper: none.
- **Side by side**:
  - "with `setIntervalId(id)`" and "with `intervalRef.current = id`": NOT the same thing. The docs' table: state "Triggers re-render when you change it"; a ref "Doesn't trigger re-render when you change it."
  - "with `setIntervalId(id)` then `console.log(intervalId)`" and "with `intervalRef.current = id` then `console.log(intervalRef.current)`": NOT the same thing. The first logs `null`, the snapshot of Lesson 15; the second logs the new ID at once.
  - "`seconds` in state" and "the interval ID in a ref", in the same component: both are right. The docs: "You can combine refs and state in a single component."
- **Surprises**:
  - The user clicks `Stop`, the number stops, and the Console still prints `Stopwatch rendered`:
    1. With state, `handleStop` calls `setIntervalId(null)`.
    2. The setter asks React for a new render, Lesson 12.
    3. React calls `Stopwatch` again; the log line prints; the page shows the same number.
    4. With the ref, `handleStop` only calls `clearInterval`; React is not asked to render, and the Console prints nothing.
  - The log counts, with `<StrictMode>` calling the component twice in development: `unconfirmed`, a lab check.
- **Where did that come from?**:
  - The extra `Stopwatch rendered` line: the setter `setIntervalId`, not any change on the page.
- **Real beginner mistake** (the bank row's friction, "storing it in state re-renders the app every time it changes"):
  1. A developer keeps the ID with `useState`, because state is the only way the developer knows to keep a value between renders.
  2. In `handleStart`, the developer calls `setIntervalId(id)` and then logs `intervalId` to check it.
  3. The Console shows `null`, and the developer thinks the ID was lost.
  4. The ID is there on the next render; the log ran on the snapshot of this one, Lesson 15.
  5. Each Start and each Stop also renders the component again for a value the page never shows.
- **Interview depth**:
  - The docs: "in most cases, you'll want to use state. Refs are an 'escape hatch' you won't need often."
  - The docs' three-way list in the `useRef` reference: kept between renders, no re-render, "local to each copy of your component".
  - The docs' "When to use refs": "Storing timeout IDs", "Storing and manipulating DOM elements", "Storing other objects that aren't necessary to calculate the JSX."
- **React does**:
  - Page: the same with state and with the ref. `unconfirmed`, a lab check.
  - Console: `Stopwatch rendered` after `Stop` with state; nothing after `Stop` with the ref. `unconfirmed`, a lab check.
  - Elements panel: unchanged after `Stop` in both. `unconfirmed`.
- **Example step**:
  - `Stopwatch.jsx`, as a short comparison: the state version of the ID beside the ref version, with one `console.log` in the body; the ref version stays.

### Principle 4: A Shared intervalId Stops the Wrong Stopwatch

- **Rule**: A variable outside the component survives every render but is one variable for every copy of the component; a ref belongs to one copy, so each stopwatch keeps its own interval ID.
- **Move**: Steps for a surprise, because the user clicks `Stop` under Tea, and the Eggs stopwatch stops.
- **Opening Essence**:
  - Smallest code, two places that both survive a re-render:
    1. `let intervalId = null;` at the top of `Stopwatch.jsx`, above `export default function Stopwatch`.
    2. `const intervalRef = useRef(null);` inside `Stopwatch`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* With one stopwatch on the page, both work: the variable outside is not created again on each render, so Principle 2's failure is gone. The difference shows only with two copies.
  - The `useRef` reference: "The information is local to each copy of your component (unlike the variables outside, which are shared)."
- **Root Distinction**:
  - Junior: "Moving `let intervalId` out of the component fixed it."
  - Senior: it fixed the reset and made one variable for every stopwatch on the page; a ref is kept between renders and belongs to one copy, as state does, Lesson 12.
- **Simplest version**:
  - `App.jsx`: `<Stopwatch label="Tea" />` and `<Stopwatch label="Eggs" />`.
  - `Stopwatch.jsx`: `export default function Stopwatch({ label })`, `<h2>{label}</h2>` above the line, and `const intervalRef = useRef(null);` inside.
- **Words to teach**:
  - *variable outside the component*: a variable at the top of the file, created once when the file loads, shared by every copy. The docs' word "shared". Needed at the wrong try.
  - Known: props, Lesson 08. Each copy has its own state, Lesson 12. Top level of the file, Lesson 04.
  - Helper: none.
- **Side by side**:
  - "with `let intervalId` above the component" and "with `useRef(null)` inside the component": with one stopwatch, the exact same page; with two, NOT the same thing.
- **Surprises**:
  - The user starts both stopwatches and clicks `Stop` under Tea:
    1. The page shows Tea and Eggs, each at `Seconds: 0`.
    2. The user clicks `Start` under Tea. `intervalId` holds Tea's ID.
    3. The user clicks `Start` under Eggs. Eggs' `handleStart` first calls `clearInterval(intervalId)`, which stops Tea, then stores Eggs' ID. `unconfirmed`, a lab check.
    4. Tea now stands still and Eggs counts. `unconfirmed`, a lab check.
    5. Without the `clearInterval` line in `handleStart`, Tea keeps counting, the user clicks `Stop` under Tea, `clearInterval` gets Eggs' ID, and Eggs stops while Tea goes on with no ID left to stop it. `unconfirmed`, a lab check.
  - With `useRef`: each `Stopwatch` gets its own ref object, so each `Stop` stops its own interval.
- **Where did that come from?**:
  - The one `intervalId` for both: the line at the top of the file runs once, when the file is imported, not on each render. Both copies read and write the same variable.
  - One ref per stopwatch: React stores each ref object with the copy of the component that called `useRef`, as it stores state, Lesson 12.
- **Real beginner mistake** (the docs' Challenge "Fix debouncing"):
  1. Three buttons each wait one second before a pop-up, with `let timeoutID;` at the top of the file.
  2. The user clicks one button, then at once another.
  3. Only the second button's message appears. The docs: "The first button's message gets lost."
  4. The docs: "A variable like `timeoutID` is shared between all components. This is why clicking on the second button resets the first button's pending timeout."
  5. The docs' fix: "keep timeout in a ref. Each button will get its own ref, so they won't conflict with each other."
- **Interview depth**:
  - The docs' full list of what a ref gives: kept between renders, no re-render, local to each copy.
  - A variable outside the component that changes while the page runs breaks the same way for any component used twice.
- **React does**:

### Principle 5: secondsRef.current on the Page Stays at 0

- **Rule**: A value the page shows must be state, because changing a ref does not re-render; and our code does not read or write `ref.current` during rendering, except to fill an empty ref once.
- **Move**: Steps for a surprise, because the interval runs and the line stays on `Seconds: 0`.
- **Opening Essence**:
  - Smallest code, the docs' broken counter: `let countRef = useRef(0);`, `countRef.current = countRef.current + 1;` in the handler, and `<button>You clicked {countRef.current} times</button>`.
  - The docs: "If you tried to implement this with a ref, React would never re-render the component, so you'd never see the count change!"
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* On the first render, `{seconds}` from state and `{secondsRef.current}` from a ref both show `0`. Only state shows the next number.
  - Where readers go wrong, the docs: "Perhaps you're thinking refs seem less 'strict' than state... But in most cases, you'll want to use state."
- **Root Distinction**:
  - Junior: "The ref holds the right number, so the page shows it."
  - Senior: the page shows what the last render read; a ref changes without a render, so the page keeps the old number.
- **Simplest version**:
  - Wrong try in `Stopwatch`: `const secondsRef = useRef(0);`, the interval does `secondsRef.current = secondsRef.current + 1;`, and the JSX shows `<p>Seconds: {secondsRef.current}</p>`.
  - Fix: `seconds` back in `useState`, with `setSeconds(s => s + 1)` in the interval.
- **Words to teach**:
  - *during rendering*: while React calls the component function, that is, in its body and its JSX, as opposed to inside an event handler. The `useRef` caveat: "Do not write _or read_ `ref.current` during rendering, except for initialization." Needed at `{secondsRef.current}` in the JSX.
  - *initialization*: filling the ref once, the first time, with `if (ref.current === null) { ref.current = ... }`. The docs: "it's fine in this case because the result is always the same, and the condition only executes during initialization". Needed in interview depth only.
  - Known: render, Lesson 13. Purity, Lesson 14.
  - Helper: none.
- **Side by side**:
  - "with `<p>Seconds: {seconds}</p>`" and "with `<p>Seconds: {secondsRef.current}</p>`": the same on the first render, NOT the same after a click on `Start`.
  - The docs' Challenge "Fix a component failing to re-render": `{isOnRef.current ? 'On' : 'Off'}` "always shows 'Off'"; the docs' fix is "remove the ref and use state instead".
- **Surprises**:
  - The user clicks `Start`, and the line stays on `Seconds: 0`:
    1. The interval adds one to `secondsRef.current` every second.
    2. Nothing calls a setter, so React is not asked to render. The `useRef` caveat: "React is not aware of when you change it because a ref is a plain JavaScript object."
    3. The `<p>` keeps the text of the last render: `Seconds: 0`.
  - The line jumps when something else renders the component:

    2. That render reads `secondsRef.current`, such as `6`, and the line jumps from `Seconds: 0` to `Seconds: 6`. `unconfirmed`, a lab check.
    3. The docs: "This is why reading `ref.current` during render leads to unreliable code."
- **Where did that come from?**:
  - The `0` on the page after six seconds: the JSX read `secondsRef.current` during the last render, before the interval changed it.
- **Real beginner mistake** (the docs' Challenge "Fix a component failing to re-render"):
  1. A developer keeps a toggle in a ref: `const isOnRef = useRef(false);`.
  2. The click changes `isOnRef.current`.
  3. The button text reads `isOnRef.current` during rendering.

- **Interview depth**:

  - The Pitfall: "When you break these rules, your component might still work, but most of the newer features we're adding to React will rely on these expectations."

## Interview Points

- `useRef(initialValue)` returns a plain object `{ current: initialValue }`; React returns the same object on every render and ignores the initial value after the first.
- Like state, a ref keeps its value between re-renders; unlike state, changing `ref.current` does not re-render.
- A change to `ref.current` is there at once, in the same handler; a state value stays the same for the whole render.
- A `let` inside the component resets on every render; a variable outside the component is shared by every copy; a ref is kept and belongs to one copy.
- Keep information used for rendering in state; keep information that only event handlers need, such as an interval ID or a timeout ID, in a ref.
- The stopwatch keeps `seconds` in state and the interval ID in a ref; `handleStart` clears the old interval before starting a new one, and `handleStop` clears it.
- Do not read or write `ref.current` during rendering; read and write it in event handlers or effects. The one exception is filling an empty ref once.
- A value shown on the page and kept in a ref does not update; that is a sign it belongs in state.
- Refs are an escape hatch for values outside React's rendering, such as browser timers and, in the next lesson, DOM elements.
