## Scope

Covered here:
- Passing a function to `<form action={fn}>`, and the one thing React passes to it: the form data of the submitted form, a `FormData` object (form.md, Props).
- The work the `action` prop removes from an `onSubmit` handler: the event `e`, `e.preventDefault()`, and `new FormData(e.target)` (form.md, Usage and its `<Note>`).
- The automatic reset: after the `action` function succeeds, React resets every uncontrolled field in the form (form.md; React 19 blog).
- An `async` action: React waits for it, runs it in a Transition, and tracks its pending state (form.md Props and `<Note>`; useTransition.md).
- What an action returns: a plain form action may return a promise, because it may be `async`; a returned value that becomes state on the page belongs to `useActionState`, Lesson 42.

## Start of the Lecture

**Opening Essence of the chapter** (a few lines of code show the idea, so it opens with the smallest code):
1. The smallest code, two tags side by side:
   - With a URL: `<form action="/send">`, plain HTML.
   - With a function: `<form action={sendMessage}>`, React 19.
2. The confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Same tag, same attribute name, `action`.
   - With a URL: the browser sends the form data to that URL and loads the answer as a new page (MDN `<form>`: "The URL that processes the form submission"; form.md: "When a URL is passed to `action` the form will behave like the HTML form component").
   - With a function: React calls the function and passes it the form data; the page stays (form.md: "This differs from the conventional HTML action, which only accepts URLs").
3. The second confusion to say out loud: *"Yes, it is the exact same thing!"* The `formData` that React passes to the action is the same kind of `FormData` object the reader built by hand in Lesson 40 with `new FormData(e.target)`. `formData.get('message')` reads it the same way.
4. The key idea to remember: the `action` prop takes a function that receives the form data. No event, no `e.preventDefault()`, no `new FormData(...)`.
5. What is at stake for the user, on the chat screen:
   1. With `onSubmit` and a forgotten `e.preventDefault()`, the browser "sends the form data to the current URL and refreshes the page" (form.md).
   2. The reload starts the app again, so the messages kept in state go back to the first message only (`unconfirmed`; the lab confirms it).
   3. With `onSubmit`, the box keeps the sent text until the code clears it by hand.
   4. With the `action` prop, the page does not reload and the box empties after a successful send.
6. Where readers usually go wrong: they read `action` as one more event handler, like `onSubmit`, and write `function sendMessage(e) { e.preventDefault(); ... }`. The parameter is the form data, not an event (Principle 1, Real beginner mistake).

**Theme**: the message box of a chat must send the typed text and then be empty again, without a page reload.

**Ways** (form.md, "Handle form submission with an event handler", its `<Note>`, and "Handle form submission with an action prop"):
1. `onSubmit` with `e.preventDefault()` and `new FormData(e.target)`: "works in every version of React and gives you direct access to the submit event". Fits a project on an older React version, or code that needs the event itself.
2. `action={fn}`: React 19. The function runs in a Transition; React "tracks the pending state, sends thrown errors to the nearest error boundary, and lets the form work with `useActionState` and `useOptimistic`". It can also be a Server Function. Fits new React 19 forms.
3. `action="/url"`: plain HTML. The browser sends the data to a server address and loads a new page. Fits a page with no React code handling the form.

**Example page chosen for this lesson**: the message box of a chat.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx` rendering `<ChatRoom />`, `src/components/ChatRoom.jsx`. Principle 3 adds `src/api.js`, the stand-in server.
- Parts of the page: a list of messages that starts with `Hello there!`, one message box with the placeholder `Write a message`, and a `Send` button.
- Principle 1 builds the page with the `action` prop and a plain function. Principle 2 shows the box emptying after Send. Principle 3 makes the action `async` and sends the message to the stand-in server first.

**Why this page**:
1. Everyone has used a chat. A list, one box, and one button need no explanation.
2. Every chat user expects the box to be empty after Send, so the automatic reset is something the user sees and wants.
3. Sending a message is a real place where developers use a form: Enter or a click on Send submits it. The docs use the same screen: a thread with `Hello there!`, a `message` box, and a `Send` button (form.md, "Optimistically updating form data").
4. Actions are typing and clicking one button.
5. Outside helper code is small: `placeholder` in Principle 1, and in Principle 3 a stand-in server made of `new Promise` and `setTimeout`, both already taught.

## Principles

### Principle 1: action={sendMessage} Receives the Form Data

- **Rule**: when a function is passed to `<form action>`, React calls it on submit with one argument, the form data of the submitted form, and the page does not reload.
- **Move**: Side by side, because the reader already knows the `onSubmit` version from Lesson 40, and the `action` version reads the same data with three lines fewer.
- **Opening Essence**:
  - The smallest code: the docs' two `Search` versions, one with `onSubmit`, one with `action={search}`, each with `<input name="query" />` and a `Search` button.
  - The confusion: *"Yes, it is the exact same thing!"* for the data: `formData.get("query")` in the action gives the same text as `formData.get("query")` after `new FormData(e.target)`.
  - The difference to name: the action gets no event, so there is nothing to call `e.preventDefault()` on, and it needs no `new FormData(...)` (form.md: "calling `e.preventDefault()` isn't needed").
- **Root Distinction**:
  - Junior: "`action` is another event handler, so its first parameter is the event."
  - Senior: `onSubmit` receives the submit event; `action` receives the form data. React handles the submit event itself.
- **Simplest version**:
  - With `onSubmit`: `function handleSubmit(e) { e.preventDefault(); const formData = new FormData(e.target); alert(formData.get('message')); }` and `<form onSubmit={handleSubmit}>`.
  - With `action`: `function sendMessage(formData) { alert(formData.get('message')); }` and `<form action={sendMessage}>`.
  - Both forms hold `<input name="message" />` and `<button type="submit">Send</button>`.
- **Words to teach**:
  - *`action` prop with a function*: provided by React DOM in React 19. A function passed to it "will handle the form submission" and "will be called with a single argument containing the form data of the submitted form" (form.md). Needed when the reader first passes `sendMessage` to `<form>`.
  - *Action*: React's name, by convention, for a function used in a Transition, such as a function passed to the `action` prop (React 19 blog; useTransition.md). Needed when the lecture names `sendMessage` as an action.
  - Known words: `onSubmit`, `e`, `e.target`, `e.preventDefault()`, `<button type="submit">`: Lesson 11. `useState`: Lesson 12. Array spread: Lessons 17 and 19. `map()`, `key`: Lesson 18. `nextId`: Lesson 19. `name`, `FormData`, `formData.get()`: Lesson 40. `alert`: Lesson 16.
  - Helper words: `placeholder`.
- **Side by side**:
  - "with `onSubmit`" and "with `action`": the exact same thing for the data that `formData.get('message')` returns. NOT the same thing for the code: with `action` there is no event, no `e.preventDefault()`, and no `new FormData(...)`, and the function runs in a Transition (Principle 3).
  - "with `action=\"/send\"`" and "with `action={sendMessage}`": NOT the same thing. The URL makes the browser send the data and load a new page; the function is called by React and the page stays.
- **Surprises**:
  1. The developer writes no `e.preventDefault()`.
  2. The user types `Hi` and clicks Send.
  3. The page does not reload, although nothing in our code stops the reload.
  4. Reason: React handles the submit itself when `action` is a function (form.md). The lab confirms that no reload happens (`unconfirmed` in the Network panel).
- **Where did that come from?**:
  - `formData` in `function sendMessage(formData)`: our code never creates it.
    1. The user clicks Send.
    2. React collects the form's boxes by their `name` into a `FormData` object.
    3. React calls `sendMessage` with that object as its only argument (form.md, Props).
- **Real beginner mistake**:
  1. The developer moves the old `onSubmit` handler to the `action` prop unchanged: `function sendMessage(e) { e.preventDefault(); ... }`.
  2. The user clicks Send.
  3. React calls `sendMessage` with the form data, so `e` holds a `FormData` object.
  4. `FormData` has no `preventDefault` method, so JavaScript throws a `TypeError`.
  5. React "sends thrown errors to the nearest error boundary" (form.md `<Note>`). With no error boundary on the page, the result on the screen is `unconfirmed`; the lab records it.
  6. The Console message is `unconfirmed`. The expected browser wording is `e.preventDefault is not a function`; the lab puts the real message into the lecture.
- **Interview depth**:
  - The docs' answer to "action or onSubmit": `onSubmit` works in every React version and gives the submit event; `action` runs in a Transition, tracks the pending state, sends thrown errors to the nearest error boundary, and works with `useActionState` and `useOptimistic` (form.md `<Note>`).
  - An `action` can also be a Server Function, which `onSubmit` does not support (form.md `<Note>`; Lesson 110).
  - When a function is passed to `action` or `formAction`, the HTTP method is POST whatever the `method` prop says (form.md, Caveats).
  - A `<button formAction={save}>` overrides the form's `action` for that button, as in the docs' Publish and Save draft form (form.md, "Handling multiple submission types").
  - In the docs' Publish example, the clicked button's `name` and `value` arrive in the form data: `formData.get("button")` (form.md).
- **React does**:
  - Page: after Send, the list shows a second message, `Hi`, under `Hello there!`.
  - Console: nothing in the working version.
  - Elements panel: a new `<li>` node with the text `Hi` inside the `<ul>` (`unconfirmed`).
  - Vite: no full page reload (`unconfirmed`).
- **Example step**: creates `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx` returning `<ChatRoom />`, and `src/components/ChatRoom.jsx` with `initialMessages`, `let nextId = 2;`, `messages` state, `sendMessage(formData)` that adds `{ id: nextId++, text: formData.get('message') }`, the `<ul>` of messages, and the form with the box and the Send button.
- **Code names**: `index.html`, `src/main.jsx`, `src/App.jsx`, `src/components/ChatRoom.jsx`, `ChatRoom`, `initialMessages`, `{ id: 1, text: 'Hello there!' }`, `let nextId = 2;`, `messages`, `setMessages`, `useState(initialMessages)`, `sendMessage`, `formData`, `formData.get('message')`, `<form action={sendMessage}>`, `<input name="message" placeholder="Write a message" />`, `<button type="submit">Send</button>`, `Hello there!`, `Hi`, `handleSubmit`, `e.preventDefault()`, `new FormData(e.target)`, `action="/send"`, `e.preventDefault is not a function` (`unconfirmed`)

### Principle 2: The Message Box Empties After Send

- **Rule**: after the `action` function succeeds, React resets every uncontrolled field in the form; a controlled box keeps showing its state.
- **Move**: Steps for a surprise, because no line of our code clears the box, yet the box is empty after Send.
- **Opening Essence**:
  - The smallest code: the two Send forms of Principle 1, with `onSubmit` and with `action`, each with an uncontrolled `<input name="message" />`.
  - The confusion: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both versions send `Hi`. After Send, the box with `onSubmit` still shows `Hi`; the box with `action` is empty.
  - What is at stake for the user: a chat box that keeps the sent text invites a second send of the same message by mistake.
  - Where readers usually go wrong: they keep the box controlled by habit (Lesson 20) and then wonder why it does not empty.
- **Root Distinction**:
  - Junior: "To empty the box, my code must clear it."
  - Senior: with a function in `action`, React resets the uncontrolled fields after a successful action; the code clears only what it controls.
- **Simplest version**:
  - With `onSubmit`: the box keeps `Hi`; to empty it, the code calls `e.target.reset()`, the browser's `reset()` of the form (MDN `HTMLFormElement`).
  - With `action`: `<form action={sendMessage}>` and `<input name="message" />`; the box is empty after Send, and no line of our code empties it.
- **Words to teach**:
  - *reset*: the form's uncontrolled fields go back to their starting value, here an empty box with the placeholder. Provided by React for a function in `action`: "After the `action` function succeeds, all uncontrolled field elements in the form are reset" (form.md); "When a `<form>` Action succeeds, React will automatically reset the form for uncontrolled components" (React 19 blog). Needed the moment the user sees the empty box after Send.
  - Known words: uncontrolled and controlled box, `value`, `onChange`: Lesson 20. `onSubmit`, `e.target`: Lesson 11.
  - Helper words: `reset()` of a form, named once.
- **Side by side**:
  - "with `onSubmit`" and "with `action`": NOT the same thing after Send. The first keeps `Hi` in the box; the second empties it.
  - "uncontrolled box with `name`" and "controlled box with `value` and `onChange`", both inside `<form action={sendMessage}>`: NOT the same thing. React resets the first; the docs promise the reset only for uncontrolled fields, so the second keeps showing its state (`unconfirmed`; the lab confirms it).
- **Surprises**:
  1. The user types `Hi` in the box.
  2. The user clicks Send.
  3. React calls `sendMessage` with the form data.
  4. `sendMessage` adds `Hi` to `messages` and ends without an error.
  5. React resets the uncontrolled box.
  6. The list shows `Hi`, and the box is empty again with `Write a message`.
- **Where did that come from?**:
  - The empty box: our code has no line that empties it. React performs the reset after the successful action (form.md; React 19 blog).
- **Real beginner mistake**:
  1. After Lesson 20, the developer makes the box controlled: `const [text, setText] = useState('')`, `value={text}`, `onChange={e => setText(e.target.value)}`.
  2. The form still uses `action={sendMessage}`.
  3. The user types `Hi` and clicks Send.
  4. The message appears in the list.
  5. The box still shows `Hi`, because React resets only uncontrolled fields (`unconfirmed`; the lab confirms it).
  6. The developer adds `setText('')` inside `sendMessage`, work that the uncontrolled box did not need.
- **Interview depth**:
  - The reset happens only "after the `action` function succeeds" (form.md). When the action throws, the docs promise no reset; the lab checks what the box shows.
  - When the reset is not wanted, such as a search box or a sign in form with a wrong password, Lesson 45 covers it, with `requestFormReset` for a manual reset (React 19 blog).
  - The reset is one reason form actions favor uncontrolled boxes (Lesson 40).
- **React does**:
  - Page: after Send, the list shows `Hi` and the box shows the placeholder `Write a message`.
  - Console: nothing.
  - Elements panel: the `<input>` value is empty after Send (`unconfirmed`).
- **Example step**: no new file. `ChatRoom.jsx` is the same; the lecture shows the box before and after Send, and the short wrong try with a controlled box and its fix.
- **Code names**: `ChatRoom.jsx`, `sendMessage`, `<input name="message" placeholder="Write a message" />`, `Write a message`, `Hi`, `e.target.reset()`, `text`, `setText`, `useState('')`, `value={text}`, `onChange={e => setText(e.target.value)}`, `setText('')`, `requestFormReset`

### Principle 3: An async Action Empties the Box After await

- **Rule**: the function in `action` may be `async`; React waits for it, runs it in a Transition, and resets the box only after it succeeds.
- **Move**: Steps for a surprise, because for one second after Send the box still shows the text and the list does not show it yet.
- **Opening Essence**:
  - The smallest code: MDN's shape of an `async` function that waits for a promise: `async function asyncCall() { const result = await resolveAfter2Seconds(); console.log(result); }`.
  - The key idea to remember: `await` pauses the action until the promise is done; only then does the action finish, and only then does React reset the box.
  - What is at stake for the user: a real chat sends the message to a server first. While the server works, the page must stay usable, and the box must not empty before the send has succeeded.
  - Where readers usually go wrong: they write the Lesson 21 work by hand, a `status` or `isSending` state set before and after the request, which React already tracks for an action (React 19 blog, "Before Actions").
- **Root Distinction**:
  - Junior: "An action is called and is over at once, like a click handler."
  - Senior: an action can wait; React treats the whole wait as one Transition, keeps track of it as pending, and resets the form when it ends without an error.
- **Simplest version**:
  - `src/api.js`: `export async function deliverMessage(text) { await new Promise(resolve => setTimeout(resolve, 1000)); return text; }`, the docs' stand-in server from form.md.
  - `ChatRoom.jsx`: `async function sendMessage(formData) { const message = { id: nextId++, text: formData.get('message') }; await deliverMessage(message.text); setMessages(m => [...m, message]); }`.
- **Words to teach**:
  - *`async` function*: provided by JavaScript. MDN: the `await` keyword is permitted within its body, "enabling asynchronous, promise-based behavior". Needed when `sendMessage` gets the word `async`.
  - *`await`*: provided by JavaScript. MDN: "used to wait for a Promise and get its fulfillment value". Needed at the line that waits for `deliverMessage`.

## Interview Points

- `<form action>` takes a URL, as in HTML, or a function, new in React 19.
- With a URL, the browser sends the data and loads a new page; with a function, React calls it on submit and the page stays.
- The function receives one argument: the form data of the submitted form, a `FormData` object read with `formData.get()` by each box's `name`.
- No event reaches the action, so there is no `e.preventDefault()` and no `new FormData(e.target)`.
- After the action succeeds, React resets every uncontrolled field in the form; a controlled box is not reset.
- The action may be `async`; React waits for it and runs it in a Transition, so the page stays usable.
- React tracks the pending state of the action; `useActionState` (Lesson 42) and `useFormStatus` (Lesson 43) read it, which replaces a hand-written `isSending` state.
- A thrown error goes to the nearest error boundary.
- A plain form action may return a promise; a returned value that the page shows belongs to `useActionState`.
- `onSubmit` still works in every React version and gives the submit event; `action` adds Transitions, the reset, pending tracking, and Server Functions.
- With a function in `action` or `formAction`, the HTTP method is POST; `formAction` on a button overrides the form's `action`.
