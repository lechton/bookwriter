# Q14 Principle Map (River Version v1): Pure Components and Where Side Effects Belong
- **Version**: River Version (`v1`)
- **Bank Row**: `questions/questions.md` row 14, Version 4
- **Topic Tag**: `#purity` | `❱ CORE`
- **Interview Question**: *What does it mean for a component to be pure, and what breaks across renders when it is not?*

## Authorized Scope
- What a pure function is in plain JavaScript, using the two rules from `react.dev`: it minds its own business (it does not change any variable or object that existed before it was called), and same inputs give the same output.
- Why React assumes every component is a pure function: given the same props and state, a component must return the same JSX every time React calls it.
- What breaks when a component changes a variable created outside it during render: the page shows correct numbers on the first load and wrong numbers after every re-render, even when the component's own props never changed.
- What `<StrictMode>` does for rendering: in development only, React calls each component function twice, so an impure component shows its bug on the very first load; a pure component shows the same page with or without it; the production build calls each component once.
- Why changing an array that came from outside the component (a prop) during render breaks the page, and why changing an array the component created inside the same render (local mutation) is completely fine.
- Where side effects belong: event handlers run only when the user acts, never during render, so they do not need to be pure and `<StrictMode>` does not call them twice. An Effect (`useEffect`) is named only as a last resort and taught later.
- Out of scope: list rendering with `.map()` and `key` (`Q18 #rendering_lists`), non-mutating array methods and array spread for state updates (`Q19 #state_arrays`), updating objects in state (`Q17 #state_objects`), state as a snapshot (`Q15 #state_snapshots`), `useEffect` and synchronizing with external systems (`Q32 #use_effect`), `<StrictMode>` re-running Effects and ref callbacks (`Q47 #strict_mode`), skipping renders with `memo` (`Q55 #memo`), interrupting and restarting renders (`Q66 #concurrent_rendering`), the React Compiler (`Q63 #react_compiler`), purity of custom Hooks and Hook arguments (`Q39 #custom_hooks`), and rendering on the server (`Q108 #server_components`).

## General Concepts Introduction (Runway Plan)
- **Opening Essence**:
  - **Furniture-free snippet**:
    - Pure function: `function double(number) { return 2 * number; }`, where `double(3)` returns `6` every time.
    - Impure function: `let total = 0; function addToTotal(number) { total = total + number; return total; }`, where `addToTotal(3)` returns `3` the first time and `6` the second time with the same input.
    - Pure component: `function Greeting({ name }) { return <h1>Hello, {name}</h1>; }`
  - **Human image**:
    1. A math formula, from `react.dev`: with `y = 2x`, when `x` is `3`, `y` is `6`, always, no matter the time of day.
    2. A recipe, from `react.dev`: follow the same recipe with the same ingredients and you get the same dish every time; a cook who adds a new ingredient during cooking gets a different dish.
    3. The everyday meaning of the word **pure**: nothing mixed in from outside. A pure component uses only what it was given (its props and state) and leaves everything else as it found it.
    4. The everyday meaning of **side effect**, as in medicine: the result you did not ask for that happens on the side of the main job. A component's main job is to return JSX; changing anything else is the thing on the side.
  - **Exact nuance of confusion to state out loud**:
    1. `double` and `addToTotal` both take a number and both return a number, so they look like the same kind of function, but they are NOT the same thing: calling `addToTotal(3)` twice gives `3` then `6`, because it changes `total`, which existed before the call.
    2. An impure component and a pure component can show the exact same page on the first load (`1. Milk`, `2. Bread`, `3. Eggs`), so they seem to work the same at first, but they are NOT the same thing: the first click on `Dark mode` makes the impure one show `4. Milk`, `5. Bread`, `6. Eggs`.
- **Theme**: A small shopping list page numbers its three items and has a `Dark mode` button; clicking the button changes nothing about the items, yet an impure item component makes the numbers climb on every click, and an impure summary line repeats `Shopping bags` on every click.
- **Ways**: Where a change can live in a component file, and when each fits:
  1. In the component body (runs during render): only calculations that return JSX from props and state, plus local mutation of variables created in the same render.
  2. In an event handler such as `handleToggle` (runs only when the user acts): side effects such as changing a variable outside the component, logging a count, or setting state.
  3. In an Effect (`useEffect`, runs after the commit): last resort for side effects that no event causes; named only, taught in `Q32 #use_effect`.
- **Recall**:
  - Props are read-only; a component never assigns to its own props (Lecture 08, `Q08 #props`).
  - Event handlers are functions passed to `onClick` that React runs when the user clicks, not while the component renders (Lecture 11, `Q11 #event_handling`).
  - `useState` keeps a value between renders, and calling the setter (`setDark(!dark)`) asks React to render again (Lecture 12, `Q12 #use_state`).
  - Rendering means React calling your component functions; a state update in `App` makes React call `App` and every child it returns (Lecture 13, `Q13 #render_and_commit`).
  - A ternary `dark ? 'Light mode' : 'Dark mode'` picks between two values inside JSX (Lecture 10, `Q10 #conditional_rendering`).
- **Runway topics**:
  - Pure function in plain JavaScript: same inputs, same output, and no change to anything that existed before the call.
  - Variable scope recall: a `let` variable written at the top of a module file, outside every function, is created once when the file loads and keeps its value between calls.
  - Mutation: changing a value in place, such as `number = number + 1` or `items.push('Shopping bags')`; new word, unlocked through its everyday meaning of a change to the thing itself rather than to a copy.
  - Arrays as boxes of values: `['Milk', 'Bread', 'Eggs']`, `.push()` adds to the end of the same array, `.slice()` with no arguments makes a new copy, `.join(', ')` turns the array into one line of text. Only these three methods are needed; `.map()` is not used in this lesson.
  - Side effect: anything a function does other than returning its result.
  - Development build versus production build: `npm run dev` versus `npm run build`, recalled from Lecture 07 for the `<StrictMode>` difference.
  - How the project files are organized: `index.html`, `src/main.jsx`, `src/App.jsx`, `src/components/Item.jsx`, `src/components/ListSummary.jsx`.
- **Example**:
  - **Chosen page**: `My Shopping List`, a page with a heading, three numbered items (`1. Milk`, `2. Bread`, `3. Eggs`), and one `Dark mode` button that switches the page between light and dark with `const [dark, setDark] = useState(false)` in `App`. Principle 1 numbers the items with an outside counter in `Item.jsx`, then fixes it with a `number` prop. Principle 2 wraps `<App />` in `<StrictMode>` in `src/main.jsx`. Principle 3 adds `ListSummary.jsx`, a line `You need: Milk, Bread, Eggs, Shopping bags` that always reminds the shopper to bring bags. Principle 4 counts how many times the shopper switched the theme.
  - **Why this concept is the reason this page exists**:
    1. The `Dark mode` button re-renders `App` and every item without changing any item's props, so the only thing that can change the numbers or the summary line is impure code. Same inputs, different output is visible at once.
    2. Numbers on a shopping list and a repeated `Shopping bags` are mistakes anyone notices without being told what to look for.
    3. Clicking a theme button is something everyone does without thinking, and counting theme switches is a believable product request that splits cleanly into "counts renders" versus "counts clicks".
  - **Other candidate pages considered**:
    1. *The ticket counter from Lecture 13 (`TicketCounter`, `OrderSummary`)*: rejected, because its click changes the count, so the reader cannot tell whether a changed number comes from the new input or from impure code.
    2. *The `react.dev` tea set (`Cup`, `guest`)*: rejected, because three cups with no button cannot show a bug that grows on every re-render; the reader needs something to click.
    3. *A story tray with a `Create Story` tile, from `react.dev`*: rejected, because it needs `.map()` and `key`, which arrive in `Q18 #rendering_lists`.

## Principle Thread
- **Anchor**: React may call a component function at any time and any number of times, so the function must only calculate JSX from its props and state, and leave every value that existed before the call unchanged.
- **Axis**: From the rule, to the tool that exposes broken rules, to the two ways a component breaks it, to where the change belongs instead:
  1. What pure means and what breaks when a component changes an outside variable during render (Principle 1).
  2. How `<StrictMode>` calls each component twice in development to make that break visible on the first load (Principle 2).
  3. Why changing an outside array during render breaks, and why changing a local array is fine (Principle 3).
  4. Why side effects belong in event handlers, which never run during render (Principle 4).
- **Why This Axis**: Cause before effect. The reader must first own the rule and see it broken (Principle 1) before a tool that checks the rule makes sense (Principle 2). The array case (Principle 3) is the same rule applied to an object instead of a number, and it needs `<StrictMode>` already in place to show its doubled growth. Only once the reader has seen what must not happen during render does the question "then where does the change go?" arise (Principle 4).

## Principles

### Principle 1: A Pure Component Returns the Same JSX for the Same Inputs and Changes Nothing That Existed Before It Ran
- **Handle**: `pure-means-same-output`
- **Rule**: A component is pure when, given the same props and state, it returns the same JSX every time and does not change any variable or object that existed before React called it; a component that changes a variable created outside it shows different output on every render, even when its own props never change.
- **Opening Essence**:
  - **Furniture-free snippet**: `function double(number) { return 2 * number; }` next to `let total = 0; function addToTotal(number) { total = total + number; return total; }`, each called twice with `3`: `double` gives `6`, `6`; `addToTotal` gives `3`, `6`.
  - **Human image**: the formula `y = 2x` and the recipe that gives the same dish every time; a cook who secretly adds an ingredient from the last meal gets a different dish.
  - **Exact nuance of confusion to state out loud**: the impure `Item` and the pure `Item` show the same page on the first load, so they seem to work the same at first, but they are NOT the same thing; the difference appears on the first re-render.
- **Root Distinction**:
  - *Junior blurred view*: "My `Item` shows the right numbers on the page, so it works."
  - *Senior grounding*: right output on the first render proves nothing; a component must give the same output every time React calls it with the same props, because React calls it again on every re-render of its parent.
- **Real Beginner Mistake (events, in order)**:
  1. A developer wants each shopping item numbered and does not want to type the numbers by hand.
  2. In `Item.jsx`, the developer writes `let number = 0;` at the top of the file, and inside `Item` writes `number = number + 1;` before returning `<li>{number}. {name}</li>`.
  3. `App` places `<Item name="Milk" />`, `<Item name="Bread" />`, and `<Item name="Eggs" />` inside `<ul>`.
  4. The page loads without `<StrictMode>` and shows `1. Milk`, `2. Bread`, `3. Eggs`, so the developer believes it works.
  5. The shopper clicks `Dark mode`; `setDark(!dark)` re-renders `App`, and React calls `Item` three more times.
  6. `number` was never reset, because it lives outside `Item`; the list now shows `4. Milk`, `5. Bread`, `6. Eggs`.
  7. The second click shows `7. Milk`, `8. Bread`, `9. Eggs`, although no item's props changed.
  8. The fix: delete the outside `number`, write `function Item({ number, name })`, and place `<Item number={1} name="Milk" />`, `<Item number={2} name="Bread" />`, `<Item number={3} name="Eggs" />`; the numbers stay `1`, `2`, `3` on every click.
- **Interview Depth**:
  - The two rules of a pure function from `react.dev`: it minds its own business, and same inputs give the same output.
  - The three inputs a component may read during render are props, state, and context, and all three are read-only; context is named only, taught later.
  - React does not promise any order of calling components, so components must not talk to each other through shared outside variables during render; they talk through props (`react.dev` "Fix a broken profile": `currentPerson` written in `Profile` and read in `Header`).
  - The word idempotent: calling the same code with the same inputs gives the same result. `new Date()` and `Math.random()` are not idempotent, so calling them during render makes a component impure.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any line in `App.jsx` or `Item.jsx` that calls `Item` again when `Dark mode` is clicked; the click only calls `setDark(!dark)` in `App`.
    - **Who supplies it**: React; the state update in `App` makes React call `App` and then every child component `App` returns (recall from Lecture 13).
    - **What JavaScript and React do**:
      1. `src/components/Item.jsx` loads once, and JavaScript creates `number` with the value `0`.
      2. On the first render, React calls `Item` three times; `number` becomes `1`, `2`, `3`.
      3. The click calls `setDark(true)`, and React renders `App` again.
      4. React calls `Item` three more times with the same props `name="Milk"`, `name="Bread"`, `name="Eggs"`.
      5. Each call adds `1` to the same `number`, which still holds `3`, so the items get `4`, `5`, `6`.
  - **Bridge 2**:
    - **Reader will not find**: `number` inside the parameter list of the fixed `Item` call written as a function call.
    - **Who supplies it**: the `number={1}` attribute on the tag in `App.jsx`; React puts it into `props.number` (recall from Lecture 08).
    - **What JavaScript and React do**:
      1. `App` writes `<Item number={1} name="Milk" />`.
      2. React passes `{ number: 1, name: 'Milk' }` as the props object.
      3. `Item` reads `number` and `name` from its props and returns `<li>1. Milk</li>` on every call.
- **React Does**:
  - Impure `Item`, no `<StrictMode>`, dev server: load shows `<ul><li>1. Milk</li><li>2. Bread</li><li>3. Eggs</li></ul>`; after click 1, `<li>4. Milk</li><li>5. Bread</li><li>6. Eggs</li>`; after click 2, `<li>7. Milk</li><li>8. Bread</li><li>9. Eggs</li>`. The button text switches `Dark mode` then `Light mode` then `Dark mode`, and `<main>` switches `class="page"` then `class="page dark"`. No Console warning or error.
  - Pure `Item` with the `number` prop: `1. Milk`, `2. Bread`, `3. Eggs` on load and after every click.
- **Example Step**: Creates `index.html`, `src/main.jsx` (plain `root.render(<App />)`), `src/App.jsx` with `const [dark, setDark] = useState(false)`, `<main className={dark ? 'page dark' : 'page'}>`, `<h1>My Shopping List</h1>`, `<ul>` with three `<Item />` tags, and `<button className="theme-btn" onClick={handleToggle}>{dark ? 'Light mode' : 'Dark mode'}</button>`, where `handleToggle` calls `setDark(!dark)`; creates `src/components/Item.jsx`, first with the outside `number`, then fixed with the `number` prop. New page elements here: the heading, the three numbered items, and the `Dark mode` button.
- **Code names**: `double`, `addToTotal`, `total`, `index.html`, `src/main.jsx`, `src/App.jsx`, `src/components/Item.jsx`, `App`, `Item`, `let number = 0`, `number = number + 1`, `name`, `dark`, `setDark`, `handleToggle`, `useState(false)`, `'page'`, `'page dark'`, `theme-btn`, `'My Shopping List'`, `'Milk'`, `'Bread'`, `'Eggs'`, `'Dark mode'`, `'Light mode'`, `1. Milk`, `4. Milk`, `7. Milk`
- **Visual idea**: Two columns, impure `Item` and pure `Item`, with three rows for load, click 1, click 2, showing `1, 2, 3` / `4, 5, 6` / `7, 8, 9` against `1, 2, 3` every time.

### Principle 2: `<StrictMode>` Calls Every Component Twice in Development So Impure Code Shows on the First Load
- **Handle**: `strict-mode-double-call`
- **Rule**: Wrapping `<App />` in `<StrictMode>` makes React call each component function twice on every render in development only; a pure component looks exactly the same, while an impure one shows its bug at once on the first load, and the production build calls each component once.
- **Opening Essence**:
  - **Furniture-free snippet**: `double(3)` called twice gives `6` and `6`; `addToTotal(3)` called twice gives `3` and `6`. Calling a function a second time is a free test of whether it is pure.
  - **Human image**: the everyday meaning of **strict**: a strict teacher who checks your answer twice. If you solved `y = 2x` honestly, the second check gives the same answer; if you copied a running total from your neighbour, the second check gives a different one.
  - **Exact nuance of confusion to state out loud**:
    1. The doubled numbers `2, 4, 6` make it look as if `<StrictMode>` caused the bug, but it did NOT: the bug was already in `Item`, and `<StrictMode>` only made it show on the first load instead of after the first click.
    2. The page in development and the page in production may look different (`2. Milk` versus `1. Milk`), but the code is the same thing; only development calls each component twice.
- **Root Distinction**:
  - *Junior blurred view*: "`<StrictMode>` is breaking my numbers, so I will remove it from `main.jsx`."
  - *Senior grounding*: `<StrictMode>` adds a second call to every component in development; a pure component is unaffected, so a changed result proves the component is impure, and removing `<StrictMode>` only hides the bug until the next re-render.
- **Real Beginner Mistake (events, in order)**:
  1. The project's `src/main.jsx` wraps `<App />` in `<StrictMode>`, as the Vite React starter does.
  2. The developer keeps the impure `Item` with the outside `number`.
  3. The page loads in `npm run dev` and shows `2. Milk`, `4. Bread`, `6. Eggs`.
  4. The developer searches for who skips the odd numbers and finds that removing `<StrictMode>` brings back `1. Milk`, `2. Bread`, `3. Eggs`.
  5. The developer removes `<StrictMode>` and ships.
  6. In production, the first `Dark mode` click shows `4. Milk`, `5. Bread`, `6. Eggs`; the bug was still there.
  7. The real fix is the pure `Item` with the `number` prop, which shows `1. Milk`, `2. Bread`, `3. Eggs` with `<StrictMode>`, without it, and in production.
- **Interview Depth**:
  - Exactly which functions `<StrictMode>` calls twice: the component function body (top-level code only, not code inside event handlers) and functions passed to `useState`, `set` functions, `useMemo`, and `useReducer`.
  - `<StrictMode>` is development only and does not slow the production build.
  - `<StrictMode>` can wrap only part of the tree, and there is no way to opt out inside a wrapped tree.
  - `<StrictMode>` also re-runs Effects and ref callbacks and warns about deprecated APIs; deferred to `Q47 #strict_mode`.
  - `<StrictMode>` renders nothing of its own: no element for it appears in the Elements panel.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any second call of `Item` written in `App.jsx`, `Item.jsx`, or `main.jsx`.

    - **What JavaScript and React do**:

      2. React calls `Item` for `Milk` once; `number` becomes `1`.
      3. React calls `Item` for `Milk` a second time and keeps that second result; `number` becomes `2`, so the page shows `2. Milk`.
      4. The same happens for `Bread` (`3`, then `4`) and `Eggs` (`5`, then `6`).
      5. On the first `Dark mode` click, each item is called twice again, so the page shows `8. Milk`, `10. Bread`, `12. Eggs`.
- **React Does**:

### Principle 3: Changing an Array That Came From Outside Breaks the Page, but Changing an Array Made in the Same Render Is Fine
- **Handle**: `outside-vs-local-mutation`
- **Rule**: During render, a component must not change an array or object it received or that existed before the render, such as a prop; it may freely change an array it created itself in the same render, because that array is new on every call and nobody outside sees it.
- **Opening Essence**:
  - **Furniture-free snippet**:
    - Outside: `const groceries = ['Milk', 'Bread', 'Eggs']; function addBags() { groceries.push('Shopping bags'); return groceries; }`, called twice: the array ends with `Shopping bags` twice.
    - Local: `function addBags(items) { const list = items.slice(); list.push('Shopping bags'); return list; }`, called twice: each result has `Shopping bags` once, and `groceries` stays three items long.
  - **Human image**: writing on the shared shopping list on the fridge versus writing on your own photocopy of it. Each note on the fridge list stays there for everyone; notes on a fresh photocopy disappear when the copy is thrown away.
  - **Exact nuance of confusion to state out loud**:
    1. `items.push('Shopping bags')` and `list.push('Shopping bags')` look like the exact same line, but they are NOT the same thing: the first changes the array that lives outside the component, the second changes a copy made inside this call.
    2. The word mutation sounds dangerous, but changing an array is not forbidden in itself; what matters is only whether the array existed before the render began.
- **Root Distinction**:
  - *Junior blurred view*: "`items` is my component's own parameter, so I can add to it."
  - *Senior grounding*: a prop array is the same array object the parent holds; `.push()` on it changes the parent's array, and every later render starts from the changed array, while an array made with `.slice()` or `[]` in this render is new every time.
- **Real Beginner Mistake (events, in order)**:
  1. The developer wants a summary line under the list that always reminds the shopper to bring shopping bags.
  2. In `App.jsx`, `const groceries = ['Milk', 'Bread', 'Eggs'];` sits at the top of the file, and `App` places `<ListSummary items={groceries} />`.
  3. In `ListSummary.jsx`, the developer writes `items.push('Shopping bags');` and returns `<p className="summary">You need: {items.join(', ')}</p>`.
  4. With `<StrictMode>` from Principle 2, the page loads showing `You need: Milk, Bread, Eggs, Shopping bags, Shopping bags`.
  5. The shopper clicks `Dark mode`; the line grows to four `Shopping bags`, and after the second click to six.
  6. In the production build, the line shows one `Shopping bags` on load, so the developer thinks the doubled version was only a development quirk.
  7. In production, the first `Dark mode` click still shows `Shopping bags, Shopping bags`.
  8. The fix: `const list = items.slice(); list.push('Shopping bags');` and `{list.join(', ')}`; the line shows `You need: Milk, Bread, Eggs, Shopping bags` on load and after every click, and `groceries` stays three items long.
- **Interview Depth**:
  - Local mutation is the `react.dev` term; it is fine because the array is created inside the same render, so no code outside the component sees it, and it is created fresh on the next render.
  - `.slice()` with no arguments returns a new array with the same items, so pushing into the copy leaves the original unchanged; a second fix is to write `Shopping bags` straight into the JSX and not touch the array at all.
  - Props and state are read-only: changing them in place makes the output depend on how many times the component already ran.
  - Which array methods change the array in place and which return a new one is deferred to `Q19 #state_arrays`.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any line in `App.jsx` that adds `Shopping bags` to `groceries`.
    - **Who supplies it**: `ListSummary`, through `items.push(...)`, because `items` and `groceries` are the same array object; React hands the child the array itself, not a copy.
    - **What JavaScript and React do**:
      1. `App.jsx` loads once, and JavaScript creates the array `['Milk', 'Bread', 'Eggs']` and names it `groceries`.
      2. React calls `ListSummary` with `{ items: groceries }`, so `items` points at that same array.
      3. `items.push('Shopping bags')` adds a fourth item to the array that `groceries` also names.
      4. On the next render, `App` passes the same `groceries`, now four items long, and `ListSummary` pushes a fifth.
      5. Under `<StrictMode>`, `ListSummary` is called twice per render, so two items are added per render.
  - **Bridge 2**:
    - **Reader will not find**: any `Shopping bags` inside `groceries` after the fix, although the page shows it.
    - **Who supplies it**: the new array `list` made by `items.slice()` in this call of `ListSummary`.
    - **What JavaScript and React do**:
      1. `items.slice()` creates a new array with `Milk`, `Bread`, `Eggs`.
      2. `list.push('Shopping bags')` changes only the new array.
      3. `list.join(', ')` gives the text `Milk, Bread, Eggs, Shopping bags`.
      4. On the next call, `.slice()` makes another fresh copy from the unchanged three-item `groceries`.
- **React Does**:
  - Impure `ListSummary`, no `<StrictMode>`, dev server: load `<p class="summary">You need: Milk, Bread, Eggs, Shopping bags</p>` with `groceries.length` `4`; click 1 shows two `Shopping bags` (`length` `5`); click 2 shows three (`length` `6`).
  - Impure `ListSummary`, `<StrictMode>`, dev server: load shows two `Shopping bags` (`length` `5`); click 1 shows four (`length` `7`); click 2 shows six (`length` `9`). No Console warning or error.
  - Impure `ListSummary`, `<StrictMode>`, production build: load shows one `Shopping bags` (`length` `4`); click 1 shows two (`length` `5`).
  - `ListSummary` with `items.slice()`, `<StrictMode>`, dev server: `You need: Milk, Bread, Eggs, Shopping bags` on load and after every click, and `groceries.length` stays `3`.
- **Example Step**: Adds `const groceries = ['Milk', 'Bread', 'Eggs'];` at the top of `src/App.jsx`, creates `src/components/ListSummary.jsx`, and places `<ListSummary items={groceries} />` below the `<ul>` and above the button. New page element here: the summary line `You need: ...`.
- **Code names**: `src/App.jsx`, `src/components/ListSummary.jsx`, `ListSummary`, `groceries`, `items`, `list`, `.push()`, `.slice()`, `.join(', ')`, `summary`, `'Shopping bags'`, `You need: Milk, Bread, Eggs, Shopping bags`, `groceries.length`
- **Visual idea**: A fridge list versus a photocopy: the shared `groceries` array growing by one or two `Shopping bags` per render, next to a fresh `list` copy made and thrown away on each call while `groceries` stays at three items.

### Principle 4: Side Effects Belong in Event Handlers, Which Never Run During Render
- **Handle**: `side-effects-in-handlers`
- **Rule**: Code that changes something outside the component, such as counting in an outside variable or logging what the user did, belongs in an event handler like `handleToggle`; React runs a handler only when the user acts, never during render, so handlers do not need to be pure and `<StrictMode>` does not call them twice. An Effect is a last resort, taught later.
- **Opening Essence**:
  - **Furniture-free snippet**: the same two lines `switches = switches + 1;` and `console.log('Theme switches counted:', switches);` placed once in the body of `App` and once inside `function handleToggle() { ... }` in `App`.
  - **Human image**: the everyday meaning of side effect from medicine, the extra result that happens on the side of the main job; a component's main job is to return JSX, so every extra change goes somewhere that runs only when the user acts.
  - **Exact nuance of confusion to state out loud**: `handleToggle` is written inside `App`, so it looks as if it runs whenever `App` runs, but it does NOT: being written inside the component is not the same thing as running during render. React only creates the function during render; it calls it when the button is clicked.
- **Root Distinction**:
  - *Junior blurred view*: "Every line inside `App` runs when `App` renders, so a counter anywhere in `App` counts the same thing."
  - *Senior grounding*: lines at the top level of the body run on every render, including the first and the extra `<StrictMode>` call; lines inside a handler run once per user action. A count in the body counts renders; a count in the handler counts clicks.
- **Real Beginner Mistake (events, in order)**:
  1. The product owner asks for a count of how many times shoppers switch the theme.
  2. The developer writes `let switches = 0;` at the top of `App.jsx` and puts `switches = switches + 1;` and `console.log('Theme switches counted:', switches);` in the body of `App`, above `return`.
  3. With `<StrictMode>` in development, the page loads and the Console already shows `Theme switches counted: 1` and `Theme switches counted: 2`, although nobody clicked.
  4. Two clicks later, the Console has reached `Theme switches counted: 6`.
  5. Without `<StrictMode>` or in production, the load alone still logs `Theme switches counted: 1`, and two clicks reach `3`; the count is always one too many and counts any other re-render of `App`.
  6. The fix: move both lines into `handleToggle`, above `setDark(!dark)`.
  7. With `<StrictMode>` in development, the load logs nothing, the first click logs `Theme switches counted: 1`, and the second logs `Theme switches counted: 2`.
- **Interview Depth**:
  - The quick test from `react.dev` for whether code runs during render: code at the top level of the component body runs during render; code inside an event handler or an Effect does not.
  - Event handlers are defined inside the component but do not run during render, so they are the first place for side effects; `useEffect` is the last resort when no event causes the change (`Q32 #use_effect`).
  - Changing the DOM during render, such as `document.title = ...` or `document.getElementById('time').className = 'night'`, is a side effect; when the change can be expressed in JSX, return it instead, such as `<h1 className={className}>` (`react.dev` "Fix a broken clock").
  - Why React cares about purity: the same component can render on the server for many requests (`Q108 #server_components`), React can skip rendering a component whose inputs did not change (`Q55 #memo`), and React can stop and restart a render that became outdated (`Q66 #concurrent_rendering`). All three are safe only when calling a component has no effect beyond its JSX.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any call of `handleToggle()` written with parentheses in `App.jsx`; the tag only says `onClick={handleToggle}`.
    - **Who supplies it**: React calls `handleToggle` when the browser reports the click on the button (recall from Lecture 11).
    - **What JavaScript and React do**:
      1. During render, JavaScript creates the function `handleToggle` but does not run its body.
      2. `<StrictMode>` calls `App` twice, creating `handleToggle` twice and running neither.
      3. The shopper clicks `Dark mode`, and React calls `handleToggle` once.
      4. `switches` becomes `1`, the Console logs `Theme switches counted: 1`, and `setDark(!dark)` asks for a re-render.
      5. The re-render calls `App` twice again, and `handleToggle` still does not run, so the count stays `1`.
- **React Does**:
  - Count in the body of `App`, `<StrictMode>`, dev server: load then two clicks log `Theme switches counted: 1` through `Theme switches counted: 6`, two lines per render.
  - Count in the body of `App`, no `<StrictMode>`, dev server: load then two clicks log `Theme switches counted: 1`, `2`, `3`.
  - Count in the body of `App`, `<StrictMode>`, production build: load then one click log `Theme switches counted: 1`, `2`.
  - Count in `handleToggle`, `<StrictMode>`, dev server: load logs nothing; click 1 logs `Theme switches counted: 1`; click 2 logs `Theme switches counted: 2`. Same in the production build.
  - Both versions switch the button text and the `<main>` class the same way; no Console warning or error.
- **Example Step**: Adds `let switches = 0;` at the top of `src/App.jsx`, first places the count in the body of `App`, then moves it into `handleToggle` above `setDark(!dark)`. No new page element; the change is seen in the Console.
- **Code names**: `src/App.jsx`, `App`, `handleToggle`, `let switches = 0`, `switches = switches + 1`, `console.log('Theme switches counted:', switches)`, `Theme switches counted: 1`, `Theme switches counted: 6`, `onClick={handleToggle}`, `setDark(!dark)`, `useEffect`, `document.title`
- **Visual idea**: Two Console panes side by side for the same load and two clicks: body count `1` to `6`, handler count `1` and `2`.

## Interview Points
1. Definition: a pure component minds its own business, meaning it does not change variables or objects that existed before it ran, and it returns the same JSX for the same props, state, and context.
2. What breaks: an impure component looks right on the first render but changes its output on later renders with the same inputs, such as a number that climbs on every re-render or an item that repeats in a prop array.
3. `<StrictMode>`: in development, React calls each component function twice so impure code shows on the first load; pure components are unaffected, and production calls each component once.
4. Local mutation: changing an array or object created in the same render is fine; changing one that existed before the render, such as a prop or a module-level variable, is not.
5. Where side effects go: in event handlers, which run only on user actions and not during render, so they need not be pure; `useEffect` is the last resort.
6. Why React insists: purity lets React render the same component on the server, skip rendering when inputs did not change, and safely stop or repeat a render.
