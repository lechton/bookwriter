# Q42 Principle Map (River Version v1): How useActionState Remembers the Last Answer and the Pending Flag

- **Version**: River Version v1, skills `v10.6`
- **Bank row**: 42 of `questions/questions.md`
- **Topic tag**: `#use_action_state` | `❱ CORE`
- **Interview question**: How does useActionState manage a form's submitted state and pending flag?
- **Bank hook**: You need the last action's returned message and a pending indicator, without hand-rolled useState bookkeeping next to every form. What does useActionState track?

## Scope

This lesson covers:
- `useActionState(signup, null)` and the three values it returns: the current state, the action to pass to the form, and `isPending`.
- The action's two parameters: the previous state first, the submitted `formData` second.
- How the value the action returns becomes the state the screen shows, and why a known error is returned, not thrown.
- How `isPending` is `true` while the action runs, and what it replaces: `useState` calls for the message and the pending flag set by hand.
- Only the client form path: the dispatcher passed to `<form action={...}>`.

## Start of the Lecture

- **Opening Essence of the chapter** (a way of working, so it opens in plain words on a real screen, before any code):
  1. The screen: a newsletter box at the bottom of a news site, titled "Get our weekly news", with one email box and one Sign up button.
  2. The user types `john@example.com` and clicks Sign up.
  3. For about one second, the button reads "Signing up..." and cannot be clicked.
  4. Then one line appears under the box: "Thanks! john@example.com is signed up."
  5. The user signs up with the same email again. The line now reads "This email is already signed up."
  6. The question this screen raises for the developer: after each submit, the form must remember two things, what the last submit answered, and whether a submit is still running.
- **Key idea to remember**: `useActionState` keeps what the action returned last time as state, and gives a pending flag that React turns on and off around the action.
- **What is at stake for the user**: with the message and the pending flag written by hand, one forgotten line leaves the button stuck on "Signing up..." forever, or leaves the old answer next to a new one.
- **Where readers usually go wrong**: they keep the Lesson 41 action shape, `signup(formData)`, but with `useActionState` the first parameter is the previous state, so `formData` moves to second place.
- **Theme**: a form must show the answer of its last submit and a busy button while the submit runs.
- **Ways** (developers really choose between these for the same job):
  1. `useState` for the message, `useState` for the pending flag, both set by hand around the request in a submit handler (Lessons 11, 12, 33, 40). Fits: any React version, or when the code must run outside a form action.

## Principles

### Principle 1: useActionState Gives the Form Three Values

- **Rule**: calling `useActionState(signup, null)` at the top of the component returns exactly three values: the current state, an action to pass to `<form action>`, and `isPending`; on the first render the state equals the initial state.
- **Move**: Smallest code first, because the hook is a new idea and must be seen on one line before the newsletter files.
- **Opening Essence**: the smallest code is one line, `const [message, signupAction, isPending] = useActionState(signup, null);`. The confusion to say out loud: it looks like `useState`, and "it may look the same, but it is NOT the same thing": the second value is not a setter you call with a new value; it is an action you give to the form, and React fills the state with what `signup` returns.
- **Root Distinction**:
  - junior: "I wrote `signup` and put it on the form, so React will show its answer."
  - senior: the form gets the action returned by `useActionState`, not `signup` itself; only that returned action stores the answer in state.
- **Simplest version**:

```jsx
const [message, signupAction, isPending] = useActionState(signup, null);

<form action={signupAction}>
```

- **Words to teach**:
  - `useActionState`: a Hook that creates state for the result of an Action. Provided by React, imported from `'react'`. Needed when the reader writes the first line of `Newsletter`.
  - the current state, named `message` here: "During the first render, it will match the `initialState` you passed. After `dispatchAction` is invoked, it will match the value returned by the `reducerAction`." Provided by React. Needed when the line under the box first appears.
  - the action dispatcher, named `signupAction` here (the docs call it `dispatchAction`): "A `dispatchAction` function that you call inside Actions." Provided by React. Needed when the reader writes `<form action={signupAction}>`.
  - `isPending`: "tells you if any dispatched Actions for this Hook are pending." Provided by React. Needed in Principle 4; introduced here only as the third value.
  - `initialState`, here `null`: "React ignores this argument after `dispatchAction` is invoked for the first time." Needed when the reader asks why no line shows before the first submit.
  - Already taught: `useState` and array destructuring (12), named import (5), `&&` (10), `<form action>` (41), top-level Hooks (38).
  - Helper words: none.
- **Side by side**:
  - "with `useState`": `const [message, setMessage] = useState(null);` two values, the second one is called with the new value.
  - "with `useActionState`": `const [message, signupAction, isPending] = useActionState(signup, null);` three values, the second one goes on the form.
  - Verdict: NOT the same thing.
  - Reason: with `useActionState`, the new state comes from what `signup` returns, not from a value our code passes to a setter.
- **Surprises**:
  1. The page loads. `message` is `null`, so `{message && <p>{message}</p>}` shows no line.
  2. The user clicks Sign up. React calls `signup` and stores what it returns.
  3. The line appears only after the first submit, never on the first render.
- **Where did that come from?**:
  - `message`, `signupAction`, `isPending`: names we choose; array destructuring (Lesson 12) gives a name to each of the three items React returns, in order.
  - `null` as the first value of `message`: our second argument, `initialState`.
  - The call of `signup`: our code never calls it. Steps: the user submits the form; React calls the action on the form, `signupAction`; `signupAction` calls `signup`; React stores the return value as the new `message` and re-renders.
- **Real beginner mistake** (from the Troubleshooting section "Cannot update action state while rendering"):
  1. A developer wants the form to run once when the page opens and calls `signupAction()` directly in the component body.
  2. The call schedules a state update, which triggers a re-render.
  3. The re-render calls `signupAction()` again.
  4. The Console shows the error quoted under React does.
  5. The fix: call the action only in response to the user, here by the form submit.
- **Interview depth**:
  - Why three values and not two: the third, `isPending`, tracks the Action, which `useState` knows nothing about.
  - `dispatchAction` has a stable identity, so it can be left out of Effect dependencies.
  - `useActionState` is a Hook: top level only, not in loops or conditions.
  - It was called `ReactDOM.useFormState` in Canary releases, renamed and `useFormState` deprecated (React 19 blog).
- **React does**:
  - Page on first render: the heading, the email box, the Sign up button, no message line.
  - Console on first render: nothing; `unconfirmed`, checked in the lab.
  - Elements panel on first render: `<form>` with `<h2>`, `<input name="email">`, `<button>`; no `<p>`. The exact serialization of the `action` attribute React writes on the `<form>` node: `unconfirmed`.
  - Console for the mistake, exact text from the docs: `Cannot update action state while rendering.`
- **Example step**: `src/App.jsx` gets `Newsletter` with the heading, the email box, the Sign up button, the hook line, `action={signupAction}`, and the message line; `signup` takes no parameters yet and returns the fixed string `'Thanks, you are signed up!'`. `src/api.js` is not used yet.
- **Code names**: `src/App.jsx`, `Newsletter`, `signup`, `useActionState`, `'react'`, `message`, `signupAction`, `isPending`, `null`, `<form action={signupAction}>`, `<h2>Get our weekly news</h2>`, `<input name="email" placeholder="john@example.com" />`, `<button>Sign up</button>`, `{message && <p>{message}</p>}`, `'Thanks, you are signed up!'`, `Cannot update action state while rendering.`

### Principle 2: formData Moves to the Second Parameter

- **Rule**: when the action is given to `useActionState`, React calls it with the previous state first and the submitted `formData` second, so it must be written `signup(previousState, formData)`.
- **Move**: Side by side, because the Lesson 41 action and this action look almost the same and differ only in the parameter list.
- **Opening Essence**: two lines side by side, `function signup(formData)` from Lesson 41 and `function signup(previousState, formData)`. The confusion to say out loud: "It may look the same, but it is NOT the same thing!" The same `formData.get('email')` works in one and breaks in the other, because React puts a new value in the first place.
- **Root Distinction**:
  - junior: "The form always hands my action the form data first."
  - senior: what the action receives depends on who calls it; through `useActionState`, the first argument is the previous state.
- **Simplest version**:

```jsx
function signup(formData) {
  const email = formData.get('email');
}

function signup(previousState, formData) {
  const email = formData.get('email');
}
```

- **Words to teach**:
  - `previousState`: "The last state. Initially this is equal to the `initialState`. After the first call to `dispatchAction`, it's equal to the last state returned." Provided by React. Needed when the reader writes the parameter list of `signup`.
  - `reducerAction`, reducer action: the docs' name for the function passed to `useActionState`; "It reduces the previous state into a new state, like `useReducer`. It's an Action because it's called inside a Transition and can perform side effects." Needed when the reader asks why the first parameter is a state.
  - Already taught: `formData`, `formData.get` (40), the Lesson 41 action shape (41), reducer `(state, action)` (27), side effect (14).
  - Helper words: none.
- **Side by side**:
  - "with `signup(formData)`" (Lesson 41 shape) given to `useActionState`: the first parameter receives the previous state, `null` on the first submit.
  - "with `signup(previousState, formData)`": the first parameter receives the previous state, the second the form data.
  - Verdict: NOT the same thing.
  - Reason: "the `reducerAction` receives an extra argument as its first argument: the previous or initial state. The submitted form data is therefore its second argument instead of its first."
- **Surprises**:
  1. The developer keeps `function signup(formData)` and passes it to `useActionState(signup, null)`.
  2. The user submits the form for the first time.
  3. React calls `signup(null, formData)`, so the parameter named `formData` holds `null`.
  4. `formData.get('email')` throws, because `null` has no `get`.
  5. Nothing about the email reaches the screen. The exact error text and what the page shows: `unconfirmed`.
- **Where did that come from?**:
  - `previousState`: supplied by React. Steps: first submit, React passes `initialState`, here `null`; every later submit, React passes the value `signup` returned last time.
  - `formData`: supplied by React from the submitted `<form>`; it collects every field by its `name`, here `email` (form.md, Lesson 40).
- **Real beginner mistake** (from the Troubleshooting section "My Action cannot read form data"):
  1. A developer has a working Lesson 41 form, `<form action={signup}>` with `function signup(formData)`.
  2. To show a message, they wrap it: `useActionState(signup, null)` and put `signupAction` on the form.
  3. They leave the parameter list as it was.
  4. On submit, `formData` holds the previous state, and reading the email fails.
  5. The fix: add `previousState` as the first parameter.
- **Interview depth**:
  - `useActionState` is like `useReducer`, but the reducer can perform side effects; `useReducer`'s reducer must be pure.
  - Called from a click handler instead of a form, the second argument is whatever value is passed to `dispatchAction`, often an object with a `type`; that path needs `startTransition` (Lesson 67).
  - `reducerAction` is not invoked twice in `<StrictMode>`, because it is designed to allow side effects.
  - The return type of `reducerAction` must match the type of `initialState`.
- **React does**:
  - Page with the right signature: same as Principle 1.
  - Console with the wrong signature: a `TypeError` about reading `get` of `null`; exact text `unconfirmed`.
  - Page with the wrong signature, no Error Boundary present: `unconfirmed`.
- **Example step**: `src/App.jsx`: `signup` becomes `function signup(previousState, formData)`, reads `const email = formData.get('email');`, and returns `` `Thanks! ${email} is signed up.` ``. `src/api.js` is not used yet.
- **Code names**: `src/App.jsx`, `signup`, `previousState`, `formData`, `formData.get('email')`, `email`, `'email'`, `` `Thanks! ${email} is signed up.` ``, `null`

### Principle 3: The Returned Text Becomes the Message Line

- **Rule**: whatever the action returns becomes the new state; a known problem, such as an email already signed up, is returned as state, never thrown.
- **Move**: Steps for a surprise, because the line on the screen changes with no setter in our code, and the reader must see each step from the click to the new line.
- **Opening Essence**: the smallest code is two `return` lines inside one action, the error text and the thanks text. Key idea: the action's `return` is the only way the line under the box changes. What is at stake: a thrown error for a known case does not reach the line; React cancels queued actions and shows the nearest Error Boundary. Where readers go wrong: they throw on "already signed up" as they would in a `try` block.
- **Root Distinction**:
  - junior: "A failed sign-up is an error, so I throw it."
  - senior: an expected answer, even a bad one, is state and is returned; only an unexpected failure is thrown.
- **Simplest version**:

```jsx
async function signup(previousState, formData) {
  const error = await signUp(formData.get('email'));
  if (error) {
    return error;
  }
  return 'Thanks!';
}
```

- **Words to teach**:
  - the returned value: "`reducerAction` returns the new state, and triggers a Transition to re-render with that state." Provided by our code, stored by React. Needed when the reader asks how the line changed.
  - known errors versus unknown errors: the docs' two ways. "For known errors, such as 'quantity not available' validation errors from your backend, you can return it as part of your `reducerAction` state and display it in the UI. For unknown errors, such as `undefined is not a function`, you can throw an error." Needed when the reader writes the "already signed up" branch.
  - Already taught: `async`, `await` (33), `return`, `if`, template string, named import (5), `&&` (10).
  - Helper words in the given `src/api.js`: `setTimeout`, `new Promise`, `includes`, `push`. The lecture shows the file and does not teach them.
- **Side by side**:
  - "with `return error`": the text reaches `message`, and the line shows "This email is already signed up".
  - "with `throw new Error(error)`": React cancels all queued actions and rethrows the error from the `useActionState` Hook to the nearest Error Boundary.
  - Verdict: NOT the same thing.
  - Reason: only a returned value becomes state; a thrown error leaves the form.
- **Surprises**:
  1. The user types `john@example.com` and clicks Sign up.
  2. React calls `signup(null, formData)`.
  3. `signUp` waits one second and returns `null`, so `signup` returns `'Thanks! john@example.com is signed up.'`.
  4. React stores the text as `message` and re-renders; the line appears. No `setMessage` exists in our code.
  5. The user submits the same email again. `previousState` now holds the thanks text.
  6. `signUp` returns `'This email is already signed up'`; `signup` returns it; the line changes to that text.
  7. After each submit, the email box is empty again. The docs say: "After the `action` function succeeds, all uncontrolled field elements in the form are reset." That a returned error text counts as success, so the box also empties after the error line: `unconfirmed`. The fix for this belongs to Lesson 45.
- **Where did that come from?**:
  - `signUp`: imported from our `src/api.js` (named import, Lesson 5).
  - `error` inside `signup`: the value `signUp` returns, `null` or the error text.
  - The new `message`: React takes the return value of `signup`; our code calls no setter.
- **Real beginner mistake** (from the Troubleshooting section "My actions are being skipped" and "Handling errors"):
  1. A developer writes `throw new Error('This email is already signed up')` for the known case.
  2. The user signs up with an email already on the list.
  3. React cancels every queued action and sends the error to the nearest Error Boundary.
  4. With no Error Boundary, the message line never shows the text. What the page shows instead: `unconfirmed`.
  5. The fix from the docs: "catch errors within your `reducerAction` and return an error state instead of throwing."
- **Interview depth**:
  - "If `dispatchAction` throws an error, React cancels all queued actions and shows the nearest Error Boundary."
  - The state can be any shape; the docs' error example returns `{ count, error }`, a plain object.
  - There is no built-in reset function; the docs offer a reset payload handled in `reducerAction`, a `key` on the component, or the automatic form reset.
  - Setting other state after `await` inside `reducerAction` currently needs an extra `startTransition` (Lesson 67).
- **React does**:
  - Page after the first submit: `Thanks! john@example.com is signed up.` under the box.
  - Page after the second submit with the same email: `This email is already signed up` under the box.
  - Elements panel: a `<p>` node appears inside the `<form>` after the first submit and its text changes after the second.
  - Console: nothing for either submit; `unconfirmed`, checked in the lab.
- **Example step**: `src/api.js` is added with `signUp`. `src/App.jsx`: `signup` becomes `async`, awaits `signUp(email)`, returns the error text when there is one, and the thanks text otherwise.
- **Code names**: `src/api.js`, `signUp`, `emails`, `src/App.jsx`, `signup`, `error`, `email`, `'This email is already signed up'`, `` `Thanks! ${email} is signed up.` ``, `john@example.com`, `throw new Error(...)`

### Principle 4: isPending Turns the Button into Signing up...

- **Rule**: `isPending` is `true` from the moment the user submits until React shows the state the action returned, so the button can read "Signing up..." and be disabled without any `useState` or `finally`.
- **Move**: Side by side, because the hand-written pending flag and `isPending` give the same screen, and the reader must see that nothing is lost.
- **Opening Essence**: two buttons side by side, one driven by `const [isPending, setIsPending] = useState(false)` with `setIsPending(true)` and `setIsPending(false)` around the request, one driven by `isPending` from `useActionState`. The confusion to say out loud: "Yes, it is the exact same thing!" on the screen for one submit. The difference is in the code only: the hook version has no `setIsPending(true)` and no `setIsPending(false)` line that a developer can forget.
- **Root Distinction**:
  - junior: "A busy button needs its own state, turned on before the request and off after it."
  - senior: the busy flag belongs to the Action; React already knows when the Action starts and ends.
- **Simplest version**:

```jsx
<button disabled={isPending}>
  {isPending ? 'Signing up...' : 'Sign up'}
</button>
```

- **Words to teach**:
  - `isPending`: "The `isPending` flag that tells you if any dispatched Actions for this Hook are pending." Provided by React. Needed when the user clicks Sign up and the button must change.
  - pending: the docs' word for "the Action is in progress". Everyday sense: waiting, not finished.
  - Already taught: ternary `? :` (10), `useState` (12), loading flags by hand (33).
  - Helper words: `disabled`, the HTML attribute that stops a button from being clicked (MDN).
- **Side by side**:
  - "with `setIsPending` by hand": three `useState` calls (`email` or the form data, `message`, `isPending`), `setIsPending(true)` before the request, `setIsPending(false)` after it, often inside `finally`.
  - "with `isPending` from `useActionState`": no `useState`, no `setIsPending`, no `finally`.
  - Verdict: the exact same thing on the screen for one submit.
  - Reason: React sets `isPending` to `true` when the action starts and back to `false` when the returned state is shown; the hand-written code does the same with two lines.
- **Surprises**:
  1. The line from the last submit says "Thanks! john@example.com is signed up."
  2. The user types a new email and clicks Sign up.
  3. For one second the button reads "Signing up..." and the old thanks line is still on the screen, because `message` changes only when the new value returns.
  4. The new line replaces the old one, and the button reads "Sign up" again, in the same render.
  5. Steps 3 and 4 follow from the docs' Returns text; what the screen shows between them: `unconfirmed`, checked in the lab.
- **Where did that come from?**:
  - `isPending`: the third value of `useActionState`; React flips it. Our code never sets it.
- **Real beginner mistake**:
  1. A developer writes the hand-written version: `setIsPending(true)`, then `await signUp(email)`, then `setIsPending(false)`.
  2. The request throws, for example when the network fails.
  3. The line `setIsPending(false)` never runs.
  4. The button stays on "Signing up..." and disabled, and the user cannot try again.
  5. The usual fix is a `try` and `finally` block; with `useActionState` there is no such line to forget.
- **Interview depth**:
  - React queues several submits and runs them one after the other; each call gets the result of the one before. "4 clicks will take ~4 seconds to complete", and this is "intentional in the design of `useActionState`."
  - `isPending` stays `true` until all queued actions finish: "React shows the pending state until all the tickets are added, and then re-renders with the final state."
  - Calling the dispatcher outside a form action without `startTransition` makes `isPending` not update and logs: `An async function with useActionState was called outside of a transition. This is likely not what you intended (for example, isPending will not update correctly). Either call the returned function inside startTransition, or pass it to an `action` or `formAction` prop.` (Lesson 67.)
  - A button in another component reads the form's pending state with `useFormStatus` and its `pending` field (Lesson 43).
  - Showing the expected result before the answer arrives is `useOptimistic` (Lesson 44).
  - Aborting a queued action with `AbortController` is possible but "isn't always safe", because it does not undo a server-side change.
- **React does**:
  - Page during the one-second wait: the button reads `Signing up...` and cannot be clicked.
  - Page after the wait: the button reads `Sign up`, and the new message line shows.
  - Elements panel during the wait: the `<button>` node carries the `disabled` attribute; exact serialization `unconfirmed`.
  - Console: nothing; `unconfirmed`, checked in the lab.
- **Example step**: `src/App.jsx`: the button gets `disabled={isPending}` and the text `{isPending ? 'Signing up...' : 'Sign up'}`. The finished `Newsletter` is complete; `src/api.js` and `src/main.jsx` are unchanged.

## Interview Points

- `useActionState(reducerAction, initialState)` returns exactly three values: the current state, the action dispatcher, and `isPending`.
- On the first render the state equals `initialState`; after each action it equals what the action returned.
- The action receives the previous state first and the payload second; from a `<form action>`, the payload is the submitted `FormData`.
- Passing the dispatcher to `<form action>` runs the submit in a Transition, so no `startTransition` is needed.
- Known errors are returned as state and shown on the screen; unknown errors are thrown, cancel queued actions, and reach the nearest Error Boundary.
- `isPending` is `true` while any dispatched action for this Hook runs, and it replaces the hand-written pending flag and its `finally` line.
- Calls are queued and run one after the other, because each needs the previous result; for parallel actions, use `useState` with `useTransition`.
- It is like `useReducer` with side effects allowed; `useReducer`'s reducer must be pure.
- Calling the dispatcher during render logs `Cannot update action state while rendering.`
