- **Interview Question**: *How do you connect a component to an external system, and how do you disconnect it?*

## Scope

Covered here:
- What an Effect is, in the docs' words: "Effects let you specify side effects that are caused by rendering itself, rather than by a particular event."
- The two kinds of code the reader already knows, rendering code and event handlers, and the case neither one covers: something must start because the component is on the screen, and no click causes it.
- What an external system is: "These systems aren't controlled by React, so they are called external." The docs' list: a timer with `setInterval()` and `clearInterval()`, an event subscription with `window.addEventListener()` and `window.removeEventListener()`, a chat server, a third-party library.
- The docs' three steps: declare an Effect with `useEffect`, specify the dependencies, add cleanup if needed.
- When React runs an Effect: after the commit. With no dependency array, after every commit; with `[]`, only after the first commit, on mount; with `[a, b]`, on mount and after any commit where `a` or `b` changed, compared with `Object.is`.
- The dependencies are decided by the code inside the Effect, not chosen by us; the linter checks them.
- The cleanup function: React calls it before the Effect runs again and one final time when the component unmounts. It must stop or undo what the setup started.
- Strict Mode in development: one extra setup and cleanup before the real setup. The docs' question to ask: "how to fix my Effect so that it works after remounting", not "how to run an Effect once". A ref that blocks the second run hides the test but leaves the bug.
- An event is not an Effect: buying a product belongs in the Buy click handler.

## Start of the Lecture

**Opening Essence of the chapter**:
- The question of the lesson: a counter on the page must count seconds by itself while it is shown, and stop when it is hidden. No click starts it. Where does the code that starts the timer go, and who stops it?
- No short code shows this idea with a surprise, so the idea comes first in plain words, as opening-essence Example 8 does.
- The two kinds of code the reader knows, from the docs' section "What are Effects and how are they different from events?":
  1. Rendering code, at the top level of the component: it takes props and state and returns JSX. It must be pure. The docs: "Like a math formula, it should only _calculate_ the result, but not do anything else." Lesson 14.
  2. Event handlers: they "*do* things rather than just calculate them", and they run because of "a specific user action (for example, a button click or typing)". Lesson 11.
- The third case: something must happen because the component is on the screen, "no matter which interaction caused the component to appear". The docs' example: a `ChatRoom` that must stay connected to the chat server while it is visible. This is an Effect.
- Everyday image for the whole lesson, the light in a room:
  1. Entering a room: we switch the light on. Leaving it: we switch the light off.
  2. The match in code: the component appearing and leaving; the setup and the cleanup.
  3. What React removes when the component leaves: the DOM nodes it created from our JSX.
  4. What React does not stop: the timer, because our code started it, not React.
- Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"*
  1. Lesson 30's Stopwatch calls `setInterval` inside `handleStart`, the Start click handler.
  2. This lesson's counter calls `setInterval` inside `useEffect`.
  3. Both start the same browser timer. The first runs because the user clicked Start. The second runs because the counter appeared on the page.
- What is at stake for the user, on the example page:
  1. With the timer started in the component body, the counter climbs faster and faster. `unconfirmed`, a lab check.
  2. With the timer in an Effect and no cleanup, in development the counter goes up by two every second. The docs: "instead of incrementing once per second, it increments twice."
  3. In production the counter looks right, but after the user clicks `Hide counter`, the timer keeps running. Each `Show counter` adds one more timer. The docs, for the chat: "the connections would keep piling up."
- Where readers usually go wrong:
  1. They start the timer or the subscription in the component body, as in the bank row: "after six renders you have six subscriptions."
  2. They read `[]` as "run once" and then fight the second run in development, often with a ref.
  3. They write the setup and forget the cleanup.
  4. They put work caused by a click, such as buying, into an Effect.

**Theme**: a seconds counter that must start counting when it appears on the page and stop when the user hides it.

**Ways** (the places the docs give for code that does something, and when each fits):
1. An event handler: when a specific user action causes it, such as Lesson 30's Start click or the docs' Buy button.
2. `useEffect` with a cleanup function: when being on the screen causes it, such as a timer, a chat connection, a `window` event listener, or a widget not written in React.
3. Code outside any component: logic that "should only run once when the application starts", the docs' section "Not an Effect: Initializing the application".
4. No Effect at all: when there is no external system and the Effect "only adjusts some state based on other state". Lesson 34. Named only.

**Example page chosen for this lesson**: a seconds counter that the user can show and hide.
- Parts of the page:
  1. A button that reads `Show counter`, and `Hide counter` while the counter is shown.
  2. Under it, the counter: a big number in an `<h1>`, starting at `0`.
- What the user does, and what each click changes:
  1. Clicks `Show counter`: the number `0` appears and goes up by one every second.
  2. Clicks `Hide counter`: the number disappears, and the timer must stop.
  3. Clicks `Show counter` again: the counter starts again from `0`, with one timer only.
- At the start of the lesson:
  1. `App` has `const [show, setShow] = useState(false);`, a button with `onClick={() => setShow(!show)}` and the text `{show ? 'Hide' : 'Show'} counter`, and `{show && <Counter />}`.
  2. `Counter` has `const [count, setCount] = useState(0);` and returns `<h1>{count}</h1>`.
  3. The problem: the counter shows `0` and never moves, because nothing starts a timer, and there is no click inside the counter to start one.
- At the end of the lesson, `Counter.jsx`:
  1. `import { useState, useEffect } from 'react';`
  2. Inside `useEffect`: `function onTick() { console.log('Tick'); setCount(c => c + 1); }`, then `console.log('Timer started');` and `const intervalId = setInterval(onTick, 1000);`
  3. The cleanup: `return () => { console.log('Timer stopped'); clearInterval(intervalId); };`
  4. The dependency array: `[]`.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx`, `src/components/Counter.jsx`.
- Names follow the docs' Challenge "Fix an interval that fires twice" and the `useEffect` reference section "Updating state based on previous state from an Effect": `Counter`, `count`, `onTick`, `intervalId`, `setCount(c => c + 1)`, `Show counter`, `Hide counter`. The three `console.log` lines are ours, so that the reader can see in the Console when the timer starts, ticks, and stops.

## Principles

### Principle 1: useEffect Starts the Timer After the Commit

- **Rule**: Code that must run because the component is on the screen goes inside `useEffect`; React runs it after the commit, when the DOM is already on the page, while the component body runs during every render and must only calculate the JSX.
- **Move**: Side by side, because the same line in the component body and inside `useEffect` looks alike and does not behave alike.
- **Opening Essence**:
  - Smallest code, the docs' Step 1: `import { useEffect } from 'react';` and `function MyComponent() { useEffect(() => { ... }); return <div />; }`.
  - The docs' sentence for what `useEffect` does: "**`useEffect` "delays" a piece of code from running until that render is reflected on the screen.**"
  - Two places for the same line, Lesson 31's box that must get the cursor when it appears:
    1. In the component body: `inputRef.current.focus();` gives a blank page, because `inputRef.current` is `null` during the first render. Lesson 31.
    2. Inside `useEffect(() => { inputRef.current.focus(); });` the box gets the cursor, because React runs the Effect after it put the `<input>` on the page.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* The line is the same; the moment it runs is not.
  - The docs' reason for the body: "Connecting to a server is not a pure calculation (it's a side effect) so it can't happen during rendering."
- **Root Distinction**:
  - Junior: "The component function is my code, so anything I write in it runs when the component appears."
  - Senior: the component body runs during every render and only calculates JSX; `useEffect` hands React a function that React runs later, after the commit.
- **Simplest version**:
  - The docs' Challenge "Focus a field on mount": `const ref = useRef(null);`, `useEffect(() => { ref.current.focus(); });`, `<input ref={ref} />`.
  - A check: `console.log('Render')` in the body and `console.log('Effect')` inside `useEffect`; the Console shows `Render` before `Effect`. `unconfirmed`, a lab check.
- **Words to teach**:
  - *Effect*: the docs' Note, "capitalized "Effect" refers to the React-specific definition above, i.e. a side effect caused by rendering." Provided by React. Needed at the first `useEffect`.
  - *`useEffect`*: a React Hook; its first argument is a function, the setup function, that React runs after the commit. It returns `undefined`. Provided by React. Needed when the timer moves out of the body.
  - *setup function*: the docs' name for "The function with your Effect's logic". Needed at the same moment.
  - *external system*: "any piece of code that's not controlled by React", such as a timer, the `window` object, a chat server. Needed when the reader asks why a timer is special.
  - *synchronize*: the docs' word for keeping the external system in step with the component while it is on the screen. Needed when the docs' sentence "synchronize a component with an external system" appears.
  - Known: side effect, pure, Lesson 14. Commit, mount, paint, Lesson 13. `ref`, `focus()`, Lesson 31. `setInterval`, Lesson 30. `<StrictMode>`, Lessons 07 and 14.
  - Helper: none.
- **Side by side**:
  - "with `setInterval(onTick, 1000)` in the component body" and "with `setInterval(onTick, 1000)` inside `useEffect`": NOT the same thing. The first runs during rendering, and `<StrictMode>` calls the body twice in development; the second runs after the commit.
  - "with `inputRef.current.focus()` in the body" and "with `inputRef.current.focus()` inside `useEffect`": NOT the same thing. The first reads `null`; the second reads the `<input>` node.
- **Surprises**:
  - The counter climbs faster and faster when `setInterval` is in the body:
    1. React calls `Counter` for the first render; the body calls `setInterval`, and one timer starts.
    2. In development, `<StrictMode>` calls the body twice, so two timers start. Lesson 14.
    3. A second later, a timer calls `onTick`, `setCount` asks for a render, and React calls `Counter` again.
    4. The body calls `setInterval` again, and more timers start.
    5. Every render adds timers, and every timer asks for more renders. The number on the page jumps faster each second, and the Console prints more `Tick` lines each second. `unconfirmed`, a lab check.
  - The counter still climbs faster after the code moves into `useEffect` with no second argument:
    1. React runs the Effect after the first commit, and one timer starts.
    2. Each tick changes `count`, React renders and commits again.
    3. With no second argument, React runs the Effect after every commit. The docs: "By default, your Effect will run after every commit."
    4. The Console prints `Timer started` after every tick, and timers pile up. `unconfirmed`, a lab check. Principle 2 answers it.
- **Where did that come from?**:
  - The function passed to `useEffect`: our code creates it during the render; React keeps it and calls it after the commit. Our code never calls it.
- **Real beginner mistake** (the bank row's friction):
  1. A developer subscribes to a live comments feed in the component body.
  2. Each state change renders the component again.
  3. Each render opens one more subscription.
  4. After six renders, the page holds six subscriptions.
  5. The docs: code at the top level of the component is rendering code, and "Rendering code must be pure."
- **Interview depth**:
  - The docs: "Effects run at the end of a commit after the screen updates."
  - The `useEffect` Caveats: if the Effect "wasn't caused by an interaction (like a click), React will generally let the browser **paint the updated screen first before running your Effect.**" If it was caused by a click, "React may run your Effect before the browser paints the updated screen". For work that must come before the paint, `useLayoutEffect`, Lesson 49.
  - `useEffect` is called at the top level of the component, never inside a loop or a condition: the Caveats, Lesson 38.
  - Effects only run on the client, "They don't run during server rendering": Lesson 102.
  - The docs' `VideoPlayer`: calling `ref.current.play()` during rendering "isn't allowed" and crashes, because "its DOM does not exist yet"; inside `useEffect` it works.
  - `keeping-components-pure`: when no event handler fits, `useEffect` "should be your last resort."
- **React does**:
  - Page: with `setInterval` in the body, the number climbs faster and faster. `unconfirmed`, a lab check.
  - Console: more `Tick` lines every second; with the Effect and no array, `Timer started` after every tick. `unconfirmed`, a lab check.
  - Elements panel: only the text inside `<h1>` changes. `unconfirmed`.
- **Example step**:

### Principle 2: [] Starts the Timer Only on Mount

- **Rule**: The second argument of `useEffect` lists every value from the component that the Effect reads; with no array the Effect runs after every commit, with `[]` only after the first commit, and with `[a, b]` also after any commit where `a` or `b` changed.
- **Move**: Side by side, because the docs give three forms that look almost the same and run at different moments.
- **Opening Essence**:
  - Smallest code, the docs' Pitfall, three forms:
    1. `useEffect(() => { ... });` "This runs after every render".
    2. `useEffect(() => { ... }, []);` "This runs only on mount (when the component appears)".
    3. `useEffect(() => { ... }, [a, b]);` "This runs on mount *and also* if either a or b have changed since the last render".
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* The docs: "The behaviors without the dependency array and with an *empty* `[]` dependency array are different."
  - Key idea: "you can't "choose" your dependencies." They "are determined by the code inside the Effect."
- **Root Distinction**:
  - Junior: "The array is a list of the moments I want the Effect to run."
  - Senior: the array is a list of the values the Effect reads; React compares them with the last render's values and skips the Effect when all are the same.
- **Simplest version**:
  - The docs' `VideoPlayer`: `useEffect(() => { if (isPlaying) { ref.current.play(); } else { ref.current.pause(); } }, [isPlaying]);`.
  - With `[]` instead of `[isPlaying]`, the docs: "You should see an error saying `React Hook useEffect has a missing dependency: 'isPlaying'`".
- **Words to teach**:
  - *dependencies, dependency array*: the second argument; "The list of all reactive values referenced inside of the `setup` code." Provided by our code, read by React. Needed when `[]` is added.
  - *`[]`*: the empty dependency array; "The code inside the Effect does not use any props or state, so your dependency array is `[]` (empty)." Needed at the same moment.
  - *linter, lint error*: a tool that reads our code before it runs. The `exhaustive-deps` rule "Validates that dependency arrays for React hooks contain all necessary dependencies." Provided by `eslint-plugin-react-hooks`. Needed when the reader asks how React knows a value is missing.
  - *`Object.is`*: the comparison React uses for each dependency; MDN, it "determines whether two values are the same value." Name only.
  - Known: mount, Lesson 13. Props and state, Lessons 08 and 12. Snapshot, Lesson 15. Updater function, Lesson 16.
  - Helper: reactive value, name only, Lesson 35.
- **Side by side**:
  - "with no second argument" and "with `[]`": NOT the same thing. The first runs after every commit, so after every tick of the counter; the second runs after the first commit only.
  - "with `setCount(count + 1)`" and "with `setCount(c => c + 1)`" inside the Effect: NOT the same thing for the dependencies. The first reads `count`, so `count` must be in the array; the second reads no state, so `[]` is honest. The `useEffect` reference: "Now that you're passing `c => c + 1` instead of `count + 1`, your Effect no longer needs to depend on `count`."
- **Surprises**:
  - With `[]`, the counter goes up by two every second in development:
    1. The user clicks `Show counter`.
    2. React mounts `Counter` and runs the Effect; `Timer started` appears, and one timer starts.
    3. In development, React remounts the component once at once, and runs the Effect again; `Timer started` appears a second time, and a second timer starts.
    4. No code stopped the first timer, so two timers call `onTick` every second.
    5. The page shows `0`, `2`, `4`. The docs: "instead of incrementing once per second, it increments twice." The exact numbers on the page are `unconfirmed`, a lab check.
    6. In production, the Effect runs once and the counter goes up by one. Principle 3 explains the second run.
- **Where did that come from?**:
  - The `c` in `c => c + 1`: React passes the latest value of `count` to the updater function. Lesson 16.
- **Real beginner mistake** (the `useEffect` reference Pitfall on suppressing the linter):
  1. A developer writes `setCount(count + 1)` inside an Effect with `[]`.
  2. The linter reports that `count` is missing. The exact text for `count` is `unconfirmed`; the docs give the same shape for `isPlaying`.
  3. The developer turns the lint rule off for that line.
  4. The Effect keeps the `count` of the first render, `0`, Lesson 15, and sets it to `1` every second.
  5. The page stops at `1`. `unconfirmed`, a lab check.
  6. The docs: "By suppressing the linter, you "lie" to React about the values your Effect depends on." The docs' fix is the updater `c => c + 1`.
- **Interview depth**:
  - React compares each dependency with `Object.is`, and skips the Effect only if "*all* of the dependencies you specify have exactly the same values".
  - With `[count]` and `setCount(count + 1)`, the counter works, but "specifying `count` as a dependency always resets the interval." The `useEffect` reference.
  - The `ref` from `useRef` and the `set` functions from `useState` have a "stable identity", so leaving them out of the array is safe; "If the linter lets you omit a dependency without errors, it is safe to do."
  - Objects and functions created in the component body can make the Effect run more often than needed: Lesson 37.
  - "If your Effect's code doesn't use any reactive values, its dependency list should be empty (`[]`)."
- **React does**:

### Principle 3: The Cleanup Function Stops the Hidden Counter's Timer

- **Rule**: The function that the setup returns is the cleanup function; React calls it before the Effect runs again and one final time when the component unmounts, so it must stop or undo what the setup started, such as `clearInterval(intervalId)` for `setInterval`.
- **Move**: Everyday image, because cleanup is a new word and the light in a room shows it: whoever switched the light on switches it off.
- **Opening Essence**:
  - Smallest code: inside the Effect, `const intervalId = setInterval(onTick, 1000);` and `return () => clearInterval(intervalId);`.
  - Everyday image, the light in a room from the start of the lecture:
    1. Whoever switched the light on switches it off.
    2. React removes the `<h1>` it created from our JSX.
    3. Our setup started the timer, so our cleanup stops it.
  - The docs' pairs: ""connect" needs "disconnect", "subscribe" needs "unsubscribe", and "fetch" needs either "cancel" or "ignore"." For this page: `setInterval` needs `clearInterval`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Hiding the counter removes the number from the page, and it looks as if everything stopped. Without cleanup, the timer goes on.
- **Root Distinction**:
  - Junior: "When the component disappears, React removes everything that belongs to it."
  - Senior: React removes what it created from the JSX; anything the Effect started outside React keeps running until the cleanup function stops it.
- **Simplest version**:
  - The docs' Challenge solution: `const intervalId = setInterval(onTick, 1000);` and `return () => clearInterval(intervalId);` with `[]`.
- **Words to teach**:
  - *cleanup function*: the function the setup returns. The docs: "React will call your cleanup function each time before the Effect runs again, and one final time when the component unmounts (gets removed)." Provided by our code, called by React. Needed when the user clicks `Hide counter`.
  - *unmount*: the component "is removed from the screen"; here, when `show` becomes `false` and `{show && <Counter />}` gives nothing. Needed at the same moment.
  - *remount*: React mounts the component again. In development, React "remounts every component once immediately after its initial mount." Needed to explain Principle 2's second `Timer started`.
  - Known: `clearInterval`, interval ID, Lesson 30. State lost on removal, Lesson 25. Snapshot, Lesson 15.
  - Helper: none.
- **Side by side**:
  - "with `return () => clearInterval(intervalId)`" and "without a cleanup function": with one mount in production, the same page; NOT the same thing after `Hide counter`, and NOT the same thing in development. The first stops the timer each time React unmounts the counter; the second never stops it.
- **Surprises**:
  - In development, with the cleanup, the counter goes up by one, though the setup runs twice:
    1. The user clicks `Show counter`; React mounts `Counter` and runs the setup: `Timer started`.
    2. React remounts the counter once: it calls the cleanup, `Timer stopped`, and the first timer stops.
    3. React runs the setup again: `Timer started`, and one timer runs.
    4. The docs' Console order for the chat: `"✅ Connecting..."`, `"❌ Disconnected."`, `"✅ Connecting..."`. Our three lines follow the same order. `unconfirmed`, a lab check.
    5. The docs: "The user-visible behavior in both cases is the same: the counter increments once per second."
  - Without cleanup, the Console keeps printing `Tick` after the counter is hidden:
    1. The counter is shown, and a timer calls `onTick` every second.
    2. The user clicks `Hide counter`; React removes the `<h1>`.
    3. The timer still calls `onTick`; the Console still prints `Tick` every second. `unconfirmed`, a lab check.
    4. The user clicks `Show counter`; a new counter starts at `0`, Lesson 25, and a new timer starts.
    5. Now two timers print `Tick`. Each `Show counter` adds one more. `unconfirmed`, a lab check.
- **Where did that come from?**:
  - `intervalId` inside the cleanup: the cleanup function is created inside the setup, so it sees the `intervalId` of that same setup run. The docs: "Each Effect "captures" the `text` value from its corresponding render."
  - The returned function: React keeps what the setup returns and calls it later. Our code never calls the cleanup.
- **Real beginner mistake** (the docs' `ChatRoom` in Step 3):
  1. A `ChatRoom` connects to the chat server in an Effect with `[]` and no cleanup.
  2. The user opens the chat page; the component mounts and connects.
  3. The user goes to the Settings page; the component unmounts, and the connection stays open.
  4. The user clicks Back; the component mounts again and opens a second connection.
  5. The docs: "As the user navigates across the app, the connections would keep piling up."

- **Interview depth**:
  - The `useEffect` reference, the order React follows: setup when the component mounts; "After every commit of your component where the dependencies have changed", first cleanup "with the old props and state", then setup "with the new props and state"; cleanup "one final time" after unmount. The full sequence with a changing dependency is Lesson 35.

  - The cleanup should mirror the setup: the Troubleshooting entry, "Avoid: Cleanup logic without corresponding setup logic".
  - Other pairs from the docs: `window.addEventListener('scroll', handleScroll)` with `window.removeEventListener('scroll', handleScroll)`; `dialog.showModal()` with `dialog.close()`; `node.style.opacity = 1` with `node.style.opacity = 0`; a fetch with the `ignore` flag, Lesson 33.
  - Some Effects need no cleanup: the docs' map with `setZoomLevel(zoomLevel)`, because calling it twice with the same value "does not do anything".

### Principle 4: A Ref Guard Leaves the Timer Running

- **Rule**: In development, Strict Mode runs one extra setup and cleanup before the real setup to test the cleanup; the fix for a problem it shows is a cleanup function, never a ref that stops the Effect from running twice.
- **Move**: Steps for a surprise, because the ref guard makes the development page look right while the bug stays.
- **Opening Essence**:
  - Smallest code, two ways to see `Timer started` only once in development:
    1. A ref guard: `const startedRef = useRef(false);` and, inside the Effect with `[]`, `if (startedRef.current) return; startedRef.current = true;` before `setInterval`.
    2. A cleanup: `return () => clearInterval(intervalId);` from Principle 3. With it, `Timer started` appears twice, and the page is right.

- **Root Distinction**:
  - Junior: "React runs my Effect twice by mistake, so I must stop the second run."
  - Senior: the second run is a test React does on purpose in development; it shows that the Effect has no cleanup, a bug that users meet in production when they leave the page and come back.
- **Simplest version**:

- **Words to teach**:

- **Rule**: Work caused by a specific user action, such as buying, goes in the event handler of that action; an Effect is only for work caused by the component being on the screen.

## Interview Points

- An Effect is a side effect caused by rendering itself, not by a particular event; it synchronizes the component with an external system, something React does not control, such as a timer, a `window` listener, or a server connection.
- The code goes inside `useEffect`, called at the top level of the component; React runs the setup after the commit, never during rendering, because rendering must stay pure.
- The dependency array decides when the setup runs again: no array, after every commit; `[]`, only after mount; `[a, b]`, also when `a` or `b` changed, compared with `Object.is`.
- The dependencies are decided by the code inside the Effect; the `exhaustive-deps` lint rule checks them, and turning it off lies to React.
- The setup returns a cleanup function that stops or undoes what the setup started: `clearInterval` for `setInterval`, `disconnect` for `connect`, `removeEventListener` for `addEventListener`.
- React calls the cleanup before the Effect runs again and one final time when the component unmounts.
- In development, Strict Mode runs one extra setup and cleanup before the real setup to test the cleanup; the fix is a cleanup that makes setup, cleanup, setup look the same to the user as one setup, never a ref guard.
- Work caused by a specific click, such as buying, belongs in the event handler, not in an Effect.
- When there is no external system, there is usually no need for an Effect, Lesson 34; data fetching and its race conditions are Lesson 33; the full lifecycle as dependencies change is Lesson 35.
