# Q43 Principle Map (River Version v1): How a Button Deep in a Form Reads the Form's Pending State

- **Version**: River Version v1, skills `v10.6`
- **Bank row**: 43 of `questions/questions.md`
- **Topic tag**: `#use_form_status` | `❱❱ MORE`
- **Interview question**: How does a field nested deep in a form read the form's pending state?
- **Bank hook**: The submit button lives three components inside the form, and passing pending down through all of them is prop drilling. How does useFormStatus reach the enclosing form?

## Scope

This lesson covers:
- `useFormStatus()` from `'react-dom'`: a Hook with no parameters that returns one object with `pending`, `data`, `method`, and `action` (useFormStatus.md, Reference).
- `pending`: `true` while the parent `<form>` is submitting, otherwise `false`.
- The placement rule: the Hook reads only a parent `<form>`. Called in the component that renders the `<form>` tag itself, `pending` is never `true` (useFormStatus.md, Pitfall and Troubleshooting).
- Why the Hook exists: a button inside a form reads the form's status without a `pending` prop passed through every component in between (React 19 blog, "New hook: `useFormStatus`").
- `data`: the `FormData` the parent form is submitting, or `null` when there is no active submission (useFormStatus.md, Returns, and "Read the form data being submitted").
- `method` and `action`: named in Interview depth only.

## Start of the Lecture

- **Opening Essence of the chapter** (a way of working seen on a real screen, so it opens in plain words, then the smallest code):
  1. The screen: the comments under a photo post. One comment is already there, `Great shot!`. Under it sit a box with the placeholder `Add a comment...` and a `Post` button.
  2. The user types `Nice photo!` and clicks Post.
  3. For about one second the button reads `Posting...` and cannot be clicked.
  4. Then `Nice photo!` appears under `Great shot!`, the box is empty again, and the button reads `Post`.
  5. The question this screen raises for the developer: the button is its own component, inside another component, inside the form. How does the button know that the form is submitting right now?
  6. The answer in one line: the button asks the form above it, with `useFormStatus`, and reads `pending`.
- **Key idea to remember**: `useFormStatus` reads the status of the closest `<form>` above the component that calls it. The form must be a parent, never in the same component.
- **What is at stake for the user**:
  1. When `pending` never becomes `true`, the button keeps reading `Post` and stays clickable during the one-second wait.
  2. The user sees no sign that the click worked and clicks again.
  3. The comment is posted twice. That two clicks give two comments on this page: `unconfirmed`, checked in the lab.
- **Where readers usually go wrong**: they call `useFormStatus()` in the same component that renders `<form>`, next to the form tag. There `pending` stays `false` on every submit, with no error (useFormStatus.md, Pitfall: "`pending` will never be true").
- **The confusion to say out loud**:
  1. "With a `pending` prop passed down" and "with `useFormStatus`": for the user, "Yes, it is the exact same thing!" The same button reads `Posting...`. In the code, the components in the middle no longer carry a prop they never use.
  2. "With `useFormStatus` in the form's own component" and "with `useFormStatus` in the button component": the same line of code. "It may look the same, but it is NOT the same thing!" Only the second one has a parent form.
- **What the two share, then the one difference** (Back to the basics): both `useFormStatus` and context (Lesson 28) let a component deep in the tree read a value without props from every layer. The one difference: with context, our code writes a provider; with `useFormStatus`, the `<form>` tag plays that part. The blog: "`useFormStatus` reads the status of the parent `<form>` as if the form was a Context provider."
- **Theme**: a reusable submit button inside a form must show that the form is submitting, without a prop from every component above it.
- **Ways** (developers really choose between these for the same job):
  1. Pass `isPending` down as a prop from the component that owns the form (Lessons 8 and 42). The `useActionState` page does this: `<Total quantity={count} isPending={isPending}/>`. Fits when the button is one level below and the form owner already has `isPending`.
  2. Make a context by hand and provide the pending flag (Lesson 28). The blog: "This can be done via Context, but to make the common case easier, we've added a new hook `useFormStatus`." Fits status that is not a form submission.
  3. `useFormStatus` in the button component. Fits a button or field rendered inside a `<form>`, at any depth, and a design component reused in many forms. The blog: "In design systems, it's common to write design components that need access to information about the `<form>` they're in, without drilling props down to the component."
- **Example page**: the comments under a photo post, described above.
  - Why chosen:
    1. Everyone has posted a comment. A list, one box, and one button need no explanation.
    2. A button that turns into `Posting...` and cannot be clicked twice is where developers really use `useFormStatus`: a submit button component inside a form.
    3. The broken case is big on the page: the button that never changes, and a comment posted twice.
    4. Actions are typing and one click.
    5. The page needs little outside code: `useActionState` from Lesson 42 keeps the list, and a given `src/api.js` waits one second.
  - Pages considered and rejected:
    1. The chat message box with a Send button: Lesson 41 built it. A new page keeps this lesson's question in front.
    2. The newsletter sign-up box: Lesson 42 built it, and its point was the returned message.
    3. The docs' "Request a Username" form (useFormStatus.md): a username request is a screen few readers have used.
    4. A log-in form: two boxes and a password before the idea starts, and after log-in the page usually moves to another screen, so the button is gone.
    5. One `SubmitButton` reused in two forms on one screen: shows reuse, but two forms are more parts than the idea needs. Kept for Interview depth.

## Principles

### Principle 1: useFormStatus Gives the Post Button pending

- **Rule**: a component rendered inside a `<form>` calls `useFormStatus()` from `'react-dom'` and reads `pending`, which is `true` while that form is submitting and `false` otherwise.
- **Move**: Smallest code first, because the Hook is a new idea and must be seen in a few lines before the comment files.
- **Opening Essence**:
  - The smallest code, the docs' shape: a `Submit` component with `const { pending } = useFormStatus();` and `<button disabled={pending}>`, rendered between `<form action={action}>` and `</form>`.
  - The key idea: the button does not receive `pending` from anyone; it asks the form it sits in.
  - The place where readers go wrong: they import it from `'react'`, like every Hook so far; it comes from `'react-dom'`.
- **Root Distinction**:
  - junior: "The button needs a prop from the form to know it is submitting."
  - senior: a component inside a form can ask the form for its status itself; the form needs to pass nothing.
- **Simplest version**:

```jsx
import { useFormStatus } from 'react-dom';

function Submit() {
  const { pending } = useFormStatus();
  return <button type="submit" disabled={pending}>Submit</button>;
}

<form action={action}>
  <Submit />
</form>
```

- **Words to teach**:
  - `useFormStatus`: "a Hook that gives you status information of the last form submission." It takes no parameters. Provided by React DOM, imported from `'react-dom'`. Needed when the reader writes the first line of `PostButton`.
  - `pending`: "A boolean. If `true`, this means the parent `<form>` is pending submission. Otherwise, `false`." Provided by React DOM, inside the object the Hook returns. Needed when the user clicks Post and the button must change.
  - the status object: the one object the Hook returns, with `pending`, `data`, `method`, and `action`. Needed to explain the curly braces in `const { pending } = useFormStatus();`.
  - Form Hooks in `react-dom`: the docs' "Hooks that are only supported for web applications (which run in the browser DOM environment)". Needed when the reader asks why the import line names `'react-dom'`.
  - Already taught: Hook (12), top level (38), object destructuring in curly braces (8), `disabled` (42), ternary (10), `<button type="submit">` (11), `<form action>` (41), `react-dom` (7).
  - Helper words: none.
- **Side by side**: none.
- **Surprises**:
  1. The user types `Nice photo!` and clicks Post.
  2. Our code never sets `pending`, and no prop reaches `PostButton`.
  3. Still, the button reads `Posting...` and cannot be clicked for one second.
  4. The steps, from the docs' Returns: while the parent `<form>` "is pending submission", `pending` is `true`; otherwise it is `false`. That `PostButton` renders again at each change of `pending`: `unconfirmed`, checked in the lab.
- **Where did that come from?**:
  - `useFormStatus`: imported from `'react-dom'`, the package of Lesson 7, not from `'react'`.
  - `pending`: a property of the object `useFormStatus()` returns; the curly braces take it out by name (Lesson 8).
  - The value of `pending`: supplied by React DOM from the parent `<form>`; our code never writes it.
- **Real beginner mistake**:
  1. A developer writes `import { useFormStatus } from 'react';`, next to `useState` and `useActionState`.
  2. The page loads.
  3. The import fails, because `'react'` has no export with that name. What the page shows: `unconfirmed`, checked in the lab.
  4. The exact Console or Vite message: `unconfirmed`, checked in the lab.
  5. The fix: `import { useFormStatus } from 'react-dom';`.
- **Interview depth**:
  - It is in `react-dom`, not `react`, because Form Hooks are "only supported for web applications" and "not supported in non-browser environments like iOS, Android, or Windows applications" (react-dom hooks index).
  - It takes no parameters; there is no way to name the form it reads. The form is always the parent form.
  - It works with any function action on the form: a plain Action (Lesson 41) or the action from `useActionState` (Lesson 42).
  - It is a Hook: top level of the component only, not in a condition or a loop (Lesson 38).
- **React does**:
  - Page before the click: the comment `Great shot!`, the box `Add a comment...`, and the button `Post`.
  - Page during the one-second wait: the button reads `Posting...` and cannot be clicked.
  - Page after the wait: `Nice photo!` under `Great shot!`, the box empty, the button `Post`. That the box is empty when the button returns to `Post`: `unconfirmed`, checked in the lab.
  - Elements panel during the wait: the `<button>` node carries the `disabled` attribute; exact serialization `unconfirmed`.
  - Console on a normal submit: nothing; `unconfirmed`, checked in the lab.
- **Example step**: the full page appears. `src/App.jsx` renders `<CommentSection />`; `src/CommentSection.jsx` and `src/api.js` are the given files above; `src/CommentFooter.jsx` returns `<div><PostButton /></div>`; `src/PostButton.jsx` calls `useFormStatus()` and returns `<button type="submit" disabled={pending}>{pending ? 'Posting...' : 'Post'}</button>`.
- **Code names**: `src/App.jsx`, `src/CommentSection.jsx`, `src/CommentFooter.jsx`, `src/PostButton.jsx`, `src/api.js`, `CommentSection`, `CommentFooter`, `PostButton`, `useFormStatus`, `'react-dom'`, `'react'`, `pending`, `disabled={pending}`, `type="submit"`, `'Posting...'`, `'Post'`, `Great shot!`, `Nice photo!`, `Add a comment...`, `saveComment`, `addComment`, `postAction`, `comments`

### Principle 2: pending Stays false Next to the form Tag

- **Rule**: `useFormStatus` reads only a parent `<form>`; called in the component that renders the `<form>` tag, it does not see that form, and `pending` stays `false`.
- **Move**: Side by side, because the same line of code sits in two places and only one place works.
- **Opening Essence**:
  - The smallest code, the docs' Pitfall: `function Form() { const { pending } = useFormStatus(); return <form action={submit}></form>; }` beside `function Submit() { const { pending } = useFormStatus(); return <button disabled={pending}>...</button>; }` rendered inside `<form action={submit}>`.
  - The confusion to say out loud: "It may look the same, but it is NOT the same thing!" The Hook line is identical. In `Form`, the form is rendered by the same component, so it is not a parent. In `Submit`, the form is above, so it is a parent.
  - What the two share, then the one difference: both components call the Hook while a form is on the page; the one difference is whether the `<form>` tag is above the calling component or inside its own return.
- **Root Distinction**:
  - junior: "The `<form>` is right there in my component, so the Hook can see it."
  - senior: the Hook looks only above the component that calls it; the form a component returns is below it.
- **Simplest version**:

```jsx
function Form() {
  const { pending } = useFormStatus();
  return <form action={submit}></form>;
}

function Submit() {
  const { pending } = useFormStatus();
  return <button disabled={pending}>Submit</button>;
}
```

- **Words to teach**:
  - parent `<form>`: the docs' words for the form above the calling component. "The `useFormStatus` Hook must be called from a component that is rendered inside a `<form>`." Needed when the reader moves the Hook line out of `CommentSection`.
  - Already taught: parent and child in the tree (6), the closest provider above, and a provider in the same component does not count (28).
  - Helper words: none.
- **Side by side**:
  - "with `useFormStatus` in `CommentSection`", the component that renders `<form>`: `pending` is always `false`.
  - "with `useFormStatus` in `PostButton`", rendered inside `<form>`: `pending` is `true` while the form submits.
  - Verdict: NOT the same thing.
  - Reason: `useFormStatus` "will only return status information for a parent `<form>`. It will not return status information for any `<form>` rendered in that same component or children components."
- **Surprises**:
  1. The developer calls `useFormStatus()` at the top of `CommentSection` and writes `disabled={pending}` and `{pending ? 'Posting...' : 'Post'}` on a button in the same component.
  2. The user types `Nice photo!` and clicks Post.
  3. The button keeps reading `Post` and stays clickable for the whole second.
  4. The Console shows no error; `unconfirmed`, checked in the lab. The docs give no error message, only: "`pending` will never be true".
  5. The user clicks again during the wait, and `Nice photo!` is posted twice: `unconfirmed`, checked in the lab.
- **Where did that come from?**:
  - The `false` in `pending`: the docs' Troubleshooting. "If the component that calls `useFormStatus` is not nested in a `<form>`, `status.pending` will always return `false`." `CommentSection` renders the form, so it is not nested in it.
- **Real beginner mistake** (useFormStatus.md, Pitfall and Troubleshooting "`status.pending` is never `true`"):
  1. A developer learns `useFormStatus` and adds it to the component that already has the form.
  2. The button never changes during a submit.
  3. Nothing in the Console says why.
  4. The developer adds a `useState` flag by hand, set before and after the request.
  5. The fix from the docs: "call `useFormStatus` from inside a component that is located inside `<form>`", here a separate `PostButton`.
- **Interview depth**:
  - Outside any form, the Hook returns `pending` as `false`, `data` as `null`, and `action` as `null` (useFormStatus.md, Returns and Troubleshooting).
  - It also ignores a `<form>` rendered by a child component of the caller; only a form above counts.
  - The same rule holds for context: a provider in the same component does not count (Lesson 28).
  - The form owner that needs the pending flag for itself uses `isPending` from `useActionState` (Lesson 42), not `useFormStatus`.
- **React does**:
  - Page during the wait, mistake version: the button reads `Post` and can be clicked; `unconfirmed` for the exact screen, checked in the lab.
  - Console, mistake version: nothing; `unconfirmed`.
  - Elements panel, mistake version: the `<button>` node has no `disabled` attribute during the wait; `unconfirmed`.
- **Example step**: shown as a broken version of `src/CommentSection.jsx` only: the Hook line at its top and the button written inline in its `<form>`. The page then returns to the Principle 1 files: the button stays in `src/PostButton.jsx`.
- **Code names**: `src/CommentSection.jsx`, `CommentSection`, `PostButton`, `Form`, `Submit`, `useFormStatus`, `pending`, `false`, `<form action={postAction}>`, `status.pending`

### Principle 3: CommentFooter Passes No pending Prop

- **Rule**: `useFormStatus` reaches the parent form through any number of components in between, so the components in the middle pass no `pending` prop.
- **Move**: Side by side, because the drilled version and the Hook version give the same screen, and the reader must see that only the middle components change.
- **Opening Essence**:
  - The smallest code, three components each way:
    1. With a `pending` prop: `CommentSection` takes `isPending` from `useActionState` and renders `<CommentFooter pending={isPending} />`; `CommentFooter({ pending })` renders `<PostButton pending={pending} />`; `PostButton({ pending })` uses it.
    2. With `useFormStatus`: `CommentSection` renders `<CommentFooter />`; `CommentFooter()` renders `<PostButton />`; `PostButton()` calls `useFormStatus()`.
  - The confusion to say out loud: "Yes, it is the exact same thing!" for the user. The same button reads `Posting...` for the same second.
  - What the two share, then the one difference: in both, the form's submission decides the button. The one difference: with the prop, `CommentFooter` receives `pending` and never uses it; with the Hook, `CommentFooter` does not mention it.
- **Root Distinction**:
  - junior: "Every component between the form and the button has to hand `pending` on."
  - senior: the form's status is read where it is needed; the components in the middle only lay out the page.
- **Simplest version**:

```jsx
function CommentFooter({ pending }) {
  return <PostButton pending={pending} />;
}

function CommentFooter() {
  return <PostButton />;
}
```

- **Words to teach**:
  - prop drilling, in this lesson's case: the docs' words, "passing props can become verbose and inconvenient when you need to pass some prop deeply through the tree". Already taught (24, 28); here it is the `pending` prop through `CommentFooter`.
  - design component: the blog's words for a button reused across many forms. "In design systems, it's common to write design components that need access to information about the `<form>` they're in, without drilling props down to the component." Needed when the reader asks why the button is its own file.
  - Already taught: props (8), context and the closest provider above (28), `useActionState` and `isPending` (42).
  - Helper words: none.
- **Side by side**:
  - "with a `pending` prop": `isPending` from `useActionState` in `CommentSection`, passed through `CommentFooter` to `PostButton`. The docs' own shape: `<Total quantity={count} isPending={isPending}/>` on the `useActionState` page.
  - "with `useFormStatus`": no prop; `PostButton` calls the Hook.
  - Verdict: the exact same thing on the screen.
  - Reason: both are `true` while the comment is saved. `isPending` "tells you if any dispatched Actions for this Hook are pending"; `pending` says "the parent `<form>` is pending submission". Whether the two turn back to `false` in the same render: `unconfirmed`, checked in the lab.
- **Surprises**:
  1. The developer moves `PostButton` from `CommentFooter` into another row of the same form, or adds one more component around it.
  2. With the prop version, every new component in between needs the `pending` prop again, or the button stops changing.
  3. With `useFormStatus`, nothing else changes, because the button still sits inside the same `<form>`.
  4. That the Hook reads the form through any number of components: the docs say only "rendered inside a `<form>`" and "a component that is a child of a `<form>` element". Checked in the lab with two components in the middle.
- **Where did that come from?**:
  - The way the Hook reaches the form: the docs give only the blog's sentence, "`useFormStatus` reads the status of the parent `<form>` as if the form was a Context provider." The syllabus card's claim that React adds an internal context provider to every `<form>` is not in the corpus. See Open Issues.
- **Real beginner mistake**:
  1. A team has one `SubmitButton` component used in many forms.
  2. Each form passes `pending` down to it through its own layout components.
  3. A developer adds a new form and wraps the button in one more layout component.
  4. The new layout component does not pass `pending` on.
  5. In that form, the button never shows that the form is submitting.
  6. The fix: the button calls `useFormStatus()`, and no form passes `pending` at all.
- **Interview depth**:
  - The blog names the motive: design components that read the `<form>` they are in "without drilling props down to the component", and "This can be done via Context, but to make the common case easier, we've added a new hook `useFormStatus`."
  - `useFormStatus` reads a form's submission only; any other shared value still needs props or context (Lesson 28).
  - The same `PostButton` placed in two forms reads each its own parent form. The docs' caveat: status information "for a parent `<form>`". Checked in the lab: `unconfirmed`.
  - The docs' alternative to context also applies: passing JSX as `children` cuts the layers in the middle (Lesson 28).
- **React does**:
  - Page, both versions: the same `Posting...` during the wait and the same `Post` after it.
  - Console, both versions: nothing; `unconfirmed`.
  - Elements panel: both versions give the same `<button>` node; `unconfirmed`, checked in the lab.
- **Example step**: the drilled version is shown in `src/CommentSection.jsx` (`const [comments, postAction, isPending] = ...` and `<CommentFooter pending={isPending} />`), `src/CommentFooter.jsx`, and `src/PostButton.jsx`. Then the page returns to the Principle 1 files, which are the Hook version.

### Principle 4: data Shows the Comment Being Posted

- **Rule**: `data` holds the `FormData` the parent form is submitting right now, and is `null` when there is no active submission, so a component inside the form can show what the user just sent.
- **Move**: Smallest code first, because `data` is one more property of the same object, and a few lines show it.
- **Opening Essence**:
  - The smallest code, the docs' shape: `const { pending, data } = useFormStatus();` and `<p>{data ? `Requesting ${data?.get("username")}...` : ''}</p>` (useFormStatus.md, "Read the form data being submitted").
  - The key idea: `data` is the same kind of `FormData` as the `formData` the action receives (Lesson 40), read with `.get('comment')`.
  - The confusion to say out loud: "Yes, it is the exact same thing!" `data.get('comment')` in `CommentFooter` and `formData.get('comment')` in `addComment` read the same box. That they are the same object: `unconfirmed`; the docs say both contain the data of the submitted form.
  - Where readers go wrong: they read `data.get(...)` with no check, and before the first submit `data` is `null`.
- **Root Distinction**:
  - junior: "Only the action can see what the user typed."
  - senior: while the form submits, any component inside it can read the submitted data with `useFormStatus`.
- **Simplest version**:

```jsx
const { data } = useFormStatus();

{data && <p>Posting "{data.get('comment')}"...</p>}
```

- **Words to teach**:
  - `data`: "An object implementing the `FormData interface` that contains the data the parent `<form>` is submitting. If there is no active submission or no parent `<form>`, it will be `null`." Provided by React DOM. Needed when the line under the box first appears.
  - Already taught: `FormData` and `.get()` (40), `&&` (10), `null`.
  - Helper words: none.
- **Side by side**:
  - "with `data.get('comment')` in `CommentFooter`": shows the text during the submission only.
  - "with `formData.get('comment')` in `addComment`": reads the text inside the action.
  - Verdict: the exact same text, read in two places.
  - Reason: both read the form data of the same submission.
- **Surprises**:
  1. Before the first submit, `data` is `null`, so no line shows.
  2. The user types `Nice photo!` and clicks Post.
  3. A line `Posting "Nice photo!"...` appears under the box while the button reads `Posting...`.
  4. When the submission ends, `data` is `null` again, and the line disappears.
  5. Whether the box is already empty while the line still shows the text: `unconfirmed`, checked in the lab.
- **Where did that come from?**:
  - `data`: a property of the object `useFormStatus()` returns; React DOM fills it from the parent form's current submission.
  - `'comment'`: the `name` on the `<input>` in `CommentSection` (Lesson 40).
- **Real beginner mistake**:
  1. A developer writes `<p>Posting "{data.get('comment')}"...</p>` with no check.
  2. The page renders for the first time, with no submission.
  3. `data` is `null`, so `data.get` throws.
  4. The exact `TypeError` text and what the page shows: `unconfirmed`, checked in the lab.
  5. The fix: show the line only when `data` is there, `{data && ...}`, or the docs' `data ? ... : ''`.
- **Interview depth**:
  - `method`: "A string value of either `'get'` or `'post'`." With a function passed to `action`, form.md says "the HTTP method will be POST regardless of value of the `method` prop". Whether `method` then reads `'post'`: `unconfirmed`.
  - `action`: "A reference to the function passed to the `action` prop on the parent `<form>`." It is `null` with a URL action or no `action` prop.
  - Showing the new comment in the list before the server answers is `useOptimistic` (Lesson 44); `data` only reports what is being sent.
  - A `formAction` on a second button overrides the form's `action` (form.md); what `status.action` then holds: `unconfirmed`.
- **React does**:
  - Page before any submit: no line under the box.
  - Page during the wait: `Posting "Nice photo!"...` under the box, and the button `Posting...`.
  - Page after the wait: the line is gone; `Nice photo!` is in the list.
  - Elements panel during the wait: a `<p>` node inside the `<form>`, after the box; it is gone after the wait.
  - Console: nothing; `unconfirmed`. Console for the mistake: a `TypeError`, exact text `unconfirmed`.
- **Example step**: `src/CommentFooter.jsx` calls `const { data } = useFormStatus();` and renders `{data && <p>Posting "{data.get('comment')}"...</p>}` above `<PostButton />`. `PostButton`, `CommentSection`, and `api.js` are unchanged. This is the finished page.
- **Code names**: `src/CommentFooter.jsx`, `CommentFooter`, `useFormStatus`, `data`, `data.get('comment')`, `'comment'`, `null`, `Posting "Nice photo!"...`, `formData.get('comment')`, `addComment`, `method`, `action`, `'get'`, `'post'`

## Interview Points

- `useFormStatus()` from `'react-dom'` takes no parameters and returns `{ pending, data, method, action }` for the parent `<form>`.
- `pending` is `true` while the parent form is submitting; `data` is the `FormData` being submitted, or `null`.
- It must be called in a component rendered inside the `<form>`; in the component that renders the `<form>` tag, `pending` is never `true`, with no error.
- It replaces passing a pending flag as a prop through every component between the form and the button.
- The blog: it "reads the status of the parent `<form>` as if the form was a Context provider", made for design components reused across forms.
- The form owner reads its own pending flag with `isPending` from `useActionState`; components inside the form read the form's with `useFormStatus`.
- Outside any form, `pending` is `false` and `data` and `action` are `null`.
- It is a Form Hook of `react-dom`, supported only in the browser.
