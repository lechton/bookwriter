# Q26 Principle Map (River Version v1): Thinking in React, the Five Steps from a Mockup to a Working Page

- **Version**: River Version (`v1`), written under `skills/v10.6`
- **Bank Row**: `questions/questions.md` row 26

- **Interview Question**: *What is the step-by-step process for building a UI in React?*

## Scope

Covered here:
- The five steps of React's "Thinking in React" page, in their order: Step 1, break the UI into a component hierarchy; Step 2, build a static version in React; Step 3, find the minimal but complete representation of UI state; Step 4, identify where your state should live; Step 5, add inverse data flow.
- Why the order matters: what each step needs from the step before, and what the page shows after each step.
- Step 1: drawing boxes on the mockup, naming each box, and nesting the names into a hierarchy; the data model often has the same shape as the UI.
- Step 2: a static version uses props only and no state; one-way data flow; top down against bottom up.
- Step 3: the four values of the page and the three questions, applied once. The test itself is Lesson 22.
- Step 4: the three steps for finding the owner, applied once. Lifting state up is Lesson 24.
- Step 5: passing the setters down and calling them from `onChange`. Callback props are Lesson 23.
- The page between Step 4 and Step 5: the values show, but the search box and the tick box refuse the user's input.

Left to other lessons:

- `import`, `export default`, one component per file: Lesson 05. Used.

## Start of the Lecture

**Opening Essence of the chapter**:
- No short code shows this idea with a surprise. The idea is the order of a way of working, so it opens in plain words before any code, as Examples 3 and 8 of [Opening Essence](../../skills/v10.6/opening-essence/SKILL.md) do.
- Start from the lesson's question: a designer hands over a mockup of a page with a search box, a tick box, and a list of drinks. Where does the developer start?
- Confusion to say out loud: *"Yes, it is the exact same thing!"* The five steps bring no new tool. Each step is a tool the reader already has: components and the tree, Lessons 04 to 06; props, Lesson 08; the test for what is state, Lesson 22; the owner of state, Lesson 24; a function passed down, Lesson 23. Thinking in React is the order in which to use them.
- Everyday image, once, only in the opening: building a house. The plan comes first, then the walls, then the decision of which lamps must switch on and off, then where each switch goes, and only then the wires from each switch. Nobody puts wires in before the walls stand. After the opening, the lecture uses React's words only: "wires", "walls", and "switches" never stand for code. See Open Issues.
- The docs' own sentence for why the order helps: "Building a static version requires a lot of typing and no thinking, but adding interactivity requires a lot of thinking and not a lot of typing."
- The docs' Intro in three moves: break the UI into components; describe the different visual states for each component; connect the components so that the data flows through them.
- Key idea: build what does not change first, then add the few values that do change, in the component that owns them, and only then inverse data flow, from the boxes the user types in up to that component.
- What is at stake, from the syllabus card: a developer who starts with `useState` calls and handlers at random ends up with state stored twice and props passed in a tangle. On the page: the user ticks "Only show drinks in stock" and a sold-out drink stays on the list, or the user types in the search box and the list does not move.
- Where readers usually go wrong: they start from `useState` and handlers; they store the filtered list as state; they put the search text inside the search box component, where the list cannot read it; they expect `value={filterText}` to update `filterText` by itself.

**Theme**: a drinks menu page. A search box and a tick box sit in one component, the list of drinks sits in a sibling, and the list must follow what the user types and ticks.

**Ways** (developers really choose between these for Step 2, from the docs):
1. Top down: start with the component at the top of the hierarchy, here `MenuPage`. The docs: "In simpler examples, it's usually easier to go top-down."
2. Bottom up: start with the components at the bottom, here `DrinkRow`. The docs: "on larger projects, it's easier to go bottom-up."
- The lesson uses top down, because the page is small. Named in Principle 2.

**Example page chosen for this lesson**: the drinks menu of a cafe.
- Parts of the final page: `<h1>Drinks</h1>`; a search box with the placeholder `Search...`; a tick box with the label `Only show drinks in stock`; a list of drinks, each row with the name and the price, and `Sold out` after a drink that is not in stock.
- Data in `App.jsx`, an array `DRINKS` of five objects with `id`, `name`, `price`, `inStock`:
  1. `{ id: 1, name: 'Coffee', price: '$3', inStock: true }`
  2. `{ id: 2, name: 'Tea', price: '$2', inStock: true }`
  3. `{ id: 3, name: 'Hot chocolate', price: '$4', inStock: false }`
  4. `{ id: 4, name: 'Lemonade', price: '$3', inStock: true }`
  5. `{ id: 5, name: 'Iced tea', price: '$3', inStock: false }`
- What the user does on the final page: types `tea` and sees `Tea` and `Iced tea`; ticks the box and sees only `Tea`, because `Iced tea` is sold out.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx`, `src/components/MenuPage.jsx`, `src/components/SearchBar.jsx`, `src/components/DrinkList.jsx`, `src/components/DrinkRow.jsx`.
- Hierarchy: `App` renders `MenuPage`; `MenuPage` renders `SearchBar` and `DrinkList`; `DrinkList` renders one `DrinkRow` for each drink.
- State at the end, in `MenuPage`: `filterText`, starting `''`; `inStockOnly`, starting `false`.
- Names follow the docs' own code: `filterText`, `setFilterText`, `inStockOnly`, `setInStockOnly`, `onFilterTextChange`, `onInStockOnlyChange`, `SearchBar`. The reader meets the same names on react.dev and in interviews.

**Why this page**:
1. A menu with a search box and a tick box is on every shop and cafe site. Nothing needs explaining.
2. It needs this lesson's idea: two values change, they are typed in one component and read by a sibling, so all five steps have real work to do.
3. Each step changes what the page shows, so the reader can see where the page stands after every step: all drinks and a search box that changes nothing after Step 2, frozen boxes after Step 4, a working filter after Step 5.
4. The two filters work together on one word: `tea` finds two drinks, and the tick box removes one. The result is big on the page.
5. Helper code is small and almost all known: `.map` with `key`, Lesson 18; `filter`, Lesson 19; `includes`, Lesson 21; `&&`, Lesson 10; `checked` and `e.target.checked`, Lesson 20. The only new helper is `toLowerCase`, so that `tea` also finds `Tea`.
6. It keeps the shape of the docs' own example, `FilterableProductTable`, so the reader can read the docs page next to the lecture.

## Principles

### Principle 1: Boxes on the Mockup Become Four Components

- **Rule**: Before writing any code, draw a box around every part of the mockup, name each box as a component, and nest the names the way the boxes nest; one component should do one thing.
- **Move**: Everyday image for "component hierarchy", because the reader already knows the tree from Lesson 06 and only needs to see that boxes drawn inside boxes give the same tree. Then a `tree` figure of the four names.
- **Opening Essence**:
  - The naked idea, with no project files: the mockup with boxes drawn on it, and the same boxes written as a nested list of names.
  - Everyday image: drawing with a pen on a printed page. The docs: "Start by drawing boxes around every component and subcomponent in the mockup and naming them."
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* The component hierarchy of the docs is the UI tree of Lesson 06. A box inside another box on the mockup is a child inside a parent in the tree.
  - Key idea: the boxes come from the mockup and from the data, not from the code; the docs say the JSON data and the UI "often have the same information architecture", "the same shape".
- **Root Distinction**:
  - Junior: "I will see which components I need once I start writing the code."
  - Senior: the components are decided on the mockup, before any code, and each one matches one piece of the data.
- **Simplest version**:
  - The mockup with four boxes: the whole menu, the search part, the list, one row.
  - The hierarchy as a nested list: `MenuPage`, with `SearchBar` and `DrinkList` inside it, and `DrinkRow` inside `DrinkList`.
- **Words to teach**:
  - *mockup*: the drawing of the finished page that a designer gives the developer. Provided by the designer, in a design tool. Needed at the first line of the principle.
  - *component hierarchy*: the docs' name for the nested list of components drawn from the mockup. "Components that appear within another component in the mockup should appear as a child in the hierarchy." Needed when the four boxes become four names.
  - *separation of concerns*: the docs' technique for deciding where one component ends: "a component should ideally only be concerned with one thing. If it ends up growing, it should be decomposed into smaller subcomponents." A computer science term the docs link to. Needed when the reader asks why the row is its own box.
  - *data model*: the shape of the data the page shows, here the array `DRINKS`. The docs: "Separate your UI into components, where each component matches one piece of your data model." Needed when each drink object matches one `DrinkRow`.
  - Known: UI tree, parent, child, sibling, Lesson 06. Components and `PascalCase`, Lesson 04.
  - Helper: none.
- **Side by side**:
  - "with the list title inside `DrinkList`" and "with the list title as its own component": the docs say this is "a matter of preference, and you could go either way". Both give the same page. The docs' example: the table header is part of `ProductTable`, and moves into its own `ProductTableHeader` "if this header grows to be complex (e.g., if you add sorting)". The verdict: the exact same page; the choice is about how big the part will grow.
  - The docs' three ways to split a design: Programming, the same way you decide on a new function or object; CSS, what you would make class selectors for, "However, components are a bit less granular"; Design, how you would organize the design's layers. Not a pair; a list of three starting points.
- **Surprises**: none.
- **Where did that come from?**:
  - The names `MenuPage`, `SearchBar`, `DrinkList`, `DrinkRow`: chosen by the developer, or by the designer. The docs: "If you work with a designer, they may have already named these components in their design tool. Ask them!"
  - `App` is not a box on the mockup: it is the root component that `main.jsx` renders, Lesson 07. It holds the data and renders `MenuPage`.
- **Real beginner mistake** (the syllabus card's naive way, "mixing state, network calls, and UI in a single unstructured component file"):
  1. A developer gets the mockup and opens `App.jsx`.
  2. The developer writes the search box, the tick box, and the list of drinks in one component.
  3. The component grows with every new part of the page.
  4. The list cannot be used on another page without the search box.
  5. Splitting it later means moving state and handlers between new files.
- **Interview depth**:
  - The docs' five components of their example: `FilterableProductTable` "contains the entire app", `SearchBar` "receives the user input", `ProductTable` "displays and filters the list according to the user input", `ProductCategoryRow` "displays a heading for each category", `ProductRow` "displays a row for each product".
  - Why the data and the UI have the same shape: "UI and data models often have the same information architecture". Each drink object is one row.
  - When to split a component: when it is concerned with more than one thing, or when a part grows, such as a header that gets sorting.
- **React does**:
  - Page: nothing yet. This step writes no code.
  - Console: nothing.
  - Elements panel: nothing.
- **Example step**:
  - No file changes. A browser preview of the mockup: `<h1>Drinks</h1>`, the search box, the tick box, and five rows, with four boxes drawn on it.
  - A `tree` figure: `MenuPage` with `SearchBar` and `DrinkList`, and `DrinkRow` under `DrinkList`.
- **Code names**: `MenuPage`, `SearchBar`, `DrinkList`, `DrinkRow`, `App`, `DRINKS`, `Drinks`, `Search...`, `Only show drinks in stock`, `Sold out`, `FilterableProductTable`, `ProductTable`, `ProductCategoryRow`, `ProductRow`, `ProductTableHeader`

### Principle 2: The Static Menu Ignores the Typed Search

- **Rule**: Build the whole page from the data with components and props only, and no state; the data enters at the top component as a prop and flows down to the rows.
- **Move**: Steps for a surprise, because the user can type `tea` into the search box and every drink stays on the list. Side by side for top down and bottom up.
- **Opening Essence**:
  - Smallest code: `function DrinkRow({ drink }) { return <li>{drink.name} {drink.price}</li>; }` and `<DrinkRow drink={{ name: 'Tea', price: '$2' }} />`. Only props, no `useState`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* The static version and the finished page look the same in the browser, and the search box takes letters in both. Only the finished page changes the list.
  - Key idea, from the docs: "It's often easier to build the static version first and add interactivity later." And: "Building a static version requires a lot of typing and no thinking, but adding interactivity requires a lot of thinking and not a lot of typing."
  - What is at stake: when state and handlers go in while the components are still being typed, the hard thinking and the long typing happen at the same time.
- **Root Distinction**:
  - Junior: "The page has a search box, so the search box needs state from the start."
  - Senior: first the page shows the data with props only; state is "reserved only for interactivity, that is, data that changes over time", and it comes in Step 3.
- **Simplest version**:
  - `App` passes `drinks={DRINKS}` to `MenuPage`.
  - `MenuPage` returns `SearchBar` and `<DrinkList drinks={drinks} />`.
  - `DrinkList` returns `<ul>` with `drinks.map(drink => <DrinkRow key={drink.id} drink={drink} />)`.
  - `SearchBar` returns `<input type="text" placeholder="Search..." />` and a `<label>` with `<input type="checkbox" />` and `Only show drinks in stock`. No `value`, no `checked`, no `onChange`.
- **Words to teach**:
  - *static version*: the docs' name for the page built from the data with components and props, "without adding any interactivity... yet!" Needed at the first file of the project.
  - *interactivity*: what the user can change on the page. The docs: state "is reserved only for interactivity, that is, data that changes over time". Needed when the reader asks why no `useState` yet.
  - *top down, bottom up*: the two orders in which to write the components of the static version. Top down starts with `MenuPage`; bottom up starts with `DrinkRow`. Needed when the reader asks which file to write first.
  - Known: props, Lesson 08. One-way data flow, Lessons 06 and 23. `.map` and `key`, Lesson 18. A tick box with no `checked` prop keeps its own tick, Lesson 18. `&&`, Lesson 10.
  - Helper: none.
- **Side by side**:
  - "top down" and "bottom up": NOT the same order, the exact same result. Both end with the same four components. The docs: top down is usually easier "in simpler examples", bottom up "on larger projects".
  - "the static version" and "the finished page": NOT the same thing. They look the same in the browser before the user types; only the finished page changes the list.
- **Surprises**:
  - The user types `tea`, and the list still shows all five drinks:
    1. React renders `App`, `MenuPage`, `SearchBar`, `DrinkList`, and five `DrinkRow` components.
    2. The search box has no `value` prop, so the browser keeps the typed text inside the input's DOM node.
    3. The user types `tea`. The box shows `tea`.
    4. No `onChange` runs our code, and no state changes, so React does not render `MenuPage` again.
    5. `DrinkList` still has the same `drinks` array, so the page still shows `Coffee`, `Tea`, `Hot chocolate`, `Lemonade`, `Iced tea`.
  - The same for the tick box: the user ticks it, the tick shows, and `Hot chocolate` and `Iced tea` stay on the list.
- **Where did that come from?**:
  - `drinks` in `MenuPage` and `DrinkList`: the prop `drinks={DRINKS}` written on the tag in `App`, then `drinks={drinks}` on the tag in `MenuPage`. React packs each tag's attributes into the props object, Lesson 08.
  - `drink` in `DrinkRow`: the prop `drink={drink}` written inside `.map` in `DrinkList`, where `drink` is the parameter of the arrow function, one array item at a time.
  - `DRINKS` in `App.jsx`: the data written by hand in place of the docs' JSON API.
- **Real beginner mistake** (the docs' Pitfall: "At this point, you should not be using any state values. That's for the next step!"):

### Principle 3: Only the Search Text and the Tick Box Become State

- **Rule**: List every value the page uses and keep as state only what changes over time, does not come from a parent, and cannot be computed from other state or props.
- **Move**: Side by side, because the reader sorts four values with one verdict each. The test is known from Lesson 22, so the principle applies it once and does not teach it again.
- **Opening Essence**:
  - Smallest code: the four values as a list, with no project file: the list of drinks, the search text, the tick of the box, the drinks that match.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* The list of drinks that match changes when the user types, so it looks like state. It is not: it is computed from the list of drinks, the search text, and the tick.
  - Key idea, from the docs: "Think of state as the minimal set of changing data that your app needs to remember." And: "Figure out the absolute minimal representation of the state your application needs and compute everything else on-demand."
  - What is at stake: every value stored as state is one more value that can disagree with the others, Lesson 22.
- **Root Distinction**:
  - Junior: "Everything that changes on the page is state."
  - Senior: only what the user changes and nothing else can compute is state; the rest is computed during rendering.
- **Simplest version**:
  - The three questions from the docs, asked of each value: Does it remain unchanged over time? Is it passed in from a parent via props? Can you compute it based on existing state or props in your component?
  - The four verdicts:
    1. The list of drinks, `drinks`: passed in as props, so not state.
    2. The search text: changes over time and cannot be computed, so state.
    3. The tick of the box: changes over time and cannot be computed, so state.
    4. The drinks that match: computed from the list, the search text, and the tick, so not state.
- **Words to teach**:
  - *minimal but complete representation of UI state*: the title of Step 3 in the docs. Minimal: nothing that can be computed. Complete: everything the page needs to remember. Needed in the title of the step.
  - Known: the three questions, "minimal set of changing data", redundant state, DRY, Lesson 22. Props against state, Lessons 08 and 12.
  - Helper: none.
- **Side by side**:
  - "the drinks that match, stored with `useState`" and "the drinks that match, computed with `filter` during rendering": NOT the same thing. The stored list must be updated by hand after every key and every tick; the computed list is always right, because it is made again on every render.
  - "props" and "state", from the DeepDive "Props vs State": props "are like arguments you pass to a function"; state "is like a component's memory". "Props and state are different, but they work together": a parent keeps information in state and passes it down as props.
- **Surprises**: none.
- **Where did that come from?**:

  3. The developer adds the tick box and forgets to update the matching drinks from its `onChange`.

  - Console: nothing.

### Principle 4: State in MenuPage Freezes the Search Box

- **Rule**: Put each piece of state in the closest common parent of every component that renders from it, and pass it down as props; until Step 5, the boxes show the state but refuse the user's input.
- **Move**: Steps for a surprise, because the page now shows the state, and the user cannot change it. The ownership steps are known from Lesson 24, so they are applied once.
- **Opening Essence**:

### Principle 5: onFilterTextChange Lets the Search Box Change MenuPage's State

- **Rule**: Only the owner of the state can call its setter, so the owner passes the setters down as props, and the boxes deep in the tree call them from `onChange`.
- **Move**: Side by side, because the reader may expect `value={filterText}` to update `filterText` by itself, as two-way data binding does, and React needs inverse data flow written out as props and `onChange`. The callback prop is known from Lesson 23.
- **Opening Essence**:
  - Smallest code: `<SearchBar onFilterTextChange={setFilterText} />` in the parent and `onChange={(e) => onFilterTextChange(e.target.value)}` on the box in the child.
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* This is the callback prop of Lesson 23 and the passed-down setter of Lesson 24. The docs give it a name for its direction: inverse data flow, data that goes the other way, up the tree.
  - Key idea, from the docs: "The state is owned by `FilterableProductTable`, so only it can call `setFilterText` and `setInStockOnly`."
  - What is at stake: without this step, the page from Principle 4 stays frozen.
- **Root Distinction**:
  - Junior: "The box shows `filterText`, so typing in the box changes `filterText`."
  - Senior: `value` only sends the state down into the box; a function passed down and called from `onChange` sends the typed text back up.
- **Simplest version**:
  - `MenuPage`: `<SearchBar filterText={filterText} inStockOnly={inStockOnly} onFilterTextChange={setFilterText} onInStockOnlyChange={setInStockOnly} />`.
  - `SearchBar`: `onChange={(e) => onFilterTextChange(e.target.value)}` on the text box, `onChange={(e) => onInStockOnlyChange(e.target.checked)}` on the tick box.
- **Words to teach**:
  - *two-way data binding*: named only. The docs: "React makes this data flow explicit, but it requires a little more typing than two-way data binding." It names the habit of other tools where a box and a variable update each other with no handler written. Needed when the reader asks why React needs the extra props.
  - Known: inverse data flow, callback prop, owns the state, passing a setter itself, Lesson 23. `onChange`, `e.target.value`, Lesson 11 and Lesson 20. `e.target.checked`, Lesson 20.
  - Helper: none.
- **Side by side**:
  - "with `value={filterText}` only" and "with `value={filterText}` and `onChange` that calls `onFilterTextChange`": NOT the same thing. The first freezes the box; the second lets every keystroke by the user reach `MenuPage`.
  - "with `onFilterTextChange={setFilterText}`" and "with `onFilterTextChange={handleFilterTextChange}`, a handler that calls `setFilterText`": the exact same thing on this page, because the box sends exactly the next text. The docs pass the setter itself. Known from Lesson 24.
- **Surprises**:
  - The user types `tea`, and the list changes after every letter:
    1. The user types `t`. React calls the `onChange` arrow function in `SearchBar` with the event object `e`.
    2. The arrow function calls `onFilterTextChange('t')`, which is `setFilterText` from `MenuPage`.
    3. React renders `MenuPage` again with `filterText` `'t'`.
    4. `SearchBar` gets `'t'` and shows it in the box. `DrinkList` gets `'t'` and computes `visibleDrinks` again: every drink whose name has a `t`.
    5. The same happens for `e` and `a`. With `tea`, the list shows `Tea` and `Iced tea`.
    6. The user ticks the box. `onInStockOnlyChange(true)` calls `setInStockOnly`. `Iced tea` leaves the list, and only `Tea` stays.
- **Where did that come from?**:
  - `onFilterTextChange` and `onInStockOnlyChange` in `SearchBar`: the props written on the `SearchBar` tag in `MenuPage`. Their values are the setters `setFilterText` and `setInStockOnly`, created by `useState` in `MenuPage`.

  2. The developer expects the box to change `filterText` when the user types, as two-way data binding does in other tools.

  4. The developer adds `onFilterTextChange` and calls it from `onChange`, and the box works.

## Interview Points

- The five steps, in order: break the UI into a component hierarchy; build a static version; find the minimal but complete representation of UI state; identify where the state should live; add inverse data flow.
- Step 1 starts from the mockup and the data: draw boxes, name them, nest them; each component does one thing and matches one piece of the data model.
- Step 2 uses props only and no state; the data enters at the top component and flows down, which the docs call one-way data flow; top down for small pages, bottom up for large ones.
- Building the static version first separates "a lot of typing and no thinking" from "a lot of thinking and not a lot of typing".
- Step 3 keeps as state only what changes over time, does not come from a parent, and cannot be computed; on the docs' example, only the search text and the checkbox value.
- Props are like arguments passed to a function; state is like a component's memory; a parent keeps state and passes it down as props.
- Step 4 finds every component that renders from the state, their closest common parent, and puts the state there, or above it, or in a new component made only to hold it.
- Between Step 4 and Step 5, the page shows the state and refuses input, with the read-only field error in the Console.
- Step 5 passes the setters down; the boxes call them from `onChange`; only the owner of the state can call its setter.
- React makes the data flow explicit, with a little more typing than two-way data binding.
