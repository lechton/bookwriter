## Scope

Covered here:
- The docs' rule: Effects are for synchronizing with an external system. The docs: "If there is no external system involved (for example, if you want to update a component's state when some props or state change), you shouldn't need an Effect."
- The docs' two common cases with no Effect: "You don't need Effects to transform data for rendering." "You don't need Effects to handle user events."
- Case one: a value calculated from state, such as a cart total, is calculated during rendering, not copied into state by an Effect. The cost of the Effect, in the docs' words: "an entire render pass with a stale value", then a re-render.
- Case two: code that runs because the user clicked a button, such as sending an order, goes in the click's event handler, not in an Effect.
- The docs' test for what goes where: "ask yourself *why* this code needs to run. Use Effects only for code that should run *because* the component was displayed to the user."
- What stays in an Effect on the same page: an analytics event sent because the cart was shown. The docs keep it as is, and it runs twice in development.
- The lint rule `set-state-in-effect` from `eslint-plugin-react-hooks`, which reports a setter called directly in an Effect.

## Start of the Lecture

**Opening Essence of the chapter**:
- No short code shows the idea with a surprise before the reader sees the page, so the idea opens in plain words on a real screen, as Examples 8 and 9 of opening-essence open.
- The real screen: a shopping cart with two items, `Socks` at `$5` and `Hat` at `$20`, a Remove button on each row, a line `Total: $25`, and a `Place order` button.
- What the user does, and what changes:
  1. The user clicks Remove on `Hat`. The row goes away and the total line shows `Total: $5`.
  2. The user clicks `Place order`. The button is replaced by the line `Thank you! Your order is placed.`, and the order goes to the server once.
- The bank's friction, on this screen: the developer wrote one Effect that recomputes the total when an item changes, and another Effect that sends the order when the thank-you line appears. Both run, and both are the wrong tool.
- Key idea the reader must remember, the docs' question: why does this code need to run?
  1. To show something calculated from state or props: calculate it during rendering.
  2. Because the user did something: put it in that event's handler.
  3. Because the component is on the screen and must stay in sync with something outside React: that is an Effect.
- What is at stake for the user:
  1. With the total in an Effect, every change renders the cart once with the old total, then again with the new one. On the first load, the first render returns `Total: $0`. Whether the user sees `Total: $0` on the screen is `unconfirmed`, a lab check.
  2. With the order in an Effect, in development the Console shows the order sent twice. The docs: "You wouldn't want to buy the product twice." In production, the docs: "What if the user goes to another page and then presses Back? Your Effect would run again."
- Where readers usually go wrong:
  1. They read "the total depends on the items" as "watch the items with an Effect".
  2. They read "show the thank-you line, then send the order" as "send the order when the thank-you line appears".
- Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* After the page settles, the total from an Effect and the total calculated during rendering show the same `Total: $25`. In production, one click sends one order with either version. The difference is in the extra render with the old total, and in what happens when the thank-you line mounts again.

**Theme**: a shopping cart that shows a total calculated from its items, and sends an order when the user clicks `Place order`.

**Ways** (where the code for "something changed" goes, from the docs, and when each fits):
1. Calculate during rendering: the value can be calculated from props or state, such as the total.
2. The event handler: the code runs because of one interaction, such as the click on `Place order`.
3. An Effect: the code runs because the component is on the screen, and it synchronizes with an external system, such as an analytics server or a chat server.
4. A different `key`: the state of a whole child must start over when a prop changes, such as a comment box per profile. Lesson 25. Named only.

## Principles

### Principle 1: The Total Line Is Calculated During Rendering

- **Rule**: When a value can be calculated from the props or state the component already has, the component calculates it in its body during rendering; it does not keep it in state and set it from an Effect.
- **Move**: Side by side, because the version with an Effect and the version with a `const` show the same total once the page settles, and the difference is hidden in the render passes.
- **Opening Essence**:
  - Smallest code, the docs' own pair:
    1. `const [fullName, setFullName] = useState('');` and `useEffect(() => { setFullName(firstName + ' ' + lastName); }, [firstName, lastName]);`
    2. `const fullName = firstName + ' ' + lastName;`
  - The confusion: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both end with the same name on the page.
  - The docs on the first: "it does an entire render pass with a stale value for `fullName`, then immediately re-renders with the updated value."
  - The docs on the second: "That code will automatically re-run whenever your props or state change."
  - The docs' order of events, for why the Effect costs a render: "When you update the state, React will first call your component functions to calculate what should be on the screen. Then React will "commit" these changes to the DOM, updating the screen. Then React will run your Effects. If your Effect *also* immediately updates the state, this restarts the whole process from scratch!"
- **Root Distinction**:
  - Junior: "The total depends on the items, so I watch the items with an Effect and set the total."
  - Senior: the component body already runs again every time `items` changes, so the total calculated there is always the total for these items.
- **Simplest version**:
  - `const total = items.reduce((sum, item) => sum + item.price, 0);`
  - `<p>Total: ${total}</p>`
- **Words to teach**:
  - *render pass*: one call of the component functions, followed by the commit. Docs words. Needed when the reader counts what the Effect version costs.
  - *stale value*: the old value a render shows before the Effect sets the new one, such as `Total: $0` on the first render. Docs words. Needed at the first render of the Effect version.
  - *cascading updates*: the docs' name, in quotes, for a state update from an Effect that starts another render. Needed once, when the docs' reasons are listed: "faster", "simpler", "less error-prone".
  - *`set-state-in-effect`*: a lint rule from `eslint-plugin-react-hooks`, provided by the React team. The docs: "Validates against calling setState synchronously in an effect, which can lead to re-renders that degrade performance." Needed when the reader asks how to find these Effects in a project. Whether the Vite template turns it on is `unconfirmed`, a lab check.
  - Known: redundant state and `const` during rendering, Lesson 22. `useEffect`, the dependency array, Lesson 32. Render, commit, paint, Lesson 13.
  - Helper: `.reduce`, one line at its first use: it walks the array and adds each `item.price` to `sum`, starting at `0`. Shown in Lesson 27.
- **Side by side**:
  - "with `total` in state, set from an Effect" and "with `const total`": NOT the same thing. Same `Total: $25` once the page settles; the first renders once with the stale total and again with the new one, and adds a state variable, a setter, and an Effect.
  - "with `const total` here" and "with the `const` of Lesson 22": the exact same thing. Lesson 22's rule for redundant state is the fix; this lesson adds only that an Effect is not a way around it.
- **Surprises**:
  - On the first load, the Effect version renders the cart twice:
    1. React calls `App`. `total` is `0`, so the JSX returns `Total: $0`.
    2. React commits `Total: $0` to the DOM.
    3. React runs the Effect, which calls `setTotal(25)`.
    4. React calls `App` again and commits `Total: $25`.
    5. Whether the browser paints `Total: $0` between steps 2 and 3 is `unconfirmed`. The `useEffect` reference: "If your Effect wasn't caused by an interaction (like a click), React will generally let the browser **paint the updated screen first before running your Effect.**" The lint page: "Synchronous `setState` calls in effects trigger immediate re-renders before the browser can paint". The lab must say which the page shows.
  - After a click on Remove, one render pairs one row with the old total:
    1. The click calls `setItems` with only `Socks`.
    2. React calls `App`: the list shows `Socks` only, and `total` is still `25`, so the JSX returns `Total: $25` under one `$5` row.
    3. React commits, then runs the Effect, which calls `setTotal(5)`.
    4. React calls `App` again and commits `Total: $5`.
    5. The `useEffect` reference: "If your Effect is caused by an interaction (like a click), **React may run your Effect before the browser paints the updated screen**." So the user may never see step 2. A `console.log` of `total` in the body shows the two renders. The exact Console lines are `unconfirmed`, a lab check; in development, Strict Mode calls the body twice, Lesson 14, so each render may print twice.
- **Where did that come from?**:
  - `sum` and `item` in `.reduce`: `.reduce` calls the arrow function once per item; `sum` is the running total, starting from the `0` after the arrow function, and `item` is the current element of `items`.
  - `item.price`: the field name comes from our `initialItems`, `{ id: 1, name: 'Socks', price: 5 }` and `{ id: 2, name: 'Hat', price: 20 }`.
- **Real beginner mistake**:
  1. A developer stores the cart total in state, as the bank row says, and sets it from an Effect that lists `[items]`.
  2. Later, a second value is added the same way, such as an item count, with its own state and Effect.
  3. Each change of `items` now renders the cart once with old values, then again.
  4. The linter reports the setter calls with `set-state-in-effect`. The exact message text is `unconfirmed`.
  5. The docs' challenge "Transform data without Effects" shows the same habit with three Effects, for `activeTodos`, `visibleTodos`, and a `footer`; the docs' solution keeps only `todos` and `showActive` in state.
- **Interview depth**:
  - The docs: "When something can be calculated from the existing props or state, don't put it in state. Instead, calculate it during rendering." The three reasons: "faster", "simpler", "less error-prone".
  - A slow calculation: `useMemo` caches it, not an Effect. The docs: "To cache expensive calculations, add `useMemo` instead of `useEffect`." Usually not needed: "unless you're creating or looping over thousands of objects, it's probably not expensive." Lesson 56. The React Compiler "can automatically memoize expensive calculations for you", Lesson 63.
  - A chain of Effects, each setting state that starts the next, as in the docs' `Game`: in the worst case "there are three unnecessary re-renders of the tree below", and the chain breaks when the code sets old values, such as a game history. The docs' fix: "calculate what you can during rendering, and adjust the state in the event handler."
  - Mirroring a prop in state, Lesson 22: an Effect that copies a prop into state has the same cost as the total.
  - Resetting all state of a child when a prop changes: a different `key`, not an Effect that calls the setters. The docs' `ProfilePage` with `key={userId}`. Lesson 25.
  - Adjusting part of the state when a prop changes: the docs allow setting state during rendering with a `prevItems` state and a condition, then say "most components shouldn't need it either"; the docs' best option is to store `selectedId` and find the item during rendering.
- **React does**:
  - Page, Effect version: `Total: $0` on the first render, then `Total: $25`. Whether `Total: $0` is painted is `unconfirmed`.
  - Page, `const` version: `Total: $25` from the first render.
  - Console: no React warning or error is expected for either version; `unconfirmed`, a lab check. The render log lines are ours and `unconfirmed`.
  - Elements panel: `<p>Total: $25</p>` in both versions once the page settles. `unconfirmed`, a lab check, including the exact text inside the `<p>`.
  - Lint: `set-state-in-effect` on the `setTotal` call, the shape of the docs' Invalid example "Transforming data in effect". Message text `unconfirmed`.
- **Example step**: `App.jsx` loses `const [total, setTotal] = useState(0);` and the Effect that set it, and gains `const total = items.reduce(...)`. The page looks the same.
- **Code names**: `App.jsx`, `initialItems`, `items`, `setItems`, `total`, `setTotal`, `useState(0)`, `useEffect`, `[items]`, `.reduce`, `sum`, `item.price`, `Socks`, `Hat`, `Total: $0`, `Total: $25`, `Total: $5`, `fullName`, `firstName`, `lastName`, `set-state-in-effect`, `🔴 Avoid: redundant state and unnecessary Effect`, `✅ Good: calculated during rendering`

### Principle 2: The Place order Click Sends the Order

- **Rule**: When code runs because the user did one thing, such as clicking `Place order`, it goes in that click's event handler; it does not go in an Effect that runs when the thank-you line appears or when a state flag changes.
- **Move**: Steps for a surprise, because the reader expects one click to send one order, and in development the Effect version sends it twice.
- **Opening Essence**:
  - Smallest code, two places for the same line `sendOrder(items)`:
    1. `function handlePlaceOrder() { sendOrder(items); setIsOrdered(true); }`
    2. In `OrderPlaced`: `useEffect(() => { sendOrder(items); }, [items]);`
  - The confusion: *"It may look the same, or work the same at first, but it is NOT the same thing!"* In production, one click prints one `Sending order: 2 items` with either version. `unconfirmed`, a lab check.
  - The docs' test: "ask yourself *why* this code needs to run. Use Effects only for code that should run *because* the component was displayed to the user."
  - The order is sent because the user clicked, not because the thank-you line is on the screen. The docs: "You don't want to buy the product when the user *visits* a page; you want to buy it when the user *clicks* the Buy button."
- **Root Distinction**:
  - Junior: "The order goes out after the click and the thank-you line appears after the click, so sending it when the thank-you line appears is the same."
  - Senior: the click happens once; the thank-you line can mount more than once, in development by Strict Mode and in production when the user comes back to it.
- **Simplest version**:
  - `function handlePlaceOrder() { sendOrder(items); setIsOrdered(true); }`
  - `<button onClick={handlePlaceOrder}>Place order</button>`
- **Words to teach**:
  - *event-specific logic*: the docs' words for code caused by one interaction. Needed at the docs' label `🔴 Avoid: Event-specific logic inside an Effect`.
  - *POST request*: a request that sends data to the server, such as an order. MDN, POST. The docs' examples: `/api/buy` and `/api/register`. Needed at `sendOrder`, which stands in for one and only prints.
  - The docs on what an Effect cannot know: "By the time an Effect runs, you don't know *what* the user did (for example, which button was clicked)."
  - Known: event handler, Lesson 11. Strict Mode's extra setup and cleanup on mount, Lesson 32. Mount, unmount, Lesson 32.
  - Helper: `sendOrder`, our function in `api.js`.
- **Side by side**:
  - "with `sendOrder` in `handlePlaceOrder`" and "with `sendOrder` in an Effect in `OrderPlaced`": NOT the same thing. The handler runs once per click; the Effect runs on every mount of `OrderPlaced`, twice in development.
  - "with a flag Effect, `useEffect(() => { if (isOrdered) sendOrder(items); }, [isOrdered, items])`" and "with `sendOrder` in the handler": NOT the same thing. It works on one click, but the order now depends on a state value, not on the click; the docs' `jsonToSubmit` form has this shape, labeled `🔴 Avoid: Event-specific logic inside an Effect`.
- **Surprises**:
  - In development, one click on `Place order` sends the order twice:
    1. The click calls `setIsOrdered(true)`.
    2. React renders `App`; the button is replaced by `<OrderPlaced items={items} />`.
    3. React mounts `OrderPlaced` and runs its Effect: the Console prints `Sending order: 2 items`.
    4. Strict Mode runs the cleanup, which is empty, and the setup again: the Console prints `Sending order: 2 items` a second time.
    5. The docs: "🔴 Wrong: This Effect fires twice in development, exposing a problem in the code." The two Console lines are `unconfirmed`, a lab check.
  - In production, the order can go out again with no click:
    1. The user places the order and sees the thank-you line.
    2. The user goes to another page, then presses Back.
    3. `OrderPlaced` mounts again and its Effect runs again. The docs: "What if the user goes to another page and then presses Back? Your Effect would run again." The lab cannot show this on one page; it stays a docs fact.
- **Where did that come from?**:
  - `items` in `OrderPlaced`, Effect version: a prop from `App`, `<OrderPlaced items={items} />`. In the handler version, `items` is `App`'s own state, so `OrderPlaced` needs no props.
  - `sendOrder`: imported from our `src/api.js`.
- **Real beginner mistake**:
  1. A developer puts `sendOrder` in an Effect in the thank-you component, so the order goes out "when the order is done".
  2. In development, the Console shows the order twice.
  3. To stop the second line, the developer adds a ref that blocks the second run.
  4. The Console shows one line, and in production the order still goes out again after Back.
  5. Lesson 32: the docs ask "how to fix my Effect so that it works after remounting", not how to run it once. Here the fix is to delete the Effect.
- **Interview depth**:
  - The docs' `ProductPage`: a notification shown from an Effect when `product.isInCart` is true appears again "every time you refresh that product's page", when the cart is remembered across reloads. The fix: one function `buyProduct()` called from both handlers.
  - The docs' challenge "Submit a form without Effects": change `showForm` to start at `false`, and the Effect sends an empty message with no click; the docs' Console line is `'Sending message: ' + message`. The fix: `sendMessage(message)` in `handleSubmit`.
  - Notifying a parent: the docs' `Toggle` calls `onChange` in the same event handler as `setIsOn`, not in an Effect, so "there will only be one render pass". Lesson 23.
  - Passing data to a parent from an Effect makes the data flow "very difficult to trace"; the docs' fix: the parent fetches and passes the data down. Lesson 24.
  - Inside the handler, state is a snapshot: after `setIsOrdered(true)`, `isOrdered` is still `false` on the next line. Lesson 15.
  - Logic that must run once per app load: a top-level `didInit` variable or code outside the component, not an Effect with `[]`. The docs' "Initializing the application".
- **React does**:
  - Page: `Thank you! Your order is placed.` in place of the button, with both versions.
  - Console, Effect version in development: `Sending order: 2 items` twice. Handler version: once. Both `unconfirmed`, a lab check. The strings are ours.
  - Elements panel: `<p>Thank you! Your order is placed.</p>` where the `<button>` was. `unconfirmed`, a lab check.
- **Example step**: `App.jsx` gains `handlePlaceOrder`, which calls `sendOrder(items)` and then `setIsOrdered(true)`; the button's `onClick` becomes `handlePlaceOrder`. `OrderPlaced.jsx` loses its Effect and its `items` prop.

### Principle 3: The Cart Visit Is Logged by an Effect

- **Rule**: When code runs because the component was shown, and it talks to something outside React, such as an analytics server, it stays in an Effect; that it runs twice in development is not a reason to move it.
- **Move**: Side by side, because the visit log and the order both print twice in development, and only one of the two must move.
- **Opening Essence**:
  - Smallest code: `useEffect(() => { logVisit('cart'); }, []);`
  - The confusion: *"It may look the same, or work the same at first, but it is NOT the same thing!"* In development, `Visit: cart` prints twice, just as `Sending order: 2 items` did in Principle 2. One extra visit changes nothing the user sees; one extra order charges the user twice.
  - The docs keep this code: "**We recommend keeping this code as is.** Like with earlier examples, there is no *user-visible* behavior difference between running it once and running it twice." "**In production, there will be no duplicate visit logs.**"
  - The docs' reason it is an Effect: "the _reason_ to send the analytics event is that the form was displayed."
- **Root Distinction**:
  - Junior: "Effects that run twice are wrong, so every Effect that runs twice must move to a handler."
  - Senior: the question is why the code runs. The visit happens because the cart is on the screen; there is no click to put it in.
- **Simplest version**:
  - `useEffect(() => { logVisit('cart'); }, []);`
- **Words to teach**:
  - *analytics event*: a message to a server that counts what users see and do, such as one visit of the cart. Docs words. Needed at `logVisit`.
  - The docs' sentence that holds the whole lesson: "If this logic is caused by a particular interaction, keep it in the event handler. If it's caused by the user _seeing_ the component on the screen, keep it in the Effect."
  - Known: external system, Lesson 32. `[]` runs the setup after the first mount, Lesson 32.
  - Helper: `logVisit`, our function in `api.js`.
- **Side by side**:
  - "with `logVisit('cart')` in an Effect" and "with `sendOrder(items)` in an Effect": NOT the same thing. Both print twice in development; the visit is caused by the cart on the screen, and the order is caused by a click.
- **Surprises**:
  - In development, `Visit: cart` prints twice on the first load:
    1. React mounts `App` and runs the setup: `Visit: cart`.
    2. Strict Mode runs the cleanup, which is empty, and the setup again: `Visit: cart`.
    3. In production, one line. The Console lines are `unconfirmed`, a lab check.
- **Where did that come from?**:
  - `logVisit` and `'cart'`: our function in `api.js` and our page name; the docs' version is `logVisit(url)`, and the docs' other version is `post('/analytics/event', { eventName: 'visit_form' })`.
- **Real beginner mistake**:
  1. A developer sees `Visit: cart` twice in the Console.
  2. They add a ref that blocks the second run, or move the call out of the Effect.
  3. The docs keep the code as is, and say the development logs should not count: "you don't want the logs from the development machines to skew the production metrics."
- **Interview depth**:
  - Fetching stays in an Effect too: the docs, "You *don't* need to move this fetch to an event handler", because results must match the query "while this component is visible". Lesson 33.
  - Subscribing to data from outside React, such as `navigator.onLine`: the docs prefer `useSyncExternalStore` to an Effect. Lesson 53.
  - The docs: "The fewer raw `useEffect` calls you have in your components, the easier you will find to maintain your application." Custom Hooks, Lesson 39.
  - For more exact analytics, the docs name sending analytics "from the route change event handlers instead of Effects", and intersection observers.
- **React does**:
  - Page: nothing changes.
  - Console, development: `Visit: cart` twice; production: once. `unconfirmed`, a lab check. The string is ours.
- **Example step**: `App.jsx` gains `useEffect(() => { logVisit('cart'); }, []);`, the one Effect left in the finished cart.
- **Code names**: `App.jsx`, `api.js`, `logVisit`, `'cart'`, `Visit: cart`, `useEffect`, `[]`, `post('/analytics/event', { eventName: 'visit_form' })`, `logVisit(url)`

## Interview Points

- Effects are an escape hatch for synchronizing with an external system; with no external system, there is usually no need for an Effect.
- A value calculated from props or state is calculated during rendering; an Effect that sets it costs a render pass with a stale value and a second render.
- Code caused by one interaction goes in that event's handler; by the time an Effect runs, it does not know what the user did.
- The docs' test: why does this code need to run? Because the component was displayed: an Effect. Because of a click: the handler.
- An Effect that sends an order or a purchase runs again on remount: twice in development, and again after Back in production.
- An Effect that only logs a visit stays; running it twice changes nothing the user sees.
- To reset a child's state when a prop changes, give it a different `key`. Lesson 25.
- To cache a slow calculation, use `useMemo`, not an Effect. Lesson 56.
- To update a parent, call its function in the same event handler, so React batches both updates into one render pass.
- The lint rule `set-state-in-effect` reports a setter called directly in an Effect.
