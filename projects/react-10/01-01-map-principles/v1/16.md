# Q16 Principle Map (River Version v1): Batching and Updater Functions
- **Version**: River Version (`v1`)
- **Bank Row**: `questions/questions.md` row 16, Version 4
- **Topic Tag**: `#state_updates` | `❱ CORE`
- **Interview Question**: *How does React queue multiple state updates, and when do you need an updater function?*

## Authorized Scope
- Batching: React runs every line of an event handler first and processes the state updates only after the handler has finished, so several setter calls in one handler, for one state variable or for several, end in one render, and the screen never shows a half-finished mix of old and new values.
- Each separate click is handled on its own: React does not batch across several intentional events.
- Why three `setScore(score + 1)` calls in one handler add one: each call reads the same snapshot (Lesson 15) and adds "replace with 1" to the queue three times.
- The updater function `setScore(s => s + 1)`: React adds the function itself to the queue and, during the next render, calls it with the pending state, the result of the updates queued before it, so three calls add three.
- How React walks the queue in order from the current state: a value entry replaces the running result and ignores what came before it, an updater entry continues from the running result, so the order of mixed calls decides the final number.
- Why an updater must be pure: React calls it during the next render, not on the click, and in `<StrictMode>` development calls it twice and keeps one result.
- When an updater is needed: the next value depends on the previous one and more than one update of the same state can be queued before the next render; one update per click works with a plain value. The naming habits `s`, `score`, and `prevScore` for the updater's parameter.
- Out of scope: `flushSync` (`Q65 #flush_sync`), batching inside timeouts and promises and other batching internals (`Q75 #batching_internals`), reducers for state calculated from other state (`Q27 #use_reducer`), React skipping a render when the new value equals the current one and updating objects in state (`Q17 #state_objects`), array state and `push` inside an updater (`Q19 #state_arrays`), the full list of what `<StrictMode>` runs twice (`Q47 #strict_mode`), the snapshot and the `nextNumber` variable (`Q15 #state_snapshots`, recall only), Trigger, Render, and Commit (`Q13 #render_and_commit`, recall only), and purity and `<StrictMode>` calling components twice (`Q14 #purity`, recall only).

## General Concepts Introduction (Runway Plan)
- **Opening Essence**:
  - **Furniture-free snippet**: `const [count, setCount] = useState(0);` and a button `+3` whose handler calls `setCount(count + 1);` three times; one click shows `1`. The same button with `setCount(c => c + 1);` three times; one click shows `3`. Both are the `react.dev` `+3` counter (`learn/queueing-a-series-of-state-updates.md`).
  - **Human image**:
    1. The waiter from `react.dev`: "A waiter doesn't run to the kitchen at the mention of your first dish!" The waiter lets the guest finish the whole order, change it, and hears the others at the table, then goes to the kitchen once. That is batching: React hears every setter call of the handler, then renders once.
    2. The queue as a pile of order slips read from top to bottom. A slip with a value says "make it 1", whatever the slips above it said. A slip with an updater says "add one to whatever the total is by now". Everyday meaning of queue: a line where things wait their turn in the order they arrived, the same word as the bakery line of Lesson 15 and as "queueing a render" in Lesson 13.
  - **Exact nuance of confusion to state out loud**:
    1. Three `setCount(count + 1)` lines look like three additions, but they are NOT the same thing: each line hands React the finished number `1`, so React receives "make it 1" three times.
    2. `setCount(count + 1)` and `setCount(c => c + 1)` look like the same job, and with one call per click they work the same at first, but they are NOT the same thing: the value is calculated now from this render's snapshot; the function is calculated later by React from the pending state.
    3. The screen not changing between two setter lines looks like React is slow or the setter failed, but it did NOT fail: React waits for the whole handler, the way the waiter waits for the whole order.
- **Theme**: A basketball scoreboard shows `Home: 0`; the `+3` button for a three-point shot calls the one-point helper three times, and the score goes up by one instead of three.
- **Ways**: Three ways to give a setter the next value, and when each fits:
  1. A value calculated from the snapshot, `setScore(score + 3)`: fits one update of that state per event.
  2. A value saved first in a variable, `const nextScore = score + 3`, passed to the setter and to every other line (Lesson 15): fits when the handler itself must use the new value right away.
  3. An updater, `setScore(s => s + 1)`: fits when the new value depends on the old one and more than one update of the same state is queued before the next render, such as a helper called several times. A reducer for state calculated from other state is a fourth way, owned by `Q27 #use_reducer`.
- **Recall**:
  - `const [score, setScore] = useState(0)` keeps the value inside React; the setter asks React for a new render with the next value (Lesson 12, `Q12 #use_state`).
  - Calling a setter triggers a render; React calls the component again after the handler and commits the change to the DOM; "queueing a render" (Lesson 13, `Q13 #render_and_commit`).
  - A pure function only calculates its result from its inputs and changes nothing outside; `<StrictMode>` in `src/main.jsx` calls each component function twice in development, never calls an event handler twice, and lets both `console.log` lines reach the Console (Lesson 14, `Q14 #purity`).
  - Every render gets its own fixed value of each state variable; the setter does not change the variable in the running handler; three `setNumber(number + 1)` calls in one handler move the screen by one, announced as the topic of this lesson; `nextNumber` keeps the new value for the rest of the handler (Lesson 15, `Q15 #state_snapshots`).
  - Event handlers passed as `onClick={handleThree}`, inline arrow functions such as `onClick={() => handleShare('Email')}`, and a handler that calls another function (Lesson 11, `Q11 #event_handling`).
- **Runway topics**:
  - Batching: React collects the setter calls of one handler and renders once after it. New word, unlocked through its everyday meaning: a batch is a group of things handled together in one go, like cookies baked on one tray instead of one by one. Introduced in `batching-one-render`.
  - The queue: React keeps, for each state variable, a list of the updates waiting for the next render, in the order the setter calls happened. New in this sense.
  - The short arrow function `s => s + 1`: one parameter with no parentheses around it, no curly braces, and the value after the arrow is returned. Refresher on the arrow functions of Lesson 11; it is the exact same thing as `function (s) { return s + 1; }`. New in this short form.
  - Passing a function as a value without calling it, recalled from `onClick={handleThree}` in Lesson 11: `setScore(s => s + 1)` hands the function to React the same way.
  - A helper function: a small function such as `addPoint` that several handlers call so the same lines are not written three times.
  - `alert('...')`: the browser's pop-up message, which stops the running JavaScript until the user clicks `OK`. New for this lesson.
  - How the project files are organized: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx`, `src/components/Scoreboard.jsx`.
- **Example**:
  - **Chosen page**: `Scoreboard`, the score of one basketball team. `Scoreboard` holds `const [score, setScore] = useState(0)` and `const [lastPlay, setLastPlay] = useState('Game start')`, and shows `<h1>Scoreboard</h1>`, `<p className="score">Home: {score}</p>`, `<p className="last-play">Last play: {lastPlay}</p>`, and the buttons. Principle 1 has only the `+3` button with `handleThree` setting both states and an `alert`. Principle 2 adds the `+1` and `+2` buttons and the helper `addPoint` with `setScore(score + 1)`, called once, twice, and three times. Principle 3 rewrites `addPoint` as an updater. Principle 4 adds the helper `addTwo` written with a value and shows the two orders of `addTwo()` and `addPoint()` in `+3`. Principle 5 puts a `console.log` inside the updater, then moves it to the handler.
  - **Why this concept is the reason this page exists**:
    1. A scoreboard has `+1`, `+2`, and `+3` buttons, so one helper that adds a point, called once, twice, or three times, is the natural way a developer writes it, the same shape as the `increment()` helper of `react.dev`.
    2. The bug is big and seen at once: a three-point shot that shows `Home: 1` is wrong for everyone watching the game.
    3. A score and a last-play line change together on every basket, so two state variables in one handler are there from the start, and the one render of batching has a reason to matter.
    4. Everyone knows a scoreboard, and the only action is clicking a button.
  - **Other candidate pages considered**:
    1. *The syllabus card's ticket order with `+3 Tickets` and `setTickets`*: rejected, because Lesson 13 already built a ticket counter (`Concert Tickets`, `Add ticket`), and a ticket box gives no natural reason to add one ticket three times.
    2. *The `react.dev` `+3` counter with `number`*: kept only as the furniture-free essence, because a bare number gives no reason to call the setter three times.
    3. *The `react.dev` art marketplace request counter (`Pending`, `Completed`, `Buy`, `await delay(3000)`)*: rejected as the page, because it needs `async`, `await`, and promises, and batching after `await` belongs to `Q75 #batching_internals`; its lesson, that an updater reads the latest state rather than the click's snapshot, is kept as one interview line.
    4. *The bakery queue of Lesson 15*: rejected, because each click makes one update of each state, so it never queues two updates of the same state, and it is the page of the lesson before.

## Principle Thread
- **Anchor**: React keeps a queue of the setter calls of one event handler and processes it in one render after the handler finishes; a value in the queue replaces the running result, and an updater function is called with the running result.
- **Axis**: From when the updates are processed, to what each kind of entry does, to what may live inside an updater and when to reach for it:
  1. React waits for the whole handler and renders once for all its setter calls (Principle 1).
  2. A value entry replaces: three calls from the same snapshot queue the same number three times (Principle 2).
  3. An updater entry continues: React calls it with the pending state, so three calls add three (Principle 3).
  4. Mixed entries are walked in order, so the order of a value and an updater decides the result (Principle 4).
  5. Updaters run during the next render, maybe twice, so they must be pure; use one when more than one update of the same state is queued (Principle 5).
- **Why This Axis**: Cause before effect. The queue is made by batching, so the reader first sees that React waits for the whole handler (Principle 1). Only then does "replace with 1, three times" make sense as three slips in a waiting queue (Principle 2). The updater is the fix for that exact bug (Principle 3). Mixing the two needs both kinds already known (Principle 4). Purity and the choice of when to use an updater come last, because they need to know that React calls the updater later, during the render (Principle 5).

## Principles

### Principle 1: React Runs the Whole Handler First, Then Renders Once for All Its Setter Calls
- **Handle**: `batching-one-render`
- **Rule**: When a handler calls one or several setters, React waits until every line of the handler has run, including any code after the setters, and then processes all the queued updates in one render; the screen changes once, with every state variable updated together, and each separate click is handled on its own.
- **Opening Essence**:
  - **Furniture-free snippet**: `const [count, setCount] = useState(0);` and `const [label, setLabel] = useState('Not clicked');`, with `function handleClick() { setCount(count + 1); setLabel('Clicked'); alert('Done'); }` on a button. While the `Done` pop-up is open, the page still shows `0` and `Not clicked`; after `OK`, it shows `1` and `Clicked` together.
  - **Human image**: the `react.dev` waiter, who lets the guest finish the whole order before walking to the kitchen once. Batching unlocked through its everyday meaning: a tray of cookies baked together, not one by one.
  - **Exact nuance of confusion to state out loud**:
    1. Two setter lines look like two updates of the screen, one after the other, but they are NOT two renders: React renders once, after the handler.
    2. The old page behind the pop-up looks as if the setters failed, but they did NOT fail: they are waiting in the queue, and the render comes only when the handler finishes.
- **Root Distinction**:
  - *Junior blurred view*: "Each setter call updates the screen at the moment it runs."
  - *Senior grounding*: a setter call only adds an update to the queue; React processes the queue in one render after the handler returns.
- **Real Beginner Mistake (events, in order)**:
  1. The scoreboard shows `Home: 0` and `Last play: Game start`.
  2. The developer writes `handleThree` with `setScore(score + 3);`, then `setLastPlay('Three-pointer');`, then `alert('Three points for Home!');` to announce the basket.
  3. The user clicks `+3`.
  4. The pop-up `Three points for Home!` opens, while the scoreboard behind it still shows `Home: 0` and `Last play: Game start`.
  5. The developer thinks the setters are slow or broken and starts moving the `alert` line around.
  6. The user clicks `OK`; the handler finishes, and the scoreboard shows `Home: 3` and `Last play: Three-pointer` at the same moment.
- **Interview Depth**:
  - `react.dev`: "React waits until *all* code in the event handlers has run before processing your state updates."
  - `react.dev`: batching "makes your React app run much faster. It also avoids dealing with confusing "half-finished" renders where only some of the variables have been updated."
  - Batching covers several state variables, "even from multiple components", in one event.
  - `react.dev`: "React does not batch across *multiple* intentional events like clicks"; each click is handled separately, so "if the first button click disables a form, the second click would not submit it again."
  - `useState` Caveats: React "updates the screen **after all the event handlers have run**"; to force an earlier update, for example to read the DOM, `flushSync` exists (`Q65 #flush_sync`).
  - Batching inside timeouts and promises is `Q75 #batching_internals`.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any line in `handleThree` that tells React to render; the handler only calls two setters and `alert`.
    - **Who supplies it**: React, which keeps the updates in a queue and starts one render when the handler returns.
    - **What JavaScript and React do**:
      1. The click runs `handleThree` from the render where `score` is `0`.
      2. `setScore(0 + 3)` adds an update for `score` to its queue; nothing on the screen changes.
      3. `setLastPlay('Three-pointer')` adds an update for `lastPlay` to its queue; nothing on the screen changes.
      4. `alert` opens the pop-up and stops the handler until `OK`.
      5. After `OK`, the handler returns; React calls `Scoreboard` once, `useState` returns `3` and `'Three-pointer'`, and React commits both lines.
- **React Does**:
  - Behavior from the corpus: the page keeps the old values until the handler and any code in it completes, then both lines change in one render. The exact page text while the pop-up is open (`Home: 0`, `Last play: Game start`) and after `OK` (`Home: 3`, `Last play: Three-pointer`) is `unconfirmed`.
  - A `console.log('Scoreboard renders')` at the top of the body would print once per render, which under `<StrictMode>` in development is two lines per click (Lesson 14) and one line in the production build: `unconfirmed`.
  - The corpus names no Console warning or error for this case: `unconfirmed`.
- **Example Step**: Creates `index.html`, `src/main.jsx` with `root.render(<StrictMode><App /></StrictMode>)`, `src/App.jsx` returning `<Scoreboard />`, and `src/components/Scoreboard.jsx` with both `useState` calls, the heading, the two lines, the `+3` button, and `handleThree` as in the mistake. New page elements here: `Scoreboard`, `Home: 0`, `Last play: Game start`, and the `+3` button.
- **Code names**: `index.html`, `src/main.jsx`, `src/App.jsx`, `src/components/Scoreboard.jsx`, `Scoreboard`, `score`, `setScore`, `useState(0)`, `lastPlay`, `setLastPlay`, `'Game start'`, `handleThree`, `setScore(score + 3)`, `setLastPlay('Three-pointer')`, `alert('Three points for Home!')`, `score`, `last-play`, `Home: 0`, `Home: 3`, `Last play: Three-pointer`, `+3`, `OK`, `count`, `setCount`, `label`, `setLabel`, `'Not clicked'`, `'Clicked'`, `alert('Done')`, `flushSync`
- **Visual idea**: A timeline of one click: two setter calls dropping slips into two queues, the pop-up over the unchanged board, then one render that changes both lines together.

### Principle 2: A Value Replaces: Three Calls From the Same Snapshot Queue the Same Number Three Times
- **Handle**: `value-replaces`
- **Rule**: A setter given a value, such as `setScore(score + 1)`, adds "replace with that value" to the queue; the value is calculated at the moment of the call from this render's snapshot, so three such calls in one handler queue the same number three times and the score rises by one.
- **Opening Essence**:

### Principle 3: An Updater Continues: React Calls It With the Pending State, So Three Calls Add Three
- **Handle**: `updater-continues`
- **Rule**: A setter given a function, such as `setScore(s => s + 1)`, adds the function itself to the queue; during the next render React calls each updater in order with the pending state, the result of the updates before it, and stores the last result, so three calls add three.
- **Opening Essence**:
  - **Furniture-free snippet**: `setNumber(n => n + 1);` three times. The `react.dev` table: first `n` is `0` and returns `1`, second `n` is `1` and returns `2`, third `n` is `2` and returns `3`; "React stores `3` as the final result and returns it from `useState`."
  - **Human image**: a slip that says "add one to whatever the total is by now", read only when the kitchen gets to it.
  - **Exact nuance of confusion to state out loud**:
    1. `setScore(score + 1)` and `setScore(s => s + 1)` work the same at first, with one call per click, but they are NOT the same thing: the first hands React a number calculated now from the snapshot; the second hands React a function that React calls later with the pending state.
    2. `s` and `score` look like the same variable, but they are NOT the same thing: `score` is this render's fixed value; `s` is a parameter that React fills in, with a different number for each queued updater.
    3. `s => s + 1` is the exact same thing as `function (s) { return s + 1; }`, written short.
- **Root Distinction**:
  - *Junior blurred view*: "The arrow function is just a longer way to write `score + 1`."
  - *Senior grounding*: the arrow function is not called by our code; React calls it during the next render, one updater after another, each with the result of the one before.
- **Real Beginner Mistake (events, in order)**:
  1. The developer reads that an updater fixes the `+3` button and writes `setScore(s => score + 1)` inside `addPoint`.
  2. The user clicks `+3`: the score still rises by one, because the function never reads `s` and returns `score + 1` from the snapshot each time.
  3. The developer changes the body to read the parameter: `setScore(s => s + 1)`.
  4. The user clicks `+3`: from `Home: 0` the score shows `Home: 3`; `+2` adds two, and `+1` adds one.
- **Interview Depth**:
  - `useState` Parameters: an updater "must be pure, should take the pending state as its only argument, and should return the next state"; React "will calculate the next state by applying all of the queued updaters to the previous state."
  - `react.dev`: an updater is "a way to tell React to "do something with the state value" instead of just replacing it."
  - Naming: the first letters of the state variable, such as `a` for `age` or `s` for `score`, the full name, or a prefix like `prevScore` (`setEnabled(prevEnabled => !prevEnabled)` in `react.dev`).
  - Any function passed to a setter is treated as an updater; to store a function in state, write `setFn(() => someOtherFunction)`.
  - `set` functions return nothing, so `const next = setScore(s => s + 1)` gives `undefined`.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any call that passes a number into `s`; `addPoint` only writes `setScore(s => s + 1)`.
    - **Who supplies it**: React, which calls each queued updater during the next render and passes it the pending state.
    - **What JavaScript and React do**:
      1. The click runs the `+3` handler from the render where `score` is `0`.
      2. Each `addPoint()` call passes a new arrow function to `setScore` without calling it; React adds it to the queue, three times.
      3. The handler returns; React calls `Scoreboard`, and `useState` walks the queue.
      4. The first updater gets `s` as `0` and returns `1`; the second gets `1` and returns `2`; the third gets `2` and returns `3`.
      5. `useState` returns `3`, and React commits `Home: 3`.
- **React Does**:
  - Behavior from the corpus: three updater calls in one handler raise the state by three after one click; the `react.dev` `+3` counter "correctly increments the value by 3". The exact page texts `Home: 3` after `+3` and `Home: 5` after a following `+2` are `unconfirmed`.
  - `setScore(s => score + 1)` raising the score by one is derived from the queue rules, not shown in the corpus: `unconfirmed`.
- **Example Step**: Rewrites `addPoint` in `src/components/Scoreboard.jsx` as `setScore(s => s + 1)`, first with the mistaken `s => score + 1`, then fixed. No new page element.
- **Code names**: `setScore(s => s + 1)`, `setScore(s => score + 1)`, `s`, `prevScore`, `addPoint`, `Home: 3`, `Home: 5`, `n => n + 1`, `setNumber(n => n + 1)`, `setAge(a => a + 1)`, `setFn(() => someOtherFunction)`
- **Visual idea**: The three updater slips as a chain, each arrow handing its result to the next: `0` to `1`, `1` to `2`, `2` to `3`.

### Principle 4: React Walks the Queue in Order, So the Order of a Value and an Updater Decides the Result
- **Handle**: `queue-in-order`
- **Rule**: During the next render React starts from the current state and walks the queue in the order the calls happened: a value entry replaces the running result and ignores everything before it, and an updater entry is called with the running result; a value placed after updaters wipes them out.
- **Opening Essence**:
  - **Furniture-free snippet**: the `react.dev` cases from `0`: `setNumber(number + 5); setNumber(n => n + 1);` gives "replace with `5`", then `5 + 1`, so `6`; adding `setNumber(42);` at the end gives `42`. Laid out as two orders of the same two calls, A: `setNumber(number + 5)` before `setNumber(n => n + 1)`, giving `6`; B: `setNumber(n => n + 1)` before `setNumber(number + 5)`, where the updater gives `1` and the value then replaces it with `5`, so `5`.
  - **Human image**: the same pile of slips read from top to bottom; a "make it 5" slip throws away whatever the slips above it built, and an "add one" slip builds on it.
  - **Exact nuance of confusion to state out loud**:
    1. First state that a value call and an updater call can sit in the same handler for the same state; then that they can come in two orders; only then that the two orders are NOT the same thing, by tracing each from top to bottom.
    2. `setNumber(5)` and `setNumber(n => 5)` look different, but they are the exact same thing in the queue: `react.dev` says `setState(5)` "actually works like `setState(n => 5)`, but `n` is unused!"
- **Root Distinction**:
  - *Junior blurred view*: "I add two points and one point, so the order does not matter."
  - *Senior grounding*: a value entry is not "add two"; it is "make it this number", so whatever was queued before it is lost.
- **Real Beginner Mistake (events, in order)**:
  1. The page reloads to `Home: 0`.
  2. A teammate writes a second helper, `function addTwo() { setScore(score + 2); }`, for the `+2` button; it works, because it is the only score update in that click.
  3. The teammate rewrites the `+3` handler as `addTwo(); addPoint();`, a basket of two and one point more.
  4. The user clicks `+3`: `Home: 3`, correct, because "replace with `2`" comes first and the updater adds one to it.
  5. Later, someone swaps the two lines to `addPoint(); addTwo();`.
  6. After a reload, the user clicks `+3`: `Home: 2`, because the updater gives `1` and "replace with `2`" then throws it away.
  7. The fix: `addTwo` becomes `setScore(s => s + 2)`, and both orders give `Home: 3`.
- **Interview Depth**:
  - The `react.dev` queue tables: "replace with `5`" gets `0 (unused)` and returns `5`; `n => n + 1` gets `5` and returns `6`; "replace with `42`" gets `6 (unused)` and returns `42`.
  - The algorithm from the `react.dev` challenge solution, `getFinalState(baseState, queue)`: start with `finalState = baseState`; for each update, if `typeof update === 'function'`, `finalState = update(finalState)`, otherwise `finalState = update`.
  - Mixing value calls and updater calls for the same state in one handler is the case where order matters; using updaters throughout makes the order not matter for additions.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any line that throws away the point added by `addPoint()` in the order `addPoint(); addTwo();`.
    - **Who supplies it**: React, whose queue walk treats a value entry as "replace with" and ignores the running result.
    - **What JavaScript and React do**:
      1. The click runs the `+3` handler from the render where `score` is `0`.
      2. `addPoint()` adds the updater `s => s + 1` to the queue.
      3. `addTwo()` calculates `0 + 2` and adds "replace with `2`".
      4. The handler returns; React renders and walks the queue from `0`: the updater returns `1`; "replace with `2`" ignores `1` and gives `2`.
      5. `useState` returns `2`, and React commits `Home: 2`.
- **React Does**:
  - From the corpus: `setNumber(number + 5); setNumber(n => n + 1);` from `0` renders `6`; with `setNumber(42)` after them, `42`.
  - Derived from the corpus algorithm, not shown as a page: order B, updater before value, from `0` gives `5`; the scoreboard gives `Home: 3` for `addTwo(); addPoint();` and `Home: 2` for `addPoint(); addTwo();`: `unconfirmed`.
- **Example Step**: Adds `addTwo` with `setScore(score + 2)` to `src/components/Scoreboard.jsx`, uses it in the `+2` handler, writes the `+3` handler as `addTwo(); addPoint();`, swaps it to `addPoint(); addTwo();`, and finally rewrites `addTwo` as `setScore(s => s + 2)`. No new page element.
- **Code names**: `addTwo`, `setScore(score + 2)`, `setScore(s => s + 2)`, `addPoint`, `addTwo(); addPoint();`, `addPoint(); addTwo();`, `Home: 3`, `Home: 2`, `setNumber(number + 5)`, `setNumber(n => n + 1)`, `setNumber(42)`, `setState(5)`, `setState(n => 5)`, `getFinalState`, `baseState`, `queue`, `finalState`
- **Visual idea**: Two queues side by side, A and B, each walked from `0`, with the "replace with 2" slip cutting off the running result in B.

### Principle 5: An Updater Runs Later, During the Render, So It Must Be Pure; Use One When Several Updates Are Queued
- **Handle**: `pure-updater-and-when`
- **Rule**: React calls an updater during the next render, not on the click, and in `<StrictMode>` development calls it twice and keeps one result, so an updater only calculates and returns the next value from its parameter, with no setters, logs, or outside changes; reach for an updater when the next value depends on the previous one and more than one update of the same state can be queued before the render, while one update per click works with a plain value.
- **Opening Essence**:
  - **Furniture-free snippet**: `setCount(c => { console.log('adding'); return c + 1; });` next to `console.log('adding'); setCount(c => c + 1);`. Under `<StrictMode>` in development, the first prints `adding` twice per click and the second once (`unconfirmed`); the count rises by one in both.
  - **Human image**: the updater is a recipe card handed to the kitchen; the cook may read it twice to check it, so the card may only say how to cook, never "and ring the bell".
  - **Exact nuance of confusion to state out loud**:
    1. The updater is written inside the handler, so it looks like handler code that runs on the click, but it is NOT the same thing: it runs during the next render, like the component body, under the purity rules of Lesson 14.
    2. With one update per click, `setScore(score + 1)` and `setScore(s => s + 1)` give the exact same result, because React updates the state before the next click; the difference shows only when several updates are queued.
- **Root Distinction**:
  - *Junior blurred view*: "Always use the updater, it is the safe version," or "never bother with it."
  - *Senior grounding*: the updater is needed when updates of the same state stack up in one event; when it is used, it must be a pure calculation, because React calls it during render and may call it twice.
- **Real Beginner Mistake (events, in order)**:
  1. The developer wants a Console line for every point and writes `addPoint` as `setScore(s => { console.log('Point for Home'); return s + 1; })`.
  2. In development with `<StrictMode>`, the user clicks `+3`.
  3. The Console shows `Point for Home` six times instead of three.
  4. The developer fears the points are counted twice and looks at the board: `Home: 3`, correct, because React keeps one result of each pair.
  5. The developer moves `console.log('Point for Home')` into `addPoint`, before `setScore(s => s + 1)`.
  6. The user clicks `+3`: the Console shows `Point for Home` three times, and the board shows `Home: 3`.
- **Interview Depth**:
  - `react.dev`: "Updater functions run during rendering, so **updater functions must be pure** and only *return* the result. Don't try to set state from inside of them or run other side effects. In Strict Mode, React will run each updater function twice (but discard the second result) to help you find mistakes."
  - `useState` Troubleshooting: "**Only component, initializer, and updater functions need to be pure.** Event handlers don't need to be pure, so React will never call your event handlers twice."
  - `<DeepDive>` "Is using an updater always preferred?": "There is no harm in it, but it is also not always necessary"; React "always makes sure that for intentional user actions, like clicks," the state "would be updated before the next click", so a click handler never starts with a "stale" value; updaters help "if you do multiple updates within the same event".
  - Writing an updater every time the state is calculated from its previous value is a reasonable team habit; state calculated from another state variable points to a reducer (`Q27 #use_reducer`).
  - The `react.dev` request counter: after `await delay(3000)`, `setPending(pending - 1)` uses the click's value and shows `-1`; `setPending(p => p - 1)` works "in relation to its *latest* state rather than what the state was at the time of the click". Batching around `await` is `Q75 #batching_internals`.
  - `nextScore` (Lesson 15) and the updater do different jobs: the variable gives the handler the new value to use; the updater lets several queued updates build on each other.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any line that calls the updater twice; `addPoint` passes it to `setScore` once.
    - **Who supplies it**: React in development under `<StrictMode>`, which calls each updater a second time during render and discards one result.
    - **What JavaScript and React do**:
      1. The click runs the `+3` handler; three updaters wait in the queue, and no `console.log` inside them has run yet.
      2. The handler returns; React renders `Scoreboard` and walks the queue.
      3. Each updater is called twice; each call prints `Point for Home` and returns `s + 1`.
      4. React keeps one result of each pair, so the walk still goes `0`, `1`, `2`, `3`.
      5. `useState` returns `3`, and React commits `Home: 3`; the production build calls each updater once.
- **React Does**:
  - From the corpus: in Strict Mode, each updater runs twice in development and one result is discarded; event handlers are never called twice; production is not affected.
  - The number of `Point for Home` lines (six in development under `<StrictMode>`, three in the production build, three after the fix) is `unconfirmed`, as is whether the second line of each pair appears dimmed with React DevTools installed.
  - The corpus names no Console warning for a log inside an updater: `unconfirmed`.
- **Example Step**: Puts `console.log('Point for Home')` inside the updater of `addPoint` in `src/components/Scoreboard.jsx`, then moves it into `addPoint` before `setScore(s => s + 1)`. No new page element; the finished page has `+1`, `+2`, and `+3`, all built on updaters.

## Interview Points
1. Setting state does not change the variable in the running render; it adds an update to a queue and requests a new render.
2. Batching: React waits until all code in the event handler has run, then processes every queued update in one render, so several setter calls, for one or several state variables, give one render and no half-finished screens; each click is handled separately.
3. A setter given a value adds "replace with that value" to the queue; because every call in a handler reads the same snapshot, three `setCount(count + 1)` calls queue the same number and the count rises by one.
4. A setter given a function adds an updater to the queue; during the next render React calls each updater with the pending state, the result of the updates before it, so three `setCount(c => c + 1)` calls add three.
5. React walks the queue in order from the current state: a value replaces the running result and an updater builds on it, so mixed calls depend on their order.
6. Updaters run during rendering, so they must be pure; in Strict Mode development React calls each one twice and discards one result.
7. You need an updater when the next value depends on the previous one and more than one update of the same state is queued before the next render; with one update per click a plain value works, because React updates state before the next click; always writing updaters is a reasonable habit, and state calculated from other state points to a reducer.
