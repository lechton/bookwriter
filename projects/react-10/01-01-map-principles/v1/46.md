# Q46 Principle Map (River Version v1): How to Choose Between a Framework and a Build Tool

- **Version**: River Version v1, skills `v10.6`
- **Bank row**: 46 of `questions/questions.md`
- **Topic tag**: `#project_setup` | `❱❱ MORE`
- **Interview question**: How do you choose between a full-stack framework and a standalone build tool?
- **Bank hook**: You need to architect a production React application today. When does a full-stack framework like Next.js justify its complexity, and when is a standalone Vite SPA the superior engineering choice?
- **Syllabus card**: `01-01-map/46.md` exists and was read. This map keeps its scope limit: no Server Components, no Server Functions, no streaming, and no new teaching of `createRoot`. One part of its Friction is changed, see Open Issues 1.

## Scope

This lesson covers:
- What React itself does not decide. react.dev home page: "React is a library. It lets you put components together, but it doesn't prescribe how to do routing and data fetching."
- What a build tool gives: it turns JSX into JavaScript, packs the files into a bundle, runs a development server, and gives a build command (build-a-react-app-from-scratch.md, Step 1). It starts as "a client-only, single-page app (SPA)" with no routing and no data fetching (same page, Step 2).
- What the user and a crawler receive from a client-only app: an HTML file whose root is the empty `<div id="root"></div>` (createRoot.md, Note).
- What a full-stack framework adds on top of a build tool: routing, data loading in the router before the page renders, code splitting per route, and HTML made on the server or at build time, chosen per route (creating-a-react-app.md; sunsetting-create-react-app.md, "Why we Recommend Frameworks").
- The three framework start commands on react.dev, and the three build tools, each named with its command.
- When a build tool is the right choice, in react.dev's own words, and what that choice costs.
- Create React App: deprecated on February 14, 2025, and not a choice for a new app.

## Start of the Lecture

- **Opening Essence of the chapter** (a choice made before the first line of code, seen on a real screen, so it opens in plain words, then the smallest code):
  1. The screen: a product page in an online shop. It shows a title, `Blue Sneakers`, and a price, `$49`.
  2. The user copies the page link and pastes it into a chat app to send to a friend.
  3. The chat app shows a link preview card. On the card the title reads `Shop`, the same for every product in the shop, and the name `Blue Sneakers` is missing.
  4. The friend opens the link on a phone with a slow connection. The page stays blank, then shows `Loading...`, and only then `Blue Sneakers`.
  5. The question this screen raises for the developer: the page looks right on the developer's computer, so what did the chat app and the phone receive?
  6. The answer in one line: they received the HTML file of the app, and in an app made with a build tool alone that file holds only `<div id="root"></div>`. The product exists only after the JavaScript has loaded and run.
- **The confusion to say out loud**: *"It may look the same, or work the same at first, but it is NOT the same thing!"*
  - In the developer's browser, the product page made with Vite and the product page made with a framework look the same.
  - The HTML file that leaves the server is not the same. With Vite alone it is empty. With a framework that renders the route on the server or at build time, it already holds `Blue Sneakers`.
- **Key idea to remember**: React draws components. It does not decide how the first HTML is made, how URLs map to pages, or when data is loaded. A framework decides these for us. A build tool leaves them to our own code.
- **What is at stake for the user**:
  1. A shared link shows the wrong title, because social media crawlers usually do not run JavaScript (MDN, SSR glossary).
  2. The user waits for the whole bundle, then waits again for the product data, before seeing the product.
  3. A link to one product opens the shop's home page when the app keeps the current page in state instead of in the URL.
- **Where readers usually go wrong**:
  1. They think a framework always needs a server. react.dev: "Full-stack frameworks do not require a server."
  2. They think server rendering is only for search engines. react.dev: "Server Rendering is not just for SEO."
  3. They start a new app with `npx create-react-app`, which react.dev deprecated.
- **Theme**: a team must pick, before the first line of code, the tool that decides what the first HTML holds, how pages get URLs, and when data loads.
- **Ways** (developers really choose between these when they start a React app):
  1. A full-stack framework: Next.js App Router (`npx create-next-app@latest`), React Router v7 (`npx create-react-router@latest`), or Expo for native apps (`npx create-expo-app@latest`). Fits: a new app or website, and react.dev's rule of thumb, "if your app needs routing, you would probably benefit from a framework".
  2. A build tool, starting from scratch: Vite (`npm create vite@latest my-app -- --template react-ts`), Parcel (`npm install --save-dev parcel`), or Rsbuild (`npx create-rsbuild --template react`). Fits, in react.dev's words: "your app has constraints not well-served by existing frameworks, you prefer to build your own framework, or you just want to learn the basics of a React app".
  3. Adding React to part of an existing page, such as a page made with Rails: a build tool such as Vite, and `createRoot` on one element of that page (add-react-to-an-existing-project.md). Fits: the rest of the site already exists in another technology.
  4. Not a way: Create React App. react.dev: "Should I use Create React App? No. Create React App has been deprecated."
- **Example page**: the product page above.
  - Why chosen: every reader has pasted a shop link into a chat and seen a preview card, and every reader has waited on a slow phone. A public product page is where developers really meet this choice at work: the page must show its name to people and to crawlers before any JavaScript runs. Two lines of content, a name and a price, are the fewest parts that show the empty HTML. A home page with one link, `Blue Sneakers`, is added only in Principle 3, because a URL problem needs two pages.
  - Pages considered and rejected:
    1. A blog article: also fits, but its text is long, and the lecture skill asks for the shortest real content.
    2. A dashboard behind a login: the case where Vite alone is the right choice. It appears only in Principle 6, as react.dev's own example, "an internal admin tool", in plain words and one short code block. It is not built.
    3. A counter or a form: they look the same with either tool, so the choice never shows on the screen.
    4. A landing page with no data: it shows the empty HTML, but not the late data or the URLs.
  - Files of the build tool version: `index.html` (with `<title>Shop</title>` and `<div id="root"></div>`), `main.jsx` (as in Lesson 07), `App.jsx` (the product page), `api.js` (a stand-in server whose `getProduct()` waits one second, then gives `{ name: 'Blue Sneakers', price: 49 }`).
  - Files of the framework version: one route file with a `loader` and a component, as react.dev's blog shows it. Its file name and folder in React Router are `unconfirmed`, see Open Issues 3.
- **Older facts the reader needs**:
  - Vite's `index.html` holds only `<div id="root"></div>` until `main.jsx` runs, and Vite turns JSX into JavaScript: Lesson 07.
  - `npm run dev` starts Vite's development server; `vite build` and `npm run build` make the files for production: Lessons 07 and 15.
  - `useState`: Lesson 12. `&&`: Lesson 10. `onClick`: Lesson 11.
  - Fetching in an Effect, showing `Loading...` until the data arrives: Lessons 32 and 33.
  - Props, reading `{ loaderData }` in the parameter list: Lessons 08 and 09.

## Principles

### Principle 1: A Build Tool Turns the JSX Files into One Page

- **Rule**: a build tool such as Vite turns JSX into JavaScript, packs the files into bundles, runs a development server, and makes production files with a build command; it does nothing else for the app.
- **Move**: Smallest code first. The reader has used a build tool since Lesson 07, so one command and the files it makes show the idea.
- **Opening Essence**:
  - The smallest code: `npm create vite@latest my-app -- --template react-ts`, then `npm run dev`.
  - The confusion to say out loud: *"Yes, it is the exact same thing!"* The project this book has used since Lesson 07, with `index.html`, `main.jsx`, and Vite, is the "build a React app from scratch" path of react.dev.
  - Key idea: the build tool prepares our files for the browser. Routing, data fetching, and server rendering are not in it.
- **Root Distinction**:
  - Junior: "Vite is how you make a React app, so Vite gives me everything an app needs."
  - Senior: Vite gives JSX, bundles, a development server, and a build command; every other decision is ours.
- **Simplest version**:
  - `npm create vite@latest my-app -- --template react-ts` (react.dev's own command; `react-ts` means React with TypeScript).
  - `npm run dev` while writing code; `npm run build` for production.
- **Words to teach**:
  - Build tool: a program that packages and runs source code. react.dev: "These build tools provide features to package and run source code, provide a development server for local development and a build command to deploy your app to a production server." Provided by Vite, Parcel, or Rsbuild. Needed when the reader runs the first command.
  - Library: React's own name for itself. react.dev home page: "React is a library. It lets you put components together, but it doesn't prescribe how to do routing and data fetching." Needed to explain why the build tool and React leave routing and data fetching open.
  - Single-page app, SPA: an app that loads one HTML document and changes its content with JavaScript (MDN, SPA glossary). react.dev: the build tools "start off with a client-only, single-page app (SPA)". Needed when the reader sees that Vite's app has one `index.html`.
  - Deprecated: no longer recommended, kept only so old apps keep working. react.dev, for Create React App: "Create React App will continue working in maintenance mode". Needed in the Real beginner mistake.
  - Known words: Vite, `index.html`, `main.jsx`, `npm run dev`, `vite build` (07), `npm run build` (15).
  - Helper words: `react-ts`, TypeScript. Parcel and Rsbuild, each with its command, named only.
- **Side by side**:
  - "With `npm create vite@latest`" and "with `npx create-react-app my-app`".
  - Verdict: they look the same at first, both give a working page with JSX and a development server, but they are NOT the same thing.
  - Reason: Create React App is deprecated and has "no active maintainers" (sunsetting-create-react-app.md); Vite is one of the three build tools react.dev lists today.
- **Surprises**: none. Every file the command makes is the setup of Lesson 07.
- **Where did that come from?**:
  - `my-app`: the folder name we choose; the command creates the project inside it.
  - `--template react-ts`: tells Vite which starting files to copy. The extra `--` passes the option through `npm create` to Vite: `unconfirmed`, Vite's documentation is not in the corpus.
- **Real beginner mistake**:
  1. A developer follows an older tutorial and runs `npx create-react-app my-app`.
  2. The terminal shows an error that Create React App is deprecated.
  3. The developer either ignores it and starts an app on a tool with no active maintainers, or searches for a replacement.
  4. react.dev's answer: start with a framework, or with Vite, Parcel, or Rsbuild.
- **Interview depth**:
  - Why Create React App existed: in 2016 there was "no clear way to build a new React app", and it combined several tools "into a single recommended configuration" (sunsetting-create-react-app.md).
  - Why it was deprecated: no active maintainers, and existing frameworks already solve its limits.
  - Existing Create React App apps: react.dev links migration guides to a framework or to a build tool.
  - For React Native from scratch, the bundler is Metro, which "lacks many features when compared to the tools here" (build-a-react-app-from-scratch.md).
- **React does**:
  - Terminal, running `npx create-react-app` (sunsetting-create-react-app.md, quoted exactly; the blog shows it as an error line):
    - `create-react-app is deprecated.`
    - `You can find a list of up-to-date React frameworks on react.dev`
    - `For more info see: react.dev/link/cra`
    - `This error message will only be shown once per install.`
  - Terminal, running `npm run build` in a Vite app: the names of the files in `dist/`: `unconfirmed`, the lab prints them under "Vite messages" with `--prod`.
  - Page and Console: nothing new; the page is the starting page of the template: `unconfirmed`, not checked in the lab, which starts from its own template.
- **Example step**: none yet; the commands stand alone before the product page.
- **Code names**: `npm create vite@latest my-app -- --template react-ts`, `npm run dev`, `npm run build`, `my-app`, `react-ts`, `npx create-react-app my-app`, `create-react-app is deprecated.`, `npm install --save-dev parcel`, `npx create-rsbuild --template react`, `dist/`

### Principle 2: The First HTML Holds Only an Empty div

- **Rule**: in a client-only app, the HTML that the server sends holds only `<div id="root"></div>`; the user sees a blank page and a crawler sees no content until the JavaScript loads and runs.
- **Move**: Steps for a surprise. The page looks complete in the developer's browser, while the chat app's preview card shows `Shop`.
- **Opening Essence**:
  - The real screen and action: the `Blue Sneakers` product page; the user pastes its link into a chat app.
  - The confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* The page the user sees after the JavaScript runs, and the HTML file the server sends, are two different things.
- **Root Distinction**:
  - Junior: "the page shows `Blue Sneakers`, so the page contains `Blue Sneakers`."
  - Senior: the HTML file contains an empty root; `Blue Sneakers` is added later by JavaScript in the browser.
- **Simplest version**:
  - `index.html`: `<title>Shop</title>` in the head, `<div id="root"></div>` in the body.

### Principle 3: A Page Kept in useState Gives Every Product the Same Link

- **Rule**: an app that picks its page with `useState` has one URL for every page, so a shared link always opens the first page; a router gives each page its own URL.
- **Move**: Side by side. Both versions switch pages on a click; only one changes the address bar.
- **Opening Essence**:
  - The real screen and action: the shop's home page lists one product, `Blue Sneakers`. The user clicks it, the product page appears, and the user copies the link from the address bar.
  - The confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* With `useState` and with a router, the click shows the product page. Only with a router does the link lead back to it.
- **Root Distinction**:
  - Junior: "the click shows another page, so the app has two pages."
  - Senior: the app has two pages for the user only when each one has its own URL.
- **Simplest version**:
  - With `useState`, react.dev's own example: `const [route, setRoute] = useState('home');`, `{route === 'home' && <Home />}`, `{route === 'product' && <Product />}`.
  - With a router, react.dev's own example: `createBrowserRouter([{ path: '/', element: <Home /> }, { path: '/products/1', element: <Product /> }])`.
- **Words to teach**:
  - Routing: react.dev: "Routing determines what content or pages to display when a user visits a particular URL." Needed when the reader copies the link.
  - Router, route: the code that maps each URL to a part of the app, and one such pair of a URL and a page (build-a-react-app-from-scratch.md, "You need to set up a router to map URLs to different parts of your app."). Needed at the same moment.
  - Known words: `useState` (12), `&&` (10), `onClick` (11).
  - Helper words: `createBrowserRouter`, `RouterProvider`, `path`, `element`, from React Router, shown only as react.dev's example; their API is not taught.
- **Side by side**:
  - "With `useState('home')`" and "with `createBrowserRouter`".
  - Verdict: NOT the same thing.
  - Reason: react.dev's own comment on the first is "Routing in state does not create URLs", and on the second "Each route has it's own URL" (sunsetting-create-react-app.md, quoted with its spelling).
- **Surprises**:
  1. The user opens the shop at `/` and clicks `Blue Sneakers`.
  2. `setRoute('product')` runs, and the product page appears.
  3. The address bar still reads the shop's home URL.
  4. The user sends that link to a friend.
  5. The friend's app starts with `useState('home')`, so the friend sees the home page, not the sneakers.
- **Where did that come from?**:
  - `route`, `setRoute`: the state variable and its setter from `useState('home')` (Lesson 12).
  - `Home`, `Product`: our own components, imported from their files (Lesson 05).
  - `createBrowserRouter`, `RouterProvider`: imported from `'react-router'`, a library installed with npm, not part of React.
- **Real beginner mistake**:
  1. A developer on a Vite app needs a second page and keeps the current page in state, because `useState` is the tool already known.
  2. Clicks work, so the code ships.
  3. A user bookmarks a product, or presses the browser's back button.
  4. The bookmark opens the home page. What the back button does here is `unconfirmed`: react.dev does not describe it, and the lab can check it with `page.goBack()` in a `steps.mjs`.
  5. The team installs a routing library, then must also join it to data loading and code splitting by hand, which react.dev calls "essentially build a framework yourself".
- **Interview depth**:
  - react.dev's rule of thumb: "if your app needs routing, you would probably benefit from a framework" (sunsetting-create-react-app.md, "Do I need a framework?").
  - Routers "are usually integrated with data fetching (including prefetching data for a whole page for faster loading), code splitting (to minimize client bundle sizes), and page rendering approaches" (build-a-react-app-from-scratch.md).
  - A router adds complexity in exchange for features: "the routing library adds complexity to the app, but it also adds features that are difficult to implement without it."
  - Routers react.dev suggests for a build tool app: React Router and TanStack Router.
- **React does**:
  - Page in the lab with `useState`: home page, then after `--click "::-p-text(Blue Sneakers)"` the product page: `unconfirmed`, checked in the lab.
  - `--eval "location.pathname"` after the click: `/`: `unconfirmed`, checked in the lab.
  - The router version cannot run in the lab, which has no React Router: see Open Issues 3.
  - Console: no message from our code.
- **Example step**: `App.jsx` gains a home page with one product link and keeps the current page in `route`. A file `Home.jsx` is added: `unconfirmed` whether the lecture splits it out. The router version is shown as a short code block only.

### Principle 4: A Loader Fetches the Product Before the Page Renders

- **Rule**: fetching in an Effect starts only after the bundle has loaded and the page has rendered once; a framework's loader starts the fetch before the route renders, in parallel with downloading the code.
- **Move**: Side by side. The page code is almost the same; only where the fetch starts differs.
- **Opening Essence**:
  - The smallest code: `useEffect(() => { getProduct().then(setProduct); }, []);` next to `export async function loader() { return getProduct(); }`.
  - The confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both show `Blue Sneakers`; the user waits less with the loader.
- **Root Distinction**:
  - Junior: "the data arrives either way, so it does not matter where I fetch it."
  - Senior: in an Effect the fetch waits for the code to download and the component to render; in a loader, the router starts it first.
- **Simplest version**:
  - In an Effect: the `App.jsx` of Principle 2.
  - With a loader, react.dev's own shape: `export async function loader() { return getProduct(); }` and `export default function Product({ loaderData }) { return <><h1>{loaderData.name}</h1><p>${loaderData.price}</p></>; }`
- **Words to teach**:
  - Network waterfall: react.dev: "Network waterfalls are caused by fetching data when your app renders instead of in parallel while the code is downloading." Each step waits for the one before it. Needed when the reader counts the waits in the Effect version.
  - Loader: a function exported next to a route component; the router calls it to get the route's data. react.dev: "On initial load, the router can fetch the data immediately before the route is rendered." Provided by the framework's router. Needed when the reader sees the second version.
  - `loaderData`: the prop through which the route component receives what the loader returned (react.dev's example). Who passes it: the framework's router.
  - Known words: `useEffect`, `.then`, `Loading...` (32, 33), `async`, `await` (41), props (08), the parameter list `{ loaderData }` (09), `export default` (05).
  - Helper words: `export async function`.
- **Side by side**:
  - "With `useEffect`" and "with `loader`".
  - Verdict: NOT the same thing.
  - Reason: react.dev's comments on its own examples: "Fetching data in a component causes network waterfalls" and "Fetching data in parallel while the code is downloading".
- **Surprises**:
  1. The friend opens the product link.
  2. With `useEffect`: the browser downloads the HTML, then the bundle; React renders `Loading...`; only then does the Effect start `getProduct()`; one second later `Blue Sneakers` appears.
  3. With a loader: the router starts `getProduct()` before the route renders, while the code is still downloading, so the two waits overlap.
  4. The product appears sooner with the loader, though the stand-in server still takes one second: the exact gain is `unconfirmed` and not measurable in the lab.
- **Where did that come from?**:
  - `loaderData`: not written in our page; the framework's router passes it as a prop, holding what `loader` returned (react.dev's example).
  - `loader`: never called by our code; the router finds the exported function by its name and calls it. That the name must be exactly `loader`: `unconfirmed`, React Router's documentation is not in the corpus.
- **Real beginner mistake**:
  1. A team on a Vite app fetches every page's data in `useEffect`, as Lesson 33 showed.
  2. A page grows: the product loads, then its reviews component renders and fetches its own data.
  3. Each fetch waits for the one before, and the user sees one `Loading...` after another.
  4. react.dev names this a network waterfall and points to a framework's data fetching or a client-side cache.
- **Interview depth**:
  - synchronizing-with-effects.md: "Effects don't run on the server." and "If you use a framework, use its built-in data fetching mechanism."
  - Without a framework, react.dev suggests TanStack Query, SWR, or RTK Query, and Apollo or Relay for GraphQL (build-a-react-app-from-scratch.md): Lesson 60.
  - Code splitting with `React.lazy` can add a second waterfall, because "the code is not fetched until the component renders"; a router's `lazy` option avoids it (sunsetting-create-react-app.md): named only, Lesson 70.
  - The loader trades complexity for speed: "this requires correctly configuring the loaders in your app and trades off complexity for performance."
- **React does**:
  - Page with `useEffect`: `Loading...` first, then `Blue Sneakers` and `$49`: `unconfirmed`, checked in the lab.
  - Page with a loader: no `Loading...` text on first load: `unconfirmed`, cannot run in the lab.
  - Console: no message from our code.
- **Example step**: no change to the Vite files. The route file with `loader` and `Product` is shown as a short code block of the framework version.
- **Code names**: `useEffect`, `getProduct`, `setProduct`, `loader`, `export async function loader()`, `Product`, `loaderData`, `loaderData.name`, `loaderData.price`, `Loading...`, `Fetching data in a component causes network waterfalls`, `Fetching data in parallel while the code is downloading`

### Principle 5: A Framework Puts the Product Name into the HTML

- **Rule**: a framework can render a route on the server or at build time, so the HTML that leaves the server already holds the page's content; it chooses this per route, and it does not require a server.
- **Move**: Side by side. The two HTML files of the same product page differ in one place: what sits inside the root.
- **Opening Essence**:
  - The smallest code: the HTML file of each version, `<div id="root"></div>` next to `<div id="root"><h1>Blue Sneakers</h1><p>$49</p></div>`.
  - The confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* In the browser, both show `Blue Sneakers`. Only the second file shows it to a crawler and to a user whose JavaScript has not loaded yet.
- **Root Distinction**:
  - Junior: "a framework means a server, and a server means a bill."
  - Senior: a framework can send finished HTML from a server, or make it once at build time, or send an SPA like Vite does; the choice is per route.
- **Simplest version**:
  - Vite's HTML file: `<div id="root"></div>`.
  - The framework's HTML file: `<div id="root"><h1>Blue Sneakers</h1><p>$49</p></div>`. The exact markup a framework sends, with its scripts and attributes: `unconfirmed`.
- **Words to teach**:
  - Server-side rendering, SSR: making the HTML on the server and sending it to the browser (MDN, SSR glossary). Needed at the second HTML file.
  - Static site generation, SSG: making the HTML files at build time, so they can be served from a CDN with no server (MDN, SSG and SSR glossaries; react.dev, build-a-react-app-from-scratch.md). Needed when the reader asks whether a server is required.
  - Full-stack framework: react.dev: "These recommended frameworks support all the features you need to deploy and scale your app in production." The blog: tools "that integrate build tools, rendering, routing, data fetching, and code splitting are known as 'frameworks'". Needed when the reader sees what the framework did that Vite did not.
  - Per route: react.dev: "these frameworks allow you to add server-side rendering on a per-route basis, when it makes sense for your use case." Needed when the reader asks whether the whole app must change.
  - Known words: `<div id="root"></div>` (07), `<h1>`, `<p>` (02).
  - Named only: hydration, `hydrateRoot` (104), React Server Components (108), static export, CDN.
- **Side by side**:
  1. "With Vite alone" and "with a framework that renders the route on the server".
     - Verdict: NOT the same thing.
     - Reason: the first sends an empty root; the second sends the product in the HTML. MDN, SSR glossary: crawlers "can easily read the content without needing to execute JavaScript".
  2. "With server-side rendering" and "with static site generation".
     - Verdict: NOT the same thing.
     - Reason: SSR makes the HTML for every request; SSG makes it once at build time. react.dev: a Terms of Service page or documentation can be static, "while a page with a content feed might perform best with server-side rendering".
- **Surprises**:
  1. The team moves the shop to a framework and keeps the product page code.
  2. The user pastes the product link into a chat app.
  3. The crawler downloads the HTML file, which now holds `Blue Sneakers`.
  4. The preview card can show the product name. Whether the card reads the `<h1>` or only `<title>` and `<meta>` tags: `unconfirmed`, not described in the corpus; per-page titles are Lesson 121.
  5. On a slow phone, the friend sees `Blue Sneakers` before the bundle loads; clicks start to work only after the JavaScript loads (hydrateRoot.md: "The user will spend some time looking at the server-generated HTML before your JavaScript code loads.").
- **Where did that come from?**:
  - The finished HTML: the framework calls React on the server or during the build, with the data from the loader, and writes the result into the file (createRoot.md Note; react-dom/server). Our code does not do it.
  - `createRoot`: not written in a framework app; react.dev: "If you use a framework, it might do this call for you." With server HTML, the framework uses `hydrateRoot` instead: named only, Lesson 104.
- **Real beginner mistake**:
  1. A team building an internal dashboard hears "framework" and thinks "server".
  2. The team picks Vite to avoid paying for a server.
  3. Months later, the dashboard gains public pages that must show their content to crawlers.
  4. react.dev's Note says the opposite of step 1: the recommended frameworks support CSR, SPA, and SSG, and "can be deployed to a CDN or static hosting service without a server".
- **Interview depth**:
  - react.dev: frameworks "allow you to start with a client-only app, and if your needs change later, you can opt-in to using server features on individual routes without rewriting your app."
  - Server rendering costs: "Generating pages on the server incurs additional cost and takes time to generate which can increase Time to First Byte (TTFB)" (sunsetting-create-react-app.md). Lesson 156.
  - Server rendering "generally sends less JavaScript to the client, and a full HTML document which produces a faster First Contentful Paint".
  - Next.js App Router "fully implements the official React Server Components specification" and is "the most complete implementation" (creating-a-react-app.md): named only, Lesson 108.
  - A build tool can also do SSR or SSG, by hand: react.dev links Vite's SSR guide and notes "SSR can be very complex to set up and maintain".

## Interview Points

- React is a library: it puts components together but does not decide routing, data fetching, or how the first HTML is made.
- A build tool such as Vite, Parcel, or Rsbuild turns JSX into JavaScript, bundles the code, runs a development server, and has a build command; it starts as a client-only single-page app.
- In a client-only app, the HTML file holds only `<div id="root"></div>`: the user sees a blank page until the JavaScript runs, and social media crawlers usually see no content.
- Keeping the current page in `useState` creates no URLs; a router maps each URL to a page.
- Fetching in an Effect waits for the bundle and the first render, which causes network waterfalls; a framework's loader fetches before the route renders, in parallel with the code download.
- A full-stack framework joins the build tool, routing, data fetching, code splitting, and rendering on the server or at build time, chosen per route.
- Frameworks do not require a server: they support CSR, SPA, and SSG on a CDN or static hosting.
- Server rendering is not only for SEO; it also shows content before the JavaScript loads.
- react.dev recommends a framework for a new app: Next.js App Router, React Router v7, or Expo for native apps; "if your app needs routing, you would probably benefit from a framework".
- A build tool fits a client-only app such as an internal admin tool, React inside part of an existing page, a team that builds its own framework, or learning; its cost is building an ad hoc framework later.
- Create React App was deprecated on February 14, 2025, and is not a choice for a new app.
