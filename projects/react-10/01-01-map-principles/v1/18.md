# Q18 Principle Map (River Version v1): Rendering Lists with Keys
- **Version**: River Version (`v1`)
- **Bank Row**: `questions/questions.md` row 18, Version 4
- **Topic Tag**: `#rendering_lists` | `❱ CORE`
- **Interview Question**: *How do you render a list from an array, and why does React demand a stable key on every item?*

## Authorized Scope
- Turning an array of data into an array of JSX elements with JavaScript's `map()`, and placing that array inside the markup, where React shows each element as a sibling.
- The arrow function inside `map()`: the short form returns the element by itself, and the curly-brace form returns nothing unless it writes `return`.
- The Console error React shows for a list without keys, and what a `key` is: a string or a number that names one item among its siblings, so React can match each item between renders.
- Where the key sits: on the outermost element written directly inside the `map()` call; after a list row is moved into its own component, on that component's tag in the list, never inside the row component; on `<Fragment key={...}>` when one item gives several elements, because `<>...</>` takes no key.
- Why `key` is not a prop: React keeps it for itself and never puts it in the row component's `props`, so a row that needs the same value receives it again under another name, such as `id`.
- Choosing a stable key: an ID that comes with the data, from a database or made once when the item is created; the array index, which React also uses when no key is given, moves to another item when an item is inserted at the top, deleted, or reordered; a key made during render, such as `Math.random()`, never matches between renders and rebuilds every row.
- The two rules of keys from `react.dev`: unique among siblings, and never changing.
- `filter()` before `map()` named as one of the ways to build the list, with no principle of its own.
- Out of scope: adding, removing, inserting, and reordering items in a state array, `[newEmail, ...emails]`, `filter()` for deleting, and `[...list].reverse()` (`Q19 #state_arrays`, used here as a Preview only to put one new email at the top), controlled inputs with `value` and `onChange` (`Q20 #controlled_inputs`), which values belong in state (`Q22 #state_structure`), passing a function down so a row can tell the list to delete it (`Q23 #callback_props`), using a `key` outside lists to reset a component's state, such as `<Chat key={to.id} />` (`Q25 #component_identity`), the full reconciliation rules for keys, duplicate keys, and the ghost rows they leave (`Q61 #keys_and_reconciliation`), rendering ten thousand rows (`Q62 #virtualization`), skipping re-renders of rows with `memo` (`Q55 #memo`), and the `Children` API for reading `children` as a list (Dropped).

## General Concepts Introduction (Runway Plan)
- **Opening Essence**:
  - **Furniture-free snippet**: three names written by hand, `<li>Anna</li>`, `<li>Ben</li>`, `<li>Cara</li>`, inside `<ul>`; next to it the same names as data, `const names = ['Anna', 'Ben', 'Cara'];` and `<ul>{names.map(name => <li>{name}</li>)}</ul>`. Then the same list with `key`: `const people = [{ id: 1, name: 'Anna' }, { id: 2, name: 'Ben' }, { id: 3, name: 'Cara' }];` and `<li key={person.id}>{person.name}</li>`.
  - **Human image**:
    1. The everyday meaning of **map** in `map()`: a stamp pressed once on every item of a row of boxes; each box goes in, one stamped card comes out, and the row of cards keeps the same order and length.
    2. The `react.dev` image for **key**: files on a desktop with no names, known only as the first file, the second file, and so on; delete one, and the second file becomes the first. A file name stays with its file wherever it moves, and a key stays with its item.
    3. A name tag at a meeting: the tag is for the organizer who seats the guests, not something the guest reads out loud, which is why the row component never receives its own `key`.
  - **Exact nuance of confusion to state out loud**:
    1. Three `<li>` tags written by hand and `names.map(name => <li>{name}</li>)` are the exact same thing on the page: the same three list items in the same order.
    2. `key={person.id}` sits on the tag beside the other attributes, so it looks like a prop, but it is NOT the same thing as a prop: React takes it for itself and the component never receives it.
    3. A list keyed by the index and a list keyed by an ID look the same and work the same at first, but they are NOT the same thing: the difference shows only when an item is added at the top, removed, or moved.
    4. First show that an item can be named by its position or by its own ID, then lay out both lists before and after a new item arrives at the top, and only then state which one keeps each tick beside its own email.

- **Ways**:

## Principle Thread
- **Anchor**: React turns an array of data into rows with `map()`, and it tells the rows apart only by their keys; a key is React's own name tag for one item, kept out of `props`, and it must come with the item so it never moves to another one.
- **Axis**: From making the rows, to naming them, to who can read the name, to which name to choose:
  1. `map()` turns the array into an array of elements, and React shows them, then asks for a key (Principle 1).
  2. The key names each item among its siblings and sits on the element directly inside `map()`, which after extracting a row component is the component's tag (Principle 2).
  3. React keeps the key for itself, so the row component never receives it and gets the same value again as another prop (Principle 3).
  4. The key must come with the data and never change: an index moves to another item when a new email arrives at the top, and a random key rebuilds every row (Principle 4).
- **Why This Axis**: Cause before effect. The rows must exist before anything can name them (Principle 1). The key is then written and placed (Principle 2), and only once it sits on the `<EmailRow>` tag can the reader ask whether the row can read it (Principle 3). The choice of key comes last because its cost is seen only when the list changes, which needs the state and the `Check mail` button that Principle 4 adds.

## Principles

### Principle 1: `map()` Turns the Array of Data into an Array of Rows, and React Shows Them
- **Handle**: `map-array-to-rows`
- **Rule**: When many rows share one shape and differ only in their data, keep the data in an array and write `emails.map(email => <li>...</li>)` inside the markup: `map()` returns a new array with one element per item, in the same order, and React shows the elements as siblings; with a curly-brace body the function must write `return`, or every row is `undefined` and nothing shows.
- **Opening Essence**:
  - **Furniture-free snippet**: Way A, three tags by hand: `<ul><li>Anna</li><li>Ben</li><li>Cara</li></ul>`. Way B, the same names as data: `const names = ['Anna', 'Ben', 'Cara'];` then `<ul>{names.map(name => <li>{name}</li>)}</ul>`. Then the two bodies side by side: `name => <li>{name}</li>` and `name => { <li>{name}</li> }`.
  - **Human image**: the stamp pressed once on every box in a row: three names go in, three list items come out, in the same order.
  - **Exact nuance of confusion to state out loud**:
    1. Way A and Way B are the exact same thing on the page: three `<li>` inside one `<ul>`, in the same order.
    2. `map()` looks like it changes the array, but it does NOT: `names` still holds three strings, and `map()` hands back a second array of three elements.
    3. `name => <li>{name}</li>` and `name => { <li>{name}</li> }` look almost the same, but they are NOT the same thing: the first returns the element, the second runs a block that returns nothing.
- **Root Distinction**:
  - *Junior blurred view*: "A list on the page means writing a row for each email in the markup."

### Principle 2: The Key Names Each Item Among Its Siblings, and It Sits on the Element Directly Inside `map()`
- **Handle**: `key-names-each-item`
- **Rule**: Give every element written directly inside a `map()` call a `key`, a string or a number that no other sibling has, such as `key={email.id}`; when the row moves into its own component, the key goes on the `<EmailRow>` tag inside `map()`, not on the `<li>` inside `EmailRow`; when one item gives several elements, the key goes on `<Fragment key={...}>`, because `<>...</>` takes no key.
- **Opening Essence**:
  - **Furniture-free snippet**: `const people = [{ id: 1, name: 'Anna' }, { id: 2, name: 'Ben' }, { id: 3, name: 'Cara' }];` then `people.map(person => <li key={person.id}>{person.name}</li>)`. Then the two places a key could be written once the row is a component: `people.map(person => <Person key={person.id} name={person.name} />)` versus `function Person({ name }) { return <li key={...}>{name}</li>; }`.
  - **Human image**: the desktop files of `react.dev`: with no names they are the first file, the second, the third; delete one and every later file changes its number. A key is the file name, and it stays with its file.
  - **Exact nuance of confusion to state out loud**:
    1. The key is written on the tag like `className`, but it does not appear on the page or, as far as the corpus says, in the Elements panel; it is a note for React.

### Principle 3: `key` Is Not a Prop: React Keeps It, and the Row Receives the Same Value Again Under Another Name
- **Handle**: `key-is-not-a-prop`
- **Rule**: React takes `key` off the tag for itself and never puts it in the component's `props`, so `EmailRow` cannot read its own key; when the row needs the same value, such as an `id` for its tick box and label, the list passes it a second time as an ordinary prop, `<EmailRow key={email.id} id={email.id} ... />`.
- **Opening Essence**:
  - **Furniture-free snippet**: `<Person key={1} name="Anna" />` and `function Person(props)`: `props.name` is `'Anna'`, and `props.key` is `undefined`. Next to it `<Person key={1} id={1} name="Anna" />`: `props.id` is `1`.
  - **Human image**: the meeting name tag of the Runway: the organizer reads it to seat each guest, and the guest never hears it; if the guest must say the name, the organizer tells it to the guest separately.

    1. `key={email.id}` and `id={email.id}` sit side by side on the same tag and look like two props, but they are NOT the same thing: `id` reaches `props`, `key` stays with React.
    2. Writing the same value twice looks like repetition, and it is the exact same value, but it serves two readers: `react.dev` calls it separating "app logic from hints to React".

### Principle 4: A Stable Key Comes with the Data: an Index Moves to Another Email, and a Random Key Rebuilds Every Row
- **Handle**: `stable-key-from-data`
- **Rule**: Use a key that comes with the item and never changes, such as the ID a mail server gives each email, or an ID made once when the item is created; the index, which React also uses when no key is given, belongs to a position, so when a new email arrives at the top every index moves to another email and the tick the browser keeps stays at its position; a key made during render, such as `Math.random()`, never matches between renders, so React rebuilds every row and every tick is lost.
- **Opening Essence**:
  - **Furniture-free snippet**: the list `Anna`, `Ben`, `Cara` before and after `Zoe` arrives at the top. By position: before, `0` Anna, `1` Ben, `2` Cara; after, `0` Zoe, `1` Anna, `2` Ben, `3` Cara. By ID: before, `1` Anna, `2` Ben, `3` Cara; after, `4` Zoe, `1` Anna, `2` Ben, `3` Cara. Then the two ways to make an ID with a random function: `{ id: crypto.randomUUID(), name: 'Zoe' }` when the item is created, versus `key={Math.random()}` on the tag inside `map()`.
  - **Human image**: the desktop files again: a file known as the second file becomes the third file when a new one is put first; a file known by its name keeps it.
  - **Exact nuance of confusion to state out loud**:
    1. First state that an item can be named by its position or by its ID, then lay out both lists before and after `Zoe` arrives, and only then trace which name stays with `Anna`.
    2. `key={index}` and `key={email.id}` look the same and work the same at first, and the Console is silent for both, but they are NOT the same thing: after the insert, key `0` is the new email, while key `101` is still the dentist.
    3. `crypto.randomUUID()` when the email is created and `Math.random()` inside `map()` both use a random function, but they are NOT the same thing: the first is made once and stored with the item, the second is made again on every render.
- **Root Distinction**:
  - *Junior blurred view*: "Any unique value silences the warning, so the index is a fine key."

## Interview Points
1. Keep the data in an array and call `map()` inside the markup; `map()` returns a new array of elements, one per item, and React shows them as siblings; a curly-brace arrow body must write `return`.
2. React then asks for a `key` on every element directly inside `map()`: a string or a number that names the item among its siblings, so React can match each item between renders.
3. The key sits on the element that `map()` returns: on the component tag in the list after a row is extracted, and on `<Fragment key>` when an item gives several elements, because `<>...</>` takes no key.
4. `key` is not a prop: React keeps it as a hint for itself, the component never receives it, and a row that needs the value gets it again as another prop such as `id`.
5. Keys must be unique among siblings and must not change, so the best key is an ID that comes with the data, from a database or made once when the item is created.
6. The index, React's default when no key is given, belongs to a position: after an insert at the top, a delete, or a reorder, it points at another item, and inputs or state inside the rows end up beside the wrong item.
7. A key made during render, such as `Math.random()`, never matches, so React recreates every row and DOM node, which is slow and loses user input; the index is acceptable only for a list that never changes order.
