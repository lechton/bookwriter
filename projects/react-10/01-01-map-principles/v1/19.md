# Q19 Principle Map (River Version v1): Updating Arrays in State
- **Version**: River Version (`v1`)
- **Bank Row**: `questions/questions.md` row 19
- **Topic Tag**: `#state_arrays` | `❱ CORE`
- **Interview Question**: *How do you add, remove, insert, and reorder items in a state array?*

## Authorized Scope
- Treating every array held in state as read-only: an array is a kind of object, so changing it in place (a mutation) and passing the same array to the setter does not re-render, because the setter compares the next value with the current one using `Object.is`, and an array changed from inside is still the same array.
- The two groups of array operations from `react.dev`: the ones that change the array they are called on (`push`, `unshift`, `pop`, `shift`, `splice`, `sort`, `reverse`, and assignment by index such as `arr[0] = 'bird'`), and the ones that return a new array (`[...arr]` spread, `concat`, `filter`, `slice`, `map`).
- Adding: `[...queue, song]` at the end and `[song, ...queue]` at the start.
- Removing: `queue.filter(s => s.id !== id)`; the old array is left as it was.
- Inserting in the middle: `[...queue.slice(0, insertAt), song, ...queue.slice(insertAt)]`, and the `slice` versus `splice` trap.
- Reordering: copy the array first with `[...queue]`, then change the copy (swap two items by index, or `sort` and `reverse`); `sort` and `reverse` change the array they are called on and hand back that same array.
- Changing one item: `map` returns the untouched items as they are and a new object for the changed one, `{ ...song, liked: !song.liked }`; copying the array is shallow, so the copied array points at the same song objects, and changing an item inside a copy changes the item the old array still holds.
- Local mutation of an array we have just created is fine (the copy in reordering), because no other code points at it yet.
- JavaScript's newer `toSorted`, `toReversed`, and `toSpliced` named as methods that return a new array; Immer named as an optional helper, with no API taught.
- Out of scope: object spread and the nested object copy (`Q17 #state_objects`, recalled), rendering lists and keys (`Q18 #rendering_lists`, recalled), the full rules of controlled inputs (`Q20 #controlled_inputs`), which values belong in state and whether a `previous` copy for Undo should be state (`Q22 #state_structure`), moving each row into its own component that calls a function from the list (`Q23 #callback_props`), reducers (`Q27 #use_reducer`), skipping re-renders with `memo` (`Q55 #memo`), drag and drop and duplicate keys (`Q61 #keys_and_reconciliation`), ten thousand rows (`Q62 #virtualization`), and the React Compiler (`Q63 #react_compiler`).

Way A: `names.push('Dan'); setNames(names);`, the page keeps three names. Way B: `setNames([...names, 'Dan']);`, the page shows four. Then the `react.dev` table as two columns: avoid `push`, `unshift`, `pop`, `shift`, `splice`, `sort`, `reverse`, `arr[i] = ...`; prefer `[...arr]`, `concat`, `filter`, `slice`, `map`, and copy first before sorting.
  - **Human image**:
    1. Lesson 17's barcode at the library: React scans the array as one box and never reads the list inside; handing back the same box with a name written into it is the same barcode, so React files nothing new.
    2. Two kinds of tools on a desk: a pen that writes on the original sheet (`push`, `splice`, `sort`) and a photocopier that hands back a new sheet with the change on it (spread, `filter`, `slice`, `map`).
    3. The everyday meaning of **splice**: film or rope cut and joined again, the original reel itself; the everyday meaning of **slice**: taking a slice to keep, here a copy of part of the sheet while the sheet stays whole.
    4. The everyday meaning of **shallow** from Lesson 17, now for a list: a photocopy of a guest list is a new sheet, but the guests on it are the same people.

    1. `names.push('Dan'); setNames(names);` and `setNames([...names, 'Dan']);` look like the same change, and both arrays do hold four names, but they are NOT the same thing: the first hands React the array it already holds, the second hands it a new one.
    2. Arrays look different from objects, with square brackets and methods instead of fields, but for React they are the exact same thing as the objects of Lesson 17: a box compared by identity, never by contents.
    3. `slice` and `splice` look like one word with a typo, but they are NOT the same thing: `slice` copies, `splice` changes the original.
    4. `queue.sort()` looks like it returns a new sorted array, because it does return an array, but it is NOT a new one: it returns the same array it just changed.

- **Ways**: Several ways to give the setter a new array, and when each fits:
  1. Spread with the new item, `[...queue, song]` or `[song, ...queue]`: adding at either end; `concat` is the same job by method.
  2. `filter`: removing one or more items by a test.
  3. `slice` with spread: inserting at a position.
  4. `map`: replacing or changing one or more items, returning the others as they are.
  5. Copy first with `[...queue]`, then `sort`, `reverse`, or assignment by index on the copy: reordering; `toSorted` and `toReversed` do both steps in one call.
  6. Immer's `useImmer`: lets mutating-looking code produce the copies; named only.

## Principle Thread
- **Anchor**: React decides whether an array in state changed by asking whether the setter received a different array, never by reading its items; so every add, remove, insert, reorder, and change builds a new array and leaves the old one exactly as it was, down to the item objects inside it.
- **Axis**: From why a changed array is invisible, through one recipe per operation, to the items inside the copy:
  1. A mutated array is the same array, so React skips the render; adding with spread gives a new array (Principle 1).
  2. Removing with `filter` gives a new array and leaves the old one whole, which `Undo` can hand back (Principle 2).
  3. Inserting in the middle with `slice` and spread, never `splice` (Principle 3).
  4. Reordering on a copy: copy first, then swap, sort, or reverse the copy (Principle 4).
  5. A copied array still points at the same items, so changing one item means `map` with a new object for that item (Principle 5).
- **Why This Axis**: Cause before effect. The reader must first see why React ignores a pushed array (Principle 1) before any recipe has a reason. Removing comes next because `filter` is the plainest new-array method and its untouched old array makes `Undo` possible (Principle 2). Inserting needs `slice`, which the `slice` and `splice` trap separates from the mutating method (Principle 3). Reordering introduces the copy that may then be changed, the local mutation (Principle 4). Only once the reader trusts a copy can its limit be shown: the copy is new, the items are not (Principle 5).

## Principles

### Principle 1: A Changed Array Is the Same Array, So Adding Means a New Array
- **Handle**: `new-array-to-add`
- **Rule**: When a song must be added to the queue, never call `push` or `unshift` on the state array; build a new array with spread, `[...queue, song]` for the end or `[song, ...queue]` for the start, and pass it to the setter, because the setter compares arrays by identity with `Object.is` and skips the render when it receives the array it already holds.
- **Opening Essence**:
  - **Furniture-free snippet**: `const [names, setNames] = useState(['Cara', 'Anna', 'Ben']);` Way A: `names.push('Dan'); setNames(names);`. Way B: `setNames([...names, 'Dan']);`. ### Principle 2: `filter` Removes a Song into a New Array and Leaves the Old Array Whole
- **Handle**: `filter-to-remove`
- **Rule**: To remove a song, keep every song except that one with `queue.filter(s => s.id !== id)` and pass the result to the setter; never use `splice`, `pop`, or `shift` on the state array; because `filter` leaves the old array untouched, that old array can be kept and handed back by `Undo`.
- **Opening Essence**:
  - **Furniture-free snippet**: `const names = ['Cara', 'Anna', 'Ben'];` then `const fewer = names.filter(name => name !== 'Anna');`: `fewer` is `['Cara', 'Ben']`, and `names` is still `['Cara', 'Anna', 'Ben']`. Next to it `names.splice(1, 1);`: `names` itself is now `['Cara', 'Ben']`.
  - **Human image**: a sieve that lets every item through except the one we pick out, into a new bowl, while the first bowl stays full.
  - **Exact nuance of confusion to state out loud**:
    1. `names.filter(name => name !== 'Anna')` and `names.splice(1, 1)` both end with `Cara` and `Ben`, but they are NOT the same thing: `filter` hands back a new array and leaves `names` with three names, `splice` changes `names`.
    2. "Remove" sounds like taking something out of the array, but with `filter` nothing is taken out of anything: a new array is made without it.
- **Root Distinction**:
  - *Junior blurred view*: "Removing a song means deleting it from the array."
  - *Senior grounding*: removing means making a new array without the song; the old array stays whole, which is what makes the change visible to React and what lets `Undo` bring the old list back.

### Principle 3: Inserting in the Middle Is Two Slices and the New Song Between Them
- **Handle**: `slice-to-insert`
- **Rule**: To put a song at a position, build `[...queue.slice(0, insertAt), song, ...queue.slice(insertAt)]`: the songs before the position, the new song, then the songs from the position on; `slice` copies part of the array and leaves it whole, while `splice`, one letter longer, changes the array itself.
- **Opening Essence**:
  - **Furniture-free snippet**: `const names = ['Cara', 'Anna', 'Ben'];` `names.slice(0, 1)` is `['Cara']`, `names.slice(1)` is `['Anna', 'Ben']`, and `[...names.slice(0, 1), 'Dan', ...names.slice(1)]` is `['Cara', 'Dan', 'Anna', 'Ben']`, while `names` is unchanged. ### Principle 4: Reordering Happens on a Copy: Copy First, Then Move, Sort, or Reverse the Copy
- **Handle**: `copy-then-reorder`
- **Rule**: Methods that reorder, `sort` and `reverse`, and assignment by index all change the array they work on, so make a copy first, `const next = [...queue];`, change the copy, and pass the copy to the setter; changing the copy is a local mutation and is fine, because no other code points at it yet.
- **Opening Essence**:
  - **Furniture-free snippet**: `const names = ['Cara', 'Anna', 'Ben'];` Way A: `const sorted = names.sort();`: `sorted` is `['Anna', 'Ben', 'Cara']`, and `names` is that same sorted array. Way B: `const sorted = [...names].sort();`: `sorted` is sorted, `names` is still `['Cara', 'Anna', 'Ben']`. Then `names.toSorted()`, which does both steps at once.
  - **Human image**: rearranging the photocopy of a seating plan, never the plan pinned to the wall; once the photocopy is ours alone, we may write on it as much as we like.
  - **Exact nuance of confusion to state out loud**:
    1. `names.sort()` and `[...names].sort()` both hand back the sorted names, but they are NOT the same thing: the first sorts `names` itself and returns it, the second sorts a new copy.
    2. `const next = queue;` and `const next = [...queue];` look like two ways to copy, but they are NOT the same thing: the first is a second name for the same array, the second is a new array.
    3. Writing `next[index - 1] = ...` on a copy looks like the forbidden mutation, and it is the exact same kind of line, but it is safe here: the copy was made a line earlier and React has never seen it.
- **Root Distinction**:
  - *Junior blurred view*: "Mutation is forbidden, so the swap must be written without ever assigning an item."
  - *Senior grounding*: the rule is about arrays React already holds; a copy we just made may be changed freely before it is handed to the setter.

### Principle 5: A Copied Array Still Holds the Same Songs, So Changing One Song Means a New Song Object
- **Handle**: `copy-the-changed-item`
- **Rule**: Copying the array is shallow: the new array points at the same song objects as the old one, so never change a field of a song inside a copy; use `queue.map(s => s.id === id ? { ...s, liked: !s.liked } : s)`, which returns every other song as it is and a new object for the changed song, so the old array, the one `Undo` keeps, still holds the song as it was.
- **Opening Essence**:
  - **Furniture-free snippet**: `const people = [{ id: 1, name: 'Anna', seen: false }];` `const copy = [...people];` then `copy[0].seen = true;`: `people[0].seen` is now `true` as well, and `copy[0] === people[0]` is `true`. Next to it `const next = people.map(p => p.id === 1 ? { ...p, seen: true } : p);`: `next[0].seen` is `true`, `people[0].seen` is still `false`.
  - **Human image**: the photocopy of a guest list is a new sheet, but the guests on it are the same people; giving a guest a hat through the copy gives the hat to the guest on the original list too.
  - **Exact nuance of confusion to state out loud**:
    1. `copy[0].seen = true` after `[...people]` and `map` with `{ ...p, seen: true }` both give a new array whose first person is seen, and both re-render, but they are NOT the same thing: the first changes the person the old array still holds, the second makes a new person.
    2. The copy and the original look like two separate lists of people, but the people are the exact same objects in both; only the sheet is new.
    3. This is the exact same rule as the nested object of Lesson 17, one level up: copy every level on the path to the change, here the array and the one song.
- **Root Distinction**:
  - *Junior blurred view*: "I copied the array, so everything inside it is mine to change."

## Interview Points
1. Arrays in state are read-only: an array is an object, and React compares the next state with `Object.is`, so a mutated array passed back to the setter is the same array and the render is skipped.
2. Split the methods into two groups: `push`, `unshift`, `pop`, `shift`, `splice`, `sort`, `reverse`, and assignment by index change the array; spread, `concat`, `filter`, `slice`, and `map` return a new one.
3. Add with spread, `[...arr, item]` at the end and `[item, ...arr]` at the start.
4. Remove with `filter`, which leaves the old array whole, so past versions can be kept, as for Undo.
5. Insert with two slices and the new item between them, `[...arr.slice(0, i), item, ...arr.slice(i)]`; `slice` copies, `splice` mutates.
6. Reorder on a copy: `[...arr]` first, then `sort`, `reverse`, or a swap by index on the copy, which is a local mutation; `toSorted` and `toReversed` do it in one call.
7. Copying an array is shallow, so to change one item use `map` and return a new object for that item, `{ ...item, field: value }`, and the item unchanged otherwise; Immer can write this with mutating syntax.
