# Q23 Principle Map (River Version v1): How a Child Tells Its Parent to Change State

- **Version**: River Version (`v1`), written under `skills/v10.6`
- **Bank Row**: `questions/questions.md` row 23
- **Topic Tag**: `#callback_props` | `❱ CORE`
- **Interview Question**: *How does a child component notify its parent or trigger state updates using callback props?*

## Scope

Covered here:
- State is private to the component that declares it, so a child cannot call its parent's setter, and props are read-only, so a child cannot change what it receives.
- A prop can hold a function. The parent writes a handler next to its state and passes it on the child's tag, such as `onRemove={handleRemove}`.
- On a built-in component such as `<button>`, `onClick` is a browser event. On our own component, `onRemove` is an ordinary prop, named by us, that holds a function.
- The child calls the function with the value the parent needs, `() => onRemove(guest.id)`. The parent's own code calls its own setter, React renders the parent again, and the new list comes down as props.
- This is the React docs' "inverse data flow". The data flow stays one-way: only a function call goes up, and the new data still comes down.
- A child can send up a value that only the child has, such as the text typed in its own box, with `onAdd(name)`, and it can run its own code before the call.
- The naming habit from the docs: `on` and a capital letter for the prop, `handle` and the event for the function.

## Start of the Lecture

**Opening Essence of the chapter**:
- The naked idea is the shape of a way of working, so it opens in plain words before any code, as Examples 3 and 8 of [Opening Essence](../../skills/v10.6/opening-essence/SKILL.md) open.
- Everyday case: a phone number left with someone so they can call you back. You cannot walk into their office and change their papers. When something happens, you call the number, say what happened, and the owner of the papers makes the change. The word "callback" comes from this: a function handed over so it can be called later.
- The two things named as two forms of one thing, as the Back to the basics table asks: both are props written on the child's tag. The one difference: `name="John"` carries a value for the child to show, and `onRemove={handleRemove}` carries a function for the child to call.
- Key idea: the parent owns the state and the only code that changes it. The child gets a function as a prop and calls it when the user acts. The child never changes the parent's state itself.
- What is at stake: the user clicks Remove on a guest and nothing happens, or the row disappears while the line above still says `3 guests`.
- Where readers usually go wrong: they picture the child reaching up and changing the parent's list, or they think data now flows both ways. Only a function call goes up; the new list still comes down as props.
- No look-alike pair for the chapter opening. The look-alike pairs live in the principles.

**Theme**: a party guest list keeps its guests in the list component's state, but each Remove button sits inside a separate row component that cannot reach that state.

**Ways** (developers really choose between these when a child must change the parent's state):
1. Pass a handler the parent wrote, `onRemove={handleRemove}`, and let the child call it with a value. The docs' usual way: `onDeleteTodo={handleDeleteTodo}` in `updating-arrays-in-state.md`.
2. Pass the setter itself, `onFilterTextChange={setFilterText}`. The docs do this in Step 5 of `thinking-in-react.md`. Fits when the child sends exactly the next value.
3. Pass an arrow with a fixed value, `onShow={() => setActiveIndex(0)}`. The docs do this in `sharing-state-between-components.md`. Fits when each child tag is written by hand.
4. Pass one `dispatch` function, or put the functions in context, when many components deep in the tree need them: Lessons 27 to 29, named only.

**Example page chosen for this lesson**: a party guest list. A heading, a count line, a list of three guests with a Remove button on each row, and from Principle 4 a text box with an Add button.

## Principles

### Principle 1: `GuestRow` Cannot Call `setGuests`

- **Rule**: State is private to the component that declares it, so a child component cannot call its parent's setter; the child sees only the props written on its tag.
- **Move**: Steps for a surprise, because the Remove button does nothing on the page while the Console shows an error. Side by side for the row that hides only itself.
- **Opening Essence**:
  - Smallest code, two files: `Parent.jsx` with `const [count, setCount] = useState(0);` and `return <Child />;`, and `Child.jsx` with `return <button onClick={() => setCount(count + 1)}>Add</button>;`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* The button sits inside the parent on the page, but the child's code is a separate function. Being inside on the page does not mean seeing the parent's names.
  - The fact behind it, from Lesson 06: a name created inside one function cannot be seen inside another.
  - What is at stake: a button that does nothing, with the user's click lost.
- **Root Distinction**:
  - Junior: "The row is inside the list on the page, so the row can use the list's setter."
  - Senior: placing a tag inside a parent passes only the props written on that tag; the parent's state and setters stay inside the parent's function.
- **Simplest version**:
  - `Parent.jsx`: `const [count, setCount] = useState(0);` and `<p>{count}</p><Child />`.
  - `Child.jsx`: `<button onClick={() => setCount(count + 1)}>Add</button>`.
  - The user clicks Add, the number stays `0`, and the Console shows a `ReferenceError` for `setCount`. `unconfirmed`.
- **Words to teach**:
  - *state is private to the component that declares it*: React keeps each state variable inside the component that called `useState`; no other component can read it or change it. The React docs: "state is fully private to the component declaring it. The parent component can't change it." Needed when the click on Remove fails.
  - *owns the state*: the docs' word for the one component that holds a state variable and is the only one that can call its setter. Needed to name `GuestList` as the owner of `guests`.
  - Known: a name created in one function is not visible in another, and `ReferenceError`, Lesson 06. Props are read-only, Lesson 08. `useState` and the setter, Lesson 12. `map` and `key`, Lesson 18. `import` and `export default`, Lesson 05. `return null`, Lesson 10.
  - Helper: none.
- **Side by side**:
  - "with `setGuests` inside `GuestRow`" and "with `guest` inside `GuestRow`": NOT the same thing. `guest` is written on the tag, so React passes it in; `setGuests` is not on the tag, so the row has no way to reach it.
  - "with its own `isRemoved` state in `GuestRow`" and, later in Principle 3, "with `onRemove(guest.id)`": it may look the same at first, the row disappears in both, but it is NOT the same thing. Only the second changes `guests`, so only the second changes the count line.
- **Surprises**:
  - With `setGuests` called inside `GuestRow`, the user clicks Remove on Mia and nothing changes on the page:
    1. The user clicks Remove on Mia.
    2. React runs the arrow function given to Mia's button.
    3. The arrow asks for `setGuests`. `GuestRow.jsx` has no such name.
    4. JavaScript throws a `ReferenceError` inside the handler.
    5. The Console shows the error. The page keeps all three rows and the line `3 guests`.
  - With an `isRemoved` state inside `GuestRow`, the user clicks Remove on Mia and the line still says `3 guests`:
    1. The user clicks Remove on Mia.
    2. Mia's row calls its own `setIsRemoved(true)`.
    3. React renders Mia's `GuestRow` again, and it returns `null`. Mia's row disappears.
    4. `guests` inside `GuestList` still holds three guests, because nothing changed it.
    5. The count line, calculated from `guests.length`, still says `3 guests`.
- **Where did that come from?**:
  - `guest` inside `GuestRow`: `GuestList` writes `guest={guest}` on each tag inside `map`, React puts it inside `props`, and the parameter list unpacks it, Lessons 08 and 18.
  - `setGuests` inside `GuestRow`: nobody supplies it. It was created by `useState` inside `GuestList` and stays there.
- **Real beginner mistake** (the React docs' `Accordion`, `sharing-state-between-components.md`):
  1. Each `Panel` keeps its own `isActive` state.
  2. The page should show only one open panel at a time.
  3. The user clicks Show on the second panel.
  4. The first panel stays open, because each panel changes only its own state and the parent cannot influence it.
  5. The docs' fix removes the state from the panels, keeps one `activeIndex` in the parent, and passes `onShow` down. The full fix belongs to Lesson 24.
- **Interview depth**:
  - The tic-tac-toe tutorial: "Since state is private to a component that defines it, you cannot update the `Board`'s state directly from `Square`."
  - `passing-props-to-a-component.md`: when a component needs to change its props, "it will have to 'ask' its parent component to pass it _different props_".
  - State is private both ways: a parent cannot change a child's state either.
  - Writing `props.guest = ...` in development throws a `TypeError`, because React freezes the props object, Lesson 08.
- **React does**:
  - Console, with `setGuests` in `GuestRow`: `Uncaught ReferenceError: setGuests is not defined`. `unconfirmed`; the form matches Lesson 06, and the lab records the exact line.
  - Page, with `setGuests` in `GuestRow`: all three rows and `3 guests` stay on screen. `unconfirmed`. The docs say only that an error thrown during rendering removes the UI, and that error boundaries do not catch errors in event handlers (`reference/react/Component.md`).
  - Page, with `isRemoved` in `GuestRow`: two rows under the line `3 guests`. `unconfirmed`.
- **Example step**:
  - Creates `src/components/GuestList.jsx`: `initialGuests`, `const [guests, setGuests] = useState(initialGuests);`, `<h1>Party Guests</h1>`, `<p>{guests.length} guests</p>`, and a `<ul>` that maps each guest to `<GuestRow key={guest.id} guest={guest} />`.
  - Creates `src/components/GuestRow.jsx`: `<li>{guest.name} <button>Remove</button></li>`.
  - First broken version: the button gets `onClick={() => setGuests(guests.filter(g => g.id !== guest.id))}`.
  - Second broken version, shown side by side: `const [isRemoved, setIsRemoved] = useState(false);`, `if (isRemoved) return null;`, and `onClick={() => setIsRemoved(true)}`.
  - `src/App.jsx` renders `<GuestList />`.

### Principle 2: `onRemove` Carries `handleRemove` Down to the Row

- **Rule**: A prop can hold a function; the parent writes the handler next to its state, passes it on the child's tag, and the child gives it to the built-in component `<button>` through `onClick`.
- **Move**: Side by side, because `name="John"` and `onRemove={handleRemove}` look different and are the same kind of thing, while `onClick` on `<button>` and `onRemove` on `<GuestRow>` look alike and are not. Everyday image for the word "callback".
- **Opening Essence**:
  - Smallest code: `function MyButton({ onSmash }) { return <button onClick={onSmash}>Click me</button>; }` with `<MyButton onSmash={() => console.log('Hello')} />`. The docs use the same name, `onSmash`.
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* `name="John"` and `onSmash={...}` are both props written on the tag. One holds text, the other holds a function.
  - Second confusion: *"It may look the same, but it is NOT the same thing!"* `onClick` on `<button>` is a browser event that React listens for. `onSmash` on `<MyButton>` is just a prop; nothing happens until `MyButton` gives it to a `<button>`.
  - Everyday image: the phone number of the chapter opening. The parent hands its number down; the child keeps it until it needs to call.
- **Root Distinction**:
  - Junior: "Props that start with `on` are special event props that React wires up for me."
  - Senior: on our own component, `onRemove` is an ordinary prop holding a function; only a built-in component such as `<button>` attaches a function to a browser event.
- **Simplest version**:
  - `function MyButton({ onSmash }) { return <button onClick={onSmash}>Click me</button>; }`
  - `<MyButton onSmash={() => console.log('Hello')} />`
  - The user clicks the button, and the Console shows `Hello`. `unconfirmed`.
- **Words to teach**:
  - *event handler prop*: a prop whose value is a function that the child calls when something happens. The React docs' name, in "Passing event handlers as props" and "Naming event handler props". Needed when `onRemove` is written on the tag.
  - *callback prop*: the interview's name for the same thing; react.dev uses it in `useTransition.md`, "such as a callback prop". Needed at the same moment, as the second name.
  - *callback function*: a function passed to other code so that code can call it later. From MDN, wording `unconfirmed`. Needed with the everyday image.
  - *built-in component*: a tag React gives us, such as `<button>` or `<div>`. The docs: "Built-in components like `<button>` and `<div>` only support browser event names like `onClick`." Needed for the second confusion.
  - the naming habit: a prop name starts with `on` and a capital letter, such as `onRemove`; a handler name starts with `handle`, such as `handleRemove`. The docs' convention. Needed when the names are chosen.
  - Known: `onClick={handleClick}` passes a function, Lesson 11. Props unpacked in the parameter list, Lesson 08. `filter`, Lesson 19.
  - Helper: none.
- **Side by side**:
  - "with `name="John"`" and "with `onRemove={handleRemove}`": the exact same thing for React, both are props. The one difference is the value: text to show, or a function to call.
  - "with `onClick` on `<button>`" and "with `onRemove` on `<GuestRow>`": NOT the same thing. React attaches the first to the click event of a real button; the second only arrives in `props`.
- **Surprises**:
  - With `<button onClick={onRemove}>`, the user clicks Remove on Mia and nobody is removed:
    1. The user clicks Remove on Mia.
    2. React calls the function given to the button, which is `handleRemove` itself.
    3. React passes the event object as the only argument, Lesson 11. The docs: "Event handlers receive an **event object** as their only argument."
    4. Inside `handleRemove(id)`, `id` holds the event object, not `1`.
    5. `filter` keeps every guest, because no guest's `id` equals the event object.
    6. `setGuests` receives a new array with all three guests. The page shows three rows and `3 guests`, with no error.
- **Where did that come from?**:
  - `onRemove` inside `GuestRow`: `GuestList` writes `onRemove={handleRemove}` on the tag, React puts it inside `props`, and the parameter list unpacks it.
  - `handleRemove` can call `setGuests`: it is written inside `GuestList`, next to the `useState` line, so it sees `guests` and `setGuests`, Lesson 06.
- **Real beginner mistake** (a prop name that does not match):
  1. `GuestList` writes `onDelete={handleRemove}` on the tag.
  2. `GuestRow` unpacks `{ guest, onRemove }`.
  3. `props` holds `onDelete`, so `onRemove` is `undefined`.
  4. The button gets `onClick={undefined}`, so React attaches no handler.

### Principle 3: `onRemove(guest.id)` Tells the Parent Which Guest

- **Rule**: The child wraps the call in an arrow function and passes the value the parent needs, `() => onRemove(guest.id)`; the parent's handler calls its own setter, React renders the parent again, and the new list comes down as props.
- **Move**: Steps for a surprise, because the click happens in the row and the change shows in a line outside the row. Side by side for `onClick={onRemove}` and `onClick={() => onRemove(guest.id)}`.
- **Opening Essence**:
  - Smallest code: `function Row({ id, onRemove }) { return <button onClick={() => onRemove(id)}>Remove</button>; }` with `<Row id={2} onRemove={handleRemove} />`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* It looks as if the row removes the guest. The row only calls a function; the code that changes the list is the parent's own code.
  - Key idea: data still flows one way. Values go down as props. Only a function call goes up, carrying the id.
- **Root Distinction**:
  - Junior: "The child sends the new data up to the parent, so data now flows both ways."
  - Senior: the child sends only a request with an id; the parent decides the new list, and the new list comes down as props on the next render.
- **Simplest version**:
  - `<button onClick={() => onRemove(id)}>Remove</button>` in `Row`.
  - `function handleRemove(id) { setNames(names.filter(n => n.id !== id)); }` in the parent.
- **Words to teach**:
  - *one-way data flow*: data goes from the parent to the child through props, never back up as props. The React docs, `thinking-in-react.md`: "the data flows down from the top-level component to the ones at the bottom of the tree." Needed at the trace of the click.
  - *inverse data flow*: the docs' name for a child changing the parent's state by calling a function the parent passed down. Step 5 of `thinking-in-react.md`. Needed right after the trace.
  - *two-way data binding*: named only. The docs: "React makes this data flow explicit, but it requires a little more typing than two-way data binding."
  - Known: the arrow function that passes an argument, Lesson 11. A re-render of the parent renders its children again, Lesson 13. `guests.length` calculated during rendering, Lesson 22.
  - Helper: none.
- **Side by side**:
  - "with `onClick={onRemove}`" and "with `onClick={() => onRemove(guest.id)}`": NOT the same thing. The first lets React call `handleRemove` with the event object; the second calls it with the guest's `id`.
- **Surprises**:
  - The user clicks Remove inside Mia's row, and the count line outside the row changes to `2 guests`:
    1. The user clicks Remove on Mia.
    2. React runs the arrow function given to Mia's button.
    3. The arrow calls `onRemove(1)`. `onRemove` is `handleRemove` from `GuestList`.
    4. `handleRemove` calls `setGuests` with a new array of John and Sara.
    5. React renders `GuestList` again. `guests` holds two guests, and the count line shows `2 guests`.
    6. `map` gives two `<GuestRow>` tags, so Mia's row is gone.
    7. `GuestRow` itself changed nothing.
- **Where did that come from?**:
  - `1` inside `handleRemove(id)`: Mia's `GuestRow` supplies it from its own `guest` prop, `guest.id`.
  - `guests` inside `handleRemove`: the `guests` of the render in which `GuestList` passed this function down, Lesson 15.
- **Real beginner mistake** (the React docs' tic-tac-toe, `onSquareClick={handleClick(0)}`):
  1. To pass the id, a developer writes `onRemove={handleRemove(guest.id)}` on the tag inside `map`.
  2. The parentheses call `handleRemove` while `GuestList` renders, once for every guest.
  3. Each call runs `setGuests` during rendering.
  4. Setting state asks React to render `GuestList` again, and that render calls `handleRemove` again.
  5. React stops the loop with an error, and the page shows nothing.
  6. The fix: the parent passes the function, `onRemove={handleRemove}`, and the child adds the id in its own arrow.

### Principle 4: `AddGuest` Sends the Typed Name Up with `onAdd(name)`

- **Rule**: When the value exists only in the child, such as the text typed in its own box, the child passes it as the argument of the callback; the child may run its own code, such as clearing its box, in the same handler.
- **Move**: Smallest code first, because the shape is a new use of the same tool. Steps for a surprise for `setName('')` written before `onAdd(name)`, because readers expect that order to lose the typed name.
- **Opening Essence**:
  - Smallest code, the docs' `AddTodo` shape with simpler names: `function NameBox({ onAdd }) { const [name, setName] = useState(''); ... <input value={name} onChange={e => setName(e.target.value)} /> <button onClick={() => { setName(''); onAdd(name); }}>Add</button> }`.

  - Key idea: each component owns what it knows. The box owns the typing; the list owns the guests. The finished name travels up as an argument.
- **Root Distinction**:
  - Junior: "The parent has to reach into the child's text box to read the name."
  - Senior: the child keeps the typing in its own state and hands the finished name to the parent's function when the user clicks Add.

## Interview Points

1. State is private to the component that declares it, so a child cannot call its parent's setter, and props are read-only, so a child cannot change what it receives.
2. The parent passes a function as a prop, such as `onRemove={handleRemove}`; a prop can hold any JavaScript value, including a function.
3. The child calls that function when the user acts, with the value the parent needs, such as `onRemove(guest.id)` or `onAdd(name)`.
4. The parent's own handler calls its own setter; React renders the parent again and passes the new data down as props.
5. One-way data flow stays intact: data only goes down as props, and only a function call goes up. The React docs call this inverse data flow.
6. On a built-in component such as `<button>`, `onClick` is a browser event; on our own component, `onRemove` is an ordinary prop, and by convention its name starts with `on` and the handler's name starts with `handle`.
7. Pass the function, do not call it: `onRemove={handleRemove(guest.id)}` calls the handler during rendering and ends in "Too many re-renders"; the id goes in the child's arrow, `() => onRemove(guest.id)`.
8. The same callback props connect two siblings once their shared state moves up to the common parent, Lesson 24.
