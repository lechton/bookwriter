## Scope

This lesson covers:
- The automatic reset: after the function passed to `<form action={...}>` succeeds, React resets every uncontrolled field of that form (form.md, "Handle form submission with an action prop"; React 19 blog, "React DOM: `<form>` Actions").
- What "succeeds" means for React: the action finished without throwing. An action that returns an error message, as Lesson 42 taught, has succeeded, so the boxes are emptied while the error line appears.
- Keeping what the user typed when the server says no: the action returns the submitted text in its state, and each box reads it back through `defaultValue`. A reset puts every field back to its default value (MDN, `HTMLFormElement.reset()`), so the box gets the text back.
- The second way to keep text: a controlled box with `value` and `onChange` (Lesson 20). The docs reset only uncontrolled fields.
- `requestFormReset` from `'react-dom'`: the manual reset, for a form submitted without the `action` prop (React 19 blog: "If you need to reset the `<form>` manually, you can call the new `requestFormReset` React DOM API").
- What progressive enhancement needs from a form, as a concept: a real `<form>`, a `name` on every field, a real submit button, and an action the browser can send without JavaScript. What each kind of `action` does when JavaScript has not loaded.

## Start of the Lecture

- **Opening Essence of the chapter** (a way of working seen on a real screen, so it opens in plain words, then the smallest code):
  1. The screen: a Create account form on a website. It has a Username box, an Email box, and a Create account button.
  2. The user types `john` into the Username box and `john@mail.com` into the Email box, then clicks Create account.
  3. About one second later, one line appears under the button: `Username john is taken.`
  4. Both boxes are empty. The email was right, and the user must type it again.
  5. The question this screen raises for the developer: who emptied the boxes? No line of our code empties them.
  6. The answer in one line: React did. After the action finishes without throwing, React resets every uncontrolled box of the form, and a returned error message does not stop it.
- **The confusion to say out loud**: *"It may look the same, or work the same at first, but it is NOT the same thing!"*
  - For the user, `Username john is taken.` is a failure.
  - For React, the action returned a value and did not throw, so the action succeeded, and the form is reset.
- **Key idea to remember**: the reset puts each box back to its default value. To keep the user's text after a refusal, make the text the default value: the action returns it in state, and the box reads it through `defaultValue`.
- **What is at stake for the user**:
  1. After every refusal from the server, the user types the whole form again.
  2. On a slow phone, before the JavaScript has loaded, the Create account button must still send the form. Whether it can depends on the kind of `action` the form has (Principle 5).
- **Where readers usually go wrong**: they think the reset happens only when the account was created. It happens after every action that does not throw.
- **Theme**: a form must clear itself after a success and keep the user's text after a refusal.
- **Ways** (developers really choose between these for the same job, keeping text after a refusal):
  1. Uncontrolled boxes with `defaultValue` read from the state the action returned. Fits: forms built on `<form action>` and `useActionState`, the React 19 way; the form keeps working as plain HTML.
  2. Controlled boxes with `value` and `onChange` (Lesson 20). Fits: the page must change on every keystroke anyway, such as a live hint; React does not reset these boxes.
  3. `onSubmit` with `e.preventDefault()` (Lessons 11 and 40). No automatic reset at all; the code clears the form itself, with `requestFormReset` when it runs inside a Transition. Fits: older forms moved to Actions step by step.
- **Example page**: the Create account form above.
  - Why chosen: every reader has filled a sign-up form and has seen a username refused. It is where developers meet the reset at work: a server check that can say no. Two boxes are the fewest parts that show the loss, because the email box was right and is emptied anyway. One success line, `Welcome, john!`, shows the case where the empty form is what the user wants.
  - Pages considered and rejected:
    1. The newsletter box of Lesson 42: one box only, so the loss of a right field cannot be shown.
    2. The comment box of Lesson 43 and the chat of Lesson 41: the user always wants the box empty after sending, so the reset never hurts.
    3. A checkout address form: too many fields to hold in mind.
    4. A login form: browsers and sites usually clear a refused password on purpose, which blurs the point.
  - Files: `App.jsx` (the form), `api.js` (a stand-in server that waits one second and refuses the username `john`).
- **Older facts the reader needs**:
  - `name` on every box and `formData.get('username')`: Lesson 40.
  - `<form action={fn}>`, the action runs in a Transition, the boxes are reset after success: Lesson 41.
  - `useActionState(signUp, initialState)`, the action receives `previousState` then `formData`, a known error is returned, not thrown: Lesson 42.
  - `defaultValue` gives only the starting text of an uncontrolled box; `value` without `onChange` freezes the box: Lesson 20.
  - Vite's `index.html` holds only `<div id="root"></div>` until `main.jsx` runs: Lesson 07.

## Principles

### Principle 1: A Successful Action Empties the Form

- **Rule**: when the function passed to `<form action={...}>` finishes without throwing, React resets every uncontrolled field of that form.
- **Move**: Smallest code first. The reset is a new fact about code the reader wrote in Lesson 41, and three lines show it.
- **Opening Essence**:
  - The smallest code: one form, one box with `name="username"`, a submit button, an action that only reads `formData.get('username')`.
  - The user types `john` and clicks the button. The box is empty after the action.
  - No real confusion here: this is the case the user wants. The key idea: the reset is React's own step after the action, not a line in our code. What is at stake: a developer who does not know the step cannot explain Principle 2.
- **Root Distinction**:
  - Junior: "the box is empty because the browser sent the form and loaded a new page."
  - Senior: with a function in `action`, the page stays, and React resets the uncontrolled fields after the action succeeds.
- **Simplest version**:
  - `function save(formData) { console.log(formData.get('username')); }`
  - `<form action={save}><input name="username" /><button type="submit">Save</button></form>`
- **Words to teach**:
  - Reset: putting every field of a form back to its default value. Provided by the browser as `form.reset()` (MDN), and called for us by React after an action. Needed when the reader sees the box empty after clicking Save.
  - Automatic reset: React's reset after a successful action, with no line of our code. Provided by React DOM (form.md; React 19 blog). Needed at the same moment.
  - Known words: `<form action={fn}>`, Action (41), `name`, `formData.get()` (40), uncontrolled box (20), Console (01).
  - Helper words: none.
- **Side by side**: none.
- **Surprises**:
  1. The user types `john` and clicks Save.
  2. React calls `save` with the form data. The Console shows `john`.
  3. `save` returns without throwing, so React resets the form.
  4. The box is empty, though no line of the code emptied it.
- **Where did that come from?**:
  - `formData`: React builds it from the submitted form and passes it as the only argument of `save` (form.md, Props). Taught in Lesson 41.
- **Real beginner mistake**:
  1. A developer moves a form from `onSubmit` to `action` (Lesson 41).
  2. The old handler ended with a line that emptied the box by hand.
  3. The developer keeps that line inside the action.
  4. The line does nothing new, because React resets the uncontrolled box anyway.
- **Interview depth**:
  - The reset covers only uncontrolled fields (form.md: "all uncontrolled field elements in the form are reset").
  - The reset happens only for the `action` prop path. With `onSubmit` and `e.preventDefault()`, no automatic reset happens: `unconfirmed`, checked in the lab.
  - A function passed to `formAction` on a `<button>` also resets the form: `unconfirmed`.
  - The form is reset after the action's Transition ends, not at the click: `unconfirmed` beyond the docs' "after the `action` function succeeds".
- **React does**:
  - Page: the box shows `john` while the action runs, then shows nothing.
  - Console: `john`.
  - Elements panel: whether the `<input name="username">` carries a `value` attribute before or after the reset: `unconfirmed`. Whether React writes an `action` attribute on the `<form>` element, and its text: `unconfirmed`, read in the lab with `--elements`.
- **Example step**: none yet; the smallest code stands alone, before the Create account form.
- **Code names**: `save`, `formData`, `formData.get('username')`, `name="username"`, `<button type="submit">`, `Save`, `john`

### Principle 2: A Returned Error Still Empties the Form

- **Rule**: an action that returns an error message has succeeded for React, so the boxes are emptied even while the error line appears.
- **Move**: Steps for a surprise. The page shows the error and the empty boxes together, which no reader expects.
- **Opening Essence**:
  - The real screen and action: the Create account form; the user types `john` and `john@mail.com` and clicks Create account.
  - The confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* A refusal for the user and a success for React.
- **Root Distinction**:
  - Junior: "the server said no, so the action failed, so React keeps the text."
  - Senior: React knows only whether the action threw; a returned error is a normal return value, and the reset follows it.
- **Simplest version**:
  - ``async function signUp(previousState, formData) { const username = formData.get('username'); const error = await createAccount(username); if (error) { return error; } return `Welcome, ${username}!`; }``
  - `const [message, formAction] = useActionState(signUp, '');`
  - `<form action={formAction}><input name="username" /><input name="email" /><button type="submit">Create account</button>{message && <p>{message}</p>}</form>`
- **Words to teach**:
  - Succeed, for an action: the action finished without throwing (form.md: "After the `action` function succeeds"). Provided by React's reading of the action's end. Needed when the reader sees the error line next to empty boxes.
  - Known words: `useActionState`, `previousState`, a known error returned as state (42), `async`, `await` (41), `&&` (10), template literal.
  - Helper words: `includes()` inside `api.js`.
- **Side by side**:
  - "With `return error`" and "with `throw new Error(error)`".
  - Verdict: NOT the same thing.
  - Reason: a returned value becomes the state and the form is reset; a thrown error goes to the nearest Error Boundary (useActionState.md, Caveats and "Handling errors"), and no reset happens: the no-reset part is `unconfirmed`.
- **Surprises**:
  1. The user types `john` in Username and `john@mail.com` in Email, then clicks Create account.
  2. React calls `signUp` with the previous state `''` and the form data.
  3. `createAccount('john')` waits one second and returns `'Username john is taken.'`.
  4. `signUp` returns that text. It did not throw, so for React the action succeeded.
  5. React renders with the new state: the line `Username john is taken.` appears.
  6. React resets the form: both boxes are empty.
  7. The user sees the refusal and an empty form at the same time.
- **Where did that come from?**:
  - `previousState`: React passes the state from the last call, first `''`, as the first argument (useActionState.md). Taught in Lesson 42.
  - `createAccount`: imported from our own `api.js`, the stand-in server. It waits one second with a promise and `setTimeout`, then returns an error text for `john` and `null` for any other name.
  - `message`: the first value `useActionState` returns, equal to what `signUp` returned last.
- **Real beginner mistake**:
  1. The developer returns the error as Lesson 42 taught.
  2. The developer tests with a free username: the welcome line appears and the boxes are empty, which looks right.
  3. The bug report comes later: a user's username was taken, and the email the user typed is gone.
  4. The developer changes `return error` to `throw new Error(error)` to stop the reset.
  5. Without an Error Boundary, what the page shows after the throw: `unconfirmed`, checked in the lab. The useActionState page says a throw cancels queued actions and shows the nearest Error Boundary.
- **Interview depth**:
  - The reset changes the DOM fields only; it does not change the `useActionState` state. The useActionState page: "`useActionState` doesn't provide a built-in reset function."
  - Known errors are returned, unknown errors are thrown (useActionState.md, "Handling errors").
- **React does**:
  - Page after about one second: `Username john is taken.` under the button, both boxes empty.
  - Console: no line from our code; any React warning: `unconfirmed`.
  - Exact timing of the empty boxes against the error line, same render or not: `unconfirmed`, checked in the lab.
- **Example step**: the Create account form appears. Files: `App.jsx` (form, `signUp`, `useActionState`), `api.js` (`createAccount`).
- **Code names**: `App.jsx`, `api.js`, `createAccount`, `signUp`, `previousState`, `formData`, `message`, `formAction`, `useActionState`, `name="username"`, `name="email"`, `Create account`, `john`, `john@mail.com`, `'Username john is taken.'`, `Welcome, john!`

### Principle 3: defaultValue From State Brings the Text Back

- **Rule**: to keep the user's text after a refusal, return the submitted text in the action's state and give each box `defaultValue` from that state; the reset then restores that text.
- **Move**: Side by side. The fix is one prop, and the reader must see the box with `defaultValue={state.email}` next to the box without it.
- **Opening Essence**:
  - The smallest code: `<input name="email" defaultValue={state.email} />`.
  - The confusion to say out loud: *"Yes, it is the exact same thing!"* The reset still runs. A reset puts each box back to its default value (MDN, `reset()`: "restores a form element's default values"), and the default value is now the text the user typed.
- **Root Distinction**:
  - Junior: "I must stop React from resetting the form."
  - Senior: the reset is kept; only the value the reset goes back to changes.
- **Simplest version**:
  - The state is one object: `{ message: '', username: '', email: '' }`.
  - On a refusal: `return { message: error, username, email };`
  - On success: ``return { message: `Welcome, ${username}!`, username: '', email: '' };``
  - `<input name="username" defaultValue={state.username} />` and `<input name="email" defaultValue={state.email} />`
- **Words to teach**:
  - Default value: the text a box goes back to when its form is reset. Provided by the browser (MDN, `HTMLInputElement.defaultValue`, which "reflects the element's `value` attribute"); React's `defaultValue` prop sets it. Needed when the reader asks why the reset now brings the text back.
  - Known words: `defaultValue`, uncontrolled box (20), `useActionState`, initial state (42), object with three keys (17).
  - Helper words: none.
- **Side by side**:
  1. "With `defaultValue={state.email}`" and "without `defaultValue`".
     - Verdict: NOT the same thing.
     - Reason: without it, the default value is empty and the reset empties the box; with it, the reset puts back what the action returned.
  2. "With `defaultValue={state.email}`" and "with `value={state.email}`".
     - Verdict: NOT the same thing.
     - Reason: `value` without `onChange` freezes the box (Lesson 20); the user can no longer type in it.
  3. "With `defaultValue` from state" and "with `value` and `onChange`" (a controlled box, Lesson 20).
     - Verdict: NOT the same thing, though both keep the text after a refusal.
     - Reason: the controlled box is not reset at all (the docs reset only uncontrolled fields) and renders on every keystroke; the `defaultValue` box renders only when the action returns.
- **Surprises**:
  1. The user types `john` and `john@mail.com` and clicks Create account.
  2. `signUp` returns `{ message: 'Username john is taken.', username: 'john', email: 'john@mail.com' }`.
  3. React renders: each box gets the new default value from `state`.
  4. React resets the form: each box goes back to its default value, so the boxes show `john` and `john@mail.com` again.
  5. The user changes `john` to `john7` and clicks again.
  6. `signUp` returns `{ message: 'Welcome, john7!', username: '', email: '' }`.
  7. The default values are now empty, so the same reset empties both boxes.
  8. That steps 3 and 4 happen in this order in React 19.3.1, so the text really comes back: `unconfirmed`, checked in the lab. The docs do not state this order.
- **Where did that come from?**:
  - `state.username` and `state.email`: the object `signUp` returned last time, which `useActionState` gives back as the current state (useActionState.md, Returns).

Objects in state: Lesson 17; the lesson that first used the shorthand: `unconfirmed`.
- **Real beginner mistake**:

- **Interview depth**:
  - The pattern keeps the form uncontrolled, so the boxes cause no render while the user types (Lesson 40).
  - The useActionState page lists other ways to reset state: a reset signal sent to the action, or a `key` that remounts the component (Lesson 25).
  - With a Server Function, the returned state is shown before hydration finishes and `initialState` must be serializable (useActionState.md): named only, Lessons 110 and 137.
- **React does**:

### Principle 4: requestFormReset Asks for the Reset by Hand

- **Rule**: when a form is submitted without the `action` prop, React does not reset it (`unconfirmed`, Open Issues 3); call `requestFormReset(form)` inside the Transition to ask for the same reset (the import from `'react-dom'` and the argument: `unconfirmed`, Open Issues 1).
- **Move**: Side by side. The reader already knows the browser's `form.reset()`, and the new function looks the same.
- **Opening Essence**:
  - The smallest code: `requestFormReset(form);` next to `form.reset();`.
  - The confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both empty the boxes; they differ in when.
- **Root Distinction**:
  - Junior: "a reset is a reset; I call `form.reset()` whenever I want the boxes empty."
  - Senior: `form.reset()` empties the boxes at once, while the action may still be running; `requestFormReset` waits for the Transition, so the boxes change in the same update as the state: the timing is `unconfirmed`.
- **Simplest version**:
  - `function handleSubmit(e) { e.preventDefault(); const form = e.currentTarget; startTransition(() => { formAction(new FormData(form)); requestFormReset(form); }); }`
  - `<form onSubmit={handleSubmit}>`
- **Words to teach**:
  - `requestFormReset`: a React DOM function that resets a form by hand (React 19 blog). Imported from `'react-dom'`: `unconfirmed`, no reference page in the corpus. It takes the form element as its argument: `unconfirmed`. Needed when the reader sees a form submitted with `onSubmit` keep `john7` after the welcome line.
  - Known words: `onSubmit`, `e.preventDefault()`, `e.currentTarget` (11), `new FormData(form)` (40), `formAction` from `useActionState` (42), Transition by name (41).
  - Helper words: `startTransition`, from `'react'`, needed because the useActionState page says the dispatcher "must be called from an Action" and shows it wrapped in `startTransition`. Taught in Lesson 67.
- **Side by side**:
  1. "With `form.reset()`" and "with `requestFormReset(form)`".
     - Verdict: NOT the same thing.
     - Reason: `form.reset()` is the browser's method and runs at once (MDN); `requestFormReset` is React DOM's, and the reset waits for the Transition: the waiting is `unconfirmed`.
  2. "With `<form action={formAction}>`" and "with `<form onSubmit={handleSubmit}>` and `requestFormReset`".
     - Verdict: the exact same thing for the user, the boxes clear after success and come back after a refusal, when `defaultValue` from state is kept: `unconfirmed`, checked in the lab.
     - Reason: the second way asks by hand for the reset the first way gets from React.
- **Surprises**:
  1. The form uses `onSubmit` with `e.preventDefault()` and calls `formAction` inside `startTransition`, without `requestFormReset`.
  2. The user types `john7` and clicks Create account.
  3. The line `Welcome, john7!` appears, and the box still shows `john7`: `unconfirmed`, checked in the lab.
  4. Nothing reset the form, because no form `action` ran.
  5. With `requestFormReset(form)` added inside the same `startTransition`, the box is empty after the welcome line: `unconfirmed`, checked in the lab.
- **Where did that come from?**:
  - `form`: `e.currentTarget`, the `<form>` element whose `onSubmit` is running (Lesson 11). Saved in a variable before `startTransition`.
  - `formAction`: the dispatcher returned by `useActionState` (Lesson 42), here called by our code with a `FormData` instead of being passed to `<form action>`.
- **Real beginner mistake**:
  1. The developer calls `form.reset()` right after starting the action, to empty the boxes quickly.
  2. The boxes empty at once, before the server answers.
  3. The server answers `Username john is taken.`
  4. The user's text is already gone, and `defaultValue` from state cannot help, because nothing resets the form again after the state changes.
- **Interview depth**:
  - Calling `requestFormReset` outside a Transition or an Action: React reports an error; its exact text is `unconfirmed`.
  - The docs' own examples call `formRef.current.reset()` inside an action (form.md, "Optimistically updating form data"; useFormStatus.md): that empties the box at once, which a chat box wants (Lesson 44).
  - Whether React's automatic reset is the same request made for us: `unconfirmed`.
- **React does**:
  - Page with `onSubmit` and no `requestFormReset`, after success: `Welcome, john7!` and the box still shows `john7`: `unconfirmed`.
  - Page with `requestFormReset`, after success: `Welcome, john7!` and the boxes empty: `unconfirmed`.
  - Console, `requestFormReset` called outside a Transition: message `unconfirmed`.
- **Example step**: `App.jsx` changes: `<form action={formAction}>` becomes `<form onSubmit={handleSubmit}>`, with imports of `startTransition` from `'react'` and `requestFormReset` from `'react-dom'`. `api.js` does not change.
- **Code names**: `requestFormReset`, `'react-dom'`, `startTransition`, `'react'`, `handleSubmit`, `e.preventDefault()`, `e.currentTarget`, `form`, `form.reset()`, `new FormData(form)`, `formAction`

### Principle 5: name and a Submit Button Keep the Form Working Without JavaScript

- **Rule**: a form keeps working before its JavaScript loads only when it is real HTML, a `<form>` with a `name` on every field and a submit button, and its action is one the browser can send by itself: a URL, or a Server Function from a framework.
- **Move**: Side by side. Two forms look the same on the screen and behave differently when JavaScript is missing.
- **Opening Essence**:
  - The real screen and action: the same Create account form on a phone with a slow connection. The page is visible, the JavaScript bundle is still loading, and the user clicks Create account.
  - The confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* `<form action="/signup">` and `<form action={formAction}>` look the same on the screen. Without JavaScript, only the first one sends the form.
- **Root Distinction**:
  - Junior: "the form has an action, so the button sends it."
  - Senior: a URL action is read by the browser; a function action exists only after React's JavaScript has run.
- **Simplest version**:
  - With a URL: `<form action="/signup" method="post"><input name="username" /><button type="submit">Create account</button></form>`
  - With a function: `<form action={formAction}>` with the same box and button.
- **Words to teach**:
  - Progressive enhancement: a page gives every user a basic version that works, and adds the richer version when the browser can run it (MDN glossary: "a baseline of essential content and functionality to as many users as possible"). Provided by the way we build the page, not by one API. Needed when the reader asks what the slow-phone user gets.
  - JavaScript bundle: the JavaScript file of the app that the browser downloads (react.dev docs words: "before the JavaScript bundle loads"). Needed at the slow-phone click.
  - What progressive enhancement needs from a form, the parts the browser can use alone: `<form>`, `name` on every field (input.md: the `name` is the key in the form data), `<button type="submit">`, an `action` the browser can send.
  - Known words: `name` (40), `action` with a URL and with a function (41), `<div id="root"></div>` (07), POST (41).
  - Named only: server-side rendering (102), hydration (104), Server Function (110), `permalink`, replay of early submits (137).
  - Helper words: `method="post"`.
- **Side by side**:
  1. "With `action="/signup"`" and "with `action={formAction}`", JavaScript not loaded.
     - Verdict: NOT the same thing.
     - Reason: with a URL, "the form will behave like the HTML form component" (form.md) and the browser sends the named fields itself; with a function, React must be running to call it.
  2. "With a function from our own code in a Vite app" and "with a Server Function in a framework that renders HTML on the server".
     - Verdict: NOT the same thing.
     - Reason: a Vite app sends only `<div id="root"></div>`, so before `main.jsx` runs there is no form on the page at all (Lesson 07); with a Server Function, the form "can be submitted before the JavaScript bundle is loaded" (use-server.md), and React "will also automatically replay form submissions entered before hydration finishes" when `useActionState` is used (server-functions.md).
- **Surprises**:
  1. The Vite version of the Create account form is opened with JavaScript turned off.
  2. The browser receives `index.html` with only `<div id="root"></div>`.
  3. `main.jsx` never runs, so React never renders the form.
  4. The user sees a blank page, not a form that fails: `unconfirmed`, checked in the lab with JavaScript turned off.
- **Where did that come from?**:
  - `method="post"`: an HTML attribute of `<form>` that tells the browser to send the data with POST (MDN `<form>`). With a function in `action`, React uses POST "regardless of value of the `method` prop" (form.md, Caveats).
  - `/signup`: a URL on our own server that would receive the form; this lesson has no server, so it stays an example in code only.
- **Real beginner mistake**:
  1. A developer builds the Create account button as a `<div onClick={...}>`, or leaves `name` off a box, because the React code reads the values from state.
  2. Everything works while JavaScript runs.
  3. The team later renders the page on the server so it appears fast on slow phones (Lesson 102).
  4. A user clicks before the bundle loads. The `<div>` is not a submit button, so nothing is sent; a box without `name` has no key in the form data, so its value is missing: `unconfirmed` for the missing key, input.md says only that the `name` "will be used as a key in the form data".
- **Interview depth**:
  - form.md: "When `<form>` is rendered by a Server Component, and a Server Function is passed to the `<form>`'s `action` prop, the form is progressively enhanced."
  - form.md lists three conditions for showing a submit error before the JavaScript bundle loads: a Client Component renders the form, the action is a Server Function, and `useActionState` shows the message.
  - useActionState.md: with `permalink`, if the form is submitted before the bundle loads, "the browser will navigate to the specified permalink URL rather than the current page's URL"; once the page is interactive, the parameter "has no effect".
  - The same `name` and submit button that make the form work without JavaScript are what `FormData` reads with JavaScript (Lesson 40), so they cost nothing extra.
  - Progressive enhancement and graceful degradation are related but not the same (MDN glossary): named only.
- **React does**:
  - Page with JavaScript off in the Vite lab: blank: `unconfirmed`.
  - Elements panel with JavaScript off: `<div id="root"></div>` and nothing inside: `unconfirmed`.
  - Elements panel with JavaScript on, the `action` attribute React writes on a `<form>` whose `action` is a function: `unconfirmed`.
- **Example step**: no new project file. The URL form appears only as a short code block for comparison. The lesson's Vite form keeps the parts progressive enhancement needs that it already has: `<form>`, `name` on both boxes, `<button type="submit">`.
- **Code names**: `action="/signup"`, `method="post"`, `action={formAction}`, `<div id="root"></div>`, `index.html`, `main.jsx`, `<div onClick={...}>`, `name`, `<button type="submit">`, `permalink`, `'use server'`

## Interview Points

- After a function in `<form action>` succeeds, React resets every uncontrolled field of the form.
- Succeeds means the action did not throw; a returned error message is a success, so the boxes are emptied next to the error line.
- A reset puts each field back to its default value.
- To keep the user's text after a refusal, return the submitted values in the `useActionState` state and give each box `defaultValue` from that state.
- `value` without `onChange` freezes the box; a controlled box with `value` and `onChange` is not reset at all, and renders on every keystroke.
- The reset changes the DOM fields only, never the `useActionState` state.
- `requestFormReset` from React DOM resets a form by hand, for a form submitted without the `action` prop; it runs inside a Transition, unlike the browser's `form.reset()`, which empties the boxes at once.
- Progressive enhancement: a basic version that works for everyone, made richer when JavaScript runs.
- What progressive enhancement needs from a form: a real `<form>`, a `name` on every field, a real submit button, and an action the browser can send without JavaScript.
- A URL action works without JavaScript; a function from our own code needs React running; a Server Function in a server-rendered page works before the bundle loads, and `useActionState` replays early submits.
- A Vite app that renders only in the browser has no form at all before its JavaScript runs.
