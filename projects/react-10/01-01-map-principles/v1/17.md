# Q17 Principle Map (River Version v1): Updating Objects in State
- **Version**: River Version (`v1`)
- **Bank Row**: `questions/questions.md` row 17, Version 4
- **Topic Tag**: `#state_objects` | `❱ CORE`
- **Interview Question**: *How do you update an object in state without mutating it?*

## Authorized Scope
- Treating every object held in state as read-only: changing a property of the existing object (a mutation) and passing that same object to the setter does not re-render, because the setter compares the next value with the current one using `Object.is`, and an object changed from inside is still the same object.
- Replacing instead of mutating: create a new object with the change and pass it to the setter; React replaces the state with the new object and renders again.
- The late surprise of a mutation: the changed field stays hidden until any unrelated state update re-renders the component, and then it appears all at once, because the object was changed all along.
- Copying the other fields with object spread, `{ ...order, quantity: order.quantity + 1 }`: the same three dots as the JSX spread of Lesson 09, inside an object literal; properties are read from left to right and the last one wins, so the change is written after the spread.
- Spread is shallow: it copies one level, and an object that looks nested is a separate object the parent only points to, so a change to a nested field needs a fresh copy of every object on the path from the state object down to the changed field.
- One change handler for several input fields, with a computed property name: `setOrder({ ...order, [e.target.name]: e.target.value })`, where `e.target.name` is the `name` attribute of the input that fired.
- Local mutation of an object we have just created is fine, because no other code points at it yet.
- Immer named as an optional helper for deep nesting, with no API taught.
- Out of scope: arrays in state, `push`, `splice`, `sort`, and `[...todos]` (`Q19 #state_arrays`), flattening deeply nested state and deciding what belongs in state (`Q22 #state_structure`), the full rules of controlled inputs with `value` and `onChange` (`Q20 #controlled_inputs`, used here as a Preview only), controlled versus uncontrolled forms (`Q40 #forms`), skipping re-renders with `memo` (`Q55 #memo`), the React Compiler and its lint rules (`Q63 #react_compiler`, `Q95 #eslint_and_tooling`), external state libraries (`Q60 #state_libraries`), reducers (`Q27 #use_reducer`), and, recall only, the setter and the initial value (`Q12 #use_state`), the `Object.is` skip (`Q13 #render_and_commit`), local mutation during render (`Q14 #purity`), the snapshot (`Q15 #state_snapshots`), and the updater function (`Q16 #state_updates`).

## General Concepts Introduction (Runway Plan)
- **Opening Essence**:
  - **Furniture-free snippet**: the bank's own case. `const [user, setUser] = useState({ name: 'John' });` with a button whose handler runs `user.name = 'Alice'; setUser(user);`: the page keeps `John`. The same button with `setUser({ name: 'Alice' });`: the page shows `Alice`. Beside them, the `react.dev` number case: `const [x, setX] = useState(0);` then `setX(5);` replaces the value, and the number `0` itself never changed.
  - **Human image**:
    1. The everyday meaning of **mutation**: the same living thing changed from inside, like a caterpillar that becomes a butterfly and is still the same animal. Changing `user.name` mutates the object: it is still the same object, with different contents.
    2. React checks the box, not what is inside it. Handing React the same box back with new contents is like returning a library book with a page rewritten: the librarian scans the barcode, sees the same book, and files nothing new. Handing React a new box is a new barcode, so React looks again.
    3. The everyday meaning of **read-only**: a printed receipt we may read but never write on; when something must change, we ask for a new receipt.
  - **Exact nuance of confusion to state out loud**:
    1. `user.name = 'Alice'; setUser(user);` and `setUser({ name: 'Alice' });` look like the same change, and the object inside does say `Alice` in both, but they are NOT the same thing: the first hands React the same object it already holds, the second hands it a new one.
    2. The setter running without an error looks like the update worked, but it did NOT reach the screen: React compared the two values, found the same object, and skipped the render.
    3. `{ ...user, name: 'Alice' }` and `{ name: 'Alice' }` with every other field typed by hand are the exact same thing: a new object with every old field and one changed.
- **Theme**: An online order card shows `Quantity: 1`; the shopper clicks `+1` twice and the card still says `1`, then clicks `Add gift wrap` and the quantity jumps to `3` at the same moment the gift wrap line changes.
- **Ways**: Four ways to give the setter a new object, and when each fits:
  1. Write every field of the new object by hand, `setOrder({ item: order.item, quantity: order.quantity + 1, giftWrap: order.giftWrap })`: fits a small object, or an object built fresh, such as the `react.dev` `{ x: e.clientX, y: e.clientY }`.
  2. Spread the old object and write the change after it, `setOrder({ ...order, quantity: order.quantity + 1 })`: the normal way once an object has more than a couple of fields; a nested change spreads once per level.
  3. The same spread inside an updater, `setOrder(o => ({ ...o, quantity: o.quantity + 1 }))`: fits when several updates of the same state are queued in one event (Lesson 16).
  4. Immer's `useImmer`, which lets mutating-looking code produce copies: fits deep nesting the team does not want to flatten; named only. Flattening the state is a fifth way, owned by `Q22 #state_structure`.
- **Recall**:
  - `const [likes, setLikes] = useState(0)` keeps a value inside React; the setter asks for a new render with the next value; the initial value is used only on the first render (Lesson 12, `Q12 #use_state`).
  - Calling a setter with the exact same value that is already in state makes React compare the two with `Object.is` and skip re-rendering the component and its children (Lesson 13, `Q13 #render_and_commit`, met there as an interview follow-up with a number).
  - Changing an array that came from outside during render breaks the page, while changing one created in the same render, a local mutation, is fine (Lesson 14, `Q14 #purity`).
  - Every render gets its own fixed value of each state variable, its snapshot; the setter does not change the variable in the running handler (Lesson 15, `Q15 #state_snapshots`).
  - The updater `setScore(s => s + 1)` and the short arrow function with an implicit return (Lesson 16, `Q16 #state_updates`).
  - `{...article}` on a JSX tag copies every property of `article` into `props`, and when it shares a tag with `title="New Title"`, the one written last wins (Lesson 09, `Q09 #children`).
  - React freezes the `props` object, and mutating an object that a parent and a child share changes it for both (Lesson 08, `Q08 #props`).
  - React passes the event object `e` to every handler, and `e.target` is the element where the event started (Lesson 11, `Q11 #event_handling`).
- **Runway topics**:
  - An object in state: `useState` can hold an object such as `{ item: 'Coffee mug', quantity: 1, giftWrap: false }`, not only a number, a string, or a true or false value. New in this lesson.
  - Numbers, strings, and true or false values cannot be changed from inside in JavaScript; an object can. Refresher, unlocked by the `react.dev` case `setX(5)`.
  - `Object.is(a, b)`: plain JavaScript that, for two objects, answers whether they are the very same object, never whether their contents match. `Object.is(user, user)` is `true` after `user.name` changed; `Object.is(user, { name: 'Alice' })` is `false`. Refresher from Lesson 13, now with objects.
  - Object spread inside an object literal, `{ ...order, giftWrap: true }`: opens the old object and lays out its fields in the new one; the exact same three dots as the JSX spread of Lesson 09. New in this form.
  - An object that points at another object: `order.delivery` holds a link to a second object, not a copy of it. New for this lesson.
  - Shallow: the everyday meaning of shallow water, only the top layer. Spread copies only the top layer of fields. New word.
  - Computed property name, `{ [key]: value }`: square brackets inside an object literal mean the property name is read from a variable. New for this lesson.
  - The `name` attribute of an `<input>` and reading it through `e.target.name`. New for this lesson.
  - An input that shows state and reports each keystroke, `value={order.customer}` with `onChange={handleChange}`: introduced only as far as Principle 4 needs it; its full rules belong to `Q20 #controlled_inputs`.
  - Parentheses around an object literal after an arrow, `o => ({ ...o })`, so the curly braces are read as an object and not as a function body. New for this lesson.
  - How the project files are organized: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx`, `src/components/OrderCard.jsx`.
- **Example**:
  - **Chosen page**: `Your Order`, the order card of an online shop for one item. `OrderCard` holds one state object, `const [order, setOrder] = useState(...)`, and shows `<h1>Your Order</h1>`, `<p>Item: {order.item}</p>`, `<p>Quantity: {order.quantity}</p>`, and `<p>Gift wrap: {order.giftWrap ? 'Yes' : 'No'}</p>`. Principle 1 starts with `item`, `quantity`, `giftWrap`, the `+1` button, and the `Add gift wrap` button. Principle 2 adds the field `customer` and the line `For: Anna Lee`. Principle 3 moves the starting object into `const initialOrder` above the component, adds the nested `delivery` object with the line `Delivery: 12 Main Street, Morning`, the `Deliver in the evening` button, and the `Start over` button. Principle 4 adds the field `note`, the line `Note: ...`, and two inputs, `Name` and `Note for the courier`, handled by one `handleChange`.
  - **Why this concept is the reason this page exists**:
    1. An order is one thing with several fields that change one at a time, quantity, gift wrap, delivery time, name, note, so one state object is the natural shape, and every button must keep the other fields.
    2. The mutation bug is big and seen at once: a quantity that ignores two clicks and then jumps to `3` when gift wrap is added is wrong for any shopper.
    3. A delivery address and time naturally sit together in their own object inside the order, so the nested copy has a reason, and `Start over` is a button every shopper knows, which makes the shared nested object visible when the morning slot does not come back.
    4. A name box and a courier note are the most ordinary inputs on the web, so one handler for two fields has a reason.
    5. The actions are click and type, nothing more.
  - **Other candidate pages considered**:
    1. *The syllabus card's author profile on an admin page (`profile.author.bio`)*: rejected, because an admin page is not something everyone uses, and a bio edit needs a text box from the first principle, while controlled inputs belong to `Q20 #controlled_inputs`.
    2. *The `react.dev` form for Barbara Hepworth (`person`, `firstName`, `lastName`, `email`)*: rejected as the page, because every change in it is typing, so the first principle would already rest on controlled inputs; its `...person` handler is kept in the facts.

    4. *The `react.dev` moving red dot (`position`, `onPointerMove`)*: rejected, because pointer coordinates are built fresh every time and never need the old fields copied.

## Principle Thread
- **Anchor**: React decides whether state changed by asking whether the setter received a different object, never by looking inside it; so every change to an object in state is made by building a new object, copying every level on the path to the change.
- **Axis**: From why a mutation is invisible, to how the copy is made, to how deep the copy goes, to one handler for many fields:
  1. A mutated object is the same object, so `Object.is` finds no change and React skips the render; a new object makes React render (Principle 1).
  2. Spread copies the other fields so only the change has to be written, and the change must come after the spread (Principle 2).
  3. Spread copies one level; a nested object is a separate object, so each level on the path needs its own copy (Principle 3).
  4. A computed property name lets one spread handler update whichever field the input names (Principle 4).
- **Why This Axis**: Cause before effect. The reader must first see why React ignores a changed object (Principle 1) before a copy has any reason. The copy is then made by hand and shortened with spread (Principle 2). Only once spread is known can its limit, one level, be shown (Principle 3). The computed property handler is a convenience built on the spread of Principle 2 and needs input fields, so it comes last (Principle 4).

## Principles

### Principle 1: A Mutated Object Is Still the Same Object, So React Skips the Render; a New Object Makes It Render
- **Handle**: `same-object-no-render`
- **Rule**: When a handler changes a property of the object in state and passes that same object to the setter, `Object.is` finds the next value equal to the current one and React skips the render; to change what the screen shows, create a new object with the change and pass it to the setter.
- **Opening Essence**:
  - **Furniture-free snippet**: `const [user, setUser] = useState({ name: 'John' });` and `<p>{user.name}</p>`. Way A: `user.name = 'Alice'; setUser(user);`, the page keeps `John`. Way B: `setUser({ name: 'Alice' });`, the page shows `Alice`. Next to them, `Object.is(user, user)` is `true` after the name changed, and `Object.is(user, { name: 'Alice' })` is `false`.
  - **Human image**: the library book returned with a page rewritten: the barcode is the same, so nothing new is filed. A mutation is the caterpillar turned butterfly, the same animal changed from inside.
  - **Exact nuance of confusion to state out loud**:
    1. Way A and Way B look like the same change, and in both the object says `Alice`, but they are NOT the same thing: Way A hands React the object it already holds, Way B hands it a new object.
    2. `setX(5)` with a number always works, so `setUser(user)` looks like it should work the same, but it is NOT the same thing: a number cannot be changed from inside, so a new number is always a new value; an object changed from inside stays the same value for `Object.is`.
    3. The setter running with no error looks like success, but it did NOT update the screen: React compared, found the same object, and stopped.
- **Root Distinction**:
  - *Junior blurred view*: "I changed the data and called the setter, so React must show the change."
  - *Senior grounding*: React does not look inside the object; it only asks whether the setter received a different object, and a mutated object is the same object.
- **Real Beginner Mistake (events, in order)**:

### Principle 2: Spread Copies the Other Fields, and the Change Is Written After the Spread
- **Handle**: `spread-copy-then-change`
- **Rule**: To change one field and keep the rest, write `{ ...order, field: newValue }`: the three dots copy every field of the old object into the new one, and the field written after them replaces the copied value, because properties are read from left to right and the last one wins; a field missing from a hand-written copy, or a spread placed after the change, gives the wrong object.
- **Opening Essence**:
  - **Furniture-free snippet**: `const user = { name: 'John', age: 30, city: 'Rome' };` Way A: `{ name: user.name, age: user.age, city: 'Paris' }`. Way B: `{ ...user, city: 'Paris' }`. Then the two orders on the same object: Order 1, `{ ...user, city: 'Paris' }` gives `city: 'Paris'`; Order 2, `{ city: 'Paris', ...user }` gives `city: 'Rome'`.
  - **Human image**: the closed box of Lesson 09 opened and its items laid out on the table of the new object, after which one item is swapped. Writing the change first and spreading after it is laying the new item down and then pouring the old box over it.
  - **Exact nuance of confusion to state out loud**:
    1. Way A and Way B are the exact same thing: a new object with every old field and one changed.
    2. The three dots inside `{ }` look like a new syntax, but they are the exact same idea as `{...article}` on a JSX tag in Lesson 09: open the box and lay out its fields.
    3. First state that the spread and a single field can share one object literal, then that they can come in two orders, and only then that the two orders are NOT the same thing, tracing each from left to right.
    4. `{ ...order }` looks like the old object, but it is NOT the same object: `Object.is(order, { ...order })` is `false`, so React renders.
- **Root Distinction**:
  - *Junior blurred view*: "`setOrder({ giftWrap: true })` changes the gift wrap field of the order."
  - *Senior grounding*: the setter replaces the whole state with exactly the object it receives; any field not in that object is gone, so the old fields must be copied in.

  6. Later, a teammate tidies the gift wrap handler to `setOrder({ giftWrap: true, ...order })`.
  7. The shopper clicks `Add gift wrap`: the card keeps `Gift wrap: No`, because the copied `giftWrap: false` came last.
  8. The teammate moves `giftWrap: true` back after `...order`, and the button works.

  - The `react.dev` challenge: `setPlayer({ lastName: e.target.value })` "did not copy the existing `...player` fields into the new object. This is why the score got lost".

### Principle 3: Spread Copies One Level, So a Nested Change Copies Every Object on the Path
- **Handle**: `nested-copy-every-level`
- **Rule**: An object inside another object is a separate object that the outer one only points to, and spread copies only the top level, so `{ ...order }` still shares the same `delivery` object; to change `order.delivery.time`, make a new `delivery` object with the change and a new `order` object that points at it, and never change a field of the shared nested object.
- **Opening Essence**:
  - **Furniture-free snippet**: `const user = { name: 'John', address: { city: 'Rome' } };` then `const copy = { ...user };`. `Object.is(copy, user)` is `false`, and `Object.is(copy.address, user.address)` is `true`. So `copy.address.city = 'Paris'` makes `user.address.city` `'Paris'` too. The fix: `{ ...user, address: { ...user.address, city: 'Paris' } }`. The `react.dev` picture: `obj1` holds the artwork, and `obj2` and `obj3` both say `artwork: obj1`.
  - **Human image**:
    1. Shallow water: only the top layer. Spread photocopies the top sheet of a folder, and the sheet says "the address card is in drawer 3", so the photocopy points at the same drawer, not at a new card.
    2. An object that points is like a street address written on paper: copying the paper does not build a second house.
  - **Exact nuance of confusion to state out loud**:
    1. `user` written with `address` inside its curly braces looks like one object holding another, but it is NOT one object: `react.dev` says "there is no such thing as a "nested" object", there are two objects pointing at each other.
    2. `const next = { ...order }; next.delivery.time = 'Evening'; setOrder(next);` and the two-level copy work the same at first, both show `Evening`, but they are NOT the same thing: the first changed the `delivery` object that the old order and the starting object still point at.
    3. Setting a field on `next` itself is a local mutation and is fine, the exact same thing as writing that field in the object literal; reaching through `next.delivery` is NOT the same thing, because that object is not new.
- **Root Distinction**:
  - *Junior blurred view*: "`{ ...order }` makes a full copy of the order, so I may change anything in it."
  - *Senior grounding*: spread makes a new top object whose nested fields still point at the old nested objects; each object on the path to the change needs its own new copy.

### Principle 4: One Handler for Many Fields: the Computed Property Name Reads the Input's `name`
- **Handle**: `one-handler-computed-name`

## Interview Points
1. Treat every object in state as read-only: React does not look inside it, and the setter compares the new value with the current one using `Object.is`.
2. A mutated object is still the same object, so passing it back to the setter is ignored and nothing re-renders; the change then shows up later, on any unrelated render, because the object was changed all along.
3. To update, create a new object with the change and pass it to the setter; React replaces the state and renders.
4. Spread copies the other fields, `{ ...obj, field: newValue }`; the setter replaces rather than merges, so the spread is required, and the change goes after the spread because the last property wins.
5. Spread is shallow: a nested object is a separate object the parent points to, so a nested change needs a new copy of every object from the state object down to the changed field.
6. Mutating shared or earlier objects corrupts past snapshots, shared starting objects, and features like Undo and history, while mutating a fresh object you just created is fine.
7. A computed property name, `[e.target.name]`, lets one change handler update whichever field the input names.
8. For deep nesting, flatten the state or use a helper such as Immer, which produces the copies for you.
