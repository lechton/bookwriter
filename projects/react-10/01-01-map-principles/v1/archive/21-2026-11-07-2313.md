- **Interview Question**: *How do you design a component that reacts to input with state instead of touching the DOM?*

## Scope

Covered here:
- List every screen the component can show. The React docs call them "visual states". This map says "screen".
- Write each screen once in JSX, and let one value, `status`, pick the screen.
- Find what changes the screen: human inputs, such as typing and clicking, and computer inputs, such as a timer finishing.
- Every input only calls a setter. No code shows, hides, enables, or disables a page part by hand.
- Keep the screen in one `status` string, not in several true-or-false flags that can be true together.
- A look that depends on the screen, such as a red border, comes from `status` in JSX, not from adding and removing classes on the DOM node.

## Start of the Lecture

**The chapter's one difference**: "Writing each line by hand vs. letting `status` pick the line".

By hand, plain JavaScript:

```js
errorText.textContent = 'This email is already subscribed.';
doneText.textContent = 'You are subscribed!'; // the error line is still on the page
```

With `status` in state, React:

```jsx
{status === 'error' && <p>This email is already subscribed.</p>}
{status === 'success' && <p>You are subscribed!</p>}
```

- With commands: the second command adds a line and removes nothing. Both lines are on the page.
- With `status`: `setStatus('error')`, then `setStatus('success')`. `status` holds one word at a time, so exactly one line shows.
- Verdict: NOT the same thing. With commands, every change must also undo the old screen by hand. With `status`, the old line disappears because its condition is now false.

**The real page problem** (the syllabus card's friction, moved to a newsletter box):
1. A news site has a box: "Get our weekly news", an email box, and a `Subscribe` button.
2. The plain JavaScript handler writes `Subscribing...`, waits, then writes either the error line or the success line.
3. The user types `john@example.com` and clicks `Subscribe`.
4. The pretend server answers `This email is already subscribed.`
5. The user changes the email to `anna@example.com` and clicks again.
6. The success branch writes `You are subscribed!` and forgets to clear the error line.
7. The page shows `This email is already subscribed.` and `You are subscribed!` at the same time.

**Example page chosen for this lesson**: a newsletter box, "Get our weekly news".
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx`, `src/components/SubscribeBox.jsx`, `src/index.css` for one class in Principle 4.
- The plain JavaScript version is a snippet beside the React project, not a project file.
- Four screens: typing, sending, success, error.
- The pretend server is one `setTimeout` of 1500 milliseconds. It answers with the error for `john@example.com` and with success for any other email.

**Why this page**:
1. Everyone has seen a "subscribe to our newsletter" box. An email box and one button need no explanation.
2. It has all four kinds of screen from the React docs: typing, sending, success, error.
3. It has both kinds of input from the React docs: human (typing, clicking) and computer (the server answering).
4. The break is big on the page: two opposite messages at once.
5. The pretend server uses only `setTimeout`, known from Lesson 15, and `===`. No promise, `async`, `await`, `try`, or `catch`.
6. Hiding and showing in the plain version uses only `textContent`, known from Lesson 01. No `classList` or `style.display` before the lesson's idea.

**Other pages considered**:
1. *The syllabus card's members-only sign-up form with "Welcome, Mary Jones"*: same idea, but a name, a welcome text, and a members area add parts that need explaining. The one-field newsletter box keeps the same break.
2. *The React docs' city quiz*: a quiz that answers with a fake network call needs a promise and `async` code, and a quiz is not a page most users fill in.
3. *A checkout promo-code box*: needs a list of valid codes and a price that changes, which is extra code outside this lesson.
4. *A "Follow" button that turns into "Following"*: only two screens and no computer input, so no impossible mix can appear.

## Principles

### Principle 1: `status` Picks Which Screen the Box Shows

- **Rule**: Before writing any handler, list every screen the user can see, and write JSX for each one, chosen by a single `status` value.
- **Move**: Smallest code first. The same tag with two different `status` values draws two different screens, and that is the whole idea before any handler exists.
- **Simplest version**: "`status="error"` vs. `status="success"`".
  ```jsx
  <SubscribeBox status="error" />   {/* the email box, the button, and This email is already subscribed. */}
  <SubscribeBox status="success" /> {/* only You are subscribed! */}
  ```
  - Inside, `function SubscribeBox({ status = 'typing' })` returns `<h2>You are subscribed!</h2>` early when `status === 'success'`, and otherwise the email box and the button, with `{status === 'sending' && <p>Subscribing...</p>}` and `{status === 'error' && <p>This email is already subscribed.</p>}`.
  - The box and the button get `disabled={status === 'sending'}`.
- **Words to teach**:
  - Screen: one picture of the component that the user can see. The React docs call it a "visual state" and compare it to a designer's mockups. Needed at the first `status` comparison.
  - `status`: our own prop name. The React docs: "You could call that prop anything you like, the naming is not important." Needed at the first tag.
  - The four screens of this box, as the docs list them for their form: typing (box and button on), sending (both off, `Subscribing...`), success (the message instead of the box), error (like typing, plus the error line).
  - Living styleguide or storybook: a page that shows every screen at once. Name only, at the step that maps over all four.
  - Known: default prop value, Lesson 09. Early `return` and `&&`, Lesson 10. `disabled={...}`, Lesson 03. `map` with `key`, Lesson 18.
  - Helper: none.
- **Side by side**: "with `status="error"`" and "with `status="success"`". NOT the same thing: the same component draws a different screen for each value, and no line of it hides or shows anything by hand.
- **Surprises**: none. Each tag draws what its `status` says.
- **Where did that come from?**:
  - `'typing'` when `<SubscribeBox />` has no `status`: JavaScript supplies it.
    1. The tag passes no `status`.
    2. `status` would be `undefined`.
    3. The default `= 'typing'` fills it in.
- **Real beginner mistake** (the React docs: "forgetting to show or hide something"):
  1. The developer starts from the actions, not the screens: "on click, write Subscribing", "on error, write the error", "on success, write the success line".
  2. Each action is written as a command in plain JavaScript.
  3. The success command writes `You are subscribed!` and does not clear the error line.
  4. After one failed try and one good try, the page shows both messages.
  5. Listing the four screens first shows that success has no error line, so the JSX for success has none.
- **Interview depth**:
  - The docs' first step: "Identify your component's different visual states".
  - Mocking with a `status` prop lets you see every screen before any logic exists. Docs: "Mocking lets you quickly iterate on the UI before you wire up any logic."
  - Showing all screens on one page is "often called 'living styleguides' or 'storybooks'".
  - Imperative code must handle the change from every screen to every other screen. Declarative JSX describes each screen once.
- **React does**:
  - Page with `status="error"`: the box, the button, and `This email is already subscribed.` Docs show the same pattern with their quiz; the exact page for this code is `unconfirmed` until the lab runs it.
  - Page with `status="success"`: only `You are subscribed!`. Docs: the "Thank you" message "is shown instead of a form".
  - Elements panel for `status="success"`: one `<h2>` and no `<input>` or `<button>`. `unconfirmed`.
  - Console: no message expected. `unconfirmed`.
- **Example step**: `src/components/SubscribeBox.jsx` is created with the `status` prop and the four screens, and no state. `src/App.jsx` maps over `['typing', 'sending', 'success', 'error']` and renders `<SubscribeBox status={status} />` for each, under a small heading with the status name, as in the docs' Deep Dive.
- **Code names**: `SubscribeBox.jsx`, `App.jsx`, `SubscribeBox`, `status`, `'typing'`, `'sending'`, `'success'`, `'error'`, `Get our weekly news`, `Your email`, `Subscribe`, `Subscribing...`, `This email is already subscribed.`, `You are subscribed!`, `disabled={status === 'sending'}`, `statuses`, `key={status}`

### Principle 2: A Click and a Timer Only Call `setStatus`

- **Rule**: Find every input that changes the screen, human or computer, and make each one call a setter. The handler never turns the button off or on, and never writes a message.
- **Move**: Side by side. A click by the user and a timer finishing look like two different kinds of event, and they do the exact same thing: set `status`.
- **Simplest version**: "a human input vs. a computer input".
  ```jsx
  <button onClick={() => setStatus('sending')}>Subscribe</button> {/* the user clicks: the screen becomes sending */}
  setTimeout(() => setStatus('success'), 1500);                   // the timer ends: the screen becomes success
  ```
- **Words to teach**:
  - Human input: something the user does, such as typing or clicking. The docs add "navigating a link". Needed at the `Subscribe` click.
  - Computer input: something that arrives without the user, such as "a network response arriving, a timeout completing, an image loading". Needed when the pretend server answers.
  - The docs' rule for both: "you must set state variables to update the UI."
  - The docs' drawing advice: each screen as a circle, each change as an arrow. A `tree` figure of typing, sending, success, error, with arrows labelled by the input that causes them.
  - Known: `useState` and the setter, Lesson 12. Controlled box with `value` and `onChange`, Lesson 20. `setTimeout`, Lesson 15. Two setters, one render, Lesson 16.
  - Helper: `===`, known JavaScript.
- **Side by side**: "with a click" and "with a timer". Yes, it is the exact same thing: both only call `setStatus`, and React draws the new screen in both cases.
- **Surprises**:
  1. While `status` is `'sending'`, the email box and the button are greyed out.
  2. The timer ends, and `setStatus('error')` runs.
  3. The box and the button are on again, and no line of our code turned them on.
  4. Steps: React renders `SubscribeBox` again. `status === 'sending'` is now `false`. `disabled={false}` goes on both. React changes only that attribute in the DOM.
- **Where did that come from?**:
  - `email` inside the timer callback, 1500 milliseconds after the click: React supplies it from the render where the user clicked.
    1. The user clicks while `email` holds `john@example.com`.
    2. `handleSubscribe` from that render starts the timer.
    3. The callback reads `email` from that same render, Lesson 15.
    4. The box is disabled while sending, so the user cannot change the email before the answer.
  - The error line disappearing when the user starts typing again, with no line removing it:
    1. `handleEmailChange` calls `setEmail(e.target.value)` and `setStatus('typing')`.
    2. React renders once, Lesson 16.
    3. `status === 'error'` is `false`, so the line is not in the JSX any more.
- **Real beginner mistake** (the docs' imperative form must "enable" the form again after an error, in its `finally` block):
  1. The plain JavaScript handler sets `button.disabled = true` on click.
  2. The success branch leaves the button off, which matches a finished sign-up.
  3. The error branch writes the error line and forgets `button.disabled = false`.
  4. The user reads `This email is already subscribed.`, fixes the email, and cannot click `Subscribe` again.
  5. In the React version, `disabled={status === 'sending'}` is the only place that decides it, and every screen except sending turns the button on.
- **Interview depth**:
  - Steps 2, 3, and 5 of the docs: find the triggers, keep the screen in `useState`, connect the handlers to set state.
  - "Notice that human inputs often require event handlers!"
  - Declarative code is longer than the imperative version, and "much less fragile". Docs: it "lets you later introduce new visual states without breaking existing ones."
  - A new screen, for example "already subscribed, resend the link", adds one value of `status` and one JSX branch. The existing handlers do not change.
  - The docs' quiz keeps the error message in its own state, `error`, because the server sends the text. Here the text is fixed, so no `error` state is needed.
- **React does**:
  - Page after clicking `Subscribe` with `john@example.com`: `Subscribing...`, box and button greyed out, then after about 1.5 seconds the error line, box and button on. Behavior from the docs' form; this page is `unconfirmed`.
  - Page after clicking with `anna@example.com`: `Subscribing...`, then only `You are subscribed!`. `unconfirmed`.
  - Elements panel while sending: `disabled` on `<input>` and `<button>`. Exact attribute text `unconfirmed`.
  - Console: no message expected. `unconfirmed`.
- **Example step**: in `SubscribeBox.jsx`, the `status` prop becomes `const [status, setStatus] = useState('typing');`, and `const [email, setEmail] = useState('');` is added. The box gets `value={email}` and `onChange={handleEmailChange}`. The button gets `onClick={handleSubscribe}`. `handleSubscribe` calls `setStatus('sending')` and starts the 1500 millisecond timer that sets `'error'` for `john@example.com` and `'success'` for any other email. `App.jsx` renders one `<SubscribeBox />`.
- **Code names**: `useState('typing')`, `useState('')`, `email`, `setEmail`, `status`, `setStatus`, `handleEmailChange`, `handleSubscribe`, `setTimeout`, `1500`, `john@example.com`, `anna@example.com`, `button.disabled = true`, `button.disabled = false`, `disabled={status === 'sending'}`

### Principle 3: One `status` Replaces Three True-or-False Flags

- **Rule**: Keep the screen in one `status` string with a fixed list of values. Separate true-or-false flags for each screen can be true together, and then the page shows two screens at once.
- **Move**: Side by side. Three flags and one string both seem to describe the same four screens, and they are not the same.
- **Simplest version**: "three flags vs. one `status`".
  ```jsx
  const [isSending, setIsSending] = useState(false);
  const [isError, setIsError] = useState(false);
  const [isSuccess, setIsSuccess] = useState(false);
  ```
  ```jsx
  const [status, setStatus] = useState('typing'); // 'typing', 'sending', 'success', or 'error'
  ```
  - With flags: `setIsError(true)`, later `setIsSending(true)`. Both are true: the error line and `Subscribing...` show together.
  - With `status`: `setStatus('error')`, later `setStatus('sending')`. `status` holds one word, so only `Subscribing...` shows.
- **Words to teach**:
  - Impossible state: a mix of values that matches no screen you would want the user to see. The docs call it a "paradox": "`isTyping` and `isSubmitting` can't both be `true`." Needed when both lines show together.
  - State machine: the computer science name for a thing that is in exactly one of a fixed list of states. Everyday image: a traffic light, where one light is on at a time and red and green are never on together. Use the image once, then back to `status`.
  - Known: `useState`, Lesson 12. Lesson 16 for two setters in one handler.
  - Helper: none.
- **Side by side**: "with three flags" and "with one `status`". NOT the same thing: three flags allow 8 mixes and only 4 of them are real screens, while `status` can only hold one of the 4 words.
- **Surprises**:
  1. With flags, the user gets the error for `john@example.com`, then types `anna@example.com` and clicks `Subscribe`.
  2. The page shows `Subscribing...` and `This email is already subscribed.` together, with the box greyed out.
  3. Steps: the click calls `setIsSending(true)`. Nothing set `isError` back to `false`. Both flags are `true`, so both `&&` lines are in the JSX.
  4. The docs name this exact screen as one to avoid: "you never want to show an error message and disable the input at the same time".
- **Where did that come from?**:
  - The number 8: each of three flags is `true` or `false`, so 2 times 2 times 2 mixes. Arithmetic from the docs' own count, "There are four possible combinations of two booleans, but only three correspond to valid states."
  - The 4 real screens among them: all `false` (typing), and exactly one flag `true` (sending, error, success).
- **Real beginner mistake** (the docs' Step 3: "Your first idea likely won't be the best", and Step 4's paradox):
  1. The developer gives each screen its own flag: `isSending`, `isError`, `isSuccess`.
  2. The timer sets `setIsSending(false)` and `setIsError(true)` for `john@example.com`.
  3. `handleEmailChange` sets only `email`, and the click sets only `setIsSending(true)`. Nothing sets `isError` back to `false`.
  4. The user fixes the email and clicks `Subscribe`.
  5. The page shows `Subscribing...` and the error line at once, with the box greyed out.
  6. The developer replaces the three flags with one `status` and the four values.
- **Interview depth**:
  - Docs, Step 3: "you want as few 'moving pieces' as possible. More complexity leads to more bugs!"
  - Docs, Step 4: the goal is to "prevent the cases where the state in memory doesn't represent any valid UI that you'd want a user to see."
  - The syllabus card's count: four flags allow sixteen mixes. Each new flag doubles the mixes, while a new screen adds only one value to `status`.
  - Other state that can be computed, such as an empty box from `email.length === 0` in place of `isEmpty`: Lesson 22.
  - Some mixes can still make no sense across several state variables, such as an error text while `status` is `'success'`. Docs: a reducer can "unify multiple state variables into a single object". Lesson 27.
- **React does**:
  - Page with flags: `Subscribing...` and `This email is already subscribed.` together on the second try. `unconfirmed`.
  - Page with `status`: only `Subscribing...` on the second try. `unconfirmed`.
  - Console: no message in either version. React gives no warning for impossible mixes. `unconfirmed`.
- **Example step**: in `SubscribeBox.jsx`, the mistake version swaps `status` for `isSending`, `isError`, and `isSuccess`, with `{isSending && ...}` and `{isError && ...}`. The fix returns to the single `status` of Principle 2. No new file.
- **Code names**: `isSending`, `setIsSending`, `isError`, `setIsError`, `isSuccess`, `setIsSuccess`, `status`, `setStatus`, `'typing'`, `'sending'`, `'success'`, `'error'`, `isTyping`, `isSubmitting`, `isEmpty`, `email.length === 0`

### Principle 4: The Red Border Follows `status`, Not `classList`

- **Rule**: When a look changes with the screen, such as a red border on the email box during the error screen, compute `className` from `status` in JSX. Do not add or remove classes on the DOM node by hand.
- **Move**: Side by side. Adding a class by hand and computing it from `status` both turn the border red on the error screen, and only one takes it away again.
- **Simplest version**: "`classList.add` by hand vs. `className` from `status`".
  ```js
  document.getElementById('email').classList.add('invalid'); // the border turns red, and stays red
  ```
  ```jsx
  <input className={status === 'error' ? 'invalid' : ''} /> {/* red only while status is 'error' */}
  ```
  - `src/index.css`: `.invalid { border: 2px solid red; }`
- **Words to teach**:
  - `className` computed from state: the docs' answer to their Challenge "Add and remove a CSS class": "in React you need to describe what you want to see rather than manipulate the UI elements. So you need to calculate both CSS classes based on the current state." Needed when the error screen gets a red border.
  - Known: `className`, Lesson 02. `? :`, Lesson 10. Writing to a React-managed DOM node by hand is wrong, and React commits only what changed, Lesson 13. `getElementById`, Lesson 01.
  - Helper: `classList.add`, the browser's way to add one class to an element. In the wrong code only, half a line.
- **Side by side**: "with `classList.add`" and "with `className` from `status`". It looks the same on the error screen, but it is NOT the same thing: React never removes a class it did not write, so the hand-added class stays after the screen changes.
- **Surprises**:
  1. The mistake version adds `invalid` by hand inside the timer for `john@example.com`.
  2. The user types a new letter, `status` becomes `'typing'`, and the error line disappears.
  3. The red border stays.
  4. Steps: the JSX of the box has no `className`. React compares the new JSX with the old one and finds no change to `className`. React does not touch the class on that box. The hand-added `invalid` is still there.
  5. The docs' rule behind step 4: "React also avoids touching the DOM for properties that have not changed since the last time they were set."
- **Where did that come from?**:
  - The red border on the typing screen, with no line of JSX asking for it: our hand-written `classList.add` put it on the real DOM node, outside React's description of the screen.
- **Real beginner mistake** (the bank row's hook: "Your instinct is to show and hide page parts by toggling classes on DOM nodes", and the docs' Challenge task):
  1. The developer wants a red border on the error screen.
  2. Out of plain JavaScript habit, the timer's error branch calls `document.getElementById('email').classList.add('invalid')`.
  3. The error screen shows the red border.
  4. The user starts typing a new email. The error line goes away, and the red border stays.
  5. The developer adds `classList.remove` in `handleEmailChange`, and now two places must agree again.
  6. The fix: `className={status === 'error' ? 'invalid' : ''}` on the box, and both hand-written lines removed.
- **Interview depth**:
  - The docs' Challenge solution computes both class names from one true-or-false state, and also shows a second way: return two separate chunks of JSX.
  - With two chunks, their nesting must line up, or "toggling `isActive` would recreate the whole tree below and reset its state." Lesson 25.
  - The docs' last Challenge: a plain JavaScript `updateDOM` function that redraws everything from variables "shows what React does under the hood when you set the state."
- **React does**:
  - Page with `className` from `status`: red border only on the error screen. `unconfirmed`.
  - Page with `classList.add`: the red border stays after the error line disappears. `unconfirmed`; the lab must confirm this.
  - Elements panel: `class="invalid"` on the `<input>` during the error screen in both versions, and still there after typing in the `classList` version. `unconfirmed`.
  - Console: no message. `unconfirmed`.
- **Example step**: `src/index.css` gains `.invalid { border: 2px solid red; }`, imported in `src/main.jsx`. In `SubscribeBox.jsx`, the box gains `className={status === 'error' ? 'invalid' : ''}`. This is the finished page.

## Interview Points

1. React reacts to input by changing state, and the JSX follows. Code never enables, disables, shows, or hides a page part by hand.
2. The docs' five steps: identify the screens, find what triggers each change, keep the state in `useState`, remove state that is not needed, connect the handlers to set state.
3. Inputs are human, such as typing and clicking, or computer, such as a network answer or a timer. Both only set state.
4. One `status` string with a fixed list of values beats separate true-or-false flags, which allow impossible mixes such as an error line while sending.
5. Each screen is written once in JSX. A new screen adds one value and one branch, without changing the existing handlers.
6. A look that depends on the screen, such as a CSS class, is computed from state, because React leaves alone any DOM attribute whose JSX did not change.
7. The declarative version is longer but "much less fragile" than the imperative one.
8. Limits of this lesson: computed state is Lesson 22, and a reducer for the last impossible mixes is Lesson 27.
