## Scope

This lesson covers:
- Imperative code versus declarative code for a form that changes over time: plain DOM code commands each element, React code describes each visual state and lets React change the DOM.
- The five steps of `react.dev`: identify the visual states, find what triggers each change, represent the state with `useState`, remove state that adds nothing, connect the event handlers.
- Mocking each visual state with a `status` prop before any logic, and showing every state on one page, which `react.dev` calls a "living styleguide" or "storybook".
- Human inputs and computer inputs as the two kinds of triggers, and drawing states as circles and changes as arrows.
- One `status` string instead of several true or false values, and why a single string rules out impossible combinations.
- The three questions `react.dev` asks to remove a state variable: does it cause a paradox, is the same information already in another state variable, can it come from the opposite of another state variable. Only as far as this form needs them.
- An event handler that waits for a fake server, with `async`, `await`, `try`, and `catch`, so that a computer input can set state.
- Computing a `className` from state instead of adding and removing classes on a DOM node, from the first `react.dev` challenge.

## Start of the Lecture

- **Simplest version of the idea**: one `Subscribe` button that turns into a thank-you line.
  - Plain JavaScript: a click handler runs `button.disabled = true` and `thanks.classList.remove('hidden')`. Two commands, one for each element.
  - React: `const [done, setDone] = useState(false);` with `<button disabled={done} onClick={() => setDone(true)}>Subscribe</button>` and `{done && <p>Thanks!</p>}`. The handler changes one value. The JSX already says how the page looks when `done` is `true`.
  - Everyday picture from `react.dev`: imperative code is riding next to a driver and telling them every turn; declarative code is getting into a taxi and telling the driver where you want to go.
- **The real page problem**: a form that waits for a server has several looks over time: empty, typed, waiting, refused, accepted. Plain DOM code must show, hide, enable, and disable each element on every change. One forgotten command leaves the page in a look nobody designed.
- **Example page**: the `Promo code` box on the checkout page of an online shop.
  - The page: a heading `Promo code`, a text box, an `Apply` button, a `Checking...` line while the shop's server checks the code, a red line `This code is not valid.` when the server refuses, and the line `Code applied! You get free delivery.` when the server accepts.
  - The fake server accepts only `WELCOME` and answers after 1.5 seconds.
  - The story: the shopper types `WELCOM`, a typo, and is refused. The shopper fixes it to `WELCOME` and is accepted.
- **Why this page**:
  1. Almost every web user has typed a promo code or gift code at a checkout and seen it refused.
  2. A refused code followed by a retry is the normal path, so the card's friction appears without any trick: the error line from the first try is still on screen after the second try succeeds.
  3. The box has every kind of trigger the lesson needs: typing and clicking are human inputs, the server's answer is a computer input.
  4. It has exactly the five visual states of the `react.dev` quiz, so every step of the five-step method has a visible job.
  5. The page is small: one box, one button, three lines of text.
- **Other pages considered**:
  1. The syllabus card's members-only sign-up form with `Mary Jones`: close in shape. Rejected because the fake server needs an invented reason to refuse a name, and a promo code is refused for a reason everyone knows.
  2. The `react.dev` city quiz: rejected because a quiz answer has no everyday stake and the lecture should not copy the documentation's page.
  3. A login form: rejected because two fields and a password bring security questions that have nothing to do with visual states.
  4. A `Like` button: rejected because it has only two looks and no waiting or refused state.
  5. The `Contact Us` form of Lesson 20: rejected because Lesson 20 used it, and its `sent` value was kept as one true or false value on purpose.

## Principles

### Principle 1: Plain DOM code gives a command for every change, and one forgotten command breaks the page

- **Rule**: When a page changes in several ways over time, plain DOM code must name every element in every handler. React code describes the page for each state once, and the handler only changes state.
- **Simplest version**: the `Subscribe` button from the Start of the Lecture. Each new element the click affects needs one more command in the plain handler. In React it needs one more piece of JSX that reads `done`, and the handler stays `setDone(true)`.
  - Everyday picture: turn-by-turn directions versus telling a taxi driver the address. `react.dev`: the driver "might even know some shortcuts you haven't considered".
- **New code words**:
  - `classList`: provided by the browser. A list of the CSS classes on a DOM node.
  - `classList.add('hidden')` and `classList.remove('hidden')`: provided by the browser. They put a class on the node or take it off.
  - `hidden`: our own CSS class, `.hidden { display: none; }`. A node with it is not shown.
  - `el.disabled = true`: provided by the browser. A disabled box or button takes no typing or clicks and looks dimmed.
  - `async function`: provided by JavaScript. A function that is allowed to wait with `await`.
  - `await`: provided by JavaScript. Pauses the function until the server's answer arrives, then goes on with the next line.
  - `try` and `catch`: provided by JavaScript. If the code inside `try` fails, JavaScript jumps to `catch`.
  - `finally`: provided by JavaScript. Runs after `try` or `catch`, whichever happened.
  - `checkCode`: our own fake server, in `src/checkCode.js`. It answers after 1.5 seconds and accepts only `WELCOME`.
- **What happens, in order** (plain version, two tries):
  1. The shopper types `WELCOM` and clicks `Apply`.
  2. `handleSubmit` disables the box and the button and removes `hidden` from `Checking...`.
  3. `await checkCode(codeInput.value)` waits 1.5 seconds. The fake server refuses.
  4. JavaScript jumps to `catch`, which removes `hidden` from `This code is not valid.`.
  5. `finally` adds `hidden` to `Checking...` and enables the box and the button.
  6. The shopper fixes the code to `WELCOME` and clicks `Apply`.
  7. The fake server accepts. The success branch removes `hidden` from the success line and adds `hidden` to the form.
  8. No line adds `hidden` back to the error line, so it stays.
  9. The page shows `This code is not valid.` and `Code applied! You get free delivery.` at the same time.
- **Look-alikes**:
  - The plain handler and the React handler both run on `Apply`. They differ at step 2: the plain handler touches four elements, the React handler calls one setter, and React decides which elements change.
  - `button.disabled = true` and `disabled={status === 'checking'}` both disable the button. They differ in who writes the DOM: our code in the first, React in the second, during the commit.
- **Where did that come from?**:
  - `form`, `codeInput`, `applyButton`, `checkingText`, `errorText`, `successText` in the plain file: our code finds them with `document.getElementById` at the top of the file, using the `id` attributes written in `index.html`.
  - `checkCode`: our code, imported from `src/checkCode.js`. Steps inside it:
    1. It returns a `Promise`, a JavaScript object that stands for an answer that is not here yet.
    2. `setTimeout` waits 1500 milliseconds.
    3. If the code is `WELCOME`, it calls `resolve()`, and `await` goes on to the next line.
    4. Otherwise it calls `reject(new Error('This code is not valid.'))`, and JavaScript jumps to `catch`.
- **Real beginner mistake**: the forgotten hide above, which is the syllabus card's friction and the bug `react.dev` names: "forgetting to show or hide something".
  1. The developer writes the plain handler and tests a wrong code. It works.
  2. The developer tests a right code from a fresh page. It works.
  3. A shopper tries a wrong code and then a right code.
  4. Both messages are on screen.
  5. The developer adds `errorText.classList.add('hidden')` to the success branch.
  6. Next month a new `Remove code` button is added, and every handler must be checked again for every element.
- **Interview depth**:
  - `react.dev`: imperative UI code "gets exponentially more difficult to manage in more complex systems".
  - `react.dev`: adding a new element or interaction "would require carefully checking all existing code to make sure you haven't introduced a bug".
  - `react.dev`: "In React, you don't directly manipulate the UI", you "declare what you want to show, and React figures out how to update the UI."
  - With four looks, plain code must handle the change from each look to each other look; declarative JSX describes each look once.
  - The third `react.dev` challenge writes the plain page with one `updateDOM` function that redraws every element from variables. `react.dev`: that function "shows what React does under the hood when you set the state", and React "also avoids touching the DOM for properties that have not changed since the last time they were set."
- **React does**: nothing in this principle; it is plain JavaScript in the browser.
  - The two messages showing together: derived from the code, `unconfirmed` until the lab runs it.
  - Console: no message expected, `unconfirmed`.
- **Example step**: creates `index.html` with the plain form, `src/plain-promo.js` with the plain handlers, `src/checkCode.js` with the fake server, and the `.hidden` and `.error` rules in `src/index.css`. The plain form, as facts:
  - `index.html` holds `<form id="promo-form">` with `<h2>Promo code</h2>`, `<input id="code-input">`, `<button id="apply-button" disabled>Apply</button>`, and `<p id="checking" class="hidden">Checking...</p>`. Below the form: `<p id="error" class="error hidden">This code is not valid.</p>` and `<p id="success" class="hidden">Code applied! You get free delivery.</p>`. The error and success lines sit outside the form, so hiding the form does not hide them.
  - `codeInput.oninput` enables `Apply` when the box has text and disables it when the box is empty.
  - The fake server:

```js title="src/checkCode.js"
export function checkCode(code) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (code === 'WELCOME') {
        resolve();
      } else {
        reject(new Error('This code is not valid.'));
      }
    }, 1500);
  });
}
```

### Principle 2: List every visual state first, and draw each one from a `status` prop

- **Rule**: Before writing any logic, list every look the user can see, and write JSX that draws each look from one value. A prop called `status` lets you see each look by changing one word.
- **Simplest version**: `function Light({ status = 'off' }) { return status === 'on' ? <p>Light is on</p> : <p>Light is off</p>; }`. Changing `'off'` to `'on'` shows the other look.
  - Everyday picture: a designer's mockups, one drawing for each screen. `react.dev`: "Just like a designer, you'll want to 'mock up' or create 'mocks' for the different states before you add logic."
- **New code words**:
  - visual state: one look of the component that the user can see. Our word, from design.
  - `status`: our own prop name. `react.dev`: "You could call that prop anything you like, the naming is not important."
  - state machine: a computer science name for something that is always in exactly one of several states. Name only.
  - mock: a version of the component with no logic, used only to see each look.
- **What happens, in order** (changing the default):
  1. `App` renders `<PromoCode />` with no `status`.
  2. The default value gives `status` the value `'empty'`.
  3. `status === 'success'` is false, so the function goes on to the form.
  4. `status === 'empty'` is true, so the button gets `disabled={true}`.
  5. The developer changes the default to `'success'`, and the next render returns only the success line.
- **The five looks of the promo box**:
  - `empty`: the box is empty, `Apply` is disabled.
  - `typing`: the box has text, `Apply` is enabled.
  - `checking`: the box and `Apply` are disabled, `Checking...` is shown.
  - `error`: like `typing`, plus the red line `This code is not valid.`.
  - `success`: `Code applied! You get free delivery.` is shown instead of the form.
- **Look-alikes**:
  - `status` as a prop here and `status` as state in Principle 5: same name, same values in the JSX. They differ in who sets it: the parent tag in the mock, a setter inside the component later.
  - `error` and `typing`: the same form, with one extra line in `error`. They are two looks because the user sees a difference.
- **Where did that come from?**:
  - `status` inside `PromoCode` when `App` passes nothing: the default value `= 'empty'` in the parameter list, Lesson 09.
  - The `status` of each section in the living styleguide: our array `statuses`, which `map` walks one item at a time and passes as `status={status}`.
- **Real beginner mistake**:
  1. The developer lists only three looks: empty, typed, done. There is no `checking` look.
  2. The form stays enabled while the server checks.
  3. An impatient shopper clicks `Apply` twice, and the code is sent twice.
  4. Listing the `checking` look on paper shows that the box and the button must be disabled while waiting.
  - Grounding: `react.dev` lists "Submitting: Form is completely disabled. Spinner is shown." as its own look, and the batching page notes "if the first button click disables a form, the second click would not submit it again".
- **Interview depth**:
  - `react.dev`: "React stands at the intersection of design and computer science"; both state machines and designers' visual states inspire the method.
  - `react.dev` Deep Dive: rendering every look on one page, with `statuses.map(...)`, is often called a "living styleguide" or "storybook".
  - Mocking lets you "quickly iterate on the UI before you wire up any logic".
  - The `empty` look is listed now and later computed from `code.length === 0`, as `react.dev` does in its Step 4.
- **React does**:
  - The mock shows the form with `Apply` disabled for `'empty'`, and only the success line for `'success'`: derived from the `react.dev` mock, page text `unconfirmed`.
  - The living styleguide shows five sections, one per look: derived, `unconfirmed`.
  - Elements panel: in the `success` section there is no `<form>` node, because the early `return` gives only the `<p>`: derived, `unconfirmed`.
- **Example step**: creates `src/components/PromoCode.jsx` as a mock with `{ status = 'empty' }`, and `src/App.jsx` that first renders `<PromoCode />`, then the living styleguide with `const statuses = ['empty', 'typing', 'checking', 'error', 'success'];` and `<section key={status}><h4>{status}</h4><PromoCode status={status} /></section>`. The mock:

  - `<input disabled={status === 'checking'} />`
  - `<button disabled={status === 'empty' || status === 'checking'}>Apply</button>`
  - `{status === 'checking' && <p>Checking...</p>}`
  - `{status === 'error' && <p className="error">This code is not valid.</p>}`

### Principle 3: Find what moves the component from one state to the next, both people and computers

- **Rule**: Every change between looks has a trigger. Human inputs are clicking, typing, and following a link. Computer inputs are a network answer arriving, a timer ending, and an image loading. Both must set state to change the page.
- **Simplest version**: a timer is a computer input. `setTimeout(() => setStatus('done'), 1500)` changes the page with no click at all.
  - Everyday picture: `react.dev` draws a finger for human inputs and ones and zeroes for computer inputs.
- **New code words**:
  - human input: something the user does. `react.dev` Note: "human inputs often require event handlers".
  - computer input: something that happens without the user, such as the server's answer.
  - The arrow diagram: each look is a labeled circle, each change is an arrow with its trigger written on it. A tool on paper, not code.
- **The triggers of the promo box**:
  1. Typing in the box, human: `empty` to `typing`, or back to `empty` when the box is cleared.
  2. Clicking `Apply`, human: `typing` to `checking`.
  3. The server accepts, computer: `checking` to `success`.
  4. The server refuses, computer: `checking` to `error`.
  5. Typing after a refusal: the box stays enabled in `error`, and the next click on `Apply` goes to `checking` again.
- **What happens, in order** (a computer input setting state):
  1. The click handler calls `setStatus('checking')` and starts waiting with `await checkCode(code)`.
  2. The handler pauses, so the synchronous part of the handler is over. React renders the `checking` look.
  3. 1.5 seconds later the fake server answers. No one clicked anything.
  4. The handler goes on after `await` and calls `setStatus('success')` or, in `catch`, `setStatus('error')`.
  5. React renders the new look.
- **Look-alikes**:
  - A click and a server answer look like very different events. For React they are the same: each ends in a setter call, and each setter call asks for a render.
  - The code after `await` sits inside the click handler, but it does not run during the click. It runs 1.5 seconds later, when the computer input arrives.
- **Where did that come from?**:
  - The `checking` look appearing before the server answers, with no second setter call: React processes state updates after the handler's code has run, Lesson 16. An `async` handler's first part ends at `await`, so React can render `checking` while the handler waits. Derived from the `react.dev` final form, whose box is disabled while submitting; exact timing `unconfirmed`.
- **Real beginner mistake**:
  1. The developer thinks only clicks change state and writes the click handler with `setStatus('checking')` and `await checkCode(code)` followed by `setStatus('success')`, with no `try` and no `catch`.
  2. The shopper types `WELCOM` and clicks `Apply`.
  3. The fake server refuses, and nothing sets the next state.
  4. The box stays on `Checking...` and stays disabled forever.
  5. The Console shows an uncaught error for the refused promise. Exact text `unconfirmed`; a likely form is `Uncaught (in promise) Error: This code is not valid.`.
  6. Drawing the arrows shows that `checking` has two ways out, and the `catch` branch is added.
- **Interview depth**:
  - `react.dev`: "In both cases, you must set state variables to update the UI."
  - `react.dev`: drawing states as circles and changes as arrows lets you "sort out bugs long before implementation".
  - Every look in the diagram needs at least one way out; a look with no arrow out is a dead end for the user.
  - Inside the handler, after `await`, the variable `status` still holds the value from the render that created the handler, Lesson 15. So the handler should not read `status` to decide the next step after waiting.
- **React does**:
  - With the `catch` missing, the page stays on `Checking...`: derived, `unconfirmed`.
  - The Console line for a refused promise with no `catch`: `unconfirmed`.
- **Example step**: adds the arrow diagram of the five looks and four triggers, from the `react.dev` diagram "Form states" with our names: `empty`, `typing`, `checking`, `error`, `success`, and the arrows `start typing`, `press Apply`, `server refuses`, `server accepts`. No file changes in this principle.

### Principle 4: Keep one `status` string instead of many true or false values

- **Rule**: Represent the look with as few state variables as possible. One `status` that holds exactly one of the listed strings cannot be in two looks at once. Several true or false values can.
- **Simplest version**: two values, `isChecking` and `isSuccess`. They give four combinations: false and false, true and false, false and true, true and true. Only three are real looks. True and true means "checking and already accepted", which no one designed. One `status` with `'typing'`, `'checking'`, or `'success'` gives exactly three.
  - Everyday picture: a traffic light. It has three lamps, but only one is lit at a time. A light with three separate switches could show red and green together.
- **New code words**:
  - impossible state: a combination of state values that matches no look anyone designed. `react.dev` calls it "a paradox".
  - essential state: a state variable you cannot remove without breaking the component.
  - `code.length === 0`: JavaScript. True when the box is empty. It replaces an `isEmpty` state.
- **What happens, in order** (counting the combinations):
  1. One true or false value has 2 possible values.
  2. Each extra true or false value doubles the count.
  3. Four values, `isTyping`, `isChecking`, `isSuccess`, `isError`, give 16 combinations.
  4. Only four of them are real looks; the other 12 are impossible states.
  5. One `status` string with four allowed values gives exactly four.
- **The `react.dev` clean-up questions, applied to the promo box**:
  1. Does this state cause a paradox? `isChecking` and `isError` can both be true. Merge them into `status`.
  2. Is the same information already in another state variable? `isEmpty` repeats what `code` already says. Use `code.length === 0`.
  3. Can it come from the opposite of another state variable? In `react.dev`, `isError` is replaced by `error !== null`. In our box, `status === 'error'` already says it.
  - Result for the promo box: two essential state variables, `code` and `status`.
- **Look-alikes**:
  - `isChecking` and `status === 'checking'`: both are true while the server checks. They differ in what else can be true at the same time: with booleans, `isError` can also be true; with `status`, nothing else can.
  - `react.dev` keeps `error` as its own state and `status` with three values, `'typing'`, `'submitting'`, `'success'`. Our box puts `'error'` inside `status`, as the syllabus card does. The `react.dev` Deep Dive notes that its version can still hold "a non-null `error`" while `status` is `'success'`; with `'error'` inside `status`, that pair cannot exist. Both designs are valid; the lecture uses one, `status` with four values, and names the other.
- **Where did that come from?**:
  - The number 16: JavaScript has no part in it. It is counting, 2 times 2 times 2 times 2.
  - The empty look with no `'empty'` value in `status`: the JSX computes it from `code.length === 0` on every render.
- **Real beginner mistake** (the paradox `react.dev` warns about):
  1. The developer starts with `isChecking` and `isError`.
  2. On a click, the handler calls `setIsChecking(true)`.
  3. In `catch`, the handler calls `setIsError(true)` and forgets `setIsChecking(false)`.
  4. The page shows `This code is not valid.` and the box is still disabled.
  5. The shopper cannot fix the typo.
  6. With one `status`, `setStatus('error')` replaces `'checking'`, so the box is enabled again.
  - Grounding: `react.dev`: "you never want to show an error message and disable the input at the same time, or the user won't be able to correct the error!"
- **Interview depth**:
  - `react.dev`: "each piece of state is a 'moving piece', and you want as few 'moving pieces' as possible. More complexity leads to more bugs!"
  - `react.dev`: the goal is to "prevent the cases where the state in memory doesn't represent any valid UI that you'd want a user to see."
  - `react.dev` starts its quiz with seven state variables and ends with three; "you can't remove any of them without breaking the functionality."
  - `react.dev` "Avoid contradictions in state": `isSending` and `isSent` replaced by one `status` with `'typing'`, `'sending'`, `'sent'`, and true or false values computed from it, `const isSending = status === 'sending';`.
  - "Your first idea likely won't be the best, but that's ok"; starting with many booleans and merging them is part of the process.
  - The full rules for what should not be state at all: Lesson 22. A reducer for the last impossible pairs: Lesson 27.

### Principle 5: Event handlers only set the next state, and React makes the DOM match

- **Rule**: Connect each trigger to a handler that calls a setter and does nothing else to the page. The JSX already says how each look appears. React changes only the DOM properties that differ from the last render.
- **Simplest version**: the first `react.dev` challenge. Instead of adding and removing a CSS class on click, compute the class from state: `let className = 'picture'; if (isActive) { className += ' picture--active'; }`, then `<img className={className} onClick={() => setIsActive(true)} />`.
  - Everyday picture: the taxi again. The handler names the destination, `setStatus('error')`. React drives.
- **New code words**:
  - `async function handleSubmit(e)`: our handler, made `async` so it can `await` the fake server.
  - `catch` with no name after it, as in `catch { ... }`: JavaScript. Allowed when the handler does not need the error object.
  - `className={...}` computed from state: known from Lesson 02, new here as the replacement for `classList.add` and `classList.remove`.
- **What happens, in order** (the full story in React):
  1. The page opens. `code` is `''` and `status` is `'typing'`. `code.length === 0` is true, so `Apply` is disabled.
  2. The shopper types `WELCOM`. `onChange` calls `setCode('WELCOM')`. React renders, and `Apply` is enabled.
  3. The shopper clicks `Apply`. The form's `onSubmit` calls `handleSubmit`, which calls `e.preventDefault()` and `setStatus('checking')`, then waits at `await`.
  4. React renders `checking`: the box and `Apply` are disabled, `Checking...` appears.
  5. 1.5 seconds later the fake server refuses. JavaScript jumps to `catch`, which calls `setStatus('error')`.
  6. React renders `error`: `Checking...` is removed, the red line appears, the box and `Apply` are enabled.
  7. The shopper fixes the code to `WELCOME` and clicks `Apply`. React renders `checking` again, and the red line is removed because `status === 'error'` is now false.
  8. The fake server accepts. `setStatus('success')` runs.
  9. React renders `success`: the early `return` gives only `Code applied! You get free delivery.`. The red line cannot be on screen, because `status` cannot be `'error'` and `'success'` at once.
- **Look-alikes**:
  - The plain version of Principle 1 and the React version give the same screens on the happy path. They differ at step 7: the plain code needs a command to hide the error line; React removes it because the JSX for `checking` has no error line.
  - The `updateDOM` function of the third `react.dev` challenge and React's commit both redraw the page from variables. They differ in what they touch: `updateDOM` writes every element every time; React skips properties that did not change.
- **Where did that come from?**:
  - The red line disappearing at step 7 with no line of ours removing it: React compares the new JSX with the last one, Lesson 13. The new JSX has no error `<p>`, so the commit removes that node.
  - The form disappearing at step 9: the early `return` gives a different element, Lesson 10, so React removes the form and adds the `<p>`.
- **Real beginner mistake** (DOM poking inside React):
  1. The developer, used to plain code, writes `document.getElementById('apply-button').disabled = true` in `handleSubmit` instead of `setStatus('checking')`.
  2. The button is disabled during the check.
  3. The server refuses, and `catch` calls `setStatus('error')`.
  4. React renders. In the JSX, `disabled` was `false` in the last render and is `false` again, so React does not touch the button.
  5. The button stays disabled, and the shopper cannot try again.
  - Grounding: `react.dev` says React "avoids touching the DOM for properties that have not changed since the last time they were set." The stuck button is derived from that line, `unconfirmed` until the lab runs it.
- **Interview depth**:
  - `react.dev`: the React code "is longer than the original imperative example", but "much less fragile".
  - `react.dev`: expressing interactions as state changes "lets you later introduce new visual states without breaking existing ones" and lets you "change what should be displayed in each state without changing the logic of the interaction itself."
  - Adding a fifth look, such as `expired` with the line `This code has expired.`, adds one value and one piece of JSX. The plain version needs a hide command for it in every other branch.
  - First `react.dev` challenge: "in React you need to describe what you want to see rather than manipulate the UI elements. So you need to calculate both CSS classes based on the current state."
  - First challenge solution: when two returned JSX branches describe the same tree, their nesting must line up, or React recreates the tree and resets its state; details in Lesson 25.
  - React 19 form actions give a pending flag without a hand-made `status`: Lessons 41 to 44.

```jsx title="src/components/PromoCode.jsx"
import { useState } from 'react';
import { checkCode } from '../checkCode.js';

export default function PromoCode() {
  const [code, setCode] = useState('');
  const [status, setStatus] = useState('typing');

  if (status === 'success') {
    return <p>Code applied! You get free delivery.</p>;
  }

  async function handleSubmit(e) {
    e.preventDefault();
    setStatus('checking');
    try {
      await checkCode(code);
      setStatus('success');
    } catch {
      setStatus('error');
    }
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Promo code</h2>
      <input
        className={status === 'error' ? 'code-box code-box--error' : 'code-box'}
        value={code}
        onChange={e => setCode(e.target.value)}
        disabled={status === 'checking'}
      />
      <button disabled={code.length === 0 || status === 'checking'}>
        Apply
      </button>
      {status === 'checking' && <p>Checking...</p>}
      {status === 'error' && <p className="error">This code is not valid.</p>}
    </form>
  );
}
```

## Interview Points

1. Imperative code commands each element: disable this, show that. Declarative code describes the page for each state, and React changes the DOM to match.
2. Imperative code must handle every change from every look to every other look, so one forgotten command leaves two messages on screen.
3. The `react.dev` method has five steps: identify the visual states, find the triggers, represent the state with `useState`, remove non-essential state, connect the handlers.
4. Mock each look first with a `status` prop; showing all looks on one page is a living styleguide or storybook.
5. Triggers are human inputs, such as clicks and typing, and computer inputs, such as a network answer or a timer; both must set state.
6. Draw looks as circles and changes as arrows; every look needs a way out, including the error path of a request.
7. Use one `status` string instead of several booleans; four booleans allow 16 combinations, a four-value string allows exactly four.
8. Remove state that causes a paradox, repeats another state, or is the opposite of another state; compute it instead, such as `code.length === 0`.
9. Handlers only set the next state; the JSX decides what is disabled, shown, or hidden, and classes are computed from state.
10. React touches only the DOM properties that changed, so mixing manual DOM edits with React rendering can leave stale values on screen.
11. A new look adds one value and one branch, without changing the other looks; for the last impossible pairs, a reducer is the next tool, and React 19 actions give a built-in pending flag.
