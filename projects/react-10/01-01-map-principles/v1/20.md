# Q20 Principle Map (River Version v1): Controlled Inputs
- **Version**: River Version (`v1`)
- **Bank Row**: `questions/questions.md` row 20
- **Topic Tag**: `#controlled_inputs` | `❱ CORE`
- **Interview Question**: *How do you make an input, textarea, or select fully controlled by React state?*

## Authorized Scope
- Uncontrolled fields: `<input />`, `<textarea />`, and `<select>` with no `value` keep their own value inside the browser; `defaultValue` (and `defaultChecked` for checkboxes and radios) only gives the starting value, "not the value right now", so a state change never reaches such a field.
- The controlled pair: `value` (or `checked` for checkboxes and radios) forces the field to show the state value, and `onChange` reads the field's new value from the event and writes it into state. When either prop is passed, an `onChange` handler that updates the passed value is required.
- `value` without `onChange`: the field refuses every keystroke, and React logs the read-only Console error, quoted from the corpus; `defaultValue` and `readOnly` are the two other ways out that the error names.
- React's `onChange` fires on every keystroke, like the browser `input` event.
- The synchronous rule: the handler must set state synchronously to `e.target.value` (or `e.target.checked`); whatever the handler writes into state, or fails to write, is what the field shows after the render, because React forces the field back to the state value.
- The same pair on every field type: `<textarea value onChange>` (never text between the tags), `<select value onChange>` (never `selected` on an `<option>`), and `<input type="checkbox" checked onChange>` read through `e.target.checked`.
- A controlled field must receive a string `value` (or a boolean `checked`) for its whole life: starting from `undefined` or `null` and later passing a string triggers the warning that a component is changing an uncontrolled input to be controlled; start state at `''`, or pass `value={someValue ?? ''}`.
- Clearing every field after sending by setting each state variable back to its starting value.
- Out of scope: choosing between controlled fields and uncontrolled fields read with `FormData`, and the re-render cost of every keystroke (`Q40 #forms`), reading a field through a ref (`Q31 #dom_refs`, with the ref box in `Q30 #use_ref`), React 19 form actions, `useActionState`, `useFormStatus`, and `useOptimistic` (`Q41` to `Q44`), designing the form as a set of visual states such as typing, sending, and sent (`Q21 #reacting_to_input`), why the character count is computed from `message.length` and is not its own state (`Q22 #state_structure`), a custom field component controlled by its parent through props (`Q23 #callback_props`, `Q24 #lifting_state`), a field that loses its text because its `key` changes or its component is defined inside another (`Q25 #component_identity`), `useId` for label pairs (`Q52 #use_id`), and `useTransition` and `useDeferredValue` for slow typing (`Q67 #use_transition`, `Q68 #use_deferred_value`).

## General Concepts Introduction (Runway Plan)
- **Opening Essence**:
  - **Furniture-free snippet**: three lines on one name box. Line A: `<input defaultValue="John" />`. Line B: `<input value="John" />`. Line C: `const [name, setName] = useState('John');` with `<input value={name} onChange={e => setName(e.target.value)} />`. All three show `John` when the page opens. Typing `ny` gives `Johnny` in A and C, and nothing changes in B. A button running `setName('')` empties C only; A keeps `Johnny`.
  - **Human image**:
    1. The everyday meaning of **default**: the setting a thing starts with until someone changes it, like the default ringtone of a new phone. `defaultValue` is the starting text, and after that the box keeps whatever the user types.
    2. The everyday meaning of **controlled**: someone else decides what is shown. A departure board at a train station shows only what the station's system sends it; nobody walks up and writes on the board. A controlled field is that board: it shows only what state holds.
    3. Two copies of the same text: an uncontrolled box keeps its own copy inside the browser, and state keeps another; nothing keeps them equal. Controlling the field leaves one copy, the one in state, which developers call the **single source of truth**: one master copy, like the one official clock that every other clock is set from.
    4. `onChange` as the report: the box tells React "the user wants this text now", and the handler decides whether state takes it.
  - **Exact nuance of confusion to state out loud**:
    1. Line A and Line C show the exact same `John` when the page opens and both accept typing, but they are NOT the same thing: in A the box owns the text, in C state owns it, so only C empties when state is set to `''`.
    2. Line B and Line C both write `value`, but they are NOT the same thing: B gives a fixed `value` with no `onChange`, so React forces `John` back after every keystroke.
    3. `value="John"` and `value={name}` while `name` is `'John'` are the exact same thing for the field: in both, React forces the field to show `John`; what makes C editable is `onChange` setting state, not the curly braces.
    4. `onChange` sounds like the browser's `change` event, but it is NOT the same thing: React's `onChange` "fires on every keystroke" and "Behaves like the browser `input` event".
- **Theme**: The `Contact Us` page of an online shop: the customer types `Where is my order?` and clicks `Send`, and the message is still in the box; the developer links the box to state and now the box takes no letters at all.
- **Ways**: Developers really choose between two ways to own a field's value:
  1. Controlled, `value` with `onChange` and state: fits when the page must react to every keystroke (a live count, a field that clears or resets after sending, a button that changes the field).
  2. Uncontrolled, `defaultValue` (or `defaultChecked`) and reading every field once at submit with `new FormData(e.target)`: fits a form whose values matter only when it is sent; named here, chosen and compared in `Q40 #forms`.
- **Recall**:
  - Curly braces in JSX run JavaScript and put its result in place; quotes keep the exact characters as text, so `value="John"` is fixed text and `value={name}` reads a variable (Lesson 03, `Q03 #jsx_expressions`).
  - `condition && <Element />` shows the element only when the condition is true (Lesson 10, `Q10 #conditional_rendering`).
  - React passes the event object `e` to every handler; `e.target` is the element where the event started; `<form onSubmit={handleSend}>` with `e.preventDefault()` stops the browser from reloading the page on submit (Lesson 11, `Q11 #event_handling`).
  - `useState` keeps a value between renders, the setter asks for a new render, and the initial value is used only on the first render (Lesson 12, `Q12 #use_state`).
  - A state change triggers a render, and the commit changes only the DOM nodes that differ (Lesson 13, `Q13 #render_and_commit`).
  - An input with `value={order.customer}` and `onChange={handleChange}`, the handler reading `e.target.value` and `e.target.name`, and the corpus line "React will revert the input after every keystroke back to the `value` that you specified", met as a Preview (Lesson 17, `Q17 #state_objects`).

## Principle Thread
- **Anchor**: A field shows the browser's own value unless React is given a `value` (or `checked`); once it is, React forces the field to show state after every render, so the field changes only when `onChange` writes the new value into state, and state becomes the single source of truth.
- **Axis**: From the box that owns its text, through the pair that hands it to state, to the same pair on every field type and for the field's whole life:
  1. An uncontrolled box keeps its own text; setting state does not reach it (Principle 1).
  2. `value` forces the box to show state, and `onChange` lets the typing reach state; one without the other freezes the box (Principle 2).
  3. What the handler writes into state is exactly what the box shows, so it writes `e.target.value` at once (Principle 3).
  4. The select is controlled by `value` on `<select>`, never `selected` on an `<option>` (Principle 4).
  5. The checkbox is controlled by `checked` and reports through `e.target.checked` (Principle 5).
  6. The `value` is a string from the very first render; starting at `undefined` turns an uncontrolled field into a controlled one and React warns (Principle 6).
- **Why This Axis**: Cause before effect. The reader must first see that a field keeps its own copy (Principle 1) before `value` has a reason. The pair comes next, and its half-written form, `value` alone, is the card's second friction (Principle 2). Only once the pair works can the reader see that the handler decides the text (Principle 3). The select and the checkbox repeat the pair with a different prop or event field, so they follow the text boxes (Principles 4 and 5). The lifetime rule comes last because it needs a field that appears later and starts without a value (Principle 6).

## Principles

### Principle 1: An Uncontrolled Box Keeps Its Own Text, So State Cannot Clear It
- **Handle**: `default-only-starts`
- **Rule**: A field with no `value` prop, such as `<textarea defaultValue="" />`, is uncontrolled: `defaultValue` only gives the starting text, the browser keeps whatever the user types, and setting a state variable that the field never reads changes nothing in the box.
- **Opening Essence**:
  - **Furniture-free snippet**: `<input defaultValue="John" />`; the user types `ny`, and the box shows `Johnny`. Beside it, `const [name, setName] = useState('John');` and a button running `setName('')`: the box still shows `Johnny`, because no line connects `name` to the box.
  - **Human image**: the default ringtone of a new phone: the phone starts with it and then keeps whatever its owner picks; the shop that set the default no longer decides. The box is that phone, and `defaultValue` is the shop's starting choice.
  - **Exact nuance of confusion to state out loud**:

### Principle 2: `value` Forces the Box to Show State, and `onChange` Lets Typing Reach State
- **Handle**: `value-needs-onchange`
- **Rule**: To control a field, pass `value={message}` and `onChange={e => setMessage(e.target.value)}` together, with state starting at `''`: React forces the field to show `message` after every render, and `onChange` runs on every keystroke so state takes the new text; `value` without `onChange` makes typing impossible and logs a Console error.
- **Opening Essence**:
  - **Furniture-free snippet**: `<input value="John" />` beside `<input value={name} onChange={e => setName(e.target.value)} />`. In the first, typing `ny` leaves `John`. In the second, `name` becomes `'Johnny'` and the box shows `Johnny`; `setName('')` empties it.
  - **Human image**: the departure board: the board shows only what the station's system sends; `onChange` is the passenger's request slip handed to the system, and the board changes only after the system takes it.
  - **Exact nuance of confusion to state out loud**:
    1. `value` and `defaultValue` both put `John` in the box at first, but they are NOT the same thing: `value` keeps forcing it after every render, `defaultValue` sets it once.
    2. `value="John"` and `value={name}` with no `onChange` are the exact same thing for the user: a box that refuses every letter.
    3. React's `onChange` and the browser's `change` event share a name but are NOT the same thing: React's fires on every keystroke, "like the browser `input` event"; the browser's `change` event on a text box waits until the box loses focus (`unconfirmed`, browser fact not in the corpus).
- **Root Distinction**:
  - *Junior blurred view*: "`value={message}` connects the box to state, so typing will update it."
  - *Senior grounding*: `value` only carries state into the box; a second line, `onChange`, must carry each keystroke back into state.
- **Real Beginner Mistake (events, in order)**:
  1. The developer replaces `defaultValue=""` with `value={message}` and adds nothing else.
  2. The page loads, and the Console shows the read-only error.
  3. The customer types `Where is my order?`, and no letter stays in the box.
  4. The developer adds `onChange={e => setMessage(e.target.value)}` to the textarea.
  5. The customer types `Where is my order?`, and the text appears.
  6. The customer clicks `Send`; the thanks line appears and the box is empty.
  7. The developer adds `<p>{message.length} / 200</p>` under the box, and it counts up with every letter typed.
- **Interview Depth**:
  - `react.dev`: "**To render a _controlled_ input, pass the `value` prop to it (or `checked` for checkboxes and radios).** React will force the input to always have the `value` you passed."
  - `react.dev` `<Pitfall>`: "**If you pass `value` without `onChange`, it will be impossible to type into the input.**" and "React will revert the input after every keystroke back to the `value` that you specified."
  - The error names three answers: `onChange` for a controlled field, `defaultValue` for a field that only needs a starting value, and `readOnly={true}` for a field that must not change.
  - `onChange` "Fires immediately when the input's value is changed by the user (for example, it fires on every keystroke). Behaves like the browser `input` event." `onInput` "works similarly", and `onChange` is the idiomatic name.
  - A controlled field "makes sense if you needed state anyway", for example to re-render on every edit, or to change the field another way, such as `react.dev`'s `Add 10 years` button; `Send` clearing the box is the same kind of change.
  - The count is computed in render from `message.length`, not stored as a second state; why it should not be state is `Q22 #state_structure`.
  - Every keystroke re-renders the component that holds the state; the cost and its remedies are `Q40 #forms` and `Q68 #use_deferred_value`.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: where `e` comes from, or where `e.target.value` gets the new text; the textarea tag never passes them.
    - **Who supplies it**: React passes the event object `e` to the handler (Lesson 11); `e.target` is the textarea node; the browser has already put the new letter into that node's `value`.
    - **What JavaScript and React do**:
      1. The customer presses `W`; the browser puts `W` into the textarea node.
      2. React calls the `onChange` arrow with `e`; `e.target.value` is `'W'`.
      3. `setMessage('W')` asks for a render.
      4. React renders with `message` at `'W'`, the textarea's `value` is `'W'`, and the count reads `1 / 200`.
  - **Bridge 2**:
    - **Reader will not find**: any line that writes the old text back into the box when `onChange` is missing.
    - **Who supplies it**: React, which forces the field to the `value` it was given.
    - **What JavaScript and React do**:
      1. The browser puts the typed letter into the node.
      2. No handler sets state, so `message` is still `''`.
      3. React puts the node back to `''`, the `value` it was given.
- **React Does**:
  - Console error, quoted from `input.md` and `textarea.md` Troubleshooting: "You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`." Its exact text in the lab's React build, and whether it appears at page load or on the first keystroke: `unconfirmed`.

  - What the Elements panel shows for a controlled textarea while typing: not in the corpus, `unconfirmed`.

### Principle 3: Whatever the Handler Writes Into State Is What the Box Shows
- **Handle**: `handler-decides-text`
- **Rule**: In a controlled field, the text after each keystroke is the state value, not the typed text, so the handler sets state synchronously to `e.target.value` as it is; a handler that writes a changed copy, such as a trimmed one, changes what the user sees, and a handler that writes nothing keeps the old text; cleaning such as trimming happens at `Send`.
- **Opening Essence**:
  - **Furniture-free snippet**: three handlers for one box `value={name}`. A: `setName(e.target.value)`. B: `setName(e.target.value.trim())`. C: `if (e.target.value.length <= 5) setName(e.target.value)`. Typing `Ann Lee`: A shows `Ann Lee`; B shows `AnnLee`; C stops at `Ann L`.
  - **Human image**: the departure board again: the passenger's slip asks for one line, but the board shows what the system sends; if the system edits the line, the board shows the edit, and if it ignores the slip, the board keeps the old line.
  - **Exact nuance of confusion to state out loud**:
    1. `setName(e.target.value)` and `setName(e.target.value.trim())` look like the same line with a harmless clean-up, and for `Ann` they give the same text, but they are NOT the same thing: the second removes every space the moment it is typed.
    2. Refusing to set state in handler C and missing `onChange` in Principle 2 look different, but for the letter that is refused they are the exact same thing: React puts back the last state value.
- **Root Distinction**:
  - *Junior blurred view*: "The box shows what the user typed; my handler only stores a copy, so I can store a tidier copy."
  - *Senior grounding*: in a controlled box, the stored value is the shown value; the handler decides the screen.
- **Real Beginner Mistake (events, in order)**:
  1. The developer adds the `Your name` box with `value={name}` and, to avoid stray spaces, `onChange={e => setName(e.target.value.trim())}`.
  2. The customer types `Anna`, then a space.
  3. The space does not stay in the box.
  4. The customer types `Lee`, and the box shows `AnnaLee`.
  5. The developer changes the handler to `setName(e.target.value)` and trims in `handleSend` instead, `name.trim()`.
  6. The customer types `Anna Lee`, and the box shows `Anna Lee`.
- **Interview Depth**:
  - `react.dev` Troubleshooting "My input caret jumps to the beginning on every keystroke": "you must update its state variable to the input's value from the DOM during `onChange`"; "You can't update it to something other than `e.target.value`", with `setFirstName(e.target.value.toUpperCase())` as the bug; "You also can't update it asynchronously", with `setTimeout(() => { setFirstName(e.target.value); }, 100)` as the bug.
  - Caveat in every field page: "Every controlled input needs an `onChange` event handler that synchronously updates its backing value."
  - Refusing a keystroke on purpose, as the 200-character limit does, relies on the reverting of Principle 2; the browser attribute `maxLength={200}` is the other way to limit length. Where the caret ends up after a refused letter typed in the middle: `unconfirmed`.
  - A caret that jumps can also come from a box that is removed and added again on every keystroke, through a changing `key` or a component defined inside another: `Q25 #component_identity`.
  - `e.target.value` is always a string, even for `type="number"`; `react.dev` converts with `Number(age)`.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any line that removes the space from the box; the handler only sets state.
    - **Who supplies it**: React, which forces the box to the new `name` after the render.
    - **What JavaScript and React do**:
      1. The customer types a space after `Anna`; `e.target.value` is `'Anna '`.
      2. `trim()` returns `'Anna'`, and `setName('Anna')` runs.
      3. React renders and forces the box to `'Anna'`, so the space is gone.
      4. `L` arrives as `'AnnaL'`.
  - **Bridge 2**:
    - **Reader will not find**: a line that blocks the 201st character.
    - **Who supplies it**: our condition, `e.target.value.length <= 200`, which skips the setter, and React, which puts back the 200-character `message`.
    - **What JavaScript and React do**:
      1. The 201st letter enters the node; `e.target.value.length` is `201`.
      2. The condition is false, so `setMessage` does not run.
      3. React forces the node back to the 200-character `message`.

### Principle 4: A Select Is Controlled by `value` on `<select>`, Never `selected` on an `<option>`
- **Handle**: `select-value-on-select`
- **Rule**: Control a select with `<select value={topic} onChange={e => setTopic(e.target.value)}>`, where `topic` matches the `value` of one `<option>`; React does not support the HTML `selected` attribute on `<option>`.
- **Opening Essence**:
  - **Furniture-free snippet**: the HTML habit `<select><option value="tea">Tea</option><option value="coffee" selected>Coffee</option></select>` beside React's `<select value={drink} onChange={e => setDrink(e.target.value)}>` with the same two options and no `selected`, where `drink` starts at `'coffee'`.
  - **Human image**: the old way marks the chosen item on the menu itself; React's way writes the choice once on the order slip, `value` on `<select>`, and the select shows the item whose `value` matches.

    1. `selected` on an `<option>` and `value` on the `<select>` both aim to show `Coffee` first, but they are NOT the same thing in React: `selected` "is not supported".
    2. The `<select value onChange>` pair and the textarea pair of Principle 2 look like different tools, but they are the exact same pair: `value` carries state in, `onChange` with `e.target.value` carries the choice out.
    3. The text the user sees, `Coffee`, and `e.target.value`, `'coffee'`, look like the same thing, but they are NOT: `e.target.value` is the `value` attribute of the chosen `<option>`.
- **Root Distinction**:
  - *Junior blurred view*: "The chosen option is marked on the option, as in HTML."

### Principle 5: A Checkbox Is Controlled by `checked`, and Reports Through `e.target.checked`
- **Handle**: `checkbox-uses-checked`
- **Rule**: Control a checkbox with `<input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(e.target.checked)} />`, with state starting at `false`; a checkbox's answer is `true` or `false` in `e.target.checked`, never `e.target.value`.

### Principle 6: The `value` Is a String From the First Render to the Last
- **Handle**: `value-always-a-string`
- **Rule**: A field cannot switch between uncontrolled and controlled, so a controlled field receives a string `value` on every render, starting with `useState('')`; `useState()` starts at `undefined`, React reads `value={undefined}` as no value, and when the first keystroke makes it a string React warns that a component is changing an uncontrolled input to be controlled.

## Interview Points
1. A field is uncontrolled by default: the browser keeps its value, and `defaultValue` (or `defaultChecked`) only sets the starting value.
2. To control it, pass `value` from state (or `checked` for checkboxes and radios); React then forces the field to show that value after every render, so state is the single source of truth.
3. Always pair it with `onChange`, which fires on every keystroke like the browser `input` event, and set state from `e.target.value`; without `onChange` the field is read-only and React logs an error naming `onChange`, `defaultValue`, or `readOnly`.
4. Update state synchronously to `e.target.value` as typed; whatever the handler stores is what the field shows, so clean-ups like trimming belong at submit, and async or transformed updates cause caret jumps.
5. The same pair works for `<textarea value>` (never children) and `<select value>` (never `selected` on `<option>`), and for checkboxes with `checked` and `e.target.checked`.
6. A controlled field must get a string `value` (or a boolean `checked`) on every render; start state at `''` or pass `value ?? ''`, otherwise React warns that a component is changing an uncontrolled input to be controlled.
7. Because state owns the value, the page can count, limit, and clear fields; uncontrolled fields read with `FormData` at submit are the alternative.
