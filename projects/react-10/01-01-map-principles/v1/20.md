# Q20 Principle Map (River Version v1): Controlled Inputs

- **Version**: River Version (`v1`), written under `skills/v10.4`
- **Bank Row**: `questions/questions.md` row 20
- **Topic Tag**: `#controlled_inputs` | `❱ CORE`
- **Interview Question**: *How do you make an input, textarea, or select fully controlled by React state?*

## Scope

Covered here:
- `onChange` carries each change from the box into state, on every keystroke.
- `value` carries state into the box, so the box shows only what state holds.
- The pair together makes a controlled field. State is the one place that decides the text.
- `defaultValue` sets only the starting text. After that the box keeps its own text, and React leaves it alone. Such a box is uncontrolled.
- `value` without `onChange` freezes the box, with the Console error about a read-only field.
- The handler must set state from `e.target.value`, right away, inside the handler.
- The same pair on `<select>`: `value` on the select, never `selected` on an `<option>`.
- The same pair on a checkbox: `checked` and `e.target.checked`, never `value`.
- A controlled field must start with a string, such as `''`, never `undefined`, or React warns that an uncontrolled input is changing to controlled.
- Clearing a whole form after Send by setting each state back to its start.

## Start of the Lecture

**Simplest version of the chapter's idea**:
- One state, one box, one greeting, one button.
- `const [name, setName] = useState('');`
- `<input value={name} onChange={e => setName(e.target.value)} />`
- `<p>Hello, {name}</p>`
- `<button onClick={() => setName('')}>Clear</button>`
- What the reader sees: typing `John` shows `John` in the box and `Hello, John` below. Clicking `Clear` empties both.
- Everyday picture for *controlled*: the classroom whiteboard. Students call out an answer, that is `onChange`. Only the teacher writes on the board, that is the setter. The board shows only what the teacher wrote, that is `value`. If the teacher writes nothing, the board stays as it was.
- Everyday picture for *uncontrolled*: a student's own notebook. The teacher may write a first line on page one, that is `defaultValue`. After that the student writes freely, and the teacher cannot erase it from the front of the room.
- Everyday picture for *single source of truth*: one station clock that every platform screen copies. When the clock changes, every screen changes. Nobody sets a platform screen by hand.

**The real page problem**:
1. A contact form needs two jobs from its fields at once.
2. First, state must hear every keystroke: a live count under the message box, such as `12 / 200`, must update on every letter through `onChange`.
3. Second, the box must obey state on every render: after Send empties state, `value` must carry that empty state back into the box so the box clears on screen.
4. A box that only reports to state fails the second job; a box that only listens to state fails the first job.

**Example page chosen for this lesson**: `Contact Us`, the contact form of an online shop.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx` rendering `<ContactForm />`, `src/components/ContactForm.jsx`.
- Final parts of the page: `<h1>Contact Us</h1>`, a `Name` box, a `Topic` select with `Delivery`, `Payment`, `Other`, a `Message` text area with `{message.length} / 200` under it, a checkbox `Email me a reply`, an `Email` box that appears only when the checkbox is ticked, and a `Send` button.
- Principle 1 starts with only the message box and the count. Each later principle adds one part.

**Why this page**:
1. Everyone has filled in a contact form. Name, topic, message, a tick box, and Send need no explanation.
2. It needs all three field types of the bank question: input, textarea, select, plus the checkbox of the syllabus card.
3. The live count is the plainest reason to have the text in state on every key.
4. Clearing after Send is the plainest reason for state to write back into the box. The failure is big: the count says `0 / 200` while the old text is still in the box.
5. Actions are typing, picking, ticking, and clicking Send.
6. Outside helper code is small: `<form onSubmit>` and `e.preventDefault()` are known from Lesson 11, labels and checkboxes from Lesson 18, and `.length` is the only new helper.

**Other pages considered**:
1. *The syllabus card's `FeedbackForm`*: same kind of page. Renamed to the contact form every shop site has, with the same four field types, the count, and the clear after Send.
2. *Three boxes holding `John`, labeled A, B, C*: rejected. The writing skill shows it as a counter-example: five new words at once, explained only in comments.
3. *A search box filtering a list*: rejected. It needs filtering and derived lists, which belong to Lesson 22, and it has no reason to clear or to use a select and checkbox.

## Principles

### Principle 1: `onChange` Sends Every Key into State

- **Rule**: When the page must react to what the user types, give the field `onChange`. React calls it on every keystroke, and the handler saves `e.target.value` with the setter.
- **Simplest version**:
  - `const [name, setName] = useState('');`
  - `<input onChange={e => setName(e.target.value)} />`
  - `<p>Hello, {name}</p>`
  - Typing `J`, `o`, `h`, `n` shows `Hello, J`, then `Hello, Jo`, then `Hello, Joh`, then `Hello, John`.
  - Everyday picture: a student calling out each letter to the teacher as they write it.
- **Words to teach**:
  - `onChange`: a prop React gives to every field. React calls our function each time the user changes the text, on every keystroke, not when the user leaves the box. Needed at the moment the count must move while the user types.
  - Known: `useState` and the setter, Lesson 12. `e` and `e.target`, Lesson 11. `e.target.value`, Lesson 17 preview.
  - Helper: `.length`, the number of characters in a string. Half a sentence.
- **Surprises and their steps**:
  - Facts: 1. The Message box has `onChange={handleMessageChange}`. 2. The user presses a key. 3. The count updates immediately on that key, never one letter behind. Question: "Why does `e.target.value` already include the newest letter when the handler runs?"
    1. The user presses a key in the message box.
    2. The browser puts the letter into the box first.
    3. React calls our `onChange` function right after and hands it the event object `e`.
    4. `e.target` is the message box, and `e.target.value` reads its full text at that moment, with the new letter already inside.
    5. `setMessage` saves that text in state.
    6. React renders `ContactForm` again, and `{message.length} / 200` shows the new count.
- **Angle**: In plain JavaScript, a text box has two different events: `change`, which stays quiet while the user types and fires only when the user leaves the box, and `input`, which fires on every keystroke. React wired its `onChange` prop to behave like the browser's `input` event so state stays live on every key. Sources: `input.md` ("Behaves like the browser `input` event"), MDN `HTMLElement: input event`.
- **Look-alikes**:
  - React's `onChange` prop and the browser's `change` event: the browser's `change` event waits until the user leaves the box, whereas React's `onChange` fires on every keystroke like the browser's `input` event. They are NOT the same because a live UI needs to react while the user is still typing.
  - Saving text in a plain variable (`let message = ''`) vs saving text in React state (`useState('')`): a plain variable lives only for one render and never asks React to redraw the page, whereas state persists across renders and triggers a re-render on every update. They are NOT the same because the browser draws the typed letters inside the box on its own, while React draws the character count and only updates it when state triggers a re-render.
  - Reading `e.target.value` vs reading `message` inside `handleMessageChange`: `e.target.value` reads the live DOM box right now (which already holds the new letter), whereas `message` holds the state snapshot from the render before this key was pressed.
- **Where did that come from?**:
  - `e` in `e => setMessage(e.target.value)`: React supplies it.
    1. The browser reports a change in the box.
    2. React builds the event object.
    3. React calls our arrow with it as the first argument.
  - The new letter inside `e.target.value`: the browser supplies it.
    1. The browser has already put the letter into the box before our function runs.
    2. `e.target.value` reads the box's text at that moment.
- **Real beginner mistake** (the corpus challenge "Fix stuck form inputs" in `state-a-components-memory.md`):
  1. The developer keeps the typed text in a plain variable, `let message = '';`.
  2. The handler writes `message = e.target.value;`.
  3. The user types `Hi`.
  4. The box shows `Hi`, but the count stays `0 / 200`.
  5. Nothing asked React to render again, and a plain variable starts over at `''` on every render.
  6. The developer switches to `const [message, setMessage] = useState('');` and `setMessage(e.target.value)`.
  7. The count follows every letter.
- **Interview depth**:
  - `onChange` "Fires immediately when the input's value is changed by the user (for example, it fires on every keystroke)."
  - Every keystroke means one state update and one render. With a large tree this "can get slow". Fix: move the field's state into its own small component so only it renders. Named only: `useDeferredValue`, Lesson 68.
  - Inside the handler, `message` still holds the text from before this key, the snapshot of Lesson 15. The new text is in `e.target.value`.
  - The count is computed from `message` during render, not stored as its own state. Why that matters: Lesson 22.
- **React does**:
  - Page: the count moves with each letter. Confirmed in `lab/cases/20/c1-count`.
  - Console: no message. Confirmed in `lab/cases/20/c1-count`.
- **Example step**: `src/components/ContactForm.jsx` starts with `<h1>Contact Us</h1>`, a `<form>`, a `Message` label around `<textarea onChange={handleMessageChange} />`, `const [message, setMessage] = useState('');`, and `<p>{message.length} / 200</p>`. The box has no `value` yet. `src/App.jsx` renders `<ContactForm />`.
- **Code names**: `ContactForm.jsx`, `App.jsx`, `ContactForm`, `Contact Us`, `Message`, `message`, `setMessage`, `useState('')`, `onChange`, `e`, `e.target`, `e.target.value`, `message.length`, `0 / 200`, `let message = '';`, `message = e.target.value;`, `name`, `setName`, `Hello, John`, `change`, `input`, `onInput`

### Principle 2: `value` Sends State Back into the Box

- **Rule**: When our code must change what the box shows, such as emptying it after Send, give the box `value={message}` as well. Then the box always shows what state holds. `defaultValue` only sets the starting text, and after that React never changes the box.
- **Simplest version**:
  - Two boxes and one `Clear` button that runs `setName('')`.
  - Box with `defaultValue`: `<input defaultValue="" onChange={e => setName(e.target.value)} />`.
  - Box with `value`: `<input value={name} onChange={e => setName(e.target.value)} />`.
  - After typing `John` and clicking `Clear`: the greeting says `Hello,` in both cases, the box with `defaultValue` still shows `John`, and the box with `value` is empty.
  - Everyday picture: the notebook and the whiteboard from the start of the lecture.
- **Words to teach**:
  - `value`: a prop React gives to fields. React makes the box show exactly this text after every render. Needed at the moment Send empties state but the box keeps the text.
  - `defaultValue`: a prop React gives to fields. The text the box starts with, and nothing more. `input.md`: "your JSX only specifies the initial value. It does not control what the value should be right now." Needed at the same moment, as the reason the box did not empty.
  - *Controlled*: a field that gets `value` from state and reports with `onChange`. `input.md`: "React will force the input to always have the `value` you passed."
  - *Uncontrolled*: a field without `value`. It keeps its own text. `input.md`: "An input like `<input />` is *uncontrolled.*"
  - *Single source of truth*: state is the one place that holds the text. The box and the count both copy it.
  - Known: `<form onSubmit>`, `e.preventDefault()`, Lesson 11.
  - Helper: `console.log` to show the sent text, known.
- **Surprises and their steps**:
  - Facts: 1. The box has `value={name}` and `onChange={e => setName(e.target.value)}`. 2. `value` forces the box to match `name` after every render. 3. The user types a letter and it stays in the box. Question: "With `value={name}` locking the box to state, why can I still type?"
    1. The user presses a key, and the browser shows the letter in the box.
    2. React calls `onChange`, and `setName` saves the new text in state.
    3. React renders again, and `value` is now that new text.
    4. React writes that same text into the box, so the letter stays.
- **Angle**: In HTML, `<input value="John">` sets only the starting text, and the browser's DOM calls that starting text `input.defaultValue` while using `input.value` for the live text in the box right now. React renames HTML's starting attribute to `defaultValue` and reserves `value` for the live text on every render. This explains why `setName('')` empties the box with `value={name}` but leaves `John` inside the box with `defaultValue=""`. Sources: MDN `HTMLInputElement.defaultValue`, React `<input>` reference.
- **Look-alikes**:
  - `defaultValue=""` and `value={message}`: `defaultValue` sets only the initial starting text on the first render and then severs the connection between state and the box, whereas `value` locks the box to state as a live mirror on every render. They look identical when the page opens and while typing (because `onChange` updates the count), but they are NOT the same: with `defaultValue`, the box and state live two separate lives, so when Send wipes `message`, the count drops to `0 / 200` while the old text stays in the box. With `value`, the box has no separate life of its own and clears together with the count.
  - Controlled vs uncontrolled is decided by `value`, not by `onChange`. The box in Principle 1 had `onChange` and was still uncontrolled.
- **Where did that come from?**:
  - The empty box after Send, with no line that clears the box itself: React supplies it.
    1. Our code only sets state.
    2. React reads `value` on the next render and writes it into the box.
- **Real beginner mistake** (the syllabus card's friction):
  1. The developer writes `<textarea defaultValue="" onChange={handleMessageChange} />`.
  2. The count works while the user types.
  3. The developer adds `Send`. `handleSend` calls `e.preventDefault()`, logs the message, and calls `setMessage('')`.
  4. The user types `Where is my parcel?` and clicks `Send`.
  5. The count shows `0 / 200`, and the box still shows `Where is my parcel?`.
  6. The user clicks `Send` again, and the Console logs `Sent:` with an empty message, because state holds `''`.
  7. The developer replaces `defaultValue=""` with `value={message}`.
  8. After a reload, `Send` empties the box and the count together.
- **Interview depth**:
  - `input.md`: "**To render a _controlled_ input, pass the `value` prop to it (or `checked` for checkboxes and radios).** React will force the input to always have the `value` you passed."
  - A controlled field is worth it when state is needed anyway, such as to "re-render your UI on every edit", or to offer "multiple ways to adjust the input state (for example, by clicking a button)". Both reasons are on this page: the count and Send.
  - Caveats: "An input can't be both controlled and uncontrolled at the same time." "An input cannot switch between being controlled or uncontrolled over its lifetime."
  - `<textarea>Some text</textarea>` with children is not supported in React and logs a red Console error (`Use the defaultValue or value props instead of setting children on <textarea>.`). Source: `textarea.md` `<Pitfall>`, confirmed in `lab/cases/20/c2-textarea-children`.
  - Controlled against uncontrolled with `FormData` as a design choice: Lesson 40.
- **React does**:
  - Page: with `defaultValue`, the box keeps `Where is my parcel?` after Send while the count shows `0 / 200`. Confirmed in `lab/cases/20/c2-send-default`.
  - Page: with `value={message}`, Send empties the box and count together. Confirmed in `lab/cases/20/c2-send-controlled`.
  - Console: logs `Sent: Where is my parcel?` on first click and `Sent:` on second click with no warning for `defaultValue` + `onChange`. Confirmed in `lab/cases/20/c2-send-default`.
- **Example step**: in `ContactForm.jsx`, adds `<form onSubmit={handleSend}>`, `handleSend(e)` with `e.preventDefault()`, `console.log('Sent:', message)`, and `setMessage('')`, and `<button type="submit">Send</button>`. The text area goes from `defaultValue=""` in the mistake to `value={message}`.
- **Code names**: `value`, `value={message}`, `defaultValue`, `defaultValue=""`, `handleSend`, `e.preventDefault()`, `console.log('Sent:', message)`, `setMessage('')`, `Send`, `<button type="submit">Send</button>`, `<form onSubmit={handleSend}>`, `Where is my parcel?`, `0 / 200`, `Clear`, `setName('')`

### Principle 3: `value` Without `onChange` Freezes the Box

- **Rule**: When a field has `value`, it must also have an `onChange` that sets that same state, right away, to `e.target.value`. Without it, React puts the old text back after every key, and the Console shows an error. A box meant to be read-only says so with `readOnly`.
- **Simplest version**:
  - `const [name, setName] = useState('John');`
  - `<input value={name} />`
  - Typing `ny` after `John`: the box still shows `John`, and the Console shows the read-only field error.
  - Everyday picture: the whiteboard again. A student calls out a letter, but the teacher is not listening, so the board never changes.
- **Words to teach**:
  - The read-only field error: React's message in the Console when `value` has no `onChange`. Needed the moment the Name box refuses letters.
  - `readOnly`: a prop that says on purpose that the box cannot be edited, and stops the error. Name only, one line.
  - Known: `value` and `onChange`, Principles 1 and 2. `e.target.value`, Lesson 17.
  - Helper: `if` with `.length` for the 200 limit in the last example step. Known JavaScript.
- **Surprises and their steps**:
  - Facts: 1. The box has `value={name}` (`'John'`) and no `onChange`. 2. The user presses `n`. 3. The box still shows `John`. Question: "When a box has `value` and no `onChange`, what happens inside a single keystroke?"
    1. The browser puts `n` into the box, so for a split second the box holds `Johnn`.
    2. The box has no `onChange`, so no handler runs, and `name` stays `John`.
    3. React sees that the box no longer matches `value={name}` and immediately writes `John` back into the box.
  - Facts: 1. The message box holds 200 characters. 2. `handleMessageChange` checks `if (e.target.value.length <= 200)` before calling `setMessage`. 3. The user types a 201st letter and it disappears. Question: "How does skipping `setMessage` enforce a 200-character limit?"
    1. The browser puts the 201st letter into the box.
    2. React calls `handleMessageChange`. The new text is 201 characters long, so the handler skips `setMessage`.
    3. `message` still holds the 200 characters, so React writes those 200 characters back into the box, and the extra letter disappears.
  - Facts: 1. The handler wraps `setName(e.target.value)` inside `setTimeout(..., 100)`. 2. The user types into the box. 3. React reverts the box right after the keystroke. Question: "Why does delaying `setName` inside `setTimeout` break typing?"
    1. The user presses a key, and the browser shows the letter in the box.
    2. `handleNameChange` starts a timer and finishes right away without changing `name`.
    3. React sees that `name` has not changed when the handler finishes and immediately puts the old text back into the box.
    4. When the timer runs 100 milliseconds later, the box has already been wiped back to the old text during typing.
- **Angle**: An HTML `readOnly` box tells the browser to block typing at the keyboard. A React box with `value` and no `onChange` is different: the browser accepts every keystroke, and React immediately overwrites the box back to the unchanged state. Skipping the setter on purpose uses that exact same overwrite to reject any character past 200. Sources: `input.md` `<Pitfall>` ("React will revert the input after every keystroke back to the `value` that you specified").
- **Look-alikes**:
  - `<input value={name} onChange={e => setName(e.target.value)} />`, `<input value={name} />`, `<input defaultValue={name} />`, and `<input value={name} readOnly />`:
    - `value` + `onChange` makes an editable controlled box where every keystroke updates state.
    - `value` alone without `onChange` makes state the only source of truth without giving state a way to change, so React overwrites every keystroke and prints a red Console error.
    - `defaultValue` sets only the starting text on an uncontrolled box.
    - `value` + `readOnly` marks an intentionally frozen display box and silences the Console error.
  - `setName(e.target.value)` vs `setTimeout(() => setName(e.target.value), 100)` vs `setName(e.target.value.toUpperCase())`:
    - Saving `e.target.value` right away keeps the box and state in sync.
    - Delaying inside `setTimeout` leaves state unchanged when the handler exits, so React reverts the keystroke immediately.
    - Transforming the string with `toUpperCase()` makes React overwrite the box with a different string than the browser just inserted, jumping the cursor to the end of the box.
- **Where did that come from?**:
  - The error text, with no `console.error` in our code: React supplies it in development when a field has `value` and no `onChange`.
- **Real beginner mistake** (`thinking-in-react.md` Step 4 shows the same frozen search box):
  1. The developer adds a `Name` box above the message, with `const [name, setName] = useState('');`.
  2. Copying the idea of Principle 2, they write `<input value={name} />` and forget `onChange`.
  3. The page opens with an empty Name box and the red Console error.
  4. The user clicks into it and types `Anna`.
  5. The box stays empty.
  6. The developer adds `onChange={e => setName(e.target.value)}`.
  7. After a reload, `Anna` appears letter by letter, and the Console is clean.
- **Interview depth**:
  - `input.md` Caveats: "Every controlled input needs an `onChange` event handler that synchronously updates its backing value."
  - The error offers three ways out: `onChange` to make it editable, `defaultValue` if only a starting text was wanted, `readOnly` if frozen on purpose.
  - The handler must set state to `e.target.value`, not to a changed copy such as `toUpperCase()`, and not later inside `setTimeout`. Both are listed under "My input caret jumps to the beginning on every keystroke".
  - Another cause of a jumping caret: the input is removed and added again on every keystroke, from a changing `key` or a component defined inside another component. Lesson 25 owns it, and Lesson 04 showed the nested component.
  - `thinking-in-react.md`: "If you try to type or check the box in the example above, you'll see that React ignores your input. This is intentional."
- **React does**:
  - Console, quoted from `input.md` and confirmed in `lab/cases/20/c3-readonly-john` and `c3-readonly-anna`: ``You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.``
  - Page: the Name box stays on `John` (or empty) while typing. Confirmed in `lab/`.
  - Page: the 201st letter of the message disappears while the first 200 stay. Confirmed in `lab/cases/20/c3-limit-200`.

The message handler becomes `handleMessageChange(e)`, which calls `setMessage(e.target.value)` only when `e.target.value.length <= 200`. `handleSend` also logs `name` and runs `setName('')`.

### Principle 4: The Same Pair on a Menu and a Tick Box

- **Rule**: A `<select>` is controlled the same way, with `value` on the select and `onChange` reading `e.target.value`. Never mark an `<option>` as `selected`. A checkbox uses `checked` instead of `value`, and its handler reads `e.target.checked`, which is `true` or `false`.
- **Simplest version**:
  - `const [fruit, setFruit] = useState('orange');`
  - `<select value={fruit} onChange={e => setFruit(e.target.value)}>` with options `apple`, `banana`, `orange`.
  - `const [agree, setAgree] = useState(false);`
  - `<input type="checkbox" checked={agree} onChange={e => setAgree(e.target.checked)} />`
  - Everyday picture: the same whiteboard, now with a chosen word and a ticked square written on it.
- **Words to teach**:
  - `value` on `<select>`: which option is chosen. It must match the `value` of one `<option>`. Needed when `Topic` must start on `Delivery` and return to it after Send.
  - `<option value="delivery">`: the string the select reports when this option is picked. The text between the tags is what the user reads.
  - `checked`: the checkbox's tick, `true` or `false`, from state. Needed when Send must untick `Email me a reply`.
  - `e.target.checked`: the tick right after the click, supplied by the browser.
  - Name only: `selected` on `<option>` is not supported in React. `defaultChecked` is the checkbox's starting tick, like `defaultValue`.
  - Known: checkbox and `<label>`, and that a checkbox without `checked` keeps its own tick in the browser, Lesson 18.
- **Surprises and their steps**:
  - Facts: 1. The checkbox has `checked={wantsReply}` and `onChange={e => setWantsReply(e.target.value)}`. 2. The user clicks once and the box ticks. 3. The user clicks a second time and the box refuses to untick. Question: "Why does reading `e.target.value` on a checkbox trap it in the ticked state?"
    1. Most checkboxes have no `value` attribute of their own, so the browser sets `e.target.value` to the fixed string `'on'`, which never changes when you click.
    2. On the first click, `setWantsReply` saves `'on'`. Because `'on'` is a non-empty string, React treats `checked={wantsReply}` as ticked.
    3. On the second click, the user tries to untick the box, but `e.target.value` is still `'on'`. So `wantsReply` stays `'on'`, and React puts the tick right back.
- **Angle**: Plain HTML marks starting choices with `selected` on `<option>` and `checked` on `<input type="checkbox">` (which the browser's DOM calls `option.defaultSelected` and `input.defaultChecked`). React renames uncontrolled starting props to `defaultValue` and `defaultChecked`, puts `value` on the `<select>` tag itself so one state variable controls the whole menu, and pairs `checked` with `e.target.checked` on checkboxes because `e.target.value` on a checkbox is the fixed string `'on'`. Sources: `select.md`, `option.md`, `input.md` `<Pitfall>`, MDN `HTMLInputElement.value`.
- **Look-alikes**:
  - `<select value="payment">` vs `<option value="payment" selected>`: in React, `value` on `<select>` highlights whichever `<option>` has a matching `value` from one state variable, whereas `selected` on `<option>` is an unsupported HTML habit that prints a red Console error.
  - `checked` + `e.target.checked` vs `value` + `e.target.value` on a checkbox: `checked` and `e.target.checked` carry the boolean tick (`true` or `false`), whereas `e.target.value` on a checkbox without a `value` attribute is always the fixed string `'on'`, which locks the checkbox on after the first click.
- **Where did that come from?**:
  - The string `'payment'` in `e.target.value`, when the user read `Payment`: the browser supplies it from the picked `<option value="payment">`.
    1. The user picks `Payment`.
    2. The select's value becomes the option's `value` attribute, `'payment'`.
    3. React calls `onChange`, and `e.target.value` is `'payment'`.
- **Real beginner mistake** (the corpus `<Pitfall>` on checkboxes):
  1. The developer adds `Email me a reply` with `checked={wantsReply}`.
  2. Copying the text box handler, they write `onChange={e => setWantsReply(e.target.value)}`.
  3. The user ticks the box, and it looks ticked.
  4. The user clicks again to untick it, and it stays ticked.
  5. The developer changes the handler to `setWantsReply(e.target.checked)`.
  6. After a reload, the box ticks and unticks with each click.
- **Interview depth**:
  - `select.md`: `value` "Controls which option is selected. Every value string match the `value` of some `<option>` nested inside the `<select>`."
  - Select `onChange` "Fires immediately when the user picks a different option."
  - `select.md` `<Pitfall>`: "**If you pass `value` without `onChange`, it will be impossible to select an option.**"
  - `checked` without `onChange` gives its own Console error, which names `defaultChecked`.
  - `<select multiple={true}>` takes an array as `value` and reads `e.target.selectedOptions`. Name only.
- **React does**:
  - Console for `selected` on an `<option>`, confirmed in `lab/cases/20/c4-option-selected`: ``Use the `defaultValue` or `value` props on <select> instead of setting `selected` on <option>.``
  - Page: reading `e.target.value` on the checkbox ticks it on the first click and keeps it ticked on the second click. Confirmed in `lab/cases/20/c4-checkbox-value-bug`.
- **Example step**: in `ContactForm.jsx`, adds `const [topic, setTopic] = useState('delivery');` and a `Topic` label around `<select value={topic} onChange={e => setTopic(e.target.value)}>` with `<option value="delivery">Delivery</option>`, `<option value="payment">Payment</option>`, `<option value="other">Other</option>`. Adds `const [wantsReply, setWantsReply] = useState(false);` and a label around `<input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(e.target.checked)} />` with the text `Email me a reply`. `handleSend` logs both and runs `setTopic('delivery')` and `setWantsReply(false)`.
- **Code names**: `Topic`, `topic`, `setTopic`, `'delivery'`, `'payment'`, `'other'`, `Delivery`, `Payment`, `Other`, `<select value={topic} onChange={e => setTopic(e.target.value)}>`, `<option value="payment">`, `selected`, `Email me a reply`, `wantsReply`, `setWantsReply`, `checked={wantsReply}`, `e.target.checked`, `e.target.value`, `'on'`, `defaultChecked`, `multiple`, `fruit`, `agree`

### Principle 5: A Controlled Box Starts with an Empty String

- **Rule**: The state behind `value` must hold a string from the first render, so a box that starts empty starts with `useState('')`. If `value` is `undefined` first and a string later, React warns that an uncontrolled input is changing to controlled, because a field cannot switch over its lifetime.
- **Simplest version**:
  - `const [city, setCity] = useState();`
  - `<input value={city} onChange={e => setCity(e.target.value)} />`
  - Typing the first letter shows the warning. With `useState('')`, no warning.
  - Everyday picture: a notebook that is suddenly declared a whiteboard halfway through the lesson. Nobody knows who owns the page any more.
- **Words to teach**:
  - The warning "A component is changing an uncontrolled input to be controlled": React's message when `value` goes from `undefined` to a string. Needed the moment the user types the first letter of the email.
  - Known: `useState()` with no starting value gives `undefined`, JavaScript function argument rule. `&&` in JSX, Lesson 10.
  - Helper, interview only: `??`, which uses the right side when the left side is `null` or `undefined`.
- **Surprises and their steps**:
  - Facts: 1. `const [city, setCity] = useState();` passes no argument, so `city` starts as `undefined`. 2. The user types `a` and `a` appears in the box. 3. The Console prints the uncontrolled-to-controlled warning. Question: "What happens between the first render and the first keystroke when state starts with `useState()`?"
    1. When the page opens, `city` is `undefined`. To React, `value={undefined}` is the same as giving the box no `value` prop at all, so React creates the City box as an **uncontrolled** box.
    2. When the user types `a`, `setCity` saves the string `'a'`.
    3. On the next render, `value={city}` is now the string `'a'`, so the very same box suddenly becomes a **controlled** box, and React prints the Console error.
- **Angle**: In JavaScript, calling `useState()` with empty parentheses passes `undefined`, and to React `value={undefined}` means "no `value` prop was passed at all." That makes the box start life uncontrolled and flip to controlled on the very first keystroke. Starting with `useState('')` passes a real string from render one so the box is controlled from birth. Sources: `input.md` Troubleshooting ("A component is changing an uncontrolled input to be controlled").
- **Look-alikes**:
  - `useState('')` vs `useState()`: `useState('')` starts state with an empty string so `value` is defined from the first render and the box is controlled for its entire life, whereas `useState()` starts state as `undefined` so the box starts uncontrolled and flips to controlled on the first keystroke. Both draw a blank box when the page opens, but they are NOT the same.
  - Resetting state with `setEmail('')` vs `setEmail(undefined)` or `setEmail(null)`: `setEmail('')` keeps the box controlled with an empty string, whereas `undefined` or `null` flips a controlled box back to uncontrolled.
- **Where did that come from?**:
  - `undefined` in `city` or `email`, with no `undefined` written in our code: JavaScript supplies it.
    1. `useState()` receives no starting value.
    2. A missing argument is `undefined` in JavaScript.
    3. React stores `undefined` as the first state.
- **Real beginner mistake** (`input.md` Troubleshooting: the value "might be initialized to `null` or `undefined`"):
  1. The developer adds an `Email` box that appears only when `Email me a reply` is ticked: `{wantsReply && <label>Email <input value={email} onChange={e => setEmail(e.target.value)} /></label>}`.
  2. Since the email is not needed at first, they write `const [email, setEmail] = useState();`.
  3. The user ticks `Email me a reply`, and the empty `Email` box appears.
  4. The user types `a`.
  5. The letter appears, and the Console shows the uncontrolled-to-controlled warning.
  6. The developer writes `useState('')`.
  7. After a reload, typing into `Email` gives no warning.
- **Interview depth**:
  - `input.md`: "If you provide a `value` to the component, it must remain a string throughout its lifetime." "A controlled component should always receive a string `value`, not `null` or `undefined`."
  - When the value comes from an API, start with `''`, or pass `value={someValue ?? ''}`.
  - The checkbox version: "if you pass `checked` to a checkbox, ensure it's always a boolean."
  - Clearing with `setEmail(null)` or `setEmail(undefined)` instead of `''` makes the box go the other way, controlled to uncontrolled.
  - Send clears the whole form by setting every state back to its start. No code touches a box directly.
- **React does**:
  - Console, confirmed in `lab/cases/20/c5-city-undef` and `c5-email-undef`: `A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen. Decide between using a controlled or uncontrolled input element for the lifetime of the component. More info: https://react.dev/link/controlled-components`
  - Page: the `Email` box accepts the letters in both versions, and disappears when `wantsReply` is reset to `false` on Send. Confirmed in `lab/cases/20/c5-full-form`.
- **Example step**: in `ContactForm.jsx`, adds `const [email, setEmail] = useState('');`, first as `useState()` for the mistake, and `{wantsReply && <label>Email <input value={email} onChange={e => setEmail(e.target.value)} /></label>}` under the checkbox. `handleSend` now logs every field and clears all of them: `setName('')`, `setTopic('delivery')`, `setMessage('')`, `setWantsReply(false)`, `setEmail('')`. This is the finished page.
- **Code names**: `Email`, `email`, `setEmail`, `useState()`, `useState('')`, `undefined`, `null`, `{wantsReply && ...}`, `value={email}`, `value={someValue ?? ''}`, `??`, `city`, `setCity`, `A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen. Decide between using a controlled or uncontrolled input element for the lifetime of the component. More info: https://react.dev/link/controlled-components`

## Interview Points

1. A controlled field takes what it shows from state through `value`, or `checked` for checkboxes and radios, and reports each change through `onChange`.
2. `onChange` in React fires on every keystroke, like the browser's `input` event, and the handler sets state to `e.target.value`.
3. After each render React writes the state into the field, so state is the single source of truth: setting state to `''` empties the box.
4. `defaultValue` and `defaultChecked` only set the starting value. Such a field is uncontrolled and keeps its own text.
5. `value` without `onChange` freezes the field, React reverts each keystroke, and the Console shows the read-only field error. `readOnly` marks a frozen field on purpose.
6. The handler must update state synchronously and to exactly `e.target.value`, or the caret can jump.
7. A `<select>` is controlled with `value` on the select, not `selected` on an `<option>`. A checkbox uses `checked` and `e.target.checked`.
8. A controlled field must start with a string such as `''`, never `undefined` or `null`, or React warns that an uncontrolled input is changing to controlled.
9. Every keystroke re-renders the component that holds the state, so keep a field's state in a small component when the page is large.
