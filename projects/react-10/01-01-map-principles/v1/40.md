# Q40 Principle Map (River Version v1): Choosing Between Controlled State and Uncontrolled FormData

- **Version**: River Version (`v1`), written under `skills/v10.7`
- **Bank Row**: `questions/questions.md` row 40
- **Topic Tag**: `#forms` | `❱ CORE`
- **Interview Question**: *Should a form use controlled state or uncontrolled FormData, and how do you choose?*

## Scope

Covered here:
- Reading every box of a form once, at submit, with `new FormData(e.currentTarget)` and `formData.get('email')`. Each box needs a `name`, and that `name` is the key in the form data.
- What typing costs in each way: an uncontrolled box keeps its text in the browser, and React renders nothing while the user types; a controlled box sets state on every keystroke, and React renders the component again on every keystroke.
- Where a controlled box wins: the page must change on every edit, such as a password hint under the box, or the value has more than one way to change, such as a button.
- One form may mix both ways: the email box stays uncontrolled, the password box is controlled. At submit, the email comes from `FormData` and the password comes from state, as `form.md` says.
- Keeping the keystroke renders small: the state lives in the component that holds the form, so the rest of the page does not render on every keystroke.

## Start of the Lecture

**Opening Essence of the chapter** (a way of working, so it opens on a real screen in plain words, then the smallest code):
1. The screen: the Sign up form on almost every website. It has an Email box, a Password box, one hint line under the password, and a Sign up button.
2. The user types `john@mail.com` into the Email box. Nothing else on the page changes. The site needs the email only once, when the user clicks Sign up.
3. The user types a password. The hint line under it changes while the user types: it reads `Use 8 or more characters` until the password has 8 characters, then `Looks good`.
4. The question this screen raises for the developer: does every box need a state variable, or only the box whose text the page must show while the user types?
5. The two ways, as they appear in code:
   - With `name`: `<input name="email" />`, read at submit with `new FormData(e.currentTarget)`.
   - With `value` and `onChange`: `<input value={password} onChange={e => setPassword(e.target.value)} />`.
6. The confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both boxes show the typed text the same way on the screen. Only the box with `value` and `onChange` makes React render the component again after every keystroke by the user.
7. The key idea to remember: choose per box. Keep a box in state only when the page must change while the user types; otherwise let the browser keep the text and read it at submit.
8. What is at stake for the user: in a large form where every box is in state, every keystroke renders the whole form, and the docs say this "can get slow". The syllabus card's case: a forty-box admin form lags on low-end laptops and phones.
9. Where readers usually go wrong: after Lesson 20 they put every box in state by habit, even boxes that are only read when the user clicks Sign up.

**Theme**: a sign up form where one box needs live feedback and the other is only read at submit.

**Ways**:
1. Uncontrolled box with `name`, read once at submit with `FormData`: fits boxes that are only inspected on submit.
2. Controlled box with `value` and `onChange` in state: fits boxes whose value the page shows or checks on every edit, such as a password hint, or whose value a button also changes.
3. Named only: reading one box through a ref, Lesson 31.
4. Named only: a form action that receives `FormData` without `e.preventDefault()`, Lesson 41.

**Example page chosen for this lesson**: `Sign up`, the account sign up page of a small online shop.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx` rendering `<SiteHeader />` and `<SignupForm />`, `src/components/SiteHeader.jsx`, `src/components/SignupForm.jsx`.
- Final parts of the page: a header with the shop name `MyShop`, an `Email` box, a `Password` box with `type="password"`, a hint line under it, and a `Sign up` button.
- Principle 1 starts with the Email box and the button only. Principle 3 adds the Password box and the hint. Principle 4 shows the header next to the form.

**Why this page**:
1. Everyone has filled in a sign up form. An email, a password, and one button need no explanation.
2. It holds both cases of the question on one screen: the email is only read when the user clicks Sign up, and the password hint must follow every keystroke.
3. A live password hint is a case developers really build, and the syllabus card names "password strength meters" as the kind of field that needs control.
4. Actions are typing and clicking one button.
5. Outside helper code is small: `type="password"` and `.length` are the only helper words.

**Other pages considered**:
1. *The syllabus card's forty-box admin article form*: rejected as the page. The reader cannot hold forty boxes; the forty boxes stay as a fact in What is at stake and in Interview depth.
2. *The search box of the docs' `form.md`*: rejected. It has no box that needs live feedback, so it shows only one of the two ways.
3. *The Contact Us form with a character count*: rejected. Lesson 20 used that page for controlled boxes.
4. *A post composer with a character limit*: close. Rejected because its single box needs control, so it has no box that is only read at submit.

**Older facts the reader needs**:
- `onSubmit` on `<form>`, `e.preventDefault()` stops the browser from reloading the page: Lesson 11.
- `e.target` is the node where the event happened, `e.currentTarget` is the node whose handler runs: Lesson 11.
- A state change makes React call the component function again: Lessons 12 and 13.
- In development, `<StrictMode>` calls each component function twice: Lesson 14.
- `value` with `onChange` makes a box controlled; a box with only `defaultValue`, or with nothing, is uncontrolled and keeps its own text: Lesson 20.

## Principles

### Principle 1: name Puts the Email into FormData

- **Rule**: when a box has a `name` and the form's `onSubmit` handler calls `new FormData(e.currentTarget)`, `formData.get(name)` returns the box's text at the moment of submit, with no state.
- **Move**: Smallest code first, because `FormData` is new and the reader has not seen a form read without state.
- **Opening Essence**:
  - The smallest code: one form, one box `<input name="email" />`, one `Sign up` button, one `handleSubmit` that logs `formData.get('email')`.
  - The user types `john@mail.com` and clicks Sign up; the Console shows `john@mail.com`.
  - The key idea: the browser already keeps the text of every box; `FormData` collects it by each box's `name` when the user submits.
  - What is at stake: a box without `name` is missing from the form data, so the value the code reads is empty.
  - Where readers go wrong: they think a box must be in state for the code to read it.
- **Root Distinction**:
  - Junior: "To read what the user typed, I need a state variable."
  - Senior: the browser holds the typed text; state is needed only when React must show that text during typing.
- **Simplest version**:
  - `function handleSubmit(e) { e.preventDefault(); const formData = new FormData(e.currentTarget); console.log(formData.get('email')); }`
  - `<form onSubmit={handleSubmit}><input name="email" /><button type="submit">Sign up</button></form>`
- **Words to teach**:
  - `name`: an attribute of the box, from HTML, passed to the DOM by React. The docs: "The `name` you specified will be used as a key in the form data, for example `{ firstName: "Taylor" }`." Needed when the reader writes the Email box.
  - `FormData`: a browser object, not React. `new FormData(form)` collects every named box of that form. Needed in `handleSubmit`.
  - `formData.get('email')`: a browser method. Returns the value stored under that `name`. Needed on the line that logs the email.
  - Known words: `<form>`, `onSubmit`, `e.preventDefault()`, `e.currentTarget`, `e.target`: Lesson 11. Uncontrolled box: Lesson 20. `<label>`: Lesson 18.
  - Helper words: `new`, `console.log`.
- **Side by side**:
  - "with `e.target`" and "with `e.currentTarget`" inside `onSubmit` on the form: the exact same thing here. The submit event happens on the form, and the handler sits on the same form, so both are the `<form>` node. The docs' examples write `new FormData(e.target)`; the syllabus card writes `new FormData(e.currentTarget)`. The equality on the submit event is `unconfirmed` in the React docs; the lab confirms it.
- **Surprises**:
  1. The developer forgets `name` on the box.
  2. The user types `john@mail.com` and clicks Sign up.
  3. The page does not reload and no error appears.
  4. The Console shows `null`, because the form data has no entry called `email`. The value `null` is MDN behavior of `FormData.get()`; the exact Console line is `unconfirmed`.
- **Where did that come from?**:
  - `e` in `handleSubmit`: React passes the event object to the handler (Lesson 11).
  - `e.currentTarget`: React sets it to the node whose handler runs, here the `<form>`.
  - `formData`: our code makes it with `new FormData(...)`; the browser fills it with every named box of the form, at that moment.
  - `'email'` inside `formData.get('email')`: it is the same string as `name="email"` on the box. Nothing else links them.
- **Real beginner mistake**:
  1. The developer writes the Email box without `name`, because a box in state never needed one.
  2. The user types an email and clicks Sign up.
  3. `formData.get('email')` returns `null`.
  4. The sign up code sends no email.
- **Interview depth**:
  - What keys the form data uses: the `name` of each box.
  - What `FormData` reads: the DOM values at the moment of submit, not the JSX.
  - The docs' way to get a plain object: `Object.fromEntries(formData.entries())`.
  - The docs' way to send it: `fetch('/some-api', { method: form.method, body: formData })`.
  - Without `e.preventDefault()`, the browser sends the form to the current URL and refreshes the page (docs).
  - In Lesson 41, a form action receives the same `FormData` without `e.preventDefault()`.
- **React does**:
  - Page: the box shows `john@mail.com`; nothing else changes on submit.
  - Console: `john@mail.com` (`unconfirmed` format); `null` when `name` is missing (`unconfirmed` format).
  - Elements panel: `<input name="email">` inside `<form>`; React adds no `value` attribute to an uncontrolled box (`unconfirmed`).
- **Example step**: `SignupForm.jsx` gets the form with the Email box, the Sign up button, and `handleSubmit`. `App.jsx` renders `<SiteHeader />` and `<SignupForm />`.
- **Code names**: `SignupForm.jsx`, `App.jsx`, `SiteHeader.jsx`, `SignupForm`, `handleSubmit`, `e`, `e.preventDefault()`, `e.currentTarget`, `e.target`, `formData`, `new FormData(e.currentTarget)`, `formData.get('email')`, `name="email"`, `'john@mail.com'`, `Sign up`, `null`

### Principle 2: Typing in the Email Box Skips the Render

- **Rule**: while the user types into an uncontrolled box, React does not render the component; while the user types into a controlled box, React renders the component once for every keystroke.
- **Move**: Side by side, because both boxes look and behave the same on the screen, and only a render log shows the difference.
- **Opening Essence**:
  - The smallest code: `console.log('SignupForm rendered')` at the top of `SignupForm`, then two versions of the Email box.
  - The confusion: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both versions show `john` in the box after the user types `john`.
  - Where they differ: the Console shows no new line for the box with `name` only; the box with `value` and `onChange` adds one line for each of the 4 keystrokes.
- **Root Distinction**:
  - Junior: "Both boxes show what I type, so they cost the same."
  - Senior: a controlled box sets state on every keystroke, and each state change renders the whole component again.
- **Simplest version**:
  - Version with `name`: `<input name="email" />`
  - Version with `value` and `onChange`: `const [email, setEmail] = useState('');` and `<input value={email} onChange={e => setEmail(e.target.value)} />`
  - `console.log('SignupForm rendered');` as the first line of `SignupForm`.
- **Words to teach**:
  - None new. This principle teaches the cost of the words of Lesson 20.
  - Known words: `useState`, setter: Lesson 12. Render: Lesson 13. `<StrictMode>` calls the component twice in development: Lesson 14. Controlled, uncontrolled, `value`, `onChange`: Lesson 20.
  - Helper words: `console.log`, React DevTools.
- **Side by side**:
  - "with `name`" and "with `value` and `onChange`": NOT the same thing. The same text on the screen, but only the second one renders the component on every keystroke.
  - The docs: "When you use a controlled input, you set the state on every keystroke. If the component containing your state re-renders a large tree, this can get slow."
- **Surprises**:
  1. The page loads and the Console shows `SignupForm rendered`, twice in development because of `<StrictMode>` (Lesson 14).
  2. The user types `john` into the box with `name`.
  3. The Console shows no new line. The browser keeps the text, and no state changed.
  4. The developer switches to the box with `value` and `onChange`.
  5. The user types `john` again.
  6. The Console shows `SignupForm rendered` after each of the 4 keystrokes, twice each in development. With React DevTools installed, the second log of each pair "will appear slightly dimmed" (StrictMode docs). The exact count is `unconfirmed`; the lab confirms it.
- **Where did that come from?**:
  - `email` and `setEmail`: our code gets them from `useState('')`.
  - `e.target.value` in `onChange`: the box's text after the keystroke, from the browser (Lesson 20).
- **Real beginner mistake**:
  1. After learning controlled boxes, the developer gives every box of a forty-box admin form its own `useState`, as in the syllabus card.
  2. The user types one letter in any box.
  3. React renders the whole form with all forty boxes.
  4. On a low-end laptop or phone, letters appear late while the user types.
- **Interview depth**:
  - Under the hood (syllabus card): an uncontrolled box lets the browser keep its own text; a controlled box sends each change through state, a render, and back into the DOM.
  - The render is the cost, not the box: a small form with a few controlled boxes is fine.
  - Strict Mode's double render is development only (Lesson 14).
  - A box cannot switch between controlled and uncontrolled over its lifetime (input.md Caveats).
- **React does**:
  - Page: the box shows `john` in both versions.
  - Console: `SignupForm rendered` on load; no new line while typing with `name`; one new line per keystroke with `value` and `onChange` (counts `unconfirmed`).
  - Elements panel: no difference to see; the `<input>` node stays the same node in both versions (`unconfirmed`).
- **Example step**: `SignupForm.jsx` gets `console.log('SignupForm rendered')`. The Email box shows both versions side by side, then keeps the version with `name`.
- **Code names**: `SignupForm.jsx`, `console.log('SignupForm rendered')`, `email`, `setEmail`, `useState('')`, `value={email}`, `onChange`, `e.target.value`, `name="email"`, `john`, `<StrictMode>`

### Principle 3: The Password Hint Follows State

- **Rule**: when the page must change while the user types, such as a hint under the box, keep that box in state with `value` and `onChange`, and at submit read it from state, not from `FormData`.
- **Move**: Side by side, because a password box with `name` only and a controlled password box look the same until the hint must change.
- **Opening Essence**:
  - The real screen: the Password box with the hint line `Use 8 or more characters` under it.
  - The user types `secret`; the hint still reads `Use 8 or more characters`. The user types `12`; the hint reads `Looks good`.
  - The key idea: a hint that follows every keystroke needs a render after every keystroke, so the password must be in state. The docs: "A controlled input makes sense if you needed state anyway--for example, to re-render your UI on every edit."
  - What is at stake: with the password kept only in the browser, the component has no `password` value to compute the hint from, and no render happens while the user types, so the hint cannot follow the typing.
  - Where readers go wrong: they read the same box from both state and `FormData`, or they think the whole form must now be controlled.
- **Root Distinction**:
  - Junior: "One controlled box means the whole form must be controlled."
  - Senior: the choice is made per box; the email stays in the browser, the password goes into state.
- **Simplest version**:
  - `const [password, setPassword] = useState('');`
  - `<input type="password" value={password} onChange={e => setPassword(e.target.value)} />`
  - `<p>{password.length < 8 ? 'Use 8 or more characters' : 'Looks good'}</p>`
  - In `handleSubmit`: `const email = formData.get('email');` and `password` from state; `console.log({ email, password })`.
- **Words to teach**:
  - None new. The new fact is when to choose a controlled box: the docs give re-rendering the UI on every edit, and more than one way to change the value, such as the docs' `Add 10 years` button.
  - Known words: ternary: Lesson 10. `useState`: Lesson 12. Controlled box: Lesson 20.
  - Helper words: `type="password"`, `.length`.
- **Side by side**:
  - "Password with `name`" and "Password with `value` and `onChange`": NOT the same thing. Both show dots for each typed letter, but only the second renders, so only the second updates the hint.
  - "read the password from `FormData`" and "read the password from state" at submit: `form.md` says "If you instead control an input with state, read from that state on submit rather than from `FormData`." The map gives this as the docs' rule; whether the two give the same string is not stated in the docs.
- **Surprises**: none. The hint follows the code: each keystroke sets `password`, React renders, and the ternary picks the hint text.
- **Where did that come from?**:
  - `password` and `setPassword`: our code gets them from `useState('')`.
  - `password.length`: JavaScript gives every string its number of characters.
  - `email` in `handleSubmit`: our code reads it from `formData.get('email')`, as in Principle 1.
- **Real beginner mistake**:
  1. The developer turns the uncontrolled password box into a controlled one and writes `useState()` with no starting value.
  2. The box first gets `value={undefined}`, so React treats it as uncontrolled.
  3. The user types the first letter, and `value` becomes a string.
  4. The Console shows the warning that begins "A component is changing an uncontrolled input to be controlled" (docs Troubleshooting heading). The full message is `unconfirmed`.
  5. The fix from the docs: start the state with `''` (Lesson 20).
- **Interview depth**:
  - Where controlled wins (syllabus card and docs): password strength hints, live character limits, autocomplete, a value that a button also changes, a Sign up button disabled until the form is valid (Lesson 21).
  - Where uncontrolled wins: boxes read only on submit, fewer renders, less code.
  - The docs: a box "can't be both controlled and uncontrolled at the same time."
  - The docs: in practice "controlled" and "uncontrolled" are not strict technical terms for a whole component, which usually mixes local state and props (Lesson 24).
- **React does**:
  - Page: the hint reads `Use 8 or more characters` for fewer than 8 characters, and `Looks good` from 8 characters on.
  - Console: `SignupForm rendered` after each keystroke in the Password box; none while typing in the Email box; on submit, the object with `email` and `password` (format `unconfirmed`).
  - Elements panel: the `<p>` text node of the hint changes after the eighth character (`unconfirmed`).
- **Example step**: `SignupForm.jsx` gets `password` state, the Password box, the hint line, and a `handleSubmit` that takes the email from `FormData` and the password from state.

### Principle 4: State in SignupForm Keeps SiteHeader Still

- **Rule**: the keystroke renders reach only the component that holds the state and its children, so keep the form's state inside the form component, not in `App`.
- **Move**: Side by side, because the same `password` state placed in `App` or in `SignupForm` gives the same form on the screen.
- **Opening Essence**:
  - The smallest code: the docs' shape, an `App` that renders the form and other page content, with the state in `App` or in the form component.
  - The confusion: *"It may look the same, or work the same at first, but it is NOT the same thing!"* The page, the hint, and the submit are the same in both versions.
  - Where they differ: with the state in `App`, `SiteHeader rendered` appears in the Console after every keystroke; with the state in `SignupForm`, it does not.
- **Root Distinction**:
  - Junior: "State at the top of the app is always fine."
  - Senior: every state change renders the component that holds it and everything inside it, so typing state belongs as low as the page allows.
- **Simplest version**:
  - Version with state in `App`: `App` holds `password` and renders `<SiteHeader />` and `<SignupForm password={password} onPasswordChange={setPassword} />`.

  - `console.log('SiteHeader rendered')` in `SiteHeader`.
- **Words to teach**:
  - None new. The docs' fact: "This significantly improves performance because now only `SignupForm` re-renders on every keystroke."
  - Known words: the component tree: Lesson 06. Props: Lesson 08. Render: Lesson 13. A function passed as a prop, such as `onPasswordChange`: Lesson 23. Lifting state up: Lesson 24.
  - Helper words: `console.log`.
- **Side by side**:
  - "with state in `App`" and "with state in `SignupForm`": NOT the same thing. The same page, but the first renders `SiteHeader` on every keystroke and the second does not.
- **Surprises**:

  2. `App` renders again, so React also calls `SiteHeader` and `SignupForm` again.
  3. The Console shows `SiteHeader rendered`, although nothing in the header changed.
  4. With the state in `SignupForm`, only `SignupForm rendered` appears.

- **Real beginner mistake**:
  1. The developer writes the form directly inside `App`, next to the rest of the page, as the docs' first example does.
  2. The form's state lives in `App`.
  3. Every keystroke renders the whole page.
  4. On a big page, typing becomes slow.
- **Interview depth**:

## Interview Points

- Controlled box: `value` and `onChange` keep the text in state; React renders the component on every keystroke.
- Uncontrolled box: the browser keeps the text; the code reads it once at submit with `new FormData(e.currentTarget)`.
- Every box read through `FormData` needs a `name`; the `name` is the key, and `formData.get()` returns `null` for a missing key.
- Choose controlled when the page must change on every edit: password hints, live limits, autocomplete, a button disabled until valid, a value a button also changes.
- Choose uncontrolled when the box is only inspected on submit: fewer renders, less code.
- Choose per box: one form may mix both; read the controlled box from state, the others from `FormData`.
- Keep typing state in the smallest component that needs it, so only that component renders on every keystroke; `useDeferredValue` helps when a large render cannot be avoided.
- A box never switches between controlled and uncontrolled; a controlled box starts with `''`.
- React 19 form actions (Lesson 41) receive the same `FormData`, which favors uncontrolled boxes.
