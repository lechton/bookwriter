## Scope

Covered here:
- The docs' main claim: "Effects have a different lifecycle from components. Components may mount, update, or unmount. An Effect can only do two things: to start synchronizing something, and later to stop synchronizing it."
- The setup starts synchronizing; the cleanup stops synchronizing. The docs: "Your Effect's body specifies how to **start synchronizing**" and "The cleanup function returned by your Effect specifies how to **stop synchronizing**".
- The exact order when a dependency changes, from the `useEffect` reference: "After every commit with changed dependencies, React will first run the cleanup function (if you provided it) with the old values, and then run your setup function with the new values."
- The final cleanup on unmount: "React will **stop synchronizing** your Effect one last time".
- The Effect's perspective: "always focus on a single start/stop cycle at a time. It shouldn't matter whether a component is mounting, updating, or unmounting."
- How React knows it must re-synchronize: it compares each dependency with the value "at the same spot that you passed during the previous render", with `Object.is`.
- Reactive values: "Props, state, and other values declared inside the component are _reactive_ because they're calculated during rendering and participate in the React data flow."
- What is not reactive: values declared outside the component, values declared inside the Effect, the stable `set` function and ref object, and mutable values such as `location.pathname` and `ref.current`, which "can't be a dependency".
- What `[]` means from the Effect's perspective: "your Effect's code does not use *any* reactive values".
- The linter checks that every reactive value the Effect reads is in the array. The docs: "You can't "choose" your dependencies." Suppressing the linter leaves a stale value.
- Each Effect is one synchronization process: "Each Effect in your code should represent a separate and independent synchronization process."

## Start of the Lecture

**Opening Essence of the chapter**:
- The real screen: a chat app with rooms, as in Slack or Discord. A menu picks the room. The page shows `Welcome to the general room!`. The app stays connected to the chat server of the room that is shown.
- What the user does: picks `travel` in the menu. The heading changes to `Welcome to the travel room!`.
- The question that screen raises for the developer: the component did not leave the page, so who disconnects from `general` and connects to `travel`?
- The answer, in the docs' words: "Your Effect's body specifies how to start synchronizing, and your cleanup function specifies how to stop synchronizing. All that React needs to do now is to call them in the correct order and with the correct props and state."
- The smallest code, the docs' own Effect, eight lines: `useEffect(() => { const connection = createConnection(serverUrl, roomId); connection.connect(); return () => { connection.disconnect(); }; }, [roomId]);`
- Key idea the reader must remember: an Effect does not mount, update, and unmount. It starts synchronizing and stops synchronizing, once for each value of its dependencies.
- Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"*
  1. The component's lifecycle: mount, update, unmount. Lesson 13.
  2. The Effect's lifecycle: start synchronizing, stop synchronizing, and again for each new `roomId`.
  3. On the first visit both look the same: the component mounts and the Effect connects. They split the first time the user picks another room: the component only updates, while the Effect stops and starts.
- What is at stake for the user, on the example page:
  1. The heading says `travel`.
  2. Without the cleanup, the app is still connected to `general`, and now also to `travel`. The bank row: "you now have two connections."
  3. With `roomId` left out of the array, the app stays connected to `general` only. The docs: "You will remain connected to the initial `roomId` and `serverUrl` even after the user picks different values in the UI."
  4. In both cases the page and the connection give two different answers to the question "which room am I in?". The docs: "what your Effect did back then (connecting to the `"general"` room) no longer matches the UI."
- Where readers usually go wrong:
  1. They read the cleanup as "the unmount code". The docs' Troubleshooting title: "My cleanup logic runs even though my component didn't unmount".
  2. They expect the cleanup to see the new `roomId`; it sees the old one.
  3. They leave a dependency out "to prevent re-running the effect", as the syllabus card's naive version does, and the chat stays on the first room.
  4. They add unrelated work, such as logging a visit, to an Effect only because it runs at the same time.

**Theme**: a chat page where the user switches rooms, and the connection must always be to the room the heading shows.

**Ways** (what the docs give for a value that the Effect reads, and when each fits):
1. List it in the dependency array: when the value can change on a re-render and the Effect must follow it, such as `roomId`.
2. Move it outside the component: when it never changes, such as a fixed `serverUrl`. Then it is not reactive and leaves the array.
3. Move it inside the Effect: when only the Effect needs it and it does not depend on rendering. It is not reactive.
4. Read it in an Effect Event: when the Effect needs the latest value without re-synchronizing. Lesson 36. Named only.

**Example page chosen for this lesson**: a chat room picker.
- Parts of the page:

  3. Under them, while the chat is shown, the heading `Welcome to the general room!`.

  4. `index.html` and `src/main.jsx` with `<StrictMode>`.

## Principles

### Principle 1: The Effect Connects to One Room Until It Disconnects

- **Rule**: An Effect's lifecycle is not the component's lifecycle; each run of the setup starts synchronizing with the values of that render, and its own cleanup stops it, so the reader thinks about one start and stop at a time, not about mount, update, and unmount.
- **Move**: Side by side, because the docs give the same four user actions twice, once as the component sees them and once as the Effect sees them, and the two lists do not line up.
- **Opening Essence**:
  - Smallest code: the docs' Effect with `[roomId]`, its body marked "start synchronizing" and its `return () => { connection.disconnect(); }` marked "stop synchronizing".
  - The docs' first list, the component's perspective:
    1. `ChatRoom` mounted with `roomId` set to `"general"`.
    2. `ChatRoom` updated with `roomId` set to `"travel"`.
    3. `ChatRoom` updated with `roomId` set to `"music"`.
    4. `ChatRoom` unmounted.
  - The docs' second list, the Effect's perspective:
    1. Your Effect connected to the `"general"` room (until it disconnected).
    2. Your Effect connected to the `"travel"` room (until it disconnected).
    3. Your Effect connected to the `"music"` room (until it disconnected).
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Four moments for the component, three connections for the Effect. The docs: "**It's a good way to think about components, but _not_ about Effects.**"
  - The docs' reason to think from the Effect: thinking of Effects "as "callbacks" or "lifecycle events" that fire at a specific time like "after a render" or "before unmount"" "gets complicated very fast".
- **Root Distinction**:
  - Junior: "My Effect has a mount part and an unmount part, like the component."
  - Senior: the Effect has one start and one stop; React repeats that pair as often as the dependencies change, and the code is the same for every pair.
- **Simplest version**:
  - `useEffect(() => { const connection = createConnection(serverUrl, roomId); connection.connect(); return () => { connection.disconnect(); }; }, [roomId]);`
- **Words to teach**:
  - *lifecycle*: the docs' word for what happens to a component over time: mount, update, unmount. "Every React component goes through the same lifecycle". Provided by React's docs. Needed at the first list.
  - *update*: a component "updates when it receives new props or state, usually in response to an interaction". Needed when the user picks `travel`.
  - *start synchronizing, stop synchronizing*: the docs' names for what the setup and the cleanup do. Needed at the smallest code.
  - *the Effect's perspective*: the docs' name for the second list. Needed at the second list.
  - Known: mount, Lesson 13. Setup function, cleanup function, unmount, Lesson 32. Connection, connect, disconnect, Lesson 32.
  - Helper: `createConnection`, `connect()`, `disconnect()`, from `chat.js`; the docs' stand-in for a real server.
- **Side by side**:
  - "from the component's perspective" and "from the Effect's perspective": NOT the same thing. The first counts four moments of the component; the second counts three connections, each with its own end.
  - "an Effect with a cleanup" and "an Effect without a cleanup": the docs' Note, "React will behave as if you returned an empty cleanup function." Yes, the exact same thing for React; for the chat, nothing disconnects.
- **Surprises**:
  - The component mounted once, and the Effect connected three times:
    1. The user clicks `Open chat`; `ChatRoom` mounts; the Effect connects to `general`.
    2. The user picks `travel`; `ChatRoom` updates, it does not mount again; the Effect disconnects and connects to `travel`.
    3. The user picks `music`; the same, to `music`.
    4. Three `✅ Connecting` lines in production, for one mount. In development, one more pair at the start, Principle 2.
- **Where did that come from?**:
  - `createConnection`, `connect`, `disconnect`: our `chat.js` exports `createConnection`; it returns an object with the two methods. The docs: "A real implementation would actually connect to the server".
  - `serverUrl`: a `const` above the component in `ChatRoom.jsx`, `'https://localhost:1234'`.
- **Real beginner mistake** (the docs' warning on thinking from the component):
  1. A developer thinks of the Effect as "the code that runs on mount".
  2. The developer writes the connect code and `[]`, and the disconnect code "for unmount".
  3. The chat works on the first visit.
  4. The user picks `travel`; nothing reconnects. Principle 3.
- **Interview depth**:
  - The docs: "If you do it well, your Effect will be resilient to being started and stopped as many times as it's needed."
  - The docs compare this with JSX: "you don't think whether a component is mounting or updating when you write the rendering logic that creates JSX."
  - The docs' Deep Dive: "The Effect is *also* a part of the rendering output." Each render gives its own Effect and its own dependencies, such as `['general']`.
  - The `useEffect` reference: "When your cleanup logic correctly "mirrors" the setup logic, your Effect is resilient to running setup and cleanup as often as needed."
- **React does**:
  - Page: `Welcome to the general room!`, then `travel`, then `music`; after `Close chat`, no heading.
  - Console, production, the whole story: `✅ Connecting to "general" room at https://localhost:1234...`, then `❌ Disconnected from "general" room at https://localhost:1234` and `✅ Connecting to "travel" room at https://localhost:1234...`, then the same pair for `travel` to `music`, then `❌ Disconnected from "music" room at https://localhost:1234`. Order from the docs; exact lines `unconfirmed` until the lab runs them.
  - Elements panel: only the text inside `<h1>` changes when the room changes. `unconfirmed`.

### Principle 2: Picking travel Runs the Cleanup for general First

- **Rule**: When a dependency changes, React first calls the cleanup from the last Effect that ran, with that render's old values, then runs the new setup with the new values; after unmount, React calls the last cleanup one final time.
- **Move**: Steps for a surprise, because the Console prints `general` after the heading already says `travel`.
- **Opening Essence**:
  - Smallest code: the same Effect, and the user picks `travel`.
  - The `useEffect` reference, the order:
    1. "Your setup code runs when your component is added to the page *(mounts)*."
    2. "After every commit of your component where the dependencies have changed: First, your cleanup code runs with the old props and state. Then, your setup code runs with the new props and state."
    3. "Your cleanup code runs one final time after your component is removed from the page *(unmounts).*"

- **Rule**: The dependency array must list every reactive value the Effect reads; React re-synchronizes only when a listed value changes, so a value left out leaves the Effect with the value of the first render.
- **Move**: Side by side, because `[roomId]` and `[]` look almost the same and give the same first visit.
- **Opening Essence**:

### Principle 4: A serverUrl in State Joins the Array

- **Rule**: Props, state, and every value declared or calculated in the component body are reactive and belong in the array; a value declared outside the component or inside the Effect is not reactive and does not.
- **Move**: Side by side, because the same `serverUrl` is a dependency in one place and not in the other.
- **Opening Essence**:
  - Smallest code, two places for `serverUrl`:
    1. Above the component: `const serverUrl = 'https://localhost:1234';` with `[roomId]`.
    2. In state: `const [serverUrl, setServerUrl] = useState('https://localhost:1234');` with `[roomId, serverUrl]`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Same name, same text. The first "never changes due to a re-render"; the second "may change over time".
  - The docs' rule: "**Props, state, and other values declared inside the component are _reactive_ because they're calculated during rendering and participate in the React data flow.**"
  - The docs: "dependencies only do something when they change over time!"
- **Root Distinction**:
  - Junior: "The array lists props and state."
  - Senior: the array lists every value from the component body that the Effect reads, including values calculated from props and state; values outside rendering are not dependencies.
- **Simplest version**:
  - The docs' sandbox: `ChatRoom` with `serverUrl` in state, `<input value={serverUrl} onChange={e => setServerUrl(e.target.value)} />` under `Server URL:`, and `}, [roomId, serverUrl]);`.
- **Words to teach**:
  - *reactive value*: a value that can change on a re-render: props, state, and variables in the component body. Provided by the docs as a name. Needed when `serverUrl` moves into state.
  - *data flow*: the docs' words for values "calculated during rendering". Needed in the same rule.
  - *stable*: the docs' word for values React guarantees "to not change on a re-render": the `set` function from `useState` and the ref object from `useRef`. "Stable values aren't reactive, so you may omit them from the list. Including them is allowed". Needed when the reader asks why `setRoomId` is never in the array.
  - *mutable value*: a value that "can change at any time completely outside of the React rendering data flow", such as `location.pathname` and `ref.current`. Needed in Interview depth.
  - Known: `useState`, Lesson 12. `value`, `onChange`, `e.target.value`, Lesson 20. `useRef`, `ref.current`, Lesson 30.
  - Helper: none.
- **Side by side**:
  - "with `serverUrl` above the component" and "with `serverUrl` in state": NOT the same thing. The first cannot change; the second changes with every letter in the box, and must be in the array.
  - "with `serverUrl` and `roomId` above the component, and `[]`" and "with `serverUrl` and `roomId` inside the Effect, and `[]`": Yes, it is the exact same thing for the array. The docs: "They aren't calculated during rendering, so they're not reactive".
  - "`[]` from the component's perspective" and "`[]` from the Effect's perspective": the same behavior today, connect on mount and disconnect on unmount. The docs: "your Effect's code does not use *any* reactive values"; when the user can later change them, "your Effect's code won't change. You will only need to add them to the dependencies."
- **Surprises**:
  - Each letter typed in the `Server URL:` box disconnects and connects again:
    1. The user types one letter at the end of `https://localhost:1234`.

    3. React compares `[roomId, serverUrl]` with the last array; `serverUrl` differs.
    4. React calls the cleanup: `❌ Disconnected from "general" room at https://localhost:1234`.
    5. React runs the setup with the new URL: a `✅ Connecting` line with the new text. `unconfirmed`, a lab check.
    6. The docs: "Whenever you change a reactive value like `roomId` or `serverUrl`, the Effect re-connects to the chat server."

  - The docs' `serverUrl` calculated in the body: `const serverUrl = selectedServerUrl ?? settings.defaultServerUrl;`, from a prop and a context value. "It's a regular variable that you calculate during rendering", so it is reactive. Lesson 28 for `useContext`.

  2. The pathname changes, and nothing re-renders the component.
  3. React does not compare the array, so the Effect does not re-synchronize.

### Principle 5: Logging the Visit Gets Its Own Effect

- **Rule**: Each Effect is one synchronization process; work that only happens at the same time as the connection, such as logging a visit, goes in its own Effect with its own dependencies.
- **Move**: Side by side, because one Effect with both jobs and two Effects with one job each run the same on the first visit.
- **Opening Essence**:
  - Smallest code, two shapes:
    1. One Effect: `logVisit(roomId);` on the first line of the connection Effect.
    2. Two Effects: `useEffect(() => { logVisit(roomId); }, [roomId]);` and the connection Effect below it.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both log one visit when the room changes. Once the connection Effect also depends on `serverUrl`, the first shape logs a visit for every letter typed in the `Server URL:` box.
  - The docs: "Logging the visit **is a separate process** from connecting."
- **Root Distinction**:
  - Junior: "These two lines run at the same moment, so they go in the same Effect."
  - Senior: ask whether they synchronize the same thing; the docs' test is whether "deleting one Effect wouldn't break the other Effect's logic."
- **Simplest version**:
  - The docs' split: `useEffect(() => { logVisit(roomId); }, [roomId]);` and `useEffect(() => { const connection = createConnection(serverUrl, roomId); ... }, [roomId, serverUrl]);`
- **Words to teach**:
  - *synchronization process*: the docs' name for what one Effect does. "**Each Effect in your code should represent a separate and independent synchronization process.**" Needed when the second Effect appears.
  - *`logVisit`*: the docs' name for sending an analytics event when the user visits the room. Provided by our code; the docs do not define it.
  - Known: analytics, Lesson 34. Reactive value, Principle 4.
  - Helper: `src/analytics.js`, our own file with `logVisit`.
- **Side by side**:

## Interview Points

- A component mounts, updates, and unmounts; an Effect only starts synchronizing and stops synchronizing, and it can do that many times while the component stays on the page.
- The setup starts synchronizing with the values of its render; the cleanup it returns stops that same synchronization.
- When a dependency changes after a commit, React first runs the old cleanup with the old values, then the new setup with the new values; after unmount, it runs the last cleanup once more.
- The cleanup sees the values of its own render, so it disconnects the old room, not the new one.
- In development, Strict Mode adds one setup and cleanup before the first real setup, so the Console shows connect, disconnect, connect.
- React compares each dependency with the previous render's value using `Object.is`, and skips the Effect when all are the same.
- Reactive values are props, state, and every value declared or calculated in the component body; they all belong in the array. Values outside the component or inside the Effect are not reactive; the `set` function and the ref object are stable; mutable values such as `location.pathname` and `ref.current` cannot be dependencies.
- `[]` means the Effect reads no reactive values, not "run once".
- You cannot choose the dependencies; the linter checks them, and suppressing it leaves a stale value, such as a chat stuck on the first room.
- Without a cleanup, each change of the dependency opens one more connection.
- Each Effect is one synchronization process; unrelated work, such as logging a visit, gets its own Effect.
- Too many re-runs are fixed by changing the code, Lessons 36 and 37, never by shortening the array.
