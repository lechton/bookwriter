# Q29 Principle Map (River Version v1): Combining a Reducer with Context for App-Wide State

- **Version**: River Version (`v1`), written under `skills/v10.6`

- **Interview Question**: *How do you combine a reducer with context for app-wide state?*

## Scope

Covered here:
- The problem the docs name: the state and the `dispatch` function from `useReducer` are only available in the component that calls it, so every other component gets them as props, through every component in the middle.
- The docs' three steps: create the context; put state and dispatch into context; use context anywhere in the tree.
- Two separate contexts, one for the state and one for `dispatch`, both created with `createContext(null)`.
- Providing both from the component that calls `useReducer`, one provider inside the other.
- Reading state with `useContext(CartContext)` in a component that shows the cart, and reading `dispatch` with `useContext(CartDispatchContext)` in a component that only changes it; the components in the middle lose their props.
- The state still lives in the component that calls `useReducer`; context only delivers it.
- Moving all the "wiring" into one file: a provider component, `CartProvider`, that calls `useReducer`, provides both contexts, and takes `children`.
- Two small functions in the same file, `useCart` and `useCartDispatch`, that read the two contexts; the docs call such functions custom Hooks.
- Why two contexts and not one object: the docs' facts on `dispatch` having a stable identity, on `Object.is` comparison of context values, on an object value being a different object on every render, and on children passed as JSX. The measured re-render counts go to the lab.
- The Troubleshooting entries this page can show: a provider with a wrong prop name, a component rendered outside the provider, a context read in the wrong place.
- The docs' Recap point that an app can have many context-reducer pairs.

## Start of the Lecture

**Opening Essence of the chapter**:
- The question of the lesson: the cart's state and `dispatch` live in one component at the top; how do the components far below read the cart and change it, without every component in between passing them on?
- Smallest code, with no project files:
  1. Lesson 27 gives `const [cart, dispatch] = useReducer(cartReducer, initialCart);`
  2. Lesson 28 gives `<ThemeContext value={theme}>` and `const theme = useContext(ThemeContext);`
  3. Put together: `<CartContext value={cart}>` and `<CartDispatchContext value={dispatch}>` around the tree in the component that calls `useReducer`; `const cart = useContext(CartContext);` in a component that shows the cart; `const dispatch = useContext(CartDispatchContext);` in a component that changes it.
- Confusion to say out loud: *"Yes, it is the exact same thing!"* Reducer plus context is not a new tool. It is the reducer of Lesson 27 and the context of Lesson 28 on the same page. `dispatch` is a value like `theme`: React delivers it from the closest provider above, the same way.
- The docs' own frame, from the Intro: "Reducers let you consolidate a component's state update logic. Context lets you pass information deep down to other components. You can combine reducers and context together to manage state of a complex screen."
- The docs' frame of the problem: "**Currently, the `tasks` state and the `dispatch` function are only available in the top-level `TaskApp` component.** To let other components read the list of tasks or change it, you have to explicitly pass down the current state and the event handlers that change it as props."
- What the two parts share and the one difference: both the state and `dispatch` come from the same `useReducer` call. The state changes after every action; `dispatch` stays the same function for the life of the component. That one difference is why the docs give each its own context.
- Key idea: the state still lives in the component that calls `useReducer`. The docs: "**The state still 'lives' in the top-level `TaskApp` component, managed with `useReducer`.** But its `tasks` and `dispatch` are now available to every component below in the tree by importing and using these contexts."
- What is at stake for the user: the user clicks `Delete` on the Bread row, deep in the page, and two distant places must change at once, the row leaves the list and the header line goes from `Cart: 3 items` to `Cart: 2 items`. With props, every component on the way must carry `cart` and four handlers; a component in the middle that drops `onDelete` leaves the `Delete` button broken.
- Where readers usually go wrong:
  1. They think the state moved into the context. It did not: the context holds no information itself (Lesson 28); it carries what the component with `useReducer` gives it.
  2. They think "app-wide" means one global variable for the whole app. Each reader gets the value of the closest provider above it; components outside the provider get the default `null`.
  3. They put `cart` and `dispatch` in one object in one context, and every reader receives a different object on every render.
  4. They remove every prop, including the ones a component really needs, such as `item` on each row.

**Theme**: a shop page where the cart state and its four update functions travel as props from `App` through `CartPage` and `CartList` down to each `CartRow`, while the header far away also shows the cart.

**Ways** (developers really choose between these for the same job, from the docs):
1. Pass the state and the handlers as props, as Lessons 23 and 24 did: fits when few components sit in the middle. The docs: "In a small example like this, this works well, but if you have tens or hundreds of components in the middle, passing down all state and functions can be quite frustrating!"
2. Pass JSX as `children` so fewer components sit in the middle: Lesson 28's alternative, named only.
3. A reducer together with context: fits when many distant components read or change the same state. The docs' use case "Managing state": "Many distant components below may want to change it. It is common to use a reducer together with context to manage complex state and pass it down to distant components without too much hassle."
4. `useState` with context, an object value with the state and its setter: the `useContext` recipe "Updating an object via context", Lesson 28 named it. Named only.

**Example page chosen for this lesson**: a small shop page with a cart, built on Lesson 27's cart.
- Parts of the page:
  1. At the top, a header: the title `Corner Shop` and a line `Cart: 3 items`.
  2. Below, the cart: the heading `Your cart`, one row per item, such as `Bread: 2`, each with three buttons, `+`, `-`, `Delete`; when the cart has no items, the line `Your cart is empty.`
  3. Under the rows, a button `Empty cart`.
- What the user does, and what each click changes:
  1. Clicks `+` on Bread: the row shows `Bread: 3`; the header still shows `Cart: 3 items`.
  2. Clicks `Delete` on Apple: the Apple row leaves, and the header shows `Cart: 2 items`.
  3. Clicks `Empty cart`: every row leaves, `Your cart is empty.` appears, and the header shows `Cart: 0 items`.
- State: one array, `cart`, from `useReducer(cartReducer, initialCart)`, with Lesson 27's `initialCart`: `[{ id: 0, name: 'Apple', quantity: 1 }, { id: 1, name: 'Bread', quantity: 2 }, { id: 2, name: 'Milk', quantity: 1 }]`.
- `cartReducer`: Lesson 27's file `src/cartReducer.js`, unchanged, with `export default function cartReducer(cart, action)` and the four types `'increased'`, `'decreased'`, `'deleted'`, `'emptied'`.
- The tree: `App` renders `Header` and `CartPage`; `CartPage` renders `CartList` and `EmptyCartButton`; `CartList` renders one `CartRow` for each item.
- At the start of the lesson, the version with props:
  1. `App` calls `useReducer` and holds four handlers, `handleIncrease(id)`, `handleDecrease(id)`, `handleDelete(id)`, `handleEmpty()`, each one line that calls `dispatch`, as in Lesson 27.
  2. `App` renders `<Header cart={cart} />` and `<CartPage cart={cart} onIncrease={handleIncrease} onDecrease={handleDecrease} onDelete={handleDelete} onEmpty={handleEmpty} />`.
  3. `CartPage` receives five props and uses none of them; it passes four to `CartList` and one to `EmptyCartButton`.
  4. `CartList` uses `cart` and passes three handlers to each `CartRow`.
  5. `CartRow` uses `item` and calls the three handlers: `onClick={() => onIncrease(item.id)}`.
  6. `EmptyCartButton` calls `onEmpty`.
- At the end of the lesson: `src/CartContext.jsx` holds the two contexts, `CartProvider`, `useCart`, and `useCartDispatch`; `App` renders `<CartProvider><Header /><CartPage /></CartProvider>`; `Header` and `CartList` call `useCart()`; `CartRow` and `EmptyCartButton` call `useCartDispatch()` and dispatch in their own `onClick`; `CartPage` takes no props; the four handlers in `App` are gone.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx`, `src/cartReducer.js`, `src/CartContext.jsx`, `src/components/Header.jsx`, `src/components/CartPage.jsx`, `src/components/CartList.jsx`, `src/components/CartRow.jsx`, `src/components/EmptyCartButton.jsx`.
- Names follow the docs' own code: `TasksContext` and `TasksDispatchContext` become `CartContext` and `CartDispatchContext`; `TasksProvider` becomes `CartProvider`; `useTasks` and `useTasksDispatch` become `useCart` and `useCartDispatch`; the docs' file `TasksContext.js` becomes `CartContext.jsx`, see Open Issues for the extension.

## Principles

### Principle 1: createContext Makes CartContext and CartDispatchContext

- **Rule**: To pass a reducer's state and `dispatch` down the tree, create two separate contexts, one for the state and one for `dispatch`, each with `createContext(null)`, in a file of their own.
- **Move**: Smallest code first, because creating the two contexts is three lines and nothing changes on the page yet.
- **Opening Essence**:
  - Smallest code: `import { createContext } from 'react';`, `export const CartContext = createContext(null);`, `export const CartDispatchContext = createContext(null);`
  - The docs, Step 1: "`TasksContext` provides the current list of tasks. `TasksDispatchContext` provides the function that lets components dispatch actions."
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* Each line is Lesson 28's `createContext`. Nothing in `createContext` knows about reducers; the two contexts are two ordinary contexts.
  - The docs on the default: "Here, you're passing `null` as the default value to both contexts. The actual values will be provided by the `TaskApp` component."
  - Where readers go wrong: they ask why there are two contexts when one `useReducer` call made both values. The answer comes in Principle 4, after the page works.
- **Root Distinction**:
  - Junior: "`cart` and `dispatch` come from one `useReducer` call, so they belong in one context."
  - Senior: the state changes after every action and `dispatch` never changes, so each gets its own context, and a component reads only the one it needs.
- **Simplest version**:
  - `src/CartContext.jsx`: `import { createContext } from 'react';`, `export const CartContext = createContext(null);`, `export const CartDispatchContext = createContext(null);`
- **Words to teach**:
  - *two separate contexts*: the docs' Recap, "Create two contexts (for state and for dispatch functions)". `CartContext` carries the current cart and `CartDispatchContext` carries `dispatch`. Provided by our code, created with React's `createContext`. Needed at the two `export const` lines.
  - Known: `createContext`, context object, default value, Lesson 28. Named `export`, Lesson 05. `dispatch`, Lesson 27. `null`, Lesson 28's `createContext(null)`.
  - Helper: none.
- **Side by side**:
  - "with two contexts, `CartContext` and `CartDispatchContext`" and "with one context and `value={{ cart, dispatch }}`": the same page on the first load, and NOT the same thing. With one object, every reader of the context receives a different object on every render of the providing component. The `useContext` reference: "this will be a *different* object pointing at a *different* function, so React will also have to re-render all components deep in the tree that call `useContext(AuthContext)`." The full reason: Principle 4.
  - "with `createContext(null)`" and "with `createContext([])`": NOT the same result for a component outside the provider. With `null`, reading `cart.length` throws, see Principle 4; with `[]`, the component is expected to show `Cart: 0 items` and hide the mistake: `unconfirmed`. The docs' choice for this pattern is `null`.
- **Surprises**: none. Nothing reads the contexts yet.
- **Where did that come from?**:
  - `createContext`: imported from `'react'`.
  - `CartContext` and `CartDispatchContext` in other files: named exports, imported with curly braces, Lesson 05.
- **Real beginner mistake** (the `useContext` reference, "Optimizing re-renders when passing objects and functions"):
  1. A developer creates one context and provides `value={{ cart, dispatch }}`.
  2. Every render of the providing component creates a new object.
  3. React compares the old and new value with `Object.is` and finds two different objects.
  4. Every component that reads the context renders again, including `EmptyCartButton`, which uses only `dispatch`.
- **Interview depth**:
  - The docs' Recap: "Create two contexts (for state and for dispatch functions)."
  - The `useContext` reference fix for an object value: wrap it in `useMemo` and the function in `useCallback`, "This is a performance optimization". Lesson 59.
  - `dispatch` from `useReducer` needs no `useCallback`: the `useReducer` reference: "The `dispatch` function has a stable identity".
- **React does**:
  - Page: nothing new.
  - Console: nothing.
  - Elements panel: nothing.
- **Example step**:
  - Creates `src/CartContext.jsx` with the three lines.
  - `App` still calls `useReducer` and passes `cart` and the four handlers as props.
- **Code names**: `src/CartContext.jsx`, `createContext`, `CartContext`, `CartDispatchContext`, `null`, `[]`, `import { createContext } from 'react'`, `export const CartContext = createContext(null)`, `export const CartDispatchContext = createContext(null)`, `value={{ cart, dispatch }}`, `TasksContext`, `TasksDispatchContext`

### Principle 2: App Puts cart and dispatch into Two Providers

- **Rule**: The component that calls `useReducer` provides the state in one provider and `dispatch` in the other, one inside the other, around everything it renders.
- **Move**: Side by side, because the two providers can sit in either order, and the two orders look different and are the exact same thing.
- **Opening Essence**:
  - Smallest code: `<CartContext value={cart}><CartDispatchContext value={dispatch}>...</CartDispatchContext></CartContext>` in `App`, with `const [cart, dispatch] = useReducer(cartReducer, initialCart);` above it.
  - The docs, Step 2: "Take the `tasks` and `dispatch` returned by `useReducer()` and provide them to the entire tree below".
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* `CartContext` outside and `CartDispatchContext` inside, or the other way round, give every reader the same values, because each reader asks for one context and finds the closest provider of that context (Lesson 28); a provider of another context does not count.
  - The docs' in-between step: "For now, you pass the information both via props and in context". The page still works through props, so nothing changes for the user.
- **Root Distinction**:
  - Junior: "Providing `dispatch` in context makes the buttons dispatch."

### Principle 3: CartRow Reads dispatch, and CartPage Loses Its Props

- **Rule**: Any component below the providers reads the state with `useContext(CartContext)` or `dispatch` with `useContext(CartDispatchContext)` and dispatches its own action; the components in the middle stop receiving and passing props they never used.
- **Move**: Side by side, because `CartPage` with five props and `CartPage` with none show the same page, and the difference is the whole point of the lesson.
- **Opening Essence**:
  - Smallest code, two ways for `CartRow` to remove its item:
    1. `function CartRow({ item, onDelete }) { return <button onClick={() => onDelete(item.id)}>Delete</button>; }`
    2. `function CartRow({ item }) { const dispatch = useContext(CartDispatchContext); return <button onClick={() => dispatch({ type: 'deleted', id: item.id })}>Delete</button>; }`
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* for the user: the same click removes the same row. The first gets a handler from its parent, which got it from its parent; the second gets `dispatch` from the closest provider above.
  - The docs: "**The `TaskApp` component does not pass any event handlers down, and the `TaskList` does not pass any event handlers to the `Task` component either.** Each component reads the context that it needs".
  - Key idea, the docs: "**This way, any component below `TaskApp` in the tree can read the tasks and dispatch actions without the repetitive 'prop drilling'.**"
- **Root Distinction**:
  - Junior: "Context replaces props, so every prop goes."
  - Senior: context replaces only the props that components in the middle carried for others; `CartList` still passes `item` to each `CartRow`, as the docs' `TaskList` passes `task`.
- **Simplest version**:
  - `Header`: `const cart = useContext(CartContext);` and `<p>Cart: {cart.length} items</p>`.
  - `CartList`: `const cart = useContext(CartContext);` and `<CartRow key={item.id} item={item} />`.
  - `CartRow`: `const dispatch = useContext(CartDispatchContext);` and three `onClick` arrows that dispatch `'increased'`, `'decreased'`, and `'deleted'` with `id: item.id`.

- **Words to teach**:
  - No new React word. `useContext`, Lesson 28. Dispatching an action, Lesson 27.
  - The docs' word for where the state is: the state still "lives" in `App`.
  - Helper: none.
- **Side by side**:
  - "`CartPage` with `cart`, `onIncrease`, `onDecrease`, `onDelete`, `onEmpty`" and "`CartPage` with no props": the exact same page. Only the second leaves `CartPage` free of values it never uses.
  - "`onClick={() => onDelete(item.id)}`" and "`onClick={() => dispatch({ type: 'deleted', id: item.id })}`": the exact same action reaches `cartReducer`. In the first, `App` builds the action in `handleDelete`; in the second, `CartRow` builds it where the click happens, as the docs' `Task` does.
  - "`useContext(CartContext)`" and "`use(CartContext)`": the exact same value, Lesson 28.
- **Surprises**:

    3. The `dispatch` is the one `App` got from `useReducer`, so React renders `App` again and calls `cartReducer` with the current cart and the action.

  - `cart` inside `Header`: the same, from `CartContext`.
  - `item` inside `CartRow`: still a prop, from `CartList`'s `map`.
- **Real beginner mistake**:
  1. A developer adds `const dispatch = useContext(CartDispatchContext);` to `EmptyCartButton.jsx`.
  2. The developer forgets `import { CartDispatchContext } from '../CartContext.jsx';` in that file.
  3. The page goes blank on load: `ReferenceError: CartDispatchContext is not defined`, the same kind of error as Lesson 06. Exact text `unconfirmed`.
  4. The fix: import the context in every file that reads it.
- **Interview depth**:
  - The docs: "The state still 'lives' in the top-level `TaskApp` component, managed with `useReducer`." Reducer plus context is lifting state up, with context in place of the props.
  - The docs' last line: "This is a powerful way to scale your app and lift state up without too much work whenever you want to access the data deep in the tree."
  - The `useContext` caveat: "React **automatically re-renders** all the children that use a particular context starting from the provider that receives a different `value`." And: "Skipping re-renders with `memo` does not prevent the children receiving fresh context values."
- **React does**:

### Principle 4: CartProvider Wraps children and Holds the Reducer

- **Rule**: A provider component, `CartProvider`, calls `useReducer`, provides both contexts, and renders the `children` it receives; `App` only places `<CartProvider>` around the parts of the page that need the cart.
- **Move**: Side by side, because `App` with `useReducer` and two providers and `App` with `<CartProvider>` give the exact same page.
- **Opening Essence**:
  - Smallest code: `export function CartProvider({ children }) { const [cart, dispatch] = useReducer(cartReducer, initialCart); return (<CartContext value={cart}><CartDispatchContext value={dispatch}>{children}</CartDispatchContext></CartContext>); }` and in `App`: `<CartProvider><Header /><CartPage /></CartProvider>`.
  - The docs' three jobs of the provider: "1. It will manage the state with a reducer. 2. It will provide both contexts to components below. 3. It will take `children` as a prop so you can pass JSX to it."
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* `CartProvider` is a component like any other; `children` is Lesson 09's `children`, here `<Header />` and `<CartPage />`. The docs: "**This removes all the complexity and wiring from your `TaskApp` component**".
  - "You don't have to do this", the docs say; it declutters the components.
- **Root Distinction**:
  - Junior: "`CartProvider` is a special React provider."
  - Senior: it is our own component that calls `useReducer` and renders two of React's providers around its `children`.
- **Simplest version**:
  - `src/CartContext.jsx`: `import { createContext, useReducer } from 'react';`, `import cartReducer from './cartReducer.js';`, `initialCart`, the two contexts, and `export function CartProvider({ children })`.
  - `src/App.jsx`: `import { CartProvider } from './CartContext.jsx';` and `return (<CartProvider><Header /><CartPage /></CartProvider>);` with no `useReducer`.
- **Words to teach**:
  - *provider component*: the docs' "a component like `TasksProvider` that provides context". Provided by our code. Needed at `export function CartProvider`.
  - *"wiring"*: the docs' word, in quotes, for the code that creates the state and connects it to the contexts. Needed when `App` loses that code.
  - Known: `children`, Lesson 09. `useReducer`, Lesson 27.
  - Helper: none.
- **Side by side**:
  - "with `useReducer` and two providers in `App`" and "with `<CartProvider>` in `App`": the exact same page.
  - "`<CartProvider><Header /><CartPage /></CartProvider>`" and "`<Header />` above `<CartProvider><CartPage /></CartProvider>`": NOT the same thing. `Header` outside the provider gets the default `null`. See the beginner mistake.
- **Surprises**:
  - Placing a `console.log` in `EmptyCartButton` and clicking `+` on Bread:
    1. With the providers inside `App`, as in Principle 3, the state lives in `App`.
    2. The click renders `App` again.
    3. React renders the components `App` returns, and theirs: `Header`, `CartPage`, `CartList`, every `CartRow`, and `EmptyCartButton`. The docs: "This process is recursive: if the updated component returns some other component, React will render _that_ component next".
    4. Expected: `EmptyCartButton` logs on every click, `unconfirmed`.
    5. With `CartProvider`, the state lives in `CartProvider`, and the click renders `CartProvider` again.
    6. `<Header />` and `<CartPage />` were created by `App`, and `App` does not render again. The `memo` page: "When a component visually wraps other components, let it accept JSX as children. This way, when the wrapper component updates its own state, React knows that its children don't need to re-render."
    7. `CartContext` gets a new array, so React renders again its readers, `Header` and `CartList`, and the rows `CartList` returns.
    8. `CartDispatchContext` gets the same `dispatch` by `Object.is`. The `useReducer` reference: "The `dispatch` function has a stable identity".
    9. Expected: nothing renders `EmptyCartButton` or `CartPage` again, so `EmptyCartButton` logs only on the first render, `unconfirmed`.
  - The syllabus card's point holds only with both conditions, two contexts and `children`. The counts, with `<StrictMode>` rendering twice in development: a lab check.
- **Where did that come from?**:
  - `children` in `CartProvider`: React collects `<Header />` and `<CartPage />`, written between `<CartProvider>` and `</CartProvider>` in `App`, into `props.children`, Lesson 09.
  - `cart` and `dispatch` in `CartProvider`: its own `useReducer` call, moved from `App`.
  - `cartReducer` in `CartContext.jsx`: imported from Lesson 27's `./cartReducer.js`.
- **Real beginner mistake** (the `useContext` Troubleshooting, "My component doesn't see the value from my provider", point 2):
  1. A developer wants the header outside the cart part of the page and writes `<Header />` above `<CartProvider>` in `App`.
  2. No `CartContext` provider is above `Header`, so `useContext(CartContext)` returns the default `null`.
  3. `Header` reads `cart.length` on `null`.
  4. The page goes blank: `TypeError: Cannot read properties of null (reading 'length')`. Exact text `unconfirmed`.
  5. The docs: "You may have forgotten to wrap your component with `<SomeContext>`, or you might have put it in a different part of the tree than you thought. Check whether the hierarchy is right using React DevTools."
- **Interview depth**:
  - The docs: "You can think of `TasksProvider` as a part of the screen that knows how to deal with tasks".
  - Why two contexts, as the four facts above: a new state value re-renders its readers; `dispatch` never changes; an object `value={{ cart, dispatch }}` is new on every render; children created by a parent that did not render again are skipped. Without `children`, a re-render of the provider's own component renders everything below it anyway. Measuring this is Lesson 59.
  - The docs' Recap: "You can have many context-reducer pairs like this in your app."
- **React does**:
  - Page: the same as Principle 3. `unconfirmed`.
  - Console: with `Header` outside the provider, the `TypeError` above. `unconfirmed`.
  - Elements panel: `CartProvider` adds no DOM node. `unconfirmed`.
- **Example step**:
  - `CartContext.jsx`: adds `useReducer` to the import, imports `cartReducer`, takes `initialCart` from `App`, adds `export function CartProvider({ children })`.
  - `App.jsx`: loses `useReducer`, `initialCart`, and the two providers; renders `<CartProvider><Header /><CartPage /></CartProvider>`.

### Principle 5: useCart and useCartDispatch Read the Two Contexts

- **Rule**: The file that holds the contexts can export two functions, `useCart` and `useCartDispatch`, that return `useContext` of each context; components call them instead of importing the contexts, and the contexts no longer need to be exported.
- **Move**: Side by side, because `useContext(CartDispatchContext)` and `useCartDispatch()` look different and are the exact same thing.
- **Opening Essence**:
  - Smallest code: `export function useCart() { return useContext(CartContext); }`, `export function useCartDispatch() { return useContext(CartDispatchContext); }`, and in a component `const dispatch = useCartDispatch();`
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* The docs: "This doesn't change the behavior in any way, but it lets you later split these contexts further or add some logic to these functions."
  - The docs' Note: "Functions like `useTasks` and `useTasksDispatch` are called *Custom Hooks.* Your function is considered a custom Hook if its name starts with `use`. This lets you use other Hooks, like `useContext`, inside it."
  - The docs' payoff: "**Now all of the context and reducer wiring is in `TasksContext.js`. This keeps the components clean and uncluttered, focused on what they display rather than where they get the data**".
- **Root Distinction**:
  - Junior: "`useCart` is a new Hook from React."
  - Senior: it is our own function, one line long; its name starts with `use` because it calls a Hook.
- **Simplest version**:
  - `CartContext.jsx`: `import { createContext, useContext, useReducer } from 'react';`, `const CartContext = createContext(null);` and `const CartDispatchContext = createContext(null);` without `export`, then `CartProvider`, `useCart`, `useCartDispatch`.
  - `Header.jsx` and `CartList.jsx`: `import { useCart } from '../CartContext.jsx';` and `const cart = useCart();`
  - `CartRow.jsx` and `EmptyCartButton.jsx`: `import { useCartDispatch } from '../CartContext.jsx';` and `const dispatch = useCartDispatch();`
- **Words to teach**:
  - *custom Hook*: our own function whose name starts with `use` and that calls other Hooks. Provided by our code. Needed at `export function useCart`. The full lesson is Lesson 39.
  - Known: Hook, `use` at the start of the name, Lesson 12. `useContext`, Lesson 28.
  - Helper: none.
- **Side by side**:
  - "`const dispatch = useContext(CartDispatchContext);`" and "`const dispatch = useCartDispatch();`": the exact same thing.
  - "contexts with `export`" and "contexts without `export`": the exact same page. Without `export`, the only way in from another file is `CartProvider`, `useCart`, and `useCartDispatch`, as in the docs' last version.
- **Surprises**: none. The page behaves as in Principle 4.
- **Where did that come from?**:
  - `cart` in `Header`: `useCart()` returns what `useContext(CartContext)` returns inside it, the `value` of the closest `CartContext` above `Header`, not above the file `CartContext.jsx`. A custom Hook runs inside the component that calls it.
- **Real beginner mistake**:
  1. A developer writes `onClick={() => useCartDispatch()({ type: 'emptied' })}` in `EmptyCartButton`, calling the Hook inside the click.
  2. Hooks may be called only at the top level of a component or a custom Hook, Lesson 38.
  3. The click fails with an error from React. Text `unconfirmed`.
  4. The fix: call `useCartDispatch()` at the top of `EmptyCartButton` and use `dispatch` in the arrow.
- **Interview depth**:
  - The final shape of the pattern, from the docs: one file with the reducer, two contexts, a provider component, and two custom Hooks; components only call the Hooks.
  - The docs: "As your app grows, you may have many context-reducer pairs like this."
  - Custom Hooks share logic, not state: each call reads the same provider's state here because the provider above holds it. Lesson 39.
- **React does**:
  - Page: unchanged. `unconfirmed`.
  - Console: no warning. `unconfirmed`. Vite's Fast Refresh may print a message when a file exports a component and functions together: `unconfirmed`, see Open Issues.
  - Elements panel: unchanged.
- **Example step**:
  - `CartContext.jsx`: adds `useContext` to the import, adds `useCart` and `useCartDispatch`, removes `export` from the two contexts.
  - `Header.jsx`, `CartList.jsx`, `CartRow.jsx`, `EmptyCartButton.jsx`: import and call the custom Hooks in place of `useContext` and the contexts.
- **Code names**: `useCart`, `useCartDispatch`, `export function useCart() { return useContext(CartContext); }`, `export function useCartDispatch() { return useContext(CartDispatchContext); }`, `import { createContext, useContext, useReducer } from 'react'`, `const CartContext = createContext(null)`, `import { useCart } from '../CartContext.jsx'`, `import { useCartDispatch } from '../CartContext.jsx'`, `const cart = useCart()`, `const dispatch = useCartDispatch()`, `useTasks`, `useTasksDispatch`, `useQueue`, `useQueueDispatch`

## Interview Points

- A reducer keeps the state update logic in one function; context passes values deep into the tree; together they let any component below read and update state that lives above it.
- The docs' three steps: create the contexts; put state and `dispatch` into them from the component that calls `useReducer`; read either one in the components that need it.
- Use two separate contexts, one for the state and one for `dispatch`, each with `createContext(null)`.
- The state still lives in the component that calls `useReducer`; context only delivers it, and components outside the provider get the default value.
- Components in the middle stop passing props they never used; props a component really needs, such as one item for one row, stay.
- `dispatch` has a stable identity, so the value of the context for `dispatch` never changes; when the provider component renders `children`, a component that reads only `dispatch` is not re-rendered by a change of the state.
- One context with `{ state, dispatch }` gives every reader a new object on every render, so every reader renders again.
- A provider component that calls `useReducer` and renders `children` keeps the wiring in one file; its children, created by the parent, are not rendered again when only the provider's state changes.
- Custom Hooks such as `useCart` and `useCartDispatch` wrap `useContext`; they change no behavior and let the file hide the contexts.
- An app can have many context-reducer pairs; this is lifting state up, with context in place of props.
