Calling Hooks Only at the Top Level of React Functions

Interview Question · ❱ CORE

Why must hooks be called at the top level, and only from React functions?

OverviewWhy Every Render Must Call the Same Hooks

A feedback form, and the place of one useState

Many apps end a page with a small feedback form: a message box and a Send button. When the page opens, the box is empty, and its grey placeholder text says Message:

Now look at the same screen as the developer. The component shows one of two screens, the form or the thank-you heading, so its code has an if with two branches. The text the user types lives in a state variable, message, and only the form uses it. So where does the useState for message go: inside the form's branch, next to the form, or at the top of the component?

At the top, always. React's docs say it in one line: "always use Hooks at the top level of your React function, before any early returns."

Why? Well, React does not know a Hook by its variable name. It knows the Hook by its place in the order of Hook calls (as seen in Lesson 12). So every render of a component must call the same Hooks, in the same order. An if, a loop, an early return, or a function written inside the component must never decide whether a Hook runs.

Two forms that look the same until the user clicks Send

Here are two places for the same line, the useState for message:

  1. At the top of the component, above the if.
  2. Inside the form's branch, right next to the form that uses it.

It may look the same, or work the same at first, but it is NOT the same thing! Both versions show the empty box when the page opens, and in both the user can type. Only the version with useState at the top shows Thank you! after Send. The version with useState inside the form's branch crashes, with the error that React's docs quote: "Rendered fewer hooks than expected".

What is at stake

What is at stake is the user's last click. The user writes a message and clicks Send. Instead of Thank you!, the whole page goes blank, and the message is gone. React's docs explain the blank page: "By default, if your application throws an error during rendering, React will remove its UI from the screen."

The bug hides well. The page opens without an error, and typing works. A developer who only types in the box never sees the crash. The first user who clicks Send sees it.

Readers usually go wrong in four ways:

  1. They think React finds message by its name.
  2. They move a Hook next to the code that uses it, inside a branch.
  3. They silence the linter when it marks that line, so the bug ships.
  4. They call a Hook inside an event handler, to create state at the moment of the click.

The five principles of this lesson

PRINCIPLES

React keeps the data of every Hook in the order of the calls, and it matches each call to its data by position: the first call gets the first entry, and the second call gets the second. React's docs name two rules that keep those positions right, and they call them the Rules of Hooks: "Only call Hooks at the top level" and "Only call Hooks from React functions". Five principles follow from them:

  1. React sees an order, not names. In FeedbackForm, React never sees isSent or message. It sees a first Hook call and a second Hook call, and this holds for every kind of Hook.
  2. A Hook in a branch crashes the render that skips it. When the user clicks Send, the thank-you render calls fewer Hooks than the render before it, and React stops.
  3. Every Hook goes above the first return. Move the Hook up, and let the if decide only what the component returns.
  4. The condition moves, not the Hook. When a Hook seems to need a condition, the condition goes inside the Hook, into its initial value, or into a new component.
  5. Hooks run only while React renders. A Hook works in a function component or a custom Hook, never in an event handler or a regular JavaScript function.

Section 1 · Principle 1Two useState Calls in FeedbackForm Run in One Order

Neither Hook call passes a name to React

Look at two state variables at the top of a component:

Two useState calls, one after the other
1const [name, setName] = useState('John');
1st Hook call: React matches 'John' to it
2const [count, setCount] = useState(0);
2nd Hook call: React matches 0 to it

The names name and count exist only inside our function. Neither call hands a name to React. React receives only 'John' and 0. So React matches them by order: the first stored value goes to the first call, and the second goes to the second (as seen in Lesson 12). React's docs say Hooks "rely on a stable call order on every render of the same component."

The new fact of this lesson is that the order counts for every Hook, not only useState. useEffect, useRef, and useReducer are matched by their place in the same way. useContext keeps no data of its own, because it reads the nearest provider. React still counts it in the order, and React prints an error in the Console when the useContext call moves. React's docs: "Each time your component renders, React expects the exact same hooks to be called in the exact same order."

Renaming a state variable changes nothing for React

Suppose we rename message to text:

The same Hook call under two variable names
1const [message, setMessage] = useState('');
The 2nd Hook call in FeedbackForm
2const [text, setText] = useState('');
Still the 2nd Hook call: React sees no difference

Yes, it is the exact same thing for React! Each line is the second useState call in FeedbackForm, so React hands it the second value it stored.

A Hook belongs at the top, like an import

React's docs give an image for this, and they present it as a way of thinking, not as a fact about the code: "it's helpful to think of them as unconditional declarations about your component's needs. You "use" React features at the top of your component similar to how you "import" modules at the top of your file."

An import line never sits inside an if. It sits at the top of the file, and it always runs. A Hook belongs in the same kind of place. Unconditional means that no condition decides whether it runs.

React's docs call that place the top level of your React function. It is the body of the component itself:

  1. Outside any if, any loop, and any nested function, which is a function written inside the component.
  2. Above the first early return.

Principle 1

Call Order: React Matches Every Hook by Its Place in the Order

React tracks every Hook in a component, of any kind, by its place in the order of Hook calls, so every render must call the same Hooks in the same order.

React never receives the names isSent or message. It receives a first Hook call and a second Hook call, and it hands each one the data stored at that position. This works only while every render makes the same calls in the same order. That is why every Hook sits at the top level of the component.

Clicking Send blanks the page

Beware! With the Hook inside else, the click on Send removes the whole page. The thank-you render calls one Hook where the render before it called two, and React stops. Here is what happens, in order:

  1. The page opens. isSent is false. React calls the useState for isSent, goes into else, and calls the useState for message. That makes two Hook calls.
  2. The user types Great app. Each letter typed by the user calls setMessage, and each render makes the same two calls.
  3. The user clicks Send. The onSubmit function stops the browser from reloading the page, and it sets isSent to true.
  4. React calls FeedbackForm again. The first Hook call now returns true.
  5. The if returns the thank-you heading, so the useState for message never runs. That makes one Hook call.
  6. React expected two Hook calls and got one. It throws an error while rendering FeedbackForm.
  7. Nothing above the form catches the error, so React removes the whole page from the screen. A component that catches such an error and shows a fallback screen instead is called an error boundary, and our page has none.

The same crash in the other direction

Suppose a Hook sits inside the if branch instead, so it runs only after Send. Then the thank-you render calls more Hooks than the render before it, and React stops with "Rendered more hooks than during the previous render." (as seen in Lesson 12). Just before that error, React prints another one: "React has detected a change in the order of Hooks called by FeedbackForm". Under it, a table lists the Hooks of the two renders.

Fewer or more, the cause is the same: a condition decided whether a Hook ran.

Every place where a Hook must not go

React's docs list every place where a Hook call is not supported:

  1. Inside a condition, such as an if, a ternary, &&, or ||.
  2. Inside a loop, such as for. The number of Hook calls would then follow the number of items.
  3. After a conditional return.
  4. In an event handler.
  5. In a class component.
  6. Inside a function passed to useMemo, useReducer, or useEffect.
  7. Inside a try, catch, or finally block.

The docs page for the linter adds two more places: an async function, and the top of a file, outside any component.

The tool that catches all of these is the lint rule rules-of-hooks, from the package eslint-plugin-react-hooks. The package comes with a ready-made set of rules called the recommended preset. This rule is part of it, so every project that uses the preset has the rule on. It marked our line inside else. The developer silenced it, and the bug shipped. The docs' hint for this exercise says where to look first: "Check if there are any comments disabling the linter checks--this is where the bugs often hide!"

Principle 2

Hooks in Branches: A Hook in a Branch Crashes the Render That Skips It

A Hook inside a condition, a loop, or below an early return runs on some renders and not on others, so the number of Hook calls changes and React stops with an error.

Where a value is used and where its Hook is called are two separate things. Only the form uses message, but the useState for message must also run on the thank-you render. When a render skips a Hook, React throws "Rendered fewer hooks than expected", and without an error boundary the whole page goes blank.

2if (isSent) {
3 return <h1>Thank you!</h1>;
4} else {

Section 3 · Principle 3useState Above the First return Brings Back Thank You

The same line in two places

The fix is to move one line. Here is the useState for message in its two possible places:

useState for message inside else, below the if
1if (isSent) {
2 return <h1>Thank you!</h1>;
3} else {
4 const [message, setMessage] = useState('');
WRONG skipped on the thank-you render
5}
useState for message above the if
1const [isSent, setIsSent] = useState(false);
2const [message, setMessage] = useState('');
Runs on every render, before the first return
3if (isSent) {
4 return <h1>Thank you!</h1>;
5}

It looks the same, but it is NOT the same thing! With useState inside else, the thank-you render makes one Hook call. With useState above the if, every render makes two Hook calls, so the order never changes.

React's docs give this exact fix for this exact form: "Hooks can only be called at the top level of the component function. Here, the first isSent definition follows this rule, but the message definition is nested in a condition. Move it out of the condition to fix the issue". They add: "Remember, Hooks must be called unconditionally and always in the same order!"

The else branch is no longer needed

Once both Hooks sit above the if, the else around the form has no job left. The if already returns early, so the lines below it run only when isSent is false. With the else or without it, the form behaves the same. Yes, it is the exact same thing! React's docs suggest removing it "to reduce the nesting", and they keep one condition: "it's still important that all calls to Hooks happen before the first return."

The thank-you screen still has a message

A common worry is that the thank-you screen does not need message, so it should not create it. But creating a value and showing it are two separate things. On the thank-you render, the second Hook call still runs, and React still hands back 'Great app'. The thank-you screen simply does not show it.

The same mistake on a loading screen

Developers often meet this rule with an early return for a screen that is not ready yet, such as a loading line. React's docs show this case:

Principle 3

Top Level: Call Every Hook Above the First Early return

Call every Hook at the top level of the component, above the first early return, and let the condition decide only what the component returns.

An early return stops the function, so every Hook written below it is skipped on that render. Move the Hook above the return, and every render calls the same Hooks. The component then creates every value on every render, and the if decides only which screen the user sees.

Section 4 · Principle 4The Condition Moves Inside the Hook

Moving the condition, not the Hook

Sometimes a developer really needs a Hook "only sometimes": an Effect only for a signed-in user, or a starting value that depends on the kind of user. The Hook still stays at the top. The condition moves instead. React's docs give four ways to move it:

  1. Put the condition inside the Effect.
  2. Give useState a conditional initial value.
  3. Extract a new component and move the state into it.
  4. Read context with use instead of useContext.

1. The condition goes inside the Effect

Suppose a developer wants to fetch the user's data only when the user is signed in. The first idea is to wrap the Effect in an if:

useEffect inside if
1if (isLoggedIn) {
2 useEffect(() => {
WRONG when the user signs in, the next render calls one more Hook
3 fetchUserData();
4 }, []);
5}

React's docs keep the Effect at the top and move the if inside it:

if inside the Effect
1useEffect(() => {
Called on every render, so the number of Hook calls never changes
2 if (isLoggedIn) {
3 fetchUserData();
4 }
5}, [isLoggedIn]);
The Effect runs again when isLoggedIn changes

It looks the same, but it is NOT the same thing! With useEffect inside the if, the useEffect call itself comes and goes with isLoggedIn. With the if inside the Effect, React gets one useEffect call on every render, and the condition decides only what the Effect does. Because isLoggedIn is in the dependency array, the Effect runs again when the user signs in (as seen in Lesson 32).

2. The condition goes into the initial value

Suppose the starting permissions depend on the kind of user. The first idea is two useState calls in two branches:

Two useState calls in two branches
1if (userType === 'admin') {
2 const [permissions, setPermissions] = useState(adminPerms);

4 const [permissions, setPermissions] = useState(userPerms);
WRONG a Hook inside else
5}

React's docs replace them with one useState and a conditional initial value: a ternary picks the starting value, and the Hook call stays at the top:

One useState with a conditional initial value
1const [permissions, setPermissions] = useState(userType === 'admin' ? adminPerms : userPerms);
One Hook call, and the condition picks only the starting value

Both versions try to start permissions with the right value, but they are NOT the same thing. In the version with two branches, each useState sits inside a condition, so the linter marks both lines. In the version with the ternary, useState sits at the top level and is called once on every render. Keep in mind that React uses an initial value only on the first render, so the ternary picks the starting value once.

4. Context goes through use

The last case is a branch that only reads context. useContext is a Hook, so it must stay at the top. But React has an API that may sit inside an if: use (as seen in Lesson 28).

Principle 4

Moving the Condition: The Hook Stays, the Condition Moves Inside It

When a Hook seems to need a condition, keep the Hook at the top level and put the condition inside it, in its initial value, or in a new component that holds the Hook.

A condition may decide what a Hook does, never whether it runs. Inside an Effect, the if decides what the Effect does. In useState, a ternary picks the starting value. When state belongs to one branch only, a new component holds it, and the parent's if decides whether that component appears.

Section 5 · Principle 5A Hook Inside the onSubmit Function Breaks Send

It may look the same, but it is NOT the same thing! Only FeedbackForm is a React function. React's docs use that name for the two kinds of functions that may call Hooks:

  1. A function component, such as FeedbackForm. React calls it to render.
  2. A custom Hook, a function our code writes whose name starts with use followed by a capital letter, such as useOnlineStatus. A custom Hook may call other Hooks, and a component calls it at its own top level. The next lesson covers custom Hooks in full.

Every other function is a regular JavaScript function, and it may not call Hooks. React's docs give the reason: "You can only call Hooks while React is rendering a function component". React knows which component a Hook call belongs to only while it renders that component. A regular function can run at any moment our code chooses, outside any render.

The use prefix shows where state may hide

The rule has a purpose beyond the crash. React's docs: "By following this rule, you ensure that all stateful logic in a component is clearly visible from its source code."

The naming convention makes that visible. React's docs: "Hook names must start with use followed by a capital letter". So a reader of the code can tell at a glance which calls may hold state. The docs give an example: a call to a function named getColor inside your component "can't possibly contain React state inside because its name doesn't start with use."

So the prefix is a promise, and it belongs only on functions that call Hooks. Take a function named useSorted that calls no Hook, and a function named getSorted with the same body. Yes, it is the exact same code! React's docs: "Functions that don't call Hooks don't need to be Hooks." Name it getSorted, and you may even call it inside an if, because it is not a Hook.

Principle 5

React Functions Only: Call Hooks While React Renders a Component or a Custom Hook

Call Hooks only while React renders a function component or a custom Hook, and never from an event handler, a regular JavaScript function, or a class component.

A Hook needs the component that React is rendering at that moment. An event handler runs later, when the user clicks, outside any render, so a Hook inside it throws. Keep every Hook at the top level of a component or a custom Hook, and let event handlers call only setters.

Interview PrepFor the Interview

The Interview Question: Why must hooks be called at the top level, and only from React functions?

How to Answer Clearly in 30 Seconds

"React does not identify a Hook by its variable name, because no Hook call passes a name. It matches each call to its stored data by its place in the order of Hook calls. So every render must call the exact same Hooks in the exact same order. Two rules keep that order safe:

  1. Only call Hooks at the top level: never inside a condition, a loop, or a nested function, and never below an early return. If a feedback form calls the useState for its message inside an else, the thank-you render skips it, React throws 'Rendered fewer hooks than expected', and the page goes blank.
  2. Only call Hooks from React functions: function components and custom Hooks, never event handlers or regular functions. React ties a Hook call to the component it is rendering at that moment, and the use prefix shows a reader where state may hide.

When a Hook seems to need a condition, I keep the Hook at the top and move the condition inside it, into its initial value, or into a new component. The rules-of-hooks lint rule catches these mistakes, so I never silence it."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why does React use call order instead of names?"
    Order keeps the syntax short: a call to useState needs no key or label. React's docs say Hooks "rely on a stable call order on every render of the same component". This works in practice because the top-level rule keeps the order the same, and the linter catches most mistakes. The cost is the rule itself: a Hook may never be skipped on one render and called on another.
  2. "How do you run an Effect only when a condition is true?"
    You call useEffect on every render and put the if inside the Effect function, so the Effect checks isLoggedIn before it fetches the user's data. Then you add isLoggedIn to the dependency array, so the Effect runs again when the condition changes. Wrapping useEffect itself in an if changes the number of Hook calls when the user signs in.
  3. "Can anything like a Hook be called inside an if?"
    Yes, use. React's docs say use "can be called inside conditionals like if and loops like for", while useContext must stay at the top level. use is not a Hook, but it still has two limits: it cannot sit inside a try and catch block, and it must be called inside a component or a Hook. A regular function such as getSorted may also be called inside an if, because it is not a Hook.
