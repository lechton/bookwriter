How a Form Remembers the Answer of Its Last Submit

A newsletter box that answers after every click

Picture the bottom of a news site. A small box reads "Get our weekly news". It has one email box and one Sign up button. Every reader has seen one.

The user types john@example.com and clicks Sign up. Two things happen, one after the other:

  1. For about one second, the button reads "Signing up..." and the user cannot click it.
  2. Then one line appears under the button: "Thanks! john@example.com is signed up."

Later, the user signs up with the same email again. This time the line under the button reads "This email is already signed up".

So after every submit, the form must remember two things:

  1. What the last submit answered: the thanks line or the error line.
  2. Whether a submit is still running: so the button can read "Signing up..." and refuse a second click.

A plain form action already receives the form data and can send the email to a server (as seen in Lesson 41). But React does nothing with what a plain form action returns, so the answer has nowhere to go. React also tracks the pending state of every action, but a plain form action gives our component no variable to read it (as seen in Lesson 41).

React gives us both with one Hook: useActionState. It keeps what the action returned last time as state. It also gives a pending flag, isPending. A flag is a value that is either true or false, and pending means waiting: the submit has started, and its answer is not on the screen yet. React turns isPending on when the action starts and off when the answer is on the screen. The name of the Hook says what it holds: the state that comes out of an action.

What is at stake

Without useActionState, we keep both values by hand. One useState holds the message, another holds the pending flag, and our code sets each one at the right moment. Forget one line, and the user sees it:

  1. The button stays on "Signing up..." forever, and the user cannot try again.
  2. Or the thanks line for the last email stays on the screen, while the new email was refused.

Readers usually go wrong in one place. They keep the shape of a plain form action, which takes the form data as its only parameter (as seen in Lesson 41). With useActionState, React hands the action one more value first, so the form data moves to second place. Principle 2 shows both shapes.

Three ways to show the answer and the pending state

Developers really choose between three ways for this same job:

  1. useState for the message and useState for the pending flag, both set by hand in a submit handler (as seen in Lessons 33 and 40). This fits any React version, and code that does not run as a form action.
  2. useState with useTransition, which a later lesson teaches. This fits when several actions must run at the same time. The useActionState page of the React docs says: "If you want to perform Actions in parallel, use useState and useTransition directly."
  3. useActionState. This fits when the screen shows the result of the last submit, and the submits run one after the other.

This lesson teaches the third way. Principle 4 puts it next to the first.

Four Principles of useActionState

PRINCIPLES

useActionState keeps the answer of the last submit as state, and tells us whether a submit is still running. Four rules come up in daily debugging and in interviews:

  1. useActionState Gives the Form Three Values: the Hook returns the current state, an action to give to the form, and isPending. The form must get that returned action, not our signup.
  2. formData Moves to the Second Parameter: React calls our action with the previous state first and the form data second, so the action must keep both places.
  3. The Returned Text Becomes the Message Line: whatever our action returns becomes the new state. So a known problem, such as an email already signed up, is returned, not thrown.
  4. isPending Turns the Button into Signing up...: isPending is true while the action runs. The button can read "Signing up..." with no extra useState, and with no line for us to forget.

Here is the complete map of those four principles before we walk through each one:

Section 1 · Principle 1useActionState Gives the Form Three Values

One line, three values

Here is the whole Hook in one line, and the one place where its second value goes:

useActionState in one line
1const [message, signupAction, isPending] = useActionState(signup, null);
Returns three values, in this order
2
3<form action={signupAction}>

useActionState takes two arguments:

  1. signup: our action, the function that does the work when the user submits the form.
  2. null: the initial state, what message holds before the first submit.

It returns three values. Array destructuring gives each one a name of our choice, in order (as seen in Lesson 12):

  1. message: the current state. On the first render, it equals the initial state, null. After each submit, it equals what signup returned.
  2. signupAction: the action to give to the form. React builds it around our signup. The React docs name this value dispatchAction, the action dispatcher. To dispatch means to send off: each call of signupAction sends one new submit to React.
  3. isPending: true while a submit is still running. Principle 4 uses it.

It looks like useState, but it is NOT the same thing

The first line looks a lot like a useState line. Put the two side by side:

With useState and with useActionState
1const [message, setMessage] = useState(null);
Two values: our code calls setMessage with the new message
2const [message, signupAction, isPending] = useActionState(signup, null);
Three values: the form calls signupAction

It may look the same, but it is NOT the same thing! Both lines give a message that starts as null. The difference is in the second value:

  • With useState, the second value is a setter. Our code calls it and hands it the new message.
  • With useActionState, the second value is an action. Our code never hands it a message. The form calls it, React calls our signup, and React stores what signup returns as the new message.

React calls signup, not our code

React calls signup for us, and React stores what it returns. Our code calls neither signup nor a setter, yet the line changed. Here is what happens after the user clicks Sign up:

  1. The form calls the action in its action prop, signupAction.
  2. signupAction calls our signup.
  3. signup returns 'Thanks, you are signed up!'.
  4. React stores that text as the new message and renders Newsletter again. This time message is not null, so the line appears.

Mistake: calling the action while the component renders

Another developer wants the form to run once when the page opens, so they call the action in the component body:

Principle 1

Three Values: The Form Gets the Action That useActionState Returns

Call useActionState(signup, null) at the top of the component, destructure the current state, the action, and isPending, and give the form the returned action.

A form needs to show what its last submit answered. useActionState keeps that answer as state: on the first render it holds the initial state, and after each submit it holds what our action returned. React stores the answer only when the form calls the action that useActionState returned. When the form gets our own signup, it runs, but its answer goes nowhere.

Section 2 · Principle 2formData Moves to the Second Parameter

The same line inside two parameter lists

Now signup must read the email the user typed. A plain form action is called with one value, the form data (as seen in Lesson 41). Look at two ways to write the parameters of signup:

With formData alone and with previousState first
1function signup(formData) {
The plain form action shape: one parameter
2 const email = formData.get('email');
3}
4
5function signup(previousState, formData) {
The useActionState shape: two parameters
6 const email = formData.get('email');
7}

It may look the same, but it is NOT the same thing! Both read the email with the same formData.get('email'). But who calls the action decides what arrives in each place:

  • A plain form action is called by React with the form data in first place.
  • An action given to useActionState is called through signupAction, and signupAction puts one more value first: the previous state. So the form data moves to second place.

What previousState holds

previousState holds what signup returned last time:

  1. On the first submit, it is the initial state, our null.
  2. On every later submit, it is the value that signup returned on the submit before.

That shape should look familiar. A reducer receives the current state first and returns the next state (as seen in Lesson 27). For that reason, the React docs call the function we give to useActionState a reducerAction: it turns the previous state into a new state, like the reducer of useReducer. One difference stands out. A reducer must be pure, but this function may have side effects, such as sending a request to a server. That is why the docs call it an Action too.

Our signup does not need previousState yet. It must still keep the first place, because React fills the places in order.

Two returns, two lines on the screen

The line under the button changes in only one way: through what the action returns. useActionState gives our code no setter to call.

The line changes with no setter

Two submits with the same email give two different lines, and no line of our code sets message. Each line is simply what signup returned. Here is what happens, in order:

  1. The user types john@example.com and clicks Sign up. React calls signup with null and the form data.
  2. signUp waits one second and returns null, because the email is new. So signup returns 'Thanks! john@example.com is signed up.', and React shows that line.
  3. The user types john@example.com again and clicks Sign up. This time React passes the thanks text as previousState.
  4. signUp finds the email on its list and returns 'This email is already signed up'. signup returns that text, and React replaces the line with it.

Return a known error, do not throw it

"Already signed up" is a failure, so a developer may want to throw it, as they would inside a try block. Put the two side by side:

  • With throw new Error(error), the text never becomes state. React passes the error to the nearest error boundary. Our page has none, so the newsletter box disappears, as it did in Principle 2.

The React docs draw the line between the two:

  1. A known error, such as an email already signed up, is part of the answer. Return it, and show it on the screen.
  2. An error you did not expect, such as a bug in the code, is thrown.
Principle 3

Returned State: What the Action Returns Becomes the Line

Return every answer the user should read, including known errors such as an email already signed up; throw only for failures you did not expect.

Mistake: the flag that never turns off

The hand-written version has one line that is easy to lose. When the request throws, the button freezes:

  1. Our handler calls setIsPending(true).
  2. The request throws, for example when the network fails.
  3. The line setIsPending(false) never runs.
  4. The button stays on "Signing up..." and disabled. The user cannot try again.

The usual fix is a try and finally block around the request. With useActionState, there is no such line to forget. A request that throws inside the action goes to the nearest error boundary, as Principle 3 showed, instead of leaving a frozen button.

For the Interview

The Interview Question: How does useActionState manage a form's submitted state and pending flag?

How to Answer Clearly in 30 Seconds

"useActionState takes an action and an initial state, and returns three values: the current state, an action to pass to the form, and isPending. When the user submits, React calls my action with two arguments: the previous state first and the form data second. Whatever my action returns becomes the new state, so the screen shows the answer of the last submit with no setter in my code. That is why I return known errors, such as an email already signed up, instead of throwing them. isPending is true while the action runs, so I can disable the button without a second useState and without a finally block that turns the flag off."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why does the action receive the previous state as its first argument?"
    Because useActionState works like a reducer: the action turns the previous state into the next one. On the first submit, the previous state is the initial state. After that, it is what the action returned last time. The difference from useReducer is that a reducer must be pure, while this action may send a request to a server. So the form data moves to second place, and an action written in the one-parameter shape of a plain form action reads the form data from the wrong place.
  2. "What happens if the user submits the form twice before the first answer comes back?"
    On our form, this cannot happen, because the button is disabled while isPending is true. Without disabled, React puts the second submit in a queue, a waiting line, and runs the submits one after the other, so each call receives the result of the one before. The React docs say this is intentional in the design of useActionState. isPending stays true until every submit in the queue has finished, and then React renders once with the final state. When several actions must run at the same time, the docs recommend useState with useTransition instead.
  3. "How do you show a server error with useActionState?"
    A known error, such as an email already signed up, is part of the answer. So the action returns it as state, and the component renders it like any other message. An error the code did not expect is thrown. A thrown error does not become state: React cancels every submit still waiting in the queue and passes the error to the nearest error boundary.
