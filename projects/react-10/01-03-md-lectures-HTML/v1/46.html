How to Choose Between a Framework and a Build Tool

Interview Question · ❱❱ MORE

How do you choose between a full-stack framework and a standalone build tool?

OverviewWhy the Choice Comes Before the First Line of Code

It may look the same, or work the same at first, but it is NOT the same thing! Build this shop twice: once with Vite alone, and once with a framework. In the developer's browser, the two product pages look the same. The HTML file that leaves the server is different:

  • With Vite alone, the root in that file is empty. JavaScript adds the product later, in the browser.
  • With a framework that makes the page on the server or at build time, the file already holds Blue Sneakers before any JavaScript runs.

React draws the components and leaves three questions open

React's home page says it plainly: "React is a library. It lets you put components together, but it doesn't prescribe how to do routing and data fetching."

So every React app must answer three questions that React itself leaves open:

  1. What does the first HTML file hold? An empty root, or the finished page?
  2. Which URL shows which page? This question is called routing.
  3. When does the data load? After the page renders, or before?

A full-stack framework, or framework for short, answers all three for us. Full-stack means it can also do work on a server, not only in the browser. Next.js and React Router are two of them. A build tool such as Vite answers none of them. It leaves all three to our own code.

The two words "library" and "framework" come from everyday life, and they tell us who is in charge. With a library, we are in charge: we take the tool we need, the way we take a book from a library shelf, and we decide how the rest of the app is built. A framework is a frame, like the frame of a house that already stands: it decides the shape of the app, such as where each page lives and when it loads its data, and we fill in the rooms. React is the library. A framework such as Next.js is the frame built around it.

What is at stake

The choice shows up on the user's screen in three places:

  1. The shared link shows the wrong title. A chat app builds its preview card with a crawler: a program that downloads a web page to read what it says. Social media crawlers usually do not run JavaScript, so the card can show only what the HTML file holds.
  2. The user waits twice. First for the whole JavaScript bundle, then again for the product data, before the product appears.
  3. A link to one product opens the home page. This happens when the app keeps the current page in state instead of in the URL.

Where readers usually go wrong

  1. They think a framework always needs a server. react.dev says the opposite: "Full-stack frameworks do not require a server."
  2. They think server rendering is only for search engines. react.dev: "A common misunderstanding is that server rendering is only for SEO." SEO is the work of making a page easy for search engines to find. Server rendering also shows the content to the user before the JavaScript loads.
  3. They start a new app with npx create-react-app. react.dev has deprecated it.

The ways to start a React app

When developers start a React app at work, they choose one of these ways. react.dev lists each one with its command:

  1. A full-stack framework. react.dev recommends this for a new app or website:
    - Next.js, with its App Router.
    - React Router, version 7.
    - Expo, for native apps.
  2. A build tool, starting from scratch: Vite, Parcel, or Rsbuild. react.dev says this fits when "your app has constraints not well-served by existing frameworks, you prefer to build your own framework, or you just want to learn the basics of a React app".
  3. A build tool such as Vite, for React in part of an existing page, such as a page made with Rails. The rest of the site already exists in another technology, and React takes over one element of that page.
  4. Not a way: Create React App. react.dev: "Should I use Create React App? No. Create React App has been deprecated."

PRINCIPLES

A framework and a build tool both run React. They differ in what they decide for us. Six practical rules come up when a team makes this choice, in daily debugging and in React interviews:

  1. Principle 1: A Build Tool Prepares Our Files, and Nothing Else. Vite turns JSX into JavaScript, packs the files into a bundle, runs a development server, and makes the production files. Routing, data loading, and server rendering are not part of it.
  2. Principle 2: The First HTML Holds Only an Empty Root. In an app made with a build tool alone, the HTML file the server sends holds no product. The user sees a blank page, and a crawler sees no content, until the JavaScript runs.
  3. Principle 3: A Page Kept in State Has No URL of Its Own. When the app picks its page with useState, every page has the same address. A shared link always opens the first page. A router gives each page its own URL.
  4. Principle 4: A Loader Starts the Fetch Before the Page Renders. A fetch in an Effect waits for the bundle and the first render. A framework's loader starts the fetch first, while the code is still downloading.
  5. Principle 5: A Framework Can Put the Product into the HTML. A framework can make a page on the server or at build time, so the file already holds the product. It chooses this for each page, and it does not need a server.
  6. Principle 6: An Admin Tool Behind a Login Can Stay on Vite. When no page must show its content before the JavaScript runs, and no page needs its own URL, a build tool is enough.

PRINCIPLE1A Build Tool Prepares Our Files, and Nothing Else

One command starts a Vite project

Here is react.dev's own command to start a React app with Vite:

Terminal: starting a React app with Vite
1npm create vite@latest my-app -- --template react-ts

The command creates a new folder named my-app, the name we chose, and copies Vite's starting files into it. The option react-ts asks for React with TypeScript. The template named react gives plain JavaScript files instead, like the .jsx files of our shop.

Inside the folder, two commands do the daily work (as seen in Lesson 07 and Lesson 15):

Terminal: the two daily commands
1npm run dev
2npm run build
  1. npm run dev starts the development server while we write code.
  2. npm run build makes the files we put on a production server.

react.dev calls this path "building a React app from scratch". The name sounds like new and harder work. Yes, it is the exact same thing as the project we already know (as seen in Lesson 07): one index.html, one main.jsx, and Vite. Nothing new is added. This lesson only gives the path its name.

What a build tool does, and what it leaves to us

A build tool is a program that prepares our source files for the browser. react.dev lists its jobs: build tools "provide features to package and run source code, provide a development server for local development and a build command to deploy your app to a production server."

So Vite does four jobs for us:

  1. It turns JSX into JavaScript that the browser can run.
  2. It packs our files into a bundle.
  3. It runs a development server.
  4. It makes the production files with a build command.

That is all. react.dev says the build tools "start off with a client-only, single-page app", or SPA for short. Two words in that sentence matter:

  • Single-page app, SPA: the browser loads one HTML document, and JavaScript changes what that one document shows. Our shop has one index.html, and every page of the shop is drawn inside it.
  • Client-only: the client is the user's browser. All the drawing happens there. Nothing is drawn on the server.

Routing, data fetching, and rendering on the server are not part of a build tool. If the app needs them, our team adds them.

What the chat app receives

The preview card reads Shop because the chat app never runs our JavaScript. Here is what happens when the user pastes the product link, in order:

  1. The chat app's crawler downloads the HTML file of the link.
  2. The crawler does not run the JavaScript in that file.
  3. In that file, the only title is Shop, and the root is empty.
  4. So the card reads Shop. It reads Shop for this product and for every other product of the shop, because a single-page app sends the same index.html for every page.

After npm run build, the file the server sends is still our index.html. Vite only replaces our script tag with one in the head that points at the bundle it made, under a file name that Vite chooses:

The file the server sends after npm run build, shortened
1<title>Shop</title>
The same title for every product
2<div id="root"></div>
Still empty: Blue Sneakers is not in the file

Search engines have crawlers too. MDN explains the difference between the two kinds: "major search engines are capable of executing JavaScript so pure CSR sites can still be indexed, but social media crawlers usually cannot."

CSR in that sentence stands for client-side rendering: JavaScript makes the content of the page in the browser. That is exactly what our shop does. MDN's own example of a CSR page holds only <div id="root"></div>, like ours.

What the friend's slow phone shows

The friend waits twice: first for the bundle, then for the product. Here is what the slow phone does, in order:

  1. The page is blank while the bundle downloads. react.dev describes it: "the user sees a blank page until the app's JavaScript code loads and runs."
  2. React runs and draws Loading..., and only then does the Effect ask for the product.
  3. One second later, Blue Sneakers appears.

On the developer's computer, the bundle arrives in a moment, so the blank page is too short to notice. On a slow phone, it is the first thing the user sees.

Why this bug ships

This mistake is easy to make, because nobody on the team sees it at first:

  1. A team starts a public shop with Vite alone, because the first screen is quick to build.
  2. Every page looks right on the developers' computers.
  3. Months later, the marketing team shares product links, and every preview card shows the same shop title.
  4. The team learns that the HTML of every page is the same empty file.
  5. To fix it, someone must make the HTML on the server or at build time. When a team starts from scratch, react.dev says it "will have to implement" this on its own.

react.dev gives the cure in the docs of createRoot: "To solve this, you can generate the initial HTML from your components on the server or during the build." And it adds: "We recommend using a framework that does this optimization out of the box." Principle 5 shows what that looks like.

Client-side rendering has a real benefit too. Once the bundle has loaded, the user moves between pages without a full page reload. The cost is the empty first file.

The same shop with a router

A router library ties each page to its own URL. React Router is one of the routers react.dev suggests for an app made with a build tool, together with TanStack Router. It is a library we install with npm. It is not part of React:

Why a router pulls in a framework

At work, the router is rarely the end of the story:

  1. A developer on a Vite app needs a second page and keeps the current page in state, because useState is the tool the developer already knows.
  2. Clicks work, so the code ships.
  3. A user bookmarks a product, and the bookmark opens the home page.
  4. The team installs a router.
  5. Now the router must also work together with data loading and with code splitting. react.dev says routers "are usually integrated with data fetching", with code splitting, and with the way each page is rendered (code splitting is taught in Lesson 70).

At that point, the team is writing the parts of a framework by hand. That is why react.dev gives this rule of thumb: "if your app needs routing, you would probably benefit from a framework".

Principle 3

When the app picks its page with useState, the click changes state and the address bar stays the same. A friend who opens the shared link starts the app from the first state again and sees the home page. A router ties each URL to a page, so /products/1 always opens the sneakers. Once an app needs routing, react.dev suggests a framework.

Counting the waits with useEffect

With useEffect, every wait starts only after the one before it has ended. Here is the friend's first visit to the product page made with Vite alone:

  1. The browser downloads the HTML file.
  2. The browser finds the script tag and downloads the bundle.
  3. React renders Product for the first time, and the page shows Loading....
  4. Only now does the Effect run and call getProduct().
  5. One second later, Blue Sneakers appears.

react.dev calls this chain a network waterfall: "Network waterfalls are caused by fetching data when your app renders instead of in parallel while the code is downloading." The name is an image: like water falling from one step to the next, each request starts only when the step above it is done.

On a bigger page, the waterfall grows longer. The product renders, then its reviews component renders and fetches its own data, and the user sees one Loading... after another.

The same page with a loader

A framework's router offers a loader: a function we export from the same file as the page component. The router calls it to get the page's data. react.dev: "On initial load, the router can fetch the data immediately before the route is rendered."

PRINCIPLE5A Framework Can Put the Product into the HTML

The file with an empty root vs. the file with the product

A framework can send the finished page inside the HTML file itself. Then the product is there before any JavaScript runs. Compare the part that matters in the two files the server sends for the same product page:

With Vite alone: the file the server sends, shortened
1<body>
2 <div id="root"></div>
Empty: JavaScript adds the product later
3</body>
With a framework that renders on the server: the file the server sends, shortened
1<body>
2 <h1>Blue Sneakers</h1>
Already in the file before any JavaScript runs
3 <p>$49</p>
4</body>

Each framework adds its own wrapper tags and script tags around the page. We leave them out here.

It may look the same, or work the same at first, but it is NOT the same thing! Once the JavaScript has loaded, both shops show Blue Sneakers in the developer's browser. Only the second file shows it to a crawler, and to a user whose JavaScript has not loaded yet.

Who made that HTML

Our code did not make it. The framework did. It ran our components with React, together with the data from loader, and wrote the result into the file. A framework can do this at two moments:

  • Server-side rendering, SSR: the framework makes the HTML on the server, for every request. When the friend opens the link, the server runs loader, renders Product, and sends the finished file.
  • Static site generation, SSG: the framework makes the HTML files once, during the build. The finished files then sit on a static host or a CDN: servers that only hand out ready files and never run our code.

Both give a file that already holds the product. They differ in when the file is made. react.dev gives an example of each: a Terms of Service page or documentation can be static, "while a page with a content feed might perform best with server-side rendering".

What the chat app and the slow phone receive now

The team moves the shop to a framework, and the product page becomes the route with a loader from Principle 4. Here is what changes:

  1. The user pastes the product link into a chat app.
  2. The chat app's crawler downloads the HTML file, which now holds Blue Sneakers.
  3. The crawler can now read the product name without running any JavaScript. To show that name as the title of the preview card, each page also needs its own <title> in that file (taught in Lesson 121).
  4. The friend opens the link on a slow phone and sees Blue Sneakers before the bundle has loaded.
  5. The buttons on the page start to work only after the JavaScript loads. react.dev: "The user will spend some time looking at the server-generated HTML before your JavaScript code loads."

That last step has a name. Once the bundle arrives, React attaches itself to the HTML that is already on the page, instead of drawing it again. This is called hydration (taught in Lesson 104). In a framework app, we do not even write createRoot ourselves. react.dev: "If you use a framework, it might do this call for you."

This is why server rendering is not only about search engines. react.dev: server rendering sends "a full HTML document which produces a faster First Contentful Paint". First Contentful Paint is the moment the user first sees content on the screen.

A framework does not require a server

Yes, a framework can run with no server at all. react.dev: "Full-stack frameworks do not require a server." The recommended frameworks also support client-only apps and static site generation, and they "can be deployed to a CDN or static hosting service without a server". Next.js also supports a static export, which needs no server.

Here is the mistake this clears up:

  1. A team building an internal dashboard hears "framework" and thinks "server".
  2. The team picks Vite to avoid running a server.
  3. Months later, the dashboard gains public pages that must show their content to crawlers.
  4. Now the team must add server rendering to a Vite app by hand. react.dev warns that this "can be very complex to set up and maintain".

react.dev describes the other path: frameworks "allow you to start with a client-only app, and if your needs change later, you can opt-in to using server features on individual routes without rewriting your app."

Server rendering has its own cost. react.dev: generating pages on the server "incurs additional cost and takes time to generate", which can increase the Time to First Byte. The Time to First Byte is the wait before the browser receives the first byte of the page (this cost is weighed in Lesson 156).

Principle 5

Server Rendering: A Framework Can Put the Product into the HTML, Route by Route

A framework can render a route on the server or at build time, so the file that leaves the server already holds the page's content; it chooses this per route, and it does not require a server.

With server-side rendering, the framework makes the HTML for every request. With static site generation, it makes the HTML once during the build, and a static host can send it with no server. Either way, a crawler finds the product in the file, and a user on a slow phone sees it before the JavaScript loads. A route that does not need this can stay client-only, as with Vite.

When react.dev says a build tool fits

react.dev gives three reasons to start from scratch with a build tool: "your app has constraints not well-served by existing frameworks, you prefer to build your own framework, or you just want to learn the basics of a React app".

It adds a fourth case on another page: adding React to part of an existing site, such as a page made with Rails. There, Vite builds the React part, and createRoot mounts it on one element of that page. Once the whole page is made with React, react.dev recommends moving to a framework.

What Vite costs on a public site

Here is the mistake behind that warning:

  1. A developer picks Vite for a new public site, because react.dev's tutorial and our own earlier lessons used it.
  2. The site grows more routes, more data, and more shared links.
  3. The team adds a router, then a data library, then code splitting, then tries server rendering.
  4. Each fix touches the others. react.dev: "Many limitations you'll hit can be difficult to solve as each problem is interconnected with the others."

react.dev has a name for this result: starting from scratch is "often the same as building your own adhoc framework". Ad hoc means made for one case only. The team ends up with its own framework, built one problem at a time, and nobody outside the team maintains it.

A framework has a cost too, and it is not a server bill. react.dev: frameworks "impose some opinions about structuring your app", the same way build tools do. These opinions are rules, such as where each route file goes and how a page loads its data. For the admin tool, those rules buy nothing.

Principle 6

Choosing the Tool: A Client-Only App Behind a Login Can Stay on Vite

Start a new app with a framework; choose a build tool when the app is client-only and will never need URLs per page or HTML with content, when React goes into part of an existing page, when the team wants to build its own framework, or when the goal is to learn.

The tool follows what the pages need. A public shop needs its products in the HTML and a URL for each page, which a framework gives. An internal admin tool opened only by signed-in staff needs neither, so Vite is enough. Picking Vite for a public site means building an ad hoc framework later, one problem at a time.

Interview PrepFor the Interview

The Interview Question: How do you choose between a full-stack framework and a standalone build tool?

How to Answer Clearly in 30 Seconds

"React is a library. It draws components, but it does not decide what the first HTML holds, which URL shows which page, or when data loads. A build tool such as Vite turns JSX into JavaScript, bundles the code, runs a development server, and builds for production. It starts as a client-only single-page app. So the HTML holds an empty root, social media crawlers usually see no content, and data fetched in an Effect starts only after the bundle and the first render. A full-stack framework such as Next.js or React Router adds routing, loaders that fetch before the route renders, code splitting, and HTML made on the server or at build time, chosen per route. It does not require a server. So for a new app or a public site, I pick a framework, following react.dev's rule of thumb: if the app needs routing, it probably benefits from a framework. I pick Vite for a client-only app such as an internal admin tool, for React inside part of an existing page, or for learning. I never start a new app with Create React App, which is deprecated."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Doesn't a framework force you to pay for and run a server?"
    No. react.dev says it directly: "Full-stack frameworks do not require a server." The recommended frameworks support client-only apps, single-page apps, and static site generation, and they can be deployed to a CDN or a static host. Next.js also supports a static export. A framework lets us start client-only and add server rendering later, on the routes that need it, without rewriting the app. The real cost of a framework is its rules about how to structure the app.
  2. "Isn't server rendering just for SEO?"
    No. react.dev calls that a common misunderstanding. Server rendering sends a full HTML document, so the user sees the content before the JavaScript loads, which gives a faster First Contentful Paint. It also lets chat and social apps read the page from the HTML, because their crawlers usually do not run JavaScript. The cost is server work on every request, which can raise the Time to First Byte. So a framework lets us choose server rendering, static generation, or client-only rendering for each route.
  3. "Why is fetching in useEffect slower than fetching in a loader?"
    An Effect runs only after the component has rendered, and the component renders only after the bundle has downloaded. So the user waits for the HTML, then the bundle, then the first render with Loading..., and only then does the fetch start. react.dev calls this a network waterfall. A framework's loader lets the router start the fetch before the route renders, in parallel with downloading the code, and the component receives the result as loaderData. Without a framework, react.dev points to a client-side cache such as TanStack Query or SWR.
