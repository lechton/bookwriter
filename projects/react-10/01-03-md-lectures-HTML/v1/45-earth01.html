What is at stake

The reset puts each box back to its default value. The default value is the text a box starts with, and the text it goes back to whenever its form is reset. Our two boxes have no default value, so the reset leaves them empty.

That gives us the key idea of this lesson. To keep what the user typed after a refusal, we do not stop the reset. We make the user's text the new default value, so the reset puts that text back.

Two things are at stake for the user:

  1. After every refusal from the server, the user types the whole form again, including the parts that were right.
  2. On a phone with a slow connection, the user may click Create account before the JavaScript of the page has loaded. Whether that click sends anything depends on how the form is built.

Readers usually go wrong by thinking that React resets the form only when the account was created. React resets it after every action that does not throw.

Three ways to keep the text after a refusal

Developers really choose between three ways for this job:

  1. Uncontrolled boxes with defaultValue from the state the action returned. This fits forms built on <form action> and useActionState, the React 19 way. The form stays plain HTML, so it can still work before JavaScript loads.
  2. Controlled boxes with value and onChange (as seen in Lesson 20). This fits a form where the page must change on every keystroke by the user anyway, such as a live hint under the box. React does not reset these boxes at all.
  3. onSubmit with e.preventDefault() (as seen in Lessons 11 and 41). React does no automatic reset here, so the text stays after a refusal by itself. After a success, our code asks for the reset itself, with requestFormReset. This fits older forms that a team moves to Actions step by step.

Five Principles of Form Resets and Progressive Enhancement

PRINCIPLES

React resets a form after its action, and the reset sends each box back to its default value. Five practical principles follow from that:

  1. Principle 1: A Successful Action Empties the Form: When the function passed to <form action={...}> finishes without throwing, React resets every uncontrolled box of that form. No line of our code does it.
  2. Principle 2: A Returned Error Still Empties the Form: An action that returns an error message has succeeded for React. React shows the error line and empties the boxes at the same time.
  3. Principle 3: defaultValue From State Brings the Text Back: The action returns the submitted text in its state, and each box reads it through defaultValue. The reset still runs, and it puts that text back.
  4. Principle 4: requestFormReset Asks for the Reset by Hand: React never resets a form submitted through onSubmit. Calling requestFormReset(form) inside the Transition gives the same reset, at the same moment.
  5. Principle 5: name and a Submit Button Keep the Form Working Without JavaScript: A form works before its JavaScript loads only when it is real HTML and its action is one the browser can send by itself.

Here is the complete map of those five principles before we walk through each one:

The word uncontrolled matters. A box with value and onChange shows what its state holds, and the reset does not change state, so that box keeps john after Save (as seen in Lesson 41).

A form with a function in action does not reload the page. React calls the function with the form data, and when the function returns, React resets the form: every uncontrolled box goes back to its default value. A controlled box is not reset, because it shows what its state holds.

Throwing the error does not save the text

A developer who finds this bug may try to stop the reset by throwing the error instead of returning it:

It looks the same, but it is NOT the same thing! Both lines stop signUp with the same message. But only a returned value becomes state:

  • With return error, React stores the message as the new state, shows the line, and resets the form.
  • With throw new Error(error), the message never becomes state. React passes the error to the nearest Error Boundary (Lesson 72). Our page has none, so the whole form disappears from the screen (as seen in Lesson 42). The user loses the boxes and the line together.

So returning the message stays right. The text has to come back another way, and Principle 3 shows it.

Principle 2

A Returned Error Is a Success: React Resets the Form After Any Action That Does Not Throw

An action that returns an error message has succeeded for React, so React empties the boxes while the error line appears.

React does not read the message an action returns. It only knows whether the action threw. A known error, such as a taken username, is returned as state, as React's docs recommend. So React resets the form, and the user loses every box at the moment the refusal appears. Throwing the error instead does not save the text: it hands the whole form to the nearest Error Boundary.

PRINCIPLE3defaultValue From State Brings the Text Back

The reset goes back to the default value

React gives no way to switch the reset off for a form with a function in action. But the reset does not have to empty the boxes. It sends each box back to its default value, and our code decides what that is. The browser keeps a default value for every box, and React's defaultValue prop sets it (as seen in Lesson 20):

A box with no default value vs. a box whose default value comes from state
1<input name="email" />
The reset empties the box
2<input name="email" defaultValue={state.email} />
The reset puts back whatever state.email holds

It is the exact same reset in both boxes. Only the default value differs. So the fix has two parts:

  1. The action returns the text the user typed, together with the message.
  2. Each box reads that text through defaultValue.

Then the reset itself puts the user's text back.

The state becomes one object

The state now holds three things, so it becomes one object. On a refusal, signUp returns the message and the two texts it read from the form. On a success, it returns empty texts, because after a success the user wants an empty form:

PRINCIPLE4requestFormReset Asks for the Reset by Hand

form.reset() vs. requestFormReset(form)

The browser's own way to reset a form is the reset() method of the form element (as seen in Lesson 41). React DOM adds a function with the same job, requestFormReset:

The browser's reset vs. React DOM's reset
1import { requestFormReset } from 'react-dom';
2
3form.reset();
The browser empties the boxes right now
4requestFormReset(form);
React empties the boxes when the current Transition ends

It looks the same, but it is NOT the same thing! Both put every box back to its default value. They differ in when the boxes change:

  • With form.reset(), the browser resets the boxes at once, even while the action is still waiting for the server.
  • With requestFormReset(form), React waits for the Transition the call was made in. So the boxes change in the same update as the new state.

This is the reset React already does for us after a function in <form action>. We ask for it by hand only when the form is submitted another way.

React never resets a form submitted through onSubmit

Some forms do not pass the action to <form action>. A team moving an older form to Actions often keeps its onSubmit handler (as seen in Lessons 11 and 41) and calls the dispatcher formAction from it. React's docs say this dispatcher must be called inside a Transition, so the handler wraps the call in startTransition from 'react' (Lesson 67):

The handler only asks by hand for the reset that <form action> gets from React.

form.reset() empties the boxes too early

form.reset() is the method developers already know, so it is tempting to call it in the handler, right after starting the action. But the browser runs it at once. The boxes empty the moment the user clicks, a full second before the server answers. If the answer is Username john is taken., the user has already watched the form clear as if the account was created. One second later, the refusal appears, and the boxes fill again with the default values from the new state.

React's docs do call reset() at once in one example: the chat in the docs of <form>, which shows each new message at once with useOptimistic. There, the user always wants the box empty right after sending, whatever the server answers. A sign-up form is the opposite case: the user wants the text kept until the server says yes.

PRINCIPLE5name and a Submit Button Keep the Form Working Without JavaScript

A user who clicks before the JavaScript has loaded

Picture the same Create account form on a phone with a slow connection. The page has appeared, but the JavaScript of the app is still downloading. React's docs call this file the JavaScript bundle. The user clicks Create account.

Whether that click sends anything depends on what the action of the form holds. Compare two forms that look the same on the screen:

An action with a URL vs. an action with a function
1<form action="/signup" method="post">
The browser sends the form to /signup by itself
2<form action={formAction}>
Only React can call formAction, so React must be running

They look the same, but they are NOT the same thing! The browser understands a URL without any JavaScript. It reads every box that has a name, and sends the values to /signup with the POST method. A function exists only inside our JavaScript. Until React runs, nobody can call it.

Progressive enhancement

A page that still works at this moment is built with progressive enhancement. The words say what it does: the page starts from a basic version that works, and enhances it, step by step, when the browser can run more. MDN describes it as giving a baseline of essential content and functionality to as many users as possible, then adding the richer version for browsers that can run it.

Here is an everyday image for it: a building with stairs and an elevator. The stairs take everyone to the top floor. The elevator is faster and nicer, and while it is not running yet, the stairs still work. For a form, the stairs are plain HTML that the browser can send by itself. The elevator is React's version: the error line without a reload, the reset, and the rest of what our JavaScript adds.

A form needs four parts so the browser can send it alone:

  1. A real <form> element.
  2. A name on every box. The browser sends only boxes that have a name, and the name becomes the key in the form data.
  3. A real submit button, a <button type="submit">. A click on it submits the form with no handler at all.
  4. An action the browser can send without JavaScript: a URL, or a Server Function in a framework that renders the page on the server.

Our form already has the first three parts, and they cost nothing extra. The name that formData.get('username') reads is the same name the browser would send (as seen in Lesson 40).

What our Vite app shows before its JavaScript runs

Our Vite app shows the user nothing at all before its JavaScript runs. It is not a broken form. It is an empty page. Here is why, in order:

  1. The browser receives index.html, which holds only <div id="root"></div> (as seen in Lesson 07).
  2. main.jsx has not run yet, so React has not rendered App.
  3. There is no form on the page to click.

The mistake that breaks it

The classic mistake is building the button or the boxes in a way only JavaScript understands:

  1. A developer builds the Create account button as a <div onClick={...}>, because a click handler does the job.
  2. Another box has no name, because the React code reads its value from state.
  3. Everything works while the JavaScript runs.
  4. Later, the team renders the page on the server, so it appears fast on slow phones.
  5. A user clicks before the bundle loads. A <div> is not a submit button, so the browser sends nothing. And a box without a name is never part of the form data.
Principle 5

Progressive Enhancement: name and a Submit Button Keep the Form Working Without JavaScript

A form works before its JavaScript loads only when it is a real <form> with a name on every box and a real submit button, and its action is one the browser can send by itself.

Progressive enhancement gives every user a basic version that works, and adds React's richer version when the JavaScript runs. The browser can send a form alone only from HTML: the <form>, the named boxes, the submit button, and a URL or a Server Function in action. A function from our own code needs React running, and a click on a <div> needs a handler that has not loaded yet.

Interview PrepFor the Interview

The Interview Question: How do React 19 form actions manage automatic form resets, manual requestFormReset, and progressive enhancement?

How to Answer Clearly in 30 Seconds

"When a function is passed to <form action>, React calls it with the form data, and after it succeeds, React resets every uncontrolled field of the form. Succeeds means it did not throw, so a returned validation error also clears the boxes. Three points follow:

  1. Keeping the text after a refusal: the reset puts each field back to its default value. So the action returns the submitted values in the useActionState state, and each field reads them through defaultValue.
  2. requestFormReset: when a form is submitted without the action prop, for example through onSubmit, we call requestFormReset(form) from react-dom inside a Transition. It gives the same reset, when the action ends.
  3. Progressive enhancement: a basic version that works for everyone, made richer when JavaScript runs. A form needs a real <form>, a name on every field, a real submit button, and an action the browser can send without JavaScript, such as a URL or a Server Function in a server-rendered page."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Our sign-up form clears the email after the server says the username is taken. Why, and how do you fix it?"
    React resets a form after every action that does not throw, and a returned error message is a normal return value. The reset sends each box back to its default value. So the action returns the submitted values together with the message, and each box gets defaultValue from that state. After a refusal, the reset puts the text back. After a success, the action returns empty values, and the same reset empties the form. Writing value instead freezes the box.
  2. "What is the difference between form.reset() and requestFormReset(form)?"
    Both put every box back to its default value. form.reset() is the browser's method and runs at once, so the boxes empty before the server has answered. requestFormReset comes from React DOM and is called inside a Transition, so the reset happens when the action ends, together with the new state. React does this same reset for us after a function in <form action>, so we call it by hand only for a form submitted another way.
  3. "Does a form with a function in action work before JavaScript loads?"
    Not by itself. A function from our own code exists only after React runs, and a Vite app that renders only in the browser has no form on the page at all before main.jsx runs. The browser sends a form with a URL in action by itself. In a framework that renders the page on the server, a Server Function in action makes the form progressively enhanced: the user can submit it before the bundle loads, and useActionState can replay that submit once React takes over.
