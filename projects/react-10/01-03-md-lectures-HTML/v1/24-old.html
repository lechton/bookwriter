How Two Sibling Components Share One Changing Value

Interview Question · ❱ CORE

How do two sibling components share one changing value?

How Two Parts of a Page Show the Same Name

A clock in every room vs. one clock in the hall

How do two parts of a page show the same changing value? Think of a house with a clock in every room. On Monday morning, someone sets all the clocks to the same time. By Friday, the kitchen clock is two minutes fast, the bedroom clock is three minutes slow, and nobody knows which one is right. Now think of a house with one clock on the wall of the hall. Everyone reads that one clock, so two people in the house never disagree about the time.

A page can have the same problem. On a name badge maker, the user types a first name into a box, and a badge below the box shows that name. The box and the badge are two separate components, and the same parent component places both of them. That makes them siblings. In a family, a brother and a sister are siblings because they have the same parents. React's docs use the same word for components that have the same parent.

There are two ways to give both siblings the name. They share one thing: in both, the name lives in state, created by useState. The one difference is where the useState line sits:

  • A useState line inside each sibling, like a clock in every room. Each sibling keeps its own copy of the name.
  • One useState line in the parent above both siblings, like one clock in the hall. The parent keeps the name, and both siblings read it.

The two ways may look the same, or work the same at first, but they are NOT the same thing! With a useState line inside each sibling, the page looks right when it opens: both copies of the name are empty, so the box and the badge agree. Then the user types the first letter, and only the copy inside the box changes. From then on, the two copies disagree, like two clocks that were set to the same time on Monday.

So here is the key idea of this lesson: a sibling cannot reach into another sibling. A value that two siblings need lives in the closest component above both of them. That parent passes the value down to both siblings as a prop, and it passes a function down to the sibling that changes the value.

What is at stake

What is at stake is a page whose parts disagree. The user types John into the box, and the large badge below it stays blank, or it keeps showing a name from before.

Readers usually go wrong in one of two places. Some look for a way to send the name sideways, from the box straight to the badge, through a global variable on window or by asking the browser for the text in the box. Others give the badge its own copy of the state and try to keep the two copies equal. Neither works. The name has to live above both siblings.

Four ways to share one changing value

When two components need the same changing value, developers choose among four ways:

  1. Move the state up into the closest common parent, the first component above both siblings, and pass the value and a callback prop down. React's docs call this lifting state up. It is the usual way, and the way this lesson teaches.
  2. Put the state in a component above the closest common parent, or in a new component written only to hold it, when the closest common parent is not a sensible owner. React's docs give both options on their Thinking in React page.
  3. Put the value in context, when the common parent is far above the components that need it and every layer between them would pass along a prop it never uses. Lessons 28 and 29 teach context.
  4. Keep a copy in each sibling and copy one into the other with an Effect. This is not a good way, and it is named here only so you recognize it. React's docs say: "Whenever you try to keep two different state variables synchronized, try lifting state up instead!" Lesson 34 shows why.

Four Principles of Lifting State Up

PRINCIPLES

Two siblings cannot read each other's state, but they can both read a value from their parent. Four practical principles follow from that:

  1. Principle 1: BadgePreview Cannot See NameBox's firstName: State is private to the component that declares it. A second useState in the other sibling makes a second, separate state, and the two stop matching after the user's first keystroke.
  2. Principle 2: firstName Moves Up to App: Remove the state from the child, find the closest common parent of every component that shows the value, and let that parent pass the value down to each of them as a prop.
  3. Principle 3: onFirstNameChange Lets NameBox Change App's firstName: The parent declares the state and passes a function down to the sibling that changes it. One keystroke by the user renders the parent again, and both siblings get the same new name in the same render.
  4. Principle 4: Start Over Clears NameBox from App: A component driven by props is controlled by its parent, so the parent can clear it from anywhere. Copying the prop into the child's own state breaks that.

Section 2 · Principle 2firstName Moves Up to App

State inside the child vs. a value written on the child's tag

The fix starts by moving one line. React's docs do it in three steps, and the first two need no state at all:

  1. Remove the state from the child components.
  2. Pass hardcoded data from the common parent. Hardcoded means written straight into the code as a fixed value, such as count={3}.
  3. Add state to the common parent, and pass it down together with the event handlers. Principle 3 does this step.

Here are the first two steps on the smallest page. Counter and Display lose their useState lines and read count from their props. Parent writes the same number on both tags:

Why React's docs call it lifting state up

This move has a name in React's docs: lifting state up. In the UI tree, a parent sits above its children. So when the state leaves a child and goes into the parent, it moves up the tree, the way the clock left one bedroom and went up on the wall of the hall, where every room can see it. React's docs say: "This is known as lifting state up, and it's one of the most common things you will do writing React code."

The state goes into the closest common parent: the first component above every component that needs the value. React's docs find it in three steps on their Thinking in React page:

  1. Find every component that renders something based on the value.
  2. Find their closest common parent, the first component above all of them in the tree.
  3. Put the state there, or in a component above it.

On our page, two components render something based on the name: NameBox shows it in the box, and BadgePreview shows it on the badge. The first component above both is App, so the name goes into App:

One owner for each piece of state

App is now the one clock in the hall. React's docs call this a single source of truth: for each piece of state, one specific component holds it. It does not mean that all the state of a page lives in one component. In the docs' words: "for each piece of state, there is a specific component that holds that piece of information." On our page, App holds firstName, and both siblings read it from their props.

A lifted name with no function passed down

One mistake is left, and React's docs warn about it on their Thinking in React page. A developer lifts firstName into App and passes it down to both siblings, but forgets to pass a function down to the box. The box has only value={firstName}. The page behaves as in Principle 2: React ignores the user's typing, and the Console shows the read-only field error. App owns the state, so only App can call setFirstName. The docs give the fix: to let a child update the parent's state, the parent passes its functions down to that child.

Principle 3

Callback Prop: The Parent Passes a Function Down to the Sibling That Changes the Value

Declare the state in the common parent, pass the value down to every sibling that shows it, and pass a function down to the sibling that changes it.

The box never sends the name to the badge. When the user types, the box calls the function it received, App changes its own firstName, and React renders App again with both siblings. Both read the same new name in the same render, so they can never disagree. Without the function, the box is frozen, because only the owner of the state can call its setter.

For the Interview

The Interview Question: How do two sibling components share one changing value?

How to Answer Clearly in 30 Seconds

"Two siblings cannot read each other's state, because state is private to the component that declares it, and each sibling sees only the props written on its own tag. So we lift the state up: we remove it from the children, find their closest common parent, and declare the state there. The parent passes the value down as a prop to every sibling that shows it, and passes a callback prop, such as onFirstNameChange={setFirstName}, to the sibling that changes it. Three details matter:

  1. One change, one render: the child calls the parent's function, the parent sets its state, and React renders the parent and both siblings again, so both get the identical value in the same render.
  2. Single source of truth: each piece of state has one owner. A second useState in the other sibling is a second copy that stops matching after the first change.
  3. Controlled components: a child driven by props is controlled by its parent, so the parent can reset it. The child uses the prop directly and does not copy it into its own state."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why not keep a copy of the value in each sibling and keep the copies equal with an Effect?"
    Because the copies disagree first and agree later. With an Effect, the first sibling changes its state, and React renders. Only after that render does the Effect set the second copy, which costs a second render. Between the two renders, the screen can show two different values. React's docs say: "Whenever you try to keep two different state variables synchronized, try lifting state up instead!" When the parent changes its state during the event, the docs note that there is only one render pass. Effects come in Lessons 32 and 34.
  2. "Does the state keep its shape when you lift it?"
    Not always. React's docs show an Accordion with two Panel components, where only one panel may be open at a time. When each Panel keeps its own isActive boolean, pressing Show on one panel does not close the other, so both can be open. Lifting the state into Accordion replaces two booleans with one number, activeIndex, which says which panel is open. Each Panel receives isActive as a prop and an onShow function. In the docs' words: "Lifting state up often changes the nature of what you're storing as state."
  3. "Does a single source of truth mean all the state lives at the top of the app?"
    No. Each piece of state lives in the closest common parent of the components that need it, and no higher. The docs say: "It doesn't mean that all state lives in one place." It is also normal to move state down or back up while you work out where each piece belongs. When the closest common parent sits far above, and every layer between passes a prop it never uses, the docs call it prop drilling, and context is the next tool, as Lesson 28 shows. And two components that call the same custom hook do not share state, because each call gets its own, as Lesson 39 shows.
