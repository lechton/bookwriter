What a JavaScript object looks like

To see what JSX turns into, we need one small building block from plain JavaScript: an object.

A JavaScript object keeps several values together, each under a name. Each name with its value is called a property. We write an object with curly braces, and we read a property with a dot:

Plain JavaScript
1const article = {
2 title: 'Library Hours',
A property named title
3 topic: 'City',
4};
5
6console.log(article.title);
Prints "Library Hours" in the Console

The article object holds two properties for the title and the topic. Reading article.title gives 'Library Hours'. A property name is a JavaScript name, and an object can also hold other objects inside its properties.

How Vite rewrites JSX before the browser runs it

The browser does not read App.jsx as we wrote it. When the page asks for the file, our dev server, Vite, reads it, rewrites every JSX tag into plain JavaScript, and sends the result to the browser. This rewriting step is called the build. When the site is ready to publish, npm run build does the same rewrite for every file at once.

When a mistake in our JSX stops the build from reading a file, nothing in that file runs. Vite covers the page with a dark box called the error overlay. It shows what went wrong and which line stopped the build, and it goes away as soon as we fix the file and save.

Along with the page itself, we use two panels in Chrome's developer tools throughout this lesson:

  • The Elements panel shows the live DOM, the tree of real page elements that React built.
  • The Console panel shows values printed with console.log and any red runtime error messages from React.

Five Principles of JSX Syntax

PRINCIPLES

Everything in this lecture comes down to one idea: JSX looks like HTML, but it is JavaScript. Five rules govern every JSX snippet we write:

  1. Principle 1: The JSX Transform: The build rewrites each JSX tag into a React function call that returns a plain object called a React element, and React builds the DOM from those objects.
  2. Principle 2: Closed Tags: Because the build must know where each tag's content ends, every tag needs a closing tag or a trailing slash, even single tags that hold no content inside.
  3. Principle 3: Single Root: Each tag becomes one call, and a JavaScript return gives back one value, so every component returns one outer root element that holds the rest.
  4. Principle 4: Fragments: When sibling tags need one root for return, group them with an empty Fragment wrapper so no extra box is added to the page.
  5. Principle 5: camelCase Attributes: Tag attributes become properties on a JavaScript object, so reserved words and multi-word attribute names use their JavaScript property names.

How the build turns every tag into a function call

Where did that object come from? We wrote HTML-looking angle-bracket tags, not curly braces!

Before the browser received App.jsx, the build rewrote every tag into a JavaScript function call. In the rewritten file that the browser receives, every angle-bracket tag is gone. In its place is a call to a helper function from React named _jsxDEV:

App.jsx after the build, shortened
1const card = _jsxDEV("article", {
<article> became a function call
2 children: [
3 _jsxDEV("h2", { children: "Library Hours" }),
4 _jsxDEV("p", { children: "The library stays open until nine." }),
5 ],
6});

Look at how simple that rewrite is:

  • The tag's name became the first argument, such as "article" or "h2".
  • The tag's attributes and inner content became the properties of an object in the second argument.

This rewrite by the build is called the JSX transform. Each call returns the plain object we saw in the Console, and React calls that object a React element. When React renders the component, it reads those React elements and builds the real browser DOM from them.

The build also adds the import line for _jsxDEV at the top of the file automatically. Older versions of React rewrote tags into React.createElement, which required importing React at the top of every file. Because React 19 uses the automatic JSX transform, you never need to import React just to write JSX.

Principle 1

The JSX Transform: Each Tag Becomes a Call That Returns an Object

Read JSX as JavaScript: the build rewrites every tag into a function call that returns a plain React element object, and React builds the DOM from those objects.

The browser never reads raw JSX tags. Before the browser receives your file, the build turns every tag into a call to a function from React. That call returns a plain object called a React element, holding type and props. Because a JSX tag evaluates to a normal JavaScript object, you can return it from a function or store it in a variable.

Section 2 · Principle 2Closed Tags: Close Every Tag Including <img /> and <br />

Two shapes of HTML tags, and why JSX requires both shapes to close

In HTML, tags come in two shapes:

  • Shape 1: Tags that wrap content with an opening and closing pair, such as <h2>Library Hours</h2> or <p>Open until nine.</p>.
  • Shape 2: Single tags that stand alone and can never hold anything inside them, such as an image <img> or a line break <br>. HTML calls these void elements, and plain HTML lets you write them without a closing tag or a slash:
Plain HTML: Shape 2 void elements left open
1<img src="/library.jpg" alt="The city library">
2<br>
3<input type="text">

In JSX, however, every tag becomes a JavaScript function call, so the build must see an explicit end for every tag. Shape 1 closes with its matching closing tag. Shape 2 must close itself with a slash before the closing bracket, such as <img /> or <input />.

Now we want our article card to show the library photo above the heading. A developer copies the <img> line from the old HTML site and pastes it into ArticleCard as it is, with no closing slash:

App.jsx

4 <img src="/library.jpg" alt="The city library">
WRONG no closing slash on img!

6 <p>The library stays open until nine.</p>
7 </article>
8 );
9}

When the developer saves, the build stops at the image tag, and nothing in the file runs. Vite covers the page with its error overlay. Look at the two lines the overlay points to. It marks <img> on line 4 as opened here, and </article> on line 7 as where it expected the closing image tag:

Why an open <img> tag makes the build complain at </article>

Why did a mistake on line 4 point to </article> down on line 7?

Each tag becomes a call, and the build must know where that call's children end. After an open tag, the build reads everything that follows as the content of that tag until it finds the closing tag. HTML knows that <img> is a void element that holds nothing, but JSX makes no exception for void elements.

So the build read the heading and paragraph tags as if they were children sitting inside <img>! When it reached </article> on line 7, it was still waiting for </img>, and the build stopped.

To tell the build that a tag holds nothing and ends right where it opens, put a slash / before the closing >:

App.jsx
1export default function ArticleCard() {
2 return (
3 <article>
4 <img src="/library.jpg" alt="The city library" />
Closed with a slash: ends right here
5 <h2>Library Hours</h2>
6 <p>The library stays open until nine.</p>
7 </article>
8 );
9}

Save the file, and the error overlay disappears. The photo, the heading, and the text appear on the page. Line breaks <br /> and inputs <input /> follow the same rule, and any empty tag in JSX may close itself the same way.

Why does HTML allow two tags side by side while a React component forbids them?

Remember Principle 1: each JSX tag becomes one function call, and one call produces one object. In JavaScript, a return statement can only give back one value. You cannot return two separate objects side by side from a JavaScript function:

Plain JavaScript
1function getCard() {
2 return (
3 { type: 'h2' }
4 { type: 'p' }
SyntaxError: a function cannot return two separate values!
5 );
6}

Because <h2> and <p> are two separate calls, the build cannot turn them into a single returned value.

Wrapping both tags in one outer <article> gives return one value

To give return a single value, we put one outer <article> tag around both inner tags:

App.jsx
1export default function ArticleCard() {
2 return (
3 <article>

5 <p>The library stays open until nine.</p>
6 </article>
7 );
8}

With <article> around both tags, return gives back one call for the outer tag. The two inner calls become its children, just as we saw in the Console object in Principle 1.

Save the file, and the card appears. Notice the help line at the bottom of the overlay above: it mentioned a JSX fragment <>...</>. Wrapping the heading and paragraph in <article> was right here because our card needed an <article> box on the page. What if a component returns two tags, and an extra box on the page would break the layout? Principle 4 takes up that case next.

Section 5 · Principle 5camelCase Attributes: Write Attributes as JavaScript Property Names

Why HTML attributes like class and for are renamed in JSX

JavaScript keeps certain words for its own grammar, such as class and for. They are called reserved words: class starts a class definition, and for starts a loop.

When the browser builds a DOM object in memory for an HTML element, that DOM object stores the element's attributes as JavaScript properties. Because those two HTML words are reserved in JavaScript, the DOM gives their properties JavaScript names: className and htmlFor. Other property names made of several words join them in camelCase, such as tabIndex.

What happens when you keep class, for, and tabindex from HTML

Now suppose a developer pastes a newsletter form from the old HTML site into SignUp, keeping its original HTML attribute names:

App.jsx
1export default function SignUp() {
2 return (
3 <form>

Interview PrepFor the Interview

The Interview Question: What is JSX, what syntax rules must every snippet follow, and how do Fragments group elements without wrapper nodes?

How to Answer Clearly in 30 Seconds

"JSX looks like HTML, but it is a syntax extension for JavaScript. During the build, each JSX tag is rewritten into a function call that returns a plain JavaScript object called a React element, with type and props. React reads those objects to build the browser DOM.

Every JSX syntax rule follows from the fact that tags become JavaScript calls:

  1. Close every tag: every tag must close, including void elements like <img /> and <br />, so the build knows where each call ends.
  2. Return a single root: a component must return one outer root because a JavaScript function can only return one value.
  3. Use a Fragment <>...</> when no DOM box is wanted: wrapping list items or flex children in a <div> inserts a real DOM box that breaks flex, grid, and direct-child CSS. A Fragment gives return one value and adds zero nodes to the DOM.
  4. Use JavaScript property names for attributes: attributes become properties on props, so we write className, htmlFor, and camelCase like tabIndex, while aria-* and data-* keep their dashes."

Four Follow-Up Questions Interviewers Ask

  1. "Does a Fragment <>...</> appear as an element in Chrome's Elements panel?"
    No. An extra <div> wrapper inserts a real <div> node into the DOM, which breaks display: flex, display: grid, and .parent > child CSS rules. A Fragment <>...</> compiles to one Fragment call for return and adds 0 nodes to the DOM, so its children sit directly inside the parent.
  2. "Why do class and for still work on screen in React 19, yet log an error in the Console?"
    The build accepts any attribute name as a property on props, and React 19 still sets class and for on the DOM element. However, React expects the DOM's JavaScript property names, className and htmlFor, and logs an Invalid DOM property error in the Console for each HTML name.
  3. "Why don't React 19 files need import React from 'react' at the top to use JSX?"
    Older transforms rewrote every tag into React.createElement, which needed React in scope. React 19 uses the automatic JSX transform, where the build adds its own import of React's JSX helper function automatically.
  4. "Can the short Fragment syntax <>...</> take a key attribute in a list?"
    No. The empty tag <>...</> cannot take any attributes. When a Fragment in a list needs a key, import Fragment from 'react' and write <Fragment key={item.id}>...</Fragment>.
