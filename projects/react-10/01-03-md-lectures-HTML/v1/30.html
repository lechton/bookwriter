Keeping a Value Between Renders with useRef

Interview Question · ❱ CORE

How do you keep a value between renders without triggering a re-render?

OverviewHow a Component Remembers a Number It Never Shows

The number the Stop button needs

Think of the stopwatch on your phone. You tap Start, and the seconds count up. You tap Stop, and the number stands still. Behind those two taps, the Stop tap has to find the timer that the Start tap started.

In the browser, a repeating timer starts with setInterval. You know setTimeout from Lesson 15, and setInterval takes the same two things: a function and a delay in milliseconds. They differ in one way: setTimeout calls the function once, while setInterval calls it again and again, every time the delay passes. To stop the timer, our code hands its number to clearInterval. In the smallest example, the repeated function is called tick:

Starting and stopping a repeating timer in the browser
1const id = setInterval(tick, 1000);
Calls tick every 1000 milliseconds and returns a number for this interval
2clearInterval(id);
Stops the interval with that number: tick is never called again

The browser gives back that number at the moment the interval starts. MDN calls it the interval ID. It is the only handle our code has on the interval. Without it, no code can stop the timer. And when clearInterval gets a number the browser does not know, or no number at all, it simply does nothing.

Now put the stopwatch inside a React component. The click on Start gets the interval ID. The click on Stop comes later, and in between, the component renders again once a second to show the new number. So the interval ID has to wait somewhere, through all those renders, until the user clicks Stop.

A ref keeps the number between renders

React's answer is a ref, created with the Hook useRef. Three lines do the whole job:

Keeping the interval ID in a ref
1const intervalRef = useRef(null);
1. In the component: creates the ref, an object that starts as { current: null }
2intervalRef.current = setInterval(tick, 1000);
2. In the Start handler: puts the new interval ID inside the ref
3clearInterval(intervalRef.current);
3. In the Stop handler: reads the same ID back and stops the interval

A ref is an object with one property, current. React keeps the ref for the component through every render, so the Stop handler finds the ID, however many renders came between the two clicks.

A ref and state: kept the same way, with one difference

A ref and state have one thing in common: React keeps both between renders. The docs say it plainly: "Like state, refs are retained by React between re-renders." The one difference comes in the next line of the docs: "However, setting state re-renders a component. Changing a ref does not!"

A number kept in state, and a number kept in a ref
1const [count, setCount] = useState(0);
Kept between renders: setCount(1) asks React to render again
2const countRef = useRef(0);
Kept between renders: countRef.current = 1 asks React for nothing

It may look the same, or work the same at first, but it is NOT the same thing! Both remember a number between renders, and on the first render both hold zero. But only the setter of state makes React render the component again, so only a number in state ever changes the page. The docs put both facts into one short phrase: a ref is like "a regular state variable without a setter."

Why it is called a ref

Ref is short for reference. The docs' page about it is called "Referencing Values with Refs". A ref keeps a reference to a value, so that later code, such as the Stop handler, can find the value again. The docs also give the ref an everyday image: "It's like a secret pocket of your component that React doesn't track." Our code can put a value into a ref during one click and take it out during a later click, and React never looks at it, so putting a value there never causes a render.

Four places a component can keep a value

A ref is not the only place to put a value. The useRef reference in the docs compares four places, and each one fits a different job:

Four places a component file can keep a value

2

4 let localId = null;
A local variable: created again on every render
5 const [seconds, setSeconds] = useState(0);

6 const intervalRef = useRef(null);

Here is the job each place fits:

  1. A local variable, such as localId, fits a value the component computes fresh during each render, as in Lesson 22. It does not survive a re-render, because, in the words of the docs, regular variables "reset on every render".
  2. A variable outside the component, such as outsideId at the top of the file, fits a value that never changes while the page runs, such as initialCart in Lesson 27. It survives every render, but it is one variable for the whole file, and the docs call such variables "shared".
  3. State, from useState, fits information the page shows. Changing it renders the component again.
  4. A ref, from useRef, fits information that only event handlers need, and whose change needs no new render, such as an interval ID. The docs call refs an "escape hatch" that "you won't need often."

An escape hatch is a small door in a ship or a plane, for the rare moment when the main door does not fit the job. In React, almost every value goes through state and rendering. A ref lets a value step outside that path, for things React does not draw, such as a browser timer.

What is at stake

When the interval ID sits in the wrong place, the user sees it at once:

  1. With a local variable, the user clicks Stop, and the stopwatch keeps counting.
  2. With one variable outside the component, the user runs two stopwatches, and a click on one of them stops the other.
  3. With the shown number in a ref instead of state, the user clicks Start, and the line stays at zero.

Readers usually go wrong in three ways. First, they think a local variable inside the component keeps its value between renders. Second, they think every value a component remembers must be state, so the component renders again for a number nobody sees. Third, once they learn refs, they keep a shown number in a ref because the ref changes at once, and the page stops updating.

Five Principles of Keeping a Value Between Renders

PRINCIPLES

A ref keeps a value between renders, as state does, and changing it renders nothing. Each principle below puts the interval ID in one place and shows what the user sees:

  1. Principle 1: useRef Returns the Same Object on Every Render: useRef gives the component an object with one property, current. React hands back the same object on every render, and our code changes current without a new render.
  2. Principle 2: Stop Fails When intervalId Is a let: A local variable is created again on every render, so the interval ID from the Start click is gone by the time the user clicks Stop.
  3. Principle 3: useState for the Interval ID Renders the Stopwatch Again: State also makes Stop work, but every change of the ID renders the component again for a value the page never shows.
  4. Principle 4: A Shared intervalId Stops the Wrong Stopwatch: A variable outside the component survives renders, but every stopwatch on the page uses the same one.
  5. Principle 5: secondsRef.current on the Page Stays at 0: A value the page shows must be state, because changing a ref does not render, and our code does not read a ref during rendering.

When the user clicks the button, the pop-up says "You clicked 1 times!". After the next click, it says "You clicked 2 times!", and then "You clicked 3 times!". The button itself never changes, because, as the docs say, "the component doesn't re-render with every increment."

useRef takes one argument, the initial value, and returns the ref object. The object has exactly one property, current, which starts as that initial value. The docs call current "intentionally mutable, meaning you can both read and write to it." Mutable comes from the same root as mutation, which Lesson 17 taught: changing a thing from the inside. State must never be mutated. A ref is meant for exactly that: our code changes current by plain assignment, and there is no setter.

Yes, it is the exact same thing! Writing into current is the same as writing any property of any JavaScript object:

Writing current on a ref, and writing a property on any object
1ref.current = 5;
The ref object: current now holds 5
2user.name = 'Alice';
Any JavaScript object: name now holds 'Alice'

In the words of the docs, "the ref itself is a regular JavaScript object, so it behaves like one." There is no hidden magic in current. React does only two things for us: it creates the object, and it keeps it.

The same object on every render

The useRef line runs on every render, just as a line such as let count = 0 would. So it looks as if the ref goes back to zero each time. It may look the same, but it is NOT the same thing! React uses the initial value only on the first render:

  1. On the first render, useRef creates the ref object with current set to zero, and React stores it with the component.
  2. On every later render, useRef returns that same stored object, with whatever current holds now. The zero passed to useRef is ignored.

The useRef reference says it in one line: "This argument is ignored after the initial render."

The line const ref = useRef with the initial value 0

It looks the same, but it is NOT the same thing! The setter asks React for a new render, and the new value arrives with that render. Writing current changes the object itself, right now. The docs say: "when you mutate the current value of a ref, it changes immediately".

The first line of handleStart protects the stopwatch from a second click on Start. Without that line, two clicks on Start leave an interval that nothing can stop:

  1. The user clicks Start. An interval starts, and its ID goes into intervalRef.current.
  2. The user clicks Start again. A second interval starts, and its ID replaces the first one in intervalRef.current. The first ID is now lost.
  3. Both intervals add one every second, so the line counts two seconds for every real second.
  4. The user clicks Stop. clearInterval gets the second ID and stops only the second interval. The first interval runs on, and the line keeps counting one by one.

With the first line in place, a second click on Start stops the old interval before it starts a new one. On the very first click, the ref still holds null, and clearInterval does nothing with null, so that first click is safe too. The docs' own stopwatch writes its Start handler the same way.

Principle 1

useRef: React Returns the Same Ref Object on Every Render

useRef returns an object whose current property starts as the initial value. React gives back the same object on every later render, and our code changes current freely without a new render.

A component often needs to remember a value that the page never shows, such as an interval ID. A ref keeps that value in its current property. React creates the object on the first render, ignores the initial value after that, and returns the same object every time. A change to current is there at once, and React is not told about it.

The Console stays quiet, because nothing in the code is an error. The interval ID is still in the variable that the Start click filled, but by the time the user clicks Stop, the Stop button reads a different variable. Here is what happens, in order:

  1. The user clicks Start. handleStart stores the new interval ID in this render's intervalId.
  2. One second later, the interval calls setSeconds, and React renders Stopwatch again.
  3. The new render runs the let line again. That makes a brand-new intervalId, and it holds null.
  4. The new render also makes a new handleStop, and React puts it on the Stop button. This handleStop reads the new variable, which is null.
  5. The user clicks Stop. clearInterval gets null and does nothing.
  6. The interval still runs, and the line keeps counting, to four and then five.

There is one case where the let version works. If the user clicks Stop within the first second, before the first tick, React has not rendered the stopwatch again yet, because the Start click itself sets no state. The Stop button still holds the handleStop of the same render, and it reads the same variable that handleStart filled, so the stopwatch stops. That is why a quick test can hide this bug: it shows up only after the component renders again.

The same mistake in the docs: an Undo button that cannot undo

The docs have a challenge with the same bug. A chat starts a three second setTimeout when the user clicks Send, and keeps its timeout ID, the number setTimeout returns, in a let variable. clearTimeout takes that number and cancels the timeout, the same way clearInterval stops an interval. The Send click also sets state, which renders the component again. When the user clicks Undo, clearTimeout gets the new null, so the "Sent!" message still appears after the click on Undo. The docs' fix is the fix of this principle: "store it in a ref, which React will preserve between renders."

Back to the ref

So the stopwatch keeps intervalRef from Principle 1. Every render gets the same ref object back from React, so the Stop handler of the latest render reads the same current that the Start handler filled many renders earlier.

Principle 2

Local Variables: A let Inside the Component Resets on Every Render

A let variable inside the component is created again on every render. The interval ID from the Start click is gone before the Stop click reads it, and a ref keeps it.

Every render runs the component from the top, so every let line runs again and makes a new variable. The interval renders the stopwatch once a second, so the Stop button soon holds a handleStop that reads a fresh null. clearInterval does nothing with null, and the stopwatch keeps counting with zero Console errors.

With the interval ID in state, one click on Stop prints the line twice, because <StrictMode> calls the component twice in development, as Lesson 14 showed. The page shows the same number as before, yet React did all the work of a render for a value nobody sees. The same happens on every click on Start, when the setter stores the new ID. There is a second trap in the state version. A developer who logs intervalId right after calling setIntervalId sees null, and thinks the ID was lost. It was not lost: the log read this render's snapshot, as Principle 1 showed, and the ID arrives with the next render.

The docs' rule for choosing

The docs give one test for choosing between state and a ref: "When a piece of information is used for rendering, keep it in state. When a piece of information is only needed by event handlers and changing it doesn't require a re-render, using a ref may be more efficient."

A value is used for rendering when it appears in the JSX the component returns, or when the component needs it to compute that JSX. Our stopwatch holds one value of each kind:

  • seconds appears in the paragraph the component returns, so it is used for rendering, and it stays in state.
  • The interval ID appears nowhere in the JSX. Only handleStart and handleStop read it, so it goes in a ref. About their own stopwatch, the docs say: "Since the interval ID is not used for rendering, you can keep it in a ref".

State and a ref in the same component are both right, each for its own value. The docs say: "You can combine refs and state in a single component."

Principle 3

State or Ref: Keep in State Only What the Page Shows

A value the page never shows does not belong in state. Storing the interval ID with a setter works, but every change renders the component again for nothing.

The setter of state always asks React for a new render. For seconds, that is the point, because the page must show the new number. For the interval ID, the render changes nothing on the page. Keep information used for rendering in state, and keep information that only event handlers need in a ref.

Principle 4

One Ref per Copy: A Variable Outside the Component Is Shared

A variable outside the component survives every render, but every copy of the component shares it. A ref belongs to one copy, so each stopwatch keeps its own interval ID.

Moving a let variable above the component fixes the reset of Principle 2, and with one stopwatch the page looks fine. As soon as the component appears twice, both copies write the same variable, and a click on one stopwatch stops the other. A ref, like state, belongs to the copy that created it.

Do not read or write current during rendering

The useRef reference turns this into a rule: "Do not write or read ref.current during rendering, except for initialization."

During rendering means while React calls the component function: the lines in its body and the JSX it returns. An event handler, such as handleStart, is defined during rendering, but its code runs later, when the user clicks. So reading secondsRef.current in the JSX happens during rendering, while writing intervalRef.current inside handleStart does not.

React cares because of purity. Lesson 14 showed that React expects a component to be pure: the same props and state give the same JSX. A ref can change without React knowing, so JSX that reads a ref can show a different result for the same props and state. The docs say: "You can read or write refs from event handlers or effects instead." Effects come in Lesson 32.

There is one exception, which the docs call initialization: filling an empty ref once, on the first render. It helps when the ref holds an object that is costly to create, such as a video player. Compare passing the new object straight to useRef with filling the ref only while it is empty:

Passing a new player straight to useRef
1const playerRef = useRef(new VideoPlayer());
Creates a new player on every render, and React ignores all but the first
Filling an empty ref once, during the first render
1const playerRef = useRef(null);
2if (playerRef.current === null) {
True only on the first render
3 playerRef.current = new VideoPlayer();
Runs once; every later render skips it

Both give the component the right player. But the first line creates a new player on every render, and every player after the first is thrown away, because React ignores the initial value after the first render. The check for null creates the player only once. Writing current during rendering is fine here, as the docs say, "because the result is always the same, and the condition only executes during initialization". It is the same idea as the initializer function of useState in Lesson 12.

Principle 5

Rendering: A Shown Value Belongs in State, Not in a Ref

A value the page shows must be state, because changing a ref does not render. Our code does not read or write ref.current during rendering, except to fill an empty ref once.

The page shows what the last render read. A ref changes without a render, so JSX that reads current keeps showing the old number until something else renders the component, and then the number jumps. When a value is needed to compute the JSX, that value belongs in state. Read and write refs in event handlers.

Interview PrepFor the Interview

The Interview Question: How do you keep a value between renders without triggering a re-render?

How to Answer Clearly in 30 Seconds

"I use a ref. useRef returns a plain object with one property, current, which starts as the initial value. React creates it on the first render and returns the same object on every later render, so the value survives re-renders like state does. But changing ref.current does not re-render the component, and the change is there at once. A stopwatch is the classic case: the interval ID from setInterval goes in a ref, so the Stop handler can pass it to clearInterval many renders later. Three rules keep it right:

  1. A local let variable resets on every render, and a variable outside the component is shared by every copy, so neither can hold the interval ID.
  2. Information used for rendering goes in state, and information only event handlers need, such as an interval ID or a timeout ID, goes in a ref.
  3. Never read or write ref.current during rendering, except to fill an empty ref once. A value shown on the page and kept in a ref does not update when the ref changes."

Three Classic Follow-Up Questions Interviewers Ask

  1. "How is useRef different from useState, and could you build it with useState?"
    Both keep a value between renders, and both belong to one copy of the component. The setter of state asks React to render again, and the new value arrives with the next render. A ref has no setter: our code changes current directly, at once, and React is not told. The docs show that useRef could be built on top of useState: a state variable holds the object with current forever, and nobody ever calls its setter. That is why the docs call a ref "a regular state variable without a setter". The docs also compare refs to instance fields in class components, such as this.something.
  2. "Why should you not read ref.current during rendering, and when is it allowed?"
    React expects a component to be pure: the same props and state give the same JSX. A ref can change without a render, so JSX that reads it shows an old value, and then jumps when something else renders the component. A warning in the useRef reference says that when you break this rule, "your component might still work", but newer React features rely on it. The refs lint rule flags three things: reading a ref during render, updating a ref during render, and keeping in a ref a value that should be state. The React Compiler also reports an error on a line that reads a ref during render. The one allowed case is initialization: a check that playerRef.current is still null, which fills the empty ref once, on the first render.
  3. "When would you reach for a ref at all?"
    The docs call refs an "escape hatch" that "you won't need often", for values outside React's rendering. Their list: storing timeout IDs, storing and manipulating DOM elements, and storing other objects that are not needed to calculate the JSX. An interval ID or a timeout ID is the case from this lesson. The docs name the most common use: accessing a DOM element through the ref attribute, which the next lesson covers. A ref can hold any value: "a string, an object, or even a function". In Strict Mode, React calls the component twice in development. Both calls get back the same ref object, but an initial value such as a new video player is built twice.
