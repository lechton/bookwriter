Choosing Between Controlled State and Uncontrolled FormData

Interview Question · ❱ CORE

Should a form use controlled state or uncontrolled FormData, and how do you choose?

This screen raises one question for the developer: does every box need a state variable? No. Only the box whose text the page must show or check while the user types needs state. Every other box can keep its text in the browser, and our code reads that text once, when the user clicks Sign up.

So a box in a form can be written in two ways:

Two ways to write a box in a form
1<input name="email" />
The browser keeps the text until the user clicks Sign up
2<input value={password} onChange={e => setPassword(e.target.value)} />
State keeps the text
  1. The box with name has no value, so it is an uncontrolled box (as seen in Lesson 20). The browser keeps what the user types. The name is the label our code uses to find that text later. When the user clicks Sign up, our code asks the browser for the text of every box that has a name, through a browser object called FormData. Principle 1 shows how.
  2. The box with value and onChange is a controlled box (as seen in Lesson 20). State keeps the text. After every keystroke by the user, onChange saves the new text into state.

The two lines look different in the code. On the screen, though, the two boxes behave the same: both show each letter the moment the user types it. So a developer easily believes they do the same work. It may look the same, or work the same at first, but it is NOT the same thing! After every keystroke by the user, the box with value and onChange changes state, and React calls the component function again. The box with name changes no state, so React calls nothing.

What is at stake

The key idea to remember: choose for each box. Keep a box in state only when the page must change while the user types. Otherwise, let the browser keep the text, and read it when the user submits the form.

What is at stake is how fast the page answers the user's typing. Picture an admin form with forty boxes, where every box has its own state. The user types one letter in any box, and React renders the whole form again, with all forty boxes. React's docs warn that when the component holding the state renders a large tree on every keystroke, "this can get slow". On a low-end laptop or phone, the letters appear late while the user types.

Readers usually go wrong right after Lesson 20. They have just learned controlled boxes, so they put every box in state by habit, even the boxes the page reads only when the user clicks Sign up.

Four Principles of Choosing Between Controlled State and FormData

PRINCIPLES

A box that the page reads only at submit can keep its text in the browser. A box whose text the page must follow while the user types goes into state. Four practical rules follow from that choice:

  1. Principle 1: name Puts the Email into FormData: When the user clicks Sign up, new FormData(e.currentTarget) collects the text of every box that has a name. Our code reads the email with formData.get('email'), and no state is needed.
  2. Principle 2: Typing in the Email Box Skips the Render: While the user types into the box with name, React renders nothing. While the user types into a box with value and onChange, React renders the whole component after every keystroke.
  3. Principle 3: The Password Hint Follows State: When the page must change while the user types, as the hint under the password does, that box goes into state. At submit, our code reads the email from FormData and the password from state.
  4. Principle 4: State in SignupForm Keeps SiteHeader Still: Every keystroke renders the component that holds the state, and every component inside it. When the state lives in SignupForm, the header does not render while the user types.

Here is the complete map of those four principles before we walk through each one:

Reading a box at submit without state

A box does not need state for our code to read it. The browser already keeps the text of every box. When the user submits a form, the browser can hand our code all of that text at once.

Three new words appear in this code. None of them comes from React. All three come from the browser:

  1. name is an HTML attribute of the box. React passes it on to the box in the DOM. React's docs say that the name you write "will be used as a key in the form data".
  2. FormData is a browser object that holds the data of a form: one entry for each box that has a name, with the text inside that box. new FormData(e.currentTarget) builds that object from our form, at the moment the user submits it.
  3. formData.get('email') is a method of that object. It returns the text stored under the name email.

The string 'email' inside formData.get('email') is the same string as name="email" on the box. Nothing else links the two.

e.target vs. e.currentTarget inside onSubmit

React's docs write new FormData(e.target), and our code writes new FormData(e.currentTarget). In a submit handler on the form, yes, it is the exact same thing! The submit event happens on the <form> itself, and the handler sits on that same <form>. So e.target, the node where the event happened, and e.currentTarget, the node whose handler runs, are both the form (as seen in Lesson 11).

Principle 1

name Puts the Email into FormData: Read Each Box by Its Name at Submit

Give every box that the form reads at submit a name, build the form data with new FormData(e.currentTarget), and read each box with formData.get and that same name.

You do not need state to read what the user typed. The browser already keeps the text of every box. When the user submits, FormData collects the text of every box that has a name, and the name is the key you ask for. A box without name is left out, so your code gets null, and the page shows no error.

The cost is the render, not the box

One render per keystroke is fine for a small form. Our form has two boxes, and React renders it in no time. The cost grows with how much React has to render after each keystroke.

Beware! When every box of a large form sits in state, every keystroke in any box renders the whole form. Here is how a developer runs into it:

  1. After learning controlled boxes, the developer gives every box of a forty-box admin form its own useState.
  2. The user types one letter in any box.
  3. React renders the whole form again, with all forty boxes.
  4. On a low-end laptop or phone, the letters appear late while the user types.

Most of those forty boxes are read only when the user clicks Save. They never needed state. As boxes with name, read at submit with FormData, they would cost no render at all while the user types.

So the Email box of our Sign up form stays the box with name, because the page reads the email only when the user clicks Sign up:

Principle 2

Typing in the Email Box Skips the Render: Keep a Box Uncontrolled When the Page Reads It Only at Submit

A box with value and onChange makes React render the component after every keystroke; a box with name makes React render nothing while the user types.

Both boxes show what the user types, so they seem to cost the same. They do not. A controlled box sets state after every keystroke, and every state change renders the component that holds it. When the page needs the text only at submit, that work buys nothing, and in a large form the user feels it as letters that appear late.

It may look the same, or work the same at first, but it is NOT the same thing! Both boxes show one dot for each letter. But with the box with name, the page now gives the wrong hint, for two reasons:

  1. There is no value to check. The text sits in the browser, so the component has no password to measure with .length.
  2. There is no render while the user types. Even with a value, nothing would make React call the component again to pick a new hint.

The box with value and onChange has both. Every keystroke by the user saves the text into password, and React renders the component again with the new password.

React's docs give the reason to choose a controlled box: you need state anyway, for example to render the page again on every edit. Here are the cases developers really meet:

  1. The page shows or checks the value on every edit, such as a password hint, a live character limit, or autocomplete suggestions under the box.
  2. Something other than typing also changes the value, such as a button that fills or clears the box.
  3. A button stays off until the form is valid, such as a Sign up button with disabled (as seen in Lesson 21).

Principle 3

The Password Hint Follows State: Control a Box When the Page Changes on Every Edit

Put a box in state with value and onChange when the page must change while the user types, and read that box from state at submit.

Principle 4

State in SignupForm Keeps SiteHeader Still: Keep the State of a Box in the Component That Holds the Form

Write the useState of a controlled box in the component that holds the form, not in App, so each keystroke renders only the form.

A state change renders the component that holds the state and every component inside it. The state of a box at the top of the page renders the whole page after every keystroke, header included. The same state inside the form component gives the same form, and React renders only the form.

For the Interview

The Interview Question: Should a form use controlled state or uncontrolled FormData, and how do you choose?

How to Answer Clearly in 30 Seconds

"I choose for each box, not for the whole form. A controlled box, with value and onChange, keeps its text in state, so React renders the component after every keystroke. An uncontrolled box keeps its text in the browser, and I read it once at submit with new FormData(e.currentTarget) and formData.get, using the box's name as the key. So:

  1. Uncontrolled with FormData when the page reads the box only at submit: no render while the user types, and less code.
  2. Controlled when the page must change on every edit, such as a password hint, a character limit, autocomplete, or a button disabled until the form is valid, or when something other than typing changes the value.
  3. Mixed in one form: I read the controlled boxes from state and the others from FormData, and I keep the state of each box in the component that holds the form, so each keystroke renders only that component."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Your FormData code returns null for a field. What happened?"
    The box has no name, or its name differs from the string passed to formData.get. FormData keys each entry by the box's name, so a box without one is left out, and formData.get returns null for a name it does not hold. Nothing on the page shows an error. To turn the whole form data into a plain object, React's docs use Object.fromEntries(formData.entries()), and the same formData can be sent with fetch as the request body.
  2. "Aren't controlled inputs always slow?"
    No. The cost is the render, not the box. A small form with a few controlled boxes renders in no time. It gets slow when the component holding the state renders a large tree after every keystroke, such as a forty-box form where every box has its own state, or the state of a box placed in App. The fixes, in order:
    1. Make a box uncontrolled when the page reads it only at submit.
    2. Move the state of the box down into the component that holds the box.
    3. When the rest of the page really needs the value, use useDeferredValue, which Lesson 68 covers. Unlike debouncing, it waits for no fixed delay.
  3. "Can one box be controlled at first and uncontrolled later, or both at once?"
    No. React's docs say a box cannot be both controlled and uncontrolled at the same time, and it should not switch during its lifetime. That is why a controlled box starts with '' and not undefined. With undefined, the box starts uncontrolled, and the first keystroke by the user makes React print the error "A component is changing an uncontrolled input to be controlled". Different boxes of the same form can still make different choices. In React 19, form actions receive the same FormData directly, which makes uncontrolled boxes the natural default for boxes read only at submit. Lesson 41 covers form actions.
