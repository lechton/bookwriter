Reacting to Input with State: Letting status Pick the Screen

Interview Question · ❱ CORE

How do you design a component that reacts to input with state instead of touching the DOM?

OverviewWhy a Component Describes Its Screens Instead of Changing Them

Writing each message by hand vs. letting status pick the message

Lesson 01 compared plain JavaScript, which changes the page with one command at a time, with React, which describes the finished page. Here is that difference on a small sign-up box that has two messages: an error line when a sign-up fails, and a thank-you line when it works. The user tries to sign up twice. It looks the same, but it is NOT the same thing! After the first try, both ways show the same error line. After the second try, the command for the thank-you line writes into its own paragraph and removes nothing, so the old error stays above it. status holds one word at a time. When it becomes 'success', the condition of the error line is false, and React takes that line off the page.

So with commands, every change must also undo the old message by hand. With status, our code only says which message is true now, and React makes the page match.

No line of handleSubscribe clears the error paragraph. Each command fixes one part of the page, so the developer must remember every part that an earlier command left behind, and here one part was forgotten.

React turns the work around. Each picture of the box that the user can see is called a screen. We first write every screen of the box once. After that, each click by the user and each answer from the server only says which screen is on the page now.

Four Principles of Reacting to Input with State

PRINCIPLES

A React component never shows, hides, turns on, or turns off a part of the page by hand. It describes every screen once, and state picks the screen. Four rules follow:

  1. status picks which screen the box shows. List every screen first, and write each one in JSX, chosen by one value.
  2. A click and a timer only call setStatus. Every input, from the user or from the computer, only sets state, and React draws the new screen.
  3. One status replaces three true-or-false flags. Separate flags can be true together, and then the page shows two screens at once.
  4. The red border follows status, not classList. A look that changes with the screen comes from status in JSX, because React leaves alone a class that its JSX never set.

Here is the map of the four principles before we walk through each one:

Principle 1

Screens First: status Picks Which Screen the Box Shows

Before writing any handler, list every screen the user can see, and write JSX for each one, chosen by a single status value.

A box written from its actions needs one command for each click and each answer, and every command must also undo whatever the last one left on the page. When one command forgets, the user sees two opposite messages at once. When the box is written from its screens, each screen sits in the JSX once, and status says which one is on the page. A message that does not belong to the current screen is simply not in the JSX.

Section 2 · Principle 2A Click and a Timer Only Call setStatus

An input from the user vs. an input from the computer

Something must change status while the page runs. Two kinds of input change the screen of our box. The first comes from the user, and the second comes from the computer:

When the user clicks Subscribe
1<button onClick={() => setStatus('sending')}>Subscribe</button>
The screen becomes sending
When the timer ends
1setTimeout(() => setStatus('success'), 1500);
The screen becomes success

Yes, it is the exact same thing! A click and a timer look like two different kinds of event, but both only call setStatus, and React draws the screen that the new status picks.

The React docs give the two kinds their own names:

  • A human input is something the user does, such as typing in a box, clicking a button, or following a link. Human inputs usually need an event handler.
  • A computer input arrives without the user doing anything, such as an answer from a server, a timer that ends, or an image that finishes loading.

For both kinds, the docs give one rule: to change what the user sees, you set state.

The box turns itself back on

On the error screen, the email box and the Subscribe button are on again, and no line of our code turned them on. React turns them on, because disabled follows status:

  1. The timer calls setStatus with 'error'.
  2. React calls SubscribeBox again, and status is now 'error'.
  3. status === 'sending' is now false, so the email box and the button both get disabled={false}.
  4. React compares the new JSX with the last one and changes only what differs, as Lesson 13 showed. It takes the disabled attribute off the email box and the button, and it swaps the Subscribing... line for the error line.

The timer reads email from the render in which the user clicked Subscribe, as Lesson 15 showed. That is safe here. The email box is greyed out while sending, so the user cannot change the email before the answer arrives.

When the user types a new letter on the error screen, the error line goes away. handleEmailChange calls two setters, and React renders once for both, as Lesson 16 showed. In that render, status is 'typing', so the condition of the error line is false.

Principle 2

Inputs Set State: A Click and a Timer Only Call setStatus

Find every input that changes the screen, from the user or from the computer, and make each one call a setter; the handler never turns a page part on or off and never writes a message.

A click by the user and a timer that ends look like two different kinds of event, but in React they do the same job: they set status, and React draws the screen that status picks. When a handler turns the button off by hand, some other branch must turn it on by hand, and one forgotten line leaves the user stuck. When disabled comes from status in the JSX, exactly one place decides it, and every screen gets the right answer.

✓ DO THIS
1<button onClick={() => setStatus('sending')} disabled={status === 'sending'}>Subscribe</button>
The click only sets state
✗ DO NOT DO THIS
1function handleSubscribe() {
2 button.disabled = true;
WRONG turned off by hand, so every later branch must turn it on by hand!
3}

There is another way to keep the screen in state: one true-or-false flag for each screen. Here are both ways, after a failed try and a second click on Subscribe:

It looks the same, but it is NOT the same thing! Both seem to describe the same four screens. But three flags can be true together, while status can only hold one of its four words at a time.

A mix of values that matches no screen you would want the user to see is called an impossible state. The React docs call it a paradox: a form cannot be typing and sending at the same time. One status with a fixed list of values cannot hold such a mix.

Programmers call a thing that is always in exactly one of a fixed list of states a state machine. Think of a traffic light: exactly one light is on at a time, and red and green are never on together. Our status works the same way. It is always exactly one of 'typing', 'sending', 'success', and 'error'.

This is the exact screen the React docs warn about: you never want to show an error message and disable the box at the same time. Here is how it happens:

  1. The first timer set isError to true.
  2. Each letter the user types calls only setEmail, and nothing sets isError back to false.
  3. The second click sets isSending to true, while isError is still true.
  4. Both && lines read a true flag, so both lines are in the JSX, and React puts both on the page.

React prints no warning, because every flag holds a valid true or false. Only the mix is wrong.

Eight mixes for four screens

Each of the three flags can be true or false, so together they allow two times two times two, which is eight mixes. Only four of them are real screens: all three flags false is typing, and exactly one flag true is sending, error, or success. The other four mixes are impossible states that the code must never reach. Each new flag doubles the number of mixes, while a new screen adds only one word to status.

Principle 3

One Status: One status Replaces Three True-or-False Flags

Keep the screen in one status string with a fixed list of values, never in one true-or-false flag for each screen.

Three flags allow eight mixes, and only four of them are real screens. When one handler forgets to switch an old flag off, the page shows two screens at once, such as an error line next to Subscribing..., and React gives no warning. A single status works like a traffic light: it holds exactly one of its words, so setting a new word always ends the old screen.

Section 4 · Principle 4The Red Border Follows status, Not classList

classList.add by hand vs. className from status

On the error screen, the email box should get a red border. The CSS file holds one class for it:

src/index.css
1.invalid {
2 border: 2px solid red;
3}

There are two ways to put that class on the email box. The first adds it by hand with classList.add, the browser's way to add one class to an element. The second computes className from status in the JSX:

Adding the class by hand
1document.getElementById('email').classList.add('invalid');
The border turns red, and it stays red
Computing className from status
1<input className={status === 'error' ? 'invalid' : ''} />
Red only while status is 'error'

It looks the same, but it is NOT the same thing! On the error screen, both email boxes have a red border. But React leaves alone a class that its JSX never set, so the class added by hand stays after the screen changes. The class computed from status leaves as soon as status is no longer 'error'.

No line of our JSX asks for a red border on the typing screen. Our classList.add put the class straight onto the real DOM node, outside the screen that React describes. Here is why React leaves it there:

  1. The user's keystroke sets status to 'typing', and React calls SubscribeBox again.
  2. The JSX of the email box has no className, in this render or in the last one.
  3. React compares the two and finds no change to className, so it does not touch the class of that box.
  4. The invalid class that our code added by hand is still on the box.

Principle 4

Looks Follow State: The Red Border Follows status, Not classList

When a look changes with the screen, such as a red border on the error screen, compute className from status in JSX; never add or remove classes on the DOM node by hand.

React changes only the parts of the DOM whose JSX changed since the last render. A class added with classList.add is not in the JSX at all, so React never sees it and never takes it away, and the red border stays after the error is gone. When className comes from status, the class is part of the screen React describes, so it appears with the error screen and leaves with it.

Interview PrepFor the Interview

The Interview Question: How do you design a component that reacts to input with state instead of touching the DOM?

How to Answer Clearly in 30 Seconds

"I never show, hide, turn on, or turn off a page part by hand. I describe every screen once in JSX and let state pick the screen. The React docs give five steps, and I follow them in this order:

  1. List every screen the user can see. The docs call them visual states. For a newsletter box, they are typing, sending, success, and error. I can draw all of them on one page by passing a status prop before any logic exists.
  2. Find every input that changes the screen. Human inputs are things like typing and clicking. Computer inputs are things like a server answer or a timer that ends.
  3. Keep the screen in useState. I use one status string with a fixed list of values, not one true-or-false flag for each screen, because flags can be true together and show an impossible mix.
  4. Remove state that is not needed. Anything that can be worked out from other state needs no state of its own.
  5. Connect every input to a setter. Handlers only call setStatus. Messages, disabled, and class names all come from status in JSX. React then changes only the DOM parts that differ, and it leaves alone a class that no JSX set, which is why I never use classList on a node that React renders."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why is one status string better than several booleans such as isSending and isError?"
    Each true-or-false flag doubles the number of possible mixes. Three flags allow eight mixes, and only four of them are real screens. When one handler forgets to switch an old flag off, the page shows an error line next to Subscribing..., and React prints no warning, because every flag holds a valid value. One status with a fixed list of values works like a state machine. Like a traffic light, it is always in exactly one state, so setting a new word always ends the old screen. Some mixes can still make no sense across several state variables, such as an error text while status is 'success'. A reducer can bring those into one place, which is Lesson 27.
  1. "How would you add a new screen to this component, and why is the declarative version safer than the imperative one?"
    A new screen, such as a Check your inbox to confirm line, adds one value of status, one branch in the JSX, and one setter call where its input arrives. The handlers that already work do not change, and no existing screen breaks. In the imperative version, every new screen means new commands, and every existing command must learn to undo it. The React docs admit that the declarative version is longer, and they call it much less fragile. Teams often draw every screen on one page, called a living styleguide or a storybook, to check each one before the logic exists.
  1. "Why does a class added with classList.add stay on a React element, and what do you write instead?"
    React compares the new JSX with the last one and changes only the DOM properties that differ. A class added with classList.add is not in the JSX, so React never sees it and never removes it. After the error screen ends, the red border stays. Instead, I compute the class from state, such as className={status === 'error' ? 'invalid' : ''}, so the class is part of the screen React describes. Another way is to return two separate chunks of JSX, one for each screen. Then their nesting must line up, or switching between them can rebuild the whole tree below and reset what the user typed, which is Lesson 25.
