This small block holds several words that do all the work. Let us take them one at a time.

The first line creates a piece of state with useState, which we met in earlier lessons. It gives us two things. The variable name holds the current name, and it starts as John. The function setName comes from React. When we call it with a new name, React stores that name and draws the component again.

Box A has defaultValue. This word comes from React, and it means the text the box starts with. React puts John into the box once, when the box first appears. After that, React leaves the box alone.

Box B has value. This word also comes from React, but it means something much stronger. It means the text the box must show. React makes the box show John. Whenever the box shows something else, React puts John back.

Box C also has value, but its value is the variable name. So box C must show whatever name holds right now. Box C also has onChange. This is a function that React calls every time the user changes the text in the box. React hands it one thing, an event object, which we call e. Inside that object, e.target is the box itself, and e.target.value is the text that sits in the box at that moment, with the newest letter included.

So read the whole line of box C like this. Every time the user types, take the text that is now in the box. Then save it as the new name.

The Console already shows a message from React. It is about box B, which has a value but no onChange. We will see in a moment why React complains.

Box A and box C show Johnny. Box B still shows John. Why? Let us follow one key press, the letter n, through each box.

In box A:

  1. The user presses n.
  2. The browser adds n to the text in the box, and the box shows Johnn.
  3. Nothing else happens. React does not watch this box after the start, so the letter stays.

In box B:

  1. The user presses n.
  2. The browser adds n, and for a moment the box shows Johnn.
  3. Box B has no onChange, so nothing tells our code about the new letter. Its value is still John.
  4. React sees that the box no longer shows its value. So React puts John back, and the n disappears.

In box C:

  1. The user presses n.
  2. The browser adds n, and for a moment the box shows Johnn.
  3. React calls onChange. Inside it, e.target.value is Johnn.
  4. setName stores Johnn as the new name, and React draws the component again.
  5. The value of box C is now Johnn. The box already shows Johnn, so the letter stays.

Now compare box B and box C. Both use value, and React treats that value the same way in both boxes: the box must show it. The difference is step 3. In box C, onChange saves each new text into state, so the value grows with the typing. In box B, nothing saves the new text, so the value stays John, and React keeps putting John back. That is what the Console message means: a value with no onChange gives a box the user cannot change.

So the curly braces in box C are not what makes it editable. Writing value={name} only reads the name. It never writes anything back into it. Imagine box C without its onChange. The name would stay John forever, and box C would refuse every letter, exactly like box B. The only road from the box back to state is onChange.

Four words describe what we just saw. You will hear them in every React team and in every interview:

  • Default: a new phone comes with a default ringtone. The phone starts with it, and then it plays whatever ringtone its owner picks. A default value works the same way. It is only the starting text.
  • Uncontrolled: a box like box A is called uncontrolled. After the starting text, the browser decides what it shows, and React does not.
  • Controlled: think of the departure board at a train station. It shows only what the station's system sends to it. Nobody writes on it with a pen. A controlled box is that board. It shows only what state holds, like box C.
  • Single source of truth: in box A, the text in the box and the name in state are two separate copies, and nothing keeps them equal. In box C, there is only one copy, the one in state. Developers call that one copy the single source of truth.

Why a contact form keeps the message after Send

Now look at a real page. Almost every online shop has a Contact Us page. A customer types a question, such as where is my order, and clicks Send. A thank-you line appears under the form. Yet the question is still sitting in the box. The customer wonders whether the message really went out, and may even send it twice.

So the developer wants the box to be empty after Send. Before writing a single line, the developer has to answer one question: who owns the text inside the box, the browser or React state? This lesson answers that question, one field at a time.

Two ways to own a field's value

In real projects, developers choose between two owners for what a field holds:

  1. Controlled: state holds the value, and the field receives it through value. A change handler sends every keystroke back into state. This fits a page that reacts to every keystroke, such as a live character count or a box that empties after Send.
  2. Uncontrolled: the browser holds the value, and defaultValue gives only the starting text. The code reads every field once, when the form is sent, with FormData, a browser tool that collects all the fields of a form at once. This fits a form whose values matter only at the moment it is sent.

Both are real choices, and neither is an error. This lesson teaches the controlled way. Choosing between the two belongs to a later lesson on forms.

What this lesson stands on

This lesson builds on six facts from earlier lessons:

  • Curly braces versus quotes: in JSX, quotes keep the exact characters as text. Curly braces run JavaScript and put the result in place. So value="John" is fixed text, and value={name} reads a variable.
  • The double ampersand in JSX: a condition followed by a double ampersand and an element shows the element only when the condition is true.
  • The event object: React passes an event object e to every handler. Its target is the element where the event started.
  • Sending a form: a form's submit handler runs when the user clicks its submit button. Calling preventDefault on the event stops the browser from reloading the page.
  • State: useState keeps a value between renders. Its setter asks React for a new render. The starting value is used only on the first render.
  • Render and commit: after a state change, React renders the component again and changes only the page nodes that differ.

Two small JavaScript tools also appear in this lesson:

  • A string's length is the number of characters in it. The word Hello has a length of 5.
  • A string's trim method gives back a copy of the string without the spaces at its start and its end.

Six Principles of Controlled Inputs

PRINCIPLES

A field keeps its own value inside the browser until React gives it one. Once React gives it a value, React makes the field show that value after every render. Six practical rules follow from that:

  1. Principle 1: An Uncontrolled Box Keeps Its Own Text: A field with only a starting text keeps whatever the user types. Changing state does not reach it.
  2. Principle 2: The Value and the Change Handler Work as a Pair: The value carries state into the box. The change handler carries each keystroke back into state. One without the other freezes the box.
  3. Principle 3: The Handler Decides What the Box Shows: Whatever the handler stores in state is exactly what the box shows next. So the handler stores the typed text as it is.
  4. Principle 4: A Dropdown Is Controlled on the Dropdown Itself: The chosen item is one piece of text in state, given to the dropdown. It is never marked on one of the options.
  5. Principle 5: A Checkbox Is Controlled by a Yes or No Answer: A checkbox answers yes or no, so it uses true or false, never text.
  6. Principle 6: The Value Stays a String for the Field's Whole Life: A controlled field needs a real value from its very first render.

Here is the complete map of those six principles before we walk through each one:

Principle 1

Uncontrolled Fields: The Box Keeps Its Own Text

A field with no value from React keeps whatever the user types, so changing state that the field never reads changes nothing in the box.

This one surprises everybody once. You put the message in state, you empty the state after Send, and the message is still sitting there in the box. A value alone vs. a value with a change handler

Look at two name boxes. Both get a value. Only the second one also gets a change handler, onChange:

4<input value={name} onChange={e => setName(e.target.value)} />

These are box B and box C from the opening. We already followed one key through them. Here is the short version:

  1. In both boxes, the browser adds the new letter.
  2. In the second box, onChange stores the new text in state. In the first box, nothing stores it.
  3. React then makes each box show its value. The first box gets John back. The second box gets the new text, so the letter stays.

So a value carries state into the box. The change handler carries the typing back into state. Each one does only half of the job, and a controlled box needs both.

Three pairs look alike here, so let us compare them now that we have seen the steps:

  • A value and a default value both put John in the box at first. But a default value sets the text once, and then the browser takes over. A value keeps making the box show it, after every key.
  • A fixed value in quotes and a value from state with no change handler act the same for the user. In both, nothing changes the value, so the box refuses every letter.
  • React's change handler and the browser's own change event have the same name. But they run at different moments, as we see next.

React's change handler vs. the browser's change event

In plain browser JavaScript, a text box fires two different events while the user edits it:

Plain JavaScript: two browser events on one text box
1const box = document.querySelector('input');
2box.addEventListener('input', () => console.log('input'));
1. Runs on every keystroke
3box.addEventListener('change', () => console.log('change'));
2. Waits until the user leaves the box

The input event runs on every single keystroke. The browser's change event waits until the user finishes and leaves the box.

React's change handler sounds like the browser's change event, but it behaves like the input event. It runs on every keystroke. That is exactly what a controlled box needs, because state must hear every letter.

Principle 2

Controlled Fields: The Value and the Change Handler Work as a Pair

Give the field its value from state and a change handler that stores the typed text in state, always together.

The value only carries state into the box. It carries nothing back. So say you give the box a value and forget the change handler. Every letter the user types is thrown away, because React keeps putting the old state back. The change handler is the road back. It runs on every keystroke, reads the new text, and hands it to state. Then the box shows it.

Section 3 · Principle 3Whatever the Handler Writes Into State Is What the Box Shows

Why the handler decides what the box shows

Look at three change handlers for the same kind of controlled box. Each one does something slightly different with the typed text before it stores it:

Three handlers for one controlled box
1<input value={name} onChange={e => setName(e.target.value)} />
A. Stores the text as typed
2<input value={name} onChange={e => setName(e.target.value.trim())} />
B. Stores a copy without outer spaces
3<input value={name} onChange={e => { if (e.target.value.length <= 5) setName(e.target.value); }} />
C. Stores only up to 5 characters

Box A stores the text exactly as it arrives. Box B calls trim first, the string method that removes spaces from the start and the end. Box C checks length, the number of characters, and stores the text only while it is five characters or shorter.

The user types Ann Lee into each box. Watch what happens when the user presses the space after Ann:

  1. In every box, the browser adds the space, and for a moment the box shows Ann , with the space.
  2. Box A stores 'Ann '. Box B trims it and stores 'Ann'. Box C stores 'Ann ', because it is only four characters long.
  3. React makes each box show its value. Box A and box C keep the space. Box B shows Ann, so the space is gone.

Why a checkbox answers true or false

A checkbox is an input with the type checkbox. It has a property called checked, which the browser keeps. It is true when the box is ticked and false when it is not. In React, we control a checkbox by giving it checked from state, the same way we give a text box its value.

Look at the same checkbox with two different handlers:

One checkbox, two handlers

For the Interview

The Interview Question: How do you make an input, textarea, or select fully controlled by React state?

How to Answer Clearly in 30 Seconds

"By default, a field is uncontrolled. The browser keeps its value, and defaultValue only sets the starting text. To control it, I keep the value in state and pass it as value, or as checked for a checkbox. React then makes the field show that state after every render, so state becomes the single source of truth. I always pair it with onChange, which runs on every keystroke like the browser's input event, and I store e.target.value in state right away. Without onChange, the field is read-only and React logs an error. Whatever I store is exactly what the field shows, so I never trim or reformat while the user types. I tidy the text on submit instead. The same pair works for a textarea, and for a select, where value goes on the select and never selected on an option. A checkbox uses checked and reads e.target.checked. Finally, a controlled field must get a string from its very first render. I start state as an empty string, or I write value={draft ?? ''}. Otherwise React warns that an uncontrolled input became controlled."

Three Classic Follow-Up Questions Interviewers Ask

  1. "What happens if you pass value without onChange, and what are the alternatives?"
    The field becomes read-only. The browser puts each typed letter into the node, but no handler updates state, so React puts the old value back after every keystroke. React also logs an error: "You provided a value prop to a form field without an onChange handler." The error names three ways out. Add onChange if the user should edit the field. Use defaultValue if you only need a starting value. Add readOnly if the field must never change.
  2. "Why does a controlled field lose spaces or make the caret jump when the handler changes the text?"
    In a controlled field, the text on screen is the state value, not the typed text. If the handler stores a trimmed copy, every space is removed the moment it is typed. If it stores an uppercase copy, or stores the value later inside a setTimeout, the caret jumps to the end of the text. It jumps even when the user was typing in the middle. The rule is to store e.target.value right away, exactly as typed, and to clean the data on submit. Refusing a keystroke on purpose, such as a 200-character limit, is fine: React simply keeps the old value.
  3. "Why does React warn that a component is changing an uncontrolled input to be controlled, and how do you fix it?"
    React decides whether a field is controlled by looking at its value. Calling useState with no argument gives undefined, and value={undefined} means no value, so the field starts uncontrolled. When the first keystroke stores a string, the field becomes controlled, and a field cannot switch kinds during its life. The fix is to start state as an empty string. For data from a server that may be null, write value={someValue ?? ''}. For checkboxes, checked must always be a boolean.
