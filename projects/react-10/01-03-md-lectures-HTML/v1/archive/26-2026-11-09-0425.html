Thinking in React, the Five Steps from a Mockup to a Working Page

Interview Question · ❱ CORE

What is the step-by-step process for building a UI in React?

OverviewHow We Build a Page in React, One Step at a Time

Where to start when a designer hands us a mockup

Picture the drinks menu on a cafe website. At the top sit a search box and an Only show drinks in stock tick box. Below them sits a list of drinks.

Type tea into the search box and tick Only show drinks in stock, and three things happen on the list below:

  • Every drink without tea in its name disappears.
  • The sold-out Iced tea disappears too.
  • Only Tea stays on the list.

Before a single line of code exists, a designer hands us a drawing of this finished cafe menu. That drawing of the finished page is called a mockup.

Where do we start when we turn that mockup into a working page?

We do not start from what the user types. First, we build the unchanging menu on the screen. Only after the whole menu is visible do we wire up the values that change.

Compare the two ways a developer can start on this cafe menu:

  • Starting from what the user does: we open App.jsx and add a useState and a handler for the search box right away. Then we grow the rest of the menu around them as each piece comes to mind.
  • The React way: we follow five steps in a fixed order. React's documentation calls them Thinking in React:

1. Component hierarchy: we draw boxes on the cafe menu mockup and turn each box into a component. Our four boxes become MenuPage for the whole menu, SearchBar for the two inputs at the top, DrinkList for the list below, and DrinkRow for one drink. React's docs call this nested tree of components a component hierarchy.

2. Static version: we build those four components from the drinks data with props only and no state. Think of a printed menu board on a cafe wall. Every drink and box appears on the page to read, and nothing reacts to the user yet. React's docs call this unchanging page a static version.

3. Minimal state: we keep as state only the values that change over time and cannot be computed from anything else. On our menu, that minimal state is only two values: the search text filterText and the tick inStockOnly. The matching list of drinks is computed from them, so it is never stored in state.

4. Where state lives: both SearchBar and DrinkList need filterText and inStockOnly. So we put both state variables inside MenuPage, their closest common parent.

5. Inverse data flow: MenuPage passes its state setters down into SearchBar as props. When the user types or ticks, SearchBar calls those setters from onChange to send the new values back up to MenuPage. React's docs call this upward flow inverse data flow.

The five steps bring no new tool. Yes, it is the exact same toolbox you already know! Step 1 uses components and the UI tree. Step 2 uses props. Step 3 uses the three questions for what is state. Step 4 uses the closest common parent. Step 5 uses a function passed down as a prop. Thinking in React is the order in which we use them.

Why does the order matter? React's docs give the reason in their own words: "Building a static version requires a lot of typing and no thinking, but adding interactivity requires a lot of thinking and not a lot of typing." The order keeps the long typing and the hard thinking apart.

Lesson 21 also gave five steps from React's docs, for designing the visual states of one form. Those five steps design one component. These five steps build a whole page out of many components.

What is at stake

What is at stake is what the user sees on the cafe menu when the steps get mixed up. A developer who starts from useState calls and handlers at random often stores the same value twice, once in each component that needs it. Soon the two copies stop agreeing.

Then the menu breaks on the screen:

  • The user ticks Only show drinks in stock, and Iced tea Sold out stays on the list.
  • The user types tea into the search box, and all five drinks stay in place.

The search bar at the top and the drink list below give two different answers on the same page.

Readers usually go wrong in four places. They start from useState and handlers before the static page exists. They store the filtered list as state. They put the search text inside SearchBar, where DrinkList cannot read it. And they expect value={filterText} to update filterText by itself.

In this lesson, we will build this cafe menu across the five steps.

Five Principles of Thinking in React

PRINCIPLES

Each principle is one of the five steps, in order, and after each one we look at what the page shows:

  1. Principle 1: Boxes on the Mockup Become Four Components: Before any code, we draw a box around every part of the mockup and name each box. A box inside a box becomes a child inside a parent.
  2. Principle 2: The Static Menu Ignores the Typed Search: We build the whole page from the data with props only. The page looks finished, but the list does not follow what the user types.
  3. Principle 3: Only the Search Text and the Tick Box Become State: Of the four values the page uses, only two change over time and cannot be computed from anything else. Only those two become state.
  4. Principle 4: State in MenuPage Freezes the Search Box: We put both pieces of state in the closest common parent of the search box and the list. The page now shows the state, but the boxes refuse the user's input.
  5. Principle 5: onFilterTextChange Lets the Search Box Change MenuPage's State: Only the owner of the state can call its setter. So the owner passes the setters down, and the boxes call them from onChange.

Section 1 · Principle 1Boxes on the Mockup Become Four Components

Drawing a box around every part of the mockup

Step 1 writes no code. We print the mockup and take a pen. React's docs say: "Start by drawing boxes around every component and subcomponent in the mockup and naming them."

On our menu, we draw four boxes:

  1. A big box around the search part and the list together. We name it MenuPage.
  2. A box around the search box and the tick box. We name it SearchBar.
  3. A box around the whole list of drinks. We name it DrinkList.
  4. A box around one row of the list. We name it DrinkRow. The list has five rows, but every row looks the same, so they are five copies of one component.

Then we write the names the way the boxes sit inside each other. A box that sits inside another box goes under it:

Figure 5 — The four boxes drawn on the mockup, written as a component hierarchy.

React's docs call this nested list of names a component hierarchy. It is not a new kind of structure. Yes, it is the exact same thing as the UI tree from Lesson 06! A box inside another box on the mockup is a child inside a parent in the tree. The docs say it this way: "Components that appear within another component in the mockup should appear as a child in the hierarchy." So SearchBar and DrinkList are children of MenuPage and siblings of each other, and DrinkRow is a child of DrinkList.

Where one box ends: one component does one thing

Why does one row get its own box, instead of staying inside the list? React's docs answer with a computer science idea called separation of concerns: "a component should ideally only be concerned with one thing. If it ends up growing, it should be decomposed into smaller subcomponents." The search part lets the user type and tick. The list shows the drinks. One row shows one drink. Each of them does one thing, so each gets its own box.

The docs give three habits you can start from when you split a design:

  • Programming: split it where you would write a new function in plain JavaScript.
  • CSS: split it where you would write a new CSS class. The docs add that a component is usually a bigger piece than one class.
  • Design: split it the way the designer grouped the layers in the design tool.

The data helps too. The shape of the data a page shows is called its data model. Our data model is the DRINKS array. It has the same shape as the boxes: the whole array is the list, DrinkList, and each object in it is one row, DrinkRow. The docs say that the UI and the data "often have the same information architecture, that is, the same shape." So they advise: "Separate your UI into components, where each component matches one piece of your data model."

Some parts can go either way. The tick box, for example, can stay inside SearchBar, or it can get its own component. The docs call a choice like this "a matter of preference, and you could go either way". Both choices give the exact same page. The choice is only about how big that part will grow: if the cafe later adds more filters next to the tick box, they can move into a component of their own.

Where the four names and App come from

We chose the names MenuPage, SearchBar, DrinkList, and DrinkRow ourselves. Often the designer has already chosen them. The docs say: "If you work with a designer, they may have already named these components in their design tool. Ask them!"

App is not a box on the mockup. It is the root component that main.jsx renders, as in Lesson 07. It holds the DRINKS array and the heading Drinks, and it renders MenuPage.

After Step 1, the browser shows nothing new, because this step writes no code at all.

Mistake: writing the whole page in one component

The habit this step replaces is opening App.jsx and writing the search box, the tick box, and the list of drinks all inside one component. That component grows with every part the designer adds. The list cannot be used on another page without bringing the search box along. And splitting the component later means moving state and handlers into new files after the page already works.

Mistake: adding state while the page is still being typed

React's docs warn about this step: "At this point, you should not be using any state values. That's for the next step!" A developer who adds state too early usually writes SearchBar first and puts a useState for the search text inside it, because the box is there. Then the developer writes the list in DrinkList, a sibling of SearchBar, and finds that the list cannot read the search text, because a sibling cannot read another component's state, as in Lesson 24. Section 3 · Principle 3Only the Search Text and the Tick Box Become State

The four values of the page

Step 3 also writes no code. We read the page and the data, and we list every value the page uses. React's docs list the same four values for their own example page. On our menu, they are:

  1. The list of drinks.
  2. The search text the user typed.
  3. The tick of the box.
  4. The drinks that match the search text and the tick.

The fourth value changes every time the user types or ticks, so it looks like state. It may look the same, but it is NOT the same thing! The drinks that match are computed from the other three values. Whenever we know the list, the text, and the tick, we can always work out which drinks match.

The key idea of this step, in the docs' words: "Think of state as the minimal set of changing data that your app needs to remember." The docs' title for this step is find the minimal but complete representation of UI state. Minimal means nothing that can be computed. Complete means everything the page needs to remember.

The three questions, asked once of each value

Lesson 22 taught three questions that tell what is state: Does it remain unchanged over time? Is it passed in from a parent via props? Can you compute it from existing state or props? A "yes" to any of them means it is not state. Here are the answers for the four values of our menu:

Storing the drinks that match, and computing them

There are two ways to get the drinks that match, and they look alike in the code:

They are NOT the same thing. With useState, the list of matching drinks is a copy that our code must update by hand after every keystroke and every tick by the user. With filter, the list is made again on every render from the current text and tick, so it is always right. Principle 4 writes out the full filter call.

The docs name the rule behind this DRY, short for Don't Repeat Yourself, and give a shopping list as the example: "don't store the number of items as another state value, instead, read the length of your array."

Props and state

The list of drinks failed the second question because it is a prop. The docs put the two words side by side: props "are like arguments you pass to a function", and state "is like a component's memory". They also say: "Props and state are different, but they work together." A parent keeps information in state and passes it down to its children as props. That is exactly what Step 4 does with filterText and inStockOnly.

After Step 3, the browser shows nothing new, because this step writes no code.

Mistake: storing the drinks that match as a second state

A developer stores the matching drinks in a second state variable, next to the search text, and the onChange of the search box updates both. Later the developer adds the tick box and forgets to update the matching drinks from its onChange. Now the user ticks the box, inStockOnly changes, and Iced tea stays on the list although it is sold out, because nothing told the stored copy about the tick.

Principle 3

Minimal State: Only the Search Text and the Tick Box Become State

List every value the page uses and keep as state only what changes over time, does not come from a parent, and cannot be computed from other state or props.

Every value stored as state is one more value that can disagree with the others. The list of drinks comes from a parent. The drinks that match can be computed from the list, the text, and the tick. Only the search text and the tick of the box change over time and cannot be computed, so only they become state.

The box with value and no onChange refuses every letter the user types. Yes, it is the exact same frozen box as in Lesson 20! Here the value comes from state in a parent, and in the project it will reach the box through props, but the box freezes in the same way.

Finding the owner in three steps

Lesson 24 taught how to find the owner of a piece of state. React's docs list the same three steps, and we apply them once to filterText and inStockOnly:

  1. Find every component that renders something from that state: DrinkList needs both values to pick the drinks that match. SearchBar needs both values to show the text in the box and the tick.
  2. Find their closest common parent: SearchBar and DrinkList are siblings, and their closest common parent is MenuPage.
  3. Decide where the state lives: in MenuPage.

For the last of these three, the docs give three choices: "Often, you can put the state directly into their common parent." "You can also put the state into some component above their common parent." "If you can't find a component where it makes sense to own the state, create a new component solely for holding the state." Our common parent works, so the state goes into MenuPage. Both values go to the same place, and the docs explain why: "they always appear together, so it makes sense to put them into the same place."

The state cannot live in SearchBar, even though the boxes are there. DrinkList is a sibling of SearchBar, and a sibling cannot read another component's state, as in Lesson 24.

Passing the setter down, and calling it from onChange

Only the owner of the state can call its setter, and the owner here is MenuPage. React's docs say it about their own example: "The state is owned by FilterableProductTable, so only it can call setFilterText and setInStockOnly." FilterableProductTable is the docs' name for the component that plays the part of our MenuPage. So MenuPage hands its setter down as a prop, and the box calls it:

The parent passes its setter down, and the box in the child calls it
1<SearchBar onFilterTextChange={setFilterText} />
In MenuPage: the setter travels down as a prop
2
3<input onChange={(e) => onFilterTextChange(e.target.value)} />
In SearchBar: the typed text travels back up

Yes, it is the exact same thing as the callback prop from Lesson 23, and the setter passed down in Lesson 24! The docs give it a name for its direction: inverse data flow. Inverse means the other way round. Props carry data down the tree, and a function passed down carries the typed text the other way, up the tree to its owner.

value alone and value with onChange

A reader may expect value={filterText} to change filterText when the user types, since the box already shows it. Compare the two boxes:

A box with value only, and a box with value and onChange
1<input value={filterText} />
Value only: the state goes down into the box, and the box stays frozen
2<input value={filterText} onChange={(e) => onFilterTextChange(e.target.value)} />
Value and onChange: every keystroke goes back up

They look alike, but they are NOT the same thing. value only sends the state down into the box. The onChange that calls onFilterTextChange sends each new text back up to MenuPage. Some other tools let a box and a variable update each other with no handler written. That is called two-way data binding, and React does not do it. The docs say: "React makes this data flow explicit, but it requires a little more typing than two-way data binding."

Interview PrepFor the Interview

The Interview Question: What is the step-by-step process for building a UI in React?

How to Answer Clearly in 30 Seconds

"React's docs call it Thinking in React, and it has five steps in a fixed order. First, I break the mockup into a component hierarchy: I draw a box around every part, name it, and nest the names, so each component does one thing and matches one piece of the data. Second, I build a static version with props only and no state, so the data flows down from the top component. Third, I find the minimal state: only what changes over time, does not come from a parent, and cannot be computed. Fourth, I put each piece of state in the closest common parent of the components that render from it. Fifth, I add inverse data flow: the owner passes its setters down, and the inputs call them from onChange. On a search page, only the search text and the checkbox are state, and the filtered list is computed during rendering."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why build a static version first, without any state?"
    Because the two jobs are different. React's docs say that building a static version "requires a lot of typing and no thinking, but adding interactivity requires a lot of thinking and not a lot of typing." When state goes in while the components are still being typed, it often lands in the wrong component, such as the search text inside the search box component, where the list cannot read it. After the static version, the data already flows down with props, and the state goes in with one clear question: who needs it? The static version takes its data as a prop at the top, whether the data is written in the file, as in our menu, or fetched from a server, which a later lesson covers.
  2. "On a page with a search box and a filtered list, is the filtered list state?"
    No. It changes when the user types, but it can be computed from the full list, the search text, and the checkbox, so it is computed during rendering with filter. If it were stored as a second state, every handler would have to update it by hand, and a forgotten update would leave a sold-out item on the list. The docs' rule is to find the minimal set of changing data the app needs to remember and compute everything else when it is needed. On their own example, the docs conclude that only the search text and the value of the checkbox are state.
  3. "After you move the state up and pass it down, why does typing in the box do nothing, and how do you fix it?"
    The box has value={filterText}, so React makes it always show filterText, but nothing calls setFilterText when the user types. React prints the read-only field error in the Console. React has one-way data flow, so the fix is inverse data flow: the owner passes its setter down as a prop, such as onFilterTextChange={setFilterText}, and the box calls it from onChange with e.target.value. React makes this flow explicit, with a little more typing than two-way data binding. When the setters and props passed down grow too many or go too deep, later lessons bring useReducer and context.
