Controlled Inputs: Letting State Decide What Every Box Shows

Interview Question · ❱ CORE

How do you make an input, textarea, or select fully controlled by React state?

Look at the Clear button once more. Its code only puts an empty string into name. No line of our code touches the box. So who empties the box?

The two props on the box do. React understands both of them on every input:

  • onChange is our function, and React calls it every time the user changes the text in the box. Here it saves the new text in name.
  • value tells React what the box must show. Here it says: show whatever name holds right now.

  2. React renders App again.
  3. The greeting reads name, so it shows only Hello.
  4. The box also reads name, through value. So React makes the box empty too.

Think of a classroom whiteboard. The students call out their answers, but only the teacher writes on the board. The board shows only what the teacher wrote. Our box works the same way. The user calls out letters through onChange. Only our state writes the text. The box shows only what state holds, through value.

A box that works like this is called a controlled box, because React state controls what it shows. Principles 1 and 2 look at each of the two props on its own.

The real page: a contact form that counts and clears

Now think of the contact form of an online shop. Under the message box, a small line counts the letters as the user types, such as 12 / 200. This form needs two things from its boxes.

First, the count must change on every key. So the text must reach state on every key, not only when the user clicks Send.

Second, after Send, every box must be empty again, ready for the next message. Our code empties the state. So state must be able to reach back into the box and empty it too.

A box that only reports to state fails the second job. A box that only listens to state fails the first job. This lecture shows how one box does both jobs.

Five Principles of Controlled Inputs

PRINCIPLES

  1. onChange sends every key into state. React calls it on every key, so the count can follow each letter.
  2. value sends state back into the box. Then setting state is enough to empty the box after Send. A prop that only sets the starting text cannot do this.
  3. value without onChange freezes the box. React puts the old text back after every key, and the Console shows an error.
  4. A menu and a tick box use the same pair. The menu takes its choice from state. The tick box takes its tick from state, and its handler reads the tick, not the text.
  5. A controlled box starts with an empty string. If it starts with nothing at all, React warns as soon as the user types.

Here is the map of the five principles before we walk through each one:

React's onChange and the browser's change event are NOT the same

If you have written plain JavaScript, this may surprise you. The browser has its own event called change, and it does not fire on every key. In plain JavaScript, there are two different events you can listen to on a text box:

page.js
1messageBox.addEventListener('change', e => console.log(e.target.value));
Runs only when the user leaves the box
2messageBox.addEventListener('input', e => console.log(e.target.value));
Runs on every key

The browser's change event waits until the user is done with the box and clicks somewhere else. The browser's input event fires on every change.

React's onChange behaves like the second line, the input event. So the two share a name, but they are NOT the same. The browser's change event waits for the user to leave the box. React's onChange fires on every key.

React also accepts onInput, which does the same job. React code uses onChange by long habit, so this book uses it too.

Inside the handler, message is still one letter behind

There is one more trap here. Suppose we add a log line to the handler for a moment:

In Lesson 15, you saw that each render sees its own fixed state values. The handler belongs to a render too. Here is the order:

  1. When the box held Wher, React rendered ContactForm. In that render, message is Wher, and the handler is made in that same render.
  2. The user types e, and the browser puts it into the box.
  3. React calls the handler from that render. Inside it, message is still Wher.
  4. setMessage saves Where, but only the next render will see it.

So inside the handler, the new text lives only in e.target.value. That is why the handler saves e.target.value, and never builds the new text from message. We take the log line out again before we go on.

Principle 1

onChange: React Calls It on Every Key

When the page must react to what the user types, give the box onChange and save e.target.value with the setter.

The count must move while the user types, so the text must reach state on every key. React's onChange is not the browser's change event, which waits for the user to leave the box. It fires on every key, like the browser's input event. By the time it runs, the browser has already put the new letter into the box, so e.target.value holds the whole new text. A plain variable cannot do this job, because changing it never makes React render again.

✓ DO THIS
1const [message, setMessage] = useState('');
2<textarea onChange={e => setMessage(e.target.value)} />
Saves the whole text on every key
✗ DO NOT DO THIS
1let message = '';
2<textarea onChange={e => { message = e.target.value; }} />
WRONG a plain variable never makes React render again

Why the box with defaultValue keeps John

While the user types, the two boxes behave exactly the same. Only Clear shows the difference. So why does the left box keep John?

The answer is in what defaultValue does. defaultValue is a React prop that gives the box its starting text, and nothing more. React writes it into the box once, when the box first appears. After that, the box keeps whatever the user types, and React never changes it again.

Here is what happens in the left column after the click, in order:

  1. The user clicks Clear, and setName saves an empty string.
  2. React renders App again. The greeting reads name, so it shows only Hello.
  3. The box has no value prop. Its defaultValue was used once, when the page opened. So on this render, React writes nothing into the box.
  4. The browser still holds John inside the box, so the box keeps it.

value works the other way. It is a React prop too, and React writes it into the box after every render. In the right column, the first two steps are the same. Then the steps change:

  1. React reads value, and name is now an empty string.
  2. React writes that empty text into the box.
  3. The box is empty, just like the greeting.

React's documentation says it plainly: with defaultValue, your code "only specifies the initial value. It does not control what the value should be right now."

Think of a student's own notebook. On the first day, the teacher writes one line on page one. That is defaultValue. After that, the student writes freely, and the teacher cannot erase anything from the front of the room. A box like this, without value, is called an uncontrolled box. It keeps its own text.

A box with value from state and onChange back into state is the whiteboard from the start of the lecture. It is a controlled box. React's documentation puts it this way: "React will force the input to always have the value you passed."

With value, why can I still type?

If React forces the box to show name, how does a new letter get in? Here is what happens on every key in the right column:

  1. The user presses a key, and the browser shows the letter in the box.
  2. React calls onChange, and setName saves the new text.
  3. React renders again, and value is now the new text.
  4. React writes that same text into the box, so the letter stays.

The letter survives because state already holds it when React writes the box again.

State is the single source of truth

Our page now shows the message in two places: the box and the count. Both copy the same state. Think of a train station with one main clock. Every platform screen copies that clock. When the clock changes, every screen changes with it. Nobody sets a platform screen by hand.

State is our main clock. The box and the count are the screens. This idea is called a single source of truth: one place holds the text, and everything on the page copies it. To change what the box shows, we never touch the box. We change the state.

An empty defaultValue and value={message} are NOT the same

When the page opens and message is empty, both versions draw the exact same empty box. So it is easy to think they are the same. But you saw where they split: at the first render after Send. In step 3 above, only value writes the empty string back into the box. defaultValue already did its one job when the page opened.

There is one more thing to notice. The message box in Principle 1 had onChange, and it was still uncontrolled. onChange only reports. Only value decides whether a box is controlled.

One last note for readers who know HTML. In HTML, you write the starting text of a text area between its tags. React does not support that. The box still shows the text, but React prints a red error in the Console. The error tells you to use defaultValue or value instead. So in React, a text area gets its text from one of these two props, just like an input.

Principle 2

value: React Writes State into the Box After Every Render

When our code must change what the box shows, such as emptying it after Send, give the box value from state.

A box without value keeps its own text. defaultValue only sets the starting text, so after Send the count says zero while the old message stays in the box. With value from state, React writes the state into the box after every render. Then saving an empty string empties the box too, and state becomes the single source of truth.

✓ DO THIS
1<textarea value={message} onChange={e => setMessage(e.target.value)} />
Setting message to an empty string now empties the box
✗ DO NOT DO THIS
1<textarea defaultValue="" onChange={e => setMessage(e.target.value)} />
WRONG starting text only, so the box keeps its text after Send

Refusing a letter on purpose: the 200 limit

React puts back whatever state says. So can our code refuse a letter on purpose? Yes. Our count already promises a limit of 200 characters, so let's make the box keep that promise. We add one check to the message handler:

src/components/ContactForm.jsx
7 function handleMessageChange(e) {
8 if (e.target.value.length <= 200) {
Saves the text only while it fits
9 setMessage(e.target.value);
10 }
11 }

Suppose the box already holds 200 characters, and the user types one more. Here is what happens:

  1. The browser puts the extra letter into the box.
  2. React calls handleMessageChange. The new text is 201 characters long, so the handler does not call setMessage.
  3. message still holds the 200 characters.
  4. React writes those 200 characters back into the box, and the extra letter disappears.

This is the freeze from the start of this principle, used on purpose. The box accepts a letter only when our code saves it.

The handler must save e.target.value right away

The handler has two more rules. It must save the text right away, and it must save exactly e.target.value. Here is a Name handler that breaks the first rule. It saves the text later, inside a timer:

2 setTimeout(() => setName(e.target.value), 100);
WRONG the state waits, but React puts the old text back right away
3}
4

The user types, and the box still refuses every letter. The handler does run, so why? Here is the order:

  1. The user presses a key, and the browser shows the letter in the box.
  2. React calls handleNameChange, but the handler only starts a timer.
  3. The handler ends, and name still holds the old text.
  4. State did not change, so React writes the old text back into the box.
  5. A moment later, the timer runs and reads e.target.value. That is the same box, and it now holds the old text again.
  6. So setName saves the old text, and nothing changes.

This box refuses letters just like a box with no onChange. This time, though, the Console stays quiet, because the box does have a handler. React's documentation says the state update cannot wait. It must happen inside the handler, right away.

The second rule is broken by a handler that saves a changed copy of the text. One example is a handler that turns every letter into a capital with toUpperCase. The browser has just shown one text, and React then writes a different text into the box. React's documentation lists this as a cause of a caret that jumps while the user types.

So keep the handler simple: save exactly e.target.value, right away. If you need to refuse a letter, refuse the whole change with an if, as the 200 limit does.

Principle 3

Read-Only: value Without onChange Freezes the Box

Every box with value also needs an onChange handler that saves the new text, exactly as typed, right away.

With value, React writes the state into the box after every key. If no handler saves the new letter, state never changes, so React puts the old text back, and the Console shows the read-only field error. The same freeze happens when the handler waits inside a timer. A box that should be frozen on purpose says so with readOnly.

What value means on a menu

On a <select>, value says which option is chosen. It must match the value of one of the options inside. Each <option> has two texts:

  • The text between its tags, such as Banana, is what the user reads.
  • Its value, such as banana with a small b, is the string the menu reports to our code.

The user reads Banana, but our code receives banana with a small b. Where did that string come from? The browser supplies it:

  1. The user picks Banana.
  2. The menu's value becomes the value of that option, which is banana.
  3. React calls onChange, and e.target.value is banana.
  4. setFruit saves banana, and React writes it back into the menu, so Banana stays chosen.

What checked means on a tick box

A tick box has no text to show. It is either ticked or not. So it does not use value. It uses checked, a React prop that holds true or false. After every render, React makes the box ticked or unticked to match.

The handler reads e.target.checked, which the browser supplies. It is the tick right after the click: true if the box is now ticked, and false if not.

For a tick box that only needs a starting tick, React has defaultChecked, which works like defaultValue. A tick box with checked and no onChange freezes too, just like the frozen text box of Principle 3. React prints the same read-only error, but this time it names checked and defaultChecked.

Where did undefined come from?

Our code never writes undefined. JavaScript supplies it. Here, useState receives no starting value, and in JavaScript a missing argument is undefined. So React saves undefined as the first state of city.

Why React warns when the box works

The box works, so what is React complaining about? Here is what happens, in order:

  1. The page opens. city is undefined, so the box gets no real value at all.
  2. React treats the box as uncontrolled, the same as a box with no value prop.
  3. The user types a. onChange runs, and setCity saves the string a.
  4. React renders again. Now the box has a real value, the string a.
  5. The same box has switched from uncontrolled to controlled. React cannot tell which one we meant, so it warns.

React's documentation explains it the same way. You cannot give a box an undefined value first and a string later. In its words, "React won't know whether you want the component to be uncontrolled or controlled." A box must stay one kind for its whole life.

Think of a notebook that is suddenly declared a whiteboard in the middle of the lesson. The student was writing freely, and now the teacher wants to write on the same page. Nobody knows who owns the page any more.

Starting with nothing and starting with an empty string are NOT the same

Both versions draw the same empty box when the page opens. But they split at step 1. When the state starts as an empty string, value is a real string from the very first render. So the box is controlled from the start, and it never switches.

The opposite pair really is the same. An undefined value and no value prop at all are the exact same thing for React. Both give an uncontrolled box.

Interview PrepFor the Interview

The Interview Question: How do you make an input, textarea, or select fully controlled by React state?

How to Answer Clearly in 30 Seconds

"A controlled field takes what it shows from state and reports every change back to state. I give it two props: value from state, and onChange, which saves e.target.value with the setter. React's onChange fires on every key, like the browser's input event, not like the change event. After every render, React writes the state into the field, so state is the single source of truth. To empty the box after Send, I only set the state to an empty string. Four rules keep this working:

  1. value always comes with onChange. Without it, React puts the old text back after every key and logs a read-only field error. The handler saves exactly e.target.value, right away.
  2. defaultValue is not controlled. It only sets the starting text, and the box keeps its own text after that.
  3. Menus and tick boxes use the same pair. A <select> takes value on the select itself, never selected on an option. A checkbox takes checked and reads e.target.checked.
  4. Start with an empty string. A controlled field must get a string from the first render. If it starts as undefined, React warns that an uncontrolled input is changing to controlled."

Three Classic Follow-Up Questions Interviewers Ask

  1. "What is the difference between a controlled and an uncontrolled input, and when would you use each?"
    A controlled input gets value from state, or checked for a checkbox, and reports with onChange. React forces it to show what state holds. An uncontrolled input has no value. It may get a starting text from defaultValue or defaultChecked, and after that it keeps its own text inside the browser. A controlled field is worth it in two cases. The page needs the text on every key, such as for a live count. Or our code must change the field, such as emptying it after Send. A field can never be both, and it cannot switch over its life. Choosing between controlled fields and reading an uncontrolled form with FormData at submit time is the topic of Lesson 40.
  1. "Why does my input's caret jump, or why does typing feel slow?"
    A caret jumps when the handler does not save exactly e.target.value right away. Two common causes are saving a changed copy, such as with toUpperCase, and saving later, inside setTimeout. Another cause is a field that React removes and adds again on every key. That happens when a component is defined inside another component, as in Lesson 04, or when its key changes, which Lesson 25 covers. Slow typing has a different cause. Every key sets state, and every state change renders the component that holds it. If that component draws a large page, every key makes React render all of it again. The fix is to move the field and its state into a small component of its own, so each key renders only that small part. useDeferredValue, from Lesson 68, is another tool for this.
  1. "How do you control a select, a checkbox, and a field whose value comes from an API?"
    A <select> gets value on the select, and it must match the value of one <option>. Writing selected on an option is not supported in React. A select with multiple takes a list of values instead of one string. A checkbox gets checked, which must always be true or false, and its handler reads e.target.checked, because e.target.value on a checkbox is a fixed string such as on. A value from an API is often null or undefined until it arrives. So start the state with an empty string, or write value={someValue ?? ''}. The ?? uses the empty string whenever the left side is null or undefined, so the field always gets a string.
