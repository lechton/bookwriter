The Trigger, Render, and Commit Lifecycle

Interview Question · ❱ CORE

What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?

OverviewHow a Screen Update Reaches the Page

The three steps of every React update

Before we build a multi-file project, look at what happens inside a tiny component when a user clicks a button to add a ticket:

When you click the button in the browser, the text on the screen changes from Tickets: 1 to Tickets: 2 in the blink of an eye. Because that change happens so fast, two things are easy to misunderstand at first:

  • First, does setCount change the page right on that line? It looks like it works that way at first, but it does NOT touch the DOM on that line! Calling setCount only places a request in React's queue. While handleAdd is still running, the paragraph on the page still holds Tickets: 1.
  • Second, does "rendering" mean drawing pixels or rebuilding the whole DOM? In everyday web talk, people say "rendering" when the browser draws pixels on the screen. Many also assume re-rendering a component destroys and recreates all of its HTML tags. It may sound the same, but in React they are NOT the same thing!

Every screen update in React passes through three separate steps in order, followed by the browser drawing the screen at the end. The official React documentation compares these steps to a waiter and a chef working together in a restaurant kitchen, where the guest's table is the browser screen:

  1. Step 1 is Triggering a render: In everyday English, to trigger something means to set a process in motion. In the restaurant, the waiter takes the guest's order at the table and walks the order slip into the kitchen. In React, a trigger is either the app starting up for the first time or a state setter queueing an update after a click.
  2. Step 2 is Rendering the components: In the kitchen, the chef reads the order slip and prepares the dish. In React, rendering simply means React calling your component function in memory to calculate the JSX it returns. It does not touch the guest's table yet.
  3. Step 3 is Committing to the DOM: In everyday English, to commit means to carry out a change for real. The waiter brings the finished dish out to the guest's table and updates only the plate that changed. Everything else on the table stays untouched.
  4. After Step 3 comes Browser Paint: After React finishes updating the real DOM nodes, the browser draws the updated pixels onto the screen so you see the new number:

Every render you will ever see in a React app comes from one of those two triggers:

  • Way 1 is the initial render: When the page first loads, your startup file calls root.render with <App />. That triggers the very first render of your application.

Why the lifecycle steps matter on a real page

Suppose we are building a ticket counter for a city box office page. The page has a main heading and a card for concert tickets. Inside the card sit the ticket count, a text box for a seat note, and a button to add a ticket.

When developers treat a state update as a single instant event instead of three separate steps, three practical questions immediately trip them up:

  1. If you read the page text from the DOM on the line right after calling setCount, why does the DOM still show the old count?
  2. When one component updates its state, does React re-run the whole app from the top, or only that component and its children?
  3. When a component function runs again from top to bottom, why doesn't React destroy the input box inside it and erase what the buyer typed?

Walking through Trigger, Render, and Commit one step at a time answers all three questions.

Three Principles of the Trigger, Render, and Commit Lifecycle

PRINCIPLES

Every update in React follows the same strict timeline from Step 1 to Step 3:

  1. Principle 1: Triggering a Render on Startup or State Update: A render starts only when the app first mounts on startup or when a state setter queues a re-render in a mounted component. The state setter waits for the event handler to finish first. So reading the live DOM on the next line of the handler still sees the old page text.
  2. Principle 2: Rendering by Calling Component Functions in Memory: Rendering means React calling your component functions in memory to calculate what the UI should look like. On startup, React calls the root component and every child down the tree. On a state update, React calls the component whose state changed and every child inside it. It skips parent components above it and touches zero DOM nodes.
  3. Principle 3: Committing Minimal DOM Changes Before Browser Paint: After rendering finishes in memory, React commits the result to the browser DOM. On startup, it inserts every newly created DOM node. On a re-render, it updates only the DOM nodes that changed from the previous render. Unchanged elements such as an input box keep their typed text, and then the browser paints the screen.

Here is the complete overview of all three principles before we walk through each one:

A component renders only when root.render starts the app or when a state setter queues a re-render for after the event handler finishes.

"Rendering" in React means one very specific thing: React calling your component functions to ask what JSX markup they return!

When developers first trace Step 2, two questions immediately come up:

  • First, which component functions does React call when TicketCounter updates its state? You might think React re-runs the whole app from App down, or that it calls only TicketCounter and stops there. It may seem like one of those must happen, but it is NOT the same thing!
    • On the initial render, React starts at the very top of the tree. It calls App first, then TicketCounter. Finally, it calls the child component OrderSummary.
    • On a re-render, React starts at the component whose state updated, which is TicketCounter. It skips App above it and calls TicketCounter. Then it sees <OrderSummary count={count} /> in the returned JSX and recursively calls OrderSummary.
  • Second, does Step 2 change the DOM while those functions are running? No! While the counter and summary components run with the new count of 2, the live DOM on the page still says Tickets: 1. Step 2 only calculates JSX in memory.

Look at the two words that describe how Step 2 works:

  • What does "recursive" mean? In everyday English, a step is recursive when it repeats the exact same rule on whatever is inside it. When the ticket counter returns <OrderSummary />, React calls OrderSummary next. If OrderSummary returned another child component, React would call that child too. It continues down the tree until only built-in HTML tags remain.
  • What is a "pure calculation"? A calculation is pure when it takes inputs, such as props and state, and computes a result in memory without changing anything outside the function. Step 2 only computes React element objects in memory and touches zero DOM nodes:

Principle 2

Rendering by Calling Component Functions in Memory

In the Render phase, React calls your component functions in memory: from App down on startup, and from the updated component down its children on a re-render.

Never confuse React rendering with changing the browser DOM. During Step 2, React is only calling your JavaScript functions in memory to ask what JSX elements they return. Why does 'Window seat' stay safe inside the input box even when TicketCounter re-renders ten times in a row?

  • Remember that returning the <input> tag in Step 2 only creates a lightweight JavaScript object in memory. It does not create a new browser DOM node!
  • When React enters Step 3: Commit, what it does depends on whether this is the initial render or a re-render:

1. On the initial render, the #root container on the page is empty. React creates the real browser DOM nodes for every element in the tree and puts them into #root using the browser's appendChild DOM method.

2. On a re-render, React compares the new JSX descriptions from Step 2 against the previous render. It sees that the section, the heading, the input box, and the button have not changed at all! Only the number inside <p class="count-text"> changed from one to two.

3. So React commits only that single text change to the real DOM and leaves the existing <input> DOM node and its 'Window seat' text untouched.

  • What happens after Step 3 finishes? Once React commits that single text change to the DOM, the browser recalculates the layout and draws the new pixels on the screen. That final step by the browser is called Browser Paint, which CSS tools sometimes call "browser rendering":

Principle 3

In the Commit phase, React inserts all nodes with appendChild on startup, and on a re-render updates only the changed DOM nodes before the browser paints.

Interview PrepFor the Interview

The Interview Question: What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?

How to Answer Clearly in 30 Seconds

"Every screen update in React flows through three phases in order: Trigger, Render, and Commit, followed by Browser Paint at the end.

  1. Step 1 is Trigger: Only two things trigger a render. The initial render runs when the app starts via createRoot and root.render. A re-render runs when a mounted component calls a useState setter like setCount. Calling setCount only queues a render request for after the event handler finishes. It does not mutate the DOM on that line.
  2. Step 2 is Render: Rendering in React means React calling your component functions to compute JSX elements in memory. On the initial render, React calls the root component App and every nested child down the tree. On a state-triggered re-render, React starts at the component whose state updated and recursively calls the child components it returns, skipping unaffected parent components above it. Rendering is a pure calculation in memory that touches zero DOM nodes.
  3. Step 3 is Commit, followed by Browser Paint: In the Commit phase, React applies the result to the real browser DOM. On the initial render, it inserts all newly created DOM nodes into the container using appendChild. On a re-render, it compares the new render output with the previous render output and mutates only the specific DOM nodes or attributes that actually changed. Unchanged sibling elements like an <input> and its typed text stay untouched. Only after Commit finishes does the browser repaint the screen in Browser Paint."

Three Classic Follow-Up Questions Interviewers Ask

  1. "If you call setCount in a click handler and read the DOM on the next line, what does it return? What if you pass the same value?"
    Reading the DOM on the next line of the click handler returns the old DOM text, such as 'Tickets: 1'. That happens because calling setCount is only Step 1: Trigger. It queues a render request in React and returns immediately without touching the DOM. React waits for the event handler to finish before running Step 2 and Step 3. If you call setCount with the exact same value that is already in state, React compares the two values with Object.is. Because they match, React bails out and skips re-rendering the component and its children.
  2. "When a child component like TicketCounter calls setCount, does React re-render App above it, or only TicketCounter?"
    Neither App nor only TicketCounter. React starts the re-render at the component whose state updated, so App above it is not called. React calls TicketCounter and looks at the JSX elements it returns. Then it recursively calls any child components inside that returned JSX, such as OrderSummary, until only built-in HTML tags remain.
  3. "Is 'React rendering' the same thing as 'browser rendering', and why doesn't re-rendering TicketCounter wipe out text typed into an <input> inside it?"
    No. React rendering is Step 2, where React calls your component functions in JavaScript to calculate JSX objects in memory. Browser rendering, or Browser Paint, happens after Step 3, when the browser draws pixels on the screen after React commits changes to the DOM. Re-rendering TicketCounter does not wipe out an <input> inside it because Step 2 only creates a lightweight JavaScript object in memory. In Step 3, React compares the previous and next element trees and sees that <input /> is at the same spot with the same attributes. So React leaves the existing <input> DOM node and its typed text untouched, and updates only the text node that changed.
