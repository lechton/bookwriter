Connecting a Component to an External System with useEffect

Interview Question · ❱ CORE

How do you connect a component to an external system, and how do you disconnect it?

How a Component Starts Something When It Appears, and Stops It When It Leaves

Code that runs because the component is on the screen

Think of a counter on a page that counts the seconds by itself. When the counter appears, it shows zero and goes up by one every second. When the user hides it, it stops. The user never clicks anything inside the counter to start it. So where does the code that starts the timer go, and who stops it?

Until now, a component has held two kinds of code:

  1. Rendering code, at the top level of the component. It takes props and state and returns JSX. Lesson 14 showed that it must be pure. The docs put it this way: "Like a math formula, it should only _calculate_ the result, but not do anything else."
  2. Event handlers, such as the function in onClick from Lesson 11. In the docs' words, they "do things rather than just calculate them", and they run because of "a specific user action", such as a click on a button or typing in a box.

Our counter fits neither. Starting a timer is not a calculation, so it cannot sit in the rendering code. And no click by the user causes it, so there is no event handler to put it in. The timer must start because the counter is on the screen, "no matter which interaction caused the component to appear". The docs give a chat page as their example: the chat must stay connected to the chat server for as long as the user can see it.

React has a third place for exactly this case, called an Effect. The docs say: "Effects let you specify side effects that are caused by rendering itself, rather than by a particular event." In plain words, the code runs because React has put the component on the screen, not because the user did something.

Switching the light on, and switching it off

When we walk into a dark room, we switch the light on. When we leave, we switch it off. Whoever switched the light on is the one who switches it off.

A component works the same way. When our counter appears, our code starts a timer. When the counter leaves the page, React removes the DOM nodes it built from our JSX, here the <h1> with the number. But React did not start the timer. Our code did, by calling the browser's setInterval, as in Lesson 30. So React does not stop the timer either. Our code has to stop it, with clearInterval.

The docs have a name for things like this timer: "These systems aren't controlled by React, so they are called external." An external system is any piece of code that React does not control. The docs list the usual ones: a timer started with setInterval, an event listener added with window.addEventListener, a connection to a chat server, and a widget from a library that is not written in React.

The same timer, started for two different reasons

The stopwatch in Lesson 30 also called setInterval. There, the call sat in the handler of the Start button. In this lesson, the counter calls setInterval inside an Effect. It may look the same, or work the same at first, but it is NOT the same thing! Both start the same kind of browser timer. The stopwatch's timer starts because the user clicked Start. The counter's timer starts because the counter appeared on the page. Principle 5 puts the two side by side.

What is at stake

What is at stake is a timer that keeps running after the user can no longer see it. On our example page, each mistake of this lesson shows up at once:

  1. With the timer started in the body of the component, the number climbs faster and faster.
  2. With the timer in an Effect and no code that stops it, the number goes up by two every second in development. The docs say it plainly: "instead of incrementing once per second, it increments twice."
  3. In production, the number goes up by one, and the page looks right. But after the user hides the counter, the timer keeps running, and each time the user shows the counter again, one more timer starts. The docs say the same of the chat: "the connections would keep piling up."

Readers usually go wrong in four ways. They start the timer or the connection in the body of the component. They read the empty array [] as "run once", and then fight React when it runs the Effect twice in development, often with a ref. They write the code that starts the timer and forget the code that stops it. And they put work that a click causes, such as buying a product, into an Effect.

Five Principles of Connecting a Component to an External System

PRINCIPLES

An Effect is code that React runs because the component is on the screen. Its setup starts the connection to the external system, and its cleanup ends it. Five principles follow from that:

  1. Principle 1: useEffect Starts the Timer After the Commit: The body of the component runs during every render and must only calculate the JSX. Code that must run because the component is on the screen goes inside useEffect, and React runs it after the commit.
  2. Principle 2: [] Starts the Timer Only on Mount: The second argument of useEffect lists the values the Effect reads. With no array, the Effect runs after every commit. With [], it runs only when the component appears.
  3. Principle 3: The Cleanup Function Stops the Hidden Counter's Timer: The function that the setup returns is the cleanup. React calls it before the Effect runs again, and one last time when the component leaves the page.
  4. Principle 4: A Ref Guard Leaves the Timer Running: In development, React runs the setup and the cleanup one extra time to test the cleanup. What this test shows is fixed with a cleanup, not with a ref that blocks the second run.
  5. Principle 5: The Buy Click Sends the Order, Not an Effect: Work that a click causes, such as buying, goes in the handler of that click. An Effect is only for work that being on the screen causes.

Here is the complete map of those five principles before we walk through each one:

What useEffect is

useEffect is a Hook, like useState, and we import it from react. Its first argument is a function. The docs call it the setup function: "The function with your Effect's logic". Our code creates this function during the render and hands it to React. React keeps it and calls it after the commit. Our code never calls it.

React's docs write Effect with a capital E for this meaning: a side effect caused by rendering. Here the Effect reaches outside React, into the browser, which decides where the cursor is. For the box, that means one thing: whenever the box appears, the cursor is in it.

The user clicks the show button. The number starts to climb, then climbs faster and faster, and the Console prints more Tick lines every second. Here is why:

  1. React calls Counter for the first render. The body calls setInterval, and one timer starts.
  2. In development, <StrictMode> calls the body twice, as Lesson 14 showed, so a second timer starts.
  3. A second later, a timer calls onTick. The setter asks for a render, and React calls Counter again.
  4. The body calls setInterval again, and more timers start.
  5. Every render adds timers, and every timer asks for more renders.

Starting a timer is a side effect, so it does not belong in the rendering code. The docs say the same of a chat connection: connecting to a server is not a pure calculation, it is a side effect, so it cannot happen during rendering. They state the rule in four words: "Rendering code must be pure."

The same mistake hits a page with a live comments feed. A developer subscribes to the feed in the body of the component. Each change of state renders the component again, and each render opens one more subscription. After six renders, the page holds six subscriptions to the same feed.

Principle 1

Effects: useEffect Starts the Timer After the Commit

Code that must run because the component is on the screen goes inside useEffect; React runs it after the commit, while the body of the component runs during every render and must only calculate the JSX.

A timer, a subscription, or a call to focus written in the body runs during rendering. On the first render, the DOM node is not there yet, and every later render starts the side effect again. Inside useEffect, our code hands React a setup function, and React calls it after the commit, when the page is already on the screen.

Three ways to write the second argument

useEffect takes a second argument: an array. The docs show three ways to write it:

1useEffect(() => { /* ... */ });

3useEffect(() => { /* ... */ }, [a, b]);

It may look the same, or work the same at first, but it is NOT the same thing! No array and an empty array differ by two characters. The docs say it directly: "The behaviors without the dependency array and with an empty [] dependency array are different." With no array, the Effect runs after every commit. With [], it runs after the first commit only, when the component mounts.

What the array lists

The array is called the dependency array, and the values in it are the dependencies. In the docs' words, it is "The list of all reactive values referenced inside of the setup code": every prop, state variable, or other value from the component that the Effect reads. Lesson 35 covers reactive values in full.

We do not pick these values. The docs: "you can't "choose" your dependencies." The code inside the Effect decides them. After each commit, React compares each dependency with its value from the last render, using Object.is, the same check React uses on the value given to a setter. React skips the Effect only if every dependency has exactly the same value as before.

The docs show this with a video player. Its Effect plays or pauses the video, depending on the isPlaying prop:

The docs' VideoPlayer: the Effect reads isPlaying, so isPlaying is in the array
1useEffect(() => {
2 if (isPlaying) {
3 ref.current.play();
4 } else {
5 ref.current.pause();
6 }
7}, [isPlaying]);
The Effect reads isPlaying, so it runs again whenever isPlaying changes

With [] instead, the Effect would never see a new value of isPlaying. A linter, a tool that reads our code before it runs, catches this. Its exhaustive-deps rule checks that every dependency is listed, and the docs show its message: React Hook useEffect has a missing dependency: 'isPlaying'.

count + 1 and c => c + 1 inside the Effect

The updater is what makes [] honest here. Compare two ways to add one inside the Effect:

It may look the same, or work the same at first, but it is NOT the same thing! Both add one on the first tick. With count + 1, the Effect reads count, so count is a dependency. With the updater, the Effect reads no state at all, and [] tells React the truth. The useEffect reference says: "Now that you're passing c => c + 1 instead of count + 1, your Effect no longer needs to depend on count."

A common mistake starts from count + 1 with [], and the page stops at 1:

  1. A developer calls setCount with count + 1 in an Effect with [].
  2. The linter reports that count is missing, with a message like the one for isPlaying.
  3. The developer turns the lint rule off for that line.
  4. The Effect keeps the count of the first render, which is 0, because each render keeps its own values, as Lesson 15 showed. So every second, it sets count to 0 + 1, which is 1.

The docs: "By suppressing the linter, you "lie" to React about the values your Effect depends on." Putting count in the array also works, but then the Effect runs again on every change of count, and the reference warns that "specifying count as a dependency always resets the interval." The updater is the clean fix.

Principle 2

The second argument of useEffect lists every value from the component that the Effect reads; with no array the Effect runs after every commit, with [] only after the first commit, and with [a, b] also after any commit where a or b changed.

Section 3 · Principle 3The Cleanup Function Stops the Hidden Counter's Timer

The setup returns a function that stops the timer

setInterval returns an interval ID, and clearInterval with that ID stops the timer, as Lesson 30 showed. Inside an Effect, the setup function can return a second function, and React calls it when the timer must stop:

The setup returns the function that stops its timer
1useEffect(() => {
2 const intervalId = setInterval(onTick, 1000);
The setup starts the timer
3 return () => clearInterval(intervalId);
The cleanup stops that same timer
4}, []);

This returned function is the cleanup function. Our code writes it, and React calls it. The docs: "React will call your cleanup function each time before the Effect runs again, and one final time when the component unmounts". A component unmounts when React removes it from the page. On our page, that happens when the user clicks the hide button: show becomes false, and {show && <Counter />} gives nothing.

This is the light in the room from the start of this lecture. Our setup started the timer, so our cleanup stops it. The docs list the usual pairs: ""connect" needs "disconnect", "subscribe" needs "unsubscribe", and "fetch" needs either "cancel" or "ignore"." On our page, setInterval needs clearInterval.

Hiding the counter does not stop its timer

The counter with [] from Principle 2 has no cleanup. When the user hides it, the number disappears, and it looks as if everything stopped. It may look the same, but it is NOT the same thing! The <h1> is gone, and the timers are still running:

  1. The counter is on the page, and its timers call onTick every second.
  2. The user clicks the hide button. React removes the <h1>.
  3. Nothing calls clearInterval, so the timers still call onTick, and the Console still prints Tick every second.
  4. The user clicks the show button again. A new counter starts from 0, because a component removed from the page loses its state, as Lesson 25 showed. Its setup starts new timers, while the old ones still run.
  5. Each click on the show button adds more timers that nothing will ever stop.

Principle 3

Cleanup: The Cleanup Function Stops the Hidden Counter's Timer

The function that the setup returns is the cleanup function; React calls it before the Effect runs again and one final time when the component unmounts, so it must stop or undo what the setup started.

When a component leaves the page, React removes the DOM nodes it built from our JSX. It does not stop a timer, a listener, or a connection that our setup started, because React did not start them. The cleanup stops them: clearInterval for setInterval, removeEventListener for addEventListener, and disconnect for connect.

The extra run is a test

The extra setup and cleanup in development is a test that React runs on purpose. The useEffect reference calls it a stress-test: "This is a stress-test that verifies your Effect's logic is implemented correctly." It shows us at once, on our own screen, the bug that users would meet later. The docs' Challenge on the interval says: "React's behavior is not the cause of the bug: the bug already exists in the code. React's behavior makes the bug more noticeable."

So the docs ask a different question: "The right question isn't "how to run an Effect once", but "how to fix my Effect so that it works after remounting"." The answer is a cleanup, so that setup, cleanup, setup looks to the user exactly like one setup. With the cleanup from Principle 3, the user sees one step per second in development and in production.

Turning off <StrictMode> hides the test the same way the ref guard does. The docs: "You can turn off Strict Mode to opt out of the development behavior, but we recommend keeping it on." Lesson 47 covers Strict Mode in full.

For the Interview

The Interview Question: How do you connect a component to an external system, and how do you disconnect it?

How to Answer Clearly in 30 Seconds

"With an Effect. An external system is anything React does not control, such as a timer, a listener on window, or a chat server. I call useEffect at the top level of the component and pass it a setup function that connects, for example by calling setInterval. React runs it after the commit, never during rendering, because rendering must stay pure. The setup returns a cleanup function that disconnects, here clearInterval with the interval ID. Three rules keep it right:

  1. The dependency array lists what the Effect reads: no array runs it after every commit, [] only on mount, and [a, b] also when a or b changed. The exhaustive-deps lint rule checks the list, and I never turn it off.
  2. The cleanup undoes the setup: React calls it before the Effect runs again and one final time when the component unmounts. Without it, the timer runs on and connections pile up.
  3. Only work caused by being on the screen: a purchase caused by a click goes in the click handler, not in an Effect."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why does my Effect run twice in development, and how do I make it run once?"
    In development, Strict Mode remounts every component once right after it first mounts, so React runs setup, cleanup, setup. The useEffect reference calls it "a stress-test that verifies your Effect's logic is implemented correctly." The docs say the right question is not how to run an Effect once, but how to fix the Effect so it works after remounting. The fix is a cleanup, so that the user cannot tell one setup from setup, cleanup, setup. A ref guard or turning off <StrictMode> only hides the test, and the bug stays for users who leave the page and come back. In production there is no extra run. Lesson 47 covers Strict Mode in full.
  2. "Can I leave a value out of the dependency array to stop the Effect from running again?"
    No. The docs: "you can't "choose" your dependencies." The code inside the Effect decides them, and suppressing the linter means you "lie" to React, so the Effect keeps the values of an old render. For our counter, count + 1 with [] stops the page at 1. The fix is to change the code so that it no longer reads the value, such as the updater c => c + 1. A ref from useRef and a setter from useState keep the same identity on every render, so they can stay out: "If the linter lets you omit a dependency without errors, it is safe to do." Lesson 36 shows useEffectEvent, and Lesson 37 removes object and function dependencies.
  3. "Does an Effect run before or after the browser paints the screen?"
    After the commit, and usually after the paint. The useEffect Caveats say that when the Effect was not caused by a click, "React will generally let the browser paint the updated screen first before running your Effect." When it was caused by a click, "React may run your Effect before the browser paints the updated screen". When the work must happen before the paint, for example to measure a tooltip before the user sees it in the wrong place, the tool is useLayoutEffect, which Lesson 49 teaches. Effects also never run during server rendering, as Lesson 102 shows.
