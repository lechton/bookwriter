Well, in both branches of the ? :, App returns a <div> whose first child is a Counter. The click on Next only gives that same Counter a new person prop, so React keeps its count.

React works this way because the state is not kept inside the JSX tag, and not inside the component function either. React holds the state itself, and it ties each piece of state to the place where the component sits in the UI tree, such as "the first child of the <div>". Think of a letter and the address on its envelope. The post office delivers a letter to an address, not to a person. What is at stake

The key idea of this lesson is one rule. React keeps a component's state while the same component stays at the same position. When React removes the component, or puts a different component at that position, the state is gone.

What is at stake is the text the user writes. On the page of this lesson, the user writes "Happy birthday, Anna!" to a friend, then clicks the button for Ben. The same text now sits under the heading "Note to Ben", right above a button that says "Send to Ben". In another case, the user's whole note disappears the moment a tip appears above it. No line of our code moves the text or clears it.

Readers usually go wrong in three places:

  • They think the state lives inside the component function, or inside the JSX tag. It lives in React, at a position.
  • They think a new prop makes a new component. A new prop at the same position reaches the same component.
  • They read the if and the ? : in their code. React never sees those. It sees only the tree that the code returns.

Four Principles of Keeping and Resetting State

PRINCIPLES

React holds every piece of state at a position in the UI tree. On every render, React compares the new tree with the old one, position by position. Four practical principles follow from that:

  1. Principle 1: Closing the Note Throws Away Its Text: When React removes a component from the tree, it destroys the component's state. When the component comes back, its state starts from scratch.
  2. Principle 2: Switching to Ben Keeps Anna's Text: The same component at the same position keeps its state, even when its props change, and even when the code writes two separate tags in two branches.
  3. Principle 3: The Tip Box Around the Note Erases It: A different component type at a position, such as a <div> where NoteBox was, destroys the old component and the state of everything inside it. To keep state, the tree must keep the same shape from one render to the next.
  4. Principle 4: key={friend} Gives Ben an Empty Note: A key becomes part of the position. When the key changes, React creates a new component with new state and new DOM elements.

Here is the complete map of those four principles before we walk through each one:

This is a common mistake on real pages. A developer shows a panel only while a condition is true, with &&. Principle 1

Removed From the Tree: React Destroys the State

React keeps a component's state while the component is rendered at its position in the UI tree; when React removes the component, it destroys the state, and when the component comes back, its state starts from scratch.

The text is not kept in the JSX tag or in the NoteBox function. React holds it at the position where NoteBox was rendered. When the user closes the note, nothing is rendered at that position, so React throws the text away, and the reopened note starts empty. When the text must survive closing, keep it in App, which stays on the page, and pass it down with a function that changes it, as Lesson 24 taught.

✓ DO THIS
1function App() {
2 const [isOpen, setIsOpen] = useState(true);
3 const [text, setText] = useState('');
4 return isOpen && <NoteBox text={text} onTextChange={setText} />;

2 const [isOpen, setIsOpen] = useState(true);

WRONG expecting the text to come back after isOpen goes false and true; the new NoteBox starts empty!

The same rule causes a well-known bug with forms that copy a prop into state, the mistake Lesson 22 showed. The form stays at the same position, so React keeps its state, and useState reads initialData.name only on the first render. React's docs describe the result: "the state updates but the form keeps showing the previous contact's details."

Principle 2

Same Position: A New Prop Keeps the Old State

When the same component is rendered at the same position, React keeps its state, even when its props change and even when the code writes two separate tags in two branches, because React matches the tree the code returns, not how the code is written.

When the user clicks Ben, NoteBox gets a new friend prop, but it is still a NoteBox at the same position. React keeps it and its text, so the note typed for Anna now sits under Ben's name. React never sees the if or the ? : in the code. It sees only the tree that the code returns.

The tip appears, and the box under it is empty. The tip line never touches the note, yet the note is gone. Here is what happens, in order:

  1. The user types Happy birthday, Anna!, and NoteBox holds it in text.
  2. The user clicks Show tip, and App sets showTip to true.
  3. React renders App again. The if wraps note in a <div>, so the position that held a NoteBox now holds a <div>.
  4. A <div> is a different type from NoteBox, so React removes the NoteBox and destroys its text.
  5. React builds the <div>, the tip line, and a new NoteBox inside the <div>, with text set to an empty string.

The new NoteBox comes from the same NoteBox function, but it now sits one level deeper, inside a new branch of the tree. It also happens the other way. When the user types a new note and clicks Hide tip, the <div> goes, a NoteBox takes the position again, and the note is lost a second time.

The fix: keep the tree the same shape

The tip has to appear without changing what sits at the note's position. Compare two ways to show the same tip above the same note:

Wrapping the note in a div, and placing the tip line above the note
1{isOpen && note}
Note is a div with the tip and the NoteBox when showTip is true: the text is gone
2{showTip && <p>Tip: say one thing you like about them.</p>}
The tip line keeps its own position
3{isOpen && <NoteBox friend={friend} />}
NoteBox keeps its position: the text stays

Both show the tip above the note. It may look the same, but it is NOT the same thing! With the wrapper, the note's position holds a <div> instead of a NoteBox, and the text is gone. With the tip line above the note, the NoteBox keeps its position, and the text stays.

The tip line does not push NoteBox to a new position when it appears. Why? Well, the line with showTip && always keeps its own place among the children of <main>. When showTip is false, that place holds false, which shows nothing, as Lesson 10 taught. So NoteBox is always the child right after it, whether the tip shows or not. React's docs give the same fix for a hint above a form, so that "Form always renders in the same position."

Principle 3

A Different Type at the Position: React Resets Everything Inside

When a different component type appears at a position, React destroys the old component and the state of everything inside it; to keep state, the tree must keep the same shape from one render to the next.

Wrapping the note in a <div> only when the tip is on puts a <div> where a NoteBox was. React removes the NoteBox with its whole subtree, and the user's text is gone. A conditional line placed next to the note keeps its own place, even when it shows nothing, so NoteBox stays where it was.

In both versions, the user clicks Anna's counter three times and then clicks Next.

When the page opens, both versions show Anna: 0, and the code differs by one attribute. It may look the same, or work the same at first, but it is NOT the same thing! Without a key, React finds a component by its order inside the parent. With a key, React uses the key as part of the position. React's docs: "Specifying a key tells React to use the key itself as part of the position, instead of their order within the parent." The key changed from 'Anna' to 'Ben', so for React this is a different position, and Ben's counter is a new one that starts at 0.

Think of the houses and letters from the start of this lecture. By default, React finds a house by its number on the street: the first house, the second house. A key writes a name on the door. When the name on the door changes, it is a different home, even at the same number. React's docs say it this way: "A key lets you specify a named position instead of relying on order." The docs call this giving each component "an explicit identity with key".

This is not a new kind of key. Yes, it is the exact same thing! It is the same key you wrote on each item inside .map in Lesson 18. React's docs: "Keys aren't just for lists!" In a list and outside one, the key tells React which component is which.

Coming back to Anna: her note is gone too

Now the user clicks Anna to go back. Anna's note is empty as well. You might expect the key 'Anna' to bring her note back, so here is what happens, in order:

  1. The user types Happy birthday, Anna! into the NoteBox with the key 'Anna'.
  2. The user clicks Ben, and App sets friend to 'Ben'.
  3. React renders App again. The NoteBox now has the key 'Ben', which is a different position for React.
  4. React removes Anna's NoteBox and destroys its text. It builds a new NoteBox for Ben, with an empty text and new DOM elements.
  5. The user clicks Anna. The key is 'Anna' again, but Anna's old NoteBox was destroyed in step 4.
  6. React builds a new NoteBox for Anna, with an empty text.

The key does not store anything. It only tells React whether this is the same component as before. React's docs: "Toggling between them resets their state over and over." Principle 1 already showed why: a removed component's state is destroyed. To keep each friend's note and still give each friend a fresh box, the notes must live in a component that stays on the page, such as App. The interview section below shows how.

Two ways to reset the note, and one wrong way

React's docs give two ways to reset a component at the same position. The first is the key. The second renders each friend's note at its own position:

One NoteBox with key={friend}, and two NoteBox tags at two positions
1{isOpen && <NoteBox key={friend} friend={friend} />}
One tag: a new NoteBox for each friend
2{isOpen && friend === 'Anna' && <NoteBox friend="Anna" />}
Anna's note at its own position
3{isOpen && friend === 'Ben' && <NoteBox friend="Ben" />}
Ben's note at the next position

On this page, both ways give the same result: every switch gives the user a fresh note. The docs call the second way "convenient when you only have a few independent components rendered in the same place". With two friends it works. With twenty friends it needs twenty lines. The docs call the key "more generic", and it needs one tag for any number of friends. On real pages, the key is usually an id, such as key={contact.id}. Here the two friends have different names, so key={friend} is enough.

A common wrong way is to clear the state from an Effect whenever the prop changes. An Effect is code that React runs after the page is already on the screen. So the page first shows the old note, and then renders a second time with the empty one. React's docs: "This is inefficient because ProfilePage and its children will first render with the stale value, and then render again." Every nested component with its own state would also need the same Effect. Effects come in Lessons 32 and 34. The key does the whole job in one place: "This and any other state below will reset on key change automatically."

Principle 4

A New key: React Creates a New Component

To reset a component at the same position on purpose, give it a key that changes when it should become a different one; React uses the key as part of the position, so a new key makes a new component with new state and new DOM elements.

A note to Anna and a note to Ben are two different notes. Without a key, React sees one NoteBox at one position and keeps the text. With key={friend}, each friend's note has its own position, so the click on Ben gives the user an empty box. A key works outside lists exactly as it does inside .map.

For the Interview

The Interview Question: Why does state sometimes vanish, or survive, when you did not expect it?

How to Answer Clearly in 30 Seconds

"React does not keep state inside the component function or inside the JSX tag. React holds it, and ties each piece of state to the component's position in the UI tree. On every render, React compares the new tree with the old one, position by position:

  1. Same component at the same position: React keeps the state, even when the props change, and even when the code writes two tags in two branches of an if. That is why a note typed for Anna can stay on screen when the user switches to Ben.
  2. Removed, or a different type at that position: React destroys the state of the component and of everything inside it. That is why a note vanishes when the user closes it, or when a condition wraps it in a new <div>.
  3. Reset on purpose: to give a component a fresh start, I give it a key that changes when it should become a different one, such as key={friend}. The key becomes part of the position, so React creates a new component with new state and new DOM elements."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why does a component defined inside another component lose everything the user typed on every update?"
    Every time the outer component renders, JavaScript creates a new inner function. React compares the type at that position with the type from the last render and finds a different function, so it treats it as a different component. React's docs: "You're rendering a different component in the same position, so React resets all state below." It is the same rule as a <div> that takes the place of a <section>. React's docs end with the advice: "Don't nest component definitions, or you'll reset state by accident."
  2. "Is key only for lists, and must every key be unique in the whole app?"
    No to both. A key works on any component: <NoteBox key={friend} /> resets the note whenever friend changes, just as a key inside .map tells React which row is which. And a key only has to differ among the children of the same parent. React's docs: "keys are not globally unique. They only specify the position within the parent." To put a key on a group of tags, write <Fragment key={...}>, because the short <>...</> form cannot take a key.
  3. "With key={friend}, how would you keep each friend's draft when the user switches back and forth?"
    The key destroys the old note, so the drafts must live somewhere that stays. React's docs name three ways. The most common is to lift the drafts up into App, as Lesson 24 taught: App keeps one draft for each friend and passes the right one down, while the key still gives each friend their own NoteBox. The second is to render every note and hide the ones not in use with CSS, which "can get very slow if the hidden trees are large and contain a lot of DOM nodes." The third is to save each draft in the browser's localStorage, so it survives even when the user closes the page. React also has <Activity mode="hidden">, which hides a part of the page and keeps its state, covered in Lesson 73.
