Reusing Logic Between Components with Custom Hooks

Interview Question · ❱ CORE

How do you extract and reuse stateful logic between components?

How Two Components Use the Same Logic

A status heading and a Save button that both follow the network

Picture a notes app that saves your work to a server. At the top of the screen, a heading reads Online. Below it sits a Save progress button.

  2. The button turns grey, reads Reconnecting..., and stops taking clicks.

When the Wi-Fi comes back, the heading reads Online again, and the button reads Save progress and takes clicks again.

The heading and the button are two different components, and they look nothing alike. Yet both need the same knowledge: is the network on right now? And both need the same code to keep that knowledge up to date: one state variable, and one Effect that listens to the browser (as seen in Lesson 32). So where should that code live?

There are two ways to give both components the same code:

  • Copy it into each component: the heading and the button each hold their own state variable and their own Effect, line for line the same. It works, but every later fix must be made twice.
  • Extract a custom Hook: to extract means to move the repeated code out of the components and into one function that both of them call. Here that function is useOnlineStatus. Our code writes it, not React, and inside it our code calls React's own Hooks, useState and useEffect. A function like this is a custom Hook (as seen in Lesson 38). Each component calls useOnlineStatus() and reads the value it returns, isOnline.

React's answer is the second way.

What is at stake

Copied code drifts apart, and the page ends up giving two answers to one question. Here is how it happens on our screen:

  1. The heading and the button each hold a copy of the same state variable and the same Effect.
  2. Both copies start by assuming that the network is on. That is wrong for a user who opens the app while already offline.
  3. A developer notices the problem and fixes the starting value in the heading's copy only. The button's copy is forgotten.
  4. Later, a user opens the app while offline.

The page now displays the wrong information. The heading reads Disconnected. Right below it, the button still reads Save progress and takes clicks. The Console shows no error and no warning.

localhost:5173
Disconnected
Save progress
Figure 4 — A user opens the app while offline, after the fix went into the heading's copy only: the heading says Disconnected, and the button still offers to save.

With a custom Hook, there is only one copy, so there is nothing to forget. The fix goes into useOnlineStatus once, and both components get it.

A custom Hook shares the code, not the value

This is the idea to remember from this lesson: a custom Hook shares the code that makes state, not the state itself. React's docs call that code stateful logic. Every component that calls useOnlineStatus() gets its own isOnline and its own Effect.

That sounds wrong at first, because the heading and the button change at the same moment. It looks as if both read one shared isOnline. It may look the same, but it is NOT the same thing! There are two isOnline values, one in each component. They agree only because both listen to the same browser events, and the browser tells both of them at once when the network goes off.

So a custom Hook cannot give two components one value. When two components must show one value that changes, such as whether the work was saved, that state moves up into their parent instead (as seen in Lesson 24).

Developers usually go wrong here in three ways:

  1. They copy the state variable and the Effect into a second component, and later fix only one copy. The two components then disagree on the same screen.
  2. They believe that two calls of one custom Hook share one value. So they put state in a custom Hook to share it between components, and a click in one component never reaches the other.
  3. They wrap every small piece of code in a custom Hook, even a single useState, or they name Hooks after timing, such as useMount.

Three Principles of Custom Hooks

PRINCIPLES

A custom Hook is our own function that calls React's Hooks. It moves repeated stateful code out of the components, but each call still runs that code separately. Three practical rules follow:

  1. Principle 1: Extract the Copied State and Effect into a Custom Hook: When two components copy the same state variable and Effect, move that code into one function whose name starts with use and a capital letter, return the value the components need, and let each component call it. The page works exactly as before, and every later fix happens in one place.
  2. Principle 2: Each Call Gets Its Own State and Its Own Effect: Two components that call useOnlineStatus() hold two separate isOnline values and run two separate Effects. They show the same value only because both listen to the same browser events.
  3. Principle 3: Share One Changing Value Through the Parent, Not Through a Custom Hook: When two components must show one value that changes, such as whether the work was saved, the state lives in their parent and goes down as props. A custom Hook would give each component its own copy, and the copies never agree.

Here are the three principles side by side, before we walk through each one:

Section 2 · Principle 2Each Call to useOnlineStatus Gets Its Own isOnline

Two components that change at the same moment

Each call to useOnlineStatus() creates its own state variable and its own Effect, inside the component that made the call. This is true even though the heading and the button change in the same instant when the Wi-Fi drops, which makes it look as if both read one shared isOnline.

What the two calls to useOnlineStatus really run

Two components that each call useOnlineStatus(), and the two components with the copied useState and useEffect from Principle 1: yes, it is the exact same thing! Both run the same two state variables and the same two Effects. The Hook removed the copied text from our files. It did not remove the second state variable or the second Effect.

One shared isOnline, and two isOnline values that hold the same value: it may look the same on the page, but it is NOT the same thing! The heading and the button agree only because both listen to the same browser events. Nothing in React links the two values.

React's docs name the two halves of this idea:

  • Stateful logic is the code that creates and updates state. Here it is the useState call and the Effect inside useOnlineStatus. A custom Hook shares this code.
  • State itself is the stored value. Here it is each component's isOnline. A custom Hook does not share it.

In the docs' words: custom Hooks let you share stateful logic but not state itself. Each call to a Hook is completely independent from every other call to the same Hook.

When the network goes off

One browser event reaches two separate Effects, so both components update at once. Here is what happens when the Wi-Fi drops:

  1. The browser fires one offline event on window.
  2. Two listeners are attached to that event, one from each Effect. So the browser calls two handleOffline functions.
  3. The handleOffline of StatusBar calls the setIsOnline of StatusBar. The handleOffline of SaveButton calls the setIsOnline of SaveButton.
  4. React re-renders both components. The heading reads Disconnected, and the button reads Reconnecting....

No line of SaveButton.jsx writes setIsOnline. The second setIsOnline comes from the useState call inside useOnlineStatus, which runs while React renders SaveButton. The second pair of listeners comes from the same place: the Effect that useOnlineStatus declares during the render of SaveButton.

Why All changes saved never appears

Beware! The click saves the work, and the screen never says so. The button changes its own isSaved, and the heading keeps reading a different one.

Here is what happens, in order:

  1. The page opens. StatusBar calls useSaveStatus() and gets its own isSaved, which is false. SaveButton calls useSaveStatus() and gets a second isSaved, also false.
  2. StatusBar checks its own isSaved. It is false, so the heading shows no line under it.
  3. The user clicks Save progress. handleSaveClick prints Progress saved and calls the setIsSaved that SaveButton received from its own call.
  4. React re-renders SaveButton. The isSaved of SaveButton is now true.
  5. Nothing ever called the setter of StatusBar. Its isSaved is still false, and the click does not ask React to render StatusBar again.
  6. The line All changes saved never appears.

Principle 3

Sharing the Value Itself: Lift the State into the Parent, Not into a Custom Hook

When two components must show one value that changes, such as whether the work was saved, put that state in their closest common parent and pass it down as props.

A custom Hook gives every component that calls it a separate copy of its state. That is right for isOnline, because the browser keeps every copy in step. It is wrong for isSaved: the button changes its own copy, and the heading keeps reading the other one, with no error and no warning. The parent owns one value, passes it down, and hands the button a function that changes it.

For the Interview

The Interview Question: How do you extract and reuse stateful logic between components?

How to Answer Clearly in 30 Seconds

"When two components repeat the same stateful logic, such as a state variable and an Effect that listens to the browser's online and offline events, I extract it into a custom Hook. A custom Hook is my own JavaScript function whose name starts with use and a capital letter, and which calls other Hooks. It returns what the components need, so each component calls useOnlineStatus() and reads isOnline. The page behaves exactly as before, and every fix happens in one place. Two things to keep in mind:

  1. A custom Hook shares logic, not state: every call runs its own useState and its own useEffect, so two components get two independent values.
  2. To share the value itself, I lift the state into the closest common parent and pass it down as props, or I use context when the components are far apart."

Three Classic Follow-Up Questions Interviewers Ask

  1. "If two components call the same custom Hook, do they share its state?"
    No. Each call to a Hook is completely independent from every other call to the same Hook. When StatusBar and SaveButton both call useOnlineStatus(), each one gets its own isOnline, its own setter, and its own Effect with its own listeners. They show the same value only because both listen to the same browser events. So a state variable inside a custom Hook such as useSaveStatus cannot carry a click from one component to the other. For that, the state goes up into the parent.
  2. "Should every piece of repeated code become a custom Hook?"
    No. React's docs say that some duplication is fine. A Hook that wraps a single useState adds a name and saves nothing. The strongest case for a custom Hook is an Effect that talks to something outside React, such as the network, a socket, or a media query. Name the Hook after its purpose, such as useOnlineStatus or useChatRoom, and never after timing, such as useMount. A Hook like useMount hides the Effect's dependencies, and the linter checks only direct useEffect calls, so it cannot warn about them. A function that calls no Hooks at all stays a regular function without the use prefix, such as getSorted (as seen in Lesson 38).
  3. "Why wrap an Effect in a custom Hook even when it already works inside the component?"
    Because the component then says what it wants, and the Hook hides how it is done. StatusBar asks for the online status, and only useOnlineStatus knows about navigator.onLine and the browser's events. That pays off when a better way arrives. React's docs later rewrite useOnlineStatus with useSyncExternalStore (covered in Lesson 53), and no component has to change. One more detail follows from where the code runs: the code of a custom Hook runs again on every render of its component, so it must stay pure, and it always receives the latest props and state (as seen in Lesson 14).
