Removing Effect Dependencies by Changing the Code

Interview Question · ❱ CORE

How do you remove unnecessary effect dependencies, and when must a dependency stay?

OverviewHow to Remove an Effect Dependency Without Lying to React

A chat that reconnects when nothing changed

Open a chat app with rooms, such as Slack. A menu at the top picks the room. Under it, a heading says which room you are in. Below the heading, the messages that arrive in the room appear one under the other. At the bottom sits a box where you type your own message.

The user does three things on this screen, and expects three results:

  1. The user types hi in the message box. The letters appear in the box. Nothing else changes, and the user is still in the general room.
  2. The user picks travel in the menu. The app leaves the general room and connects to the travel room.
  3. The user waits. Messages such as hey and lol arrive, and each one appears under the ones before it.

Only the second action should touch the connection to the chat server.

Now look at the same screen as the developer. The connection lives in an Effect, and the Effect's dependency array must list every reactive value the Effect reads (as seen in Lesson 35). The linter checks that list. Sometimes the linter asks for a value whose change should not touch the connection at all. The developer adds it, and from then on the chat disconnects and connects again after every letter the user types, or after every message that arrives. React's docs call such a value an unnecessary dependency: a dependency whose change should not run the Effect again.

The fix is never to edit the list by hand. You change the code. React's docs say it plainly: "If you want to change the dependencies, change the surrounding code first."

There are two ways to get a value out of the dependency array, and only one of them tells the truth:

  • Delete the value from the array and silence the linter. The linter goes quiet, but the Effect still reads the value. From now on, it reads an old copy of it.
  • Change the code so the Effect no longer reads a reactive value there. Then the linter itself stops asking for it. React's docs call this proving it to the linter: "*To remove a dependency, "prove" to the linter that it doesn't need to be a dependency.*"

The key idea to remember: you never pick the dependencies. You change the code until the list the linter asks for is the list you want.

Two objects with the same contents are NOT the same value

One comparison explains why an object makes a bad dependency. After every render, React compares each dependency with its value from the last render, using Object.is (as seen in Lesson 32). Here are two objects with the same contents, and two strings with the same text, both from React's docs:

The two objects look the same, but they are NOT the same thing! They hold the same server and the same room, yet Object.is says they are different. The two strings are the same. The difference is in what JavaScript compares:

  • Strings and numbers are compared by their content. React's docs: "In JavaScript, numbers and strings are compared by their content." Two 'music' strings are one and the same value.
  • Objects and functions are compared by which object they are. Each new object is a different value, even when its contents match. React's docs: "In JavaScript, each newly created object and function is considered distinct from all the others. It doesn't matter that the contents inside of them may be the same!"

What is at stake

What is at stake is what the user sees: a chat that drops its connection and opens a new one for no reason, or a chat that quietly loses messages. On the chat page of this lesson, three versions of the code show it:

  1. An options object made in the component body and listed in the array. Every letter the user types disconnects the chat and connects it again. React's docs: "the chat re-connects as you type."
  2. The messages list read inside the Effect and listed in the array. Every message that arrives disconnects the chat and connects it again. React's docs: "every new message will make the chat re-connect. The user would not like that!"
  3. The dependency deleted and the linter silenced. The chat stays connected, but the list on the screen shows only the newest message.

Readers usually go wrong in three places:

  1. They delete the dependency and add a comment that silences the linter. React's docs: "By suppressing the linter, you "lie" to React about the values your Effect depends on."
  2. They think an object with the same contents is the same dependency.
  3. They remove a dependency that must stay, such as roomId, because the Effect runs "too often". Then the chat stays in the old room after the user picks a new one.

Four Principles of Removing Effect Dependencies

PRINCIPLES

The dependency array describes the code of the Effect. To change the array, we change the code. Our chat room gives us four practical rules:

  1. Principle 1: Typing in the Message Box Reconnects the Chat: An object made in the component body is a new object on every render. When the Effect lists it, every letter the user types disconnects the chat and connects it again.
  2. Principle 2: Building options Inside the Effect Leaves Only roomId: Move an object that depends on props or state inside the Effect, and one that depends on neither above the component. Then it is not reactive, it leaves the array, and only the string roomId stays.
  3. Principle 3: An Updater Function Keeps New Messages from Reconnecting the Chat: When the Effect adds a message to messages, an updater function lets it do so without reading messages. Then messages leaves the array, and no comment has to silence the linter.
  4. Principle 4: roomId Stays Because Picking a Room Must Reconnect: A dependency stays when its change, seen from the user's side, means the Effect must connect again. A dependency goes only when the code no longer reads a reactive value there.

An object made in the component body is new on every render

Start from the shape React's docs use for this chat. The settings of the connection sit together in one object, options, and the Effect passes that object to createConnection:

The array matches the code: the Effect reads options, and options is listed. Yet this Effect runs again after every render. Why? Well, ChatRoom runs from the top on every render, so the options line builds a brand-new object every time. React's docs: "A new options object is created from scratch on every re-render of the ChatRoom component."

The options of the last render and the options of this render hold the same server and the same room. They look the same, but they are NOT the same thing! They are two objects, so Object.is returns false, exactly as it did for options1 and options2. React's docs: "React sees that the options object is a different object from the options object created during the last render."

React's docs have a name for this case. An object listed in the dependency array is an object dependency, and a function listed there is a function dependency. The docs warn about both in bold: "Object and function dependencies can make your Effect re-synchronize more often than you need."

The linter sees this too. With [options], it no longer reports a missing dependency. Instead, it warns that this object changes the dependencies of the Effect on every render, and it tells you to move the object inside the Effect. Principle 2 does exactly that.

Principle 1

An object or a function made in the component body is a new value on every render, so an Effect that lists it re-synchronizes after every render, even when the contents are the same.

When options is made in the component body, every letter the user types re-renders ChatRoom, builds a new options, and makes React disconnect the chat and connect it again. It may look the same, or work the same at first, but it is NOT the same thing! Both versions connect to the general room when the page opens. Both reconnect when the user picks travel. Only the version with options in the component body reconnects when the user types a letter.

The reason is simple: a value made inside the Effect is not reactive, so it is not a dependency (as seen in Lesson 35). React's docs: "Now that options is declared inside of your Effect, it is no longer a dependency of your Effect. Instead, the only reactive value used by your Effect is roomId."

The linter itself asks for roomId in the new array, because the Effect now reads roomId directly, in the line that builds options. If you left the array empty, the linter would report: React Hook useEffect has a missing dependency: 'roomId'.

This is what React's docs mean by proving to the linter. We never argued with the linter about options. We moved one line, and the linter stopped asking for options and asked for roomId instead.

Why roomId causes no trouble in the array

roomId is a string. Strings, numbers, and booleans are primitive values: JavaScript compares them by their content, as the two 'music' strings showed. So while the user stays in the general room, every render gives roomId the same value, 'general', and React keeps the connection. When the user picks travel, the value really changes, and React reconnects.

That is why React's docs give one piece of advice for every object or function dependency: "try moving them outside the component, inside the Effect, or extracting primitive values out of them."

Static objects go above the component, dynamic ones inside the Effect

The right place for the object depends on what it reads. React's docs name two kinds of objects, and each has its own place:

  1. A static object "does not depend on any props and state". It goes above the component. JavaScript makes it once, when the file loads, so it is the same object on every render, and the array becomes [].
  2. A dynamic object "depends on some reactive value that may change as a result of a re-render, like a roomId prop". It goes inside the Effect, and the array lists the values it reads, such as [roomId].

React's docs show the static kind with a chat that is always in the music room:

When options arrives as a prop

Sometimes the object is not ours to move. React's docs show this mistake in one of their Challenges:

  1. App builds options from its own state and passes it down as a prop, <ChatRoom options={options} />.
  2. ChatRoom reads options inside its Effect and lists [options].
  3. The user clicks a Toggle theme button, which changes only the theme of App.
  4. App renders again and builds a new options, so the chat reconnects. The docs: "Your Effect is re-running because it depends on the options object."

ChatRoom cannot move a prop. Instead, it reads the primitive values out of the object, before the Effect:

A function that arrives as a prop, such as getOptions, works the same way. Call it outside the Effect, read roomId and serverUrl from the object it returns, and list the two strings. The docs add one condition about pure functions (as seen in Lesson 14): "This only works for pure functions because they are safe to call during rendering." When you also write the parent, the docs suggest a simpler fix: pass roomId and serverUrl as two props instead of one options object.

Section 3 · Principle 3An Updater Function Keeps New Messages from Reconnecting the Chat

Reading messages vs. passing an updater function

Now the room shows the messages that arrive. The Effect hands the connection a function through its on method, and the connection calls that function with each message (as seen in Lesson 36). Inside that function, the Effect must add the new message to the end of messages state. There are two ways to write that line:

Reading messages, and passing an updater function
1setMessages([...messages, msg]);
Reads messages: the Effect now depends on messages
2setMessages(msgs => [...msgs, msg]);
Never reads messages: React passes the current list as msgs

Both lines put msg at the end of the list. But the first line reads messages, so the linter asks for messages in the array. The second line reads nothing but msg, so messages never enters the array.

Developers usually try two other ways before they reach the updater function. Each one breaks the page in its own way, so we look at both first.

With messages in the array, every message reconnects the chat

Here is the first try. ChatRoom gets messages state and a list under the heading. The Effect reads messages, so the developer follows the linter and lists it:

The docs' three steps

The whole lesson fits in three steps from React's docs:

  1. "First, you change the code of your Effect or how your reactive values are declared."
  2. "Then, you follow the linter and adjust the dependencies to match the code you have changed."
  3. "If you're not happy with the list of dependencies, you go back to the first step."

The questions to ask about an unnecessary dependency

React's docs give three reasons why a developer may not want a dependency:

  1. "You might want to re-execute different parts of your Effect under different conditions."
  2. "You might want to only read the latest value of some dependency instead of "reacting" to its changes."
  3. "A dependency may change too often unintentionally because it's an object or a function."

For each unnecessary dependency, the docs ask a short list of questions. Each answer leads to one tool:

  1. "Should this code move to an event handler?" When the code runs because of one interaction, such as a form submit, it belongs in the event handler (as seen in Lesson 34).
  2. "Is your Effect doing several unrelated things?" Split it into two Effects, each with its own array (as seen in Lesson 35).
  3. "Are you reading some state to calculate the next state?" Pass an updater function, as Principle 3 did with messages.
  4. "Do you want to read a value without "reacting" to its changes?" Move that code into an Effect Event (as seen in Lesson 36).
  5. "Does some reactive value change unintentionally?" This is an object or a function made during rendering. Move it above the component or inside the Effect, or read its primitive values, as Principles 1 and 2 did with options.

Silencing the linter is not on the list. React's docs: "We recommend treating the dependency lint error as a compilation error."

The first question catches a mistake that React's docs show with a form:

  1. When the user submits the form, the code sets submitted to true, and an Effect with [submitted] sends the form and shows a notification.
  2. Later, the notification reads the page theme, so the developer follows the linter and adds theme to the array.
  3. Now the user submits the form and then switches the theme. The Effect runs again and shows the same notification a second time.

The docs: "The problem here is that this shouldn't be an Effect in the first place." The code moves into the submit handler, and the dependency question disappears with it.

Interview PrepFor the Interview

The Interview Question: How do you remove unnecessary effect dependencies, and when must a dependency stay?

How to Answer Clearly in 30 Seconds

"I never choose the dependencies. The array lists every reactive value the Effect reads, and the linter checks it. To remove a dependency, I change the code so the Effect no longer reads a reactive value there, and then the linter stops asking for it. Three changes cover most cases:

  1. Move an object or a function: one made in the component body is a new value on every render, so I move a static one above the component and a dynamic one inside the Effect, or I read its primitive values.
  2. Pass an updater function: when the Effect sets state from the same state, such as adding a message with msgs => [...msgs, msg], it no longer reads that state.
  3. Put the code where it belongs: in an event handler when it answers one interaction, in two Effects when it does two unrelated things, or in an Effect Event when it reads a value without reacting to it.

A dependency must stay when its change means the Effect must re-synchronize, such as the chat room the user picked. I never silence the linter, because the Effect then keeps stale values."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why does an options object re-run the Effect when its contents did not change?"
    React compares each dependency with Object.is. Strings and numbers are compared by their content, but each new object is a different value, even with the same contents. React's docs show two objects with the same server and the same room, and Object.is returns false for them. An object made in the component body is made again on every render, so the Effect re-synchronizes after every render. The fix is to move the object inside the Effect, or above the component, so that only primitive values such as roomId stay in the array.
  2. "Can an object in the dependency array cause an infinite loop?"
    Only when the Effect also sets state. React's docs say an infinite cycle needs two things: "Your Effect is updating some state." and "That state leads to a re-render, which causes the Effect's dependencies to change." Our chat Effect with [options] sets no state, so it runs again once after each render, on every letter the user types, and then stops. If that Effect also set state to a new value on every run, such as a new object, the runs would never end. Each run would cause a render, a new options, and another run, and the Console would fill with React's error Maximum update depth exceeded. Setting state to a value it already holds, such as true again, causes no new render, so the runs stop.
  3. "What if the object comes from a parent as a prop, and you cannot move it?"
    Read its primitive values before the Effect, such as const { roomId, serverUrl } = options;, and list [roomId, serverUrl]. A new object with the same room then does not reconnect, while a real change of room still does. For a function prop, call it outside the Effect, which works only for pure functions. Better still, pass roomId and serverUrl as separate props. React's docs keep useMemo and useCallback as the last resort for this case (covered in Lessons 56 and 57).
