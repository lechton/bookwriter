Fetching Data in an Effect, with Loading, Errors, and Race Conditions

Interview Question · ❱ CORE

How do you fetch data from an API in a client component, and how do you handle loading, error, and race conditions?

How a Page Shows Data That Lives on a Server

The answer comes later, and not always in order

When you open the team page of a work app and click a name, the page shows that person's bio under the buttons. The bio is not written in the code of the page. It lives on a server, and the page has to ask the server for it every time the user clicks a name. The page sends a request, and some time later the server sends back a response with the bio.

Two things follow from that "some time later", and they are the whole lesson:

  1. The page must show something while it waits. React puts the page on the screen before the bio arrives, so the page needs a line for the time in between, such as Loading..., and a line for the case where the server fails.
  2. The answers do not always come back in the order the user clicked. React's docs say it plainly: "network responses may arrive in a different order than you sent them."

What is at stake

What is at stake is a page that shows the wrong person's details and gives no sign that anything is wrong. Here is how it happens on our team page:

  1. The user clicks Bob. The server is slow to answer for Bob.
  2. The user changes their mind at once and clicks Taylor.
  3. Taylor's bio comes back first, and the page shows it.
  4. Bob's bio comes back a moment later, and the page shows it in place of Taylor's.

The page now shows Taylor's name with Bob's bio under it. There is no error and no message in the Console. On the developer's fast machine, the answers always come back in order, so the developer never sees it. A user on a slow phone sees it often.

Readers usually go wrong in four places. They think the last click always gets the last answer. They write the request with no code that cleans up after it. They expect the request to fail when the server has a problem, and it does not. And when they learn to stop an old request, they show that stop to the user as an error.

Two fixes that give the same page

Lesson 32 ended with a list of what each setup needs from its cleanup. One line of it belongs to this lesson: ""fetch" needs either "cancel" or "ignore"." So there are two fixes for the late answer, and Principles 3 and 4 show both:

  • Ignore the late answer: the old request runs to the end, and the page drops what it brings.
  • Cancel the old request: the browser stops the old request, so no answer comes at all.

It may look the same, or work the same at first, but it is NOT the same thing! Both fixes leave the right bio on the page. With the first, the server still does the work for Bob and sends his bio back for nothing. With the second, the browser stops waiting for Bob as soon as the user clicks Taylor.

Our example page: a team page with three names

Our page has three buttons, Alice, Bob, and Taylor. Under them sit the name of the person chosen and one line for that person's bio. The page opens on Alice. Here is what the user does, and what each click should change:

  1. The page opens. The line shows Loading..., then Alice's bio.

Four Principles of Fetching Data in an Effect

PRINCIPLES

A component that shows data from a server asks for it in an Effect, shows a line while it waits and a line when the server fails, and uses the cleanup so that an old answer never replaces a new one. Four principles follow from that:

  1. Principle 1: fetch Inside useEffect Loads the Bio: The browser's fetch sends the request, and the answer arrives later. The request goes in an Effect that lists person in its array, and the line shows Loading... until the bio arrives.
  2. Principle 2: response.ok Turns a Server Error into the Error Line: fetch fails only when it cannot reach the server. When the server answers with an error, the code must check response.ok and show the error line.
  3. Principle 3: The ignore Flag Drops Bob's Late Answer: When the user clicks a new name before the old answer arrives, the old answer can arrive last. The cleanup marks the old request, and its answer is dropped.
  4. Principle 4: AbortController Stops Bob's Request: With fetch, the cleanup can stop the old request itself. The stopped request fails with an AbortError, which is not an error for the user.

Here is the complete map of those four principles before we walk through each one:

Section 1 · Principle 1fetch Inside useEffect Loads the Bio

fetch sends the request, and the answer comes later

The browser gives every page a function called fetch. It sends a request to an address on the server. Here are three lines that ask for Alice's bio and print it in the Console:

fetch does not give back the bio on the same line. The bio is not there yet, because the server has not answered. So fetch gives back a promise at once: a JavaScript object that stands for a value that will arrive later. .then hands the promise a function to call when the value arrives:

  1. fetch sends the request and returns a promise.
  2. When the server answers, the browser creates a response object and passes it to the first function.
  3. response.json reads the body of the response, the JSON text, and turns it into a JavaScript object. Reading takes time too, so it also returns a promise.
  4. When the object is ready, the second function gets it as data, and data.bio is the bio.

The name bio comes from the server's JSON, { "bio": "This is Alice’s bio." }, not from our state.

Why the request goes in an Effect

The request must go out because Bio is on the screen and must show the bio of person. No click inside Bio causes it. This is the job of an Effect from Lesson 32: it keeps something outside React in step with the component. React's docs make the same point for a search page: the main reason to fetch is not the typing, but that "While this component is visible, you want to keep results synchronized with data from the network". Here, while Bio is visible, the bio on the line must match person.

So we move the request into useEffect, and the second .then puts the bio into state:

Section 2 · Principle 2response.ok Turns a Server Error into the Error Line

fetch fails only when it cannot reach the server

Servers have bad moments. When something breaks on the server, it still answers, but with an error status code: a number such as 500 in place of the usual 200. fetch treats that answer as a success. MDN, the reference for the web, says it plainly. The promise of fetch fails only when the request fails, for example because the address is badly formed or the network is lost. It does not fail when the server answers with a status code that means an error, such as 404 or 504.

It may look the same, or work the same at first, but it is NOT the same thing! For the user, a broken server and a lost network are the same: no bio. For fetch, they are two different cases. With a lost network, the promise fails. With a broken server, the promise succeeds, and the answer holds the error.

The server fails, and the page says Loading... forever

Say the server breaks while the user looks at Alice. It answers with status 500 and the JSON { "message": "Server error" }. Our code from Principle 1 has no check, and the line shows Loading... with no end:

  1. The setup sets bio to null, and the line shows Loading....
  2. The server answers with status 500.
  3. fetch succeeds, because the server answered.
  4. response.json gives { message: 'Server error' }, which has no bio, so data.bio is undefined.
  5. setBio puts undefined in bio, and ?? shows Loading... for undefined too.

Checking response.ok and showing the error line

The response object says whether the status is good. response.ok is true for a status from 200 to 299, and false otherwise. response.status holds the number itself. When response.ok is false, our code turns the answer into an error with throw new Error. A throw inside .then makes the promise fail, so the next .then is skipped, and the function in .catch runs with the error. The text in the error, such as Status 500, is for the developer who inspects the error. The user sees only the error line.

We keep the error in a second state variable, error, and the JSX checks it first:

Section 3 · Principle 3The ignore Flag Drops Bob's Late Answer

Bob's late answer replaces Taylor's bio

Here is the code from Principle 2, with no cleanup, and two quick clicks by the user. The page ends on Bob's bio under Taylor's name:

  1. The user clicks Bob. person becomes 'Bob', and the Effect sends the request for Bob, which the server answers after two seconds. The line shows Loading....
  2. Half a second later, the user clicks Taylor. The Effect sends the request for Taylor, which the server answers after a fifth of a second.
  3. Taylor's answer arrives first. setBio puts Taylor's bio on the line.
  4. Bob's answer arrives more than a second later. Its .then still runs, because nothing told it that the user moved on, and setBio puts Bob's bio on the line.

This is a race condition. React's docs define it: "two different requests "raced" against each other and came in a different order than you expected." There is no error, and the Console is quiet. On a fast network the answers come back in order, so the bug shows up only for some users.

The ignore flag

The docs' fix uses the cleanup from Lesson 32. Each run of the setup creates its own variable, ignore, set to false. The cleanup of that run sets it to true. The answer sets state only while ignore is still false. The docs show it with a function of their own, fetchBio, which returns a promise of the bio, as fetch does:

The cleanup knows which ignore to change because it is created inside the same run of the setup, as the cleanup in Lesson 32 knew which intervalId to stop. Each run has its own ignore, and its own cleanup that changes only that one.

Section 4 · Principle 4AbortController Stops Bob's Request

Stopping a request with AbortController

The browser has a tool that stops a fetch before it finishes: the AbortController. MDN describes it as "a controller object that allows you to abort one or more Web requests as and when desired." It works in three steps:

Stopping a request with AbortController
1const controller = new AbortController();
1. Creates the controller
2fetch('/api/bio/Bob', { signal: controller.signal });
2. Gives fetch the controller's signal
3controller.abort();
3. Stops the request

controller.signal is the part of the controller that fetch listens to. We hand it to fetch in the second argument, { signal: controller.signal }. When our code calls controller.abort, the browser stops the request, and the fetch promise fails. MDN says that when abort is called, the promise of fetch fails with a DOMException named AbortError. A DOMException is the kind of error object the browser itself creates. So the error that reaches .catch has the name 'AbortError', and our code reads it in err.name.

The ignore flag and abort

Here are the two cleanups side by side:

The cleanup with the ignore flag, and with abort on the controller
1return () => { ignore = true; };
Bob's request runs to the end, and its answer is dropped
2return () => controller.abort();
Bob's request is stopped, and no answer comes

It may look the same, or work the same at first, but it is NOT the same thing! After the user clicks Bob and then Taylor, both cleanups leave Taylor's bio on the page. With the ignore flag, the browser still waits for Bob's answer and reads it, and our code drops it. With controller.abort, the browser cancels Bob's request when the user clicks Taylor, and stops waiting for it.

React's docs leave the choice open: the cleanup "should either abort the fetch or ignore its result". abort saves the network and the reading of an answer nobody needs. The flag works for any promise, even one that cannot be stopped.

The abort reaches .catch

A developer replaces the flag with a controller and keeps the .catch from Principle 2. In development, the page opens on the error line:

The page works, the server works, and yet the user reads that the bio could not be loaded. Here is why:

  1. React mounts Bio and runs the setup. It creates the first controller, sends the first request for Alice, and sets error to null.
  2. Strict Mode runs the cleanup. controller.abort stops the first request.
  3. Strict Mode runs the setup again. It creates a second controller, sends the second request, and sets error to null.
  4. The first request's promise fails with an AbortError. A promise never calls its functions in the middle of other code: it waits until the code that is running now has finished. React runs the setup, the cleanup, and the second setup in one go, so this .catch runs after the second setup, and setError keeps the AbortError.
  5. The second request brings Alice's bio, and setBio sets it. But error is not null, and the JSX checks error first.

The same thing happens in production when the user clicks Bob and then Taylor: the cleanup stops Bob's request, its AbortError reaches .catch, and the user sees the error line under Taylor's name.

An AbortError is not something that went wrong. It is our own cleanup doing its job. So .catch skips it and keeps every other error:

Principle 4

Aborting: AbortController Stops Bob's Request

With fetch, the cleanup can stop the old request: the setup creates an AbortController, passes controller.signal to fetch, and the cleanup calls controller.abort; the stopped fetch fails with an AbortError, which .catch must skip, because it is not an error for the user.

The ignore flag lets the old request finish and drops its answer. controller.abort stops the old request, so no answer comes, and the browser does not wait for it. The stop itself makes the promise fail, so .catch checks err.name and shows the error line only for a real error.

For the Interview

The Interview Question: How do you fetch data from an API in a client component, and how do you handle loading, error, and race conditions?

How to Answer Clearly in 30 Seconds

"I call fetch inside useEffect, because the data must match the props while the component is on the screen, and I list the props the request reads, such as [person]. The data arrives later, in .then, so the component has three states: loading, error, and data. Three rules keep it right:

  1. Loading: the state starts at null, the JSX shows a loading line for null, and each new request sets it back to null.
  2. Errors: fetch fails only when it cannot reach the server, so I check response.ok, throw an error when it is false, and keep the error in state from .catch.
  3. Race conditions: answers can come back in a different order than I sent the requests. The cleanup either sets an ignore flag so that the old answer is dropped, or calls abort on an AbortController so that the old request stops. With abort, .catch skips the AbortError."

Three Classic Follow-Up Questions Interviewers Ask

  1. "Why does my page send every request twice in development?"
    In development, Strict Mode runs the setup, the cleanup, and the setup again when the component mounts, so two requests go out. The docs: "There is nothing wrong with that." With a cleanup, the first request's answer is dropped or its request is stopped, so it does not change the state. "In production, there will only be one request." The fix is never to block the second run. It is a cleanup that makes the two runs look like one to the user.
  2. "What about the warning "Can't perform a React state update on an unmounted component"?"
    React 18 removed it. The upgrade guide: React "warned about memory leaks when you call setState on an unmounted component", but "people primarily run into it in scenarios where setting state is fine, and workarounds make the code worse." React 19 prints nothing when a late answer sets state on a component that is gone. The cleanup still matters, because it keeps a late answer from replacing the current data, and with abort it stops requests nobody needs.
  3. "Would you write fetch in an Effect in a real app?"
    The docs call it "a very manual approach", for three reasons. Effects do not run on the server, so the first HTML shows only the loading state. A parent and a child that each fetch one after the other create "network waterfalls". And nothing is cached, so a component that mounts again fetches again. The docs recommend the data fetching of a framework, or a client-side cache such as TanStack Query or useSWR, which Lesson 60 compares. Without those, the fetch Effect can go into a custom Hook, such as the docs' useData, which Lesson 39 teaches. React 19's use with Suspense is Lesson 71, and Server Components are Lesson 101.
