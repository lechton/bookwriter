Every app with a comment box behaves like this. Now look at the same screen as the developer who builds it. In our code, the Post button is its own component. It sits inside another component, the row under the box, and that row sits inside the form. No line of our code tells the button that the form is sending a comment.

So how does the button know that the form is submitting right now? It asks the form. The button calls a Hook named useFormStatus and reads one value from it, pending. While the form above the button is submitting, pending is true. The rest of the time, it is false.

What "pending" means

In everyday English, something is pending when it has started and is still waiting to finish, like a bank payment that your banking app marks as Pending. A form is pending in the same sense: the user has clicked Post, and the comment is on its way, but the answer has not come back yet.

What is at stake

The key idea to remember is this: useFormStatus reads the status of the closest <form> above the component that calls it. The form must be a parent of that component, higher up in the tree. A form that the same component returns does not count.

What is at stake is what the user sees when pending never becomes true. The same comment gets posted twice:

  1. The user clicks Post. The button keeps reading Post during the whole one-second wait, and it can still be clicked.
  2. The user sees no sign that the first click worked, so the user clicks Post again.
  3. The same comment is sent twice, and the list shows Nice photo! two times.

Readers usually go wrong in one place. They call useFormStatus in the component that renders the <form> tag, right next to it. There, pending stays false on every submit, and the Console shows no error. Principle 2 shows this mistake on our page.

Context and useFormStatus: two ways to read a value from far above

You already know one way for a component deep in the tree to read a value that no component above it passes down as a prop: context (as seen in Lesson 28). useFormStatus works the same way. The one difference is who provides the value:

  • With context, our code writes the provider, and the component reads the closest provider above it.
  • With useFormStatus, our code writes no provider. The <form> tag plays that part, and the component reads the closest form above it.

React's blog says it in one sentence: "useFormStatus reads the status of the parent <form> as if the form was a Context provider."

Three ways to tell the button that the form is submitting

Developers choose between three ways to give a submit button the pending state of its form:

  1. Pass isPending down as a prop. The component that owns the form already gets isPending from useActionState (as seen in Lesson 42), and it hands that value down to the button. React's own useActionState page passes isPending to a child component this way. This fits a button that sits one level below the owner of the form.
  2. Make a context by hand. Our code creates a context and provides the pending flag through it (as seen in Lesson 28). This fits a status that does not come from a form submission.
  3. Call useFormStatus in the button component. This fits a button or a box rendered anywhere inside a <form>, at any depth, and a button that many forms reuse.

React's blog explains why the third way exists: "This can be done via Context, but to make the common case easier, we've added a new hook useFormStatus." This lesson is about the third way.

The four principles

PRINCIPLES

A component inside a form can ask that form whether it is submitting. It calls useFormStatus, and React DOM answers from the closest form above it. React DOM is the part of React, in the react-dom package, that works with the browser page. Four practical rules follow:

  1. Principle 1: useFormStatus Gives the Post Button pending: the button calls useFormStatus from 'react-dom' and reads pending. Our code never sets pending. React DOM makes it true while the form submits and false after.
  2. Principle 2: pending Stays false Next to the form Tag: the Hook reads only a form above the component that calls it. In the component that renders the <form> tag itself, pending never becomes true, and nothing warns you.
  3. Principle 3: CommentFooter Passes No pending Prop: the Hook reaches the form through any number of components in between, so the components in the middle no longer carry a prop they never use.
  4. Principle 4: data Shows the Comment Being Posted: the same Hook also returns data, the form data being submitted right now, so a component inside the form can show what the user just sent. Before the first submit, data is null.

What useFormStatus returns

useFormStatus is a Hook that gives you "status information of the last form submission", in the words of React's docs. React DOM provides it. It takes no parameters, so there is no way to name a form: it always reads the form above the component that calls it.

It returns one object, which the docs call the status object. That object holds four properties: pending, data, method, and action. The curly braces in const { pending } = useFormStatus(); take pending out of that object by name (as seen in Lesson 8). This lesson uses two of the four: pending here, and data in Principle 4.

The docs define pending in two sentences: "If true, this means the parent <form> is pending submission. Otherwise, false."

Import it from 'react-dom', not from 'react'

Every Hook in this book so far came from 'react', such as useState and useActionState. useFormStatus does not. It comes from 'react-dom', the package that connects React to the browser page (as seen in Lesson 7):

The two import lines a developer might write
1import { useFormStatus } from 'react';
WRONG 'react' has no useFormStatus, so the page breaks with an error
2import { useFormStatus } from 'react-dom';
The right package: React DOM provides this Hook

It lives in 'react-dom' because a <form> exists only on a web page. React's docs list useFormStatus among the Form Hooks of React DOM, which work only in web applications that run in the browser. Apps for iOS, Android, or Windows do not support them.

What happens when the user clicks Post

Our code never writes pending, and no prop reaches PostButton. Still, the button reads Posting... for one second and cannot be clicked. React DOM does the work. Here is what happens, in order:

  1. The user clicks Post. The button has type="submit", so the click submits the form (as seen in Lesson 11).
  2. React DOM starts the action of the form, postAction. The form is now pending, so React DOM gives PostButton a pending of true. React renders the button again, and the button reads Posting... and turns off.
  3. addComment waits one second for saveComment, then returns the list with Nice photo! added.
  4. The submission is over. pending goes back to false, the button reads Post again, and React empties the box (as seen in Lesson 41).

Principle 1

useFormStatus: A Component Inside a Form Asks the Form for pending

Call useFormStatus from 'react-dom' in a component rendered inside a <form>, and read pending, which is true while that form is submitting.

A submit button often needs to know that its form is sending something, so it can turn off and say so. No prop has to bring that value. The button calls useFormStatus, React DOM looks at the form above the button, and pending tells the button whether that form is submitting right now. The Hook comes from 'react-dom', because forms exist only on a web page.

The same Hook line in two places

Here are two components from React's docs. Both call useFormStatus with the exact same line. The one difference is where the <form> tag is: inside the component's own return, or above the component:

It may look the same, but it is NOT the same thing! The Hook line is identical, and both components have a form on the page. But useFormStatus looks only above the component that calls it:

  • In Form, the <form> tag is in the component's own return, so it sits below Form, not above it. The Hook finds no form, and pending stays false.
  • In Submit, the <form> tag sits above Submit, because the form renders <Submit />. The Hook finds that form, and pending is true while it submits.

React's docs call the form above the component the parent <form>: "The useFormStatus Hook must be called from a component that is rendered inside a <form>." They also say what happens otherwise: useFormStatus "will only return status information for a parent <form>. It will not return status information for any <form> rendered in that same component or children components."

The Console stays quiet. React prints no error and no warning for this case. The docs only warn that "pending will never be true". In the Elements panel, the button never gets the disabled attribute.

Many developers then give up on the Hook and add a useState flag by hand, set before the request and cleared after it. There is no need. The docs give the fix: "call useFormStatus from inside a component that is located inside <form>". On our page, that component is PostButton, exactly as Principle 1 wrote it.

The owner of the form already has its own flag

When CommentSection itself needs to know that the form is pending, it does not need useFormStatus at all. It already gets isPending from useActionState (as seen in Lesson 42). So each component has its own tool:

  • The owner of the form, CommentSection, reads isPending from useActionState.
  • A component inside the form, such as PostButton, reads pending from useFormStatus.

Context follows the same rule: a provider in the same component does not count, only one above it (as seen in Lesson 28).

Why the button is its own component

Real teams write one submit button and reuse it in every form of the app: the comment box, the sign-up form, the settings page. React's blog calls such a reusable piece a design component, and it names this exact case: "In design systems, it's common to write design components that need access to information about the <form> they're in, without drilling props down to the component."

useFormStatus reads only the submission of a form. Any other value that many components share still needs props or context (as seen in Lesson 28).

Principle 3

No Prop Drilling: The Components in the Middle Pass Nothing

Let the component that needs the status of the form call useFormStatus itself, so the components between the form and that component pass no pending prop.

With a pending prop, every component between the form and the button must receive the prop and hand it on, even though it never uses it. One forgotten prop leaves the button stuck on Post. With useFormStatus in the button, the button asks the form directly, through any number of components in the middle, and the user sees the exact same button.

The docs define data like this: "An object implementing the FormData interface that contains the data the parent <form> is submitting. If there is no active submission or no parent <form>, it will be null."

So data is the same kind of object as the formData that our action receives (as seen in Lesson 40). You read it the same way, with .get and the name of the box:

  • With formData.get('comment') in addComment, the action reads the text that the user sent.
  • With data.get('comment') in a component inside the form, the screen reads that same text while it is on its way.

Yes, it is the exact same thing! Both read the form data of the same submission, so both give Nice photo!. The only difference is the place: one runs inside the action, the other inside a component on the screen.

Principle 4

data: The Form Data Being Submitted, or null

Read data from useFormStatus to show what the parent form is submitting, and check that data is not null before you call data.get.

While the form submits, data holds the same form data that the action receives, so a component inside the form can show the text of the user on the screen. The rest of the time, data is null. Calling data.get on the first render, before any submit, throws an error and empties the page.

For the Interview

The Interview Question: How does a field nested deep in a form read the form's pending state?

How to Answer Clearly in 30 Seconds

"The field or the button calls useFormStatus, a Hook from 'react-dom'. It takes no parameters and returns the status of the parent form: pending, data, method, and action. pending is true while that form is submitting, so a Post button can turn off and read Posting.... Three rules keep it working:

  1. Call it inside the form: the Hook reads only a form above the component. In the component that renders the <form> tag itself, pending is never true, and no error tells you so.
  2. No prop drilling: the components between the form and the button pass nothing. React's blog says the Hook reads the parent form as if the form was a Context provider.
  3. Check data: data holds the form data being submitted, and it is null when nothing is being submitted."

Three Classic Follow-Up Questions Interviewers Ask

  1. "I called useFormStatus in my form component, and pending is always false. Why?"
    Because the Hook reads only a parent <form>, a form above the component that calls it. A form in the component's own return is below it, so the Hook does not see it. With no form above, the Hook returns pending as false, and data, method, and action as null. The fix is to move the Hook into a component rendered inside the form, such as the submit button. If the owner of the form needs the flag itself, it reads isPending from useActionState.
  2. "What is the difference between isPending from useActionState and pending from useFormStatus?"
    They answer the same question for two different components. isPending goes to the component that calls useActionState, which is usually the component that owns the form. pending goes to any component inside the form, at any depth, without a prop. On one page, the owner uses isPending, and the reusable submit button uses pending.
  3. "Why does useFormStatus come from 'react-dom', and what do method and action hold?"
    It is one of the Form Hooks of React DOM, which work only in web applications that run in the browser, because <form> is a browser element. During a submission, method is the string 'get' or 'post', taken from the method prop of the form, and 'get' when the form has no method prop. Our comment form has a function in its action prop and no method prop, so method reads 'get' during the wait. React does not want a method prop on such a form. When the form has method="post" next to a function, the Console shows this error: "Cannot specify a encType or method for a form that specifies a function as the action. React provides those automatically. They will get overridden." action is a reference to the function passed to the action prop of the parent form. It is null when there is no parent form, when the form has a URL in its action prop, or when the form has no action prop at all.
