How a Child Tells Its Parent to Change State

Interview Question · ❱ CORE

How does a child component notify its parent or trigger state updates using callback props?

OverviewHow a Child Asks Its Parent for a Change

Changing the file yourself vs. calling the owner back

Think of a doctor's office that keeps your file. You cannot walk behind the desk and change your file yourself, because the file belongs to the office. So the office gives you its phone number and says: call us back when something changes. One day you move to a new street. You call the number, you say what happened, and the person at the desk updates your file. You never touched the file. You only made a call.

This is where the word callback comes from. A callback is a function that one piece of code hands to another piece of code, so the other piece can call it back later, when something happens.

React components work the same way. A parent component keeps a list in its state, and it hands a function down to a child component as a prop. When the user clicks a button inside the child, the child calls that function and says what happened. Then the parent's own code changes the list.

What the parent passes down is nothing new: it is a prop written on the child's tag, like any other prop. The one difference is what the prop carries:

  • A prop that holds a value, such as name="John", carries something for the child to show.
  • A prop that holds a function, such as onRemove={handleRemove}, carries something for the child to call.

So here is the key idea of this lesson: the parent owns the state and the only code that changes it. The child never changes that state itself. It only calls the function it was given.

What is at stake

What is at stake is a button that does not do its job. The user clicks Remove next to a guest, and the guest stays on the list. Or the guest's row disappears, while the line above the list still says 3 guests. Both happen when the child tries to do the parent's job.

Readers usually go wrong in one of two places. Some picture the child reaching up into the parent and changing the parent's list. Others think that once a child can change the parent's state, data flows both ways. Neither is true. Only a function call goes up. The new list still comes down as props.

Four ways to let a child change its parent's state

When a child must change its parent's state, developers choose among four ways:

  1. Pass a handler the parent wrote, such as onRemove={handleRemove}, and let the child call it with a value. This is the usual way in React's docs, and the way this lesson teaches.
  2. Pass the setter itself, such as onFilterTextChange={setFilterText}. React's docs do this on their Thinking in React page. It fits when the child sends exactly the next value of the state.
  3. Pass an arrow function that already holds its value, such as an onShow arrow that calls setActiveIndex with the number of its own panel. It fits when each child tag is written by hand, so each tag already knows its own value.
  4. Pass one dispatch function, or put the functions in context, when many components deep in the tree need them. Lessons 27 to 29 teach these.

Four Principles of Callback Props

PRINCIPLES

A child cannot change its parent's state, but it can call a function the parent gave it. Four practical principles follow from that:

  1. Principle 1: GuestRow Cannot Call setGuests: State is private to the component that declares it. A row placed inside the guest list sees only the props written on its tag, so the list's setter is out of its reach.
  2. Principle 2: onRemove Carries handleRemove Down to the Row: A prop can hold a function. The parent writes the handler next to its state and passes it on the child's tag, and the child gives it to a real <button>.
  3. Principle 3: guest.id Tells the Parent Which Guest: The child calls the function inside its own arrow function, with the value the parent needs. The parent's handler calls its own setter, and the new list comes down as props.
  4. Principle 4: AddGuest Sends the Typed Name Up Through onAdd: When the value exists only in the child, such as the text typed in its own box, the child sends it as the argument of the call.

Yes, it is the exact same thing! For React, both are props written on the tag, and both arrive inside the same props object. The one difference is the value: text to show, or a function to call.

React's docs call a prop like onSmash an event handler prop: a prop whose value is a function that the child calls when something happens. In interviews you will hear a second name for the same thing, a callback prop, because the function it holds is a callback function: a function handed to other code so that code can call it later.

onClick on <button> vs. onSmash on <MyButton>

Both lines below give handleClick to a tag through a name that starts with on:

onClick on a built-in button, and onSmash on our own component
1<button onClick={handleClick}>Click me</button>
React calls handleClick when the user clicks
2<MyButton onSmash={handleClick} />
HandleClick only arrives in props.onSmash

It may look the same, but it is NOT the same thing! <button> is a built-in component: a tag that React gives us, such as <button> or <div>. React's docs say that built-in components support only browser event names, such as onClick, and React attaches onClick to the click of a real button in the browser. <MyButton> is our own component, and onSmash is just a prop that arrives inside props. Nothing happens on a click until MyButton gives that function to a real <button>, as its onClick={onSmash} line does.

So the name onSmash is not special. React's docs say that when you build your own components, you can name their event handler props any way you like. By habit, the prop name starts with on and a capital letter, such as onRemove, and the function that handles the event starts with handle, such as handleRemove.

One-way data flow, and the call that goes up

React's docs describe the usual direction of data with the words one-way data flow: data goes from the parent to the child through props, from the top of the tree to the bottom, and never back up as props. Think of water running downhill. On our page, guest and onRemove run down from the guest list to each row.

A callback prop does not reverse that flow. The row did not send a new list up. It sent a call with an id. The parent decided the new list, and the new list came down again as props on the next render. React's docs call this way of working inverse data flow: the child changes the parent's state by calling a function the parent passed down. The docs add that React makes this flow explicit, and that it takes a little more typing than two-way data binding, which some other tools use to let a box change a variable by itself.

React ran handleRemove while it was drawing the list, again and again, until nobody was left. Here is what happens as soon as the page opens:

  1. React calls GuestList, and map reaches the three <GuestRow> tags for John, Mia, and Sara.
  2. On each tag, the parentheses after handleRemove call it right now, during rendering.
  3. All three calls filter the same three guests of this render, so only the last call counts: the new list holds John and Mia.

Nothing here breaks a rule that React checks, so the Console stays quiet. React's docs show the same mistake in their tic-tac-toe tutorial, with a call to handleClick with the number 0 written on a square's tag. There the square with the call is always on the page, so every render calls the handler again, and the loop never ends. React stops it with the error Too many re-renders. React limits the number of renders to prevent an infinite loop., and the page goes blank.

The fix is to keep each job in its place. The parent passes the function itself, with no parentheses after handleRemove. The child adds the id inside its own arrow function on the button, which runs only when the user clicks.

Principle 3

Inverse Data Flow: guest.id Tells the Parent Which Guest

The child wraps the call to onRemove in an arrow function and passes the value the parent needs, the guest's id; the parent's handler calls its own setter, React renders the parent again, and the new list comes down as props.

The row knows which guest the user clicked, and the guest list knows how to change the list. The arrow joins the two: the row calls onRemove with its own guest.id, and the guest list's handleRemove calls setGuests. Data still flows one way. Only the call with the id goes up, and the new list comes down on the next render.

2<button onClick={() => onRemove(guest.id)}>Remove</button>

1<GuestRow key={guest.id} guest={guest} onRemove={handleRemove(guest.id)} />

The box should also empty itself after the click, so the user can type the next guest. The child can run its own code in the same handler as the call, and there are two ways to order the two lines:

  1. In this render, name is 'Leo'.
  2. Calling setName with an empty string asks React for a new render with an empty box. It does not change name in this render, as Lesson 15 taught.
  3. onAdd runs with name, which still holds 'Leo'.
  4. After the click, React renders again, and the box is empty.

Interview PrepFor the Interview

The Interview Question: How does a child component notify its parent or trigger state updates using callback props?

How to Answer Clearly in 30 Seconds

"A child cannot change its parent's state, because state is private to the component that declares it, and props are read-only. So the parent writes a handler next to its state, such as handleRemove, and passes it to the child as a prop, such as onRemove. When the user acts, the child calls that prop with the value the parent needs, such as the guest's id for onRemove or the typed name for onAdd. The parent's own handler calls its own setter, React renders the parent again, and the new data comes down as props. Three details matter:

  1. Data still flows one way: only a function call goes up, and React's docs call this inverse data flow.
  2. on names are ordinary props on our own components: only built-in components such as <button> turn onClick into a browser event. By habit, the prop starts with on and the handler with handle.
  3. Pass the function, do not call it: parentheses after handleRemove on the tag call the handler during rendering, which changes state before the user clicks and can end in Too many re-renders. The id goes into an arrow function inside the child, which runs only when the user clicks."

Three Classic Follow-Up Questions Interviewers Ask

  1. "If the child can change the parent's state, does data now flow both ways?"
    No. Data still goes only from the parent to the child through props. The child sends up a call with a value, such as an id, and nothing else. The parent decides what the new state is, and the new state comes down as props on the next render. React's docs say this makes the flow explicit, at the cost of a little more typing than two-way data binding. The benefit is that you can follow every change: the Remove button's arrow calls onRemove, GuestRow received onRemove from GuestList, and GuestList wrote handleRemove.
  2. "Why not pass setGuests itself to the child?"
    Sometimes you can. React's docs pass a setter straight down on their Thinking in React page, as onFilterTextChange={setFilterText}, because the child sends exactly the next value. But a row should not decide what the whole new list is. With onRemove, the row says only which guest the user clicked, and the parent keeps the rule for building the new list. The parent can also check the value first, such as skipping an empty name, and the child never needs to know. A name that describes the action, such as onRemove, also leaves the parent free to change how it handles it.
  3. "Does a new arrow function on every render cause problems?"
    Usually not. The arrow function in the row is a new function each time the row renders, and that is normal in React. It matters only when a child is skipped with memo and should receive the same function between renders. Then useCallback keeps one function, as Lessons 55 and 57 show. When many components deep in the tree need the same functions, passing one dispatch function or putting the functions in context saves passing them through every level, as Lessons 27 to 29 show. And when two siblings must share one changing value, the state moves up to their common parent and the same callback props connect them, as Lesson 24 shows.
