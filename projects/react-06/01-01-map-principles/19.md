# Q19: Batching and Updater Functions — Operational Principle Map
- **Source Map**: `01-01-map/19.md`
- **Topic Tag**: `#state_updates` | `❱ CORE`
- **Interview Question**: *How does React queue multiple state updates, and when do you need an updater function?*

## Authorized Scope
Q19 teaches the update queue inside the National Times newsletter widget (`PassCounter` with a "+3 Free Passes" button): every setter call from one event adds an entry to a queue instead of updating the screen, React waits until the whole handler has run and then processes the queue in a single render, a direct value adds "replace with this value" and ignores everything queued before it while an updater function receives the accumulated value, so three `setPasses(passes + 1)` calls end at 1 (each computed from the same snapshot, Q18) and three `setPasses(p => p + 1)` calls end at 3, replace-then-update and update-then-replace sequences end where the last entry says, and updaters must be pure because they run during rendering; it builds on Q16 (the setter stores the next value and triggers a re-render), Q17 (a setter queues a render and the rest of the handler runs first), and Q18 (the running handler reads its own render's snapshot and its callbacks close over it), and it excludes batching across promises, timeouts, and native listeners (Q75), `flushSync` (Q65), the StrictMode component (Q20), `Object.is` bail-outs and object and array replacement (Q21, Q22), reducers (Q29), state structure (Q25), and test flushes with `act()` (Q87).

## Principles

### Principle 1: Expect one render per event, after the whole handler has run
- **Kind**: Model
- **Rule**: A setter call queues an entry instead of updating the screen, and React waits until every line of the event handler has run before it processes the queue and renders; several setters, even on different state variables or in different components, still produce one render for that event, while each separate user event is its own batch, so a first click that disables a form is already in effect when the second click is handled.
- **Importance**: The card's Friction begins with "where did the other two updates go?", and without the batch model a developer fears one render per setter, cannot explain why a log or a measurement taken right after a click still looks at the old screen (Previews of Q65 and Q87), and cannot reason about half-finished states where only some variables have been updated.
- **Prediction**: A handler that calls two setters and logs shows the setter lines and "handler end" before a single render line, and the screen shows both updates at once; a second click produces a second render; a read placed on the line after a setter still returns the handler's snapshot value (Q18).
- **Required Lesson Proof**: Add logs to the component body and to a handler that updates two state variables; click once and show one render after the handler ends, click again and show a second render, and show that no intermediate screen state appears between the two updates.
- **Sources**: Core Truth and Mechanism of `01-01-map/19.md`; queueing "React batches state updates" and Recap bullet 2; useState `set` Caveat 3; the merged waiter, rationale, and clicks candidates.

### Principle 2: Read the queue as replacements and updaters
- **Kind**: Model
- **Rule**: During the next render React walks the queued entries in order: a direct value adds "replace with this value" and ignores everything queued before it, while an updater function is called with the accumulated value of the entries before it and its return value becomes the new accumulated value, so whatever the last entry produces is the state the next render returns.
- **Importance**: The `+3` button that adds one, and the mixed sequences (`0 + 5` then an updater gives `6`; appending `42` gives `42`), are the standard interview puzzles; the same model explains why an entry created after an `await` computes from a stale value instead of the latest one.
- **Prediction**: From `0`, three `setPasses(passes + 1)` entries show `1`; three `setPasses(p => p + 1)` entries show `3`; `setPasses(0 + 5)` then `setPasses(p => p + 1)` shows `6`, and appending `setPasses(42)` shows `42`.
- **Required Lesson Proof**: Build the "+3" widget and click it in both forms; then run the mixed sequences and log the value the next render receives, and optionally implement the page's `getFinalState` loop to pass its four cases.
- **Sources**: Under the Hood of `01-01-map/19.md`; queueing "Updating the same state multiple times before the next render", both "What happens if..." sections, and the Note; state-as-a-snapshot "+3" experiment; the merged collapse, mixed-sequence, `setState(5)`, and queue-exercise candidates.

### Principle 3: Compute from the pending state with an updater function
- **Kind**: Decision
- **Rule**: When the next value is calculated from the state it replaces, pass a function (`setPasses(p => p + 1)`); React queues it and pipes the pending value through each queued updater in order, which is what makes repeated updates in one event accumulate and what keeps an update after an `await` correct, while a direct value stays fine when the next value is independent of the old one, and for a single update per user action both styles behave the same because React applies the update before the next click.
- **Importance**: `setPending(pending - 1)` after a three-second delay subtracts from the click-time number and can drive a count to `-1`, and fast double clicks make both counters unpredictable; reviewers flag `setX(x + 1)` patterns in repeated or delayed updates, and the `+3` bug is the page's headline example.
- **Review Point — Condition**: If the update is computed from the previous value, prefer the updater form; it is necessary when the same state is updated more than once in one event or after an `await`. When the next value does not depend on the old one (`setPasses(0)`), the direct value is simpler and equally correct.
- **Required Lesson Proof**: Convert the `+3` widget to `setPasses(p => p + 1)` and show `3`; run the request counter with direct values to show `Pending: -1` after the delay, then switch both counters to updaters and show the correct numbers after two fast clicks.
- **Sources**: Core Truth and Mechanism of `01-01-map/19.md`; queueing "Updating the same state multiple times before the next render" and Challenge "Fix a request counter"; useState "Updating state based on the previous state" with its Deep Dive and Recipes; the merged RequestTracker, function-trap, Recipes, and Deep Dive candidates.

### Principle 4: Keep updater functions pure
- **Kind**: Decision
- **Rule**: An updater runs during the next render rather than inside the handler, so it must only compute and return the next value: no mutation of the previous state, no setter calls, no side effects; because it runs during rendering React may call it twice in development and discard one result, which leaves a pure updater unchanged and makes a mutating one visible.
- **Importance**: An updater that pushes into the previous array shows the new item twice in development; the failure is a standard reviewer flag and the demonstration that connects this lesson to the purity contract, and the interview probe is "where does an updater actually run?".
- **Review Point — Do not**: Do not mutate the previous state or run side effects inside an updater; return a new value, such as `[...prevPasses, newPass]`.
- **Required Lesson Proof**: Write the impure updater that pushes into the previous array and show the doubled entry (one sentence names Q20's double call), then return `[...prevTodos, todo]` and show one entry, with the array replaced rather than mutated (recall of Q21 and Q22).
- **Sources**: Mechanism and the purity paragraph of `01-01-map/19.md`; queueing closing paragraph; useState `set` Parameters and Troubleshooting "runs twice"; the merged impure-updater candidate and the Q12 purity prerequisite.

## Senior Answer
React queues the setter calls made by one event and applies them after the whole handler has run, in a single render, so code after a setter still sees the old snapshot and the screen never shows a half-updated state; separate clicks are separate batches, so each is handled with the previous click's result in place. During the next render React walks the queue in order: a direct value adds a replacement and discards everything queued before it, while an updater function receives the accumulated value of the entries before it; that is why three `setNumber(number + 1)` calls end at `1` while three `n => n + 1` updaters end at `3`, and why a replacement followed by an updater (and then another replacement) ends wherever the last entry says. When the next state depends on the previous value, especially with several updates in one event or an update after an `await`, I pass an updater and let React pipe the pending value through it; for a single independent update either style is fine. And I keep updaters pure because they run during rendering, twice in development, so I return a new value instead of mutating the old one.
