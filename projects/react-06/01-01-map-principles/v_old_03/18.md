# Q18: State as a Snapshot — Operational Principle Map
- **Source Map**: `01-01-map/18.md`
- **Topic Tag**: `#state_snapshots` | `❱ CORE`
- **Interview Question**: *Why does state appear frozen inside a render, even right after you set it?*

## Authorized Scope
Q18 teaches the snapshot model inside the National Times `StoryFeedback` form: a state variable is not a live variable but the value React handed to one render, so a setter call records the next value and queues the next render without changing the variable the running code reads, and a log, an alert, an analytics call, or a three-second timer after the setter still sees the old value; every handler, callback prop, and timer body created during that render is a closure over that render's props, state, and locals, so a handler that runs later uses the values from when the user acted rather than the newest ones, which React does on purpose so handlers are not exposed to state changing while their code runs; the lesson shows the substitution method for predicting a handler, uses the page's three-call experiment as the observable collapse of repeated setters (the queue itself is Q19's), and recalls the computed-next-value habit for the rest of the handler; it builds on Q12 (render is a pure calculation doubled by StrictMode), Q14 (handlers run on interaction and are where side effects go), Q15 (a callback is a closure that runs in the render that created it), Q16 (state lives outside the function, the initial value is used once, and only the setter changes it), and Q17 (a setter queues a render and the rest of the handler runs first), and it excludes the update queue, batching, and updater functions (Q19), the StrictMode component (Q20), refs as mutable boxes (Q33), object and array replacement (Q21, Q22), state structure and `key` resets (Q25, Q27), Effects and their dependencies (Q35, Q47), `flushSync` (Q65), concurrent rendering (Q66), and Fiber internals (Q78).

## Principles

### Principle 1: Treat the state value as frozen for the render that reads it
- **Kind**: Model
- **Rule**: A state variable is the snapshot of one render: the setter records the next value and queues the next render without changing the variable the running code reads, so a log, an alert, an analytics call, or a timer set up after the setter still sees the value React handed to this render; predict any handler by mentally substituting the render's value into its code.
- **Importance**: The card's Friction is exactly this symptom: `setEdition('Evening'); console.log(edition); sendAlert(edition);` prints and sends `'Morning'`, and a developer who reads the setter as a live assignment concludes that React's setter is broken or has a timing bug; an interviewer opens this topic with "did the set fail, or is something deeper going on?".
- **Prediction**: In the `StoryFeedback` form, `setRating(5)` followed by `console.log(rating)` prints the old number, and the same log inside a three-second `setTimeout` still prints the old number while the screen already shows `5`; three `setRating(rating + 1)` calls in one handler each compute `1` from the same `0`, so one click shows `1`, not `3` (the queue that carries those three entries is Q19).
- **Required Lesson Proof**: Add the log and the delayed log to the rating handler and show the console beside the screen; then write `const nextRating = rating + 1; setRating(nextRating); console.log(nextRating);` and show the new value inside the same handler (recall of Q17's computed-variable habit).
- **Sources**: Core Truth, Friction, and Mechanism of `01-01-map/18.md`; state-as-a-snapshot "Rendering takes a snapshot in time" and "State over time"; useState `set` Caveat 1, the Pitfall, and Troubleshooting "logging gives me the old value"; the merged substitution, `+5`, timeout, and "Remove unnecessary state" candidates.

### Principle 2: Treat every handler as a closure over the render that created it
- **Kind**: Model
- **Rule**: Each render calls the component again and creates fresh handlers and callbacks that close over that render's props, state, and local variables, so a handler, a callback prop, or a timer body that runs later uses the values from its own render, not the newest ones; React keeps these values fixed on purpose so a handler is not exposed to state changing while its code runs.
- **Importance**: A five-second delayed send alerts "You said Hello to Alice" after the user changed the recipient to Bob, and a developer who expects delayed code to read the latest state cannot explain the alert, cannot reason about stale values in async work, or accidentally trusts callbacks that captured earlier data.
- **Prediction**: In the send form, type "Hello", submit, and change To to Bob within five seconds: the alert says Alice; the traffic-light handler alerts "Stop is next" whether the `alert` line sits before or after `setWalk`, because the handler's `walk` is the value of its own render; every render's handlers are new functions even when their code looks identical.
- **Required Lesson Proof**: Run the send form, switch the recipient before the alert fires, and show that the alert uses the click-time values; then move the traffic-light alert before and after the setter and show both orders alert the same text.
- **Sources**: Under the Hood of `01-01-map/18.md`; state-as-a-snapshot "State over time" and Recap bullets 4, 5, and 7; the traffic-light Challenge Solution; the Q15 Principle 3 prerequisite; the merged send-form, recap, and fixed-values candidates.

## Senior Answer
State behaves like a snapshot. The setter does not assign to the variable in the code that is running; it records the next value and queues a new render, so after `setRating(5)` the handler's `rating` still holds the value of its render, a three-second timer it started still prints that value even though the screen has changed, and three repeated `setRating(rating + 1)` calls all compute from the same number, which is why one click adds one (the queue that carries those entries is Q19's subject). The reason is the closure: each render calls the function again and creates new handlers that close over that render's props, state, and locals, so a handler or callback that runs later uses the values from when it was created; the delayed send still says Alice after the field changed to Bob, and React fixes these values on purpose so a running handler is not exposed to state changing mid-flight. So I predict a handler by substituting the render's value into its code, I use the next value I computed for the rest of the handler, and when code truly needs the latest state I reach for the update queue and updater functions.
