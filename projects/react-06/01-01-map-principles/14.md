## Authorized Scope
Q14 teaches why a local variable cannot hold a value that changes on interaction (React creates it fresh each time it calls the component, and assigning it tells React nothing) and how `useState`, a Hook React provides, keeps the value between renders: the `[value, setValue]` pair from array destructuring, calling the setter from an event handler to store the next value and ask for a render, the initial value used on the first render only, several independent state variables in one component, and state private to each rendered instance. It builds on Q12 (React may call a component any number of times) and Q13 (handlers are passed, not called), and it leaves what happens between the setter call and the screen update to Q15, the frozen value inside a render to Q16, updater functions and batching to Q17, objects and arrays in state to Q18 and Q19, and why the call order of Hooks must never change to Q37.

## Principles

### Principle 1: Keep a changing value that the screen shows in state, not in a local variable
- **Kind**: Decision
- **Roles**: `let isBookmarked = false`: local variable our code creates fresh each time React calls `ArticleCard`; `useState(false)`: Hook React provides that keeps the value between renders; `setIsBookmarked`: setter React provides that stores the next value and asks for a render.
- **Placement**: `const [isBookmarked, setIsBookmarked] = useState(false)` at the top of the component body, and the handler calls `setIsBookmarked`; not a `let` in the body, and not a `let` at module level above the component.
- **Mechanism**: assigning a local variable: plain JavaScript, no message to React, no render; every render: the function body runs from the top, so the `let` is re-initialized; a module-level `let`: survives renders, still no render, shared by every instance of the component.
- **Defect**: the bookmark handler logs `true` while the icon stays "gray"; after a Like click re-renders the card, the next bookmark click logs `true` again, because the variable restarted at `false` (verified in React 19.3).
- **Importance**: The card's Friction and the first bug most newcomers to React ship; an interviewer expects both reasons, "no render" and "starts over", in a complete answer.
- **Review Point — Do**: Check that every value a handler changes and the JSX displays comes from `useState` and is changed only through its setter.
- **Required Lesson Proof**: Build `ArticleCard` with `let isBookmarked = false` and a `useState` like count, click Bookmark and show the console logging `true` while the icon stays gray, click Like, click Bookmark again and show `true` once more, then replace the `let` with `useState(false)` and show the icon turning blue.
- **Sources**: Core Truth, Friction, and Code Experiment of `01-01-map/14.md`; state-a-components-memory "When a regular variable isn't enough" and Recap bullet 1; the merged no-render, starts-over, module-level, and stuck-form candidates, verified in React 19.3.

### Principle 2: Expect `useState` to hand back the stored value, and read its argument as the first value only
- **Kind**: Model
- **Roles**: `useState(0)`: call our code makes on every render; `0`: initial value, read on the first render only; `likes`: value React stored for this component, returned on each render; `setLikes(likes + 1)`: call that stores the next value and asks for a render.
- **Placement**: one `useState` call per remembered value at the top of the component body, before any JSX is computed from it.
- **Mechanism**: React keeps state outside the component function, attached to this component's place in the tree; on each render `useState` returns what React stored, so the argument matters only when no value is stored yet; several calls in one component are told apart by their order (the rule that keeps the order fixed belongs to Q37).
- **Defect**: Without this model a reader expects `useState(0)` to reset the count to zero on every render, or tries to change state by calling `useState` again with a new argument.
- **Importance**: An interview probe ("why does `useState(0)` not reset?") and the model Q15, Q16, Q17, and Q80 build on.
- **Prediction**: With `console.log('render', likes)` in the body of `StoryCard`, the first render logs `0` and each click logs one more (`1`, `2`), even though the body passes `0` to `useState` every time.
- **Required Lesson Proof**: Add the log, click the like button twice, and show the console printing `render 0`, `render 1`, `render 2`.
- **Sources**: Mechanism and Under the Hood of `01-01-map/14.md`; "Anatomy of useState", Recap bullets 2 and 5, and the Deep Dive "How does React know which state to return?"; useState "Avoiding recreating the initial state"; the merged console-log candidate, verified in React 19.3.

### Principle 3: Treat each rendered instance as owning its own private state
- **Kind**: Model
- **Roles**: `StoryCard`: one component function our code defines; `<StoryCard />`: each use in JSX, a separate instance with its own state; parent component: renders the instances, holds no variable that reaches their state.
- **Placement**: state declared inside the component that uses it; a parent that needs the value cannot read it from the child.
- **Mechanism**: React stores state per rendered instance, not per function; the same definition rendered twice gets two independent values; nothing in the parent's scope points at a child's state.
- **Defect**: A reader who pictures state as belonging to the function expects a click on one card to change both counts, or tries to read a child's count from the parent and finds no variable to read.
- **Importance**: State is private and isolated is a Recap bullet and an expected part of a senior answer, and it sets up lifting state (Q23) and state identity by position (Q24).
- **Prediction**: Two `<StoryCard />` elements side by side: two clicks on the first show 2 on the first and 0 on the second.
- **Required Lesson Proof**: Render two `StoryCard` elements in `StoryList`, click the first one twice, and show 2 and 0 on screen; then point out that `StoryList` has no variable holding either count, and name Q23 as the lesson that moves shared state to the parent.
- **Sources**: Under the Hood and Code Experiment of `01-01-map/14.md`; "State is isolated and private" and Recap bullet 7; the merged two-cards candidate, verified in React 19.3; the Preview rows for Q23 and Q24.

## Senior Answer
A local variable lives only for one call of the component function. React may call that function many times, and each time the variable starts over. Assigning it is plain JavaScript that React never sees, so the screen never changes. So when a value changes on interaction and appears on screen, I keep it in state: `const [likes, setLikes] = useState(0)` at the top of the component. React stores the value outside the function. On every render `useState` returns the stored value, which is why `useState(0)` does not reset the count; the argument is only the first value. I change the value only through the setter, and I wrap that call in an arrow function in the event prop: `onClick={() => setLikes(likes + 1)}`. The setter stores the next value and asks React to render again. A component can hold several independent state variables. Each rendered instance keeps its own private state, so two `StoryCard` elements count separately, and the parent cannot read either count. If two components need the same value, the state moves up to their parent.
