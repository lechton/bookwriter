## Authorized Scope
Lesson 17 teaches what React does with several setter calls. It works on one component, `FreePasses`, which shows a count of free passes and a "+3 Free Passes" button. React waits until all the code in an event handler has run. Then it renders once. This is called batching. Each setter call adds one entry to a queue. In the next render, React works through the queue in order, starting from the current state. A plain value replaces the running result. An updater function, such as `p => p + 1`, receives the running result and returns the next one. So three updaters add three, while three plain values set the same number three times. We need an updater when the next value comes from the previous one and another update can be queued first. React calls updaters during the next render, so they must be pure. The lesson builds on Q12, pure rendering, Q15, the render after the handler, and Q16, state as a snapshot.

## Principles

### Principle 1: React renders once, after the whole event handler has run
- **Handle**: `one-render-per-event`
- **Kind**: Model
- **Reader Question**: "My click handler calls `setPasses` three times and `setNote` once. Does `FreePasses` render four times?"
- **Reader Expects**: four renders, one per setter call; a habit from plain DOM code, where each assignment to `textContent` changes the page at once, and from Q15, where a setter call is followed by a render
- **React Does**: each setter call adds its update to a queue and asks for a render; the handler keeps running and logs "handler done"; after the handler, and every other handler of the same event, has returned, React renders `FreePasses` once with every queued update; this is batching; the console shows "handler done", then a single `render passes=1 note=Thanks`; the screen shows `1` and "Thanks"; a second click is its own event: its handler logs `passes=1`, and one more render follows
- **Placement**: every setter call in one handler, for one state variable or several, waits for the same render; a separate click gets its own render
- **Real Mistake**: none; expecting four renders leads to no code that breaks, and the one log that surprises, a log after the setter that shows the old value, belongs to Q16 `fixed-in-render`
- **Importance**: interviewers ask for batching by name; it is why a log after the setter sees old values
- **Prediction**: however many setters one click calls, the body log of `FreePasses` prints once after the click, and it prints after the handler's own last log.
- **Required Lesson Proof**: `FreePasses` with `passes` and `note` state and a body log; the "+3 Free Passes" handler calls `setPasses(passes + 1)` three times and `setNote('Thanks')`, then logs "handler done"; the console shows "handler done", then one render log; a second click logs that the handler sees `passes=1`.

### Principle 2: React applies the queue in order: a value replaces, an updater receives
- **Handle**: `queue-in-order`
- **Kind**: Model
- **Reader Question**: "I call `setPasses(passes + 1)` three times. Why does the screen show 1 and not 3?"
- **Reader Expects**: each call adds one, so three calls add three; a habit from `count++` and `+=`, which change a variable step by step
- **React Does**: `passes` is `0` for the whole handler (Q16 `fixed-in-render`); each call computes `0 + 1` and adds "replace with 1" to the queue; the next render starts from the current state, `0`, and applies the entries in order: a value replaces the running result, a function would be called with it; "replace with 1" three times gives `1`; `useState` returns `1`; the screen shows `1`
- **Placement**: the order of setter calls in the handler is the order of the queue; the queue is applied in the next render, starting from the current state
- **Real Mistake**: the "+3 Free Passes" handler written as three `setPasses(passes + 1)` calls, to add three; from `0`, the screen shows `1` after the click and `2` after the next click (React 19.3.0)
- **Importance**: the interview question asks how React queues; the mixed queue is a common interview puzzle
- **Prediction**: from `0`, a handler with `setPasses(passes + 5)` and then `setPasses(p => p + 1)` shows `6`, and a log inside that updater prints `p=5` after the handler's last log, in the next render.
- **Required Lesson Proof**: `FreePasses` with one button per queue: three plain calls (screen `1`), `+5` then an updater (screen `6`), and `+5`, an updater, then `42` (screen `42`); a log in each updater of the three-updater button prints `p=0`, `p=1`, `p=2` before the render log; on a later click all three print after "handler done", but on the first click after the page loads React 19 calls the first updater at the setter call, so `p=0` prints before "handler done".

### Principle 3: Pass an updater when another update can come first
- **Handle**: `updater-from-previous`
- **Kind**: Decision
- **Reader Question**: "How do I make the +3 Free Passes button really add three? And do I need `p => p + 1` on every setter from now on?"
- **Reader Expects**: some way to read the newest count inside the handler; after the surprise of `queue-in-order`, an updater on every setter, to be safe
- **React Does**: `setPasses(p => p + 1)` adds the function itself to the queue; the next render calls it with `0` and gets `1`, then with `1` and gets `2`, then with `2` and gets `3`; the screen shows `3`; after an `await`, `pending` still holds the snapshot `0` (Q16 `handler-keeps-its-render`) while the state is already `1`; `setPending(p => p - 1)` receives `1`, and Pending shows `0`, also after two fast clicks; with one plain setter per click, React has rendered the previous click before the next handler runs, so `setPasses(passes + 1)` reads the current count and the screen rises by one per click
- **Placement**: `setPasses(p => p + 1)` when the next value comes from the previous one and the handler queues more than one update, or sets state after an `await`; a plain value, `setPasses(passes + 1)`, is fine for one update per click
- **Real Mistake**: the react.dev request counter on `FreePasses`: a Buy handler with `setPending(pending + 1)`, `await delay()`, then `setPending(pending - 1)`; after one purchase Pending shows `-1` (React 19.3.0)
- **Importance**: the card's Friction; counters that skip or go negative after a delay reach production
- **Review Point**: Condition
- **Required Lesson Proof**: the "+3 Free Passes" handler of `FreePasses` rewritten with three `setPasses(p => p + 1)` calls shows `3`; a Pending counter on the same component, supplied with a ready-made `delay` helper, ends at `-1` with plain values and at `0` with updaters, also after two fast clicks.

### Principle 4: An updater only computes and returns the next value
- **Handle**: `updater-stays-pure`
- **Kind**: Decision
- **Reader Question**: "I put a `console.log` inside `p => p + 1` to watch it work, and every line prints twice. Does my updater run twice?"
- **Reader Expects**: an updater runs once, at the moment of the setter call, like any function we call ourselves; a doubled line looks like a double click or a bug
- **React Does**: the setter queues the function; React calls it while it computes the next state, during the next render (on the first click after the page loads, the first updater at the setter call); rendering must be pure (Q12); in development under `StrictMode`, React calls each updater twice with the same `p` and keeps one result; the console shows `p=0`, `p=0`, `p=1`, `p=1`, `p=2`, `p=2`; the screen still shows `3`
- **Placement**: `p => p + 1` returns a value and does nothing else; a log, an `alert`, an API call, or another setter goes in the handler, outside the updater, with the value it needs computed there
- **Real Mistake**: after Q16 showed that an `alert` after the setter reports the old count, the `alert` moved into the updater, where the new count is: `setPasses(p => { alert('You have ' + (p + 1) + ' passes'); return p + 1; })`; under `StrictMode` every click shows the alert twice, without `StrictMode` once; the screen rises by one per click (React 19.3.0)
- **Importance**: reviewers flag side effects inside updaters; every Vite app starts with `StrictMode`, so a reader sees the doubled log on day one
- **Review Point**: Do not
- **Required Lesson Proof**: the three-updater button of `FreePasses` with a log inside each updater, rendered inside `StrictMode`; the console shows six updater lines and the screen `3`; the fixed version logs once in the handler; the `alert` moved into the handler as `setPasses(p => p + 1)` followed by an `alert` of `passes + 1` shows once per click under `StrictMode`.

## Senior Answer
React batches state updates. It waits until all the code in an event handler has run, and then it renders once. Each setter call adds an entry to a queue. In the next render, React works through the queue in order, starting from the current state. A plain value replaces the result so far. An updater function receives the result so far and returns the next one. That is why three calls to `setCount(count + 1)` add one. Each call reads the same snapshot, so the queue says "replace with one" three times. Three calls to `setCount(c => c + 1)` add three, because each updater receives the result of the one before. I use an updater when the next value comes from the previous one and another update can come first. That means several calls in one handler, or a call after an `await`. For one update per click, a plain value is fine. Updaters run during rendering, so they must be pure. In development, Strict Mode calls them twice to catch side effects.
