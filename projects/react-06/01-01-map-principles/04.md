## Operational Principles

### Principle 1: Use Curly Braces to Evaluate Dynamic Child Content
- **Operational Rule**: Place a JavaScript expression inside `{}` when JSX child content should use a value from memory. Bare text between tags remains literal markup text and does not look up a variable with the same spelling.
- **Review Point — Do**: Wrap a local value in curly braces when the screen should display that value rather than its identifier name.
- **Required Lesson Proof**: Render `<h2>headline</h2>` beside `<h2>{headline}</h2>` and show the distinct compiler inputs and screen output.

### Principle 2: Put Value-Producing Expressions Inside JSX Curly Braces
- **Operational Rule**: Use variables, property access, calls, arithmetic, template literals, logical operators, or ternaries that evaluate to a value. Statements such as `if`, `for`, and `while` do not fit an expression position inside JSX.
- **Review Point — Do not**: Do not place a control-flow statement directly inside JSX curly braces; calculate the value before the return or use an expression form.
- **Required Lesson Proof**: Show the parser rejecting `{if (...) ...}` and accepting an equivalent value prepared before JSX or produced by a ternary expression.

### Principle 3: Remove Quotes When an Attribute Should Receive a JavaScript Value
- **Operational Rule**: Use `attribute={expression}` for a dynamic attribute value. Quotation marks create a literal string, so `src="avatarUrl"` requests that text instead of reading the variable `avatarUrl`.
- **Review Point — Do**: Choose quotes for static text and curly braces without quotes for an evaluated value.
- **Required Lesson Proof**: Compare the compiled props and browser request produced by `src="avatarUrl"` and `src={avatarUrl}`.

### Principle 4: Treat Strings and Numbers as Visible JSX Output
- **Operational Rule**: React turns string and number values in a JSX child position into visible text nodes. Format, round, or convert those values deliberately when the raw representation is not the user-facing result.
- **Review Point — Do**: Check every string or number expression for the exact text it will place on screen rather than treating primitive evaluation as invisible plumbing.
- **Required Lesson Proof**: Render local strings, integers, and arithmetic results, then inspect the text nodes and show one explicit formatting step.

### Principle 5: Use Suppressed Primitives Only When No Node Is Intended
- **Operational Rule**: Booleans, `null`, and `undefined` produce no visible child node. Use that behavior for intentional absence, and convert the value to text when the user must actually see `false`, `null`, or `undefined` as diagnostic content.
- **Review Point — Condition**: Leave a suppressed primitive unconverted only when the correct rendered result is no node; use explicit text when its value is meaningful to the reader.
- **Required Lesson Proof**: Render `false`, `true`, `null`, and `undefined` beside explicit string conversions and inspect the resulting DOM.

### Principle 6: Convert Numeric Guards to Booleans Before Using `&&`
- **Operational Rule**: A numeric left operand can become the result of an `&&` expression. Because React renders numbers, a zero count can create an unwanted `0` text node instead of hiding the following element.
- **Review Point — Do**: Use a boolean comparison such as `count > 0 && <Badge />` when zero should render nothing.
- **Required Lesson Proof**: Trace `0 && <Badge />` to the numeric result `0`, show the rogue text node, and compare the guarded boolean result.
