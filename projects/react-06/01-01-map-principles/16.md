## Authorized Scope
Lesson 16 teaches why state looks frozen inside a render. It works on one component, `StoryFeedback`, which shows a story rating and a few rating buttons. React calls the component with the state for this render. Inside that render, the state variable is a constant. A setter call does not change it. The setter only tells React which value to use in the next render. So a log or an API call on the line after the setter still sees the old value. When the handler needs the new value, it computes it once in a variable and uses that variable twice. Every render also creates its own event handlers. A handler keeps the values of the render that created it, even when it runs later from a timer. The lesson builds on Q13, event handlers, Q14, `useState`, and Q15, the render that runs after the handler.

## Principles

### Principle 1: A state variable keeps one value for the whole render
- **Handle**: `fixed-in-render`
- **Kind**: Model
- **Reader Question**: "I call `setRating(5)` and log `rating` on the next line. Shouldn't it say 5 now?"
- **Reader Expects**: `5`, because the setter looks like an assignment; a habit from plain JavaScript, where `rating = 5` changes the variable at once, and from Vue and Svelte, where an assignment does; Q15 taught that the page changes after the handler, so the reader thinks only the page waits, not the variable
- **React Does**: React keeps `rating` outside the component and handed this render `0`; `const [rating, setRating]` is a constant of this call; `setRating(5)` stores `5` in React and queues a render; the next line reads the same constant and logs `rating=0`; the handler returns; React calls `StoryFeedback` again; `useState` returns `5` to the new call; the body log prints `render rating=5`; the screen shows `5`
- **Placement**: every line of one render, and every handler it creates, reads the same `rating`; the new value exists only in the next render
- **Real Mistake**: a log after the setter to check it worked, `setRating(5); console.log(rating)`, prints `rating=0` and looks like a bug in React; a "+3" handler with three `setRating(rating + 1)` calls moves the screen from `2` to `3`, because all three read `2` (React 19.3.0)
- **Importance**: the interview question itself; developers read the old value and file a bug against React
- **Prediction**: logs before and after `setRating(5)` print the same `rating=0`, and the body log of the next render prints `rating=5`.
- **Required Lesson Proof**: `StoryFeedback` with `useState(0)`, a body log of `rating`, and a "5 stars" button whose handler logs `rating` before and after `setRating(5)`; the click logs `rating=0` twice, then `render rating=5`; a "+3" button with three `setRating(rating + 1)` calls moves the screen from `2` to `3`.

### Principle 2: Compute the next value once and use it after the setter
- **Handle**: `compute-next-once`
- **Kind**: Decision
- **Reader Question**: "When the reader clicks 5 stars, I set the rating and send it to the server. Which value do I give `sendRating`?"
- **Reader Expects**: `rating`, right after `setRating(5)`, because it now holds the value just set; a habit from plain JavaScript, where code after an assignment reads the new value
- **React Does**: `rating` is this render's constant, `0` (`fixed-in-render`); `setRating(5)` queues the next render; `sendRating(rating)` records `0`; after the handler the screen shows `5`; with `const nextRating = 5`, the running handler holds `5` now; `setRating(nextRating)` and `sendRating(nextRating)` both get `5`; the recorded send is `5` and the screen shows `5`
- **Placement**: in the handler, `const nextRating = 5`, then `setRating(nextRating)` and `sendRating(nextRating)`; not `sendRating(rating)` on the line after the setter
- **Real Mistake**: `setRating(5); sendRating(rating)` in the "5 stars" handler; the recorded send is `0` while the screen shows `5` (React 19.3.0)
- **Importance**: the card's Code Experiment; analytics and API calls that send the previous value reach production
- **Review Point**: Do
- **Required Lesson Proof**: the "5 stars" handler of `StoryFeedback` calls `setRating(5)` and then `sendRating(rating)`; the recorded send is `0` and the screen shows `5`; the fixed handler computes `nextRating` once, and the recorded send is `5`.

### Principle 3: A handler keeps the state of the render that created it
- **Handle**: `handler-keeps-its-render`
- **Kind**: Model
- **Reader Question**: "My Send button starts a `setTimeout` that thanks the reader for the rating. If the rating changes before the timer fires, which number does the message show?"
- **Reader Expects**: the newest rating, because the callback reads `rating` when it fires; a habit from plain JavaScript, where a closure over one `let` sees every later assignment
- **React Does**: the render with `rating` `5` created its own Send handler; the click runs that handler, which schedules a callback that closes over that render's `rating`; clicking 2 calls the setter; React calls `StoryFeedback` again, with a new `rating` of `2` and new handlers; the screen shows `2`; the timer fires the old callback; it reads its own render's `rating`; the log says "Thanks for rating 5" while the screen still shows `2`
- **Placement**: a `setTimeout` callback, or code after an `await`, created in one render reads that render's `rating`, whenever it runs
- **Real Mistake**: none
- **Importance**: interviewers ask about stale closures; Q29, Q35, and Q36 build on it
- **Prediction**: a message scheduled with `setTimeout` reports the rating shown when Send was clicked, even after the rating on screen has changed.
- **Required Lesson Proof**: `StoryFeedback` with a Send button whose handler calls ``setTimeout(() => log(`Thanks for rating ${rating}`), 100)``; rate `5`, click Send, rate `2` before the timer fires; the screen shows `2`, and the log says "Thanks for rating 5".

## Senior Answer
State is not frozen because the setter failed. It is frozen because each render gets its own snapshot. React keeps state outside the component. When it calls the component, `useState` hands back the value for this render. In that render, the state variable is a constant. Calling the setter stores the next value in React and asks for a new render. It cannot change the constant the running code already holds. So a log right after the setter prints the old value. Three calls to `setCount(count + 1)` all read the same `count`. When I need the new value right away, I compute it once in a variable. Then I pass that variable to the setter and to the API call. Event handlers are closures over their own render. A timer started in one render still sees that render's values when it fires. That protects delayed code from values that changed in the meantime.
