## Authorized Scope
Q16 teaches that a state variable holds one fixed value for the whole of one render: setting state does not change the variable our code already has, it asks React for a new render in which `useState` returns the new value; three `setNumber(number + 1)` calls in one handler therefore add 1; code after the setter that needs the new value takes it from a variable our code computed; and every event handler keeps the values of the render that created it, even when it runs later from a `setTimeout`. It builds on Q14 (React stores state and the setter asks for a render) and Q15 (the render and commit happen after the handler returns), and it leaves updater functions as the way to add three in one click to Q17, refs for a value that must be current when delayed code runs to Q29, and stale values inside Effects to Q35 and Q36.

## Principles

### Principle 1: Read state as fixed for the whole render
- **Kind**: Model
- **Roles**: `edition`: constant for this render, holding the value React handed to this call of the component; `setEdition('Evening')`: request for a next render with a new value; next render: a new call of the component, in which `useState` returns `'Evening'`.
- **Placement**: reasoning happens inside one handler: every read of `edition` in it sees the value from the render that created the handler.
- **Mechanism**: React calls the component with the state for this render; `const [edition, setEdition]` makes `edition` a constant inside that call; the setter cannot reach a variable inside a call that is already running; three `setNumber(number + 1)` calls each read the same `number` and each request `setNumber(0 + 1)`.
- **Defect**: A reader expecting the variable to change calls the setter "broken" or "asynchronous", and adds delays or extra setter calls that change nothing.
- **Importance**: The card's Friction and the question itself; a senior answer to "is `setState` asynchronous?" explains that the variable is a constant of the render, not that the call is slow.
- **Prediction**: In `handlePublish`, `console.log(edition)` after `setEdition('Evening')` prints `Morning` while the screen then shows Evening; a "+3" button whose handler calls `setNumber(number + 1)` three times shows 1 after one click and 2 after the next.
- **Required Lesson Proof**: Click Publish and show `Morning` in the console with Evening on screen; click "+3" twice and show 1, then 2; rewrite the handler with the render's value substituted (`setNumber(0 + 1)` three times) to show why.
- **Sources**: Core Truth, Friction, Mechanism, and Code Experiment Naive of `01-01-map/16.md`; state-as-a-snapshot "Rendering takes a snapshot in time", Recap bullets 3, 5, and 6, and the Challenge "Implement a traffic light"; useState Pitfall and `set` Caveat 1; the merged log, "+3", substitution, and "asynchronous" candidates, verified in React 19.3.

### Principle 2: Compute the next value once and use that variable after the setter
- **Kind**: Decision
- **Roles**: `nextRating`: local constant our code computes before the setter call; `setRating(nextRating)`: stores the value for the next render; `sendRating(nextRating)`: sends the same value now.
- **Placement**: inside the handler, `const nextRating = ...` before `setRating`, and every later line reads `nextRating`; not `sendRating(rating)` after `setRating`.
- **Mechanism**: the state variable keeps this render's value for the rest of the handler (Principle 1); a local constant holds the new value immediately.
- **Defect**: `setRating(5); sendRating(rating)` sends 3 to the server while the screen shows 5, so the server and the screen disagree (verified in React 19.3).
- **Importance**: A shipped bug: analytics, API calls, and log lines record the previous value, and a reviewer flags any read of a state variable after its own setter.
- **Review Point — Do**: Check that a handler which sets state and then uses the new value reads it from a local variable computed before the setter call, not from the state variable.
- **Required Lesson Proof**: In `StoryFeedback`, call `setRating(5)` then `sendRating(rating)` and show 3 in the console and 5 on screen; change to `const nextRating = 5` passed to both and show 5 in both places.
- **Sources**: Code Experiment of `01-01-map/16.md`; useState Troubleshooting "I've updated the state, but logging gives me the old value"; the merged rating and API-call candidates, verified in React 19.3.

### Principle 3: Expect a handler to keep the values of the render that created it
- **Kind**: Model
- **Roles**: handler from render 1: closure over `number = 0` and `to = 'Alice'`; handler from render 2: a new function with the new values; `setTimeout` callback: created inside render 1's handler, so it reads render 1's values.
- **Placement**: delayed code (`setTimeout`, a promise callback) inside a handler reads the values of the render in which the handler was created.
- **Mechanism**: each render creates its own handlers; a JavaScript function keeps the variables of the scope where it was created; a later render creates new variables and new handlers and leaves the old ones as they were.
- **Defect**: A reader expecting delayed code to see the latest state reports the alert showing 0 as a React bug and patches it with extra state, which still reads the old render's values.
- **Importance**: Interviewers probe it, it makes delayed handlers safe from later edits, and it is the model behind stale values that refs (Q29) and Effects (Q35, Q36) handle later.
- **Prediction**: A handler that calls `setNumber(number + 5)` and then `setTimeout(() => alert(number), 3000)` alerts 0 while the screen shows 5; a message sent to Alice with a five-second delay still says "You said Hello to Alice" after the To field changes to Bob.
- **Required Lesson Proof**: Click the "+5" button, show 5 on screen and 0 in the alert three seconds later; then send to Alice, switch the field to Bob, and show the alert naming Alice.
- **Sources**: Core Truth, Under the Hood, and Code Experiment React of `01-01-map/16.md`; state-as-a-snapshot "State over time" and Recap bullets 4 and 7; the merged alert, Alice, and closure candidates, verified in React 19.3.

## Senior Answer
State is not a variable that changes in place. When React calls my component, it hands over the state for that render, and `const [edition, setEdition] = useState('Morning')` makes `edition` a constant for that whole call. Calling `setEdition('Evening')` does not change that constant. It asks React for a new render, in which `useState` returns `'Evening'`. So a log right after the setter prints `Morning`, and calling `setNumber(number + 1)` three times adds 1, because each call reads the same `number`. This is not a slow call; the variable simply belongs to the render. When the rest of my handler needs the new value, I compute it once, `const nextRating = 5`, and pass that variable both to the setter and to the code that sends it. Each render also creates its own event handlers, and each handler keeps that render's values. A `setTimeout` started from a click therefore reports the value from the moment of the click, and a delayed message still goes to the recipient the reader chose. Adding three in one click, by reading the latest queued value, is a separate tool.
