## Operational Principles

### Principle 1: Provide a Real Browser Element as the Mount Container
- **Operational Rule**: Put a stable host element such as `<div id="root"></div>` in `index.html` and resolve that exact DOM element before creating the React root. A missing or misspelled target leaves React with no physical browser node to manage.
- **Review Point — Do**: Verify that the container exists and that its identifier matches the lookup in the JavaScript entry module.
- **Required Lesson Proof**: Show the empty host element, the result of `document.getElementById('root')`, and the target-container error caused by an identifier mismatch.

### Principle 2: Declare the Browser Entry Script as an ES Module
- **Operational Rule**: Load `main.jsx` from `index.html` with `type="module"` so the browser applies ES Module semantics and the entry can use static `import` statements. A classic script does not provide the module scope expected by the React entry graph.
- **Review Point — Do**: Verify that the HTML entry declares the React source as a module and points to the intended entry path.
- **Required Lesson Proof**: Remove `type="module"`, show the import or script-mode failure, then restore `<script type="module" src="/src/main.jsx">` and inspect the module request.

### Principle 3: Run JSX Through Vite's Transform Pipeline
- **Operational Rule**: Serve or build the module graph through Vite so JSX is transformed into browser-compatible JavaScript and imports are resolved. A module declaration alone does not teach the browser JSX syntax, and opening the source through `file://` bypasses the development pipeline.
- **Review Point — Do not**: Do not expect a browser to parse raw `.jsx` merely because the script is marked as a module; run the project through the configured build tool.
- **Required Lesson Proof**: Compare a raw-file JSX syntax failure with the transformed module response served by Vite for the same entry source.

### Principle 4: Import the Browser Renderer from `react-dom/client`
- **Operational Rule**: Import `createRoot` from `react-dom/client` because the React core package defines component and element behavior while the client renderer owns browser DOM attachment. Importing from the wrong package confuses the renderer boundary and does not provide the mounting API.
- **Review Point — Do**: Check that browser entry code imports `{ createRoot }` from `react-dom/client`.
- **Required Lesson Proof**: Place the `react` and `react-dom/client` responsibilities side by side, then show the valid named import and the failure from an incorrect module source.

### Principle 5: Create One Root per Managed DOM Container
- **Operational Rule**: Call `createRoot(container)` once during startup for each independent React-managed DOM container and retain the returned root. A full React application normally has one root, while separately embedded React islands may intentionally have several containers and roots.
- **Review Point — Condition**: Use one root for one fully React-owned application surface; add another only for a genuinely independent DOM island.
- **Required Lesson Proof**: Compare one application root containing a nested component tree with two intentionally independent host containers, and show why repeated root creation is not a component update mechanism.

### Principle 6: Render Through the Root Object with `root.render`
- **Operational Rule**: Call `root.render(<App />)` on the root returned by `createRoot` and let that root manage its container from then on. React 19 removed the legacy `ReactDOM.render` entry API; Q02 already owns the requirement to express `App` as a JSX component element.
- **Review Point — Do not**: Do not use the removed `ReactDOM.render` entry API in a React 19 application; render through the retained root object.
- **Required Lesson Proof**: Show the modern two-step `createRoot` and `root.render` pipeline beside the legacy call, while treating `<App />` as reused Q02 syntax rather than a new Q09 principle.
