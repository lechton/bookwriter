## Operational Principles

### Principle 1: Name Custom Components in PascalCase
- **Operational Rule**: Start a custom component name with a capital letter so the JSX transform emits a JavaScript identifier. A lowercase JSX tag is routed as a host element name rather than as the component function you intended to run.
- **Review Point — Do not**: Do not render a custom component with a lowercase tag such as `<articleCard />`; it does not invoke `articleCard` as a React component.
- **Required Lesson Proof**: Compare compiler output for `<ArticleCard />` and `<articleCard />`, then show the unknown lowercase DOM element produced by the latter.

### Principle 2: Keep Render-Phase Component Code Pure
- **Operational Rule**: Compute the returned UI from the component's inputs and local calculations without changing preexisting values or external systems during render. React may evaluate rendering more than once, so render-phase side effects produce unstable results.
- **Review Point — Do not**: Do not mutate an outer variable, storage, the DOM, or another external system while the component function is rendering.
- **Required Lesson Proof**: Render the same component more than once and show an external counter or collection drifting when the function mutates it.

### Principle 3: Make Every Component Return Path Intentional
- **Operational Rule**: Return JSX, another React-renderable value, or explicit `null` when the component intentionally displays nothing. React 18 and later can tolerate `undefined`, but an implicit fall-through still hides an unfinished or forgotten return path.
- **Review Point — Prefer**: Prefer explicit `return null` for deliberate absence and make unintended fall-through visible to linting or review.
- **Required Lesson Proof**: Compare a normal JSX return, an intentional `null` branch, and an accidental missing `return` without claiming that every `undefined` result throws at runtime.

### Principle 4: Render Components as JSX Elements Rather Than Calling Them Directly
- **Operational Rule**: Use `<ArticleCard />` so React creates and owns a component boundary. Calling `ArticleCard()` as an ordinary function bypasses that boundary and breaks React's ability to associate rendering behavior with the component node.
- **Review Point — Do not**: Do not call a component directly from render code as a substitute for a JSX element.
- **Required Lesson Proof**: Compare the element produced by `<ArticleCard />` with direct function execution and show the missing component boundary in the component tree.
