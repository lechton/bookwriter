# Q07: Container Composition with Children and Prop Spreading — Operational Principle Map
- **Source Map**: `01-01-map/07.md`
- **Topic Tag**: `#children` | `❱ CORE`
- **Interview Question**: *How do the children prop, spread attributes, and default values work?*

## Authorized Scope
Q07 teaches slot composition with static data: JSX nested between a component's opening and closing tags arrives as the ordinary `children` prop, a container such as `CardContainer` decides where that content sits while the caller decides what it is, JSX spread (`{...rest}`) forwards the attributes a wrapper does not consume, and attribute position around a spread decides which values are overridable defaults and which are enforced; it builds on Q02 component definition, Q03 JSX compilation, Q04 curly-brace values, Q05 the UI tree, and Q06 props, destructuring, parameter defaults, and the read-only contract, and it excludes render props and context (both named by the card), state and re-renders, list mapping and keys (Q11), conditional branches (Q10), the `Children` and `cloneElement` APIs (Q100), named JSX slots (Q88), and `ref` forwarding (Q85).

## Principles

### Principle 1: Read nested JSX as the `children` prop
- **Kind**: Model
- **Rule**: Whatever JSX a caller writes between a component's opening and closing tags is compiled into the same props object as the attributes, under the key `children`, so a container reads it like any other prop and the caller, not the container, chooses the content.
- **Importance**: An interviewer expects "children is just a prop" as the first sentence of the answer, and Q60, Q88, and Q115 build their composition patterns on this model.
- **Prediction**: A `console.log(props)` inside `CardContainer` shows a `children` key next to the attributes, and `<CardContainer children="attr">nested</CardContainer>` renders `nested`, because the nested content is written into `props.children` after the attribute.
- **Required Lesson Proof**: Render `<CardContainer><Headline /></CardContainer>`, log the props object in the console to show the `children` key, then render the attribute-versus-nested case and show `nested` on screen.
- **Sources**: Core Truth and Under the Hood of `01-01-map/07.md`; passing-props "Passing JSX as children" and Recap bullet 5; the merged attribute-versus-nested candidate verified in React 19.3.

### Principle 2: Place `{children}` where the slot belongs
- **Kind**: Decision
- **Rule**: A container returns its own frame and puts `{children}` at the exact position where the caller's content belongs, because React renders nested JSX only where a component places it; a container that omits `{children}` discards the content silently.
- **Importance**: A developer ships an empty card with no warning or error in the console, so the bug survives until a person notices the missing headline on screen.
- **Review Point — Do**: Check that every component that accepts nested content renders `{children}` once, inside the element that should contain it.
- **Required Lesson Proof**: Remove `{children}` from `CardContainer`, show the card frame on screen without the headline and a silent console, and show that a `console.log` in the nested `Headline` body never runs; restore `{children}` and show both the headline and the log.
- **Sources**: passing-props "Passing JSX as children" (the "hole" filled by the parent); Code Experiment; the merged candidate that the nested component never runs, verified in React 19.3.

### Principle 3: Treat children as descriptions, not rendered output
- **Kind**: Model
- **Rule**: The caller creates element descriptions such as `{ type: Headline, props: {} }` and hands them to the container, so the container runs first, receives descriptions of what to render, and never sees what those components will return.
- **Importance**: Without this model a developer expects a container to inspect or count what its children render, which breaks the moment a child is extracted into its own component such as `<MoreRows />`, and Q60's composition-over-memoization argument depends on it.
- **Prediction**: Logging `children.type` inside `CardContainer` prints the `Headline` function rather than an `<h2>`, and the "CardContainer body" log appears before the "Headline body" log.
- **Required Lesson Proof**: Add a `console.log` to `CardContainer` and to `Headline`, render the composition once, and show the order of the two logs and the logged `children.type` in the console.
- **Sources**: Under the Hood ("opaque element descriptor tree"); Children.md Pitfall "does not include rendered output" and Troubleshooting; createElement Deep Dive "What is a React element, exactly?"; render order verified in React 19.3.

### Principle 4: Never depend on the shape of `children`
- **Kind**: Decision
- **Rule**: Render `children` as one opaque value, because React passes a single element as an object, several elements as an array, text as a string, and no content as `undefined`; code that reads `children.length` or calls array methods works for one caller and fails for the next.
- **Importance**: `children.map(...)` throws `TypeError: children.map is not a function` as soon as a caller nests a single child, and interviewers probe exactly this shape question.
- **Review Point — Do not**: Do not call array methods or read `.length` or an index on `children`; place it whole with `{children}`, and when the container needs per-item data, accept an explicit prop instead.
- **Required Lesson Proof**: Log `Array.isArray(children)` and `children.length` for one nested element and for two, showing `false` and `undefined` versus `true` and `2`, then show the `TypeError` in the console when a single-child caller meets `children.map`.
- **Sources**: Under the Hood; Children.md Deep Dive "Why is the children prop not always an array?"; common.md `children` definition; the Preview rows for the `Children` API (Q100) and explicit array props (Q11).

### Principle 5: Compose inner layout through `children` instead of layout-flag props
- **Kind**: Decision
- **Rule**: When callers need different inner layouts, let them nest the pieces (`<LiveBadge />`, `<Byline />`) inside the container instead of adding a prop and an internal branch for each variation, and keep a named prop only for a piece the container itself must guarantee, position, or format on every use.
- **Importance**: A senior reviewer flags a `NewsCard` whose API grows another `hasImage`, `badgeText`, or `buttonText` prop with every design request, because each change edits the shared component and risks every other caller.
- **Review Point — Condition**: If the content varies by caller, pass it as `children`; if every instance must show it in a fixed place and format, such as a required title, keep it a named prop.
- **Required Lesson Proof**: Show the Naive `NewsCard` needing a new prop and a new branch for a "Live" badge, then render three different compositions through an unchanged `CardContainer` file, one of which adds the badge without editing the container.
- **Sources**: Friction and Code Experiment of `01-01-map/07.md`; passing-props Challenge 3 Solution (title as a separate prop), merged; the Preview row for named JSX slots (Q88).

### Principle 6: Keep spread for pass-through wrappers
- **Kind**: Decision
- **Rule**: Name the props a component reads in its parameter list and at its call sites, and use `{...props}` or `{...rest}` only where a wrapper forwards attributes it does not read to one underlying element, because spread hides which values a child actually receives.
- **Importance**: react.dev states it in bold ("Use spread syntax with restraint"), and a reviewer who cannot see from a call site which data a component receives asks for explicit props or a `children` split.
- **Review Point — Prefer**: Prefer explicit props for data a component uses; accept spread when a wrapper passes through arbitrary HTML attributes, and treat frequent spread as a sign to extract components and pass JSX as `children`.
- **Required Lesson Proof**: Compare the explicit `<Avatar person={person} size={size} />` call with `<Avatar {...props} />` and show that only the explicit version reveals, in one file, which props the child receives.
- **Sources**: passing-props "Forwarding props with the JSX spread syntax" and Recap bullet 4.

### Principle 7: Forward only the props you did not consume
- **Kind**: Decision
- **Rule**: Destructure the props a wrapper uses (`tone`, `title`, `children`) and spread only `...rest` onto the DOM element, so callers can still pass `id`, `aria-*`, and `data-*` while component-only props never reach the DOM.
- **Importance**: Spreading the whole props object onto a DOM element produces the development warning "React does not recognize the `isFeatured` prop on a DOM element", the warning "Received `true` for a non-boolean attribute `featured`", or, worse, a silent leak such as `kicker="Sport"` in the markup or a consumed `title` turned into a hover tooltip.
- **Review Point — Do not**: Do not spread the full props object onto a DOM element when the component consumes props of its own; separate them with `({ tone, children, ...rest })` and spread `rest`.
- **Required Lesson Proof**: Spread the whole props of `CardContainer` onto its `<div>`, show the two warnings in the console and the leaked `kicker` and `title` attributes in the DevTools Elements panel, then destructure and spread `rest`, and show a clean `<div>` that still carries a caller's `aria-label`.
- **Sources**: Mechanism (`{...restProps}`); passing-props spread section; common.md custom-attributes paragraph; the merged warning, leak, and accessibility candidates, verified in React 19.3.

### Principle 8: Order attributes around the spread to choose defaults or enforced values
- **Kind**: Decision
- **Rule**: JSX applies attributes from left to right, so a value written before `{...rest}` is a default the caller can override and a value written after it is enforced; a `className` in `rest` replaces the wrapper's class, so merge it explicitly from a destructured `className = ''`.
- **Importance**: A reviewer flags a wrapper whose required attribute callers can silently overwrite, or whose default callers cannot change, and a card that loses its base `card` class the moment a caller adds `className="wide"`.
- **Review Point — Condition**: If the caller may change the value, write it before the spread; if the wrapper must keep it, write it after; if both sides contribute a class, destructure `className = ''` and render ``className={`card ${className}`}``.
- **Required Lesson Proof**: Render `<div className="card" {...rest} />` with `className="wide"` and show `class="wide"` in the Elements panel, move the attribute after the spread and show `class="card"`, then apply the explicit merge and show `class="card wide"`, and show `"card undefined"` when the `= ''` default is missing.
- **Sources**: Mechanism (spread forwarding); the merged `className` candidate, verified in React 19.3; the Prerequisite row for parameter defaults (Q06).

## Senior Answer
Anything I nest between a component's tags reaches it as the `children` prop, an ordinary key in the props object, so a container such as `CardContainer` owns its frame and places `{children}` where the content belongs, while the caller decides what the content is; the container receives element descriptions, runs before them, and cannot see what they render, so I treat `children` as opaque, never index it or call array methods on it, and switch to an explicit prop when I need per-item control. That is what replaces a `NewsCard` with a dozen layout flags: variable inner layout goes in `children`, and only pieces the container must guarantee stay named props. For spread, I name the props a component reads and keep `{...rest}` for pass-through wrappers, destructuring what I consume so that only the leftover attributes reach the DOM, which avoids React's unknown-prop warnings and silent leaks like a `title` turned into a tooltip, and I place fixed attributes before the spread when callers may override them and after it when they must not, merging class names explicitly. Default values are ES parameter defaults in the destructuring, such as `className = ''`, and they apply only when a prop is missing or `undefined`, never for `null` or `0`; `defaultProps` on function components is ignored in React 19.
