# Q11: Rendering Lists and Keys — Operational Principle Map
- **Source Map**: `01-01-map/11.md`
- **Topic Tag**: `#rendering_lists` | `❱ CORE`
- **Interview Question**: *How do you render a list from an array, and why does React demand a key on every item?*

## Authorized Scope
Q11 teaches turning an array of story objects into an array of JSX elements with `.map()` inside curly braces (`{stories.map(story => <StoryRow key={story.id} story={story} />)}`), where each key goes, what makes a key correct, and why keys give items identity across renders; the identity proof re-renders the feed with a prepended story through a second `root.render` call and uses uncontrolled `<input>` fields, whose typed text lives in the DOM, so no state is needed; it builds on Q03 Fragments, Q04 curly-brace expressions, Q06 props, Q08 imports, Q09 `root.render`, and Q10 boolean guards, and it excludes state-driven insertion, removal, and filtering (Q22, Q25), resetting state with a key (Q27), deep reconciliation and state-leak bugs (Q61), virtualization (Q62), and the `Children` API (Q100).

## Principles

### Principle 1: Build a list by mapping data to an array of elements
- **Kind**: Model
- **Rule**: `stories.map(story => <StoryRow story={story} />)` is ordinary JavaScript that returns a new array of element descriptions, one per story, and React renders an array placed inside curly braces as its items in order, so the list's shape follows the data.
- **Importance**: An interviewer expects "map the data to JSX" as the first half of the answer, and a developer without the model writes thirty hand-coded rows that drift from the data.
- **Prediction**: Logging the result of `stories.map(...)` prints an array of element objects whose `type` is the row component and whose `key` is the story ID, and adding a story to the array adds a row without touching the JSX.
- **Required Lesson Proof**: Replace hand-written headline rows with a `stories` array and one `map` call, log the mapped array in the console, and add a fourth story to show a fourth row.
- **Sources**: Core Truth and Mechanism of `01-01-map/11.md`; rendering-lists "Rendering data from arrays"; the merged console candidate, verified in React 19.3.

### Principle 2: Return the JSX from the `map` callback
- **Kind**: Decision
- **Rule**: An arrow function returns the expression right after `=>`, but a block body (`=> {`) returns only what a `return` statement returns, so a callback with braces must write `return <StoryRow ... />`.
- **Importance**: react.dev marks it as a Pitfall because the mistake is silent: the callback returns `undefined` for every story, the `<ul>` renders empty, and the console shows no error and no key warning.
- **Review Point — Do**: Check that every `map` callback either uses an expression body or returns the JSX explicitly from its block body.
- **Required Lesson Proof**: Write the callback as `story => { <StoryRow story={story} /> }`, show the empty `<ul>` in the Elements panel with a silent console, then add `return` and show the rows.
- **Sources**: rendering-lists Pitfall on arrow functions; the merged empty-list candidate, verified in React 19.3.

### Principle 3: Put a unique key on the element directly inside `map`
- **Kind**: Decision
- **Rule**: The key belongs on the outermost element the `map` callback returns, such as `<StoryRow key={story.id} />` or `<Fragment key={story.id}>`, not on the root element inside `StoryRow`, it must be unique among the siblings of that array, and it must be written directly on the tag rather than inside a spread object.
- **Importance**: A missing or misplaced key logs "Each child in a list should have a unique "key" prop.", duplicate keys log "Encountered two children with the same key", and a key hidden in a spread object logs "A props object containing a "key" prop is being spread into JSX"; extracting a row component is exactly when keys get left behind.
- **Review Point — Do**: Check that each element returned from `map` carries its own unique key, that `<>` is replaced by `<Fragment key>` when items return several nodes, and that the key is written as `key={...}` next to any spread.
- **Required Lesson Proof**: Show the missing-key warning, move the key inside `StoryRow` and show the warning persist with "Check the render method of `Feed`", move it to `<StoryRow key={story.id} />` and show a clean console, then show the duplicate-key and spread-key warnings and their fixes.
- **Sources**: Mechanism of `01-01-map/11.md`; rendering-lists key section, Note, "Rules of keys", Deep Dive, and the Challenges "Extracting a list item component" and "List with a separator"; Fragment.md; the merged placement, Fragment, duplicate, scope, and spread candidates, verified in React 19.3.

### Principle 4: Treat keys as the identity React uses to match items between renders
- **Kind**: Model
- **Rule**: When a list renders again, React pairs each new element with the previous element that has the same key and keeps that item's DOM node, so an item keeps its node when it moves; without keys, or with index keys, React pairs items by position and rewrites each position's content in place.
- **Importance**: This is the second half of the interview question, and the model every later lesson on state preservation (Q27), list updates (Q22), and reconciliation (Q61) relies on.
- **Prediction**: After typing "fix typo in Budget" into the first row's `<input>` and re-rendering with an urgent story prepended, ID keys show the text next to "Budget passes" in the second row, while index keys leave it in the first row next to "URGENT: Election called"; a DOM node marked before the re-render moves to the second row with ID keys and stays first with index keys.
- **Required Lesson Proof**: Render the feed, type into the first input, mark the first `<li>` in the console, call `root.render` again with the prepended story, and show the typed text and the marked node for index keys and for ID keys.
- **Sources**: Under the Hood and Friction of `01-01-map/11.md`; rendering-lists "Why does React need keys?"; the merged prepend candidate, verified in React 19.3 with Vite 8.3.1.

### Principle 5: Key items by a stable ID from the data
- **Kind**: Decision
- **Rule**: Use an ID that belongs to the item and never changes, such as `story.id` from the database or an ID created together with a local item, because the index changes when stories are inserted or reordered and a value generated during render, like `Math.random()`, changes on every render.
- **Importance**: With index keys an editor's correction ends up next to the wrong headline after a prepend, and with random keys every row's DOM is destroyed and recreated on each render, so typed text disappears and rendering slows.
- **Review Point — Do not**: Do not use the index for a list that can reorder, insert, or delete, and do not generate keys while rendering; use the item's own ID, or an index only for a static list that never changes order.
- **Required Lesson Proof**: Repeat the prepend experiment with `key={Math.random()}` and show every input emptied, then switch to `key={story.id}` and show the correction staying with "Budget passes".
- **Sources**: Code Experiment and Friction of `01-01-map/11.md`; rendering-lists Pitfall, "Where to get your `key`", and the Challenges "Nested lists" and "List with a separator", merged; the random-key output verified in React 19.3; the Preview row for state-leak bugs (Q61).

### Principle 6: Pass the ID as its own prop when the row needs it
- **Kind**: Decision
- **Rule**: React consumes `key` for matching and does not pass it to the component, so a row that needs the story's ID, for a link or a `data-` attribute, receives it through a separate prop such as `<StoryRow key={story.id} storyId={story.id} />` or through the `story` object.
- **Importance**: A developer who reads `props.key` gets `undefined` and the warning "`key` is not a prop. Trying to access it will result in `undefined` being returned. If you need to access the same value within the child component, you should pass it as a different prop."
- **Review Point — Do**: Check that no component reads `key` from its props and that any ID it needs arrives as an ordinary prop.
- **Required Lesson Proof**: Render `{String(props.key)}` inside the row and show `undefined` on screen with the warning in the console, then pass `storyId` and show the ID rendered.
- **Sources**: rendering-lists Pitfall ("your components won't receive `key` as a prop"); the merged warning candidate, verified in React 19.3.

## Senior Answer
I render a list by mapping the data array to an array of elements inside curly braces, `{stories.map(story => <StoryRow key={story.id} story={story} />)}`, remembering that a callback with a block body must `return` its JSX or the list silently renders empty. Every element directly inside the `map` needs a key that is unique among its siblings, placed on that element (on `<StoryRow>` or on `<Fragment key>`, not inside the row component) and written directly rather than spread. React demands keys because they are the identity it uses to match items between renders: it pairs each new element with the old one that has the same key and keeps its DOM node, so a story keeps its node, its typed text, and later its state when the list changes; without keys, or with the index, React matches by position, so prepending a story leaves an editor's correction next to the wrong headline, and random keys recreate every row on each render. So I use a stable ID from the data, allow the index only for static lists, and pass the ID as a separate prop when the row needs it, because `key` never reaches the component.
