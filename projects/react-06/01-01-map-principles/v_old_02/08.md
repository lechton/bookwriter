## Principles

### Principle 1: Decompose monolithic files into dedicated component modules with standard ES exports
- **Kind**: Decision
- **Rule**: Split monolithic component files into dedicated `.jsx` files, reserving `export default` for the primary component and using named `export function` for secondary helpers or variants, preventing merge conflicts, reducing cognitive load, and enabling clean cross-file reuse.
- **Importance**: Monolithic files (the card's 1,200-line `App.jsx`) block multi-developer workflows with merge conflicts and prevent reuse; reviewers flag monolithic files and demand component decomposition.
- **Review Point — Prefer**: Prefer moving distinct components into dedicated files; reserve `export default` for the file's primary component and use named exports for secondary utilities.
- **Required Lesson Proof**: Refactor a monolithic `App.jsx` containing `App`, `ArticleCard`, and `SubscriberBadge` by extracting `ArticleCard` and `SubscriberBadge` into `src/components/ArticleCard.jsx` with a default card export and a named badge export; import and render both cleanly in `App.jsx`.
- **Sources**: card Core Truth, Mechanism, Code Experiment; `importing-and-exporting-components.md` Intro, "Exporting and importing a component", DeepDive.

### Principle 2: Match import syntax strictly to export declaration to prevent undefined component errors
- **Kind**: Decision
- **Rule**: Import default exports using a bare identifier without curly braces (`import ArticleCard from './ArticleCard.jsx'`), and import named exports using destructuring curly braces (`import { SubscriberBadge } from './ArticleCard.jsx'`), because an import syntax mismatch resolves the component identifier to `undefined`, triggering React's runtime error `Element type is invalid: expected a string... or a class/function... but got: undefined` or Vite's `SyntaxError: The requested module does not provide an export named...`.
- **Importance**: The card's primary Friction; one of the most frequent errors encountered by React developers; interviewers expect candidates to immediately recognize and explain this error.
- **Review Point — Condition**: Import default exports without curly braces; import named exports inside curly braces matching the exact exported name.
- **Required Lesson Proof**: In `App.jsx`, intentionally write `import ArticleCard from './ArticleCard.jsx'` when `ArticleCard` is exported as a named `export function`; start Vite and show the browser console runtime crash: `Uncaught Error: Element type is invalid: expected a string (for built-in components) or a class/function (for composite components) but got: undefined. You likely forgot to export your component from the file it's defined in, or you might have mixed up default and named imports.`; then write `import { MissingExport } from './ArticleCard.jsx'` to show Vite's build error: `The requested module '/src/components/ArticleCard.jsx' does not provide an export named 'MissingExport'`; fix the syntax and show clean rendering.
- **Sources**: card Friction, Under the Hood, Code Experiment; `importing-and-exporting-components.md` DeepDive table; runtime check in React 19 and Vite.

### Principle 3: Name component functions explicitly on default exports to preserve DevTools and stack trace identity
- **Kind**: Decision
- **Rule**: Always declare an explicit PascalCase function name when exporting a component as a default export (`export default function ArticleCard() {}`), avoiding anonymous function declarations or arrow functions (`export default () => {}`), ensuring that React DevTools, error boundaries, and browser stack traces preserve the component's true name for debugging.
- **Importance**: react.dev DeepDive specifically warns against anonymous default exports; senior reviewers reject anonymous default component exports in pull requests because they obscure component identity during debugging.
- **Review Point — Do not**: Do not export anonymous functions or arrow functions as default exports; write `export default function ComponentName()`.
- **Required Lesson Proof**: In `src/components/ArticleCard.jsx`, write `export default () => <article>Headline</article>`; inspect React DevTools and show the component displayed as `_default` or `Anonymous`; then change to `export default function ArticleCard() {}` and show the component name appear explicitly as `ArticleCard` in DevTools.
- **Sources**: `importing-and-exporting-components.md` DeepDive ("Components without names, like `export default () => {}`, are discouraged because they make debugging harder"); general senior engineering practice.

### Principle 4: Match import path character casing exactly to on-disk filenames to prevent case-sensitive CI build failures
- **Kind**: Decision
- **Rule**: Write import paths with the exact character casing of the on-disk file (`import ArticleCard from './ArticleCard.jsx'`), because while macOS and Windows local filesystems are case-insensitive and resolve mismatched casing (`./articlecard.jsx`) silently, case-sensitive Linux CI runners and production build containers will fail with unresolved module errors.
- **Importance**: Common production failure where code works on a developer's laptop but breaks in CI/CD pipelines; senior reviewers enforce strict casing consistency across platforms.
- **Review Point — Do**: Match import path casing exactly to the on-disk filename; never rely on case-insensitive local filesystem resolution.
- **Required Lesson Proof**: In `App.jsx`, write `import ArticleCard from './articlecard.jsx'` (lowercase `a`) while the file is named `ArticleCard.jsx`; demonstrate that while macOS local dev server may resolve the file, running `vite build` or checking in a case-sensitive environment throws a Rollup resolution failure: `Could not resolve "./articlecard.jsx" from "src/App.jsx"`; correct the import path to `./ArticleCard.jsx` and show the build succeed.
- **Sources**: general senior engineering knowledge; Vite and Rollup case-sensitivity diagnostics; brief 21 audit findings.

## Senior Answer
React components are organized as modular JavaScript functions using standard ES Module `export` and `import` declarations. When an application grows, we decompose monolithic files into dedicated component modules to prevent merge conflicts and enable code reuse across pages. A module can have at most one default export, created with `export default function ComponentName()`, which is best suited for the file's primary component, and as many named exports as needed (`export function Helper()`), which are ideal for secondary variants or utility sub-components. How a component is exported dictates how it must be imported: default exports are imported with a bare identifier without braces (`import ArticleCard from './ArticleCard'`), while named exports must be imported using destructuring curly braces matching the exact exported name (`import { SubscriberBadge } from './ArticleCard'`). Mixing up brackets causes the imported variable to evaluate to `undefined`, which triggers React's classic runtime crash: `Element type is invalid: expected a string or a class/function but got: undefined`, or Vite's `The requested module does not provide an export named...` error. To maintain clear debugging traces, we never export anonymous arrow functions as default exports, which would display as `Anonymous` in DevTools. Finally, we always match import path casing exactly to the filesystem filename (`./ArticleCard.jsx`), preventing silent resolution on case-insensitive developer laptops from failing on case-sensitive Linux CI runners. Dynamic imports and lazy loading are deferred to Q70, while root mounting in `main.jsx` is covered in Q09.
