# Q05: UI as a Tree and Component Hierarchy — Operational Principle Map
- **Source Map**: `01-01-map/05.md`
- **Topic Tag**: `#ui_tree` | `❱ CORE`
- **Interview Question**: *How does React organize nested components into a tree, and why does hierarchy dictate data flow?*

## Authorized Scope
Q05 teaches the structural component tree with static markup in a single file: how the JSX each component returns forms a render tree rooted at `App`, how a monolithic layout is decomposed into a root, branch containers (`NewsHeader`, `EditorialFeed`), and leaf components (`ArticleCard`, `EditorialByline`), how React visits that tree from the root downward, and why the parent-child edges are the only paths data can travel; it builds on Q01 (component tags vanish into plain HTML), Q02 component definition and declarative invocation, and Q03 JSX and Fragments, and it excludes props syntax (Q06), children composition (Q07), imports and the module dependency tree (Q08), mounting (Q09), conditional branches (Q10), purity and render-order guarantees (Q12), state and its position in the tree (Q14, Q24), lifting state (Q23), context (Q27), and re-render performance (Q55, Q64).

## Principles

### Principle 1: Read the hierarchy from JSX nesting, not from the file
- **Kind**: Model
- **Rule**: A component becomes the child of whichever component returns it in JSX, so the render tree follows the nesting of `<NewsHeader />`, `<EditorialFeed />`, and `<ArticleCard />` inside returned markup, while the order in which functions are written in a file, or the files they live in, decides nothing about the hierarchy.
- **Importance**: The card's Friction is a developer who sees an application as a flat collection of files and snippets; without this model every later lesson on data flow, state position, and composition has no structure to reason over.
- **Prediction**: Moving the `EditorialByline` function definition above `App` leaves the React DevTools Components tree unchanged, while moving the `<EditorialByline />` tag from `ArticleCard`'s JSX into `NewsHeader`'s JSX moves it under `NewsHeader` in the tree although no definition moved.
- **Required Lesson Proof**: Show the Components tab for the decomposed page, reorder the function definitions and show the same tree, then move one JSX tag and show the node move to its new parent.
- **Sources**: Under the Hood and Friction of `01-01-map/05.md`; understanding-your-ui-as-a-tree "The Render Tree"; the Preview row for the module dependency tree (Q08).

### Principle 2: Decompose a monolithic layout into root, branch, and leaf components
- **Kind**: Decision
- **Rule**: Let `App` compose the page's regions, let branch components (`NewsHeader`, `EditorialFeed`) group related pieces, and let leaf components (`ArticleCard`, `EditorialByline`) render one piece each, giving every component one concern and extracting a piece of markup when it grows its own responsibility rather than for every tag.
- **Importance**: A senior reviewer flags a 500-line single-function layout because no one can find, reuse, or reason about its parts, and flags the opposite extreme of one component per tag; the tree built here is what Q06, Q23, and Q25 reason over.
- **Review Point — Prefer**: Prefer one concern per component; keep a small piece inline inside its parent until it has a name and a responsibility of its own, then extract it, even if it is used only once.
- **Required Lesson Proof**: Replace the monolithic layout with `App`, `NewsHeader`, `EditorialFeed`, `ArticleCard`, and `EditorialByline`, show in the Elements panel that the DOM markup is unchanged, and show in the Components tab the root, branch, and leaf structure that did not exist before.
- **Sources**: Mechanism and Code Experiment of `01-01-map/05.md`; thinking-in-react Step 1 (separation of concerns, the `ProductTable` header judgment, mockup nesting), merged; your-first-component Deep Dive "Components all the way down", merged.

### Principle 3: Expect rendering to walk the tree from the root down
- **Kind**: Model
- **Rule**: React calls the root component first, and each component runs only because its parent returned an element for it, so a parent always runs before its own children and a subtree runs only when its parent includes it.
- **Importance**: A developer without this model expects a child to run independently of its parent or before it, which breaks the Q15 render pipeline and the Q24 rule that state lives at a tree position.
- **Prediction**: With a `console.log` in `App`, `NewsHeader`, `EditorialFeed`, and `ArticleCard`, the console prints `App` first and prints each parent before its own children, so `ArticleCard` never appears before `EditorialFeed`.
- **Required Lesson Proof**: Add one `console.log` per component, load the page, and show the parent-before-child order in the console, stating that the order between siblings is not a contract (Preview of Q12).
- **Sources**: Under the Hood of `01-01-map/05.md`; understanding-your-ui-as-a-tree ("the root component ... is the first component React renders"); order verified with React 19.3 and Vite 8.3.1 (`render App`, `render Header`, `render Branch`, `render Leaf`).

### Principle 4: Route shared data through the closest common ancestor
- **Kind**: Model
- **Rule**: A component can hand values only to the components it renders, and siblings do not render each other, so a value that two siblings both need must originate in their closest common ancestor and travel down each branch; there is no horizontal path between branches.
- **Importance**: The card's Friction is the attempt to reach across horizontally, and an interviewer expects "because data flows down the parent-child edges" as the answer to why hierarchy dictates data flow.
- **Prediction**: If `NewsHeader` reads a `readerName` variable declared inside its sibling `EditorialFeed`, the page fails with "ReferenceError: readerName is not defined", and in the Components tab the only path between the two siblings runs through `App`, the lowest place the value can come from.
- **Required Lesson Proof**: Reproduce the `ReferenceError` in the console, point to `App` as the closest common ancestor in the Components tab, and state in one sentence that Q06 props carry the value down each branch.
- **Sources**: Interview Question, Core Truth, and Friction of `01-01-map/05.md`; the merged sibling-scope candidate, verified in React 19.3 with Vite 8.3.1; the Preview row for props (Q06).

## Senior Answer
React builds a render tree from the JSX each component returns: `App` is the root, branch components such as `NewsHeader` and `EditorialFeed` group related pieces, and leaves such as `ArticleCard` render one piece, and it is this nesting, not the file layout or the order of definitions, that makes a component a parent or a child, which is why I decompose a monolithic layout into components with one concern each. React walks that tree from the root down, calling each parent before its children, and a component only runs because its parent returned it. Hierarchy dictates data flow because a component can only hand values to the components it renders: siblings never render each other, so there is no path between them, and a value two siblings need must come from their closest common ancestor and travel down each branch, which in the next lesson happens through props.
