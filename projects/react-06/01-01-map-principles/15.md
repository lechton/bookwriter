## Authorized Scope
Lesson 15 teaches the three steps behind every screen update. It works on one component, `LikeCounter`, which shows a like count and a Like button. A trigger asks React for a render. There are two triggers: the first `root.render(<App />)` call, and a setter call. Rendering means React calls our component functions to get their JSX. It changes nothing on the page. A state update renders the component that owns the state and every component inside it. The commit is the step that changes the page. It changes only the DOM nodes whose output differs, so text typed into an `<input>` stays. After the commit, the browser paints the screen. The commit comes after our event handler has finished. So on the line after a setter call, the page still shows the old value. The lesson builds on Q09, the React root, Q12, pure rendering, and Q14, `useState`.

## Principles

### Principle 1: The setter asks React for an update; React calls the component, then changes the page
- **Handle**: `setter-to-screen`
- **Kind**: Model
- **Reader Question**: "I call `setLikes(likes + 1)`. How does the new number get onto the screen?"
- **Reader Expects**: React runs `LikeCounter` again and the new number appears, as Lecture 14 showed; this is right; what the reader does not know is how that run turns into a changed page; a reader from plain JavaScript may picture the setter writing to the page, like `element.textContent = 1`
- **React Does**: the setter stores `1` and asks React for a render, the trigger; React calls `LikeCounter`, which returns `<p>1</p>`, the render, and the page does not change yet; React compares that JSX with the last one and changes the text `0` to `1` on the page, the commit; the first trigger is `root.render(<App />)`, and its commit adds every node
- **Placement**: the handler calls the setter; the component returns JSX built from `likes`; no code of ours touches the `<p>`
- **Real Mistake**: the plain JavaScript habit of changing the page by hand: `document.querySelector('.like-count').textContent = likes + 1` in the handler, with no setter; every click shows `1`, never `2`, because `likes` stays `0`; verified in React 19.3.0
- **Importance**: the whole interview question in one click; every developer brings the by-hand habit from plain JavaScript
- **Prediction**: with a log in the Like handler and one in the body of `LikeCounter`, a click prints the handler's log first, then `LikeCounter runs, likes = 1`, and then the page shows `1`.
- **Required Lesson Proof**: `LikeCounter` with `useState(0)`, a `<p className="like-count">`, a body log, and a Like handler that calls `setLikes(likes + 1)`; a click logs the handler line, then `LikeCounter runs, likes = 1`, and the page shows `1`; the by-hand handler shows `1` after every click.

### Principle 2: A state change runs its own component and the components inside it
- **Handle**: `update-renders-below`
- **Kind**: Model
- **Reader Question**: "When I click Like, does React run my whole app again, or only `LikeCounter`?"
- **Reader Expects**: either the whole app, like a page reload or the first `root.render(<App />)`, or only `LikeCounter`; both guesses are partly wrong
- **React Does**: React calls `LikeCounter`, the component whose state changed; then each component it returns, here `LikeLabel`; it stops there; `App` and `StoryTitle` do not run; `LikeLabel` runs even when its output is the same; the console shows `LikeCounter runs`, then `LikeLabel runs`
- **Placement**: the component that owns the state, and every component it returns, down the tree; not its parent, and not its siblings
- **Real Mistake**: none; a wrong picture here breaks no code in this lesson, and skipping renders is Q55's
- **Importance**: interviewers ask which components re-render; Q54 builds on it
- **Prediction**: with a log in every component of `App > StoryTitle, LikeCounter > LikeLabel`, the first render logs all four, and each Like click logs only `LikeCounter` and `LikeLabel`.
- **Required Lesson Proof**: `App` renders `StoryTitle` and `LikeCounter`; `LikeCounter` renders `LikeLabel`, which shows the count; each logs its name; first render: `App, StoryTitle, LikeCounter, LikeLabel`; Like click: `LikeCounter, LikeLabel`. `StoryTitle` and `LikeLabel` show where the render stops and where it goes.

### Principle 3: The commit changes only what is different, so typed text stays
- **Handle**: `commit-only-differences`
- **Kind**: Model
- **Reader Question**: "If React runs `LikeCounter` again on every like, will it wipe the comment the reader is typing?"
- **Reader Expects**: yes, a new run rebuilds the page, like a page reload or setting `innerHTML`
- **React Does**: the render returns new JSX; React compares it with the last JSX; the commit changes only what differs, here the text of the count; the `<input>`, the `<p>`, and the typed text stay the same DOM nodes; then the browser paints the screen, a step the browser also calls "rendering"
- **Placement**: re-render freely; a DOM node at the same place in the JSX is kept, and only its changed text or attributes are updated
- **Real Mistake**: none; the reader's fear leads to avoiding a re-render, not to code that breaks
- **Importance**: the card's second Friction; interviewers ask the difference between a render and a paint
- **Prediction**: a saved reference to the `<input>` still equals `document.querySelector('input')` after a Like click, and its typed text stays.
- **Required Lesson Proof**: `LikeCounter` with an `<input>` beside the count; type "great post", save the `<input>` and the `<p>` in variables, click Like; the typed text stays, both variables still equal the nodes on the page, and the count shows `1`.

### Principle 4: The page changes only after the event handler finishes
- **Handle**: `dom-after-handler`
- **Kind**: Decision
- **Reader Question**: "I call `setLikes(likes + 1)` and then read the number from the page to send it. Why does it send the old number?"
- **Reader Expects**: the setter changed the page on that line, as `element.textContent = ...` does in plain JavaScript, so the next line reads the new number
- **React Does**: the setter stores the next value and asks for a render; the rest of the handler runs; after the handler, and every other handler of the same event, has returned, React renders `LikeCounter` and commits; so on the line after the setter the page still shows `0`
- **Placement**: in the handler, use the value the code computed (`const next = likes + 1`, then `setLikes(next)` and `sendLikeEvent(next)`); not `document.querySelector('.like-count').textContent` on the line after the setter
- **Real Mistake**: `setLikes(likes + 1)`, then `document.querySelector('.like-count').textContent` sent to the statistics server; the click that shows `1` sends `0`; the render log for `1` prints after the handler's log; verified in React 19.3.0
- **Importance**: the card's first Friction; analytics that report the old count reach production
- **Review Point**: Do not
- **Required Lesson Proof**: the Like handler of `LikeCounter` calls `setLikes(likes + 1)`, then logs the `.like-count` text: it logs `0`; the body log for `likes=1` prints after it; the fixed handler computes `next` once and sends it.

## Senior Answer
Every screen update in React has three steps. First, a trigger asks for a render. There are two triggers: the first `root.render(<App />)` call, and a setter call. Second, React renders. That means it calls our component functions and gets JSX back. Nothing on the page changes in this step. On a state update, React renders the component that owns the state and everything inside it, not its parent. Third, React commits. It compares the new output with the last one and changes only the DOM nodes that differ. So text typed into an input stays. Then the browser paints the screen. All of this happens after our event handler finishes. So if I read the DOM right after a setter, I still see the old value. I use the value I computed instead.
