- **Interview Question**: *What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?*

## Authorized Scope
Q15 teaches the three steps behind every screen update and what runs in each: the trigger (the initial `root.render()` call, or a state setter that queues a render), the render (React calling our component functions, starting from the root on the first render and from the component whose state changed on a re-render, then every component those return), and the commit (React changing only the DOM nodes that differ from the previous render), followed by the browser's paint, which is a separate step from React's render. It builds on Q01 (the screen as a projection of data), Q05 (rendering walks the tree from the root down), Q09 (`root.render` updates the DOM after our code continues), Q12 (rendering is a pure calculation), and Q14 (the setter asks for a render), and it leaves the frozen state value inside a render to Q16, batching several setter calls to Q17, StrictMode's extra render to Q46, re-render causes beyond state and performance tuning to Q54 and Q55, and concurrent rendering and the Fiber work loop to Q66 and Q78.

## Principles

### Principle 1: Expect the DOM to change only in the commit, after our handler returns
- **Kind**: Model
- **Roles**: trigger: the initial `root.render(<App />)` call, or a setter call such as `setLikes(likes + 1)`; render: React calling our component functions to compute JSX; commit: React changing the DOM to match; paint: the browser drawing the committed DOM.
- **Placement**: code that needs the new number uses a value our code computed (Q16 owns that pattern), not a DOM query on the line after the setter.
- **Mechanism**: the setter stores the next value, queues a render, and returns; the rest of the handler keeps running; React renders and commits after the event handler has finished.
- **Defect**: `document.querySelector('.like-count').textContent` read on the line after `setLikes(likes + 1)` holds `0`, so the analytics event reports the old count (verified in React 19.3).
- **Importance**: The card's first Friction and the core of the interview answer; Q16, Q17, Q31, and Q49 all assume this order.
- **Prediction**: With `console.log('render', likes)` in the body of `LikeCounter` and a DOM read in its handler, a click prints `handler reads DOM: 0` first and `render 1` after it, and only then does the page show 1.
- **Required Lesson Proof**: Add both logs, click Like, show the order in the console, and show that the page displays 1 once the handler has finished.
- **Sources**: Core Truth, Friction, and Code Experiment of `01-01-map/15.md`; render-and-commit overview, Step 1, and Recap bullet 1; the merged trigger, queue, and DOM-read candidates, verified in React 19.3.

### Principle 2: Expect a state update to render the owner of the state and everything it returns
- **Kind**: Model
- **Roles**: `Feed`: component whose state changed, called again; `Badge`: component `Feed` returns, called again even though it receives no props; `App`: parent of `Feed`, not called; `Sidebar`: sibling of `Feed`, not called.
- **Placement**: state declared in the lowest component that needs it, because its update renders that component's whole subtree and nothing above it.
- **Mechanism**: a re-render starts at the component whose state changed; React calls each component that one returns, recursively, until no nested components remain; components above it or beside it are not called.
- **Defect**: A reader who expects the whole app to run again blames the wrong component for a slow click, and a reader who expects only the changed component to run is surprised by logs from its children.
- **Importance**: Interviewers ask which components re-render when state changes, and the answer is the base of lifting state (Q23), re-render causes (Q54), and `memo` (Q55).
- **Prediction**: With a `console.log` in `App`, `Feed`, `Badge`, and `Sidebar`, a click on `Feed`'s button prints `render Feed` and `render Badge` and nothing else.
- **Required Lesson Proof**: Load the page and show all four logs in tree order, click the button, and show only the two logs from the subtree of `Feed`.
- **Sources**: Mechanism of `01-01-map/15.md`; render-and-commit Step 1 (reason 2) and Step 2; the merged start, recursion, and four-log candidates, verified in React 19.3.

### Principle 3: Expect the commit to touch only the nodes that differ, and the paint to come after it
- **Kind**: Model
- **Roles**: render: React computing the new JSX and which properties changed; commit: React applying only those changes to the DOM; paint: the browser computing layout and drawing pixels after the commit.
- **Placement**: re-render freely when state changes; an `<input>` the reader is typing into keeps its text as long as it stays at the same place in the JSX.
- **Mechanism**: React compares the new output with the previous render's output; a DOM node at the same place is kept and only its changed text or properties are updated; identical output means no DOM change; the browser paints only what the commit changed.
- **Defect**: A reader who equates a React render with a page rebuild avoids re-rendering a form for fear of wiping the reader's typing, and adds needless workarounds.
- **Importance**: The card's second Friction and the interview probe "what is the difference between a render and a paint?"; Q54 builds on it to show that most re-renders are harmless.
- **Prediction**: A `Clock` whose `<h1>` shows the time and whose `<input>` holds typed text: when the time changes, the `<input>` is the same DOM node and keeps "Breaking: typed text", while the `<h1>` text changes; a component that renders again with identical JSX, such as `Badge` when `Feed`'s count changes, produces no DOM mutation at all.
- **Required Lesson Proof**: Save the `<input>` node in a console variable, type into it, let the time tick, and show the text still in place, the new time in the `<h1>`, and the saved variable still equal to `document.querySelector('input')`; then click `Feed`'s button from Principle 2 and show `render Badge` in the console while the Elements panel shows no change inside `Badge`'s `<i>`.
- **Sources**: Core Truth, Friction, and Under the Hood of `01-01-map/15.md`; render-and-commit Step 2, Step 3, Epilogue, and Recap bullet 3; the merged calculated-changes, identical-output, typed-input, and render-versus-paint candidates, verified in React 19.3.

## Senior Answer
Every screen update in React has three steps. The trigger is either the first `root.render(<App />)` call or a setter call; the setter stores the next value and queues a render, and our handler keeps running. The render is React calling our component functions to compute JSX. On the first render it starts at the root. On a re-render it starts at the component whose state changed and calls every component that one returns, but not its parent or its siblings. Rendering is a pure calculation and changes no DOM. The commit is the step where React changes the DOM, and it changes only the nodes whose output differs: an `<input>` beside a ticking clock keeps the text the reader typed, and a render that returns the same JSX changes nothing. After the commit the browser paints, which is a separate step from React's render. Because the DOM changes only in the commit, a handler that reads the DOM right after calling a setter still sees the old value.
