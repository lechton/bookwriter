## Authorized Scope
Lesson 15 teaches the three steps behind every screen update. It works on one component, `LikeCounter`, which shows a like count and a Like button. A trigger asks React for a render. There are two triggers: the first `root.render(<App />)` call, and a setter call. Rendering means React calls our component functions to get their JSX. It changes nothing on the page. A state update renders the component that owns the state and every component inside it. The commit is the step that changes the page. It changes only the DOM nodes whose output differs, so text typed into an `<input>` stays. After the commit, the browser paints the screen. The commit comes after our event handler has finished. So on the line after a setter call, the page still shows the old value. The lesson builds on Q09, the React root, Q12, pure rendering, and Q14, `useState`.

## Principles

### Principle 1: Rendering means React calls our components, and the page does not change
- **Handle**: `render-is-a-call`
- **Kind**: Model
- **Placement**: everything in the component body runs during the render; nothing in it changes the page
- **Mechanism**: a trigger (the first `root.render`, or a setter) asks for a render; React then calls the component function and gets JSX back; the page changes only later, in the commit
- **Tempting Belief**: "render" means drawing on the page; a habit from the browser, which calls its own drawing "rendering", and from server templates that write HTML as they run
- **Defect**: a log in the body of `LikeCounter` during the render for `likes=1` reads `.like-count` and finds `0`; code on the line after `root.render(<LikeCounter />)` finds the container still holding its old HTML
- **Importance**: the middle step of the interview question; the word "render" misleads every newcomer
- **Prediction**: a `console.log` in the body that prints `likes` and the text of `.like-count` shows the new `likes` next to the old text on every re-render.
- **Required Lesson Proof**: `LikeCounter` with `useState(0)`, a `<p className="like-count">`, and a body log of `likes` and the `.like-count` text; the first render logs `0` and finds no `<p>` yet; a Like click logs `likes=1`, page shows `0`; a log after `root.render` shows the container unchanged.

### Principle 2: A state update renders its own component and everything inside it
- **Handle**: `update-renders-below`
- **Kind**: Model
- **Placement**: the component that owns the state, and every component it returns, down the tree; not its parent, and not its siblings
- **Mechanism**: React calls the component whose state changed, then each component that one returns, until no components are left; the first render starts at the root
- **Tempting Belief**: a state change runs the whole app again from the top; a habit from full page reloads and from the first `root.render(<App />)`
- **Defect**: a click on Like logs `LikeCounter, Label`, and neither `App` nor `Title` logs; `Label` runs again although its output is the same
- **Importance**: interviewers ask which components re-render; Q54 builds on it
- **Prediction**: with a log in every component of `App > Title, LikeCounter > Label`, the first render logs all four, and each Like click logs only `LikeCounter` and `Label`.
- **Required Lesson Proof**: `App` renders `Title` and `LikeCounter`; `LikeCounter` renders `Label` beside the count; each logs its name; first render: `App, Title, LikeCounter, Label`; Like click: `LikeCounter, Label`. `Title` and `Label` exist only to show where the render stops and where it goes.

### Principle 3: The commit changes only what differs, and the browser paints after it
- **Handle**: `commit-only-differences`
- **Kind**: Model
- **Placement**: re-render freely; a DOM node at the same place in the JSX is kept, and only its changed text or attributes are updated
- **Mechanism**: during the render React works out what differs from the last output; the commit applies only those changes; on the first render it inserts all nodes with `appendChild()`; the browser's paint draws the result afterwards
- **Tempting Belief**: a re-render rebuilds the page and wipes what the user typed; a habit from full page reloads and from setting `innerHTML`
- **Defect**: after a Like click the text typed into the `<input>` is still there, and the `<input>`, the `<p>`, and its text node are the same DOM nodes as before; only the count's text changed
- **Importance**: the card's second Friction; interviewers ask the difference between a render and a paint
- **Prediction**: a saved reference to the `<input>` still equals `document.querySelector('input')` after a Like click, and its typed text stays.
- **Required Lesson Proof**: `LikeCounter` with an `<input>` beside the count; type "great post", save the `<input>` and the `<p>` in variables, click Like; the typed text stays, both variables still equal the nodes on the page, and the count shows `1`.

### Principle 4: The page changes after the event handler finishes
- **Handle**: `dom-after-handler`
- **Kind**: Decision
- **Placement**: in the handler, use the value the code computed (`const next = likes + 1`, then `setLikes(next)` and `sendLikeEvent(next)`); not `document.querySelector('.like-count').textContent` on the line after the setter
- **Mechanism**: the setter only queues a render; React renders and commits after the handler, and every other handler of the same event, has returned
- **Tempting Belief**: `setLikes(likes + 1)` changes the page on that line, like `element.textContent = ...` in plain DOM code or jQuery
- **Defect**: the click that shows `1` reads `0` from `.like-count` on the line after `setLikes(likes + 1)`; the render log for `1` prints after the handler's log
- **Importance**: the card's first Friction; analytics that report the old count reach production
- **Review Point**: Do not
- **Required Lesson Proof**: the Like handler of `LikeCounter` calls `setLikes(likes + 1)`, then logs the `.like-count` text: it logs `0`; the body log for `likes=1` prints after it; the fixed handler computes `next` once and sends it.

## Senior Answer
Every screen update in React has three steps. First, a trigger asks for a render. There are two triggers: the first `root.render(<App />)` call, and a setter call. Second, React renders. That means it calls our component functions and gets JSX back. Nothing on the page changes in this step. On a state update, React renders the component that owns the state and everything inside it, not its parent. Third, React commits. It compares the new output with the last one and changes only the DOM nodes that differ. So text typed into an input stays. Then the browser paints the screen. All of this happens after our event handler finishes. So if I read the DOM right after a setter, I still see the old value. I use the value I computed instead.
