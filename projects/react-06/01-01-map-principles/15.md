# Q15: Inverse Data Flow with Callback Props — Operational Principle Map
- **Source Map**: `01-01-map/15.md`
- **Topic Tag**: `#callback_props` | `❱ CORE`
- **Interview Question**: *How does a child component notify its parent or trigger actions using callback props?*

## Authorized Scope
Q15 teaches the inverse-data-flow model with static data: data travels only down from parent to child, so a child such as `FilterBar` has no way to change what `NewsroomPage` owns by mutating a received object, reassigning a prop, or reaching around the tree with global events; instead the parent defines a handler and passes it down (`<FilterBar onSelectCategory={handleCategoryChange} />`), the child calls it with an app-level value on user interaction (`onSelectCategory('business')`), and the handler runs as a closure in the parent's scope, so the parent keeps the authority to decide what happens; the parent only logs the category it receives, because state is not available yet; it builds on Q05 (shared data lives in the closest common ancestor), Q06 (props are read-only, optional props get defaults), Q13 (handlers are passed, not called, and handler props are wired to real elements), and Q14 (handlers are the home of side effects), and it excludes storing the selected category in state and re-rendering (Q16), lifting state and passing setters down (Q26), notifying parents from Effects (Q37), context for deep trees (Q30), and callback identity with `useCallback` (Q59).

## Principles

### Principle 1: Expect data to flow only down, with no path back up except a function
- **Kind**: Model
- **Rule**: A parent hands values to its children through props, and a child receives the value, not a link to the parent's variable, so mutating a received object changes the parent's data without React noticing, reassigning a prop changes only the child's local variable, and React offers no two-way binding (unlike Vue's `v-model` or Angular's `[(ngModel)]`, which sync a value in both directions automatically); the only upward path is a function the parent chooses to pass down.
- **Importance**: The card's Friction is the attempt to reach into the parent, and a developer who remembers two-way binding from Vue expects the child's change to show up in the parent; an interviewer expects "one-way data flow" as the first sentence of the answer.
- **Prediction**: When `FilterBar` sets `filters.category = 'business'` on the object it received, the console logs `business` while the heading still reads "Showing: politics", and reassigning a destructured `category` prop logs `tech` inside `FilterBar` while the parent's heading does not change.
- **Required Lesson Proof**: Render `NewsroomPage` with a `filters` object and a `category` prop, click the mutating button and the reassigning button, and show both console lines beside the unchanged "Showing: politics" heading.
- **Sources**: Core Truth and Friction of `01-01-map/15.md`; thinking-in-react Steps 2, 4, and 5; tutorial "Lifting state up"; the merged mutation and reassignment candidates, verified in React 19.3; the Q01 Deferred row on two-way binding.

### Principle 2: Let the parent pass a callback and have the child call it when the user acts
- **Kind**: Decision
- **Rule**: When a child's interaction should affect data its parent owns, the parent defines a handler and passes it as a prop (`<FilterBar onSelectCategory={handleCategoryChange} />`), and the child calls that prop from its own event handler (`onClick={() => onSelectCategory('business')}`), so the child reports what happened and each parent decides what that means; a mutated prop, a shared module variable, a global `CustomEvent`, or a DOM query does the same job invisibly and cannot be traced from the JSX.
- **Importance**: This is the card's Mechanism and the answer to the interview question; a `FilterBar` that hardcodes its reaction cannot be reused by a second page, and a reviewer rejects global events and shared variables because nothing in the component tree shows who reacts to the click.
- **Review Point — Do**: Check that every child that needs to change parent-owned data does so by calling a callback prop from an event handler, and that it never mutates a prop, writes a shared variable, or dispatches a global event for that purpose.
- **Required Lesson Proof**: Pass `handleCategoryChange` to `FilterBar`, click Business and then Tech, and show "NewsroomPage received business for the Morning edition" and the matching Tech line, one per click; then render the same `FilterBar` under a second parent with a different callback and show a different log from the same click.
- **Sources**: Mechanism and Code Experiment of `01-01-map/15.md`; thinking-in-react Step 5; sharing-state Step 3 and Recap bullet 3; passing-props "How props change over time"; tutorial "Lifting state up" recap; the merged reuse and global-event candidates; the callback output verified in React 19.3.

### Principle 3: Treat the callback as a closure that runs in the parent's scope
- **Kind**: Model
- **Rule**: The handler is created inside the parent's render, so it closes over the parent's variables; when the child calls it, the parent's code runs with the parent's values, which the child never sees, and the child can only trigger the handler and supply arguments, while the decision about what happens stays inside the parent.
- **Importance**: Interviewers ask how a child can run code that lives in its parent, and a developer who cannot answer "closures" treats the callback as magic; the same model explains Q18's snapshot behavior once handlers read state.
- **Prediction**: With `const edition = 'Morning'` declared in `NewsroomPage` and never passed to `FilterBar`, clicking Business logs "NewsroomPage received business for the Morning edition", because the handler reads `edition` from the parent's scope.
- **Required Lesson Proof**: Declare `edition` in the parent, use it only inside `handleCategoryChange`, show that `FilterBar`'s props contain only `onSelectCategory` (in the Components tab or by logging the props), click Business, and show the log containing "Morning".
- **Sources**: Under the Hood of `01-01-map/15.md`; state-a-components-memory Challenge "Complete the gallery" Solution; the merged `edition` candidate, verified in React 19.3.

### Principle 4: Send the value the parent needs, not the DOM event
- **Kind**: Decision
- **Rule**: The child translates the browser event into an app-level value before calling the callback (`onSelectCategory(c.slug)`, `onFilterTextChange(e.target.value)`), so the parent receives a category or a string and never needs to know whether the child used buttons, a `<select>`, or links.
- **Importance**: `onClick={onSelectCategory}` hands the parent the click event, so the parent logs "Showing: [object Object]", and a parent that digs `e.target.textContent` out of it breaks as soon as the child's markup or label text changes.
- **Review Point — Prefer**: Prefer calling callback props with app-level values; pass the event itself only when the parent truly needs event behavior, and then name the prop for that purpose.
- **Required Lesson Proof**: Wire `onClick={onSelectCategory}` and show "Showing: [object Object] | target BUTTON" in the console, then change the child to `onClick={() => onSelectCategory('business')}` and show "business" arriving in the parent.
- **Sources**: thinking-in-react Step 5 (`onFilterTextChange(e.target.value)`); the merged event-object candidate, verified in React 19.3.

## Senior Answer
React data flows one way: a parent passes values down as props, and a child receives the values, not a link to the parent's variables, so mutating a received object or reassigning a prop never updates the parent's screen, and unlike Vue's `v-model` there is no automatic two-way binding. To let a child report an action, the parent defines a handler and passes it down as a callback prop, `<FilterBar onSelectCategory={handleCategoryChange} />`, and the child calls it from its own click handler with an app-level value, `onSelectCategory('business')`, rather than the raw DOM event. The callback is a closure created in the parent's render, so it runs with the parent's variables and the parent alone decides what happens, while the child stays reusable because a different parent can pass a different callback; global events or shared variables would do the same job invisibly. I wire the prop to a real button, give an optional callback a default so a page that omits it does not crash, and once state arrives the parent stores the received value in state and re-renders.
