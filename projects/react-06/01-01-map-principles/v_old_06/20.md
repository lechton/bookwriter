## Authorized Scope
Q20 teaches the `<StrictMode>` component inside the National Times article page: wrapped around `<App />` in `main.jsx`, it makes React call every function that should be pure (the component body, the function passed to `useState`, and updater functions) twice per call in development and keep only one result, so a pure component logs twice and shows the same screen while an impure one (a `StoryTray` that pushes "Create Story" into the array it receives) shows the damage at once instead of on some later re-render; event handlers are never called twice, the extra call disappears from a production build, the boundary checks every descendant with no opt-out inside it, and a quiet StrictMode is evidence rather than proof of purity; it builds on Q09 (`main.jsx` and the root), Q12 (the purity contract and local mutation), Q14 (handlers run on interaction, not during render), Q16 (the initial state argument), and Q19 (updater functions and their purity), and it excludes the extra Effect setup and cleanup cycle (Q35), the extra ref callback cycle (Q86), deprecated API warnings (Q97), `useMemo` and reducers (Q58, Q29), profiling (Q64), lint rules (Q94), and test renders (Q87).

## Principles

### Principle 1: Read the double call as a purity test that keeps one result
- **Kind**: Model
- **Rule**: React is allowed to call a render function more than once and use only one of the results, and in development `<StrictMode>` does exactly that on every call: it runs each function that should be pure a second time and discards one result, so a pure function produces the same output both times and nothing on screen changes, while a function that changes something both calls share (an external variable, an array it received) changes it twice and the damage is visible immediately.
- **Importance**: This is the answer to the interview question, and without it a developer reads the card's doubled `console.log('Rendering Article')` as a React bug or a performance disaster and spends hours trying to make it go away.
- **Prediction**: A `StoryTray` that pushes `{ id: 'create', label: 'Create Story' }` into its `stories` prop shows "Create Story" twice on the first load under StrictMode; the same component without StrictMode looks correct on load and adds another "Create Story" every time a hover re-renders it; a version that pushes into `stories.slice()` shows one "Create Story" in every case.
- **Required Lesson Proof**: Run the `StoryTray` from the StrictMode page with and without the wrapper, hover over the unwrapped tray to show the list growing, then copy the array before pushing (recall of Q12) and show a single "Create Story" under StrictMode and after any number of hovers.
- **Sources**: Core Truth and Under the Hood of `01-01-map/20.md`; StrictMode.md "Fixing bugs found by double rendering in development"; rules "Why does purity matter?"; useState Troubleshooting; the merged `StoryTray`, rehearsal, one-result, and request-in-render candidates.

### Principle 2: Know which functions run twice, and that handlers never do
- **Kind**: Model
- **Rule**: In development StrictMode calls the top level of the component body twice for every render, the initializer function passed to `useState` twice when the component is created, and each updater function passed to a setter twice when the queue is processed (with `useMemo` calculations and reducers on the same list, Previews of Q58 and Q29), while event handlers run exactly once per interaction because they are not part of rendering; Effects get a separate extra setup and cleanup cycle that belongs to Q35.
- **Importance**: The card's Friction is a developer staring at a doubled log; reading it correctly requires knowing which code is on the list, and knowing that handlers are not tells the developer where a one-time action (a request, an analytics event) is safe.
- **Prediction**: With logs in the `Article` body, in `useState(() => { console.log('init'); return [] })`, in an updater, and in an `onClick` handler, a page load prints the body log twice and the init log twice; each click prints the handler log once, the updater log twice, and the body log twice for the re-render; with React DevTools installed the second line of each pair is dimmed.
- **Required Lesson Proof**: Instrument the four places with logs, load the page and click once, and read the console line by line against the list; show the dimmed second lines with React DevTools installed.
- **Sources**: Mechanism of `01-01-map/20.md`; StrictMode.md list of double-called functions and its DevTools Note; useState Caveats and Troubleshooting "runs twice"; useRef Caveat; the merged handler, dimming, initializer, updater, and ref-object candidates.

### Principle 3: Expect the production build to call everything once
- **Kind**: Model
- **Rule**: Every StrictMode check is development-only: the production build contains no second call, no extra cost, and no behavior change, so a component that is correct under StrictMode behaves the same for users, and the double call is never a reason to fear for production performance.
- **Importance**: The interviewer's follow-up is "does it slow down production?", and the card's Friction ends with a developer considering removing StrictMode over a performance fear that does not exist in the shipped app; development timings are also inflated for the same reason (Preview of Q64).
- **Prediction**: The `Article` body log prints twice per render on the Vite development server and once per render after `vite build` and `vite preview`.
- **Required Lesson Proof**: Run the same instrumented app on the development server and from a production build served with `vite preview`, and compare the log counts for a page load and one click.
- **Sources**: Core Truth, Mechanism, and Scope Boundary of `01-01-map/20.md`; StrictMode.md Note ("All of these checks are development-only and do not impact the production build"); keeping-components-pure Deep Dive; the merged production-cost candidate.

### Principle 4: Fix the impurity StrictMode exposes and keep StrictMode on
- **Kind**: Decision
- **Rule**: A duplicate under StrictMode points at a bug that already exists and would appear in production on some later re-render, so the correction is to make the function pure (copy instead of mutate, move the side effect to a handler); removing `<StrictMode>` or adding a module-level "already ran" flag only hides the symptom, and the flag is itself a write during render.
- **Importance**: Removing the wrapper is the exact mistake the card's Friction describes, a reviewer rejects that pull request, and the hover version of `StoryTray` shows the hidden bug returning for users as soon as the component re-renders for an unrelated reason.
- **Review Point — Do**: When StrictMode shows a duplicate, find the shared value the function changes and make the function pure; keep `<StrictMode>` in `main.jsx`.
- **Required Lesson Proof**: Remove the wrapper from the buggy `StoryTray` to show the duplicate disappear on load and come back with every hover, then restore the wrapper, fix the copy, and show one "Create Story" both on load and after hovering.
- **Sources**: Friction of `01-01-map/20.md`; StrictMode.md hover sandbox and its closing paragraphs; StrictMode.md "Enabling Strict Mode for entire app"; the merged hidden-bug and run-once-flag candidates.

### Principle 5: Wrap the whole app at the root
- **Kind**: Decision
- **Rule**: Place `<StrictMode>` around `<App />` in the `root.render` call so every component is checked, which the Vite template already does; when an older codebase adopts it gradually, wrap a subtree instead, knowing that every component inside it is checked no matter how deep, components outside it are not, and nothing inside can opt out, so changing coverage means moving the boundary.
- **Importance**: The card's Code Experiment wraps `<App />` in `main.jsx`, a component outside the boundary carries its bugs unchecked, and the interview follow-up "can you enable it for only part of the app?" has a precise answer.
- **Review Point — Prefer**: Prefer one `<StrictMode>` at the root; when adopting it gradually, wrap the subtree that is ready and move the boundary up as more of the tree passes.
- **Required Lesson Proof**: Show `main.jsx` with the root wrapper, then wrap only `<main>` around `Sidebar` and `Content` with `Header` outside and show the `Header` body log once per render and the `Content` body log twice.
- **Sources**: Code Experiment of `01-01-map/20.md`; StrictMode.md "Enabling Strict Mode for entire app", "Enabling Strict Mode for a part of the app", and Caveat; the merged Vite template and opt-out candidates.

### Principle 6: Treat a quiet StrictMode as evidence, not proof
- **Kind**: Model
- **Rule**: Because React keeps only one of the two results, StrictMode makes impurity visible only when the damage accumulates across the calls, such as a mutation of something both calls share or a request sent from render; a value that merely differs per call, like `Math.random()`, leaves the screen showing one plausible result, and code that never ran during the session was never checked, which is why the Rules of React pair StrictMode with the lint rules (Q94).
- **Importance**: The senior follow-up is "does a clean StrictMode run prove my components are pure?", and a developer who answers yes ships the non-idempotent calls Q12 warns about.
- **Prediction**: A component that renders `Math.random()` logs two different numbers per render under StrictMode while the screen shows one number and nothing duplicates; a component that pushes into a module-level array shows the duplicates.
- **Required Lesson Proof**: Render both components side by side under StrictMode and compare the console with the screen (recall of Q12 Principle 4 for the random value).
- **Sources**: general engineering knowledge; useState Troubleshooting ("React uses the result of one of the calls"); rules index recommendation; lints `globals` and `purity`; the merged random-value and lint candidates.

## Senior Answer
React renders components twice in development because `<StrictMode>`, which the Vite template places around `<App />` in `main.jsx`, deliberately calls every function that should be pure a second time and keeps only one result. React is already allowed to render a component more than once, so a pure component gives the same output both times and nothing changes on screen, while a component that mutates something shared, such as a `StoryTray` that pushes "Create Story" into the array it received, shows the duplicate at once instead of on some later re-render in production. The double call covers the component body, the `useState` initializer, and updater functions, never event handlers, so a doubled render log (dimmed by React DevTools) is expected and a click handler still runs once. None of this exists in the production build, so there is no cost for users. When StrictMode shows a duplicate I fix the impure code rather than removing the wrapper or adding a run-once flag, I wrap the whole app at the root, or a subtree that I grow during gradual adoption, and I remember that a quiet StrictMode is evidence rather than proof: a per-call difference like `Math.random()` does not duplicate anything, so I pair it with the lint rules.
