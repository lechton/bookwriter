# Q22: Updating Arrays in State — Operational Principle Map
- **Source Map**: `01-01-map/22.md`
- **Topic Tag**: `#state_arrays` | `❱ CORE`
- **Interview Question**: *How do you add, remove, insert, and reorder items in a state array?*

## Authorized Scope
Q22 teaches array updates inside the National Times `NewsTicker` manager, where an editor adds, deletes, inserts, reorders, and edits stories keyed by `story.id`: an array is an object, so the Q21 rule applies and every update passes a new array to the setter, which means sorting each array method into those that change the array in place (`push`, `unshift`, `pop`, `shift`, `splice`, `sort`, `reverse`, index and `length` assignment) and those that return a new one (`concat`, spread, `filter`, `slice`, `map`); adding uses spread at either end, removing uses `filter` on the id, inserting spreads two slices around the new item, reordering works on a copy that is fresh and therefore safe to mutate, a copied array still points at the same story objects, and editing a story uses `map` with a new object for the changed item; it builds on Q11 (stable keys from the data), Q12 (local mutation of values just created), Q19 (the updater form), Q20 (updaters are called twice in development), and Q21 (the `Object.is` check, replacement, and shallow spreads), and it excludes sorted and filtered views computed for display (Q25), key reconciliation internals (Q61, Q77), virtualization (Q62), drag-and-drop libraries, and Immer.

## Principles

### Principle 1: Sort every array method into mutating or copying before using it on state
- **Kind**: Decision
- **Rule**: `push`, `unshift`, `pop`, `shift`, `splice`, `sort`, `reverse`, and assignments to an index or to `length` change the array in place, so the state array keeps its reference and the setter ignores it (Q21); worse, their return values mislead, because `push` returns the new length and `sort` returns the same array, while `concat`, spread, `filter`, `slice`, and `map` return a new array and are the ones to call on state; `slice` copies and `splice` mutates despite the similar names.
- **Importance**: The card's Friction is a developer using `push`, `splice`, and `sort` on the ticker and seeing stale and ghost stories, and reviewers scan for exactly these calls on any array that came from `useState`.
- **Review Point — Do not**: Do not call a mutating method on an array that is in state; call a copying method or copy the array first.
- **Required Lesson Proof**: In `NewsTicker`, run `stories.push(newStory); setStories(stories)` and show the ticker unchanged; run `setStories(stories.push(newStory))` and show the next render throwing a TypeError because a number has no `map` method; log `stories.sort() === stories` as `true`; then replace each call with its copying counterpart from the react.dev table.
- **Sources**: Core Truth, Friction, and Under the Hood of `01-01-map/22.md`; arrays table and Pitfall; lint `immutability`; useState Troubleshooting; keeping-components-pure Challenge 3 Solution; the merged return-value, `slice` and `splice`, assignment, same-reference, and "Fix the mutations" candidates.

### Principle 2: Add with spread at the end or the start
- **Kind**: Decision
- **Rule**: Append with `setStories([...stories, newStory])` and prepend with `setStories([newStory, ...stories])` (`concat` also returns a new array), creating the new story's id in the handler together with the story so its key is stable from its first render.
- **Importance**: Adding is the first operation in the interview question, `push` is the first mistake in the card's Friction, and a story added without an id from the data gets a key that cannot follow it when the list changes (Q11).
- **Review Point — Do**: Add items by spreading the old array into a new one with the new item before or after it.
- **Required Lesson Proof**: Add a breaking story at the top and a routine story at the bottom of the ticker, and show both appearing with ids created in the handler.
- **Sources**: Mechanism of `01-01-map/22.md`; arrays "Adding to an array" and Recap bullet 3; useState Recipe "List (array)"; lint `immutability` Troubleshooting "I need to add items to an array"; the merged prepend and id candidates.

### Principle 3: Remove with `filter` on the item's id
- **Kind**: Decision
- **Rule**: `setStories(stories.filter(s => s.id !== id))` builds a new array without the deleted story and leaves the old one untouched; matching on the id keeps the deletion correct even if the list was reordered or changed since the button rendered, and the same `filter` drops every item that fails a condition, such as a cart line whose count reached zero after a `map`.
- **Importance**: Removing is the second operation in the interview question and the card's "deletes a published typo" Friction; `splice` on state is the mistake it replaces, and deleting by a stale index removes the wrong story.
- **Review Point — Prefer**: Prefer filtering on the item's id; filter on an index only when the index is read from the same array that is being filtered.
- **Required Lesson Proof**: Delete the typo story from the ticker with `filter` on its id; then run the shopping cart challenge's decrement, which maps the count down and filters out the item at zero.
- **Sources**: Mechanism and Friction of `01-01-map/22.md`; arrays "Removing from an array", Recap bullet 4, and Challenge "Remove an item from the shopping cart" Solution; the merged cart and stale-index candidates.

### Principle 4: Insert by spreading two slices around the new item
- **Kind**: Decision
- **Rule**: To place a story at position `i`, build `[...stories.slice(0, i), newStory, ...stories.slice(i)]`: `slice` copies the part before and the part after without touching the original, and the new array holds the old stories with the new one between them.
- **Importance**: Inserting is the third operation in the interview question, the reflex `splice(i, 0, item)` mutates state, and an editor slotting a story into second place is the card's real scenario.
- **Review Point — Do**: Insert with two `slice` calls and spread; keep `splice` off arrays that are in state.
- **Required Lesson Proof**: Insert a story at index `1` of the ticker and show it between the first and second stories, with every story keeping its own row because keys come from `story.id` (recall of Q11).
- **Sources**: Mechanism of `01-01-map/22.md`; arrays "Inserting into an array"; the Pitfall on `slice` and `splice`.

### Principle 5: Reorder a copy, never the array in state
- **Kind**: Decision
- **Rule**: `sort` and `reverse` change the array they are called on, so copy first and reorder the copy (`const next = [...stories]; next.reverse(); setStories(next)`), which is fine because the copy was just created and nothing else points at it yet; `toSorted` and `toReversed` do the copy and the reorder in one call where the target browsers support them, while `setStories(stories.sort())` passes the same array and is ignored.
- **Importance**: Reordering is the last operation in the interview question and `stories.sort()` is in the card's Friction; a reviewer flags any `sort` or `reverse` on a state array.
- **Review Point — Do**: Copy the array (or use a copying method such as `toSorted`) before sorting or reversing it, then pass the result to the setter.
- **Required Lesson Proof**: Run `setStories(stories.sort(byPriority))` and show the ticker unchanged, then sort a copy and show the new order, with each story's row moving with it because of its key (recall of Q11); swap two stories by assigning indexes on the copy to show that assignments on a fresh copy are allowed.
- **Sources**: Friction of `01-01-map/22.md`; arrays "Making other changes to an array"; lint `immutability` "Sort without spreading"; the merged copy-first, ES2023, and same-array candidates.

### Principle 6: Expect a copied array to share its items with the original
- **Kind**: Model
- **Rule**: Copying an array creates a new list of pointers to the same objects, so `[...stories]` is a new array whose items are the old story objects; mutating an item through the copy changes the item in the original state, in every other array that holds the same object, and in the previous render's snapshot.
- **Importance**: This is the bug react.dev calls "difficult to think about": a checkbox in one list changes another list, and the copied array makes the code look safe in review.
- **Prediction**: With `myList` and `yourList` both created from `initialList`, toggling an artwork through `const next = [...myList]; next.find(a => a.id === id).seen = true; setMyList(next)` checks the box in both lists; logging `next[0] === myList[0]` prints `true`.
- **Required Lesson Proof**: Run the first `BucketList` sandbox from react.dev, toggle one artwork, and show both lists changing, then log the identity check.
- **Sources**: arrays "Making other changes to an array" closing warning and "Updating objects inside arrays"; the merged `nextList[0].seen` and two-lists candidates; Q21 Principle 4 (prerequisite).

### Principle 7: Update an item with `map` and a new object for the changed item
- **Kind**: Decision
- **Rule**: `setStories(stories.map(s => s.id === id ? { ...s, isBreaking: true } : s))` returns a new array in which only the changed story is a new object and every other story is the same object as before; for an array of primitives the same `map` uses the index argument to return the new value at one position.
- **Importance**: Editing an item is the card's "updating stories" experiment and react.dev's fix for the shared-item bug; it is the recipe a reviewer expects in every list editor, and the shopping cart challenge is the common interview exercise.
- **Review Point — Do**: Change an item by mapping to a new array that holds a new object for that item and the existing objects for the rest.
- **Required Lesson Proof**: Mark one story as breaking with `map` and an object spread, then rerun the `BucketList` toggle with `map` and show only one list changing; increase a cart count the same way.
- **Sources**: Mechanism and Code Experiment of `01-01-map/22.md`; arrays "Transforming an array", "Replacing items in an array", "Updating objects inside arrays", and Challenge "Update an item in the shopping cart" Solution; the merged primitive-replace, cart, and copy-to-the-top candidates.

## Senior Answer
An array is an object, so the rule for objects applies: React compares the next state with the current one using `Object.is`, and I always pass the setter a new array. That starts with knowing which methods change an array in place, `push`, `unshift`, `pop`, `shift`, `splice`, `sort`, `reverse`, and index assignments, and which return a new one, `concat`, spread, `filter`, `slice`, and `map`; `slice` copies, `splice` mutates. To add I spread the old array with the new item before or after it, to remove I filter on the item's id, to insert I spread two slices around the new item, and to reorder I copy first and sort or reverse the copy, or use `toSorted` where it is supported, which is safe because the copy is fresh. A copied array still points at the same item objects, so I never change an item through it; to edit a story I map to a new array that holds a new object for the changed story and the existing objects for the rest. Because every story is keyed by its id, React keeps each row attached to its story through inserts and reorders.
