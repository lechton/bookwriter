## Authorized Scope
Q19 teaches that we treat an array in state as read-only, like an object: every change builds a new array and passes it to the setter, with the non-mutating recipe for each operation (adding with spread, removing with `filter`, inserting with `slice` and spread, replacing and transforming with `map`, reordering a copy with `[...arr].sort()` or `toSorted()`), and that copying an array does not copy the items inside it, so changing one item means replacing it with a new object through `map`. It builds on Q11 (lists and keys), Q14 (the setter), Q16 (snapshots), Q17 (the updater form), and Q18 (read-only objects, spread, and `Object.is`), and it leaves restructuring deeply nested state to Q22 and virtualization to Q62; Immer may be named as an optional helper without teaching its API.

## Principles

### Principle 1: Change a state array only by building a new one
- **Kind**: Decision
- **Roles**: mutating methods (`push`, `pop`, `shift`, `unshift`, `splice`, `sort`, `reverse`, `arr[i] =`): change the array they are called on; new-array forms (spread, `concat`, `filter`, `slice`, `map`, `toSorted`, `toReversed`, `toSpliced`, `with`): return a new array and leave the old one alone; `slice`: copies part of an array; `splice`: removes or inserts in place.
- **Placement**: add `[...stories, newStory]`; remove `stories.filter(s => s.id !== id)`; insert `[...stories.slice(0, i), newStory, ...stories.slice(i)]`; replace or transform `stories.map(...)`; reorder `[...stories].sort(byTime)` or `stories.toSorted(byTime)`; the result goes to `setStories`.
- **Mechanism**: an array is an object; the setter compares with `Object.is`; a mutated array is the same array, so the render is skipped; sorting a fresh copy is a local mutation and is fine.
- **Defect**: `stories.splice(0, 1); setStories(stories)` causes no render and the deleted story stays on screen; `push` and `sort` on the state array fail the same way (verified in React 19.3).
- **Importance**: The card's Friction and the interview question itself; "which array methods mutate?" is a standard probe, and `splice` against `slice` is the classic look-alike.
- **Review Point — Do not**: Do not call a mutating method on a state array or assign to one of its indexes; build the new array with the matching non-mutating form and pass it to the setter.
- **Required Lesson Proof**: In `NewsTicker`, delete the typo story with `splice` and show it still on screen with no render log; then delete with `filter`, insert with `slice` and spread, and reorder with `toSorted`, showing each result on screen and the original array unchanged in the console.
- **Sources**: Core Truth, Friction, Mechanism, Under the Hood, and Code Experiment of `01-01-map/19.md`; arrays avoid and prefer table, Pitfall, every recipe section, Recap bullets 1 to 4, and the Challenge "Fix the mutations using non-mutative methods"; Troubleshooting "the screen doesn't update"; the merged recipe candidates, verified in React 19.3.

### Principle 2: Replace a changed item with a copy through `map`
- **Kind**: Decision
- **Roles**: copied array (`[...stories]`): a new array holding the same item objects; item object: shared by the old array and the copy; `stories.map(s => s.id === id ? { ...s, title } : s)`: a new array in which only the changed item is a new object.
- **Placement**: every item change goes through `map` with an object spread for the matching item; not an assignment to a field of an item inside a copied array.
- **Mechanism**: copying an array is shallow: the new array points to the same item objects; changing a field of a shared item changes it in the previous render's array and in any other list that holds it.
- **Defect**: `const copy = [...stories]; copy[1].title = 'Corrected'; setStories(copy)` renders "Corrected", but the first render's array item also reads "Corrected"; two lists that start from the same items both show a checkbox checked after it is checked in one of them (verified in React 19.3).
- **Importance**: The bug survives a quick test because the screen updates, so reviewers and interviewers probe it; the card's Friction names it.
- **Review Point — Do**: Check that every change to an item in a state array creates a new item object, and that the only objects mutated are ones created in the same handler.
- **Required Lesson Proof**: Keep a reference to the first render's `stories`, correct a title through a copied array plus assignment, and show the screen updating while the old reference also changed; then correct it with `map` and an object spread and show the old reference unchanged; finally render two lists from the same initial items and show the shared checkbox bug and its fix.
- **Sources**: Core Truth, Friction, and Under the Hood of `01-01-map/19.md`; arrays "Making other changes to an array" and "Updating objects inside arrays"; the Challenges "Update an item in the shopping cart" and "Remove an item from the shopping cart"; the merged copy-then-mutate and shared-lists candidates, verified in React 19.3.

## Senior Answer
I treat an array in state as read-only, exactly like an object. An array is an object, so the setter compares it with `Object.is`. If I call `stories.splice(index, 1)` and pass the same array back, React skips the render and the deleted story stays on screen; `push` and `sort` fail the same way. So every change builds a new array. I add with `[...stories, newStory]`, remove with `filter`, and insert with `[...stories.slice(0, i), newStory, ...stories.slice(i)]`. I replace or transform with `map`, and I reorder a copy with `[...stories].sort(byTime)` or `toSorted(byTime)`. I keep `slice`, which copies, apart from `splice`, which mutates. A copied array still holds the same item objects, so changing one item means replacing it: `stories.map(s => s.id === id ? { ...s, title } : s)`. Assigning to a field of an item inside a copy would update the screen but also change the previous render's array, and any other list holding that item. When the updates get repetitive, Immer can produce the copies.
