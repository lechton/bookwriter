## Authorized Scope
Q08 teaches splitting a monolithic `App.jsx` into modules with standard ES module syntax in a Vite project: `src/components/ArticleCard.jsx` exports the card as its default export and badge components as named exports, `App.jsx` imports each with the matching form, import paths match on-disk filenames exactly, exported components carry names, and the reader distinguishes the module dependency tree (what runs on import) from the render tree (what runs on render); it builds on Q02 top-level component definition and Q05 the render tree, and it excludes dynamic `import()` and `React.lazy` (Q70), bundle splitting and size analysis (Q70), the mounting files `index.html` and `main.jsx` (Q09), server and client module graphs (Q131, Q132, Q155), and TypeScript (Q90).

## Principles

### Principle 1: Give each shared component its own module
- **Kind**: Decision
- **Rule**: Move a component into its own file under `src/components/` when another file needs it or when its current file becomes hard to scan, export it from there, and keep a helper that only one component uses in that component's file without `export`.
- **Importance**: The card's Friction is a 1,200-line `App.jsx` that causes merge conflicts and blocks reuse, and a reviewer flags both the monolith and a helper exported for no consumer.
- **Review Point — Prefer**: Prefer one module per component that other files import; keep small, tightly related components together until the file gets crowded, and leave private helpers unexported.
- **Required Lesson Proof**: Split the monolithic `App.jsx` into `src/components/ArticleCard.jsx` in three steps (make the file, export, import), show the page unchanged, and show that importing the unexported helper fails the build.
- **Sources**: Core Truth, Mechanism, and Code Experiment of `01-01-map/08.md`; importing-and-exporting "Exporting and importing a component" (merged three steps); your-first-component "Nesting and organizing components" (merged condition).

### Principle 2: Import each component where it renders, in the form it was exported
- **Kind**: Decision
- **Rule**: Every file that renders a component imports it, with `import ArticleCard from '...'` for a default export and `import { Badge } from '...'` for a named export, because ES modules link imports to exports by kind and name before any component runs.
- **Importance**: In the Vite dev server a mismatch blanks the page with "The requested module '/src/components/ArticleCard.jsx' does not provide an export named 'default'", `vite build` stops with `[MISSING_EXPORT] "default" is not exported by "src/components/ArticleCard.jsx".`, and a missing import fails with "ReferenceError: Profile is not defined".
- **Review Point — Do not**: Do not import a named export with default syntax or a default export with braces, and do not render a component in a file that does not import it.
- **Required Lesson Proof**: Reproduce the development error, the build error, and the `ReferenceError`, then show the "Element type is invalid ... but got: undefined" message from `<M.Card />` with a namespace import, and state that this last message, not the module error, is what CommonJS-interop bundlers show for a mismatch.
- **Sources**: importing-and-exporting Deep Dive table and Challenge Hint; the merged development, build, `ReferenceError`, and "Element type is invalid" candidates, verified with Vite 8.3.1 and React 19.3.

### Principle 3: Choose the export style by what the file exports, and keep one convention
- **Kind**: Decision
- **Rule**: Use a default export when a file exists to provide one component and named exports when it provides several components or values, knowing that a file has at most one default export, that a default import accepts any local name, and that a named import must match the exported name.
- **Importance**: An interviewer expects the difference and its trade-off, and a reviewer flags a default import under a misleading name (`import Byline from './ArticleCard.jsx'`) that compiles and renders the card, a mistake a named import would have stopped at build time.
- **Review Point — Condition**: If the file's job is one component, export it as default and import it under the component's own name; if the file exports several things, use named exports; follow the team's single convention when one exists.
- **Required Lesson Proof**: Show `import Byline from './components/ArticleCard.jsx'` rendering the article card without any error, then rename the named export `Badge` and show `vite build` failing with `[MISSING_EXPORT]` at the importer.
- **Sources**: importing-and-exporting Deep Dive and multiple-components section with its Note, merged; Mechanism and Under the Hood of `01-01-map/08.md`.

### Principle 4: Name every exported component
- **Kind**: Decision
- **Rule**: Export components as named function declarations (`export default function ArticleCard() {}`), because an anonymous default export receives the name `default`, and that is the name React prints in its errors and warnings.
- **Importance**: react.dev discourages anonymous components because they make debugging harder, and a crash inside one reports "An error occurred in the <default> component", which points nowhere in a project with many default exports.
- **Review Point — Do**: Check that every exported component has a function name that matches its file.
- **Required Lesson Proof**: Export `() => { throw new Error('boom') }` as a default, show "An error occurred in the <default> component" in the console, then name the function and show the error naming it.
- **Sources**: importing-and-exporting Deep Dive; the merged `<default>` candidate, verified in React 19.3 with Vite 8.3.1.

### Principle 5: Match import paths to filenames exactly, including case
- **Kind**: Decision
- **Rule**: Write every import path with the exact capitalization of the file on disk, because macOS's default file system ignores case and resolves `./components/articleCard.jsx` to `ArticleCard.jsx`, while Linux CI servers do not.
- **Importance**: The build passes on the developer's Mac and fails in CI with `[UNRESOLVED_IMPORT] Could not resolve './components/articleCard.jsx' in src/App.jsx`, and Git on macOS does not record a case-only rename made in Finder, so the wrong casing survives the commit.
- **Review Point — Do**: Check that each import path matches the filename character for character, and rename files with `git mv` when only the case changes.
- **Required Lesson Proof**: Build the wrong-case import successfully on macOS, build the same project on a case-sensitive volume (a case-sensitive disk image or Linux CI) and show the `[UNRESOLVED_IMPORT]` error, then correct the path.
- **Sources**: general engineering knowledge; the merged Git candidate; both builds verified with Vite 8.3.1.

### Principle 6: Separate what runs on import from what runs on render
- **Kind**: Model
- **Rule**: Imports form a module dependency tree: importing a module evaluates its top-level code once, however many files import it, and the bundler ships every module in that tree, while a component function inside the module runs only when the render tree reaches it.
- **Importance**: Without this model a developer expects an imported component to run, or expects an unused import to cost nothing, which breaks Q70's lazy loading and Q131's module boundaries.
- **Prediction**: A `console.log` at the top of an imported module prints once when the page loads even though none of its components render, while a `console.log` inside a component exported from that module stays silent until the component is rendered.
- **Required Lesson Proof**: Import a module with a top-level log and an unrendered component, show the top-level log and the silent component in the console, then render the component and show its log.
- **Sources**: understanding-your-ui-as-a-tree "The Module Dependency Tree" and Recap bullets 5 and 6 (merged); Under the Hood of `01-01-map/08.md`; verified with Vite 8.3.1.

## Senior Answer
I split components across files with standard ES modules: a component that other files use gets its own module under `src/components/`, is exported from there, and is imported in every file that renders it, while helpers used by one component stay unexported in its file. A default export is the one thing a file provides and can be imported under any name, `import ArticleCard from './ArticleCard.jsx'`; named exports can be many per file and must be imported by their exact name inside braces, `import { Badge } from './ArticleCard.jsx'`, so I use a default for a one-component file, named exports for multi-export files, and one team convention. The import form must match the export form: in Vite a mismatch blanks the dev page with "does not provide an export named 'default'" and fails the build with `MISSING_EXPORT`, while the "Element type is invalid ... got: undefined" error appears when an `undefined` value reaches JSX, which is how CommonJS-interop bundlers surface the same mistake. I name every exported component so errors name it, match import paths to filenames including case because Linux CI is case-sensitive even when my Mac is not, and I keep in mind that importing a module runs its top-level code while a component runs only when it renders.
