# Architectural Decision Brief — 2026-09-26-06: Authoritative Natural-Prose Principle Definitions, Genuine Architectural Contrasts, and Anti-Strawman Standard

## Executive Summary
This brief resolves a major systemic defect in how principles were authored across React 06 lectures:
1. **Robotic Bold-Parentheses Stuffing**: Principle definitions had degraded into mechanical formulaic sentences appending bold-parentheses tags (e.g. `(**single common parent**)`, `(**conflicting, desynchronized values**)`) at the end of clauses, mimicking robotic prompt-filling rather than professional senior engineering literature.
2. **Strawman Anti-Patterns**: Principle comparison cards frequently defaulted to trivial syntax mistakes (such as forgetting the `return` keyword), absurd data conversions (`{readTime}` vs `{String(readTime)}` when rendering numbers), or empty comment-only placeholder cards that failed to illustrate real architectural choices.
3. **Repetitive Monolithic Strawmen**: In multi-principle chapters (such as Lesson 05), multiple principles repeatedly attacked the identical anti-pattern ("dumping all HTML into App.jsx") rather than isolating distinct architectural invariants.

Under `#2026_09_26_06_group_1`, we de-prescribe robotic parenthetical tagging, mandate fluent natural prose with inline-bolded terminology, enforce genuine competing architectural paradigms in comparative code cases, and require multi-principle chapters to isolate distinct architectural dimensions.

## 1. Root Cause Analysis

### 1.1 The Robotic Bold-Parentheses Instruction Defect
In batch `#2026_09_26_03_group_1`, an instruction was added to `principled-theory/SKILL.md`:
> *"Does the definition lead with plain-English physical reality and everyday developer concepts first, immediately followed by the formal interview term in bold parentheses or attached context (e.g. tree of **React components** (active runtime render tree) or store shared data once in the common parent component that wraps our widgets (**single common parent**))..."*

Models interpreted this guidance as a strict literal imperative to append bolded terms inside parentheses `(**term**)` after clauses. This resulted in jarring, unnatural sentences like:
> *"We store shared data once in the common parent component that wraps our widgets (**single common parent**). We pass that data down to each child through props so different parts of the screen never show conflicting information (**conflicting, desynchronized values**)."*

This violated The Golden Rule of De-Prescription. The marginal gloss (`>> term : definition`) was already designed to display the isolated dictionary definition; forcing duplicate parenthetical bold-tags inside the prose created visual clutter and destroyed editorial cadence.

### 1.2 The Trivial Syntax Error & Absurd Conversion Traps
When generating "Instead of doing this:" / "We should not do this:" cases, models frequently resorted to trivial strawmen:
- In Lesson 02: Contrasting returning JSX against omitting the `return` keyword entirely (`function Card() { <div>...</div> }`). Forgetting a `return` keyword is a junior JavaScript syntax typo, not an architectural invariant of React.
- In Lesson 04: Contrasting `{readTime}` with `{String(readTime)}` under the guise of teaching primitive rendering. React natively renders numbers into text nodes; calling `String()` produces the exact same DOM output and teaches nothing about React's boolean/null primitive rules.
- In Lesson 05: Showing `import ArticleCard from './ArticleCard.jsx';` with an empty card and a comment `// Never mounted in a JSX return!`.

### 1.3 The Repetitive Monolith Anti-Pattern
In Lesson 05, four separate principles (Principles 1, 2, 4, and 5) all set their bad code case to "dumping all HTML into App.jsx". This created severe fatigue and failed to articulate why trees exist: composition boundaries, unidirectional data flow, and logical ownership vs DOM nesting are three completely different architectural invariants.

## 2. The New Standards (#2026_09_26_06_group_1)

### 2.1 Natural Prose Principle Definitions
Principle definitions must be written in fluent, authoritative English prose across 2 to 3 calm sentences. Formal terms are embedded and bolded naturally where they occur in the sentence. Robotic parenthetical tagging `(**term**)` is strictly prohibited. The marginal gloss (`>> term : definition`) handles the formal definition alongside the card.

### 2.2 Genuine Architectural Contrasts (Anti-Strawman Standard)
Principle code cases must contrast real, competing engineering paradigms or authentic real-world failure modes:
1. **Declarative Projection vs Imperative DOM Mutation** (Lesson 01 Principle 1): Returning JSX descriptors vs `document.getElementById()` / `element.textContent`.
2. **Declarative UI Descriptors vs Imperative DOM Creation** (Lesson 02 Principle 2): Returning JSX vs `document.createElement()` and `document.body.appendChild()`.
3. **Component Elements vs Direct Function Invocation** (Lesson 02 Principle 3): `<ArticleCard />` (tracked component instance with lifecycle and hooks) vs `{ArticleCard()}` (direct helper call bypassing React).
4. **React Fragments vs Extraneous DOM Wrappers** (Lesson 03 Principle 2): `<>...</>` vs polluting the DOM with extra `<div>...</div>` containers.
5. **Idiomatic Boolean Short-Circuit vs Null-Returning Ternary** (Lesson 04 Principle 4): `{isUrgent && <span className="badge">LIVE</span>}` vs `{isUrgent ? <span className="badge">LIVE</span> : null}`.
6. **Top-Down Downward Props vs Global State** (Lesson 05 Principle 2): Passing props downward vs mutating `window.selectedStory = 42`.
7. **Logical Component Ownership vs Physical DOM Nesting** (Lesson 05 Principle 3): Composing via props children vs monolithic HTML wrapper nesting.

### 2.3 Distinct Architectural Dimensions in Multi-Principle Chapters
When a chapter contains multiple principles, each principle must govern an independent architectural invariant. Repeating the same anti-pattern across multiple principles is strictly prohibited.

## 3. Examples to Follow (Proper Examples)

### Example 1: Natural Prose & Declarative vs Imperative Contrast (Lesson 1 Principle 1)
```markdown
> [!PRINCIPLE]
> **Principle 1: Derive the Entire User Interface Directly from Data**
> User interfaces in React are pure projections of application data: UI = f(data). When data changes, React recalculates the required markup automatically, eliminating manual DOM queries and surgical querySelector scripts.
> 
> >> pure projection : interface markup calculated directly from input data without reading external browser DOM state
> 
> *It is best practice to do this:*
> function Header({ user }) {
>   return (
>     <h1>Welcome, {user.name}</h1>
>   );
> }
> 
> *Instead of doing this:*
> function updateHeader(user) {
>   const el =
>     document.getElementById('name');
>   el.textContent = user.name;
> }
```

### Example 2: React Component Tags vs Direct Function Calls (Lesson 2 Principle 3)
```markdown
> [!PRINCIPLE]
> **Principle 3: Render Components Using JSX Tags, Not Direct Function Calls**
> When mounting a component, write it as a JSX tag like `<ArticleCard />` so React registers the component in its tree. Calling a component as a raw JavaScript function like `{ArticleCard()}` executes the code immediately but bypasses React's lifecycle and hook tracking.
> 
> >> JSX element tag : syntax that tells React to manage a component's lifecycle and render tree presence
> 
> *It is best practice to do this:*
> function NewsFeed() {
>   return (
>     <main>
>       <ArticleCard />
>     </main>
>   );
> }
> 
> *Instead of doing this:*
> function NewsFeed() {
>   return (
>     <main>
>       {ArticleCard()}
>     </main>
>   );
> }
```

## 4. Counter-Examples to NOT Follow

### Counter-Example 1: The Robotic Parentheses Stuffing Anti-Pattern
```markdown
> [!PRINCIPLE]
> **Principle 2: Lift Shared State to the Closest Common Parent**
> We store shared data once in the common parent component that wraps our widgets (**single common parent**). We pass that data down to each child through props so different parts of the screen never show conflicting information (**conflicting, desynchronized values**).
```
*Why it fails*: Appending `(**single common parent**)` and `(**conflicting, desynchronized values**)` in bold parentheses at the ends of sentences reads like an automated template rather than published literature.

### Counter-Example 2: The Trivial Syntax Typo Strawman
```markdown
> [!PRINCIPLE]
> **Principle 2: Always Return JSX from Components**
> 
> *We should do this:*
> function Card() {
>   return (
>     <div>Story</div>
>   );
> }
> 
> *We should not do this:*
> function Card() {
>   <div>Story</div>
> }
```
*Why it fails*: Forgetting `return` is a trivial syntax omission, not an architectural principle.

### Counter-Example 3: The Absurd Data Conversion Strawman
```markdown
> [!PRINCIPLE]
> **Principle 4: Render Dynamic Primitives in JSX**
> 
> *It is best practice to do this:*
> <span>{readTime}</span>
> 
> *Instead of doing this:*
> <span>{String(readTime)}</span>
```
*Why it fails*: React renders numbers natively; `{String(readTime)}` produces the identical DOM output and is not an authentic architectural mistake.

### Counter-Example 4: Repetitive Monolithic Strawmen
Repeating "dumping all HTML in App.jsx" across Principles 1, 2, 4, and 5 in the same lesson.
*Why it fails*: Each principle must address an independent invariant rather than attacking the same strawman four times.
