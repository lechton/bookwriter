## 2. Detailed Defect Analysis: What Is Missing from Lecture 04

An exhaustive audit of `01-02-md-LECTURES/04.md` and its corresponding blueprint `01-01-md-PRE-lectures/04.md` reveals that the treatment of JSX attributes and DOM properties is completely superficial:

1. **Bare Assertion Without Derivation**: The phrase `Attribute names use camelCase (className, htmlFor) to prevent collisions with JavaScript reserved keywords` asserts a rule without showing the collision in action. A newcomer cannot visualize how a keyword collision manifests during compilation or execution.
2. **Total Absence of `htmlFor` in Code and Narrative**: While `htmlFor` is mentioned once in parentheses on line 49 and cited in a closing footnote on line 204, there is no `<label>` element, no `<input>` element, and no form control anywhere in the lecture code. The student is told `htmlFor` exists but is never shown why `for` fails or how `htmlFor` links to an input `id`.
3. **Missing Distinction Between HTML Attributes and DOM Properties**: The lecture fails to explain the foundational architecture of the web platform: that HTML markup strings (`class="..."`, `for="..."`) represent markup attributes, whereas parsed JavaScript nodes in the browser DOM represent object properties (`node.className`, `node.htmlFor`).
4. **Missing Compilation Deconstruction**: The lecture mentions that JSX compiles to `_jsx()`, but fails to show that JSX attributes become keys in a plain JavaScript object: `{ className: "story-photo", src: "/breaking.jpg" }`. In early ECMAScript environments, unquoted reserved words as object keys or dot properties (`props.class`, `{ class: "btn" }`) caused syntax errors in JavaScript engines, cementing the decision to adopt DOM property names.
5. **No Coverage of the Broader camelCase Invariant**: Common multi-word HTML attributes (`tabindex` ➔ `tabIndex`, `contenteditable` ➔ `contentEditable`, `colspan` ➔ `colSpan`, `stroke-width` ➔ `strokeWidth`, `onclick` ➔ `onClick`) are never mentioned.
6. **No Mention of Universal Exceptions**: The two load-bearing web standards that strictly retain hyphens/kebab-case—`aria-*` accessibility attributes (e.g. `aria-label`, `aria-hidden`) and `data-*` custom data attributes (e.g. `data-testid`)—are omitted entirely.

## 4. The Complete Knowledge Base: What Must Be Taught

To provide a serious, zero-gap pedagogical explanation for the student, Lecture 4 must unpack four interrelated layers of browser and compiler reality:

### Layer 1: HTML Markup Strings vs. JavaScript DOM Object Properties
In plain HTML files, developers write raw markup strings:
```html
<div class="alert-box">
  <label for="subscriber-email">Email:</label>
  <input id="subscriber-email" tabindex="1" />
</div>
```
When the browser parses this HTML into the Document Object Model (DOM) in memory, it instantiates JavaScript objects (`HTMLDivElement`, `HTMLLabelElement`, `HTMLInputElement`). Decades before React existed, the ECMAScript DOM committee had to map markup attributes to JavaScript object properties:
- In JavaScript, `class` was already a reserved keyword used for object-oriented class declarations (`class Rectangle { ... }`). Writing `element.class` was illegal syntax in ECMAScript. Therefore, the browser DOM API named the property `element.className`.
- In JavaScript, `for` was already a reserved keyword used for loops (`for (let i = 0; ...)`). Writing `label.for` was illegal syntax. Therefore, the browser DOM API named the property `labelElement.htmlFor`.
- Similarly, HTML attributes without casing were standardized as camelCase properties on DOM nodes: `tabindex` became `element.tabIndex`, `readonly` became `element.readOnly`, and `colspan` became `element.colSpan`.

### Layer 2: JSX Is an Object Literal Transform, Not HTML String Parsing
JSX does not evaluate to an HTML string. When the compiler processes JSX, it transforms element tags and attributes into function calls that receive a plain JavaScript object:
```javascript
// JSX Input:
<label className="field-label" htmlFor="email-input">

// Transpiled JavaScript Output:
_jsx("label", {
  className: "field-label",
  htmlFor: "email-input"
});
```
React deliberately designed JSX attributes to match the **browser's native DOM property names** (`node.className`, `node.htmlFor`) rather than raw HTML attribute strings (`node.getAttribute('class')`). This alignment creates a 1:1 mental model between writing JSX properties and manipulating native DOM element properties in JavaScript.

### Layer 3: The Universal camelCase Rule
Because JSX attributes are JavaScript object properties, JSX enforces camelCase for virtually all standard HTML attributes that consist of multiple words or compound tokens:
- `tabindex` ➔ `tabIndex`
- `contenteditable` ➔ `contentEditable`
- `stroke-width` (SVG) ➔ `strokeWidth`
- `autofocus` ➔ `autoFocus`
- Native event listener attributes: `onclick` ➔ `onClick`, `onchange` ➔ `onChange`, `onsubmit` ➔ `onSubmit`.

### Layer 4: The Strict Universal Exceptions (`aria-*` and `data-*`)
Unlike standard HTML attributes, accessibility attributes (`aria-*`) and custom dataset attributes (`data-*`) are **never converted to camelCase**. They strictly retain their hyphenated kebab-case syntax in JSX:
- `<input aria-label="Search articles" aria-required="true" />`
- `<div data-testid="news-alert-card" data-category="breaking" />`

**Why?** Web accessibility specifications (W3C WAI-ARIA) and HTML5 custom dataset standards define these attributes with strict hyphens. Furthermore, assistive screen-reader software and CSS attribute selectors (`[aria-expanded="true"]`, `[data-category="breaking"]`) rely on exact hyphenated string queries. Converting them to camelCase would break CSS styling hooks and accessibility auditing tools.
