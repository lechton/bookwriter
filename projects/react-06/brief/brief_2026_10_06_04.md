# Brief 2026-10-06-04: Principles Learned From Examples, Not From Steps

## Overview & Metadata

## Review: What the Sessions Taught

1. **Every rule added to fix a box made the next box worse.** Over the last batches the instructions gained "a code pair in every box", "four beats: expectation, choice, reason, cost", "general names in the box, lesson names below it", "define render once", eight thinking steps, a field-by-field map entry (Roles, Placement, Mechanism, Review Point, Code Pair), and a blueprint element answering every step. Each rule was reasonable alone. Together they produced the demo's Principle 7, which followed the four beats exactly and still made no sense: "stores code that runs later" (later than what?), then "to build the button, React runs the component function", before the reader knew what goes wrong.
2. **The owner's version works because it follows the reader's questions, not a pattern.** We give a button a function. When does it run? We expect: on the click. It actually runs already when the component appears. So write this instead. A different principle asks different questions in a different order, so no fixed order of parts can produce this. Examples can, because they show the move and leave the order to the topic.
3. **Precise words beat pictures, and the reader loses.** The rules asked for canonical terms, so boxes said "survive renders", "during render", "evaluation window", "empty render slot", "premature invocation", "living DOM text nodes". The reader can picture none of them. The fix is one standard (say what the reader would see or do), not a list of banned words.
4. **The instructions contradicted each other.** `principle-definition` required a code pair in every box; `principled-theory` Section 04 and `verification` Section 10 still required Model principles to drop the pair. The skills also told authors to read Lecture 04 as the living benchmark, while Lecture 04's boxes are the jargon the owner rejects ("evaluation window", "injects its value directly into the rendered tree").
5. **The exemplar bank taught the wrong thing.** Most of its PROPER boxes came from Lectures 01 to 13 and carry the same abstractions (virtual DOM reconciliation "surgically patching", "UI descriptors", "empty render slots"). Several exemplar names (`coverUrl`, `handlePublish`) leaked into later lectures, because an exemplar without an analysis is copied for its surface.
6. **Bad versions teach as much as good ones, when each carries its diagnosis.** "What is later? Later from what?" teaches more than any checklist line. The old rule "describe failing drafts in prose, never print them" removed exactly this evidence.
7. **The map wrote the box before the author did.** Its Roles, Code Pair, and Review Point fields were finished sentences and one-line pairs on the lesson's names. Authors pasted them, which gave context-free pairs such as `onClick={() => setLikes(likes + 1)}` alone in a box.
8. **The mechanical limits are real but belong to scripts.** The 68-character card line, a comment on each card, quoted backtick lines inside the `>` block, and named owner lessons are build needs. `diagnose-lecture` and the build already check most of them, so the writing guidance does not need to repeat them as quality rules.

## The Plan

1. **One casebook** (`group_1`): a new file `skills/v6.5/principle-definition/examples.md`. Each case has its context (what the reader knows at that point), the real failing version quoted verbatim with its source, a better version, and an analysis: what the reader is asking, what the failing version does to them, what the better version does, what to take to another topic, and what not to copy. Cases come from different lessons and topics (curly braces, the rogue zero, purity, passing a handler, callback props, the state pair, assignment, the setter in render, look-alike names, a jargon sweep, the code pair, the paragraph under the box), so no single surface is copied.
2. **One short instruction** (`group_2`): `principle-definition/SKILL.md` is rewritten to a page: what a box is for, the single reading test, "study the casebook and adapt; take the moves, not the words, names, or length", where the facts come from (the map, verified), and the minimum syntax the build needs. The eight steps, the exemplar bank, and the failing-draft list are removed; their useful cases move into the casebook with analyses.
3. **Pruning elsewhere** (`group_3`): every other place that prescribes the box or its explanation is cut back to standards and a pointer to the casebook: `principled-theory` (benchmark gate, the card-free Model rule, the speech-bubble canon, the Lesson 04 explanation canon, mandatory term deconstruction and layer breakdowns, the senior-interview stance, the duplicate universal template), `verification` (the card-free Model rule, gate 20), `lecture-structure` Section 12B (the jargon example box and the steps clause), `pre-lecture` (the eight-step `[principle-steps]` element becomes a free-form `[principle-notes]`), `build`, `README`, and the owner's `produce_prompt.md`.
4. **A slimmer map** (`group_4`): the map gives facts, not prose. `Roles` and `Code Pair` leave the principle entry; `Review Point` keeps only its label (Do, Prefer, Avoid, Do not, Condition), which decides the card labels. `diagnose-map` and maps 04 and 14 follow.
5. **Mechanics in the scripts** (`group_5`): `diagnose-lecture` fails a principle box without a code pair, so no prose rule has to say it twice.
6. **A pilot** (`group_6`): Lecture 14's boxes 1 to 6 are rewritten with only the new instruction and the casebook, beside the owner's Principle 7, then checked with `diagnose-lecture`, the build, and the link check. A good result adds cases to the casebook later; the series is not regenerated in this batch.
