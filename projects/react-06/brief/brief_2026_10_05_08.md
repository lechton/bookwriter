## Batch 1: Maps 14, 15, 16

### Map 14 (`#use_state`, "Why do ordinary variables forget their values between renders, and how does useState remember?")

- **Principle 1 (Decision)**: keep a changing value that the screen shows in state, not in a local variable. Proven by a `let isBookmarked` whose handler logs `true` while the icon stays gray, and which restarts at `false` after a Like click re-renders the card.
- **Principle 2 (Model)**: `useState` hands back the stored value, and its argument is the first value only. Prediction: a log in the body prints 0, 1, 2 over two clicks although the body passes 0 every time.
- **Principle 3 (Model)**: each rendered instance owns its own private state. Prediction: two `StoryCard` elements show 2 and 0 after two clicks on the first.
- **Routed elsewhere**: the "Too many re-renders" error from `onClick={setLikes(likes + 1)}` is recalled from Q13's pass-not-call principle; updaters and batching to Q17; `Object.is`, mutation, and Immer to Q18 and Q19; Hook call order to Q37; StrictMode's double initializer to Q46.

### Map 15 (`#render_and_commit`, "What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?")

- **Principle 1 (Model)**: the DOM changes only in the commit, after our handler returns. Prediction: a DOM read on the line after `setLikes(likes + 1)` prints 0, and the render log for 1 follows it.
- **Principle 2 (Model)**: a state update renders the owner of the state and everything it returns. Prediction: a click in `Feed` logs `Feed` and `Badge`, and neither `App` nor `Sidebar`.
- **Principle 3 (Model)**: the commit touches only the nodes that differ, and the browser's paint comes after it. Prediction: an `<input>` keeps its typed text and stays the same node while the `<h1>` clock changes, and `Badge` renders again with no DOM change.
- **Found while checking**: on a re-render React 19.3 briefly sets and removes an `<input>`'s `name` attribute, which ends with no attribute changed. The proof therefore checks the input by node identity, not by the Elements panel staying still.

### Map 16 (`#state_snapshots`, "Why does state appear frozen inside a render, even right after you set it?")

- **Principle 1 (Model)**: state is fixed for the whole render. Prediction: a log after `setEdition('Evening')` prints `Morning`, and a "+3" button shows 1, then 2.
- **Principle 2 (Decision)**: compute the next value once and use that variable after the setter. Proven by `setRating(5); sendRating(rating)` sending 3 while the screen shows 5.
- **Principle 3 (Model)**: a handler keeps the values of the render that created it. Prediction: the `setTimeout` alert shows 0 while the screen shows 5, and the delayed message still names Alice after the field changes to Bob.
- **Routed elsewhere**: the updater as the way to add three is a one-sentence Preview of Q17 that shows no updater code, as card 16's Scope Boundary requires; refs to Q29; stale values in Effects to Q35 and Q36.

## Batch 2: Maps 17, 18, 19

Written after brief 2026-10-05-09, so every ledger owner carries its number and topic tag (`Q16 #state_snapshots`).

### Map 17 (`#state_updates`, "How does React queue multiple state updates, and when do you need an updater function?")

- **Principle 1 (Model)**: one render per event, however many setters it calls. Prediction: three `setPasses` calls and one `setLabel` call render once; two separate clicks render twice.
- **Principle 2 (Model)**: the queue is read in order; a value replaces the running result, an updater receives it. Prediction: from 0, `+5` then `n => n + 1` renders 6, and adding `setNumber(42)` renders 42.
- **Principle 3 (Decision, Condition)**: pass an updater when the next value comes from the previous one and other updates can come first. Proven by "+3 Free Passes" adding 1 against 3, and by react.dev's Buy counter: with value forms one click ends at `pending -1` and two fast clicks end at `completed 1`; with updaters they end at `pending 0 completed 2`. The Condition keeps react.dev's point that the updater is not required for one update per event.
- **Principle 4 (Decision, Do not)**: keep updaters pure. Proven by an updater called twice per click under StrictMode while the screen rises by 1.
- **Routed elsewhere**: storing a function in state (`setFn(() => fn)`), which map 14 sent here, is Supporting; `flushSync` to Q65; batching across timeouts and promises to Q75; reducers to Q26.

### Map 18 (`#state_objects`, "How do you update an object in state without mutating it?")

- **Principle 1 (Decision, Do not)**: treat a state object as read-only and hand the setter a new one. Proven by `profile.author.bio = 'New bio'; setProfile(profile)`: no render, the old bio on screen, and the new bio appearing on an unrelated render, as card 18's Friction says.
- **Principle 2 (Decision, Do)**: spread the old fields into the new object. Proven by `setProfile({ title: 'Chief' })` losing `author`.
- **Principle 3 (Decision, Do)**: copy every object on the path to a nested change. Proven by a one-level copy plus assignment that updates the screen but also changes the first render's `author` object, while the nested spread leaves it intact.
- **Supporting**: the computed-property handler (`[e.target.name]`) and Immer as a named optional helper; Immer's Proxy internals are Dropped, as the card forbids teaching its API.

### Map 19 (`#state_arrays`, "How do you add, remove, insert, and reorder items in a state array?")

- **Principle 1 (Decision, Do not)**: change a state array only by building a new one, with the full recipe (spread, `filter`, `slice` plus spread, `map`, a sorted copy or `toSorted`) and react.dev's `slice` against `splice` Pitfall. Proven by `splice`, `push`, and `sort` on state causing no render.
- **Principle 2 (Decision, Do)**: replace a changed item with a copy through `map`. Proven by a copied array whose item edit also changes the first render's item, and by react.dev's two lists sharing items.
- **Atomicity**: the individual recipes are one decision with one failure and one correction, so they merge into Principle 1 instead of becoming one principle each.
