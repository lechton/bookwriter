# Brief 2026_09_21_11: Clean Practical Example Section Title Law

- **Date**: 2026-09-21
- **Tag**: `#2026_09_21_11_group_1`
- **Affected Skills**: `skills/lecture-structure/SKILL.md`, `skills/verification/SKILL.md`, `skills/RULE-TAGS.md`

## Context & Defect Analysis
In Lecture 03 (both pre-lecture and production lecture), the main heading for the practical example section was authored as:
`### Let's Design a Practical Example ArticleCard ArticleAuthor`

This was driven by an over-prescriptive rule in `skills/lecture-structure/SKILL.md` (Section 14) that commanded:
`Title using the pattern ### Let's Design a Practical Example <Component1> <Component2>, naming the concrete components assembled.`

This introduced several issues:
1. **Aesthetic & Syntactic Clutter**: Tacking bare component names onto the end of an English sentence produces an ungrammatical, cluttered heading.
2. **Redundancy**: Component files and their roles are already introduced immediately below in Stage A via the Rendered UI Canvas and File Explorer (` ```files `), and individual components are named in the subtitles of Stage C (`### Step 1: First, we construct the parent container ArticleCard.jsx`, etc.).

## The Solution: The Clean Practical Example Heading Law
1. **Clean Uniform Title**: The practical example section must always be titled simply and cleanly:
   `### Let's Design a Practical Example`
2. **Ban Appended Component or Feature Names**: Never append component names, file names, or feature tags to this heading. Component roles belong in the File Explorer and individual step subtitles.
