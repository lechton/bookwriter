# Brief 2026_09_21_15: Tag-Free Code Comments and Right vs Wrong Exception Law

- **Date**: 2026-09-21
- **Tag**: `#2026_09_21_15_group_1`
- **Affected Skills**: `skills/code-blocks/SKILL.md`, `skills/lecture-revision/SKILL.md`, `skills/pedagogical-crossroads/SKILL.md`, `skills/verification/SKILL.md`, `skills/RULE-TAGS.md`

## Context & Defect Analysis
In earlier iterations, rule `#2026_09_20_04_group_6` in `skills/code-blocks/SKILL.md` (Section 12) mandated that authors annotate code lines in Stage C assembly steps with structured uppercase tags (`// **CODE LOGIC:**<br>` and `// **DATA FLOW:**<br>`).

This prescriptive requirement caused several severe defects across lectures:
1. **Speech Bubble Clutter**: The uppercase prefix tags consumed precious horizontal width inside print speech bubbles, creating bureaucratic administrative taxonomy rather than helpful, concise explanations.
2. **Model Extrapolation & Tag Proliferation**: The model generalized this pattern and began inventing dozens of uppercase category tags across every code block (`**CLIENT API:**<br>`, `**ROOT INITIALIZATION:**<br>`, `**DOM CONTAINER:**<br>`, `**TREE PROJECTION:**<br>`, `**SAFETY GUARD:**<br>`, `**ERROR BOUNDARY:**<br>`, `**DEVELOPER TOOL:**<br>`, `**COMPONENT:**<br>`).
3. **Alienated Reader Experience**: Code comments should clarify line-level mechanics and data flow in natural, fluent English that directly matches the reader's thoughts, not pigeonhole statements into artificial categories.

## The Solution: The Golden Rule of De-Prescription
1. **Pruning Section 12**: Section 12 of `skills/code-blocks/SKILL.md` is completely pruned and superseded by rule `#2026_09_21_15_group_1`.
2. **Tag-Free Code Comments**: All code comments across all steps must be written in clean, natural English prose without uppercase category prefix tags.
3. **The Single Permitted Exception (RIGHT vs WRONG Comparisons)**: When contrasting competing approaches inside comparative code blocks where identifying the valid versus invalid line is directly necessary, comments MAY be prefixed with `// **WRONG:** ...` and `// **RIGHT:** ...`.
4. **Natural Emphasis**: Standard comments retain emphasis on single load-bearing architectural terms formatted in uppercase bold (Section 10) or chronological sequential numbering `// (1) ...` (Section 11), ensuring scanning clarity without tag clutter.
