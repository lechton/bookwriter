# Architectural Decision Brief — 2026-09-26-10: Routine vs. Experimental Visual Warrant Law, Absolute pdftoppm Production Ban, and Terminal Build Boundary

## Executive Summary
This architectural decision brief establishes the definitive boundary between **Routine Production** and **Experimental Visual Engineering**, codifying an absolute ban on `pdftoppm` and PDF page screenshots during routine lecture authoring and figure adaptation.

Historically, AI agents suffered from a reflexive tendency to convert PDFs to PNGs and call `view_file` after compiling routine lectures. When asked why, agents pointed to legacy instructions—specifically a rule originally drafted for the CSS rendering pipeline (`AGENTS.md#L104`) that instructed taking screenshots *"after creating or modifying every UI image"*. When applied blindly to React lecture production, this caused massive token waste, slowed down delivery, and violated the core principle that clean compiler output (`node src/build-lectures.mjs` with code 0 and zero warnings) is the definitive proof of structural and layout completion.

Under `#2026_09_26_10_group_1`, we apply the **Golden Rule of De-Prescription**: we prune the blanket "every UI image" prescription, ban reflexive screenshotting during routine authoring, and restrict visual image inspections via `pdftoppm` strictly to three narrow, warranted conditions.

## 1. Root Cause Analysis

### 1.1 The "Every Figure" Legacy Prescription
In earlier visual pipelines (such as `css-01`), canvas modes were written in raw JavaScript (`src/css-figure.mjs`) without pre-tested component architectures. To protect against layout blowups, a rule was added:
> *"UI Image Verification Gate: Take screenshots ... after creating or modifying every UI image / figure canvas mode"*

In production React lecture authoring, however, figures are NOT built from scratch every time. Instead, lectures routinely adapt proven catalog templates:
- **Archetype 09**: Progressive Assembly Step Cards (`templates/09-progressive-assembly-step-cards.html`) for Stage B.
- **Archetype 10**: Architecture Audit Comparison Tables (`templates/10-architecture-audit-vtable.html`) for Stage E.

These catalog archetypes have already been mathematically stress-tested and visually certified. Adapting them with lecture-specific text and component names is a routine templating task. Treating every routine adaptation as a new visual experiment triggered constant, pointless `pdftoppm` dumps.

### 1.2 The Reflexive Screenshot Overreach
Even after running `node src/build-lectures.mjs` and obtaining exit code 0 with zero warnings, models frequently fabricated pretexts to run `pdftoppm` ("checking pagination", "verifying visual appeal", "confirming zero defects"). This violated the core tenet of agentic efficiency and ignored the existing rule `#2026_09_20_28_group_1`.

### 1.3 The Two Types of Figure Creation: Routine vs. Experimental
As clarified by user guidance, figure creation falls into two distinct categories:
1. **Routine Figure Adaptation (Camera OFF)**: Adapting existing, proven catalog templates (Archetypes 01–10) to the current lecture's topic. Here, 100% of validation is mechanical. If Prince XML compiles cleanly without warnings, the figure is correct. No screenshot is warranted or permitted.
2. **Experimental Visual Blueprints & Visual Defect Resolution (Camera WARRANTED)**: Engineering brand-new visual templates in `figures/templates/` from scratch with unproven CSS geometry, diagnosing an explicit visual layout defect (e.g. text overlapping, clipping), or responding to an explicit user command in chat.

## 2. The New Standards (#2026_09_26_10_group_1)

### 2.1 The Terminal Build Boundary
A clean compiler exit (`node src/build-lectures.mjs` exiting with code 0 and zero warnings) marks the definitive, non-negotiable end of routine build tasks. Agents must immediately halt tool calls upon seeing clean compiler output.

### 2.2 The Three Explicit Warrant Conditions for `pdftoppm`
Executing `pdftoppm`, converting PDFs to images, or calling `view_file` on PDF page renders is strictly prohibited unless one of three explicit conditions is met:
1. **Experimental Visual Blueprints**: When authoring or testing a brand-new visual archetype or blueprint template from scratch in `figures/templates/` with unproven CSS geometry.
2. **Visual Layout Defect Resolution**: When diagnosing or resolving an explicit, known visual bug (e.g., text overlapping, container clipping, border collision).
3. **Explicit User Chat Command**: When the human user directly commands a visual inspection in their chat message.

Outside these three narrow conditions, the camera remains strictly off.
