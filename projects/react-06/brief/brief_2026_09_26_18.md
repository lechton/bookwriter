# Architectural Decision Brief — 2026-09-26-18: Principle Explanation Substrate Variety, Lesson 04 Benchmark Patterns, and Natural Code Comments Standard

## Executive Summary
This brief de-prescribes the rigid 5-part explanation checklist previously codified under `#2026_09_26_16_group_1`, which inadvertently caused authors to treat principle derivations as a mechanical form-filling exercise ending with identical, cookie-cutter 1-to-5 numbered lists under every principle. Under `#2026_09_26_18_group_1`, we restore the living pedagogical benchmark of Lesson 04 (`01-02-md-LECTURES/v5/04.md#L90-L380`), establish the **Principle Explanation Canon** with 3 distinct benchmark pedagogical patterns (Grammar / Compiler Proofs, Runtime Evaluation Walkthroughs, and Deconstruction / Extraction Proofs), and codify the **Natural Code Comments Standard** to permanently eliminate uppercase category shouting and markdown asterisk clutter inside code comments (`// Top-level **ROOT**` -> `// Top-level container`).

## 1. Root Cause Analysis

### 1.1 The Bureaucratic Checklist Fallacy
Under rule `#2026_09_26_16_group_1`, the instruction stated: *"Every derivation must provide: (1) tactile real-world friction context, (2) titled code block of the naive or anti-pattern code, (3) titled code block of the compiler translation, browser DOM breakdown, or runtime crash, (4) titled code block of the React resolution, and (5) step-by-step physical machine trace."* When interpreting this rule, authors and AI models treated the 5 items as a mandatory cookie-cutter template that had to be stamped identically onto every single principle.

### 1.2 Forced Numbered List Homogenization
Item `(5) step-by-step physical machine trace` was mechanically translated into a repetitive numbered list (`1... 2... 3... 4... 5...`) across every principle in Lesson 05. This replaced organic, conversational B2 English explanations with robotic pipeline recitation, destroying the pedagogical variety demonstrated in canonical benchmark lessons.

### 1.3 Comment Shouting and Markdown Asterisk Clutter
Authors began inserting markdown bolding syntax (`**...**`) into inline code comments (e.g. `// Top-level **ROOT**`, `// Layout **BRANCH**`, `// Article **CARD**`). In code display blocks, markdown asterisks do not render as styled typography; they remain literal asterisk characters, creating unparsed syntax clutter and looking like prompt leakage.

## 2. The Solution Architecture (#2026_09_26_18_group_1)

### 2.1 De-Prescription of the Explanation Checklist
- The rigid 5-item checklist in `skills/v6.3/principled-theory/SKILL.md#L105` is pruned.
- The rule is re-anchored directly in the Lesson 04 living benchmark, mandating that derivations ground principles in concrete titled code blocks illustrating machine behavior (compiler outputs, evaluated expressions, browser renders, syntax errors) while allowing the pedagogical substrate to emerge organically from the mechanism.
- Rigid cookie-cutter homogenization and forced numbered list quotas are explicitly prohibited.

### 2.2 Codification of the Principle Explanation Canon
A new dedicated section—`### The Principle Explanation Canon (Benchmark Pedagogical Patterns from Lesson 04)`—is added to `skills/v6.3/principled-theory/SKILL.md`, featuring:
1. **The Grammar / Compiler Proof Pattern (Lesson 04 Principle 2)**: Explaining why statements like `if` cannot be passed into functions using compiler output and rhetorical JavaScript grammar proofs (`console.log(if (...))`).
2. **The Runtime Evaluation Walkthrough Pattern (Lesson 04 Principle 5)**: Explaining the Rogue Zero bug by tracing the 4-step short-circuiting of `&&`, contrasting stringification with DOM text node creation, and presenting the 3 production remedies.
3. **The Counter-Example for Cookie-Cutter Numbered Lists & Comment Shouting**: Demonstrating the homogenized template failure seen in Lesson 05.

### 2.3 Natural Code Comments Standard
- Inline code comments must be written in clean, active English describing the physical code action (e.g. `// Short-circuits to boolean value`, `// Evaluates left side zero`).
- Markdown asterisks (`**...**`) and uppercase shouting labels inside code comments are strictly eliminated.
