# Q14: Responding to Events
* **Topic Tag**: `#event_handling` | `❱ CORE`
* **Interview Question**: *How do you respond to user events like clicks and typing?*
* **Core Truth**: React attaches event handlers declaratively as camelCase function props (like `onClick` and `onChange`); handler functions receive a synthetic event object and execute in response to user interactions, acting as the primary home for side effects.
* **The Friction**: An engineer writes `onClick={handleClick()}` instead of `onClick={handleClick}` on a "Subscribe" button. The function executes immediately on page load before the user ever touches the button, triggering infinite alerts or premature analytics events, while passing parameters inline requires awkward workarounds.
* **The Mechanism**: Declarative event handling. Passing function references (`onClick={handleClick}`), inline arrow functions for arguments (`onClick={() => handleBookmark(article.id)}`), reading `event.target`, and stopping default browser actions via `event.preventDefault()` and `event.stopPropagation()`.
* **Under the Hood**: Passing a function reference vs calling a function during render; how React wraps native browser events in a cross-browser SyntheticEvent wrapper, delegating events at the root container to maximize performance.
* **The Code Experiment**:
  * *Naive*: Invoking the handler immediately in JSX (`onClick={openArticle(id)}`) causing execution at render time, or attempting imperative `addEventListener` in script tags.
  * *React*: An `ArticleActions` toolbar with `onClick={handleBookmark}` and an inline arrow function passing arguments, using `e.stopPropagation()` to prevent triggering parent card navigation.
* **Scope Boundary**: Focus strictly on event handler syntax, passing references vs invoking, synthetic event basics, and event propagation. Do not introduce `useState` for stateful updates (reserved for Q16).
