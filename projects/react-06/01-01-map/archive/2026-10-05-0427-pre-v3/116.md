# Q116: Context Across the Server/Client Boundary
* **Topic Tag**: #context_server | ❱ CORE (Server)
* **Interview Question**: *How does context behave across the server/client boundary?*
* **Core Truth**: createContext and useContext are client-only APIs because Server Components do not maintain state or re-render; Context Providers must be Client Components, but they can accept server-fetched data as value props to distribute across client trees.
* **The Friction**: A developer attempts to create a ServerEditionContext in an async Server Component at The National Times to share current edition metadata with 15 child components; the build fails immediately with "createContext is not supported in Server Components", leaving the team confused about how to distribute shared data.
* **The Mechanism**: Context boundary rules: (1) createContext cannot be called in Server Components; (2) Context Providers must be marked 'use client'; (3) A Server Component can render a Client Provider and pass server data via props: <ClientThemeProvider initialTheme={theme}>{children}</ClientThemeProvider>.
* **Under the Hood**: Why Server Components lack Context: Context is designed for dynamic propagation of state changes and re-renders; Server Components render once into a static or streaming payload and have no reactive update cycle, so React provides per-request cache() for server data sharing instead.
* **The Code Experiment**:
  * *Naive*: Calling React.createContext() inside a Server Component file and wrapping server children in <EditionContext.Provider>.
  * *React*: Creating a 'use client' EditionProvider component that receives server data as props and provides it to interactive client consumers via useContext.
* **Scope Boundary**: Focus on why Context is client-only, how to bridge server data into client context providers, and proper architectural boundaries. Server-side caching (cache()) is covered in Q123.
