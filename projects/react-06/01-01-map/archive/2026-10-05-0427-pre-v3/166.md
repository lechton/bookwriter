# Q166: The RSC Payload Encoding: Rows, Module References, and Lazy Chunks
* **Topic Tag**: #rsc_payload | ❱❱❱ ADVANCED (Server)
* **Interview Question**: *How is the RSC payload encoded: rows, module references, and lazy chunks?*
* **Core Truth**: The RSC payload is a line-delimited, streaming text protocol where each row defines a tagged instruction—module references (M), element trees (J), Suspense chunk placeholders, and error rows—enabling the client to assemble the virtual DOM as chunks arrive.
* **The Friction**: A performance engineer at The National Times analyzing network traces sees mysterious lines like 1:I["./Button.js",["chunk1"],""] and 0:{"title":"Breaking News","body":"$L2"} in HTTP responses; unable to decode the Flight wire protocol, they cannot optimize chunk payloads or debug stream delivery stalls.
* **The Mechanism**: Row prefixes in React Flight: (1) M: Client module reference (chunk path, exports); (2) J: JSON virtual DOM element tree; (3) $L: Lazy promise placeholder pointing to a row ID that will arrive later in the stream; (4) S: Symbol/Suspense boundary; (5) E: Serialized error.
* **Under the Hood**: Incremental Flight parsing: the browser Flight client maintains an array of deferred chunk resolvers; when it encounters a $L2 reference in row 0, it creates an unresolved promise; when row 2: arrives later down the wire, it resolves that promise and stitches the new subtree into the live Fiber tree.
* **The Code Experiment**:
  * *Naive*: Treating the RSC payload as a standard monolithic JSON object and attempting to parse it with JSON.parse(), causing syntax errors on streaming line breaks.
  * *React*: Streaming the line-delimited response and decoding row identifiers (M, J, $L) to observe how lazy chunks resolve in real-time.
* **Scope Boundary**: Focus on the exact Flight wire encoding, row structure, module reference syntax, and how lazy row IDs coordinate out-of-order resolution.
