# Q66: Concurrent Rendering and Interruptible Work
* **Topic Tag**: `#concurrent_rendering` | `❱❱ MORE`
* **Interview Question**: *What is concurrent rendering, and how does React keep the interface responsive during heavy computation?*
* **Core Truth**: Concurrent rendering allows React to pause, abort, and resume rendering work in memory across multiple frames without blocking the main browser thread, ensuring urgent user interactions (typing, clicking) are never delayed by heavy background updates.
* **The Friction**: A reader types into an article filter while a heavy 10,000-node chart renders. In synchronous React (pre-18), the entire browser thread is locked during the render pass; the user's keystrokes freeze, cursor blinking stops, and the page becomes completely unresponsive.
* **The Mechanism**: Concurrent rendering. React assigns priority lanes to updates (Urgent lanes for typing/clicks, Transition lanes for search results/charts). React can yield execution back to the browser between individual component renders to process user input.
* **Under the Hood**: Cooperative multitasking with the Fiber workLoop: rather than executing synchronously via recursion, React runs a loop (`while (workInProgress !== null && !shouldYield())`) checked against the browser's deadline; incomplete renders are kept in memory and never committed to the physical DOM until finished.
* **The Code Experiment**:
  * *Naive*: Executing a heavy calculation inside a standard state update, completely freezing input responsiveness during execution.
  * *React*: Demonstrating how React's concurrent scheduler splits a heavy render across multiple micro-chunks, keeping an input cursor responsive while the tree computes.
* **Scope Boundary**: Focus on the foundational concepts of concurrent rendering (interruptible work, yielding to the browser, priority lanes, no partial DOM commits). Do not delve into specific hooks like `useTransition` (Q67) or `useDeferredValue` (Q68).
