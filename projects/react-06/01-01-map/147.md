# Q147: Lifecycle and Boundaries of cache(): What It Is and What It Is Not
* **Topic Tag**: #cache | ❱❱ MORE (Server)
* **Interview Question**: *How long does cache() live, and what is it not?*
* **Core Truth**: React's cache() lives strictly for the duration of a single server request or render pass, deduplicating work within that request; it is not a shared cross-request cache, not a distributed store like Redis, and does not persist across user visits.
* **The Friction**: An engineer wraps getGlobalTrendingStories() in React's cache(), expecting it to serve all 50,000 concurrent readers from a shared in-memory cache; instead, every incoming HTTP request re-executes the database query, overwhelming the database cluster.
* **The Mechanism**: Scope of cache(): per-request memoization; arguments are compared by shallow equality (Object.is); the cached return value is garbage-collected as soon as the current HTTP request finishes rendering.
* **Under the Hood**: Request-scoped storage: cache() uses an internal WeakMap keyed to the current render context / AsyncLocalStorage; because it has no cross-process or cross-request storage, it provides zero risk of leaking private user session data across different readers, but provides zero cross-request caching.
* **The Code Experiment**:
  * *Naive*: Expecting cache() to replace Redis or CDN caching for high-traffic shared data across multiple users.
  * *React*: Using cache() to deduplicate user-specific fetches (e.g. getUserSession(id)) across multiple components within a single request, while using Redis or HTTP cache headers for cross-request shared data.
* **Scope Boundary**: Focus on the exact lifecycle, memory boundaries, and misuse of cache(). Do not confuse with persistent server caches.
