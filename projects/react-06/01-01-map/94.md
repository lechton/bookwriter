# Q94: ESLint Rules of Hooks and React Compiler Tooling
* **Topic Tag**: `#eslint_and_tooling` | `❱❱❱ ADVANCED`
* **Interview Question**: *What do the React Hooks and Compiler lint rules catch, and why should they never be disabled?*
* **Core Truth**: React lint rules (`eslint-plugin-react-hooks` and `eslint-plugin-react-compiler`) are formal verifiers of the mathematical contract of React; disabling them suppresses early warnings of severe runtime bugs including stale closures, infinite render loops, and compiler bailouts.
* **The Friction**: A rushed developer adds `// eslint-disable-next-line react-hooks/exhaustive-deps` to bypass an effect dependency warning. Weeks later, an article bookmarking feature silently reads a stale user token, saving articles to the wrong account in production and causing an embarrassing privacy breach.
* **The Mechanism**: ESLint rules for React: `rules-of-hooks` (enforces top-level calls) and `exhaustive-deps` (guarantees effect dependency correctness), complemented by React Compiler linter checks that detect mutations during render, illegal ref access in render, and non-idempotent functions.
* **Under the Hood**: Static control flow analysis: the linter constructs an AST graph of variable declarations and closures within component bodies; when an effect references a variable that can change between renders without listing it in dependencies, it formally detects a stale closure hazard.
* **The Code Experiment**:
  * *Naive*: Silencing `exhaustive-deps` with a comment to stop an infinite re-render loop, masking an underlying reference instability bug.
  * *React*: Refactoring the component by extracting helper functions, using updater functions, or stabilizing dependencies, allowing the linter to pass with zero suppressions.
* **Scope Boundary**: Focus on the rationale and enforcement of React lint rules, the dangers of lint suppression, and fixing root-cause dependency bugs. Do not delve into custom ESLint plugin development.
