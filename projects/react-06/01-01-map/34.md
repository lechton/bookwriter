# Q34: Accessing the DOM with Refs
* **Topic Tag**: `#dom_refs` | `❱ CORE`
* **Interview Question**: *How do you reach a DOM node from React to focus it, scroll it, or measure it?*
* **Core Truth**: Passing a `ref` object to a JSX element gives React a target handle to assign the underlying physical DOM node to `ref.current` after mounting, enabling imperative operations like focusing, scrolling, and geometry measurement.
* **The Friction**: When an editor clicks "Report Error", a modal opens, but the reader's keyboard focus remains lost on the background page, violating accessibility. Attempting to query `document.getElementById('correction-input')` fails if multiple article modals exist or if the component has not yet mounted to the DOM.
* **The Mechanism**: DOM refs (`const inputRef = useRef(null); <input ref={inputRef} />`). After React creates the DOM node and puts it on screen, it assigns the DOM node to `inputRef.current`; event handlers can then call `inputRef.current.focus()` or `inputRef.current.scrollIntoView()`.
* **Under the Hood**: The commit phase DOM attachment: React sets `ref.current` to the physical DOM node during the commit phase (before layout/paint) and resets it to `null` on unmount; reading or writing `ref.current` during render is strictly forbidden because the DOM does not exist yet.
* **The Code Experiment**:
  * *Naive*: Querying the DOM with `document.querySelector` or attempting to read `inputRef.current.focus()` directly during the render phase.
  * *React*: An `EditorialCorrectionModal` attaching `inputRef` to a textarea and calling `inputRef.current.focus()` inside a button click handler or mount effect.
* **Scope Boundary**: Focus on attaching refs to built-in DOM elements (`<input>`, `<div>`) and standard browser imperative methods (`focus`, `scrollIntoView`). Do not cover `useImperativeHandle` (Q51) or React 19 ref cleanup callbacks (Q86).
