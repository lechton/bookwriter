# Q110: Server Functions and 'use server': Creating Callable Backend Endpoints
* **Topic Tag**: #server_functions | ❱ CORE (Server)
* **Interview Question**: *What are Server Functions, and how does 'use server' create a callable endpoint?*
* **Core Truth**: The 'use server' directive marks asynchronous functions as Server Functions—callable RPC endpoints that can be invoked from client components, forms, and event handlers while executing securely on the server with full database and backend access.
* **The Friction**: An engineer building a "Subscribe to Newsletter" widget at The National Times manually creates a REST API route /api/subscribe, writes fetch('/api/subscribe', { method: 'POST', body: ... }), parses JSON, and handles HTTP status codes; they mistakenly believe 'use server' turns a component into a Server Component.
* **The Mechanism**: 'use server' directive: placed at the top of a module or at the beginning of an async function body; creates an encrypted RPC endpoint; can be passed directly to <form action={subscribe}> or invoked inside startTransition(async () => { await subscribe(email); }).
* **Under the Hood**: RPC transpilation: the bundler generates a unique action ID for the function, replaces client references with a stub that issues an HTTP POST request carrying the serialized arguments, and executes the server function in the server environment, returning the serialized result back to the client.
* **The Code Experiment**:
  * *Naive*: Manually configuring a custom Express or API route handler, serialization headers, and client fetch logic for a simple newsletter signup.
  * *React*: Declaring an async function subscribe(formData) with 'use server' and passing it directly to <form action={subscribe}> for seamless, end-to-end type-safe execution.
* **Scope Boundary**: Focus on what Server Functions are, how 'use server' creates callable RPC endpoints, and how they bridge client-to-server calls. Form action progressive enhancement details belong in Q112.
