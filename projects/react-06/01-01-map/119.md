# Q119: Static Prerendering: Generating HTML in Advance with prerender APIs
* **Topic Tag**: #static_prerender | ❱ CORE (Server)
* **Interview Question**: *What is static prerendering, and when is it the right choice?*
* **Core Truth**: Static prerendering executes React components at build time or deployment time to generate static HTML and RSC payloads for pages that do not depend on per-request parameters, eliminating server compute costs and enabling global CDN caching.
* **The Friction**: The "Ethics Policy" and "Masthead" pages at The National Times are rendered on-demand on every HTTP request by a dynamic Node.js server; during a viral traffic surge, these completely unchanging pages consume 40% of server CPU capacity, causing database connection timeouts.
* **The Mechanism**: React 19 prerender APIs: prerender (Web Streams) and prerenderToNodeStream (Node.js); they render the entire component tree to completion (waiting for all promises), returning { prelude } containing the complete static HTML stream.
* **Under the Hood**: Full tree resolution at build time: unlike streaming SSR which flushes fallbacks immediately, prerendering waits for all <Suspense> boundaries to resolve so that the generated HTML is complete, self-contained, and can be served statically by any CDN or object store without a running server.
* **The Code Experiment**:
  * *Naive*: Rendering static evergreen pages dynamically on every incoming request using server-side rendering, wasting server CPU.
  * *React*: Using React 19's prerender API at build time to produce static HTML files for editorial policy pages, serving them with instantaneous CDN delivery.
* **Scope Boundary**: Focus on static prerendering, when to choose it over dynamic SSR, and React 19's prerender APIs. Do not confuse with resuming (Q120).
