# Q133: Client References: What Client Components Look Like to the Server
* **Topic Tag**: #client_references | ❱❱ MORE (Server)
* **Interview Question**: *What is a Client Component from the server's perspective?*
* **Core Truth**: To the server runtime, a Client Component is not executable code but an opaque Client Reference—a lightweight metadata object containing a chunk ID and export name that instructs the client runtime to load and render the real component.
* **The Friction**: A developer at The National Times logs console.log(ArticleComments) inside a Server Component and is baffled to see { $$typeof: Symbol(react.client.reference), filepath: '...', name: 'ArticleComments' } instead of a function; attempting to call ArticleComments() as a regular function throws an immediate error.
* **The Mechanism**: Client Reference anatomy: { $$typeof: Symbol.for('react.client.reference'), $$async: false, id: 'chunk_12.js', name: 'ArticleComments' }; the server does not execute the component's body during the RSC pass; it simply serializes the reference and its props into the flight stream.
* **Under the Hood**: Flight emission of Client References: when React's server renderer encounters a Client Reference element, it writes an M (module) row to the stream defining the bundle URL, followed by an element row referencing that module ID and its serialized props; the browser downloads the chunk and executes the component.
* **The Code Experiment**:
  * *Naive*: Calling a Client Component as a normal JavaScript function const html = MyClientComp(props) inside a Server Component.
  * *React*: Rendering <MyClientComp {...props} /> as JSX, allowing the server to emit an opaque client reference with serialized props into the RSC payload.
* **Scope Boundary**: Focus on what Client References are from the server's perspective, their internal structure, and how the flight protocol represents them.
