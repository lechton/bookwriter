# Q51: Constrained Imperative APIs with useImperativeHandle
* **Topic Tag**: `#use_imperative_handle` | `❱❱ MORE`
* **Interview Question**: *How does a child expose a focused API to its parent through a ref?*
* **Core Truth**: `useImperativeHandle` customizes the ref instance exposed to a parent component, providing a controlled, limited imperative interface (like `focus()` or `scrollIntoView()`) rather than exposing raw internal DOM nodes.
* **The Friction**: A parent `ArticlePublishModal` needs to focus a custom `RichTextEditor` component. If the child exposes its raw `<div contenteditable>` DOM node via ref, the parent can unsafely mutate internal child styles, delete child DOM elements, or bypass component encapsulation.
* **The Mechanism**: The `useImperativeHandle` hook (`useImperativeHandle(ref, () => ({ focus() { inputRef.current.focus(); }, reset() { ... } }), [deps])`). The parent ref receives only the designated methods in the handle object.
* **Under the Hood**: Ref forwarding and handle interception: React attaches the returned object from the handle factory to the `ref.current` pointer during commit; this enforces encapsulation by acting as an intentional gateway barrier between parent and child DOM internals.
* **The Code Experiment**:
  * *Naive*: Exposing the entire underlying DOM node to the parent, inviting dangerous external DOM manipulations and leaking private child structure.
  * *React*: A `CommentInput` component using `useImperativeHandle` to expose only `{ focus, clear }` methods to the parent form, keeping internal DOM nodes private.
* **Scope Boundary**: Focus strictly on `useImperativeHandle` for deliberate API narrowing. Emphasize that imperative handles are an escape hatch and should not replace declarative props.
