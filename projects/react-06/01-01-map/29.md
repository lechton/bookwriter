# Q29: Consolidating State Logic with useReducer
* **Topic Tag**: `#use_reducer` | `❱ CORE`
* **Interview Question**: *When does state logic outgrow useState, and how does a reducer consolidate it?*
* **Core Truth**: `useReducer` consolidates complex, multi-branch state transitions into a single pure reducer function that maps previous state and dispatched actions to the next state, separating "what happened" (actions) from "how state changes".
* **The Friction**: An editorial live-blog component manages five interacting states: `status`, `draftText`, `pendingUploads`, `error`, and `tags`. Adding a "Publish" feature requires updating all five states across multiple handlers, leading to scattered, inconsistent state transitions and impossible UI bugs.
* **The Mechanism**: The `useReducer` hook (`const [state, dispatch] = useReducer(reducer, initialState)`). Event handlers dispatch plain action objects (`dispatch({ type: 'published', articleId })`), and a centralized pure `reducer(state, action)` computes the next state.
* **Under the Hood**: Reducer purity and predictable state transitions: reducers execute during the render phase and must be pure functions with zero side effects; decoupling action intent from state transformation enables straightforward unit testing of state logic outside the DOM.
* **The Code Experiment**:
  * *Naive*: A component with six separate `useState` setters called in various combinations across eight event handlers, prone to partial or conflicting updates.
  * *React*: A `LiveBlogEditor` using `useReducer` with a clean `switch (action.type)` statement handling `'typed'`, `'upload_started'`, `'publish_success'`, and `'error'` actions.
* **Scope Boundary**: Focus strictly on `useReducer`, action objects, and reducer functions within a single component. Do not combine with Context yet (reserved for Q31).
