# Q108: Server Components vs Client Components: The Complete Capability Trade-off
* **Topic Tag**: #server_components | ❱ CORE (Server)
* **Interview Question**: *What can a Server Component do that a Client Component cannot, and vice versa?*
* **Core Truth**: Server Components trade away browser interactivity (state, effects, event listeners, DOM APIs) for direct backend capabilities (database queries, secret keys, zero client bundle cost), while Client Components provide rich browser responsiveness at the cost of network transmission and client execution.
* **The Friction**: An engineer at The National Times tries to use useState and window.addEventListener('scroll', ...) inside an async Server Component, while another tries to query a private Redis cache inside a 'use client' component; both run into fundamental runtime errors because they misunderstand the strict capability divide.
* **The Mechanism**: Feature matrix: Server Components support async/await, direct filesystem/DB access, environment secrets, and zero client JS; Client Components support useState, useReducer, useEffect, browser event listeners (onClick), DOM APIs (window, document), and custom hooks.
* **Under the Hood**: Execution environments: Server Components execute strictly in the Node.js/Edge runtime and never have a browser Fiber representation or event loop; Client Components execute on the client (and optionally during SSR), requiring browser Fiber nodes and hydration hooks.
* **The Code Experiment**:
  * *Naive*: Trying to fetch data via useEffect and useState in a client component when the data is static, adding 50KB of libraries and loading spinners.
  * *React*: Structuring an article view with a Server Component parent handling secure data access (db.query) and a Client Component leaf handling user interactions (onClick).
* **Scope Boundary**: Focus on the comprehensive capability matrix and design trade-offs between Server and Client components. Do not detail Server Functions (Q110).
