# Q32: Context Optimization and Re-Render Blast Radius
* **Topic Tag**: `#context_optimization` | `❱ CORE`
* **Interview Question**: *How does context propagation cause re-renders, and how do you keep it fast?*
* **Core Truth**: Any change to a Context provider's `value` prop triggers a re-render of every component consuming that context; keeping context fast requires splitting independent contexts and preventing unmemoized object literals in the provider value.
* **The Friction**: In The National Times app, `AppContext` bundles `theme`, `currentUser`, and `activeNotification` into a single object literal: `value={{ theme, user, notification }}`. Every time a 5-second notification ticker updates, two hundred article cards across the entire page re-render, dropping framerates and lagging scrolling.
* **The Mechanism**: Context splitting and value memoization: split unrelated states into separate providers (`ThemeContext`, `UserContext`, `NotificationContext`), and memoize composite provider values with `useMemo` so consumers only re-render when their specific slice changes.
* **Under the Hood**: React's context propagation algorithm: React traverses the fiber tree from the provider, comparing `oldValue` and `newValue` via `Object.is`. When unequal, it unconditionally schedules a render on every consuming fiber, bypassing `React.memo` boundaries of intermediate components.
* **The Code Experiment**:
  * *Naive*: Creating a giant monolithic `AppContext` passing an unmemoized object literal `{ user, theme, alerts }`, causing the entire application to re-render on any alert tick.
  * *React*: Splitting into dedicated `ThemeContext` and `AlertsContext`, isolating notification re-renders strictly to the top banner component.
* **Scope Boundary**: Focus on the context re-render blast radius, `Object.is` value identity, and the context splitting pattern. Do not introduce selector libraries (use-context-selector) or external stores (Q54).
