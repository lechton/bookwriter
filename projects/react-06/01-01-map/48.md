# Q48: Separating Events from Effects with useEffectEvent
* **Topic Tag**: `#effect_events` | `❱❱ MORE`
* **Interview Question**: *How do you keep non-reactive values from re-running an effect?*
* **Core Truth**: `useEffectEvent` extracts non-reactive logic from an effect into an Effect Event function that always reads the latest props and state without being declared as a reactive dependency.
* **The Friction**: A live chat connection effect synchronizes to a `roomId`: `useEffect(() => { const conn = connect(roomId); conn.on('message', () => showNotification(theme)); }, [roomId, theme])`. The effect should only reconnect when `roomId` changes, but because it reads `theme`, toggling the dark mode theme disconnects and reconnects the entire chat room.
* **The Mechanism**: The `useEffectEvent` API (`const onMessage = useEffectEvent(() => showNotification(theme))`). Call `onMessage()` inside the effect; `onMessage` sees the latest `theme` without needing `theme` in the effect's dependency array `[roomId]`.
* **Under the Hood**: Breaking reactivity chains: Effect Events behave like event handlers—they are non-reactive closures that React updates in place on every render; they can only be called from inside effects and cannot be passed to child components.
* **The Code Experiment**:
  * *Naive*: Including `theme` in the connection effect's dependencies, causing chat reconnections on every theme switch.
  * *React*: Wrapping the message handler in `useEffectEvent`, allowing the chat room to maintain a stable connection across theme changes while still displaying notifications with the latest theme.
* **Scope Boundary**: Focus strictly on `useEffectEvent`, the distinction between reactive synchronization and non-reactive event logic, and its usage rules. Do not confuse with `useCallback` (Q59).
