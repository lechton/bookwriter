# Q175: Why Rules of React Bite Harder on the Server
* **Topic Tag**: #rules_of_react | ❱❱❱ ADVANCED (Server)
* **Interview Question**: *Why do the Rules of React bite harder on the server?*
* **Core Truth**: Impure components and global mutations that cause occasional UI glitches in the browser become catastrophic data corruption vulnerabilities on the server because concurrent requests and multi-pass resuming share the same long-lived Node.js process memory.
* **The Friction**: An editor at The National Times publishes an urgent embargoed article, but readers suddenly see draft content mixed into published feeds; developers trace the leak to a server component that mutated an imported module-level cache array during render, corrupting shared memory across hundreds of concurrent reader requests.
* **The Mechanism**: Server-side purity invariant: React Server Components must be mathematically pure functions of their props and request context; mutating module-level variables, modifying shared database singletons during render, or relying on non-deterministic globals (`Math.random()`, unseeded dates) violates the server contract because React may re-execute, interrupt, or resume components concurrently across different requests.
* **Under the Hood**: Process-level memory bleed: in the browser, each user owns an isolated JavaScript heap; on a server running Node.js or edge runtimes, thousands of concurrent requests share a single process heap; any in-render mutation of an external variable leaks state between requests, causing race conditions, cache poisoning, and security breaches under concurrent streaming SSR.
* **The Code Experiment**:
  * *Naive*: Mutating a module-scoped array `recentArticles.push(story)` inside a Server Component render function to track page views, bleeding reader data across separate HTTP requests.
  * *React*: Keeping component render passes strictly pure by computing derived data locally or delegating mutations exclusively to Server Functions and transactional databases outside the render pipeline.
* **Scope Boundary**: Do not re-cover client-side StrictMode or basic purity concepts (covered in Q13/Q26); focus strictly on the catastrophic consequences of server-side impurity: process memory sharing, race conditions during concurrent streaming, cache poisoning, and data leakage across distinct user requests.
