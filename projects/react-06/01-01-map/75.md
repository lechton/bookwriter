# Q75: Automatic Batching Across Async Boundaries
* **Topic Tag**: `#batching_internals` | `❱❱ MORE`
* **Interview Question**: *How does automatic batching coordinate state updates across promises and timeouts?*
* **Core Truth**: React 18 and 19 automatically batch all state updates occurring within event handlers, `setTimeout`, `fetch` promises, and native event listeners into a single coordinated re-render pass, eliminating unnecessary intermediate paints.
* **The Friction**: A newsroom developer updates `setIsLoading(false)` and `setArticles(data)` inside a `fetch().then()` callback. In React 17, this triggered two distinct re-renders: the first render showed empty data with no spinner (a flash of empty content), followed milliseconds later by the second render with data.
* **The Mechanism**: Automatic batching. Regardless of where `setState` is called (even inside asynchronous microtasks or macrotasks), React groups updates occurring in the same execution turn into a single trigger phase, scheduling one unified render pass.
* **Under the Hood**: The microtask batching queue: React schedules a microtask to flush updates; multiple `setState` calls append updates to the fiber's update queue during the tick, and when the microtask executes, React processes the entire queue in a single render pass.
* **The Code Experiment**:
  * *Naive*: Fearing multiple `setState` calls inside a `setTimeout` or `fetch` promise and attempting manual debounce or merging into single monster state objects.
  * *React*: Calling `setAuthor(data.author)` and `setBio(data.bio)` independently inside an async promise, verifying in the console that React executes only one combined render pass.
* **Scope Boundary**: Focus on automatic batching behavior across async boundaries, comparing React 17 vs React 18/19, and the microtask queue model. Do not repeat `flushSync` (covered in Q65).
