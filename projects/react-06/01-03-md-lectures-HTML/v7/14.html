Lecture 14: Component Memory with useState

Interview Question

CORE

Why do ordinary variables forget their values between renders, and how does useState remember?

Imagine this scenario:

  1. Leo is adding a Like button to the story cards of The National Times.
  2. He stores the count in a plain variable and adds one on every click.
  3. The console counts up, but the button keeps saying Like (0).
  4. Worse, pressing the card's Save button wipes the count back to zero.
  5. Readers think the site is broken, and every like they give is lost.
  6. React never looks at plain variables, and it runs the card's code again from the top.
  7. Today we learn where React keeps a component's memory, and how to change it.

⚡ IN THE WILD

Why does a plain variable fail as a like counter?

React does not watch variables, so changing one never updates the screen. When React does update the card, it runs the whole StoryCard function again. So let likes = 0 runs again too. The variable is invisible to React, and each new run erases it. A counter needs memory that React keeps and a way to tell React that the value changed.

What happens when a card changes

A React component is a JavaScript function that returns JSX. To show the card, React runs StoryCard from its first line to its return. Then it builds page elements from the JSX it got back. React never edits the page any other way. When the card must change, React runs StoryCard again and updates the page to match the new JSX. React developers call each of these runs a render, the word in this lesson's interview question. You will meet it in the docs and in interviews. This lesson says what physically happens instead: React runs the function. The steps between the run and the updated page are the subject of Lecture 15.

Each run is an ordinary function call. In JavaScript, every call of a function creates its local variables fresh and drops them when it returns. Nothing in a function body survives to the next call. Lecture 12 added a second fact: React may call a component any number of times. The body must not depend on how often it runs.

This leaves a puzzle. If the body forgets everything between calls, where can a like count live? And how does React learn that the count changed, when it does not watch variables? The seven principles below answer both questions. React keeps the value outside the function. It also hands you a function that changes the value and asks React to run the component again.

Principles of React: Component Memory with useState

An interviewer who asks this question wants two answers. Why does a plain variable forget, and where does useState keep the value instead? The first two principles explain the forgetting. The next three explain how useState remembers. The last two are decisions you make every time you write state.

PRINCIPLE 1

The screen keeps the value it got when the component ran

When React runs a component, the {count} in its JSX puts the current value of count on the screen, for example 0. A click handler then changes count to 1, but nothing puts the new value on the screen. The screen changes only when React runs the component again, because only then is {count} read again. Changing a variable does not make React run the component. Calling a setter does, as Principle 3 shows.

We should do this:
const [count, setCount] = useState(0);
setCount(count + 1);
React runs the component again
We should not do this:
let count = 0;
count = count + 1;
the screen still shows 0

Leo's first card shows this exact failure. Each click on Like ran likes = likes + 1, and the console proved that the number grew to 3. But nothing asked React to call StoryCard again, so the JSX was never rebuilt. The button kept the text from the first run, Like (0). In a spreadsheet, changing one cell updates every cell that uses it, and newcomers expect the same here. React waits to be asked. The setter in the first code pair is the way to ask, and Principle 3 shows it at work.

PRINCIPLE 2

Each run of a component starts its variables over

React runs a component more than once: every time the screen must change. Each time, it calls the component's function again from its first line. So let count = 0 runs again, and count is back to 0, whatever it held before. A plain variable inside a component never lasts from one run to the next.

We should do this:
function Counter() {
const [count, setCount] = useState(0);
keeps its value
return <p>{count}</p>;
}
We should not do this:
function Counter() {
let count = 0;
back to 0 on every run
return <p>{count}</p>;
}

The Save button in Leo's card did make React run the card again. Clicking it called setIsBookmarked, so React called StoryCard again from the first line. That call ran let likes = 0 once more, and the log line printed StoryCard runs, likes = 0. The three clicks had raised a variable that belonged to the previous call, and that call was over. The next click on Like started from the new zero and printed clicked, likes = 1. A plain variable fails twice, then: React never sees it change, and the next run erases it.

PRINCIPLE 3

useState gives a value that lasts and a function that changes it

state variable a value that keeps its value from one run of the component to the next

A value on the screen needs two things. It must keep its value from one run of the component to the next. And changing it must make React run the component again, so the screen shows the new value. A plain variable does neither. useState gives both, in one line: const [count, setCount] = useState(0).

  • count is the state variable, the current value: 0 on the first run. We read it, and we never assign to it.
  • setCount is the setter. setCount(1) stores 1 and makes React run the component again. In that run, count is 1.
We should do this:
const [count, setCount] = useState(0);
setCount(count + 1);
the screen shows 1
We should not do this:
const [count, setCount] = useState(0);
count = count + 1;
TypeError, the screen stays at 0

useState is a Hook, a function React provides for use at the top of a component. You import it from React with a named import: import { useState } from 'react' It returns an array of two items, and the square brackets in const [likes, setLikes] are array destructuring. They copy the first item into likes and the second into setLikes. The names are yours to choose. By convention the setter repeats the value's name after set.

Here is Leo's card with the like count moved into state. Only the top of the file changes. The JSX stays as it was, and the click handler now calls the setter function.

The second click prints StoryCard runs, likes = 2, and the button shows Like (2). Now Leo clicks Save. The console prints StoryCard runs, likes = 2, and the button still shows Like (2). The new run that once erased the count now keeps it.

likes is now a state variable, and it is declared with const. Writing likes = likes + 1 in the handler fails on the click. It throws TypeError: Assignment to constant variable. and the button stays at Like (0). One more surprise waits here. If you log likes right after calling setLikes, you still see the old number. The setter asks for the next run. It does not change the variable in the code that is running now. Lecture 16 explains that behavior.

A value that never appears on the screen and is used inside one handler can stay a plain variable. State is for values that must survive the next run and change what the reader sees.

PRINCIPLE 4

React keeps state outside the component and matches it by order

Each run calls the component's function from its first line, so useState(0) runs again on every run. We might expect it to set count back to 0, as let count = 0 does. It does not. React keeps the value itself, outside our function. On the first run, useState(0) stores 0. On every later run, React ignores the 0 and returns the stored value.

A component can call useState several times, once for each value. React never sees our names count or isOn. It matches each call to its stored value only by order: first call, second call. So the calls must come in the same order on every run, which means never inside an if.

We should do this:
const [count, setCount] = useState(0);
first call
const [isOn, setIsOn] = useState(false);
always the second call
We should not do this:
const [count, setCount] = useState(0);
if (count > 0) {
const [isOn, setIsOn] = useState(false);
React throws an error
}

This answers the puzzle from the start of the lesson. The function body forgets, so React remembers on its behalf. Leo's card makes two calls: the first for likes, the second for isBookmarked. React does not know these names. It knows only that the card made a first call and a second call.

To watch the two values, change the log line in the card to console.log('StoryCard runs:', likes, isBookmarked) The first run prints StoryCard runs: 0 false. A click on Like prints StoryCard runs: 1 false. A click on Save prints StoryCard runs: 1 true. Each call returned its own stored value, in the same order as before.

If a call sits inside an if, the order can change from one run to the next. In the second code pair, the first click makes count greater than zero. On the next run, the component makes two calls where it made one before. React logs a warning that begins "React has detected a change in the order of Hooks". Then it throws "Rendered more hooks than during the previous render." Lecture 37 gives the full rule for where Hooks may be called.

PRINCIPLE 5

Each copy of a component on the screen keeps its own state

component instance one copy of a component on the screen, with its own stored values

One component function can appear on the screen many times. A parent that returns <Counter /> twice shows two counters. Both copies run the same function, with the same useState(0) line, so we might expect them to share one count. They do not. React keeps a separate set of stored values for each copy on the screen, called a component instance. A click on the first counter changes only the first count, and React runs only that copy again.

We should do this:
function Counter() {
const [count, setCount] = useState(0);
one count per copy
const add = () => setCount(count + 1);
return <button onClick={add}>{count}</button>;
}
We should not do this:
let count = 0;
one variable shared by every copy
function Counter() {
const add = () => { count = count + 1; };
screen stays at 0
return <button onClick={add}>{count}</button>;
}

The front page shows two stories, so App returns two cards. Each <StoryCard /> element becomes its own component instance, with its own memory inside React.

Now try the workaround from the opening: move let likes = 0 above StoryCard, outside the function. The variable now survives each run, but it still asks React for nothing. Three clicks on the first card leave both buttons at Like (0). Clicking Save on the first card makes React run it, and it jumps to Like (3). Clicking Save on the second card makes React run that one, and it also shows Like (3). The two cards read one shared variable. When two cards really must show the same count, Lecture 23 moves the state up into their parent. Lecture 24 explains how React ties state to a component's position in the tree.

PRINCIPLE 6

Pass an expensive starting value as a function

initializer function a function passed to useState that React calls once to make the starting value

React uses the starting value of useState only on the first run and ignores it after that. In JavaScript, f() calls a function at once and passes its result, while f passes the function itself. Each run of the component executes the whole useState line. So useState(createItems()) calls createItems on every run, and React throws each later result away. When createItems does slow work, that work is wasted on every run. useState(createItems) passes the function itself, an initializer function, and React calls it only on the first run. A cheap starting value such as 0 needs no function.

It is best practice to do this:
const [items, setItems] = useState(createItems);
first run only
Instead of doing this:
const [items, setItems] = useState(createItems());
every run

Suppose Leo's card computes its starting likes from a long reading history. A log line shows how often that work runs.

Try it first with the parentheses, useState(createInitialLikes()) Two clicks on Like print createInitialLikes ran three times, once per run of StoryCard. The button shows Like (10), Like (11), then Like (12), so the extra results were thrown away. Without the parentheses, the button counts the same way, and the log appears only once. This is the difference between passing a function and calling it. A new Vite project turns on StrictMode. In development, it makes React call the initializer function twice on the first run and keep one result. Lecture 46 explains why.

PRINCIPLE 7

Call a setter only when the user clicks

We give a button a function to run on click with onClick={...}. When does that function run? We expect it to run when the user clicks. But onClick={setCount(count + 1)} runs the setter already when the component appears on the screen, not when the user clicks. The setter makes React draw the component again. Drawing it again runs the setter again, and so on, until React stops with an error. Instead, write onClick={() => setCount(count + 1)}. Now the setter runs only when the user clicks.

We should do this:
<button onClick={() => setCount(count + 1)}>Add</button>
runs on click
We should not do this:
<button onClick={setCount(count + 1)}>Add</button>
runs at once

Leo writes onClick={setLikes(likes + 1)} on the Like button. The card is about to appear, and setLikes(1) runs right away, before any click. React draws the card again, and setLikes(1) runs again. This repeats until React stops with "Too many re-renders. React limits the number of renders to prevent an infinite loop." The card never appears.

With onClick={() => setLikes(likes + 1)} the button gets the arrow function and keeps it. The setter inside runs only when the user clicks. Passing a named handler, onClick={handleLike}, works the same way. This is the rule from Lecture 13: give the button a function, do not call it.

Component Summary

App

The parent component shows two story cards and passes each a title. It keeps no state, because no value belongs to the whole page. It cannot read the likes inside its cards, and a like on one card does not make React run it again.

StoryCardtitle={title}

The state owner calls useState twice, for likes and isBookmarked, in the same order every time it runs. Each card on the screen keeps its own two values inside React. Its handlers change them only through setters, so every change asks React to run the card again.

The display button keeps no state. It shows Save or Saved from the isBookmarked prop and calls onToggle on a click. The card decides what the click means and stores the result.

A newcomer expects a variable to be enough: change it, and the card shows the change. The finished card shows what React needs instead. The value lives in React, one copy per card. Every change goes through a setter that asks React to run the card again.

Where you will meet this

  1. Like and reaction counters: each post in a feed keeps its own count and updates on every click.
  2. Bookmark and follow buttons: a toggle switches between two labels and remembers its choice.
  3. Open and closed panels: an accordion section or menu remembers whether it is open.
  4. Selected tabs: a tab bar remembers which tab is showing.

Glossary

  • Render: The developers' word for one run of a component function by React, which returns the JSX for the screen.
  • Hook: A React function whose name starts with use, called at the top of a component.
  • State Variable: A value React keeps for a component between runs; only its setter changes it.
  • Setter Function: The second item useState returns; it stores the next value and asks React to run the component again.
  • Array Destructuring: JavaScript syntax that copies the items of an array into separate names, as in const [likes, setLikes]
  • Component Instance: One copy of a component on the screen, with its own state inside React.
  • Initializer Function: A function passed to useState that React calls once, on the first run, to make the starting value.

Beyond the basics

  • Several setter calls in one handler lead to a single new run of the component (see react.dev/learn/queueing-a-series-of-state-updates).
  • A state variable keeps its value until the component runs again, even right after its setter is called (see react.dev/learn/state-as-a-snapshot).
  • Passing a function to the setter computes the next value from the previous one (see react.dev/reference/react/useState#updating-state-based-on-the-previous-state).
  • React does not run the component again when the next value is identical to the current one (see react.dev/reference/react/useState#caveats).
  • Hooks are called only at the top level of a component, never inside conditions or loops (see react.dev/reference/rules/rules-of-hooks).

Summary

Architectural Takeaways & Decision Matrix

❒ Choosing Where a Value Lives

➔ ALWAYS keep a value in state when it must survive the next run and change what the reader sees.

➔ IF a value is used only inside one handler and never shown THEN keep it a plain variable.

➔ NEVER move a variable above the component to keep it; every copy shares it, and React is never asked.

❒ Changing State Safely

➔ ALWAYS change state by calling its setter, never by assigning to the state variable.

➔ ALWAYS call useState at the top of the component, in the same order every time it runs.

➔ NEVER call a setter while React runs the component; pass a handler that the click calls later.

➔ IF the starting value is expensive to compute THEN pass the function itself, as in useState(createInitialLikes).
