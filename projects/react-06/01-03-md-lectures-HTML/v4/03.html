The Syntax Crash of Adjacent Unwrapped Tags

Think back to how you write markup in standard HTML. You open an HTML file, write an <h2> heading on one line, and write a <p> paragraph directly beneath it. You save the file, refresh the browser, and the browser displays both tags as sequential sibling elements. The browser parser processes the document top to bottom, appending each element into the DOM tree. When developers transition from plain HTML to React, they naturally assume they can paste that exact same HTML snippet directly into a component's return statement.

On The National Times, Elena Rostova sits down to build the lead editorial component for the morning investigative edition. The component needs to render an editorial headline and an accompanying summary. Elena opens EditorialLead.jsx and writes the component return statement with no enclosing parent tag:

return ( <h2 className="headline">...</h2> <p className="summary">...</p> );

Elena saves the file and switches to the browser.

Instead of rendering the story, the development environment immediately crashes. The terminal prints a fatal syntax error:

SyntaxError: Adjacent JSX elements must be wrapped in an enclosing tag. Did you want a JSX fragment <>...</>?

The dev server halts compilation, the browser displays a red error overlay, and the editorial desk is blocked from previewing the front page.

Why did the compiler crash on two valid HTML tags? To fix the error, Elena tries what most developers try: wrapping the two tags in a generic <div>. Wrapping the tags satisfies the compiler, the build succeeds, and the page renders. But when Elena inspects the layout in the browser, a new disaster appears: the newsroom's responsive two-column CSS grid is completely mangled.

The National Times layout establishes a multi-column CSS grid:

display: grid; grid-template-columns: 2fr 1fr; gap: 24px;

In CSS grid, layout rules apply strictly to direct children of the grid container. By inserting an arbitrary wrapper <div> solely to satisfy the compiler, Elena accidentally created an extra DOM element. The browser treats that wrapper <div> as a single grid item. Both the headline and summary are crushed into column one, while column two sits completely empty. This anti-pattern is known as div soup.

⚡ IN THE WILD

Why does an extra <div> break CSS flexbox and grid layouts?

In modern CSS, layout engines treat immediate direct children as distinct layout items. When a parent container declares a multi-column track: display: grid; grid-template-columns: 2fr 1fr;

The browser expects child one to populate column one and child two to populate column two. If a component introduces an unstyled wrapper <div>, the browser treats that wrapper node as child one. Both nested tags become trapped inside a single grid track, and column two is abandoned. React Fragments solve this platform dilemma by letting you group siblings in code without emitting physical wrapper nodes to the browser DOM.

What is JSX and Why Does It Require a Single Root?

To understand why adjacent tags trigger compiler errors, we must look past the visual appearance of JSX. JSX looks like HTML, but it is not HTML. It is an XML-like syntax extension for ECMAScript designed to describe user interfaces. The browser engine has no native understanding of JSX. When you load a React project, build tools like SWC, Babel, or esbuild transpile every JSX tag into standard JavaScript function calls.

Under the modern JSX transform, an element tag compiles directly into a function call:

<h2 className="headline">Title</h2>

The compiler transforms this markup into a JavaScript runtime invocation:

_jsx("h2", { className: "headline", children: "Title" })

When you look at JSX through the lens of compiled JavaScript, the reason for the single-root rule becomes self-evident. A React component is a standard JavaScript function. In JavaScript grammar, a return statement can only return a single value or expression.

In standard ECMAScript, writing return a, b; does not return both values; it uses the comma operator to evaluate a, discard it, and return only b. If a component returns two adjacent JSX tags without a container, the compiler would have to emit two separate function calls:

return _jsx("h2", ...), _jsx("p", ...);

That is illegal syntax for returning multiple objects. Just as a function cannot return two independent numbers without placing them inside an array or object literal, a component cannot return two JSX elements without an enclosing root.

To bridge this language constraint without forcing developers to pollute the DOM with meaningless <div> tags, React introduced React Fragments. A Fragment is a virtual container recognized by the React compiler. You write the explicit component tag:

<React.Fragment>...</React.Fragment>

or its clean modern shorthand:

<>...</>

Under the hood, the compiler transforms the Fragment into a single parent call:

_jsx(React.Fragment, { children: [...] })

When React evaluates the element tree and commits nodes to the browser, it unpacks the Fragment's children directly into the parent DOM element. In the physical browser DOM, zero wrapper nodes exist.

Principles of React: The Core Laws of JSX Grammar

In senior technical interviews, candidates are evaluated on whether they understand the underlying compiler mechanics of JSX or merely treat it as "HTML in JavaScript." To master JSX syntax and platform behavior, we formalize the four governing principles of JSX grammar:

PRINCIPLE 1

Return a Single Root Element from Every Component Function

single root container a single parent tag or Fragment that encloses all sibling markup in a component return
JavaScript expression a unit of code that resolves to a single discrete value in memory

We wrap all adjacent tags inside one parent element or a Fragment (single root container). Because a JavaScript function can only return one thing at a time, this turns our markup into a single value in memory (JavaScript expression).

We should do this:
return (
  <article className="lead">
    <h2>Breaking Story</h2>
  </article>
);
Returning a single root container
We should not do this:
return (
  <h2>Breaking Story</h2>
  <p>Story summary</p>
);
Returning adjacent uncontained tags

A React component function executes standard ECMAScript code. When the JSX compiler parses your component, each tag transforms into a call to _jsx(). If a function attempts to return two adjacent tags, the compiler encounters two disconnected function calls. Standard JavaScript syntax forbids returning multiple expressions from a single return statement. Enclosing siblings in a single parent tag produces a single root _jsx() call that passes child elements inside a unified children property.

PRINCIPLE 2

Group Sibling Elements with React Fragments to Prevent DOM Wrapper Pollution

React Fragment a virtual ghost container that groups child tags in code without rendering a physical DOM node
DOM wrapper pollution adding redundant div or span elements solely to satisfy compiler syntax rules

We group sibling tags together using empty tags <>...</> (React Fragment). This satisfies the single-root rule without adding useless extra <div> tags to our HTML (DOM wrapper pollution).

It is best practice to do this:
return (
  <>
    <h2>Headline</h2>
    <p>Summary text</p>
  </>
);
Grouping siblings with React Fragment
Instead of doing this:
return (
  <div>
    <h2>Headline</h2>
    <p>Summary text</p>
  </div>
);
Injecting redundant wrapper div

In web typography and editorial design, wrapping elements in redundant <div> containers breaks CSS inheritance and ruins layout calculations. In CSS grid and flexbox, direct children become grid items or flex items. When an extra <div> wraps your headline and summary, the browser treats the wrapper as a single layout item, destroying multi-column alignment. React Fragments solve this by acting as virtual containers in React's memory tree. When React paints the DOM, it unpacks the Fragment's contents directly into the parent DOM element with zero intermediate wrapper nodes.

PRINCIPLE 3

Terminate Every Tag with an Explicit Closure

explicit closure terminating a tag with a closing partner (</span>) or a trailing slash (/>)
XML compiler requirements strict parser rules that reject floating, unterminated markup tags

We close every single JSX tag with a closing tag or a trailing slash /> (explicit closure). JSX follows strict XML syntax rules (XML compiler requirements), so leaving tags unclosed causes an immediate syntax error.

We should do this:
<img src="/lead.jpg" alt="Story" />
<input type="text" />
<br />
Closing void tags with trailing slash
We should not do this:
<img src="/lead.jpg" alt="Story">
<input type="text">
<br>
Leaving void tags open and unclosed

In standard HTML5, void elements like <img>, <input>, <br>, and <hr> do not require closing tags. The browser's lenient HTML parser knows these tags cannot contain children and closes them automatically. JSX, however, follows strict XML parsing rules. The JSX compiler does not maintain a hardcoded dictionary of HTML void elements; it parses tags through a unified tokenization pipeline. If an opening tag lacks a closing slash, the compiler assumes every subsequent line is nested inside that tag until the file ends, triggering a catastrophic syntax crash:

SyntaxError: Expected corresponding JSX closing tag

PRINCIPLE 4

Align Attribute Names to DOM Properties and CamelCase

camelCase DOM property names standard property naming convention on browser element objects
reserved keywords protected JavaScript words like class and for that cannot be used as unquoted identifiers

We write attribute names using camelCase like className and htmlFor (camelCase DOM property names). This matches how the browser names element properties, and it avoids conflicts with protected JavaScript words (reserved keywords).

We should do this:
<label htmlFor="email">Email</label>
<section className="editorial-lead">
  <input id="email" />
</section>
Using camelCase DOM property names
We should not do this:
<label for="email">Email</label>
<section class="editorial-lead">
  <input id="email">
</section>
Using reserved HTML keywords

In native HTML markup, you write class="editorial-lead" and for="news-input". In JavaScript, however, class is a reserved keyword for declaring classes, and for is a reserved keyword for loops. Decades before React existed, the W3C DOM specification named these properties on living JavaScript element objects element.className and element.htmlFor. Because JSX compiles directly into JavaScript object arguments, React aligns its attribute names with living browser DOM properties.

Interview Tip

To impress the interviewer: When asked why React requires a single root element, junior developers often say "because React needs to compare virtual DOM trees." The authoritative, senior answer is rooted in ECMAScript expression grammar: JSX is syntactic sugar that compiles directly into standard JavaScript function calls (_jsx()). In JavaScript, a return statement can only return a single expression value. Returning adjacent JSX tags would require a function to evaluate to multiple comma-separated expressions, which is syntactically invalid. React Fragments solve this by wrapping children in a virtual container object in memory that React unpacks directly into the parent DOM node without appending wrapper elements to the DOM.

Component Summary

App

The root application component provides the top-level semantic page shell. It declares <main className="page-shell"> and establishes the masthead header. Why is this significant? It creates a predictable layout boundary that isolates the editorial column from outer document styling.

EditorialColumn

The layout container component defines the two-column CSS grid structure. It mounts the editorial lead component directly inside <section className="editorial-grid">. What is its primary role? It dictates the spatial arrangement of the page while delegating editorial markup entirely to child components.

EditorialLead

This is the presentation child component. It returns an editorial headline and summary grouped inside a React Fragment (<>...</>). What makes this essential? It satisfies the JavaScript single-root return invariant while emitting zero physical wrapper nodes into the DOM, keeping the headline and summary as direct children of the parent CSS grid.

In naive web development, pasting HTML snippets often results in "div soup", a deep nest of meaningless <div> elements inserted solely to satisfy framework rules. In React, using <>...</> allows EditorialLead to return multiple semantic siblings without compromising the parent's CSS grid rules. The browser receives a clean, flat DOM structure, input focus and CSS selectors remain predictable, and the layout engine calculates column widths with mathematical precision.

Where you will meet this

  1. CSS Grid and Flexbox Direct Child Layouts: Whenever child components must align with a parent container's grid tracks or flex distribution rules, inserting wrapper <div> nodes destroys layout calculations. Using React Fragments ensures that child tags remain immediate children of the parent layout.
  2. HTML Table Architectures (<tr> and <td>): The HTML specification strictly forbids placing a <div> directly inside a <table>, <tbody>, or <tr>. When building modular table components, child components must return groups of <td> cells or <tr> rows wrapped in React Fragments to avoid producing invalid HTML that crashes browser parsers.
  3. Semantic Definition Lists (<dl>, <dt>, <dd>): In accessible web documents, definition lists require paired <dt> terms and <dd> descriptions. Wrapping each term-definition pair in a React Fragment allows developers to build reusable terminology components while maintaining strict compliance with accessibility standards.

Glossary

  • JSX: A JavaScript syntax extension that allows developers to write XML-like tree structures that compile into nested _jsx() function calls.
  • Single-Root Rule: The language requirement that every component return must evaluate to a single JavaScript expression, requiring all sibling elements to be enclosed in a parent tag or Fragment.
  • React Fragment: A ghost container (<React.Fragment> or <>...</>) that groups multiple sibling tags in code without adding an extra wrapper node to the browser DOM tree.
  • Self-Closing Tag: An explicit closure syntax (<img />, <input />) required by the JSX compiler for all tags that do not contain child content, replacing lenient HTML void tags.
  • DOM Property Alignment: The practice of naming JSX attributes using camelCase properties from the browser DOM API (className, htmlFor) to prevent collisions with JavaScript reserved keywords.
  • Div Soup: An anti-pattern where redundant, unstyled <div> tags clutter the DOM tree, inflating memory usage and breaking CSS flexbox and grid calculations.
