Lecture 1: What is React and the Declarative Model

Interview Question

CORE

What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

Imagine this scenario:

  1. Clara logs into The National Times website to read the morning investigative edition.
  2. The newsroom header displays her name in multiple places across the top navigation bar.
  3. Your plain JavaScript script runs a function to update the user name across the screen.
  4. Why does the greeting say Clara while the subscriber badge still displays Guest?
  5. Readers see conflicting user information, suspect account errors, and lose trust in the platform.
  6. The manual script updated two DOM nodes but missed the third element entirely.
  7. Today, your UI will synchronize every element automatically from a single source of truth.

Manual DOM Hunting and State Drift

In plain browser JavaScript, you build dynamic pages by manipulating the Document Object Model. Developers commonly call this the DOM. The DOM is the browser's internal tree of live C++ objects representing every HTML element on screen. To change a word on the page, your script must locate the exact element first. You call browser methods like document.getElementById or document.querySelector. Once the element is found, you overwrite its properties directly in memory. You assign new text using textContent or replace markup using innerHTML.

In a growing application like The National Times, a single piece of reader data appears across multiple sections. The subscriber's name appears in the welcome banner, the profile menu, and the subscription badge. When the user logs in, your script must find and update every single copy by hand.

Look at the naive imperative update function below:

Naive DOM Update
1function updateHeaderUser(name) {
2 const greeting = document.getElementById('header-greeting');
3 greeting.textContent = 'Welcome, ' + name;
Updates header GREETING
4 const profile = document.getElementById('nav-profile-name');
5 profile.textContent = name;
Updates navigation PROFILE
6}

When updateHeaderUser runs, it updates the greeting and the profile pill. However, notice the omission: the script forgot to query #subscriber-badge. The greeting displays Clara, but the badge still displays Guest.

This synchronization failure is called state drift. State drift happens when two interface elements that should show the same data show different values. In imperative programming, you bear two burdens: deciding what changed, and finding every affected node. As your website grows to hundreds of elements, manual hunting inevitably misses nodes.

To avoid missing individual nodes, developers often attempt to replace the entire parent container at once. They wipe the whole container using innerHTML. While this guarantees all text gets updated, it introduces a severe hidden penalty:

Destructive Replacement
1function replaceHeader(name) {
2 const root = document.getElementById('header-root');
3 const markup = `<header><h1>National Times</h1><p>${name}</p></header>`;
4 root.innerHTML = markup;
WRONG: wipes container, losing input FOCUS
5}

⚡ IN THE WILD

Why does innerHTML destroy your active input focus? When you assign a new string to innerHTML, the browser parser does not compare text. It destroys every existing DOM node inside that container and creates brand-new nodes in memory. If a reader is typing in an input when innerHTML runs, that <input> element is deleted from existence. The browser recreates a new input that looks identical, but the active cursor focus is lost. Text selection vanishes, and running CSS transitions reset to their initial frames. React avoids this by comparing changes in memory and surgically updating only the text nodes that changed.

Interview Tip

To impress the interviewer: When asked why React was created, do not merely say "it makes building websites faster." Explain that React solves the fundamental problem of state drift inherent in imperative programming. In vanilla JavaScript, the developer must manually keep the DOM in sync with data across dozens of queries. React replaces this manual choreography with a declarative model. The user interface becomes a pure projection of application data: UI = f(data).

Components as Reusable Blueprints

To eliminate manual DOM hunting and state drift, modern web development relies on declarative UI. In a declarative system, you do not write step-by-step instructions telling the browser how to locate or mutate nodes. Instead, you declare what the user interface should look like for a given set of data. React takes on the mechanical burden of computing changes and physically updating the browser DOM.

The core building block of a React application is a component. A component is a self-contained, reusable JavaScript function. It accepts input data called props and returns a description of markup. In React, every component function name must start with a capital letter. Capitalization is a strict compiler rule. It tells React that <SiteHeader /> is a custom component, while <header> is a built-in browser DOM tag. Lowercase tags instruct React to produce standard HTML elements. Capitalized tags tell React to invoke your custom component function.

When React runs a component, it passes all declared attributes inside a single object called props. To read this incoming data, you have two options:

  • Option 1 (The foundational way): Receive the full props object as an argument, then access variables with dot notation (props.readerName).
  • Option 2 (The modern idiomatic way): Unpack variables directly in the parameter list using JavaScript object destructuring ({ readerName }).

First, look at Option 1 using the explicit props object:

Option 1: The Foundational Way (props.readerName)
1export default function ReaderGreeting(props) {
Receives props OBJECT
2 return <div className="greeting">Welcome back, {props.readerName}</div>;
3}

In Option 1, React passes the full props object into the function. This is the underlying mechanical reality of how React operates. Every attribute on the JSX tag becomes a property on this object. However, typing props. across larger components adds visual clutter.

Next, look at Option 2 using parameter destructuring:

Option 2: The Modern Idiomatic Way ({ readerName })
1export default function ReaderGreeting({ readerName }) {
Unpacks PROP
2 return <div className="greeting">Welcome back, {readerName}</div>;
3}

In Option 2, the JavaScript engine unpacks readerName directly at the function boundary. The component body stays clean. The function signature also explicitly documents which props the component consumes. This modern approach is the universal standard across production codebases.

Key Takeaway

In React, the user interface is a pure reflection of data. You describe what the screen looks like for a given state, and React handles the physical DOM updates.

Glossary

  • Declarative UI: An architectural paradigm where code describes what the user interface should look like for a given state, leaving the runtime engine to compute and execute the necessary physical DOM mutations.
  • Component: A self-contained, reusable JavaScript function that accepts input properties (props) and returns a tree of descriptors representing user interface markup.
  • Props: A plain JavaScript dictionary of arguments passed downward from a parent component to a child component, configuring its behavior and appearance.
  • State Drift: A synchronization bug where multiple UI elements that should reflect the exact same data display contradictory or outdated values due to missed imperative updates.
  • Virtual DOM / UI Descriptor Tree: A lightweight in-memory tree of JavaScript objects representing the desired user interface structure, used by React to compute minimal physical DOM diffs.

Beyond the basics

  • The UI descriptor tree and React elements: When JSX executes, it produces plain, immutable JavaScript objects called React elements via react/jsx-runtime. React creates this UI tree from your components and uses it to compute minimal physical DOM mutations rather than traversing browser nodes directly (see react.dev/learn/understanding-your-ui-as-a-tree).
  • Purity in component rendering: A React component function must be a pure calculation with respect to its inputs; given the same props, it must always return the same JSX without mutating preexisting variables or performing outside side effects during render (see react.dev/learn/keeping-components-pure).
  • Module dependency trees vs render trees: A React application possesses two distinct tree structures: the static module dependency tree evaluated by bundlers like Vite using import statements, and the dynamic runtime render tree constructed by React representing nested component instances on screen (see react.dev/learn/understanding-your-ui-as-a-tree).
  • Read-only immutable props: Props received by a child component are strictly read-only snapshots in JavaScript memory; components must never reassign or mutate properties like props.readerName directly, requiring state setters or parent callbacks to request updates (see react.dev/learn/passing-props-to-a-component).
  • Host elements vs custom component instances: Lowercase JSX tags (<header>, <span>, <div>) map directly to native HTML host elements in the browser DOM, whereas capitalized tags (<SiteHeader />, <ReaderGreeting />) signal custom JavaScript functions that React invokes in memory (see react.dev/learn/your-first-component).
  • Fragments and single-root returns: Every React component must return a single root JSX element because the markup compiles into a single JavaScript function call; when multiple adjacent sibling elements are needed without polluting the DOM with extra wrapper <div> nodes, developers wrap them in an empty fragment <>...</> (see react.dev/learn/writing-markup-with-jsx).

Lecture 2: Project Scaffolding: Build Tools vs Full-Stack Frameworks

Interview Question

CORE

How do you create and run a new React project, and how do you choose between a framework and a build tool?

Imagine this scenario:

  1. Leo joins The National Times engineering team to build an internal dashboard for investigative reporters.
  2. The project requires an interactive screen to coordinate article edits, review news feeds, and verify fact checks.
  3. Leo opens the official documentation, which recommends installing a full-stack framework with server rendering.
  4. Why does a private newsroom tool behind an authentication login require a Node.js server runtime and edge infrastructure?
  5. Setting up a full-stack server creates ongoing server maintenance, edge deployment friction, and unnecessary hosting costs.
  6. The team only needs a fast client-side application compiled to static HTML, JavaScript, and CSS.
  7. Today, you will master project scaffolding with Vite and learn exactly when to choose a standalone build tool over a full-stack framework.

Monolithic Bundlers and Cold-Start Latency

In modern web development, you cannot run raw React code directly inside a browser without a build step. Browsers understand standard HTML, CSS, and vanilla JavaScript, but they cannot natively parse JSX tags like <App /> or unbundled module imports across hundreds of files. A build tool is a development program that compiles JSX into standard JavaScript functions, resolves package dependencies, and prepares files for the browser. Historically, developers relied on monolithic bundlers like Webpack, packaged inside tools like Create React App.

In legacy setups like Create React App, starting the local development server required crawling and bundling every single JavaScript module in the project into memory before serving a single page. Look at the monolithic bundling bottleneck below:

When a project grew to hundreds of components, running npm start meant waiting 30 to 60 seconds just to view a single text change. Every file save forced the bundler to reconstruct large module graphs in memory. This latency created a frustrating development loop. Modern development solves this by decoupling local development from production bundling.

⚡ IN THE WILD

Why did Create React App freeze large codebases? Legacy tools like Create React App were built around Webpack at a time when web browsers could not load JavaScript modules natively. The bundler had to crawl every import statement, convert every file into CommonJS or bundle chunks, and assemble a massive in-memory bundle before the local HTTP server could send its first response. If your newsroom dashboard imported 500 files, Webpack compiled all 500 files before you could preview a single button. Modern tools like Vite eliminate this by relying on browser-native ES Modules: the server starts instantly in milliseconds, and the browser requests only the exact files currently visible on your screen.

Standalone Build Tools vs Full-Stack Frameworks

When starting a new React project today, your primary architectural decision is choosing between a standalone build tool and a full-stack framework. A standalone build tool, such as Vite, compiles client-side React code into static HTML, JavaScript, and CSS bundles that can be deployed to any static content delivery network (CDN) or cloud storage bucket. A full-stack framework, such as Next.js or Remix, combines React with a backend server runtime (such as Node.js or edge workers) to execute server rendering, server-side data fetching, and search engine optimization (SEO) pre-rendering.

If you are building a public-facing e-commerce storefront or a news publication where search engines must index HTML content immediately, a full-stack framework is essential. However, if you are building an internal newsroom dashboard behind a login wall, search engines never access the page. Choosing a full-stack framework for an internal tool adds unnecessary server hosting expenses, complex deployment pipelines, and server runtime maintenance.

To select the right toolchain, developers face a pedagogical crossroads between two architectural models:

  • Option 1 (The Standalone Client Model - Vite): Use Vite to build a fast Single-Page Application (SPA) executed entirely in the reader's browser, deployed as low-cost static files.
  • Option 2 (The Full-Stack Framework Model - Next.js / Remix): Use a full-stack framework to render React on a Node.js or edge server before sending HTML to the client.

For this internal tool, Vite provides maximum speed with minimum operational overhead.

Key Takeaway

Choose a standalone build tool (Vite) when building client-only single-page apps, dashboards, or tools behind authentication. Choose a full-stack framework (Next.js/Remix) when search engine optimization, initial page load speed for public visitors, or server-side data mutations are core product requirements.

Principles of React: The Core Laws of JSX Grammar

To prepare for any technical interview, we must separate theory from application and establish the nine fundamental laws governing the React compiler. In JSX, HTML markup strings do not exist. Every JSX component return statement must produce exactly one root element or container.

A React component is a standard JavaScript function. In JavaScript, a return statement can only return a single value or expression. When you write two adjacent tags at the root level, JavaScript cannot evaluate them as a single expression. Under the hood, JSX compiles into _jsx(type, props) function calls. Just as you cannot return two separate function calls without wrapping them in an array or container object, you cannot return adjacent JSX tags.

DOM Property Alignment for Reserved Words

HTML attribute names that collide with JavaScript reserved keywords must be written using their corresponding native browser DOM property names.

We should do this:

We should not do this:

To understand this rule in an interview, you must distinguish between three separate layers of the web platform:

  1. HTML Attributes (Markup Text): In raw HTML documents, class="card" and for="email" are static markup attributes parsed as plain text strings.
  2. JavaScript Reserved Keywords (Language Grammar): In ECMAScript, words like class (used to declare classes) and for (used to declare loops) are reserved keywords. In early JavaScript engines, using reserved words in dot-notation (element.class or element.for) triggered syntax errors.
  3. Browser DOM Properties (Living Objects): When a browser parses HTML, it instantiates living JavaScript objects in memory (such as HTMLDivElement or HTMLLabelElement). To avoid keyword collisions in JavaScript, the original 1998 W3C DOM specification explicitly mapped the class attribute to the property element.className, and the for attribute to element.htmlFor.

React does not invent className or htmlFor. When JSX compiles into _jsx("div", { className: "card" }) React updates the browser by setting the native DOM property directly (domNode.className = "card"). Because JSX operates at the level of JavaScript objects rather than raw HTML text strings, it aligns with native browser DOM properties.

PRINCIPLE 5

Standard camelCase for Compound Attributes

All multi-word JSX attribute names must be written in camelCase to align with their native browser DOM property interfaces.

We should do this:
<input tabIndex={0} readOnly={true} />
We should not do this:
<input tabindex="0" readonly>

This rule is not an arbitrary React design preference—it is the exact same DOM property alignment law established in Principle 4. In raw HTML documents, attribute parsing is case-insensitive, allowing developers to write <input tabindex="0" readonly autofocus> as uncapitalized text strings. However, in the browser's native JavaScript DOM API, the HTMLInputElement interface has defined these properties in camelCase since the initial W3C specifications: input.tabIndex, input.readOnly, and input.autoFocus. Because React maps JSX attributes directly to properties on native DOM nodes, it adheres strictly to the browser's established camelCase interface properties.

PRINCIPLE 6

Object Literals for Inline Styles

Inline element styles must be passed as JavaScript objects with camelCase CSS property keys, never as raw semicolon-delimited text strings.

We should do this:
<span style={{ color: 'red', fontWeight: 700 }}>
We should not do this:
<span style="color: red; font-weight: bold;">

Candidates frequently face two core interview questions regarding JSX inline styles:

  1. Why the double curly braces style={{ ... }}? There is no special "double-brace" syntax in React. The outer pair of braces {} is the JSX escape delimiter that switches the parser from markup mode into JavaScript expression mode. The inner pair { color: 'red', fontWeight: 700 } is simply a standard JavaScript object literal passed as the value.
  2. Why camelCase keys like fontWeight instead of font-weight? In the browser DOM, an element's inline styling is exposed as an instance of CSSStyleDeclaration (element.style). In JavaScript, writing element.style.font-weight is parsed as a subtraction expression (element.style.font minus the undefined variable weight), triggering a runtime syntax or reference error. The browser DOM API resolved this by mapping CSS hyphenated properties to camelCase JavaScript properties (element.style.fontWeight, element.style.marginTop). React's style prop passes this object directly to the browser's native element.style interface.
PRINCIPLE 7

JavaScript Expression Blocks for Markup Comments

Comments inside JSX markup must be written as JavaScript block comments enclosed within curly brace expression delimiters.

We should do this:
{/* breaking news alert */}
We should not do this:
<!-- breaking news alert -->

The JSX compiler operates as a two-state tokenizer: Markup Mode and JavaScript Mode. In Markup Mode, raw text characters are treated as literal text children, and encountering an opening angle bracket < immediately signals the parser to evaluate an element tag name. When encountering HTML comment syntax <!--, the tokenizer attempts to parse !-- as an HTML tag identifier, which is illegal syntax and halts compilation instantly. Curly braces {} serve as the explicit lexical boundary that switches the tokenizer into JavaScript Mode, where /* ... */ is safely evaluated as a standard ECMAScript block comment and erased during compilation.

PRINCIPLE 8

Hyphenated Preservation for W3C Standards

Accessibility attributes (aria-*) and custom dataset attributes (data-*) must strictly retain their hyphenated kebab-case syntax.

We should do this:
<input aria-label="Search" data-testid="search" />
We should not do this:
<input ariaLabel="Search" dataTestId="search" />

  1. Standard Props use DOM Property Assignment: For standard attributes, React assigns values directly to object properties on the living JavaScript node (domNode.className = props.className domNode.tabIndex = props.tabIndex).

Why can you not place an if statement inside JSX? When developers want conditional rendering, they often try writing {if (isLead) { ... }} inside their JSX. This triggers a fatal compiler error. Why? The Curly Brace Evaluation Window and Expressions

In JSX, curly braces {} act as an evaluation window. Placing curly braces inside text content (<h2>{authorName}</h2>) or inside an attribute (src={avatarUrl}) instructs the compiler to evaluate the enclosed JavaScript code at runtime. The evaluated value is then projected directly into the rendered output.

Inside the curly brace window, you can write any valid JavaScript expression:

  1. Variables: Evaluating local identifiers like {authorName}.
  2. Inline Arithmetic: Computing live numbers like {readMinutes * 60}.
  3. Template Literals: Assembling strings like {By ${authorName}}.
  4. Ternary Expressions: Evaluating conditional values like {isSenior ? 'Senior Editor' : 'Staff Writer'}

Default vs. Named Exports: The Module Boundary

Organizing components across dedicated files is the cornerstone of scalable React architecture. In modern JavaScript, the ES module system provides two mechanisms for sharing code across files: default exports and named exports.

The two export mechanisms serve distinct architectural roles:

  1. Default Exports (export default): Each file can have at most one default export. It represents the primary component that defines the file (such as export default function ArticleCard). Consumers import it without curly braces: import ArticleCard from './ArticleCard.jsx'
  2. Named Exports (export function): A file can have multiple named exports. They represent secondary helper functions, constants, or companion components (such as export function formatRole). Consumers import them using curly braces: import { formatRole } from './ArticleCard.jsx'

When organizing component files, you face an architectural crossroad between two team conventions:

  • Option 1 (The foundational way): Use named exports for everything, forcing curly braces on every import across the codebase.
  • Option 2 (The modern idiomatic way): Use a default export for the primary component, and named exports for companion helpers and formatters.

In JavaScript, false, null, and undefined carry no visual meaning; they represent absence. React purposely ignores them so you can write {condition && <Element />} without rendering unwanted strings. If React automatically hid 0, displaying numeric counters would be impossible. React treats numbers as text nodes. Therefore, you must ensure the left-hand side of an && expression is always a genuine boolean.

Declarative Control Flow and the Branching Matrix

Declarative conditional rendering means your component describes what the UI should look like for every possible data state. When state changes, React recalculates the returned JSX tree and updates the DOM to match.

React developers rely on three standard branching patterns:

  1. Early Return with null: If essential data is missing or loading, return early before executing the main JSX: if (!article) return null;
  2. Inline Ternary Operator (? :): For binary branching between two mutually exclusive UI elements: {isSubscriber ? <FullArticle /> : <PaywallNotice />}
  3. Logical AND Operator (&&): For conditionally rendering an element when a condition is true, and rendering nothing when false: {isBreaking && <BreakingBadge />}

When branching markup, you face an architectural crossroad between these three patterns:

  • Option 1 (The Early Return): Exit the function before the main return statement when a precondition is not met.
  • Option 2 (The Inline Ternary): Switch between two distinct UI branches inside the JSX tree using condition ? <A /> : <B />.

The Scrambled Input Trap and Index Diffing

In web applications, data almost always arrives as collections of records: lists of news articles, subscriber profiles, or live market tickers. In vanilla JavaScript, developers wrote imperative loops to create DOM nodes, append them to parent containers, and manually remove outdated elements. In React, rendering lists is completely declarative: you transform an array of raw JavaScript objects into an array of JSX elements using the standard array .map() method. React takes this array of element descriptors and reconciles it against the real DOM.

When developers first render lists in React, they encounter a compiler warning demanding a "key" prop. To silence the warning, many developers hastily write key={index}. This creates one of the most notorious and insidious bugs in React.

Because the keys are indices, React compares the old tree's item at key="0" with the new tree's item at key="0". React concludes that item 0 did not move; it simply changed its headline text! Therefore, React updates the text node inside the existing DOM node, but leaves the native <input> completely untouched. As a result, the note you typed for the old story is now visibly attached to the new breaking story!

⚡ IN THE WILD

Why does prepending an item scramble form inputs? When you prepend an item to an array using key={index}, the new item receives key={0}, the previous first item becomes key={1}, and so forth. React's reconciler assumes the element with key={0} is the exact same component instance as before, just with updated props. It reuses the physical DOM node in place. While React updates the text props it controls, the browser's native <input> state, text cursor, and focus live inside the unmanaged DOM node. Because the DOM node was recycled for the new record, your typed text remains stuck in the first input box while the headline above it changes completely!

The Three Trees Governing Your Application

To build scalable applications, an engineer must distinguish between the three different trees that exist at different stages of your application's lifecycle: the Module Dependency Tree, the Component Tree, and the Render Tree.

The Module Dependency Tree represents the static relationship between files on disk. Every JavaScript module is a node, and every import statement is a directed edge. Bundlers like Vite and Rollup inspect this tree to determine which code to package, which unused exports to drop (tree shaking), and where to split bundles. This tree is evaluated at build time.

The Component Tree describes the logical hierarchy of your components based on JSX nesting: <NewsLayout> contains <HeaderBar> and <ArticleGrid>. This tree defines how props flow downward from ancestors to descendants. The Render Tree is the live, runtime hierarchy of React element objects evaluated during the current render pass. The render tree contains only the components that are currently rendered on screen (ignoring unrendered conditional branches) along with native host elements like <div> and <header>.

The Purity Contract and the StrictMode Double-Render

In computer science, a pure function is a mathematical formula: given the same inputs, it always returns the exact same result, and it changes nothing outside of its own function body. React is designed entirely around this concept. Every React component you write must be a pure function. When React calls your component, the component should only calculate and return JSX describing what the screen should look like. It must never reach outside its own boundaries to mutate pre-existing variables, modify incoming props, or trigger side effects during the render pass.

When developers violate the purity contract by mutating external variables, silent bugs explode across their application.

Look at the naive attempt below, where an engineer increments a global counter inside the component body:

In development, React wraps your application in <StrictMode>. One of StrictMode's primary duties is to verify component purity by calling every component function twice! For a pure component, running the function twice produces the exact same JSX with zero side effects. But for our impure StoryByline, running the function twice increments guestViewCount from 0 to 1, and then immediately from 1 to 2. The counter doubles on every single page load! In production, concurrent rendering, server component streaming, and background pre-rendering can pause, abort, and restart rendering at any moment. If your component is not pure, these pauses and restarts corrupt application data.

⚡ IN THE WILD

Why does StrictMode render your component twice? When developers first see console.log() or counters firing twice in development, they often assume React has a bug. In reality, React's <StrictMode> intentionally calls your component functions, initializers, and reducers twice in development. Why? Because React is testing your code for purity! If a component is pure, calling it twice produces no observable side effects; the output is identical. But if a component mutates an external variable or modifies a prop array, the second run produces different results, exposing the bug immediately in development before it causes corrupted state in production.

Side Effects, Idempotence, and Local Mutation

To maintain purity, developers must understand what is forbidden and what is permitted. Mutating pre-existing variables, modifying incoming props, or directly changing the DOM during render is strictly forbidden. However, local mutation is 100% legal: you can freely create new variables, arrays, and objects inside the component function and mutate them as much as you want before returning JSX.

When preparing or sorting data for display, developers face an architectural crossroad between in-place array mutation and pure array derivation:

  • Option 1 (The foundational trap / mutation): Mutate the incoming prop array in place using mutating methods like tags.push('Live') or tags.sort().
  • Option 2 (The modern idiomatic way / pure derivation): Create a new array or shallow copy using the spread operator [...tags, 'Live'] or non-mutating methods before rendering.
