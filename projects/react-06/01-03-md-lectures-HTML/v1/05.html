Lecture 5: JavaScript Expressions in JSX with Curly Braces

Interview Question

CORE

How do you use JavaScript expressions inside JSX with curly braces, what grammar constraints separate expressions from statements, and how do attributes differentiate static strings from dynamic bindings?

Imagine this scenario:

  1. Clara builds a journalist profile card for The National Times investigative team.
  2. She declares variables in her component for the reporter name, read time, and avatar path.
  3. Clara writes the variable names directly between tags and inside attribute quotes.
  4. Why does the browser print the word headline and display a broken image icon?
  5. Readers see raw variable names instead of author names, and profile pictures fail to load.
  6. Static JSX treated the variable names as plain string characters.
  7. Today, you will master the JSX curly brace window to evaluate live JavaScript expressions.

Literal Text and Broken Image Paths

In standard HTML, text written between opening and closing tags is always treated as a static string. If you write <h2>authorName</h2>, the browser displays the literal letters a-u-t-h-o-r-N-a-m-e. Similarly, if you write <img src="avatarUrl" />, the browser attempts to fetch a file named literally avatarUrl from the web server. HTML has no concept of JavaScript memory or local variables.

When a developer declares variables inside a component and writes their identifiers directly into JSX markup, the output remains static.

When this component runs, the browser displays the literal word "authorName". The image fails to load because the browser requests a file named literally avatarUrl instead of reading the memory address stored in the variable.

The JSX compiler follows a strict parsing boundary. When text is enclosed in quotes ("avatarUrl") or placed between tags (<h2>authorName</h2>), the compiler emits literal strings: _jsx("img", { src: "avatarUrl" }). To instruct the compiler to step out of static markup and read JavaScript memory, you must open an evaluation window using curly braces: {}.

Interview Tip

To impress the interviewer: When asked how curly braces work in JSX, do not say "they let you put JavaScript inside HTML." State that JSX is a strict syntax extension that compiles into function calls (_jsx()). Curly braces serve as the lexical escape boundary that switches the tokenizer from Markup Mode into JavaScript Evaluation Mode. The enclosed JavaScript expression is evaluated during render, and its resolved value is passed directly as an argument to the element's descriptor.

⚡ IN THE WILD

Why can you not place an if statement inside JSX? When developers need conditional rendering, their initial instinct is often writing {if (isSenior) { ... }} inside their JSX markup. This triggers a fatal compiler error. Why? Because curly braces accept JavaScript expressions, but strictly reject JavaScript statements. An expression produces a concrete value that can be passed as an argument to a function (_jsx("span", { children: value })). A variable, arithmetic calculation, or ternary operation (isSenior ? 'Senior' : 'Staff') all evaluate to a single value. An if statement or a for loop produces no value; it is a control-flow statement. You cannot pass a statement as a function argument in JavaScript. To branch inside JSX, you must use expressions that resolve to values.

Principles of React: The Core Laws of JSX Expressions

To prepare for any technical interview, we must separate theory from application and establish the fundamental laws governing how the React compiler parses, evaluates, and projects JavaScript code inside JSX. In React, markup is not a separate templating language—it is pure JavaScript execution. We formalize these rules into six standalone principles.

PRINCIPLE 1

Wrap Dynamic JavaScript in Curly Braces

curly braces syntax boundary that switches the compiler from HTML parsing to executing live JavaScript

You must wrap JavaScript expressions in curly braces ({}) to switch the compiler from static markup mode to live JavaScript evaluation.

We should do this:
<h2>{authorName}</h2>
We should not do this:
<h2>authorName</h2>

In senior technical interviews, explaining JSX curly braces requires understanding the compiler's two-state tokenizer mechanics:

  1. Markup Mode (Static String Parsing): By default, the JSX parser operates in markup mode. Any characters appearing between an opening <tag> and closing </tag> are treated as literal text content. If you write <h2>authorName</h2>, the parser passes the literal string "authorName" into the AST, producing _jsx("h2", { children: "authorName" }). The browser paints the variable name rather than the journalist's actual identity.
  2. JavaScript Evaluation Mode (Dynamic Lexical Window): An opening curly brace { serves as a lexical escape delimiter. It immediately halts markup tokenization and switches the compiler into ECMAScript evaluation mode until a matching closing brace } is encountered. The compiler looks up the identifier authorName in the component's active lexical scope and emits _jsx("h2", { children: authorName }). At runtime, React reads the live variable value and renders the resolved text node.

WRONG: Raw variable identifier treated as literal text

3<h2>{authorName}</h2>
RIGHT: Curly braces evaluate variable from component scope
PRINCIPLE 2

Pass Only Value-Producing Expressions Inside Curly Braces

JavaScript expressions that resolve to a value code that calculates a result you can pass or store (like a ternary or addition)
control-flow statements code that guides execution flow (like if, for, or while) without producing any value

You must place exclusively JavaScript expressions that resolve to a value inside curly braces, strictly avoiding control-flow statements.

We should do this:
{isSenior ? 'Senior' : 'Staff'}
We should not do this:
{if (isSenior) { 'Senior' }}

To understand why statements are forbidden inside JSX, interviewers evaluate the distinction between JavaScript grammar categories and compiler call-site arguments:

  1. Expressions (Value-Producing Operands): An expression is any syntactic unit that evaluates to a concrete value. Arithmetic operations (2 + 2), variable identifiers (authorName), property lookups (user.role), function calls (formatDate()), and ternary conditionals (isSenior ? "Senior" : "Staff") all produce a single value. Because JSX compiles directly into function calls (_jsx(type, props)), every child is passed as an argument. Any expression is valid because arguments must evaluate to values.
  2. Statements (Non-Value Control Flow): A statement is an imperative instruction that performs an action but evaluates to no value. Keywords like if, else, for, while, switch, and const direct program control flow. In ECMAScript grammar, statements cannot be placed where expressions or arguments are expected. Writing _jsx("span", { children: if (isSenior) { "Senior" } }) is a fatal JavaScript syntax error. To branch within JSX, developers must use value-producing ternary expressions (? :) or logical operators (&&).
Principle 2: Expressions vs Statements
1<div>{if (isSenior) { 'Senior Editor' }}</div>
WRONG: Control-flow statements produce no value and halt compilation
2
3<div>{isSenior ? 'Senior Editor' : 'Staff Writer'}</div>
RIGHT: Ternary expression evaluates to a single string value
PRINCIPLE 3

Never Wrap Curly Braces in Quotes for Attributes

You must delimit JSX attributes either with quotes for static strings or with bare curly braces for dynamic expressions, never wrapping curly braces inside quotes (which passes the literal text string "{avatarPath}").

We should do this:
<img src={avatarPath} />
We should not do this:
<img src="{avatarPath}" />

Senior technical evaluations focus on attribute delimitation disjunction and runtime URL resolution:

  1. The Static String Delimiter ("..."): Wrapping an attribute in quotation marks explicitly informs the compiler that the content is a static string literal. Emitting <img src="avatar.jpg" /> compiles to _jsx("img", { src: "avatar.jpg" }). The browser resolves this exact string path against the host origin.
  2. The Dynamic Expression Delimiter ({...}): Using bare curly braces switches the attribute into expression evaluation mode. Emitting <img src={avatarPath} /> compiles to _jsx("img", { src: avatarPath }). At runtime, JavaScript resolves the variable avatarPath in memory and passes its resolved string value to the DOM node's src property.
  3. The Quoted-Brace Disjunction Trap ("{...}"): When you combine quotation marks and curly braces (src="{avatarPath}"), the outer quotes take absolute precedence. The parser stays in static string mode and treats {avatarPath} as literal text characters. At runtime, the browser attempts an HTTP request to GET /"{avatarPath}", producing a broken image icon and a 404 server error because no file named "{avatarPath}" exists on disk.
Principle 3: Attribute Delimitation Disjunction
1<img src="{avatarPath}" alt="{authorName}" />
WRONG: Wrapping curlies in quotes passes literal string
2
3<img src={avatarPath} alt={authorName} />
RIGHT: Bare curly braces evaluate variables as attribute values
PRINCIPLE 4

Use Double Curly Braces to Pass Inline Objects

two pairs of curly braces outer pair evaluates JavaScript; inner pair builds the object literal

You must write two pairs of curly braces when passing an inline object to a prop—the outer pair opens the evaluation window, while the inner pair constructs the object literal.

We should do this:
<b style={{ color: 'teal' }}>LIVE</b>
We should not do this:
<b style={ color: 'teal' }>LIVE</b>

In technical interviews, this pattern is used to test whether a candidate understands the boundary between JSX grammar and standard ECMAScript object literal syntax:

  1. The Outer Curly Braces (JSX Expression Boundary): The outer pair of curly braces style={ ... } belongs to the JSX compiler. It serves the exact same role as in any other dynamic prop: it exits HTML attribute parsing and signals that the prop value must be evaluated as live JavaScript.
  2. The Inner Curly Braces (ECMAScript Object Literal): The inner pair of braces { color: "#0e7490", fontWeight: 700 } belongs to native JavaScript. It is a standard ECMAScript object literal containing key-value pairs representing inline CSS properties.
  3. The Single-Brace Grammar Failure: If you write <span style={ color: "#0e7490" }>, the JavaScript engine inside the JSX expression window attempts to parse color: "#0e7490" as an illegal block statement containing a labeled statement rather than an object expression, resulting in an immediate compilation syntax error. To pass an object without double braces, you must assign the object literal to an intermediate variable first (const styles = { color: "#0e7490" }) and pass it as style={styles}.

PRINCIPLE 5

Convert Falsy Conditions to Explicit Booleans to Prevent Rogue Zeros

You must use explicit boolean comparisons (unreadCount > 0) when conditionally rendering with && (because the number 0 renders visibly as text, while booleans render nothing on the page).

It is best practice to do this:
{count > 0 && <span>{count}</span>}
Instead of doing this:
{count && <span>{count}</span>}

In senior React interviews, the rogue zero defect tests deep knowledge of JavaScript short-circuit evaluation combined with React's virtual DOM rendering rules:

  1. React's Zero-Node Render Rules for Booleans: To facilitate clean conditional markup, React's reconciler explicitly treats false, true, null, and undefined as zero-node render instructions. When an expression evaluates to false, React paints nothing to the DOM.
  2. ECMAScript Short-Circuit Return Value: The JavaScript logical AND operator (&&) does not return a boolean true or false. According to ECMAScript specifications, expr1 && expr2 returns the value of expr1 if expr1 can be converted to false; otherwise, it returns expr2. If unreadCount is 0, JavaScript evaluates 0 && <Badge /> and directly returns the number 0.
  3. The Numeric Text Node Leak: Unlike booleans, React treats numbers as meaningful content that users want to see on screen (such as item counts or prices). When React receives the returned number 0, it creates a physical DOM text node containing "0". The user sees a rogue zero floating in the header. Converting the condition to an explicit comparison (unreadCount > 0) forces the left-hand operand to evaluate to boolean false, which React safely renders as nothing.
Principle 5: Falsy Numeric Leak vs Explicit Comparison
1<div>{unreadCount && <span className="badge">{unreadCount}</span>}</div>
WRONG: Renders rogue "0" when unreadCount is 0
2
3<div>{unreadCount > 0 && <span className="badge">{unreadCount}</span>}</div>
RIGHT: Explicit boolean comparison renders nothing when false
PRINCIPLE 6

Evaluate Expressions Immediately for Text, but Pass Callbacks for Events

You must evaluate text expressions immediately during component rendering, while passing deferred function references for event handlers.

We should do this:
<p>{readMinutes * 60}</p>
We should not do this:
<p>{() => readMinutes * 60}</p>

In technical interviews, this distinction separates render-phase computations from interactive lifecycle handlers:

  1. Synchronous Render-Phase Evaluation (Text and Data): When React executes a component, every expression placed in child curly braces is evaluated immediately on the call stack. Inline arithmetic (readMinutes * 60), string concatenations, and formatting utilities must run synchronously so their resolved primitive values can populate the virtual DOM element descriptors before commit to the browser DOM. Wrapping text calculations in a function ({() => readMinutes * 60}) produces a function reference; React ignores functions as child nodes, leaving the element blank.
  2. Deferred Callback References (Interactive Events): By contrast, event listener props like onClick and onChange expect a function reference that the browser can invoke later when a user interaction occurs. If a developer accidentally executes the function immediately during render (onClick={handleClick()}), the handler fires immediately upon component mount, and its return value (often undefined) is assigned to the click prop. Passing an uninvoked callback (onClick={handleClick}) ensures the operation is deferred until the user clicks the element.
Principle 6: Synchronous Render vs Deferred Callback
1<p>{() => readMinutes * 60}</p>
WRONG: Wrapping text in arrow function produces unrendered function object
2
3<p>{readMinutes * 60}</p>
RIGHT: Inline arithmetic evaluates synchronously during render phase

Where you will meet this

  1. Journalist Profile Cards: Projecting dynamic author names, photo URLs, and editorial badges from component state or data props.

Glossary

  • JSX Evaluation Window: The syntax construct {} that temporarily steps out of static JSX markup mode to evaluate an inline JavaScript expression.
  • JavaScript Expression: Any valid unit of JavaScript code that resolves to a single value, such as a variable, arithmetic calculation, or ternary operation.
  • Control-Flow Statement: A unit of JavaScript code that executes an action but produces no value (if, for, while), strictly forbidden inside JSX curlies.
  • Pure Attribute Delimitation: The language rule requiring JSX attributes to use either quotes for static strings or curly braces for dynamic expressions.
  • Object Literal Pass-Through: The syntax pattern where an outer curly brace pair opens the JSX window and an inner pair defines a JavaScript object (style={{ ... }}).
  • Falsy Numeric Leak: The runtime defect where the falsy number 0 in a logical AND expression (0 && <Badge />) evaluates to 0 and renders as visible text on the page.

Beyond the basics

  • JSX curly braces compiler output: The expression {readMinutes * 60} compiles directly to the function argument _jsx("p", { children: [readMinutes * 60, " seconds read"] }) (see react.dev/learn/javascript-in-jsx-with-curly-braces).
  • Expressions vs statements in language specifications: In the ECMAScript specification, expressions evaluate to a value, while statements control execution flow; JSX child positions only accept expressions because function calls require argument values (see react.dev/learn/javascript-in-jsx-with-curly-braces).
  • Objects as JSX children: React cannot render raw JavaScript objects directly inside text curlies ({userObject}); attempting to do so throws a runtime error, requiring you to access primitive properties like {userObject.name} (see react.dev/learn/javascript-in-jsx-with-curly-braces).
  • Double curlies for inline style objects: When applying inline styles in JSX, you write style={{ color: 'red' }}; the outer braces open the evaluation window, and the inner braces declare a JavaScript object literal (see react.dev/learn/javascript-in-jsx-with-curly-braces).
  • Boolean and nullish rendering: React treats true, false, null, and undefined as empty values inside curly braces, rendering nothing to the DOM, which enables conditional rendering shortcuts like {isPublished && <Badge />} (see react.dev/learn/conditional-rendering).

❒ Evaluation Windows & Text

➔ ALWAYS wrap JavaScript variables in curly braces ({authorName}) when rendering dynamic text inside JSX elements.
