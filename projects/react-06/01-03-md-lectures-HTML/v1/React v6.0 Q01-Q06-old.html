Lecture 1: What is React and the Declarative Model

Interview Question

CORE

What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

Imagine this scenario:

  1. Clara logs into The National Times website to read the morning investigative edition.
  2. The newsroom header displays her name in multiple places across the top navigation bar.
  3. Your plain JavaScript script runs a function to update the user name across the screen.
  4. Why does the greeting say Clara while the subscriber badge still displays Guest?
  5. Readers see conflicting user information, suspect account errors, and lose trust in the platform.
  6. The manual script updated two DOM nodes but missed the third element entirely.
  7. Today, your UI will synchronize every element automatically from a single source of truth.

Manual DOM Hunting and State Drift

In plain browser JavaScript, you build dynamic pages by manipulating the Document Object Model. Developers commonly call this the DOM. The DOM is the browser's internal tree of live C++ objects representing every HTML element on screen. To change a word on the page, your script must locate the exact element first. You call browser methods like document.getElementById or document.querySelector. Once the element is found, you overwrite its properties directly in memory. You assign new text using textContent or replace markup using innerHTML.

In a growing application like The National Times, a single piece of reader data appears across multiple sections. The subscriber's name appears in the welcome banner, the profile menu, and the subscription badge. When the user logs in, your script must find and update every single copy by hand.

When updateHeaderUser runs, it updates the greeting and the profile pill. However, notice the omission: the script forgot to query #subscriber-badge. The greeting displays Clara, but the badge still displays Guest.

This synchronization failure is called state drift. State drift happens when two interface elements that should show the same data show different values. In imperative programming, you bear two burdens: deciding what changed, and finding every affected node. As your website grows to hundreds of elements, manual hunting inevitably misses nodes.

To avoid missing individual nodes, developers often attempt to replace the entire parent container at once. They wipe the whole container using innerHTML. While this guarantees all text gets updated, it introduces a severe hidden penalty:

⚡ IN THE WILD

Why does innerHTML destroy your active input focus? When you assign a new string to innerHTML, the browser parser does not compare text. It destroys every existing DOM node inside that container and creates brand-new nodes in memory. If a reader is typing in an input when innerHTML runs, that <input> element is deleted from existence. The browser recreates a new input that looks identical, but the active cursor focus is lost. Text selection vanishes, and running CSS transitions reset to their initial frames. React avoids this by comparing changes in memory and surgically updating only the text nodes that changed.

In vanilla JavaScript, the developer must manually keep the DOM in sync with data across dozens of queries. React replaces this manual choreography with a declarative model. Principles of React: The Core Laws of the Declarative Model

To prepare for any technical interview, we must separate theory from application and establish the five fundamental laws governing how React replaces imperative DOM mutation with a declarative, component-driven architecture. In vanilla JavaScript, the developer manually orchestrates browser DOM updates. In React, the user interface is a pure projection of application data: UI = f(data). We formalize these rules into five standalone principles.

PRINCIPLE 1

Declare UI as a Pure Function of Data Instead of Mutating DOM Nodes

You must declare what the user interface looks like for a given set of data (UI = f(data)), strictly avoiding manual DOM queries like document.getElementById or property mutations.

We should do this:
return (<h1>Welcome, {name}</h1>);
Declares UI as a pure projection of data
We should not do this:
const el = document.getElementById('title'); el.textContent = name;
Manual DOM mutation causes state drift

To understand the declarative model in an interview, you must decompose the governing formula UI = f(data) into three separate architectural tiers:

  1. The Data Input (data): Immutable snapshots of application state and incoming props that represent the single source of truth at a given moment in time.
  2. The Pure Component Function (f): A deterministic JavaScript function that takes data as an input and calculates the visual interface without performing outside mutations.
  3. The Virtual Descriptor (UI): A lightweight tree of plain JavaScript objects returned by the component, describing what DOM nodes the browser should ultimately display.

In imperative browser programming, you write sequential commands telling the browser how to locate elements, parse strings, and mutate living C++ objects. When application state changes, you must manually trace every dependent DOM node across the entire page. In declarative React, you write pure functions that return descriptions of the desired UI for any given data. React takes on the mechanical burden of computing the differences in memory and applying minimal DOM patches automatically.

In software architecture, state drift occurs whenever multiple parts of a user interface hold duplicate representations of the same underlying data:

  1. The Imperative Synchronization Trap: In vanilla JavaScript, updating a user name requires querying the greeting banner, the navigation bar badge, and the account drawer independently. If a network event or exception interrupts the sequence, one DOM node updates while another shows stale text.

Because all child components derive their markup from the identical data reference in the same render pass, state drift is mathematically impossible.

Interviewers frequently probe whether candidates understand why mutating props is disastrous in a component architecture:

  1. Broken Change Detection: React relies on shallow reference equality (Object.is(prevProps, nextProps)) to determine whether a component or memoized subtree needs to re-render. If a child component mutates props.tier = 'VIP', it mutates the parent's memory reference in place, blinding React to changes and corrupting cache layers.
  2. Idempotent Render Snapshots: Every render pass represents an immutable historical record of the interface for a given state. If you need a modified representation of incoming data, calculate a fresh local variable (const normalizedTier = tier.toUpperCase()) without touching the incoming prop snapshot.

  1. The Destructive C++ Cost of innerHTML: Assigning a markup string to innerHTML forces the browser engine to wipe out all existing C++ DOM nodes inside that container. Glossary

  • Declarative UI: An architectural paradigm where code describes what the user interface should look like for a given state, leaving the runtime engine to compute and execute the necessary physical DOM mutations.
  • Component: A self-contained, reusable JavaScript function that accepts input properties (props) and returns a tree of descriptors representing user interface markup.
  • Props: A plain JavaScript dictionary of arguments passed downward from a parent component to a child component, configuring its behavior and appearance.
  • State Drift: A synchronization bug where multiple UI elements that should reflect the exact same data display contradictory or outdated values due to missed imperative updates.
  • Virtual DOM / UI Descriptor Tree: A lightweight in-memory tree of JavaScript objects representing the desired user interface structure, used by React to compute minimal physical DOM diffs.

Beyond the basics

  • The UI descriptor tree and React elements: When JSX executes, it produces plain, immutable JavaScript objects called React elements via react/jsx-runtime. React creates this UI tree from your components and uses it to compute minimal physical DOM mutations rather than traversing browser nodes directly (see react.dev/learn/understanding-your-ui-as-a-tree).
  • Purity in component rendering: A React component function must be a pure calculation with respect to its inputs; given the same props, it must always return the same JSX without mutating preexisting variables or performing outside side effects during render (see react.dev/learn/keeping-components-pure).
  • Module dependency trees vs render trees: A React application possesses two distinct tree structures: the static module dependency tree evaluated by bundlers like Vite using import statements, and the dynamic runtime render tree constructed by React representing nested component instances on screen (see react.dev/learn/understanding-your-ui-as-a-tree).
  • Read-only immutable props: Props received by a child component are strictly read-only snapshots in JavaScript memory; components must never reassign or mutate properties like props.readerName directly, requiring state setters or parent callbacks to request updates (see react.dev/learn/passing-props-to-a-component).
  • Host elements vs custom component instances: Lowercase JSX tags (<header>, <span>, <div>) map directly to native HTML host elements in the browser DOM, whereas capitalized tags (<SiteHeader />, <ReaderGreeting />) signal custom JavaScript functions that React invokes in memory (see react.dev/learn/your-first-component).
  • Fragments and single-root returns: Every React component must return a single root JSX element because the markup compiles into a single JavaScript function call; when multiple adjacent sibling elements are needed without polluting the DOM with extra wrapper <div> nodes, developers wrap them in an empty fragment <>...</> (see react.dev/learn/writing-markup-with-jsx).

Monolithic Bundlers and Cold-Start Latency

In modern web development, you cannot run raw React code directly inside a browser without a build step. Browsers understand standard HTML, CSS, and vanilla JavaScript, but they cannot natively parse JSX tags like <App /> or unbundled module imports across hundreds of files. A build tool is a development program that compiles JSX into standard JavaScript functions, resolves package dependencies, and prepares files for the browser. Historically, developers relied on monolithic bundlers like Webpack, packaged inside tools like Create React App.

In legacy setups like Create React App, starting the local development server required crawling and bundling every single JavaScript module in the project into memory before serving a single page. Look at the monolithic bundling bottleneck below:

Every file save forced the bundler to reconstruct large module graphs in memory. This latency created a frustrating development loop. Modern development solves this by decoupling local development from production bundling.

⚡ IN THE WILD

Why did Create React App freeze large codebases? Legacy tools like Create React App were built around Webpack at a time when web browsers could not load JavaScript modules natively. The bundler had to crawl every import statement, convert every file into CommonJS or bundle chunks, and assemble a massive in-memory bundle before the local HTTP server could send its first response. If your newsroom dashboard imported 500 files, Webpack compiled all 500 files before you could preview a single button. Modern tools like Vite eliminate this by relying on browser-native ES Modules: the server starts instantly in milliseconds, and the browser requests only the exact files currently visible on your screen.

Glossary

  • Build Tool: A development program (such as Vite) that transforms JSX, resolves module dependencies, and bundles static assets for browser execution.
  • Full-Stack Framework: An integrated application framework (such as Next.js or Remix) that pairs React with a backend server runtime for server-side rendering, routing, and data mutations.
  • Native ES Modules: The ECMAScript standard for loading JavaScript files in web browsers using <script type="module"> and standard import / export syntax without upfront bundling.
  • Hot Module Replacement (HMR): A development server capability that swaps updated JavaScript modules in the browser memory in real time without triggering a full page refresh.
  • Single-Page Application (SPA): A web application architecture where the browser loads a single static HTML page and dynamically updates content via client-side JavaScript rendering.

Beyond the basics

  • Native ES modules and browser module graphs: Modern browsers natively parse import and export statements when loaded with <script type="module">, allowing Vite to serve unbundled source files directly during development and letting the browser handle dependency resolution (see react.dev/learn/start-a-new-react-project).
  • Dependency pre-bundling with esbuild: Vite uses esbuild written in Go to convert CommonJS dependencies into standard ES modules and bundle multi-file libraries into single cached files, preventing hundreds of simultaneous HTTP network requests on cold start (see react.dev/learn/start-a-new-react-project).
  • Client-side rendering vs server-side rendering: Client-side rendering (CSR) downloads an empty HTML container and executes JavaScript in the browser to construct DOM nodes, whereas server-side rendering (SSR) generates fully populated HTML strings on a Node.js server before delivery (see react.dev/learn/understanding-your-ui-as-a-tree).
  • The root HTML entry point convention: In Vite, index.html resides in the project root rather than a public subfolder because Vite treats the HTML file as the central source code entry point, discovering script tags and assets directly from the markup (see react.dev/learn/start-a-new-react-project).
  • Separation of runtime and dev dependencies: The package.json manifest strictly isolates packages executed in the user's browser (dependencies) from build tools, compilers, and linters executed exclusively in the developer's Node.js environment (devDependencies) (see react.dev/learn/start-a-new-react-project).
  • Strict mode in development: React's <StrictMode> component intentionally double-invokes component render functions in local development to help developers identify impure calculations, memory leaks, and unintended side effects before deploying to production (see react.dev/reference/react/StrictMode).

Lowercase Tags and Silent Disappearances

In standard HTML, web browsers recognize dozens of built-in tags like <article>, <header>, and <p>. These tags are defined by web standards. When a browser parses a lowercase tag name, it creates a native DOM element in memory. If the tag name is unknown, the browser still creates an empty HTML element. It does not throw an error. It simply paints nothing on the screen.

When Leo writes a function named articleCard and places <articleCard /> in his JSX, he expects React to run his code.

The JSX compiler does not inspect your JavaScript scope to see if a function exists. Instead, it inspects the first letter of the tag name. Why does a lowercase component fail silently? The JSX compiler follows a strict syntactic rule. When the tag starts with a lowercase letter, the transpiler generates _jsx("tagname"). The browser treats this as an unknown custom element. It creates an empty HTML element without styling or content. The terminal reports a successful build because the syntax is valid JavaScript. The browser console stays empty because unknown HTML tags are permitted by the HTML specification. To tell the compiler that your tag represents a JavaScript function, you must capitalize the first letter: <ArticleCard />.

Principles of React: The Core Laws of Component Anatomy and Invocation

To prepare for any technical interview, we must separate theory from application and establish the five fundamental laws governing how React identifies, instantiates, and executes component functions. In React, a component is not an HTML tag—it is a pure JavaScript function that returns user interface descriptors. We formalize these rules into five standalone principles.

PRINCIPLE 1

Always Capitalize Component Names Using PascalCase

You must name every React component using PascalCase (starting with an uppercase letter), so the compiler routes the tag to your custom JavaScript function rather than a native HTML element string.

We should do this:

Transpiles to _jsx(ArticleCard, {})
We should not do this:
<articleCard />
Transpiles to _jsx('articlecard', {})

In senior technical interviews, explaining why React requires PascalCase requires dissecting the compiler's Abstract Syntax Tree (AST) tag name evaluation:

  1. The Lowercase Tag Pathway (Native HTML String Literal): If the tag begins with a lowercase character (/^[a-z]/), the JSX compiler assumes it represents a built-in browser host element. It emits a string literal: _jsx("articlecard", {}). At runtime, React passes this raw string to document.createElement("articlecard"). Because "articlecard" is not a standard HTML element, the browser instantiates an empty HTMLUnknownElement, ignoring your JavaScript function completely and painting a blank node.
  2. The Uppercase Tag Pathway (Component Function Identifier): If the tag begins with an uppercase character (/^[A-Z]/) or contains a dot (Article.Card), the JSX compiler treats it as an in-scope JavaScript variable. It emits the variable identifier directly: _jsx(ArticleCard, {}). At runtime, React receives a direct function reference, invokes ArticleCard(props) in memory, and mounts its rendered tree.

If a component mutates an external counter (globalCount++) during render, the counter increments by two instead of one. Glossary

  • Component: A pure JavaScript function that accepts inputs and returns a tree of JSX element descriptors representing user interface markup.
  • PascalCase: A naming convention where the first letter of every word is capitalized (ArticleCard), required by React compilers to identify custom components.
  • JSX AST Routing: The compiler mechanism where lowercase tags become string literals ("div") and capitalized tags become direct function identifiers (ArticleCard).
  • Declarative Invocation: Mounting a component using JSX tag syntax (<ArticleCard />), allowing React to control function execution and lifecycle management.
  • Component Purity: The architectural contract that a component function must calculate its output without mutating external variables or causing side effects during render.

Beyond the basics

  • JSX compiler transform specification: Modern React uses the react/jsx-runtime automatic transform, where <ArticleCard /> compiles to _jsx(ArticleCard, {}) and <article /> compiles to _jsx("article", {}) (see react.dev/learn/your-first-component).
  • Component purity and idempotent rendering: React expects component functions to be pure calculations; given the same inputs, they must always return the exact same JSX without modifying preexisting variables outside their scope (see react.dev/learn/keeping-components-pure).
  • The render tree and component instances: When you declare <ArticleCard /> in JSX, React creates an in-memory element descriptor; it does not instantiate a persistent object until it reconciles the render tree (see react.dev/learn/understanding-your-ui-as-a-tree).
  • Automatic Semicolon Insertion (ASI) in return statements: JavaScript automatically inserts a semicolon after a bare return keyword if followed by a line break, returning undefined unless wrapped in parentheses (see react.dev/learn/writing-markup-with-jsx).
  • Custom HTML elements vs React components: While HTML Web Components use hyphenated lowercase names (<article-card>), React components require PascalCase (<ArticleCard>) to compile into direct function references (see react.dev/learn/your-first-component).

Permissive Browsers vs Strict Compilers

In plain HTML, web browsers are remarkably forgiving. Browsers allow unclosed void tags like <img> or <input>. Browsers also permit multiple adjacent elements at the top level of a document. If you paste raw HTML markup into a standard .html file, the browser parses the text and paints the page.

When a developer pastes raw HTML into a React component function, the build tool halts immediately with fatal syntax errors.

The compiler crashes because a JavaScript function cannot return multiple values. Writing return a, b evaluates both expressions but returns only the second value. Furthermore, JSX compiles into _jsx() function calls. Every _jsx() call represents a single element descriptor. You cannot pass two separate expressions to a single return statement without a wrapping structure.

Principles of React: The Core Laws of JSX Grammar

To prepare for any technical interview, we must separate theory from application and establish the nine fundamental laws governing the React compiler. In JSX, HTML markup strings do not exist. Every tag, attribute, inline style, and comment is transformed into JavaScript function calls and plain JavaScript objects. We formalize these rules into nine standalone principles.

PRINCIPLE 1

Always Return Exactly One Root Element

You must ensure every component return statement produces exactly one root element (because JavaScript functions can only return a single value).

We should do this:

We should not do this:

A React component is a standard JavaScript function. In JavaScript, a return statement can only return a single value or expression. When you write two adjacent tags at the root level, JavaScript cannot evaluate them as a single expression. Under the hood, JSX compiles into _jsx(type, props) function calls. Just as you cannot return two separate function calls without wrapping them in an array or container object, you cannot return adjacent JSX tags.

Why does a wrapper div break your CSS Flexbox layout? When developers hit the single-root error, their instinctive reflex is wrapping everything in a <div>. PRINCIPLE 3

You must explicitly close every JSX tag using a matching closing tag or a self-closing trailing slash (preventing unclosed void elements like <img> from halting the compiler).

In HTML5, browser parsers maintain hardcoded lists of void elements like <img>, <input>, <br>, and <hr> that cannot accept children, permitting closing slashes to be omitted. JSX, by contrast, enforces strict XML grammar. The compiler builds an Abstract Syntax Tree where every opening token <tag> must have an explicit matching boundary, either via a closing tag </tag> or a self-closing trailing slash <tag />. Omitting the trailing slash halts compilation instantly.

Write className and htmlFor to Match Native DOM Properties

You must write HTML attributes that collide with JavaScript reserved keywords using their native browser DOM property names (writing className instead of class, and htmlFor instead of for).

We should not do this:

To understand this rule in an interview, you must distinguish between three separate layers of the web platform:

  1. HTML Attributes (Markup Text): In raw HTML documents, class="card" and for="email" are static markup attributes parsed as plain text strings.
  2. JavaScript Reserved Keywords (Language Grammar): In ECMAScript, words like class (used to declare classes) and for (used to declare loops) are reserved keywords. In early JavaScript engines, using reserved words in dot-notation (element.class or element.for) triggered syntax errors.
  3. Browser DOM Properties (Living Objects): When a browser parses HTML, it instantiates living JavaScript objects in memory (such as HTMLDivElement or HTMLLabelElement). To avoid keyword collisions in JavaScript, the original 1998 W3C DOM specification explicitly mapped the class attribute to the property element.className, and the for attribute to element.htmlFor.

React does not invent className or htmlFor. When JSX compiles into _jsx("div", { className: "card" }), React updates the browser by setting the native DOM property directly (domNode.className = "card"). Because JSX operates at the level of JavaScript objects rather than raw HTML text strings, it aligns with native browser DOM properties.

PRINCIPLE 5

Write Multi-Word Attribute Names in camelCase

You must write all multi-word JSX attribute names in camelCase (such as tabIndex and readOnly to align with the browser's native DOM property interfaces).

We should do this:
<input tabIndex={0} readOnly={true} />
We should not do this:
<input tabindex="0" readonly>

This rule is not an arbitrary React design preference—it is the exact same DOM property alignment law established in Principle 4. In raw HTML documents, attribute parsing is case-insensitive, allowing developers to write <input tabindex="0" readonly autofocus> as uncapitalized text strings. However, in the browser's native JavaScript DOM API, the HTMLInputElement interface has defined these properties in camelCase since the initial W3C specifications: input.tabIndex, input.readOnly, and input.autoFocus. Because React maps JSX attributes directly to properties on native DOM nodes, it adheres strictly to the browser's established camelCase interface properties.

PRINCIPLE 6

Pass Inline Styles as JavaScript Objects, Never Text Strings

You must pass inline element styles as JavaScript objects with camelCase keys using double curly braces (writing style={{ color: 'red' }} instead of raw CSS text strings).

We should do this:
<span style={{ color: 'red' }}>
We should not do this:
<span style="color: red;">

Candidates frequently face two core interview questions regarding JSX inline styles:

  1. Why the double curly braces style={{ ... }}? There is no special "double-brace" syntax in React. The outer pair of braces {} is the JSX escape delimiter that switches the parser from markup mode into JavaScript expression mode. The inner pair { color: 'red', fontWeight: 700 } is simply a standard JavaScript object literal passed as the value.
  2. Why camelCase keys like fontWeight instead of font-weight? In the browser DOM, an element's inline styling is exposed as an instance of CSSStyleDeclaration (element.style). In JavaScript, writing element.style.font-weight is parsed as a subtraction expression (element.style.font minus the undefined variable weight), triggering a runtime syntax or reference error. The browser DOM API resolved this by mapping CSS hyphenated properties to camelCase JavaScript properties (element.style.fontWeight, element.style.marginTop). React's style prop passes this object directly to the browser's native element.style interface.
PRINCIPLE 7

Write Comments Inside Curly Braces as JavaScript Comments

You must write comments inside JSX markup as JavaScript block comments enclosed within curly braces ({/* comment */}), strictly avoiding raw HTML comment syntax (<!-- -->).

We should do this:
{/* breaking news alert */}
We should not do this:
<!-- breaking news alert -->

The JSX compiler operates as a two-state tokenizer: Markup Mode and JavaScript Mode. In Markup Mode, raw text characters are treated as literal text children, and encountering an opening angle bracket < immediately signals the parser to evaluate an element tag name. When encountering HTML comment syntax <!--, the tokenizer attempts to parse !-- as an HTML tag identifier, which is illegal syntax and halts compilation instantly. Curly braces {} serve as the explicit lexical boundary that switches the tokenizer into JavaScript Mode, where /* ... */ is safely evaluated as a standard ECMAScript block comment and erased during compilation.

PRINCIPLE 8

Preserve Hyphens for aria-* and data-* Attributes

You must strictly retain hyphens for aria-* and data-* attributes (writing aria-label and data-testid to align with W3C accessibility and DOM dataset specifications).

We should do this:
<input aria-label="Search" data-testid="search" />
We should not do this:
<input ariaLabel="Search" dataTestId="search" />

A common interview question asks why React converts standard HTML attributes to camelCase DOM properties, yet strictly preserves hyphens for aria-* and data-*. The answer lies in how React commits updates to the browser DOM:

  1. Standard Props use DOM Property Assignment: For standard attributes, React assigns values directly to object properties on the living JavaScript node (domNode.className = props.className, domNode.tabIndex = props.tabIndex).
  2. aria-* and data-* use DOM Attribute Assignment: The browser DOM does not define native JavaScript properties like node.ariaLabel. Screen readers (via the browser accessibility tree) and CSS attribute selectors ([data-testid="search-input"]) query the serialized HTML attribute string. Therefore, during DOM mutation, React calls the native browser method: domNode.setAttribute('aria-label', value) and domNode.setAttribute('data-testid', value). Because React relies on setAttribute(), it strictly preserves the official W3C hyphenated attribute names.

Glossary

  • JSX: A syntax extension for JavaScript that allows developers to write XML-like markup that compiles into standard _jsx() function calls.
  • React Fragment: A built-in React component (<>...</>) that groups a list of children without adding extra nodes to the physical browser DOM.
  • Single Root Invariant: The compiler requirement that every component return statement must resolve to a single JavaScript expression.
  • Self-Closing Tag: A tag that closes itself with a trailing slash (<img />, <input />), mandatory in JSX for void HTML elements that have no children.
  • DOM Property Mapping: The convention where JSX attributes match browser DOM object properties (such as className and htmlFor) to avoid collisions with JavaScript reserved words.
  • Tag Casing Rule: The compiler convention where lowercase tags denote browser DOM strings and capitalized tags denote in-scope component functions.

  • DOM property mapping: JSX attributes closely match browser DOM properties rather than HTML attribute strings; for example, class becomes className and for becomes htmlFor (see react.dev/learn/writing-markup-with-jsx).

Principles of React: The Core Laws of JSX Expressions

To prepare for any technical interview, we must separate theory from application and establish the fundamental laws governing how the React compiler parses, evaluates, and projects JavaScript code inside JSX. In React, markup is not a separate templating language—it is pure JavaScript execution. We formalize these rules into six standalone principles.

PRINCIPLE 1

Wrap Dynamic JavaScript in Curly Braces

⚡ IN THE WILD

Why does root.render() leave container.innerHTML empty immediately after running? When developers migrate from legacy React or vanilla DOM scripts, they often expect DOM mounting to finish synchronously. In legacy React, calling ReactDOM.render(<App />, container) executed the entire render pass immediately, meaning the very next line of code could inspect container.innerHTML and find rendered markup. With modern createRoot, root.render(<App />) is asynchronous and concurrent! Calling root.render() does not mount the tree immediately; it schedules a concurrent render task with React's priority scheduler. If you execute root.render(<App />) and immediately query container.innerHTML on the next line, the browser returns an empty string (""). React yields execution back to the browser event loop before painting, ensuring that heavy initial tree renders never freeze user input or block animations.

Principles of React: The Core Laws of Mounting with createRoot

To prepare for any technical interview, we must separate theory from application and establish the six fundamental laws governing how modern React initializes, attaches, and renders application trees into the browser DOM. In React 19, mounting is not a single opaque function call—it is an explicit bridge between living DOM nodes and concurrent fiber architectures. We formalize these rules into six standalone principles.

PRINCIPLE 1

Always Import createRoot from react-dom/client

When mounting an application in the browser, you must always import createRoot from the client subpath (react-dom/client), strictly avoiding the deprecated monolithic package (react-dom).

In senior technical interviews, explaining why ReactDOM was broken into subpaths requires contrasting three distinct execution environments:

  1. Targeted Subpath Packaging (react-dom/client vs react-dom/server): Modern React applications run across diverse JavaScript runtimes (browsers, Node.js servers, Cloudflare Workers, and Deno edge runtimes). Browsers require DOM-specific code (createRoot, hydrateRoot), while servers require HTML streaming streams (renderToPipeableStream). The dedicated subpath react-dom/client isolates browser-only DOM mounting logic into its own bundle entry point.
  2. Bundler Tree-Shaking and Dead-Code Elimination: When you import from the monolithic react-dom, bundlers cannot reliably eliminate legacy APIs, pulling in deprecated synchronous reconcilers and server stubs that bloat the client bundle. By importing strictly from react-dom/client, bundlers like Vite and esbuild include only the lightweight client mounting runtime.
  3. Deprecation Warnings and Future Compatibility: React 19 treats imports of createRoot directly from react-dom as deprecated legacy behavior. Importing from the root package triggers compilation warnings and risks breaking changes in future React versions that intend to remove monolithic exports entirely.

In technical interviews, this architectural shift from React 16 to React 17+ is evaluated across two event delegation models:

  1. The Legacy Document Delegation Model (React 16 and Earlier): Legacy React attached a single top-level event listener for each event type (click, keydown, input) to the global browser document node. This architecture enables micro-frontend architectures, where multiple independent React applications, or a mix of React and Vue widgets, can live side by side on a single webpage without event handlers colliding or stepping on each other.

Glossary

  • createRoot: The official factory function from react-dom/client that initializes a concurrent React root container attached to a physical DOM node.
  • Concurrent Root: A React root instance that supports React 19 concurrent features, interruptible rendering, and priority scheduling.
  • Fiber Root: The internal React data structure that tracks the root container, reconciliation queue, and active component tree in memory.
  • Root Container DOM Node: The physical HTML element (typically <div id="root">) that houses the mounted React component tree and receives delegated synthetic events.
  • Event Delegation: The architecture where React attaches a single event listener per event type to the root container rather than individual DOM nodes.
  • Component-DOM Decoupling: The architectural practice of keeping component functions pure and free of direct DOM queries or mounting APIs.

Beyond the basics

  • The two-step createRoot lifecycle: Calling createRoot(container) creates a FiberRootNode in memory, while calling root.render(element) schedules the initial concurrent render pass (see react.dev/reference/react-dom/client/createRoot).
  • Root unmounting mechanics: Calling root.unmount() destroys the entire React tree, unbinds root event listeners, and clears the container element (see react.dev/reference/react-dom/client/createRoot#root-unmount).
  • Hydration with hydrateRoot: When server-rendered HTML exists in the container, applications use hydrateRoot(domNode, <App />) instead of createRoot to attach event listeners without destroying existing markup (see react.dev/reference/react-dom/client/hydrateRoot).
  • Multiple roots on a single page: A single HTML document can host multiple independent createRoot containers, enabling progressive migration of legacy server templates (see react.dev/reference/react-dom/client/createRoot#rendering-a-page-partially-built-with-react).
  • Strict Mode verification: Wrapping the root element in <StrictMode> causes React to double-invoke component render passes in development to catch impure side effects (see react.dev/reference/react/StrictMode).
