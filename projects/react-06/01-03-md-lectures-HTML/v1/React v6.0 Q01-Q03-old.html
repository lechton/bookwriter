Lecture 1: What is React and the Declarative Model

Interview Question

CORE

What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

Imagine this scenario:

  1. Clara logs into The National Times website to read the morning investigative edition.
  2. The newsroom header displays her name in multiple places across the top navigation bar.
  3. Your plain JavaScript script runs a function to update the user name across the screen.
  4. Why does the greeting say Clara while the subscriber badge still displays Guest?
  5. Readers see conflicting user information, suspect account errors, and lose trust in the platform.
  6. The manual script updated two DOM nodes but missed the third element entirely.
  7. Today, your UI will synchronize every element automatically from a single source of truth.

Manual DOM Hunting and State Drift

In plain browser JavaScript, you build dynamic pages by manipulating the Document Object Model. Developers commonly call this the DOM. The DOM is the browser's internal tree of live C++ objects representing every HTML element on screen. To change a word on the page, your script must locate the exact element first. You call browser methods like document.getElementById or document.querySelector. Once the element is found, you overwrite its properties directly in memory. You assign new text using textContent or replace markup using innerHTML.

In a growing application like The National Times, a single piece of reader data appears across multiple sections. The subscriber's name appears in the welcome banner, the profile menu, and the subscription badge. When the user logs in, your script must find and update every single copy by hand.

Look at the naive imperative update function below:

Naive DOM Update
1function updateHeaderUser(name) {
2 const greeting = document.getElementById('header-greeting');
3 greeting.textContent = 'Welcome, ' + name;
Updates header GREETING
4 const profile = document.getElementById('nav-profile-name');
5 profile.textContent = name;
Updates navigation PROFILE
6}

When updateHeaderUser runs, it updates the greeting and the profile pill. However, notice the omission: the script forgot to query #subscriber-badge. The greeting displays Clara, but the badge still displays Guest.

This synchronization failure is called state drift. State drift happens when two interface elements that should show the same data show different values. In imperative programming, you bear two burdens: deciding what changed, and finding every affected node. As your website grows to hundreds of elements, manual hunting inevitably misses nodes.

To avoid missing individual nodes, developers often attempt to replace the entire parent container at once. They wipe the whole container using innerHTML. While this guarantees all text gets updated, it introduces a severe hidden penalty:

Destructive Replacement
1function replaceHeader(name) {
2 const root = document.getElementById('header-root');
3 const markup = `<header><h1>National Times</h1><p>${name}</p></header>`;
4 root.innerHTML = markup;
WRONG: wipes container, losing input FOCUS
5}

⚡ IN THE WILD

Why does innerHTML destroy your active input focus? When you assign a new string to innerHTML, the browser parser does not compare text. It destroys every existing DOM node inside that container and creates brand-new nodes in memory. If a reader is typing in an input when innerHTML runs, that <input> element is deleted from existence. The browser recreates a new input that looks identical, but the active cursor focus is lost. Text selection vanishes, and running CSS transitions reset to their initial frames. React avoids this by comparing changes in memory and surgically updating only the text nodes that changed.

Interview Tip

To impress the interviewer: When asked why React was created, do not merely say "it makes building websites faster." Explain that React solves the fundamental problem of state drift inherent in imperative programming. In vanilla JavaScript, the developer must manually keep the DOM in sync with data across dozens of queries. React replaces this manual choreography with a declarative model. The user interface becomes a pure projection of application data: UI = f(data).

Principles of React: The Core Laws of the Declarative Model

To prepare for any technical interview, we must separate theory from application and establish the five fundamental laws governing how React replaces imperative DOM mutation with a declarative, component-driven architecture. In vanilla JavaScript, the developer manually orchestrates browser DOM updates. In React, the user interface is a pure projection of application data: UI = f(data). We formalize these rules into five standalone principles.

PRINCIPLE 1

Declare UI as a Pure Function of Data Instead of Mutating DOM Nodes

You must declare what the user interface looks like for a given set of data (UI = f(data)), strictly avoiding manual DOM queries like document.getElementById or property mutations.

We should do this:
return (<h1>Welcome, {name}</h1>);
Declares UI as a pure projection of data
We should not do this:
const el = document.getElementById('title'); el.textContent = name;
Manual DOM mutation causes state drift

In imperative browser programming, you write sequential commands telling the browser how to locate elements, parse strings, and mutate living C++ objects. When application state changes, you must manually trace every dependent DOM node across the entire page. In declarative React, you write pure functions that return descriptions of the desired UI for any given data. React takes on the mechanical burden of computing the differences in memory and applying minimal DOM patches automatically.

Principle 1: Declarative Projection vs Imperative Mutation

WRONG: Imperative DOM hunting is fragile and manual
2title.textContent = article.headline;

PRINCIPLE 2

Maintain a Single Source of Truth to Eliminate State Drift

You must store shared application data in a single parent container and pass it downward, never maintaining separate copies that can fall out of sync.

It is best practice to do this:
<SiteHeader readerName={name} />
Single source of truth updates all children
Instead of doing this:
updateGreeting(name); updateBadge(name);
Independent queries drift when updates miss

When data appears in multiple visual regions—such as a subscriber name in the welcome banner and a membership tag in the navigation bar—imperative scripts must locate and update each copy independently. Missing a single query causes state drift, leaving stale values on screen. In React, you declare shared state in a common ancestor component and distribute that value downward to child components through props. Because all children derive their display from the exact same variable, state drift is mathematically impossible.

PRINCIPLE 3

Unpack Props with Parameter Destructuring to Document Inputs

You should unpack incoming props directly in the component parameter list ({ readerName }), rather than repeating the props. prefix throughout the function body.

It is best practice to do this:
function User({ name }) { return (<span>{name}</span>); }
Destructuring documents required inputs
Instead of doing this:
function User(props) { return (<span>{props.name}</span>); }
Repetitive props prefix clutters markup

Every React component receives an incoming dictionary called props. In foundational code, developers write function Greeting(props) and access values with props.readerName. While this reflects the underlying object structure, it litters JSX markup with repetitive prefixes. Modern idiomatic React uses JavaScript parameter destructuring ({ readerName }). Destructuring extracts variables directly at the function boundary, immediately signaling to any reviewing engineer exactly which props the component depends on.

PRINCIPLE 4

Treat Incoming Props as Read-Only Immutable Snapshots

read-only immutable snapshots data passed into a component that cannot be reassigned or modified in memory

You must treat all props received by a component as strictly read-only immutable snapshots, never reassigning or mutating prop values inside the function body.

We should do this:
const formatted = name.toUpperCase(); return (<span>{formatted}</span>);
Calculates derived value without mutating prop
We should not do this:
props.name = props.name.toUpperCase(); return (<span>{props.name}</span>);
Mutating props causes unpredictable bugs

React components must remain pure calculations with respect to their inputs. Props flow strictly downward from parent to child. If a child component attempts to mutate props.readerName = 'New Name' it violates the uni-directional data contract and causes silent bugs, race conditions, and corrupted memoization caches. If you need a transformed version of a prop, calculate a new local constant or evaluate the expression inline. Never mutate the incoming prop object.

PRINCIPLE 5

Let React Reconcile Changes in Memory to Preserve DOM Node Identity

You must allow React to reconcile element updates in memory, never wiping containers with innerHTML (which destroys active input focus and resets CSS animations).

We should do this:
<header><h1>{title}</h1></header>
Surgical update preserves active input focus
We should not do this:
root.innerHTML = '<h1>' + title + '</h1>';
Container wipe destroys DOM nodes and focus

When developers use imperative methods like container.innerHTML = markup, the browser parser wipes out all existing DOM nodes inside that container and constructs brand-new C++ nodes. If an end user is actively typing in a text field or navigating via keyboard, deleting the element destroys active cursor focus, text selection, and running CSS transitions. React solves this by maintaining a lightweight in-memory tree of virtual descriptors. During reconciliation, React diffs the old and new descriptors and surgically updates only the exact text nodes or attributes that changed, leaving living DOM nodes, active focus, and cursor positions completely intact.

The parent container SiteHeader.jsx holds the single data truth and distributes it downward to ReaderGreeting.jsx and SubscriberBadge.jsx. React then calculates the physical DOM operations required and mounts the nodes efficiently into the browser window.

Glossary

  • Declarative UI: An architectural paradigm where code describes what the user interface should look like for a given state, leaving the runtime engine to compute and execute the necessary physical DOM mutations.
  • Component: A self-contained, reusable JavaScript function that accepts input properties (props) and returns a tree of descriptors representing user interface markup.
  • Props: A plain JavaScript dictionary of arguments passed downward from a parent component to a child component, configuring its behavior and appearance.
  • State Drift: A synchronization bug where multiple UI elements that should reflect the exact same data display contradictory or outdated values due to missed imperative updates.
  • Virtual DOM / UI Descriptor Tree: A lightweight in-memory tree of JavaScript objects representing the desired user interface structure, used by React to compute minimal physical DOM diffs.

Beyond the basics

  • The UI descriptor tree and React elements: When JSX executes, it produces plain, immutable JavaScript objects called React elements via react/jsx-runtime. React creates this UI tree from your components and uses it to compute minimal physical DOM mutations rather than traversing browser nodes directly (see react.dev/learn/understanding-your-ui-as-a-tree).
  • Purity in component rendering: A React component function must be a pure calculation with respect to its inputs; given the same props, it must always return the same JSX without mutating preexisting variables or performing outside side effects during render (see react.dev/learn/keeping-components-pure).
  • Module dependency trees vs render trees: A React application possesses two distinct tree structures: the static module dependency tree evaluated by bundlers like Vite using import statements, and the dynamic runtime render tree constructed by React representing nested component instances on screen (see react.dev/learn/understanding-your-ui-as-a-tree).
  • Read-only immutable props: Props received by a child component are strictly read-only snapshots in JavaScript memory; components must never reassign or mutate properties like props.readerName directly, requiring state setters or parent callbacks to request updates (see react.dev/learn/passing-props-to-a-component).
  • Host elements vs custom component instances: Lowercase JSX tags (<header>, <span>, <div>) map directly to native HTML host elements in the browser DOM, whereas capitalized tags (<SiteHeader />, <ReaderGreeting />) signal custom JavaScript functions that React invokes in memory (see react.dev/learn/your-first-component).
  • Fragments and single-root returns: Every React component must return a single root JSX element because the markup compiles into a single JavaScript function call; when multiple adjacent sibling elements are needed without polluting the DOM with extra wrapper <div> nodes, developers wrap them in an empty fragment <>...</> (see react.dev/learn/writing-markup-with-jsx).

Lecture 2: Project Scaffolding: Build Tools vs Full-Stack Frameworks

Interview Question

CORE

How do you create and run a new React project, and how do you choose between a framework and a build tool?

Imagine this scenario:

  1. Leo joins The National Times engineering team to build an internal dashboard for investigative reporters.
  2. The project requires an interactive screen to coordinate article edits, review news feeds, and verify fact checks.
  3. Leo opens the official documentation, which recommends installing a full-stack framework with server rendering.
  4. Why does a private newsroom tool behind an authentication login require a Node.js server runtime and edge infrastructure?
  5. Setting up a full-stack server creates ongoing server maintenance, edge deployment friction, and unnecessary hosting costs.
  6. The team only needs a fast client-side application compiled to static HTML, JavaScript, and CSS.
  7. Today, you will master project scaffolding with Vite and learn exactly when to choose a standalone build tool over a full-stack framework.

Monolithic Bundlers and Cold-Start Latency

In modern web development, you cannot run raw React code directly inside a browser without a build step. Browsers understand standard HTML, CSS, and vanilla JavaScript, but they cannot natively parse JSX tags like <App /> or unbundled module imports across hundreds of files. A build tool is a development program that compiles JSX into standard JavaScript functions, resolves package dependencies, and prepares files for the browser. Historically, developers relied on monolithic bundlers like Webpack, packaged inside tools like Create React App.

In legacy setups like Create React App, starting the local development server required crawling and bundling every single JavaScript module in the project into memory before serving a single page. Look at the monolithic bundling bottleneck below:

Legacy Monolithic Bundler

2const memoryBundle = compileAllModules(modules);

3server.listen(3000, () => {

4 console.log('Server ready');
5});

When a project grew to hundreds of components, running npm start meant waiting 30 to 60 seconds just to view a single text change. Every file save forced the bundler to reconstruct large module graphs in memory. This latency created a frustrating development loop. Modern development solves this by decoupling local development from production bundling.

⚡ IN THE WILD

Why did Create React App freeze large codebases? Legacy tools like Create React App were built around Webpack at a time when web browsers could not load JavaScript modules natively. The bundler had to crawl every import statement, convert every file into CommonJS or bundle chunks, and assemble a massive in-memory bundle before the local HTTP server could send its first response. If your newsroom dashboard imported 500 files, Webpack compiled all 500 files before you could preview a single button. Modern tools like Vite eliminate this by relying on browser-native ES Modules: the server starts instantly in milliseconds, and the browser requests only the exact files currently visible on your screen.

Glossary

  • Build Tool: A development program (such as Vite) that transforms JSX, resolves module dependencies, and bundles static assets for browser execution.
  • Full-Stack Framework: An integrated application framework (such as Next.js or Remix) that pairs React with a backend server runtime for server-side rendering, routing, and data mutations.
  • Native ES Modules: The ECMAScript standard for loading JavaScript files in web browsers using <script type="module"> and standard import / export syntax without upfront bundling.
  • Hot Module Replacement (HMR): A development server capability that swaps updated JavaScript modules in the browser memory in real time without triggering a full page refresh.
  • Single-Page Application (SPA): A web application architecture where the browser loads a single static HTML page and dynamically updates content via client-side JavaScript rendering.

Beyond the basics

  • Native ES modules and browser module graphs: Modern browsers natively parse import and export statements when loaded with <script type="module">, allowing Vite to serve unbundled source files directly during development and letting the browser handle dependency resolution (see react.dev/learn/start-a-new-react-project).
  • Dependency pre-bundling with esbuild: Vite uses esbuild written in Go to convert CommonJS dependencies into standard ES modules and bundle multi-file libraries into single cached files, preventing hundreds of simultaneous HTTP network requests on cold start (see react.dev/learn/start-a-new-react-project).
  • Client-side rendering vs server-side rendering: Client-side rendering (CSR) downloads an empty HTML container and executes JavaScript in the browser to construct DOM nodes, whereas server-side rendering (SSR) generates fully populated HTML strings on a Node.js server before delivery (see react.dev/learn/understanding-your-ui-as-a-tree).
  • The root HTML entry point convention: In Vite, index.html resides in the project root rather than a public subfolder because Vite treats the HTML file as the central source code entry point, discovering script tags and assets directly from the markup (see react.dev/learn/start-a-new-react-project).
  • Separation of runtime and dev dependencies: The package.json manifest strictly isolates packages executed in the user's browser (dependencies) from build tools, compilers, and linters executed exclusively in the developer's Node.js environment (devDependencies) (see react.dev/learn/start-a-new-react-project).
  • Strict mode in development: React's <StrictMode> component intentionally double-invokes component render functions in local development to help developers identify impure calculations, memory leaks, and unintended side effects before deploying to production (see react.dev/reference/react/StrictMode).

Interview Question

What is a React component, and what rules govern how you write and name one?

Lowercase Tags and Silent Disappearances

In standard HTML, web browsers recognize dozens of built-in tags like <article>, <header>, and <p>. These tags are defined by web standards. When a browser parses a lowercase tag name, it creates a native DOM element in memory. If the tag name is unknown, the browser still creates an empty HTML element. It does not throw an error. It simply paints nothing on the screen.

When Leo writes a function named articleCard and places <articleCard /> in his JSX, he expects React to run his code.

Look at the naive lowercase attempt below:

7}

When App runs, the browser displays a blank space. Notice the problem: the function articleCard is never executed. The terminal reports a successful build, and the browser console stays clean.

The JSX compiler does not inspect your JavaScript scope to see if a function exists. Instead, it inspects the first letter of the tag name. If the tag begins with a lowercase letter, the compiler emits a string literal: _jsx("articlecard"). React receives this string and calls document.createElement("articlecard") The browser creates an empty native DOM node. Your custom function articleCard() is completely ignored.

⚡ IN THE WILD

Why does a lowercase component fail silently? The JSX compiler follows a strict syntactic rule. When the tag starts with a lowercase letter, the transpiler generates _jsx("tagname"). The browser treats this as an unknown custom element. It creates an empty HTML element without styling or content. The terminal reports a successful build because the syntax is valid JavaScript. The browser console stays empty because unknown HTML tags are permitted by the HTML specification. To tell the compiler that your tag represents a JavaScript function, you must capitalize the first letter: <ArticleCard />.

The transpiler uses the first letter to decide whether to pass a string literal ("div") or a direct function identifier (ArticleCard). Lowercase tags always become strings, bypassing your component function entirely.

Principles of React: The Core Laws of Component Anatomy and Invocation

To prepare for any technical interview, we must separate theory from application and establish the five fundamental laws governing how React identifies, instantiates, and executes component functions. In React, a component is not an HTML tag—it is a pure JavaScript function that returns user interface descriptors. We formalize these rules into five standalone principles.

PRINCIPLE 1

Always Capitalize Component Names Using PascalCase

You must name every React component using PascalCase (starting with an uppercase letter), so the compiler routes the tag to your custom JavaScript function rather than a native HTML element string.

<articleCard />
Transpiles to _jsx('articlecard', {})

The JSX compiler does not inspect your JavaScript scope at compile time to see if a function named articleCard exists. Instead, it inspects the first character of the tag name. If the tag begins with a lowercase letter, the compiler emits a string literal: _jsx("articlecard"). React passes this string to the browser DOM method document.createElement("articlecard") creating an empty native HTML element that paints nothing. Capitalizing the tag (<ArticleCard />) forces the transpiler to emit a direct function identifier: _jsx(ArticleCard). React then calls your component function in memory during render.

In our experiment, we saw how a lowercase tag caused a silent blank screen. The JSX transpiler uses the first letter of every tag to choose between a string literal and a function identifier. By adopting PascalCase and declarative JSX tags, we allow React to construct a managed component tree.

Where you will meet this

  1. Design System Libraries: Exporting capitalized UI primitives like Button, Modal, and Card so consumers can mount them declaratively in JSX.
  2. News Publication Feeds: Building modular article widgets like ArticleTeaser, JournalistProfile, and NewsAlert that compose into clean editorial layouts.
  3. E-Commerce Product Grids: Creating reusable ProductCard components that display merchandise without leaking markup details to parent containers.
  4. Dashboard Metric Cards: Packaging analytics charts and status indicators into self-contained components like MetricWidget across corporate portals.

Glossary

  • Component: A pure JavaScript function that accepts inputs and returns a tree of JSX element descriptors representing user interface markup.
  • PascalCase: A naming convention where the first letter of every word is capitalized (ArticleCard), required by React compilers to identify custom components.
  • JSX AST Routing: The compiler mechanism where lowercase tags become string literals ("div") and capitalized tags become direct function identifiers (ArticleCard).
  • Declarative Invocation: Mounting a component using JSX tag syntax (<ArticleCard />), allowing React to control function execution and lifecycle management.
  • Component Purity: The architectural contract that a component function must calculate its output without mutating external variables or causing side effects during render.

Beyond the basics

  • JSX compiler transform specification: Modern React uses the react/jsx-runtime automatic transform, where <ArticleCard /> compiles to _jsx(ArticleCard, {}) and <article /> compiles to _jsx("article", {}) (see react.dev/learn/your-first-component).
  • Component purity and idempotent rendering: React expects component functions to be pure calculations; given the same inputs, they must always return the exact same JSX without modifying preexisting variables outside their scope (see react.dev/learn/keeping-components-pure).
  • The render tree and component instances: When you declare <ArticleCard /> in JSX, React creates an in-memory element descriptor; it does not instantiate a persistent object until it reconciles the render tree (see react.dev/learn/understanding-your-ui-as-a-tree).
  • Automatic Semicolon Insertion (ASI) in return statements: JavaScript automatically inserts a semicolon after a bare return keyword if followed by a line break, returning undefined unless wrapped in parentheses (see react.dev/learn/writing-markup-with-jsx).
  • Custom HTML elements vs React components: While HTML Web Components use hyphenated lowercase names (<article-card>), React components require PascalCase (<ArticleCard>) to compile into direct function references (see react.dev/learn/your-first-component).

Summary

Architectural Takeaways & Decision Matrix

❒ Component Capitalization

➔ ALWAYS name component functions with PascalCase (ArticleCard) so the JSX compiler emits a function identifier.

➔ NEVER name component functions with lowercase letters (articleCard) because the compiler treats lowercase tags as native HTML strings.

➔ IF a component tag renders blank with zero console errors THEN check that the function and tag begin with a capital letter.

❒ Declarative Invocation

➔ ALWAYS mount components using JSX tag syntax (<ArticleCard />) to preserve component identity in React DevTools.

➔ NEVER call component functions directly with parentheses (ArticleCard()) because this bypasses React's component tree.
