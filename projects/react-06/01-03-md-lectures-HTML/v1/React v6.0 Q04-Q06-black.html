Interview Question

CORE

What is JSX, what syntax rules must every snippet follow, and how do Fragments group elements without wrapper nodes?

Imagine this scenario:

  1. An editor on The National Times copies formatted wire copy into a new story component.
  2. The wire copy contains an unclosed image tag, an adjacent headline, and summary text.
  3. The developer pastes the markup directly into the component return statement.

  5. The development server halts, blocking the newsroom team from previewing breaking wire alerts.

Permissive Browsers vs Strict Compilers

In plain HTML, web browsers are remarkably forgiving. Browsers allow unclosed void tags like <img> or <input>. Browsers also permit multiple adjacent elements at the top level of a document. If you paste raw HTML markup into a standard .html file, the browser parses the text and paints the page.

When a developer pastes raw HTML into a React component function, the build tool halts immediately with fatal syntax errors.

Look at the naive HTML paste attempt below:

2 <img src="/wire-photo.jpg">
3 <h2>Breaking Dispatch</h2>
4 <p class="alert-text">Live news feed.</p>
5);

When this snippet runs through the compiler, the build tool crashes immediately. Notice the syntax errors: an unclosed <img> tag and adjacent sibling elements without an enclosing parent.

The compiler crashes because a JavaScript function cannot return multiple values. Writing return a, b evaluates both expressions but returns only the second value. Furthermore, JSX compiles into _jsx() function calls. Every _jsx() call represents a single element descriptor. You cannot pass two separate expressions to a single return statement without a wrapping structure.

Interview Tip

To impress the interviewer: When asked to explain JSX, do not call it "HTML inside JavaScript." State that JSX is a strict syntax extension that compiles into regular JavaScript function calls (_jsx()). Because functions can only return a single value, every JSX snippet requires a single root element.

Principles of React: The Core Laws of JSX Grammar

To prepare for any technical interview, we must separate theory from application and establish the nine fundamental laws governing the React compiler. In JSX, HTML markup strings do not exist. Every tag, attribute, inline style, and comment is transformed into JavaScript function calls and plain JavaScript objects. We formalize these rules into nine standalone principles.

PRINCIPLE 1

Always Return Exactly One Root Element

You must ensure every component return statement produces exactly one root element (because JavaScript functions can only return a single value).

We should do this:
return (<div><img /><h2 /></div>);
We should not do this:
return (<img /><h2 />);

A React component is a standard JavaScript function. In JavaScript, a return statement can only return a single value or expression. When you write two adjacent tags at the root level, JavaScript cannot evaluate them as a single expression. Under the hood, JSX compiles into _jsx(type, props) function calls. Just as you cannot return two separate function calls without wrapping them in an array or container object, you cannot return adjacent JSX tags.

PRINCIPLE 2

Group Siblings with React Fragments to Avoid Extra DOM Nodes

React Fragment ghost container that groups child tags in memory without creating a physical DOM node

You should group adjacent sibling elements using a React Fragment (<>...</>) rather than an extra <div> (satisfying the single-root rule without injecting wrapper nodes that break CSS Flexbox and Grid layouts).

It is best practice to do this:
return (<><img /><h2 /></>);
Instead of doing this:

Wrapping elements in an extra <div> satisfies the JavaScript single-expression rule, but it inserts an unnecessary physical node into the browser DOM. This wrapper adds DOM memory overhead and disrupts CSS parent-child layout relationships like Flexbox and Grid. React solves this dilemma with the React Fragment shorthand (<>...</>).

The compiler transforms <>...</> into _jsx(Fragment, { children: [...] }) React evaluates the child elements in memory and mounts them directly into the host container, creating zero wrapper DOM nodes.

⚡ IN THE WILD

Why does a wrapper div break your CSS Flexbox layout? When developers hit the single-root error, their instinctive reflex is wrapping everything in a <div>. While this satisfies the compiler, it often destroys layout styling. In CSS Flexbox and Grid, layout properties apply exclusively to direct child elements. If a parent container declares display: flex; gap: 16px;, its direct children become flex items. Placing an extra <div> wrapper around your siblings turns those elements into grandchildren. The flex container now sees only one child: the wrapper div. Your flex row layout collapses into a single vertical block, and gap spacing between items vanishes. React Fragments solve this by satisfying the compiler without creating a physical DOM wrapper.
PRINCIPLE 3

Always Close Every Tag Explicitly

You must explicitly close every JSX tag using a matching closing tag or a self-closing trailing slash (preventing unclosed void elements like <img> from halting the compiler).

We should do this:
<img src="/photo.jpg" alt="Photo" />
We should not do this:
<img src="/photo.jpg" alt="Photo">

In HTML5, browser parsers maintain hardcoded lists of void elements like <img>, <input>, <br>, and <hr> that cannot accept children, permitting closing slashes to be omitted. JSX, by contrast, enforces strict XML grammar. The compiler builds an Abstract Syntax Tree where every opening token <tag> must have an explicit matching boundary, either via a closing tag </tag> or a self-closing trailing slash <tag />. Omitting the trailing slash halts compilation instantly.

PRINCIPLE 4

Write className and htmlFor to Match Native DOM Properties

native browser DOM property names live properties on element objects in browser memory (e.g. node.className)

You must write HTML attributes that collide with JavaScript reserved keywords using their native browser DOM property names (writing className instead of class, and htmlFor instead of for).

We should do this:
<div className="card">
We should not do this:
<div class="card">

To understand this rule in an interview, you must distinguish between three separate layers of the web platform:

  1. HTML Attributes (Markup Text): In raw HTML documents, class="card" and for="email" are static markup attributes parsed as plain text strings.
  2. JavaScript Reserved Keywords (Language Grammar): In ECMAScript, words like class (used to declare classes) and for (used to declare loops) are reserved keywords. In early JavaScript engines, using reserved words in dot-notation (element.class or element.for) triggered syntax errors.
  3. Browser DOM Properties (Living Objects): When a browser parses HTML, it instantiates living JavaScript objects in memory (such as HTMLDivElement or HTMLLabelElement). To avoid keyword collisions in JavaScript, the original 1998 W3C DOM specification explicitly mapped the class attribute to the property element.className, and the for attribute to element.htmlFor.

React does not invent className or htmlFor. When JSX compiles into _jsx("div", { className: "card" }) React updates the browser by setting the native DOM property directly (domNode.className = "card"). Because JSX operates at the level of JavaScript objects rather than raw HTML text strings, it aligns with native browser DOM properties.

PRINCIPLE 5

Write Multi-Word Attribute Names in camelCase

You must write all multi-word JSX attribute names in camelCase (such as tabIndex and readOnly to align with the browser's native DOM property interfaces).

We should do this:
<input tabIndex={0} readOnly={true} />
We should not do this:
<input tabindex="0" readonly>

This rule is not an arbitrary React design preference—it is the exact same DOM property alignment law established in Principle 4. In raw HTML documents, attribute parsing is case-insensitive, allowing developers to write <input tabindex="0" readonly autofocus> as uncapitalized text strings. However, in the browser's native JavaScript DOM API, the HTMLInputElement interface has defined these properties in camelCase since the initial W3C specifications: input.tabIndex, input.readOnly, and input.autoFocus. Because React maps JSX attributes directly to properties on native DOM nodes, it adheres strictly to the browser's established camelCase interface properties.

PRINCIPLE 6

Pass Inline Styles as JavaScript Objects, Never Text Strings

You must pass inline element styles as JavaScript objects with camelCase keys using double curly braces (writing style={{ color: 'red' }} instead of raw CSS text strings).

We should do this:
<span style={{ color: 'red' }}>
We should not do this:
<span style="color: red;">

Candidates frequently face two core interview questions regarding JSX inline styles:

  1. Why the double curly braces style={{ ... }}? There is no special "double-brace" syntax in React. The outer pair of braces {} is the JSX escape delimiter that switches the parser from markup mode into JavaScript expression mode. The inner pair { color: 'red', fontWeight: 700 } is simply a standard JavaScript object literal passed as the value.
  2. Why camelCase keys like fontWeight instead of font-weight? In the browser DOM, an element's inline styling is exposed as an instance of CSSStyleDeclaration (element.style). In JavaScript, writing element.style.font-weight is parsed as a subtraction expression (element.style.font minus the undefined variable weight), triggering a runtime syntax or reference error. The browser DOM API resolved this by mapping CSS hyphenated properties to camelCase JavaScript properties (element.style.fontWeight, element.style.marginTop). React's style prop passes this object directly to the browser's native element.style interface.
PRINCIPLE 7

Write Comments Inside Curly Braces as JavaScript Comments

You must write comments inside JSX markup as JavaScript block comments enclosed within curly braces ({/* comment */}), strictly avoiding raw HTML comment syntax (<!-- -->).

We should do this:
{/* breaking news alert */}
We should not do this:
<!-- breaking news alert -->

The JSX compiler operates as a two-state tokenizer: Markup Mode and JavaScript Mode. In Markup Mode, raw text characters are treated as literal text children, and encountering an opening angle bracket < immediately signals the parser to evaluate an element tag name. When encountering HTML comment syntax <!--, the tokenizer attempts to parse !-- as an HTML tag identifier, which is illegal syntax and halts compilation instantly. Curly braces {} serve as the explicit lexical boundary that switches the tokenizer into JavaScript Mode, where /* ... */ is safely evaluated as a standard ECMAScript block comment and erased during compilation.

React Principle

*Principle 8: Preserve Hyphens for aria- and data- Attributes You must strictly retain hyphens for aria- and data- attributes* (writing aria-label and data-testid to align with W3C accessibility and DOM dataset specifications).

We should do this: <input aria-label="Search" data-testid="search" />

We should not do this: <input ariaLabel="Search" dataTestId="search" />

A common interview question asks why React converts standard HTML attributes to camelCase DOM properties, yet strictly preserves hyphens for aria-* and data-*. The answer lies in how React commits updates to the browser DOM:

  1. Standard Props use DOM Property Assignment: For standard attributes, React assigns values directly to object properties on the living JavaScript node (domNode.className = props.className domNode.tabIndex = props.tabIndex).
  2. aria-* and data-* use DOM Attribute Assignment: The browser DOM does not define native JavaScript properties like node.ariaLabel. Screen readers (via the browser accessibility tree) and CSS attribute selectors ([data-testid="search-input"]) query the serialized HTML attribute string. Therefore, during DOM mutation, React calls the native browser method: domNode.setAttribute('aria-label', value) and domNode.setAttribute('data-testid', value) Because React relies on setAttribute(), it strictly preserves the official W3C hyphenated attribute names.

PRINCIPLE 9

Capitalize Custom Component Names and Keep HTML Tags Lowercase

You must start custom component names with a capitalized letter (<NewsAlert />) and built-in HTML tags with lowercase (<div>), signaling to the compiler whether to invoke a function or create a DOM element.

We should do this:
<NewsAlert />
We should not do this:
<newsAlert />

When an interviewer asks how the React compiler distinguishes between a built-in browser DOM element and a custom developer component, the answer is the Abstract Syntax Tree (AST) lexical tokenizer:

  1. Lowercase Initials (/^[a-z]/): When a tag identifier begins with a lowercase letter (such as <header> or <div>), the compiler treats it as a built-in HTML tag and emits a string literal: _jsx("header", props). At runtime, React passes that string directly to document.createElement("header")
  2. Capitalized Initials (/^[A-Z]/) or Dot-Notation (<Obj.Component>): When a tag identifier begins with a capital letter (such as <NewsAlert>) or contains property access, the compiler treats it as a scoped JavaScript variable identifier: _jsx(NewsAlert, props). At runtime, React invokes the function: NewsAlert(props).

If you write <newsAlert /> with a lowercase initial, the compiler emits _jsx("newsalert", props). The browser attempts to instantiate an unknown custom element <newsalert>, rendering nothing on the screen and never executing your component function.

Where you will meet this

  1. CSS Grid & Flexbox Layouts: Returning multiple grid or flex items from a child component without breaking layout alignment with extra wrapper divs.
  2. HTML Table Rows & Cells: Returning multiple <td> table data cells from a component without inserting invalid <div> tags inside a <tr>.
  3. Accessible Form Controls: Binding <label htmlFor="..."> to <input id="..." /> while applying aria-label and tabIndex without keyword collision crashes.

Glossary

  • JSX: A syntax extension for JavaScript that allows developers to write XML-like markup that compiles into standard _jsx() function calls.
  • React Fragment: A built-in React component (<>...</>) that groups a list of children without adding extra nodes to the physical browser DOM.
  • Single Root Invariant: The compiler requirement that every component return statement must resolve to a single JavaScript expression.
  • Self-Closing Tag: A tag that closes itself with a trailing slash (<img />, <input />), mandatory in JSX for void HTML elements that have no children.
  • DOM Property Mapping: The convention where JSX attributes match browser DOM object properties (such as className and htmlFor) to avoid collisions with JavaScript reserved words.
  • Tag Casing Rule: The compiler convention where lowercase tags denote browser DOM strings and capitalized tags denote in-scope component functions.

Beyond the basics

  • JSX compilation under the hood: The JSX transform turns <><h1>Hello</h1></> into _jsx(Fragment, { children: _jsx("h1", { children: "Hello" }) }) using the React Fragment symbol (see react.dev/learn/writing-markup-with-jsx).
  • Fragments with keys in mapped collections: While the shorthand <>...</> syntax does not accept attributes, the explicit <React.Fragment key={id}> syntax allows passing keys when rendering lists of fragments (see react.dev/learn/rendering-lists).
  • DOM property mapping: JSX attributes closely match browser DOM properties rather than HTML attribute strings; for example, class becomes className and for becomes htmlFor (see react.dev/learn/writing-markup-with-jsx).
  • Single-expression returns in JavaScript: A JavaScript return statement can only evaluate and return one value; wrapping multiple expressions in parentheses and a Fragment creates a single compound expression (see react.dev/learn/writing-markup-with-jsx).
  • Void elements and strict XML rules: In HTML5, void elements like <input>, <img>, and <br> can omit closing slashes, but JSX strictly follows XML rules where all tags must be explicitly closed (see react.dev/learn/writing-markup-with-jsx).

Lecture 5: JavaScript Expressions in JSX with Curly Braces

Interview Question

CORE

How do you use JavaScript expressions inside JSX with curly braces, what grammar constraints separate expressions from statements, and how do attributes differentiate static strings from dynamic bindings?

Imagine this scenario:

  1. Clara builds a journalist profile card for The National Times investigative team.
  2. She declares variables in her component for the reporter name, read time, and avatar path.
  3. Clara writes the variable names directly between tags and inside attribute quotes.
  4. Why does the browser print the word headline and display a broken image icon?
  5. Readers see raw variable names instead of author names, and profile pictures fail to load.
  6. Static JSX treated the variable names as plain string characters.
  7. Today, you will master the JSX curly brace window to evaluate live JavaScript expressions.

Literal Text and Broken Image Paths

In standard HTML, text written between opening and closing tags is always treated as a static string. If you write <h2>authorName</h2> the browser displays the literal letters a-u-t-h-o-r-N-a-m-e. Similarly, if you write <img src="avatarUrl" /> the browser attempts to fetch a file named literally avatarUrl from the web server. HTML has no concept of JavaScript memory or local variables.

When a developer declares variables inside a component and writes their identifiers directly into JSX markup, the output remains static.

The JSX compiler follows a strict parsing boundary. Interview Tip

To impress the interviewer: When asked how curly braces work in JSX, do not say "they let you put JavaScript inside HTML." State that JSX is a strict syntax extension that compiles into function calls (_jsx()). Curly braces serve as the lexical escape boundary that switches the tokenizer from Markup Mode into JavaScript Evaluation Mode. The enclosed JavaScript expression is evaluated during render, and its resolved value is passed directly as an argument to the element's descriptor.

⚡ IN THE WILD

Why can you not place an if statement inside JSX? When developers need conditional rendering, their initial instinct is often writing {if (isSenior) { ... }} inside their JSX markup. This triggers a fatal compiler error. Why? Because curly braces accept JavaScript expressions, but strictly reject JavaScript statements. An expression produces a concrete value that can be passed as an argument to a function (_jsx("span", { children: value })). A variable, arithmetic calculation, or ternary operation (isSenior ? 'Senior' : 'Staff') all evaluate to a single value. An if statement or a for loop produces no value; it is a control-flow statement. You cannot pass a statement as a function argument in JavaScript. To branch inside JSX, you must use expressions that resolve to values.

Principles of React: The Core Laws of JSX Expressions

To prepare for any technical interview, we must separate theory from application and establish the fundamental laws governing how the React compiler parses, evaluates, and projects JavaScript code inside JSX. In React, markup is not a separate templating language—it is pure JavaScript execution. We formalize these rules into six standalone principles.

PRINCIPLE 1

Wrap Dynamic JavaScript in Curly Braces

curly braces syntax boundary that switches the compiler from HTML parsing to executing live JavaScript

You must wrap JavaScript expressions in curly braces ({}) to switch the compiler from static markup mode to live JavaScript evaluation.

We should do this:
<h2>{authorName}</h2>
We should not do this:
<h2>authorName</h2>

In JavaScript, grammar is strictly partitioned into expressions and statements. Without curly braces, the JSX tokenizer treats all characters between tags as literal text children. When the compiler encounters an opening curly brace {, it suspends markup parsing and activates standard ECMAScript evaluation. The identifier authorName is looked up in the component's lexical scope, and its current string value is passed directly to the element's children descriptor: _jsx("h2", { children: authorName })

PRINCIPLE 2

Pass Only Value-Producing Expressions Inside Curly Braces

JavaScript expressions that resolve to a value code that calculates a result you can pass or store (like a ternary or addition)
control-flow statements code that guides execution flow (like if, for, or while) without producing any value

You must place exclusively JavaScript expressions that resolve to a value inside curly braces, strictly avoiding control-flow statements.

We should do this:
{isSenior ? 'Senior' : 'Staff'}
We should not do this:
{if (isSenior) { 'Senior' }}

In JavaScript, grammar is strictly partitioned into expressions and statements. An expression produces a value (4 + 2, formatDate(), user.name, ternary conditions). A statement executes an imperative action but produces no value (if, for, while, switch, variable declarations). Because JSX compiles into function calls (_jsx(type, props)), every child and attribute must evaluate to a valid argument value. Writing a statement inside curlies violates ECMAScript argument syntax, causing the compiler to halt instantly.

PRINCIPLE 3

Never Wrap Curly Braces in Quotes for Attributes

You must delimit JSX attributes either with quotes for static strings or with bare curly braces for dynamic expressions, never wrapping curly braces inside quotes (which passes the literal text string "{avatarPath}").

We should do this:
<img src={avatarPath} />
We should not do this:
<img src="{avatarPath}" />

In JSX attributes, quotes and curly braces are mutually exclusive delimiters. Double quotes (src="...") instruct the compiler that the enclosed content is an immutable string literal. Curly braces (src={...}) instruct the compiler that the value is a dynamic JavaScript expression. Wrapping curly braces inside quotes (src="{avatarPath}") treats the braces as literal characters. The browser attempts to fetch the literal file path "/{avatarPath}" from the server, triggering a 404 network failure.

PRINCIPLE 4

Use Double Curly Braces to Pass Inline Objects

two pairs of curly braces outer pair evaluates JavaScript; inner pair builds the object literal

You must write two pairs of curly braces when passing an inline object to a prop—the outer pair opens the evaluation window, while the inner pair constructs the object literal.

We should do this:
<b style={{ color: 'teal' }}>LIVE</b>
We should not do this:
<b style={ color: 'teal' }>LIVE</b>

Candidates frequently misunderstand style={{ ... }} as a special "double-brace syntax" invented by React. There is no double-brace syntax in React. The outer pair of curly braces { ... } is the standard JSX escape delimiter that opens the JavaScript evaluation window. The inner pair { color: '#0e7490', fontWeight: 700 } is simply a standard JavaScript object literal. Omitting the inner braces causes the compiler to parse the contents as an invalid block statement with labels, throwing a syntax error.

PRINCIPLE 5

Convert Falsy Conditions to Explicit Booleans to Prevent Rogue Zeros

You must use explicit boolean comparisons (unreadCount > 0) when conditionally rendering with && (because the number 0 renders visibly as text, while booleans render nothing on the page).

It is best practice to do this:
{count > 0 && <span>{count}</span>}
Instead of doing this:
{count && <span>{count}</span>}

To make conditional rendering effortless, React deliberately ignores booleans, null, and undefined inside JSX children. Writing {true}, {false}, or {null} outputs nothing to the DOM. However, JavaScript numbers are treated as meaningful text content. In JavaScript, the logical AND operator (&&) returns its first falsy operand without converting it to a boolean. If unreadCount is 0, the expression unreadCount && <Badge /> evaluates to the number 0. React renders this number directly to the screen, creating a rogue "0" on the page. To prevent numeric leaks, always convert the condition to an explicit boolean using a comparison operator (unreadCount > 0).

Principle 5: Falsy Numeric Leak vs Explicit Comparison

You must evaluate text expressions immediately during component rendering, while passing deferred function references for event handlers.

We should do this:

We should not do this:

Every expression placed inside curly braces is executed synchronously when the component function runs. Inline arithmetic (readMinutes * 60) and pure formatting functions calculate their results during the render phase and project the returned value into the virtual DOM tree. By contrast, wrapping a text calculation in an arrow function ({() => ...}) creates a function object that React does not render. Function references are strictly reserved for event handler props (onClick={handleClick}).

Glossary

  • JSX Evaluation Window: The syntax construct {} that temporarily steps out of static JSX markup mode to evaluate an inline JavaScript expression.
  • JavaScript Expression: Any valid unit of JavaScript code that resolves to a single value, such as a variable, arithmetic calculation, or ternary operation.
  • Control-Flow Statement: A unit of JavaScript code that executes an action but produces no value (if, for, while), strictly forbidden inside JSX curlies.
  • Pure Attribute Delimitation: The language rule requiring JSX attributes to use either quotes for static strings or curly braces for dynamic expressions.
  • Object Literal Pass-Through: The syntax pattern where an outer curly brace pair opens the JSX window and an inner pair defines a JavaScript object (style={{ ... }}).
  • Falsy Numeric Leak: The runtime defect where the falsy number 0 in a logical AND expression (0 && <Badge />) evaluates to 0 and renders as visible text on the page.

Beyond the basics

  • JSX curly braces compiler output: The expression {readMinutes * 60} compiles directly to the function argument _jsx("p", { children: [readMinutes * 60, " seconds read"] }) (see react.dev/learn/javascript-in-jsx-with-curly-braces).
  • Expressions vs statements in language specifications: In the ECMAScript specification, expressions evaluate to a value, while statements control execution flow; JSX child positions only accept expressions because function calls require argument values (see react.dev/learn/javascript-in-jsx-with-curly-braces).
  • Objects as JSX children: React cannot render raw JavaScript objects directly inside text curlies ({userObject}); attempting to do so throws a runtime error, requiring you to access primitive properties like {userObject.name} (see react.dev/learn/javascript-in-jsx-with-curly-braces).
  • Double curlies for inline style objects: When applying inline styles in JSX, you write style={{ color: 'red' }}; the outer braces open the evaluation window, and the inner braces declare a JavaScript object literal (see react.dev/learn/javascript-in-jsx-with-curly-braces).
  • Boolean and nullish rendering: React treats true, false, null, and undefined as empty values inside curly braces, rendering nothing to the DOM, which enables conditional rendering shortcuts like {isPublished && <Badge />} (see react.dev/learn/conditional-rendering).

We will progress across four sequential steps: inspecting the host HTML document in index.html, constructing the root component in src/App.jsx, declaring the child banner component in src/components/BreakingBanner.jsx and establishing the concurrent mounting bridge in src/main.jsx. The two-step initialization creates a concurrent Fiber root container and safely projects declarative JSX into physical DOM pixels.

Where you will meet this

  1. Single-Page Application Bootstrapping: Initializing the root component of a Vite or Webpack client-side application.
  2. Multi-Root Micro-Frontends: Mounting independent React widgets into separate DOM containers on the same legacy page.
  3. Modal and Portal Targets: Creating secondary mounting roots for floating dialogs and fullscreen overlays outside the primary tree.
  4. Testing Environments: Mounting component trees into isolated JSDOM containers during unit and integration test runs.

Glossary

  • createRoot: The official factory function from react-dom/client that initializes a concurrent React root container attached to a physical DOM node.
  • Concurrent Root: A React root instance that supports React 19 concurrent features, interruptible rendering, and priority scheduling.
  • Fiber Root: The internal React data structure that tracks the root container, reconciliation queue, and active component tree in memory.
  • Root Container DOM Node: The physical HTML element (typically <div id="root">) that houses the mounted React component tree and receives delegated synthetic events.
  • Event Delegation: The architecture where React attaches a single event listener per event type to the root container rather than individual DOM nodes.
  • Component-DOM Decoupling: The architectural practice of keeping component functions pure and free of direct DOM queries or mounting APIs.

Beyond the basics

  • The two-step createRoot lifecycle: Calling createRoot(container) creates a FiberRootNode in memory, while calling root.render(element) schedules the initial concurrent render pass (see react.dev/reference/react-dom/client/createRoot).
  • Root unmounting mechanics: Calling root.unmount() destroys the entire React tree, unbinds root event listeners, and clears the container element (see react.dev/reference/react-dom/client/createRoot#root-unmount).
  • Hydration with hydrateRoot: When server-rendered HTML exists in the container, applications use hydrateRoot(domNode, <App />) instead of createRoot to attach event listeners without destroying existing markup (see react.dev/reference/react-dom/client/hydrateRoot).
  • Multiple roots on a single page: A single HTML document can host multiple independent createRoot containers, enabling progressive migration of legacy server templates (see react.dev/reference/react-dom/client/createRoot#rendering-a-page-partially-built-with-react).
  • Strict Mode verification: Wrapping the root element in <StrictMode> causes React to double-invoke component render passes in development to catch impure side effects (see react.dev/reference/react/StrictMode).

Architectural Takeaways & Decision Matrix

❒ Root Initialization & Mounting

➔ ALWAYS import createRoot from react-dom/client when mounting React 19 applications into the browser DOM.

➔ NEVER use deprecated ReactDOM.render from react-dom because it disables concurrent rendering and triggers console warnings.

➔ IF querying the DOM container THEN verify that the element exists before calling createRoot to avoid null pointer crashes.

❒ Component Separation & Delegation

➔ ALWAYS keep component files purely declarative and free of direct DOM queries like document.getElementById.

➔ NEVER attach manual DOM event listeners inside components when React's root event delegation handles them automatically.
