Lecture 14: Component Memory with useState

Interview Question

CORE

Why do ordinary variables forget their values between renders, and how does useState remember?

Imagine this scenario:

  1. Leo opens his editor at The National Times to add an interactive reader counter to the morning feed.
  2. A reader clicks the like button to recommend a breaking news story to colleagues.
  3. Leo increments a local variable on each click to update the displayed recommendation total.
  4. Why does the number on the screen stay permanently stuck at zero?
  5. Readers click repeatedly, but their recommendations never appear on the page.
  6. The variable resets on every render, and React never hears about your change.
  7. Today, we give our components true memory that survives every screen update.

The Friction of Ephemeral Variables in Component Functions

Every web application exists to present dynamic data. Modern interfaces must also respond when users interact with the screen. Readers click reaction buttons, toggle bookmarks, and submit feedback forms. In earlier lessons, you learned that React components are JavaScript functions. In Lecture 13, you wired user clicks by passing event handler functions to onClick. When developers begin adding dynamic numbers to their components, they frequently bring programming habits from traditional scripting.

Leo sits at his editor on The National Times to build src/components/StoryCard.jsx. He wants each article card to display a like count. When a reader clicks the Like button, the displayed count should increase by one.

An engineer often declares a local variable like let likes = 0 inside the component body. Inside the click handler, they write likes = likes + 1, expecting React to display the updated number. But when they open their browser and click the button, nothing changes on the screen. The counter remains permanently stuck at 0 likes.

5 }

Why did the screen fail to update? When you click the button, handleLike executes and increments likes in JavaScript memory. In the browser console, console.log prints 1, 2, and 3. The variable changes, but React never updates the screen. Two distinct platform rules explain this failure:

First, assigning a local variable does not trigger a render. React does not listen to plain variable assignments. React only updates the screen when it executes your component function again to compute fresh JSX. Because changing likes sends no signal to React, React never schedules a render pass.

Second, local variables do not survive between renders. Whenever something else causes StoryCard to render again, React calls the component function from line 1. The statement let likes = 0 runs from scratch, creating a brand-new local variable set to 0. Any accumulated changes are erased instantly.

⚡ IN THE WILD

Why does assigning a variable never update the screen?

In React, interfaces update only when React calls your component function again to compute new JSX markup. When you increment a local variable (likes = likes + 1), you modify an untracked memory slot. React never schedules a render pass, so the browser DOM remains untouched. Furthermore, whenever the component does render again, the function runs from the top. The variable resets back to its starting value. To update the screen, declare a state variable with useState and update it through its setter.

Component Memory and the Execution Cycle

To build interactive interfaces, we must understand how React executes component functions. In standard JavaScript, functions are temporary calculations. You call a function, it allocates local variables in memory, returns a result, and cleans up its scope. In earlier lessons, you saw that React components follow this exact functional model: StoryCard receives props, executes its body, and returns a JSX descriptor tree.

If React treated components strictly as ordinary functions, every interactive feature would lose its data. Search fields would wipe their text, modals would snap shut, and reaction counters would reset to zero. Components require component memory: private data that survives across renders.

React provides this memory through the useState Hook. A Hook is a special function provided by React that lets your component connect to React runtime features. When you call useState(0), you ask React to hold a piece of state initialized to 0 for this component. React reserves a memory cell outside the component function and returns an array containing exactly two items: the current state value for this render, and a setter function that updates it.

When declaring state, developers choose between direct array indexing and array destructuring:

  • Option 1 (The Foundational Way: Direct Array Indexing): Assign the return value of useState to a single variable and read items using numeric indexes.
  • Option 2 (The Modern Idiomatic Way: Array Destructuring Assignment): Unpack the value and setter directly into distinct variables using JavaScript array destructuring.

First, examine Option 1 using direct array indexing:

Option 1: The Foundational Way (Direct Array Indexing)

3 const likes = likesState[0];
4 const setLikes = likesState[1];

6 <button type="button" onClick={() => setLikes(likes + 1)}>

In Option 1, likesState stores the raw array returned by useState(0). Index 0 holds the current value (0), and index 1 holds the setter function (setLikes). While this reveals the underlying data structure React returns, reading properties via numeric indexes creates noisy boilerplate across components.

Next, examine Option 2 using modern JavaScript array destructuring:

7 );

In Option 2, array destructuring unpacks the two items directly at the point of declaration. The square brackets on the left of the assignment tell JavaScript to store item 0 in likes and item 1 in setLikes. This is the universal standard in React development. By community convention, developers name the pair [something, setSomething] to make reading and updating state immediately clear.

Principles of React: The Core Laws of Component State

When preparing for senior technical interviews, candidates must clearly explain why local variables forget their values between renders, how useState preserves memory outside the component function, how React matches multiple Hooks by call order, why each rendered component instance owns isolated state, and how to optimize expensive initial state. To master these concepts, we formalize the six governing principles of component state:

PRINCIPLE 1

Assigning a Local Variable Never Triggers a Render

React updates the screen only when it renders a component again to calculate fresh JSX markup. Assigning a new value to a local variable changes memory that React does not track, so React never schedules a render. When you increment a local variable inside an event handler, the variable changes in the background while the screen keeps showing the old value.

In browser JavaScript, assigning a value modifies a local memory slot allocated during that specific function execution. When you write likes = likes + 1, the CPU increments the integer stored in that local slot. However, React does not wrap local variables in proxies or listen to memory mutations. The React rendering engine operates on a pull model: it only calls a component when an interaction or parent update explicitly requests a render pass.

Because a plain assignment sends zero signal to React, the component never re-renders, no fresh JSX is produced, and the browser DOM remains completely untouched.

Local Assignment Never Triggers Render
1export default function StoryCard({ title }) {
2 let likes = 0;
Local variable in function scope
3 function handleLike() {
4 likes = likes + 1;
Mutates local variable silently
5 console.log('likes =', likes);
6 }
7 return <button type="button" onClick={handleLike}>{likes} likes</button>;
8}

When a reader clicks the button three times, the console prints clicked, likes = 1, clicked, likes = 2, and clicked, likes = 3. But the screen never updates because React was never asked to render.

PRINCIPLE 2

Component Calls Run from the Top and Reset Local Variables

A React component is a JavaScript function that React calls anew every time it renders. Each render executes the component body from the first line, allocating all local variables fresh with their initial values. When a render occurs, previous local variables disappear, so any value stored in a local variable resets back to its starting declaration.

When a component renders, JavaScript executes the function body from line 1. The statement let likes = 0 runs every time. Even if another interaction (such as toggling a bookmark) causes React to render the card, the function runs from the top. When the function returns, its execution context closes and its local variables are destroyed.

In Lecture 12, you learned that React components must remain pure calculations that can be called repeatedly. Because React may call a component function at any time, local variables cannot preserve state across calls.

Local Variables Reset on Subsequent Render
1export default function StoryCard({ title }) {
2 let likes = 0;

5 likes = likes + 1;
Increments variable in current call scope
6 }
7 return <button type="button" onClick={handleLike}>{likes} likes</button>;
8}

If the reader clicks Like three times, likes becomes 3 in memory. But the moment any re-render occurs, StoryCard runs again from line 1. The console logs render, likes = 0, and the next click starts counting from 1 again.

PRINCIPLE 3

Store Persistent Interactive Data in State and Update It Through the Setter

state variable a value held by React that persists across component renders
Hook a special function starting with use that lets a component tap into React features
setter function a function returned by useState that updates state and asks React to render

When data must survive between renders and update the screen, declare a state variable by calling the useState Hook. React returns a pair containing the current value and a setter function. We update the value exclusively by calling the setter with the next value, which stores the data inside React and requests a fresh render.

We should do this:
const [likes, setLikes] = useState(0);
setLikes(likes + 1);
Updates React memory and requests a fresh render
We should not do this:
const [likes, setLikes] = useState(0);
likes = likes + 1;
Throws TypeError: Assignment to constant variable

To preserve data across renders, React stores state values outside the component function in internal memory cells. When you call useState(0), React checks whether an existing value exists for this component cell. If not, it stores 0. It returns that value and a setter function (setLikes).

Calling setLikes(1) does two things: it stores 1 in React's internal cell, and it queues a render pass. During the next render, React calls StoryCard again. This time, useState(0) looks at its internal cell, finds 1, and returns [1, setLikes]. The JSX calculates markup using 1, and the screen updates to display 1 likes.

Notice that state variables are declared as const. You cannot assign directly to a state variable; doing so throws TypeError: Assignment to constant variable. Calling the setter is the only door to updating state.

Working State Counter with useState

2export default function StoryCard({ title }) {
3 const [likes, setLikes] = useState(0);
State retained across renders
4 function handleLike() {
5 setLikes(likes + 1);
Setter stores next value and requests render
6 }
7 return <button type="button" onClick={handleLike}>{likes} likes</button>;

Some developers attempt to move let likes = 0 outside the component function at module scope. While a module-level variable survives renders, assigning it still never tells React to render. Even worse, if you mount two <StoryCard /> elements on screen, both cards share that single variable, corrupting independent counts.

PRINCIPLE 4

React Stores State Outside the Function and Matches Calls by Order

call order the exact sequential order in which a component invokes its Hooks on each render

State does not live inside the component function; React holds state externally in an ordered list tied to that component. On the initial render, React saves the initial value for each useState call. On every subsequent render, React ignores the argument and returns the stored value matching that call's position in the execution sequence.

A common mystery for developers is: "If useState(0) executes on every render, why doesn't likes reset to 0?" The answer lies in where state lives. When React mounts a component, it creates an internal array of state cells for that specific component in the tree. Before rendering, React initializes an internal index pointer to 0.

When your component calls useState(0) the first time, React notes index 0, records 0, and increments the index to 1. If your component makes a second call, useState(false), React notes index 1, records false, and increments the index to 2.

On subsequent renders, React resets its internal pointer to 0. Call 1 asks for state; React checks index 0, finds the existing value (e.g. 2), returns it, and advances the pointer. Call 2 asks for state; React checks index 1, finds true, returns it, and advances the pointer.

Because React matches state calls strictly by their sequential call order, Hooks must always be called at the top level of the component, never inside conditional branches or loops (a rule explored in Lecture 37).

Multiple State Variables Matched by Order
1export default function StoryCard() {
2 const [likes, setLikes] = useState(0);
Slot 0 in React memory
3 const [saved, setSaved] = useState(false);
4 return (
5 <section>
6 <button onClick={() => setLikes(likes + 1)}>{likes} likes</button>
7 <button onClick={() => setSaved(!saved)}>Bookmark</button>
8 </section>
9 );
Slot 1 updated by setter
10}

On initial render, React initializes both slots: 0 and false. Clicking Like updates slot 0 without affecting slot 1. Clicking Bookmark updates slot 1 without resetting slot 0. Each call maintains its own state independently.

PRINCIPLE 5

State Is Completely Private and Isolated to Each Component Instance

component instance a specific copy of a component mounted at a distinct location in the UI tree

State belongs to a specific component instance at its exact position in the render tree, not to the component function definition. When you render multiple copies of the same component side by side, React creates an independent memory record for each one. Updating state in one instance re-renders only that instance and leaves all sibling instances untouched.

In JavaScript, a module-level variable is shared by all functions in that file. In contrast, React state is tied to the physical component instance in the UI tree. If you render <StoryCard /> twice inside App.jsx, React instantiates two distinct nodes in the tree: Instance A and Instance B.

Instance A receives its own private array of state cells (likes = 0, isSaved = false). Instance B receives a completely separate private array of state cells (likes = 0, isSaved = false). When a user clicks Like on Instance A, Instance A's setter fires, updating only Instance A's memory and re-rendering only Instance A. Instance B is completely unaware of the interaction and retains its original count.

The parent component App cannot read or modify the private state of either card directly. In Lecture 23, you will learn how to lift state upward when two components genuinely need to share synchronized data.

PRINCIPLE 6

Pass an Initializer Function for Expensive Initial State

initializer function a function passed to useState that React calls only on the initial render to compute starting state

React reads the useState argument only on the first render and ignores it on all later renders. However, if you pass a function call like useState(calculateTotal()), JavaScript runs that function on every render anyway. When computing an initial value is expensive, pass an initializer function reference (useState(calculateTotal)) so React runs it strictly on the initial render.

It is best practice to do this:
const [likes, setLikes] = useState(getInitialLikes);
React calls function once on initial render
Instead of doing this:
const [likes, setLikes] = useState(getInitialLikes());
Runs expensive calculation on every render

When JavaScript executes code, it evaluates function arguments before calling the outer function. If you write useState(getInitialLikes()), JavaScript executes getInitialLikes() first, and passes its return value into useState.

On the initial render, React uses that return value. On the second and third renders, React already has the stored state in its internal cell, so it completely ignores the argument you passed. However, the calculation already ran and consumed CPU time! If getInitialLikes reads from localStorage or parses thousands of records, your component suffers unnecessary performance overhead on every click.

When you pass the function reference without parentheses (useState(getInitialLikes)), you hand the recipe to React. React checks if this is the initial render; if it is, React calls getInitialLikes() once. On subsequent renders, React skips calling the function entirely. Note that in development mode under StrictMode, React calls initializer functions twice on mount to verify that they are pure calculations with zero side effects.

Initializer Function Execution Proof
1function getInitialLikes() {
2 return 10;
Executed only on initial mount
3}
4export default function StoryCard() {
5 const [likes, setLikes] = useState(getInitialLikes);
6 function handleLike() {
7 setLikes(likes + 1);
Next render skips initializer call
8 }
9 return <button onClick={handleLike}>{likes} likes</button>;
10}

With useState(getInitialLikes), clicking Like twice prints the proof log only on the initial mount. With useState(getInitialLikes()), clicking Like twice prints the proof log three times.

Component Summary

App

The reading desk shell orchestrates the editorial layout. It mounts two independent StoryCard instances side by side. Notice it deliberately holds zero state for likes or bookmarks, keeping the root container lean. Why? To let child cards manage their own private memory autonomously.

StoryCardtitle={title}

The interactive story card owns two private state variables: likes and isBookmarked. It receives its headline through props from App. Notice it updates memory exclusively through setter functions, triggering local re-renders on user interaction. Why? To isolate reader reactions to individual card instances.

Examine the architectural elegance of this implementation. In a naive approach, an engineer might have used local variables (let likes = 0), resulting in stuck buttons that never update the screen. Or they might have attempted a global module variable, causing every article on the site to share one counter.

By contrast, our React architecture relies on useState. React stores state records outside the function body, matched securely by Hook call order. Each rendered instance of StoryCard retains completely private memory. Clicking Like on the first card updates only that card, leaving the second card at zero.

Where you will meet this

  1. Interactive Reaction Counters and Engagement Metrics: Social cards, news feeds, and comment widgets use integer state (const [likes, setLikes] = useState(0)) to track and display reader reactions in real time without refreshing the page.
  2. Toggle Switches and Accordion Panels: Expanding menus, bookmark buttons, and reading theme toggles use boolean state (const [isOpen, setIsOpen] = useState(false)) to switch visual states on user click.
  3. Controlled Form Inputs and Search Filters: Text search fields and feedback forms store active user input in string state (const [query, setQuery] = useState('')), synchronizing keystrokes directly with React component memory.
  4. Multi-Step Wizards and Tabbed Navigation: Multi-page checkout flows and section switchers track the currently active step (const [activeTab, setActiveTab] = useState('news')), rendering distinct content branches based on state.

Glossary

  • State Variable: A persistent value managed by React that survives across component renders and drives the user interface.
  • Setter Function: A function returned by useState that stores the next state value inside React and schedules a re-render.
  • Hook: A special function provided by React whose name starts with use that allows components to connect to React runtime features.
  • Array Destructuring: A JavaScript syntax pattern using square brackets (const [a, b] = array) to unpack array elements into distinct local variables.
  • Initializer Function: A function passed by reference to useState that React executes only during initial component mounting to compute starting state.

Beyond the basics

  • State snapshots and execution timing: calling a setter does not change the state variable in already running JavaScript code, because state behaves as a fixed snapshot for that render (see Lecture 16, react.dev/learn/state-as-a-snapshot).
  • Updater functions and batching queues: passing an updater function like setLikes(prev => prev + 1) allows multiple pending state updates to be queued and calculated sequentially during the next render pass (see Lecture 17, react.dev/learn/queueing-a-series-of-state-updates).
  • Immutable object and array updates: state should be treated as read-only, replacing nested objects and arrays using object spread or map rather than mutating existing memory (see Lecture 18, react.dev/learn/updating-objects-in-state).
  • Storing information from previous renders: patterns for adjusting state during render by comparing previous prop values without triggering infinite render loops (see Lecture 80, react.dev/reference/react/useState#storing-information-from-previous-renders).
  • The Rules of Hooks: why Hooks must be called exclusively at the top level of component functions and never inside loops, conditions, or nested functions (see Lecture 37, react.dev/reference/rules/rules-of-hooks).
