The Friction of Ephemeral Local Variables

Every web application exists to present content and respond to user actions. In earlier lessons, you learned that React components are functions that execute and return JSX markup. A component function runs from top to bottom, calculates its output, and finishes execution. When the function returns, its local variables disappear from active memory.

However, interactive user interfaces require components to remember decisions over time. To see this in action on The Daily Courier, Nora builds an interactive story card: src/components/StoryCard.jsx. She wants readers to click a Like button to express appreciation for an article. The card should display the current number of likes, starting at zero and increasing by one with each click.

Because she has not yet learned how React manages memory, Nora declares a standard JavaScript variable inside the component function: let likes = 0 She writes a click handler named handleLike that increments likes and attaches it to the button:

Opening the browser reveals a confusing bug. Nora clicks the Like button three times. In the browser developer console, she sees the messages: "likes: 1", "likes: 2", and "likes: 3". The variable is definitely changing in JavaScript memory! Yet on the screen, the button text stubbornly reads "Like (0)". The visual user interface remains completely frozen.

Worse, suppose Nora adds a working bookmark toggle to the card. When she clicks the bookmark button, the card updates to show "Saved". But as soon as the card updates, the Like counter resets back to zero! The next time she clicks the Like button, the console logs "likes: 1" all over again.

This breakdown occurs because ordinary local variables suffer from two critical limitations in React:

  1. Local variable changes do not trigger renders: In React, modifying a local variable like likes = likes + 1 produces no notification signal. React has no idea that data has changed, so it never schedules a render pass to update the DOM.
  2. Local variables do not persist between renders: Every time React renders a component, it calls the component function again from scratch. Each call creates a fresh execution scope. The statement let likes = 0 runs again, wiping whatever number existed during the previous click.

If a developer attempts to solve this by moving the variable outside the component function (such as declaring let globalLikes = 0 at the top of the file), another serious problem emerges. While a module-level variable survives across renders, mutating it still fails to notify React to update the screen. Even worse, if you display five different story cards on your page, all five cards share that same single variable. Clicking Like on one story increments the count for every other story in the newspaper!

⚡ IN THE WILD

Why did changing the like counter leave the screen stuck?

Local variables declared inside a component function exist only during that single function execution. When the function returns JSX, its execution scope finishes and its local variables vanish. Incrementing a local variable changes a value in JavaScript memory, but React receives no update signal, leaving the browser screen frozen on the initial markup. When an unrelated update re-renders the component, the function runs from the top and resets the local variable to zero. To preserve data across renders and notify React to update the display, components must use React's built-in memory system: the useState hook.

Component Memory and the Mechanics of useState

To build interactive applications, components must remember information across user interactions. In React, component-specific memory that persists across renders is called state.

Think of component state as a private notebook or a dedicated shelf in memory. While props represent incoming data passed downward from a parent, state represents internal data that a component creates, owns, and modifies itself. When a reader clicks a like button, selects a tab, or types text into a form input, the component uses state to retain that information across renders.

React provides this capability through a built-in function called useState. When you call useState, you tell React: "I want this component to remember a piece of information."

Where does this state actually live? In standard JavaScript, local variables vanish when a function completes. React solves this by storing state outside your component function entirely. React maintains an internal memory cell associated with that specific component's position in the user interface tree. When your component function runs, it asks React for its stored value. React checks its memory shelf and hands the current value back.

Because useState is the first place in this curriculum where we encounter array destructuring, let us briefly review how this JavaScript feature works.

Array destructuring is a clean JavaScript syntax that unpacks values from an array into separate variables in a single statement. Calling useState(0) returns a JavaScript array containing exactly two items:

  1. The current state value: The first element in the array is the current value stored in React's memory cell. On the initial render, this is the initial value you provided (0).
  2. The setter function: The second element in the array is a function that lets you update the state value and tell React to re-render the component (setLikes).

Writing const [likes, setLikes] = useState(0) unpacks the two items directly. It assigns the first item to a constant named likes and the second item to a constant named setLikes. You could technically name these variables anything you want, but React developers follow a strict naming convention: if the state value is named something, the setter function is always named setSomething.

Another essential rule concerns the argument passed to useState. In useState(0), the argument 0 is the initial state. React uses this initial argument strictly during the initial render when the component first mounts on screen. On every subsequent render, React already has the current value stored in its memory cell, so it completely ignores the argument passed to useState. The line useState(0) runs on every render, but it acts as a state lookup rather than a variable reset.

Functions like useState whose names start with the word use are called Hooks. Hooks are special functions that let components connect to React's built-in runtime features. Because React relies on the exact order in which Hooks are called to match each state variable to its storage cell, you must always call Hooks at the top level of your component function. Never call useState inside loops, conditional statements, or nested functions.

Principles of React: Component Memory with useState

Senior technical interview candidates must clearly explain the distinction between ephemeral local variables and persistent component state. Interviewers frequently probe: "Why do local variables fail to persist, where does React store state between renders, and what happens when you invoke a setter?" To answer with authority, we formalize the six governing principles of component memory:

PRINCIPLE 1

Expect a Local Variable to Forget, and to Change Nothing on Screen

local variable a variable declared inside a function whose lifetime ends when the function returns
re-render a new execution of a component function triggered by state or prop changes

Every render is a new call of the component function, so a local variable is created fresh by each call. Assigning to it inside a handler changes only that single call's copy in memory. React receives no update signal, and the next render pass starts the variable again from its initial declaration.

When a user clicks a button tied to a local variable let likes = 0 the click handler executes likes = likes + 1. The variable in JavaScript memory increments to 1, 2, and 3, which can be verified with console.log. However, React does not monitor raw variable assignments. Because no state setter was called, React schedules no render pass, leaving the DOM untouched at "Like (0)".

Furthermore, if an unrelated state update (such as a working save toggle) causes the component to re-render, React executes the component function from the top. The statement let likes = 0 runs again, wiping previous local mutations and resetting the counter back to 0:

Instead of doing this: function StoryCard() { let ~likes~ = 0; // Resets to 0 on every render return ( <button onClick=~{() => { likes++; }}~> // Mutates local copy Like {likes} </button> ); }

PRINCIPLE 2

Store in State Exactly What Must Survive a Re-Render

component state persistent memory retained across renders to control UI output
handler variable a temporary calculation scoped strictly to a single event execution

Use useState strictly for information the component must remember between renders to change what appears on screen. Keep values that are calculated and used only inside a single event handler as ordinary local variables, because calling a setter always schedules a re-render.

Every time a state setter is invoked, React schedules a re-render for that component and its children. If a developer places values in useState that do not affect the rendered JSX output, every user action triggers unnecessary render cycles.

For example, if copying an article share link stores its URL in state via const [shareUrl, setShareUrl] = useState('') calling setShareUrl forces React to re-render the card twice in development under StrictMode, even though the screen output does not change. In contrast, calculating const url = window.location.href as a local variable inside the click handler performs the clipboard copy without triggering any renders:

PRINCIPLE 3

Expect React to Hand Back the Stored Value on Every Render

external memory cell a record managed by React in memory outside the component function
initial state the starting value passed to useState, used only during component mounting

React stores state outside the component function in an external memory cell. On the initial render, it stores the initial argument and returns it. On every subsequent render, useState ignores the initial argument and returns the latest stored value from React's memory cell.

When StoryCard renders for the first time, React executes useState(0), creates an internal state cell initialized to 0, and returns [0, setLikes]. When the user clicks the like button, setLikes(1) updates the value in React's external cell to 1 and schedules a re-render.

On the second render pass, React executes StoryCard again. Even though the line in source code still literally reads useState(0), React recognizes that this component instance already possesses an initialized memory cell. React ignores the 0 argument and returns 1. If you edit the component file in your editor, Fast Refresh preserves the state cell in browser memory. Only a full browser page reload wipes JavaScript memory and restores the initial 0:

PRINCIPLE 4

Change State Only by Calling Its Setter

setter function the updater function returned by useState that requests a re-render
read-only snapshot the immutable state value provided to a single render execution

A state variable is a read-only snapshot for the current render. Calling the setter function is the only way to store the next value and notify React to update the screen. Assigning directly to the state variable throws an error or silently fails to re-render.

When you unpack state using const [likes, setLikes] = useState(0) the variable likes is declared as a constant. If a developer attempts to modify it directly via likes = likes + 1, the JavaScript engine throws an immediate runtime exception: TypeError: Assignment to constant variable. and the button remains stuck at "Like (0)".

Even if the developer declares let [likes, setLikes] assigning to likes merely changes a local variable inside that single function execution. React has no getter or setter trap on raw JavaScript variables and receives no notification to update the DOM. Calling setLikes(likes + 1) is the mandatory contract: it updates React's internal storage and schedules the re-render:

PRINCIPLE 5

Expect Each Rendered Instance to Keep Its Own State

component instance a specific mounted occurrence of a component in the UI tree
state isolation the guarantee that each component instance manages independent memory

State belongs to a specific instance of a component on the screen, not to the component function or file. Rendering a component multiple times creates completely independent state cells, and parent components cannot directly read or alter a child's private state.

When App renders two <StoryCard /> elements, React attaches two distinct state cells to their positions in the UI tree. If the reader clicks the Like button on the first card, React calls setLikes(1) for that first cell and re-renders only the first card. The second card remains untouched at Like (0) because its state cell is completely isolated.

Furthermore, the parent component App cannot inspect or overwrite the child card's internal state. State is entirely private to the component that declares it. (Preview of Q26: If two sibling cards need to share a synchronized count, state must be removed from the children and lifted up into their common parent):

PRINCIPLE 6

Call Setters from Handlers, Never Unconditionally During Render

render loop an infinite cycle of render passes caused by unconditional state updates
delayed execution wrapping a function call so it runs only upon user interaction

A setter call requests a re-render. If a setter is called unconditionally in the component body or directly inside a JSX event prop, it executes during the render pass, immediately scheduling another render. This creates an infinite loop that crashes React with a fatal error.

When writing JSX, passing parentheses immediately executes the function during render: <button onClick={setLikes(likes + 1)}> As React renders the button, JavaScript evaluates setLikes(likes + 1). Calling setLikes informs React that state has changed and demands an immediate re-render. React re-renders the component, encounters the button again, calls setLikes again, and enters a runaway loop.

Within milliseconds, React halts execution and throws a fatal runtime exception: Error: Too many re-renders. React limits the number of renders to prevent an infinite loop. leaving the screen blank. To prevent this crash, always wrap setter calls inside an event handler function or an inline arrow function: onClick={() => setLikes(likes + 1)}

Where you will meet this

  1. Interactive Counters and Metrics: Like buttons, clap counters, and item quantity pickers use useState to increment values and update the display.
  2. Toggle Switches and Status Flags: Bookmark buttons, favorite icons, and dark mode toggles store boolean values in state to alternate between active and inactive states.
  3. Form Input Controls: Search bars, comment text areas, and filter checkboxes use state to remember the text typed by the user as they interact.
  4. Collapsible Accordions and Modals: Expandable article summaries and dropdown menus use state to track whether a panel is currently open or closed.

Glossary

  • Component Memory: Persistent data stored by React outside the component function that survives across re-renders.
  • useState Hook: The built-in React function that declares a state variable and returns a pair: the current value and a setter function.
  • Setter Function: The updating function returned by useState that changes the value in React's memory cell and schedules a re-render.
  • Array Destructuring: JavaScript syntax that extracts elements from an array into distinct variables in a single statement.
  • State Isolation: The architectural invariant where each mounted instance of a component maintains its own private, independent state.
  • Infinite Render Loop: A fatal runtime condition where calling a setter unconditionally during render triggers continuous re-renders until React halts.
