  2. He wants to record a rating score and immediately send an analytics alert with the newly updated value.

  5. Believing that state updates like a regular mutable variable causes developers to log stale data, trigger race conditions in delayed network requests, and assume React is broken.
  6. If calling a setter does not change the running variable, where does React store the new value, and why does JavaScript keep seeing the old one?

The Mystery of the Frozen State Variable

Every interactive web interface captures user reactions (such as article ratings, bookmark choices, or reader comments). In traditional JavaScript, developers expect variables to mutate instantly upon assignment: if you assign a new number to a variable, inspecting that variable on the very next line yields the updated number. In React, state behaves very differently from this live mutable variable model: calling a state setter function requests a future render pass, but it leaves the state variable in the currently executing function completely untouched.

To see this friction in action on The National Times, Julian opens his code editor to build a reader feedback component for news articles: StoryFeedback.jsx. When a reader clicks a five-star rating button, Julian wants to update the score on the screen and immediately send that new score to an analytics service to measure reader engagement.

Julian declares a state variable named rating initialized to 0. Inside the button click handler handleScore, he calls setRating(5). On the very next line of code, he logs rating to the browser console to inspect the new score:

When Julian runs the application and clicks the button, a surprising sequence of events takes place. The button on the screen eventually updates to display "Rate: 5". However, in the browser developer console, the log statement inside handleScore stubbornly printed "Rating: 0"! Even though setRating(5) was executed on line 4, inspecting rating on line 5 revealed the old number from before the click.

This discrepancy causes genuine architectural confusion. When developers first encounter this behavior, they frequently assume that React's state setter has a timing bug, that asynchronous execution has scrambled their instructions, or that the setter failed entirely. If Julian passes rating to an analytics reporting function inside that same click handler, his application reports that the reader gave the article zero stars.

Why does reading a state variable right after calling its setter fail? It fails because state variables are not live mutable storage cells that you can overwrite in place. A state variable is an immutable snapshot provided by React for one specific render pass. Calling a setter records the next desired value in React's external memory and schedules a future render, but it cannot travel back in time to alter the variable in the running JavaScript execution.

To understand why React designs state this way, we must examine the core mechanism: the snapshot mental model and JavaScript closures.

⚡ IN THE WILD

Why does state appear frozen inside a render, even right after you set it?

Calling a state setter function does not mutate the state variable inside the currently running JavaScript function. Instead, state variables are immutable snapshots captured by JavaScript closures for a specific render pass. When React calls your component, it hands it a fixed snapshot of state. The setter records the next value in React's storage and schedules a new render pass, but the running handler continues to read the frozen values from when the render began. To use the next value inside the same handler, compute the number into a local variable before passing it to the setter.

The Snapshot Mental Model: How React Sees State Over Time

To understand how state operates across time, consider a helpful physical analogy: a photographer taking pictures of a newsroom. Each photograph captures the room at one exact moment in time: the position of the desks, the headlines written on the board, and the journalists present. If someone walks through the door five seconds after the shutter clicks, that person does not magically appear inside the photograph you already printed.

In React, rendering is taking a snapshot of your component in time. When React executes a component function, it passes in a snapshot of state for that specific render pass. The JSX returned by your function is an interactive photograph of the user interface. Its props, local variables, and event handlers were all calculated using the state values from that exact render pass.

Unlike a static paper photograph, this UI snapshot is interactive. It returns JSX elements carrying event handlers that specify how the application responds to reader clicks. When React receives this JSX description, it updates the browser DOM and connects the event listeners. Because the component function executed with specific values, every event handler created during that render pass carries those exact values locked inside its function body.

Recall from earlier lessons that state does not live inside your component function. If state lived inside the component, it would disappear every time the function finished running. Instead, state lives in React itself, stored externally as if on a shelf (recalled from Lecture 16). When React calls your component, it inspects the shelf and hands your component a snapshot of that state value. When your handler calls setRating(5), React updates the value on its shelf and queues a new render pass (recalled from Lecture 17). React does not touch the variable inside the currently running function execution.

Because state variables remain fixed throughout a render pass, you can predict what any event handler will do using the substitution method. Mentally replace the state variable in your code with its actual value for that render pass. If rating is 0, then setRating(rating + 1) is literally setRating(0 + 1). Even if you inspect the variable or pass it to other functions, it remains 0 throughout that handler execution:

The substitution method explains a classic interview puzzle: what happens if you call setRating(rating + 1) three times in a single event handler? A developer who views state as a mutable variable expects the rating to increase by three. In reality, the rating increases by only one! In that render's handler, rating is always 0. The handler tells React: setRating(0 + 1), setRating(0 + 1), and setRating(0 + 1). React records that the next state should be 1 three times in a row. When the handler finishes, React re-renders the component once with rating equal to 1. Principles of React: State as a Snapshot

Senior technical interview candidates must clearly explain how JavaScript closures and React's render lifecycle interact. Interviewers frequently probe: "Why does state appear frozen inside a render, even right after you set it?" To answer with precision and authority, we formalize the two governing principles of state snapshots:

PRINCIPLE 1

Treat the State Value as Frozen for the Entire Render

snapshot value the constant state data React passes to a component for a single render execution
queued render a scheduled render pass that React executes after the active handler finishes

A state variable is a fixed snapshot provided by React for one render pass. Calling a setter records the next value and queues the next render, but it never alters the variable inside running code. Any log, calculation, or timer set up after the setter continues to read the snapshot value from that specific render.

When a user rates an article, calling setRating(5) instructs React to store 5 for the upcoming render pass. However, inside the currently executing function, rating remains the exact snapshot value handed to it when the render began. If rating started at 0, logging rating on the very next line prints 0.

Even more surprisingly, if you place that log inside a three-second setTimeout, the timer callback still prints 0 when it executes three seconds later! By the time the timer fires, the screen may already show 5, but the timer callback was created during the initial render pass where rating was 0. The callback closed over that specific snapshot:

PRINCIPLE 2

Treat Every Handler as a Closure Over the Render That Created It

closure a JavaScript function that retains access to variables from its parent scope at creation time
fixed state values that remain unchanged throughout an event handler to prevent asynchronous data drift

Each render pass creates fresh event handlers that close over that specific render's props, state, and local variables. Even if an event handler runs after an asynchronous delay or after state has changed on screen, it accesses the values from when the user acted. React keeps values fixed on purpose so asynchronous code never suffers from state changing mid-execution.

When a component renders, JavaScript creates fresh event handler functions. In JavaScript, a closure is a function that retains access to variables declared in its surrounding lexical scope at the time it was defined. Because each render pass calls your component function again, each render creates new handler functions that close over that render's specific props and state.

This closure behavior is not an inconvenient bug; it is an essential safety guarantee. Consider an asynchronous feedback form where a reader sends a message to a journalist: you select "Alice", click Send with a five-second delay, and then quickly change the recipient dropdown to "Bob". When the five-second timer completes, the alert announces: "Sent to Alice". Because the submission handler closed over the state snapshot from when you clicked Send, the message goes to Alice rather than Bob.

If React mutated state variables in place like live mutable storage, changing the dropdown would mutate the variable while the request was in flight, corrupting the message and sending private feedback to the wrong person! React intentionally keeps state values fixed within each render's event handlers so your code never has to worry that state might change under its feet:

Our practical example demonstrates the snapshot mental model in action. When a reader clicks a rating button, StoryFeedback receives the new score and calls setRating(newScore). Inside that event handler, rating remains completely frozen at 0. Logging rating or inspecting it inside a timer callback yields 0.

Meanwhile, React stores the new score externally and schedules a new render pass. When that new render pass executes, React calls StoryFeedback again, this time providing a fresh snapshot where rating is 5. Handlers created in that second render pass will see 5.

Where you will meet this

  1. Analytics and Event Logging: When tracking user actions like rating an article or submitting a review, developers calculate the next value in a local variable before logging to avoid sending the frozen previous state.
  2. Asynchronous Form Submissions: Delayed network requests and message dispatchers rely on closures to ensure that feedback is sent to the recipient selected at the moment of the click, even if the user changes form fields during transmission.
  3. Multi-Step Status Toggles: Toggling buttons (such as like counters or traffic signals) use computed variables to calculate the next state reliably instead of reading the state variable right after setting it.
  4. Optimistic UI Updates and Confirmation Modals: Dialog boxes and confirmation prompts safely reference the exact data the user acted upon without fearing that background state updates will mutate information mid-interaction.

Glossary

  • State Snapshot: The immutable state data React passes to a component for a single render pass, remaining completely constant throughout that execution.
  • Closure: A JavaScript function that retains access to variables from its surrounding lexical scope at creation time, preserving those values across asynchronous delays.
  • Queued Render: A scheduled render pass placed in React's work queue by a state setter, executed only after the active event handler finishes.
  • Substitution Method: A mental reasoning technique where you replace state variables in an event handler with their literal snapshot values to predict execution behavior.
  • Stale State Read: Inspecting a state variable inside an event handler immediately after calling its setter, observing the frozen value of the current render rather than the upcoming one.
  • Local Calculation Variable: A temporary JavaScript variable created inside an event handler to hold the next computed state value for immediate use in logging or alerts.
