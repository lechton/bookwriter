Interview Question

The Friction of Event Bubbling and Default Actions

Every web application exists to present content. Real user interfaces must also respond when users interact with the screen. Users click buttons, submit search queries, and save articles for later reading. In earlier lessons, you learned that React components are pure functions. They calculate JSX markup from incoming props. However, when developers begin adding interactivity to their components, they frequently encounter unexpected browser behaviors.

To see this in action on The Daily Courier, Nora builds an interactive news desk: src/App.jsx. She renders a list of news articles. Each card features an article headline and a nested "Save" button. When the reader clicks the card itself, the application should open the full story. When the reader clicks the Save button, the application should save the story without opening it.

It is common for an engineer to write the code below, expecting button clicks and card clicks to stay separate. Opening the browser reveals an immediate defect. Clicking Save logs the bookmark, but it also opens the full article. The user triggered two conflicting actions with a single click.

Why did clicking the inner button trigger the parent card handler? In the browser DOM, events do not stop at the element you clicked. They bubble upward through every parent element in the tree. The button sits inside the card. Clicking the button triggers its handler first, then triggers the enclosing card handler.

A second failure occurs when an engineer submits a search form without halting browser defaults. Decades ago, HTML forms submitted data by navigating to a new URL. When a reader presses Enter inside a search form without special handling, the browser reloads the page. The page refreshes, the URL appends a question mark, and all client memory disappears.

⚡ IN THE WILD

Why did clicking Save also open my article card?

In the browser DOM and React, click events bubble upward from child to parent. When you click a button inside an article card, the click runs the button handler first. Then, the event travels up to the article card and runs the card click handler as well. To prevent the parent card from opening, call e.stopPropagation() inside the button handler. This halts the event immediately and prevents it from reaching any parent elements.

Synthetic Events, Input Handlers, and Propagation Pathways

To build reliable user interfaces, we must understand how React connects JavaScript functions to browser events. In the browser DOM, elements dispatch native events like click, input, and submit. Different browsers historically implemented slightly different event properties. React solves this by wrapping native events in a cross-browser object called SyntheticEvent.

The synthetic event object conforms directly to the standard DOM Event interface. It normalizes browser differences so your event code behaves identically across all modern browsers. In React, you attach handlers using camelCase props like onClick, onChange, and onSubmit. Every handler function receives this synthetic event object e automatically as its first argument.

A critical distinction in event handling is the difference between e.currentTarget and e.target. The property e.currentTarget always points to the element that owns the active handler. In contrast, e.target points to the innermost element the user physically touched. If a button contains an icon <span>★</span> clicking the star sets e.target to that inner span. However, e.currentTarget remains the button element. Reading e.currentTarget ensures you inspect the element that declared the handler.

Let us also examine how React handles text inputs. In native DOM, input change events wait for blur. They fire only when the user leaves the field. In React, onChange behaves differently: it fires on every single keystroke. Under the hood, React listens to the browser input event and normalizes it to onChange. The property e.target.value contains the full text typed so far, providing real-time access to user queries.

Finally, let us review two JavaScript features used in clean event handling. First, object destructuring (const { value } = e.target) unpacks properties from an object into local variables. Second, an arrow function (() => handleOpen(story.id)) creates a waiting function value. It passes specific identifiers upward only when the user clicks, preventing premature execution during render.

Principles of React: The Core Laws of Event Handling and Propagation

Senior interview candidates must clearly explain event handling and propagation. They must distinguish targets, handle keystrokes, and stop bubbling cleanly. To master these concepts, we formalize the six governing principles of event handling:

PRINCIPLE 1

Put Side Effects in Handlers, Never in Render

side effect an operation that interacts with outside systems or modifies external memory
render calculation the pure step where a component calculates its JSX markup

Handlers run strictly when the user interacts, never during the render calculation. This makes event handlers the natural home for side effects like logging, analytics, and network calls. Placing side effects in component bodies causes unwanted executions and crashes pure rendering contracts.

In earlier lessons, you learned that React components must remain pure calculations. React calls your component function whenever it needs to compute markup. Under StrictMode in development, React invokes your component twice to detect unexpected side effects.

Side effects placed in component bodies run on page load. Under StrictMode, they execute twice during development. By contrast, React calls event handlers only when a user physically clicks, types, or submits. An event handler is not part of the render calculation. It can safely send network requests, write to local storage, and trigger outside systems.

Render vs Handler Execution

3 function save() {
4 console.log('Bookmarked:', story.id);

PRINCIPLE 2

Read currentTarget for the Bound Element and target for What Was Touched

currentTarget the element whose event handler is currently executing
target the innermost DOM element where the event originated

Every handler receives a React event object that mirrors DOM standards. The currentTarget property refers to the element that owns the handler. The target property refers to the innermost element the user physically touched, such as an icon inside a button.

When an event occurs, the browser creates an event object. React wraps this event in a SyntheticEvent. If you attach an onClick handler to an <article> card, the card is the currentTarget.

If the user clicks an icon <span>★</span> inside that card, e.target is the inner <span> tag. A common bug occurs when developers read e.target.dataset.id expecting the card ID. If the reader clicks the icon, e.target is the span, returning undefined. Always inspect e.currentTarget to read attributes from the element that declared the handler.

Target vs CurrentTarget

PRINCIPLE 3

Expect onChange to Fire on Every Keystroke

onChange event a synthetic event firing on every text modification in an input
input event the native browser event dispatched on each individual keystroke

React fires the onChange prop on every single keystroke. In the browser DOM, native change events wait until an input loses focus. React wraps the native input event so onChange provides immediate updates as the user types.

In traditional JavaScript, developers had to choose between input and change events. The native change event on <input> elements dispatches only when the user commits text by pressing Enter or clicking away.

In React, onChange fires immediately on every keypress. The property e.target.value contains the full text typed into the field so far. The underlying native event type is input, exposed through e.nativeEvent.type. This immediate dispatch allows components to log searches, validate formats, or filter lists in real time.

PRINCIPLE 4

Expect Events to Bubble Up Through Parent Handlers

event bubbling the upward propagation of an event through ancestor DOM elements
capture phase the downward pass where capture handlers execute before bubbling starts

Events start at the innermost element touched and bubble upward through ancestors in order. Each parent handler on the path executes unless explicitly stopped. The onScroll event is the sole exception in React that does not bubble.

Event propagation in React follows the DOM event model. When a user clicks an element, the event first travels downward from the root during the capture phase. You can listen to this phase using onClickCapture.

Once the event reaches the target, it bubbles upward through each parent element. If a button sits inside an <article> card, clicking the button invokes the button handler first, then the card handler. All events propagate in React except onScroll, which fires strictly on the scrolled element.

PRINCIPLE 5

Stop Propagation Where a Child Action Must Stay Local

stopPropagation a method on the event object that prevents further bubbling to parents
child isolation keeping child button actions from activating enclosing card click handlers

When clicking an inner control must not trigger the parent container handler, call e.stopPropagation() in the child handler. Stopping propagation keeps the action local and prevents accidental parent activation.

It is best practice to do this:
function ActionBtn({ onSave }) {
function handleClick(e) {
e.stopPropagation();
Stops bubbling to parent
onSave();
}
return <button onClick={handleClick}>Save</button>;
}
Instead of doing this:
function ActionBtn({ onSave }) {
function handleClick(e) {
onSave();
Omitting stopPropagation bubbles click to parent
}
return <button onClick={handleClick}>Save</button>;
}

In modern web applications, clickable cards often contain independent actions like bookmark, like, or share buttons. If a user clicks Bookmark, they intend to save the article, not navigate to the article page.

Without calling e.stopPropagation(), the event bubbles to the card, triggering both actions. Calling e.stopPropagation() halts the event at the button boundary. If the parent needs notification, the child calls a parent callback prop explicitly after stopping propagation.

Stopped Propagation Pattern
1export default function BookmarkAction({ storyId }) {
2 function handleSave(e) {
3 e.stopPropagation();
Halts bubbling before reaching parent
4 console.log('Saved story:', storyId);
Runs isolated action in memory
5 }
6 return (
7 <button onClick={handleSave}>Save Story</button>
8 );
9}

Clicking the Save button now prints only Saved story: art-1. The enclosing card click handler never runs because bubbling was stopped at the button boundary.

PRINCIPLE 6

Prevent Browser Default Actions on Form Submission

preventDefault a method that cancels the default browser behavior for an event
full-page reload native browser form submission that refreshes the page and wipes memory

Forms natively reload the browser page upon submission. Call e.preventDefault() in your onSubmit handler to cancel the native reload. This allows React to handle the event in memory.

It is best practice to do this:
function SearchForm({ onSearch }) {
function handleSubmit(e) {
e.preventDefault();
Prevents full-page reload on submit
onSearch();
}
return <form onSubmit={handleSubmit}><button>Go</button></form>;
}
Instead of doing this:
function SearchForm({ onSearch }) {
function handleSubmit(e) {
e.stopPropagation();
Does not prevent full-page reload
onSearch();
}
return <form onSubmit={handleSubmit}><button>Go</button></form>;
}

HTML form elements carry built-in browser behaviors established decades ago. When a <form> is submitted, the browser collects inputs and navigates to its action URL. If no action exists, it reloads the current page with query parameters.

In a single-page React application, a full-page reload wipes all client state and clears the browser console. Developers sometimes mistakenly call e.stopPropagation() to fix this reload. However, stopping propagation only halts bubbling to parent components; it does nothing to prevent browser default behaviors. To cancel the reload, you must call e.preventDefault().

Preventing Form Submission Reload

2 function handleSubmit(e) {

Cancels native browser full-page reload
4 console.log('Search submitted');
Executes custom submission in memory
5 }
6 return (
7 <form onSubmit={handleSubmit}><button>Go</button></form>
8 );
9}

With e.preventDefault(), pressing Enter logs "Search submitted" while the page stays in place. The console logs remain visible and the page never refreshes.

Where you will meet this

  1. E-Commerce Product Cards: Product cards navigate on click. Nested Add-to-Cart buttons call e.stopPropagation() to stay on the page.
  2. Search and Filter Bars: Search forms call e.preventDefault() to prevent page reloads. Input fields use onChange for real-time filtering.
  3. Dropdown Menus and Modals: Modals stop propagation on dialog windows. This prevents clicks inside from triggering backdrop dismissal.
  4. Interactive News Feeds: Social feeds use nested bookmark controls. These controls isolate click events from full-article view navigation.

Glossary

  • SyntheticEvent: A cross-browser wrapper around native DOM events providing identical behavior across all modern browsers.
  • Event Bubbling: The natural upward propagation of an event through parent DOM elements until it reaches the root.
  • Propagation Stopping: Calling e.stopPropagation() to halt the upward journey of an event, preventing ancestor handlers from executing.
  • Default Action Prevention: Calling e.preventDefault() to cancel the built-in browser behavior for an event, such as form submit reloads.
  • Event Target: The innermost element the user touched (e.target), contrasted with the element owning the handler (e.currentTarget).
