The Friction of Premature Execution and Custom Props

Every web application exists to present dynamic content, but real user interfaces must also respond when users interact with the screen. Users click buttons, submit search queries, and save articles for later reading. In earlier lessons, you learned that React components are pure functions that calculate JSX markup from incoming props. However, when developers begin adding interactivity to their components, they frequently carry habits from traditional scripting that clash with React's declarative rendering model.

To see this in action on The National Times, Leo sits at his desk to build the interactive reading desk: src/App.jsx. He renders a list of news articles and wants each card to feature a "Read Article" button. When the reader clicks the button, the application should log the selected article ID to the console.

It is common for an engineer to write onClick={openArticle(id)} on the button, expecting React to store the function and its argument until the user clicks. But when they open their browser, they immediately see an alarming failure: the console prints "Opened article: art-1" and "Opened article: art-2" immediately on page load, before the user touches anything! Even worse, when the user clicks the button later, nothing happens at all.

Why did the function execute on page load? In JSX, any expression placed inside curly braces evaluates immediately during the render phase. When JavaScript encounters openArticle(id), it executes the function right then and there. Because openArticle does not return another function, it returns undefined. React assigns undefined to the onClick prop, leaving the button with no click handler when the user finally interacts with the page.

A second common failure occurs when an engineer passes an event prop to a custom component, such as writing <ArticleCard onClick={handleSelect} /> Custom components are JavaScript functions, not browser DOM elements. React does not attach browser event listeners to custom component tags. If ArticleCard does not explicitly receive that prop and pass it down to a native browser element like <button>, the event prop is completely ignored and clicks are silently lost.

⚡ IN THE WILD

Why did my button click handler run on page load?

In JSX, expressions inside curly braces run immediately during component rendering. If you write onClick={openArticle(story.id)} JavaScript executes openArticle right away while constructing the element tree. The function runs on page load before the user touches anything, and its return value (undefined) is passed to onClick, leaving the button unresponsive when clicked later. To fix this, wrap the call in an arrow function: onClick={() => openArticle(story.id)} The arrow function acts as a delayed container: it is created during render, but its inner code executes only when the user triggers the click event.

Event Handlers as Functions and the DOM Boundary

To build predictable user interfaces in React, we must understand how React connects JavaScript functions to browser events. In the browser DOM, elements dispatch events (such as click, input, keydown, and submit) when users interact with the screen. In standard HTML, developers used lowercase attributes like onclick="handleClick()". In React, event props are written in camelCase, such as onClick, onChange, onKeyDown, and onSubmit. Instead of passing a string containing code, you pass an actual JavaScript function value. When the user interacts with the rendered element, React receives the native browser event and invokes your handler function.

A fundamental rule of React is the distinction between passing a function reference and calling a function. When you write onClick={handleClick}, you are giving React the address of the function; you are saying, "Remember this function and execute it when the user clicks this button." But when you write onClick={handleClick()}, the parentheses tell JavaScript to execute handleClick right now, while the component function is running. The return value of handleClick is then assigned to onClick. If you need to pass an argument to a handler, you must not call it directly in JSX. Instead, you create a new function on the fly using an arrow function: onClick={() => handleSelect(article.id)} Because the arrow function body does not execute until the arrow function itself is called, the inner handleSelect call waits safely until the user clicks.

A frequent source of confusion is understanding where browser events stop and React component props begin. Built-in HTML elements (like <button>, <input>, <a>, and <form>) represent real browser DOM elements; React attaches native event listeners to these built-in elements. In contrast, custom components (like <ArticleCard /> or <BookmarkButton />) are purely JavaScript abstractions. If you write <ArticleCard onClick={handleClick} /> React does not attach a click listener to any DOM node because ArticleCard is not a DOM node. The prop onClick is merely a custom prop, exactly like title or color. For that click to do anything, ArticleCard must receive the prop and attach it to a real built-in element inside its return markup: <button onClick={onClick}>. By convention, custom components name their handler props after the application action (such as onSelect or onBookmark) rather than low-level DOM events. The parent decides what action should occur, passes a callback function down, and the child wires that callback to a native button.

Let us review two JavaScript features essential for clean event handling: arrow functions and naming conventions. An arrow function (() => expression) is a concise way to create an anonymous function value in JavaScript. When written as () => onSelect(article.id) it accepts the event and forwards the specific article.id to the parent callback. Second, React developers follow a universal naming convention: handler functions defined inside a component are named with the prefix handle followed by the action or event (such as handleSelect or handleBookmark), while props that receive callbacks are named with the prefix on followed by the action (such as onSelect or onBookmark). This distinction makes code instantly readable: on signals a prop that accepts behavior, while handle signals the function that implements that behavior.

Principles of React: The Core Laws of Event Handling

When preparing for senior technical interviews, candidates must clearly explain why handlers must be passed rather than called, how inline arrow functions pass arguments safely, why custom components require explicit wiring to built-in DOM elements, and why click targets must use semantic button tags. To master these concepts, we formalize the three governing principles of event handling:

PRINCIPLE 1

Pass the Handler, Never Call It

function reference passing the function itself as an uncalled value so an event listener can execute it later
premature invocation executing a function during render by adding parentheses inside JSX braces instead of waiting for user interaction

Give an event prop a function value (onClick={handlePublish}) so React can call it when the user clicks, and when the handler needs arguments, pass a new function that makes the call (onClick={() => openArticle(article.id)}), because anything written inside JSX curly braces runs immediately during render.

We should do this:
<button onClick={handlePublish}>Publish</button>
Passes uncalled function reference to run on click
We should not do this:
<button onClick={handlePublish()}>Publish</button>
Parentheses call the function immediately during render

In React, JSX curly braces are an evaluation window into JavaScript. Any expression placed inside { ... } runs synchronously during the render phase. If you write onClick={handlePublish()}, JavaScript invokes handlePublish() immediately while constructing the JSX element tree. If handlePublish logs "PUBLISH ran" to the console, that message appears on page load before any user interaction. Because handlePublish does not return a function, onClick receives undefined. When the user later clicks the button, the browser finds no function to call, and the click produces zero output.

The exact same defect occurs when passing arguments: writing onClick={openArticle(story.id)} executes openArticle during render for every item in your list. To pass a handler without running it, pass the bare function name: onClick={handlePublish}. When arguments are required, wrap the call inside an arrow function: onClick={() => openArticle(story.id)} The arrow function is an uncalled function value created during render; it runs only when the user dispatches a click event.

PRINCIPLE 2

Hand Behavior to a Child Through an on Prop and Wire It to a Real Element

callback prop a function prop passed from parent to child allowing the child to report user actions upward
DOM element boundary the terminal built-in HTML elements (like button or input) where React connects event props to browser events

When the parent decides what a click means, pass a function through a prop named for the app action (<ArticleCard onSelect={handleSelect} />) and, inside the child, pass that prop to a built-in element's event prop (<button onClick={() => onSelect(id)}>), because only built-in elements turn browser events into handler calls; a custom component ignores props it does not use.

We should do this:
function ArticleCard({ onSelect, id }) {
Receives custom callback prop from parent
return <button onClick={() => onSelect(id)}>Read</button>;
Wires callback to native button via inline arrow
}
We should not do this:
function ArticleCard({ onSelect }) {
return <div className="card">Read</div>;
Non-interactive div ignores callback prop and drops click events
}

Custom React components are not DOM elements. When you write <ArticleCard onClick={handleClick} /> the browser does not see a DOM element named <ArticleCard>, and React does not attach an event listener to the card boundary. Custom components only receive props; if ArticleCard does not explicitly take onClick and wire it to a built-in element, clicking anywhere on the rendered card does nothing.

To establish clear architectural boundaries, name handler props after the semantic application action rather than generic DOM events: pass onSelect={handleSelect} instead of onClick={handleSelect}. This separation decouples the parent from the child's internal layout: the parent cares that a story was selected, while the child decides whether that selection is triggered by a button, a keypress, or an icon click. Inside the child, connect the callback prop directly to a built-in browser element's event prop: <button onClick={() => onSelect(article.id)}> When the user clicks the button, the child executes the callback, passing relevant identifiers upward while the parent retains full authority over application data.

PRINCIPLE 3

Make Click Targets Real Buttons

semantic button an HTML button element providing built-in keyboard navigation, focus management, and screen reader accessibility
inaccessible click target a non-interactive element like div or span given an onClick handler without keyboard support

Attach click handlers to <button> elements (or links for navigation), not to <div> or <span>, because the browser gives a button keyboard focus and activation with Enter and Space, while a clickable <div> responds only to a mouse.

We should do this:
<button type="button" className="action-btn" onClick={handleSave}>
Built-in button element with keyboard focus and activation
Save
</button>
We should not do this:
<div className="action-btn" onClick={handleSave}>
Inaccessible click target unreached by Tab or Enter
Save
</div>

A frequent design flaw in modern web applications is turning generic layout containers into clickable controls by writing <div onClick={handleClick}> or <span onClick={handleClick}>. While a mouse click may fire the handler, non-interactive elements lack built-in accessibility. A user navigating with the Tab key cannot move focus to a <div>, and pressing the Enter or Space keys produces zero response. Screen readers announce the element as generic text or a grouping, giving visually impaired users no indication that the element is actionable.

In contrast, the HTML <button> element provides full accessibility out of the box: the browser includes it in the keyboard tab sequence, displays native focus outlines, dispatches click events when the user presses Enter or Space, and communicates its interactive role to assistive technologies. If you need a button to look like a plain link or badge, use CSS to remove the default background and borders (border: none; background: transparent;) while preserving the underlying semantic <button>.

Examine how this three-file architecture handles user interaction cleanly. In a naive implementation, an engineer might have written onClick={openArticle(id)} directly in App.jsx, causing every article to fire on page load and leaving buttons non-functional. They might have passed onClick to <ArticleCard /> without wiring it internally, leaving clicks ignored. Or they might have created clickable <div onClick> elements that keyboard users cannot reach.

By contrast, our architecture passes uncalled function references downward through on-prefixed props, wraps parameterized calls in inline arrow functions, and connects all user interactions to native <button> elements at the DOM boundary. The child components remain reusable presentation controls, while the parent container retains full decision-making power.

Where you will meet this

  1. Interactive Design Systems and Component Libraries: UI libraries like Material UI or Radix pass callback props like onClick, onSelect, or onValueChange from parent containers down to reusable styled button components.
  2. Form Controls and Input Handlers: Search bars, filters, and text fields accept user input through onChange and onKeyDown, passing user text upward to parent validation and processing handlers.
  3. Modal Dialogs and Drawer Toggles: Overlay dialogs receive onClose callback props from root pages, allowing a child close button to notify the parent when the user requests dismissal.
  4. Accessibility and Keyboard Navigation Audits: Automated accessibility scanners (like axe-core and Lighthouse) check that interactive elements use semantic <button> tags rather than plain <div> elements with click handlers.

Glossary

  • Function Reference: Passing a function by name as an uncalled value without parentheses so React can execute it later when an event fires.
  • Premature Invocation: Accidental execution of a function during the render phase caused by placing parentheses after the function name inside JSX curly braces.
  • Callback Prop: A function passed downward through props from parent to child, allowing the child to report user interactions upward.
  • Inline Arrow Function: An anonymous function expression (() => handler(arg)) created inside JSX to delay function execution until an event occurs while passing arguments.
  • DOM Element Boundary: The terminal built-in HTML elements (such as button, input, or a) where React connects JSX event props directly to browser event listeners.
