Lecture 15: Trigger, Render, and Commit

Interview Question

CORE

What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?

Imagine this scenario:

  1. Leo's story page at The National Times has a Like button and a comment box.
  2. His editor wants every like sent to the newsroom's statistics server, with the new count.
  3. Leo calls the setter, then reads the count from the page and sends it.
  4. The page shows 1, yet the server receives 0. Where did the like go?
  5. Every report the newsroom reads will be one like short.
  6. Between the setter call and the new number on the screen, React works in three steps, and Leo's line runs before all of them.
  7. Today we follow one click through those three steps: trigger, render, and commit.

The server receives the old like count

In Lecture 14 we gave a component memory. useState keeps the count, and the setter stores the next value and makes React run the component again. Leo's story page now has a LikeCounter component. It shows the count in a paragraph, a Like button under it, and a comment box. A colleague wrote a helper called sendLikeEvent in the file analytics.js. It posts a number to the newsroom's statistics server, and Leo must call it on every like.

Leo comes from plain JavaScript, where the page is the place the number lives. So he calls the setter, reads the number back from the page, and sends what he finds. document.querySelector('.like-count') is the browser's way to find the first element with the class like-count, and .textContent is the text inside it.

Leo clicks Like once. The paragraph shows 1. But the console prints sending 0 first, and only after it LikeCounter runs, likes = 1 A second click shows 2 on the page and sends 1. Every number the server receives is one like behind the screen.

Leo has two more worries. If React runs LikeCounter again on every like, does it run the whole app again? And does it rebuild the comment box, wiping what the reader is typing? He types "great post" and clicks Like. The comment stays. To understand all three results, we need to know what happens between a setter call and the screen.

⚡ IN THE WILD

Why does the page still show the old number?

On the line after setLikes(likes + 1), the paragraph on the page still holds 0. The setter only stores the next value. React changes the page after the click handler has finished, so any line inside the handler that reads the page reads the old text. The handler must use the number it computed itself.

Three steps from a click to the screen

The browser keeps the page as a tree of objects called the DOM. Each element, such as the paragraph with the count, and each piece of text inside it is a DOM node. In plain JavaScript we change the page by changing these nodes ourselves. document.querySelector('.like-count') finds the node, and setting its textContent to 1 puts 1 on the page on that very line. Lecture 1 showed that React takes this job over. We describe the screen with JSX, and React changes the DOM nodes.

Every screen update in React happens in three steps. First, a trigger starts the update. There are two triggers: the first root.render(<App />) call from Lecture 9, and a setter call. Second, React renders. It calls our component functions and gets their JSX back. Our code never calls them itself; React calls each one because the JSX names it, as Lecture 2 showed. Lecture 14 introduced this word for one run of a component. Nothing on the page changes in this step. Third, React commits. It changes the DOM nodes so the page matches the new JSX. After the commit, the browser draws the changed page on the screen, a step called browser paint. Browsers also call this step "rendering", so in an interview, say which of the two you mean.

The React documentation compares the three steps to a restaurant. A guest orders, the kitchen cooks, and a waiter brings the plate to the table. The order is the trigger, the cooking is the render, and serving the plate is the commit. The guest sees the food only at the end.

Because a render only calls functions and collects JSX, React may render a component without changing the page at all. This is why Lecture 12 asked components to be pure: a render must not change anything outside the function. Changes to the outside world, such as sending a like to a server, belong in event handlers. One note for your own console: a new Vite project turns on StrictMode, and in development React then calls each component twice, so every log line inside a component appears twice. Lecture 46 explains why.

The first trigger sits in main.jsx. The line after root.render runs before any component does.

This picture raises the questions Leo already met. How does a setter's new value travel through these steps onto the screen? Which components does React call after a click? Will a commit wipe the comment box? And when, exactly, does the page change? The four principles answer them in that order.

Principles of React: Trigger, Render, and Commit

An interviewer who asks this question wants to hear the three steps, what runs in each, and one consequence a developer can feel. The first principle follows one click through the steps. The second says which components run. The third says what the commit changes. The fourth is the decision that follows from the timing.

PRINCIPLE 1

After a setter call, React runs the component and then changes the page

In plain JavaScript, we change the page ourselves: p.textContent = 1 puts 1 on the page on that line. In React, we call setCount(count + 1) and never touch the page. Three steps follow. First, the setter stores 1 and makes React run the component again: this is the trigger. Second, React calls the component function, which returns JSX with {count} now 1: this is the render. The page has not changed yet. Third, React compares this JSX with the JSX of the last run and changes the page where they differ, so the text 0 becomes 1: this is the commit. Changing the page by hand skips all three steps. count stays 0, so every click writes 1.

We should do this:
const [count, setCount] = useState(0);
setCount(count + 1);
the page shows 1, then 2, then 3
We should not do this:
const [count, setCount] = useState(0);
const p = document.querySelector('p');
p.textContent = count + 1;
the page shows 1 on every click

In Leo's finished handler, the click calls setLikes(1). When the handler is done, the console prints LikeCounter runs, likes = 1 that is the render. LikeCounter returns JSX with 1 in the paragraph, and React changes the text node from 0 to 1: that is the commit. Leo never wrote a line that touches the paragraph.

His plain JavaScript habit would have been to skip the setter and write the number into the page himself.

LikeCounter.jsx, by hand
7 function handleLike() {
8 const label = document.querySelector('.like-count');
9 label.textContent = likes + 1;
Changes the page directly
10 }

The first click shows 1, so it looks like it works. The second click shows 1 again, and so does every click after it. No LikeCounter runs line appears in the console, because nothing triggered a render. likes is still 0, so likes + 1 is always 1. The same three steps also ran once at the very start: root.render(<App />) was the trigger, React rendered every component, and that first commit added every node to the page.

PRINCIPLE 2

After a setter call, React runs that component and its children, not the whole app

Components form a tree. Say App returns <Header /> and <Counter />, and Counter returns <Label />. On the first render, React calls all four, from App down. After a setter call in Counter, React does not start again from App. It calls Counter, the component that owns the state, and then Label, the component inside it. App and Header do not run. Label runs even when it returns the same JSX as before. A run does not mean the page changes, as Principle 3 shows.

We should do this:
function Counter() {
const [count, setCount] = useState(0);
return (
<button onClick={() => setCount(count + 1)}>
runs Counter
<Label count={count} />
and then Label
</button>
);
}

Leo's page is a component tree of the same shape, the tree from Lecture 5. App returns StoryTitle and LikeCounter, and LikeCounter returns LikeLabel, which shows the count. Each component logs its name when it runs. When the page first appears, the console prints App runs, StoryTitle runs, LikeCounter runs, likes = 0 and LikeLabel runs, likes = 0. A click on Like prints only LikeCounter runs, likes = 1 and LikeLabel runs, likes = 1. The headline never runs again, and neither does App. A component also runs again when its parent runs, as LikeLabel does here. Lecture 54 covers the other reasons a component runs again, and why these runs are usually cheap.

PRINCIPLE 3

Running a component again does not rebuild the page

In plain JavaScript, setting innerHTML throws the old elements away and builds new ones, and any text typed into an <input> there is lost. We might expect a new run of a component to do the same. It does not. The run only returns JSX. React compares it with the JSX of the last run, and in the commit it changes only what differs, for example the text of a number. An <input> that stays in the same place in the JSX stays the same element on the page, with the text typed into it.

We should do this:
return (
<section>
<p>{count}</p>
only this text changes
<input />
same element, typed text stays
</section>
);

Leo checks this in the browser console. He types "great post" into the comment box. Then he saves the input in a variable with const box = document.querySelector('input') and the paragraph with const label = document.querySelector('.like-count') He clicks Like. The paragraph shows 1, and the comment still reads "great post". box === document.querySelector('input') is true, and so is the same test for label. React kept both nodes and changed only the text inside the paragraph. After that commit, the browser paints the new number on the screen. React keeps a node because the same element stays in the same place in the JSX. Lecture 24 explains how that position decides what React keeps.

PRINCIPLE 4

The page changes only after the click handler has finished

In plain JavaScript, p.textContent = 1 changes the page on that line, so the next line can read 1 back. A setter does not change the page. It stores the next value, and the rest of the handler runs. React renders and commits only after the handler has finished. So a line right after setCount(count + 1) that reads the page still finds the old number. When the handler needs the new number, compute it once in a variable and give that variable to both the setter and the code that uses it, such as send(next).

We should do this:
const next = count + 1;
setCount(next);
send(next);
sends 1, the number the page will show
We should not do this:
setCount(count + 1);
send(document.querySelector('p').textContent);
sends 0

This is the bug from the start of the lesson. In Leo's first handler, setLikes(likes + 1) stored 1, and the next line read the paragraph. React had not rendered yet, so the paragraph still said 0, and the console printed sending 0. Only after handleLike returned did React render, and the console printed LikeCounter runs, likes = 1 The fixed handler computes next once and passes it to both setLikes and sendLikeEvent. The server now receives 1, then 2, the same numbers the reader sees. Reading likes instead of the page does not help either: on the line after the setter, likes also still holds 0. Lecture 16 explains why.

Component Summary

App

The parent component shows the headline and the like counter. It keeps no state, so it runs only after the first trigger, root.render(<App />), and never again on a like.

LikeCounter

The state owner keeps likes. Its handler computes next, calls the setter, which is the trigger, and sends the same number to the server. React renders it after the handler has finished.

LikeLabellikes={likes}

The display component runs on every like, because it sits inside the state owner. The commit changes only the text of its paragraph.

A newcomer from plain JavaScript expects to keep the page up to date by hand and to read the new number back from it. The finished page shows what React does instead. A setter triggers a render of the state owner and the components inside it. The commit then changes only the text that differs, and only after the handler has finished.

Where you will meet this

  1. Analytics on clicks: code that reports a like, a vote, or a purchase must send the number it computed, not the number it reads from the page.
  2. Forms beside changing data: a comment box, a search field, or a draft keeps its typed text while counters and lists around it update.
  3. Console logs while debugging: a log line in each component shows which components React called after a click.
  4. Interviews: questions about render against paint, and which components run again after a state change.

Glossary

  • Trigger: The start of a screen update: the first root.render call, or a setter call.
  • Render: React calling component functions to get their JSX; the page does not change in this step.
  • Commit: React changing the DOM nodes so the page matches the new JSX, only where it differs.
  • DOM Node: One object in the browser's tree of the page, such as an element or the text inside it.
  • Browser Paint: The browser drawing the changed page on the screen, after the commit.

Beyond the basics

  • The React documentation walks through the same three steps with more examples (see react.dev/learn/render-and-commit).
  • Several setter calls in one event handler lead to a single render (see react.dev/learn/queueing-a-series-of-state-updates).
  • A state variable keeps its old value until the next render, even right after its setter is called (see react.dev/learn/state-as-a-snapshot).
  • A component can skip a render when its props did not change (see react.dev/reference/react/memo).
  • flushSync makes React commit before the next line runs, for the rare case that needs it (see react.dev/reference/react-dom/flushSync).

Summary

Architectural Takeaways & Decision Matrix

❒ Letting React Change the Page

➔ ALWAYS change what the screen shows by calling a setter; React renders and commits the change.

➔ NEVER set the textContent of a node that React shows; the state stays old, and the next render can overwrite it.

➔ IF a state changes THEN expect React to run its component and every component inside it, but not its parent.

❒ Timing Inside an Event Handler

➔ ALWAYS compute the next value once and pass it to both the setter and any code that needs it.

➔ NEVER read the page on the line after a setter; the commit has not happened yet.
