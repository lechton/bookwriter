Lecture 11: Rendering Lists and Keys in React

Interview Question

CORE

How do you render a list from an array, and why does React demand a key on every item?

Imagine this scenario:

  1. Marcus sits down at his workstation at The National Times to build the morning news feed.
  2. The editorial team provides a list of breaking stories as a JavaScript array, and Marcus needs to display each story as an interactive card on the homepage.
  3. When an urgent breaking headline arrives at the top of the feed, Marcus prepends it to the array, but an editor's typed correction note on the first story suddenly jumps to the new breaking headline.
  4. Why does React attach existing user input to the wrong story when a new item is added to the front of a list?
  5. Relying on array indices as keys or omitting keys entirely causes React to match elements by position rather than identity, scrambling form inputs, audio players, and checkboxes across unrelated items.
  6. Many developers also struggle with blank screens when their array map callback uses curly braces but forgets the explicit return statement.
  7. Today, we master transforming data arrays into JSX elements using the map method, understand how keys provide persistent identity across renders, and build resilient list interfaces.

The Friction of Static Repetition and Dynamic Feeds

Every modern web application displays dynamic collections of data (such as articles in a news feed, products in a catalog, or messages in an inbox). In basic HTML, every item is written by hand as a separate tag. When you build applications with React, writing hardcoded tags for every item (<StoryCard story={story1} /> <StoryCard story={story2} />) makes code repetitive and rigid. If a newsroom publishes twenty new articles or removes an old report, an engineer would have to edit the component file and redeploy the code.

To see this in action on The National Times, you open your editor to build the main news feed: src/App.jsx. The editorial team gives you an array of story objects from their database. Each story has a unique id, a title, and a category. You want to display these stories in a clean list where editors can type notes directly into each story card.

It is possible that a developer may reach for the array map() method and write {stories.map((story, index) => <StoryRow key={index} story={story} />)} assuming that the array index is a simple and harmless choice for the key. When they do, the initial page appears to render without issues:

Notice what happens when the collection changes. Suppose an editor types "verify budget figures" into the note input for the first story ("City Transit Accord Finalized"). Suddenly, breaking news occurs, and an urgent story is prepended to the top of the array at index 0. The browser updates, but the editor's typed note does not stay with the transit story. Instead, the note "verify budget figures" now appears inside the note input for the brand new urgent story!

This bug happens because index keys force React to match elements by their numerical position (0 to 0, 1 to 1) rather than their real identity. When the new story enters at index 0, React compares the previous index 0 with the new index 0. React updates the text title inside the existing DOM node, but it leaves the internal input text untouched. The physical input stays at index 0, attached to the wrong article.

To solve this problem, React combines standard JavaScript array transformations with stable element keys. Instead of hardcoding markup or using fragile indices, you transform arrays of data into arrays of JSX elements using .map(). Crucially, you assign each item a stable, unique key prop based on permanent data (such as a database ID). This key gives each item a permanent identity across renders, ensuring that React moves the physical DOM node and its typed text to the correct new position.

⚡ IN THE WILD

Why do user inputs jump to the wrong item when using index keys?

When using array indices as keys (key={index}), React tracks elements purely by their numerical order rather than their data identity. When an item is prepended at index 0, every existing item shifts down by one position. React looks at index 0, sees that the title text changed, and mutates the existing DOM node in place. However, the browser's internal input buffer lives directly inside the physical DOM node. Because React reuses the existing node at index 0 instead of moving it, whatever text the user typed stays in that first box. To the user, their typed input appears to jump to the wrong story. To prevent this, you must always provide a permanent database ID (key={story.id}) so React can move the actual DOM node to its new position.

How JavaScript Transforms Arrays and How React Understands Collections

To understand how React renders lists, we must first look at what a list actually is in React. React does not introduce a proprietary <List> component or a custom loop directive like v-for or *ngFor. In React, a list is simply a standard JavaScript array containing JSX elements. In earlier lessons, you learned that curly braces {} inside JSX open an evaluation window for JavaScript expressions. When you put an array of JSX elements inside curly braces—such as {[<li key="1">A</li>, <li key="2">B</li>]}—React unpacks that array and renders each item in sequential order into the browser DOM.

For developers who are newer to JavaScript, let us briefly review the map() array method. The map() method is a standard JavaScript function available on all arrays. It takes a callback function, runs that function once on each item in the array, and returns a brand-new array containing the transformed items. The original array remains completely untouched. For example, [1, 2, 3].map(n => n * 2) produces [2, 4, 6]. In React, instead of multiplying numbers, our callback function takes a data object (like a story) and returns a JSX element (like <StoryRow key={story.id} story={story} />).

Next, let us review the difference between an arrow function with an implicit return and an arrow function with a block body. In JavaScript, when you write an arrow function without curly braces on the right side of the arrow (story => <StoryRow story={story} />), JavaScript uses an implicit return. It automatically returns the expression right after the arrow. However, if you add curly braces after the arrow (story => { ... }), you create a block body. A block body executes code statements line by line, but it returns undefined unless you explicitly write the return keyword. If you write stories.map(story => { <StoryRow story={story} /> }) the callback returns undefined for every story, and your list renders completely blank.

Finally, we must understand why React demands a key prop on every item in a list. When an application updates, React creates a new tree of element descriptions and compares it with the previous tree to decide what needs to change in the browser DOM. When React compares two lists of child elements, it needs a way to tell which item in the new list matches which item in the old list. Without keys, React falls back to positional matching: it compares the first new item to the first old item, the second to the second, and so on. If an item is inserted, deleted, or reordered, positional matching overwrites DOM nodes in place and scrambles state. With unique, stable keys, React can track each item throughout its lifetime, moving existing DOM nodes smoothly and preserving user inputs.

Principles of React: The Core Laws of Lists and Keys

When preparing for technical interviews, candidates must clearly explain how to transform arrays into JSX, why block bodies in arrow functions can cause silent blank screens, how React uses keys during reconciliation, why array indices and random numbers make dangerous keys, and why child components cannot read props.key. To master these concepts, we formalize the six governing principles of lists and keys:

PRINCIPLE 1

Build a List by Mapping Data to an Array of Elements

array transformation converting an array of raw data objects into a new array of JSX element descriptors using map
declarative list rendering placing an array of element descriptors inside JSX curly braces for React to unpack and render in order

We transform an array of data objects into an array of JSX elements using the standard JavaScript map() method. When we place the resulting array inside JSX curly braces, React automatically renders each element in sequential order. This ensures the structure of the user interface follows the data rather than hardcoded markup.

In React, the user interface is a direct projection of data (UI = f(data)). When you have a collection of items, you do not write imperative loops that append elements to the page one by one. Instead, you call stories.map(story => <StoryRow key={story.id} story={story} />)

Under the hood, map() runs your callback function once for every story in the array and returns a new array of lightweight React element objects in memory.

PRINCIPLE 2

Return the JSX from the Map Callback

expression body an arrow function without curly braces that automatically returns the single expression after =>
block body an arrow function with curly braces that requires an explicit return statement to output a value

When writing a map() callback function, ensure it returns a JSX element. If you use an arrow function with curly braces, you must write an explicit return statement. If you omit the return statement, the callback returns undefined for every item, and the list silently renders completely empty.

It is best practice to do this:
stories.map(story => (
<StoryRow key={story.id} story={story} />

))
Instead of doing this:
stories.map(story => {
<StoryRow key={story.id} story={story} />
Block body without return yields undefined
})

The official React documentation marks this pattern as an important pitfall because the mistake is completely silent. In JavaScript, an arrow function can be written with an expression body or a block body. In an expression body (story => <StoryRow ... />), there are no curly braces around the body, and JavaScript implicitly returns the value.

However, if you write curly braces after the arrow (story => { <StoryRow ... /> }), JavaScript treats those braces as a code block. Inside a code block, statements execute sequentially, but nothing is returned unless you explicitly write the return keyword.

When map() runs a block-body callback without a return statement over an array of ten stories, it collects ten undefined values and returns [undefined, undefined, ...]. Because React's suppression whitelist renders zero DOM nodes for undefined, the container element (<ul> or <div>) renders completely blank. The browser console produces no errors and no warnings. Whenever a list renders blank, check whether your arrow function uses curly braces without an explicit return.

PRINCIPLE 3

Put a Unique Key on the Outermost Element Returned by Map

outermost element the top-level JSX tag returned directly by the map callback function
sibling uniqueness the requirement that keys must be distinct among elements within the same array

Place the key prop on the outermost element directly returned inside the map() call, never on elements nested inside a child component. The key must be unique among its sibling elements in that array. If an item returns multiple sibling nodes, wrap them in a <Fragment key={...}> instead of an empty <> tag.

It is best practice to do this:
stories.map(story => (
<StoryRow key={story.id} story={story} />

Instead of doing this:
stories.map(story => (

When you do this, React immediately prints a warning in the console: "Warning: Each child in a list should have a unique 'key' prop. Check the render method of Feed."

PRINCIPLE 4

Treat Keys as the Identity React Uses to Match Items Between Renders

element identity a persistent identifier that ties a virtual element to its physical DOM node across renders
positional diffing React's fallback reconciliation model that compares items by numerical index when keys are missing or unstable

React uses keys as permanent identifiers to match elements between renders. When a list re-renders, React pairs each new element with the previous element that shares the same key and preserves its physical DOM node. Without keys, React pairs elements purely by position, rewriting DOM content in place and breaking local element state.

This principle explains the core mechanism behind React's reconciliation engine. When React renders components into the browser, it creates real DOM nodes. Certain DOM elements hold internal state that lives exclusively inside the browser: text typed into an uncontrolled <input>, the scroll position of a box, or the state of a checkbox.

When a list re-renders, React must decide whether to create new DOM nodes, delete old ones, or update existing nodes.

If you do not provide keys, or if you use array indices, React defaults to positional diffing. It compares index 0 to index 0, index 1 to index 1, and so on. When an urgent story is prepended at index 0, the story that was previously at index 0 moves to index 1. Because React compares by position, it looks at index 0, sees that the title changed, and updates the text of the existing DOM node in place. However, the browser's internal input buffer is not touched; whatever the user typed into the input at index 0 stays in that physical DOM node. To the user, their typed note suddenly jumps to the new urgent story!

When you provide stable keys (key={story.id}), React matches the previous story-1 element with the new story-1 element. It sees that story-1 moved from index 0 to index 1, and it physically moves the existing DOM node in the page. The input text, focus, and cursor position move along with their story.

PRINCIPLE 5

Key Items by a Stable ID from the Data, Never by Array Index or Random Values

stable identifier a permanent ID tied to a data entity that never changes throughout the application lifetime
random key churn generating keys on the fly during render, causing React to destroy and recreate the entire DOM tree on every update

Always use a permanent, stable identifier from your data as the key, such as a database ID or a unique ID created when the item was first generated. Never use the array index for lists that can change, and never generate keys during render using Math.random(). Random keys force React to recreate all DOM nodes on every render, losing focus and destroying performance.

It is best practice to do this:
stories.map(story => (
<StoryRow key={story.id} story={story} />
Stable database ID persists across renders
))
Instead of doing this:
stories.map(story => (
<StoryRow key={Math.random()} story={story} />
Random key forces complete DOM teardown and recreation on every render
))

A key must be stable across renders. There are three common sources of keys: permanent database IDs from server data (story.id), locally generated IDs created once when an item is created (crypto.randomUUID()), and array indices.

You should only use the array index as a key if your list meets three strict conditions: the list is completely static, it will never be filtered or reordered, and items will never be added or removed.

Generating keys on the fly during render with key={Math.random()} is even worse than using indices. Because Math.random() executes on every single render pass, every element gets a completely new key every time the component updates.

When React compares the new tree with the old tree, none of the keys match. React assumes that all previous items were deleted and that completely new items were created. It tears down all existing DOM nodes and rebuilds them from scratch. This drops typing focus, wipes input values, and causes noticeable visual lag. Keys must remain constant across renders for the same data entity.

PRINCIPLE 6

Pass the ID as Its Own Prop When the Component Needs It

reserved prop a prop like key or ref that React consumes internally and excludes from props
explicit data passing passing an identifier under a distinct prop name so child components can read it

React reserves the key prop for its internal reconciliation engine and does not pass it down to your component. If a child component needs the story's ID for links, event handlers, or accessibility labels, you must pass it as a separate, explicitly named prop such as id={story.id} or pass the entire story object.

It is best practice to do this:
<StoryRow key={story.id} id={story.id} story={story} />
Explicit id prop accessible inside child component
Instead of doing this:
<StoryRow key={story.id} story={story} />
Component attempts to read props.key directly, yielding undefined

Developers are often surprised to find that reading props.key inside a child component returns undefined. If an engineer writes <button onClick={() => deleteStory(props.key)}>Delete</button> the delete function receives undefined, and React prints a warning in the console: "Warning: StoryRow: key is not a prop. Trying to access it will result in undefined being returned. If you need to access the same value within the child component, you should pass it as a different prop."

React consumes key (and ref) internally for its fiber and reconciliation system and intentionally strips it from the component's props object. If your component needs the ID—for example, to build a link URL <a href={/story/${storyId}}>, set an HTML data-id attribute, or trigger a callback—you must pass the ID under an ordinary prop name such as id, storyId, or pass the whole story object and read story.id.

Rendering lists in React is built on standard JavaScript array transformations and explicit element identity. By using map() to project data arrays into JSX descriptors, your application's user interface stays perfectly synchronized with your data. By placing stable, unique keys on the outermost element returned by map(), you give React the identity information it needs to preserve DOM nodes, protect user inputs, and update lists efficiently.

Where you will meet this

  1. Dynamic Content Feeds and Catalogs: In news portals, social media feeds, and product catalogs, you map collections of server data into card components, using permanent entity database IDs as keys to allow smooth filtering and insertion.
  2. Interactive Form Repeaters: In invoice generators, survey builders, or recipe ingredient lists where users can add, remove, and reorder input rows, stable keys ensure that typed text and active cursor focus never jump between rows when an item is deleted.
  3. Tabbed Navigation and Menus: When rendering navigation bars or tab lists from an array of routes, stable keys allow React to track which tab is active without tearing down DOM nodes during tab switching.

Glossary

  • Array Transformation ◼ Using methods like map to convert an array of raw data objects into a new array of JSX element descriptors.
  • Key Prop ◼ A special string or number attribute passed to list elements that React uses to identify items across renders.
  • Positional Diffing ◼ React's fallback reconciliation behavior when keys are absent or based on array index, comparing elements purely by sequential position.
  • Element Identity ◼ The association between a React virtual element and its persistent browser DOM node established by a stable key.
  • Key Churn ◼ An antipattern where keys change on every render (such as from Math.random), forcing React to destroy and recreate all DOM nodes.
  • Reserved Prop ◼ A prop such as key or ref that React consumes internally for reconciliation and does not pass down to the component.
