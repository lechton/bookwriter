Lecture 6: Passing Data into Components with Props

Interview Question

CORE

How do you pass data into a component, and why can a component never change its own props?

Imagine this scenario:

  1. Julian builds the front-page news feed for The National Times.
  2. He creates an ArticleCard component, but every card on the homepage renders the exact same static headline.
  3. When Julian passes a title attribute and tries to edit it inside the child, React throws a TypeError: Cannot assign to read only property.
  4. Why does a component have no right to modify the data it receives from its parent?
  5. Sibling cards desynchronize, rendering passes become non-deterministic, and the UI tree loses its single source of truth.
  6. Props are read-only snapshots; React freezes them in development to enforce unidirectional data flow.
  7. Today, you will master component props, parameter destructuring, and the immutability contract that keeps React predictable.

The Identical Clones and the Mutation Trap

In plain HTML, tags take attributes like src or href to customize their behavior. When building reusable React components, hardcoding static text inside a function produces identical clones. If an editorial page renders three <ArticleCard /> elements with hardcoded text, every card displays the exact same headline and author. To make components reusable across different stories, you must pass dynamic data into them from their parent.

When developers attempt to modify props inside a child component, JavaScript throws an unhandled runtime exception.

In development mode, React invokes Object.freeze() on the props object before passing it into your component function. Attempting to assign props.title = ... in strict mode triggers TypeError: Cannot assign to read only property 'title' of object '#<Object>'. But why does React freeze props? Because React relies on unidirectional data flow. Data flows strictly downward from parent to child. If a child could mutate its own props, it would silently alter data shared with sibling components or cache layers, destroying deterministic rendering and breaking React's ability to know when components need updating.

⚡ IN THE WILD

Why does React freeze props in development but not in production? When developers see Object.freeze in development, they wonder why production builds omit the freeze. Is mutating props legal in production? No! Mutating props in production is still a catastrophic anti-pattern that causes desynchronized state and ghost renders. React skips Object.freeze in production purely for raw execution performance: deeply freezing thousands of prop objects on every render pass would slow down rendering on low-powered mobile devices. The development freeze is an automated safety net to catch mutation bugs before your code reaches production.

Interview Tip

To impress the interviewer: When asked why a component cannot change its own props, explain that props are read-only input snapshots governed by unidirectional data flow. Mutating props violates component purity, breaks memoization and reconciliation assumptions, and corrupts shared state across siblings. Mention that React freezes props in development with Object.freeze to enforce this contract.

Principles of React: The Core Laws of Component Props

To prepare for any technical interview, we must separate static HTML attribute string passing from React's dynamic prop pipeline and establish the fundamental laws governing how components receive and protect data. In React, props represent immutable inputs that flow strictly downward from parent to child, enabling deterministic rendering and reusable UI building blocks. We formalize these rules into five standalone principles.

PRINCIPLE 1

Pass Dynamic Data Exclusively Downward via JSX Attributes

You must pass configuration data into child components by declaring custom JSX attributes on the component tag, strictly avoiding hardcoded component bodies.

In senior engineering interviews, component reusability begins with parameterization:

  1. Hardcoded Component Clones (Anti-Pattern): Inlining static text inside a component function produces identical visual clones. If a newsroom homepage requires three article cards, hardcoded components force developers to duplicate the entire component file for every distinct story.
  2. Dynamic Prop Parameterization (Idiomatic): Declaring JSX attributes like title={headline} transforms a static template into a parameterized blueprint. The parent component owns the dynamic data, while the child focuses exclusively on visual presentation. Multiple instances render distinct headlines from a single component declaration.

PRINCIPLE 2

Unpack Props in Function Headers with Parameter Destructuring

parameter destructuring unpacking object keys directly in the function argument list
repetitive dot notation repeating props.title across every expression in JSX markup

You must unpack props directly in the component function signature using parameter destructuring ({ title, author }), avoiding repetitive props. dot notation.

It is best practice to do this:
function Card({ title }) { return (<h2>{title}</h2>); }
Instead of doing this:
function Card(props) { return (<h2>{props.title}</h2>); }

Interviewers evaluate how cleanly candidates structure function headers to communicate component contracts:

  1. Object Parameter with Dot Notation: Accepting props as a single object parameter forces developers to prefix every identifier with props. throughout the JSX markup. While functional, it clutters expressions and forces engineers to scan the entire function body to discover which props the component actually requires.
  2. Parameter Destructuring (Modern Standard): Unpacking keys directly in the function signature ({ title, author }) serves as self-documenting code. Any developer inspecting the function header immediately sees its required inputs. The local identifiers become direct variables in scope, keeping JSX clean.

PRINCIPLE 3

Treat Props as Strictly Immutable Input Snapshots

read-only snapshots data objects frozen by the runtime that cannot be modified by the receiver
direct mutation attempting to reassign properties like props.title = '...'

You must treat incoming props as read-only snapshots governed by unidirectional data flow, strictly avoiding any direct mutation of the props object.

We should do this:
const upper = title.toUpperCase();
We should not do this:
props.title = props.title.toUpperCase();

Understanding the immutability contract is central to mastering React's execution model:

  1. Unidirectional Data Flow: Data flows in a single direction from parent to child. The parent owns the state, and the child merely receives an immutable snapshot. If a child component could mutate props.title, it would silently alter data belonging to the parent or shared across sibling components.
  2. Component Purity and Determinism: A pure component must behave like a mathematical function: given identical inputs, it must always produce identical JSX output without side effects. Mutating props destroys component purity, invalidates memoization caches, and produces desynchronized ghost renders.

PRINCIPLE 4

Provide Fallback Values Using ES6 Default Parameters

default values in parameter destructuring ES6 default values that apply when a prop argument is undefined
omitted or undefined when a parent renders a tag without supplying that specific attribute

You must assign default values in parameter destructuring ({ category = 'general' }) to protect components when props are omitted or undefined.

It is best practice to do this:
function Card({ category = 'news' }) { return (<span>{category}</span>); }
Instead of doing this:
function Card(props) { const cat = props.category || 'news'; return (<span>{cat}</span>); }

Senior engineers handle missing props gracefully without introducing brittle fallback chains:

  1. The Undefined Trap: When a parent omits an optional prop on a JSX tag, JavaScript sets that property to undefined. If your component attempts to invoke methods on an undefined prop (such as category.toUpperCase()), the application halts with an unhandled TypeError.
  2. ES6 Default Parameters: Assigning default values during destructuring ({ category = 'general' }) ensures the component always receives a valid value. Note that default parameters activate exclusively when the incoming prop is undefined (or omitted). If a parent explicitly passes null or "", the default value does NOT activate.

Glossary

  • Props: The read-only inputs passed from a parent component downward to a child component via JSX attributes.
  • Unidirectional Data Flow: The architectural rule in React where data flows strictly in one direction from parent to child.
  • Parameter Destructuring: The JavaScript syntax ({ title, author }) that unpacks properties from the props object directly in the function signature.
  • Object.freeze: The JavaScript runtime method React calls in development on the props object to prevent accidental property mutations.
  • Immutability Contract: The non-negotiable rule that components must never alter their inputs, ensuring deterministic rendering.

Beyond the basics

  • Props freezing in development vs production: React freezes props with Object.freeze() in development to catch illegal mutations, but omits it in production for raw execution speed (see react.dev/learn/passing-props-to-a-component).
  • Default prop values via destructuring: You can assign fallback values during destructuring via { author = 'Staff Reporter' }, which apply when the prop is undefined (see react.dev/learn/passing-props-to-a-component#specifying-a-default-value-for-a-prop).
  • JSX spread syntax for forwarding props: Passing multiple props can be streamlined using the spread operator <ArticleCard {...storyProps} />, though explicit props are preferred for clarity (see react.dev/learn/passing-props-to-a-component#forwarding-props-with-the-jsx-spread-syntax).
  • Props as function arguments: JSX compiles <ArticleCard title="News" /> directly to _jsx(ArticleCard, { title: "News" }), proving that props are simply the second argument to the element factory (see react.dev/learn/passing-props-to-a-component).
  • Pure components and deterministic rendering: A component that never mutates props behaves as a pure function: given the same props, it always renders the exact same output (see react.dev/learn/keeping-components-pure).
