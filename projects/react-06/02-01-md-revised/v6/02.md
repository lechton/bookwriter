### The Silent Blank Screen of Lowercase Tags

In standard JavaScript development, developers follow camelCase naming conventions for almost every identifier. You write helper functions named `calculateReadingTime()`, declare variables named `activeArticle`, and attach event handlers named `handleSubscribe()`. When starting out with React, developers naturally carry this established muscle memory forward. You write `articleCard()`, assemble headline and summary markup inside its body, and mount it as `<articleCard />`. The syntax looks clean, the code editor shows no red squiggles, and the terminal build finishes with zero errors.

When you refresh the browser page, the article card is completely missing. The terminal reports no errors, and the browser developer console reports zero warnings. When you inspect the living page in the Elements panel, you find a bizarre custom tag: `<articlecard></articlecard>`. The browser treated your component tag as a native HTML element instead of executing your JavaScript function. The browser ignores the unknown tag, skips your function, and leaves an empty white screen.

To see this failure in concrete code, examine how a junior developer attempts to declare and mount a news card:

```jsx title="Naive Component Declaration"
function ~articleCard~() { // Lowercase name prevents compiler invocation
  return (
    <article className="article-card">
      <h2>Morning Dispatch</h2>
    </article>
  );
}
export default function App() {
  return <~articleCard~ />; // Compiles to literal HTML string
}
```

Notice what happened under the hood. When the JSX transpiler parsed `<articleCard />`, it looked at the very first letter of the tag. Because the letter `a` is lowercase, the compiler assumed `<articleCard />` was a native HTML tag like `<div>` or `<article>`. It compiled the tag into `_jsx("articlecard", {})`. At runtime, React passed this string literal directly to `document.createElement("articlecard")`. The browser instantiated a generic, unstyled `HTMLUnknownElement` and appended it to the DOM. Your component function `articleCard()` sat completely forgotten in JavaScript memory.

When the browser encounters an unknown tag in markup, it does not throw an exception. The HTML specification dictates that unrecognized tag names instantiate a generic `HTMLUnknownElement` DOM node. The JSX compiler converted `<articleCard />` into a string literal request for `"articlecard"`. React instructed the browser to create that unknown element directly. Your function `articleCard()` remained idle in JavaScript memory, completely untouched by React's rendering pipeline.

> [!WILD]
> **Why do lowercase custom tags fail silently in the browser?**
>
> When the browser parser encounters an unrecognized HTML tag name, it never throws a syntax error. Under the W3C HTML living standard, browsers instantiate an `HTMLUnknownElement` DOM node with default inline layout styles. The JSX compiler branches on tag identifier casing. Lowercase identifiers compile into string literals for `document.createElement()`. Uppercase identifiers compile into direct function references. The browser allows unknown HTML tags for backwards compatibility, rendering the element completely invisible with zero console warnings.

### What is a React Component and How Does JSX Compile Markup?

A React component is the foundational building block of modern web applications. At its core, a component is a standard JavaScript function that returns a description of a user interface written in JSX. Unlike monolithic HTML files where markup, style, and scripts live in separate silos, a React component unifies structure and presentation into an isolated, reusable unit. When you declare `ArticleCard()`, you are defining a reusable blueprint for a slice of the page. Every time React evaluates this component, it executes the function to calculate what elements should appear on the screen.

In standard JavaScript runtimes, JSX markup is not valid language grammar. Browsers cannot parse tags like `<ArticleCard />` natively. Before your code reaches the browser, a compiler like Babel or SWC parses your source code into an **Abstract Syntax Tree** (AST). When the parser encounters an opening angle bracket, it inspects the very first character of the tag name. If the character is lowercase, the compiler treats the tag as a built-in DOM element, emitting `_jsx("article")`. If the character begins with an uppercase letter, the compiler emits an unquoted function identifier: `_jsx(ArticleCard)`.

React models every component as a pure mathematical projection: `UI = f(data)`. A component function must behave as a pure calculation that returns UI descriptors without modifying outside state. When React calls your component, it expects the function to evaluate its inputs and return JSX markup or `null`. If a component tries to manipulate the DOM imperatively inside its body, it breaks React's ability to coordinate screen updates across renders.

To coordinate updates safely, React splits execution into two distinct stages: the **Render Phase** and the **Commit Phase**. In the render phase, React executes your component function in memory to produce a lightweight JavaScript object called a **UI descriptor**. React attaches this descriptor to an internal **Fiber node**. This Fiber node tracks component position, lifecycle, and scheduled updates. Only during the subsequent commit phase does React touch the real browser DOM, inserting or updating living HTML elements. Calling a component function directly as `{ArticleCard()}` bypasses fiber creation, breaking React's ability to manage the component in memory.

### Principles of React: Component Anatomy and Invocation

When preparing for senior engineering interviews, candidates must explain why React enforces strict capitalization, purity, and return contracts for components. To master this architecture, we formalize the four governing principles of component anatomy and invocation:

> [!PRINCIPLE]
> **Principle 1: Enforce PascalCase Capitalization to Emit Function Identifiers**
> Always name custom components with an initial capital letter in **PascalCase** so the JSX compiler emits an unquoted function identifier. A lowercase tag instructs the compiler to emit a string literal. The browser instantiates an empty unknown HTML element, skipping your component function.
> 
> >> PascalCase : naming convention where the first letter of each compound word is capitalized
> >> function identifier : an unquoted reference to a JavaScript function in memory
> 
> *We should do this:*
> `function ArticleCard() {`
> `  return <h2>Morning Dispatch</h2>;`
> `}`
> `<~ArticleCard~ /> // React runs capitalized component function`
> 
> *We should not do this:*
> `function articleCard() {`
> `  return <h2>Morning Dispatch</h2>;`
> `}`
> `<~articleCard~ /> // Lowercase tag creates empty HTML element`

In standard JavaScript, functions are written in camelCase by default. Developers naturally write `function articleCard()` and mount `<articleCard />`. The compiler parses the tag and checks the Unicode category of the first letter. Because `a` is lowercase, the compiler emits a string literal: `_jsx("articlecard", {})`.

Look at the naive implementation where the component function uses a lowercase initial letter:

```jsx title="Component Source (Lowercase Anti-Pattern)"
function ~articleCard~() { // Lowercase initial letter disables component
  return (
    <article className="article-card">
      <h2>~Morning Dispatch~</h2> // Renders inside unrecognized HTML tag
    </article>
  );
}
```

The JSX compiler parses the tag identifier `<articleCard />` and observes that the first character is lowercase. Instead of emitting a reference to your JavaScript function, it emits a string literal:

```jsx title="Compiler Output (String Literal)"
_jsx(~"articlecard"~, {}) // Emits string literal to createElement
```

At runtime, React passes this string directly to `document.createElement("articlecard")`. Because the browser does not recognize this custom tag, it creates an empty `HTMLUnknownElement` DOM node:

```html title="Browser DOM Render (Empty Unknown Element)"
<~articlecard~></articlecard> <!-- Empty unknown element in DOM -->
```

The browser screen remains completely blank, and your function `articleCard()` is never invoked. Now, examine the correct implementation using PascalCase capitalization:

```jsx title="Component Source (PascalCase Standard)"
function ~ArticleCard~() { // Capitalized name signals custom component
  return (
    <article className="article-card">
      <h2>~Morning Dispatch~</h2> // Renders headline inside valid markup
    </article>
  );
}
```

When you capitalize the component name to `ArticleCard`, the compiler detects an uppercase initial character. It immediately emits an unquoted function identifier:

```jsx title="Compiler Output (Function Identifier)"
_jsx(~ArticleCard~, {}) // Emits direct function reference pointer
```

Notice the physical shift in the compiler's output. By capitalizing the tag identifier to `<ArticleCard />`, the AST parser treats `ArticleCard` as a live variable in JavaScript memory rather than an unknown HTML tag name. When React evaluates `_jsx(ArticleCard, {})` at runtime, it resolves the function pointer from memory, invokes `ArticleCard()`, and takes custody of the returned `<article>` descriptor tree. The browser engine receives valid semantic elements instead of an empty unknown tag, painting the headline and story summary cleanly to the screen.

> [!PRINCIPLE]
> **Principle 2: Keep Component Rendering Pure and Free of Outside Side Effects**
> Treat component functions as pure calculations that produce identical UI descriptors for identical inputs. Rendering code must never mutate external variables, alter outside objects, or perform imperative DOM updates. In development, React StrictMode intentionally calls your function twice to expose impure side effects.
> 
> >> pure calculation : a function that depends only on its inputs and causes zero observable outside side effects
> >> side effect : any modification of outside state, global memory, or external DOM nodes during render
> 
> *We should do this:*
> `function ArticleCard({ edition }) {`
> `  const ~headline~ = `Edition #${edition}`; // Calculates output purely from inputs`
> `  return <h2>{headline}</h2>;`
> `}`
> 
> *We should not do this:*
> `let ~editionCount~ = 0; // External variable outside component`
> `function ArticleCard() {`
> `  ~editionCount~ += 1; // Mutating outside variable corrupts render`
> `  return <h2>{editionCount}</h2>;`
> `}`

Developers are sometimes tempted to increment analytics counters, format external caches, or mutate global variables directly inside the component body:

```jsx title="Component Source (Impure Render Mutation)"
let ~renderCount~ = 0; // External variable outside component scope
function ArticleCard() {
  ~renderCount += 1~; // Mutating outside variable corrupts render
  return (
    <article className="article-card">
      <h2>Morning Dispatch #~{renderCount}~</h2> // Displays impure counter
    </article>
  );
}
```

In development mode, `React.StrictMode` intentionally mounts every component twice to detect hidden side effects. Look at the visual output on screen:

```html title="StrictMode Double-Invocation Output"
<h2>
  Morning Dispatch #~2~ <!-- StrictMode invocation doubles count -->
</h2>
```

The rendered number skips from 0 straight to 2! If an update triggers, the number jumps unpredictably. To fix this, keep component rendering strictly pure:

```jsx title="Component Source (Pure Calculation)"
function ArticleCard({ ~edition~ = 1 }) { // Pure calculation from input props
  const title = `Morning Dispatch #${edition}`;
  return (
    <article className="article-card">
      <h2>{~title~}</h2> // Headline derives purely from inputs
      <p>Investigative newsroom report.</p>
    </article>
  );
}
```

This strict requirement stems directly from React's declarative formula: `UI = f(data)`. Because pure functions cause zero outside mutations, the React runtime can execute them repeatedly in memory without corrupting application state. In modern concurrent rendering, React frequently pauses, discards, or re-runs rendering passes in the background to keep typing and animations responsive. When your components are pure calculations, aborted renders leave zero abandoned variables or polluted caches behind, guaranteeing that the interface remains completely predictable.

> [!PRINCIPLE]
> **Principle 3: Fulfill the Pure Return Contract and Use Null to Explicitly Suppress Output**
> Every component function must return a valid React element, Fragment, or `null`. Forgetting a return statement causes the function to evaluate to `undefined`, triggering a fatal development crash. To intentionally render nothing on screen, explicitly return `null` so React paints an empty slot cleanly.
> 
> >> return contract : the requirement that a component return a valid element descriptor or null
> >> null suppression : explicitly returning null to render nothing without triggering an undefined crash
> 
> *We should do this:*
> `function DraftCard({ isLive }) {`
> `  if (!isLive) return ~null~; // Tells React to render nothing safely`
> `  return <article>Dispatch</article>;`
> `}`
> 
> *We should not do this:*
> `function DraftCard({ isLive }) {`
> `  if (!isLive) ~return~; // Returns undefined and crashes React`
> `  return <article>Dispatch</article>;`
> `}`

In standard JavaScript functions, omitting a return value returns `undefined` by default. When developers write conditional rendering logic, they often forget an `else` branch or write a bare `return;` hoping to skip output:

```jsx title="Component Source (Undefined Return Bug)"
function ArticleCard({ isPublished }) {
  if (!isPublished) {
    ~return;~ // Bare return produces fatal undefined
  }
  return <article className="card">Morning Dispatch</article>;
}
```

When React evaluates this function, it catches `undefined` immediately. In development mode, the runtime halts execution and displays a fatal red error overlay:

```text title="Fatal Development Crash"
Error: Nothing was returned from render // Halts execution on undefined render
Tip: return statement was missing
Fix: to render nothing, return ~null~ // Explicit requirement for empty output
```

Why does React crash on `undefined`? To protect developers from subtle typos, such as writing `return` on one line and JSX on the next without parentheses (triggering Automatic Semicolon Insertion). If you genuinely intend to render nothing (such as suppressing an unpublished draft), you must explicitly return `null`:

```jsx title="Component Source (Explicit Null Return)"
function ArticleCard({ isPublished }) {
  if (!isPublished) {
    return ~null~; // Explicitly signals empty output slot
  }
  return <article className="card">Morning Dispatch</article>;
}
```

Returning `null` acts as an explicit instruction rather than an accidental omission. When React's reconciliation engine receives `null`, it allocates an empty leaf slot in the Fiber tree while deliberately skipping any DOM node creation. The component retains its registered position in the hierarchy without emitting unnecessary elements. When props update later—such as changing `isPublished` to `true`—React re-evaluates the component and mounts the article card seamlessly, without ever throwing undefined runtime errors.

> [!PRINCIPLE]
> **Principle 4: Render Components Using Declarative JSX Tags, Not Direct Function Calls**
> Mount components using declarative JSX tags like `<ArticleCard />` so React registers an independent element descriptor `{ type: ArticleCard }`. Invoking a component directly as a plain JavaScript function `{ArticleCard()}` inlines child elements into the parent, stripping component boundaries and breaking lifecycle tracking.
> 
> >> declarative JSX tag : syntax creating a component element descriptor managed by React
> >> direct function invocation : executing a function inline as plain JavaScript without element identity
> 
> *We should do this:*
> `<main>`
> `  <~ArticleCard~ /> // Gives React custody of component lifecycle`
> `</main>`
> 
> *We should not do this:*
> `<main>`
> `  {~ArticleCard~()} // Inlines HTML directly and skips component tracking`
> `</main>`

Because a React component is a standard JavaScript function, developers frequently ask: "Why can't I simply invoke it with curly braces inside JSX?"

```jsx title="Direct Function Invocation (Inlined Fragment)"
function App() {
  return (
    <main className="national-times-app">
      {~ArticleCard~()} // Inlines return value directly into parent
    </main>
  );
}
```

Look at the compiled output when you invoke a component function directly:

```jsx title="Compiler Output (Synchronous Inlining)"
_jsx("main", {
  className: "national-times-app",
  children: ~ArticleCard~() // Evaluated synchronously inside parent arguments
})
```

The function `ArticleCard()` runs immediately as plain JavaScript. The parent element receives raw child markup directly, but React never registers `ArticleCard` as a distinct node in its virtual DOM tree. React cannot attach a dedicated Fiber node, cannot isolate re-renders, and cannot manage future state hooks or lifecycles.

Now, examine the declarative approach where you mount the component as a JSX tag:

```jsx title="Declarative Element Invocation"
function App() {
  return (
    <main className="national-times-app">
      <~ArticleCard~ /> // Declared as independent React element
    </main>
  );
}
```

The compiler transforms this tag into an independent element descriptor:

```jsx title="Compiler Output (Component Fiber Descriptor)"
_jsx("main", {
  className: "national-times-app",
  children: _jsx(~ArticleCard~, {}) // Independent component descriptor node
})
```

When you mount the component as a JSX tag `<ArticleCard />`, React creates a dedicated Fiber node in the virtual DOM tree tagged with `type: ArticleCard`. This Fiber node establishes an independent component boundary. React schedules the component's execution within its own lifecycle scope, allowing it to preserve local state hooks and optimize updates. If `ArticleCard` needs to re-render in response to future data changes, React evaluates only that component subtree, preserving performance without re-running the entire parent `App` container.

| **CONTRACT DIMENSION**<br>(architectural layer) | **NAIVE JAVASCRIPT REFLEX**<br>(anti-pattern or trap) | **REACT COMPONENT REALITY**<br>(compiler and runtime contract) | **ENGINE RATIONALE**<br>(platform consequence) |
| :--- | :--- | :--- | :--- |
| **1. PascalCase Naming** | Lowercase camelCase: `function articleCard()` | PascalCase uppercase: `function ArticleCard()` | AST branches on ASCII casing: string literal vs unquoted function identifier |
| **2. Render Purity** | Mutating outside variables or caches during render | Pure mathematical calculation: `UI = f(data)` | StrictMode double-invocation exposes mutations; concurrent render resilience |
| **3. Return Contract** | Forgetting return or returning `undefined` | Returning valid element descriptor or `null` | Development crash: `Nothing was returned from render` vs clean null slot |

```

```

### Step 1: First, we construct the article card component <ArticleCard.jsx>

We construct the standalone article card component `ArticleCard.jsx` to encapsulate headline and summary copy into an isolated, reusable function. Notice that the function name begins with an uppercase letter: `ArticleCard`. This PascalCase naming guarantees that the JSX compiler treats `<ArticleCard />` as a custom component rather than an unknown HTML tag. The component function contains no hardcoded DOM queries, mutates no external variables, and returns semantic HTML elements wrapped in a single root `<article>` tag.

When returning multi-line JSX markup from a component function, you encounter a foundational JavaScript syntax crossroad:
- **Option 1 (The Foundational Way)**: Write a naked multi-line return without wrapping parentheses, exposing the code to Automatic Semicolon Insertion.
- **Option 2 (The Modern Idiomatic Way)**: Wrap the multi-line JSX expression in parentheses, signaling to the parser that the return expression continues across lines.

First, examine Option 1 with a naked multi-line return:

```jsx title="Option 1: The Foundational Way (Naked Multi-Line Return)"
export default function ArticleCard() {
  ~return~ // Parser automatically inserts semicolon here
    <article className="article-card">
      <h2>~Morning Dispatch~</h2> // Unreachable code never evaluated
    </article>;
}
```

In Option 1, the JavaScript engine encounters a newline immediately after the `return` keyword. Under the rules of Automatic Semicolon Insertion (ASI), the parser inserts a semicolon after `return;`. The function immediately terminates and returns `undefined`. The JSX markup on the following line is never evaluated, and the browser displays a blank card with zero errors.

Now, examine Option 2 with defensive parenthesized return wrapping:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() {
  return ( // Parentheses prevent automatic semicolon insertion
    <article className="article-card">
      <h2 className="headline">~Morning Dispatch~</h2> // Story headline text
      <p className="summary">~Civic report.~</p> // Descriptive summary text
    </article>
  );
}
```

In Option 2, the opening parenthesis `(` tells the ECMAScript parser that the return expression continues across multiple lines. Semicolon insertion is prevented, and the component function reliably evaluates the entire JSX tree. Notice how `ArticleCard.jsx` functions as a pure presentation component: it owns no state, requires no external DOM lookups, and cleanly packages the newsroom card into a predictable, reusable unit.

Notice how `ArticleCard.jsx` satisfies the core architectural rules of component anatomy:
1. It uses PascalCase naming (`ArticleCard`) so the compiler treats it as a custom component.
2. It returns a single root container element (`<article>`) satisfying JavaScript expression return grammar.
3. It encloses its multi-line return inside parentheses to neutralize Automatic Semicolon Insertion traps.
4. It operates as a pure rendering calculation without touching external memory or the browser DOM.

### Step 2: Finally, we mount the card declaratively inside <App.jsx>

To complete our application layout, we mount `ArticleCard.jsx` inside the root container `App.jsx`. In standard JavaScript development, inserting a new widget required querying an existing container with `document.querySelector` and appending elements imperatively. In React, the entire document organizes into a declarative hierarchy. Notice that `App.jsx` imports `ArticleCard` as an unquoted JavaScript identifier and mounts it using the self-closing tag `<ArticleCard />`. We do not call `ArticleCard()` directly with parentheses; writing `<ArticleCard />` tells React's mounting engine to register an independent fiber node in the render tree and execute the component during the render pass.

```jsx title="App.jsx"
import ArticleCard from './components/ArticleCard.jsx';

export default function App() {
  return (
    <main className="national-times-app">
      <~ArticleCard~ /> // Mounts component declaratively as tag
    </main>
  );
}
```

When React evaluates `App`, the JSX compiler transforms `<ArticleCard />` into `_jsx(ArticleCard, {})`. React attaches the component to its virtual tree, executes `ArticleCard()` in memory, and paints the returned `<article>` node inside `<main>` in a single atomic operation. Because the component follows PascalCase naming and declarative invocation, the browser receives living, semantic DOM elements without manual query scripts or silent lowercase failures.

Notice how `App.jsx` establishes clean declarative boundaries:
1. It imports `ArticleCard` as a first-class function identifier from its module path.
2. It mounts `<ArticleCard />` as a declarative JSX element, registering a dedicated fiber node.
3. It performs zero manual DOM querying or element manipulation, delegating page mounting to React.

### Where you will meet this

1. **Design System Component Libraries**: When authoring buttons, modals, input cards, and layout grids in a shared corporate design system, every component must enforce PascalCase naming to ensure downstream consuming applications can mount them as standard JSX tags without compiler confusion.
2. **Micro-Frontend Layout Shells**: In large enterprise web applications where independent teams ship isolated widgets into a unified page, mounting widgets declaratively as `<DispatchWidget />` allows the parent shell to manage lifecycles and error boundaries without executing arbitrary synchronous function calls.

### Glossary

- **Component**: A self-contained, reusable JavaScript function whose name starts with an uppercase letter and returns a tree of UI descriptors written in JSX.
- **PascalCase**: A naming convention where the first letter of each compound word is capitalized, used by the JSX compiler to distinguish custom component functions from native HTML elements.
- **UI Descriptor**: A lightweight JavaScript object produced by the JSX transpiler that describes what elements, attributes, and children should appear on the screen.
- **Fiber Node**: An internal React data structure that represents a component instance in memory, tracking its lifecycle, hooks, and position in the virtual DOM tree.
- **Render Phase**: The initial computational phase of React's execution where component functions are evaluated in memory to produce UI descriptor trees without modifying the living browser DOM.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Component Function Naming

➔ ALWAYS name custom components in PascalCase so the JSX compiler emits an unquoted function identifier rather than an HTML string literal.

➔ NEVER define component functions in lowercase or camelCase because the browser treats lowercase tags as native elements and fails silently.

❒ Markup Return Invariants

➔ ALWAYS wrap multi-line JSX return statements in parentheses to prevent the JavaScript engine from inserting an unintended semicolon.

➔ ALWAYS return a single root element or React Fragment so the component evaluates to a single valid JavaScript return expression.

❒ Declarative Invocation and Purity

➔ ALWAYS mount components as declarative JSX tags like `<ArticleCard />` so React registers the component fiber node and tracks its lifecycle.

➔ NEVER invoke component functions directly as raw JavaScript calls like `{ArticleCard()}` because direct execution bypasses React's virtual DOM tree and hook isolation.
