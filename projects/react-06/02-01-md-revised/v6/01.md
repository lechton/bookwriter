# Lecture 1: What is React and the Declarative Model
> INTERVIEW QUESTION | ❱ CORE | What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

1. Clara Foster logs into The National Times website to read the morning investigative edition.
2. Clara updates her subscriber profile name from "Clara F." to "Clara Foster" in account settings.
3. The vanilla JavaScript script queries the page to update the reader's name across every widget.
4. Why does the greeting bar update while the subscriber tier badge stays frozen on the old name?
5. Readers see mismatched account names, suspecting credential leaks and submitting urgent support tickets.
6. An engineer renamed a markup container ID, leaving the imperative query script searching for an element that no longer exists.
7. Today, we replace fragile element hunting with a single data source that synchronizes every widget automatically.

### The Fragility of Imperative DOM Hunting

Think back to the very first script you ever wrote in vanilla JavaScript. You had an HTML tag on the page, like `<span id="user-greeting">Guest</span>`. When the user logged in, you reached into the browser using `document.getElementById('user-greeting')` and manually reassigned its `textContent`. For a single element, this works reliably.

But on a real production website like The National Times, Clara Foster's name does not live in just one place. It appears in the top navigation bar, inside a subscriber badge, and across the mobile drawer. To update her name, you cannot simply change the data in memory. You must physically track down every matching HTML tag across the document. You query each node by hand. Then, you push the new text into the living DOM node.

Suppose a designer renames an element ID in the HTML template. Or imagine adding a new subscriber badge to the sidebar. Your existing query function silently misses the new element. The reader sees conflicting names on the same screen. This failure creates immediate **state drift** between application memory and the screen pixels.

To see this friction in plain JavaScript, consider an update function that queries elements across the header:

```js title="Naive DOM Scripting"
function updateHeaderUser(user) {
  const nav = document.getElementById('greeting');
  if (nav) nav.textContent = ~user.name~; // Manually pushes text to node
  const badge = document.getElementById('badge');
  if (badge) badge.textContent = ~user.tier~; // Misses unqueried elements
}
```

Notice what went wrong. The code assumes every element exists in the document. It couples directly to markup IDs. Worse, it completely forgets the mobile drawer greeting if an element is added later. When Clara Foster views her profile on a phone, the mobile header still displays her old account name. The application now suffers from **state drift**: the user data in memory does not match the user interface on screen.

Developers often try to avoid individual queries by re-rendering containers with `element.innerHTML`. This approach triggers a catastrophic browser side effect. The browser destroys every living DOM node inside that container. It parses the raw HTML string from scratch. Then, it creates brand-new DOM elements. Any input field inside that container immediately loses keyboard focus. Active text selections vanish. Unsubmitted user input disappears from browser memory.

> [!WILD]
> **Why does innerHTML destroy user cursor focus?**
>
> When you assign a new string to `element.innerHTML`, the browser engine throws away all existing C++ DOM nodes inside that container and creates new ones from scratch. Even if the new HTML contains the exact same `<input>` element with the exact same characters, the browser treats it as a brand-new element with a new identity in memory. The active keyboard cursor belongs to the destroyed node, so focus vanishes instantly. React solves this by diffing lightweight descriptors in memory, surgically patching changed text nodes without destroying living element identity.

### What is Declarative UI and the Component Model?

Imperative programming is like giving turn-by-turn driving directions: turn left at the corner, drive three hundred meters, shift into second gear, and stop. If one street sign changes or a detour appears, the entire sequence crashes. Declarative programming is like entering an address into a navigation system: you specify the destination, and the navigation engine calculates the optimal route to get you there. In user interface development, declarative UI means you describe what the interface should look like for a given state, and the UI library handles the physical browser steps to reach that visual result.

React formalizes this declarative model as a predictable mathematical formula: the user interface is a pure projection of application data, expressed as `UI = f(data)`. You do not write commands instructing the computer how to traverse DOM trees or when to mutate text nodes. Instead, you write component functions that receive reader data as input and return descriptors of the desired interface as output. When the input data changes, React evaluates the function again and updates the screen to match the new output.

In React, the fundamental unit of code organization is the **component**. A component is a standard JavaScript function whose name starts with an uppercase letter and returns a tree of UI descriptors written in JSX. Components allow developers to encapsulate structure, presentation, and logic into isolated, reusable building blocks. Complex applications like The National Times are constructed by nesting small, focused child components inside parent layout containers.

To update the browser without destroying user focus or resetting active state, React maintains a lightweight representation of the interface in JavaScript memory called the **UI descriptor tree** (traditionally referred to as the **virtual DOM**). When component data updates, React evaluates the component in memory, constructs a new tree of plain JavaScript objects, and compares it to the previous tree through a process called **reconciliation**. React identifies the exact text nodes or attributes that changed and applies surgical mutations to the living browser DOM, leaving all unchanged nodes and input focus untouched.

### Principles of React: Declarative Synchronization

When preparing for senior engineering interviews, candidates must explain why React chose the declarative component architecture over imperative DOM scripting. To master this paradigm, we formalize the five governing principles of declarative synchronization:

> [!PRINCIPLE]
> **Principle 1: Build Components as Functions That Turn Data into Markup (UI = f(data))**
> React builds user interfaces using **component functions** that turn data directly into markup: UI = f(data). When data changes, React runs the function again with new values, so you never have to search the page with `document.getElementById` or update nodes by hand.
> 
> >> component function : a function that receives data inputs and returns markup descriptors
> >> null selector crash : a crash that happens when code cannot find a renamed element on the page
> 
> *It is best practice to do this:*
> `function Header({ user }) {`
> `  return (`
> `    <h1>Welcome, ~{user.name}~</h1> // Reads user data from argument`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function updateHeader(user) {`
> `  const el =`
> `    document.querySelector(~'#name'~); // Searches page by string ID`
> `  el.textContent = ~user.name~; // Fails when element is renamed`
> `}`

In plain JavaScript, writing `document.getElementById('name').textContent = user.name` feels direct because you are commanding the browser to find an element and change its text. But look at what happens the moment your application grows. Your script couples directly to string ID selectors scattered across external HTML templates. If a designer changes `<h1 id="name">` to `<h1 id="user-name">`, `document.getElementById('name')` returns `null`. Your update script immediately throws `TypeError: Cannot set properties of null`, and execution halts.

React replaces manual DOM queries with direct function arguments. A React component is a standard JavaScript function. When you write a component, you do not search the browser document:

```jsx title="Component Source"
function Header({ user }) {
  return <h1>Welcome, ~{user.name}~</h1>; // Projects user data into markup
}
```

To see the difference in execution, consider how the browser and compiler handle this component. The JSX compiler transforms `<h1>Welcome, {user.name}</h1>` into a plain JavaScript function call:

```jsx title="Compiler Output"
_jsx("h1", {
  children: ["Welcome, ", ~user.name~] // Evaluates expression in memory
});
```

The JavaScript engine executes this function directly in memory. It accesses `user.name` from the argument object without traversing a single DOM node or querying the document tree. Once the descriptor is returned, React mounts the element and paints the resulting markup cleanly to the page:

```html title="Browser Render"
<h1>Welcome, ~Clara Foster~</h1> <!-- Displays evaluated data in browser -->
```

Because the component receives its data directly through function parameters, there are zero string selector lookups to fail, and zero ID typos that can crash your application.

> [!PRINCIPLE]
> **Principle 2: Pass Data Downward from a Single Source of Truth to Prevent State Drift**
> Data flows in only one direction in React, passing from parent components down to children through **props**. This rule is called **unidirectional data flow**. Because all related widgets receive their data from a **single source of truth**, they always update together. This prevents **state drift**, where different parts of the screen show conflicting information for the same user.
> 
> >> unidirectional data flow : passing data strictly downward from parent to child components via props
> >> state drift : a defect where two UI elements display contradictory data for the same entity
> 
> *It is best practice to do this:*
> `function Header({ user }) {`
> `  return (`
> `    <header>`
> `      <Greeting name=~{user.name}~ /> // Passes data to greeting`
> `      <Badge name=~{user.name}~ /> // Passes same value to badge`
> `    </header>`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function syncUser(user) {`
> `  setNav(~user.name~); // Updates first widget alone`
> `  setBadge(~user.name~); // Second update risks drift`
> `}`

On a publication website like The National Times, Clara Foster's name appears in multiple places on the screen: the top greeting bar (`Welcome, Clara Foster`) and the subscriber tier badge (`PRO: Clara Foster`).

In plain JavaScript, keeping these two widgets synchronized requires writing two separate update routines:

```js title="Independent Imperative Queries"
function updateGreeting(name) {
  const el = document.getElementById(~'nav'~); // Queries greeting independently
  if (el) el.textContent = name;
}
function updateBadge(name) {
  const el = document.getElementById(~'badge'~); // Fails if selector changes
  if (el) el.textContent = name;
}
```

What happens when Clara updates her account name from "Clara F." to "Clara Foster"? If `updateGreeting` succeeds, but `updateBadge` fails because of a network glitch or a renamed class selector, the screen splits:

```html title="Desynchronized Browser Render"
<header>
  <span>Welcome, ~Clara Foster~</span> <!-- Updated to new name -->
  <span class="badge">PRO: ~Clara F.~</span> <!-- Stale name causes drift -->
</header>
```

The user sees two contradictory identities on the exact same page. This is **state drift**, and it destroys user trust.

In React, synchronizing related elements is not an operational chore left to manual scripts. The parent component `SiteHeader` holds the authoritative user record in JavaScript memory and passes `user.name` down to both child components:

```jsx title="Single Parent Component"
function SiteHeader({ user }) {
  return (
    <header>
      <Greeting name=~{user.name}~ /> // Receives reader identity from parent
      <Badge name=~{user.name}~ /> // Guaranteed identical value in memory
    </header>
  );
}
```

When `user.name` changes, React evaluates `SiteHeader`. In a single atomic render pass, both `<Greeting />` and `<Badge />` receive the exact same string from the same variable in memory. They can never drift out of sync, because they derive from a single source of truth.

> [!PRINCIPLE]
> **Principle 3: Write Declarative UI Descriptions Instead of Scripting Imperative DOM Transitions**
> In React, you use **declarative UI** to describe what the screen should look like for every state. You never write **imperative DOM scripts** that add or remove CSS classes step by step (`classList.add`, `classList.remove`). If a script fails halfway through those steps, the element gets stuck in a broken intermediate state. React prevents this by swapping to the complete target design in one clean step.
> 
> >> declarative UI : describing what the screen should look like instead of scripting each DOM change
> >> intermediate state : a broken half-way condition where old and new styles collide during transitions
> 
> *It is best practice to do this:*
> `function Status({ isPro }) {`
> `  const cls = ~isPro~ ? 'pro' : 'std'; // Resolves class in JSX`
> `  return (`
> `    <span className={cls}>`
> `      Status`
> `    </span>`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function setStatus(isPro) {`
> `  const el = get('status');`
> `  if (isPro) el.classList.add(~'pro'~); // Mutates class imperatively`
> `  else el.classList.remove(~'pro'~); // Fails if step is aborted`
> `}`

In vanilla JavaScript, updating an element's visual appearance feels like choreographing a sequence of falling dominoes. When a subscriber toggles between standard and pro tiers, an imperative script must manually execute every step:

```js title="Choreographed DOM Steps"
function setStatus(isPro) {
  const el = document.getElementById('status-badge');
  el.classList.remove(~'standard'~); // Removes prior state class
  el.classList.add('pro');
  el.textContent = ~'PRO MEMBER'~; // Manually updates visible label
}
```

Look at what happens if an unhandled runtime error or network race condition interrupts execution between Step 1 and Step 2. The old class was removed, but the new class was never added, and the text label was never updated! The badge is now trapped in an unstyled, broken intermediate state.

In React, you never script transition steps from state A to state B. Instead, you declare the complete target visual output for each condition:

```jsx title="Component Source"
function StatusBadge({ isPro }) {
  const cls = ~isPro~ ? 'badge-pro' : 'badge-std'; // Resolves class in memory
  return (
    <span className={cls}>
      {isPro ? ~'PRO MEMBER'~ : 'FREE READER'} // Declares complete target label
    </span>
  );
}
```

React compares the existing browser DOM against your newly returned descriptor. In a single atomic reconciliation pass, React swaps the CSS classes and text content simultaneously. The element can never become trapped in a half-updated limbo.

> [!PRINCIPLE]
> **Principle 4: Store Data in JavaScript Variables, Not in HTML Attributes**
> Keep your data in JavaScript variables, numbers, and objects, not in HTML elements. React uses the DOM only to display results, so your code never reads HTML attributes like `data-tier` to figure out what is happening in your app.
> 
> >> write-only DOM : using the browser page only to display results, never to store app data
> >> DOM state coupling : an anti-pattern where code reads HTML attributes to make decisions
> 
> *It is best practice to do this:*
> `const ~user~ = { // Authoritative state in memory`
> `  name: 'Clara',`
> `  tier: 'PRO',`
> `};`
> `return <Badge tier=~{user.tier}~ />; // Passes data directly to prop`
> 
> *Instead of doing this:*
> `const el = get('badge');`
> `const tier =`
> `  el.getAttribute(~'data-tier'~); // Reads state out of HTML markup`

In legacy web development, developers frequently used HTML elements as an in-browser database:

```js title="Reading State from the DOM"
const badge = document.getElementById('badge');
const tier = badge.getAttribute(~'data-tier'~); // Inspects markup for state
if (tier === 'PRO') {
  ~unlockSubscriberFeature~(); // Executes logic from DOM attribute
}
```

Why is treating the DOM as your database an architectural disaster? The browser DOM is an expensive C++ layout tree designed specifically for painting pixels onto a screen, not for querying application data. Reading from HTML attributes requires the browser to parse strings from living C++ nodes. Even worse, it binds your application's security and app logic to the presentation layer. If a designer changes `data-tier="PRO"` to `class="badge-pro"`, or if an HTML sanitizer strips custom attributes, your code silently breaks.

In React, the dependency is completely inverted:

```jsx title="State in JavaScript Memory"
const user = {
  name: 'Clara Foster',
  ~tier: 'PRO'~ // Holds authoritative state in memory
};
const hasAccess = ~user.tier === 'PRO'~; // Evaluates pure JavaScript variable
return <ArticleContent access={hasAccess} />;
```

React uses the browser DOM only to display results. Components read values from JavaScript variables and render them to the screen, but they never query the DOM to find out what is happening in your application.

> [!PRINCIPLE]
> **Principle 5: Use Virtual DOM Reconciliation to Surgically Patch the DOM Without Destroying Focus**
> When data changes, React updates only the specific text or element that changed instead of wiping the whole container with `innerHTML`. It achieves this precision through **virtual DOM reconciliation**. Before touching the real browser, React builds a fresh tree of objects in memory and checks it against the previous tree. It finds the exact difference and updates only that single node in the browser, keeping living elements and the active text cursor alive.
> 
> >> virtual DOM reconciliation : comparing two lightweight object trees in memory to find differences before touching the page
> >> focus preservation : keeping the active text cursor alive inside an input field during UI updates
> 
> *It is best practice to do this:*
> `function Header({ readerName }) {`
> `  return (`
> `    <span>Welcome, ~{readerName}~</span> // Patches text surgically`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function updateHeader(readerName) {`
> `  header.~innerHTML~ = // Destroys nodes and focus`
> `    '<span>' + readerName + '</span>';`
> `}`

When developers want to update content in vanilla JavaScript without writing dozens of tedious `createElement` statements, they frequently reach for `innerHTML`:

```js title="Destructive DOM Wiping"
headerContainer.~innerHTML~ = // Destroys living DOM nodes and cursor focus
  '<span>' + readerName + '</span>';
```

Writing `innerHTML` feels quick and convenient, but look at what physically happens inside the browser's C++ rendering engine. The browser destroys every single living DOM element inside `headerContainer`. It discards their pointers, deletes their event listeners, and reconstructs brand-new C++ DOM nodes from the raw string.

What happens if `headerContainer` contains a search `<input>` where the reader is currently typing their query? The active keyboard cursor belongs to the destroyed C++ element. The moment `innerHTML` executes, the input is annihilated and rebuilt. The user's active keyboard cursor vanishes instantly! Any partially typed characters disappear, and keyboard navigation breaks.

How does React solve this? React never wipes the living container. When `readerName` changes from `"Clara F."` to `"Clara Foster"`, React creates two lightweight JavaScript objects in memory:

```js title="In-Memory Descriptors"
const prev = {
  type: 'span',
  props: ~{ children: 'Clara F.' }~ // Previous tree in memory
};
const next = {
  type: 'span',
  props: ~{ children: 'Clara Foster' }~ // Next tree compared during diffing
};
```

React compares the two trees in memory (**reconciliation**). It verifies that the `<span>` element itself, its layout geometry, and its sibling `<input>` are identical. It issues a single surgical browser command targeting only the text node:

```js title="Surgical Browser Mutation"
textNode.~data~ = 'Welcome, Clara Foster'; // Surgically patches text node
```

Because the living C++ elements are never destroyed, the `<input>` node keeps its identity, active keyboard focus stays alive, and the user continues typing without interruption.

| | **VANILLA IMPERATIVE DOM**<br>(manual scripting) | **REACT DECLARATIVE MODEL**<br>(in-memory synchronization) | **SENIOR INTERVIEW TAKEAWAY**<br>(architectural reality) |
| :--- | :--- | :--- | :--- |
| **Data Synchronization** | Manual `getElementById` queries executed per event | Automatic tree derivation: `UI = f(data)` | Eliminates state drift by establishing a single source of truth |
| **Multi-Widget Cohesion** | Independent query scripts updating DOM nodes separately | Centralized parent data passed downward through props | Guarantees all related elements reflect identical identity state |
| **State Transitions** | Imperative `classList.add` and `style.display` choreography | Target end-states declared via conditional expressions | Prevents corrupt intermediate UI states during aborted transitions |
| **State Storage** | Reading DOM attributes like `dataset.tier` as a database | Authoritative data kept in pure JavaScript variables | Decouples business logic from ephemeral browser markup strings |
| **DOM Mutation Strategy** | Destructive `innerHTML` or manual node mutation | Surgical text node patching via in-memory diffing | Preserves active element cursor focus and avoids layout thrashing |

> [!TIP]
> **To impress the interviewer:** When interviewers ask why React uses a Virtual DOM, junior candidates often answer "because the Virtual DOM is faster than the real DOM." This answer is technically incorrect. Direct, highly optimized manual DOM operations can execute faster than React's diffing pass. The true architectural benefit of the Virtual DOM is **declarative predictability**: it allows developers to write code as if the entire page is re-rendered on every state change, while React ensures the physical updates remain surgical and efficient. It eliminates human synchronization bugs and state drift across complex interfaces.

### Step 1: First, we construct the parent container <SiteHeader.jsx>

We construct the parent container `SiteHeader.jsx` to establish the single source of truth for reader data. In legacy JavaScript, user identity was queried independently by different scripts scattered across the document. In React, the parent container holds the authoritative reader state in JavaScript memory and passes it directly to child components as props. Notice how `SiteHeader` imports both child widgets and establishes their shared contract before either child file is finalized on disk.

```jsx title="SiteHeader.jsx"
export default function SiteHeader() {
  const ~readerName~ = 'Clara Foster'; // Authoritative state in memory
  return (
    <header className="site-header">
      <ReaderGreeting readerName=~{readerName}~ /> // Passes name to greeting
      <SubscriberBadge readerName=~{readerName}~ /> // Passes name to badge
    </header>
  );
}
```

Notice how lean the parent component remains. It does not search the document for HTML IDs, attach event listeners, or manipulate styles imperatively. It declares the composition of the site header and passes data downward to each child widget. Because `SiteHeader` acts as the single source of truth, both widgets receive the identical `readerName` value without independent network queries or manual synchronization routines.

### Step 2: Next, we build the child greeting component <ReaderGreeting.jsx>

We construct the child component `ReaderGreeting.jsx` to display the personalized welcome text. The component owns zero independent user data: it relies completely on the `readerName` passed downward from `SiteHeader`. When declaring child components that accept data, developers encounter a classic pedagogical crossroad: whether to receive the raw `props` argument as a single object or unpack properties directly using JavaScript parameter destructuring.

When declaring component functions that receive input data, you face an architectural crossroad:
- **Option 1 (The Explicit Object Way)**: Accept the complete `props` parameter and access values via dot notation `props.readerName`.
- **Option 2 (The Modern Idiomatic Way)**: Unpack properties directly in the function parameter list using JavaScript destructuring `{ readerName }`.

```jsx title="Option 1: The Explicit Object Way (props.readerName)"
export default function ReaderGreeting(~props~) { // Receives raw props object
  return (
    <div className="nav-greeting">
      <span>
        Welcome back, ~{props.readerName}~ // Reads prop via dot notation
      </span>
    </div>
  );
}
```

In Option 1, the function receives a single JavaScript object named `props`. To display reader data, the code writes `props.readerName`. While this makes the object origin explicit, repeating `props.` across larger components introduces visual clutter and obscures the required input interface.

```jsx title="ReaderGreeting.jsx"
export default function ReaderGreeting({ readerName }) {
  return (
    <div className="nav-greeting">
      <span className="greeting-label">Welcome,</span>
      <strong className="reader-name">
        ~{readerName}~ // Injects unpacked reader name
      </strong>
    </div>
  );
}
```

In Option 2, curly braces in the parameter list unpack `readerName` directly at the function boundary. The component body accesses the variable without ceremony. This pattern is the modern industry standard across professional React development because it makes the required component contract immediately visible in the function signature. Notice how `ReaderGreeting.jsx` functions as an authentic presentation component: it contains no hardcoded reader names, queries no external DOM nodes, and projects pure markup from its inputs.

### Step 3: Then, we declare the subscriber badge component <SubscriberBadge.jsx>

We construct the second consumer of our shared data: `SubscriberBadge.jsx`. This component lives as a sibling to `ReaderGreeting` inside the site header. In plain JavaScript, keeping two separate widgets in sync required updating both DOM elements manually whenever user identity changed. If a script updated the greeting but forgot the badge, the interface suffered from state drift. In React, `SubscriberBadge` receives the exact same `readerName` prop from `SiteHeader`. Sibling components never speak to each other directly; they stay synchronized because both derive from the single truth managed by their common ancestor.

```jsx title="SubscriberBadge.jsx"
export default function SubscriberBadge({ readerName }) {
  return (
    <div className="subscriber-badge">
      <span className="badge-tier">~PRO~</span> // Displays static tier badge
      <span className="badge-user">
        ~{readerName}~ // Displays synchronized reader name
      </span>
    </div>
  );
}
```

Notice the complete independence between sibling components. `SubscriberBadge` knows nothing about `ReaderGreeting`, and `ReaderGreeting` knows nothing about `SubscriberBadge`. Neither component queries the other's DOM nodes or registers custom cross-widget listeners. Both components function as pure projections of data, leaving all synchronization responsibilities to React's declarative data flow.

### Step 4: Finally, we mount the site header inside <App.jsx>

To complete our application tree, we mount `SiteHeader.jsx` inside the root container `App.jsx`. In standard web development, applications often required separate initialization scripts to locate root containers and inject fragments. In React, the entire interface organizes into a unified component hierarchy. `App.jsx` acts as the primary root container, embedding `SiteHeader` into the application layout. When React renders `App`, the mounting engine evaluates the full component tree in memory and paints the resulting DOM nodes in a single, predictable operation.

```jsx title="App.jsx"
import SiteHeader from './components/SiteHeader.jsx';

export default function App() {
  return (
    <main className="national-times-app">
      <~SiteHeader~ /> // Mounts header tree at root
    </main>
  );
}
```

The completed tree showcases the power of the React component model. From `App` down to the smallest text node in `ReaderGreeting`, every element belongs to a single declarative hierarchy. Data flows unidirectionally downward through props, eliminating global query selectors, element caching, and manual string concatenation.

In React, the entire header derives from modular, declarative components. Because `SiteHeader` holds reader identity as a single source of truth and passes it downward, both `ReaderGreeting` and `SubscriberBadge` remain permanently synchronized. Modifying the reader name in memory updates every widget across the screen simultaneously, with zero risk of state drift.

### Where you will meet this

1. **Multi-Widget Navigation Bars**: When a user logs in, their avatar, display name, notification count, and account tier must appear synchronously across the desktop header, sidebar navigation, and mobile drawer. Declarative components guarantee that every widget reflects identical user data without manual DOM hunting.
2. **E-Commerce Checkout Carts**: The number of items in a shopping bag appears in the top navigation cart pill, the checkout button badge, and the order summary sidebar. Passing cart data downward from a single source ensures that item counts match perfectly across the entire store.
3. **Editorial News Feeds**: Live breaking news banners, article card titles, and reader recommendation lists all consume articles from a shared publication feed. Encapsulating article presentation into reusable components allows engineers to update headline rendering everywhere without editing individual HTML files.

### Glossary

- **Declarative Programming**: A programming paradigm where developers describe the desired end state of the user interface rather than writing the step-by-step DOM manipulation commands required to build it.
- **State Drift**: A critical defect where two or more interface elements display contradictory or stale data because manual update routines failed to synchronize every affected DOM node.
- **Component**: A self-contained, reusable JavaScript function whose name starts with an uppercase letter and returns a tree of UI descriptors representing a slice of the interface.
- **UI Descriptor Tree**: A lightweight hierarchy of plain JavaScript objects maintained in memory (historically termed the Virtual DOM) that describes what the screen should look like.
- **Reconciliation**: The internal diffing process where React compares the newly generated UI descriptor tree with the previous tree to calculate the minimal set of surgical DOM mutations required.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Declarative Data Flow

➔ ALWAYS derive interface structure directly from data so that UI is a pure projection: `UI = f(data)`.

➔ IF reader profile details appear in multiple screen locations THEN declare the data once in a common ancestor component and pass it downward via props.

❒ Component Encapsulation

➔ ALWAYS start component function names with an uppercase letter to signal custom React components to the JSX compiler.

➔ IF multiple child components require the same user state THEN keep child components stateless and distribute data from their parent container.

❒ DOM Node Identity and Focus

➔ ALWAYS delegate DOM updates to React's reconciliation engine to preserve browser input focus and avoid layout thrashing.

➔ NEVER use `innerHTML` to update dynamic user interfaces because tearing down living DOM nodes destroys keyboard focus and wipes unsubmitted input buffers.

**DO THIS:** derive all interface representations directly from a single data source

```jsx right
function SiteHeader() {
  const readerName = 'Clara Foster';
  return (
    <header className="site-header">
      <ReaderGreeting readerName={readerName} />
      <SubscriberBadge readerName={readerName} />
    </header>
  );
}
```

**DO NOT DO THIS:** query the DOM manually to synchronize multiple elements

```jsx wrong
function updateHeader(readerName) {
  document.getElementById('nav-greeting').textContent = readerName;
  document.getElementById('badge-user').textContent = readerName;
}
```

| | **MANUAL DOM SCRIPTING**<br>(imperative) | **REACT ENGINE**<br>(declarative) |
| ---: | :--- | :--- |
| **Interface Construction** | Step-by-step imperative commands:<br>`document.`<br>`getElementById('id')`<br>`.textContent = name` | Declarative descriptor projection:<br>`<span>`<br>`{readerName}</span>`<br>derived from input data |
| **Multi-Widget Synchronization** | Fragile manual queries prone to state drift and missed elements | Single source of truth distributed downward via component props |
| **State Transitions** | Imperative `classList.add` and `style.display` choreography | Target end-states declared via conditional expressions |
| **State Storage** | Reading DOM attributes like `dataset.tier` as a database | Authoritative data kept in pure JavaScript variables |
| **DOM Mutation Strategy** | Destructive node replacement via `innerHTML` or manual node setters | In-memory reconciliation with surgical updates to changed text nodes |
| **Input Focus & State** | Active keyboard focus and cursor position destroyed on re-render | Living DOM node identity and active element focus preserved |
| **Prevented Bug Class** | State drift, null selector exceptions, and frozen desynchronized widgets | Uncoordinated UI updates and accidental focus loss during data refreshes |
