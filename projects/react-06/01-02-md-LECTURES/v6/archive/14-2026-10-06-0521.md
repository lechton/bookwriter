### The Friction of Ephemeral Local Variables

Every interactive web application needs to remember data that changes over time, like an upvote tally, a dark mode toggle, or the text typed into an input. In standard JavaScript functions, local variables exist only while the function executes and vanish the moment it returns. React components are functions called repeatedly whenever the interface redraws, so preserving data across renders requires an external storage mechanism that notifies the engine when values change.

To see this in action on The National Times, Clara sits at her desk to build an article reaction widget: `src/components/StoryCard.jsx`. She wants readers to click an upvote button to celebrate breaking dispatches. She begins with standard JavaScript intuition by declaring a local counter variable: `let likes = 0`. Inside the button's click handler, she writes `likes = likes + 1` and logs the result to the browser console.

It is common for an engineer to expect that incrementing `likes` will cause the button text to update on screen. But when Clara opens her browser and clicks the button, the rendered text stubbornly displays "Likes (0)". In the console, the messages "Likes: 1", "Likes: 2", and "Likes: 3" appear with every click, proving that the variable is changing in memory. Even more confusingly, when an unrelated search query or parent filter re-renders the page, the next click logs "Likes: 1" all over again.

```jsx title="Naive Local Variable Attempt"
export default function StoryCard() {
  let likes = 0; // Local variable allocated on each call
  function handleLike() {
    likes = likes + 1; // Modifies local variable in memory
    console.log('Likes:', likes); // Prints incremented number
  }
  return (
    <button type="button" onClick={handleLike}>Likes ({likes})</button>
  );
}
```

Why did the button text refuse to change? In JavaScript, functions create a new stack frame whenever they run. Local variables declared with `let` or `const` exist only during that single invocation. When `StoryCard` finishes rendering, its execution frame disappears. When the user clicks the button, `handleLike` increments the variable in its closure, but React is never notified that anything changed. React does not inspect local variables, so it schedules no re-render. When another component triggers a re-render later, React calls `StoryCard` from the top, allocating a fresh `likes` variable initialized to `0`.

In legacy browser scripting, developers worked around this limitation by mutating DOM nodes directly with `document.getElementById('likes').textContent = likes` or storing counts on global objects like `window.likes`. In React, directly touching the DOM bypasses virtual DOM reconciliation (see Lecture 1), and mutating external variables violates component purity (see Lecture 12). React requires a declarative mechanism that preserves values across calls and notifies the engine to redraw the screen.

> [!WILD]

Using `const [count, setCount] = useState(0)` stores the value in React's external memory cell and provides a setter that schedules a fresh render pass with the updated value.

### Component Execution and the Need for Persistent Memory

To understand why React needs `useState`, we must examine what happens when a function component renders. In standard JavaScript, calling a function creates a fresh execution context: local variables are allocated, code runs line by line, the return value is handed to the caller, and the stack frame is cleaned up. A React component is invoked not once, but repeatedly throughout the lifecycle of an application. Every time data changes or a parent updates, React calls the component function again to compute a fresh tree of UI descriptors. Because every render is a brand-new function call, any variable declared with `let` or `const` inside the component body is re-created from scratch.

If local variables are discarded on every render, where does state actually live? React stores component state outside the component function, in an internal memory cell associated with that component's position in the UI tree. You can picture this as a shelf of memory slots maintained by React in the background. When your component function runs, calling `useState` reaches out to React's internal shelf and asks for the current value assigned to this specific slot. On the very first render (the initial mount), React initializes the slot with the argument you passed (`0`). On all subsequent renders, React ignores that initial argument and hands back whatever value is currently stored in the slot.

The `useState` hook returns a JavaScript array containing exactly two items, which developers unpack using **array destructuring**: `const [likes, setLikes] = useState(0)`. The first element (`likes`) is the current state value for this render pass; it is treated as a read-only constant during the execution of the component. The second element (`setLikes`) is a setter function that allows you to change the state. When you invoke `setLikes(nextValue)`, React updates the value stored on its internal shelf and queues a re-render for this component instance.

It is critical to distinguish between re-renders and page reloads. A re-render occurs within the living JavaScript application: React re-executes the component function in memory, preserves internal state cells, and updates only the changed DOM nodes. In contrast, a full browser page reload (or navigation) destroys the entire JavaScript runtime environment, clearing all memory cells and resetting all components back to their initial state. `useState` provides persistent memory across renders within a living session, not persistent storage across browser restarts.

### Principles of React: Component Memory and State

When preparing for senior technical interviews, candidates must articulate why local variables fail to persist across renders, how React manages state outside the component function scope, why setters are mandatory for updates, and how multiple instances maintain isolated memory. To master these core concepts, we formalize the six governing principles of component memory and state:

> [!PRINCIPLE]
> **Principle 1: Expect a Local Variable to Forget and to Change Nothing on Screen**
> An ordinary local variable belongs exclusively to a single function execution. When we modify a local variable inside an event handler, React receives zero notification that data changed and schedules no update, leaving the screen unchanged. Whenever the component renders again, the function executes from the top and resets the local variable to its initial starting value.
> 
> >> ephemeral variable : a local variable created inside a function that disappears when execution finishes
> >> render pass : a single complete call of a component function to calculate its return markup

When a component renders, JavaScript executes the function body from the top down. Declaring `let likes = 0` allocates a slot on the call stack for that invocation only. If an event handler reassigns `likes = likes + 1`, the change takes place purely within that closure's local scope. React has no knowledge that a JavaScript variable was modified because variables do not dispatch notifications. Furthermore, when an unrelated event (such as a parent re-render or timer) prompts React to redraw the component, React invokes the function again. That new call allocates a brand-new `likes` variable initialized to `0`. A local variable is completely ephemeral: it cannot persist data between calls, and modifying it cannot update the browser screen.

```jsx title="Ephemeral Variable Execution"
export default function LocalCounter() {
  let count = 0; // Re-created on every render
  function handleClick() {
    count = count + 1; // Updates local copy only
    console.log('Count:', count); // Logs incremented number
  }
  return (
    <button type="button" onClick={handleClick}>Clicked ({count})</button>
  );
}
```

Notice that clicking the button runs `handleClick` and increments `count` in local memory, but React never schedules a re-render. The button text remains permanently fixed at its initial rendered string.

> [!PRINCIPLE]
> **Principle 2: Store in State Exactly What Must Survive a Re-Render**
> We store in state only data that must survive between renders and directly affects what the component displays on screen. Values calculated and consumed entirely inside a single event handler, such as a formatted sharing link or temporary math result, belong in ordinary local variables because every state setter call requests a full re-render.
> 
> >> state variable : a persistent value preserved by React across component function executions
> >> transient calculation : an intermediate value computed and discarded within a single handler run
> 
> *It is best practice to do this:*
> `const [likes, setLikes] = useState(0); // State preserves counter`
> `const shareUrl = `/stories/${id}`; // Local transient calculation`
> 
> *Instead of doing this:*
> `const [shareUrl, setShareUrl] = useState(''); // Redundant state`

Novice engineers often swing between two extremes: using zero state (leaving the UI unresponsive) or placing every variable into `useState`. Every call to a state setter instructs React to schedule a re-render of the component and its children. If an event handler formats a string to send to an analytics server or calculates a temporary URL for clipboard copying, that value does not need to survive beyond the handler's execution, nor does it alter the JSX structure. Storing transient calculations in state forces React to re-render the component tree unnecessarily, wasting CPU cycles and introducing subtle race conditions. We reserve state strictly for values that the component must remember across renders to decide what to paint on screen.

```jsx title="State vs Local Variable"
import { useState } from 'react';
export default function ArticleCard({ id }) {
  const [likes, setLikes] = useState(0); // State preserves counter
  function handleShare() {
    const shareUrl = `/stories/${id}`; // Transient calculation
    navigator.clipboard.writeText(shareUrl); // Copies url to clipboard
  }
  return <button onClick={() => setLikes(likes + 1)}>Likes ({likes})</button>;
}
```

Notice the division of responsibilities: `likes` is stored in state because it controls the button label across renders, while `shareUrl` is a local variable because it is used only while `handleShare` executes.

> [!PRINCIPLE]
> **Principle 3: Expect React to Hand Back the Stored Value on Every Render**
> React stores component state outside our function in an internal memory cell tied to the component's position in the UI tree. On the initial render, `useState(initialValue)` registers the initial value in that cell and returns it. On every subsequent render, React ignores the initial argument and returns the latest value from its internal cell.
> 
> >> initial render : the first time React calls a component function to create and insert its DOM nodes
> >> internal state cell : an isolated memory record kept by React outside the component function

When beginners look at `const [likes, setLikes] = useState(0)`, they frequently wonder: "If the component executes again, why doesn't `useState(0)` reset `likes` to `0` every single time?" The answer lies in how React tracks hook execution. State does not reside within the function scope; it resides on an internal Fiber record that React preserves between calls. When React renders a component for the first time, it creates an internal state cell and initializes it with the argument `0`. On all subsequent renders, React recognizes that a state cell already exists for this hook call. It ignores the argument `0` entirely and retrieves the latest value stored in that cell. The initial argument acts strictly as a one-time seed value during initial mounting.

```jsx title="State Memory Retrieval"
import { useState } from 'react';
export default function StoryMetrics() {
  const [likes, setLikes] = useState(0); // Ignores 0 on re-renders
  console.log('Current likes value:', likes); // Prints stored value
  return (
    <button type="button" onClick={() => setLikes(likes + 1)}>
      Like ({likes})
    </button>
  );
}
```

When this component mounts, `likes` evaluates to `0`. After clicking the button, React invokes `StoryMetrics` a second time: `useState(0)` runs, but React hands back `1` from its internal state cell.

> [!PRINCIPLE]
> **Principle 4: Change State Only by Calling Its Setter**
> The state variable returned by `useState` is a read-only snapshot for the current render. We never assign a new value directly to the state variable. Calling the setter function (`setLikes`) is the only way to update React's internal state cell and schedule a fresh render to redraw the screen.
> 
> >> state setter : the update function returned by useState that requests a new render with a new value
> >> direct mutation : attempting to reassign or modify a state variable in place without using its setter
> 
> *We should do this:*
> `setLikes(likes + 1); // Updates React memory and schedules re-render`
> 
> *We should not do this:*
> `likes = likes + 1; // Throws TypeError on const or fails to update UI`

In React, state variables are meant to be treated as immutable snapshots of data for the current execution frame. When you destructure `const [likes, setLikes] = useState(0)`, declaring `likes` as a `const` enforces this contract at the JavaScript language level: writing `likes = likes + 1` immediately crashes with `TypeError: Assignment to constant variable`. Even if you deliberately declared it with `let [likes, setLikes]`, assigning to `likes` changes only a local identifier in that single closure. React is not a proxy engine; it does not intercept assignments to local variables. The setter function (`setLikes`) is the sole communication mechanism provided by React to record a new state value and place this component into the re-render queue.

```jsx title="State Setter Updates"
import { useState } from 'react';
export default function ReactionCounter() {
  const [likes, setLikes] = useState(0); // Destructures value and setter
  function handleLike() {
    setLikes(likes + 1); // Communicates update to React
  }
  return (
    <button type="button" onClick={handleLike}>Like ({likes})</button>
  );
}
```

Notice that `handleLike` does not modify `likes` directly. It passes `likes + 1` into `setLikes`, instructing React to store the next number and schedule a render pass.

> [!PRINCIPLE]
> **Principle 5: Expect Each Rendered Instance to Keep Its Own State**
> State belongs to a specific rendered instance of a component on screen, not to the component function or its source file. If we render `<StoryCard />` three times, React creates three separate state cells in memory. Clicking a button inside the first card updates only that card's count, leaving the other two instances completely unaffected.
> 
> >> component instance : a distinct mounted occurrence of a component placed in the UI tree
> >> isolated state : private memory allocated to one component instance that siblings cannot see

In object-oriented programming, a class definition is separate from its instantiated objects; similarly, in React, a component definition is separate from its mounted component instances. If you define a `StoryCard` component that holds `const [likes, setLikes] = useState(0)` and render `<StoryCard />` twice inside `App.jsx`, React tracks each card by its unique location in the UI tree. It creates two completely independent state cells in memory. Clicking "Like" on the first card invokes the first card's setter, incrementing its internal cell to `1` and scheduling a re-render strictly for that first card. The second card remains at `0`, and its function does not even run. Furthermore, state is completely private: `App` cannot read or modify the `likes` state of either child card. If two sibling cards ever need to share a synchronized count, that state must be lifted into their common parent (a pattern explored in Lecture 23).

```jsx title="Independent Component Instances"
import StoryCard from './StoryCard.jsx';

export default function StoryFeed() {
  return (
    <main className="story-feed">
      <StoryCard title="Transit Accord" /> // Maintains its own state slot
      <StoryCard title="Clean Energy" /> // Maintains separate state slot
    </main>
  );
}
```

Each rendered `<StoryCard />` instance maintains its own isolated state slot. Upvoting the "Transit Accord" card updates its counter without triggering an update in the "Clean Energy" card.

> [!PRINCIPLE]
> **Principle 6: Call Setters from Handlers, Never Unconditionally During Render**
> A state setter requests a new render, so we must invoke setters exclusively inside event handlers when a user interacts with the page. Calling a setter directly in the component body or invoking it inside JSX curly braces runs the setter during render, causing React to abort with a fatal "Too many re-renders" infinite loop error.
> 
> >> infinite render loop : a crash where setting state during render immediately triggers another render
> 
> *We should do this:*
> `<button onClick={() => setLikes(likes + 1)}> // Defers setter to click`
> `  Like`
> `</button>`
> 
> *We should not do this:*
> `<button onClick={setLikes(likes + 1)}> // Invokes setter during render`
> `  Like`
> `</button>`

In Lecture 13, you learned that expressions inside JSX curly braces evaluate immediately during the render pass. If you write `onClick={setLikes(likes + 1)}`, JavaScript calls `setLikes` right away while constructing the element tree. Calling a setter instructs React to schedule a new render. React attempts to render the component again, but during that second render, JavaScript encounters `onClick={setLikes(likes + 1)}` again, calling the setter once more. This creates an unconstrained recursive loop: render calls setter, setter calls render. To prevent the browser tab from freezing completely, React halts execution and throws an unrecoverable runtime crash: `Error: Too many re-renders. React limits the number of renders to prevent an infinite loop.` To prevent this failure, always wrap parameterized setter calls in an arrow function (`onClick={() => setLikes(likes + 1)}`), ensuring the setter executes strictly when the user physically clicks.

```jsx title="Deferred Setter Execution"
import { useState } from 'react';

export default function UpvoteButton() {
  const [count, setCount] = useState(0); // State preserved across renders
  return (
    <button type="button" onClick={() => setCount(count + 1)}>
      Applaud ({count})
    </button>
  );
}
```

By wrapping `setCount` inside an arrow function, the setter remains uncalled during render, executing only when the reader triggers a browser click event.

### Step 3: Finally, we build the stateful reaction control <src/components/ReactionButton.jsx>

In `src/components/ReactionButton.jsx`, we build the terminal reaction button. The component declares a numeric state variable initialized to zero: `const [upvotes, setUpvotes] = useState(0)`. Inside `handleUpvote`, we call `setUpvotes(upvotes + 1)`. When the user clicks the button, React records the new upvote count in its internal memory cell and schedules a re-render for this specific `ReactionButton` instance. Because we use a semantic `<button type="button">`, the control supports full keyboard accessibility with Enter and Space keys (see Lecture 13). Notice that because each `StoryCard` mounted its own `<ReactionButton />`, each button maintains its own independent upvote tally. Upvoting the first story increments its count to 1 without triggering a render in the second story card.

```jsx title="ReactionButton.jsx"
import { useState } from 'react';
export default function ReactionButton() {
  const [upvotes, setUpvotes] = useState(0); // Isolated state counter
  function handleUpvote() {
    setUpvotes(upvotes + 1); // Updates internal cell and schedules render
  }
  return (
    <button type="button" onClick={handleUpvote}>Upvotes: {upvotes}</button>
  );
}
```

Notice how clean the control is: it owns its upvote count completely, uses `useState` to persist the number across renders, and communicates updates strictly through `setUpvotes`.

2. **Accordion Panels, Drawers, and Disclosure Widgets**: Collapsible FAQ items, navigation menus, and sliding drawers track their open or closed visibility state using boolean flags (`isOpen`, `setIsOpen`).

### Glossary

- **Component State** ◼ Persistent memory maintained by React across render passes that stores data affecting what appears on the screen.
- **State Setter Function** ◼ The updater function returned by `useState` that updates React's internal state record and schedules a component re-render.
- **Render Pass** ◼ A single complete execution of a component function by React to calculate its tree of UI descriptors.
- **Internal State Cell** ◼ An isolated data structure maintained by React outside the component function, mapped to the component's position in the UI tree.
- **Infinite Render Loop** ◼ A runtime crash caused by invoking a state setter unconditionally during the render pass, repeatedly triggering new renders without stopping.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Ephemeral Variables vs Persistent State

➔ ALWAYS use `useState` for data that must survive between renders and directly affects the user interface.

➔ NEVER rely on local variables (`let count = 0`) to track data across user interactions.

**DO THIS:** Store interactive data in React state

```jsx right
function LikeButton() {
  const [likes, setLikes] = useState(0);
  return <button onClick={() => setLikes(likes + 1)}>Likes: {likes}</button>;
}
```

**DO NOT DO THIS:** Increment local variables inside click handlers

```jsx wrong
function LikeButton() {
  let likes = 0;
  return <button onClick={() => { likes = likes + 1; }}>Likes: {likes}</button>;
}
```

❒ State Modification and Setters

➔ ALWAYS call the state setter function (`setCount`) to update state and schedule a re-render.

➔ NEVER mutate a state variable directly (`count = count + 1`).

**DO THIS:** Pass the next value to the setter function

```jsx right
function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>Next</button>;
}
```

**DO NOT DO THIS:** Directly reassign the state variable

```jsx wrong
function Counter() {
  let [count, setCount] = useState(0);
  return <button onClick={() => { count = count + 1; }}>Next</button>;
}
```

❒ Execution Timing and Infinite Loops

➔ ALWAYS invoke state setters inside event handlers or delayed callback wrappers.

➔ NEVER invoke a state setter directly during the render pass or in naked JSX braces.

**DO THIS:** Wrap parameterized setter calls in an arrow function

```jsx right
function UpvoteAction({ onUpvote }) {
  return <button onClick={() => onUpvote(1)}>Upvote</button>;
}
```

**DO NOT DO THIS:** Call the setter immediately in JSX curly braces

```jsx wrong
function UpvoteAction({ onUpvote }) {
  return <button onClick={onUpvote(1)}>Upvote</button>;
}
```

| | **EPHEMERAL LOCAL VARIABLE**<br>(Naive Function Scope) | **REACT USESTATE MEMORY**<br>(Persistent State Engine) |
| ---: | :--- | :--- |
| **Storage Location** | Allocated on temporary JavaScript call stack frame | Maintained externally in React internal Fiber state cells |
| **Render Persistence** | Discarded on return; reset to initial value on each call | Preserved across render passes for the lifetime of component |
| **Re-render Trigger** | None: React is unaware that local variables changed | Setter call queues a re-render and updates browser DOM |
| **Update Mechanism** | Direct assignment (`count = count + 1`) | Invoking setter function (`setCount(count + 1)`) |
| **Instance Isolation** | Scoped to individual function call execution | Private to specific component instance in UI tree |
| **Initial Value Role** | Evaluated on every call, repeatedly resetting value | Used once on initial mount; ignored on later renders |
