# Lecture 1: What is React and the Declarative Model
> INTERVIEW QUESTION | ❱ CORE | What is React, and how does its declarative, component-based model differ from plain JavaScript DOM scripting?

1. Clara logs into The National Times website to read the morning investigative edition.
2. The newsroom header displays her name in multiple places across the top navigation bar.
3. Your plain JavaScript script runs a function to update the user name across the screen.
4. Why does the greeting say Clara while the subscriber badge still displays Guest?
5. Readers see conflicting user information, suspect account errors, and lose trust in the platform.
6. The manual script updated two DOM nodes but missed the third element entirely.
7. Today, your UI will synchronize every element automatically from a single source of truth.

### Manual DOM Hunting and State Drift

In plain browser JavaScript, you build dynamic pages by manipulating the Document Object Model. Developers commonly call this the **DOM**. The DOM is the browser's internal tree of live C++ objects representing every HTML element on screen. To change a word on the page, your script must locate the exact element first. You call browser methods like `document.getElementById` or `document.querySelector`. Once the element is found, you overwrite its properties directly in memory. You assign new text using `textContent` or replace markup using `innerHTML`.

In a growing application like The National Times, a single piece of reader data appears across multiple sections. The subscriber's name appears in the welcome banner, the profile menu, and the subscription badge. When the user logs in, your script must find and update every single copy by hand.

Look at the naive imperative update function below:

```js title="Naive DOM Update"
function updateHeaderUser(name) {
  const greeting = document.getElementById('header-greeting');
  greeting.textContent = 'Welcome, ' + name; // Updates header **GREETING**
  const profile = document.getElementById('nav-profile-name');
  profile.textContent = name;                // Updates navigation **PROFILE**
}
```

When `updateHeaderUser` runs, it updates the greeting and the profile pill. However, notice the omission: the script forgot to query `#subscriber-badge`. The greeting displays Clara, but the badge still displays Guest.

This synchronization failure is called **state drift**. State drift happens when two interface elements that should show the same data show different values. In imperative programming, you bear two burdens: deciding what changed, and finding every affected node. As your website grows to hundreds of elements, manual hunting inevitably misses nodes.

```html-figure src="figures/01-00-manual-vs-declarative.html" caption="Imperative DOM queries fail as the interface grows: missing a single query creates state drift across the header."
```

To avoid missing individual nodes, developers often attempt to replace the entire parent container at once. They wipe the whole container using `innerHTML`. While this guarantees all text gets updated, it introduces a severe hidden penalty:

```js title="Destructive Replacement"
function replaceHeader(name) {
  const root = document.getElementById('header-root');
  const markup = `<header><h1>National Times</h1><p>${name}</p></header>`;
  root.innerHTML = markup; // **WRONG:** wipes container, losing input **FOCUS**
}
```

> [!WILD]
> **Why does innerHTML destroy your active input focus?** When you assign a new string to `innerHTML`, the browser parser does not compare text. It destroys every existing DOM node inside that container and creates brand-new nodes in memory. If a reader is typing in an input when `innerHTML` runs, that `<input>` element is deleted from existence. The browser recreates a new input that looks identical, but the active cursor focus is lost. Text selection vanishes, and running CSS transitions reset to their initial frames. React avoids this by comparing changes in memory and surgically updating only the text nodes that changed.

> [!TIP]
> **To impress the interviewer:** When asked why React was created, do not merely say "it makes building websites faster." Explain that React solves the fundamental problem of **state drift** inherent in imperative programming. In vanilla JavaScript, the developer must manually keep the DOM in sync with data across dozens of queries. React replaces this manual choreography with a declarative model. The user interface becomes a pure projection of application data: `UI = f(data)`.

### Principles of React: The Core Laws of the Declarative Model

To prepare for any technical interview, we must separate theory from application and establish the five fundamental laws governing how React replaces imperative DOM mutation with a declarative, component-driven architecture. In vanilla JavaScript, the developer manually orchestrates browser DOM updates. In React, the user interface is a pure projection of application data: UI = f(data). We formalize these rules into five standalone principles.

> [!PRINCIPLE]
> **Principle 1: Declare UI as a Pure Function of Data Instead of Mutating DOM Nodes**
> You must declare what the user interface looks like for a given set of data (`UI = f(data)`), strictly avoiding manual DOM queries like `document.getElementById` or property mutations.
> 
> *We should do this:*
> `return (<h1>Welcome, {name}</h1>);`
> // Declares UI as a pure projection of data
> 
> *We should not do this:*
> `const el =`
> `  document.getElementById('title');`
> `el.textContent = name;`
> // Manual DOM mutation causes state drift

To understand the declarative model in an interview, you must decompose the governing formula `UI = f(data)` into three separate architectural tiers:

1. **The Data Input (`data`):** Immutable snapshots of application state and incoming props that represent the single source of truth at a given moment in time.
2. **The Pure Component Function (`f`):** A deterministic JavaScript function that takes data as an input and calculates the visual interface without performing outside mutations.
3. **The Virtual Descriptor (`UI`):** A lightweight tree of plain JavaScript objects returned by the component, describing what DOM nodes the browser should ultimately display.

In imperative browser programming, you write sequential commands telling the browser how to locate elements, parse strings, and mutate living C++ objects. When application state changes, you must manually trace every dependent DOM node across the entire page. In declarative React, you write pure functions that return descriptions of the desired UI for any given data. React takes on the mechanical burden of computing the differences in memory and applying minimal DOM patches automatically.

```jsx title="Principle 1: Declarative Projection vs Imperative Mutation"
// **WRONG:** Imperative DOM hunting is fragile and manual
const title = document.getElementById('news-title');
title.textContent = article.headline;

// **RIGHT:** Declarative component projects UI directly from data
export default function Headline({ article }) {
  return (<h1 className="news-title">{article.headline}</h1>);
}
```

> [!PRINCIPLE]
> **Principle 2: Maintain a Single Source of Truth to Eliminate State Drift**
> You must store shared application data in a single parent container and pass it downward, never maintaining separate copies that can fall out of sync.
> 
> *It is best practice to do this:*
> `<SiteHeader readerName={name} />`
> // Single source of truth updates all children
> 
> *Instead of doing this:*
> `updateGreeting(name);`
> `updateBadge(name);`
> // Independent queries drift when updates miss

In software architecture, **state drift** occurs whenever multiple parts of a user interface hold duplicate representations of the same underlying data:

1. **The Imperative Synchronization Trap:** In vanilla JavaScript, updating a user name requires querying the greeting banner, the navigation bar badge, and the account drawer independently. If a network event or exception interrupts the sequence, one DOM node updates while another shows stale text.
2. **Unidirectional Top-Down Flow:** React solves state drift by mandating that shared data resides in a single common ancestor. That parent distributes the value downward to all descendants via props. Because all child components derive their markup from the identical data reference in the same render pass, state drift is mathematically impossible.

```jsx title="Principle 2: Centralized Truth vs Independent Queries"
// **WRONG:** Independent queries leave sibling elements out of sync
document.getElementById('greeting').textContent = name;

// **RIGHT:** Parent container holds single truth and passes props down
function Header({ name }) {
  return (<header><Greeting name={name} /><Badge name={name} /></header>);
}
```

> [!PRINCIPLE]
> **Principle 3: Unpack Props with Parameter Destructuring to Document Inputs**
> You should unpack incoming props directly in the component parameter list (`{ readerName }`), rather than repeating the `props.` prefix throughout the function body.
> 
> *It is best practice to do this:*
> `function User({ name }) {`
> `  return (<span>{name}</span>);`
> `}`
> // Destructuring documents required inputs
> 
> *Instead of doing this:*
> `function User(props) {`
> `  return (<span>{props.name}</span>);`
> `}`
> // Repetitive props prefix clutters markup

To understand why senior teams enforce **parameter destructuring**, consider how JavaScript executes component calls:

1. **The Single Props Dictionary Contract:** React always invokes component functions with a single argument containing all passed attributes: `ReaderGreeting(props)`.
2. **Lexical Scope Extraction:** When you write `export default function ReaderGreeting({ readerName })`, the JavaScript engine uses ECMAScript object destructuring to pull `readerName` out of the incoming dictionary and bind it directly to local lexical scope. This self-documents the component contract at the function header and eliminates repetitive `props.` property access throughout the render body.

```jsx title="Principle 3: Parameter Destructuring vs Props Object"
// **FOUNDATIONAL:** Explicit props object requires repetitive dot notation
export default function ReaderGreeting(props) {
  return (<div className="greeting">Welcome back, {props.readerName}</div>);
}

// **MODERN IDIOMATIC:** Destructuring unpacks inputs cleanly at signature
export default function ReaderGreeting({ readerName }) {
  return (<div className="greeting">Welcome back, {readerName}</div>);
}
```

> [!PRINCIPLE]
> **Principle 4: Treat Incoming Props as Read-Only Immutable Snapshots**
> You must treat all props received by a component as strictly **read-only immutable snapshots**, never reassigning or mutating prop values inside the function body.
> 
> >> read-only immutable snapshots : data passed into a component that cannot be reassigned or modified in memory
> 
> *We should do this:*
> `const formatted =`
> `  name.toUpperCase();`
> `return (<span>{formatted}</span>);`
> // Calculates derived value without mutating prop
> 
> *We should not do this:*
> `props.name =`
> `  props.name.toUpperCase();`
> `return (<span>{props.name}</span>);`
> // Mutating props causes unpredictable bugs

Interviewers frequently probe whether candidates understand *why* mutating props is disastrous in a component architecture:

1. **Broken Change Detection:** React relies on shallow reference equality (`Object.is(prevProps, nextProps)`) to determine whether a component or memoized subtree needs to re-render. If a child component mutates `props.tier = 'VIP'`, it mutates the parent's memory reference in place, blinding React to changes and corrupting cache layers.
2. **Idempotent Render Snapshots:** Every render pass represents an immutable historical record of the interface for a given state. If you need a modified representation of incoming data, calculate a fresh local variable (`const normalizedTier = tier.toUpperCase()`) without touching the incoming prop snapshot.

```jsx title="Principle 4: Immutable Props Contract"
// **WRONG:** Mutating incoming props corrupts application state
function SubscriberBadge(props) {
  props.tier = props.tier.toUpperCase(); // Crashes pure rendering
  return (<span>{props.tier}</span>);
}

// **RIGHT:** Derive local values without altering the incoming prop
function SubscriberBadge({ tier }) {
  const normalizedTier = tier.toUpperCase();
  return (<span>{normalizedTier}</span>);
}
```

> [!PRINCIPLE]
> **Principle 5: Let React Reconcile Changes in Memory to Preserve DOM Node Identity**
> You must allow React to reconcile element updates in memory, never wiping containers with `innerHTML` (which destroys active input focus and resets CSS animations).
> 
> *We should do this:*
> `<header><h1>{title}</h1></header>`
> // Surgical update preserves active input focus
> 
> *We should not do this:*
> `root.innerHTML =`
> `  '<h1>' + title + '</h1>';`
> // Container wipe destroys DOM nodes and focus

In senior engineering interviews, candidates must clearly contrast browser DOM destruction against virtual reconciliation:

1. **The Destructive C++ Cost of `innerHTML`:** Assigning a markup string to `innerHTML` forces the browser engine to wipe out all existing C++ DOM nodes inside that container. Even if the new HTML structure matches the old, the physical nodes are destroyed. Active text input focus is lost, text selection collapses, and active CSS transition animations reset to their first frame.
2. **Surgical In-Memory Patching:** React maintains an in-memory virtual tree of descriptors. During reconciliation, React diffs the previous descriptors against the new descriptors. It detects that only the `<h1>` text changed, and executes a targeted DOM mutation (`node.nodeValue = title`), leaving the living `<input>` element and active user focus completely undisturbed.

```jsx title="Principle 5: In-Memory Reconciliation vs DOM Destruction"
// **WRONG:** innerHTML wipes container, deleting active inputs and focus
root.innerHTML = `<header><h1>${title}</h1><input /></header>`;

// **RIGHT:** React diffs in memory and patches only the h1 text node
function Header({ title }) {
  return (<header><h1>{title}</h1><input /></header>);
}
```

| **CRITERIA**<br>(dimension) | **VANILLA JS (DOM)**<br>(imperative scripting) | **REACT (DECLARATIVE)**<br>(component model) | **INTERVIEW TAKEAWAY**<br>(architectural rationale) |
| :--- | :--- | :--- | :--- |
| **Data Projection** | Manual queries (`getElementById`,<br>`querySelector`) | Pure function calculation (`UI = f(data)`) | Decouples business logic from low-level browser DOM navigation |
| **State Drift** | Frequent: forgotten DOM queries leave stale nodes | Mathematically impossible: single parent source of truth | Guarantees all dependent visual regions update in the same render pass |
| **Props Handling** | Imperative function parameters or global state | Read-only immutable snapshots via destructuring | Enforces uni-directional data flow and prevents side-effect mutations |
| **DOM Sync** | Destructive `innerHTML` wipes or surgical manual loops | Virtual DOM reconciliation with minimal host patches | Preserves living DOM node identities, cursor focus, and CSS transitions |
| **Component Model** | Disconnected HTML snippets and separate script files | Encapsulated, reusable JavaScript functions | Unifies markup, styling contract, and render logic in self-contained units |

To eliminate state drift, we will build a unified site header using four components assembled strictly top-down. The parent container `SiteHeader.jsx` holds the single data truth and distributes it downward to `ReaderGreeting.jsx` and `SubscriberBadge.jsx`. Finally, `App.jsx` mounts the feature at the application root boundary.

### Step 1: First, we construct the parent container <SiteHeader.jsx>

We begin by constructing the parent container `SiteHeader.jsx`. This component acts as the orchestrator of the site header. Inside this file, we declare our reader data once in a local constant: `readerName = 'Clara Foster'`. Notice that `SiteHeader.jsx` does not query any DOM elements. Instead, it renders JSX describing the header layout and passes `readerName` downward as an explicit prop to both child components:

```jsx title="SiteHeader.jsx"
import ReaderGreeting from './ReaderGreeting.jsx';
import SubscriberBadge from './SubscriberBadge.jsx';
export default function SiteHeader() {
  const readerName = 'Clara Foster'; // Declares reader data **TRUTH**
  return (
    <header className="site-header">
      <ReaderGreeting readerName={readerName} /> // Passes name **PROP**
      <SubscriberBadge readerName={readerName} tier="Premium" />
    </header>);
}
```

Notice what is physically absent from `SiteHeader.jsx`: there are zero `document.getElementById` calls, zero query selectors, and zero manual string concatenations. If the value of `readerName` changes, both child components receive the new prop simultaneously. Because both children derive their display from the exact same variable in the parent, state drift is mathematically impossible.

### Step 2: Next, we build the child component <ReaderGreeting.jsx>

Now we build the first child component `ReaderGreeting.jsx`. This component has a single responsibility: display a personalized welcome greeting for the current subscriber. It declares a function parameter using object destructuring: `{ readerName }`. Inside its JSX markup, it renders a `<div>` element containing a `<span>`. It embeds the `readerName` variable directly inside the text using curly braces:

```jsx title="ReaderGreeting.jsx"
export default function ReaderGreeting({ readerName }) { // Unpacks **PROP**
  return (
    <div className="header-greeting">
      <span>Welcome back, {readerName}</span> // Evaluates in **JSX**
    </div>
  );
}
```

Inside `ReaderGreeting.jsx`, the curly braces around `{readerName}` act as an **evaluation window**. When the JavaScript engine reaches `{readerName}`, it evaluates the variable in memory and inserts its value into the rendered text. The component does not know where `readerName` came from. Nor does it care if other components display the same name. It simply takes its input prop and returns the corresponding markup description.

### Step 3: Then, we declare the child component <SubscriberBadge.jsx>

Next, we construct the second child component `SubscriberBadge.jsx`. In our plain JavaScript test, this widget fell victim to state drift. The script forgot to query its ID. In React, we define `SubscriberBadge` to accept two explicit props: `{ readerName, tier }`. It renders the subscriber's tier level alongside their name:

```jsx title="SubscriberBadge.jsx"
export default function SubscriberBadge({ readerName, tier }) {
  return (
    <div className="subscriber-badge">
      <span className="tier-tag">{tier}</span>          // Shows tier **TAG**
      <span className="member-name">{readerName}</span> // Renders **NAME**
    </div>
  );
}
```

What happens if `SubscriberBadge` manages its own reader lookup? If children query the DOM independently, timing differences cause desynchronized data. By requiring `SiteHeader` to pass `readerName` down to both children, we establish a **single source of truth**. Both widgets are guaranteed to display the exact same user identity on every render.

### Step 4: Finally, we mount the feature inside <App.jsx>

Finally, we seal our feature by importing and mounting `SiteHeader` inside the top-level application component `App.jsx`. `App.jsx` acts as the root boundary of our application layout. It renders a containing `<div className="newsroom-layout">` and mounts `<SiteHeader />` at the top of the page:

```jsx title="App.jsx"
import SiteHeader from './components/SiteHeader.jsx'; // Imports **ROOT**

export default function App() {
  return (
    <div className="newsroom-layout">
      <SiteHeader /> // Mounts at root **BOUNDARY**
    </div>
  );
}
```

When React renders `<App />`, it does not touch the physical DOM immediately. First, it executes `App()`, which calls `SiteHeader()`, which in turn calls `ReaderGreeting()` and `SubscriberBadge()`. React constructs an in-memory tree of lightweight JavaScript objects representing the entire layout. This in-memory tree is called the **Virtual DOM**, or in official modern documentation, the **UI descriptor tree**. React then calculates the physical DOM operations required and mounts the nodes efficiently into the browser window.

In our plain JavaScript experiment, updating a user required searching through document nodes and mutating elements by hand. When an application grows to dozens of components, that manual approach creates brittle code and state drift. React inverts this model completely. You declare components as pure functions of incoming props. React's engine then handles the DOM synchronization behind the scenes.

### Glossary

- **Declarative UI**: An architectural paradigm where code describes what the user interface should look like for a given state, leaving the runtime engine to compute and execute the necessary physical DOM mutations.
- **Component**: A self-contained, reusable JavaScript function that accepts input properties (props) and returns a tree of descriptors representing user interface markup.
- **Props**: A plain JavaScript dictionary of arguments passed downward from a parent component to a child component, configuring its behavior and appearance.
- **State Drift**: A synchronization bug where multiple UI elements that should reflect the exact same data display contradictory or outdated values due to missed imperative updates.
- **Virtual DOM / UI Descriptor Tree**: A lightweight in-memory tree of JavaScript objects representing the desired user interface structure, used by React to compute minimal physical DOM diffs.

## Beyond the basics

- **The UI descriptor tree and React elements**: When JSX executes, it produces plain, immutable JavaScript objects called React elements via `react/jsx-runtime`. React creates this UI tree from your components and uses it to compute minimal physical DOM mutations rather than traversing browser nodes directly (see [react.dev/learn/understanding-your-ui-as-a-tree](https://react.dev/learn/understanding-your-ui-as-a-tree)).
- **Purity in component rendering**: A React component function must be a pure calculation with respect to its inputs; given the same props, it must always return the same JSX without mutating preexisting variables or performing outside side effects during render (see [react.dev/learn/keeping-components-pure](https://react.dev/learn/keeping-components-pure)).
- **Module dependency trees vs render trees**: A React application possesses two distinct tree structures: the static module dependency tree evaluated by bundlers like Vite using `import` statements, and the dynamic runtime render tree constructed by React representing nested component instances on screen (see [react.dev/learn/understanding-your-ui-as-a-tree](https://react.dev/learn/understanding-your-ui-as-a-tree)).
- **Read-only immutable props**: Props received by a child component are strictly read-only snapshots in JavaScript memory; components must never reassign or mutate properties like `props.readerName` directly, requiring state setters or parent callbacks to request updates (see [react.dev/learn/passing-props-to-a-component](https://react.dev/learn/passing-props-to-a-component)).
- **Host elements vs custom component instances**: Lowercase JSX tags (`<header>`, `<span>`, `<div>`) map directly to native HTML host elements in the browser DOM, whereas capitalized tags (`<SiteHeader />`, `<ReaderGreeting />`) signal custom JavaScript functions that React invokes in memory (see [react.dev/learn/your-first-component](https://react.dev/learn/your-first-component)).
- **Fragments and single-root returns**: Every React component must return a single root JSX element because the markup compiles into a single JavaScript function call; when multiple adjacent sibling elements are needed without polluting the DOM with extra wrapper `<div>` nodes, developers wrap them in an empty fragment `<>...</>` (see [react.dev/learn/writing-markup-with-jsx](https://react.dev/learn/writing-markup-with-jsx)).

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Declarative Data Flow

➔ ALWAYS declare shared application data in a single parent container and pass it downward to children through explicit props.

➔ NEVER query or mutate the physical DOM directly with methods like `document.getElementById` or `container.innerHTML` inside React applications.

➔ IF multiple components display the same data THEN derive their output from a single source of truth to permanently prevent state drift.

❒ Component Naming & Syntax

➔ ALWAYS capitalize component function names (`SiteHeader`) so React can distinguish custom components from native HTML elements (`<header>`).

➔ ALWAYS use parameter destructuring (`{ readerName }`) in component signatures to explicitly document required props and eliminate repetitive `props.` prefixes.

**DO THIS:** derive all UI output declaratively from incoming props

```jsx right
export default function ReaderGreeting({ readerName }) {
  return (<span>Welcome back, {readerName}</span>);
}
```

**DO NOT DO THIS:** hunt and mutate physical DOM nodes manually

```jsx wrong
export default function ReaderGreeting() {
  document.getElementById('greeting').textContent = 'Welcome back, Clara';
  return (<span id="greeting" />);
}
```
