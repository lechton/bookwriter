### The Friction of Forgotten Variables and Silent Clicks

In earlier lessons, you learned that React components turn props into JSX markup. In Lecture 13, you wired button clicks to event handlers using function references. However, web interfaces must also remember user interactions across time. When a reader clicks a like button or bookmarks an article, the screen must display the updated value. In traditional JavaScript, developers assigned values to local variables or modified DOM properties directly. When developers bring that mental model to React, they often declare a local variable inside their component. They write `let likes = 0` and increment it on click. But clicking the button changes nothing on screen: the count remains stuck at zero.

A developer might assume that modifying a variable in memory automatically updates the page. They might expect React to watch their variables. But React does not observe plain variable assignments. An assignment like `likes = likes + 1` alters a number in JavaScript memory. It never asks React to calculate new JSX. Even worse, if another interaction re-renders the card, the component function executes from the top. It re-runs `let likes = 0` and erases the counter back to zero.

A developer experiencing this friction might try two naive workarounds. They might reassign a local variable inside the function, or move `let likes = 0` outside the component. Mutating the local variable leaves the screen stuck. Moving the variable to the module level keeps the count in memory. But it still triggers no render, and every card on the page shares the exact same number.

```jsx title="Naive Counter Attempt"
export default function StoryCard({ title }) {
  let likes = 0; // Local variable declared inside component
  function handleLike() {
    likes = likes + 1; // Mutates local variable silently
    console.log('clicked, likes =', likes);
  }
  return <button onClick={handleLike}>Like ({likes})</button>;
}
```

React solves both problems through a special function called `useState`. When you declare state with `useState`, React stores that value outside the component function in its own internal memory. Calling `useState` gives you two items: the current value to read during this render, and a setter function that stores the next value and queues a re-render. When the setter runs, React calls the component function again, hands back the updated value, and paints the new count on screen.

> [!WILD]
> **Why does assigning a local variable fail to update the screen?**
>
> Plain JavaScript assignments change memory that React does not watch. React redraws the screen only when asked to render. An assignment like `likes = likes + 1` updates local memory silently while leaving the screen stuck on the old number. When another interaction triggers a re-render, the component function executes from the top and resets the local variable to zero. The `useState` Hook solves both problems: it provides durable memory that survives renders, and a setter function that requests a new render.

### Functions That Run from the Top and React's External Memory

To understand component memory, we must look at how JavaScript functions execute. In standard JavaScript, when a function runs, its local variables exist only for the duration of that call. When the function returns, all local variables are discarded. Because a React component is a standard JavaScript function, React executes the entire function body from top to bottom on every render. If your component declares `let likes = 0`, that line executes every single time React renders the card. In Lecture 12, we learned that React can call a component function at any time, and components must remain pure. Therefore, a component cannot rely on its own function scope to remember values across time.

Because the function body cannot hold memory between calls, React stores component state outside the function. Think of React as maintaining an internal shelf of memory slots for each component mounted on the page. When your component calls `useState(0)`, it asks React: "Give me the value stored in my memory slot; if this is the first time I am rendering, store 0 as my initial value." On the initial render, React stores `0` and returns `0` alongside a setter function. When the user clicks the button, your handler calls the setter: `setLikes(likes + 1)`. The setter updates the value in React's external memory slot and requests a new render. When React renders the component again, the function runs from the top, calls `useState(0)`, but React returns the stored value `1` instead of `0`.

To read the value and the setter in one clean line, React developers use JavaScript array destructuring. The `useState` Hook returns an array containing exactly two items: the current state value at index 0, and the setter function at index 1. Writing `const [likes, setLikes] = useState(0)` unpacks those two items into two distinct local variables. The square brackets tell JavaScript to pull the first item into `likes` and the second item into `setLikes`. By community convention, developers name this pair `[something, setSomething]`, making state variables instantly recognizable across codebases.

### Principles of React: Component Memory and State Management

When preparing for senior technical interviews, candidates must clearly explain why ordinary variables fail between renders, how `useState` preserves values in external memory, why Hook call order matters, and why state remains private to each rendered instance. To master these concepts, we formalize the seven governing principles of component memory:

> [!PRINCIPLE]
> **Principle 1: Assigning a Local Variable Does Not Ask React to Render**
> React updates what is on the screen only when it renders a component again. Assigning a new value to a local variable changes memory that React does not watch. Because an assignment alone never requests a render, the screen remains stuck on the old value.
>
> *We should do this:*
> `setLikes(likes + 1); // Asks React to render again with the next number`
>
> *We should not do this:*
> `likes = likes + 1; // Assigns local variable without notifying React`

In plain JavaScript, developers expect changes to variables to take effect immediately. In React, the screen is a declarative projection of state calculated during the render phase. When a user clicks a button and your code executes `likes = likes + 1`, JavaScript increments the number stored in local variable memory. However, React has no mechanism to observe plain JavaScript variable mutations. Because React does not know the number changed, it never schedules a render. The browser never recalculates JSX, and the screen continues displaying the old markup.

```jsx title="Local Variable Assignment"
export default function StoryCard({ title }) {
  let likes = 0; // Plain local variable
  function handleLike() {
    likes = likes + 1; // Mutates variable silently
    console.log('clicked, likes =', likes);
  }
  return <button onClick={handleLike}>Like ({likes})</button>;
}
```

When you click the Like button three times in this component, the browser console prints `clicked, likes = 1`, `clicked, likes = 2`, and `clicked, likes = 3`. The data in JavaScript memory changed on every click. Yet on the screen, the button text remains permanently fixed at `Like (0)`. An assignment alone never asks React to update the DOM. What happens inside React between the setter call and the browser painting the new screen belongs to Lecture 15.

> [!PRINCIPLE]
> **Principle 2: Each Render Calls the Function Again and Resets Local Variables**
> A React component is a function that React calls from the top every time it renders. Every local variable declared inside the component body is created fresh during that call and vanishes when the function returns. When a component re-renders, its local variables reset back to their initial values.
>
> *We should do this:*
> `const [likes, setLikes] = useState(0); // State survives across renders in React`
>
> *We should not do this:*
> `let likes = 0; // Local variable resets to zero on every render`

In Lecture 12, we established that React components must be pure functions that compute their output from incoming inputs. Whenever a component re-renders, React invokes the function again. Just like any normal JavaScript function, each invocation creates a brand-new execution context. Every `let` and `const` declaration inside the body runs from scratch. Any values calculated or modified during the previous render are completely gone.

```jsx title="Local Variable Reset"
import { useState } from 'react';
export default function StoryCard({ title }) {
  let likes = 0; // Resets on every render pass
  const [saved, setSaved] = useState(false);
  console.log('render, likes =', likes); // Logs reset count
  const like = () => console.log('clicked, likes =', ++likes);
  const label = saved ? 'Saved' : 'Save';
  return <button onClick={() => setSaved(!saved)}>{label}</button>;
}
```

Watch what happens when you interact with this component. On initial render, the console logs `render, likes = 0`. You click the Like button three times; the console prints `clicked, likes = 1`, `clicked, likes = 2`, and `clicked, likes = 3`, while the screen still shows `0 likes`. Now, click the Save button. The Save button uses `useState`, so calling `setSaved` asks React to render the card again. React runs `StoryCard` from the top. The console logs `render, likes = 0`. All previous click increments vanished! If you click Like once more, the console logs `clicked, likes = 1` again. In Lecture 4, we learned how curly braces evaluate expressions; here, the Save button uses a ternary expression (`saved ? 'Saved' : 'Save'`) to prove that re-rendering wipes local variables.

> [!PRINCIPLE]
> **Principle 3: Store Durable Values in State and Update Them Exclusively with Setters**
> To keep data that survives across renders and updates the screen, store it in a state variable using the `useState` Hook. React returns a pair: the current value to read during this render, and a setter function to request the next value. We update state exclusively by calling the setter; reassigning the state variable directly throws a TypeError: Assignment to constant variable.
>
> >> state variable : a value React retains across renders for a component
> >> Hook : a special function starting with use that lets components tap into React features
> >> setter function : a function returned by useState that stores the next state and requests a render
>
> *We should do this:*
> `onClick={() => setLikes(likes + 1)} // Calls setter to store next count and render`
>
> *We should not do this:*
> `onClick={() => { likes = likes + 1; }} // Assignment to constant variable throws TypeError`

The `useState` Hook provides the dual capability local variables lack: memory persistence and re-render triggers. When you write `const [likes, setLikes] = useState(0)`, you declare a state variable `likes` and a setter function `setLikes`. Because `likes` is declared with `const`, attempting to write `likes = likes + 1` throws `TypeError: Assignment to constant variable.` in standard JavaScript. Even if declared with `let`, direct assignment would fail to notify React. Calling `setLikes(likes + 1)` hands the new value to React and schedules a render. Why a console log immediately after calling `setLikes` still reads the old number belongs to Lecture 16.

```jsx title="State Counter with useState"
import { useState } from 'react';
export default function StoryCard({ title }) {
  const [likes, setLikes] = useState(0); // State persists in React
  console.log('render, likes =', likes);
  function handleLike() {
    setLikes(likes + 1); // Updates state and requests render
  }
  return <button onClick={handleLike}>Like ({likes})</button>;
}
```

With `useState`, click the Like button twice. On initial mount, the console logs `render, likes = 0`. After the first click, React re-renders the component and logs `render, likes = 1`, and the screen displays `Like (1)`. After the second click, React logs `render, likes = 2`, and the screen updates to `Like (2)`. Some developers are tempted to declare `let likes = 0` outside the component at the module level. A module-level variable survives across renders, but it still triggers no render on click, and every card rendered on the page shares the exact same variable, destroying component isolation.

> [!PRINCIPLE]
> **Principle 4: React Keeps State Outside the Function and Matches It by Call Order**
> React stores state data outside the component function in an internal memory list. On the initial render, React saves each starting value in order. On subsequent renders, React ignores the argument and returns the stored value matching that call's position in the sequence. Calling Hooks conditionally disrupts this call order and corrupts state alignment.
>
> >> call order : the fixed sequence in which a component invokes its Hooks on every render
> >> internal memory list : React's private storage outside the component function that holds state pairs
>
> *We should do this:*
> `const [saved, setSaved] = useState(false); // Second call in stable top-level order`
>
> *We should not do this:*
> `if (likes > 0) { useState(false); } // Conditional Hook call corrupts React state order`

Beginners often ask: "If `useState(0)` runs on every single render, why doesn't likes reset to 0 every time?" The answer is that React does not inspect the argument on re-renders. When React renders a component, it maintains an internal pointer index starting at 0. The first call to `useState` retrieves slot 0 from React's internal list for this component. The second call to `useState` retrieves slot 1. React does not identify state variables by their names (`likes` or `saved`); it identifies them strictly by their call order. Why Hooks must never be placed inside conditions or loops belongs to Lecture 37.

```jsx title="Multiple State Variables"
import { useState } from 'react';
export default function StoryCard({ title }) {
  const [likes, setLikes] = useState(0); // Slot 0: like counter
  const [saved, setSaved] = useState(false); // Slot 1: bookmark flag
  console.log('render:', likes, saved);
  const onLike = () => setLikes(likes + 1);
  return <button onClick={onLike}>Like ({likes})</button>;
}
```

Look at the console when running this component. On initial render, the component logs `render: 0 false`. When you click Like, React retrieves slot 0 as 1 and slot 1 as false, logging `render: 1 false`. Next, click Save. React retrieves slot 0 as 1 and slot 1 as true, logging `render: 1 true`. Each call to `useState` retrieves its own independent value from React's internal memory list. Because call order dictates slot alignment, calling `useState` inside an `if` block would shift the slots on subsequent renders, causing React to log a warning and throw an error.

> [!PRINCIPLE]
> **Principle 5: Each Rendered Component Instance Maintains Its Own Isolated State**
> State belongs to each rendered component instance, not to the component function in your file. When you render two `<StoryCard />` elements on the same page, React creates two completely independent memory slots in the tree. Clicking Like on the first card updates only that card's count to 2 likes while the second card remains at 0 likes. The parent component can neither read nor modify these private values.
>
> >> component instance : a single mounted copy of a component element in the UI tree
> >> private state : memory isolated inside one rendered instance that outside components cannot touch
>
> *We should do this:*
> `const [likes, setLikes] = useState(0); // Declared in component: each card has own count`
>
> *We should not do this:*
> `let likes = 0; // Declared outside: both cards share one variable`

In React, state is completely private and isolated to the specific component instance that declared it. If your application mounts two `<StoryCard />` components side by side, React assigns separate, dedicated state stores to each position in the UI tree. When you click Like on Card 1, React calls `StoryCard` for Card 1 only. Card 2 does not re-render, and its counter remains completely untouched. When two sibling cards need to share one count, moving state to their common parent belongs to Lecture 23. How React ties state to a component's position in the UI tree belongs to Lecture 24.

```jsx title="Independent Component Instances"
import StoryCard from './StoryCard.jsx';
export default function App() {
  return (
    <main className="story-feed">
      <h1>The National Times</h1>
      <StoryCard title="Downtown Transit Accord" /> // First instance
      <StoryCard title="City Rail Extension" /> // Second instance
    </main>
  );
}
```

Mount two `<StoryCard />` instances in `App.jsx`. Click Like twice on the first card ("Downtown Transit Accord"). The first card updates its screen to display `2 likes`. Now inspect the second card ("City Rail Extension"): its counter still displays `0 likes`. Each card maintains completely isolated memory. Furthermore, `App` cannot read or modify the `likes` variable of either card. State is fully private to the component instance that creates it.

> [!PRINCIPLE]
> **Principle 6: Pass an Initializer Function When Initial State Is Expensive to Compute**
> React uses the initial state argument on the first render only and ignores it on all later renders. However, calling a function in the argument like `useState(createInitialLikes())` runs on every single render cycle. When computing the start value is expensive, pass an initializer function by reference (`useState(createInitialLikes)`), so React invokes it once during setup and skips the work on subsequent renders.
>
> >> initializer function : a function passed without parentheses that React calls once to create the initial state
> >> initial state argument : the value or function passed to useState to seed a state variable
>
> *It is best practice to do this:*
> `useState(createInitialLikes) // Passes function reference: React calls it once`
>
> *Instead of doing this:*
> `useState(createInitialLikes()) // Calls function on every render, wasting calculation`

When you pass an expression to `useState`, JavaScript evaluates that expression before calling `useState`. If you write `useState(createInitialLikes())`, JavaScript executes `createInitialLikes()` on every render pass. Even though React discards the return value after the initial render, the CPU still paid the cost of computing it. When initial state requires parsing JSON, reading storage, or iterating over large arrays, this repeated computation causes frame drops. Passing `createInitialLikes` as an initializer function lets React call it only when initializing the component. In development under StrictMode, React calls initializers twice on the initial render to verify purity; why StrictMode does this belongs to Lecture 46.

```jsx title="Initializer Function Optimization"
import { useState } from 'react';
function createInitialLikes() {
  console.log('computed initial likes'); // Logs when initializer runs
  return 10;
}
export default function StoryCard({ title }) {
  const [likes, setLikes] = useState(createInitialLikes); // Passes reference
  return <button onClick={() => setLikes(likes + 1)}>Like ({likes})</button>;
}
```

In this component, we pass `createInitialLikes` without parentheses. When the card mounts initially, the console logs `computed initial likes` (or twice under StrictMode in development). When you click the Like button twice, the card re-renders and updates the count to 11 and 12, but `computed initial likes` never logs again! In contrast, if you wrote `useState(createInitialLikes())`, the log would appear on initial mount and on every subsequent click, proving that the calculation ran pointlessly on every render.

> [!PRINCIPLE]
> **Principle 7: Call Setters Exclusively Inside Event Handlers and Never During Render**
> Call a setter function only inside an event handler, never unconditionally in the component body or directly inside JSX evaluation braces. Calling `onClick={setLikes(likes + 1)}` invokes the setter immediately during render, which schedules another render, invoking the setter again in an infinite loop. React halts this cycle by throwing the fatal runtime error: Too many re-renders. React limits the number of renders to prevent an infinite loop.
>
> >> unconditional render call : executing a state setter directly while React is calculating JSX
> >> infinite render loop : a crash where a render triggers a state update that immediately triggers another render
>
> *We should do this:*
> `onClick={() => setLikes(likes + 1)} // Arrow function waits until user clicks button`
>
> *We should not do this:*
> `onClick={setLikes(likes + 1)} // Runs during render and throws Too many re-renders`

In Lecture 13, we learned that expressions inside JSX curly braces evaluate immediately during the render phase. If you write `onClick={setLikes(likes + 1)}`, JavaScript executes `setLikes` while React is building the element tree. The setter updates state and immediately queues another render. React re-runs the component, hits the JSX braces, and executes `setLikes` again. Without a stopping condition, this creates an infinite render loop. To prevent the browser tab from freezing, React aborts execution and throws: "Too many re-renders. React limits the number of renders to prevent an infinite loop." Wrapping the call in an arrow function (`() => setLikes(likes + 1)`) defers the setter until the user physically clicks.

```jsx title="Safe Handler vs Immediate Setter Call"
import { useState } from 'react';
export default function StoryCard({ title }) {
  const [likes, setLikes] = useState(0);
  const handleLike = () => setLikes(likes + 1); // Waits for click event
  return <button onClick={handleLike}>Like ({likes})</button>;
}
```

By wrapping `setLikes(likes + 1)` in an arrow function or handler, the setter executes strictly when the user clicks the button. The component mounts cleanly displaying `Like (0)`, and each click increments the count without triggering a crash.

### Step 1: First, we declare the story feed container <src/App.jsx>

In `src/App.jsx`, we establish the top-level container for our news feed. The component imports `StoryCard` and mounts two distinct story cards side by side. Notice that `App` owns zero state: it passes only static story titles downward as props. By mounting two separate `<StoryCard />` elements, `App` creates two independent component instances in the React tree.

```jsx title="App.jsx"

    </main>

```

Notice that `App` does not manage like counters or bookmark flags. It delegates all interactive memory to the individual cards. This architecture ensures that when a reader likes an article, only that specific card re-renders, while the parent feed remains untouched.

### Step 2: Next, we build the interactive story card <src/components/StoryCard.jsx>

In `src/components/StoryCard.jsx`, we construct the interactive card boundary. The component receives `title` through object destructuring and calls `useState` twice to declare two independent state variables: `likes` initialized to `0`, and `isBookmarked` initialized to `false`.

```jsx title="StoryCard.jsx" startLine="1" continues="bottom"

import SaveButton from './SaveButton.jsx'; // Imports button
export default function StoryCard({ title }) {
  const [likes, setLikes] = useState(0); // State slot 0
  const [isBookmarked, setIsBookmarked] = useState(false);
  return (
    <article className="story-card">
      <h3>{title}</h3>
```

Inside the JSX return statement, we render a Like button and mount the child `<SaveButton />`. The Like button connects its click event to an inline arrow function: `onClick={() => setLikes(likes + 1)}`. When clicked, it calls `setLikes` with the next count, asking React to re-render this card. Next, `StoryCard` passes `isBookmarked` and an `onToggle` callback down to `SaveButton`.

```jsx title="StoryCard.jsx" startLine="9" continues="top"
      <button type="button" onClick={() => setLikes(likes + 1)}>
        Like ({likes}) // Displays state count
      </button>
      <SaveButton
        isBookmarked={isBookmarked}
        onToggle={() => setIsBookmarked(!isBookmarked)} // Toggles state
```

Notice how `StoryCard` serves as the state owner: it owns both pieces of state, updates `likes` directly through its own button, and delegates the display of bookmark status to `SaveButton`.

### Step 3: Finally, we construct the bookmark toggle button <src/components/SaveButton.jsx>

In `src/components/SaveButton.jsx`, we construct the leaf button control. The component receives `isBookmarked` and `onToggle` as props. It owns zero local state. Instead, it renders a native `<button type="button">` and uses a ternary expression to display "Saved" or "Save" based on the incoming boolean prop.

```jsx title="SaveButton.jsx"
export default function SaveButton({ isBookmarked, onToggle }) {
  const label = isBookmarked ? 'Saved' : 'Save';
  return (
    <button type="button" className="save-btn" onClick={onToggle}>
      {label} // Displays current bookmark status
    </button>
  );
}
```

When a reader clicks the Save button, the click invokes `onToggle`, which calls `setIsBookmarked(!isBookmarked)` inside `StoryCard`. React re-renders `StoryCard`, updates the boolean state, and passes the new value down to `SaveButton`, flipping the text from "Save" to "Saved" cleanly.

### Where you will meet this

1. **Article reaction buttons and like counters**: Each story card in a media feed tracks reader engagement independently without global variable conflicts.
2. **Accordion and disclosure panels**: Section headers toggle local open and closed states, letting readers expand articles independently.
3. **Form text fields and interactive filters**: Search bars and text inputs preserve user input across re-renders using state variables.
4. **Tabbed reading layouts and dashboards**: Navigation headers switch active views by tracking the selected tab index in local state.

### Glossary

- **State Variable**: A value retained by React across renders that drives what appears on the screen.
- **Setter Function**: A function returned by useState that updates the state variable and requests a new render.
- **Hook**: A special function provided by React that lets component functions tap into state and lifecycle features.
- **Component Instance**: A single mounted occurrence of a component in the UI tree with its own isolated state memory.
- **Initializer Function**: A function passed to useState that React invokes only once during component setup to compute initial state.
- **Array Destructuring**: A JavaScript syntax that unpacks values from an array into distinct variables in a single assignment.

## Beyond the basics

- State updates are batched to group multiple setter calls into a single render pass (see [react.dev/learn/queueing-a-series-of-state-updates](https://react.dev/learn/queueing-a-series-of-state-updates)).
- State behaves like a snapshot where reading a state variable immediately after calling its setter returns the value from the current render (see [react.dev/learn/state-as-a-snapshot](https://react.dev/learn/state-as-a-snapshot)).
- Updater functions allow sequential updates when calculating new state depends directly on the previous state (see [react.dev/reference/react/useState#updating-state-based-on-the-previous-state](https://react.dev/reference/react/useState#updating-state-based-on-the-previous-state)).
- React skips rendering when a setter is called with a value identical to the current state by Object.is comparison (see [react.dev/reference/react/useState#caveats](https://react.dev/reference/react/useState#caveats)).
- Top-level Hook rules require calling Hooks unconditionally at the top level of component functions (see [react.dev/reference/rules/rules-of-hooks](https://react.dev/reference/rules/rules-of-hooks)).

**Architectural Takeaways & Decision Matrix**

❒ Storing Component Memory

➔ ALWAYS declare state variables using `useState` when data must survive across renders and update the screen.

➔ NEVER reassign local variables directly expecting React to detect the change and redraw the user interface.

➔ IF an initial state calculation is computationally expensive THEN pass an initializer function by reference (`useState(computeStart)`) to avoid re-running it on every render.

❒ Setter Invariants

➔ NEVER call a state setter function unconditionally inside the component render body or JSX braces to prevent fatal infinite render loops.

➔ ALWAYS wrap parameterized setter calls inside inline arrow functions or event handlers so they execute only upon user interaction.

**DO THIS:** update state exclusively through setter functions inside event handlers

```jsx right
function LikeButton() {
  const [likes, setLikes] = useState(0);
  return (
    <button type="button" onClick={() => setLikes(likes + 1)}>
      Like ({likes})
    </button>
  );
}
```

**DO NOT DO THIS:** reassign local variables or call setters during render

```jsx wrong
function LikeButton() {
  let likes = 0;
  return (
    <button type="button" onClick={setLikes(likes + 1)}>
      Like ({likes})
    </button>
  );
}
```

| | **LOCAL VARIABLES**<br>(Ephemeral Memory) | **REACT USESTATE**<br>(Durable Memory) |
| ---: | :--- | :--- |
| **Persistence** | Discarded when function completes;<br>resets on every render | Retained by React across renders<br>in external memory slots |
| **Screen Updates** | Changing variable triggers zero renders;<br>screen stays stuck | Calling setter requests a new render<br>and updates the screen |
| **Instance Scope** | Shared globally if moved to module;<br>reset locally if in function | Completely private and isolated<br>to each rendered component instance |
| **Initial Value** | Re-evaluated and re-assigned on<br>every single function call | Seeded once on initial render;<br>initializer functions run once |
