# Lecture 16: State as a Snapshot
> INTERVIEW QUESTION | ❱ CORE | Why does state appear frozen inside a render, even right after you set it?

1. Ann builds a reader rating widget for stories at The National Times.
2. When a reader clicks five stars, the widget must store the rating and send it to the server.
3. Ann calls `setRating(5)` and logs `rating` on the very next line.
4. The screen displays five stars, yet the console prints zero. Where is the five?
5. Worse, the server receives a rating of zero while the reader sees five.
6. The setter ran, but the variable in Ann's running function never changed.
7. Today we learn why state behaves as a snapshot fixed for an entire render.

### The console prints the old rating after the setter

In Lecture 14 we gave a component memory. `useState` keeps state across runs, and the setter asks React to run the component again. In Lecture 15 we traced the path from a setter call to the screen. React triggers, renders, and commits, updating the page only after the event handler finishes.

Ann now builds a reader rating widget called `StoryFeedback` for The National Times. Readers can click buttons to rate an article from one to five stars. A colleague created a helper function named `sendRating` in the file `feedbackApi.js`. When a reader clicks five stars, Ann must update the screen and send the new score to the server.

Ann comes from plain JavaScript, where assigning a variable changes its value immediately. In React, Ann calls `setRating(5)` and logs `rating` on the very next line. She also passes `rating` to `sendRating(rating)`.

```jsx title="StoryFeedback.jsx, first attempt" startLine="6"
  function handleFiveStars() {
    setRating(5);
    console.log('rating after setter:', rating); // prints 0 in this run
    sendRating(rating);
  }
```

Ann opens the browser and clicks the five-star button. The card on the screen updates to show 5 stars. But the development console prints `rating after setter: 0`. Even worse, the server receives a rating of 0.

Ann is puzzled. Did the setter fail to run? If the setter ran, why is `rating` still 0 on the next line? What happens if she calls `setRating(rating + 1)` three times in a row? And what does a delayed timer see if the reader clicks another rating?

> [!WILD]
> **Why does state appear frozen after you set it?**
>
> On the line after `setRating(5)`, the state variable `rating` still holds `0`. Calling a setter does not mutate the variable in your running code. React updates state by triggering a new render with the new value. The current function continues executing using its existing snapshot. Code in the running handler must compute the new value once in a local variable.

### State as a snapshot of one moment in time

When React renders a component, it calls your component function. The `useState` call returns the state value for that specific run. In that run, the state variable is a standard JavaScript `const`. It never changes while that function executes.

The JSX, props, local variables, and event handlers are all computed using the state of that render. We call this fixed set of values a **snapshot**. React takes a snapshot of the UI every time it calls your component.

Calling a setter function does not change the variable in your running code. Instead, the setter tells React what value to use in the next render. It asks React to call your component function again with that new value. The running handler finishes executing using the current snapshot.

You can visualize this behavior using the substitution method from the official React documentation. If `rating` is `0` when the component runs, you can substitute `0` for `rating` everywhere. The call `setRating(rating + 1)` evaluates as `setRating(0 + 1)`.

```jsx title="StoryFeedback.jsx, three calls" startLine="6"
  function handleTripleBoost() {
    setRating(rating + 1); // evaluates setRating(0 + 1)
    setRating(rating + 1);
    setRating(rating + 1); // asks for 1 three times
  }
```

Calling `setRating(rating + 1)` three times in one handler evaluates as `setRating(0 + 1)` three times. Each call asks React for 1, not 3. The screen moves from 0 to 1, exactly as if you called `setRating(1)` three times.

Every render also creates its own fresh event handlers. In JavaScript, an inner function is a **closure**. A closure remembers the variables of the scope where it was created. A handler created when `rating` is 5 closes over that 5.

A delayed timer created with `setTimeout` keeps reading the 5 from that render. In browser JavaScript, `setTimeout` runs a function after waiting a set number of milliseconds. Even if other clicks happen during the delay, that timer callback still sees its own snapshot.

Earlier lessons laid the foundation for this mental model. Lecture 13 established that event handlers are functions passed to `onClick`, not called during render. Lecture 14 taught that `useState` stores memory outside the component and starts local variables fresh on each call. Lecture 15 proved that React renders and commits only after the event handler finishes.

Looking ahead, Lecture 17 will introduce updater functions like `r => r + 1` for consecutive updates. Lecture 18 will show how mutating objects directly can accidentally damage earlier snapshots.

This snapshot model answers all of Ann's questions. Why did logging `rating` print 0? How should she send the new rating to the server? And why does a timer protect delayed code from later changes? The three principles explain each answer.

### Principles of React: State as a Snapshot

Interviewers ask this question to probe the snapshot model and closure behavior. The first principle explains why state never changes within a render. The second principle shows how to use the next value right away. The third principle explains how closures preserve earlier renders.

> [!PRINCIPLE]
> **Principle 1: State is a constant number during one run of your component**
> In your component, `count` is a regular constant. When React runs the function, `count` holds one value, such as 0. Calling `setCount(1)` does not change that constant in your running code. Instead, it asks React to run the component next time with 1. Because this run is still executing, `count` stays 0 on every line. Calling `setCount(count + 1)` three times in the same click just asks for `0 + 1` three times.
>
> *We should do this:*
> `const [count, setCount] = useState(0);`
> `setCount(count + 1); // asks React for 1 on the next run`
> `console.log(count); // prints 0, this run's constant number`
>
> *We should not do this:*
> `const [count, setCount] = useState(0);`
> `setCount(count + 1); // asks for 0 + 1`
> `setCount(count + 1); // still reads 0, asks for 0 + 1 again`

In Ann's component, `rating` starts at 0. When she clicks "+3 Boost", the function executes three calls to `setRating(rating + 1)`. Because `rating` is 0 throughout that render, all three calls pass `0 + 1`. React queues a render with 1. When `StoryFeedback` runs again, `useState` returns 1, and the console logs `render rating = 1`. A second click on "+3 Boost" evaluates `1 + 1` three times, moving the count to 2.

> [!PRINCIPLE]
> **Principle 2: Calculate the next value once if other code needs it right away**
> Any line of code inside the same click handler still reads the current run's state. Reading `count` right after calling `setCount(count + 1)` still reads the old number. When you need to send the new number to an API right away, calculate it once in a plain variable. Pass that variable to the setter, and pass that same variable to your other code.
>
> *We should do this:*
> `const nextCount = count + 1; // calculate the new value once`
> `setCount(nextCount); // tells React what to show next`
> `send(nextCount); // sends 1, the new number`
>
> *We should not do this:*
> `setCount(count + 1); // asks React for 1 on next run`
> `send(count); // sends 0, current run's old number`

In Ann's five-star button, she replaces `sendRating(rating)` with a local variable: `const nextRating = 5`. She calls `setRating(nextRating)` and `sendRating(nextRating)`. The server receives 5 immediately. After the handler returns, React re-renders `StoryFeedback` with `rating = 5`. The server and the screen now agree completely.

> [!PRINCIPLE]
> **Principle 3: A click handler keeps the values of the run that created it**
> Every run of a component creates its own functions. When you declare a click handler, it captures the variables from that specific run. If the handler waits for a delay like `setTimeout`, it still sees the values from when it was created. If another click changes state while the timer waits, the delayed code still reads its original value safely.
>
> *We should do this:*
> `function handleSend() {`
> `  setTimeout(() => {`
> `    console.log(count); // prints the count from this run`
> `  }, 1000);`
> `}`

In `StoryFeedback`, Ann adds a Send button that logs a thank-you message after a 100-millisecond delay using `setTimeout`. She rates the story with 5 stars, clicks Send, and quickly clicks 2 stars before the timer finishes. The screen updates to show 2 stars. But when the timer fires, the console logs `Thanks for rating 5`. The callback was created during the render where `rating` was 5, so it preserves that snapshot faithfully.

### Step 1: First, we lay out the feedback application <src/App.jsx>

```jsx title="App.jsx"
import StoryFeedback from './components/StoryFeedback.jsx';
export default function App() {
  console.log('App runs'); // logs on initial render
  return (
    <main className="feedback-layout">
      <h1>Story Review Desk</h1>
      <StoryFeedback />
    </main>
  );
}
```

`App` owns zero state, so clicks inside the feedback card never force `App` to re-render. It executes once on initial load, keeping top-level layout completely isolated from rating clicks.

### Step 2: Next, we build the rating boundary <src/components/StoryFeedback.jsx>

```jsx title="StoryFeedback.jsx" startLine="1" continues="bottom"
import { useState } from 'react';
import RatingControls from './RatingControls.jsx';
import { sendRating } from '../feedbackApi.js';
export default function StoryFeedback() {
  const [rating, setRating] = useState(0); // rating snapshot
  console.log('StoryFeedback runs, rating =', rating);
```

```jsx title="StoryFeedback.jsx" startLine="7" continues="both"
  function handleRate(score) {
    const nextRating = score; // compute value once
    setRating(nextRating);
    sendRating(nextRating);
  }
  function handleSend() {
    setTimeout(() => {
      console.log('Thanks for rating', rating); // captures snapshot
    }, 100);
  }
```

```jsx title="StoryFeedback.jsx" startLine="17" continues="top"
  return (
    <section className="feedback-card">
      <p>Rating: {rating} stars</p> // displays snapshot value
      <RatingControls onRate={handleRate} onSend={handleSend} />
    </section>
  );
}
```

`StoryFeedback` owns the state. When `handleRate(5)` executes, `nextRating` holds 5. Both `setRating` and `sendRating` receive 5. Then `handleSend` captures `rating` as a closure.

### Step 3: Finally, we build the rating action controls <src/components/RatingControls.jsx>

```jsx title="RatingControls.jsx"
export default function RatingControls({ onRate, onSend }) {
  return (
    <div className="button-group">
      <button onClick={() => onRate(5)}>5 Stars</button> // rates 5 stars
      <button onClick={() => onRate(2)}>2 Stars</button>
      <button onClick={onSend}>Send Feedback</button>
    </div>
  );
}
```

`RatingControls` owns no state of its own. It acts as an interactive control bridge, invoking callback props when buttons are pressed. The parent component executes the real updates.

### Where you will meet this

You will meet this when logging analytics or sending API payloads immediately after calling a state setter.

You will meet this when building forms that clear input fields while dispatching form content to backend endpoints.

You will meet this when setting delayed timer notifications, toast alerts, or auto-dismiss messages with `setTimeout`.

You will meet this when handling rapid button clicks, such as like counters or shopping cart increment buttons.

You will meet this in technical interviews when asked whether `setState` is asynchronous and how closures interact with React state.

### For the interview

> **The Interview Question:** Why does state seem frozen within the same component run?

**1. The Hidden Signal**

Interviewers ask why state appears frozen to probe whether you understand JavaScript execution mechanics. A junior candidate often assumes React relies on mysterious asynchronous timing tricks. A senior engineer explains that a component run is an ordinary JavaScript function call. State is a local constant primitive in that call frame.

**2. The Classic Trap**

The most common wrong answer is: "State is frozen because `setState` is asynchronous." That statement misses the core JavaScript reality. Even if React re-rendered synchronously in zero nanoseconds, calling a setter cannot change a constant in a running function. The frozen value is a consequence of JavaScript scope, not a timing delay.

**3. What is Actually Going On**

In React, rendering takes a snapshot of the interface in time. When React calls a component, `useState` returns the state for that run as a constant. Calling a setter does not mutate that local variable. It queues the next state value in React and requests a new render. Because the current function is still executing, every line in that run sees the starting value. When code in the handler needs the new value immediately, compute it once in a local variable.

**4. Where It Gets Tricky**

*What happens if the click handler uses async and await?*

Even after an `await`, the resumed function still reads the snapshot from the render that created it. The closure keeps that value intact, even if another click already updated the screen.

*Why is frozen state a feature rather than a bug?*

Snapshots protect delayed code from timing race conditions. If a reader clicks Send to Alice and quickly selects Bob, the delayed network request still sends to Alice.

*How do you read the latest value in delayed code if you truly need it?*

When an operation genuinely requires the latest value across renders, store that value in a React ref. Lecture 29 covers `useRef` for mutable values that persist across renders without triggering updates.

### Glossary

- **Snapshot**: The fixed value of state that React provides to a component for one specific render.
- **Closure**: A JavaScript function that remembers and accesses variables from the outer scope where it was created.
- **Setter Function**: A function returned by `useState` that stores the next state value in React and requests a new render.
- **`setTimeout`**: A standard browser function that waits a specified duration in milliseconds before running a callback function.
- **Substitution Method**: A mental technique where you replace state variables with concrete values to predict how event handlers execute.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ State Mutability vs Snapshots

➔ ALWAYS treat state variables as read-only constants for the duration of the current render.

➔ NEVER expect a setter call to change the value of a local variable in running code.

**DO THIS:** compute the next value once in a local variable before setting and sending

```jsx right
const nextRating = 5;
setRating(nextRating);
sendRating(nextRating);
```

**DO NOT DO THIS:** read the state variable directly after calling its setter

```jsx wrong
setRating(5);
sendRating(rating);
```

❒ Delayed Handlers & Timing Safety

➔ ALWAYS remember that event handlers capture the state snapshot from the render that created them.

➔ IF you need repeated updates in one event THEN use updater functions as taught in Lecture 17.

| | **PLAIN JAVASCRIPT**<br>(Mutable Variable) | **REACT STATE**<br>(Render Snapshot) |
| ---: | :--- | :--- |
| **Variable mutability** | Mutates in memory on every assignment | Stays fixed as a constant for the whole render |
| **Line after setter** | Reads the newly assigned value immediately | Reads the value from the current render snapshot |
| **Consecutive updates** | Multiple operations accumulate sequentially in memory | All calls in one handler evaluate the same snapshot |
| **Delayed callbacks** | Reads whatever latest value exists when timer fires | Captures the state snapshot of the render that created it |
