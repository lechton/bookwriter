### The Imperative Toggle and the Zero Trap

- [p] ◇ In traditional DOM scripting, developers show or hide elements imperatively by querying nodes and modifying their styles: `element.classList.toggle('hidden')`. In React, the UI is a direct projection of data. Trying to imperatively toggle DOM visibility creates a split brain where the physical DOM disagrees with React's virtual tree. Instead, React handles conditional rendering declaratively: you decide which JSX to return based on props and conditions. ◼ Educational objective: establish the declarative foundation of conditional rendering versus imperative DOM manipulation.
- [p] ★ {preknowledge: JavaScript truthiness, short-circuit evaluation, JSX expressions} {bridging: developers assume logical AND short-circuits to nothing on all falsy values, but React renders numbers} When developers use the logical AND (`&&`) operator with numeric counts, a notorious bug occurs. Look at the naive attempt: ◼ Educational objective: demonstrate the common zero-rendering bug with logical AND.
- [code] Naive Conditional Rendering:
```jsx title="Naive Conditional Rendering and the Zero Trap"
export default function ArticleHeader({ commentsCount }) {
  return (
    <header className="article-header">
      {commentsCount && <span>{commentsCount}</span>}
      <button onClick={() => document.getElementById('pw')}>
        Unlock
      </button>
    </header>
  );
}
```
◼ **The what-this-introduces list:** 1. `commentsCount && <span>`: the zero-rendering trap. 2. `document.getElementById`: imperative DOM manipulation violating declarative UI. 3. Desynchronized UI state.
- [p] ★ {preknowledge: falsy values, type coercion, JavaScript expressions} {bridging: React ignores false, null, and undefined, but numbers like 0 are valid renderable content} When `commentsCount` is `0`, JavaScript evaluates the expression `0 && <span ...>`. In JavaScript, the `&&` operator evaluates the left-hand operand; if it is falsy, it returns that operand immediately. Thus, the expression evaluates to `0`! React treats `false`, `null`, and `undefined` as empty slots, rendering nothing. But `0` is a valid number; React cannot know whether `0` is a counter or a boolean guard, so it renders a literal `0` into the DOM! To fix this, you must explicitly convert the condition to a boolean: `commentsCount > 0 && ...` or `Boolean(commentsCount) && ...`. ◼ Educational objective: deconstruct the JavaScript evaluation of 0 && JSX and how to prevent it.
- [figure] ```html-figure src="figures/10-00-conditional-rendering-branching.html" caption="Conditional rendering: early return, inline ternary, and avoiding the falsy zero trap."```
- [grounding] [!WILD] **Why does React render 0 but ignores false, null, and undefined?** Many developers wonder why React renders `0` while ignoring other falsy values. In JavaScript, `false`, `null`, and `undefined` carry no visual meaning; they represent absence. React purposely ignores them so you can write `{condition && <Element />}` without rendering unwanted strings. However, numbers like `0` are frequently legitimate content to display—such as displaying "You have 0 unread messages" or "Score: 0". If React automatically hid `0`, displaying numeric counters would be impossible. React treats numbers as text nodes. Therefore, you must ensure the left-hand side of an `&&` expression is always a genuine boolean.
- [callout] > [!TIP]
> **To impress the interviewer:** When asked how conditional rendering works in React, state that React has no special template directives like `v-if` or `*ngIf`. Instead, React relies purely on standard JavaScript control flow: `if` statements for early returns, the ternary operator `? :` for dual branches, and logical `&&` for single branches. Always mention the `0 && <Component />` trap and explain that you guard it with `count > 0` or `Boolean(count)`.

### Principles of React: The Core Laws of Conditional Rendering

- [p] ◇ To prepare for senior technical interviews, we must separate imperative DOM manipulation habits from React's declarative architecture and establish the five fundamental laws governing how components branch, switch, and render markup conditionally. In React, conditional rendering is not handled by magic compiler directives; it is governed by pure JavaScript control flow and immutable projection. We formalize these rules into five standalone principles. ◼ Educational objective: establish the necessity of principled conditional rendering for senior interviews.
- [principle] Principle 1: Branch Declaratively with JavaScript Control Flow Over Imperative DOM Queries
> [!PRINCIPLE]
> **Principle 1: Branch Declaratively with JavaScript Control Flow Over Imperative DOM Queries**
> You must branch UI declaratively using standard JavaScript expressions (`if`, `? :`, `&&`) inside your component, strictly avoiding imperative DOM manipulation or class toggling.
> 
> >> declarative branching : describing UI outcomes as pure functions of incoming state and props
> >> imperative DOM manipulation : querying nodes with document.getElementById and modifying classList directly
> 
> *It is best practice to do this:*
> `export default function Header({ isLive }) {`
> `  return (`
> `    <header>`
> `      {isLive && <span>LIVE</span>}`
> `    </header>`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function showLive() {`
> `  const el = document.getElementById('live');`
> `  el.classList.add('visible');`
> `}`
- [p] ★ {preknowledge: virtual DOM reconciliation, state synchronization} {bridging: imperative class toggles bypass React's virtual DOM, causing desynchronization} In React, the virtual DOM is the single source of truth. Imperatively adding or removing DOM classes creates state drift where the screen diverges from React's internal model. Declarative branching guarantees that the rendered output always matches current data. ◼ Educational objective: deconstruct Principle 1.
- [principle] Principle 2: Return null Early to Guard Against Missing Data
> [!PRINCIPLE]
> **Principle 2: Return null Early to Guard Against Missing Data**
> You must return **`null`** early from a component function when required props or data are missing, preventing runtime errors and unmounting the component from the DOM.
> 
> >> early return with null : exiting the component before main JSX when preconditions fail
> >> null rendering : React instruction that renders nothing to the DOM without throwing errors
> 
> *It is best practice to do this:*
> `export default function Header({ story }) {`
> `  if (!story) return null;`
> `  return <h1>{story.title}</h1>;`
> `}`
> 
> *Instead of doing this:*
> `export default function Header({ story }) {`
> `  // Crashes if story is undefined`
> `  return <h1>{story.title}</h1>;`
> `}`
- [p] ★ {preknowledge: function returns, property access on null, defensive programming} {bridging: early returns protect downstream destructuring and prevent deeply nested conditions} Returning `null` early acts as a defensive guard. It prevents fatal exceptions like `Cannot read properties of undefined` and keeps the main return statement clean and readable. ◼ Educational objective: deconstruct Principle 2.
- [principle] Principle 3: Use Inline Ternary Operators for Binary Mutual Exclusions
> [!PRINCIPLE]
> **Principle 3: Use Inline Ternary Operators for Binary Mutual Exclusions**
> You must use the ternary operator (`condition ? <BranchA /> : <BranchB />`) when choosing between two mutually exclusive visual states inside JSX.
> 
> >> inline ternary operator : JavaScript ? : expression evaluating to one of two JSX descriptors
> >> mutually exclusive states : dual UI branches where exactly one must be rendered at any time
> 
> *It is best practice to do this:*
> `return (`
> `  <div>`
> `    {isAuth ? <Dashboard /> : <Login />}`
> `  </div>`
> `);`
> 
> *Instead of doing this:*
> `return (`
> `  <div>`
> `    {isAuth && <Dashboard />}`
> `    {!isAuth && <Login />}`
> `  </div>`
> `);`
- [p] ★ {preknowledge: ternary expressions, boolean logic} {bridging: separate logical ANDs duplicate condition checks and risk rendering collisions} Using dual `&&` checks requires evaluating the condition twice and introduces subtle bugs if conditions overlap. A ternary guarantees that exactly one branch executes. ◼ Educational objective: deconstruct Principle 3.
- [principle] Principle 4: Enforce Explicit Boolean Guards with Logical AND to Prevent the Falsy Zero Trap
> [!PRINCIPLE]
> **Principle 4: Enforce Explicit Boolean Guards with Logical AND to Prevent the Falsy Zero Trap**
> You must always ensure the left side of a logical `&&` operator evaluates to a **strict boolean** (`count > 0` or `Boolean(count)`), never a raw number.
> 
> >> falsy zero trap : JavaScript 0 && <JSX> evaluating to 0, which React renders as visible text
> >> explicit boolean guard : converting numeric expressions to boolean truth via comparison or Boolean()
> 
> *It is best practice to do this:*
> `return (`
> `  <div>`
> `    {count > 0 && <span>{count}</span>}`
> `  </div>`
> `);`
> 
> *Instead of doing this:*
> `return (`
> `  <div>`
> `    {count && <span>{count}</span>}`
> `  </div>`
> `);`
- [p] ★ {preknowledge: JavaScript truthiness, short-circuit evaluation, text nodes} {bridging: React hides booleans and null but renders numbers, causing stray zeros to appear on screen} In JavaScript, `0 && <Component />` returns `0`. Because React treats numbers as legitimate printable content, it renders a literal "0" text node into the DOM. Guarding with `count > 0` ensures the expression evaluates to `false`, which React ignores cleanly. ◼ Educational objective: deconstruct Principle 4.
- [principle] Principle 5: Assign JSX to Variables Outside Returns for Multi-Branch Complexity
> [!PRINCIPLE]
> **Principle 5: Assign JSX to Variables Outside Returns for Multi-Branch Complexity**
> You must assign JSX to a local variable using standard `if/else` statements before the return when conditional logic exceeds two branches, avoiding nested unreadable ternaries.
> 
> >> variable assignment in JSX : storing JSX element trees in local let variables before return
> >> nested ternary anti-pattern : chaining multiple ? : inside JSX, obscuring control flow
> 
> *It is best practice to do this:*
> `let content;`
> `if (loading) content = <Spinner />;`
> `else if (error) content = <ErrorNotice />;`
> `else content = <ArticleFeed />;`
> `return <main>{content}</main>;`
> 
> *Instead of doing this:*
> `return (`
> `  <main>`
> `    {loading ? <Spinner /> :`
> `      error ? (`
> `        <ErrorNotice />`
> `      ) : (`
> `        <Feed />`
> `      )}`
> `  </main>`
> `);`
- [p] ★ {preknowledge: nested ternaries, code maintainability} {bridging: complex nested ternaries degrade code readability and complicate debugging} Chaining multiple ternary operators inside JSX creates visual noise and makes reading control flow difficult. Extracting multi-branch logic into standard JavaScript `if/else` statements outside the return keeps the JSX markup clean, flat, and maintainable. ◼ Educational objective: deconstruct Principle 5.
