### The Purity Contract and the StrictMode Double-Render

- [p] ◇ In computer science, a pure function is a mathematical formula: given the same inputs, it always returns the exact same result, and it changes nothing outside of its own function body. React is designed entirely around this concept. Every React component you write must be a pure function. When React calls your component, the component should only calculate and return JSX describing what the screen should look like. It must never reach outside its own boundaries to mutate pre-existing variables, modify incoming props, or trigger side effects during the render pass. ◼ Educational objective: establish the foundational definition of component purity and mathematical formulas.
- [p] ★ {preknowledge: JavaScript functions, variable scope, mutation} {bridging: developers assume components render exactly once per update, but React re-runs renders freely} When developers violate the purity contract by mutating external variables, silent bugs explode across their application. Look at the naive attempt below, where an engineer increments a global counter inside the component body: ◼ Educational objective: demonstrate the common impure external mutation bug.
- [code] Naive Impure Component:
```jsx title="Naive Impure Component and External Mutation"
let guestViewCount = 0; // **DANGER:** shared external variable outside **COMPONENT**

export default function StoryByline({ author }) {
  guestViewCount = guestViewCount + 1; // **WRONG:** mutates external state during **RENDER**
  return (
    <div className="byline">
      <span>By {author}</span>
      <small>Views: {guestViewCount}</small>
    </div>
  );
}
```
◼ **The what-this-introduces list:** 1. `let guestViewCount = 0`: external variable living in module scope. 2. `guestViewCount + 1`: illegal mutation inside render body. 3. Violation of component isolation.
- [p] ★ {preknowledge: StrictMode, concurrent rendering, idempotence} {bridging: React intentionally renders twice in development to uncover impure mutations before production} In development, React wraps your application in `<StrictMode>`. One of StrictMode's primary duties is to verify component purity by calling every component function twice! For a pure component, running the function twice produces the exact same JSX with zero side effects. But for our impure `StoryByline`, running the function twice increments `guestViewCount` from 0 to 1, and then immediately from 1 to 2. The counter doubles on every single page load! In production, concurrent rendering, server component streaming, and background pre-rendering can pause, abort, and restart rendering at any moment. If your component is not pure, these pauses and restarts corrupt application data. ◼ Educational objective: deconstruct why StrictMode double-renders in development and how concurrent rendering relies on idempotence.
- [figure] ```html-figure src="figures/13-00-purity-contract-mutation-trap.html" caption="The Purity Contract: contrasting impure external mutations against pure mathematical functions."```
- [grounding] [!WILD] **Why does StrictMode render your component twice?** When developers first see `console.log()` or counters firing twice in development, they often assume React has a bug. In reality, React's `<StrictMode>` intentionally calls your component functions, initializers, and reducers twice in development. Why? Because React is testing your code for purity! If a component is pure, calling it twice produces no observable side effects; the output is identical. But if a component mutates an external variable or modifies a prop array, the second run produces different results, exposing the bug immediately in development before it causes corrupted state in production.

> **To impress the interviewer:** When asked what component purity means, state that React components must be **idempotent**: given the same inputs (props, state, and context), they must always return the exact same JSX, producing zero mutations outside their render phase. Emphasize that StrictMode double-rendering exists specifically to detect side effects during the render phase, and explain that side effects belong exclusively in event handlers or lifecycle effects.

### Side Effects, Idempotence, and Local Mutation

- [p] ◇ To maintain purity, developers must understand what is forbidden and what is permitted. Mutating pre-existing variables, modifying incoming props, or directly changing the DOM during render is strictly forbidden. However, **local mutation** is 100% legal: you can freely create new variables, arrays, and objects inside the component function and mutate them as much as you want before returning JSX. ◼ Educational objective: define the boundary between illegal cross-boundary mutation and safe local mutation.
- [p] ★ {preknowledge: array mutation methods, array spreading, immutability} {bridging: developers often mutate prop arrays in place using push or sort, corrupting parent state} When preparing or sorting data for display, developers face an architectural crossroad between in-place array mutation and pure array derivation: ◼ Educational objective: frame the crossroad between in-place array mutation and pure array derivation.
- [p] - **Option 1 (The foundational trap / mutation)**: Mutate the incoming prop array in place using mutating methods like `tags.push('Live')` or `tags.sort()`. ◼ Educational objective: declare Option 1 with concrete syntax tokens.
- [p] - **Option 2 (The modern idiomatic way / pure derivation)**: Create a new array or shallow copy using the spread operator `[...tags, 'Live']` or non-mutating methods before rendering. ◼ Educational objective: declare Option 2 with concrete syntax tokens.
- [p] First, examine Option 1 with illegal prop mutation: ◼ Educational objective: transition to Option 1 code.
- [code] Option 1:
```jsx title="Option 1: The Foundational Trap (In-Place Prop Mutation)"
export default function TagList({ tags }) {
  tags.push('Breaking'); // **WRONG:** mutates incoming **PROP ARRAY**
  tags.sort();           // **WRONG:** sorts parent array in **PLACE**
  return <div className="tags">{tags.join(', ')}</div>;
}
```
◼ **The what-this-introduces list:** 1. `tags.push(...)`: mutating incoming prop array. 2. `tags.sort()`: in-place sort modifying parent memory. 3. Corrupting shared data across sibling components.
- [p] ★ In Option 1, `tags.push('Breaking')` mutates the array owned by the parent component. Every time `TagList` renders, a new 'Breaking' item is pushed into the parent's array! Furthermore, any sibling component reading `tags` sees this mutated data, creating bizarre data corruption across the application. ◼ Educational objective: analyze the disastrous consequences of in-place prop mutation.
- [p] Next, examine Option 2 with pure array derivation: ◼ Educational objective: transition to Option 2 code.
- [code] Option 2:
```jsx title="Option 2: The Modern Idiomatic Way (Pure Array Derivation)"
export default function TagList({ tags }) {
  const displayTags = [...tags, 'Breaking']; // Creates local copy via **SPREAD OPERATOR**
  displayTags.sort(); // Safe: mutates only **LOCAL VARIABLE**
  return <div className="tags">{displayTags.join(', ')}</div>;
}
```
◼ **The what-this-introduces list:** 1. `const displayTags = [...tags, 'Breaking']`: non-mutating copy using array spread. 2. `displayTags.sort()`: safe local mutation on newly created object. 3. Zero parent state pollution.
- [p] ★ In Option 2, the component creates a new array `displayTags` using the spread operator. Mutating `displayTags` is completely safe because it was created during the current render pass; no other component in the application has a reference to it. The parent's original `tags` array remains 100% pure and untouched. ◼ Educational objective: demonstrate safe local mutation using array copies.
- [callout] > [!KEY]
> The golden rule of purity: **never mutate objects or variables that existed before the render started**. Render logic must act as a read-only calculation.

- [p] Now we construct `src/components/TagList.jsx`. This component demonstrates safe local mutation: it creates a shallow copy of the incoming `tags` array using the spread operator, adds a verified status badge, sorts the tags alphabetically, and renders the result: ◼ Educational objective: construct TagList demonstrating safe local mutation on copied arrays.
- [code] TagList.jsx:
```jsx title="src/components/TagList.jsx" startLine="1"
export default function TagList({ tags }) {
  const safeTags = [...tags, 'Verified']; // (1) Creates local copy via **SPREAD**
  safeTags.sort();                       // (2) Safe: mutates only **LOCAL ARRAY**
  return <div className="tag-container">
    {safeTags.map((tag) => (
      <span key={tag} className="tag-pill">{tag}</span> // (3) Renders sorted **TAG PILL**
    ))}
  </div>;
}
```
◼ **The what-this-introduces list:** 1. `const safeTags = [...tags, 'Verified']`: creating a shallow copy via spread. 2. `safeTags.sort()`: mutating newly created local array safely. 3. Clean, pure component return.
- [p] Notice lines 2 and 3: `safeTags` is a brand-new array created inside `TagList`. Calling `safeTags.sort()` mutates `safeTags`, but this mutation is completely local. The parent component's `tags` array remains pristine and untouched. This is the definition of safe local mutation! ◼ Educational objective: reinforce the difference between illegal prop mutation and safe local mutation.

### Glossary

- [glossary] Pure Component ◼ A component that behaves as a mathematical function: given the same inputs, it always returns the same JSX without side effects.
- [glossary] Idempotence ◼ The property of an operation where executing it multiple times produces the exact same result as executing it once.
- [glossary] Side Effect ◼ Any observable change outside the current function execution, such as mutating global variables, timers, or DOM mutations.
- [glossary] Render Phase ◼ The phase where React executes component functions to calculate the new JSX descriptor tree; must be 100% pure.
- [glossary] Local Mutation ◼ Mutating objects, arrays, or variables that were freshly created inside the component body during the current render pass.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ The Purity Contract

➔ ALWAYS write components as pure mathematical functions: identical inputs must return identical JSX.

➔ NEVER mutate variables, arrays, or objects that existed before the component render started.

➔ NEVER perform side effects (such as network requests, DOM mutations, or timers) inside the component render body.

❒ Safe Local Mutation & Arrays

➔ ALWAYS create shallow copies of arrays (`[...tags]`) or objects before sorting, pushing, or mutating them.

➔ IF you need to perform side effects THEN quarantine them strictly inside event handlers or lifecycle effects.

➔ IF a component behaves unpredictably in StrictMode THEN search immediately for render-phase mutations.

**DO THIS:** derive data purely by creating local copies before mutating

```jsx right
export default function TagList({ tags }) {
  const sortedTags = [...tags].sort();
  return <div>{sortedTags.join(', ')}</div>;
}
```

**DO NOT DO THIS:** mutate incoming prop arrays directly in place

```jsx wrong
export default function TagList({ tags }) {
  tags.sort();
  return <div>{tags.join(', ')}</div>;
}
```

| | **PURE COMPONENT**<br>(Mathematical Function) | **IMPURE COMPONENT**<br>(Side Effects & Mutation) |
| ---: | :--- | :--- |
| **Formula** | `y = f(x)`: predictable, idempotent | Unpredictable, dependent on outside time/state |
| **External Memory** | Zero reads or mutations outside render | Mutates module variables or global state |
| **Prop Handling** | Treats props as strictly read-only | Mutates incoming prop arrays or objects in place |
| **StrictMode Dev** | Renders twice with zero bugs or drift | Counter doubles; arrays accumulate duplicate items |
| **Concurrent Safe** | React can safely pause, abort, and restart | Paused renders corrupt application state permanently |
