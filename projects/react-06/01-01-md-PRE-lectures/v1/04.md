### Permissive Browsers vs Strict Compilers

- [p] ◇ In plain HTML, web browsers are remarkably forgiving. Browsers allow unclosed void tags like `<img>` or `<input>`. Browsers also permit multiple adjacent elements at the top level of a file. If you paste raw HTML markup into a standard `.html` file, the browser engine parses the text and paints the page. ◼ Educational objective: establish the forgiving baseline of plain HTML before introducing the strict grammar of JSX.
- [p] ★ {preknowledge: HTML elements, JavaScript functions, return statements} {bridging: developers assume they can paste HTML directly into React components, but JSX is strict JavaScript syntax that enforces rigorous compiler rules} When a developer pastes raw HTML into a React component function, the build tool halts immediately with fatal syntax errors. Look at the naive HTML paste attempt: ◼ Educational objective: demonstrate the syntax crashes caused by pasting raw HTML into a component.
- [code] Naive Markup Paste:
```jsx title="Naive Markup Paste"
// **WRONG:** Raw HTML pasted into JavaScript return statement
return (
  <img src="/wire-photo.jpg">
  <h2>Breaking Dispatch</h2>
  <p class="alert-text">Live news feed.</p>
);
```
◼ **The what-this-introduces list:** 1. Unclosed `<img>`: missing self-closing slash. 2. Adjacent siblings: multiple top-level elements inside a single return. 3. `class` attribute: JavaScript reserved word collision. 4. Compiler crash: syntax errors preventing bundle generation.
- [p] ★ {preknowledge: JavaScript return syntax, function arguments, compiler transforms} {bridging: the failure occurs because JSX is not HTML; it is a syntax extension for JavaScript that compiles to function calls} The compiler crashes because a JavaScript function cannot return multiple values. Writing `return a, b` evaluates both but returns only the second value. Furthermore, JSX compiles into `_jsx()` function calls. Every `_jsx()` call represents a single element descriptor. You cannot pass two separate expressions to a single `return` statement without a wrapping structure. ◼ Educational objective: deconstruct why JavaScript functions cannot return adjacent sibling expressions.
- [callout] > [!TIP]
> **To impress the interviewer:** When asked to explain JSX, do not call it "HTML inside JavaScript." State that JSX is a strict syntax extension that compiles into regular JavaScript function calls (`_jsx()`). Because functions can only return a single value, every JSX snippet requires a single root element.

#### Principles of React: The Core Laws of JSX Grammar

- [p] ◇ To prepare for any technical interview, we must separate theory from application and establish the nine fundamental laws governing the React compiler. In JSX, HTML markup strings do not exist. Every tag, attribute, inline style, and comment is transformed into JavaScript function calls and plain JavaScript objects. We formalize these rules into nine standalone principles. ◼ Educational objective: establish the autonomous theoretical foundation of JSX grammar before embarking on the case study.
- [principle-1] > [!PRINCIPLE]
> **Principle 1: Single Root Invariant**
> Every JSX component return statement must produce exactly one root element or container.
> 
> *Example:* `return (<div><img /><h2 /></div>)` (or `return (<><img /><h2 /></>)`), never `return (<img /><h2 />);`.
- [p] ★ Under the hood, JSX compiles into `_jsx()` calls. A component is a JavaScript function, and a function return statement accepts only a single expression. Writing adjacent elements at the root level produces a syntax error because JavaScript cannot return two values simultaneously. ◼ Educational objective: explain Principle 1 and its underlying ECMAScript function return constraint.
- [code] Single Root Minimal Contrast:
```jsx title="Principle 1: Single Root Invariant"
// **WRONG:** Adjacent elements violate single return
return (<img src="/a.jpg" alt="A" /><h2>Alert</h2>);

// **RIGHT:** Single root container wraps children
return (<div><img src="/a.jpg" alt="A" /><h2>Alert</h2></div>);
```
◼ **The what-this-introduces list:** 1. Adjacent elements: syntax failure. 2. Wrapped single root: valid JavaScript expression.
- [principle-2] > [!PRINCIPLE]
> **Principle 2: Zero-DOM Fragmentation**
> Adjacent sibling elements must be grouped with a React Fragment (`<>...</>`) to satisfy the single root invariant without injecting wrapper nodes into the DOM.
> 
> *Example:* `return (<><img /><h2 /></>);` mounts siblings directly into the parent with zero wrapper nodes.
- [p] ★ Wrapping elements in an extra `<div>` satisfies the compiler but pollutes the browser DOM tree, bloats memory, and destroys CSS Flexbox and Grid parent-child projections. A React Fragment (`<>...</>`) compiles to `_jsx(Fragment, { children: [...] })`. React evaluates the children in memory but commits zero wrapper nodes to the DOM. ◼ Educational objective: explain Principle 2 and contrast physical DOM containers against containerless React Fragments.
- [code] Fragment Minimal Contrast:
```jsx title="Principle 2: Zero-DOM Fragmentation"
// Compiles to _jsx(Fragment, { children: [...] })
// Mounts children directly into parent with zero DOM nodes:
return (
  <>
    <img src="/a.jpg" alt="Alert" />
    <h2>Alert</h2>
  </>
);
```
◼ **The what-this-introduces list:** 1. `<>`: opening Fragment tag. 2. `</>`: closing Fragment tag. 3. Zero DOM container: siblings mount directly into host container.
- [figure] ```html-figure src="figures/04-00-jsx-root-and-fragments.html" caption="DOM wrapper divs pollute the DOM and break layouts, while React Fragments group siblings with zero DOM overhead."```
- [grounding] [!WILD] **Why does a wrapper div break your CSS Flexbox layout?** When developers hit the single-root error, their instinctive reflex is wrapping everything in a `<div>`. While this satisfies the compiler, it often destroys layout styling. In CSS Flexbox and Grid, layout properties apply exclusively to direct child elements. If a parent container declares `display: flex; gap: 16px;`, its direct children become flex items. Placing an extra `<div>` wrapper around your siblings turns those elements into grandchildren. The flex container now sees only one child: the wrapper div. Your flex row layout collapses into a single vertical block, and gap spacing between items vanishes. React Fragments solve this by satisfying the compiler without creating a physical DOM wrapper.
- [principle-3] > [!PRINCIPLE]
> **Principle 3: Strict Tag Termination**
> Every JSX tag must be **explicitly terminated**—using a matching closing tag or a self-closing trailing slash.
> 
> *Do This:*
> `<img src="/photo.jpg" alt="Photo" />` and `<input type="text" />`
> 
> *Do Not Do This:*
> `<img>` or `<input>`
- [p] ★ In HTML5, void elements such as `<img>`, `<input>`, `<br>`, and `<hr>` are permitted without closing slashes. JSX, by contrast, adheres to strict XML grammar. The compiler parser builds an Abstract Syntax Tree (AST); every opening tag delimiter must have an unambiguous closing delimiter (`<img />`, `<input />`) or the build halts. ◼ Educational objective: explain Principle 3 and XML strictness for void tags.
- [code] Self-Closing Void Tag Minimal Example:
```jsx title="Principle 3: Explicit Tag Closing"
// **WRONG:** Unclosed void tags crash compiler
<input type="text">
<img src="/photo.jpg">

// **RIGHT:** Explicit self-closing slashes
<input type="text" />
<img src="/photo.jpg" alt="Photo" />
```
◼ **The what-this-introduces list:** 1. Unclosed void tag: syntax crash. 2. Self-closing trailing slash: XML AST parser compliance.
- [principle-4] > [!PRINCIPLE]
> **Principle 4: DOM Property Alignment for Reserved Words**
> HTML attribute names that collide with JavaScript reserved keywords must be written using their corresponding **native browser DOM property names**.
> 
> *Do This:*
> `<div className="card">` and `<label htmlFor="email">`
> 
> *Do Not Do This:*
> `<div class="card">` or `<label for="email">`
- [p] ★ To understand this rule, distinguish between three web layers: HTML attributes (plain text markup strings), JavaScript reserved keywords (`class` and `for` tokens), and browser DOM properties (`element.className` and `element.htmlFor` on living object instances). React compiles JSX to JavaScript objects that directly set native DOM properties. ◼ Educational objective: explain Principle 4 across HTML attributes, ECMAScript keywords, and W3C DOM properties.
- [principle-5] > [!PRINCIPLE]
> **Principle 5: Standard camelCase for Compound Attributes**
> All multi-word JSX attribute names must be written in **camelCase** to align with their native browser DOM property interfaces.
> 
> *Do This:*
> `<input tabIndex={1} readOnly={true} />`
> 
> *Do Not Do This:*
> `<input tabindex="1" readonly>`
- [p] ★ In HTML, attributes are case-insensitive strings (`tabindex`, `readonly`). In the browser's native DOM API, the `HTMLInputElement` interface defines these properties in camelCase (`input.tabIndex`, `input.readOnly`). React aligns 1:1 with native W3C DOM interface properties. ◼ Educational objective: explain Principle 5 and W3C DOM property alignment for compound attributes.
- [principle-6] > [!PRINCIPLE]
> **Principle 6: Object Literals for Inline Styles**
> Inline element styles must be passed as **JavaScript objects with camelCase CSS property keys**, never as raw semicolon-delimited text strings.
> 
> *Do This:*
> `<span style={{ color: 'red', fontWeight: 700 }}>`
> 
> *Do Not Do This:*
> `<span style="color: red; font-weight: bold;">`
- [p] ★ In JSX, the outer `{}` switches into JavaScript expression mode, while the inner `{}` is a plain object literal. In the browser DOM, `element.style` is an instance of `CSSStyleDeclaration`. Because `element.style.font-weight` is parsed as subtraction in JavaScript, the DOM API uses camelCase (`element.style.fontWeight`). React's `style` prop passes this object directly to native `element.style`. ◼ Educational objective: explain Principle 6, the double-brace syntax, and CSSStyleDeclaration mapping.
- [principle-7] > [!PRINCIPLE]
> **Principle 7: JavaScript Expression Blocks for Markup Comments**
> Comments inside JSX markup must be written as **JavaScript block comments enclosed within curly brace expression delimiters**.
> 
> *Do This:*
> `{/* breaking news alert */}`
> 
> *Do Not Do This:*
> `<!-- breaking news alert -->`
- [p] ★ The JSX compiler operates as a two-state tokenizer: Markup Mode and JavaScript Mode. In Markup Mode, `<` initiates element parsing, causing `<!--` to parse as an illegal tag identifier `!--`. Curly braces `{}` explicitly switch the tokenizer into JavaScript Mode, where `/* ... */` is evaluated as an ECMAScript block comment and erased during compilation. ◼ Educational objective: explain Principle 7 and the compiler tokenizer state machine.
- [principle-8] > [!PRINCIPLE]
> **Principle 8: Hyphenated Preservation for W3C Standards**
> Accessibility attributes (`aria-*`) and custom dataset attributes (`data-*`) must strictly **retain their hyphenated kebab-case syntax**.
> 
> *Do This:*
> `<input aria-label="Search" data-testid="search-input" />`
> 
> *Do Not Do This:*
> `<input ariaLabel="Search" dataTestId="search-input" />`
- [p] ★ Standard props update the DOM via property assignment (`node.className = ...`), but the DOM does not define properties like `node.ariaLabel`. Screen readers and CSS selectors inspect the serialized HTML attribute string. Therefore, React calls `node.setAttribute('aria-label', ...)` and `node.setAttribute('data-testid', ...)`, requiring exact W3C hyphenated names. ◼ Educational objective: contrast DOM property assignment against DOM attribute assignment (`setAttribute`) for Principle 8.

```javascript title="Transpiled JavaScript Object Output"
  className: "field-label",

  ]

```
- [principle-9] > [!PRINCIPLE]
> **Principle 9: Tag Casing Dictates Compilation Target**
> **Lowercase tag names** instruct the compiler to create native browser DOM elements, while **capitalized tag names** instruct the compiler to invoke custom component functions.
> 
> *Do This:*
> `<header>` (native DOM node) and `<NewsAlert />` (custom component function call)
> 
> *Do Not Do This:*
> `<newsAlert />` (compiles to `_jsx("newsalert")`, failing to invoke the component function)
- [p] ★ In the AST lexical tokenizer, tags matching `/^[a-z]/` emit string literals (`_jsx("header", ...)`), passed to `document.createElement()`. Tags matching `/^[A-Z]/` emit direct variable identifiers (`_jsx(NewsAlert, ...)`), invoking the component function. Lowercase custom tags `<newsAlert />` produce unknown HTML elements `<newsalert>`, rendering nothing. ◼ Educational objective: explain Principle 9 and the AST lexical tokenizer regex rules.
- [table] Tag Casing Compilation Matrix:
| **JSX TAG**<br>(markup syntax) | **TRANSPILED OUTPUT**<br>(compiler emit) | **BROWSER RUNTIME TARGET**<br>(execution reality) | **INTERVIEW DISTINCTION**<br>(core rule) |
| :--- | :--- | :--- | :--- |
| `<header>` | `_jsx("header", props)` | Native Browser DOM | Lowercase string creates built-in HTML element |
| `<NewsAlert>` | `_jsx(NewsAlert, props)` | React Component Function | Capitalized identifier invokes JavaScript function |
- [code] Tag Casing Semantics Minimal Example:
```jsx title="Principle 9: Tag Casing Semantics"

// Transpiles to: _jsx("div", { className: "alert-box" })

// Capitalized: emits identifier NewsAlert to execute function
const customComponent = <NewsAlert priority="urgent" />;
// Transpiles to: _jsx(NewsAlert, { priority: "urgent" })
```
◼ **The what-this-introduces list:** 1. Lowercase `<tag>`: emits native DOM string. 2. Capitalized `<Tag>`: emits component function reference.

### Glossary

- [glossary] JSX ◼ A syntax extension for JavaScript that allows developers to write XML-like markup that compiles into standard `_jsx()` function calls.
- [glossary] React Fragment ◼ A built-in React component (`<>...</>`) that groups a list of children without adding extra nodes to the physical browser DOM.
- [glossary] Single Root Invariant ◼ The compiler requirement that every component return statement must resolve to a single JavaScript expression.
- [glossary] Self-Closing Tag ◼ A tag that closes itself with a trailing slash (`<img />`, `<input />`), mandatory in JSX for void HTML elements that have no children.
- [glossary] DOM Property Mapping ◼ The convention where JSX attributes match browser DOM object properties (such as `className` and `htmlFor`) to avoid collisions with JavaScript reserved words.
- [glossary] Tag Casing Rule ◼ The compiler convention where lowercase tags denote browser DOM strings and capitalized tags denote in-scope component functions.

## Beyond the basics

- **JSX compilation under the hood**: The JSX transform turns `<><h1>Hello</h1></>` into `_jsx(Fragment, { children: _jsx("h1", { children: "Hello" }) })` using the React Fragment symbol (see [react.dev/learn/writing-markup-with-jsx](https://react.dev/learn/writing-markup-with-jsx)).
- **Fragments with keys in mapped collections**: While the shorthand `<>...</>` syntax does not accept attributes, the explicit `<React.Fragment key={id}>` syntax allows passing keys when rendering lists of fragments (see [react.dev/learn/rendering-lists](https://react.dev/learn/rendering-lists)).
- **DOM property mapping**: JSX attributes closely match browser DOM properties rather than HTML attribute strings; for example, `class` becomes `className` and `for` becomes `htmlFor` (see [react.dev/learn/writing-markup-with-jsx](https://react.dev/learn/writing-markup-with-jsx)).
- **Single-expression returns in JavaScript**: A JavaScript `return` statement can only evaluate and return one value; wrapping multiple expressions in parentheses and a Fragment creates a single compound expression (see [react.dev/learn/writing-markup-with-jsx](https://react.dev/learn/writing-markup-with-jsx)).
- **Void elements and strict XML rules**: In HTML5, void elements like `<input>`, `<img>`, and `<br>` can omit closing slashes, but JSX strictly follows XML rules where all tags must be explicitly closed (see [react.dev/learn/writing-markup-with-jsx](https://react.dev/learn/writing-markup-with-jsx)).

**Architectural Takeaways & Decision Matrix**

❒ Single Root & Fragments

➔ ALWAYS wrap adjacent sibling elements in a React Fragment (`<>...</>`) to satisfy the single-return rule without adding DOM nodes.

➔ NEVER wrap sibling elements in an unnecessary `<div>` when they reside inside CSS Flexbox or Grid containers.

➔ IF returning multiple siblings without a wrapper THEN use `<>...</>` to prevent compiler syntax errors.

❒ Tag Closing, Attributes & Syntax

➔ ALWAYS close all JSX tags explicitly, including void elements like `<img />`, `<input />`, and `<br />`.

➔ ALWAYS use `className` instead of `class` and `htmlFor` instead of `for` when assigning styling and form bindings.

➔ ALWAYS pass inline styles as JavaScript objects with camelCase keys (`style={{ color: 'red' }}`) rather than CSS text strings.

➔ ALWAYS use JavaScript expression comment blocks (`{/* ... */}`) inside JSX instead of HTML comment delimiters.

➔ ALWAYS keep `aria-*` and `data-*` in hyphenated kebab-case syntax.

**DO THIS:** wrap sibling elements in a Fragment with self-closing tags, DOM properties, and style objects

```jsx right
export default function NewsAlert() {
  return (
    <>
      <img className="story-photo" src="/breaking.jpg" alt="Story photo" />
      <h2 className="alert-headline">Breaking Alert</h2>
      {/* Sibling form controls without wrapper */}
      <span className="live-badge" style={{ color: '#dc2626', fontWeight: 700 }}>LIVE</span>
      <label className="alert-label" htmlFor="alert-input">Subscribe:</label>
      <input id="alert-input" className="alert-input" tabIndex={1} aria-label="Subscribe" />
    </>
  );
}
```

**DO NOT DO THIS:** return adjacent elements, use unclosed tags, or paste HTML comments and string styles

```jsx wrong
export default function NewsAlert() {
  return (
    <img class="story-photo" src="/breaking.jpg">
    <h2>Breaking Alert</h2>
    <!-- HTML comment crashes parser -->
    <span style="color: red;">LIVE</span>
    <label for="alert-input">Subscribe:</label>
    <input id="alert-input" class="alert-input" tabindex="1">
  );
}
```

| | **PLAIN HTML**<br>(permissive markup) | **REACT JSX & FRAGMENT**<br>(strict javascript syntax) |
| ---: | :--- | :--- |
| **Sibling Roots** | Allows multiple top-level siblings | Strictly requires a single root or Fragment `<>...</>` |
| **Void Tag Closing** | Unclosed tags allowed (`<img>`, `<input>`) | Strictly requires self-closing slashes (`<img />`) |
| **Attribute Format** | Raw markup strings (`class`, `for`) | DOM properties (`className`, `htmlFor`) |
| **Inline Styles** | CSS text string (`style="color:`<br>`'red';"`) | JavaScript object (`style={{`<br>`color: 'red' }}`) |
| **Markup Comments** | HTML comment tags (`<!-- ... -->`) | JavaScript comment blocks (`{/* ... */}`) |
| **DOM Overhead** | Developers often add wrapper divs | Fragments render zero wrapper nodes to the DOM |
| **CSS Layout Impact** | Extra wrapper divs break flex/grid rows | Fragments preserve direct parent-child layouts |
