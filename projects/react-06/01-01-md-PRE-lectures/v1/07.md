### The Monolithic File and the Import Trap

- [p] ◇ In early project stages, developers often place multiple components in a single file for convenience. As an application grows, a monolithic `App.jsx` becomes an unmaintainable bottleneck. Five developers editing different widgets inside the same file generate endless merge conflicts. Furthermore, locating bugs in a 1,200-line script slows down the entire engineering team. To build scalable React applications, you must extract each component into its own dedicated ES module file. ◼ Educational objective: establish the necessity of component file splitting for team scalability and maintainability.
- [p] ★ {preknowledge: JavaScript functions, ES modules, JSX component definitions} {bridging: developers assume importing any export works with or without curly braces, but ES modules strictly separate default bindings from named properties} When splitting components into separate files, mistyping import syntax causes fatal runtime crashes. Look at the naive attempt: ◼ Educational objective: demonstrate runtime failure caused by wrapping a default export in curly braces.
- [code] Naive Import Mismatch:
```jsx title="Naive Import Mismatch"
import { ArticleCard } from './ArticleCard.jsx'; // **WRONG:** curly braces search named property on **DEFAULT EXPORT**

export default function App() {
  return <ArticleCard />; // **WRONG:** crashes with undefined element type **EXCEPTION**
}
```
◼ **The what-this-introduces list:** 1. `export default function ArticleCard`: module default export. 2. `import { ArticleCard }`: erroneous named import syntax on a default export. 3. `<ArticleCard />`: passing undefined to JSX element factory.
- [p] ★ {preknowledge: module namespace objects, JavaScript undefined, React element types} {bridging: React elements require valid string tags or functions, and an undefined import fails during React.createElement resolution} When a file exports a component using `export default`, the bundler places that function on the `.default` property of the module namespace object. If you write `import { ArticleCard } from './ArticleCard.jsx'`, the JavaScript engine looks for an export literally named `ArticleCard`. Because none exists, `ArticleCard` is assigned `undefined`. When React attempts to render `<ArticleCard />`, it invokes `_jsx(undefined, {})`. React throws a fatal runtime exception: `Error: Element type is invalid: expected a string or a class/function but got: undefined. You likely forgot to export your component or mixed up default and named imports.` ◼ Educational objective: deconstruct the underlying module namespace object mechanics and the resulting invalid element type error.
- [figure] ```html-figure src="figures/07-00-default-vs-named-exports.html" caption="The ES module namespace: default exports bind to .default, while named exports bind to exact identifier keys."```
- [grounding] [!WILD] **Why does an undefined component crash during rendering instead of import?** When developers mix up import syntax, they expect Vite or the browser to throw a syntax error immediately at the import statement. Why does the file load silently, only to explode when React renders? Because in JavaScript ES modules, importing a non-existent named export from a module is legally permitted at syntax level; it simply resolves to undefined. The failure only occurs when React's runtime attempts to evaluate `<ArticleCard />`. React inspects the first argument to `_jsx()` and finds `undefined` instead of a function or DOM string tag, halting with a fatal type error.
- [callout] > [!TIP]
> **To impress the interviewer:** When asked how default and named imports differ, explain that a default export binds to the module's internal `.default` property and is imported without curly braces, while named exports represent specific properties and must be imported with curly braces matching their exact exported names.

### Default vs. Named Exports: The Module Boundary

- [p] ◇ Organizing components across dedicated files is the cornerstone of scalable React architecture. In modern JavaScript, the ES module system provides two mechanisms for sharing code across files: default exports and named exports. ◼ Educational objective: introduce default and named exports as complementary module boundary mechanisms.
- [p] ★ {preknowledge: ES modules, export statements, import statements} {bridging: developers must distinguish between the primary component of a file and secondary companion helpers} The two export mechanisms serve distinct architectural roles: ◼ Educational objective: categorize default and named exports by architectural purpose.
- [p] 1. **Default Exports (`export default`)**: Each file can have at most one default export. It represents the primary component that defines the file (such as `export default function ArticleCard`). Consumers import it without curly braces: `import ArticleCard from './ArticleCard.jsx'`. ◼ Educational objective: define default exports.
- [p] 2. **Named Exports (`export function`)**: A file can have multiple named exports. They represent secondary helper functions, constants, or companion components (such as `export function formatRole`). Consumers import them using curly braces: `import { formatRole } from './ArticleCard.jsx'`. ◼ Educational objective: define named exports.
- [p] ★ {preknowledge: code organization, import conventions, refactoring safety} {bridging: developers face an architectural crossroad between using named exports exclusively or combining default components with named helpers} When organizing component files, you face an architectural crossroad between two team conventions: ◼ Educational objective: frame the pedagogical crossroad between named-only and combined export patterns.
- [p] - **Option 1 (The foundational way)**: Use named exports for everything, forcing curly braces on every import across the codebase. ◼ Educational objective: declare Option 1 with concrete syntax tokens.
- [p] - **Option 2 (The modern idiomatic way)**: Use a default export for the primary component, and named exports for companion helpers and formatters. ◼ Educational objective: declare Option 2 with concrete syntax tokens.
- [p] First, look at Option 1 using named exports exclusively: ◼ Educational objective: transition to Option 1 code.
- [code] Option 1:
```jsx title="Option 1: The Foundational Way (Named-Only)"
export function ArticleCard() { // Named export for primary **COMPONENT**
  return <article className="card">Headline</article>;
}

import { ArticleCard } from './ArticleCard.jsx'; // Requires curly braces on **IMPORT**
```
◼ **The what-this-introduces list:** 1. `export function ArticleCard`: named component export. 2. `import { ArticleCard }`: bracketed named import matching identifier. 3. Zero default export.
- [p] ★ In Option 1, every export is named. This guarantees that consumers cannot accidentally rename the component upon import, enforcing strict naming consistency across the team. However, it requires curly braces on every import, creating friction when a file clearly represents one single component. ◼ Educational objective: analyze the trade-offs of named-only exports.
- [p] Next, look at Option 2 using the modern idiomatic pattern: ◼ Educational objective: transition to Option 2 code.
- [code] Option 2:
```jsx title="Option 2: The Modern Idiomatic Way (Default Component + Named Helper)"
export function formatRole(role) { // Named export for utility **HELPER**
  return `By ${role.toUpperCase()}`;
}

export default function ArticleCard() { // Default export for primary **COMPONENT**
  return <article className="card">{formatRole('news')}</article>;
}
```
◼ **The what-this-introduces list:** 1. `export function formatRole`: named utility export. 2. `export default function ArticleCard`: single primary default component export. 3. Clean separation between UI component and helper logic.
- [p] ★ In Option 2, the file has one unambiguous primary identity: the `ArticleCard` component. Any secondary utility or data transformer is exported alongside it as a named export. Consumers can import the primary component cleanly (`import ArticleCard from './ArticleCard.jsx'`) or pull in helpers as needed (`import ArticleCard, { formatRole } from './ArticleCard.jsx'`). ◼ Educational objective: explain the ergonomics of combining default and named exports.
- [callout] > [!KEY]
> Use a default export for the single primary component of a file. Use named exports for secondary utility functions, constants, or companion components. Never wrap a default import in curly braces.

### Step 1: First, we construct the parent container <App.jsx>

- [p] We begin by constructing the top-level application shell in `src/App.jsx`. This component acts as the outer editorial container. It imports `ArticleCard` as a default import without curly braces and mounts it inside the page layout: ◼ Educational objective: construct the parent shell importing a child component via default import.
- [code] App.jsx:
```jsx title="src/App.jsx"
import ArticleCard from './components/ArticleCard.jsx'; // Imports default component without **CURLIES**

export default function App() {
  return (
    <div className="editorial-shell">
      <ArticleCard /> // Mounts modular article card at layout **ROOT**
    </div>
  );
}
```
◼ **The what-this-introduces list:** 1. `import ArticleCard`: default import without curly braces. 2. `./components/ArticleCard.jsx`: relative path to child module. 3. `<ArticleCard />`: mounting the extracted component.
- [p] Notice the import syntax: `import ArticleCard from './components/ArticleCard.jsx'`. Because `ArticleCard.jsx` exports its component as `default`, we do not use curly braces. Writing `{ ArticleCard }` here would assign `undefined` and crash the render pass. ◼ Educational objective: emphasize the absence of curly braces for default imports.

### Step 2: Next, we extract the primary card component <ArticleCard.jsx>

- [p] Now we create the component file `src/components/ArticleCard.jsx`. This file represents the primary article presentation card. We declare the component and export it as the default export of the module: ◼ Educational objective: declare a primary component using export default.
- [code] ArticleCard.jsx:
```jsx title="src/components/ArticleCard.jsx" startLine="1" continues="bottom"
import AuthorBadge, { formatRole } from './AuthorBadge.jsx'; // Combined default and named **IMPORT**

export default function ArticleCard() { // Primary component default **EXPORT**
  const headline = 'Offshore Banking Secrets Exposed';
  const role = formatRole('investigative'); // Calls named utility **FUNCTION**
  return (
    <article className="article-card">
      <span className="desk-tag">{role}</span>
      <h2 className="headline">{headline}</h2>
```
◼ **The what-this-introduces list:** 1. `import AuthorBadge, { formatRole }`: combining default and named imports in one statement. 2. `export default function ArticleCard`: declaring default component export. 3. `continues="bottom"`: continuation fence.
- [p] Notice line 1: `import AuthorBadge, { formatRole } from './AuthorBadge.jsx'`. In a single line, we import the default component `AuthorBadge` without braces, and the named utility `formatRole` with braces. This demonstrates how default and named imports coexist harmoniously. ◼ Educational objective: deconstruct combined default and named import syntax.

### Step 3: Then, we declare the author badge and named helper <AuthorBadge.jsx>

- [p] Next, we create `src/components/AuthorBadge.jsx`. This file exports two entities: a named helper function `formatRole` that formats editorial desk tags, and a default component `AuthorBadge` that renders the reporter's credentials: ◼ Educational objective: author a module with both a named utility export and a default component export.
- [code] AuthorBadge.jsx:
```jsx title="src/components/AuthorBadge.jsx"
export function formatRole(role) { // Named export for string **FORMATTER**
  return role.toUpperCase() + ' DESK';
}
export default function AuthorBadge() { // Default export for badge **COMPONENT**
  return (
    <div className="author-badge">
      <span className="author-name">Elena Rostova</span> // Reporter **BYLINE**
    </div>
  );
}
```
◼ **The what-this-introduces list:** 1. `export function formatRole`: named function export. 2. `export default function AuthorBadge`: default functional component export. 3. Clean separation of utility logic from UI rendering.
- [p] Notice that `formatRole` carries `export`, while `AuthorBadge` carries `export default`. The keyword `default` flags `AuthorBadge` as the primary export of the file. Any other export in the file must be a named export. ◼ Educational objective: distinguish export from export default in the same file.

### Step 4: Finally, we mount the child badge inside <ArticleCard.jsx>

- [p] Finally, we complete `src/components/ArticleCard.jsx` by mounting the `<AuthorBadge />` component inside the article card layout and closing the JSX return statement: ◼ Educational objective: mount the imported child component and seal the component file.
- [code] ArticleCard.jsx:
```jsx title="src/components/ArticleCard.jsx" startLine="9" continues="top"
      <AuthorBadge /> // Mounts imported child component at card **BASE**
    </article>
  );
}
```
◼ **The what-this-introduces list:** 1. `<AuthorBadge />`: declarative child component tag. 2. `continues="top"`: completing the component file.
- [p] Notice how modular our application has become: `App.jsx` imports `ArticleCard.jsx`, which in turn imports `AuthorBadge.jsx` and its helper `formatRole`. Each file has a single clear responsibility, carries its own imports, and can be edited without conflicting with other components. ◼ Educational objective: highlight the modular composition and maintenance benefits of component file splitting.

### Glossary

- [glossary] Default Export ◼ The primary export of an ES module (`export default`), imported without curly braces and bound to `.default` on the module namespace.
- [glossary] Named Export ◼ A specific exported member of an ES module (`export function`), imported with curly braces matching its exact identifier.
- [glossary] Module Specifier ◼ The path string in an import statement (such as `'./components/ArticleCard.jsx'`) indicating the target file's location on disk.
- [glossary] Module Namespace Object ◼ The internal JavaScript object containing all exports of a module, where default exports sit on `.default` and named exports sit on matching keys.
- [glossary] Component Extraction ◼ The architectural process of refactoring a component from a monolithic file into its own dedicated ES module file.

## Beyond the basics

- **Default vs named export specifications**: In the ECMAScript module specification, default exports are syntactic sugar for a named export with the identifier `default` (see [react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components)).
- **Import aliases with the as keyword**: Both named and default imports can be renamed during import to resolve naming collisions via `import { formatRole as formatTag }` (see [react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components)).
- **Re-exporting from barrel files**: Modules can re-export components directly using `export { default } from './ArticleCard.jsx'`, creating clean public entry points for component directories (see [react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components)).
- **Dynamic imports and code splitting**: React supports lazy loading components via `React.lazy(() => import('./ArticleCard.jsx'))`, which requires the imported module to provide a default export (see [react.dev/reference/react/lazy](https://react.dev/reference/react/lazy)).
- **File extension resolution in bundlers**: Modern bundlers like Vite resolve `.jsx` and `.js` extensions automatically, though explicit extensions improve module clarity and native ESM compatibility (see [react.dev/learn/importing-and-exporting-components](https://react.dev/learn/importing-and-exporting-components)).

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Module Exports & File Structure

➔ ALWAYS dedicate each component file to a single primary component exported via `export default`.

➔ NEVER place multiple major UI layout components in a single monolithic file once they exceed 50 lines.

➔ IF exporting secondary utility functions or constants alongside a component THEN use named exports (`export function`).

❒ Import Syntax & Braces

➔ ALWAYS import default exports without curly braces (`import ArticleCard from './ArticleCard.jsx'`).

➔ NEVER wrap default imports in curly braces (`import { ArticleCard }`) because this resolves to `undefined` and crashes React during render.

➔ IF importing both a default component and named helpers THEN combine them in one statement (`import ArticleCard, { formatRole } from './ArticleCard.jsx'`).

**DO THIS:** import default component without curlies, named helper with curlies

```jsx right
import ArticleCard, { formatRole } from './ArticleCard.jsx';

export default function App() {
  return <ArticleCard tag={formatRole('news')} />;
}
```

**DO NOT DO THIS:** wrap default exports in curly braces or import non-existent named exports

```jsx wrong
import { ArticleCard } from './ArticleCard.jsx';

export default function App() {
  return <ArticleCard />;
}
```
