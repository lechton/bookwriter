### The Friction of Child-to-Parent Communication

- [p] ★ {preknowledge: props as function arguments, unidirectional data flow, pure rendering, event handlers} In earlier lessons, you learned that React enforces one-way data flow. Parents pass data downward to children through props like water flowing down a waterfall. A child component receives these props as read-only inputs and returns JSX markup describing what to render. However, real applications require user interactions in child components to influence the rest of the page. Readers click a category button inside a filter bar, but the news feed that needs filtering belongs to the top-level newsroom container. Beginners often struggle because a child component has no natural way to reach upward into parent memory. Mutating a received object changes data silently without notifying React, while reassigning a prop variable changes only a local copy inside the child. ◼ Educational objective: recall unidirectional downward props while exposing the architectural friction of communicating user actions from child components back up to parents.
- [p] ★ {problem: child mutating parent data or reassigning props fails silently} It is common for a developer new to React to assume that modifying a prop updates the parent. Suppose the parent passes an object `filters = { category: 'politics' }` down to `FilterBar`. Inside the child, the developer writes `filters.category = 'business'`. In JavaScript memory, the property updates, but React never receives an update signal. The browser continues to display "Showing: politics" because no re-render was scheduled. If the developer tries reassigning a destructured prop like `category = 'tech'`, JavaScript only reassigns the local parameter variable. The parent never sees this reassignment, leaving both components desynchronized. ◼ Educational objective: analyze the silent runtime failure of direct prop mutation and prop reassignment.
- [p] ★ {old solution: two-way data binding, global custom events, or direct parent variable mutation} In two-way binding systems like Vue's `v-model` or Angular's `[(ngModel)]`, changing a form control in a child automatically syncs the parent's data. In legacy JavaScript, developers dispatched global DOM events like `window.dispatchEvent(new CustomEvent('filter-change'))`. In React, there is no automatic two-way binding. Global events and direct mutations bypass the component tree, making it impossible to trace which parent reacts to a child button click. React requires an explicit, traceable communication channel. ◼ Educational objective: contrast automatic two-way data binding and global DOM events with React's explicit component communication.

- [code] Naive Prop Mutation Attempt:

```jsx title="Naive Execution Attempt"
function FilterBar({ filters, category }) {
  function pickBusiness() {
    ~filters.category~ = 'business'; // **WRONG:** mutates prop object directly
    console.log(~filters.category~); // Logs business while screen stays frozen
  }
  return (
    <button type="button" onClick={pickBusiness}>Business</button>
  );
}
```

◼ **The what-this-introduces list:** 1. `filters.category = 'business'`: unobserved mutation of a parent-owned object. 2. `pickBusiness`: local click handler modifying props directly. 3. `console.log(...)`: observable divergence between memory mutation and unchanged screen output.

- [p] ★ {mechanism: inverse data flow via callback props} React solves this challenge through **inverse data flow** using **callback props**. The parent component defines an event handler function and passes a reference to that function downward to the child as a prop, such as `<FilterBar onSelectCategory={handleCategoryChange} />`. The child component receives this function as a regular prop and executes it when the user clicks a button: `onSelectCategory('business')`. Data still travels strictly downward because the function itself was passed down as a prop. What travels upward is the notification and the argument payload. The parent retains full authority to decide how to respond. ◼ Educational objective: establish the mechanism of inverse data flow where children notify parents by invoking downward-passed callback functions.

### Unidirectional Data Flow and the Inverse Path

- [p] ◇ {conceptual grounding: unidirectional data flow and component boundaries} In React, data flows strictly downward from parent to child through **props**. This architecture is called **unidirectional data flow**. Think of it as a one-way street or a clean river. The parent component owns the application data and passes copies of that data down to its children. A child component is a consumer: it receives inputs and renders UI elements. Because children cannot modify parent variables directly, your application remains predictable. You always know where data comes from by looking up the component tree. ◼ Educational objective: establish the concept of unidirectional data flow and explain why React forbids children from writing directly into parent memory.
- [p] ★ {architectural comparison: React one-way flow versus two-way data binding} To understand why React works this way, contrast it with two-way data binding. In frameworks like Vue with `v-model` or Angular with `[(ngModel)]`, child controls can bind directly to parent variables. When the user interacts with the child control, the framework automatically syncs the value in both directions. While two-way binding requires less typing upfront, it creates hidden communication pathways. In complex applications, tracking which child modified which parent variable becomes difficult. React chooses explicit one-way data flow: data only goes down, and notifications only go up through functions you explicitly pass in JSX. ◼ Educational objective: contrast React one-way data flow with two-way data binding in Vue and Angular.
- [p] ★ {runtime mechanism: what is a callback prop and why does it enable inverse flow} A **callback function** is a function passed as an argument or prop to another piece of code so it can be called later. In React, when a parent passes a function to a child via a prop like `onSelectCategory={handleCategoryChange}`, that prop is called a **callback prop**. When the user clicks a button, the child invokes this function. This pattern is called **inverse data flow** because the communication travels upward against the waterfall. However, the rule of unidirectional data flow is never broken: the parent passed a function value downward, and the child merely triggered the function. ◼ Educational objective: define callback functions and explain the runtime mechanism of inverse data flow.
- [p] ★ {syntactic reminder: destructuring, closures, and arrow functions} Let us review three JavaScript features that work together in callback props. First, **prop destructuring** (`function FilterBar({ onSelectCategory })`) unpacks the callback function directly from the props object into a local variable. Second, a **JavaScript closure** ensures that when the parent creates a handler function, that function remembers all variables in the parent's surrounding scope. Third, an **inline arrow function** (`() => onSelectCategory('business')`) delays execution so the callback runs only when the user clicks, while allowing the child to pass arguments upward. ◼ Educational objective: review prop destructuring, JavaScript closures, and inline arrow function wrappers in the context of callback props.

### Principles of React: The Core Laws of Inverse Data Flow

- [p] ◇ Senior technical interviews test whether an engineer truly understands how data moves through a React application. Interviewers frequently ask: "How does a child component update state in its parent, and what happens under the hood when a callback executes?" To answer with authority, we formalize the four governing principles of inverse data flow: ◼ Educational objective: frame the four operational principles of callback props from the perspective of an engineering candidate preparing for a senior technical interview.

> [!PRINCIPLE]
> **Principle 1: Expect Data to Flow Only Down, with No Path Back Up Except a Function**
> Data travels strictly downward from parent to child through props. A child receives value copies rather than links to parent variables, meaning mutating a received object or reassigning a prop never triggers an update in the parent. React provides no automatic two-way binding, so the only upward communication path is a function the parent explicitly passes down.
> 
> >> unidirectional data flow : passing data strictly downward from parent to child through props
> >> two-way data binding : automatic bidirectional synchronization between user controls and parent data

- [p] ★ Principle 1 operational derivation: When a parent renders a child component in JSX, it evaluates prop values and passes them into the child function as an object. In JavaScript, primitive values like strings and numbers are passed by value, while objects are passed by reference. If a child component modifies an object property like `filters.category = 'business'`, it mutates the object in JavaScript heap memory. However, React does not monitor object mutations. React only schedules updates when components re-render or state changes occur. Because no render was scheduled, the parent screen remains frozen on "Showing: politics". Furthermore, if the child reassigns a destructured prop like `category = 'tech'`, JavaScript only reassigns that single local function parameter. The parent's variable in the outer scope remains unchanged. React has no two-way binding mechanism like Vue's `v-model`. If a child needs to report a change, it cannot write to parent memory; it must call a function provided by the parent. ◼ Educational objective: derive why direct mutation and prop reassignment fail to update parent components, contrasting React with two-way data binding.

- [code] Silent Mutation and Reassignment Failure:

```jsx title="Silent Mutation Failure"
export default function NewsroomPage() {
  const ~filters~ = { category: 'politics' }; // Object holding category
  return (
    <div>
      <h2>Showing: {filters.category}</h2>
      <FilterBar ~filters={filters}~ /> // Passes object reference to child
    </div>
  );
}
```

◼ **The what-this-introduces list:** 1. `filters`: parent data object. 2. `FilterBar filters={filters}`: passing object reference downward. 3. `Showing: {filters.category}`: parent heading remaining unchanged after child mutation.

> [!PRINCIPLE]
> **Principle 2: Let the Parent Pass a Callback and Have the Child Call It When the User Acts**
> When an action inside a child component needs to affect parent data, the parent defines a handler and passes it downward as a callback prop. The child executes that callback inside its own click or change handler, allowing the child to report what happened while the parent decides what that action means.
> 
> >> callback prop : a function prop passed from parent to child to receive notifications
> >> inverse data flow : child components triggering parent functions to send information upward
> 
> *It is best practice to do this:*
> `function FilterBar({ onSelectCategory }) {`
> `  return (`
> `    <button onClick={() => onSelectCategory('business')}>`
> `      Business`
> `    </button>`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function FilterBar({ filters }) {`
> `  return (`
> `    <button onClick={() => { filters.category = 'business'; }}>`
> `      Business`
> `    </button>`
> `  );`
> `}`

- [p] ★ Principle 2 operational derivation: When a user clicks a button in a child component, the browser triggers the button's native event listener. To communicate upward, the parent component passes a function reference down as a prop, named with the `on` prefix followed by the action name, like `onSelectCategory={handleCategoryChange}`. Inside the child, the button's `onClick` handler calls this callback prop. When the user clicks the Business button, the child executes `onSelectCategory('business')`. This triggers `handleCategoryChange` inside the parent component. This pattern achieves two vital architectural goals. First, it makes data flow visible in JSX: any developer reading `NewsroomPage` can see exactly which function responds to the filter selection. Second, it keeps the child component reusable. A different parent, such as an `ArchivePage`, can render the exact same `FilterBar` and pass its own callback handler. Global custom events or shared module variables hide these relationships and break component reusability. ◼ Educational objective: analyze how callback props establish visible, traceable communication channels while preserving child component reusability.

- [code] Parent Callback Invocation:

```jsx title="Parent Callback Invocation"
export default function NewsroomPage() {
  function handleCategoryChange(category) {
    console.log(~'Newsroom received:', category~); // Executes parent handler
  }
  return (
    <FilterBar
      onSelectCategory=~{handleCategoryChange}~ // Passes callback prop
    />
  );
}
```

◼ **The what-this-introduces list:** 1. `handleCategoryChange`: parent handler receiving child category. 2. `onSelectCategory={handleCategoryChange}`: passing function reference as callback prop. 3. `console.log(...)`: verified parent execution.

> [!PRINCIPLE]
> **Principle 3: Treat the Callback as a Closure That Runs in the Parent's Scope**
> A callback function is created inside the parent component, so it closes over the parent's variables and execution context. When the child invokes the callback, the function executes within the parent's scope, allowing it to read parent data the child never sees while keeping update authority strictly inside the parent.
> 
> >> JavaScript closure : a function that remembers and accesses variables from the outer scope where it was created
> >> parent scope : the execution context and local variables declared inside the parent component

- [p] ★ Principle 3 operational derivation: A frequent question in senior technical interviews is: "How can a child component run code that modifies the parent without having access to the parent's variables?" The answer is JavaScript closures. In JavaScript, every function retains access to the variables declared in its outer scope at the time the function was defined. When `NewsroomPage` renders, it defines `handleCategoryChange`. Suppose `NewsroomPage` declares `const edition = 'Morning'`. The `FilterBar` component never receives `edition` as a prop and knows nothing about editions. However, when the user clicks Business and `FilterBar` calls `onSelectCategory('business')`, the function executes inside `NewsroomPage`'s lexical scope. The handler reads `edition` directly from parent memory. The child acts solely as the trigger: it provides the new category argument, while the parent alone decides how to process the information. ◼ Educational objective: derive the role of JavaScript closures in allowing callback props to execute within parent scope.

- [code] Closure Execution in Parent Scope:

```jsx title="Closure Scope Verification"
export default function NewsroomPage() {
  const ~edition~ = 'Morning'; // Variable private to parent scope
  function handleSelect(category) {
    console.log(~edition, category~); // Reads parent variable via closure
  }
  return <FilterBar onSelectCategory={handleSelect} />;
}
```

◼ **The what-this-introduces list:** 1. `edition = 'Morning'`: variable declared in parent scope. 2. `handleSelect`: closure reading parent variable alongside child argument. 3. `onSelectCategory={handleSelect}`: child receives only callback, not edition.

> [!PRINCIPLE]
> **Principle 4: Send the Value the Parent Needs, Not the DOM Event**
> A child component should translate raw browser events into clean application-level values before calling a callback prop. Passing a category name or item identifier decouples the parent from the child's internal HTML markup, preventing fragile code that breaks when HTML tags change.
> 
> >> app-level value : clean domain data like a category name or identifier, independent of HTML markup
> >> DOM event coupling : tying parent logic directly to child HTML element structure and event objects
> 
> *It is best practice to do this:*
> `function FilterButton({ category, onSelect }) {`
> `  return (`
> `    <button onClick={() => onSelect(category.slug)}>`
> `      {category.name}`
> `    </button>`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function FilterButton({ category, onSelect }) {`
> `  return (`
> `    <button onClick={onSelect}>`
> `      {category.name}`
> `    </button>`
> `  );`
> `}`

- [p] ★ Principle 4 operational derivation: When developers wire a button click directly to a callback prop like `<button onClick={onSelectCategory}>`, the browser's native click event object is passed directly to the parent handler. The parent function receives a SyntheticEvent object instead of a string category. When the parent logs `Showing: ` plus the category, the browser prints `"Showing: [object Object]"`. If the parent tries to fix this by digging into the event object with `e.target.textContent`, the parent becomes tightly coupled to the child's internal HTML structure. If a designer changes the button label from "Business" to "Business News", or wraps the text in an icon `<span>💼 Business</span>`, `e.target.textContent` changes or returns the icon text, breaking the parent's logic. By wrapping the callback in an arrow function `() => onSelectCategory('business')`, the child extracts and translates the user action into a clean domain value. The parent receives exactly what it needs without knowing whether the child used buttons, tabs, links, or a dropdown menu. ◼ Educational objective: analyze why children should translate DOM events into application-level values before calling callback props.

- [code] Event Object vs App Value Translation:

```jsx title="Translating Events to Domain Values"
export default function FilterBar({ onSelectCategory }) {
  return (<div>
    <button onClick=~{onSelectCategory}~> // Passes raw event object
      Raw
    </button>
    <button onClick=~{() => onSelectCategory('tech')}~> // Passes clean string
      Clean
    </button>
  </div>);
}
```

◼ **The what-this-introduces list:** 1. `onClick={onSelectCategory}`: anti-pattern passing raw event object. 2. `onClick={() => onSelectCategory('tech')}`: recommended pattern passing clean domain string.

### Where you will meet this

1. **Category and Filter Navigation**: Filter bars and tab controls notify parent lists when a user selects a new filter or sorting option.
2. **Search Input Fields**: Search bars pass the latest query string upward to the containing page component on every keystroke or submit.
3. **Modal Dialogs and Drawers**: Reusable modal components call `onClose` callback props when the user clicks the dismiss button or backdrop.
4. **Form Field Components**: Custom input and select controls notify parent form managers of new values without owning persistent state.

### Glossary

- **Callback Prop**: A function passed from a parent component to a child component as a prop, intended to be called by the child upon user interaction.
- **Inverse Data Flow**: The pattern where a child component triggers a function in its parent, passing data upward while preserving downward unidirectional data flow.
- **Unidirectional Data Flow**: The architecture where data flows strictly in one direction from parent components downward to children through props.
- **JavaScript Closure**: A function that retains access to variables declared in its outer scope even when invoked in a different part of the application.
- **App-Level Value**: A clean domain value, such as a category name or item identifier, passed to a callback instead of a raw browser DOM event object.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ One-Way Data Flow & Child Notifications

➔ ALWAYS pass a callback function downward when a child interaction must notify a parent component.

➔ NEVER mutate a prop object or reassign a prop variable inside a child component.

**DO THIS:** pass a callback prop to allow the child to notify the parent
```jsx right
function FilterBar({ onSelectCategory }) {
  return (
    <button type="button" onClick={() => onSelectCategory('business')}>
      Business
    </button>
  );
}
```

**DO NOT DO THIS:** mutate received prop objects directly inside child components
```jsx wrong
function FilterBar({ filters }) {
  function handleClick() {
    filters.category = 'business';
  }
  return (
    <button type="button" onClick={handleClick}>
      Business
    </button>
  );
}
```

❒ Application Values vs DOM Events

➔ ALWAYS translate raw browser events into clean domain values before calling callback props.

➔ NEVER pass raw SyntheticEvent objects to callbacks unless the parent explicitly requires event mechanics.

**DO THIS:** pass clean domain values like strings or identifiers to callbacks
```jsx right
function CategoryItem({ slug, onSelect }) {
  return (
    <button type="button" onClick={() => onSelect(slug)}>
      Select
    </button>
  );
}
```

**DO NOT DO THIS:** pass raw click events directly into domain callbacks
```jsx wrong
function CategoryItem({ slug, onSelect }) {
  return (
    <button type="button" onClick={onSelect}>
      Select
    </button>
  );
}
```

❒ Closures & Component Scope

➔ ALWAYS rely on closures to allow parent handlers to read parent-scoped variables upon child invocation.

➔ ALWAYS provide default fallbacks like `() => {}` for optional callback props to prevent runtime crashes.

| | **TWO-WAY BINDING & MUTATION**<br>(Fragile Coupling) | **INVERSE DATA FLOW**<br>(Declarative Callbacks) |
| ---: | :--- | :--- |
| **Data direction** | Data flows bidirectionally or child mutates parent objects in place | Data flows strictly down via props; notifications travel up via callbacks |
| **Component coupling** | Child reaches into parent memory or relies on hidden two-way sync | Child remains reusable; parent provides custom handler behavior |
| **Change traceability** | Unclear which child changed parent values; changes happen silently | Fully visible in JSX: parent passes named callback prop |
| **Callback execution** | Child modifies local variable or dispatches global DOM events | Callback executes as a closure in parent's lexical scope |
| **Passed argument** | Raw DOM event object or implicit two-way variable link | Clean application-level value like a category name or identifier |
