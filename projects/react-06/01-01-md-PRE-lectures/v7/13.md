### The Friction of Premature Execution and Custom Props

- [p] ★ {preknowledge: JSX markup, components as functions, props passing, pure rendering} In previous lessons, you learned that React components are pure functions that calculate JSX markup from incoming props. You built structured layouts by passing numbers, strings, and objects downward through props. However, modern web applications are not static documents; users click buttons, type text into search inputs, and save items for reading later. In traditional JavaScript, developers attached event listeners using `element.addEventListener('click', handler)` or assigned strings to HTML attributes like `onclick="handlePublish()"`. When moving to React, developers often bring these old habits into JSX. If an engineer writes parentheses after their handler name inside JSX braces (`onClick={openArticle(id)}`), JavaScript executes the function immediately during the render pass, long before any user touches the mouse. Furthermore, when developers pass `onClick` to a custom component like `<ArticleCard onClick={handleClick} />`, they are surprised when clicking the card produces no response at all because custom components do not automatically listen to browser DOM events. ◼ Educational objective: recall component rendering and props while identifying the twin frictions of premature function execution in JSX and unwired custom component props.
- [p] ★ {problem: premature execution from parentheses in JSX and unwired custom component props} It is possible that a developer may write `onClick={openArticle(id)}` on a button inside an article card, expecting React to store both the function and its argument until the user clicks. Instead, JavaScript evaluates the expression inside the curly braces immediately while building the virtual element. If an application displays ten articles, `openArticle` runs ten times while the page loads. In the browser console, messages like "Opened article: art-1" and "Opened article: art-2" appear before the first paint. When the user later clicks the button, nothing happens because the expression evaluated to `undefined`, leaving the click prop with no function to call. A second failure occurs when an engineer passes an `onClick` prop to a custom component: `<ArticleCard onClick={handleSelect} />`. Custom components are JavaScript functions, not browser DOM nodes. Unless `ArticleCard` explicitly takes that prop and passes it down to a native browser element like `<button>`, the event prop is completely ignored and clicks are silently lost. ◼ Educational objective: analyze the operational failure where parentheses cause immediate render-phase execution and unwired custom component props remain silent.
- [p] ★ {old solution: inline HTML onclick strings or imperative addEventListener calls} In traditional web pages, developers either placed string commands inside HTML attributes (`onclick="selectItem('123')"`) or searched for elements imperatively with `document.querySelector()` to attach listener functions. In React, JSX props do not take string statements; they require direct JavaScript function values, and interactive behavior must be handed down explicitly through props to built-in DOM elements. ◼ Educational objective: contrast legacy HTML attribute strings and imperative element queries with React declarative event binding.

- [code] Naive Premature Execution Attempt:

```jsx title="Naive Execution Attempt"
function ArticleCard({ title, id }) {
  function openArticle(articleId) {
    console.log('Opened article:', articleId);
  }
  return (
    <button onClick=~{openArticle(id)}~> // Evaluates immediately on page load during render
      Read {title}
    </button>
  );
}
```

◼ **The what-this-introduces list:** 1. `openArticle(id)`: function call executed immediately during JSX evaluation rather than on click. 2. `onClick={...}`: React event prop receiving the return value of `openArticle` instead of a callable function. 3. `console.log(...)`: observable side effect firing during page load before user interaction.

- [p] ★ {mechanism: passing function references, inline arrow functions, and callback props} React solves these problems by treating event handlers as first-class JavaScript functions passed as values. To register a click handler without running it immediately, you pass the function reference without parentheses: `onClick={handlePublish}`. When your handler needs specific arguments (such as an article identifier), you wrap the call inside an inline arrow function: `onClick={() => openArticle(article.id)}`. The arrow function acts as a waiting wrapper: it creates a new function that sits quietly until the user clicks, at which point it executes `openArticle` with the exact ID. To let parent components coordinate user actions across the application, parents pass callback functions downward through custom props (such as `onSelect={handleSelect}`). The child component receives the callback prop and wires it to a built-in browser element like `<button onClick={...}>`. This pattern, known as callback props, allows child components to report user actions upward while keeping data management and business decisions safely inside the parent. ◼ Educational objective: establish the mechanics of passing function references, wrapping arguments in arrow functions, and delegating behavior through callback props.
- [grounding] [!] Grounding card: Why did my button click handler run on page load? ◼ Opening question: Why did my button click handler run on page load? ◼ Friction target: Developers adding an event handler with arguments notice that their action executes immediately on page load and fails to respond to actual user clicks. ◼ Tactile scene: A developer creates a "Read Article" button with `onClick={openArticle(story.id)}`; upon refreshing the browser, the console prints `Opened article: 1` instantly, before the cursor has even moved across the screen; when the developer clicks the button, nothing happens at all. ◼ Bold key terms: **function reference**, **premature invocation**, **inline arrow function**, **callback prop**, **event handler binding**. ◼ Operational resolution: In JSX, expressions inside curly braces run immediately during component rendering; writing `openArticle(story.id)` calls the function on the spot and passes its return value (`undefined`) to `onClick`; wrapping the call in an arrow function (`onClick={() => openArticle(story.id)}`) creates an uncalled function reference that React executes only when the user triggers the click event.

### Event Handlers as Functions and the DOM Boundary

- [p] ◇ {conceptual grounding: browser events and React declarative handlers} To master user interaction in React, we must understand how React connects JavaScript functions to browser events. In the browser DOM, elements dispatch events (such as `click`, `input`, `keydown`, and `submit`) when users interact with the screen. In standard HTML, developers used lowercase attributes like `onclick`. In React, event props are written in **camelCase**, such as `onClick`, `onChange`, `onKeyDown`, and `onSubmit`. Instead of passing a string containing code, you pass an actual JavaScript function value. When the user interacts with the rendered element, React receives the native browser event and invokes your handler function. ◼ Educational objective: ground React event handling in native browser events and contrast declarative camelCase function props with legacy HTML attributes.
- [p] ★ {runtime distinction: passing a reference versus invoking during render} A foundational rule of React is the distinction between **passing a function reference** and **calling a function**. When you write `onClick={handleClick}`, you are giving React the address of the function; you are saying, "Remember this function and execute it when the user clicks this button." But when you write `onClick={handleClick()}`, the parentheses tell JavaScript to execute `handleClick` right now, while the component function is running. The return value of `handleClick` (which is usually `undefined`) is then assigned to `onClick`. If you need to pass an argument to a handler, you must not call it directly in JSX. Instead, you create a new function on the fly using an arrow function: `onClick={() => handleSelect(article.id)}`. Because the arrow function body does not execute until the arrow function itself is called, the inner `handleSelect` call waits safely until the user clicks. ◼ Educational objective: clarify the operational distinction between passing a function reference versus calling a function during render, explaining how inline arrow functions defer execution.
- [p] ★ {architectural model: callback props and component boundaries} A frequent source of confusion is understanding where browser events stop and React component props begin. Built-in HTML elements (like `<button>`, `<input>`, `<a>`, and `<form>`) represent real browser DOM elements; React attaches native event listeners to these built-in elements. In contrast, custom components (like `<ArticleCard />` or `<BookmarkButton />`) are purely JavaScript abstractions. If you write `<ArticleCard onClick={handleClick} />`, React does not attach a click listener to any DOM node because `ArticleCard` is not a DOM node. The prop `onClick` is merely a custom prop, exactly like `title` or `color`. For that click to do anything, `ArticleCard` must receive the prop and attach it to a real built-in element inside its return markup: `<button onClick={onClick}>`. By convention, custom components name their handler props after the application action (such as `onSelect` or `onBookmark`) rather than low-level DOM events. The parent decides what action should occur, passes a callback function down, and the child wires that callback to a native button. ◼ Educational objective: establish the DOM element boundary, explaining why custom components require explicit wiring to built-in elements and how callback props maintain parent authority.
- [p] ★ {syntactic reminder: arrow functions and callback conventions} Let us review two JavaScript features essential for clean event handling: **arrow functions** and **naming conventions**. An arrow function (`() => expression`) is a concise way to create an anonymous function value in JavaScript. When written as `() => onSelect(article.id)`, it accepts the event and forwards the specific `article.id` to the parent callback. Second, React developers follow a universal naming convention: handler functions defined inside a component are named with the prefix `handle` followed by the action or event (such as `handleSelect` or `handleBookmark`), while props that receive callbacks are named with the prefix `on` followed by the action (such as `onSelect` or `onBookmark`). This distinction makes code instantly readable: `on` signals a prop that accepts behavior, while `handle` signals the function that implements that behavior. ◼ Educational objective: provide clear reminders on arrow function syntax and the universal handle-versus-on naming conventions in React.

### Principles of React: The Core Laws of Event Handling

- [p] ◇ When preparing for senior technical interviews, candidates must clearly explain why handlers must be passed rather than called, how inline arrow functions pass arguments safely, why custom components require explicit wiring to built-in DOM elements, and why click targets must use semantic button tags. To master these concepts, we formalize the three governing principles of event handling: ◼ Educational objective: frame the three principles from the perspective of an engineering candidate preparing for senior technical interviews.

> [!PRINCIPLE]
> **Principle 1: Pass the Handler, Never Call It**
> Give an event prop a function value (onClick={handlePublish}) so React can call it when the user clicks, and when the handler needs arguments, pass a new function that makes the call (onClick={() => openArticle(article.id)}), because anything written inside JSX curly braces runs immediately during render.
> 
> >> function reference : passing the function itself as an uncalled value so an event listener can execute it later
> >> premature invocation : executing a function during render by adding parentheses inside JSX braces instead of waiting for user interaction
> 
> *We should do this:*
> `<button onClick=~{handlePublish}~>Publish</button> // Passes uncalled function reference to run on click`
> 
> *We should not do this:*
> `<button onClick=~{handlePublish()}~>Publish</button> // Parentheses call the function immediately during render`

- [p] ★ Principle 1 operational derivation: In React, JSX curly braces are an evaluation window into JavaScript. Any expression placed inside `{ ... }` runs synchronously during the render phase. If you write `onClick={handlePublish()}`, JavaScript invokes `handlePublish()` immediately while constructing the JSX element tree. If `handlePublish` logs "PUBLISH ran" to the console, that message appears on page load before any user interaction. Because `handlePublish` does not return a function, `onClick` receives `undefined`. When the user later clicks the button, the browser finds no function to call, and the click produces zero output. The exact same defect occurs when passing arguments: writing `onClick={openArticle(story.id)}` executes `openArticle` during render for every item in your list. To pass a handler without running it, pass the bare function name: `onClick={handlePublish}`. When arguments are required, wrap the call inside an arrow function: `onClick={() => openArticle(story.id)}`. The arrow function is an uncalled function value created during render; it runs only when the user dispatches a click event. ◼ Educational objective: derive why parentheses inside JSX cause immediate execution on page load and how arrow function wrappers preserve deferred event dispatch.

- [code] Handler Reference vs Immediate Invocation:

```jsx title="Handler Reference vs Immediate Invocation"
export default function PublishButton() {
  function handlePublish() {
    console.log('PUBLISH ran');
  }
  return (
    <button type="button" onClick=~{handlePublish}~> // Passes uncalled function reference to run on click
      Publish Story
    </button>
  );
}
```

◼ **The what-this-introduces list:** 1. `handlePublish`: function defined inside component containing action logic. 2. `onClick={handlePublish}`: function reference passed to JSX without parentheses. 3. `console.log('PUBLISH ran')`: observable output confirming execution occurs strictly upon user click.

> [!PRINCIPLE]
> **Principle 2: Hand Behavior to a Child Through an on Prop and Wire It to a Real Element**
> When the parent decides what a click means, pass a function through a prop named for the app action (<ArticleCard onSelect={handleSelect} />) and, inside the child, pass that prop to a built-in element's event prop (<button onClick={() => onSelect(id)}>), because only built-in elements turn browser events into handler calls; a custom component ignores props it does not use.
> 
> >> callback prop : a function prop passed from parent to child allowing the child to report user actions upward
> >> DOM element boundary : the terminal built-in HTML elements (like button or input) where React connects event props to browser events
> 
> *We should do this:*
> `function ArticleCard({ ~onSelect~, id }) { // Receives custom callback prop from parent`
> `  return <button onClick=~{() => onSelect(id)}~>Read</button>; // Wires callback to native button via inline arrow`
> `}`
> 
> *We should not do this:*
> `function ArticleCard({ onSelect }) {`
> `  return ~<div className="card">~Read</div>; // Non-interactive div ignores callback prop and drops click events`
> `}`

- [p] ★ Principle 2 operational derivation: Custom React components are not DOM elements. When you write `<ArticleCard onClick={handleClick} />`, the browser does not see a DOM element named `<ArticleCard>`, and React does not attach an event listener to the card boundary. Custom components only receive props; if `ArticleCard` does not explicitly take `onClick` and wire it to a built-in element, clicking anywhere on the rendered card does nothing. To establish clear architectural boundaries, name handler props after the semantic application action rather than generic DOM events: pass `onSelect={handleSelect}` instead of `onClick={handleSelect}`. This separation decouples the parent from the child's internal layout: the parent cares that a story was selected, while the child decides whether that selection is triggered by a button, a keypress, or an icon click. Inside the child, connect the callback prop directly to a built-in browser element's event prop: `<button onClick={() => onSelect(article.id)}>`. When the user clicks the button, the child executes the callback, passing relevant identifiers upward while the parent retains full authority over application data. ◼ Educational objective: analyze why custom component props do not capture browser events automatically and how explicit callback wiring establishes clean component contracts.

- [code] Parent Callback Delegation:

```jsx title="Parent Callback Delegation"
export default function ArticleCard({ article, ~onSelect~ }) { // Callback prop passed down from parent
  return (
    <article className="article-card">
      <h3>{article.title}</h3>
      <button type="button" onClick=~{() => onSelect(article.id)}~> // Inline arrow function delays execution until user clicks
        Read Story
      </button>
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `onSelect`: callback prop passed from parent representing the semantic selection action. 2. `onClick={() => onSelect(article.id)}`: inline arrow function wiring native click event to the parent callback. 3. `article.id`: argument passed upward to the parent without mutating parent data.

> [!PRINCIPLE]
> **Principle 3: Make Click Targets Real Buttons**
> Attach click handlers to <button> elements (or links for navigation), not to <div> or <span>, because the browser gives a button keyboard focus and activation with Enter and Space, while a clickable <div> responds only to a mouse.
> 
> >> semantic button : an HTML button element providing built-in keyboard navigation, focus management, and screen reader accessibility
> >> inaccessible click target : a non-interactive element like div or span given an onClick handler without keyboard support
> 
> *We should do this:*
> `<button ~type="button"~ className="action-btn" onClick={handleSave}> // Built-in button element with keyboard focus and activation`
> `  Save`
> `</button>`
> 
> *We should not do this:*
> `<div className="action-btn" ~onClick={handleSave}~> // Inaccessible click target unreached by Tab or Enter`
> `  Save`
> `</div>`

- [p] ★ Principle 3 operational derivation: A frequent design flaw in modern web applications is turning generic layout containers into clickable controls by writing `<div onClick={handleClick}>` or `<span onClick={handleClick}>`. While a mouse click may fire the handler, non-interactive elements lack built-in accessibility. A user navigating with the Tab key cannot move focus to a `<div>`, and pressing the Enter or Space keys produces zero response. Screen readers announce the element as generic text or a grouping, giving visually impaired users no indication that the element is actionable. In contrast, the HTML `<button>` element provides full accessibility out of the box: the browser includes it in the keyboard tab sequence, displays native focus outlines, dispatches click events when the user presses Enter or Space, and communicates its interactive role to assistive technologies. If you need a button to look like a plain link or badge, use CSS to remove the default background and borders (`border: none; background: transparent;`) while preserving the underlying semantic `<button>`. ◼ Educational objective: demonstrate why clickable generic containers fail keyboard accessibility and why semantic button elements are mandatory for interactive controls.

- [code] Accessible Button Target:

```jsx title="Accessible Button Target"
export default function BookmarkControl({ onSave }) {
  return (
    <button type="button" ~onClick={onSave}~> // Passes function reference directly to native button click listener
      Save to Bookmarks
    </button>
  );
}
```

◼ **The what-this-introduces list:** 1. `<button type="button" ...>`: semantic interactive element with default keyboard and focus support. 2. `className="bookmark-btn"`: CSS class allowing full visual styling without sacrificing accessibility. 3. `onClick={onSave}`: clean function reference binding to the native button click.

### Glossary

- **Function Reference** ◼ Passing a function by name as an uncalled value without parentheses so React can execute it later when an event fires.
- **Premature Invocation** ◼ Accidental execution of a function during the render phase caused by placing parentheses after the function name inside JSX curly braces.
- **Callback Prop** ◼ A function passed downward through props from parent to child, allowing the child to report user interactions upward.
- **Inline Arrow Function** ◼ An anonymous function expression (`() => handler(arg)`) created inside JSX to delay function execution until an event occurs while passing arguments.
- **DOM Element Boundary** ◼ The terminal built-in HTML elements (such as button, input, or a) where React connects JSX event props directly to browser event listeners.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Event Handler Attachment

➔ ALWAYS pass event handlers as function references without parentheses: `onClick={handleClick}`.

➔ ALWAYS wrap handlers that require arguments inside an inline arrow function: `onClick={() => handleClick(item.id)}`.

**DO THIS:** pass function references or arrow functions to event props

```jsx right
function SelectButton({ id, onSelect }) {
  return <button type="button" onClick={() => onSelect(id)}>Select</button>;
}
```

**DO NOT DO THIS:** call functions immediately inside JSX curly braces

```jsx wrong
function SelectButton({ id, onSelect }) {
  return <button type="button" onClick={onSelect(id)}>Select</button>;
}
```

❒ Callback Props and Component Boundaries

➔ ALWAYS name callback props after the application action with an `on` prefix: `onSelect={handleSelect}`.

➔ ALWAYS wire callback props to built-in DOM elements (like `<button>`) inside the child component.

**DO THIS:** wire incoming callback props to native button click handlers

```jsx right
function ArticleCard({ story, onSelect }) {
  return (
    <article>
      <h3>{story.title}</h3>
      <button type="button" onClick={() => onSelect(story.id)}>Read</button>
    </article>
  );
}
```

**DO NOT DO THIS:** attach event props to custom components without internal wiring

```jsx wrong
function Feed({ stories, onSelect }) {
  return (
    <div>
      {stories.map((s) => (
        <ArticleCard key={s.id} story={s} onClick={onSelect} />
      ))}
    </div>
  );
}
```

❒ Accessible Interactive Targets

➔ ALWAYS use `<button>` elements (or links for navigation) for clickable user controls.

➔ NEVER attach click handlers to generic `<div>` or `<span>` elements without keyboard support.

**DO THIS:** use semantic button elements with CSS styling for interactive controls

```jsx right
function BookmarkAction({ onSave }) {
  return (
    <button type="button" className="bookmark-btn" onClick={onSave}>
      Save Story
    </button>
  );
}
```

**DO NOT DO THIS:** attach click handlers to non-interactive div containers

```jsx wrong
function BookmarkAction({ onSave }) {
  return (
    <div className="bookmark-btn" onClick={onSave}>
      Save Story
    </div>
  );
}
```

| | **PREMATURE CALL / GENERIC DIV**<br>(Fragile Anti-Pattern) | **DECLARATIVE CALLBACK & BUTTON**<br>(React Architecture) |
| ---: | :--- | :--- |
| **Execution timing** | Runs immediately on page load during render; fails on click | Defers execution until user interacts with the element |
| **Supplying arguments** | Immediate call (`onClick={fn(id)}`) evaluates during render | Wrapped in arrow function (`onClick={`<br>`() => fn(id)}`) |
| **Custom component wiring** | Unwired event props on custom components silently do nothing | Parent passes `on` prop; child wires to built-in `<button>` |
| **Keyboard accessibility** | Clickable `<div>` cannot be reached with Tab or Enter | Semantic `<button>` provides native focus and Enter/Space support |
| **Data flow authority** | Child attempts to mutate parent data directly | Child invokes callback prop; parent retains update authority |
