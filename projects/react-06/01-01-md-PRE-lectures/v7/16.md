### State as a snapshot of one moment in time

- [p] ◇ {conceptual grounding: rendering takes a snapshot} When React renders a component, it calls the component function. The `useState` hook returns the state value for that specific run. In that run, the state variable is a standard JavaScript `const`. It never changes while that function executes. All JSX, event handlers, and calculations in that run are created using that single fixed value. We call this fixed set of values a **snapshot**. ◼ Educational objective: establish the snapshot mental model; anchor it to constant local variables.
- [p] ◇ {mechanism: what the setter actually does} Calling a setter function does not change the variable in your running code. Instead, the setter tells React what value to store for the next render. It asks React to call your component function again with that new value. The running handler finishes executing using the current snapshot. ◼ Educational objective: separate the running function scope from React's external state shelf.
- [p] ◇ {picture: the substitution method} You can visualize this behavior using the substitution method from the official React documentation. If `rating` is `0` when the component runs, you can substitute `0` for `rating` everywhere. The code `setRating(rating + 1)` evaluates as `setRating(0 + 1)`. Calling `setRating(rating + 1)` three times in one handler evaluates as `setRating(0 + 1)` three times. Each call asks React for 1, not 3. ◼ Educational objective: provide an intuitive mental calculation method for repeated updates.
- [p] ★ {preknowledge: closures and setTimeout} Every render produces its own fresh set of event handlers. In JavaScript, a function created inside another function is a **closure**. A closure remembers the variables of the scope where it was born. A handler created during a render where `rating` is 5 closes over that 5. A delayed timer started with `setTimeout` keeps reading the 5 from that render. In browser JavaScript, `setTimeout` runs a function after waiting a set number of milliseconds. ◼ Educational objective: explain JavaScript closure capture and browser setTimeout clearly.
- [p] ★ {prerequisite recalls and previews} Lecture 13 showed that functions are passed to `onClick`, not called immediately. Lecture 14 taught that `useState` stores memory outside the component and starts local variables fresh on each call. Lecture 15 proved that React renders and commits only after the event handler finishes. Looking forward, Lecture 17 will introduce updater functions like `r => r + 1` for consecutive updates. Lecture 18 will show how mutating objects directly can accidentally break earlier snapshots. ◼ Educational objective: name all prerequisite and preview owner lessons in clear sentences.

### Principles of React: State as a Snapshot

- [p] ◇ Interviewers ask this question to probe the snapshot model and closure behavior. The first principle explains why state never changes within a render. The second principle shows how to use the next value right away. The third principle explains how closures preserve earlier renders. ◼ Educational objective: frame the three principles clearly.

- [principle-notes] Principle 1: The reader expects calling setCount(count + 1) to update the variable count right away, like changing a normal variable. What actually happens: count is a regular JavaScript constant inside this function run, so calling a setter cannot change the number sitting on the current line. It only tells React what number to pass to the next run. Move from casebook Case 1: start with the plain JavaScript constant, state the reader's expectation, show why the setter cannot change the running line, and explain why three calls yield 1 instead of 3.

> [!PRINCIPLE]
> **Principle 1: State is a constant number during one run of your component**
> In your component, `count` is a regular constant. When React runs the function, `count` holds one value, such as 0. Calling `setCount(1)` does not change that constant in your running code. Instead, it asks React to run the component next time with 1. Because this run is still executing, `count` stays 0 on every line. Calling `setCount(count + 1)` three times in the same click just asks for `0 + 1` three times.
>
> *We should do this:*
> `const [count, setCount] = useState(0);`
> `setCount(count + 1); // asks React for 1 on the next run`
> `console.log(count); // prints 0, this run's constant number`
>
> *We should not do this:*
> `const [count, setCount] = useState(0);`
> `setCount(count + 1); // asks for 0 + 1`
> `setCount(count + 1); // still reads 0, asks for 0 + 1 again`

- [p] ★ In Ann's component, `rating` starts at 0. When she clicks "+3 Boost", the function executes three calls to `setRating(rating + 1)`. Because `rating` is 0 throughout that render, all three calls pass `0 + 1`. React queues a render with 1. When `StoryFeedback` runs again, `useState` returns 1, and the console logs `render rating = 1`. A second click on "+3 Boost" evaluates `1 + 1` three times, moving the count to 2. ◼ Educational objective: prove Principle 1 on the lesson's example with verified runtime numbers.

- [principle-notes] Principle 2: The reader expects to read the updated number right after calling the setter. What actually happens: reading the state variable right after its setter still gives the current run's old number. Move from casebook Case 1 and Case 3: state the need (sending the new number right away), show why reading state fails, and show the clean fix: calculate the new value once in a plain variable and pass it to both places.

> [!PRINCIPLE]
> **Principle 2: Calculate the next value once if other code needs it right away**
> Any line of code inside the same click handler still reads the current run's state. Reading `count` right after calling `setCount(count + 1)` still reads the old number. When you need to send the new number to an API right away, calculate it once in a plain variable. Pass that variable to the setter, and pass that same variable to your other code.
>
> *We should do this:*
> `const nextCount = count + 1; // calculate the new value once`
> `setCount(nextCount); // tells React what to show next`
> `send(nextCount); // sends 1, the new number`
>
> *We should not do this:*
> `setCount(count + 1); // asks React for 1 on next run`
> `send(count); // sends 0, current run's old number`

- [p] ★ In Ann's five-star button, she replaces `sendRating(rating)` with a local variable: `const nextRating = 5`. She calls `setRating(nextRating)` and `sendRating(nextRating)`. The server receives 5 immediately. After the handler returns, React re-renders `StoryFeedback` with `rating = 5`. The server and the screen now agree completely. ◼ Educational objective: prove Principle 2 with the exact fix and verified network payload.

- [principle-notes] Principle 3: The reader wonders whether a delayed timer or network callback will pick up later state changes if the user clicks again while waiting. What actually happens: the click handler captured the state of the render that created it. Move from casebook Case 5: explain that each run creates its own functions that keep their own values, protecting delayed code from timing bugs. Real Mistake is none (single right card).

> [!PRINCIPLE]
> **Principle 3: A click handler keeps the values of the run that created it**
> Every run of a component creates its own functions. When you declare a click handler, it captures the variables from that specific run. If the handler waits for a delay like `setTimeout`, it still sees the values from when it was created. If another click changes state while the timer waits, the delayed code still reads its original value safely.
>
> *We should do this:*
> `function handleSend() {`
> `  setTimeout(() => {`
> `    console.log(count); // prints the count from this run`
> `  }, 1000);`
> `}`

- [p] ★ In `StoryFeedback`, Ann adds a Send button that logs a thank-you message after a 100-millisecond delay using `setTimeout`. She rates the story with 5 stars, clicks Send, and quickly clicks 2 stars before the timer finishes. The screen updates to show 2 stars. But when the timer fires, the console logs `Thanks for rating 5`. The callback was created during the render where `rating` was 5, so it preserves that snapshot faithfully. ◼ Educational objective: prove Principle 3 with the timer experiment and verified console output.

### Step 1: First, we lay out the feedback application <src/App.jsx>

```jsx title="App.jsx"
import StoryFeedback from './components/StoryFeedback.jsx';
export default function App() {
  console.log('App runs'); // logs on initial render
  return (
    <main className="feedback-layout">
      <h1>Story Review Desk</h1>
      <StoryFeedback />
    </main>
  );
}
```

◼ **The what-this-introduces list:** 1. `App`: top-level root component. 2. `StoryFeedback`: self-contained state boundary.

- [p] `App` owns zero state, so clicks inside the feedback card never force `App` to re-render. It executes once on initial load, keeping top-level layout completely isolated from rating clicks. ◼ Meaningful pedagogical commentary: architectural container isolation.

### Step 2: Next, we build the rating boundary <src/components/StoryFeedback.jsx>

```jsx title="StoryFeedback.jsx" startLine="1" continues="bottom"
import { useState } from 'react';
import RatingControls from './RatingControls.jsx';
import { sendRating } from '../feedbackApi.js';
export default function StoryFeedback() {
  const [rating, setRating] = useState(0); // rating snapshot
  console.log('StoryFeedback runs, rating =', rating);
```

```jsx title="StoryFeedback.jsx" startLine="7" continues="both"
  function handleRate(score) {
    const nextRating = score; // compute value once
    setRating(nextRating);
    sendRating(nextRating);
  }
  function handleSend() {
    setTimeout(() => {
      console.log('Thanks for rating', rating); // captures snapshot
    }, 100);
  }
```

```jsx title="StoryFeedback.jsx" startLine="17" continues="top"
  return (
    <section className="feedback-card">
      <p>Rating: {rating} stars</p> // displays snapshot value
      <RatingControls onRate={handleRate} onSend={handleSend} />
    </section>
  );
}
```

◼ **The what-this-introduces list:** 1. `const [rating, setRating] = useState(0)`: component state snapshot. 2. `handleRate`: computes next value once. 3. `handleSend`: scheduled timer reading captured snapshot.

- [p] `StoryFeedback` owns the state. When `handleRate(5)` executes, `nextRating` holds 5. Both `setRating` and `sendRating` receive 5. Then `handleSend` captures `rating` as a closure. ◼ Meaningful pedagogical commentary: state encapsulation, single value computation, and closure safety.

### Step 3: Finally, we build the rating action controls <src/components/RatingControls.jsx>

```jsx title="RatingControls.jsx"
export default function RatingControls({ onRate, onSend }) {
  return (
    <div className="button-group">
      <button onClick={() => onRate(5)}>5 Stars</button> // rates 5 stars
      <button onClick={() => onRate(2)}>2 Stars</button>
      <button onClick={onSend}>Send Feedback</button>
    </div>
  );
}
```

◼ **The what-this-introduces list:** 1. `onRate`: upward callback passing chosen score. 2. `onSend`: upward callback scheduling the delayed alert.

- [p] `RatingControls` owns no state of its own. It acts as an interactive control bridge, invoking callback props when buttons are pressed. The parent component executes the real updates. ◼ Meaningful pedagogical commentary: upward callback delegation and stateless child design.

### For the interview

- [interview] Repeated Interview Question ◼ `> **The Interview Question:** Why does state seem frozen within the same component run?`
- [interview] The Hidden Signal ◼ Interviewers test whether candidates understand JavaScript function execution and closures versus framework timing magic. A junior developer blames asynchronous timing; a senior developer explains that a component run is a regular function call where state is a local constant primitive in memory.
- [interview] The Classic Trap ◼ Candidates blurt out "state is frozen because setting state is asynchronous." Even if React updated synchronously in zero nanoseconds, calling a setter cannot rewrite a local constant in an executing stack frame. The frozen behavior is a property of JavaScript scope, not a timing delay.
- [interview] What is Actually Going On ◼ State is a snapshot. When React calls a component, `useState` returns the state for that run as a constant. A setter does not mutate that constant; it schedules the next render with a new value. Every line in the running handler reads the same snapshot. Compute the new value once in a local variable if other code needs it right away.
- [interview] Where It Gets Tricky: Async and Await ◼ An `async` handler that awaits a promise still reads the original snapshot after returning. The closure preserves the variables from the run that spawned it, even if the screen has already updated from another click.
- [interview] Where It Gets Tricky: Feature Not a Bug ◼ Snapshots protect delayed operations from race conditions. If a user clicks Send to Alice and quickly changes the recipient to Bob, the delayed network call still sends to Alice.
- [interview] Where It Gets Tricky: Reading the Latest Value ◼ If delayed code genuinely requires the latest value across renders, store that value in a mutable ref (`useRef`), as taught in Lecture 29.

### Glossary

- [glossary] Snapshot ◼ The fixed value of state that React provides to a component for one specific render.
- [glossary] Closure ◼ A JavaScript function that remembers and accesses variables from the outer scope where it was created.
- [glossary] Setter Function ◼ A function returned by `useState` that stores the next state value in React and requests a new render.
- [glossary] `setTimeout` ◼ A standard browser function that waits a specified duration in milliseconds before running a callback function.
- [glossary] Substitution Method ◼ A mental technique where you replace state variables with concrete values to predict how event handlers execute.
