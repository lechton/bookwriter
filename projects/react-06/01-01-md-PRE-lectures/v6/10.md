### The Friction of Imperative DOM Branching

- [p] ★ {preknowledge: props passing, JSX expressions, HTML document structure} In previous lessons, you learned how to pass data downward from parent components to child components through props, and how to interpolate JavaScript values into markup using curly braces. Every component returned a predictable, uniform tree of JSX elements. However, modern web interfaces are rarely static or uniform. A digital newsroom must adapt its display depending on incoming data: an urgent story needs a bold "BREAKING NEWS" banner, an active investigative piece requires a pulsating "LIVE" badge, a premium article displays a subscriber paywall, and an article with disabled comments must omit the discussion panel entirely. ◼ Educational objective: recall props and curly braces while establishing the universal need for dynamic markup branching based on runtime data.
- [p] ★ {problem: naive imperative class toggling creates desynchronization and layout bugs} It is possible that a developer coming from vanilla JavaScript may attempt to handle these visual variations by searching the DOM and toggling CSS classes directly. They might render all elements unconditionally into the page, and then write helper scripts that call `document.querySelector('.comments').classList.add('hidden')` or set `element.style.display = 'none'`. When they do, the application quickly becomes fragile. Imperative DOM queries run outside React's memory model, meaning the browser DOM and React's virtual tree fall out of sync. If a parent re-renders, React re-evaluates the component and overwrites the manual changes, causing UI flickering and layout bugs. Furthermore, elements hidden with `display: none` remain inside the physical DOM tree and the browser accessibility tree, cluttering memory and confusing screen readers. ◼ Educational objective: expose the operational failure of manipulating classes or inline styles imperatively outside React's render pipeline.
- [p] ★ {old solution: imperative DOM mutation and jQuery-style element hiding} In legacy web development, developers regularly kept invisible elements in the DOM and toggled their visibility using imperative scripts or jQuery methods like `$('#comments').hide()`. In a modern declarative framework like React, this approach violates the fundamental principle that user interface is a pure projection of data (`UI = f(data)`). ◼ Educational objective: identify the legacy jQuery-style hiding pattern and contrast it with React's pure projection model.

- [code] Naive Imperative Hiding Attempt:

```javascript title="Naive DOM Mutation Attempt"
function updateArticleVisibility(isBreaking) {
  const badge = document.~querySelector~('.breaking-badge'); // Manual DOM query
  if (!isBreaking && badge) {
    badge.classList.~add~('hidden'); // Fights React DOM reconciliation
  }
}
```

◼ **The what-this-introduces list:** 1. `document.querySelector('.comments')`: fragile DOM query searching for an element outside React's control. 2. `classList.add('hidden')`: imperative class manipulation that desynchronizes with React's virtual tree. 3. `hidden`: CSS class leaving hidden nodes in the accessibility tree and memory.

- [p] ★ {mechanism: declarative conditional rendering with standard JavaScript control flow} React solves this problem through declarative conditional rendering. Instead of creating elements and then hiding them by mutating the DOM, you decide which elements exist in the first place directly inside your component function. React does not invent a special templating syntax or custom attributes like `v-if` or `ngIf`. Instead, you use standard JavaScript control flow: `if` statements for early returns, the ternary operator (`? :`) for choosing between two alternate elements, and the logical AND operator (`&&`) for including an element or rendering nothing. When a condition evaluates to false, React leaves that element out of the virtual tree entirely, meaning it is never created in the browser DOM. ◼ Educational objective: explain how declarative conditional rendering uses standard JavaScript control flow to control element existence.
- [grounding] [!] Grounding card: Why does a stray 0 print on the screen when using logical AND? ◼ Opening question: Why does a stray 0 print on the screen when using logical AND? ◼ Friction target: Developers writing `{commentCount && <Comments />}` discover a literal number `0` rendered on the screen when an article has zero comments. ◼ Tactile scene: An engineer builds an article summary card, sets `commentCount={0}` on a fresh story, and opens the browser; instead of hiding the comment counter, the card displays an ugly, orphaned `0` next to the article title. ◼ Bold key terms: **logical AND operator**, **short-circuit evaluation**, **falsy values**, **DOM text node**, **explicit boolean guard**. ◼ Operational resolution: In JavaScript, `0 && <Component />` evaluates to the number `0`, not `false`; because React treats numbers as visible content and renders them as DOM text nodes, you must always convert numeric checks to explicit booleans using comparisons like `commentCount > 0 && <Comments />`.

### How React Evaluates Conditions and Suppresses Falsy Values

- [p] ◇ {conceptual grounding: control flow in React is plain JavaScript} To master conditional rendering in React, we must first understand how React evaluates your code. In many other frameworks, conditional rendering relies on proprietary template directives that you write as custom HTML attributes. In React, components are standard JavaScript functions. Because JSX is transformed directly into JavaScript function calls (`_jsx(...)`), you have the full power of JavaScript at your disposal. You can use standard `if` statements, store JSX elements in local variables, evaluate ternary expressions, and short-circuit with logical operators. You do not need to learn a separate templating language. ◼ Educational objective: anchor the concept that React conditional rendering is built entirely on standard JavaScript language semantics.
- [p] ◇ {syntactic grounding: statements versus expressions inside JSX curly braces} In earlier lessons, you learned that curly braces `{}` inside JSX open an evaluation window where you can write JavaScript. However, JavaScript distinguishes between **statements** and **expressions**. An expression is a piece of code that evaluates to a single value, such as `2 + 2`, `article.title`, or a function call. A statement is an instruction that performs an action, such as `if (condition) { ... }`, `for`, or `while`. Function arguments and object properties can only accept expressions. Because JSX compiles into function calls, you cannot write an `if` statement directly inside JSX curly braces (`<div>{if (isLive) { ... }}</div>` throws a fatal syntax error). For inline branching inside markup, you must use expressions like the ternary operator or logical AND. ◼ Educational objective: explain the grammatical difference between statements and expressions, proving why if statements cannot live inside JSX curly braces.
- [p] ★ {syntactic reminder: how the ternary operator works} For developers who are newer to JavaScript, let us briefly review the **ternary operator** (`? :`). The ternary operator is a compact, inline conditional expression that takes three operands: a condition, followed by a question mark (`?`), an expression to execute if the condition is truthy, followed by a colon (`:`), and an expression to execute if the condition is falsy. For example, `isLive ? <LiveBadge /> : <StaticDate />` checks `isLive`; if `isLive` is true, the expression evaluates to `<LiveBadge />`; if false, it evaluates to `<StaticDate />`. Because the entire ternary evaluates to a single concrete value, it fits cleanly inside JSX curly braces. ◼ Educational objective: provide an easy-to-read, beginner-friendly explanation of the ternary conditional operator syntax.
- [p] ★ {syntactic reminder: how logical AND short-circuiting works} Similarly, let us review the **logical AND operator** (`&&`). In JavaScript, the `&&` operator evaluates expressions from left to right using **short-circuit evaluation**. If the left operand is truthy, JavaScript evaluates and returns the right operand. If the left operand is falsy, JavaScript stops immediately and returns the value of that left operand without evaluating the right side. For example, in `isBreaking && <span className="alert">BREAKING</span>`, if `isBreaking` is `true`, JavaScript evaluates the right side and returns the JSX element. If `isBreaking` is `false`, JavaScript stops and returns `false`. ◼ Educational objective: explain logical AND short-circuiting in clear, step-by-step terms.
- [p] ★ {the suppression whitelist: how React handles booleans, null, and undefined} Now comes the crucial link between JavaScript evaluation and React rendering: the **suppression whitelist**. When React encounters a value inside JSX curly braces, it inspects that value before touching the browser DOM. If the value is `false`, `null`, `undefined`, or `true`, React considers it an "empty slot" or a hole, and renders **zero DOM nodes**. It produces no tags, no text, and no whitespace. However, if the value is a string or a primitive number, React does not suppress it. React treats strings and numbers as legitimate user content and renders them as real browser text nodes. This is why returning `null` from a component renders nothing, why `false && <Badge />` renders nothing, and why `0 && <Badge />` renders a visible `"0"`. ◼ Educational objective: define React's suppression whitelist and explain why booleans and nullish values render nothing while numbers render as text.

### Principles of React: The Core Laws of Conditional Rendering

- [p] ◇ When preparing for technical interviews, candidates must clearly explain how to show, hide, and branch markup using standard JavaScript, why numeric values cause the classic stray zero bug, how early returns protect components against missing data crashes, and when to extract complex conditions into plain JavaScript variables. To master these concepts, we formalize the five governing principles of conditional rendering: ◼ Educational objective: frame the five principles from the perspective of an engineering candidate preparing for technical interviews.

> [!PRINCIPLE]
> **Principle 1: Return Early When the Component Cannot Produce Its Output**
> When a component depends on data to display its content, check for that data at the top of the function. Return `null` or a fallback before reading any properties so missing data does not crash your render. If the parent component decides whether the element belongs on screen at all, place the condition directly in the parent's JSX.
> 
> >> early return : exiting a component function early with null or fallback markup before reaching the main return
> >> defensive guarding : checking that data exists before reading its nested properties
> 
> *It is best practice to do this:*
> `function ArticleHeader({ article }) {`
> `  if (!~article~) return null; // Returns early before reading missing data`
> `  return <h1>{article.title}</h1>;`
> `}`
> 
> *Instead of doing this:*
> `function ArticleHeader({ article }) {`
> `  return <h1>{article.~title~}</h1>; // Crashes if article is undefined`
> `}`

- [p] ★ Principle 1 operational derivation: When a component receives its data as a prop, there are times when that data has not yet arrived or is completely undefined. If you attempt to access nested properties on missing data, such as writing `<h1>{article.title}</h1>` when `article` is `undefined`, the JavaScript runtime throws a fatal error: `Uncaught TypeError: Cannot read properties of undefined (reading 'title')`. This halts the entire rendering process and crashes the user interface. By placing an early return at the very top of your component (`if (!article) return null;`), you intercept the missing state before any property access occurs. When a component returns `null`, React paints nothing for that component in the DOM, leaving an empty slot while preserving the rest of the page. If the component should display a temporary loading state instead of an empty space, you can return a fallback element such as `<p>Loading article...</p>`. However, returning `null` from deep within a child component can sometimes surprise a teammate reading the parent code; whenever the decision is purely whether the parent should render the child, it is cleaner to write the guard in the parent's own JSX (`{article && <ArticleHeader article={article} />}`). ◼ Educational objective: prove how early returns prevent fatal undefined property crashes and contrast child early returns with parent guards.

- [code] Early Return and Parent Guard Proof:

```jsx title="Child Early Return Guard"
function ArticleHeader({ ~article~ }) { // Input prop
  if (!article) {
    return ~null~; // Prevents crash on article.title
  }
  return <h1>{article.title}</h1>;
}
```

```jsx title="Parent Inclusion Guard"
function Feed({ currentArticle }) {
  return (
    <main>
      {~currentArticle~ && ( // Parent decides child presence
        <ArticleHeader article={currentArticle} />
      )}
    </main>
  );
}
```

◼ **The what-this-introduces list:** 1. `if (!article) return null`: early return pattern returning null to render zero DOM nodes. 2. `article.title`: safe property access guarded by the early return. 3. `{currentArticle && <ArticleHeader />}`: parent-level inclusion guard controlling child mounting.

> [!PRINCIPLE]
> **Principle 2: Use && for Show-or-Nothing and the Ternary for One of Two**
> Use the logical AND operator (`&&`) when you want to show an element or render nothing at all. Use the ternary operator (`? :`) when you need to choose between two different elements. Matching the operator to the shape of your condition keeps both outcomes clear and prevents duplicated logic.
> 
> >> logical AND operator : a JavaScript operator (&&) that renders the right-hand element only when the left condition is true
> >> ternary operator : a JavaScript inline conditional operator (? :) that chooses between two alternative values
> 
> *It is best practice to do this:*
> `{~isLive~ ? <LiveBadge /> : <StaticDate />} // Single ternary for 2 choices`
> 
> *Instead of doing this:*
> `{isLive && <LiveBadge />}`
> `{!~isLive~ && <StaticDate />} // Duplicating inverse conditions`

- [p] ★ Principle 2 operational derivation: In technical interviews, interviewers frequently evaluate whether a developer understands the distinct architectural roles of the logical AND operator (`&&`) and the ternary operator (`? :`). A common mistake is using two separate `&&` expressions with opposite conditions to simulate an `if/else` branch: `{isLive && <LiveBadge />}` followed by `{!isLive && <StaticDate />}`. This pattern is fragile because it duplicates the condition in two places. If another engineer later updates the condition for the live badge but forgets to update the inverted condition below it, both elements or neither element may render at the same time. When your user interface requires choosing between two alternate elements (Branch A or Branch B), the ternary operator expresses this intent in a single, unified expression. Conversely, when your interface requires showing an element or nothing at all (Branch A or Nothing), writing `{isBreaking ? <span className="alert">BREAKING</span> : null}` is needlessly verbose. The logical AND operator (`{isBreaking && <span className="alert">BREAKING</span>}`) cleanly expresses show-or-nothing, relying on React's suppression whitelist to discard the `false` result when the condition is not met. ◼ Educational objective: contrast the branch shapes of && and ternary operators to establish clean, non-duplicated conditional markup.

- [code] Branch Shape Comparison:

```jsx title="Operator Selection by Branch Shape"
// SHOW-OR-NOTHING: renders badge when true, nothing when false
{~isBreaking~ && <span className="alert">BREAKING</span>}

// CHOICE BETWEEN TWO: picks one of two alternative elements
{~isLive~ ? <LiveBadge /> : <StaticDate />}
```

◼ **The what-this-introduces list:** 1. `{isBreaking && ...}`: idiomatic show-or-nothing branching with logical AND. 2. `{isLive ? ... : ...}`: idiomatic binary choice between two distinct elements with ternary operator.

> [!PRINCIPLE]
> **Principle 3: Make the Left Side of && an Explicit Boolean**
> Always convert numbers and arrays to a real boolean before using the `&&` operator in JSX. JavaScript returns the value of the left side whenever it is falsy, and React renders numbers directly to the screen. Comparing a number with zero (`count > 0`) produces `true` or `false`, preventing an unwanted `0` or `NaN` from appearing on your page.
> 
> >> stray zero : an unwanted 0 displayed on screen when a numeric zero short-circuits in JSX
> >> explicit boolean comparison : using a comparison operator like count > 0 to produce a real true or false value
> 
> *It is best practice to do this:*
> `{~commentCount~ > 0 && <span>Comments</span>} // Explicit boolean check`
> 
> *Instead of doing this:*
> `{~commentCount~ && <span>Comments</span>} // Raw zero prints on screen`

- [p] ★ Principle 3 operational derivation: The most infamous trap in React conditional rendering is the "Rogue Zero" or stray zero bug. A developer may assume that because `0` is a falsy value in JavaScript, writing `{commentCount && <Comments />}` will render nothing when `commentCount` equals `0`. Look at what JavaScript physically executes: when evaluating `0 && <Comments />`, JavaScript checks the left operand. Because `0` is falsy, the `&&` operator short-circuits and evaluates to the number `0`. It does NOT evaluate to `false`. React then receives `0` inside the curly braces. According to React's suppression whitelist, `false`, `null`, and `undefined` are ignored, but numbers are always preserved as valid content. Therefore, React creates a living browser DOM text node containing `"0"` and paints it directly onto the screen. The exact same trap occurs with `NaN`: if an uninitialized calculation results in `NaN`, writing `{rating && <StarRating />}` causes React to render the string `"NaN"` on screen while logging a console warning: `"Received NaN for the children attribute. If this is expected, cast the value to a string."`. Similarly, passing an empty array `tags = []` directly to `{tags && <TagList />}` renders an empty list because empty arrays are truthy in JavaScript. To guarantee your conditions behave predictably, never rely on raw numeric truthiness on the left of `&&`; always convert the condition into an explicit boolean comparison: write `commentCount > 0 && ...`, `!Number.isNaN(rating) && ...`, or `tags.length > 0 && ...`. ◼ Educational objective: unpack the physical runtime evaluation of the stray zero and NaN bugs, providing explicit boolean comparison solutions.

- [code] Falsy Evaluation Walkthrough:

```jsx title="Raw Number Zero Trap"
const ~commentCount~ = 0; // Raw numeric zero value
<div>{~commentCount~ && <span>Comments</span>}</div> // Paints stray 0
```

```jsx title="Safe Boolean Comparisons"
// Comparison produces boolean false: React renders nothing
<div>{~commentCount~ > 0 && <span>Comments</span>}</div>

// Length check avoids rendering empty container markup
<div>{tags.~length~ > 0 && <TagList tags={tags} />}</div>
```

◼ **The what-this-introduces list:** 1. `commentCount && ...`: short-circuit returning number 0. 2. `commentCount > 0 && ...`: safe boolean comparison returning boolean false. 3. `tags.length > 0 && ...`: safe array length check preventing empty container rendering.

> [!PRINCIPLE]
> **Principle 4: Move Branching Out of JSX When It Outgrows One Expression**
> When conditional logic grows beyond a single inline choice, move the calculation out of JSX into standard `if` statements with a variable or a lookup table before the `return`. Keeping complex branching in plain JavaScript avoids confusing nested ternaries and makes your code easy to read, test, and update.
> 
> >> nested ternary : chaining multiple ? : operators inside one expression, making code difficult to read
> >> variable extraction : calculating markup in JavaScript variables before returning the main JSX tree
> 
> *It is best practice to do this:*
> `let badge = null;`
> `if (isBreaking) badge = <span className="alert">BREAKING</span>;`
> `else if (isLive) badge = <span className="live">LIVE</span>;`
> `return <header>{~badge~}<h1>{title}</h1></header>; // Flat, readable JSX`
> 
> *Instead of doing this:*
> `return (`
> `  <header>`
> `    {~isBreaking~ ? <Alert /> : isLive ? <Live /> : null} // Nested ternary`
> `    <h1>{title}</h1>`
> `  </header>`
> `);`

- [p] ★ Principle 4 operational derivation: When building real-world user interfaces, a component often needs to choose between three or more visual states. For example, an article badge area might need to display a red "BREAKING" badge for urgent alerts, a blue "LIVE" badge for ongoing coverage, a grey "ARCHIVED" tag for older dispatches, or nothing at all for standard stories. When developers try to force all this logic inline inside JSX curly braces, they end up writing nested ternary expressions: `{isBreaking ? <Alert /> : isLive ? <Live /> : isArchived ? <Archive /> : null}`. Reviewers and teammates struggle to parse this code. Finding which colon corresponds to which question mark requires mental gymnastics, and adding a new case requires editing a fragile inline chain. In React, JSX is just JavaScript. You are not forced to write everything inside the `return` statement. When conditional branching outgrows a single clean expression, extract the logic before the `return` statement using standard `let` variables and `if/else` statements, or a clean lookup table. You assign the resulting JSX element (or `null`) to a variable such as `let statusBadge = null;`, and then embed `{statusBadge}` cleanly inside your returned markup. This keeps your JSX clean, readable, and easy to maintain. ◼ Educational objective: demonstrate how nested ternaries degrade readability and teach variable extraction and lookup patterns.

- [code] Variable Extraction and Lookup Table Patterns:

```jsx title="Extracted Variable Branching"
let ~badge~ = null; // Default empty slot
if (status === 'breaking') {
  badge = <span className="badge alert">BREAKING</span>;
} else if (status === 'live') {
  badge = <span className="badge live">LIVE</span>;
}
return <header>{~badge~}<h1>{title}</h1></header>; // Embeds precomputed JSX
```

◼ **The what-this-introduces list:** 1. `let badge = null`: local variable initialized to null before return. 2. `if/else`: standard JavaScript control flow assigning JSX to variables. 3. `{badge}`: clean embedding of the calculated element inside returned JSX.

> [!PRINCIPLE]
> **Principle 5: Omit Elements Through JSX Instead of Hiding Them with DOM Commands**
> Control whether an element exists on the page by including or omitting it in JSX, rather than searching the page and modifying CSS classes by hand. When JSX omits an element, React leaves it out of the DOM entirely. If an element must remain in the DOM while hidden, pass a CSS class or the `hidden` prop through JSX.
> 
> >> DOM omission : completely leaving an element out of the rendered DOM tree using a JSX condition
> >> imperative class toggle : manually adding or removing CSS classes like hidden using document queries
> 
> *It is best practice to do this:*
> `{~showComments~ && <section>Comments</section>} // Omitted from real DOM`
> 
> *Instead of doing this:*
> `el.classList.~add~('hidden'); // Mutates classes behind React`

- [p] ★ Principle 5 operational derivation: In declarative web engineering, there is a fundamental architectural difference between **omitting** an element and **hiding** an element. When you conditionally render an element using JSX (`{showComments && <Comments />}`), React physically includes or excludes the element from the rendered DOM. When `showComments` is `false`, the `<section className="comments">` element does not exist in the browser DOM at all. If you run `document.querySelector('.comments')` in the browser console, it returns `null`. It consumes zero memory and is completely absent from the browser accessibility tree. In contrast, if you render the element and hide it with CSS (`display: none` or `<section className="comments" hidden>`), the DOM node still physically exists in browser memory. It continues to occupy space in the document object model, can still be found by DOM queries, and may retain focus or form state. Never attempt to manipulate classes on React-managed nodes using imperative scripts like `classList.add('hidden')`, because manual mutations fight React's reconciliation engine. If an element should not be part of the UI, omit it through JSX. If the physical node must stay in the DOM while hidden, control its visibility declaratively by passing a class or the `hidden` boolean prop through JSX: `<section hidden={!showComments}>`. ◼ Educational objective: contrast physical DOM omission via JSX with CSS hiding, emphasizing accessibility and memory differences.

- [code] DOM Omission vs Declarative CSS Hiding:

```jsx title="Declarative Visibility Control"
// DOM OMISSION: element is absent from DOM; query returns null
{~showComments~ && <section className="comments">Discussion</section>}

// DECLARATIVE CSS HIDING: node stays in DOM but hidden from view
<section className="comments" hidden={!~showComments~}>
  Discussion
</section>
```

◼ **The what-this-introduces list:** 1. `{showComments && <section>}`: declarative omission completely removing the node from the DOM. 2. `<section hidden={!showComments}>`: declarative CSS hiding keeping the node in the DOM while passing the boolean hidden prop.

### Step 2: Next, we build the conditional header <src/components/ArticleHeader.jsx>

- [p] ★ {step motivation: implementing early returns, ternaries, boolean-guarded AND operators, and variable extraction} Now we construct the core component of this lesson: `src/components/ArticleHeader.jsx`. This component demonstrates all five principles in a single cohesive file. First, it implements an early return (`if (!article) return null;`) to guard against missing data. Second, it extracts reading time logic before the `return` statement using a clean `if` statement and a `let readingBadge` variable, avoiding nested ternaries. Third, inside the JSX markup, it uses logical AND with an explicit boolean check (`isBreaking && ...`) to display a red "BREAKING NEWS" alert. Fourth, it uses a ternary operator (`isLive ? <LiveBadge /> : <span className="date">{date}</span>`) to choose between live coverage and a static timestamp. Finally, it uses an explicit boolean comparison (`commentCount > 0 && ...`) to display the comment count only when comments exist, completely preventing the stray zero bug. ◼ Meaningful pedagogical commentary: combining early returns, variable extraction, inline ternaries, and boolean-guarded logical AND.

- [code] ArticleHeader.jsx (Part 1 - Data Guarding and Early Return):

```jsx title="ArticleHeader.jsx" startLine="1" continues="bottom"

export default function ArticleHeader({ article }) {
  if (!~article~) {
    return null; // Principle 1: guards missing data
  }

  const { title, isBreaking, isLive, commentCount, date } = article;
```

- [p] Declarative conditional rendering fundamentally changes how developers build dynamic interfaces. Instead of mutating the DOM after elements are created, React components describe exactly which elements should exist for any given combination of props. By using early returns for missing data, ternaries for binary choices, boolean-guarded logical AND operators for show-or-nothing branches, and variables for complex logic, you build user interfaces that are predictable, resilient to edge cases, and completely free of stray zeroes or layout flickering.

### Glossary

- [glossary] Conditional Rendering ◼ The ability to show, hide, or switch user interface markup based on JavaScript conditions and props.
- [glossary] Early Return ◼ Exiting a component function early with null or fallback markup before executing the main render logic.
- [glossary] Ternary Operator ◼ A JavaScript inline conditional expression (? :) that evaluates a condition and returns one of two values.
- [glossary] Short-Circuit Evaluation ◼ The evaluation model where logical AND (&&) stops and returns the left operand immediately if it is falsy.
- [glossary] Suppression Whitelist ◼ React's built-in rule that renders zero DOM nodes for booleans (true, false), null, and undefined.
- [glossary] Stray Zero ◼ An unwanted visible 0 printed on screen when a numeric zero short-circuits on the left side of a logical AND operator.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Operator Selection & Branch Shape

➔ ALWAYS use logical AND (`&&`) for show-or-nothing branches, and use the ternary operator (`? :`) when choosing between two alternate elements.

➔ NEVER use two separate inverted `&&` expressions (`{isLive && ...}{!isLive && ...}`) to simulate an `if/else` choice.

❒ Numeric Guarding & Falsy Safety

➔ ALWAYS convert numbers to explicit booleans (`count > 0 && ...`) before using the `&&` operator to prevent the stray zero bug.

➔ NEVER place a raw numeric counter or unverified calculation on the left side of `&&`.

❒ Complexity Management & DOM Ownership

➔ ALWAYS move complex multi-branch conditions before the `return` statement using `let` variables or lookup objects.

➔ NEVER manipulate CSS classes or styles imperatively using `classList` on DOM elements managed by React.

**DO THIS:** guard numeric values with explicit boolean comparisons

```jsx right
{commentCount > 0 && (
  <span className="comments">{commentCount} Comments</span>
)}
```

**DO NOT DO THIS:** pass raw numeric counters to logical AND operators

```jsx wrong
{commentCount && (
  <span className="comments">{commentCount} Comments</span>
)}
```

| ---: | :--- | :--- |
| **Missing Data Guarding** | Early return<br>`if (!data)`<br>`return null;`<br>prevents property crashes | Reading properties on undefined<br>(throws TypeError crash) |
