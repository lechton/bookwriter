### A Like That Reaches the Server One Click Late

- [p] ★ {preknowledge: `useState`, the setter, event handlers, Lecture 14's counter} In Lecture 14 we gave a component memory: `useState` keeps the count, and the setter stores the next value and makes React run the component again. Leo's page now has a `LikeCounter` component with a Like button, the count in a `<p>`, and a comment box. A colleague wrote a helper, `sendLikeEvent`, in `analytics.js`, which posts a number to the statistics server. Leo must call it on every like. ◼ Educational objective: recall the setter from Lecture 14 and set the scene with the real task.
- [p] ★ {problem: the server receives the old count} Leo comes from plain JavaScript, where the page is the place where the number lives. So he calls the setter and then reads the number back from the page with `document.querySelector`, and sends what he finds. The page shows 1, but the console shows `sending 0`, and only then `LikeCounter runs, likes = 1`. Every report is one like behind. ◼ Educational objective: show the concrete symptom before any theory; frame it as a habit from plain JavaScript, not a foolish mistake.

- [code] Leo's first handler (verified in React 19.3.0: logs `sending 0`, then `LikeCounter runs, likes = 1` and `LikeLabel runs, likes = 1`; the page shows 1):

```jsx title="LikeCounter.jsx, first attempt" startLine="7"
  function handleLike() {
    setLikes(likes + 1); // stores the next count
    const shown = document.querySelector('.like-count').textContent;
    console.log('sending', shown);
    sendLikeEvent(shown); // reads the number from the page
  }
```

◼ **The what-this-introduces list:** 1. `document.querySelector('.like-count')`: the browser's way to find the first element with that class. 2. `.textContent`: the text inside that element. 3. `sendLikeEvent(shown)`: the colleague's helper that posts the number.

- [p] ◇ {question} Leo has two more worries. If React runs `LikeCounter` again on every like, does it also run the whole app again? And does it rebuild the comment box, wiping what the reader is typing? He types "great post" and clicks Like: the text stays. To understand all three results, we need to know what happens between a setter call and the screen. ◼ Educational objective: raise the three reader questions the principles answer, without answering them yet.

- [grounding] Why does the page still show the old number? ◼ Opening question: Why does the page still show the old number? ◼ Friction target: a read of the page on the line after a setter call. ◼ Tactile scene: the console prints `sending 0` before `LikeCounter runs, likes = 1`, while the screen ends at 1. ◼ Bold key terms: **setter**, **event handler**, **DOM**. ◼ Operational resolution: the setter only stores the next value; React changes the page after the handler has finished, so the handler must use the number it computed.

### Three Steps From a Click to the Screen

- [p] ◇ {conceptual grounding: the DOM and changing it by hand} The browser keeps the page as a tree of objects called the **DOM**. Each element, such as the `<p>` with the count, and each piece of text inside it is a **DOM node**. In plain JavaScript, we change the page by changing these nodes ourselves: `document.querySelector('.like-count')` finds the node, and setting its `textContent` to `1` puts 1 on the page on that very line. Lecture 1 showed that React takes this job over: we describe the screen with JSX, and React changes the DOM nodes. ◼ Educational objective: teach DOM node, querySelector, and textContent (New terms) before any box uses them; recall Q01.
- [p] ◇ {mechanism: the three steps} Every screen update in React happens in three steps. First, a **trigger** tells React that the screen may need to change. There are two triggers: the first `root.render(<App />)` call from Lecture 9, and a setter call. Second, React **renders**: it calls our component functions and gets their JSX back; our code never calls them itself, React calls each one because the JSX names it (Lecture 2). Lecture 14 introduced this word for one run of a component. Nothing on the page changes in this step. Third, React **commits**: it changes the DOM nodes so the page matches the new JSX. After the commit, the browser draws the changed page on the screen, a step called **browser paint**. Browsers also call this step "rendering", so in an interview, say which one you mean. ◼ Educational objective: name the three steps plainly, then paint; dual meaning of rendering.
- [p] ◇ {picture} The React docs compare the steps to a restaurant. A guest orders, the kitchen cooks, and a waiter brings the plate to the table. The order is the trigger, the cooking is the render, and serving the plate is the commit. The guest sees the food only at the end. ◼ Educational objective: one everyday anchor from react.dev, Supporting row.
- [p] ★ {preknowledge: purity, Lecture 12} Because a render only calls functions and collects JSX, React may render a component without changing the page at all. This is why Lecture 12 asked components to be pure: a render must not change anything outside the function. Changes to the outside world, such as sending a like to a server, belong in event handlers. In a new Vite project, `StrictMode` is on, and in development React calls each component twice, so every log line inside a component appears twice in the console; Lecture 46 explains why. ◼ Educational objective: Prerequisite recalls (Q12) and the StrictMode Preview (Q46), one sentence.
- [p] ★ {first trigger} The first trigger is `root.render(<App />)` in `main.jsx`. The line after it runs before any component does: on that line, the `<div id="root">` still holds whatever HTML it had, such as a `Loading...` paragraph. Then React renders `App` and every component inside it, and the first commit replaces the old HTML with the new nodes. ◼ Educational objective: Merged row (root.render Caveat 4) and Supporting row (clears the container), verified.

- [code] The first trigger (verified: logs `after root.render` before `App runs`):

```jsx title="main.jsx"
import { createRoot } from 'react-dom/client';
import App from './App.jsx';
const root = createRoot(document.getElementById('root'));
root.render(<App />); // the first trigger
console.log('after root.render'); // no component has run yet
```

◼ **The what-this-introduces list:** 1. `root.render(<App />)`: recalled from Lecture 9, now named as the first trigger. 2. `console.log('after root.render')`: proof that the render comes after this line.

- [p] ◇ {surprise left for the principles} This picture raises the questions Leo already met. How does the setter's new value travel through these steps onto the screen? Which components does React call after a click? Will a commit wipe the comment box? And when, exactly, does the page change? The four principles answer them in that order. ◼ Educational objective: hand the open questions to the principles.

### Principles of React: Trigger, Render, and Commit

- [p] ◇ An interviewer who asks this question wants to hear the three steps, what runs in each, and one consequence a developer feels. The first principle follows one click through the steps. The second says which components run. The third says what the commit changes. The fourth is the decision that follows from the timing. ◼ Educational objective: frame the four principles.

- [principle-notes] Principle 1 (`setter-to-screen`, Real Mistake filled): The reader expects, rightly, that the setter makes React run the component and the number appears; Lecture 14 showed it. What they lack is the path from that run to the changed page. So the box starts from the plain JavaScript way (we change the page ourselves), then walks the three steps in order with things the reader can see: the stored 1, the JSX with 1, the text 0 becoming 1. The wrong card is the real plain JavaScript habit, verified: setting `textContent = count + 1` with no setter shows 1 on every click, because `count` stays 0, and no render log appears. The box says why in its last sentence. Sense test: a beginner asks exactly this question; every sentence is a step they can picture; the wrong card is code people really write, and the box explains its result. Moves from casebook Case 1 (show how the screen gets its value) and Case 2 (basic fact first).

> [!PRINCIPLE]
> **Principle 1: A Setter Call Reaches the Screen in Three Steps**
> In plain JavaScript, we change the page ourselves: `p.textContent = 1` puts 1 on the page on that line. In React, we call `setCount(count + 1)` and never touch the page. Three steps follow. First, the setter stores 1 and makes React run the component again: this is the trigger. Second, React calls the component function, which returns JSX with `{count}` now 1: this is the render. The page has not changed yet. Third, React compares this JSX with the JSX of the last run and changes the page where they differ, so the text 0 becomes 1: this is the commit. Changing the page by hand skips all three steps. `count` stays 0, so every click writes 1.
>
> *We should do this:*
> `const [count, setCount] = useState(0);`
> `setCount(count + 1); // the page shows 1, then 2, then 3`
>
> *We should not do this:*
> `const [count, setCount] = useState(0);`
> `const p = document.querySelector('p');`
> `p.textContent = count + 1; // the page shows 1 on every click`

- [p] ★ Under the box: Leo's final handler calls `setLikes(next)` and logs `handleLike, next = 1`; after it, the console prints `LikeCounter runs, likes = 1` and `LikeLabel runs, likes = 1`, and the `<p>` shows 1. Then the by-hand variant: the first click shows 1, the second still 1, and no `LikeCounter runs` line appears, because nothing triggered a render. Close on the first trigger: the same three steps ran when `root.render(<App />)` first showed the page, and that commit added every node. ◼ Educational objective: the rule on the lesson's own example, with verified output.

- [code] The by-hand handler (verified: shows 1 after the first and the second click, no render log):

```jsx title="LikeCounter.jsx, by hand" startLine="7"
  function handleLike() {
    const label = document.querySelector('.like-count');
    label.textContent = likes + 1; // changes the page directly
  }
```

◼ **The what-this-introduces list:** 1. `label.textContent = likes + 1`: the plain JavaScript way of changing the page, with no setter.

- [principle-notes] Principle 2 (`update-renders-below`, Real Mistake `none`): The reader guesses either the whole app runs again, like the first `root.render`, or only the clicked component; both are partly wrong. Basic fact first: components form a tree (Lecture 5). Then what happens on the first render (all of them) and after a setter (the owner and everything inside it, nothing above or beside). The last sentence prepares Principle 3: a run does not mean a page change. No real mistake breaks code here, so one card. Sense test: the question is the one interviewers ask; the generic tree (`App`, `Header`, `Counter`, `Label`) is pictured before the rule. Move from casebook Case 5 (picture the copies, then the rule).

> [!PRINCIPLE]
> **Principle 2: A State Change Runs Its Component and Every Component Inside It**
> Components form a tree. Say `App` returns `<Header />` and `<Counter />`, and `Counter` returns `<Label />`. On the first render, React calls all four, from `App` down. After a setter call in `Counter`, React does not start again from `App`. It calls `Counter`, the component that owns the state, and then `Label`, the component inside it. `App` and `Header` do not run. `Label` runs even when it returns the same JSX as before. A run does not mean the page changes, as Principle 3 shows.
>
> *We should do this:*
> `function Counter() {`
> `  const [count, setCount] = useState(0);`
> `  return (`
> `    <button onClick={() => setCount(count + 1)}> // runs Counter`
> `      <Label count={count} /> // and then Label`
> `    </button>`
> `  );`
> `}`

- [p] ★ Under the box: recall the component tree from Lecture 5. Leo's page is `App` with `StoryTitle` and `LikeCounter`, and `LikeCounter` returns `LikeLabel`. Every component logs its name. The first render logs `App runs`, `StoryTitle runs`, `LikeCounter runs, likes = 0`, `LikeLabel runs, likes = 0`. A click on Like logs only `LikeCounter runs, likes = 1` and `LikeLabel runs, likes = 1`. Preview Q54: a component also runs again when its parent runs, and Lecture 54 covers the other causes and why the runs are usually cheap. ◼ Educational objective: verified log on the lesson's tree; Preview Q54 in one sentence.

- [principle-notes] Principle 3 (`commit-only-differences`, Real Mistake `none`): The reader fears that a new run rebuilds the page, as `innerHTML` does in plain JavaScript, and wipes the comment. The fear leads to avoiding re-renders, not to broken code, so one card. Basic fact first (what `innerHTML` does), the expectation, "It does not.", then the mechanism in order: the run returns JSX, React compares, the commit changes only what differs. Paint stays out of the box (one idea) and goes in the paragraph. Sense test: the fear is real (map Friction 2); the proof is visible (typed text stays, same nodes). Move from casebook Case 4 (state the expectation, break it, give the mechanism).

> [!PRINCIPLE]
> **Principle 3: The Commit Changes Only What Differs, So Typed Text Stays**
> In plain JavaScript, setting `innerHTML` throws the old elements away and builds new ones, and any text typed into an `<input>` there is lost. We might expect a new run of a component to do the same. It does not. The run only returns JSX. React compares it with the JSX of the last run, and in the commit it changes only what differs, for example the text of a number. An `<input>` that stays in the same place in the JSX stays the same element on the page, with the text typed into it.
>
> *We should do this:*
> `return (`
> `  <section>`
> `    <p>{count}</p> // only this text changes`
> `    <input /> // same element, typed text stays`
> `  </section>`
> `);`

- [p] ★ Under the box: Leo types "great post" into the comment box and keeps the `<input>` and the `<p>` in two variables from the console. He clicks Like. The count shows 1, the comment still reads "great post", and both variables still point at the nodes on the page. Then the browser paints. Preview Q24: React keeps a node because the same element stays in the same place, and Lecture 24 explains how position decides it. ◼ Educational objective: verified node identity; paint; Preview Q24.

- [principle-notes] Principle 4 (`dom-after-handler`, Real Mistake filled, Review Point Do not): The reader expects the setter to change the page on its line, as `textContent` does. Basic fact first (plain JavaScript changes the page on that line), then what the setter does instead, then when React renders and commits, then the consequence on the next line, then the fix. The wrong card is Leo's real bug in general names, verified: it sends 0. Sense test: the reader's question is the ladder's question; the fix is one line of code anyone can apply. Move from casebook Case 6 (remind the JavaScript before the React).

> [!PRINCIPLE]
> **Principle 4: The Page Changes Only After the Event Handler Finishes**
> In plain JavaScript, `p.textContent = 1` changes the page on that line, so the next line can read 1 back. A setter does not change the page. It stores the next value, and the rest of the handler runs. React renders and commits only after the handler has finished. So a line right after `setCount(count + 1)` that reads the page still finds the old number. When the handler needs the new number, compute it once in a variable and give that variable to both the setter and the code that uses it, such as `send(next)`.
>
> *We should do this:*
> `const next = count + 1;`
> `setCount(next);`
> `send(next); // sends 1, the number the page will show`
>
> *We should not do this:*
> `setCount(count + 1);`
> `send(document.querySelector('p').textContent); // sends 0`

- [p] ★ Under the box: back to Leo's first handler. It logged `sending 0`, and the render logs for 1 printed after it, because React rendered and committed after `handleLike` returned. The fixed handler computes `next` once, passes it to `setLikes` and `sendLikeEvent`, and the server receives 1, then 2. Preview Q16: `likes` itself also still holds 0 on the line after the setter, and Lecture 16 explains why. ◼ Educational objective: verified fix; Preview Q16.

### Step 1: First, we lay out the story page <src/App.jsx>

```jsx title="App.jsx" startLine="1" continues="bottom"
import StoryTitle from './components/StoryTitle.jsx';
import LikeCounter from './components/LikeCounter.jsx';
export default function App() {
  console.log('App runs'); // logs only on the first render
```

```jsx title="App.jsx" startLine="5" continues="top"
  return (
    <main className="story-page">
      <StoryTitle title="Downtown Transit Accord" /> // beside the counter
      <LikeCounter /> // owns the like count
    </main>
  );
}
```

◼ **The what-this-introduces list:** 1. `console.log('App runs')`: shows when React calls `App`.

- [p] `App` holds no state, so no click in this page triggers a render of `App`. It runs once, after the first trigger. ◼ Educational objective: Principle 2 on the parent.

### Step 2: Next, we show the headline <src/components/StoryTitle.jsx>

```jsx title="StoryTitle.jsx"
export default function StoryTitle({ title }) {
  console.log('StoryTitle runs'); // logs only on the first render
  return <h1>{title}</h1>;
}
```

- [p] `StoryTitle` sits beside `LikeCounter`, not inside it, so a like never makes it run. Its single log line proves where a render stops. ◼ Educational objective: the sibling that shows the boundary of a re-render.

### Step 3: Then, we build the like counter <src/components/LikeCounter.jsx>

```jsx title="LikeCounter.jsx" startLine="1" continues="bottom"
import { useState } from 'react';
import LikeLabel from './LikeLabel.jsx';
import { sendLikeEvent } from '../analytics.js';
export default function LikeCounter() {
  const [likes, setLikes] = useState(0); // the state this component owns
  console.log('LikeCounter runs, likes =', likes);
```

```jsx title="LikeCounter.jsx" startLine="7" continues="both"
  function handleLike() {
    const next = likes + 1; // compute the new count once
    setLikes(next);
    sendLikeEvent(next); // sends the number the page will show
  }
```

```jsx title="LikeCounter.jsx" startLine="12" continues="top"
  return (
    <section className="like-counter">
      <LikeLabel likes={likes} />
      <button type="button" onClick={handleLike}>Like</button>
      <input placeholder="Write a comment" /> // keeps its text
    </section>
  );
}
```

- [p] The handler is the one place that changes the outside world, the server, and it uses `next`, not the page. The JSX passes `likes` down; nothing here touches a DOM node. ◼ Educational objective: Principles 1 and 4 in the finished file; purity recall.

### Step 4: Finally, we show the count <src/components/LikeLabel.jsx>

```jsx title="LikeLabel.jsx"
export default function LikeLabel({ likes }) {
  console.log('LikeLabel runs, likes =', likes);
  return <p className="like-count">{likes}</p>; // the commit changes this text
}
```

- [p] With all four files, the first render logs all four components; each like logs `LikeCounter` and `LikeLabel`, sends the new count, and leaves the comment in place. ◼ Educational objective: the finished loop.

### Glossary

- [glossary] Trigger ◼ The start of a screen update: the first `root.render` call or a setter call.
- [glossary] Render ◼ React calling component functions to get their JSX; the page does not change.
- [glossary] Commit ◼ React changing the DOM nodes so the page matches the new JSX.
- [glossary] DOM Node ◼ One object in the browser's page tree: an element or a piece of text.
- [glossary] Browser Paint ◼ The browser drawing the changed page on the screen after the commit.
