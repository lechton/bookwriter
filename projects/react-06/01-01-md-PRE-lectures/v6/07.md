### The Friction of Monolithic Prop Explosions

- [p] ★ {preknowledge: props passing, parameter destructuring, pure rendering contract} Think back to how you passed data into reusable components: you declared explicit key-value attributes on child tags, and React packed those attributes into an immutable props object. When a component displays a predictable set of fields, like a title and a reading time, explicit props establish a clean, self-documenting contract. But as an application grows, different pages and sections demand different visual layouts inside the same container frame. On The National Times, the morning editorial grid needs breaking bulletins with red alert badges, feature investigations with lead imagery, and opinion columns with author bylines. ◼ Educational objective: recall explicit props passing and establish the physical limitation of rigid field-based component signatures.
- [p] ★ {problem: adding props for every inner layout variation creates fragile, bloated components} To accommodate multiple visual permutations inside a single component, developers often add specialized boolean flags and string props like `hasBadge`, `badgeText`, `hasImage`, `imageUrl`, `hasByline`, and `buttonText`. As design requirements multiply, the component parameter list swells to twenty props, and the function body fills with nested ternary operators and conditional branches. Every time an art director requests a new badge placement or an alternate button style, engineers must open and modify the shared card file. This edits core shared code, risks regressing existing callers across the entire site, and creates an unmaintainable "mega-component" that no single team member fully understands. ◼ Educational objective: expose the architectural rot of layout-flag prop explosions.
- [p] ★ {old solution: rigid NewsCard with twenty layout-flag props} To see this anti-pattern in code, consider a monolithic card component attempting to satisfy multiple editorial designs through boolean layout flags:

- [code] Naive Layout-Flag Explosion:

```jsx title="Naive Layout-Flag Explosion"
function NewsCard({ title, hasBadge, badgeText, hasImage, imageUrl, authorName }) {
  return (
    <article className="news-card">
      {hasBadge && <span className="badge">{badgeText}</span>}
      <h3>{title}</h3>
      {hasImage && <img src={imageUrl} alt="" />}
      {authorName && <p className="byline">By {authorName}</p>}
    </article>
  );
}
```

◼ **The what-this-introduces list:** 1. `hasBadge`, `hasImage`: boolean layout flags coupling the container to specific child elements. 2. `badgeText`, `imageUrl`, `authorName`: scattered data props that belong to distinct inner elements rather than the card container itself. 3. Rigid internal order: fixed JSX hierarchy that prevents callers from reordering badges or nesting custom interactive controls.

- [p] ★ {mechanism: slot composition with children decouples container framing from inner content} To resolve this architectural bottleneck, React provides **slot composition** through the built-in **children prop**. Instead of forcing the container to anticipate every possible combination of badges, images, and text, the container provides an outer visual shell (such as borders, shadows, padding, and background colors) and leaves an open slot for nested content. The caller chooses whatever markup, headlines, badges, or buttons belong inside, nesting them directly between opening and closing tags. The container receives those nested elements under the standard prop name `children` and places `{children}` wherever that content belongs. This inverts control, keeping the container completely decoupled from caller layout variations. ◼ Educational objective: introduce slot composition via children as the architectural inversion of control that eliminates prop explosions.

### What is the Children Prop and How Does JSX Compile Slots?

- [p] ◇ {conceptual grounding: nesting native tags versus component slots} In standard HTML, nesting elements inside one another is the most fundamental way to build documents: you place an `<img>` and an `<h2>` inside an `<article>`, or an `<a>` inside a `<nav>`. In React, custom components support that exact same physical nesting syntax. When you write `<CardContainer><Headline /></CardContainer>`, you are not inventing a new language construct. You are passing `<Headline />` into `CardContainer` as an input. React automatically captures whatever markup appears between a component's opening and closing tags and delivers it to the component function under a reserved property name: `children`. ◼ Educational objective: connect component slot nesting to native HTML element containment.
- [p] ◇ {mathematical foundation: inversion of control and the slot hole model} The `children` prop implements the computer science principle of **inversion of control**. In a traditional monolithic component, the child function decides both the outer container structure and the inner visual details. With slot composition, that responsibility splits cleanly: the container component (`CardContainer`) decides where the content sits and how the outer boundary looks, while the calling component (`EditorialGrid`) decides what content is displayed. Think of `{children}` as an open physical hole or window inside the container's return statement. React simply takes the caller's nested elements and drops them into that hole during rendering. ◼ Educational objective: anchor the slot hole model and explain how inversion of control divides architectural responsibilities.
- [p] ◇ {syntactic decoding: props.children and destructured { children }} Because `children` is an ordinary key on the props object, a component can access it using standard property access (`props.children`) or unpack it directly in its parameter list using object destructuring: `function CardContainer({ children })`. Destructuring is the idiomatic standard across the React community because it clearly announces in the function signature that the component acts as a composable container. If the caller passes nothing between the tags, `children` evaluates to `undefined`, and React renders an empty slot without error. ◼ Educational objective: teach parameter destructuring for children and explain the empty slot baseline.
- [p] ★ {compiler transformation: nested JSX elements to props.children property} Under the hood, JSX tags do not exist as native browser markup. The JSX compiler transforms every JSX element into a `_jsx()` function call. When the compiler parses nested content inside custom component tags, it translates those nested elements into the `children` property of the props object. Writing `<CardContainer><Headline /></CardContainer>` compiles into `_jsx(CardContainer, { children: _jsx(Headline, {}) })`. Because `children` is compiled into the exact same props object as any regular attribute, it participates in standard React prop passing, subject to the same immutability guarantees and pure rendering contracts as any other prop. ◼ Educational objective: demystify the compiler translation that writes nested tags into props.children.

### Principles of React: Container Composition and Prop Spreading

- [p] ◇ When preparing for senior engineering interviews, candidates must explain how slot composition decouples container layout from inner content, why `children` is treated as an opaque element descriptor tree, and how JSX spread syntax forwards attributes cleanly without leaking component-only props. To master this architecture, we formalize the eight governing principles of container composition: ◼ Educational objective: frame the upcoming principles from the perspective of an engineering candidate preparing for technical evaluation.

> [!PRINCIPLE]
> **Principle 1: Read Nested JSX as the children Prop**
> When you place elements between a component's tags, React passes them to that component as a prop named **children**. React packages nested markup into the exact same props object as regular attributes. This allows a container to display dynamic content without hardcoding what that content must be.
> 
> >> children prop : a reserved property that receives any JSX elements or text nested between a component's tags
> 
> *It is best practice to do this:*
> `// Nested markup compiles into children prop`
> `<CardContainer>`
> `  <h2>Morning Dispatch</h2>`
> `</CardContainer>`
> 
> *Instead of doing this:*
> `// Passing markup through custom props`
> `<CardContainer`
> `  contentMarkup={`
> `    <h2>Morning Dispatch</h2>`
> `  }`
> `/>`

- [p] ★ Principle 1 operational derivation: In React, there is zero mechanical difference between an attribute passed in the tag head and elements nested between tags. When you inspect `props` inside `CardContainer`, you find a `children` key sitting right alongside any other passed props. Under the hood, the JSX compiler translates `<CardContainer><Headline /></CardContainer>` into `_jsx(CardContainer, { children: _jsx(Headline, {}) })`. Furthermore, if a caller mistakenly provides both an attribute and nested content, such as `<CardContainer children="attr">nested</CardContainer>`, the nested content wins because the compiler writes nested JSX into `props.children` after evaluating opening tag attributes. ◼ Educational objective: demonstrate compiler translation into props.children and verify attribute-versus-nested precedence.

> [!PRINCIPLE]
> **Principle 2: Place {children} Where the Slot Belongs**
> A container component must place **{children}** inside its returned JSX at the exact location where caller content belongs. If a container returns its own wrapper elements but omits `{children}`, React renders the outer frame and silently discards all nested caller markup without throwing a warning.
> 
> >> silent slot drop : failing to render nested children so caller markup disappears with zero console errors
> 
> *We should do this:*
> `// Places slot inside wrapper frame`
> `function CardContainer({ children }) {`
> `  return (`
> `    <div className="card">`
> `      {children}`
> `    </div>`
> `  );`
> `}`
> 
> *We should not do this:*
> `// Omits slot so nested content disappears`
> `function CardContainer({ children }) {`
> `  return (`
> `    <div className="card">`
> `      {/* Missing slot! */}`
> `    </div>`
> `  );`
> `}`

- [p] ★ Principle 2 operational derivation: When a container omits `{children}`, React renders the container's own elements (like `<div className="card">`) and silently drops the nested elements. Crucially, the component nested as a child never executes its function body. If `Headline` contains a `console.log('Headline rendered')`, that log never appears in the console. Because React operates on declarative element descriptors, it only executes child component functions if the parent's returned JSX actually mounts them. Restoring `{children}` instantly renders the child on screen and fires its execution log. ◼ Educational objective: prove that dropped children cause silent UI disappearance and halt child component execution.

> [!PRINCIPLE]
> **Principle 3: Treat Children as Descriptions, Not Rendered Output**
> The `children` prop contains **React element descriptors** created by the caller, not the rendered HTML output of those components. The container component executes first, receives lightweight objects describing what to render (`{ type: Headline, props: {} }`), and cannot inspect what the child will return.
> 
> >> element descriptor : a lightweight JavaScript object describing a component type and its props before rendering
> 
> *It is best practice to do this:*
> `// Treating children as descriptor`
> `function CardContainer({ children }) {`
> `  return (`
> `    <div className="card">`
> `      {children}`
> `    </div>`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `// Assuming children holds DOM nodes`
> `function CardContainer({ children }) {`
> `  // Not a DOM element: query fails`
> `  const el =`
> `    children.querySelector?.('h2');`
> `  return (`
> `    <div className="card">`
> `      {children}`
> `    </div>`
> `  );`
> `}`

- [p] ★ Principle 3 operational derivation: Many developers mistakenly believe that by the time `CardContainer` runs, its children have already rendered into DOM nodes. In reality, the caller creates element descriptors using `_jsx()`. When you log `children.type` inside `CardContainer`, you see the `Headline` function pointer itself, not an `<h2>` element. Furthermore, logging execution order reveals that `CardContainer` executes its function body before `Headline` executes. The container acts as a conduit for descriptors, never an inspector of rendered DOM output. ◼ Educational objective: establish the descriptor model and prove component execution order.

> [!PRINCIPLE]
> **Principle 4: Never Depend on the Shape of Children**
> Treat `children` as an **opaque data structure** and avoid reading `.length` or calling array methods directly on it. React passes a single nested child as a plain object, multiple children as an array, text as a string, and no children as `undefined`. Code calling `children.map()` crashes as soon as a caller nests a single element.
> 
> >> opaque data structure : a value whose internal shape varies and should not be directly inspected or iterated
> 
> *We should do this:*
> `// Renders opaque children whole`
> `function CardContainer({ children }) {`
> `  return (`
> `    <div className="card">`
> `      {children}`
> `    </div>`
> `  );`
> `}`
> 
> *We should not do this:*
> `// Calling array methods on children`
> `function CardContainer({ children }) {`
> `  // Crashes on single child element!`
> `  return children.map(`
> `    child => <div>{child}</div>`
> `  );`
> `}`

- [p] ★ Principle 4 operational derivation: If a caller nests two elements `<CardContainer><h2 /><p /></CardContainer>`, React sets `children` to an array, and `Array.isArray(children)` evaluates to `true`. But if another caller nests a single element `<CardContainer><h2 /></CardContainer>`, React sets `children` directly to that single element object to save memory overhead. Calling `children.map(...)` on a single child immediately throws a fatal runtime exception: `TypeError: children.map is not a function`. If a container needs to map over structured items, it should accept an explicit array prop instead of introspecting `children`. ◼ Educational objective: demonstrate shape-shifting children and prevent single-child array crashes.

> [!PRINCIPLE]
> **Principle 5: Compose Inner Layout Through Children Instead of Layout-Flag Props**
> When callers need different inner arrangements, let them nest the needed subcomponents directly inside the container instead of adding boolean flags to the container's parameter list. Keep a named prop only for a piece that the container itself must position, format, or guarantee across every instance.
> 
> >> component composition : assembling complex interfaces by nesting smaller, focused components together
> 
> *It is best practice to do this:*
> `// Callers compose custom inner markup`
> `<CardContainer>`
> `  <span className="badge">LIVE</span>`
> `  <h3>Election Update</h3>`
> `</CardContainer>`
> 
> *Instead of doing this:*
> `// Bloating container with boolean layout flags`
> `<CardContainer`
> `  hasLiveBadge={true}`
> `  title="Election Update"`
> `/>`

- [p] ★ Principle 5 operational derivation: In naive architectures, every new design variant forces developers to edit the shared container: adding `hasLiveBadge`, `isUrgent`, or `showByline`. In a composable architecture, `CardContainer` remains completely untouched. One caller nests an alert badge and a headline; another caller nests a headline and a byline; a third caller nests a simple paragraph. All three render through the exact same `CardContainer.jsx` file. The container owns the outer card frame, while callers own the composition of inner elements. ◼ Educational objective: prove that slot composition accommodates infinite layout permutations without modifying container code.

> [!PRINCIPLE]
> **Principle 6: Keep Spread for Pass-Through Wrappers**
> Use explicit props for data a component reads and uses in its own logic, and reserve JSX spread syntax (**{...rest}**) for generic pass-through wrappers that forward unconsumed attributes to a single underlying element. Overusing spread across application components obscures data dependencies and hides what props a child receives.
> 
> >> JSX spread syntax : forwarding an object of properties onto an element using {...props}
> >> pass-through wrapper : a component whose primary purpose is to style or wrap an underlying element while forwarding attributes
> 
> *It is best practice to do this:*
> `// Explicit props for consumed values`
> `<ArticleCard`
> `  title={story.title}`
> `  readTime={story.readTime}`
> `/>`
> 
> *Instead of doing this:*
> `// Hiding props with spread`
> `<ArticleCard {...story} />`
> `// (Hides what child actually reads)`

- [p] ★ Principle 6 operational derivation: The React documentation explicitly warns developers to use spread syntax with restraint. When an application component receives `{...story}`, a developer reading the call site cannot tell which properties `ArticleCard` actually requires or uses. If `story` contains database IDs, internal author notes, or deleted fields, all of those properties are blindly passed downward. Frequent spread in business components signals that the component should be split or refactored into composable slots. Spread belongs specifically in generic wrappers that forward native HTML attributes like `id`, `aria-label`, or event handlers. ◼ Educational objective: enforce the boundary between explicit data props and generic wrapper spread.

> [!PRINCIPLE]
> **Principle 7: Forward Only the Props You Did Not Consume**
> When a wrapper component consumes custom props of its own (such as `color` or `title`), destructure those props out of the parameter list and spread only the remaining **...rest** properties onto the underlying DOM element. Spreading the entire props object leaks component-only attributes to the DOM, triggering console warnings and invalid attributes.
> 
> >> rest properties : extracting unconsumed properties into a separate object using JavaScript rest syntax (...rest)
> >> DOM attribute leakage : passing non-standard custom attributes onto native browser elements
> 
> *We should do this:*
> `// Destructures consumed props`
> `function CardContainer({`
> `  color,`
> `  children,`
> `  ...rest`
> `}) {`
> `  return (`
> `    <div`
> `      className={`card card-${color}`}`
> `      {...rest}`
> `    >`
> `      {children}`
> `    </div>`
> `  );`
> `}`
> 
> *We should not do this:*
> `// Spreading full props leaks custom props to DOM`
> `function CardContainer(props) {`
> `  return (`
> `    <div className="card" {...props}>`
> `      {props.children}`
> `    </div>`
> `  );`
> `}`

- [p] ★ Principle 7 operational derivation: If a developer spreads the entire `props` object onto a native `<div>`, React attempts to apply every custom property to the DOM node. If `props` contains `isFeatured={true}`, React logs the development warning: `React does not recognize the isFeatured prop on a DOM element`. If it contains a boolean `featured={true}`, React logs: `Received true for a non-boolean attribute featured`. Worse, valid lowercase HTML attributes leak silently: a custom `kicker="Sport"` prop renders as `<div kicker="Sport">` in real DOM, and a custom `title` prop becomes an unintended browser hover tooltip. Destructuring `({ color, children, ...rest })` and spreading only `rest` ensures custom props are consumed while standard attributes like `aria-label` reach the DOM cleanly. ◼ Educational objective: prevent DOM attribute leakage by destructuring consumed props and spreading only rest.

> [!PRINCIPLE]
> **Principle 8: Order Attributes Around the Spread to Choose Defaults or Enforced Values**
> JSX evaluates attributes from left to right. An attribute written **before** `{...rest}` acts as an overridable default that caller props can replace, while an attribute written **after** `{...rest}` is enforced and overrides caller values. When merging class names, destructure `className = ''` and combine them explicitly to prevent caller classes from wiping the base style.
> 
> >> attribute precedence : the left-to-right evaluation order where later JSX attributes overwrite earlier ones
> >> class name merging : combining a wrapper's base CSS class with a caller's custom class name
> 
> *It is best practice to do this:*
> `// Merging base class with caller class`
> `function CardContainer({`
> `  className = '',`
> `  ...rest`
> `}) {`
> `  const base = 'card ' + className;`
> `  return (`
> `    <div`
> `      className={base.trim()}`
> `      {...rest}`
> `    />`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `// Static class before spread is lost`
> `function CardContainer(props) {`
> `  // If caller passes className="wide"`
> `  // base "card" class is overwritten!`
> `  return (`
> `    <div className="card" {...props} />`
> `  );`
> `}`

- [p] ★ Principle 8 operational derivation: Because JSX attributes merge left-to-right, writing `<div className="card" {...rest} />` means that if a caller passes `className="wide"`, the incoming attribute completely replaces `"card"`, stripping the component's foundation styles in the browser. Conversely, writing `<div {...rest} className="card" />` prevents callers from adding custom utility classes altogether. To achieve robust composition, the container destructures `className = ''` with an ES default fallback and explicitly merges both strings: ``className={`card ${className}`.trim()}``. Notice the `= ''` default: if omitted, an undefined caller class produces the broken string `"card undefined"` in the DOM. ◼ Educational objective: master JSX attribute evaluation order and implement safe class name merging with fallback defaults.

### Summary Reference: The Core Laws of Container Composition and Prop Spreading

| **PRINCIPLE**<br>(governing rule) | **INCORRECT PATTERN**<br>(anti-pattern / crash) | **IDIOMATIC REACT**<br>(resilient architecture) | **ENGINE RATIONALE**<br>(platform consequence) |
| :--- | :--- | :--- | :--- |
| **1. Children Prop** | Passing markup through custom props: `contentMarkup={...}` | Nesting elements between tags: `<Card><h2>...</h2></Card>` | JSX compiles nested tags into `props.children` alongside attributes |
| **2. Slot Placement** | Omitting `{children}` in container return markup | Placing `{children}` where content belongs: `<div>{children}</div>` | Without `{children}`, React renders container but silently drops caller markup |
| **3. Descriptor Model** | Treating children as rendered DOM nodes: `children.querySelector` | Treating children as opaque element descriptors: `{ type, props }` | Container runs before child components and cannot see their rendered output |
| **4. Shape Invariance** | Calling array methods on children: `children.map(...)` | Rendering `{children}` whole or passing an explicit array prop | Single child is an object, multiple are an array; `.map` crashes on single child |
| **5. Slot Composition** | Bloating container with boolean flags: `hasBadge`, `hasImage` | Letting callers nest arbitrary child markup inside open slot | Inverts control, keeping container code untouched across design updates |
| **6. Restrained Spread** | Overusing spread across domain components: `<Card {...props} />` | Naming explicit props; reserving `{...rest}` for pass-through wrappers | Explicit props document dependencies; uncontrolled spread hides received data |
| **7. Consumed Props** | Spreading full `props` onto DOM: `<div {...props}>` | Destructuring consumed props: `({ color, children, ...rest })` | Prevents unknown-prop console warnings and silent HTML attribute leaks |
| **8. Attribute Order** | Overwriting base class: `<div className="card" {...rest} />` | Merging classes with defaults: `` `card ${className}`.trim() `` | JSX applies attributes left-to-right; explicit merge preserves base styling |

### Step 1: First, we construct the slot-based container component <CardContainer.jsx>

- [p] ★ We construct the foundational container component `CardContainer.jsx` to establish the reusable visual frame for news dispatches. In monolithic component designs, containers accept dozens of boolean layout flags that dictate inner elements. In our composable architecture, `CardContainer` exposes an open slot by destructuring `children` from its parameter list. Notice how the parameter signature also unpacks `color = 'gray'` and `className = ''` with explicit ES parameter defaults, while collecting all remaining attributes into `...rest`. The component calculates a merged CSS class string and forwards `...rest` onto the root `<div>`. ◼ Meaningful pedagogical commentary: slot container definition, parameter destructuring with defaults, rest collection, and safe class merging.

- [code] CardContainer.jsx:

```jsx title="CardContainer.jsx"
export default function CardContainer({
  children, color = 'gray', className = '', ...rest
}) {
  const cls = `card card-${color} ${className}`.trim();
  return (
    <div className={cls} {...rest}>
      {children}
    </div>
  );
}
```

◼ **The what-this-introduces list:** 1. `CardContainer`: the reusable slot container. 2. `{ children, color = 'gray', className = '', ...rest }`: parameter destructuring isolating consumed props from pass-through attributes. 3. `cls`: pure local derivation merging base styles, color styles, and caller classes without `"undefined"` leakage. 4. `{...rest}`: attribute forwarding to the native DOM element. 5. `{children}`: the slot mounting caller-provided element descriptors.

### Step 2: Next, we assemble the composable editorial grid <EditorialGrid.jsx>

- [p] ★ We construct the caller component `EditorialGrid.jsx` to organize the morning dispatches. When building complex grid layouts, developers encounter a classic architectural crossroad: whether to use a monolithic card component loaded with specialized boolean props, or use slot composition with `children` to let each call site compose its own markup. ◼ Meaningful pedagogical commentary: caller orchestration, composing diverse cards, introducing the composition crossroad.
- [p] ◇ When designing a component that supports multiple visual permutations, you face an architectural crossroad:
  - **Option 1 (The Monolithic Prop Explosion Way)**: Pass data through dozens of specialized props (`hasBadge`, `badgeText`, `authorName`) and rely on complex internal conditional branches inside the card.
  - **Option 2 (The Slot Composition Way)**: Let the container expose `{children}` and allow callers to nest whatever headlines, badges, or bylines each story demands.
- [code] Option 1: The Monolithic Prop Explosion Way:

```jsx title="Option 1: The Monolithic Prop Explosion Way"
function RigidNewsCard({ title, hasBadge, badgeText, author }) {
  return (
    <div className="card">
      {hasBadge && <span className="badge">{badgeText}</span>}
      <h3>{title}</h3>
      {author && <span className="byline">By {author}</span>}
    </div>
  );
}
```

### Glossary

- [glossary] Children Prop ◼ A reserved React property that automatically receives any JSX elements or text passed between a component's opening and closing tags.
- [glossary] Slot Composition ◼ An architectural design pattern where a container component defines visual boundaries and leaves open slots for caller-provided content.
- [glossary] Inversion of Control ◼ A design principle where the calling component chooses what inner content to render, while the container decides where and how that content is framed.
- [glossary] JSX Spread Syntax ◼ A syntax pattern using `{...props}` or `{...rest}` to forward an object of properties onto an underlying JSX element.
- [glossary] Opaque Data Structure ◼ A data representation whose internal shape varies (such as children being an object, array, string, or undefined) and should not be directly inspected or iterated over.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Slot Composition with Children

➔ ALWAYS nest markup inside component tags and place `{children}` in the returned JSX to decouple container styling from inner content.

➔ NEVER call array methods like `children.map()` directly on `children`, because React passes single elements as plain objects and multiple elements as arrays.

❒ Controlled Prop Spreading

➔ ALWAYS destructure the props a component consumes (`{ color, children, ...rest }`) and spread only `...rest` onto native DOM elements.

➔ NEVER spread the entire `props` object onto a DOM element when the component accepts custom props, preventing invalid attribute warnings and DOM leakage.

❒ Attribute Precedence & Defaults

➔ ALWAYS place overridable default attributes before `{...rest}` and enforced attributes after `{...rest}` in JSX element declarations.

➔ ALWAYS destructure `className = ''` with an ES parameter default and merge classes explicitly to prevent caller classes from wiping base styles.

**DO THIS:** compose inner layout with children and merge class names explicitly

```jsx right
function CardContainer({ children, className = '', ...rest }) {
  return (
    <div className={`card ${className}`.trim()} {...rest}>
      {children}
    </div>
  );
}
```

**DO NOT DO THIS:** bloat containers with boolean flags and spread unconsumed props

```jsx wrong
function CardContainer(props) {
  return (
    <div className="card" {...props}>
      {props.hasBadge && <span>Badge</span>}
      <h3>{props.title}</h3>
    </div>
  );
}
```

- [comparison-table]
| | **MONOLITHIC LAYOUT PROPS**<br>(Rigid Mega-Card) | **SLOT COMPOSITION**<br>(Composable Container) |
| ---: | :--- | :--- |
| **Architectural Model** | Container dictates both outer chrome and all inner element positions | Inversion of control; container frames open slot `{children}` |
| **API Complexity** | Parameter explosion: dozens of boolean flags (`hasBadge`, `hasImage`) | Lean interface: accepts `{ children }` plus styling configuration |
| **Caller Permutations** | Rigidly constrained to combinations pre-programmed inside container | Infinite permutations: caller nests any arbitrary JSX hierarchy |
| **Shared Code Risk** | Every new layout design requires editing and testing shared card file | Zero edits to container; new layouts composed entirely at call site |
| **Attribute Handling** | Blindly spreads full props or scatters manual attribute mappings | Destructures consumed props; forwards only `...rest` to DOM node |
| **Class Name Strategy** | Replaces base styles or ignores caller classes on spread collisions | Merges base and caller classes with fallback default `className = ''` |
| **Prevented Bug Class** | Prop explosion, attribute leakage, and broken layout regressions | Rigid coupling, console DOM warnings, and single-child array crashes |
