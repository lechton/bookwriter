### The Mystery of the Dual Click and the Vanishing Form

- [p] ★ {preknowledge: event handlers as function references, callback props, button elements, component rendering} In the previous lesson, you learned that React event handlers are functions passed as values to event props like `onClick`. You saw that passing a bare function reference (`onClick={handleClick}`) defers execution until the user clicks, whereas invoking a function inside JSX braces runs it immediately during render. You also learned that child components use callback props to notify parents of user interactions. However, real-world user interfaces rarely feature isolated, single-level buttons. In modern web applications, interactive buttons often live inside larger clickable containers, such as an action button nested inside an article card. Furthermore, users type continuous text into input fields and submit forms to filter content. In traditional browser scripting, developers attached event listeners directly to DOM elements and relied on browser events bubbling up the document tree. When engineers transition to React, they often assume event handlers operate in complete isolation. When an engineer clicks a "Bookmark" button nested inside an article card, both the bookmark action and the card's navigation handler execute in rapid succession. Even worse, when a user submits a search form, the browser suddenly flashes white and reloads the entire page, wiping away all client memory and whatever text the user had just typed. ◼ Educational objective: connect handler function references from Lecture 13 to nested UI hierarchies while exposing the double-execution defect of event bubbling and the memory-erasing defect of unprevented form submissions.
- [p] ★ {problem: unwanted parent handler execution from event bubbling and full-page reloads on form submit} It is possible that a developer may create a clickable article card with `onClick={openArticle}` and place a Bookmark button inside it with `onClick={saveBookmark}`. When the user clicks the Bookmark button, the browser executes `saveBookmark`, but immediately afterward it executes `openArticle`. The user wanted only to save the story for later reading, but the application abruptly opens the story reader. The second operational trap happens in text search forms. When a user presses Enter inside an `<input>` wrapped in a `<form>`, the native browser behavior intercepts the submit event and attempts to navigate to the form's action URL. Because no server action URL is defined, the browser issues an HTTP GET request to the current page. The application reloads completely, clearing all memory variables and resetting the input field to an empty string before React can process the search query. ◼ Educational objective: analyze the operational failure where unstopped event propagation cascades into ancestor handlers and native form submissions erase client state via full-page reloads.
- [p] ★ {old solution: relying on automatic DOM bubbling or manual window event interception} In classic web development, engineers either allowed events to bubble up uncontrollably through the document or wrote imperative `window.event` scripts to cancel navigation. In React, events are handled declaratively through a cross-browser event object passed directly into handler functions, providing dedicated methods to halt upward bubbling and cancel native browser defaults. ◼ Educational objective: contrast fragile legacy event handling with React declarative event object methods.

  }
  return (

- [p] ★ {mechanism: the React event object, currentTarget, stopPropagation, and preventDefault} React solves these problems by providing every event handler with a standardized **React event object**. When an interaction occurs, React wraps the native browser event in a cross-browser wrapper that conforms to the W3C DOM standard. This event object is passed as the first argument (conventionally named `e`) to your handler function. The event object contains two distinct element references: `e.currentTarget` refers to the element that owns the running handler (such as your `<article>` card), while `e.target` refers to the innermost element the user physically touched (such as an icon or headline). To prevent an event from bubbling up to parent containers, the event object provides `e.stopPropagation()`. Calling `e.stopPropagation()` inside the Bookmark button's handler ensures that only the bookmark action executes, keeping the parent card's handler silent. To prevent the browser from reloading the page during a form submission or link click, the event object provides `e.preventDefault()`. Calling `e.preventDefault()` halts the browser's native submission behavior, allowing your JavaScript handler to process the search query cleanly without refreshing the window. ◼ Educational objective: establish the core mechanisms of the React event object, distinguishing currentTarget from target and stopPropagation from preventDefault.

### The React Event Object and the Native DOM Boundary

- [p] ◇ {conceptual grounding: the synthetic event wrapper and cross-browser consistency} To master event handling in React, we must understand the object that arrives in our handlers. When a user clicks, types, or submits, the browser generates a native DOM event. Different browsers historically implemented event properties with subtle inconsistencies. React normalizes these differences by wrapping the browser event in a **React event object**, also known in the React community as a synthetic event. This object exposes standard W3C properties like `target`, `currentTarget`, `bubbles`, and `timeStamp`, and provides identical behavior across Chrome, Safari, Firefox, and Edge. If you ever need to inspect the underlying browser event directly, React exposes it through `e.nativeEvent`. ◼ Educational objective: ground the React event object in native DOM events and explain cross-browser normalization.
- [p] ★ {runtime distinction: target versus currentTarget} A frequent source of subtle bugs is confusing `e.target` with `e.currentTarget`. Imagine an article card containing an `<h3>` headline and a `<span>` icon. You attach an `onClick` handler to the outer `<article>` tag and store the article identifier in `data-id`. If the user clicks directly on the icon, `e.target` points to the `<span>` element. If your handler reads `e.target.dataset.id`, it returns `undefined` because the `<span>` does not have that dataset attribute. In contrast, `e.currentTarget` always points to the element that owns the running handler, which is the `<article>` tag. To read attributes reliably from the element that registered the listener, you must always read `e.currentTarget`. ◼ Educational objective: contrast e.target with e.currentTarget and explain why dataset lookups fail on nested elements.
- [p] ★ {text input timing: onChange per keystroke versus native change on blur} In native HTML and plain JavaScript, an `<input>` dispatches two separate events: `input` fires on every keystroke, while `change` fires only after the user unfocuses or tabs away from the field. React simplifies this model. In React, the `onChange` prop fires immediately on every character typed or deleted, mirroring the native `input` event. The current text is always available through `e.target.value`. If you need an event that waits until the user leaves the input, attach your handler to `onBlur` instead. ◼ Educational objective: clarify that React's onChange fires per keystroke rather than on blur, demonstrating how to read e.target.value.
- [p] ★ {propagation lifecycle: capture phase, target, and upward bubbling} When an event occurs, it travels through three distinct phases: first, it descends from the root of the document down to the target element during the **capture phase**; second, it reaches the clicked element; third, it ascends back up through every ancestor during the **bubble phase**. In React, standard JSX props like `onClick` listen during the bubble phase. All events bubble upward through ancestor handlers, with one notable exception: the `onScroll` event does not bubble, firing strictly on the element being scrolled. ◼ Educational objective: deconstruct the three phases of event propagation and identify the onScroll bubbling exception.

### Principles of React: Event Handlers, Propagation, and Default Actions

- [p] ◇ In technical interviews, senior candidates must articulate where side effects belong, how the React event object resolves targets, why onChange fires on every keystroke, how event bubbling travels through ancestor components, and how to stop bubbling and browser defaults cleanly. > [!PRINCIPLE]
> **Principle 1: Put Side Effects in Event Handlers, Never in the Component Body**
> Event handlers provide a safe home for side effects, keeping them out of the pure component rendering calculation:
>
> - **The Component Body (`ArticleCard`):** runs synchronously during render to calculate and return JSX markup.
> - **The Event Handler (`handleBookmark`):** runs asynchronously only when the user triggers an interaction, such as clicking a button.
>
> Placing side effects such as network requests, analytics logging, or storage writes in the component body causes them to execute on every render before the user has touched anything.
>
> >> side effect : work that changes something outside the component, such as a network request, storage write, or log entry
> >> component body : the top-level function scope executed synchronously during render to calculate JSX

- [p] ★ Principle 1 operational derivation: In Lecture 12, you learned that React components must remain pure calculations that return JSX without modifying external variables. The component body executes every time React renders, and in development under StrictMode, React invokes the function body twice to detect unintended side effects. If you place a network request, analytics log, or storage write directly inside the component body, that operation fires twice on page load and repeats every time the component re-renders. Event handlers exist specifically to house side effects. Because an event handler is stored as a function reference during render and called only when the user physically clicks, types, or submits, it is completely free from the purity restrictions of the render phase. An event handler may safely log analytics, send HTTP requests, write to browser storage, and later update application state without disrupting component rendering. ◼ Educational objective: derive why event handlers are the designated home for side effects and contrast render-time purity with interaction-time execution.

- [code] Side Effects in Event Handlers:

  console.log("Render card:", title); // Double-called in StrictMode
  function handleBookmark() {
    console.log("Saved bookmark:", title); // Runs strictly on click
  }
  return <button onClick={handleBookmark}>Save {title}</button>;
}
```

> [!PRINCIPLE]
> **Principle 2: Read CurrentTarget for the Listening Element and Target for What Was Touched**
> When a user interacts with your interface, the React event object gives you two different element references:
>
> - **`e.currentTarget` (The Listener):** the element to which the active event handler is attached, such as the parent `<article>` card.
> - **`e.target` (The Trigger):** the innermost element where the user interaction physically started, such as a nested `<span>` label or `<svg>` star icon.
>
> Reading dataset identifiers or attributes from `e.target` instead of `e.currentTarget` returns undefined whenever the user clicks an icon or nested label inside your listening container.
>
> >> e.currentTarget : the element to which the running event handler is attached
> >> e.target : the deepest element where the user interaction physically started

- [p] ★ Principle 2 operational derivation: When a user clicks a button or article card, they rarely click an empty boundary; they click a headline, a paragraph, or a decorative icon nested inside. The browser's hit-testing algorithm determines the deepest element under the cursor and assigns it to `e.target`. The event then bubbles upward until it reaches an element with a registered listener, which React assigns to `e.currentTarget`. If you attach an `onClick` handler to an `<article data-id="101">` container, clicking the card's nested `<span>★</span>` sets `e.target` to the `<span>` and `e.currentTarget` to the `<article>`. An engineer who writes `e.target.dataset.id` receives `undefined` because the `<span>` holds no `data-id`. In contrast, `e.currentTarget.dataset.id` reliably returns `"101"`. Whenever you need properties of the element that owns the handler, read `e.currentTarget`. ◼ Educational objective: analyze the operational distinction between event target and currentTarget, demonstrating why dataset lookups fail on nested children.

    - Step 5, the technical words: `onChange` and `onBlur` are both standard and appear in the definition and marginal glosses.
    - Step 6, the title: Expect OnChange to Fire on Every Keystroke Rather Than on Blur.

> [!PRINCIPLE]
> **Principle 3: Expect OnChange to Fire on Every Keystroke Rather Than on Blur**
> React normalizes input events so that the `onChange` prop reports every value change immediately rather than waiting for the field to lose focus:
>
> - **React's `onChange` (Per Keystroke):** fires on every character typed, pasted, or deleted, providing the current input value in `e.target.value`.
> - **Native DOM `change` (On Blur):** fires only after the user commits a change by unfocusing or tabbing away from the input field.
>
> Assuming `onChange` waits for the user to leave the field causes validation, filtering, or network searches to run on every single keystroke.
>
> >> onChange : a React event prop that fires immediately on every user keystroke or input value change
> >> onBlur : a React event prop that fires only when a form element loses keyboard focus

- [p] ★ Principle 3 operational derivation: In the native browser DOM, the `change` event on an `<input>` element does not fire while the user is typing; it waits until the user presses Enter or clicks outside the field to commit the change. To capture keystrokes live, native DOM developers had to listen to the `input` event. React unifies this behavior: on React `<input>`, `<textarea>`, and `<select>` elements, the `onChange` prop is wired to the browser's live input dispatch. Typing the letters "a" then "b" into a search box triggers `onChange` twice: first with `e.target.value` equal to `"a"`, and second with `e.target.value` equal to `"ab"`. Inspecting `e.nativeEvent.type` confirms that the underlying browser event is an `input` event. If an engineer designs an expensive search filter assuming `onChange` runs once after the user finishes typing, the search fires on every keystroke. To execute logic only after the user leaves the input, attach your handler to `onBlur` instead. ◼ Educational objective: explain how React unifies onChange with native input events, demonstrating that e.target.value updates on every keystroke.

- [code] Typing with OnChange:

    console.log("Event type:", e.nativeEvent.type); // Native browser input

  return (

  );
}
```

◼ **The what-this-introduces list:** 1. `onChange`: React event prop capturing live keystrokes. 2. `e.target.value`: current string value of the input element. 3. `e.nativeEvent.type`: property revealing the underlying browser `input` event.

    - Step 1, the decision: account for upward event bubbling when designing interactive elements inside clickable containers.
    - Step 2, the shape: bullets, because the reader must distinguish the child click handler from ancestor click handlers in the propagation path.
    - Step 3, the names: Child Click Handler (`BookmarkButton`), Ancestor Click Handler (`ArticleCard`).

> [!PRINCIPLE]
> **Principle 4: Expect Events to Bubble Up Through Every Ancestor Handler**
> Browser events travel through the component tree, running handlers on nested elements before bubbling upward to their parent containers:
>
> - **Child Click Handler (`BookmarkButton`):** runs first at the element where the user initiated the click.
> - **Ancestor Click Handler (`ArticleCard`):** runs subsequently as the event bubbles up the DOM hierarchy toward the document root.
>
> Placing an action button inside a clickable card without stopping bubbling causes the card's navigation handler to execute right after the button's action fires.
>
> >> event bubbling : the upward propagation of an event from the innermost target through every ancestor handler
> >> capture phase : the downward travel of an event through capture handlers before reaching the target element

- [p] ★ Principle 4 operational derivation: When a user clicks an element, the browser does not notify only that single element. Instead, the event begins at the document root, descends through ancestor elements during the capture phase, reaches the target, and then ascends back up through every ancestor during the bubble phase. In React, JSX event props like `onClick` listen during the bubble phase. If you render a `<button>` inside an `<article onClick={openCard}>`, clicking the button runs the button's `onClick` handler first, and then immediately runs the `<article>`'s `onClick` handler. If the `<article>` is wrapped in a `<main onClick={trackSection}>`, the section handler runs third. All events in React bubble up the tree, with the single exception of `onScroll`, which fires only on the specific JSX tag being scrolled. If you ever need to intercept an event before child handlers run, you can attach a capture listener like `onClickCapture`, which executes on the downward descent. ◼ Educational objective: analyze the mechanics of event bubbling across component hierarchies and identify the onScroll exception.

> [!PRINCIPLE]
> **Principle 5: Stop Event Propagation Where a Child Action Must Stay Local**
> When an action inside a container has its own independent purpose, stop the event from continuing up the component tree:
>
> - **`e.stopPropagation()` (Local Containment):** halts the event's upward journey immediately, preventing parent ancestor handlers from running.
> - **Explicit Callback Call (`onBookmark(id)`):** invokes a specific parent handler directly through props when the parent still needs to be notified.
>
> Failing to call `e.stopPropagation()` inside nested action buttons allows clicks to bubble up, triggering unintended container selections or unwanted page transitions.
>
> >> e.stopPropagation : a method on the event object that prevents ancestor handlers from receiving the event
> >> explicit callback invocation : directly calling a parent prop function inside a child handler rather than relying on automatic event bubbling

- [p] ★ Principle 5 operational derivation: In complex user interfaces, nested controls often have completely different meanings from their surrounding containers. An article card may navigate to the full story when clicked, while a Bookmark button inside that card saves the story to local reading lists. Because clicks bubble up by default, clicking Bookmark opens the story unless propagation is explicitly halted. Calling `e.stopPropagation()` on the React event object tells React to stop walking up the component tree. No ancestor click handlers will run for that event. However, what if the parent component still needs to know that a bookmark action occurred? The solution is not to let the click bubble up blindly; the professional pattern is to call `e.stopPropagation()` to stop raw DOM bubbling, and then explicitly invoke a callback prop passed down from the parent: `onBookmark(article.id)`. This pattern keeps event propagation contained while making the line of communication between child and parent explicit, readable, and easy to trace. ◼ Educational objective: demonstrate how e.stopPropagation halts bubbling and explain why explicit callback props provide a superior alternative to relying on DOM bubbling.

}

> [!PRINCIPLE]
> **Principle 6: Prevent the Browser Default Action When React Handles the Event**
> Certain native HTML elements trigger built-in browser actions that must be intercepted when your JavaScript handles the interaction:
>
> - **`e.preventDefault()` (Browser Action Cancel):** cancels native browser behaviors, such as form submissions reloading the page or link clicks navigating to a URL.
> - **`e.stopPropagation()` (Ancestor Handler Cancel):** halts event bubbling to parent containers without affecting the browser's default action.
>
> Submitting a search form without calling `e.preventDefault()` causes the browser to reload the entire page, clearing all client memory and erasing what the user typed.
>
> >> e.preventDefault : a method on the event object that halts native browser actions like page reloads
> >> browser default action : native browser behavior triggered by an event, such as navigation or form submission

- [p] ★ Principle 6 operational derivation: HTML elements were designed decades before single-page JavaScript applications existed. Built-in elements carry native behaviors: submitting a `<form>` issues a network request and reloads the page; clicking an `<a href="/story">` navigates to a new document; right-clicking opens a context menu. When building React applications, you want JavaScript to handle user interactions on the current page without the browser performing a full-page reload that destroys client memory. Calling `e.preventDefault()` instructs the browser to suppress its built-in default behavior. A common mistake among junior developers is confusing `e.stopPropagation()` with `e.preventDefault()`. Calling `e.stopPropagation()` stops parent handlers from receiving the event, but it does nothing to prevent the browser from reloading the page. Conversely, calling `e.preventDefault()` prevents the page from reloading, but allows the event to continue bubbling up to ancestor components. Whenever React handles form submission or custom navigation, call `e.preventDefault()` at the start of your handler. ◼ Educational objective: derive the purpose of e.preventDefault in single-page applications and contrast it with e.stopPropagation.

### Glossary

- [glossary] React Event Object ◼ A normalized cross-browser wrapper around native browser events that provides standard properties like target and currentTarget across all platforms.
- [glossary] Event Bubbling ◼ The natural upward propagation of a DOM event starting at the innermost clicked element and ascending through every ancestor component handler.
- [glossary] e.currentTarget ◼ The DOM element to which the currently executing event handler is attached in the React component tree.
- [glossary] e.target ◼ The deepest DOM element where the user interaction physically occurred, which may be a child of currentTarget.
- [glossary] e.stopPropagation ◼ A method on the React event object that halts upward event bubbling, preventing ancestor handlers from receiving the event.
- [glossary] e.preventDefault ◼ A method on the React event object that cancels native browser default actions, such as form submit reloads and link navigation.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Side Effects and Render Purity

➔ ALWAYS place side effects like network requests, storage writes, and analytics logging inside event handlers, never in the component body.

➔ IF you need live text input updates THEN use React's `onChange` prop to read `e.target.value` on every keystroke.

❒ Event Target Resolution

➔ ALWAYS read `e.currentTarget` when you need attributes or datasets from the element holding the event handler.

➔ NEVER assume `e.target` is the container holding the handler, because users often click nested child icons or labels.

❒ Event Propagation & Browser Defaults

➔ ALWAYS call `e.stopPropagation()` inside nested action buttons when their click must not trigger parent card navigation.

➔ ALWAYS call `e.preventDefault()` on form submit handlers to prevent the browser from reloading the page and clearing client memory.

**DO THIS:** stop bubbling and prevent default page reloads explicitly

```jsx right title="Explicit Event Containment"
function ActionControl({ onSave }) {
  function handleClick(e) {
    e.stopPropagation();
    onSave();
  }
  return (
    <button type="button" onClick={handleClick}>
      Save
    </button>
  );
}
```

**DO NOT DO THIS:** allow clicks to bubble into parent container handlers

```jsx wrong title="Unstopped Bubble Cascade"
function ActionControl({ onSave }) {
  return (
    <button type="button" onClick={onSave}>
      Save
    </button>
  );
}
```

| | **EVENT BUBBLING**<br>(propagation) | **DEFAULT ACTIONS**<br>(browser navigation) |
| ---: | :--- | :--- |
| **Trigger Mechanism** | Event travels upward through parent component hierarchy | Browser executes built-in behaviors like form page reloads |
| **Cancellation Method** | Call `e.stopPropagation()` on the React event object | Call `e.preventDefault()` on the React event object |
| **Failure Consequence** | Parent container handlers execute unexpectedly | Whole page reloads and clears client memory |
| **Primary Target** | Nested action buttons inside clickable cards | Form submission and navigation links |
| **Component Benefit** | Keeps child interactions strictly local | Preserves single-page state and form text |
