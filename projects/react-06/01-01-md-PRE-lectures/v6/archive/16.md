### The Friction of Ephemeral Local Variables

- [p] ★ {preknowledge: component functions, JSX return, pure rendering, event handlers} Every user interface exists to present information and respond to reader interactions. In earlier lessons, you learned that React components are functions that execute and return JSX markup. A component function runs from top to bottom, calculates its output, and finishes execution. When the function returns, its local variables disappear from active memory. However, interactive features like like counters and bookmark buttons need to remember information across clicks. Beginners often try to track this data using regular JavaScript variables declared inside the component, such as `let likes = 0`. While the variable can be modified inside an event handler, changing it never updates what the reader sees on the screen. ◼ Educational objective: recall component functions as executable units while exposing the fundamental limitation of local variables for interactive state.
- [p] ★ {problem: local variables reset on every render pass and fail to notify React} When a developer writes `let likes = 0` inside a component function, two distinct problems prevent the screen from updating. First, local variable changes do not trigger renders: when the user clicks the button and executes `likes = likes + 1`, the number increments in JavaScript memory, but React receives no signal that data changed. The screen remains frozen at "Like (0)". Second, local variables do not persist between renders: whenever an outside update or parent re-render causes React to call the component function again, the function starts from line 1 and declares `let likes = 0` afresh. Any value stored during a previous call is permanently lost. ◼ Educational objective: deconstruct the two operational failures of local variables: lack of render triggering and failure to persist across calls.
- [p] ★ {old solution: mutating local variables or assigning to module-level variables} To work around this issue, a junior developer may try assigning to a module-level variable outside the component function. While a module variable survives function calls, mutating it still fails to notify React to re-render the screen. Worse, if multiple story cards are rendered on the page, they all share that same single module variable, causing one card's click to overwrite data for every other card. React requires a dedicated mechanism that both retains private data across renders and automatically schedules screen updates when values change. ◼ Educational objective: explain why module-level variables fail and establish the necessity of React-managed component memory.

- [code] Naive Local Variable Execution Attempt:

```jsx title="Naive Execution Attempt"
function StoryCard() {
  let ~likes~ = 0; // Local variable created fresh on each call
  function handleLike() {
    likes = likes + 1;
    console.log(~'likes:', likes~); // Logs count while screen stays frozen
  }
  return (
    <button onClick=~{handleLike}~>Like ({likes})</button>); // UI never updates
}
```

◼ **The what-this-introduces list:** 1. `let likes = 0`: ephemeral local variable reset on every function execution. 2. `handleLike`: local click handler modifying unobserved local memory. 3. `console.log(...)`: observable divergence where the console logs incremented values while the screen stays frozen.

- [p] ★ {mechanism: component memory with useState} React solves this challenge by providing **component memory** through the `useState` hook. When you declare `const [likes, setLikes] = useState(0)`, React allocates a private memory cell for that specific component instance outside the function. The `useState` hook returns two values: the current state value to read during this render, and a **setter function** (`setLikes`). Calling the setter stores the new value in React's external memory cell and tells React to schedule a re-render. When React re-renders the component, it calls the function again, retrieves the updated value from memory, and paints the new count on screen. ◼ Educational objective: introduce useState as the mechanism providing external persistent storage and automated re-render scheduling.
- [grounding] [!] Grounding card: Why did changing the like counter leave the screen stuck? ◼ Opening question: Why did changing the like counter leave the screen stuck? ◼ Friction target: Developers attempting to use local variables discover that increments fail to update the DOM and reset on future renders. ◼ Tactile scene: A developer clicks the Like button three times; the browser console logs "likes is now 1", "likes is now 2", and "likes is now 3", but the button text stubbornly shows "Like (0)"; when an unrelated state update occurs, the count resets to 0. ◼ Bold key terms: **local variable**, **component memory**, **re-render**, **useState**, **setter function**. ◼ Operational resolution: Local variables belong to a single function execution; to persist values across renders and notify React to update the DOM, use the `useState` hook, which stores state outside the component function and triggers a re-render when its setter is called.

### Component Memory and the Mechanics of useState

- [p] ◇ {conceptual grounding: what is state and why components need memory} In React, data that changes over time and determines what appears on screen is called **state**. Think of a component's state as its personal notebook or memory shelf. While props represent incoming data passed down from a parent, state represents private data that the component owns, remembers, and updates itself. When a reader clicks a like button, expands an article summary, or checks a bookmark toggle, the component must remember that decision even after its rendering function finishes running. ◼ Educational objective: define state as internal, persistent component memory and contrast it with incoming props.
- [p] ★ {engine mechanics: how React stores state outside the component function} To understand how `useState` remembers, we must look at where state lives. When you run a plain JavaScript function, local variables live on the call stack and vanish when the function returns. React solves this by keeping state outside your component function altogether. React holds an internal record, like a shelf in memory, tied to your component's exact position in the user interface tree. When your component calls `useState(0)`, React checks its shelf: if this is the first time the component is rendering, React places `0` on the shelf; if the component is re-rendering, React ignores the `0` and hands back the latest value stored on the shelf. ◼ Educational objective: explain the engine mental model of state stored externally on a shelf associated with tree position.
- [p] ★ {syntactic reminder: array destructuring syntax and setter naming convention} Let us look at the syntax of `useState`: `const [likes, setLikes] = useState(0)`. Because this is the first time we use this syntax in our curriculum, let us review **array destructuring**. In JavaScript, array destructuring is a convenient shorthand that unpacks values from an array into distinct variables. Calling `useState(0)` returns an array containing exactly two items: the first item is the current state value, and the second item is the setter function. Writing `[likes, setLikes]` assigns the first item to a constant named `likes` and the second item to a constant named `setLikes`. By community convention, if your state is named `something`, the setter is always named `setSomething`. ◼ Educational objective: review array destructuring syntax and establish the standard setter naming convention.
- [p] ★ {initial render vs re-renders: initial value is used only once} A common point of confusion for beginners is the initial argument passed to `useState`. In `useState(0)`, the number `0` is the **initial state**. React uses this initial value strictly during the component's initial render. On subsequent renders, React already has the current value stored in its memory cell, so it completely ignores the argument passed to `useState`. The code `useState(0)` continues to execute on every render pass, but it acts as a retrieval lookup rather than a variable reset. ◼ Educational objective: clarify that the initial argument to useState is evaluated on every call but used only on the first render pass.
- [p] ◇ {vocabulary: what is a Hook and the top-level execution rule} In React, functions whose names start with the word `use` are called **Hooks**. Hooks are special functions that allow your component to connect to React framework features like state and lifecycle tracking. Because React relies on the exact order in which Hooks are called to match each state variable to its storage cell, you must always call Hooks at the top level of your component function. Never call `useState` inside loops, conditions, or nested functions. ◼ Educational objective: define React Hooks and introduce the top-level invocation requirement.

### Principles of React: Component Memory with useState

- [p] ◇ Senior technical interviews test whether an engineer truly understands how React coordinates state, renders, and memory. Interviewers frequently ask: "Why do ordinary variables forget their values between renders, and how does useState remember?" To answer with precision and authority, we formalize the six governing principles of component memory: ◼ Educational objective: frame the six operational principles of useState from the perspective of an engineering candidate preparing for a senior technical interview.

> [!PRINCIPLE]
> **Principle 1: Expect a Local Variable to Forget, and to Change Nothing on Screen**
> Every render is a new call of the component function, so a local variable is created fresh by each call. Assigning to it inside a handler changes only that single call's copy in memory. React receives no update signal, and the next render pass starts the variable again from its initial declaration.
> 
> >> local variable : a variable declared inside a function whose lifetime ends when the function returns
> >> re-render : a new execution of a component function triggered by state or prop changes

- [p] ★ Principle 1 operational derivation: When a user clicks a button tied to a local variable `let likes = 0`, the handler executes `likes = likes + 1`. The variable in JavaScript memory increments to 1, 2, and 3, which can be verified with `console.log`. However, React does not monitor variable assignments. Because no state setter was called, React schedules no render pass, leaving the DOM untouched at "Like (0)". Furthermore, if an unrelated state update (such as a working save toggle) causes the component to re-render, React executes the component function from the top. The statement `let likes = 0` runs again, wiping previous local mutations and resetting the counter back to 0. ◼ Educational objective: derive the dual failure of local variables: invisible mutations that trigger no renders, and unavoidable resets on future render passes.

- [code] Local Variable Reset Proof:

```jsx title="Local Variable Reset Proof"
function StoryCard() {
  let ~likes~ = 0; // Local variable allocated on every render
  function handleLike() {
    likes = likes + 1;
    console.log(~'likes:', likes~); // Increments in memory but DOM stays stuck
  }
  return (
    <button onClick=~{handleLike}~>Like ({likes})</button>); // Frozen on 0
}
```

◼ **The what-this-introduces list:** 1. `let likes = 0`: local variable re-instantiated on every call. 2. `handleLike`: click handler mutating local variable without notifying React. 3. `button`: UI element stuck at initial zero.

> *It is best practice to do this:*
> `function StoryCard() {`
> `  const [likes, setLikes] = ~useState(0)~; // Retains count in memory`
> `  return (`
> `    <button onClick={() => ~setLikes(likes + 1)~}> // Calls setter`
> `      Like {likes}`
> `    </button>`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function StoryCard() {`
> `  let ~likes~ = 0; // Resets to 0 on every render`
> `  return (`
> `    <button onClick=~{() => { likes++; }}~> // Mutates local copy`
> `      Like {likes}`
> `    </button>`
> `  );`
> `}`

> [!PRINCIPLE]
> **Principle 2: Store in State Exactly What Must Survive a Re-Render**
> Use useState strictly for information the component must remember between renders to change what appears on screen. Keep values that are calculated and used only inside a single event handler as ordinary local variables, because calling a setter always schedules a re-render.
> 
> >> component state : persistent memory retained across renders to control UI output
> >> handler variable : a temporary calculation scoped strictly to a single event execution

- [p] ★ Principle 2 operational derivation: Every time a state setter is invoked, React schedules a re-render for that component and its children. If a developer places values in `useState` that do not affect the rendered JSX output, every user action triggers unnecessary render cycles. For example, if copying an article share link stores its URL in state via `const [shareUrl, setShareUrl] = useState('')`, calling `setShareUrl` forces React to re-render the card twice in development under StrictMode, even though the screen output does not change. In contrast, calculating `const url = window.location.href` as a local variable inside the click handler performs the clipboard copy without triggering any renders. ◼ Educational objective: teach the boundary between state and local variables to prevent unnecessary re-renders.

- [code] Single-Handler Local Calculation:

```jsx title="Handler Local Calculation"
function ShareButton({ articleId }) {
  function handleShare() {
    const ~url~ = window.location.href; // Local variable for action
    navigator.clipboard.writeText(~url~); // Action runs without render
  }
  return (
    <button onClick=~{handleShare}~>Share</button>); // Zero state overhead
}
```

◼ **The what-this-introduces list:** 1. `const url`: temporary local calculation inside an event handler. 2. `navigator.clipboard.writeText`: browser side effect executed without scheduling renders. 3. `ShareButton`: lean interactive control owning zero state.

> *It is best practice to do this:*
> `function ShareAction() {`
> `  function handleShare() {`
> `    const ~url~ = window.location.href; // Local value for action`
> `    navigator.clipboard.writeText(url);`
> `  }`
> `  return (`
> `    <button onClick=~{handleShare}~> // Runs handler without render`
> `      Share`
> `    </button>`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function ShareAction() {`
> `  const [url, setUrl] = ~useState('')~; // Unneeded state overhead`
> `  function handleShare() {`
> `    ~setUrl~(window.location.href); // Triggers wasted re-render`
> `  }`
> `  return (`
> `    <button onClick=~{handleShare}~> // Re-renders unchanged screen`
> `      Share`
> `    </button>`
> `  );`

> [!PRINCIPLE]
> **Principle 3: Expect React to Hand Back the Stored Value on Every Render**
> React stores state outside the component function in an external memory cell. On the initial render, it stores the initial argument and returns it. On every subsequent render, useState ignores the initial argument and returns the latest stored value from React's memory cell.
> 
> >> external memory cell : a record managed by React in memory outside the component function
> >> initial state : the starting value passed to useState, used only during component mounting

- [p] ★ Principle 3 operational derivation: When `StoryCard` renders for the first time, React executes `useState(0)`, creates an internal state cell initialized to `0`, and returns `[0, setLikes]`. When the user clicks the like button, `setLikes(1)` updates the value in React's external cell to `1` and schedules a re-render. On the second render pass, React executes `StoryCard` again. Even though the line in source code still literally reads `useState(0)`, React recognizes that this component instance already possesses an initialized memory cell. React ignores the `0` argument and returns `1`. If you edit the component file in your editor, Fast Refresh preserves the state cell in browser memory. Only a full browser page reload wipes JavaScript memory and restores the initial `0`. ◼ Educational objective: trace how React resolves useState across renders and distinguish Fast Refresh from full page reloads.

- [code] State Retrieval Across Renders:

```jsx title="State Retrieval Inspection"
export default function StoryCard({ title }) {
  const [likes, setLikes] = ~useState(0)~; // Initial 0 used on mount only
  console.log(~'likes:', likes~); // Logs 0 on mount, 1 on re-render
  return (
    <button
      type="button"
      onClick=~{() => setLikes(likes + 1)}~ // Schedules next render pass
    >Like ({likes})</button>
  );
}
```

◼ **The what-this-introduces list:** 1. `useState(0)`: declaration demonstrating single-use initial value. 2. `console.log(...)`: verification that re-renders receive updated state despite literal code argument. 3. `setLikes(likes + 1)`: setter storing next value and triggering render.

> *It is best practice to do this:*
> `function StoryCounter() {`
> `  const [likes, setLikes] = ~useState(0)~; // Used only on first mount`
> `  return (`
> `    <button onClick=~{() => setLikes(likes + 1)}~> // Updates state`
> `      Count {likes}`
> `    </button>`
> `  );`
> `}`
> 
> *Instead of doing this:*
> `function StoryCounter() {`
> `  let [likes, setLikes] = useState(0);`
> `  if (likes === 0) {`
> `    ~likes~ = 5; // Direct mutation breaks state synchronization`
> `  }`
> `  return <button onClick={() => setLikes(likes + 1)}>Count {likes}</button>;`
> `}`

> [!PRINCIPLE]
> **Principle 4: Change State Only by Calling Its Setter**
> A state variable is a read-only snapshot for the current render. Calling the setter function is the only way to store the next value and notify React to update the screen. Assigning directly to the state variable throws an error or silently fails to re-render.
> 
> >> setter function : the updater function returned by useState that requests a re-render
> >> read-only snapshot : the immutable state value provided to a single render execution

- [p] ★ Principle 4 operational derivation: When you unpack state using `const [likes, setLikes] = useState(0)`, the variable `likes` is declared as a constant. If a developer attempts to modify it directly via `likes = likes + 1`, the JavaScript engine throws an immediate runtime exception: `TypeError: Assignment to constant variable.`, and the button remains stuck at "Like (0)". Even if the developer declares `let [likes, setLikes]`, assigning to `likes` merely changes a local variable inside that single function execution. React has no getter or setter trap on raw JavaScript variables and receives no notification to update the DOM. Calling `setLikes(likes + 1)` is the mandatory contract: it updates React's internal storage and schedules the re-render. ◼ Educational objective: demonstrate why direct assignment to state variables fails and establish setters as the sole update mechanism.

- [code] Direct Assignment Runtime Failure:

```jsx title="Assignment Failure Demonstration"
function BrokenCard() {
  const [likes, setLikes] = ~useState(0)~; // Constant state binding
  function handleClick() {
    ~likes~ = likes + 1; // **WRONG:** throws TypeError on const assignment
  }
  return (
    <button onClick=~{handleClick}~>Like ({likes})</button>); // Crashes handler
}
```

◼ **The what-this-introduces list:** 1. `const [likes, setLikes]`: immutable constant state declaration. 2. `likes = likes + 1`: fatal assignment attempt throwing TypeError. 3. `handleClick`: broken handler failing to schedule renders.

> *It is best practice to do this:*
> `<button onClick=~{() => setLikes(likes + 1)}~> // Calls setter`
> `  Like`
> `</button>`
> 
> *Instead of doing this:*
> `<button onClick={() => { ~likes~ = likes + 1; }}> // Throws TypeError`
> `  Like`
> `</button>`

> [!PRINCIPLE]
> **Principle 5: Expect Each Rendered Instance to Keep Its Own State**
> State belongs to a specific instance of a component on the screen, not to the component function or file. Rendering a component multiple times creates completely independent state cells, and parent components cannot directly read or alter a child's private state.
> 
> >> component instance : a specific mounted occurrence of a component in the UI tree
> >> state isolation : the guarantee that each component instance manages independent memory

- [p] ★ Principle 5 operational derivation: When `App` renders two `<StoryCard />` elements, React attaches two distinct state cells to their positions in the UI tree. If the reader clicks the Like button on the first card, React calls `setLikes(1)` for that first cell and re-renders only the first card. The second card remains untouched at `Like (0)` because its state cell is completely isolated. Furthermore, the parent component `App` cannot inspect or overwrite the child card's internal state. State is entirely private to the component that declares it. (Preview of Q26: If two sibling cards need to share a synchronized count, state must be removed from the children and lifted up into their common parent). ◼ Educational objective: explain instance-level state isolation and preview lifting state up for cross-component synchronization.

◼ **The what-this-introduces list:** 1. `StoryCard (first instance)`: mounted card with private memory. 2. `StoryCard (second instance)`: sibling card maintaining independent state. 3. `App`: parent orchestrator with zero visibility into child state cells.

> *It is best practice to do this:*

> [!PRINCIPLE]
> **Principle 6: Call Setters from Handlers, Never Unconditionally During Render**
> A setter call requests a re-render. If a setter is called unconditionally in the component body or directly inside a JSX event prop, it executes during the render pass, immediately scheduling another render. This creates an infinite loop that crashes React with a fatal error.
> 
> >> render loop : an infinite cycle of render passes caused by unconditional state updates
> >> delayed execution : wrapping a function call so it runs only upon user interaction

- [p] ★ Principle 6 operational derivation: When writing JSX, passing parentheses immediately executes the function during render: `<button onClick={setLikes(likes + 1)}>`. As React renders the button, JavaScript evaluates `setLikes(likes + 1)`. Calling `setLikes` informs React that state has changed and demands an immediate re-render. React re-renders the component, encounters the button again, calls `setLikes` again, and enters a runaway loop. Within milliseconds, React halts execution and throws a fatal runtime exception: `Error: Too many re-renders. React limits the number of renders to prevent an infinite loop.`, leaving the screen blank. To prevent this crash, always wrap setter calls inside an event handler function or an inline arrow function: `onClick={() => setLikes(likes + 1)}`. ◼ Educational objective: analyze the infinite render loop trap caused by immediate setter execution and reinforce the delayed execution rule.

- [code] Unconditional Setter Execution Trap:

```jsx title="Infinite Render Loop Trap"
function BrokenCounter() {

  return (
    <button
      type="button"
      onClick=~{setLikes(likes + 1)}~ // **CRASH:** called during render pass
    >Like ({likes})</button>
  );
}
```

◼ **The what-this-introduces list:** 1. `onClick={setLikes(likes + 1)}`: premature function invocation during render. 2. `Too many re-renders`: fatal exception thrown by React. 3. `BrokenCounter`: broken component crashing entire application tree.

> *It is best practice to do this:*

> `  Like`

### Step 1: First, we construct the interactive story card <src/components/StoryCard.jsx>

- [p] ★ In `src/components/StoryCard.jsx`, we establish the stateful boundary for an interactive news story card. We import `useState` from the React package. Inside `StoryCard`, we declare two distinct pieces of component memory: `likes` initialized to `0`, and `saved` initialized to `false`. Notice that each piece of state is managed by its own independent `useState` hook. ◼ Meaningful pedagogical commentary: importing useState, declaring independent state variables for counts and booleans, and establishing the stateful component boundary.

- [code] StoryCard.jsx (State Declarations):

```jsx title="StoryCard.jsx" startLine="1" continues="bottom"

import ActionToolbar from './ActionToolbar.jsx';

export default function StoryCard({ article }) {
  const [likes, setLikes] = ~useState(0)~; // Independent counter memory
  const [saved, setSaved] = ~useState(false)~; // Independent boolean memory
```

◼ **The what-this-introduces list:** 1. `useState`: named hook import from React. 2. `[likes, setLikes]`: state pair for integer counter. 3. `[saved, setSaved]`: state pair for boolean bookmark toggle.

- [p] ★ Next, we define our event handler functions: `handleLike` and `handleSave`. When the reader clicks the Like button, `handleLike` executes `setLikes(likes + 1)`. When the reader clicks Save, `handleSave` executes `setSaved(!saved)`. Both functions execute inside the component's scope and invoke their respective setter functions to request a re-render. ◼ Meaningful pedagogical commentary: defining handler functions that invoke state setters, demonstrating state transitions for counters and booleans.

- [code] StoryCard.jsx (Handler Functions):

```jsx title="StoryCard.jsx" startLine="7" continues="both"
  function handleLike() {
    setLikes(~likes + 1~); // Stores next integer and schedules render
  }

  function handleSave() {
    setSaved(~!saved~); // Toggles boolean flag and schedules render
  }
```

◼ **The what-this-introduces list:** 1. `handleLike`: click handler calculating next counter value. 2. `handleSave`: click handler toggling boolean state. 3. `setLikes` / `setSaved`: setters updating React's external memory cells.

- [p] ★ We complete `StoryCard.jsx` by rendering the card markup. We render the article headline, then mount the child `<ActionToolbar />`. We pass down the current state values (`likes` and `saved`) along with our handler functions (`onLike={handleLike}` and `onSave={handleSave}`) as props. ◼ Meaningful pedagogical commentary: mounting presentation child and passing state values downward alongside callback handlers.

### Step 2: Next, we build the action toolbar controls <src/components/ActionToolbar.jsx>

Clicking Like on the first card increments its count without affecting the second card, preserving complete state isolation. ◼ Educational objective: summarize the operational flow of useState from click to setter call, external memory update, and isolated re-render.

### Glossary

- [glossary] Component Memory ◼ Persistent data stored by React outside the component function that survives across re-renders.
- [glossary] useState Hook ◼ The built-in React function that declares a state variable and returns a pair: the current value and a setter function.
- [glossary] Setter Function ◼ The updating function returned by useState that changes the value in React's memory cell and schedules a re-render.
- [glossary] Array Destructuring ◼ JavaScript syntax that extracts elements from an array into distinct variables in a single statement.
- [glossary] State Isolation ◼ The architectural invariant where each mounted instance of a component maintains its own private, independent state.
- [glossary] Infinite Render Loop ◼ A fatal runtime condition where calling a setter unconditionally during render triggers continuous re-renders until React halts.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Local Variables vs Component Memory

➔ ALWAYS use `useState` when a value must survive re-renders and change what appears on screen.

➔ NEVER rely on local function variables to retain interactive state across renders.

**DO THIS:** declare persistent state with useState and call the setter on interaction
```jsx right
function StoryCard() {
  const [likes, setLikes] = useState(0);
  return (
    <button type="button" onClick={() => setLikes(likes + 1)}>
      Like ({likes})
    </button>
  );
}
```

**DO NOT DO THIS:** mutate local function variables and expect the screen to update
```jsx wrong
function StoryCard() {
  let likes = 0;
  function handleLike() {
    likes = likes + 1;
  }
  return (
    <button type="button" onClick={handleLike}>
      Like ({likes})
    </button>
  );
}
```

❒ State Updating & Setter Discipline

➔ ALWAYS update state by invoking the setter function to schedule a React re-render.

➔ NEVER reassign the state variable directly or call the setter unconditionally during render.

**DO THIS:** wrap setter calls inside event handlers or arrow functions
```jsx right
function LikeButton({ likes, onLike }) {
  return (
    <button type="button" onClick={onLike}>
      Like ({likes})
    </button>
  );
}
```

**DO NOT DO THIS:** call setter functions directly in the component body or JSX expressions
```jsx wrong
function LikeButton({ likes, setLikes }) {
  return (
    <button type="button" onClick={setLikes(likes + 1)}>
      Like ({likes})
    </button>
  );
}
```

❒ State Scope & Isolation

➔ ALWAYS expect each rendered component instance to maintain its own private state cell.

➔ KEEP temporary values used only inside a single handler as local variables rather than state.

| | **LOCAL VARIABLE**<br>(Ephemeral Call) | **REACT USESTATE**<br>(Persistent Memory) |
| ---: | :--- | :--- |
| **Storage location** | Local execution call stack; wiped on function exit | External React memory cell associated with tree position |
| **Survival across renders** | Resets to initial declaration on every render pass | Preserved across renders; initial argument ignored after mount |
| **Screen update trigger** | Modifying variable triggers no render; screen stays frozen | Calling setter schedules re-render with updated value |
| **Instance isolation** | Scoped to one function run; module variables leak across cards | Private to each mounted component instance on screen |
| **Update syntax** | Direct assignment (`likes = likes + 1`) | Invoking setter function (`setLikes(likes + 1)`) |
