### The Friction of Static Repetition and Dynamic Feeds

- [p] ★ {preknowledge: JavaScript arrays, object collections, JSX expressions, props} In previous lessons, you learned how to build self-contained components and pass data into them through props. You created single cards and article headers by writing individual JSX tags. However, real-world applications rarely display a fixed, predetermined number of items. A live newsroom feed, an online store catalog, or a user comment thread contains dozens or hundreds of items stored in arrays. If a developer attempts to render these items by writing repetitive JSX tags by hand (`<StoryCard story={story1} />`, `<StoryCard story={story2} />`), the codebase becomes bloated and rigid. Every time a journalist publishes a new story or deletes an outdated post, an engineer would have to edit the component file and redeploy the application. ◼ Educational objective: recall props and JSX while establishing why hardcoded component instances fail for dynamic collections.
- [p] ★ {problem: naive index keys cause state and input scrambling during list mutations} It is possible that a developer may discover the array `map()` method and write `{stories.map((story, index) => <StoryRow key={index} story={story} />)}`, assuming that the array index is a convenient and harmless identifier. When they do, the initial page appears to render correctly. However, as soon as the collection changes—such as when an urgent breaking headline is prepended to index 0, or an item is deleted—subtle and confusing bugs appear. Because the new story now occupies index 0, React compares the previous index 0 with the new index 0 and reuses the existing DOM node in place. If an editor typed a quick spelling correction into an `<input>` on the original first story, that typed text remains stuck inside the first DOM node, now sitting next to the brand new breaking headline. ◼ Educational objective: expose the operational failure of using array indices as keys during insertions, reordering, and deletions.
- [p] ★ {old solution: writing duplicate static markup by hand or using array indices} In legacy web development, programmers either generated HTML strings through string concatenation loops or copied and pasted identical template blocks across files. In React, writing duplicate tags by hand creates unmaintainable code, while using array indices as keys creates fragile interfaces that desynchronize user inputs from underlying data. ◼ Educational objective: identify the legacy manual repetition pattern and the index-key trap.

- [code] Naive Repetition and Fragile Index Key Attempt:

```jsx title="Naive Repetition and Index Key Attempt"
// WRONG: Using array index as key creates identity bugs on prepend
function Feed({ stories }) {
  return (
    <ul>
      {stories.map((story, index) => (
        <li key={index}>
          <span>{story.title}</span>
          <input type="text" placeholder="Add note..." />
        </li>
      ))}
    </ul>
  );
}
```

◼ **The what-this-introduces list:** 1. `stories.map(...)`: array transformation method converting data into elements. 2. `key={index}`: fragile positional identifier that changes when items are prepended or reordered. 3. `<input placeholder="Add note..." />`: uncontrolled DOM input whose state is tied to the physical DOM node.

- [p] ★ {mechanism: transforming data with map and assigning stable entity IDs as keys} React solves this problem by combining JavaScript's declarative array transformation method, `.map()`, with a unique, stable `key` prop on every item. Instead of hardcoding markup, you pass an array of data objects to `stories.map()`. The callback function returns a JSX element for each object, producing an array of lightweight UI descriptors. React renders arrays of elements in order inside curly braces. Crucially, each item receives a `key` prop containing a permanent, unique identifier from the data (such as a database ID `story.id`). This key acts like a permanent passport for the element. When the list changes, React uses these keys to match old elements with new elements across renders, ensuring that DOM nodes and their internal inputs move to their correct new positions without losing data. ◼ Educational objective: explain how map converts data arrays to JSX and how stable keys preserve element identity.

### How JavaScript Transforms Arrays and How React Understands Collections

- [p] ◇ {conceptual grounding: lists in React are plain JavaScript arrays of elements} To understand how React renders lists, we must demystify what a "list" is in React. React does not have a special `<List>` tag or a proprietary looping directive like `*ngFor` in Angular or `v-for` in Vue. In React, a list is simply a standard JavaScript array containing JSX element objects. You already know that curly braces `{}` inside JSX allow you to embed JavaScript expressions. When you place an array of JSX elements inside curly braces—such as `{[<li key="1">A</li>, <li key="2">B</li>]}`—React automatically unpacks that array and renders each element into the DOM in sequential order. ◼ Educational objective: establish that a list in React is an ordinary JavaScript array of element descriptors embedded in JSX.
- [p] ★ {syntactic reminder: how Array.prototype.map works} For developers who are newer to JavaScript, let us review the **`map()` array method**. The `map()` method is a built-in JavaScript function that creates a **new array** populated with the results of calling a provided function on every element in the calling array. It does not modify or mutate the original array. For example, `[1, 2, 3].map(x => x * 2)` produces `[2, 4, 6]`. In React, instead of multiplying numbers, our callback function takes a data object (such as a story object with an `id` and a `title`) and returns a JSX element descriptor (such as `<StoryRow key={story.id} story={story} />`). ◼ Educational objective: provide a clear, beginner-friendly explanation of JavaScript's Array.prototype.map method.
- [p] ★ {syntactic reminder: arrow function implicit return versus block body} A common source of frustration for developers is the difference between an arrow function with an **expression body** and an arrow function with a **block body**. When you write an arrow function on one line without curly braces (`story => <StoryRow story={story} />`), JavaScript uses an **implicit return**. It automatically returns the expression right after the arrow `=>`. However, if you write curly braces after the arrow (`story => { ... }`), you have created a block body. A block body does not return anything automatically; it returns `undefined` unless you explicitly write the `return` keyword. If you write `stories.map(story => { <StoryRow story={story} /> })`, the callback returns `undefined` for every item, and the list silently renders completely empty. ◼ Educational objective: explain the syntactic trap of block-body arrow functions missing an explicit return keyword.
- [p] ★ {the role of keys: identity across renders versus positional matching} Now we come to the core question: why does React demand a `key` prop on every item in a dynamically generated array? When a component re-renders, React produces a fresh tree of UI descriptors and compares it with the previous tree to decide what browser DOM changes are needed. When React compares two lists of child elements, it needs a way to know which item in the new list corresponds to which item in the old list. Without keys, React can only compare items by their sequential index position: the first new element is compared against the first old element, the second against the second, and so on. If you insert a new item at the top of the array, every subsequent item shifts down by one position. React thinks that every single item changed its text, and it overwrites existing DOM nodes in place rather than moving them. With unique, stable keys, React can identify each element across renders regardless of where it appears in the array. ◼ Educational objective: explain the mechanics of element identity during reconciliation, contrasting positional matching with key-based matching.

### Principles of React: The Core Laws of Lists and Keys

- [p] ◇ When preparing for technical interviews, candidates must clearly explain how to render collections from arrays, why React enforces key uniqueness, how arrow function syntax impacts list rendering, why using array indices as keys creates subtle state-leak bugs, and why `props.key` cannot be read inside child components. To master these concepts, we formalize the six governing principles of lists and keys: ◼ Educational objective: frame the six principles from the perspective of an engineering candidate preparing for senior technical interviews.

> [!PRINCIPLE]
> **Principle 1: Build a List by Mapping Data to an Array of Elements**
> We transform an array of data objects into an array of JSX elements using the standard JavaScript `map()` method. When we place the resulting array inside JSX curly braces, React automatically renders each element in sequential order. This ensures the structure of the user interface follows the data rather than hardcoded markup.
> 
> >> array transformation : converting an array of raw data objects into a new array of JSX element descriptors using map
> >> declarative list rendering : placing an array of element descriptors inside JSX curly braces for React to unpack and render in order

- [p] ★ Principle 1 operational derivation: In React, user interface is a pure function of data (`UI = f(data)`). When you have a collection of items, you do not write loops that imperatively append child elements to a parent container. Instead, you call `stories.map(story => <StoryRow key={story.id} story={story} />)`. Under the hood, `map()` runs your callback function once for every story in the array and returns a brand-new array containing React element objects. If you inspect the output of `stories.map(...)` in the console, you see an array of plain JavaScript objects, where each object has a `type` property (pointing to your `StoryRow` component) and a `props` property. When you embed this array inside curly braces `{...}`, React unpacks the array and renders its elements in exact array order. If the data array contains three items, React creates three DOM nodes. If an item is added to the data array, the next render produces four element objects, and React adds the corresponding DOM node. ◼ Educational objective: derive how map produces an array of element descriptor objects that React sequentially mounts into the DOM.

- [code] Mapped Array Structure and Element Inspection:

```jsx title="Data Array to JSX Mapping"
const stories = [
  { id: 'story-1', title: 'City Transit Budget Approved' },
  { id: 'story-2', title: 'Clean Energy Project Begins' },
];

// Mapped array contains lightweight React element objects
const storyElements = stories.map(story => (
  <li key={story.id}>{story.title}</li>
));

console.log(storyElements); // [ { type: 'li', key: 'story-1', ... }, { ... } ]
```

◼ **The what-this-introduces list:** 1. `stories`: array of plain JavaScript data objects. 2. `storyElements`: new array of React element objects created by map. 3. `console.log(storyElements)`: runtime proof that JSX compiles into plain objects in memory.

> [!PRINCIPLE]
> **Principle 2: Return the JSX from the Map Callback**
> When writing a `map()` callback function, ensure it returns a JSX element. If you use an arrow function with curly braces, you must write an explicit `return` statement. If you omit the `return` statement, the callback returns `undefined` for every item, and the list silently renders completely empty.
> 
> >> expression body : an arrow function without curly braces that automatically returns the single expression after =>
> >> block body : an arrow function with curly braces that requires an explicit return statement to output a value
> 
> *It is best practice to do this:*
> `stories.map(story => (`
> `  <StoryRow key={story.id} story={story} /> // Implicit return passes element`
> `))`
> 
> *Instead of doing this:*
> `stories.map(story => {`
> `  <StoryRow key={story.id} story={story} /> // Block body without return yields undefined`
> `})`

- [p] ★ Principle 2 operational derivation: The official React documentation highlights this pattern as a frequent developer pitfall because the mistake is completely silent. In JavaScript, an arrow function can be written in two ways: with an expression body or with a block body. In an expression body (`story => <StoryRow ... />`), there are no curly braces around the function body, and JavaScript implicitly returns the value of that expression. However, if you write curly braces (`story => { <StoryRow ... /> }`), JavaScript treats the curly braces as a statement block rather than an object or expression. Inside a statement block, JavaScript executes statements sequentially and returns `undefined` unless it encounters a `return` keyword. When `map()` runs this callback over an array of ten stories, it collects ten `undefined` values and returns `[undefined, undefined, ...]`. Because React's suppression whitelist renders zero DOM nodes for `undefined`, the container element (`<ul>` or `<div>`) renders completely blank. The browser console produces zero error messages and zero warnings. Whenever a list renders blank, immediately check whether your arrow function has curly braces without an explicit `return`. ◼ Educational objective: analyze the silent blank-screen failure caused by omitting the return statement in block-body arrow functions.

- [code] Expression Body vs Block Body Return Proof:

```jsx title="Implicit vs Explicit Return in Map"
// 1. Implicit return: expression right after => is returned automatically
const validList = stories.map(story => (
  <StoryRow key={story.id} story={story} />
));

// 2. Explicit return: required when curly braces {} create a block body
const validBlockList = stories.map(story => {
  const formattedTitle = story.title.toUpperCase();
  return <StoryRow key={story.id} story={story} title={formattedTitle} />;
});
```

◼ **The what-this-introduces list:** 1. `stories.map(story => (...))`: concise implicit return for single expressions. 2. `stories.map(story => { ... return ... })`: safe explicit return when pre-calculating values inside a block body.

> [!PRINCIPLE]
> **Principle 3: Put a Unique Key on the Outermost Element Returned by Map**
> Place the `key` prop on the outermost element directly returned inside the `map()` call, never on elements nested inside a child component. The key must be unique among its sibling elements in that array. If an item returns multiple sibling nodes, wrap them in a `<Fragment key={...}>` instead of an empty `<>` tag.
> 
> >> outermost element : the top-level JSX tag returned directly by the map callback function
> >> sibling uniqueness : the requirement that keys must be distinct among elements within the same array
> 
> *It is best practice to do this:*
> `stories.map(story => (`
> `  <StoryRow key={story.id} story={story} /> // Key placed on outermost element returned by map`
> `))`
> 
> *Instead of doing this:*
> `stories.map(story => (`
> `  <StoryRow story={story} /> // Missing key on child component: key placed inside StoryRow root li`
> `))`

- [p] ★ Principle 3 operational derivation: A frequent architectural error occurs when developers extract a list row into its own component. Suppose you have `stories.map(story => <li key={story.id}>{story.title}</li>)`. When you extract the row into a `<StoryRow />` component, developers often mistakenly move the `key` prop inside `StoryRow.jsx`, placing it on the component's root `<li>`. When you do this, React immediately logs a warning in the console: *"Warning: Each child in a list should have a unique 'key' prop. Check the render method of `Feed`."* React evaluates keys at the array level inside the parent component where the collection is mapped. It needs the key on the element returned by the `map` callback—`<StoryRow key={story.id} />`—so it can identify which `<StoryRow>` component to render. Furthermore, keys must be unique among **siblings** within that specific array; using the same key in a completely different list component is completely valid. Finally, if each item in the list must render two adjacent elements without an extra wrapper `<div>` (for example, a `<dt>` and a `<dd>`), you cannot use the empty `<>...</>` shorthand because shorthand fragments cannot accept props; you must import `Fragment` from `'react'` and write `<Fragment key={story.id}>`. ◼ Educational objective: prove why keys must sit on the outermost element returned by map and how to key multi-node items with Fragment.

- [code] Correct Key Placement and Keyed Fragment:

```jsx title="Correct Key Placement on Extracted Component"
// CORRECT: Key sits on the outermost component returned by map
function Feed({ stories }) {
  return (
    <ul>
      {stories.map(story => (
        <StoryRow key={story.id} story={story} />
      ))}
    </ul>
  );
}

// CORRECT: Multi-node item uses explicit Fragment with key
import { Fragment } from 'react';
function StoryDetails({ stories }) {
  return (
    <dl>
      {stories.map(story => (
        <Fragment key={story.id}>
          <dt>{story.title}</dt>
          <dd>{story.category}</dd>
        </Fragment>
      ))}
    </dl>
  );
}
```

◼ **The what-this-introduces list:** 1. `<StoryRow key={story.id} />`: correct placement of key on the extracted component tag. 2. `import { Fragment } from 'react'`: importing explicit Fragment component. 3. `<Fragment key={story.id}>`: keyed fragment grouping multiple sibling elements without adding extra DOM nodes.

> [!PRINCIPLE]
> **Principle 4: Treat Keys as the Identity React Uses to Match Items Between Renders**
> React uses keys as permanent identifiers to match elements between renders. When a list re-renders, React pairs each new element with the previous element that shares the same key and preserves its physical DOM node. Without keys, React pairs elements purely by position, rewriting DOM content in place and breaking local element state.
> 
> >> element identity : a persistent identifier that ties a virtual element to its physical DOM node across renders
> >> positional diffing : React's fallback reconciliation model that compares items by numerical index when keys are missing or unstable

- [p] ★ Principle 4 operational derivation: This principle is the heart of React's list reconciliation engine. When React renders a component tree, it creates real browser DOM nodes. Some DOM nodes carry internal state that lives exclusively in the browser: text typed into an uncontrolled `<input>`, the scroll position of a container, the checked state of a checkbox, or the playback position of an `<audio>` element. When a re-render occurs, React must decide whether to create new DOM nodes, delete existing DOM nodes, or update existing nodes with new attributes. If you omit keys or use array indices, React defaults to **positional diffing**. It compares index 0 to index 0, index 1 to index 1, and so on. If you prepend an urgent story at index 0, the story that was previously at index 0 is now at index 1. Because React compares by position, it looks at index 0, sees that the title changed, and updates the text content of the existing DOM node. However, the browser's internal input buffer is not touched; whatever the user typed into the input at index 0 remains in that physical DOM node. To the user, their typed note suddenly jumps from the original story to the new urgent story! When you provide stable entity keys (`key={story.id}`), React matches the old `story-1` element with the new `story-1` element. It recognizes that `story-1` moved from index 0 to index 1, and it physically moves the existing DOM node in the document. The input text, focus, and audio position move together with their story. ◼ Educational objective: trace the physical DOM mechanics of positional diffing versus key-based identity matching during array prepends.

- [code] Prepend Proof: Positional vs Identity Matching:

```jsx title="Array Prepend Mutation Scenario"
// Initial list render: 2 stories
const initialFeed = [
  { id: 'story-1', title: 'City Transit Budget Approved' },
  { id: 'story-2', title: 'Clean Energy Project Begins' },
];

// Re-render: Urgent story prepended at index 0
const updatedFeed = [
  { id: 'urgent-99', title: 'URGENT: Flash Flood Warning' },
  { id: 'story-1', title: 'City Transit Budget Approved' },
  { id: 'story-2', title: 'Clean Energy Project Begins' },
];
// With key={story.id}: DOM node for story-1 moves from index 0 to index 1
// With key={index}: DOM node at index 0 stays in place, text rewritten, typed input corrupted
```

◼ **The what-this-introduces list:** 1. `initialFeed`: baseline array with two items. 2. `updatedFeed`: updated array prepending a high-priority item at index 0. 3. Physical DOM movement: proof that stable keys move existing nodes while index keys mutate nodes in place.

> [!PRINCIPLE]
> **Principle 5: Key Items by a Stable ID from the Data, Never by Array Index or Random Values**
> Always use a permanent, stable identifier from your data as the key, such as a database ID or a unique ID created when the item was first generated. Never use the array index for lists that can change, and never generate keys during render using `Math.random()`. Random keys force React to recreate all DOM nodes on every render, losing focus and destroying performance.
> 
> >> stable identifier : a permanent ID tied to a data entity that never changes throughout the application lifetime
> >> random key churn : generating keys on the fly during render, causing React to destroy and recreate the entire DOM tree on every update
> 
> *It is best practice to do this:*
> `stories.map(story => (`
> `  <StoryRow key={story.id} story={story} /> // Stable database ID persists across renders`
> `))`
> 
> *Instead of doing this:*
> `stories.map(story => (`
> `  <StoryRow key={Math.random()} story={story} /> // Random key forces complete DOM teardown and recreation on every render`
> `))`

- [p] ★ Principle 5 operational derivation: The stability of a key is just as important as its uniqueness. There are three common sources of keys: (1) permanent database IDs from server data (`story.id`), (2) locally generated UUIDs created once when a user creates an item (`crypto.randomUUID()`), and (3) array indices. You should only use the array index as a key if your list satisfies three strict conditions: the list is completely static, it will never be filtered or reordered, and items will never be added or removed. If the list can change in any way, using the array index is an antipattern. Even worse than index keys is generating keys on the fly during render, such as writing `key={Math.random()}` or `key={crypto.randomUUID()}` inside the `map` callback. Because `Math.random()` executes on every single render pass, every element receives a completely different key every time the component updates. When React compares the new tree with the old tree, zero keys match. React assumes that every single previous element was deleted and that ten completely brand new elements were created. It destroys all existing DOM nodes and rebuilds them from scratch. This completely destroys typing focus, wipes input text, resets video playback, and causes severe rendering lag. Keys must remain identical across renders for the same data entity. ◼ Educational objective: evaluate key sources, proving why render-time random keys destroy DOM persistence and focus.

- [code] Stable ID vs Random Key Churn Proof:

```jsx title="Stable Data ID vs Render-Time Random Key"
// CORRECT: Permanent entity ID created at data inception
const storiesFromAPI = [
  { id: 'art-101', title: 'City Transit Plan' },
  { id: 'art-102', title: 'Clean Water Initiative' },
];
// Key remains 'art-101' across all subsequent renders

// WRONG: Generating keys on the fly during render
stories.map(story => (
  // Every render pass generates a new random string!
  // Destroys DOM nodes, wipes user input, loses input focus
  <StoryRow key={Math.random()} story={story} />
));
```

◼ **The what-this-introduces list:** 1. `art-101`: permanent semantic string identifier from server data. 2. `Math.random()` in key: anti-pattern creating unstable keys on every render pass. 3. DOM node teardown: physical browser consequence of key churn.

> [!PRINCIPLE]
> **Principle 6: Pass the ID as Its Own Prop When the Component Needs It**
> React reserves the `key` prop for its internal reconciliation engine and does not pass it down to your component. If a child component needs the story's ID for links, event handlers, or accessibility labels, you must pass it as a separate, explicitly named prop such as `id={story.id}` or pass the entire story object.
> 
> >> reserved prop : a prop like key or ref that React consumes internally and excludes from props
> >> explicit data passing : passing an identifier under a distinct prop name so child components can read it
> 
> *It is best practice to do this:*
> `<StoryRow key={story.id} id={story.id} story={story} /> // Explicit id prop accessible inside child component`
> 
> *Instead of doing this:*
> `<StoryRow key={story.id} story={story} /> // Component attempts to read props.key directly, yielding undefined`
> 

- [p] ★ Principle 6 operational derivation: Developers frequently encounter a confusing warning when they try to read `props.key` inside a child component. For example, an engineer might write `<button onClick={() => deleteStory(props.key)}>Delete</button>`. When they run this code, the delete function receives `undefined`, and React logs an explicit warning in the browser console: *"Warning: StoryRow: `key` is not a prop. Trying to access it will result in `undefined` being returned. If you need to access the same value within the child component, you should pass it as a different prop."* React strips `key` (and `ref`) from the component's `props` object during element creation because `key` belongs to React's fiber and reconciliation machinery, not to the component's business logic. If your child component needs the identifier—for example, to construct a URL link `<a href={`/story/${id}`}>`, set a `data-story-id` attribute, or trigger a callback—you must pass the ID under a distinct prop name such as `id`, `storyId`, or simply pass the whole `story` object and read `story.id`. ◼ Educational objective: explain why React strips key from props and demonstrate how to pass entity identifiers explicitly.

- [code] Accessing Entity IDs via Props:

```jsx title="Passing Entity IDs as Dedicated Props"
// Parent passes key for React, and storyId for component logic
function Feed({ stories }) {
  return (
    <div>
      {stories.map(story => (
        <StoryRow key={story.id} storyId={story.id} story={story} />
      ))}
    </div>
  );
}

// Child component receives storyId cleanly through props
function StoryRow({ storyId, story }) {
  // Reading props.key would return undefined!
  return <article data-id={storyId}><h2>{story.title}</h2></article>;
}
```

◼ **The what-this-introduces list:** 1. `key={story.id}`: reserved prop consumed by React's reconciler. 2. `storyId={story.id}`: ordinary component prop accessible inside child. 3. `data-id={storyId}`: safe attribute binding using the dedicated prop.

### Step 1: First, we declare the parent container <src/App.jsx>

- [p] ★ {step motivation: constructing the parent feed component that maps data to elements and assigns stable keys} We begin our implementation by constructing `src/App.jsx`. In our newsroom application, story items are stored as an array of structured objects. Each story has a permanent `id` string (such as `'story-101'`), a `title`, and a `category`. In `App.jsx`, we define our initial story collection and render a list of cards by calling `stories.map()`. Notice how we place the `key` prop directly on the outermost element returned by the callback: `<StoryRow key={story.id} story={story} />`. - [p] Rendering lists in React is built on standard JavaScript array transformations and explicit element identity. By using `map()` to project data arrays into JSX descriptors, your application's user interface stays perfectly synchronized with your data. By placing stable, unique keys on the outermost element returned by `map()`, you give React the identity information it needs to preserve DOM nodes, protect user inputs, and update lists efficiently.

### Where you will meet this

- [p] 1. **Dynamic Content Feeds and Catalogs**: In news portals, social media feeds, and product catalogs, you map collections of server data into card components, using permanent entity database IDs as keys to allow smooth filtering and insertion.
- [p] 2. **Interactive Form Repeaters**: In invoice generators, survey builders, or recipe ingredient lists where users can add, remove, and reorder input rows, stable keys ensure that typed text and active cursor focus never jump between rows when an item is deleted.
- [p] 3. **Tabbed Navigation and Menus**: When rendering navigation bars or tab lists from an array of routes, stable keys allow React to track which tab is active without tearing down DOM nodes during tab switching.

### Glossary

- [glossary] Array Transformation ◼ Using methods like map to convert an array of raw data objects into a new array of JSX element descriptors.
- [glossary] Key Prop ◼ A special string or number attribute passed to list elements that React uses to identify items across renders.
- [glossary] Positional Diffing ◼ React's fallback reconciliation behavior when keys are absent or based on array index, comparing elements purely by sequential position.
- [glossary] Element Identity ◼ The association between a React virtual element and its persistent browser DOM node established by a stable key.
- [glossary] Key Churn ◼ An antipattern where keys change on every render (such as from Math.random), forcing React to destroy and recreate all DOM nodes.
- [glossary] Reserved Prop ◼ A prop such as key or ref that React consumes internally for reconciliation and does not pass down to the component.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Array Transformation & Return Syntax

➔ ALWAYS use `array.map()` to project data arrays into JSX element arrays inside curly braces.

➔ NEVER forget to write an explicit `return` statement when using a block body (`=> { ... }`) in a `map` callback, which causes the list to render blank.

❒ Key Placement & Multi-Node Grouping

➔ ALWAYS place the `key` prop on the outermost element directly returned by the `map()` callback.

➔ NEVER use empty shorthand `<>...</>` tags inside a mapped list when an item renders multiple siblings; always use `<Fragment key={item.id}>`.

❒ Key Source & Reconciliation Safety

➔ ALWAYS use permanent, stable entity IDs from your data (such as database IDs) as list keys.

➔ NEVER use array indices for lists that can reorder or insert, and NEVER generate keys on the fly during render with `Math.random()`.

**DO THIS:** use stable entity IDs as keys on the outermost element returned by map

```jsx right
// Stable ID preserves element identity across reordering and insertions
{stories.map(story => (
  <StoryRow key={story.id} story={story} />
))}
```

**DO NOT DO THIS:** use array indices as keys for dynamic lists

```jsx wrong
// Positional index keys scramble user inputs when items are prepended
{stories.map((story, index) => (
  <StoryRow key={index} story={story} />
))}
```
