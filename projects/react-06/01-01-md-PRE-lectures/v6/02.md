### The Silent Blank Screen of Lowercase Tags

- [p] ★ {preknowledge: JavaScript function declarations, HTML markup tags, camelCase naming conventions} In standard JavaScript, developers follow camelCase conventions for almost every identifier: functions are named `calculateTotal()`, variables are named `activeArticle`, and event handlers are named `handleClick()`. When starting out with React, developers naturally carry this muscle memory forward. You write a standard function named `articleCard()`, assemble headline and summary markup inside its body, and mount it in your layout as `<articleCard />`. The syntax looks clean, the code editor shows no red squiggles, and the terminal build finishes with zero errors. ◼ Educational objective: establish the familiar developer baseline and explain why muscle memory pushes developers toward camelCase.
- [p] ★ {problem: lowercase custom tags compile to native HTML string literals, causing silent render failures} When you refresh the browser page, the article card is completely missing. The terminal reports no errors, and the browser developer console reports zero warnings. When you inspect the living page in the Elements panel, you find a bizarre custom tag: `<articlecard></articlecard>`. The browser treated your component tag as a native HTML element instead of executing your JavaScript function. Because the browser does not recognize this custom tag and your function was never invoked, the browser renders an empty DOM node, leaving the user with an empty white screen. ◼ Educational objective: identify the silent failure mode of lowercase component tags in the DOM.
- [p] ★ {old solution: naive lowercase component declaration} To see this failure in concrete code, examine how a junior developer attempts to declare and mount a news card:

- [code] Naive Component Declaration:

```jsx title="Naive Component Declaration"
function ~articleCard~() { // Lowercase name prevents compiler invocation
  return (
    <article className="article-card">
      <h2>Morning Dispatch</h2>
    </article>
  );
}
export default function App() {
  return <~articleCard~ />; // Compiles to literal HTML string
}
```

◼ **The what-this-introduces list:** 1. `articleCard`: naive lowercase function declaration following standard JavaScript camelCase. 2. `<articleCard />`: lowercase JSX tag compiling to an HTML string literal. 3. Silent failure: complete bypass of the component function during render.

- [p] ★ {mechanism: the browser engine instantiates unknown HTML tags without executing the JavaScript function} When the browser encounters an unknown tag in markup, it does not throw an exception. The HTML specification dictates that unrecognized tag names instantiate a generic `HTMLUnknownElement` DOM node. Because the JSX compiler converted `<articleCard />` into a string literal request for an HTML element named `"articlecard"`, React instructed the browser to create that element directly. Your function `articleCard()` remained idle in JavaScript memory, completely untouched by React's rendering pipeline. ◼ Educational objective: deconstruct the browser HTML parser and DOM instantiation behavior for unrecognized tags.
- [grounding] [!] Grounding card: Why do lowercase custom tags fail silently in the browser? ◼ Opening question: Why do lowercase custom tags fail silently in the browser? ◼ Friction target: Developers wondering why lowercase tags create empty DOM nodes without console errors. ◼ Tactile scene: An engineer writes `<articleCard />`, compiles cleanly, but observes an empty `<articlecard></articlecard>` node in the DevTools inspector. ◼ Bold key terms: **string literal**, **HTMLUnknownElement**, **silent failure**, **AST branch**. ◼ Operational resolution: The JSX transpiler branches on ASCII casing: lowercase tags compile to string literals for `document.createElement`, while uppercase tags compile to unquoted function references; capitalizing the component name allows React to execute the function.

### What is a React Component and How Does JSX Compile Markup?

- [p] ◇ {conceptual grounding: the component as a self-contained function returning UI descriptors} A React component is the foundational building block of modern web applications. At its core, a component is a standard JavaScript function that returns a description of a user interface written in JSX. Unlike monolithic HTML files where markup, style, and scripts live in separate silos, a React component unifies structure and presentation into an isolated, reusable unit. When you declare `ArticleCard()`, you are defining a reusable blueprint for a slice of the page. Every time React evaluates this component, it executes the function to calculate what elements should appear on the screen. ◼ Educational objective: define the React component as a reusable function returning UI descriptors.
- [p] ◇ {ast compilation: the JSX transpiler AST branch distinguishing strings from identifiers} In standard JavaScript runtimes, JSX markup is not valid language grammar. Browsers cannot parse tags like `<ArticleCard />` natively. Before your code reaches the browser, a compiler like Babel or SWC parses your source code into an **Abstract Syntax Tree** (AST). When the parser encounters an opening angle bracket, it inspects the very first character of the tag name. If the character is lowercase, the compiler treats the tag as a built-in DOM element and emits a string literal: `_jsx("article")`. If the character begins with an uppercase letter, the compiler emits an unquoted function identifier: `_jsx(ArticleCard)`. ◼ Educational objective: explain the AST compiler branching mechanism that differentiates native tags from custom components.
- [p] ◇ {the component definition: pure mathematical projection UI = f(data)} React models every component as a pure mathematical projection: `UI = f(data)`. A component function must behave as a pure calculation that returns UI descriptors without modifying outside state. When React calls your component, it expects the function to evaluate its inputs and return JSX markup or `null`. If a component tries to manipulate the DOM imperatively inside its body, it breaks React's ability to coordinate screen updates across renders. ◼ Educational objective: establish the pure function contract of component rendering.
- [p] ★ {runtime execution: the two-phase commit pipeline, fiber node registration, and tree management} To coordinate updates safely, React splits execution into two distinct stages: the **Render Phase** and the **Commit Phase**. In the render phase, React executes your component function in memory to produce a lightweight JavaScript object called a **UI descriptor**. React attaches this descriptor to an internal structure called a **Fiber node**, which tracks the component's place in the tree, its lifecycle, and its scheduled updates. Only during the subsequent commit phase does React touch the real browser DOM, inserting or updating living HTML elements. Calling a component function directly as `{ArticleCard()}` bypasses fiber creation, breaking React's ability to manage the component in memory. ◼ Educational objective: unpack the two-phase commit pipeline and explain how fiber nodes anchor components in memory.

### Principles of React: Component Anatomy and Invocation

- [p] ◇ When preparing for senior engineering interviews, candidates must explain why React enforces strict capitalization, purity, and return contracts for components. To master this architecture, we formalize the four governing principles of component anatomy and invocation: ◼ Educational objective: frame the upcoming principles from the perspective of an engineering candidate preparing for technical evaluation.

> [!PRINCIPLE]
> **Principle 1: Enforce PascalCase Capitalization to Emit Function Identifiers**
> Always name custom components with an initial capital letter in **PascalCase** so the JSX compiler emits an unquoted function identifier. A lowercase tag instructs the compiler to emit a string literal, causing the browser to instantiate an empty unknown HTML element without running your JavaScript function.
> 
> >> PascalCase : naming convention where the first letter of each compound word is capitalized
> >> function identifier : an unquoted reference to a JavaScript function in memory
> 
> *We should do this:*
> `function ArticleCard() {`
> `  return <h2>Morning Dispatch</h2>;`
> `}`
> `<~ArticleCard~ /> // React runs capitalized component function`
> 
> *We should not do this:*
> `function articleCard() {`
> `  return <h2>Morning Dispatch</h2>;`
> `}`
> `<~articleCard~ /> // Lowercase tag creates empty HTML element`

- [p] ★ Principle 1 operational derivation: In standard JavaScript, functions are written in camelCase by default. Developers naturally write `function articleCard()` and mount `<articleCard />`. The compiler parses the tag and checks the Unicode category of the first letter. Because `a` is lowercase, the compiler emits a string literal: `_jsx("articlecard", {})`. At runtime, React passes this string to `document.createElement("articlecard")`. The browser creates an `HTMLUnknownElement` with zero styles and zero children, and the screen remains blank. When you capitalize the name to `ArticleCard`, the compiler emits an unquoted identifier: `_jsx(ArticleCard, {})`. React reads the function reference from memory, executes `ArticleCard()`, and paints the returned `<article>` to the screen. ◼ Educational objective: trace the physical AST compiler branch from lowercase string literals to uppercase function references.

> [!PRINCIPLE]
> **Principle 2: Keep Component Rendering Pure and Free of Outside Side Effects**
> Treat component functions as pure calculations that produce identical UI descriptors for identical inputs. Rendering code must never mutate external variables, alter outside objects, or perform imperative DOM updates. In development, React StrictMode intentionally calls your function twice to expose impure side effects.
> 
> >> pure calculation : a function that depends only on its inputs and causes zero observable outside side effects
> >> side effect : any modification of outside state, global memory, or external DOM nodes during render
> 
> *We should do this:*
> `function ArticleCard({ edition }) {`
> `  const ~headline~ = `Edition #${edition}`; // Calculates output purely from inputs`
> `  return <h2>{headline}</h2>;`
> `}`
> 
> *We should not do this:*
> `let ~editionCount~ = 0; // External variable outside component`
> `function ArticleCard() {`
> `  ~editionCount~ += 1; // Mutating outside variable corrupts render`
> `  return <h2>{editionCount}</h2>;`
> `}`

- [p] ★ Principle 2 operational derivation: React assumes that every component function is an idempotent calculation: given the same inputs, it must return the same UI descriptors. If a component modifies an external variable during render, it pollutes outside memory during execution. When `React.StrictMode` intentionally evaluates the component twice in development mode, the counter increments twice per mount, jumping from 0 to 2 immediately. During concurrent rendering, React may pause, abort, or re-run rendering calculations in memory. Pure functions ensure that aborted renders leave zero trace in application memory, making user interface updates robust and predictable. ◼ Educational objective: deconstruct mathematical function purity and explain why side effects during render break under StrictMode double-rendering.

> [!PRINCIPLE]
> **Principle 3: Fulfill the Pure Return Contract and Use Null to Explicitly Suppress Output**
> Every component function must return a valid React element, Fragment, or `null`. Forgetting a return statement causes the function to evaluate to `undefined`, triggering a fatal development crash. To intentionally render nothing on screen, explicitly return `null` so React paints an empty slot cleanly.
> 
> >> return contract : the requirement that a component return a valid element descriptor or null
> >> null suppression : explicitly returning null to render nothing without triggering an undefined crash
> 
> *We should do this:*
> `function DraftCard({ isLive }) {`
> `  if (!isLive) return ~null~; // Tells React to render nothing safely`
> `  return <article>Dispatch</article>;`
> `}`
> 
> *We should not do this:*
> `function DraftCard({ isLive }) {`
> `  if (!isLive) ~return~; // Returns undefined and crashes React`
> `  return <article>Dispatch</article>;`
> `}`

- [p] ★ Principle 3 operational derivation: In standard JavaScript functions, omitting a return value returns `undefined` by default. When developers write conditional rendering logic, they often forget an `else` branch or write a bare `return;` hoping to skip output. When React evaluates this function, it catches `undefined` immediately and throws `Error: ArticleCard(...): Nothing was returned from render`. This strict failure prevents accidental bugs like writing `return` on one line and JSX on the next without parentheses (triggering Automatic Semicolon Insertion). If you genuinely intend to render nothing, you must explicitly return `null`. React reads `null` as an empty slot in the virtual DOM tree, paints zero DOM nodes, and keeps the engine stable. ◼ Educational objective: enforce the pure return contract and distinguish undefined crashes from explicit null suppression.

> [!PRINCIPLE]
> **Principle 4: Render Components Using Declarative JSX Tags, Not Direct Function Calls**
> Mount components using declarative JSX tags like `<ArticleCard />` so React registers an independent element descriptor `{ type: ArticleCard }`. Invoking a component directly as a plain JavaScript function `{ArticleCard()}` inlines child elements into the parent, stripping component boundaries and breaking lifecycle tracking.
> 
> >> declarative JSX tag : syntax creating a component element descriptor managed by React
> >> direct function invocation : executing a function inline as plain JavaScript without element identity
> 
> *We should do this:*
> `<main>`
> `  <~ArticleCard~ /> // Gives React custody of component lifecycle`
> `</main>`
> 
> *We should not do this:*
> `<main>`
> `  {~ArticleCard~()} // Inlines HTML directly and skips component tracking`
> `</main>`

- [p] ★ Principle 4 operational derivation: Because a component is a JavaScript function, developers often wonder why they cannot call it directly with curly braces: `{ArticleCard()}`. In JavaScript, calling `ArticleCard()` executes the function synchronously during the parent's evaluation. The parent receives raw child elements directly, but React never registers `ArticleCard` as a distinct node in its virtual DOM tree. React cannot attach a dedicated Fiber node, cannot isolate re-renders, and cannot manage future state hooks or lifecycles. Writing `<ArticleCard />` tells React to create a component descriptor: `_jsx(ArticleCard, {})`. React places the component into its fiber hierarchy, scheduling its execution and managing its identity independently. ◼ Educational objective: deconstruct why declarative JSX tags create fiber nodes while direct function calls inline anonymous markup.

| | **NAIVE JAVASCRIPT REFLEX**<br>(anti-pattern or trap) | **REACT COMPONENT REALITY**<br>(compiler and runtime contract) | **ENGINE RATIONALE**<br>(platform consequence) |
| :--- | :--- | :--- | :--- |
| **1. PascalCase Naming** | Lowercase camelCase: `function articleCard()` | PascalCase uppercase: `function ArticleCard()` | AST branches on ASCII casing: string literal vs unquoted function identifier |
| **2. Render Purity** | Mutating outside variables or caches during render | Pure mathematical calculation: `UI = f(data)` | StrictMode double-invocation exposes mutations; concurrent render resilience |

- [callout] [!TIP] **To impress the interviewer:** When interviewers ask why React requires PascalCase for custom components, junior candidates often answer "because it is a style convention so developers can spot components easily." This answer misses the underlying compiler architecture. PascalCase is not an aesthetic style guideline; it is a **hard compiler specification** enforced by the JSX Babel/SWC transpiler. The compiler parser branches on the Unicode casing of the tag's first character: lowercase characters compile to string literals (`_jsx("articlecard")`), while uppercase characters compile to unquoted variable identifiers (`_jsx(ArticleCard)`). Without PascalCase, the browser creates an unknown HTML element and the component function never runs.

### Step 1: First, we construct the article card component <ArticleCard.jsx>

- [p] ★ We construct the standalone article card component `ArticleCard.jsx` to encapsulate headline and summary copy into an isolated, reusable function. Notice that the function name begins with an uppercase letter: `ArticleCard`. This PascalCase naming guarantees that the JSX compiler treats `<ArticleCard />` as a custom component rather than an unknown HTML tag. The component function contains no hardcoded DOM queries, mutates no external variables, and returns semantic HTML elements wrapped in a single root `<article>` tag. ◼ Meaningful pedagogical commentary: component function anatomy, PascalCase compiler contract, single root container encapsulation.
- [p] ◇ When returning multi-line JSX markup from a component function, you encounter a foundational JavaScript syntax crossroad:
  - **Option 1 (The Foundational Way)**: Write a naked multi-line return without wrapping parentheses, exposing the code to Automatic Semicolon Insertion.
  - **Option 2 (The Modern Idiomatic Way)**: Wrap the multi-line JSX expression in parentheses, signaling to the parser that the return expression continues across lines.
- [code] Option 1: The Foundational Way (Naked Multi-Line Return):

```jsx title="Option 1: The Foundational Way (Naked Multi-Line Return)"
export default function ArticleCard() {
  ~return~ // Parser automatically inserts semicolon here
    <article className="article-card">
      <h2>~Morning Dispatch~</h2> // Unreachable code never evaluated
    </article>;
}
```

- [p] ★ In Option 1, the JavaScript engine encounters a newline immediately after the `return` keyword. Under the rules of Automatic Semicolon Insertion (ASI), the parser inserts a semicolon after `return;`. The function immediately terminates and returns `undefined`. The JSX markup on the following line is never evaluated, and the browser displays a blank card with zero errors. ◼ Educational objective: explain the mechanical failure mode of Automatic Semicolon Insertion on naked multi-line return statements.
- [code] ArticleCard.jsx:

```jsx title="ArticleCard.jsx"
export default function ArticleCard() {
  return ( // Parentheses prevent automatic semicolon insertion
    <article className="article-card">
      <h2 className="headline">~Morning Dispatch~</h2> // Story headline text
      <p className="summary">~Civic report.~</p> // Descriptive summary text
    </article>
  );
}
```

- [p] ★ In Option 2, the opening parenthesis `(` tells the ECMAScript parser that the return expression continues across multiple lines. Semicolon insertion is prevented, and the component function reliably evaluates the entire JSX tree. Notice how `ArticleCard.jsx` functions as a pure presentation component: it owns no state, requires no external DOM lookups, and cleanly packages the newsroom card into a predictable, reusable unit. ◼ Meaningful pedagogical commentary: parenthesized return protection, pure presentation contract, satisfying single root invariant.

◼ **The what-this-introduces list:** 1. `ArticleCard`: the standalone custom component function. 2. PascalCase identifier: uppercase naming signaling custom component to JSX compiler. 3. Parenthesized JSX return: defensive multi-line expression wrapping.

### Step 2: Finally, we mount the card declaratively inside <App.jsx>

- [p] ★ To complete our application layout, we mount `ArticleCard.jsx` inside the root container `App.jsx`. In standard JavaScript development, inserting a new widget required querying an existing container with `document.querySelector` and appending elements imperatively. In React, the entire document organizes into a declarative hierarchy. Notice that `App.jsx` imports `ArticleCard` as an unquoted JavaScript identifier and mounts it using the self-closing tag `<ArticleCard />`. We do not call `ArticleCard()` directly with parentheses; writing `<ArticleCard />` tells React's mounting engine to register an independent fiber node in the render tree and execute the component during the render pass. ◼ Meaningful pedagogical commentary: declarative mounting, unquoted identifier import, fiber node registration.

- [code] App.jsx:

```jsx title="App.jsx"
import ArticleCard from './components/ArticleCard.jsx';

export default function App() {
  return (
    <main className="national-times-app">
      <~ArticleCard~ /> // Mounts component declaratively as tag
    </main>
  );
}
```

- [p] ★ When React evaluates `App`, the JSX compiler transforms `<ArticleCard />` into `_jsx(ArticleCard, {})`. React attaches the component to its virtual tree, executes `ArticleCard()` in memory, and paints the returned `<article>` node inside `<main>` in a single atomic operation. Because the component follows PascalCase naming and declarative invocation, the browser receives living, semantic DOM elements without manual query scripts or silent lowercase failures. ◼ Meaningful pedagogical commentary: AST transformation to _jsx function identifier, atomic mounting, complete component tree resolution.

◼ **The what-this-introduces list:** 1. `App`: the top-level application root container. 2. Component import: importing `ArticleCard` as an unquoted identifier. 3. Declarative JSX mount: `<ArticleCard />` tag creating a managed fiber node.

### Glossary

- [glossary] Component ◼ A self-contained, reusable JavaScript function whose name starts with an uppercase letter and returns a tree of UI descriptors written in JSX.
- [glossary] PascalCase ◼ A naming convention where the first letter of each compound word is capitalized, used by the JSX compiler to distinguish custom component functions from native HTML elements.
- [glossary] UI Descriptor ◼ A lightweight JavaScript object produced by the JSX transpiler that describes what elements, attributes, and children should appear on the screen.
- [glossary] Fiber Node ◼ An internal React data structure that represents a component instance in memory, tracking its lifecycle, hooks, and position in the virtual DOM tree.
- [glossary] Render Phase ◼ The initial computational phase of React's execution where component functions are evaluated in memory to produce UI descriptor trees without modifying the living browser DOM.

### Summary

**Architectural Takeaways & Decision Matrix**

❒ Component Function Naming

➔ ALWAYS name custom components in PascalCase so the JSX compiler emits an unquoted function identifier rather than an HTML string literal.

➔ NEVER define component functions in lowercase or camelCase because the browser treats lowercase tags as native elements and fails silently.

❒ Markup Return Invariants

➔ ALWAYS wrap multi-line JSX return statements in parentheses to prevent the JavaScript engine from inserting an unintended semicolon.

➔ ALWAYS return a single root element or React Fragment so the component evaluates to a single valid JavaScript return expression.

❒ Declarative Invocation and Purity

➔ ALWAYS mount components as declarative JSX tags like `<ArticleCard />` so React registers the component fiber node and tracks its lifecycle.

➔ NEVER invoke component functions directly as raw JavaScript calls like `{ArticleCard()}` because direct execution bypasses React's virtual DOM tree and hook isolation.

**DO THIS:** name custom components in PascalCase and mount them declaratively as JSX tags

```jsx right
function ArticleCard() {
  return (
    <article className="article-card">Dispatch</article>
  );
}
function App() {
  return <ArticleCard />;
}
```

**DO NOT DO THIS:** name components in lowercase or call them directly as functions

```jsx wrong
function articleCard() {
  return (
    <article className="article-card">Dispatch</article>
  );
}
function App() {
  return articleCard();
}
```
