# Q24 Principle Map (River Version v1): How Two Sibling Components Share One Changing Value

- **Version**: River Version (`v1`), written under `skills/v10.6`
- **Bank Row**: `questions/questions.md` row 24
- **Topic Tag**: `#lifting_state` | `❱ CORE`
- **Interview Question**: *How do two sibling components share one changing value?*

## Scope

Covered here:
- Two sibling components cannot read each other's state. State is private to the component that declares it, and a sibling's variables are invisible to the other sibling's function.
- Two separate `useState` lines, one in each sibling, make two separate memories. They start equal and drift apart after the first change.
- Lifting state up: remove the state from the child, find the closest common parent of every component that renders based on that state, and declare the state there.
- The React docs' three steps: Remove state from the child components, Pass hardcoded data from the common parent, Add state to the common parent and pass it down together with the event handlers.
- The parent passes the value down as a prop to both siblings, and passes a function down as a callback prop to the sibling that changes it.
- One click or keystroke changes the parent's state once. React renders the parent again, and both siblings receive the same new value in the same render.
- Single source of truth: for each piece of state, one specific component owns it.
- Controlled and uncontrolled components: a component driven by its own state is uncontrolled; a component driven by props is controlled by its parent. A component with a controlled `<input>` inside can still be an uncontrolled component.
- The real beginner mistakes: a window global shared between siblings, a second copy of the state in the other sibling, and a mirrored prop left in the child after lifting.

## Start of the Lecture

**Opening Essence of the chapter**:
- The naked idea is the shape of a way of working, so it opens in plain words before any code, as Examples 3 and 8 of [Opening Essence](../../../react-10/skills/v10.6/opening-essence/SKILL.md) open.
- Everyday case: a house with one clock on the wall of the hall, against a clock in every room. Clocks set to the same time at first drift apart, and nobody knows which one is right. With one clock that everyone reads, two people never disagree about the time. The React docs' name for the one clock is "single source of truth".
- The two ways, named as two forms of one thing, as the Back to the basics table asks: in both, the value lives in `useState`. The one difference is where the `useState` line sits: inside each sibling, or once in the parent above both.
- Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Two `useState('')` lines, one in each sibling, show the same empty value when the page opens. They are two separate memories, and the first keystroke changes only one.
- Key idea: a sibling cannot reach sideways into another sibling. A shared value lives in the closest common parent, goes down to both siblings as props, and a function goes down to the sibling that changes it.
- What is at stake: the user types a name in one part of the page, and the other part of the page stays blank or shows an old name.
- Where readers usually go wrong: they look for a way to send the value sideways from one sibling to the other, through a window global or a DOM query, or they give the second sibling its own copy of the state and try to keep the two copies equal.

**Theme**: a name badge maker. The box where the user types a first name lives in one component, and the badge that shows the name lives in a sibling component, so the badge cannot see what the user types.

**Ways** (developers really choose between these when two components need the same changing value):
1. Lift the state to the closest common parent and pass the value and a callback prop down. The React docs' usual way, this lesson.
2. Put the state in a component above the closest common parent, or create a new component only to hold the state, when no common parent is a sensible owner. Step 4 of `thinking-in-react.md`, options 2 and 3.
3. Put the value in context when the common parent is far above the components that need it and every layer between would pass a prop it never uses: Lessons 28 and 29, named only.
4. Not a good way, named so the reader recognizes it: keeping a copy of the state in each component and copying one into the other with an Effect. The React docs: "Whenever you try to keep two different state variables synchronized, try lifting state up instead!" Lesson 34, named only.

**Example page chosen for this lesson**: a name badge maker. A heading, a text box labelled `First name`, and below it a badge that reads `Hello, my name is` with the typed name in large letters. From Principle 4, a `Start over` button.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx`, `src/components/NameBox.jsx`, `src/components/BadgePreview.jsx`.
- Final parts of the page: `<h1>Make a Name Badge</h1>`, `<label>First name <input /></label>` inside `NameBox`, `<p>Hello, my name is</p>` and `<h2>{firstName}</h2>` inside `BadgePreview`, and `<button>Start over</button>` in `App`.
- Final state: `firstName` in `App`, starting as `useState('')`. Final props: `firstName` and `onFirstNameChange` on `NameBox`, `firstName` on `BadgePreview`.
- Final tree: `App` with two children, `NameBox` and `BadgePreview`. `App` is their closest common parent.
- The state is called `firstName`, not `name`, on purpose. See Open Issues.

## Principles

### Principle 1: `BadgePreview` Cannot See `NameBox`'s `firstName`

- **Rule**: State is private to the component that declares it, so a sibling cannot read it; a second `useState` in the sibling is a second, separate memory, not a shared one.
- **Move**: Steps for a surprise, because the badge stays blank while the box shows `John`, and in the first broken version the whole page goes blank. Side by side for the two `useState('')` lines.
- **Opening Essence**:
  - Smallest code, one parent and two siblings: `function Parent() { return <><Counter /><Display /></>; }`, `function Counter() { const [count, setCount] = useState(0); return <button onClick={() => setCount(count + 1)}>Add</button>; }`, and `function Display() { return <p>{count}</p>; }`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Giving `Display` its own `const [count, setCount] = useState(0);` makes both show `0` when the page opens. They are two memories, and the click changes only the one in `Counter`.
  - The fact behind it, from Lessons 06 and 12: a name created inside one function cannot be seen inside another, and each component keeps its own state.
  - What is at stake: the part of the page that should follow the user's action stays still.
- **Root Distinction**:
  - Junior: "The box and the badge sit next to each other on the page, so the badge can use the box's `firstName`."
  - Senior: siblings share nothing; each one sees only its own variables and the props written on its own tag by the parent.
- **Simplest version**:
  - `Counter` holds `count`; `Display` reads `{count}` without declaring it.
  - Second version: `Display` declares its own `useState(0)`. The user clicks Add three times, and `Display` still shows `0`. `unconfirmed`.
- **Words to teach**:
  - *sibling components*: two components that have the same parent in the UI tree, such as `NameBox` and `BadgePreview` under `App`. React docs use "siblings" for elements with the same parent, in `rendering-lists.md`; the bank question uses "sibling components". Needed at the first tree of the page.
  - Known: state is private to the component that declares it, Lessons 12 and 23. `ReferenceError`, Lesson 06. Each copy of a component has isolated state, Lesson 12. A setter renders its own component again, Lesson 12. Controlled box, Lesson 20. An error during rendering removes the UI, Lesson 23.
  - Helper: none.
- **Side by side**:
  - "with `firstName` declared only in `NameBox`" and "with `useState('')` in both `NameBox` and `BadgePreview`": NOT the same thing as one shared value. Both show an empty value when the page opens; after the first keystroke only the box's copy changes.
  - "with `{firstName}` read in `NameBox`" and "with `{firstName}` read in `BadgePreview`": NOT the same thing. The name exists only inside the function where `useState` created it.
- **Surprises**:
  - With `BadgePreview` reading `{firstName}` that it never declared, the page is blank when it opens, box included:
    1. React renders `App`, then `NameBox`, then `BadgePreview`.
    2. `BadgePreview` asks for `firstName`. `BadgePreview.jsx` has no such name.
    3. JavaScript throws a `ReferenceError` while React is rendering.
    4. React removes the whole UI from the screen, so the box disappears too.
    5. The Console shows the error.
  - With its own `useState('')` in `BadgePreview`, the user types `John` and the badge stays blank:
    1. The page opens. Both copies of `firstName` are `''`. The box and the badge are both empty.
    2. The user types `J`.
    3. `NameBox` calls its own `setFirstName('J')`.
    4. React renders `NameBox` again. The box shows `J`.
    5. Nothing called the setter of `BadgePreview`, so its `firstName` is still `''`.
    6. After `John`, the box shows `John` and the badge under `Hello, my name is` is still empty.
- **Where did that come from?**:
  - `firstName` inside `NameBox`: created by `useState('')` in `NameBox` itself.
  - `firstName` inside `BadgePreview`, first broken version: nobody supplies it. It is not declared there and not passed on the tag.
  - `firstName` inside `BadgePreview`, second broken version: created by a second `useState('')` in `BadgePreview`, a separate memory with the same name.
- **Real beginner mistake** (the syllabus card's friction: a window global):
  1. A developer wants the badge to see the typed name without moving any state.
  2. In `NameBox`, the change handler also writes `window.sharedName = e.target.value`.
  3. `BadgePreview` shows `{window.sharedName}`.
  4. The user types `John`. `NameBox` calls its own setter, and React renders `NameBox` again.
  5. `BadgePreview` is not rendered again, because nothing changed its props or its state, and React does not watch a plain variable. The docs: "Changes to local variables won't trigger renders."
  6. The badge stays blank, although `window.sharedName` now holds `John`.
- **Interview depth**:
  - The tic-tac-toe tutorial: "Since state is private to a component that defines it, you cannot update the `Board`'s state directly from `Square`." The same wall stands between siblings.
  - `state-a-components-memory.md`: "if you render the same component twice, each copy will have completely isolated state!"
  - The tic-tac-toe tutorial on a parent that asks each child for its state: "Although this approach is technically possible in React, we discourage it because the code becomes difficult to understand, susceptible to bugs, and hard to refactor."
  - Reading the box from the DOM with a query during rendering is the card's other friction. `manipulating-the-dom-with-refs.md`: "During the first render, the DOM nodes have not yet been created", and "during the rendering of updates, the DOM nodes haven't been updated yet." DOM nodes from React are Lesson 31; named only.
- **React does**:
  - Console, with `{firstName}` undeclared in `BadgePreview`: `Uncaught ReferenceError: firstName is not defined`. `unconfirmed`; the form matches Lessons 06 and 23, and the lab records the exact lines React 19 prints.
  - Page, same case: blank, with no box and no badge. Quoted rule: "if your application throws an error during rendering, React will remove its UI from the screen." The page result is `unconfirmed`.
  - Page, with a second `useState('')`: the box shows `John`, and the badge shows `Hello, my name is` with nothing under it. `unconfirmed`.
  - Page, with `window.sharedName`: the badge stays blank while typing. `unconfirmed`.
- **Example step**:
  - Creates `src/App.jsx`: `<h1>Make a Name Badge</h1>`, `<NameBox />`, `<BadgePreview />` inside a Fragment.
  - Creates `src/components/NameBox.jsx`: `const [firstName, setFirstName] = useState('');` and `<label>First name <input value={firstName} onChange={e => setFirstName(e.target.value)} /></label>`.
  - Creates `src/components/BadgePreview.jsx`: `<p>Hello, my name is</p>` and `<h2>{firstName}</h2>`, first with `firstName` undeclared, then with its own `useState('')`.

### Principle 2: `firstName` Moves Up to `App`

- **Rule**: To share a value between siblings, remove the state from the child, find the closest common parent of every component that renders based on it, and have that parent pass the value down as a prop to each of them.
- **Move**: Smallest code first, because the new idea is where one line of code lives. Everyday image for the word "lifting". Side by side for the state inside the child and the prop from the parent.
- **Opening Essence**:
  - Smallest code, the docs' Step 2 with a hardcoded value: `function Parent() { return <><Counter count={3} /><Display count={3} /></>; }`, with `Counter` and `Display` both reading `count` from their props.
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* Both siblings now show `3`, because both get the value from the same place, the parent's tag.
  - Everyday image: moving the clock from one bedroom to the hall, one floor up from both rooms, where everyone sees it. The docs' word "lifting": the state goes up the tree, from a child to the parent above both.
  - A `tree` of the page before and after: before, `firstName` sits in `NameBox`; after, it sits in `App`, with arrows down to `NameBox` and `BadgePreview`.
- **Root Distinction**:
  - Junior: "The value belongs to the box, because the user types it there."
  - Senior: a value belongs to the closest component above every component that renders based on it; where the user types it does not decide where it lives.
- **Simplest version**:
  - Step 1 of the docs: delete `const [count, setCount] = useState(0);` from the child, and add `count` to its props.
  - Step 2 of the docs: the parent writes `count={3}` on both tags.
- **Words to teach**:
  - *lifting state up*: moving a state variable out of the children and into their closest common parent, then passing it down as props. React docs, `sharing-state-between-components.md`: "This is known as *lifting state up,* and it's one of the most common things you will do writing React code." Needed when `firstName` leaves `NameBox`.
  - *closest common parent*: the first component above every component that needs the value. The docs' way to find it, Step 4 of `thinking-in-react.md`: 1. identify every component that renders something based on that state; 2. find their closest common parent; 3. put the state there, or above it. Needed when the reader looks at the tree and finds `App`.
  - *hardcoded value*: a fixed value written in the code, such as `firstName="John"`, used in the docs' Step 2 so the reader sees both siblings show the value before any state exists. Needed at the `John` badge.
  - Known: props from the tag, Lesson 08. The controlled box and the read-only field error, Lesson 20.
  - Helper: none.
- **Side by side**:
  - "with `useState('')` in `NameBox`" and "with `firstName` received as a prop": NOT the same thing. The first lets `NameBox` change the value; with the second, the docs: "the `Panel` component now has *no control* over the value of `isActive`--it's now up to the parent component!"
  - "with `firstName="John"` on `<NameBox>`" and "with `firstName="John"` on `<BadgePreview>`": the exact same value, written once in the same parent, so the box and the badge agree.
- **Surprises**:
  - With the hardcoded `firstName="John"` on both tags, the user cannot change the box:
    1. The page opens. The box shows `John` and the badge shows `John`.
    2. The user types `ny` at the end of the box.
    3. The input's `value` comes from the `firstName` prop, and `NameBox` has no setter to call.
    4. React puts `John` back after every keystroke, as in Lesson 20.
    5. The Console shows the read-only field error.
    6. The docs, Step 5 of `thinking-in-react.md`: "you'll see that React ignores your input. This is intentional."
- **Where did that come from?**:
  - `firstName` inside `NameBox` and inside `BadgePreview`: `App` writes `firstName="John"` on both tags; React puts it inside `props`, and each parameter list unpacks it, Lesson 08.
  - `App` as the parent: `App` returns both tags, so it is the first component above both in the UI tree, Lesson 06.
- **Real beginner mistake** (the React docs' `Accordion`, `sharing-state-between-components.md`):
  1. Each `Panel` keeps its own `isActive` state.
  2. The page should show only one open panel at a time.
  3. The user presses Show on both panels.
  4. Both panels open, because "pressing one panel's button does not affect the other panel--they are independent."
  5. The fix moves the state up to `Accordion`, the closest common parent, and passes `isActive` down to each panel.
- **Interview depth**:
  - The tic-tac-toe tutorial, in bold: "To collect data from multiple children, or to have two child components communicate with each other, declare the shared state in their parent component instead."

### Principle 3: `onFirstNameChange` Lets `NameBox` Change `App`'s `firstName`

- **Rule**: The common parent declares the state, passes the value down to every sibling that shows it, and passes a callback prop down to the sibling that changes it; one change renders the parent again, and every sibling gets the same new value in the same render.
- **Move**: Steps for a surprise, because the user types in one sibling and the other sibling changes, with no code connecting the two siblings.
- **Opening Essence**:
  - Smallest code, as in the docs' Step 3: `function Parent() { const [count, setCount] = useState(0); return <><Counter count={count} onAdd={() => setCount(count + 1)} /><Display count={count} /></>; }`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* It looks as if `Counter` sends the number sideways to `Display`. `Counter` only calls the parent's function; the parent's new render gives both of them the same `count`.
  - Key idea from the docs: "For each unique piece of state, you will choose the component that 'owns' it." One owner means the two siblings can never disagree.
- **Root Distinction**:
  - Junior: "After the box updates, the badge must be told to update too."
  - Senior: neither sibling holds the value; the parent renders once with the new value, and both siblings read it from their props in that same render.
- **Simplest version**:
  - `App`: `const [firstName, setFirstName] = useState('');`
  - `<NameBox firstName={firstName} onFirstNameChange={setFirstName} />` and `<BadgePreview firstName={firstName} />`
  - `NameBox`: `<input value={firstName} onChange={e => onFirstNameChange(e.target.value)} />`
- **Words to teach**:
  - *single source of truth*: for each piece of state, one specific component holds it. React docs: "It doesn't mean that all state lives in one place--but that for _each_ piece of state, there is a _specific_ component that holds that piece of information." The docs call `Accordion` the "source of truth" for which panel is active. Needed after the trace, with the clock image of the chapter opening.
  - Known: callback prop, passing the setter itself, `on` and `handle` names, Lesson 23. A re-render renders the children again, Lesson 13. Several updates in one event, one render, Lesson 16. `e.target.value`, Lesson 20.
  - Helper: none.
- **Side by side**:
  - "with `firstName` in `NameBox`", Principle 1, and "with `firstName` in `App`": NOT the same thing. In the first, typing renders only `NameBox`; in the second, typing renders `App`, and with it both siblings.
  - "with `onFirstNameChange={setFirstName}`" and "with `onFirstNameChange={handleFirstNameChange}`", where `handleFirstNameChange(text)` calls `setFirstName(text)`: the exact same thing for this page. The docs pass the setter itself in `thinking-in-react.md` and a handler in the synced inputs Solution.
- **Surprises**:
  - The user types `J` in the box, and the badge in another component shows `J`:
    1. The user types `J`.
    2. React calls the input's `onChange` in `NameBox` with the event object.
    3. `NameBox` calls `onFirstNameChange('J')`. `onFirstNameChange` is `setFirstName` from `App`.
    4. `App`'s `firstName` becomes `'J'` for the next render.
    5. React renders `App` again, and with it `NameBox` and `BadgePreview`.
    6. `NameBox` receives `firstName` `'J'`, and the box shows `J`.
    7. `BadgePreview` receives the same `'J'` in the same render, and the badge shows `J`.
    8. No line of `NameBox` mentions `BadgePreview`.
  - The letter in the box itself comes back from `App`: if `App` did not change `firstName`, the box would put the old text back, as in Principle 2.
- **Where did that come from?**:
  - `onFirstNameChange` inside `NameBox`: `App` writes `onFirstNameChange={setFirstName}` on the tag, and the parameter list unpacks it.
  - `'J'` inside `setFirstName`: the browser puts the box's new text in `e.target.value`, and `NameBox` passes it as the argument.
  - `firstName` inside `BadgePreview`: `App` writes `firstName={firstName}` on its tag, the same variable it gives `NameBox`.
- **Real beginner mistake** (the React docs, `thinking-in-react.md`, Steps 4 and 5):
  1. A developer lifts `firstName` into `App` and passes `firstName={firstName}` down to both siblings.
  2. The developer forgets to pass a function down to `NameBox`.
  3. The user types in the box.
  4. React ignores the input, because the box's `value` is always `firstName` from `App`, and nothing sets it.
  5. The Console shows the read-only field error.
  6. The docs' fix: "The state is owned by `FilterableProductTable`, so only it can call `setFilterText` and `setInStockOnly`. To let `SearchBar` update the `FilterableProductTable`'s state, you need to pass these functions down to `SearchBar`."
- **Interview depth**:
  - The syllabus card's "Under the Hood": with one owner, both siblings get the identical value in the same render, so there is no moment when one shows the new name and the other the old one.
  - The tic-tac-toe tutorial: calling the setter "will trigger a re-render of the components that use the `squares` state (`Board`) as well as its child components".
  - `you-might-not-need-an-effect.md`: updating the parent "during the event" instead of from an Effect means "there will only be one render pass", and "Whenever you try to keep two different state variables synchronized, try lifting state up instead!" Effects, Lessons 32 and 34.
  - The docs' Recap order: move the state to the common parent, pass the information down through props, pass the event handlers down "so that the children can change the parent's state."
  - "Filtering a list" Solution: the parent keeps `query`, calculates `results = filterItems(foods, query)`, and passes `results` to the other sibling, Lesson 22 joined with this lesson.
  - Two components that call the same custom hook do not share state; each gets its own, Lesson 39.

  - Console: no error or warning. `unconfirmed`.

### Principle 4: Start Over Clears `NameBox` from `App`

- **Rule**: A component driven by its own state is uncontrolled; a component driven by props is controlled by its parent, so only the parent can reset it; the child must use the prop directly and must not copy it into its own state.
- **Move**: Side by side, because `<input value onChange>` and `<NameBox firstName onFirstNameChange>` look different and follow the same idea, while a mirrored prop and the prop itself work the same while typing and differ after Start over.
- **Opening Essence**:
  - Smallest code, side by side: `<input value={text} onChange={e => setText(e.target.value)} />` and `<NameBox firstName={firstName} onFirstNameChange={setFirstName} />`.
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* The box of Lesson 20 gets its text and a function from its parent; `NameBox` now gets its name and a function from `App`. The same idea, one level up. The docs use the same word, "controlled", for both.
  - Second confusion: *"It may look the same, or work the same at first, but it is NOT the same thing!"* `NameBox` in Principle 1 also had a controlled `<input>` inside it, yet `NameBox` itself was uncontrolled, because `App` could not influence it.
  - Key idea: the parent decides what a controlled child shows, so the parent can change it from anywhere, such as a button outside the child.
- **Root Distinction**:
  - Junior: "`NameBox` has a controlled input inside, so `NameBox` is a controlled component."
  - Senior: "controlled" asks who drives the information: an input controlled by `NameBox`'s state still leaves `NameBox` uncontrolled; only props from `App` make `NameBox` controlled by `App`.
- **Simplest version**:
  - `App` adds `<button onClick={() => setFirstName('')}>Start over</button>`.
  - The user types `John`, clicks Start over, and the box and the badge are both empty. `unconfirmed`.
- **Words to teach**:
  - *uncontrolled component*: a component whose important information lives in its own state, so its parent cannot influence it. React docs: "the original `Panel` component with an `isActive` state variable is uncontrolled because its parent cannot influence whether the panel is active or not." Needed when looking back at `NameBox` in Principle 1.
  - *controlled component*: a component whose important information comes from props. React docs: "a component is 'controlled' when the important information in it is driven by props rather than its own local state. This lets the parent component fully specify its behavior." Needed at the Start over button.
  - The trade-off, from the docs: "Uncontrolled components are easier to use within their parents because they require less configuration. But they're less flexible when you want to coordinate them together. Controlled components are maximally flexible, but they require the parent components to fully configure them with props."
  - Known: controlled and uncontrolled inputs, Lesson 20. Mirroring props in state, Lesson 22. `onClick`, Lesson 11.
  - Helper: none.
- **Side by side**:
  - "with `<input value={text} onChange={...}>`" and "with `<NameBox firstName={firstName} onFirstNameChange={setFirstName}>`": the exact same thing, one level up. A value and a function come from the parent, so the parent drives what the child shows.
  - "with the `firstName` prop used directly" and "with `useState(firstName)` in `NameBox`": NOT the same thing. Both work while the user types; after Start over, only the first empties the box.
- **Surprises**:
  - With the mirrored prop, `const [text, setText] = useState(firstName);` in `NameBox`, `value={text}`, and a handler that calls both `setText` and `onFirstNameChange`, Start over empties the badge but not the box:
    1. The user types `John`. `text` in `NameBox` and `firstName` in `App` both become `'John'`. The box and the badge show `John`.
    2. The user clicks Start over.
    3. `App` calls `setFirstName('')`, and React renders `App`, `NameBox`, and `BadgePreview` again.
    4. `BadgePreview` receives `''`, and the badge is empty.
    5. `NameBox` receives `firstName` `''`, but `useState(firstName)` reads its argument only on the first render.
    6. `text` stays `'John'`, so the box still shows `John` above an empty badge.
- **Where did that come from?**:
  - `setFirstName` inside the Start over button: declared in `App` itself, next to the button, so `App` needs no callback prop.
  - `''` inside `NameBox` after Start over: `App` passes its new `firstName` on the `<NameBox>` tag.
  - `text` inside `NameBox`, mirrored version: a second state in `NameBox`, filled from the prop on the first render only, Lesson 22.
- **Real beginner mistake** (mirroring a prop after lifting state, the React docs' DeepDive "Don't mirror props in state"):
  1. A developer lifts `firstName` into `App`, but keeps a `useState` line in `NameBox` and fills it from the prop: `useState(firstName)`.
  2. Typing works, because the handler calls both setters.
  3. `App` sets `firstName` to `''` from the Start over button.
  4. The box keeps the old name, because "The state is only initialized during the first render."
  5. The badge and the box now disagree: the bug that lifting state was meant to remove.
  6. The docs' fix: "use the `messageColor` prop directly in your code." Here, `value={firstName}`.
- **Interview depth**:
  - The docs: "'controlled' and 'uncontrolled' aren't strict technical terms--each component usually has some mix of both local state and props."
  - The docs: "consider which information in it should be controlled (via props), and which information should be uncontrolled (via state). But you can always change your mind and refactor later."
  - The docs' `Toggle` is "fully controlled by its parent" once it receives `isOn` and `onChange` from props and keeps no state, `you-might-not-need-an-effect.md`.
  - "It is common that you will move state down or back up while you're still figuring out where each piece of the state 'lives'."
  - A mirrored prop is right only when later values should be ignored, and its name then starts with `initial` or `default`, such as `initialColor`, Lesson 22.

  - Page, controlled `NameBox`: after Start over, the box and the badge are both empty. `unconfirmed`.
  - Page, mirrored `NameBox`: after Start over, the box shows `John` and the badge is empty. `unconfirmed`.
  - Console, both cases: no error or warning. `unconfirmed`.

  - In `App.jsx`: adds `<button onClick={() => setFirstName('')}>Start over</button>` under `<BadgePreview>`.

## Interview Points

1. Sibling components cannot read each other's state: state is private to the component that declares it, and a sibling sees only the props its parent writes on its tag.
2. A second `useState` in the other sibling is a second memory: both start equal, and they drift apart after the first change.
3. Lifting state up: remove the state from the children, find the closest common parent of every component that renders based on it, and declare the state there.
4. The parent passes the value down as a prop to each sibling that shows it, and passes a callback prop, such as `onFirstNameChange={setFirstName}`, to the sibling that changes it.
5. One change sets the parent's state once; React renders the parent and both siblings again, and both siblings get the identical value in the same render.
6. Single source of truth: for each piece of state, one specific component owns it; it does not mean all state lives in one place.
7. A component driven by its own state is uncontrolled; a component driven by props is controlled, so its parent can reset it. Do not mirror the lifted prop back into the child's state.
8. When the common parent is far up and many layers pass a prop they never use, context is the next tool, Lesson 28; keeping two copies in step with an Effect is the wrong tool, Lesson 34.
