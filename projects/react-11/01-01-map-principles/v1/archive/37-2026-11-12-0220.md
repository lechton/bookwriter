# Q37 Principle Map (River Version v1): Removing Effect Dependencies by Changing the Code

- **Version**: River Version (`v1`), written under `skills/v10.6`
- **Bank Row**: `questions/questions.md` row 37
- **Topic Tag**: `#effect_dependencies` | `❱ CORE`
- **Interview Question**: *How do you remove unnecessary effect dependencies, and when must a dependency stay?*

## Scope

Covered here:
- The docs' starting point: "Unnecessary dependencies may cause your Effect to run too often, or even create an infinite loop."
- The dependency array describes the code. The docs: "You don't *choose* what to put on that list. The list *describes* your code. To change the dependency list, change the code."
- The three steps the docs give: change the code, follow the linter, and if the list is still wrong, change the code again.
- To remove a dependency, prove that it is not reactive. The docs: "**To remove a dependency, "prove" to the linter that it *doesn't need* to be a dependency.**"
- Object and function dependencies: an object or a function created in the component body is a different value on every render. The docs: "**This problem only affects objects and functions. In JavaScript, each newly created object and function is considered distinct from all the others. It doesn't matter that the contents inside of them may be the same!**"
- The fixes the docs give for object and function dependencies: move a static one outside the component, move a dynamic one inside the Effect, read primitive values out of an object prop, call a pure function prop outside the Effect.
- Reading state to calculate the next state: pass an updater function, so the Effect no longer reads that state.
- When a dependency must stay: when a change of that value means the Effect must re-synchronize, such as `roomId`. The docs: "It is important to declare it as a dependency!"
- The docs' list of questions to ask about each unwanted dependency, used as the order of the lesson's tools.
- Suppressing the linter as the wrong way, shown once on this lesson's page, where it freezes a list.

## Start of the Lecture

**Opening Essence of the chapter**:
- No short code shows the idea before the reader knows the screen, so the idea opens in plain words on a real screen, as Examples 8 and 9 of opening-essence open.
- The real screen: a chat app with rooms, as in Slack. A menu picks the room. The heading reads `Welcome to the general room!`. Under it, the messages that arrive in the room, and a box where the user types a message.
- What the user does, and what the user expects:
  1. Types `hi` in the message box: the letters appear in the box. Nothing else changes; the user is still in `general`.
  2. Picks `travel` in the menu: the app leaves `general` and connects to `travel`.
  3. Messages arrive, `hey` or `lol`: each one is added under the ones before it.
- The question that screen raises for the developer: the linter asks for a dependency the developer believes does not matter, and after adding it the chat reconnects on every letter the user types, or on every message that arrives. How do you make the dependency go away without lying to the linter?
- The answer, the docs: "**If you want to change the dependencies, change the surrounding code first.**"
- Key idea the reader must remember: you never pick the dependencies; you change the code until the list the linter asks for is the list you want. A value may leave the list only when the code no longer reads a reactive value there.
- Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"*
  1. Two `options` objects made on two renders, both with `serverUrl` `'https://localhost:1234'` and `roomId` `'music'`, look the same.
  2. For React they are not the same. The docs: `console.log(Object.is(options1, options2)); // false`.
  3. Two strings `'music'` made on two renders are the same for React. The docs: `console.log(Object.is(roomId1, roomId2)); // true`.
- What is at stake for the user, on the example page:
  1. With `options` made in the component body and listed in the array, each letter typed in the box disconnects and reconnects the chat. The docs: "the chat re-connects as you type."
  2. With `messages` read inside the Effect and listed in the array, each message that arrives reconnects the chat. The docs: "every new message will make the chat re-connect. The user would not like that!"
  3. With the dependency deleted and the linter suppressed, the chat stays connected, and the list shows only the newest message. The docs' twin, a timer: "you always see `1`."
- Where readers usually go wrong:
  1. They delete the dependency and add `// eslint-disable-next-line react-hooks/exhaustive-deps`. The docs: "By suppressing the linter, you "lie" to React about the values your Effect depends on."
  2. They think an object with the same contents is the same dependency.
  3. They remove a dependency that must stay, such as `roomId`, because the Effect runs "too often".

**Theme**: a chat room that must reconnect when the user picks another room, and never because the user types a letter or a message arrives.

**Ways** (the docs' questions for a dependency you do not want, and the tool each one leads to):
1. "Should this code move to an event handler?": when the code runs because of one interaction, such as a form submit. Lesson 34. Named only.
2. "Is your Effect doing several unrelated things?": split it into two Effects. Lesson 35. Named only.
3. "Are you reading some state to calculate the next state?": pass an updater function. This lesson, Principle 3.
4. "Do you want to read a value without "reacting" to its changes?": move that code into an Effect Event. Lesson 36. Named only.
5. "Does some reactive value change unintentionally?": an object or a function made during rendering; move it outside the component, inside the Effect, or read primitive values out of it. This lesson, Principles 1 and 2.
6. Suppress the linter: shown only as the wrong way, in Principle 3. The docs: "We recommend treating the dependency lint error as a compilation error."

## Principles

### Principle 1: Typing in the Message Box Reconnects the Chat

- **Rule**: An object or a function created in the component body is a new value on every render, so when the Effect lists it, every re-render re-synchronizes the Effect, even when the contents are the same.
- **Move**: Steps for a surprise, because the user types a letter in a box that has nothing to do with the connection, and the Console shows a disconnect and a connect.
- **Opening Essence**:
  - The real screen and action: the user is in `general` and types `h` in the message box.
  - Smallest code, the docs' shape for this page:
    1. `const options = { serverUrl: serverUrl, roomId: roomId };` in the component body.
    2. `const connection = createConnection(options);` inside the Effect.
    3. `}, [options]);`
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"*
    1. The `options` of the last render and the `options` of this render hold the same `serverUrl` and the same `roomId`.
    2. They are two objects. The docs: "React sees that the `options` object is a *different object* from the `options` object created during the last render."
  - The docs' proof, with two renders written by hand:
    1. `const options1 = { serverUrl: 'https://localhost:1234', roomId: 'music' };`
    2. `const options2 = { serverUrl: 'https://localhost:1234', roomId: 'music' };`
    3. `console.log(Object.is(options1, options2)); // false`
  - Key idea, the docs: "**Object and function dependencies can make your Effect re-synchronize more often than you need.**"
  - What is at stake: the user types a message, and the chat drops its connection and opens a new one after every letter.
- **Root Distinction**:
  - Junior: "`options` has the same server and the same room, so React sees nothing new."
  - Senior: `Object.is` compares an object by which object it is, not by what is inside it; an object made during rendering is a new object on every render.
- **Simplest version**:
  - `const a = { name: 'John' }; const b = { name: 'John' }; console.log(Object.is(a, b)); // false` and `console.log(Object.is('John', 'John')); // true`. The second line follows the docs' `roomId1` and `roomId2` example; the names are ours.
- **Words to teach**:
  - *object dependency* and *function dependency*: the docs' names for an object or a function listed in the array. Provided by the docs as names. Needed when `[options]` appears.
  - *created from scratch*: the docs' words for what happens to `options` on each render. "A new `options` object is created from scratch on every re-render of the `ChatRoom` component." Needed when the user types the first letter.
  - *distinct*: the docs' word for two objects that are not the same object. Needed in the same moment.
  - Known: `Object.is`, the dependency array, Lesson 32. Reactive value, re-synchronize, the component body is reactive, Lesson 35. Controlled `<input>`, Lesson 20. Re-render, Lesson 13.
  - Helper: none.
- **Side by side**:
  - "`options` made on the last render" and "`options` made on this render": NOT the same thing for React, though they hold the same text. `Object.is` returns `false`.

### Principle 2: options Built Inside the Effect Leaves Only roomId

- **Rule**: Move an object or a function that depends on props or state inside the Effect, and one that depends on neither outside the component; then it is not reactive, it leaves the array, and only the primitive values it reads, such as `roomId`, stay.

- **Opening Essence**:

## Interview Points

- You do not choose the dependencies; the array lists every reactive value the Effect reads, and the linter checks it.
- To change the array, change the code first, then follow the linter; if the array is still wrong, change the code again.
- A dependency is removable only when the code no longer reads a reactive value there, and the linter agrees without a suppression comment.
- A dependency must stay when a change of that value means the Effect must re-synchronize, such as the chat room the user picked.
- React compares each dependency with `Object.is`. Strings and numbers are compared by content; each new object and function is a different value, even with the same contents.
- An object or a function created in the component body re-synchronizes the Effect on every render. Move a static one outside the component, a dynamic one inside the Effect, or read primitive values out of an object prop.
- When the Effect sets state from the same state, pass an updater function, such as `setMessages(msgs => [...msgs, msg])`, so the state is not read and leaves the array.
- The docs' other questions: should the code be in an event handler, is the Effect doing two unrelated things, and does it need the latest value without reacting, which is an Effect Event.
- An infinite cycle needs an Effect that sets state and a dependency that changes because of that state.
- Suppressing the linter lies to React and leaves stale values; treat the lint error as a compilation error. `useMemo` and `useCallback` are the docs' last resort, not the first fix.
