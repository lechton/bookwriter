# Q22 Principle Map (River Version v1): Choosing Which Values Belong in State

- **Version**: River Version (`v1`), written under `skills/v10.6`
- **Bank Row**: `questions/questions.md` row 22
- **Topic Tag**: `#state_structure` | `❱ CORE`
- **Interview Question**: *How do you decide which values belong in state and which are derived?*

## Scope

Covered here:
- Redundant state: a value the page shows that can be calculated from state or props during rendering, such as a count, is a `const` in the component body, not a state variable.
- A filtered list is calculated from two state values, the full list and the search text. Only those two are state.
- The test from Thinking in React: a value is not state when it stays the same over time, when it comes from a parent through props, or when it can be computed from existing state or props.
- Duplication in state: keep the id of the chosen item in state, not a copy of the item object, and find the item during rendering.
- Mirroring a prop in state: `useState(name)` reads the prop only on the first render, so later values from the parent never reach the state. The deliberate case is named with `initial` or `default`.
- Group related state: two values that always change together become one object, such as `position` with `x` and `y`.
- Avoid deeply nested state: store items flat, by id, with each item holding an array of its child ids.

## Start of the Lecture

**Opening Essence of the chapter**:
- The naked idea is the shape of a way of working, so it opens in plain words before any code, as Examples 3 and 8 of [Opening Essence](../../../react-10/skills/v10.6/opening-essence/SKILL.md) open.
- Everyday case: a shopping list on paper. The number of items is counted from the lines when needed, not written at the bottom. A written number needs fixing after every added or crossed-out line, and one fix is eventually forgotten.
- The two ways to give the page a value, named as two forms of one thing, as the Back to the basics table asks: both are values the page shows. The one difference: React remembers a state value between renders, and a calculated value is made again from state on every render.
- Key idea: state holds only what changes over time and cannot be calculated from anything else. Every other value is calculated during rendering.
- What is at stake: the page shows two answers that disagree, such as a line saying 5 players above a list of 4.
- Where readers usually go wrong: they make a new `useState` for every value the page shows, then must remember to call every setter in every handler.
- The React docs' own words for the goal: "make state easy to update without introducing mistakes", and, paraphrasing Albert Einstein, "Make your state as simple as it can be--but no simpler." (`choosing-the-state-structure.md`)
- No look-alike pair for the chapter opening. The look-alike pairs live in the principles.

**Theme**: a team page shows a player count, a search box, and a captain line, and each value stored in its own state falls out of sync with the list after one click on Remove.

**Ways** (developers really choose between these for a value the page shows):
1. Store it in its own state and call its setter in every handler that changes what it depends on. Works only while every handler remembers. The docs: "Although you could carefully change each event handler to update the `total` and `packed` counters correctly, the root problem is that these state variables exist at all."
2. Calculate it during rendering with a `const` in the component body. The docs' default.
3. Calculate it during rendering and cache it with `useMemo` when a measured calculation is slow. Lesson 56, named only.
4. Store it in state and update it from an Effect. The docs: "This is more complicated than necessary. It is inefficient too". Lesson 34, named only.

**The five rules on the React docs' page** (`choosing-the-state-structure.md`), listed once at the start:
1. Group related state. Principle 5.
2. Avoid contradictions in state. Lesson 21.
3. Avoid redundant state. Principles 1, 2, and 4.
4. Avoid duplication in state. Principle 3.
5. Avoid deeply nested state. Principle 6.

## Principles

### Principle 1: `players.length` Keeps the Count Right

- **Rule**: When a value can be calculated from state or props during rendering, write it as a `const` in the component body, not as a state variable.
- **Move**: Side by side, because a stored count and a calculated count look the same on the first render and differ after the first click. Steps for a surprise for the line that says 5 above 4 rows.
- **Opening Essence**:
  - Smallest code: `const [names, setNames] = useState(['John', 'Mia', 'Sara']);` with `const [count, setCount] = useState(3);`, beside the same `names` with `const count = names.length;`. Both render `<p>{count} names</p>`.
  - Everyday image: the shopping list of the chapter opening, counted from its lines.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both show `3 names` on the first render. They differ when a handler changes `names` and does not call `setCount`.
- **Root Distinction**:
  - Junior: "The page shows a count, so the count needs its own state."
  - Senior: the count is already inside the list; the code reads it from the list on every render.
- **Simplest version**:
  - `const [names, setNames] = useState(['John', 'Mia', 'Sara']);`
  - `const count = names.length;`
  - `<p>{count} names</p>` shows `3 names`.
- **Words to teach**:
  - *redundant state*: a state variable whose value can be calculated from other state or props. Named by the React docs. Needed when the stored count is shown beside the calculated one.
  - *calculate during rendering*: a `const` in the component body, run again every time React calls the component. The React docs' phrase. Needed at the fix.
  - *out of sync*: two values on the page that should agree and do not. The React docs' phrase. Needed when the line says 5 above 4 rows.
  - Known: `useState` and the setter, Lesson 12. React calls the component again on every re-render, Lesson 13. `filter`, Lesson 19. `map` and `key`, Lesson 18. Arrow handler with an argument, Lesson 11.
  - Helper: none.
- **Side by side**:
  - "with `useState(initialPlayers.length)`" and "with `players.length`": NOT the same thing. The stored count changes only when a handler calls `setCount`; the calculated count changes whenever `players` changes.
- **Surprises**:
  - With `count` in state: the user clicks Remove on John, the row disappears, and the line still says `5 players`.
    1. The user clicks Remove on John.
    2. `handleRemove` calls `setPlayers` with a new array of four players.
    3. `handleRemove` does not call `setCount`.
    4. React renders `TeamList` again. `players` holds four players, and `count` still holds `5`.
    5. The list shows four rows, and the line shows `5 players`.
- **Where did that come from?**:
  - `count` in the JSX of the fixed version, with no `useState` for it: the `const count = players.length;` line above the `return` supplies it.
    1. React calls `TeamList`.
    2. `useState` gives back the current `players`.
    3. The `const` line reads `players.length`.
    4. The JSX puts that number on the page.
- **Real beginner mistake** (the React docs' packing list challenge):
  1. A packing list keeps `items`, `total`, and `packed` as three state variables.
  2. Each handler updates the counters by hand: Add calls `setTotal(total + 1)`, the checkbox calls `setPacked(packed + 1)` or `setPacked(packed - 1)`.
  3. The Delete handler calls `setTotal(total - 1)` and forgets `packed`.
  4. The user marks an item as packed, then deletes it.
  5. The footer counts a packed item that is no longer on the list.
  6. The docs' fix: remove `total` and `packed` from state and calculate both from `items`.
- **Interview depth**:
  - The docs: "When you call `setFirstName` or `setLastName`, you trigger a re-render, and then the next `fullName` will be calculated from the fresh data."
  - The docs' check-in form: `fullName` is redundant because it is `firstName + ' ' + lastName`.
  - The docs' shopping list in Thinking in React: "don't store the number of items as another state value--instead, read the length of your array."
  - The docs' tic-tac-toe tutorial removes `xIsNext` from state and calculates it from `currentMove`.
  - Managing State: "many bugs in React apps are fixed this way."
- **React does**:
  - Page, with `count` in state: four rows under the line `5 players` after one Remove. `unconfirmed`, the lab checks it.
  - Page, with `players.length`: `4 players` after one Remove. `unconfirmed`.
  - Console: no warning in either version. `unconfirmed`.
- **Example step**:
  - Creates `src/components/TeamList.jsx`: `initialPlayers`, `const [players, setPlayers] = useState(initialPlayers);`, `<h1>Team</h1>`, and a `<ul>` with one row per player, the name and a `Remove` button.
  - `handleRemove(id)` calls `setPlayers(players.filter(player => player.id !== id))`.
  - First version: `const [count, setCount] = useState(initialPlayers.length);` and `<p>{count} players</p>`.
  - Fix: that state line is deleted, and `const count = players.length;` takes its place.
  - `src/App.jsx` renders `<TeamList />`.
- **Code names**: `TeamList.jsx`, `App.jsx`, `TeamList`, `initialPlayers`, `players`, `setPlayers`, `count`, `setCount`, `useState(initialPlayers.length)`, `players.length`, `handleRemove`, `players.filter(player => player.id !== id)`, `Team`, `Remove`, `5 players`, `4 players`, `names`, `John`, `Mia`, `Sara`, `Leo`, `Anna`

### Principle 2: `query` Filters the List During Rendering

- **Rule**: Keep the search text in state and calculate the filtered list from the full list and the search text during rendering; never keep the filtered list as its own state.
- **Move**: Smallest code first for the three questions of Thinking in React, because the test is new. Steps for a surprise for the removed player who stays on the list.
- **Opening Essence**:
  - Smallest code: `const visibleNames = names.filter(name => name.includes(query));` with `names` and `query` as the only two state variables.
  - The three questions, from Thinking in React, asked of each value:
    1. Does it stay the same over time? Then it is not state.
    2. Is it passed in from a parent through props? Then it is not state.
    3. Can it be computed from existing state or props? Then it is definitely not state.
  - The four values of the team page sorted by the questions: the players change when the user removes one, so state. The search text changes as the user types and cannot be computed, so state. The filtered list is computed from both, so not state. The count line is computed from both lists, so not state.
  - No look-alike pair at the start. Key idea: state holds the minimal set of changing data, and everything else is computed. What is at stake: a filtered list kept in state misses every change that does not come through the search box. Where readers go wrong: they filter inside `onChange`, because typing is when the list seems to change.
- **Root Distinction**:
  - Junior: "The list changes when the user types, so the filtered list is state, set in `onChange`."
  - Senior: the user changes only the search text; the filtered list follows from the search text and the full list on every render.
- **Simplest version**:
  - `const [names, setNames] = useState(['John', 'Mia', 'Sara']);`
  - `const [query, setQuery] = useState('');`
  - `const visibleNames = names.filter(name => name.includes(query));`
  - With `query` as `'a'`, `visibleNames` is `['Mia', 'Sara']`.
- **Words to teach**:
  - *minimal set of changing data*: the Thinking in React description of state. Needed with the three questions.
  - *derive, derived*: another word for a value calculated from state or props. The interview question uses it, and the react.dev reference page `set-state-in-render` writes "Derive during render". Needed once, when the interview word is matched to the docs' phrase.
  - *essential state*: state that cannot be removed without breaking what the page does. The docs: "You know they are essential, because you can't remove any of them without breaking the functionality." Needed after the sort, when only `players` and `query` are left.
  - Known: controlled box with `value` and `onChange`, Lesson 20. `filter`, Lesson 19. `includes`, Lesson 21. Props, Lesson 08.
  - Helper: none new. `includes` is case-sensitive, so `a` does not match `Anna`'s capital A but does match her last letter. `unconfirmed` against MDN.
- **Side by side**:
  - "with `filteredPlayers` in state, set in `onChange`" and "with `visiblePlayers` calculated from `players` and `query`": NOT the same thing. Both show the right rows while the user types; only the calculated one also follows a Remove.
- **Surprises**:
  - With `filteredPlayers` in state: the user clicks Remove on John and John stays on the list, while the count line says `Showing 5 of 4 players`.
    1. On the first render, `filteredPlayers` starts as `initialPlayers`, all five.
    2. The user clicks Remove on John.
    3. `handleRemove` calls `setPlayers` with four players and does not touch `filteredPlayers`.
    4. React renders again. `players` has four players; `filteredPlayers` still has five.
    5. The list is drawn from `filteredPlayers`, so John's row stays.
    6. The line reads `filteredPlayers.length` and `players.length`: `Showing 5 of 4 players`.
- **Where did that come from?**:
  - `visiblePlayers` in the JSX, with no `useState`: the `const visiblePlayers = players.filter(...)` line above the `return` supplies it on every render.
  - `player` inside the `filter` callback: `filter` calls the arrow function once for each item of `players` and passes that item in, Lesson 19.
- **Real beginner mistake** (the bank friction, the syllabus card):
  1. A developer stores `articles`, `filterText`, `filteredArticles`, and `articleCount` as four state variables.
  2. The search box's `onChange` sets `filterText` and `filteredArticles`.
  3. A new article is added through a different handler.
  4. That handler updates `articles` only.
  5. The counter says "0 results" while five articles are displayed.
- **Interview depth**:
  - Thinking in React sorts four values of a product table: the original list is passed in as props, so not state; the search text and the checkbox are state; the filtered list "isn't state because it can be computed".
  - Thinking in React calls the principle DRY, Don't Repeat Yourself: "Figure out the absolute minimal representation of the state your application needs and compute everything else on-demand."
  - Reacting to Input, Step 4: `isEmpty` is removed and replaced by `answer.length === 0`; `isError` is replaced by `error !== null`.
  - You Might Not Need an Effect: keeping `visibleTodos` in state and setting it from an Effect "is both unnecessary and inefficient". Lesson 34.
  - When a calculation is slow, `useMemo` caches it: "unless you're creating or looping over thousands of objects, it's probably not expensive", and `console.time` measures it. "`useMemo` won't make the *first* render faster." Lesson 56.
- **React does**:
  - Page, with `filteredPlayers` in state: John's row stays after Remove, under `Showing 5 of 4 players`. `unconfirmed`.
  - Page, with `visiblePlayers` calculated: typing `a` shows Mia, Sara, and Anna under `Showing 3 of 5 players`; Remove on Mia then shows `Showing 2 of 4 players`. `unconfirmed`.
  - Console: no warning. `unconfirmed`.
- **Example step**:
  - In `TeamList.jsx`, adds `const [query, setQuery] = useState('');` and the box `<input value={query} onChange={e => setQuery(e.target.value)} placeholder="Search players" />`.
  - First version: `const [filteredPlayers, setFilteredPlayers] = useState(initialPlayers);`, set inside `onChange` with `players.filter(player => player.name.includes(e.target.value))`, and the rows drawn from `filteredPlayers`.
  - Fix: that state is deleted, and `const visiblePlayers = players.filter(player => player.name.includes(query));` takes its place. The rows are drawn from `visiblePlayers`.
  - The count line becomes `<p>Showing {visiblePlayers.length} of {players.length} players</p>`, and the line `const count = players.length;` of Principle 1 is no longer needed.
- **Code names**: `TeamList.jsx`, `query`, `setQuery`, `useState('')`, `visiblePlayers`, `filteredPlayers`, `setFilteredPlayers`, `players.filter(player => player.name.includes(query))`, `players.filter(player => player.name.includes(e.target.value))`, `e.target.value`, `Search players`, `Showing 5 of 5 players`, `Showing 3 of 5 players`, `Showing 5 of 4 players`, `names`, `visibleNames`, `filterText`, `filteredArticles`, `articleCount`, `0 results`

### Principle 3: `captainId` Finds the Captain in the List

- **Rule**: When the user picks one item from a list, keep its id in state, not a copy of the item object, and find the item in the list during rendering.
- **Move**: Side by side, because storing the object and storing the id both show `Captain: Mia` right after the click. Steps for a surprise for `Captain: Mia` after Mia is removed.
- **Opening Essence**:
  - Smallest code: `const [chosen, setChosen] = useState(names[1]);` beside `const [chosenId, setChosenId] = useState(1);` with `const chosen = names.find(item => item.id === chosenId);`, where `names` is `[{ id: 0, name: 'John' }, { id: 1, name: 'Mia' }]`.
  - Everyday image: a bookmark and a photocopy of a page. The bookmark points to the page in the book, so a corrected or torn-out page shows at once. The photocopy keeps the old page.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both print `Mia`. Only the one with `chosenId` follows a change to the list.
- **Root Distinction**:
  - Junior: "The user chose Mia, so I store Mia."
  - Senior: Mia already lives in `players`; the state stores which one, `1`, and the code looks her up.
- **Simplest version**:
  - `const [chosenId, setChosenId] = useState(1);`
  - `const chosen = names.find(item => item.id === chosenId);`
  - `<p>{chosen.name}</p>` shows `Mia`.
- **Words to teach**:
  - *duplication in state*: the same information kept in two places, here Mia inside `players` and Mia inside `captain`. The React docs' name. Needed at the first version, with `captain` in state.
  - `find`: a JavaScript array method that returns the first item for which the function returns `true`, and `undefined` when no item matches. From MDN, wording `unconfirmed`. Needed at the fix, and again when the captain is removed and `find` returns nothing.
  - `captainId`: our own state variable holding the chosen player's `id`, or `null` before any choice. Needed at the fix.
  - Known: `key={player.id}` and `id` in the data, Lesson 18. `? :` and `&&`, Lesson 10. Arrow handler with an argument, Lesson 11.
  - Helper: `find`.
- **Side by side**:
  - "with `captain` in state" and "with `captainId` in state": NOT the same thing. The object is a second copy of a player; the id points to the player in `players`.
- **Surprises**:
  - With `captain` in state: the user clicks Make captain on Mia, then Remove on Mia, and the page still says `Captain: Mia`.
    1. The user clicks Make captain on Mia. `setCaptain(player)` stores Mia's object.
    2. The page shows `Captain: Mia`.
    3. The user clicks Remove on Mia. `setPlayers` stores a list without Mia.
    4. `captain` still holds Mia's object, because nothing changed it.
    5. React renders again. Mia's row is gone, and the line still reads `captain.name`: `Captain: Mia`.
  - With `captainId` in state, after the same two clicks, the page says `No captain yet`:
    1. `captainId` still holds `1`.
    2. `find` looks through `players` and finds no player with the id `1`.
    3. `find` returns `undefined`, so `captain` is `undefined`.
    4. The ternary picks its second branch: `No captain yet`.
- **Where did that come from?**:
  - `captain` in the JSX of the fixed version, with no `useState` for it: the line `const captain = players.find(player => player.id === captainId);` supplies it on every render.
  - `No captain yet` on the first render: `captainId` starts as `null`, no player has the id `null`, so `find` returns `undefined`, and the ternary picks the second branch.
- **Real beginner mistake** (the React docs' travel snack menu):
  1. A menu keeps `items` and `selectedItem` in state, and `selectedItem` starts as `items[0]`.
  2. Each item gets a text box to edit its title.
  3. The user clicks Choose on an item, then edits its title.
  4. The box shows the new title.
  5. The line "You picked ..." keeps the old title, because `selectedItem` is a separate copy.
  6. The docs' fix: hold `selectedId` in state and find the item with `items.find(item => item.id === selectedId)`.
- **Interview depth**:
  - The docs' Recap: "For UI patterns like selection, keep ID or index in state instead of the object itself."
  - The docs' mail challenge: `highlightedLetter` held as an object stops matching after a Star click, because the click creates a new letter object; `highlightedId` fixes it.
  - Multiple selection keeps an array of ids, such as `[0, 2]`, or a `Set`; the count is `selectedIds.length` or `selectedIds.size`, calculated, not stored.
  - A `Set` in state must be copied before it changes, like any object, Lesson 17.
- **React does**:
  - Page, with `captain` in state: `Captain: Mia` under a list with no Mia. `unconfirmed`.
  - Page, with `captainId` in state: `No captain yet` after Mia is removed. `unconfirmed`.
  - Console: no warning in either version. `unconfirmed`.
  - If the JSX reads `captain.name` without the ternary, the first render throws an error, because `captain` is `undefined`. `unconfirmed`, with its exact message; the lab records both if the lecture shows it.
- **Example step**:
  - In `TeamList.jsx`, adds a `Make captain` button on each row and, below the list, `{captain ? <p>Captain: {captain.name}</p> : <p>No captain yet</p>}`.

  - Fix: `const [captainId, setCaptainId] = useState(null);` with `onClick={() => setCaptainId(player.id)}`, and `const captain = players.find(player => player.id === captainId);` in the component body.

### Principle 4: `useState(name)` Freezes the Captain Line

- **Rule**: Use a prop directly, or in a `const`; copy a prop into state only when the component should ignore every later value, and then start the prop's name with `initial` or `default`.
- **Move**: Side by side, because `useState(name)` and `const shownName = name` show the same name on the first render. Steps for a surprise for the line that stays on Mia.
- **Opening Essence**:
  - Smallest code: `function Hello({ name }) { const [shownName] = useState(name); return <p>Hello, {shownName}</p>; }` beside `function Hello({ name }) { return <p>Hello, {name}</p>; }`, with the parent first passing `John` and then `Mia`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both show `Hello, John`. When the parent passes `Mia`, only the second shows `Hello, Mia`.
  - The fact behind it, from Lesson 12: the value passed to `useState` is used only on the first render.
- **Root Distinction**:
  - Junior: "`useState(name)` connects the state to the prop."
  - Senior: `useState(name)` takes one reading of the prop, on the first render, and never reads it again.
- **Simplest version**:
  - `function Hello({ name }) { return <p>Hello, {name}</p>; }`
  - `<Hello name="John" />`, later `<Hello name="Mia" />`, shows `Hello, Mia`.
- **Words to teach**:
  - *mirroring props in state*: putting a prop into a state variable with `useState(prop)`. The React docs' name, in quotes. Needed at the frozen line.
  - `initial` or `default` at the start of a prop name: the docs' naming habit that tells the reader later values are ignored, as in `initialColor`. Needed at the end, for the one case where the copy is wanted.
  - Known: props, Lesson 08. The initial value used only on the first render, Lesson 12. Splitting a component into its own file and importing it, Lesson 05.
  - Helper: none.
- **Side by side**:
  - "with `useState(name)`" and "with `name` used directly": NOT the same thing. The first keeps the first value; the second shows the value of this render.
  - "with `useState(name)`" and "with `useState(initialName)`": the exact same thing for React, both keep the first value. The one difference is the prop's name, which tells the reader that later values are ignored on purpose.
- **Surprises**:
  - With `useState(name)`: the user clicks Make captain on Mia, then on John, and the line stays `Captain: Mia` while John's row says `(captain)`.
    1. The user clicks Make captain on Mia. `captain` is Mia, and `TeamList` renders `<CaptainLine name="Mia" />` for the first time.
    2. On this first render of `CaptainLine`, `useState(name)` stores `'Mia'`.
    3. The user clicks Make captain on John. `TeamList` renders `<CaptainLine name="John" />` in the same place.
    4. React keeps the same `CaptainLine` and its state, because it is the same component at the same position, and passes the new `name`. `preserving-and-resetting-state.md`: "React preserves a component's state for as long as it's being rendered at its position in the UI tree."
    5. `useState` ignores its argument after the first render, so `shownName` stays `'Mia'`.
    6. The row says `John (captain)`, and the line says `Captain: Mia`.
- **Where did that come from?**:
  - `name` inside `CaptainLine`: `TeamList` supplies it on the tag, `<CaptainLine name={captain.name} />`, and the parameter list unpacks it, Lesson 08.
  - `shownName` with `useState(name)`: the first item of the array `useState` returns, Lesson 12.
- **Real beginner mistake** (the React docs' Clock challenge):
  1. `Clock` receives a `color` prop and writes `const [color, setColor] = useState(props.color);`.
  2. The parent shows a select box, and the user picks a new color.
  3. The parent passes the new `color` prop.
  4. The clock keeps its first color.
  5. The docs' fix: remove the state variable and use `props.color` directly.
- **Interview depth**:
  - The docs: "if the parent component passes a different value of `messageColor` later (for example, `'red'` instead of `'blue'`), the `color` *state variable* would not be updated!" and "The state is only initialized during the first render."
  - The docs: mirroring props into state "only makes sense when you *want* to ignore all updates for a specific prop."
  - `useState.md`: "This argument is ignored after the initial render."
  - Resetting a child's state when the parent picks someone else, with a `key`, is Lesson 25.
- **React does**:
  - Page, with `useState(name)`: `Captain: Mia` while John's row shows `(captain)`. `unconfirmed`.
  - Page, with `name` used directly: `Captain: John` after the second click. `unconfirmed`.
  - Console: no warning. `unconfirmed`.
- **Example step**:
  - Creates `src/components/CaptainLine.jsx`, which receives `name`.
  - `TeamList.jsx` imports it and writes `{captain ? <CaptainLine name={captain.name} /> : <p>No captain yet</p>}`.
  - First version: `const [shownName] = useState(name);` inside `CaptainLine`, and `<p>Captain: {shownName}</p>`.
  - Fix: the state line is deleted, and the line becomes `<p>Captain: {name}</p>`.

### Principle 5: `position` Holds `x` and `y` Together

- **Rule**: When two state variables always change together, merge them into one object; when you set that object, write every field, or spread the old object first.
- **Move**: Side by side, because two state variables and one object both work. The docs' verdict: "Technically, you can use either of these approaches."
- **Opening Essence**:
  - Smallest code: `const [x, setX] = useState(0); const [y, setY] = useState(0);` beside `const [position, setPosition] = useState({ x: 0, y: 0 });`.
  - Everyday image: a cinema ticket names a row and a seat, and both are chosen together as one place.
  - No look-alike confusion. Key idea: values that always change together are one value. What is at stake: two setters that must be called together can be called apart. Where readers go wrong: they write `setPosition({ x: 100 })` and lose `y`.
- **Root Distinction**:
  - Junior: "Every number on the page gets its own state."
  - Senior: values that always change in the same handler belong in one object.
- **Simplest version**:
  - `const [position, setPosition] = useState({ x: 0, y: 0 });`
  - `setPosition({ x: e.clientX, y: e.clientY });` in one handler.
- **Words to teach**:
  - *group related state*: the docs' name for this rule. Needed at the start of the principle.
  - Known: an object in state, spread to keep the other fields, Lesson 17. The docs' `{ x: e.clientX, y: e.clientY }` was named in Lesson 17.
  - Helper: `e.clientX` and `e.clientY`, the pointer's position, only if the lecture shows the docs' moving dot. `unconfirmed` against MDN.
- **Side by side**:
  - "with `setPosition({ x: 100 })`" and "with `setPosition({ ...position, x: 100 })`": NOT the same thing. The first object has no `y` at all; the second keeps `y`.
- **Surprises**:
  - `setPosition({ x: 100 })` leaves `position.y` as `undefined`, because the new object has no `y` property. The docs' Pitfall: "it would not have the `y` property at all!"
- **Where did that come from?**: none. Every name is written in the code.
- **Real beginner mistake** (the docs' Pitfall):
  1. A developer merges `x` and `y` into `position`.
  2. A handler wants to move only `x` and writes `setPosition({ x: 100 })`.
  3. The new object has no `y`.
  4. The docs' fix: `setPosition({ ...position, x: 100 })`, or two state variables with `setX(100)`.
- **Interview depth**:
  - The docs: grouping also fits "when you don't know how many pieces of state you'll need", such as a form where the user adds custom fields.
  - Grouping and contradictions go together: `isSending` and `isSent` became one `status`, Lesson 21.
  - `useState.md`: when a state is calculated from the previous state of another state variable, combine them into one object and use a reducer, Lesson 27.
- **React does**:
  - Page: none on the team page.
  - The docs' moving dot: the red dot follows the pointer. Named only.
- **Example step**: none. The team page does not change. The principle uses its own smallest code.
- **Code names**: `x`, `y`, `setX`, `setY`, `position`, `setPosition`, `{ x: 0, y: 0 }`, `setPosition({ x: 100 })`, `setPosition({ ...position, x: 100 })`, `e.clientX`, `e.clientY`

### Principle 6: `childIds` Keeps Nested Places Flat

- **Rule**: When state is nested so deeply that one change needs copies at every level, store each item once in a flat object keyed by id, and give each item an array of its child ids.
- **Move**: Side by side, nested object and flat object holding the same three places. Smallest code first, because the shape is new.
- **Opening Essence**:
  - Smallest code, nested: `{ id: 0, title: 'Earth', childPlaces: [{ id: 1, title: 'Africa', childPlaces: [{ id: 2, title: 'Kenya', childPlaces: [] }] }] }`.
  - Smallest code, flat: `{ 0: { id: 0, title: 'Earth', childIds: [1] }, 1: { id: 1, title: 'Africa', childIds: [2] }, 2: { id: 2, title: 'Kenya', childIds: [] } }`.
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* for the information: both hold the same three places in the same order. *"NOT the same thing"* for the work of a change: removing Kenya.
  - Everyday image, from the docs: "This data restructuring might remind you of seeing a database table."
- **Root Distinction**:
  - Junior: "The data is a tree, so the state must be a tree."
  - Senior: the tree can be stored as a flat table of items, each pointing to its children by id.
- **Simplest version**:
  - The flat object above, stored with `useState`.
  - Removing Kenya: `const nextParent = { ...parent, childIds: parent.childIds.filter(id => id !== 2) };` then `setPlan({ ...plan, [1]: nextParent });`.
- **Words to teach**:
  - *flat state*, also *normalized state*: the docs write that the state is now "flat", also known as "normalized". Needed at the flat version.
  - `childIds`: the docs' name for the array of child ids inside each item. Needed at the flat version.
  - the "table" object: the docs' name for the flat object keyed by id. Needed when the two updates are listed.
  - Known: copying every object on the path to a nested change, object spread, computed property name, Lesson 17. `filter`, Lesson 19.
  - Helper: none.
- **Side by side**:
  - "with `childPlaces`" and "with `childIds`": the same information, NOT the same work. Removing Kenya from the nested object needs a new Africa and a new Earth, one copy per level above Kenya; removing it from the flat object changes two levels, the parent Africa and the table object, however deep Kenya sits.
- **Surprises**: none. The amount of work follows from Lesson 17's rule of copying every level.
- **Where did that come from?**:
  - `parent` in the removal code: read from the table by id, `plan[parentId]`.
  - `[parentId]` inside the new object: a computed property name, Lesson 17. It writes the new parent under its own id.
- **Real beginner mistake**: the docs state the cost, not a story: "Deleting a deeply nested place would involve copying its entire parent place chain. Such code can be very verbose."
- **Interview depth**:
  - The docs: to remove a place from flat state, update two levels: the parent place without the removed id in its `childIds`, and the root "table" object with the updated parent.
  - The docs compare removing duplicate data to how a database engineer might want to normalize the database structure, a computer science term.
  - The DeepDive "Improving memory usage": also delete the removed items and their children from the table; the docs' version uses Immer.
  - Flat state also helps against duplication "in different parts of a nested object".
  - The docs: nesting can also shrink by moving short-lived state, "like whether an item is hovered", into child components.
- **React does**:
  - Page: none on the team page.
  - The docs' travel plan: a `Complete` button removes a place and its children from the list. Named only.
- **Example step**: none. The team page does not change. The principle uses its own smallest code.
- **Code names**: `childPlaces`, `childIds`, `plan`, `setPlan`, `parent`, `parentId`, `nextParent`, `plan[parentId]`, `{ ...plan, [parentId]: nextParent }`, `Earth`, `Africa`, `Kenya`, `initialTravelPlan`

## Interview Points

1. State is the minimal set of changing data the component needs to remember; everything else is calculated during rendering.
2. The test from Thinking in React: a value is not state if it stays the same over time, if it comes from a parent through props, or if it can be computed from existing state or props.
3. For a filtered list with a count, only the full list and the search text are state; the filtered list and the count are calculated from them on every render.
4. Two copies of the same information need every handler to update both, and one missed handler leaves the page out of sync; a calculated value cannot disagree with its state, because it is recalculated on every render.
5. Keep the id of a chosen item in state, not the item object, and find the item in the list during rendering.
6. Do not mirror a prop with `useState(prop)`: the initial value is read only on the first render. When ignoring later values is wanted, name the prop `initialX` or `defaultX`.
7. The other structure rules from the React docs: group values that always change together, replace contradicting booleans with one `status`, and store deeply nested data flat, by id.
8. Calculating during rendering is usually cheap. When a measured calculation is slow, `useMemo` caches it; an Effect that copies a calculated value into state is the wrong tool, because it renders once with a stale value.
