## Scope

Covered here:
- Listing every visual state the user can see, and drawing each one first as a mockup controlled by a `status` prop.
- Showing all the mockups on one page with `map`, the "living styleguide".
- Keeping the current visual state in one `status` state variable that holds one string, instead of several booleans that can contradict each other.
- Dropping state that can be computed: the empty box is read from `answer.length === 0`.
- Finding what changes the status: human inputs, such as typing and clicking Check, and computer inputs, such as a timer finishing.
- Event handlers that only set the next status, while the JSX already describes every status.

## Start of the Lecture

**Simplest version of the chapter's idea**:
- One state variable holds the name of what the user sees, and each name has its own JSX.
- `const [status, setStatus] = useState('asking');`
- `if (status === 'right') { return <h1>That's right!</h1>; }`
- `return <button onClick={() => setStatus('right')}>Paris</button>;`
- What the reader sees: a `Paris` button, and after one click only the heading `That's right!`: `unconfirmed`.

**The real page problem** (plain JavaScript, no React):
1. The page asks `What is the capital of France?`, with a text box, a `Check` button, and two hidden lines: `Not quite. Try again!` and `That's right!`.
2. The click handler shows one of the two lines: `rightText.hidden = false` when the box holds `Paris`, and `wrongText.hidden = false` otherwise.
3. The user types `Lyon` and clicks `Check`.
4. `Not quite. Try again!` appears.
5. The user changes the answer to `Paris` and clicks `Check`.
6. `That's right!` appears, and `Not quite. Try again!` is still on the page under it.
7. The handler never hid the old line. Every branch must undo what every other branch did.
8. Each new part, such as a `Checking...` line or a dimmed button, adds more lines to every branch.
- Source of the problem: `reacting-to-input-with-state.md`: "Adding a new UI element or a new interaction would require carefully checking all existing code to make sure you haven't introduced a bug (for example, forgetting to show or hide something)."
- Page result of step 6: `unconfirmed`. The lab runs it.

**Example page chosen for this lesson**: `Capital quiz`, one quiz question with an answer box.
- Files for the plain JavaScript problem: `index.html` and `src/quiz.js`, no React.
- Files for the React page: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx`, `src/components/CapitalQuiz.jsx`.
- Final parts of the page: `<h2>Capital quiz</h2>`, `<p>What is the capital of France?</p>`, a text box, a `Check` button, a `Checking...` line, a `Not quite. Try again!` line, and the heading `That's right!` that replaces everything when the answer is right.
- The five visual states: empty, typing, checking, wrong, right.

**Why this page**:
1. Everyone has answered a quiz question. A question, a box, and a Check button need no explanation.
2. Every reader knows the answer, so nobody has to be told why `Paris` is right and `Lyon` is wrong.
3. It has five visual states the reader can see at once: dimmed button, live button, dimmed box with `Checking...`, the wrong line, the right heading.
4. The broken result is big: two answers to one question on the screen at the same time.
5. It has both kinds of input from react.dev: human inputs, typing and clicking Check, and a computer input, the one-second check finishing.
6. The actions are typing and clicking.
7. Outside helper code is small. `setTimeout` is known from Lesson 15, the controlled box from Lesson 20. The only new helpers are `disabled` and `||`, and `hidden` for the plain JavaScript version.

## Principles

### Principle 1: Each Visual State Gets Its Own Mockup

- **Rule**: Before writing any handler, list every visual state the user can see, and draw each one as JSX controlled by a `status` prop. The list is complete when every screen the user can reach has a name.
- **Move**: Everyday image. The new word is *visual state*, and react.dev takes it from designers, who draw one screen for each moment before anything works.
- **Simplest version**:
  - `function Light({ status = 'off' }) { return status === 'on' ? <p>On</p> : <p>Off</p>; }`
  - `<Light />` shows `Off`. `<Light status="on" />` shows `On`: `unconfirmed`.
  - Everyday image: a designer's set of drawings for one screen, one drawing per moment the user can see, made before anything is clickable.
- **Words to teach**:
  - *visual state*: one screen the user can see, such as empty, typing, checking, wrong, right. Our own list, React does not provide it. Needed at the moment the reader writes down what the quiz can look like.
  - `status`: our own prop name. React gives it no meaning. react.dev: "You could call that prop anything you like, the naming is not important." Needed at the moment the mockup must switch between screens.
  - *mockup*: JSX that draws a screen without any logic. react.dev: "Mocking lets you quickly iterate on the UI before you wire up any logic." Needed when the five screens are drawn before any click works.
  - *living styleguide* or *storybook*: one page that shows every visual state at once. Name only, from the react.dev `<DeepDive>`.
  - Known: default prop value, Lesson 09. `if` with early `return`, `&&`, Lesson 10. `map` with `key`, Lesson 18. `<>...</>`, Lesson 02.
  - Helpers: `disabled`, a browser attribute that dims a box or button and stops it from reacting. `||`, JavaScript "or".
- **Side by side**: none.
- **Surprises**: none. Each mockup shows exactly what its `status` asks for.
- **Where did that come from?**:
  - `'empty'` in `CapitalQuiz` when `App.jsx` writes `<CapitalQuiz />` with no `status`: the default value in the parameter list supplies it.
    1. `App` renders `<CapitalQuiz />` without a `status` attribute.
    2. React calls `CapitalQuiz` with a props object that has no `status`.
    3. JavaScript uses the default `'empty'`.
  - `status` inside `statuses.map(status => ...)` in `App.jsx`: `map` supplies it.
    1. `map` calls the arrow once for each string in `statuses`.
    2. Each call receives the next string as `status`.
    3. The arrow passes it on as `<CapitalQuiz status={status} />`.
- **Real beginner mistake**:
  1. The developer starts from the click and thinks of two outcomes only: right and nothing.
  2. `handleCheck` sets the right screen when the box holds `Paris` and does nothing otherwise.
  3. The user types `Lyon` and clicks `Check`.
  4. Nothing changes on the page.
  5. The user clicks again and again and gets no answer.
  6. The wrong screen was never drawn, so no code could show it.
  7. Listing all five screens first shows the missing one before any handler exists.
- **Interview depth**:
  - react.dev: "React stands at the intersection of design and computer science." A computer scientist calls this a "state machine", a designer calls each screen a "visual state".
  - Mocking each state first lets the team review every screen before any logic exists.
  - A page that shows every state at once, as in the `<DeepDive>`, is often called a "living styleguide" or "storybook".
  - The flow can be drawn on paper first: each state as a labeled circle, each change as an arrow. react.dev: "You can sketch out many flows this way and sort out bugs long before implementation."
- **React does**:
  - Page: `<CapitalQuiz status="right" />` shows only `That's right!`. react.dev: "Try editing `status = 'empty'` to `status = 'success'` to see the success message appear."
  - Page: `disabled={true}` on the box: "If `true`, the input will not be interactive and will appear dimmed." Source: `input.md`. The same on `<button>`: `unconfirmed`.
  - Elements panel: a `disabled` button shows as `<button disabled="">Check</button>`, and a live one as `<button>Check</button>`: `unconfirmed`.
  - Console: no message with the `key` on each `<section>`: `unconfirmed`.
- **Example step**:
  - `src/components/CapitalQuiz.jsx` is created as a mockup: `CapitalQuiz({ status = 'empty' })`, an early `return <h1>That's right!</h1>` for `'right'`, then `<h2>Capital quiz</h2>`, `<p>What is the capital of France?</p>`, `<input disabled={status === 'checking'} />`, `<button disabled={status === 'empty' || status === 'checking'}>Check</button>`, `{status === 'checking' && <p>Checking...</p>}`, `{status === 'wrong' && <p>Not quite. Try again!</p>}`.
  - `src/App.jsx` holds `const statuses = ['empty', 'typing', 'checking', 'wrong', 'right'];` and renders `<section key={status}><h4>CapitalQuiz ({status}):</h4><CapitalQuiz status={status} /></section>` for each.
  - The page shows all five screens one under the other.
- **Code names**: `CapitalQuiz.jsx`, `App.jsx`, `CapitalQuiz`, `status`, `status = 'empty'`, `'empty'`, `'typing'`, `'checking'`, `'wrong'`, `'right'`, `statuses`, `statuses.map`, `<section key={status}>`, `<h4>`, `disabled`, `||`, `Capital quiz`, `What is the capital of France?`, `Check`, `Checking...`, `Not quite. Try again!`, `That's right!`, `Light`, `'on'`, `'off'`

### Principle 2: One status Shows One Message at a Time

- **Rule**: When only one of several screens can be true at a time, keep them in one state variable that holds one string, not in one boolean per screen. Separate booleans allow combinations no user should ever see.
- **Move**: Side by side. The idea is the difference between two ways of storing the same screens: several booleans, and one `status`.
- **Simplest version**:
  - With two booleans: `const [isChecking, setIsChecking] = useState(false);` and `const [isWrong, setIsWrong] = useState(false);`. Four combinations, three valid. Both `true` is the impossible one.
  - With one `status`: `const [status, setStatus] = useState('typing');` holding `'typing'`, `'checking'`, or `'wrong'`. Three values, all valid.
- **Words to teach**:
  - `status` as state: one state variable whose string names the current visual state. Our own name and our own strings, stored by React's `useState`. Needed at the moment the mockup prop becomes real state.
  - *impossible state*: a mix of values that matches no screen, such as checking and wrong at once. react.dev's word, in quotes. Needed at the moment the page shows `Checking...` and `Not quite. Try again!` together.
  - *paradox*: react.dev's word for two state variables that cannot both be `true`. Name only, inside the impossible state.
  - Known: `useState`, Lesson 12. `setTimeout`, Lesson 15. `? :`, Lesson 10.
  - Helpers: none new.
- **Side by side**:
  - "With `isChecking`, `isWrong`, and `isRight`" and "with one `status`".
  - Verdict: NOT the same thing.
  - Reason: three booleans allow eight combinations and only four are screens, while `status` can only hold one of four names.
- **Surprises**:
  - The page shows `Checking...` and `Not quite. Try again!` together, the box stays dimmed, and the user can never try again. Steps:
    1. The user types `Lyon` and clicks `Check`.
    2. `handleCheck` calls `setIsChecking(true)`, and the box and button dim.
    3. One second later the timer calls `setIsWrong(true)` and forgets `setIsChecking(false)`.
    4. Now `isChecking` and `isWrong` are both `true`.
    5. The JSX draws both lines, and `disabled={isChecking}` keeps the box dimmed.
    6. No handler can run, because the box and button no longer react.
  - Source of the rule: react.dev: "you never want to show an error message and disable the input at the same time, or the user won't be able to correct the error!"
  - Page result of steps 4 to 6: `unconfirmed`.
- **Where did that come from?**:
  - The strings `'typing'`, `'checking'`, `'wrong'`, `'right'`: our own code invents them. React stores the string and never reads its meaning. Only our `===` checks in the JSX give it a meaning.
  - `isChecking` as a constant after the change: our own code. `const isChecking = status === 'checking';` is computed during render from `status`. react.dev: "they're not state variables, so you don't need to worry about them getting out of sync with each other."
- **Real beginner mistake** (react.dev, "Avoid contradictions in state": "if you forget to call `setIsSent` and `setIsSending` together, you may end up in a situation where both `isSending` and `isSent` are `true` at the same time"):
  1. The developer keeps one boolean per screen: `isChecking`, `isWrong`, `isRight`.
  2. The timer in `handleCheck` sets `setIsChecking(false)` and `setIsRight(true)` in the right branch.
  3. In the wrong branch it sets only `setIsWrong(true)`.
  4. The user types `Lyon` and clicks `Check`.
  5. After one second `Checking...` and `Not quite. Try again!` show together, and the box stays dimmed.
  6. The developer replaces the three booleans with `const [status, setStatus] = useState('typing');`.
  7. The timer calls `setStatus('wrong')`, and `'wrong'` is not `'checking'`, so the box comes back.
- **Interview depth**:
  - react.dev: "There are four possible combinations of two booleans, but only three correspond to valid states. To remove the "impossible" state, you can combine these into a `status` that must be one of three values."
  - Each boolean doubles the combinations: three booleans give eight, five give thirty-two.
  - react.dev: "Simplicity is key: each piece of state is a "moving piece", and you want as few "moving pieces" as possible. More complexity leads to more bugs!"
  - Starting with too many booleans is normal. react.dev: "Your first idea likely won't be the best, but that's ok--refactoring state is a part of the process!"
  - Some impossible mixes can remain across two variables, such as an error message while the status says success. A reducer removes them: Lesson 27. Named only.
- **React does**:
  - Page with one `status`: `Checking...` and `Not quite. Try again!` never show together: `unconfirmed`.
  - Elements panel during checking: `<input disabled="">`, `<button disabled="">Check</button>`, `<p>Checking...</p>`: `unconfirmed`.
  - Console: no message in either version: `unconfirmed`.
- **Example step**:
  - `CapitalQuiz.jsx` stops taking a `status` prop. It gets `const [answer, setAnswer] = useState('');` and `const [status, setStatus] = useState('typing');`, and the box becomes `<input value={answer} onChange={e => setAnswer(e.target.value)} disabled={status === 'checking'} />`.
  - For the mistake, the same file first holds `isChecking`, `isWrong`, `isRight` and the forgotten `setIsChecking(false)`.
  - `App.jsx` now renders one `<CapitalQuiz />`.
  - The empty state is still stored separately here: `const [isEmpty, setIsEmpty] = useState(true);` and `<button disabled={isEmpty || status === 'checking'}>Check</button>`. Principle 3 removes it.
  - The mistake needs a full `handleCheck` with the three booleans and a `setTimeout`. The `status` version of `handleCheck` is written in Principle 4.
- **Code names**: `isEmpty`, `isChecking`, `setIsChecking`, `isWrong`, `setIsWrong`, `isRight`, `setIsRight`, `status`, `setStatus`, `useState('typing')`, `answer`, `setAnswer`, `const isChecking = status === 'checking';`, `Lyon`, `Checking...`, `Not quite. Try again!`, `handleCheck`

### Principle 3: answer.length Turns the Check Button Off

- **Rule**: When a screen can be read from state you already have, compute it during render instead of storing it. The empty screen is `answer.length === 0`, so it needs no state of its own.
- **Move**: Steps for a surprise. The reader would not expect the Check button to stay on after the box is emptied.
- **Simplest version**:
  - With a stored copy: `const [isEmpty, setIsEmpty] = useState(true);` and `<button disabled={isEmpty}>`.
  - With a computed value: `<button disabled={answer.length === 0}>`.
- **Words to teach**:
  - *essential state*: state you cannot remove without breaking the page. react.dev: "You know they are essential, because you can't remove any of them without breaking the functionality." Needed at the end, when the quiz is left with `answer` and `status` only.
  - The three questions react.dev asks about each state variable, needed while removing `isEmpty`: "Does this state cause a paradox?", "Is the same information available in another state variable already?", "Can you get the same information from the inverse of another state variable?"
  - Known: `.length`, `value`, `onChange`, Lesson 20. `disabled` and `||`, Principle 1.
  - Helpers: none new.
- **Side by side**:
  - "With `isEmpty` in state" and "with `answer.length === 0`".
  - Verdict: NOT the same thing.
  - Reason: the stored copy changes only when a handler remembers to change it, while the computed value is read fresh from `answer` on every render.
- **Surprises**:
  - The box is empty, and the Check button is still on. Steps:
    1. The box handler calls `setAnswer(e.target.value)` and `setIsEmpty(false)`.
    2. The user types `Lyon`. `isEmpty` becomes `false`, and the button turns on.
    3. The user deletes all four letters. `answer` becomes `''`.
    4. The handler sets `isEmpty` to `false` again, because it never checks the text.
    5. The button reads `isEmpty`, so it stays on.
    6. The user clicks `Check`, and after one second `Not quite. Try again!` appears for an empty answer.
  - Page result of steps 5 and 6: `unconfirmed`.
- **Where did that come from?**:
  - `answer` inside `disabled={answer.length === 0 || status === 'checking'}`: the state variable from `useState('')`. React supplies its current value on each render, and `.length` reads it during that render.
- **Real beginner mistake** (react.dev, Step 4: "By making them separate state variables, you risk them going out of sync and causing bugs."):
  1. The developer keeps `isEmpty` as its own state next to `answer`.
  2. The box handler sets `isEmpty` to `false` on every change.
  3. The user types `Lyon`, then deletes it.
  4. The button stays on for an empty box.
  5. The user clicks `Check` and is told the empty answer is wrong.
  6. The developer deletes `isEmpty` and writes `disabled={answer.length === 0 || status === 'checking'}`.
  7. The button turns off the moment the box is empty again.
- **Interview depth**:
  - react.dev counts seven state variables before the clean-up and three after: "After this clean-up, you're left with 3 (down from 7!) *essential* state variables."
  - The quiz goes from six, `answer` plus five booleans, to two: `answer` and `status`.
  - The same move for an error message: `isError` is not needed when `error !== null` says the same. react.dev: "`isError` is not needed because you can check `error !== null` instead."
  - The full rules for redundant and duplicate state belong to Lesson 22. Named only.
- **React does**:
  - Page with `answer.length === 0`: the button dims when the box is emptied: `unconfirmed`.
  - Elements panel: the button gets `disabled=""` again when the box is empty: `unconfirmed`.
  - Console: no message: `unconfirmed`.
- **Example step**:
  - In `CapitalQuiz.jsx`, `isEmpty` is removed. The button becomes `<button disabled={answer.length === 0 || status === 'checking'}>Check</button>`.
  - `'empty'` is no longer a value of `status`. `status` holds `'typing'`, `'checking'`, `'wrong'`, or `'right'`.
  - For the mistake, the same file first holds `const [isEmpty, setIsEmpty] = useState(true);` and `setIsEmpty(false)` in the box handler.
- **Code names**: `isEmpty`, `setIsEmpty`, `useState(true)`, `answer.length === 0`, `disabled={answer.length === 0 || status === 'checking'}`, `''`, `Lyon`, `error !== null`, `isError`

### Principle 4: Clicks and Timers Only Set status

- **Rule**: Every input that changes the screen, from the user or from the computer, only sets the next `status`. The JSX already describes every status, so no handler shows, hides, enables, or disables anything.
- **Move**: Side by side. The plain JavaScript handler and the React handler answer the same click in two different ways.
- **Simplest version**:
  - With `hidden` in plain JavaScript: `if (box.value === 'Paris') { rightText.hidden = false; } else { wrongText.hidden = false; }`.
  - With `setStatus`: `setStatus(answer === 'Paris' ? 'right' : 'wrong');`.
- **Words to teach**:
  - *human input*: something the user does, such as typing in the box or clicking `Check`. react.dev: "Human inputs, like clicking a button, typing in a field, navigating a link." Needed when the reader lists what moves the quiz from typing to checking.
  - *computer input*: something that happens without the user, such as a timer finishing. react.dev: "Computer inputs, like a network response arriving, a timeout completing, an image loading." Needed when the quiz moves from checking to right or wrong with no click.
  - Both must set state. react.dev: "In both cases, you must set state variables to update the UI."
  - Known: `onClick`, `addEventListener`, Lesson 11. `setTimeout`, snapshot, Lesson 15. `? :`, Lesson 10. `getElementById`, Lesson 01. React changes only the DOM nodes that differ, Lesson 13.
  - Helper: `hidden`, a browser attribute that hides an element. Plain JavaScript version only.
- **Side by side**:
  - "With `hidden`" and "with `setStatus`".
  - Verdict: NOT the same thing.
  - Reason: with `hidden`, each branch must also undo what every other branch showed, while `setStatus` names the one next screen, and the JSX for that screen leaves out everything else.
- **Surprises**:
  - The user clicks `Check` a second time after a wrong answer, and `Not quite. Try again!` disappears, with no line that hides it. Steps:
    1. The page shows `Not quite. Try again!`, because `status` is `'wrong'`.
    2. The user changes the answer to `Paris` and clicks `Check`.
    3. `handleCheck` calls `setStatus('checking')`.

## Interview Points

1. Imperative code commands each element after each event. Declarative code describes the screen for each visual state, and React updates the DOM.
2. The five steps from react.dev: identify the visual states, determine what triggers each change, represent the state with `useState`, remove non-essential state, connect the event handlers.
3. Triggers come from human inputs, such as typing and clicking, and computer inputs, such as a network response or a timeout. Both must set state.
4. One `status` string beats separate booleans: two booleans allow four combinations and only three are valid. One string allows only the valid values.
5. Remove state that can be computed: the empty screen is `answer.length === 0`, and an error flag is `error !== null`.
6. Event handlers only set the next state. The JSX already describes every state, so a new state adds one branch and breaks none of the others.
7. Each visual state can be mocked first with a prop, and all of them shown on one page as a living styleguide.
8. Under the hood React does what an `updateDOM` function would do, but changes only the DOM nodes that differ.
9. Remaining impossible mixes across two variables can be removed with a reducer, Lesson 27. React 19 form actions track pending state, Lessons 41 and 42.
