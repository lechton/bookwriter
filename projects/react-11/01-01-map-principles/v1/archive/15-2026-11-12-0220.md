# Q15 Principle Map (River Version v1): State as a Snapshot
- **Version**: River Version (`v1`)
- **Bank Row**: `questions/questions.md` row 15, Version 4
- **Topic Tag**: `#state_snapshots` | `❱ CORE`
- **Interview Question**: *Why does state appear frozen inside a render, even right after you set it?*

## Authorized Scope
- Why reading a state variable on the line right after its setter (`setNumber(number + 1)` then `console.log(number)`) gives the old value: the setter stores the next value inside React and asks for a new render; it does not change the variable in the code that is already running.
- Why the setter did not fail: the screen shows the new value after the handler finishes, because React calls the component again and `useState` returns the new value in that new render.
- What a snapshot is: every render gets its own fixed value of each state variable from React, and the JSX and every event handler created in that render are calculated with that value. A handler created in a render keeps that render's value, wherever the read sits in the handler, before or after the setter.
- Why a closure is the JavaScript reason: a function created inside another function keeps reading the variables of the call that created it.
- Why even delayed code (`setTimeout`) started from a handler reads that render's value, three seconds later and after the screen has changed, and why this protects each click's work from being mixed up with a later click.
- How to use the next value right away: calculate it once in a variable (`const nextNumber = number + 1`) and pass that same variable to the setter and to every line that needs the new value.
- Out of scope: calling the same setter several times in one handler and the updater function `setNumber(n => n + 1)` (`Q16 #state_updates`), updating objects in state and React ignoring a setter call with an unchanged value (`Q17 #state_objects`), controlled `<select>` and `<textarea>` fields (`Q20 #controlled_inputs`), reading the latest value from delayed code with `useRef` (`Q30 #use_ref`), Effects that read state (`Q32 #use_effect`), when React updates the DOM during the Trigger, Render, and Commit steps (`Q13 #render_and_commit`, recall only), and `<StrictMode>` calling components twice (`Q14 #purity`, recall only).

## General Concepts Introduction (Runway Plan)
- **Opening Essence**:
  - **Furniture-free snippet**: `const [count, setCount] = useState(0);` with `function handleClick() { setCount(count + 1); console.log(count); }` on a button `Count: {count}`. One click: the button shows `Count: 1`, and the Console shows `0`.
  - **Human image**:
    1. The everyday meaning of **snapshot**: a quick photo taken at one moment. When the room changes afterward, the people in the photo do not move. Each render is one photo of the page, taken with the state value of that moment.
    2. The shelf from `react.dev`: state lives in React itself, outside the component, as if on a shelf. When React calls the component, it takes the value off the shelf and hands the component a copy for that render. The setter puts a new value on the shelf for the next render; it cannot reach into the copy the running code already holds.
  - **Exact nuance of confusion to state out loud**:
    1. `setCount(count + 1)` looks like the assignment `count = count + 1`, but it is NOT the same thing: an assignment changes the variable on that line; the setter leaves `count` alone and asks React for a new render in which `count` is `1`.
    2. The old value in the Console looks like the setter failed, but it did NOT fail: the button shows `Count: 1`. The setter worked for the next render, and the Console line belongs to the old render.
- **Theme**: A bakery queue screen shows `Now serving: 12`; the staff clicks `Next customer`, the screen moves to `13`, but the announcement line under it calls `Number 12, please come to the counter`, so the wrong customer is called for a number that was just served.
- **Ways**: Two ways a handler can use the value it just set:
  1. Read the state variable again after the setter: always gives this render's old value; fits only when the old value is what is needed.
  2. Calculate the next value once in a variable such as `nextNumber`, then pass it to the setter and to every other line: fits whenever the handler needs the new value right away. The updater function is a third way for a different job (several updates in one click) and belongs to `Q16 #state_updates`.
- **Recall**:
  - Event handlers are functions passed to `onClick` that React calls when the user clicks; writing `onClick={handleNext}` hands the function to React without calling it (Lecture 11, `Q11 #event_handling`).
  - `const [number, setNumber] = useState(12)` stores the value inside React, outside the component function, and the setter asks React to render again with the new value; `useState` returns a two-item array unpacked by position (Lecture 12, `Q12 #use_state`).
  - Calling a setter only triggers a render; React calls the component again and commits the change to the DOM after the handler finishes, so the DOM still shows the old number inside the handler (Lecture 13, `Q13 #render_and_commit`).
  - `<StrictMode>` in `src/main.jsx` calls each component function twice in development, but never calls an event handler twice (Lecture 14, `Q14 #purity`).
  - Text joined with `+`, such as `'Items: ' + count` (Lecture 01, `Q01 #what_is_react`).
- **Runway topics**:
  - A local variable belongs to one call of a function: each call of a component function makes its own `number`, even though the name is the same.
  - `const` means the name cannot be pointed at a new value inside that call; in each render, `const [number, setNumber]` is a new constant.
  - Closure: a function created inside another function keeps reading the variables of the call that created it, even when it runs later. New word, unlocked through its everyday meaning of something closed in: the inner function closes over the values around it, like a sealed envelope that keeps what was put in.
  - `setTimeout(function, 3000)`: plain JavaScript that runs a function later, after a number of milliseconds; `3000` is three seconds. New for this lesson.
  - Snapshot as the name `react.dev` gives to the state value of one render.
  - How the project files are organized: `index.html`, `src/main.jsx`, `src/App.jsx`, `src/components/QueueBoard.jsx`.
- **Example**:
  - **Chosen page**: `Bakery Queue`, the number screen of a bakery counter. `QueueBoard` holds `const [number, setNumber] = useState(12)` and `const [announcement, setAnnouncement] = useState('Welcome! Please take a number.')`, and shows `<h1>Bakery Queue</h1>`, `<p className="now-serving">Now serving: {number}</p>`, `<p className="announcement">{announcement}</p>`, and `<button className="next-btn" onClick={handleNext}>Next customer</button>`. Principle 1 writes `handleNext` with `setNumber(number + 1)` and the announcement built from `number`. Principle 2 moves the announcement line above the setter and clicks twice. Principle 3 adds a `Last call for number ...` line that runs three seconds after the click. Principle 4 fixes every line with `nextNumber`.
  - **Why this concept is the reason this page exists**:
    1. A queue screen exists to show a new number and call that number at once, so reading the state right after setting it is the first thing the handler does, and the off-by-one is a real customer called by mistake.
    2. The two lines sit one above the other on the page, `Now serving: 13` and `Number 12, please come to the counter`, so the old snapshot is seen without opening the Console.
    3. A repeated last call after a few seconds is a believable queue feature, and clicking `Next customer` twice before the last call fires shows that each click keeps its own number.
    4. Everyone knows a take-a-number screen, and the only action is clicking one button.
  - **Other candidate pages considered**:
    1. *The `react.dev` `+3` counter (`setNumber(number + 1)` three times)*: rejected, because its question, three calls in one click, is the hook of `Q16 #state_updates`, and a bare counter gives no reason to read the value after setting it.
    2. *The `react.dev` message form with `To: Alice / Bob` and a five-second send*: rejected as the page, because it needs a controlled `<select>` and `<textarea>` (`Q20 #controlled_inputs`); its idea, each click keeps the value of its moment, is kept through the two quick clicks in Principle 3.
    3. *The syllabus card's `StoryFeedback` rating form with `sendRating`*: rejected, because a wrong rating sent to a server is invisible on the page, while a wrong customer number is seen at once.
    4. *The `react.dev` traffic light (`walk`, `Stop is next`)*: rejected, because a flipped true or false value with a message about the next state is hard to read aloud, while numbers going 12, 13, 14 are plain.
    5. *The shopping list of Lecture 14*: rejected, because its `Dark mode` button changes nothing that a handler reads after setting it.

## Principle Thread
- **Anchor**: A state variable holds one fixed value for the whole of one render; the setter only changes what `useState` returns in the next render, and every function created in a render keeps that render's value.
- **Axis**: From the surprise, to its cause, to its reach in time, to the fix:
  1. The setter does not change the variable in the running code, so the next line reads the old value, yet the screen updates (Principle 1).
  2. Why: each render gets its own snapshot, and each handler is created in one render and closes over that render's value (Principle 2).
  3. How far the snapshot reaches: delayed code started by that handler still reads the same value, seconds later, and this keeps each click's work apart (Principle 3).
  4. The fix when the handler needs the new value now: calculate it once in a variable and pass it everywhere (Principle 4).
- **Why This Axis**: Cause before effect. The reader first sees the surprise on the page (Principle 1). Only then does the question "why the old number?" make sense, answered by the snapshot and the closure (Principle 2). The timer case needs the closure already owned, since nothing else explains a value three seconds old (Principle 3). The fix comes last, because it only makes sense once the reader knows that `number` cannot change inside the running handler (Principle 4).

## Principles

### Principle 1: The Setter Asks for the Next Render; It Does Not Change the Variable in the Running Code
- **Handle**: `setter-asks-for-next-render`
- **Rule**: Calling `setNumber(number + 1)` stores the next value inside React and asks for a new render; `number` in the handler that is running keeps its old value to the last line, and the screen shows the new value only after React renders again.
- **Opening Essence**:
  - **Furniture-free snippet**: `const [count, setCount] = useState(0);` and `function handleClick() { setCount(count + 1); console.log(count); }` on `<button onClick={handleClick}>Count: {count}</button>`. One click: the button says `Count: 1`, the Console says `0`.
  - **Human image**: a ticket handed to the kitchen. Ordering a new dish does not change the plate already on the table; the new plate arrives with the next serving.
  - **Exact nuance of confusion to state out loud**:
    1. `setCount(count + 1)` and `count = count + 1` look like the same job, but they are NOT the same thing: the assignment changes the variable on that line; the setter never touches `count` and asks React for a render in which `count` is `1`.
    2. The Console `0` and the button `Count: 1` look like a contradiction, but both are right: the Console line ran in the old render, and the button belongs to the new one.
- **Root Distinction**:
  - *Junior blurred view*: "I called `setNumber`, so `number` is now `13` on the next line."
  - *Senior grounding*: the setter changes the value React will hand to the next render; the `number` in this render is a constant, and nothing in this handler can change it.
- **Real Beginner Mistake (events, in order)**:
  1. The screen shows `Now serving: 12` and the announcement `Welcome! Please take a number.`
  2. The developer writes `handleNext` with `setNumber(number + 1);` and then `setAnnouncement('Number ' + number + ', please come to the counter');`.
  3. The staff clicks `Next customer`.
  4. The screen moves to `Now serving: 13`, but the announcement says `Number 12, please come to the counter`.
  5. Customer 12, already served, walks back to the counter, and customer 13 keeps waiting.
  6. The developer adds `console.log(number)` after the setter, sees `12`, and decides the setter is broken or slow.
  7. The second click shows `Now serving: 14` and `Number 13, please come to the counter`: always one number behind.
- **Interview Depth**:
  - `react.dev`: "The `set` function only updates the state variable for the next render"; reading the variable after calling it gives "the old value that was on the screen before your call".
  - Writing `let [number, setNumber]` instead of `const` changes nothing: the Console still shows `12`; the setter never assigns to the variable.
  - Assigning `number = number + 1` to the `const` throws `Uncaught TypeError: Assignment to constant variable.` in the browser, and Vite reports `[ILLEGAL_REASSIGNMENT] Unexpected re-assignment of const variable` both in the dev server terminal and as a failed `vite build`.
  - The DOM also still shows the old number inside the handler, because React commits after the handler finishes (recall Lecture 13); the state variable and the DOM are two separate reasons for the same old value.
  - `<StrictMode>` calls the component twice but the handler once, so `12` is logged once per click.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any line in `handleNext` that writes `13` into `number`; the handler only calls `setNumber(number + 1)`.
    - **Who supplies it**: React, which keeps the value outside the component and hands `13` to the next call of `QueueBoard` through `useState`.
    - **What JavaScript and React do**:
      1. React calls `QueueBoard`; `useState(12)` returns `12`, and JavaScript creates the constant `number` with `12` for this call.
      2. The click runs `handleNext`; `setNumber(12 + 1)` stores `13` inside React and asks for a render.
      3. The next line builds `'Number 12, please come to the counter'`, because this `number` is still `12`.
      4. The handler finishes; React calls `QueueBoard` again, and `useState` returns `13` into a new constant `number`.
      5. React commits `Now serving: 13` and the announcement stored in step 3.
- **React Does**:
  - Dev server with `<StrictMode>`: load shows `<p class="now-serving">Now serving: 12</p><p class="announcement">Welcome! Please take a number.</p>`; click 1 shows `Now serving: 13` and `Number 12, please come to the counter`, Console `12`; click 2 shows `Now serving: 14` and `Number 13, please come to the counter`, Console `13`. Same without `<StrictMode>` and in the production build. No Console warning or error.
  - Essence snippet, dev server with `<StrictMode>`: one click shows `Count: 1`, Console `0`.
- **Example Step**: Creates `index.html`, `src/main.jsx` with `root.render(<StrictMode><App /></StrictMode>)`, `src/App.jsx` returning `<QueueBoard />`, and `src/components/QueueBoard.jsx` with both `useState` calls, the heading, the two lines, the button, and `handleNext` as in the mistake. New page elements here: `Bakery Queue`, `Now serving: 12`, the announcement line, and the `Next customer` button.
- **Code names**: `index.html`, `src/main.jsx`, `src/App.jsx`, `src/components/QueueBoard.jsx`, `QueueBoard`, `number`, `setNumber`, `useState(12)`, `announcement`, `setAnnouncement`, `'Welcome! Please take a number.'`, `handleNext`, `setNumber(number + 1)`, `'Number ' + number + ', please come to the counter'`, `console.log(number)`, `now-serving`, `announcement`, `next-btn`, `Bakery Queue`, `Next customer`, `Now serving: 13`, `Number 12, please come to the counter`, `count`, `setCount`, `handleClick`, `Count: 1`, `Uncaught TypeError: Assignment to constant variable.`, `[ILLEGAL_REASSIGNMENT]`
- **Visual idea**: The screen after click 1 with the two lines `Now serving: 13` and `Number 12, please come to the counter`, next to the Console line `12`.

### Principle 2: Every Render Gets Its Own Fixed Value, and Every Handler Keeps the Value of the Render That Made It
- **Handle**: `each-render-has-its-own-value`
- **Rule**: When React calls the component, it hands it a snapshot of the state for that render; the JSX and every handler made in that call are calculated with that value, so a handler reads the same value on every line, before or after the setter.
- **Opening Essence**:
  - **Furniture-free snippet**: `function render(number) { function handleNext() { console.log(number); } return handleNext; }` with `const first = render(12); const second = render(13); first(); second(); first();`, which logs `12`, `13`, `12`.
  - **Human image**: two photos of the same screen taken one click apart; each photo keeps its number. The substitution method from `react.dev` is reading the handler with the photo's number written in: in the render with `12`, `handleNext` is `setNumber(12 + 1); setAnnouncement('Number ' + 12 + ...)`.
  - **Exact nuance of confusion to state out loud**:
    1. `console.log(number)` above the setter and below the setter look like different moments, but they are the exact same thing: both log `12`, because both run in the handler of the render where `number` is `12`.
    2. `first` and `second` have the same code and the same name `number` inside, so they look like the same function, but they are NOT the same thing: each was made by a different call and closes over its own `number`.
- **Root Distinction**:
  - *Junior blurred view*: "There is one `number` in my component, and the setter updates it."
  - *Senior grounding*: there is one `number` per render; each call of `QueueBoard` makes a new constant and a new `handleNext` that closes over it.
- **Real Beginner Mistake (events, in order)**:
  1. After Principle 1, the developer thinks the setter is slow and moves the announcement line above `setNumber(number + 1)`, so it runs first.
  2. The staff clicks `Next customer`.
  3. The announcement still says `Number 12, please come to the counter`, and the screen shows `Now serving: 13`.
  4. The developer clicks twice very fast, expecting the second click to read the stale `12`.
  5. The screen shows `Now serving: 14` and `Number 13, please come to the counter`: the second click ran the handler of the render with `13`.
- **Interview Depth**:
  - `react.dev` Recap: "Every render (and functions inside it) will always see the snapshot of the state that React gave to that render" and "Event handlers created in the past have the state values from the render in which they were created".
  - The JavaScript reason is the closure: `handleNext` is created inside the call of `QueueBoard` and keeps reading that call's `number`.
  - React makes sure the state is updated before the next intentional user action such as a click, so a click handler never starts with an old value (`react.dev` `<DeepDive>` "Is using an updater always preferred?").
  - The word stale for a value older than what the screen shows; the snapshot is not stale when the handler starts.
  - Preview: calling `setNumber(number + 1)` three times in one handler moves the screen from `12` to `13`, not `15`, because all three read the same `12`; why, and the updater function that fixes it, are `Q16 #state_updates`.
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any second `handleNext` in `QueueBoard.jsx`; the file defines it once.
    - **Who supplies it**: JavaScript, which creates a new `handleNext` every time React calls `QueueBoard`; React connects the newest one to the button at commit.
    - **What JavaScript and React do**:
      1. Render with `12`: JavaScript creates `number` as `12` and a `handleNext` that reads it.
      2. React connects that `handleNext` to the button's click.
      3. The click runs it; it reads `12` on every line.
      4. Render with `13`: JavaScript creates a new `number` as `13` and a new `handleNext`.
      5. React connects the new `handleNext`; the next click reads `13`.
- **React Does**:
  - Announcement line moved above `setNumber`, dev server with `<StrictMode>`: click 1 shows `Now serving: 13` and `Number 12, please come to the counter`, Console `12`; click 2 shows `Now serving: 14` and `Number 13, please come to the counter`, Console `13`.
  - Two back-to-back clicks with no wait: `Now serving: 14` and `Number 13, please come to the counter`, Console `12` then `13`.
  - Plain closure script in Chrome: `first()`, `second()`, `first()` give `12`, `13`, `12`.
  - Three `setNumber(number + 1)` calls in one handler: `Now serving: 12` to `13` to `14`, one per click.
- **Example Step**: In `src/components/QueueBoard.jsx`, moves the announcement line and the `console.log(number)` above `setNumber(number + 1)` in `handleNext`. No new page element.
- **Code names**: `src/components/QueueBoard.jsx`, `QueueBoard`, `handleNext`, `number`, `setNumber(number + 1)`, `setAnnouncement`, `console.log(number)`, `render`, `first`, `second`, `Now serving: 14`, `Number 13, please come to the counter`
- **Visual idea**: Three photos in a row, one per render (`12`, `13`, `14`), each holding its own `number` and its own `handleNext` with the number written in.

### Principle 3: Code That Runs Later Still Reads the Snapshot of the Click That Started It
- **Handle**: `delayed-code-keeps-the-snapshot`
- **Rule**: A state value never changes within a render, even in code that runs seconds later; a function passed to `setTimeout` inside a handler reads that render's value after the screen has moved on, and so each click's delayed work keeps the number of its own click.
- **Opening Essence**:
  - **Furniture-free snippet**: `function render(number) { return function handleNext() { setTimeout(() => console.log(number), 300); }; }` with `render(12)()` then `render(13)()`; after the wait, the Console gets `12` and `13`.
  - **Human image**: a letter written now and posted with a delay. It arrives later, but it says what was true when it was written.
  - **Exact nuance of confusion to state out loud**:
    1. Waiting three seconds looks as if it should give React time to update `number`, so the delayed line seems different from the line right after the setter, but it is the exact same thing: both read the value of the render that made the handler.
    2. Delayed code that reads the old click's number looks like a bug, but it is NOT always one: when two clicks overlap, each click's last call names its own number instead of both naming the newest.
- **Root Distinction**:
  - *Junior blurred view*: "By the time the timer fires, the screen says `13`, so `number` inside the timer is `13`."
  - *Senior grounding*: the timer's function was created in the render with `12` and closes over that `number`; how much time passes does not matter.
- **Real Beginner Mistake (events, in order)**:
  1. Customers miss their call, so the developer adds a last call to `handleNext`: `setTimeout(() => { setAnnouncement('Last call for number ' + number); }, 3000);`.
  2. The staff clicks `Next customer`; the screen shows `Now serving: 13` and `Number 12, please come to the counter`.
  3. Three seconds later, the announcement changes to `Last call for number 12`, while the screen still shows `Now serving: 13`.
  4. The developer believes waiting would bring the new number and is surprised the timer still reads `12`.
  5. The staff clicks `Next customer` again one second after the first click; the screen shows `14` and `Number 13, please come to the counter`.
  6. The first timer fires and shows `Last call for number 12`; one second later the second timer shows `Last call for number 13`: each timer kept the number of its own click, both one behind.
- **Interview Depth**:
  - `react.dev`: "A state variable's value never changes within a render, even if its event handler's code is asynchronous."
  - The snapshot protects from timing mistakes: in the `react.dev` form, a message sent to Alice still says Alice after the user switches the field to Bob before the five-second send.
  - When delayed code truly needs the latest value instead of the click's value, a ref is the tool (`Q30 #use_ref`).
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: any `number` passed to the arrow function inside `setTimeout`; it takes no parameters.
    - **Who supplies it**: JavaScript, through the closure: the arrow function is created inside `handleNext`, which was created in the render with `12`.
    - **What JavaScript and React do**:
      1. The click runs `handleNext` from the render with `12`.
      2. `setTimeout` stores the arrow function and returns at once; the handler finishes.
      3. React renders with `13` and commits `Now serving: 13`.
      4. Three seconds later, the browser runs the stored arrow function.
      5. It reads the `number` it closed over, `12`, and calls `setAnnouncement('Last call for number 12')`.
- **React Does**:
  - One click, dev server with `<StrictMode>`: after 0.2 seconds, `Now serving: 13` and `Number 12, please come to the counter`; after 3.4 seconds, `Now serving: 13` and `Last call for number 12`; Console `timer reads 12`.
  - Two clicks one second apart: after click 2, `Now serving: 14` and `Number 13, please come to the counter`; at about three seconds after click 1, `Last call for number 12`; at about three seconds after click 2, `Last call for number 13`; Console `timer reads 12`, `timer reads 13`. Same in the production build.
  - Plain closure script with `setTimeout` in Chrome: `12` then `13`.
- **Example Step**: Adds the `setTimeout` last call at the end of `handleNext` in `src/components/QueueBoard.jsx`. No new page element; the announcement line changes to the last call after three seconds.
- **Code names**: `setTimeout`, `3000`, `'Last call for number ' + number`, `Last call for number 12`, `Last call for number 13`, `handleNext`, `setAnnouncement`, `Now serving: 13`, `Now serving: 14`, `useRef`
- **Visual idea**: A timeline of two clicks one second apart, with the screen moving `12`, `13`, `14` above and two delayed last calls below, each linked back to the click that created it.

### Principle 4: To Use the New Value Now, Calculate It Once and Pass the Same Variable Everywhere
- **Handle**: `calculate-next-value-once`
- **Rule**: When a handler needs the next state right away, calculate it once in a new constant such as `nextNumber`, pass it to the setter, and use that constant in every other line, including delayed code; never read the state variable to get the value just set.
- **Opening Essence**:
  - **Furniture-free snippet**: `const nextCount = count + 1; setCount(nextCount); console.log(count); console.log(nextCount);`, which logs `0` and `1` (`react.dev` Troubleshooting).
  - **Human image**: writing the new number on a note before handing it over: the cashier keeps the note, so every later step reads the same new number.
  - **Exact nuance of confusion to state out loud**:
    1. `setNumber(number + 1)` and `setNumber(nextNumber)` give React the exact same value, `13`; the only difference is that `nextNumber` stays in the handler to be read again.
    2. `nextNumber` looks like a way around the snapshot, but it is NOT a change to `number`: `number` is still `12` in this handler, and `nextNumber` is a separate constant that holds `13`.
- **Root Distinction**:
  - *Junior blurred view*: "I need to wait for the state to update, then read it."
  - *Senior grounding*: the handler already knows the next value because it calculated it; keep that value in a variable instead of reading the state again.
- **Real Beginner Mistake (events, in order)**:
  1. The announcement has called the wrong number since Principle 1, and the last call since Principle 3.
  2. The developer first tries to read `number` again later in the handler, then inside the timer; both give `12`.
  3. The fix: `const nextNumber = number + 1;` as the first line of `handleNext`, then `setNumber(nextNumber);`, `setAnnouncement('Number ' + nextNumber + ', please come to the counter');`, and `setAnnouncement('Last call for number ' + nextNumber);` inside the timer.
  4. The staff clicks `Next customer`: the screen shows `Now serving: 13` and `Number 13, please come to the counter`; three seconds later, `Last call for number 13`.
  5. Two clicks one second apart: `Number 14, please come to the counter`, then `Last call for number 13`, then `Last call for number 14`; each click calls its own customer.
- **Interview Depth**:
  - The `react.dev` advice: "If you need to use the next state, you can save it in a variable before passing it to the `set` function."
  - `nextNumber` is created inside the handler, so it is also part of the click's snapshot; the timer closes over it the same way it closed over `number`.
  - This fixes one update per click; several updates of the same state in one click need the updater function (`Q16 #state_updates`).
- **Bridges**:
  - **Bridge 1**:
    - **Reader will not find**: `13` written anywhere in `handleNext`, yet the announcement and the last call both say `13`.
    - **Who supplies it**: the handler itself, which calculates `number + 1` once and names it `nextNumber`.
    - **What JavaScript and React do**:
      1. In the render with `12`, the click runs `handleNext`; `nextNumber` becomes `13`.
      2. `setNumber(nextNumber)` stores `13` inside React.
      3. `setAnnouncement` builds `'Number 13, please come to the counter'` from `nextNumber`.
      4. The timer function closes over `nextNumber`, so three seconds later it builds `'Last call for number 13'`.
      5. React renders with `13` and commits `Now serving: 13`; both lines now agree.
- **React Does**:
  - One click, dev server with `<StrictMode>`: after 0.2 seconds, `Now serving: 13` and `Number 13, please come to the counter`, Console `12 13`; after 3.4 seconds, `Last call for number 13`, Console `timer reads 13`.
  - Two clicks one second apart: after click 2, `Now serving: 14` and `Number 14, please come to the counter`; then `Last call for number 13`; then `Last call for number 14`; Console `12 13`, `13 14`, `timer reads 13`, `timer reads 14`. Same in the production build. No Console warning or error.
- **Example Step**: Rewrites `handleNext` in `src/components/QueueBoard.jsx` with `const nextNumber = number + 1` and uses `nextNumber` in the setter, the announcement, and the timer. No new page element; both lines now agree.
- **Code names**: `nextNumber`, `const nextNumber = number + 1`, `setNumber(nextNumber)`, `'Number ' + nextNumber + ', please come to the counter'`, `'Last call for number ' + nextNumber`, `Number 13, please come to the counter`, `Last call for number 13`, `Number 14, please come to the counter`, `Last call for number 14`, `nextCount`
- **Visual idea**: Before and after: the screen with `Now serving: 13` above `Number 12...` next to `Now serving: 13` above `Number 13...`.

## Interview Points
1. A state variable holds one fixed value for the whole of one render; React hands the component a snapshot of the state each time it calls it.
2. The setter does not change the variable in the running code; it stores the next value in React and asks for a new render, so reading the variable after the setter gives the old value, while the screen updates after the handler.
3. The JavaScript reason is the closure: each render creates new handlers that keep reading that render's value, wherever the read sits in the handler.
4. Delayed code such as `setTimeout` started in a handler still reads that render's value, which keeps each event's work tied to the values of its own moment.
5. React makes sure state is updated before the next click, so a handler never starts with an old value.
6. To use the new value right away, calculate it once in a variable and pass it to the setter and every other line; several updates in one click need the updater function, the next topic.
