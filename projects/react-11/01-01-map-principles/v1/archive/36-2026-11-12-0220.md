# Q36 Principle Map (River Version v1): Separating Events from Effects with useEffectEvent

- **Version**: River Version (`v1`), written under `skills/v10.6`
- **Bank Row**: `questions/questions.md` row 36
- **Topic Tag**: `#effect_events` | `❱ CORE`
- **Interview Question**: *How do you keep non-reactive values from re-running an effect?*

## Scope

Covered here:
- The docs' starting point: "Event handlers only re-run when you perform the same interaction again. Unlike event handlers, Effects re-synchronize if some value they read, like a prop or a state variable, is different from what it was during the last render."
- Reactive logic and non-reactive logic. The docs: "**Logic inside event handlers is *not reactive.***" and "**Logic inside Effects is *reactive.***"
- The problem: one line inside an Effect reads a value the Effect should not react to, and the linter makes that value a dependency, so the Effect re-synchronizes when it changes.
- `useEffectEvent`: "a React Hook that lets you separate events from Effects." It returns an Effect Event, which "always "sees" the latest values of your props and state" and "must be omitted from dependencies".
- Passing a value to the Effect Event as an argument when that value belongs to the event, such as the text of the message that arrived.
- Why suppressing the linter is not the same fix: the value gets stuck at its old value.
- When an Effect Event is the wrong tool: logic that should re-synchronize, such as the connection to `roomId`, and names that describe timing, such as `onMount`.
- The limits: call it only from Effects or other Effect Events, never during rendering, never from an event handler, never pass it to other components or Hooks, never list it in the array; it is a Hook, so it is called at the top level.
- The version: the React blog lists `useEffectEvent` among the features React 19.2 adds.

## Start of the Lecture

**Opening Essence of the chapter**:
- No short code shows the idea before the reader knows the screen, so the idea opens in plain words on a real screen, as Examples 8 and 9 of opening-essence open.
- The real screen: a chat app with rooms, as in Slack. A menu picks the room. The heading reads `Welcome to the general room!`. A tick box reads `Mute notifications`. When a new message arrives in the room, the app shows a notification, unless the tick box is ticked.
- What the user does, and what the user expects:
  1. Picks `travel` in the menu: the app leaves `general` and connects to `travel`.
  2. Ticks `Mute notifications`: the notifications stop. Nothing else changes; the user is still in `travel`.
- The question that screen raises for the developer: the code that shows the notification runs inside the Effect that keeps the connection, and it reads `muted`. How can the Effect read `muted` without reconnecting when `muted` changes?
- The answer, the docs: "You can think of Effect Events as being very similar to event handlers. The main difference is that event handlers run in response to user interactions, whereas Effect Events are triggered by you from Effects."
- Key idea the reader must remember: one Effect can hold two kinds of logic. Connecting to `roomId` must follow `roomId`. Deciding whether to show a notification must read `muted` at the moment a message arrives, and must not follow it. `useEffectEvent` moves the second kind out of the Effect.
- Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"*
  1. `roomId` and `muted` are both props, and the Effect reads both. To the linter they are the same: two reactive values, two dependencies.
  2. For the user they are not the same. The docs: "**a change to the `roomId` *does* mean that they want to connect to a different room.**" Ticking Mute does not mean the user wants to reconnect.
- What is at stake for the user, on the example page:
  1. With `muted` in the array, each tick of the box disconnects and reconnects the chat. The docs, for the same case: "every time `isMuted` changes (for example, when the user presses the "Muted" toggle), the Effect will re-synchronize, and reconnect to the chat. This is not the desired user experience!"
  2. With `muted` left out and the linter suppressed, the chat stays connected, but the tick box stops working. The docs: "even disabling the linter would not work--if you do that, `isMuted` would get "stuck" with its old value."
- Where readers usually go wrong:
  1. They silence the linter to stop the reconnect. The blog: "most users just disable the lint rule and exclude the dependency."
  2. They wrap too much in `useEffectEvent`, including code that should follow `roomId`, only to make the array shorter.
  3. They call the Effect Event from a click handler, or pass it to a child, as if it were an ordinary function.

**Theme**: a chat room that must stay connected to the room the user picked, while it reads the user's current Mute setting each time a message arrives.

**Ways** (what the docs give for a value that the Effect reads, and when each fits):
1. Keep it in the dependency array: when a change of the value means the Effect must re-synchronize, such as `roomId`.
2. Read it in an Effect Event: when the value is only needed at the moment something happens, such as `muted` when a message arrives. This lesson.
3. Change the code so the value is not a dependency at all: move it outside the component or inside the Effect, or pass an updater function instead of reading state. Lesson 37. Named only.
4. Suppress the linter: the docs, "We recommend **never suppressing the linter**." Shown only as the wrong way, in Principle 3.

## Principles

### Principle 1: Reading muted Inside the Effect Reconnects the Chat

- **Rule**: Every reactive value an Effect reads must be in its array, so when one line inside the Effect reads a value only to decide what to do at the moment a message arrives, a change of that value still disconnects and reconnects.
- **Move**: Steps for a surprise, because the user ticks a box that has nothing to do with the connection, and the Console shows a disconnect and a connect.
- **Opening Essence**:
  - The real screen and action: the user is in `general` and ticks `Mute notifications`.
  - Smallest code, the docs' shape for this page:
    1. `connection.on('message', msg => { if (!muted) { showNotification('New message: ' + msg); } });` inside the Effect.
    2. `}, [roomId, muted]);`
  - The docs' two kinds of logic, on the docs' own chat:
    1. "With an event handler, you can be sure that `sendMessage(message)` will *only* run if the user presses the button."
    2. "Effects are reactive, so `createConnection(serverUrl, roomId)` and `connection.connect()` will run for every distinct value of `roomId`."
  - Key idea, the docs: "Things get more tricky when you want to mix reactive logic with non-reactive logic."
  - What is at stake: the user ticks Mute and the chat drops its connection and opens a new one.
- **Root Distinction**:
  - Junior: "The linter asked for `muted`, I added it, so the code is correct."
  - Senior: the array is now correct for the code as written, but the code puts non-reactive logic inside a reactive block; the fix is to move that logic out, not to change the array.
- **Simplest version**:
  - The docs' learn page: `function ChatRoom({ roomId, theme }) { useEffect(() => { ... connection.on('connected', () => { showNotification('Connected!', theme); }); ... }, [roomId, theme]); }`
- **Words to teach**:
  - *reactive logic* and *non-reactive logic*: the docs' names. Logic that should run again when a value changes, such as connecting to `roomId`, and logic that only reads a value when something happens, such as checking `muted` when a message arrives. Needed when `muted` enters the array.
  - *`connection.on('message', ...)`*: provided by our `chat.js`. It hands the connection a function, and the connection calls it with the text of each message. Needed when the notification code appears.
  - *`showNotification`*: provided by our `notifications.js`. Needed at the same moment.
  - Known: reactive value, re-synchronize, Lesson 35. Event handler, Lesson 11. Event handler or Effect, Lesson 34. Linter, Lesson 32.
  - Helper: `'hey'`, `'lol'`, the three-second interval inside `chat.js`.
- **Side by side**:
  - "picking `travel` in the menu" and "ticking `Mute notifications`": NOT the same thing for the user, yet the same thing for the Effect with `[roomId, muted]`. Both disconnect and reconnect. The docs: "From the user's perspective, **a change to the `roomId` *does* mean that they want to connect to a different room.**"
- **Surprises**:
  - Ticking the box disconnects and reconnects the chat:
    1. The user ticks `Mute notifications`.
    2. `setMuted(true)` in `App` asks for a re-render; `ChatRoom` gets `muted` as `true`.
    3. React compares `[roomId, muted]` with the last array; `muted` differs.
    4. React runs the old cleanup: `❌ Disconnected from "general" room at https://localhost:1234`.
    5. React runs the new setup: `✅ Connecting to "general" room at https://localhost:1234...`.
    6. The heading did not change. The order of the two lines follows Lesson 35; their appearance after a tick is `unconfirmed`, a lab check.
  - Messages stop while the user keeps ticking:
    1. Each reconnect clears the old interval and starts a new one, in `chat.js`.
    2. A message arrives only three seconds after the last connect.
    3. A user who ticks and unticks faster than every three seconds gets no message at all. ### Principle 5: onMessage Runs Only Inside Its Own Effect

- **Rule**: Call an Effect Event only from an Effect or another Effect Event in the same component or Hook; never call it during rendering or from an event handler, never pass it to another component or Hook, and declare it next to the Effect that uses it.
- **Move**: Side by side, because calling `onMessage` from the Effect and calling it from a click handler look like two calls of the same function.
- **Opening Essence**:
  - Smallest code, three places for the same call:
    1. Inside the Effect: `connection.on('message', msg => onMessage(msg));`
    2. In a click handler: `<button onClick={() => onMessage('test')}>Test notification</button>`.
    3. As a prop: `<MessageList onMessage={onMessage} />`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* All three call the same function. Only the first is allowed.
  - The docs: "Effect Events are very limited in how you can use them: **Only call them from inside Effects.** **Never pass them to other components or Hooks.**"

- **Simplest version**:

## Interview Points

- Event handlers run in response to specific interactions and are not reactive; Effects run whenever synchronization is needed and are reactive.
- Every reactive value an Effect reads must be in its array, so a value read only at event time, such as `muted` or `theme`, still re-synchronizes the Effect.
- `useEffectEvent` extracts that non-reactive logic into an Effect Event, which always reads the latest props and state at the time of the call.
- An Effect Event is called from inside the Effect and is never listed in the array; the values it reads leave the array too.
- Suppressing the linter also stops the re-run, but the Effect keeps the old value, such as a Mute setting that stops working.
- Only non-reactive logic moves; code that must follow a value, such as the connection to `roomId`, stays in the Effect, and using `useEffectEvent` to skip dependencies hides bugs.
- A value that is part of the event, such as the message or the visited URL, is passed to the Effect Event as an argument.
- Name Effect Events after what the user thinks happened, such as `onMessage` or `onVisit`, not after timing, such as `onMount`.
- Effect Events are called only from Effects or other Effect Events in the same component or Hook, never during rendering, never from event handlers, and never passed to other components or Hooks; for those, use a regular function or `useCallback`.
- Their identity changes on every render on purpose, so a wrong dependency on them shows up at once.
- `useEffectEvent` is a Hook, so it is called at the top level, and React 19.2 added it.
