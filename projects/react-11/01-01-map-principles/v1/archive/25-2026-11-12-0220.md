# Q25 Principle Map (River Version v1): Why State Stays or Goes When the Page Changes

- **Version**: River Version (`v1`), written under `skills/v10.6`
- **Bank Row**: `questions/questions.md` row 25
- **Topic Tag**: `#component_identity` | `❱ CORE`
- **Interview Question**: *Why does state sometimes vanish, or survive, when you did not expect it?*

## Scope

Covered here:
- React holds each component's state, not the JSX tag and not the component function. React ties each piece of state to the component's position in the UI tree.
- React keeps the state for as long as the same component is rendered at the same position. When React removes the component from the tree, it destroys its state. When the component comes back, its state starts from scratch.
- The same component at the same position keeps its state, even when its props change, and even when the code writes two separate tags in two branches. React sees only the tree the component returns, not where the conditions sit in the code.
- A different component type at the same position resets the state, and resets the state of everything inside it. A wrapper tag that changes, such as a `<div>` that appears around the component, is enough.
- To keep state, the tree must match from one render to the next.
- Resetting state on purpose at the same position: the two ways from the React docs, rendering in different positions, or giving each component its own `key`.
- `key` is not only for lists. A `key` becomes part of the position. A different `key` makes React create the component and its DOM elements again from scratch.
- Keys only need to differ among the children of the same parent.

## Start of the Lecture

**Opening Essence of the chapter**:
- The naked idea fits in a few lines of code, with a surprise, so it opens with the smallest code, as Example 7 of [Opening Essence](../../../react-10/skills/v10.6/opening-essence/SKILL.md) does.
- Smallest code: `{isAnna ? <Counter person="Anna" /> : <Counter person="Ben" />}`. The user clicks Anna's counter up to 3, then switches to Ben. Ben's counter shows 3.
- Confusion to say out loud: *"Yes, it is the exact same thing!"* To the reader, two tags with two names look like two counters. To React, they are the exact same `Counter`: the same component at the same position, with only a new `person` prop.
- The second confusion, for later: *"It may look the same, or work the same at first, but it is NOT the same thing!"* `<Counter key="Anna" person="Anna" />` and `<Counter key="Ben" person="Ben" />` look almost the same as the two tags above, and both show 0 on the first render. With different keys, they are two different counters.
- Everyday image, from the React docs' own word "address": a letter goes to an address, not to a person. A new family that moves into the same house finds the old family's letters. React gives state to a position in the tree, so a new prop at the same position finds the old state. The docs: "To React, these two counters have the same 'address': the first child of the first child of the root."
- Key idea: React keeps state by position in the UI tree. Same component, same position: the state stays. Removed, or a different component there: the state is gone.
- What is at stake: the user writes "Happy birthday, Anna!", clicks Ben, and the same text sits under "Note to Ben", next to a button "Send to Ben". Or the user's whole note disappears when a tip appears above it.
- Where readers usually go wrong: they think the state lives inside the component function or inside the JSX tag; they think a new prop makes a new component; they read the `if` and `? :` in their code instead of the tree that the code returns.

**Theme**: a note to a friend. The user picks Anna or Ben and types a note in one text box, and the text must belong to the right friend.

**Ways** (developers really choose between these to give a component a fresh start when it should be a different one):
1. Give each component its own `key`, such as `key={friend}`. The docs call it "more generic". Principle 4, the lesson's main way.
2. Render the components in different positions, such as `{isAnna && <NoteBox friend="Anna" />}` and `{!isAnna && <NoteBox friend="Ben" />}`. The docs: "convenient when you only have a few independent components rendered in the same place." Principle 4, side by side.
3. Not a good way, named so the reader recognizes it: clearing the state from an Effect when a prop changes. The docs: "This is inefficient because `ProfilePage` and its children will first render with the stale value, and then render again." Lesson 34, named only.

**Example page chosen for this lesson**: a page to write a note to a friend.
- Parts of the final page: `<h1>Write a Note</h1>`; two buttons `Anna` and `Ben`; a button `Show tip` / `Hide tip`; a button `Close note` / `Write a note`; a line `Tip: say one thing you like about them.` when the tip is on; and the `NoteBox` with `<h2>Note to Anna</h2>`, a `<textarea>` with the placeholder `Write to Anna`, and a button `Send to Anna`.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx`, `src/components/NoteBox.jsx`.
- State in `App`: `isOpen`, starting `true`; `friend`, starting `'Anna'`; `showTip`, starting `false`.
- State in `NoteBox`: `text`, starting `''`, in a controlled `<textarea>`.
- Final tag: `{isOpen && <NoteBox key={friend} friend={friend} />}`, with `{showTip && <p>Tip: say one thing you like about them.</p>}` just above it.
- The `Send to` button has no handler. Sending is not this lesson. See Open Issues.

**Why this page**:
1. Everyone knows a text box, a friend's name, and a send button. Nothing needs explaining.
2. It needs this lesson's idea: one text box serves two friends, so the page must decide whether the text stays or goes.
3. The broken result is big and has a real cost: "Happy birthday, Anna!" under the heading "Note to Ben", above "Send to Ben".
4. The actions are click and type.
5. Every helper is known: `useState`, Lesson 12; `&&` and a `let` with `if`, Lesson 10; the controlled `<textarea>`, Lesson 20; `key`, Lesson 18. No array, no `.map`, no data file, no Effect.
6. It follows the React docs' own case, "Resetting a form with a key": "You don't want to let the user send a message they already typed to a wrong person due to an accidental click."

## Principles

### Principle 1: Closing the Note Throws Away Its Text

- **Rule**: React keeps a component's state while the component is rendered at its position in the UI tree; when React removes the component, it destroys the state, and when the component comes back, its state starts from scratch.
- **Move**: Steps for a surprise, because the user closes the note, opens it again, and the typed text is gone with no line of code that clears it.
- **Opening Essence**:
  - Smallest code, from the docs: `const counter = <Counter />;` and `return <div>{counter}{counter}</div>;`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* One JSX tag, written once, gives two counters. The user clicks one up to 2, and the other stays at 0. The state is not in the tag; it is at each position.
  - Second smallest code: `{showB && <Counter />}` with a checkbox. The user clicks the second counter up to 3, clears the checkbox, ticks it again: the counter shows 0.
  - Key idea from the docs: "the state is actually held inside React. React associates each piece of state it's holding with the correct component by where that component sits in the render tree."
  - What is at stake: anything the user typed inside a part of the page that disappears is lost when that part comes back.
- **Root Distinction**:
  - Junior: "The note's text lives inside `NoteBox`, so it comes back when `NoteBox` comes back."
  - Senior: React keeps the text at the position where `NoteBox` was rendered; when nothing is rendered there, React throws the text away.
- **Simplest version**:
  - `function Counter() { const [count, setCount] = useState(0); return <button onClick={() => setCount(count + 1)}>{count}</button>; }`
  - Parent: `{showB && <Counter />}` and a button or checkbox that flips `showB`.
- **Words to teach**:
  - *position in the UI tree*: where a component sits among its parent's children, such as the first child of a `<div>`. Provided by React, which matches components between two renders by this position. Needed when the reader sees one tag give two counters.
  - *destroy state, reset state*: React's docs say that when React removes a component, "it destroys its state", and that the next time it appears, its state is "initialized from scratch". Needed when the note comes back empty.
  - Known: `useState` and isolated state for each copy, Lesson 12. `&&` that shows the tag or nothing, Lesson 10. The controlled `<textarea>`, Lesson 20. The UI tree, Lesson 06.
  - Helper: none.
- **Side by side**:
  - "with one `<Counter />` tag stored in `counter` and placed twice" and "with two `<Counter />` tags": the exact same thing. Both give two separate counters, because each one sits at its own position.
  - "with `showB` true, then false, then true" and "with `showB` true the whole time": NOT the same thing. The second keeps the count; the first gives a new counter at 0.
- **Surprises**:
  - The user types a note, closes it, opens it again, and the box is empty:
    1. The page opens with `isOpen` `true`. React renders `NoteBox` at its position, with `text` `''`.
    2. The user types `Happy birthday, Anna!`. `NoteBox` holds it in `text`.
    3. The user clicks `Close note`. `App` sets `isOpen` to `false`.
    4. React renders `App` again. `isOpen && <NoteBox ... />` gives `false`, so nothing is rendered at that position.
    5. React removes `NoteBox` from the tree and destroys its `text`.
    6. The user clicks `Write a note`. `App` sets `isOpen` to `true`.
    7. React renders a `NoteBox` at the position again. It is a new one, so `useState('')` starts it with `''`.
    8. The box is empty. No line of our code set `text` back to `''`.
- **Where did that come from?**:
  - `''` in the box after reopening: the `''` written in `useState('')` inside `NoteBox`. React uses it again because the `NoteBox` is new.
  - `isOpen` and `setIsOpen` in `App`: created by `useState(true)` in `App`.
- **Real beginner mistake** (the bank's row 73 hook, and the React docs' `<Activity>` page, "unmounting a component destroys its internal state, which is not always what you want"):
  1. A developer shows a panel with `{isShowing && <Panel />}`.
  2. The user types in a box inside the panel.
  3. The user closes the panel for a moment to look at something else.
  4. The user opens the panel again.
  5. The box is empty, and the user must type everything again.
- **Interview depth**:
  - The docs' Recap: "State is not kept in JSX tags. It's associated with the tree position in which you put that JSX."
  - The docs' bold rule: "React preserves a component's state for as long as it's being rendered at its position in the UI tree. If it gets removed, or a different component gets rendered at the same position, React discards its state."
  - Ways to keep the text of a removed part, from the DeepDive "Preserving state for removed components": render it and hide it with CSS, which "can get very slow if the hidden trees are large"; lift the state up into the parent, "the most common solution", Lesson 24; or save it in `localStorage` so a draft survives even when the user closes the page.
  - `<Activity mode="hidden">` hides children and keeps their state: "React will reveal the children with their previous state restored." Lesson 73, named only.
- **React does**:
  - Page: after `Close note` and `Write a note`, the `<textarea>` is empty and shows the placeholder `Write to Anna`. `unconfirmed`.
  - Console: no error or warning. `unconfirmed`.
  - Elements panel: while the note is closed, there is no `<h2>`, no `<textarea>`, and no `Send to Anna` button in the DOM. `unconfirmed`.
- **Example step**:
  - Creates `src/components/NoteBox.jsx`: `const [text, setText] = useState('');`, `<h2>Note to {friend}</h2>`, `<textarea value={text} placeholder={'Write to ' + friend} onChange={e => setText(e.target.value)} />`, and `<button>Send to {friend}</button>`.
  - Creates `src/App.jsx`: `<h1>Write a Note</h1>`, `const [isOpen, setIsOpen] = useState(true);`, `<button onClick={() => setIsOpen(!isOpen)}>{isOpen ? 'Close note' : 'Write a note'}</button>`, and `{isOpen && <NoteBox friend="Anna" />}`.
- **Code names**: `App.jsx`, `NoteBox.jsx`, `App`, `NoteBox`, `isOpen`, `setIsOpen`, `useState(true)`, `text`, `setText`, `useState('')`, `friend`, `Write a Note`, `Note to Anna`, `Write to Anna`, `Send to Anna`, `Close note`, `Write a note`, `Happy birthday, Anna!`, `Counter`, `count`, `setCount`, `counter`, `showB`

### Principle 2: Switching to Ben Keeps Anna's Text

- **Rule**: When the same component is rendered at the same position, React keeps its state, even when its props change and even when the code writes two separate tags in two branches, because React matches what the component returns, not how the code is written.
- **Move**: Steps for a surprise, because the heading changes to Ben while the text written for Anna stays. Side by side for one tag against two tags in a `? :`.
- **Opening Essence**:
  - Smallest code: `{isAnna ? <Counter person="Anna" /> : <Counter person="Ben" />}`. The user clicks Anna's counter up to 3 and switches: Ben's counter shows 3.
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* For React, the two tags in the `? :` and one tag `<Counter person={person} />` are the exact same thing: a `Counter` as the first child, with a new prop.
  - Everyday image: the address from the chapter opening. Ben moves into the house where Anna lived, and finds Anna's letters.
  - The fact the reader already has, Lesson 13: a re-render keeps the DOM nodes in the same spot with their typed text. This principle says the same holds for state.
  - What is at stake, from the docs: "You don't want to let the user send a message they already typed to a wrong person due to an accidental click."
- **Root Distinction**:
  - Junior: "`friend` is now Ben, so `NoteBox` is now Ben's note."
  - Senior: a new prop at the same position is the same `NoteBox`; only a new component type or a new `key` at that position makes a new one.
- **Simplest version**:
  - `{isAnna ? <Counter person="Anna" /> : <Counter person="Ben" />}` and a button `Next` that flips `isAnna`.
  - The docs' two `return` lines, one inside `if (isFancy)` and one after it, each with its own `<Counter />` inside a `<div>`: the count stays when the user ticks the box.
- **Words to teach**:
  - *same component at the same position*: React's rule for keeping state. React's docs: "It's the same component at the same position, so from React's perspective, it's the same counter." Needed at the moment the text stays under "Note to Ben".
  - *the "address"*: the docs' word for a position, such as "the first child of the first child of the root". Needed with the `if` and two `return` lines.
  - Known: props from the tag, Lesson 08. `? :` and early `return`, Lesson 10. A re-render keeps DOM nodes in the same spot, Lesson 13.
  - Helper: none.
- **Side by side**:
  - "with `<NoteBox friend={friend} />`" and "with `friend === 'Anna' ? <NoteBox friend="Anna" /> : <NoteBox friend="Ben" />`": the exact same thing for React. Both put a `NoteBox` at the same position, so the text stays in both.
  - "with two `return` lines, one inside `if`, each with `<Counter />` as the first child of a `<div>`" and "with one `return`": the exact same thing. The docs: "React doesn't know where you place the conditions in your function. All it 'sees' is the tree you return."
- **Surprises**:
  - The user writes to Anna, clicks Ben, and Anna's text is now under Ben's name:
    1. The page opens with `friend` `'Anna'`. The heading says `Note to Anna`.
    2. The user types `Happy birthday, Anna!`. `NoteBox` holds it in `text`.
    3. The user clicks `Ben`. `App` sets `friend` to `'Ben'`.
    4. React renders `App` again. At the same position, `App` returns a `NoteBox` again, with the prop `friend` `'Ben'`.
    5. React sees the same component type at the same position, so it keeps this `NoteBox` and its `text`.
    6. `NoteBox` runs again with the new prop. The heading says `Note to Ben`, and the button says `Send to Ben`.
    7. `text` is still `Happy birthday, Anna!`, so the box still shows it.
- **Where did that come from?**:
  - `friend` inside `NoteBox`: `App` writes `friend={friend}` on the tag, and the parameter list unpacks it, Lesson 08.
  - `Happy birthday, Anna!` under `Note to Ben`: the `text` state of the `NoteBox` that React kept, typed by the user before the click.
- **Real beginner mistake** (the React docs' "Reset a detail form" challenge):
  1. A contact page shows an edit form for the chosen contact, with `useState(initialData.name)` in `EditContact`.
  2. The user picks Taylor and sees Taylor's name in the form.
  3. The user picks Alice.
  4. `EditContact` stays at the same position, so React keeps its state.
  5. `useState` reads `initialData.name` only on the first render, Lesson 22.
  6. "the state updates but the form keeps showing the previous contact's details."
- **Interview depth**:
  - The docs: "it's the position in the UI tree--not in the JSX markup--that matters to React!"
  - The docs: "By default, React preserves state of a component while it stays at the same position. Usually, this is exactly what you want, so it makes sense as the default behavior."
  - The docs, on the chat: "In many apps, this may be the desired behavior, but not in a chat app!"
  - The docs' "Clear an image while it's loading" challenge: the same `<img>` tag keeps showing the old image until the next one loads, because React reuses the DOM node at the same position.
- **React does**:
  - Page: after clicking `Ben`, the heading reads `Note to Ben`, the button reads `Send to Ben`, and the box still shows `Happy birthday, Anna!`. `unconfirmed`.
  - Console: no error or warning. `unconfirmed`.

### Principle 3: The Tip Box Around the Note Erases It

- **Rule**: When a different component type appears at a position, React destroys the old component and the state of everything inside it; to keep state, the tree must match from one render to the next.
- **Move**: Steps for a surprise, because showing a tip line erases a note that the tip never touches. Side by side for the wrapped note and the tip placed above the note.
- **Opening Essence**:
  - Smallest code, from the docs: `{isPaused ? <p>See you later!</p> : <Counter />}`. The user clicks the counter up to 3, pauses, and comes back: the counter shows 0.
  - Second smallest code, from the docs: `{isFancy ? <div><Counter /></div> : <section><Counter /></section>}`. The `Counter` is the same, but the tag around it changes, and the count goes back to 0.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* The `Counter` looks untouched, because only the tag around it changed. React compares the tree from the top, so a new `<div>` where a `<section>` was is a new branch, and everything inside it is new.
  - Key idea from the docs: "if you want to preserve the state between re-renders, the structure of your tree needs to 'match up' from one render to another."
- **Root Distinction**:
  - Junior: "I only added a `<div>` around the note; the note itself did not change."
  - Senior: the position now holds a `<div>` instead of a `NoteBox`, a different component type, so React removes the `NoteBox` and everything inside it.
- **Simplest version**:
  - `{isPaused ? <p>See you later!</p> : <Counter />}` and a checkbox `Take a break`.
- **Words to teach**:
  - *component type*: which component or tag sits at a position, such as `NoteBox`, `<div>`, or `<p>`. React's docs: "you switch between _different_ component types at the same position." Needed when the `<div>` takes the place of `NoteBox`.
  - *subtree*: a component and everything rendered inside it. React's docs: "when you render a different component in the same position, it resets the state of its entire subtree." Needed when the reader asks why `NoteBox` loses its state although `NoteBox` itself did not change.
  - Known: a `let` variable filled by an `if`, and `cond && <Tag />`, Lesson 10. A component defined inside another one, Lesson 04.
  - Helper: none.
- **Side by side**:
  - "with `note` wrapped in a `<div>` when `showTip` is true" and "with `{showTip && <p>...</p>}` above `{isOpen && <NoteBox ... />}`": NOT the same thing. Both show the tip above the note. With the wrapper, the note's position holds a `<div>` instead of a `NoteBox`, and the text is gone. With the tip above, the `NoteBox` keeps its position, and the text stays.
  - "with `{showTip && <p>...</p>}` giving `false`" and "with `{showTip && <p>...</p>}` giving the tip line": the exact same position for `NoteBox`. The `{showTip && ...}` line keeps its place in the parent even when it shows nothing, so `NoteBox` stays the next child. The docs' fix puts `{showHint && ...}` before `<Form />` so that "`Form` always renders in the same position". `false` shows nothing, Lesson 10.
- **Surprises**:
  - The user clicks `Show tip`, and the note the user typed is gone:
    1. `App` has `let note = <NoteBox friend={friend} />;`, then `if (showTip) { note = <div><p>Tip: say one thing you like about them.</p>{note}</div>; }`, and returns `{isOpen && note}`.
    2. The user types `Happy birthday, Anna!`.
    3. The user clicks `Show tip`. `App` sets `showTip` to `true`.
    4. React renders `App` again. The position that held a `NoteBox` now holds a `<div>`.
    5. A `<div>` is a different type from `NoteBox`, so React removes `NoteBox` and destroys its `text`.
    6. React builds the `<div>`, the tip line, and a new `NoteBox` inside it, with `text` `''`.
    7. The tip shows, and the box under it is empty.
    8. The user types again and clicks `Hide tip`. The `<div>` goes, a `NoteBox` takes the position, and the text is lost a second time.
- **Where did that come from?**:
  - `note` in `App`: a `let` variable that holds a JSX tag, filled before the `return`, as in Lesson 10. Holding a tag in a variable does not keep state: the docs' `const counter = <Counter />` of Principle 1.
  - The new `NoteBox` inside the `<div>`: the same `NoteBox` function, now one level deeper, inside a new branch of the tree.
- **Real beginner mistake** (the React docs' "Fix disappearing input text" challenge):
  1. A component returns a hint line, a `<Form />`, and a button inside `if (showHint)`, and a `<Form />` and a button after it.
  2. The user types in the form.
  3. The user clicks `Show hint`.
  4. In the `if` branch, `Form` is the second child; in the other branch, it is the first child.
  5. "The first position changes between holding a `p` and a `Form`", so React resets `Form`.
  6. The typed text is gone.
  7. The docs' fix: "unify the branches so that `Form` always renders in the same position", with `{showHint && <p>...</p>}` before `<Form />`.
- **Interview depth**:
  - The docs: "When the child `section` was removed from the DOM, the whole tree below it (including the `Counter` and its state) was destroyed as well."
  - The docs' other fix for the hint challenge, `{null}` before `<Form />`, works but "is much less obvious and introduces a risk that someone else will remove that `null`."
  - The same rule explains Lesson 04's nested component: "a *different* `MyTextField` function is created for every render of `MyComponent`. You're rendering a *different* component in the same position, so React resets all state below." The docs: "This leads to bugs and performance problems."
  - The docs' Recap: "Don't nest component definitions, or you'll reset state by accident."
  - `Fragment.md`: going from `<><Child /></>` to `<Child />` does not reset the state; going from `<><><Child /></></>` to `<Child />` does. The Fragment is the one wrapper that does not count, and only one level deep.
- **React does**:
  - Page: after `Show tip`, the tip line shows and the `<textarea>` is empty. `unconfirmed`.
  - Page, with the tip above the note: after `Show tip`, the tip line shows and the box still shows `Happy birthday, Anna!`. `unconfirmed`.
  - Console: no error or warning. `unconfirmed`.
  - Elements panel: with the wrapper, a new `<div>` holds a new `<p>` and a new `<textarea>`. `unconfirmed`.
- **Example step**:
  - In `App.jsx`, the broken version first: adds `const [showTip, setShowTip] = useState(false);`, `<button onClick={() => setShowTip(!showTip)}>{showTip ? 'Hide tip' : 'Show tip'}</button>`, `let note = <NoteBox friend={friend} />;`, the `if (showTip)` that wraps `note` in a `<div>` with the tip, and `{isOpen && note}`.
  - In `App.jsx`, the fix: removes `note` and the `if`; returns `{showTip && <p>Tip: say one thing you like about them.</p>}` and then `{isOpen && <NoteBox friend={friend} />}`.
  - `NoteBox.jsx` does not change.
- **Code names**: `App.jsx`, `NoteBox.jsx`, `showTip`, `setShowTip`, `useState(false)`, `Show tip`, `Hide tip`, `Tip: say one thing you like about them.`, `note`, `<div>`, `<p>`, `{isOpen && note}`, `Happy birthday, Anna!`, `Counter`, `isPaused`, `See you later!`, `Take a break`, `isFancy`, `<section>`, `showHint`, `Form`, `Show hint`, `MyTextField`, `MyComponent`

### Principle 4: `key={friend}` Gives Ben an Empty Note

- **Rule**: To reset a component at the same position on purpose, give it a `key` that changes when it should become a different one; React uses the `key` as part of the position, so a new `key` makes a new component with new state and new DOM elements.
- **Move**: Side by side, because `<NoteBox friend={friend} />` and `<NoteBox key={friend} friend={friend} />` look almost the same and both show an empty box at first, but behave differently after the click on `Ben`.
- **Opening Essence**:
  - Smallest code, from the docs: `{isAnna ? <Counter key="Anna" person="Anna" /> : <Counter key="Ben" person="Ben" />}`. The user clicks Anna's counter up to 3 and switches: Ben's counter shows 0.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Next to Principle 2's tags, only `key` was added, and the first render looks the same. With different keys, they are two counters.
  - Second confusion: *"Yes, it is the exact same thing!"* This `key` is the same `key` as in Lesson 18's lists. The docs: "Keys aren't just for lists!"
  - Everyday image, from the docs: "By default, React uses order within the parent ('first counter', 'second counter')". A `key` says "not just a *first* counter, or a *second* counter, but a specific counter", like a name on the door instead of a house number. The docs' Solution: "A `key` lets you specify a named position instead of relying on order."
- **Root Distinction**:
  - Junior: "To clear the box for Ben, I must find a way to set `text` back to `''` when `friend` changes."
  - Senior: Anna's note and Ben's note are two different notes; a `key` from `friend` tells React so, and React gives each one its own fresh state.
- **Simplest version**:
  - `<Counter key="Anna" person="Anna" />` and `<Counter key="Sarah" person="Sarah" />` in the two branches of `? :`, as in the docs, with `Anna` and `Ben`.
  - The docs' `useState.md` reset button: `<Form key={version} />` with `setVersion(version + 1)` on `Reset`.
- **Words to teach**:
  - *`key` outside a list*: the same `key` as Lesson 18, on any component. React's docs: "Specifying a `key` tells React to use the `key` itself as part of the position, instead of their order within the parent." Needed when the user clicks `Ben`.
  - *explicit identity*: the docs' second way to reset is to "Give each component an explicit identity with `key`". Needed in one line next to the name on the door.
  - *re-create*: React's docs, on `key={to.id}`: "the `Chat` component will be recreated from scratch, including any state in the tree below it. React will also re-create the DOM elements instead of reusing them." Needed for the Elements panel.
  - Known: `key` is not a prop, so `NoteBox` still needs `friend={friend}`, Lesson 18. Keys must be unique among siblings, Lesson 18.
  - Helper: none.
- **Side by side**:
  - "with `<NoteBox friend={friend} />`" and "with `<NoteBox key={friend} friend={friend} />`": NOT the same thing. Both show an empty box for Anna when the page opens. After the click on `Ben`, the first keeps Anna's text, and the second shows an empty box for Ben.
  - "with `key={friend}`" and "with `{friend === 'Anna' && <NoteBox friend="Anna" />}` and `{friend === 'Ben' && <NoteBox friend="Ben" />}`": the same result for this page; both reset the note on each switch. The docs' Option 1 uses two positions and suits "only a few independent components"; the `key` is "more generic" and needs one tag.
  - "with `key={friend}` on `<NoteBox>`" and "with `key={email.id}` on a row inside `.map`": the exact same thing. In both, the `key` tells React which component is which.
- **Surprises**:
  - The user writes to Anna, goes to Ben, comes back to Anna, and Anna's note is also gone:
    1. The page opens with `friend` `'Anna'`. React renders `NoteBox` with `key` `'Anna'`.
    2. The user types `Happy birthday, Anna!`.
    3. The user clicks `Ben`. `App` sets `friend` to `'Ben'`.
    4. React renders `App` again. The `NoteBox` now has `key` `'Ben'`, a different position for React.
    5. React removes Anna's `NoteBox` and destroys its `text`. It builds a new `NoteBox` for Ben with `text` `''`, and new DOM elements.

## Interview Points

1. React holds state, not the component function and not the JSX tag, and ties each piece of state to the component's position in the UI tree.
2. While the same component is rendered at the same position, React keeps its state, even when its props change.
3. React matches the tree a component returns, not the code: two tags in two branches of `if` or `? :` at the same position are the same component to React.
4. When a component is removed, or a different component type takes its position, React destroys its state and the state of everything inside it. A new wrapper tag is enough.
5. To keep state, keep the tree's structure the same between renders: put a conditional line before the component, such as `{showTip && <p>...</p>}`, instead of wrapping the component in a different tag.
6. Defining a component inside another one creates a new function on every render, so React sees a different type and resets its state each time.
7. To reset on purpose, give the component a `key` that changes when it should become a different one, such as `key={friend}`. The `key` becomes part of the position, and React builds new state and new DOM elements.
8. `key` is not only for lists, and keys only need to differ among the children of the same parent. Resetting from an Effect is the wrong tool: it renders twice and must be repeated in every nested component.
9. To keep a removed component's draft, lift it up into the parent, hide the component with CSS, save it in `localStorage`, or use `<Activity>`.
