- **Interview Question**: *When does state logic outgrow useState, and how does a reducer consolidate it?*

## Scope

Covered here:
- The docs' three steps to move from `useState` to `useReducer`: move from setting state to dispatching actions; write a reducer function; use the reducer from the component.
- The action: a plain JavaScript object, by convention with a string `type` that says what happened, and other fields with the minimal information the reducer needs.
- The reducer function: takes the current state and the action, returns the next state; declared outside the component; `switch (action.type)` by convention, if/else also fine; a `default` that throws `'Unknown action: ' + action.type`.
- `useReducer(reducer, initialState)` returns the current state and the `dispatch` function; calling `dispatch(action)` makes React call the reducer with the current state and that action, store the result, and render again.
- `useState` and `useReducer` are equivalent; what differs is where the update logic lives.
- Reducers must be pure: they run during rendering, Strict Mode calls them twice in development, and they update objects and arrays without mutation.
- Each action describes a single user interaction, even when it leads to several changes in the data; action types name what the user did, not how the state should change.
- Why a reducer helps: one place for the update logic, a log line in the reducer for every update, and a test of the reducer on its own, outside the component.
- Choosing between `useState` and `useReducer`: the docs' five points of comparison and their recommendation.
- The reducer's own Troubleshooting entries that this page can show: the old value after `dispatch`, a mutated state that does not update the screen, a field that becomes `undefined`, the whole state that becomes `undefined`.

## Start of the Lecture

**Opening Essence of the chapter**:
- The question of the lesson: when does state logic outgrow `useState`, and where does the logic go instead?
- Smallest code, two versions of one counter, with no project files:
  1. With `useState`: `const [count, setCount] = useState(0);` and `onClick={() => setCount(count + 1)}`. The rule "add one" sits inside the handler.
  2. With `useReducer`: `function reducer(count, action) { if (action.type === 'incremented') { return count + 1; } }`, `const [count, dispatch] = useReducer(reducer, 0);`, and `onClick={() => dispatch({ type: 'incremented' })}`. The handler says what happened; the rule "add one" sits in `reducer`.
  3. Both buttons show `0`, then `1` after one click by the user.
- Confusion to say out loud: *"Yes, it is the exact same thing!"* The docs: "You can always convert between `useState` and `useReducer` back and forth: they are equivalent!" The same state, the same page, the same re-render. What the two share: one state variable that React keeps between renders, changed by a function React gives back. The one difference: with `useState` every handler holds its own rule for the next state; with `useReducer` the handlers only report what the user did, and one function holds every rule.
- The docs' own frame, from the Intro: "Components with many state updates spread across many event handlers can get overwhelming. For these cases, you can consolidate all the state update logic outside your component in a single function, called a _reducer._"
- The docs' frame for the handlers: "Instead of telling React 'what to do' by setting state, you specify 'what the user just did' by dispatching 'actions' from your event handlers."
- Everyday image, offered once for the opening only: a waiter in a restaurant writes what the customer ordered on a slip and hands it to the kitchen; the waiter never cooks, and the kitchen alone knows how each dish is made. After the opening, the lecture uses React's words only: "slip", "waiter", and "kitchen" never stand for code. See Open Issues.
- Key idea: event handlers say what happened; the reducer says how the state changes in response; React connects the two with `dispatch`.
- What is at stake for the user: the cart shows a wrong number, such as `Milk: -1`, and with four handlers each holding its own rule, the developer must read all four to find which rule made it. The docs' Debugging point: "When you have a bug with `useState`, it can be difficult to tell _where_ the state was set incorrectly, and _why_." With a reducer, one log line inside it names every action.
- Where readers usually go wrong:
  1. They think `useReducer` is a new kind of state, or state shared by the whole app. It is one component's state, as with `useState`; sharing it is Lesson 29.
  2. They think `dispatch` changes the state at once. It asks React for the next render, as a setter does (Lesson 15).
  3. They put side effects, such as `alert`, inside the reducer, and see them run twice in development.
  4. They think every component should use a reducer. The docs: "You don't have to use reducers for everything: feel free to mix and match!"

**Theme**: a shopping cart whose four buttons each change the same array of items in their own way, with the four update rules sitting in four event handlers.

**Ways** (developers really choose between these for the same job, from the docs):
1. `useState`, with the update logic inside each event handler: fits when the updates are simple. The docs: "`useState` is very easy to read when the state updates are simple."
2. `useReducer`, with the handlers dispatching actions and one reducer holding the logic: fits when many handlers change the same state in different ways. The docs: "We recommend using a reducer if you often encounter bugs due to incorrect state updates in some component, and want to introduce more structure to its code."
3. Both in one component: "You can even `useState` and `useReducer` in the same component."
4. `useImmerReducer` from the Immer library, which lets the reducer write mutating code on a `draft`: named only, as Lesson 17 named Immer.
- Inside the reducer, two ways to branch: a `switch` statement, the docs' convention, or if/else. The docs: "The result is the same." Taught in Principle 2.

**Example page chosen for this lesson**: a shopping cart.
- Parts of the page: `<h1>Your cart</h1>`; a list with one row per item, showing the name and the quantity, such as `Bread: 2`, and three buttons on each row: `+`, `-`, `Delete`; under the list, a button `Empty cart`; when the cart has no items, the line `Your cart is empty.` in place of the list.
- Data above the component in `Cart.jsx`: `const initialCart = [{ id: 0, name: 'Apple', quantity: 1 }, { id: 1, name: 'Bread', quantity: 2 }, { id: 2, name: 'Milk', quantity: 1 }];`
- What the user does, and what each click changes:
  1. Clicks `+` on Bread: `Bread: 3`.
  2. Clicks `-` on Bread: `Bread: 1` after one click from `Bread: 2`; a second click removes the Bread row, because a quantity of zero means the item leaves the cart.
  3. Clicks `Delete` on Apple: the Apple row leaves the cart.
  4. Clicks `Empty cart`: every row leaves, and `Your cart is empty.` appears.
- State: one array, `cart`. At the start of the lesson it comes from `useState(initialCart)`; from Principle 3 it comes from `useReducer(cartReducer, initialCart)`.
- Handlers at the start of the lesson, each calling `setCart` with its own rule:
  1. `handleIncrease(id)`: `setCart(cart.map(item => item.id === id ? { ...item, quantity: item.quantity + 1 } : item));`
  2. `handleDecrease(id)`: `setCart(cart.map(item => item.id === id ? { ...item, quantity: item.quantity - 1 } : item).filter(item => item.quantity > 0));`
  3. `handleDelete(id)`: `setCart(cart.filter(item => item.id !== id));`
  4. `handleEmpty()`: `setCart([]);`
- Actions at the end of the lesson: `{ type: 'increased', id }`, `{ type: 'decreased', id }`, `{ type: 'deleted', id }`, `{ type: 'emptied' }`.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx` that renders `<Cart />`, `src/components/Cart.jsx`, and from Principle 5 `src/cartReducer.js`.
- Names follow the docs' own code where the docs have one: `dispatch`, `action`, `action.type`, `action.id`, a reducer named after its state as `tasksReducer` is, here `cartReducer`, past-tense action types as `'added'`, `'changed'`, `'deleted'`.

## Principles

### Principle 1: dispatch Sends What the User Did

- **Rule**: In a component with a reducer, an event handler does not compute the next state; it calls `dispatch` with an action object that says what the user just did, with the minimal information the reducer needs.
- **Move**: Side by side, because the handler with `setCart(...)` and the handler with `dispatch(...)` look alike, a function call inside the same handler, and they are NOT the same thing.
- **Opening Essence**:
  - Smallest code, two handlers for one plus button:
    1. `function handleIncrease(id) { setCart(cart.map(item => item.id === id ? { ...item, quantity: item.quantity + 1 } : item)); }`
    2. `function handleIncrease(id) { dispatch({ type: 'increased', id: id }); }`
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both lines are one call inside the handler. `setCart` receives the next state itself, worked out in the handler. `dispatch` receives a description of the click, and the next state is worked out somewhere else.
  - The docs: "Your event handlers currently specify _what to do_ by setting state." And: "So instead of 'setting `tasks`' via an event handler, you're dispatching an 'added/changed/deleted a task' action. This is more descriptive of the user's intent."
  - Everyday image for the word *dispatch*: to send something off to where it is handled, as a shop dispatches a parcel. The handler sends the action off; it does not handle it.
- **Root Distinction**:
  - Junior: "The handler is where the state changes, so the handler must say what the new cart is."
  - Senior: the handler only reports the event; one other function decides what the event does to the cart.
- **Simplest version**:
  - `dispatch({ type: 'increased', id: 1 })` for a click on `+` in the Bread row.
  - The action itself: `{ type: 'increased', id: 1 }`, a regular JavaScript object.
- **Words to teach**:
  - *action*: the object passed to `dispatch`. The docs: "It is a regular JavaScript object. You decide what to put in it, but generally it should contain the minimal information about _what happened_." Provided by our code, written in the handler. Needed at the first `dispatch` call.
  - *`type`*: the field that names what happened, by convention a string. The docs' Note: "By convention, it is common to give it a string `type` that describes what happened, and pass any additional information in other fields." Provided by our code. Needed when the reader asks how the reducer tells one click from another.
  - *dispatch, dispatching actions*: calling `dispatch` with an action. Provided by React, from `useReducer` in Principle 3. Needed in the first line of the principle, named here and supplied later.
  - Known: event handler, `onClick`, an arrow that passes `item.id`, Lesson 11. `setCart` with `map` and `{ ...item }`, Lessons 17 and 19.
  - Helper: none.
- **Side by side**:
  - "with `setCart(...)`" and "with `dispatch({ type: 'increased', id })`": NOT the same thing. The first puts the rule for the next cart in the handler; the second puts only the event in the handler.
  - "with `type: 'increased'`" and "with `type: 'set_quantity'`": NOT the same thing for the reader of the code. The docs' Challenge Solution: "action types should ideally describe 'what the user did' rather than 'how you want the state to change'. This makes it easier to later add more features." Both can produce the same cart.
  - "with `'added'`" and "with `'added_task'`": the exact same thing. The docs' Note: "The `type` is specific to a component, so in this example either `'added'` or `'added_task'` would be fine. Choose a name that says what happened!"
- **Surprises**: none.
- **Where did that come from?**:
  - `dispatch` in the handler: not written anywhere yet. The docs: "You will add the `dispatch` function itself in a later step." It comes from `useReducer` in Principle 3.
  - `id` in the action: the argument of `handleIncrease(id)`, passed by the arrow `() => handleIncrease(item.id)` on the row's `+` button, Lesson 11.
- **Real beginner mistake** (the docs' Challenge "Clear the input on sending a message"):
  1. A developer adds a Send button to a chat box.
  2. The developer reuses the action for typing: `dispatch({ type: 'edited_message', message: '' })`.
  3. The box empties, so the code seems right.
  4. The action now says "the user typed an empty message" when the user clicked Send.
  5. The docs' better version: a new action `sent_message`, handled in the reducer. "From the user's perspective, sending a message is a different action than editing the field."
- **Interview depth**:
  - "An action object can have any shape."
  - The reference: an action "can be a value of any type. By convention, an action is usually an object with a `type` property identifying it and, optionally, other properties with additional information."
  - The action types are local to the component: "The action type names are local to your component."
  - The docs' three handlers in `TaskApp` after Step 1: `handleAddTask(text)` is called when the user presses "Add", `handleChangeTask(task)` when the user toggles a task or presses "Save", `handleDeleteTask(taskId)` when the user presses "Delete".
- **React does**:
  - Page: nothing new; this step only rewrites the handlers, and the page runs again after Principle 3.
  - Console: nothing.
  - Elements panel: nothing.
- **Example step**:
  - `Cart.jsx`: the four handlers side by side, before and after. After: `handleIncrease(id)` dispatches `{ type: 'increased', id: id }`, `handleDecrease(id)` dispatches `{ type: 'decreased', id: id }`, `handleDelete(id)` dispatches `{ type: 'deleted', id: id }`, `handleEmpty()` dispatches `{ type: 'emptied' }`.
  - No `map`, `filter`, or `[]` is left in any handler.

### Principle 2: cartReducer Holds Every Rule for the Cart

- **Rule**: A reducer is a function, declared outside the component, that takes the current state and the action and returns the next state; one `case` for each action type, and a `default` that throws for a type it does not know.
- **Move**: Smallest code first, because the reducer is plain JavaScript and can be called by hand with no React at all. Everyday image for the word *reducer*, from the docs' DeepDive.
- **Opening Essence**:
  - Smallest code: `function counterReducer(count, action) { if (action.type === 'incremented') { return count + 1; } }`, then `counterReducer(0, { type: 'incremented' })` gives `1`, and `counterReducer(5, { type: 'incremented' })` gives `6`.
  - Key idea: the reducer only computes. It takes two inputs and returns one value; it does not touch the page, and React is not involved yet.
  - Everyday image for the name, from the docs' DeepDive: `[1, 2, 3, 4, 5].reduce((result, number) => result + number)` gives `15`. The function given to `reduce` "takes the _result so far_ and the _current item,_ then it returns the _next result._" A React reducer takes the state so far and the action, and returns the next state. "In this way, they accumulate actions over time into state." The docs: "Although reducers can 'reduce' the amount of code inside your component, they are actually named after the `reduce()` operation."
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* A `switch` on `action.type` and a chain of if/else give the same result. The docs: "The result is the same, but it can be easier to read switch statements at a glance." And: "If you're not yet comfortable with switch statements, using if/else is completely fine."
- **Root Distinction**:
  - Junior: "The update logic belongs to the component, so it goes inside the component."
  - Senior: the reducer takes the state as an argument, so it needs nothing from inside the component and can live outside it, even in another file.
- **Simplest version**:
  - The docs' three moves: declare the current state, `cart`, as the first argument; declare the `action` object as the second argument; return the next state.
  - `function cartReducer(cart, action) { switch (action.type) { case 'increased': { return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity + 1 } : item); } case 'decreased': { return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity - 1 } : item).filter(item => item.quantity > 0); } case 'deleted': { return cart.filter(item => item.id !== action.id); } case 'emptied': { return []; } default: { throw Error('Unknown action: ' + action.type); } } }`
- **Words to teach**:
  - *reducer, reducer function*: the docs: "A reducer function is where you will put your state logic. It takes two arguments, the current state and the action object, and it returns the next state." Provided by our code. Needed at the first line of the principle.
  - *current state, next state*: the state the reducer receives and the state it returns. The docs: "React will set the state to what you return from the reducer." Needed when the reader reads the two arguments.
  - *`switch`, `case`, `default`*: plain JavaScript, from MDN: `switch` compares one value, here `action.type`, with each `case` and runs the first that matches; `default` runs when none matches. Needed at the first `case`. The docs' advice: wrap each `case` in `{` and `}` "so that variables declared inside of different `case`s don't clash with each other", and end each `case` with a `return`.
  - *fall through*: the docs: "If you forget to `return`, the code will 'fall through' to the next `case`, which can lead to mistakes!" Needed in Real beginner mistake.
  - *`throw Error(...)`*: plain JavaScript, from MDN: stops the function and reports an error in the Console. The docs' reducers end with `throw Error('Unknown action: ' + action.type);`. Needed at `default`.
  - Known: `map` that replaces one item and `filter` that removes one, Lesson 19. `{ ...item, quantity: ... }`, Lesson 17. The ternary, Lesson 10. Pure function, Lesson 14.
  - Helper: `reduce()`, named in the image only, MDN wording `unconfirmed`. Calling `.filter` on the array that `.map` returns: plain JavaScript, no new word.
- **Side by side**:
  - "with `switch (action.type)`" and "with if/else on `action.type`": the exact same thing. The docs show `tasksReducer` both ways.
  - "the reducer inside `Cart`" and "the reducer below `Cart`, outside it": the exact same result. The docs: "Because the reducer function takes state (`tasks`) as an argument, you can **declare it outside of your component.** This decreases the indentation level and can make your code easier to read."
  - "`case 'decreased'` with `.filter(item => item.quantity > 0)`" and "without it": NOT the same cart. Without it, a row can show `Milk: 0`, then `Milk: -1`.
- **Surprises**:

    2. The Console shows `[]`. Exact printed form `unconfirmed`.
    3. The page still shows Apple, Bread, and Milk, because nothing gave the result to React. That is Principle 3.
    4. `initialCart` still holds three items, because the reducer returned a new array and changed nothing.
- **Where did that come from?**:
  - `cart` in `cartReducer`: the first parameter, named after the state, as the docs name it `tasks`. In Principle 3, React passes the current state into it.
  - `action` in `cartReducer`: the second parameter. In Principle 3, React passes the object that the handler gave to `dispatch`.

### Principle 3: useReducer Hands Back the Cart and dispatch

- **Rule**: `useReducer(cartReducer, initialCart)` takes the reducer and the initial state and returns the current state and the `dispatch` function; each `dispatch(action)` makes React call the reducer with the current state and that action, store what it returns, and render the component again.
- **Move**: Side by side, because the `useReducer` line takes the place of the `useState` line and gives back two values in the same shape. Then Steps for a surprise, for one click on `+`.
- **Opening Essence**:
  - Smallest code, one line against one line:
    1. `const [cart, setCart] = useState(initialCart);`
    2. `const [cart, dispatch] = useReducer(cartReducer, initialCart);`
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* The docs: "The `useReducer` Hook is similar to `useState`", and "you must pass it an initial state and it returns a stateful value and a way to set state (in this case, the dispatch function). But it's a little different." The docs join the two parts with a dash. What the two share: the initial state, the current state on the left, a function React gives back on the right. The one difference: `useReducer` also takes the reducer, and the function it gives back takes an action, not the next state.
  - The docs' Challenge "Implement `useReducer` from scratch" shows the sameness in code: `const [state, setState] = useState(initialState); function dispatch(action) { const nextState = reducer(state, action); setState(nextState); } return [state, dispatch];`
- **Root Distinction**:
  - Junior: "`dispatch` runs my reducer and changes `cart` right there in the handler."
  - Senior: `dispatch` hands the action to React; React calls the reducer and gives the new `cart` to the next render, while the running handler keeps the old `cart`.
- **Simplest version**:
  - `import { useReducer } from 'react';`
  - `const [cart, dispatch] = useReducer(cartReducer, initialCart);` in place of the `useState` line.
  - The handlers from Principle 1 and the reducer from Principle 2, unchanged.
- **Words to teach**:
  - *`useReducer`*: a React Hook. The docs: "The `useReducer` Hook takes two arguments: 1. A reducer function 2. An initial state. And it returns: 1. A stateful value 2. A dispatch function (to 'dispatch' user actions to the reducer)." Provided by React, imported from `'react'`. Needed at the line that replaces `useState`.
  - *`dispatch` function*: the reference: "The `dispatch` function returned by `useReducer` lets you update the state to a different value and trigger a re-render. You need to pass the action as the only argument to the `dispatch` function." "`dispatch` functions do not have a return value." Provided by React. Needed at the first click.
  - *initial state*: the second argument, here `initialCart`. The reference: "React saves the initial state once and ignores it on the next renders." Needed at the `useReducer` line.
  - Known: `useState`, Hook, `import { ... } from 'react'`, Lesson 12. Render and re-render, Lesson 13. Snapshot, Lesson 15. Queue and batching, Lesson 16. `Object.is` skip, Lesson 17.
  - Helper: none.
- **Side by side**:
  - "with `useState(initialCart)` and `setCart(next)`" and "with `useReducer(cartReducer, initialCart)` and `dispatch(action)`": the exact same page and the same cart after each click; the docs: "they are equivalent!" They differ only in where the rule lives.
  - "`setCart` receives the next cart" and "`dispatch` receives an action": NOT the same thing. Passing an action object to `setCart` would make the action the new `cart`.
- **Surprises**:
  - The user clicks `+` on Bread, and the row shows `Bread: 3`:
    1. React calls the arrow on the button, which calls `handleIncrease(1)`.
    2. `handleIncrease` calls `dispatch({ type: 'increased', id: 1 })`. The docs: "Actions are queued until the next render."
    3. The handler ends. `cart` in the running handler still has `Bread: 2`.
    4. React renders `Cart` again. It calls `cartReducer` with the current cart and the action. The reference: "React will pass the current state and the action to your reducer function. Your reducer will calculate and return the next state. React will store that next state, render your component with it, and update the UI."

  - A `console.log(cart)` right after `dispatch` in the handler prints the old cart. The reference: "Calling the `dispatch` function **does not change state in the running code**." The same snapshot as Lesson 15.
- **Where did that come from?**:
  - `cart` on the left of `useReducer`: the current state, given by React; on the first render, `initialCart`.
  - `dispatch` on the left of `useReducer`: the function React gives back; this is the `dispatch` that Principle 1 used before it existed.

- **Real beginner mistake** (the reference Troubleshooting, "I've dispatched an action, but logging gives me the old state value"):
  1. A developer writes `dispatch({ type: 'emptied' });` and then `console.log(cart.length);` in `handleEmpty`.
  2. The user clicks `Empty cart`.
  3. The Console shows `3`, and the page shows `Your cart is empty.` The `3`: from the reference's `// Still 42!` case, for this page `unconfirmed`.
  4. The developer thinks `dispatch` failed.
  5. The docs' way to see the next state in the handler: call the reducer by hand, `const nextCart = cartReducer(cart, action);`.
- **Interview depth**:
  - The reference Returns: "`useReducer` returns an array with exactly two values: 1. The current state. During the first render, it's set to `init(initialArg)` or `initialArg` (if there's no `init`). 2. The `dispatch` function."
  - The third argument, the initializer: `useReducer(reducer, username, createInitialState)` passes the function itself, so it runs only for the initial state. "Notice that you're passing `createInitialState`, which is the *function itself*, and not `createInitialState()`."

  - Caveats: "If the new value you provide is identical to the current `state`, as determined by an `Object.is` comparison, React will **skip re-rendering the component and its children.**" "React batches state updates."
  - Caveat: "`useReducer` is a Hook, so you can only call it **at the top level of your component** or your own Hooks." Lesson 38.

  - The reference: "`useReducer` is very similar to `useState`, but it lets you move the state update logic from event handlers into a single function outside of your component."

### Principle 4: An alert Inside cartReducer Pops Up Twice

- **Rule**: A reducer must be pure: the same state and action always give the same next state, with no side effects and no mutation, because React calls it during rendering and, in Strict Mode, twice in development.
- **Move**: Steps for a surprise, because the user clicks once and sees the pop-up twice, or sees the quantity jump.
- **Opening Essence**:
  - Smallest code: `case 'emptied': { alert('Cart emptied'); return []; }` in the reducer, and `<StrictMode>` in `main.jsx`. One click on `Empty cart`, two pop-ups.
  - Key idea, from the docs: "Similar to state updater functions, reducers run during rendering! (Actions are queued until the next render.) This means that reducers must be pure", and "same inputs always result in the same output." The docs join the two parts with a dash.
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* This is the purity rule of Lesson 14 and the updater rule of Lesson 16, for one more kind of function. The reference: "**Only component, initializer, and reducer functions need to be pure.** Event handlers don't need to be pure, so React will never call your event handlers twice."
  - What is at stake: a side effect in the reducer runs twice in development, and a mutation in the reducer changes the cart twice or not at all.
- **Root Distinction**:
  - Junior: "The reducer runs when the user clicks, so it is part of the click, like the handler."
  - Senior: the handler runs on the click; the reducer runs later, during rendering, maybe twice, so it may only compute.
- **Simplest version**:
  - Wrong: `alert` inside `case 'emptied'`.
  - Right: `alert('Cart emptied')` in `handleEmpty`, next to `dispatch({ type: 'emptied' })`; the reducer only returns `[]`.
- **Words to teach**:
  - No new word. Pure function, side effect, Strict Mode calls twice: Lesson 14. Running during rendering, the queue, `alert`: Lesson 16. Mutation, read-only, `Object.is`: Lesson 17.
  - The docs' list of what a reducer must not do: "They should not send requests, schedule timeouts, or perform any side effects (operations that impact things outside the component). They should update objects and arrays without mutations."
  - Helper: none.
- **Side by side**:
  - "with `alert` in `case 'emptied'`" and "with `alert` in `handleEmpty`": NOT the same thing. The docs' Solution: "it's important that you **don't** place the `alert` inside a reducer. The reducer should be a pure function--it should only calculate the next state. It should not 'do' anything, including displaying messages to the user. That should happen in the event handler."
  - "`return { ...item, quantity: item.quantity + 1 }`" and "`item.quantity = item.quantity + 1; return item;`" inside `map`: NOT the same thing. The first makes a new item; the second changes the item that the current state holds.
  - "with `<StrictMode>`" and "in production": NOT the same number of calls. The reference: "This is development-only behavior and does not affect production." "The result from one of the calls is ignored."
- **Surprises**:
  - The user clicks `Empty cart` once, and the pop-up appears twice:
    1. `handleEmpty` calls `dispatch({ type: 'emptied' })`.
    2. React renders `Cart` again and calls `cartReducer` with the action.
    3. `<StrictMode>` calls `cartReducer` a second time with the same state and action.
    4. Each call runs `alert('Cart emptied')`.
    5. The docs: "To help catch mistakes like this, React will call your reducers multiple times in Strict Mode. This is why, if you put an alert in a reducer, it fires twice."
  - The user clicks `+` once on Bread with a mutating `case 'increased'`, and the row may show `Bread: 4`:
    1. `case 'increased'` writes `item.quantity = item.quantity + 1` on the item from the current state.
    2. React calls the reducer twice with the same current state.
    3. Both calls add one to the same Bread object.
    4. The docs' version for an array: "Because React calls your reducer function twice, you'll see the todo was added twice, so you'll know that there is a mistake." Whether this page shows `Bread: 4`: `unconfirmed`.
  - The user clicks `Delete` with a mutating reducer that returns the same array, and the row stays:
    1. The reducer changes `cart` in place, such as with `splice`, and returns `cart`.
    2. React compares the next state with the current one by `Object.is` and finds the same array.
    3. The reference: "You mutated an existing `state` object and returned it, so React ignored the update."
- **Where did that come from?**:
  - The second pop-up: from `<StrictMode>` in `src/main.jsx`, Lesson 07, not from our code.
  - The second call of the reducer: Strict Mode, in development only. The reference: "In Strict Mode, React will **call your reducer and initializer twice** in order to help you find accidental impurities."
- **Real beginner mistake** (the docs' Challenge "Clear the input on sending a message", Solution):
  1. A developer wants a message to the user after a click.
  2. The developer writes `alert` in the reducer, next to the state logic, because "all the logic lives there".
  3. In development, the user sees the message twice.
  4. The fix: the `alert` goes in the event handler; the reducer only returns the next state.
- **Interview depth**:
  - The reference Pitfall: "State is read-only. Don't modify any objects or arrays in state." "Instead, always return new objects from your reducer."
  - Immer: `useImmerReducer` gives the reducer a `draft` that "is safe to mutate"; "Under the hood, Immer will create a copy of your state with the changes you made to the `draft`." Named only.
  - The syllabus card's point: purity is what lets the reducer be tested outside the DOM.
- **React does**:
  - Page, `alert` in the reducer: two pop-ups with `Cart emptied` for one click, in development. From the docs, for this page `unconfirmed`.
  - Page, mutating `case 'increased'`: `Bread: 4` after one click from `Bread: 2`: `unconfirmed`.
  - Page, mutation that returns the same array: no change on the screen. From the reference; for this page `unconfirmed`.
  - Console: no warning for an impure reducer. `unconfirmed`.
  - Elements panel: unchanged rows in the third case. `unconfirmed`.
- **Example step**:
  - `Cart.jsx`, as a short wrong try and its fix: `alert('Cart emptied')` placed in `case 'emptied'`, then moved to `handleEmpty`.
  - The final `cartReducer` keeps no `alert`, no mutation, and no other side effect.
- **Code names**: `alert('Cart emptied')`, `Cart emptied`, `case 'emptied'`, `handleEmpty`, `<StrictMode>`, `src/main.jsx`, `item.quantity = item.quantity + 1`, `splice`, `Object.is`, `Bread: 4`, `useImmerReducer`, `draft`

### Principle 5: One emptied Action Clears the Whole Cart

- **Rule**: Each action describes one user interaction, even when the interaction leads to several changes in the data; then a log in the reducer reads as the list of what the user did, and the reducer can be tested on its own.
- **Move**: Side by side, because one `'emptied'` action and one `'deleted'` action for each row give the same empty cart, and they are NOT the same thing.
- **Opening Essence**:
  - Smallest code, two `Empty cart` handlers:
    1. `dispatch({ type: 'emptied' });`
    2. `cart.forEach(item => dispatch({ type: 'deleted', id: item.id }));`
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both leave `Your cart is empty.` on the page. The first says what the user did: one click on `Empty cart`. The second says three deletes that the user never clicked.
  - The docs: "For example, if a user presses 'Reset' on a form with five fields managed by a reducer, it makes more sense to dispatch one `reset_form` action rather than five separate `set_field` actions. If you log every action in a reducer, that log should be clear enough for you to reconstruct what interactions or responses happened in what order."
- **Root Distinction**:
  - Junior: "An action is a change to the data, so a click that changes three things sends three actions."
  - Senior: an action is one thing the user did; the reducer turns it into as many changes as it needs.
- **Simplest version**:
  - `case 'decreased'` lowers the quantity and, at zero, removes the row: one click by the user, two changes in the data, one action.
  - `console.log(action)` as the first line of `cartReducer`.
  - `src/cartReducer.js` with `export default function cartReducer(cart, action) { ... }`, and `import cartReducer from '../cartReducer.js';` in `Cart.jsx`.

If each `action` is correct, you'll know that the mistake is in the reducer logic itself." Needed when the reader adds `console.log(action)`.
  - Known: `export default`, `import`, Lesson 05. `console.log`, Lesson 11. Separate concerns, Lesson 26.
  - Helper: `forEach`, only inside the counter-example handler, plain JavaScript; MDN wording `unconfirmed`. The writer may show the three dispatches as three lines instead.
- **Side by side**:

  - "with `case 'decreased'` removing the row at zero" and "with the handler dispatching `'decreased'` and then `'deleted'`": NOT the same thing. The first keeps the rule in the reducer and the log shows one click.

## Interview Points

- `useState` and `useReducer` are equivalent; a reducer moves the state update logic out of the event handlers into one function.
- Use a reducer when many event handlers change the same state in different ways, or when bugs from incorrect state updates keep coming back; `useState` stays the better fit for simple updates, and both can live in one component.
- The three steps: dispatch actions from the handlers; write a reducer that returns the next state for a given state and action; replace `useState` with `useReducer`.
- An action is a plain object, by convention with a `type` that says what the user did and the minimal extra information.
- The reducer takes the current state and the action and returns the next state; a `switch` on `action.type` is the convention, and a `default` that throws catches unknown types.
- `useReducer(reducer, initialState)` returns the current state and `dispatch`; React calls the reducer during the next render and stores what it returns.
- `dispatch` does not change the state in the running code; the handler still reads the old value.
- Reducers must be pure: no side effects, no mutation; Strict Mode calls them twice in development to show impurities.
- Each action describes one user interaction, even if it leads to several changes in the data, so a log of the actions reads as what the user did.
- A reducer does not depend on the component, so it can be exported and tested on its own.
- The name comes from the array method `reduce()`: the state so far plus the action gives the next state.
