## Start of the Lecture

**Opening Essence of the chapter**:
- No short code shows the idea with a surprise before `fetch` is taught, so the idea comes first in plain words, from a real screen, as opening-essence asks.
- The real screen: a team page in a work app, with one button per person, `Alice`, `Bob`, and `Taylor`. Clicking a name shows that person's bio under the buttons. The bio is not in our code; the page asks the server for it.
- Key idea the reader must remember: the server answers in its own order, not in the order the user clicked. The docs: "network responses may arrive in a different order than you sent them."
- What is at stake for the user:
  1. The user clicks `Bob`, then `Taylor`, quickly.
  2. Taylor's bio comes back first, and the page shows it.
  3. Bob's bio comes back later, and replaces it.
  4. The page now shows Bob's bio, while the user asked for Taylor. Nothing on the page says it is wrong.
- Where readers usually go wrong:
  1. They think the last click gives the last answer.
  2. They write the fetch with no cleanup, as in the docs' `🔴 Avoid: Fetching without cleanup logic`.
  3. They trust `fetch` to fail on a server error; it does not.
  4. They add `AbortController` and then show its `AbortError` to the user as an error.
- Confusion to say out loud, for the two fixes of Principle 3 and Principle 4: *"It may look the same, or work the same at first, but it is NOT the same thing!"* With the `ignore` flag and with `controller.abort()`, the page shows the same bio. With the flag, the old request still runs to the end and its answer is dropped; with `abort()`, the browser stops the old request.

**Theme**: a team page where a click on a name must show that person's bio from the server, and only that person's bio.

**Ways** (what the docs give for loading data in a client component, and when each fits):
1. `fetch` in an Effect, with the `ignore` flag in the cleanup: the docs' main code, for any promise, including one that cannot be stopped.
2. `fetch` in an Effect, with `AbortController` in the cleanup: when the request is a `fetch`, so the browser can also stop the request that is no longer needed.
3. The data fetching of a framework, or a client-side cache library such as TanStack Query or useSWR: the docs recommend these for real apps, because they also cache, avoid network waterfalls, and work on the server. Named only, Lesson 60.
4. `use(promise)` with Suspense, and Server Components: Lessons 71 and 101. Named only.

**Example page chosen for this lesson**: a team page that shows one person's bio.
- Parts of the page:

  2. Under them, one line: the bio of the person chosen, `Loading...` while it loads, or an error line.
- What the user does, and what each click changes:
  1. The page opens on Alice: `Loading...`, then `This is Alice’s bio.`
  2. Clicks `Bob`: `Loading...` for two seconds, then `This is Bob’s bio.`
  3. Clicks `Bob`, then `Taylor` at once: the page must end on Taylor's bio.
- The server for the example, the same answers as the docs' hidden `api.js`: `'This is ' + person + '’s bio.'`; Bob answers after 2000 ms and the others after 200 ms. In the lecture, the server is a URL, `/api/bio/Alice`, that answers with JSON `{ "bio": "This is Alice’s bio." }`. The lab supplies these answers.
- At the start of the lesson:

## Principles

### Principle 1: fetch Inside useEffect Loads the Bio

- **Rule**: When a component must show data from the server for the props it has, it calls `fetch` inside `useEffect`, lists those props in the dependency array, and sets state when the answer arrives; while the state is still `null`, the JSX shows a loading line.
- **Move**: Smallest code first, because `fetch`, the promise, and `.then` are new, and each needs its line of code before the example page uses it.
- **Opening Essence**:
  - Smallest code, three lines: `fetch('/api/bio/Alice')`, `.then(response => response.json())`, `.then(data => console.log(data.bio))`. The Console prints `This is Alice’s bio.` `unconfirmed`, a lab check.
  - Key idea: `fetch` does not give the bio back on the same line. It gives a promise, and the function in `.then` runs later, when the server answers.
  - What is at stake: the bio arrives after React has already put the page on the screen, so the page needs a line for the time in between, `Loading...`.
  - Why an Effect, the docs: the main reason to fetch is not a click; "While this component is visible, you want to keep `results` synchronized with data from the network". Here, the bio must match `person` while `Bio` is on the screen.
- **Root Distinction**:
  - Junior: "I call `fetch`, so the next line has the data."
  - Senior: `fetch` only sends the request; the data arrives later, in `.then`, and the component must show something until then.
- **Simplest version**:
  - `useEffect(() => { fetch('/api/bio/' + person).then(response => response.json()).then(data => setBio(data.bio)); }, [person]);`
  - `return <p>{bio ?? 'Loading...'}</p>;`
- **Words to teach**:
  - *server, request, response*: the page sends a request to a URL on the server, and the server sends back a response. Everyday web words. Needed at the first `fetch`.
  - *`fetch(url)`*: a browser function that sends a request and returns a promise. Provided by the browser. Needed at the first line of code.
  - *promise*: an object that stands for a value that is not there yet. MDN: "The **`Promise`** object represents the eventual completion (or failure) of an asynchronous operation and its resulting value." Provided by JavaScript. Needed at the same moment. `unconfirmed`: the MDN sentence was not opened in the corpus; quote it only after the lab step reads MDN, or say it in plain words.
  - *`.then(fn)`*: gives the promise a function to call with the value when it arrives. Provided by JavaScript. Needed at the same moment.
  - *`response.json()`*: reads the body of the response as JSON and returns another promise with the JavaScript object. Provided by the browser. Needed at the second `.then`.
  - *JSON*: the text format the server uses, such as `{ "bio": "This is Alice’s bio." }`. Needed at the same moment.
  - *loading state*: what the component shows before the data arrives. Here, `bio` is `null`, and `bio ?? 'Loading...'` shows `Loading...`. Needed when the reader asks what the page shows during the wait.
  - Known: `useEffect`, the dependency array, Lesson 32. Props, Lesson 08. `useState`, Lesson 12.
  - Helper: `??`, one line at its first use: it gives the right side when the left side is `null` or `undefined`.
- **Side by side**:
  - "with `fetch` in the component body" and "with `fetch` inside `useEffect`": NOT the same thing. The first sends a request during every render, and `setBio` asks for another render, so the requests never stop; the second sends a request after the commit, and again only when `person` changes.
  - "with `[person]`" and "with `[]`": NOT the same thing. With `[]`, a click on `Bob` changes `person` but the Effect does not run again, so the page keeps Alice's bio. The linter reports `person` as missing. `unconfirmed`, a lab check, and the exact lint text is `unconfirmed`.
- **Surprises**:
  - With `fetch` in the component body, the requests never stop:
    1. React calls `Bio`; the body calls `fetch`.
    2. The answer arrives; `setBio` sets the bio and asks for a render.
    3. React calls `Bio` again; the body calls `fetch` again.
    4. Each answer starts the next request. The page shows the bio, and the requests go on forever. `unconfirmed`, a lab check. Whether React stops the loop because `setBio` gets the same string is `unconfirmed`: `Object.is` on equal strings may let React skip the render after the second answer. The lab must say which.
  - In development, the page sends two requests for Alice when it opens:
    1. React mounts `Bio` and runs the setup: request one.
    2. Strict Mode runs the cleanup and the setup again: request two. Lesson 32.
    3. The docs: "**In development, you will see two fetches in the Network tab.** There is nothing wrong with that." "**In production, there will only be one request.**"
- **Where did that come from?**:
  - `response` in the first `.then`: the browser creates it when the server answers and passes it to the function.
  - `data` in the second `.then`: `response.json()` turns the JSON text into an object and passes it on.
  - `data.bio`: the name `bio` comes from the server's JSON, not from our state.
- **Real beginner mistake**:
  1. A developer writes `const data = fetch('/api/bio/Alice');` and puts `data.bio` in the JSX.
  2. `data` is a promise, not the bio.
  3. `data.bio` is `undefined`, so the line is empty. `unconfirmed`, a lab check; keep it in Interview depth if the lab does not run it.
- **Interview depth**:
  - The docs: "If your Effect fetches something, the cleanup function should either abort the fetch or ignore its result". Principles 3 and 4.
  - The `async` and `await` version from the `useEffect` reference: an `async function startFetching()` inside the Effect, called at once; "you still need to provide a cleanup function". The setup itself is not `async`, because the setup must return a cleanup function or nothing, and an `async` function returns a promise. The exact React warning for an `async` setup is `unconfirmed`.
  - Effects do not run on the server: "the initial server-rendered HTML will only include a loading state with no data." Lesson 102.
  - Fetching in Effects "makes it easy to create "network waterfalls"" and usually means no cache: "if the component unmounts and then mounts again, it would have to fetch the data again."
- **React does**:
  - Page: `Loading...`, then `This is Alice’s bio.` `unconfirmed`, a lab check.
  - Network tab in development: two requests to `/api/bio/Alice`; in production, one. From the docs.
  - Console: nothing from React. `unconfirmed`.
- **Example step**:
  - `Bio.jsx`: `import { useState, useEffect } from 'react';`, the Effect with `fetch`, `setBio(data.bio)`, and `[person]`; `setBio(null)` at the top of the setup, so the page shows `Loading...` again after each click. `App.jsx` unchanged.
- **Code names**: `Bio.jsx`, `Bio`, `person`, `bio`, `setBio`, `fetch('/api/bio/' + person)`, `/api/bio/Alice`, `response`, `response.json()`, `data`, `data.bio`, `.then`, `'Loading...'`, `bio ?? 'Loading...'`, `setBio(null)`, `[person]`, `This is Alice’s bio.`, `This is Bob’s bio.`

### Principle 2: response.ok Turns a Server Error into the Error Line

- **Rule**: `fetch` fails only when the request cannot reach the server; when the server answers with an error status such as `500`, the promise succeeds, so the code checks `response.ok`, throws an error when it is `false`, and shows the error line from `.catch`.
- **Move**: Side by side, because the two versions, "with `response.ok`" and "without `response.ok`", look almost the same and give the user two different pages when the server fails.
- **Opening Essence**:
  - Smallest code: `.then(response => { if (!response.ok) { throw new Error('Status ' + response.status); } return response.json(); })` and `.catch(err => setError(err));`
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* A server error and a missing network look alike to the user, both mean no bio, but `fetch` treats them differently. MDN: "A `fetch()` promise only rejects when the request fails, for example, because of a badly-formed request URL or a network error." "A `fetch()` promise _does not_ reject if the server responds with HTTP status codes that indicate errors (`404`, `504`, etc.)."
  - What is at stake for the user: without the check, the page shows `Loading...` forever when the server fails, and the user waits for nothing.
- **Root Distinction**:
  - Junior: "If the server has a problem, `fetch` fails and `.catch` runs."
  - Senior: `fetch` succeeds whenever the server answers; the code must read `response.ok` and turn a bad status into an error.
- **Simplest version**:
  - `const [error, setError] = useState(null);`
  - In the setup: `setError(null);` next to `setBio(null);`
  - The chain: the `response.ok` check, then `.then(data => setBio(data.bio))`, then `.catch(err => setError(err))`.
  - The JSX: `if (error) return <p>Could not load the bio.</p>;` before `return <p>{bio ?? 'Loading...'}</p>;`
- **Words to teach**:
  - *`response.ok`*: `true` when the status is from `200` to `299`. Provided by the browser. Needed when the server answers `500`.
  - *`response.status`*: the number the server sends, such as `200`, `404`, or `500`. Needed at the same moment.
  - *`throw new Error(message)`*: stops the function and makes the promise fail, so the next `.then` is skipped and `.catch` runs. Provided by JavaScript.
  - *`.catch(fn)`*: gives the promise a function to call when it fails. Provided by JavaScript.
  - *error state*: a second state variable, `error`, that the JSX checks first.
  - Known: early `return` in a component, Lesson 21. `useState`, Lesson 12.
  - Helper: none.
- **Side by side**:
  - "with the `response.ok` check" and "without the `response.ok` check", when the server answers `500` with the JSON `{ "message": "Server error" }`: NOT the same thing. ### Principle 3: The ignore Flag Drops Bob's Late Answer

- **Rule**: When the user clicks a new name before the old answer arrives, the old answer can arrive last and replace the new bio; the cleanup sets `ignore` to `true`, and the old setup only sets state when its own `ignore` is still `false`.
- **Move**: Steps for a surprise, because the wrong bio appears with no error, and only the order of events explains it.
- **Opening Essence**:
  - The real screen, the user's two clicks: `Bob`, then `Taylor`, within two seconds.
  - Key idea, the docs: "network responses may arrive in a different order than you sent them." The docs' name: "This is called a "race condition": two different requests "raced" against each other and came in a different order than you expected."
  - What is at stake: the page shows `This is Bob’s bio.` while the user chose Taylor, and nothing tells the user it is wrong.
  - Smallest code of the fix, the docs: `let ignore = false;` at the top of the setup, `if (!ignore) { setBio(result); }` in `.then`, and `return () => { ignore = true; };`
- **Root Distinction**:
  - Junior: "The last click sends the last request, so its answer arrives last."
  - Senior: each request takes its own time; the code must say which answer still counts, and the cleanup marks every older one as not counting.
- **Simplest version**:
  - The docs' `useEffect` reference: `let ignore = false; setBio(null); fetchBio(person).then(result => { if (!ignore) { setBio(result); } }); return () => { ignore = true; };` with `[person]`. In the lecture, with `fetch` instead of `fetchBio`.
- **Words to teach**:
  - *race condition*: the docs' sentence above. A computer science term the docs use. Needed when the wrong bio appears.
  - *stale response*: the docs' words, "ignore stale responses": an answer to a request that the page no longer needs.
  - *the `ignore` flag*: a local variable of one Effect run; the cleanup of that run sets it to `true`. The docs: "Note the `ignore` variable which is initialized to `false`, and is set to `true` during cleanup."
  - Known: the cleanup runs before the next setup, Lesson 32. Each render keeps its own values, Lesson 15: each Effect run has its own `ignore`.
  - Helper: none.
- **Side by side**:
  - "with the `ignore` flag" and "without a cleanup": the same page when the user clicks once and waits; NOT the same thing when the user clicks `Bob` and then `Taylor`. Without the cleanup, Bob's late answer replaces Taylor's bio; with it, Bob's answer is dropped.
- **Surprises**:
  - Without a cleanup, the page ends on Bob's bio after the user clicked Taylor:
    1. The user clicks `Bob`. `person` becomes `'Bob'`; the Effect sends request B, which the server answers after 2000 ms. The page shows `Loading...`.
    2. Half a second later, the user clicks `Taylor`. The Effect sends request T, answered after 200 ms.
    3. Answer T arrives first; `setBio` shows `This is Taylor’s bio.`
    4. Answer B arrives later; its `.then` still runs and calls `setBio` with Bob's bio.
    5. The page shows `This is Bob’s bio.` under the buttons, while `person` is `'Taylor'`. `unconfirmed`, a lab check.
  - With the `ignore` flag:
    1. Click `Bob`: the setup of the Bob run sends request B, with its own `ignore` set to `false`.
    2. Click `Taylor`: React runs the cleanup of the Bob run first, so the Bob run's `ignore` becomes `true`; then the setup of the Taylor run sends request T.
    3. Answer T arrives; the Taylor run's `ignore` is `false`; the page shows Taylor's bio.
    4. Answer B arrives; the Bob run's `ignore` is `true`; `setBio` is skipped.
    5. The page stays on `This is Taylor’s bio.` `unconfirmed`, a lab check.
    6. The docs, for `'Alice'` and `'Bob'`: "cleanup ensures that the `'Alice'` response is ignored even if it arrives after `'Bob'`."
- **Where did that come from?**:
  - Which `ignore` the cleanup changes: the cleanup function is created inside the same setup run, so it sees that run's `ignore`, not the next one's. Lesson 32, Principle 3, for `intervalId`.
- **Real beginner mistake** (the bank row's friction and the docs' `🔴 Avoid: Fetching without cleanup logic`):
  1. A developer writes the fetch Effect with `[person]` and no cleanup.
  2. On a fast network, every answer arrives in order, and the page looks right.
  3. On a slow phone, a user clicks two names quickly.
  4. The page shows the first person's details under the second person's name.
  5. The bug cannot be seen on the developer's machine, and appears only for some users.
- **Interview depth**:
  - The docs' `SearchResults`: the user types `"hello"` fast; "the `"hell"` response may arrive *after* the `"hello"` response", and the page shows "the wrong search results". The same fix: "all responses except the last requested one will be ignored."
  - The `ignore` flag works for any promise, not only `fetch`, such as the docs' `fetchBio`.
  - In development, the first request of the Strict Mode setup is ignored the same way: "the first Effect will immediately get cleaned up so its copy of the `ignore` variable will be set to `true`."
  - When the user leaves the page, the cleanup runs one final time, so a late answer does not set state of a component that is gone. React 18 removed the warning about this: "No warning about `setState` on unmounted components". The card's message "Can't perform a React state update on an unmounted component" does not appear in React 19. `unconfirmed`, a lab check.
- **React does**:
  - Page without cleanup: ends on `This is Bob’s bio.` after `Bob`, then `Taylor`. With the flag: ends on `This is Taylor’s bio.` `unconfirmed`, a lab check.
  - Network tab: both requests run to the end with the flag. `unconfirmed`, a lab check.
  - Console: nothing from React. `unconfirmed`.
- **Example step**:
  - `Bio.jsx`: `let ignore = false;`, `if (!ignore)` before `setBio` and before `setError`, and `return () => { ignore = true; };`

### Principle 4: AbortController Stops Bob's Request

- **Rule**: With `fetch`, the cleanup can stop the old request: the setup creates an `AbortController`, passes `controller.signal` to `fetch`, and the cleanup calls `controller.abort()`; the stopped `fetch` fails with an `AbortError`, which `.catch` must skip, because it is not an error for the user.
- **Move**: Side by side, because the `ignore` flag and `controller.abort()` give the same page and are NOT the same thing in the network.
- **Opening Essence**:
  - Smallest code, MDN: `const controller = new AbortController();`, `fetch(url, { signal: controller.signal })`, and later `controller.abort();`
  - MDN: `AbortController` is "a controller object that allows you to abort one or more Web requests as and when desired." "When `abort()` is called, the `fetch()` promise rejects with a `DOMException` named `AbortError`."
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* With the `ignore` flag, Bob's request runs to the end and its answer is dropped; with `controller.abort()`, the browser stops Bob's request, and no answer comes.
  - What is at stake: the abort itself makes the promise fail, so a `.catch` that shows every error puts `Could not load the bio.` on the page every time the user clicks a new name, and in development on the first load.
- **Root Distinction**:
  - Junior: "Every error that reaches `.catch` is a problem to show."
  - Senior: an `AbortError` is our own cleanup at work; only other errors are for the user.
- **Simplest version**:
  - In the setup: `const controller = new AbortController();`
  - `fetch('/api/bio/' + person, { signal: controller.signal })`
  - `.catch(err => { if (err.name === 'AbortError') return; setError(err); })`
  - The cleanup: `return () => controller.abort();`
- **Words to teach**:
  - *`AbortController`*: a browser object that can stop a `fetch`. Provided by the browser. Needed when the reader asks whether Bob's request can be stopped, not only ignored.
  - *`controller.signal`*: the object `fetch` listens to. MDN: it "can be used to communicate with, or to abort, an asynchronous operation." Passed in the second argument of `fetch`, `{ signal: controller.signal }`.
  - *`controller.abort()`*: stops the request. MDN: it "aborts an asynchronous operation before it has completed. This is able to abort fetch requests, consumption of any response bodies, and streams."
  - *`AbortError`*: the name of the error the stopped `fetch` fails with, `err.name`. MDN.
  - *Network tab*: the browser tab that lists every request. Name only.
  - Known: cleanup, Lesson 32. `.catch`, Principle 2. Each Effect run has its own variables, Lesson 15.
  - Helper: `DOMException`, name only.
- **Side by side**:
  - "with the `ignore` flag" and "with `controller.abort()`": the same page; NOT the same thing in the Network tab. With the flag, request B finishes; with `abort()`, request B is stopped and shows as canceled. The Network tab label is `unconfirmed`.
  - "with `if (err.name === 'AbortError') return;`" and "without it": NOT the same thing. Without it, the page shows `Could not load the bio.` after a click on a new name, even after the new bio loads, because the error line comes first in the JSX. `unconfirmed`, a lab check.
- **Surprises**:
  - Without the `AbortError` check, the page opens on the error line in development:
    1. React mounts `Bio` and runs the setup: controller A, request A for Alice. `setError(null)`.
    2. Strict Mode runs the cleanup: `controller.abort()` for A.
    3. Strict Mode runs the setup again: controller B, request B for Alice, `setError(null)`.
    4. Request A's promise fails with `AbortError`, after the second setup, and its `.catch` calls `setError(err)`.
    5. Request B's answer arrives and sets the bio, but `error` is not `null`.
    6. The page shows `Could not load the bio.` `unconfirmed`, a lab check, both the order of steps 3 and 4 and the final page.
  - With the check, in production, a click on `Bob` then `Taylor` stops request B; the page ends on Taylor's bio. `unconfirmed`, a lab check.
- **Where did that come from?**:
  - `controller` in the cleanup: the cleanup is created in the same setup run, so it stops that run's request only.
  - `err.name` equal to `'AbortError'`: set by the browser on the `DOMException` when the signal aborts. MDN. The `err.message` text, such as `signal is aborted without reason`, is `unconfirmed`, a lab check.
- **Real beginner mistake**:
  1. A developer replaces the `ignore` flag with `AbortController`, as the card suggests.
  2. The developer keeps `.catch(err => setError(err))`.
  3. Each click on a new name stops the old request, and the stopped request reports an `AbortError`.
  4. The page shows `Could not load the bio.` after almost every click. `unconfirmed`, a lab check.
  5. The fix: skip the `AbortError` in `.catch`.
- **Interview depth**:
  - The docs leave the choice open: "abort the fetch or ignore its result". `abort()` also saves the network and the server work for a request nobody needs; the `ignore` flag works for promises that cannot be stopped.
  - "You can't "undo" a network request that already happened": `abort()` stops the browser from waiting and reading, but the server may already have received the request. For a purchase this matters, which is why a purchase is not an Effect, Lesson 32.
  - MDN: "An `AbortSignal` can only be used once." That is why the setup creates a new controller on every run.
  - When the user leaves the page, the cleanup stops the request that was still loading. With the docs' Strict Mode setup, the Network tab shows the first request canceled. `unconfirmed`, a lab check.
  - For real apps, the docs recommend a framework or a client-side cache, "TanStack Query, useSWR, and React Router 6.4+", which also cache and deduplicate: Lesson 60. Or a custom Hook such as `useData`: Lesson 39.
- **React does**:
  - Page: with the check, the same pages as Principle 3; without it, `Could not load the bio.` `unconfirmed`, a lab check.
  - Network tab in development: two requests to `/api/bio/Alice`, the first canceled. `unconfirmed`.
  - Console: nothing from React. Chrome may print nothing for an aborted request. `unconfirmed`, a lab check.
- **Example step**:
  - `Bio.jsx`: the `ignore` flag replaced by `controller`; `{ signal: controller.signal }`; the `AbortError` check in `.catch`; `return () => controller.abort();`. This is the final `Bio`.

## Interview Points

- Fetching for the data a component shows is an Effect, because the data must match the props while the component is on the screen, not because of a click; the props it reads go in the dependency array, such as `[person]`.
- `fetch` returns a promise; the data arrives later in `.then`, so the component shows a loading state until then, such as `bio` at `null` and `Loading...`.
- `fetch` only fails when the request cannot reach the server; a `404` or `500` must be caught with `response.ok`, thrown as an error, and shown from `.catch`.
- A screen fetches in three states: loading, error, and data; each new request resets the old bio and the old error.
- Answers can arrive in a different order than the requests were sent; without a cleanup, an old answer can replace the new data, which is a race condition.
- The cleanup fixes it in one of two ways: an `ignore` flag that drops the old answer, or an `AbortController` whose `abort()` stops the old request; with `abort()`, `.catch` skips the `AbortError`.
- In development, Strict Mode sends two requests on mount, and the cleanup handles the first one; in production there is one.
- React 18 removed the warning about setting state on an unmounted component; the cleanup still matters, because it stops wrong data and wasted requests.
- For real apps, the docs recommend a framework's data fetching or a client-side cache such as TanStack Query or useSWR, which add caching and avoid network waterfalls.
