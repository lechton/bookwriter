## Scope

Covered here:
- The plain JavaScript way: commands that change each part of the page after each event, and the bug when one command is forgotten.
- Step 1 of react.dev: list every visual state the component can be in, and mock each one with a `status` prop before any logic.
- Step 2: find what changes the state, human inputs such as typing and clicking, and computer inputs such as a reply arriving.
- Steps 3 and 4: keep the current visual state in one `status` string, not in several true or false values, and drop state that can be computed.
- Step 5: event handlers only set the next state. The JSX describes each state once, and React makes the page match.
- *State machine* as a name only: a thing that is in exactly one of a few states at a time.

## Start of the Lecture

**Simplest version of the chapter's idea**:
- One state, one button, three looks.
- `const [status, setStatus] = useState('ready');`
- `<button onClick={() => setStatus('sending')}>{status === 'sending' ? 'Sending...' : 'Send'}</button>`
- What the reader sees: the button says `Send`. After the click it says `Sending...`.
- The handler never touches the button's text. It only changes `status`. The JSX already says what the button shows for each value.
- Everyday picture for *one visual state at a time*: a parcel tracker on a shop website. The steps are Ordered, Shipped, Out for delivery, Delivered. Exactly one step is lit. Nobody ever sees Out for delivery and Delivered lit together.
- Everyday picture for *imperative against declarative*, from `reacting-to-input-with-state.md`: telling a driver every turn, against telling a taxi driver the address. Lesson 01 already used the picture of an empire giving orders for the same contrast. The writer picks one and keeps it.

**The real page problem**:
1. A newsletter box asks for an email and has a `Sign up` button.
2. After the click, it shows `Sending...` and turns the button off.
3. After a moment, the reply comes. The page shows either an error or a thank-you line.
4. The user can fix the email after an error and try again.
5. In plain JavaScript, every event needs commands for every part of the page. The success branch forgets to clear the old error, and the page shows the error and the thank-you line together.

**Example page chosen for this lesson**: the newsletter sign-up box at the bottom of a news site.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx` rendering `<NewsletterForm />`, `src/components/NewsletterForm.jsx`. For Principle 1 only: a plain page `plain/index.html` with `plain/signup.js`.
- Final parts of the page: `<h2>Get our weekly newsletter</h2>`, an email box, a `Sign up` button, a `Sending...` line, the error line `This email is already signed up.`, and the thank-you line `Thanks! You are signed up.` that replaces the form.
- The fake reply: `setTimeout` waits 1500 milliseconds. The email `john@mail.com` is already on the list, so it gets the error. Any other email gets the thank-you line.

**Why this page**:
1. Everyone has seen a newsletter box. An email box and one button need no explanation.
2. It has all five visual states of react.dev with no extra parts: empty, typing, sending, error, success.
3. It has both kinds of input: the user types and clicks, and the reply arrives by itself.
4. The broken thing is big: two opposite messages on screen at once.
5. Actions are typing and clicking.
6. Outside code is small. `setTimeout` is known from Lesson 15, the controlled box from Lesson 20, `onSubmit` and `e.preventDefault()` from Lesson 11, `disabled={...}` from Lesson 03. The fake reply needs only an `if` inside the timer, no promise.
7. The plain JavaScript version uses only `getElementById` and `textContent`, known from Lesson 01, `addEventListener`, known from Lesson 04, and two helper properties, `.disabled` and `.value`.

## Principles

### Principle 1: Commands Must Cover Every Change, So One Forgotten Command Breaks the Page

- **Rule**: When a page has several looks, plain JavaScript must write a command for every part of the page after every event. One forgotten command leaves an old part on screen. React instead describes each look once.
- **Simplest version**:
  - Plain: `button.textContent = 'Sending...';` inside a click listener, and later `button.textContent = 'Send';`.
  - React: `{status === 'sending' ? 'Sending...' : 'Send'}`, from the start of the lecture.
  - Everyday picture: telling a driver every turn. Miss one turn and you end up in the wrong place. Source: `reacting-to-input-with-state.md`, "And if you get the directions wrong, you end up in the wrong place!"
- **Words to teach**:
  - *Visual state*: one look of the component that the user can see, such as sending or error. Needed at the moment the bug shows two looks mixed together.
  - Known: imperative and declarative, `getElementById`, `textContent`, Lesson 01. `addEventListener`, Lesson 04. `setTimeout`, Lesson 15. `e.preventDefault()`, Lesson 11.
  - Helper: `button.disabled = true`, the DOM property behind the `disabled` attribute of Lesson 03. `box.value`, the text in the box. Half a sentence each.
- **Surprises and their steps**:
  - Question: "The second try worked. Why does the page still say the email is already signed up?"
    1. The user types `john@mail.com` and clicks `Sign up`.
    2. The listener turns the button off and writes `Sending...`.
    3. After 1500 milliseconds, the timer clears `Sending...`, turns the button on, and writes `This email is already signed up.` into the error line.
    4. The user changes the email to `mary@mail.com` and clicks `Sign up` again.
    5. The listener turns the button off and writes `Sending...`. No line clears the error.
    6. The timer writes `Thanks! You are signed up.` into the thank-you line. No line clears the error.
    7. Both lines now stand on the page together.
  - Question: "Why is this not a one-off slip?"
    1. Each event must say what happens to every part: box, button, sending line, error line, thank-you line.
    2. Five parts and four events already make many commands.
    3. A new part, such as a second error, needs new commands in every event.
    Source: "Adding a new UI element or a new interaction would require carefully checking all existing code to make sure you haven't introduced a bug (for example, forgetting to show or hide something)."
- **Look-alikes**:
  - `button.disabled = true` in plain JavaScript and `disabled={status === 'submitting'}` in JSX: both end with a button that is off, but they are NOT the same. The first is a command run once, at one moment. The second is a description React reads on every render. They differ when a new event arrives: the command must be undone by another command, the description is simply read again.
  - The bug of this lesson and the cart bug of Lesson 01: the same cause, a forgotten command. Lesson 01 had one value in two places. Here one page has several looks, and the forgotten command belongs to a change from one look to another.
- **Where did that come from?**:
  - The old error line on the success screen, with no line that writes it again: the browser keeps it.
    1. The first try wrote the error text into the paragraph.
    2. The browser keeps that text until a command changes it.
    3. No command in the success branch changes it.
- **Real beginner mistake** (the syllabus card's friction, cut to one email box):
  1. The developer writes the listener for `Sign up`: button off, `Sending...` on, then the timer.
  2. In the timer, the error branch writes the error line, and the success branch writes the thank-you line.
  3. They test once with a new email, and it works.
  4. A real user first types an email that is already signed up and sees the error.
  5. The user fixes the email and tries again.
  6. The page shows `This email is already signed up.` and `Thanks! You are signed up.` together.
  7. The developer adds `errorText.textContent = '';` to the success branch, and must remember it in every future branch.
- **Interview depth**:
  - react.dev: "Manipulating the UI imperatively works well enough for isolated examples, but it gets exponentially more difficult to manage in more complex systems."
  - React's way: "you don't directly manipulate the UI, meaning you don't enable, disable, show, or hide components directly. Instead, you **declare what you want to show,** and React figures out how to update the UI." The corpus uses two hyphens where this map has a comma.
  - With commands, every change from one look to every other look needs its own code. With a description, each look is written once. Source: the syllabus card, "Under the Hood".
- **React does**:
  - Page, plain version: both lines visible after the second try. Derived from the code, `unconfirmed`.
  - Console: no message. `unconfirmed`.
  - Elements: the error `<p>` still holds its text after success. `unconfirmed`.
- **Example step**: `plain/index.html` holds a `<form id="form">` with `<h2>Get our weekly newsletter</h2>`, `<input id="email">`, `<button id="signup">Sign up</button>`, `<p id="sending"></p>`, `<p id="error"></p>`, and `<p id="thanks"></p>`. `plain/signup.js` finds each element with `getElementById`, adds a `submit` listener that calls `e.preventDefault()`, sets `button.disabled = true` and `sending.textContent = 'Sending...'`, and starts a 1500 millisecond timer. The timer clears `sending`, sets `button.disabled = false`, and writes either the error or the thanks text, checking `box.value === 'john@mail.com'`. The empty-box rule is left out of the plain version to keep it short.
- **Code names**: `plain/index.html`, `plain/signup.js`, `form`, `email`, `signup`, `sending`, `error`, `thanks`, `box`, `button`, `errorText`, `document.getElementById`, `addEventListener('submit', ...)`, `e.preventDefault()`, `button.disabled = true`, `textContent`, `box.value`, `setTimeout(..., 1500)`, `john@mail.com`, `mary@mail.com`, `Get our weekly newsletter`, `Sign up`, `Sending...`, `This email is already signed up.`, `Thanks! You are signed up.`, `errorText.textContent = '';`

### Principle 2: List Every Visual State and Draw Each One Before Writing Logic

- **Rule**: Before any handler, list every look the component can have, and write JSX that draws each look from one value, `status`. Check each look by changing that value by hand.
- **Simplest version**:
  - `function SendButton({ status = 'ready' }) { return <button>{status === 'sending' ? 'Sending...' : 'Send'}</button>; }`
  - Changing `'ready'` to `'sending'` in the code shows the other look.
  - Everyday picture: a designer's mockups, one drawing per screen. Source: "If you work with a designer, you may have seen mockups for different 'visual states'."
- **Words to teach**:
  - *Visual states* of this page, from react.dev Step 1:
    1. Empty: the button is off.
    2. Typing: the button is on.
    3. Submitting: the box and the button are off, and `Sending...` shows.
    4. Success: the thank-you line shows instead of the form.
    5. Error: the same as typing, plus the error line.
  - *Mock*: the JSX for each look, driven by a `status` prop with a default value, before any logic. Needed when the reader asks how to see the error look without a real failure.
  - *Living styleguide* or *storybook*: one page that shows every look at once. Name only.
  - `status`: our own name. react.dev: "You could call that prop anything you like, the naming is not important."
  - Known: default prop value, Lesson 09. Early `return`, `&&`, Lesson 10. `disabled={...}`, Lesson 03. `map` with `key`, Lesson 18.
  - Helper: `===` and `||`, known JavaScript.
- **Surprises and their steps**:
  - Question: "No click happened. How does the page already show the error line?"
    1. `App.jsx` renders `<NewsletterForm status="error" />`.
    2. React calls `NewsletterForm` with `status` set to `'error'`.
    3. The early `if` for `'success'` does not match, so the form is drawn.
    4. `status === 'error' && ...` is true, so the error line is drawn.
  - Question: "How can one page show all five looks at once?"
    1. `App.jsx` holds the array `['empty', 'typing', 'submitting', 'success', 'error']`.
    2. `map` renders one `<NewsletterForm status={status} />` per item, each with `key={status}`.
    3. Each copy draws its own look from its own prop.
    Source: the `<DeepDive>` "Displaying many visual states at once".
- **Look-alikes**:
  - `status` as a prop in the mock and `status` as state in Principle 5: the same JSX reads it in both, but they are NOT the same. The prop is set by the parent and never changes by itself. The state is set by our handlers. They differ at the moment the user clicks: only the state version changes look.
  - The success look and the other four: the success look returns different JSX, the other four share one form. react.dev uses an early `return` for success.
- **Where did that come from?**:
  - `status` inside `NewsletterForm` when `App.jsx` renders `<NewsletterForm />` with no attribute: the default value supplies it.
    1. The tag passes no `status`.
    2. `props.status` is `undefined`.
    3. The `= 'empty'` default in the parameter list gives `'empty'`.
- **Real beginner mistake** (react.dev Step 4: "you never want to show an error message and disable the input at the same time, or the user won't be able to correct the error!"):
  1. The developer writes the box as `disabled={status !== 'typing'}`, to turn it off while sending.
  2. They test only the typing and sending looks.
  3. The first real error arrives, and the error line shows.
  4. The box is still off, because `'error'` is not `'typing'`.
  5. The user cannot fix the email.
  6. With all five looks on one page, the greyed box under the error line is plain to see.
  7. The developer writes `disabled={status === 'submitting'}`.
- **Interview depth**:
  - react.dev: "Mocking lets you quickly iterate on the UI before you wire up any logic."
  - "Pages like this are often called 'living styleguides' or 'storybooks'."
  - react.dev's name for the idea comes from computer science, a *state machine* in one of several states, and from design, visual states. "React stands at the intersection of design and computer science."
  - Deciding which looks exist is a design decision. Ask what the user must see, not what the code must do.
- **React does**:
  - Page: each mock shows its own look. Derived from the corpus, exact display `unconfirmed`.
  - Elements: the box has a `disabled` attribute only in the submitting look. How React writes the attribute in the Elements panel is `unconfirmed`.
  - Console: no message, as long as each item has its `key`. `unconfirmed`.
- **Example step**: `src/components/NewsletterForm.jsx` becomes a mock: `export default function NewsletterForm({ status = 'empty' })`. An early `if (status === 'success') return <p>Thanks! You are signed up.</p>;`. Otherwise a `<form>` with the `<h2>`, `<input disabled={status === 'submitting'} />`, `<button disabled={status === 'empty' || status === 'submitting'}>Sign up</button>`, `{status === 'submitting' && <p>Sending...</p>}`, and `{status === 'error' && <p>This email is already signed up.</p>}`. `src/App.jsx` maps the five values into five `<NewsletterForm status={status} key={status} />` copies, each under an `<h4>` with its name. No state yet.
- **Code names**: `NewsletterForm.jsx`, `NewsletterForm`, `App.jsx`, `status`, `status = 'empty'`, `'empty'`, `'typing'`, `'submitting'`, `'success'`, `'error'`, `disabled={status === 'submitting'}`, `disabled={status !== 'typing'}`, `status === 'empty' || status === 'submitting'`, `statuses`, `map`, `key={status}`, `<h4>`, `SendButton`, `'ready'`, `'sending'`

### Principle 3: Find What Moves the Page from One State to the Next

- **Rule**: For each change between two looks, name what causes it. Some causes are the user, such as typing or clicking. Some are the computer, such as a reply arriving or a timer ending. Both must set state, or the page never changes.
- **Simplest version**:
  - The parcel tracker again: the shop clicks Shipped, a human input. The van's scanner reports Delivered, a computer input.
  - On paper: each look is a circle, each change is an arrow with its cause written on it.
- **Words to teach**:
  - *Trigger*: what causes a change of state. Needed when the reader asks what moves the page out of `Sending...`.
  - *Human input*: "clicking a button, typing in a field, navigating a link". Usually needs an event handler. Source: the `<Note>`, "Notice that human inputs often require event handlers!"
  - *Computer input*: "a network response arriving, a timeout completing, an image loading". Here, the timer of the fake reply.
  - *State diagram*: circles for looks, arrows for changes. react.dev: "try drawing each state on paper as a labeled circle, and each change between two states as an arrow."
  - Known: `onChange` and `onSubmit`, Lessons 11 and 20. `setTimeout`, Lesson 15.
- **Surprises and their steps**:
  - Question: "Nobody clicks anything after `Sign up`. What moves the page to the thank-you line?"
    1. The click on `Sign up` is a human input. Its handler sets `submitting`.
    2. The handler also starts the 1500 millisecond timer.
    3. The handler ends. React draws the submitting look.
    4. 1500 milliseconds later, the browser runs the timer. This is the computer input.
    5. The timer sets `success` or `error`.
    6. React draws that look.
  - The arrows of this page, from react.dev's diagram and list:
    1. Empty to typing: the user types the first letter.
    2. Typing to empty: the user deletes the last letter.
    3. Typing to submitting: the user clicks `Sign up`.
    4. Submitting to success: the reply says yes.
    5. Submitting to error: the reply says no.
    6. Error to submitting: the user clicks `Sign up` again. This arrow is in this map's page, not in react.dev's diagram.
- **Look-alikes**:
  - The click and the timer: both set state, and React treats both the same way. They differ in who starts them: the user, or the browser running a function our code handed it earlier.
  - react.dev's `<Note>` says human inputs *often* need handlers, not always. The timer needs no handler on any element. Source: "In both cases, **you must set state variables to update the UI.**"
- **Where did that come from?**:
  - The call to our timer function, with no click: the browser makes it.
    1. `setTimeout` hands our function and `1500` to the browser.
    2. The browser waits 1500 milliseconds.
    3. The browser calls our function.
  - `email` inside the timer, 1500 milliseconds after the click: the render that made the handler supplies it, the snapshot of Lesson 15. It is the email that was in the box at the click.
- **Real beginner mistake** (the stuck spinner, a common bug of forgetting the computer input):
  1. The developer writes `handleSubmit` to call `setStatus('submitting')`.
  2. They draw only the human arrows and forget the reply.
  3. The timer only logs the result, `console.log('signed up')`, and sets no state.
  4. The user clicks `Sign up`.
  5. The page shows `Sending...`, and the box and button are off.
  6. The reply arrives, the Console shows the log, and the page stays on `Sending...` forever.
  7. The developer draws the arrows, sees no arrow out of submitting, and adds `setStatus('success')` and `setStatus('error')` to the timer.
- **Interview depth**:
  - react.dev: "You can sketch out many flows this way and sort out bugs long before implementation."
  - An arrow that is not on the diagram should not happen. A look with no arrow out of it is a dead end.
  - Real computer inputs come from `fetch`. Loading, errors, and replies that arrive out of order: Lesson 33.
- **React does**:
  - Page: `Sending...` for about 1500 milliseconds, then the thank-you line or the error line. Derived, `unconfirmed`.
  - Console in the mistake: `signed up`, and the page stays on `Sending...`. `unconfirmed`.
- **Example step**: no page code yet. The lecture shows the state diagram of `NewsletterForm` as a figure: circles `empty`, `typing`, `submitting`, `success`, `error`, with arrows labeled `type`, `delete all`, `click Sign up`, `reply yes`, `reply no`, `click Sign up again`.
- **Code names**: `handleSubmit`, `setStatus('submitting')`, `setTimeout(..., 1500)`, `setStatus('success')`, `setStatus('error')`, `console.log('signed up')`, `email`, `onChange`, `onSubmit`, `Sign up`, `Sending...`

### Principle 4: Keep the Current State in One `status` String, Not in Many True or False Values

- **Rule**: When a component can be in only one look at a time, store that look in one string, `status`, whose value is one of a short list. Separate true or false values allow mixes that no look matches. A value that can be computed from other state, such as an empty box, is not stored at all.
- **Simplest version**:
  - Two values: `const [isSending, setIsSending] = useState(false);` and `const [isDone, setIsDone] = useState(false);`. Four mixes, and both true matches no look.
  - One value: `const [status, setStatus] = useState('ready');` with `'ready'`, `'sending'`, or `'done'`. Three values, three looks.
  - Everyday picture: the parcel tracker with one light per step, each with its own switch. Two switches on means two steps lit. With one dial, one step is lit.
- **Words to teach**:
  - *Impossible state*, react.dev's *paradox*: a mix of values that matches no look, such as sending and error together. Source: "`isTyping` and `isSubmitting` can't both be `true`. A paradox usually means that the state is not constrained enough."
  - *Essential state*: state that cannot be removed without breaking the page. react.dev ends with three: `answer`, `error`, `status`. This page needs two: `email` and `status`, because its error text never changes.
  - *Computed value*: `email.length === 0` gives the empty look, so there is no `isEmpty`. Source: "you can remove `isEmpty` and instead check `answer.length === 0`." The full rules belong to Lesson 22.
  - Known: `useState`, Lesson 12. `.length`, Lesson 20.
- **Surprises and their steps**:
  - Question: "How can the page show `Sending...` and the error at the same time?"
    1. The form uses `isSubmitting` and `isError`.
    2. The first try fails. The timer sets `isSubmitting` to false and `isError` to true.
    3. The user clicks `Sign up` again. The handler sets `isSubmitting` to true and forgets `setIsError(false)`.
    4. React renders. `isSubmitting` is true, so `Sending...` shows.
    5. `isError` is still true, so the error line shows too.

- **Rule**: Each handler sets the next value of `status` and nothing on the page. The JSX already says what each look shows, so React works out what to change. Adding a new look means adding one branch to the JSX, not new commands in every handler.

## Interview Points

1. Plain JavaScript changes the page with commands after each event. Every change from one look to another needs its own commands, and one forgotten command leaves an old part on screen.
2. React's way is declarative: describe what each look shows, keep the current look in state, and let React change the page.
3. Step 1: list every visual state, such as empty, typing, submitting, success, and error, and mock each one before any logic.
4. Step 2: find the triggers. Human inputs, such as typing and clicking, usually need event handlers. Computer inputs, such as a network reply or a timer, also set state.
5. Step 3: store the state with `useState`, with as few moving pieces as possible.
6. Step 4: replace separate true or false values with one `status` string, so impossible mixes cannot exist, and compute what can be computed, such as an empty box from `email.length`.
7. Step 5: handlers only set the next state. The JSX describes each state, and React updates only what changed.
8. A new look adds one branch, not new commands everywhere. The longer code is less fragile.
9. When one string still allows odd mixes, a reducer can model the state more strictly, Lesson 27.
