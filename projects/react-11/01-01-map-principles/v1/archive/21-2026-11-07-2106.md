# Q21 Principle Map (River Version v1): Reacting to Input with State

- **Version**: River Version (`v1`), written under `skills/v10.4`
- **Bank Row**: `questions/questions.md` row 21
- **Topic Tag**: `#reacting_to_input` | `❱ CORE`
- **Interview Question**: *How do you design a component that reacts to input with state instead of touching the DOM?*

## Scope

Covered here:
- Plain JavaScript changes the page with commands, one change at a time, such as show the error, hide the box. Each command must remember what every other command showed. One forgotten hide leaves two messages on the page at once.
- React's way, in the five steps of `learn/reacting-to-input-with-state.md`: list the pictures the component can show, find what moves it from one picture to the next, keep the current picture in state, drop state that adds nothing, and let event handlers only set the next state.
- A picture of the page is a *visual state*. The JSX describes each picture once, and a variable named `status` says which picture is on the page now.
- Two kinds of inputs move the page: human inputs, such as typing and clicking, and computer inputs, such as an answer arriving or a timer finishing. Both set state.
- The circles and arrows drawing of the pictures and the moves between them, the *state machine*.
- One `status` string instead of several `true` or `false` variables, because the variables allow pictures that must never appear.
- The Empty picture needs no status of its own, because the length of the typed code already tells it. Named once here, the full rules belong to Lesson 22.
- Adding a new picture later adds one branch and touches no other picture.

Left to other lessons:
- Lesson 01 already showed one value in two places going out of sync in plain JavaScript, with the words *declarative* and *imperative*. This lesson builds on it: here the problem is pictures that must replace each other, not one value shown twice.
- The full rules for which values belong in state and which are calculated, redundant and duplicated state: Lesson 22, `#state_structure`.
- React's own step by step method for building a whole page from a design: Lesson 26, `#thinking_in_react`.
- Gathering the status changes into a reducer, `useReducer`: Lesson 27, `#use_reducer`. Named once in interview depth.
- State lost when a condition swaps one tree of tags for a different one: Lesson 25, `#component_identity`. Named once in interview depth.
- Controlled fields, `value` and `onChange`: Lesson 20, known.
- Controlled state against uncontrolled `FormData`: Lesson 40, `#forms`. React 19 form actions, `useActionState`, `useFormStatus`: Lessons 41 to 44. Named once in interview depth.
- State machine libraries such as XState: not taught. Named once in interview depth.
- A real network request with `fetch`, promises, `async`, `await`, `try`, `catch`: not taught here. The example uses `setTimeout` from Lesson 15 as a pretend server, so no promise is needed.

## Start of the Lecture

**Simplest version of the chapter's idea**:
- One status, two pictures, one button.
- `const [status, setStatus] = useState('typing');`
- `if (status === 'sent') { return <p>Thanks!</p>; }`
- `return <button onClick={() => setStatus('sent')}>Send</button>;`
- What the reader sees: a Send button. After one click, the button is gone and Thanks! is on the page. No line hides the button.
- Everyday picture for *imperative* against *declarative*, from the corpus: telling a driver every turn on the way, against telling a taxi driver the address and letting the driver find the way. Lesson 01 met the same two words.
- Everyday picture for *visual states* and a *state machine*: a traffic light. It shows one of a fixed set of pictures, red, amber, or green, never two at once, and it moves between them only along fixed arrows. Three separate switches, one per lamp, could light red and green together. One dial with three positions cannot.

**The real page problem**:
1. A checkout page has a coupon box: a Coupon code box, an Apply button, and room for one message under it.
2. The user types SAVE5 and clicks Apply. The page shows the red message `This code is not valid.`
3. The user changes the code to SAVE10 and clicks Apply again. The page shows `SAVE10 applied. You save 10%.`
4. In the plain JavaScript version, the red message is still there under the green one. The success branch showed its message and never hid the error, because it had no way of knowing the error branch had shown it.
5. Each new message makes every other branch longer, because every command must undo what all the other commands may have done.

**The plain JavaScript version for the opening**:
- Files: `index.html`, `coupon.js`.
- `index.html`: `<input id="code">`, `<button id="apply">Apply</button>`, `<p id="error" hidden>This code is not valid.</p>`, `<p id="success" hidden>SAVE10 applied. You save 10%.</p>`, `<script src="coupon.js"></script>`.
- `coupon.js`: `const box = document.getElementById('code');`, `const errorText = document.getElementById('error');`, `const successText = document.getElementById('success');`, then `document.getElementById('apply').addEventListener('click', () => { if (box.value === 'SAVE10') { successText.hidden = false; } else { errorText.hidden = false; } });`
- No promise, no `async`, no `try`. The only helper is the HTML attribute `hidden`, which keeps a tag out of sight, and its JavaScript twin `errorText.hidden`.
- Result on the page after SAVE5 then SAVE10: both messages visible. Confirmed by the corpus only as a kind of bug, "forgetting to show or hide something". The exact page is `unconfirmed`, for the lab.

**Example page chosen for this lesson**: the coupon box of a checkout page.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx` rendering `<CouponBox />`, `src/components/CouponBox.jsx`. The plain JavaScript version for the opening lives in its own `index.html` and `coupon.js`.
- Final pictures: Empty, the box blank and Apply greyed out. Typing, Apply ready. Checking, the box and Apply greyed out and `Checking...` under them. Applied, only `SAVE10 applied. You save 10%.` Error, like Typing plus the red `This code is not valid.` Principle 5 adds Expired, like Typing plus `This code has expired.`
- The pretend server: `setTimeout` waits one second, then accepts `SAVE10`, reports `SUMMER` as expired from Principle 5 on, and rejects any other code.

**Why this page**:
1. Everyone has typed a coupon code at a checkout. A box, a button, and a message need no explanation.
2. It has exactly the pictures of the bank question and the corpus form: empty, typing, a waiting picture, success, and error.
3. The bug is big and plain: a red error and a green success on the page at the same time.
4. It needs one human input of each kind, typing and clicking, and one computer input, the answer arriving.
5. The answer can come from `setTimeout`, known from Lesson 15, so no promise, `async`, `await`, `try`, `catch`, or `finally` enters the lesson. This is the problem named in the map skill's counter-example for an earlier map of this lesson.
6. The plain JavaScript version needs only `getElementById`, `addEventListener`, and `hidden`. The first two are known from Lessons 01 and 11.

**Other pages considered**:
1. *The syllabus card's members-only sign-up form*: the same bug, `Sign-up failed` next to `Welcome, Mary Jones`. Rejected because a sign-up form needs several fields, and its imperative version needs a spinner, `disabled`, and a pretend network call before the bug can show.
2. *The corpus City quiz*: rejected. Its plain JavaScript version needs a promise, `async`, `await`, `try`, `catch`, and `finally`.
3. *The contact form of Lesson 20*: rejected. The reader would carry five fields from the last lesson into a lesson about pictures, and the new idea would hide behind them.
4. *The corpus challenge with a picture and a purple background, toggling CSS classes*: close, and it matches the bank's wording about toggling classes. Rejected as the main page because it has only two pictures and no computer input. Kept for interview depth.
5. *A Like button with a count*: rejected. It has one picture that changes a number, not pictures that replace each other.

**Older facts the reader needs**:

- `addEventListener` in plain JavaScript and `onClick` in React: Lessons 04 and 11.

## Principles

### Principle 1: The Coupon Box Has Five Pictures

- **Rule**: Before writing any handler, list every picture the component can show, and write JSX that draws each picture from one variable, `status`. The picture follows only from `status`, never from what happened before.
- **Simplest version**:
  - `function CouponBox({ status = 'empty' }) { ... }`
  - `if (status === 'applied') { return <p>SAVE10 applied. You save 10%.</p>; }`
  - Otherwise the box, the button, and `{status === 'error' && <p className="error">This code is not valid.</p>}`.
  - Changing the word `'empty'` to `'error'` in the code shows the error picture, with no typing and no click.
  - Everyday picture: a designer's set of mockups, one drawing for each moment of the box, laid side by side.
- **Words to teach**:
  - *Visual state*: one picture the user can see. The corpus lists Empty, Typing, Submitting, Success, Error; here Empty, Typing, Checking, Applied, Error. Needed at the start, when the reader lists what the coupon box can look like.
  - `status`: our own variable, one string that names the picture on the page now. The name is our choice; the corpus says "the naming is not important". Needed when the first JSX branch is written.
  - *Mock*: the component drawn for each picture before any handler exists, here driven by a prop with a default value. Needed when the reader changes `'empty'` to `'error'` and sees the error picture.
  - Known: default prop value, Lesson 09. `if (...) return` and `&&`, Lesson 10. `className`, Lesson 02.
  - Helper: `disabled`, the HTML attribute that greys out a box or button and blocks typing and clicks. Half a sentence. `===` and `||`, known JavaScript.
- **Surprises and their steps**:
  - Facts: 1. `CouponBox` has a prop `status` with the default `'empty'`. 2. No handler exists yet, and nobody types. 3. The developer changes the default to `'error'`, and the page shows the box, a ready Apply button, and the red message. Question: "How can the error picture appear when nobody typed a wrong code?"
    1. React calls `CouponBox` with no `status` prop, so the default value fills `status`.
    2. `status` is `'error'`, so the `if` for `'applied'` is skipped.
    3. `status === 'checking'` is false, so the box and Apply are not greyed out.
    4. `status === 'error'` is true, so `&&` gives the red paragraph.
    5. The JSX never asked what the user did before. It asked only what `status` holds.
  - Facts: 1. The Empty picture has the box blank and Apply greyed out. 2. The Typing picture has Apply ready. 3. The only difference in the JSX is the condition on the button. Question: "Why does one `disabled` condition draw two different buttons?"
    1. The button gets `disabled={status === 'empty' || status === 'checking'}`.
    2. With `'empty'`, the condition is true, and the button is greyed out.
    3. With `'typing'`, both parts are false, and the button is ready.
- **Angle**: Because the JSX reads only `status`, every picture can be drawn at once, with no user action at all. The corpus does exactly this: one page renders the form once for each status with `map()`, and calls such a page a "living styleguide" or "storybook". The plain JavaScript version cannot do this, because its error picture exists only after someone types a wrong code and clicks Apply. This explains why changing one word shows the error picture. Source: `reacting-to-input-with-state.md`, `<DeepDive>` "Displaying many visual states at once".
- **Look-alikes**:
  - `if (status === 'applied') { return ... }` and `{status === 'error' && <p>...</p>}`: the `if` with `return` swaps the whole picture, so the Applied picture has no box and no button; `&&` adds or drops one part inside the same picture. Not the same result: the first replaces everything, the second adds one line. Reason: the Applied picture shares nothing with the others, while Error is the Typing picture plus one line.
  - `status` as a prop with a default, in this principle, and `status` from `useState`, in Principle 3: the same JSX reads the same name. With the prop, the developer picks the picture by editing code; with state, the user's actions pick it. The JSX does not change between the two.
- **Where did that come from?**:
  - `status` inside `CouponBox`, when `App.jsx` writes only `<CouponBox />`: the default value in the parameter list supplies it.
    1. React calls `CouponBox` with an empty props object.
    2. JavaScript finds no `status` in it.
    3. The default `'empty'` fills the variable.
- **Real beginner mistake** (the corpus, Step 4: "you never want to show an error message and disable the input at the same time, or the user won't be able to correct the error!"):
  1. The developer draws the Error picture by copying the Checking picture and adding the red line.
  2. The box gets `disabled={status === 'checking' || status === 'error'}`.
  3. The user types SAVE5 and clicks Apply, and the red message appears.
  4. The box is greyed out, so the user cannot fix the code.
  5. Laying the five pictures side by side shows it at once: Error must be Typing plus one line.
  6. The developer changes the condition back to `disabled={status === 'checking'}`.
- **Interview depth**:
  - The corpus Intro: "you describe the different states that your component can be in, and switch between them in response to the user input. This is similar to how designers think about the UI."
  - "Mocking lets you quickly iterate on the UI before you wire up any logic."
  - A page that renders every picture at once is a "living styleguide" or "storybook", from the corpus `<DeepDive>`.
  - The corpus challenge with the picture and the purple background: instead of `classList.add` and `classList.remove`, calculate `className` from one boolean state during render. This answers the bank's wording about toggling classes on DOM nodes. `className` in JSX instead of DOM changes was met in Lesson 14.
  - The corpus solution to that challenge warns that two different JSX trees returned by `if` must line up, or toggling recreates the tree and resets its state. Lesson 25 owns it.
- **React does**:
  - Page: with `status = 'error'`, the box, a ready Apply button, and the red message. `unconfirmed`, for the lab.
  - Page: with `status = 'applied'`, only `SAVE10 applied. You save 10%.` `unconfirmed`, for the lab.
  - Console: no message. `unconfirmed`, for the lab.
- **Example step**: `src/components/CouponBox.jsx` is the mock: `export default function CouponBox({ status = 'empty' })`, the `if` for `'applied'`, a `<label>Coupon code <input disabled={status === 'checking'} /></label>`, `<button disabled={status === 'empty' || status === 'checking'}>Apply</button>`, `{status === 'checking' && <p>Checking...</p>}`, `{status === 'error' && <p className="error">This code is not valid.</p>}`. `src/App.jsx` renders `<CouponBox />`. Optional extra: `App.jsx` maps over `['empty', 'typing', 'checking', 'applied', 'error']` and renders `<CouponBox key={status} status={status} />` for each, the living styleguide.
- **Code names**: `CouponBox.jsx`, `App.jsx`, `CouponBox`, `status`, `'empty'`, `'typing'`, `'checking'`, `'applied'`, `'error'`, `Coupon code`, `Apply`, `Checking...`, `SAVE10 applied. You save 10%.`, `This code is not valid.`, `disabled`, `className="error"`, `statuses`, `key={status}`

### Principle 2: Clicks and a Timer Move the Status

- **Rule**: For every picture, find what moves the page into it. Human inputs, such as typing and clicking, and computer inputs, such as an answer arriving or a timer finishing, both move the page only by setting state.
- **Simplest version**:
  - Five circles: Empty, Typing, Checking, Applied, Error.
  - Arrows: Empty to Typing, "types a letter". Typing to Empty, "clears the box". Typing to Checking, "clicks Apply". Checking to Applied, "answer: code accepted". Checking to Error, "answer: code rejected". Error to Checking, "clicks Apply again".
  - Everyday picture: the traffic light again. Its arrows are fixed; green never jumps straight to red.
- **Words to teach**:
  - *Human input*: something the user does, such as typing in the box or clicking Apply. The corpus: "Human inputs often require event handlers". Needed when the reader draws the arrow out of Typing.
  - *Computer input*: something that arrives without the user doing anything, such as a network answer, a timer finishing, an image loading. Needed when the reader asks what moves the page out of Checking.
  - *State machine*: the corpus's computer science name for a thing that is always in exactly one of several states, drawn as labeled circles with arrows. Needed when the drawing is finished. Name and drawing only.
  - Known: `setTimeout`, Lesson 15, here as the pretend server.
- **Surprises and their steps**:
  - Facts: 1. The user clicks Apply once. 2. The page shows `Checking...`. 3. One second later, with no second click, the page shows `SAVE10 applied. You save 10%.` Question: "Who moved the page from Checking to Applied, when the user did nothing?"
    1. The click is a human input. Its handler sets the status to `'checking'` and starts a timer.
    2. The handler finishes. The page shows the Checking picture.
    3. One second later, the timer finishes. This is a computer input.
    4. The timer's function sets the status to `'applied'`.
    5. React renders `CouponBox` again and draws the Applied picture.
- **Angle**: The answer from a server is an input, the same kind of thing as a click. The corpus puts "a network response arriving" and "a timeout completing" in one list with clicking and typing, and says: "In both cases, you must set state variables to update the UI." So the function the timer runs does not show the green message itself; it sets state, exactly like a click handler. This explains why the page leaves Checking with no user action. Source: `reacting-to-input-with-state.md`, Step 2.
- **Look-alikes**:
  - Human input and computer input: the first starts with the user, through a handler such as `onClick`; the second starts outside the user, here the function given to `setTimeout`. Same result on the page: both end by calling a setter, and React draws the next picture. Reason: React does not care who asked for the change, only which state was set.
  - A picture and an arrow: a picture is what the user sees, a circle in the drawing; an arrow is the input that moves the page from one picture to another. The JSX holds the pictures; the handlers hold the arrows.
- **Where did that come from?**:
  - The answer of the pretend server, with no server in the project: our own `setTimeout` supplies it.
    1. The click handler calls `setTimeout` with a function and `1000`.
    2. The browser keeps the function and waits one second.
    3. The browser calls the function, which checks the code and sets the status.
- **Real beginner mistake** (the corpus describes Error as "Same as Typing state, but with an extra error message", and advises drawing the arrows to "sort out bugs long before implementation"):
  1. The developer writes the Apply button as `disabled={status !== 'typing'}`.
  2. The user types SAVE5 and clicks Apply.
  3. The answer sets the status to `'error'`, and the red message appears.
  4. The user fixes the code to SAVE10.
  5. Apply stays greyed out, because the status is `'error'`, not `'typing'`.
  6. The drawing has no arrow from Error to Checking, and the code has none either.
  7. The developer adds the arrow and writes the condition from the pictures: `disabled={code.length === 0 || status === 'checking'}`.
- **Interview depth**:
  - The corpus's two lists: human inputs, "clicking a button, typing in a field, navigating a link"; computer inputs, "a network response arriving, a timeout completing, an image loading".
  - "try drawing each state on paper as a labeled circle, and each change between two states as an arrow."
  - The drawing is a state machine; React "stands at the intersection of design and computer science".
  - In a real app the answer comes from a network request; the timer stands in for it. Promises and `async` are not this lesson.
- **React does**:
  - Page: `Checking...` for about one second after the click, then the Applied picture. `unconfirmed`, for the lab.
  - Console: no message. `unconfirmed`, for the lab.
- **Example step**: no change to `CouponBox.jsx`. The lecture shows the drawing of the five circles and six arrows.
- **Code names**: `onClick`, `setTimeout`, `1000`, `'checking'`, `'applied'`, `'error'`, `status !== 'typing'`, `code.length === 0`, `SAVE5`, `SAVE10`

### Principle 3: One status String Replaces Four Switches

- **Rule**: Keep the current picture in one state variable, `status`, holding one string such as `'typing'`, `'checking'`, `'applied'`, or `'error'`. Separate `true` or `false` state variables, one per picture, allow combinations that are no picture at all.
- **Simplest version**:
  - First idea, from the corpus: `const [isTyping, setIsTyping] = useState(true);`, and the same for `isChecking`, `isApplied`, `isError`.
  - Four switches give 16 combinations; only 4 are pictures.
  - Final: `const [code, setCode] = useState('');` and `const [status, setStatus] = useState('typing');`.
  - Everyday picture: the traffic light again. Three switches, one per lamp, can light red and green together; one dial with three positions cannot.
- **Words to teach**:
  - `status` as state: `useState('typing')`, one string that can hold only one value at a time. Needed when the mock's prop becomes state.
  - *Impossible state*, the corpus also says *paradox*: a combination of state values that matches no picture, such as `isChecking` and `isApplied` both `true`. Needed when the reader counts the combinations.
  - *Essential state*: state you cannot remove without breaking the page. Name only; the full rules are Lesson 22.
  - The Empty picture has no status: `code.length === 0` already tells it. Needed when the reader asks where `'empty'` went.
  - Known: `useState`, Lesson 12. `value` and `onChange`, Lesson 20.
- **Surprises and their steps**:
  - Facts: 1. The page uses four `true` or `false` state variables. 2. The answer for SAVE10 calls `setIsChecking(false)` and `setIsApplied(true)`. 3. An earlier wrong code had set `isError` to `true`. Question: "Why does React draw the red error and the green success together, when React is supposed to keep the page right?"
    1. `isError` is still `true`, because no line set it back to `false`.
    2. `isApplied` is now `true`.
    3. React renders and reads both variables.
    4. The JSX says: when `isError`, show the red line; when `isApplied`, show the green line.
    5. React draws exactly what state says, so both lines appear.
  - Facts: 1. The mock had five statuses, with `'empty'`. 2. The final state has four, with no `'empty'`. 3. The Apply button is still greyed out when the box is blank. Question: "How does the page still show the Empty picture with no `'empty'` status?"
    1. The box shows `code`, and `code` is `''`.
    2. During render, `code.length === 0` is true.
    3. The button gets `disabled={code.length === 0 || status === 'checking'}`, so it is greyed out.
    4. A separate `'empty'` status would have to be kept equal to `code.length === 0` by hand, and could fall out of step with it.
- **Angle**: React makes the page match state, faithfully, even when state describes a page that must never exist. So React alone does not stop the two-message bug of the opening: four switches let the same bug back in. Only the shape of state stops it. The corpus's goal is to "prevent the cases where the state in memory doesn't represent any valid UI that you'd want a user to see", and it counts: "There are four possible combinations of two booleans, but only three correspond to valid states." Four switches give 16 combinations for 4 pictures. One string holds one value, so the page can be in only one picture. Source: `reacting-to-input-with-state.md`, Steps 3 and 4; `choosing-the-state-structure.md`, "Avoid contradictions in state".
- **Look-alikes**:
  - Four switches, `isTyping`, `isChecking`, `isApplied`, `isError`, and one `status` string: both can describe the four pictures. The switches also describe 12 combinations that are no picture; the string describes only the four. Not the same: with switches, every arrow must set four variables right; with the string, every arrow sets one.
  - `'empty'` as a status and `code.length === 0`: both tell that the box is blank. The status is a second copy that must be kept in step by hand; the length is read from `code` on every render and cannot disagree with it. The corpus: "you can remove `isEmpty` and instead check `answer.length === 0`."
  - `status === 'checking'` written inline, and a constant such as `const isChecking = status === 'checking';`: the same value. The constant is not state, so it cannot fall out of step. Source: `choosing-the-state-structure.md`.
- **Where did that come from?**:

### Principle 4: The Click Only Sets the Status

- **Rule**: Event handlers and the timer only set the next status. They never show, hide, enable, or disable anything. React draws the picture for the new status and removes what that picture does not contain.
- **Simplest version**:
  - `function handleApply() { setStatus('checking'); setTimeout(() => { if (code === 'SAVE10') { setStatus('applied'); } else { setStatus('error'); } }, 1000); }`
  - `<button onClick={handleApply} disabled={code.length === 0 || status === 'checking'}>Apply</button>`
  - Everyday picture: the taxi from the opening. The handler gives the address, a status; React drives.
- **Words to teach**:
  - No new code word. The new idea is the job of a handler: set the next status, and nothing else.
  - Known: `onClick`, Lesson 11. `setTimeout` and the snapshot inside it, Lesson 15. `if (...) return`, Lesson 10. Commit changes only the nodes that differ, Lesson 13.
- **Surprises and their steps**:
  - Facts: 1. The user typed SAVE5, clicked Apply, and sees `This code is not valid.` 2. The user changes the box to SAVE10, and the red line stays, because the status is still `'error'`. 3. The user clicks Apply. 4. `handleApply` has no line that hides the red message. 5. The red message is gone at once, and `Checking...` is on the page. Question: "Who removed the red message, when no line of our code hides it?"
    1. The click calls `handleApply`, and `setStatus('checking')` asks for a new render.
    2. React calls `CouponBox` again, and `status` is `'checking'`.
    3. `status === 'error'` is false, so `&&` gives nothing for the red line.
    4. `status === 'checking'` is true, so the JSX has `Checking...`.
    5. React compares the new JSX with the last one and removes the red paragraph from the DOM, adds the `Checking...` paragraph, and greys out the box and the button.
  - Facts: 1. The user clicks Apply with SAVE10. 2. One second later the timer's function runs. 3. It reads `code`. 4. The box is greyed out during Checking. Question: "Which code does the timer's function read, the code at the click or the code one second later?"
    1. The click happened in a render where `code` was SAVE10.
    2. The function given to `setTimeout` was created in that render and keeps that render's `code`.
    3. The box is greyed out during Checking, so the code cannot change anyway.
    4. The function reads SAVE10 and sets `'applied'`.
- **Angle**: The last corpus challenge rebuilds the plain JavaScript form so that every setter calls one function, `updateDOM`, which redraws every part of the page from the variables, every time. The corpus then says: "The `updateDOM` function you wrote shows what React does under the hood when you set the state. (However, React also avoids touching the DOM for properties that have not changed since the last time they were set.)" So a handler never needs to know what the last picture showed: setting state redraws the whole picture from scratch, and the red line goes because the new picture has none. This explains why `handleApply` clears the error without mentioning it. Source: `reacting-to-input-with-state.md`, Challenge "Refactor the imperative solution without React", solution.
- **Look-alikes**:
  - `errorText.hidden = false` in plain JavaScript and `{status === 'error' && <p className="error">This code is not valid.</p>}` in JSX: the first is a command, a change made at one moment, which stays until some other command undoes it; the second is a description, true for every render, so the red line exists only while the status is `'error'`. Not the same: the command needs an undo in every other branch; the description needs none.
  - `handleApply` in the plain JavaScript version and in React: the plain one decides which message to show; the React one decides only which status comes next. The corpus: "you don't enable, disable, show, or hide components directly. Instead, you declare what you want to show".
- **Where did that come from?**:
  - The removal of the red paragraph from the DOM, with no `remove` or `hidden` in our code: React supplies it in the commit step, Lesson 13.
    1. The new JSX has no red paragraph.
    2. React compares it with the last JSX.
    3. React removes the paragraph that is no longer described.
  - `code` inside the timer's function: the render of the click supplies it, Lesson 15.
- **Real beginner mistake** (the bank row's wording: "Your instinct is to show and hide page parts by toggling classes on DOM nodes"; Lesson 14 named DOM changes inside a component as a side effect):
  1. Inside `CouponBox`, the developer keeps `<p id="error" className="hidden">This code is not valid.</p>` in the JSX for every picture.
  2. In the answer branch for a wrong code, they write `document.getElementById('error').className = ''`.
  3. The user types SAVE5 and clicks Apply, and the red line appears.
  4. The user changes the code and React renders again. The JSX still says `className="hidden"`, the same as the last render, so React does not touch the paragraph, and the red line stays.
  5. The page now has two owners: React for the JSX, and the developer's command for that one paragraph.
  6. The developer removes the command, deletes `id="error"`, and writes `{status === 'error' && <p className="error">This code is not valid.</p>}`.
  - Step 4 rests on the corpus sentence that React "avoids touching the DOM for properties that have not changed since the last time they were set". The exact page is `unconfirmed`, for the lab.
- **Interview depth**:
  - The corpus Recap: "Declarative programming means describing the UI for each visual state rather than micromanaging the UI (imperative)."
  - "Expressing all interactions as state changes lets you later introduce new visual states without breaking existing ones. It also lets you change what should be displayed in each state without changing the logic of the interaction itself."
  - The corpus form keeps a separate `error` state with the error object and shows `{error.message}`; this page uses one fixed message, so `status` is enough.
  - The early `return` for Applied removes the box and the button, so the typed text is gone from the DOM. Losing state when a tree is swapped: Lesson 25.
  - React 19 forms can handle the waiting picture with actions and `useFormStatus`: Lessons 41 to 44.

  - Console: no message. `unconfirmed`, for the lab.

The `if (status === 'applied')` return moves below the two `useState` lines. This is the working page.

### Principle 5: A New Picture Adds One Branch

- **Rule**: To add a picture, add one status value, one line of JSX for it, and the arrow that sets it. No other picture changes. In plain JavaScript, every existing branch must also learn to hide the new message.
- **Simplest version**:
  - The pretend server learns one more answer: `SUMMER` is a real code, but it has expired.
  - In the timer: `else if (code === 'SUMMER') { setStatus('expired'); }`
  - In the JSX: `{status === 'expired' && <p className="error">This code has expired.</p>}`
  - Everyday picture: adding one more mockup to the designer's row; the other drawings stay as they are.
- **Words to teach**:
  - No new code word. `'expired'` is one more value of our own `status`.
  - Known: everything from Principles 1 to 4.
- **Surprises and their steps**:
  - Facts: 1. The user types SUMMER and clicks Apply, and sees `This code has expired.` 2. The user changes the code to SAVE10 and clicks Apply. 3. The expired line is gone, and the Applied picture shows. 4. No line written for Applied or Checking mentions `'expired'`. Question: "Why did the new message not need an undo in any old branch?"
    1. The click sets the status to `'checking'`.
    2. React renders. `status === 'expired'` is false, so the expired line is not in the JSX.
    3. React removes it from the DOM.
    4. The timer sets `'applied'`, and the early `return` draws only the green line.
- **Angle**: The corpus admits the React version is the longer one: "Although this code is longer than the original imperative example, it is much less fragile." The extra length is paid once, in the list of pictures; after that, a new picture costs one value, one line of JSX, and one arrow, and no old line changes. In plain JavaScript the cost grows with every message already on the page, because each command must hide everything the others may have shown. This explains why adding Expired touched no Applied or Error code. Source: `reacting-to-input-with-state.md`, end of Step 5; the syllabus card's "Under the Hood".
- **Look-alikes**:
  - Adding Expired in plain JavaScript and in React: in plain JavaScript, one new `<p id="expired" hidden>`, one new branch that shows it, and a new `hidden = true` line in the success branch and the error branch, while the new branch must hide both old messages; in React, one `else if` in the timer and one `&&` line in the JSX. Same page when every line is right. Not the same risk: the plain version has three old places to forget, the React version none.
- **Where did that come from?**:
  - The disappearance of `This code has expired.` on the next click: React supplies it, the same steps as Principle 4.
- **Real beginner mistake** (the corpus: "Adding a new UI element or a new interaction would require carefully checking all existing code to make sure you haven't introduced a bug (for example, forgetting to show or hide something)"):
  1. In the plain JavaScript version, the developer adds `<p id="expired" hidden>This code has expired.</p>` and a branch for SUMMER that sets `expiredText.hidden = false`.
  2. They add `errorText.hidden = true` to that new branch, so a wrong code followed by SUMMER looks right.
  3. They forget to add `expiredText.hidden = true` to the success branch.
  4. The user types SUMMER and clicks Apply, then types SAVE10 and clicks Apply.
  5. The page shows `This code has expired.` and `SAVE10 applied. You save 10%.` together.
  6. In the React version, the same change is one `else if` and one `&&` line, and this bug has no place to happen.
- **Interview depth**:
  - The bank's "state machine replaces DOM poking": the number of pictures grows by one; the number of moves to handle by hand in plain JavaScript grows with every pair of pictures.
  - Declarative code describes each picture once, so a change to what one picture shows does not touch the arrows, and a new arrow does not touch the pictures.
  - When the arrows grow many, a reducer gathers them in one place: Lesson 27.
- **React does**:
  - Page: SUMMER shows `This code has expired.`; SAVE10 next shows only the Applied picture. `unconfirmed`, for the lab.
  - Page, plain JavaScript mistake: both messages visible. `unconfirmed`, for the lab.
  - Console: no message. `unconfirmed`, for the lab.
- **Example step**: in `CouponBox.jsx`, the timer gains `else if (code === 'SUMMER') { setStatus('expired'); }` and the JSX gains `{status === 'expired' && <p className="error">This code has expired.</p>}`. ## Interview Points

1. Imperative code commands each change, such as show this, hide that; declarative code describes what the page looks like in each state, and React makes the DOM match.
2. Start by listing every visual state the component can show, like a designer's mockups, and draw each one from one variable before writing any handler.
3. Find what moves the page between states: human inputs such as typing and clicking, and computer inputs such as a network answer or a timer. Both only set state.
4. The states and the moves between them form a state machine, drawn as circles and arrows.
5. Keep the current state in one `status` string rather than several booleans. Four booleans allow 16 combinations for 4 real pictures; one string allows only the real ones.
6. React draws whatever state says, so impossible combinations in state become impossible pages. The shape of state prevents them, not React.
7. Remove state that can be calculated, such as an empty flag that `code.length === 0` already gives. Full rules: Lesson 22.
8. Event handlers only set the next status. They never show, hide, or disable anything, so no branch needs to undo what another branch did.
9. A new state costs one value, one branch of JSX, and one arrow, without touching existing states. The React version is longer at first and much less fragile.
10. For many arrows, `useReducer` gathers them in one place, Lesson 27; libraries such as XState model state machines formally.
