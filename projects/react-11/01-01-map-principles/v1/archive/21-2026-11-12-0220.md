# Q21 Principle Map (River Version v1): Reacting to Input with State

- **Version**: River Version (`v1`), written under `skills/v10.5`
- **Bank Row**: `questions/questions.md` row 21
- **Topic Tag**: `#reacting_to_input` | `❱ CORE`
- **Interview Question**: *How do you design a component that reacts to input with state instead of touching the DOM?*

## Scope

Covered here:
- Listing every picture the user can see on one form, and giving each picture a name. React's docs call these pictures "visual states".
- Drawing all the pictures from one `status` value, first as a prop (a mock), then as state.
- Finding what changes the picture: human inputs (typing, clicking Join) and computer inputs (a timer finishing, standing in for a server answer).
- Event handlers that only set `status`, while the JSX decides what shows.
- The same form written with DOM commands, where a forgotten hide leaves two messages on the page.
- One `status` string instead of several true/false state variables, so an impossible picture cannot happen.
- `disabled` on the box and the button.

Left to other lessons:
- The full rules for which values belong in state and which are computed: Lesson 22, `#state_structure`. Here only one case is used: the Join button is off while the box is empty, computed from `email.length`, with no `'empty'` status.
- Two JSX branches that describe the same tree and reset state when the nesting differs: Lesson 25, `#component_identity`. Named once in interview depth.
- The five-step process for building a whole UI from a design mock: Lesson 26, `#thinking_in_react`.
- `useReducer`: Lesson 27, `#use_reducer`. Named once in interview depth.
- State machine libraries such as XState: not taught.
- Real network requests with loading and error states: Lesson 33, `#data_fetching_client`. Here a `setTimeout` stands in for the server.
- Form actions, `useActionState`, `useFormStatus` and their pending flag: Lessons 41 to 43. Named once in interview depth.

## Start of the Lecture

**Opening Essence of the chapter**:
- Key idea: a form has a small set of named pictures. A click or a timer only changes which name is current. The JSX already says what each name looks like.
- What is at stake: the user sees exactly one message after each try, never an old error next to a new success.
- Where readers usually go wrong: they think in commands, "now show this line, now hide that one", and forget one hide.
- The pair to name, as in the Back to the basics table of [Opening Essence](../../../react-10/skills/v10.5/opening-essence/SKILL.md): both ways change what the page shows after the user acts. The one difference: our code edits the page directly through DOM commands, or our code changes a state value and React edits the page.
- Smallest code for the pair, two lines each:
  - DOM command: `error.style.display = '';`
  - State: `setStatus('error');` with `{status === 'error' && <p>Please enter a full email address.</p>}` in the JSX.
- Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both show the red line on the first wrong try. They differ on the next try, when the email is right.

**Theme**: a newsletter box must show one clear answer after each click on Join, and DOM commands let an old error line stay on screen next to the welcome line.

**Ways** (developers really choose between these for the same job):
1. DOM commands: find each element and show or hide it. Fits a page without React.
2. One true/false state variable per message, such as `isError`, `isSubmitting`, `isSuccess`. Works only while every handler resets every flag.
3. One `status` string that holds the name of the current picture. React's docs recommend it.
- Beyond this lesson: `useReducer` (Lesson 27) and form actions with a pending flag (Lessons 41 to 43).

**Example page chosen for this lesson**: the newsletter box at the bottom of a recipe site.
- Files: `index.html`, `src/main.jsx` with `<StrictMode>`, `src/App.jsx`, `src/components/NewsletterSignup.jsx`.
- For the plain JavaScript comparison in Principle 3 only: one separate file, `plain-newsletter.html`, with an inline `<script>`. No React.
- Final parts of the page: `<h2>Join our newsletter</h2>`, one email box, a `Join` button, a line `Sending...` while submitting, a red line `Please enter a full email address.` after a wrong try, and the line `Welcome to the list!` that replaces the whole form on success.
- The four pictures, with their `status` names:
  1. `'typing'`: box and `Join`. `Join` is grey while the box is empty.
  2. `'error'`: box, `Join`, and the red line.
  3. `'submitting'`: box and `Join` both grey, and `Sending...`.
  4. `'success'`: only `Welcome to the list!`.
- Status names follow the syllabus card and the React docs: `'typing'`, `'submitting'`, `'success'`, `'error'`.

**Why this page**:
1. Everyone has seen a newsletter box: one text box and one button. Nothing needs explaining.
2. It needs this lesson's idea: four different pictures from one box and one button.
3. The broken result is big: the red error line and `Welcome to the list!` on the page together.
4. Actions are typing and clicking `Join`.
5. The error needs no server: an email without `@` is wrong, a rule everyone knows.
6. The computer input is one `setTimeout`, already taught in Lesson 15. No promise, no `async`, no `try`.
7. Helper words are few: `includes` and `style.display`.

**Other pages considered**:
1. *The syllabus card's members-only sign-up with a name and a server*: rejected. Two fields and a fake server built on a promise bring in `async`, `await`, `try`, `catch`, and `finally` before the idea starts. The map skill names this as a counter-example.
2. *The React docs' city quiz*: rejected for the same reason: its answer check is a fake network request built on a promise.
3. *A Like button that turns red*: rejected. Only two pictures, so one true/false value is enough and `status` has no job.
4. *The contact form of Lesson 20*: rejected. Five fields would hide the four pictures, and the reader would meet a page chosen for another lesson.
5. *A photo upload box*: rejected. File inputs and upload progress are helper words with no link to state.

**Older facts the reader needs**:
- Imperative code gives step-by-step commands to the DOM; declarative code describes the finished page, and React updates it: Lesson 01.
- `document.getElementById` finds an element by its `id`: Lessons 01 and 07.
- A prop arrives inside the component from the tag, such as `status="error"`: Lesson 08.
- A default value in the parameter list, `{ status = 'typing' }`, is used when the tag gives no value: Lesson 09.
- `if (...) return ...` before the main JSX, and `condition && <p>...</p>` inside JSX: Lesson 10.
- `<form onSubmit={...}>` with `e.preventDefault()` stops the browser from reloading the page; `addEventListener` is the plain JavaScript way to attach a handler: Lesson 11.
- `useState` keeps a value between renders, and the setter asks React to render again: Lesson 12.
- On a new render, React changes only the DOM nodes that differ from the last render: Lesson 13.
- `setTimeout(fn, ms)` runs a function later, after a number of milliseconds: Lesson 15.
- `style={{ color: 'red' }}`: Lesson 03.
- A controlled box with `value={email}` and `onChange={e => setEmail(e.target.value)}`, and `.length` of a string: Lesson 20.

## Principles

### Principle 1: Each `status` Draws One Picture of the Form

- **Rule**: Before writing any handler, list every picture the user can see, give each one a name, and write the JSX for each picture from one `status` value.
- **Move**: Smallest code first, because the idea is new and needs no project file. Everyday image for the term *state machine*, because the word sounds academic.
- **Opening Essence**:
  - Smallest code: `function Signup({ status = 'typing' }) { if (status === 'success') return <p>Welcome to the list!</p>; return <button>Join</button>; }`, with `<Signup />` and `<Signup status="success" />` on one page.
  - Everyday image for *state machine*: a traffic light. It shows one light at a time, red, yellow, or green. It is never red and green together. Each light is drawn in advance; a timer or the walk button only picks which one is on.
  - A second image from the React docs: a designer draws one mockup for each picture before any logic.
  - No real look-alike pair here. Key idea: the pictures come first, the clicks come later. Stake: a picture never drawn can never show. Where readers go wrong: they start from the click and ask what it should hide.
- **Root Distinction**:
  - Junior: "The form is one screen, and my clicks change bits of it."
  - Senior: the form is a few complete pictures; the code draws each picture once, and a click only picks one.
- **Simplest version**:
  - `function Signup({ status = 'typing' })`
  - `if (status === 'success') return <p>Welcome to the list!</p>;`
  - `return <button>Join</button>;`
  - `<Signup />` shows `Join`. `<Signup status="success" />` shows `Welcome to the list!`.
- **Words to teach**:
  - *visual state*: one complete picture the user can see. React's docs use the term. Needed at the start, when the reader lists the four pictures of the newsletter box.
  - `status`: our own name for the value that says which picture is current. The React docs: "You could call that prop anything you like, the naming is not important." Needed when the first `if` is written.
  - *state machine*: a thing that is always in exactly one of a few named states. The React docs take the term from computer science. Needed once, with the traffic light.
  - *mock*: a drawing of each picture before any logic. The React docs: "Mocking lets you quickly iterate on the UI before you wire up any logic." Needed when App shows all four pictures at once.
  - `disabled`: a true/false attribute from the browser, passed through by React. `input.md`: "A boolean. If `true`, the input will not be interactive and will appear dimmed." Needed for the `'submitting'` picture, where the box and `Join` turn grey.
  - Known: props, Lesson 08. Default value in the parameter list, Lesson 09. Early `return` and `&&`, Lesson 10. `style={{ color: 'red' }}`, Lesson 03.
  - Helper: none.
- **Side by side**: none. The four pictures are listed one under another, not compared.
- **Surprises**: none. Each tag shows exactly the picture its `status` names.
- **Where did that come from?**:
  - `status` inside `NewsletterSignup`, never set inside the component: App supplies it on the tag.
    1. App writes `<NewsletterSignup status="error" />`.
    2. React puts `"error"` into the props object.
    3. The parameter list unpacks it as `status`.
  - `'typing'` when the tag has no `status`: the default value in the parameter list supplies it, Lesson 09.
- **Real beginner mistake**: none specific to this step. The real mistakes of this lesson come in Principles 3 and 4.
- **Interview depth**:
  - The React docs list five steps: identify the visual states, determine the triggers, represent the state with `useState`, remove non-essential state, connect the event handlers.
  - Showing every picture on one page is called a "living styleguide" or "storybook", in the React docs' words.
  - The `'success'` picture uses an early `return`; the other three share one JSX tree. The docs' challenge solution: when two JSX branches describe the same tree, their nesting must line up, or React rebuilds the tree below and resets its state. Lesson 25 owns this.
  - The React docs call React "the intersection of design and computer science": mockups from design, the state machine from computer science.
- **React does**:
  - Page: four copies of the box, one per picture, each under its own label. `unconfirmed`, the lab checks it.
  - Page: in the `'submitting'` picture, the box and `Join` look grey and do not respond. The box part is quoted from `input.md`: "will not be interactive and will appear dimmed". The button part: `unconfirmed`.
  - Elements panel: the grey box shows a `disabled` attribute, such as `<input disabled="">`. `unconfirmed`.
  - Elements panel: the `'success'` copy holds only the welcome line, with no `<form>`. `unconfirmed`.
  - Console: no message. `unconfirmed`.
  - Clicking `Join` inside the mock reloads the page, because the mock form has no `onSubmit` (Lesson 11). `unconfirmed`. The mock is for looking, not clicking.
- **Example step**: creates `src/components/NewsletterSignup.jsx` with `export default function NewsletterSignup({ status = 'typing' })`. It returns `<p>Welcome to the list!</p>` when `status === 'success'`. Otherwise it returns a `<form>` with `<h2>Join our newsletter</h2>`, `<input disabled={status === 'submitting'} />`, `<button type="submit" disabled={status === 'submitting'}>Join</button>`, `{status === 'submitting' && <p>Sending...</p>}`, and `{status === 'error' && <p style={{ color: 'red' }}>Please enter a full email address.</p>}`. `src/App.jsx` renders four tags: `<NewsletterSignup status="typing" />`, `<NewsletterSignup status="error" />`, `<NewsletterSignup status="submitting" />`, `<NewsletterSignup status="success" />`, each under an `<h4>` with the status name.
- **Code names**: `NewsletterSignup.jsx`, `App.jsx`, `NewsletterSignup`, `Signup`, `status`, `'typing'`, `'error'`, `'submitting'`, `'success'`, `{ status = 'typing' }`, `disabled`, `disabled={status === 'submitting'}`, `Join our newsletter`, `Join`, `Sending...`, `Please enter a full email address.`, `Welcome to the list!`, `<h4>`, `style={{ color: 'red' }}`

### Principle 2: Clicks and a Timer Only Set `status`

- **Rule**: Keep `status` in state. Each input, from the user or from the computer, calls `setStatus` with the name of the next picture, and the JSX from Principle 1 stays the same.
- **Move**: Side by side for the opening, because the prop version and the state version look different but draw the same picture. Steps for a surprise for the red line that goes away with no line of code hiding it.
- **Opening Essence**:
  - Smallest code: `<Signup status="error" />` next to `const [status, setStatus] = useState('typing');` and a click that runs `setStatus('error')`.
  - Confusion to say out loud: *"Yes, it is the exact same thing!"* The JSX does not change. Only the place where `status` comes from changes: from the tag, or from state.
  - Everyday image: the traffic light again. The walk button is a human input; the timer inside the light is a computer input. Both only switch which light is on.
- **Root Distinction**:
  - Junior: "The Join handler must show the sending line, then hide it, then show the welcome line."
  - Senior: the handler only names the next picture; React draws it from the JSX already written.
- **Simplest version**:
  - `const [status, setStatus] = useState('typing');`
  - `if (status === 'success') return <p>Welcome to the list!</p>;`
  - `return <button onClick={() => setStatus('success')}>Join</button>;`
  - Clicking `Join` replaces the button with `Welcome to the list!`.
- **Words to teach**:
  - *human input*: something the user does, such as typing in the box or clicking `Join`. React's docs term. Needed when the reader lists what changes each picture.
  - *computer input*: something that happens without the user, such as "a network response arriving, a timeout completing, an image loading", in the docs' words. Needed when the timer moves `'submitting'` to `'success'`.
  - The arrows between pictures: the docs suggest drawing "each state on paper as a labeled circle, and each change between two states as an arrow". Needed for the figure of the four pictures and their arrows.
  - Known: `useState` and the setter, Lesson 12. `<form onSubmit>` and `e.preventDefault()`, Lesson 11. `value` and `onChange`, Lesson 20. `setTimeout`, Lesson 15. `.length`, Lesson 20.
  - Helper: `includes`, true when the text contains the given letters. Half a sentence.
- **Side by side**:
  - With `status` from the tag, `<NewsletterSignup status="error" />`, and with `status` from state, `setStatus('error')`: the exact same thing. The same JSX draws the same red line; only the source of `status` differs.
- **Surprises**:
  - The red line goes away when the user clicks `Join` with a full email, though no line of our code hides it:
    1. The user typed `mary` and clicked `Join`, so `status` is `'error'` and the red line shows.
    2. The user types `mary@mail.com` and clicks `Join` again.
    3. `handleSubmit` runs `setStatus('submitting')` and starts a timer. It never touches the red line.
    4. React renders `NewsletterSignup` again with `status` as `'submitting'`.
    5. `status === 'error'` is now false, so the JSX holds no red line.
    6. React removes the red `<p>` from the page and shows `Sending...`, as Lesson 13 described.
  - One second later, the whole form is replaced by `Welcome to the list!`, though the user did nothing:
    1. The timer started in step 3 finishes after 1000 milliseconds.
    2. Its function runs `setStatus('success')`.
    3. React renders again, and the early `return` gives only the welcome line.
- **Where did that come from?**:
  - `status` now comes from `useState`, not from the tag. App renders `<NewsletterSignup />` with no prop.
  - `e` in `handleSubmit(e)`: React supplies it, Lesson 11.
  - The removal of the red line: React supplies it, as in the steps above.
- **Real beginner mistake** (the Lesson 11 rule, met again on this form):
  1. The developer writes `handleSubmit` without `e.preventDefault()`.
  2. The user types `mary@mail.com` and clicks `Join`.
  3. The browser reloads the page.
  4. The box is empty again, the picture is `'typing'`, and `Welcome to the list!` never shows.
  5. The developer adds `e.preventDefault()` as the first line of `handleSubmit`.
  6. After a reload, `Join` shows `Sending...`, then `Welcome to the list!`.
- **Interview depth**:
  - React's docs: "In both cases, you must set state variables to update the UI."
  - React's docs: "Notice that human inputs often require event handlers!"
  - The arrows of this form: typing to error (Join without `@`), typing to submitting (Join with `@`), error to error, error to submitting, submitting to success (timer).
  - `Join` is off while the box is empty, computed from `email.length === 0`, so no `'empty'` status is needed. The React docs remove `isEmpty` the same way. Lesson 22 owns the full rule.
  - In a real app the timer is a network response; fetching with loading and error states belongs to Lesson 33.
  - React 19 form actions give a built-in pending flag: Lessons 41 to 43, named only.
- **React does**:
  - Page: the red line disappears on the second `Join`, `Sending...` shows for about one second, then only `Welcome to the list!` remains. `unconfirmed`.
  - Page: while `status` is `'submitting'`, the box and `Join` are grey. Box part quoted from `input.md`; button part `unconfirmed`.
  - Page: `Join` is grey while the box is empty. `unconfirmed`.
  - Elements panel: the red `<p>` node is gone during `'submitting'`, not hidden with a style. `unconfirmed`.
  - Without `e.preventDefault()`: the page reloads and the box is empty. `unconfirmed`.
  - Console: no message. `unconfirmed`.
- **Example step**: in `NewsletterSignup.jsx`, the `status` prop is removed. Adds `const [email, setEmail] = useState('');` and `const [status, setStatus] = useState('typing');`. The box becomes `<input value={email} onChange={e => setEmail(e.target.value)} disabled={status === 'submitting'} />`. The button becomes `<button type="submit" disabled={email.length === 0 || status === 'submitting'}>Join</button>`. Adds `<form onSubmit={handleSubmit}>` and `handleSubmit(e)`: `e.preventDefault()`; if `email.includes('@')`, then `setStatus('submitting')` and `setTimeout(() => { setStatus('success'); }, 1000)`; otherwise `setStatus('error')`. `src/App.jsx` now renders one `<NewsletterSignup />`.
- **Code names**: `NewsletterSignup.jsx`, `App.jsx`, `email`, `setEmail`, `status`, `setStatus`, `useState('typing')`, `useState('')`, `handleSubmit`, `e.preventDefault()`, `email.includes('@')`, `setTimeout`, `1000`, `email.length === 0`, `mary`, `mary@mail.com`, `Sending...`, `Please enter a full email address.`, `Welcome to the list!`

### Principle 3: DOM Commands Leave Two Messages on the Page

- **Rule**: When code shows and hides lines by command, every branch must hide every line that should go; with `status`, each picture is described once, so an old line cannot stay.
- **Move**: Side by side, because the DOM command and the state change look like they do the same job on the first try and behave differently on the second.
- **Opening Essence**:
  - Smallest code: `error.style.display = '';` next to `setStatus('error');`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* After the first wrong try, both show the red line. After the next right try, only the DOM version still shows it.
  - Name what they share first: both change what the page shows after a click. Then the one difference: who edits the page.
- **Root Distinction**:
  - Junior: "The red line is a thing I showed, so I must remember to hide it later."
  - Senior: the red line belongs to one picture; when the picture changes, the line goes with it.
- **Simplest version**:
  - Plain JavaScript: `error.style.display = '';` shows the line; `error.style.display = 'none';` hides it.
  - React: `setStatus('error');` with `{status === 'error' && <p>...</p>}`.
- **Words to teach**:
  - `style.display = 'none'`: the browser hides the element. `style.display = ''`: the browser shows it again. The React docs' plain JavaScript form uses exactly these two lines in its `hide` and `show` functions. Needed to read the plain version.
  - Known: imperative and declarative, Lesson 01. `document.getElementById`, Lessons 01 and 07. `addEventListener`, Lesson 11. `e.preventDefault()`, Lesson 11.
  - Helper: `includes`, Principle 2. `.value` of a box in plain JavaScript, the same text as `e.target.value`, Lesson 20.
- **Side by side**:
  - With `error.style.display = ''` and with `setStatus('error')`: NOT the same thing. The DOM command changes one element and leaves every other element as it was; the state change picks a whole picture, and React removes what the picture does not hold.
- **Surprises**:
  - In the plain version, the red line and `Welcome to the list!` show together:
    1. The user types `mary` and clicks `Join`.
    2. The `else` branch runs `error.style.display = ''`, and the red line shows.
    3. The user types `mary@mail.com` and clicks `Join`.
    4. The success branch runs `form.style.display = 'none'` and `welcome.style.display = ''`.
    5. No line runs `error.style.display = 'none'`, so the red line stays.
    6. The page shows `Please enter a full email address.` under `Welcome to the list!`.
- **Where did that come from?**:
  - `e` in `form.addEventListener('submit', e => ...)`: the browser supplies it.
  - `email.value`: the browser keeps the box's text on the element itself.
- **Real beginner mistake** (the syllabus card's friction, and the React docs: "forgetting to show or hide something"):
  1. The developer builds the newsletter box in plain JavaScript in `plain-newsletter.html`.
  2. The handler shows the red line when the email has no `@`.
  3. In the success branch, the developer hides the form and shows the welcome line.
  4. The developer forgets to hide the red line in that branch.
  5. A user tries `mary`, then `mary@mail.com`.
  6. The page shows the red error line and `Welcome to the list!` at the same time.
  7. In the React version, the same two tries show only `Welcome to the list!`, because the `'success'` picture has no red line.
- **Interview depth**:
  - React's docs: imperative code means "you have to 'command' each element, from the spinner to the button, telling the computer *how* to update the UI."
  - React's docs: imperative code "gets exponentially more difficult to manage in more complex systems"; a new element or interaction requires "carefully checking all existing code".
  - With four pictures, DOM commands must handle the change from each picture to each other picture: up to 4 times 3, which is 12 changes. Declarative JSX describes 4 pictures. A fifth picture adds one branch, not a new set of commands.
  - React's docs, the challenge solution: an `updateDOM` function that redraws every element from the current values "shows what React does under the hood when you set the state. (However, React also avoids touching the DOM for properties that have not changed since the last time they were set.)"
  - React's docs: the React version is longer "but it is much less fragile".
  - React's docs' images: imperative is telling a driver every turn; declarative is telling a taxi driver where to go. Lesson 01 already gave its own image, so the lecture needs only a recall.
- **React does**:
  - Page, plain version: red line and `Welcome to the list!` visible together after the two tries. `unconfirmed`.
  - Page, React version: only `Welcome to the list!` after the same two tries. `unconfirmed`.
  - Elements panel, plain version: `<p id="error" style="color: red;">` still in the page with no `display: none`, the form with `style="display: none;"`. `unconfirmed`.
  - Console: no message in either version. `unconfirmed`.

### Principle 4: One `status` String Rules Out an Error Next to `Sending...`

- **Rule**: When pictures cannot appear together, keep them in one `status` string, not in one true/false state per picture, so every handler sets one value and no impossible mix can render.
- **Move**: Side by side, because the true/false version and the string version draw the same four pictures while every handler is right, and differ when one reset is forgotten.
- **Opening Essence**:
  - Smallest code: `const [isError, setIsError] = useState(false);` and `const [isSubmitting, setIsSubmitting] = useState(false);` next to `const [status, setStatus] = useState('typing');`.
  - Confusion to say out loud: *"It may look the same, or work the same at first, but it is NOT the same thing!"* Both versions draw the four pictures when every handler sets every flag. Only the string version cannot be in two pictures at once.
  - Everyday image: the traffic light again. Three separate switches for red, yellow, and green could turn on red and green together; one dial with three positions cannot.
- **Root Distinction**:
  - Junior: "Each message has its own true/false flag, and I turn each one on and off."
  - Senior: the messages belong to pictures that exclude each other, so one value names the current picture.
- **Simplest version**:
  - Two flags: `isError`, `isSubmitting`. Four combinations: both false, only error, only submitting, both true. Both true is a picture no one wants.
  - One string: `status` is `'typing'`, `'error'`, or `'submitting'`. Three values, three pictures.
- **Words to teach**:
  - *impossible state*: a mix of state values that matches no picture the user should see. The React docs: "prevent the cases where the state in memory doesn't represent any valid UI that you'd want a user to see." Needed when the red line and `Sending...` show together.
  - *paradox*: the React docs' word for two flags that can never both be true but are allowed to be. Example from the docs: "`isTyping` and `isSubmitting` can't both be `true`." Needed at the same moment.
  - Known: `useState`, Lesson 12. `&&` in JSX, Lesson 10.
  - Helper: none.
- **Side by side**:
  - With three flags, `isError`, `isSubmitting`, `isSuccess`, and with one `status` string: NOT the same thing. Three flags allow 2 times 2 times 2, which is 8 combinations, for only 4 real pictures; one string allows only the 4 names.
- **Surprises**:
  - With flags, the red error line and `Sending...` show together, and the box is grey:
    1. The user types `mary` and clicks `Join`. The handler runs `setIsError(true)`. The red line shows.
    2. The user types `mary@mail.com` and clicks `Join`.
    3. The handler runs `setIsSubmitting(true)` and starts the timer. It forgets `setIsError(false)`.
    4. React renders with `isError` true and `isSubmitting` true.
    5. The page shows `Please enter a full email address.` and `Sending...` together, and the box is grey, so the user cannot fix what the red line asks to fix.
    6. One second later, `setIsSubmitting(false)` and `setIsSuccess(true)` run, and the early `return` shows `Welcome to the list!`. `isError` is still true in memory.
- **Where did that come from?**: none. Every name is written in the code shown.
- **Real beginner mistake** (`choosing-the-state-structure.md`, "Avoid contradictions in state": "if you forget to call `setIsSent` and `setIsSending` together, you may end up in a situation where both `isSending` and `isSent` are `true` at the same time"):

  2. The Join handler turns on `isSubmitting` for a good email.
  3. The developer forgets to turn off `isError` in that branch.
  4. A user tries `mary`, then `mary@mail.com`.
  5. The red error line and `Sending...` show together, with the box grey.
  6. The developer replaces the three flags with `const [status, setStatus] = useState('typing');`.
  7. Each branch now sets one name, and the two lines can never show together.
- **Interview depth**:
  - React's docs: "each piece of state is a 'moving piece', and you want as few 'moving pieces' as possible. More complexity leads to more bugs!"
  - React's docs: "There are four possible combinations of two booleans, but only three correspond to valid states."
  - React's docs start from seven state variables (`answer`, `error`, `isEmpty`, `isTyping`, `isSubmitting`, `isSuccess`, `isError`) and end with three: `answer`, `error`, `status`. "You know they are essential, because you can't remove any of them without breaking the functionality."

## Interview Points

1. React's way is declarative: describe the UI for each visual state, and switch between states in response to input, instead of enabling, disabling, showing, or hiding elements by command.
2. Step one is to list every visual state the user can see, such as typing, error, submitting, and success, and to draw each one, for example from a `status` prop, before any logic.
3. Step two is to find what changes the state: human inputs such as typing and clicking, and computer inputs such as a network response or a timer.
4. The current visual state lives in `useState`; event handlers only set the next state, and React makes the DOM match.
5. One `status` string beats separate booleans: booleans allow impossible mixes, such as an error and a spinner at once, while a string allows only the listed values.
6. Remove state that adds nothing: an empty box is computed from the text, not stored as its own state. The full rules are the next topic, state structure.
7. Imperative code must handle the change from every state to every other state, and one forgotten hide leaves an old message on screen. Declarative code describes each state once, so a new state adds one branch.
8. For stricter models: `useReducer`, or a state machine library; for forms in React 19, actions with a built-in pending state.
