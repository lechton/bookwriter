# Lecture 37: a case to examine separately

Lecture 37 shows an Effect that runs too often, and how we fix it by changing the code. Its VS opening is hard to write, because the reader must hold three facts at once: when a component renders again, when an Effect runs again, and how React compares two values. Examine this case on its own, before you write the opening of any lecture about an Effect and its dependencies.

## What the opening of this case must do

1. **Ground the process step by step.** Remind the reader of each step, in order. The user types a letter, `onChange` goes off, the handler calls the setter, React renders the component again, and React runs the component body from the top. After the render, React compares each dependency with its old value, and when one is different, React runs the cleanup and then the Effect again. Skip no step, so nothing feels like a mystery.
2. **Basic facts first, then put them together.** First, what happens every time the user writes a letter. Second, what happens every time a dependency of the Effect changes. Only then combine the two.
3. **Full sentences.** Write each step as a full sentence a person would say. Do not shrink it into a label or a shorthand, such as "Every letter renders the component again".
4. **A real example.** Every value in the opening comes from the example on the page: the `options` object is created in the component body from a real `serverUrl` and a real `roomId`. Do not bring in a value from nowhere, such as a `'music'` string the example never showed.
5. **Do not load the whole lesson.** Do not pile up insistent sentences. The opening gives one fix, in bold. The lecture brings the rest.

## The most important role of the introduction

This is arguably the single most operational principle: be philosophical and pedagogical and logical when structuring the text, not technical describing a React topic, a pedagogue that structures the topic logically and philosophically, on how things operate. What part of the code is "safe" or "radioactive". Where we move our code to place it where else? This kind of introduction makes it more easy to grasp, while retaining precision in technical terms on top and in completion of the logical pedagogy of the material.  

The whole role and purpose of introduction is for the junior reader to feels he "gets" what is going on in the chapter, what is the role of the chapter, in fact looking forward on how to learn more about something that is introduced as interesting and important. 

If the intro is vague, unclear or filled with technical details that make little sense, then there is no motivation to continue. 





## BAD (the effort of simplification fails the common intro)

> **We do not delete a dependency the Effect still reads: we change the code so the Effect no longer reads it.**

In React, an Effect sometimes runs more often than it should, like a chat that reconnects while you type, or a request sent again on every render. The dependency array tells React when to run the Effect again, so the first idea is to delete the value that causes the extra runs. But the array is not a setting you pick. It describes what the code reads. **Never delete a dependency the Effect still reads. Change the code so the Effect no longer reads that value.**

Take a chat room where the user types a message into the text box at the bottom. The user never switches rooms, yet every letter makes the chat disconnect and connect again. Ask yourself: what changes on every letter? Not the room. The settings object `options` is built again in the component body on every render, so React sees a new object each time.

**Why:** Every letter renders the component again, and the component body builds a brand-new `options` object, so React thinks the settings changed and restarts the chat. Deleting `options` from the dependency array only hides the bug: the Effect still reads `options`, and it no longer runs again when the room really changes. See the problem? The fix is to move the object inside the Effect, so the Effect depends only on `serverUrl` and `roomId`, and neither of them changes while the user types.

**Note for the AI:** This fails because it loads the whole lesson in a few lines: the dependency array, the wrong fix, the bug, and the right fix. It skips the steps between a typed letter and a reconnect. It never says that `onChange` calls the setter, that the setter makes React render the component again, or that React compares each dependency with its old value. The Why shrinks the process into a shorthand, "Every letter renders the component again", and then pushes the reader with "See the problem?". The leading sentence puts two rules together with a colon.

## ALSO BAD - convoluted 

> **When an Effect runs too often, we change the code, not the list of dependencies.**

**Every time the user writes a letter in a text field, `onChange` goes off**: The `onChange` handler calls the setter of the state variable with the new text, and the setter tells React to render the component again. To render the component again, React runs the component body from the top, so every line of the body runs once more:

> letter typed → `onChange` → setter called → component rendered again

**Every time a dependency of the Effect changes, the Effect runs again:** After each render, React compares each value in the dependency array with its value from the last render. When one of them is different, React first runs the cleanup of the Effect, and then runs the Effect again. Without a dependency array, the Effect runs after every render.

**Enterring new room --> u**: Take a chat room with a message box at the bottom. To connect, the chat needs two pieces of information: the address of the server, this is provided in an object named options which is calculated every time you enter a new room, which updates the chat box that you read. How? By updating the roomId. 

```
const options = { serverUrl: serverUrl, roomId: roomId }; 
```


In plain JavaScript, `'general' === 'general'` is `true`: two strings with the same text are the same value. But two objects written as `{ roomId: 'general' }` are not equal: `===` returns `false`, because each pair of braces creates a new object. React compares dependencies the same way. So every letter the user types renders the component again, the body creates a new `options` object, React sees a different value, and the chat disconnects from `general` and connects to `general` again:

> letter typed → component rendered again → new `options` object → cleanup disconnects → Effect connects again

The user never changed the room, and yet the chat reconnects on every letter. **Create `options` inside the Effect, so the Effect reads only `serverUrl` and `roomId`.** Both are strings, and neither changes while the user types, so the Effect no longer runs again.

## GOOD

> **When an Effect runs too often, we do not need to remove its dependencies: we can define the objects of the dependencies in a "safer place" (inside the Effect itself).**

Why do we need dependencies in the first place? It is a form of indirect control of actions. 

**A form of direct control: an action gives a direct order to a target.** When you click a "Print" button, the button's click handler calls `window.print()`. Cause and effect live in the exact same place: the button knows what it wants to happen and makes it happen on the spot:

> button clicked → handler runs → `window.print()` called directly

**A form of indirect control: an action only changes a value, and an invisible network does the rest.** Imagine a travel page with a city selector at the top, a weather box on the left, a street map in the middle, and a list of hotels on the right. When you pick `'Rome'` from the selector, its handler does not call the weather box, does not move the map, and does not fetch the hotels. The handler only changes a single piece of state: it sets `city` from `'Athens'` to `'Rome'`. Yet a moment later, the weather reloads, the map flies to Italy, and new hotels appear:

> `'Rome'` selected → handler changes `city` → component renders again → weather, map, and hotels see a new `city` and run again

**An invisible world of dependencies:** Nothing in the city selector mentions the weather, the map, or the hotels. Instead, each of those three tasks reads `city` to do its job, which makes `city` their **dependency**. Behind the scenes, an invisible wire connects the value `city` to every Effect that reads it. The selector simply drops a new value into `city`, and every Effect wired to `city` pulls itself into motion:

* `city` changes → **Weather Effect** sees a new `city` → loads Rome's forecast
* `city` changes → **Map Effect** sees a new `city` → centers the map on Rome
* `city` changes → **Hotel Effect** sees a new `city` → fetches Rome's hotels

That is why dependencies feel like invisible forces. When you look at the click handler, you only see `setCity('Rome')`: one line of code that appears to do nothing but store a word. You cannot see what will happen next by reading the button; you have to look at what is *listening* to that word across the component.

**Three places to write code:** 

1. We can write code in an event handler, and it runs only after a click or another event. 
2. We can write code inside an Effect, and it runs after a render, but only when one of its dependencies changed. 
3. And we can write code in the component body. This place is "radioactive"

**The component body is a "radioactive" place:** This part of the code runs, and reruns, and reruns all the time. Every time a setter gets a new value, React renders the component again and runs the component body from the top. So when we create an object there, like `options = { city: city, zoom: 12 }`, we create a new object on every render. Believe it or not, the object is NEW even when no variable has changed: `city` is still `'Rome'`, but the object around it is a different object. What changed is the reference of the object in javascript. Therefore, defining an object in the component code becomes "radioactive" since it constantly appears as a new object, even when nothing has changed. Imagine if you create a dependency, from an object that constantly changes. 

**Where is the catch?** React does not look inside the object. It only asks: "Is this the same object as last time?" So when the map Effect depends on `options`, every keystroke in a text box renders the component again, creates a new `options`, and fires the map Effect again, even though the text box and the map never touch each other.

**The fix is to take the object out of the "radioactive" place and hide it inside the Effect.** Then the only outside value the Effect reads is `city`, and the map reloads only when the user picks a new city.

**Note for the AI:** This works because it first asks why dependencies exist at all, and answers with a contrast anyone can picture: a "Print" button that acts directly, and a city selector that only changes a value while the weather, the map, and the hotels follow. Only then does it name the three places to write code, show why the component body is the "radioactive" place, and give the one fix, in the same words as the leading sentence.

## Notes for the AI: why this case is the benchmark for difficult topics #2026_11_13_06_group_1

This opening took many rounds. Each round failed for a different reason, and each failure showed something the student does not understand. Use this case as the benchmark of quality for any difficult topic: examine what the student does not understand, find the ideas the topic depends on, ask why the thing exists, and examine every part, so that no sentence drops to the ground unexamined.

### 1. Start from what the student does not understand

The student's real question is not "how do I remove a dependency?". It is "why does my Effect run again when I changed nothing?". Behind that question hide three facts the student has not put together: when the component body runs, when an Effect runs, and how React compares two values. The BAD opening assumed the student already knew all three. Before you write, write down the student's question in the student's own words, and check that the opening answers it.

### 2. Find the chain of ideas the topic depends on

A difficult topic is a chain. Each idea needs the one before it. In this case the chain is:

1. A click handler can act directly, like `window.print()`, or only change a value, like `setCity('Rome')`.
2. When a setter gets a new value, React renders the component again.
3. An Effect that reads a value depends on it, and runs again when that value changes.
4. The component body runs again on every render.
5. An object created in the component body is a new object on every render, even when nothing inside it changed.
6. React does not look inside the object. It only asks whether it is the same object as last time.
7. So the fix is to create the object inside the Effect.

If one link is missing, the next sentence drops to the ground: the reader reads it but cannot hold it. List the chain before you write, and check that every link is on the page, in this order.

### 3. Ask the philosophical question first: why does this thing exist?

The GOOD opening asks "Why do we need dependencies in the first place?" before it says anything about a bug. A reader who knows what dependencies are for understands why they can fire too often. Answer the question with a contrast: direct control, where the button acts on the spot, and indirect control, where an action only changes a value and an invisible network does the rest.

### 4. Present a teaching frame as a frame, not as React's own term

"Direct control" and "indirect control" are a way to explain dependencies. They are not React terms. So the opening says "A form of direct control" and "A form of indirect control", not "In direct control" as if React's docs named it. When you bring in a frame of your own, present it as one form of looking at the thing.

### 5. Ground every idea in an everyday page before the chapter's case

The travel page, with a city selector, a weather box, a map, and a list of hotels, is a page anyone recognizes. The ALSO BAD opening used a chat room, and then had to explain a server address, a room name, and an object that holds both, before the real idea could even start. A complicated example on top of a difficult idea makes the idea harder. Choose the simplest page that shows the idea, and keep every value in it: `city`, `'Rome'`, `'Athens'`, and `options` built from `city`. Do not bring in a value from nowhere, such as `{ song: song }` or a `'music'` string.

### 6. Name each place, what it gives, and what it costs

The opening names the three places to write code: the event handler, the Effect, and the component body. For each one it says when the code runs. Then it names the component body as the "radioactive" place: it runs, and reruns, and reruns, so a value calculated there is always fresh, but an object created there is always new.

### 7. Say the surprising fact openly

"Believe it or not, the object is NEW even when no variable has changed." This is the fact the student does not expect, so the opening says it is surprising, and says what really changed: the reference of the object in JavaScript. Do not hide the surprise inside a long sentence.

### 8. Examine every sentence

Read each sentence and ask four questions:

1. Does the reader know every word in it?
2. Does it follow from the sentence before it?
3. Does it say who acts: the user, the handler, React, or the Effect?
4. Is it exactly true?

In this case, three sentences failed the last question and were corrected:

1. "Every time you update a setter, the main code will run." It is exact only when the setter gets a new value. If `city` is already `'Rome'`, `setCity('Rome')` may not render the component again.
2. "Dependencies resting inside this object." The dependency is the object itself, `options`, because the Effect lists it. The value inside it, `city`, is fine.
3. "Build `options` inside the Effect." The owner asked what it meant. A fix the reader cannot picture is not yet a fix. Say where the line moves from, where it moves to, and why the Effect then reads only `city`.

### 9. Write each step as a full sentence, and do not push

The rounds that failed shrank the steps into labels, such as "Every letter renders the component again", and pushed the reader with "See the problem?" or "remember". The GOOD opening writes each step as a sentence a person would say, and lets the arrow lines show the order.

### 10. Keep the owner's text as the owner wrote it

When the owner gives a text for the opening, keep it word for word. Change only what the opening needs, and list each change. In this case, the changes were the leading sentence, the em-dashes, and the music example replaced by the `options` object of the travel page. Rewriting the owner's text from scratch was rejected.

### 11. One leading sentence, one fix, one name for the place

The leading sentence holds the true message: we do not need to remove the dependencies, we can define the objects in a safer place, inside the Effect itself. An earlier leading sentence, "we change the code, not the list of dependencies", was wrong: it named an action without saying what changes or where. The fix at the end says the same thing as the leading sentence. Use one name for each place: the component body is the "radioactive" place, and the Effect is the safer place.

### The benchmark, in some operational steps (not for strict prescription, but for storng inspiration)

Before you write the opening of a difficult topic:

1. Write the student's real question in the student's own words.
2. List the chain of ideas the topic depends on, in order.
3. Find the question of why the thing exists, and answer it with a contrast.
4. Choose the simplest everyday page that shows the idea, and keep every value on it.
5. Examine each sentence with the four questions of note 8.
6. Leading sentences of paragraphs are NPT labels like "A click does this" but as a living experience "When you click this happens". Separate logical blocks, do not confuse them all.
7 Avoid rigid technical steps. If you pay attention above, the example does not makes a strict technical description of the topic, the structure is motly logical, philosophical, pedagogical.
