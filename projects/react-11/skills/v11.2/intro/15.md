## State Setter `setNumber` vs. State Variable `number`: the state setter `setNumber` schedules the next render and leaves `number` at `12`



First, let's set the three building blocks this lesson stands on:

1. **State and its setter** come from `useState`: state is the value React keeps for a component between renders, and the setter, such as `setNumber`, is the function that asks React to update that value (Lesson 12).


2. **A render** is React calling your component function to ask what JSX should appear on the screen. After every setter call, React renders the component again (Lesson 13).


3. **An event handler** is the function that runs only when the user does something on the page, such as clicking a button with `onClick` (Lesson 11).



In plain JavaScript, when you change a variable on one line, the very next line reads the new value.

React state breaks this rule.

Calling `setNumber(13)` does not change the `number` variable inside the function that is currently running. When you call a setter, you are not changing an existing variable. You are only making a request to React: *"The next time you call my component function, pass me `13` instead of `12`."*

React never hands that new value to the code that is already running. It hands the new value only to the **next render**. Every render gets its own fixed copy of state from the moment React called the component, like a photo taken at a single point in time.

React's docs call this fixed copy a **snapshot**, and they give it two rules:

1. **Setting state only changes it for the next render.** In the docs' words, "Setting state only changes it for the next render." Your running code keeps reading the old value until it finishes.


2. **A state variable never changes inside a single render.** In the docs' words, "A state variable's value never changes within a render, even if its event handler's code is asynchronous." Even if your handler waits three seconds inside a timer or waits for a server reply, it still reads the value from the render that created it.



**Beware! Code that reads a state variable right after calling its setter gets the old value, even though the screen is about to show the new one.**

### Render Snapshot `number` Inside `onClick` and `setTimeout`: the render snapshot locks `number` at `12` for the entire render



## What does "fixed inside a render" mean in practice?

Think of a photo. You take a photo of a bakery ticket board while it shows `12`. A second later, the clerk changes the board on the wall to `13`. The wall now shows `13`, but the printed photo you are looking at still shows `12`, and it always will. To see `13`, you must take a new photo.

In a component, "the photo" is the snapshot of values that one render hands to your code:

1. **The state variable `number`.** It holds the value from the exact moment React called your component. If your click handler calls `setNumber(number + 1)` and then reads `number` on the very next line, it reads the old snapshot (`12`), so anything built from `number` falls one step behind.


2. **Every event handler created during that render.** When React runs your component with `number` at `12`, it creates your `onClick` handler with `12` locked inside it. Even if that handler starts a timer that fires three seconds after the click, the timer still reads `12` from that same snapshot, long after the screen has moved on to `13`.



Reading the snapshot is completely fine when you want the value the user saw on screen at the moment of the click, because the snapshot holds that exact value.

### State Variable `number` After State Setter `setNumber`: the handler reads the old state variable `number` at `12` and calls the wrong customer



**Beware! When an event handler sets state and then reads that same state variable on the next line, the screen and the rest of the handler stop agreeing.**

Users click buttons that must do two jobs at once all the time. A `Next` button advances the ticket number and updates an announcement. A `Pay` button adds a tip to the total and sends the charge to the bank. An `Add ticket` button increments a counter and saves the new count to the server. If the second job reads the state variable right after the setter, it uses the old number while the screen displays the new one.

Let's see what reading the old snapshot does to a real page. At a bakery counter, a board on the screen shows the ticket being served, and a loudspeaker line underneath calls the customer to the counter. When the clerk clicks `Next customer`, the click handler does two things:

1. It calls `setNumber(number + 1)` to update the board.


2. On the next line, it calls `setAnnouncement('Number ' + number + ', please come to the counter')` using `number`.



On the first load, the board shows `Now serving: 12`. Then the clerk clicks `Next customer`:

```page width=text caption="After one click on Next customer: the board serves 13, but the loudspeaker calls 12."
heading: Bakery Queue
line: Now serving: 13 | good
line: Number 12, please come to the counter | bad
line: [Next customer]

```

**The page now displays two conflicting numbers.** The board serves `13`, while the loudspeaker line calls `12`. Customer 12, who already bought their bread, walks back to the counter, while customer 13 keeps waiting by the door.

Here is what went wrong, step by step:

1. **React renders the component with `number` at `12`:** The snapshot for this render holds `12`, so the click handler created in this render also holds `12`.


2. **The clerk clicks `Next customer`:** The handler runs and calls `setNumber(12 + 1)`. This asks React to use `13` on the *next* render, but it does not change `number` inside the handler that is already running.


3. **The handler builds the announcement from the old snapshot:** On the very next line, the handler reads `number`, gets `12`, and calls `setAnnouncement('Number 12, please come to the counter')`.


4. **React renders the new screen:** The next render runs with `number` at `13` and `announcement` at `'Number 12...'`. Click again and again, and the loudspeaker stays one customer behind on every single click: `14` on the board, `13` on the loudspeaker.



**This bug hides well.** The main ticket number on the board updates properly on every click. Meanwhile, `console.log(number)` inside the handler prints `12`, which tricks developers into thinking `setNumber` failed or ran too slowly. In a bakery app, the cost is a confused customer. In an online store, the exact same mistake displays the updated cart total on screen while sending the old total to the payment server.

### The Rule of Thumb for State Variable `number` and Local Variable `nextNumber`: the state variable `number` keeps its old value during the click, so save the new value in `nextNumber` first   

**Inside an event handler, a state variable always holds the value from the moment of the click, never the value you just passed to the setter.** React's docs state this rule directly: "React keeps the state values 'fixed' within one render's event handlers."

At the end of the day, a senior developer follows three rules:

1. **Need the new value right away? Store it in a `const` variable first.** In a developer's mind, calling `setNumber(number + 1)` and then reading `number` looks like it does the same job as creating `const nextNumber = number + 1` and reading `nextNumber`: both aim to use "the next customer's number". They are NOT the same! After the setter runs, `number` still holds `12`. Calculate `const nextNumber = number + 1` on the first line, and pass `nextNumber` to both `setNumber(nextNumber)` and `setAnnouncement(...)` so the board and the loudspeaker both receive `13`.


2. **Waiting does not update the variable. Do not wrap the read in a timer.** Wrapping your code in `setTimeout` to read `number` three seconds after the click seems like it should give React time to finish updating. It does not! You started that timer inside the old render's handler, so it stays locked to the old snapshot: it reads `12` after three seconds, and it still reads `12` after ten minutes. Pass `nextNumber` into the timer instead.


3. **If `console.log` prints the old value after a setter, the setter did not fail.** Calling `setNumber(number + 1)` a second time in the same handler will not push the number from `12` to `14`, because both lines read the exact same `12` (`12 + 1` twice is still `13`). Moving `console.log(number)` below the setter changes nothing either, because every line in that handler reads the same snapshot. Log `nextNumber` instead, or place the `console.log` at the top of the component body to see what React passes into the next render.
