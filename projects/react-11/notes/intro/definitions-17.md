# Definitions for Lesson 17: Updating Objects in State

A hierarchy of definitions, from the simplest prerequisite to the one-sentence summary of the whole chapter.

## ☆ An object and a reference

An object is a box in memory with named fields inside it. When you write `const user = { name: 'John', age: 30 }`, JavaScript builds that box, and the variable `user` holds a reference to the box, not a copy of its contents. This is the first fact that makes React state objects behave differently from numbers. A number is a value you hold directly: `0` is `0`, and you cannot open it and change its insides. An object is a container: `user.name = 'Alice'` reaches inside the box and changes one field. Here is the catch: two variables can hold a reference to the same box. If `const sameUser = user` runs, then `sameUser` and `user` point at one object, and changing `sameUser.name` changes what `user.name` shows too. Two objects can also look identical and still be two separate boxes: `{ name: 'Alice' }` written twice creates two boxes with the same contents. Keep the box image in mind for the whole lesson. React never opens the box to compare the fields inside it. It only asks whether the box you handed it is the same box it already holds.

## ☆ State and its setter

In React, state is the value a component keeps between renders, and it always arrives as a pair: the state variable and its setter. For the order card, that pair is `order` and `setOrder`, declared together in one line: `const [order, setOrder] = useState(initialOrder)`. EVERY. SINGLE. TIME. You read `order` during a render, and you call `setOrder` when the order changes. The setter does not merge, and it does not edit the old value. It replaces the old value with whatever you pass. That sounds obvious for a number: `setCount(5)` replaces `0` with `5`. For an object, the same rule is easy to forget. `setOrder({ quantity: 2 })` does not keep the item, the gift wrap, the customer, or the delivery details. The new state is exactly the object you passed, and every field you left out becomes `undefined`. This is why the rest of Lesson 17 spends so much time on building a complete new object. The setter's job is replacement, and your job is to hand it a complete replacement. (Lesson 12)

## ☆ A render and a snapshot

A render is one full call of your component function. You never call the component yourself; React calls it, runs its body from the first line to the last, and works out what the screen should look like from the JSX it returns. React renders on the first load of the page, again after every state change, and again whenever the parent renders. Each render sees a snapshot of state: the values are fixed for that render. Inside one event handler, `order.quantity` does not change under your feet, even after you call `setOrder`. The new value appears only in the next render, when React calls the component again and gives it the new snapshot. Here is the catch that matters for objects: the snapshot holds a reference to the state object, not a deep copy of it. If you mutate the object's fields, you are changing the snapshot that earlier renders still point at. React will not notice, because the reference is the same, but the values behind that reference have changed. That is how a mutation can hide in memory and then appear on the screen during a later, unrelated render. (Lessons 13 and 15)

## ☆ An event handler

An event handler is the function you attach to a user action, such as `onClick` or `onChange`. You write it, React calls it when the user acts, and it runs from top to bottom. In the order card, `handleAddOne` is the event handler for the `+1` button. It does not run when the page loads. It waits until the shopper clicks, and then it runs once for that click. Here is the catch: the screen does not update line by line while the handler runs. React waits until the whole handler has finished, and only then does it apply the queued state updates and render the component again. That is why a long handler with an `alert` can leave the screen showing old values behind the pop-up. The handler is still running, so the render has not happened yet. When you read the order card code, read every handler as one complete unit: all the lines run first, and the screen catches up at the end. (Lesson 11)

## ☆ Batching and the update queue

Batching is React's habit of grouping the state updates from one event handler into a single render. If a handler calls two setters, React does not render after the first call and again after the second. It waits for the handler to finish, collects the updates, and renders once. For each state variable, React keeps a waiting line called the update queue. Every setter call drops one more update at the back of the line. After the handler finishes, React walks that line from first to last, in the exact order you called the setters, and works out the next state. Two separate clicks are never batched together: the first click finishes its render before the second click runs. Here is the catch: the queue is a line of updates, not a line of screen changes. Nothing reaches the screen until the handler is done and React walks the queue. That is why a mutation inside the handler can pile up silently while the card still shows the old quantity. (Lesson 16)

## ☆ An updater function

An updater function is the second way to call a state setter. Instead of passing a value, you pass a function: `setOrder(o => ({ ...o, quantity: o.quantity + 1 }))`. React calls that function with the pending state, the value the state will have after the updates already in the queue, and uses whatever the function returns as the next state. This is how several updates to the same state stack up correctly in one click. A plain value is calculated immediately from the snapshot, so three calls with `order.quantity + 1` all read the same old quantity. An updater function waits its turn in the queue and builds on the result before it. Here is the catch that trips people up: the arrow function returns an object, so the object needs parentheses around it. `o => ({ ...o, quantity: o.quantity + 1 })` returns the new object. Without the parentheses, `o => { ...o }` looks like the start of a function body, and JavaScript complains or returns nothing useful. (Lesson 16)

## ☆ Object spread

Object spread is the three dots that open an object and copy its fields into a new object. `{ ...user, city: 'Paris' }` takes every field of `user`, copies it into a brand-new object, and then writes `city: 'Paris'` after the copy. The old `user` object is untouched. The new object is a separate box. JavaScript reads an object literal from left to right, and when the same property name appears twice, the one that comes last wins. So `{ ...user, city: 'Paris' }` ends with `city: 'Paris'`, while `{ city: 'Paris', ...user }` ends with the old city from `user`, because the spread comes last and copies the old value over the new one. Here is the catch: spread copies only the top level of properties. It is a shallow copy, not a deep copy. If `user` has a nested object such as `address`, the new object gets a reference to the same `address` box, not a new copy of it. Keep that in mind for Principle 3. (Plain JavaScript)

## ☆ A computed property name

A computed property name is a property name calculated from a variable at runtime. Inside an object literal, square brackets tell JavaScript to evaluate the expression inside them and use the result as the property name. If `const key = 'city'`, then `{ [key]: 'Paris' }` creates `{ city: 'Paris' }`. Without the brackets, `{ key: 'Paris' }` creates a property literally named `key`, which is not what you wanted. This is the plain JavaScript tool behind the one-handler pattern in Principle 4. An input tag can carry a `name` attribute, and the browser reports it on the event object as `e.target.name`. The typed text is `e.target.value`. When you write `{ [e.target.name]: e.target.value }`, JavaScript reads the input's name, such as `customer` or `note`, and uses that string as the property name. One object literal can then update whichever field the shopper touched. Here is the catch: the string inside the brackets must match the state field exactly. A name of `customerName` creates a new property named `customerName` and leaves `order.customer` alone. (Plain JavaScript, plus the browser's event object)

## ★ A state object

A state object is one state variable that holds several related fields together. In the order card, `order` is a state object with fields for the item, the quantity, the gift wrap, the customer, the delivery address and time, and the courier note. Keeping them together is natural: they describe one order, and they change together as the shopper edits the card. The setter replaces the whole object, so every update has to carry the other fields forward. That is the trade: you get one clean group instead of six separate state variables, but you must build a complete new object on every change. A state object is not automatically read-only. JavaScript will let you write `order.quantity = 2`, and React will not throw an error. The next definitions explain why that line is a trap and what to do instead. (Lesson 17)

## ★ Read-only state

Treat every object in state as read-only. Think of a printed store receipt: you read every line, and you never scribble over the ink to change the total. When the order changes, the cashier prints a brand-new receipt. In React, the same rule applies. You read `order.quantity` and `order.customer` during a render. When a field changes, you do not write inside the old object. You build a brand-new object with the new value and pass that new object to `setOrder`. This is not a JavaScript rule; JavaScript happily lets you mutate an object. It is a React rule, and React does not enforce it with an error. If you break it, the screen may stay frozen with zero warnings in the Console, and the change may jump onto the screen later during an unrelated update. Read-only state is the discipline that prevents that silent class of bug. Every principle in Lesson 17 is a practical way to follow it. (Lesson 17, Principle 1)

## ★ Mutation vs. replacement (Principle 1)

This is the core distinction of the whole lesson. A mutation changes the inside of the existing box. A replacement builds a new box and hands it to React. Suppose the order starts at quantity one. Mutation does this: `order.quantity = order.quantity + 1; setOrder(order);`. The first line changes the field inside the existing object. The second line passes that exact same object back to React. Replacement does this: `setOrder({ ...order, quantity: order.quantity + 1 });`. The spread builds a brand-new object, and React receives a different box. React compares the old state and the new value with `Object.is`, which asks whether both sides are the same box in memory. It never looks inside the curly braces. For the mutation, `Object.is(order, order)` is true, so React skips the render. For the replacement, `Object.is(oldOrder, newOrder)` is false, so React renders. Here is the bug in action on the order card. The shopper clicks `+1` twice. Each click mutates `order.quantity` inside the same object and passes it back. The card still says `Quantity: 1`, and the Console shows nothing. The quantity in memory is already three. Then the shopper clicks `Add gift wrap`. That handler builds a brand-new object and copies `order.quantity`, which is now three. React sees a different box, renders, and the quantity jumps from one straight to three. Nothing was lost and nothing was magically recovered: the two mutations were sitting in memory the whole time, hidden behind the same reference. The fix is always the same: do not write inside the old object; build a new object with the changed field and pass that. (Lesson 17, Principle 1)

## ★ Object spread inside a state update (Principle 2)

Once you know you must pass a new object, object spread becomes your everyday tool. The pattern is `setOrder({ ...order, quantity: order.quantity + 1 })`. Read it from left to right. First, `...order` copies every existing field into a new object. Then `quantity: order.quantity + 1` writes the changed field after the copy, so it wins. Because the setter replaces the whole object rather than merging, the spread is what keeps the item, the gift wrap, the customer, the delivery, and the note alive. There are two classic ways to get this wrong. First, leave a field out. If the gift wrap handler runs `setOrder({ item: order.item, quantity: order.quantity, giftWrap: true })` and forgets `customer`, the new state has no customer field. The card shows `For:` with nothing after it, and the Console is silent. Second, put the change before the spread. `setOrder({ giftWrap: true, ...order })` writes the new value first, then copies the old `giftWrap: false` over it. The card stays on `Gift wrap: No`, even though the handler clearly says true. The rule is short: spread first, change last. When several updates to the same object are queued in one click, put the same spread inside an updater function: `setOrder(o => ({ ...o, quantity: o.quantity + 1 }))`, with parentheses around the object so the arrow returns it. (Lesson 17, Principle 2)

## ★ A shallow copy (Principle 3)

Object spread looks like it copies the whole object, but it copies only the top level. That is why it is called a shallow copy. Imagine the outer `order` box holds a key to another box called `delivery`. When you write `const next = { ...order }`, JavaScript builds a new outer box and copies every field into it. For the `delivery` field, it copies the key, not the room. `next.delivery` and `order.delivery` now point at the very same inner box. This is fine as long as you never change the inner box. It becomes a trap the moment you do. Suppose the evening delivery handler does this: `const next = { ...order }; next.delivery.time = 'Evening'; setOrder(next);`. The top-level object is new, so React renders, and the card shows Evening. It looks like it worked. But the line `next.delivery.time = 'Evening'` changed the shared inner delivery box. If `initialOrder.delivery` points at that same box, the starting order has changed too. Later, the shopper clicks `Start over`, which runs `setOrder(initialOrder)`. The quantity returns to one, but the delivery line stays on Evening, because the original delivery box no longer holds Morning. No line in `handleStartOver` wrote Evening. The mutation did, through a shared reference. That is the shallow-copy trap: the top object is new, but the nested object is still the old one. (Lesson 17, Principle 3)

## ★ Copying every level on the path (Principle 3)

The fix for a nested change is to copy every object on the path from the changed field up to the root. For the delivery time, that means two copies: `setOrder({ ...order, delivery: { ...order.delivery, time: 'Evening' } })`. Read it from the inside out. The inner `...order.delivery` builds a brand-new delivery box, copies the existing address into it, and sets `time: 'Evening'`. The outer `...order` builds a brand-new order box, copies every top-level field, and points `delivery` at the new inner box. The original delivery box inside `initialOrder` is never touched, so it keeps Morning. Notice that the word `address` does not appear anywhere in that line. The inner spread carries it. That is the point of spreading every level: you only write the field that changes, and every other field comes along automatically. After this fix, the shopper can click `Deliver in the evening`, then `+1` twice, then `Start over`, and both the quantity and the morning delivery return. The rule generalizes: for a change three levels deep, spread three times, one for each object on the path. If the nesting gets so deep that the spreads become hard to read, teams either flatten the state or use a helper library such as Immer. (Lesson 17, Principle 3)

## ★ A computed property name inside a state update (Principle 4)

This is the pattern that lets one handler serve many inputs: `setOrder({ ...order, [e.target.name]: e.target.value })`. The spread copies every existing field. The square brackets evaluate `e.target.name`, which is the `name` attribute of the input that fired, and use that string as the property name. The value is the text the shopper typed. When the customer box fires, `e.target.name` is `customer`, so the object updates `customer`. When the note box fires, the same handler updates `note`. You do not need a separate `handleNameChange` and `handleNoteChange`. The pattern has two conditions. First, every input needs a `name` attribute that matches its field in the state object, character for character. Second, the input should display the matching state value, such as `value={order.customer}`, so the box and the state stay in sync. Here is the trap when the names do not match. Suppose the name box says `name="customerName"` while the state field is `order.customer`. On every keystroke, the handler writes a new property called `customerName`. `order.customer` never changes. The input still displays `order.customer`, so React reverts the box to Anna Lee after every keystroke. The typed letters refuse to stay, the card never updates, and the Console shows zero warnings. The fix is not in the handler; it is in the input tag: make the `name` match the state key. (Lesson 17, Principle 4)

## ★ One handler for many inputs (Principle 4)

A single `handleChange` replaces a pile of near-identical handlers. Without it, a form grows one function per box: `handleNameChange` updates `customer`, `handleNoteChange` updates `note`, and so on. Copy and paste makes the second function easy to write and easy to get wrong. The classic bug is a pasted handler that still updates `customer`; typing in the note box then overwrites the customer name, while the note stays empty and the note box reverts on every keystroke. With one handler, the input itself says which field changed: `setOrder({ ...order, [e.target.name]: e.target.value })`. The handler does not need to know any field names. It reads the name from the event and updates that field. The pattern is safe only when every input's `name` matches a real state key and every input is controlled by the matching state value. One shared handler is not magic; it is a contract between the input tags and the state object. Keep the names exact, and the contract holds. (Lesson 17, Principle 4)

## ★ The whole chapter in one definition

State can hold an object. Treat that object as read-only: read its fields, never write inside it. React compares the object you pass to the setter with the object it already holds using `Object.is`, which asks whether both sides are the same box in memory, not whether their fields look alike. Mutating the existing box and passing it back keeps the same reference, so React skips the render; the change hides in memory until an unrelated update reveals it. Replacing the box with a brand-new object makes `Object.is` false, so React renders. Because the setter replaces the whole object rather than merging, spread the old object first and write the changed field last, so no field is lost and the change wins from left to right. Spread is shallow, so a nested object is still the same inner box; copy every level on the path from the change up to the root. For a form with many fields, give each input a `name` that matches its state key and use one handler with `[e.target.name]: e.target.value`. The chapter in one sentence: treat state as read-only, replace the box, spread first and change last, copy every level on the path, and let the input's name choose the field. (Lesson 17)
