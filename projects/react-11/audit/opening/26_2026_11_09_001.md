# Audit of Lecture 26 Opening (`01-02-md-LECTURES/v1/26.md`)

## 1. Verdict

**Verdict:** `change`

The opening starts from a designer handing the developer a silent drawing with no user action or screen change, drops `App.jsx`, `useState`, handlers, and five documentation terms in abstract language before the reader sees the cafe menu work, and uses a four-sentence house-building scene (walls, lamps, switches, and wires) that unlocks no technical word.

## 2. Form of Move 1 Used

The opening uses the **plain-words** form of Move 1 (`### Where to start when a designer hands us a mockup` and `### What is at stake`). Because the lesson teaches the shape of a way of working (React's five-step *Thinking in React* order for building a page from a mockup: component hierarchy, static version with props only, minimal state, closest common parent, and inverse data flow) and no short code shows that five-step order with an immediate surprise on its own, opening in plain words on a real screen before any code is the required form under Move 1 and Example 9 of `skills/v10.6/opening-essence/SKILL.md`.

## 4. Plan for the New Opening

- **Real screen and user action (Points 1 and 2):** Keep one screen across the opening and the lesson (`skills/v10.6/lecture/SKILL.md`, *One real screen, one idea*): open directly on the **drinks menu of a cafe website** with a search box at the top, an `Only show drinks in stock` tick box, and a short list of drinks below (`Coffee`, `Tea`, `Hot chocolate Sold out`, `Lemonade`, `Iced tea Sold out`). Show one action by the user and what changes on screen in plain words:
  1. The user types `tea` into the search box.
  2. `Coffee`, `Hot chocolate`, and `Lemonade` disappear, leaving only `Tea` and `Iced tea Sold out`.
  3. When the user also ticks `Only show drinks in stock`, the sold-out `Iced tea` disappears too, and only `Tea` stays.
- **The question and immediate answer (Point 3):** Introduce the word **mockup** right on that screen: a designer hands you a drawing of this finished cafe menu, called a **mockup**, before a single line of code exists. Ask the one question that screen raises for the developer: when the user types and ticks in the search bar at the top and the drink list below must update to match, where do you start building the page? Answer at once: you do not start from what the user types. You build everything on the page that does not change first, and only add the changing state after the whole page is on the screen.
- **The React pieces on that screen and the `tree` figure (Point 4):** Contrast the two ways to start on that cafe menu screen, naming every React piece directly on the cafe menu:
  1. **Starting from what the user does:** opening `App.jsx`, adding a `useState` and a handler for the search box first, and growing the page around them one piece at a time as each piece comes to mind.
  2. **The React way (*Thinking in React*):** following five steps in a fixed order on this cafe menu:
     - **Step 1 (Component hierarchy):** Draw boxes on the cafe menu mockup and turn each box into a component: the menu (`MenuPage`), the search area (`SearchBar`), the drink list (`DrinkList`), and one drink row (`DrinkRow`).
     - **Step 2 (Static version):** Build the menu from the drinks data with `props` only and no state, so all five drinks and the boxes appear on screen, but typing changes nothing yet.
     - **Step 3 (Minimal state):** Look at the values on the menu and keep as state only the two values the user changes that cannot be computed from anything else: the search text (`filterText`) and the tick (`inStockOnly`), never the filtered list of drinks.
     - **Step 4 (Where state lives):** Put both pieces of state in `MenuPage`, the closest common parent above both `SearchBar` and `DrinkList`.
     - **Step 5 (Inverse data flow):** Pass the state setters down into `SearchBar` so typing in the search box or clicking the tick box updates `MenuPage`'s state from `onChange`.
  3. Keep the reassurance that the five steps bring no new tool (**"Yes, it is the exact same toolbox you already know!"** with the five-lesson mapping), the React docs quote on why the order matters (`"Building a static version requires a lot of typing and no thinking, but adding interactivity requires a lot of thinking and not a lot of typing."`), the `tree` figure (`The five steps from a mockup to a working page`), and the distinction from Lesson 21's five steps for one component.
- **Everyday image to unlock one word (Point 5):** Remove the four-sentence house-building scene (`plan`, `walls`, `lamps`, `switches`, `wires`), which unlocked no technical word. As `01-01-map-principles/v1/26.md` line 462 notes, the docs' own physical action of drawing boxes with a pen on the printed mockup already grounds **mockup** and **component hierarchy**; if a one-sentence image is wanted for **static version**, compare Step 2 in one sentence to a printed café menu board where every drink and box is visible to read, before wiring the boxes to react to the user.
- **The broken case on that screen / What is at stake (Point 6):** In `### What is at stake`, keep the broken case on the same cafe drinks menu screen, now that the reader has already seen the working menu and its sold-out drinks in Points 1 and 2: a developer who starts from `useState` and handlers at random either stores the filtered drink list as a second state variable or puts `filterText` inside `SearchBar` where its sibling `DrinkList` cannot read it. On the screen, the user ticks `Only show drinks in stock` and `Iced tea Sold out` stays on the list, or the user types `tea` into the search box and all five drinks stay frozen in place. Keep the four places where readers usually go wrong.
- **Bridge sentence to the example page (Point 7):** End the opening with one sentence that bridges directly into `### The page for this lesson: the drinks menu of a cafe` (for example: *"Here is our cafe menu on screen, the data array behind it, and the files we will build across the five steps."*), and trim the duplicate introductory sentences in lines 46 and 61 (`"Our page is the drinks menu of a cafe..."`) so the two browser previews (`page` blocks at lines 48 to 70), the `DRINKS` array, and the `files` panel follow without repeating the prose description of the menu.
