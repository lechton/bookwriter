### Problem 2: Missing the Core Architectural Collision
The opening compares arrays to books with barcodes and mentions pens and photocopiers, but it fails to formulate the foundational architectural conflict that governs state updates in React:
**React's reconciliation engine treats state as immutable and verifies state transitions using reference identity (`Object.is`); mutating an in-memory array in place reuses the existing reference pointer, causing the setter to skip reconciliation and leave the UI completely frozen with zero console warnings, while shallow-copied arrays share inner object references across historical render snapshots and corrupt Undo state.**

When an array is updated in React, developers fall into two distinct mental traps:
- In-place mutation: calling `push`, `pop`, `splice`, `sort`, or `reverse` modifies the array in memory but leaves the reference pointer identical. React's setter checks `Object.is(prev, next)`, sees `true`, and skips rendering entirely.
- Shallow copy leak: spreading an array `[...queue]` produces a new outer array reference (satisfying `Object.is`), but its elements are reference pointers to the exact same objects in memory. Mutating a child object's property directly corrupts all prior snapshots, including historical state kept for Undo.

## The Collision Between In-Place Array Mutation and Identity-Based Reconciliation

### Reference identity vs. in-place mutation: why React rejects push

In plain JavaScript, adding an item to an array is traditionally done by calling `push`:

```jsx title="Adding an item by mutating the array in place"
const names = ['Cara', 'Anna', 'Ben'];
```

In React, state updates rely on reference identity. When an array lives in state, pushing an item into it and handing that same array back to the setter completely fails to update the screen:

```jsx title="Two ways to handle adding 'Dan' to state"
const [names, setNames] = useState(['Cara', 'Anna', 'Ben']);

// Way A: In-place mutation (BROKEN)
function handleAddBroken() {
  names.push('Dan'); // 1. Modifies the array in place
  setNames(names); // 2. Hands the same reference back -> Object.is returns true -> NO RENDER!
}

// Way B: Immutable spread (CORRECT)
function handleAddCorrect() {
  setNames([...names, 'Dan']); // Allocates a brand-new array -> Object.is returns false -> RE-RENDERS!
}
```

Four core confusions trip developers up whenever an array lives in state:
1. **Calling `push` and spreading `[...names, 'Dan']` both leave four names in memory, but they are NOT the same thing to React.** Pushing modifies the existing array in place and hands React the exact same reference pointer it already holds. Spreading allocates a brand-new array in memory and hands that new reference to React.
2. **Arrays look different from plain objects because they have brackets and numbered slots, but React treats them as identical object references.** React never inspects an array's contents during a setter call. It performs an instant `Object.is(prev, next)` check on the outer container. Because `names` and `names` share the same memory pointer, React assumes nothing changed and aborts reconciliation.
3. **The method names `slice` and `splice` differ by only one letter, but they behave in opposite ways.** In everyday life, to splice means cutting and taping into the original film reel; in JavaScript, `splice` cuts and mutates the source array in place. To slice means taking a piece to keep; in JavaScript, `slice` copies part of the array into a brand-new array, leaving the original intact.
4. **Calling `sort` or `reverse` returns the sorted list, but it does NOT return a new array.** Both methods rearrange the original array in place and return that exact same mutated reference pointer.

To navigate JavaScript array methods without confusion, separate them into two distinct operational classes:
1. **Mutating operations (The Pen)**: `push`, `unshift`, `pop`, `shift`, `splice`, `sort`, `reverse`, and index assignment (`arr[i] = ...`) modify the existing array in place. Never call them directly on state arrays.
2. **Non-mutating operations (The Photocopier)**: `[...arr]` spread, `concat`, `filter`, `slice`, and `map` allocate a brand-new array and leave the source array untouched. Always use them to produce next state arrays.

| Operation | Avoid: Mutates Existing Array | Prefer: Returns Brand-New Array |
| :--- | :--- | :--- |
| **Adding** | `push`, `unshift` | `[...arr, item]`, `[item, ...arr]`, `concat` |
| **Removing** | `pop`, `shift`, `splice` | `filter`, `slice` |
| **Replacing** | `splice`, `arr[i] = ...` | `map` |
| **Reordering** | `sort`, `reverse` | `[...arr].sort()`, `[...arr].reverse()`, `toSorted()`, `toReversed()` |

1. Clicking Add to queue, Remove, Play next, or Move up mutates the array in memory, but because `Object.is` sees the same reference, the screen stays frozen on three songs with zero console warnings.
