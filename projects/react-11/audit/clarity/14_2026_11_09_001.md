```markdown
## The Reconciler's Contract: Why React Demands Pure Functions

### Deterministic formulas vs. stateful memory leaks

When you write a React component, you are writing a JavaScript function whose sole responsibility is to return JSX markup describing what should appear on the screen.

React's reconciler calls your component functions repeatedly: on initial application boot, whenever parent state updates, and whenever props change. Because your component function executes again and again throughout the life of a web page, React requires every component to behave as a **pure function**.

What is a pure function? In computer science, a pure function satisfies two strict invariants:
1. **Zero Side Effects**: It minds its own business. It never mutates any variable, array, or object that existed before the function was called.
2. **Referential Idempotency**: Same inputs always produce the exact same output. Calling the function ten times with the identical arguments returns the identical result ten times in a row.

Compare two tiny JavaScript functions that both take a number and return a number:

```js title="A pure function vs. an impure function with external mutation"
// Pure: Deterministic math formula (same input -> same output)
function double(number) {
  return 2 * number; // 1. Uses only its input parameter and mutates nothing outside
}

console.log(double(3)); // First call -> returns 6
console.log(double(3)); // Second call -> still returns 6!

// Impure: Modifies shared module memory outside its call stack
let total = 0;

function addToTotal(number) {
  total = total + number; // 2. Mutates a variable that existed before this call!
  return total;
}

console.log(addToTotal(3)); // First call -> returns 3
console.log(addToTotal(3)); // Second call -> returns 6!
```

**At first glance, `double` and `addToTotal` both accept a number and return a number. They look like the same kind of function, but they are NOT the same thing!**

When you call `double(3)`, the result is `6` every single time, whether you call it once, twice, or a thousand times. When you call `addToTotal(3)`, the first call produces `3` and the second call produces `6`. The output of `addToTotal` depends not only on its input, but on how many times it was previously called. It leaks a side effect into external memory.

React assumes that every component you write is strictly like `double`:

```jsx title="A pure React component: deterministic mapping from props to JSX"
function Greeting({ name }) {
  return <h1>Hello, {name}</h1>; // Pure: given the same name prop, always returns identical JSX
}
```

Whenever React calls `Greeting` with `name="John"`, it must return the exact same heading element. If `Greeting` altered an external counter or mutated an outside array while calculating its JSX, its output would drift across render passes, corrupting the user interface.

```tree caption="Pure functions behave as deterministic formulas; impure functions leak state into outside memory."
Pure functions vs. impure functions with external mutation
- +Pure [`double` and `Greeting`] | **Zero side effects** | **Same inputs, same output**: calling it with `3` or `name="John"` produces the **identical result** every time
- !Impure [`addToTotal`] | **Mutates outside memory** | **Same inputs, different output**: calling it twice with `3` produces **`3` first and `6` second**
```

### Render phase vs. event handlers vs. post-commit effects

If components must stay strictly pure during render, where do real applications modify state, count user clicks, or send analytics pings?

Inside a React component file, code executes across **three distinct runtime phases**:

```jsx title="The three execution phases inside a component file"
function MyPage() {
  const label = 'Dark mode'; // 1. Component Body (Render Phase) -> MUST BE 100% PURE

  function handleToggle() {
    console.log('User clicked'); // 2. Event Handler (Event Phase) -> SIDE EFFECTS BELONG HERE!
  }

  return <button onClick={handleToggle}>{label}</button>;
}
```

Each phase executes under a completely different runtime contract:
1. **The Render Phase (Component Body)**: Lines written at the top level of the component execute synchronously every time React evaluates the component to produce JSX. This code must remain completely pure: it calculates JSX element descriptions from props and state, touches zero outside variables, and mutates zero incoming objects.
2. **The Event Phase (Event Handlers)**: Functions like `handleToggle` execute asynchronously on the browser's event loop only when the user interacts with the page (such as clicking a button). Event handlers never run during render, which means **event handlers do not need to be pure**. This is the primary home for user-driven side effects.
3. **The Post-Commit Phase (`useEffect`)**: Functions passed to `useEffect` execute after React commits DOM mutations to the browser screen. Keep Effects as a last resort when a side effect must synchronize with an external system without a direct user interaction (as taught in Lesson 32).

```tree caption="The three execution phases of a React component and where side effects belong."
The three execution phases of a component
- +1. Component Body [Render Phase] | Evaluated synchronously to calculate JSX | +**DO** keep **100% pure**: zero external mutations
- +2. Event Handlers [Event Phase] | Executed asynchronously on user interaction | +**DO** place **side effects** here: update state, log clicks, dispatch mutations
- +3. useEffect [Post-Commit Phase] | Executed after React commits DOM changes | Use as a **last resort** for external system synchronization
```

### The re-render trap: how unrelated state updates expose impure code

To see how an impure component silently breaks an application, we will build a shopping list page with three grocery items (`Milk`, `Bread`, `Eggs`) and a `Dark mode` toggle button.

The `Dark mode` button flips a boolean theme state (`dark`) inside the parent `App` component. It changes **nothing** about the grocery items.

Why is a theme toggle on a shopping list the most revealing pedagogical test of component purity? Because clicking the theme toggle triggers a state re-render in `App`. As React re-evaluates `App` to produce the dark-mode layout, it recursively re-evaluates all three child `<Item />` components with the **exact same props** they received on initial load.
