# Audit of Lecture 21, 2026-11-08, number 001

Lecture: [01-02-md-LECTURES/v1/21.md](../01-02-md-LECTURES/v1/21.md), *Reacting to Input with State*. Map: [01-01-map-principles/v1/21.md](../01-01-map-principles/v1/21.md). Draft: [01-01-md-DRAFT-lectures/v1/21.md](../01-01-md-DRAFT-lectures/v1/21.md).

Written under skills v10.5 after batch 2026_11_07_14, which brought the v10.1 Opening Essence back as its own skill. The map has the Opening Essence fields, so the new skills were used.

## 1. The mock section and Figure 6 do not belong in this lesson

The lecture has a section *Drawing the four pictures of the newsletter box* (from line 125) with Figure 6, captioned "The mock: all four pictures of the newsletter box on one page. In the submitting copy, the box and Join are grey." It draws all four states of the newsletter form one under another on one page, before any click works.

Where it comes from: the React docs page *Reacting to Input with State* shows a designer's trick, drawing every state of a form on one page before writing logic, which the docs call mocking or a living styleguide. The map copied it: line 136 ("a designer draws one mockup for each picture before any logic"), line 150 (*mock* listed as a new term), line 165 ("living styleguide" or "storybook").

What is wrong with it:
1. It is the docs' teaching device, not something our reader needs for the lesson's idea.
2. It brings in documentation words: mock, visual state, styleguide.
3. It does not work as a page. The lecture itself must warn at line 211 that a click on `Join` in the mock reloads the page, and that the mock "is for looking, not for clicking".
4. It puts a design technique in front of the key idea of the lesson.

## 2. The "grey" captions are false

The caption of Figure 6 says the box and `Join` are grey in the submitting copy. In the rendered picture they look exactly like the other copies. The page renderer (`src/build-river.mjs`) cannot draw a disabled or greyed control, so every "grey" caption shows something that is not there. Other places: the opening page at line 362 ("Join is grey"), line 383, and line 623. The `dom` figure at line 202 explains `disabled` as "makes the box grey and locked". The map marks the button part `unconfirmed` (lines 170, 234, 235), and the lecture states it as fact anyway.

## 3. "Picture" is an invented label

"Picture" is not a React word. The map translated the docs' term "visual state" as "one complete picture the user can see" (line 147), and the lecture then uses "picture" everywhere: 94 times. Examples: the opening code comment at line 19 ("Names the current picture"), the key idea at line 25 ("A form has a small set of named pictures"), the PRINCIPLES list at line 72, and the title of Principle 1, *Each `status` Draws One Picture of the Form*.

What "picture" is meant to mean: what the newsletter box shows at one moment. The four are:
1. `'typing'`: the email box and the `Join` button.
2. `'error'`: the same, plus the red line "Please enter a full email address."
3. `'submitting'`: the same box and button, plus the line "Sending...".
4. `'success'`: only the line "Welcome to the list!".

The owner did not understand the sentence "A real form has to pick its picture itself, after the user acts." It only makes sense after the mock, where `App` showed all four looks at once. In plain words: when the user clicks `Join`, our code calls `setStatus('submitting')`, and React changes the page to show "Sending...".

This breaks the workspace rule to name things as the reader sees them, by the name in the code first: here `status` and its four values. It is also not what was discussed in brief_2026_11_07_13, whose key idea needs no new word: we change the page through a reactive variable, or we change the page directly through DOM manipulation.

## 6. The causes, under any skill version

1. The React docs page itself teaches with visual states, mocks, a living styleguide, a state machine, and a disabled button. The writer copies the docs' devices instead of choosing what our reader needs.
2. The same line in both skill sets: v10.1 `map-principles` line 59 and v10.5 `map` line 17 say to read every `learn/` and `reference/` page, including every Pitfall, Deep Dive, Recap, and Challenge. Neither says that reading is not the same as putting it into the lecture.
3. The renderer cannot draw a disabled control, so a writer who follows the docs' `disabled` example always writes a false "grey" caption.
4. Neither skill set has a lecture rule against invented labels. "Name things as the reader sees them, the code name first" lives only in the workspace law and in prompt-writing, which are for skill writers. v10.5's "do not invent labels" is also only in editing-skills.

Also still open from the earlier diagnosis of v10.5: the lecture start, item 3, still asks for "The real page problem", a slot that pushed writers to invented plain JavaScript bugs.

## 7. Proposed fixes, not yet approved

1. Map skill: read every Deep Dive, but take into the map only what this lesson needs. The docs' own devices, such as mocks, styleguides, and state machine diagrams, stay out unless the lesson is about them.
2. Lecture skill: name each thing by its code name, such as `status` and `'submitting'`, never by an invented word such as "picture".
3. Figures skill: a preview or caption never claims a look the renderer cannot draw, such as grey or disabled. Say it in the text, or leave it out.
4. Later, separately: renderer support for disabled controls.
