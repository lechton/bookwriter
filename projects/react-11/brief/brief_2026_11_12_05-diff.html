Here is the good news: the app is faster, and the user never sees a half-updated screen where some variables are updated (e.g. the score), while other variables are not yet updated (e.g. the name). Batching allows React to group together all the updates from all the setter calls inside the same event handler. If you write setScore(s => s + 1), you pass a function (s => s + 1), and that function is called an updater function. It tells React: "take whatever the score is by now (s), and add 1 to it." But for state in React, you need to declare the name of the variable (e.g. `name`, `score`), and always at the same time you need to declare its twin setter function (e.g. `setName`, `setScore`). You need to declare both of them. EVERY. SINGLE. TIME. But pay attention here: if you write `setScore(score + 1)`, you do a simple value update, which can be tricky. Remember the snapshot? It's the fact that state variables do not change within the same event handler until the component renders. You can update any state variable, cool... but the value updates do not add up. If you update `score` with `setScore(score + 1)`, then JavaScript will work out `score + 1` from the current snapshot, telling React: "REPLACE the score with this number". Did you notice the detail? It says "REPLACE": `setScore(score + 1)` will replace the previous value with the new one. Each value update replaces the one before it, so only the last one counts! The last update wins because the last update commands the actual replacement. But what happens when your state object holds another object nested inside it, such as `delivery: { address: 'Main St', time: 'Morning' }`? That brings us to a shallow copy. Pay attention here: object spread looks like it copies everything, but it only copies the top level! Think of the outer order box holding an address card that points to a second, inner delivery box in memory. When you write `const next = { ...order }`, JavaScript builds a new outer box, but for `delivery`, it only copies the pointer: both `order.delivery` and `next.delivery` point to the exact same inner box in memory. That is why it is called a shallow copy: it is not a deep copy! As long as you only read `delivery`, that is cool... but the moment you write `next.delivery.time = 'Evening'`, you have walked right into the shallow-copy trap. You mutated the shared inner box that `order` still points to! No line in the reset handler wrote Evening, but the starting state was corrupted through that shared reference! Moral of the story: spread is shallow.
