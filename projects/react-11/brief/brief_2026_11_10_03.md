## PROPER (the opening the owner chose, 2026-11-10)

> ## Why Every Render Must Call the Same Hooks
>
> A Hook is a function from React whose name starts with `use`. You met the first one in Lesson 12: `useState`. React's docs say: "In React, `useState`, as well as any other function starting with "use", is called a Hook." A Hook lets a component ask React to keep something between renders, such as the text in a box. The component calls its Hooks again on every render, and each time React hands back what it kept for each one.
>
> But React does not know your Hooks by their names. It knows them by their order: the first Hook your component calls, the second, the third. On each render, React gives the first call what it kept for the first Hook, the second call what it kept for the second, and so on. So every render of a component must call the same Hooks, in the same order. That is why React's docs say: "always use Hooks at the top level of your React function, before any early returns."
>
> What is at stake is the user's last click. Take a feedback form: a message box and a `Send` button. After Send, the form disappears, and the heading `Thank you!` takes its place. The component holds two Hooks: one that remembers whether the message was sent, and one for the text in the box, `message`. Suppose the `useState` for `message` sits inside the form's branch, next to the form that uses it. While the user types, the form works. Then the user clicks Send. On the next render, the component shows the thank-you heading and skips the form's branch, so it calls one Hook instead of two. React stops with the error "Rendered fewer hooks than expected", the whole page goes blank, and the message the user wrote is gone.
>
> The bug hides well. A developer who only types in the box never sees it. The first user who clicks Send does.
>
> *(Then the two figures: the form, and the thank-you page.)*

````markdown
## What Happens Between `setCount` and the New Number on the Screen

### What this question is really about

Picture a box office page where a buyer orders concert tickets. The page shows how many tickets are in the order, a box for a seat note, and a button to add one more ticket:

```page width=text caption="The box office page of this lesson: the ticket count, the seat note box, and the Add ticket button."
heading: City Box Office
card: title=Concert Tickets | text=Tickets: 1 | typed=Window seat
line: [Add ticket]
```

You click `Add ticket`, and the number goes from 1 to 2. It looks like one instant move. It is not.

When you call `setCount`, React runs your component function again. That sounds risky, and it raises three questions every beginner has:

1. When does the page actually change: on the `setCount` line, or later?
2. Does React run the whole app again, or only this component?
3. Does React rebuild the page, so the text the user typed in the `Seat note` box disappears?

**The short answer: React never changes the page in one move. It works in three steps, and the page changes only in the last one.**

1. **Trigger.** `setCount` changes nothing on the page. It asks React for an update, and React waits until your click code finishes.
2. **Render.** React calls your component function again, and the functions of the components inside it. It does not call `App` above it. All of this happens in memory, so the page still shows the old number.
3. **Commit.** React compares the new result with the old one, and changes on the page only what is different: the number. The heading, the button, and the typed `Window seat` stay exactly as they were.

Then the browser draws the new number on the screen.

### Why the three steps have names

Interviewers ask for these names. But the names do a real job too: each one tells you what is true at that moment.

- During Trigger and Render, the page still shows the old number.
- Only Commit touches the page, and it touches as little as possible. This is why running a component again is safe for what the user typed.
````

````markdown
## The Decoupled Pipeline: Why State Setters Never Touch the DOM Directly

### Trigger, Render, and Commit: The Three Distinct Phases of Every Update

When a user clicks a button to add a ticket on a box office page, the number on the screen jumps from `Tickets: 1` to `Tickets: 2` in less than a millisecond.

Because the screen changes right away, developers often assume that calling `setCount` reaches straight into the browser DOM and rewrites the paragraph on that exact line of code.

State setters never touch the browser DOM.

If your click handler reads the live DOM paragraph on the line right after `setCount`, it gets the old text back, and the Console still logs `Tickets: 1`:

```jsx title="Calling setCount and querying the DOM on the very next line"
function TicketCounter() {
  const [count, setCount] = useState(1);

  function handleAdd() {
    ~setCount(count + 1)~; // 1. Queues an update request in React memory
    console.log(~document.querySelector('.count-text').textContent~); // 2. Logs "Tickets: 1"!
  }

  return <p className="count-text">Tickets: {count}</p>;
}
```

The DOM still holds the old text because React never updates the screen in one single step.

Instead, React splits every screen update into three phases in order, and then the browser paints the screen at the end:
1. **Phase 1: Triggering a render**: Your startup code or an event handler tells React that the screen needs an update. Calling `setCount` does not change the DOM. Instead, it puts an update request into React's queue and lets your event handler finish running first.
2. **Phase 2: Rendering the components**: React calls your component functions in memory to figure out what JSX should appear on screen. This calculation happens entirely in memory and touches zero DOM nodes.
3. **Phase 3: Committing to the DOM**: React compares the new JSX from Phase 2 against the previous render, finds what changed, and updates only those specific nodes in the real browser DOM.
4. **After Commit: Browser Paint**: Once React finishes updating the DOM, the browser recalculates the page layout and paints the new pixels on the screen.

The official React documentation compares these steps to a waiter and a chef in a restaurant kitchen, where the guest's table is the browser screen:
- **Trigger**: The waiter takes the guest's order at the table and clips the order slip into the kitchen queue.
- **Render**: The chef in the kitchen reads the slip and prepares the dish, without touching the guest's table yet.
- **Commit**: The waiter brings the finished dish to the table and swaps only the plate that changed, while leaving the glasses, silverware, and notepad alone.
- **Browser Paint**: The guest looks at the table and sees the new dish on the plate.

```tree dir=right caption="Every screen update in React passes through Trigger, Render, and Commit before the browser paints the screen."
The three-phase update lifecycle in React
- +Phase 1: Trigger [`root.render` or `setCount`] | Asynchronous dispatch | Places a render request in React queue; live DOM is untouched
- +Phase 2: Render [React calls component functions] | Pure in-memory calculation | Invokes component functions to produce new JSX objects with 0 DOM mutations
- +Phase 3: Commit [React mutates the DOM] | Targeted DOM updates | Appends all nodes on mount, or updates only changed text and attributes on re-render
- +After Commit: Browser Paint [Browser paints screen] | Host browser rasterization | Recalculates layout and paints pixels so the user sees the update
```
````

## Why React Components Must Be Pure

First, three terms this lesson stands on. A render is React calling your component function to get its JSX (Lesson 13). Props are the values a parent hands to a component on its tag (Lesson 8), and state is the memory React keeps for that component between renders (Lesson 12). An event handler is the function that runs when the user clicks, such as the one in `onClick` (Lesson 11).

React does not call your component only once. It calls it again and again: it calls your component on the first load, and it calls it again after every click that changes state. So every component must be pure. React's docs give a pure component two rules:

1. **Same inputs, same output.** With the same props and state, the component returns the same JSX, every time React calls it.
2. **It minds its own business.** In the docs' words, "it does not change any objects or variables that existed before it was called."

**Beware! An impure component changes the page even when the user changed nothing.**

What does "change something that existed before" mean? Think of a book. Someone hands you a book, and you write in it with a pen. Everyone who reads it after you gets your changes. The original book is gone. But if you make a copy and write in the copy, the original stays exactly as it was.

In a component, the book is anything that existed before React called the component:

1. **A variable outside the component**, such as a counter at the top of the file.
2. **An array the parent passed down as a prop.**

An impure component writes in the book. A pure component writes only in a copy it made itself, such as a new array it creates during the same render. React's docs call this "local mutation", and it is completely fine.

Here is what writing in the book does to a real page. On this shopping list, each item adds one to a counter outside the component, and takes its number from that counter. The list opens fine, as 1, 2, 3. Then the user clicks `Dark mode`. That click should change only the colors:

line: 6. Eggs | bad
line: [Light mode]

The bug can strike even before the first click. While you build the app on your own computer, React runs a checking tool called `StrictMode`. `StrictMode` calls every component twice in a row, on purpose, to catch exactly this bug. So the list opens as 2, 4, 6 before anyone has clicked at all. On the live site, React calls the component only once per render.

1. **The component body only calculates.** It never writes in the book.
2. **The event handler makes the changes.** Code that must change something, such as counting a click, goes in the event handler. The event handler runs once per click, and never during a render.

Now React can call your component as often as it likes. The list stays 1, 2, 3.

# Pure Components and Where Side Effects Belong

## The Reconciler's Contract: Why React Demands Pure Functions

*(Who decides when your component runs: you or React?)*

**Interview question:** What does it mean for a component to be pure, and what breaks across renders when it is not?

## Why React Components Must Be Pure

First, let's set the three building blocks this lesson stands on:

1. **A render** is React calling your component function to ask what JSX should appear on the screen (Lesson 13).
2. **Props and state** are the inputs your component reads: props are the values a parent passes down on the component's tag (Lesson 8), and state is the memory React keeps for that component between renders (Lesson 12).
3. **An event handler** is the function that runs only when the user does something on the page, such as clicking a button with `onClick` (Lesson 11).

In plain JavaScript, you call a function only when you want an action to happen.

React components break this rule.

You do not decide when your component runs. React decides. When React calls your component, it is not asking your code to change data—it is only asking a question: *"Given these props and this state, what should the screen look like right now?"*

And React does not ask that question only once. It calls your component on the first load, and it calls it again after every click that changes state so its engine (the **reconciler**) can compare the old screen with the new one.

Because React must be free to call your component whenever it wants without breaking your data, every component must obey **the reconciler's contract**: it must be **pure**. React's docs give a pure component two rules:

1. **Same inputs, same output.** With the same props and state, the component returns the exact same JSX every time React calls it.
2. **It minds its own business.** In the docs' words, "it does not change any objects or variables that existed before it was called." Changing anything outside the component is called a **side effect**, and it does not belong inside a render.

**Beware! An impure component changes the page even when the user changed nothing.**

### The Book Analogy: Existing Data vs. Local Copies

What does "change something that existed before" mean in practice?

Think of a book. Someone hands you a book, and you write in it with a pen. Everyone who reads that book after you—including you, the next time you open it—gets your permanent changes. The original book is gone. But if you make a photocopy and write on the copy, the original book stays exactly as it was.

In a component, "the book" is anything that already existed before React called your component:

1. **A variable outside the component**, such as a counter at the top of the file. If your component changes it during a render, the new value stays there and corrupts the next render.
2. **An array or object the parent passed down as a prop.** If your component changes that array directly, it silently corrupts the parent's data too.

An impure component writes directly in the book. A pure component writes only in a fresh copy it created for itself during that single render, such as a new array created inside the function. React's docs call this **local mutation**, and it is completely fine because nobody outside that render ever sees the copy.

### How Writing in the Book Breaks a Real Page

**Beware! When a component changes an outside variable during a render, even an unrelated click—like switching to Dark Mode—overwrites the numbers on the screen.**

Users click things on the screen all the time: opening a menu, switching a tab, or toggling Dark Mode. Every time one of those clicks updates state, React calls the components on the page again to recalculate the screen. If a component changes an outside variable while it renders, every unrelated click changes your data by accident.

Let's see what writing in the book does to a real page. On this shopping list, each item component adds `1` to a counter outside the component during its render, and takes its item number from that counter.

On the first load, the list opens fine as `1, 2, 3`. Then the user clicks `Dark mode`. That click should change only the colors:

```page width=text caption="After one click on Dark mode: every number on the list has jumped by three."
heading: My Shopping List
line: 4. Milk | bad
line: 5. Bread | bad
line: 6. Eggs | bad
line: [Light mode]

```

**The page now shows the wrong numbers.** Nobody touched the shopping list. Yet the items jumped from `1, 2, 3` to `4, 5, 6`.

Here is what went wrong step by step:

1. **The first load runs each item once:** React calls the three item components. Each item adds `1` to the outside counter, so the screen displays `1, 2, 3`.
2. **The user clicks `Dark mode`:** This click updates the theme state, so React calls the components on the page again to check what the screen should look like in dark mode.
3. **Each item writes in the book a second time:** Because all three items run again, each one adds `1` to the same outside counter. The counter climbs from `3` to `6`, and overwrites the screen with `4, 5, 6`. Click once more, and the list leaps to `7, 8, 9`. The numbers keep climbing with every click.

**The bug can strike even before the first click.** While you build the app on your own computer, React runs a checking tool called `StrictMode`. `StrictMode` calls every component twice in a row on purpose to catch this exact bug right away. Because each item runs twice before the page finishes loading, the list opens as `2, 4, 6` before anyone has clicked at all. On the live site, React calls the component only once per render, so without `StrictMode` the bug hides until a real user clicks a button.

### The Rule of Thumb

**While React renders your component, treat everything you did not create in that render as read-only.** React's docs say the same about props and state: "You should always treat these inputs as read-only."

At the end of the day, a senior developer follows three rules:

1. **Need a changed list? Copy it first, then change the copy.** In a developer's mind, calling `items.push('Shopping bags')` on a prop and pushing into a copy seem to do the same job: both put `'Shopping bags'` at the end of the list. They are NOT the same! Calling `items.push()` directly on a prop writes into the parent's original array, so every re-render pushes `'Shopping bags'` into the list again. Always make a copy first with `items.slice()`, and push into the copy so the parent's list stays untouched.
2. **Need to change something for real, such as counting a click? Put it in the event handler.** Side effects belong in event handlers like `onClick`. An event handler runs once per click, and never runs when React is simply re-rendering the screen.
3. **`StrictMode` shows doubled numbers? Do not switch `StrictMode` off—fix the component.** Turning `StrictMode` off does not fix the code; it only hides the bug on your computer until a real click breaks the page for your users.
