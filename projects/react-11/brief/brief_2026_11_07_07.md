## 1. Why This Batch Exists

In Principle 4 of Lecture 20 (controlling a `<select>` menu and a checkbox), the opening bullets led with cryptic token-swapping sentences:
- `"On a <select> menu, value sits on the menu tag itself, never selected on an option."`
- `"On a tick box, checked replaces value, and e.target.checked replaces e.target.value."`

And when a first revision tried to unpack them Inside nested prose bullets, it fell into the opposite trap: repeating `selected`, `<option>`, `value`, and `<select>` back and forth in prose (`A and B and A and B and A is not B`) and inlining a full tag (`<option value="orange" selected>Orange</option>`) inside a sentence.

Both habits frustrate an impatient reader:
1. **Cryptic token-swapping (`"A sits on X, never B on Y"`, `"C replaces A, and D replaces E"`)** treats code names like algebraic symbols the reader already holds in mind, announcing what is not what or what replaces what before showing what either thing is.
2. **Prose ping-pong with inline tags** overloads the sentence with `A` and `B` repetitions instead of letting a clean 3-line code block on its own lines show the structure immediately.

The owner's rewrite of Principle 4 solved both problems with directness and simplicity:
- State how plain HTML marks a starting choice in a static way (`selected` inside `<option>`), and show the 4-line HTML block on its own lines.
- State why `selected` does not work in React (we need a dynamic way driven by our state variable `fruit`: if `fruit` starts as `'orange'`, Orange is selected), and show the 4-line JSX block on its own lines.
- Explain the tick box in the same direct sequence: it holds `true` or `false` instead of text, so we control it with `checked` and read `e.target.checked`, followed by its code block on its own lines.
