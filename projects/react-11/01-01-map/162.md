# Q162: Server Function Security: Input Validation and Public Attack Surfaces
* **Topic Tag**: #security | ❱❱ MORE (Server)
* **Interview Question**: *Why is a Server Function a public endpoint, and what must you validate?*
* **Core Truth**: Every Server Function is compiled into an unauthenticated public HTTP POST endpoint; servers must validate user sessions, enforce authorization permissions, and parse input schemas on every invocation.
* **The Friction**: A developer writes a Server Function updateArticleStatus(id, status) that changes articles from "Draft" to "Published"; a signed-in user who is not an admin discovers the action ID in network traffic and issues a curl request to publish an unchecked article, bypassing the review on the admin page.
* **The Mechanism**: Zero-trust Server Function pattern: (1) Authenticate session (const user = await auth()); (2) Authorize role (if (!user.isAdmin) throw new ForbiddenError()); (3) Validate input schema using Zod/Valibot (const { id, status } = schema.parse(rawInput)); (4) Execute database mutation.
* **Under the Hood**: The public URL hazard: bundlers assign predictable or hash-based action IDs to Server Functions exposed via POST /; because browser dev tools make action IDs trivial to discover, any parameter passed into the function must be treated with the same skepticism as raw query params in a REST endpoint.
* **The Code Experiment**:
  * *Naive*: Assuming that because a Server Function is imported into an admin-only page component, callers are automatically authorized.
  * *React*: Implementing strict session verification and Zod schema validation inside the Server Function before touching the database.
* **Scope Boundary**: Focus on Server Function security best practices, schema validation, and authorization. Do not confuse with Taint APIs (Q149).
