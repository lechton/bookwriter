# Q06: UI as a Tree and Component Hierarchy
* **Topic Tag**: `#ui_tree` | `❱ CORE`
* **Interview Question**: *How does React organize nested components into a tree, and why does hierarchy dictate data flow?*
* **Core Truth**: React models a user interface as a hierarchical Component Render Tree of nested component instances alongside a build-time Module Dependency Tree of imported files; parent-child hierarchy in the Render Tree dictates top-down rendering and one-way data flow.
* **The Friction**: After splitting an app into separate files (`App.jsx`, `SiteHeader.jsx`, `ArticleList.jsx`, `ArticleCard.jsx`, and `Badges.jsx`), a developer sees a flat folder of `.jsx` files and treats components as flat peers. They nest `<SiteHeader />` inside the wrong component, confuse the file import graph with the component render tree, or try to read a local variable sideways between sibling components (`SiteHeader` and `ArticleList`).
* **The Mechanism**: JSX tag nesting builds the runtime Component Render Tree starting from the root component (`App`), branching through intermediate parent components (`ArticleList`, `ArticleCard`), and ending at leaf components (`SiteHeader`, `LiveBadge`, `NewBadge`), while `import` statements build a separate Module Dependency Tree of files for the bundler.
* **Under the Hood**: Why HTML tags (`<main>`, `<article>`, `<span>`) appear in the browser DOM tree (`Elements` panel) but not in the React Component Render Tree (`Components` panel), why rendering a parent cascades top-down through every child instance in its subtree, and why sibling branches share no lexical scope so shared data must live in their lowest common parent or a shared module.
* **The Code Experiment**:
  * *Naive*: Treating files in `src/components/` as flat peers—placing `<SiteHeader />` inside `ArticleCard`, or duplicating/reading a local `category` variable sideways between `SiteHeader` and `ArticleList`.
  * *React*: A clean multi-file hierarchy where `App` renders `SiteHeader` and `ArticleList`, `ArticleList` renders multiple `ArticleCard` instances, `ArticleCard` renders `LiveBadge` and `NewBadge`, and `siteData.js` demonstrates the difference between the Module Dependency Tree and the Component Render Tree.
* **Scope Boundary**: Focus strictly on the Component Render Tree (root, branch, leaf, instances vs. files, HTML DOM tree vs. React Component tree), top-down render order, why hierarchy dictates one-way data flow between parents and siblings, and how the Component Render Tree differs from the Module Dependency Tree. Do not introduce dynamic `props` destructuring (Q08), `children` slots (Q09), or `useState` (Q12) in the lesson's code snippets.
