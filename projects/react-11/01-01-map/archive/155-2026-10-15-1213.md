# Q155: Module Segregation: Server-Only Exports and Conventional Boundaries
* **Topic Tag**: #server_only | ❱❱ MORE (Server)
* **Interview Question**: *What are server-only exports and the server-only package convention?*
* **Core Truth**: To prevent unintended server code leakage, modules that access backend resources must be strictly segregated from shared client utilities using dedicated file conventions or import 'server-only'.
* **The Friction**: A utils/articles.ts file at The National Times contains three harmless string formatting functions and one getArticleFromDatabase() function; a client component imports formatSlug() from this file, accidentally causing the bundler to include the database driver in the client bundle, triggering compilation failure.
* **The Mechanism**: Segregation strategies: (1) Split mixed modules into pure utilities (article-utils.ts) and server utilities (article-data.ts); (2) Add import 'server-only' to the data module; (3) Re-export pure helpers safely without exposing database imports.
* **Under the Hood**: Tree-shaking limitations: although modern bundlers tree-shake unused exports, side-effectful top-level imports cannot always be eliminated; if a module is marked server-only, the bundler prohibits any client entry into that module regardless of which export is used.
* **The Code Experiment**:
  * *Naive*: Mixing database queries and string formatting helpers in a single shared file lib/stories.ts, allowing client imports to drag in server dependencies.
  * *React*: Segregating into lib/stories.server.ts with import 'server-only' and lib/stories.shared.ts for pure functions, maintaining clean module boundaries.
* **Scope Boundary**: Focus on practical module segregation conventions, tree-shaking pitfalls, and isolating server-only exports. Do not re-explain basic server-only from Q122.
