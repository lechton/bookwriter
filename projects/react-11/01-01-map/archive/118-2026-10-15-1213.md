# Q118: Server Streaming APIs: renderToPipeableStream and renderToReadableStream
* **Topic Tag**: #streaming | ❱ CORE (Server)
* **Interview Question**: *How do you stream HTML on the server with renderToPipeableStream or renderToReadableStream?*
* **Core Truth**: React provides two server streaming entrypoints—renderToPipeableStream for Node.js environments and renderToReadableStream for Web Stream environments (Edge, Cloudflare, Deno)—which manage the streaming lifecycle via callbacks like onShellReady and onAllReady.
* **The Friction**: An infrastructure engineer at The National Times deploys a Node.js server that uses renderToString; under heavy election night traffic, the server process hits memory limits buffering multi-megabyte HTML strings; attempting to switch to streaming, they do not know how to handle search crawler bots versus regular readers.
* **The Mechanism**: Streaming entry points: renderToPipeableStream(jsx, { bootstrapScripts, onShellReady, onShellError, onError }) returns { pipe, abort }; renderToReadableStream(jsx, options) returns a Promise resolving to a ReadableStream.
* **Under the Hood**: Shell lifecycle vs crawler strategy: onShellReady fires as soon as the synchronous shell finishes rendering, ideal for human readers (piping immediately for fast TTFB); for SEO search crawlers, servers wait for onAllReady to ensure the complete HTML with all Suspense fallbacks resolved is buffered before sending the response.
* **The Code Experiment**:
  * *Naive*: Using renderToString on the server, buffering the entire HTML string in memory and preventing progressive streaming to the client.
  * *React*: Implementing renderToPipeableStream in an Express handler, piping the response on onShellReady for human users, and providing bootstrapScripts for hydration.
* **Scope Boundary**: Focus on renderToPipeableStream and renderToReadableStream APIs, their callbacks (onShellReady, onAllReady, onShellError), and runtime environment differences.
