# Q12: Keeping Components Pure
* **Topic Tag**: `#purity` | `❱ CORE`
* **Interview Question**: *What does it mean for a component to be pure, and what breaks when it is not?*
* **Core Truth**: React components must be pure functions—given the same inputs (props, state), they must always return the exact same JSX and produce zero side effects during rendering; StrictMode in development enforces this by deliberately rendering components twice.
* **The Friction**: A developer increments a global counter variable or mutates an external array inside the component function body. On initial render it looks fine, but when React re-renders or StrictMode runs, the counter doubles, editorial headlines duplicate, and UI numbers drift unpredictably.
* **The Mechanism**: Pure rendering principles. Components treat render execution as a mathematical formula: `UI = f(data)`. All side effects (DOM mutations, timers, network requests, analytics) belong inside event handlers or lifecycle mechanisms, never in the render path.
* **Under the Hood**: Why React demands purity: concurrent rendering can pause, abort, and restart rendering work in memory without committing; impure components produce conflicting or corrupted UI states when renders restart.
* **The Code Experiment**:
  * *Naive*: Mutating an external `guestCount` variable directly inside the component body, producing corrupted numbers under React StrictMode double rendering.
  * *React*: Computing values purely from props without external mutation, ensuring deterministic output across any number of render cycles.
* **Scope Boundary**: Focus strictly on function purity during render, eliminating mutations of external scope variables, and explaining why development double-rendering happens. Do not introduce `useEffect` or state setters.
