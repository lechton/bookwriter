# Q61: Keys and Reconciliation: Why Array Index is a Trap
* **Topic Tag**: `#keys_and_reconciliation` | `❱❱ MORE`
* **Interview Question**: *What makes a good key, and why is the array index a trap?*
* **Core Truth**: Keys provide stable identity across renders so React can track item additions, removals, and reordering; using array indices as keys binds identity to position rather than data, causing state corruption and uncontrolled input swaps when lists change.
* **The Friction**: An editor sorts tonight's headline queue by priority or deletes the top story. Each story row contains an inline correction input. Because the developer used `key={index}`, React reuses the existing DOM nodes at index 0, 1, 2, leaving the typed draft notes stuck in the wrong rows while headlines move around them.
* **The Mechanism**: Reconciliation with stable, unique entity IDs (`key={item.id}`). Keys must remain permanent across renders (never generated via `Math.random()`), unique among siblings, and tied directly to the data record.
* **Under the Hood**: React's list reconciliation algorithm: React pairs old fibers with new virtual elements using their `key`. When keys are indices (`0, 1, 2`), deleting item 0 causes old fiber 1 to be matched with new item 0, mutating its props in place while preserving its local state and DOM focus, corrupting internal state.
* **The Code Experiment**:
  * *Naive*: Rendering `<StoryRow key={index} />` with an internal stateful checkbox or text field; sorting the array causes checkboxes to stay in place while row labels change.
  * *React*: Rendering `<StoryRow key={story.id} />` using stable UUIDs, ensuring that component instances and their internal state follow their respective data items through sorting and deletions.
* **Scope Boundary**: Focus on reconciliation mechanics, the index-as-key antipattern, and state-leak bugs. Do not introduce virtualization (Q62).
