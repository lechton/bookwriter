# Q112: Form Actions and Progressive Enhancement with Server Functions
* **Topic Tag**: #form_actions | ❱ CORE (Server)
* **Interview Question**: *How do forms work with Server Function actions, and what is progressive enhancement?*
* **Core Truth**: Passing a Server Function to <form action={fn}> provides progressive enhancement: if JavaScript is disabled or still downloading, the browser submits standard multipart/form-data via native HTTP POST; once hydrated, React intercepts the submit with a seamless fetch RPC.
* **The Friction**: During a major news breaking event, readers with spotty cellular reception submit subscription forms to The National Times before the 2MB JavaScript bundle finishes downloading; because the form relied on e.preventDefault(), submissions are completely lost unless progressive enhancement is built into the form action.
* **The Mechanism**: <form action={serverAction}>: native HTML form semantics where action accepts a Server Function; with JavaScript enabled, React intercepts submit, packages FormData, and issues a transition fetch; without JavaScript, the browser issues a standard HTTP POST request to the server endpoint.
* **Under the Hood**: React's form interception: when the client runtime hydrates, it registers an event listener on the form; it constructs new FormData(form), calls the server action via the RPC client within a transition, preventing full page reload while preserving native browser fallback.
* **The Code Experiment**:
  * *Naive*: Building a form with <form onSubmit={(e) => { e.preventDefault(); fetch(...); }}>, rendering the form completely inert before client JavaScript executes.
  * *React*: Authoring <form action={publishArticle}> with a Server Function, ensuring the form submits reliably both before and after client hydration.
* **Scope Boundary**: Focus on progressive enhancement, native HTML form behavior, and how <form action> bridges no-JS and JS environments. Handling action return values and status is covered in Q113 and Q114.
