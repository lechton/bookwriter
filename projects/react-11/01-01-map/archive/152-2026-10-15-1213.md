# Q152: Revalidating Server State: Connecting Mutations Back to the UI
* **Topic Tag**: #data_fetching | ❱❱ MORE (Server)
* **Interview Question**: *After a Server Function mutates data, how does the client see fresh server data?*
* **Core Truth**: When a Server Function mutates backend data, the server returns both the action result and a freshly rendered RSC payload for the current tree, allowing React to update server-rendered components on screen without a full page reload.
* **The Friction**: An editor edits a breaking news headline in the CMS at The National Times and clicks "Publish"; the Server Function successfully updates PostgreSQL, but the article list on screen still displays the outdated headline because the client has no mechanism to re-fetch the updated Server Component tree.
* **The Mechanism**: Revalidation and refresh: invoking a Server Function inside a transition triggers the server to re-render affected Server Components and stream the updated RSC payload back in the same HTTP response; React merges the new server tree into the existing client DOM seamlessly.
* **Under the Hood**: Multi-part response and reconciliation: the server action response contains the serialized return value and an updated RSC flight stream; the client router / React runtime passes this stream into the existing Fiber tree, updating only the DOM nodes whose server-rendered props or text changed, preserving client state.
* **The Code Experiment**:
  * *Naive*: Forcing a hard browser page reload window.location.reload() after every server mutation, losing scroll position and client state.
  * *React*: Wrapping the Server Function call in startTransition(async () => { await updateHeadline(id, text); }) so React revalidates and re-renders server content seamlessly.
* **Scope Boundary**: Focus on how Server Function mutations trigger server re-rendering and client tree reconciliation. For optimistic UI during mutations, see Q153.
