# Q65: Synchronous DOM Updates with flushSync
* **Topic Tag**: `#flush_sync` | `❱❱ MORE`
* **Interview Question**: *What does flushSync do, and when is it the right escape hatch?*
* **Core Truth**: `flushSync` forces React to immediately flush all pending state updates and commit them to the physical DOM synchronously, serving as an escape hatch when third-party libraries or precise measurements require instantaneous DOM synchronization.
* **The Friction**: When a user clicks "Jump to Latest Comment", the developer calls `setComments([...comments, newComment])` and immediately executes `lastCommentRef.current.scrollIntoView()`. Because React batches the state update asynchronously, the new comment does not exist in the DOM yet, and the browser scrolls to the previous item instead.
* **The Mechanism**: The `flushSync` escape hatch (`flushSync(() => { setComments(newComments); }); lastCommentRef.current.scrollIntoView();`). React halts whatever it was doing, immediately renders and commits the state update to the DOM, and only then continues to the next line of code.
* **Under the Hood**: Bypassing the batching scheduler: `flushSync` forces React to synchronously run the entire Render and Commit cycle immediately, suppressing automatic batching and concurrent scheduling; this can trigger severe performance drops if called frequently.
* **The Code Experiment**:
  * *Naive*: Calling `scrollIntoView()` immediately after `setComments()`, failing to scroll because the DOM has not updated yet.
  * *React*: Wrapping `setComments` inside `flushSync`, ensuring the new DOM node exists before calling `lastCommentRef.current.scrollIntoView()`.
* **Scope Boundary**: Focus strictly on `flushSync` as a rare escape hatch for post-update DOM measurements/scrolling. Strongly emphasize its performance penalties and why it should not be used routinely.
