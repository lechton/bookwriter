# Lecture 43: How a Button Deep in a Form Reads the Form's Pending State

*(How does a Post button know that its form is sending a comment right now?)*

> INTERVIEW QUESTION | ❱❱ MORE | How does a field nested deep in a form read the form's pending state?

---

## VS | The owner of the form `isPending` vs. a button inside the form `useFormStatus`: the owner gets the flag from its own Hook, the button asks the form above it

**`useFormStatus` lets a child component inside a `<form>` read whether that parent form is submitting right now, without passing props down.**

Say you build a reusable `<PostButton />` component that sits deep inside a comment form. The moment the user submits the form, `<PostButton />` needs to disable itself so the user cannot send the same comment twice.

**Why:** Only the parent component that renders the form calls `useActionState`, so child components inside the form do not have `isPending`. Instead of passing `isPending` down through props, the button calls `useFormStatus` to ask the closest form above it directly.

Let's start where Lesson 42 ended. The component that renders the form calls `useActionState`, and gets `isPending` back. That works, but only inside that one component.

In a real app, the submit button is rarely written right inside the form. It is its own component, such as `PostButton`, and it often sits two or three components down. It never calls `useActionState`, so it has no `isPending`. So how does it know that the form is sending something?

Remember `closest` from plain JavaScript? A button can find the form it sits in. The browser starts at the button and walks up, parent by parent, until it meets a `<form>`. Then you listen for the submit and turn the button off yourself:

```js title="Plain JavaScript: the button walks up to its form"
const form = ~button.closest('form')~; // Walks up from the button to the first <form> above it
form.addEventListener('submit', () => {
  button.disabled = true; // You turn it off, and later you must remember to turn it on again
});
```

`useFormStatus` does the same walk, inside React. Your component calls it. React walks up from that component to the closest `<form>` above it, and brings back the status of that form. You never set or clear anything. React does it for you.

```jsx title="React: the button asks its form"
import { useFormStatus } from 'react-dom';

function PostButton() {
  const { ~pending~ } = useFormStatus(); // true while the closest <form> above is submitting
  return <button type="submit" disabled={pending}>Post</button>;
}
```

> [!DEFINITION]
> **What is isPending?** [REVIEW] `isPending` is the third value that `useActionState` returns: `const [comments, postAction, isPending] = useActionState(addComment, [])`.
> It is `true` from the moment the user submits, until the answer of the action is on the screen. React turns it on and off by itself.
> Something that can be tricky: only the component that calls `useActionState` gets it. A button deeper down must receive it as a prop (Lesson 42).

> [!DEFINITION]
> **What is useFormStatus?** [NEW] `useFormStatus` is a Hook from `'react-dom'`, not from `'react'`. It takes no arguments, so you cannot name a form. It always reads the closest `<form>` above the component that calls it.
> It returns one object, the status object, with four fields: `pending`, `data`, `method`, and `action`. You take out the field you need with curly braces: `const { pending } = useFormStatus()`, as in Lesson 8.
> `pending` is `true` while that form is submitting, and `false` the rest of the time. Pending means waiting, like a bank payment that your banking app marks as Pending: it has started, and the answer has not come back yet.
> The React docs: "If `true`, this means the parent `<form>` is pending submission. Otherwise, `false`."
> So once more: `useFormStatus` asks the closest form above your component whether it is submitting (Lesson 43).

You already know one way for a deep component to read a value with no prop: context (Lesson 28). `useFormStatus` works the same way. The one difference is who provides the value:
- **With context**, our code writes the provider, and the component reads the closest provider above it.
- **With `useFormStatus`**, our code writes no provider. The `<form>` tag plays that part, and the component reads the closest form above it.

The React blog says it in one sentence: "`useFormStatus` reads the status of the parent `<form>` as if the form was a Context provider."

```tree caption="Context vs. useFormStatus: both let a deep component read a value from above, only the provider differs."
Two ways a deep component reads a value with no prop
- +Context [`useContext`] | **Our code** writes the provider | The component reads the **closest provider above it**
- +`useFormStatus` [`const { pending } = useFormStatus`] | **The `<form>` tag** plays the provider | The component reads the **closest form above it**
```

### The Rule of Thumb: which component needs the flag?

**The component that renders the `<form>` reads `isPending` from `useActionState`. Every component inside the form calls `useFormStatus` and reads `pending`.**

What is at stake? A Post button that never learns about the wait stays clickable. The user sees no sign that the click worked, clicks again, and the same comment is posted twice.

Developers really choose between three ways to tell a button that its form is submitting:
1. **Pass `isPending` down as a prop.** The owner of the form already has it from `useActionState`. React's own `useActionState` page passes `isPending` to a child this way. It fits a button one level below the owner.
2. **Make a context by hand** (Lesson 28). Our code creates a context and provides the flag through it. It fits a status that does not come from a form submission.
3. **Call `useFormStatus` in the button.** It fits a button at any depth inside a `<form>`, and a button that many forms reuse.

The React blog explains why the third way exists: "This can be done via Context, but to make the common case easier, we've added a new hook `useFormStatus`." This lesson teaches the third way.

```tree caption="Three ways to give a submit button the pending state of its form, and when each one fits."
Three ways to tell the button that the form is submitting
- +1. A prop from the owner [`isPending={isPending}`] | The owner **hands `isPending` down** | Fits a button **one level below** the owner
- +2. A context made by hand [`<PendingContext value={isPending}>`] | **Our code** writes the provider | Fits a status that is **not a form submission**
- +3. `useFormStatus` in the button [`const { pending } = useFormStatus`] | The button **asks the form above it** | Fits a button **at any depth** inside a form
```

A senior developer also knows the four classic mistakes:
1. **The import from `'react'`.** `'react'` has no `useFormStatus`, so the page breaks.
2. **The Hook next to the `<form>` tag.** In the component that renders the form, `pending` stays `false`, and no error tells you.
3. **A `pending` prop through the middle.** Every component in between must hand it on. Forget one, and the button never turns off.
4. **`data.get` with no check.** Before the first submit, `data` is `null`, and the page goes blank.

The rest of the lesson shows each mistake on a real comment form.

It sits inside `CommentFooter`, the row under the field, and that row sits inside the form. No line of our code tells the button that the form is sending a comment. The button asks the form.

This page stands on three facts from earlier lessons:

2. `useActionState` keeps the list of comments, gives the form its action, and also returns `isPending` (Lesson 42).
3. `formData.get('comment')` reads the field whose `name` is `comment` (Lesson 40).

The file api.js stands in for a real server. It is given, not taught. It waits one second, only so that you can see the wait on the screen:

```js title="src/api.js"
let nextId = 1;

  await new Promise(resolve => setTimeout(resolve, ~1000~)); // Waits one second, like a slow server
  return { id: nextId++, text };

```

The file CommentSection.jsx owns the list and the form. It stays the same in every principle, except where a principle shows a broken or an older version of it:

```jsx title="src/CommentSection.jsx"
import { useActionState } from 'react';
import { saveComment } from './api.js';
import CommentFooter from './CommentFooter.jsx';

async function addComment(previousComments, formData) {
  const comment = await saveComment(formData.get('comment'));
  return [...previousComments, comment];
}

export default function CommentSection() {
  const [comments, postAction] = useActionState(addComment, [{ id: 0, text: 'Great shot!' }]);
  return (
    <section>
      <ul>
        {comments.map(comment => <li key={comment.id}>{comment.text}</li>)}
      </ul>
      ~<form action={postAction}>~ {/* Every component inside this form can ask it for its status */}
        <input name="comment" placeholder="Add a comment..." />
        <CommentFooter />
      </form>
    </section>
  );
}
```

The form renders `CommentFooter`, and `CommentFooter` renders `PostButton`. So `CommentFooter` is the component in the middle, between the form and the button.

**PRINCIPLES:** `useFormStatus` asks the closest `<form>` above your component whether it is submitting. The form must be above the component, never in its own return. Four principles follow:
1. **Principle 1: useFormStatus Gives the Post Button pending.** The button imports the Hook from `'react-dom'` and reads `pending`. Our code never sets it.
2. **Principle 2: pending Stays false Next to the form Tag.** In the component that renders the `<form>` tag, `pending` never becomes `true`, and nothing warns you.
3. **Principle 3: The Components in the Middle Pass No pending Prop.** The button asks the form through any number of components, so nobody in between carries a prop it never uses.
4. **Principle 4: data Holds the Comment Being Posted, or null.** The same Hook returns the form data being submitted. Before the first submit, `data` is `null`.

## PRINCIPLE | `useFormStatus` from `'react-dom'`: the Post button reads `pending` from its form, with no prop

> [!PRINCIPLE]
> **Principle 1: useFormStatus Gives the Post Button pending**
>
> *Call `useFormStatus` from `'react-dom'` in a component rendered inside a `<form>`, and read `pending`, which is `true` while that form is submitting.*
>
> A submit button needs to know that its form is sending something, so it can turn off and say so. No prop has to bring that value. The button calls `useFormStatus`, React DOM looks at the form above the button, and `pending` says whether that form is submitting right now. The Hook comes from `'react-dom'`, because forms exist only on a web page.
>
> **DO THIS:**
> ```jsx
> import { useFormStatus } from 'react-dom';
>
> function PostButton() {
>   const { ~pending~ } = useFormStatus(); // true while the form above is submitting
>   return <button type="submit" disabled={pending}>{pending ? 'Posting...' : 'Post'}</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import { ~useFormStatus~ } from 'react'; // **WRONG:** 'react' has no useFormStatus, so the page breaks
>
> function PostButton() {
>   const { pending } = useFormStatus();
>   return <button type="submit" disabled={pending}>{pending ? 'Posting...' : 'Post'}</button>;
> }
> ```

Here is the whole idea in the fewest lines. A small `Submit` component calls `useFormStatus`, and the form renders it:

```jsx title="A button that asks its form"
import { useFormStatus } from 'react-dom';

function Submit() {
  const { ~pending~ } = useFormStatus(); // true while the form above is submitting
  return <button type="submit" disabled={pending}>Submit</button>;
}

<form action={action}>
  ~<Submit />~ {/* Submit is rendered inside the form, so this form is above it */}
</form>
```

The form passes `Submit` no prop at all. `Submit` asks the form it sits in, and the form answers.

### The Post button on our page

Now the same idea on our page. `PostButton` calls `useFormStatus` and reads `pending`:

```jsx title="src/PostButton.jsx"
import { useFormStatus } from 'react-dom';

export default function PostButton() {
  const { ~pending~ } = useFormStatus(); // Comes from the form above, not from a prop
  return (
    <button type="submit" ~disabled={pending}~> {/* The user cannot click while the comment is on its way */}
      {pending ? 'Posting...' : 'Post'}
    </button>
  );
}
```

`CommentFooter`, the component in the middle, renders the button and nothing else:

```jsx title="src/CommentFooter.jsx"
import PostButton from './PostButton.jsx';

export default function CommentFooter() {
  return (
    <div>
      ~<PostButton />~ {/* No pending prop: the button asks the form itself */}
    </div>
  );
}
```

And `App` renders the comment section:

```jsx title="src/App.jsx"
import CommentSection from './CommentSection.jsx';

export default function App() {
  return <CommentSection />;
}
```

### Who sets pending? React DOM does

**Our code never writes `pending`, and no prop reaches `PostButton`. Still, the button reads `Posting...` for one second and cannot be clicked.**

React DOM does the work. React DOM is the part of React, in the `react-dom` package, that works with the browser page (Lesson 7). Here is what happens, in order:
1. The user clicks Post. The button has `type="submit"`, so the click submits the form (Lesson 11).
2. React DOM starts the action of the form, `postAction`. The form is now pending, so the Hook in `PostButton` returns `pending` as `true`. React renders the button again, and it reads `Posting...` and turns off.
3. `addComment` waits one second for `saveComment`, then returns the list with `Nice photo!` added.
4. The submission is over. `pending` goes back to `false`, the button reads Post again, and React empties the `<input>` field (Lesson 41).


```tree dir=right caption="Where the value of pending comes from: React DOM fills it from the form, and the button only reads it."
How `pending` reaches `PostButton`
- +1. The user clicks Post [`type="submit"`] | The click **submits the form**
- +2. React DOM marks the form as submitting | The form above `PostButton` is **pending**
- +3. `PostButton` asks the form [`useFormStatus`] | `pending` is **`true`**: the button reads **Posting...** and turns off
- +4. The action finishes | `pending` is **`false`**: the button reads **Post** again
```

### Mistake: the import from 'react'

Every Hook in this book so far came from `'react'`, such as `useState` and `useActionState`. So the first import a developer writes is the wrong one:

```jsx title="The two import lines a developer might write"
import { ~useFormStatus~ } from 'react'; // **WRONG:** 'react' has no useFormStatus, so the page breaks with an error
import { ~useFormStatus~ } from 'react-dom'; // The right package: React DOM provides this Hook
```

Why `'react-dom'`? Because a `<form>` exists only on a web page. The React docs list `useFormStatus` among the Form Hooks of React DOM. They work only in web apps that run in the browser. Apps for iOS, Android, or Windows do not support them.

## PRINCIPLE | `useFormStatus` next to the `<form>` tag: `pending` stays `false` on every submit

> [!PRINCIPLE]
> **Principle 2: pending Stays false Next to the form Tag**
>
> *Call `useFormStatus` in a component rendered inside the `<form>`. In the component that renders the `<form>` tag, `pending` is never `true`.*
>
> The Hook looks only above the component that calls it. A form in the component's own return sits below it, so the Hook does not see that form, and `pending` stays `false` on every submit. Nothing in the Console says why. On the page, the button stays clickable during the wait, and the user can post the same comment twice.
>
> **DO THIS:**
> ```jsx
> function PostButton() {
>   const { ~pending~ } = useFormStatus(); // PostButton sits inside the form, so pending works
>   return <button type="submit" disabled={pending}>Post</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function CommentSection() {
>   const { ~pending~ } = useFormStatus(); // **WRONG:** this component renders the form, so pending stays false
>   return <form action={postAction}><button type="submit" disabled={pending}>Post</button></form>;
> }
> ```

### VS | `useFormStatus` in `Form` vs. in `Submit`: the same line, only the component inside the form sees `pending`

Here are two components from the React docs. Both call `useFormStatus` with the exact same line:

```jsx title="The same Hook line, next to the form tag and inside the form"
function Form() {
  const { ~pending~ } = useFormStatus(); // **WRONG:** this component renders the form, so pending is never true
  return <form action={submit}></form>;
}

function Submit() {
  const { ~pending~ } = useFormStatus(); // Submit is rendered inside the form, so pending is true while it submits
  return <button disabled={pending}>Submit</button>;
}
```

It looks the same, but it is NOT the same thing! Remember the walk: React starts at the component that calls the Hook, not at the `<button>` tag, and walks only up.
- **In `Form`**, the `<form>` tag is in the component's own return. It sits below `Form`, not above it. Walking up from `Form` never meets it, so `pending` stays `false`.
- **In `Submit`**, the `<form>` tag sits above `Submit`, because the form renders `<Submit />`. Walking up from `Submit` meets that form, so `pending` is `true` while it submits.

The React docs: "The `useFormStatus` Hook must be called from a component that is rendered inside a `<form>`." And what happens otherwise: it "will only return status information for a parent `<form>`. It will not return status information for any `<form>` rendered in that same component or children components."

```tree caption="useFormStatus next to the form tag vs. inside the form: the same line of code, two different results."
Where the component that calls `useFormStatus` sits
- !Next to the `<form>` tag [`function Form`] | The form is in the component's **own return**, below it | `pending` is **always `false`**
- +Inside the `<form>` [`function Submit`] | The form is **above** the component | `pending` is **`true`** while the form submits
```

### Mistake: the Hook in CommentSection

A developer learns `useFormStatus` and adds it to the component that already has the form, `CommentSection`. The button is written right inside the form, with no `CommentFooter` and no `PostButton`:

```jsx title="src/CommentSection.jsx, with useFormStatus next to the form tag"
import { useActionState } from 'react';
import { useFormStatus } from 'react-dom';
import { saveComment } from './api.js';

async function addComment(previousComments, formData) {
  const comment = await saveComment(formData.get('comment'));
  return [...previousComments, comment];
}

export default function CommentSection() {
  const [comments, postAction] = useActionState(addComment, [{ id: 0, text: 'Great shot!' }]);
  const { ~pending~ } = useFormStatus(); // **WRONG:** CommentSection renders the form, so pending stays false
  return (
    <section>
      <ul>
        {comments.map(comment => <li key={comment.id}>{comment.text}</li>)}
      </ul>
      <form action={postAction}>
        <input name="comment" placeholder="Add a comment..." />
        <button type="submit" disabled={pending}>
          {pending ? 'Posting...' : 'Post'}
        </button>
      </form>
    </section>
  );
}
```

**Beware! The button never changes, and the user can post the same comment twice.** Here is what the user meets:
1. The user types `Nice photo!` and clicks Post.
2. The button keeps reading Post, and it can still be clicked during the whole second.
3. The user sees no sign that the click worked, so the user clicks Post again. The field still holds `Nice photo!`, because React empties it only after the action finishes (Lesson 41).
4. The second click submits the same text again, and `Nice photo!` appears twice in the list.

```page caption="The broken page during the one-second wait: the button still reads Post and can be clicked again."

```


The Console stays quiet. React prints no error and no warning here. The docs only say that "`pending` will never be true". In the Elements panel, the button never gets the `disabled` attribute.

Many developers then give up on the Hook and add a `useState` flag by hand, set before the request and cleared after it. There is no need. The docs give the fix: "call `useFormStatus` from inside a component that is located inside `<form>`". On our page, that component is `PostButton`, exactly as Principle 1 wrote it.

### The owner of the form already has its own flag

When `CommentSection` itself needs to know about the wait, it does not need `useFormStatus` at all. It already gets `isPending` from `useActionState` (Lesson 42). So each component has its own tool:
- **The owner of the form**, `CommentSection`, reads `isPending` from `useActionState`.
- **A component inside the form**, such as `PostButton`, reads `pending` from `useFormStatus`.

Context follows the same rule: a provider in the same component does not count, only a provider above it (Lesson 28).

## PRINCIPLE | `useFormStatus` in the button: the components in the middle pass no `pending` prop

> [!PRINCIPLE]
> **Principle 3: The Components in the Middle Pass No pending Prop**
>
> *Let the component that needs the status of the form call `useFormStatus` itself, so the components between the form and that component pass no `pending` prop.*
>
> With a `pending` prop, every component between the form and the button must receive the prop and hand it on, even though it never uses it. One forgotten prop leaves the button stuck on Post. With `useFormStatus` in the button, the button asks the form directly, through any number of components in the middle, and the user sees the exact same button.
>
> **DO THIS:**
> ```jsx
> function CommentFooter() {
>   return <div>~<PostButton />~</div>; // No pending prop: PostButton calls useFormStatus
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function CommentFooter({ pending }) {
>   return <div>~<CommentActions />~</div>; // **WRONG:** pending is dropped here, so the button never turns off
> }
> ```

### VS | A `pending` prop vs. `useFormStatus` in the button: the same button, only `CommentFooter` changes

Here is `CommentFooter`, the component in the middle, written two ways. First with a `pending` prop:

```jsx title="CommentFooter with a pending prop"
function CommentFooter({ ~pending~ }) { // Receives pending only to hand it on
  return <PostButton pending={pending} />;
}
```

Then with `useFormStatus` in the button:

```jsx title="CommentFooter with useFormStatus in the button"
function CommentFooter() { // Mentions no pending at all
  return ~<PostButton />~; // PostButton asks the form itself
}
```

In both versions, the submission of the form decides what the button shows. The one difference is in the middle. With the prop, `CommentFooter` receives `pending` and never uses it. With `useFormStatus` in the button, `CommentFooter` does not mention it.

### The whole page with a pending prop

Here is the older way on our page, before `useFormStatus`. `CommentSection` takes `isPending` from `useActionState` and passes it down:

```jsx title="src/CommentSection.jsx, with a pending prop" startLine="10"
export default function CommentSection() {
  const [comments, postAction, ~isPending~] = useActionState(addComment, [{ id: 0, text: 'Great shot!' }]); // true while addComment runs
  return (
    <section>
      <ul>
        {comments.map(comment => <li key={comment.id}>{comment.text}</li>)}
      </ul>
      <form action={postAction}>
        <input name="comment" placeholder="Add a comment..." />
        ~<CommentFooter pending={isPending} />~ {/* 1. The owner hands the flag down */}
      </form>
    </section>
  );
}
```

`CommentFooter` receives the prop and hands it on:

```jsx title="src/CommentFooter.jsx, with a pending prop"
import PostButton from './PostButton.jsx';

export default function CommentFooter({ pending }) {
  return (
    <div>
      ~<PostButton pending={pending} />~ {/* 2. The middle component only passes it through */}
    </div>
  );
}
```

And `PostButton` reads it as a prop:

```jsx title="src/PostButton.jsx, with a pending prop"
export default function PostButton({ ~pending~ }) { // 3. The button finally uses it
  return (
    <button type="submit" disabled={pending}>
      {pending ? 'Posting...' : 'Post'}
    </button>
  );
}
```

On the screen, it is the exact same thing! The button reads `Posting...` for the same second and reads Post again after the answer. The two flags are `true` during the same wait: `isPending` while the action runs, and `pending` while the form submits that same action.

```tree caption="A pending prop and useFormStatus give the same button, only the component in the middle changes."
Two ways the Post button gets the pending state of the form
- +With a `pending` prop [`<CommentFooter pending={isPending} />`] | `CommentFooter` **receives `pending` and only hands it on** | The button reads **Posting...** during the wait
- +With `useFormStatus` [`<CommentFooter />`] | `CommentFooter` **mentions no `pending`** | **Exact same button**: it reads **Posting...** during the wait
```

Passing a value through components that do not use it is called prop drilling (Lesson 28). The React docs describe the cost: "passing props can become verbose and inconvenient when you need to pass some prop deeply through the tree". Here the prop is `pending`, and `CommentFooter` carries it only for the button.

### Mistake: one more component in the middle

**The difference shows up the day the page changes. With the prop, every new component in the middle must hand `pending` on, and one forgotten prop leaves the button stuck on Post.**

Say a developer wraps the Post button in a new row component, `CommentActions`, to place an emoji button next to it later. With the prop version, `CommentActions` must also receive `pending` and hand it on. The developer forgets:

```jsx title="src/CommentFooter.jsx, with a pending prop and one more component in the middle"
import PostButton from './PostButton.jsx';

export default function CommentFooter({ pending }) {
  return (
    <div>
      ~<CommentActions />~ {/* **WRONG:** pending is not handed on, so PostButton reads Post forever */}
    </div>
  );
}

function CommentActions({ pending }) {
  return <PostButton pending={pending} />;
}
```

`PostButton` now receives no `pending`. The button never turns off, and the user can post the same comment twice, as in Principle 2.

With `useFormStatus` in the button, the same change needs nothing else. The button still sits inside the same `<form>`, now two components down, and it still asks that form:

```jsx title="src/CommentFooter.jsx, with useFormStatus in the button and one more component in the middle"
import PostButton from './PostButton.jsx';

export default function CommentFooter() {
  return (
    <div>
      <CommentActions />
    </div>
  );
}

function CommentActions() {
  return ~<PostButton />~; // Still inside the form, so useFormStatus still finds it
}
```

The React docs ask only that the component is "rendered inside a `<form>`". They set no limit on how many components sit in between.

### Why the button is its own component

Real teams write one submit button and reuse it in every form of the app: the comment form, the sign-up form, the settings page. The React blog calls such a reusable piece a design component, and it names this exact case: "In design systems, it's common to write design components that need access to information about the `<form>` they're in, without drilling props down to the component."

One limit: `useFormStatus` reads only the submission of a form. Any other value that many components share still needs props or context (Lesson 28).

## PRINCIPLE | `data` from `useFormStatus`: the form data being submitted, or `null` when nothing is submitted

> [!PRINCIPLE]
> **Principle 4: data Holds the Comment Being Posted, or null**
>
> *Read `data` from `useFormStatus` to show what the parent form is submitting, and check that `data` is not `null` before you call `data.get`.*
>
> While the form submits, `data` holds the same form data that the action receives, so a component inside the form can show the text of the user on the screen. The rest of the time, `data` is `null`. Calling `data.get` on the first render, before any submit, throws an error and empties the page.
>
> **DO THIS:**
> ```jsx
> const { data } = useFormStatus();
> return <div>{~data &&~ <p>Posting "{data.get('comment')}"...</p>}</div>; // The line shows only during a submission
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const { data } = useFormStatus();
> return <div><p>Posting "{~data.get('comment')~}"...</p></div>; // **WRONG:** data is null before the first submit, so this throws
> ```

The status object holds a second useful field, `data`. A component inside the form reads it the same way it reads `pending`:

```jsx title="Reading data from useFormStatus"
const { ~data~ } = useFormStatus(); // The form data being submitted, or null

{~data &&~ <p>Posting "{data.get('comment')}"...</p>} {/* Shows the line only during a submission */}
```

The React docs: "An object implementing the `FormData interface` that contains the data the parent `<form>` is submitting. If there is no active submission or no parent `<form>`, it will be `null`."

### VS | `formData.get` in the action vs. `data.get` in a component: the same text, read in two places

So `data` is the same kind of object as the `formData` that our action receives (Lesson 40). You read it the same way, with `get` and the `name` of the field:
- **`formData.get('comment')` in `addComment`**: the action reads the text that the user sent.
- **`data.get('comment')` in a component inside the form**: the screen reads that same text while it is on its way.

Yes, it is the exact same thing! Both read the form data of the same submission, so both give `Nice photo!`. The only difference is the place. One runs inside the action, the other inside a component on the screen.

### A line under the field while the comment is on its way

Now we use `data` on our page. `CommentFooter` sits inside the form too, so it can call the Hook as well. It shows a line with the text being posted, above the button:

```jsx title="src/CommentFooter.jsx"
import { useFormStatus } from 'react-dom';
import PostButton from './PostButton.jsx';

export default function CommentFooter() {
  const { ~data~ } = useFormStatus(); // CommentFooter is inside the form too
  return (
    <div>
      {~data &&~ <p>Posting "{data.get('comment')}"...</p>} {/* Only while the form submits */}
      <PostButton />
    </div>
  );
}
```

`PostButton`, `CommentSection`, and the server file do not change. Here is the page through one comment:
1. Before the first submit, `data` is `null`, so no line shows under the field.
2. The user types `Nice photo!` and clicks Post.
3. During the wait, the line `Posting "Nice photo!"...` appears, and the button reads `Posting...`.
4. When the submission ends, `data` is `null` again, and the line disappears.

```page caption="The finished page before any submit: no line under the field."
card: lines=Great shot! | input=Add a comment...
line: [Post]
console: quiet
```

```page caption="The finished page during the wait: a line shows the comment being posted, and the button reads Posting..."
card: lines=Great shot! | typed=Nice photo!
line: Posting "Nice photo!"... | good
line: [Posting...] | good
console: quiet
```

```page caption="The finished page after the wait: the line is gone, and Nice photo! is in the list."
card: lines=Great shot!; Nice photo! | input=Add a comment...
line: [Post]
console: quiet
```

The line shows only what is being sent. It does not put the new comment in the list early. Showing the comment in the list before the server answers is the job of `useOptimistic`, in Lesson 44.

### Mistake: data.get before the first submit

A developer sees `data` work during the wait, drops the check, and writes the line directly:

```jsx title="src/CommentFooter.jsx, reading data with no check"
export default function CommentFooter() {
  const { data } = useFormStatus();
  return (
    <div>
      <p>Posting "{~data.get('comment')~}"...</p> {/* **WRONG:** data is null on the first render, so this throws */}
      <PostButton />
    </div>
  );
}
```

The page breaks before the user can type a letter. On the first render, nothing is being submitted, so `data` is `null`. And `null` has no `get` method. The browser throws an error, and React removes everything it rendered, so the page is blank:

```page width=full caption="The page with data.get and no check: the first render throws, and nothing is left on the page."
blank
console: Uncaught TypeError: Cannot read properties of null (reading 'get')
  warn: An error occurred in the <CommentFooter> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The fix is the check from our finished file: show the line only when `data` is there, with `data &&` in front of it. The React docs write the same check as a ternary that shows an empty text when `data` is `null`.

## All 4 Principles Together

### The complete project

Here are the five files of the finished comment page. The form lives in `CommentSection`. Both `CommentFooter` and `PostButton` sit inside it, and both ask it for its status:

```js title="src/api.js"
let nextId = 1;

export async function saveComment(text) {
  await new Promise(resolve => setTimeout(resolve, 1000));
  return { id: nextId++, text };
}
```

```jsx title="src/App.jsx"
import CommentSection from './CommentSection.jsx';

export default function App() {
  return <CommentSection />;
}
```

```jsx title="src/CommentSection.jsx"
import { useActionState } from 'react';
import { saveComment } from './api.js';
import CommentFooter from './CommentFooter.jsx';

async function addComment(previousComments, formData) {
  const comment = await saveComment(formData.get('comment'));
  return [...previousComments, comment];
}

export default function CommentSection() {
  const [comments, postAction] = useActionState(addComment, [{ id: 0, text: 'Great shot!' }]);
  return (
    <section>
      <ul>
        {comments.map(comment => <li key={comment.id}>{comment.text}</li>)}
      </ul>
      ~<form action={postAction}>~ {/* Principle 2: the form is above CommentFooter and PostButton */}
        <input name="comment" placeholder="Add a comment..." />
        <CommentFooter />
      </form>
    </section>
  );
}
```

```jsx title="src/CommentFooter.jsx"
import { useFormStatus } from 'react-dom';
import PostButton from './PostButton.jsx';

export default function CommentFooter() {
  const { ~data~ } = useFormStatus(); // Principle 4: the text being posted, or null
  return (
    <div>
      {data && <p>Posting "{data.get('comment')}"...</p>}
      ~<PostButton />~ {/* Principle 3: no pending prop */}
    </div>
  );
}
```

```jsx title="src/PostButton.jsx"
import { ~useFormStatus~ } from 'react-dom'; // Principle 1: from react-dom, not react

export default function PostButton() {
  const { ~pending~ } = useFormStatus(); // Principle 2: called inside the form, so pending works
  return (
    <button type="submit" disabled={pending}>
      {pending ? 'Posting...' : 'Post'}
    </button>
  );
}
```

### How React calls the components, in order

When the page loads, React calls the components from the top down, in the order of the tree below. When a submit starts and when it ends, React calls `CommentFooter` and `PostButton` again, and both read the new status of the form:

```tree caption="The component tree of the comment page, the order in which React calls each component, and where each one reads the status of the form."
`App` [1. Called first] | Renders `<CommentSection />`
- +`CommentSection` [2. Called second] | **Owns the list and renders the `<form>`** | Does not call `useFormStatus`: the form is in its own return
  - +`CommentFooter` [3. Called third, inside the form] | Calls `useFormStatus` and reads **`data`** | Shows **Posting "Nice photo!"...** during the wait
    - +`PostButton` [4. Called fourth, inside the form] | Calls `useFormStatus` and reads **`pending`** | Reads **Posting...** and turns off during the wait
```

| Mistake | What the user sees | The fix |
| :--- | :--- | :--- |
| **The import from `'react'`** | The page breaks with an error | Import `useFormStatus` from `'react-dom'` |
| **The Hook next to the `<form>` tag** | The button stays on Post, and the comment is posted twice | Call the Hook in a component inside the `<form>` |
| **A `pending` prop through the middle** | One forgotten prop, and the button never turns off | Let the button ask the form, and pass nothing through the middle |
| **`data.get` with no check** | The first render throws, and the page is blank | Show the line only when `data` is not `null` |

One last time, the sentence of this lesson: **`useFormStatus` asks the closest `<form>` above your component: "Are you submitting right now?" The form must be above the component, never in its own return.**

## For the Interview

> **The Interview Question:** How does a field nested deep in a form read the form's pending state?

### How to Answer Clearly in 30 Seconds

"The field or the button calls `useFormStatus`, a Hook from `'react-dom'`. It takes no arguments and returns the status of the parent form: `pending`, `data`, `method`, and `action`. `pending` is `true` while that form is submitting, so a Post button can turn off and read `Posting...`. Three rules keep it working:
1. **Call it inside the form**: the Hook reads only a form above the component. In the component that renders the `<form>` tag itself, `pending` is never `true`, and no error tells you so.
2. **No prop drilling**: the components between the form and the button pass nothing. The React blog says the Hook reads the parent form as if the form was a Context provider.
3. **Check `data`**: `data` holds the form data being submitted, and it is `null` when nothing is being submitted."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"I called `useFormStatus` in my form component, and `pending` is always `false`. Why?"**
   Because the Hook reads only a parent `<form>`, a form above the component that calls it. A form in the component's own return sits below it, so the Hook does not see it. With no form above, the Hook returns `pending` as `false`, and `data`, `method`, and `action` as `null`. The fix is to move the Hook into a component rendered inside the form, such as the submit button. If the owner of the form needs the flag itself, it reads `isPending` from `useActionState`.
2. **"What is the difference between `isPending` from `useActionState` and `pending` from `useFormStatus`?"**
   They answer the same question for two different components. `isPending` goes to the component that calls `useActionState`, which is usually the component that owns the form. `pending` goes to any component inside the form, at any depth, without a prop. On one page, the owner uses `isPending`, and the reusable submit button uses `pending`.
3. **"Why does `useFormStatus` come from `'react-dom'`, and what do `method` and `action` hold?"**
   It is one of the Form Hooks of React DOM, which work only in web apps that run in the browser, because `<form>` is a browser element. During a submission, `method` is the string `'get'` or `'post'`, taken from the `method` prop of the form, and `'get'` when the form has no `method` prop. Our comment form has a function in its `action` prop and no `method` prop, so `method` reads `'get'` during the wait. React does not want a `method` prop on such a form. When the form has `method="post"` next to a function, the Console shows this error: "Cannot specify a encType or method for a form that specifies a function as the action. React provides those automatically. They will get overridden." `action` is a reference to the function passed to the `action` prop of the parent form. It is `null` when there is no parent form, when the form has a URL in its `action` prop, or when the form has no `action` prop at all.

```tree caption="Interview comparison: which component reads the pending state of the form, and with which tool."
Who reads the pending state of one form
- +The owner of the form [`CommentSection`] | Calls `useActionState` | Reads **`isPending`**
- +A component inside the form [`PostButton` `CommentFooter`] | Calls `useFormStatus` | Reads **`pending`** and **`data`**, with no prop
- !The owner of the form calling `useFormStatus` | The form is **in its own return**, not above it | `pending` is **always `false`**
```
