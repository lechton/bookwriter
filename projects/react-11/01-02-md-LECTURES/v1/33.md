# Lecture 33: Fetching Data in an Effect, with Loading, Errors, and Race Conditions

*(How does a component load data from a server, and always show the right answer?)*

> INTERVIEW QUESTION | ❱ CORE | How do you fetch data from an API in a client component, and how do you handle loading, error, and race conditions?

---

## VS | The Order of the Clicks vs. the Order of the Answers: the last click does not always get the last answer

**When you fetch data inside `useEffect`, server answers can arrive out of order. Your Effect needs a cleanup flag so a slow answer from an older click never overwrites a newer click on the screen.**

Say a profile page has two buttons: Alice and Bob. The user clicks Alice, and half a second later changes their mind and clicks Bob. If Alice's server request happens to be slow and finishes after Bob's, Alice's bio suddenly replaces Bob's bio on the page.

**Why:** Starting a `fetch` for Bob does not stop the earlier `fetch` for Alice. Both requests keep running in the background, and whichever answer arrives last updates the screen. Returning a cleanup function that marks Alice's Effect as ignored ensures only the latest click can update the state.

Let's start with what you already know. In plain JavaScript, you ask a server for data with `fetch`, a function the browser gives every page. Then you put the answer into the page yourself:

```js title="Plain JavaScript: ask the server for Alice's bio and put it on the page"
~fetch('/api/bio/Alice')~ // Sends the request, and returns a promise at once
  .then(response => ~response.json()~) // When the server answers: reads the JSON
  .then(data => {
    document.getElementById('bio').textContent = data.bio; // Writes the bio into the paragraph
  });
```

Notice what `fetch` gives back. It does not give back the bio. The bio is not here yet, because the server has not answered. So `fetch` gives back a promise, at once.

> [!DEFINITION]
> **What is a promise?** [NEW] A promise is a JavaScript object that stands for a value that arrives later.
> `fetch` returns one at once, before the server has answered. So you cannot read the bio on the next line.
> Instead, you hand the promise a function with `.then`. When the value arrives, JavaScript calls that function with it.
> `response.json()` reads the body of the answer and turns its JSON text into a JavaScript object. Reading takes time too, so it also returns a promise. That is why there are two `.then` calls.
> When something fails, the promise skips the `.then` functions and calls the function you gave to `.catch` (Lesson 33).

The server sends its answer as JSON, the text format servers use for data: `{ "bio": "This is Alice’s bio." }`. So the name `bio` in `data.bio` comes from the server, not from our code.

### Where does fetch go in React?

In React, you never write into the page with `textContent`. You put the bio into state, and React draws the page from it. So the last step becomes `setBio(data.bio)`.

The real question is where the request goes. A component has three places for code, from Lesson 32:
1. **The body.** It runs on every render, and it must only calculate. A request there would go out on every render.
2. **An event handler.** It runs when the user clicks. But the bio must load when the component appears, and nobody clicks for that.
3. **An Effect.** It runs because the component is on the screen. This is the place.

React's docs make the same point for a search page: "While this component is visible, you want to keep `results` synchronized with data from the network."

```jsx title="React: ask for the bio of person, after Bio is on the screen"
useEffect(() => {
  ~fetch('/api/bio/' + person)~ // Runs after Bio is on the screen, and again when person changes
    .then(response => response.json())
    .then(data => ~setBio(data.bio)~); // The bio arrives later, and React renders again
}, [person]);
```

> [!DEFINITION]
> **An Effect and its cleanup.** [REVIEW] An Effect is code that React runs because the component is on the screen, not because the user clicked.
> You write it with `useEffect`. React runs your setup function after it puts the component on the page, and again whenever a value in the array changes.
> The setup can return a cleanup function. React calls it before it runs the setup again, and when the component leaves the page.
> Lesson 32 ended with a list of what each setup needs from its cleanup. A timer needs `clearInterval`. A `fetch` needs one of two things: cancel the request, or ignore its answer (Lesson 32).

### Some time later: the two problems

Between the request and the answer, time passes. Two problems follow from that, and they are the whole lesson:
1. **The page must show something while it waits.** React puts the page on the screen before the bio arrives. So the page needs `Loading...` for the wait, and an error line for the case where the server fails.
2. **The answers do not always come back in the order the user clicked.** React's docs say it plainly: "network responses may arrive in a different order than you sent them."

The second problem is the dangerous one. Here is how it looks on a team page:

```tree dir=right caption="The user clicks Bob, then Taylor, and the two answers come back in the other order."
Two clicks, two answers, in the wrong order
- +1. Click Bob | The request for Bob goes out | The server needs **two seconds**
- +2. Click Taylor | The request for Taylor goes out | The server needs **a fifth of a second**
- +3. Taylor's answer | Arrives **first** | The page shows **Taylor's bio**
- !4. Bob's answer | Arrives **last** | The page shows **Bob's bio under Taylor's name**
```

The page now shows Taylor's name with Bob's bio under it. There is no error, and the Console is quiet.

Something that can be tricky: on the developer's fast machine, the answers always come back in order. So the developer never sees the bug. A user on a slow phone sees it often.

### The Rule of Thumb: every fetch Effect needs three things

**A loading line for the wait, an error line for a failed server, and a cleanup that drops the old answer.**

A senior developer also knows the four classic mistakes:
1. **Thinking the last click gets the last answer.** The network answers in its own order.
2. **No cleanup.** Nothing stops an old answer from replacing the new one.
3. **Expecting `fetch` to fail when the server fails.** It does not. A server that answers with an error is still an answer.
4. **Showing a stopped request as an error.** When your own cleanup stops a request, nothing went wrong.

The rest of the lesson shows each mistake on a real page.

## SECTION | A Team Page with Three Names

Our page has three buttons: Alice, Bob, and Taylor. Under them sit the name of the person chosen and a `<p>` element for that person's bio. The page opens on Alice.

```page width=text caption="The team page when it opens: the paragraph under Alice's name shows Loading... and never changes."
line: [Alice] [Bob] [Taylor]
heading: Alice
line: Loading...
console: quiet
```

Here is what the user does, and what each click must change:
1. The page opens. The paragraph shows `Loading...`, then Alice's bio.
2. The user clicks Bob. The paragraph shows `Loading...` for two seconds, then Bob's bio.
3. The user clicks Bob and then Taylor at once. The page must end on Taylor's bio.

The server answers at an address such as `/api/bio/Alice`. It answers in a fifth of a second for Alice and Taylor, and in two seconds for Bob. This is the same page as in React's docs.

`App` keeps `person` in state and passes it to `Bio`:

```jsx title="src/App.jsx"
import { useState } from 'react';
import Bio from './components/Bio.jsx';

export default function App() {
  const [person, setPerson] = useState('Alice');

  return (
    <main>
      <button ~onClick={() => setPerson('Alice')}~>Alice</button> {/* Each click sets person */}
      <button onClick={() => setPerson('Bob')}>Bob</button>
      <button onClick={() => setPerson('Taylor')}>Taylor</button>
      <h2>{person}</h2>
      ~<Bio person={person} />~ {/* Bio must show the bio of this person */}
    </main>
  );
}
```

At the start, `Bio` only has a place for the bio:

```jsx title="src/components/Bio.jsx"
import { useState } from 'react';

export default function Bio({ person }) {
  const [bio, setBio] = useState(null);

  return <p>{~bio ?? 'Loading...'~}</p>; // bio is null, so the paragraph shows Loading...
}
```

`bio` starts as `null`, because no bio has arrived yet. The `??` operator gives the value on its right when the value on its left is `null` or `undefined`. So while `bio` is `null`, the paragraph shows `Loading...`.

Ten seconds later, it still shows `Loading...`. No line of our code asks the server for anything.

The entry file mounts `App` inside `<StrictMode>`, as in Lesson 07. Here are the files:

```files title="team-page: File Explorer" caption="How the team page project files sit inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it inside `<StrictMode>`
  App.jsx | parent | Keeps `person` in state, renders the three buttons, and passes `person` to `Bio`
  components/
    Bio.jsx | Effect | Keeps `bio` in state and asks the server for the bio of `person` in an Effect
```

**PRINCIPLES:** The server answers later, and not always in order. Four principles follow:
1. **Principle 1: fetch Inside useEffect Loads the Bio of Each person.** The request goes in an Effect with `person` in its array, and the paragraph shows `Loading...` until the bio arrives.
2. **Principle 2: response.ok Turns a Server Error into the Error Line.** `fetch` fails only when it cannot reach the server. When the server answers with an error, our code must check `response.ok`.
3. **Principle 3: The ignore Variable Drops a Late Answer.** The cleanup marks the old request, and its answer is thrown away when it arrives.
4. **Principle 4: AbortController Stops the Old Request.** The cleanup stops the old request itself. The stopped request fails with an `AbortError`, which is not an error for the user.

## PRINCIPLE | `fetch` in `useEffect`: every new `person` sends a new request

> [!PRINCIPLE]
> **Principle 1: fetch Inside useEffect Loads the Bio of Each person**
>
> *When a component must show server data for its props, it calls fetch inside useEffect, lists those props in the array, and sets state when the answer arrives. While the state is still null, the JSX shows a loading line.*
>
> The request goes in an Effect because the bio must match person while Bio is on the screen, not because of a click. The address is built from person, so person goes in the array, and every new name sends a new request. Setting bio back to null at the start of each run brings back Loading... for the wait.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   setBio(null);
>   fetch('/api/bio/' + person)
>     .then(response => response.json())
>     .then(data => setBio(data.bio));
> }, ~[person]~); // A new request each time the user clicks a name
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   fetch('/api/bio/' + person)
>     .then(response => response.json())
>     .then(data => setBio(data.bio));
> }, ~[]~); // **WRONG:** runs only on mount, so the page keeps Alice's bio after a click on Bob
> ```

We move the request into `useEffect`, and the second `.then` puts the bio into state:

```jsx title="src/components/Bio.jsx" startLine="1"
import { useState, ~useEffect~ } from 'react'; // useEffect comes from react, as in Lesson 32

export default function Bio({ person }) {
  const [bio, setBio] = useState(null);

  useEffect(() => {
    ~setBio(null);~ // Shows Loading... again while the new bio is on its way
    fetch('/api/bio/' + person)
      .then(response => response.json())
      .then(data => ~setBio(data.bio)~); // The bio arrives, and React renders the paragraph again
  }, ~[person]~); // The Effect reads person, so it runs again whenever person changes

  return <p>{bio ?? 'Loading...'}</p>;
}
```

Here is what happens, step by step:
1. React renders `Bio`. `bio` is `null`, so the paragraph shows `Loading...`.
2. React puts the page on the screen, then runs the Effect. The request for Alice goes out.
3. A fifth of a second later, the answer arrives, and `setBio` puts Alice's bio into state.
4. React renders `Bio` again, and the paragraph shows the bio.

```page width=text caption="The team page a moment after it opens: the Effect has loaded Alice's bio."
line: [Alice] [Bob] [Taylor]
heading: Alice
line: This is Alice’s bio. | good
console: quiet
```

Then the user clicks Bob. `person` changes, so React runs the Effect again for Bob. For two seconds the paragraph shows `Loading...`, then Bob's bio:

```page width=text caption="The team page right after the user clicks Bob: Loading... for two seconds, while the server answers."
line: [Alice] [Bob] [Taylor]
heading: Bob
line: Loading...
console: quiet
```

This `Loading...` is the loading state: what the component shows before the data arrives. It costs nothing extra. While we wait, `bio` is `null`, and the JSX already handles that case.

Why the line `setBio(null)` at the top of the setup? Without it, Alice's bio would stay under Bob's name for the two seconds his request takes.

### VS | `[person]` vs. `[]`: both load Alice, only `[person]` loads Bob

The array decides whether a click on a name brings a new bio:

```jsx title="The same Effect with [person] and with []"
useEffect(() => { /* fetch the bio of person */ }, ~[person]~); // Runs again after each click on a name
useEffect(() => { /* fetch the bio of person */ }, ~[]~); // **WRONG:** runs only on mount, so the page keeps Alice's bio
```

Both load Alice's bio when the page opens. With `[]`, React runs the Effect only on mount. The user clicks Bob, the heading changes to Bob, and the paragraph keeps Alice's bio. The linter from Lesson 32 reports `person` as a missing dependency.

### Two requests in development

Open the Network tab of the browser's developer tools. It lists every request the page sends. In development, you see two requests for Alice when the page opens.

This is Strict Mode, from Lesson 32. On mount, React runs the setup, the cleanup, and the setup again. Each setup sends a request. The docs: "In development, you will see two fetches in the Network tab. There is nothing wrong with that." And: "In production, there will only be one request."

Our Effect has no cleanup yet. Both answers call `setBio` with the same bio, so the page looks right. Principle 3 adds the cleanup that the docs count on.

## PRINCIPLE | `response.ok`: a server error shows the error line, not `Loading...` forever

> [!PRINCIPLE]
> **Principle 2: response.ok Turns a Server Error into the Error Line**
>
> *fetch fails only when the request cannot reach the server. When the server answers with an error status such as 500, the promise succeeds, so the code checks response.ok, throws an error when it is false, and shows the error line from .catch.*
>
> Without the check, the error answer goes on to response.json, the bio is undefined, and the page shows Loading... forever. With it, the error goes to .catch, the component keeps it in state, and the user sees an error line. Each new request clears the old error, so one bad answer does not stay on the page.
>
> **DO THIS:**
> ```jsx
> fetch('/api/bio/' + person)
>   .then(response => {
>     if (~!response.ok~) throw new Error('Status ' + response.status); // The error goes to catch
>     return response.json();
>   })
>   .then(data => setBio(data.bio))
>   .catch(err => setError(err));
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> fetch('/api/bio/' + person)
>   .then(response => ~response.json()~) // **WRONG:** a status 500 answer is read as a bio, and the page says Loading... forever
>   .then(data => setBio(data.bio));
> ```

Servers have bad moments. When something breaks on the server, it still answers. But it answers with an error status code.

> [!DEFINITION]
> **What is a status code?** [NEW] Every answer from a server carries a number, the status code. `200` means everything went well. `404` means not found. `500` means something broke on the server.
> In our code, the `response` object holds it. `response.status` is the number itself, such as `500`.
> `response.ok` is `true` for a status from `200` to `299`, and `false` for every other status.
> Something that can be tricky: `fetch` never checks it for you. The promise of `fetch` succeeds for a `500` answer too (Lesson 33).

### VS | A Lost Network vs. a Broken Server: for the user both mean no bio, for `fetch` only one is a failure

MDN, the reference for the web, says it plainly. The promise of `fetch` fails only when the request fails. For example, the address is badly formed, or the network is lost. It does not fail when the server answers with an error status, such as `404` or `504`.

So for the user, a broken server and a lost network are the same: no bio. For `fetch`, they are two different cases:
1. **A lost network.** No answer comes, so the promise fails, and `.catch` runs.
2. **A broken server.** An answer comes, so the promise succeeds, and the error sits inside the answer.

### The server fails, and the page says Loading... forever

Say the server breaks while the user looks at Alice. It answers with status `500` and the JSON `{ "message": "Server error" }`. Our code from Principle 1 has no check:
1. The setup sets `bio` to `null`, and the paragraph shows `Loading...`.
2. The server answers with status `500`.
3. `fetch` succeeds, because the server answered.
4. `response.json()` gives `{ message: 'Server error' }`. That object has no bio field, so `data.bio` is `undefined`.
5. `setBio` puts `undefined` into state. The `??` operator treats `undefined` like `null`, so the paragraph still shows `Loading...`.

```page width=text caption="The team page when the server answers with status 500 and the code has no check: Loading... with no end."
line: [Alice] [Bob] [Taylor]
heading: Alice
line: Loading... | bad
console: Failed to load resource: the server responded with a status of 500 (Internal Server Error)
console: Failed to load resource: the server responded with a status of 500 (Internal Server Error)
```

The user waits for a bio that will never come, and nothing on the page says why. The only sign is in the Console. The browser prints its own message about the status, once for each of the two requests in development. Our code never reads that status.

### The fix: check response.ok and throw

When `response.ok` is `false`, we turn the answer into an error ourselves, with `throw new Error`. A `throw` inside `.then` makes the promise fail. So the next `.then` is skipped, and the function in `.catch` runs with the error.

The text in the error, such as `Status 500`, is for the developer who inspects it. The user sees only the error line. We keep the error in a second state variable, `error`, and the JSX checks it first:

```jsx title="src/components/Bio.jsx" startLine="3" good="10,11,12,17"
export default function Bio({ person }) {
  const [bio, setBio] = useState(null);
  const [error, setError] = useState(null);

  useEffect(() => {
    setBio(null);
    ~setError(null);~ // Clears an old error before each new request
    fetch('/api/bio/' + person)
      .then(response => {
        if (~!response.ok~) { // Status 500: the server answered with an error
          throw new Error('Status ' + response.status); // Skips the next then and goes to catch
        }
        return response.json();
      })
      .then(data => setBio(data.bio))
      ~.catch(err => setError(err));~ // Keeps the error, and React shows the error line
  }, [person]);

  if (error) {
    return <p>Could not load the bio.</p>;
  }
  return <p>{bio ?? 'Loading...'}</p>;
}
```

Now the same broken server gives the user an answer:

```page width=text caption="The team page when the server answers with status 500 and the code checks response.ok: the error line."
line: [Alice] [Bob] [Taylor]
heading: Alice
line: Could not load the bio. | good
console: Failed to load resource: the server responded with a status of 500 (Internal Server Error)
console: Failed to load resource: the server responded with a status of 500 (Internal Server Error)
```

The browser still prints its message in the Console, because the server did answer with `500`. The difference is on the page: the user now knows the bio is not coming.

What is cool: the same `.catch` also runs when the network is lost, because then the `fetch` promise itself fails. One error line covers both cases.

### Why clearing the error at the top matters

The line `setError(null)` at the top of the setup matters as much as the check. Without it, the error stays in state after the user clicks another name. The new bio loads into `bio`. But the JSX checks `error` first, so the user still reads `Could not load the bio.` under a name whose bio loaded fine.

So the paragraph now has three states:
1. **The loading state.** `bio` is `null`, and the paragraph shows `Loading...`.
2. **The error state.** `error` holds an error, and the paragraph shows the error line.
3. **The data.** `bio` holds the bio, and the paragraph shows it.

Each new request starts from the loading state, with the old bio and the old error both cleared.

## PRINCIPLE | The `ignore` variable: a late answer for an old request never reaches the screen

> [!PRINCIPLE]
> **Principle 3: The ignore Variable Drops a Late Answer**
>
> *When the user clicks a new name before the old answer arrives, the old answer can arrive last and replace the new bio. The cleanup sets ignore to true, and each run of the setup sets state only while its own ignore is still false.*
>
> The network answers in its own order, not in the order the user clicked. Each run of the setup has its own ignore, and React runs the old cleanup before the new setup. So every answer except the last one requested is dropped. The bug shows no error, so the cleanup goes in every fetch Effect, not only after a user reports it.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   let ignore = false;
>   fetch('/api/bio/' + person)
>     .then(response => response.json())
>     .then(data => { ~if (!ignore)~ setBio(data.bio); }); // Only the current request sets the bio
>   return () => { ignore = true; };
> }, [person]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   fetch('/api/bio/' + person)
>     .then(response => response.json())
>     .then(data => ~setBio(data.bio)~); // **WRONG:** Bob's late answer replaces Taylor's bio
> }, [person]);
> ```

Take the code from Principle 2, with no cleanup. The user clicks Bob, and half a second later, Taylor:
1. The user clicks Bob. The Effect sends the request for Bob. The server needs two seconds. The paragraph shows `Loading...`.
2. The user clicks Taylor. The Effect sends the request for Taylor. The server needs a fifth of a second.
3. Taylor's answer arrives first. `setBio` puts Taylor's bio into state.
4. Bob's answer arrives more than a second later. Its `.then` still runs, because nothing told it that the user moved on. `setBio` puts Bob's bio into state.

```page width=text caption="The team page three seconds after the user clicks Bob and then Taylor, with no cleanup: Bob's bio under Taylor's name."
line: [Alice] [Bob] [Taylor]
heading: Taylor
line: This is Bob’s bio. | bad
console: quiet
```

> [!DEFINITION]
> **What is a race condition?** [NEW] A race condition is a bug where the result depends on which of two things finishes first.
> Here, two requests race. The request for Bob went out first, but its answer came back last, and it won.
> React's docs: "two different requests "raced" against each other and came in a different order than you expected."
> Something that can be tricky: there is no error, and the Console is quiet. On a fast network the answers come back in order, so only some users ever see it (Lesson 33).

### The ignore variable

The fix uses the cleanup from Lesson 32. Here is the idea in plain words: when the user clicks a new name, the old request becomes old news. Its answer may still arrive, but we must not use it.

So each run of the setup creates its own boolean variable, `ignore`, set to `false`. The cleanup of that run sets it to `true`. When the answer arrives, it sets state only if `ignore` is still `false`.

The docs show it with a function of their own, `fetchBio`. It returns a promise of the bio, the way `fetch` returns a promise of the answer:

```jsx title="The docs' ignore variable, with their fetchBio function"
useEffect(() => {
  ~let ignore = false;~ // This run's own variable
  fetchBio(person).then(result => {
    if (~!ignore~) { // Only while this run is still the current one
      setBio(result);
    }
  });
  return () => {
    ~ignore = true;~ // The cleanup marks this run's answer as one to drop
  };
}, [person]);
```

The docs: "Note the `ignore` variable which is initialized to `false`, and is set to `true` during cleanup."

How does the cleanup know which `ignore` to change? Every run of the setup is a new call of the setup function. So `let ignore = false` creates a new variable each time. The cleanup is created in that same call, so it sees that run's own `ignore`. It is the same reason the cleanup in Lesson 32 knew which `intervalId` to stop.

### The ignore variable in Bio

In `Bio`, the check guards both setters, so a late error is dropped too:

```jsx title="src/components/Bio.jsx" startLine="7" good="8,18,19,21"
  useEffect(() => {
    ~let ignore = false;~ // Each run of the setup gets its own variable
    setBio(null);
    setError(null);
    fetch('/api/bio/' + person)
      .then(response => {
        if (!response.ok) {
          throw new Error('Status ' + response.status);
        }
        return response.json();
      })
      .then(data => { if (!ignore) setBio(data.bio); }) // Only the current request sets the bio
      .catch(err => { if (!ignore) setError(err); }); // Only the current request sets the error
    return () => {
      ~ignore = true;~ // Runs when person changes: the old answer will be dropped
    };
  }, [person]);
```

Here are the same two clicks with the cleanup:
1. The user clicks Bob. The Bob run sends the request for Bob. Its own `ignore` is `false`.
2. The user clicks Taylor. Before the new setup, React runs the cleanup of the Bob run. The Bob run's `ignore` becomes `true`. Then the Taylor run sends the request for Taylor.
3. Taylor's answer arrives. The Taylor run's `ignore` is `false`, so the paragraph shows Taylor's bio.
4. Bob's answer arrives. The Bob run's `ignore` is `true`, so `setBio` is skipped.

```page width=text caption="The team page three seconds after the user clicks Bob and then Taylor, with the ignore variable: Taylor's bio under Taylor's name."
line: [Alice] [Bob] [Taylor]
heading: Taylor
line: This is Taylor’s bio. | good
console: quiet
```

The docs say the same of two users named Alice and Bob: "cleanup ensures that the `'Alice'` response is ignored even if it arrives after `'Bob'`."

Something that can be tricky: when the user clicks one name and waits, the code with the cleanup and the code without it give the same page. They differ only when the user clicks a second name before the first answer arrives. That is why a quick test hides the bug.

### The two requests in development, explained

The same `ignore` explains the docs' sentence from Principle 1. When the page opens, Strict Mode runs the setup, the cleanup, and the setup again. The cleanup sets the first run's `ignore` to `true`. So the first request still goes out, but its answer is dropped.

The docs: "even though there is an extra request, it won't affect the state". The check on `ignore` drops its answer.

### What ignore does not do

The `ignore` variable works for any promise, not only `fetch`. The docs' `fetchBio` is not `fetch` at all.

But look at what happens to Bob's request. It still runs to the end. The server still does the work, and the browser still waits for Bob's bio and reads it, only for our code to throw it away. Principle 4 stops the request itself.

## PRINCIPLE | `AbortController`: the cleanup stops the old request, and `.catch` skips the `AbortError`

> [!PRINCIPLE]
> **Principle 4: AbortController Stops the Old Request**
>
> *With fetch, the cleanup can stop the old request. The setup creates an AbortController and passes controller.signal to fetch, and the cleanup calls controller.abort. The stopped fetch fails with an AbortError, which .catch must skip, because it is not an error for the user.*
>
> The ignore variable lets the old request finish and drops its answer. controller.abort stops the old request, so no answer comes, and the browser stops waiting for it. The stop itself makes the promise fail, so .catch checks err.name and shows the error line only for a real error.
>
> **DO THIS:**
> ```jsx
> const controller = new AbortController();
> fetch('/api/bio/' + person, { signal: controller.signal })
>   .then(response => response.json())
>   .then(data => setBio(data.bio))
>   .catch(err => { ~if (err.name === 'AbortError') return;~ setError(err); }); // Skips our own stop
> return () => controller.abort();
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const controller = new AbortController();
> fetch('/api/bio/' + person, { signal: controller.signal })
>   .then(response => response.json())
>   .then(data => setBio(data.bio))
>   ~.catch(err => setError(err));~ // **WRONG:** our own stop shows the error line on a page that works
> return () => controller.abort();
> ```

The browser has a tool that stops a `fetch` before it finishes, the `AbortController`. It works in three steps:

```jsx title="Stopping a request with AbortController"
const controller = ~new AbortController()~; // 1. Creates the controller
fetch('/api/bio/Bob', { ~signal: controller.signal~ }); // 2. Gives fetch the controller's signal
~controller.abort();~ // 3. Stops the request
```

> [!DEFINITION]
> **What is an AbortController?** [NEW] An `AbortController` is an object the browser gives you to stop a request. MDN: "a controller object that allows you to abort one or more Web requests as and when desired."
> `controller.signal` is the part that `fetch` listens to. You hand it to `fetch` in the second argument: `{ signal: controller.signal }`.
> When your code calls `controller.abort()`, the browser stops the request, and the `fetch` promise fails.
> It fails with a `DOMException` named `AbortError`. A `DOMException` is an error object that the browser itself creates. So in `.catch`, `err.name` is `'AbortError'`.
> A signal works only once. MDN: "An `AbortSignal` can only be used once." So every request needs a new controller (Lesson 33).

### VS | `ignore = true` vs. `controller.abort()`: both keep Taylor's bio, only `abort` stops Bob's request

Here are the two cleanups side by side:

```jsx title="The cleanup with the ignore variable, and with abort on the controller"
return () => { ~ignore = true;~ }; // Bob's request runs to the end, and its answer is dropped
return () => ~controller.abort()~; // Bob's request is stopped, and no answer comes
```

After the user clicks Bob and then Taylor, both cleanups leave Taylor's bio on the page. The difference is in the network:
1. **With `ignore`,** the browser still waits for Bob's answer and reads it, and our code drops it.
2. **With `abort`,** the browser cancels Bob's request the moment the user clicks Taylor.

React's docs leave the choice open: the cleanup "should either abort the fetch or ignore its result". `abort` saves the network, and the reading of an answer nobody needs. `ignore` works for any promise, even one that cannot be stopped.

### The stop reaches .catch

A developer replaces `ignore` with a controller and keeps the `.catch` from Principle 2. In development, the page opens on the error line:

```page width=text caption="The team page when it opens in development, with abort in the cleanup and a catch that keeps every error: the error line."
line: [Alice] [Bob] [Taylor]
heading: Alice
line: Could not load the bio. | bad
console: quiet
```

**The page works, the server works, and yet the user reads that the bio could not be loaded.** Here is why:
1. React mounts `Bio` and runs the setup. It creates the first controller, sends the first request for Alice, and sets `error` to `null`.
2. Strict Mode runs the cleanup. `controller.abort()` stops the first request.
3. Strict Mode runs the setup again. It creates a second controller, sends the second request, and sets `error` to `null`.
4. The first request's promise fails with an `AbortError`. Its `.catch` runs now, after the second setup, and `setError` keeps the `AbortError`.
5. The second request brings Alice's bio, and `setBio` sets it. But the `AbortError` is still in state, and the JSX checks `error` first.

Why does step 4 come after step 3? A promise never calls its functions in the middle of other code. It waits until the code that is running now has finished. React runs the setup, the cleanup, and the second setup in one go. So the `.catch` of the first request can only run after all three.

The same thing happens in production. The user clicks Bob and then Taylor. The cleanup stops Bob's request, its `AbortError` reaches `.catch`, and the user sees the error line under Taylor's name.

An `AbortError` is not something that went wrong. It is our own cleanup doing its job. So `.catch` skips it and keeps every other error:

```jsx title="Skipping the AbortError in catch"
.catch(err => {
  if (~err.name === 'AbortError'~) return; // Our own cleanup stopped this request: nothing to show
  setError(err); // A real error: show the error line
});
```

### The final Bio

Here is the Effect of `Bio` with the controller in place of `ignore`:

```jsx title="src/components/Bio.jsx" startLine="7" good="8,11,20,23"
  useEffect(() => {
    const ~controller~ = new AbortController(); // A new controller for each run of the setup
    setBio(null);
    setError(null);
    fetch('/api/bio/' + person, { ~signal: controller.signal~ }) // fetch listens to this run's controller
      .then(response => {
        if (!response.ok) {
          throw new Error('Status ' + response.status);
        }
        return response.json();
      })
      .then(data => setBio(data.bio))
      .catch(err => {
        if (err.name === 'AbortError') return; // Skips the request our cleanup stopped
        setError(err);
      });
    return () => ~controller.abort()~; // Stops this run's request when person changes or Bio unmounts
  }, [person]);
```

The setup creates a new controller on every run, because a signal works only once. The cleanup sees the controller of its own run, so it stops only that run's request.

Now the page opens on Alice's bio, in development too. The user clicks Bob and then Taylor. The cleanup stops Bob's request, its `AbortError` is skipped, and the page ends on Taylor's bio:

```page width=text caption="The finished team page after the user clicks Bob and then Taylor: Bob's request was stopped, and the paragraph shows Taylor's bio."
line: [Alice] [Bob] [Taylor]
heading: Taylor
line: This is Taylor’s bio. | good
console: quiet
```

The cleanup also runs when `Bio` leaves the page, as Lesson 32 showed. If the user leaves the team page while a bio is still loading, the cleanup stops that request too.

## All 4 Principles Together

### The complete files

The entry file mounts `App` inside `<StrictMode>`:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  ~<StrictMode>~ {/* Setup, cleanup, setup in development: the cleanup must make it look like one setup */}
    <App />
  </StrictMode>
);
```

`App` keeps the chosen person and passes it to `Bio`:

```jsx title="src/App.jsx"
import { useState } from 'react';
import Bio from './components/Bio.jsx';

export default function App() {
  const [person, setPerson] = useState('Alice');

  return (
    <main>
      <button onClick={() => setPerson('Alice')}>Alice</button>
      <button onClick={() => setPerson('Bob')}>Bob</button>
      <button onClick={() => setPerson('Taylor')}>Taylor</button>
      <h2>{person}</h2>
      ~<Bio person={person} />~ {/* Principle 1: a new person brings a new request */}
    </main>
  );
}
```

`Bio` asks the server for the bio, shows a paragraph for each state, and stops the old request in the cleanup:

```jsx title="src/components/Bio.jsx"
import { useState, useEffect } from 'react';

export default function Bio({ person }) {
  const [bio, setBio] = useState(null);
  const [error, setError] = useState(null);

  useEffect(() => {
    const controller = new AbortController();
    setBio(null);
    setError(null);
    ~fetch~('/api/bio/' + person, { signal: controller.signal }) // Principle 1: the request goes in an Effect
      .then(response => {
        if (~!response.ok~) { // Principle 2: a server error goes to catch
          throw new Error('Status ' + response.status);
        }
        return response.json();
      })
      .then(data => setBio(data.bio))
      .catch(err => {
        if (~err.name === 'AbortError'~) return; // Principle 4: our own stop is not an error
        setError(err);
      });
    return () => ~controller.abort()~; // Principles 3 and 4: the old request never sets state
  }, ~[person]~); // Principle 1: runs again whenever person changes

  if (error) {
    return <p>Could not load the bio.</p>;
  }
  return <p>{bio ?? 'Loading...'}</p>;
}
```

The user opens the page, clicks Bob, and clicks Taylor half a second later:

```page width=text caption="The finished team page after the user clicks Bob and then Taylor: Taylor's name and Taylor's bio."
line: [Alice] [Bob] [Taylor]
heading: Taylor
line: This is Taylor’s bio. | good
console: quiet
```

### How React calls the components and runs the Effect

When the user clicks Taylor, React calls `App`, then `Bio`, and commits the new name with the old bio still in state. Then it runs the old cleanup and the new setup. The answer arrives last:

```tree dir=right caption="The order of events from the click on Taylor to Taylor's bio on the page."
From the click on Taylor to Taylor's bio
- +1. Render [`App` `Bio`] | React calls `App`, then `Bio`, with `person` set to Taylor | `Bio` **hands React the new setup**
- +2. Commit [`<h2>Taylor</h2>`] | React puts **Taylor's name** into the DOM | The paragraph still shows the old text
- +3. Cleanup [`controller.abort`] | React runs **the Bob run's cleanup** | Bob's request **stops**
- +4. Setup [`fetch`] | React runs **the Taylor run's setup** | The paragraph shows **`Loading...`**; the request goes out
- +5. Answer [`setBio`] | Taylor's bio **arrives** | React renders the paragraph with **Taylor's bio**
```

### What the Effect does, and what the user sees

| What the Effect does | What the user sees | Why |
| :--- | :--- | :--- |
| **Fetches with `[]`** | The paragraph keeps Alice's bio after a click on Bob | The Effect runs only on mount |
| **Fetches with `[person]` and no `response.ok` check** | `Loading...` forever when the server fails | `fetch` succeeds whenever the server answers, and the bio is `undefined` |
| **Checks `response.ok`, with no cleanup** | Bob's bio under Taylor's name after two quick clicks | Bob's late answer still calls `setBio` |
| **Uses the `ignore` variable** | Taylor's bio | Bob's answer arrives and is dropped |
| **Uses `controller.abort`, and `.catch` keeps every error** | The error line on a page that works | The `AbortError` of the stopped request reaches `setError` |
| **Uses `controller.abort` and skips the `AbortError`** | Taylor's bio | Bob's request is stopped, and only real errors show |

One last time, the sentence of this lesson: **The server answers later, and not always in the order you asked. So the page shows `Loading...` while it waits, an error line when the server fails, and only the answer to the last request.**

## For the Interview

> **The Interview Question:** How do you fetch data from an API in a client component, and how do you handle loading, error, and race conditions?

### How to Answer Clearly in 30 Seconds

"I call `fetch` inside `useEffect`, because the data must match the props while the component is on the screen. I list the props the request reads, such as `[person]`. The data arrives later, in `.then`, so the component has three states: loading, error, and data. Three rules keep it right:
1. **Loading**: the state starts at `null`, the JSX shows a loading line for `null`, and each new request sets it back to `null`.
2. **Errors**: `fetch` fails only when it cannot reach the server. So I check `response.ok`, throw an error when it is `false`, and keep the error in state from `.catch`.
3. **Race conditions**: answers can come back in a different order than I sent the requests. The cleanup either sets an `ignore` variable so the old answer is dropped, or calls `abort` on an `AbortController` so the old request stops. With `abort`, `.catch` skips the `AbortError`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does my page send every request twice in development?"**
   In development, Strict Mode runs the setup, the cleanup, and the setup again when the component mounts, so two requests go out. The docs: "There is nothing wrong with that." With a cleanup, the first request's answer is dropped or the request is stopped, so it does not change the state. "In production, there will only be one request."

   The fix is never to block the second run. It is a cleanup that makes the two runs look like one to the user.
2. **"What about the warning "Can't perform a React state update on an unmounted component"?"**
   React 18 removed it. The upgrade guide says React "warned about memory leaks when you call `setState` on an unmounted component". But "people primarily run into it in scenarios where setting state is fine, and workarounds make the code worse." React 19 prints nothing when a late answer sets state on a component that is gone.

   The cleanup still matters. It keeps a late answer from replacing the current data, and with `abort` it stops requests nobody needs.
3. **"Would you write fetch in an Effect in a real app?"**
   The docs call it "a very manual approach", for three reasons. Effects do not run on the server, so the first HTML shows only the loading state. A parent and a child that each fetch one after the other create "network waterfalls". And nothing is cached, so a component that mounts again fetches again.

   The docs recommend the data fetching of a framework, or a client-side cache such as TanStack Query or useSWR, which Lesson 60 compares. Without those, the fetch Effect can go into a custom Hook, such as the docs' `useData`, which Lesson 39 teaches. React 19's `use` with Suspense is Lesson 71, and Server Components are Lesson 101.

```tree dir=right caption="Interview comparison: what each part of a fetch Effect protects the user from."
What each part of a fetch Effect protects
- +The array [`[person]`] | A new prop brings **a new request** | The page never keeps **the old person's data**
- +The loading and error states [`response.ok` `.catch`] | The page always shows **one answer**: loading, error, or data | The user never waits for **a bio that will not come**
- +The cleanup [`ignore` `abort`] | Every answer except **the last one requested** is dropped or stopped | The page never shows **the wrong person's data**
```
