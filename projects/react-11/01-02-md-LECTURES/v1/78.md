## VS | A recursive walk vs. React's work loop: both render every component, only the loop can stop between two

> When the user clicks a tab, React calls your components again to build the next screen, and with 500 slow posts that takes a while. **Under the hood, React keeps one object for every component and every tag, the Fiber node, and walks these objects in a loop, one at a time.** That loop can stop between any two objects to let the browser answer a click, and a half-built screen never reaches the user.

Remember how the browser keeps a page. Every tag on the page is a JavaScript object, a DOM node. Each DOM node is linked to its neighbors: `document.body.firstChild` is the first element inside the body, and `nextSibling` is the element right after it. The browser walks the whole page through these links.

React does the same thing for your components. A component is a function, and a function forgets everything when it returns. So React keeps one object for each component and each tag, in its own memory, and links these objects into a tree, like the DOM. That object is the **Fiber node**. Your state lives in it.

Then React renders by walking through these objects with a plain `while` loop, one Fiber node per turn. Between two turns, the loop can stop and give the browser a moment to handle a click. And the loop writes the next screen into a second tree of Fiber nodes. The user sees the new screen only when every object in that tree is finished.

**Why:** This decides whether the page answers the user while React renders something slow:
1. **One long run of nested function calls freezes the page.** The browser cannot run a click handler or paint anything until the last component returns. MDN puts it plainly: "long-running JavaScript functions can block the thread, leading to an unresponsive page and a bad user experience."
2. **A loop over Fiber nodes and a second tree keep the page answering.** The browser handles a click in the middle of a slow render, and the user never sees half of a list.

### The Four Pieces of Fiber

React's docs say that rendering is recursive: React calls a component, then the components it returns, then the components those return, and so on (Lesson 13). A **recursive** walk is a function that calls itself, once for each child.

A recursive walk and React's loop visit the same components in the same order: the parent before its children, and the children in the order of the JSX. The one difference is where the walk keeps its place:
- **A recursive walk** keeps its place on the call stack. Nothing can stop it until the last call returns.
- **React's loop** keeps its place in one variable that points to the next Fiber node. After any Fiber node, the loop can stop, and React picks up from that variable later.

So React renders with four pieces, and the whole lesson is about them:
1. **One object for each component and each tag.** React keeps a Fiber node for every component, such as `ProfileTabs`, and for every tag, such as a `<button>`. The object lasts from one render to the next, and it holds the state.
2. **Three links on each object.** Each Fiber node points to its first child, to its next sibling, and to its parent. There is no array of children.
3. **A loop that visits one Fiber node per turn.** The place in the walk is one variable, so React can stop after any Fiber node and give the main thread back to the browser.
4. **A second tree beside the one on the screen.** React builds the new Fiber nodes in a second tree and switches to it only when it is finished. A half-built tree is thrown away, and the screen never sees it.

```tree dir=right caption="The four pieces of Fiber that let React stop in the middle of a render and never show half of it."
How React renders a page
- +1. One Fiber node per component and per tag [`ProfileTabs` `PostsTab` `SlowPost`] | An object that **lasts across renders** | It **holds the state**
- +2. Three links on each Fiber node [`child` `sibling` `return`] | First child, next sibling, and parent | **No array of children**
- +3. One loop, one Fiber node per turn [`workInProgress`] | The place in the walk is **one variable** | React can **stop after any Fiber node**
- +4. A second tree beside the screen's tree [`current` `workInProgress`] | React switches trees **only when the new one is finished** | A half-built tree **never reaches the screen**
```

**Why is it called Fiber?** In computer science, a thread is a line of work that the computer runs, such as the browser's main thread (Lesson 66). A fiber is a thinner, lighter piece of work that stops and continues only at points it chooses itself. React's Fiber takes its name from that idea: React stops only where it chooses, between two Fiber nodes.

> [!DEFINITION]
> **React element.** [REVIEW] A React element is the plain object that a JSX tag such as `<ProfileTabs />` becomes, with a `type`, `props`, and a `key`; a component returns brand-new elements every time it renders, and React freezes them in development, so nothing can change them (Lesson 76).

> [!DEFINITION]
> **Urgent update and Transition.** [REVIEW] A setter called normally is an urgent update, and React renders it at once without stopping; a setter called inside `startTransition` is a Transition, and React renders it in a concurrent render that it may pause, so the page keeps answering while the slow part renders (Lesson 66).

> [!DEFINITION]
> **Call stack.** [NEW] The call stack is the list where JavaScript remembers which function called which: when `a` calls `b`, JavaScript writes down where it was in `a`, runs `b`, and comes back to that place when `b` returns; MDN says it lets the interpreter "keep track of its place in a script that calls multiple functions", and a running function on it cannot be stopped from outside (Lesson 78).

> [!DEFINITION]
> **Fiber node.** [NEW] A Fiber node is the plain JavaScript object React keeps for each component and each tag on the page; it holds the type, the key, the props, the state of the Hooks, and for a tag the real DOM node, it lasts from one render to the next, and it links to its first child, its next sibling, and its parent (Lesson 78).

### Where Readers Usually Go Wrong

Readers usually go wrong in four places:
1. **They think the element is the Fiber node.** The element is a description, made new on every render and frozen. The Fiber node is the object React keeps across renders, and it holds the state.
2. **They think React creates all its inner objects again on every render.** React keeps two trees, and it fills the new one by reusing the objects of the old one.
3. **They think a paused render always continues where it stopped.** When React stops only to give the browser time, it continues from the same Fiber node. When a more urgent update arrives, React's docs say React "will restart the rendering work".
4. **They think a Fiber node is something they write or touch in their code.** It is React's own inner object. React's docs say React uses "sophisticated techniques in its internal implementation", and that "you won't see those concepts anywhere in our public APIs."

### The Rule of Thumb: React stops only between two Fiber nodes, and shows only a finished tree

**React can stop between two components, never inside one. And React may throw away a render the user never sees.** So spread slow work over many small components. And keep work that must happen once per screen out of the component body, in an Effect.

```jsx title="src/components/ProfileTabs.jsx"
import { startTransition, useState } from 'react';
import PostsTab from './PostsTab.jsx';

export default function ProfileTabs() {
  const [selected, setSelected] = ~useState('about')~; // The tab the user clicked last
  const [tab, setTab] = ~useState('about')~; // The tab the panel shows

  function selectTab(nextTab) {
    ~setSelected(nextTab)~; // Urgent: the clicked tab turns bold at once
    startTransition(() => {
      ~setTab(nextTab)~; // Transition: the panel follows when it is ready
    });
  }

  return (
    <section>
      {selected === 'about' ? <b>About</b> : <button onClick={() => selectTab('about')}>About</button>}
      {selected === 'posts' ? <b>Posts</b> : <button onClick={() => selectTab('posts')}>Posts</button>}
      {selected === 'contact' ? <b>Contact</b> : <button onClick={() => selectTab('contact')}>Contact</button>}
      <hr />
      {tab === 'about' && <p>Welcome to my profile!</p>}
      {tab === 'posts' && <PostsTab />}
      {tab === 'contact' && <p>Contact me at admin@mysite.com</p>}
    </section>
  );
}
```

Lesson 66 showed that this works. This lesson shows how. When the user clicked Contact, React was in the middle of 500 posts. So we have three questions:
1. Where does React keep the half-built list while it waits?
2. How does React stop in the middle of a render?
3. Why does the half-built list never reach the screen?

**PRINCIPLES:** Under every render, React keeps one object for each component and each tag, links these objects into a tree, walks them one at a time in a loop, and builds the next tree beside the one on the screen. Four principles follow:
1. **Principle 1: The Fiber Node Holds the State.** After the click on Contact, `useState('about')` hands back `'contact'`, because React reads it from the Fiber node of `ProfileTabs`.
2. **Principle 2: Three Links Connect Every Fiber Node.** The `<section>` holds no list of its tabs. It points to the About tab, and each tab points to the next one.
3. **Principle 3: The Work Loop Can Stop After Any Fiber Node.** React stops between two posts, and the browser runs the Contact click.
4. **Principle 4: The Second Tree Hides Unfinished Work.** The half-built Posts tree is thrown away, and the About line stays on the screen until the Contact line replaces it.

## PRINCIPLE | The Fiber node: React keeps one object per component, and the state lives in it

> [!PRINCIPLE]
> **Principle 1: Fiber Node: The Fiber Node Holds the State of `ProfileTabs`**
>
> *For each component and each tag on the page, React keeps one Fiber node across renders; it holds the type, the key, the props, the state, and for a tag the DOM node.*
>
> A component function runs again from its first line on every render, and the elements it returns are new each time. So neither the function nor its elements can remember anything. The Fiber node does: React keeps it at the component's position in the tree, stores the state of its Hooks in it, and updates it from each new element. That is why `useState('about')` hands back `'contact'` after the click.
>
> **DO THIS:**
> ```jsx
> function ProfileTabs() {
>   const [tab, setTab] = ~useState('about')~; // React stores tab in the Fiber node of ProfileTabs, so it survives every render
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ProfileTabs() {
>   ~let tab = 'about'~; // **WRONG:** a plain variable starts again at 'about' each time React calls ProfileTabs
> }
> ```

Here is the smallest code of this principle. `App` writes one tag, and `ProfileTabs` asks for one piece of state:

```jsx title="One tag and one piece of state"
<ProfileTabs /> {/* Written in App */}

const [tab, setTab] = useState('about'); // Written in ProfileTabs
```

Ask yourself a simple question. `ProfileTabs` is a function. Every time React calls it, every line runs again, including `useState('about')`. So after the click on Contact, where does `'contact'` come from? It cannot come from the function, which forgets everything when it returns. It comes from an object React keeps for `ProfileTabs`, outside the function: its Fiber node.

### VS | The element vs. the Fiber node: a description made new on every render, and the object React keeps

The tag `<ProfileTabs />` becomes an element: a plain object with a `type`, `props`, and a `key` (Lesson 76). React also keeps a second object for `ProfileTabs`, its Fiber node. Here are the two, simplified:

```js title="The element of <ProfileTabs />, simplified"
{ ~type: ProfileTabs~, key: null, props: {} } // A description: made new each time App renders, frozen, no state
```

```js title="The Fiber node of ProfileTabs, simplified"
{
  ~type: ProfileTabs~, // The same type as the element
  key: null,
  memoizedProps: {}, // The props of the last render
  ~memoizedState~: { memoizedState: 'about', next: { memoizedState: 'about', next: null } }, // The state of both Hooks, selected and tab, one after the other
  stateNode: null, // No DOM node: ProfileTabs is a component, not a tag
}
```

The field names are React's own. "Memoized" is a programming word for a value that is saved so it can be used again:
- **`memoizedProps`** holds the props of the last render.
- **`memoizedState`** holds the state. The two Hooks of `ProfileTabs` sit in a small chain. The first Hook holds `selected`, and its `next` link leads to the Hook that holds `tab`.
- **`stateNode`** holds the real DOM node for a tag such as `<button>`. For a component, it is `null`.

Both objects carry the type `ProfileTabs` and the key `null`. It may look the same, but it is NOT the same thing!
- **The element** is a description. React's docs call it "a lightweight description of a piece of the user interface". A component returns new elements every time it renders, and React freezes them in development.
- **The Fiber node** is the object React keeps. React creates it the first time `ProfileTabs` appears at its position, and keeps it as long as `ProfileTabs` stays there (Lesson 25). On each render, React reads the new element and updates the Fiber node from it.

```tree caption="The element of ProfileTabs and the Fiber node of ProfileTabs carry the same type, but only the Fiber node lasts and holds the state."
Two objects for one `ProfileTabs`
- !The element [`type: ProfileTabs` `props`] | A **description**, made new on every render | **Frozen**, and holds **no state**
- +The Fiber node [`type: ProfileTabs` `memoizedState`] | The object React **keeps across renders** | Holds the **state**, and for a tag the **DOM node**
```

### Where `'contact'` comes from after the click

**After the user clicks Contact, `tab` holds `'contact'`, even though the code still says `useState('about')`.** React reads the value from the Fiber node, not from the code and not from the elements. Here is what happens, in order:
1. The user clicks Contact. The two setters ask React to change the state that React holds for `ProfileTabs` (Lesson 25).
2. React calls `ProfileTabs` again. The function runs from its first line, and `useState('about')` runs again with `'about'` in it.
3. React ignores that `'about'`. It finds the Fiber node of `ProfileTabs`, reads the state stored in it, and hands `'contact'` back from `useState`.
4. `ProfileTabs` returns brand-new elements: a new `<section>`, new tabs, and a new `<p>` for the Contact line. The elements of the previous render are gone.
5. React updates the Fiber nodes under `ProfileTabs` from these new elements.

React's docs say that the state "is actually held inside React", and that React ties each piece of state to where its component "sits in the render tree". The Fiber node is that place. It is the object that sits at the position of `ProfileTabs` in the tree.

You can see the state in it without reading any code. Open React Developer Tools, go to the Components panel, and select `ProfileTabs` (Lesson 64). Under Hooks, the panel shows the two pieces of state. Both show `"about"` when the page opens. After the click on Contact, both show `"contact"`.

### How many Fiber nodes the profile page has

React keeps a Fiber node for every component and every tag on the page, not only for `ProfileTabs`. While the Posts tab shows, the page has one Fiber node for each of these:
1. `App`, `ProfileTabs`, the `<section>`, each of the three tabs, and the `<hr>`.
2. `PostsTab` and its `<ul>`.
3. Each of the 500 `SlowPost` components, and each of their 500 `<li>` tags.
4. Pieces of text, such as the text inside each `<li>`.

That is well over a thousand Fiber nodes for one small page. A post on the V8 blog about React's own `FiberNode` class says: "Many real-world React apps don't just have two, but rather tens of thousands of these `FiberNode`s."

Remember: the function forgets, the element is thrown away, and the Fiber node remembers.

## PRINCIPLE | `child`, `sibling`, and `return`: three links connect every Fiber node, with no array of children

> [!PRINCIPLE]
> **Principle 2: Linked Tree: `child`, `sibling`, and `return` Connect the Three Tabs**
>
> *Each Fiber node points to its first child with `child`, to its next sibling with `sibling`, and to its parent with `return`; the children of a Fiber node form a chain, not an array.*
>
> The DOM links its nodes the same way, with `firstChild`, `nextSibling`, and `parentNode`. With these three links, React can go from any Fiber node to any other one: down to the first child, across to the next sibling, and back up to the parent. That is all React needs to walk the whole tree with one loop, as Principle 3 shows. These links belong to React. Our code reaches the tree only through props, state, and refs.
>
> **DO THIS:**
> ```jsx
> <button onClick={() => ~selectTab('contact')~}>Contact</button> {/* Our code talks to React through state; React keeps the links */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const key = Object.keys(button).find((name) => name.startsWith('__reactFiber$'));
> const section = ~button[key].return~; // **WRONG:** an internal link that can change in any React version
> ```

Here is the smallest code of this principle: the three tabs inside the `<section>` of `ProfileTabs`, as they look when the page opens:

```jsx title="The three tabs inside the section"
<section>
  <b>About</b>
  <button>Posts</button>
  <button>Contact</button>
</section>
```

### VS | The DOM's links vs. the Fiber node's links: the same shape, shorter names

You already know this shape from plain JavaScript (Lesson 01). Every DOM node has three properties, and MDN describes them:
- **`firstChild`** "returns the node's first child in the tree, or `null` if the node has no children."
- **`nextSibling`** returns the node right after it under the same parent, or `null` for the last one.
- **`parentNode`** "returns the parent of the specified node in the DOM tree."

A Fiber node has the same three links, under shorter names:
- **`child`** points to the first child only.
- **`sibling`** points to the next Fiber node under the same parent, and it is `null` for the last one.
- **`return`** points to the parent.

Here is the same link written both ways, for the About tab. `aboutNode` stands for its DOM node, and `aboutFiber` for its Fiber node:

```js title="The DOM's links and the Fiber node's links for the About tab"
aboutNode.~nextSibling~; // The DOM: the Posts button
aboutFiber.~sibling~; // Fiber: the Fiber node of the Posts button
```

Yes, it is the exact same shape! Both trees link each node to its first child, its next sibling, and its parent. Only the names differ. One more difference: the Fiber tree also holds Fiber nodes for components such as `ProfileTabs` and `PostsTab`, which have no DOM node at all.

### The links of the profile page

**The Fiber node of the `<section>` does not hold a list of its tabs. It points only to the About tab.** To reach the Contact tab, React goes from About by `sibling` to Posts, and from Posts by `sibling` again. Here are all the links of the page when it opens:
1. The `child` of `ProfileTabs` is the `<section>`.
2. The `child` of the `<section>` is the About tab.
3. The `sibling` of the About tab is the Posts tab, and the `sibling` of the Posts tab is the Contact tab.
4. The Contact tab's `sibling` is the `<hr>`. The `<hr>`'s `sibling` is the paragraph of the About line.
5. The `sibling` of that paragraph is `null`, because it is the last child.
6. The `return` of each tab, of the `<hr>`, and of the paragraph is the `<section>`.

When the page opens, the conditions for the Posts panel and the Contact panel are false. A false value puts nothing on the page, so React creates no Fiber node for it.

A chain like these siblings is called a **linked list**: a list where each object holds a link to the next one, and no array holds them all. To reach the fifth object, you follow the links through the first four. The 500 posts under the `<ul>` form one chain of 500 `sibling` links.

When the panel shows the Posts tab, `PostsTab` takes the place of the `<p>`, and the tree grows by more than a thousand Fiber nodes:

## PRINCIPLE | The work loop: React visits one Fiber node per turn, so it can stop between any two

> [!PRINCIPLE]
> **Principle 3: Work Loop: The Loop Can Stop After Any `SlowPost`**
>
> *React walks the Fiber nodes in a loop, one per turn: it begins work on the way down and completes it on the way up; in a concurrent render it can stop between two Fiber nodes and continue later, or restart when a more urgent update arrives.*
>
> A recursive walk keeps its place on the call stack and cannot stop until the last call returns. React keeps its place in one variable, `workInProgress`. So after any Fiber node, React can give the main thread back to the browser, let it run a click handler or paint, and pick up again. React cannot stop inside one component, so slow work stays interruptible only when it is spread over many components.
>
> **DO THIS:**
> ```jsx
> for (let i = 0; i < 500; i++) {
>   items.push(~<SlowPost key={i} index={i} />~); // 500 short Fiber nodes: React can stop between any two
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function PostsTab() {
>   let startTime = performance.now();
>   ~while (performance.now() - startTime < 500) {}~ // **WRONG:** one Fiber node that runs half a second; React cannot stop inside it
> }
> ```

### VS | A function that calls itself vs. a `while` loop: the same order, only the loop can stop

Here are two ways to visit every node of the same tree. Both are sketches: the names `visit`, `work`, `timeToStop`, and `doOneFiber` are ours, not React's. First, the recursive walk:

```js title="A sketch of a recursive walk"
function visit(node) {
  work(node); // Calls the component of this node
  for (const child of node.children) {
    ~visit(child)~; // Waits here until the whole subtree of child is done
  }
}
```

Now the loop. It keeps its place in one variable, `next`:

```js title="A sketch of React's loop"
let next = rootFiber; // The place in the walk: one variable
while (next !== null && ~!timeToStop()~) { // Can stop between any two Fiber nodes
  next = doOneFiber(next); // Visits one Fiber node and returns the next one
}
```

Both visit `ProfileTabs`, the `<section>`, the three tabs, `PostsTab`, the `<ul>`, and the 500 posts, in the same order. It may look the same, but it is NOT the same thing! The difference sits in one line of each:
- **In the recursive walk**, the line `visit(child)` waits on the call stack until the whole subtree is done. A running function in JavaScript cannot be stopped from outside. MDN says it "cannot be preempted and will run entirely before any other code runs". So the walk ends only when the last call returns.
- **In the `while` loop**, each turn visits one Fiber node and returns. When it is time to stop, the loop ends, and `next` still points to the next Fiber node. Later, React starts the loop again from `next`.

```tree caption="A recursive walk and React's loop visit the same components in the same order; only the loop can stop in the middle."
Two ways to walk the same tree
- !A recursive walk [`visit` calls `visit`] | Keeps its place **on the call stack** | Cannot stop until **the last call returns**
- +React's loop [`while` over `child` `sibling` `return`] | Keeps its place **in one variable** | Can stop **after any Fiber node** and continue later
```

### One turn of the loop: down, across, and back up

The three links of Principle 2 decide which Fiber node comes next. React does its work at each Fiber node in two steps, which its source code names `beginWork` and `completeWork`:
- **`beginWork`** happens on the way down. React calls the component, then compares the elements it returns with the old child Fiber nodes, with the type and key checks of Lesson 77.
- **`completeWork`** happens on the way up, when a Fiber node and everything under it are finished. For a tag, this is where React prepares its DOM node.

```js title="A sketch of one turn of the loop: which Fiber node comes next"
function doOneFiber(fiber) {
  beginWork(fiber); // On the way down: call the component, compare with the old Fiber nodes
  if (fiber.child !== null) {
    return ~fiber.child~; // Go down to the first child
  }
  let done = fiber;
  while (done !== null) {
    completeWork(done); // On the way up: this Fiber node and everything under it are finished
    if (done.sibling !== null) {
      return ~done.sibling~; // Go across to the next sibling
    }
    done = ~done.return~; // Go back up to the parent
  }
  return null; // Back above the root: the walk is finished
}
```

Now the name `return` makes sense. It points to where the walk returns when a Fiber node and all its children are complete. A function's return does the same job on the call stack.

The real names in React's source are these:
- **`workInProgress`** is the variable we called `next`.
- **`performUnitOfWork`** is one turn of the loop, our `doOneFiber`.
- **`workLoopConcurrentByScheduler`** is the loop of a concurrent render in React 19.

These are the names interviewers mean when they say "the workLoop". You never write them in an app.

Here is the order in which the loop visits the profile page while it renders the Posts tab:

```tree dir=right caption="The order in which React's loop visits the Fiber nodes of the profile page while it renders the Posts tab."
The walk of the Posts render
- +1. `ProfileTabs` | **Begin**: React calls `ProfileTabs` | Go down by `child` to the section
- +2. The section | **Begin** it | Go down by `child` to the About tab
- +3. The three tabs and the `<hr>` | **Begin** and **complete** each one | Go across by `sibling`
- +4. `PostsTab` | **Begin**: React calls `PostsTab`, which prints its log line | Go down to the `<ul>`, then to `SlowPost` 1
- +5. `SlowPost` 1 to 500 | **Begin** each one, which waits 1 millisecond, and **complete** its `<li>` | Go across by `sibling`: React **can stop between any two**
- +6. Back up by `return` | **Complete** the `<ul>`, `PostsTab`, the section, `ProfileTabs` | The tree is **finished**
```

### What the loop does when the user clicks Contact

Here is `PostsTab`, unchanged from Lesson 66. Each `SlowPost` waits 1 millisecond while it renders, to stand for slow code:

```jsx title="src/components/PostsTab.jsx"
export default function PostsTab() {
  console.log('[ARTIFICIALLY SLOW] Rendering 500 <SlowPost />');

  let items = [];
  for (let i = 0; i < 500; i++) {
    items.push(<SlowPost ~key={i}~ index={i} />); // 500 sibling Fiber nodes under the ul
  }
  return <ul className="items">{items}</ul>;
}

function SlowPost({ index }) {
  let startTime = performance.now();
  while (performance.now() - startTime < 1) {} // Waits 1 millisecond to stand for slow code

  return <li className="item">Post #{index + 1}</li>;
}
```

**The loop stops between two posts, the browser runs the Contact click, and React starts the render again with the new state.** Here is what happens, in order:
1. The user clicks Posts. `setTab('posts')` runs inside `startTransition`, so its render is a concurrent render (Lesson 66).
2. React begins work at `ProfileTabs`, which returns the three tabs and `<PostsTab />`.
3. React walks down to `PostsTab`. The Console prints the log line, and `PostsTab` returns 500 `<SlowPost />` elements.
4. When React begins the `<ul>`, it creates all 500 `SlowPost` Fiber nodes at once, linked by `sibling`, but calls none of them yet.
5. React visits `SlowPost` 1 and its `<li>`, goes by `sibling` to `SlowPost` 2, and so on. Each `SlowPost` takes 1 millisecond.
6. After some posts, React stops between two Fiber nodes and gives the main thread back to the browser. The variable `workInProgress` still points to the next `SlowPost`.
7. The user clicks Contact. The main thread is free, so the browser runs the click handler at once.
8. `setSelected('contact')` is an urgent update, so React does not continue at the saved `SlowPost`. It handles the urgent update first.
9. Then React renders the Transition again from the top, with `tab` as `'contact'`.

React's docs call step 6 yielding: "React yields to the browser during concurrent rendering". For step 9, they describe the same case with a chart: "React will restart the rendering work on the chart component after handling the input state update."

Without the click on Contact, React would come back after yielding and continue at the saved `SlowPost` until all 500 are done. React's docs say that React "may start rendering an update, pause in the middle, then continue later."

React alone decides where it stops and how often. React's docs say only that React "can let the browser do some work between component calls so that re-rendering a large component tree doesn't block the main thread."

You can see this in the browser's Performance panel, in development and profiling builds (Lesson 64):
- **In the main flame chart**, the render shows up as many short blocks of work. Inside them you find names such as `workLoopConcurrentByScheduler`, `performUnitOfWork`, and `beginWork`.
- **On the Components track** of React's Performance tracks, React's docs say the label "Blocked" appears "when rendering is blocked due to yielding to work outside React".

### React cannot stop inside one component

The loop can stop only between two Fiber nodes. It cannot stop inside a component, because a running JavaScript function runs to its end. Each `SlowPost` takes only 1 millisecond, so React gets 500 chances to stop. If all the slow work sat inside one component, React would get none:

```jsx title="One component that does all the slow work in one call"
function PostsTab() {
  let startTime = performance.now();
  ~while (performance.now() - startTime < 500) {}~ // Half a second inside one Fiber node: the loop cannot stop here
  return <ul className="items">...</ul>;
}
```

`startTransition` does not help this component. After a click on Posts, the page freezes for at least half a second, because the loop gets its turn back only when `PostsTab` returns. The loop helps only when the slow work is spread over many Fiber nodes.

The same fact explains why a debounce does not fix a slow list. A debounce waits until the user stops typing, and only then updates the list (Lesson 66). React's docs say a debounce can only "merely postpone the moment when rendering blocks the keystroke". Once a normal render starts, it runs to its end. A render that can stop between Fiber nodes does not block the keystroke (Lesson 68).

Remember: React stops between two Fiber nodes, never inside one.

## PRINCIPLE | `current` and `workInProgress`: React builds the next screen in a second tree, so a half-built tree never shows

> [!PRINCIPLE]
> **Principle 4: Double Buffering: The Half-Built Posts Tree Is Thrown Away While About Stays on the Screen**
>
> *React keeps two trees of Fiber nodes, the current tree that matches the screen and the work-in-progress tree that the loop builds; at the commit it changes the DOM and makes the finished tree the current one.*
>
> The loop writes only into the work-in-progress tree, so stopping in the middle never leaves the screen half old and half new. When a more urgent update arrives, React throws the unfinished tree away, and the screen goes straight from the old view to the new one. Each Fiber node links to its pair in the other tree with `alternate`, so React reuses the objects instead of creating them again on every render.
>
> **DO THIS:**
> ```jsx
> function PostsTab() {
>   ~useEffect~(() => { sendLog('posts opened'); }, []); // Runs only after a commit, so only when the posts reach the screen
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function PostsTab() {
>   ~sendLog('posts opened')~; // **WRONG:** also runs for a Posts tree that React throws away before the user sees it
> }
> ```

Look at the screen during the Posts render. The Posts tab is bold, the panel still shows `Welcome to my profile!`, and React is already working on the posts:

```page width=text caption="During the Posts render: the Posts tab is bold, and the panel still shows the About line while React builds the posts."
line: [About] Posts [Contact]
line: Welcome to my profile!
log: [ARTIFICIALLY SLOW] Rendering 500 <SlowPost /> | PostsTab.jsx:2
log: [ARTIFICIALLY SLOW] Rendering 500 <SlowPost /> | PostsTab.jsx:2
```

At this moment, React holds two trees of Fiber nodes. Here they are, just before the user clicks Contact:
1. **The tree that matches the screen**: `ProfileTabs` with `tab` as `'about'`, the section, the three tabs, and the `<p>` of the About line.
2. **The tree the loop is building**: `ProfileTabs` with `tab` as `'posts'`, the section, the three tabs, `PostsTab`, the `<ul>`, and a Fiber node for each of the 500 posts. React has called only the first posts, so this tree is unfinished.

### VS | One tree that changes as React walks vs. a second tree: only the second tree survives a stop

React could have kept one tree and changed it as the loop walks. When nothing interrupts the render, both ways end with the same finished tree. But they are NOT the same thing!
- **With one tree**, a stop in the middle leaves the only tree React has half old and half new. When the user clicks Contact, React must commit the urgent update at once. The only tree it could commit holds half of the posts, and no whole tree matches the About screen anymore.
- **With a second tree**, the loop writes only into the new tree. The tree that matches the screen stays whole until the new tree is finished.

React's names for the two trees are these:
- **The current tree** holds the Fiber nodes that match what is on the screen.
- **The work-in-progress tree** holds the Fiber nodes the loop is building for the next screen. The variable `workInProgress` of Principle 3 always points to a Fiber node of this tree.

> [!DEFINITION]
> **Double buffering.** [NEW] Double buffering is a name from computer graphics: a video game draws the next frame on a hidden canvas while the player looks at the current one, then shows the finished frame in one step, so the player never sees half a frame; React's work-in-progress tree is that hidden canvas, and React's docs use a wider word, saying React uses "multiple buffering" inside (Lesson 78).

```tree caption="React keeps two trees of Fiber nodes: the current tree matches the screen, and the work-in-progress tree is the one the loop builds."
Two trees of Fiber nodes [`current` `workInProgress`]
- +The current tree [`tab: 'about'`] | Matches **what is on the screen** | Does **not change** during the render
- +The work-in-progress tree [`tab: 'posts'`] | The loop **writes only here** | Becomes the current tree **only when it is finished**
```

### What happens to the half-built Posts tree

**React throws the Posts tree away half-built, and the user goes straight from the About line to the Contact line.** Here is what happens, in order:
1. The user clicks Posts. React renders and commits the urgent update first, and the Posts tab turns bold.
2. React starts the Transition render. It builds a work-in-progress tree, starting from the Fiber nodes of the current tree.
3. The loop adds `PostsTab`, the `<ul>`, and the 500 post Fiber nodes to the work-in-progress tree only, and calls the first posts.
4. The screen still shows `Welcome to my profile!`, because the current tree and the DOM have not changed.
5. The user clicks Contact. The urgent update arrives, and React throws the unfinished Posts tree away.
6. React renders the urgent update and commits it. The Contact tab turns bold, and the About line still shows.
7. React renders the Transition again with `tab` as `'contact'`, finishes the tree, and commits it.
8. The user sees `Contact me at admin@mysite.com`, and never a single post.

For step 5, React's docs say React "will throw out the stale rendering work that wasn't finished".

React changes the DOM only in the commits. During the whole Posts render, the Elements panel never holds a `<ul>` or an `<li>`:

```dom caption="The Elements panel during the Posts render: the About paragraph stays, and no ul is ever added."
<section>
  <button>About</button>
  <b>Posts</b>
  <button>Contact</button>
  <hr>
  + <p>Welcome to my profile!</p> | note: The current tree still has the About line
</section>
```

React's docs give the rule: "React guarantees that the UI will appear consistent even if a render is interrupted. To do this, it waits to perform DOM mutations until the end, once the entire tree has been evaluated." The second tree is how React keeps that promise.

### The switch at the commit, and the `alternate` link

At the commit, React changes the DOM, and then it makes the finished tree the current one. The root of the page has a link named `current`, and React moves that link to the finished tree. The tree that was current becomes the one React fills on the next render.

So the "one Fiber node per component" of Principle 1 is really a pair, one in each tree. Each Fiber node links to the Fiber node at the same position in the other tree with a field named `alternate`. In the Console of Principle 2, the `alternate` of the Contact button was still `null`, because the page had rendered only once. After the first click, it points to the Contact button's pair in the other tree.

On each render, React starts each work-in-progress Fiber node from its `alternate`, when the type and the key still match (Lesson 77). Here is what that means on the Posts click:
- **The `<section>`, the `<hr>`, and the Contact button** keep their types. React does not create new objects for them. It reuses the objects it already has and updates them.
- **The About and Posts tabs** get new Fiber nodes, because each one changes from `<b>` to `<button>` or back.

```tree dir=right caption="How the two trees of Fiber nodes trade places at each commit."
Two trees that trade places
- +1. Render starts | React builds the work-in-progress tree **from the `alternate` of each current Fiber node**
- +2. The loop walks | React writes **only into the work-in-progress tree** | The screen **stays as it was**
- +3. Commit | React **changes the DOM** and moves the root's **`current` link** to the finished tree
- +4. Next render | The old current tree becomes **the one React fills next** | Objects are **reused**, not created again
```

### The real mistake: work in the component body for a tree the user never sees

React may throw a work-in-progress tree away. So it may call a component for a screen the user never sees. On our page, React called `PostsTab` for the Posts tree, and then threw that tree away. Here is how that turns into a wrong number on a server:
1. A developer wants to count how often users open the Posts tab. In the body of `PostsTab`, the developer calls `sendLog('posts opened')`, a function of our own code that sends one line to the server.
2. The user clicks Posts and then Contact, as above.
3. React calls `PostsTab`, so the log goes to the server. In development it goes twice, because of Strict Mode.
4. React throws the Posts tree away, and the user never sees a single post. The server still counts the Posts tab as opened.

React's docs say that "rendering logic can be run multiple times", and that is why components must stay pure (Lesson 14). The fix is to move the log into an Effect. React runs Effects only after a commit, so a tree React throws away never runs them.

Remember: the loop writes into the second tree, and only a finished tree reaches the screen.

### What developers believe, and what React does

| Aspect | The Common Belief | The React Rule |
| :--- | :--- | :--- |
| **Where state lives** | The element of `<ProfileTabs />` is what React keeps for the component | Elements are new and frozen on every render; the Fiber node lasts and holds the state |
| **How the tree is linked** | A parent holds an array of its children | Each Fiber node links to its first `child`, its next `sibling`, and its parent with `return` |
| **How React walks it** | Rendering is one run of nested calls that cannot stop | One loop visits one Fiber node per turn and can stop between any two in a concurrent render |
| **What the screen shows** | React changes the tree on the screen as it walks | React builds a work-in-progress tree beside the current one and switches them at the commit |

Remember the one sentence of this lesson. **React keeps one Fiber node for every component and every tag, walks them in a loop one at a time, and builds the next screen in a second tree, so it can stop between any two and never shows half a screen.**

## For the Interview

> **The Interview Question:** What is a Fiber node, and how does the dual-buffering workLoop manage rendering?

### How to Answer Clearly in 30 Seconds

"A Fiber node is the object React keeps for each component and each tag, across renders. It holds the type, the key, the props, the state of the Hooks, and for a tag the DOM node. Elements are only descriptions, made new on every render, and React updates the Fiber nodes from them. The Fiber nodes form a linked tree, and React renders it in three parts:
1. **The links**: `child` points to the first child, `sibling` to the next sibling, and `return` to the parent.
2. **The work loop** visits one Fiber node per turn. It begins work on the way down, calling the component and comparing its elements with the old Fiber nodes, and completes work on the way up. Its place is one variable, `workInProgress`. So in a concurrent render, React can stop between two Fiber nodes, yield to the browser, and continue later.
3. **Double buffering**: the loop builds a work-in-progress tree beside the current tree, which matches the screen. At the commit, React changes the DOM and makes the finished tree current. If a more urgent update arrives, React throws the unfinished tree away, so the user never sees half a screen."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does Fiber protect React from a call stack overflow on a deep tree?"**
   **Only during the render.** A recursive walk adds one entry to the call stack for each level of the tree. MDN warns that when the stack takes more space than it was given, "a 'stack overflow' error is thrown". Chrome shows it as `RangeError: Maximum call stack size exceeded`. React's render loop adds no entry per level. It moves one variable along `child`, `sibling`, and `return`, so a deeper tree does not grow the stack while React calls the components. The commit is different. React 19 walks the finished tree there with nested calls, one level deeper for each level of the tree. So a tree of components nested several thousand levels deep still throws that `RangeError` during the commit. React's docs give a different reason for the loop: React "can let the browser do some work between component calls so that re-rendering a large component tree doesn't block the main thread."
2. **"Can a Transition make one very slow component interruptible?"**
   **No.** React can stop only between two Fiber nodes. A component that runs for half a second runs to its end, because nothing can stop a running JavaScript function from outside. The loop helps when the slow work is spread over many small components, such as 500 posts that take 1 millisecond each.
3. **"Does React create new Fiber nodes on every render?"**
   **No.** Each Fiber node links to its pair in the other tree with `alternate`. When a render starts, React builds each work-in-progress Fiber node from that `alternate`, as long as the type and the key still match (Lesson 77). The two trees trade places at each commit. React may still throw a work-in-progress tree away and render again. So components must stay pure, and work that must happen once per screen belongs in an Effect.

```tree caption="Interview summary: what a Fiber node is, how the work loop walks it, and why there are two trees."
Fiber in three parts
- +The Fiber node [`type` `key` `memoizedState` `stateNode`] | One per component and per tag | **Lasts across renders** and holds the state
- +The work loop [`child` `sibling` `return` `workInProgress`] | One Fiber node per turn | Can **stop between two** and continue or restart
- +Double buffering [`current` `alternate`] | The loop builds a **work-in-progress tree** | It becomes current **at the commit**; thrown-away work **never shows**
```
