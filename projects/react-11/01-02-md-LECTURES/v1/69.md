# Lecture 69: How a Suspense Boundary Lets the Rest of the Page Paint First

*(How do the fast parts of a page appear at once while one slow part is still loading?)*

> INTERVIEW QUESTION | ❱❱ MORE | How does Suspense display fallbacks, and where should boundaries sit?

---

## VS | A Loading Text Inside the Component vs. a `<Suspense>` Fallback Above It: the component handles its own wait, or the parent decides which parts wait

> A home page often has one slow part, such as a weather line whose server needs 3 seconds, next to a title and headlines that are ready at once. **Wrap only the slow part in `<Suspense>`, and give it a `fallback`, such as `Loading weather...`, that React shows until that part is ready.** Everything outside the `<Suspense>` appears at once, so one slow part never hides the whole page.

You already know one way to show a loading text, from Lesson 33. The component fetches in an Effect, keeps the result in state, and writes its own loading text while that state is still empty:

```jsx title="A loading text inside the component"
function EffectWeather({ city }) {
  const [weather, setWeather] = useState(null);
  useEffect(() => {
    fetchData('/weather/' + city).then(result => setWeather(result));
  }, [city]);
  return <p>{~weather ?? 'Loading...'~}</p>; // The component writes its own loading text
}
```

Every component that loads something must do this by itself. Each one handles only its own wait.

With `<Suspense>`, the component only reads its data. It never writes a loading text. The loading text moves up, into the parent:

```jsx title="A fallback in the parent, above the component"
function Weather({ city }) {
  const weather = use(fetchData('/weather/' + city));
  return <p>{~weather~}</p>; // Only the weather: no loading text here
}

<Suspense ~fallback={<p>Loading weather...</p>}~> {/* The parent decides what stands in for Weather */}
  <Weather city="London" />
</Suspense>
```

Two names here are new. `use` is a function from React that reads the value of a promise, and Lesson 71 covers it in full. `fetchData` is our fake weather server, and you will see its file in the example page below.

Both versions show a loading text until the weather arrives. It may look the same, but it is NOT the same thing! The loading text now lives above the components. So one `<Suspense>` can stand in for several components at once. And when you move the `<Suspense>` to another place, you change which parts of the page wait, without touching a single component.

### The Idea Behind It: `try...catch`

Remember `try...catch` from plain JavaScript? When a function throws an error, the error does not stay where it happened. It travels up, out of every function, until it reaches the closest `catch`. That `catch` decides what happens next:

```js title="Plain JavaScript: the closest catch handles the error"
try {
  ~showWeather()~; // Throws deep inside
} catch (error) {
  showMessage('Could not load weather'); // The closest catch above decides what the user sees
}
```

`<Suspense>` works the same way, but for a component that is not ready. When `Weather` reads a promise that has no answer yet, React puts `Weather` on hold. Then React walks up the tree to the closest `<Suspense>` above it, and that one shows its fallback:

```jsx title="React: the closest Suspense handles the wait"
<Suspense ~fallback={<p>Loading weather...</p>}~> {/* The closest Suspense above decides what the user sees */}
  <Weather city="London" />
</Suspense>
```

Keep one sentence in mind for the whole lesson. **A component that is not ready suspends, and the closest `<Suspense>` above it shows its fallback. Everything inside that `<Suspense>` waits together. Everything outside it appears at once.**

### The Words This Lesson Stands On

> [!DEFINITION]
> **A loading state in an Effect.** [REVIEW] The component starts with empty state, such as `useState(null)`, and renders at once. After the commit, its Effect starts the fetch. When the data arrives, the set function makes React render the component again, now with the data. Until then, the component itself must write a loading text, such as `weather ?? 'Loading...'` (Lesson 33).

> [!DEFINITION]
> **A promise: pending and resolved.** [NEW] A promise is a JavaScript object that stands for a value that will arrive later, such as the answer of a server. While the server has not answered yet, the promise is pending. Once the answer has arrived, the promise is resolved, and it holds that answer (Lesson 69).

### What Is at Stake

React's documentation puts the key idea in one sentence: "`<Suspense>` lets you display a fallback until its children have finished loading."

What is at stake is that one slow part must not hide the whole page. Wrap the whole page in one `<Suspense>` with the fallback `Loading page...`, and the user stares at `Loading page...` for 3 seconds, although the title and the headlines were ready from the start. Wrap only the weather, and the user reads the headlines at once.

Developers usually go wrong in one of three ways:
1. **One `<Suspense>` at the top of the app.** The slowest part holds back the whole page.
2. **A `<Suspense>` around every component.** The page jumps in many small pieces. React's documentation says: "Don't put a Suspense boundary around every component."
3. **A fetch in an Effect, wrapped in `<Suspense>`.** They expect the fallback, and it never shows. React's documentation says: "Suspense does not detect when data is fetched inside an Effect or event handler."

### The Rule of Thumb: which parts may wait together?

**Ask one question about every slow part of the page: which other parts may wait for it? Put a `<Suspense>` around exactly those parts, and leave everything that is ready outside of it.**

### Three Ways to Show a Loading State

At work, developers pick one of three ways:
1. **A loading text inside each component**, with an Effect and `useState`, as seen in Lesson 33. It fits when your data does not come from a source that works with Suspense.
2. **A `<Suspense>` with a data source that works with Suspense.** This is the way of this lesson. It fits when the data comes from `use` with a cached promise, from `lazy`, as seen in Lesson 70, or from a framework such as Next.js. React's documentation calls such a framework a **Suspense-enabled framework**, and adds: "The exact way you load your data depends on your framework".
3. **Keep the old content on the screen** with a Transition or a deferred value, as seen in Lessons 66 to 68. It fits when the content is already on the screen and an update loads new data. Principle 5 shows it.

### `data.js`: one promise per address

The file `data.js` plays the slow server. Lesson 71 explains it line by line. Here, two facts matter:
1. `fetchData` returns a promise. That promise is resolved, and holds the weather, after 3 seconds.
2. For the same address, `fetchData` always returns the very same promise. It keeps one promise per address in a `Map`, and hands that one back every time.

```js title="src/data.js"
const ~cache~ = new Map(); // One promise per address. Normally, a framework does this for you

export function fetchData(url) {
  if (!cache.has(url)) {
    cache.set(url, getData(url));
  }
  return ~cache.get(url)~; // The same address always gets the same promise
}

const answers = {
  '/weather/London': ['London: 18 degrees, sunny', 3000],
};

async function getData(url) {
  const [value, delay] = answers[url];
  await new Promise(resolve => setTimeout(resolve, delay));
  return value;
}
```

Why does the second fact matter? React will call `Weather` more than once. If every call got a new promise, every call would start a new wait of 3 seconds, and the weather would never appear. React's own examples use the same helper, with the same note: "Normally, the caching logic would be inside a framework."

### The three components

`Weather` reads the weather in its very first line:

```jsx title="src/components/Weather.jsx"
import { use } from 'react';
import { fetchData } from '../data.js';

export default function Weather({ city }) {
  const weather = ~use(fetchData('/weather/' + city))~; // Weather suspends here while the promise is pending
  return <p>{weather}</p>;
}
```

`Headlines` reads a plain array, so it is ready at once:

```jsx title="src/components/Headlines.jsx"
const ~headlines~ = ['Main Street park opens today', 'Bus fares drop on Monday', 'Library stays open late']; // A plain array: ready at once

export default function Headlines() {
  return (
    <ul>
      {headlines.map(title => (
        <li key={title}>{title}</li>
      ))}
    </ul>
  );
}
```

`HomePage` puts only the weather inside the `<Suspense>`:

```jsx title="src/components/HomePage.jsx"
import { Suspense } from 'react';
import Headlines from './Headlines.jsx';
import Weather from './Weather.jsx';

export default function HomePage() {
  return (
    <main>
      <h1>City News</h1>
      <Headlines />
      <Suspense ~fallback={<p>Loading weather...</p>}~> {/* Stands in for Weather for 3 seconds */}
        <Weather city="London" />
      </Suspense>
    </main>
  );
}
```

These three files give exactly the two screens above. Now each principle moves the `<Suspense>`, or changes how the weather loads, and shows what the user sees.

**PRINCIPLES:** A component that is not ready suspends, and the closest `<Suspense>` above it shows its fallback. Everything inside that `<Suspense>` waits together. Five principles follow:
1. **Principle 1: The Closest `<Suspense>` Above Shows Its Fallback.** When `Weather` reads a pending promise, it suspends. The closest `<Suspense>` above it shows `Loading weather...`, and React shows `Weather` once the promise is resolved. A `<Suspense>` inside `Weather` itself never catches `Weather`.
2. **Principle 2: A Fetch in an Effect Never Suspends.** The component renders at once with empty state. Nothing suspends, so the fallback never shows, and the user sees an empty weather line.
3. **Principle 3: One `<Suspense>` Is One Unit.** Everything inside one `<Suspense>` waits for its slowest part. Around the whole page, the slow weather hides the headlines that were ready.
4. **Principle 4: Nested `<Suspense>` Gives a Loading Sequence.** A `<Suspense>` inside another one makes the page appear in stages. Use no more of them than the stages the user should see.
5. **Principle 5: `startTransition` Keeps the Old Content on the Screen.** A click that makes `Weather` suspend again brings the fallback back. Inside `startTransition`, React keeps London's weather until Paris is ready.

## PRINCIPLE | `<Suspense fallback>`: the closest boundary above a suspended component shows its fallback

> [!PRINCIPLE]
> **Principle 1: Suspense: The Closest Boundary Above Shows Its Fallback**
>
> *When a component suspends while it renders, the closest `<Suspense>` above it shows its `fallback`; when the data is ready, React shows the `children` with the data.*
>
> A component suspends when it reads data that is not ready yet, such as a pending promise read with `use`. React shows nothing from that component. The closest `<Suspense>` above it shows its `fallback` instead, and the rest of the page goes on. The component itself never writes a loading text, so the `<Suspense>` must sit in the parent, above the line that reads the data.
>
> **DO THIS:**
> ```jsx
> <Suspense fallback={<p>Loading weather...</p>}>
>   ~<Weather city="London" />~ {/* Weather suspends, and this Suspense shows Loading weather... */}
> </Suspense>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Weather({ city }) {
>   const weather = ~use(fetchData('/weather/' + city))~; // **WRONG:** suspends before the Suspense below is ever returned
>   return <Suspense fallback={<p>Loading weather...</p>}><p>{weather}</p></Suspense>;
> }
> ```

### `fallback` and `children`: two props, one on the screen at a time

```jsx title="One Suspense with its two props"
import { Suspense } from 'react';

<Suspense ~fallback={<p>Loading weather...</p>}~> {/* fallback: what the user sees while the weather is not ready */}
  ~<Weather city="London" />~ {/* children: what the user should see once the weather is ready */}
</Suspense>
```

`<Suspense>` is a component from React, so you import it from `'react'`. It takes two props:
- **`fallback`** is written on the opening tag. It is a prop, just like `city` (Lesson 08), and it holds JSX.
- **`children`** is everything between the opening and the closing tag (Lesson 09).

There is no special syntax here. What is new is what React does with the two props: it shows only one of them at a time. `children` while everything inside is ready, `fallback` while something inside is not.

> [!DEFINITION]
> **A Suspense boundary.** [NEW] React's documentation calls a `<Suspense>` placed in your page a Suspense boundary, or a boundary for short. It marks off one part of the page: everything between its tags. While any component inside that part is not ready, the boundary shows its `fallback` in place of the whole part (Lesson 69).

> [!DEFINITION]
> **To suspend.** [NEW] In everyday English, to suspend something is to put it on hold. A component suspends when it reads data that is not ready yet while it renders, such as a pending promise read with `use`. React puts the component on hold, shows nothing from it, and lets the closest boundary above it show its fallback. When the data is ready, React renders the component again (Lesson 69).

Look again at `Weather`. It never writes a loading text. It only reads the weather. The boundary above it decides what stands in while the weather is not ready.

### What happens when the user opens the page

**The boundary shows the fallback while the promise is pending, and shows `Weather` once the promise is resolved.** Step by step:
1. React renders `HomePage`: the title, the headlines, and the boundary.
2. React renders `Weather`. `fetchData('/weather/London')` returns a promise that is still pending.
3. `use` finds the promise pending, so `Weather` suspends. React shows nothing from `Weather`.
4. The closest boundary above `Weather` is the one in `HomePage`. It shows its `fallback`.
5. React commits: the title, the three headlines, and `Loading weather...` appear together on the page.
6. After 3 seconds, the promise resolves. React renders `Weather` again. `fetchData` returns the same promise, now resolved, so `use` returns `'London: 18 degrees, sunny'`.
7. React replaces the fallback with `Weather`: the line reads `London: 18 degrees, sunny`.

```tree dir=right caption="How one boundary shows its fallback while Weather suspends, and then shows Weather with its data."
What the weather line shows after the user opens the page
- +1. `Weather` suspends [`use`] | The promise for London is **still pending** | React shows **nothing from `Weather`**
- +2. The boundary shows its fallback [`fallback`] | The closest boundary above is **in `HomePage`** | The line reads **`Loading weather...`**
- +3. The promise resolves after 3 seconds | React **renders `Weather` again** | The line reads **`London: 18 degrees, sunny`**
```

Three things in this path are not written anywhere in our code:
1. **The value of `weather`.** No set function sets it. `use` returns the resolved value of the promise that `fetchData` gave it.
2. **The text `Loading weather...` on the page.** No line of `Weather` writes it. React takes it from the `fallback` prop of the boundary above.
3. **The second render of `Weather`.** No set function starts it. React tries to render the suspended part again when the promise resolves. React's documentation says it retries "from scratch".

### A `<Suspense>` inside the component never catches that component

A common first attempt puts the `<Suspense>` inside `Weather` itself, around the returned paragraph:

**DO NOT DO THIS:**
```jsx title="src/components/Weather.jsx" bad="2"
export default function Weather({ city }) {
  const weather = ~use(fetchData('/weather/' + city))~; // **WRONG:** Weather suspends here, before the Suspense below is ever returned
  return (
    <Suspense fallback={<p>Loading weather...</p>}>
      <p>{weather}</p>
    </Suspense>
  );
}
```

That `<Suspense>` never shows its fallback for the weather. Why? `use` runs on the first line of `Weather`, so `Weather` suspends right there, before it returns any JSX. The `<Suspense>` in the `return` never reaches the page. It is not above `Weather`, so React never gets to it.

Think of `try...catch` again. A `try` block that starts after the line that throws cannot catch that line. The same goes here: the boundary must already exist above the component when the component suspends.

So React keeps looking further up the page, for the **closest parent Suspense boundary**: the nearest `<Suspense>` above the component that suspends. If that boundary wraps more of the page, a bigger part of the page waits for the weather.

The fix: put the boundary in the parent, above the component that reads the data.

**DO THIS:**
```jsx title="src/components/HomePage.jsx" good="1"
<Suspense ~fallback={<p>Loading weather...</p>}~> {/* In the parent, above the component that reads the data */}
  <Weather city="London" />
</Suspense>
```

Remember: the component reads, the boundary above it waits.

## PRINCIPLE | A fetch in `useEffect`: the component never suspends, so the fallback never shows

> [!PRINCIPLE]
> **Principle 2: Effect Fetch: Only a Component That Suspends Activates the Boundary**
>
> *`<Suspense>` shows its fallback only when a child suspends while it renders; data fetched in an Effect or an event handler does not make the component suspend.*
>
> An Effect runs after the commit, when the component has already rendered with its empty state. The boundary has nothing to wait for, so it shows the component at once, and the user sees an empty line until the set function runs. To use a fallback, read the data during render with a source that works with Suspense, such as `use` with a cached promise or a Suspense-enabled framework.
>
> **DO THIS:**
> ```jsx
> function Weather({ city }) {
>   const weather = ~use(fetchData('/weather/' + city))~; // Suspends during render, so the fallback shows
>   return <p>{weather}</p>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function EffectWeather({ city }) {
>   const [weather, setWeather] = useState(null);
>   ~useEffect~(() => { fetchData('/weather/' + city).then(setWeather); }, [city]); // **WRONG:** Suspense cannot see this fetch, so the line stays empty
>   return <p>{weather}</p>;
> }
> ```

### The same boundary around an Effect fetch

Now put the Lesson 33 way of loading inside the same boundary. `EffectWeather` fetches the same weather in an Effect. This time it has no loading text of its own, because the developer expects the boundary to show one:

```jsx title="An Effect fetch inside the same boundary"
<Suspense fallback={<p>Loading weather...</p>}>
  ~<EffectWeather city="London" />~ {/* Fetches in an Effect: the fallback never shows */}
</Suspense>
```

```jsx title="src/components/EffectWeather.jsx"
import { useState, useEffect } from 'react';
import { fetchData } from '../data.js';

export default function EffectWeather({ city }) {
  const [weather, setWeather] = useState(~null~); // The first render has no weather
  useEffect(() => {
    let ignore = false;
    fetchData('/weather/' + city).then(result => {
      if (!ignore) {
        setWeather(result);
      }
    });
    return () => {
      ignore = true;
    };
  }, [city]);
  return <p>{weather}</p>;
}
```

It may look the same in the code, but it is NOT the same thing! Both components read the same weather, and both sit in the same boundary. After 3 seconds, both show `London: 18 degrees, sunny`. But during those 3 seconds, only `Weather` lets the boundary show `Loading weather...`. The user of the Effect version sees an empty line and no sign that anything is loading.

React's documentation states the rule plainly: "Suspense does not detect when data is fetched inside an Effect or event handler." Why? A boundary reacts only to a component that suspends while it renders. An Effect runs after the commit (Lesson 32). By then, the component has already rendered, and it did not suspend.

### What happens with the Effect fetch

**The boundary never shows its fallback, because nothing suspends.** Step by step:
1. React renders `EffectWeather` with `weather` set to `null`. It returns an empty paragraph.
2. `EffectWeather` did not suspend, so the boundary shows its `children`: the empty paragraph.
3. React commits. The weather line is empty, and `Loading weather...` never appears.
4. The Effect runs after the commit and starts `fetchData`.
5. After 3 seconds, `.then` calls `setWeather` with `'London: 18 degrees, sunny'`, and React renders `EffectWeather` again.
6. The line reads `London: 18 degrees, sunny`.

The empty line comes from `useState(null)`: a paragraph that holds `null` shows nothing (Lesson 10). React's documentation describes the same case with its own album list: "Suspense can't see this fetch, so its fallback never shows. The list stays empty until the data arrives."

```tree caption="Which way of loading the weather lets the boundary show its fallback."
What the boundary sees while the weather loads
- +Reading with `use` during render [`use`] | The component **suspends** while the promise is pending | The boundary shows **`Loading weather...`**
- !Fetching in an Effect [`useEffect`] | The component **renders at once** with `null` and **never suspends** | The boundary has nothing to wait for, so the line stays **empty for 3 seconds**
```

### The developer who removes the loading text

This happens in real teams:
1. A developer has a weather component from Lesson 33, with a fetch in an Effect.
2. The developer reads that `<Suspense>` shows a loading text, and wraps the component in it.
3. The developer removes the component's own loading text, `weather ?? 'Loading...'`.
4. Now the page opens with an empty weather line for 3 seconds.
5. The fallback never shows, and the developer thinks Suspense is broken.

Suspense is not broken. It needs a data source that makes the component suspend: `use` with a cached promise, `lazy`, or a Suspense-enabled framework. Next.js, for example, "integrates data fetching with Suspense". With such a framework, you write the `<Suspense>`, and the framework makes the components suspend.

React's rule also names event handlers. An event handler may still start a request. What makes a component suspend is the reading: the component must read that promise with `use` while it renders. Lesson 71 shows how.

For the rest of the lesson, `HomePage` goes back to `Weather`, which reads with `use`. Remember: no suspend, no fallback.

## PRINCIPLE | One `<Suspense>` around the whole page: every part inside waits for the slowest one

> [!PRINCIPLE]
> **Principle 3: One Unit: Everything Inside One Boundary Appears Together**
>
> *Everything inside one boundary waits for its slowest child and appears together; place the boundary around the slow part only, so the parts that are ready appear first.*
>
> When any child inside a boundary suspends, the whole boundary shows its fallback, even the parts that were ready. A boundary around the whole page lets one slow weather line hide the title and every headline. A boundary around the weather only leaves the title and the headlines outside, so React shows them at once.
>
> **DO THIS:**
> ```jsx
> <Headlines />
> <Suspense fallback={<p>Loading weather...</p>}>
>   ~<Weather city="London" />~ {/* Only the weather line waits */}
> </Suspense>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Suspense fallback={<p>Loading page...</p>}>
>   ~<Headlines />~ {/* **WRONG:** ready headlines wait 3 seconds for the weather */}
>   <Weather city="London" />
> </Suspense>
> ```

### Everything inside one boundary is one unit

React's documentation gives the rule: "By default, the whole tree inside Suspense is treated as a single unit." In plain words, a boundary never shows some of its children and hides the others. When any child inside it suspends, the whole boundary shows its fallback. When every child is ready, they all appear at the same moment. React's documentation says these components "pop in" together.

**With the boundary around the whole page, the ready title and headlines wait for the slow weather.** Step by step:
1. The user opens the page, and the boundary wraps all three parts.
2. React renders the title and `Headlines`. Both are ready.
3. React renders `Weather`, and it suspends.
4. The closest boundary above `Weather` is the one around the whole page. So that whole boundary shows `Loading page...`, and the title and the headlines that were ready do not appear.
5. After 3 seconds, the weather is ready. The title, the headlines, and the weather "pop in" together.

`Headlines` did not suspend, and no line of it writes `Loading page...`. Still, the fallback stands in for it. The `fallback` of a boundary replaces all of its `children`, including the parts that were ready.

A child does not have to sit directly between the boundary's tags. React's documentation says: "Components that load data don't have to be direct children of the Suspense boundary." A `Weather` placed two components deeper still makes the same whole boundary show its fallback. Just like an error thrown three functions deep still reaches the `catch` above.

```tree caption="With one boundary around the whole page, the parts that are ready wait for the slowest part inside the same boundary."
Which parts wait when `Weather` suspends
- !Boundary around the whole page [`Loading page...`] | The title, the headlines, and the weather are **one unit** | The user sees **only `Loading page...`** for 3 seconds
- +Boundary around the weather only [`Loading weather...`] | The title and the headlines sit **outside the boundary** | React shows them **at once**; **only the weather line waits**
```

### The developer who wraps the whole app

This is common in real projects:
1. A developer wraps the whole app in one `<Suspense>`, inside `App.jsx`, so that every loading case is covered. `HomePage` has no boundary of its own.
2. The page has one slow part, the weather.
3. The closest boundary above `Weather` is now the one in `App.jsx`. So every visit shows `Loading page...` for 3 seconds, although the headlines need no wait.
4. The developer blames the weather server.

**DO NOT DO THIS:**
```jsx title="src/App.jsx"
export default function App() {
  return (
    <Suspense ~fallback={<p>Loading page...</p>}~> {/* **WRONG:** the whole home page waits 3 seconds for the weather */}
      <HomePage />
    </Suspense>
  );
}
```

The fix is to move the boundary down, around the weather only. Our `HomePage` already does that, so no file changes in this step. Moving a boundary changes only which parts wait. React's documentation says: "You can add, move, or delete Suspense boundaries in any place in the tree without affecting the rest of your app's behavior."

Remember: everything inside one boundary waits together. Wrap only the slow part.

## PRINCIPLE | Nested `<Suspense>`: the page appears in stages, one boundary at a time

> [!PRINCIPLE]
> **Principle 4: Nested Boundaries: Boundaries Follow the Loading Sequence**
>
> *When a component suspends, the closest boundary above it shows its fallback; an outer boundary with an inner boundary gives a loading sequence, one level at a time.*
>
> Each component listens only to its closest boundary. The outer boundary stands in for everything inside it until its own children are ready, then the inner boundary takes over for the slower part. Boundaries do not make data arrive sooner. They decide which parts appear together, so use no more of them than the loading stages the user should see.
>
> **DO THIS:**
> ```jsx
> <Suspense fallback={<p>Loading news...</p>}>
>   <Headlines />
>   ~<Suspense fallback={<p>Loading weather...</p>}>~ {/* Two stages: the news, then the weather */}
>     <Weather city="London" />
>   </Suspense>
> </Suspense>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~<Suspense fallback={<p>Loading...</p>}>~<h1>City News</h1></Suspense> {/* **WRONG:** one boundary per component, even around the title that never waits */}
> <Suspense fallback={<p>Loading...</p>}><Headlines /></Suspense>
> <Suspense fallback={<p>Loading...</p>}><Weather city="London" /></Suspense>
> ```

### A boundary inside another boundary

Now the headlines come from the server too, and they take 1 second. The weather still takes 3 seconds. Here is a boundary for the news, with a boundary for the weather inside it:

```jsx title="A boundary for the news with a boundary for the weather inside it"
<h1>City News</h1>
<Suspense ~fallback={<p>Loading news...</p>}~> {/* Outer: stands in for the headlines and the weather */}
  <Headlines />
  <Suspense ~fallback={<p>Loading weather...</p>}~> {/* Inner: stands in for the weather only */}
    <Weather city="London" />
  </Suspense>
</Suspense>
```

A `<Suspense>` inside the `children` of another `<Suspense>` gives **nested boundaries**. Each component listens only to its closest boundary:
- **`Headlines`** is closest to the outer one.
- **`Weather`** is closest to the inner one.

It is the same as two nested `try...catch` blocks: each error goes to the `catch` closest to it.

React's documentation: "This lets you nest multiple Suspense components to create a loading sequence." A **loading sequence** is the order in which the parts of the page appear. React's word for the moment a boundary replaces its fallback with its content is **reveal**.

### The page in three stages

**First the title, then the headlines, then the weather.**

```page caption="Stage 1, right after the user opens the page: the title, and the news still loading."
heading: City News
line: Loading news...
```

```page caption="Stage 2, after 1 second: the headlines are there, and the weather is still loading."
heading: City News
line: Main Street park opens today
line: Bus fares drop on Monday
line: Library stays open late
line: Loading weather...
```

```page caption="Stage 3, after 3 seconds: the headlines and the weather are both there."
heading: City News
line: Main Street park opens today
line: Bus fares drop on Monday
line: Library stays open late
line: London: 18 degrees, sunny | good
```

How React gets from one stage to the next:
1. The user opens the page. `<h1>City News</h1>` sits outside every boundary, so it is ready.
2. `Headlines` suspends. Its closest boundary is the outer one. That boundary shows `Loading news...` in place of everything inside it: the headlines and the weather together.
3. React commits: `City News` and `Loading news...`.
4. After 1 second, the headlines are ready. React renders the outer boundary's `children` again. `Weather` suspends, and its closest boundary is the inner one.
5. React reveals the outer content: the headlines appear, and the weather line reads `Loading weather...`.
6. After 3 seconds, the weather is ready, and the inner boundary reveals it.

Notice stage 1: `Loading news...` also stands in for the weather. The inner boundary sits inside the outer boundary's `children`, so the outer fallback covers it too, until React reveals the outer content.

```tree dir=right caption="The loading sequence of the home page with a boundary for the news and a boundary for the weather inside it."
How the home page appears, one level at a time
- +Stage 1: at once | `City News` and **`Loading news...`** | The outer boundary stands in for the headlines **and** the weather
- +Stage 2: after 1 second | The **headlines** and **`Loading weather...`** | The outer boundary reveals its content; the inner boundary stands in for the weather
- +Stage 3: after 3 seconds | The headlines and **`London: 18 degrees, sunny`** | The inner boundary reveals the weather
```

One detail about timing. React's documentation says: "React reveals suspended content at most once every 300ms, measured from the last reveal. Boundaries that become ready within that window are revealed together rather than one at a time." On our page, the gap between 1 second and 3 seconds is much longer than 300 milliseconds, so the two stages appear one after the other.

### How many boundaries is the right number

This is the second half of the interview question: how granular should boundaries be? In plain words, how many boundaries should a page have, and how small a part should each one wrap?

React's documentation answers it directly: "Don't put a Suspense boundary around every component. Suspense boundaries should not be more granular than the loading sequence that you want the user to experience."

More boundaries do not make the data arrive sooner. A boundary only decides which parts appear together. So the number of boundaries is a design choice about what the user sees.

This happens in real teams:
1. A developer learns that a boundary lets the parts that are ready appear first.
2. The developer wraps every component on the page in its own `<Suspense>`, each with its own `Loading...` line.
3. On our home page, the user now sees two identical `Loading...` lines at once, and cannot tell which part is loading. On a bigger page, where each part loads on its own, the page jumps each time one part appears.
4. The design the team agreed on had only two loading stages: the news, then the weather.

React's documentation gives the practical advice: ask the designer where the loading states should go, because the designer has most likely drawn them in the design wireframes already.

A fallback itself should be light. React's documentation says: "in practice, a fallback is a lightweight placeholder view, such as a loading spinner or skeleton." On our page, one line of text is enough.

Remember: one boundary for each stage the user should see, and no more.

## PRINCIPLE | `startTransition`: the weather already on the screen stays while the next city loads

> [!PRINCIPLE]
> **Principle 5: Transition: A Transition Avoids an Unwanted Fallback**
>
> *When content is already on the screen and an update makes it suspend again, the boundary shows its fallback again; inside `startTransition`, React keeps the content on the screen until the new data is ready.*
>
> A boundary shows its fallback every time a child suspends, not only on the first visit. An urgent update, such as a plain set function in a click handler, lets the fallback replace the content the user was reading. A non-urgent update inside `startTransition` keeps that content, and `isPending` from `useTransition` lets you show that new data is on its way.
>
> **DO THIS:**
> ```jsx
> <button onClick={() => ~startTransition(() => setCity('Paris'))~}>Paris</button> {/* London stays until Paris is ready */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button onClick={() => ~setCity('Paris')~}>Paris</button> {/* **WRONG:** London disappears behind Loading weather... for 3 seconds */}
> ```

> [!DEFINITION]
> **A Transition.** [REVIEW] A set function called inside `startTransition`, which you import from `'react'`, makes a non-urgent update. A plain set function in a click handler is an urgent update. React renders a Transition in the background, and nothing of it reaches the screen before its commit. `useTransition` gives the same `startTransition`, plus `isPending`, which is `true` while that background work is not finished (Lessons 66 and 67).

### The same click with and without `startTransition`

Now the weather gets two buttons above it, `London` and `Paris`. `HomePage` keeps the chosen city in a state variable, `city`, and passes it to `Weather` as a prop. The line shows London's weather, and the user clicks `Paris`. Paris's weather also takes 3 seconds.

The same click, written two ways:

```jsx title="The same click on Paris, with setCity and with startTransition"
<button onClick={() => ~setCity('Paris')~}>Paris</button> {/* Urgent: London's weather disappears behind the fallback */}
<button onClick={() => ~startTransition(() => setCity('Paris'))~}>Paris</button> {/* Non-urgent: London's weather stays until Paris is ready */}
```

What the user sees during the 3 seconds after the click:

```page size=mini

line: Library stays open late
line: [London] [Paris]
line: Loading weather... | bad
```
The weather the user was reading is gone. The line reads `Loading weather...` for 3 seconds.
:::
::: col title="setCity inside startTransition" tag="London stays" tone=good
```page size=mini

line: Main Street park opens today
line: Bus fares drop on Monday

```
London's weather stays on the screen until Paris is ready.

After 3 seconds, both lines show `Paris: 21 degrees, cloudy`. During those 3 seconds, `setCity` alone hides London's weather behind the fallback, and `setCity` inside `startTransition` keeps it on the screen.

### Why the fallback comes back after the click

A boundary shows its fallback every time a child suspends, not only when the page first opens. React's documentation says: "If Suspense was displaying content for the tree, but then it suspended again, the `fallback` will be shown again unless the update causing it was caused by `startTransition` or `useDeferredValue`."

**With `setCity` alone, the click is urgent, so the fallback replaces London. Inside `startTransition`, the click is non-urgent, so React keeps London.** Step by step:
1. The line shows `London: 18 degrees, sunny`. The user clicks `Paris`, and the handler calls `setCity('Paris')`.
2. React renders `Weather` with `city` set to `'Paris'`. `fetchData('/weather/Paris')` returns a new promise that is still pending, so `Weather` suspends.
3. The click is an urgent update. React's documentation says React "will not delay a render if it's the result of an urgent update". So the boundary shows its fallback again: London's weather disappears, and the line reads `Loading weather...` for 3 seconds.
4. Inside `startTransition`, the same click is a non-urgent update. `Weather` suspends in the same way, but React keeps London's weather on the screen.
5. After 3 seconds, the line reads `Paris: 21 degrees, cloudy`.

No new code asks for the second fallback in step 3. It comes from the same boundary as in Principle 1, which shows its fallback whenever a child suspends.

React's documentation names the problem in plain words: "Replacing visible UI with a fallback creates a jarring user experience." It calls the content a boundary has already shown **already revealed content**, and a fallback that replaces it an **unwanted fallback**. It also says: "During a Transition, React will wait until enough data has loaded to prevent an unwanted fallback from appearing".

```tree caption="The same click on Paris as an urgent update and as a non-urgent update inside startTransition."
What the weather line shows while Paris loads
- !Urgent update [`setCity`] | `Weather` suspends, and the boundary **shows its fallback again** | London's weather **disappears** behind `Loading weather...`
- +Non-urgent update [`startTransition`] | `Weather` suspends, and React **keeps the already revealed content** | London's weather **stays on the screen** until Paris is ready
```

### `isPending`: show that Paris is on its way

With `startTransition` alone, the user clicks `Paris` and sees nothing change for 3 seconds. React's documentation warns about this: "there is no visual indication that a navigation is in progress."

The fix is `useTransition`. `HomePage` now calls `useTransition`. Its `isPending` fades London's weather while React waits for Paris:

```jsx title="src/components/HomePage.jsx" startLine="5"
export default function HomePage() {
  const [city, setCity] = useState('London');
  const [~isPending~, startTransition] = useTransition(); // true while React waits for the new weather

  return (
    <main>
      <h1>City News</h1>
      <Suspense fallback={<p>Loading news...</p>}>
        <Headlines />
        <button onClick={() => startTransition(() => setCity('London'))}>London</button>
        <button onClick={() => ~startTransition(() => setCity('Paris'))~}>Paris</button> {/* London stays on screen while Paris loads */}
        <div style={{ ~opacity: isPending ? 0.7 : 1~ }}> {/* London fades while Paris loads */}
          <Suspense fallback={<p>Loading weather...</p>}>
            <Weather city={city} />
          </Suspense>
        </div>
      </Suspense>
    </main>
  );
}
```

`data.js` gets Paris, with the same 3 second delay. `Weather.jsx` does not change:

```js title="src/data.js" startLine="10"
const answers = {
  '/headlines': [['Main Street park opens today', 'Bus fares drop on Monday', 'Library stays open late'], 1000],
  '/weather/London': ['London: 18 degrees, sunny', 3000],
  ~'/weather/Paris'~: ['Paris: 21 degrees, cloudy', 3000], // Ready 3 seconds after the first click on Paris
};
```

### Back to London: no wait at all

Now the user clicks `London` again. London's weather appears at once, with no fallback and no fade. Why? `fetchData('/weather/London')` returns the same promise as before, and that promise is already resolved. React's documentation says: "When `use` receives the same Promise on a re-render, it reads the already-resolved value synchronously without suspending." Nothing suspends, so `isPending` is `true` for only a few milliseconds.

A Transition does not wait for everything. React's documentation says: "A Transition doesn't wait for *all* content to load. It only waits long enough to avoid hiding already revealed content." A boundary that appears on the page for the first time still shows its fallback at once.

### The developer who removes the weather boundary

This happens in real teams:
1. A developer adds the city buttons, with `setCity` alone.
2. On every click, the weather the user was reading disappears, and `Loading weather...` blinks in its place for 3 seconds.
3. To hide the blink, the developer removes the weather boundary. Now the news boundary is the closest one above `Weather`, so the whole news area, with the headlines and the buttons, flashes `Loading news...` on each click.
4. The fix is to keep the weather boundary where it was, and wrap the update in `startTransition`, with `isPending` to show that Paris is on its way.

Remember: the boundary decides what waits on the first visit. `startTransition` keeps what the user is already reading.

### The order in which React calls the components

When the user opens the page, React calls the components from the top down. Each component that suspends hands its part of the page to its closest boundary until its data is ready:

```tree caption="The order in which React calls the components of the home page, and which boundary stands in for each one."
`App` [1. Called first] | Renders `<HomePage />`
- +`HomePage` [2. Called second] | Renders the title, the outer boundary, the buttons, and the inner boundary | `City News` appears **at once**
  - +`Headlines` [3. Suspends for 1 second] | Closest boundary: the **outer** one | The page shows **`Loading news...`** until the headlines are ready
  - +`Weather` [4. Suspends for 3 seconds] | Closest boundary: the **inner** one | Once the headlines appear, the line shows **`Loading weather...`** until the weather is ready
```

### The habit that breaks the page, and the rule

| Aspect | The Habit That Breaks the Page | The React Rule |
| :--- | :--- | :--- |
| **Where the fallback lives** | `<Suspense>` inside the component that reads the data | `<Suspense>` in the parent, above the component that suspends |
| **What activates it** | A fetch in an Effect, with the fallback expected | Reading during render with `use` and a cached promise, `lazy`, or a Suspense-enabled framework |
| **How much one boundary covers** | One boundary around the whole page | One boundary is one unit, so wrap only the slow part |
| **How many boundaries** | A boundary around every component | Nested boundaries that match the loading stages the user should see |
| **After the content is shown** | A plain set function that brings the fallback back | `startTransition` keeps the content, and `isPending` shows that new data is coming |

Remember the one sentence of this lesson. **A component that is not ready suspends, and the closest `<Suspense>` above it shows its fallback. Everything inside that `<Suspense>` waits together. Everything outside it appears at once.**

## For the Interview

> **The Interview Question:** How does Suspense display fallbacks, and where should boundaries sit?

### How to Answer Clearly in 30 Seconds

"`<Suspense>` shows its `fallback` while any component inside it suspends, and shows its `children` once the data is ready. A component suspends when it reads data that is not ready during render, for example with `use` and a cached promise, with `lazy`, or through a Suspense-enabled framework. A fetch inside an Effect does not suspend, so it never shows the fallback. When a component suspends, the closest boundary above it shows its fallback, much like a thrown error reaches the closest `catch`. Everything inside that boundary appears together, as one unit. So boundaries should sit around the slow parts, and the parts that are ready paint first. Nest them to match the loading sequence the user should see, and never put one around every component. Once content is on the screen, an update inside `startTransition` keeps it there instead of bringing the fallback back."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"I wrapped my component in `<Suspense>`, but the fallback never shows. Why?"**
   Most likely, the component fetches its data in an Effect. React's documentation says: "Suspense does not detect when data is fetched inside an Effect or event handler." The Effect runs after the commit, so the component has already rendered with its empty state, and nothing suspended. The boundary needs a data source that suspends during render: `use` with a cached promise, `lazy`, or a Suspense-enabled framework such as Next.js. The promise must be cached. A promise created during render is new on every render, which "causes React to show the Suspense fallback repeatedly and prevents content from appearing."
2. **"How granular should Suspense boundaries be?"**
   No more granular than the loading sequence the user should see. Everything inside one boundary is one unit, so a boundary around the whole page lets the slowest part hide everything. A boundary around every component makes the page jump in many small pieces. React's documentation says: "Don't put a Suspense boundary around every component," and advises asking the designer where the loading states go. Nested boundaries give stages, one level at a time. React reveals content at most once every 300 milliseconds after the last reveal, so boundaries that become ready within that window appear together.
3. **"The user clicks a tab, and the content they were reading is replaced by a spinner. How do you stop that?"**
   The boundary shows its fallback every time a child suspends, unless the update is non-urgent. Wrap the update in `startTransition`, or use `useDeferredValue`, and React keeps the already revealed content until the new data is ready. `useTransition` adds `isPending`, so you can fade the old content to show that something is loading. If the new content is a different thing, such as another user's profile, put a `key` on the boundary, for example the user's ID. React then treats it as different content and shows the fallback on purpose (Lesson 25).

```tree caption="The three interview answers about Suspense: what activates it, where boundaries sit, and how to keep content on the screen."
Suspense in an interview
- +What activates a boundary [`use` `lazy`] | A component that **suspends during render** | An Effect fetch **never** shows the fallback
- +Where boundaries sit [`Suspense`] | Around the **slow parts**, nested to match the **loading sequence** | Not around **every component**
- +After content is shown [`startTransition` `isPending`] | A non-urgent update **keeps the already revealed content** | A `key` on the boundary shows the fallback **on purpose** for different content
```
