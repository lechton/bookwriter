*(How does React keep a hostile comment from running, and where does that protection stop?)*

> INTERVIEW QUESTION | ❱❱ MORE | How does React protect you from cross-site scripting, and when does dangerouslySetInnerHTML remove that protection?

## VS | Curly Braces `{comment}` vs. `dangerouslySetInnerHTML`: the same string shows as text, or runs as code

> React protects your app by handing every string in curly braces to the browser as plain text, so a hostile tag inside a comment never runs. **When you use `dangerouslySetInnerHTML` to show formatted text, that protection ends, and the browser runs any code the HTML carries**. So before you show HTML written by other people, pass it through a sanitizer such as DOMPurify, which keeps the formatting and removes the code.

Remember `textContent` and `innerHTML` from plain JavaScript? Both put a string inside an element, but they do very different things with it:
- **`textContent`** shows the characters exactly as they are. A tag inside the string appears on the page as the characters `<`, `img`, and the rest.
- **`innerHTML`** reads the string as HTML. The browser builds real elements from the tags, and it runs the code those elements carry.

```js title="Plain JavaScript: one string, two properties"
const div = document.getElementById('comment');
const comment = `<img src="" onerror='alert("you were hacked")'>`;

div.~textContent~ = comment; // The page shows the characters of the tag, and nothing runs
div.~innerHTML~ = comment; // The browser builds an img element, and its onerror code runs
```

In React, you do not set these properties yourself, because React creates the elements from your JSX. But React gives you the same two choices, under other names. **Curly braces work like `textContent`. `dangerouslySetInnerHTML` works like `innerHTML`.**

```jsx title="React: the same two choices"
<div>~{comment}~</div> {/* Like textContent: the page shows the characters, and nothing runs */}
<div ~dangerouslySetInnerHTML={{ __html: comment }}~ /> {/* Like innerHTML: the browser builds an img, and its onerror runs */}
```

`alert` is a function the browser gives every page. It opens a small dialog with a message and an OK button. People who attack websites use it to prove that their code runs.

Take a news site. The article page shows a title, `Park Opens Today`, one line with one bold word, "The park opens at **noon**.", and a list of reader comments under it. A reader named Mia posts a comment. She does not type words. She types exactly the `<img>` tag from the code above. Ask yourself: what does every other visitor see when the page shows Mia's comment?

Nothing bad. The page shows comments with curly braces, so every visitor sees Mia's characters printed in the list, exactly as she typed them. No image appears, and no alert opens:

```page caption="The article page after Mia posts her comment: her characters are printed as a line of text."
heading: Park Opens Today
line: The park opens at noon.
section: Comments
line: • John: Great news!
line: • Mia: <img src="" onerror='alert("you were hacked")'> | good
```

Now suppose the same characters end up inside the article body. The article body needs its bold word, so the page shows it with `dangerouslySetInnerHTML`. As soon as the article loads, the browser of every visitor opens the alert:

```page caption="The same characters placed inside the article body: the browser opens the alert for every visitor."
line: localhost:5173 says: you were hacked [OK] | bad
heading: Park Opens Today
line: The park opens at noon.
section: Comments
line: • John: Great news!
line: • Mia: <img src="" onerror='alert("you were hacked")'> | good
```

**Why:** The string is the same, and the page is the same. Only the way our code hands the string to the browser changed. With curly braces, the browser gets text, and the browser never runs text. With `dangerouslySetInnerHTML`, the browser gets HTML to read, and it runs whatever that HTML carries. See the problem? With a harmless article, `dangerouslySetInnerHTML` simply looks like the way to get a bold word, so developers treat it as a choice of formatting. **It looks like a choice of formatting, but it is NOT only that!** It is the exact line where React's protection ends.

> [!DEFINITION]
> **Cross-site scripting.** [NEW] Cross-site scripting, or XSS, is an attack where someone gets a site to run their own code as though it were part of the site. The person who sends that code is called the attacker, here Mia. Her code then runs in the browser of every visitor, with the same rights as the code of the site itself (Lesson 48).

Remember the one sentence of this lesson. **Curly braces give the browser text, and the browser never runs text. `dangerouslySetInnerHTML` gives the browser HTML, and the browser runs what that HTML carries.**

### Where React's Protection Ends

React's protection is the curly braces. Every string we put in curly braces, as text between tags or as the value of an attribute, reaches the browser as text. The protection ends in two places:
1. **At `dangerouslySetInnerHTML`.** Here our code decides what HTML the browser reads and runs.
2. **At an address in `href`.** React 19 blocks one kind of address, the one that starts with `javascript:`. Every other address goes on the link exactly as given, and the browser follows it when the user clicks.

What is at stake is every visitor of the page:
1. The React docs warn: "The code embedded in the HTML will run."
2. With a real attack instead of an alert, "a hacker could use this security hole to steal user information or to perform actions on their behalf."
3. A comment or an article is saved on the server. MDN explains that when hostile text is saved, "the infected content will be served to all users who access the page, every time they access it."

### The Rule of Thumb: does it need to be HTML, and who can write it?

**Ask two questions about every string you put on the page. Does it need to be HTML? If not, use curly braces. If it must be HTML, who can write it? If anyone outside your team can influence it, pass it through a sanitizer first.**

A senior developer also knows the four classic mistakes:
1. **Believing React protects every string.** React protects the curly braces. HTML passed to `dangerouslySetInnerHTML` gets no protection at all.
2. **Trusting HTML because it comes from our own server or our own admin page.** The danger depends on who wrote the string, not on where it is stored.
3. **Searching the HTML for `<script>` only.** A `<script>` tag that arrives inside such HTML does not run, but an `onerror` attribute on an image does.
4. **Trusting React with every link.** React 19 blocks only addresses that start with `javascript:`.

### Three Ways to Show Text Written by Other People

A news page shows text written by other people. Some of it is plain text, such as a comment. Some of it is formatted HTML, such as an article body with a bold word. There are three ways to show it:
1. **Curly braces, such as `{comment.body}`.** This fits any text that should appear as text: names, comments, chat messages, titles. There is nothing to add.
2. **`dangerouslySetInnerHTML` with HTML we trust.** This fits HTML that only its own author ever sees, or HTML from a source we trust completely. The React docs show a Markdown preview: the user types text with simple marks, such as two stars around a word for bold, and sees it formatted. There, "the user only sees their own input".
3. **`dangerouslySetInnerHTML` with HTML that went through a sanitizer first.** This fits HTML written by other people, such as article bodies from an editor or a product description from a supplier.

> [!DEFINITION]
> **A sanitizer.** [NEW] A sanitizer is a library that takes a string of HTML and returns a new string without the parts that run code. It keeps the tags that only format the text, such as `<b>`, and removes the parts that run code, such as `onerror`. The library this lesson uses is DOMPurify, and its function is `DOMPurify.sanitize` (Lesson 48).

```tree caption="Three ways to show text written by other people, and when each one fits."
Three ways to show text written by other people
- +1. Curly braces [`{comment.body}`] | Names, comments, messages, titles | **Safe** with no extra work
- +2. `dangerouslySetInnerHTML` with trusted HTML | HTML that only its own author sees | Safe only while **nobody else** can write the string
- +3. `dangerouslySetInnerHTML` after `DOMPurify.sanitize` | HTML written by **other people** | The sanitizer **removes the parts that run code** first
```

**PRINCIPLES:** Curly braces give the browser text, and the browser never runs text. The danger starts where our code asks the browser to read a string as HTML, or to follow an address a user typed. Five principles follow:
1. **Principle 1: Curly Braces Show a Tag as Plain Text.** A comment that holds an `<img>` tag reaches the page as characters, so nothing in it runs.
2. **Principle 2: `dangerouslySetInnerHTML` Turns a String into Elements.** When a page must show HTML made elsewhere, this prop hands the string to the browser, which builds elements from it.
3. **Principle 3: `onerror` Runs in the Browser of Every Visitor.** Once the browser builds elements from the string, it also runs the code inside them, for every visitor, on every visit.
4. **Principle 4: DOMPurify Removes `onerror` Before the Browser Sees It.** HTML written by other people goes through a sanitizer, which keeps the bold word and removes the code.
5. **Principle 5: React 19 Blocks a `javascript:` Link.** React stops one kind of link that runs code on a click, and places every other address exactly as the user typed it.

## PRINCIPLE | Curly braces `{comment.body}`: a tag inside the string reaches the page as text

> [!PRINCIPLE]
> **Principle 1: Escaping: A Tag Inside a String Reaches the Page as Text**
>
> *Show every name, comment, and title with curly braces; React gives the string to the browser as text, so any tag inside it is shown and never run.*
>
> A comment is a string, and a string can hold any characters, including a whole `<img>` tag. With curly braces, React DOM hands those characters to the browser as text. The browser makes elements only from the JSX tags in our code, so the payload stays a line of strange characters, and nothing runs. The same holds for the value of an attribute, such as `title={comment.body}`.
>
> **DO THIS:**
> ```jsx
> <li key={comment.id}>
>   <strong>{comment.author}</strong>: ~{comment.body}~ {/* Mia's tag shows as characters, nothing runs */}
> </li>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <li key={comment.id} ~dangerouslySetInnerHTML={{ __html: comment.body }}~ /> {/* **WRONG:** Mia's tag becomes an img, and its onerror runs for every visitor */}
> ```

Start with the smallest case. A string holds the characters of Mia's comment, and a paragraph shows it with curly braces:

```jsx title="A string that holds a tag, placed in a paragraph with curly braces"
const text = `<img src="" onerror='alert("you were hacked")'>`;

<p>~{text}~</p> {/* The page shows the characters of the tag: no image, no alert */}
<p ~title={text}~>John</p> {/* When the user hovers over John, the tooltip shows the same characters */}
```

> [!DEFINITION]
> **A payload.** [NEW] A payload is the hostile string an attacker sends to a site, hoping that the site will run it. The body of Mia's comment is a payload: to her, the important part is the `onerror` code inside the `<img>` tag (Lesson 48).

A friendly comment such as `Great news!` and Mia's payload go on the page in the same way. **Yes, it is the exact same thing!** Both are strings, and React gives both to the browser as text, whatever characters they hold. The browser makes elements only from the JSX tags our code writes, never from the characters inside a value.

```tree caption="A friendly comment and a hostile comment go on the page the exact same way with curly braces."
Two comments placed with `{comment.body}`
- +A friendly comment [`Great news!`] | React gives the browser **text** | The page shows **Great news!**
- +The hostile comment of Mia [`<img onerror>`] | React gives the browser **text** too | The page shows **the characters of the tag**, and nothing runs
```

### Why No Image Appears and No Alert Opens

The page shows Mia's tag as a line of text, because the browser never reads it as HTML. Here is what happens, in order:
1. Mia types her `<img>` tag into the comment field, and the server saves it exactly as she typed it.
2. The comment list places `{comment.body}` inside the list item of her comment.
3. React DOM gives the browser the string as a **text node**: a piece of the page that holds only characters.
4. The browser shows the characters `<`, `img`, and the rest, one by one.
5. No `<img>` element exists, so no image fails to load, and `onerror` never fires.
6. The visitor sees Mia's comment as a line of strange text. No alert opens.

> [!DEFINITION]
> **Escaping.** [NEW] Escaping, also called output encoding, is how React keeps a string as text: every value you put in curly braces reaches the page as characters, never as tags. MDN says it in one sentence about React: "values embedded in JSX are automatically encoded". When you ask the browser for the HTML of that list item, it writes each `<` as `&lt;` and each `>` as `&gt;`. These codes are called HTML entities: they tell the browser to show the character instead of reading it as the start of a tag (Lesson 48).

### Our First Step: the Comment List

Our page starts with the saved comments. John's comment is friendly, and Mia's comment is the payload:

```js title="src/data.js"
export const comments = [
  { id: 1, author: 'John', body: 'Great news!' },
  { id: 2, author: 'Mia', body: ~`<img src="" onerror='alert("you were hacked")'>`~ }, // Saved by the server exactly as Mia typed it
];
```

`CommentList` receives the comments as a prop and shows each one with curly braces:

```jsx title="src/CommentList.jsx"
export default function CommentList({ comments }) {
  return (
    <ul>
      {comments.map(comment => (
        <li key={comment.id}>
          <strong>{comment.author}</strong>: ~{comment.body}~ {/* Mia's tag reaches the page as characters */}
        </li>
      ))}
    </ul>
  );
}
```

`comment` is the parameter of the arrow function we give to `comments.map`. JavaScript calls that function once for each saved comment and passes the comment in (Lesson 18).

`App` imports the comments from the data file and passes them to `CommentList`:

```jsx title="src/App.jsx"
import { comments } from './data.js';
import CommentList from './CommentList.jsx';

export default function App() {
  return (
    <main>
      <h1>Park Opens Today</h1>
      <h2>Comments</h2>
      ~<CommentList comments={comments} />~ {/* Both comments go through the same curly braces */}
    </main>
  );
}
```

```page caption="The comment list: the payload of Mia is printed as text, and no alert opens."

section: Comments
```

### A Real Beginner Mistake: "Fixing" the Printed Tag

The page is safe, but it looks odd. That is where the trouble starts:
1. A developer sees Mia's `<img>` tag printed in a comment.
2. The developer thinks the page is broken, because a user should never see tags.
3. The developer "fixes" it by showing comments with `dangerouslySetInnerHTML`, so that tags in comments turn into formatting.
4. The next visitor who opens the page gets Mia's alert.

The printed tag is not a bug. It is the protection doing its job.

## PRINCIPLE | `dangerouslySetInnerHTML`: the browser turns the string into real elements

> [!PRINCIPLE]
> **Principle 2: `dangerouslySetInnerHTML`: The Browser Reads the String as HTML**
>
> *When a page must show HTML made elsewhere, pass `{ __html: string }` to `dangerouslySetInnerHTML`; React sets the `innerHTML` of the element, and the browser parses the string into elements.*
>
> Curly braces always give the browser text, so `{article.html}` prints every tag as characters. Showing formatted HTML needs a separate act: React sets `innerHTML` on the DOM node, and the browser builds elements from the string. React makes that act long, odd, and easy to find on purpose, because from that line on, the browser follows whatever the string says.
>
> **DO THIS:**
> ```jsx
> export default function ArticleBody({ article }) {
>   return <div ~dangerouslySetInnerHTML={{ __html: article.html }}~ />; // The visitor sees noon in bold
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function ArticleBody({ article }) {
>   return <div ~dangerouslySetInnerHTML={article.html}~ />; // **WRONG:** a plain string instead of { __html }, so React stops with an error
> }
> ```

Comments need only text. The article body is different. The editors of the site write articles on an **admin page**, a private page where the team writes and saves articles. The editor made **noon** bold, so the article body is saved as HTML. A string that holds HTML tags as characters is called a **raw HTML string**.

Curly braces would print the tags of that string. To show the bold word, we need the other line from the start of this lesson:

```jsx title="A raw HTML string handed to the browser as HTML"
const html = '<p>The park opens at <b>noon</b>.</p>';

<div ~dangerouslySetInnerHTML={{ __html: html }}~ /> {/* The page shows "The park opens at noon." with noon in bold */}
```

Three names sit on that line:
- **`dangerouslySetInnerHTML`** is a prop that React DOM gives every built-in element. It takes "an object of the form `{ __html: '<p>some html</p>' }`", with a raw HTML string inside.
- **`__html`** is the one key React reads from that object. React chose the name.
- **`innerHTML`** is the same browser property you know from plain JavaScript. The React docs say the prop "overrides the `innerHTML` property of the DOM node". The browser then **parses** the string: it reads the characters, builds elements from the tags it finds, and puts them inside the element.

The double braces are not a special React syntax. The outer braces step into JavaScript, and the inner braces are an ordinary object, exactly as in `style={{ color: 'red' }}` (Lesson 03).

The name is long and odd on purpose. The React docs say: "This should be used with extreme caution!" The word "dangerously" and the extra `__html` object make every place that hands HTML to the browser easy to spot in the code.

```tree dir=right caption="What happens to the string after our code passes it to dangerouslySetInnerHTML."
From `__html` to elements on the page
- +1. Our code [`{ __html: html }`] | Wraps the **raw HTML string** in an object
- +2. React DOM [`innerHTML`] | Sets the **`innerHTML`** of the `<div>` to the string
- +3. The browser | **Parses** the string and builds **a `<p>` that holds a `<b>`**
```

## PRINCIPLE | `onerror` inside that HTML: the browser runs it for every visitor

> [!PRINCIPLE]
> **Principle 3: Stored XSS: The Browser Runs `onerror` for Every Visitor**
>
> *HTML passed to `dangerouslySetInnerHTML` is parsed and run by the browser exactly as written, so an event handler attribute such as `onerror` inside it runs code for every visitor who opens the page.*
>
> The payload needs no `<script>` tag. An `<img>` with an empty `src` fails to load, and the browser runs its `onerror` attribute. Because the article is saved on the server, the same code runs for every visitor, on every visit. Coming from our own admin page does not make the HTML safe: the question is who can write the string.
>
> **DO THIS:**
> ```jsx
> <li key={comment.id}>
>   <strong>{comment.author}</strong>: ~{comment.body}~ {/* A comment needs no HTML, so its onerror stays text */}
> </li>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <div ~dangerouslySetInnerHTML={{ __html: article.html }}~ /> {/* **WRONG:** anyone who can edit article.html runs code in the browser of every visitor */}
> ```

**Beware! Once the browser parses a string as HTML, it also runs the code that the HTML carries.** No `<script>` tag is needed. An image that fails to load is enough.

Here is the smallest case. The React docs show it themselves, as an example of a security hole:

```jsx title="The React docs example of a security hole"
const post = {
  content: ~`<img src="" onerror='alert("you were hacked")'>`~, // Imagine this content is stored in the database
};

<div ~dangerouslySetInnerHTML={{ __html: post.content }}~ /> {/* The browser opens the alert: you were hacked */}
```

It is the same string Mia typed in Principle 1. Only the way it reaches the page changed. With curly braces, the browser showed these characters. With `dangerouslySetInnerHTML`, the browser builds an `<img>` element from them, and the code inside that element runs.

> [!DEFINITION]
> **An inline event handler.** [NEW] An inline event handler, also called an event handler attribute, is an HTML attribute whose value is JavaScript code. The browser runs that code when the event happens. `onerror` is one of them: the browser runs it when an `<img>` fails to load, and an `<img>` with an empty `src` always fails. `onmouseover` is another one: it runs when the visitor moves the mouse over the element (Lesson 48).

### Our Third Step: an Attacker Edits the Article

**Beware! Coming from our own admin page does not make the HTML safe.** One stolen password is enough. Here is how it happens, in order:
1. An attacker signs in to the admin page with a stolen password.
2. The attacker adds the `<img>` tag with `onerror` to the end of the article HTML, and saves.
3. A visitor opens the article.
4. `ArticleBody` passes the string to `dangerouslySetInnerHTML`, and the browser parses it.
5. The browser builds an `<img>` element with an empty `src`.
6. Loading the image fails, so the browser fires the `error` event.
7. The browser runs the `onerror` attribute: the alert opens, saying `you were hacked`.
8. The same happens for every visitor, on every visit, until someone fixes the article.

The only change is in the data file:

```js title="src/data.js" startLine="1"
export const article = {
  title: 'Park Opens Today',
  html: `<p>The park opens at <b>noon</b>.</p>~<img src="" onerror='alert("you were hacked")'>~`, // Added by the attacker on the admin page
};
```

`ArticleBody` does not change. It still passes the article HTML to `dangerouslySetInnerHTML`, and the page now opens the alert as soon as it loads:

```page caption="The article page after the attacker edits the body: the alert opens for every visitor."
line: localhost:5173 says: you were hacked [OK] | bad
heading: Park Opens Today
line: The park opens at noon.
section: Comments
line: • John: Great news!
line: • Mia: <img src="" onerror='alert("you were hacked")'> | good
```

The page now holds two `<img>` tags written by attackers. The one in the comments is still printed as text, because the comments still use curly braces. The one in the article runs, because the article uses `dangerouslySetInnerHTML`.

```dom caption="The HTML of the article body after the attack: a real img element with an onerror attribute."
<div>
  <p>The park opens at <b>noon</b>.</p>
! <img src="" onerror="alert(&quot;you were hacked&quot;)"> | note: A real element, built from the string of the attacker
</div>
```

> [!DEFINITION]
> **Stored XSS.** [NEW] Stored XSS, also called persistent XSS, is the name MDN gives to a payload that is saved on the server and then served to everyone who opens the page. One saved payload reaches every visitor, on every visit. The code of the attacker can do anything our own code can do on the page. The alert is only the harmless demonstration: with a real payload, the attacker can steal user information or act on behalf of the user (Lesson 48).

### Why the Attacker Uses `onerror` and Not `<script>`

A `<script>` tag in the same place would not run. MDN explains that setting `innerHTML` does "prevent `<script>` elements from executing when they are injected". But MDN adds that "it is susceptible to many other ways that attackers can craft HTML to run malicious JavaScript". An `onerror` attribute is one of those ways. Every other inline event handler works the same way, such as `onmouseover`.

### A Real Beginner Mistake: Trusting the Admin Page

1. A team shows article bodies with `dangerouslySetInnerHTML`, because only editors can write them.
2. Months later, the password of an editor leaks.
3. Someone adds an `<img>` with `onerror` to one popular article.
4. The code runs in the browser of every reader, with the same rights as the code of the site itself.
5. The team searches the articles for `<script>` and finds nothing.

What matters is who can write the string. An admin account can be taken over, and an editor can paste HTML copied from anywhere.

## PRINCIPLE | `DOMPurify.sanitize`: the bold word stays, and the `onerror` is removed

> [!PRINCIPLE]
> **Principle 4: Sanitizing: DOMPurify Removes the Code and Keeps the Formatting**
>
> *Pass HTML that anyone outside the team can influence through `DOMPurify.sanitize` before it reaches `__html`, and create the `{ __html }` object in one function next to the sanitizer.*
>
> The article body needs HTML for its bold word, so curly braces cannot show it. DOMPurify keeps the tags that format, such as `<p>` and `<b>`, and removes the parts that run code, such as `onerror` and `<script>`. A filter we write ourselves misses cases, so a library that experts maintain does the cleaning. One function such as `toSafeHTML` keeps every raw HTML string in one place that a reader can find.
>
> **DO THIS:**
> ```jsx
> function toSafeHTML(html) {
>   return { __html: ~DOMPurify.sanitize(html)~ }; // onerror is removed, noon stays bold
> }
> <div dangerouslySetInnerHTML={toSafeHTML(article.html)} />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const cleaned = ~article.html.replace('<script>', '')~; // **WRONG:** removes <script> but lets the img with onerror through
> <div dangerouslySetInnerHTML={{ __html: cleaned }} />
> ```

The article body really needs HTML, because of the bold word. So we cannot go back to curly braces. Instead, we clean the HTML before the browser sees it.

**Sanitizing** is "the process of removing unsafe features from a string of HTML: for example, `<script>` tags or inline event handlers", in the words of MDN. MDN recommends a library for it, DOMPurify, which "is recommended by many experts". Its function `DOMPurify.sanitize` takes a string of HTML and returns a new string without the unsafe parts:

```jsx title="Sanitizing a string with DOMPurify before it reaches __html"
import DOMPurify from 'dompurify';

const clean = ~DOMPurify.sanitize~(`<b>noon</b><img src="" onerror='alert("you were hacked")'>`); // Returns <b>noon</b><img src="">

<div dangerouslySetInnerHTML={{ __html: ~clean~ }} /> {/* noon in bold, and no alert */}
```

The key idea to remember: **sanitizing keeps the tags that format, such as `<b>`, and removes the parts that run code, such as `onerror`**. The visitor keeps the bold word and loses the alert.

### VS | The Raw String vs. the Sanitized String: the same page at first, only one stops the attack

Passing the raw article HTML and passing the sanitized article HTML differ by one call. With the harmless article of Principle 2, they give the exact same page. **They work the same at first, but they are NOT the same thing!** With the article the attacker edited, the raw string carries `onerror` to the browser. The sanitized string has no `onerror` left in it.

```tree caption="The raw article HTML carries onerror to the browser; the sanitized HTML keeps the bold word and drops the code."
What reaches `__html`
- !The raw string [`article.html`] | Still holds **`onerror`** | The browser **opens the alert**
- +The sanitized string [`DOMPurify.sanitize`] | Keeps **`<p>` and `<b>`**, removes **`onerror`** | The visitor sees **noon in bold**, and **nothing runs**
```

Why not write our own filter? Because sanitizing HTML is, in the words of MDN, "difficult to get right". A filter that removes the word `<script>` lets `onerror` through, as Principle 3 showed. A library that experts maintain does the cleaning, and our code only decides where to call it.

### VS | The Object Built Inline vs. the Object Built in One Function: the same page, one place to look

There are two places to build the `{ __html }` object. One is right on the tag. The other is one function that sanitizes the HTML and wraps it at the same moment:

```jsx title="Creating the { __html } object inline on the tag, and in one function"
<div dangerouslySetInnerHTML={~{ __html: DOMPurify.sanitize(article.html) }~} /> {/* 1. Built inline on the tag */}

function ~toSafeHTML~(html) { // 2. Built in one function, right next to the sanitizer
  return { __html: DOMPurify.sanitize(html) };
}
<div dangerouslySetInnerHTML={toSafeHTML(article.html)} />
```

For the page, **yes, it is the exact same thing!** Both show the same bold word, and neither runs the payload. The difference is for the people who read the code. The React docs advise against creating the object inline. They say it "should be created as close to where the HTML is generated as possible". With one function, every raw HTML string in the code passes through the same place, and a reader can find every place that builds `{ __html }`.

`toSafeHTML` is our own function. It follows the shape of the Markdown example in the React docs, where a function named `renderMarkdownToHTML` returns `{__html: renderedHTML}`.

### Our Fourth Step: Sanitizing the Article Body

First we install the library in the project folder (Lesson 07):

```bash title="Terminal"
npm install dompurify
```

The article body component now imports DOMPurify, builds the object in `toSafeHTML`, and passes it to the `<div>`:

```jsx title="src/ArticleBody.jsx"
import DOMPurify from 'dompurify';

function toSafeHTML(html) {
  const clean = ~DOMPurify.sanitize(html)~; // Keeps <p> and <b>, removes onerror
  return { __html: clean };
}

export default function ArticleBody({ article }) {
  return <div ~dangerouslySetInnerHTML={toSafeHTML(article.html)}~ />; // Only sanitized HTML reaches the browser
}
```

The data file keeps the payload the attacker added, so we can see that it no longer runs. DOMPurify does not remove the `<img>` itself. It removes only the `onerror` attribute. The image still fails to load, but nothing runs, because no handler is left.

```page caption="The article page with the sanitized body: noon is in bold, and no alert opens."
heading: Park Opens Today
line: The park opens at noon. | good
section: Comments
line: • John: Great news!
line: • Mia: <img src="" onerror='alert("you were hacked")'> | good
```

```dom caption="The Elements panel with the sanitized body: the img element is still there, but its onerror attribute is gone."
<div>
  <p>The park opens at <b>noon</b>.</p>

</div>
```

The React docs set the condition in one line: "Only use `dangerouslySetInnerHTML` with **trusted and sanitized data**." Our page now follows the three ways from the start of the lesson. The comments use curly braces and need no sanitizing. The article body comes from other people, so it goes through the sanitizer.

### A Real Beginner Mistake: One Filter by Hand, One Component Without It

1. A developer removes `<script>` from the article HTML with a string replace.
2. The `<img>` with `onerror` passes through untouched.
3. Later, another developer sanitizes the body in `ArticleBody`, but passes the raw string in a second component that shows article previews on the home page.
4. The payload runs on the home page, where the previews are.

One `toSafeHTML` function, used by every component that shows article HTML, closes both holes.

## PRINCIPLE | `href` with a `javascript:` URL: React 19 blocks it, and every other address is yours to check

> [!PRINCIPLE]
> **Principle 5: `javascript:` URLs: React 19 Blocks One Scheme Only**
>
> *React 19 blocks a `javascript:` URL in `href` or `src`, but places every other address on the element as given, so check a link a user typed before it goes in `href`.*
>
> Escaping keeps a value inside its attribute, but it does not judge what the value means. The browser runs a `javascript:` URL when the user clicks the link. React 19 replaces such an address with one that only throws an error. Any other address, including a fake sign-in page, reaches the link unchanged, so our code allows only addresses that start with `https://`.
>
> **DO THIS:**
> ```jsx
> {~comment.website.startsWith('https://')~ ? <a href={comment.website}>{comment.author}</a> : <span>{comment.author}</span>} {/* Mia's name shows as text */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <a ~href={comment.website}~>{comment.author}</a> {/* **WRONG:** every address a user types becomes a link, unchecked */}
> ```

### An Address Can Be Code

Escaping keeps a value inside its attribute. It does not judge what the value means to the browser. Some attributes are dangerous with any value, because the browser acts on them. `href` is one of them: the browser follows it when the user clicks the link.

```jsx title="An address that is really code, placed in href with curly braces"
const url = 'javascript:alert("you were hacked")';

<a ~href={url}~>Mia</a> {/* Without the block in React 19, a click by the user would run alert */}
```

> [!DEFINITION]
> **A `javascript:` URL.** [NEW] The word before the colon at the start of an address is its URL scheme, such as `https` or `javascript`. A `javascript:` URL is, in the words of MDN, a fake navigation target that will "execute JavaScript when the browser attempts to navigate". It needs no tag and no quote to break out of: the whole value is code (Lesson 48).

React 19 blocks it in `href` and in `src`. React DOM does not put Mia's address on the link. In its place, it writes a `javascript:` URL of its own, which only throws an error when the user clicks.

John's link and Mia's link are both written as `href={comment.website}`. **It looks the same, but it is NOT the same thing!** John's address leads to a page. Mia's address is code that the browser would run on a click, and React 19 blocks it.

### Our Fifth Step: a Website Link for Each Comment

Blog comments often have a "Your website" field. Each saved comment gets a `website`:

```js title="src/data.js" startLine="6"
export const comments = [
  { id: 1, author: 'John', website: 'https://john.example.com', body: 'Great news!' },
  { id: 2, author: 'Mia', website: ~'javascript:alert("you were hacked")'~, body: `<img src="" onerror='alert("you were hacked")'>` }, // Mia typed code into the website field
];
```

`CommentList` makes the name of each author a link to their website:

```jsx title="src/CommentList.jsx" startLine="5"
<li key={comment.id}>
  <a ~href={comment.website}~>{comment.author}</a>: {comment.body} {/* John's link opens his site; Mia's link is blocked */}
</li>
```

John's link works, and Mia's link does nothing harmful. Here is what happens on each row:
1. On the row of John, a click by the user opens his website.
2. On the row of Mia, React 19 sees the `javascript:` scheme in `href` and replaces the address.
3. The link is still on the page, with Mia's name on it.
4. When the user clicks it, no alert opens. The Console shows the error of React instead:

```page caption="The link of Mia after a click by the user: no alert opens, and the Console shows the error of React."

line: The park opens at noon.

line: • John: Great news!
line: • Mia: <img src="" onerror='alert("you were hacked")'> | good

```

```dom caption="The href that React 19 writes on the link of Mia in place of her javascript: URL."
<li>
  <a href="https://john.example.com">John</a>: Great news!
</li>
<li>
+ <a href="javascript:throw new Error('React has blocked a javascript: URL as a security precaution.')">Mia</a>: ... | note: Written by React, not by Mia
</li>
```

### What React 19 Leaves to Our Code

React blocks one scheme only. Every other address Mia types, React places in `href` exactly as given. She could type the address of a page made to look like the sign-in page of our site, and her name would link to it. So we check a link a user typed before it goes in `href`. The simple check allows only the scheme we want, `https:`, instead of trying to list every bad one:

```jsx title="src/CommentList.jsx"
export default function CommentList({ comments }) {
  return (
    <ul>
      {comments.map(comment => {
        const isLink = ~comment.website.startsWith('https://')~; // true for John, false for Mia
        return (
          <li key={comment.id}>
            {isLink ? <a href={comment.website}>{comment.author}</a> : <span>{comment.author}</span>}: {comment.body}
          </li>
        );
      })}
    </ul>
  );
}
```

`startsWith` is a JavaScript string method that answers true or false. With this check, Mia's name appears as plain text, and no link is made for her at all.

Escaping and the block on `javascript:` URLs are two different protections:
- **Escaping protects characters.** A tag inside a string stays text.
- **The block protects against one URL scheme.** A `javascript:` address in a link, or in the source of an image, does not run.

Neither one checks where an ordinary address leads. That check is ours.

### A Real Beginner Mistake: Trusting React with Every Link

1. A developer adds "Your website" to the comment form and shows the name of the author as a link to that address.
2. The developer trusts that React escapes attributes.
3. An attacker enters a `javascript:` URL.
4. In React 19, the click is blocked. But the developer still ships a link whose address nobody checked.

### How React Calls the Components in Order

When the page loads, React calls `App` first. `App` returns the tags of the two other components. So React then calls `ArticleBody`, which sanitizes the body, and then `CommentList`, which places each comment as text:


| Where the string goes | What the browser does with it | What our code must do |
| :--- | :--- | :--- |
| **Text in curly braces, such as `{comment.body}`** | Shows the characters; tags never run | Nothing: React escapes it |
| **An attribute in curly braces, such as `title={text}`** | Keeps the characters inside the attribute | Nothing for most attributes |
| **`dangerouslySetInnerHTML`** | Parses the string and runs what it carries, such as `onerror` | Pass only trusted HTML, or HTML from `DOMPurify.sanitize` |
| **`href` or `src` with a `javascript:` URL** | Would run the code; React 19 blocks it | Still check the address: allow only `https://` |
| **`href` with any other address** | Follows it when the user clicks | Check it before it goes on the link |

Remember the one sentence of this lesson. **Curly braces give the browser text, and the browser never runs text. `dangerouslySetInnerHTML` gives the browser HTML, and the browser runs what that HTML carries.**

## For the Interview

> **The Interview Question:** How does React protect you from cross-site scripting, and when does dangerouslySetInnerHTML remove that protection?

### How to Answer Clearly in 30 Seconds

"React protects us through curly braces. Every string we place in JSX text or in an attribute reaches the browser as text. So a comment that holds an `<img>` tag shows as characters and never runs. That protection ends at `dangerouslySetInnerHTML`. It sets the `innerHTML` of the element, and the browser parses the string as HTML. Then it runs whatever the HTML carries, such as an `onerror` attribute on a broken image. Because the HTML is usually saved, that is stored XSS: it runs for every visitor. So I follow three rules:
1. **Text stays in curly braces**: names, comments, and titles never need HTML.
2. **HTML from other people goes through a sanitizer**: I pass it through `DOMPurify.sanitize` and build the `{ __html }` object in one function.
3. **Links from users get checked**: React 19 blocks only `javascript:` URLs, so I allow only addresses that start with `https://`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"If the HTML has no `<script>` tag, is it safe to pass to `dangerouslySetInnerHTML`?"**
   **No.** The browser does not run a `<script>` tag inserted through `innerHTML`, but it does run inline event handlers. An `<img>` with an empty `src` fails to load, and the browser runs its `onerror`. `onmouseover` and the other handlers work the same way. That is why a sanitizer such as DOMPurify removes inline event handlers as well as `<script>` tags. Setting `ref.current.innerHTML` by hand carries the same danger (Lesson 31).
2. **"The HTML comes from our own admin page. Do we still need to sanitize it?"**
   **Yes, when anyone outside the team can influence it.** The danger depends on who can write the string, not on where it is stored. The password of an editor can leak, and an editor can paste HTML copied from anywhere. The rule of React is to use `dangerouslySetInnerHTML` only "with trusted and sanitized data". The browser offers a second line of defense. A **Content Security Policy** is a rule the server sends that tells the browser which code may run on the page. **Trusted Types** is a browser feature that can refuse to set `innerHTML` from a plain string. They add safety, but they do not replace sanitizing.
3. **"Does React check every link a user gives us?"**
   **No.** React escapes attribute values, so a value cannot break out of `href`. But escaping does not judge what the address means. React 19 blocks one scheme, `javascript:`, in `href` and `src`, and replaces it with an address that only throws an error. Every other address goes on the link as given, so our code checks it, for example by allowing only `https://`.

```tree caption="What React does for us against cross-site scripting, and what stays our job."
Cross-site scripting in a React app
- +What React does [`{comment.body}` `title={text}`] | **Escapes** every string in curly braces | Blocks **`javascript:` URLs** in `href` and `src`
- !What stays our job [`dangerouslySetInnerHTML` `href`] | **Sanitize** HTML from other people with DOMPurify | **Check** every address a user types
```
