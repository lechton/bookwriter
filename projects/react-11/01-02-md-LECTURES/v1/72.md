# Lecture 72: Catching a Rendering Error with an Error Boundary

*(How do you keep one broken comment from turning the whole page white?)*

> INTERVIEW QUESTION | ❱❱ MORE | How do you catch a rendering error before it unmounts the whole app?

---

## VS | `try` and `catch` vs. an Error Boundary: one catches the code that runs inside it, the other catches the components React renders inside it

> In plain JavaScript, when one line throws an error, you wrap it in `try` and `catch`, and the rest of the script keeps running. **In React, an error thrown while React renders one component removes the whole page from the screen, and a `try` around the JSX cannot stop it**. An Error Boundary can: it catches that error and shows one short message in place of the broken part, so the rest of the page stays.

In React, the data on a page often comes from a server, and **you do not control what is inside it**. A list of comments can hold one comment without its author, because that person deleted their account. The line that reads the author's name then throws a `TypeError`. In plain JavaScript, you would expect one broken line, maybe one missing comment. React does something much harsher: it removes everything it drew, and the user sees a white page.

This is why we have Error Boundaries. An Error Boundary is a component you wrap around a part of the page, and it catches the errors thrown while React renders that part.

Take a news article with a title and two comments under it. Ask yourself: should one broken comment take the whole article with it? No. The title and the first comment have nothing wrong with them. At worst, the comments should be replaced by one short line, such as `Comments are unavailable.`, and the article should stay.

**Why:** You could fix this one bug with a check, such as `comment.author?.name`, which gives `undefined` instead of throwing. That is a good fix for a bug you know about. But nobody knows every bug in advance. Tomorrow another field arrives broken, in another component. An Error Boundary keeps the page on the screen for the errors nobody foresaw.

### One Missing Field, One White Page

Here is the smallest code that breaks a page:

```jsx title="Comment.jsx"
function Comment({ comment }) {
  return <li>{~comment.author.name~}: {comment.text}</li>; // For a comment with no author, this line throws
}
```

For a comment with no author, `comment.author` is `undefined`. JavaScript gives that value for any field the object does not have. Reading a field of `undefined` throws a `TypeError`. That is the JavaScript error for using a value in a way its type does not allow.

This line runs while React renders `Comment`. Two reminders and two new words carry the whole lesson:

> [!DEFINITION]
> **Rendering.** [REVIEW] Rendering is the moment React calls your component function to find out what to show. The lines of the body and the JSX it returns run during rendering. An event handler is different: you write it inside the component, but its code runs later, when the user clicks (Lesson 13).

> [!DEFINITION]
> **Unmount.** [REVIEW] Unmount is React's word for removing what a component drew from the screen. It is the word in the interview question: one error during rendering unmounts the whole app (Lesson 32).

> [!DEFINITION]
> **Error Boundary.** [NEW] An Error Boundary is a component you wrap around a part of the page, such as the comments. The React docs call it "a special component that lets you display some fallback UI instead of the part that crashed." Without one, the docs warn: "By default, if your application throws an error during rendering, React will remove its UI from the screen" (Lesson 72).

> [!DEFINITION]
> **Fallback.** [REVIEW] The fallback, or fallback UI, is what React shows in place of a part of the page that cannot show its real content. You met the word with `<Suspense>`, which shows a fallback while data is on its way. An Error Boundary shows a fallback when a part has crashed, such as the line `Comments are unavailable.` (Lesson 69).

### Why `try` and `catch` Do Not Help

Remember `try` and `catch`? Around a function call, they work, because the function runs inside the `try` block:

```js title="Plain JavaScript: the function runs inside the try"
try {
  ~readName(comment)~; // readName runs right here, so its error lands in the catch
} catch (error) {
  console.log('Caught it');
}
```

So the first idea every developer has is to do the same around the JSX:

```jsx title="React: the tag inside the try only describes Comment"
try {
  return <ul>{comments.map(c => ~<Comment key={c.id} comment={c} />~)}</ul>; // Comment does not run here
} catch (error) {
  return <p>Comments are unavailable.</p>;
}
```

**It looks the same, but it is NOT the same thing!** The tag `<Comment />` is not a call to `Comment`. It is a description that tells React: "call Comment later" (Lesson 4). React calls it after the parent has returned, and by then the `try` block is over. Principle 2 shows it step by step.

### The Error Bubbles Up to the Closest Boundary

So where does the error go? Remember how a click on a `<button>` bubbles up to the `<div>` around it, and then to the body? A rendering error travels the same way, but through your components. It goes from `Comment` to its parent, then to that parent's parent, one level at a time, until it meets an Error Boundary. With no boundary on the way, it reaches the top, and React removes the whole page.

The React docs use the same word: "Errors thrown in rendering methods or hooks bubble up through the component tree. Only Error Boundaries can catch these errors."

Keep this one sentence in mind for the whole lesson: **an error during rendering travels up to the closest Error Boundary above it. That boundary shows its fallback, and everything outside it stays on the screen.**

```tree caption="The same broken comment gives two different pages: with no Error Boundary, and with one around the comments."
The second comment arrives without its author
- !No Error Boundary above the comments | The error travels up to the top of the app | React **removes the whole page**: the user sees **white**
- +An Error Boundary around the comments | The error stops at the **closest boundary** | The boundary shows **its fallback**; the title **stays on the screen**
```

### The Rule of Thumb: when did the error happen?

**Ask one question about every error: did it happen while React renders, or later, in your own code? While React renders, only an Error Boundary catches it. In a click handler or a timer, `try` and `catch` catch it.**

A senior developer also knows the three classic mistakes:
1. **`try` and `catch` around the JSX.** The child runs after the parent returns, so the `catch` never runs.
2. **An Error Boundary written as a function component.** React has no Hook for catching a child's error, so it must be a class.
3. **An Error Boundary that should catch a click.** A click handler runs after rendering, so the boundary never sees its error.

The rest of the lesson shows each mistake on a real news article.

## SECTION | A News Article with Two Comments

Our page is one news article: a title, a `Comments` heading, and two comments from readers. When both comments arrive with their author, it looks like this:

```page url=news.example/city-park caption="The article page when both comments arrive with their author."
heading: City park opens on Saturday
section: Comments
line: John: Great news!
line: Mia: See you there.
```

The page is one small Vite project. `App` holds the article and the list of comments. Each comment is its own component:

```files title="article-page: File Explorer" caption="How the files of our article page sit inside src/."
index.html | page | The HTML page with the empty root div where React mounts
src/
  main.jsx | entry | Imports `App` and renders it into `#root` with `createRoot`
  App.jsx | parent | Holds the title and the `comments` array, and renders one `Comment` for each comment
  Comment.jsx | child | Shows one comment as the author's name and the text
  ErrorBoundary.jsx | new in Principle 3 | The class component that shows a fallback when a child throws
  errorService.js | new in Principle 5 | Exports `logErrorToMyService`, which reports an error to the team
```

`App` holds the title, the heading, and `comments`, which stands for the list the server sent:

```jsx title="src/App.jsx"

const comments = [
  { id: 1, author: { name: 'John' }, text: 'Great news!' },
  { id: 2, author: { name: 'Mia' }, text: 'See you there.' },
];

export default function App() {
  return (
    <main>
      <h1>City park opens on Saturday</h1>
      <h2>Comments</h2>
      <ul>
        {comments.map(comment => (
          ~<Comment key={comment.id} comment={comment} />~ // One Comment tag for each comment
        ))}
      </ul>
    </main>
  );
}
```

`Comment` gets its own file:

```jsx title="src/Comment.jsx"
export default function Comment({ comment }) {
  return <li>{~comment.author.name~}: {comment.text}</li>; // Reads the author's name during rendering
}
```

It works, as long as every comment has an author. Now let's break it. Each principle changes one thing and shows what the user sees:

**PRINCIPLES:** An error during rendering travels up to the closest Error Boundary. Six principles follow:
1. **No boundary removes the whole page.** One broken comment, and React removes the title and John's comment too.
2. **`try` and `catch` around the JSX catch nothing.** React calls the child after the parent has returned.
3. **`getDerivedStateFromError` switches the boundary to its fallback.** An Error Boundary is a class, because no Hook can catch a child's error.
4. **The place of the boundary decides what the user keeps.** Around the comments, the article stays. Around each comment, John's comment stays too.
5. **`componentDidCatch` tells the team.** The fallback hides the error from the user, and this method reports it.
6. **A click handler error skips the boundary.** In a handler, `try` and `catch` is the tool.

## PRINCIPLE | `comment.author.name` during rendering: with no Error Boundary above it, React removes the whole page

> [!PRINCIPLE]
> **Principle 1: Rendering Errors: One Broken Component Removes the Whole Page**
>
> *When a component throws an error during rendering and no Error Boundary sits above it, React removes the whole UI of the root from the screen, not only the broken component.*
>
> A comment from a server can arrive without its author. When `Comment` reads `comment.author.name` for that comment, JavaScript throws a `TypeError` while React is rendering. Nothing above `Comment` catches it, so React removes everything `App` rendered, and the user sees a white page with no message.
>
> **DO THIS:**
> ```jsx
> <h1>City park opens on Saturday</h1>
> ~<ErrorBoundary fallback={<p>Comments are unavailable.</p>}>~ {/* A broken comment stops here; the title stays */}
>   <ul>{comments.map(c => <Comment key={c.id} comment={c} />)}</ul>
> </ErrorBoundary>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <h1>City park opens on Saturday</h1>
> ~<ul>~{comments.map(c => <Comment key={c.id} comment={c} />)}</ul> {/* **WRONG:** no boundary above the comments, so one broken comment blanks the whole page */}
> ```

Mia deletes her account, and the server now sends her comment without its author:

```jsx title="src/App.jsx" startLine="3"
const comments = [
  { id: 1, author: { name: 'John' }, text: 'Great news!' },
  ~{ id: 2, text: 'See you there.' }~, // Sent by the server without its author
];
```

`Comment` has not changed. For the second comment, it reads `.name` of `undefined` and throws. The user opens the article:

```page url=news.example/city-park caption="What the user sees: the whole article page is white, not only the broken comment."
blank
```

**The whole page is white.** The broken comment is gone, and so are the title and John's comment, which have nothing wrong with them. The user sees no message at all.

The Console shows two messages. The first is the browser's report of the `TypeError`, and "Uncaught" means no code caught it. The second is a warning from React that names the broken component and suggests an Error Boundary:

```devconsole width=full caption="The Console after the user opens the article: the browser's TypeError and React's warning that suggests an Error Boundary."
x Uncaught TypeError: Cannot read properties of undefined (reading 'name')
! An error occurred in the <Comment> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

React did not hide the page. It removed it. Open the Elements panel: the root div, where `createRoot` put our app (Lesson 7), is empty:

```dom caption="The Elements panel after the error: the root div holds nothing."
<body>
! <div id="root"></div> | note: Empty: nothing from App is on the page
</body>
```

### Why the title disappears too

**The title has no error, and React still removes it.** The error starts in one comment, but nothing stops it on its way up, so React gives up on the whole page. Here is the order:
1. The user opens the article, and React calls `App`. It returns the title, the heading, and two `<Comment>` tags.
2. React calls `Comment` for John. It returns `John: Great news!`.
3. React calls `Comment` for the second comment. Reading the name of `undefined` throws a `TypeError`.
4. The error bubbles up, looking for an Error Boundary. There is none, neither in `App` nor above it.
5. React removes the whole page from the screen. The title and John's comment go with it.

```tree dir=right caption="How one error in the second Comment removes the whole article page when no Error Boundary sits above it."
One error while React renders the second comment
- +1. React calls `App` and the first `Comment` | Both return their markup **without an error**
- !2. React calls the second `Comment` [`comment.author.name`] | `comment.author` is **`undefined`** | Reading `.name` **throws a `TypeError`**
- !3. No Error Boundary above `Comment` | React **removes the whole UI** of the root | The user sees **a white page**
```

Something that can be tricky: this bug rarely shows up on the developer's own screen. The developer tests with comments that all have an author, and the page works. In production, one comment arrives without its author. From then on, every user who opens that article sees a white page.

## PRINCIPLE | `try` and `catch` around the JSX: the catch is already over when the child throws

> [!PRINCIPLE]
> **Principle 2: Bubbling: `try` and `catch` Cannot Catch a Child's Rendering Error**
>
> *A `try` and `catch` inside a parent component cannot catch an error thrown while React renders a child component, because the parent only returns the child's tag and React calls the child later.*
>
> The error bubbles up the component tree from the component that threw it, one parent at a time. Only an Error Boundary on that path can catch it. A `catch` block in the parent was already finished when the child threw.
>
> **DO THIS:**
> ```jsx
> ~<ErrorBoundary fallback={<p>Comments are unavailable.</p>}>~ {/* Catches the error that bubbles up from any Comment inside */}
>   <CommentList comments={comments} />
> </ErrorBoundary>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function CommentList({ comments }) {
>   try {
>     return <ul>{comments.map(c => <Comment key={c.id} comment={c} />)}</ul>;
>   } ~catch~ { // **WRONG:** Comment runs after CommentList returns, so this catch never sees its error
>     return <p>Comments are unavailable.</p>;
>   }
> }
> ```

A developer sees the white page and reaches for the tool they know. They move the list into its own component and wrap its JSX in `try` and `catch`. React's docs show this exact code under the words "Try/catch won't catch render errors":

```jsx title="src/CommentList.jsx" bad="10"
import Comment from './Comment.jsx';

export default function CommentList({ comments }) {
  try {
    return (
      <ul>
        {comments.map(comment => ~<Comment key={comment.id} comment={comment} />~)} {/* Only describes each Comment: Comment does not run here */}
      </ul>
    );
  } ~catch~ (error) { // **WRONG:** never runs: Comment throws after CommentList has returned
    return <p>Comments are unavailable.</p>;
  }
}
```

The user opens the article. The page is still white.

### Why the `catch` is already over when `Comment` throws

**The `catch` is not broken. It is simply over before the error happens.** Writing `<Comment />` never calls `Comment` (Lesson 4). React renders a child only after its parent has returned (Lesson 13). Here is the order:
1. React calls `CommentList`.
2. The `try` block runs the `return` line. It builds a description of two `<Comment>` tags, and nothing throws.
3. `CommentList` returns. Its `try` and its `catch` are finished.
4. React calls `Comment` for each tag. The second one throws.
5. No `catch` is waiting anymore, and no Error Boundary sits above, so React removes the page.

```tree dir=right caption="Why the catch block in CommentList never sees the error that the second Comment throws."
`try` and `catch` in `CommentList` around `<Comment />`
- +1. React calls `CommentList` | The `try` block **only describes** the `<Comment>` tags | Nothing throws, and `CommentList` **returns**
- !2. React calls `Comment` next | The second `Comment` **throws** | The `catch` in `CommentList` is **already finished**
- !3. The error bubbles up | No boundary above it | The page goes **white**
```

Compare it with plain JavaScript. Around `readName(comment)`, the function runs inside the `try`. So the catch block sees its error. Around `<Comment />`, nothing runs inside the `try`. The tag only describes the child.

So does `try` and `catch` never work in a component? It does, for code that runs inside that same `try` block. If `Comment` itself wrapped the line that reads the author's name in a `try` block, that catch block would run. What a `try` misses are the errors of child components.

The linter can save you here (Lesson 38). The `error-boundaries` rule of the React Hooks ESLint plugin flags this code. The docs describe the rule in one line: "Validates usage of Error Boundaries instead of try/catch for errors in child components."

## PRINCIPLE | `getDerivedStateFromError`: React switches the boundary from its children to its fallback

> [!PRINCIPLE]
> **Principle 3: Class Boundary: `getDerivedStateFromError` Switches `render` to the Fallback**
>
> *An Error Boundary is a class component with `static getDerivedStateFromError`, which returns new state when a child throws during rendering, and a `render` method that returns the fallback when that state says so and the children otherwise.*
>
> No Hook tells a function component that a child threw, so the boundary must be a class. When a child throws, React calls `getDerivedStateFromError`, puts the state it returns into the boundary, and renders the boundary again. This time `render` returns the fallback.
>
> **DO THIS:**
> ```jsx
> class ErrorBoundary extends Component {
>   state = { hasError: false };
>   static ~getDerivedStateFromError~() { // React calls it when a child throws, and the fallback shows
>     return { hasError: true };
>   }
>   render() {
>     return this.state.hasError ? this.props.fallback : this.props.children;
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ErrorBoundary({ children, fallback }) {
>   const [~hasError~] = useState(false); // **WRONG:** nothing sets it when a child throws, so the page still goes white
>   return hasError ? fallback : children;
> }
> ```

Every component you wrote so far is a function. Before Hooks existed, React components were also written as JavaScript classes. Today you almost never need one, with one exception: the Error Boundary. React tells a component that a child threw only through a class method, and no Hook does the same job.

> [!DEFINITION]
> **Class component.** [NEW] A class component is a React component written as a JavaScript class instead of a function. It extends `Component` from React, keeps its state in a field named `state`, and returns its JSX from a method named `render`. Today its main use is the Error Boundary, because "there is currently no way to write an Error Boundary as a function component" (Lesson 72).

### The smallest Error Boundary

An Error Boundary has two answers: its children, or its fallback. One state field, `hasError`, picks between them. Here is the smallest boundary, the same shape the React docs use:

```jsx title="src/ErrorBoundary.jsx"
import { ~Component~ } from 'react'; // React provides the base class for class components

export default class ~ErrorBoundary extends Component~ { // A class component, not a function
  state = { ~hasError: false~ }; // The first state: no child has thrown yet

  static ~getDerivedStateFromError~(error) { // React calls this when a child throws during rendering
    return { hasError: true }; // The new state: show the fallback
  }

  render() {
    if (~this.state.hasError~) { // React calls render to ask what to show
      return this.props.fallback;
    }
    return ~this.props.children~; // No error: show what sits between the tags
  }
}
```

We use it like any other component. The fallback is an ordinary prop, and the children are everything between the tags (Lesson 9):

```jsx title="Using ErrorBoundary around the comments"
<ErrorBoundary ~fallback={<p>Comments are unavailable.</p>}~> {/* What to show if a child throws */}
  <ul>{comments.map(comment => <Comment key={comment.id} comment={comment} />)}</ul>
</ErrorBoundary>
```

### The class words, one at a time

The file uses five words the earlier lessons never needed. Each one does one job:
1. **`class` and `extends Component`.** A class is a JavaScript template for objects, and JavaScript provides both words. `Component` comes from React, and extending it makes our class a React component.
2. **`state = { hasError: false }`.** This is the first state of the class, before any error. The docs: "The `state` field must be an object."
3. **`render`.** This method returns what appears on the screen. The docs: "The `render` method is the only required method in a class component."
4. **`static`.** A static method belongs to the class itself, not to one object made from it. React calls `getDerivedStateFromError` on the class, so the method must be static.
5. **`getDerivedStateFromError`.** React calls it when a child throws during rendering, "including distant children", so a child of a child counts too. It "should return the state telling the component to display the error message."

The `error` it receives is the value that was thrown. The docs say it "will usually be an instance of `Error` but this is not guaranteed because JavaScript allows to `throw` any value."

### VS | `this.state` vs. state in a function: the same thing, read through `this`

`this.state` and `this.props` look new. They are not:

```jsx title="Reading state and props in a class and in a function component"
if (~this.state.hasError~) return ~this.props.fallback~; // In a class: read through this
if (~hasError~) return ~fallback~; // In a function: hasError from useState, fallback from the props
```

**Yes, it is the exact same thing!** A class reads its own state and props through the word `this`, which means "this boundary". The docs: "The props passed to a class component are available as `this.props`", and "The state of a class component is available as `this.state`."

### Why a function component cannot be a boundary

So can we write the boundary as a function with `useState`? Reading state is the same, but catching is not:

```jsx title="A function component that tries to be an Error Boundary"
function ErrorBoundary({ children, fallback }) {
  const [~hasError~, setHasError] = useState(false); // **WRONG:** no Hook tells this function that a child threw
  return hasError ? fallback : children;
}
```

**It looks the same, but it is NOT the same thing!** Nothing ever calls `setHasError`, because React calls `getDerivedStateFromError` only on a class. The page still goes white.

So in practice there are two ways to add an Error Boundary:
1. **Write one class, and use it everywhere.** The docs: "write a single `ErrorBoundary` component like above and use it throughout your app." It fits a team that wants no extra package.
2. **Use the `react-error-boundary` package.** The docs: "you don't have to write the Error Boundary class yourself. For example, you can use `react-error-boundary` instead." It fits most apps.

A framework can also do it for you. In Next.js, an `error.js` file wraps a page in a boundary (Lesson 46). In this lesson we write the class ourselves, because it shows what every boundary does, including the one inside the package.

### What React does when the second comment throws

**React renders the boundary first with its children, and then again with its fallback.** No line of our code calls a setter, yet the boundary's state changes. Here is the order:
1. React renders `ErrorBoundary`. Its `hasError` is `false`, so it returns the children.
2. React renders the children, and the second `Comment` throws.
3. The error bubbles up to `ErrorBoundary`, and React calls `getDerivedStateFromError` with the error.
4. It returns `{ hasError: true }`, and React puts that into the boundary's state. The docs: "Update state so the next render will show the fallback UI."
5. React calls `render` again. Now it returns the fallback, and the broken children never reach the screen.

```tree dir=right caption="How ErrorBoundary switches from its children to its fallback when a child throws during rendering."
`ErrorBoundary` when the second `Comment` throws
- +1. First render [`hasError: false`] | `render` returns **`this.props.children`** | React renders the comments, and **one throws**
- +2. React calls `getDerivedStateFromError` | It returns **`hasError: true`** | React puts it into **the boundary's state**
- +3. Second render [`hasError: true`] | `render` returns **`this.props.fallback`** | The user sees **Comments are unavailable.**
```

A `console.log` inside `render` prints these steps more than once. After the error, React runs the whole render of the page a second time before it shows anything. In development, Strict Mode also calls `render` twice each time.

One more rule: `getDerivedStateFromError` must stay a pure function (Lesson 14). It only returns new state. Reporting the error is the job of another method, in Principle 5.

## PRINCIPLE | `<ErrorBoundary>` placement: it replaces only what sits inside it

> [!PRINCIPLE]
> **Principle 4: Placement: The Closest Boundary Decides What the User Keeps**
>
> *An Error Boundary replaces only what sits inside it; place it around the part of the page where a fallback message makes sense to the user, such as the comments list or each comment, not around every small piece.*
>
> The error bubbles up to the closest boundary above the broken component. That boundary replaces its own children with its fallback, and everything outside it stays. Around the whole app, the user loses the article. Around each comment, the user loses only the broken comment.
>
> **DO THIS:**
> ```jsx
> {comments.map(comment => (
>   <ErrorBoundary ~key={comment.id}~ fallback={<li>This comment could not be shown.</li>}> {/* Only the broken comment is replaced */}
>     <Comment comment={comment} />
>   </ErrorBoundary>
> ))}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> createRoot(root).render(
>   ~<ErrorBoundary fallback={<p>Something went wrong.</p>}>~ {/* **WRONG:** the only boundary, so one broken comment still removes the whole article */}
>     <App />
>   </ErrorBoundary>
> );
> ```

Remember the one sentence of this lesson: the error travels up to the closest Error Boundary, and that boundary replaces only what sits inside it. So the same boundary, with the same broken comment, gives three different pages, depending on where we put it.

### Around the whole app

The first place a developer tries is the top, in the entry file:

```jsx title="src/main.jsx, with the boundary around the whole app"
import { createRoot } from 'react-dom/client';
import App from './App.jsx';
import ErrorBoundary from './ErrorBoundary.jsx';

createRoot(document.getElementById('root')).render(
  ~<ErrorBoundary fallback={<p>Something went wrong.</p>}>~ {/* Replaces everything App renders */}
    <App />
  </ErrorBoundary>
);
```

```page url=news.example/city-park caption="The page with one boundary around the whole app: the white page becomes one line, and the article is still gone."
line: Something went wrong. | bad
```

The white page became one line. But the user still cannot read the article.

### Around the comments list

Next, the boundary goes inside `App`, around the list. `App` first imports it:

```jsx title="src/App.jsx" startLine="1"
import Comment from './Comment.jsx';
~import ErrorBoundary from './ErrorBoundary.jsx';~ // The class from Principle 3
```

Then the boundary wraps the list:

```jsx title="src/App.jsx, with the boundary around the comments list" startLine="12"
      <h1>City park opens on Saturday</h1>
      <h2>Comments</h2>
      ~<ErrorBoundary fallback={<p>Comments are unavailable.</p>}>~ {/* Replaces only the list */}
        <ul>
          {comments.map(comment => (
            <Comment key={comment.id} comment={comment} />
          ))}
        </ul>
      </ErrorBoundary>
```

```page url=news.example/city-park caption="The page with a boundary around the comments list: the title and the heading stay, and John's comment is gone too."
heading: City park opens on Saturday
section: Comments
line: Comments are unavailable. | good
```

The article is back. But John's comment went away with the broken one, because both sit inside the same boundary.

### Around each comment

Last, one boundary for each comment:

```jsx title="src/App.jsx, with a boundary around each comment" startLine="14"
        <ul>
          {comments.map(comment => (
            <ErrorBoundary ~key={comment.id}~ fallback={<li>This comment could not be shown.</li>}> {/* The key moves to the outer tag */}
              <Comment comment={comment} />
            </ErrorBoundary>
          ))}
        </ul>
```

```page url=news.example/city-park caption="The page with a boundary around each comment: only the broken comment is replaced."
heading: City park opens on Saturday
section: Comments
line: John: Great news! | good
line: This comment could not be shown. | good
```

Two small details in this version:
1. **The `key` moves to `ErrorBoundary`.** The `key` goes on the outer tag that `map` returns (Lesson 18), and the outer tag is now the boundary.
2. **The fallback is an `<li>`.** The fallback sits inside the `<ul>`, in the place of a comment, so it must be a list item too.

**It is the same boundary, but NOT the same page!** The boundary replaces only its own children and leaves everything outside it alone:

```tree caption="The same broken comment with the same ErrorBoundary in three places, and what the user keeps in each."
Where we place `<ErrorBoundary>`
- !Around the whole app [`<ErrorBoundary><App /></ErrorBoundary>`] | Replaces **everything** | The user sees **Something went wrong.** and **no article**
- +Around the comments list [`<ErrorBoundary><ul>...</ul></ErrorBoundary>`] | Replaces **only the list** | The user keeps **the title**, and loses **John's comment** too
- +Around each comment [`<ErrorBoundary key={comment.id}>`] | Replaces **only the broken comment** | The user keeps **the title and John's comment**
```

### How to choose the place

The docs call this choice "the granularity of Error Boundaries". They ask you to "consider where it makes sense to display an error message." Their own example fits our page: "in a messaging app, it makes sense to place an Error Boundary around the list of conversations. It also makes sense to place one around every individual message. However, it wouldn't make sense to place a boundary around every avatar."

Our comments list and each comment are the same two choices. A boundary around the author's name alone would make no sense: the user cannot read half a comment.

A boundary around the whole app still has a use, as the last safety net: one line of text is better than a white page. It only must not be the only boundary.

## PRINCIPLE | `componentDidCatch`: the team gets the error, the user gets the fallback

> [!PRINCIPLE]
> **Principle 5: Reporting: `componentDidCatch` Tells the Team, the Fallback Tells the User**
>
> *`componentDidCatch` is the optional method React calls after a child throws during rendering, so the boundary can send the error and `info.componentStack` to an error reporting service; showing the fallback stays the job of `getDerivedStateFromError`.*
>
> The fallback hides the error from the user, so without a report the team never learns which comment broke. `componentDidCatch` may do side effects, such as a call to a server. `getDerivedStateFromError` must stay pure and only return new state.
>
> **DO THIS:**
> ```jsx
> ~componentDidCatch~(error, info) { // Side effects belong here: the team receives the error and where it happened
>   logErrorToMyService(error, info.componentStack);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> static getDerivedStateFromError(error) {
>   ~logErrorToMyService(error)~; // **WRONG:** a side effect in a method that must stay pure
>   return { hasError: true };
> }
> ```

Our page now shows one fallback line in place of the broken comment, and the user can read the article. That is good for the user. But the team never learns that a comment broke, so the bug stays forever. React gives the boundary a second method for that:

```jsx title="Two methods that receive the same error"
static ~getDerivedStateFromError~(error) { // Changes what the user sees
  return { hasError: true };
}

~componentDidCatch~(error, info) { // Tells the team what broke
  logErrorToMyService(error, info.componentStack);
}
```

### VS | `getDerivedStateFromError` vs. `componentDidCatch`: one changes the screen, the other reports

**They look alike, but they are NOT the same thing!** Both receive the same error. One changes what the user sees. The other tells the developer:
- **`getDerivedStateFromError`** is static, receives the error, and returns new state. It must stay pure, and a boundary needs it.
- **`componentDidCatch`** is not static, receives the error and an `info` object, and returns nothing. It may do side effects, such as a call to a server, and it is optional.

The docs draw the line between them: "`static getDerivedStateFromError` should be a pure function." For a side effect, such as a call to an analytics service, "you need to also implement `componentDidCatch`."

### What the team receives

React calls `componentDidCatch` when a child, even a distant one, throws during rendering. The docs give its purpose: "This lets you log that error to an error reporting service in production."

An error reporting service is an outside service that collects the errors that happen in your users' browsers, so the team can see them. `logErrorToMyService` is the docs' placeholder name for the call to that service.

The second argument, `info`, holds `componentStack`. The docs describe it as "a stack trace with the component that threw, as well as the names and source locations of all its parent components." For our page, it says that `Comment` threw, inside the boundary, inside `App`. So the team knows exactly which part of the page broke.

Something that can be tricky: "In production, the component names will be minified." The build shortens the names, often to one or two letters, so a production report is harder to read.

### Our boundary, with the report

`ErrorBoundary` gains one method:

```jsx title="src/ErrorBoundary.jsx" good="11,12,13"
import { Component } from 'react';
import { logErrorToMyService } from './errorService.js';

export default class ErrorBoundary extends Component {
  state = { hasError: false };

  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  ~componentDidCatch~(error, info) { // React calls it after a child throws during rendering
    logErrorToMyService(error, info.componentStack);
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback;
    }
    return this.props.children;
  }
}
```

In this lesson, the reporting file only logs a line to the Console. In a real app, this is the one place that sends the error to your service:

```js title="src/errorService.js"
export function logErrorToMyService(error, componentStack) {
  console.log('Reported:', ~error.message~); // A real app sends error and componentStack to its service here
}
```

The user still sees only the fallback:

```page url=news.example/city-park caption="The page after the report is added: the user sees the same fallback as before."
heading: City park opens on Saturday
section: Comments
line: John: Great news! | good
line: This comment could not be shown. | good
```

The Console tells the full story. React prints one error message: the error it caught, and two sentences that name the component that threw and the boundary that caught it. Then our report appears:

```devconsole width=full caption="The Console: one error message from React with the error the boundary caught, and then our report from componentDidCatch."
x TypeError: Cannot read properties of undefined (reading 'name') The above error occurred in the <Comment> component. React will try to recreate this component tree from scratch using the error boundary you provided, ErrorBoundary.
+ Reported: Cannot read properties of undefined (reading 'name') | errorService.js:2
```

Why is the error in the Console when the user sees a polite line? React 19 sends every error caught by an Error Boundary to `console.error`, so the developer still finds it.

### Two mistakes with the two methods

1. **The fallback set from `componentDidCatch`.** Older class code calls `setState` inside `componentDidCatch` to turn on the fallback. The docs: "This is deprecated in favor of defining `static getDerivedStateFromError`."
2. **A report sent from `getDerivedStateFromError`.** That method must stay pure. The call to the service belongs in `componentDidCatch`.

### Reporting errors for the whole app

For the interview, know one more place to report errors. `createRoot` accepts three options for this (Lesson 7):
1. **`onCaughtError`** is "called when React catches an error in an Error Boundary."
2. **`onUncaughtError`** is "called when an error is thrown and not caught by an Error Boundary."
3. **`onRecoverableError`** is "called when React automatically recovers from errors."

Each one receives the error and an `errorInfo` object with `componentStack`. They report errors for the whole app, but they do not keep the page on the screen. Only an Error Boundary shows a fallback.

Without these options, React 19 sends the errors no boundary caught to `window.reportError`. That is the browser function that printed the "Uncaught" line in Principle 1.

## PRINCIPLE | `onClick`: an error in a click handler skips the boundary, so the handler needs its own `try` and `catch`

> [!PRINCIPLE]
> **Principle 6: Event Handlers: A Click Error Never Reaches the Boundary**
>
> *An Error Boundary catches only errors thrown while React renders its children; errors in event handlers, in asynchronous code such as `setTimeout`, in the boundary itself, and during server side rendering are not caught; an error thrown inside `startTransition` from `useTransition` is caught.*
>
> A click handler runs when the user clicks, not while React renders. So when it throws, React never calls `getDerivedStateFromError`, and the page stays as it was, with the error only in the Console. Inside a handler, `try` and `catch` work, because the handler's own code runs inside the `try`.
>
> **DO THIS:**
> ```jsx
> function handleReply() {
>   ~try~ { // The handler catches its own error and tells the user
>     setNotice('Replying to ' + comment.author.name);
>   } catch (error) {
>     setNotice('You cannot reply to this comment.');
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleReply() {
>   setNotice('Replying to ' + ~comment.author.name~); // **WRONG:** throws after the click, and the boundary around Comment never sees it
> }
> ```

Suppose each comment gets a `Reply` button. Here are two places in `Comment` that read the same broken name. Both sit inside the same `ErrorBoundary`:

```jsx title="The same broken read, while rendering and in a click handler"
<li>{~comment.author.name~}: {comment.text}</li> {/* Throws while React renders: the boundary shows its fallback */}
<button onClick={() => setNotice('Replying to ' + ~comment.author.name~)}>Reply</button> {/* Throws when the user clicks: the boundary does nothing */}
```

**It looks the same, but it is NOT the same thing!** Both throw the same `TypeError`, from code written inside the boundary. But a boundary catches only errors thrown while React renders its children. A click handler runs later, when the user clicks (Lesson 11). At that moment React is not rendering anything, so the boundary never hears about the error.

### The user clicks Reply, and nothing happens

To see the click on its own, this version of `Comment` shows only the text, so rendering reads no author. The `Reply` button reads the name only when the user clicks it:

```jsx title="src/Comment.jsx, with a Reply button"
import { useState } from 'react';

export default function Comment({ comment }) {
  const [notice, setNotice] = useState('');

  function handleReply() {
    setNotice('Replying to ' + ~comment.author.name~); // Throws only when the user clicks Reply on comment 2
  }

  return (
    <li>
      {comment.text} <button onClick={handleReply}>Reply</button>
      {notice && <p>{notice}</p>}
    </li>
  );
}
```

The page opens with both comments. The user clicks `Reply` on the second comment:


**The user clicks, and nothing happens.** There is no fallback and no message on the page. Here is why:
1. The user clicks `Reply` on the second comment.
2. The browser event reaches `handleReply`, and the handler throws.
3. No render is running, so React does not call `getDerivedStateFromError`.
4. The comments stay on the screen as they were, with no fallback.
5. The error appears only in the Console.

A developer who expected the fallback now searches for a bug in the boundary. The boundary works. The docs simply leave event handlers out.

### The fix inside a handler: `try` and `catch`

Inside an event handler, your code really runs inside the `try` block. So plain `try` and `catch` work again:

```jsx title="src/Comment.jsx, handleReply with try and catch" startLine="6"
  function handleReply() {
    ~try~ { // The handler's own code runs inside the try, so the catch can see its error
      setNotice('Replying to ' + comment.author.name);
    } catch (error) {
      setNotice('You cannot reply to this comment.');
    }
  }
```


This is the Rule of Thumb again: during rendering, an Error Boundary. In your own handler, `try` and `catch`.

### What an Error Boundary does not catch

The docs list four places where an Error Boundary catches nothing:
1. **Event handlers**, such as our `Reply` button.
2. **Asynchronous code**, such as callbacks of `setTimeout` or `requestAnimationFrame`. They run later, outside rendering, just like a click handler.
3. **Server side rendering**, which belongs to Part Two.
4. **Errors thrown in the boundary itself**, rather than in its children. Those go past it, to the next boundary above.

### One exception: `startTransition`

When the click starts a Transition (Lesson 67), the error does reach the boundary. The docs: "Errors thrown inside the transition function are caught by error boundaries."

```jsx title="The same broken read inside startTransition"
const [isPending, startTransition] = useTransition();

function handleReply() {
  ~startTransition~(() => { // An error thrown in here goes to the closest Error Boundary
    setNotice('Replying to ' + comment.author.name);
  });
}
```

Each comment has had its own boundary since Principle 4. So with this version, a click on the second `Reply` button shows the fallback line in place of that comment. The `useTransition` docs say it the same way: "Once the function passed to `startTransition` errors, the fallback for the error boundary will be displayed."

Form Actions follow the same path (Lessons 41 and 42). So does a rejected Promise read with `use` (Lesson 71).

```tree caption="Three errors thrown from code inside the same ErrorBoundary, and which of them the boundary catches."

- +While React renders `Comment` [`<li>{comment.author.name}</li>`] | Thrown **during rendering** | The boundary shows **its fallback**
- !In a plain click handler [`onClick`] | Thrown **after the user clicks**, outside rendering | The boundary **does nothing**: use **`try` and `catch`**
- +Inside `startTransition` in a click handler [`startTransition`] | React **sends the error** to the closest boundary | The boundary shows **its fallback**
```

### Where the error is caught, and what the user sees

| Situation | What the user sees | The React rule |
| :--- | :--- | :--- |
| **No Error Boundary, and a comment throws during rendering** | A white page with no message | React removes the whole UI of the root |
| **`try` and `catch` around the returned JSX** | The same white page | The child runs after the parent returns, so the `catch` never runs |
| **A function component with `useState` as the boundary** | The same white page | Only a class with `static getDerivedStateFromError` can catch |
| **One boundary around the whole app** | One line, and no article | A boundary replaces everything inside it |
| **A boundary around each comment** | The article, John's comment, and one fallback line | Only the children of the closest boundary are replaced |
| **`componentDidCatch` in the boundary** | The same fallback; the team gets a report | Side effects go in `componentDidCatch`, never in `getDerivedStateFromError` |
| **An error in a plain click handler** | Nothing changes; the error is only in the Console | Boundaries catch errors during rendering only; use `try` and `catch` in the handler |

Remember the one sentence of this lesson. **An error during rendering travels up to the closest Error Boundary above it. That boundary shows its fallback, and everything outside it stays on the screen.**

## For the Interview

> **The Interview Question:** How do you catch a rendering error before it unmounts the whole app?

### How to Answer Clearly in 30 Seconds

"By default, when a component throws during rendering, React removes the whole UI of the root, so one broken item of data turns the page white. A `try` and `catch` around the JSX cannot help. The parent only describes the child, and React calls the child after the parent has returned. The error bubbles up the component tree, and only an Error Boundary can catch it. An Error Boundary is a class component with `static getDerivedStateFromError`, which returns state that tells `render` to show a fallback instead of the children. Three rules:
1. **Place boundaries where a fallback makes sense to the user**, such as around a list of comments or around each comment, not only around the whole app.
2. **Add `componentDidCatch`** to send the error and its component stack to an error reporting service.
3. **Errors in event handlers and timers skip the boundary**, so I catch those with `try` and `catch`.

In most apps, I use the `react-error-boundary` package instead of writing the class myself."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why can't you write an Error Boundary as a function component?"**
   Because there is no Hook for it. React calls `getDerivedStateFromError` and `componentDidCatch` only on a class. The docs say: "There is no direct equivalent for `static getDerivedStateFromError` in function components yet." So a team writes one `ErrorBoundary` class and uses it everywhere, or uses the `react-error-boundary` package. The package also adds `fallbackRender` and `resetKeys`, which let the boundary try its children again, for example after the user presses a "Try again" button.
2. **"Does an Error Boundary catch an error thrown in a click handler?"**
   No. A boundary catches only errors thrown while React renders its children. A click handler runs later, when the user clicks, so its error goes past the boundary, and the page does not change. The same goes for asynchronous code such as `setTimeout`, for errors in the boundary itself, and for server side rendering. Inside a handler, we use `try` and `catch`. The exception is `startTransition` from `useTransition`: an error thrown inside the transition function goes to the closest Error Boundary. So does the error of a Form Action.
3. **"What is the difference between `getDerivedStateFromError` and `componentDidCatch`?"**
   Both receive the same error, but they do different jobs. `getDerivedStateFromError` is `static` and pure: it returns new state, such as `hasError: true`, so the next render shows the fallback. `componentDidCatch` receives the error and `info.componentStack`, and it may do side effects, such as sending a report to an error reporting service. Calling an analytics service inside `getDerivedStateFromError` breaks its purity. Calling `setState` inside `componentDidCatch` to show the fallback is deprecated.

```tree dir=right caption="Interview summary: what catches a rendering error, and what does not."
Catching an error thrown while React renders a child
- !`try` and `catch` around the returned JSX | The parent **has already returned** when the child throws | The page still goes **white**
- +An Error Boundary class [`getDerivedStateFromError`] | Catches the error that **bubbles up** from its children | Shows **its fallback**; the rest of the page **stays**
- +`componentDidCatch` in the same class | Receives the error and **`componentStack`** | Sends a **report** to the team
```
