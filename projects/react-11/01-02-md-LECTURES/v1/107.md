# Lecture 107: What a Server Component Can Pass to a Client Component

*(Why does a number reach the browser, while a function stops the whole page?)*

> INTERVIEW QUESTION | ❱ CORE | What can you pass from a Server Component to a Client Component?

---

## VS | A Number vs. a Function in a Prop: the number reaches the browser, the function stops the page

> A parent component can pass any value to a child through a prop, and the child receives it as it is. **When a Server Component passes a prop to a Client Component, React must write the prop down as text on the server and rebuild it in the browser.** So you can pass data, such as numbers, plain objects, and dates, but not a plain function, because a function is code, and no text can carry it.

Remember `JSON.stringify`? You use it in plain JavaScript every time you send data to a server with `fetch`. The object becomes a string of characters. The string travels over the network. On the other side, `JSON.parse` rebuilds the same object. Now try it with a function:

```js title="Plain JavaScript: what JSON.stringify keeps, and what it drops"
JSON.stringify({ likes: 12 }); // '{"likes":12}': the number travels as text
JSON.stringify({ likes: 12, ~onLike~: () => {} }); // '{"likes":12}': the function is silently gone
```

The number becomes the characters `12`, and the other side gets 12 back. The function becomes nothing at all. Why? Because a function is code, not data. There are no characters that could carry it to the other side and make it run there.

React meets the same problem between a Server Component and a Client Component. The Server Component runs on the server. The Client Component runs in the browser. So every prop on the tag of the Client Component must travel from one to the other. React writes each prop down on the server and rebuilds it in the browser. It uses its own format, which is not JSON and carries more than JSON can. And when it meets a function, React does not drop it silently. It throws an error, and the page does not render.

```jsx title="Two props from a Server Component to a Client Component"
<LikeButton ~initialLikes={12}~ /> {/* A number: React writes down 12, and the browser rebuilds 12 */}
<LikeButton ~onLike={() => db.posts.like(1)}~ /> {/* **WRONG:** a function: React throws, and the page does not render */}
```

So here is the one sentence to keep in mind for this whole lesson:

**Between a Server Component and a Client Component, send data, not code. Every prop must be serializable: React writes it down on the server and rebuilds it in the browser.**

> [!DEFINITION]
> **Server Component and Client Component.** [REVIEW] A Server Component runs on the server, before the page is sent, so it can read a database or a file directly, and the browser receives only what it rendered, never its code. A Client Component is a component whose code is sent to the browser and runs there, so it can use `useState` and `onClick`; its file starts with `'use client'` (Lesson 101).

> [!DEFINITION]
> **Serializable.** [NEW] To serialize a value is to write it out as a series of characters that can travel over the network, as `JSON.stringify` does; *serial* means one after another, like the episodes of a TV series. A value is serializable when React knows how to write it down on the server and rebuild the same value in the browser. React's docs give the rule in one sentence: prop values passed from a Server Component to a Client Component "must be serializable" (Lesson 107).

### The Same Line of Code, Two Different Trips

You passed a function as a prop before, in the guest list where each row has a Remove button (as seen in Lesson 23). Put that line next to a line from a blog post page:

```jsx title="A function passed as a prop: from GuestList, and from Post"
<GuestRow guest={guest} ~onRemove={handleRemove}~ /> {/* Both components run in the browser: the row calls handleRemove */}
<LikeButton initialLikes={post.likes} ~onLike={() => db.posts.like(1)}~ /> {/* **WRONG:** Post runs on the server, so React throws */}
```

**It looks the same, but it is NOT the same thing!** Both lines pass a function. The difference is where the two components run:
- **In the guest list**, the list and the row both run in the browser. The function never leaves the browser. The row receives it and calls it.
- **On the post page**, `Post` is a Server Component and `LikeButton` is a Client Component. Every prop on the `LikeButton` tag must travel from the server to the browser. The number makes the trip. The function cannot.

### What Crosses, and What Does Not

The list of what crosses is longer than most developers expect. React's docs list these serializable values:
1. **Primitives.** A primitive is a single plain value: a string, a number, a boolean, `null`, or `undefined`. A `bigint` counts too, and so does a symbol made with `Symbol.for`.
2. **Arrays**, and the built-in collections `Map` and `Set`. The binary types `TypedArray` and `ArrayBuffer` cross too.
3. **`Date`.** It arrives in the browser as a real date, not as a string. `JSON.stringify` cannot do this.
4. **Plain objects.** A plain object is an object written with curly braces, such as `{ likes: 12 }`, whose fields are all serializable. React's docs call this way of writing an object an "object initializer".
5. **JSX.** React's docs say "Client or Server Component elements". This is why a Server Component can place JSX between the tags of a Client Component, as its `children` (as seen in Lesson 106).
6. **Promises.** A Server Component can pass a Promise that has not finished yet, and the Client Component reads it with `use` (as seen in Lesson 71). The value the Promise brings must be serializable too.
7. **Server Functions.** A Server Function is a function marked with `'use server'`. It is the one kind of function that crosses, and it crosses as a reference. Principle 3 shows it.

And these values do not cross:
1. **Functions**, unless they are Server Functions, or are exported from a `'use client'` file.
2. **Classes.**
3. **Objects that are instances of a class**, other than the built-ins above. Principle 4 shows what an instance is. An object with a null prototype, a rare kind of object made with `Object.create`, does not cross either.
4. **Symbols not made with `Symbol.for`**, such as a symbol made with plain `Symbol`.

```tree caption="What React can write down on the server and rebuild in the browser, and what it cannot."
What a Server Component can pass to a Client Component
- +Crosses: data [`12` `'Park Opens Today'` `{ likes: 12 }` `[1, 2]`] | Primitives, arrays, **plain objects**, `Date`, `Map`, `Set` | Also **JSX**, **Promises**, and **Server Functions**
- !Does not cross: code, and objects built by a class [`function` `class`] | **Plain functions** and **classes** | **Instances of a class** other than the built-ins, and symbols not made with `Symbol.for`
```

### What the Wrong Prop Costs

What the reader of the blog gets depends on what you put in the prop:
1. **A plain function.** The post page does not render at all. React throws an error about event handlers, although `LikeButton` itself has no mistake in it.
2. **The whole post from the database, built by a class.** The page does not render either.
3. **The whole post as a plain object.** The page renders with no error at all. And every field of the post, such as the email address of the author, reaches every reader's browser.

The third case is the dangerous one, because nothing on the screen tells you.

### The Rule of Thumb: is it data, or is it code?

**Before you put a value on the tag of a Client Component, ask one question: is it data, or is it code? Data crosses. A plain function does not.**

When the Client Component needs something that is a function on the server, there are three ways out:
1. **Call the function on the server, and pass its result**, a number or a string. This fits a function that only computes something to show.
2. **Move the function into the file of the Client Component**, or into a file it imports. Then it is client code from the start (as seen in Lesson 106). This fits a function about what happens in the browser, such as adding one to the count.
3. **Mark the function with `'use server'`.** It becomes a Server Function. The browser gets a reference to it, and a call from the browser sends a request to the server. This fits a click that must change data on the server, such as saving a like.

A senior developer also knows the five classic mistakes:
1. **Passing a function down as in the guest list**, because the code looks the same.
2. **Reading "serializable" as "anything that is not a function"**, and passing an object that a class built.
3. **Removing the method from that class**, and expecting the object to cross. It still fails, because the class itself is the problem.
4. **Passing the whole post to save typing.** Fields the page never shows reach the browser.
5. **Turning a date into a string before passing it**, as you would for JSON. React's docs list `Date` as serializable.

The rest of the lesson shows each mistake on a real blog post page.

## SECTION | The Blog Post with a Like Button

Open the blog post again (as seen in Lesson 101). The page shows the title, `Park Opens Today`, and under it a `Like` button with its count. This time the count does not start at zero. Twelve readers liked the post before you, so the page shows `12 likes`.

```page width=text caption="The blog post page with the like count read from the database, before the tap."
heading: Park Opens Today
line: 12 likes [Like]
```

The user taps `Like` once, and the page shows `13 likes`:

```page width=text caption="The same page after the user taps Like once."
heading: Park Opens Today
line: 13 likes [Like] | good
```

The number 12 lives in the database, on the server. So two components share the work:
1. **`Post` is a Server Component.** It reads the post from the database and shows the title.
2. **`LikeButton` is a Client Component.** It shows the count and answers the taps. `Post` hands it the count through a prop.

```files title="blog: the post page with a database" caption="The three files of our post page: the database stand-in, one Server Component, and one Client Component."
src/
  db.js | stand-in | Plays the database: `db.posts.get(id)` returns one post
  Post.jsx | Server Component | Reads the post and renders `LikeButton`
  LikeButton.jsx | Client Component | Starts with `'use client'` and counts the likes
```

The database file is a stand-in: a small file that plays the part of the database, so our page needs no real database server. React's docs do the same when they write `db.notes.get(id)` without showing the database behind it. To keep the page small, the post holds only its title and its likes.

Again, the one sentence of this lesson: **between a Server Component and a Client Component, send data, not code.**

**PRINCIPLES:** A Server Component can pass props to a Client Component, but only values React can write down on the server and rebuild in the browser. Four principles follow:
1. **Principle 1: A number crosses as a number.** `LikeButton` receives `initialLikes` exactly as it would from a client parent. Dates, plain objects, arrays, JSX, and Promises cross the same way.
2. **Principle 2: A plain function stops the whole page.** React throws while the server renders `Post`, and the reader gets no page at all.
3. **Principle 3: A Server Function crosses as a reference.** The code stays on the server, and a call from the browser sends a request to run it.
4. **Principle 4: Pass only the fields the button uses.** A class instance stops the page. A plain copy of the whole post sends every field to the browser.

## PRINCIPLE | `initialLikes={post.likes}`: `LikeButton` receives the same number as from any parent

> [!PRINCIPLE]
> **Principle 1: Serializable Props: A Number Crosses as a Number**
>
> *A Server Component can pass a Client Component any value React can write down on the server and rebuild in the browser: primitives, arrays, plain objects, `Date`, `Map`, `Set`, JSX, Promises, and Server Functions.*
>
> `Post` runs on the server and `LikeButton` runs in the browser, so every prop on the tag travels from one to the other. A number makes the trip easily, and `LikeButton` receives the same 12 it would get from a client parent. The list is longer than most developers expect, so there is no need to turn a date or an object into a string first.
>
> **DO THIS:**
> ```jsx
> <LikeButton ~initialLikes={post.likes}~ /> // A number crosses as a number
> <PublishedDate ~publishedAt={post.publishedAt}~ /> // A Date crosses as a Date
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <PublishedDate ~publishedAt={post.publishedAt.toISOString()}~ /> // **WRONG:** a Date already crosses; the string only forces a new Date back in the browser
> ```

### VS | A Server Parent vs. a Client Parent: `LikeButton` receives the same 12

Here is the smallest prop that crosses: the number 12. First a Server Component passes it, then a Client Component:

```jsx title="Post.jsx: a Server Component passes 12"
export default async function Post() {
  return <LikeButton ~initialLikes={12}~ />; // LikeButton receives the number 12
}
```

```jsx title="Page.jsx: a Client Component passes 12"
'use client';

export default function Page() {
  return <LikeButton ~initialLikes={12}~ />; // LikeButton receives the number 12
}
```

**Yes, for `LikeButton` it is the exact same thing!** In both cases, `initialLikes` holds the number 12. `LikeButton` reads it from its props object, as always (as seen in Lesson 08). Nothing in `LikeButton` changes.

What changes is the trip the number takes. With the client parent, both components run in the browser, so the number never moves. With `Post`, the parent runs on the server and the child runs in the browser. React's docs call these two places two **environments**: "As they are rendered in different environments, passing data from a Server Component to a Client Component requires extra consideration." Between two environments, React writes the number down on the server and rebuilds it in the browser. That is what serializable means.

### The First Version of the Post Page

The database file holds one post and returns it from `db.posts.get`:

```js title="src/db.js" startLine="1"
const rows = {
  1: { title: 'Park Opens Today', likes: 12 },
};

export const db = {
  posts: {
    async ~get~(id) { // Returns the post with this id, as a database would
      return rows[id];
    },
  },
};
```

`Post` is an async Server Component (as seen in Lesson 101). It awaits the post, shows the title, and passes the count on the `LikeButton` tag:

```jsx title="src/Post.jsx" startLine="1"
import { db } from './db';
import LikeButton from './LikeButton';

export default async function Post() {
  const post = await db.posts.get(1);
  return (
    <article>
      <h1>{post.title}</h1>
      <LikeButton ~initialLikes={post.likes}~ /> {/* A number: React writes down 12 */}
    </article>
  );
}
```

`LikeButton` starts its state at `initialLikes`, not at zero. The name follows React's docs, whose own `Counter` receives its starting value from a Server Component as `initialValue`:

```jsx title="src/LikeButton.jsx" startLine="1"
'use client';

import { useState } from 'react';

export default function LikeButton({ initialLikes }) {
  const [likes, setLikes] = useState(~initialLikes~); // The state starts at 12
  return (
    <>
      <span>{likes} likes</span>
      <button onClick={() => setLikes(likes + 1)}>Like</button>
    </>
  );
}
```

The page opens on `12 likes`, the number from the database:

```page width=text caption="The post page with the count passed from Post, before the tap."
heading: Park Opens Today
line: 12 likes [Like]
```

Each tap by the user adds one in the browser, as before:

```page width=text caption="The same page after the user taps Like once."
heading: Park Opens Today
line: 13 likes [Like] | good
```

### VS | A Date vs. the Same Date as a String: both cross, the string is extra work

Many developers learned with JSON that a date must travel as a string. So they convert it by hand. Suppose a page shows when a post was published:

```jsx title="Passing a date, and passing the same date turned into a string"
<PublishedDate ~publishedAt={post.publishedAt}~ /> {/* A Date: crosses as a Date */}
<PublishedDate ~publishedAt={post.publishedAt.toISOString()}~ /> {/* A string: crosses too, then needs new Date back in the browser */}
```

Both lines work. But the conversion was never needed. With JSON, a date really does arrive as a string. With React, it arrives as a real `Date`, because React's docs list `Date` as serializable. The developer wrote two extra steps, one on each side, to solve a problem that does not exist. Lesson 135 shows in depth how dates, `Map`, and `Set` cross.

Remember: data crosses, and the Client Component receives it as from any parent.

## PRINCIPLE | `onLike` with a plain function: React throws, and the whole post page does not render

> [!PRINCIPLE]
> **Principle 2: Functions Across the Boundary: A Plain Function Stops the Whole Page**
>
> *A plain function cannot cross from a Server Component to a Client Component; React throws while the server renders, and the whole page fails, not only the Client Component.*
>
> A function is code, and the function in `Post` reaches the database on the server. React has nothing to write down that the browser could run, so it throws while `Post` renders. The fix is one of the three ways out: call the function on the server, move it into client code, or mark it `'use server'`.
>
> **DO THIS:**
> ```jsx
> <LikeButton ~likesText={formatLikes(post.likes)}~ /> // Calls the function on the server, and passes the string
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <LikeButton ~onLike={() => db.posts.like(1)}~ /> // **WRONG:** a plain function, so the post page does not render
> ```

### Saving Each Like on the Server

So far, a tap on `Like` changes only the count in this browser. When the user reloads the page, it shows `12 likes` again, because nothing told the database. The developer wants each tap saved.

First, the database file gets a second function, `like`, which adds one like to the post:

```js title="src/db.js" startLine="5"
export const db = {
  posts: {
    async get(id) {
      return rows[id];
    },
    async ~like~(id) { // Saves one more like for this post
      rows[id].likes += 1;
    },
  },
};
```

The saving code must reach `db`, and the post file already imports `db`. So the developer writes the function there, and passes it down as `onLike`, the way the guest list passed `onRemove`:

```jsx title="src/Post.jsx" startLine="4"
export default async function Post() {
  const post = await db.posts.get(1);
  return (
    <article>
      <h1>{post.title}</h1>
      <LikeButton
        initialLikes={post.likes}
        ~onLike={() => db.posts.like(1)}~ // **WRONG:** a plain function cannot cross to the browser
      />
    </article>
  );
}
```

`LikeButton` takes `onLike`, and calls it after it adds one to the count:

```jsx title="src/LikeButton.jsx" startLine="5"
export default function LikeButton({ initialLikes, onLike }) {
  const [likes, setLikes] = useState(initialLikes);
  return (
    <>
      <span>{likes} likes</span>
      <button onClick={() => { setLikes(likes + 1); ~onLike()~; }}>Like</button> {/* Shows the new count, then saves it */}
    </>
  );
}
```

### Why the Page Stops

**The post page does not render at all, although `LikeButton` has no mistake in it.** The error comes from sending the prop to the browser, not from the button. Here is what happens, in order:
1. The framework calls `Post` on the server. `Post` reads the post and reaches the `LikeButton` tag.
2. To send the props to the browser, React must write each one down.
3. `initialLikes` is a number, so React writes down `12`.
4. `onLike` is a plain function, not a Server Function. React has nothing to write down, so it stops and throws an error.
5. The error comes while `Post` renders, so the whole page fails, not only the button.

This is the error React throws:

```text title="The error React throws while the server renders Post"
Event handlers cannot be passed to Client Component props.
  <... initialLikes={12} onLike={function onLike}>
                                ^^^^^^^^^^^^^^^^^
If you need interactivity, consider converting part of this to a Client Component.
```

The two middle lines show the props of the `LikeButton` tag. The marks under `onLike` point at the prop that cannot cross. React's docs say the same rule in plain words: "event handlers like `onClick` can only be defined in Client Components."

### VS | `onLike` vs. `save`: the same mistake, two messages

React picks the message by the name of the prop. A name that starts with `on` and a capital letter, such as `onLike`, looks like an event handler, so React says "Event handlers". Rename the same prop to `save`, and React throws a different message:

```jsx title="The same function under two prop names"
<LikeButton ~onLike={() => db.posts.like(1)}~ /> {/* "Event handlers cannot be passed to Client Component props." */}
<LikeButton ~save={() => db.posts.like(1)}~ /> {/* "Functions cannot be passed directly to Client Components..." */}
```

```text title="The error React throws for a function under any other prop name"
Functions cannot be passed directly to Client Components unless you explicitly expose it by marking it with "use server". Or maybe you meant to call this function rather than return it.
  <... initialLikes={12} save={function save}>
                              ^^^^^^^^^^^^^^^
```

The two messages read differently, but the mistake is the exact same one: a plain function in a prop that crosses. Both stop the page. And the second message already names two of the three ways out: mark the function with `'use server'`, or call the function.

### VS | Passing `formatLikes` vs. Passing What `formatLikes` Returns: only the result crosses

"Or maybe you meant to call this function" points at a very common slip. Suppose the post file has a small helper, `formatLikes`, that turns the number 12 into the text `12 likes`. Look at these two tags:

```jsx title="Passing the helper vs. passing what the helper returns"
<LikeButton ~likesText={formatLikes}~ /> {/* **WRONG:** passes the function itself, and the page stops */}
<LikeButton ~likesText={formatLikes(post.likes)}~ /> {/* Calls it on the server, and passes the string "12 likes" */}
```

**They look almost the same, but they are NOT the same thing!** The only difference is the pair of round brackets after `formatLikes`. Without them, the prop holds the function, which cannot cross. With them, `formatLikes` runs on the server, and the prop holds a string, which crosses. This is the first way out: call the function on the server, and pass its result.

### The Quick Fix That Makes Things Worse

When the error appears, one fix looks fast: add `'use client'` to the post file. Then both components run in the browser, as the guest list and its rows did.

```jsx title="src/Post.jsx" startLine="1"
~'use client';~ // **WRONG:** Post and everything it imports become client code, db.js included
import { db } from './db';
import LikeButton from './LikeButton';
```

This trades one problem for a bigger one. `'use client'` marks the file and everything it imports as client code (as seen in Lesson 106). So `Post` is no longer a Server Component, and the page still does not render. Why? Well, `Post` is an async function, and React runs async components only on the server. In the browser, React stops at `Post` and prints this error in the Console:

```text title="The error React prints when Post.jsx starts with use client"
<Post> is an async Client Component. Only Server Components can be async at the moment. This error is often caused by accidentally adding `'use client'` to a module that was originally written for the server.
```

And the database file becomes client code too, pulled into the bundle that the browser downloads. The page has lost the very reason for a Server Component: a component that reads its data on the server (as seen in Lesson 101). The real fix is the one the second error message names: mark the function with `'use server'`.

## PRINCIPLE | `'use server'`: the function stays on the server, and the browser gets a reference to call it

> [!PRINCIPLE]
> **Principle 3: Server Functions: A Function Marked `'use server'` Crosses as a Reference**
>
> *When a click must change data on the server, mark the function with `'use server'`; React passes the browser a reference to it, and a call from the browser sends a request to run it on the server.*
>
> A plain function cannot cross, but saving a like must run on the server, where the database is. A Server Function solves this. Its code never leaves the server. The browser receives only a reference that names it, and calling that reference asks the server to run the code.
>
> **DO THIS:**
> ```jsx
> async function likePost() {
>   ~'use server'~; // A Server Function: crosses as a reference
>   await db.posts.like(1);
> }
> <LikeButton initialLikes={post.likes} onLike={likePost} />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <LikeButton
>   initialLikes={post.likes}
>   ~onLike={() => db.posts.like(1)}~ // **WRONG:** a plain function, so the post page does not render
> />
> ```

### Which Way Out Fits Each Function

Each of the three ways out fits a different kind of function:

```tree caption="Three ways to give a Client Component what a plain function would have given it."
A Client Component needs something that is a function on the server
- +1. Call it on the server and pass the result [`likesText="12 likes"`] | Fits a function that **only computes something to show** | The prop holds a **string or a number**, which crosses
- +2. Move it into client code [`setLikes` in `LikeButton.jsx`] | Fits a function about **what happens in the browser** | It is **client code** from the start, so it never crosses
- +3. Mark it `'use server'` [`likePost`] | Fits a click that must **change data on the server** | React passes a **reference**, and a call **sends a request to the server**
```

Our button already uses the second way. Adding one to the count lives in the button file, and `Post` never passes it down. Saving the like is different. It must run on the server, where `db` lives. So our button needs the third way.

> [!DEFINITION]
> **Server Function.** [NEW] A Server Function is an async function marked with the directive `'use server'` that runs on the server, but that the browser can call. React's docs: "Server Functions allow Client Components to call async functions executed on the server." When a Server Component passes one as a prop, the browser receives a reference to it, not its code (Lesson 107).

### A Server Function Inside `Post`

We write the Server Function inside `Post`, in the same shape as React's own example in its docs:

```jsx title="src/Post.jsx" startLine="4"
export default async function Post() {
  const post = await db.posts.get(1);

  async function likePost() {
    ~'use server'~; // Marks likePost as a Server Function
    await db.posts.like(1);
  }

  return (
    <article>
      <h1>{post.title}</h1>
      <LikeButton initialLikes={post.likes} ~onLike={likePost}~ /> {/* Crosses as a reference to likePost */}
    </article>
  );
}
```

The button file does not change. It still calls `onLike` after `setLikes`.

### What the Browser Receives: a Reference, Not the Code

In the browser, `onLike` does not hold the code of `likePost`. It holds a reference to it. React's docs: "your framework will automatically create a reference to the Server Function, and pass that reference to the Client Component." A **reference** is a small value that names the Server Function, so the browser can ask the server to run it. Think of the URL you pass to `fetch`. The browser does not have the code behind that URL. It only knows where to send the request. The code of `likePost`, with `db` inside it, stays on the server.

**When the user taps `Like`, the count changes in the browser, and the like is saved on the server.** Here is the path of one tap:
1. `LikeButton` calls `setLikes`, and the page shows 13 likes.
2. Then it calls `onLike`, which holds the reference to `likePost`.
3. React sends a request to the server to run `likePost`.
4. On the server, `likePost` calls `db.posts.like`, and the database saves the like.

```page width=text caption="The post page after the user taps Like once: the count changed in the browser, and likePost saved the like on the server."
heading: Park Opens Today
line: 13 likes [Like] | good
```

Now the user reloads the page, and it shows `13 likes`, because the database has it. React's docs add that a Server Function should be called inside a Transition. Lesson 110 shows that way of calling it, and teaches Server Functions in full. Here we keep the simple shape of React's own example.

Remember: a plain function is code, and it stays where it is. A Server Function also stays on the server, but the browser gets a way to call it.

## PRINCIPLE | `post.likes`, not `post`: nothing else from the database row reaches the browser

> [!PRINCIPLE]
> **Principle 4: Shape the Props: Pass Only the Fields the Client Component Uses**
>
> *Pass a Client Component only the fields it uses, as primitives or a small plain object; an instance of a class does not cross at all, and a plain copy of a database row crosses with every field in it.*
>
> An object built by a class stops the page, even when the class has no methods, because React checks what built the object. A plain copy of the same row crosses without any message, and every field in it, such as the email of the author, reaches the browser. The props of a Client Component are the data the browser receives, so pick only the fields the component uses.
>
> **DO THIS:**
> ```jsx
> <LikeButton ~initialLikes={post.likes}~ onLike={likePost} /> // Only the number 12 reaches the browser
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <LikeButton ~post={{ ...post }}~ onLike={likePost} /> // **WRONG:** authorEmail reaches every reader's browser
> ```

### The Post from the Database Is an Instance of a Class

Remember classes in JavaScript? A class is a template for creating objects. `new Date()` builds an object from the class `Date`. That object is an **instance** of the class. An instance can use the methods of its class, such as `getFullYear`.

`Date` is a built-in class, and React's list allows it. A class that you or your database library writes is not on the list. And some database code builds each post with such a class, instead of returning a plain object.

Our row in the database also holds a field the page never shows: the email address of the author.

```js title="src/db.js" startLine="1"
class ~PostRow~ { // A template for every post the database returns
  constructor(row) {
    this.title = row.title;
    this.likes = row.likes;
    this.authorEmail = row.authorEmail;
  }
  isNew() {
    return this.likes < 5;
  }
}

const rows = {
  1: { title: 'Park Opens Today', likes: 12, authorEmail: 'john@example.com' },
};
```

`db.posts.get` now returns an instance of `PostRow`, instead of the plain row:

```js title="src/db.js" startLine="16"
export const db = {
  posts: {
    async get(id) {
      return ~new PostRow(rows[id])~; // An instance of PostRow, with authorEmail inside
    },
    async like(id) {
      rows[id].likes += 1;
    },
  },
};
```

### Passing the Whole Post: `post={post}`

`LikeButton` needs the count today. Maybe it will need the title tomorrow. To save typing, the developer passes the whole post:

```jsx title="src/Post.jsx" startLine="15"
<LikeButton ~post={post}~ onLike={likePost} /> {/* **WRONG:** an instance of PostRow, so the post page does not render */}
```

`LikeButton` would then start its state at `post.likes`. But React stops before `LikeButton` ever runs. The post page fails again, now with a different error:

```text title="The error React throws for an object built by a class"
Only plain objects, and a few built-ins, can be passed to Client Components from Server Components. Classes or null prototypes are not supported.
  <... post={{title: ..., likes: 12, authorEmail: ...}} onLike=...>
            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
```

### VS | `PostRow` with `isNew` vs. `PostRow` without `isNew`: both stop the page

A developer who read "functions cannot cross" sees the method `isNew`, and blames it. So they delete `isNew` from the class:

```js title="PostRow with isNew, and PostRow without it"
class ~PostRow~ { constructor(row) { this.likes = row.likes; } isNew() { return this.likes < 5; } } // With isNew: an instance of a class, and the page stops
class ~PostRow~ { constructor(row) { this.likes = row.likes; } } // Without isNew: still an instance of a class, and the page still stops
```

**Yes, for React it is the exact same thing!** Both versions build an instance of a class, and both stop the page with the same error. React does not look at what sits inside the object. It looks at what built the object. React's docs forbid "Objects that are instances of any class" other than the built-ins in the list. So a class with no methods at all fails too.

### VS | The Instance vs. a Plain Copy `{ ...post }`: the copy crosses with every field

Next, the developer copies the fields into a plain object with the three dots (as seen in Lesson 09):

```jsx title="src/Post.jsx" startLine="15"
<LikeButton ~post={{ ...post }}~ onLike={likePost} /> {/* A plain object: no error, and authorEmail goes to the browser */}
```

**Beware: the error is gone, but the email address now reaches every reader's browser.** The page shows `12 likes` with no message of any kind. Here is why:
1. The three dots copy the fields the instance holds itself: the title, the likes, and `authorEmail`. The method `isNew` belongs to the class, not to the instance, so it stays behind.
2. The copy is a plain object. All three fields are strings and numbers, so React writes all of them down.
3. The browser rebuilds the whole object for `LikeButton`. `LikeButton` shows only the likes, but `post.authorEmail` has arrived in the browser too.

**The instance and the plain copy hold the very same fields, but they are NOT the same thing!** The instance stops the page with an error. The plain copy crosses with no error, and with every field in it. React's docs warn about exactly this: "A Client Component should never accept objects that carry sensitive data." **Sensitive data** is any field the reader of the page must not get, such as the email of the author. React's docs mark the same shape, a whole `user` row passed to a Client Component, with "DO NOT DO THIS".

Something that can be tricky: a plain object crosses only when every field in it is serializable. A plain object with a method inside, such as `isNew`, stops the page with the "Functions cannot be passed directly" message of Principle 2.

### Pass Only What the Button Uses

The fix is to pass only the field `LikeButton` uses, the count, as a number. React's docs give the same advice: "pick off the specific properties you need for this use case."

```jsx title="src/Post.jsx" startLine="15"
<LikeButton ~initialLikes={post.likes}~ onLike={likePost} /> {/* Only the number 12 crosses */}
```

```page width=text caption="The post page with only the count passed to LikeButton: the same screen, and no email in the browser."
heading: Park Opens Today
line: 12 likes [Like]
```

The screen looks the same as with the plain copy. The difference is what the browser received: one number, and nothing else from the row.

```tree caption="Three ways to pass the post from the database to LikeButton, and what each one sends to the browser."
Passing the post from `Post` to `LikeButton`
- !The instance [`post={post}`] | Built by the class `PostRow` | The page **does not render**: only plain objects can be passed
- !A plain copy of the whole row [`post={{ ...post }}`] | Crosses **with no error** | `authorEmail` reaches **every reader's browser**
- +Only the field the button uses [`initialLikes={post.likes}`] | One **number** crosses | The browser gets **12**, and nothing else from the row
```

Remember: the props of a Client Component are exactly what the browser receives. Send the data the button needs, and nothing more.

## All 4 Principles Together

### The complete code

Here is the finished post page: the database stand-in, one Server Component, and one Client Component.

```files title="blog: the finished post page" caption="The finished post page: the database stand-in, one Server Component, and one Client Component."
src/
  db.js | stand-in | Builds each post with `PostRow` and saves likes with `db.posts.like`
  Post.jsx | Server Component | Reads the post, defines the Server Function `likePost`, and passes `initialLikes` and `onLike`
  LikeButton.jsx | Client Component | Starts with `'use client'`, counts the likes, and calls `onLike`
```

  constructor(row) {

```jsx title="src/Post.jsx" startLine="1"
import { db } from './db';
import LikeButton from './LikeButton';

export default async function Post() {
  const post = await db.posts.get(1);

  async function likePost() {
    ~'use server'~; // Principle 3: a Server Function crosses as a reference
    await db.posts.like(1);
  }

  return (
    <article>
      <h1>{post.title}</h1>
      <LikeButton ~initialLikes={post.likes}~ onLike={likePost} /> {/* Principles 1 and 4: only the number 12 crosses */}
    </article>
  );
}
```

```jsx title="src/LikeButton.jsx" startLine="1"
'use client';

import { useState } from 'react';

export default function LikeButton({ initialLikes, onLike }) {
  const [likes, setLikes] = useState(initialLikes);
  return (
    <>
      <span>{likes} likes</span>
      <button onClick={() => { setLikes(likes + 1); ~onLike()~; }}>Like</button> {/* Principle 3: sends a request to run likePost on the server */}
    </>
  );
}
```

### The order in which React calls the components

React calls `Post` on the server, and `LikeButton` in the browser. The props travel from the server to the browser, and a tap travels back:

```tree dir=right caption="The path of the post page: Post on the server, the props across, LikeButton in the browser, and a tap back to the server."
How the post page reaches the user, and how a tap comes back
- +1. On the server [`Post`] | The framework calls `Post`; it **awaits the post** from `db.posts.get` | React **writes down `12`** and a **reference to `likePost`**
- +2. In the browser [`LikeButton`] | React **rebuilds `initialLikes` and `onLike`**, and calls `LikeButton` | The page shows **12 likes**
- +3. The user taps Like [`setLikes` `onLike`] | The count becomes **13** in the browser | React **sends a request** to run `likePost`
- +4. Back on the server [`likePost`] | `likePost` calls **`db.posts.like`** | The database **saves the like**
```

### Summary

| Value on the `LikeButton` tag | Crosses? | What the reader of the blog gets |
| :--- | :--- | :--- |
| `initialLikes={post.likes}`, a number | Yes | The page with `12 likes` |
| `publishedAt={post.publishedAt}`, a `Date` | Yes | A real date in the browser, with no conversion needed |
| `onLike={() => db.posts.like(1)}`, a plain function | No | No page: `Event handlers cannot be passed to Client Component props.` |
| `likesText={formatLikes(post.likes)}`, the result of a call | Yes | The string `12 likes` |
| `onLike={likePost}`, a Server Function | Yes, as a reference | A tap that saves the like on the server |
| `post={post}`, an instance of `PostRow` | No | No page: `Only plain objects, and a few built-ins, can be passed...` |
| `post={{ ...post }}`, a plain copy of the row | Yes, every field | The page, and the email of the author in every reader's browser |

Remember the one sentence of this lesson. **Between a Server Component and a Client Component, send data, not code. Every prop must be serializable: React writes it down on the server and rebuilds it in the browser.**

## For the Interview

> **The Interview Question:** What can you pass from a Server Component to a Client Component?

### How to Answer Clearly in 30 Seconds

"A Server Component and a Client Component run in different environments, so every prop between them must be serializable. React writes it down on the server and rebuilds it in the browser. Three rules follow:
1. **Data crosses.** Primitives, arrays, plain objects, `Date`, `Map`, `Set`, JSX elements, and Promises all cross, and the Client Component receives them as from any parent.
2. **Plain functions do not.** Passing one stops the render with an error. I call the function on the server and pass its result, or move it into client code. When the click must change data on the server, I mark it `'use server'`. React then passes a reference, and a call becomes a request to the server.
3. **Class instances do not, and whole rows should not.** An object built by a class fails, even without methods. A plain copy of a database row crosses with every field, sensitive ones included. So I pass only the fields the Client Component uses."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What does serializable mean here? Is it the same as JSON?"**
   It means React can write the value down on the server and rebuild it in the browser. React's docs do not call the format JSON, and their list goes beyond what JSON can hold: `Date`, `Map`, `Set`, and even Promises cross. A Promise can cross before it finishes, and the Client Component reads it with `use`; the value it brings must be serializable too. Lessons 124, 166, and 167 look at what the server actually sends.
2. **"Why can't you pass a function, and what do you do instead?"**
   A function is code, and a function in a Server Component can reach server-only things, such as the database. React has nothing to write down that the browser could run, so it throws. For a prop named like `onLike`, the message starts with `Event handlers cannot be passed`. For any other name, it starts with `Functions cannot be passed directly`. Instead, call the function on the server and pass the result, move it into the file of the Client Component, or mark it `'use server'`. A Server Function crosses as a reference, and calling it sends a request to the server. React's docs add that it should be called inside a Transition, which Lesson 110 covers.
3. **"Can you pass a whole object from the database?"**
   If the database builds it with a class, no. React throws an error that starts with `Only plain objects, and a few built-ins`. It does so even when the class has no methods, because React checks what built the object. If it is a plain object, yes, and that is the danger. Every field crosses, including fields the page never shows, such as an email address. React's docs say a Client Component should never accept objects that carry sensitive data, so pass only the fields it uses. The experimental taint APIs can make React throw when a marked object crosses, but React's docs warn not to rely on them alone; Lesson 149 covers them.

```tree dir=right caption="Interview summary: what a Server Component can pass to a Client Component, and what to do with the rest."
Props from a Server Component to a Client Component
- +Data [`12` `{ likes: 12 }` `Date` `<p>` `Promise`] | React **writes it down and rebuilds it** | The Client Component receives it **as from any parent**
- !A plain function [`onLike`] | ~Do **NOT** pass code | +**DO** call it on the server, move it to client code, or mark it `'use server'`
- !A class instance or a whole row [`post={post}`] | Instance: **the render stops**; plain row: **every field leaks** | +**DO** pass only the fields the component uses
```
