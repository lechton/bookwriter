# Lecture 110: How 'use server' Lets a Click in the Browser Run a Function on the Server

*(How does a button in the browser save something in a database that lives on the server?)*

> INTERVIEW QUESTION | ❱ CORE | What are Server Functions, and how does 'use server' create a callable endpoint?

---

## VS | `isValidEmail(email)` vs. `subscribe(email)`: both look like a function call, only the second one travels to the server

> In plain JavaScript, when a click must save something in the database, you write two pieces: a URL on the server that saves the data, and a `fetch` in the browser that sends the data to that URL. **A Server Function lets you write only one `async` function in a file that starts with `'use server'`, and the browser calls it like any other function, while React and the framework write the request for you.** The call looks ordinary, but it is a network request: a copy of the arguments goes to the server, and a copy of the answer comes back later.

Remember how you save data from the browser in plain JavaScript. The database lives on the server, and the button lives in the browser, on the user's computer. The button cannot reach the database, so you write two pieces of code:

```js title="Plain JavaScript: a URL on the server, and a fetch in the browser"
app.post(~'/api/subscribe'~, async (req, res) => { /* save the email */ }); // On the server
await ~fetch('/api/subscribe', { method: 'POST', body: JSON.stringify({ email }) })~; // In the browser
```

With a Server Function, you write only the function that saves the email. You put it in a file whose first line is `'use server'`. The browser code imports it and calls it, as if it were a normal function:

```jsx title="React: one function, imported and called from the browser"
import { subscribe } from './actions'; // actions.js starts with 'use server'
const answer = await ~subscribe(email)~; // React sends the request to the server for you
```

You did not write a URL. You did not write a `fetch`. React and the framework write both for you, behind the call.

Here is the one sentence to keep in mind for this whole lesson:

**A Server Function call looks like a normal function call, but it is a network request.**

> [!DEFINITION]
> **Client Component.** [REVIEW] A Client Component is a component in a file that starts with `'use client'`. Its code goes into the JavaScript bundle the browser downloads, so it runs in the browser, and it can use state, event handlers, and Hooks such as `useState` (Lesson 106).

> [!DEFINITION]
> **Server Component.** [REVIEW] A Server Component is a component that runs only on the server. Its code never reaches the browser, only what it renders does. A component is a Server Component by default, when its file has no directive at the top (Lesson 101).

> [!DEFINITION]
> **Serializable.** [REVIEW] A value is serializable when React can write it down as text, send that text over the network, and build the same value again on the other side. A string, a number, a plain object, and an array are serializable. A click event, JSX, and a plain function are not (Lesson 107).

### Two Calls That Look the Same

Put a call to an ordinary function next to a call to a Server Function. `isValidEmail` is an ordinary function that checks the email in the browser. `subscribe` is a Server Function that saves it in the database:

```jsx title="An ordinary function call vs. a Server Function call"
const ok = ~isValidEmail(email)~; // Runs right here, in the browser, at once
const answer = await ~subscribe(email)~; // Runs on the server; the answer comes back later
```

**It may look the same, but it is NOT the same thing!** `isValidEmail` runs in the browser, on the spot. `subscribe` never runs in the browser at all. One call of `subscribe` does three things, in order:
1. A copy of the email travels from the browser to the server.
2. `subscribe` runs on the server, where the database is.
3. Its answer, `'You are subscribed!'`, travels back to the browser.

> [!DEFINITION]
> **Server Function.** [NEW] A Server Function is an `async` function that runs on the server, and that code in the browser can call like a normal function. React's docs: "Server Functions allow Client Components to call async functions executed on the server." The line `'use server'` at the top of a file turns every function the file exports into a Server Function. It is about functions, not about components (Lesson 110).

Each way has a benefit and a problem:
- **By hand**, you control the URL, the request, and the reading of the answer. The problem is that you write and keep two pieces of code in sync, one on the server and one in the browser.
- **With a Server Function**, you write one function, and you never write `/api/subscribe` or its `fetch`. The problem is that the call hides a network request, and three rules come with it:
  1. The function must be `async`, because the answer comes back from the network later.
  2. Every value you pass to it, and every value it returns, must be serializable.
  3. Anyone can call it, with any arguments, just as anyone can call any URL on your server.

For the user, nothing looks different. The email reaches the database, the server's answer appears on the same page, and the page does not reload.

### Where Readers Usually Go Wrong

Readers usually go wrong because the call looks so ordinary:
1. **They read `'use server'` as "this is a Server Component"**, and put it at the top of a component file. The framework stops with an error when it builds the page.
2. **They write `onClick={subscribe}`.** React hands the click event to `subscribe` in place of the email. The event cannot be sent to the server, and the email never arrives.
3. **They treat the call as instant.** The page shows nothing while the server works, so the user thinks the click failed and clicks again.

### Three Ways to Change Data on the Server

When a click must change data on the server, developers choose between three ways:
1. **A URL you write on the server, and a `fetch` in the browser** (as seen in Lesson 33). This fits an app whose framework has no Server Functions, or a URL that other programs call too.
2. **A Server Function called from a click handler, inside `startTransition`.** This lesson builds this way. It fits a button that is not part of a form, or a call whose answer you keep in state.
3. **A Server Function passed to `<form action>`.** This fits a real form, with fields and a submit button. Lesson 112 teaches it.

Our signup has one field, so it could be a form. Here we call `subscribe` from a click handler, so every step of the call stays in our own code, where we can see it. Lesson 112 turns the same signup into a form.

2. **`subscribe(email)`: a copy of the email goes to the server, and a copy of the answer comes back.** So every argument must be serializable, and `onClick={subscribe}` sends the click event instead of the email.

## PRINCIPLE | `'use server'`: every function the file exports runs only on the server, and the browser gets only a reference to it

> [!PRINCIPLE]
> **Principle 1: `'use server'` Turns `subscribe` into a Server Function**
>
> *Put `'use server'` at the top of a file of `async` functions; every export becomes a Server Function that a Client Component can import, and the browser gets a reference to it, not its code.*
>
> A Client Component often needs to change data that lives on the server, such as saving an email in the database. `'use server'` builds what that takes: a reference in the browser bundle, and an endpoint on the server that the reference calls. The code of the function, with the database inside it, never reaches the browser. The line is about functions only. There is no directive for Server Components, because a component with no directive already is one.
>
> **DO THIS:**
> ```js
> ~'use server'~; // actions.js: every export becomes a Server Function
>
> export async function subscribe(email) {
>   await db.subscribers.add(email);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~'use server'~; // **WRONG:** App.jsx is a component file; there is no directive for Server Components
>
> export default function App() {
>   return <main><NewsletterSignup /></main>;
> }
> ```

Here is the smallest Server Function. It is one file with one function, and the first line marks it:

```js title="src/actions.js"
~'use server'~; // Every function this file exports becomes a Server Function

import { db } from './db';

export async function subscribe(email) {
  await db.subscribers.add(email);
}
```

And here is the Client Component that uses it. It imports `subscribe` exactly as it imports any other function:

```jsx title="src/NewsletterSignup.jsx"
'use client';

import { ~subscribe~ } from './actions'; // In the browser, subscribe is a reference, not the code above
```

React's docs say what the first line of `actions.js` does: it marks "all exports within that file as Server Functions that can be used anywhere, including imported in client code."

### An Import That Does Not Bring the Code

Remember what an import normally does. When the bundler builds the bundle for the browser, it copies the code of every imported function into it (as seen in Lesson 07). So `import { isValidEmail }` puts the code of `isValidEmail` in the browser, and a call runs there.

**The import of `subscribe` looks the same, but the bundler does something else.** It sees `'use server'` at the top of `actions.js`, and it leaves the body of `subscribe` out of the browser bundle. In its place, it puts a **reference**: a small object that only names the Server Function, so the browser can ask the server to run it (as seen in Lesson 107). The code itself, with `db` inside it, stays on the server.

React's docs show what a reference looks like, for one of their own Server Functions, named `createNote`:

```js title="The reference to createNote, as React's docs show it"
{ $$typeof: Symbol.for("react.server.reference"), ~$$id~: 'createNote' } // $$id tells the server which Server Function to run
```

React writes this object, not you. You never type `$$typeof` or `$$id` yourself.

```tree caption="What a normal import puts in the browser bundle, and what an import from a 'use server' file puts there."
What the import gives the browser
- +A normal import [`import { isValidEmail }`] | The bundler puts **the code of the function** in the browser bundle | A call **runs in the browser**
- +An import from a `'use server'` file [`import { subscribe }`] | The bundler puts **a reference** in the bundle; the code **stays on the server** | A call **sends a request to the server**
```

### A Reference in the Browser, an Endpoint on the Server

`'use server'` builds two things that work as a pair:
1. **In the browser:** the reference to `subscribe`, in the bundle.
2. **On the server:** an **endpoint**, a URL on the server that answers requests from the browser, like the `/api/subscribe` you would write by hand. The framework creates one for every Server Function. React's docs: "Server Functions are exposed server endpoints and can be called anywhere in client code."

When the browser calls the reference, the request goes to that endpoint, and the server runs the real `subscribe`. You never choose the URL of the endpoint. The framework chooses it, and React's docs do not say what it is.

```tree dir=right caption="The two things 'use server' builds: a reference in the browser, and an endpoint on the server that the reference calls."
What `'use server'` builds for `subscribe`
- +1. In the browser [`subscribe`] | A **reference** that names the Server Function | Calling it **sends a request**
- +2. On the server | An **endpoint** created by the framework | The request arrives, and **the real `subscribe` runs**
```

React's docs call `'use server'` and `'use client'` **directives**: lines at the top of a file or a function that give instructions to the bundler. Lesson 111 explains them in full.

### VS | `'use client'` vs. `'use server'`: they look like a pair, they are not

The two directives look like a matching pair. So it is tempting to think: `'use client'` makes a Client Component, so `'use server'` must make a Server Component. **It may look the same, but it is NOT the same thing!**

```jsx title="'use client' at the top of a file vs. 'use server' at the top of a file"
~'use client'~; // NewsletterSignup.jsx: this file, and what it imports, runs in the browser too
~'use server'~; // actions.js: the functions this file exports run only on the server, and the browser can call them
```

- **`'use client'`** is about components that run in the browser.
- **`'use server'`** is about functions that stay on the server.

There is no directive for Server Components at all. A component is a Server Component by default, when its file has no directive (as seen in Lesson 101). React's docs warn about this exact mix-up: "A common misunderstanding is that Server Components are denoted by `"use server"`, but there is no directive for Server Components. The `"use server"` directive is used for Server Functions."

### VS | `'use server'` at the top of a function vs. at the top of a file: the same Server Function, a different way to reach it

In Lesson 107, `'use server'` sat inside one function, `likePost`, written inside a Server Component:

```jsx title="'use server' at the top of a function, inside a Server Component"
async function likePost() {
  ~'use server'~; // Marks this one function
  await db.posts.like(1);
}
```

Here it sits at the top of a whole file:

```js title="'use server' at the top of a file, in actions.js"
~'use server'~; // Marks every function this file exports

export async function subscribe(email) {
  await db.subscribers.add(email);
}
```

**Yes, it is the exact same thing** for each function they mark: both make a Server Function, with a reference in the browser and an endpoint on the server. The one difference is how a Client Component gets the function:
- **At the top of a function**, the function lives inside a Server Component, so no other file can import it. The Server Component hands it down to a Client Component as a prop (as seen in Lesson 107).
- **At the top of a file**, any Client Component can import the function, as `NewsletterSignup` does. React's docs require this form for an import from client code.

### The Files So Far

`db.js` plays the database. Its `add` saves one email in an array:

```js title="src/db.js"
const subscribers = [];

export const db = {
  subscribers: {

      subscribers.push(email);
```

`actions.js` is the file above. `NewsletterSignup.jsx` only imports `subscribe` so far; Principle 2 gives it the email field and the button. `App.jsx` renders the post with the signup under it:

```jsx title="src/App.jsx"
import NewsletterSignup from './NewsletterSignup';

export default function App() { // No directive: App is a Server Component
  return (
    <main>
      <h1>Park Opens Today</h1>
      <p>The city opened a new park on Main Street.</p>

    </main>

```

### `'use server'` on a Component File

A developer wants to be sure that `App` runs on the server. By analogy with `'use client'`, they add `'use server'` at the top of `App.jsx`:

```jsx title="src/App.jsx" bad="1"
~'use server'~; // **WRONG:** marks App as a Server Function, not as a Server Component

import NewsletterSignup from './NewsletterSignup';

export default function App() {
  return <main><NewsletterSignup /></main>;
}
```

**The framework stops with an error, and the post never appears.** Why? With `'use server'` at the top, every export of the file becomes a Server Function, an endpoint for the browser to call. `App` is a component, not an `async` function. And React's docs say that `'use server'` can only be used on `async` functions. The framework checks this rule when it builds the page.

The fix is to delete the line. `App` was already a Server Component, because its file has no directive.

Remember: `'use server'` marks functions the browser can call. It never marks a component.

## PRINCIPLE | `subscribe(email)`: a copy of the email goes to the server, and a copy of the answer comes back

> [!PRINCIPLE]
> **Principle 2: One Click Sends `john@example.com` and Brings Back `You are subscribed!`**
>
> *Calling a Server Function sends a network request with a copy of its arguments; the function runs on the server, and a copy of its return value comes back as the value of a promise, so pass only serializable values and `await` the answer.*
>
> The call looks like a normal function call, but the function never runs in the browser. React serializes the arguments, sends them to the server, runs the real function there, and sends its return value back. That is the same job as a `fetch` to your own URL, with the URL, the request, and the reading of the answer written for you. Every value must make the trip, so a click event, JSX, or a plain function cannot be an argument.
>
> **DO THIS:**
> ```jsx
> async function handleClick() {
>   const answer = await ~subscribe(email)~; // A copy of email goes to the server; the answer comes back
>   setMessage(answer);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button ~onClick={subscribe}~>Subscribe</button> {/* **WRONG:** subscribe receives the click event, which cannot be sent to the server */}
> ```

### VS | `fetch('/api/subscribe')` vs. `subscribe(email)`: the same HTTP request, a different author

Both ways send the email to an endpoint on the server in an **HTTP request**, the same kind of request a browser sends when it asks a server for a page or for data. Both get an answer back. The one difference is who writes the request.

By hand, you write two pieces. On the server, a file of your own answers the URL `/api/subscribe`. Its exact shape depends on the server you use:

```js title="api/subscribe.js"
export async function POST(request) {
  const { email } = await request.json();
  await db.subscribers.add(email);
  return new Response('You are subscribed!');
}
```

In the browser, the click handler sends the email to that URL and reads the answer:

```jsx title="With fetch: you write the URL, the request, and the reading of the answer"
async function handleClick() {
  const res = await ~fetch('/api/subscribe', { method: 'POST', body: JSON.stringify({ email }) })~; // You write the URL and turn the email into text
  const answer = await res.text(); // You read the answer yourself
  setMessage(answer);
}
```

With a Server Function, `actions.js` holds the whole server side. `subscribe` now also returns the answer line:

```js title="src/actions.js"
'use server';

import { db } from './db';

export async function subscribe(email) {
  await db.subscribers.add(email);
  ~return 'You are subscribed!'~; // The answer that travels back to the browser
}
```

And the click handler holds one call:

```jsx title="With subscribe: React writes the request for you"
async function handleClick() {
  const answer = await ~subscribe(email)~; // React builds the request, sends it, and reads the answer
  setMessage(answer);
}
```

**Yes, it is the exact same job!** Both send an HTTP request to an endpoint, and both get `'You are subscribed!'` back. In the browser, React turns your call into that request. On the server, React turns the request back into a call of the real `subscribe`.

### What Travels on One Click

**The server never sees your `email` variable. It gets a copy, and the answer comes back later.** To make the copy, React serializes the email: it writes the value down as text, sends the text over the network, and the server builds the same value again from it (as seen in Lesson 107).

Here is the path of one click, in order:
1. The user types `john@example.com`. The state variable `email` holds it.
2. The user clicks `Subscribe`. The click handler calls `subscribe(email)`.
3. In the browser, `subscribe` is a reference. React serializes the email and sends it to the endpoint in a network request.
4. On the server, React builds the email again from that text, and calls the real `subscribe` with it.
5. `subscribe` saves the email with `db.subscribers.add(email)`, and returns `'You are subscribed!'`.
6. React serializes that string and sends it back in the answer to the request.
7. In the browser, the promise from `subscribe(email)` resolves with `'You are subscribed!'`, and `setMessage(answer)` puts it on the page.

```tree dir=right caption="The path of one click: a copy of the email goes to the server, and a copy of the return value comes back."
What crosses between the browser and the server on one click
- +1. In the browser [`await subscribe`] | React **serializes the email** and sends it | The server gets **a copy** of `'john@example.com'`
- +2. On the server [`subscribe`] | The real function **saves the email** | It returns **`'You are subscribed!'`**
- +3. Back in the browser [`setMessage`] | React **builds the string again**, and the promise resolves | The page shows **`You are subscribed!`**
```

In Lesson 107, React serialized props once, on their way from the server to the browser. A Server Function call serializes twice, once in each direction. React's docs: "When calling a Server Function on the client, it will make a network request to the server that includes a serialized copy of any arguments passed. If the Server Function returns a value, that value will be serialized and returned to the client."

This is also why every Server Function is `async`. The answer comes back from the network later, as the value of a promise, and the caller `await`s that promise to read it. React's docs: "Because the underlying network calls are always asynchronous, `'use server'` can only be used on async functions."

### The Email Field, the Button, and the Answer Line

Now `NewsletterSignup` gets two state variables, the email field, the button, and the answer line. The email field is a controlled `<input>`, with `value` and `onChange` (as seen in Lesson 20):

```jsx title="src/NewsletterSignup.jsx"
'use client';

import { useState } from 'react';
import { subscribe } from './actions';

export default function NewsletterSignup() {
  const [email, setEmail] = useState('');
  const [message, setMessage] = useState('');

  async function handleClick() {
    const answer = await ~subscribe(email)~; // A copy of email goes to the server
    setMessage(answer); // The answer that came back goes on the page
  }

  return (
    <section>
      <h2>Get new posts by email</h2>
      <label>
        Your email
        <input value={email} onChange={e => setEmail(e.target.value)} />
      </label>
      <button ~onClick={handleClick}~>Subscribe</button> {/* handleClick passes email to subscribe, not the click event */}
      <p>{message}</p>
    </section>
  );
}
```

When the page opens, the email field is empty, and there is no answer line. After the user types `john@example.com` and clicks `Subscribe`, the server's answer appears:

The handler still misses one thing: while the server works, the page shows nothing. Principle 3 adds it.

### `onClick={subscribe}`

A developer sees that `handleClick` only calls `subscribe`, and wants to drop the extra function. So they pass `subscribe` straight to the button:

```jsx title="An arrow function that passes email vs. subscribe passed straight to onClick"
<button ~onClick={() => subscribe(email)}~>Subscribe</button> {/* Sends the email */}
<button ~onClick={subscribe}~>Subscribe</button> {/* **WRONG:** React passes the click event as the first argument */}
```

**It may look the same, but it is NOT the same thing!** React calls any function you give to `onClick` with the click event as its first argument (as seen in Lesson 11). So with `onClick={subscribe}`, `subscribe` receives the click event in place of the email.

Then React must serialize that event to send it to the server, and it cannot. The event is not a plain object, and React's docs list "Events from event handlers" among the values a Server Function cannot receive. Depending on the framework, one of two things happens. React may reject the call in the browser, before any request leaves, with this error:

```devconsole width=full
x Error: Only plain objects, and a few built-ins, can be passed to Server Functions. Classes or null prototypes are not supported.
```

Or React may send the server a placeholder in place of the event, which the server cannot read.

Either way, the email never reaches the server. The fix is the arrow function `onClick={() => subscribe(email)}`. React passes the click event to the arrow function, and the arrow function passes only `email` to `subscribe`.

### Anyone Can Call the Endpoint

A Server Function is an endpoint, and anyone can send a request to an endpoint, not only your button. React's docs warn: "Arguments to Server Functions are fully client-controlled." So treat every argument as **untrusted input**: a value that whoever sent the request may have made up.

Checking the email with `isValidEmail` in the browser is not enough, because a request can reach the endpoint without your button. Therefore, you need to pay attention and always check inside `subscribe` itself: check that the email is a real email, and check that the user is allowed to do what the function does. Lessons 130 and 162 teach how.

Remember: the call looks like a normal function call, but it is a network request, and only copies of serializable values make the trip.

## PRINCIPLE | `startTransition`: `isPending` stays `true` until the server's answer is on the page

> [!PRINCIPLE]
> **Principle 3: `startTransition` Shows `Subscribing...` While the Server Works**
>
> *Outside a form, call a Server Function inside `startTransition`, so `isPending` is `true` while the request is on its way; wrap the state update after `await` in a second `startTransition`.*
>
> A Server Function call lasts as long as a trip to the server and back. If React does not know that an Action is running, the page shows nothing during that time, the button looks dead, and the user sends the email again. Inside `startTransition`, the call is an Action, and `isPending` stays `true` until the answer is on the page. The update after `await` needs a second `startTransition`, because React does not count updates after `await` as part of the Transition.
>
> **DO THIS:**
> ```jsx
> function handleClick() {
>   ~startTransition(async () => {~ // isPending is true until the answer is on the page
>     const answer = await subscribe(email);
>     startTransition(() => { setMessage(answer); });
>   });
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> async function handleClick() {
>   const answer = await ~subscribe(email)~; // **WRONG:** nothing shows the request is on its way, and the user clicks again
>   setMessage(answer);
> }
> ```

### The Button Looks Dead

The handler from Principle 2 works, but a trip to the server and back takes time. On a slow phone network, it can take a second or more. During that time, nothing on the page changes: the button still reads `Subscribe`, and there is no answer line yet.

**Without a pending state, the button looks dead, and the user clicks again.** The user thinks the first click missed. The second click sends a second request, and `subscribe` saves `john@example.com` a second time.

React's docs give the fix in one line: "Server Functions should be called in a Transition." A Transition lets the page show that something is in progress (as seen in Lesson 67).

> [!DEFINITION]
> **Action.** [REVIEW] An Action is a function you pass to `startTransition`. `useTransition` gives you `startTransition` and `isPending`, and `isPending` is `true` while an Action runs, so the page can show that something is in progress. React's docs: "Any async calls awaited in the `action` will be included in the transition" (Lesson 41).

### VS | `await subscribe` in a plain handler vs. inside `startTransition`: the same answer, only one shows the wait

Here are the two handlers. Both call `subscribe(email)`, and both put the answer on the page:

```jsx title="await subscribe in a plain handler"
async function handleClick() {
  const answer = await ~subscribe(email)~; // React does not know that a request is on its way
  setMessage(answer);
}
```

```jsx title="await subscribe inside startTransition"
function handleClick() {
  ~startTransition(async () => {~ // React knows: isPending is true until the answer is on the page
    const answer = await subscribe(email);
    startTransition(() => {
      setMessage(answer);
    });
  });
}
```

**It may look the same, but it is NOT the same thing!** Only the second handler tells React that an Action is running. The awaited call to `subscribe` is part of the Action, so `isPending` stays `true` for the whole trip to the server and back, and the button can show it.

### Why the Handler Calls `startTransition` Twice

**One `startTransition` does not cover the line after `await`, so the handler needs a second one.** In Lesson 67, one `startTransition` around a state update was enough, because there was no `await`. Here is what happens after one click:
1. The first `startTransition` calls the `async` function at once. `isPending` turns `true`, and the button can read `Subscribing...`.
2. The function reaches `await subscribe(email)` and waits for the server. `isPending` stays `true`, because the awaited call is part of the Transition.
3. The answer arrives, and the code after `await` runs. React's docs: "When you use `await` inside a `startTransition` function, the state updates that happen after the `await` are not marked as Transitions." So without help, `setMessage(answer)` would fall outside the Transition.
4. The second `startTransition` puts `setMessage(answer)` back inside the Transition. React's docs call the need for it "a known limitation that we will fix in the future."
5. `isPending` "stays `true` until all Actions complete and the final state is shown to the user," as React's docs say. So the answer line appears, and the button reads `Subscribe` again.

```tree dir=right caption="The two startTransition calls in handleClick, and what isPending is during each step."
What happens in `handleClick` after one click
- +1. First `startTransition` [`async`] | The Action **starts** | `isPending` turns **`true`**: the button reads **`Subscribing...`**
- +2. `await subscribe` | The Action **waits** for the server | `isPending` **stays `true`**
- +3. Second `startTransition` [`setMessage`] | The update after `await` is **part of the Transition** | The answer appears, and `isPending` turns **`false`**
```

### The Pending Button

Now the component also calls `useTransition`. It gives back two values, `isPending` and `startTransition`:

```jsx title="src/NewsletterSignup.jsx" startLine="9"
  const [isPending, ~startTransition~] = ~useTransition()~; // isPending is true while the Action runs
```

`handleClick` becomes the handler with the two `startTransition` calls:

```jsx title="src/NewsletterSignup.jsx" startLine="11"
function handleClick() {
  ~startTransition(async () => {~ // 1. The Action starts: isPending turns true
    const answer = await subscribe(email); // 2. The Action waits for the server
    ~startTransition(() => {~ // 3. The update after await stays part of the Transition
      setMessage(answer);
    });
  });
}
```

And the button shows `isPending`:

```jsx title="src/NewsletterSignup.jsx" startLine="27"
<button onClick={handleClick} ~disabled={isPending}~> {/* The user cannot click again while the request is on its way */}
  {isPending ? 'Subscribing...' : 'Subscribe'}
</button>
```

The user types `john@example.com` and clicks `Subscribe`. While the request is on its way, the button reads `Subscribing...`, and a second click does nothing, because the button is disabled (as seen in Lesson 21). When the answer comes back, the answer line appears, and the button reads `Subscribe` again:

### A Form Does This by Itself

Our signup calls `subscribe` from a click handler, so we wrap the call in `startTransition` ourselves. A form does it for you. React's docs: "Forms will automatically wrap Server Functions in transitions." So for the Transition, a Server Function passed to `<form action>` and a Server Function called inside `startTransition` are the exact same thing. Lesson 112 teaches the form way.

Remember: the call is a network request, so it takes time, and `startTransition` lets the page show that time.

### The Complete Code

`db.js` plays the database:

```js title="src/db.js"
const subscribers = [];

export const db = {
  subscribers: {
    async add(email) {
      subscribers.push(email);

  },
```

`actions.js` holds the Server Function:

```js title="src/actions.js"
~'use server'~; // Principle 1: every export becomes a Server Function

import { db } from './db';

export async function subscribe(email) {
  await db.subscribers.add(email);
  ~return 'You are subscribed!'~; // Principle 2: a copy of this string travels back to the browser
}
```

`NewsletterSignup.jsx` is the Client Component that calls it:

```jsx title="src/NewsletterSignup.jsx"
'use client';

import { useState, useTransition } from 'react';
import { ~subscribe~ } from './actions'; // Principle 1: a reference, not the code

export default function NewsletterSignup() {
  const [email, setEmail] = useState('');
  const [message, setMessage] = useState('');
  const [isPending, startTransition] = useTransition();

  function handleClick() {
    ~startTransition(async () => {~ // Principle 3: isPending is true until the answer is on the page
      const answer = await ~subscribe(email)~; // Principle 2: a copy of email goes to the server
      startTransition(() => {
        setMessage(answer);
      });
    });
  }

  return (
    <section>
      <h2>Get new posts by email</h2>
      <label>
        Your email
        <input value={email} onChange={e => setEmail(e.target.value)} />
      </label>
      <button onClick={handleClick} ~disabled={isPending}~> {/* Principle 3: no second click while waiting */}

  );
}
```

### The Order in Which Things Run

```tree dir=right caption="The order in which the components and the Server Function run, from the first render to the answer on the page."
From the first render to `You are subscribed!`
- +1. On the server [`App`] | The framework renders `App`, a **Server Component** | `App` places **`<NewsletterSignup />`**
- +2. In the browser [`NewsletterSignup`] | React renders the **Client Component** | The bundle holds a **reference** to `subscribe`, not its code
- +3. The click [`handleClick`] | The Action starts; the button reads **`Subscribing...`** | React sends **a copy of the email** to the endpoint
- +4. On the server [`subscribe`] | The real function **saves the email** | Returns **`'You are subscribed!'`**
- +5. In the browser [`setMessage`] | The promise resolves | The page shows **`You are subscribed!`**, and the button reads **`Subscribe`**
```

### Summary

| Aspect | What a Developer Might Expect | What React Does |
| :--- | :--- | :--- |
| **`'use server'`** | Marks a Server Component, as the partner of `'use client'` | Marks every export of a file as a Server Function; there is no directive for Server Components |
| **The import** | Brings the code of `subscribe` into the browser | Brings a reference; the code, with `db`, stays on the server |
| **The call** | Runs `subscribe` right away, with your variable | Sends a network request with a copy of the arguments, and brings back a copy of the return value |
| **The arguments** | Anything, such as the click event from `onClick={subscribe}` | Only serializable values, such as the email string |
| **The wait** | The click is done at once | The call lasts a trip to the server and back; `startTransition` and `isPending` show it |

Remember the one sentence of this lesson. **A Server Function call looks like a normal function call, but it is a network request.**

## For the Interview

> **The Interview Question:** What are Server Functions, and how does 'use server' create a callable endpoint?

### How to Answer Clearly in 30 Seconds

"A Server Function is an `async` function that runs on the server, and that code in the browser can call. When I put `'use server'` at the top of a file, every function it exports becomes a Server Function. A Client Component imports it like any function, but the bundler gives the browser only a reference, and the framework creates an endpoint on the server for it. Three rules follow:
1. **A call is a network request.** React sends a serialized copy of the arguments to the endpoint, runs the function on the server, and sends back a serialized copy of the return value as the value of a promise.
2. **Everything that crosses must be serializable.** A string or a plain object can be an argument; a click event, JSX, or a plain function cannot. That is why I write `onClick={() => subscribe(email)}`, not `onClick={subscribe}`.
3. **Outside a form, I call it inside `startTransition`**, so `isPending` can show that the request is on its way, and I wrap the state update after `await` in a second `startTransition`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does `'use server'` mark a Server Component?"**
   **No.** There is no directive for Server Components. A component whose file has no directive is a Server Component by default. `'use server'` marks functions that the browser can call over the network. Put at the top of a component file, it makes the file's exports Server Functions, and the framework stops with an error when it builds the page. React's docs call this "a common misunderstanding".
2. **"Can anyone call a Server Function, and should I use one to read data?"**
   Anyone can call it. It is an exposed endpoint, and React's docs say: "Arguments to Server Functions are fully client-controlled." So I check every argument on the server, and I check that the logged-in user may do the action. And no, I do not use it to read data. React's docs say Server Functions "are designed for mutations that update server-side state; they are not recommended for data fetching." A **mutation** here is a change to data on the server, such as saving an email. To read data, a Server Component reads it while it renders (as seen in Lesson 109).
3. **"What is the difference between `'use server'` at the top of a file and at the top of a function?"**
   Both make Server Functions. At the top of a function, the line works inside a Server Component, and the function reaches a Client Component as a prop. At the top of a file, client code can import every export of the file, and React's docs require this form for an import from client code. Until September 2024, React's docs called all Server Functions "Server Actions"; Lesson 136 explains the exact difference between the two names.

```tree caption="Interview comparison: the two places 'use server' can go, and the one place it must never go."
Where `'use server'` goes
- +Top of a file of `async` functions [`actions.js`] | Every export becomes a **Server Function** | Client code **imports** it and gets a **reference**
- +Top of an `async` function body [`likePost`] | One function inside a **Server Component** | Reaches a Client Component **as a prop**
- !Top of a component file [`App.jsx`] | ~Do **NOT** use it to make a Server Component | +**DO** leave the file with **no directive**
```
