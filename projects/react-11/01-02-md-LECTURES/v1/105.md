# Lecture 105: Why the Greeting Flips from Good morning to Good evening

*(Why does a page from the server change its text, and print a red error, when the JavaScript arrives?)*

> INTERVIEW QUESTION | ❱ CORE | What causes hydration mismatches, and how do you fix them?

---

## VS | The Server's Clock `renderToString` vs. the Phone's Clock `hydrateRoot`: one line of code gives two answers, and React reports an error

> On a page rendered by a server, every component runs twice: once on the server to write the HTML, and again in the browser during `hydrateRoot`. **A hydration mismatch means the browser's first render gives different output from the server's HTML, such as `Good evening` where the server wrote `Good morning`**. React does not quietly correct the text: it prints an error, throws that part of the page away, and builds it again in the browser.

Remember how you read the hour in plain JavaScript? You call `new Date().getHours()`, and you get the hour of the computer that runs your script. On a normal web page, that computer is the user's own computer. One script, one computer, one clock.

```js title="Plain JavaScript: one script, one computer, one clock"
const hour = ~new Date().getHours()~; // The clock of the user's computer: 18 at 6 PM in Los Angeles
document.querySelector('p').textContent = hour < 12 ? 'Good morning' : 'Good evening';
```

With a server, the same line sits inside a React component, and React runs that component on two computers (Lesson 104). First the server runs it, to write the HTML. Then the user's phone runs it again, during `hydrateRoot`. Two computers means two clocks, and often two time zones.

```jsx title="React with a server: one line, two computers"
const hour = ~new Date().getHours()~; // Server in UTC at 2 AM: 2. John's phone in Los Angeles at 6 PM: 18

<p>{hour < 12 ? 'Good morning' : 'Good evening'}, John</p>
```

The server writes `Good morning, John`. The phone renders `Good evening, John`. React compares the two, finds a different text, and prints a red error in the Console.

So here is the one sentence to keep in mind for this whole lesson:

**The browser's first render must give exactly the server's HTML. A value that only the browser knows waits until after hydration.**

> [!DEFINITION]
> **Hydration.** [REVIEW] The server sends the page as finished HTML, so the user sees it at once, but HTML cannot carry your event handlers. When the JavaScript arrives, `hydrateRoot` runs your components again in the browser, keeps every element the server sent, and attaches your handlers to them. React can keep those elements only when the browser's first render gives the same output as the server (Lesson 104).

> [!DEFINITION]
> **Hydration mismatch.** [NEW] A hydration mismatch is a first browser render that gives different output from the server HTML: a different text, a different tag, or a different attribute. The React docs call the error it causes a hydration error, and their verdict is short: "You should treat mismatches as bugs and fix them." The usual cause is a value that differs between the two computers, such as the clock, the width of the screen, or what the browser saved in `localStorage` (Lesson 105).

### What John Sees at 6 PM

An online shop greets a signed-in shopper at the top of its home page, by name and by the time of day. John lives in Los Angeles. He opens the page on his phone at 6 PM. Here is what he sees, in order:
1. The page appears at once, because the server sends it as finished HTML (Lesson 102). The line reads `Good morning, John`.
2. A moment later, the JavaScript arrives, and the line changes by itself to `Good evening, John`.
3. In the Console, React prints a red error.

```page width=full caption="The shop home page as the server sends it: at 6 PM in Los Angeles, John's phone shows Good morning, John."
line: Good morning, John | bad
console: quiet
```

```page width=full caption="The same page after the JavaScript arrives: the greeting has changed, and the Console shows a red error."
line: Good evening, John
console: Uncaught Error: Hydration failed because the server rendered text didn't match the client. As a result this tree will be regenerated on the client.
```

Here is where each greeting comes from:
- **On the server**, `renderToString` runs `App` to write the HTML. Many servers run in UTC, the world's reference time zone. There it is 2 AM, so `hour` is 2, and the HTML says `Good morning, John`.
- **On John's phone**, `hydrateRoot` runs `App` again. The phone's clock is set to Los Angeles, where it is 6 PM. So `hour` is 18, and the first browser render says `Good evening, John`.

```tree caption="The same line of App runs on two computers: the server's clock writes the HTML, and the phone's clock writes the first browser render."
One line that reads the hour, run on two computers
- !On the server, in UTC [`renderToString`] | `hour` is **2** at 2 AM | The HTML says **`Good morning, John`**
- !On John's phone, in Los Angeles [`hydrateRoot`] | `hour` is **18** at 6 PM | The first browser render says **`Good evening, John`**
```

**It looks like one value, but it is NOT one value!** In the code, `new Date().getHours()` is written once. In reality, it reads two clocks on two computers, so it gives two answers.

A second confusion does the real damage. The change on the screen looks like a correction: the server guessed wrong, and the browser fixed the guess.

**It is not a correction.** React expects the browser's first render to give the exact same output as the server, so that it can keep the server's elements (Lesson 104). When the two differ, React does not quietly patch the text. It reports an error, throws away that part of the page, and builds it again in the browser.

### What a Mismatch Costs

The user pays in three ways:
1. **The text the user is already reading changes.** The server sends HTML so that the page shows at once. The React docs: "Suddenly showing different content breaks that illusion."
2. **React throws away the server's part and builds it again.** The error says so: "this tree will be regenerated on the client." With no boundary around it, that part is the whole page (Lesson 104). The docs: "In the best case, they'll lead to a slowdown; in the worst case, event handlers can get attached to the wrong elements."
3. **A different attribute may stay wrong.** To stay fast, React does not check every attribute. The docs: "There are no guarantees that attribute differences will be patched up in case of mismatches."

### The Rule of Thumb: would the server and the phone give the same answer?

**Ask one question about every value your render reads: would the server and the phone give the same answer? If yes, render it. If not, it cannot appear in the first render.**

That leaves a practical job. A page often must show something that only the browser knows: the hour, the width of the screen, or a saved setting. React gives four ways to do it, and each one fits a different case:

```tree caption="Four ways to show a value that only the browser knows, without a hydration mismatch."
Four ways to show a value the server cannot know
- +1. Two-pass render [`useState` `useEffect`] | For a value that must appear **as text**, such as the greeting | Costs a **second render** and a **visible change**
- +2. CSS [`@media`] | For a difference in **layout only**, such as a `Menu` button on phones | **No second render** and **no change** after hydration
- +3. A store with a server value [`getServerSnapshot`] | For a browser value with a **fixed answer on the server** | Taught in **Lesson 53**
- !4. Silence one element [`suppressHydrationWarning`] | For **one text or attribute** that cannot match, such as a timestamp | The page **keeps the server's text**
```

This lesson shows the first, the second, and the fourth on our page. The third belongs to stores, and Lesson 53 teaches it.

A senior developer also knows the four classic mistakes:
1. **A `typeof window` check to stop the server crash.** The crash is gone, but the React docs list that exact check as a cause of a mismatch.
2. **The clock, a random number, or `localStorage` read during render.** It works on a page without a server. Lesson 14 already showed that the clock in a render makes a component impure.
3. **`suppressHydrationWarning` on the element.** The red error disappears, so the page looks fixed. The docs: "React will **not** attempt to patch mismatched text content." The user keeps reading the server's text.
4. **The error treated as noise from development mode.** The docs: "you must fix them like other bugs."

The rest of the lesson shows each one on the real home page.

Again, the one sentence of this lesson: **the browser's first render must give exactly the server's HTML. A value that only the browser knows waits until after hydration.**

**PRINCIPLES:** Every mismatch has the same shape: the server and the browser run the same components and get two different outputs. The causes differ, and so do the fixes. Five principles follow:
1. **Principle 1: `new Date()` during render gives the server and the phone two greetings.** The clock gives one answer on the server and another on the phone, and React reports a hydration error.
2. **Principle 2: `typeof window` gives the server the links and the phone the `Menu` button.** The check stops the server crash and creates a mismatch. CSS shows the right part on every screen, with one HTML.
3. **Principle 3: a `<div>` inside a `<p>` changes the server HTML before React reads it.** The browser rebuilds HTML that breaks the rules of HTML, so the page no longer matches what React renders.
4. **Principle 4: an Effect shows `Good evening` right after hydration.** The first browser render repeats the server's text, and an Effect switches to the phone's hour right after.
5. **Principle 5: `suppressHydrationWarning` hides the error and keeps `Good morning`.** It silences the warning for one element. It does not fix the text.

## PRINCIPLE | `new Date()` during render: the server and the phone write two different greetings

> [!PRINCIPLE]
> **Principle 1: Same First Render: A Value Read During Render Must Give the Same Answer on Both Computers**
>
> *The browser's first render must give the same output as the server HTML; a value read during render that differs between the two computers, such as the clock, causes a hydration error, and React builds that part of the page again.*
>
> The server and the phone run the same `App`, but not at the same moment and not in the same place. Any value that depends on the moment or the place gives two answers: the hour, a random number, the locale. The user sees the text change, and React rebuilds that part of the page in the browser.
>
> **DO THIS:**
> ```jsx
> <p>~Hello~, John</p> {/* No clock in the render: the server and the phone write the same text */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const hour = ~new Date().getHours()~; // **WRONG:** the server in UTC gets 2, the phone in Los Angeles gets 18
> <p>{hour < 12 ? 'Good morning' : 'Good evening'}, John</p>
> ```

### The Greeting in Its Smallest Form

**When a component reads a value during render that differs on the server and on the phone, the first browser render differs from the server HTML.** Here is the whole `App` that greets John:

```jsx title="src/App.jsx"
export default function App() {
  const hour = ~new Date().getHours()~; // Server in UTC at 2 AM: 2. John's phone in Los Angeles at 6 PM: 18
  return (
    <main>
      <p>{hour < 12 ? 'Good morning' : 'Good evening'}, John</p>
    </main>
  );
}
```

`getHours()` returns the hour in the time zone of the computer that runs it. Nothing in this file says which computer that is. So the same file gives the server one hour and the phone another.

### What React Does with Two Greetings

**React compares the browser's first render with the server HTML, finds a different text, reports an error, and builds the paragraph again.** That one check explains both things on the screen: the greeting John sees change, and the red error the developer sees. Here is the order:
1. The server runs `App` at 2 AM in UTC and sends the HTML `<p>Good morning, John</p>`.
2. John's phone shows `Good morning, John` while the JavaScript downloads.
3. The JavaScript arrives, and `hydrateRoot` runs `App` on the phone, at 6 PM in Los Angeles.
4. The browser's first render gives `Good evening, John`.
5. React compares that output with the server HTML and finds a different text.
6. React reports a hydration error in the Console.
7. React throws away the server's part of the page and builds it again in the browser. The React docs call this **regenerating** the tree **on the client**, and the client is the browser. The line now reads `Good evening, John`.

In development, the whole error looks like this:

```devconsole width=full caption="The Console on John's phone after hydrateRoot, when the server wrote Good morning and the browser rendered Good evening."
x Uncaught Error: Hydration failed because the server rendered text didn't match the client. As a result this tree will be regenerated on the client. This can happen if a SSR-ed Client Component used:
  - A server/client branch `if (typeof window !== 'undefined')`.
  - Variable input such as `Date.now()` or `Math.random()` which changes each time it's called.
  - Date formatting in a user's locale which doesn't match the server.
  - External changing data without sending a snapshot of it along with the HTML.
  - Invalid HTML tag nesting.
  It can also happen if the client has a browser extension installed which messes with the HTML before React loaded.
  https://react.dev/link/hydration-mismatch
  <App>
    <main>
      <p>
+ +       Good evening
-       Good morning
        ...
```

"A SSR-ed Client Component" means a component that the server rendered first, as it rendered our `App`. Read the rest of the message in two parts:
1. **The list of causes.** It is the React docs' own checklist, and this lesson covers it. Our greeting is the second item: a value that changes each time it is read, and in each place.
2. **The diff at the bottom.** A **diff** is React's way of showing what differs. It walks down from `<App>` to the exact tag, here the `<p>`. The line marked with a plus holds what the browser rendered. The line marked with a minus holds what the server sent. So the diff tells you which element to fix.

Before React 19, React printed several warnings for one mismatch, such as "Text content did not match". React 19 prints one message with a diff.

### The Clock Is Only One Example

The clock is the most common case. But every value that changes from one call to the next, or from one computer to the next, does the same thing. React's message names them:
- **`Date.now()` and `Math.random()`.** The server and the browser call them at two different moments, so they get two different numbers.
- **A date formatted in the user's locale.** The **locale** is the language and region the browser uses to write dates. A server in the United States writes the month first, 11/17/2026, while a phone in Paris writes the day first, 17/11/2026.
- **Data that changes**, such as a stock count. The server reads it once, and the browser reads it again. The server never sent its own copy along with the HTML.

All of them break one rule from Lesson 14: a component must give the same output for the same props, state, and context. On a page without a server, nobody notices. On a page with a server, the broken rule shows up at once, as a hydration error.

### Why the Bug Never Shows on the Laptop

**The greeting works perfectly on the developer's laptop and breaks only for real shoppers.** Here is how it ships:
1. A developer writes the greeting by the hour and tests it on a laptop.
2. The laptop is both the server and the browser, so both runs read one clock. The greeting matches, and the Console stays quiet.
3. The site goes live on a server that runs in UTC.
4. Every shopper outside UTC sees the greeting change after the page loads, and the Console shows a hydration error.

```tree dir=right caption="Why the greeting works on the developer's laptop and breaks for a shopper in Los Angeles."
Where the two clocks come from
- +On the developer's laptop | The server and the browser read **one clock** | Both renders say **`Good evening, John`**: no error
- !On the live site | The server reads **UTC**; the phone reads **Los Angeles** | **`Good morning`** then **`Good evening`**: a hydration error
```

## PRINCIPLE | `typeof window` in render: the crash is gone, but the server sends the links and the phone renders `Menu`

> [!PRINCIPLE]
> **Principle 2: Browser-Only Values: `typeof window` Makes the Server and the Browser Render Different Things**
>
> *Do not branch the render on `typeof window` or on browser-only APIs such as `window.innerWidth`, `window.matchMedia`, or `localStorage`; when the difference is only layout, render both parts and let a CSS media query hide one.*
>
> The server has no window and no screen, so any check of the browser gives the server one answer and the phone another. The check stops the crash but creates a mismatch. CSS solves the layout case without any check: the server and the browser render the same HTML, and the browser hides the part that does not fit the screen.
>
> **DO THIS:**
> ```jsx
> <button ~className="menu"~>Menu</button> {/* Rendered on both sides: a media query hides it on wide screens */}
> <nav className="links">...</nav>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const isPhone = ~typeof window !== 'undefined'~ && window.innerWidth < 600; // **WRONG:** the server gets false, the phone gets true
> ```

### The Server Has No `window`

**`window` is an object that only the browser creates.** It holds everything about the browser tab: the width of the screen in `window.innerWidth`, the saved data in `localStorage`, and much more. The server is a program with no screen, so it has no `window` at all. The React docs call these features **browser-only APIs**.

Now look at the navigation of our shop. On a phone, it shows one `Menu` button. On a wide screen, it shows the links Shoes and Bags. A developer chooses between the two with the width of the screen:

```jsx title="The navigation in App.jsx"
const isPhone = ~window.innerWidth~ < 600; // **WRONG:** on the server, window does not exist and the render stops

{isPhone ? (
  <button>Menu</button>
) : (
  <nav>
    <a href="/shoes">Shoes</a> <a href="/bags">Bags</a>
  </nav>
)}
```

On the server, `renderToString` runs the component and reaches `window`. The render stops with `ReferenceError: window is not defined`. The server sends no page, so John sees nothing.

### The Check That Moves the Bug

The usual fix is one more condition in front:

```jsx title="The first line of the navigation, with the check"
const isPhone = ~typeof window !== 'undefined'~ && window.innerWidth < 600; // Server: false. Phone: true
```

For a name that does not exist, JavaScript's `typeof` gives the text `'undefined'` instead of an error. So on the server the check is false, and `&&` stops before it reads `innerWidth`. The crash is gone.

**It may look like a fix, and it seems to work at first, but it is NOT the same thing!** The check makes the code run on the server. It also makes the server and the phone render two different things:
- **On the server**, `isPhone` is false, so the HTML holds the links Shoes and Bags.
- **On John's phone**, `isPhone` is true, so the first browser render holds the `Menu` button.

Here is the navigation on John's phone:

```page width=full caption="The navigation on John's phone, as the server sends it: the server could not see the screen, so it sent the links."
line: Shoes Bags
console: quiet
```

```page width=full caption="The same navigation after hydrateRoot: the links turn into a Menu button, and the Console shows a hydration error."
line: [Menu]
console: Uncaught Error: Hydration failed because the server rendered HTML didn't match the client. As a result this tree will be regenerated on the client.
```

This time the message says "HTML" instead of "text". A whole tag differs: a `<nav>` from the server, a `<button>` in the browser.

The error shows on some screens and not on others:
1. On a wide laptop, the server picks the links, and the browser picks the links too. The outputs match, and the Console stays quiet.
2. On a phone, the server picks the links, and the browser picks `Menu`. React reports a hydration error and builds that part again.
3. So a developer who tests only on a laptop never sees the error.

The React docs name this exact check as a cause: "Using checks like `typeof window !== 'undefined'` in your rendering logic." Right next to it: "Using browser-only APIs like `window.matchMedia` in your rendering logic." `localStorage` belongs to the same group. The docs: "if your app reads some data from `localStorage`, it can't possibly do that on the server."

### VS | A Branch in the Render `typeof window` vs. a CSS Rule `@media`: only CSS gives every screen the same HTML

**The menu and the links differ only in layout, so CSS can choose between them.** The React docs: "In many cases, you can avoid the need for this by conditionally showing different things with CSS." Instead of rendering one part or the other, `App` renders both parts, each with a class name:

```jsx title="The navigation in App.jsx, with both parts"
<button ~className="menu"~>Menu</button> {/* Shown only on phones by the CSS below */}
<nav ~className="links"~> {/* Shown only on wide screens by the CSS below */}
  <a href="/shoes">Shoes</a> <a href="/bags">Bags</a>
</nav>
```

Then CSS hides one of them. A **media query** is a CSS rule that applies only when the screen matches a condition, such as a width. You write it with `@media`:

```css title="styles.css"
.menu {
  display: none;
}

@media (max-width: 599px) {
  .menu {
    display: inline;
  }
  .links {
    display: none;
  }
}
```

On a wide screen, only the first rule applies: the `Menu` button is hidden, and the links show. On a screen narrower than 600 pixels, the media query applies too. It shows the `Menu` button and hides the links.

**It looks like the same result on the screen, but it is NOT the same thing!**
- **With `typeof window`**, the server and the phone render two different HTML trees, and every phone gets a hydration error.
- **With CSS**, the server and the phone render the exact same HTML: the button and the links together. The browser then hides one part, by the width. The outputs match, so there is no error.

There is a bonus. The CSS arrives with the HTML, so John's phone shows `Menu` even before the JavaScript loads.

```tree caption="The same navigation chosen during render with typeof window, or rendered whole and hidden by CSS."
Two ways to show `Menu` on phones and links on wide screens
- !Choose during render [`typeof window` `innerWidth`] | The server renders **the links**; the phone renders **`Menu`** | A **hydration error** on every phone
- +Render both, hide with CSS [`className` `@media`] | The server and the phone render **the same HTML** | **No error**, and the phone shows `Menu` **before the JavaScript arrives**
```

For that, the server must send the CSS with the page. So the server file adds one link before the root:

```jsx title="server.js"
response.send(`
  <link rel="stylesheet" href="/styles.css">
  <div id="root">${html}</div>
  <script type="module" src="/bundle.js"></script>
`); // The CSS arrives with the HTML, so the right part shows at once
```

When a value really must be read in JavaScript and shown as text, CSS cannot help. Principle 4 shows the way for that case.

### Why the Bug Ships

**The developer fixes a server crash and creates a bug that only phones see.** Here is how it ships:
1. A component reads `window.innerWidth` to choose between the `Menu` button and the links. Without a server, it works.
2. The team adds server rendering (Lesson 102), and the server crashes on `window`.
3. The developer wraps the read in a `typeof window` check. The crash is gone.
4. On every phone, the links turn into `Menu` after the page loads, and the Console shows a hydration error.

## PRINCIPLE | `<div>` inside `<p>`: the browser moves the `<div>` out before React compares

> [!PRINCIPLE]
> **Principle 3: Valid HTML: The Browser Must Keep the Server HTML as React Wrote It**
>
> *Write valid HTML nesting, and send the server HTML inside the root with nothing around it; HTML that the browser changes, such as a `<div>` inside a `<p>`, no longer matches what React renders.*
>
> Hydration compares React's render with the page the browser built, and the browser builds that page by the rules of HTML. A tag that breaks those rules is moved before any JavaScript runs. The screen looks the same, but the tree is different, and React reports a hydration error.
>
> **DO THIS:**
> ```jsx
> <p>Blue Sneakers ~<span>$49</span>~</p> {/* A span may sit inside a p: the browser keeps it */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <p>Blue Sneakers ~<div>$49</div>~</p> {/* **WRONG:** the browser moves the div out of the p */}
> ```

### A Price Inside a Line of Text

**React does not compare its render with the HTML text the server sent. It compares it with the elements the browser built from that text.** Usually the two are the same. With invalid HTML, they are not.

Our product line shows a name and a price. The price comes from a small component in its own file:

```jsx title="src/Price.jsx"
export default function Price() {
  return ~<div>$49</div>~; // **WRONG:** a div, which App places inside a p
}
```

```jsx title="src/App.jsx" startLine="6"
<p>Blue Sneakers ~<Price />~</p> {/* The p now holds a div */}
```

This code has no clock, no `window`, and no random number. Yet the page shows a hydration error.

### What the Browser Does with the Server HTML

**HTML does not allow a `<div>` inside a `<p>`, so the browser moves the `<div>` out before React sees it.** React's message calls this **invalid HTML tag nesting**: a tag placed inside a tag that HTML does not allow it in. Here is what happens, in order:
1. The server writes `<p>Blue Sneakers <div>$49</div></p>`.
2. The browser reads that HTML. By the rules of HTML, a `<p>` ends where a `<div>` starts. So the browser closes the `<p>` right before the `<div>`.
3. The browser puts the `<div>` after the `<p>`. Then it meets the leftover `</p>`, which closes nothing, and turns it into a new, empty `<p>`.
4. Then `hydrateRoot` runs `App`. Its render still has the `<div>` inside the `<p>`.
5. React finds a different shape in the page and reports a hydration error.

The Elements panel shows the shape the browser built:

```dom caption="The DOM the browser builds from the server HTML: the div was moved out of the p, and an empty p was added."
<main>
! <p>Blue Sneakers </p>
! <div>$49</div>
! <p></p>
</main>
```

The Console shows three errors. The first two warn about the nesting, and the third one is the hydration error:

```devconsole width=full caption="The Console on the phone during hydration, when Price returns a div inside the p."
x In HTML, <div> cannot be a descendant of <p>.
  This will cause a hydration error.
x <p> cannot contain a nested <div>.
  See this log for the ancestor stack trace.
x Uncaught Error: Hydration failed because the server rendered HTML didn't match the client. As a result this tree will be regenerated on the client.
```

**It may look the same, but it is NOT the same thing!** On the screen, both shapes show Blue Sneakers and the price. But the HTML the server wrote and the page the browser built are two different trees. React compares its render with the second one.

### Why It Worked Without a Server

On a page without a server, React creates every element itself (Lesson 07). It never goes through the browser's HTML rules, so the `<div>` stays inside the `<p>`, and the page works. Only the two nesting errors above appear in the Console. The first one already says what will happen: "This will cause a hydration error."

With server rendering, that warning comes true. The fix is valid HTML: the price becomes a `<span>`, which HTML allows inside a `<p>`.

```jsx title="A div inside the p, and a span inside the p"
<p>Blue Sneakers <div>$49</div></p> {/* The browser moves the div out: hydration error */}
<p>Blue Sneakers <span>$49</span></p> {/* Valid HTML: the browser keeps it as React wrote it */}
```

### Extra Whitespace Inside the Root

**The same thing happens when the server file adds anything around the HTML inside the root.** The React docs list extra whitespace, such as newlines, around the HTML that React generated inside the root node. Compare two ways to write the root in the template of the server file:

```jsx title="server.js, with the HTML right after the opening tag"
<div id="root">~${html}~</div> {/* The root holds only what React wrote */}
```

```jsx title="server.js, with the HTML on its own line"
~<div id="root">~ {/* **WRONG:** a newline and spaces follow the tag inside the root, and React never rendered them */}
  ${html}
</div>
```

The fix is to write the HTML right after the opening tag of the root, with nothing around it. The server file of Lesson 102 already does this.

The error message also names a third outside cause: "a browser extension installed which messes with the HTML before React loaded." React 19 skips tags that extensions add to the `<head>` and the `<body>`. It also skips a tag added straight inside the root, next to our `<main>`. But an extension that adds a tag inside one of our own elements, such as `<main>`, still causes a hydration error.

### Why the Bug Ships

**Two developers each write code that looks fine, and together they break hydration.** Here is how it ships:
1. One developer writes `Price`, which returns a `<div>`.
2. Another developer places `<Price />` inside a `<p>` line of text.
3. Without a server, React builds the elements itself, so the page looks right.
4. With server rendering, the browser moves the `<div>` out of the `<p>`, and hydration reports a mismatch.

## PRINCIPLE | `useEffect` with `isClient`: the first render matches the server, and the phone's hour comes right after

> [!PRINCIPLE]
> **Principle 4: Two Passes: Show the Browser's Value After Hydration**
>
> *When a value that only the browser knows must appear as text, start a state variable such as `isClient` at `false`, set it to `true` in an Effect, and show the browser's value only in the second render.*
>
> Effects do not run on the server. So the server and the first browser render both see `false`, give the same output, and React keeps the server's elements. Right after hydration, the Effect sets the state, and React renders the browser's value. The price is a second render and a visible change, so use it only when CSS cannot do the job.
>
> **DO THIS:**
> ```jsx
> const [isClient, setIsClient] = useState(false);
> useEffect(() => { setIsClient(true); }, []);
> <p>{~isClient ? greeting : 'Hello'~}, John</p> {/* Hello on both sides first, then Good evening after hydration */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <p>{~greeting~}, John</p> {/* **WRONG:** greeting comes from the clock during render, so the server and the phone disagree */}
> ```

### The Server's Text First, the Phone's Text Right After

**When a value that only the browser knows must appear as text, render the server's version first. Switch to the browser's value after hydration.** The React docs call this **two-pass rendering**. Their smallest example uses a state variable named `isClient`:

```jsx title="The two-pass render from the React docs"
const [isClient, setIsClient] = ~useState(false)~; // false on the server and in the browser's first render

useEffect(() => {
  ~setIsClient(true)~; // Runs only in the browser, after hydration
}, []);

<p>{isClient ? 'Is Client' : 'Is Server'}</p>
```

It works because of two facts you already know:
1. `useEffect` runs after the render, and only in the browser (Lesson 32). The React docs: "Effects don't run on the server."
2. Calling a setter makes React render the component again (Lesson 12).

`isClient` is our own state variable, named as on the `hydrateRoot` page of the React docs. The `useEffect` page of the docs writes the same pattern with the name `didMount`. Yes, it is the exact same thing, under two names.

### The Greeting in Two Passes

On our page, the server and the first browser render both say `Hello, John`. That text is true on both computers. The Effect then switches to the hour on the phone:

```jsx title="src/App.jsx"
import { useState, useEffect } from 'react';

export default function App() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  const hour = new Date().getHours();
  const greeting = hour < 12 ? 'Good morning' : 'Good evening';

  return (
    <main>
      <p>{~isClient ? greeting : 'Hello'~}, John</p> {/* Server and first browser render: Hello. After the Effect: Good evening */}
    </main>
  );
}
```

Here is what John sees on the phone at 6 PM:

```page width=full caption="On John's phone, from the server and during hydration: both renders say Hello, John."
line: Hello, John
console: quiet
```

```page width=full caption="The same phone right after hydration: the Effect has run, and the greeting reads Good evening, John with no error."
line: Good evening, John | good
console: quiet
```

**Yes, it is the exact same output!** The first browser render gives the exact same output as the server, because `isClient` is false on both. So React keeps the server's paragraph, and only then does the clock reach the screen. Here is the order:
1. The server renders `App` with `isClient` set to false. It sends `Hello, John`. The Effect never runs on the server.
2. John's phone shows `Hello, John` while the JavaScript downloads.
3. During hydration, `App` renders with `isClient` still false. The output matches the server, so React keeps the paragraph.
4. The Effect runs and calls `setIsClient` with true.
5. React renders `App` again, and the line becomes `Good evening, John`. The React docs: "an additional pass will happen synchronously right after hydration."

```tree dir=right caption="The two passes of the greeting: the first render matches the server, and the Effect brings the browser's value after hydration."
The greeting in two passes
- +Server [`isClient` is `false`] | Sends **`Hello, John`** | The Effect **never runs** here
- +First browser render [`isClient` is `false`] | Gives **`Hello, John`** again | **Matches** the server: React keeps the paragraph
- +After the Effect [`setIsClient`] | Sets `isClient` to **true** and renders `App` again | The line becomes **`Good evening, John`**, with **no error**
```

### What Two Passes Cost

**The greeting no longer causes an error, but it still changes in front of John.** The two-pass render has two costs:
1. **A second render.** The React docs: "This approach makes hydration slower because your components have to render twice."
2. **A visible change.** The docs: "rendering a different UI immediately after hydration may also feel jarring to the user."

That is why the menu of Principle 2 uses CSS, not two passes. With CSS, the phone shows `Menu` at once, and nothing changes after hydration.

### Why the Bug Ships

**The developer learns the two-pass render and uses it for every browser value.** Here is how it ships:
1. The greeting, the menu, and the saved settings all wait for `isClient`.
2. After the page loads, every one of those parts changes at once.
3. On a slow phone, the server's version stays on the screen for seconds before the switch.

The React docs warn about exactly this: "Use this pattern sparingly." Users with a slow connection see the server's version for a long time, possibly many seconds. A page whose every part changes after loading feels broken.

## PRINCIPLE | `suppressHydrationWarning`: the red error disappears, but the server's `Good morning` stays

> [!PRINCIPLE]
> **Principle 5: Escape Hatch: `suppressHydrationWarning` Silences One Element and Keeps the Server's Text**
>
> *Use `suppressHydrationWarning={true}` only on one element whose text or attribute cannot match, such as a timestamp; it works one level deep, React does not warn, and React does not patch the text, so the user keeps reading the server's version.*
>
> The prop is the one narrow answer to the question of what may differ: the text or attributes of one element, when the server's version is fine to keep. It removes the error, not the cause. For text that the user must read correctly, use the two-pass render of Principle 4.
>
> **DO THIS:**
> ```jsx
> <h1 ~suppressHydrationWarning={true}~>Current Date: {new Date().toLocaleDateString()}</h1> {/* A timestamp: the server's date is fine to keep */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <p ~suppressHydrationWarning={true}~>{greeting}, John</p> {/* **WRONG:** the Console is clean, but John reads Good morning at 6 PM */}
> ```

### The Prop That Silences One Element

**`suppressHydrationWarning` stops React from warning about one element. It does not fix the text of that element.** It is a boolean prop, true or false, that React DOM accepts on every built-in element. The React docs show it on a line with today's date:

```jsx title="The suppressHydrationWarning example from the React docs"
<h1 ~suppressHydrationWarning={true}~> {/* No hydration error for the text of this h1 */}
  Current Date: {new Date().toLocaleDateString()}
</h1>
```

The docs allow it only when "a single element's attribute or text content is unavoidably different between the server and the client". Their example of such a value is a timestamp. They also set a limit: "It only works one level deep, and is intended to be used as an escape hatch. Don't overuse it."

Two phrases in that limit need plain words:
- **One level deep** means the prop covers only the text and the attributes of that element itself. A `<span>` inside the element is not covered, so a mismatch inside the `<span>` still causes an error.
- An **escape hatch**, in the words of the React docs, is a way out of React's normal rules for a rare case. It is not the first fix to reach for.

### VS | The Two-Pass Render `isClient` vs. the Prop `suppressHydrationWarning`: the first fixes the greeting, the second only hides the error

**Both ways clear the red error, but only the two-pass render shows the right greeting.** Put the prop on our greeting, and compare it with the two-pass render of Principle 4:

```jsx title="The greeting with the two-pass render"
<p>{~isClient ? greeting : 'Hello'~}, John</p> {/* Hello first, then Good evening after hydration: no error */}
```

```jsx title="The greeting with suppressHydrationWarning"
<p ~suppressHydrationWarning={true}~>{greeting}, John</p> {/* No error, and the page keeps the server's Good morning */}
```

**It may look the same, since both clear the red error, but it is NOT the same thing!** Here is what happens with the prop:
1. The server sends `Good morning, John`.
2. The browser's first render gives `Good evening, John`.
3. React sees the prop and does not warn. The Console is clean.
4. React also does not change the text. The React docs: "React will **not** attempt to patch mismatched text content."
5. At 6 PM, John still reads `Good morning, John`.

```page width=full caption="John's phone after hydration with suppressHydrationWarning: the Console is clean, and the wrong greeting stays."
line: Good morning, John | bad
console: quiet
```

The two-pass render shows the browser's text. `suppressHydrationWarning` keeps the server's text and hides the warning. The first fixes the greeting, and the second only hides the problem.

```tree caption="The two-pass render and suppressHydrationWarning both remove the error, but only one shows the right greeting."
Two ways to remove the hydration error on the greeting
- +Two-pass render [`isClient` `useEffect`] | The first render **matches** the server | The line becomes **`Good evening, John`**
- !`suppressHydrationWarning` [`suppressHydrationWarning={true}`] | React **does not warn** and **does not patch** | The line stays **`Good morning, John`**
```

So the prop fits only where the server's version is fine to keep. A "last updated" time can stay as the server wrote it, a few seconds old. A greeting that says morning in the evening cannot.

### Why the Bug Ships

**The developer makes the Console clean and leaves the page wrong.** Here is how it ships:
1. A developer sees the hydration error on the greeting.
2. A search turns up `suppressHydrationWarning`.
3. The developer adds it, and the Console is clean.
4. Shoppers in other time zones read the wrong greeting all day.
5. Later, the developer puts the prop on `<main>` to silence a mismatch in a `<p>` inside it. The prop works only one level deep, so the error in the `<p>` stays.

### What Readers Expect, and What Really Happens

| Cause | What readers expect | What really happens | The fix |
| :--- | :--- | :--- | :--- |
| **The clock in render** | The browser corrects the server's greeting | The first render differs; React reports an error and rebuilds that part | Two-pass render with `isClient` set in an Effect |
| **`typeof window` in render** | The check makes the code safe on the server | The server renders the links, and the phone renders `Menu` | Render both parts and hide one with CSS |
| **A `<div>` inside a `<p>`** | The page looks right, so the HTML matches | The browser moves the `<div>` before React reads the page | Valid nesting, such as a `<span>`; nothing around the HTML of the root |
| **The two-pass render** | Read the browser's value as early as possible | The first render repeats the server; the browser's value comes after hydration | Use it sparingly: it costs a second render and a visible change |
| **`suppressHydrationWarning`** | The error is gone, so the page is fixed | React does not warn and keeps the server's text | Only for one unavoidable text or attribute, such as a timestamp |

Remember the one sentence of this lesson. **The browser's first render must give exactly the server's HTML. A value that only the browser knows waits until after hydration.**

## For the Interview

> **The Interview Question:** What causes hydration mismatches, and how do you fix them?

### How to Answer Clearly in 30 Seconds

"A hydration mismatch happens when the first render in the browser gives different output from the HTML the server sent. React expects the two to be identical, so that it can reuse the server's elements. When they differ, React logs one error with a diff in development and regenerates that part of the page in the browser. The user sees content change, and attributes may stay wrong.

The causes fall into three groups:
1. **Values that differ by moment or by place**, read during render: the time, `Date.now()`, `Math.random()`, the locale, or changing data without a snapshot sent with the HTML.
2. **Browser-only checks and APIs** in render: `typeof window`, `window.matchMedia`, `localStorage`.
3. **HTML the browser changes**: invalid nesting such as a `<div>` inside a `<p>`, extra whitespace inside the root, or a browser extension.

The fixes match the causes. CSS handles layout differences. A two-pass render, with a state variable set in an Effect, handles text that only the browser knows. Valid HTML handles the nesting. `suppressHydrationWarning` is only for one unavoidable value, such as a timestamp."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What is allowed to differ between the server render and the first browser render?"**
   **Nothing.** The React docs: "`hydrateRoot()` expects the rendered content to be identical with the server-rendered content." The one narrow exception is the text or attributes of one element marked with `suppressHydrationWarning`, and even there React keeps the server's version. After hydration, anything may change through a state update, which is why the two-pass render works.
2. **"Why not just add `suppressHydrationWarning` everywhere?"**
   Because it hides the warning, not the bug. React does not patch the text, so users keep reading the server's version. It works only one level deep, and the docs call it "an escape hatch. Don't overuse it." It fits a timestamp, where the server's value is fine to keep. It does not fit a greeting that must be correct.
3. **"How do you show a value from the browser, such as `localStorage` or the online status, on a server-rendered page?"**
   It depends on the value. A layout difference goes into CSS. Text from a browser API waits for an Effect, as in the two-pass render. A value read through a store can use `useSyncExternalStore` with `getServerSnapshot`, which gives the server and the first browser render the same fixed value (Lesson 53). IDs that must match on both sides come from `useId`, not from a counter (Lesson 52).

```tree caption="Interview summary: what a hydration mismatch is, what causes it, and how each cause is fixed."
Hydration mismatches
- !What it is | The first browser render **differs** from the server HTML | React logs an **error with a diff** and **regenerates** that part
- !What causes it | **Time, random, locale**; **`typeof window`** and browser-only APIs | **Invalid nesting**, whitespace in the root, browser extensions
- +How to fix it | **CSS** for layout; **two-pass render** for browser-only text | **Valid HTML**; `suppressHydrationWarning` only for **one timestamp**
```
