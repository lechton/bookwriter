# Lecture 79: How One Listener at the Root Runs Every onClick

*(Where does React really listen for your clicks?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How does React's SyntheticEvent delegator work at the root DOM container?

---

## VS | `addEventListener` on the button vs. `onClick` on the button: both run your function, only the first puts a listener on the button

> In plain JavaScript, `addEventListener` puts your function on the button itself, and the browser calls it right there. **In React, `onClick` puts no listener of yours on the button: one listener of React's, on the root `<div id="root">`, hears every click in the app.** That is why a listener on `document` runs after every `onClick`, and why your handler gets React's own event object, not the browser's.

Remember `addEventListener`? In plain JavaScript, you grab the button and hand your function to the browser. In React, you write `onClick` on the tag. Here are both, side by side:

```jsx title="Two ways to print Settings when the user clicks Settings"
const button = document.querySelector('button');
button.~addEventListener~('click', () => console.log('Settings')); // Plain JavaScript: the browser keeps our function on the button
<button ~onClick~={() => console.log('Settings')}>Settings</button> {/* React: our function goes to React, not to the button */}
```

Both print `Settings` when the user clicks. So it looks like both put a click listener on the button. **It may look the same, and it works the same, but it is NOT the same thing!**
1. **With `addEventListener`**, the browser keeps your function on the button. When the user clicks, the browser calls it right there.
2. **With `onClick`**, you hand your function to React, not to the browser. React builds the button from your JSX and keeps your function in its own memory. The browser never gets it.

So who hears the click? Remember bubbling (Lesson 11). A click starts on the clicked tag and travels up through every parent, to the top of the page. So every click inside your app passes `<div id="root">` on its way up. That is the `div` the entry file hands to `createRoot` (Lesson 07). React put its own listener on it. That listener hears the click, finds the `onClick` you wrote on the button, and calls your function.

You may already know this trick from plain JavaScript. To handle clicks on a list of 100 items, you do not add 100 listeners. You add one listener on the `<ul>`, and read `e.target` to know which item the user clicked:

```js title="Event delegation by hand, in plain JavaScript"
const list = document.querySelector('ul');
list.~addEventListener~('click', e => console.log(e.target.textContent)); // One listener on the list hears a click on any item
```

This trick has a name: **event delegation**. To delegate means to hand a job to someone else. Here, the items hand the job of listening to their parent. React does exactly this for your whole app, automatically. The root is the parent, and one listener of React's serves every `onClick` you write.

```tree caption="A listener added with addEventListener sits on the button; onClick hands our function to React, whose listener sits on the root."
Where the browser listener sits
- +With `addEventListener` on the button [`button.addEventListener`] | The browser keeps our function **on the button** | One button, **one listener**
- +With `onClick` on the button [`<button onClick>`] | React keeps our function and puts **no listener of ours** on the button | React's listener sits **once on `<div id="root">`** and serves **every `onClick`**
```

**Why:** Most of the time, you never notice where the listener sits, because the click works either way. The trouble starts when your React code and a plain browser listener hear the same click.

Take an account menu that must close when the user clicks anywhere else on the page. To hear "anywhere else", developers add a listener on `document`, the top of the page. Then the user clicks Settings, inside the menu, and the menu closes. There is no error in the Console. The listener on `document` ran after React had finished, and nothing told it that the click was inside the menu.

### The Four Facts of Event Delegation

Here are the words this lesson builds on. Three are reminders, and one is new:

> [!DEFINITION]
> **Bubbling and capture.** [REVIEW] When the user clicks a tag, the browser sends the click down from the top of the page to that tag, the capture phase, and then back up through every parent, the bubbling phase; `onClickCapture` belongs to the way down, and `onClick` to the way up (Lesson 11).

> [!DEFINITION]
> **The root.** [REVIEW] The root is the empty `<div id="root">` in `index.html`; `main.jsx` passes it to `createRoot`, and React renders the whole app inside it (Lesson 07).

> [!DEFINITION]
> **The event object.** [REVIEW] When the user clicks, React calls your handler and passes it an event object, usually named `e`; `e.target` is the tag the user clicked, `e.currentTarget` is the tag whose handler is running, and `e.stopPropagation()` stops the click from going further up (Lesson 11).

> [!DEFINITION]
> **Event delegation.** [NEW] Event delegation means that one listener on a parent handles the events of all its children: the event bubbles up to the parent, and the listener there finds out which child it came from; React delegates every event of your app to its own listeners on the root (Lesson 79).

From that one listener on the root, four facts follow. The whole lesson is about them:
1. **`onClick` puts no listener on its tag.** React keeps your function, and React's listener on the root calls it.
2. **`e` is React's object, not the browser's.** React builds it at the root. The browser's own event sits inside it, in `e.nativeEvent`.
3. **React copies the browser's order.** At the root, React calls the capture handlers from the top down, then the `onClick` handlers from the clicked tag up.
4. **A listener on `document` runs after React.** The click reaches `document` only after React has run every `onClick`.

### Where Readers Usually Go Wrong

Readers usually picture one chain of handlers, in the order of the tags. First the button's handler, then the menu's handler, then the listener on `document`, each one running as the click passes its tag. That chain does not exist. Here is what really happens:
1. The click travels all the way up to the root. No code of yours runs on the way.
2. At the root, React runs every `onClick`, one after another.
3. Only after that does the click go on to `<body>` and to `document`.

### The Rule of Thumb: every `onClick` runs while the click sits at the root

**React runs every `onClick` while the click sits at the root.** So a browser listener on a tag inside the root runs before React. And a browser listener above the root, such as one on `document`, runs after React.

## PRINCIPLE | `onClick`: React keeps your function, and one listener on the root calls it

> [!PRINCIPLE]
> **Principle 1: Event Delegation: React Listens at the Root, Not on Each Tag**
>
> *Writing `onClick` on a tag adds no listener of ours to that tag; React attaches its listeners to the root, the DOM node given to `createRoot`, and they serve every `onClick` in the app.*
>
> A click starts on the button and bubbles up through every parent to `<div id="root">`. React's listener waits there, finds the `onClick` functions on the clicked tag and its parents, and calls them. That is why DevTools shows the click listeners on the root, and why a thousand `onClick` props never hand the browser a thousand of our functions.
>
> **DO THIS:**
> ```jsx
> <div>
>   <button ~onClick={handleSettings}~>Settings</button> {/* React calls handleSettings from its listener on the root */}
>   <button onClick={handleSignOut}>Sign out</button>
> </div>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <div ~onClick={e => handleButton(e.target)}~> {/* **WRONG:** delegating by hand saves no listener, React already listens at the root */}
>   <button>Settings</button>
>   <button>Sign out</button>
> </div>
> ```

Start with the Settings button alone:

```jsx title="One button with onClick"
<button ~onClick~={() => console.log('Settings')}>Settings</button> {/* React keeps this function; the browser never gets it */}
```

The user clicks, and the Console prints `Settings`. You know that part from Lesson 11. The new question is this: which browser listener makes it happen, and where does it sit?

### Look for the listener in DevTools

The browser can show every listener on a tag. In DevTools, select a tag in the Elements panel, then open the **Event Listeners** tab next to Styles. By default, it also lists the listeners of every parent. So untick **Ancestors**, and you see only the listeners of the tag itself.

**The listener that runs our `onClick` is not on the Settings button. It is on `<div id="root">`.**
1. **Select the Settings button.** The tab shows one `click` entry, and its function is empty. React puts this empty function on every tag that has `onClick`, because Safari on iPhone does not bubble clicks from some tags without one. It does nothing, and our function is not in it.
2. **Select `<div id="root">`.** The tab shows three `click` entries, and all three belong to React. One is the same empty function, which React put on the root when it first added our app to the page. The other two are the listeners that `createRoot` added.

Those two listeners split the work of one click:
- **The capture listener** runs while the click travels down the page.
- **The bubbling listener** runs while the click comes back up. This is the one that runs our `onClick`.

The root also lists many other event names, such as `keydown` and `pointerdown`. React listens for every event it supports, whether or not a component uses it.

```dom caption="The Elements panel: the click listeners that run our onClick sit on div#root, not on the Settings button."
<body>
+ <div id="root"> | note: React's two click listeners, added by createRoot
    <main>
      <header>
        <div>
          <button>Menu</button>
          <div>
*           <button>Settings</button> | note: Only an empty function from React, never our own
            <button>Sign out</button>
          </div>
        </div>
      </header>
      <p>Welcome back, John</p>
    </main>
  </div>
</body>
```

### Where the listener on the root comes from

Nobody in our code wrote `addEventListener` on the root. React added it, on one line of the entry file. Here are the two files from Lesson 07, unchanged:

```html title="index.html"
<!DOCTYPE html>
<html lang="en">
  <body>
    <div ~id="root"~></div> <!-- The root: React renders our app inside it -->
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>
```

```jsx title="src/main.jsx"
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

const container = document.getElementById('root');
const root = ~createRoot(container)~; // React takes over this div, and listens for events on it
root.render(<App />);
```

Here is what that line does:
1. The entry file calls `createRoot` with `<div id="root">`.
2. React takes over the DOM inside that `div`.
3. Right then, before any component has rendered, React adds its listeners to that `div`. For `click`, it adds two: one for the capture phase and one for the bubbling phase.

So the root already listens for clicks before our menu even exists. Writing `onClick` on a tag adds no listener. It only gives React one more function to call when a click arrives at the root.

```tree dir=right caption="How a click on Settings reaches our function: the browser carries it up to the root, and React calls our onClick there."
How a click on Settings reaches our `onClick`
- +1. The user clicks Settings [`<button>Settings</button>`] | The browser starts the click event **on the button**
- +2. The click bubbles up [`div` `header` `main`] | The browser carries it **through every parent** | None of them has a listener of ours
- +3. React's listener on the root runs [`<div id="root">`] | React finds the `onClick` on the button | React **calls our function**, and the Console prints `Settings`
```

### The plain JavaScript habit that saves nothing in React

A developer who knows plain JavaScript reasons like this: every `addEventListener` adds one listener, so every `onClick` must add one too. To save listeners, they delegate by hand, as in the list at the start of this lesson. They remove the handler from each button, and put one `onClick` on the parent `div`. That one handler reads `e.target` to find the button.

In React, this saves nothing. React's listeners were on the root before the developer wrote a single `onClick`, and they stay the same. The code only hides which button does what. Keep one `onClick` on each button.

Remember: `onClick` gives your function to React, and React's one listener on the root calls it.

## PRINCIPLE | `e`: React builds its own event object, and the browser's event sits inside `e.nativeEvent`

> [!PRINCIPLE]
> **Principle 2: The React Event Object: The Browser's Event Lives in `e.nativeEvent`**
>
> *Our handler receives a React event object, also called a synthetic event, that React builds from the browser event; the browser's own event is `e.nativeEvent`, and its `currentTarget` is the root, while `e.currentTarget` is the tag whose handler React is calling.*
>
> React's object follows the browser's event standard and fixes some browser differences, so `e` works like a browser event. But the browser's listener really runs on `<div id="root">`, so the browser event inside reports the root as its `currentTarget`. Read the clicked tag from React's object.
>
> **DO THIS:**
> ```jsx
> function handleSettings(e) {
>   console.log(~e.currentTarget~); // The Settings button, the tag whose onClick React is calling
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleSettings(e) {
>   console.log(~e.nativeEvent.currentTarget~); // **WRONG:** logs <div id="root">, where the browser's listener runs
> }
> ```

Your handler receives `e`. It has the same fields and methods as the browser's event, such as `target` and `stopPropagation()`, so it looks like the browser's event. It is not. It is an object React built, and the browser's event sits inside it.

Log one `currentTarget` from each object:

```jsx title="Logging the two currentTarget values"
<button onClick={e => console.log(~e.currentTarget~, ~e.nativeEvent.currentTarget~)}>Settings</button> {/* Logs the button, then the root div */}
```

Both values are called `currentTarget`, and both come from one click. Yet the first is the Settings button, and the second is `<div id="root">`.

> [!DEFINITION]
> **React event object.** [NEW] The React event object is the `e` your handler receives: React builds it from the browser's event when the click reaches the root, React's docs also call it a synthetic event, and the browser's own event stays inside it as `e.nativeEvent` (Lesson 79).

Why "synthetic"? In everyday life, synthetic means made by people, like a synthetic fabric. The browser creates the native event. React makes this one, from the browser's event.

React's object follows the same standard as the browser's events, so code written for browser events works with it. It also fixes some differences between browsers. In TypeScript, its base type is `React.SyntheticEvent`, and that is where the interview question gets its name. Lesson 91 shows how to type it.

**`e.nativeEvent`** is the browser's original event. React keeps it inside its own object, in case your code ever needs it. Most code never does.

```tree caption="One click, two event objects: the React event object our handler receives, and the browser event inside it."
What our handler receives when the user clicks Settings
- +The React event object [`e`] | Built **by React** from the browser event | `e.currentTarget` is **the Settings button**, the tag whose handler React is calling
- +The browser event inside it [`e.nativeEvent`] | Created **by the browser** for the click | `e.nativeEvent.currentTarget` is **`<div id="root">`**, where the browser's listener runs
```

### The menu logs both values

Now the Settings button gets a named handler, `handleSettings`, that logs both values. Only the menu file changes:

```jsx title="src/AccountMenu.jsx" startLine="3"
export default function AccountMenu() {
  const [open, setOpen] = useState(false);

  function handleSettings(e) {
    console.log(~e.currentTarget~, ~e.nativeEvent.currentTarget~); // Logs the Settings button, then <div id="root">
  }

  return (
    <div>
      <button onClick={() => setOpen(!open)}>Menu</button>
      {open && (
        <div>
          <button onClick={~handleSettings~}>Settings</button> {/* React passes its own event object to handleSettings */}
          <button>Sign out</button>
        </div>
      )}
    </div>
  );
}
```

The user opens the menu and clicks Settings. The Console shows the button first and the root second:

```devconsole caption="The Console after the user clicks Settings: e.currentTarget is the button, and e.nativeEvent.currentTarget is the root div."
+ <button>Settings</button> <div id="root">…</div> | AccountMenu.jsx:7
```

### Why the two values differ

**`currentTarget` names the tag whose listener is running. For the browser, that is the root. For React, that is the button.** Here is the click, in order:
1. The user clicks Settings.
2. The browser event bubbles from the button up to `<div id="root">`. No code of ours runs on the way.
3. React's listener on the root runs. For the browser, this is the listener running right now, so it sets its own `currentTarget` to `<div id="root">`.
4. React builds its event object from the browser event. It finds the `onClick` on the Settings button and sets `e.currentTarget` to that button, the value our code expects.
5. React calls `handleSettings(e)`.

What about `e.target` and `e.nativeEvent.target`? **Yes, they are the exact same node!** Both are the Settings button, the tag the user clicked. Only `currentTarget` differs.

`e.nativeEvent` can also be a different kind of event. React's docs give an example. In an `onMouseLeave` handler, the browser event inside is a `mouseout` event. The docs add that this mapping is not part of the public API and may change. So do not build code on it.

### The mistake: reading the button from the browser's event

A developer reads that `e.nativeEvent` is "the real event", and trusts it more than React's object. To find the clicked button, they read `e.nativeEvent.currentTarget`. They get `<div id="root">`. Any data they read from it next, such as the button's label, comes from the root `div` instead. The fix is `e.currentTarget`, the value React sets for our code.

Remember: `e` is React's object, built at the root, and the browser's event is inside it.

## PRINCIPLE | `onClick` order: React calls the clicked tag's handler first, then each parent's, along the React tree

> [!PRINCIPLE]
> **Principle 3: Propagation: React Copies the Browser's Order Along the React Tree**
>
> *React calls the capture handlers from the top of the React tree down to the clicked tag, then the `onClick` handlers from the clicked tag up, so the order matches the browser's; it walks the React tree, not the DOM tree.*
>
> The browser only calls React's listeners on the root. React then visits each tag of the React tree on the way up from the clicked button, and calls its `onClick`. On most pages the two trees match, so the order is the familiar one. A portal shows the difference: its clicks reach its React parent. `onScroll` is the one event that does not walk up.
>
> **DO THIS:**
> ```jsx
> <div onClick={() => console.log('menu')}>
>   <button onClick={e => { ~e.stopPropagation()~; handleSettings(e); }}>Settings</button> {/* React calls no onClick above the button */}
> </div>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <div ~onScroll~={() => console.log('scrolled')}> {/* **WRONG:** onScroll does not propagate, so this never runs when the list scrolls */}
>   <ul className="notifications">{notifications}</ul>
> </div>
> ```

Put an `onClick` on the Settings button, and another on the `div` around it:

```jsx title="An onClick on the button and on its parent div"
<div ~onClick~={() => console.log('menu')}> {/* Runs second */}
  <button ~onClick~={() => console.log('Settings')}>Settings</button> {/* Runs first */}
</div>
```

The user clicks Settings. The Console prints `Settings`, then `menu`. The button's handler runs first, then the parent's, exactly as with browser bubbling (Lesson 11).

So for the order, **yes, it is the exact same thing!** But for who walks the click up, **it is NOT the same thing!** The browser never calls the parent's `onClick`, because the parent `div` has no listener of ours. React calls it.

### React's walk, at the root

Principle 1 found two click listeners on the root, one for each phase. React uses both to copy the browser's three steps:
1. **The capture phase, on the way down.** The browser sends the click down from the top of the page toward the button, and it passes the root first. React's capture listener runs. React calls every `onClickCapture`, from the top of the React tree down to the button.
2. **At the button.** The browser event reaches the Settings button. No code of ours runs here.
3. **The bubbling phase, on the way up.** The browser event bubbles back up and reaches the root. React's bubbling listener runs. React calls every `onClick`, from the button up to the top.

React finds these handlers in the **React tree**, the tree of our components and their tags (Lesson 06), not in the browser's DOM. On our page, the two trees have the same shape, so the order is the same.

A portal shows the difference. Its DOM nodes can sit in `document.body`, outside the root (Lesson 51). Yet a click inside a portal still reaches the `onClick` of its React parent. React's docs say that events from portals propagate according to the React tree, rather than the DOM tree.

```tree dir=right caption="A click on Settings: the browser carries it down and up, and React calls the handlers each time the click passes the root."
How React runs the handlers for one click on Settings
- +1. Capture phase, at the root [`onClickCapture`] | React's capture listener runs | React calls capture handlers **from the top down**
- +2. At the button [`<button>Settings</button>`] | The browser event reaches **the clicked tag** | No code of ours runs here
- +3. Bubbling phase, at the root [`onClick`] | React's bubbling listener runs | React calls `onClick` **from the button up**: `Settings`, then `menu`
```

### The menu shows the walk

For this step only, the outer `div` of the menu gets an `onClick` that logs the word menu. Only the menu file changes:

```jsx title="src/AccountMenu.jsx" startLine="10"
  return (
    <div ~onClick~={() => console.log('menu')}> {/* React calls this after the handler of any button inside */}
      <button onClick={() => setOpen(!open)}>Menu</button>
      {open && (
        <div>
          <button onClick={handleSettings}>Settings</button>
          <button>Sign out</button>
        </div>
      )}
    </div>
  );
```

The user clicks Menu, then Settings. The first `menu` line comes from the click on Menu, because the Menu button sits inside the menu `div` too. The next two lines come from the click on Settings:

```devconsole caption="The Console after the user clicks Menu and then Settings: on each click, the button's handler runs first and the menu div's handler second."
+ menu | AccountMenu.jsx:11
+ <button>Settings</button> <div id="root">…</div> | AccountMenu.jsx:7
+ menu | AccountMenu.jsx:11
```

**Here is the surprise: by the time either handler runs, the browser event has already passed the menu `div`, and sits at the root.** The order still looks like bubbling, because React walks the React tree from the button up, one tag at a time:
1. The user clicks Settings.
2. The browser event bubbles from the button through both `div` tags of the menu, the header, and `main`, up to the root. No code of ours runs on the way.
3. React's bubbling listener on the root runs.
4. React starts at the Settings button and calls `handleSettings`. The Console prints the two targets.
5. React moves up the React tree to the menu `div`, and calls its `onClick`. The Console prints `menu`.

### `e.stopPropagation()` stops React's walk

Calling `e.stopPropagation()` in a handler stops this walk. React's docs say it stops the event propagation through the React tree. So React calls no `onClick` above that handler.

### The one event that does not walk up: `onScroll`

React's docs say that all events propagate in React, except `onScroll`. It works only on the JSX tag you attach it to. So an `onScroll` on a parent `div` never runs when a list inside it scrolls.

Remember: the order is the browser's, but React does the walking, at the root, along the React tree.

## PRINCIPLE | `document.addEventListener`: the listener runs after every `onClick`, unless a React handler stops the click

> [!PRINCIPLE]
> **Principle 4: React and the Browser: A `document` Listener Runs After Every React Handler**
>
> *A browser listener on `document` hears a click only after the browser event has left the root, so it runs after every React handler; a React handler that calls `e.stopPropagation()` keeps the click from reaching it.*
>
> React runs every `onClick` while the browser event sits at `<div id="root">`. `document` sits above the root, so its listener runs last. Stop the click on the `div` that holds the whole menu, or let it through and check with `contains()` whether it happened inside the menu.
>
> **DO THIS:**
> ```jsx
> <div onClick={e => ~e.stopPropagation()~}> {/* Every click inside the menu stops here, before document */}
>   <button onClick={() => setOpen(!open)}>Menu</button>
>   {open && <button onClick={handleSettings}>Settings</button>}
> </div>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <div>
>   <button onClick={e => { ~e.stopPropagation()~; setOpen(!open); }}>Menu</button> {/* **WRONG:** a click on Settings still reaches document and closes the menu */}
>   {open && <button onClick={handleSettings}>Settings</button>}
> </div>
> ```

The menu must close when the user clicks anywhere outside it. No React tag covers "anywhere", because the click can land outside our component. So developers listen on `document`, the top of the page. An Effect adds the listener while the menu is open, and its cleanup removes it (Lesson 32):

```jsx title="Closing the menu on any click on the page"
useEffect(() => {
  if (!open) return;
  function handleDocumentClick() {
    setOpen(false);
  }
  ~document.addEventListener~('click', handleDocumentClick); // A browser listener, outside React
  return () => document.removeEventListener('click', handleDocumentClick);
}, [open]);
```

**The listener on `document` always runs last, after every React handler.** `document` sits above `<body>`, and so above the root. A click on Settings bubbles up to the root first, where React runs every `onClick`. Only after that does it go on to `<body>`, and then to `document`.

### The Effect alone: the menu never opens

Add the Effect to the menu, and drop the `menu` log from Principle 3:

```jsx title="src/AccountMenu.jsx"
import { useEffect, useState } from 'react';

export default function AccountMenu() {
  const [open, setOpen] = useState(false);

  useEffect(() => {
    if (!open) return;
    function handleDocumentClick() {
      setOpen(false);
    }
    ~document.addEventListener~('click', handleDocumentClick); // Hears every click that leaves the root
    return () => document.removeEventListener('click', handleDocumentClick);
  }, [open]);
```

The user clicks Menu. **Nothing opens.** The list opens and closes again during the same click, so the user never sees it:

```page width=text caption="After the user clicks Menu with only the document listener added: the list never appears."
line: [Menu] | bad
line: Welcome back, John
console: quiet
```

The click that opens the menu also adds the listener, and then that same click reaches the new listener:
1. The user clicks Menu.
2. The browser event bubbles up to the root. React calls the `onClick` of the Menu button, which calls `setOpen(true)`.
3. React renders the open list. When a click changes state, React also runs the Effects of that render right away, before the browser has finished with the click.
4. Our Effect runs, now that `open` is true, and adds the listener on `document`.
5. The same click goes on from the root to `<body>`, and then to `document`. The brand-new listener hears it and calls `setOpen(false)`.
6. React renders the closed menu. The user saw nothing.

Step 3 is new since React 18. React's upgrade guide says that React now always flushes effect functions synchronously, if a discrete user input event such as a click triggered the update.

### `e.stopPropagation()` on the Menu button: now Settings closes the menu

The click must not reach `document`. A React handler can stop it. In React, `e.stopPropagation()` stops React's walk, and it also stops the browser event, which at that moment sits at the root. Since `document` sits above the root, the click never reaches it.

A first try puts `e.stopPropagation()` on the Menu button only:

```jsx title="src/AccountMenu.jsx" startLine="19"
  return (
    <div>
      <button onClick={e => { ~e.stopPropagation()~; setOpen(!open); }}>Menu</button> {/* The opening click never reaches document */}
      {open && (
        <div>
          <button onClick={handleSettings}>Settings</button>
          <button>Sign out</button>
        </div>
      )}
    </div>
  );
```

Now the menu opens:

```page width=text caption="With e.stopPropagation on the Menu button only, after the user clicks Menu: the menu opens and shows Settings and Sign out."
line: [Menu]
line: [Settings] [Sign out]
line: Welcome back, John
console: quiet
```

Then the user clicks Settings, and **the menu closes**. This is the bug from the start of the lesson:

```page width=text caption="The same page right after the user clicks Settings: the list is gone, though the click was inside the menu."
line: [Menu]
line: Welcome back, John | bad
log: <button>Settings</button> <div id="root">…</div> | AccountMenu.jsx:16
```

Nothing stopped the click on Settings:
1. The user clicks Settings, inside the open menu.
2. The browser event bubbles up to the root. React calls `handleSettings`, which logs the two targets.
3. No handler on the way calls `e.stopPropagation()`. The one on the Menu button is not on the path of this click.
4. The browser event goes on to `<body>` and to `document`. The listener on `document` calls `setOpen(false)`.
5. The list closes, though the user clicked inside it.

A click on Sign out closes the menu the same way. You could add `e.stopPropagation()` to Settings, then to Sign out, then to every future button. That chase never ends.

### `e.stopPropagation()` on the whole menu

The fix is one `e.stopPropagation()` on the `div` that holds the whole menu: the Menu button and the list. In React's walk, every click inside the menu reaches that `div`, so React stops every one of them there. Only the menu file changes:

```jsx title="src/AccountMenu.jsx" startLine="19"
  return (
    <div onClick={e => ~e.stopPropagation()~}> {/* No click inside the menu reaches document */}
      <button onClick={() => setOpen(!open)}>Menu</button>
      {open && (
        <div>
          <button onClick={handleSettings}>Settings</button>
          <button>Sign out</button>
        </div>
      )}
    </div>
  );
```

The user clicks Menu, and the list opens. The user clicks Settings, and the list stays open:

```page width=text caption="With e.stopPropagation on the menu div, after the user clicks Settings: the list stays open."
line: [Menu]
line: [Settings] [Sign out] | good
line: Welcome back, John
log: <button>Settings</button> <div id="root">…</div> | AccountMenu.jsx:16
```

Then the user clicks `Welcome back, John`, and the list closes. That line sits outside the menu `div`, so nothing stops its click, and the click reaches `document`:

```page width=text caption="The same page after the user then clicks Welcome back, John: the list closes."
line: [Menu]
line: Welcome back, John | good
log: <button>Settings</button> <div id="root">…</div> | AccountMenu.jsx:16
```

It is the same call in two places, and only one place covers every click:
- **With `e.stopPropagation()` on the Menu button**, React stops only the opening click. A click on Settings or Sign out reaches `document` and closes the menu.
- **With `e.stopPropagation()` on the menu `div`**, React stops every click inside the menu, because every one of them reaches that tag in React's walk.

### A browser listener inside the root runs before React

A browser listener can also sit on a tag inside the root. You add it with `addEventListener`, through a ref (Lesson 31). That listener runs before every `onClick`, because the click passes the tag on its way up, before it reaches the root. When a React handler later calls `e.stopPropagation()`, that listener has already run. React cannot stop it.

So where a browser listener sits decides when it hears the click:

```tree caption="Where a browser listener sits decides when it hears a click, compared with React's onClick handlers."
When a browser listener hears a click on Settings
- +On a tag inside the root [`addEventListener` through a ref] | The click passes the tag **before** it reaches the root | Runs **before every `onClick`**; `e.stopPropagation` in React **cannot stop it**
- +On `<div id="root">` [React's listeners] | React runs **every `onClick`** here | `e.stopPropagation` stops React's walk **and the browser event**
- !On `document` [`document.addEventListener`] | The click arrives **after** it has left the root | Runs **after every `onClick`**; never runs if a React handler stopped the click
```

### The second way: let the click through, and check where it happened

`e.stopPropagation()` on the menu `div` hides every click inside the menu from every listener above the root. That fits when no other code on the page needs those clicks. But sometimes other code must hear every click, such as analytics that count what users press. Then let the click through, and make the `document` listener check where the click happened.

The menu `div` gets a ref, `menuRef` (Lesson 31). The browser method `contains()` tells you whether one node sits inside another. The listener closes the menu only when the clicked tag is not inside the menu:

```jsx title="src/AccountMenu.jsx with a contains check instead of e.stopPropagation"
import { useEffect, useRef, useState } from 'react';

export default function AccountMenu() {
  const [open, setOpen] = useState(false);
  const menuRef = useRef(null);

  useEffect(() => {
    if (!open) return;
    function handleDocumentClick(e) {
      if (~menuRef.current.contains(e.target)~) return; // A click inside the menu: keep it open
      setOpen(false);
    }
    document.addEventListener('click', handleDocumentClick);
    return () => document.removeEventListener('click', handleDocumentClick);
  }, [open]);

  function handleSettings(e) {
    console.log(e.currentTarget, e.nativeEvent.currentTarget);
  }

  return (
    <div ~ref={menuRef}~> {/* No e.stopPropagation: every click still reaches document */}
      <button onClick={() => setOpen(!open)}>Menu</button>
      {open && (
        <div>
          <button onClick={handleSettings}>Settings</button>
          <button>Sign out</button>
        </div>
      )}
    </div>
  );
}
```

For the user, the page behaves the same. The menu opens, stays open on a click on Settings, and closes on a click on the welcome line. The opening click on Menu also reaches the new listener. But its `e.target` is the Menu button, which sits inside the menu, so the listener ignores it.

### VS | `e.stopPropagation()` on the menu vs. a `contains()` check: the same page, but different listeners hear the click

**It looks the same on the page, but it is NOT the same thing in the code!**
- **With `e.stopPropagation()` on the menu `div`**, React stops the click at the root. No listener above the root ever hears a click inside the menu.
- **With the `contains()` check in the `document` listener**, every click gets through. Every listener on the page hears it, and only the menu's own listener decides to ignore it.

Remember: a listener on `document` runs after every `onClick`, so stop the click on the whole menu, or check where it happened.

    if (!open) return;
    function handleDocumentClick() {

      <button onClick={() => setOpen(!open)}>Menu</button>

        <div>
          <button ~onClick~={handleSettings}>Settings</button> {/* Principle 1: no listener of ours on this button */}

        </div>
      )}
    </div>

### The order of one click on Settings

When the user clicks Settings in the open menu, the browser and React take turns in this order:

```tree dir=right caption="One click on Settings in the finished menu: who runs, in which order, and where the click stops."
One click on Settings
- +1. Capture phase, at the root [React's capture listener] | React looks for `onClickCapture` | There is none, so nothing of ours runs
- +2. Bubbling phase, at the root [React's bubbling listener] | React calls `handleSettings`, then the `onClick` of the menu `div` | The Console logs the button and the root; the `div` calls `e.stopPropagation`
- !3. `document` [`handleDocumentClick`] | The browser event **never arrives** | The menu **stays open**
```

### What developers expect, and what React really does

| Principle | What a developer expects | What React really does |
| :--- | :--- | :--- |
| **1. The listener sits on the root** | `onClick` adds a click listener to the Settings button | React's listener on `<div id="root">` hears the click and calls our function |
| **2. `e.nativeEvent`** | `e` is the browser's click event | `e` is React's event object; the browser event is `e.nativeEvent`, whose `currentTarget` is the root |
| **3. React's walk** | The browser calls the parent's `onClick` as the click passes the parent | React calls each `onClick` from the button up the React tree, after the click has reached the root |
| **4. The `document` listener** | All handlers run in one chain, in the order of the tags | A listener on `document` runs after every React handler, unless a React handler stopped the click |

Remember the one sentence of this lesson. **`onClick` puts no listener on its tag. React's one listener on the root runs every `onClick`, and only then does the click go on to `document`.**

## For the Interview

> **The Interview Question:** How does React's SyntheticEvent delegator work at the root DOM container?

### How to Answer Clearly in 30 Seconds

"React does not put a listener on each tag that has `onClick`. When `createRoot` runs, React attaches its event listeners to the root container, the `<div id="root">`. That is event delegation: every click bubbles up from the clicked tag to the root, and React's listener there handles all of them.
1. **The event object:** React builds a React event object, also called a synthetic event, from the browser event. It follows the browser's event standard and fixes some browser differences. The browser's own event is `e.nativeEvent`.
2. **Propagation:** inside its root listeners, React copies the browser's order. It calls `onClickCapture` from the top down, then `onClick` from the clicked tag up, along the React tree. `e.stopPropagation()` stops that walk.
3. **The edge:** browser listeners above the root, such as one on `document`, run after every React handler. So a menu that closes on outside clicks needs `e.stopPropagation()` on the menu, or a `contains()` check."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"If a list has ten thousand rows, each with `onClick`, does the browser get ten thousand click listeners?"**
   Not ten thousand of ours. React's click listeners sit on the root before the first row renders, and none of our row functions goes to the browser. Each row gets only the same empty function from React, which runs no code. That is the whole point of delegation. The cost that remains is React's own work: each render creates the handler functions for the rows. Large lists are a question of rendering, not of listeners (as seen in Lessons 54 and 62).
2. **"Why can `e.currentTarget` and `e.nativeEvent.currentTarget` be different?"**
   Because two different listeners are running. For the browser, the running listener is React's, on the root, so the `currentTarget` of the browser event is `<div id="root">`. React then calls the handler of one specific tag, and sets `e.currentTarget` on its own object to that tag. React's docs say the React event reflects "the values your React code expects".
3. **"Where did React attach its listeners before React 17, and why did it move them?"**
   Before React 17, React attached its listeners to `document`. React 17 moved them to the root container. With listeners on `document`, a React handler's `e.stopPropagation()` came too late to stop other `document` listeners. Two React apps on one page also shared the same listeners. With listeners on each root, every root handles its own events. So a page can hold several React roots, even of different React versions, without mixing their events.
