# Lecture 76: What a JSX Tag Becomes

*(What does `<h1>Hello</h1>` turn into, before React puts anything on the page?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | What does JSX compile into, and what is an element object?

---

## VS | A JSX tag vs. the real `<h1>` on the page: the tag is a plain object that only describes the heading

> In plain JavaScript, `document.createElement('h1')` gives you a real heading, an element you can fill with text and add to the page. **In React, a JSX tag such as `<h1>Hello</h1>` is a function call that returns a plain JavaScript object, a React element, which only describes the heading.** React reads that object later and creates the real heading itself, so the object in your hands is a description, not the heading.

You write JSX every day: `<h1 className="greeting">Hello</h1>`. It looks like HTML, so it is easy to believe that this line creates a heading. **It does not. The browser cannot even read JSX.** Before your file reaches the browser, the build tool, Vite, rewrites every tag as a function call (Lesson 07).

Here is the same heading, written as a tag and as the call that React documents:

```jsx title="The same heading, written as a JSX tag and as a createElement call"
import { createElement } from 'react';

const withJsx = ~<h1 className="greeting">Hello</h1>~; // What you write
const byHand = ~createElement('h1', { className: 'greeting' }, 'Hello')~; // What it means: the exact same object
```

Watch the name. React's `createElement` is not the browser's `document.createElement`. They share a name, and they do very different jobs:
1. **The browser's `document.createElement('h1')`** creates a real `<h1>` element. It has methods such as `focus` and `append`.
2. **React's `createElement('h1', ...)`** creates a plain object that says "a heading, with this class, with this text". No element exists yet.

So who puts the heading on the page? React does. Your component returns the object, React reads it, and React creates the real `<h1>` during the commit (Lesson 13).

**Why:** As long as you see a tag as the real element, three bugs look like magic:
1. You call `focus` on a tag kept in a variable. JavaScript throws a `TypeError`, and the cursor never reaches the `<input>` field.
2. You change the text inside an element after creating it. In development, JavaScript throws a `TypeError`, and the page goes blank.
3. You show an object that came from a server as if it were an element. React throws `Objects are not valid as a React child`, and the page goes blank again.

Once you see the tag as an object, each of these bugs has a plain reason.

### One Tag, Opened in the Console

Let's look at that object. Put one tag in a variable, and log it:

```jsx title="One JSX tag, stored in a variable and logged"
const title = ~<h1 className="greeting">Hello</h1>~; // Puts nothing on the page
console.log(title); // Prints the object below in the Console
```

```devconsole caption="The Console after the two lines above run: one object, opened with its small triangle."
v {$$typeof: Symbol(react.transitional.element), type: 'h1', key: null, props: {…}, _owner: null, …}
  $$typeof: Symbol(react.transitional.element) | Marks the object as a real React element
  key: null | No key was written on the tag
  props: {className: 'greeting', children: 'Hello'} | The attribute, and the text between the tags
  type: "h1" | The tag name, as a string
  _owner: null | Added by React in development
  _store: {validated: 0} | Added by React in development
  ref: null | No ref on the tag; React 19 keeps a ref in props
  _debugInfo: null | Added by React in development
  _debugStack: Error: react-stack-top-frame | Added by React in development
  _debugTask: {run: ƒ} | Added by React in development
```

No heading appears on the page. The Console shows no HTML and no element of the page. It shows an object.

> [!DEFINITION]
> **A React element.** [REVIEW] A React element is the plain JavaScript object that a JSX tag returns. React's docs call it "a lightweight description of a piece of the user interface".
> `<h1>Hello</h1>` describes a heading that says Hello. It is not the heading.
> You first logged one when the Console showed an object with `type` and `props` (Lesson 02).

Four fields of this object matter in this lesson:
1. **`type`** says what to draw. Here it is the string `'h1'`, a built-in tag.
2. **`props`** holds the attributes. Under `children`, it holds whatever sits between the tags (Lesson 09).
3. **`key`** holds the key written on the tag, or `null` when there is none.
4. **`$$typeof`** marks the object as a real React element. You never write it. React puts it there.

The other fields are for React itself. In development, React adds fields whose names start with an underscore, such as `_owner`, `_store`, and `_debugStack`. Your code never reads them. The `ref` field stays `null`, because React 19 keeps a ref inside `props`.

### The Rule of Thumb: the tag describes, React builds

**A JSX tag is a function call that returns a plain object. Writing the tag puts nothing on the page. React reads the object later, and decides what to create.**

```tree dir=right caption="A JSX tag becomes a plain object that describes the screen; React creates the real DOM node later."
What `<h1 className="greeting">Hello</h1>` becomes
- +1. The JSX tag [`<h1 className="greeting">Hello</h1>`] | What **you write** in the file | The build turns it into **a function call**
- +2. The React element [`type` `props` `key` `$$typeof`] | A **plain object** that the call returns | It **describes** the heading; nothing is on the page yet
- +3. The DOM node [`<h1 class="greeting">`] | Created **by React during the commit** | Only for an element that **reaches React**
```

A senior developer also knows the three classic mistakes:
1. **Avoiding JSX in a variable.** Developers think a tag creates an element or runs the component, so they avoid keeping JSX in a variable or building it in a helper function. React's docs answer: "Creating elements is extremely cheap so you don't need to try to optimize or avoid it."
2. **Reading `key` inside the component.** It gives `undefined` (Lesson 18).
3. **Changing the props of an element.** For example, changing the `children` a component received, instead of making a new element.

The rest of the lesson shows each one on a real page.

## SECTION | The Comment List Under an Article

Our page is the comment list under an article. Everyone has read one: a heading, and one line per comment.

```page width=text caption="The comment list under an article: a heading and two comments."
heading: Comments
line: John: Great article!
line: Mia: Me too!
```

Developers build lists like this every day, and this is where the element stops being theory. When a comment does not show, or shows the wrong text, the developer opens the Console and reads elements. Every row carries a `key`, and the comments arrive from a server as JSON. So this one page touches every field of the element.

The project has four files:


`main.jsx` mounts `App` inside `<StrictMode>`, and `App` renders the list:

```jsx title="src/main.jsx"
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>

```

```jsx title="src/App.jsx"
import CommentList from './CommentList.jsx';

export default function App() {
  return <CommentList />;
}
```

`Comment` shows the author in bold, then the text. Its `console.log` tells us each time React calls it:

```jsx title="src/Comment.jsx"
export default function Comment({ author, text }) {
  ~console.log('Comment rendered:', author);~ // Prints one line each time React calls Comment
  return <p><b>{author}</b>: {text}</p>;
}
```

`CommentList` holds the two comments. With `map`, it makes one `<Comment />` element for each (Lesson 18):

```jsx title="src/CommentList.jsx"
import Comment from './Comment.jsx';

const comments = [
  { id: 1, author: 'John', text: 'Great article!' },
  { id: 2, author: 'Mia', text: 'Me too!' },
];

export default function CommentList() {
  return (
    <section>
      <h2>Comments</h2>
      {comments.map(c => (
        ~<Comment key={c.id} author={c.author} text={c.text} />~ // One element for each comment
      ))}
    </section>
  );
}
```

The page shows the heading and the two comments. The Console prints two lines for each comment, because in development `<StrictMode>` calls each component twice (Lessons 14 and 47):

```page width=text caption="The working comment list: the heading, two comments, and two Console lines for each comment."

line: Mia: Me too!

log: Comment rendered: Mia | Comment.jsx:2
log: Comment rendered: Mia | Comment.jsx:2
```

Each principle below changes `CommentList.jsx` for one experiment, and then puts it back.

**PRINCIPLES:** A JSX tag is a call that returns a plain object. React reads the object later, and only the objects React receives reach the page. Five principles follow:
1. **Principle 1: A JSX Tag and createElement Build the Same Element.** The build tool turns every tag into a function call. The tag name, the attributes, and what sits between the tags become its arguments.
2. **Principle 2: A Comment Kept in a Variable Never Reaches the Page.** Creating an element does not call the component and does not create a DOM node. The element has none of the methods of a DOM node.
3. **Principle 3: key Leaves props for the Element.** React takes `key` out of `props`, turns it into a string, and keeps it on the element. The component never receives it.
4. **Principle 4: A Frozen Element Rejects New Text.** In development, React freezes every element, so an assignment throws. New text needs a new element.
5. **Principle 5: A JSON Copy Loses $$typeof.** JSON cannot hold a `Symbol`, so an object rebuilt from JSON is not an element, and React refuses to render it.

## PRINCIPLE | JSX tag: a function call that returns the same element as `createElement`

> [!PRINCIPLE]
> **Principle 1: The JSX Transform: A JSX Tag and createElement Build the Same Element**
>
> *Before the browser gets the file, a build tool turns every JSX tag into a function call; `createElement(type, props, ...children)` is the call React documents, and it gives the exact same element as the tag.*
>
> The browser cannot read JSX, so Vite rewrites each tag before the file reaches it. The tag name becomes `type`, the attributes become `props`, and whatever sits between the tags becomes the children. A capital letter keeps the name as your function. A lowercase letter turns it into a string, which React reads as a built-in HTML tag.
>
> **DO THIS:**
> ```jsx
> ~<Comment author="John" text="Great article!" />~ // type is our Comment function, so React calls Comment
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~<comment author="John" text="Great article!" />~ // **WRONG:** type is the string 'comment', so Comment never runs!
> ```

Here is a component tag from React's docs, written both ways:

```jsx title="A component tag written with JSX and with createElement"
<Greeting name="Taylor" /> {/* Written with JSX */}
~createElement(Greeting, { name: 'Taylor' })~ // Written by hand: the same element
```

React's docs say that both lines "produce an object like this": one and the same element. Each part of the tag lands in one argument of the call:
1. **The tag name becomes the first argument, `type`.** Here it is our function `Greeting` itself, not called.
2. **The attributes become the second argument, `props`.** Here it is the object with `name`.
3. **Whatever sits between the opening and the closing tag becomes the rest of the arguments, the children.** `<Greeting />` closes itself, so it has none. In the heading of the opening, the text `'Hello'` was the third argument.

```tree dir=right caption="Each part of a JSX tag lands in one argument of createElement."
How a tag maps onto `createElement`
- +1. The tag name [`h1` `Greeting`] | Becomes the **first argument**, `type` | A **string** for a built-in tag, **your function** for a component
- +2. The attributes [`className="greeting"` `name="Taylor"`] | Become the **second argument**, `props` | One object, as in Lesson 08
- +3. Between the tags [`Hello`] | Become **the rest of the arguments** | React stores them in `props.children`
```

### VS | `<Comment />` vs. `<comment />`: your function or a built-in tag name

You already follow the capital-letter rule (Lesson 04). Now you can see where it comes from. The first letter decides what goes into `type`:

```jsx title="A capital first letter and a lowercase first letter"
<Comment /> {/* Becomes createElement with Comment as type: React calls your function */}
~<comment />~ // Becomes createElement with the string 'comment' as type: a built-in HTML tag
```

With a capital letter, `type` holds your function `Comment`. With a lowercase letter, `type` holds the string `'comment'`. React's docs say the lowercase name becomes a string, "so it will be treated as a built-in HTML tag." React never calls your `Comment` function for it.

### Why two tags side by side need a wrapper

The same fact explains another rule you follow: a component returns one root tag (Lesson 02). Each tag is one function call, and each call returns one object. Two tags side by side are two objects, with nothing to hold them:

```jsx title="Two tags with no wrapper, and the same two tags inside a section"
const withoutWrapper = ~<h2>Comments</h2><p>John: Great article!</p>~; // **WRONG:** two objects side by side: the build stops with an error
const withSection = <section><h2>Comments</h2><p>John: Great article!</p></section>; // One object, with the heading and the line as its children
```

A JavaScript function cannot return two values either. React's docs give the reason: JSX "is transformed into plain JavaScript objects. You can't return two objects from a function without wrapping them into an array." A parent tag, such as `<section>`, or a Fragment `<>...</>`, turns the two objects into the children of one object.

### Who writes the call: the JSX transform

You never write the call yourself. Vite writes it, every time it builds the file (Lessons 02 and 07).

> [!DEFINITION]
> **The JSX transform.** [NEW] The JSX transform is the step of the build that rewrites every JSX tag as a function call, before the browser gets the file.
> React's docs call JSX "a syntax extension": an addition to JavaScript that the browser does not understand. So the browser never sees a single tag.
> The docs also say that "JSX and React are two separate things": React works without JSX, as the `createElement` version below shows (Lesson 76).

In development, the call that Vite writes is `_jsxDEV` (Lesson 02). It comes from a module of React named `react/jsx-dev-runtime`. A production build uses `react/jsx-runtime` instead. You never import either one. The transform adds the import by itself.

That is why your component files use JSX without importing anything from React. React 19 requires this transform, which its upgrade guide calls "the new JSX transform". An older setup wrote `React.createElement` for every tag, so every file had to import `React`. When an app still uses that old transform, React 19 prints this warning:

```devconsole width=full caption="The warning React 19 prints when an app still uses the old JSX transform."
! Your app (or one of its dependencies) is using an outdated JSX transform. Update to the modern JSX transform for faster performance: https://react.dev/link/new-jsx-transform
```

`createElement` is the function React documents for writing the call by hand. When you use it, you import it yourself from `react`, as the opening did.

### The same list, written with createElement

You can choose how to write what a component returns:
1. **JSX.** React's docs say "most React developers prefer the conciseness of JSX, and most codebases use it." It needs a build tool, such as Vite (Lesson 07).
2. **`createElement` by hand.** React's docs say: "If you don't like JSX or can't use it in your project, you can use `createElement` as an alternative."

The docs add: "Both coding styles are fine". To prove that both give the same elements, here is `CommentList.jsx` once more, without a single tag:

```jsx title="src/CommentList.jsx, written with createElement"
import { createElement } from 'react';
import Comment from './Comment.jsx';

const comments = [
  { id: 1, author: 'John', text: 'Great article!' },
  { id: 2, author: 'Mia', text: 'Me too!' },
];

export default function CommentList() {
  return createElement(
    ~'section'~, // 1. The section tag: a string
    null, // 2. No attributes on the section
    createElement('h2', null, 'Comments'), // 3. First child: the heading
    comments.map(c =>
      ~createElement(Comment, { key: c.id, author: c.author, text: c.text })~ // 4. Second child: the array of comments
    )
  );
}
```

The browser shows the same page and the same four Console lines:

```page width=text caption="The comment list built with createElement: the exact same page and the same Console lines."
heading: Comments
line: John: Great article!
line: Mia: Me too!
log: Comment rendered: John | Comment.jsx:2
log: Comment rendered: John | Comment.jsx:2
log: Comment rendered: Mia | Comment.jsx:2
log: Comment rendered: Mia | Comment.jsx:2
```

Two details in this version are worth a look:
1. **`key` sits in the props object, next to `author` and `text`.** You write it the same way. Principle 3 shows that it does not stay there.
2. **The array from `map` goes in as one argument.** React's docs say that when the children are dynamic, you should "pass the entire array as the third argument". Then React can still warn you when a key is missing.

So why does almost everyone write JSX? React's docs: "The main benefit of using JSX compared to `createElement` is that it's easy to see which closing tag corresponds to which opening tag." Above, you had to count parentheses to see where the section ends. The docs also list `createElement` among the legacy APIs, the old functions React keeps but no longer recommends: "Typically, you'll use JSX instead." So we go back to the JSX version of `CommentList.jsx`.

Remember: a tag is a call, and the call returns an object.

## PRINCIPLE | React element: creating it calls no component and puts nothing on the page

> [!PRINCIPLE]
> **Principle 2: React Elements: An Element Describes the Screen and Renders Nothing by Itself**
>
> *A JSX tag returns a React element, a plain object that describes what to show; creating it does not call the component and does not create a DOM node.*
>
> React calls a component only for an element that React receives, such as one that a component returns. An element kept in a variable stays an object in memory: the component never runs, and no DOM node is created. Because an element is only a description, creating one is cheap, and it has none of the methods of a DOM node. To work with the real node, use a ref.
>
> **DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> function handleReply() {
>   ~inputRef.current.focus();~ // The real input field on the page, after the commit
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const field = <input placeholder="Write a reply" />;
> function handleReply() {
>   ~field.focus();~ // **WRONG:** field is a plain element object, so focus is not a function!
> }
> ```

React's docs show the element for `<Greeting name="Taylor" />`, "slightly simplified":

```js title="The element for the Greeting tag, slightly simplified by React's docs"
{
  ~type: Greeting~, // Your function itself, not called
  props: { name: 'Taylor' },
  key: null,
  ref: null,
}
```

Look at `type`. It holds the function `Greeting`, and nobody has called it. The docs say it plainly: "creating this object does not render the `Greeting` component or create any DOM elements."

So when does `Greeting` run? Only when React receives the element, for example because a component returns it. An element kept in a variable is an object in memory, and nothing more.

### VS | An element in the `return` vs. an element in a variable: only the returned one reaches React

Suppose Leo is writing a new comment, and a developer wants to look at its element in the Console before showing it. In `CommentList`, the developer creates the element, logs it, and leaves the `return` unchanged:

```jsx title="src/CommentList.jsx" startLine="8"
export default function CommentList() {
  const preview = ~<Comment author="Leo" text="First!" />~; // Creates an element; nothing calls Comment yet
  console.log(preview);
  return (
    <section>

      {comments.map(c => (
        <Comment key={c.id} author={c.author} text={c.text} />

```

Leo's comment appears only in the Console. The page still shows John and Mia, and the Console has no `Comment rendered: Leo` line:

Here is what happens, in order:
1. React calls `CommentList`. Its first line creates `preview`, the element for Leo's comment. Its `type` is your `Comment` function, and its props hold Leo's author and text.
2. `console.log` prints that object. `Comment` has not run, so it prints no line.
3. `CommentList` returns the section with John and Mia. `preview` is not in it.
4. React receives the section, and calls `Comment` once for John and once for Mia. Each call prints its line.
5. React never received Leo's element. So it never calls `Comment` for Leo, and it never creates a `<p>` for Leo.

Two fields in the Console are worth a look. `type` holds your `Comment` function itself, because the tag starts with a capital letter, as Principle 1 showed. `key` is `null`, because the tag has no key. React's docs say: "If missing, `null`."

### The component, the element, and the DOM node

Three words name three different things here:
1. **The component** is your function, `Comment`. It sits in the `type` field of the element.
2. **The element** is the object that `<Comment author="Leo" text="First!" />` returns. It describes what to show.
3. **The DOM node** is the real `<p>` on the page. React creates it during the commit, and only for an element React has received (Lesson 13).

```tree caption="The component is the function, the element is the object, and the DOM node is what React creates on the page."
Three things behind one comment line
- +The component [`Comment`] | **Your function** | Sits in the element's **`type`** field
- +The element [`<Comment author="Leo" text="First!" />`] | A **plain object** that describes the line | Costs almost nothing to create; **renders nothing** by itself
- +The DOM node [`<p>`] | The **real paragraph** on the page | Created **by React during the commit**, only for elements React receives
```

Because an element is a plain object, it can sit anywhere a value can sit: in a variable, in an array, or in a prop, as `children` does (Lesson 09). Nothing renders until React receives it. Creating one costs almost nothing, so there is no reason to avoid JSX in a variable or in a helper function.

React's docs also ask you to treat every element as **opaque**: "Although you may read the element's properties, it's best to treat every element as opaque after it's created, and only render it." Opaque means you cannot see through it. We read the fields in the Console to learn what an element is. App code only hands the element to React.

> [!DEFINITION]
> **A React node.** [NEW] A React node is anything a component may return: an element, a string, a number, true or false, null or undefined, a portal, or an array of nodes.
> The text `'Great article!'` is a React node. `<Comment />` is a React node, and it is also a React element.
> Every element is a node, but most nodes are not elements (Lesson 76).

### The real mistake: calling focus on an element

In plain JavaScript, you grab the `<input>` field from the page, and you call `focus` on it:

```js title="Plain JavaScript: you hold the real input field"
~document.querySelector('input').focus()~; // A real element of the page, so focus exists
```

That works, because `querySelector` gives you the real element. Now the same idea in React. Comment sections often have a reply field with a `Reply` button. When the user clicks `Reply`, the cursor should land in the field. A developer keeps the field as JSX in a variable, and calls `focus` on it:

```jsx title="src/ReplyForm.jsx"
export default function ReplyForm() {
  const field = <input placeholder="Write a reply" />;

  function handleReply() {
    ~field.focus();~ // **WRONG:** field is an element object, not the input field on the page, so focus does not exist!
  }

  return (
    <>
      {field}
      <button onClick={handleReply}>Reply</button>
    </>
  );
}
```

The user clicks `Reply`, and nothing happens on the page. The cursor never reaches the field, and the Console shows an error:

```page width=text caption="After the user clicks Reply: the cursor is not in the input field, and the Console shows a TypeError."
form:
  field: Write a reply | | bad
  button: Reply
error: Uncaught TypeError: field.focus is not a function
```

`field` holds a description of an `<input>` field, not the field. The object has `type`, `props`, and `key`, and none of the methods of a DOM node. So JavaScript throws a `TypeError`, the error it throws when a value cannot do what the code asks of it.

The real `<input>` exists only after the commit. A ref is how you ask React: "when you create this `<input>`, give it to me" (Lesson 31). React puts the real element into `inputRef.current`, and from then on it is the same element you know from plain JavaScript:

```jsx title="src/ReplyForm.jsx"
import { useRef } from 'react';

export default function ReplyForm() {
  const inputRef = useRef(null);

  function handleReply() {
    ~inputRef.current.focus();~ // current holds the real input field on the page
  }

  return (
    <>
      <input ref={inputRef} placeholder="Write a reply" />
      <button onClick={handleReply}>Reply</button>
    </>
  );
}
```

Now the user clicks `Reply`, and the cursor lands in the field.

Remember: the element describes the `<input>`. Only React creates it, and only a ref gives it to you.

## PRINCIPLE | key: React keeps it on the element, so the component never receives it

> [!PRINCIPLE]
> **Principle 3: The key Field: key Lives on the Element, Not in props**
>
> *React takes `key` out of the props written on the tag, turns it into a string, and stores it on the element as `element.key`; the component never receives it.*
>
> `key` and `author` are written the same way on a tag, but they go to two different readers. `author` goes into `props` for the component. `key` stays on the element for React, which compares it between renders. Reading `key` inside the component gives `undefined`. When the component needs the same value, pass it again under another name.
>
> **DO THIS:**
> ```jsx
> <Comment key={c.id} ~id={c.id}~ author={c.author} text={c.text} /> // id reaches Comment as a prop
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Comment({ ~key~, author, text }) { // **WRONG:** key is never in props, so it is undefined!
>   return <p id={'comment-' + key}>{text}</p>;
> }
> ```

### VS | `key` vs. `author` on the same tag: one goes to React, one goes to the component

You write `key` and `author` the same way on a tag:

```jsx title="key and author written on the same tag"
const element = <Comment ~key={1}~ author="John" />; // key: '1' on the element; props: { author: 'John' }
```

They look alike, but they land in two different places. `author` goes to the component, inside `props`. `key` stays with React, on the element itself. React's docs say that `key` is special and "will *not* be available" as `element.props.key`. It is available as `element.key`.

```tree caption="key and author sit on the same tag but land in two different places on the element."
Where each attribute of `<Comment key={1} author="John" />` lands
- +`author="John"` | Goes **into `props`** | The component reads it as **`author`**
- +`key={1}` | Goes **onto the element** as **`element.key`** | Turned into the **string `'1'`**; `props` has **no `key`**
```

### Logging the first element of the list

Now look at the elements that `map` builds in `CommentList`. Keep them in `items`, log the first one, and return the same list:

```jsx title="src/CommentList.jsx" startLine="8"
export default function CommentList() {
  const items = comments.map(c => (
    <Comment key={c.id} author={c.author} text={c.text} />
  ));
  ~console.log(items[0]);~ // The element for John's comment
  return (
    <section>
      <h2>Comments</h2>
      {items}
    </section>
  );
}
```

The page does not change. In the Console, the key is the string `"1"`, and `props` holds only the author and the text:

```devconsole source="CommentList.jsx:12" caption="The element for John's comment: the key is a string on the element, and props has no key."
v {$$typeof: Symbol(react.transitional.element), type: ƒ, key: '1', props: {…}, _owner: FiberNode, …}
  key: "1" | A string, though c.id is the number 1
  props: {author: 'John', text: 'Great article!'} | No key inside props
  type: ƒ Comment({ author, text })
> {$$typeof: Symbol(react.transitional.element), type: ƒ, key: '1', props: {…}, _owner: FiberNode, …} | The second call of CommentList, from StrictMode
+ Comment rendered: John
+ Comment rendered: John
+ Comment rendered: Mia
+ Comment rendered: Mia
```

John's `c.id` is the number `1`, yet the Console shows the string `"1"`. Here is what React did when it created the element:
1. It took `key` out of the props you wrote on the tag.
2. It turned the key into a string. React's docs say: "The `key` you have passed, coerced to a string. If missing, `null`." Coerced means converted from one type to another, here from a number to a string.
3. It stored the string on the element as `key`, next to `props`, not inside it.

### The real mistake: reading key inside the component

Inside `Comment`, a developer needs the comment's id, for example to give the paragraph an id that a link can point to. The developer reads `key`:

```jsx title="src/Comment.jsx"
export default function Comment({ ~key~, author, text }) { // **WRONG:** key is not in props, so it is undefined!
  return <p id={'comment-' + key}><b>{author}</b>: {text}</p>;
}
```

The page looks the same, but every comment gets the id `comment-undefined`, so a link to one comment finds nothing. In development, React leaves a hidden `key` on `props` for exactly this case. Reading it returns `undefined`, and React prints this warning once (Lesson 18):

```devconsole width=full caption="The warning React prints when a component reads key from its props."
x Comment: `key` is not a prop. Trying to access it will result in `undefined` being returned. If you need to access the same value within the child component, you should pass it as a different prop. (https://react.dev/link/special-props)
```

React's docs explain why: "your components won't receive `key` as a prop. It's only used as a hint by React itself." The fix in the docs is to pass the id a second time, under another name:

```jsx title="src/CommentList.jsx" startLine="13"
<Comment key={c.id} ~id={c.id}~ author={c.author} text={c.text} /> // id reaches Comment as a normal prop
```

Why does React keep `key` apart? Because it is information for React, not for the component. Between two renders, React compares the `type` and the `key` of each element to decide which DOM nodes to keep. A later lesson shows how.

React's docs on `createElement` name one more special name next to `key`: `ref`. React 19 changed it. `ref` is now a regular prop for function components, and reading `element.ref` is deprecated. A later lesson covers `ref` as a prop.

Remember: `key` is for React. Anything the component needs goes in under another name.

## PRINCIPLE | props of an element: frozen after creation, so new text needs a new element

> [!PRINCIPLE]
> **Principle 4: Immutable Elements: Create a New Element Instead of Changing One**
>
> *React elements and their props never change after creation; in development, React freezes them shallowly, so an assignment throws in a module, and different text needs a new element.*
>
> An element is a finished description. In development, React calls `Object.freeze` on each element and its `props`, and every module runs in strict mode, so assigning to `props.text` throws a `TypeError` and the page goes blank. In production the freeze is skipped, but the rule holds. To show different text, create a new element, which is cheap.
>
> **DO THIS:**
> ```jsx
> const edited = ~<Comment author="Leo" text="Edited" />~; // A new element with the new text
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const preview = <Comment author="Leo" text="First!" />;
> ~preview.props.text = 'Edited';~ // **WRONG:** the element is frozen in development, so this throws a TypeError!
> ```

React's docs give this rule (Lesson 58): "You must treat React elements and their props as immutable and never change their contents after creation. In development, React will freeze the returned element and its `props` property shallowly to enforce this."

To see what "freeze" does, start in plain JavaScript:

```js title="Plain JavaScript: a frozen object inside a module"
const user = Object.freeze({ name: 'John' });
~user.name = 'Mia';~ // Throws a TypeError, because a module runs in strict mode
```

Two definitions explain that line.

> [!DEFINITION]
> **Object.freeze.** [NEW] `Object.freeze` is a JavaScript function that makes the fields of an object unchangeable. After `Object.freeze(user)`, no code can change `user.name`.
> In development, React calls it on every element and on its `props` object. React freezes them **shallowly**: only those two objects. An object that you pass inside a prop is not frozen (Lesson 76).

> [!DEFINITION]
> **Strict mode.** [NEW] Strict mode is a stricter way for JavaScript to run your code. When code assigns a new value to a field of a frozen object, MDN says the assignment "silently does nothing", except in strict mode, where it will "throw TypeErrors".
> MDN also says: "The entire contents of JavaScript modules are automatically in strict mode." `CommentList.jsx` is a module, because it uses `import`.
> JavaScript's strict mode has nothing to do with React's `<StrictMode>` wrapper (Lesson 05).

So in a React file, an assignment to an element's props does not fail quietly. It throws.

### Changing Leo's text inside CommentList

The developer from Principle 2 now wants Leo's preview to say Edited, and adds one line in `CommentList`:

```jsx title="src/CommentList.jsx" startLine="8"
export default function CommentList() {
  const preview = <Comment author="Leo" text="First!" />;
  ~preview.props.text = 'Edited';~ // **WRONG:** assigns to a frozen object inside a module
  return (
    <section>
      <h2>Comments</h2>
      {comments.map(c => (
        <Comment key={c.id} author={c.author} text={c.text} />
      ))}
    </section>
  );
}
```

**One assignment blanks the whole page.** The comments disappear, and the Console shows the error:

```page width=text caption="The page after preview.props.text is assigned in development: the page is blank, and JavaScript reports a read-only property."
blank
error: Uncaught TypeError: Cannot assign to read only property 'text' of object '#<Object>'
warn: An error occurred in the <CommentList> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

Nothing in that line looks dangerous, so here is what happens, in order:
1. React calls `CommentList`, and its first line creates `preview`. In development, React freezes the element and its `props` as it creates them.
2. The next line assigns `'Edited'` to `preview.props.text`.
3. `CommentList.jsx` is a module, so it runs in strict mode, and JavaScript throws a `TypeError`. The error comes from JavaScript, not from React. React's part was the freeze.
4. `CommentList` stops before its `return`, so React has nothing to show, and it removes the page. React's docs say: "By default, if your application throws an error during rendering, React will remove its UI from the screen."

React's docs name the freeze for development only. In a production build, React does not freeze the element, so the same line does not throw. The rule does not change: the freeze only makes the mistake loud while you work.

### Creating a new element instead

To show Leo's comment with different text, create a new element with the new text:

```jsx title="src/CommentList.jsx" startLine="9"
const edited = ~<Comment author="Leo" text="Edited" />~; // A new element: cheap, and nothing is frozen
```

The assignment changes a frozen object and throws. The new tag creates a new object, which costs almost nothing, as Principle 2 showed. We now remove the preview lines, and `CommentList` is back to the working version.

```tree caption="Changing a created element throws in development; creating a new element is the fix."
Two ways to give Leo's comment the text Edited
- !Assign into the element [`preview.props.text = 'Edited'`] | Changes a **frozen** object inside a **module** | JavaScript throws a **`TypeError`**, and the page goes **blank**
- +Create a new element [`<Comment author="Leo" text="Edited" />`] | Makes a **new object** from new props | **Cheap**, and nothing is changed
```

### The real mistake: changing the props of children

The same mistake hides in a wrapper component. Suppose the article's author pins John's comment to the top. A `PinnedComment` receives the `<Comment />` element as `children` (Lesson 09):

```jsx title="src/CommentList.jsx"
<PinnedComment>
  ~<Comment author="John" text="Great article!" />~ {/* Arrives inside PinnedComment as children */}
</PinnedComment>
```

`PinnedComment` wants to put `Pinned:` in front of the text, and changes the props of `children`:

```jsx title="src/PinnedComment.jsx"
export default function PinnedComment({ children }) {
  ~children.props.text = 'Pinned: ' + children.props.text;~ // **WRONG:** children is a frozen element!
  return children;
}
```

In development, this line throws the same `TypeError`, and the page goes blank. React's docs do have a tool that builds "a new React element using another element as a starting point": `cloneElement`. But they warn: "Using `cloneElement` is uncommon and can lead to fragile code." The usual fix is to pass the data as props, and let the component build its own element:

```jsx title="src/PinnedComment.jsx"
import Comment from './Comment.jsx';

export default function PinnedComment({ author, text }) {
  return ~<Comment author={author} text={'Pinned: ' + text} />~; // Builds a new element from props
}
```

`CommentList` now writes `<PinnedComment author="John" text="Great article!" />`, and the page shows `John: Pinned: Great article!`.

Why does React insist? So that it can trust an element it already holds. React's docs say: "A JSX node object could not have changed over time, so React knows it's safe to skip a re-render" (Lesson 58). Changing an element during rendering also breaks purity: a component must not change objects that existed before it ran (Lesson 14).

Remember: you never edit an element. You create a new one.

## PRINCIPLE | `$$typeof`: only JSX and `createElement` make a real element, never JSON

> [!PRINCIPLE]
> **Principle 5: The $$typeof Field: Only JSX and createElement Make Elements**
>
> *A real element carries a `Symbol` in `$$typeof`; JSON cannot hold a `Symbol`, so an object rebuilt from JSON is not an element, `isValidElement` returns `false`, and React refuses to render it.*
>
> An object with `type` and `props` is not enough to be an element. Only JSX and `createElement` put React's symbol in `$$typeof`. `JSON.stringify` leaves Symbol values out, so data from a server can never pass as an element, and React throws `Objects are not valid as a React child` when such an object sits between tags. To show data from a server, show its text fields.
>
> **DO THIS:**
> ```jsx
> <p>~{comment.text}~</p> // A string from the server: React shows it as text
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <p>~{comment}~</p> // **WRONG:** a plain object from JSON has no $$typeof, so React refuses it!
> ```

React has a function that answers one question: is this value an element? Its docs give two lines:

```jsx title="What isValidElement says about a JSX tag and a plain object"
isValidElement(<p />); // true: made by JSX
~isValidElement({ age: 42 })~; // false: a plain object
```

`isValidElement` "checks whether a value is a React element". The docs give the rule behind it: "Only JSX tags and objects returned by `createElement` are considered to be React elements."

### What JSON does to a Symbol

Start in plain JavaScript. Put a `Symbol` in an object, and send the object through JSON:

```js title="Plain JavaScript: a Symbol does not survive JSON"
const user = { name: 'John', tag: Symbol.for('vip') };
~JSON.stringify(user)~; // Gives the text {"name":"John"}: the Symbol field is gone
```

> [!DEFINITION]
> **A Symbol.** [NEW] A `Symbol` is a JavaScript value that is not a string, not a number, and not an object. `Symbol.for` finds or creates a symbol by name, "in a runtime-wide symbol registry", as MDN says.
> React uses the symbol named `react.transitional.element`, the one in the `$$typeof` field you saw in the Console at the start of this lesson (Lesson 76).

JSON can hold strings, numbers, booleans, `null`, arrays, and plain objects. It cannot hold a `Symbol`. MDN says that Symbol values "are not valid JSON values", and that `JSON.stringify` leaves one out, "omitted", when it sits in an object.

### VS | A real element vs. its JSON copy: they look the same, only one is an element

Now do the same with a real element. Turn it into JSON text, and parse that text back into an object:

```jsx title="A real element and its copy through JSON"
import { isValidElement } from 'react';

const name = <b>John</b>;
const copy = ~JSON.parse(JSON.stringify(name))~; // Rebuilds a plain object from JSON text

console.log(isValidElement(name), isValidElement(copy)); // true false
console.log(name.$$typeof, copy.$$typeof); // Symbol(react.transitional.element) undefined
```

```devconsole caption="The real element passes isValidElement; its JSON copy has no $$typeof and fails."
+ true false
+ Symbol(react.transitional.element) undefined
```

`copy` looks just like `name`: the same type, the same key, and the same props, with John between the tags. But `copy` lost `$$typeof` on its way through JSON, so it is not an element. Here is the trip, in order:
1. `JSON.stringify(name)` turns the element into text. The `$$typeof` field holds a `Symbol`, so it is left out of the text.
2. `JSON.parse` builds a brand-new plain object from that text. It has the type, the key, and the props, and no `$$typeof`.
3. `isValidElement(name)` is `true`. `isValidElement(copy)` is `false`.

### Showing the copy in the comment list

Comment data comes from a server as JSON (Lesson 33). So what does React do with the copy? Put `name` and `copy` at the top of the file, and show `copy` under the comments:

```jsx title="src/CommentList.jsx" startLine="8"
const name = <b>John</b>;
const copy = JSON.parse(JSON.stringify(name));

  return (
    <section>
      <h2>Comments</h2>
      {comments.map(c => (
        <Comment key={c.id} author={c.author} text={c.text} />
      ))}
      ~<p>{copy}</p>~ {/* **WRONG:** copy is a plain object, not an element */}
    </section>
  );
}
```

**React refuses the copy, and the whole page goes blank.** The Console shows the error (Lesson 03):

```page width=text caption="The page after the JSON copy is placed between tags: the page is blank, and React refuses the object."
blank

log: Comment rendered: John | Comment.jsx:2
log: Comment rendered: Mia | Comment.jsx:2
log: Comment rendered: Mia | Comment.jsx:2
```

The `Comment rendered` lines come first, because React calls both `Comment` components before it reaches the copy. When rendering throws, React tries the whole render once more before it gives up, so the four lines appear twice.

React sees an object between the tags. The object has no `$$typeof`, so to React it is not an element. It is not text or a number either. React has no way to show it, so it throws. We remove the `<p>` and the two lines above `CommentList`, and the file is back to the working version.

Why do elements carry this mark at all? React's docs do not say. Outside the docs, the React team has given the reason:
1. A server may store text that users type, and send it back as JSON.
2. Suppose any object with `type` and `props` counted as an element. Then a user could send an object that looks like an element, for example one with `dangerouslySetInnerHTML`, the prop that puts raw HTML on the page. The page would draw it.
3. A `Symbol` cannot travel in JSON, so an object from a server can never pass as an element.

React's own advice on raw HTML stays the same: "Only use `dangerouslySetInnerHTML` with trusted and sanitized data" (Lesson 48).

### The real mistake: showing the server's object instead of its text

The mistake developers really make with server data is simpler. A comment arrives from the server as an object, and the developer puts the whole object between tags instead of its text:

```jsx title="src/CommentList.jsx"
const comment = { id: 1, author: 'John', text: 'Great article!' }; // One comment, as the server sends it

<p>~{comment}~</p> {/* **WRONG:** a plain object: Objects are not valid as a React child */}
<p>~{comment.text}~</p> {/* A string: React shows Great article! */}
```

The first paragraph throws `Objects are not valid as a React child` (Lesson 03). The second shows the text, because a string is a React node. The fix is always to show the field that holds the text.

You will rarely call `isValidElement` yourself. React's docs say: "It is very uncommon to need `isValidElement`." It answers one question only: is this value an element? It does not answer whether a value can be rendered, because strings and numbers can be rendered and are not elements.

After the element, React builds its own internal tree to do the rendering work. A later lesson covers that tree, called Fiber.

Remember: only JSX and `createElement` make elements. Anything that came through JSON is plain data.

## For the Interview

> **The Interview Question:** What does JSX compile into, and what is an element object?

### How to Answer Clearly in 30 Seconds

"JSX is a syntax extension the browser cannot run. Before the file reaches the browser, a build tool's JSX transform turns every tag into a function call. In development, Vite's output calls `_jsxDEV` from `react/jsx-dev-runtime`, and the documented form we can write by hand is `createElement(type, props, ...children)`. Both give the exact same result: a React element, a plain object that describes a piece of the screen. Four fields matter:
1. **`type`** is a string such as `'p'` for a built-in tag, or the component function itself for a capitalized tag.
2. **`props`** holds the attributes, with the content between the tags in `children`.
3. **`key`** is taken out of `props`, coerced to a string, or `null` when missing.
4. **`$$typeof`** holds a `Symbol` that marks a real element, so an object rebuilt from JSON can never pass as one.

Creating an element does not call the component or create DOM nodes, so it is cheap. Elements are immutable, and React freezes them in development."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What is the difference between a component, an element, and a DOM node?"**
   The component is our function, such as `Comment`. The element is the object that `<Comment />` returns, with the function in its `type` field. It only describes what to show. The DOM node is the real `<p>` that React creates during the commit, and only for elements React receives. That is why `field.focus()` fails on an element: the element has no DOM methods. A ref gives us the real node instead.
2. **"Why can't a component read its own `key`, and why does `element.key` show `'1'` when we passed the number `1`?"**
   `key` is information for React, not for the component. When React creates the element, it takes `key` out of `props`, coerces it to a string, and stores it as `element.key`. Between renders, React compares the `type` and `key` of each element to decide which DOM nodes to keep. Inside the component, `key` is `undefined`, so we pass the same value again under another name, such as `id={c.id}`.
3. **"What is `$$typeof` for, and what happens if you render an element that went through JSON?"**
   `$$typeof` holds a `Symbol`, React's mark of a real element. Only JSX and `createElement` set it. `JSON.stringify` leaves Symbol values out, so the copy that `JSON.parse` returns has `type` and `props` but no `$$typeof`. `isValidElement` returns `false` for it, and React throws `Objects are not valid as a React child`. The React team has explained this as a guard: data that a server stores and sends as JSON can never pose as an element on the page.

```tree dir=right caption="Interview comparison: a real element made by JSX vs. a look-alike object rebuilt from JSON."
What React accepts as an element
- +Made by JSX or `createElement` [`<b>John</b>`] | Carries **`$$typeof`**, a `Symbol` | `isValidElement` is **`true`**; React **renders it**
- !Rebuilt from JSON [`JSON.parse`] | Has `type` and `props`, but **no `$$typeof`** | `isValidElement` is **`false`**; React throws **Objects are not valid as a React child**
```
