# Lecture 116: How a Server Page Hands the Signed-In User to Client Context

*(How do Client Components read the signed-in user when only the server can read the database?)*

> INTERVIEW QUESTION | ❱ CORE | How does context behave across the server/client boundary?

---

## VS | `createContext` in a Server Component vs. in a `'use client'` Provider: context lives only in the browser

> Who is signed in is stored in the database, so only the server can read it, yet the components that show the name run in the browser. **Context lives only in the browser, so the server reads the user and passes it as a prop to a small Client Component that provides it**. The reason: context exists to re-render the components that read it, and a Server Component runs once and is gone.

Remember how a site greeted John before React. The server read John from the database and printed him into the page, inside a `<script>` tag. Every script in the browser then read him from that one place:

```html title="The page the server sends: the server printed the user into a script tag"
<script>~window.currentUser = { id: 1, name: 'John' };~</script> <!-- Written by the server, read by every script in the browser -->
<button id="account"></button>
```

```js title="account.js, a script in the browser"
document.getElementById('account').textContent = ~window.currentUser.name~; // John, printed into the page by the server
```

The server reads the user once and hands it over. The browser keeps the value in one place, and every script reads it from there. No script in the browser ever touches the database.

React with Server Components keeps the same split. The server reads the user. The hand-over is a prop. The one place where the browser keeps the value is context.

### The Context Code From Lesson 28, Moved Into a Server Component

Here is the context code you wrote in Lesson 28. Now it sits in `App.jsx`, which has no directive, so it is a Server Component. It awaits the user from `db.js`, our stand-in for the database (as seen in Lesson 109):

```jsx title="App.jsx, a Server Component" startLine="1" bad="4"
import { createContext } from 'react';
import db from './db';

const UserContext = ~createContext~(null); // **WRONG:** on the server, React has no createContext, so the page stops

export default async function App() {
  const user = await db.users.get(1);
  return (
    <UserContext value={user}>
      <p>Hello, {user.name}</p>
    </UserContext>
  );
}
```

These are the lines that worked in Lesson 28, letter for letter. **It may look the same, but it is NOT the same thing!** In Lesson 28, the file ran in the browser. Here, it runs on the server, and the copy of React on the server has no `createContext` at all. The server stops at this file, and the reader gets no article.

Why does React leave context out of the server? React's docs give two facts, and they fit together:
1. **Context exists to re-render.** React's docs: "React automatically re-renders components that read some context if it changes."
2. **A Server Component does not stay around after it renders.** React's docs: "Server Components do not persist in memory after render and cannot have their own state."

So a Server Component runs once, hands over its output, and is gone. On the server, no component is left for context to update. Context belongs where components stay alive: in the browser.

That gives the whole fix in three steps:

```tree dir=right caption="How a value read on the server reaches context in the browser: the server reads it, a Client Component provides it, and Client Components below read it."
How the signed-in user reaches the comment form
- +1. The server reads the value [`App.jsx`, no directive] | `App` **awaits the user** from `db.js` | Passes it on as a **prop**: `user={user}`
- +2. A Client Component provides it [`UserProvider.jsx`, `'use client'`] | **Makes the context** and renders the provider | Wraps the page it receives as **`children`**
- +3. Client Components below read it [`useContext`] | `AccountButton` and `CommentForm` **read the same user** | Both show **John**
```

Here is the one sentence to keep in mind for this whole lesson:

**Context lives only in the browser. The server reads the user and passes it as a prop to a Client Component provider, and every Client Component below reads it with `useContext`.**

### Three Ideas From Earlier Lessons

> [!DEFINITION]
> **Server Component and Client Component.** [REVIEW] A file with no directive holds Server Components. They run on the server, they can be `async` and `await` the database, and they send only their output to the browser. A file that starts with `'use client'` holds Client Components. Their code goes into the bundle the browser downloads, so they can use state, Hooks, and click handlers. Hooks do not work in a Server Component (Lesson 108).

> [!DEFINITION]
> **Context.** [REVIEW] Context lets a component deep in the page read a value that a component far above it holds, with no prop passed through every layer in between. You make it once with `createContext(null)`, where `null` is the default value. The provider, `<UserContext value={user}>`, wraps a part of the page. Any component inside it reads the value with `useContext(UserContext)`, and React re-renders that component when the value changes (Lesson 28).

> [!DEFINITION]
> **What can travel from the server to the browser.** [REVIEW] When a Server Component renders a Client Component, React writes the props down on the server and rebuilds them in the browser. Strings, numbers, arrays, plain objects, and JSX can make this trip. A plain function cannot, because it is code, not data, and an instance of a class cannot either (Lesson 107).

### What the Reader of the Page Sees

What is at stake is what the reader of the news page sees:
1. **With the context made in the server file, the reader sees no article at all.** The server stops before it sends any part of the page.
2. **With the provider set up right, both places show `John` in the first page the server sends.** The browser makes no extra request to learn who is signed in.

### Where Readers Usually Go Wrong

Readers usually go wrong in three ways:
1. **They write `createContext` in the server file**, because that is where the data is.
2. **They import the context into the server file and read it there**, because a server page that already knows the user seems the right place to read it.
3. **They believe a provider around the whole page turns the whole page into client code**, so they pass the user as a prop through every layer instead.

### Four Ways to Bring a Server Value to Client Components

When Client Components need a value that only the server can read, you choose between four ways:
1. **Pass the value as a prop through every layer.** React's docs: "Start by passing props." This fits one or two layers. On our page, every layer between `App` and the comment form would carry `user` without using it.
2. **Pass JSX as `children`, so the layers in the middle disappear** (as seen in Lesson 115). This fits when the layers in the middle only wrap their content.
3. **A client provider that receives the value as a prop, and `useContext` in each component that reads it.** This fits when many Client Components at different depths read the same value. This lesson builds this way.
4. **A Promise passed into the provider and read with `use`.** This fits a value that is slow to read, when the page should not wait for it. Lesson 165 builds it.

The client provider and the Promise both work only for Client Components, because a Server Component cannot read context. A Server Component that needs the user takes it as a prop, or reads it from the database itself.

## SECTION | A News Article for a Signed-In User

Open a news article on a site where you are signed in as John. At the top of the page, a button shows your name. Under the article, the comment form tells you who you are commenting as:

```page caption="A news article for a reader signed in as John: the name John on the account button and above the comment form."
url: news.example.com/new-park
line: [John]
heading: Our new park opens
form:
  textarea: Commenting as John |
  button: Post
console: quiet
```

This small page needs two things that live on two different sides:
1. **Who is signed in is stored in the database.** Only the server can read it.
2. **The account button and the comment form answer the reader.** A click on the account button opens a menu, and the comment form takes what the reader types. Only the browser answers clicks and typing, so both are Client Components (as seen in Lesson 108).

The two components also sit far apart. The account button sits in the header, and the comment form sits inside the article. When two components far apart need the same value, we use context (as seen in Lesson 28).

Six files make the page:

```files title="news: the article page" caption="The six files of the news page: the database stand-in, two Server Components, and three Client Components."
src/
  db.js | stand-in | Plays the database and gives `db.users.get(id)`
  UserProvider.jsx | Client Component | Starts with `'use client'`; makes `UserContext` and provides `user` to its `children`
  AccountButton.jsx | Client Component | Starts with `'use client'`; reads the user and shows the name on a button
  CommentForm.jsx | Client Component | Starts with `'use client'`; reads the user and shows `Commenting as John`, a `<textarea>`, and `Post`
  Article.jsx | Server Component | Shows the heading and renders `CommentForm`
  App.jsx | Server Component | Awaits the user and renders `UserProvider` around the header and the article
```

Three files start with `'use client'`, and they run in the browser. The other three have no directive, and they run on the server. A real page reads the signed-in user from the session. Our `App` writes the id `1` by hand, to keep the page small.

**PRINCIPLES:** Context lives only in the browser. The server can read a value and pass it on, but it can neither make context nor read it. Five principles follow:
1. **`createContext` in a Server Component: the server stops before it sends the page.** The copy of React on the server has no `createContext`.
2. **`UserProvider` with `'use client'`: the server passes `user` as a prop, and the provider makes the context.** The value must be plain data.
3. **`<UserContext>` in a Server Component: the server can pass the context on, but never read it.** The server holds only a placeholder for the real context.
4. **`useContext` under the provider: every Client Component reads the same user, at any depth.** It works exactly as in Lesson 28, even inside a Server Component.
5. **`children` of the provider: a Server Component inside `UserProvider` stays on the server.** The imports decide where code runs, not the place on the screen.

## PRINCIPLE | `createContext` in a Server Component: the server stops before it sends the page

> [!PRINCIPLE]
> **Principle 1: Context Is a Client Feature: `createContext` in `App.jsx` Stops the Page**
>
> *Never call `createContext` in a Server Component file; make every context in a file that starts with `'use client'`.*
>
> Context exists to re-render the components that read it when its value changes. A Server Component runs once, hands over its output, and does not stay in memory, so on the server there is nothing for context to update. React leaves `createContext` and `useContext` out of the copy that runs on the server, and a server file that asks for them stops the page.
>
> **DO THIS:**
> ```jsx
> 'use client';
> import { createContext } from 'react';
> export const ~UserContext~ = createContext(null); // Made in a client file, where context exists
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import { createContext } from 'react';
> const UserContext = ~createContext~(null); // **WRONG:** a file with no directive runs on the server, and the page stops
> ```

### The Data Is Here, So the Context Goes Here

A team moves its news site to Server Components. `App.jsx` now awaits the user from the database. A developer adds the context to that same file, as the team always did in client code:

```jsx title="src/App.jsx" startLine="1" bad="4"
import { createContext } from 'react';
import db from './db';

const UserContext = ~createContext~(null); // **WRONG:** App.jsx runs on the server, where React has no createContext
```

The reasoning looks sound: the data is in this file, so the context goes in this file.

### Why the Page Never Arrives

**The reader gets no article and no `Hello, John`. The server stops at the first line of `App.jsx`, before it renders anything.** Here is what happens when the reader opens the page, in order:
1. `App.jsx` has no directive, so it is a Server Component. Server Components are the default, and they need no marker. React's docs: "there is no directive for Server Components."
2. The server loads `App.jsx` with its own copy of React, the one made for Server Components.
3. That copy of React has no `createContext`, and no `useContext` either. React's docs list `createContext` first among the APIs that "must run on the client".
4. The import line asks `react` for `createContext` and finds nothing. The server stops with an error that names `createContext`. Each framework words that message its own way.
5. The server sends no page, so the reader sees no article.

The error shows up on the server side: in the terminal, or on the framework's error page. It does not come from the browser, because the browser never receives this page.

```tree caption="The same createContext line in a client file vs. in a server file."
Where `createContext` runs
- +In a file with `'use client'` [`createContext`] | The file **runs in the browser** | Components that read the context **stay alive** and re-render when it changes
- !In a file without a directive [`App.jsx`] | The file **runs on the server** | The copy of React on the server has **no `createContext`**, so the page **never arrives**
```

Remember: context lives only in the browser, so `createContext` goes in a file that starts with `'use client'`.

## PRINCIPLE | `UserProvider` with `'use client'`: the server passes `user` as a prop, and the provider makes the context

> [!PRINCIPLE]
> **Principle 2: The Client Provider: `UserProvider` Takes `user` as a Prop From the Server**
>
> *Put `createContext` and the provider in a file with `'use client'`; let the Server Component read the value, pass it as a prop, and pass the page between the tags as `children`.*
>
> The server can read the database but cannot make context. The browser can make context but cannot read the database. So the server reads the user and hands it over as an ordinary prop, and a small Client Component provides it. Because the value travels from the server to the browser, it must be plain data.
>
> **DO THIS:**
> ```jsx
> export default async function App() {
>   const user = await db.users.get(1);
>   return ~<UserProvider user={user}>~<Article /></UserProvider>; // The server reads; the client provider provides
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default async function App() {
>   const row = await db.users.get(1);
>   return <UserProvider ~user={row}~><Article /></UserProvider>; // **WRONG:** row holds a signOut method, which cannot cross, so the page stops
> }
> ```

### Two Small Files: One Reads the User, One Provides It

The fix splits the work the way the plain JavaScript page did. The server file keeps what only the server can do: it reads the user. A new client file does what only the browser can do: it makes the context and provides it.

```jsx title="src/UserProvider.jsx" startLine="1"
'use client';

import { createContext } from 'react';

export const UserContext = createContext(null);

export default function UserProvider({ ~user, children~ }) { // user and the page both arrive as props from App
  return <UserContext value={user}>{children}</UserContext>;
}
```

```jsx title="src/App.jsx" startLine="1"
import UserProvider from './UserProvider';
import AccountButton from './AccountButton';
import Article from './Article';
import db from './db';

export default async function App() {
  const user = await db.users.get(1);
  return (
    ~<UserProvider user={user}>~ {/* The server value crosses as an ordinary prop */}
      <header><AccountButton /></header>
      <Article />
    </UserProvider>
  );
}
```

`App` writes `<UserProvider user={user}>`, with the page between the tags. **Yes, it is the exact same thing as any Client Component that receives a prop from the server!** React's docs show the same shape with a counter. A Server Component reads a value and renders `<Counter initialValue={initialValue} />`. Here the value is the user, and the Client Component is a provider.

`UserProvider` has one job: it renders the provider around whatever it receives. It knows nothing about the header or the article.

### Where `user`, `children`, and `UserContext` Come From

1. **`user`** is the object `App` writes on the `<UserProvider>` tag. React puts it in `props.user`, as with any prop (as seen in Lesson 08).
2. **`children`** is the header and the article that `App` writes between the tags (as seen in Lesson 09).
3. **`UserContext` has `export`**, so that the account button and the comment form can import the very same object. React's docs: "it's common to declare contexts in a separate file. Then you can use the `export` statement to make context available for other files".

And `db.js` plays the database. It answers `db.users.get(1)` with one plain object:

```js title="src/db.js" startLine="1"
const users = [{ id: 1, name: 'John' }];

const db = {
  users: {
    async get(id) {
      return ~users.find(user => user.id === id)~; // Plays a real database: answers with the user whose id is 1
    },
  },
};

export default db;
```

### What Happens When the Reader Opens the Page

Nothing stops now. Here is the trip of `John`, in order:
1. On the server, `App` awaits `db.users.get(1)` and gets the user object, with the id 1 and the name John.
2. `App` renders `<UserProvider user={user}>`. The provider file starts with `'use client'`, so `UserProvider` is a Client Component. The `user` object must cross to it as a prop.
3. `user` is a plain object with a number and a string, so it can cross (as seen in Lesson 107). React's docs list "Plain objects" with serializable properties among the values a Client Component may receive.
4. `UserProvider` runs with `user` in its props. Its file made `UserContext` in the browser, where context exists, so it provides `John` to everything between its tags.

The provider adds no element of its own to the page. In the Elements panel, `<header>` and `<article>` sit directly where the provider was.

### VS | `<UserContext value={user}>` vs. `<UserContext.Provider value={user}>`: two spellings of the same provider

Inside the provider file, you may meet the provider written two ways, especially in framework docs and older code:

```jsx title="Two ways to write the provider inside UserProvider.jsx"
<UserContext ~value={user}~>{children}</UserContext> {/* React 19: the context itself is the provider */}
<UserContext.Provider ~value={user}~>{children}</UserContext.Provider> {/* Before React 19: the same provider */}
```

**Yes, it is the exact same thing!** React's docs: "Starting in React 19, you can render `<SomeContext>` as a provider. In older versions of React, use `<SomeContext.Provider>`."

### The Database Row That Cannot Cross

Our `db.js` answers with a plain object. A real database often answers with more than plain fields. The user row may hold a `signOut` method, or it may be an instance of a `User` class. Suppose a developer passes that whole row on:

```jsx title="src/App.jsx" startLine="6" bad="8"
export default async function App() {
  const user = await db.users.get(1);
  return <UserProvider ~user={user}~><Article /></UserProvider>; // **WRONG:** user holds a signOut method, which cannot cross to the browser
}
```

**The page stops with an error, because a function cannot travel from the server to the browser.** React's docs list two kinds of values that cannot cross. The first is "Functions that are not exported from client-marked modules or marked with `'use server'`". The second is "Objects that are instances of any class" (as seen in Lesson 107). The fix is to pass only the plain fields the page shows:

```jsx title="src/App.jsx" startLine="6"
export default async function App() {
  const row = await db.users.get(1);
  const user = ~{ id: row.id, name: row.name }~; // Only plain fields cross: the id 1 and the name John
  return <UserProvider user={user}><Article /></UserProvider>;
}
```

```tree dir=right caption="The two files of the fix: App.jsx reads the user on the server, and UserProvider.jsx provides it in the browser."
How `App` hands the user to the provider
- +1. `App.jsx` on the server [`await`] | Reads **the user John** from `db.js` | Passes plain fields as **`user={user}`**
- +2. The prop crosses [`user`] | A **plain object** with a number and a string | ~Do **NOT** pass a row with **methods** or a **class instance**
- +3. `UserProvider.jsx` in the browser [`'use client'`] | **Makes `UserContext`** and renders the provider | Provides **John** to its **`children`**
```

Remember: the server reads the user, and the client provider provides it.

## PRINCIPLE | `<UserContext>` in a Server Component: the server can pass the context on, but never read it

> [!PRINCIPLE]
> **Principle 3: The Server Passes, Never Reads: `App.jsx` Can Write `<UserContext>` but Cannot Read It**
>
> *A Server Component never reads context; it can only pass a value to a client provider, and leave the reading to Client Components.*
>
> When a server file imports from a `'use client'` file, it holds only a placeholder that points to the real export in the browser. It can pass that placeholder on as a tag, and React renders it in the browser. It cannot look inside it: `use(UserContext)` stops the page, and `useContext` does not exist on the server.
>
> **DO THIS:**
> ```jsx
> export default async function App() {
>   const user = await db.users.get(1); // The server reads the database, not the context
>   return <p>Hello, {~user.name~}</p>; // The greeting shows John, with no context involved
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default async function App() {
>   const user = ~use(UserContext)~; // **WRONG:** Cannot use() an already resolved Client Reference
>   return <p>Hello, {user.name}</p>;
> }
> ```

### VS | Writing `<UserContext>` vs. Reading `UserContext` in `App.jsx`: the server can pass it on, but not read it

After Principle 2, `UserContext` lives in a client file and has `export`. So `App.jsx` can import it. A developer then tries two things in the server file. First, the developer writes the context tag directly, without `UserProvider`:

```jsx title="App.jsx writes the UserContext tag"
import { UserContext } from './UserProvider';

export default async function App() {
  const user = await db.users.get(1);
  return <~UserContext~ value={user}><Article /></UserContext>; // The server passes the tag on: the page shows John
}
```

Second, the developer reads the context in the server file, to show the name in a greeting:

```jsx title="App.jsx reads UserContext"
import { use } from 'react';
import { UserContext } from './UserProvider';

export default async function App() {
  const user = ~use(UserContext)~; // **WRONG:** the server cannot read context, and the page stops
  return <p>Hello, {user.name}</p>;
}
```

Both files use the same `UserContext`, imported from the same client file. **It may look the same, but it is NOT the same thing!** Writing the tag works, and the page shows `John`. Reading the context stops the page on the server, with this error:

```text title="The error when App.jsx reads UserContext with use"
Cannot use() an already resolved Client Reference.
```

### What the Server Holds When It Imports From a `'use client'` File

> [!DEFINITION]
> **A Client Reference.** [NEW] When a server file imports something from a `'use client'` file, it does not get the real export. It gets a placeholder object that records only two things: which file, and which export. React's error message calls this placeholder a Client Reference. The server can put it into what it sends to the browser, and there React swaps it for the real export. The server cannot look inside it, because the real export exists only in the browser (Lesson 116).

So `App.jsx` holds a placeholder, not the real `UserContext`. Here is what each line does with it:
1. **Writing `<UserContext value={user}>`** puts the placeholder in what the server sends to the browser, together with the `value` prop. The server sends `<UserProvider user={user}>` the same way. In the browser, React finds the real `UserContext` and renders the provider.
2. **Reading with `use(UserContext)`** asks the server to look inside the context and find the provider above. The server holds only the placeholder, so React stops with the error above. React's docs: "Reading context with `use` is not supported in Server Components."
3. **Reading with `useContext(UserContext)`** fails even earlier. The copy of React on the server has no `useContext`, as Principle 1 showed.

So a server file can pass a client file's export on to the browser, but it can never look inside it.

```tree caption="Writing the UserContext tag vs. reading UserContext, both in App.jsx: the server can pass the export on, but cannot look inside it."
What `App.jsx` can do with the imported `UserContext`
- +Write its tag [`<UserContext value={user}>`] | The server **passes the placeholder on** to the browser | In the browser, React renders the provider, and the page **shows John**
- !Read it [`use` `useContext`] | The server would need to **look inside the context** | React **stops the page** with an error, or finds **no `useContext`** at all
```

### Why We Still Write `UserProvider`

With the context tag written in `App.jsx`, the page in React 19 looks exactly as it does with `<UserProvider user={user}>`. Our page still keeps `UserProvider`, for two reasons:
1. **It is the shape React's docs promise.** React's docs say a server file may take from a `'use client'` file only "a React component or supported serializable prop values". `UserProvider` is a component, so it follows that rule. The context object is neither a component nor a plain value, so writing its tag in a server file is outside what the docs promise.
2. **It is the place to grow.** Later the browser may need to change the value, such as a theme the reader switches. Then the provider must keep state. Only a component can hold state, and `UserProvider` is that component.

Remember: the server passes the context on, and only Client Components read it.

## PRINCIPLE | `useContext` under the provider: every Client Component reads the same user, at any depth

> [!PRINCIPLE]
> **Principle 4: Reading Context: `CommentForm` Reads `John` With `useContext`**
>
> *Read the server value in any Client Component under the provider with plain `useContext`; keep a provider above every component that reads it.*
>
> The component that reads the context does not know where the value came from. `useContext` finds the closest provider above it, through any components in the middle, Server Components included. With no provider above, it returns the default value, and reading a field of `null` stops the page.
>
> **DO THIS:**
> ```jsx
> 'use client';
> export default function CommentForm() {
>   const user = ~useContext(UserContext)~; // UserProvider above provides John
>   return <p>Commenting as {user.name}</p>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function GalleryPage() {
>   return ~<CommentForm />~; // **WRONG:** no UserProvider above, so useContext returns null and user.name throws
> }
> ```

### The Same `useContext` Line From Lesson 28

Once the provider holds `John`, a Client Component reads it with the one line from Lesson 28:

```jsx title="src/AccountButton.jsx" startLine="1"
'use client';

import { useContext } from 'react';
import { UserContext } from './UserProvider';

export default function AccountButton() {
  const user = ~useContext(UserContext)~; // Reads the user John from the closest provider
  return <button>{user.name}</button>;
}
```

**Yes, it is the exact same thing as in Lesson 28!** The account button does not know, and does not need to know, that the value came from the server. Every component that reads the context sees only the value, never where it came from.

### `CommentForm`, Deep Inside a Server Component

The comment form reads the same user with the same line. It sits inside `Article`, a Server Component:

```jsx title="src/CommentForm.jsx" startLine="1"
'use client';

import { useContext } from 'react';
import { UserContext } from './UserProvider';

export default function CommentForm() {
  const user = ~useContext(UserContext)~; // The same user, read one level deeper than AccountButton
  return (
    <div>
      <p>Commenting as {user.name}</p>
      <textarea />
      <button>Post</button>
    </div>
  );
}
```

```jsx title="src/Article.jsx" startLine="1"
import CommentForm from './CommentForm';

export default function Article() { // No directive: a Server Component in the middle
  return (
    <article>
      <h1>Our new park opens</h1>
      ~<CommentForm />~ {/* A Client Component inside a Server Component */}
    </article>
  );
}
```

The page is complete. Both places show `John`:

```page caption="The finished news page: the account button and the comment form both read John from UserProvider."
url: news.example.com/new-park
line: [John]
heading: Our new park opens
form:
  textarea: Commenting as John |
  button: Post
console: quiet
```

**The comment form reads `John`, even though `Article`, the Server Component around it, could never read the context.** Here is why, in order:
1. `UserProvider` sits above both the account button and the comment form in the render tree.
2. `useContext` returns the value of the closest provider above the component that calls it. React's docs: "the `value` passed to the closest `SomeContext` above the calling component in the tree".
3. The components in the middle do not matter, whatever kind they are. React's docs: "Context passes through any components in the middle." `Article` is just one more component in the middle.

For context, the account button in the header and the comment form inside the article are the exact same thing: both find the same `UserProvider` above them.

The Elements panel shows only real HTML. The provider and the components add no element of their own:

```dom caption="What the Elements panel shows: the button and the comment form, with no element for UserProvider."
<header>
+ <button>John</button> | note: From AccountButton
</header>
<article>
  <h1>Our new park opens</h1>
+ <div> | note: From CommentForm, inside the Server Component Article
    <p>Commenting as John</p>
    <textarea></textarea>
    <button>Post</button>
  </div>
</article>
```

### A Page With No Provider Above the Comment Form

**A component that reads the context with no provider above it gets `null`, and the page stops.** A developer adds the comment form to a second page, a photo gallery, and `App` does not wrap that page in `UserProvider`. The reader opens the gallery and sees no gallery. Here is why, in order:
1. With no provider above it, `useContext` returns the default value of the context. Our file gave `createContext` the default value `null`. React's docs: "If there is no such provider, then the returned value will be the `defaultValue`".
2. The comment form then reads `user.name`, which asks for a property of `null`.
3. JavaScript stops with a `TypeError`, and React shows no gallery.

The fix is to render `UserProvider` above every page that holds a component that reads the user. A custom Hook that gives a clearer error message for this case is the topic of Lesson 165.

```tree caption="AccountButton and CommentForm read the same provider at two depths; a CommentForm with no provider above it gets null."
Where a Client Component reads `UserContext`
- +In the header [`AccountButton`] | The closest provider above is **`UserProvider`** | Shows **John**
- +Inside a Server Component [`CommentForm` in `Article`] | Context **passes through `Article`** | Shows **Commenting as John**
- !With no provider above [`CommentForm` on the gallery page] | Gets the default value **`null`** | **`TypeError`** at `user.name`
```

Remember: under the provider, plain `useContext` reads the user at any depth.

## PRINCIPLE | `children` of the provider: a Server Component inside `UserProvider` stays on the server

> [!PRINCIPLE]
> **Principle 5: The Imports Decide: `Article` Inside `UserProvider` Stays a Server Component**
>
> *Wrap the page in the client provider from a Server Component, and pass the page as `children`; those components stay on the server, and they read server data themselves, never the context.*
>
> A provider at the top of the page does not move the page to the browser. Only the files that a `'use client'` file imports become client code. `Article` is imported by `App`, so it runs on the server, and `UserProvider` receives only its output. Because `Article` runs on the server, it cannot read the context around it.
>
> **DO THIS:**
> ```jsx
> export default async function App() {
>   const user = await db.users.get(1);
>   return <UserProvider user={user}>~<Article />~</UserProvider>; // App imports Article: it stays on the server
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> 'use client';
> ~import Article from './Article';~ // **WRONG:** the provider file pulls Article and its imports into the browser
> ```

### VS | Inside the Provider on the Screen vs. Imported by the Provider File: the imports decide where `Article` runs

Look at the render tree of our page. Everything, the header and the article, sits inside `UserProvider`, a Client Component. So it seems the whole page must now run in the browser. **It may look the same, but it is NOT the same thing!** Compare two ways to put `Article` inside `UserProvider`:

```jsx title="App.jsx writes Article between the provider tags"
<UserProvider user={user}>
  ~<Article />~ {/* App imports Article: Article runs on the server */}
</UserProvider>
```

```jsx title="UserProvider.jsx imports Article itself"
'use client';
import Article from './Article';

export default function UserProvider({ user }) {
  return <UserContext value={user}>~<Article />~</UserContext>; // **WRONG:** Article becomes client code
}
```

On the screen, both put the article inside the provider. But where `Article` runs depends on which file imports it, not on where its tag sits (as seen in Lesson 115):
1. **When `App.jsx` writes `<Article />` between the provider tags,** the provider file never imports `Article`. `App.jsx` imports it, so `Article` runs on the server. The provider receives only its output in `children`. React's docs, on their own example: "the `InspirationGenerator` module never directly imports the `Copyright` module nor calls the component, all of that is done by App."
2. **When `UserProvider.jsx` imports `Article`,** `Article` becomes client code, together with everything it imports. React's docs: "Add `'use client'` at the top of a file to mark the module and its transitive dependencies as client code."

Our page writes `<Article />` in `App.jsx`. So only three files go to the browser: the provider, the account button, and the comment form. The article, the page file, and the database stand-in stay on the server.

```tree caption="Article inside UserProvider on the screen vs. Article imported by UserProvider.jsx: the imports decide where it runs."
Where does `Article` run?
- +`App.jsx` imports it [`<Article />` between the provider tags] | `Article` **runs on the server** | `UserProvider` gets **only its output** in `children`
- !`UserProvider.jsx` imports it [`import Article` under `'use client'`] | `Article` and its imports **become client code** | Its code **joins the bundle** every reader downloads
```

### A Server Component Inside the Provider Still Cannot Read It

Staying on the server has a second side: `Article` still cannot read the context around it. Suppose the editors want the heading to greet the reader with `Hello, John`. A developer reaches for the context in `Article`, because the article sits inside the provider:

```jsx title="src/Article.jsx" startLine="1" bad="5"
import { useContext } from 'react';
import { UserContext } from './UserProvider';

export default function Article() {
  const user = ~useContext~(UserContext); // **WRONG:** Article is a Server Component, and the copy of React on the server has no useContext
  return <h1>Hello, {user.name}</h1>;
}
```

The page stops, exactly as in Principle 1. `Article` sits inside the provider on the screen, yet it is a Server Component, and Server Components cannot read context. A Server Component that needs the user reads it on the server, from the database:

```jsx title="src/Article.jsx" startLine="1"
import db from './db';

export default async function Article() {
  const user = ~await db.users.get(1)~; // A Server Component reads the user itself, not from context
  return <h1>Hello, {user.name}</h1>;
}
```

Now `App` and `Article` each read the user. To make both reads share one call to the database in one request, React gives `cache()`, the topic of Lesson 123.

Teams that believe the provider turns the page into client code make the opposite mistake. They keep the provider away from the top of the page, and pass `user` as a prop through every Server Component down to the comment form. That brings back the passing through every layer that context exists to remove.

Remember: the imports decide where code runs, so the page inside the provider stays on the server.

When the reader opens the page, React first renders the Server Components on the server. Then the Client Components render with the user in hand, and context carries `John` from the provider to both components that read it:

```tree dir=right caption="The order in which React renders the news page: the server reads the user, the provider provides it, and two Client Components read it."

- +2. `Article` on the server [`<Article />`] | Returns the heading and a **`<CommentForm />` tag** | Its code **stays on the server**
- +3. `UserProvider` [`'use client'`] | Receives **`user`** and the finished page in **`children`** | **Provides John** to everything inside

```

### Summary

| Principle | What the code does | What the reader sees |
| :--- | :--- | :--- |
| **1. Context made in a client file** | `createContext` runs only in `UserProvider.jsx` | The page arrives, instead of no article at all |
| **2. The value crosses as a prop** | `App` reads the user and passes plain fields as `user={user}` | `John` appears in the first page the server sends |
| **3. The server passes, never reads** | `App` renders the provider and never calls `use` or `useContext` | The page renders, with no error from the server |
| **4. Plain `useContext` at any depth** | `AccountButton` and `CommentForm` read the closest provider | `John` on the button and above the comment form |
| **5. `children` stay on the server** | Only `App` imports `Article` | The article's code stays out of the reader's browser |

Remember the one sentence of this lesson. **Context lives only in the browser. The server reads the user and passes it as a prop to a Client Component provider, and every Client Component below reads it with `useContext`.**

## For the Interview

> **The Interview Question:** How does context behave across the server/client boundary?

### How to Answer Clearly in 30 Seconds

"Context is a client feature. A Server Component runs once and does not stay in memory, so there is nothing on the server for context to re-render. The copy of React on the server leaves out `createContext` and `useContext`, and reading context with `use` is not supported there.

So the work splits in three:
1. **The server reads the value.** A Server Component awaits the user from the database.
2. **A Client Component provides it.** A small `'use client'` file makes the context and renders the provider. The Server Component renders it with the value as a prop, which must be serializable, and the page as `children`.
3. **Client Components read it.** Any Client Component under the provider reads the value with plain `useContext`, at any depth, even inside a Server Component.

The page passed as `children` stays on the server, because the imports decide where code runs, not the place on the screen. Those Server Components cannot read the context; they read the data themselves."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does a provider rendered from a Server Component throw?"**
   **It throws when the server must make the context or read it.** A server file that calls `createContext` stops at once, because the copy of React on the server has no `createContext`. A server file that reads the context with `use` stops with the error `Cannot use() an already resolved Client Reference`. When the context comes from a `'use client'` file, the server holds only a Client Reference. It is a placeholder the server can pass on to the browser, but never look inside. The safe shape is a Client Component, such as `UserProvider`, that makes the context, renders the provider, and receives the server value as a prop.
2. **"Does a client provider at the root make the whole app client-rendered?"**
   **No.** The components a Server Component passes as `children` stay Server Components. React's docs explain this with `Copyright` inside `InspirationGenerator`: the client file never imports `Copyright`, so `Copyright` stays on the server. Only the files a `'use client'` file imports become client code, so the bundle holds the provider and the components that read it, not the page.
3. **"What if the browser must change the value, such as a theme the user switches?"**
   **The provider keeps state that starts from the server prop.** `UserProvider` becomes a `ThemeProvider` with `useState(initialTheme)`, the same shape as the `Counter` with `initialValue` in React's docs. A click changes the state, and React re-renders every component that reads the context. That is exactly why the provider must be a Client Component. Keeping those re-renders fast is the topic of Lesson 59.

```tree dir=right caption="Interview summary: the server reads the value, a client provider provides it, and only Client Components read it."
Context across the server and client boundary
- +The server [`App.jsx`, no directive] | **Reads the value** from the database | Passes it as a **serializable prop**, and the page as **`children`**
- +The client provider [`UserProvider.jsx`, `'use client'`] | **Makes the context** and renders the provider | The place to add **state** when the browser must change the value
- !What breaks it [`createContext` `use` `useContext` on the server] | Making or reading context **in a Server Component** | The server **stops the page**, and the reader gets **no article**
```
