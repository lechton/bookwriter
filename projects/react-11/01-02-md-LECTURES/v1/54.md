# Lecture 54: Why a Re-render Is Usually Fast and Harmless

*(Why does the Console fill up with lines from a component that did not change?)*

> INTERVIEW QUESTION | ❱❱ MORE | When does a component re-render, and why is re-rendering children usually fast and harmless?

---

## VS | A Re-render `Message rendered` vs. a DOM Change `<li>`: React calls the function again, but changes only the DOM nodes that differ

> You type one letter into a chat, and a `console.log` inside a message you never touched prints a new line. **That line is a re-render: React called the message function again to ask what it should show, and React changes the page only where the answer is different from last time.** A function call that returns the same JSX as before costs a tiny bit of JavaScript and changes no DOM node, so measure before you optimize anything.

Remember how you change a page in plain JavaScript? You find the one element, and you change it yourself. Nothing else on the page runs:

```js title="Plain JavaScript: you change the one element yourself"
document.getElementById('count').~textContent = '4 messages'~; // Only this element changes, and no other code runs
```

In React, you never write into the DOM. You call a setter, and React does two things, one after the other:
1. **React renders.** It calls your component function again, from the top, to ask: "What should the page show now?" It also calls every component that this function returns. This is the re-render, and this is what a `console.log` inside a component reports.
2. **React commits.** It compares the new JSX with the JSX from last time, and changes only the DOM nodes that are different.

```jsx title="React: you call the setter, and React decides what to change"
~setText('O')~; // React calls ChatRoom and its children again, then changes only the DOM nodes that differ
```

So a line that says "rendered" in the Console means "React called this function". It does not mean "React rebuilt this part of the page". The two feel like one event. They are NOT the same thing.

> [!DEFINITION]
> **Rendering and committing.** [REVIEW] Every screen update has two separate steps. Rendering is React calling your component functions to get their JSX. Committing is React changing the DOM so that it matches that JSX. A component can render without any change on the page, when its JSX is the same as last time (Lesson 13).

> [!DEFINITION]
> **StrictMode calls every component twice.** [REVIEW] Our project mounts `<App />` inside `<StrictMode>`. In development, StrictMode calls every component function twice on purpose, so every `console.log` inside a component prints two lines. With React Developer Tools installed, the second line of each pair appears slightly dimmed in the Console. In production, each component is called once (Lesson 47).

### One Letter, and an Untouched Message Logs Again

Here is the smallest chat screen that shows it. `ChatRoom` keeps what the user types in state. `Message` shows one message:

```jsx title="The smallest chat screen"
function ChatRoom() {
  const [text, setText] = useState('');
  return (
    <>
      <Message text="Hi!" />
      <input value={text} ~onChange={e => setText(e.target.value)}~ /> {/* Every letter the user types calls setText */}
    </>
  );
}

function Message({ text }) {
  ~console.log('Message rendered:', text);~ // Prints each time React calls Message
  return <p>{text}</p>;
}
```

When the page opens, one message, `Hi!`, sits above an empty `<input>` field. The Console already has two lines, because StrictMode called `Message` twice:

```page width=text caption="The smallest chat screen when it opens: one message, Hi!, above an empty input field, and two lines in the Console."
line: Hi!
form:
  field:  |
log: Message rendered: Hi!
log: Message rendered: Hi!
```

We clear the Console. Now the user types the letter `O` into the field:

```page width=text caption="The same screen after the user types O: the message still reads Hi!, and the Console prints Message rendered: Hi! again."
line: Hi!
form:
  field:  | O | good
log: Message rendered: Hi!
log: Message rendered: Hi!
```

**React called `Message` again, although the message did not change.** Its `text` prop is still `"Hi!"`, and the page still shows `Hi!`. The next letter does the same, and so does every letter after it.

So what did React do to the page? Nothing. `Message` returned the same `<p>Hi!</p>` as last time, so React left the `<p>` node alone. React's docs say it plainly: "React does not touch the DOM if the rendering result is the same as last time."

```tree dir=right caption="One letter typed by the user: React calls Message again, but the p node on the page stays as it was."
What one letter does to `Message`
- +Render [`<Message text="Hi!" />`] | React **calls `Message` again** | The Console prints **`Message rendered: Hi!`**
- +Commit [`<p>Hi!</p>`] | The result is **the same as last time** | React **leaves the `<p>` node alone**
```

> [!DEFINITION]
> **A re-render.** [NEW] A re-render is React calling a component function again, after its first render, to get its new JSX. It happens for exactly three reasons. First, the component's own state changed. Second, its parent re-rendered. Third, a context it reads got a different value. A re-render is only a function call: React then changes the DOM only where the new JSX differs from the old one (Lesson 54).

### What a Re-render Costs the User

The user never sees a re-render. The user feels only one thing: how fast the letters appear while typing.
1. **The common case.** Each letter re-renders a few messages in about two milliseconds, and the letter appears in the field at once. Adding optimizations to every component changes nothing the user can see. It only makes the code harder to read.
2. **The rare case.** One component that re-renders on every letter does slow work, and the typing lags: each letter appears late. React's docs describe a slow list whose re-render "makes the typing feel janky", which means the letters stutter onto the screen.

Which case are you in? A Console full of lines cannot tell you. Only a measurement can.

### The Rule of Thumb: measure first, then pick a fix

**A re-render is React calling your function again, and that is cheap. Leave it alone, measure, and act only when the user can feel a lag.**

A senior developer knows the three classic misreadings:
1. **"Rendered" means "the page was rebuilt".** It does not. It means React called the function. Every log line is a function call, not a DOM change.
2. **Twenty log lines mean a slow app.** A developer sees twenty children log after one click, and wraps every component and every handler in an optimization, without measuring anything.
3. **A child re-renders only when its props change.** It does not. A child re-renders whenever its parent re-renders.

When a measurement does show a slow component, there are four ways to handle it:
1. **Leave it, and measure first.** This fits most cases, and it is the subject of this lesson. React's docs say: "Don't optimize prematurely!"
2. **Move the state down, or pass JSX as `children`.** This fits when the state sits higher in the tree than the components that need it, so every change re-renders more than it must (Lesson 58).
3. **Memoize with `memo`, `useMemo`, and `useCallback`.** To memoize means to remember a result and reuse it while its inputs stay the same. This fits a component that re-renders often with the same props and does expensive work while rendering (Lessons 55 to 57).
4. **Let the React Compiler memoize for you** when the project is built (Lesson 63).

Remember the one sentence of this lesson. **A re-render is React calling your function again, and that is cheap: React changes only the DOM nodes whose result is different.**

**PRINCIPLES:** A re-render is React calling a component function again. It has three causes, it is a separate step from changing the DOM, and its cost can be measured. Four principles follow:
1. **Principle 1: A State Change Renders Every Component Below It Again.** When the state of `ChatRoom` changes, React calls `ChatRoom` and every `Message` it returns, even though no message changed. React does not call the components above `ChatRoom`.
2. **Principle 2: A Context Change Renders Every Reader Again.** A component that reads a context re-renders when the provider above it gets a different `value`. No component between the provider and the reader can stop it.
3. **Principle 3: React Changes Only the DOM Nodes That Differ.** After the user clicks `Send`, React calls four `Message` functions, but only one returns something new. React adds one `<li>` and leaves the other three alone.
4. **Principle 4: Measure Before You Optimize.** Counting log lines tells you how many times a function ran. `<Profiler>` tells you how long it took. Act only when the user can feel a lag.

## PRINCIPLE | setText: ChatRoom and every Message below it render again, even with the same props

> [!PRINCIPLE]
> **Principle 1: Parent Re-render: A State Change Renders Every Component Below It Again**
>
> *When the state of a component changes, React re-renders that component and every component it returns, down the tree, even when the props of a child did not change; React does not call the components above it.*
>
> A child does not wait for new props. React calls it whenever its parent re-renders, so every letter typed into the field re-runs every message. Keep fast-changing state, such as the text of an `<input>` field, in the component that needs it, so each letter re-renders as little of the tree as possible.
>
> **DO THIS:**
> ```jsx
> function ChatRoom() {
>   const [text, setText] = ~useState('')~; // Each letter re-renders ChatRoom and its messages only
>   return <input value={text} onChange={e => setText(e.target.value)} />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   const [text, setText] = ~useState('')~; // **WRONG:** the text of the field at the top: each letter re-renders App and everything below it
>   return <ChatRoom text={text} setText={setText} />;
> }
> ```

### A child re-renders because its parent re-rendered

Go back to the smallest chat screen. `Message` received the same `"Hi!"` after every letter, and React called it anyway. Why? Because React does not check whether the props of a child changed. When `ChatRoom` re-renders, React calls every component that `ChatRoom` returns, and `Message` is one of them:

```jsx title="The smallest chat screen, again"
function ChatRoom() {
  const [text, setText] = useState('');
  return (
    <>
      ~<Message text="Hi!" />~ {/* ChatRoom returns this tag on every render, so React calls Message every time */}
      <input value={text} onChange={e => setText(e.target.value)} />
    </>
  );
}
```

So a child has a second reason to re-render, besides its own state: its parent re-rendered. React's docs: "React normally re-renders a component whenever its parent re-renders."

And what about a changed prop? It is not a separate cause. A new prop is only what the new render of the parent happens to pass down. Many developers believe that a child with the same props is skipped. It is not.

### The real mistake: twenty lines, and an optimization everywhere

This is where most re-render worry starts at work:
1. A developer puts a `console.log` in a child component to debug something else.
2. They type in a field, or click a button, in the parent.
3. The Console fills up with the log of the child: twenty lines for twenty children.
4. They decide the app is slow, without measuring.
5. They wrap every component and every handler in one of the optimizations of Lessons 55 to 57.

React's docs describe what this costs. Some teams "memoize as much as possible. The downside of this approach is that code becomes less readable." Meanwhile, the user sees no difference at all.

### Three facts interviewers ask about

**Setting state to the value it already holds skips the re-render.** Say our code calls `setText('')` while the field is already empty. React compares the old and the new value with `Object.is` (as seen in Lesson 35). They are equal, so React skips re-rendering `ChatRoom` and its children. The docs add that "in some cases React may still need to call your component before skipping the children".

**Several updates in one event cause one re-render.** React batches them (as seen in Lesson 16). A handler that calls two setters re-renders the component once. We will see it with the `Send` button in Principle 3.

**Where the state lives decides how much re-renders.** Our `text` state lives in `ChatRoom`, not in `App`. So each letter re-renders `ChatRoom` and its messages, and nothing above them. React's docs give this advice: "don't keep transient state like forms and whether an item is hovered at the top of your tree." Transient state is state that changes often and matters only for a moment, such as the text in an `<input>` field. A component at the top of the tree re-renders everything beneath it, so state kept there costs the most.

## PRINCIPLE | useContext: a different provider value renders every reader again

> [!PRINCIPLE]
> **Principle 2: Context: A Context Change Renders Every Component That Reads It Again**
>
> *A component that reads a context with `useContext` re-renders when the closest provider above it gets a different `value`, compared with `Object.is`; no component between the provider and the reader can stop it.*
>
> A prop reaches a child only when its parent renders again. A context reader is re-rendered by React itself when the value of the provider changes. A string value such as `'dark'` changes only when the theme changes. An object written in place on the provider is a new object on every render, so every reader re-renders every time.
>
> **DO THIS:**
> ```jsx
> <ThemeContext ~value={theme}~> {/* A string: readers re-render only when the theme really changes */}
>   <ChatRoom />
> </ThemeContext>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ThemeContext ~value={{ theme, setTheme }}~> {/* **WRONG:** a new object on every render of App re-renders every reader, even when theme stayed the same */}
>   <ChatRoom />
> </ThemeContext>
> ```

### VS | The theme as a prop vs. the theme from context: who makes Message render with the new theme

Our messages should turn dark when the user clicks `Toggle theme`. The theme can reach `Message` in two ways. Both put the theme on the `<li>` as its `className`, and both make the messages dark after the click:

```jsx title="The theme passed as a prop to Message"
<Message ~theme={theme}~ text={m.text} /> {/* ChatRoom must receive theme, and write it on every tag */}

function Message({ theme, text }) {
  return <li className={theme}>{text}</li>;
}
```

```jsx title="The theme read from ThemeContext inside Message"
function Message({ text }) {
  const theme = ~useContext(ThemeContext)~; // React finds the closest ThemeContext above and returns its value
  return <li className={theme}>{text}</li>;
}
```

They work the same at first, but they are NOT the same thing. The difference is who makes `Message` re-render with the new theme:
- **With `theme` as a prop**, the new theme travels down one parent at a time. It reaches `Message` only when `ChatRoom` renders again and writes the new value on the tag.
- **With `useContext(ThemeContext)`**, React itself re-renders `Message` when the `value` of the provider changes. The docs: "React automatically re-renders all the children that use a particular context starting from the provider that receives a different `value`."

So a component that reads a context has a third reason to re-render: the context changed. React compares the old and the new `value` with `Object.is`. A string such as `'dark'` compares by its text, so `'dark'` and `'light'` are different values.

Why does the difference matter? Because of components in between that skip their re-render. In Lesson 55 we meet `memo`, which lets a component skip a re-render when its props are the same. If `ChatRoom` skipped its re-render, a theme passed as a prop would never reach the messages. A theme read from context still does, because `memo` checks props only. The docs: "Skipping re-renders with `memo` does not prevent the children receiving fresh context values."

```tree caption="Two ways the theme can reach Message, and what makes Message re-render in each."
How the theme reaches `Message`
- +As a prop [`<Message theme={theme} />`] | Reaches `Message` **only when its parent renders again** | If a component in between **skips its re-render**, the new theme **never arrives**
- +From context [`useContext`] | React re-renders `Message` **when the value of the provider changes** | **No component in between can stop it**
```

### ThemeContext in the chat room

We take the context way. First, a new file creates the context:

```js title="src/ThemeContext.js"
import { createContext } from 'react';

export const ThemeContext = ~createContext('light')~; // The value a reader gets with no provider above it
```

`App` gains the `theme` state, the `Toggle theme` button, and the provider around `ChatRoom`:

```jsx title="src/App.jsx"
import { useState } from 'react';
import { ThemeContext } from './ThemeContext.js';
import ChatRoom from './components/ChatRoom.jsx';

export default function App() {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext ~value={theme}~> {/* Every reader below gets 'light', then 'dark' after the click */}
      <button onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}>
        Toggle theme
      </button>
      <ChatRoom />
    </ThemeContext>
  );
}
```

`Message` reads the theme and puts it on its `<li>`:

```jsx title="src/components/Message.jsx"
import { useContext } from 'react';
import { ThemeContext } from '../ThemeContext.js';

export default function Message({ text }) {
  const theme = ~useContext(ThemeContext)~; // Not a prop: React returns the value of the closest provider
  console.log('Message rendered:', text);
  return <li className={theme}>{text}</li>;
}
```


**One click re-renders the whole tree below `App`, and every message for two reasons at once.** Here is what happens, in order:
1. The user clicks `Toggle theme`. The handler calls `setTheme('dark')` in `App`.
2. React re-renders `App`, because its state changed.
3. `App` returns `<ThemeContext value="dark">`. By `Object.is`, `'dark'` is a different value from `'light'`.
4. React re-renders `ChatRoom`, because its parent re-rendered. The Console prints `ChatRoom rendered`.
5. React re-renders each `Message`, this time for two reasons: its parent re-rendered, and its context changed. The Console prints the three `Message rendered:` lines.
6. In the commit, React changes the `class` of the three `<li>` nodes from `light` to `dark`.

A second click turns the messages light again.

Something that can be tricky: on this page, you cannot see the context reason on its own. The `theme` state sits in `App`, above everything, so every component below re-renders because of its parent anyway. React's docs show the context reason alone with a child wrapped in `memo`, which is Lesson 55.

### The real mistake: a new object as the value of the provider

A developer often wants to give the readers both the theme and the function that changes it:
1. They write `value={{ theme, setTheme }}` on the provider.
2. `App` re-renders for any reason, such as another state variable in `App`.
3. The curly braces build a new object on every render of `App`, so `Object.is` says the value changed.
4. Every component that reads the context re-renders, even when `theme` stayed the same.

The docs: this "will be a *different* object pointing at a *different* function, so React will also have to re-render all components deep in the tree that call `useContext`". They add: "In smaller apps, this is not a problem." The fix belongs to Lesson 59.

## PRINCIPLE | The commit: React changes only the DOM nodes whose result is different

> [!PRINCIPLE]
> **Principle 3: Render vs. Commit: React Changes Only the DOM Nodes That Differ**
>
> *Rendering is React calling the components and working out what changed; committing is React changing only the DOM nodes that differ; painting is the browser drawing the result. A child that returns the same JSX as last time causes zero DOM changes.*
>
> A Console line that says "rendered" reports a function call, not a change on the page. After the user clicks `Send`, four `Message` functions run and one `<li>` is added. A stable key lets React match each new result to its old node, and that is what keeps a re-render cheap.
>
> **DO THIS:**
> ```jsx
> {messages.map(m => (
>   <Message ~key={m.id}~ text={m.text} /> // The same key on every render: React keeps the old li nodes
> ))}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {messages.map(m => (
>   <Message ~key={Math.random()}~ text={m.text} /> // **WRONG:** a new key on every render: React removes and rebuilds every li
> ))}
> ```

### The Send button

Now the user can send a message. `ChatRoom` gains a `handleSend` function:

```jsx title="src/components/ChatRoom.jsx" startLine="15"
  function handleSend() {
    ~setMessages([...messages, { id: messages.length + 1, text }]);~ // A new array with one more message
    setText(''); // Empties the input field
  }
```

The `Send` button goes right after the field:

```jsx title="src/components/ChatRoom.jsx" startLine="27"
      <input value={text} onChange={e => setText(e.target.value)} />
      <button ~onClick={handleSend}~>Send</button> {/* Calls handleSend when the user clicks Send */}
```

Inside `handleSend`, `text` is the state of `ChatRoom` from the last render, the snapshot (as seen in Lesson 15). Our code makes the new `id`, and the key keeps each `<li>` matched to its message (as seen in Lesson 18).

The user types `OK`. We clear the Console, and the user clicks `Send`:

The Elements panel of the browser watches the same click, and it tells a different story:

```dom caption="The Elements panel after Send: React added one li for OK, and the three earlier li nodes are the same nodes as before the click."

  <li class="light">Sure</li> | note: The same node as before the click
  + <li class="light">OK</li> | note: The only node React added
</ul>
```

**The Console says React rendered four messages. The Elements panel says React added one node.** Both are true. React called four `Message` functions, but only one of them returned something new. So the commit adds one `<li>` and leaves the other three alone. Here is what happens, in order:
1. The user clicks `Send`. `handleSend` calls `setMessages` with four messages, then `setText('')`.
2. React re-renders `ChatRoom` once for both updates, because it batches them.
3. React calls `Message` four times. The Console prints the four `Message rendered:` lines.
4. React compares each result with the one from last time. Three of the four are the same as before, so React leaves their `<li>` nodes alone.
5. React adds one `<li>` for `OK`, and empties the field.
6. The browser paints the new line on the screen.

React's docs describe the same steps. During a re-render, React "will calculate which of their properties, if any, have changed since the previous render". Then, in the commit, it applies "the minimal necessary operations" to "make the DOM match the latest rendering output". Only after that, "the browser will repaint the screen". The docs call this last step painting "to avoid confusion" with the rendering that React does.

```tree dir=right caption="One click on Send: four Message functions run, one li is added, and the browser paints one new line."
What one click on `Send` costs
- +Render [`Message` four times] | React **calls four functions** | Three return **the same `<li>` as last time**
- +Commit [`<li class="light">OK</li>`] | React **adds one node** | Leaves **the three old `<li>` nodes alone**
- +Paint | The browser **draws the new line** | The rest of the screen **stays as it was**
```

This is why most re-renders are cheap. A function call that returns the same JSX as last time costs a little JavaScript time, and no DOM work at all.

### What a re-render does not touch

A developer who reads "re-render" as "the browser redraws the component" expects every re-render to lose what the user was doing: the typed text, the cursor in a field, the scroll position. A re-render loses none of them. While the user types `OK`, `ChatRoom` re-renders after each letter, and the cursor stays in the field. React keeps the same `<input>` node and changes only what differs.

React's docs show the same thing with a clock that re-renders every second. React "only updates the content of `<h1>` with the new `time`" and "doesn't touch the `<input>`", so the text the user typed in the field stays.

There is one condition: rendering must be pure (as seen in Lesson 14). The docs: "If re-rendering a component causes a problem or produces some noticeable visual artifact, it's a bug in your component! Fix the bug instead of adding memoization."

### The real mistake: a key that changes on every render

A re-render stays cheap only while React can match each new `<li>` to the old one, and the key does that matching. Say a developer writes `key={Math.random()}`. Every render gives every message a new key. React finds no match, so it removes every `<li>` and builds new ones. The docs: keys generated on the fly "never match up between renders, leading to all your components and DOM being recreated every time." Now each letter really does rebuild the whole list.

## PRINCIPLE | Profiler: actualDuration measures how long a re-render took

> [!PRINCIPLE]
> **Principle 4: Measure First: Read actualDuration Before You Optimize**
>
> *Measure a re-render before optimizing it: wrap the part of the tree in `<Profiler>`, read `actualDuration` in `onRender`, and act only when an interaction has a lag the user can feel.*
>
> The number of log lines says how many times a function ran, never how long it took. `actualDuration` gives the time in milliseconds. Development numbers are higher than production ones, so confirm a slow case on a production build and a slow device before you change the code.
>
> **DO THIS:**
> ```jsx
> <Profiler id="ChatRoom" ~onRender={onRender}~> {/* Prints the real cost of every re-render */}
>   <ChatRoom />
> </Profiler>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Message({ text }) {
>   ~console.log('Message rendered:', text)~; // **WRONG:** as proof that the page is slow: it counts how many times Message ran, not how long it took
>   return <li>{text}</li>;
> }
> ```

### A log line counts calls, a measurement counts time

The Console told us how many times each function ran. It never told us how long they took. Twenty lines can cost a few milliseconds, and one line can cost a whole second. Think of a stopwatch: you do not guess how fast a runner is by counting steps, you time the run. React gives us that stopwatch, a component built for measuring, `<Profiler>`:

```jsx title="Measuring ChatRoom with Profiler"
import { Profiler } from 'react';

function onRender(id, phase, actualDuration) {
  ~console.log(id, phase, actualDuration.toFixed(2), 'ms');~ // Prints the name, the phase, and the time
}

<Profiler ~id="ChatRoom" onRender={onRender}~> {/* Measures ChatRoom and every component inside it */}
  <ChatRoom />
</Profiler>
```

React's docs: "`<Profiler>` lets you measure rendering performance of a React tree programmatically." React provides it, and we import it from `'react'`. It takes two props:
1. **`id`** is a string our code chooses, "identifying the part of the UI you are measuring". React passes it back to us, so we know which part of the page a line is about.
2. **`onRender`** is a function our code writes. React calls it "every time components within the profiled tree update", and passes it the timing.

React calls `onRender` with six arguments: `id`, `phase`, `actualDuration`, `baseDuration`, `startTime`, and `commitTime`. Our function uses the first three:
- **`phase`** says why the tree rendered. It is `"mount"` the first time the tree appears on the page, and `"update"` when it re-renders. A third value, `"nested-update"`, also exists, and we do not meet it in this lesson.
- **`actualDuration`** is "the number of milliseconds spent rendering the `<Profiler>` and its descendants for the current update". This is the cost of the re-render.
- **`baseDuration`** estimates how long a re-render of the whole tree would take without any optimizations. We do not need it here.

### Profiler in the chat room

`App` gets three changes:
1. It imports `Profiler` from `'react'`.
2. It declares `onRender` outside the component.
3. It wraps `ChatRoom` in `<Profiler>`, inside the provider.

```jsx title="src/App.jsx"
import { useState, Profiler } from 'react';
import { ThemeContext } from './ThemeContext.js';
import ChatRoom from './components/ChatRoom.jsx';

function onRender(id, phase, actualDuration) {
  console.log(id, phase, actualDuration.toFixed(2), 'ms');
}

export default function App() {
  const [theme, setTheme] = useState('light');
  return (
    <ThemeContext value={theme}>
      <button onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}>
        Toggle theme
      </button>
      ~<Profiler id="ChatRoom" onRender={onRender}>~ {/* Adds no node to the DOM */}
        <ChatRoom />
      </Profiler>
    </ThemeContext>
  );
}
```

When the page loads, the last line in the Console is the first measurement, with the phase `mount`, as the finished chat room in the example page shows. We clear the Console, and the user types `O`:

```page width=text caption="The chat room after the user types O, measured: after the eight render lines, onRender prints ChatRoom update and about two milliseconds."
line: Sure
```

**Eight render lines in the Console, and the whole re-render took about two milliseconds.** That one number covers `ChatRoom` and its three messages, each called twice by StrictMode. The user sees no lag.

React's docs give the rule for this case: "If there is no perceptible lag when your component re-renders, `memo` is unnecessary." A perceptible lag is a delay the user can feel.

For a single calculation inside a component, the docs give a rough line: if its time adds up to "`1ms` or more", then "it might make sense to memoize that calculation". Something that can be tricky: that line is for one calculation timed in a production build, not for a whole re-render in development.

### Development numbers are higher than real ones

The number we just read comes from development, and development is slower than what users get:
1. **StrictMode calls each component twice, and the development build of React runs extra checks.** The docs: "measuring performance in development will not give you the most accurate results."
2. **Users get the production build.** That is the optimized version of the app that you build for real users. The docs: "To get the most accurate timings, build your app for production and test it on a device like your users have." `<Profiler>` itself "is disabled in the production build by default", so measuring in production takes a special build.
3. **Your computer is probably faster than the phones of your users.** The docs suggest an artificial slowdown, such as the CPU Throttling option in Chrome, which makes the browser run as if on a slower processor.

### When a re-render is not harmless

The measurement matters because sometimes the number is big. A re-render becomes a real cost in these cases:
1. **The rendering logic is expensive.** The docs: "unless you're creating or looping over thousands of objects, it's probably not expensive."
2. **The component re-renders often with the same props,** and does that expensive work each time.
3. **The component whose state changes sits high in the tree,** so every component beneath it re-renders.
4. **The interactions are granular.** That means many small updates in a row, like moving a shape in a drawing editor, rather than coarse ones, like replacing a whole page.
5. **Effects set state over and over.** The docs: "Most performance problems in React apps are caused by chains of updates originating from Effects that cause your components to render over and over" (as seen in Lesson 34).

Before any memoization, the docs give an order of fixes:
1. Accept JSX as `children`.
2. Keep state local.
3. Keep rendering pure.
4. Avoid Effects you do not need.

Then, "If a specific interaction still feels laggy, use the React Developer Tools profiler". Lesson 64 covers that profiler. To time one calculation inside a component, the browser gives `console.time` and `console.timeEnd`. In Chrome they print a line such as `filter array: 0.174072265625 ms`.

### The real mistake: memo everywhere, and no measurement

1. A developer sees many re-renders in the Console and wraps every component in `memo`, the tool of Lesson 55 that skips a re-render when the props are the same.
2. One prop is a new object or a new arrow function on every render.
3. That component re-renders anyway. The docs: "a single value that's 'always new' is enough to break memoization for an entire component."
4. The code is harder to read, and the user sees no difference.

One measurement with `<Profiler>` would have shown that there was nothing to fix.

### Which components React calls for each action

The three actions of the user start at two different places in the tree. Typing and `Send` change the state of `ChatRoom`, and `Toggle theme` changes the state of `App`:

```tree caption="Which components React calls when the user types, clicks Send, and clicks Toggle theme in the chat room."
The action of the user and the components React calls
- +Types a letter in the field | The **own state** of `ChatRoom` changed | React calls **`ChatRoom` and its three `Message` functions**, not `App`
- +Clicks `Send` | The **own state** of `ChatRoom` changed, **one re-render for two setters** | React calls **`ChatRoom` and four `Message` functions**, and adds **one `<li>`**
- +Clicks `Toggle theme` | The **own state** of `App` changed, and the **context value** changed | React calls **`App`, `ChatRoom`, and every `Message`**, and changes **each `class`**
```

| Aspect | What Developers Often Assume | What React Does |
| :--- | :--- | :--- |
| **A child with the same props** | React will not call it, because nothing it receives changed | React calls it whenever its parent re-renders |
| **A component that reads context** | It updates only when its parent passes something new | React re-renders it when the `value` of the provider changes by `Object.is` |
| **A "rendered" line in the Console** | The page was rebuilt | React called a function; the commit changes only the DOM nodes that differ |
| **Twenty log lines after one click** | The page is slow, so every component needs an optimization | Only `actualDuration` tells the cost; optimize when the user can feel a lag |

Remember the one sentence of this lesson. **A re-render is React calling your function again, and that is cheap: React changes only the DOM nodes whose result is different.**

## For the Interview

> **The Interview Question:** When does a component re-render, and why is re-rendering children usually fast and harmless?

### How to Answer Clearly in 30 Seconds

"A component re-renders for three reasons: its own state changed, its parent re-rendered, or a context it reads got a different value. A child re-renders with its parent even when its props are the same. Setting state to the value it already holds, by `Object.is`, skips the re-render. Re-rendering is usually harmless for two reasons:
1. **A re-render is only a function call.** React calls the component to get its JSX, and that is usually very fast.
2. **Rendering is not committing.** React compares the new result with the last one and changes only the DOM nodes that differ. A child that returns the same JSX causes zero DOM changes, and the browser paints only what changed.

So I measure first, with `<Profiler>` and `actualDuration` or with the React Developer Tools profiler, and I optimize only when an interaction has a lag the user can feel."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does a child re-render if its props did not change?"**
   **Yes.** By default, React re-renders every component that a re-rendered component returns, down the tree. In our chat room, each letter typed into the field re-renders every `Message`, although their `text` props stay the same. A changed prop is not a separate cause, only what the new render of the parent passes down. React does not call the components above the one whose state changed. To skip a child with the same props, there are tools such as `memo`, passing JSX as `children`, and the React Compiler, which Lessons 55, 58, and 63 cover.
2. **"Is re-rendering the same as repainting the DOM?"**
   **No.** There are three steps. Rendering is React calling the components and working out what changed. Committing is React applying the smallest set of changes to the DOM. Painting is the browser drawing the screen. After the user clicks `Send` in our chat room, React calls four `Message` functions, but adds only one `<li>` and leaves the other three nodes untouched. A re-render that returns the same JSX causes no DOM change, so the typed text and the cursor in an `<input>` field stay where they are.
3. **"When is a re-render not harmless, and what do you do about it?"**
   A re-render costs something real in four cases. The rendering logic is expensive, a component high in the tree re-renders often, the interactions are granular like dragging a shape in a drawing editor, or Effects set state over and over. If a re-render causes a visible problem, that is a bug in an impure component, and the fix is to make rendering pure. Otherwise I measure with `<Profiler>` on a production build and a slowed-down device. If it is really slow, I first keep state low and pass JSX as `children`, and only then reach for `memo`, `useMemo`, or `useCallback`.

```tree caption="Interview summary: the three causes of a re-render, and why a re-render is usually cheap."
When and why a component re-renders
- +Its own state changed [`setText`] | React re-renders **this component and everything below it** | Components **above it are not called**
- +Its parent re-rendered | Happens **even when its props are the same** | A changed prop is **only what the parent passes**
- +A context it reads changed [`useContext`] | The provider got a **different `value` by `Object.is`** | **No component in between can stop it**
```
