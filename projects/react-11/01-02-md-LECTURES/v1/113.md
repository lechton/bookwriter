# Lecture 113: How a Server Function's Answer Reaches the Line Under the Email Field

*(How does the server's "already subscribed" get onto the page, right under the email field?)*

> INTERVIEW QUESTION | ❱ CORE | How do a Server Function's return values and errors reach the UI?

---

## VS | A Form `action={subscribe}` vs. `useActionState(subscribe)`: both run the Server Function, only `useActionState` keeps its answer

> A function answers with `return`, and only the code that called it receives that answer. **When a form calls a Server Function, pass the Server Function through `useActionState`: React keeps whatever it returns as state, and your component shows it.** Without it, the form is the caller, so a refusal such as "already subscribed" reaches the browser, nothing shows it, and the user believes the signup worked.

Remember how `return` works in plain JavaScript. The value goes back to the line that called the function. If that line stores it in a variable, you have it. If not, the value is lost:

```js title="Plain JavaScript: the caller receives the returned value"
const total = ~add(2, 3)~; // The caller keeps the answer: total is 5
add(2, 3); // The function still returns 5, but no variable receives it
```

A Server Function works exactly the same way. In Lesson 110, our own click handler called it, so our code kept the answer:

```jsx title="Our handler is the caller, so our code receives the answer"
const answer = await ~subscribe(email)~; // answer holds what subscribe returned
```

In Lesson 112, we gave the Server Function to the form instead: `<form action={subscribe}>`. Now the form is the caller. React collects the fields, calls `subscribe` on the server, and gets the answer back. But no variable of ours receives it. It is the second line of the plain JavaScript example: the function answers, and nobody keeps the answer.

**This is why we pass the Server Function to `useActionState`.** It is the same Hook you know from Lesson 42. React calls the action for us, and keeps whatever it returns as state:

```jsx title="useActionState keeps the answer of the Server Function"
const [state, formAction] = ~useActionState(subscribe, { error: null })~; // state holds what subscribe returned last
<form ~action={formAction}~> {/* The form calls formAction, and React calls subscribe */}
```

Take a newsletter form at the bottom of a blog post. A user types `john@example.com` and clicks `Subscribe`. A week later, the same user forgets, and subscribes again with the same email. The server looks in the database, finds the email, and refuses. Ask yourself: how does the server's sentence get onto the page, right under the email field?

**Why:** Only the server can decide this refusal, because only the server can look in the database. But the line under the email field is drawn in the browser. So the answer must travel back over the network, and something in the browser must keep it. It takes three steps:
1. `subscribe` returns the answer as a plain object, with the refusal in its `error` field.
2. React sends a serialized copy of that object back to the browser (as seen in Lesson 110).
3. `useActionState` keeps the copy as `state`, and the component shows `state.error` under the email field.

```tree dir=right caption="The three steps from the refusal on the server to the line under the email field."
How the server's answer reaches the screen
- +1. On the server [`return { error }`] | `subscribe` **returns** the refusal as an object
- +2. Over the network | React sends a **serialized copy** of the returned value to the browser
- +3. In the browser [`state.error`] | `useActionState` keeps the copy as **state**, and the component **shows it under the email field**
```

One more rule decides where an answer lands. A refusal the user can fix, like an email that is already saved, is **returned**. A failure nobody expected, like a database that does not answer, is **thrown**. A returned value becomes `state`. A thrown error skips `state`, and goes to the nearest Error Boundary.

Here is the one sentence to keep in mind for this whole lesson:

**A Server Function answers by returning a value, and `useActionState` keeps that value as state. Return the refusals the user can fix. Throw only the failures nobody expected.**

> [!DEFINITION]
> **Server Function.** [REVIEW] A Server Function is an `async` function that runs on the server, and that code in the browser can call like a normal function. It lives in a file that starts with `'use server'`. The browser gets only a reference to it, and a call sends a request to the server (Lesson 110).

> [!DEFINITION]
> **useActionState.** [REVIEW] `useActionState` is a Hook that takes an action function and a starting value, and returns two things: `state` and `formAction`. When the form calls `formAction`, React calls your action with the previous state and the form data. Whatever the action returns becomes the new `state`, and React renders the component again (Lesson 42).

> [!DEFINITION]
> **Serializable value.** [REVIEW] A serializable value is a value React can turn into text, send over the network, and rebuild on the other side: strings, numbers, booleans, `null`, plain objects and arrays of those, and a few built-ins that React's docs list. An instance of a class you wrote is not one of them (Lesson 107).

> [!DEFINITION]
> **Error Boundary.** [REVIEW] An Error Boundary is a class component that catches an error thrown by any component inside it, and shows its `fallback` prop in place of that part of the page. It works like `catch` for components: the part that failed is replaced, and the rest of the page stays (Lesson 72).

> [!DEFINITION]
> **Hydration.** [REVIEW] The server sends the HTML of the page first, and the JavaScript bundle arrives later. Hydration is the step where React, once the bundle has loaded, takes the HTML already on the screen and attaches your event handlers to it. Before hydration, no handler of yours runs (Lesson 104).

### Where Readers Usually Go Wrong

1. **They return an error and keep `action={subscribe}`.** They expect the error to show up by itself. But the form is the caller, and the form keeps nothing.
2. **They keep the one parameter of Lesson 112.** With `useActionState`, React passes the previous state first. So the parameter named `formData` receives the previous state, not the form data.
3. **They throw for the refusal, or they return the `Error` object itself.** A thrown refusal replaces the whole form with a fallback. An `Error` object is not text, so React cannot draw it inside a paragraph.

### The Two Questions to Ask

**For every answer of a Server Function, ask: who receives the returned value?** If the form receives it, nothing shows it, so pass the Server Function through `useActionState`.

**Then ask: can the user fix the problem?** If yes, return the message. If no, throw, and let an Error Boundary catch it.

### Four Ways to Show a Server Function's Answer

When a Server Function must answer on the screen, developers choose between four ways. Each one fits a different job:

```tree caption="Four ways to show a Server Function's answer, and the job each one fits."
Four ways to show a Server Function's answer
- +Our own handler with `useState` [`await subscribe` `setError`] | Our code calls the Server Function and **sets the message by hand** | Fits a button that is **not in a form**; does **nothing before hydration**
- +`useActionState` with the Server Function [`useActionState` `formAction`] | React keeps the **last returned value** as state | Fits **a form that shows its last answer**, even **before JavaScript loads**
- +The Server Function straight in `action` [`action={subscribe}`] | The form calls the Server Function and **keeps no answer** | Fits a form with **nothing to show** except the emptied field
- !A thrown error caught by an Error Boundary [`throw` `ErrorBoundary`] | The **fallback** replaces the part that failed | Fits only **unexpected failures**, never a refusal the user can fix
```

This lesson builds the second way. On the way, it shows why the third way loses the answer, and when the fourth way is the right one.

**PRINCIPLES:** A Server Function's answer is its returned value, and the form needs `useActionState` to keep it. Five principles follow:
1. **`action={subscribe}`: the form is the caller, so the returned refusal reaches no code of ours.** The answer comes back to the browser, React empties the email field as after a success, and nothing shows the refusal.
2. **`useActionState`: whatever the Server Function returns becomes `state`.** The Server Function receives the previous state first and the form data second.
3. **`state.error`: the refusal appears exactly where the component writes it.** Under the email field, the user knows at once which field is wrong.
4. **`throw` in a Server Function: the error skips `state` and reaches the nearest Error Boundary.** The fallback replaces the whole form, so throw only failures the user cannot fix.
5. **`useActionState` with a Server Function: the refusal appears even before JavaScript loads.** The server renders the page again with the answer already under the email field.

## PRINCIPLE | `action={subscribe}`: the form is the caller, so the returned refusal reaches no code of ours

> [!PRINCIPLE]
> **Principle 1: The Caller Gets the Answer: `action={subscribe}` Drops the Server's Refusal**
>
> *A Server Function's returned value goes back to whoever called it; when the form calls it through `action={subscribe}`, no code of ours receives the answer.*
>
> The server returns the refusal, and React sends it back to the browser. But the form was the caller, and the form keeps nothing. Because `subscribe` did not throw, React treats the submit as a success and empties the email field. The user sees the same page as after a real signup.
>
> **DO THIS:**
> ```jsx
> const [state, formAction] = useActionState(subscribe, { error: null });
> <form ~action={formAction}~> {/* useActionState keeps what subscribe returns */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <form ~action={subscribe}~> {/* **WRONG:** subscribe returns { error }, and no code of ours ever reads it */}
> ```

### `subscribe` Gains the Duplicate Check

To refuse an email, the server must first know whether the email is already saved. Our stand-in database gains one method, `has`:

```js title="src/db.js"
const subscribers = [];

export const db = {
  subscribers: {
    async ~has~(email) { // New: true when the email is already saved
      return subscribers.includes(email);
    },
    async add(email) {
      subscribers.push(email);
    },
  },
};
```

Now `subscribe` checks the email before it saves it. When the email is already there, it returns the refusal:

```js title="src/actions.js"
'use server';

import { db } from './db';

export async function subscribe(formData) {
  const email = formData.get('email');
  if (await db.subscribers.has(email)) {
    ~return { error: `${email} is already subscribed.` };~ // The refusal, sent back to whoever called subscribe
  }
  await db.subscribers.add(email);
}
```

The form of Lesson 112 stays as it was. It still calls `subscribe` directly:

```jsx title="src/SubscribeBox.jsx"
<form ~action={subscribe}~> {/* Unchanged from Lesson 112: the form is the caller */}
  <label>
    Your email
    <input name="email" />
  </label>
  <button type="submit">Subscribe</button>
</form>
```

### The Second Click With the Same Email

**The server refuses the email, and the page looks exactly as it does after a successful signup.** The refusal reaches the browser, and nothing on the page shows it. Here is what happens when the user clicks `Subscribe` a second time with `john@example.com`:
1. React collects the form data and calls `subscribe` on the server with a network request (as seen in Lesson 112).
2. On the server, `db.subscribers.has` answers `true`, so `subscribe` returns the object with the refusal.
3. React sends the returned value back to the browser as a serialized copy.
4. No code of ours reads it. The form called `subscribe`, and the form has no place to keep the answer.
5. `subscribe` did not throw, so for React the action succeeded. React resets the form, and the email field is empty (as seen in Lesson 45).

```page caption="The page after the second click with the same email: an empty field and no line, exactly as after a real signup."
heading: Park Opens Today
line: The city opened a new park on Main Street.
section: Get new posts by email
form:
  field: Your email | | bad
  submit: Subscribe
```

### The Mistake: Returning an Answer That Nothing Reads

A developer adds the duplicate check, returns the refusal exactly as above, and tests the form:
1. The developer subscribes with a new email. The field empties, which looks right.
2. A tester subscribes twice with the same email. The field empties again, and no message appears.
3. The developer looks for an error in the browser's Console and finds none. `subscribe` threw nothing. It returned an answer that nobody read.

The fix is to give the returned value a place to land. That place is the state of `useActionState`.

Remember: a returned value goes back to whoever called the function. With `action={subscribe}`, the caller is the form, and the form keeps nothing.

## PRINCIPLE | `useActionState`: whatever the Server Function returns becomes `state`

> [!PRINCIPLE]
> **Principle 2: useActionState: The Server Function's Answer Becomes state**
>
> *Pass the Server Function to `useActionState` in a Client Component, give the form the returned `formAction`, and write the Server Function as `subscribe(previousState, formData)`.*
>
> `useActionState` works the same whether the action runs in the browser or on the server. With a Server Function, React sends the form data to the server, runs the function there, and brings the returned value back as a serialized copy. That copy becomes `state`. The file that calls the Hook needs `'use client'`, and the starting value must be serializable.
>
> **DO THIS:**
> ```js
> export async function subscribe(~previousState, formData~) { // React passes the last state first, the form data second
>   const email = formData.get('email');
> ```
>
> **DO NOT DO THIS:**
> ```js
> export async function subscribe(~formData~) { // **WRONG:** with useActionState, this parameter receives the previous state
>   const email = formData.get('email');
> ```

### What `useActionState` Does, in Plain JavaScript

Think of `useActionState` as a variable that React keeps for you, and two lines that React runs on every submit:

```js title="What useActionState does on every submit, written as plain JavaScript"
let state = ~{ error: null }~; // The starting value, before any submit
state = await ~subscribe(state, formData)~; // The last answer goes in, and the new answer comes out
```

Then React renders the component again, so the page always shows the last answer. You call no setter. The `return` of the Server Function does the job of the setter.

### VS | An Action in the Browser vs. a Server Function: the same Hook, the same `state`

In Lesson 42, the action was a function written in the browser. Here, the action is the Server Function `subscribe`, imported from the actions file:

```jsx title="With the action written in the browser"
async function signup(previousState, formData) {
  return { message: 'You are subscribed!' };
}

const [state, formAction] = useActionState(~signup~, { error: null }); // React calls signup in the browser
<form action={formAction}>
```

```jsx title="With the Server Function imported from actions.js"
import { subscribe } from './actions';

const [state, formAction] = useActionState(~subscribe~, { error: null }); // React calls subscribe on the server, with the same two arguments
<form action={formAction}>
```

**Yes, it is the exact same thing!** For the component, nothing changes: the same Hook, the same `state` and `formAction`, and the same form. Whatever the action returns becomes the new `state`. `useActionState` does not care where the action runs.

What changes is the network between the browser and the server. The form data travels to the server as a serialized copy, and the returned value travels back the same way. So every value `useActionState` hands over must be serializable, including its starting value.

React's docs say it plainly: "When using Server Functions, `initialState` needs to be serializable." Our starting value, `{ error: null }`, is a plain object, so it qualifies.

```tree caption="The action in the browser and the Server Function share everything in the component, and differ only in where the action runs."
`useActionState` with two kinds of action
- +The action in the browser [`signup`] | React calls it with **previousState, formData** | The returned value **becomes state**
- +The Server Function [`subscribe`] | React calls it **on the server** with the same two arguments | The returned value **travels back serialized** and **becomes state**
```

### Two Changes in Our Files

First, `subscribe` gains the parameter `previousState` in front of `formData`. It also returns an answer when the signup succeeds:

```js title="src/actions.js"
'use server';

import { db } from './db';

export async function subscribe(~previousState, formData~) { // React passes the last state first
  const email = formData.get('email');
  if (await db.subscribers.has(email)) {
    return { error: `${email} is already subscribed.` };
  }
  await db.subscribers.add(email);
  ~return { message: 'You are subscribed!' };~ // New: the answer for a successful signup
}
```

Our code never passes `previousState`. React passes it. On the first submit, it is the starting value `{ error: null }`. After that, it is whatever `subscribe` returned the time before (as seen in Lesson 42).

Second, the component calls `useActionState`. Its form now calls `formAction` instead of `subscribe`:

```jsx title="src/SubscribeBox.jsx"
~'use client'~; // useActionState is a Hook, so this file must be client code

import { useActionState } from 'react';
import { subscribe } from './actions';

export default function SubscribeBox() {
  const [state, formAction] = ~useActionState(subscribe, { error: null })~; // state holds what subscribe returned last
  return (
    <section>
      <h2>Get new posts by email</h2>
      <form ~action={formAction}~> {/* The form now calls the function React returned */}
        <label>
          Your email
          <input name="email" />
        </label>
        <button type="submit">Subscribe</button>
      </form>
    </section>
  );
}
```

`formAction` is the second value `useActionState` returns. It is the function the form now calls. When the user submits, React calls `subscribe` on the server, waits for the answer, and stores it in `state`.

The page does not change yet. The component now keeps the answer, but it does not show it anywhere. Principle 3 gives it a place on the page.

### Two Lines That Surprise Readers of Lesson 112

**The component file must start with `'use client'` again.** In Lesson 112, `SubscribeBox` was a Server Component, because a form with a Server Function in `action` needs no Hook. Now it calls `useActionState`, and a Hook runs only in client code (as seen in Lesson 108). React's docs say it about this exact Hook: like most Hooks, `useActionState` "can only be called in client code."

**`subscribe` still runs only on the server, even though a `'use client'` file imports it.** The `'use server'` line at the top of the actions file marks every export as a Server Function. React's docs say a Server Function can be used anywhere, "including imported in client code". The JavaScript bundle holds only a reference to `subscribe`, not its code (as seen in Lesson 110). So the database check never reaches the browser.

### VS | `subscribe(formData)` vs. `subscribe(previousState, formData)`: the form data moves to second place

With `useActionState`, the form data moves to the second parameter:

```js title="With formData alone and with previousState first"
async function subscribe(~formData~) {} // Lesson 112: formData is the first argument
async function subscribe(~previousState, formData~) {} // With useActionState: formData is the second argument
```

**It may look like the same function with one extra name, but it is NOT the same thing!** React's docs explain why. With `useActionState`, the action "receives an extra argument as its first argument: the previous or initial state. The submitted form data is therefore its second argument instead of its first."

### The Mistake: Keeping the One Parameter of Lesson 112

A developer wraps the old `subscribe(formData)` in `useActionState`, and leaves its parameter list alone. The submit then fails on the server, and no email is saved:
1. React calls `subscribe` with the previous state first.
2. So the parameter named `formData` holds `{ error: null }`, a plain object.
3. A plain object has no `get` method. So the call throws a `TypeError` on the server: `formData.get is not a function`.
4. `subscribe` stops there, before it saves anything.

The fix is to write both parameters, even when the function never reads `previousState`:

```js title="src/actions.js"
export async function subscribe(~previousState, formData~) { // formData is now the second argument
  const email = formData.get('email');
```

Remember: `useActionState` keeps the last answer, and hands it back to the Server Function as its first argument.

## PRINCIPLE | `state.error`: the refusal appears exactly where the component writes it

> [!PRINCIPLE]
> **Principle 3: Known Errors: Return the Refusal as State and Show It Next to Its Field**
>
> *Return an expected refusal from the Server Function as part of the state, such as `{ error: '...' }`, and render `state.error` right next to the field it is about.*
>
> The server decides what the refusal says, and the component decides where it appears. React carries the returned object back, makes it the new state, and renders the component again, with no setter in our code. Start `useActionState` with the same shape, `{ error: null }`, so the first render can read `state.error`.
>
> **DO THIS:**
> ```jsx
> <input name="email" />
> ~{state.error && <p>{state.error}</p>}~ {/* The refusal appears under the field it is about */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [state, formAction] = useActionState(subscribe, ~null~); // **WRONG:** state.error throws a TypeError on the first render
> ```

### The Server Decides the Words, the Component Decides the Place

The server decides only what the refusal says. The component decides where the refusal appears. Here is the whole idea in four lines:

```jsx title="The answer placed next to what it is about"
<input name="email" />
~{state.error && <p>{state.error}</p>}~ {/* The refusal: right under the email field */}
<button type="submit">Subscribe</button>
~{state.message && <p>{state.message}</p>}~ {/* The thanks: under the button */}
```

When `state.error` holds text, the paragraph under the email field appears (as seen in Lesson 10). When it is `null`, nothing appears there.

> [!DEFINITION]
> **Known error.** [NEW] A known error is a problem you expect, and the user can fix, such as an email that is already subscribed or a quantity that is not available. React's docs advise: "you can return it as part of your `reducerAction` state and display it in the UI." Developers also call it a validation error, because the server checks, or validates, what the user typed. Here, the server checks the email against the database (Lesson 113).

For React, writing `state.error` right under the email field or at the bottom of the form is the exact same thing. React renders it wherever the component writes it.

For the user, it is NOT the same thing. A refusal right under the field says which field is wrong. A refusal at the bottom of the form makes the user guess.

### Placing the Two Lines in `SubscribeBox`

The component gains one line under the email field, and one line under the button:

```jsx title="src/SubscribeBox.jsx" startLine="10"
      <form action={formAction}>
        <label>
          Your email
          <input name="email" />
        </label>
        ~{state.error && <p>{state.error}</p>}~ {/* Under the field it is about */}
        <button type="submit">Subscribe</button>
        ~{state.message && <p>{state.message}</p>}~ {/* Under the button */}
      </form>
```

When the page first opens, `state` is `{ error: null }`. Neither line appears. The user sees only the email field and the button.

**The refusal is decided on the server, and it appears under the email field with no setter in our code.** React carries the returned object back, makes it the new `state`, and renders the component again. Here is the first click, with an email that is not saved yet:
1. The user types `john@example.com` and clicks `Subscribe`.
2. React calls `subscribe` on the server, with `{ error: null }` as the previous state and the form data.
3. The email is not saved yet, so `subscribe` saves it, and returns the object with the thanks message.
4. React sends the value back, makes it the new `state`, and renders the component again. The thanks line appears.
5. React also empties the email field, because the submit succeeded (as seen in Lesson 45).

1. The user types `john@example.com` and clicks `Subscribe`.
2. React calls `subscribe`, and this time the previous state is the object with the thanks message.
3. `db.subscribers.has` answers `true`, so `subscribe` returns the object with the refusal.
4. React makes it the new `state`. The new state has `error` and no `message`. So the thanks line disappears, and the refusal appears under the email field.

Two things on this page come from React, not from a line of ours:
- **The thanks line is gone.** The new returned object replaces the whole state. It does not merge with the old one, so `message` is simply not there anymore.

### The Mistake: Starting `useActionState` With `null`

A developer writes the starting value as `null`, which looks like "no answer yet":

```jsx title="src/SubscribeBox.jsx"
const [state, formAction] = useActionState(subscribe, ~null~); // **WRONG:** state is null on the first render
```

The component still writes `state.error`. On the first render, `state` is `null`, and JavaScript cannot read a field of `null`. So the component throws a `TypeError`, and crashes before it draws the form.

No Error Boundary sits above it yet, so React removes the whole page. The user sees an empty screen, without the article and without the form:

```page caption="The page when the starting value is null: an empty screen, and a TypeError in the Console."
blank
console: TypeError: Cannot read properties of null (reading 'error')
```

The fix is to start with the same shape the action returns, as React's docs do in their own Server Function example:

```jsx title="src/SubscribeBox.jsx"
const [state, formAction] = useActionState(subscribe, ~{ error: null }~); // state.error is null, and nothing crashes
```

Remember: the server decides the words of the refusal. The component decides the place, right under the field it is about.

## PRINCIPLE | `throw` in a Server Function: the error skips `state` and reaches the nearest Error Boundary

> [!PRINCIPLE]
> **Principle 4: Return or Throw: Only a Returned Refusal Becomes state**
>
> *Return a refusal the user can fix as plain data; throw only an unexpected failure, and wrap the form in an Error Boundary to catch it.*
>
> A returned value becomes `state`, and appears where the component writes it. A thrown error never becomes `state`. React throws it again from `useActionState`, cancels the queued submits, and the nearest Error Boundary shows its fallback in place of the form. Whatever you return must be serializable, so return the text of an error, never the `Error` object.
>
> **DO THIS:**
> ```js
> if (await db.subscribers.has(email)) {
>   ~return { error: `${email} is already subscribed.` };~ // The user can fix it, so it becomes state
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> if (await db.subscribers.has(email)) {
>   ~throw new Error(`${email} is already subscribed.`);~ // **WRONG:** the fallback replaces the whole form
> }
> ```

### `throw` in Plain JavaScript Jumps to the Nearest `catch`

Remember what `throw` does in plain JavaScript. It skips every line after it, and jumps straight to the nearest `catch`:

```js title="Plain JavaScript: throw skips every line until the nearest catch"
try {
  ~throw new Error('The database is not answering')~; // Jumps straight to catch
  console.log('Saved'); // Never runs
} catch (err) {
  console.log(err.message); // Logs The database is not answering
}
```

Components have no `try` around them. In React, the nearest Error Boundary plays the part of `catch`. It catches the error, and shows its fallback in place of the part that failed (as seen in Lesson 72).

### VS | `return { error }` vs. `throw new Error()`: both stop `subscribe`, only the returned value becomes `state`

So far, the server refused an email for a reason the user can fix. Now picture a failure nobody expected: the database does not answer. There are two ways for `subscribe` to say no:

```js title="Returning the refusal and throwing it"
~return { error: `${email} is already subscribed.` };~ // Becomes state: the line appears under the email field
~throw new Error('The database is not answering');~ // Never becomes state: the Error Boundary shows its fallback
```

Both lines stop `subscribe`, and both mean "it did not work". **It may look the same, but it is NOT the same thing!** They land in two different places:
- **With `return { error }`**, the value travels back and becomes `state`. The line appears under the email field.
- **With `throw`**, nothing becomes `state`. React throws the error again from `useActionState`, inside `SubscribeBox`. The nearest Error Boundary above it catches the error, and shows its fallback in place of the form.

React's docs draw the same line: return known errors as part of the state, and throw only unknown errors. For an unknown error, "React will cancel all queued Actions and shows the nearest Error Boundary by rethrowing the error from the `useActionState` hook."

```tree caption="A returned refusal and a thrown error both stop subscribe, and they land in two different places."
Two ways for `subscribe` to say no
- +Return the refusal [`return { error }`] | The value **becomes state** | The line appears **under the email field**; the user can fix the email
- !Throw an error [`throw`] | React **throws it again** from `useActionState` | The nearest Error Boundary **replaces the form** with its fallback
```

### Wrapping the Form in an Error Boundary

We bring back `ErrorBoundary` from Lesson 72. Its file gains one line at the top, `'use client'`. `App` is a Server Component, and a class component runs only in client code.

Without that line, the page fails on the server. The React that runs Server Components has no `Component` class to import:

```jsx title="src/ErrorBoundary.jsx"
~'use client'~; // New: a class component runs only in client code

import { Component } from 'react';
```

Then we wrap `<SubscribeBox />` in it. The fallback tells the user what happened, in words the user understands:

```jsx title="src/App.jsx"
import SubscribeBox from './SubscribeBox';
import ErrorBoundary from './ErrorBoundary';

export default function App() {
  return (
    <main>
      <h1>Park Opens Today</h1>
      <p>The city opened a new park on Main Street.</p>
      <ErrorBoundary ~fallback={<p>Could not subscribe. Try again later.</p>}~> {/* Shown if SubscribeBox throws */}
        <SubscribeBox />
      </ErrorBoundary>
    </main>
  );
}
```

Nothing in `subscribe` catches an error of the database call. So when the database fails, the error leaves `subscribe` as a thrown error. To see it happen, we make our stand-in database fail on purpose:

```js title="src/db.js" startLine="8"
    async add(email) {
      ~throw new Error('The database is not answering');~ // A stand-in for a database that is down
    },
```

### The Click While the Database Is Down

**One line replaces the whole form, and the article stays on the page.** The thrown error never becomes `state`, so it cannot appear under the email field. Here is what happens when the user clicks `Subscribe` with a new email:
1. React calls `subscribe` on the server with a network request.
2. On the server, `db.subscribers.add` throws, so `subscribe` throws.
3. The failure travels back to the browser. React throws it again from `useActionState`, inside `SubscribeBox`.
4. React cancels any submits still waiting in its queue.
5. The nearest Error Boundary, around `<SubscribeBox />` in `App`, shows its fallback in place of the form.

```page caption="The page after the click while the database is down: the fallback replaces the form, and the article stays."
heading: Park Opens Today
line: The city opened a new park on Main Street.
line: Could not subscribe. Try again later. | bad
console: Error: The database is not answering
console: The above error occurred in the <SubscribeBox> component. React will try to recreate this component tree from scratch using the error boundary you provided, ErrorBoundary.
```

The fallback line is ours: it is the `fallback` prop we passed to `ErrorBoundary`. The two Console lines come from React in development: the error itself, and the component it left.

The error was thrown on the server, yet it is caught around `SubscribeBox` in the browser. The reason: React throws it again from the Hook inside that component.

### Mistake 1: Returning the `Error` Object Itself

Sometimes a developer wants the database failure under the email field too, as a line instead of a fallback. So the developer wraps the database call in `try` and `catch`, and returns what the `catch` receives:

```js title="src/actions.js"
try {
  await db.subscribers.add(email);
} catch (err) {
  return { error: ~err~ }; // **WRONG:** err is an Error object, not the text of the error
}
```

An `Error` is an instance of a class. React's docs list the values a Server Function may return. Instances of a class are not on that list, apart from a few built-ins, and `Error` is not one of them.

React 19 still carries the `Error` back to the browser, but as an `Error` object, not as text. Two things go wrong:
1. `state.error` now holds an object, and React cannot draw an object inside a paragraph. When the component renders again, React throws an error: objects are not valid as a React child. The Error Boundary replaces the form with its fallback, and the line the developer wanted never appears.
2. In a production build, React leaves the message out on the way to the browser. The `Error` that arrives no longer says `The database is not answering`. Its message only points to React error 441.

The fix is to return plain text. The `message` field of the error is a string:

```js title="src/actions.js"
} catch (err) {
  return { error: ~err.message~ }; // A string: the line under the email field reads The database is not answering
}
```

### Mistake 2: Throwing for the Known Refusal

The opposite mistake is to throw for the refusal the user can fix:

```js title="src/actions.js"
if (await db.subscribers.has(email)) {
  ~throw new Error(`${email} is already subscribed.`);~ // **WRONG:** the fallback replaces the form, and queued submits are cancelled
}
```

The user never sees the line under the email field. The fallback replaces the whole form, so the user cannot even type another email. React's docs give the fix for this case: "catch errors within your `reducerAction` and return an error state instead of throwing."

Remember: a returned value becomes `state`. A thrown error skips `state`, and lands in the nearest Error Boundary.

## PRINCIPLE | `useActionState` with a Server Function: the refusal appears even before JavaScript loads

> [!PRINCIPLE]
> **Principle 5: Before Hydration: The Server Renders the Refusal Into the Page**
>
> *Render the form in a Client Component, pass a Server Function through `useActionState`, and show the message from `state`; then the refusal appears even when the user taps before the JavaScript bundle loads.*
>
> Before hydration, the browser posts the form by itself, and the server runs the Server Function. The server also renders Client Components into HTML. So it renders the form with the returned value as its state, and sends that page back. A click handler with `setError` cannot do this, because the handler arrives only with the bundle.
>
> **DO THIS:**
> ```jsx
> const [state, formAction] = useActionState(subscribe, { error: null });
> <form ~action={formAction}~> {/* Before hydration, the server sends the page back with state.error */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button ~onClick={handleClick}~>Subscribe</button> {/* **WRONG:** before hydration, no handler is attached and nothing is sent */}
> ```

### Old-School Forms: the Server Sends Back a Page With the Error in It

Remember how forms worked before JavaScript did everything. The browser posted the form, and the server answered with a whole new page. If the email was wrong, the server wrote the error into that page. No JavaScript ran in the browser.

`useActionState` with a Server Function gives you exactly this, and you write no extra code for it.

### The Same Tap on the Slow Phone

We go back to the user of Lesson 112, on a phone with a slow connection. The server has sent the HTML of the post and the form. The JavaScript bundle is still downloading. The user types `john@example.com`, already saved, and taps `Subscribe`.

The refusal appears under the email field, even though `useActionState` is a Hook, and no JavaScript has run on the phone yet. React's docs say it directly: with a Server Function, `useActionState` "allows the server's response to be shown before hydration" completes.

React's docs list three conditions for a form error shown without JavaScript:
1. The `<form>` is rendered by a Client Component.
2. The function passed to the form's `action` is a Server Function.
3. `useActionState` displays the error message.

Our `SubscribeBox` already meets all three. This principle adds no code. Only the moment of the tap changes.

### VS | Lesson 112's Form vs. This Form: the same request, only this page comes back with the refusal

Compare the two forms, tapped at the same moment, before the bundle loads:

```jsx title="Lesson 112's form and this lesson's form"
<form ~action={subscribe}~> {/* Lesson 112: the page loads again with no message */}
<form ~action={formAction}~> {/* With useActionState: the page loads again with the refusal under the email field */}
```

For the request, **yes, it is the exact same thing!** In both, the browser posts the form by itself, and `subscribe` runs on the server (as seen in Lesson 112).

For the page that comes back, **it is NOT the same thing!** Only the second page holds the refusal, because the server renders `SubscribeBox` with the returned value as its state.

Here is the same tap on the slow phone, in each of the three ways:
1. **With our own click handler** from Lesson 110, the tap runs nothing, because the handler arrives with the bundle. No request is sent.
2. **With the form of Lesson 112**, the email is checked, and the page loads again with no message.
3. **With `useActionState`**, the page loads again with the refusal under the email field.

### How the Line Gets Into a Page That Ran No JavaScript

**The server, not the browser, puts the refusal into the page.** The server renders Client Components into HTML too (as seen in Lesson 102). So it can render `SubscribeBox` with the state `subscribe` just returned. Here is the tap, in order:
1. The browser posts the form by itself, with the field `email`, as it did in Lesson 112.
2. On the server, the framework calls `subscribe` with a previous state and the form data.
3. `subscribe` returns the object with the refusal.
4. The server renders the page again, with `state` set to the returned value, and sends the HTML back.
5. The browser shows the new page. The refusal sits under the email field before any JavaScript has run.

```page caption="The page the server sends back after the tap on the slow phone, before any JavaScript has run."
heading: Park Opens Today
line: The city opened a new park on Main Street.
section: Get new posts by email
form:
  field: Your email |
  error: john@example.com is already subscribed.
  submit: Subscribe
```

Our code never connects the posted form to this `useActionState` call. The framework does. React's docs say this "is typically handled by your framework for you."

### The Mistake: Showing the Answer With Our Own Click Handler

A developer shows the refusal the way of Lesson 110: a button with `onClick`, a call to `subscribe`, and `setError` with the answer.
1. Everything works on the developer's fast laptop, where the bundle loads at once.
2. A user on a slow phone taps `Subscribe` before the bundle loads. No handler is attached yet, so nothing is sent, and no line appears (as seen in Lesson 112).
3. With `useActionState` and `formAction` on the form, the same tap reaches the server, and the page comes back with the line.

`useActionState` does two more things for a form sent before hydration finishes. React replays the submits the user made before hydration finished. And its third argument, `permalink`, picks the page the browser goes to when the form is sent without JavaScript. Both come later (Lesson 137).

Remember: before JavaScript loads, the server writes the refusal into the page it sends back, exactly like an old-school form.

## All 5 Principles Together

### The Complete Code

The stand-in database, with the new `has` method. Its `add` saves the email again, as it did before we made it fail on purpose:

```js title="src/db.js"
const subscribers = [];

export const db = {
  subscribers: {
    async ~has~(email) { // Principle 1: true when the email is already saved
      return subscribers.includes(email);
    },
    async add(email) {
      subscribers.push(email);
    },
  },
};
```

The actions file holds the Server Function, which returns an answer in both cases:

```js title="src/actions.js"
'use server';

import { db } from './db';

export async function subscribe(~previousState, formData~) { // Principle 2: the form data comes second
  const email = formData.get('email');
  if (await db.subscribers.has(email)) {
    ~return { error: `${email} is already subscribed.` };~ // Principle 3: a known error, returned as state
  }
  await db.subscribers.add(email); // Principle 4: a database failure throws to the Error Boundary
  return { message: 'You are subscribed!' };
}
```

The newsletter component is a Client Component that keeps the answer in state, and shows it next to the email field:

```jsx title="src/SubscribeBox.jsx"
'use client';

import { useActionState } from 'react';
import { subscribe } from './actions';

export default function SubscribeBox() {
  const [state, formAction] = ~useActionState(subscribe, { error: null })~; // Principle 2: state holds the last answer
  return (
    <section>
      <h2>Get new posts by email</h2>
      <form ~action={formAction}~> {/* Principle 5: works before and after hydration */}
        <label>
          Your email
          <input name="email" />
        </label>
        ~{state.error && <p>{state.error}</p>}~ {/* Principle 3: the refusal under the email field */}
        <button type="submit">Subscribe</button>
        {state.message && <p>{state.message}</p>}
      </form>
    </section>
  );
}
```

The Error Boundary is the class component of Lesson 72, with one new first line:

```jsx title="src/ErrorBoundary.jsx"
~'use client'~; // Principle 4: a class component runs only in client code

import { Component } from 'react';

export default class ErrorBoundary extends Component {
  state = { hasError: false };

  static ~getDerivedStateFromError~(error) { // Principle 4: React calls this when a child throws
    return { hasError: true };
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback;
    }
    return this.props.children;
  }
}
```

The app renders the post, and wraps the newsletter form in the Error Boundary:

```jsx title="src/App.jsx"
import SubscribeBox from './SubscribeBox';
import ErrorBoundary from './ErrorBoundary';

export default function App() {
  return (
    <main>
      <h1>Park Opens Today</h1>
      <p>The city opened a new park on Main Street.</p>
      <ErrorBoundary ~fallback={<p>Could not subscribe. Try again later.</p>}~> {/* Principle 4: catches a thrown error */}
        <SubscribeBox />
      </ErrorBoundary>
    </main>
  );
}
```

### The Order in Which Things Run

```tree dir=right caption="The order in which the components and the Server Function run, from the first page to the answer under the email field."
From the click to the answer on the screen
- +1. On the server [`App` `ErrorBoundary` `SubscribeBox`] | The framework renders the page to HTML | `state` is **`{ error: null }`**, so no line shows
- +2. The click [`formAction`] | Before hydration, **the browser** posts the form; after it, **React** sends it | `subscribe` runs **on the server** with **previousState, formData**
- +3. The answer [`return` or `throw`] | A returned value travels back and **becomes state** | A thrown error goes to the **Error Boundary**
- +4. The screen [`state.error` `state.message`] | `SubscribeBox` renders again with the new state | The refusal sits **under the email field**, the thanks **under the button**
```

### Summary

| Aspect | What a Developer Might Expect | What React Does |
| :--- | :--- | :--- |
| **A returned error with `action={subscribe}`** | It shows up on the page by itself | It goes back to the form, which keeps nothing; the field empties as after a success |
| **The place for the answer** | A special channel for Server Functions | The same `useActionState` as in the browser; the returned value becomes `state` |
| **The parameters of `subscribe`** | Only the form data, as in Lesson 112 | The previous state first, the form data second |
| **The file of the form** | Can stay a Server Component | Needs `'use client'`, because `useActionState` is a Hook |
| **Where the refusal appears** | Wherever the server sends it | Wherever the component writes `state.error`, here under the email field |
| **The starting value** | `null`, meaning no answer yet | `{ error: null }`, the same shape the action returns, and serializable |
| **A thrown error** | Appears under the email field like a returned one | Never becomes `state`; the nearest Error Boundary shows its fallback |
| **Returning the `Error` object** | Sends the error to the browser | Arrives as an object a paragraph cannot draw, and without its message in production; return `err.message` |
| **A tap before JavaScript loads** | The Hook needs JavaScript, so no message | The server renders the refusal into the page it sends back |

Remember the one sentence of this lesson. **A Server Function answers by returning a value, and `useActionState` keeps that value as state. Return the refusals the user can fix. Throw only the failures nobody expected.**

## For the Interview

> **The Interview Question:** How do a Server Function's return values and errors reach the UI?

### How to Answer Clearly in 30 Seconds

"A Server Function answers by returning a value. React serializes that value on the server and sends it back to the browser. But a value only reaches the UI if some code receives it. If the form calls the Server Function directly with `action={subscribe}`, nothing keeps the answer. So we pass the Server Function to `useActionState` in a Client Component, and give its `formAction` to the form. Then:
1. **The Server Function receives `previousState` first and `formData` second**, and whatever it returns becomes `state`.
2. **Known errors are returned**, such as `{ error: 'john@example.com is already subscribed.' }`, and the component renders `state.error` right under the field it is about.
3. **Unknown errors are thrown.** React throws them again from `useActionState`, cancels queued submits, and the nearest Error Boundary shows its fallback.

Everything that crosses the network must be serializable, so we return text, never an `Error` object. And with this setup, the server can render the error into the page even before the JavaScript bundle loads."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why not throw an error for every failure and catch it in an Error Boundary?"**
   Because an Error Boundary replaces the part that failed with its fallback. For a refusal the user can fix, such as an email already subscribed, the user loses the whole form and cannot even type another email. React also cancels every submit still waiting in the queue. React's docs advise to catch errors inside the action and "return an error state instead of throwing." Throw only for failures nobody expected, such as a database that does not answer.

2. **"What can a Server Function return?"**
   Only serializable values: strings, numbers, booleans, `null`, plain objects and arrays of those, and a few built-ins that React's docs list. An instance of a class is not supported, and an `Error` is one. So return `err.message`, not `err`. The starting value of `useActionState` follows the same rule: "When using Server Functions, `initialState` needs to be serializable." The returned value can be a single string, or a plain object with one key per message, such as `{ error }`.

3. **"Can the browser check the email instead, with `required` on the email field?"**
   It can help the user, but it cannot replace the server's check, for two reasons. First, "already subscribed" is a fact only the database knows. Second, anyone can send the request without our page at all. React's docs say it plainly: "Arguments to Server Functions are fully client-controlled. For security, always treat them as untrusted input." So the Server Function validates every argument on the server (Lessons 130 and 162).

```tree dir=right caption="Interview comparison: where a returned answer and a thrown error land."
Where a Server Function's answer lands
- +A returned value [`return { error }`] | Travels back **serialized** | Becomes **state**; the component shows it **next to its field**
- !A thrown error [`throw`] | React **throws it again** from `useActionState` | The nearest **Error Boundary** shows its fallback
```
