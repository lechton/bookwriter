# Lecture 92: How a Chat Screen Tells TypeScript What Each Hook Holds

*(Why does `useState(null)` refuse the user that arrives later, and what do you write instead?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How do you type useState, useReducer, and useRef with strict TypeScript generics?

---

## VS | `useState(false)` vs. `useState(null)`: `false` is a real value, `null` is only a placeholder

> In plain JavaScript, a variable that starts as `null` can hold a user object later, and nobody complains. **In TypeScript, every hook takes its type from its start value, so `useState(null)` can hold `null` and nothing else.** Write the real type in angle brackets, `useState<User | null>(null)`, because the quick fix, `any`, turns off every check and lets the page go blank.

Remember Lesson 91? You write `const name = 'John'`, and TypeScript knows that `name` is a string. You never wrote `string`. TypeScript read it from the value.

Hooks work exactly the same way. `useState`, `useReducer`, and `useRef` all take their type from the start value you give them. Most of the time, that is all you need. The trouble starts when the start value is not the real thing yet.

Here are two state variables of a chat screen, in a `.tsx` file. Neither one has a type written on it:

```tsx title="Two start values, and no type written on either"
const [isSending, setIsSending] = useState(~false~); // Starts as false, and will later be true
const [user, setUser] = useState(~null~); // Starts as null, and will later hold the person we write to
```

Later, each setter receives its real value:

```tsx title="One setter call under each"
setIsSending(~true~); // Accepted
setUser(~{ id: 1, name: 'Taylor' }~); // **WRONG:** the editor refuses it: this state can only ever hold null
```

Both lines look like the same plan: start with something empty, fill it in later. Both take their type from the start value. react.dev says it plainly: `useState(false)` gives "the type of `boolean`" to the state.

**It may look the same, but it is NOT the same thing!** The one difference is the start value:
- **`false` is a real value.** It is a `boolean`, and `true` is a `boolean` too. So the state is a `boolean`, and `setIsSending(true)` fits.
- **`null` is only a placeholder.** It holds the place of a user who arrives later, from the server. TypeScript cannot guess what will come. It sees `null`, so the state's type is `null`, and nothing else. The user object does not fit.

The fix is to tell TypeScript what the placeholder stands for. Write the type in angle brackets right after `useState`:

```tsx title="The type in angle brackets says what null stands for"
type User = { id: number; name: string };

const [user, setUser] = useState~<User | null>~(null); // A User, or null until the User arrives
setUser({ id: 1, name: 'Taylor' }); // Accepted
```

> [!DEFINITION]
> **What is a type argument?** [REVIEW] A type argument is a type you write in angle brackets right after a function's name, such as `useState<User | null>`. It tells the function which type to use, instead of letting TypeScript read it from the value. `User | null` is a union: the value is a `User` or `null`, and nothing else (Lesson 90).

```tree caption="Two start values with no type: false leaves room for true, while null leaves room only for null."
Two start values, no type written
- +A real value [`useState false`] | TypeScript reads **`boolean`** | `setIsSending` with `true` **fits**
- !A placeholder [`useState null`] | TypeScript reads **`null`** and nothing else | The user object **does not fit**
- +A placeholder with a type argument [`useState<User or null>`] | Our code says **what `null` stands for** | The user object **fits**
```

**Remember this sentence: each hook takes its type from its start value.** When the start value is already the real kind of value, such as `false` or `''`, write nothing. When it is a placeholder, such as `null` for a user still loading, or for an element not yet on the page, write the type in angle brackets. Then TypeScript makes you handle `null` everywhere the value is read.

Interviewers often call these angle brackets **generics**. react.dev calls the type you put inside them a **type argument**, and this lesson uses that word. Here we only fill in the type argument that `useState`, `useReducer`, and `useRef` already accept. Writing generic components of your own comes in Lesson 93.

### What goes wrong with `any`: a blank chat screen

The editor refuses `setUser`, and the developer is in a hurry. **Beware! Silencing the refusal with `any` turns off every check on `user`, and the user opens a blank page.**

> [!DEFINITION]
> **What is `any`?** [REVIEW] `any` is a TypeScript type that means "this value can be anything, so check nothing on it". It removes the error, and it removes every check with it (Lesson 91).

Here is how it happens:
1. The developer changes the line to `useState<any>(null)`. The refusal is gone.
2. The editor stops checking `user`.
3. The component reads `user.name` in its title.
4. The user opens the chat. On the first render, the server has not answered yet, so `user` is still `null`.
5. Reading `name` from `null` throws while React renders the component. The browser's message starts with `TypeError: Cannot read properties of null`.
6. With no error boundary, React removes the whole page (Lesson 72).

The user sees a blank screen where `Loading...` should be. With `User | null` as the type, the editor underlines `user` in `user.name` the moment the developer types it, and the crash never leaves the editor.

### The Rule of Thumb: a real start value needs nothing, a placeholder needs a type argument

**Look at the start value. If it is already the real kind of value, write nothing. If it is a placeholder, `null` or an empty array, write the real type in angle brackets, and check for `null` before you read the value.**

A senior developer also knows the five classic mistakes:
1. **`useState(null)` with no type**, then `any` when the setter is refused.
2. **`useState<User>(null)`.** That type says the user is always there. TypeScript refuses it, because `null` is not a `User`.
3. **One loose type for every reducer action**, `{ type: string; payload?: any }`. A misspelled action name passes the editor and matches no `case` in the browser.
4. **Old workarounds for refs.** Older articles say a ref made with `null` has a `current` you cannot assign. React 19 no longer needs those workarounds.
5. **`inputRef.current!.focus()`.** The `!` tells the editor "this is never `null`, trust me", and the warning goes away. But `current` really is `null` on the first render, and after the element leaves the page.

## SECTION | A Chat Screen With an Undo Button

Open a chat in any messaging app. For a moment, the screen says `Loading...` while the app fetches the person you write to. Then the title appears, `Chat with Taylor`, with a message field and a `Send` button.

```page width=text caption="The chat screen while the person's details load."
line: Loading...
console: quiet
```

The user types `Hi` and clicks `Send`. Some apps, such as email apps, wait a few seconds before they really send, so the user can take the message back. Our chat does the same:
1. The button reads `Sending...` and is disabled, and an `Undo` button appears.
2. If the user does nothing, the message is sent after three seconds. The message field empties, and the button reads `Send` again.
3. If the user clicks `Undo` during the wait, the message is not sent. `Hi` stays in the field, and the cursor goes back into it, so the user can fix the message.

```page width=text caption="After the details arrive, with Hi typed and Send clicked: the message waits three seconds, and Undo can stop it."
heading: Chat with Taylor
form:
  field: Message | Hi
  button: Sending...
  button: Undo
console: quiet
```

Each part of this screen gets its own hook, and most of them start with a placeholder:
1. **The person** starts as `null`, because the server has not answered. That is `useState<User | null>(null)`.
2. **The text of the message and the sending state** live in a reducer with its own actions, as the Messenger example on react.dev does (Lesson 27).
3. **The timer** that sends after three seconds is started by one click and stopped by another, so its ID lives in a ref that starts as `null` (Lesson 30).
4. **The `<input>` element** goes into a ref, so `Undo` can put the cursor back. That ref is `null` until React puts the element on the page (Lesson 31).

For `useState`, you have three ways to give the state its type:
1. **Let TypeScript read it from the start value.** This fits `false`, `''`, `0`, or a full object. react.dev says "you will get inferred types a lot of the time".
2. **Write a union of strings**, such as `useState<Status>('idle')`, where `Status` is `'idle' | 'loading' | 'success' | 'error'`. This fits a fixed set of visual states (Lesson 21), and it is react.dev's own example.
3. **Write a union that includes `null`**, such as `useState<User | null>(null)`. This fits a value that arrives later, like our user.

```tree caption="Three ways to give useState its type, and the start value each one fits."
Three ways to give `useState` its type
- +1. Read from the start value [`useState false`] | Fits a start value that is **already the real kind** | Our code writes **nothing**
- +2. A union of strings [`useState<Status>`] | Fits a **fixed set of visual states** | The setter accepts **only the listed words**
- +3. A union with `null` [`useState<User or null>`] | Fits a value that **arrives later** | Our code must **check for `null`** before reading it
```

We build the chat in a small React project written in TypeScript, with the setup of Lesson 90:

```files title="chat-screen: File Explorer" caption="Our project files: App.tsx places the chat, and Chat.tsx holds the user, the reducer, the timer ref, and the input ref."
index.html | entry | The HTML page with the empty root div where React mounts
tsconfig.json | settings | Tells TypeScript how to read the project
src/
  main.tsx | boundary | Imports `App` from `./App` and mounts it into `#root`
  App.tsx | parent | Exports `App` as default and imports `Chat`
  components/
    Chat.tsx | state | Holds the user, the reducer for the message, the timer ref, and the input ref
```

**PRINCIPLES:** Every hook takes its type from its start value, unless your code writes a type argument. Six principles follow as the chat screen grows:
1. **Principle 1: `useState('')` reads `string` from the start value.** A real start value needs no type. The setter then accepts only that type.
2. **Principle 2: `useState<User | null>(null)` for a value that arrives later.** With no type argument, the state can only ever be `null`.
3. **Principle 3: `if (user === null)` shows `Loading...` and makes `user.name` safe.** Below the check, TypeScript knows `user` is a `User`.
4. **Principle 4: a union of actions checks every `dispatch`.** Type the reducer's state and arguments, and write one object for each action `type`.
5. **Principle 5: `useRef<number | null>(null)` keeps the timer ID for Undo.** Check `current` for `null` before passing it to `clearTimeout`.
6. **Principle 6: `useRef<HTMLInputElement>(null)` waits for React to fill it.** React puts the `<input>` element into `current`, so read it with `?.`.

## PRINCIPLE | `useState('')`: TypeScript reads the type from the start value, so write nothing

> [!PRINCIPLE]
> **Principle 1: Inferred Types: `useState('')` Reads `string` From the Start Value**
>
> *When the start value already has the type the state will always hold, such as `''` or `false`, write no type argument; the setter then accepts only that type.*
>
> A `useState` with no type is still checked. TypeScript reads the type from the start value, and the setter's type follows, so `setMessage(null)` is refused on a state that started as `''`. A type argument is needed only when the start value is a placeholder that does not say what will come, such as `null` or an empty array.
>
> **DO THIS:**
> ```tsx
> const [message, setMessage] = useState(~''~); // Read as string
> const [messages, setMessages] = useState~<string[]>~([]); // An empty array needs its type written
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> const [messages, setMessages] = useState(~[]~); // **WRONG:** read as never[], so every item is refused
> ```

Here are two ways to write the sending state:

```tsx title="With no type argument, and with a type argument"
const [isSending, setIsSending] = useState(~false~); // TypeScript reads boolean from false
const [isSending, setIsSending] = useState~<boolean>~(false); // Our code writes boolean by hand
```

**Yes, it is the exact same thing!** In both lines, the state is a `boolean`, and the setter accepts only a `boolean`. react.dev says the type argument "isn't very useful in this case", because the start value already says everything. The same holds for text: `useState('')` and `useState<string>('')` give the exact same `string` state.

Many developers believe the opposite: that a `useState` with no type argument is not checked at all. It is checked. The start value gives the type.

> [!DEFINITION]
> **What does inferring a type mean?** [REVIEW] Inferring a type means that TypeScript works out the type from the code around it, so you do not write it. After `const name = 'John'`, TypeScript knows that `name` is a string. After `useState('')`, it knows that the state is a string (Lesson 91).

### The setter accepts only the type of the start value

Here is the first version of our chat. It keeps the text of the message field in `message`, and `Send` empties the field:

```tsx title="src/components/Chat.tsx"
import { useState } from 'react';

export default function Chat() {
  const [message, setMessage] = useState(~''~); // TypeScript reads string from ''

  return (
    <div>
      <label>
        Message
        <input value={message} onChange={e => setMessage(e.currentTarget.value)} />
      </label>
      <button onClick={() => setMessage('')}>Send</button>
    </div>
  );
}
```

`App` places the chat on the page:

```tsx title="src/App.tsx"
import Chat from './components/Chat';

export default function App() {
  return ~<Chat />~; // React calls Chat and puts the field and the button on the page
}
```

The user types `Hi`, then clicks `Send`:

```page width=text caption="The chat after the user types Hi in the message field."
form:
  field: Message | Hi | good
  button: Send
console: quiet
```

```page width=text caption="The same chat after the user clicks Send: the message field is empty again."
form:
  field: Message |
  button: Send
console: quiet
```

Now a developer clears the field with `null` instead of `''`. Many developers use `null` to mean "nothing here":

```tsx title="Clearing a string state with null"
<button onClick={() => setMessage(~null~)}>Send</button> {/* **WRONG:** the editor refuses null: the setter accepts only a string */}
```

The editor refuses it:

```text title="The editor's message"
Argument of type 'null' is not assignable to parameter of type 'SetStateAction<string>'.
```

Nobody wrote `string` anywhere. Here is where it comes from:
1. React's types describe `useState` with one type for the state. The start value fills it in.
2. TypeScript sees `''`, so the state is a `string`.
3. The setter's type follows. `SetStateAction<string>` means "a `string`, or a function that takes the old `string` and returns a new one", the updater function (Lesson 16). `null` is neither.

So the editor has just pointed the developer to the right way to clear the field: `''`.

### An empty array is a placeholder too

Suppose the chat also keeps a list of the messages the user has sent. The developer trusts inference again:

```tsx title="A list that starts empty, with no type"
const [messages, setMessages] = useState(~[]~); // An empty array: TypeScript cannot tell what it will hold
setMessages([...messages, 'Hi']); // **WRONG:** the editor refuses 'Hi'
```

The editor refuses `'Hi'`:

```text title="The editor's message"
Type 'string' is not assignable to type 'never'.
```

Why? An empty array does not say what it will hold, exactly like `null`. So TypeScript gives it the type `never[]`, an array that may hold nothing at all. The fix is the same as for `null`: write what the placeholder stands for.

```tsx title="A list that starts empty, with a type argument"
const [messages, setMessages] = useState~<string[]>~([]); // An array of strings, empty for now
setMessages([...messages, 'Hi']); // Accepted
```

```tree caption="When the start value is real, TypeScript reads the type; when it is a placeholder, our code writes it."
What TypeScript reads from the start value
- +A real value [`useState empty string`] | Reads **`string`** | Write **no type argument**
- +The same, written by hand [`useState<string>`] | **The exact same `string`** | The type argument **adds nothing**
- !An empty array [`useState empty array`] | Reads **`never[]`** | Write **`string[]`** in the angle brackets
```

Remember: a real start value needs nothing. A placeholder needs a type argument.

## PRINCIPLE | `useState<User | null>(null)`: the state holds `null` now and the user later

> [!PRINCIPLE]
> **Principle 2: Union With `null`: `useState<User | null>(null)` for a Value That Arrives Later**
>
> *When the state starts as `null` and the real value arrives later, write the type argument with a union, `useState<User | null>(null)`; with no type argument, the state can only ever be `null`.*
>
> TypeScript cannot guess what `null` stands for, so it makes `null` the whole type, and the setter refuses the fetched user with a message about a function. `useState<User>(null)` is refused too, because the first render has no user yet. Silencing the error with `any` removes every check on the state.
>
> **DO THIS:**
> ```tsx
> const [user, setUser] = useState~<User | null>~(null); // Room for null now and for the User later
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> const [user, setUser] = useState~<any>~(null); // **WRONG:** any removes every check on user
> ```

The chat needs the person we write to. That person comes from the server after the first render, so the state must start empty:

```tsx title="With no type argument, and with a union that includes null"
const [user, setUser] = useState(~null~); // The state can only ever be null
const [user, setUser] = useState~<User | null>~(null); // A User, or null until the User arrives
```

**It may look the same, but it is NOT the same thing!** Both start as `null`, and both give the exact same first render. Only the second one accepts the user when the server answers.

### The refused setter and its strange message

Here is the chat with the fetch in an Effect (Lesson 33), written with the untyped state:

```tsx title="src/components/Chat.tsx"
type User = { id: number; name: string };

export default function Chat() {
  const [user, setUser] = useState(~null~); // **WRONG:** TypeScript reads the type null
  const [message, setMessage] = useState('');

  useEffect(() => {
    let ignore = false;
    fetch('/api/users/1')
      .then(response => response.json())
      .then((data: User) => {
        if (!ignore) {
          ~setUser(data)~; // **WRONG:** the editor refuses a User here
        }
      });
    return () => {
      ignore = true;
    };
  }, []);
```

The editor refuses `setUser`. The message is clearest when the user object is written out by hand, as at the start of this lesson:

```text title="The editor's message"
Object literal may only specify known properties, and 'id' does not exist in type '(prevState: null) => null'.
```

You passed an object, and the message talks about a function. Here is why:
1. TypeScript sees the start value `null`, so the state's type is `null`.
2. The setter accepts two forms: a new value, or an updater function that takes the old value. For this state, that means `null`, or a function from `null` to `null`.
3. Your object is not `null`, so TypeScript also tries it against the function form, and it reports on that last try.

So the message says nothing about users, because this state has no room for one.

Something that can be tricky: the page itself would still run in the browser. The types are removed before the code runs (Lesson 90). The refusal lives only in the editor.

### `useState<User>(null)` says the user is always there

The next try is often to write only `User` in the angle brackets:

```tsx title="A type that says the user is always there"
const [user, setUser] = useState~<User>~(null); // **WRONG:** null is not a User, so the editor refuses the start value
```

Now the editor refuses the start value itself:

```text title="The editor's message"
Argument of type 'null' is not assignable to parameter of type 'User | (() => User)'.
```

That is TypeScript's strict mode at work (Lesson 91). The type `User` promises a user on every render, and the very first render breaks that promise.

Only `User | null` tells the truth about both moments, before the server answers and after:

```tsx title="src/components/Chat.tsx"
export default function Chat() {
  const [user, setUser] = useState~<User | null>~(null); // A User, or null until the server answers
```

Now `setUser(data)` is accepted.

### `(data: User)` is a promise about the server, not a check

One more detail sits in the fetch. `response.json()` gives the data the type `any`, because TypeScript cannot know what a server will send. Writing `(data: User)` says what you expect the server to send. Nothing checks it while the page runs. If the server sends `{ fullName: 'Taylor' }`, the editor stays quiet, and the title shows no name.

```tree caption="Three ways to type a state that starts empty: only a union with null accepts both moments, before and after the answer."
Three ways to type the `user` state
- !No type argument [`useState null`] | The state is **only `null`** | The setter **refuses the user**
- !Only `User` [`useState<User>`] | Promises a user **on every render** | The editor **refuses the start value `null`**
- +`User` or `null` [`useState<User or null>`] | Matches **before and after** the answer | The setter **accepts the user**
```

Remember: `null` is only a placeholder. Write what it stands for, `User | null`.

## PRINCIPLE | `if (user === null)`: the check shows `Loading...` and makes `user.name` safe

> [!PRINCIPLE]
> **Principle 3: Narrowing: `user === null` Shows `Loading...` and Unlocks `user.name`**
>
> *A state typed `User | null` must be checked for `null` before `user.name` is read; below the check, TypeScript knows that `user` is a `User`.*
>
> The `null` in the type is a real moment: the first render, before the server answers. A check that returns early when `user` is `null` removes `null` from the type for every line below it, and it is also the line that shows `Loading...`. The shortcuts `user!.name` and `any` remove the warning, and the first render still throws.
>
> **DO THIS:**
> ```tsx
> if (~user === null~) {
>   return <p>Loading...</p>; // The first render shows the loading line
> }
> return <h1>Chat with {user.name}</h1>;
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> return <h1>Chat with {~user!~.name}</h1>; // **WRONG:** the editor is silenced, and the first render throws
> ```

When the user opens the chat, the person's details are not there yet. Now the developer adds the title:

```tsx title="The title read with no check"
const [user, setUser] = useState<User | null>(null);

<h1>Chat with {~user~.name}</h1> {/* **WRONG:** the editor underlines user: it is possibly null */}
```

The editor says: `'user' is possibly 'null'.`

The warning is real. React renders the component first, then runs the Effect that starts the fetch, and the server answers long after that (Lessons 32 and 33). On the first render, this line would read `name` from `null` and throw.

### The check for `null` is also the loading line

The developer puts a check for `null` above the title:

```tsx title="A check for null before the title"
if (~user === null~) {
  return <p>Loading...</p>; // While user is null, the page shows only this line
}

return <h1>Chat with {~user~.name}</h1>; // No underline: below the check, user is a User
```

The underline is gone, and no type was written, because TypeScript reads the `if`:
1. Above the `if`, `user` is `User | null`.
2. The `if` returns early when `user` is `null` (Lesson 10).
3. So every line below the `if` runs only when `user` is a `User`.

Hover over `user` below the `if`, and the editor shows `User`.

> [!DEFINITION]
> **What is narrowing?** [NEW] Narrowing means that after a check, TypeScript makes the type of a value smaller. Above `if (user === null) return ...`, `user` is `User | null`. Below it, `user` is a `User`, because the `null` case has already returned. You write no type: TypeScript reads the check (Lesson 92).

Here is the point a senior developer wants you to see. The `null` in the type is not a whim of the editor. It is a real moment on the screen, the first render before the data arrives. And the check that removes `null` from the type is the same `if` that shows `Loading...` to the user.

Here is the end of the chat, with the check and the title:

```tsx title="src/components/Chat.tsx"
  if (~user === null~) {
    return <p>Loading...</p>;
  }

  return (
    <div>
      <h1>Chat with {user.name}</h1>
      <label>
        Message
        <input value={message} onChange={e => setMessage(e.currentTarget.value)} />
      </label>
      <button onClick={() => setMessage('')}>Send</button>
    </div>
  );
}
```

The user opens the chat. The loading line comes first, then the title:

```page width=text caption="The first render: user is null, so the chat shows only the loading line."
line: Loading...
console: quiet
```

```page width=text caption="After the server answers: user is a User, so the chat shows the title, the message field, and the button."
heading: Chat with Taylor

  field: Message |
  button: Send
```

### VS | The check vs. `user?.name`: both remove the underline, only the check shows a loading line

Some developers write `user?.name` instead of a check.

> [!DEFINITION]
> **What is optional chaining?** [NEW] Optional chaining is the `?.` written in place of a dot. It is plain JavaScript. When the value before `?.` is `null` or `undefined`, the expression stops and gives `undefined` instead of throwing, as MDN describes it. `user?.name` gives `undefined` while `user` is `null` (Lesson 92).

The editor accepts `user?.name`, so the underline is gone too. But the two do NOT show the same page while the data loads:
- **With `if (user === null) return ...`**, the user sees `Loading...`, then the full chat.
- **With `user?.name`**, React shows nothing for `undefined`. The title reads `Chat with` and stops there, next to a message field the user can already type into.

Only the check gives the user an honest screen while the data loads.

### The `!` and `any` shortcuts remove the warning, not the crash

Two shortcuts make the underline go away without a check, and both bring back the crash from the start of this lesson:
1. **`user!.name`**: the `!` tells the editor "trust me, this is not `null`". The editor stops warning. On the first render, `user` is still `null`, and the line throws.
2. **`useState<any>(null)`**: the editor stops checking `user` at all. The line throws in the same place.

In both cases the browser's message starts with `TypeError: Cannot read properties of null`, and with no error boundary the user sees a blank page (Lesson 72).

```tree caption="Three ways to read user.name: only the check for null gives the user a loading line instead of a crash."
Reading `user.name` while `user` may be `null`
- +A check for `null` [`if user === null`] | The page shows **`Loading...`** first | Below the check, `user` is **a `User`**
- !Optional chaining [`user?.name`] | No crash, but the title reads **`Chat with`** and nothing after it | The user sees **half a screen** while loading
- !The `!` or `any` shortcut [`user!.name`] | The editor **stops warning** | The first render **throws**, and the page goes **blank**
```

Remember: the type says `null` because the screen really has a moment with no user. Check for it, and show `Loading...`.

## PRINCIPLE | A union of actions: `dispatch` refuses a wrong action name or a missing field

> [!PRINCIPLE]
> **Principle 4: Discriminated Unions: A Union of Actions Checks Every `dispatch`**
>
> *Type the reducer's state, its initial state, and its arguments and return value, and write the actions as a union of objects, one for each `type`, each with only its own fields.*
>
> With one loose action type, any string passes as `type`, so a misspelled action reaches the browser and matches no `case`. With a union, the `type` field tells TypeScript which action it is, so `dispatch` refuses a wrong name or a missing field, and each `case` sees only the fields of its own action. `useReducer` then reads its types from the reducer and the initial state.
>
> **DO THIS:**
> ```tsx
> type ChatAction =
>   | ~{ type: 'edited_message'; message: string }~ // Each action lists its own fields
>   | { type: 'sent_message' };
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> type ChatAction = ~{ type: string; payload?: any }~; // **WRONG:** a misspelled type passes the editor
> ```

The chat is about to get a wait before sending, an `Undo` button, and a sending state. When the update logic grows like this, we move it into a reducer.

> [!DEFINITION]
> **What is a reducer?** [REVIEW] A reducer is a function that takes the current state and an action, and returns the next state. An action is a plain object with a `type` that says what happened, such as `{ type: 'sent_message' }`. Your event handlers call `dispatch` with an action, and React calls the reducer (Lesson 27).

Here are two ways to type the actions:

```tsx title="One loose action type, and a union of action types"
type ChatAction = ~{ type: string; payload?: any }~; // Any name, any data

type ChatAction =
  | ~{ type: 'edited_message'; message: string }~ // Must carry the new text
  | ~{ type: 'sent_message' }~; // Carries nothing else
```

**It may look the same, or work the same at first, but it is NOT the same thing!** Both run the exact same reducer in the browser. The difference shows up when a developer makes a mistake:
- **With the loose type**, `dispatch({ type: 'edited_mesage', payload: 42 })` passes the editor. Any string fits `type`, and `any` fits the data.
- **With the union**, the same line is refused. `type` must be one of the listed words, and each word comes with its own fields.

> [!DEFINITION]
> **What is a discriminated union?** [NEW] A discriminated union is a union of objects that all share one field, and each object has its own fixed word in that field. In `ChatAction`, the shared field is `type`. When TypeScript sees `type: 'edited_message'`, it knows which object it is looking at, and which fields that object has. This is the name the interview question uses (Lesson 92).

### The four places to type a reducer

react.dev types a reducer in four places. Here they are for our chat:

```tsx title="src/components/Chat.tsx"
type ChatState = { message: string }; // 1. The state

type ChatAction = // 2. The actions, one object for each type
  | { type: 'edited_message'; message: string }
  | { type: 'sent_message' };

const initialState: ~ChatState~ = { message: '' }; // 3. The initial state

function chatReducer(state: ~ChatState~, action: ~ChatAction~): ~ChatState~ { // 4. The arguments and the return value
  switch (action.type) {
    case 'edited_message':
      return { ...state, message: ~action.message~ }; // Here, action is the object with message
    case 'sent_message':
      return { ...state, message: '' };
    default:
      throw new Error('Unknown action');
  }
}
```

Inside the component, `useReducer` takes the place of `useState('')`. You write no type argument on it:

```tsx title="src/components/Chat.tsx"
  const [state, dispatch] = ~useReducer(chatReducer, initialState)~; // state is a ChatState, dispatch accepts only a ChatAction
```

TypeScript reads the types from `chatReducer` and `initialState`. That is the same rule as `useState`: the hook takes its type from what you give it. react.dev recommends this: "it is often better to set the type on the initial state instead" of writing type arguments on the hook.

The message field and the button now dispatch actions:

```tsx title="src/components/Chat.tsx"
        <input
          value={state.message}
          onChange={e => dispatch(~{ type: 'edited_message', message: e.currentTarget.value }~)}
        />
      </label>
      <button onClick={() => dispatch(~{ type: 'sent_message' }~)}>Send</button>
```

The page is the same as before: the user types `Hi`, clicks `Send`, and the field empties. What changed is what the editor checks.

### Three mistakes the union catches

Here are three mistakes developers really make:

```tsx title="Two wrong dispatch calls"
dispatch(~{ type: 'edited_message' }~); // **WRONG:** the text is missing
dispatch({ type: ~'edited_mesage'~, message: 'Hi' }); // **WRONG:** a letter is missing from the name
```

```tsx title="A field read in the wrong case"
case 'sent_message':
  return { ...state, message: ~action.message~ }; // **WRONG:** this action has no message
```

1. **A missing field.** The editor says that `message` is missing, because the `edited_message` object must carry it.
2. **A misspelled name.** The editor says that `'edited_mesage'` is not one of the listed words, and it suggests `'edited_message'`.
3. **A field read in the wrong `case`.** Inside `case 'sent_message'`, `action.message` is refused, because that action has no `message`. The `switch` on `action.type` narrows `action` to one object of the union in each `case`: the same narrowing as Principle 3.

With the loose type, the editor says nothing about any of them. Suppose the misspelled line sits in the field's `onChange`:
1. The user types the first letter.
2. React calls the reducer while it renders `Chat`.
3. The `type` matches no `case`, so the reducer reaches `default` and throws `Unknown action`.
4. With no error boundary, React removes the whole page, and the user loses the chat on the first keystroke (Lesson 72).

Without that `throw`, react.dev says the whole state "becomes `undefined`".

```tree caption="A loose action type and a union of action types run the same reducer, but only the union lets the editor check every dispatch."
Two ways to type the actions of `chatReducer`
- !One loose object [`type: string, payload: any`] | Accepts **any name** and **any data** | A misspelled `type` **reaches the browser** and matches no `case`
- +A union of objects [`edited_message or sent_message`] | Each `type` has **only its own fields** | The editor **refuses** a wrong name, a missing field, or a field in the wrong `case`
```

Remember: type the reducer and the initial state, and `useReducer` reads the rest.

## PRINCIPLE | `useRef<number | null>(null)`: the ref keeps the timer ID that `Undo` stops

> [!PRINCIPLE]
> **Principle 5: Value Refs: `useRef<number | null>(null)` Keeps the Timer ID for Undo**
>
> *A ref that your code fills later starts as `null`, so write the type argument with a union, `useRef<number | null>(null)`; in React 19 its `current` can always be assigned, and it must be checked for `null` before it is passed on.*
>
> A `useRef(null)` with no type reads the type `null` from its start value, so it refuses the timer ID. With the union, the assignment is accepted, but `clearTimeout` still refuses a value that may be `null`, so a check for `null` comes first. The ref keeps the same ID across renders, so `Undo` stops the exact timer that `Send` started.
>
> **DO THIS:**
> ```tsx
> const timeoutRef = useRef~<number | null>~(null); // Room for the timer ID
> if (~timeoutRef.current !== null~) {
>   clearTimeout(timeoutRef.current); // Below the check, current is a number
> }
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> const timeoutRef = useRef(~null~); // **WRONG:** current can hold only null
> timeoutRef.current = setTimeout(() => dispatch({ type: 'sent_message' }), 3000); // **WRONG:** the editor refuses the timer ID
> ```

When the user clicks `Send`, the chat waits three seconds before it really sends. One click starts the timer, and another click, `Undo`, must stop that exact timer. So the timer's ID lives in a ref.

> [!DEFINITION]
> **What is a ref?** [REVIEW] A ref is an object with one field, `current`, that React keeps for your component between renders. `useRef(null)` returns `{ current: null }`. You read and write `current` directly, with no setter, and changing it does not make React render again (Lesson 30).

Before the first click, there is no timer yet. So the ref starts as `null`, a placeholder again. And a ref takes its type from its start value, exactly like state:

```tsx title="With no type argument, and with a union that includes null"
const timeoutRef = useRef(~null~); // current can only ever hold null
const timeoutRef = useRef~<number | null>~(null); // current holds a timer ID, or null before the first timer
```

**It may look the same, but it is NOT the same thing!** Both start as `null`. Only the second one accepts the timer ID. Why `number`? In the browser, `setTimeout` returns "a positive integer" that names the timer, as MDN says.

### The reducer gets two more actions

First, the reducer learns about the wait. The state gets one more field, `isSending`, and the union gets two more actions:

```tsx title="src/components/Chat.tsx"
type ChatState = { message: string; ~isSending: boolean~ };

type ChatAction =
  | { type: 'edited_message'; message: string }
  | ~{ type: 'started_sending' }~ // The user clicked Send, and the wait begins
  | ~{ type: 'undone' }~ // The user clicked Undo during the wait
  | { type: 'sent_message' }; // Three seconds passed, and the message is sent

const initialState: ChatState = { message: '', isSending: false };
```

Each new action gets its own `case`:

```tsx title="src/components/Chat.tsx"
    case 'started_sending':
      return { ...state, ~isSending: true~ }; // The button reads Sending...
    case 'undone':
      return { ...state, ~isSending: false~ }; // The text stays in the field
    case 'sent_message':
      return { ~message: ''~, isSending: false }; // The field empties
```

### Two refusals, one after the other

Now the handlers. The developer copies the untyped ref from react.dev's JavaScript example:

```tsx title="src/components/Chat.tsx"
  const timeoutRef = useRef(null);

  function handleSend() {
    dispatch({ type: 'started_sending' });
    ~timeoutRef.current~ = setTimeout(() => { // **WRONG:** the editor refuses a number here
      dispatch({ type: 'sent_message' });
    }, 3000);
  }
```

**Two lines copied from working JavaScript are refused, and the second refusal is about a call the browser would run without trouble.** Here is what happens:
1. The editor refuses the assignment. The untyped ref read its type from `null`.
2. The developer writes `useRef<number | null>(null)`, and the assignment is accepted.
3. In `handleUndo`, the developer writes `clearTimeout(timeoutRef.current)`, as react.dev's example does.
4. The editor refuses that call too.

Here are the two messages, in order:

```text title="The editor's two messages"
Type 'number' is not assignable to type 'null'.
Argument of type 'number | null' is not assignable to parameter of type 'number | undefined'.
```

Why the second refusal? The browser's types describe `clearTimeout` as taking a `number` or `undefined`, but not `null`. In the browser itself, MDN says a `clearTimeout` call with an ID that names no timer "does nothing". The types are simply stricter than the browser.

The fix is a check for `null` before the call, the same narrowing as Principle 3:

```tsx title="src/components/Chat.tsx"
  const timeoutRef = useRef~<number | null>~(null); // A timer ID, or null before the first timer

  function handleSend() {
    dispatch({ type: 'started_sending' });
    timeoutRef.current = setTimeout(() => { // Accepted: current may hold a number
      dispatch({ type: 'sent_message' });
    }, 3000);
  }

  function handleUndo() {
    if (~timeoutRef.current !== null~) { // Below the check, current is a number
      clearTimeout(timeoutRef.current);
    }
    dispatch({ type: 'undone' });
  }
```

The `Send` button reads `state.isSending`, and `Undo` appears only during the wait:

```tsx title="src/components/Chat.tsx"
      <button disabled={state.isSending} onClick={handleSend}>
        {state.isSending ? 'Sending...' : 'Send'}
      </button>
      {~state.isSending &&~ <button onClick={handleUndo}>Undo</button>} {/* Undo appears only during the wait */}
```

The user types `Hi` and clicks `Send`. For three seconds, the chat looks like this:

```page width=text caption="During the three-second wait: the Send button reads Sending... and is disabled, and Undo appears."
heading: Chat with Taylor
form:
  field: Message | Hi
  button: Sending...
  button: Undo
console: quiet
```

If the user does nothing, the message is sent after three seconds: the field empties, the button reads `Send`, and `Undo` is gone. If the user clicks `Undo` during the wait, `handleUndo` clears the timer, so the message is never sent:

```page width=text caption="After the user clicks Undo during the wait: the message is not sent, and Hi stays in the field."
heading: Chat with Taylor
form:
  field: Message | Hi | good
  button: Send
console: quiet
```

### In React 19, `current` can always be assigned

Older articles say that a ref made with `null` has a `current` you cannot assign, and they show workarounds. That was true of older versions of React's types. The React 19 Upgrade Guide says "all refs are mutable" now: `current` can always be assigned. `useRef` always returns one type, `RefObject`, an object with one property, `current`. Hover over `timeoutRef`, and the editor shows `RefObject<number | null>`.

React 19's types have one more convenience. When the start value is `null`, they add `null` to the type for you. So `useRef<number>(null)` gives the exact same `RefObject<number | null>`. **Yes, it is the exact same type!** Writing `number | null` in full only says it out loud in the code.

### The trap of Node's types

Something that can be tricky: some projects also load Node's types. There, `setTimeout` returns a `NodeJS.Timeout` object instead of a `number`, and the editor refuses to store it in a `number` ref. Two fixes work in both kinds of project:
1. **Type the ref as `ReturnType<typeof setTimeout>`**, which means "whatever type `setTimeout` returns here".
2. **Call `window.setTimeout`**, which always uses the browser's types and returns a `number`.

```tree caption="Three ways to type the timer ref: only a type that includes number accepts the timer ID."
Three ways to type `timeoutRef`
- !No type argument [`useRef null`] | `current` holds **only `null`** | The timer ID is **refused**
- +`number` or `null`, written in full [`useRef<number or null>`] | `current` holds **a timer ID or `null`** | **Check for `null`** before `clearTimeout`
- +Only `number`, with `null` as the start [`useRef<number>`] | React 19 **adds `null`** for us | **The exact same type** as `number` or `null` written in full
```

Remember: a ref is typed like state. A placeholder `null` needs a type argument, and a check before you pass `current` on.

## PRINCIPLE | `useRef<HTMLInputElement>(null)`: React fills `current` with the `<input>` element, and empties it again

> [!PRINCIPLE]
> **Principle 6: DOM Refs: `useRef<HTMLInputElement>(null)` Waits for React to Fill It**
>
> *Type a ref for an element with the element type, `useRef<HTMLInputElement>(null)`; its `current` is the element or `null`, so read it with `?.` or a check for `null`.*
>
> A ref for an element has the same `RefObject` type as a ref for a timer ID. The difference is that React writes its `current`: it puts the element there during the commit, and puts `null` back when the element leaves the page. The `!` shortcut silences the editor, and the line throws the first time the element is not there.
>
> **DO THIS:**
> ```tsx
> const inputRef = useRef~<HTMLInputElement>~(null);
> inputRef.current~?.~focus(); // Skipped when the input is not on the page
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> inputRef.current~!~.focus(); // **WRONG:** throws when the input is not on the page
> ```

After `Undo`, the user wants to fix the message. So the chat puts the cursor back into the message field with `focus()`.

Remember `getElementById`? In plain JavaScript, you grab the element yourself, and call `focus()` on it. In React, you never create the elements by hand. React creates them from your JSX, so you have nothing to grab. A ref is how you ask React: "When you create this `<input>`, give it to me!" React puts it into `inputRef.current`. From then on, it is the same `<input>` element you know from plain JavaScript (Lesson 31).

```tsx title="Plain TypeScript vs. React: the same input, the same focus"
const input = document.getElementById('message'); // Plain: the type is HTMLElement | null
input?.focus();

const inputRef = useRef<HTMLInputElement>(null); // React: React fills current with the <input>
<input ~ref={inputRef}~ /> {/* Tells React which element to put into inputRef.current */}
inputRef.current?.focus();
```

Notice something. Even in plain TypeScript, `getElementById` returns `HTMLElement | null`, because the element may not be on the page. A ref for an element has the same honest `null`, for the same reason.

> [!DEFINITION]
> **What is `HTMLInputElement`?** [REVIEW] `HTMLInputElement` is the browser's type for an `<input>` element. It has the properties and methods of a real input, such as `value` and `focus()`. TypeScript reads the browser's types through `tsconfig.json` (Lesson 91).

### VS | The timer ref vs. the `<input>` ref: the same type, a different writer

Here are the two refs of our chat side by side:

```tsx title="A ref for a timer ID, and a ref for the input"
const timeoutRef = useRef~<number | null>~(null); // Our code writes current: the timer ID
const inputRef = useRef~<HTMLInputElement>~(null); // React writes current: the <input> element
```

**For the type, yes, it is the exact same thing!** Both are a `RefObject`, and in both, `current` holds a value or `null`. Hover over `inputRef`, and the editor shows `RefObject<HTMLInputElement | null>`. React 19's types added the `null` for you, as with the timer ref.

The one difference is who writes `current`:
- **The timer ref** is written by your code, in `handleSend`.
- **The `<input>` ref** is written by React. React puts the `<input>` element into `current` during the commit, after it creates the element on the page, and puts `null` back when the element leaves the page.

Leaving out the type argument fails here just as it did for the timer. With `useRef(null)`, `current` can hold only `null`, and the editor refuses `focus()` on it.

```tree caption="The timer ref and the input ref have the same type shape; the one difference is who writes current."
Two refs in `Chat`
- +The timer ref [`useRef<number or null>`] | **Our code** writes `current` in `handleSend` | `null` **before the first click on Send**
- +The input ref [`useRef<HTMLInputElement>`] | **React** writes `current` during the commit | `null` **before the input is on the page**, and **after it leaves**
```

### "Possibly null", though the input is on the screen

The developer gives the `<input>` its ref and calls `focus()` at the end of `handleUndo`:

```tsx title="focus called with no check"
<input ref={inputRef} />

inputRef.current.focus(); // **WRONG:** the editor underlines inputRef.current: it is possibly null
```

The editor says: `'inputRef.current' is possibly 'null'.`

The input is plainly on the screen when the user clicks `Undo`, so the warning looks wrong. It is not. react.dev says: "During the first render, the DOM nodes have not yet been created, so `ref.current` will be `null`." And React sets `current` back to `null` when the element leaves the page. The type keeps the `null` for those moments.

The fix is optional chaining, the `?.` from Principle 3. When `current` is `null`, the call to `focus()` is skipped instead of throwing:

```tsx title="src/components/Chat.tsx"
  function handleUndo() {
    if (timeoutRef.current !== null) {
      clearTimeout(timeoutRef.current);
    }
    dispatch({ type: 'undone' });
    ~inputRef.current?.focus()~; // Calls focus only when the input is on the page
  }
```

Here, unlike the title in Principle 3, skipping is exactly right: when there is no input, there is nothing to focus. The user types `Hi`, clicks `Send`, and clicks `Undo` during the wait. `Hi` stays in the field, and the cursor is back in it, ready for the user to keep typing.

### VS | `?.` vs. `!`: the first skips the call, the second throws

Many developers silence the warning with `!` instead: `inputRef.current!.focus()`. The two are NOT the same thing:
- **With `?.`**, the call is skipped when there is no input on the page. Nothing breaks.
- **With `!`**, your code tells the editor that there is always an input. The editor believes it. When there is no input, the line throws.

**The `!` breaks the day a teammate hides the input.** Here is how:
1. A developer writes `inputRef.current!.focus()` in `handleUndo`.
2. Later, a teammate hides the input while the message is sending: `{state.isSending ? null : <input ref={inputRef} />}`.
3. The user clicks `Send`. The input leaves the page, and React sets `current` back to `null`.
4. The user clicks `Undo`. The line throws a `TypeError` that starts with `Cannot read properties of null`. The Console shows the error, and any line after it in `handleUndo` never runs.

With `?.`, the same click skips the `focus()` call, and the handler runs to its end. The editor's warning was telling the truth all along.

```tree caption="Three ways to write the input ref and its focus call: only optional chaining on a typed ref keeps working when the input is not on the page."
Calling `focus` on `inputRef.current`
- +Optional chaining [`inputRef.current?.focus`] | Calls `focus` **only when the input is there** | **Nothing breaks** when `current` is `null`
- !The `!` shortcut [`inputRef.current!.focus`] | The editor **stops warning** | **Throws** when the input is not on the page
- !No type argument [`useRef null`] | `current` holds **only `null`** | The editor **refuses `focus`** on it
```

Remember: React fills `current` only while the element is on the page. Write the element type, and read `current` with `?.`.

## All 6 Principles Together

### The complete code

The text of the message and the reducer take their types from their start values. Every `null` placeholder has a type argument that says what it stands for:

```tsx title="src/components/Chat.tsx"
import { useEffect, useReducer, useRef, useState } from 'react';

type User = { id: number; name: string };

type ChatState = { message: string; isSending: boolean };

type ChatAction =
  | ~{ type: 'edited_message'; message: string }~ // Principle 4: one object for each type
  | { type: 'started_sending' }
  | { type: 'undone' }
  | { type: 'sent_message' };

const initialState: ChatState = { message: '', isSending: false };

function chatReducer(state: ChatState, action: ChatAction): ChatState {
  switch (action.type) {
    case 'edited_message':
      return { ...state, message: action.message };
    case 'started_sending':
      return { ...state, isSending: true };
    case 'undone':
      return { ...state, isSending: false };
    case 'sent_message':
      return { message: '', isSending: false };
    default:
      throw new Error('Unknown action');
  }
}

export default function Chat() {
  const [user, setUser] = useState~<User | null>~(null); // Principle 2: null until the server answers
  const [state, dispatch] = useReducer(chatReducer, initialState);
  const inputRef = useRef~<HTMLInputElement>~(null); // Principle 6: React fills it with the input
  const timeoutRef = useRef~<number | null>~(null); // Principle 5: our code fills it with the timer ID

  useEffect(() => {
    let ignore = false;
    fetch('/api/users/1')
      .then(response => response.json())
      .then((data: User) => {
        if (!ignore) {
          setUser(data);
        }
      });
    return () => {
      ignore = true;
    };
  }, []);

  function handleSend() {
    dispatch({ type: 'started_sending' });
    timeoutRef.current = setTimeout(() => {
      dispatch({ type: 'sent_message' });
    }, 3000);
  }

  function handleUndo() {
    if (~timeoutRef.current !== null~) { // Principle 5: clearTimeout refuses null
      clearTimeout(timeoutRef.current);
    }
    dispatch({ type: 'undone' });
    ~inputRef.current?.focus()~; // Principle 6: skipped when the input is not on the page
  }

  if (~user === null~) { // Principle 3: the first render shows the loading line
    return <p>Loading...</p>;
  }

  return (
    <div>
      <h1>Chat with {user.name}</h1>
      <label>
        Message
        <input
          ref={inputRef}
          value={state.message}
          onChange={e => dispatch({ type: 'edited_message', message: e.currentTarget.value })}
        />
      </label>
      <button disabled={state.isSending} onClick={handleSend}>
        {state.isSending ? 'Sending...' : 'Send'}
      </button>
      {state.isSending && <button onClick={handleUndo}>Undo</button>}
    </div>
  );
}
```

```tsx title="src/App.tsx"
import Chat from './components/Chat';

export default function App() {
  return <Chat />;
}
```

### The order in which React calls the components and the handlers

When the page loads, React calls `App`, then `Chat`, which returns the loading line. After the commit, React runs the Effect, which starts the fetch. When the server answers, `setUser` causes a new render, and `Chat` returns the full screen. During that commit, React puts the `<input>` element into `inputRef.current`. After that, React calls a handler each time the user clicks:

```tree caption="The order of the calls: App, then Chat with the loading line, then the Effect, then Chat with the full screen, and then the handlers."
`App` [1. React calls it when the page loads] | Returns `<Chat />`
- +`Chat`, first render [2. `user` is `null`] | Returns **`Loading...`** | `inputRef.current` is **`null`**
  - +The Effect [3. After the commit] | Fetches the user | Calls **`setUser`** when the server answers
- +`Chat`, next render [4. `user` is a `User`] | Returns the **title, the message field, and Send** | React puts the input into **`inputRef.current`**
  - +`handleSend` [5. The user clicks Send] | Stores the timer ID in **`timeoutRef.current`** | The button reads **`Sending...`**
  - +`handleUndo` [6. The user clicks Undo] | Clears the timer and **focuses the input** | `Hi` **stays in the field**
```

| What the hook holds | Its start value | What your code writes | Before reading it |
| :--- | :--- | :--- | :--- |
| **The text of the message, `message`** | `''`, a real value | Nothing: TypeScript reads `string` | Nothing |
| **The person, `user`** | `null`, a placeholder | `useState<User \| null>(null)` | A check for `null`, which shows `Loading...` |
| **The message and the sending state** | `initialState`, typed `ChatState` | A union of actions, and types on the reducer | Nothing: each `case` sees its own fields |
| **The timer ID, `timeoutRef`** | `null`, a placeholder | `useRef<number \| null>(null)` | A check for `null` before `clearTimeout` |
| **The `<input>` element, `inputRef`** | `null`, until React fills it | `useRef<HTMLInputElement>(null)` | `?.` or a check for `null` |

Remember the one sentence of this lesson. **Each hook takes its type from its start value: a real start value needs nothing, and a `null` placeholder needs the real type in angle brackets and a check for `null` before you read it.**

## For the Interview

> **The Interview Question:** How do you type useState, useReducer, and useRef with strict TypeScript generics?

### How to Answer Clearly in 30 Seconds

"Each hook takes its type from the start value I give it. When the start value is already the real kind of value, like `''` or `false`, I write nothing and let TypeScript infer it. When the start value is a placeholder, I write the type argument in angle brackets:
1. **`useState`**: a user that loads from the server starts as `null`, so I write `useState<User | null>(null)`. Then a check for `null`, which is also my loading line, narrows `user` to `User` before I read `user.name`. I never write `useState<User>(null)`, which strict mode refuses, or `any`, which turns off every check.
2. **`useReducer`**: I type the state, the initial state, and the reducer's arguments and return value, and I write the actions as a discriminated union, one object for each `type`. Then a misspelled action or a missing field is refused, and each `case` sees only its own fields.
3. **`useRef`**: a value ref such as a timer ID is `useRef<number | null>(null)`, checked for `null` before `clearTimeout`. A DOM ref is `useRef<HTMLInputElement>(null)`, and I read it with `?.`, because React fills `current` only while the element is on the page. In React 19 both are the same `RefObject`, and both can be assigned."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Can you pass type arguments to `useReducer` instead of typing the reducer?"**
   Yes, but react.dev calls typing the initial state "often better", and that is what I do. react.dev also shows a form with one type argument, `useReducer<State>(stateReducer, initialState)`. With the current `@types/react` 19, that form is refused with `Expected 2 type arguments, but got 1.`, and so is the older `useReducer<React.Reducer<State, Action>>`. The current form takes two type arguments: `useReducer<ChatState, [ChatAction]>`. The action type sits inside square brackets, because the types describe the arguments the reducer takes after the state as a list.
2. **"Why do older articles say a ref made with `null` has a read-only `current`?"**
   Because older versions of React's types had two ref types. A ref made with `null` and a type argument without `null` got a `current` that could not be assigned, with the error `Cannot assign to 'current' because it is a read-only property`. React 19 changed this. The Upgrade Guide says "all refs are mutable", and `useRef` always returns one type, `RefObject`. `MutableRefObject` is now marked as deprecated. React 19 also requires an argument: `useRef()` with nothing in the parentheses is refused.
3. **"How do you make TypeScript report an action that the reducer forgot to handle?"**
   In the `default` branch, I assign the action to a variable of type `never`: `const unhandled: never = action;`. Then I use that variable in the error I throw: `throw new Error('Unknown action: ' + unhandled);`. The `throw` must use it, because the Vite template refuses a variable that is never read. When every `case` is handled, no action is left for `default`, so `action` has the type `never` there, and both lines are accepted. When a developer adds an action to the union and forgets its `case`, that action is left over, and the editor refuses the assignment with a message that names the forgotten action. The TypeScript handbook calls this exhaustiveness checking.

```tree caption="Interview summary: real start values need no type, placeholders need a type argument, and each placeholder must be handled where it is read."
How the three hooks get their types
- +A real start value [`useState empty string`] | TypeScript **infers** the type | Write **nothing**
- +A placeholder for later [`useState<User or null>`] | Write the **type argument** with `null` | **Check for `null`** before reading
- +A reducer [`chatReducer, initialState`] | Type the state and a **union of actions** | `useReducer` **infers** the rest
- +A ref [`useRef<HTMLInputElement>`] | One **`RefObject`** type in React 19 | Read `current` with **`?.`** or a check
```
