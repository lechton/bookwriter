# Lecture 103: Where and When the HTML of a Page Is Made

*(Why does the same product page show a blank screen, a loading line, or the finished heading in its first second?)*

> INTERVIEW QUESTION | ❱ CORE | How do CSR, SSR, streaming SSR, static prerendering, and resuming differ?

---

## VS | The Same for Every Visitor `Blue Sneakers` vs. Only for This Visitor `Cart: 2`: the first can be made in advance, the second only when the request arrives

> Every web page reaches the phone as HTML, and somebody has to write that HTML: the browser, the server, or a build that ran before anyone visited. **Client-side rendering, server-side rendering, streaming, static prerendering, and resuming are five answers to one question: where and when is the HTML made**? The answer matters, because it decides what the visitor sees in the first second, and a part made in advance can never belong to one visitor.

Remember the first web page you wrote by hand? You typed a heading into an HTML file, and everyone who opened it got the same heading. That file was made before anyone visited.

Now think of a page that says `Hello, Alice` after you log in. Nobody could type that file in advance, because nobody knew Alice would come. Somebody has to write it at the moment Alice asks for it.

React pages work the same way. React can turn your components into HTML in three places:
- **In the browser**, after the JavaScript has downloaded and run.
- **On the server**, when a visitor's request arrives.
- **In a build**, once, before anyone visits.

**The five names you hear in interviews are five combinations of where, when, and how the HTML travels: in one piece, or in parts.**

Take the product page of an online shop. It shows the heading `Blue Sneakers`, a line with the visitor's own cart, and an `Add to cart` button. For Alice, the cart line says `Cart: 2`. Ask yourself: is every line on this page the same for every visitor? No. Alice, Bob, and everyone else read the same heading. But `Cart: 2` is Alice's cart. Bob opens the same link and sees his own number.

**Why:** Each wrong answer costs something you can see on the phone:
1. **The browser makes everything.** Alice stares at a blank page until the JavaScript has downloaded and run. React's docs say it plainly: "This can feel very slow!"
2. **The server sends the page in one piece.** The heading waits for the slowest data on the page, and here that is Alice's cart.
3. **A build makes the page in advance, with the cart inside.** Every visitor gets the same file. MDN: "for any given URL, all users will receive the same content." That cart is somebody else's cart, or no cart at all.

See the problem? The heading wants to be made early, and the cart cannot be made early. That split is the whole lesson.

So here is the one sentence to keep in mind for this whole lesson:

**A part that is the same for everyone can be made in advance. A part that belongs to one visitor can only be made when that visitor's request arrives.**

### Five Ways to Make the Same Page

Here is the product page once it has fully loaded on Alice's phone:

```page caption="The product page of the shop, once it has fully loaded on Alice's phone."
url: shop.example.com/blue-sneakers
heading: Blue Sneakers
line: Cart: 2
line: [Add to cart]
```

A friend sends Alice the link, and she opens it on her phone. Five teams could have built this page in five ways. The five ways differ most in what Alice sees in the first seconds:

| The way | Who makes the HTML, and when | What Alice sees first | What she sees next |
| :--- | :--- | :--- | :--- |
| **Client-side rendering** | The browser, after the JavaScript runs | A blank page | The heading, and her cart last of all |
| **Server-side rendering** | The server, when her request arrives, in one piece | Nothing, while the server makes the whole page | The heading and her cart together |
| **Streaming server-side rendering** | The server, when her request arrives, in parts | The heading, with `Loading cart...` where her cart goes | `Cart: 2`, a moment later |
| **Static prerendering** | A build, before anyone visits | The heading, from a file made before she arrived | Her cart cannot be in that file |
| **Resuming** | A build makes the heading, the server makes her cart | The heading, from a file made before she arrived | `Cart: 2`, filled in by the server for her |

**It may look the same at the end, but it is NOT the same thing!** Put the five finished pages side by side. They show the same heading and the same button. Open the Elements panel, and you find the same tags. Yet the HTML was not made at the same moment, or in the same place:
1. With client-side rendering, the browser made the HTML.
2. With server-side rendering and with streaming, the server made it when Alice's request arrived.
3. With static prerendering, a build made it before anyone visited.
4. With resuming, a build made the heading before anyone visited, and the server made Alice's cart when her request arrived.

Only the first way makes all of the HTML in the browser. And the moment the HTML is made decides what Alice stares at while she waits.

```tree caption="The two questions that place every way of making a page, from everything in the browser to HTML made in advance."
Two questions every way of making a page answers
- +1. Where and when is the HTML made? | **In the browser**, after the JavaScript runs | **On the server**, when each request arrives | **At build time**, before anyone visits
- +2. How does the HTML arrive? | **In one piece**, when the whole page is ready | **In parts**, the first part at once and the rest as its data arrives
```

> [!DEFINITION]
> **Request time and build time.** [NEW] Request time is the moment a visitor's request reaches the server. The server does the work again for every visitor, so it can make HTML for that visitor alone. Build time is the moment the team builds the site, before any visitor arrives. The work runs once, and its result is one file that every visitor receives (Lesson 103).

### The Rule of Thumb: is this part the same for everyone?

**Ask one question about every part of a page: is it the same for every visitor? If yes, it can be made in advance, at build time. If no, it must be made at request time, on the server or in the browser.**

Teams choose between the five ways page by page. React's docs and MDN say where each one fits:
1. **Client-side rendering** fits a page that nobody opens from a shared link, such as a screen behind a login. React's docs: single-page apps "are easier to get started with, but they can have slower initial load times."
2. **Server-side rendering in one piece** fits a server that cannot send a page in parts. React's docs: "You can continue using `renderToString` if your server environment does not support streams."
3. **Streaming server-side rendering** fits a page whose content differs for each request, with some slow data. React's docs recommend the streaming calls over `renderToString` "When possible".
4. **Static prerendering** fits a page that is the same for everyone. MDN names "blogs, documentation, and other content-driven websites", and React's docs name "the landing page for your app".
5. **Resuming** fits a page that is mostly the same for everyone, with a small part for each visitor. React's docs: first "pre-render the static parts of your app and serve it from a CDN". Then "resume rendering the shell to fill it in with dynamic content later."

Our product page is the case for all five at once. People open it from shared links, so it must show something at once. Its heading is the same for every visitor, so it can be made in advance. Its cart line belongs to one visitor, so it cannot.

A senior developer also knows the five classic mistakes:
1. **Picking one way for the whole app.** React's docs let frameworks "choose the rendering strategy on a per-route level", so one app mixes several ways, one per page.
2. **Thinking a page made in advance cannot answer clicks.** It can. The browser still loads the JavaScript and calls `hydrateRoot` on it, as on any server-rendered page.
3. **Thinking `renderToString` waits for data.** It does not. React's docs: "`renderToString` does not support streaming or waiting for data."
4. **Thinking the parts that arrive later need React in the browser.** They do not. React's docs: "Streaming does not need to wait for React itself to load in the browser, or for your app to become interactive."
5. **Thinking resuming happens in the browser and replaces hydration.** In React, `resume` runs on the server, and the browser still calls `hydrateRoot` after it.

The rest of the lesson shows each one on the real product page.

## SECTION | The Blue Sneakers Product Page

Our page has two components. `App` holds the heading and wraps the cart line in a `<Suspense>` boundary, so the page has something to show while the cart loads:

```jsx title="src/App.jsx"
import { Suspense } from 'react';
import CartLine from './CartLine.jsx';

export default function App() {
  return (
    <main>
      <h1>Blue Sneakers</h1>
      <Suspense ~fallback={<p>Loading cart...</p>}~> {/* Shown while CartLine waits for the cart */}
        <CartLine />
      </Suspense>
    </main>
  );
}
```

> [!DEFINITION]
> **Suspense and its fallback.** [REVIEW] `<Suspense>` wraps a part of the page that may not be ready yet. While that part waits, React shows the `fallback` written on the tag, here `<p>Loading cart...</p>`. Everything outside the `<Suspense>` shows at once (Lesson 69).

`CartLine` reads the visitor's cart and keeps the count that the button changes:

```jsx title="src/CartLine.jsx"
import { use, useState } from 'react';
import { getCart } from './cart.js';

export default function CartLine() {
  const cart = ~use(getCart())~; // Waits for this visitor's cart: { count: 2 } for Alice
  const [count, setCount] = useState(cart.count);
  return (
    <>
      <p>Cart: {count}</p>
      <button onClick={() => setCount(count + 1)}>Add to cart</button>
    </>
  );
}
```

> [!DEFINITION]
> **use with a promise.** [REVIEW] `use(promise)` reads the value of a promise while the component renders. While the promise still waits, the component suspends: React stops rendering it and shows the fallback of the closest `<Suspense>` above it. When the promise resolves, React renders the component again with the value. The promise must be the same one on every call, not a new one each time (Lesson 71).

`getCart` is the shop's own data function, in `cart.js`. It returns a promise of this visitor's cart, and it hands back the same promise every time it is called, as `use` needs.

These two components stay almost the same in all five ways. What changes from one way to the next is one call, in one of three files:
- **`main.jsx`** runs in the browser.
- **`server.js`** runs when a request arrives.
- **`build.js`** runs when the team builds the site.

```files title="shop: File Explorer" caption="The files of the product page. Each way of making the page changes one call in main.jsx, server.js, or build.js."
build.js | build time | Runs once, before anyone visits: calls `prerender(<App />)`
server.js | request time | Runs for each visitor's request: calls `renderToString`, `renderToReadableStream`, or `resume`
src/
  App.jsx | page | Exports `App` as default: the heading and a `<Suspense>` around `CartLine`
  CartLine.jsx | per visitor | Exports `CartLine` as default: reads the cart with `use` and shows `Cart: {count}` and the button
  cart.js | data | Exports `getCart`, the shop's function that returns a promise of the visitor's cart
  main.jsx | browser | Calls `createRoot` or `hydrateRoot`
```

Again, the one sentence of this lesson: **a part that is the same for everyone can be made in advance. A part that belongs to one visitor can only be made when that visitor's request arrives.**

**PRINCIPLES:** The five ways answer the same two questions differently, and all of them end in the browser. Six principles follow:
1. **Principle 1: createRoot: The Browser Makes Every Part of the Page.** The HTML arrives with an empty root, and the phone stays blank until the JavaScript has run.
2. **Principle 2: renderToString: The Server Sends the Page in One Piece.** The server makes the HTML at each request. It does not wait for data, so a waiting part goes out as its fallback.
3. **Principle 3: renderToReadableStream: The Shell Arrives First.** The server sends everything outside the Suspense boundaries at once, and each waiting part later, in the same response.
4. **Principle 4: prerender: One File at Build Time for Every Visitor.** The build waits for all data and makes one file. No part of that file can belong to one visitor.
5. **Principle 5: resume: The Server Finishes What the Build Left Open.** The build stops early and saves the unfinished work. When Alice arrives, the server makes her cart.
6. **Principle 6: hydrateRoot: Every Way That Sends HTML Ends Here.** Four of the five ways send HTML, and all four attach the clicks with hydrateRoot. Only client-side rendering uses createRoot.

## PRINCIPLE | `createRoot`: the browser makes the whole page, so it stays blank until the JavaScript runs

> [!PRINCIPLE]
> **Principle 1: createRoot: The Browser Makes Every Part of the Page**
>
> *With client-side rendering, the HTML that arrives holds only an empty root, and `createRoot` makes every part of the page in the browser after the JavaScript loads.*
>
> A page made in the browser has nothing to show until the JavaScript has downloaded and run, so the visitor stares at a blank page. That is fine for a screen behind a login, which nobody opens from a shared link. It is a problem for a public page, such as a product page, that people open from links on slow phones.
>
> **DO THIS:**
> ```jsx
> createRoot(document.getElementById('root')).render(~<AccountSettings />~); // Behind a login: nobody opens it from a shared link
> ```
>
> **DO NOT DO THIS:**
> ```html
> ~<div id="root"></div>~ <!-- **WRONG:** the public product page reaches the phone empty, and the visitor sees a blank page -->
> <script type="module" src="/src/main.jsx"></script>
> ```

Remember how plain JavaScript fills a page? The HTML holds an empty `<div>`, and a script creates the elements and puts them inside:

```js title="Plain JavaScript: a script fills an empty div"
const h1 = document.createElement('h1');
h1.textContent = 'Blue Sneakers';
~document.getElementById('root').appendChild(h1)~; // Until this line runs, the page is blank
```

A client-only React app does exactly the same thing. The only difference: React writes those element calls for you, from your JSX. The HTML file that reaches the phone holds an empty root and a script tag (as seen in Lesson 07):

```html title="index.html"
~<div id="root"></div>~ <!-- Empty: no heading, no cart, no button -->
<script type="module" src="/src/main.jsx"></script>
```

Inside `main.jsx`, one call makes the whole page:

```jsx title="src/main.jsx"
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

~createRoot~(document.getElementById('root')).render(<App />); // Makes the heading, the cart line, and the button in the browser
```

This is **client-side rendering**: the browser makes the HTML of the page with JavaScript. The heading, the cart line, and the button are all made on Alice's phone, after the JavaScript has downloaded and run. Until then, the phone has nothing to show.

**Beware! The cart comes last of all.** In a client-only app, the browser asks for the cart only after the page itself exists:
1. The HTML arrives empty, and the phone shows a blank page.
2. The JavaScript loads, and `createRoot` renders `App`. The heading and `Loading cart...` appear.
3. Only now does `CartLine` ask for Alice's cart, so the number arrives last.

### The Blank Page Comes from the Browser, Not from React

Many developers believe that React pages start blank because React renders them. That is not the reason. **The blank page comes from where the HTML is made**. Here it is made in the browser, so the browser has nothing to draw until the JavaScript has run. React can make the exact same HTML on a server, or at build time, and the next four principles do exactly that.

Client-side rendering still fits a page that nobody opens from a shared link, such as an account settings screen behind a login. The user has already waited for the login, and nobody sends that screen to a friend.

### Why This Bug Ships

Here is how the blank page reaches real users:
1. A team ships the public product page as a client-only app, because React's docs call client-side rendering "the default architecture for most build tools".
2. A visitor opens the shared link on a slow phone.
3. The phone shows a blank page until the JavaScript has downloaded and run. On the office network, the team never notices.

## PRINCIPLE | `renderToString`: the server sends the page in one piece, and a waiting part goes out as its fallback

> [!PRINCIPLE]
> **Principle 2: renderToString: The Server Sends the Page in One Piece**
>
> *With server-side rendering, the server makes the HTML when each request arrives and sends it in one piece; `renderToString` does not wait for data, so a part that suspends is sent as its fallback.*
>
> Server-side rendering moves the HTML from the browser to the server, so the visitor sees the heading before any JavaScript runs. But one piece means one moment. Whatever is not ready at that moment either holds back the whole page, or goes out as its fallback. With `renderToString`, it goes out as the fallback, and the real content waits for the client code. When the server can send streams, React's docs point to the streaming call of Principle 3 instead.
>
> **DO THIS:**
> ```jsx
> const stream = await ~renderToReadableStream~(<App />); // Sends the heading now, and the cart when it is ready
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const html = ~renderToString~(<App />); // **WRONG:** expects Cart: 2, but the HTML always holds Loading cart...
> ```

Lesson 102 moved the HTML to the server. Here are the two calls side by side. Both render the same `App`:

```jsx title="The same App, rendered in the browser and on the server"
~createRoot~(document.getElementById('root')).render(<App />); // main.jsx: the browser makes the HTML after the JavaScript loads
const html = ~renderToString~(<App />); // server.js: the server makes the HTML before it answers
```

**It may look the same, but it is NOT the same thing!** Both make the same finished page from the same `App`. With `createRoot`, the browser makes the HTML after the JavaScript loads. With `renderToString`, the server makes the HTML before it sends anything, so the heading reaches Alice before any JavaScript.

The server runs `renderToString` again for every visitor, so it makes the HTML at request time. In the browser, `main.jsx` changes too. It now calls `hydrateRoot` instead of `createRoot`, so that the button answers clicks. Principle 6 comes back to that call.

> [!DEFINITION]
> **createRoot and hydrateRoot.** [REVIEW] `createRoot(element).render(<App />)` builds the page from nothing inside an empty element. `hydrateRoot(element, <App />)` takes HTML that is already on the page, keeps it, and attaches the click handlers to it. A page whose HTML comes from a server calls `hydrateRoot` (Lesson 102).

### What "In One Piece" Does to Alice's Cart

`renderToString` returns one string. Think of `JSON.stringify`: it gives you the whole string at once, and you cannot send half of it now and the rest later. So the server sends the page in one piece, and that leaves the team two choices for Alice's cart. Both cost something:
1. **The server loads the cart before it renders**, through the framework's data loading (as seen in Lesson 102). The HTML then holds `Cart: 2`, but the heading waits too. Nothing reaches Alice until her cart is ready. This is the server-side rendering row of the opening table.
2. **`CartLine` reads the cart through `<Suspense>`**, as our page does. `renderToString` does not wait for it. The HTML holds `Loading cart...`, for Alice and for everyone else.

Our page makes the second choice, and the result surprises most developers. **The server HTML never holds `Cart: 2`.** Here is why:
1. `renderToString` renders `App`, and the heading goes into the HTML.
2. `CartLine` calls `use(getCart())`. The cart is not ready yet, so `CartLine` suspends.
3. `renderToString` does not wait. It finds the closest `<Suspense>` above `CartLine` and puts its fallback into the HTML.
4. Alice sees `Blue Sneakers` and `Loading cart...`.
5. `Cart: 2` appears only after the JavaScript has loaded in the browser. React's docs: "The content will not appear until the client code loads."

The `Loading cart...` in the server HTML came from our own code. It is the fallback written on `<Suspense>` in `App`, and React used it in place of the part that was not ready.

### Server-Side Rendering Sends What Is Ready, Not the Finished Page

**Server-side rendering does not mean the server sends the finished page, data included.** The server sends whatever is ready at that moment. With `renderToString`, a part that still waits goes out as its fallback, and it appears only after the client code loads.

Here is how this mistake ships:
1. A developer renders the product page with `renderToString`.
2. The cart line reads its data through `<Suspense>`.
3. The developer expects `Cart: 2` in the server HTML, but the HTML always holds `Loading cart...`.
4. Search engines and slow phones see the fallback, not the cart.

React's docs recommend the streaming calls of the next principle "When possible", and keep `renderToString` for a server that cannot send streams.

## PRINCIPLE | `renderToReadableStream`: the shell arrives first, and each Suspense part follows in the same response

> [!PRINCIPLE]
> **Principle 3: renderToReadableStream: The Shell Arrives First**
>
> *With streaming server-side rendering, the server sends the shell, the part outside every `<Suspense>` boundary, as soon as it is ready, and sends each waiting part later in the same response, before any JavaScript of ours runs.*
>
> Streaming takes away both waits of server-side rendering in one piece. The heading no longer waits for the slowest data, and the cart no longer waits for the JavaScript, because React on the server sends a small script that swaps the cart in. The boundary decides what goes into the shell, so wrap only the part that is slow.
>
> **DO THIS:**
> ```jsx
> <h1>Blue Sneakers</h1>
> ~<Suspense fallback={<p>Loading cart...</p>}>~ {/* The heading is in the shell; only the cart waits */}
>   <CartLine />
> </Suspense>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~<Suspense fallback={<p>Loading...</p>}>~ {/* **WRONG:** the whole page waits, so the shell is a loading line */}
>   <h1>Blue Sneakers</h1>
>   <CartLine />
> </Suspense>
> ```

You have seen this on many sites. The header and the layout appear at once, a loading line sits where the content goes, and a moment later the content fills in. The server did not send the page in one piece. It sent it in parts, in one response.

Keep the same `App` and the same boundary around the cart line, and change only the call in `server.js`:

```jsx title="The same App, sent in one piece and sent in parts"
const html = ~renderToString~(<App />); // Sends Loading cart..., and stops
const stream = await ~renderToReadableStream~(<App />); // Sends Loading cart..., then Cart: 2 in the same response
```

**It may look the same, but it is NOT the same thing!** Both start by sending the heading and `Loading cart...`. `renderToString` stops there. `renderToReadableStream` keeps the response open, and when Alice's cart is ready on the server, it sends the cart's HTML too.

> [!DEFINITION]
> **What is streaming?** [NEW] Streaming means the server sends the HTML in parts, each part as soon as it is ready, in one response. React's docs: "Streaming allows the user to start seeing the content even before all the data has loaded on the server." `renderToReadableStream`, from `react-dom/server`, is the call that does it. Its name says what it returns: a stream, which the server sends to the browser part by part (Lesson 103).

> [!DEFINITION]
> **What is the shell?** [NEW] The shell is everything outside every `<Suspense>` boundary: the first part the server sends. React's docs: "It determines the earliest loading state that the user may see." On our page, the shell is the heading and the fallback, `Loading cart...` (Lesson 103).

### The Two Small Changes in Our Files

React's streaming examples let `App` return the whole document, from `<html>` down, so that React can send the page from its very first byte. From here on, our `App` does the same:

```jsx title="src/App.jsx"
import { Suspense } from 'react';
import CartLine from './CartLine.jsx';

export default function App() {
  return (
    ~<html>~ {/* The whole document, so React can send it from the first byte */}
      <body>
        <main>
          <h1>Blue Sneakers</h1>
          <Suspense fallback={<p>Loading cart...</p>}>
            <CartLine />
          </Suspense>
        </main>
      </body>
    </html>
  );
}
```

`server.js` streams `App` for each request, and tells React which script runs our code in the browser:

```jsx title="server.js"
import { renderToReadableStream } from 'react-dom/server';
import App from './src/App.jsx';

export async function handler(request) {
  const stream = await ~renderToReadableStream~(<App />, { // Resolves as soon as the shell is ready
    ~bootstrapScripts: ['/main.js']~, // React writes the script tag that loads our bundle
  });
  return new Response(stream, { headers: { 'content-type': 'text/html' } });
}
```

`handler` is the function our server calls for every request. It returns a `Response`, the same kind of object that `fetch` hands you in the browser, here with the stream as its body. With `bootstrapScripts`, we no longer write the script tag by hand. React writes it into the HTML for us, and Principle 6 shows what that script does.

### The Cart Appears Before Any JavaScript of Ours Runs

**Beware! With streaming, `Loading cart...` turns into `Cart: 2` while our bundle is still downloading.** After Principle 2, most developers expect the opposite. Here is what happens, in order:
1. The server sends the shell: `Blue Sneakers` and `Loading cart...`.
2. Alice sees them at once. The bundle is still downloading.
3. On the server, Alice's cart data arrives.
4. React renders `CartLine` and sends its HTML in the same response. In React's docs, it comes "along with an inline `<script>` tag that replaces the loading fallback with that HTML".
5. The browser runs that small script as soon as it arrives, and Alice sees `Cart: 2` in place of `Loading cart...`.
6. The `Add to cart` button is on the screen, but it does nothing until the bundle loads. Principle 6 covers that last step.

### One Suspense Around the Whole Page Turns the Shell into a Loading Line

The shell decides what Alice sees first, so where the boundary sits matters. Compare a boundary around the cart line with a boundary around the whole page:

```jsx title="A boundary around the cart line vs. a boundary around the whole page"
<h1>Blue Sneakers</h1>
~<Suspense fallback={<p>Loading cart...</p>}>~ {/* Only the cart waits: the heading is in the shell */}
  <CartLine />
</Suspense>

~<Suspense fallback={<p>Loading...</p>}>~ {/* **WRONG:** the heading is inside too, so the shell holds only Loading... */}
  <h1>Blue Sneakers</h1>
  <CartLine />
</Suspense>
```

With the boundary around the whole page, the heading waits for the cart. The shell holds only the fallback, and Alice sees a loading line instead of the page:

::: col title="Suspense around the cart line" tone=good
```page size=mini
url: shop.example.com/blue-sneakers
heading: Blue Sneakers | good
line: Loading cart...
```
:::
::: col title="Suspense around the whole page" tone=bad
```page size=mini

line: Loading... | bad
```

React's docs: "seeing a big spinner on the screen can feel slower and more annoying than waiting a bit more and seeing the real layout." Therefore, pay attention to where you put the boundary: around the part that is slow, and nowhere else.

## PRINCIPLE | `prerender`: one file made at build time, the same for every visitor

> [!PRINCIPLE]
> **Principle 4: prerender: One File at Build Time for Every Visitor**
>
> *With static prerendering, `prerender` runs at build time, waits for all data, and makes one HTML file that every visitor receives, so no part of that file can belong to one visitor.*
>
> Static prerendering makes the same page as server-side rendering, at a different moment: once, before anyone visits, instead of at every request. The file can be sent from a CDN at once. But no visitor exists at build time, so a cart rendered into the file is the same cart for everyone, and React prints a hydration error once the browser reads the real cart.
>
> **DO THIS:**
> ```jsx
> const { prelude } = await ~prerender~(<LandingPage />); // The same for every visitor: made once, at build time
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const { prelude } = await ~prerender~(<App />); // **WRONG:** CartLine is read at build time, so every visitor sees the same cart
> ```

Remember the HTML file you wrote by hand? It was ready before anyone visited, and everyone got the same file. Static prerendering is the same idea, except React writes the file for you, from your components.

Now move the call out of the server and into the build. Here are the two calls side by side:

```jsx title="The same App, rendered at request time and at build time"
const stream = await ~renderToReadableStream~(<App />); // server.js: runs again for every visitor's request
const { prelude } = await ~prerender~(<App />); // build.js: runs once, when the team builds the site
```

This pair holds one answer of each kind:
- **The page they make: yes, it is the exact same thing!** Both render the same `App` with the same React, so the heading, the cart line, and the button come out the same.
- **The moment: it may look the same, but it is NOT the same thing!** `renderToReadableStream` runs when Alice's request arrives. `prerender` runs once, at build time, before anyone visits.

Making the HTML at build time is **static prerendering**, also called **static site generation**, or SSG. MDN: "Content of a static site is generated at build time, not at request time."

### The Build File

`prerender` is the call that does it. It comes from a separate part of React, made for builds, and React's docs say it "waits for all data to load before resolving". Here it is in `build.js`:

```jsx title="build.js"
import { mkdir, writeFile } from 'node:fs/promises';
import { prerender } from 'react-dom/static';
import App from './src/App.jsx';

const { ~prelude~ } = await prerender(<App />, { // Waits for all data, then gives back the HTML
  bootstrapScripts: ['/main.js'],
});
await mkdir('dist', { recursive: true }); // Creates the dist folder on the first build
await writeFile('dist/blue-sneakers.html', prelude); // One file, sent to every visitor
```

`prelude` comes from the object that `prerender` returns:
1. `prerender(<App />)` returns a promise.
2. The promise resolves to an object with two fields, `prelude` and `postponed`.
3. `prelude` is the HTML of the page, as a stream. `postponed` is `null` when the page finished, and Principle 5 uses it.

> [!DEFINITION]
> **What is a CDN?** [NEW] A CDN, a content delivery network, is a set of servers in many places that keep copies of the same files close to the visitors. A file made once at build time is usually sent from a CDN, because it is the same file for everyone. MDN: static sites "can be served from a CDN" (Lesson 103).

### VS | One String `renderToString` vs. A Build File `prerender`: the first writes the fallback into the file, while the second waits for the data

For a build, `prerender` and `renderToString` are NOT the same thing. `renderToString` would write the fallback of a waiting part into the file. `prerender` waits for that part, so the file holds the finished page.

### The File Cannot Hold Alice's Cart

**Beware! A file made before anyone visits holds the same cart line for every visitor.** Here is why:
1. `prerender` reaches `CartLine` at build time.
2. There is no visitor yet, so there is no Alice and no cart of hers. `getCart` reads whatever cart exists at build time, here an empty one.
3. The same file goes to Alice and to Bob. MDN: "for any given URL, all users will receive the same content."

::: col title="Alice opens the file" tone=bad
```page size=mini
url: shop.example.com/blue-sneakers
heading: Blue Sneakers
line: Cart: 0 | bad
line: [Add to cart]
```
:::
::: col title="Bob opens the same file" tone=bad
```page size=mini
url: shop.example.com/blue-sneakers
heading: Blue Sneakers
line: Cart: 0 | bad
line: [Add to cart]
```
:::

The page now shows the wrong number. Alice has two items in her cart, and the page says `Cart: 0`. The file says `Cart: 0` to every visitor until the next build.

The wrong number does not even stay quietly on the page. Once the bundle loads, `getCart` in the browser reads Alice's real cart. So `CartLine` renders `Cart: 2`. `hydrateRoot` finds `Cart: 0` in the HTML instead, so React prints a hydration error and makes the cart line again in the browser:

```devconsole width=full caption="The Console after hydrateRoot, when the static file says Cart: 0 and the browser reads Alice's cart."

  - Variable input such as `Date.now()` or `Math.random()` which changes each time it's called.
  - Date formatting in a user's locale which doesn't match the server.
```

### Why This Bug Ships

Here is how this mistake ships:
1. A team prerenders the product page, cart line included.
2. At build time, the cart is read with no visitor.
3. Every visitor receives the same file, with the same cart line, until the next build.
4. Once the bundle loads, the browser reads each visitor's real cart, and React prints a hydration error.

Static prerendering fits the parts of a page that are the same for everyone, such as the heading. A part that belongs to one visitor has two ways onto a static page:
1. The browser renders it after the page has loaded.
2. The server fills it in when the request arrives. Principle 5 shows this way.

### A Static Page Still Answers Clicks

Many developers think a static page is a page without React. It is not. **A static page is React HTML made in advance.** `prerender` takes the same `bootstrapScripts` as the streaming call, so the file carries the script tag for our bundle. In the browser, `main.jsx` calls `hydrateRoot` on it, and the button answers clicks as on any server-rendered page. Principle 6 shows that call.

## PRINCIPLE | `resume`: the build makes the shared part, and the server fills in each visitor's part

> [!PRINCIPLE]
> **Principle 5: resume: The Server Finishes What the Build Left Open**
>
> *With resuming, `prerender` is stopped early with a `signal`; the parts that were not ready stay as their fallbacks in the `prelude`, the rest of the work is saved as `postponed`, and at request time `resume(<App />, postponed)` streams the missing parts for that visitor.*
>
> Resuming puts static prerendering and streaming on one page. The part that is the same for everyone is made once, at build time, and can be sent at once. The part that belongs to one visitor is made when that visitor's request arrives. `resume` runs on the server, so the browser still calls `hydrateRoot` afterwards.
>
> **DO THIS:**
> ```jsx
> await prerender(<App />, { signal: controller.signal, ~bootstrapScripts: ['/main.js']~ }); // build.js: the script tag goes into the prelude
> const stream = await resume(<App />, postponed); // server.js: continues the saved prerender for this visitor
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> await prerender(<App />, { signal: controller.signal });
> const stream = await resume(<App />, postponed, { ~bootstrapScripts: ['/main.js']~ }); // **WRONG:** resume does not accept bootstrapScripts
> ```

Principle 4 left the product page with a problem. The heading can be made in advance, and the cart cannot. Resuming makes each part at its own moment. Here is what Alice sees:

::: row caption="The resumed product page: the heading from a file made before Alice came, then her cart, filled in by the server at request time."
::: col title="The prerendered part arrives" tone=good
```page size=mini
url: shop.example.com/blue-sneakers
heading: Blue Sneakers
line: Loading cart...
```
:::
::: col title="The server fills in her cart" tone=good
```page size=mini
url: shop.example.com/blue-sneakers
heading: Blue Sneakers
line: Cart: 2 | good
line: [Add to cart]
```
:::
:::

`Blue Sneakers` and `Loading cart...` come from a file made before Alice came. A moment later, the server fills in `Cart: 2`, made for her alone. That is Principle 4 and Principle 3 on one page. The part that is the same for everyone is made at build time, and the visitor's part at request time.

### Stopping prerender Works Like Cancelling a fetch

Remember how you cancel a `fetch`? You create an `AbortController` and pass its `signal` to the request. Later you call `controller.abort()`, and the request stops where it is. `prerender` accepts the very same `signal`. When you abort it, React stops the build render where it is. It gives you back the HTML it finished, and an object that describes the work it did not finish.

So the page is made by two calls, in two files. At build time, `build.js` starts `prerender` and stops it before the cart is ready:

```jsx title="build.js"
import { mkdir, writeFile } from 'node:fs/promises';
import { prerender } from 'react-dom/static';
import App from './src/App.jsx';

const controller = new AbortController();
setTimeout(() => ~controller.abort()~); // Stops prerender a moment after it starts: the heading is done, the cart is not

const { prelude, ~postponed~ } = await prerender(<App />, { // postponed holds the work prerender did not finish
  ~signal: controller.signal~, // Lets controller.abort() reach prerender
  bootstrapScripts: ['/main.js'],
});
await mkdir('dist', { recursive: true });
await writeFile('dist/blue-sneakers.html', prelude); // Blue Sneakers and Loading cart...
await writeFile('dist/blue-sneakers.json', JSON.stringify(postponed)); // Saved as JSON text for request time
```

At request time, `server.js` sends that file first, then continues the prerender for this visitor, in the same response:

```jsx title="server.js"
import { readFile } from 'node:fs/promises';
import { resume } from 'react-dom/server';
import App from './src/App.jsx';

export async function handler(request) {
  return new Response(ReadableStream.from(sendPage()), { headers: { 'content-type': 'text/html' } });
}

async function* sendPage() {
  yield await readFile('dist/blue-sneakers.html'); // 1. Sent at once: Blue Sneakers and Loading cart...
  const postponed = JSON.parse(await readFile('dist/blue-sneakers.json', 'utf8'));
  const stream = await ~resume~(<App />, postponed); // 2. Continues the prerender for this visitor: makes Cart: 2
  yield* stream; // 3. Sent next, in the same response
}
```

These two files bring five new names:
- **`AbortController` and `signal`** are the standard way, in the browser and in Node, to tell a running job to stop. The `signal` goes to `prerender`. Then `controller.abort()` tells it to stop where it is.
- **`setTimeout` with no delay** calls `controller.abort()` a moment after `prerender` starts. By then React has rendered the heading, but the cart still waits for its data.
- **`postponed`** is the work `prerender` did not finish. React's docs call it "a JSON-serializeable, opaque object that can be passed to `resume` if `prerender` did not finish". Opaque means we save it and pass it on, but never read inside it.
- **`resume`** is the server call that continues a stopped prerender, at request time, and returns a stream.
- **`sendPage`** is our own helper. The star after the word function makes it a generator. Each `yield` hands over one piece of the response: first the file, then every piece of the stream from `resume`. `ReadableStream.from` turns those pieces into one stream, so Alice receives one page.

When `build.js` runs, the terminal shows `AbortError: This operation was aborted`. React prints why it stopped, because the cart was not finished. Here the stop is planned, so the build still worked: both files are written.

> [!DEFINITION]
> **What is resuming?** [NEW] Resuming means continuing a stopped prerender later, on the server, when a visitor's request arrives. `prerender` stops early and returns `postponed`, and `resume(<App />, postponed)` makes the missing parts for that visitor. React's docs call this way of working Partial Pre-rendering: part of the page is prerendered, and the rest is made per request (Lesson 103).

### VS | Prerender Alone `prerender` vs. Prerender Then Resume `resume`: one file for everyone, while each visitor gets a part filled in

**It may look the same, but it is NOT the same thing!** Both start with the same `prerender` call in `build.js`. With `prerender` alone, the call waits for all data and serves one file, cart line included, to everyone. With a `signal` and then `resume`, everyone gets the same heading from the file, and each visitor's cart is filled in at request time.

### One Page, Made Hours Apart

**The heading was made at build time, and Alice's cart was made when she arrived, maybe hours later. Both reach her in one page.** Here is the whole path, in order:
1. At build time, `prerender` starts. Then `controller.abort()` stops it before `CartLine` has its data.
2. React's docs: "Any Suspense boundaries with incomplete children will be included in the prelude in the fallback state." So the `prelude` holds the heading and the fallback, `Loading cart...`.
3. `prerender` also returns `postponed`. `build.js` saves it in a file. React's docs suggest "e.g. redis, a file, or S3".
4. Alice's request arrives. The server sends the `prelude` file at once.
5. The server loads `postponed` and calls `resume` with it.
6. `resume` "re-renders from the root until it finds a component that was not fully pre-rendered". On our page, it calls `App` again and reaches `CartLine`.
7. Alice's cart is ready, and the stream fills in `Cart: 2`.
8. The bundle loads, `hydrateRoot` runs, and `Add to cart` answers.

```tree dir=right caption="One product page made at two moments: the heading at build time, Alice's cart at request time, and the clicks in the browser."
How the resumed product page is made
- +1. Build time [`prerender` `signal`] | Makes **`Blue Sneakers`** and **`Loading cart...`** | Saves the unfinished work as **`postponed`**
- +2. Request time [`resume`] | Continues from **`postponed`** for this visitor | Streams **`Cart: 2`** in place of the fallback
- +3. In the browser [`hydrateRoot`] | Attaches **our click handler** | **`Add to cart`** answers a tap
```

### Resuming Happens on the Server, Not in the Browser

The word "resume" makes many developers picture the browser picking up where the server stopped, with no hydration. That is not what React does. **`resume` runs on the server and continues the server render**. It comes from React's server package, it returns a stream of HTML, and the browser still loads the bundle and calls `hydrateRoot`. In React's own example, the button says it plainly: "Clicking me requires hydration."

A second mistake follows from the same split. The script tag for the bundle belongs to the first call, not the second:

```jsx title="Where bootstrapScripts goes when you resume"
await prerender(<App />, { signal: controller.signal, ~bootstrapScripts: ['/main.js']~ }); // build.js: the script tag is written here
await resume(<App />, postponed, { ~bootstrapScripts: ['/main.js']~ }); // **WRONG:** resume does not accept bootstrapScripts
```

React's docs list three options that `resume` "does not accept":
- `bootstrapScripts`
- `bootstrapScriptContent`
- `bootstrapModules`

They must go to the `prerender` call that made `postponed`. React prints no warning when they go to `resume`. It ignores them, so the page has no script tag for the bundle, the bundle never loads, and `Add to cart` never answers a tap.

## PRINCIPLE | `hydrateRoot`: in every way that sends HTML, the button answers only after the bundle runs

> [!PRINCIPLE]
> **Principle 6: hydrateRoot: Every Way That Sends HTML Ends Here**
>
> *Every way that sends HTML from a server or a build ends in the browser with `hydrateRoot`, which attaches the event handlers to that HTML; only client-side rendering uses `createRoot`.*
>
> The five ways decide when and where the HTML is made, but HTML has no place for a click handler. The handler arrives with the bundle, and `hydrateRoot` attaches it to the HTML that is already on the page, reusing its nodes. `createRoot` on server HTML throws that HTML away and makes it again.
>
> **DO THIS:**
> ```jsx
> ~hydrateRoot~(document, <App />); // Reuses the prerendered HTML and attaches the click handler
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~createRoot~(document.getElementById('root')).render(<App />); // **WRONG:** #root already holds the server HTML, and React throws it away and makes it again
> ```

Remember `addEventListener`? HTML can carry the look of a button, but a click handler is a JavaScript function. Only JavaScript running in the browser can attach it. That is true whoever made the HTML: the browser, the server, or the build.

Four ways send HTML from a server or a build, and one does not. Here is the one call in `main.jsx` for each:

```jsx title="The one call in main.jsx, for each of the five ways"
~createRoot~(document.getElementById('root')).render(<App />); // Client-side rendering: the HTML arrives empty
~hydrateRoot~(document.getElementById('root'), <App />); // Server-side rendering with renderToString: App fills only #root
~hydrateRoot~(document, <App />); // Streaming, static prerendering, and resuming: App returns the whole document
```

Two answers sit in this block:
- **`createRoot` and `hydrateRoot`: NOT the same thing!** `createRoot` makes the page from nothing. `hydrateRoot` takes HTML that is already on the page and attaches React to it. React's docs say it reuses "the DOM nodes from your HTML instead of destroying and re-creating them".
- **Streaming, static prerendering, and resuming: yes, it is the exact same thing!** All three send HTML that our `App` made, from `<html>` down. So all three call `hydrateRoot` on the whole document. Server-side rendering with `renderToString` calls it on the root, because there `App` fills only the root (as seen in Lesson 102).

The five ways decide when the HTML is made. None of them sends the clicks. The click handler reaches the page only with the bundle.

### What Alice Sees Until the Bundle Runs

**In every way that sends HTML, `Add to cart` is on the screen before it answers a tap.** Alice taps it in the first seconds, and nothing happens. After `hydrateRoot` has run, the same tap changes the line to `Cart: 3`:

::: col title="Alice taps before hydrateRoot runs" tone=bad
```page size=mini

heading: Blue Sneakers
line: Cart: 2 | bad
line: [Add to cart]
```
:::
::: col title="Alice taps after hydrateRoot runs" tone=good
```page size=mini
url: shop.example.com/blue-sneakers
heading: Blue Sneakers
line: Cart: 3 | good
line: [Add to cart]
```
:::
:::

**Many developers think the page is ready because the HTML came from the server.** The HTML is ready. The page answers clicks only after `hydrateRoot` attaches React to it, in every way that sends HTML. This holds for resuming too: `resume` makes more HTML on the server, and the browser still has to hydrate it.

### Where the Script That Runs main.jsx Comes From

In a client-only app, we write the script tag in `index.html` ourselves. In a streamed or prerendered page, nobody writes it by hand. **React writes it, from `bootstrapScripts`:**
1. The server call or the build call receives `bootstrapScripts`, with the address of the bundle built from `main.jsx`.
2. React writes a script tag that loads that bundle into the HTML.
3. The browser loads that script, and the bundle calls `hydrateRoot`.

### Why This Bug Ships

This mistake ships every time a page leaves client-side rendering (as seen in Lesson 102):
1. A team moves the product page from client-side rendering to HTML sent from a server or a build.
2. `main.jsx` still calls `createRoot`.
3. React does not reuse the HTML that arrived. It throws it away and makes the page again in the browser. The page still works, so nobody notices the wasted work.

The other way round fails too. React's docs say that calling `hydrateRoot` on the empty root of a client-only app "is not supported", because there is no HTML to hydrate. React prints a hydration error in the Console: "Hydration failed because the server rendered HTML didn't match the client". Then it makes the whole page in the browser anyway. What hydration does inside, and what it costs, comes next (Lesson 104).

## All 6 Principles Together

### The Complete Resumed Product Page

Resuming uses every piece of this lesson, so here is the complete project in that way. `App` returns the whole document, with the heading in the shell and the cart line inside `<Suspense>`:

```jsx title="src/App.jsx"

import CartLine from './CartLine.jsx';

export default function App() {
  return (
    <html>
      <body>
        <main>
```

`CartLine` reads the visitor's cart and keeps the count that the button changes:

```jsx title="src/CartLine.jsx"
      <button ~onClick~={() => setCount(count + 1)}>Add to cart</button> {/* Principle 6: answers only after hydrateRoot */}

```

`build.js` runs once, at build time:

### The Order in Which Each Part of the Page Is Made

The heading, the cart, and the click handler each reach Alice at their own moment, and React calls the components at each one:

```tree dir=right caption="When React calls App and CartLine in the resumed product page, and what each call makes."
How the resumed product page reaches Alice

- +2. Request time: `resume` [`App` `CartLine`] | React calls `App` again from the root and **reaches `CartLine`** for Alice | The stream fills in **`Cart: 2`**
```

| **Streaming server-side rendering** | On the server, at each request | Parts: the shell, then each `<Suspense>` part | `renderToReadableStream` | `hydrateRoot` on `document` | The heading and `Loading cart...`, then `Cart: 2` | Content per request, with slow data |
| **Static prerendering** | At build time, once | One file, with all data waited for | `prerender` | `hydrateRoot` on `document` | The whole file at once, the same for everyone | A landing page, a blog, documentation |
| **Resuming** | The shared part at build time, the visitor's part at request time | Parts: the `prelude`, then the stream from `resume` | `prerender` with a `signal`, then `resume` | `hydrateRoot` on `document` | The heading from the file, then `Cart: 2` | A page mostly the same for everyone, with a small part per visitor |

One app mixes these ways, one per page. React's docs: "the landing page for your app might benefit from being statically generated", while "a page with a content feed might perform best with server-side rendering". A screen behind a login can stay client-only.

Remember the one sentence of this lesson. **A part that is the same for everyone can be made in advance. A part that belongs to one visitor can only be made when that visitor's request arrives.**

## For the Interview

> **The Interview Question:** How do CSR, SSR, streaming SSR, static prerendering, and resuming differ?

### How to Answer Clearly in 30 Seconds

"All five answer two questions: where and when the HTML is made, and whether it arrives in one piece or in parts.
1. **Client-side rendering** makes the HTML in the browser with `createRoot`, so the user sees a blank page until the JavaScript runs.
2. **Server-side rendering** makes it on the server at each request, in one piece. `renderToString` does not wait for data, so a suspended part goes out as its fallback.
3. **Streaming server-side rendering** with `renderToReadableStream` sends the shell at once and each `<Suspense>` part later in the same response. A small inline script swaps each part in before React loads.
4. **Static prerendering** with `prerender` makes the HTML once at build time and waits for all data. Every visitor gets the same file, often from a CDN.
5. **Resuming** stops `prerender` early and saves `postponed`. At request time, `resume` on the server fills in the per-visitor parts. React calls this Partial Pre-rendering.

Every way that sends HTML still ends with `hydrateRoot` in the browser, and one app picks a way per route. The trade shows up in Time to First Byte, First Contentful Paint, and Largest Contentful Paint."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does resuming replace hydration?"**
   **No.** `resume` is a `react-dom/server` call. It runs on the server, continues a prerender that was stopped at build time, and streams the missing HTML for one visitor. The browser still downloads the bundle and calls `hydrateRoot` before any button answers. React's own resume example shows a button that says "Clicking me requires hydration." Resuming changes when the HTML is made, not how the page becomes interactive.
2. **"Can a statically prerendered page answer clicks?"**
   **Yes.** A static page is React HTML made in advance, not a page without React. `prerender` accepts `bootstrapScripts`, so React writes the script tag for the bundle into the file, and `main.jsx` calls `hydrateRoot` on it. What a static page cannot do is hold data for one visitor, because no visitor exists at build time. MDN: "for any given URL, all users will receive the same content."
3. **"Why does the same `<Suspense>` boundary show `Loading cart...` with `renderToString` and `Cart: 2` with `renderToReadableStream`?"**
   Because `renderToString` returns one string at once. When a component suspends, it puts the fallback into the string and stops, and the real content appears only after the client code loads. `renderToReadableStream` keeps the response open. It sends the shell with the fallback first, then the finished part with a small inline script that swaps it in, without waiting for React in the browser. React's docs recommend the streaming calls "When possible", and keep `renderToString` for servers that do not support streams.
