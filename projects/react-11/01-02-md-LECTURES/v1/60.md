# Lecture 60: When Built-In State Is Not Enough

*(Why does the tab still count two unread emails after the user marks one as read?)*

> INTERVIEW QUESTION | ❱❱ MORE | When does an app outgrow useState and context, and what do external stores and server-cache libraries add?

---

## VS | Data from the Server vs. State Only the Page Knows: the first is only a copy, so keep one copy of it

> A page often fetches a list from the server, such as your emails, and several components need it: one counts the unread emails, another shows them. **When each component fetches the same URL in its own Effect, each one keeps its own copy, and one click changes only one of them.** So the server's data needs one place on the page, a common parent or a cache library such as SWR, while the open tab stays in `useState`.

Think of a train timetable you print from the railway website. The moment the railway changes a departure time, your printout is wrong, and nothing on the paper tells you. Print it twice, write a correction on one sheet, and now you hold two sheets that disagree.

Data from the server works exactly like that printout. Remember fetching in an Effect from Lesson 33? Your component calls `fetch`, and the setter puts the answer into state. That state does not hold the emails. It holds a **copy** of the emails. The real emails stay on the server.

Keep one sentence in mind for the whole lesson: **data from the server is only a copy, so the page must keep exactly one copy of it.**

An email app keeps two kinds of values in `useState`: the emails, and which tab is open. Both are written with the same line of code, so in your head both are simply "state". **It may look the same, but it is NOT the same thing!**
- **The emails belong to the server.** The page only holds a copy. When an email changes on the server, every copy on the page is out of date until our code fetches again.
- **The open tab belongs to the page.** The server never hears about it. The value in state is the real value, and no other copy exists.

Take an inbox like Gmail. At the top, a tab reads `Inbox (2)`: two emails are unread. Below it sit the two emails, each with a **Mark as read** button. The user clicks **Mark as read** on the first email. The button on that row goes away, but the tab still reads `Inbox (2)`. Ask yourself: where does the page keep the emails, and how many times? Twice. The tab fetched them into its own state, to count the unread ones. The list fetched them into its own state, to show the rows.

**Why:** A state variable belongs to the component that calls `useState`. Two components that fetch the same URL get two separate arrays, which only start out equal. The click changed the list's array. No line of code touched the tab's array, so the page now gives **two answers to one question**. The fix is not a second setter call. The fix is one copy.

### Where the One Copy Can Live

There are four places for the one copy of the server's data. Each one fits a bigger app than the one before it:

```tree caption="Four places for the one copy of the server's data, from one component to a whole app."
Where the page keeps its copy of the server's data
- +1. One Effect in the one component that shows it [`useEffect` `fetch`] | Fits **one component** on one screen | Taught in Lesson 33
- +2. One owner: the common parent or a context [`App` holds `emails`] | Fits **a few components** on a small page | Principle 3
- +3. A client-side cache library [`useSWR` `TanStack Query` `RTK Query`] | Fits **many components and screens** that share the same data | Principle 4
- +4. The data fetching built into a framework [`loader`] | Fits an app **built on a framework** | Taught in Lesson 46
```

React's docs recommend the last two. With a framework: "If you use a framework, use its built-in data fetching mechanism." Without one: "Otherwise, consider using or building a client-side cache." A **client-side cache** is a place in the browser, outside every component, where the answers from the server are kept and shared. Principle 4 adds one.

State that only the page knows needs none of this. It stays in the tools you already use:
1. **`useState` in the closest common parent**, when a few components need it (Lesson 24).
2. **A context with `useReducer`**, when many distant components read it and change it (Lesson 29).
3. **An external store**, when the state already lives in code outside React (Lesson 53).

Principle 5 compares them.

### Two Reminders

> [!DEFINITION]
> **What is fetching in an Effect?** [REVIEW] An Effect with an empty dependency list runs once, right after the component appears on the screen. Inside it, `fetch` asks the server for data, and the setter puts the answer into state.
> The cleanup sets an `ignore` flag, so an answer that arrives after the component is gone cannot change the state.
> Something that can be tricky: in development, Strict Mode mounts each component twice, so every Effect runs twice and the server gets the request twice (Lesson 33).

> [!DEFINITION]
> **What is lifting state up?** [REVIEW] When two components need the same state, you take it out of both and move it into their closest common parent.
> The parent holds it with `useState`, and passes it down to the children as props, together with a function that changes it.
> The two children then read one value, so they can never disagree (Lesson 24).

### What the User Pays for Two Copies

Two copies cost the user three things:
1. **Two answers on one page.** The tab says `Inbox (2)` while the list shows one unread email. The user does not know which one to trust.
2. **Waiting again for the same list.** The user leaves the inbox for `Sent`, comes back, and waits on `Loading...` for a list they saw a moment ago.
3. **The same request twice.** When the page loads, the server gets one request for each component that fetches, and twice as many in development.

Developers usually go wrong in four ways, and the principles fix them one by one:
1. They reach for a library such as Redux first, and put the server's emails into it. The store then holds one more copy, and that copy can still drift away from the server.
2. They move the fetch into a custom Hook such as `useData(url)`, and expect the tab and the list to share the emails. Each call to the Hook keeps its own state, so the two copies stay (Lesson 39).
3. They treat a cache library as a place for any state. It holds only answers from the server, one for each URL.
4. They put the text of a form or a ticked checkbox into a store the whole app shares. React's docs advise against it, as Principle 5 shows.

### The Rule of Thumb: who owns the real value?

**Ask one question about every value that several components share: who owns the real value? If the server owns it, keep one copy, in the common parent or in a cache. If only the page knows it, keep it in `useState`, `useReducer`, or context.**

## SECTION | An Inbox with Two Tabs

Our page is a small inbox. Two tab buttons sit at the top, `Inbox (2)` and `Sent`. While `Inbox` is open, the page lists two emails, and each unread email has a **Mark as read** button. While `Sent` is open, the page shows one line, `No sent emails`.

```page caption="The inbox when the page opens: two tabs, and two unread emails with a Mark as read button each."
line: [Inbox (2)] [Sent]
line: Get your next month for $0.99 [Mark as read]
line: Lunch at 12? [Mark as read]
console: quiet
```

The server answers two requests. Here they are as two `fetch` calls:

```js title="The two requests the server answers"
~fetch('/api/emails')~; // A GET request: the server answers with the list of emails as JSON
fetch('/api/emails/1/read', ~{ method: 'POST' }~); // A POST request: the server marks email 1 as read
```

The list arrives as JSON. Each email has an id, a title, and a `read` field:

```json title="The answer to the GET request"
[
  { "id": 1, "title": "Get your next month for $0.99", "read": false },
  { "id": 2, "title": "Lunch at 12?", "read": false }
]
```

Two details of this code are new:
- **The `method` option.** `{ method: 'POST' }` tells `fetch` to send a POST request instead of the usual GET. A POST asks the server to change something.
- **The `read` field.** It comes from the server, inside the JSON. Our code did not create it. The value `false` means unread.

Our project starts with five files. `App` holds `folder`, the open tab. It shows the tabs on top. Below them, it shows either the list or the line `No sent emails`. `FolderTabs` reads the emails to count the unread ones, and `InboxList` reads them to show the rows. Neither one sits inside the other: both are children of `App`.

```files title="inbox: File Explorer" caption="How the files of our inbox sit inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` and mounts it inside `<StrictMode>`
  App.jsx | parent | Holds `folder` and shows `FolderTabs`, then `InboxList` or `No sent emails`
  components/
    FolderTabs.jsx | child | Shows the two tabs and counts the unread emails
    InboxList.jsx | child | Shows one row for each email, with a `Mark as read` button
```

From Principle 4 on, a sixth file joins them: the fetcher.

**PRINCIPLES:** Data from the server is only a copy, so the page must keep exactly one copy of it. Five principles follow:
1. **Principle 1: Two Effects Keep Two Copies.** The tab and the list each fetch the emails, so **Mark as read** changes only the list's copy, and the tab still counts two.
2. **Principle 2: A New Mount Fetches Again.** When the user leaves `Inbox`, React throws away the list's copy. Coming back shows `Loading...` and sends the same request again.
3. **Principle 3: One Owner in `App` Keeps One Copy.** `App` fetches once and passes the emails down, so the tab and the list read the same copy. This fits a small page.
4. **Principle 4: A Cache Library Shares One Answer for Each URL.** SWR keeps the answer outside every component. Every component that asks for the same URL reads it, from one request.
5. **Principle 5: State Only the Page Knows Stays in React First.** The ticked emails stay in `useState`. An external store fits only when many distant components read small parts of it, or when the state lives outside React.

## PRINCIPLE | `fetch` in two Effects: each component keeps its own copy of the emails

> [!PRINCIPLE]
> **Principle 1: Two Effects, Two Copies: Each Component That Fetches Keeps Its Own Copy**
>
> *When two components fetch the same data in their own Effects, each one keeps its own copy in its own state, and a change to one copy never reaches the other.*
>
> The emails belong to the server, and every state that holds them is a copy. When the tab and the list each fetch the emails, the page holds two copies that only started out equal. **Mark as read** changes the list's copy, and nothing changes the tab's copy, so the tab still reads `Inbox (2)`. The Console shows no error, because every line did its job.
>
> **DO THIS:**
> ```jsx
> export default function App() {
>   const [emails, setEmails] = useState(null);
>   return (
>     <>
>       <FolderTabs ~emails={emails}~ /> {/* App holds the one copy: the tab reads it */}
>       <InboxList ~emails={emails}~ /> {/* The list reads the same copy */}
>     </>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function FolderTabs() {
>   const [emails, setEmails] = useState([]);
>   useEffect(() => { ~fetch('/api/emails')~.then(r => r.json()).then(setEmails); }, []); // **WRONG:** a second copy that Mark as read in the list never changes
> }
> ```

### The Smallest Version: Two Components, One URL

Here is the problem in its smallest form. Two components fetch the same URL, and each one puts the answer into its own state. This sketch leaves out the markup and the `ignore` flag:

```jsx title="Two components that fetch the same URL"
function FolderTabs() {
  const [~emails~, setEmails] = useState([]); // Copy 1 of the emails lives in FolderTabs
  useEffect(() => { fetch('/api/emails').then(r => r.json()).then(setEmails); }, []);
}

function InboxList() {
  const [~emails~, setEmails] = useState(null); // Copy 2 of the emails lives in InboxList
  useEffect(() => { fetch('/api/emails').then(r => r.json()).then(setEmails); }, []);
}
```

The two `fetch` lines are identical, and once the answers arrive, both states hold the same two emails. **It may look the same, or work the same at first, but it is NOT the same thing!** Each `then` puts the answer into a different state. The page now holds two arrays, and nothing ties them together.

React's docs call this duplication in state: "When the same data is duplicated between multiple state variables, or within nested objects, it is difficult to keep them in sync."

```tree caption="The same fetch line in two components fills two separate states, so the page keeps two copies."
Two components fetch the emails URL
- !`FolderTabs` [`fetch` `useState`] | Puts the answer into **its own `emails`** | Copy 1: used to **count the unread emails**
- !`InboxList` [`fetch` `useState`] | Puts the answer into **its own `emails`** | Copy 2: used to **show the rows**
```

### The Inbox with Two Effects

Now the real files. `App` holds the open tab, and shows the two components:

```jsx title="src/App.jsx" startLine="1"
import { useState } from 'react';
import FolderTabs from './components/FolderTabs.jsx';
import InboxList from './components/InboxList.jsx';

export default function App() {
  const [~folder~, setFolder] = useState('inbox'); // The open tab: state that only the page knows
  return (
    <>
      <FolderTabs onFolderChange={setFolder} />
      {folder === 'inbox' ? <InboxList /> : <p>No sent emails</p>}
    </>
  );
}
```

`App` passes its setter down to the tab as the callback prop `onFolderChange` (Lesson 23). When the user clicks a tab, the tab calls it with the string of that tab, inbox or sent.

The tab fetches the emails in its own Effect. While it renders, it counts the unread ones with `filter` (Lesson 22):

```jsx title="src/components/FolderTabs.jsx" startLine="1"
import { useState, useEffect } from 'react';

export default function FolderTabs({ onFolderChange }) {
  const [~emails~, setEmails] = useState([]); // Copy 1: the tab's own emails

  useEffect(() => {
    let ignore = false;
    fetch('/api/emails')
      .then(response => response.json())
      .then(json => {
        if (!ignore) setEmails(json);
      });
    return () => { ignore = true; };
  }, []);

  const ~unread~ = emails.filter(email => !email.read).length; // Counts the emails whose read field is false
  return (
    <div>
      <button onClick={() => onFolderChange('inbox')}>Inbox ({unread})</button>
      <button onClick={() => onFolderChange('sent')}>Sent</button>
    </div>
  );
}
```

The list fetches the same URL in its own Effect, and shows `Loading...` until the answer arrives:

```jsx title="src/components/InboxList.jsx" startLine="1"
import { useState, useEffect } from 'react';

export default function InboxList() {
  const [~emails~, setEmails] = useState(null); // Copy 2: the list's own emails

  useEffect(() => {
    let ignore = false;
    fetch('/api/emails')
      .then(response => response.json())
      .then(json => {
        if (!ignore) setEmails(json);
      });
    return () => { ignore = true; };
  }, []);
```

Below the Effect, the click handler tells the server, and then changes the list's own copy. The spread builds a new object with every field of `email`, and with `read` set to true (Lesson 19):

```jsx title="src/components/InboxList.jsx" startLine="16"
  function handleMarkAsRead(id) {
    ~fetch('/api/emails/' + id + '/read', { method: 'POST' })~; // Tells the server the email is read
    ~setEmails~(emails.map(email => // **WRONG:** changes only the list's copy; the tab's copy keeps two unread emails
      email.id === id ? { ...email, read: true } : email
    ));
  }

  if (emails === null) return <p>Loading...</p>;
  return (
    <ul>
      {emails.map(email => (
        <li key={email.id}>
          {email.title}
          {!email.read && (
            <button onClick={() => handleMarkAsRead(email.id)}>Mark as read</button>
          )}
        </li>
      ))}
    </ul>
  );
}
```

### Why the Tab Stays on `Inbox (2)`

When the page opens, the tab and the list show the same two unread emails. Then the user clicks **Mark as read** on the first email:

**The click reached the server and the list, but not the tab.** The Console stays quiet, because no line of code failed. Here is what happens, in order:
1. The page loads. React mounts `FolderTabs` and `InboxList`, and each Effect sends the GET request. The Network tab shows two requests. In development it shows four, because Strict Mode mounts each component twice (Lesson 47).
2. Each answer arrives and goes into its own state. The tab reads `Inbox (2)`, and the list shows two rows.
3. The user clicks **Mark as read** on the first email.
4. `handleMarkAsRead` sends the POST request for email 1. Then it calls the list's own `setEmails`, with that email marked as read.
5. React re-renders `InboxList`, and the button on the first row goes away.
6. No code calls the setter of `FolderTabs`. Its copy still holds two unread emails, so the tab still reads `Inbox (2)`.

The server knows the first email is read. The list knows it too. The tab does not. If the user reloads the page, both components fetch again, both copies agree again, and the tab reads `Inbox (1)`. Until the reload, the page gives two answers.

```tree dir=right caption="One click on Mark as read changes the server and the list, while the tab keeps its old copy."
What one click on Mark as read reaches
- +The server [`POST`] | Marks the first email **as read**
- +The list's copy [`setEmails` in `InboxList`] | The first row **loses its button**
- !The tab's copy [`emails` in `FolderTabs`] | **Nothing changes it** | The tab **still counts two**
```

### How This Bug Usually Grows

Nobody writes two copies on purpose. It happens in small steps:
1. A developer builds the list first, with its own Effect.
2. Later, a teammate adds the unread count to the tab, and copies the same Effect into `FolderTabs`.
3. On the first day, the tab and the list show the same numbers.
4. The first time a user marks an email as read, the count stays the same.
5. The developer passes one more function from the tab to the list to patch it, and the next screen that shows the emails needs the same patch again.

So the fix is not one more `setEmails` call. The fix is **one copy**. Principle 3 gives the emails one owner, and Principle 4 hands them to a cache.

## PRINCIPLE | `useState` in `InboxList`: the copy is thrown away on unmount, and the next mount fetches again

> [!PRINCIPLE]
> **Principle 2: A New Mount Fetches Again: State Ends When Its Component Unmounts**
>
> *A component that fetches in an Effect fetches again every time it mounts, because its state starts fresh, so the user waits again for data the page showed a moment ago.*
>
> When the user clicks `Sent`, React unmounts `InboxList` and throws away its `emails` state, and the copy goes with it. When the user clicks `Inbox`, a brand-new `InboxList` starts with `emails` set to `null`, shows `Loading...`, and sends the same request again. React does not keep the answer for us. To show the list at once, keep the copy in a component that stays on the page, or in a cache.
>
> **DO THIS:**
> ```jsx
> {folder === 'inbox'
>   ? <InboxList ~emails={emails}~ /> // App holds the copy and stays on the page: the list appears at once
>   : <p>No sent emails</p>}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function InboxList() {
>   const [emails, setEmails] = ~useState(null)~; // **WRONG:** React throws this copy away on every tab change, so Loading... shows again
> }
> ```

### A Component Shown Again Starts Fresh

`App` shows the list only while the `Inbox` tab is open:

```jsx title="The line in App that shows or hides the list"
{folder === 'inbox' ? ~<InboxList />~ : <p>No sent emails</p>} {/* While Sent is open, InboxList is not on the page */}
```

Remember Lesson 25? When a component stops being shown, React throws away its state. When it is shown again, it starts from the beginning, with the starting value of `useState`. For `InboxList`, the copy of the emails is its state, so the copy goes away with it.

To the user, coming back to `Inbox` feels like a return to a list they have already seen. To React, the first visit and the second one are **the exact same thing**: both are a fresh mount. The state starts as `null` again, the page shows `Loading...`, and the Effect sends a new request. React keeps no answer from the first visit, and nothing else on this page keeps it either.

Here is what happens, in order:
1. The user clicks `Sent`. The setter re-renders `App`, which now returns the `No sent emails` line instead of the list.
2. React unmounts `InboxList`. Its Effect's cleanup runs, and React throws away its `emails` state.
3. The user clicks `Inbox`. React mounts a brand-new `InboxList`, and its state starts as `null`.
4. The page shows `Loading...`, and the new Effect sends the GET request again. The Network tab shows one new request, and two in development.
5. The answer arrives. The server already knows that the first email is read, so the first row comes back without its button.
6. The tab still reads `Inbox (2)`. `FolderTabs` never unmounted, so it never fetched again.

No line in `App` asks for the second request. It comes from the Effect in the new `InboxList`, which runs on every mount, as every Effect with an empty dependency list does (Lesson 32). React's docs say: "Fetching directly in Effects usually means you don't preload or cache data. For example, if the component unmounts and then mounts again, it would have to fetch the data again."

### What a Cache Would Keep

The missing piece is a **cache**. In everyday English, a cache is a supply put away for later. Hikers, for example, leave food along a trail so they do not have to carry it. In code, a cache keeps an answer from the server, so the page can show it again without waiting for the server. React's docs describe what the user gains: "the user pressing the Back button won't have to wait for some data to load again because it will be cached."

```tree caption="Where the copy of the emails lives decides what the user sees when the Inbox tab opens again."
What the user sees after Sent, then Inbox
- !The copy lives in `InboxList` [`emails` in `InboxList`] | The copy is **thrown away** on unmount | The user waits on **Loading** and the server gets **a new request**
- +The copy lives somewhere that stays | The copy **survives** while `InboxList` is gone | The list appears **at once**
```

A common first fix solves only half of the problem. A developer sees `Loading...` flash on every tab change, and moves only the list's emails up into `App`, which stays on the page. `Loading...` is gone. But `App` now holds one copy, and `FolderTabs` still holds its own, so the tab still disagrees after **Mark as read**. The real fix moves both copies into one place, and Principle 3 does exactly that.

## PRINCIPLE | `useState` in `App`: the tab and the list read one copy

> [!PRINCIPLE]
> **Principle 3: One Owner in the Common Parent: Fetch Once and Pass the Copy Down**
>
> *To give several components one copy of data from the server with React alone, fetch it once in their closest common parent, and pass the data and a function that changes it down through props or context.*
>
> Fetching the data and owning it are two separate jobs. When `App` fetches the emails and passes them to the tab and the list, the page holds one copy, its single source of truth. One `setEmails` call in `App` changes the tab and the list in the same render. The list also appears at once when the user comes back to `Inbox`, because `App` never unmounts. The cost grows with the app: the owner writes the loading, error, and `ignore` code again for every new piece of data from the server.
>
> **DO THIS:**
> ```jsx
> const [emails, setEmails] = useState(null);
> <FolderTabs ~emails={emails}~ /> {/* App holds the one copy: the tab reads it */}
> <InboxList emails={emails} onMarkAsRead={handleMarkAsRead} /> {/* The list reads it and asks App to change it */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [emails, setEmails] = useState(null);
> <FolderTabs emails={emails} />
> ~<InboxList />~ {/* **WRONG:** the list still fetches in its own Effect and keeps a second copy */}
> ```

### Fetching the Data vs. Owning It

Fetching the data and owning it are two separate jobs. One component can fetch the data and keep it, and the others can read it from that one component. You already know this move: lifting state up (Lesson 24). React's docs: "Instead of duplicating shared state between components, *lift it up* to their common shared parent, and *pass it down* to the children that need it."

Here is the smallest version. `App` fetches once, and passes the same `emails` to both children:

```jsx title="One fetch in App, one copy for both children"
const [~emails~, setEmails] = useState(null); // The only copy of the emails, held by App

<FolderTabs emails={emails} /> {/* The tab reads App's copy */}
<InboxList emails={emails} /> {/* The list reads the same copy */}
```

React's docs call this a **single source of truth**: each piece of state has one owner. Here, the owner of the page's copy of the emails is `App`.

Compare it with Principle 1. Both versions fetch the same URL, and both show the same screen when the page loads. **It may look the same, or work the same at first, but it is NOT the same thing!** Two Effects keep two copies. One Effect in `App` keeps one copy, so one `setEmails` call changes the tab and the list together.

```tree caption="Two Effects in two children vs. one Effect in their common parent."
Who fetches the emails
- !Each child fetches them [`FolderTabs` and `InboxList`] | **Two copies** in two states | One click changes **one copy**, so the tab and the list **disagree**
- +`App` fetches them once [`App` passes `emails` down] | **One copy** in `App` | One click changes **the one copy**, so the tab and the list **agree**
```

### Moving the Effect and the Click Handler into `App`

`App` takes the Effect and `handleMarkAsRead` from the list:

```jsx title="src/App.jsx" startLine="1"
import { useState, useEffect } from 'react';
import FolderTabs from './components/FolderTabs.jsx';
import InboxList from './components/InboxList.jsx';

export default function App() {
  const [folder, setFolder] = useState('inbox');
  const [~emails~, setEmails] = useState(null); // The one copy of the emails

  useEffect(() => {
    let ignore = false;
    fetch('/api/emails')
      .then(response => response.json())
      .then(json => {
        if (!ignore) setEmails(json);
      });
    return () => { ignore = true; };
  }, []);

  function handleMarkAsRead(id) {
    fetch('/api/emails/' + id + '/read', { method: 'POST' });
    ~setEmails~(emails.map(email => // Changes the one copy: the tab and the list both re-render
      email.id === id ? { ...email, read: true } : email
    ));
  }
```

Below the handler, `App` passes `emails` to both children. It passes `handleMarkAsRead` to the list as the callback prop `onMarkAsRead`:

```jsx title="src/App.jsx" startLine="26"
  return (
    <>
      <FolderTabs ~emails={emails}~ onFolderChange={setFolder} /> {/* The tab reads App's copy */}
      {folder === 'inbox'
        ? <InboxList ~emails={emails}~ onMarkAsRead={handleMarkAsRead} /> // The list reads the same copy
        : <p>No sent emails</p>}
    </>
  );
}
```

The two children lose their Effects. The tab now reads `emails` from its props. Until the first answer arrives, the emails are still `null`. So the tab counts zero and reads `Inbox (0)`, just as it did in Principle 1 before its own answer arrived:

```jsx title="src/components/FolderTabs.jsx" startLine="1"
export default function FolderTabs({ ~emails~, onFolderChange }) { // emails now comes from App
  const unread = emails === null ? 0 : emails.filter(email => !email.read).length;
  return (
    <div>
      <button onClick={() => onFolderChange('inbox')}>Inbox ({unread})</button>
      <button onClick={() => onFolderChange('sent')}>Sent</button>
    </div>
  );
}
```

The list reads `emails` from its props too, and calls `onMarkAsRead` when the user clicks the button:

```jsx title="src/components/InboxList.jsx" startLine="1"
export default function InboxList({ emails, onMarkAsRead }) {
  if (emails === null) return <p>Loading...</p>;
  return (
    <ul>
      {emails.map(email => (
        <li key={email.id}>
          {email.title}
          {!email.read && (
            <button onClick={() => ~onMarkAsRead(email.id)~}>Mark as read</button> // Asks App to change the one copy
          )}
        </li>
      ))}
    </ul>
  );
}
```

### The Tab and the List Now Give One Answer

Now one click changes the one copy, and both components show the change in the same render:
1. The user clicks **Mark as read** on the first email. The list calls its `onMarkAsRead` prop with the id 1, and that prop is the handler in `App`.
2. `handleMarkAsRead` sends the POST request, and sets the emails in `App`.
3. React re-renders `App`, and with it both children. Both receive the same new array.
4. The tab reads `Inbox (1)`, and the first row loses its button.

This fixes Principle 2 too. When the user comes back from `Sent`, React mounts a new `InboxList`, and it receives the emails from the parent at once. `App` never unmounted, so its copy survived. The page shows no `Loading...`, and the Network tab shows no new request. When the page loads, the Network tab shows one GET request, and two in development.

### VS | Props vs. a Context for the One Copy: both carry the same one copy

The tab and the list are direct children of `App`, so props reach them in one step. On a bigger page, the components that need the emails sit deep below `App`. Then `App` can put the emails in a context instead (Lesson 28).

For the copy, **yes, it is the exact same thing!** Both ways keep one copy in the state of `App`. A context only saves passing the props through every component in the middle. It also re-renders every component that reads it whenever its value changes (Lesson 59). For a small page, React's docs say: "In smaller apps, this is not a problem."

### What One Owner Still Leaves to Our Code

One owner fits a small page well. Here is what happens as the app grows:
1. A sidebar shows the newest email, a search page shows matching emails, and a settings page shows the signature.
2. Each one needs data from the server. So each new piece goes into `App`, or into one big context, and each one needs its own loading line, error line, and `ignore` flag.
3. `App` now fetches data for screens the user has not opened.
4. Every change to that one big context re-renders every component that reads it.
5. When the emails change on another device, the page shows the old copy until our own code fetches again.

React's docs name what this owner code is turning into. When you write all of it yourself, you are "building a client-side cache", "in which case you would use Effects under the hood, but add logic for deduplicating requests, caching responses, and avoiding network waterfalls."

In plain words, that means three jobs:
1. Send one request when several components ask for the same data.
2. Keep the answers.
3. Start fetches early, instead of one after another (Lesson 46).

That is the moment when a team reaches for a library.

## PRINCIPLE | `useSWR`: every component that asks for the same URL reads one cached answer

> [!PRINCIPLE]
> **Principle 4: A Client-Side Cache Library: Every Component Reads One Answer for Each URL**
>
> *A client-side cache library keeps one answer for each URL outside the components, sends one request for every component that asks for it, and fetches it again for all of them after a change.*
>
> A custom Hook such as `useData(url)` shares the code, so each call keeps its own copy. A data fetching library such as SWR shares the data. Every `useSWR` call with the emails URL reads the same cached answer, so the tab and the list cannot disagree. After the POST, `mutate` with the same URL fetches it again and updates every component that uses it. A component that mounts again shows the cached answer at once. React's docs recommend such a library, or a framework's own data fetching, over fetching in Effects.
>
> **DO THIS:**
> ```jsx
> const { data: emails } = ~useSWR('/api/emails', fetcher)~; // Reads the one cached answer for this URL
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const { data } = useSWR('/api/emails', fetcher);
> const [emails, setEmails] = ~useState(data)~; // **WRONG:** a second copy that never changes when the cache changes
> ```

### A Hook Called with a URL

React's docs sketch what a data fetching library looks like from inside a component. It is a Hook that you call with a URL, and it gives back the data:

```jsx title="React's docs sketch of a data fetching library"
const todos = ~useSomeDataLibrary~(`/api/user/${userId}/todos`); // A Hook from a library, called with the URL
```

For an app without a framework, React's docs say: "the best approach is to use a solution that deduplicates requests and caches their responses between components." Here is each part of that sentence, in plain words.

> [!DEFINITION]
> **What is a client-side cache?** [NEW] A client-side cache is a place in the browser where the answers from the server are kept and shared between components.
> Think of it as one JavaScript object outside every component: the URL is the key, and the answer from the server is the value.
> It lives outside every component, so no unmount throws it away. Every component that asks for the same URL reads the same entry (Lesson 60).

- **To deduplicate requests** means to send one request when several components ask for the same data at the same time.
- **A data fetching library** does both jobs for you. React's docs: "Purpose-built data fetching libraries do the hard work of fetching and caching the data for you." They name TanStack Query, SWR, and RTK Query, and Apollo and Relay for a GraphQL API.

This lesson uses SWR, because its Hook has exactly the shape of the sketch: a URL in, the data out. The name SWR comes from stale-while-revalidate: show the stored answer first, then ask the server again.

### VS | `useData(url)` vs. `useSWR(url, fetcher)`: the first shares the code, the second shares the data

Remember the custom Hook `useData(url)` from Lesson 39? It also takes a URL and gives back the data. Compare the two Hooks, each called the same way in both components:

```jsx title="A custom Hook with an Effect inside, called in both components"
const emails = ~useData('/api/emails')~; // In FolderTabs: runs its own Effect into its own state
const emails = ~useData('/api/emails')~; // In InboxList: a second Effect, a second state, a second copy
```

```jsx title="The SWR Hook, called in both components"
const { data: emails } = ~useSWR('/api/emails', fetcher)~; // In FolderTabs: reads the cached answer for this URL
const { data: emails } = ~useSWR('/api/emails', fetcher)~; // In InboxList: reads the same cached answer
```

Both are a Hook called with a URL that gives back the emails, so you easily expect them to do the same job. **They may look the same, but they are NOT the same thing!**
- **A custom Hook shares the code.** Each call runs its own Effect into its own state, so the two copies of Principle 1 come back.
- **A client-side cache shares the data.** Every `useSWR` call with the same URL reads the same answer.

```tree caption="A custom Hook shares the code of the fetch, while a client-side cache shares the answer itself."
Two Hooks called with the emails URL in two components
- !A custom Hook [`useData`] | Shares the **code**: each call has **its own state** | **Two copies** and **two requests**, as in Principle 1
- +A client-side cache [`useSWR`] | Shares the **data**: one answer **for each URL** | **One copy** and **one request** for both components
```

### Handing the Emails to SWR

First, install the library from the project folder:

```bash title="Terminal"
npm install swr
```

SWR does not fetch by itself. It calls a function that we give it, the fetcher, with the URL. Ours is one line of `fetch`, in its own file, so both components can import it:

```js title="src/fetcher.js" startLine="1"
export const ~fetcher~ = url => fetch(url).then(response => response.json()); // SWR calls it with the URL and caches what it returns
```

`App` loses the Effect, the emails state, and the click handler. It keeps only `folder`, the state that only the page knows:

```jsx title="src/App.jsx" startLine="1"
import { useState } from 'react';
import FolderTabs from './components/FolderTabs.jsx';
import InboxList from './components/InboxList.jsx';

export default function App() {

    </>

```

The tab asks SWR for the emails URL. `useSWR` is a Hook from the SWR library, not from React. It gives back an object. Its `data` field holds the answer from the server, or `undefined` until the first answer arrives:

```jsx title="src/components/FolderTabs.jsx" startLine="1"
import useSWR from 'swr';
import { fetcher } from '../fetcher.js';

export default function FolderTabs({ onFolderChange }) {
  const { ~data: emails = []~ } = useSWR('/api/emails', fetcher); // Renames data to emails, and uses [] while it is undefined
  const unread = emails.filter(email => !email.read).length;
  return (
    <div>
      <button onClick={() => onFolderChange('inbox')}>Inbox ({unread})</button>
      <button onClick={() => onFolderChange('sent')}>Sent</button>
    </div>
  );
}
```

The list asks SWR for the same URL. After the POST reaches the server, the list calls `mutate`, a second function from SWR. `mutate` fetches that URL again, and updates every component that uses it:

```jsx title="src/components/InboxList.jsx" startLine="1"
import useSWR, { mutate } from 'swr';
import { fetcher } from '../fetcher.js';

export default function InboxList() {
  const { data: emails } = ~useSWR('/api/emails', fetcher)~; // The same URL as the tab: the same cached answer

  function handleMarkAsRead(id) {
    fetch('/api/emails/' + id + '/read', { method: 'POST' })
      .then(() => ~mutate('/api/emails')~); // After the server marks it read, fetch the URL again for every component
  }

  if (!emails) return <p>Loading...</p>;
  return (
    <ul>
      {emails.map(email => (
        <li key={email.id}>
          {email.title}
          {!email.read && (
            <button onClick={() => handleMarkAsRead(email.id)}>Mark as read</button>
          )}
        </li>
      ))}
    </ul>
  );
}
```

Look at `handleMarkAsRead`. It has no `setEmails`, and no prop reaches the tab. The tab still updates, because SWR keeps the cache outside every component. The URL is also the name of the cached answer. Two calls with the same string read one answer, and when that answer changes, SWR re-renders every component that reads it.

### One Request, One Copy, and No Wait on the Way Back

The page now behaves the way the user expects:
1. The page loads. The tab and the list both call `useSWR` with the emails URL.
2. SWR sends one GET request for both. The Network tab shows one request, in development too.
3. The user clicks **Mark as read**. The POST reaches the server, and `mutate` asks SWR to fetch the URL again.
4. The new answer goes into the cache, and both components re-render. The tab reads `Inbox (1)`, and the first row loses its button.
5. The user clicks `Sent`, then `Inbox`. The new `InboxList` gets the cached emails at once, with no `Loading...`. SWR may also ask the server again in the background, and if anything changed, the list updates.

There is one small difference from Principle 3. Here the page waits for the server: the button stays on the row for a moment after the click, until the new answer arrives. Showing the change before the server answers belongs to another lesson (Lesson 44).

### VS | One Owner in `App` vs. a Cache Library: both keep one copy, only the library writes the code around it

Once the new answer has arrived, the screen is the same as in Principle 3: both ways keep one copy. The difference is where the copy lives, and who writes the code around it:
- **With one owner,** the copy lives in the state of `App`. `App` passes it down as props, and our code writes the loading, error, and `ignore` code for every new piece of data.
- **With a cache library,** the copy lives in the library's cache, outside every component. Each component asks for the URL it needs, and the library does the fetching, the sharing, and the fetching again.

React's docs list what these libraries handle: "deduplicating requests, caching responses, and avoiding network waterfalls." They "can also be integrated into routing loaders for faster pre-fetching", which starts the fetch before the page renders (Lesson 46).

TanStack Query and RTK Query do the same job with their own code. Apollo and Relay do it for a GraphQL API. Whichever one a team picks, the rule is the same: **a cache library holds answers from the server.** It is not a place for the open tab.

### How a Team Breaks the Cache

A team can still bring back two copies. Here is the usual way:
1. A team adds a data fetching library for the emails.
2. They copy the answer from `useSWR` into a `useState` in the component, "to be able to change it".
3. The copy in `useState` does not change when the cache changes.
4. The tab and the list drift apart again, as in Principle 1.

The answer from `useSWR` is the copy. Read it directly, and change it through the server and `mutate`.

## PRINCIPLE | `useState` for the ticked emails: state that only the page knows stays in React first

> [!PRINCIPLE]
> **Principle 5: State That Only the Page Knows: Keep It in React's Own State First**
>
> *Once the data from the server lives in a cache, keep the state that only the page knows in `useState`, `useReducer`, and context, and move it to an external store only when that pays off.*
>
> The open tab and the ticked emails belong to the page, not to the server. They stay in `useState` in the closest common parent, or in a context with a reducer when many distant components read and change them. An external store holds state outside React. Through `useSyncExternalStore`, each component re-renders only when its own snapshot changes by `Object.is`, while every context reader re-renders on a new value. That helps when many components read small parts of state that changes often, or when the state already lives in code outside React. React's docs recommend the built-in tools first.
>
> **DO THIS:**
> ```jsx
> const [~selectedIds~, setSelectedIds] = useState([]); // State that only the page knows stays in App
> const { data: emails } = useSWR('/api/emails', fetcher);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> let emails = [];
> let selectedIds = [];
> export const inboxStore = {
>   ~loadEmails~() { // **WRONG:** a hand-made copy of the server's data inside a global store
>     fetch('/api/emails').then(r => r.json()).then(json => { emails = json; });
>   },
> };
> ```

### What Is Left Once the Emails Live in a Cache

Now the page gets a checkbox on each row, and a line above the list that says how many rows are ticked, such as `1 selected`. Gmail has the same checkboxes, so the user can move or delete several emails at once.

After Principle 4, `App` holds only `folder`. The ticked emails are one more piece of state. Like the open tab, they belong to the page: the server never stores which rows the user ticked. So the ticked emails stay where the open tab is, in `useState` in `App`:

```jsx title="The ticked emails in App"
const [~selectedIds~, setSelectedIds] = useState([]); // The ids of the ticked emails: state that only the page knows
```

What would a global store add here? More code, and nothing the user can see. React's docs say it plainly: "Prefer local state and don't lift state up any further than necessary. For example, don't keep transient state like forms and whether an item is hovered at the top of your tree or in a global state library."

**Transient state** is the docs' name for state that lasts only while the user works on something. Examples are the text in a form, or whether the pointer is over an item. The ticked rows are the same kind of state. They matter only until the user moves or deletes the emails.

### A Checkbox on Each Row

`App` adds a handler that ticks or unticks one id. It passes `selectedIds` and the handler down to the list:

```jsx title="src/App.jsx" startLine="5"
export default function App() {
  const [folder, setFolder] = useState('inbox');
  const [selectedIds, setSelectedIds] = useState([]);

  function handleToggle(id) {
    setSelectedIds(selectedIds.includes(id)
      ? selectedIds.filter(selectedId => selectedId !== id)

      <FolderTabs onFolderChange={setFolder} />

        ? <InboxList ~selectedIds={selectedIds}~ onToggle={handleToggle} /> // The ticked ids go down as props
        : <p>No sent emails</p>}

```

The list receives the two props. It shows the count line only while at least one row is ticked. Each row gets a controlled checkbox (Lesson 20):

### VS | `useState` vs. an External Store for the Ticked Emails: the same screen, different re-renders

Teams often hear that a growing app needs a store, and they reach for Redux or another **third-party state management library**. React's docs describe them as "Third-party state management libraries that hold state outside of React". The docs also call them a **global state library**. Remember Lesson 53? Such a library keeps the state in an external store, and components subscribe to it with `useSyncExternalStore`.

> [!DEFINITION]
> **What is an external store?** [REVIEW] An external store is plain JavaScript outside React that holds a value, such as a module with a variable and a list of listeners.
> It gives React two functions: `subscribe`, so React hears about every change, and `getSnapshot`, which returns the current value.
> A component reads it with `useSyncExternalStore`, and React re-renders that component only when its snapshot is a different value by `Object.is` (Lesson 53).

Here is the same `selectedIds` in a small external store of our own, in the shape of the `todosStore` from React's docs:

```js title="src/selectionStore.js" startLine="1"
let selectedIds = [];
let listeners = [];

export const selectionStore = {
  toggle(id) {
    selectedIds = selectedIds.includes(id)
      ? selectedIds.filter(selectedId => selectedId !== id)
      : [...selectedIds, id];
    ~listeners.forEach(listener => listener())~; // Tells React that the store changed
  },
  subscribe(listener) {
    listeners = [...listeners, listener];
    return () => {
      listeners = listeners.filter(l => l !== listener);
    };
  },
  getSnapshot() {
    return selectedIds;
  },
};
```

On the screen, `useState` and this store give the same result: the checkbox gets its tick, and the count line shows `1 selected`. On a page with two rows, the built-in way is the right one, and our final page keeps `useState`. The store is here only to show what it changes.

What it changes is which components re-render after a tick. To see it, give each row its own component, `EmailRow`, which logs every render. Then compare two ways for a row to learn whether it is ticked:
1. **With a context.** `App` keeps the ticked ids in state, and provides them through a context named `SelectionContext` (Lesson 28).
2. **With the store.** Each row asks `selectionStore` directly.

```jsx title="With selectedIds in a context: each row reads the whole array"
const selectedIds = ~useContext(SelectionContext)~; // After every tick, a new array: every row re-renders
const isSelected = selectedIds.includes(email.id);
```

```jsx title="With selectedIds in selectionStore: each row reads only its own answer"
const isSelected = ~useSyncExternalStore~( // React compares each row's true or false with Object.is
  selectionStore.subscribe,
  () => selectionStore.getSnapshot().includes(email.id)
);
```

Both ways give each row the same `isSelected`, so you expect them to cost the same. **It may look the same, but it is NOT the same thing!** A tick makes a new `selectedIds` array.
- **With the context,** every component that reads it re-renders whenever its value changes (Lesson 59). So both rows re-render.
- **With the store,** each row's snapshot is only `true` or `false`. React re-renders only the row whose answer changed.

Here is the row with the store:

```jsx title="src/components/EmailRow.jsx" startLine="1"
import { useSyncExternalStore } from 'react';
import { selectionStore } from '../selectionStore.js';

export default function EmailRow({ email }) {
  const isSelected = useSyncExternalStore(
    selectionStore.subscribe,
    () => ~selectionStore.getSnapshot().includes(email.id)~ // Only this row's answer: true or false
  );
  console.log('EmailRow rendered:', email.title);
  return (
    <li>
      <input
        type="checkbox"
        checked={isSelected}
        onChange={() => selectionStore.toggle(email.id)}
      />
      {email.title}
    </li>
  );
}
```

The arrow function in the second argument is a new function on every render. That is fine. React only calls it, and it returns a boolean, which stays the same value while the row's tick does not change (Lesson 53).

When the user ticks `Lunch at 12?`, here is what happens with the store:
1. `selectionStore.toggle` with the id 2 makes a new `selectedIds` array, and calls every listener.
2. React calls each row's snapshot function. The first row gets `false`, the same as before. The second row gets `true`, which differs from its old `false`.
3. React re-renders only the second row. The Console prints the line for `Lunch at 12?`, and no line for the first email.

### When an External Store Pays Off

With two rows, one extra render costs nothing, and a re-render with the same result changes no DOM node (Lesson 54). The store pays off in two cases only:
1. **Many distant components read small parts of state that changes often,** and the context re-renders too many of them. Measure the re-renders first.
2. **The state already lives in code outside React,** such as a library written without React. React's docs: "When possible, we recommend using built-in React state with `useState` and `useReducer` instead. The `useSyncExternalStore` API is mostly useful if you need to integrate with existing non-React code."

```tree caption="Where each kind of state in the inbox belongs."
Where the inbox keeps each kind of state
- +A copy of data from the server [`emails`] | A **client-side cache** or the framework's data fetching | One answer for each URL, **shared by every component**
- +State that only the page knows [`folder` `selectedIds`] | **`useState`**, **`useReducer`**, and **context** | Lifted only as far as the components that need it
- +The same state, read in small parts by many components [`useSyncExternalStore`] | An **external store** | Only when context re-renders too much, or the state lives **outside React**
```

A team that adds a global store too early often brings back the problem of Principle 1. Here is how it goes:
1. A team adds a global store at the start of a project.
2. They load the emails from the server into the store, next to the open tab and the ticked rows.
3. The store now holds a copy of the server's emails. The team writes the loading code, the error code, and the code that fetches again, by hand, inside the store.
4. A change on another device does not reach the store, and the copy drifts away from the server.

The store's code grows, and a cache library would have done that part for them. A global store is not the one copy of the server's data. The cache is. Remember the one sentence of this lesson: **data from the server is only a copy, so the page must keep exactly one copy of it.**

### The Complete Project

Here is the finished inbox:
1. The emails live in the SWR cache, one answer for the emails URL.
2. The tab and the list both read that one answer.
3. `App` holds only the state that the page knows: the open tab and the ticked emails.

The entry file mounts `App` inside `<StrictMode>`:

```jsx title="src/main.jsx"
createRoot(document.getElementById('root')).render(
  <StrictMode>
```

The fetcher gives SWR the answer for a URL:

```js title="src/fetcher.js"
export const fetcher = url => fetch(url).then(response => response.json());
```

`App` holds the open tab and the ticked emails:

```jsx title="src/App.jsx"
import { useState } from 'react';
import FolderTabs from './components/FolderTabs.jsx';
import InboxList from './components/InboxList.jsx';

export default function App() {
  const [folder, setFolder] = useState('inbox');
  const [~selectedIds~, setSelectedIds] = useState([]); // Principle 5: state that only the page knows stays in useState

  function handleToggle(id) {
    setSelectedIds(selectedIds.includes(id)
      ? selectedIds.filter(selectedId => selectedId !== id)
      : [...selectedIds, id]);
  }

  return (
    <>
      <FolderTabs onFolderChange={setFolder} />
      {folder === 'inbox'
        ? <InboxList selectedIds={selectedIds} onToggle={handleToggle} />
        : <p>No sent emails</p>}
    </>
  );
}
```

The tab counts the unread emails from the cached answer:

```jsx title="src/components/FolderTabs.jsx"
import useSWR from 'swr';
import { fetcher } from '../fetcher.js';

export default function FolderTabs({ onFolderChange }) {
  const { data: emails = [] } = ~useSWR('/api/emails', fetcher)~; // Principles 1 and 4: the same cached answer as the list
  const unread = emails.filter(email => !email.read).length;
  return (
    <div>
      <button onClick={() => onFolderChange('inbox')}>Inbox ({unread})</button>
      <button onClick={() => onFolderChange('sent')}>Sent</button>
    </div>
  );
}
```

The list shows the rows from the same cached answer, and asks SWR to fetch it again after **Mark as read**:

```jsx title="src/components/InboxList.jsx"
import useSWR, { mutate } from 'swr';
import { fetcher } from '../fetcher.js';

export default function InboxList({ selectedIds, onToggle }) {
  const { data: emails } = ~useSWR('/api/emails', fetcher)~; // Principle 2: a new mount shows the cached answer at once

  function handleMarkAsRead(id) {
    fetch('/api/emails/' + id + '/read', { method: 'POST' })
      .then(() => ~mutate('/api/emails')~); // Principle 4: every component that reads this URL gets the new answer
  }

  if (!emails) return <p>Loading...</p>;
  return (
    <>
      {selectedIds.length > 0 && <p>{selectedIds.length} selected</p>}
      <ul>
        {emails.map(email => (
          <li key={email.id}>
            <input
              type="checkbox"
              checked={selectedIds.includes(email.id)}
              onChange={() => onToggle(email.id)}
            />
            {email.title}
            {!email.read && (
              <button onClick={() => handleMarkAsRead(email.id)}>Mark as read</button>
            )}
          </li>
        ))}
      </ul>
    </>
  );
}
```

### Where Each Kind of State Lives

| Kind of state | Where it lives on our page | What goes wrong elsewhere |
| :--- | :--- | :--- |
| **The emails, a copy of data from the server** | The SWR cache, one answer for the emails URL | In an Effect in each component, the tab and the list keep two copies and disagree after one click |
| **The emails, shown again after a tab change** | The same cached answer, shown at once | In the state of `InboxList`, the copy is thrown away and the user waits on `Loading...` again |
| **The open tab, `folder`** | `useState` in `App` | In a global store, it adds code and changes nothing the user sees |
| **The ticked emails, `selectedIds`** | `useState` in `App`, passed down as props | In an external store, it pays off only when many distant components read it, or when it lives outside React |

## For the Interview

> **The Interview Question:** When does an app outgrow useState and context, and what do external stores and server-cache libraries add?

### How to Answer Clearly in 30 Seconds

"I first ask whether a value is a copy of data from the server, or state that only the page knows. Most data that many components share is a copy from the server. If two components each fetch it in their own Effect, they keep two copies. One click changes one copy, and the page shows two answers. A component that fetches in an Effect also fetches again every time it mounts.

So I keep one copy:
1. **On a small page,** I lift the data into the common parent or a context. That is one owner, and it works, but I write the loading, error, and `ignore` code for every new piece of data.
2. **When many components and screens share data from the server,** I use the framework's data fetching, or a client-side cache library such as TanStack Query, SWR, or RTK Query. It deduplicates requests, caches the responses between components, and fetches again after a change.
3. **For state that only the page knows,** such as the open tab or the ticked rows, I keep `useState`, `useReducer`, and context. An external store fits when many distant components read small parts of that state, because each one re-renders only when its own snapshot changes. It also fits when the state already lives outside React."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"I moved the fetch into a custom Hook, `useData(url)`, and called it in both components. Why do they still disagree?"**
   A custom Hook shares the code, not the data. Each call to `useData` runs its own Effect and keeps its own state, so the two components still hold two copies and send two requests. To share the data, the copy needs one place to live: the common parent, a context, or a client-side cache. With SWR, every `useSWR` call with the same URL reads the same cached answer, so the components cannot disagree.
2. **"What does a client-side cache library add that lifting the data into context does not?"**
   Both keep one copy, so once the data has arrived, the screen after a change is the same. The library adds the work around that copy. It sends one request when several components ask for the same URL at the same time. It keeps the answer outside every component, so a component that mounts again shows it at once instead of `Loading...`. After a change, our code asks it to fetch the URL again, and every component that uses it updates. There are no props, and no owner code for each new piece of data. React's docs recommend it for an app without a framework: "Otherwise, consider using or building a client-side cache."
3. **"When would you reach for an external store, or a library such as Redux, instead of context?"**
   Only for state that only the page knows. A copy of the server's data belongs in a cache, not in a store. Context re-renders every component that reads it whenever its value changes. An external store read through `useSyncExternalStore` re-renders a component only when its own snapshot changes by `Object.is`. That helps when many distant components read small parts of state that changes often, or when the state already lives in code outside React. React's docs recommend `useState` and `useReducer` first, and say "In smaller apps, this is not a problem", so I measure the re-renders before I add a library.

```tree dir=right caption="Interview summary: where each kind of state belongs as an app grows."
Choosing where state lives as an app grows
- !Two Effects for the same data [`fetch` in `FolderTabs` and `InboxList`] | **Two copies** and two requests | One click leaves **two answers** on the page
- +One owner or a client-side cache [`App` holds `emails` or `useSWR`] | **One copy** of the server's data | The cache also shares **one request** and keeps the answer **after an unmount**
- +React state first, a store when it pays off [`useState` `useReducer` `useSyncExternalStore`] | State that **only the page knows** | A store re-renders **only the components whose snapshot changed**
```
