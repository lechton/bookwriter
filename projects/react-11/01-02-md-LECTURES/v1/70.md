# Lecture 70: How lazy Loads a Component Only When It Renders

*(How can a page skip the code of a panel that most visitors never open?)*

> INTERVIEW QUESTION | ❱❱ MORE | How do you code-split a component and load it on demand with lazy?

---

## VS | A Static `import` Line vs. `lazy(() => import())`: the code arrives with the page, or the first time React renders the component

> Every `import` line at the top of a file makes the browser download that file when the page loads, even a stats panel that most visitors never open. **`lazy` puts that download off until the first time React renders the component.** So a visitor who never clicks `Show stats` never downloads the panel, and the page loads faster for everyone.

You already bring a component into a file with an `import` line at the top (Lesson 05). And you already hide a component with `&&` (Lesson 10):

```jsx title="src/App.jsx"
~import Stats from './Stats.jsx';~ // Downloads Stats.jsx when the page loads

{showStats && <Stats />} {/* Shows the panel only while showStats is true */}
```

Now a question. A visitor never clicks `Show stats`, so `Stats` never appears on their screen. Did their browser download the code of `Stats` anyway?

Yes, it did. In a developer's mind, "the panel is not on the screen" and "the panel was never downloaded" feel like one fact. It may look the same, but it is NOT the same thing! Two different lines decide them:
1. **The `&&` decides what React shows.** While `showStats` is `false`, the panel is not on the screen.
2. **The `import` line decides when the code arrives.** It arrives when the page loads, for every visitor, click or no click.

`lazy` changes only the second line. The `<Stats />` tag and the `&&` stay exactly as they are.

### The Idea Behind It: `import()` in Plain JavaScript

Remember that a plain JavaScript page can download a file later, on a click? You write `import` with parentheses, like a function call, and the browser downloads the file only at that moment:

```js title="Plain JavaScript: you download the file yourself, on the click"
button.addEventListener('click', async () => {
  const module = await ~import('./stats.js')~; // The browser downloads stats.js only now
  module.default(); // Calls the function that stats.js exports as default
});
```

In React, you cannot do this for a component. You never call your component yourself. You write `<Stats />` in the JSX, and React calls `Stats` when it renders. So there is no click handler where you could download `Stats` in time for the JSX.

`lazy` is how you ask React: "Here is how to download `Stats`. Do it yourself, the first time you need to render it."

```jsx title="React: you hand the download to React"
const Stats = ~lazy(() => import('./Stats.jsx'))~; // React calls this arrow function the first time it renders <Stats />
```

The name says what it does. Being lazy means putting a job off until the last moment. The React documentation says it in one sentence: "`lazy` lets you defer loading component's code until it is rendered for the first time." To defer means to put off until later.

Keep one sentence in mind for the whole lesson. **The `import` line at the top brings the code with the page. `lazy` brings it the first time React renders the component.**

### The Words This Lesson Stands On

> [!DEFINITION]
> **A promise.** [REVIEW] A promise is a JavaScript object that stands for a value that arrives later, such as a file the browser is still downloading. While the value has not arrived, the promise is pending. Once it has arrived, the promise is resolved, and it holds that value (Lesson 33).

> [!DEFINITION]
> **A `<Suspense>` fallback.** [REVIEW] A component suspends when it is not ready to render yet. React then goes up to the closest `<Suspense>` above it and shows its `fallback`, such as `<p>Loading stats...</p>`, until the component is ready. Everything outside that `<Suspense>` stays on the screen (Lesson 69).

> [!DEFINITION]
> **The bundler.** [REVIEW] The bundler is the tool that packs the files of our app into a few JavaScript files, called bundles, that the browser downloads. Our bundler is Vite. With `npm run dev`, Vite serves each file on its own. With `npm run build`, it packs them into bundles (Lesson 46).

> [!DEFINITION]
> **The static `import` declaration.** [NEW] The static `import` declaration is the line `import Stats from './Stats.jsx'` at the top of a file. Static means fixed: the browser loads the file it names before any other line of our file runs, whether the component ever renders or not. MDN says it "is static and will always result in the imported module being evaluated at load time", and evaluated means its code runs (Lesson 70).

> [!DEFINITION]
> **The dynamic `import()`.** [NEW] The dynamic `import()` is `import` followed by parentheses, like a function call: `import('./Stats.jsx')`. It is plain JavaScript, not React. It starts downloading the file only when our code calls it, and it returns a promise of that file. MDN calls it "a function-like expression that allows loading an ECMAScript module asynchronously and dynamically". An ECMAScript module is simply a JavaScript file with `import` and `export` lines, such as `Stats.jsx` (Lesson 70).

### What Is at Stake

The React documentation names the cost plainly: "Apps can become slow to load because all of the code for the entire app needs to be sent before it can be used."

Today our stats panel is one line. In a real app, a stats panel brings a chart library with it, and that library can be bigger than the whole rest of the page. A visitor on a slow phone downloads all of it before the article works.

With `lazy`, the visitor downloads only what the article needs. The author pays a small price instead: they wait a moment, once, the first time they click `Show stats`.

Developers usually go wrong in one of five ways:
1. **They think a component hidden behind `&&` is never downloaded.** It is downloaded with the page, because the `import` line never looks at the JSX.
2. **They write `lazy` with no `<Suspense>` above the tag.** React then has no fallback to show while the code loads.
3. **They switch to `lazy` and leave the file with a named export.** `lazy` finds no component, and the page goes blank.
4. **They write the `lazy` line inside the component that renders it.** The panel then disappears behind its fallback every time the page updates.
5. **They split every component into its own file.** The page then loads in many small waits. The React documentation warns: "you might encounter situations where loading becomes slower than if no code splitting were happening at all."

### The Rule of Thumb: does every visitor see it at once?

**Ask one question about every component: does every visitor see it as soon as the page loads? If yes, keep the `import` line at the top. If only some users open it, or it opens only after a click, load it with `lazy`.**

### Three Ways to Bring In the Code of a Component

At work, developers pick one of three ways:
1. **The `import` line at the top of the file** (Lesson 05). It fits what the page needs at once, such as the title and the text of an article. MDN says this form "is preferable for loading initial dependencies", which means the code a page needs from the start.
2. **`lazy` with a `<Suspense>` above the tag.** This is the way of this lesson. It fits a part that only some users open, or that opens only after a click, such as a stats panel.
3. **Splitting by route, done by a router or a framework** (Lesson 46). It fits whole pages, such as the home page and the settings page. The React documentation says this kind of split "can reduce the initial load time of your app".

```tree caption="Three ways to bring the code of a component into the page, and the part of the page each one fits."
Three ways to bring in the code of a component
- +The `import` line at the top [`import Stats from './Stats.jsx'`] | Loads **with the page** | Fits what **every visitor sees at once**, such as the title and the text
- +`lazy` with `<Suspense>` [`lazy` `<Suspense>`] | Loads **the first time React renders it** | Fits a part that **only some users open**, such as the stats panel
- +Split by route [router or framework] | Loads **each page on its own** | Fits **whole pages**, and routers and frameworks do it for you
```

## SECTION | An Article Page with a Show Stats Button

Our page is one article on a news site. It shows a title, one line of text, and a `Show stats` button. The button is there for the author of the article. When the author clicks it, a small panel says how many people read the article today.

```page caption="The article page when a visitor opens it: a title, one line of text, and a Show stats button."
heading: Main Street park opens today

```

```page caption="The same page after the author clicks Show stats: the panel shows the views of the day."
heading: Main Street park opens today
line: The park opens at noon.
line: [Hide stats]
line: Views today: 120 | good
```

Most visitors never click `Show stats`. They read the article and leave.

The page uses three files in `src/`. The panel lives in its own file:

```files title="news-article: File Explorer" caption="How the files of our article page sit inside src/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | root | Imports `App` from `./App.jsx` and mounts it inside `<StrictMode>`
  App.jsx | parent | The article page: holds `showStats` state and brings in `Stats`
  Stats.jsx | default export | Exports the stats panel `Stats` as default
```

The entry file mounts `App` inside `<StrictMode>` (Lesson 07), and it stays the same for the whole lesson:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

The panel is one paragraph:

```jsx title="src/Stats.jsx"
~export default~ function Stats() { // The panel, exported as the default export of its file
  return <p>Views today: 120</p>;
}
```

The page file brings the panel in the usual way, with an `import` line at the top. A state variable, `showStats`, starts as `false`, and the button turns it on and off:

```jsx title="src/App.jsx"
import { useState } from 'react';
~import Stats from './Stats.jsx';~ // Downloads Stats.jsx when the page loads

export default function App() {
  const [showStats, setShowStats] = useState(false);
  return (
    <>
      <h1>Main Street park opens today</h1>
      <p>The park opens at noon.</p>
      <button onClick={() => setShowStats(!showStats)}>
        {showStats ? 'Hide stats' : 'Show stats'}
      </button>
      {~showStats &&~ <Stats />} {/* The panel appears only while showStats is true */}
    </>
  );
}
```

These three files give exactly the two screens above. Now each principle changes how `Stats` arrives, and shows what the visitor and the author get.

**PRINCIPLES:** The `import` line at the top brings the code with the page. `lazy` brings it the first time React renders the component. Five principles follow:
1. **Principle 1: A Static `import` Sends `Stats` to Every Visitor.** The `import` line loads `Stats.jsx` when the page loads. Hiding the panel with `&&` changes only what React shows, not what the visitor downloads.
2. **Principle 2: `lazy` Waits for the First Render of `Stats`.** The code of `Stats` loads the first time React tries to render `<Stats />`. A `<Suspense>` above the tag shows a fallback while the code loads.
3. **Principle 3: `lazy` Renders Only the Default Export.** `Stats.jsx` must export the panel with `export default`. With a named export, the click on `Show stats` makes the page go blank.
4. **Principle 4: React Loads the Code Once.** The first click shows `Loading stats...`. Every later click shows the panel at once.
5. **Principle 5: Write `lazy` at the Top Level of the File.** Inside `App`, it makes a new lazy component on every render, and the panel disappears behind `Loading stats...` each time.

## PRINCIPLE | `import Stats from`: the code arrives with the page, even when the component never renders

> [!PRINCIPLE]
> **Principle 1: Static import: The Code Arrives with the Page, Whether or Not the Component Renders**
>
> *A static `import` declaration loads its file when the page loads; hiding the component with `&&` changes only what React shows, never what the visitor downloads.*
>
> A visitor who never clicks `Show stats` never sees the panel, yet their browser downloaded it with the page. The `import` line at the top of the file runs when the file loads, before React renders anything, and it never looks at the JSX. To keep a rarely opened panel off the visitor's phone, change the line that brings it in, not the JSX that shows it.
>
> **DO THIS:**
> ```jsx
> const Stats = ~lazy~(() => import('./Stats.jsx')); // The code of Stats loads only when <Stats /> first renders
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import Stats from './Stats.jsx';
> {~showStats &&~ <Stats />} {/* **WRONG:** hides the panel, but every visitor already downloaded Stats.jsx */}
> ```

Every component on our page answers two separate questions:
1. **When does its code reach the browser?** The `import` line answers this one.
2. **Is it on the screen right now?** The JSX answers this one.

```jsx title="The two lines that decide the stats panel"
~import Stats from './Stats.jsx';~ // 1. Decides WHEN the code arrives: when the page loads
{~showStats &&~ <Stats />} {/* 2. Decides WHAT React shows: the panel only while showStats is true */}
```

The two lines do not know about each other. The JSX can keep `Stats` off the screen forever, and the static `import` has already brought its code in.

### What the visitor downloads without ever clicking

**Beware! The visitor downloads the panel without ever seeing it, and nothing on the screen gives this away.** Here is what happens when a visitor opens the page and never clicks:
1. The visitor opens the article page.
2. The browser loads `App.jsx`. The static `import` at its top makes the browser load `Stats.jsx` with it. No click asked for this download, and React has not rendered anything yet.
3. React renders `App`. `showStats` starts as `false`, so the `&&` gives `false`. React never calls `Stats`, and the panel is not on the screen.
4. The visitor reads the article and leaves. The code of `Stats` sits in their browser, downloaded for nothing.

The page itself looks right:

```page caption="What the visitor sees: the article and the Show stats button, with no panel on the page."
heading: Main Street park opens today
line: The park opens at noon.
line: [Show stats]
console: quiet
```

The Elements panel agrees. There is no paragraph for the panel in the DOM:

```dom caption="The Elements panel before any click: the title, the text, and the button, and no panel."
<div id="root">
  <h1>Main Street park opens today</h1>
  <p>The park opens at noon.</p>
  <button>Show stats</button>
</div>
* No Views today paragraph: React never called Stats
```

Only the Network tab shows the download (Lesson 33). With `npm run dev`, Vite serves each file on its own, so the Network tab lists a request for `Stats.jsx` as soon as the page loads, before any click. After `npm run build`, Vite packs `Stats.jsx` into the same bundle as `App.jsx` (Lesson 46), so the panel has no file of its own at all. Whoever downloads the article downloads the panel.

| :--- | :--- |
| **The page** | The title, the text, and `Show stats`, with no panel |
| **The Elements panel** | No `<p>` for the panel |
| **The Network tab, with `npm run dev`** | A request for `Stats.jsx` when the page loads |
| **The files after `npm run build`** | One JavaScript bundle that holds `App` and `Stats` together |

- !3. The visitor leaves | The code of `Stats` was **downloaded for nothing**

### Real mistake: a hidden panel that every visitor still downloads

Here is how this happens at work:
1. A developer adds an author-only stats panel to the article page with a static `import`.
2. They hide it behind `{showStats && <Stats />}`, so visitors never see it.
3. They check the page in their browser. The panel is hidden, and the page looks right.
4. Months later, the panel grows and brings a chart library with it.
5. Now every visitor downloads the panel and the chart library before the article works, and the page is slow on a phone.

Nothing broke on the screen, so nobody noticed. The React documentation says why it keeps getting worse: "An app's code size increases with every new feature and additional dependency."

MDN has a name for the cure: **code splitting**. "This allows an application to load only the code it actually needs at a given point in time, and load other bundles on demand." On demand means when someone asks for it. Here, that is when the author clicks `Show stats`.

Remember: the `&&` decides what React shows. The `import` line decides what the visitor downloads.

## PRINCIPLE | `lazy(() => import())`: the code arrives the first time React renders the component

> [!PRINCIPLE]
> **Principle 2: lazy: The Code Arrives the First Time React Renders the Tag**
>
> *Write `const Stats = lazy(() => import('./Stats.jsx'))` at the top of the file, and place a `<Suspense>` with a `fallback` above the `<Stats />` tag.*
>
> The `<Stats />` tag stays the same; only the line that brings `Stats` in changes. React calls the arrow function the first time it tries to render `<Stats />`, so a visitor who never clicks never downloads the panel. While the code travels, `Stats` suspends, and the closest `<Suspense>` shows its fallback.
>
> **DO THIS:**
> ```jsx
> const Stats = lazy(() => import('./Stats.jsx'));
> <~Suspense fallback={<p>Loading stats...</p>}~><Stats /></Suspense> {/* Shows Loading stats... until the code arrives */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const Stats = lazy(() => import('./Stats.jsx'));
> {showStats && ~<Stats />~} {/* **WRONG:** no Suspense above, so React has no fallback to show while the code loads */}
> ```

Both lines below give us a component called `Stats`, from the same file. The one difference is when the code of `Stats.jsx` arrives:

```jsx title="The static import line vs. lazy with a dynamic import"
~import Stats from './Stats.jsx';~ // 1. Static: loads Stats.jsx when the page loads
const Stats = lazy(() => ~import('./Stats.jsx')~); // 2. Dynamic: loads Stats.jsx the first time React renders <Stats />
```

The word `import` plays two different roles here:
1. **In `import Stats from './Stats.jsx'`**, `import` starts a static declaration. It runs when the file loads.
2. **In `import('./Stats.jsx')`**, `import` is followed by parentheses. This is the dynamic `import()` from plain JavaScript. It runs only when our code calls it, and it returns a promise of the file.

### Why `lazy` gets an arrow function, not the `import()` itself

`lazy` is a function that React provides, and we import it by name from `'react'`. We do not hand `lazy` the `import()` itself. We hand it a small arrow function, `() => import('./Stats.jsx')`.

Why the arrow function? Because of when each one runs:
1. **`import('./Stats.jsx')` on its own** starts the download as soon as JavaScript reaches that line, at page load. That is too early.
2. **`() => import('./Stats.jsx')`** is only a function. Nothing is downloaded until someone calls it, and only React calls it.

So the line `const Stats = lazy(...)` runs when the file loads, and still nothing is downloaded. The download starts only when React meets `<Stats />` for the first time.

> [!DEFINITION]
> **`load` and the lazy component.** [NEW] The React documentation calls the arrow function we pass to `lazy` the `load` function. It "receives no parameters", and it returns the promise of `import()`. React calls it at one exact moment: "React will not call `load` until the first time you attempt to render the returned component." What `lazy` gives back, our new `Stats`, is called a lazy component. You use it in the JSX like any other component: `<Stats />` (Lesson 70).

```tree caption="The static import line and lazy with a dynamic import both give us Stats, but the code arrives at a different time."
Two ways to bring `Stats` into `App.jsx`
- !Static `import` declaration [`import Stats from './Stats.jsx'`] | Runs **when the file loads** | `Stats.jsx` arrives **with the page**, for every visitor
- +`lazy` with a dynamic `import` [`lazy` `import`] | React calls `load` only **when it first renders `<Stats />`** | `Stats.jsx` arrives **after the click** on Show stats
```

### Adding `lazy` and `<Suspense>` to the article page

We make three changes to `App.jsx`, and none to `Stats.jsx`:
1. We add `Suspense` and `lazy` to the import from `'react'`.
2. We replace the static `import` line of `Stats` with the `lazy` line.
3. We wrap the `<Stats />` tag in a `<Suspense>` with a `fallback`.

```jsx title="src/App.jsx"
import { useState, ~Suspense, lazy~ } from 'react'; // Both come from React

const Stats = ~lazy~(() => import('./Stats.jsx')); // Replaces the static import line

export default function App() {
  const [showStats, setShowStats] = useState(false);
  return (
    <>
      <h1>Main Street park opens today</h1>
      <p>The park opens at noon.</p>
      <button onClick={() => setShowStats(!showStats)}>
        {showStats ? 'Hide stats' : 'Show stats'}
      </button>
      {showStats && (
        <~Suspense fallback={<p>Loading stats...</p>}~> {/* Shows this line while the code of Stats loads */}
          <Stats />
        </Suspense>
      )}
    </>
  );
}
```

Why the `<Suspense>`? The first time React tries to render `<Stats />`, the code of `Stats` is not in the browser yet, so React has nothing to draw. The React documentation says: "While the code for the lazy component is still loading, attempting to render it will *suspend.*" A component that suspends hands its place to the closest `<Suspense>` above it, which shows its `fallback` (Lesson 69). Here, the fallback is one line: `Loading stats...`.

### What happens when the author clicks Show stats

**The visitor who never clicks never downloads `Stats.jsx`. The author downloads it with the first click.** Here is the whole story in order:
1. A visitor opens the article page. The `lazy` line has run, but React has not called `load`, so the browser has not asked for `Stats.jsx`.
2. The visitor reads the article and leaves. `Stats.jsx` never reaches their browser.
3. The author opens the page and clicks `Show stats`. React renders `<Stats />` for the first time and calls `load`, which calls `import('./Stats.jsx')`.
4. The code is not there yet, so `Stats` suspends. The closest `<Suspense>` shows `Loading stats...`.
5. The promise resolves. React renders `Stats`, and the page reads `Views today: 120`.

```page caption="The page during step 4: the code of Stats is still loading, so the Suspense boundary shows its fallback."
heading: Main Street park opens today
line: The park opens at noon.
line: [Hide stats]
line: Loading stats...
```

```page caption="The page after step 5: the code of Stats has arrived, and React shows the panel."
heading: Main Street park opens today
line: The park opens at noon.
line: [Hide stats]
line: Views today: 120 | good
```

Our code never writes `.then` on the promise of `import()`. React waits for it for us.

On the developer's own computer, step 4 is usually too short to see, because the file comes from the same machine. Principle 4 adds a small delay so we can watch the fallback.

### Where the code of Stats goes

The Network tab shows the difference. With `npm run dev`, the request for `Stats.jsx` appears only after the click on `Show stats`, not when the page loads.

The build changes too. When Vite meets `import('./Stats.jsx')`, it cuts the code there and puts `Stats` into a second, separate JavaScript file.

> [!DEFINITION]
> **Code splitting and a chunk.** [NEW] Code splitting means cutting the code of the app into smaller files, so the browser downloads each one only when it is needed. The React documentation says: "Code-splitting is the process of breaking your app into smaller bundles that can be loaded on demand." MDN calls each of these smaller files a chunk, and it names the cut that `import()` makes "Dynamic splitting: separates code where dynamic `import()` expressions are used" (Lesson 70).

| Where we look | With the static `import` line | With `lazy` |
| :--- | :--- | :--- |
| **Network tab, page load** | Requests `Stats.jsx` | Does not request `Stats.jsx` |
| **Network tab, first click on `Show stats`** | No new request | Requests `Stats.jsx` |
| **Files after `npm run build`** | One bundle holds `App` and `Stats` | `Stats` sits in its own chunk |

Remember: the `<Stats />` tag never changed. Only the line that brings `Stats` into the file changed, and with it, the moment the code arrives.

## PRINCIPLE | `export default`: `lazy` renders only the default export of the file

> [!PRINCIPLE]
> **Principle 3: Default Export: lazy Renders What the File Exports as default**
>
> *The file you pass to `import()` must export the component with `export default`; with a named export, `lazy` finds no component and the page goes blank.*
>
> When the promise of `import()` resolves, it holds one object with everything the file exports. React reads only the field named `default` of that object. A named export puts the panel under its own name, so `default` is missing, and the click on `Show stats` breaks the whole page. The fix is one word in `Stats.jsx`, not a change in `App.jsx`.
>
> **DO THIS:**
> ```jsx
> ~export default~ function Stats() { // lazy finds the panel under default
>   return <p>Views today: 120</p>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~export function~ Stats() { // **WRONG:** no default export, so lazy finds no component and the page goes blank
>   return <p>Views today: 120</p>;
> }
> ```

Remember the plain JavaScript example at the start of this lesson? After the `await`, we called `module.default()`. `import()` does not hand you the function. It hands you an object that holds everything the file exports, and the default export sits in that object under the key `default`.

> [!DEFINITION]
> **The module namespace object.** [NEW] The module namespace object is the object that the promise of `import()` resolves to. It has one field for every export of the file. MDN says it has "the default export available as a key called `default`". So for `export default function Stats()`, the object holds `Stats` under the key `default`. For `export function Stats()`, it holds `Stats` under the key `Stats`, and there is no key `default` (Lesson 70).

`lazy` reads exactly one key. The React documentation says React will "render the resolved value's `.default` as a React component", and it gives the rule: "Using this pattern requires that the lazy component you're importing was exported as the `default` export."

A default export and a named export both put a function called `Stats` in the file, and a static `import` can bring in either one. For `lazy`, it may look the same, but it is NOT the same thing:

```jsx title="Two ways Stats.jsx can export the panel"
~export default~ function Stats() { return <p>Views today: 120</p>; } // 1. The object holds the panel under default: lazy finds it
~export function~ Stats() { return <p>Views today: 120</p>; } // 2. The object holds the panel under Stats: there is no default key
```

### Real mistake: switching a named export to `lazy`

Here is how this happens at work:
1. The panel file was written with a named export, and the page file brought it in by name, with curly braces. Everything worked.
2. A developer replaces that import line with the `lazy` line, and leaves the panel file as it is.
3. The author clicks `Show stats`.
4. The code arrives, but the object has no `default` key. React stops on the missing key, and the whole page goes blank.

```page caption="The page after the click, when Stats.jsx has only a named export: React removed everything."
blank
```

```devconsole width=full caption="The Console after the click, when Stats.jsx has only a named export."
x Uncaught TypeError: Cannot convert object to primitive value
! An error occurred in one of your React components. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The first line names neither `lazy` nor the missing export. React tried to print a warning about the missing `default` key, and the browser failed while turning the module object into text. So the developer has to know the rule to find the bug.

The bug is not in `App.jsx`. The fix is one word in `Stats.jsx`:

```jsx title="src/Stats.jsx"
~export default~ function Stats() { // The panel now sits under the key default, where lazy looks
  return <p>Views today: 120</p>;
}
```

```tree caption="Why the file passed to import must export the component as its default export."
What `import` hands to React
- +`export default function Stats` [`default`] | The object holds the panel **under the key `default`** | React **renders `Stats`**
- !`export function Stats` [`Stats`] | The object holds the panel **under the key `Stats`** | **No `default` key**: React has nothing to render and **the page goes blank**
```

Remember: `lazy` looks under `default`, and nowhere else.

## PRINCIPLE | `lazy` caches the code: only the first render waits

> [!PRINCIPLE]
> **Principle 4: Cached: React Calls load Once, So Only the First Render Waits**
>
> *The first render of a lazy component shows the closest fallback while its code loads; React keeps the result and never calls `load` again, so every later render shows the component at once.*
>
> The author waits once, the first time they open the panel. React keeps the loaded panel, so closing and opening it again shows `Views today: 120` at once. A missing fallback on the second click is React reusing the code it already has, not a sign that the split failed. To watch the loading state again, reload the page.
>
> **DO THIS:**
> ```jsx
> const Stats = lazy(() => ~delayForDemo~(import('./Stats.jsx'))); // In the demo only: Loading stats... on the first open, then never again
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~import Stats from './Stats.jsx';~ // **WRONG:** switched back because the second open showed no fallback; every visitor downloads Stats again
> ```

### Slowing the load down so we can see the fallback

In Principle 2, `Loading stats...` flashed by too fast to see. The React documentation solves this exact problem in its own demo with a small helper called `delayForDemo`, under the comment "Add a fixed delay so you can see the loading state". We wrap the `import()` in it, and we add the helper at the bottom of `App.jsx`:

```jsx title="src/App.jsx: the lazy line at the top and the helper at the bottom"
const Stats = lazy(() => ~delayForDemo~(import('./Stats.jsx'))); // Waits 2 seconds before handing over the code

function delayForDemo(promise) {
  return new Promise(resolve => {
    ~setTimeout(resolve, 2000)~; // Starts a 2-second timer
  }).then(() => promise); // Then gives back the promise of import()
}
```

The helper exists only so we can watch the loading state. It never ships to real users. Nothing else in the file changes.

### The first click and the second click

**The same click on `Show stats` shows `Loading stats...` the first time, and never again.** The code that runs is the same both times. Only what React already holds is different. Here is the author's visit in order:
1. The author clicks `Show stats`. React renders `<Stats />` for the first time and calls `load`.
2. `delayForDemo` waits two seconds. `Stats` suspends, and the page reads `Loading stats...`.
3. After two seconds, the code is there. The page reads `Views today: 120`.
4. The author clicks `Hide stats`. React unmounts `Stats`, and the panel is gone.
5. The author clicks `Show stats` again. React renders `<Stats />`, but it does not call `load` this time.
6. The page reads `Views today: 120` at once. No `Loading stats...` appears, even though the two-second delay is still in the code.

line: The park opens at noon.

No line of our code removed the fallback in step 6. React kept the result of the first `load`. The React documentation says: "Both the returned Promise and the Promise's resolved value will be cached, so React will not call `load` more than once." Cached means kept and used again. React already holds the panel, so `Stats` does not suspend, and the `<Suspense>` has no reason to show its fallback.

The browser keeps the file too. MDN says a module is "never executed more than once, even if it is imported multiple times. Future imports don't even result in HTTP requests or disk access." So the Network tab lists one request for `Stats.jsx` on the first click, and none on the second.

To see the fallback again, reload the page. A reload starts the page from scratch, with nothing kept.

```tree dir=right caption="The first click on Show stats loads the code; every later click uses what React kept."
Opening the stats panel twice
- +1. First click on Show stats | React **calls `load`** | `Loading stats...` for 2 seconds, then **`Views today: 120`**
- +2. Click on Hide stats | React **unmounts `Stats`** | The panel is gone; React **keeps the loaded code**
- +3. Second click on Show stats | React **does not call `load`** | **`Views today: 120` at once**, with no fallback
```

So the author waits once, on the first click. After that, the panel opens as fast as it did with the static `import`.

### Real mistake: giving up on `lazy` because the fallback disappeared

Here is how this happens at work:
1. A developer adds `lazy` and opens the stats panel. `Loading stats...` flashes by too fast to see.
2. They close the panel and open it again to look closer. This time no fallback appears at all.
3. They decide the split did nothing, and they go back to the static `import`.
4. Now every visitor downloads the panel again.

What they missed: the first click had already loaded the code, and React had kept it. A reload with `delayForDemo` in place shows the fallback again. And the Network tab after a reload shows the request for `Stats.jsx` only after the click.

Remember: React downloads the code once. Only the first open waits.

## PRINCIPLE | `lazy` at the top level of the file: one component for every render, so the panel stays on the screen

> [!PRINCIPLE]
> **Principle 5: Top Level: Call lazy Once, Outside Every Component**
>
> *Call `lazy` at the top level of the file; inside a component, it makes a new lazy component on every render, so the panel disappears behind its fallback on every update.*
>
> `lazy` makes a component, and a component is made once, at the top level of the file (Lesson 04). Inside `App`, every click on `Like` creates a new lazy `Stats` with nothing loaded, so the panel disappears behind `Loading stats...` until the new promise resolves. Above `App`, the same click changes only the like count, and the panel stays on the screen.
>
> **DO THIS:**
> ```jsx
> const Stats = ~lazy~(() => import('./Stats.jsx')); // Top level: one Stats for every render of App
> export default function App() {
>   return <Suspense fallback={<p>Loading stats...</p>}><Stats /></Suspense>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   const Stats = ~lazy~(() => import('./Stats.jsx')); // **WRONG:** a new Stats on every render brings back Loading stats...
>   return <Suspense fallback={<p>Loading stats...</p>}><Stats /></Suspense>;
> }
> ```

### The page grows: a Like button and two range buttons

Our page grows by two small parts. The article gets a `Like` button that counts up. The panel gets two buttons, `Today` and `This week`, so the author can choose which number to read:

```jsx title="src/Stats.jsx"
import { useState } from 'react';

export default function Stats() {
  const [~range~, setRange] = useState('today'); // Remembers which button the author chose
  return (
    <section>
      <button onClick={() => setRange('today')}>Today</button>
      <button onClick={() => setRange('week')}>This week</button>
      <p>{range === 'today' ? 'Views today: 120' : 'Views this week: 840'}</p>
    </section>
  );
}
```

### Two places for the `lazy` line

Where does the `lazy` line go? A developer might write it in one of two places. Both blocks below show only the new `Like` button. The rest of `App` stays as before: the article, the stats button, and the `<Suspense>` around the panel.

```jsx title="The lazy line above App"
const Stats = ~lazy~(() => import('./Stats.jsx')); // Runs once, when the file loads

export default function App() {
  const [likes, setLikes] = useState(3);
  return <button onClick={() => setLikes(likes + 1)}>Like ({likes})</button>;
}
```

```jsx title="The lazy line inside App"
export default function App() {
  const Stats = ~lazy~(() => import('./Stats.jsx')); // **WRONG:** runs again on every render of App
  const [likes, setLikes] = useState(3);
  return <button onClick={() => setLikes(likes + 1)}>Like ({likes})</button>;
}
```

On the first click on `Show stats`, both versions show `Loading stats...` and then `Views today: 120`. It may look the same, or work the same at first, but it is NOT the same thing! The difference appears on the next render of `App`:
1. **With `lazy` above `App`**, the line runs once, when the file loads. Every render of `App` uses that same `Stats`.
2. **With `lazy` inside `App`**, the line runs on every render of `App`, like every other line in the body. Each call to `lazy` returns a brand-new lazy component, with nothing loaded yet.

It looks like the trap of a component defined inside another component (Lesson 04), but the result is different. A new lazy component has not loaded its code, so it must suspend before React knows which function it holds. Once its code arrives, React finds the same `Stats` function from the same file, and it keeps the panel that was already there.

The safe place has a name in the React documentation: the **top level of your module**. That means outside every function in the file, next to the `import` lines.

### What the author sees when they click Like

**Beware! With `lazy` inside `App`, any update of the page hides the panel behind `Loading stats...` again.** Here is the author's visit, with the `lazy` line inside `App` and `delayForDemo` still in place.

No line of our code asks for a new component in step 2. The `lazy` line makes it, because the line sits inside `App` and runs on every render.

The second `Loading stats...` in step 4 appears even though the browser already holds `Stats.jsx`. The Network tab shows no new request, because the browser keeps the file. But the new lazy component has an empty cache of its own. It must wait for its own promise, and while it waits, it suspends.

- !Inside `App` | `lazy` runs **on every render** and returns a **new lazy component** | After a click on Like: **`Loading stats...` again**, then the panel comes back

### Real mistake: moving `lazy` next to the state lines

Here is how this happens at work:
1. A developer moves the `lazy` line inside `App`, next to the state lines, because that is where the other setup lines of the component live.
2. The panel works on the first click, so they ship it.
3. The author picks `This week`, then likes the article.
4. The panel vanishes behind `Loading stats...` and comes back a moment later. It happens again on every click on `Like`.
5. The developer looks for the bug in `Stats.jsx`, whose code is correct. The fix is one line moved above `App`.

The React documentation gives the rule in two sentences: "Do not declare `lazy` components *inside* other components" and "Instead, always declare them at the top level of your module".

Remember: `lazy` makes a component. Make it once, at the top of the file.

## All 5 Principles Together

### The complete files

Here is the finished page. Three things make it work:
1. The `lazy` line sits at the top level of the page file, above `App`.
2. The panel file exports `Stats` as its default export.
3. A `<Suspense>` with a fallback sits above the `<Stats />` tag.

The `delayForDemo` helper from Principle 4 is gone, because it was only there to watch the loading state. The entry file stays as it was at the start of the lesson.

```jsx title="src/App.jsx"
import { useState, Suspense, lazy } from 'react';

const Stats = ~lazy~(() => import('./Stats.jsx')); // Principles 2 and 5: one lazy Stats, at the top level

export default function App() {
  const [showStats, setShowStats] = useState(false);
  const [likes, setLikes] = useState(3);
  return (
    <>
      <h1>Main Street park opens today</h1>
      <p>The park opens at noon.</p>
      <button onClick={() => setLikes(likes + 1)}>Like ({likes})</button>
      <button onClick={() => setShowStats(!showStats)}>
        {showStats ? 'Hide stats' : 'Show stats'}
      </button>
      {showStats && (
        <~Suspense fallback={<p>Loading stats...</p>}~> {/* Principles 2 and 4: shown only on the first open */}
          <Stats />
        </Suspense>
      )}
    </>
  );
}
```

### The habit that hurts, and the rule

| Principle | The habit that hurts | The React rule |
| :--- | :--- | :--- |
| **1. Static import** | Hide a rarely used panel with `&&` and believe it is never downloaded | The `import` line loads its file with the page; change that line to keep the code off the visitor's phone |
| **2. lazy** | Switch to `lazy` and leave out `<Suspense>` | Write `lazy(() => import('./Stats.jsx'))`, and wrap the tag in `<Suspense>` with a `fallback` |
| **3. Default export** | Switch to `lazy` and leave the component as a named export | Export the component with `export default`, because React renders the `default` key |
| **4. Cached** | Test twice in the same tab, see no fallback, and remove `lazy` | React calls `load` once and keeps the result; reload the page to see the fallback again |
| **5. Top level** | Put the `lazy` line inside the component, next to its state | Call `lazy` at the top level of the file, so every render uses the same component |

Remember the one sentence of this lesson. **The `import` line at the top brings the code with the page. `lazy` brings it the first time React renders the component.**

## For the Interview

> **The Interview Question:** How do you code-split a component and load it on demand with lazy?

### How to Answer Clearly in 30 Seconds

"A static `import` at the top of a file loads that file with the page, even if the component never renders, so hiding it with `&&` saves nothing. To split it off, I replace the import with `const Stats = lazy(() => import('./Stats.jsx'))`. The dynamic `import()` is where the bundler cuts a separate chunk, and React calls that function only the first time it tries to render `<Stats />`. Four rules keep it working:
1. **A default export**: React renders the `default` of the loaded module, so the file must export the component as `default`.
2. **A Suspense boundary**: while the code loads, the lazy component suspends, and the closest `<Suspense>` shows its `fallback`.
3. **One load**: React caches the result, so only the first render waits.
4. **The top level**: I declare `lazy` outside every component. Inside one, every render creates a new lazy component, and the panel falls back to its loading state on every update."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What happens if the chunk fails to load, for example on a lost connection?"**
   The promise of `import()` rejects. MDN says it rejects when "the network request fails". The React documentation says: "If the Promise rejects, React will `throw` the rejection reason for the nearest Error Boundary to handle." So in production, a lazy component sits inside an Error Boundary as well as a `<Suspense>`, and the Error Boundary shows a message instead of a blank page (Lesson 72).
2. **"My component is a named export. Can I still load it with `lazy`?"**
   Yes. The only rule is that the promise resolves to an object whose `default` is a component. We can build that object ourselves: `lazy(() => import('./Stats.jsx').then(module => ({ default: module.Stats })))`. The cleaner fix is usually to add a default export to the file.
3. **"Should you split every component with `lazy`?"**
   No. Every split adds a wait the first time that part appears. The React documentation warns that you "might encounter situations where loading becomes slower than if no code splitting were happening at all". A lazy chart that "loads its data *after* it has been initially rendered" makes the user wait twice, first for the code and then for the data: "This is a waterfall" (Lesson 46). Split what few users open, or what opens later, such as an author's stats panel. Leave whole pages to the router or the framework, which splits code by route.

```tree caption="When to split a component with lazy, and when to keep the static import line."
Should this component use `lazy`?
- +Split it with `lazy` | Only **some users** open it, or it opens **after a click** | The author's **stats panel**, an admin screen, an editor's preview
- !Keep the static `import` | **Every visitor** sees it as soon as the page loads | The **title and text** of the article; splitting them only **adds a wait**
```
