# Lecture 109: How a Server Component Awaits Its Data, and What It Replaces

*(How does a component get data that arrives a moment later, and what code does that remove?)*

> INTERVIEW QUESTION | ❱ CORE | How do Server Components read data with async/await, and what does that replace?

---

## VS | `fetch` in an Effect vs. `await` in a Server Component: the Effect shows a loading line first, `await` puts the data in the first page

> In plain JavaScript, when data takes a moment to arrive, you write `await`, and the next line waits until the data is there. **A Server Component can do exactly that: it is an `async` function that awaits the database inside its own body, and React waits for it.** So the data is already in the first page the user gets, and the state, the Effect, and the API you needed in the browser are gone.

Remember how you read data on a Node.js server. You call the database, you write `await`, and the next line already has the rows:

```js title="Plain JavaScript on a Node.js server"
const emails = ~await~ db.emails.getAll(); // The next line runs only when the emails are here
console.log(emails.length);
```

Until now, a React component could never do this. React calls your component, and it wants the JSX back at once. So the data could only come later. The component returns a loading line, an Effect sends a request after the first render, and a setter renders the component again when the answer comes (as seen in Lesson 33).

A Server Component removes that limit. On the server, React lets the component stop at `await`, waits for the database, and only then uses the JSX the component returns. It is the same line you write in Node.js, now inside the component:

```jsx title="React: the same line inside a Server Component"
export default ~async~ function EmailList() { // async: this component may wait while it renders
  const emails = ~await~ db.emails.getAll(); // React waits here, then goes on with the emails
  return <ul>{emails.map(email => <li key={email.id}>{email.subject}</li>)}</ul>;
}
```

Each place has a benefit and a problem:
- **In the browser**, the component sees every click, but it has no database. It must return its JSX at once, so the first page shows only a loading line, and the data comes after a second request.
- **On the server**, the component has the database, and it may wait for it. But it waits before it returns anything, so it cannot show its own loading line. A `<Suspense>` boundary in its parent shows that line instead.

Here is the one sentence to keep in mind for this whole lesson:

**A Server Component waits for its data inside its own body, so the data is already in the first page.**

> [!DEFINITION]
> **Async component.** [REVIEW] An async component is a component written as an `async` function, so it can `await` data in the middle of rendering and return its JSX only when the data is there. Only a Server Component can be async; React's docs say "async components are not supported on the client" (Lesson 108).

> [!DEFINITION]
> **Suspense boundary.** [REVIEW] A `<Suspense>` tag wraps one part of the page. While a component inside it waits for its data, React shows the `fallback` you gave it, such as `<p>Loading...</p>`, and the rest of the page shows as normal. When the component is ready, React puts it in the place of the fallback (Lesson 69).

### The Same Emails, Two Different First Pages

Open the inbox of an email app such as Gmail. The page shows the heading `Inbox` and a list of emails, each with a sender and a subject:

```page caption="The inbox the user sees after opening the page: a heading and two emails."
url: mail.example.com
heading: Inbox
line: Anna: Lunch on Friday?
line: Netflix: Get your next month for $0.99
```

The user does nothing but open the page. The emails belong to this one user, and they live in the app's database, on the server. The component that draws the list does not have them yet, and the database takes a moment to answer.

There are two places to read the emails:
- **In the browser:** the page first arrives with a line that reads `Loading emails...`. The browser downloads the JavaScript, runs the component, and only then asks the server for the emails, in a second request. The component keeps the emails, a loading flag, and an error in state, and it starts the request in an Effect.
- **On the server:** the component is an `async` function. It waits for the database inside its own body, while React renders it, and then returns the list. The list is already in what the server sends to the browser.

```tree caption="Two places to read the emails: in the browser after the first render, or on the server while React renders."
Two places to read the user's emails
- !In the browser, in an Effect [`useState` `useEffect` `fetch`] | The first page shows **only `Loading emails...`** | The emails come after **a second request** to the server
- +On the server, with `await` [`async function EmailList`] | The component **waits for the database** while React renders it | The emails are **in the first page**
```

A Server Component is a function that returns JSX, like every component you wrote before. So it looks like it must follow the same rule: return the JSX at once, and get the data later. **It may look the same, but it is NOT the same thing!** On the server, React lets the component stop at `await`, waits for the data, and only then uses what the component returns.

For the user, the difference is what the first page shows:
1. **With the Effect**, the user sees `Loading emails...` first, and the emails only after a second trip to the server. React's docs say it plainly: "the initial server-rendered HTML will only include a loading state with no data."
2. **With `await` in a Server Component**, the list itself is what reaches the browser.

For the developer, the difference is the amount of code. The Effect version needs three state variables, an Effect, and an API file. The Server Component needs one `await` line.

### Where Readers Usually Go Wrong

Readers usually go wrong by keeping their browser habits while they write a Server Component:
1. **They forget the `await`.** The component then tries to draw a list from a promise.
2. **They keep calling their own `/api/emails` from the server.** But the server can read the database directly.
3. **They look for a loading flag inside the async component**, or they put the loading line inside it, where it never shows.

### Four Ways to Show Data the Server Has

When a page must show data the server has, developers choose between four ways:
1. **`fetch` in an Effect in a Client Component** (as seen in Lesson 33). This fits an app with no framework, where React runs only in the browser. React's docs still allow it: "You can continue fetching data directly in Effects if neither of these approaches suit you."
2. **A client-side cache, or a framework's own data loading.** A client-side cache is a library that keeps the data it fetched in the browser, and fetches it again when it is out of date. React's docs name TanStack Query, useSWR, and React Router 6.4 and later. This fits data the browser must keep and fetch again after the user acts.
3. **`await` in an async Server Component.** This fits data the server can read for the first render, in a framework that runs Server Components (as seen in Lesson 46). This lesson builds this way.
4. **A Server Component starts the promise without `await`, and a Client Component reads it with `use`** (as seen in Lesson 71). React's docs keep this way for data of lower priority, such as the comments further down a page. It comes back only in the interview questions at the end.

## PRINCIPLE | `await` in an async component: React waits for the emails, then renders the list

> [!PRINCIPLE]
> **Principle 1: Async Components: `EmailList` Awaits the Emails While It Renders**
>
> *In a Server Component, write the component as an `async` function and `await` the data inside its body; React waits for the promise, then finishes rendering with the data.*
>
> A component in the browser must return its JSX at once, so its data can only arrive after the first render. A Server Component does not have that limit. When it reaches `await`, React suspends it, waits for the database, and resumes rendering with the emails. Only the finished list goes to the browser.
>
> **DO THIS:**
> ```jsx
> export default async function EmailList() {
>   const emails = ~await~ db.emails.getAll(); // React waits here, then renders the two emails
>   return <ul>{emails.map(email => <li key={email.id}>{email.subject}</li>)}</ul>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default async function EmailList() {
>   const emails = ~db.emails.getAll()~; // **WRONG:** emails is a promise, so emails.map throws a TypeError
>   return <ul>{emails.map(email => <li key={email.id}>{email.subject}</li>)}</ul>;
> }
> ```

Here is the whole list component:

```jsx title="src/EmailList.jsx" startLine="1"
import db from './db';

export default ~async~ function EmailList() { // async: this component may wait while it renders
  const emails = ~await~ db.emails.getAll(); // Waits for the database, then goes on with the two emails
  return (
    <ul>
      {emails.map(email => (
        <li key={email.id}>{email.from}: {email.subject}</li>
      ))}
    </ul>
  );
}
```

You know every line of it. The list with `map` and `key` comes from Lesson 18. The pair `async` and `await` comes from Lesson 41. Only two words are new for a component, and they do all the work:
- **`async`** makes `EmailList` return a promise, as every `async` function does in JavaScript. In the browser, React cannot use a component that returns a promise. On the server, React knows what to do with it: it waits.
- **`await`** stops `EmailList` until the promise from `db.emails.getAll()` resolves, and then hands its value to `emails`. While `EmailList` is stopped, React waits for it.

When React renders `EmailList`, the page shows the two emails:

```page caption="What EmailList renders: one line per email from the database."
url: mail.example.com
line: Anna: Lunch on Friday?
line: Netflix: Get your next month for $0.99
```

### Where `db` and `emails` Come From

`db` comes from `db.js`, the stand-in for the database:

```js title="src/db.js" startLine="1"
const db = {
  emails: {
    async getAll() {
      await ~new Promise(resolve => setTimeout(resolve, 1000))~; // Plays a real database: answers after one second
      return [
        { id: 1, from: 'Anna', subject: 'Lunch on Friday?' },
        { id: 2, from: 'Netflix', subject: 'Get your next month for $0.99' },
      ];
    },
  },
};

export default db;
```

`emails` is the array that `await db.emails.getAll()` gives back. Each email is an object with its own `id`, and the `key` of each `<li>` uses it.

### How React Waits for a Component

**React pauses `EmailList` at `await`, and picks it up again when the emails are there.** React's docs: "When you `await` in an async component, React will suspend and wait for the promise to resolve before resuming rendering." To resume rendering means to go on from the line where the component stopped, now with the data.

This works only on the server. In the browser, React needs the JSX at once, and React's docs say it outright: "async components are not supported on the client."

Here is what happens when React renders `EmailList` on the server:
1. React calls `EmailList` while it renders the page on the server.
2. `EmailList` reaches `await db.emails.getAll()`. The `async` function hands React a promise instead of JSX.
3. React suspends `EmailList` and waits for that promise to resolve (as seen in Lesson 69).
4. One second later, the database answers with the two emails, and the promise resolves with the array.
5. React resumes rendering. Now `emails` holds the array, and `EmailList` returns a list with the two emails.
6. Only this rendered output goes to the browser. The code of `EmailList.jsx` and `db.js` stays on the server (as seen in Lesson 101).

```tree dir=right caption="How React renders EmailList on the server: it suspends at await and resumes when the emails arrive."
How React renders `EmailList` on the server
- +1. React calls `EmailList` [`async function EmailList`] | The function reaches `await` | It hands React **a promise**, not JSX
- +2. React suspends it [`await`] | React **waits** for the promise | The database answers **after one second**
- +3. React resumes rendering [`emails.map`] | `emails` holds **the two emails** | `EmailList` returns the `<ul>`, and only that **output** goes to the browser
```

In the browser, the Elements panel shows only what `EmailList` returned:

```dom
+ <ul>
+   <li>Anna<!-- -->: <!-- -->Lunch on Friday?</li>
+   <li>Netflix<!-- -->: <!-- -->Get your next month for $0.99</li>
+ </ul>
```

React's server renderer writes the `<!-- -->` marks where a piece of text meets a value in curly braces (as seen in Lesson 102).

### Forgetting `await`

The most common mistake is to leave out the one word that makes the component wait:

```jsx title="src/EmailList.jsx" startLine="3" bad="4"
export default async function EmailList() {
  const emails = ~db.emails.getAll()~; // **WRONG:** no await, so emails holds a promise, not the array
  return (
    <ul>
      {emails.map(email => (
        <li key={email.id}>{email.from}: {email.subject}</li>
      ))}
    </ul>
  );
}
```

**The list does not appear, and the page shows an error.** Without `await`, `EmailList` does not wait. `emails` holds the promise itself, and a promise has no `map` method. So JavaScript stops at `emails.map` with `TypeError: emails.map is not a function`.

The error comes from JavaScript, not from React. Your code asked a promise for something only an array has.

Remember: an async component waits only where you write `await`.

## PRINCIPLE | `await db.emails.getAll()`: one line replaces three state variables, an Effect, and an API

> [!PRINCIPLE]
> **Principle 2: What `await` Replaces: The Effect Version Opens on `Loading emails...`**
>
> *When a Server Component can read the data, one `await` replaces the three state variables, the Effect, and the API file that a Client Component needs to fetch the same data.*
>
> The Effect version and the async version end with the same emails on the screen. But the Effect runs only in the browser, after the first render, so the first page holds only a loading line, and the emails come after a second request to an API built just for them. The async version reads the database while React renders on the server, so the emails are in the first page.
>
> **DO THIS:**
> ```jsx
> export default async function EmailList() {
>   const emails = ~await db.emails.getAll()~; // Reads the database directly while React renders
>   return <ul>{emails.map(email => <li key={email.id}>{email.subject}</li>)}</ul>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default async function EmailList() {
>   const emails = await ~fetch('/api/emails')~.then(res => res.json()); // **WRONG:** the server calls its own API, and the relative URL fails
>   return <ul>{emails.map(email => <li key={email.id}>{email.subject}</li>)}</ul>;
> }
> ```

### The Same List, Read in the Browser

Before Server Components, the same list was a Client Component that fetched in an Effect (as seen in Lesson 33). Here it is, written the way React's docs write it:

```jsx title="src/EmailList.jsx, written as a Client Component that fetches in an Effect" startLine="1"
'use client';

import { useState, useEffect } from 'react';

export default function EmailList() {
  const [emails, setEmails] = ~useState~(null); // 1. The emails, empty until the request answers
  const [isLoading, setIsLoading] = useState(true); // 2. The loading flag
  const [error, setError] = useState(null); // 3. The error, if the request fails

  ~useEffect~(() => { // Runs in the browser, after the first render
    fetch('/api/emails')
      .then(res => res.json())
      .then(data => {
        setEmails(data);
        setIsLoading(false);
      })
      .catch(err => {
        setError(err);
        setIsLoading(false);
      });
  }, []);

  if (isLoading) return <p>Loading emails...</p>;
  if (error) return <p>Error: {error.message}</p>;
  return (
    <ul>
      {emails.map(email => (
        <li key={email.id}>{email.from}: {email.subject}</li>
      ))}
    </ul>
  );
}
```

The browser cannot read the database. So the server needs one more file, an API that exists only to answer that `fetch`:

```js title="api.js" startLine="1"
app.get(~'/api/emails'~, async (req, res) => { // Answers the browser's second request
  const emails = await db.emails.getAll();
  res.send(emails);
});
```

`app.get`, `req`, and `res` come from the server library that React's docs use in the same example. Only our own `EmailList` asks for `/api/emails`.

### VS | The Effect Version vs. the `await` Version: the same emails in the end, a different first page

Both versions end with the same two emails on the screen. **It may look the same, but it is NOT the same thing!** The one difference is where and when the emails are read. React's docs mark it with a comment on each of their own two examples. The Effect version "loads *after* first render", and the async version "loads *during* render".

Here is what the user gets first from each version:

::: row caption="The first page the user gets: from EmailList with an Effect, and from EmailList with await."
::: col title="EmailList with an Effect" tone=bad
```page size=mini
url: mail.example.com
line: Loading emails...
```
The emails wait for a second request.
:::
::: col title="EmailList with await" tone=good
```page size=mini
url: mail.example.com
line: Anna: Lunch on Friday?
line: Netflix: Get your next month for $0.99
```
The emails are in the first page.
:::
:::

**With the Effect, the user waits for two trips to the server, and the first trip brings only a loading line.** Here is the path, in order:
1. The server sends the first page. Effects do not run on the server, so the page holds only `Loading emails...`.
2. The browser downloads the JavaScript and runs `EmailList`. React's docs: the client "will have to download all JavaScript and render your app only to discover that now it needs to load the data."
3. After the first render, the Effect runs and sends `fetch('/api/emails')`.
4. The server runs `api.js`, reads the database, and answers.
5. `setEmails` and `setIsLoading(false)` make React render again, and only now do the two emails appear.

With `await` in a Server Component, those five steps become one. The server reads the database while it renders, and the emails are in what it sends.

### What Goes Away

Put the two versions of `EmailList.jsx` next to each other, and four things disappear:
1. **The three state variables:** `emails`, `isLoading`, and `error`. In the async version, `emails` is a plain `const`.
2. **The Effect with its `fetch`.** The `await` line takes its place.
3. **The two `if` lines** that return the loading line and the error line.
4. **`api.js`**, the API the server needed only to answer the `fetch`. React's docs describe Server Components as "letting you access your data layer without having to build an API". The data layer is the code that reads the app's data, here `db.js`.

```tree caption="What one await line replaces: three state variables, an Effect, two if lines, and an API file."
`EmailList` with an Effect vs. with `await`
- !With an Effect [`useState` `useEffect` `fetch` `api.js`] | Three state variables, **an Effect**, two `if` lines, and **an API file** | The first page shows **`Loading emails...`**, the list comes after **a second request**
- +With `await` [`async function EmailList`] | **One line**, no state, no Effect, no API | The first page **holds the list**
```

Fetching in an Effect is not forbidden. React's docs still allow it for an app with no framework, and it stays a way to load data after the user acts, as Lesson 128 shows. But for data the server can read for the first page, the `await` line does the whole job.

### Keeping the Old `fetch` in a Server Component

A developer moves `EmailList` to a Server Component and keeps the old request:

```jsx title="src/EmailList.jsx" startLine="3" bad="4"
export default async function EmailList() {
  const emails = await ~fetch('/api/emails')~.then(res => res.json()); // **WRONG:** the server has no page address to complete /api/emails
  return (
    <ul>
      {emails.map(email => (
        <li key={email.id}>{email.from}: {email.subject}</li>
      ))}
    </ul>
  );
}
```

**The list does not appear.** `/api/emails` is a relative URL: it names only the path. In the browser, the rest comes from the address of the page the user has open. On the server, no page is open, so nothing fills in the rest. The `fetch` fails with `TypeError: Failed to parse URL from /api/emails`.

A full address would not help much either. The server would call itself over the network, to reach a database it can read directly. Therefore, read the database in the component, and delete the API.

Remember: the server already has the data, so a Server Component asks the database, never its own API.

## PRINCIPLE | `<Suspense fallback>` above `EmailList`: the loading line shows while the emails are on their way

> [!PRINCIPLE]
> **Principle 3: Suspense Above the Async Component: `<Suspense>` Shows `Loading emails...` While `EmailList` Waits**
>
> *The wait does not vanish with the loading flag; to show a loading line while an async component awaits, place `<Suspense fallback>` above that component, in its parent.*
>
> An async component waits for its data, so the user still needs a line that says the emails are on their way. The component cannot draw that line itself, because it is stopped at `await` before it returns anything. The parent draws it, as the `fallback` of a `<Suspense>` boundary, and React puts the list in its place when the component resumes.
>
> **DO THIS:**
> ```jsx
> <h1>Inbox</h1>
> <Suspense ~fallback~={<p>Loading emails...</p>}> {/* In App: shown while EmailList waits */}
>   <EmailList />
> </Suspense>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default async function EmailList() {
>   const emails = await db.emails.getAll();
>   return <~Suspense~ fallback={<p>Loading emails...</p>}><ul>...</ul></Suspense>; // **WRONG:** returned only after the wait, so the fallback never shows
> }
> ```

### The Loading Line Is Back

The async `EmailList` has no loading flag. Yet when the user opens the finished inbox, the page still shows `Loading emails...` for one second:

::: row caption="The finished inbox when the user opens it, and one second later."
::: col title="When the page opens"
```page size=mini
url: mail.example.com
heading: Inbox
line: Loading emails...
```
:::
::: col title="One second later"
```page size=mini
url: mail.example.com
heading: Inbox
line: Anna: Lunch on Friday?
line: Netflix: Get your next month for $0.99
```
:::
:::

**The loading line moved.** In the Effect version, it came from a state variable inside `EmailList`. Now it is the `fallback` of a `<Suspense>` boundary. That boundary sits in `App`, the parent of `EmailList` (as seen in Lesson 69):

```jsx title="src/App.jsx" startLine="1"
import { Suspense } from 'react';
import EmailList from './EmailList';

export default function App() {
  return (
    <>
      <h1>Inbox</h1>
      <Suspense ~fallback~={<p>Loading emails...</p>}> {/* Shown while EmailList waits for the database */}
        <EmailList />
      </Suspense>
    </>
  );
}
```

`EmailList.jsx` and `db.js` stay exactly as in the first principle. `EmailList` never mentions `Loading emails...`.

### What Happens When the User Opens the Inbox

The waiting from the first principle is still there. What changes is who shows the loading line while it lasts. Here is what happens, in order:
1. The user opens the inbox.
2. React renders `App` on the server. It renders the `Inbox` heading first. Then it reaches `<EmailList />` inside `<Suspense>`.
3. `EmailList` reaches `await db.emails.getAll()`, and React suspends it.
4. React shows the `fallback` of the closest `<Suspense>` above it: `Loading emails...`. The heading `Inbox` does not wait.
5. One second later, the promise resolves. React resumes `EmailList` and renders the `<ul>`.
6. The two emails take the place of `Loading emails...`. No state variable of ours changed. React made the switch by itself.

The list reaches a page the user already sees, inside the same response from the server. This is called streaming, and Lesson 117 teaches it.

```tree dir=right caption="How the inbox opens: the heading at once, the fallback while EmailList waits, then the list."
What the user sees when the inbox opens
- +1. At once [`<h1>Inbox</h1>`] | The heading **does not wait** | The user sees **`Inbox`**
- +2. While `EmailList` waits [`<Suspense fallback>`] | `EmailList` is **suspended** at `await` | The user sees **`Loading emails...`**
- +3. After one second [`<ul>`] | React **resumes** `EmailList` | The two emails **take the place** of the loading line
```

### VS | `isLoading` vs. `<Suspense fallback>`: the same words on the screen, a different owner

Both write the same words on the screen, `Loading emails...`. **It may look the same, but it is NOT the same thing!**
- **With `isLoading`**, the component holds a state variable, sets it by hand in `.then` and `.catch`, and returns the loading line itself.
- **With `<Suspense fallback>`**, the parent writes the line once. React shows it by itself while the component inside is suspended, and removes it by itself when the component resumes.

The Effect version needed its own flag because an Effect never suspends. React's docs: "Suspense does not detect when data is fetched inside an Effect or event handler." So in the Effect version, only a flag of our own could show the loading line.

### Putting `<Suspense>` Inside `EmailList`

A developer still thinks the loading line belongs to the list, and moves the boundary inside `EmailList`:

```jsx title="src/EmailList.jsx" startLine="3" bad="6"
export default async function EmailList() {
  const emails = await db.emails.getAll();
  return (
    ~<Suspense~ fallback={<p>Loading emails...</p>}> {/* **WRONG:** this boundary does not exist yet while EmailList waits */}
      <ul>
        {emails.map(email => (
          <li key={email.id}>{email.from}: {email.subject}</li>
        ))}
      </ul>
    </Suspense>
  );
}
```

**`Loading emails...` never shows.** Why? The `await` runs before the `return`. So while `EmailList` waits, the `<Suspense>` it would return does not exist yet.

React's docs: "The closest Suspense boundary above the suspending component shows its fallback." React looks above `EmailList`, finds no boundary in `App`, and has no fallback to show. So the whole page waits for the database, the heading `Inbox` included, and the user sees nothing for one second.

Remember: the component that waits cannot show its own loading line. Its parent shows it.

### The Order in Which React Renders the Inbox

When the user opens the inbox, React renders `App` on the server. It renders the heading, meets the `<Suspense>` boundary, and calls `EmailList` inside it. `EmailList` suspends at `await`, so the fallback shows. When the emails arrive, React resumes `EmailList`, and the list takes the place of the fallback:

```tree dir=right caption="The order in which React renders the components of the inbox on the server."
The order in which React renders the inbox
- +1. `App` [`<h1>Inbox</h1>`] | React renders the heading **at once** | The user sees **`Inbox`** first
- +2. `<Suspense>` and `EmailList` [`await`] | `EmailList` **suspends** at `await` | The boundary shows **`Loading emails...`**
- +3. `EmailList` again [`<ul>`] | After one second React **resumes** `EmailList` | The two emails **replace the fallback**
```

| Principle | What the code does | What the user sees |
| :--- | :--- | :--- |
| **1. `EmailList` awaits the emails** | `async function EmailList` with `await db.emails.getAll()` | The two emails, rendered on the server |
| **2. What `await` replaces** | No `useState`, no `useEffect`, no `fetch`, no `api.js` | The emails in the first page, with no second request |
| **3. `<Suspense>` above `EmailList`** | `<Suspense fallback={<p>Loading emails...</p>}>` in `App` | `Inbox` and `Loading emails...` first, then the emails |

Remember the one sentence of this lesson. **A Server Component waits for its data inside its own body, so the data is already in the first page.**

## For the Interview

> **The Interview Question:** How do Server Components read data with async/await, and what does that replace?

### How to Answer Clearly in 30 Seconds

"A Server Component can be an `async` function that awaits its data right inside its body, for example `const emails = await db.emails.getAll()`. React's docs call it an async component.
1. **How the waiting works:** at `await`, React suspends the component, waits for the promise to resolve, and then resumes rendering with the data. Only the rendered output goes to the browser.
2. **What it replaces:** a Client Component that kept the data, a loading flag, and an error in `useState`. It fetched in `useEffect` after the first render, and it needed an API built only to answer that fetch. Effects don't run on the server, so that first page held only a loading state, and the data came after a second request.
3. **Where the loading line goes:** into the `fallback` of a `<Suspense>` boundary above the async component."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Can a Client Component be async too?"**
   **No.** React's docs: "async components are not supported on the client." A Client Component reads a promise with `use` instead (as seen in Lesson 71). React's docs use this pair for data of lower priority. The Server Component starts the promise without `await` and passes it down, and the Client Component waits for it with `use`. The value the promise gives must be serializable (as seen in Lesson 107). Still, React's docs advise: "Usually, the simplest option is to `await` the Promise where you create it."
2. **"Is fetching in an Effect dead now?"**
   **No.** React's docs list four weak points of fetching in Effects:
   - "Effects don't run on the server", so the first HTML holds only a loading state.
   - It invites network waterfalls. A network waterfall is a chain of requests where each one waits for the one before it: a parent fetches, renders a child, and only then does the child start its own fetch.
   - It gives no way to load data early or keep it in a cache.
   - "It's not very ergonomic": every component repeats the same state and the same guard against race conditions (as seen in Lesson 33).

   And still, React's docs allow it: "You can continue fetching data directly in Effects if neither of these approaches suit you." It fits an app with no framework, and data the user loads after a click. Lesson 128 covers where data fetching should live.
3. **"When does the `await` run: on every request?"**
   **It depends on the data.** For data that belongs to one user, such as an inbox, the Server Component runs for each request on a web server. For data that is the same for every user, such as a page built from a markdown file, it can run once at build time, with no web server at all. Two more points belong to later lessons. Two `await` lines in a row wait one after the other, as Lesson 138 shows. And the same read, called twice in one render, can be shared with `cache`, as Lesson 123 shows.

```tree dir=right caption="Interview summary: how an async Server Component reads data, and what it replaces."
Reading data in a Server Component
- +`async` and `await` [`async function EmailList`] | React **suspends** the component at `await` | React **resumes rendering** with the data and sends **only the output**
- !What it replaces [`useState` `useEffect` `fetch` `api.js`] | State, an Effect, and **an API** built for one fetch | A first page with **only a loading state**
- +Where the loading line goes [`<Suspense fallback>`] | A boundary **above** the async component | React shows the fallback **while the component waits**
```
