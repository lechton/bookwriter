# Lecture 86: How a Weather Chart Cleans Up After Its `<div>` Leaves

*(How does a ref callback stop the work it started when its DOM node leaves the page?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How do React 19 ref cleanup functions work, and how do they eliminate memory leaks?

---

## VS | A Ref Callback That Waits for `null` vs. a Ref Callback That Returns a Cleanup: in React 19, the setup hands React its own undo

> When you hand a `<div>` to a chart library, the library draws into it and often starts listening to the browser window too, and React knows nothing about that listener. **In React 19, the ref callback that receives the `<div>` can return a cleanup function, and React calls that function the moment the `<div>` leaves the page.** React removes only the elements it built from your JSX, so whatever the ref callback starts, the function it returns must stop.

At work, many parts of a page are not written in React: a chart library, a map, a video player. They all ask for the same thing: "Give me an empty DOM element, and I will fill it." Many of them also start work outside that element. A chart library, for example, adds a listener to `window`, so it can redraw the chart when the user makes the window wider or narrower.

Remember `addEventListener` from plain JavaScript? Every `addEventListener` has a partner, `removeEventListener`. If your code adds a listener and never removes it, the listener stays on `window` as long as the tab is open, and it keeps alive every object it uses.

Take a weather page with two tabs, `Today` and `Week`. The `Week` tab shows a chart, drawn by a chart library into a `<div>`. Every time the user opens `Week`, a chart starts. Every time the user goes back to `Today`, the `<div>` leaves the page. Ask yourself: who stops the chart?

**Why:** React removes the `<div>` by itself, because React built it from your JSX. But React never saw the `addEventListener` call inside the chart library, so React cannot undo it. Only your code can tell the library to stop, with a call such as `chart.destroy()`. See the problem? Your code needs to hear the exact moment the `<div>` leaves. In React 19, the ref callback gives you that moment: return a function from it, and React calls that function when the `<div>` leaves.

### Back to plain JavaScript

In plain JavaScript, you do both halves yourself. You grab the element, you start the chart, and later you destroy it:

```js title="Plain JavaScript: you start the chart, and you destroy it"
const div = ~document.getElementById('chart')~; // You grab the element yourself
const chart = createChart(div); // The library draws into the div and listens to window
~chart.destroy()~; // When the chart must go: you remove the listener yourself
```

In React, you never grab the `<div>`. React creates it from your JSX, and React removes it. A ref callback is how you ask React: "When you put this `<div>` on the page, call my function with it." In React 19, that function can return a second function, which says: "When you take this `<div>` off the page, call this one."

```jsx title="React 19: the ref callback starts the chart, and the function it returns destroys it"
<div
  ref={(node) => {
    const chart = ~createChart(node)~; // React calls the ref callback when the div is added to the page
    return () => ~chart.destroy()~; // React calls this function when the div is removed
  }}
/>
```

> [!DEFINITION]
> **What is a ref callback?** [REVIEW] In Lesson 31, you passed an object to `ref`: `ref={inputRef}`, and React put the element into `inputRef.current`.
> You can also pass a function to `ref`. Then React fills no object. It calls your function and hands it the DOM node, the real `<div>` element it just added to the page.
> That is the moment to start work on the element, such as drawing a chart into it (Lesson 47).

> [!DEFINITION]
> **What is a ref cleanup function?** [NEW] It is the function that a ref callback returns. React keeps it, and calls it when the `<div>` leaves the page.
> React's docs: "When the `ref` is detached, React will call the cleanup function."
> React 19 added it. Before React 19, React ignored whatever a ref callback returned (Lesson 86).

### The same idea as an Effect's cleanup

The returned function looks familiar. An Effect's setup also returns a cleanup that undoes it (Lesson 32).

For the shape, it is the exact same thing. A setup starts something, and the function it returns stops it. In development, Strict Mode tests both in the same way: setup, cleanup, and setup again (Lesson 47).

For the moment they run, it is NOT the same thing. An Effect follows the component and its dependencies. A ref callback follows one DOM node: React calls it when that node is added to the page, and calls its cleanup when that node is removed. On our weather page, the `<div>` comes and goes while the component stays on the page. Principle 5 shows what this changes.

### The Rule of Thumb: what did the ref callback start?

**Whatever the ref callback starts outside React, the function it returns must stop.** React calls that function at the right moment. What it removes is up to your code.

What is at stake is a page that looks right while the work behind it keeps growing:
1. The user opens `Week`, and the chart appears. The user goes back to `Today`, and the chart's `<div>` is gone.
2. Without a cleanup, the chart library still listens to the window for a `<div>` that no longer exists. Each visit to `Week` adds one more listener.
3. After a few visits, the page shows one chart, but several charts are still alive. One resize of the window redraws every one of them.

React's docs call a list that keeps growing this way "a memory leak that can cause performance problems in a real app" (Lesson 47).

A senior developer also knows the three classic mistakes:
1. **Thinking React cleans up everything tied to the `<div>`.** React removes the `<div>`. The browser can then free the `<div>` and whatever only the `<div>` holds, which is called garbage collection. But the listener on `window` stays on `window`, and it keeps the chart alive.
2. **Handling only the call with the node.** In the old shape, the developer writes the `if (node)` branch that creates the chart, and forgets the call with `null`.
3. **Writing the ref callback as an arrow function inside `ref`.** Then React calls it again after a click that has nothing to do with the chart.

The rest of the lesson shows each one on a real weather page.

A real chart library would draw bars or a curve. In this lesson, a small file of our own plays the part of the library, and writes the week as one line of text. That is why the chart in every preview is one line of days.

`weather-chart.js` is a stand-in: a small file of our own that does the three things a real chart library does that matter here (Lesson 47):
1. **It draws into the `<div>`.** It writes the week as text.
2. **It listens to the window.** It adds a `resize` listener to `window`.
3. **It counts the charts that are still alive.** The page cannot show this number, so the stand-in logs it in the Console.

At work, you will meet three ways to start work on one DOM node and stop it when the node leaves:
1. **A ref callback that returns a cleanup.** It fits when the work belongs to one node, above all a node that appears and leaves inside a component, or one node per row of a list, where `useRef` cannot be called inside `map()`. This is the React 19 way, and the way this lesson builds.
2. **`useRef` plus `useEffect` with a cleanup.** It fits when the work must also follow props or state over time, as a map widget follows its zoom level (Lesson 32).
3. **The old ref callback that waits for `null`.** You will meet it in code written before React 19. It still works, and React's docs say it will be removed in a future version. Principle 1 starts there.

**PRINCIPLES:** React calls a ref callback with the DOM node when the node is added to the page. Whatever the callback starts there, your code must stop when the node leaves. Five principles follow:
1. **Principle 1: A ref callback with no return is called again with `null`.** The callback must check which call it got, and keep the chart in a ref, so the call with `null` can destroy it.
2. **Principle 2: A returned function destroys the chart it created.** React calls it when the `<div>` leaves and skips the call with `null`. The cleanup sees the exact chart its own setup created.
3. **Principle 3: Curly braces keep the ref callback from returning the node.** A one-line arrow function returns its value by accident, and TypeScript rejects it.
4. **Principle 4: The same function on every render leaves the chart alone.** An arrow function written inside `ref` is new on every render, so a click on `Save` destroys and rebuilds the chart.
5. **Principle 5: The ref cleanup follows the `<div>`, the Effect cleanup follows the component.** A `<div>` that appears after a click starts the ref callback, and does not start an Effect with `[]`.

## PRINCIPLE | Ref callback with no return: React calls it again with `null` when the `<div>` leaves

> [!PRINCIPLE]
> **Principle 1: The Call with null: A Ref Callback Without a Cleanup Hears the Node Leave Through null**
>
> *When a ref callback returns no function, React calls the same callback again with `null` when the `<div>` leaves; destroy the chart in that call.*
>
> React 19 still makes this second call for backwards compatibility, and its docs say the call will be removed in a future version. The call that created the chart is over by then, so the chart must wait in a ref. A callback that handles only `if (node)` creates a chart on every visit and never destroys one: the page shows one chart while the window keeps redrawing all of them.
>
> **DO THIS:**
> ```jsx
> ref={(node) => {
>   if (node) {
>     chartRef.current = createChart(node);
>   } ~else~ { // The call with null destroys the chart we kept
>     chartRef.current.destroy();
>   }
> }}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ref={(node) => {
>   ~if (node)~ { // **WRONG:** the call with null does nothing, so every chart stays alive
>     createChart(node);
>   }
> }}
> ```

### One function, called with the node and then with `null`

We start with the two tabs and a `<div>` whose ref callback only logs what React hands it. The `<div>` is on the page only while `tab` is `'week'` (Lesson 10):

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [tab, setTab] = useState('today');

  return (
    <main>
      <h1>Paris</h1>
      <nav>
        <button onClick={() => setTab('today')}>Today</button>
        <button onClick={() => setTab('week')}>Week</button>
      </nav>
      {tab === 'today' && <p>18°</p>}
      {~tab === 'week' &&~ ( // The div is on the page only while tab is 'week'
        <div
          className="chart"
          ref={(node) => {
            ~console.log('Called with', node)~; // Logs what React hands the ref callback
          }}
        />
      )}
    </main>
  );
}
```

The user clicks `Week`, and then `Today`. The Console shows four calls:

```page width=text caption="The page after the user clicks Week and then Today: the div is gone, and the Console shows four calls."
heading: Paris
line: [Today] [Week]
line: 18°
log: Called with <div class="chart"></div> | App.jsx:18
log: Called with null | App.jsx:18
log: Called with <div class="chart"></div> | App.jsx:18
log: Called with null | App.jsx:18
```

**React calls the same function with the `<div>`, and later with `null`.** Here is the order:
1. The user clicks `Week`. React adds the `<div>` to the page and calls the ref callback with it.
2. In development, Strict Mode tests the ref callback once more (Lesson 47). It calls the callback with `null`, and then with the `<div>` again.
3. The user clicks `Today`. React renders `App` again, the condition on the tab now gives nothing, and React removes the `<div>`. The callback returned no function, so React calls the same callback again, with `null`.

React's docs have two words for these two moments. When React connects the ref to the node, the ref is **attached**. When React disconnects it, the ref is **detached**. Without a cleanup, the call with `null` is the only way your code hears that the ref was detached.

Why does React 19 still make this call? For **backwards compatibility**: code written for older versions of React waits for it, and that code must keep working. React's docs add: "This behavior will be removed in a future version."

### The chart stand-in

Now the `<div>` gets a real job. Here is our stand-in for the chart library:

```js title="src/weather-chart.js"
let activeCharts = 0;

export function createChart(node) {
  node.textContent = 'Mon 18° Tue 20° Wed 17° Thu 19° Fri 21° Sat 22° Sun 20°';
  function redraw() {
    console.log('Chart redrawn');
  }
  ~window.addEventListener('resize', redraw)~; // The listener lives on window, outside the div
  activeCharts += 1;
  console.log('Chart created. Active charts: ' + activeCharts);
  return {
    destroy() {
      ~window.removeEventListener('resize', redraw)~; // Only destroy removes the listener
      activeCharts -= 1;
      console.log('Chart destroyed. Active charts: ' + activeCharts);
    },
  };
}
```

`createChart` returns an object with one method, `destroy`. Only `destroy` removes the listener from `window` and takes the chart off the count. `App.jsx` imports `createChart` from this file on its second line.

### Creating the chart without destroying it

A developer writes the first version. It creates the chart when the node arrives, and does nothing else:

```jsx title="src/App.jsx" startLine="15"
      {tab === 'week' && (
        <div
          className="chart"
          ref={(node) => {
            ~if (node)~ { // **WRONG:** handles only the call with the div; the call with null does nothing
              createChart(node);
            }
          }}
        />
      )}
```

The user clicks `Week`, then `Today`, then `Week` again. The page shows one chart. The Console counts four:

**Beware! The page shows one chart, but four charts are alive and listening to the window.** Each click on `Week` creates two charts, and the code never destroys one:
1. The user clicks `Week`. React calls the ref callback with the `<div>`, and the first chart is created.
2. Strict Mode calls the callback with `null`. The `if` skips this call, so the first chart stays alive.
3. Strict Mode calls the callback with the `<div>` again. A second chart is created in the same `<div>`.
4. The user clicks `Today`. React removes the `<div>` and calls the callback with `null`. The `if` skips this call too.
5. The user clicks `Week` again, and steps 1 to 3 run again. The count reaches four.

Now the user makes the window a little wider. The browser runs every `resize` listener, so the Console prints `Chart redrawn` four times for the one chart on the page. Two of those charts belong to the first `<div>`, which is no longer on the page. One more is the extra copy that Strict Mode's test left in the current `<div>`.

Strict Mode made the bug show on the very first click (Lesson 47). In production, without Strict Mode, each click on `Week` adds one chart instead of two, and the count still never goes down.

### VS | Without the `else` Branch vs. With It: only the `else` branch destroys the chart

The fix has two parts:
1. **The call with `null` must destroy the chart.** That is the `else` branch.
2. **That call must find the chart.** By the time React calls with `null`, the call that created the chart is over, and its variables are gone. So the old way keeps the chart in a ref, which keeps a value between renders (Lesson 30).

`useRef` joins `useState` in the import on line 1:

```jsx title="src/App.jsx" startLine="5"
  const [tab, setTab] = useState('today');
  const ~chartRef~ = useRef(null); // Keeps the chart between the call with the div and the call with null
```

```jsx title="src/App.jsx" startLine="16"
      {tab === 'week' && (
        <div
          className="chart"
          ref={(node) => {
            if (node) {
              ~chartRef.current = createChart(node)~; // The call with the div: create the chart and keep it
            } ~else~ { // The call with null: destroy the chart we kept
              chartRef.current.destroy();
            }
          }}
        />
      )}
```

The user clicks `Week`, then `Today`, then `Week` again. The count never goes above one:

```page width=text caption="With the else branch, after the user clicks Week, Today, and Week again: one chart on the page, one live chart in the Console."
heading: Paris
line: [Today] [Week]
line: Mon 18° Tue 20° Wed 17° Thu 19° Fri 21° Sat 22° Sun 20°
log: Chart created. Active charts: 1 | weather-chart.js:10
log: Chart destroyed. Active charts: 0 | weather-chart.js:15
log: Chart created. Active charts: 1 | weather-chart.js:10
log: Chart destroyed. Active charts: 0 | weather-chart.js:15
log: Chart created. Active charts: 1 | weather-chart.js:10
log: Chart destroyed. Active charts: 0 | weather-chart.js:15
log: Chart created. Active charts: 1 | weather-chart.js:10
```

Both versions draw the same chart on the page. It may look the same, but it is NOT the same thing! With the `else` branch, every call with `null` destroys the chart and removes its listener. Without it, the call with `null` does nothing, and every chart stays alive.

The fix works, but it asks you to keep two things in step:
1. **The chart lives in `chartRef`**, a second place outside the function.
2. **One function does two jobs**, told apart only by `if (node)`. The job that undoes the setup is easy to forget.

```tree caption="The old ref callback that waits for null, without the else branch and with it."
One ref callback, two calls from React
- !Without the `else` branch [`if`] | The call with the div **creates a chart** | The call with `null` **does nothing**, so every chart **stays alive**
- +With the `else` branch and `chartRef` [`if` `else` `chartRef`] | The call with the div **creates the chart and keeps it in a ref** | The call with `null` **destroys the kept chart**
```

One more detail. An object ref from `useRef`, written as `ref={divRef}`, never needs this branch. When the `<div>` leaves, React sets `divRef.current` back to `null` by itself (Lesson 31). The call with `null` matters only when the ref is a function that started some work.

## PRINCIPLE | Ref callback that returns a function: React calls it when the `<div>` leaves, and it destroys the exact chart it created

> [!PRINCIPLE]
> **Principle 2: Ref Cleanup: The Returned Function Destroys the Chart It Created**
>
> *In React 19, return a cleanup function from the ref callback that undoes exactly what the setup started; React calls it when the `<div>` leaves and skips the call with `null`.*
>
> The setup creates the cleanup in the same call, so the cleanup sees the chart and the node of that setup. There is no ref to carry the chart and no branch for `null` to forget. React undoes nothing by itself: an empty cleanup is called at the right moment and leaves every listener running.
>
> **DO THIS:**
> ```jsx
> ref={(node) => {
>   const chart = createChart(node);
>   return ~() => chart.destroy()~; // Removes the window listener of this exact chart
> }}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ref={(node) => {
>   createChart(node);
>   return ~() => {}~; // **WRONG:** React calls it when the div leaves, and nothing is destroyed
> }}
> ```

### The setup returns its own undo

In React 19, the ref callback can return the undo itself:

```jsx title="A ref callback that returns its own cleanup"
ref={(node) => {
  const chart = createChart(node);
  return ~() => chart.destroy()~; // React keeps this function and calls it when the div leaves
}}
```

When the `<div>` leaves, React calls the returned function. Because the callback returned a function, React also skips the call with `null`. So inside this ref callback, the node is always the real `<div>`, and the callback needs no `if` check.

### VS | The `null` Branch vs. the Returned Function: the same result for the user, half the parts in the code

Here are the two ways side by side:

```jsx title="With the null branch and chartRef"
ref={(node) => {
  if (node) {
    chartRef.current = createChart(node);
  } else {
    ~chartRef.current.destroy()~; // The chart must come back from the ref
  }
}}
```

```jsx title="With the returned cleanup"
ref={(node) => {
  const chart = createChart(node);
  return () => ~chart.destroy()~; // The chart is right here, in the same function
}}
```

For the user and for the Console count, it is the exact same thing. Both create the chart when the user clicks `Week`, both destroy it when the user clicks `Today`, and the count never goes above one.

For the code, it is NOT the same thing:
1. **The `null` branch** is one function with two jobs, plus a ref that carries the chart from one call to the next.
2. **The returned function** is one setup that hands React its own undo. There is no ref to keep in step, and no branch to forget.

### Why the cleanup still sees `chart`

The cleanup runs much later, when the user clicks `Today`. By then, the ref callback that created `chart` finished long ago. So how does the cleanup still reach that exact chart?

Because a function sees the variables of the place where it was created (Lesson 15). The cleanup was created inside the same call as `chart`:
1. React calls the ref callback with the `<div>`.
2. The callback creates `chart`. In the same run, it creates the arrow function `() => chart.destroy()`.
3. The callback returns that arrow function, and React keeps it.
4. When the `<div>` leaves, React calls the arrow function, and it destroys the exact chart that its own setup created.

For the same reason, a cleanup that logs `node` logs the `<div>` that was attached, never `null`.

So the cleanup is not a second callback that React runs on its own. Your setup creates it. React only keeps it and calls it at the right moment.

### The returned cleanup on our page

In `App.jsx`, the ref and the `if` check are gone, and so is `useRef` in the import. The stand-in file does not change:

```jsx title="src/App.jsx"
import { useState } from 'react';
import { createChart } from './weather-chart.js';

export default function App() {
  const [tab, setTab] = useState('today');

  return (
    <main>
      <h1>Paris</h1>
      <nav>
        <button onClick={() => setTab('today')}>Today</button>
        <button onClick={() => setTab('week')}>Week</button>
      </nav>
      {tab === 'today' && <p>18°</p>}
      {tab === 'week' && (
        <div
          className="chart"
          ref={(node) => {
            const chart = ~createChart(node)~; // The setup: draws the chart and starts the window listener
            return ~() => chart.destroy()~; // The cleanup: removes the listener of this exact chart
          }}
        />
      )}
    </main>
  );
}
```

The user clicks `Week` once. In development, the Console shows a chart created, destroyed, and created again:

```page width=text caption="With the returned cleanup, after one click on Week in development: Strict Mode's extra test ends at one live chart."
heading: Paris
line: [Today] [Week]
line: Mon 18° Tue 20° Wed 17° Thu 19° Fri 21° Sat 22° Sun 20°
log: Chart created. Active charts: 1 | weather-chart.js:10
log: Chart destroyed. Active charts: 0 | weather-chart.js:15
log: Chart created. Active charts: 1 | weather-chart.js:10
```

This is the same Strict Mode test as in Principle 1: setup, cleanup, setup. React's docs call it a check that the cleanup "mirrors" the setup. Our cleanup does, so the test ends at one live chart. When the user then clicks `Today`, the Console adds `Chart destroyed. Active charts: 0`.

### A cleanup undoes only what you write in it

The interview question asks how ref cleanups eliminate memory leaks. Here is the honest answer: a ref cleanup removes nothing by itself. React calls it at the right moment. It removes only what your code tells it to remove.

So a cleanup that is returned but does nothing still leaks. React calls the empty cleanup when the `<div>` leaves, skips the call with `null`, and nothing at all is undone. React's docs show this case and say of it: "This is a production bug!" (Lesson 47).

The rule is the one Effects follow: the cleanup must stop or undo whatever the setup started. On our page, that is the window listener and the count.

```tree dir=right caption="The life of one chart on our page, with the returned cleanup."
One visit to the Week tab
- +1. The user clicks Week [`createChart`] | React adds the div and **calls the ref callback with it** | The setup **creates `chart`** and **returns its own cleanup**
- +2. React keeps the cleanup | The cleanup **sees `chart`** because it was **created in the same call** | `chartRef` and the **call with `null`** are **not needed**
- +3. The user clicks Today [`destroy`] | React removes the div and **calls the kept cleanup** | That exact chart **stops listening to the window**
```

The cleanup is not only for DOM nodes. React's announcement says it "works for DOM refs, refs to class components, and `useImperativeHandle`". It also runs when the whole component that holds the `<div>` unmounts, because the `<div>` leaves the page with it.

## PRINCIPLE | `node => { ... }` with curly braces: the ref callback returns nothing or a cleanup, never the node by accident

> [!PRINCIPLE]
> **Principle 3: Block Bodies: A Ref Callback Returns Nothing or a Cleanup**
>
> *Write a ref callback with curly braces, so that it returns either nothing or a cleanup function, never a value by accident.*
>
> React 19 reads what a ref callback returns as its cleanup. An arrow function with parentheses returns the value of its body, so `current => (instance = current)` hands the node back to React. TypeScript cannot tell whether that node was meant as a cleanup, so it rejects the line.
>
> **DO THIS:**
> ```jsx
> <div ref={current => ~{instance = current}~} /> {/* Curly braces: returns nothing */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <div ref={current => ~(instance = current)~} /> {/* **WRONG:** returns the node, which TypeScript rejects as a cleanup */}
> ```

### VS | Parentheses vs. Curly Braces After the Arrow: one returns the node, the other returns nothing

Before React 19, React ignored whatever a ref callback returned. So a lot of older code stores the node in one short line. React's docs show it in two forms:

```jsx title="Storing the node with parentheses, and with curly braces"
<div ref={current => ~(instance = current)~} /> {/* Parentheses: stores the node, and returns it */}
<div ref={current => ~{instance = current}~} /> {/* Curly braces: stores the node, and returns nothing */}
```

Both lines put the node into `instance`. It may look the same, but it is NOT the same thing! The first line also returns the node.

Why? An arrow function whose body sits in parentheses returns the value of that body (Lesson 18). Here the body is an assignment, and in JavaScript an assignment has a value: the value it stored. So the first line hands the node back to React. The second line has a body in curly braces with no `return`, so it hands back nothing.

### Why React 19 cares about the return value

In React 19, the value a ref callback returns has a meaning: it is the cleanup. So a value returned by accident is now a value that React and TypeScript look at.

TypeScript cannot know what you meant. React's announcement says: "TypeScript wouldn't know if this was *supposed* to be a cleanup function or if you didn't want to return a cleanup function." So React 19's types reject the line: "returning anything else from a `ref` callback will now be rejected by TypeScript."

A team meets this on the day it moves to React 19:
1. Code written for React 18 stores the node with `current => (instance = current)`.
2. The team moves to React 19 and runs TypeScript.
3. TypeScript rejects the line, because the callback returns an `HTMLDivElement`, the type of a `<div>` node, and not a cleanup function.
4. The team adds curly braces, so the callback returns nothing, and TypeScript accepts it.

React's docs give the fix in one sentence: "The fix is usually to stop using implicit returns." They also name a codemod, a script that rewrites the code for you, called `no-implicit-ref-callback-return`.

```tree caption="The same one-line ref callback with parentheses and with curly braces, in React 19."
What the ref callback hands back to React
- !Parentheses after the arrow | Stores the node **and returns it** | TypeScript **rejects it**: the node is **not a cleanup**
- +Curly braces after the arrow | Stores the node **and returns nothing** | React uses the **call with `null`** when the div leaves
```

This is the rule Effects already follow: an Effect's setup may return only a cleanup function or nothing (Lesson 32). A ref callback now follows it too.

## PRINCIPLE | `ref={attachChart}`: the same function on every render, so a re-render leaves the chart alone

> [!PRINCIPLE]
> **Principle 4: The Same Function Reference: Clicking Save Leaves the Chart Alone**
>
> *When the setup is costly, pass the same function to `ref` on every render, written outside the component or kept with `useCallback`.*
>
> An arrow function written inside `ref` is a new function on every render. After each re-render, React detaches the old ref callback and attaches the new one, so it runs the old cleanup and the new setup on the same `<div>`. The cleanup keeps the count right, so this is not a leak, but every unrelated state change throws the chart away and builds it again.
>
> **DO THIS:**
> ```jsx
> function attachChart(node) {
>   const chart = createChart(node);
>   return () => chart.destroy();
> }
>
> <div ~ref={attachChart}~ /> {/* The same function on every render: Save leaves the chart alone */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <div
>   ref={~(node) => {~ // **WRONG:** a new function on every render, so Save destroys and rebuilds the chart
>     const chart = createChart(node);
>     return () => chart.destroy();
>   }}
> />
> ```

### A Save button that has nothing to do with the chart

A real weather page lets the user save the city. We add a `Save` button under the title. When the user clicks it, its label turns to `Saved`:

```jsx title="src/App.jsx" startLine="4"
export default function App() {
  const [tab, setTab] = useState('today');
  const [saved, setSaved] = useState(false);

  return (
    <main>
      <h1>Paris</h1>
      <button ~onClick={() => setSaved(true)}~>{saved ? 'Saved' : 'Save'}</button> {/* Changes saved, not tab */}
```

The rest of `App.jsx` stays as Principle 2 left it, with the ref callback written as an arrow function inside `ref`.

The user opens `Week`, and the chart is live. Then the user clicks `Save`. The label turns to `Saved`, and the Console shows two new lines under the three lines of Strict Mode's test from the click on `Week`:

```page width=text caption="The Week tab after the user clicks Save: the label says Saved, and the last two Console lines show the chart destroyed and created again."
heading: Paris
line: [Saved]
line: [Today] [Week]
line: Mon 18° Tue 20° Wed 17° Thu 19° Fri 21° Sat 22° Sun 20°
log: Chart created. Active charts: 1 | weather-chart.js:10
log: Chart destroyed. Active charts: 0 | weather-chart.js:15
log: Chart created. Active charts: 1 | weather-chart.js:10
log: Chart destroyed. Active charts: 0 | weather-chart.js:15
log: Chart created. Active charts: 1 | weather-chart.js:10
```

**The `<div>` never left the page, yet React destroyed the chart and built it again.** Here is why:
1. The user clicks `Save`. `setSaved(true)` makes React render `App` again.
2. This render runs the body of `App` again, so it creates a new arrow function for `ref`. Every render creates every function written inside the component again (Lesson 15).
3. React compares the new ref callback with the one it kept from the last render. They are two different functions.
4. So React detaches the old ref callback: it calls the old cleanup, and the chart is destroyed.
5. Then React attaches the new ref callback: it calls it with the same `<div>`, and a new chart is created.

React's docs warn about exactly this. Unless you pass "the same function reference for the `ref` callback on every render", React cleans up the callback and calls it again during every re-render of the component.

The count still ends at one, so the Console count looks right. This is not a leak. The cost is the work. Every state change in `App`, such as a click on `Save`, throws the chart away and builds it again. Our stand-in only writes the same text again, so the page looks the same. A real chart library builds the whole chart again from the start.

Without a cleanup, the old shape has the same problem: on every re-render, React calls the old callback with `null` and the new one with the `<div>`.

### VS | An Arrow Inside `ref` vs. a Function Written Outside the Component: only the second is the same function on every render

React leaves the ref alone when it gets the same function on every render. A **function reference** is the function itself, passed by its name without calling it, such as `ref={attachChart}`. When the name always points to the same function, React compares it with the one from the last render, sees the same function, and does nothing.

Our ref callback uses nothing from inside `App`. So we can write it once, above the component, where JavaScript creates it only once, when the file loads:

```jsx title="src/App.jsx" startLine="4"
function ~attachChart~(node) { // Written once, when the file loads: the same function on every render
  const chart = createChart(node);
  return () => chart.destroy();
}
```

```jsx title="src/App.jsx" startLine="22"
      {tab === 'week' && <div className="chart" ~ref={attachChart}~ />} {/* The same function reference on every render */}
```

The user opens `Week` and clicks `Save`. The label turns to `Saved`, and the Console shows nothing new:

```page width=text caption="With ref={attachChart}, the Week tab after the user clicks Save: the label says Saved, and the chart is left alone."
heading: Paris
line: [Saved]
line: [Today] [Week]
line: Mon 18° Tue 20° Wed 17° Thu 19° Fri 21° Sat 22° Sun 20°
log: Chart created. Active charts: 1 | weather-chart.js:10
log: Chart destroyed. Active charts: 0 | weather-chart.js:15
log: Chart created. Active charts: 1 | weather-chart.js:10
```

The three lines are the Strict Mode test from the click on `Week`. The click on `Save` adds none.

When the user switches tabs, the arrow inside `ref` and `attachChart` do the exact same thing. When the user clicks `Save`, they are NOT the same thing. `attachChart` is the same function on every render, so React sees no new ref callback when only `saved` changes, and leaves the chart alone.

Sometimes the ref callback must read something from the component, such as a city that arrives as a prop. Then it cannot live outside the component. In that case, `useCallback` keeps the same function between renders, and makes a new one only when what it reads changes (Lesson 57).

```tree caption="The ref callback written as an arrow inside ref, and written once outside the component, when the user clicks Save."
What React does with the chart when the user clicks Save
- !An arrow written inside `ref` | Every render **creates a new function** | React **calls the old cleanup** and **the new callback**: the chart is **destroyed and built again**
- +A function written outside the component [`attachChart`] | Every render passes the **same function reference** | React **leaves the ref alone**: the chart **stays as it is**
```

## PRINCIPLE | Ref callback, not `useEffect`: the work starts and stops with the `<div>`, not with the component

> [!PRINCIPLE]
> **Principle 5: The Right Moment: The Ref Cleanup Follows the div, the Effect Cleanup Follows the Component**
>
> *Use a ref callback for work that starts and stops with one DOM node, and an Effect for work that follows the component and its dependencies.*
>
> Both return the same kind of cleanup, and Strict Mode tests both the same way. But React calls a ref callback when its `<div>` is attached or detached, while an Effect runs after the component mounts and again only when a dependency changes. A `<div>` that appears after a click inside the same component starts the ref callback and never starts an Effect with `[]`.
>
> **DO THIS:**
> ```jsx
> {tab === 'week' && <div ~ref={attachChart}~ />} {/* Runs each time the div is attached */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   if (!divRef.current) return;
>   const chart = createChart(divRef.current);
>   return () => chart.destroy();
> }, ~[]~); // **WRONG:** runs once while the page shows Today, so the Week div stays empty
> ```

### The same chart in an Effect

A developer who knows Effects may write the chart another way (Lesson 32): an object ref on the `<div>`, and an Effect that creates the chart and returns its cleanup. The `<div>` may not be on the page, so the developer checks for it first:

```jsx title="The same chart in an Effect, inside App"
const divRef = useRef(null);

useEffect(() => {
  if (!divRef.current) {
    return; // No div on the page: nothing to draw
  }
  const chart = createChart(divRef.current);
  return ~() => chart.destroy()~; // The same cleanup as the ref callback
}, ~[]~); // Runs once, after App mounts

{tab === 'week' && <div className="chart" ref={divRef} />}
```

Both ways return `() => chart.destroy()`. Both pass the same Strict Mode test of setup, cleanup, and setup. It may look the same, but it is NOT the same thing! What differs is what starts them.

### An empty `<div>` on the Week tab

The page opens on `Today`. The user clicks `Week`. The number disappears, and no chart appears:

**The `<div>` is on the page, but no code ever drew a chart into it.** Here is why:
1. The page opens on `Today`, and `App` mounts. There is no `<div>`, so `divRef.current` stays `null` (Lesson 31).
2. The Effect runs after this first commit. It finds no `<div>` and returns.
3. The user clicks `Week`. React adds the `<div>` and puts it into `divRef.current`.
4. But the dependencies are `[]`, and they did not change, so React does not run the Effect again (Lesson 35). No code calls `createChart`.

With `ref={attachChart}`, step 3 draws the chart, because attaching the `<div>` is exactly what makes React call the ref callback.

The developer can make the Effect work. Adding `tab` to the dependencies makes the Effect run again after every tab change, and the check for a missing `<div>` stays. But now the Effect has to work out when the `<div>` exists. The ref callback says the same thing in one place: run when this `<div>` is attached, and clean up when it is detached.

```tree caption="The same chart started by an Effect inside App and by a ref callback on the div."
What starts the chart when the user clicks Week
- !An Effect with `[]` inside `App` [`useEffect` `divRef`] | Runs **once, after `App` mounts**, when there is **no div** | The click on Week **does not run it again**: the div **stays empty**
- +A ref callback on the div [`attachChart`] | Runs **when the div is attached** and cleans up **when it is detached** | Every click on Week **draws the chart**
```

### When the Effect is the right tool

An Effect is not wrong here. It follows a different thing: the component and its dependencies.
1. **When the `<div>` mounts with its own component**, an Effect with `[]` works. If the chart lived in its own `WeekChart` component, that component would mount together with its `<div>`, and its Effect would find the `<div>` every time.
2. **When the work must follow props or state over time**, an Effect fits better. React's docs show a map widget whose zoom level follows the `zoomLevel` state variable, so an Effect calls the widget again whenever that state changes.

A ref callback fits when the work starts and stops with one DOM node. It is also React's own way for one node per row of a list, because `useRef` cannot be called inside `map()` (Lesson 38).

### The complete files

Here is the finished `App.jsx`. The ref callback is written once, above the component, and returns its own cleanup:

```jsx title="src/App.jsx"

function ~attachChart~(node) { // Principles 2 and 4: one setup that returns its undo, the same function on every render

}

export default function App() {

  const [saved, setSaved] = useState(false);

let activeCharts = 0;

export function createChart(node) {
  node.textContent = 'Mon 18° Tue 20° Wed 17° Thu 19° Fri 21° Sat 22° Sun 20°';
  function redraw() {
    console.log('Chart redrawn');
  }
  window.addEventListener('resize', redraw);
  activeCharts += 1;
  console.log('Chart created. Active charts: ' + activeCharts);
  return {
    destroy() {
      ~window.removeEventListener('resize', redraw)~; // Principle 1: the work outside the div that must be stopped
      activeCharts -= 1;
      console.log('Chart destroyed. Active charts: ' + activeCharts);
    },
  };
}
```

### What React calls, in order

```tree dir=right caption="The order in which React calls attachChart and its cleanup as the user clicks Week, Save, and Today."
`App` with the chart's div on the Week tab
- +1. The user clicks Week [`attachChart`] | React adds the div and **calls `attachChart` with it** | In development, Strict Mode runs **cleanup and setup once more**
- +2. The user clicks Save [`saved`] | React renders `App` again with the **same `attachChart`** | React **leaves the ref alone**: no cleanup, no setup
- +3. The user clicks Today [`destroy`] | React removes the div and **calls the kept cleanup** | The chart **stops listening to the window**: zero live charts
```

### The mistake, and the React rule

| Principle | The Mistake | The React Rule |
| :--- | :--- | :--- |
| **1. The call with `null`** | Handle only `if (node)`, so every visit to `Week` leaves one more chart listening to the window | Without a returned cleanup, destroy the chart when React calls the ref callback with `null`, and keep the chart in a ref until then |
| **2. The returned cleanup** | Keep the chart in a ref and a branch for `null`, or return an empty cleanup | Return a cleanup from the setup; it sees the chart it created, and React skips the call with `null` |
| **3. Block bodies** | Store the node with `current => (instance = current)`, which returns the node | Use curly braces, so the ref callback returns nothing or a cleanup |
| **4. The same function reference** | Write the ref callback as an arrow inside `ref`, so every re-render destroys and rebuilds the chart | Pass the same function on every render, written outside the component or kept with `useCallback` |
| **5. The right moment** | Start the chart in an Effect with `[]` inside a component whose `<div>` appears later | Use a ref callback for work tied to one DOM node, and an Effect for work tied to the component and its dependencies |

Remember the one sentence of this lesson. **Whatever the ref callback starts outside React, the function it returns must stop, and React calls that function the moment the `<div>` leaves the page.**

## For the Interview

> **The Interview Question:** How do React 19 ref cleanup functions work, and how do they eliminate memory leaks?

### How to Answer Clearly in 30 Seconds

"A ref callback is a function in the `ref` attribute that React calls with the DOM node when the ref is attached. In React 19, that function can return a cleanup function, just as an Effect's setup does. React calls the cleanup when the ref is detached, for example when the node leaves the page, and then it skips the old call with `null`. The setup creates the cleanup, so the cleanup already holds the node and whatever the setup created, such as a chart instance. We need no ref and no `if (node)` branch. The cleanup removes a leak only when it undoes what the setup started, such as a listener on the window. Two details matter in practice:
1. **An inline arrow is a new ref callback on every render**, so React runs the cleanup and the setup again after every re-render. Pass the same function reference to avoid that work.
2. **TypeScript now rejects a ref callback that returns anything other than a cleanup**, so stop using implicit returns."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Callback refs used to receive `null` on unmount. Does that still happen in React 19?"**
   Only when the ref callback returns no function. For backwards compatibility, React 19 still calls such a callback a second time with `null` when the ref is detached, and its docs say this behavior will be removed in a future version. When the callback returns a cleanup, React calls the cleanup instead and skips the call with `null`. The cleanup is safer because the setup and its undo live in one function: the cleanup sees the exact chart its setup created, and there is no `else` branch to forget.

2. **"Does a ref cleanup guarantee that there are no memory leaks?"**
   No. React guarantees the moment: it calls the cleanup when the ref is detached, and Strict Mode runs one extra setup and cleanup in development to check that the cleanup mirrors the setup. What the cleanup removes is up to our code. A chart that only draws into its `<div>` would be freed by the browser together with the `<div>`. A chart that listens to `window` stays alive until our cleanup removes that listener. An empty cleanup is called on time and removes nothing.

3. **"When would you use a ref callback with a cleanup instead of `useRef` plus `useEffect`?"**
   When the work starts and stops with one DOM node. A ref callback runs when its node is attached and cleans up when the node is detached. So a node that appears after a click gets its setup and its cleanup at the right moment, and so does one node per row of a list. An Effect runs after the component mounts and again only when a dependency changes, so an Effect with `[]` inside a component whose node appears later never sees the node. The Effect is the better tool when the work must follow props or state, such as a map's zoom level.

```tree caption="Interview comparison: the old call with null, the React 19 ref cleanup, and an Effect cleanup."
Three ways to stop work tied to a DOM node
- !The old call with `null` [`if` `else` `chartRef`] | React calls the **same callback again with `null`** | The chart must live **in a ref**, and the `else` branch is **easy to forget**
- +The React 19 ref cleanup [`return`] | React calls the **returned function when the ref is detached** | The cleanup **sees what its own setup created**
- +An Effect cleanup [`useEffect`] | React calls it **before the Effect runs again** and **when the component unmounts** | Follows **the component and its dependencies**, not one node
```
