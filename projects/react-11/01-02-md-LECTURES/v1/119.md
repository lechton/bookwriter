# Lecture 119: Static Prerendering: Making the About Page Once, Before Anyone Opens It

*(How can React make the HTML of a page once, before any visitor opens it?)*

> INTERVIEW QUESTION | ❱ CORE | What is static prerendering, and when is it the right choice?

---

## VS | `renderToString` in the Request Handler vs. `prerenderToNodeStream` in `build.js`: the same HTML, made for every visitor or made once

> Our server renders the About page again for every visitor who opens it, and every visitor gets exactly the same HTML. **Static prerendering renders that page only once, during the build, and saves the HTML as a file that every visitor gets.** The reason: a page that is the same for everyone needs no React running on a server at each visit, only a file to send.

Remember the first web page you ever made: an `index.html` file. You saved it, put it on a server, and the server sent that same file to whoever asked. No code ran for the visitor. The file was ready before anyone came.

Then we learned server rendering (as seen in Lesson 102), and our server started to run React for every visit:

```jsx title="server.js: the About page, rendered for every visitor"
app.use('/about', (request, response) => {
  response.send(~renderToString(<About />)~); // Runs React again for every visitor who opens the page
});
```

Now look at the About page of our online shop. It shows a heading, `About our shop`, and the two cities where the shop has a store. Anna opens it and sees Paris and Berlin. Ben opens it a minute later and sees exactly the same page. Nothing on it depends on who opens it. Ask yourself: if a thousand visitors get the same HTML, why does React render it a thousand times?

It does not have to. **We can let React render the About page once, before anyone opens it, and save the HTML in a file.** This is static prerendering. It gives us back the plain `index.html` of our first web page, except that React writes the file for us, from our components.

**Why:** A thousand renders in the request handler give a thousand copies of the same HTML. Only the first one does real work; the other 999 repeat it. A saved file needs no React on the server at all. It can come from a **CDN**, a group of servers in many places that keep copies of the same files and send each visitor the nearest copy, or from a **static hosting service**, a host that only stores files and sends them, a static host for short. React's docs say such apps "can be deployed to a CDN or static hosting service without a server."

### When the File Is Made: the Build

> [!DEFINITION]
> **The build.** [NEW] The build is the step where the developer turns the project into the files the site will send, with a command such as `npm run build`, before any visitor comes. It runs once, on the developer's machine or on a build server, and it has no visitor and no request. Its result goes into a folder, here `dist`, and those files are what the site sends (Lesson 119).

So we add one small file, `build.js`, that runs during the build. It renders `About` once and saves the HTML in a file:

```jsx title="build.js: renders the About page once, during the build"
const { prelude } = await ~prerenderToNodeStream(<About />)~; // Runs React once, before any visitor comes
prelude.pipe(createWriteStream('dist/about.html'));
```

The two pieces of code share almost everything. Both run the same `About` component outside the browser. Both turn it into the same HTML. Both are server rendering. **It may look the same to the visitor, but it is NOT the same thing!** The one difference is **when** React runs:
- **`renderToString` in the request handler** runs React once for every visitor.
- **`prerenderToNodeStream` in `build.js`** runs React once in total, and every visitor only gets the saved file.

React's docs say that the first HTML of a page can be made "on the server or during the build", and its name depends on when it is made: **server-side rendering** when React runs for each visitor, and **static site generation**, or SSG, when React runs during the build.

```tree caption="The same About component, rendered at two moments: at each visit, or once during the build."
Two moments when React can render the About page
- !At each visit [`renderToString` in the request handler] | React runs **once for every visitor** | Every run gives **the same HTML** again
- +Once, during the build [`prerenderToNodeStream` in `build.js`] | React runs **once in total**, before any visitor comes | Every visitor gets **the saved file**
```

Here is the one sentence to keep in mind for this whole lesson:

**Static prerendering is server rendering done once, during the build, instead of once for every visitor.**

### The Two Words in the Name

The name of this lesson says exactly what happens:
- **"Prerender"** is "render" with "pre" in front, the same "pre" as in "prepaid". It means rendering before anyone asks for the page.
- **"Static"** means standing still. The saved HTML file does not change from one visitor to the next. React's docs call it **static HTML**.

### Three Ideas From Earlier Lessons

> [!DEFINITION]
> **Server rendering.** [REVIEW] With server rendering, React runs your components outside the browser and turns them into HTML, so the user sees the page before any JavaScript loads. `renderToString(<About />)` returns that HTML as one string, and the request handler sends it with `response.send`. The request handler runs once for every request, so React renders the page once for every visitor (Lesson 102).

> [!DEFINITION]
> **Suspense and use.** [REVIEW] A component reads a Promise with `use`, such as `use(storesPromise)`. While the Promise is still waiting, the component suspends: React cannot render it yet. The nearest `<Suspense>` boundary above it then shows its fallback, such as `Loading stores...`, until the data arrives and React renders the component again with the data (Lessons 69 and 71).

> [!DEFINITION]
> **A stream of HTML.** [REVIEW] A stream hands over HTML in pieces, instead of as one finished string. Node.js has its own kind, the Node.js Stream, and browsers, Deno, and edge runtimes use another, the Web Stream. Code connects a Node.js Stream to a target with `pipe`, such as `pipe(response)`, and the HTML flows into the target piece by piece (Lesson 118).

### Which Pages Can Be Made in Advance

Every page of our shop reaches the visitor as HTML, and developers choose how that HTML is made (as seen in Lesson 103):
1. **The browser renders the page** from an empty root.
2. **The server renders it for each visitor**, with `renderToString` or with a stream (as seen in Lessons 117 and 118).
3. **React renders it once, during the build.** This is static prerendering, this lesson.
4. **React prerenders part of the page and finishes the rest at each request.** This is Partial Pre-rendering, Lesson 120.

React's docs give the rule of fit in one sentence: the landing page of an app "might benefit from being statically generated", while "a page with a content feed might perform best with server-side rendering." Our About page is that kind of landing page. It is the same for everyone, and its stores change maybe once a year.

## SECTION | The About Page of Our Shop

The About page has one heading and a list of two stores:

```page width=text caption="The About page of our shop, exactly the same for every visitor who opens it."
heading: About our shop
line: Paris
line: Berlin
```

The list comes from `db.js`, our stand-in for the database (as seen in Lesson 109), which answers after two seconds. The build saves its result in `dist`, the folder that holds the files the site sends:

```files title="shop: File Explorer" caption="The files of the About page, and the HTML file that build.js makes."
db.js | stand-in for the database | Exports `getStores`, which answers with Paris and Berlin after 2 seconds
Stores.jsx | child | Reads `storesPromise` with `use` and returns one list item per store
About.jsx | page | Returns the whole document: the heading, and the store list inside `<Suspense>`
build.js | build | Runs once, during the build: calls `prerenderToNodeStream` and saves the HTML
dist/
  about.html | output | Made by `build.js`: the file that every visitor gets
```

The page has nothing to click. So it loads no script in the browser, and React never runs there either. The whole lesson stays on one question: where and when the HTML is made.

**PRINCIPLES:** Static prerendering is server rendering done once, during the build, instead of once for every visitor. Three principles follow:
1. **`prerenderToNodeStream` in `build.js`: React renders the page once.** It gives back a Promise of `{ prelude, postponed }`, and the build saves `prelude` as the HTML file that every visitor gets.
2. **`prerenderToNodeStream` waits for the data.** It finishes only after every `<Suspense>` boundary has its content, so Paris and Berlin are in the file. `renderToString` does not wait, and it saves the loading line.
3. **A prerendered file: every visitor gets the same HTML until the next build.** It fits a page that is the same for every visitor, with data known when the site is built. A page that depends on who opens it is rendered at each request.

## PRINCIPLE | `prerenderToNodeStream` in `build.js`: React renders the page once, before any visitor comes

> [!PRINCIPLE]
> **Principle 1: Static Prerendering: `prerenderToNodeStream` Renders the Page Once, During the Build**
>
> *For a page that is the same for every visitor, call `prerenderToNodeStream` or `prerender` once in the build, and save `prelude` as an HTML file that every visitor gets.*
>
> Rendering a page and answering a visitor are two separate steps. A page that never changes needs only one render. The build calls `prerenderToNodeStream`, the Promise resolves to `{ prelude, postponed }`, and the build pipes `prelude` into a file. From then on, each visit only sends that file, and no React runs for the visitor.
>
> **DO THIS:**
> ```jsx
> const { prelude } = await ~prerenderToNodeStream(<About />)~; // build.js: React renders About once, before any visitor
> prelude.pipe(createWriteStream('dist/about.html'));
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> app.use('/about', (request, response) => {
>   response.send(~renderToString(<About />)~); // **WRONG:** the page is the same for everyone, yet React runs again for every visitor
> });
> ```

Here is the smallest `build.js` that makes the About page. For now, `About` returns only the heading:

```jsx title="build.js"
import { ~prerenderToNodeStream~ } from 'react-dom/static'; // The static APIs of React
import { createWriteStream } from 'node:fs';
import About from './About.jsx';

const { ~prelude~ } = await prerenderToNodeStream(<About />); // React renders About once
prelude.pipe(~createWriteStream('dist/about.html')~); // The HTML flows into a file
```

Five lines, and each name comes from a different place:
- **`react-dom/static`** is provided by React. It holds the static APIs, which, in the words of React's docs, "let you generate static HTML for React components."
- **`prerenderToNodeStream`** is provided by React. It does what `renderToString` does, it turns `About` into HTML, but it hands the HTML back as a Node.js Stream.
- **`createWriteStream`** is provided by Node.js, not by React. It opens the file `dist/about.html` for writing. Remember `pipe(response)` from Lesson 118: there, `pipe` sent React's HTML into the response. Here, `prelude.pipe` sends it into the file.
- **`await`** waits for the Promise that `prerenderToNodeStream` gives back (as seen in Lesson 41). `build.js` is a module, so `await` can stand on its own line, outside any function.

Something that can be tricky: `createWriteStream` does not create the folder. The `dist` folder must exist before the build runs. When it is missing, the build stops with an `ENOENT` error, which means: no such file or directory.

`About` returns the whole document, from `<html>` down. React's docs ask for this: the component "is expected to represent the entire document", so it renders the `<html>` tag:

```jsx title="About.jsx"
export default function About() {
  return (
    ~<html>~ {/* The whole document: React adds the doctype above it */}
      <head>
        <title>About our shop</title>
      </head>
      <body>
        <h1>About our shop</h1>
      </body>
    </html>
  );
}
```

### What Happens When the Developer Runs the Build

**React runs for the About page exactly once, when the developer runs the build. After that, no React runs for any visitor, neither on a server nor in the browser.** Here are the steps, in order:
1. The developer runs the build. `build.js` calls `prerenderToNodeStream` with `<About />`.
2. React renders `About`. There is no visitor, no `request`, and no `response`. Nobody has asked for the page yet.
3. The Promise resolves to an object with two fields, `prelude` and `postponed`. Here `postponed` is `null`.
4. `prelude.pipe` writes the HTML into `dist/about.html`, starting with `<!DOCTYPE html>`.
5. Later, Anna opens the About page. The static host sends her the saved file. React does not run for her.
6. The file has no `<script>` tag, because `build.js` passed no `bootstrapScripts` (as seen in Lesson 118). So React does not run in Anna's browser either.

```tree dir=right caption="Two separate moments: React renders once during the build, and each visit only sends the saved file."
From `build.js` to Anna's browser
- +1. The developer runs the build [`build.js`] | React **renders `About` once** | There is **no visitor** and no `request`
- +2. The build saves the HTML [`dist/about.html`] | `prelude` is **piped into the file** | The file starts with **the doctype**
- +3. Anna opens the page | The static host **sends the saved file** | **No React runs** for Anna
```

### VS | `renderToString` vs. `prerenderToNodeStream`: a string right away, or a Promise of an object

Both APIs turn `About` into HTML. What they give back is different:

```jsx title="What renderToString and prerenderToNodeStream give back"
const html = ~renderToString(<About />)~; // A string of HTML, right away
const { prelude, postponed } = await ~prerenderToNodeStream(<About />)~; // A Promise that resolves to an object with two fields
```

Both names say "render", so a developer expects the same kind of result. **It may look the same, but it is NOT the same thing!** Code that expects a string gets a Promise instead. When the Promise resolves, it gives an object with two fields:
- **`prelude`** is the HTML, as a stream. React's docs: "You can use this stream to send a response in chunks, or you can read the entire stream into a string." Our build pipes it into a file.
- **`postponed`** is `null` here. React's docs say `null` means "that the `prelude` contains all the content and no resume is necessary." When `postponed` is not `null`, part of the page is left for later, Lesson 120.

The curly braces in `const { prelude }` take `prelude` out of that object, exactly as they take `name` out of props (as seen in Lesson 08).

### VS | `prerender` vs. `prerenderToNodeStream`: the exact same job, two kinds of stream

React gives two prerender APIs in `react-dom/static`. Both take the same component and give back the same `{ prelude, postponed }`. The one difference is the kind of stream inside `prelude`:

```jsx title="The two prerender APIs, one for each kind of stream"
import { ~prerender~ } from 'react-dom/static'; // prelude is a Web Stream: browsers, Deno, and some edge runtimes
import { ~prerenderToNodeStream~ } from 'react-dom/static'; // prelude is a Node.js Stream: Node.js
```

**Yes, it is the exact same job!** Only the stream differs, the same pair as `renderToReadableStream` and `renderToPipeableStream` (as seen in Lesson 118). Our `build.js` runs in Node.js, so it calls `prerenderToNodeStream`. Node.js also has the Web Stream methods, but React's docs say they "are not recommended due to worse performance."

### What the Saved File Holds

After the build, the saved file holds the document that `About` returned. Here it is, laid out on several lines so it is easy to read:

```html title="dist/about.html"
~<!DOCTYPE html>~ <!-- Added by React: About.jsx never writes it -->
<html>
  <head>
    <title>About our shop</title>
  </head>
  <body>
    <h1>About our shop</h1>
  </body>
</html>
```

React adds the `<!DOCTYPE html>` line by itself. React's docs say React "will inject the doctype" into the HTML stream when the component renders `<html>`.

There is no `<script>` tag anywhere, and that is on purpose. React's docs say about `bootstrapScripts`: "Omit it if you don't want to run React on the client at all." The About page has nothing to click, so it needs no script. It is now the same kind of file as the `index.html` of your first web page.

When Anna opens the page, the browser shows exactly what the file holds:

```page width=text caption="What Anna sees when the static host sends her dist/about.html."
heading: About our shop
```

### Real Beginner Mistake: the About Page Left in the Request Handler

1. A team sets up server rendering, and sends every page through the same `app.use` handler, the About page too.
2. Every visitor of the About page makes the server run `About` again, for the same HTML each time.
3. The page works, so nobody notices. The server simply does the same work over and over.

The fix is to take the About page out of the request handler and put it into `build.js`. No other file changes, and the page can now live on a static host, with no server running React for it.

Remember: static prerendering is server rendering done once, during the build, instead of once for every visitor.

## PRINCIPLE | `prerenderToNodeStream`: the build waits for the data, so the stores are in the file

> [!PRINCIPLE]
> **Principle 2: Waiting for Data: `prerender` Resolves Only After Every Suspense Boundary Has Its Content**
>
> *`prerender` and `prerenderToNodeStream` finish only after every `<Suspense>` boundary has its content, so data read with `use` is inside the file; `renderToString` does not wait and saves the fallback.*
>
> A static page can hold data. The build calls `getStores`, `Stores` suspends while the Promise waits, and `prerenderToNodeStream` keeps waiting until Paris and Berlin arrive. Only then does `prelude` hold the full list. `renderToString` returns at once with the fallback, and on a page with no script, that loading line stays on every visitor's screen. Data fetched in an Effect does not suspend, so `prerender` never waits for it.
>
> **DO THIS:**
> ```jsx
> const { prelude } = await ~prerenderToNodeStream(<About storesPromise={getStores()} />)~; // Waits until the stores are in the HTML
> prelude.pipe(createWriteStream('dist/about.html'));
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const html = ~renderToString(<About storesPromise={getStores()} />)~; // **WRONG:** returns at once, so the saved file says Loading stores... for good
> ```

A static page is just a file. So does it have to be a page with no data from the database? Many developers think so. It is not true. A file made during the build can hold data, as long as the build waits for that data before it writes the file.

Here is our stand-in for the database. It answers after two seconds:

```js title="db.js"
export function ~getStores~() { // Answers with Paris and Berlin after 2 seconds
  return new Promise(resolve => {
    setTimeout(() => resolve(['Paris', 'Berlin']), 2000);
  });
}
```

The build file asks the database for the stores and passes the Promise down to `About`. `About` hands it to a new component, `Stores`, which reads it with `use`:

```jsx title="Stores.jsx"
import { use } from 'react';

export default function Stores({ storesPromise }) {
  const stores = ~use(storesPromise)~; // Suspends until db.js answers
  return (
    <ul>
      {stores.map(store => <li key={store}>{store}</li>)}
    </ul>
  );
}
```

`About` wraps the store list in `<Suspense>`, with a loading line as the fallback:

```jsx title="About.jsx" startLine="10"
<body>
  <h1>About our shop</h1>
  <Suspense ~fallback={<p>Loading stores...</p>}~> {/* Shown while Stores waits for its data */}
    <Stores storesPromise={storesPromise} />
  </Suspense>
</body>
```

Now build the same `About` two ways:

::: row caption="The same About page built with renderToString and with prerenderToNodeStream: only the second waits for the stores."
::: col title="renderToString in build.js" tag="saves the fallback" tone=bad
```page size=mini
heading: About our shop
line: Loading stores... | bad
```
```jsx title="build.js" bad="1"
const html = renderToString(
  <About storesPromise={getStores()} />
);
```
The file holds `Loading stores...` and no store.
:::
::: col title="prerenderToNodeStream in build.js" tag="waits for the stores" tone=good
```page size=mini
heading: About our shop
line: Paris | good
line: Berlin | good
```
```jsx title="build.js" good="1"
const { prelude } = await prerenderToNodeStream(
  <About storesPromise={getStores()} />
);
```
The file holds Paris and Berlin.
:::
:::

Both render `About` on the server, and both save a file. **It may look the same, but it is NOT the same thing!** `renderToString` saves the loading line. `prerenderToNodeStream` waits two seconds and saves the stores. React's docs say it directly: "Unlike `renderToString`, `prerender` waits for all data to load before resolving."

### Why One File Says `Loading stores...` and the Other Lists the Stores

Here is what really happens during each build, step by step:
1. The developer runs the build. `getStores` starts its two-second wait and returns a Promise.
2. React renders `About`. `Stores` reads the Promise with `use`, finds it still waiting, and suspends.
3. **With `renderToString`**, React does not wait. It writes the fallback, `<p>Loading stores...</p>`, in place of the list, and returns the string at once. The saved file holds `Loading stores...`.
4. The About page loads no script, so nothing in Anna's browser ever replaces that line. Anna sees `Loading stores...`, and it stays there for good.
5. **With `prerenderToNodeStream`**, React keeps waiting. After two seconds the stores arrive, and React renders `Stores` again with Paris and Berlin.
6. Only then does the Promise resolve. `prelude` holds the list, and the saved file shows `About our shop`, Paris, and Berlin to every visitor.

```tree dir=right caption="What each build does when Stores suspends: renderToString writes the fallback at once; prerenderToNodeStream waits for the stores."
The build reaches `Stores`, which is still waiting for its data
- !With `renderToString` | **Does not wait**: writes the **fallback** and returns | The file shows **`Loading stores...`** to every visitor
- +With `prerenderToNodeStream` | **Waits** until every `<Suspense>` boundary has its content | The file shows **Paris and Berlin** to every visitor
```

So a file built the wrong way is wrong for every visitor, not just for one. React's docs explain why `renderToString` cannot do the job: it "returns a string immediately, so it does not support waiting for data to load for static HTML generation."

### VS | `use` vs. an Effect: only `use` makes the build wait

**`prerender` waits only for data that makes a component suspend.** React's docs: "Only data read from a source that activates a Suspense boundary, such as a Promise read with `use`, will suspend during rendering. Suspense does not detect data fetched inside an Effect or event handler."

Here are the two ways `Stores` could load the stores:

```jsx title="Reading the stores with use, and fetching them in an Effect"
const stores = ~use(storesPromise)~; // Stores suspends: prerender waits, and the stores are in the file
useEffect(() => { ~getStores().then(setStores)~; }, []); // **WRONG:** Suspense never sees this, so prerender does not wait for it
```

In the developer's mind, both lines do the same job: both ask `db.js` for the stores. **They are NOT the same thing!** Only `use` makes `Stores` suspend, so only `use` makes `prerender` wait. An Effect runs in the browser, after the page is on the screen, and the build is not a browser. With the Effect, `prerender` saves the first render of `Stores`, without the stores, and visitors with no script never see them.

This mistake is common when a team moves its build from `renderToString` to `prerender`, as React's docs advise, while `Stores` still loads its data in an Effect.

### `prerenderToNodeStream` vs. `onAllReady`: the same wait, made for different jobs

`prerenderToNodeStream` reminds many readers of `renderToPipeableStream` with `onAllReady` (as seen in Lesson 118). Both wait until every `<Suspense>` boundary has its content before the HTML is complete. The one difference is what each one is made for. `prerenderToNodeStream` is made for the build, and it gives back `prelude` and `postponed`. `renderToPipeableStream` answers a request. React's docs say `prerender` "is designed for static site generation" ahead of time, and "does not support streaming more content as it loads."

Remember: a static page can hold data, but only data that the build waits for.

## PRINCIPLE | A prerendered file: every visitor gets the same HTML until the next build

> [!PRINCIPLE]
> **Principle 3: The Right Choice: Prerender Only Pages That Are the Same for Every Visitor**
>
> *Static prerendering fits a page that is the same for every visitor and whose data is known when the site is built; a page that depends on who opens it, or on data that changes all the time, is rendered at each request.*
>
> `build.js` runs once and has no visitor, so a static file holds one answer for everyone, made at one moment. That is exactly right for the About page, which can then come from a CDN with no server running React. It is wrong for the account page, which must greet each visitor by name, and for a content feed, whose file would show old data until the next build.
>
> **DO THIS:**
> ```jsx
> const { prelude } = await ~prerenderToNodeStream(<About storesPromise={getStores()} />)~; // The same About page for every visitor
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const { prelude } = await ~prerenderToNodeStream(<Account />)~; // **WRONG:** build.js has no visitor, so nobody is greeted by name
> ```

A saved file is fast and cheap to send. So why not prerender every page of the shop? Because a file is one answer, made once, for everyone.

Our shop has another page that every shopper knows: the account page. It greets the visitor by name. Anna sees `Hi, Anna`, and Ben sees `Hi, Ben`:

::: col title="The About page" tag="one answer for everyone" tone=good
```page size=mini
heading: About our shop
line: Paris
line: Berlin
```
Anna and Ben see the same page.
:::
::: col title="The account page" tag="one answer per visitor" tone=good
```page size=mini
heading: Hi, Anna
```
```page size=mini
heading: Hi, Ben
```
Anna and Ben each see their own name.

Now look at where each page is rendered:

```jsx title="build.js has no visitor; the request handler has one"
const { prelude } = await ~prerenderToNodeStream(<About storesPromise={getStores()} />)~; // build.js: runs once, with no visitor

app.use('/account', (~request~, response) => { // Runs at each visit, with the visitor's request in hand
  response.send(renderToString(<Account />));
});
```

**`build.js` has no visitor.** `prerenderToNodeStream` takes only the component and its options. It receives no `request`, so it cannot know who will open the file. The request handler gets a `request` at each visit, and on a real site the server finds out from it who is asking. How it does that is outside this lesson.

Both pages are rendered by React on the server, but they are NOT the same thing! The About page has one answer for everyone, made once. The account page has one answer per visitor, made at the moment that visitor asks.

### Real Beginner Mistake: the Account Page in `build.js`

A team learns that static files are cheap and fast to send, and moves the account page into `build.js` too. **Nobody is greeted by name.** Here is why:
1. The team adds the account page to `build.js`, beside the About page.
2. `build.js` runs once. There is no visitor, so there is no name to greet.
3. Whatever `Account` renders at that moment is saved in the file.
4. Anna and Ben both open the account page and get that same file. Neither sees `Hi, Anna` or `Hi, Ben`.

React prints no error, so the page is wrong without any warning. The team moves the account page back to the request handler, and keeps in `build.js` only the pages that are the same for everyone.

### A New Store Opens in Rome

A static file is the same for every visitor, and it is also the same over time. It shows what was true when the site was built.

Suppose the shop opens a store in Rome, and the database now has three stores:

```js title="db.js" startLine="3"
setTimeout(() => resolve(~['Paris', 'Berlin', 'Rome']~), 2000); // The database now has three stores
```

Anna opens the About page the next morning. She still sees two stores, and Rome is missing:

```page width=text caption="The About page after Rome was added to db.js, before a new build."
heading: About our shop
line: Paris
line: Berlin
```

The saved file was made before Rome existed, and nothing has made it again. Rome appears only after the developer runs the next build:

```page width=text caption="The About page after the developer runs the build again."
heading: About our shop
line: Paris
line: Berlin
line: Rome | good
```

For the About page, this is fine. Its stores change maybe once a year, and the team runs the build again when they do. A page whose data changes every minute is different. React's docs call it "a page with a content feed", and place it with server-side rendering. Where exactly the line falls between the two is a choice of its own, Lesson 129.

### When Static Prerendering Is the Right Choice

Static prerendering is the right choice when two things are true:
1. **The page is the same for every visitor.** Nothing on it depends on who opens it.
2. **Its data is known when the site is built.** It stays true until the next build.

An About page, a landing page, and a help page pass both tests. An account page fails the first. A content feed fails the second. A page that passes both tests can live on a CDN or a static host, with no server running React for it.

One shop often mixes both ways, page by page. Frameworks support this. React's docs say they "allow you to add server-side rendering on a per-route basis, when it makes sense for your use case." For the prerender APIs themselves, the docs add that a framework "may call them for you."

```tree caption="Which pages of the shop go into build.js and which are rendered at each request."
Is static prerendering the right choice for this page?
- +The same for every visitor, data known at build time [About page, landing page, help page] | +**DO** prerender it in `build.js` | Every visitor gets **the saved file**, from a CDN or a static host
- !Different for each visitor [account page] | ~Do **NOT** prerender it | `build.js` has **no visitor**, so nobody is greeted by name
- !Data that changes all the time [content feed] | ~Do **NOT** prerender it | The file shows **what was true at the last build**
```

Remember: one file, one answer, for everyone, until the next build.

## All 3 Principles Together

### The Complete About Page

Here are the four files of the About page. `db.js` is the stand-in for the database:

```js title="db.js"
export function ~getStores~() { // Answers with the two stores after 2 seconds
  return new Promise(resolve => {
    setTimeout(() => resolve(['Paris', 'Berlin']), 2000);
  });
}
```

`Stores` reads the Promise with `use`, so it suspends until the stores arrive:

```jsx title="Stores.jsx"
import { use } from 'react';

export default function Stores({ storesPromise }) {
  const stores = ~use(storesPromise)~; // Principle 2: suspends until db.js answers, so the build waits
  return (
    <ul>
      {stores.map(store => <li key={store}>{store}</li>)}
    </ul>
  );
}
```

`About` returns the whole document, with the store list inside `<Suspense>`:

```jsx title="About.jsx"
import { Suspense } from 'react';
import Stores from './Stores.jsx';

export default function About({ storesPromise }) {
  return (
    ~<html>~ {/* Principle 1: the whole document, and React adds the doctype above it */}
      <head>
        <title>About our shop</title>
      </head>
      <body>
        <h1>About our shop</h1>
        <Suspense fallback={<p>Loading stores...</p>}>
          <Stores storesPromise={storesPromise} />
        </Suspense>
      </body>
    </html>
  );
}
```

`build.js` runs once, during the build, and saves the HTML:

```jsx title="build.js"
import { prerenderToNodeStream } from 'react-dom/static';
import { createWriteStream } from 'node:fs';
import About from './About.jsx';
import { getStores } from './db.js';

const { prelude } = await ~prerenderToNodeStream(~ // Principles 1 and 2: resolves only after the stores are in
  <About storesPromise={getStores()} />
);
prelude.pipe(~createWriteStream('dist/about.html')~); // Principle 3: the one file every visitor gets
```

And this is what every visitor sees, from a CDN or a static host, with no server running React and no script in the browser:

```page width=text caption="The finished About page: the same saved file for every visitor."
heading: About our shop
line: Paris
line: Berlin
```

### How React Renders the About Page During the Build

When the developer runs the build, React starts at `About` and follows the tags from top to bottom. It renders the heading, reaches `Stores`, and waits there until the stores arrive. Only then does the Promise resolve, and only then does the build write the file:

```tree dir=right caption="The order of events when build.js prerenders the About page, from the build to the saved file."
How `build.js` makes `dist/about.html`
- +1. `build.js` calls `prerenderToNodeStream` | `getStores` **starts its 2-second wait** | No visitor, no `request`
- +2. React renders `About` | The **heading** is ready | `Stores` **suspends** on `use`
- +3. React waits | After **2 seconds** the stores arrive | React renders `Stores` with **Paris and Berlin**
- +4. The Promise resolves [`prelude` and `postponed`] | `postponed` is **`null`** | `prelude` is **piped into `dist/about.html`**
```

### Summary

| Aspect | The Habit That Breaks | The React Rule |
| :--- | :--- | :--- |
| **When React runs** | Render the About page in the request handler, again for every visitor | Render it once in `build.js` with `prerenderToNodeStream`, and send the saved file |
| **What comes back** | Expect a string, as from `renderToString` | Expect a Promise of `{ prelude, postponed }`: `prelude` is a stream of HTML, and `postponed` is `null` when the page is complete |
| **Which API** | Use the Web Stream method in Node.js | Use `prerenderToNodeStream` in Node.js, and `prerender` with Web Streams |
| **Data** | Build with `renderToString`, or fetch in an Effect, and save `Loading stores...` | Read data with `use` inside `<Suspense>`, so `prerender` waits and the data is in the file |
| **Which pages** | Prerender every page because static files are fast | Prerender only pages that are the same for every visitor until the next build |

Remember the one sentence of this lesson. **Static prerendering is server rendering done once, during the build, instead of once for every visitor.**

## For the Interview

> **The Interview Question:** What is static prerendering, and when is it the right choice?

### How to Answer Clearly in 30 Seconds

"Static prerendering means React renders a page to HTML once, during the build, and saves it as a file that every visitor gets. React's docs also call it static site generation, or SSG. It runs the same components as server rendering on each request; the only difference is when React runs. In React 19 we call `prerender` for Web Streams or `prerenderToNodeStream` for Node.js, both from `react-dom/static`. Three facts matter:
1. **What they return**: a Promise of `{ prelude, postponed }`. `prelude` is a stream of HTML that we can send in chunks or read into a string. `postponed` is `null` when the prelude holds all the content.
2. **They wait for data**: unlike `renderToString`, they wait until every Suspense boundary has its content, so data read with `use` is inside the file.
3. **The right choice**: a page that is the same for every visitor, with data known at build time, such as a landing page or an About page. It can then be served from a CDN or a static host, with no server running React. A page that differs per visitor, or a content feed, is rendered at each request."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why is `prelude` a stream and not a string?"**
   Because a stream can be used both ways. React's docs: "You can use this stream to send a response in chunks, or you can read the entire stream into a string." A build can pipe it into a file, as our `build.js` does, and a server can send it as a response. With `prerender`, the docs read the Web Stream into a string with `getReader`. Note that `prerender` itself does not stream as data arrives: it "waits for the entire app to finish rendering, including waiting for all Suspense boundaries to resolve, before resolving."
2. **"What if the data never arrives during the build?"**
   Pass a `signal` from an `AbortController` and abort after a time limit; the docs' example uses `10000` milliseconds. React's docs: "Any Suspense boundaries with incomplete children will be included in the prelude in the fallback state." Then `postponed` is not `null`, and finishing that part later with `resume` is Partial Pre-rendering, Lesson 120.
3. **"Can a prerendered page still answer clicks, and can it use a `nonce`?"**
   It can answer clicks: pass `bootstrapScripts`, and the script calls `hydrateRoot` to make the saved HTML interactive (as seen in Lesson 104). Without `bootstrapScripts`, no React runs in the browser at all. It cannot safely use a `nonce`, the one-time value that a Content Security Policy, or CSP, uses to allow a script. React's docs: "Nonces must be unique per request and if you use nonces to secure your application with CSP it would be inappropriate and insecure to include the nonce value in the prerender itself." A file made once is the same for every request, so it cannot hold a value that must differ for each one.

```tree dir=right caption="Interview comparison: rendering at each request vs. static prerendering during the build."
`renderToString` in the request handler vs. `prerenderToNodeStream` in the build
- +At each request [`renderToString`] | React runs **once per visitor**, with the `request` in hand | Fits pages that **differ per visitor** or **change all the time**
- +Once, during the build [`prerender` `prerenderToNodeStream`] | React runs **once in total**, waits for every Suspense boundary | Fits pages that are **the same for every visitor**, served from a **CDN or a static host**
```
