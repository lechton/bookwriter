# Lecture 53: How a Component Subscribes to a Store Outside React

*(How does React find out that the browser changed a value React never touched?)*

> INTERVIEW QUESTION | ❱❱ MORE | How do you subscribe to a store that lives outside React?

---

## VS | A Copy in State `useState` + `useEffect` vs. a Subscription `useSyncExternalStore`: the copy can be wrong, the subscription reads the real value

> When the Wi-Fi drops, the browser knows at once, but React does not: React draws the screen again only after a change inside React, such as a state update. **To show a value that lives outside React, subscribe to it with `useSyncExternalStore`: you tell React how to hear about a change and how to read the value, and React reads the real value itself.** A copy of that value in state, kept up to date by an Effect, can start from a wrong guess, and two components can end up showing two different versions of it.

Remember how you react to the network in plain JavaScript? You listen to an event on `window`, and when it fires, you change the page yourself:

```js title="Plain JavaScript: you listen, and you write into the page yourself"
window.addEventListener('offline', () => {
  ~heading.textContent = 'Disconnected'~; // Your own code writes the new text into the DOM
});
```

In React, you never write into the DOM. React writes it for you, from your JSX, and only when it renders your component. And React renders a component again only after a state update (Lesson 12). The browser changing its own value is not a state update. So nothing tells React that the page is now wrong.

The fix is to subscribe. Think of a newsletter. You stop checking the website every morning. You leave your address once, and they write to you when something new comes out. In React, you leave React two functions:

```jsx title="React: you tell React how to hear about a change and how to read the value"
const isOnline = ~useSyncExternalStore(subscribe, getSnapshot)~; // React listens through subscribe and reads through getSnapshot
```

1. **`subscribe`** tells React when the value changes. It connects React to the browser's own `online` and `offline` events.
2. **`getSnapshot`** reads the value. It returns `navigator.onLine`.

React uses the first one to hear about every change, and the second one to read the value whenever it renders.

> [!DEFINITION]
> **navigator.onLine and the online and offline events.** [REVIEW] `navigator.onLine` is a value the browser gives every page, with no import. It is `true` while the browser has a network, and `false` while it has none. When the network goes away, the browser fires the `offline` event on `window`, and when it comes back, it fires `online`. Our `useOnlineStatus` Hook already listens to these two events with `useState` and `useEffect` (Lesson 39).

> [!DEFINITION]
> **An external store.** [NEW] A store is simply a place that keeps data. External means it lives outside React and changes without React's knowledge. It sits in one of two places. In the browser: a value or a function the browser gives every page, which developers call a browser API, such as `navigator.onLine`. Or in a library that keeps its own state in its own objects, not in React state, such as a map library or a state library (Lesson 53).

### Who Owns the Data

So when do you use `useSyncExternalStore`, and when plain state? Ask one question: who changes this value?
1. **Our own React code changes it.** Use `useState` or `useReducer`. React's docs recommend this whenever it is possible.
2. **The browser or a library changes it.** Use `useSyncExternalStore`, as with `navigator.onLine`, or the state of a library that keeps its data outside React.
3. **The habit to avoid: a copy in state.** `useState` plus a `useEffect` that copies the outside value into state works on a normal day. React's docs label it "Not ideal", and call `useSyncExternalStore` the less error-prone way.

```tree caption="Three ways to keep a value on the screen, chosen by who changes the data."
Who changes the data on the screen?
- +Our own React code [`useState` `useReducer`] | Our handlers **create and change** the data | The **first choice** whenever it is possible
- +Something outside React [`useSyncExternalStore`] | The browser or a library **changes the data** without React's knowledge | React **subscribes** and **reads the value itself**
- !A copy of the outside value in state [`useState` `useEffect`] | Our code keeps **a second copy** up to date by hand | React's docs label it **Not ideal**
```

### What a Wrong Status Costs the User

A page that says `Online` while the network is gone lies to the user. The user trusts it, clicks `Save progress`, and the note never reaches the server.

It gets worse when two parts of the same page read the network. The heading can say `Disconnected`, while the button right below it still offers to save.

### The Rule of Thumb: subscribe to what React cannot see

**When a value lives outside React and changes over time, never just read it in the component, and never copy it into state by hand. Subscribe to it with `useSyncExternalStore`, usually inside a custom Hook.**

A senior developer knows the two classic mistakes:
1. **Reading `navigator.onLine` straight in the component.** It shows the right value when the page opens, so the bug stays hidden until the network changes.
2. **Copying the value into state with `useState` and an Effect**, and believing it is the same thing as `useSyncExternalStore`. Both return the same `true` or `false`, but they are NOT the same thing, as Principle 3 shows.

Remember the one sentence of this lesson. **React cannot see a value that lives outside React, so the component must subscribe to it, and React must read the value itself.**

The entry file mounts `App` inside `<StrictMode>` (Lesson 07). `App` keeps the note text in state, so every letter the user types is a state update in `App`:

```jsx title="src/App.jsx"
import { useState } from 'react';
import StatusBar from './StatusBar.jsx';
import SaveButton from './SaveButton.jsx';

export default function App() {
  const [note, setNote] = useState('Buy milk');
  return (
    <>
      <StatusBar />
      <textarea value={note} ~onChange={e => setNote(e.target.value)}~ /> {/* Every letter renders App, StatusBar, and SaveButton again */}
      <SaveButton />
    </>
  );
}
```

`SaveButton` reads the network through the Hook, and turns itself off while the network is gone:

```jsx title="src/SaveButton.jsx"
import { useOnlineStatus } from './useOnlineStatus.js';

export default function SaveButton() {
  const isOnline = ~useOnlineStatus()~; // true or false, from the Hook
  function handleSaveClick() {
    console.log('Progress saved');
  }

  return (
    <button disabled={!isOnline} onClick={handleSaveClick}>
      {isOnline ? 'Save progress' : 'Reconnecting...'}
    </button>
  );
}
```

**PRINCIPLES:** React renders a component again only after an update inside React. A value that lives outside React must be subscribed to, and React must read it itself. Six principles follow:
1. **Principle 1: A Direct Read of navigator.onLine Never Updates the Page.** It is right on the first render. When the network changes, nothing tells React, so the page keeps the old value.
2. **Principle 2: useSyncExternalStore Takes Two Functions.** `subscribe` connects React to the change events, and `getSnapshot` reads the value. React renders again when the value is different.
3. **Principle 3: The Effect Version Is NOT the Same Thing.** It returns the same `true` or `false`, but our code must keep the copy right by hand, starting from the first render.
4. **Principle 4: Every Component Shows the Same Version of the Store.** When React pauses a render, React checks the store again before it changes the screen, so the heading and the button always agree.
5. **Principle 5: getSnapshot Returns the Same Value While Nothing Changed.** A new object on every call is always different, so React renders without end and stops with an error.
6. **Principle 6: Declare subscribe Outside the Hook.** A `subscribe` declared inside the Hook is a new function on every render, so React subscribes again after every letter the user types.

## PRINCIPLE | navigator.onLine in the component body: read once, and the page never hears the change

> [!PRINCIPLE]
> **Principle 1: A Direct Read of navigator.onLine Never Updates the Page**
>
> *A value that lives outside React, read directly in the component body, is right on the first render and then stays old.*
>
> React renders a component again only after a state update, in the component itself or in a parent above it. When the browser changes `navigator.onLine`, no state changes, so React never calls the component again. The page keeps the old value, with no error. A value like this must be subscribed to.
>
> **DO THIS:**
> ```jsx
> export default function StatusBar() {
>   const isOnline = ~useOnlineStatus()~; // Subscribes, so React renders again when the network changes
>   return <h1>{isOnline ? 'Online' : 'Disconnected'}</h1>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function StatusBar() {
>   const isOnline = ~navigator.onLine~; // **WRONG:** read once per render, so the heading stays on Online after the Wi-Fi drops
>   return <h1>{isOnline ? 'Online' : 'Disconnected'}</h1>;
> }
> ```

### Reading the browser's value directly

A developer looks at `StatusBar` and thinks: why state, why an Effect? The browser already has the value. So the developer reads it straight in the component:

```jsx title="src/StatusBar.jsx"
export default function StatusBar() {
  const isOnline = ~navigator.onLine~; // Reads the browser's value once, during this render
  return <h1>{isOnline ? 'Online' : 'Disconnected'}</h1>;
}
```

The page opens with the Wi-Fi on, and the heading reads `Online`. It looks right. `SaveButton` has not changed: it still calls `useOnlineStatus`, with its state and its Effect.

Now the user turns off the Wi-Fi:

```page caption="The notes app after the Wi-Fi drops, when StatusBar reads navigator.onLine directly: the heading still says Online, while the button already says Reconnecting."
heading: Online | bad
form:
  textarea:  | Buy milk
  button: Reconnecting... | | disabled
console: quiet
```

**The heading says `Online`, the button right below it says `Reconnecting...`, and the Console stays quiet.**

### Why the heading stays on Online

The line `navigator.onLine` runs only when React calls `StatusBar`. And nothing makes React call it again:
1. The page opens with the Wi-Fi on. React renders `StatusBar`. `navigator.onLine` is `true`, so the heading reads `Online`.
2. The user turns off the Wi-Fi. The browser sets `navigator.onLine` to `false`.
3. No state changed, in `StatusBar` or in `App` above it. So React does not call `StatusBar` again.
4. The heading still reads `Online`.

Why is the button right? Because `useOnlineStatus` listens to the `offline` event and calls a setter. The setter is what tells React to render `SaveButton` again. `StatusBar` has no setter, so nobody tells React anything.

Something that can be tricky: the heading does change, later, by accident. The user types one letter in the note. That letter updates the note state in `App`. So React renders `App` again, and `StatusBar` with it. The heading jumps to `Disconnected`. The page is right by luck, not by design.

```tree dir=right caption="Why a direct read of navigator.onLine freezes the heading: the browser changes the value, but nothing tells React to render again."
What happens when the Wi-Fi drops
- +1. First render [`navigator.onLine`] | React calls `StatusBar` and reads **`true`** | The heading reads **Online**
- !2. The browser changes the value | `navigator.onLine` becomes **`false`** | **No state changed**, so React does **not** call `StatusBar`
- !3. The page stays old | The heading still reads **Online** | The Console shows **no error**
```

So reading a value and hearing that it changed are two separate things. A read in the component body happens only when React chooses to render.

This read also breaks a rule of React's docs: rendering must stay pure (Lesson 14). A component must return the same output for the same props, state, and context. `StatusBar` also depends on a value that changes behind React's back.

### A dependency array does not help either

Some developers try to fix the frozen heading by putting `navigator.onLine` in the dependency array of an Effect. That cannot work. React compares the dependencies only after it renders (Lesson 35), and a value that changes without React's knowledge never makes React render.

React's docs give the fix in one sentence: read and subscribe to an outside value with `useSyncExternalStore`.

## PRINCIPLE | useSyncExternalStore: subscribe hears every change, getSnapshot reads the real value

> [!PRINCIPLE]
> **Principle 2: useSyncExternalStore Takes Two Functions**
>
> *Call `useSyncExternalStore(subscribe, getSnapshot)` at the top level; `subscribe` hands React's `callback` to the store's change events, and `getSnapshot` returns the value.*
>
> React cannot see a value outside React change, so we give it two functions. React calls `subscribe` with its own `callback`, and our code hands that `callback` to the store's events. When an event fires, React calls `getSnapshot`. If the value is different from the last one, React renders the component again.
>
> **DO THIS:**
> ```jsx
> function subscribe(callback) {
>   window.addEventListener('online', callback);
>   window.addEventListener('offline', callback);
>   return () => {
>     window.removeEventListener('online', callback);
>     window.removeEventListener('offline', callback);
>   };
> }
> const isOnline = ~useSyncExternalStore(subscribe, getSnapshot)~; // React hears every change and reads the real value
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ~subscribe~(callback) { // **WRONG:** returns no cleanup function, so the listeners stay after StatusBar leaves the screen
>   window.addEventListener('online', callback);
>   window.addEventListener('offline', callback);
> }
> ```

`useSyncExternalStore` is a React Hook. You import it from `'react'` and call it at the top level of the component, like every Hook (Lesson 38). It takes two functions, and it returns the value. Our code writes both functions, and each one does one job.

### getSnapshot: how React reads the value

`getSnapshot` is the function React calls to read the value:

```jsx title="getSnapshot: how React reads the value"
function getSnapshot() {
  return ~navigator.onLine~; // true while the network is on, false while it is off
}
```

What it returns, React's docs call a **snapshot**: the value of the store at this moment. The Hook returns that same snapshot to your component. Here, it becomes `isOnline`.

### subscribe: how React hears about a change

`subscribe` is the function React calls to start listening. It looks almost like the plain JavaScript you already know:

```jsx title="subscribe: how React hears about a change"
function subscribe(~callback~) { // React writes callback and passes it in
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}
```

These are the same two events our Effect listened to in Lesson 39. The function at the end is a cleanup function, as in an Effect (Lesson 32). React keeps it, and calls it when it unsubscribes, for example when the component leaves the screen.

### Where callback comes from

In plain JavaScript, you write the handler yourself and give it to `addEventListener`. Here, you only name the parameter `callback`. **You never write that function. React writes it, and React passes it in.** The path it takes:
1. React receives our `subscribe` as the first argument of `useSyncExternalStore`.
2. React calls `subscribe`, and passes its own function as `callback`.
3. Our code hands that function to `addEventListener`, for both events.
4. When the network changes, the browser calls `callback`, which is React's own function.

When `callback` runs, React calls `getSnapshot` again. If the value is different, React renders the component again.

### StatusBar with useSyncExternalStore

Now put the pieces together. The two functions sit above the component, at the top of the file:

```jsx title="src/StatusBar.jsx"
import { useSyncExternalStore } from 'react';

function getSnapshot() {
  return navigator.onLine;
}

function subscribe(callback) {
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}

export default function StatusBar() {
  const isOnline = ~useSyncExternalStore(subscribe, getSnapshot)~; // Reads navigator.onLine again whenever the browser fires online or offline
  return <h1>{isOnline ? 'Online' : 'Disconnected'}</h1>;
}
```

The user turns off the Wi-Fi again. This time both parts of the page change together:

```page caption="The notes app after the Wi-Fi drops, when StatusBar calls useSyncExternalStore: the heading and the button agree."
heading: Disconnected | good
form:
  textarea:  | Buy milk
  button: Reconnecting... | | disabled
console: quiet
```

### What React does when the Wi-Fi drops

1. React renders `StatusBar`, calls `getSnapshot`, and gets `true`. The heading reads `Online`.
2. React calls `subscribe` and passes its own `callback`. Our code adds that function to both events.
3. The user turns off the Wi-Fi. The browser fires `offline` on `window`, and `callback` runs.
4. React calls `getSnapshot` again, and gets `false`.
5. React compares the old value and the new one with `Object.is` (Lesson 32). `true` and `false` are different, so React renders `StatusBar` again. The heading reads `Disconnected`.

```tree dir=right caption="How React follows the network with the two functions: subscribe hears the change, getSnapshot reads it, and a different value makes React render again."
What happens when the Wi-Fi drops
- +1. React subscribes [`subscribe`] | React passes **its own `callback`** | Our code adds it to the **`online` and `offline` events**
- +2. The browser fires `offline` [`callback`] | React's **`callback` runs** | React calls **`getSnapshot`** again and gets **`false`**
- +3. React compares [`Object.is`] | **`true` and `false` differ** | React renders `StatusBar`, and the heading reads **Disconnected**
```

React watches nothing by itself. `subscribe` is the only way React hears about a change. `getSnapshot` is the only way React reads the value.

### When not to reach for it

Our data lives in the browser, so it needs a subscription. Data that our own React code creates and changes does not. React's docs say it plainly: when possible, use `useState` and `useReducer`, because `useSyncExternalStore` is mostly useful to connect with code that is not React.

A developer who has just learned the Hook, and moves the values of a form into a store, gains nothing. They only get two more functions to maintain.

## PRINCIPLE | useState plus useEffect: the copy returns the same boolean, but it starts from a guess

> [!PRINCIPLE]
> **Principle 3: The Effect Version Is NOT the Same Thing**
>
> *Do not copy an outside value into state with `useState` and `useEffect`; subscribe to it with `useSyncExternalStore`, usually from a custom Hook.*
>
> The Effect version returns the same `true` or `false`, so it looks like the same thing. It is not. It keeps a second copy of the value in state, and our code must keep that copy right by hand, starting with its first value. A wrong start, such as `useState(true)`, shows `Online` to a user who opens the app offline. `useSyncExternalStore` keeps no copy and reads the real value on the first render and on every render after it.
>
> **DO THIS:**
> ```js
> export function useOnlineStatus() {
>   return ~useSyncExternalStore(subscribe, getSnapshot)~; // Reads navigator.onLine on every render, starting with the first
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> export function useOnlineStatus() {
>   const [isOnline, setIsOnline] = ~useState(true)~; // **WRONG:** a guess, so an offline user sees Online and no event ever corrects it
>   useEffect(() => { /* copies the online and offline events into state */ }, []);
>   return isOnline;
> }
> ```

### Two versions of useOnlineStatus

`SaveButton` still reads the Effect version of the Hook. Now we move `subscribe` and `getSnapshot` out of `StatusBar` and into the Hook file, so both components get the new way. Here is the Hook file as it is now:

```js title="src/useOnlineStatus.js, with useState and useEffect"
import { useState, useEffect } from 'react';

export function useOnlineStatus() {
  const [isOnline, setIsOnline] = ~useState(navigator.onLine)~; // A copy in state, with a starting value our code must choose
  useEffect(() => {
    function handleOnline() {
      setIsOnline(true);
    }
    function handleOffline() {
      setIsOnline(false);
    }
    window.addEventListener('online', handleOnline);
    window.addEventListener('offline', handleOffline);
    return () => {
      window.removeEventListener('online', handleOnline);
      window.removeEventListener('offline', handleOffline);
    };
  }, []);
  return isOnline;
}
```

And here is the same Hook with `useSyncExternalStore`. The two functions sit above the Hook, outside it:

```js title="src/useOnlineStatus.js, with useSyncExternalStore"
import { useSyncExternalStore } from 'react';

function getSnapshot() {
  return navigator.onLine;
}

function subscribe(callback) {
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}

export function useOnlineStatus() {
  return ~useSyncExternalStore(subscribe, getSnapshot)~; // No copy: React reads navigator.onLine on every render
}
```

`StatusBar` goes back to one line, `const isOnline = useOnlineStatus();`. `SaveButton` does not change at all.

### Who holds the value

Both versions listen to the same two events. Both return `true` or `false`. On a normal day, with the Wi-Fi on when the page opens, both show `Online` and `Save progress`. **It may look the same, and it works the same at first, but it is NOT the same thing!**

The difference is who holds the value:
- **With `useState` and `useEffect`**, our code keeps a second copy of the browser's value in React state. Keeping that copy right is our job: the starting value, the two handlers that call the setter, and the cleanup. Each component that calls the Hook keeps its own copy (Lesson 39).
- **With `useSyncExternalStore`**, there is no copy. React reads the browser's value itself, through `getSnapshot`, on the first render and on every render after it.

### A copy starts from a guess

**Beware! A copy in state starts from whatever value our code gives `useState`, and no event ever corrects a wrong start.** Our first version in Lesson 39 started from `useState(true)`, the same guess React's docs use in their example. Now a user opens the app while already offline:
1. The copy starts as `true`. The first render shows `Online`, and the button says `Save progress` and takes clicks.
2. No `online` or `offline` event fires afterwards, because nothing changed after the page opened. So the copy stays wrong for as long as the network is down.
3. With `useSyncExternalStore`, there is no starting value to choose. The first render calls `getSnapshot`, which reads `false`. The heading says `Disconnected`, and the button says `Reconnecting...`.

React's docs describe this exact bug. The Effect version assumes the network is on when the component appears, and that may be wrong if the network already went offline.

### A better starting value is still not the same thing

Our current Hook file fixes the start by hand, with `useState(navigator.onLine)`. In the browser, that gives the right starting value. It is still not the same thing as `useSyncExternalStore`, for two reasons:
1. **The server has no `navigator`.** When a server renders the page first, this browser value does not exist there (Lessons 101 to 105). For this case, `useSyncExternalStore` takes an optional third argument, `getServerSnapshot`: a function that returns the value to use on the server.
2. **The copy gets no promise from React.** With `useSyncExternalStore`, React promises that every component on the screen shows the same version of the store, as Principle 4 shows. A copy that our own Effect updates gets no such promise.

React's docs label the Effect version "Not ideal: Manual store subscription in an Effect". They call `useSyncExternalStore` less error-prone than copying an outside value into state with an Effect.

### Only the Hook file changed

Look at what the swap cost. One file changed, the Hook file. Both components still call `useOnlineStatus()`, and they get the same `true` or `false` as before. React's docs point it out: you did not need to change any of the components to make this move. That is why you usually call `useSyncExternalStore` from a custom Hook, not directly in each component.

```tree caption="The Effect version and the useSyncExternalStore version of useOnlineStatus return the same boolean, but only one keeps a copy of the value."

- +With `useSyncExternalStore` [`subscribe` `getSnapshot`] | **No copy**: React reads `navigator.onLine` **itself** | The **first render is right**, and every component shows **the same version**
```

## PRINCIPLE | useSyncExternalStore: every component on the screen shows the same version of the store

> [!PRINCIPLE]
> **Principle 4: Every Component Shows the Same Version of the Store**
>
> *With `useSyncExternalStore`, every component on the screen shows the same version of the store, even when React pauses a render.*
>
> When React pauses a render, a store outside React can change in the middle, and two components could read two versions of it. For a Transition, React calls `getSnapshot` a second time just before it changes the DOM. If the value moved, React starts over as a blocking update, so the heading and the button never disagree.
>
> **DO THIS:**
> ```js
> export function useOnlineStatus() {
>   return ~useSyncExternalStore(subscribe, getSnapshot)~; // React checks getSnapshot again before changing the DOM
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> export function useOnlineStatus() {
>   return ~navigator.onLine~; // **WRONG:** no subscription, so React never checks the store again before changing the DOM
> }
> ```

### One store, one answer on the whole screen

Two components on our page read the same store: `StatusBar` and `SaveButton`. The user must never see this screen:

```page caption="A torn screen that useSyncExternalStore never lets the user see: the heading says Disconnected while the button still offers to save."
heading: Disconnected
form:
  textarea:  | Buy milk
  button: Save progress | | bad
```

The heading says the network is gone. The button right below it still offers to save. The user clicks it, and the note never reaches the server. **One store has one value at a time, so the whole screen must show one answer.**

### How a paused render can split the screen

Developers usually think a render always runs from the first component to the last in one go. It does not always. For some updates, React can start rendering, pause in the middle to let the browser handle something more urgent, and continue later. This is concurrent rendering (Lesson 66). An update that React may pause like this is a non-blocking update, such as a Transition (Lesson 67).

During such a pause, a value outside React can change. Say React read the store for `StatusBar` before the pause, and for `SaveButton` after it. The two components now hold two different values. The heading comes from one moment, and the button from another.

> [!DEFINITION]
> **Tearing.** [NEW] Tearing is the React team's word for a screen whose parts show two different versions of the same store. Think of a photo torn across the middle and taped back together, with the top half taken at one moment and the bottom half at another. On our page, a torn screen is a heading that says `Disconnected` above a button that says `Save progress` (Lesson 53).

```tree caption="A torn screen and a consistent screen: two components that read one store show either two versions of it or one."
Two components read one store during one render
- !A torn screen | `StatusBar` reads the store **before** a pause; `SaveButton` reads it **after** | The heading says **Disconnected**, and the button says **Save progress**
- +One version on the whole screen [`useSyncExternalStore`] | React **checks the store again** before changing the DOM | The heading and the button **always agree**
```

### What React does to prevent it

**With `useSyncExternalStore`, React reads the store one more time just before it changes the screen, and starts over if the value moved.** React's docs describe these steps for a Transition:
1. React starts a Transition, and calls `getSnapshot` for each component that reads the store.
2. The store changes before React changes the DOM. Here, the Wi-Fi drops during the pause.
3. Just before it changes the DOM, React calls `getSnapshot` a second time.
4. The second value is different from the first.
5. React throws the paused work away, and renders the update again from scratch, this time as a blocking update, which React does not pause.
6. Every component shows the same version of the store: `Disconnected` and `Reconnecting...` together.

Our code never calls `getSnapshot`. React makes the first call and the second call on its own. This is what the word "Sync" in the name points to: React applies updates from the store as synchronous, blocking updates.

### What the guarantee costs

The guarantee has a price, and interviewers like to ask about it. A change in an outside store can never be a Transition that React may pause. So when such a change makes a component suspend, React shows the nearest Suspense fallback, instead of keeping the old content on the screen (Lesson 69). For this reason, React's docs advise against suspending on a value read from `useSyncExternalStore`.

The guarantee is also why state libraries moved to `useSyncExternalStore` when React 18 brought concurrent rendering. A library that reads its own store during render without it can show a torn screen.

## PRINCIPLE | getSnapshot: the same value while nothing changed, or React renders forever

> [!PRINCIPLE]
> **Principle 5: getSnapshot Returns the Same Value While Nothing Changed**
>
> *While the store has not changed, every call to `getSnapshot` must return the very same value.*
>
> React compares each snapshot with the last one using `Object.is`, and renders again when they differ. A `getSnapshot` that builds a new object on every call is always different from the last one, so React renders without end and stops with an error. Return the value itself, or return the last snapshot again until the store changes.
>
> **DO THIS:**
> ```js
> function getSnapshot() {
>   return ~navigator.onLine~; // The same true or false until the network changes
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> function getSnapshot() {
>   return ~{ isOnline: navigator.onLine }~; // **WRONG:** a new object every call, so React renders forever and stops with an error
> }
> ```

### A snapshot that looks harmless

A developer wants the Hook to return an object, so more fields can be added later. They wrap the value:

```js title="src/useOnlineStatus.js" startLine="3"
function getSnapshot() {
  return ~{ isOnline: navigator.onLine }~; // **WRONG:** a brand-new object on every call
}
```

The object holds the right data. Yet the moment the page opens, it fails:

```page caption="The notes app when getSnapshot returns a new object on every call: the page is blank."
blank
```

```devconsole width=full caption="The Console when getSnapshot returns a new object on every call."
x The result of getSnapshot should be cached to avoid an infinite loop
x Uncaught Error: Maximum update depth exceeded. This can happen when a component repeatedly calls setState inside componentWillUpdate or componentDidUpdate. React limits the number of nested updates to prevent infinite loops.
! An error occurred in the <StatusBar> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

### Why a new object never matches

Remember how React decides to render again: it compares the new snapshot with the last one, using `Object.is` (Lesson 32). For an object, `Object.is` never looks at the fields. It only asks: is this the very same object?
1. React renders `StatusBar`, calls `getSnapshot`, and gets a new object.
2. React calls `getSnapshot` again to check whether the store changed, and gets another new object with the same data.
3. `Object.is` says the two objects are different, so React treats the store as changed and renders again.
4. The next render calls `getSnapshot` again, gets a third object, and the same thing happens.
5. React renders without end, so it stops with the errors above.

Here are the two snapshots side by side:

```js title="Returning the value itself, and returning a new object around it"
return ~navigator.onLine~; // true is always Object.is equal to true: React renders only when the network changes
return ~{ isOnline: navigator.onLine }~; // **WRONG:** a new object is never equal to the last one: React renders forever
```

**It looks the same, but it is NOT the same thing!** Both carry the same `true` or `false`. But `true` is always equal to `true`, while two objects created separately are never the same object.

### The rule for every snapshot

React's docs give the rule in one sentence: while the store has not changed, repeated calls to `getSnapshot` must return the same value. The snapshot must also be immutable: our code never changes it in place.

The same mistake appears with a store from a library. A developer writes `return { todos: myStore.todos };` and gets the same loop. There are two fixes:
1. **Return the store's data directly**, as `return myStore.todos;`, when the store gives a new array only after a change.
2. **Keep the last snapshot**, when the store changes its data in place, and return it again until the data really changes. How to tell that the data changed depends on the store.

Our network status is a plain `true` or `false`, so the fix is the simplest one: put back `return navigator.onLine;`.

## PRINCIPLE | subscribe outside the Hook: React subscribes once, not after every letter

> [!PRINCIPLE]
> **Principle 6: Declare subscribe Outside the Hook**
>
> *Declare `subscribe` at the top level of the file, so React receives the same function on every render.*
>
> A function declared inside a component or a custom Hook is created again on every render. When React receives a different `subscribe`, it unsubscribes and subscribes again. On a page that renders on every letter the user types, that means removing and adding the listeners for every letter. When `subscribe` needs a prop, wrap it in `useCallback` instead.
>
> **DO THIS:**
> ```js
> function ~subscribe~(callback) { // Declared once, so React subscribes once
>   window.addEventListener('online', callback);
>   window.addEventListener('offline', callback);
>   return () => {
>     window.removeEventListener('online', callback);
>     window.removeEventListener('offline', callback);
>   };
> }
>
> export function useOnlineStatus() {
>   return useSyncExternalStore(subscribe, getSnapshot);
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> export function useOnlineStatus() {
>   function ~subscribe~(callback) { // **WRONG:** a new function every render, so React subscribes again after every letter
>     window.addEventListener('online', callback);
>     window.addEventListener('offline', callback);
>     return () => {
>       window.removeEventListener('online', callback);
>       window.removeEventListener('offline', callback);
>     };
>   }
>   return useSyncExternalStore(subscribe, getSnapshot);
> }
> ```

### Two places to write subscribe

`subscribe` can sit in two places: at the top of the file, above the Hook, or inside the Hook, next to the call that uses it. Inside feels tidy, because the function stays close to where it is used. To see what React does with each, we add one `console.log` inside `subscribe`.

Here is `subscribe` declared outside the Hook:

```js title="src/useOnlineStatus.js, with subscribe declared outside the Hook"
function ~subscribe~(callback) { // Created once, when the file loads
  console.log('Subscribing to the network');
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}

export function useOnlineStatus() {
  return useSyncExternalStore(subscribe, getSnapshot);
}
```

And here is the whole file with `subscribe` declared inside the Hook:

```js title="src/useOnlineStatus.js, with subscribe declared inside the Hook"
import { useSyncExternalStore } from 'react';

function getSnapshot() {
  return navigator.onLine;
}

export function useOnlineStatus() {
  function ~subscribe~(callback) { // **WRONG:** created again every time a component calls the Hook
    console.log('Subscribing to the network');
    window.addEventListener('online', callback);
    window.addEventListener('offline', callback);
    return () => {
      window.removeEventListener('online', callback);
      window.removeEventListener('offline', callback);
    };
  }
  return useSyncExternalStore(subscribe, getSnapshot);
}
```

Both show the right status, and the page looks the same. **It may look the same, and it works the same at first, but it is NOT the same thing!**

### Why the inside version subscribes again

The code of a custom Hook runs as part of the component that calls it (Lesson 39). So a function declared inside the Hook is created again every time the component renders, just like a component declared inside another component (Lesson 04).

React compares the `subscribe` it receives with the one from the last render. It compares the functions themselves, not their code. A function created again is a different function. So React unsubscribes with the old cleanup function, and subscribes again with the new `subscribe`.

On our page, that happens all the time. `App` holds the note text in state, so every letter the user types renders `App` again, and both components with it. The developer clears the Console, and the user types one letter:

```devconsole caption="The Console after the developer clears it and the user types one letter, when subscribe is declared inside useOnlineStatus."
+ Subscribing to the network | useOnlineStatus.js:9
+ Subscribing to the network | useOnlineStatus.js:9
```

**Two lines for every letter, one for `StatusBar` and one for `SaveButton`, and no error.** Every letter removes both listeners and adds them back, in both components. React's docs treat this as a performance problem: the listeners are removed and added again for nothing.

With `subscribe` declared outside the Hook, React receives the very same function on every render. React's docs say it in one line: React won't resubscribe for as long as you pass the same function. The Console stays empty while the user types.

```tree caption="Where subscribe is declared decides whether React subscribes once or after every render."
Where `subscribe` is declared
- +Outside the Hook, at the top of the file | Created **once**, when the file loads | React **subscribes once** and keeps the listeners
- !Inside the Hook | Created **again on every render** | React **unsubscribes and subscribes again** after every letter the user types
```

### When subscribe needs a prop

Sometimes `subscribe` must use a value from the component, such as a `userId` prop, so it cannot move outside. React's docs give a second fix for that case: wrap `subscribe` in `useCallback`, with `userId` in its dependencies (Lesson 57). Then React receives the same function until `userId` changes, and subscribes again only then.

| Topic | The Habit to Avoid | The React Rule |
| :--- | :--- | :--- |
| **Reading an outside value** | Read `navigator.onLine` straight in the component, so the heading freezes after the Wi-Fi drops | Subscribe with `useSyncExternalStore`, so React hears every change |
| **The two functions** | Expect React to watch the store by itself | Write `subscribe`, which hands React's `callback` to the events, and `getSnapshot`, which returns the value |
| **The Effect version** | Copy the value into state with `useState` and `useEffect`, and choose its starting value by hand | Read the store with `useSyncExternalStore` inside a custom Hook, with no copy |
| **Two components, one store** | Assume a render always runs in one go | Let React check the store again before it changes the DOM, so no screen is torn |
| **The snapshot** | Return a new object from `getSnapshot` on every call | Return the same value while the store has not changed |
| **Where `subscribe` lives** | Declare it inside the component or the Hook | Declare it at the top of the file, or wrap it in `useCallback` when it needs a prop |

Remember the one sentence of this lesson. **React cannot see a value that lives outside React, so the component must subscribe to it, and React must read the value itself.**

## For the Interview

> **The Interview Question:** How do you subscribe to a store that lives outside React?

### How to Answer Clearly in 30 Seconds

"An external store is data that lives outside React and changes without React's knowledge, such as the browser's `navigator.onLine` or the state of a third-party library. React renders again only after an update inside React, such as a state change, so I subscribe with `useSyncExternalStore`, usually inside a custom Hook such as `useOnlineStatus`. It takes two functions:
1. **`subscribe`** receives React's `callback`, hands it to the store's change events, and returns a cleanup function.
2. **`getSnapshot`** returns the current value. React compares it with `Object.is`, and renders again only when it is different.

Two rules keep it working. `getSnapshot` must return the same value while the store has not changed, or React loops forever. `subscribe` must be declared outside the component, or React subscribes again on every render. An optional third function, `getServerSnapshot`, gives the value to use on the server."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What does `useSyncExternalStore` guarantee during concurrent rendering?"**
   It guarantees that every component on the screen shows the same version of the store, with no tearing. During a Transition, React may pause a render, and the store can change during the pause. So React calls `getSnapshot` a second time just before it changes the DOM. If the value moved, React throws the work away and renders the update again from scratch, as a blocking update. The cost: a store update can never be a paused Transition, so a component that suspends on a store value shows the nearest Suspense fallback. That is why React's docs advise against suspending on a store value.
2. **"Why not copy the value into state with `useState` and `useEffect`?"**
   Because that keeps a second copy, and our code must keep it right by hand. The copy starts from whatever value we give `useState`. With a guess such as `useState(true)`, a user who opens the page offline sees `Online`, and no event ever corrects it. Starting from the browser's value fixes that in the browser, but the value does not exist on the server, and the copy gets no tearing guarantee from React. React's docs call the Effect version "Not ideal", and `useSyncExternalStore` less error-prone. Because the call lives in a custom Hook, the swap changes one file and no component.
3. **"When should you not use `useSyncExternalStore`?"**
   When our own React code owns the data. React's docs recommend `useState` and `useReducer` whenever possible, and say `useSyncExternalStore` is mostly useful to connect with code that is not React. In daily work, most developers meet it through a state library, which calls it for them. React's docs show the same shape with a small store object called `todosStore`, which offers `todosStore.subscribe` and `todosStore.getSnapshot`. They describe it as a Hook mostly used by library authors, not in everyday application code.

```tree dir=right caption="Interview summary: how a component subscribes to a store outside React, and the two rules that keep it working."
Subscribing to a store outside React
- +Subscribe [`useSyncExternalStore`] | `subscribe` hands **React's `callback`** to the store; `getSnapshot` **reads the value** | React renders again only when **the value is different**
- +The guarantee | React **checks the store again** before changing the DOM | **Every component** shows the same version of the store
- !The two rules [`getSnapshot` `subscribe`] | ~Do **NOT** return a new object or declare `subscribe` inside | A new object **loops forever**; a new `subscribe` **subscribes again on every render**
```
