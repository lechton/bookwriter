## Why We Let State Own a Form Field

### Three name boxes that all start with John

Every form on the web has boxes that the user types into. Before we build a real form, look at a small page with three name boxes, A, B, and C. When the page opens, all three show the name John:

```page width=text caption="A small page with three name boxes, all showing John when the page opens."
heading: Three name boxes
form:
  field: Box A | John
  field: Box B | John
  field: Box C | John
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field.
```

The three boxes look identical, but the code behind them is not. Here is the code for each box:

```jsx title="Three ways to put John inside a name box"
const [name, setName] = useState('John');

<input ~defaultValue="John"~ /> {/* A. Starts with John, then keeps whatever the user types */}
<input ~value="John"~ /> {/* B. Shows John and refuses every new letter */}
<input value={name} ~onChange={e => setName(e.target.value)}~ /> {/* C. Shows whatever name holds in state */}
```

Now the user clicks into each box and types two more letters, `ny`:

```page width=text caption="The same page after the user types ny into each of the three name boxes."
heading: Three name boxes
form:
  field: Box A | Johnny | good
  field: Box B | John | bad
  field: Box C | Johnny | good
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field.
```

Here is what each box did:
- **Box A** shows `Johnny`.
- **Box B** still shows `John`. The new letters never stay.
- **Box C** shows `Johnny`, and the name in state is now `'Johnny'` too.

Next, a button empties the name in state:

```jsx title="A button that empties the name in state"
<button onClick={() => ~setName('')~}>Clear</button> {/* Sets name in state to an empty string */}
```

The user clicks Clear:

```page width=text caption="The same page after the user clicks Clear, which empties the name in state."
heading: Three name boxes
form:
  field: Box A | Johnny | bad
  field: Box B | John | bad
  field: Box C |  | good
  button: Clear
```

Box C becomes empty. Box A still shows `Johnny`. Box A never reads the name in state, so the button cannot reach it.

These three boxes hide three easy confusions. Let us say each one out loud:
- **Box A and box C look the same when the page opens, and both accept typing, but they are NOT the same thing!** In box A, the box itself keeps the text. In box C, state keeps the text. That is why only box C empties when the name in state becomes empty.
- **Box B and box C both write `value`, but they are NOT the same thing!** Box B has a fixed value, and nothing tells React about the typing. So React puts John back after every key the user presses.
- **Writing `value="John"` and writing `value={name}` while the name is John are the exact same thing for the box.** In both cases, React makes the box show John. The curly braces do not make box C editable. The change handler does.

Three words come up in every React team and every interview. Each one comes from everyday life:
- **What does "default" mean?** A new phone comes with a default ringtone. The phone starts with it, and then it plays whatever ringtone its owner picks. The shop that chose the first ringtone no longer decides. A **default value** works the same way. It is only the starting text, and after that the box keeps whatever the user types.
- **What does "controlled" mean?** Think of the departure board at a train station. It shows only what the station's system sends to it. Nobody walks up and writes on the board with a pen. A **controlled** field is that board. It shows only what state holds.
- **What is a "single source of truth"?** Box A keeps its own copy of the text inside the browser, and state may keep a second copy. Nothing keeps those two copies equal. Box C leaves only one copy, the one in state. Developers call that one master copy the **single source of truth**. It is like the one official clock that every other clock in the station is set from.

```tree caption="Three name boxes that all start with John, and what happens when the user types and when state is emptied."
Three name boxes that start with John
- +A: Starting text only [`defaultValue="John"`] | The **box keeps** the text | Typing gives **Johnny** | Emptying state changes **nothing**
- !B: Fixed value, and nothing tells React about the typing [`value="John"`] | React **puts John back** after every key | Typing changes **nothing**
- +C: Value from state plus a change handler [`value={name}` `onChange`] | **State keeps** the text | Typing gives **Johnny** | Emptying state **empties the box**
```

### Why a contact form keeps the message after Send

Now look at a real page. Almost every online shop has a Contact Us page. A customer types a question, such as where is my order, and clicks Send. A thank-you line appears under the form. Yet the question is still sitting in the box. The customer wonders whether the message really went out, and may even send it twice.

So the developer wants the box to be empty after Send. Before writing a single line, the developer has to answer one question: who owns the text inside the box, the browser or React state? This lesson answers that question, one field at a time.

### Two ways to own a field's value

In real projects, developers choose between two owners for what a field holds:
1. **Controlled**: state holds the value, and the field receives it through `value`. A change handler sends every keystroke back into state. This fits a page that reacts to every keystroke, such as a live character count or a box that empties after Send.
2. **Uncontrolled**: the browser holds the value, and `defaultValue` gives only the starting text. The code reads every field once, when the form is sent, with the browser's `FormData` object. This fits a form whose values matter only at the moment it is sent.

Both are real choices, and neither is an error. This lesson teaches the controlled way. Choosing between the two belongs to a later lesson on forms.

```tree caption="The two owners a field's value can have: React state or the browser."
Who owns the value of a field
- +Controlled [`value` `onChange`] | **State** holds the value | Fits a page that reacts to **every keystroke**
- +Uncontrolled [`defaultValue` `FormData`] | **The browser** holds the value | Fits a form read **once, when it is sent**
```

### The three browser fields this lesson controls

The browser gives us three kinds of field that a user types into or picks from:
- **The input** is a box with one line of text, such as a name.
- **The textarea** is a box with many lines, for a longer message.
- **The select** is a dropdown list. Each choice inside it is an **option**.

React renders all three as built-in tags with small first letters. Here is one of each:

```jsx title="The three browser fields"
~<input />~ {/* 1. One line of text */}
~<textarea />~ {/* 2. Many lines of text */}
~<select>~ {/* 3. A dropdown list of options */}
  <option value="tea">Tea</option>
  <option value="coffee">Coffee</option>
</select>
```

Each of these fields is a real node in the browser's page. That node keeps its own current value, and the text the user sees in the box is that value. The browser keeps this value whatever React does. This one fact is the root of the whole lesson.

We wrap every field in a **label** tag. The label holds the words that name the field, such as Message. Clicking those words puts the cursor in the field, and a screen reader reads them aloud:

```jsx title="A label wrapped around a field"
<label>Message ~<textarea />~</label> {/* Clicking the word Message puts the cursor in the textarea */}
```

### What this lesson stands on

This lesson builds on six facts from earlier lessons:
- **Curly braces versus quotes**: in JSX, quotes keep the exact characters as text. Curly braces run JavaScript and put the result in place. So `value="John"` is fixed text, and `value={name}` reads a variable.
- **The double ampersand in JSX**: a condition followed by a double ampersand and an element shows the element only when the condition is true.
- **The event object**: React passes an event object `e` to every handler. Its `target` is the element where the event started.
- **Sending a form**: a form's submit handler runs when the user clicks its submit button. Calling `preventDefault` on the event stops the browser from reloading the page.
- **State**: `useState` keeps a value between renders. Its setter asks React for a new render. The starting value is used only on the first render.
- **Render and commit**: after a state change, React renders the component again and changes only the page nodes that differ.

Two small JavaScript tools also appear in this lesson:
- A string's `length` is the number of characters in it. The word Hello has a length of `5`.
- A string's `trim` method gives back a copy of the string without the spaces at its start and its end.

### Six Principles of Controlled Inputs

**PRINCIPLES:** A field keeps its own value inside the browser until React gives it one. Once React gives it a value, React makes the field show that value after every render. Six practical rules follow from that:
1. **Principle 1: An Uncontrolled Box Keeps Its Own Text**: A field with only a starting text keeps whatever the user types. Changing state does not reach it.
2. **Principle 2: The Value and the Change Handler Work as a Pair**: The value carries state into the box. The change handler carries each keystroke back into state. One without the other freezes the box.
3. **Principle 3: The Handler Decides What the Box Shows**: Whatever the handler stores in state is exactly what the box shows next. So the handler stores the typed text as it is.
4. **Principle 4: A Dropdown Is Controlled on the Dropdown Itself**: The chosen item is one piece of text in state, given to the dropdown. It is never marked on one of the options.
5. **Principle 5: A Checkbox Is Controlled by a Yes or No Answer**: A checkbox answers yes or no, so it uses true or false, never text.
6. **Principle 6: The Value Stays a String for the Field's Whole Life**: A controlled field needs a real value from its very first render.

Here is the complete map of those six principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **The Box Keeps Its Own Text** | Emptying state after Send can leave the old message in the box, with no Console message at all. | A field without a value from React is uncontrolled. Its default value is only the starting text. |
| **Principle 2** | **Value and Change Handler Together** | Giving a box only half of the pair makes it refuse every letter. | Pass the value from state and a change handler that stores the typed text in state, always together. |
| **Principle 3** | **The Handler Decides the Text** | A handler that tidies the text while the user types can swallow letters the user really typed. | Store the typed text exactly as it arrives, right away. Tidy it up when the form is sent. |
| **Principle 4** | **Dropdowns Use Value on the Select** | The HTML way of marking the chosen option makes React print an error, and state never hears the choice. | Give the dropdown its value from state, and let each option only list a choice. |
| **Principle 5** | **Checkboxes Use Checked** | Reading a checkbox the way you read a text box breaks the second click. | Give a checkbox a true or false answer from state, and read the new answer from its checked property. |
| **Principle 6** | **A String From the First Render** | A field that starts with no value and later gets text makes React warn. | Start text state as an empty string, so the field is controlled from its very first render. |

## 1. Principle 1: An Uncontrolled Box Keeps Its Own Text, So State Cannot Clear It

### Why state and the box hold two separate copies of the name

Start with one name box and one name in state. The box gets only a starting text. A button empties the name in state:

```jsx title="A starting text in the box, and a name in state"
const [name, setName] = useState('John');

<input ~defaultValue="John"~ /> {/* 1. The box starts with John */}
<button onClick={() => ~setName('')~}>Clear</button> {/* 2. Empties the name in state */}
```

The user types `ny`, and the box shows `Johnny`. Then the user clicks Clear. The name in state becomes an empty string, but the box still shows `Johnny`!

Now look for a line that connects the name in state to the box. There is none. The box got only a starting text, and it never reads the name in state.

Think of the new phone again. It starts with the ringtone the shop chose. After that, it plays whatever its owner picks, and the shop has no say. The box is that phone. Its default value is the shop's first choice.

Two confusions hide here, so let us say them out loud:
- **This box and box C from the opening both show John on the first screen, but they are NOT the same thing!** After that first moment, this box owns its own text. Box C keeps reading state.
- **The name in state and the text in the box both look like "the name", but they are NOT the same thing!** They are two separate copies. In an uncontrolled box, nothing keeps them equal.

```tree caption="In an uncontrolled box, the name in state and the text in the box are two copies with nothing joining them."
Two copies of the name after the user types and clicks Clear
- !The name in state [`name`] | Holds an **empty string** after Clear | Nothing **carries it** into the box
- !The text in the box [`defaultValue="John"`] | Holds **Johnny**, kept by the browser | Nothing **carries it** into state
```

So where is the typed text stored, if no line of our code stores it? The browser stores it. Here is what happens, in order:
1. On the first render, React creates the box with the starting text John.
2. Each key the user presses changes the text inside the box node. React is not asked.
3. The setter changes state and asks for a new render. Nothing on the box tag changed, so React leaves the box's text alone.

### Building the Contact Us form with a message box

Now we build the Contact Us page. The contact form file starts with one piece of state. It says whether the message was sent. The send handler stops the page from reloading and shows the thank-you line:

```jsx title="src/components/ContactForm.jsx" startLine="1"
import { useState } from 'react';

export default function ContactForm() {
  const [sent, setSent] = useState(false);

  function handleSend(e) {
    ~e.preventDefault();~ // 1. Stops the browser from reloading the page
    ~setSent(true);~ // 2. Asks React to show the thank-you line
  }
```

Below the handler, the form returns a heading, the message box, and the Send button. The message box gets an empty starting text:

```jsx title="src/components/ContactForm.jsx" startLine="11"
  return (
    <>
      <h1>Contact Us</h1>
      <form onSubmit={handleSend}>
        <label>
          Message
          ~<textarea defaultValue="" />~ {/* Starts empty, then the browser keeps what the customer types */}
        </label>
        <button type="submit">Send</button>
      </form>
      {sent && <p>Thanks! Your message was sent.</p>}
    </>
  );
}
```

The button's type is submit. A button inside a form sends the form even without a type. Writing the type anyway tells every reader which button sends the form. It also saves a surprise later, when someone adds a second button that should not send anything.

The main file only renders the contact form:

```jsx title="src/App.jsx" startLine="1"
import ~ContactForm~ from './components/ContactForm.jsx'; // Renders the Contact Us form

export default function App() {
  return <ContactForm />;
}
```

The customer types a question and clicks Send. The thank-you line appears, but the question is still in the box:

```page width=text caption="The Contact Us page after the customer types a question and clicks Send, with the message box left uncontrolled."
heading: Contact Us
form:
  textarea: Message | Where is my order? | bad
row: Send
line: Thanks! Your message was sent. | good
```

### Mistake: Emptying state that the box never reads

The developer wants the box to be empty after Send. So the developer adds the message to state, just above the sent flag:

```jsx title="src/components/ContactForm.jsx" startLine="4"
  ~const [message, setMessage] = useState('');~ // New: the message in state, starting empty
  const [sent, setSent] = useState(false);
```

Then the send handler empties that message:

```jsx title="src/components/ContactForm.jsx" startLine="7"
  function handleSend(e) {
    e.preventDefault();
    setSent(true);
    ~setMessage('');~ // **WRONG:** empties the message in state, but the textarea never reads it!
  }
```

The customer types the question again and clicks Send. The question still stays in the box, and the Console shows nothing at all:

```page width=text caption="The Contact Us page after Send when the handler empties state but the message box still has only a starting text."
heading: Contact Us
form:
  textarea: Message | Where is my order? | bad
row: Send
line: Thanks! Your message was sent. | good
console: quiet
```

Here is what happened, in order:
1. The customer typed the question. The browser stored it inside the box node, and the message in state stayed an empty string.
2. The customer clicked Send. The handler set the message in state to an empty string, which it already was.
3. The box has nothing on its tag that reads the message in state. So nothing told the box to change, and the question stayed.

The variable is named message, and the box holds a message. The names match in our heads, but React has no idea they belong together. Joining them is the job of Principle 2.

One more HTML habit belongs here. In an HTML page, you can write the starting text between the opening and closing textarea tags. In React, the box still shows that text, but React prints an error in the Console:

```devconsole
x Use the `defaultValue` or `value` props instead of setting children on <textarea>.
```

So in React, a textarea gets its starting text from its default value.

> [!PRINCIPLE]
> **Principle 1: Uncontrolled Fields: The Box Keeps Its Own Text**
>
> *A field with no value from React keeps whatever the user types, so changing state that the field never reads changes nothing in the box.*
>
> This one surprises everybody once. You put the message in state, you empty the state after Send, and the message is still sitting there in the box. You see, the browser keeps its own copy of the text inside the box, and your state is a second copy that the box never looks at. A default value only says what the box starts with. After that first moment, the box belongs to the browser. So pick one owner. Either leave the box to the browser and read it once at Send, as shown below, or let the box read state, which is the next principle.
>
> **DO THIS:**
> ```jsx
> function handleSend(e) {
>   e.preventDefault();
>   const data = ~new FormData(e.target)~; // Uncontrolled on purpose: read the box once when the form is sent
> }
> <textarea name="message" defaultValue="" />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [message, setMessage] = useState('');
> function handleSend(e) {
>   e.preventDefault();
>   ~setMessage('');~ // **WRONG:** the textarea below never reads message, so the box keeps its text!
> }
> <textarea defaultValue="" />
> ```

## 2. Principle 2: `value` Forces the Box to Show State, and `onChange` Lets Typing Reach State

### A value alone vs. a value with a change handler

Look at two name boxes. Both get a value. Only the second also gets a change handler:

```jsx title="A value alone vs. a value with a change handler"
const [name, setName] = useState('John');

<input ~value="John"~ /> {/* 1. Typing ny leaves John in the box */}
<input value={name} ~onChange={e => setName(e.target.value)}~ /> {/* 2. Typing ny shows Johnny */}
```

The user types `ny` into the first box, and it still shows John. The user types `ny` into the second box. The name in state becomes `'Johnny'`, and the box shows Johnny. When state is emptied, the second box empties too.

Go back to the departure board. The board shows only what the station's system sends. A passenger cannot write on it, but a passenger can hand a request to the station desk. The board changes only after the system accepts that request.

A **value** from React is the system's line on the board. The **change handler** is the request. When the user presses a key, the box tells React: the user wants this text now. Then the handler decides whether state takes it.

Three confusions hide here, so let us say them out loud:
- **A value and a default value both put John in the box at first, but they are NOT the same thing!** A default value sets the text once. A value keeps forcing the text after every render.
- **A fixed value in quotes and a value from state with no change handler are the exact same thing for the user.** Both give a box that refuses every letter.
- **React's change handler and the browser's own change event share a name, but they are NOT the same thing!** We look at that difference next.

```tree caption="A default value, a value alone, and a value with a change handler, and what each does when the user types."
Three ways to put John in a box
- +Default value only [`defaultValue="John"`] | Sets the text **once** | The browser keeps **whatever the user types**
- !Value with no change handler [`value="John"` `value={name}`] | Puts John back **after every key** | The box **refuses every letter**
- +Value plus change handler [`value={name}` `onChange`] | The handler **stores each keystroke** in state | The box shows **what state holds**
```

### React's change handler vs. the browser's change event

In plain browser JavaScript, a text box fires two different events while the user edits it:

```js title="Plain JavaScript: two browser events on one text box"
const box = document.querySelector('input');
box.addEventListener(~'input'~, () => console.log('input')); // 1. Runs on every keystroke
box.addEventListener(~'change'~, () => console.log('change')); // 2. Waits until the user leaves the box
```

The input event runs on every single keystroke. The browser's change event waits until the user finishes and leaves the box.

React's change handler sounds like the browser's change event, but it behaves like the input event. It runs on every keystroke. That is exactly what a controlled box needs, because state must hear every letter.

### Mistake: Giving the box a value without a change handler

Back on the Contact Us page, the developer replaces the starting text with a value from state, and adds nothing else:

```jsx title="src/components/ContactForm.jsx" startLine="17"
        <label>
          Message
          ~<textarea value={message} />~ {/* **WRONG:** a value from state with no change handler freezes the box! */}
        </label>
```

As soon as the page loads, the Console shows a red error. Then the customer types the question, and not a single letter stays in the box:

```page width=text caption="The Contact Us page when the message box has a value from state but no change handler."
heading: Contact Us
form:
  textarea: Message |  | bad
row: Send
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

No line of our code removes the letters. So who removes them? React does. Here is what happens on every key, in order:
1. The customer presses a key, and the browser puts the letter into the box node.
2. No handler stores that letter, so the message in state is still an empty string.
3. React puts the box back to the empty string, because that is the value it was given.

The error names three ways out. Add a change handler when the user should edit the box. Use a default value when the box only needs a starting text. Add the read-only attribute when the box must never change.

### Adding a change handler so each keystroke reaches state

The developer adds a change handler to the message box. It stores the box's new text in state:

```jsx title="src/components/ContactForm.jsx" startLine="17"
        <label>
          Message
          <textarea value={message} ~onChange={e => setMessage(e.target.value)}~ /> {/* Stores every keystroke in state */}
        </label>
```

Look closely at that handler. Our textarea tag never passes an `e`, and it never mentions the new letter. Where do they come from?

React passes the event object `e` to the handler. Its target is the textarea node itself. The browser has already put the new letter into that node, so `e.target.value` holds the whole text, with the new letter included. Here is the first key, in order:
1. The customer presses W. The browser puts W into the textarea node.
2. React calls the change handler with the event. The target's value is `'W'`.
3. The setter stores `'W'` in state and asks for a new render.
4. React renders with the message at `'W'`, and the box shows W.

Now the send handler can empty the box for real. It already sets the message to an empty string. Because the box now reads the message, the box empties too.

A controlled box also lets the page react to every keystroke. We add a live count under the box. It reads the length of the message:

```jsx title="src/components/ContactForm.jsx" startLine="21"
        ~<p>{message.length} / 200</p>~ {/* Counts the characters on every render */}
        <button type="submit">Send</button>
```

The customer types the question, and the count rises with each letter:

```page width=text caption="The Contact Us page while the customer types, with the message box controlled by state and a live count under it."
heading: Contact Us
form:
  textarea: Message | Where is my order? | good
line: 18 / 200 | good
row: Send
console: quiet
```

Then the customer clicks Send. The thank-you line appears, the box is empty, and the count is back to zero:

```page width=text caption="The Contact Us page right after Send, when the handler empties the message in state."
heading: Contact Us
form:
  textarea: Message |  | good
line: 0 / 200 | good
row: Send
line: Thanks! Your message was sent. | good
console: quiet
```

Every keystroke travels the same loop, from the box to state and back to the box:

```tree dir=right caption="The loop that one keystroke travels through in a controlled message box."
One keystroke in a controlled box
- +1. The customer presses a key | The browser puts the letter **into the box node**
- +2. React calls the change handler [`e.target.value`] | The handler reads the **whole new text**
- +3. The setter stores it [`setMessage`] | State takes the new text and asks for **a new render**
- +4. React renders [`value={message}`] | React makes the box show **the text in state**
```

> [!PRINCIPLE]
> **Principle 2: Controlled Fields: The Value and the Change Handler Work as a Pair**
>
> *Give the field its value from state and a change handler that stores the typed text in state, always together.*
>
> The value only carries state into the box. It carries nothing back. So say you give the box a value and forget the change handler. Every letter the user types is thrown away, because React keeps putting the old state back. The change handler is the road back. It runs on every keystroke, reads the new text, and hands it to state. Then the box shows it.
>
> **DO THIS:**
> ```jsx
> const [message, setMessage] = useState('');
> <textarea value={message} ~onChange={e => setMessage(e.target.value)}~ /> // Every keystroke reaches state
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [message, setMessage] = useState('');
> ~<textarea value={message} />~ // **WRONG:** no change handler, so the box refuses every letter!
> ```

## 3. Principle 3: Whatever the Handler Writes Into State Is What the Box Shows

### Why the handler decides what the box shows

Look at three handlers for the same controlled box. Each one does something slightly different with the typed text:

```jsx title="Three handlers for one controlled box"
<input value={name} onChange={e => ~setName(e.target.value)~} /> {/* A. Stores the text as typed */}
<input value={name} onChange={e => ~setName(e.target.value.trim())~} /> {/* B. Stores a copy without outer spaces */}
<input value={name} onChange={e => { if (e.target.value.length <= 5) ~setName(e.target.value)~; }} /> {/* C. Stores only up to 5 characters */}
```

The user types `Ann Lee` into each box:
- **Box A** shows `Ann Lee`.
- **Box B** shows `AnnLee`. The space vanished!
- **Box C** stops at `Ann L`. Every letter after the fifth is refused.

In a controlled box, the text after each keystroke is not simply what the user typed. It is what the handler stored in state. Think of the departure board once more. If the station's system edits a request, the board shows the edited line. If the system ignores the request, the board keeps the old line.

Two confusions hide here, so let us say them out loud:
- **Storing the typed text and storing a trimmed copy look like the same line with a harmless clean-up, but they are NOT the same thing!** For the name Ann, both store the same text. The moment the user types a space, the trimmed version removes it.
- **Box C refusing a letter and a box with no change handler look different, but for that one letter they are the exact same thing.** In both, state does not change, so React puts back the old text.

```tree caption="What three different handlers store when the user types Ann Lee, and so what each box shows."
The user types `Ann Lee` into a controlled box
- +A: Stores the text as typed | State holds **Ann Lee** | The box shows **Ann Lee**
- !B: Stores a trimmed copy | Each space is **removed as it is typed** | The box shows **AnnLee**
- +C: Stores only up to 5 characters | Longer text is **not stored** | The box stops at **Ann L**
```

### Mistake: Trimming the name while the customer types

Now the Contact Us form needs the customer's name. The developer adds the name to state, at the top of the form:

```jsx title="src/components/ContactForm.jsx" startLine="4"
  ~const [name, setName] = useState('');~ // New: the customer's name in state, starting empty
  const [message, setMessage] = useState('');
  const [sent, setSent] = useState(false);
```

The name box goes above the message box. To keep stray spaces out of the name, the developer trims it inside the change handler:

```jsx title="src/components/ContactForm.jsx" startLine="18"
        <label>
          Your name
          <input value={name} onChange={e => ~setName(e.target.value.trim())~} /> {/* **WRONG:** removes every space the moment it is typed! */}
        </label>
```

The customer types `Anna`, then a space. The space does not stay in the box. Then the customer types `Lee`, and the box shows `AnnaLee`:

```page width=text caption="The Contact Us page when the name handler trims the text on every keystroke."
heading: Contact Us

  field: Your name | AnnaLee | bad
  textarea: Message |  | good
line: 0 / 200
row: Send
console: quiet
```

No line of ours removes the space from the box. Our handler only stores text in state. React is the one that changes the box, because it makes the box show the name in state. Here is the space, in order:
1. The customer types a space after Anna. The box node now holds `'Anna '`, with the space.
2. The handler trims it and stores `'Anna'` in state.
3. React makes the box show the name in state, so the space is gone.
4. Next, L arrives, and the box node holds `'AnnaL'`.

### Storing the text as typed and trimming at Send

The fix is to store the typed text exactly as it arrives. The name box goes back to the plain handler:

```jsx title="src/components/ContactForm.jsx" startLine="18"
        <label>
          Your name
          <input value={name} onChange={e => ~setName(e.target.value)~} /> {/* Stores the text exactly as typed */}
        </label>
```

The tidying moves to the send handler. Our page has no server, so the handler prints the trimmed name to the Console. Then it empties the name along with the message:

```jsx title="src/components/ContactForm.jsx" startLine="8"
  function handleSend(e) {
    e.preventDefault();
    ~console.log('Sending message from', name.trim());~ // Tidies the name once, when the form is sent
    setSent(true);
    setName('');
    setMessage('');
  }
```

The customer types `Anna Lee`, and the box shows every letter and the space:

```page width=text caption="The Contact Us page while the customer types, with the plain name handler and the trimming moved to Send."

  field: Your name | Anna Lee | good
  textarea: Message | Where is my order? | good
line: 18 / 200
row: Send
console: quiet
```

When the customer clicks Send, the Console prints the tidy name, and both boxes empty.

### Limiting the message to 200 characters in the handler

The same rule can also work for us. Our count says 200 is the limit. So the message box gets its own handler, written above the send handler. It stores the text only while it is 200 characters or shorter:

```jsx title="src/components/ContactForm.jsx" startLine="8"
  function handleMessageChange(e) {
    if (~e.target.value.length <= 200~) { // Stores the text only while it fits the limit
      setMessage(e.target.value);
    }
  }
```

The message box now uses that handler instead of the short arrow:

```jsx title="src/components/ContactForm.jsx" startLine="30"
        <label>
          Message
          <textarea value={message} ~onChange={handleMessageChange}~ /> {/* Refuses the 201st character */}
        </label>
```

Look for the line that blocks the 201st character. There is none. Our condition only skips the setter, and React does the rest:
1. The 201st letter enters the box node, so the text is 201 characters long.
2. The condition is false, so the setter does not run.
3. React puts the box back to the 200 characters in state, and the count stays at `200 / 200`.

The browser also has its own way to limit length, the `maxLength` attribute. Putting the rule in the handler keeps it inside our component, right next to the count.

Two more kinds of handler break this principle. The first stores a changed copy, such as the text in capital letters. The second stores the text later, inside a timer. React's documentation warns that both make the caret jump. The **caret** is the blinking line that shows where the next letter goes. So the change handler stores the typed text right away.

```tree caption="Where cleaning and limiting belong in a controlled box: in the handler only when you mean it, otherwise at Send."
What a change handler stores
- +The typed text, right away [`e.target.value`] | The box shows **exactly what the user typed** | Tidy it **once, at Send**
- +Nothing, on purpose [`if ... <= 200`] | React **puts the old text back** | A clean way to **refuse extra letters**
- !A changed copy, or the text later in a timer | The box shows **what the user did not type** | Spaces vanish, or **the caret jumps**
```

> [!PRINCIPLE]
> **Principle 3: The Handler Decides the Text: Store What the User Typed**
>
> *In a controlled field, the box shows whatever the handler stored in state, so store the typed text as it arrives and tidy it at Send.*
>
> Here is the trap. It feels like the box shows what the user typed, and your handler just keeps a copy, so a tidier copy seems harmless. But in a controlled box, your copy is the one on the screen! Trim the text while the user types, and every space disappears the moment it is pressed. So let the handler store the text as it is, and do the tidying at Send.
>
> **DO THIS:**
> ```jsx
> <input value={name} onChange={e => ~setName(e.target.value)~} /> // Stores the text exactly as typed
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input value={name} onChange={e => ~setName(e.target.value.trim())~} /> // **WRONG:** every space vanishes the moment it is typed!
> ```

## 4. Principle 4: A Select Is Controlled by `value` on `<select>`, Never `selected` on an `<option>`

### Marking an option in HTML vs. giving the select a value in React

In a plain HTML page, you mark the chosen option by writing the word selected on that option:

```html title="Plain HTML: marking the chosen option"
<select>
  <option value="tea">Tea</option>
  <option value="coffee" ~selected~>Coffee</option> <!-- The HTML habit: the choice is marked on the option -->
</select>
```

React does not support that habit. In React, the choice is written once, as the value of the dropdown itself:

```jsx title="React: the choice is the value of the select"
const [drink, setDrink] = useState('coffee');

<select ~value={drink}~ onChange={e => setDrink(e.target.value)}> {/* The dropdown shows the option whose value matches */}
  <option value="tea">Tea</option>
  <option value="coffee">Coffee</option>
</select>
```

Picture a café. The old way puts a mark next to one item on the printed menu. React's way writes the choice once, on the order slip. The waiter then points at the menu item that matches the slip.

Three confusions hide here, so let us say them out loud:
- **Marking one option and giving the dropdown a value both aim to show Coffee first, but in React they are NOT the same thing!** The mark on the option still shows Coffee first, but React prints an error for it.
- **The dropdown's pair and the message box's pair look like different tools, but they are the exact same pair!** The value carries state in, and the change handler carries the choice out.
- **The word the user sees and the text the handler reads look like the same thing, but they are NOT!** The user sees Coffee. The handler reads `'coffee'`, the value written on the chosen option.

```tree caption="The HTML habit of marking an option vs. React's way of giving the select one value from state."
How to show which option is chosen
- !The HTML habit [`selected` on an option] | The choice is **marked on the option** | ~Do **NOT** use in React: **not supported**
- +The React way [`value` on the select] | The choice is **one piece of text in state** | +**DO** let the options **only list** the choices
```

### Mistake: Writing selected on an option

The Contact Us form needs a topic, so the shop knows where to send the message. The developer adds a Topic dropdown with three options, between the name box and the message box. Out of HTML habit, the developer marks the Delivery option:

```jsx title="src/components/ContactForm.jsx" startLine="30"
        <label>
          Topic
          <select>
            <option value="order">My order</option>
            <option value="delivery" ~selected~>Delivery</option> {/* **WRONG:** shows Delivery, but React prints an error for selected on an option! */}
            <option value="refund">Refund</option>
          </select>
        </label>
```

When the page loads, the dropdown shows Delivery, so the page looks right. But React prints this error in the Console. It tells us to give the dropdown a value instead:

```devconsole
x Use the `defaultValue` or `value` props on <select> instead of setting `selected` on <option>.
```

There is a second problem too. The dropdown now owns its choice, just like the message box in Principle 1. State knows nothing about the topic, so the send handler cannot reset it.

### Controlling the select with a value and a change handler

The developer removes the mark and adds the topic to state. It starts as `'order'`, the value of the first option, because a browser shows the first option when nothing else is chosen:

```jsx title="src/components/ContactForm.jsx" startLine="5"
  ~const [topic, setTopic] = useState('order');~ // New: the topic in state, matching the first option
```

The dropdown gets its value from state and a change handler, just like the message box:

```jsx title="src/components/ContactForm.jsx" startLine="31"
        <label>
          Topic
          <select ~value={topic}~ onChange={e => setTopic(e.target.value)}> {/* Shows the option whose value matches topic */}
            <option value="order">My order</option>
            <option value="delivery">Delivery</option>
            <option value="refund">Refund</option>
          </select>
        </label>
```

Look at that handler again. The word delivery does not appear in it. So where does `'delivery'` come from when the customer picks Delivery?

The browser supplies it. When the user picks an option, the browser sets the dropdown's value to the value written on that option. Here is the pick, in order:
1. The customer picks Delivery. The dropdown node's value becomes `'delivery'`.
2. React calls the change handler. The target is the dropdown, and its value is `'delivery'`.
3. The setter stores `'delivery'` and asks for a new render.
4. React makes the dropdown show the option whose value is `'delivery'`.

The customer picks Delivery, and the dropdown shows it:

```page width=text caption="The Contact Us page after the customer picks Delivery in the controlled Topic dropdown."
heading: Contact Us

  field: Your name | Anna Lee | good
  select: Topic | Delivery | good
  textarea: Message | Where is my order? | good
line: 18 / 200
row: Send
console: quiet
```

The send handler also resets the topic to its first option:

```jsx title="src/components/ContactForm.jsx" startLine="19"
    setName('');
    ~setTopic('order');~ // After Send, the dropdown goes back to My order
    setMessage('');
```

After Send, the dropdown shows My order again.

> [!PRINCIPLE]
> **Principle 4: Controlled Dropdowns: The Choice Lives on the Select, Not on an Option**
>
> *Give the select its value from state and a change handler, matching the value of one option, and never mark an option as selected.*
>
> If you learned HTML first, your hand wants to mark the chosen option. In React that mark is not supported, and React tells you so in the Console. Think of it this way: the choice is one piece of text in state. The dropdown gets it as its value and shows the option that matches. The options only list what can be chosen. It is the same pair you used on the message box.
>
> **DO THIS:**
> ```jsx
> <select ~value={topic}~ onChange={e => setTopic(e.target.value)}> {/* The choice is one string in state */}
>   <option value="order">My order</option>
>   <option value="delivery">Delivery</option>
> </select>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <select>
>   <option value="order">My order</option>
>   <option value="delivery" ~selected~>Delivery</option> {/* **WRONG:** not supported in React, and state never hears the choice! */}
> </select>
> ```

## 5. Principle 5: A Checkbox Is Controlled by `checked`, and Reports Through `e.target.checked`

### Why a checkbox answers true or false

A checkbox is an input with the type checkbox. Look at the same checkbox with two different handlers:

```jsx title="One checkbox, two handlers"
const [agree, setAgree] = useState(false);

<input type="checkbox" checked={agree} onChange={e => setAgree(~e.target.checked~)} /> {/* 1. Reads true or false */}
<input type="checkbox" checked={agree} onChange={e => setAgree(~e.target.value~)} /> {/* 2. Reads text that never changes */}
```

Think of a light switch. Nobody asks a light switch what text it holds. You ask only one question: is it on or off? A checkbox answers that question through **checked**, which is true or false. A checkbox also has a value, but that value is only a label it would send along with a form.

Two confusions hide here, so let us say them out loud:
- **The checked pair is the exact same pair as the value pair, for a box whose answer is yes or no.** Checked carries state in, and the change handler reads the new checked answer out.
- **A checkbox's value and its checked answer both sit on the same box, but they are NOT the same thing!** The value stays the same whether the box is ticked or not. The checked answer flips with every click.

```tree caption="The two pairs that control the three kinds of field."
Which pair controls which field
- +Text boxes and dropdowns [`value` `e.target.value`] | They answer with **text** | The handler reads **the new text**
- +Checkboxes [`checked` `e.target.checked`] | They answer **yes or no** | The handler reads **true or false**
```

### Mistake: Reading the value of a checkbox

The Contact Us form should ask whether the customer wants an email reply. The developer adds that answer to state, starting unticked:

```jsx title="src/components/ContactForm.jsx" startLine="7"
  ~const [wantsReply, setWantsReply] = useState(false);~ // New: whether the customer wants a reply, starting unticked
```

Under the count, the developer adds a checkbox with its checked answer from state. Then the developer copies the change handler from the text boxes:

```jsx title="src/components/ContactForm.jsx" startLine="46"
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.value~)} /> {/* **WRONG:** a checkbox's value is the same text on every click! */}
          Email me a reply
        </label>
```

The customer ticks the box, and it shows ticked. Then the customer clicks again to untick it, and it stays ticked:

```page width=text caption="The Contact Us page after the customer clicks the checkbox twice, when its handler reads the value instead of the checked answer."
heading: Contact Us
form:
  field: Your name | Anna Lee | good
  select: Topic | Delivery | good
  textarea: Message | Where is my order? | good
line: 18 / 200
form:
  check: Email me a reply | on | bad
row: Send
console: quiet
```

Our checkbox tag has no value attribute. So what text does the handler read? The browser supplies it. A checkbox with no value attribute has the value `'on'`. Here is each click, in order:
1. The first click gives the handler the text `'on'`.
2. The setter stores `'on'`. It is text that is not empty, so React treats it as ticked.
3. The second click gives the handler `'on'` again. State still says ticked, so React puts the tick back.

### Reading checked instead of value

The fix is to read the checked answer, which is true or false:

```jsx title="src/components/ContactForm.jsx" startLine="46"
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* Reads true or false */}
          Email me a reply
        </label>
```

Our handler never flips anything from false to true. So who does the flipping? The browser does, before React calls our handler:
1. The click flips the box node's checked answer to true.
2. The handler reads that answer, true, and stores it.
3. React renders and makes the box show true, a tick.

Now each click ticks or unticks the box:

```page width=text caption="The Contact Us page after the customer ticks the checkbox, when its handler reads the checked answer."
heading: Contact Us
form:
  field: Your name | Anna Lee | good
  select: Topic | Delivery | good
  textarea: Message | Where is my order? | good
line: 18 / 200
form:
  check: Email me a reply | on | good
row: Send
console: quiet
```

The send handler also unticks the box after Send:

```jsx title="src/components/ContactForm.jsx" startLine="22"
    setMessage('');
    ~setWantsReply(false);~ // After Send, the checkbox is unticked again
```

A checked answer with no change handler freezes the box, just like a value with no change handler. React prints a matching error that suggests a default checked answer instead. Radio buttons work like checkboxes too. They are controlled by checked, and their value is only the label sent with a form.

> [!PRINCIPLE]
> **Principle 5: Controlled Checkboxes: Use Checked and Read the Checked Answer**
>
> *Control a checkbox with a true or false checked answer from state, and read the new answer from the target's checked property, never its value.*
>
> This one is sneaky because the first click works. A checkbox's value is just a label. It is the same text on every click, so a handler that stores the value stores the same thing forever. The tick goes on and never comes off. A checkbox answers yes or no, so ask it the yes or no question: read checked.
>
> **DO THIS:**
> ```jsx
> <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* true or false */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.value~)} /> {/* **WRONG:** always 'on', so the box never unticks! */}
> ```

## 6. Principle 6: The `value` Is a String From the First Render to the Last

### No starting value vs. an empty string

Look at two address boxes. The only difference is the starting value in state:

```jsx title="A box that starts with no value vs. a box that starts with an empty string"
const [city, setCity] = ~useState()~; // 1. No starting value: city is undefined
const [street, setStreet] = ~useState('')~; // 2. Starts as an empty string

<input value={city} onChange={e => setCity(e.target.value)} />
<input value={street} onChange={e => setStreet(e.target.value)} />
```

Both boxes look empty when the page opens. Now the user types P into each box. The first box makes React print a red error in the Console. The second box stays quiet.

Where does the first box get its starting value? In plain JavaScript, a missing argument becomes `undefined`:

```js title="Plain JavaScript: a missing argument is undefined"
function greet(name) {
  return name;
}
~greet()~; // Gives undefined, because no name was passed
```

So calling the state hook with nothing inside gives `undefined` as the starting value. React reads a value of `undefined` as no value at all, and that makes the box uncontrolled.

Picture a departure board that starts the day unplugged from the station's system. Staff write on it by hand. Halfway through the day, someone plugs it in. Now nobody knows who is in charge of the board, and React complains.

One confusion hides here, so let us say it out loud:

**Starting with nothing and starting with an empty string both show an empty box at first, but they are NOT the same thing!** `undefined` means no value, so the box starts uncontrolled. An empty string is a real value, so the box is controlled from the start.

```tree caption="Starting state with no value vs. with an empty string, and what happens on the first letter."
How a text box starts in state
- !No starting value [`city` is `undefined`] | The box starts **uncontrolled** | The first letter makes React **warn**
- +An empty string [`street` is `''`] | The box is **controlled from the start** | Typing stays **quiet**
```

### Mistake: Starting state with no value

When the customer asks for a reply, the shop needs an email address. The developer adds the email to state with no starting value:

```jsx title="src/components/ContactForm.jsx" startLine="8"
  const [email, setEmail] = ~useState()~; // **WRONG:** no starting value, so email starts as undefined!
```

The email box appears only while the reply checkbox is ticked:

```jsx title="src/components/ContactForm.jsx" startLine="52"
        {wantsReply && (
          <label>
            Email
            <input type="email" ~value={email}~ onChange={e => setEmail(e.target.value)} /> {/* The value is undefined at first */}
          </label>
        )}
```

The customer ticks the checkbox, and the empty email box appears. The Console is quiet. Then the customer types the letter a, and a red error appears:

```page width=text caption="The Contact Us page after the customer ticks the checkbox and types one letter into an email box that started with no value."
heading: Contact Us
form:
  field: Your name | Anna Lee | good
  select: Topic | Delivery | good
  textarea: Message | Where is my order? | good
line: 18 / 200
form:
  check: Email me a reply | on | good
form:
  field: Email | a | bad
row: Send
console: A component is changing an uncontrolled input to be controlled.
```

We never wrote `undefined` anywhere in the email lines. JavaScript supplied it, because the state hook got no argument. Here is what happens, in order:
1. The email box appears with a value of `undefined`. React treats it as uncontrolled.
2. The customer types a, and the handler stores `'a'` in state.
3. React renders with a real text value. The box is now controlled, so React warns that it changed its kind.

A field cannot switch between the two kinds during its life. React cannot tell whether we wanted the browser in charge or state in charge.

### Starting the email as an empty string

The fix is to start the email as an empty string:

```jsx title="src/components/ContactForm.jsx" startLine="8"
  const [email, setEmail] = ~useState('')~; // A real value from the very first render
```

Now the box is controlled from its very first render. The customer ticks the checkbox, types an email address, and no error appears:

```page width=text caption="The Contact Us page with the email box starting as an empty string, after the customer types an address."
heading: Contact Us
form:
  field: Your name | Anna Lee | good
  select: Topic | Delivery | good
  textarea: Message | Where is my order? | good
line: 18 / 200
form:
  check: Email me a reply | on | good
form:
  field: Email | anna@example.com | good
row: Send
console: quiet
```

Sometimes the value comes from somewhere we do not control, such as a saved draft from a server. It may arrive as `null` or `undefined`. Then we fix it at the tag with the double question mark operator. It gives the right side whenever the left side is `null` or `undefined`:

```jsx title="Turning a missing value into an empty string at the tag"
<input type="email" ~value={email ?? ''}~ onChange={e => setEmail(e.target.value)} /> {/* An empty string when email is missing */}
```

**Starting state as an empty string and turning a missing value into an empty string at the tag are the exact same fix, from two sides.** Either way, the box gets a real string on every render.

The same rule holds for checkboxes. A checked answer must always be true or false, never missing. That is why the reply checkbox starts at false.

Last, the send handler empties the email too. Now Send resets all five fields:

```jsx title="src/components/ContactForm.jsx" startLine="24"
    setWantsReply(false);
    ~setEmail('');~ // After Send, the email goes back to an empty string, never undefined
```

> [!PRINCIPLE]
> **Principle 6: A String From the First Render: Never Start a Controlled Field Empty-Handed**
>
> *A controlled field must get a text value on every render, starting from the first, so start text state as an empty string rather than leaving it undefined.*
>
> An empty box and a box with no value look identical, and that is the trap. If state starts with nothing, the value is undefined, and React treats the box as one the browser owns. The first letter turns it into a box that state owns, and React warns that the field changed its kind. Start with an empty string, and the box belongs to state from its very first moment.
>
> **DO THIS:**
> ```jsx
> const [email, setEmail] = ~useState('')~; // A real value from the first render
> <input type="email" value={email} onChange={e => setEmail(e.target.value)} />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [email, setEmail] = ~useState()~; // **WRONG:** undefined at first, so the first letter makes React warn!
> <input type="email" value={email} onChange={e => setEmail(e.target.value)} />
> ```

## Putting All Six Principles Together

### The complete project files

Here is our main file, which renders the contact form:

```jsx title="src/App.jsx"
import ~ContactForm~ from './components/ContactForm.jsx'; // Renders the Contact Us form
```

And here is the complete contact form file. Every field gets its value from state and a change handler. Text state starts as an empty string, and Send resets all five fields:

```jsx title="src/components/ContactForm.jsx"

  const [name, setName] = useState('');
  const [topic, setTopic] = useState('order');
  const [message, setMessage] = useState('');
  const [wantsReply, setWantsReply] = useState(false);
  const [email, setEmail] = ~useState('')~; // Principle 6: a string from the very first render
  const [sent, setSent] = useState(false);

  function handleMessageChange(e) {
    if (~e.target.value.length <= 200~) { // Principle 3: refuses the 201st character on purpose
      setMessage(e.target.value);
    }
  }

  function handleSend(e) {
    e.preventDefault();
    console.log('Sending message from', name.trim());
    setSent(true);
    setName('');
    setTopic('order');
    setMessage('');
    setWantsReply(false);
    setEmail('');
  }

  return (
    <>
      <h1>Contact Us</h1>
      <form onSubmit={handleSend}>
        <label>
          Your name
          <input value={name} onChange={e => setName(e.target.value)} />
        </label>
        <label>
          Topic
          <select value={topic} onChange={e => setTopic(e.target.value)}>
            <option value="order">My order</option>
            <option value="delivery">Delivery</option>
            <option value="refund">Refund</option>
          </select>
        </label>
        <label>
          Message
          <textarea value={message} onChange={handleMessageChange} />
        </label>
        <p>{message.length} / 200</p>
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* Principle 5: a yes or no answer */}
          Email me a reply
        </label>
        {wantsReply && (
          <label>
            Email
            <input type="email" value={email} onChange={e => setEmail(e.target.value)} />
          </label>
        )}
        <button type="submit">Send</button>
      </form>
      {sent && <p>Thanks! Your message was sent.</p>}
    </>
  );
}
```

Here is each tempting habit next to the React rule that replaces it:

| Aspect | The Tempting Habit | The React Rule |
| :--- | :--- | :--- |
| **Who owns the text** | Let the box keep the text and empty a separate copy in state, which leaves the old text in the box | Give the box its value from state, so state is the single source of truth |
| **Hearing the typing** | Give the box a value and nothing else, which freezes it with a Console error | Pair the value with a change handler that stores the typed text |
| **Tidying the text** | Trim or change the text while the user types, which swallows spaces or makes the caret jump | Store the text as it arrives, and tidy it once at Send |
| **Dropdowns** | Mark the chosen option with the selected attribute, which React does not support | Give the select its value from state, matching one option's value |
| **Checkboxes** | Read the value, which is the same text on every click | Use checked and read the true or false answer |
| **The first render** | Start state with no value, so the field changes its kind on the first letter | Start text state as an empty string, or turn a missing value into one at the tag |

## For the Interview

> **The Interview Question:** How do you make an input, textarea, or select fully controlled by React state?

### How to Answer Clearly in 30 Seconds

"By default, a field is uncontrolled. The browser keeps its value, and `defaultValue` only sets the starting text. To control it, I keep the value in state and pass it as `value`, or as `checked` for a checkbox. React then makes the field show that state after every render, so state becomes the single source of truth. I always pair it with `onChange`, which runs on every keystroke like the browser's `input` event, and I store `e.target.value` in state right away. Without `onChange`, the field is read-only and React logs an error. Whatever I store is exactly what the field shows, so I never trim or reformat while the user types. I tidy the text on submit instead. The same pair works for a textarea, and for a select, where `value` goes on the select and never `selected` on an option. A checkbox uses `checked` and reads `e.target.checked`. Finally, a controlled field must get a string from its very first render. I start state as an empty string, or I write `value={draft ?? ''}`. Otherwise React warns that an uncontrolled input became controlled."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What happens if you pass `value` without `onChange`, and what are the alternatives?"**
   The field becomes read-only. The browser puts each typed letter into the node, but no handler updates state, so React puts the old value back after every keystroke. React also logs an error: "You provided a `value` prop to a form field without an `onChange` handler." The error names three ways out. Add `onChange` if the user should edit the field. Use `defaultValue` if you only need a starting value. Add `readOnly` if the field must never change.
2. **"Why does a controlled field lose spaces or make the caret jump when the handler changes the text?"**
   In a controlled field, the text on screen is the state value, not the typed text. If the handler stores a trimmed copy, every space is removed the moment it is typed. If it stores an uppercase copy, or stores the value later inside a `setTimeout`, the caret jumps to the end of the text. It jumps even when the user was typing in the middle. The rule is to store `e.target.value` right away, exactly as typed, and to clean the data on submit. Refusing a keystroke on purpose, such as a 200-character limit, is fine: React simply keeps the old value.
3. **"Why does React warn that a component is changing an uncontrolled input to be controlled, and how do you fix it?"**
   React decides whether a field is controlled by looking at its value. Calling `useState` with no argument gives `undefined`, and `value={undefined}` means no value, so the field starts uncontrolled. When the first keystroke stores a string, the field becomes controlled, and a field cannot switch kinds during its life. The fix is to start state as an empty string. For data from a server that may be `null`, write `value={someValue ?? ''}`. For checkboxes, `checked` must always be a boolean.

```tree dir=right caption="Interview comparison: an uncontrolled field, a half-controlled field, and a fully controlled field."
Three ways to wire a form field in an interview
- !Uncontrolled [`defaultValue`] | The **browser** keeps the value | State changes **never reach the field**
- !Value without a change handler [`value={message}`] | React puts **the old value back** | The field is **read-only** and React **logs an error**
- +Fully controlled [`value` `onChange`] | State starts as **an empty string** and is the **single source of truth** | The page can **count, limit, and clear** the field
```
