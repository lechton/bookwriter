# Lecture 20: Controlled Inputs: Letting State Decide What Every Box Shows
> INTERVIEW QUESTION | ❱ CORE | How do you make an input, textarea, or select fully controlled by React state?

---

## Why a Form Needs Its Text in State

### The smallest controlled box: a name, a greeting, and a Clear button

Here is a tiny page with one box, one greeting, and one button. When the page opens, the box is empty:

```page width=text caption="The name page when it opens: an empty Name box, a greeting, and a Clear button."
form:
  field: Name |
line: Hello,
form:
  button: Clear
```

This is all the code behind it:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [name, setName] = useState('');

  return (
    <main>
      <label>
        Name
        <input value={name} onChange={e => setName(e.target.value)} />
      </label>
      <p>Hello, {name}</p>
      <button ~onClick={() => setName('')}~>Clear</button> {/* Clear changes only the state */}
    </main>
  );
}
```

The user types John. The greeting follows the box, letter by letter:

```page width=text caption="The same page after the user types John into the Name box."
form:
  field: Name | John | good
line: Hello, John | good
form:
  button: Clear
```

Then the user clicks Clear, and both the box and the greeting are empty again:

```page width=text caption="The same page after the user clicks Clear: the box and the greeting are both empty."
form:
  field: Name | | good
line: Hello,
form:
  button: Clear
```

Look at the Clear button once more. Its code only puts an empty string into `name`. No line of our code touches the box. So who empties the box?

The two props on the box do. React understands both of them on every input:
- **`onChange`** is our function, and React calls it every time the user changes the text in the box. Here it saves the new text in `name`.
- **`value`** tells React what the box must show. Here it says: show whatever `name` holds right now.

Now the click makes sense. Here is what happens, in order:
1. The user clicks Clear, and `setName` saves an empty string in `name`.
2. React renders `App` again.
3. The greeting reads `name`, so it shows only Hello.
4. The box also reads `name`, through `value`. So React makes the box empty too.

Think of a classroom whiteboard. The students call out their answers, but only the teacher writes on the board. The board shows only what the teacher wrote. Our box works the same way. The user calls out letters through `onChange`. Only our state writes the text. The box shows only what state holds, through `value`.

A box that works like this is called a **controlled** box, because React state controls what it shows. Principles 1 and 2 look at each of the two props on its own.

### The real page: a contact form that counts and clears

Now think of the contact form of an online shop. Under the message box, a small line counts the letters as the user types, such as 12 / 200. This form needs two things from its boxes.

First, the count must change on every key. So the text must reach state on every key, not only when the user clicks Send.

Second, after Send, every box must be empty again, ready for the next message. Our code empties the state. So state must be able to reach back into the box and empty it too.

A box that only reports to state fails the second job. A box that only listens to state fails the first job. This lecture shows how one box does both jobs.

### Our example page: the Contact Us form

Our page is the **Contact Us** form of an online shop. It has a Name box, a Topic menu, a Message box with its count, a tick box called Email me a reply, and a Send button. When the tick box is ticked, an Email box appears. Here is the finished page:

```page width=text caption="The finished Contact Us form, as it looks when the page opens."
heading: Contact Us
form:
  field: Name |
  select: Topic | Delivery
  textarea: Message |
line: 0 / 200
form:
  check: Email me a reply | off
  submit: Send
```

The project has four files. The whole form lives in one component, `ContactForm`:

```files title="contact-page: File Explorer" caption="How the files of our contact page sit inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` and mounts it inside `<StrictMode>` into `#root`
  App.jsx | parent | Exports `App` as default and renders `<ContactForm />`
  components/
    ContactForm.jsx | default export | Exports `ContactForm` as default and holds every box and its state
```

The main component only places the form on the page:

```jsx title="src/App.jsx"
import ContactForm from './components/ContactForm.jsx';

export default function App() {
  return ~<ContactForm />~; // React calls ContactForm, which holds the whole form
}
```

We start with only the message box and its count. Each principle adds one more part, until the form is finished.

A few ideas from earlier lessons come back here:
- `useState` keeps a value between renders, and calling its setter makes React render the component again, from Lesson 12.
- React hands every event handler an event object `e`, and `e.target` is the element where the event started, from Lesson 11.
- Inside a handler on a box, `e.target.value` is the text in the box, which you met once in Lesson 17.
- A form's submit handler calls `e.preventDefault` so the browser does not reload the page, also from Lesson 11.
- A `<label>` around a box makes its text clickable, and a tick box keeps its own tick inside the browser, from Lesson 18.

### Five Principles of Controlled Inputs

**PRINCIPLES:**
1. **`onChange` sends every key into state.** React calls it on every key, so the count can follow each letter.
2. **`value` sends state back into the box.** Then setting state is enough to empty the box after Send. A prop that only sets the starting text cannot do this.
3. **`value` without `onChange` freezes the box.** React puts the old text back after every key, and the Console shows an error.
4. **A menu and a tick box use the same pair.** The menu takes its choice from state. The tick box takes its tick from state, and its handler reads the tick, not the text.
5. **A controlled box starts with an empty string.** If it starts with nothing at all, React warns as soon as the user types.

Here is the map of the five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`onChange` Sends Every Key into State** | A count or a greeting that never moves means the typed text never reached state. Interviewers also ask why React's `onChange` fires on every key. | Give the box `onChange`, and save the new text with the setter on every key. |
| **Principle 2** | **`value` Sends State Back into the Box** | A form that keeps its old text after Send, while the count says zero, is the most common form bug. | Give the box `value` from state, so the box always shows what state holds. |
| **Principle 3** | **`value` Without `onChange` Freezes the Box** | A box that refuses every letter looks broken, and the Console error explains why. | Every box with `value` also needs `onChange` that saves the new text right away. |
| **Principle 4** | **The Same Pair on a Menu and a Tick Box** | A tick box that will not untick, or a menu that ignores its starting choice, comes from the habits of plain HTML. | Put the chosen value on the menu itself. Give the tick box its tick from state, and read the tick back from the browser. |
| **Principle 5** | **A Controlled Box Starts with an Empty String** | A warning about a box changing from uncontrolled to controlled appears on the first key, and confuses many developers. | Start the state behind every box with an empty string, never with nothing. |

## 1. Principle 1: `onChange` Sends Every Key into State

### The smallest version: a greeting that follows each letter

Let's take the name box apart and look at one prop at a time. First, we keep only `onChange`, and leave out `value` for now. When the page opens, the box is empty and the greeting says only Hello:

```page width=text caption="A Name box and a greeting, when the page opens."
form:
  field: Name |
line: Hello,
```

The box hands each change to our code:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [name, setName] = useState('');

  return (
    <main>
      <label>
        Name
        <input ~onChange~={e => setName(e.target.value)} /> {/* React calls this arrow on every key */}
      </label>
      <p>Hello, {name}</p>
    </main>
  );
}
```

The user types J, and the greeting says Hello, J. Then o, and it says Hello, Jo. After four keys, the page looks like this:

```page width=text caption="The same page after the user types John: the greeting has followed every letter."
form:
  field: Name | John | good
line: Hello, John | good
```

You met **`onChange`** at the start of the lecture. React understands it on every input, text area, and menu. React calls it each time the user changes the text in the box. That means on every single key, not only when the user leaves the box.

Our arrow takes the text from `e.target.value` and saves it with `setName`. The new state makes React render the greeting again.

Think of a student who calls out each letter to the teacher while writing a word on paper. The teacher hears every letter, not only the finished word.

### The message box and its live count

Now we build the first part of our contact form: a heading, a Message box, and the count under it.

```jsx title="src/components/ContactForm.jsx"
import { useState } from 'react';

export default function ContactForm() {
  const [message, setMessage] = useState('');

  function handleMessageChange(e) {
    setMessage(e.target.value);
  }

  return (
    <section>
      <h1>Contact Us</h1>
      <form>
        <label>
          Message
          <textarea ~onChange={handleMessageChange}~ /> {/* React calls the handler on every key */}
        </label>
        <p>{message.length} / 200</p>
      </form>
    </section>
  );
}
```

The count uses `.length`, the number of characters in a string. When the page opens, `message` is empty, so the count shows zero:

```page width=text caption="The first version of the Contact Us form, when the page opens."
heading: Contact Us
form:
  textarea: Message |
line: 0 / 200
```

The user types Where is my parcel? and the count moves with every letter:

```page width=text caption="The same form after the user types Where is my parcel? into the Message box."
heading: Contact Us
form:
  textarea: Message | Where is my parcel?
line: 19 / 200 | good
```

The count changed after every single letter. Who tells our code about each letter? Here is what happens on every key, in order:
1. The user presses a key in the Message box.
2. The browser puts the letter into the box first.
3. Only then does React call `handleMessageChange`, and it hands over the event object.
4. `e.target.value` reads the whole text of the box, so the new letter is already inside.
5. `setMessage` saves that text in state.
6. React renders `ContactForm` again, and the count shows the new length.

### React's `onChange` and the browser's `change` event are NOT the same

If you have written plain JavaScript, this may surprise you. The browser has its own event called `change`, and it does not fire on every key. In plain JavaScript, there are two different events you can listen to on a text box:

```js title="page.js"
messageBox.addEventListener(~'change'~, e => console.log(e.target.value)); // Runs only when the user leaves the box
messageBox.addEventListener(~'input'~, e => console.log(e.target.value)); // Runs on every key
```

The browser's `change` event waits until the user is done with the box and clicks somewhere else. The browser's `input` event fires on every change.

React's `onChange` behaves like the second line, the `input` event. So the two share a name, but they are NOT the same. The browser's `change` event waits for the user to leave the box. React's `onChange` fires on every key.

React also accepts `onInput`, which does the same job. React code uses `onChange` by long habit, so this book uses it too.

### Mistake: keeping the message in a plain variable

A developer new to React might keep the text in a plain variable, the way plain JavaScript does:

```jsx title="src/components/ContactForm.jsx" bad="2,5"
export default function ContactForm() {
  let message = '';

  function handleMessageChange(e) {
    ~message~ = e.target.value; // **WRONG:** changes a plain variable, so React never renders again
  }

  return (
    <section>
      <h1>Contact Us</h1>
      <form>
        <label>
          Message
          <textarea onChange={handleMessageChange} />
        </label>
        <p>{message.length} / 200</p>
      </form>
    </section>
  );
}
```

The user types Hi. The box shows Hi, but the count stays at zero:

```page width=text caption="The contact form with a plain variable, after the user types Hi."
heading: Contact Us
form:
  textarea: Message | Hi
line: 0 / 200 | bad
```

Why does the box show Hi while the count stays at zero? Here is what happens on each key:
1. The browser puts the letter into the box. The box has no `value` yet, so the browser keeps the letter there on its own.
2. React calls `handleMessageChange`, and the handler changes the plain variable.
3. Changing a plain variable does not ask React to render again. So React never calls `ContactForm` again.
4. The count on the page is still the one React drew when the page opened, and it says zero.

There is a second problem. Even if something else made React render again, the first line of the component would run again. It would set `message` back to an empty string.

The fix is the state from Lesson 12. The setter keeps the text between renders and asks React to render again:

```jsx title="src/components/ContactForm.jsx" good="4,7"
import { useState } from 'react';

export default function ContactForm() {
  const [message, setMessage] = useState('');

  function handleMessageChange(e) {
    ~setMessage~(e.target.value); // Saves the text and asks React to render again
  }
```

Now the count follows every letter, as in the preview before.

### Inside the handler, `message` is still one letter behind

There is one more trap here. Suppose we add a log line to the handler for a moment:

```jsx title="src/components/ContactForm.jsx" startLine="6"
  function handleMessageChange(e) {
    console.log(~message~); // Shows the text from before this key
    setMessage(e.target.value);
  }
```

The box holds Wher, and the user types e. The Console shows Wher, not Where. Why the old text?

In Lesson 15, you saw that each render sees its own fixed state values. The handler belongs to a render too. Here is the order:
1. When the box held Wher, React rendered `ContactForm`. In that render, `message` is Wher, and the handler is made in that same render.
2. The user types e, and the browser puts it into the box.
3. React calls the handler from that render. Inside it, `message` is still Wher.
4. `setMessage` saves Where, but only the next render will see it.

So inside the handler, the new text lives only in `e.target.value`. That is why the handler saves `e.target.value`, and never builds the new text from `message`. We take the log line out again before we go on.

> [!PRINCIPLE]
> **Principle 1: `onChange`: React Calls It on Every Key**
>
> *When the page must react to what the user types, give the box `onChange` and save `e.target.value` with the setter.*
>
> The count must move while the user types, so the text must reach state on every key. React's `onChange` is not the browser's `change` event, which waits for the user to leave the box. It fires on every key, like the browser's `input` event. By the time it runs, the browser has already put the new letter into the box, so `e.target.value` holds the whole new text. A plain variable cannot do this job, because changing it never makes React render again.
>
> **DO THIS:**
> ```jsx
> const [message, setMessage] = useState('');
> <textarea ~onChange~={e => setMessage(e.target.value)} /> {/* Saves the whole text on every key */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> let message = '';
> <textarea onChange={e => { ~message~ = e.target.value; }} /> {/* **WRONG:** a plain variable never makes React render again */}
> ```

## 2. Principle 2: `value` Sends State Back into the Box

### The smallest version: one Clear button, two different boxes

Go back to the name page from the start of the lecture. We change only one prop on the box, and try it two ways. In both versions, the user types John and then clicks Clear:

::: row caption="The same name page with two different props on the box, after the user types John and clicks Clear."
::: col title="defaultValue on the box" tag="box keeps John" tone=bad
```jsx title="src/App.jsx" startLine="10"
<input ~defaultValue=""~ onChange={e => setName(e.target.value)} /> {/* Sets only the starting text */}
```
```page size=mini
form:
  field: Name | John | bad
line: Hello,
form:
  button: Clear
```
The greeting is empty, but the box still shows John.
:::
::: col title="value on the box" tag="box empties" tone=good
```jsx title="src/App.jsx" startLine="10"
<input ~value={name}~ onChange={e => setName(e.target.value)} /> {/* Shows whatever name holds */}
```
```page size=mini
form:
  field: Name | | good
line: Hello,
form:
  button: Clear
```
The greeting and the box are both empty.
:::
:::

### Why the box with `defaultValue` keeps John

While the user types, the two boxes behave exactly the same. Only Clear shows the difference. So why does the left box keep John?

The answer is in what `defaultValue` does. **`defaultValue`** is a React prop that gives the box its starting text, and nothing more. React writes it into the box once, when the box first appears. After that, the box keeps whatever the user types, and React never changes it again.

Here is what happens in the left column after the click, in order:
1. The user clicks Clear, and `setName` saves an empty string.
2. React renders `App` again. The greeting reads `name`, so it shows only Hello.
3. The box has no `value` prop. Its `defaultValue` was used once, when the page opened. So on this render, React writes nothing into the box.
4. The browser still holds John inside the box, so the box keeps it.

**`value`** works the other way. It is a React prop too, and React writes it into the box after every render. In the right column, the first two steps are the same. Then the steps change:
1. React reads `value`, and `name` is now an empty string.
2. React writes that empty text into the box.
3. The box is empty, just like the greeting.

React's documentation says it plainly: with `defaultValue`, your code "only specifies the initial value. It does not control what the value should be right now."

Think of a student's own notebook. On the first day, the teacher writes one line on page one. That is `defaultValue`. After that, the student writes freely, and the teacher cannot erase anything from the front of the room. A box like this, without `value`, is called an **uncontrolled** box. It keeps its own text.

A box with `value` from state and `onChange` back into state is the whiteboard from the start of the lecture. It is a **controlled** box. React's documentation puts it this way: "React will force the input to always have the `value` you passed."

### With `value`, why can I still type?

If React forces the box to show `name`, how does a new letter get in? Here is what happens on every key in the right column:
1. The user presses a key, and the browser shows the letter in the box.
2. React calls `onChange`, and `setName` saves the new text.
3. React renders again, and `value` is now the new text.
4. React writes that same text into the box, so the letter stays.

The letter survives because state already holds it when React writes the box again.

### The Send button that empties state, but not the box

Back to our contact form. Now we add a Send button. When the form is sent, our code logs the message and empties the state, so the form is ready for the next message:

```jsx title="src/components/ContactForm.jsx" startLine="10"
  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', message);
    ~setMessage('')~; // Empties the state after sending
  }
```

The developer wants the Message box to start empty, so they give it `defaultValue` with an empty string:

```jsx title="src/components/ContactForm.jsx" startLine="16" bad="7"
  return (
    <section>
      <h1>Contact Us</h1>
      <form onSubmit={handleSend}>
        <label>
          Message
          <textarea ~defaultValue=""~ onChange={handleMessageChange} /> {/* **WRONG:** starting text only, so Send cannot empty the box */}
        </label>
        <p>{message.length} / 200</p>
        <button type="submit">Send</button>
      </form>
    </section>
  );
}
```

While the user types Where is my parcel? everything works, and the count says 19 / 200. Then the user clicks Send:

```page width=text caption="The contact form with defaultValue, after the user types Where is my parcel? and clicks Send."
heading: Contact Us
form:
  textarea: Message | Where is my parcel? | bad
line: 0 / 200 | bad
form:
  submit: Send
log: Sent: Where is my parcel? | ContactForm.jsx:12
```

The count says the box is empty, but the old message is still in the box. Who is right? Here is what happened, in order:
1. While the user typed, each key ran `handleMessageChange`, and `message` held the text.
2. The user clicked Send, and `handleSend` saved an empty string with `setMessage`.
3. React rendered again. `message` is now empty, so the count shows zero.
4. The text area has no `value` prop. So React writes no text into it on this render.
5. The browser still holds the typed text inside the box, so the box keeps it.

So state is right, and the box is out of date. If the user clicks Send again, the Console proves it. The second log is empty, because state holds an empty string:

```page width=text caption="The same form after the user clicks Send a second time without typing anything."
heading: Contact Us
form:
  textarea: Message | Where is my parcel? | bad
line: 0 / 200 | bad
form:
  submit: Send
log: Sent: Where is my parcel? | ContactForm.jsx:12
log: Sent: | ContactForm.jsx:12
```

### The fix: `value={message}` on the text area

The fix is one prop on the text area:

```jsx title="src/components/ContactForm.jsx" startLine="20" good="3"
        <label>
          Message
          <textarea ~value={message}~ onChange={handleMessageChange} /> {/* The box always shows what message holds */}
        </label>
```

After a reload, the user types the same message and clicks Send. Now the box and the count are both empty:

```page width=text caption="The contact form with value, after the user types Where is my parcel? and clicks Send."
heading: Contact Us
form:
  textarea: Message | | good
line: 0 / 200 | good
form:
  submit: Send
log: Sent: Where is my parcel? | ContactForm.jsx:12
```

No line of our code empties the box itself. So why is it empty now? Here is the order:
1. `setMessage` saves an empty string.
2. React renders `ContactForm` again.
3. React reads `value` on the text area. It is now an empty string, so React writes that empty text into the box.
4. The box is empty, and the count shows zero.

### State is the single source of truth

Our page now shows the message in two places: the box and the count. Both copy the same state. Think of a train station with one main clock. Every platform screen copies that clock. When the clock changes, every screen changes with it. Nobody sets a platform screen by hand.

State is our main clock. The box and the count are the screens. This idea is called a **single source of truth**: one place holds the text, and everything on the page copies it. To change what the box shows, we never touch the box. We change the state.

### An empty `defaultValue` and `value={message}` are NOT the same

When the page opens and `message` is empty, both versions draw the exact same empty box. So it is easy to think they are the same. But you saw where they split: at the first render after Send. In step 3 above, only `value` writes the empty string back into the box. `defaultValue` already did its one job when the page opened.

There is one more thing to notice. The message box in Principle 1 had `onChange`, and it was still uncontrolled. `onChange` only reports. Only `value` decides whether a box is controlled.

One last note for readers who know HTML. In HTML, you write the starting text of a text area between its tags. React does not support that. The box still shows the text, but React prints a red error in the Console. The error tells you to use `defaultValue` or `value` instead. So in React, a text area gets its text from one of these two props, just like an input.

> [!PRINCIPLE]
> **Principle 2: `value`: React Writes State into the Box After Every Render**
>
> *When our code must change what the box shows, such as emptying it after Send, give the box `value` from state.*
>
> A box without `value` keeps its own text. `defaultValue` only sets the starting text, so after Send the count says zero while the old message stays in the box. With `value` from state, React writes the state into the box after every render. Then saving an empty string empties the box too, and state becomes the single source of truth.
>
> **DO THIS:**
> ```jsx
> <textarea ~value={message}~ onChange={e => setMessage(e.target.value)} /> {/* Setting message to an empty string now empties the box */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <textarea ~defaultValue=""~ onChange={e => setMessage(e.target.value)} /> {/* **WRONG:** starting text only, so the box keeps its text after Send */}
> ```

## 3. Principle 3: `value` Without `onChange` Freezes the Box

### The smallest version: a box stuck on John

What if a box has `value`, but no `onChange`? When the page opens, the box shows John, and the Console already shows a red error:

```page width=text caption="A Name box with value and no onChange, when the page opens."
form:
  field: Name | John
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

The box has `value`, and nothing else:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [name, setName] = useState('John');

  return (
    <label>
      Name
      <input ~value={name}~ /> {/* **WRONG:** value without onChange */}
    </label>
  );
}
```

The user clicks at the end of the box and types ny. The box still shows John:

```page width=text caption="The same page after the user types ny into the Name box."
form:
  field: Name | John | bad
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

No line of our code removes the letters. So who removes them? React does. Here is what happens on every key, in order:
1. The user presses n.
2. The browser puts n into the box.
3. The box has no `onChange`, so no code of ours runs, and `name` stays John.
4. React writes the `value` it was given, John, back into the box.
5. The box shows John again.

Remember the whiteboard. A student calls out a letter, but the teacher is not listening. So the board never changes.

### What the red error tells you

React prints this error while you develop, whenever a box has `value` and no `onChange`. It even offers three ways out:
- If the box should be editable, add `onChange`.
- If you only wanted a starting text, use `defaultValue` instead.
- If the box should really be frozen, say so with the `readOnly` prop. Then React knows you meant it, and the error goes away.

### Mistake: the Name box that refuses Anna

Back to our contact form. The developer adds a Name box above the message, with its own state:

```jsx title="src/components/ContactForm.jsx" startLine="4"
  const [name, setName] = useState('');
  const [message, setMessage] = useState('');
```

They remember from Principle 2 that `value` lets Send empty the box. But in the markup, they forget `onChange`:

```jsx title="src/components/ContactForm.jsx" startLine="20" bad="4"
      <form onSubmit={handleSend}>
        <label>
          Name
          <input ~value={name}~ /> {/* **WRONG:** no onChange, so every letter is put back */}
        </label>
```

The user clicks into the Name box and types Anna. The box stays empty. The Console has shown the error since the page opened:

```page width=text caption="The contact form after the user types Anna into a Name box that has no onChange."
heading: Contact Us
form:
  field: Name | | bad
  textarea: Message |
line: 0 / 200
form:
  submit: Send
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

The steps are the same as for John. The browser shows each letter, no code saves it, and React writes the empty `name` back into the box. The fix is an `onChange` like the one the Message box already has:

```jsx title="src/components/ContactForm.jsx" startLine="21" good="3"
        <label>
          Name
          <input value={name} ~onChange={e => setName(e.target.value)}~ /> {/* Each letter now reaches state */}
        </label>
```

The Send handler now logs the name too, and empties it together with the message:

```jsx title="src/components/ContactForm.jsx" startLine="11"
  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, message);
    ~setName('')~; // The Name box empties together with the message
    setMessage('');
  }
```

After a reload, Anna appears letter by letter, and the Console is clean:

```page width=text caption="The contact form after the fix, when the user types Anna into the Name box."
heading: Contact Us
form:
  field: Name | Anna | good
  textarea: Message |
line: 0 / 200
form:
  submit: Send
console: quiet
```

The broken box and the fixed box look like the same box with one extra prop. They even show the same empty text when the page opens. But they are NOT the same. They split at step 3: only the fixed box saves the letter in state, so only its letters survive.

### Refusing a letter on purpose: the 200 limit

React puts back whatever state says. So can our code refuse a letter on purpose? Yes. Our count already promises a limit of 200 characters, so let's make the box keep that promise. We add one check to the message handler:

```jsx title="src/components/ContactForm.jsx" startLine="7"
  function handleMessageChange(e) {
    ~if (e.target.value.length <= 200)~ { // Saves the text only while it fits
      setMessage(e.target.value);
    }
  }
```

Suppose the box already holds 200 characters, and the user types one more. Here is what happens:
1. The browser puts the extra letter into the box.
2. React calls `handleMessageChange`. The new text is 201 characters long, so the handler does not call `setMessage`.
3. `message` still holds the 200 characters.
4. React writes those 200 characters back into the box, and the extra letter disappears.

This is the freeze from the start of this principle, used on purpose. The box accepts a letter only when our code saves it.

### The handler must save `e.target.value` right away

The handler has two more rules. It must save the text right away, and it must save exactly `e.target.value`. Here is a Name handler that breaks the first rule. It saves the text later, inside a timer:

```jsx title="A Name box whose handler saves the text later"
function handleNameChange(e) {
  ~setTimeout~(() => setName(e.target.value), 100); // **WRONG:** the state waits, but React puts the old text back right away
}

<input value={name} onChange={handleNameChange} />
```

The user types, and the box still refuses every letter. The handler does run, so why? Here is the order:
1. The user presses a key, and the browser shows the letter in the box.
2. React calls `handleNameChange`, but the handler only starts a timer.
3. The handler ends, and `name` still holds the old text.
4. State did not change, so React writes the old text back into the box.
5. A moment later, the timer runs and reads `e.target.value`. That is the same box, and it now holds the old text again.
6. So `setName` saves the old text, and nothing changes.

This box refuses letters just like a box with no `onChange`. This time, though, the Console stays quiet, because the box does have a handler. React's documentation says the state update cannot wait. It must happen inside the handler, right away.

The second rule is broken by a handler that saves a changed copy of the text. One example is a handler that turns every letter into a capital with `toUpperCase`. The browser has just shown one text, and React then writes a different text into the box. React's documentation lists this as a cause of a caret that jumps while the user types.

So keep the handler simple: save exactly `e.target.value`, right away. If you need to refuse a letter, refuse the whole change with an `if`, as the 200 limit does.

> [!PRINCIPLE]
> **Principle 3: Read-Only: `value` Without `onChange` Freezes the Box**
>
> *Every box with `value` also needs an `onChange` handler that saves the new text, exactly as typed, right away.*
>
> With `value`, React writes the state into the box after every key. If no handler saves the new letter, state never changes, so React puts the old text back, and the Console shows the read-only field error. The same freeze happens when the handler waits inside a timer. A box that should be frozen on purpose says so with `readOnly`.
>
> **DO THIS:**
> ```jsx
> <input value={name} ~onChange={e => setName(e.target.value)}~ /> {/* Each letter reaches state, so it stays */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input ~value={name}~ /> {/* **WRONG:** no onChange, so React puts the old text back after every key */}
> ```

## 4. Principle 4: The Same Pair on a Menu and a Tick Box

### The smallest version: a fruit menu and an agree box

A drop-down menu is a `<select>`, and a tick box is an `<input type="checkbox" />`. Both can be controlled with the same idea. When the page opens, the menu shows Orange and the box is not ticked:

```page width=text caption="A fruit menu and an agree box, when the page opens."
form:
  select: Fruit | Orange
  check: I agree | off
```

Here is the code. The menu uses `value`, like a text box. The tick box uses `checked` instead:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [fruit, setFruit] = useState('orange');
  const [agree, setAgree] = useState(false);

  return (
    <form>
      <label>
        Fruit
        <select ~value={fruit}~ onChange={e => setFruit(e.target.value)}> {/* The chosen option comes from state */}
          <option value="apple">Apple</option>
          <option value="banana">Banana</option>
          <option value="orange">Orange</option>
        </select>
      </label>
      <label>
        <input type="checkbox" ~checked={agree}~ onChange={e => setAgree(e.target.checked)} /> {/* The tick comes from state */}
        I agree
      </label>
    </form>
  );
}
```

The user picks Banana and ticks the box:

```page width=text caption="The same page after the user picks Banana and ticks I agree."
form:
  select: Fruit | Banana | good
  check: I agree | on | good
```

It is the same whiteboard as before. Now the board holds a chosen word and a ticked square, and only state writes them.

### What `value` means on a menu

On a `<select>`, `value` says which option is chosen. It must match the `value` of one of the options inside. Each `<option>` has two texts:
- The text between its tags, such as Banana, is what the user reads.
- Its `value`, such as banana with a small b, is the string the menu reports to our code.

The user reads Banana, but our code receives banana with a small b. Where did that string come from? The browser supplies it:
1. The user picks Banana.
2. The menu's value becomes the `value` of that option, which is banana.
3. React calls `onChange`, and `e.target.value` is banana.
4. `setFruit` saves banana, and React writes it back into the menu, so Banana stays chosen.

### Never mark an option as `selected`

In plain HTML, you choose the starting option by writing `selected` on that option. A developer who knows HTML might write this:

```jsx title="The plain HTML habit on a menu"
<select>
  <option value="delivery">Delivery</option>
  <option value="payment" ~selected~>Payment</option> {/* **WRONG:** the plain HTML habit, not supported in React */}
</select>
```

React does not support `selected` on an option. The menu still opens on Payment, but React prints a red error in the Console. The error tells you to use `value` or `defaultValue` on the select instead.

The React way puts the choice on the select itself:

```jsx title="The React way on a menu"
<select ~value="payment"~ onChange={e => setTopic(e.target.value)}> {/* React chooses the option whose value matches */}
  <option value="delivery">Delivery</option>
  <option value="payment">Payment</option>
</select>
```

React reads `value` on the select and chooses the option whose `value` matches. When the menu only needs a starting choice and no state, use `defaultValue` on the select instead. It works the same way as `defaultValue` on a text box.

### What `checked` means on a tick box

A tick box has no text to show. It is either ticked or not. So it does not use `value`. It uses **`checked`**, a React prop that holds true or false. After every render, React makes the box ticked or unticked to match.

In Lesson 18, a tick box without `checked` kept its own tick inside the browser. That box was uncontrolled. With `checked` from state, React decides the tick, and the box becomes controlled.

The handler reads **`e.target.checked`**, which the browser supplies. It is the tick right after the click: true if the box is now ticked, and false if not.

For a tick box that only needs a starting tick, React has `defaultChecked`, which works like `defaultValue`. A tick box with `checked` and no `onChange` freezes too, just like the frozen text box of Principle 3. React prints the same read-only error, but this time it names `checked` and `defaultChecked`.

### Mistake: reading `e.target.value` on the tick box

Next, we add the tick box Email me a reply. Its state starts as false:

```jsx title="src/components/ContactForm.jsx" startLine="7"
  const [wantsReply, setWantsReply] = useState(false);
```

The developer copies the handler from the text boxes:

```jsx title="src/components/ContactForm.jsx" bad="2"
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.value~)} /> {/* **WRONG:** reads a fixed string, not the tick */}
          Email me a reply
        </label>
```

The user ticks the box, and it looks ticked. Then the user clicks again to untick it, and it stays ticked:

```page width=text caption="The contact form after the user ticks Email me a reply and then clicks it again to untick it."

line: 0 / 200
```

The tick box has a value too. So why is reading it wrong? Here is what happens:
1. The user ticks the box, and React calls `onChange`.
2. On a tick box, `e.target.value` is a fixed string that never changes with the tick. When the tick box has no `value` of its own, the browser makes this string on.
3. `setWantsReply` saves the string on. React treats any text that is not empty as ticked, so the box is ticked.
4. The user clicks again to untick. The browser removes the tick for a moment, and React calls `onChange` again.
5. `e.target.value` is still on, so state is still on.
6. State did not change, so React puts the tick back, and the box stays ticked.

The fix is to read the tick itself:

```jsx title="src/components/ContactForm.jsx" good="2"
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* true or false, right after the click */}
          Email me a reply
        </label>
```

After a reload, the box ticks and unticks with each click.

### Send puts the menu and the tick box back

The Send handler now puts every part of the form back to its start:

```jsx title="src/components/ContactForm.jsx" startLine="15"
  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, topic, message, wantsReply);
    setName('');
    ~setTopic('delivery')~; // Back to the first option
    setMessage('');
    ~setWantsReply(false)~; // Back to unticked
  }
```

No line of our code touches the menu or the tick box. So why does Send put Topic back to Delivery and untick the box? The steps are the same as for the text box:
1. The Send handler saves delivery in `topic` and false in `wantsReply`.
2. React renders `ContactForm` again.
3. React writes delivery into the menu, and false into the tick box.

> [!PRINCIPLE]
> **Principle 4: Menus and Tick Boxes: The Same Pair with Their Own Props**
>
> *Control a menu with `value` on the select itself, never `selected` on an option. Control a tick box with `checked`, and read `e.target.checked` in its handler.*
>
> A menu reports the `value` of the picked option, so `value` on the select must match one option. Writing `selected` on an option is the plain HTML habit, and React does not support it. A tick box holds true or false, so it takes `checked` from state. Its `e.target.value` is a fixed string such as on, which never changes with the tick.
>
> **DO THIS:**
> ```jsx
> <select ~value={topic}~ onChange={e => setTopic(e.target.value)}> {/* The choice lives on the select */}
> <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* true or false, right after the click */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <option value="payment" ~selected~>Payment</option> {/* **WRONG:** not supported in React */}
> <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.value~)} /> {/* **WRONG:** always 'on', so the box never unticks */}
> ```

## 5. Principle 5: A Controlled Box Starts with an Empty String

### The smallest version: a City box that starts with nothing

Here is a City box whose state starts with nothing at all. When the page opens, it looks like any empty box, and the Console is clean:

```page width=text caption="A City box whose state starts with nothing, when the page opens."
form:
  field: City |
console: quiet
```

The only difference is the empty call to `useState`:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [city, setCity] = ~useState()~; // **WRONG:** no starting value at all

  return (
    <label>
      City
      <input value={city} onChange={e => setCity(e.target.value)} />
    </label>
  );
}
```

The user types a. The letter appears, but a red message appears in the Console too:

```page width=text caption="The same page after the user types a into the City box."
form:
  field: City | a
console: A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen. Decide between using a controlled or uncontrolled input element for the lifetime of the component. More info: https://react.dev/link/controlled-components
```

### Where did `undefined` come from?

Our code never writes `undefined`. JavaScript supplies it. Here, `useState` receives no starting value, and in JavaScript a missing argument is `undefined`. So React saves `undefined` as the first state of `city`.

### Why React warns when the box works

The box works, so what is React complaining about? Here is what happens, in order:
1. The page opens. `city` is `undefined`, so the box gets no real value at all.
2. React treats the box as uncontrolled, the same as a box with no `value` prop.
3. The user types a. `onChange` runs, and `setCity` saves the string a.
4. React renders again. Now the box has a real `value`, the string a.
5. The same box has switched from uncontrolled to controlled. React cannot tell which one we meant, so it warns.

React's documentation explains it the same way. You cannot give a box an undefined `value` first and a string later. In its words, "React won't know whether you want the component to be uncontrolled or controlled." A box must stay one kind for its whole life.

Think of a notebook that is suddenly declared a whiteboard in the middle of the lesson. The student was writing freely, and now the teacher wants to write on the same page. Nobody knows who owns the page any more.

### Starting with nothing and starting with an empty string are NOT the same

Both versions draw the same empty box when the page opens. But they split at step 1. When the state starts as an empty string, `value` is a real string from the very first render. So the box is controlled from the start, and it never switches.

The opposite pair really is the same. An undefined `value` and no `value` prop at all are the exact same thing for React. Both give an uncontrolled box.

### Mistake: the Email box that appears with nothing in it

Back to our contact form. When the user ticks Email me a reply, an Email box should appear. The `&&` from Lesson 10 shows the box only when `wantsReply` is true:

```jsx title="src/components/ContactForm.jsx"
        {wantsReply && (
          <label>
            Email
            <input value={email} onChange={e => setEmail(e.target.value)} />
          </label>
        )}
```

The email is not needed until the box is ticked, so the developer gives its state no starting value:

```jsx title="src/components/ContactForm.jsx" startLine="8" bad="1"
  const [email, setEmail] = ~useState()~; // **WRONG:** undefined until the first key
```

The user ticks Email me a reply, and an empty Email box appears. The user types a, and the warning appears:

```page width=text caption="The contact form after the user ticks Email me a reply and types a into the Email box."
heading: Contact Us
form:
  field: Name | Anna
  select: Topic | Payment
  textarea: Message |
line: 0 / 200
form:
  check: Email me a reply | on
  field: Email | a | bad
  submit: Send
console: A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen. Decide between using a controlled or uncontrolled input element for the lifetime of the component. More info: https://react.dev/link/controlled-components
```

The steps are the same as for the City box. The fix is one empty string:

### Send clears the whole form

Now the Send handler empties the email too. Every state goes back to its start, and no line of our code touches a box:

```jsx title="src/components/ContactForm.jsx" startLine="16"

    e.preventDefault();
```

> [!PRINCIPLE]
> **Principle 5: Starting Value: A Controlled Box Starts with an Empty String**
>
> *The state behind `value` must hold a string from the first render, so the state of an empty box starts as an empty string, never as nothing.*
>
> A `useState` call with no starting value gives `undefined`. An undefined `value` is the same as no `value` at all. So the box starts uncontrolled. On the first key, state becomes a string, the box becomes controlled, and React warns, because a box cannot switch over its life. An empty string makes the box controlled from the first render. Clear it with an empty string too.
>
> **DO THIS:**
> ```jsx
> const [email, setEmail] = ~useState('')~; // Controlled from the first render
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [email, setEmail] = ~useState()~; // **WRONG:** undefined first, a string later, so React warns
> ```

## Putting All Five Principles Together

### The complete `ContactForm.jsx` file

Here is the finished form. Every box takes what it shows from state, and every box reports its changes back to state:

```jsx title="src/components/ContactForm.jsx"
import { useState } from 'react';

export default function ContactForm() {
  const [name, setName] = useState('');
  const [topic, setTopic] = useState('delivery');
  const [message, setMessage] = useState('');
  const [wantsReply, setWantsReply] = useState(false);
  const [email, setEmail] = ~useState('')~; // 5. Starts with a string, never undefined

  function handleMessageChange(e) {
    if (e.target.value.length <= 200) {
      setMessage(e.target.value);
    }
  }

  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, topic, message, wantsReply, email);
    setName('');
    setTopic('delivery');
    setMessage('');
    setWantsReply(false);
    setEmail('');
  }

  return (
    <section>
      <h1>Contact Us</h1>
      <form onSubmit={handleSend}>
        <label>
          Name
          <input value={name} ~onChange={e => setName(e.target.value)}~ /> {/* 3. value always comes with onChange */}
        </label>
        <label>
          Topic
          <select ~value={topic}~ onChange={e => setTopic(e.target.value)}> {/* 4. The choice lives on the select */}
            <option value="delivery">Delivery</option>
            <option value="payment">Payment</option>
            <option value="other">Other</option>
          </select>
        </label>
        <label>
          Message
          <textarea ~value={message}~ onChange={handleMessageChange} /> {/* 2. State goes into the box */}
        </label>
        <p>{message.length} / 200</p>
        <label>
          <input type="checkbox" checked={wantsReply} onChange={e => setWantsReply(~e.target.checked~)} /> {/* 4. The tick, not the text */}
          Email me a reply
        </label>
        {wantsReply && (
          <label>
            Email
            <input value={email} ~onChange~={e => setEmail(e.target.value)} /> {/* 1. Every key goes into state */}
          </label>
        )}
        <button type="submit">Send</button>
      </form>
    </section>
  );
}
```

### How React calls the components, and what one key does

When the page loads, React starts at `App` and follows the tags. `App` has only one tag, so React calls `ContactForm` next:

```tree caption="The component tree of the contact page and the order in which React calls each component."
`main.jsx` mounts `App` inside `<StrictMode>`
- +`App` [1. Called first] | **Root component** | Returns `<ContactForm />`
  - +`ContactForm` [2. Called second] | Holds **five states**, one for each part of the form | Called again after **every key**, every pick, every tick, and every Send
```

Every controlled box goes around the same loop on every key:

```tree dir=right caption="The loop that one key runs in a controlled box, from the browser to state and back into the box."
One key in a controlled box
- +1. The browser | Shows the new letter in the box for a moment
- +2. `onChange` | React calls our handler with the event object
- +3. The setter [`setMessage`] | Saves the new text in **state**
- +4. React renders again | Writes the state into the box through **`value`** | The letter stays
```

### Summary

| Aspect | The Plain JavaScript Habit | The React Rule |
| :--- | :--- | :--- |
| **Reporting each key** | Listen to the `change` event, which waits until the user leaves the box, or save the text in a plain variable | Use `onChange`, which fires on every key, and save `e.target.value` with the setter |
| **Emptying a box** | Reach into the box and clear its text by hand | Give the box `value` from state, then set the state to an empty string |
| **A box with a value** | Write the value and expect the user can still type | Always pair `value` with `onChange`, or use `defaultValue` or `readOnly` |
| **Menus and tick boxes** | Write `selected` on an option, and read `value` from a tick box | Put `value` on the select, and use `checked` with `e.target.checked` |
| **The starting value** | Leave a variable empty until it is needed | Start every controlled box with an empty string, never `undefined` |

## For the Interview

> **The Interview Question:** How do you make an input, textarea, or select fully controlled by React state?

### How to Answer Clearly in 30 Seconds

"A controlled field takes what it shows from state and reports every change back to state. I give it two props: `value` from state, and `onChange`, which saves `e.target.value` with the setter. React's `onChange` fires on every key, like the browser's `input` event, not like the `change` event. After every render, React writes the state into the field, so state is the single source of truth. To empty the box after Send, I only set the state to an empty string. Four rules keep this working:
1. **`value` always comes with `onChange`.** Without it, React puts the old text back after every key and logs a read-only field error. The handler saves exactly `e.target.value`, right away.
2. **`defaultValue` is not controlled.** It only sets the starting text, and the box keeps its own text after that.
3. **Menus and tick boxes use the same pair.** A `<select>` takes `value` on the select itself, never `selected` on an option. A checkbox takes `checked` and reads `e.target.checked`.
4. **Start with an empty string.** A controlled field must get a string from the first render. If it starts as `undefined`, React warns that an uncontrolled input is changing to controlled."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What is the difference between a controlled and an uncontrolled input, and when would you use each?"**
   A controlled input gets `value` from state, or `checked` for a checkbox, and reports with `onChange`. React forces it to show what state holds. An uncontrolled input has no `value`. It may get a starting text from `defaultValue` or `defaultChecked`, and after that it keeps its own text inside the browser. A controlled field is worth it in two cases. The page needs the text on every key, such as for a live count. Or our code must change the field, such as emptying it after Send. A field can never be both, and it cannot switch over its life. Choosing between controlled fields and reading an uncontrolled form with `FormData` at submit time is the topic of Lesson 40.

2. **"Why does my input's caret jump, or why does typing feel slow?"**
   A caret jumps when the handler does not save exactly `e.target.value` right away. Two common causes are saving a changed copy, such as with `toUpperCase`, and saving later, inside `setTimeout`. Another cause is a field that React removes and adds again on every key. That happens when a component is defined inside another component, as in Lesson 04, or when its `key` changes, which Lesson 25 covers. Slow typing has a different cause. Every key sets state, and every state change renders the component that holds it. If that component draws a large page, every key makes React render all of it again. The fix is to move the field and its state into a small component of its own, so each key renders only that small part. `useDeferredValue`, from Lesson 68, is another tool for this.

3. **"How do you control a select, a checkbox, and a field whose value comes from an API?"**
   A `<select>` gets `value` on the select, and it must match the `value` of one `<option>`. Writing `selected` on an option is not supported in React. A select with `multiple` takes a list of values instead of one string. A checkbox gets `checked`, which must always be true or false, and its handler reads `e.target.checked`, because `e.target.value` on a checkbox is a fixed string such as on. A value from an API is often `null` or `undefined` until it arrives. So start the state with an empty string, or write `value={someValue ?? ''}`. The `??` uses the empty string whenever the left side is `null` or `undefined`, so the field always gets a string.
