# Lecture 37: Removing Effect Dependencies by Changing the Code
> INTERVIEW QUESTION | ❱ CORE | How do you remove unnecessary effect dependencies, and when must a dependency stay?

---

## How to Remove an Effect Dependency Without Lying to React

### A chat that reconnects when nothing changed

Open a chat app with rooms, such as Slack. A menu at the top picks the room. Under it, a heading says which room you are in. Below the heading, the messages that arrive in the room appear one under the other. At the bottom sits a box where you type your own message.

The user does three things on this screen, and expects three results:
1. **The user types `hi` in the message box.** The letters appear in the box. Nothing else changes, and the user is still in the general room.
2. **The user picks `travel` in the menu.** The app leaves the general room and connects to the travel room.
3. **The user waits.** Messages such as `hey` and `lol` arrive, and each one appears under the ones before it.

Only the second action should touch the connection to the chat server.

Now look at the same screen as the developer. The connection lives in an Effect, and the Effect's dependency array must list every reactive value the Effect reads (as seen in Lesson 35). The linter checks that list. Sometimes the linter asks for a value whose change should not touch the connection at all. The developer adds it, and from then on the chat disconnects and connects again after every letter the user types, or after every message that arrives. React's docs call such a value an **unnecessary dependency**: a dependency whose change should not run the Effect again.

The fix is never to edit the list by hand. You change the code. React's docs say it plainly: "**If you want to change the dependencies, change the surrounding code first.**"

There are two ways to get a value out of the dependency array, and only one of them tells the truth:
- **Delete the value from the array and silence the linter.** The linter goes quiet, but the Effect still reads the value. From now on, it reads an old copy of it.
- **Change the code so the Effect no longer reads a reactive value there.** Then the linter itself stops asking for it. React's docs call this proving it to the linter: "**To remove a dependency, "prove" to the linter that it *doesn't need* to be a dependency.**"

The key idea to remember: you never pick the dependencies. You change the code until the list the linter asks for is the list you want.

```tree caption="Two ways to get a value out of the dependency array: silence the linter, or change the code so the Effect no longer reads it."
Two ways to get a value out of the dependency array
- !Delete it and silence the linter | The Effect **still reads the value** | It keeps an **old copy**, and the linter can **no longer warn you**
- +Change the code first | The Effect **no longer reads a reactive value** there | The linter **stops asking for it** by itself
```

### Two objects with the same contents are NOT the same value

One comparison explains why an object makes a bad dependency. After every render, React compares each dependency with its value from the last render, using `Object.is` (as seen in Lesson 32). Here are two objects with the same contents, and two strings with the same text, both from React's docs:

```js title="Two objects with the same contents, and two strings with the same text"
const options1 = { serverUrl: 'https://localhost:1234', roomId: 'music' };
const options2 = { serverUrl: 'https://localhost:1234', roomId: 'music' };
console.log(~Object.is(options1, options2)~); // false: two different objects

const roomId1 = 'music';
const roomId2 = 'music';
console.log(~Object.is(roomId1, roomId2)~); // true: the same string
```

The two objects look the same, but they are NOT the same thing! They hold the same server and the same room, yet `Object.is` says they are different. The two strings are the same. The difference is in what JavaScript compares:
- **Strings and numbers are compared by their content.** React's docs: "In JavaScript, numbers and strings are compared by their content." Two `'music'` strings are one and the same value.
- **Objects and functions are compared by which object they are.** Each new object is a different value, even when its contents match. React's docs: "**In JavaScript, each newly created object and function is considered distinct from all the others. It doesn't matter that the contents inside of them may be the same!**"

```tree caption="How Object.is compares two strings with the same text and two objects with the same contents."
What `Object.is` compares
- +Two strings with the same text [`'music'` `'music'`] | Compared **by their content** | `Object.is` returns **`true`**: the same value
- !Two objects with the same contents [`options1` `options2`] | Compared by **which object they are** | `Object.is` returns **`false`**: two different values
```

### What is at stake

What is at stake is what the user sees: a chat that drops its connection and opens a new one for no reason, or a chat that quietly loses messages. On the chat page of this lesson, three versions of the code show it:
1. **An `options` object made in the component body and listed in the array.** Every letter the user types disconnects the chat and connects it again. React's docs: "the chat re-connects as you type."
2. **The `messages` list read inside the Effect and listed in the array.** Every message that arrives disconnects the chat and connects it again. React's docs: "every new message will make the chat re-connect. The user would not like that!"
3. **The dependency deleted and the linter silenced.** The chat stays connected, but the list on the screen shows only the newest message.

Readers usually go wrong in three places:
1. They delete the dependency and add a comment that silences the linter. React's docs: "By suppressing the linter, you "lie" to React about the values your Effect depends on."
2. They think an object with the same contents is the same dependency.
3. They remove a dependency that must stay, such as `roomId`, because the Effect runs "too often". Then the chat stays in the old room after the user picks a new one.

Many real connection libraries take their settings the same way, as one object:

```js title="src/chat.js"
export function createConnection(~{ serverUrl, roomId }~) { // One object now, instead of two separate arguments
  let intervalId;
  let messageCallback;
  return {
    connect() {
      console.log('✅ Connecting to "' + roomId + '" room at ' + serverUrl + '...');
      clearInterval(intervalId);
      intervalId = setInterval(() => {
        if (messageCallback) {
          if (Math.random() > 0.5) {
            messageCallback('hey');
          } else {
            messageCallback('lol');
          }
        }
      }, 3000);
    },
    disconnect() {
      clearInterval(intervalId);
      messageCallback = null;
      console.log('❌ Disconnected from "' + roomId + '" room at ' + serverUrl);
    },
    on(event, callback) {
      if (messageCallback) {
        throw Error('Cannot add the handler twice.');
      }
      if (event !== 'message') {
        throw Error('Only "message" event is supported.');
      }
      messageCallback = callback;
    },
  };
}
```

Each message is picked at random, so a real run shows `hey` and `lol` in any order. The previews below show one such run.

### Four Principles of Removing Effect Dependencies

**PRINCIPLES:** The dependency array describes the code of the Effect. To change the array, we change the code. Our chat room gives us four practical rules:
1. **Principle 1: Typing in the Message Box Reconnects the Chat**: An object made in the component body is a new object on every render. When the Effect lists it, every letter the user types disconnects the chat and connects it again.
2. **Principle 2: Building `options` Inside the Effect Leaves Only `roomId`**: Move an object that depends on props or state inside the Effect, and one that depends on neither above the component. Then it is not reactive, it leaves the array, and only the string `roomId` stays.
3. **Principle 3: An Updater Function Keeps New Messages from Reconnecting the Chat**: When the Effect adds a message to `messages`, an updater function lets it do so without reading `messages`. Then `messages` leaves the array, and no comment has to silence the linter.
4. **Principle 4: `roomId` Stays Because Picking a Room Must Reconnect**: A dependency stays when its change, seen from the user's side, means the Effect must connect again. A dependency goes only when the code no longer reads a reactive value there.

Here is the complete map of those four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Typing in the Message Box Reconnects the Chat** | The chat drops its connection after every letter the user types, though the room never changed, and interviewers ask why an object with the same contents is a new dependency. | An object or a function made in the component body is a new value on every render, so an Effect that lists it re-synchronizes after every render. |
| **Principle 2** | **Building `options` Inside the Effect Leaves Only `roomId`** | Moving one line ends the reconnects, and the linter itself asks for the shorter array. | Move a static object above the component and a dynamic one inside the Effect, or read its primitive values, so only strings and numbers stay in the array. |
| **Principle 3** | **An Updater Function Keeps New Messages from Reconnecting the Chat** | Listing `messages` reconnects the chat on every message, and silencing the linter leaves a list that never grows past one message. | When the Effect sets state from the same state, pass an updater function, so the Effect does not read that state. |
| **Principle 4** | **`roomId` Stays Because Picking a Room Must Reconnect** | Removing a dependency that must stay leaves the chat in the old room after the user picks a new one. | Keep every value whose change must re-synchronize the Effect; to remove any other, change the code until the linter stops asking for it. |

## 1. Principle 1: Typing in the Message Box Reconnects the Chat

### An object made in the component body is new on every render

Start from the shape React's docs use for this chat. The settings of the connection sit together in one object, `options`, and the Effect passes that object to `createConnection`:

```jsx title="An options object made in the component body"
const ~options~ = { serverUrl: serverUrl, roomId: roomId }; // Made again on every render of ChatRoom

useEffect(() => {
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, ~[options]~); // Lists options, because the Effect reads it
```

The array matches the code: the Effect reads `options`, and `options` is listed. Yet this Effect runs again after every render. Why? Well, `ChatRoom` runs from the top on every render, so the `options` line builds a brand-new object every time. React's docs: "A new `options` object is created from scratch on every re-render of the `ChatRoom` component."

The `options` of the last render and the `options` of this render hold the same server and the same room. They look the same, but they are NOT the same thing! They are two objects, so `Object.is` returns `false`, exactly as it did for `options1` and `options2`. React's docs: "React sees that the `options` object is a *different object* from the `options` object created during the last render."

React's docs have a name for this case. An object listed in the dependency array is an **object dependency**, and a function listed there is a **function dependency**. The docs warn about both in bold: "**Object and function dependencies can make your Effect re-synchronize more often than you need.**"

The linter sees this too. With `[options]`, it no longer reports a missing dependency. Instead, it warns that this object changes the dependencies of the Effect on every render, and it tells you to move the object inside the Effect. Principle 2 does exactly that.

### The chat page with `options` in the component body

Here is `ChatRoom.jsx` with `options` in the component body. It also holds the message box, controlled by `message` state (as seen in Lesson 20):

```jsx title="src/components/ChatRoom.jsx"
import { useState, useEffect } from 'react';
import { createConnection } from '../chat.js';

const serverUrl = 'https://localhost:1234';

export default function ChatRoom({ roomId }) {
  const [message, setMessage] = useState('');

  const ~options~ = { serverUrl: serverUrl, roomId: roomId }; // A new object on every render

  useEffect(() => {
    const connection = createConnection(options);
    connection.connect();
    return () => connection.disconnect();
  }, ~[options]~); // **WRONG:** a new options after every render reconnects the chat

  return (
    <section>
      <h1>Welcome to the {roomId} room!</h1>
      <input
        value={message}
        onChange={e => ~setMessage(e.target.value)~} // Every letter the user types re-renders ChatRoom
      />
    </section>
  );
}
```

**Beware! With `options` in the component body, every letter the user types disconnects the chat and connects it again, even though the room never changed.** The page itself looks fine: the letter appears in the box, and the heading stays on the general room. The damage shows only in the Console. Here is what happens when the user types `h`, in order:
1. The user types `h` in the message box.
2. `setMessage` stores `h` and asks React to render `ChatRoom` again.
3. `ChatRoom` runs again from the top, and the `options` line creates a new object with the same server and the same room.
4. React compares the new `options` with the last one using `Object.is`. The answer is `false`: the dependency changed.
5. React runs the cleanup of the last Effect, and the Console shows the disconnect line for the general room.
6. React runs the new setup, and the Console shows the connect line for the general room.

The user typed `hi`, two letters, so the Console shows two extra pairs of lines after the three lines of the page opening:

```page width=text caption="After the user types hi with options in the component body: the page looks right, and the Console shows one disconnect and one connect for each letter."
form:
  select: Choose the chat room: | general
heading: Welcome to the general room!
form:
  field:  | hi
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
```

React's docs describe this exact page from the user's side: "From the user's perspective, this should not affect the chat connection." Yet the chat reconnects on every letter.

```tree dir=right caption="Why one letter typed in the message box reconnects the chat when options is made in the component body."
What one letter in the message box does
- +1. The user types a letter [`setMessage`] | `ChatRoom` **renders again** from the top
- +2. A new `options` object [`options`] | Same server, same room, but a **different object**
- !3. React compares with `Object.is` | The answer is **`false`** | React runs the **cleanup and the setup**: the chat **reconnects**
```

### The same thing happens with a function

A function made in the component body behaves the same way. Suppose the developer builds `options` inside a helper function instead:

```jsx title="A createOptions function made in the component body"
function ~createOptions~() { // A new function on every render of ChatRoom
  return { serverUrl: serverUrl, roomId: roomId };
}

useEffect(() => {
  const options = createOptions();
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, ~[createOptions]~); // **WRONG:** a new function after every render reconnects the chat
```

React's docs say this function is also "created from scratch on every re-render", and as a dependency "it will cause your Effect to re-run after every commit." Making a new function on every render is not the problem in itself. The docs: "By itself, creating a function from scratch on every re-render is not a problem. You don't need to optimize that." The problem starts only when the function is listed in the array.

> [!PRINCIPLE]
> **Principle 1: Object Dependencies: A New Object on Every Render Reconnects the Chat**
>
> *An object or a function made in the component body is a new value on every render, so an Effect that lists it re-synchronizes after every render, even when the contents are the same.*
>
> React compares each dependency with `Object.is`. Strings and numbers are compared by their content, but each new object and each new function is a different value. When `options` is made in the component body, every letter the user types re-renders `ChatRoom`, builds a new `options`, and makes React disconnect the chat and connect it again. An object made once, outside the component, is the same object on every render.
>
> **DO THIS:**
> ```jsx
> const options = { serverUrl: 'https://localhost:1234', roomId: 'music' };
>
> function ChatRoom() {
>   useEffect(() => {
>     const connection = createConnection(options);
>     connection.connect();
>     return () => connection.disconnect();
>   }, ~[]~); // options is made once, outside the component: typing never reconnects
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ChatRoom({ roomId }) {
>   const options = { serverUrl: serverUrl, roomId: roomId };
>   useEffect(() => {
>     const connection = createConnection(options);
>     connection.connect();
>     return () => connection.disconnect();
>   }, ~[options]~); // **WRONG:** a new options on every render reconnects the chat after every letter
> }
> ```

## 2. Principle 2: Building `options` Inside the Effect Leaves Only `roomId`

### Two places for the same `options` object

Principle 1 found the cause: `options` is made in the component body. So we move the line that makes it. Compare the two places where the same `options` line can sit:

```jsx title="With options in the component body"
const options = { serverUrl: serverUrl, roomId: roomId };

useEffect(() => {
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, ~[options]~); // A new object after every render: the chat reconnects on every letter
```

```jsx title="With options inside the Effect"
useEffect(() => {
  const ~options~ = { serverUrl: serverUrl, roomId: roomId }; // Made inside the Effect: no longer a reactive value
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId]~); // Only a string: the chat reconnects only when the room changes
```

It may look the same, or work the same at first, but it is NOT the same thing! Both versions connect to the general room when the page opens. Both reconnect when the user picks `travel`. Only the version with `options` in the component body reconnects when the user types a letter.

The reason is simple: a value made inside the Effect is not reactive, so it is not a dependency (as seen in Lesson 35). React's docs: "Now that `options` is declared inside of your Effect, it is no longer a dependency of your Effect. Instead, the only reactive value used by your Effect is `roomId`."

The linter itself asks for `roomId` in the new array, because the Effect now reads `roomId` directly, in the line that builds `options`. If you left the array empty, the linter would report: `React Hook useEffect has a missing dependency: 'roomId'`.

This is what React's docs mean by proving to the linter. We never argued with the linter about `options`. We moved one line, and the linter stopped asking for `options` and asked for `roomId` instead.

### Why `roomId` causes no trouble in the array

`roomId` is a string. Strings, numbers, and booleans are **primitive values**: JavaScript compares them by their content, as the two `'music'` strings showed. So while the user stays in the general room, every render gives `roomId` the same value, `'general'`, and React keeps the connection. When the user picks `travel`, the value really changes, and React reconnects.

That is why React's docs give one piece of advice for every object or function dependency: "try moving them outside the component, inside the Effect, or extracting primitive values out of them."

### Static objects go above the component, dynamic ones inside the Effect

The right place for the object depends on what it reads. React's docs name two kinds of objects, and each has its own place:
1. **A static object** "does not depend on any props and state". It goes above the component. JavaScript makes it once, when the file loads, so it is the same object on every render, and the array becomes `[]`.
2. **A dynamic object** "depends on some reactive value that may change as a result of a re-render, like a `roomId` prop". It goes inside the Effect, and the array lists the values it reads, such as `[roomId]`.

React's docs show the static kind with a chat that is always in the music room:

```jsx title="A static options object above the component"
const ~options~ = { serverUrl: 'https://localhost:1234', roomId: 'music' }; // Made once, when the file loads

function ChatRoom() {
  useEffect(() => {
    const connection = createConnection(options);
    connection.connect();
    return () => connection.disconnect();
  }, ~[]~); // options is not reactive, so the array is empty
}
```

On our page, the menu changes the room, so `options` reads the `roomId` prop. It is dynamic, and it goes inside the Effect.

```tree caption="Where an object dependency goes: a static object above the component, a dynamic object inside the Effect."
Where to make the object the Effect reads
- +Static: depends on no props and no state [`roomId: 'music'`] | Make it **above the component**, once | The array is **empty**
- +Dynamic: depends on a prop or state [`roomId: roomId`] | Make it **inside the Effect** | The array lists only **`roomId`**
```

The same holds for a function. Keep the `createOptions` helper from Principle 1, and only move it inside the Effect: yes, it is the exact same thing as moving the object! React's docs: "As long as you also declare them *inside* your Effect, they're not reactive values, and so they don't need to be dependencies of your Effect."

### When `options` arrives as a prop

Sometimes the object is not ours to move. React's docs show this mistake in one of their Challenges:
1. `App` builds `options` from its own state and passes it down as a prop, `<ChatRoom options={options} />`.
2. `ChatRoom` reads `options` inside its Effect and lists `[options]`.
3. The user clicks a `Toggle theme` button, which changes only the theme of `App`.
4. `App` renders again and builds a new `options`, so the chat reconnects. The docs: "Your Effect is re-running because it depends on the `options` object."

`ChatRoom` cannot move a prop. Instead, it reads the primitive values out of the object, before the Effect:

```jsx title="Reading primitive values out of an options prop"
function ChatRoom({ options }) {
  const { roomId, serverUrl } = ~options~; // Reads two strings out of the object, outside the Effect

  useEffect(() => {
    const connection = createConnection({ roomId: roomId, serverUrl: serverUrl });
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId, serverUrl]~); // Two strings: a new options with the same room does not reconnect
}
```

React's docs: "If an object is re-created unintentionally by the parent component, the chat would not re-connect. However, if `options.roomId` or `options.serverUrl` really are different, the chat would re-connect."

A function that arrives as a prop, such as `getOptions`, works the same way. Call it outside the Effect, read `roomId` and `serverUrl` from the object it returns, and list the two strings. The docs add one condition about pure functions (as seen in Lesson 14): "This only works for pure functions because they are safe to call during rendering." When you also write the parent, the docs suggest a simpler fix: pass `roomId` and `serverUrl` as two props instead of one `options` object.

> [!PRINCIPLE]
> **Principle 2: Moving the Object: `options` Built Inside the Effect Leaves Only `roomId`**
>
> *Move an object or a function that depends on props or state inside the Effect, and one that depends on neither above the component; then it is not reactive, it leaves the array, and only the primitive values it reads, such as `roomId`, stay.*
>
> We do not remove `options` from the array by hand. We move the line that makes it, and the linter itself asks for the shorter array. A value made inside the Effect is not reactive, and the string `roomId` is compared by its content, so the chat reconnects only when the user picks another room. When the object arrives as a prop, read its primitive values before the Effect and list those.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const ~options~ = { serverUrl: serverUrl, roomId: roomId }; // Made inside the Effect: not reactive
>   const connection = createConnection(options);
>   connection.connect();
>   return () => connection.disconnect();
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const options = { serverUrl: serverUrl, roomId: roomId };
> useEffect(() => {
>   const connection = createConnection(options);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[options]~); // **WRONG:** options is made in the component body, so every letter reconnects the chat
> ```

## 3. Principle 3: An Updater Function Keeps New Messages from Reconnecting the Chat

### Reading `messages` vs. passing an updater function

Now the room shows the messages that arrive. The Effect hands the connection a function through its `on` method, and the connection calls that function with each message (as seen in Lesson 36). Inside that function, the Effect must add the new message to the end of `messages` state. There are two ways to write that line:

```jsx title="Reading messages, and passing an updater function"
setMessages(~[...messages, msg]~); // Reads messages: the Effect now depends on messages
setMessages(~msgs => [...msgs, msg]~); // Never reads messages: React passes the current list as msgs
```

Both lines put `msg` at the end of the list. But the first line reads `messages`, so the linter asks for `messages` in the array. The second line reads nothing but `msg`, so `messages` never enters the array.

Developers usually try two other ways before they reach the updater function. Each one breaks the page in its own way, so we look at both first.

### With `messages` in the array, every message reconnects the chat

Here is the first try. `ChatRoom` gets `messages` state and a list under the heading. The Effect reads `messages`, so the developer follows the linter and lists it:

```jsx title="src/components/ChatRoom.jsx" startLine="6"
export default function ChatRoom({ roomId }) {
  const [messages, setMessages] = useState([]);
  const [message, setMessage] = useState('');

  useEffect(() => {
    const options = { serverUrl: serverUrl, roomId: roomId };
    const connection = createConnection(options);
    connection.on('message', msg => {
      setMessages(~[...messages, msg]~); // Reads the messages of this render
    });
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId, messages]~); // **WRONG:** every new message is a new array, so the chat reconnects

  return (
    <section>
      <h1>Welcome to the {roomId} room!</h1>
      <ul>
        {messages.map((m, i) => <li key={i}>{m}</li>)}
      </ul>
      <input
        value={message}
        onChange={e => setMessage(e.target.value)}
      />
    </section>
  );
}
```

The list uses each message's position as its `key`. An index key is a weak choice when items move (as seen in Lesson 18). Here, messages are only added at the end, and the same text `hey` can arrive twice, so the text cannot be the key.

**Beware! With `messages` in the array, every message that arrives disconnects the chat and connects it again.** The list on the screen grows correctly, so the page looks right. It is the same chain as a typed letter in Principle 1, with a new array instead of a new object:
1. A message arrives, and the Effect calls `setMessages` with a new array that holds one more message.
2. `ChatRoom` renders again, and React compares `[roomId, messages]` with the last array. `messages` is a new array, so `Object.is` returns `false`.
3. React runs the cleanup, and the Console shows the disconnect line. Then React runs the new setup, and the Console shows the connect line.

### With the linter silenced, the list never grows past one message

So the developer tries the opposite. They take `messages` out of the array and silence the linter with a comment at the end of the line (as seen in Lesson 36):


1. The Effect ran after the first render, when `messages` was the empty list.
2. The array is `[roomId]`, and the room never changes, so React never runs a newer setup.
3. The function that the connection holds still sees the `messages` of the first render (as seen in Lesson 15).

### With an updater function, the Effect never reads `messages`

The fix is the updater function (as seen in Lesson 16). Instead of reading `messages`, the Effect hands React a function, and React gives that function the current list:

```jsx title="src/components/ChatRoom.jsx" startLine="10"
  useEffect(() => {
    const options = { serverUrl: serverUrl, roomId: roomId };
    const connection = createConnection(options);
    connection.on('message', msg => {
      setMessages(~msgs => [...msgs, msg]~); // React passes the current list as msgs
    });
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId]~); // messages is not read, so it is not a dependency
```

React's docs: "**Notice how your Effect does not read the `messages` variable at all now.**"

React itself passes `msgs` to the updater function. The docs: "React puts your updater function in a queue and will provide the `msgs` argument to it during the next render. This is why the Effect itself doesn't need to depend on `messages` anymore." The name `msgs` is ours, and any name works.

The linter never asks for `setMessages`, because a `set` function is stable (as seen in Lesson 35). React's docs: "Stable values aren't reactive, so you may omit them from the list. Including them is allowed".

```tree caption="Three ways to add an arriving message: list messages, silence the linter, or pass an updater function."
- +Pass an updater function [`msgs`] | The Effect **never reads `messages`** | The chat stays connected, and the list **keeps every message**
```

> [!PRINCIPLE]
> **Principle 3: Updater Functions: Reading No State Removes the State Dependency**
>
> *When the Effect sets state from the same state, such as adding a message to `messages`, pass an updater function to the setter, so the Effect does not read that state and it leaves the array.*
>
> Reading `messages` inside the Effect makes `messages` a dependency, so every message that arrives reconnects the chat. Silencing the linter stops the reconnect, but the Effect keeps the empty list of the first render, so the list shows only the newest message. An updater function reads nothing: React gives it the current list, and the array stays `[roomId]` with no comment.
>
> **DO THIS:**
> ```jsx
> connection.on('message', msg => {
>   setMessages(~msgs => [...msgs, msg]~); // React passes the current list: every message is kept
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> connection.on('message', msg => {
>   setMessages(~[...messages, msg]~); // **WRONG:** with the linter silenced, messages stays the empty list of the first render
> });
> ```

## 4. Principle 4: `roomId` Stays Because Picking a Room Must Reconnect

### Reading the final Effect value by value

After Principles 2 and 3, the array holds one value. Here is the final Effect:

```jsx title="The final Effect in src/components/ChatRoom.jsx" startLine="10"
  useEffect(() => {
    const options = { serverUrl: serverUrl, roomId: ~roomId~ }; // The only reactive value the Effect reads
    const connection = createConnection(options);
    connection.on('message', msg => {
      setMessages(msgs => [...msgs, msg]);
    });
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId]~); // Changes only when the user picks another room
```

Read it value by value. For each value, say why it is in the array or why it is not:
1. **`roomId`** is a prop, read inside the Effect. It stays.
2. **`serverUrl`** is a constant above the component. It is not reactive (as seen in Lesson 35).
3. **`options`** is made inside the Effect. It is not reactive, as Principle 2 showed.
4. **`messages`** is not read at all. The updater function reads `msgs`, as Principle 3 showed.
5. **`setMessages`** is a `set` function, and it is stable.
6. **`message`**, the text in the box, is never read by the Effect.

Typing `h` and picking `travel` both change state, and both render `ChatRoom` again. They look the same, but they are NOT the same thing for the user! Typing a letter changes nothing about the conversation. Picking a room asks for a different conversation. So only `roomId` belongs in the array.

React's docs give this question as the check after every change: "Every time you adjust the Effect's dependencies to reflect the code, look at the dependency list. Does it make sense for the Effect to re-run when any of these dependencies change?" For `roomId`, the answer is yes. The docs on the same chat: "It is important to declare it as a dependency!"

### Moving `roomId` out vs. deleting `roomId` from the array

`roomId` can leave the array only in one case: the room never changes, and the code says so. Compare the two ways a developer might get an empty array:

```jsx title="With roomId moved above the component"
const ~roomId~ = 'music'; // Outside the component: not reactive, and the room never changes

function ChatRoom() {
  useEffect(() => {
    const connection = createConnection({ serverUrl: serverUrl, roomId: roomId });
    connection.connect();
    return () => connection.disconnect();
  }, []);
}
```

```jsx title="With roomId deleted from the array"
function ChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection({ serverUrl: serverUrl, roomId: roomId });
    connection.connect();
    return () => connection.disconnect();
  }, ~[]~); // **WRONG:** the linter reports a missing dependency: 'roomId'
}
```

They look the same, but they are NOT the same thing! Both end with `[]`. With `roomId` moved above the component, the Effect reads a value that never changes, and the linter agrees. This fits a chat that is always in the music room. With `roomId` deleted from the array, the Effect still reads a prop that changes, and the linter reports `React Hook useEffect has a missing dependency: 'roomId'`. If the developer silences it, the heading changes to the travel room while the chat stays connected to the general room (as seen in Lesson 35).

### The docs' three steps

The whole lesson fits in three steps from React's docs:
1. "First, you **change the code** of your Effect or how your reactive values are declared."
2. "Then, you follow the linter and adjust the dependencies to **match the code you have changed.**"
3. "If you're not happy with the list of dependencies, you **go back to the first step**."

The docs compare this to solving an equation: "This might feel like solving an equation." You know the answer you want, such as `[roomId]`, and you look for the code that gives it.

### The questions to ask about an unnecessary dependency

React's docs give three reasons why a developer may not want a dependency:
1. "You might want to re-execute *different parts* of your Effect under different conditions."
2. "You might want to only read the *latest value* of some dependency instead of "reacting" to its changes."
3. "A dependency may change too often *unintentionally* because it's an object or a function."

For each unnecessary dependency, the docs ask a short list of questions. Each answer leads to one tool:
1. **"Should this code move to an event handler?"** When the code runs because of one interaction, such as a form submit, it belongs in the event handler (as seen in Lesson 34).
2. **"Is your Effect doing several unrelated things?"** Split it into two Effects, each with its own array (as seen in Lesson 35).
3. **"Are you reading some state to calculate the next state?"** Pass an updater function, as Principle 3 did with `messages`.
4. **"Do you want to read a value without "reacting" to its changes?"** Move that code into an Effect Event (as seen in Lesson 36).
5. **"Does some reactive value change unintentionally?"** This is an object or a function made during rendering. Move it above the component or inside the Effect, or read its primitive values, as Principles 1 and 2 did with `options`.

Silencing the linter is not on the list. React's docs: "We recommend treating the dependency lint error as a compilation error."

The first question catches a mistake that React's docs show with a form:
1. When the user submits the form, the code sets `submitted` to `true`, and an Effect with `[submitted]` sends the form and shows a notification.
2. Later, the notification reads the page theme, so the developer follows the linter and adds `theme` to the array.
3. Now the user submits the form and then switches the theme. The Effect runs again and shows the same notification a second time.

The docs: "**The problem here is that this shouldn't be an Effect in the first place.**" The code moves into the submit handler, and the dependency question disappears with it.

```tree caption="Which dependencies stay in the final array, and why each of the others is not there."
The values the final Effect touches
- +Stays in the array [`roomId`] | A prop **read inside the Effect** | Picking a room **must reconnect** the chat
- +Not reactive [`serverUrl` `options`] | Made **above the component** or **inside the Effect** | Never a dependency
- +Not read [`messages`] | The updater function reads **`msgs`** | Never a dependency
- +Stable [`setMessages`] | A **`set` function** from `useState` | The linter **never asks** for it
```

> [!PRINCIPLE]
> **Principle 4: Required Dependencies: `roomId` Stays Because Picking a Room Must Reconnect**
>
> *A dependency stays when a change of that value, from the user's side, means the Effect must re-synchronize; a dependency goes only when the code no longer reads a reactive value there, and the linter accepts the shorter array with no comment that silences it.*
>
> Every value in the array answers one question: should a change of this value reconnect the chat? For `roomId`, the answer is yes, because the user picked a different conversation. For a letter typed in the box or a message that arrives, the answer is no, so we change the code until the Effect no longer reads those values. Deleting a value from the array by hand only hides it from the linter.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const options = { serverUrl: serverUrl, roomId: roomId };
>   const connection = createConnection(options);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[roomId]~); // Picking another room reconnects the chat to that room
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const options = { serverUrl: serverUrl, roomId: roomId };
>   const connection = createConnection(options);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[]~); // **WRONG:** with the linter silenced, the chat stays in general after the user picks travel
> ```

## For the Interview

> **The Interview Question:** How do you remove unnecessary effect dependencies, and when must a dependency stay?

### How to Answer Clearly in 30 Seconds

"I never choose the dependencies. The array lists every reactive value the Effect reads, and the linter checks it. To remove a dependency, I change the code so the Effect no longer reads a reactive value there, and then the linter stops asking for it. Three changes cover most cases:
1. **Move an object or a function**: one made in the component body is a new value on every render, so I move a static one above the component and a dynamic one inside the Effect, or I read its primitive values.
2. **Pass an updater function**: when the Effect sets state from the same state, such as adding a message with `msgs => [...msgs, msg]`, it no longer reads that state.
3. **Put the code where it belongs**: in an event handler when it answers one interaction, in two Effects when it does two unrelated things, or in an Effect Event when it reads a value without reacting to it.

A dependency must stay when its change means the Effect must re-synchronize, such as the chat room the user picked. I never silence the linter, because the Effect then keeps stale values."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does an `options` object re-run the Effect when its contents did not change?"**
   React compares each dependency with `Object.is`. Strings and numbers are compared by their content, but each new object is a different value, even with the same contents. React's docs show two objects with the same server and the same room, and `Object.is` returns `false` for them. An object made in the component body is made again on every render, so the Effect re-synchronizes after every render. The fix is to move the object inside the Effect, or above the component, so that only primitive values such as `roomId` stay in the array.
2. **"Can an object in the dependency array cause an infinite loop?"**
   Only when the Effect also sets state. React's docs say an infinite cycle needs two things: "Your Effect is updating some state." and "That state leads to a re-render, which causes the Effect's dependencies to change." Our chat Effect with `[options]` sets no state, so it runs again once after each render, on every letter the user types, and then stops. If that Effect also set state to a new value on every run, such as a new object, the runs would never end. Each run would cause a render, a new `options`, and another run, and the Console would fill with React's error `Maximum update depth exceeded`. Setting state to a value it already holds, such as `true` again, causes no new render, so the runs stop.
3. **"What if the object comes from a parent as a prop, and you cannot move it?"**
   Read its primitive values before the Effect, such as `const { roomId, serverUrl } = options;`, and list `[roomId, serverUrl]`. A new object with the same room then does not reconnect, while a real change of room still does. For a function prop, call it outside the Effect, which works only for pure functions. Better still, pass `roomId` and `serverUrl` as separate props. React's docs keep `useMemo` and `useCallback` as the last resort for this case (covered in Lessons 56 and 57).

```tree dir=right caption="Interview summary: how to remove an unnecessary dependency, and when a dependency must stay."
Removing a dependency vs. keeping it
- +Removable: the code can stop reading it [`options` `messages`] | **Change the code**: move the object, or pass an updater function | The linter **stops asking** for it, with **no comment**
- +Must stay: its change must re-synchronize [`roomId`] | The user **picked another room** | The chat **must reconnect**
- !Never: delete it and silence the linter | The Effect **keeps stale values** | The linter **can no longer warn you**
```
