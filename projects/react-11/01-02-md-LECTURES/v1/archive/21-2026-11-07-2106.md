# Lecture 21: Reacting to Input with State: One Status Picks the Picture
> INTERVIEW QUESTION | ❱ CORE | How do you design a component that reacts to input with state instead of touching the DOM?

## Why a Page Needs One Status Instead of Show and Hide Commands

### The smallest version: a Send button that turns into Thanks!

In Lesson 10, an `if` with its own early `return` let a component draw a completely different picture when a condition was true. In Lesson 12, a click called a setter, and React drew the page again with the new state. Put those two together, and you already hold the whole idea of this lesson. Here is a page with one Send button:

```page width=text caption="A page with one Send button, as it looks when the page opens."
form:
  button: Send
```

This is the whole component:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [status, setStatus] = useState('typing');

  if (status === 'sent') {
    return <p>Thanks!</p>;
  }
  return <button onClick={() => ~setStatus('sent')~}>Send</button>; // The click changes only the state
}
```

The user clicks the Send button. The button is gone, and in its place the page says Thanks!:

```page width=text caption="The same page after the user clicks the Send button: the button is gone and Thanks! is on the page."
line: Thanks! | good
```

Look at the click handler again. It does not hide the button, and it does not write Thanks! anywhere. It only puts the word `'sent'` into `status`. The component already holds both pictures of the page. While `status` is `'typing'`, the picture is a Send button. When it becomes `'sent'`, the picture is the line Thanks!. The click only changes which picture is true, and React draws that picture.

Lesson 01 gave this difference two names. Plain JavaScript is *imperative*: our code gives the browser one command after another, such as hide the button, then show the text. React is *declarative*: our code describes what the page looks like for each value of state, and React makes the page match. Think of two ways to cross a city. You can sit next to a driver and call out every turn: left here, right at the bank, stop at the corner. Or you can step into a taxi, tell the driver the address, and let the driver find the way. The click handler above gives React an address, `'sent'`, and React finds the way to the page.

### The real page problem: a coupon box that shows two messages at once

Now think of the checkout page of an online shop. Under the cart sits a coupon box: a Coupon code box, an Apply button, and room for one message under them. In plain JavaScript, the page starts as HTML, with both messages already written and kept out of sight:

```html title="index.html"
<h1>Checkout</h1>
<label>Coupon code <input id="code"></label>
<button id="apply">Apply</button>
<p id="error" ~hidden~>This code is not valid.</p> <!-- hidden keeps the paragraph out of sight -->
<p id="success" hidden>SAVE10 applied. You save 10%.</p>
<script src="coupon.js"></script>
```

The word `hidden` is an HTML attribute that keeps a tag out of sight, and JavaScript can switch it off with `errorText.hidden = false`. The script finds the box and the two messages, as in Lesson 01, and listens for clicks on the Apply button, as in Lesson 11:

```js title="coupon.js"
const box = document.getElementById('code');
const errorText = document.getElementById('error');
const successText = document.getElementById('success');

document.getElementById('apply').addEventListener('click', () => {
  if (box.value === 'SAVE10') {
    ~successText.hidden = false~; // Command: show the green message
  } else {
    ~errorText.hidden = false~; // Command: show the red message
  }
});
```

The user types SAVE5 and clicks the Apply button. SAVE5 is not a real code, so the `else` branch shows the red message:

```page width=text caption="The plain JavaScript coupon box after the user types SAVE5 and clicks the Apply button."
heading: Checkout
form:
  field: Coupon code | SAVE5
  button: Apply
line: This code is not valid. | bad
```

The user fixes the code to SAVE10 and clicks the Apply button again. This time the green message appears, and the red message is still on the page above it:

```page width=text caption="The plain JavaScript coupon box after the user changes the code to SAVE10 and clicks the Apply button again: both messages are on the page."
heading: Checkout
form:
  field: Coupon code | SAVE10
  button: Apply
line: This code is not valid. | bad
line: SAVE10 applied. You save 10%. | good
```

The second click ran the right branch and showed the right message. So why is the wrong message still there? Every line in this handler is a command, and a command changes the page at one moment and then stays done until another command undoes it. Here is what happened, click by click:
1. The first click runs the `else` branch, and `errorText.hidden = false` shows the red message.
2. No line in the script ever sets `errorText.hidden` back to `true`, so the red message stays shown.
3. The second click runs the first branch, and `successText.hidden = false` shows the green message.
4. That branch only knows that it must show the green message. It has no way to know that an earlier click showed the red one, so the red message stays on the page.

The plain JavaScript fix is one more command in each branch. The success branch must also hide the red message, and the error branch must also hide the green one. That works for two messages. But every new message adds a line to every branch that already exists, because each command must undo whatever all the other commands may have shown. Lesson 01 met this problem with one value shown in two places. Here it is bigger: whole pictures of the page must replace each other, and plain JavaScript leaves every replacement to us.

### Our example page: the coupon box of a checkout page

In this lesson we build the same coupon box in React. The project has four files, and the coupon box lives in one component, `CouponBox`:

```files title="checkout-page: File Explorer" caption="How the files of our checkout page sit inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` and mounts it inside `<StrictMode>` into `#root`
  App.jsx | parent | Exports `App` as default and renders `<CouponBox />` under the heading
  components/
    CouponBox.jsx | default export | Exports `CouponBox` as default and holds the box, the button, and every message
```

`App` only places the heading and the coupon box on the page:

```jsx title="src/App.jsx"
import CouponBox from './components/CouponBox.jsx';

export default function App() {
  return (
    <main>
      <h1>Checkout</h1>
      ~<CouponBox />~ {/* React calls CouponBox, which holds the whole coupon box */}
    </main>
  );
}
```

Our project has no real shop server. To stand in for one, the finished box waits one second with `setTimeout`, which Lesson 15 taught, and then accepts SAVE10 and rejects every other code. We start with a `CouponBox` that only draws its pictures, with no state and no handler. Each principle adds one piece, until the box works.

### Five Principles of Reacting to Input with State

**PRINCIPLES:** Five rules turn show and hide commands into a component that reacts to input with state:
1. **The coupon box has five pictures.** Before writing any handler, list every picture the box can show, and draw each one from a single variable, `status`.
2. **Clicks and a timer move the status.** For each picture, find what moves the box into it: the user typing and clicking, or an answer that arrives a second later. Both only set state.
3. **One `status` string replaces four switches.** Four `true` or `false` variables can describe a box with two messages at once. One string can hold only one picture.
4. **The click only sets the status.** The handler never shows or hides anything. React draws the picture for the new status and removes everything that picture does not contain.
5. **A new picture adds one branch.** A new message costs one more status, one line of JSX, and one arrow, and no old picture changes.

Here is the map of the five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **The Coupon Box Has Five Pictures** | A message that appears in the wrong picture, or a box that stays greyed out when the user must fix it, is found the moment every picture is drawn side by side. | List every picture first, and write JSX that draws each one from `status` alone. |
| **Principle 2** | **Clicks and a Timer Move the Status** | A button that stays greyed out forever means one picture has no way out. Interviewers also ask what a state machine is. | For every picture, name the input from the user or from the computer that leads into it, and let each input only set state. |
| **Principle 3** | **One `status` String Replaces Four Switches** | Four `true` or `false` variables bring back the two-message bug of plain JavaScript, and React prints no warning. | Keep the current picture in one string, and calculate anything that state already tells, such as a blank box. |
| **Principle 4** | **The Click Only Sets the Status** | A red message that stays on the page next to Checking... comes from code that changes the page by hand. | Let handlers and timers set the next status, and let the JSX decide what is shown. |
| **Principle 5** | **A New Picture Adds One Branch** | Adding one message to a plain JavaScript page breaks pictures that used to work. | Add one status value, one line of JSX, and one arrow, and leave the other pictures alone. |

## 1. Principle 1: The Coupon Box Has Five Pictures

### The smallest version: five drawings of one coupon box

Before a designer hands a page to a developer, the designer draws it once for every moment the user can meet. There is a drawing of the box when it is blank, one with a code in it, one while the shop checks the code, and so on. Each drawing is a mockup, and all of them lie side by side on the table. We start the same way, before any handler exists. The coupon box can show five pictures:

| Picture | What the user sees |
| :--- | :--- |
| **Empty** | A blank Coupon code box, and the Apply button greyed out, because there is nothing to check yet |
| **Typing** | A code in the box, and the Apply button ready |
| **Checking** | The box and the Apply button both greyed out, and Checking... under them |
| **Applied** | Only the line SAVE10 applied. You save 10%. The box and the button are gone. |
| **Error** | The same as Typing, plus the red line This code is not valid. |

React's documentation calls each of these pictures a **visual state**: one picture of the component that the user can see. To tell the component which picture to draw, we give it one variable, `status`. It holds the name of the current picture as a string, such as `'empty'` or `'error'`. The name `status` is our own choice, and React gives it no special meaning.

To grey out a box or a button, we use `disabled`, the HTML attribute that blocks typing and clicks. In JSX it takes a condition, and the control is greyed out while the condition is `true`. Here is the first `CouponBox`, which draws the five pictures and does nothing else:

```jsx title="src/components/CouponBox.jsx"
export default function CouponBox({ ~status = 'empty'~ }) { // The developer picks the picture here
  if (status === 'applied') {
    return <p className="success">SAVE10 applied. You save 10%.</p>;
  }

  return (
    <section>
      <label>
        Coupon code
        <input disabled={status === 'checking'} />
      </label>
      <button disabled={status === 'empty' || status === 'checking'}>Apply</button>
      {status === 'checking' && <p>Checking...</p>}
      {status === 'error' && <p className="error">This code is not valid.</p>}
    </section>
  );
}
```

`App` writes the coupon box tag with no `status` prop. So the default value from Lesson 09 fills `status` with `'empty'`. The page shows the Empty picture:

```page width=text caption="The coupon box mock with status set to empty: a blank box, and the Apply button greyed out."
heading: Checkout
form:
  field: Coupon code |
  button: Apply
```

A component like this, which can draw every picture before any handler exists, is called a **mock**. We pick its picture by hand, look at it, and fix its layout before we write a single line of logic.

The JSX picks the picture in two different ways, and each one has its own job:
- **The `if` with `return`** replaces the whole picture. The Applied picture shares nothing with the others. So when `status` is `'applied'`, the component returns only the green line, and the box and the button are not part of the page at all.
- **`&&` inside the JSX** adds or drops one line inside the same picture. The Error picture is the Typing picture plus one red line, so it needs no picture of its own, only one line that appears when `status` is `'error'`.

The condition on the Apply button also draws two different buttons. In the Empty picture, `status === 'empty'` is true, so the button is greyed out. In the Typing picture, neither half of the condition is true, so the button is ready.

### How the Error picture appears with no typing

Now change one word in the parameter list. Replace `'empty'` with `'error'`, and save the file:

```jsx title="src/components/CouponBox.jsx"
export default function CouponBox({ ~status = 'error'~ }) { // Pick the Error picture
```

The page now shows a blank box, a ready Apply button, and the red message:

```page width=text caption="The coupon box mock with status set to error: a ready Apply button and the red message, with no typing and no click."
heading: Checkout
form:
  field: Coupon code |
  button: Apply
line: This code is not valid. | bad
```

Nobody typed a wrong code, and nobody clicked the Apply button. How can the Error picture appear? Because React never asks what the user did. Here is what happens when the page draws:
1. React calls `CouponBox` with no status prop, so the default value fills it with `'error'`.
2. The `if` for `'applied'` does not match, so the component goes on to its main return.
3. The conditions for `'checking'` are false, so the box and the Apply button are ready.
4. The condition for `'error'` is true, so `&&` gives the red paragraph.

At no step did the component ask what happened before. It asked only one question: what does `status` hold right now?

Because the JSX reads only `status`, every picture can be drawn at any moment, with no user at all. We can even put all five on one page. This `App` draws one mock for each status, using a list with a `key` on each item, as in Lesson 18:

```jsx title="src/App.jsx"
import CouponBox from './components/CouponBox.jsx';

const statuses = ['empty', 'typing', 'checking', 'applied', 'error'];

export default function App() {
  return (
    <main>
      <h1>Checkout</h1>
      {statuses.map(status => (
        <div key={status}>
          <h2>{status}</h2>
          ~<CouponBox status={status} />~ {/* One mock for each picture */}
        </div>
      ))}
    </main>
  );
}
```

All five pictures now sit on the page together, like the designer's drawings on the table:

```page caption="Every picture of the coupon box mock on one page. The Apply button is greyed out under empty and checking, and the box is greyed out under checking. The boxes are blank because nobody types in a mock."
heading: Checkout
section: empty
form:
  field: Coupon code |
  button: Apply
section: typing
form:
  field: Coupon code |
  button: Apply
section: checking
form:
  field: Coupon code |
  button: Apply
line: Checking...
section: applied
line: SAVE10 applied. You save 10%. | good
section: error
form:
  field: Coupon code |
  button: Apply
line: This code is not valid. | bad
```

React's documentation calls a page like this a *living styleguide* or a *storybook*. The plain JavaScript coupon box could never produce it. Its red message exists only after someone types a wrong code and clicks the Apply button. The message is the result of a command, and a command needs a moment to run in. In React, the Error picture is a description, and a description can be read whenever we like.

### Mistake: an Error picture that greys out the box

A developer draws the Error picture by starting from the Checking picture and adding the red line. So the box keeps the condition of the Checking picture, with the Error status added to it:

```jsx title="src/components/CouponBox.jsx" startLine="10"
        <input ~disabled={status === 'checking' || status === 'error'}~ /> {/* **WRONG:** the box is greyed out in the Error picture */}
```

Once the box works, the user types SAVE5, clicks the Apply button, and sees the red message. Then the user tries to fix the code, and cannot type a single letter, because the box is greyed out. React's documentation warns about exactly this: never show an error message and disable the input at the same time, or the user cannot correct the error.

With the five pictures side by side, the bug shows before any user meets it. The Error picture on the styleguide page has a greyed-out box, while the table of pictures says that Error is Typing plus one red line. The fix is to grey out the box only while the shop is checking:

```jsx title="src/components/CouponBox.jsx" startLine="10"
        <input ~disabled={status === 'checking'}~ /> {/* Greyed out only while checking */}
```

> [!PRINCIPLE]
> **Principle 1: Pictures First: The Coupon Box Has Five Pictures**
>
> *Before writing any handler, list every picture the component can show, and write JSX that draws each picture from one variable, `status`.*
>
> A plain JavaScript page has no pictures, only commands, so its error message exists only after someone makes the error happen. A React component describes every picture at once. The JSX asks only what `status` holds right now, never what happened before. So you can set the status by hand in a mock, look at each picture, and catch a wrong button or a greyed-out box before any handler exists.
>
> **DO THIS:**
> ```jsx
> function CouponBox({ status = 'empty' }) {
>   if (~status === 'applied'~) { // Each picture follows from status alone
>     return <p>SAVE10 applied. You save 10%.</p>;
>   }
>   return <button disabled={status === 'empty'}>Apply</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function CouponBox({ status = 'error' }) {
>   return <input ~disabled={status === 'error'}~ />; // **WRONG:** the Error picture locks the box the user must fix
> }
> ```

## 2. Principle 2: Clicks and a Timer Move the Status

### The smallest version: a Send button that waits one second

The mock draws every picture, but nothing moves it from one picture to the next. Go back to the Send button from the start of this lecture and give it a third picture, Sending..., which lasts one second before Thanks! appears:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [status, setStatus] = useState('typing');

  function handleSend() {
    ~setStatus('sending')~; // The click moves the page to Sending...
    setTimeout(() => {
      ~setStatus('sent')~; // One second later, the timer moves it to Thanks!
    }, 1000);
  }

  if (status === 'sent') {
    return <p>Thanks!</p>;
  }
  return (
    <section>
      <button onClick={handleSend} disabled={status === 'sending'}>Send</button>
      {status === 'sending' && <p>Sending...</p>}
    </section>
  );
}
```

The user clicks the Send button once. The button is greyed out, and Sending... appears under it:

```page width=text caption="The Send page right after the click: the Send button is greyed out and Sending... is under it."
form:
  button: Send
line: Sending...
```

One second later, with no second click, the page says Thanks!:

```page width=text caption="The same page one second after the click, with no second click from the user."
line: Thanks! | good
```

The user clicked only once, and the page moved twice. Who moved it the second time? The browser did, because our click handler left a function with it:
1. The click calls `handleSend`. Its first line sets the status to sending, which asks for a new render. Then `setTimeout` hands the arrow function to the browser to keep for one second.
2. `handleSend` finishes, and React draws the Sending picture.
3. One second later, the browser calls the function it was given.
4. That function sets the status to sent, and React draws the Thanks picture.

The first move came from the user, and the second came from the clock.

### Human inputs and computer inputs

React's documentation sorts everything that moves a page into two kinds:
- **A human input** is something the user does, such as clicking a button, typing in a box, or following a link. It reaches our code through an event handler, such as `onClick`.
- **A computer input** is something that arrives without the user doing anything, such as an answer from a server, a timer finishing, or an image loading. It reaches our code through a function that someone else calls later, here the function given to `setTimeout`.

The documentation puts both kinds in one list, and says that in both cases, you must set state variables to update the page. An answer from a server feels like a different kind of thing from a click, because no one touches the page. To React it is the same kind of thing: an input. So the function the timer runs does not show Thanks! itself. It sets state, exactly like a click handler, and React draws the picture. In a real shop, the answer would come from the network instead of from a timer. The function that receives it would still do only one thing: set the next status.

### Drawing the arrows of the coupon box

Now we do the same for the coupon box. For every picture, we ask what moves the box into it, and whether the user or the computer does the moving:

| From | What happens | To | Kind of input |
| :--- | :--- | :--- | :--- |
| **Empty** | The user types a letter in the box | **Typing** | Human |
| **Typing** | The user deletes every letter | **Empty** | Human |
| **Typing** | The user clicks the Apply button | **Checking** | Human |
| **Checking** | The answer says the code is accepted | **Applied** | Computer |
| **Checking** | The answer says the code is not valid | **Error** | Computer |
| **Error** | The user clicks the Apply button again | **Checking** | Human |

React's documentation suggests drawing this on paper: each picture as a labeled circle, and each move between two pictures as an arrow. Here are the five circles, each with the arrows that leave it:

```tree caption="The five pictures of the coupon box, each with the arrows that leave it. Applied has no arrow out."
The coupon box is always in exactly one picture
- Empty | The user types a letter: to **Typing**
- Typing | The user deletes every letter: to **Empty** | The user clicks Apply: to **Checking**
- Checking | The answer accepts the code: to **Applied** | The answer rejects the code: to **Error**
- +Applied | **No arrow** leaves this picture
- !Error | The user clicks Apply again: to **Checking**
```

A drawing like this has a name from computer science: a **state machine**. It is something that is always in exactly one of a fixed set of states, and it moves between them only along fixed arrows. A traffic light is a state machine. It shows red, amber, or green, never two at once, and it moves only along its arrows: green never jumps straight to red.

The JSX of the mock already holds the circles. The arrows have no code yet. Principle 4 writes them, and each one will do what the timer did on the Send page: set the next status.

### Mistake: an Error picture with no way out

Suppose a developer skips the drawing and writes the Apply button from a quick thought: the button is ready only while the user is typing.

```jsx title="src/components/CouponBox.jsx" startLine="12"
      <button ~disabled={status !== 'typing'}~>Apply</button> {/* **WRONG:** greys out Apply in the Error picture too */}
```

Once the box works, the user types SAVE5 and clicks the Apply button, and the answer moves the box to the Error picture. The user fixes the code to SAVE10 and reaches for the Apply button, but it is greyed out. The status is `'error'`, and the button is ready only for `'typing'`. The box is stuck: the user can type, but can never check the new code.

The drawing shows the bug before any user meets it. The Error circle has one arrow out, the user clicks Apply again, and that arrow needs a button that is ready. In the mock, setting the default to `'error'` shows the greyed-out button at once. The fix is the condition that Principle 1 wrote from the pictures, which greys out the button only in Empty and Checking:

```jsx title="src/components/CouponBox.jsx" startLine="12"
      <button ~disabled={status === 'empty' || status === 'checking'}~>Apply</button> {/* Ready in Typing and in Error */}
```

> [!PRINCIPLE]
> **Principle 2: Inputs Move the Picture: Clicks and a Timer Move the Status**
>
> *For every picture, find the input that moves the component into it: a human input such as a click, or a computer input such as an answer arriving. Let every input only set state.*
>
> A click and an answer from a server look like different things, but to React both are inputs, and both end by calling a setter. Draw each picture as a circle and each input as an arrow, and you have a state machine. A picture with no arrow out, such as an Error picture whose Apply button is greyed out, is a dead end the user cannot leave.
>
> **DO THIS:**
> ```jsx
> function handleSend() {
>   setStatus('sending'); // Human input: the click
>   setTimeout(() => {
>     ~setStatus('sent')~; // Computer input: the timer only sets state too
>   }, 1000);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button ~disabled={status !== 'typing'}~>Apply</button> {/* **WRONG:** the Error picture has no way back to Checking */}
> ```

## 3. Principle 3: One `status` String Replaces Four Switches

### The smallest version: four switches for four pictures

The mock received its picture as a prop, and the developer picked it by editing code. A working box must keep its picture in state, so that the user's typing and clicking can change it. It also needs the text the user types, and for that we already have a tool: a controlled box from Lesson 20, with its text in `code`:

```jsx title="The text of the box, kept in state"
const [code, setCode] = useState('');

<input value={code} onChange={e => setCode(e.target.value)} />
```

For the picture, the first idea that comes to mind, and the first idea React's documentation shows, is one `true` or `false` state variable for each picture. The Empty picture gets no switch, because `code` will tell it, as the end of this principle shows. The other four pictures get one switch each:

```jsx title="The first idea: one switch for each picture"
const [isTyping, setIsTyping] = useState(true);
const [isChecking, setIsChecking] = useState(false);
const [isApplied, setIsApplied] = useState(false);
const [isError, setIsError] = useState(false);
```

Count what these four switches can describe. Each one can be `true` or `false`, so together they have 2 times 2 times 2 times 2 combinations, which is 16. Only 4 of those 16 are pictures of our box: the ones where exactly one switch is on. The other 12 describe pages that must never appear, such as a box that is checking and applied at the same time.

A traffic light shows the difference. Build it from three separate switches, one for each lamp, and nothing stops red and green from lighting together. Build it from one dial with three positions, and two lamps can never light at once, because the dial points at one position.

### Mistake: four switches bring back two messages

The answer arrives one second after a click on the Apply button. Then the version with four switches turns off `isChecking` and turns on the switch for the result:

```jsx title="The answer in the version with four switches"
    setTimeout(() => {
      setIsChecking(false);
      if (code === 'SAVE10') {
        ~setIsApplied(true)~; // **WRONG:** turns on Applied, but nothing turns off Error
      } else {
        setIsError(true);
      }
    }, 1000);
```

The JSX shows one message for each switch:

```jsx title="The JSX in the version with four switches"
      {isError && <p className="error">This code is not valid.</p>}
      {isApplied && <p className="success">SAVE10 applied. You save 10%.</p>}
```

The user types SAVE5 and clicks the Apply button, and the red message appears. Then the user changes the code to SAVE10 and clicks the Apply button again. One second later, the page shows both messages:

```page width=text caption="The coupon box with four switches after SAVE5, then SAVE10: both messages are on the page, the same bug as plain JavaScript."
heading: Checkout
form:
  field: Coupon code | SAVE10
  button: Apply
line: This code is not valid. | bad
line: SAVE10 applied. You save 10%. | good
```

This is the bug of the plain JavaScript page, now in React. Why does React draw both messages, when React is supposed to keep the page right?
1. The first answer, for SAVE5, set `isError` to `true`.
2. The second answer, for SAVE10, turned on `isApplied`, and no line turned `isError` back off.
3. React renders `CouponBox` and reads both switches.
4. The JSX shows the red line while `isError` is true, and the green line while `isApplied` is true.
5. Both are true, so React draws both lines.

React made the page match state, as it always does. The trouble is that state described a page that must never exist. React's documentation calls such a combination an *impossible state*, or a paradox: values in state that match no picture you would ever want a user to see. The Console stays quiet, because React cannot know which combinations we meant to forbid.

So React alone does not protect us from the two-message bug. Lesson 01 taught that React keeps the page in step with the data, and it does. But four switches are four pieces of data that can disagree with each other, and React shows the disagreement faithfully. Only the shape of state can rule out a page with two messages.

### The fix: one string that holds one picture

One string can hold only one value at a time. So we replace the four switches with one state variable, `status`, next to `code`:

```jsx title="src/components/CouponBox.jsx"
import { useState } from 'react';

export default function CouponBox() {
  const [code, setCode] = useState('');
  const [status, setStatus] = ~useState('typing')~; // One string: only one picture at a time

  if (status === 'applied') {
    return <p className="success">SAVE10 applied. You save 10%.</p>;
  }

  return (
    <section>
      <label>
        Coupon code
        <input value={code} onChange={e => setCode(e.target.value)} disabled={status === 'checking'} />
      </label>
      <button ~disabled={code.length === 0 || status === 'checking'}~>Apply</button> {/* The Empty picture comes from code */}
      {status === 'checking' && <p>Checking...</p>}
      {status === 'error' && <p className="error">This code is not valid.</p>}
    </section>
  );
}
```

The JSX below the two `useState` lines is the JSX of the mock. Only the source of `status` changed. The mock got it from a prop that the developer picked, and this box gets it from state that the user's actions will change. Once Principle 4 writes the handler, setting the status to `'applied'` ends `'error'` by itself, because one string cannot hold both. No line has to remember to turn anything off.

### Where did the Empty picture go?

The mock had five statuses. This version has only four: typing, checking, applied, and error. None of them is `'empty'`. Yet the page still opens with a blank box and a greyed-out Apply button:

```page width=text caption="The coupon box with state, when the page opens: a blank box, and the Apply button greyed out."
heading: Checkout
form:
  field: Coupon code |
  button: Apply
```

How does the page show the Empty picture with no `'empty'` status? The condition on the Apply button reads `code` instead:
1. The box shows `code`, and `code` starts as an empty string.
2. During the render, `code.length === 0` is true.
3. So the Apply button is greyed out.
4. When the user types a letter, `code` is no longer empty, the same condition is false on the next render, and the button is ready.

An `'empty'` status would be a second copy of a fact that `code` already holds. Our code would have to keep that copy equal to `code.length === 0` by hand, on every key. One forgotten line would leave the button greyed out next to a full box. The length is read fresh from `code` on every render, so it can never disagree with the box. React's documentation calls the state that remains after this kind of pruning *essential state*: the state you cannot remove without breaking the page. Lesson 22 gives the full rules for which values belong in state and which are calculated.

> [!PRINCIPLE]
> **Principle 3: One String: One `status` String Replaces Four Switches**
>
> *Keep the current picture in one state variable that holds one string, such as `'checking'` or `'error'`, instead of one true or false variable for each picture.*
>
> React draws exactly what state says, even when state describes a page that must never exist. Four switches allow 16 combinations for 4 pictures. So a forgotten reset puts the red error and the green success on the page together, with no warning in the Console. One string can hold only one value, so setting the next picture ends the old one by itself. A blank box needs no status of its own, because `code.length === 0` already tells it.
>
> **DO THIS:**
> ```jsx
> const [code, setCode] = useState('');
> const [status, setStatus] = ~useState('typing')~; // One picture at a time
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [isApplied, setIsApplied] = useState(false);
> const [isError, setIsError] = ~useState(false)~; // **WRONG:** both can be true, and both messages show
> ```

## 4. Principle 4: The Click Only Sets the Status

### The smallest version: a handler that sets the next status

The box now keeps its picture in `status`, and the drawing of Principle 2 says which arrows must exist. Two of them already work. The arrows between Empty and Typing need no handler of their own. `onChange` already puts every key into `code`, and the Apply button reads it on every render. The other arrows start with a click on the Apply button, and a handler is where they become code. The click moves the box to Checking, and the answer one second later moves it to Applied or to Error:

```jsx title="src/components/CouponBox.jsx" startLine="7"
  function handleApply() {
    ~setStatus('checking')~; // Human input: the click sets the next status, nothing else
    setTimeout(() => {
      if (code === 'SAVE10') {
        ~setStatus('applied')~; // Computer input: the answer sets the next status too
      } else {
        setStatus('error');
      }
    }, 1000);
  }
```

The Apply button gets the handler:

```jsx title="src/components/CouponBox.jsx" startLine="28"
      <button ~onClick={handleApply}~ disabled={code.length === 0 || status === 'checking'}>Apply</button> {/* The click starts the arrow to Checking */}
```

This is the taxi from the start of this lecture. The handler gives React an address, a status, and React finds the way to the page. Nothing in `handleApply` greys out a button, writes Checking..., or shows a message.

### Who removed the red message?

The user types SAVE5 and clicks the Apply button. The box shows Checking... for one second, and then the Error picture:

```page width=text caption="The working coupon box after SAVE5 and one click on the Apply button, one second later."
heading: Checkout
form:
  field: Coupon code | SAVE5
  button: Apply
line: This code is not valid. | bad
```

The user changes the code to SAVE10. The red line stays, because typing changes only `code`, and the status is still `'error'`. Then the user clicks the Apply button. At once, the red message is gone, and Checking... is under a greyed-out box and button:

```page width=text caption="The same box right after the user changes the code to SAVE10 and clicks the Apply button: the red message is gone. The box and the Apply button are greyed out."
heading: Checkout
form:
  field: Coupon code | SAVE10
  button: Apply
line: Checking...
```

`handleApply` has no line that hides the red message. So who removed it? React did, on the render that the click asked for:
1. The click calls `handleApply`, which sets the status to checking and asks for a new render.
2. React calls `CouponBox` again, and this time the status is `'checking'`.
3. The condition for `'error'` is false, so the red line is not in the new JSX at all.
4. The conditions for `'checking'` are true, so Checking... is in the new JSX, and the box and the button are greyed out.
5. React compares the new JSX with the JSX of the last render, as Lesson 13 showed. It removes the red paragraph from the page, adds the Checking paragraph, and greys out the box and the button.

One second later, the timer sets `'applied'`, and the early `return` draws only the green line:

```page width=text caption="The same box one second after the click: only the Applied picture is on the page."
heading: Checkout
line: SAVE10 applied. You save 10%. | good
```

React's documentation has an exercise that shows why this works. It rebuilds a plain JavaScript form so that every change calls one function, `updateDOM`, which sets every part of the page from the current variables, every single time. Then it says that this function shows what React does under the hood when you set state. The one difference is that React leaves alone every part of the page that has not changed since the last render. So a handler never has to know what the last picture showed. Every time a handler sets state, React works out the whole picture again from the start. The red line goes because the new picture has no red line in it. The plain JavaScript handler had to undo the old picture. The React handler only names the new one.

### A command and a description are NOT the same

A command changes the page at one moment, and the change stays until another command undoes it. A description says what the page shows while a condition is true, and React checks it again on every render. In plain JavaScript, the red message appears through a command:

```js title="coupon.js"
~errorText.hidden = false~; // Shown now, and shown until another command hides it
```

Every other branch must remember to undo it, which is the two-message bug from the start of this lecture. In React, the red message appears through a description:

```jsx title="src/components/CouponBox.jsx"
{~status === 'error'~ && <p className="error">This code is not valid.</p>} {/* Shown only while status is error */}
```

The description has nothing to undo. The red line is on the page exactly while `status` is `'error'`, and gone on the first render where it is not. React's documentation says it plainly: in React, you do not show, hide, enable, or disable components directly; you declare what you want to show.

### Which code does the timer read?

The answer arrives one second after the click, and it reads `code`. The function given to `setTimeout` was created during the render in which the user clicked. As Lesson 15 showed, it reads the `code` of that render, SAVE10, so it sets `'applied'`. The Checking picture also greys out the box, so the user cannot change the code during that second anyway.

### Mistake: hiding the red message by hand

Many developers bring one habit with them from plain JavaScript: showing and hiding parts of the page by switching classes on DOM nodes. A developer with that habit keeps the red paragraph in the JSX of every picture, and a stylesheet rule hides every tag with the class `hidden`:

```jsx title="src/components/CouponBox.jsx" startLine="30"
      <p id="error" ~className="hidden"~>This code is not valid.</p> {/* **WRONG:** the paragraph sits in every picture, hidden only by a class */}
```

When the answer rejects a code, the developer sets the status back to `'typing'`, so the box and the button are ready again. Then the developer shows the red line by reaching into the page and swapping its class:

```jsx title="src/components/CouponBox.jsx" startLine="12"
      } else {
        setStatus('typing');
        ~document.getElementById('error').className = 'error'~; // **WRONG:** our code changes a node that React owns
      }
```

The user types SAVE5 and clicks the Apply button, and the red line appears, so the trick seems to work. Then the user changes the code to SAVE10 and clicks the Apply button. Checking... appears, and the red message is still there next to it:

```page width=text caption="The coupon box that shows the error by hand, right after the user changes the code to SAVE10 and clicks the Apply button: Checking... and the red message are on the page together."
heading: Checkout
form:
  field: Coupon code | SAVE10
  button: Apply
line: Checking...
line: This code is not valid. | bad
```

The status is now `'checking'`, and the JSX still says `className="hidden"`. So why does the red message stay? Because React compares its renders with each other, never with the page:
1. On the first render, React gives the paragraph the class `hidden`, and the stylesheet hides it.
2. When the answer for SAVE5 arrives, our command swaps the class for `error` directly in the page. React does not know, because the change did not go through state.
3. On every render after that, including the one the click on the Apply button asks for, the JSX again says `className="hidden"`, the same as the render before.
4. React compares the new JSX with the last JSX, finds no change in the class, and leaves the paragraph alone.
5. The paragraph keeps the class our command gave it, so the red line stays on the page.

The page now has two owners: React for everything in the JSX, and our command for one paragraph. Lesson 14 called a change to the page from inside a component a side effect, and this is why it does not belong there. The fix is to delete the command and the `id`, and let the status decide:

```jsx title="src/components/CouponBox.jsx" startLine="30"
      {~status === 'error'~ && <p className="error">This code is not valid.</p>} {/* React alone owns this paragraph */}
```

> [!PRINCIPLE]
> **Principle 4: Handlers Set State: The Click Only Sets the Status**
>
> *Let every event handler and every timer only set the next status, and let the JSX decide what is shown, greyed out, or removed.*
>
> A plain JavaScript command stays done until another command undoes it, so every branch must remember what every other branch showed. A React handler only names the next picture. React works out that picture from the start and removes whatever it does not contain, so the red error disappears with no line that hides it. A command that changes the page by hand gives the page a second owner. React compares only its own renders, so it leaves the wrong line on the page.
>
> **DO THIS:**
> ```jsx
> function handleApply() {
>   ~setStatus('checking')~; // Names the next picture; React removes the red line
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleApply() {
>   ~document.getElementById('error').className = 'hidden'~; // **WRONG:** a change React never sees
> }
> ```

## 5. Principle 5: A New Picture Adds One Branch

### The smallest version: a code that has expired

The shop now wants one more message. Last summer's code, SUMMER, is a real code, but it has expired, and the user should be told so instead of hearing that the code is not valid. In React, the new picture needs two changes. The answer gets one more arrow:

```jsx title="src/components/CouponBox.jsx" startLine="9"
    setTimeout(() => {
      if (code === 'SAVE10') {
        setStatus('applied');
      } ~else if (code === 'SUMMER')~ { // New arrow: the answer says the code has expired
        setStatus('expired');
      } else {
        setStatus('error');
      }

```

The JSX gets one more line, because the Expired picture is the Typing picture plus one message:

```jsx title="src/components/CouponBox.jsx" startLine="33"
      {~status === 'expired'~ && <p className="error">This code has expired.</p>} {/* New picture: Typing plus one line */}

No line written for Checking or Applied mentions `'expired'`, yet the expired message went away. The steps are the ones Principle 4 showed: the click sets `'checking'`, React draws the Checking picture, which has no expired line, and the timer later sets `'applied'`. No old picture had to learn about the new message, because no old picture ever described it.

### The same message in plain JavaScript

Now add the same message to the plain JavaScript page. Its HTML gets one more hidden paragraph:

```html title="index.html"
<p id="expired" hidden>This code has expired.</p>
```

The handler in `coupon.js` already has the fix described at the start of this lecture, so each of its two branches hides the other message. Now it gets a third branch, and every branch must hide two messages instead of one:

```js title="coupon.js" startLine="4"
const expiredText = document.getElementById('expired');

document.getElementById('apply').addEventListener('click', () => {
  if (box.value === 'SAVE10') {
    successText.hidden = false;
    ~errorText.hidden = true~; // **WRONG:** hides the red message, but nothing hides the expired one
  } else if (box.value === 'SUMMER') {
    expiredText.hidden = false;
    errorText.hidden = true;
    successText.hidden = true;
  } else {
    errorText.hidden = false;
    successText.hidden = true;
    expiredText.hidden = true;
  }
});
```

The developer wrote the new branch carefully, and added the new hide line to the error branch, but forgot it in the success branch. The user types SUMMER and clicks the Apply button, then types SAVE10 and clicks the Apply button again:

```page width=text caption="The plain JavaScript coupon box after SUMMER, then SAVE10: the success message and the expired message are on the page together."
heading: Checkout
form:
  field: Coupon code | SAVE10
  button: Apply
line: SAVE10 applied. You save 10%. | good
line: This code has expired. | bad
```

The two versions pay very different prices for the same new message:
- **In plain JavaScript**, the new message costs one paragraph, one new branch that hides both old messages, and one new line in each of the two old branches. Two of those places are in code that already worked, and one forgotten line breaks a picture that used to be right.
- **In React**, the new message costs one `else if` in the answer and one `&&` line in the JSX. No old line changes, so no old picture can break.

React's documentation admits that the React version is the longer one at first, and says it is much less fragile. The extra length is paid once, when we list the pictures and draw them. After that, every new picture costs the same small amount: one status, one line of JSX, and one arrow. In plain JavaScript, the cost of a new message grows with every message already on the page. Each command must hide everything that all the other commands may have shown.

> [!PRINCIPLE]
> **Principle 5: One Branch per Picture: A New Picture Adds One Branch**
>
> *To add a picture, add one status value, one line of JSX that draws it, and the arrow that sets it. Leave every other picture as it is.*
>
> In plain JavaScript, a new message must be hidden by every branch that already exists. So adding it means editing code that already worked, and one forgotten line puts two messages on the page. In React, no old picture describes the new message, so no old picture has to undo it. The React version is longer at the start and much less fragile as the page grows.
>
> **DO THIS:**
> ```jsx
> {~status === 'expired'~ && <p className="error">This code has expired.</p>} {/* One new line, no old line changes */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~expiredText.hidden = false~; // **WRONG:** every old branch must now remember to hide this message
> ```

## Putting All Five Principles Together

### The complete `CouponBox.jsx` file

Here is the finished coupon box. The JSX draws every picture from `status` and `code`, and the handler and the timer only set the next status:

```jsx title="src/components/CouponBox.jsx"
import { useState } from 'react';

export default function CouponBox() {
  const [code, setCode] = useState('');
  const [status, setStatus] = ~useState('typing')~; // 3. One string holds the current picture

  function handleApply() {
    ~setStatus('checking')~; // 4. The click only sets the next status
    setTimeout(() => {
      if (code === 'SAVE10') {
        ~setStatus('applied')~; // 2. A computer input sets state, like a click
      } else if (code === 'SUMMER') {
        setStatus('expired');
      } else {
        setStatus('error');
      }
    }, 1000);
  }

  if (~status === 'applied'~) { // 1. The Applied picture replaces everything
    return <p className="success">SAVE10 applied. You save 10%.</p>;
  }

  return (
    <section>
      <label>
        Coupon code
        <input value={code} onChange={e => setCode(e.target.value)} disabled={status === 'checking'} />
      </label>
      <button onClick={handleApply} ~disabled={code.length === 0 || status === 'checking'}~>Apply</button> {/* 3. The Empty picture comes from code */}
      {status === 'checking' && <p>Checking...</p>}
      {status === 'error' && <p className="error">This code is not valid.</p>}
      {~status === 'expired'~ && <p className="error">This code has expired.</p>} {/* 5. The newest picture is one line */}
    </section>
  );
}
```

`App` still places only the heading and the box:

```jsx title="src/App.jsx"
import CouponBox from './components/CouponBox.jsx';

export default function App() {
  return (
    <main>
      <h1>Checkout</h1>
      <CouponBox />
    </main>
  );
}
```

### How React calls the components, and what one click does

When the page loads, React starts at `App` and follows the tags. `App` has one component tag, so React calls `CouponBox` next:

```tree caption="The component tree of the checkout page and the order in which React calls each component."
`main.jsx` mounts `App` inside `<StrictMode>`
- +`App` [1. Called first] | **Root component** | Returns the heading and `<CouponBox />`
  - +`CouponBox` [2. Called second] | Holds **two states**, `code` and `status` | Called again after every key, every click, and every answer
```

The finished box is a state machine with six pictures: Empty, Typing, Checking, Applied, Error, and Expired. Every click on the Apply button goes around the same loop:

```tree dir=right caption="The loop that one click on the Apply button runs, from the click to the next picture on the page."
One click on the Apply button
- +1. Human input | `handleApply` sets **`'checking'`**
- +2. React renders again | Draws the **Checking** picture and removes every message
- +3. Computer input | One second later, the timer sets **`'applied'`**, **`'expired'`**, or **`'error'`**
- +4. React renders again | Draws the picture for the new status | Changes only the parts that differ
```

### Summary

| Aspect | The Plain JavaScript Habit | The React Rule |
| :--- | :--- | :--- |
| **The pictures** | Write commands that show and hide parts, and meet each picture only when it happens | List every picture first, and draw each one from `status` in the JSX |
| **What moves the page** | Treat a click as an event and a server answer as something else | Treat clicks, typing, timers, and answers all as inputs that only set state |
| **Where the picture lives** | Several `true` or `false` flags, which can describe two messages at once | One `status` string, plus values such as `code.length === 0` calculated during render |
| **The handler** | Show the new message, and remember to hide every old one | Set the next status, and let React remove what the new picture does not contain |
| **A new message** | Add a branch, and add a hide line to every old branch | Add one status value, one line of JSX, and one arrow |

## For the Interview

> **The Interview Question:** How do you design a component that reacts to input with state instead of touching the DOM?

### How to Answer Clearly in 30 Seconds

"Instead of writing commands that show and hide parts of the page, I describe what the page looks like in each state. Then React makes the DOM match. I design it in five steps:
1. **List every visual state.** Like a designer with mockups, I name each picture, such as empty, typing, checking, applied, and error. Before writing any handler, I draw each one from one variable in a mock.
2. **Find what moves the page between them.** There are human inputs, such as clicks and typing, and computer inputs, such as a network answer or a timer. Both only set state, and the states with their arrows form a state machine.
3. **Keep the current state in one `status` string.** Several booleans allow impossible combinations, such as an error and a success at the same time, and React draws whatever state says.
4. **Remove state that can be calculated.** An empty flag is not needed when `code.length === 0` already tells it.
5. **Let handlers only set the next status.** They never show, hide, or disable anything, so no branch has to undo another, and a new state costs one value, one line of JSX, and one arrow."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why one `status` string instead of booleans such as `isLoading` and `isError`?"**
   Each boolean doubles the number of combinations. Four booleans give 16 combinations for 4 real states, so a forgotten reset leaves `isError` and `isApplied` both `true`, and React renders both messages without any warning. One string holds exactly one value, so setting `'applied'` ends `'error'` by itself. Some combinations can still make no sense with one string, such as an error object kept in state while the status says success. When the transitions grow many, `useReducer` gathers them in one place, which is the topic of Lesson 27, and libraries such as XState model state machines formally.

2. **"How do you show, hide, or highlight something without toggling classes on DOM nodes?"**
   Calculate it from state during render. Instead of adding and removing a class in a handler with `classList`, keep one piece of state, such as `isActive`, and write `className={isActive ? 'picture active' : 'picture'}` in the JSX. To remove a part entirely, use `&&` or an early `return`. Changing the DOM by hand from inside a component is a side effect, as Lesson 14 showed. React compares its own renders, not the page, so a class changed by hand can stay wrong. One more caution: when an early `return` swaps one tree of tags for a different one, React throws away the state inside the old tree. Lesson 25 covers this.

3. **"In a real app, the answer comes from the network, not from a timer. What changes?"**
   Only the computer input changes. The handler sets `'checking'`, sends the request, and when the answer arrives, the code that receives it sets `'applied'` or `'error'`, exactly as the timer did. The pictures and the JSX stay the same. In a real app you would also keep the error message from the server in state if it varies. React 19 form actions with `useActionState` and `useFormStatus` can manage the waiting picture for you, and Lessons 41 to 44 cover them. Which values belong in state and which are calculated is the topic of Lesson 22.
