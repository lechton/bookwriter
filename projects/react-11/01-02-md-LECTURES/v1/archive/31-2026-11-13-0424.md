# Lecture 31: Reaching a DOM Node with a Ref

*(How does your code put the cursor back into a text field that React created?)*

> INTERVIEW QUESTION | ❱ CORE | How do you reach a DOM node from React to focus it, scroll it, or measure it?

---

## VS | JSX vs. a Ref to the DOM Node: JSX describes the page, the ref hands you the real element

Here is the one sentence to keep in mind for this whole lesson:

**Put `ref={inputRef}` on a tag, and React puts the real element into `inputRef.current`. Then your event handler calls the browser's own methods on it, such as `focus`.**

First, a reminder of the tool from the last lesson:

> [!DEFINITION]
> **What is a ref?** [REVIEW] A ref is an object that React keeps for your component. `useRef(null)` returns `{ current: null }`: an object with one field, `current`.
> React gives you back the same object on every render. Changing `current` does NOT make React render again.
> In Lesson 30, our own code wrote `current`: the Start handler stored the interval ID in it. In this lesson, React writes `current` for us (Lesson 30).

Now the problem. In plain JavaScript, you find the element yourself, and you tell it what to do:

```js title="Plain JavaScript: find the element, then call its method"
const input = ~document.getElementById('name')~; // The real input element on the page
~input.focus()~; // The browser puts the cursor in it
```

In React, you do not create the elements. You write JSX, and React creates the real elements and keeps them up to date (Lesson 01). The text in a field, a class, a line shown or hidden: the JSX says all of it.

But three jobs have no words in JSX:
1. **Focus.** No prop says "the cursor goes into this field now".
2. **Scroll.** No prop says "scroll until this picture is visible".
3. **Measure.** No prop tells you how wide an element is on the screen.

For these jobs, you need the real element. The docs say it plainly: "There is no built-in way to do those things in React, so you will need a *ref* to the DOM node."

> [!DEFINITION]
> **What is a DOM node?** [NEW] A DOM node is the real object the browser keeps for one tag on the page.
> `<input />` in your JSX is only a description. The `<input>` element that React creates from it is the DOM node.
> It is what `document.getElementById` returns, and what the Elements panel shows. The docs say "DOM node" and "DOM element" for the same thing.
> Every DOM node comes with methods and properties from the browser, such as `focus()`, `scrollIntoView()`, and `offsetWidth`. The docs call them browser APIs (Lesson 31).

Here is the whole tool, in three lines:

```jsx title="Put the cursor in a field with a ref"
const inputRef = ~useRef(null)~; // 1. In the component: the object { current: null }
<input ~ref={inputRef}~ /> {/* 2. In the JSX: React puts this input element into inputRef.current */}
~inputRef.current.focus()~; // 3. In a click handler: the browser puts the cursor in the field
```

Line 1 is the ref from Lesson 30. Line 3 calls `focus`, a method the browser gives every element. Only line 2 is new.

### The same ref as in Lesson 30, filled by React

It is the exact same kind of ref. The only difference is who writes `current`:

```jsx title="Our code writes current, or React writes current"
intervalRef.current = ~setInterval(tick, 1000)~; // Lesson 30: our Start handler writes the interval ID
<input ~ref={inputRef}~ /> {/* This lesson: React writes the input element */}
```

The docs: "Refs are a generic concept, but most often you'll use them to hold DOM elements."

```tree dir=right caption="The same ref object from useRef, filled by our code in Lesson 30 and by React in this lesson."
Who writes `current`
- +Our code [`intervalRef.current = setInterval`] | Lesson 30: the **Start handler** stores the interval ID | The **Stop handler** reads it later
- +React [`<input ref={inputRef} />`] | This lesson: the tag carries the **`ref` attribute** | React stores **the input element**, and our handler calls `focus` on it
```

The docs call this stepping "outside React". Their examples: "managing focus, scroll position, or calling browser APIs that React does not expose".

### The Rule of Thumb: can the JSX say it?

**Ask one question about every job: can the JSX say it? If yes, use state and JSX. If it is focus, scroll, or a size, use a ref, and read it in an event handler.**

This is the rare case. The docs: "React automatically updates the DOM to match your render output, so your components won't often need to manipulate it." And when you do need it: "Usually, you will access refs from event handlers."

Two more tools belong on the map:
1. **To focus a field the moment it appears**, there is no click to run code in. Use the `autoFocus` prop. The reference: "If `true`, React will focus the element on mount." With a ref, this job takes an Effect, which Lesson 32 teaches.
2. **`document.getElementById`**, the plain JavaScript way from Lesson 01, searches the whole page. It does not belong to one copy of your component, and Principle 3 shows where that breaks.

```tree caption="Which tool fits which job when a component needs something on the page."
What the component needs on the page
- +Something the JSX can say [`value={text}` `{show && <p />}`] | Text, a class, a line shown or hidden | **State and JSX**, no ref
- +Focus, scroll, or measure after a click [`inputRef.current.focus`] | The browser keeps these, **not the JSX** | **A ref**, read in the **event handler**
- +Focus a field the moment it appears [`autoFocus`] | There is **no event** to run code in | **`autoFocus`**, or an Effect in Lesson 32
- !Find the element by its id [`document.getElementById`] | Searches **the whole page** | Finds **the wrong field** when a component appears twice
```

A senior developer also knows the four classic mistakes:
1. **`useRef` without the `ref` attribute.** React never fills the ref, so `current` stays `null`, and the click throws an error.
2. **`document.getElementById` in a component used twice.** The cursor lands in the wrong list.
3. **A ref read during rendering.** On the first render it is still `null`, and the page goes blank.
4. **A ref used to remove what React drew.** It works once, and then the next update by React crashes the page.

The rest of the lesson shows each mistake on a real guest list.

**PRINCIPLES:** Put `ref={inputRef}` on a tag, and React puts the real element into `inputRef.current`. Five principles follow:
1. **Principle 1: ref={inputRef} Puts the Element into inputRef.current.** Our code never writes it. Without the attribute, it stays `null`.
2. **Principle 2: Call focus on inputRef.current in the Handler.** The cursor goes back into the field after every click on Add.
3. **Principle 3: One Ref per Copy of the Component.** `document.getElementById` puts the cursor in the wrong list.
4. **Principle 4: inputRef.current Is null During the First Render.** A call to `focus` in the body of the component blanks the page.
5. **Principle 5: Never Change a DOM Node That React Manages.** A call to `remove` works once, then the next toggle crashes the page.

## PRINCIPLE | ref={inputRef}: React puts the real input element into inputRef.current

> [!PRINCIPLE]
> **Principle 1: ref={inputRef} Puts the Element into inputRef.current**
>
> *Create a ref with useRef(null) and pass it to a built-in tag as ref={inputRef}. After React creates the element, it puts it into inputRef.current, and when the element leaves the page, React sets current back to null.*
>
> useRef alone only gives you an object whose current is null. The ref attribute on the tag is what asks React to fill it. Our code never writes current here. Forget the attribute, and current stays null, so a call on it throws a TypeError.
>
> **DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> return <input ~ref={inputRef}~ />; // React puts this input element into inputRef.current
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> return ~<input />~; // **WRONG:** no ref attribute, so inputRef.current stays null forever
> ```

### The smallest example: Focus the input

The docs show the whole tool in one small component: a field, and a button that puts the cursor in it.

```jsx title="Form.jsx"
import { ~useRef~ } from 'react'; // The same Hook as in Lesson 30

export default function Form() {
  const inputRef = ~useRef(null)~; // On the first render, the object { current: null }

  function handleClick() {
    ~inputRef.current.focus();~ // current holds the real input element, so focus works on it
  }

  return (
    <>
      <input ~ref={inputRef}~ /> {/* React puts this input element into inputRef.current */}
      <button onClick={handleClick}>Focus the input</button>
    </>
  );
}
```

The user clicks the button. The cursor appears in the field, and the browser draws a ring around it:

```page width=text caption="After the user clicks Focus the input, the cursor is in the field."
form:
  field:  |  | good
  button: Focus the input
console: quiet
```

In the words of the docs, the attribute "tells React to **put this `<input>`'s DOM node into `inputRef.current`.**"

### When React fills current

No line of our code writes `inputRef.current`. React does it, in four steps:
1. **The first render** returns `<input ref={inputRef} />`. The element does not exist yet, so `current` is still `null`.
2. **In the commit**, React creates the `<input>` element and adds it to the page (Lesson 13).
3. **Right after that**, React sets `inputRef.current` to that element. Now a handler can call `focus` on it.
4. **When the element leaves the page**, React sets `current` back to `null`.

The reference: "After React creates the DOM node and puts it on the screen, React will set the `current` property of your ref object to that DOM node."

```tree dir=right caption="How the input element reaches inputRef.current without a line of our code."
How React fills `inputRef.current`
- +1. The first render [`<input ref={inputRef} />`] | The JSX names the ref | `current` is still **`null`**
- +2. The commit | React **creates the input element** | and adds it to the page
- +3. Right after | React sets **`inputRef.current` to that element** | A handler can now call `focus`
- +4. The element leaves the page | React sets **`current` back to `null`**
```

Log it in the handler, and you see the element itself:

```jsx title="Form.jsx" startLine="6"
function handleClick() {
  ~console.log(inputRef.current);~ // Logs the input element itself
  inputRef.current.focus();
}
```

```page width=text caption="After the click, the Console shows the input element that React put into inputRef.current."
form:
  field:  |  | good
  button: Focus the input
log: <input>
```

Something that can be tricky: the `ref` attribute is for React only. React reads it and never writes it into the DOM. So the Elements panel shows a plain `<input>`:

```dom caption="The Elements panel: the input carries no ref attribute, because React keeps ref out of the DOM."

+ <input> | note: No ref attribute in the DOM
  <button>Focus the input</button>
</div>
```

### Built-in tags only

The docs call the browser's own tags, such as `<input>` and `<div>`, built-in components. On a built-in component, the `ref` attribute fills the ref with that element. The reference: "Your ref will be filled with the DOM element for this node."

A component you write yourself is different. On `<GuestList ref={listRef} />`, the attribute does not reach the `<input>` element inside. The component has to pass it on, which Lesson 85 teaches.

### Forget the attribute, and current stays null

`useRef` and the `ref` attribute are two separate pieces. The element lands in the ref only when both are there:

```jsx title="Without the ref attribute, and with it"
<input /> {/* Without the attribute: inputRef.current stays null forever */}
<input ~ref={inputRef}~ /> {/* With the attribute: React puts this input element into inputRef.current */}
```

Both tags draw the same field on the page. But only the second one fills the ref. A developer who forgets the attribute still calls `focus` in the handler, and the click fails:

```page width=text caption="Without ref={inputRef} on the tag, the click leaves the field without the cursor and throws an error."
form:
  field:  |  | bad
  button: Focus the input
console: Uncaught TypeError: Cannot read properties of null (reading 'focus')
```

`inputRef.current` still holds `null`. And `null` has no `focus` method, so JavaScript throws a TypeError. The fix is the missing attribute.

## PRINCIPLE | focus in the event handler: the cursor goes back into the field

> [!PRINCIPLE]
> **Principle 2: Call focus on inputRef.current in the Handler**
>
> *In an event handler, ref.current is the real DOM node. Call the browser's own methods on it: focus to put the cursor in it, scrollIntoView to scroll to it, offsetWidth or getBoundingClientRect to measure it.*
>
> Focus, the scroll position, and sizes have no JSX form. State changes what React draws, but it never moves the cursor. The click on Add takes the focus away from the field, and only a call to focus brings it back.
>
> **DO THIS:**
> ```jsx
> function handleAdd() {
>   setText('');
>   ~inputRef.current.focus();~ // The cursor goes back into the field
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleAdd() {
>   ~setText('');~ // **WRONG:** empties the field, but the cursor stays outside it
> }
> ```

### Why the cursor leaves the field

No line of our code moves the cursor out. The click does:
1. While the user types John, the field has focus. The cursor is in it.
2. The user presses the mouse button on Add. The field loses focus, because the user clicked another element.
3. `handleAdd` runs. It adds John and empties the field. No line brings the cursor back.
4. The user types Mary, and the letters reach no field.

Browsers differ on where the focus goes after a click on a button. In every browser, it is no longer in the field.

### The fix: one line at the end of handleAdd

```jsx title="src/components/GuestList.jsx" startLine="10" good="13"
  function handleAdd() {
    setGuests([...guests, { id: nextId++, name: text }]);
    setText('');
    ~inputRef.current.focus();~ // Puts the cursor back in the field after every click on Add
  }
```

The user types John and clicks Add. John joins the list, the field is empty, and the cursor is already in it:

```page width=text caption="After the click on Add, John is in the list and the cursor is back in the empty field."
section: Lunch guests
form:
  field:  |  | good
  button: Add
line: John
console: quiet
```

The user types Mary at once, and clicks Add again:

```page width=text caption="The user typed Mary without clicking the field first, and clicked Add again."
section: Lunch guests

  field:  |  | good
  button: Add
line: John
line: Mary
console: quiet
```

Something that can be tricky: `focus` comes right after `setText`, and the setter only asks for a new render (Lesson 15). So why does `focus` work? Because the field has been on the page since the first commit. `inputRef.current` already holds it, and the cursor moves in at once. A moment later, React renders, and the field shows the empty text.

### Focus, scroll, measure: the same shape three times

The interview question names three jobs. With a ref, all three have the same shape: the element in `current`, then a method or a property from the browser.

```jsx title="Three jobs, one shape: the element in current, then the browser's own method"
inputRef.current.~focus()~; // Focus: puts the cursor in the field
imageRef.current.~scrollIntoView()~; // Scroll: scrolls until the image is visible
setWidth(chartRef.current.~offsetWidth~); // Measure: reads the width of the element in pixels
```

What is cool: this is the same `focus` that plain JavaScript calls on an element from `document.getElementById`. React only hands you the element. The docs: "You can then access this DOM node from your event handlers and use the built-in browser APIs defined on it."

### Scroll: scrollIntoView

The docs show a row of cat pictures that scrolls sideways. A button scrolls the first picture into view:

```jsx title="Scroll to the first picture, from the docs"
const firstCatRef = useRef(null);

function handleScrollToFirstCat() {
  firstCatRef.current.~scrollIntoView~({ behavior: 'smooth', block: 'nearest', inline: 'center' }); // Scrolls until this picture is in view
}

<img ~ref={firstCatRef}~ src="https://placecats.com/neo/300/200" alt="Neo" /> {/* React puts this img element into firstCatRef.current */}
```

MDN: `scrollIntoView` "scrolls the element's ancestor containers" until the element "is visible to the user." In plain words, the page and every scrolling area around the picture move until the picture is in view.

Called with no options, it scrolls just as well. The options only ask for a smooth motion, and choose where the picture ends up in the row.

### Measure: offsetWidth and getBoundingClientRect

A chart needs to know how wide its area is. The browser computes the width when it lays out the page, so our code reads it from the element:

```jsx title="Measure an element after a click"
const chartRef = useRef(null);
const [width, setWidth] = useState(0);

function handleMeasure() {
  ~setWidth(chartRef.current.offsetWidth);~ // Reads the width the browser laid out
}

return (
  <>
    <div ~ref={chartRef}~>Chart area</div> {/* React puts this div element into chartRef.current */}
    <button onClick={handleMeasure}>Measure</button>
    <p>Width: {width}</p>
  </>
);
```

MDN: `offsetWidth` "returns the layout width of an element as an integer". The number is in pixels, "including any borders, padding, and vertical scrollbars". For a hidden element, it is `0`.

The width goes into state, because the page shows it. Lesson 30 taught it: on the screen means state.

The browser has a second way to measure, `getBoundingClientRect`. Both count the padding and the border. The difference is what you get back:
1. **`offsetWidth`** is one whole number.
2. **`getBoundingClientRect`** returns an object with, in the words of MDN, "the size of an element and its position relative to the viewport". The viewport is the part of the page the user sees in the browser window.

### A change of state is not enough

A challenge in the docs makes the same point with a video player. It keeps `isPlaying` in state, and its button switches between Play and Pause.

The user clicks Play. The button now says Pause, but the video does not move. The docs: "toggling state is not enough".

State changed the button, which React draws. But playing belongs to the browser's `<video>` element. The fix is a ref on the `<video>` element. The handler then calls `play` or `pause` on it.

## PRINCIPLE | A ref: each copy of the component reaches its own input element

> [!PRINCIPLE]
> **Principle 3: One Ref per Copy of the Component**
>
> *document.getElementById returns the first element with that id on the whole page, so a component used twice finds the field of the first copy. A ref belongs to one copy, so each list reaches its own field.*
>
> With one list, an id and a ref give the same field. Render the component twice, and the page holds the same id twice. Then the handler of every copy finds the first field. React makes a separate ref for each copy, and fills it with that copy's element.
>
> **DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> ~inputRef.current.focus();~ // The field of this copy of GuestList
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> document.~getElementById('guest-input')~.focus(); // **WRONG:** the first field on the page, even from the Dinner list
> ```

Plain JavaScript already has a way to reach the field: give it an id, and search the page for it (Lesson 01). Both ways side by side:

```jsx title="Reach the field by its id, or through a ref"
<input ~id="guest-input"~ /> {/* The id: a name for the whole page */}
document.~getElementById('guest-input')~.focus(); // Searches the whole page for that name

<input ~ref={inputRef}~ /> {/* The ref: React puts this input element into this copy's ref */}
~inputRef.current~.focus(); // Reads the ref of this copy of GuestList
```

With one list on the page, both reach the exact same field. It looks the same, but it is NOT the same thing. The difference shows as soon as the page has two lists.

### Each copy gets its own ref

Back to the ref. Each copy of `GuestList` calls `useRef` and gets its own object, the same way each copy has its own state (Lesson 30). React fills each ref with that copy's `<input>` element.

So the Dinner Add button runs the Dinner `handleAdd`, which reads the Dinner `inputRef`. The cursor goes back into the Dinner field:

## PRINCIPLE | inputRef.current during rendering: it is still null on the first render

> [!PRINCIPLE]
> **Principle 4: inputRef.current Is null During the First Render**
>
> *React fills a ref in the commit, after the render. During the first render, ref.current is null, and during later renders it still holds the old element. Read DOM refs in event handlers, never during rendering.*
>
> The component returns its JSX first, and React creates the element later, in the commit. A call to focus in the body of the component finds null, throws a TypeError, and React removes the whole page. Skipping the call with ?. hides the crash, but the field still gets no focus. Use the event handler, autoFocus, or an Effect.
>
> **DO THIS:**
> ```jsx
> function handleAdd() {
>   ~inputRef.current.focus();~ // After the click: the field is on the page
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> ~inputRef.current.focus();~ // **WRONG:** during rendering, current is null and the page goes blank
> ```

The call to `focus` works in `handleAdd`. Put the exact same line in the body of the component, and the page goes blank:

```jsx title="The same call to focus in the body, and in the handler"
export default function GuestList({ title }) {
  const inputRef = useRef(null);
  ~inputRef.current.focus();~ // In the body: runs while React renders GuestList

  function handleAdd() {
    ~inputRef.current.focus();~ // In the handler: runs when the user clicks Add
  }
}
```

The difference is when each line runs:
1. **The line in the body** runs during rendering, before React has created the field.
2. **The line in the handler** runs when the user clicks, long after the commit.

### The user opens the page, and it is blank

A developer wants the cursor in the Lunch field as soon as the page opens. So the call goes at the top of the component:

```jsx title="src/components/GuestList.jsx" startLine="5" bad="9"
export default function GuestList({ title }) {
  const [text, setText] = useState('');
  const [guests, setGuests] = useState([]);
  const inputRef = useRef(null);
  ~inputRef.current.focus();~ // **WRONG:** runs during rendering, while current is still null
```

The user opens the page, and it is blank:

```page width=text caption="With the call to focus in the body of GuestList, the page is blank when it opens."

console: Uncaught TypeError: Cannot read properties of null (reading 'focus')
  warn: An error occurred in the <GuestList> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

Here is what happens:
1. React calls `GuestList` for the first render.
2. `useRef` returns the ref object. Its `current` is `null`.
3. The body reaches the call to `focus`. `inputRef.current` is still `null`.
4. JavaScript throws a `TypeError` before the component reaches its `return`.
5. React removes the whole page. The `Component` reference: "if your application throws an error during rendering, React will remove its UI from the screen."

```dom caption="The Elements panel after the error: the root div is empty."

```

The docs explain why the body is too early: "During the first render, the DOM nodes have not yet been created, so `ref.current` will be `null`. And during the rendering of updates, the DOM nodes haven't been updated yet. So it's too early to read them."

### Skip the call, and the field still gets no focus

To silence the error, a developer may skip the call while the ref is empty. Optional chaining does that. With `?.`, the call to `focus` runs only when the ref is filled:

```jsx title="src/components/GuestList.jsx" startLine="8" bad="9"
  const inputRef = useRef(null);
  inputRef.current~?.~focus(); // **WRONG:** no crash, but the first render still finds null, so nothing gets focus
```

The page comes back. But the cursor is still not in the field when the page opens. The first render finds `null`, so the call is skipped at the one moment it was meant for.

To focus a field when it appears, use one of two tools. The simpler one is the `autoFocus` prop:

```jsx title="Focus the field when it appears on the page"
<input ref={inputRef} ~autoFocus~ value={text} onChange={e => setText(e.target.value)} /> {/* React focuses the field on mount */}
```

The other one is an Effect, which Lesson 32 teaches. The docs: "If you want to do something with a ref, but there is no particular event to do it in, you might need an Effect."

Our page needs focus after a click, so the call stays in `handleAdd`.

## PRINCIPLE | remove on a node React manages: the next toggle crashes the page

> [!PRINCIPLE]
> **Principle 5: Never Change a DOM Node That React Manages**
>
> *Use a DOM ref for non-destructive actions: focus, scroll, and measure. Do not change, add, or remove DOM nodes that React manages, because React keeps updating them from the JSX and does not know about your change.*
>
> Removing an element through a ref looks the same as hiding it through state, for one click. But React still counts the element as on the page, so its next update crashes or leaves the page inconsistent. State decides what the page shows. A ref is for the few jobs state cannot say.
>
> **DO THIS:**
> ```jsx
> <button onClick={() => ~setShow(!show)~}>Toggle with setState</button> {/* React removes the line itself */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button onClick={() => ~ref.current.remove()~}>Remove from the DOM</button> {/* **WRONG:** React still counts the line as on the page */}
> ```

A ref hands you the real element. And the browser lets you do anything with it, even remove it. The docs show what happens then, with two buttons and one line of text:

```jsx title="Counter.jsx"
import { useState, useRef } from 'react';

export default function Counter() {
  const [show, setShow] = useState(true);
  const ref = useRef(null);

  return (
    <div>
      <button onClick={() => { ~setShow(!show);~ }}>Toggle with setState</button> {/* Changes state: React removes or adds the line */}
      <button onClick={() => { ~ref.current.remove();~ }}>Remove from the DOM</button> {/* Removes the line behind the back of React */}
      {show && <p ref={ref}>Hello world</p>}
    </div>
  );
}
```

```page width=text caption="The docs' example when the page opens: two buttons and the line Hello world."
line: [Toggle with setState] [Remove from the DOM]
line: Hello world
console: quiet
```

`remove` is a browser method that takes an element off the page. A click on either button makes Hello world disappear. It looks the same, but it is NOT the same thing. Only `setShow` tells React.

### The toggle that worked now crashes the page

The user clicks Toggle with setState a few times, and Hello world hides and shows each time. Then:
1. With Hello world on the page, the user clicks Remove from the DOM. `remove` takes the `<p>` element off the page.
2. Nobody tells React. `show` is still `true`. React still counts its `<p>` as on the page.
3. The user clicks Toggle with setState. `show` becomes `false`. React goes to take its `<p>` off the page.
4. The `<p>` is no longer there. The browser throws an error, and the page crashes.

```page width=full caption="After Remove from the DOM, the next click on Toggle with setState crashes the page."
blank
console: Uncaught NotFoundError: Failed to execute 'removeChild' on 'Node': The node to be removed is not a child of this node.
  warn: An error occurred in the <p> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The docs: "This is because you've changed the DOM, and React doesn't know how to continue managing it correctly." React updates the DOM it built from your JSX (Lesson 13). Your code changed that DOM, so the next update by React no longer matches what is there.

### Use refs only for non-destructive actions

The docs call the elements that React created from your JSX "DOM nodes managed by React". Their rule: "Avoid changing DOM nodes managed by React." Changing means changing their text, adding children to them, or removing them. The docs warn that it "can lead to inconsistent visual results or crashes like above."

Reading an element is safe. So is asking it to focus, scroll, or report its size. These change nothing that React built. The docs: "If you stick to non-destructive actions like focusing and scrolling, you shouldn't encounter any problems."

Our guest list already follows the rule. Its ref only calls `focus`. The list itself changes through `setGuests`.

The docs allow one exception: "You can safely modify parts of the DOM that React has *no reason* to update." For example, "if some `<div>` is always empty in the JSX, React won't have a reason to touch its children list."

Remember: state decides what the page shows. A ref only focuses, scrolls, and measures.

### How the code reaches the field, and what the user sees

| How the code reaches the field | What the user sees | Why |
| :--- | :--- | :--- |
| **No ref at all** | The cursor leaves the field after every click on Add | Focus belongs to the browser, and no state or JSX moves it |
| **`useRef` without the `ref` attribute** | The click throws a `TypeError`, and the cursor stays out | React never fills `current`, so it stays `null` |
| **`document.getElementById` with two lists** | Add in the Dinner list puts the cursor in the Lunch field | The search covers the whole page and returns the first element with that id |
| **`focus` in the body of the component** | The page is blank when it opens | During the first render, React has not created the element, so `current` is `null` |
| **`remove` on `ref.current`** | The next toggle crashes the page | React still counts the removed element as on the page |
| **`ref={inputRef}` and `focus` in `handleAdd`** | The cursor goes back into the field of its own list | React fills each copy's ref in the commit, and the handler runs after it |

One last time, the sentence of this lesson: **Put `ref={inputRef}` on a tag, and React puts the real element into `inputRef.current`. Then your event handler calls the browser's own methods on it, such as `focus`.**

## For the Interview

> **The Interview Question:** How do you reach a DOM node from React to focus it, scroll it, or measure it?

### How to Answer Clearly in 30 Seconds

"With a ref. React updates the DOM from the JSX. But JSX has no way to say 'put the cursor here', 'scroll to this', or 'how wide is this', so I need the real node. I create a ref with `useRef(null)` and pass it to a built-in tag as `ref={inputRef}`. After React creates the node in the commit, it puts the node into `inputRef.current`, and when the node is removed, it sets `current` back to `null`. Then, in an event handler, I call the browser's own APIs on it: `focus`, `scrollIntoView`, `offsetWidth`, or `getBoundingClientRect`. Three rules keep it right:
1. **A ref, not `document.getElementById`**: an id is searched on the whole page, so a component used twice finds the first copy's element, while a ref belongs to one copy.
2. **Never read a DOM ref during rendering**: on the first render it is still `null`, so I read it in event handlers, or in an Effect when there is no event.
3. **Only non-destructive actions**: focusing, scrolling, and measuring are safe; removing or changing a node that React manages can crash the next update."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"How do you focus an edit field the moment it appears, for example after a click on Edit?"**
   A call to `focus` in the click handler does not work there. The field does not exist yet when the handler runs, because the setter only asks for a render, so `inputRef.current` is still `null`. The simplest tool is the `autoFocus` prop: "If `true`, React will focus the element on mount." With a ref, the job takes an Effect, which Lesson 32 teaches. The docs: "If you want to do something with a ref, but there is no particular event to do it in, you might need an Effect." To make React update the DOM at once inside the handler, there is `flushSync`, which Lesson 65 teaches.
2. **"Can you pass a ref to your own component, such as `<MyInput ref={inputRef} />`?"**
   Only if the component takes `ref` and passes it on to a built-in tag inside. The docs: "By default, your own components don't expose refs to the DOM nodes inside them." Lesson 85 shows how a component passes `ref` on. With `useImperativeHandle`, which Lesson 50 teaches, the component can give the parent only a few methods, such as `focus`, instead of the whole node. The docs warn that "manually manipulating *another* component's DOM nodes can make your code fragile."
3. **"How do you scroll to a row you just added to a list, and why does it lag?"**
   One `useRef` per row does not work, because a Hook must be called at the top level of a component, never inside `map` (Lesson 38). The docs use a ref callback instead, a function in the `ref` attribute, which Lessons 86 and 99 teach. When the handler adds a row and scrolls in the same click, the new row is not in the DOM yet. The setter "does not immediately update the DOM". The docs: "This is why scrolling always 'lags behind' by one item." `flushSync`, from Lesson 65, makes React update the DOM before the scroll.

```tree dir=right caption="Interview comparison: reaching the field by its id vs. through a ref."
`document.getElementById` vs. a ref in an interview
- !By its id [`document.getElementById`] | Searches **the whole page** | With two copies, returns **the first element** every time
- +Through a ref [`ref={inputRef}` `inputRef.current`] | React fills it **in the commit**, **one per copy** | Each copy reaches **its own element**, in the event handler
```
