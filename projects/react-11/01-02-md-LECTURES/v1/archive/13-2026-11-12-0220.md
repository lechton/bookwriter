## How a Screen Update Reaches the Page

### The three steps of every React update

Before we build a multi-file project, look at what happens inside a tiny component when a user clicks a button to add a ticket:

```jsx title="A button click that updates count from 1 to 2"
function TicketCounter() {
  const [count, setCount] = ~useState(1)~; // 1. Starts with 1 ticket on the screen

  function handleAdd() {
    ~setCount(count + 1)~; // 2. Requests an update to 2 tickets when clicked
  }

  return <p className="count-text">Tickets: ~{count}~</p>; // 3. Describes what the paragraph should show
}
```

When you click the button in the browser, the text on the screen changes from `Tickets: 1` to `Tickets: 2` in the blink of an eye. Because that change happens so fast, two things are easy to misunderstand at first:
- **First, does `setCount` change the page right on that line?** It looks like it works that way at first, **but it does NOT touch the DOM on that line!** Calling `setCount` only places a request in React's queue. While `handleAdd` is still running, the paragraph on the page still holds `Tickets: 1`.
- **Second, does "rendering" mean drawing pixels or rebuilding the whole DOM?** In everyday web talk, people say "rendering" when the browser draws pixels on the screen. Many also assume re-rendering a component destroys and recreates all of its HTML tags. **It may sound the same, but in React they are NOT the same thing!**

Every screen update in React passes through **three separate steps in order**, followed by the browser drawing the screen at the end. The official React documentation compares these steps to a waiter and a chef working together in a restaurant kitchen, where the guest's table is the browser screen:
1. **Step 1 is Triggering a render**: In everyday English, to **trigger** something means to set a process in motion. In the restaurant, the waiter takes the guest's order at the table and walks the order slip into the kitchen. In React, a trigger is either the app starting up for the first time or a state setter queueing an update after a click.
2. **Step 2 is Rendering the components**: In the kitchen, the chef reads the order slip and prepares the dish. In React, **rendering** simply means React calling your component function in memory to calculate the JSX it returns. It does not touch the guest's table yet.
3. **Step 3 is Committing to the DOM**: In everyday English, to **commit** means to carry out a change for real. The waiter brings the finished dish out to the guest's table and updates only the plate that changed. Everything else on the table stays untouched.
4. **After Step 3 comes Browser Paint**: After React finishes updating the real DOM nodes, the browser draws the updated pixels onto the screen so you see the new number:

```tree dir=right caption="Every screen update in React passes through Trigger, Render, and Commit before the browser paints the screen."
How a screen update reaches the user's eyes
- +Step 1: Trigger [`root.render` or `setCount`] | Like the waiter **taking the order** to the kitchen | Queues a request for React to update the screen
- +Step 2: Render [React calls component functions] | Like the chef **preparing the dish** in the kitchen | Calculates the new JSX description in memory with **0 DOM changes**
- +Step 3: Commit [React updates the browser DOM] | Like the waiter **placing only the changed dish** on the table | Inserts all nodes on startup, or updates **only the DOM nodes that changed**
- +After Commit: Browser Paint [Browser draws pixels] | Like the guest **seeing the updated table** | Browser recalculates layout and paints the screen
```

### The only two ways to trigger a render

Nothing happens in Step 2 or Step 3 until Step 1 triggers a render. In all of React, there are **only two ways** a render is ever triggered:

```jsx title="The only two ways to trigger a render in React"
const root = createRoot(document.getElementById('root'));
~root.render(<App />)~; // Way 1: Initial render when the app first starts up

function handleAdd() {
  ~setCount(count + 1)~; // Way 2: Re-render when state updates in a mounted component
}
```

Every render you will ever see in a React app comes from one of those two triggers:
- **Way 1 is the initial render**: When the page first loads, your startup file calls `root.render` with `<App />`. That triggers the very first render of your application.
- **Way 2 is a re-render when state updates**: Once the component is already on the page, you call a `useState` setter function such as `setCount`. That call queues a re-render so React updates the screen with the new state.

```tree caption="The only two reasons a React component ever renders."
Two ways to trigger a render in React
- +Way 1: Initial render on startup [`createRoot` and `root.render`] | Runs **once** when the application first starts | Tells React to render `<App />` and mount the initial DOM tree
- +Way 2: Re-render on state update [`setCount` state setter] | Runs after the component is **already mounted** on the page | Queues a re-render for **after** the event handler finishes
```

### Why the lifecycle steps matter on a real page

Suppose we are building a ticket counter for a city box office page. The page has a main heading and a card for concert tickets. Inside the card sit the ticket count, a text box for a seat note, and a button to add a ticket.

When developers treat a state update as a single instant event instead of three separate steps, three practical questions immediately trip them up:
1. If you read the page text from the DOM on the line right after calling `setCount`, why does the DOM still show the old count?
2. When one component updates its state, does React re-run the whole app from the top, or only that component and its children?
3. When a component function runs again from top to bottom, why doesn't React destroy the input box inside it and erase what the buyer typed?

Walking through **Trigger**, **Render**, and **Commit** one step at a time answers all three questions.

### Three Principles of the Trigger, Render, and Commit Lifecycle

**PRINCIPLES:** Every update in React follows the same strict timeline from Step 1 to Step 3:
1. **Principle 1: Triggering a Render on Startup or State Update**: A render starts only when the app first mounts on startup or when a state setter queues a re-render in a mounted component. The state setter waits for the event handler to finish first. So reading the live DOM on the next line of the handler still sees the old page text.
2. **Principle 2: Rendering by Calling Component Functions in Memory**: Rendering means React calling your component functions in memory to calculate what the UI should look like. On startup, React calls the root component and every child down the tree. On a state update, React calls the component whose state changed and every child inside it. It skips parent components above it and touches zero DOM nodes.
3. **Principle 3: Committing Minimal DOM Changes Before Browser Paint**: After rendering finishes in memory, React commits the result to the browser DOM. On startup, it inserts every newly created DOM node. On a re-render, it updates only the DOM nodes that changed from the previous render. Unchanged elements such as an input box keep their typed text, and then the browser paints the screen.

Here is the complete overview of all three principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **Triggering a Render on Startup or State Update** | Reading a DOM node on the line right after calling a state setter inside a click handler returns the old DOM text. | Trigger a render on startup or with a state setter on update; store the next value in a plain variable if you need it inside the handler. |
| **Principle 2** | **Rendering by Calling Component Functions in Memory** | Reading the DOM inside a component body during render sees nothing on startup and old text on re-renders; interviewers ask which components run on a state update. | Keep rendering a pure calculation in memory; initial render calls the root component down the tree, while a state re-render calls the updated component and its children recursively. |
| **Principle 3** | **Committing Minimal DOM Changes Before Browser Paint** | Developers fear re-rendering will wipe out an input box, or confuse React rendering with browser painting. | Let React commit only the changed DOM nodes while preserving unchanged sibling nodes and their typed input text, after which the browser paints. |

## 1. Principle 1: Triggering a Render on Startup or State Update

### Why calling a state setter does not change the DOM on the very next line

Before we open our project files, look closely at these two lines inside a click handler when `count` starts at `1`:

```jsx title="Calling setCount and reading the DOM on the very next line"
function handleAdd() {
  ~setCount(count + 1)~; // 1. Queues a request to render with 2
  console.log(~document.querySelector('.count-text').textContent~); // 2. Still logs "Tickets: 1"!
}
```

**When you click the button, the number on the screen changes right away. It looks like `setCount` updates the DOM on that exact line, but it is NOT the same thing!**

Why does reading the paragraph text from the DOM on the very next line still print `Tickets: 1` instead of the new count?
- Think back to the waiter at the restaurant table. While a guest is still speaking to order another dish, that dish is **not** sitting on the table yet!
- Instead, the waiter clips the order slip into the kitchen **queue** and finishes listening to the guest first.
- In React, calling `setCount` is **Step 1: Trigger**. All it does is **queue a render** for React to perform after `handleAdd` finishes running. While `handleAdd` is still running on the next line, Step 2 and Step 3 have not started yet. So the browser DOM still holds `'Tickets: 1'`:

```tree dir=right caption="Why reading the DOM on the line after setCount still sees the old text."
What happens when `handleAdd` runs on click
- +1. Inside `handleAdd` [`setCount` with `count + 1`] | **Step 1: Trigger** queues a render for count `2` | The live DOM is **not touched yet** and still says **`"Tickets: 1"`**
- +2. Next line of `handleAdd` [`textContent` of `.count-text`] | Runs **before** `handleAdd` finishes | Reads the existing DOM node, which still holds **`"Tickets: 1"`**
- +3. After `handleAdd` finishes [Step 2 Render -> Step 3 Commit] | React calls `TicketCounter` with `2` and commits to the DOM | Only now does the DOM paragraph change to **`"Tickets: 2"`**
```

### Mistake: Reading the DOM right after calling `setCount`

Now suppose a developer wants to log the updated ticket text from the page as soon as the buyer clicks the button. Inside the click handler, the developer updates the ticket count and reads the paragraph text from the DOM on the very next line:

```jsx title="src/components/TicketCounter.jsx" startLine="6"
  function handleAdd() {
    setCount(count + 1);
    console.log(
      'DOM right after setCount:',
      ~document.querySelector('.count-text').textContent~ // **WRONG:** reads the DOM during Step 1 before React renders or commits!
    );
  }
```

When you click `Add ticket` once in the browser, look at what happens on the screen versus in the Console:
1. **On the page**: The paragraph updates to `Tickets: 2`.
2. **In the Console panel**: The log still prints `Tickets: 1`!

```devconsole
x DOM right after setCount: Tickets: 1
```

Look closely at those two lines inside `handleAdd`. Nowhere inside `setCount` is there a call that rewrites the DOM paragraph while `handleAdd` is still running! Why didn't the DOM change before `console.log` ran?

Follow what JavaScript and React do in order when you click `Add ticket`:
1. You click the button, and React calls `handleAdd`.
2. Inside the handler, `setCount` runs with `1 + 1`. That call is **Step 1: Trigger**. It places the new state value `2` into React's update queue and returns right away without touching the DOM.
3. The very next line of `handleAdd` runs and reads the `.count-text` paragraph from the DOM. Because React has not run Step 2 or Step 3 yet, the paragraph in the DOM still holds `'Tickets: 1'`.
4. Now `handleAdd` reaches its closing brace and finishes running.
5. Only after `handleAdd` finishes does React run **Step 2: Render** and **Step 3: Commit**. That is when the DOM text changes to `'Tickets: 2'`.

### Saving the next value in a variable inside the handler

Sometimes your click handler needs to use or log the new ticket count right away. Store the new number in a plain variable first, and pass that variable both to the state setter and to your log:

```jsx title="src/components/TicketCounter.jsx" startLine="6"
  function handleAdd() {
    const ~nextCount = count + 1~; // 1. Compute the next ticket count in a plain variable first
    setCount(~nextCount~); // 2. Queue the re-render with nextCount
    console.log(
      'Trigger: handleAdd read DOM right after setCount:',
      document.querySelector('.count-text').textContent
    );
    console.log('Trigger: handleAdd nextCount variable:', ~nextCount~); // 3. Uses nextCount right away inside handleAdd
  }
```

**What happens if you call `setCount` with the exact same value that is already in state?** Suppose the ticket count is already two, and a handler passes `2` to `setCount` again. React compares the new value with the current state in memory using `Object.is`. When both values are the same, React sees that nothing changed and skips re-rendering the component and its children.

```tree caption="What happens in Step 1 when you call setCount with a new value vs. the exact same value."
Calling `setCount` inside an event handler
- +New state value [`setCount` with `count + 1`] | `Object.is` sees a **different value** | **Queues a re-render** for after the event handler finishes
- +Same state value [`setCount` with current `count`] | `Object.is` sees the **exact same value** | React **bails out** and skips re-rendering the subtree and touching the DOM
```

> [!PRINCIPLE]
> **Principle 1: Triggering a Render on Startup or State Update**
>
> *A component renders only when `root.render` starts the app or when a state setter queues a re-render for after the event handler finishes.*
>
> When you call `setCount` inside a click handler, you might think React rewrites the page on that exact line. It does not! Calling `setCount` is only Step 1, the Trigger phase. It hands a render request to React's queue and lets your event handler finish first. If you read a DOM element on the line right after `setCount`, the DOM still holds the old text from before the click. When you need the new number inside the handler, save `count + 1` in a `nextCount` variable first and use that variable.
>
> **DO THIS:**
> ```jsx
> function handleAdd() {
>   const ~nextCount = count + 1~; // 1. Calculate the new count first
>   ~setCount(nextCount)~; // 2. Queue the re-render for after handleAdd finishes
>   console.log('New count:', ~nextCount~); // 3. Logs 2 accurately inside the handler
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleAdd() {
>   setCount(count + 1);
>   console.log(~document.querySelector('.count-text').textContent~); // **WRONG:** DOM has not updated yet and still logs "Tickets: 1"!
> }
> ```

## 2. Principle 2: Rendering by Calling Component Functions in Memory

### Which components React calls on the initial render vs. on a re-render

Once Step 1 triggers an update, React moves to **Step 2: Render**. What does "rendering" actually mean in React?

Look at this small three-level component tree where the root component renders the ticket counter, and the ticket counter renders the order summary:

```jsx title="A three-level component tree: App -> TicketCounter -> OrderSummary"
function ~App~() { // 1. Top-level root component
  return <main><h1>City Box Office</h1><TicketCounter /></main>;
}

function ~TicketCounter~() { // 2. Middle component that owns the count state
  const [count, setCount] = useState(1);
  return (
    <section>
      <OrderSummary count={count} />
      <button onClick={() => setCount(count + 1)}>Add ticket</button>
    </section>
  );
}

function ~OrderSummary~({ count }) { // 3. Child component returned by TicketCounter
  return <p className="count-text">Tickets: {count}</p>;
}
```

**"Rendering" in React means one very specific thing: React calling your component functions to ask what JSX markup they return!**

When developers first trace Step 2, two questions immediately come up:
- **First, which component functions does React call when `TicketCounter` updates its state?** You might think React re-runs the whole app from `App` down, or that it calls only `TicketCounter` and stops there. **It may seem like one of those must happen, but it is NOT the same thing!**
  - On the **initial render**, React starts at the very top of the tree. It calls `App` first, then `TicketCounter`. Finally, it calls the child component `OrderSummary`.
  - On a **re-render**, React starts at the component whose state updated, which is `TicketCounter`. It **skips `App` above it** and calls `TicketCounter`. Then it sees `<OrderSummary count={count} />` in the returned JSX and **recursively** calls `OrderSummary`.
- **Second, does Step 2 change the DOM while those functions are running?** No! While the counter and summary components run with the new count of `2`, the live DOM on the page **still says `Tickets: 1`**. Step 2 only calculates JSX in memory.

Look at the two words that describe how Step 2 works:
- **What does "recursive" mean?** In everyday English, a step is **recursive** when it repeats the exact same rule on whatever is inside it. When the ticket counter returns `<OrderSummary />`, React calls `OrderSummary` next. If `OrderSummary` returned another child component, React would call that child too. It continues down the tree until only built-in HTML tags remain.
- **What is a "pure calculation"?** A calculation is **pure** when it takes inputs, such as props and state, and computes a result in memory without changing anything outside the function. Step 2 only computes React element objects in memory and touches **zero DOM nodes**:

```tree caption="Which component functions React calls in Step 2 on the initial render versus on a state re-render."
Step 2: Which component functions does React call?
- +Initial render [`root.render` on startup] | Starts at the **root component `App`** | Calls **`App` -> `TicketCounter` -> `OrderSummary`** from top to bottom
- +State re-render [`setCount` inside `TicketCounter`] | Starts at the **component whose state updated** | **Skips `App`**, calls **`TicketCounter`**, and recursively calls its child **`OrderSummary`**
```

### Adding `OrderSummary` as a child component inside `TicketCounter`

Now let us move the ticket count paragraph into its own child component so our page has three levels. We also add a log at the top of each component so we can watch Step 2 in the Console.

First, we create the order summary file, which logs when it renders and returns the ticket count paragraph:

```jsx title="src/components/OrderSummary.jsx" startLine="1"
export default function ~OrderSummary~({ count }) { // 1. Receives { count } from TicketCounter
  ~console.log('Render: OrderSummary count =', count)~; // 2. Logs whenever React calls OrderSummary
  return <p className="count-text">Tickets: {count}</p>;
}
```

Second, in our main application file, we add a log at the top of the root component so we can see whenever React calls it:

```jsx title="src/App.jsx" startLine="1"

export default function ~App~() { // Root component at the top of the tree
  ~console.log('Render: App')~; // Logs only when React calls App()
  return (
    <main>
      <h1>City Box Office</h1>
      <TicketCounter />
    </main>
  );
}
```

Third, in the ticket counter file, we import the order summary component and place its tag inside the ticket box:

```jsx title="src/components/TicketCounter.jsx" startLine="1"

import ~OrderSummary~ from './OrderSummary.jsx'; // 1. Import the child component

      </button>

Look closely at those files. Nowhere in the ticket counter file did we call `OrderSummary` with parentheses. And nowhere did we write code telling React to skip `App` when the button is clicked! How does React know which functions to call?

Follow what React does during Step 2 in both situations:
1. **On initial page load**, `root.render` tells React to start at the root. React calls `App` and sees `<TicketCounter />` in its returned JSX. Next, React calls `TicketCounter` and sees `<OrderSummary count={1} />`. Finally, React calls `OrderSummary` with one ticket.
2. **When you click the button**, `setCount` ran inside `TicketCounter`, so React starts there. In Step 2, React skips `App` completely and calls `TicketCounter` first. Because the counter returns `<OrderSummary count={2} />`, React then calls `OrderSummary` with two tickets.

  - +`OrderSummary` [Called 2nd with `count = 2`] | Returns `<p>Tickets: 2</p>`
```
On state update, React skips `App` above the counter. It calls `TicketCounter` and its child `OrderSummary` in memory, and updates the DOM afterward in Step 3.
:::
:::

Because Step 2 only calculates JSX in memory, your component body must always be a **pure calculation**. For the same props and state, it simply returns JSX without reading or changing the DOM. Calling child components like `OrderSummary` in memory is also very fast, so you do not need to worry when children re-render with their parent.

> [!PRINCIPLE]
> **Principle 2: Rendering by Calling Component Functions in Memory**
>
> *In the Render phase, React calls your component functions in memory: from `App` down on startup, and from the updated component down its children on a re-render.*
>
> Never confuse React rendering with changing the browser DOM. During Step 2, React is only calling your JavaScript functions in memory to ask what JSX elements they return. On the first load, React starts at `App` and calls every component down the tree, while the `#root` div in the DOM is still completely empty. When `TicketCounter` updates its state, React skips `App` above it. It calls `TicketCounter` and recursively calls its child `OrderSummary`. Throughout the entire Render phase, the live browser DOM still shows the old screen until Step 3 commits the new result.
>
> **DO THIS:**
> ```jsx
> export default function TicketCounter() {
>   const [count, setCount] = useState(1);
>   return (
>     <section className="ticket-box">
>       <h2>Concert Tickets</h2>
>       ~<OrderSummary count={count} />~ {/* Pure calculation: passes count as a prop to calculate JSX */}
>     </section>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function TicketCounter() {
>   const [count, setCount] = useState(1);
>   const currentText = ~document.querySelector('.count-text').textContent~; // **WRONG:** null on initial render and stale on re-render!
>   return <section className="ticket-box">{currentText}</section>;
> }
> ```

## 3. Principle 3: Committing Minimal DOM Changes Before Browser Paint

### Why re-rendering a component does NOT destroy its unchanged DOM nodes

Now we reach **Step 3: Commit**, followed by **Browser Paint**.

Suppose we add a seat note `<input>` box right inside `TicketCounter` between the order summary and the button:

```jsx title="TicketCounter returning four elements on every render"
  return (
    <section className="ticket-box">
      ~<h2>Concert Tickets</h2>~ {/* 1. Heading */}
      ~<OrderSummary count={count} />~ {/* 2. Paragraph whose text changes from 1 to 2 */}
      ~<input className="note-input" placeholder="Seat note" />~ {/* 3. Input where the buyer typed "Window seat" */}
      ~<button className="add-btn" onClick={handleAdd}>Add ticket</button>~ {/* 4. Button */}
    </section>
  );
```

On every click, `TicketCounter` runs from top to bottom and returns all four tags again. **It may look like returning `<input />` again will destroy the old input box and wipe out what the buyer typed, but it is NOT the same thing! Re-rendering a component in memory does NOT rebuild its unchanged DOM nodes.**

Why does `'Window seat'` stay safe inside the input box even when `TicketCounter` re-renders ten times in a row?
- Remember that returning the `<input>` tag in Step 2 only creates a lightweight JavaScript object in memory. It does not create a new browser DOM node!
- When React enters **Step 3: Commit**, what it does depends on whether this is the **initial render** or a **re-render**:
  1. **On the initial render**, the `#root` container on the page is empty. React creates the real browser DOM nodes for every element in the tree and puts them into `#root` using the browser's **`appendChild`** DOM method.
  2. **On a re-render**, React compares the new JSX descriptions from Step 2 against the previous render. It sees that the section, the heading, the input box, and the button have not changed at all! Only the number inside `<p class="count-text">` changed from one to two.
  3. So React commits **only that single text change** to the real DOM and leaves the existing `<input>` DOM node and its `'Window seat'` text untouched.
- **What happens after Step 3 finishes?** Once React commits that single text change to the DOM, the browser recalculates the layout and draws the new pixels on the screen. That final step by the browser is called **Browser Paint**, which CSS tools sometimes call "browser rendering":

```tree caption="How Step 3 Commit handles the initial render vs. a re-render, and how both differ from Browser Paint."
Step 3: Commit to the DOM and Browser Paint
- +Initial Commit [After Trigger 1 on startup] | Uses the DOM **`appendChild`** API | Inserts all newly created DOM nodes into `#root`
- +Re-Render Commit [After Trigger 2 on state update] | Compares previous and next render output | Updates **only changed DOM nodes** and keeps `<input>` and `"Window seat"` untouched
- +Browser Paint [After React finishes Commit] | Performed by the **browser**, not React | Draws the updated DOM pixels onto the screen
```

### Adding a seat note input box inside `TicketCounter`

When developers think re-rendering will erase the buyer's note, they sometimes try to avoid React state updates. Instead, they reach into the DOM and change the paragraph text by hand:

```jsx title="Mistake: Fighting React with manual DOM mutation out of fear of re-rendering"
  function handleAddWrong() {
    ~document.querySelector('.count-text').textContent = 'Tickets: 2'~; // **WRONG:** bypasses React's Trigger-Render-Commit lifecycle!
  }
```

You never need to bypass React! Let us place the seat note input box directly inside the ticket counter file and let the state setter re-render the component normally:

```jsx title="src/components/TicketCounter.jsx" startLine="1"
import { useState } from 'react';
import OrderSummary from './OrderSummary.jsx';

export default function TicketCounter() {
  const [count, setCount] = useState(1);

  function handleAdd() {
    const nextCount = count + 1;
    setCount(nextCount);
  }

  return (
    <section className="ticket-box">
      <h2>Concert Tickets</h2>
      <OrderSummary count={count} />
      ~<input className="note-input" placeholder="Seat note" />~ {/* Keeps its DOM node and typed text across re-renders! */}
      <button className="add-btn" onClick={handleAdd}>
        Add ticket
      </button>
    </section>
  );
}
```

Look closely at the input line in the code above. We did not attach a state variable to the input box, and we wrote no special code to protect it when `count` changes! Why doesn't re-rendering `TicketCounter` erase what the buyer types?

Follow what happens in the browser when the buyer types `'Window seat'` into the input box and then clicks the button twice:

4. Because nothing about `<input>` changed in the JSX, React **does not touch the `<input>` DOM node at all**. Every element on the page, including the `<section>` card and the `<input>` box, is still the **exact same DOM node in memory** as before. Only the text inside `<p class="count-text">` changed to `'Tickets: 3'`:

> [!PRINCIPLE]
> **Principle 3: Committing Minimal DOM Changes Before Browser Paint**
>
> *In the Commit phase, React inserts all nodes with `appendChild` on startup, and on a re-render updates only the changed DOM nodes before the browser paints.*
>
> When your component function runs again from top to bottom, it returns all of its JSX tags again. You might worry that React will tear down the existing HTML elements on the page and rebuild them from scratch. That never happens! | Lifecycle Step | The Common Misconception | The React Rule |
| :--- | :--- | :--- |
| **Step 1: Trigger** | Calling `setCount` immediately rewrites the DOM before the next line of the event handler runs | `setCount` only queues a render request; the event handler finishes against the existing DOM first |
| **Step 1: Same-value setter call** | Calling `setCount` with the current `count` value always runs a full subtree re-render and DOM update | React compares the next value with `Object.is` and skips re-rendering the component and its children when the value is unchanged |
| **Step 2: Render** | Rendering means drawing pixels on screen, or a state update in a child re-runs `App` at the top | Rendering is React calling component functions in memory: from `App` down on startup, and from the updated component down its children on re-render |
| **Step 3: Commit** | Re-rendering a component destroys and recreates all of its HTML DOM nodes and wipes `<input>` text | Initial commit inserts nodes with `appendChild`; re-render commit mutates only the DOM nodes that changed and keeps unchanged nodes intact |
| **After Commit: Browser Paint** | React rendering and browser rendering are the same step | Browser painting happens after React finishes committing DOM changes, when the browser draws the pixels on screen |

## For the Interview

> **The Interview Question:** What are the trigger, render, and commit phases of the React lifecycle, and what runs in each?

### How to Answer Clearly in 30 Seconds

"Every screen update in React flows through three phases in order: **Trigger**, **Render**, and **Commit**, followed by **Browser Paint** at the end.
1. **Step 1 is Trigger**: Only two things trigger a render. The **initial render** runs when the app starts via `createRoot` and `root.render`. A **re-render** runs when a mounted component calls a `useState` setter like `setCount`. Calling `setCount` only queues a render request for after the event handler finishes. It does not mutate the DOM on that line.
2. **Step 2 is Render**: Rendering in React means React calling your component functions to compute JSX elements in memory. On the initial render, React calls the root component `App` and every nested child down the tree. On a state-triggered re-render, React starts at the component whose state updated and recursively calls the child components it returns, skipping unaffected parent components above it. Rendering is a pure calculation in memory that touches zero DOM nodes.
3. **Step 3 is Commit, followed by Browser Paint**: In the Commit phase, React applies the result to the real browser DOM. On the initial render, it inserts all newly created DOM nodes into the container using `appendChild`. On a re-render, it compares the new render output with the previous render output and mutates only the specific DOM nodes or attributes that actually changed. Unchanged sibling elements like an `<input>` and its typed text stay untouched. Only after Commit finishes does the browser repaint the screen in **Browser Paint**."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"If you call `setCount` in a click handler and read the DOM on the next line, what does it return? What if you pass the same value?"**
   Reading the DOM on the next line of the click handler returns the **old DOM text**, such as `'Tickets: 1'`. That happens because calling `setCount` is only **Step 1: Trigger**. It queues a render request in React and returns immediately without touching the DOM. React waits for the event handler to finish before running Step 2 and Step 3. If you call `setCount` with the exact same value that is already in state, React compares the two values with `Object.is`. Because they match, React bails out and skips re-rendering the component and its children.
2. **"When a child component like `TicketCounter` calls `setCount`, does React re-render `App` above it, or only `TicketCounter`?"**
   Neither `App` nor *only* `TicketCounter`. React starts the re-render at the component whose state updated, so `App` above it is **not** called. React calls `TicketCounter` and looks at the JSX elements it returns. Then it **recursively** calls any child components inside that returned JSX, such as `OrderSummary`, until only built-in HTML tags remain.
3. **"Is 'React rendering' the same thing as 'browser rendering', and why doesn't re-rendering `TicketCounter` wipe out text typed into an `<input>` inside it?"**
   No. **React rendering** is Step 2, where React calls your component functions in JavaScript to calculate JSX objects in memory. **Browser rendering**, or **Browser Paint**, happens after Step 3, when the browser draws pixels on the screen after React commits changes to the DOM. Re-rendering `TicketCounter` does not wipe out an `<input>` inside it because Step 2 only creates a lightweight JavaScript object in memory. In Step 3, React compares the previous and next element trees and sees that `<input />` is at the same spot with the same attributes. So React leaves the existing `<input>` DOM node and its typed text untouched, and updates only the text node that changed.

```tree dir=right caption="Interview comparison: what happens in Trigger, Render, Commit, and Browser Paint."
The four stages of a React screen update in an interview
- +1. Trigger [`root.render` or `setCount`] | **Initial mount** or **state setter** | Queues a render; reading the DOM on the next line still sees the **old DOM**
- +2. Render [React calls component functions] | **Pure calculation** in memory with **0 DOM changes** | Calls `App` down on mount; calls **updated component + its children** on re-render
- +3. Commit [React updates the DOM] | `appendChild` on mount; **minimal DOM diff** on re-render | Mutates **only changed nodes** and preserves unchanged `<input>` nodes
- +4. Browser Paint [Browser draws pixels] | Distinct from **React rendering** | Browser repaints the screen **after** React finishes Commit
```
