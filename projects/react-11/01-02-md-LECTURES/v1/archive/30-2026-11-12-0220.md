# Lecture 30: Keeping a Value Between Renders with useRef
> INTERVIEW QUESTION | ❱ CORE | How do you keep a value between renders without triggering a re-render?

---

## How a Component Remembers a Number It Never Shows

### The number the Stop button needs

Think of the stopwatch on your phone. You tap Start, and the seconds count up. You tap Stop, and the number stands still. Behind those two taps, the Stop tap has to find the timer that the Start tap started.

In the browser, a repeating timer starts with `setInterval`. You know `setTimeout` from Lesson 15, and `setInterval` takes the same two things: a function and a delay in milliseconds. They differ in one way: `setTimeout` calls the function once, while `setInterval` calls it again and again, every time the delay passes. To stop the timer, our code hands its number to `clearInterval`. In the smallest example, the repeated function is called `tick`:

```js title="Starting and stopping a repeating timer in the browser"
const id = ~setInterval~(tick, 1000); // Calls tick every 1000 milliseconds and returns a number for this interval
~clearInterval~(id); // Stops the interval with that number: tick is never called again
```

The browser gives back that number at the moment the interval starts. MDN calls it the **interval ID**. It is the only handle our code has on the interval. Without it, no code can stop the timer. And when `clearInterval` gets a number the browser does not know, or no number at all, it simply does nothing.

Now put the stopwatch inside a React component. The click on Start gets the interval ID. The click on Stop comes later, and in between, the component renders again once a second to show the new number. So the interval ID has to wait somewhere, through all those renders, until the user clicks Stop.

### A ref keeps the number between renders

React's answer is a **ref**, created with the Hook `useRef`. Three lines do the whole job:

```jsx title="Keeping the interval ID in a ref"
const intervalRef = ~useRef(null)~; // 1. In the component: creates the ref, an object that starts as { current: null }
intervalRef.current = ~setInterval(tick, 1000)~; // 2. In the Start handler: puts the new interval ID inside the ref
~clearInterval(intervalRef.current)~; // 3. In the Stop handler: reads the same ID back and stops the interval
```

A ref is an object with one property, `current`. React keeps the ref for the component through every render, so the Stop handler finds the ID, however many renders came between the two clicks.

### A ref and state: kept the same way, with one difference

A ref and state have one thing in common: React keeps both between renders. The docs say it plainly: "Like state, refs are retained by React between re-renders." The one difference comes in the next line of the docs: "However, setting state re-renders a component. Changing a ref does not!"

```jsx title="A number kept in state, and a number kept in a ref"
const [count, setCount] = ~useState(0)~; // Kept between renders: setCount(1) asks React to render again
const countRef = ~useRef(0)~; // Kept between renders: countRef.current = 1 asks React for nothing
```

It may look the same, or work the same at first, but it is NOT the same thing! Both remember a number between renders, and on the first render both hold zero. But only the setter of state makes React render the component again, so only a number in state ever changes the page. The docs put both facts into one short phrase: a ref is like "a regular state variable without a setter."

### Why it is called a ref

Ref is short for reference. The docs' page about it is called "Referencing Values with Refs". A ref keeps a reference to a value, so that later code, such as the Stop handler, can find the value again. The docs also give the ref an everyday image: "It's like a secret pocket of your component that React doesn't track." Our code can put a value into a ref during one click and take it out during a later click, and React never looks at it, so putting a value there never causes a render.

```tree caption="State and a ref both keep a value between renders; only the state setter makes React render again."
Two places React keeps a value between renders
- +State [`useState`] | Kept by React **between renders** | The setter **asks React to render again**, so the page shows the new value
- +A ref [`useRef` `intervalRef.current`] | Kept by React **between renders** | Changing `current` **asks React for nothing**, so the page does not change
```

### Four places a component can keep a value

A ref is not the only place to put a value. The `useRef` reference in the docs compares four places, and each one fits a different job:

```jsx title="Four places a component file can keep a value"
let ~outsideId~ = null; // Outside the component: created once when the file loads, shared by every copy

function Stopwatch() {
  let ~localId~ = null; // A local variable: created again on every render
  const [seconds, setSeconds] = ~useState(0)~; // State: kept between renders, and the setter renders again
  const intervalRef = ~useRef(null)~; // A ref: kept between renders, renders nothing, one for each copy
}
```

Here is the job each place fits:
1. **A local variable**, such as `localId`, fits a value the component computes fresh during each render, as in Lesson 22. It does not survive a re-render, because, in the words of the docs, regular variables "reset on every render".
2. **A variable outside the component**, such as `outsideId` at the top of the file, fits a value that never changes while the page runs, such as `initialCart` in Lesson 27. It survives every render, but it is one variable for the whole file, and the docs call such variables "shared".
3. **State**, from `useState`, fits information the page shows. Changing it renders the component again.
4. **A ref**, from `useRef`, fits information that only event handlers need, and whose change needs no new render, such as an interval ID. The docs call refs an "escape hatch" that "you won't need often."

An escape hatch is a small door in a ship or a plane, for the rare moment when the main door does not fit the job. In React, almost every value goes through state and rendering. A ref lets a value step outside that path, for things React does not draw, such as a browser timer.

```tree caption="The four places a component can keep a value, and the job each one fits."
Where a component can keep a value
- +A local variable [`let localId`] | Created again on **every render** | Fits a value **computed fresh** in each render
- +A variable outside the component [`let outsideId` at the top of the file] | Survives renders, but is **shared by every copy** | Fits a value that **never changes**
- +State [`useState`] | Kept between renders; the setter **renders again** | Fits information **the page shows**
- +A ref [`useRef`] | Kept between renders, **renders nothing**, one per copy | Fits information **only event handlers need**
```

### What is at stake

When the interval ID sits in the wrong place, the user sees it at once:
1. With a local variable, the user clicks Stop, and the stopwatch keeps counting.
2. With one variable outside the component, the user runs two stopwatches, and a click on one of them stops the other.
3. With the shown number in a ref instead of state, the user clicks Start, and the line stays at zero.

Readers usually go wrong in three ways. First, they think a local variable inside the component keeps its value between renders. Second, they think every value a component remembers must be state, so the component renders again for a number nobody sees. Third, once they learn refs, they keep a shown number in a ref because the ref changes at once, and the page stops updating.

### Our example page: a stopwatch

Our page is a small stopwatch. It shows one line, the number of seconds, and two buttons, Start and Stop:

```page width=text caption="The stopwatch when the page opens."
line: Seconds: 0
line: [Start] [Stop]
console: quiet
```

Here is what the user does, and what each click should change:
1. The user clicks Start. The line counts up once a second: one, two, three.
2. The user clicks Stop. The line stays on its number, such as three.
3. The user clicks Start again. The count goes on from that number, to four.

At the start of the lesson, the `Stopwatch` component can start the interval, but it cannot stop it:

```jsx title="src/components/Stopwatch.jsx"
import { useState } from 'react';

export default function Stopwatch() {
  const [seconds, setSeconds] = useState(0);

  function handleStart() {
    ~setInterval~(() => { // Starts the interval and throws away the interval ID it returns
      setSeconds(s => s + 1);
    }, 1000);
  }

  return (
    <section>
      <p>Seconds: {seconds}</p>
      <button onClick={handleStart}>Start</button>
      ~<button>Stop</button>~ {/* No handler yet: there is no interval ID to give clearInterval */}
    </section>
  );
}
```

The interval uses the updater function from Lesson 16. Without it, the interval would keep the `seconds` of the render in which the user clicked Start, as Lesson 15 showed, and the line would stop at one.

The number on the page lives in state, in `seconds`, because the page shows it. The interval ID is never shown. It only has to travel from the Start click to the Stop click, and this lesson finds the right place for it.

`App` renders one stopwatch:

```jsx title="src/App.jsx"
import Stopwatch from './components/Stopwatch.jsx';

export default function App() {
  return (

  );
}
```

The entry file, `main.jsx`, mounts `App` inside `<StrictMode>`, as in Lesson 07. Here is how the files sit in the project:

### Five Principles of Keeping a Value Between Renders

**PRINCIPLES:** A ref keeps a value between renders, as state does, and changing it renders nothing. Each principle below puts the interval ID in one place and shows what the user sees:
1. **Principle 1: useRef Returns the Same Object on Every Render**: `useRef` gives the component an object with one property, `current`. React hands back the same object on every render, and our code changes `current` without a new render.
2. **Principle 2: Stop Fails When intervalId Is a let**: A local variable is created again on every render, so the interval ID from the Start click is gone by the time the user clicks Stop.
3. **Principle 3: useState for the Interval ID Renders the Stopwatch Again**: State also makes Stop work, but every change of the ID renders the component again for a value the page never shows.
4. **Principle 4: A Shared intervalId Stops the Wrong Stopwatch**: A variable outside the component survives renders, but every stopwatch on the page uses the same one.
5. **Principle 5: secondsRef.current on the Page Stays at 0**: A value the page shows must be state, because changing a ref does not render, and our code does not read a ref during rendering.

Here is the complete map of those five principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **useRef Returns the Same Object on Every Render** | Interviewers ask what `useRef` returns and why the initial value does not reset the ref; a second click on Start without clearing the old interval makes the stopwatch count twice as fast. | `useRef` returns an object whose `current` holds the initial value on the first render, and the same object on every later render; change `current` in event handlers. |
| **Principle 2** | **Stop Fails When intervalId Is a let** | The stopwatch keeps counting after Stop with zero Console errors, and a quick test that clicks Stop within the first second hides the bug. | Keep a value that must survive a re-render in a ref, never in a local variable of the component. |
| **Principle 3** | **useState for the Interval ID Renders the Stopwatch Again** | Keeping a value the page never shows in state renders the component again on every change, and a log right after the setter still shows the old value. | Keep information used for rendering in state, and information only event handlers need in a ref. |
| **Principle 4** | **A Shared intervalId Stops the Wrong Stopwatch** | A variable outside the component works with one copy and breaks as soon as the component appears twice on the page. | A ref belongs to one copy of the component, so each copy keeps its own interval ID. |
| **Principle 5** | **secondsRef.current on the Page Stays at 0** | A shown value kept in a ref leaves the page frozen with zero Console errors, and the lint rule and the React Compiler flag reading a ref during rendering. | Never read or write `ref.current` during rendering, except to fill an empty ref once; a value the page shows belongs in state. |

## 1. Principle 1: useRef Returns the Same Object on Every Render

### The smallest ref: a counter that never renders again

The docs open their page about refs with a click counter. The count lives in a ref, and the browser's pop-up shows it:

```jsx title="Counting clicks in a ref"
import { ~useRef~ } from 'react'; // useRef is a Hook from React, like useState

export default function Counter() {
  const ref = ~useRef(0)~; // On the first render, React creates the object { current: 0 }

  function handleClick() {
    ~ref.current = ref.current + 1~; // Changes current at once, and React is not told
    alert('You clicked ' + ref.current + ' times!');
  }

  return <button onClick={handleClick}>Click me!</button>;
}
```

```page width=text caption="The counter page. The button keeps the same text after every click by the user."
line: [Click me!]
console: quiet
```

When the user clicks the button, the pop-up says "You clicked 1 times!". After the next click, it says "You clicked 2 times!", and then "You clicked 3 times!". The button itself never changes, because, as the docs say, "the component doesn't re-render with every increment."

`useRef` takes one argument, the initial value, and returns the ref object. The object has exactly one property, `current`, which starts as that initial value. The docs call `current` "intentionally mutable, meaning you can both read and write to it." Mutable comes from the same root as mutation, which Lesson 17 taught: changing a thing from the inside. State must never be mutated. A ref is meant for exactly that: our code changes `current` by plain assignment, and there is no setter.

Yes, it is the exact same thing! Writing into `current` is the same as writing any property of any JavaScript object:

```jsx title="Writing current on a ref, and writing a property on any object"
~ref.current = 5~; // The ref object: current now holds 5
~user.name = 'Alice'~; // Any JavaScript object: name now holds 'Alice'
```

In the words of the docs, "the ref itself is a regular JavaScript object, so it behaves like one." There is no hidden magic in `current`. React does only two things for us: it creates the object, and it keeps it.

### The same object on every render

The `useRef` line runs on every render, just as a line such as `let count = 0` would. So it looks as if the ref goes back to zero each time. It may look the same, but it is NOT the same thing! React uses the initial value only on the first render:
1. **On the first render**, `useRef` creates the ref object with `current` set to zero, and React stores it with the component.
2. **On every later render**, `useRef` returns that same stored object, with whatever `current` holds now. The zero passed to `useRef` is ignored.

The `useRef` reference says it in one line: "This argument is ignored after the initial render."

```tree dir=right caption="What the same useRef line gives back on the first render and on every later render."
The line `const ref = useRef` with the initial value `0`
- +First render | React **creates** the object with `current` set to `0` | React **stores** the object with the component
- +Every later render | React **returns the same stored object** | `current` keeps whatever our code wrote; the `0` is **ignored**
```

### current changes at once

Lesson 15 showed that a state value stays the same for the whole render, even right after its setter. A ref has no snapshot. When our code writes `current`, the very next line already reads the new value:

```jsx title="Logging right after setCount, and right after writing current"
function handleClick() {
  setCount(5);
  console.log(~count~); // Logs the old count: this render's snapshot, as in Lesson 15
  ref.current = 5;
  console.log(~ref.current~); // Logs 5: the object changed at once
}
```

It looks the same, but it is NOT the same thing! The setter asks React for a new render, and the new value arrives with that render. Writing `current` changes the object itself, right now. The docs say: "when you mutate the current value of a ref, it changes immediately".

### The stopwatch keeps its interval ID in a ref

Now our stopwatch gets its ref, and the Stop button gets its handler:

```jsx title="src/components/Stopwatch.jsx" good="5,8,9,15,22"
import { useState, useRef } from 'react';

export default function Stopwatch() {
  const [seconds, setSeconds] = useState(0);
  const intervalRef = ~useRef(null)~; // No interval yet, so the ref starts as { current: null }

  function handleStart() {
    ~clearInterval(intervalRef.current)~; // Stops an interval that is still running, if there is one
    ~intervalRef.current = setInterval~(() => { // Keeps the new interval ID in the ref
      setSeconds(s => s + 1);
    }, 1000);
  }

  function handleStop() {
    ~clearInterval(intervalRef.current)~; // Reads the same ID, many renders later, and stops the interval
  }

  return (
    <section>
      <p>Seconds: {seconds}</p>
      <button onClick={handleStart}>Start</button>
      <button ~onClick={handleStop}~>Stop</button> {/* The Stop button now has a handler */}
    </section>
  );
}
```

The user clicks Start and waits three seconds:

```page width=text caption="Three seconds after the user clicks Start, the line has counted up to 3."
line: Seconds: 3 | good
line: [Start] [Stop]
console: quiet
```

Then the user clicks Stop. Ten seconds later, the line still shows the same number:

```page width=text caption="Ten seconds after the user clicks Stop, the line still shows 3."
line: Seconds: 3 | good
line: [Start] [Stop]
console: quiet
```

When the user clicks Start again, the count goes on to four, because `seconds` stayed in state the whole time.

The first line of `handleStart` protects the stopwatch from a second click on Start. Without that line, two clicks on Start leave an interval that nothing can stop:
1. The user clicks Start. An interval starts, and its ID goes into `intervalRef.current`.
2. The user clicks Start again. A second interval starts, and its ID replaces the first one in `intervalRef.current`. The first ID is now lost.
3. Both intervals add one every second, so the line counts two seconds for every real second.
4. The user clicks Stop. `clearInterval` gets the second ID and stops only the second interval. The first interval runs on, and the line keeps counting one by one.

With the first line in place, a second click on Start stops the old interval before it starts a new one. On the very first click, the ref still holds `null`, and `clearInterval` does nothing with `null`, so that first click is safe too. The docs' own stopwatch writes its Start handler the same way.

> [!PRINCIPLE]
> **Principle 1: useRef: React Returns the Same Ref Object on Every Render**
>
> *`useRef` returns an object whose `current` property starts as the initial value. React gives back the same object on every later render, and our code changes `current` freely without a new render.*
>
> A component often needs to remember a value that the page never shows, such as an interval ID. A ref keeps that value in its `current` property. React creates the object on the first render, ignores the initial value after that, and returns the same object every time. A change to `current` is there at once, and React is not told about it.
>
> **DO THIS:**
> ```jsx
> const intervalRef = useRef(null);
> function handleStart() {
>   clearInterval(intervalRef.current);
>   ~intervalRef.current~ = setInterval(tick, 1000); // The ID waits in the ref for the Stop click
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const intervalRef = useRef(null);
> function handleStart() {
>   ~intervalRef.current~ = setInterval(tick, 1000); // **WRONG:** a second click replaces the first ID, and that interval never stops
> }
> ```

## 2. Principle 2: Stop Fails When intervalId Is a let

### A local variable and a ref, side by side

Before they meet refs, most developers first try a plain variable inside the component. Compare the two places for the interval ID:

```jsx title="Keeping the interval ID in a let variable inside the component"
let ~intervalId = null~; // **WRONG:** this line runs again on every render and makes a new null
function handleStart() { intervalId = setInterval(tick, 1000); }
function handleStop() { clearInterval(intervalId); }
```

```jsx title="Keeping the interval ID in a ref"
const intervalRef = ~useRef(null)~; // React returns the same object on every render
function handleStart() { intervalRef.current = setInterval(tick, 1000); }
function handleStop() { clearInterval(intervalRef.current); }
```

It may look the same, or work the same at first, but it is NOT the same thing! Both store the number in `handleStart`. Only the ref still holds it after the next render. The docs explain why: every render runs the component again from scratch, and that sets up its variables again too.

### The user clicks Stop, and the line keeps counting

Here is the stopwatch with the interval ID in a `let` variable:

```jsx title="src/components/Stopwatch.jsx" bad="5,14"
import { useState } from 'react';

export default function Stopwatch() {
  const [seconds, setSeconds] = useState(0);
  let ~intervalId = null~; // **WRONG:** a new variable, set to null, on every render

  function handleStart() {
    intervalId = setInterval(() => {
      setSeconds(s => s + 1);
    }, 1000);
  }

  function handleStop() {
    clearInterval(~intervalId~); // **WRONG:** reads the new null, so nothing stops
  }

  return (
    <section>
      <p>Seconds: {seconds}</p>
      <button onClick={handleStart}>Start</button>
      <button onClick={handleStop}>Stop</button>
    </section>
  );
}
```

The user clicks Start, waits three seconds, and clicks Stop. Two seconds later, the line is still counting:

```page width=text caption="Two seconds after the user clicks Stop, the line has gone on from 3 to 5."
line: Seconds: 5 | bad
line: [Start] [Stop]
console: quiet
```

The Console stays quiet, because nothing in the code is an error. The interval ID is still in the variable that the Start click filled, but by the time the user clicks Stop, the Stop button reads a different variable. Here is what happens, in order:
1. The user clicks Start. `handleStart` stores the new interval ID in this render's `intervalId`.
2. One second later, the interval calls `setSeconds`, and React renders `Stopwatch` again.
3. The new render runs the `let` line again. That makes a brand-new `intervalId`, and it holds `null`.
4. The new render also makes a new `handleStop`, and React puts it on the Stop button. This `handleStop` reads the new variable, which is `null`.
5. The user clicks Stop. `clearInterval` gets `null` and does nothing.
6. The interval still runs, and the line keeps counting, to four and then five.

There is one case where the `let` version works. If the user clicks Stop within the first second, before the first tick, React has not rendered the stopwatch again yet, because the Start click itself sets no state. The Stop button still holds the `handleStop` of the same render, and it reads the same variable that `handleStart` filled, so the stopwatch stops. That is why a quick test can hide this bug: it shows up only after the component renders again.

### The same mistake in the docs: an Undo button that cannot undo

The docs have a challenge with the same bug. A chat starts a three second `setTimeout` when the user clicks Send, and keeps its timeout ID, the number `setTimeout` returns, in a `let` variable. `clearTimeout` takes that number and cancels the timeout, the same way `clearInterval` stops an interval. The Send click also sets state, which renders the component again. When the user clicks Undo, `clearTimeout` gets the new `null`, so the "Sent!" message still appears after the click on Undo. The docs' fix is the fix of this principle: "store it in a ref, which React will preserve between renders."

### Back to the ref

So the stopwatch keeps `intervalRef` from Principle 1. Every render gets the same ref object back from React, so the Stop handler of the latest render reads the same `current` that the Start handler filled many renders earlier.

> [!PRINCIPLE]
> **Principle 2: Local Variables: A let Inside the Component Resets on Every Render**
>
> *A `let` variable inside the component is created again on every render. The interval ID from the Start click is gone before the Stop click reads it, and a ref keeps it.*
>
> Every render runs the component from the top, so every `let` line runs again and makes a new variable. The interval renders the stopwatch once a second, so the Stop button soon holds a `handleStop` that reads a fresh `null`. `clearInterval` does nothing with `null`, and the stopwatch keeps counting with zero Console errors.
>
> **DO THIS:**
> ```jsx
> const intervalRef = ~useRef(null)~; // The same object on every render
> function handleStop() {
>   clearInterval(intervalRef.current);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> let ~intervalId = null~; // **WRONG:** a new null on every render, so Stop finds nothing to stop
> function handleStop() {
>   clearInterval(intervalId);
> }
> ```

## 3. Principle 3: useState for the Interval ID Renders the Stopwatch Again

### State and a ref both make Stop work

A developer who knows only state reaches for `useState` to keep the interval ID, and on the page that works. Compare the two:

```jsx title="Keeping the interval ID in state"
const [intervalId, setIntervalId] = ~useState(null)~; // Kept between renders, and every change renders again
function handleStart() { ~setIntervalId~(setInterval(tick, 1000)); } // Asks React for a new render
function handleStop() { clearInterval(intervalId); ~setIntervalId(null)~; } // Asks React for another render
```

```jsx title="Keeping the interval ID in a ref"
const intervalRef = ~useRef(null)~; // Kept between renders, and a change renders nothing
function handleStart() { ~intervalRef.current~ = setInterval(tick, 1000); } // React is not told
function handleStop() { clearInterval(intervalRef.current); } // React is not told
```

It may look the same, or work the same at first, but it is NOT the same thing! The user sees the same stopwatch, and Stop works in both. But with state, React renders `Stopwatch` again every time the ID changes, even though nothing on the page shows the ID.

### The Console shows the extra render

To see the renders, we add one `console.log` at the top of `Stopwatch`. The interval renders the stopwatch every second in both versions, so the Console fills up while it counts. Right before the user clicks Stop, we clear the Console:

::: row caption="After the user clicks Stop, the interval ID in state renders the stopwatch again; the interval ID in a ref renders nothing."
::: col title="Interval ID in state" tag="Stop renders again" tone=bad
```page size=mini
line: Seconds: 3
line: [Start] [Stop]
log: Stopwatch rendered | Stopwatch.jsx:6

```
```jsx title="Stopwatch.jsx" startLine="3" bad="3,7"
export default function Stopwatch() {
  const [seconds, setSeconds] = useState(0);
  const [intervalId, setIntervalId] = useState(null);
  console.log('Stopwatch rendered');
  function handleStop() {
    clearInterval(intervalId);
    setIntervalId(null);
  }
```
The click on Stop calls the setter, so React renders `Stopwatch` again and the line prints.
:::
::: col title="Interval ID in a ref" tag="Stop renders nothing" tone=good
```page size=mini

line: [Start] [Stop]

```
```jsx title="Stopwatch.jsx" startLine="3" good="3,6"
export default function Stopwatch() {

  const intervalRef = useRef(null);
  console.log('Stopwatch rendered');

    clearInterval(intervalRef.current);
  }
```
The click on Stop only calls `clearInterval`. React is not asked to render, and the Console stays empty.

With the interval ID in state, one click on Stop prints the line twice, because `<StrictMode>` calls the component twice in development, as Lesson 14 showed. The page shows the same number as before, yet React did all the work of a render for a value nobody sees. The same happens on every click on Start, when the setter stores the new ID. With the interval ID in a ref, the clicks on Start and Stop render nothing by themselves.

There is a second trap in the state version. A developer who logs `intervalId` right after calling `setIntervalId` sees `null`, and thinks the ID was lost. It was not lost: the log read this render's snapshot, as Principle 1 showed, and the ID arrives with the next render.

### The docs' rule for choosing

The docs give one test for choosing between state and a ref: "When a piece of information is used for rendering, keep it in state. When a piece of information is only needed by event handlers and changing it doesn't require a re-render, using a ref may be more efficient."

A value is used for rendering when it appears in the JSX the component returns, or when the component needs it to compute that JSX. Our stopwatch holds one value of each kind:
- **`seconds`** appears in the paragraph the component returns, so it is used for rendering, and it stays in state.
- **The interval ID** appears nowhere in the JSX. Only `handleStart` and `handleStop` read it, so it goes in a ref. About their own stopwatch, the docs say: "Since the interval ID is not used for rendering, you can keep it in a ref".

State and a ref in the same component are both right, each for its own value. The docs say: "You can combine refs and state in a single component."

> [!PRINCIPLE]
> **Principle 3: State or Ref: Keep in State Only What the Page Shows**
>
> *A value the page never shows does not belong in state. Storing the interval ID with a setter works, but every change renders the component again for nothing.*
>
> The setter of state always asks React for a new render. For `seconds`, that is the point, because the page must show the new number. For the interval ID, the render changes nothing on the page. Keep information used for rendering in state, and keep information that only event handlers need in a ref.
>
> **DO THIS:**
> ```jsx
> const [seconds, setSeconds] = useState(0);
> const intervalRef = ~useRef(null)~; // The ID is never shown, so changing it renders nothing
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [seconds, setSeconds] = useState(0);
> const [intervalId, setIntervalId] = ~useState(null)~; // **WRONG:** every new ID renders the stopwatch again for nothing
> ```

## 4. Principle 4: A Shared intervalId Stops the Wrong Stopwatch

### A variable outside the component also survives a render

Principle 2 failed because the `let` line ran again on every render. A variable at the top of the file, outside the component, does not run again. Here are two places that both survive a render:

```jsx title="Keeping the interval ID in a variable outside the component"
let ~intervalId = null~; // Above the component: runs once, when the file loads

export default function Stopwatch() {
  function handleStop() { clearInterval(intervalId); }
}
```

```jsx title="Keeping the interval ID in a ref inside the component"
export default function Stopwatch() {
  const intervalRef = ~useRef(null)~; // Inside the component: React keeps one ref for this stopwatch
  function handleStop() { clearInterval(intervalRef.current); }
}
```

With one stopwatch on the page, both versions work. The line above the component runs once, when the file is imported, and never again. No render makes a new `null`, so the failure of Principle 2 is gone, and Stop works. It may look the same, or work the same at first, but it is NOT the same thing! The difference shows as soon as the page has two stopwatches.

### Two stopwatches: Tea and Eggs

A kitchen often needs two timers at once: one for the tea, one for the eggs. `App` now renders two stopwatches, and each gets a `label` prop:

```jsx title="src/App.jsx"
import Stopwatch from './components/Stopwatch.jsx';

export default function App() {
  return (
    <main>
      ~<Stopwatch label="Tea" />~ {/* The first copy of Stopwatch */}
      ~<Stopwatch label="Eggs" />~ {/* The second copy: its own state, and from now on its own ref */}
    </main>
  );
}
```

`Stopwatch` reads `label` and shows it as a heading above its line:

```jsx title="src/components/Stopwatch.jsx" startLine="3"
export default function Stopwatch({ ~label~ }) { // Tea or Eggs, from the tag in App
  const [seconds, setSeconds] = useState(0);
  const intervalRef = useRef(null);
```

```jsx title="src/components/Stopwatch.jsx" startLine="18"
  return (
    <section>
      ~<h2>{label}</h2>~ {/* Shows which stopwatch this is */}
      <p>Seconds: {seconds}</p>
      <button onClick={handleStart}>Start</button>
      <button onClick={handleStop}>Stop</button>
    </section>
  );
}
```

### The user starts Eggs, and Tea stops

Now suppose `Stopwatch.jsx` keeps the interval ID in the variable above the component, with the same two handlers as in Principle 1. Here is the top of the file:

```jsx title="src/components/Stopwatch.jsx" bad="3"
import { useState } from 'react';

let ~intervalId = null~; // **WRONG:** one variable for every Stopwatch on the page

export default function Stopwatch({ label }) {
  const [seconds, setSeconds] = useState(0);

  function handleStart() {
    clearInterval(intervalId);
    intervalId = setInterval(() => {
      setSeconds(s => s + 1);
    }, 1000);
  }

  function handleStop() {
    clearInterval(intervalId);
  }
```

The user clicks Start under Tea, waits four seconds, then clicks Start under Eggs. Two seconds later, Tea is frozen and only Eggs counts:

```page width=text caption="Two seconds after the user starts Eggs, Tea has stopped on 4 and Eggs counts."
section: Tea
line: Seconds: 4 | bad
line: [Start] [Stop]
section: Eggs
line: Seconds: 2 | good
line: [Start] [Stop]
console: quiet
```

The user never clicked Stop under Tea. Tea stopped because both stopwatches read and write the same `intervalId`:
1. The user clicks Start under Tea. Tea's `handleStart` stores Tea's interval ID in `intervalId`.
2. The user clicks Start under Eggs. Eggs' `handleStart` first calls `clearInterval` with `intervalId`, and that variable holds Tea's ID. Tea's interval stops.
3. Eggs' `handleStart` then stores Eggs' interval ID in the same `intervalId`.
4. If the user now clicks Stop under Tea, Tea's `handleStop` calls `clearInterval` with Eggs' ID, and Eggs stops too.

Every click on one stopwatch reaches the other one's interval. The line above the component runs once, when the file loads, so there is only one `intervalId` for the whole file, and every copy of `Stopwatch` shares it.

### Each copy gets its own ref

With `useRef` inside the component, the problem is gone. React keeps each ref object with the copy of the component that called `useRef`, the same way each copy has its own state, as Lesson 12 showed. Tea has its own `intervalRef`, and Eggs has another one, so each Stop button stops its own interval. The `useRef` reference lists this as the third thing a ref gives: "The information is local to each copy of your component." The variables outside the component, the docs add, are shared.

The docs have a challenge with the same bug, about buttons that wait one second before a pop-up. With a `let timeoutID` at the top of the file, a click on one button and then at once on another loses the first message. The docs explain: "A variable like `timeoutID` is shared between all components." Their fix: "Each button will get its own ref, so they won't conflict with each other."

> [!PRINCIPLE]
> **Principle 4: One Ref per Copy: A Variable Outside the Component Is Shared**
>
> *A variable outside the component survives every render, but every copy of the component shares it. A ref belongs to one copy, so each stopwatch keeps its own interval ID.*
>
> Moving a `let` variable above the component fixes the reset of Principle 2, and with one stopwatch the page looks fine. As soon as the component appears twice, both copies write the same variable, and a click on one stopwatch stops the other. A ref, like state, belongs to the copy that created it.
>
> **DO THIS:**
> ```jsx
> export default function Stopwatch({ label }) {
>   const intervalRef = ~useRef(null)~; // Tea and Eggs each get their own ref
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> let ~intervalId = null~; // **WRONG:** Tea and Eggs share this one variable, so one stops the other
> export default function Stopwatch({ label }) {}
> ```

## 5. Principle 5: secondsRef.current on the Page Stays at 0

### A ref in the JSX does not update the page

After learning that a ref changes at once and renders nothing, some developers put the shown number in a ref too. The docs show what happens with a counter:

```jsx title="A counter that shows a ref in its JSX"
const countRef = useRef(0);

function handleClick() {
  countRef.current = countRef.current + 1;
}

return <button onClick={handleClick}>You clicked ~{countRef.current}~ times</button>; // **WRONG:** read once per render, and nothing renders again
```

The docs say: "If you tried to implement this with a ref, React would never re-render the component, so you'd never see the count change!" It may look the same, or work the same at first, but it is NOT the same thing! On the first render, a count from state and a count from a ref both show zero. Only the count from state shows the next number.

### The user clicks Start, and the line stays at zero

Here is the stopwatch with `seconds` moved from state into a ref:

```jsx title="src/components/Stopwatch.jsx" bad="6,11,22"
import { useRef } from 'react';

export default function Stopwatch({ label }) {
  const intervalRef = useRef(null);

  const secondsRef = ~useRef(0)~; // **WRONG:** the shown number in a ref

  function handleStart() {
    clearInterval(intervalRef.current);
    intervalRef.current = setInterval(() => {
      ~secondsRef.current = secondsRef.current + 1~; // Changes the number, and React is not told
    }, 1000);
  }

  function handleStop() {
    clearInterval(intervalRef.current);
  }

  return (
    <section>
      <h2>{label}</h2>
      <p>Seconds: ~{secondsRef.current}~</p> {/* **WRONG:** read during rendering, so the page keeps the old number */}
      <button onClick={handleStart}>Start</button>
      <button onClick={handleStop}>Stop</button>
    </section>
  );
}
```

The user clicks Start under Tea and waits six seconds:

```page width=text caption="Six seconds after the user clicks Start under Tea, the line still shows 0."
section: Tea
line: Seconds: 0 | bad
line: [Start] [Stop]
section: Eggs
line: Seconds: 0
line: [Start] [Stop]
console: quiet
```

The interval runs, and `secondsRef.current` really holds six. The page still shows zero because nothing renders the stopwatch again:
1. Every second, the interval adds one to `secondsRef.current`.
2. No line calls a setter, so React is never asked to render. The `useRef` reference explains: "React is not aware of when you change it because a ref is a plain JavaScript object."
3. The paragraph keeps the text it got in the last render, when `secondsRef.current` was still zero.

The line is not stuck forever, and that makes the bug harder to find. Suppose the Stop handler also called a setter, as the state version of Principle 3 did. Then the click on Stop renders the stopwatch, the render reads the ref, and the line jumps from zero straight to six. The docs say: "This is why reading `ref.current` during render leads to unreliable code."

The fix is to move `seconds` back into state, with the updater function in the interval, as in Principle 1. The page shows `seconds`, so it is used for rendering, and the rule of Principle 3 puts it in state.

### Do not read or write current during rendering

The `useRef` reference turns this into a rule: "Do not write or read `ref.current` during rendering, except for initialization."

During rendering means while React calls the component function: the lines in its body and the JSX it returns. An event handler, such as `handleStart`, is defined during rendering, but its code runs later, when the user clicks. So reading `secondsRef.current` in the JSX happens during rendering, while writing `intervalRef.current` inside `handleStart` does not.

React cares because of purity. Lesson 14 showed that React expects a component to be pure: the same props and state give the same JSX. A ref can change without React knowing, so JSX that reads a ref can show a different result for the same props and state. The docs say: "You can read or write refs from event handlers or effects instead." Effects come in Lesson 32.

There is one exception, which the docs call initialization: filling an empty ref once, on the first render. It helps when the ref holds an object that is costly to create, such as a video player. Compare passing the new object straight to `useRef` with filling the ref only while it is empty:

```jsx title="Passing a new player straight to useRef"
const playerRef = useRef(~new VideoPlayer()~); // Creates a new player on every render, and React ignores all but the first
```

```jsx title="Filling an empty ref once, during the first render"
const playerRef = useRef(null);
if (~playerRef.current === null~) { // True only on the first render
  playerRef.current = new VideoPlayer(); // Runs once; every later render skips it
}
```

Both give the component the right player. But the first line creates a new player on every render, and every player after the first is thrown away, because React ignores the initial value after the first render. The check for `null` creates the player only once. Writing `current` during rendering is fine here, as the docs say, "because the result is always the same, and the condition only executes during initialization". It is the same idea as the initializer function of `useState` in Lesson 12.

> [!PRINCIPLE]
> **Principle 5: Rendering: A Shown Value Belongs in State, Not in a Ref**
>
> *A value the page shows must be state, because changing a ref does not render. Our code does not read or write `ref.current` during rendering, except to fill an empty ref once.*
>
> The page shows what the last render read. A ref changes without a render, so JSX that reads `current` keeps showing the old number until something else renders the component, and then the number jumps. When a value is needed to compute the JSX, that value belongs in state. Read and write refs in event handlers.
>
> **DO THIS:**
> ```jsx
> const [seconds, setSeconds] = useState(0);
> return <p>Seconds: ~{seconds}~</p>; // The setter renders again, so the page shows each new number
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const secondsRef = useRef(0);
> return <p>Seconds: ~{secondsRef.current}~</p>; // **WRONG:** read during rendering, so the page stays on 0
> ```

### How React calls the components and keeps their values

When the page opens, React calls `App`, then the two copies of `Stopwatch` in the order of their tags. Each copy gets its own state and its own ref from React, and React hands both back to that copy on every later render:

```tree caption="The order in which React calls the components, and the state and ref that React keeps for each copy of Stopwatch."
`App` [1. Called first] | **Root component** | Renders `<Stopwatch label="Tea" />` and `<Stopwatch label="Eggs" />`
- +`Stopwatch` with `label` Tea [2. Called second] | Its own **`seconds`** in state | Its own **`intervalRef`**, kept between renders
- +`Stopwatch` with `label` Eggs [3. Called third] | Its own **`seconds`** in state | Its own **`intervalRef`**, kept between renders
```

| Where the interval ID lives | What the user sees | Why |
| :--- | :--- | :--- |
| **A `let` variable inside the component** | Stop does nothing after the first second, and the line keeps counting | Every render makes a new variable set to `null` |
| **State with `setIntervalId`** | The stopwatch works | Every new ID renders the component again for a value the page never shows |
| **A variable above the component** | A click on one stopwatch stops the other one | Every copy of the component shares the one variable |
| **A ref with `useRef`** | Each stopwatch starts and stops on its own | React keeps the ref between renders, a change renders nothing, and each copy has its own |
| **The shown number in a ref** | The line stays at zero | Changing `current` never renders, so the JSX keeps the old number |

## For the Interview

> **The Interview Question:** How do you keep a value between renders without triggering a re-render?

### How to Answer Clearly in 30 Seconds

"I use a ref. `useRef` returns a plain object with one property, `current`, which starts as the initial value. React creates it on the first render and returns the same object on every later render, so the value survives re-renders like state does. But changing `ref.current` does not re-render the component, and the change is there at once. A stopwatch is the classic case: the interval ID from `setInterval` goes in a ref, so the Stop handler can pass it to `clearInterval` many renders later. Three rules keep it right:
1. **A local `let` variable resets on every render**, and a variable outside the component is shared by every copy, so neither can hold the interval ID.
2. **Information used for rendering goes in state**, and information only event handlers need, such as an interval ID or a timeout ID, goes in a ref.
3. **Never read or write `ref.current` during rendering**, except to fill an empty ref once. A value shown on the page and kept in a ref does not update when the ref changes."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"How is `useRef` different from `useState`, and could you build it with `useState`?"**
   Both keep a value between renders, and both belong to one copy of the component. The setter of state asks React to render again, and the new value arrives with the next render. A ref has no setter: our code changes `current` directly, at once, and React is not told. The docs show that `useRef` could be built on top of `useState`: a state variable holds the object with `current` forever, and nobody ever calls its setter. That is why the docs call a ref "a regular state variable without a setter". The docs also compare refs to instance fields in class components, such as `this.something`.
2. **"Why should you not read `ref.current` during rendering, and when is it allowed?"**
   React expects a component to be pure: the same props and state give the same JSX. A ref can change without a render, so JSX that reads it shows an old value, and then jumps when something else renders the component. A warning in the `useRef` reference says that when you break this rule, "your component might still work", but newer React features rely on it. The `refs` lint rule flags three things: reading a ref during render, updating a ref during render, and keeping in a ref a value that should be state. The React Compiler also reports an error on a line that reads a ref during render. The one allowed case is initialization: a check that `playerRef.current` is still `null`, which fills the empty ref once, on the first render.
3. **"When would you reach for a ref at all?"**
   The docs call refs an "escape hatch" that "you won't need often", for values outside React's rendering. Their list: storing timeout IDs, storing and manipulating DOM elements, and storing other objects that are not needed to calculate the JSX. An interval ID or a timeout ID is the case from this lesson. The docs name the most common use: accessing a DOM element through the `ref` attribute, which the next lesson covers. A ref can hold any value: "a string, an object, or even a function". In Strict Mode, React calls the component twice in development. Both calls get back the same ref object, but an initial value such as a new video player is built twice.

```tree dir=right caption="Interview comparison: what state and a ref share, and the one way they differ."
State vs. a ref in an interview
- +State [`useState`] | Kept between renders, **one per copy** | The setter **renders again**; the new value arrives with the **next render**
- +A ref [`useRef` `ref.current`] | Kept between renders, **one per copy** | No setter; a change is there **at once** and **renders nothing**
```
