# Lecture 29: Combining a Reducer with Context for App-Wide State

*(How can a button deep in the page change a state that lives at the top?)*

> INTERVIEW QUESTION | ❱ CORE | How do you combine a reducer with context for app-wide state?

---

## VS | Props vs. Context for Shared State: props pass through every layer, context delivers directly

> **Combining `useReducer` with context lets any component read and update shared state without passing props through middle layers.**

In React, different parts of a page often need the exact same data. A shopping cart, a user profile, or an alert list are common examples. Normally, we store shared state in a parent component at the top of the tree. Then we pass the data and the handler functions down level by level through props.

Passing props through components that never use them is called prop drilling. When an application grows, prop drilling becomes painful. Passing values through five or six layers of layout wrappers creates messy and fragile code. If a single component in the middle forgets to forward a prop, a button deep below fails to work.

**This is why we combine `useReducer` with context.**

Together, they allow any component deep in the tree to read state and trigger updates directly. The components in the middle do not need to touch or pass any props.

Take an online shop where the header at the top says **Cart: 3 items**. Far below, inside a product row, the user clicks **Delete**. That item row must disappear immediately. At that exact same moment, the top header must change to **Cart: 2 items**.

How does a **Delete** button buried deep inside a product row update the cart at the top of the page? We call `useReducer` in the top component. Then context carries the cart data and the `dispatch` function down the tree. Both the header and the delete button access the same state, even with several layout components between them.

**Why:** Both the top header and the cart list need the cart data. Therefore, the cart state must live in a common parent component above both of them. With ordinary props, that parent must pass the cart array and every click handler down through every single child. Layout wrappers and styling containers are forced to forward props they never read. Worse, if one middle component drops the delete handler, clicking the button does nothing. Combining `useReducer` with context solves this defect by broadcasting the state and the `dispatch` function directly to the components that need them.

Here is the central rule to keep in mind for this entire lesson:

**The state still lives in the component that calls `useReducer`. Context only delivers it: the cart in one context, and `dispatch` in another.**

### Two Pieces You Already Know

You already know both building blocks. Here is a quick reminder of each piece.

> [!DEFINITION]
> **A reducer and dispatch.** [REVIEW] A reducer is a plain JavaScript function that calculates the next state from the current state and an action: `cartReducer(cart, action)`.
> You connect it to a component with `const [cart, dispatch] = useReducer(cartReducer, initialCart)`. You get two values back: `cart`, the current state, and `dispatch`, a function.
> When the user clicks a button, you do not mutate the state array yourself. You call `dispatch({ type: 'deleted', id: 1 })`. React passes that action object to your reducer and re-renders the component with the returned state.
> The `dispatch` function is a regular JavaScript value. You can pass it around like any other function (Lesson 27).

> [!DEFINITION]
> **A context.** [REVIEW] A context lets a child component access a value without props. You create a context with `createContext`. A provider component supplies the value to its tree. Any component nested below reads that value with `useContext`.
> Wrapping a section in `<ThemeContext value={theme}>` makes `theme` available to all components inside. Any nested child can call `useContext(ThemeContext)` and read `theme` directly.
> A context stores nothing on its own. It only transports what its provider gives it (Lesson 28).

### The Shared State Problem in React

In plain JavaScript outside React, sharing one value across multiple files is straightforward. You export a variable from a module and import it wherever you need it:

```js title="Plain JavaScript: one shared variable"
import { cart, deleteItem } from './cart.js';
~deleteItem(1)~; // The array changes in memory, but nothing tells React to update the DOM
```

In React, a plain imported variable does not work. You can mutate an exported array, but React will not notice. No re-render triggers, so the screen remains unchanged. Data shown to the user must live in React state. And state belongs to a component, the component that calls `useReducer`.

The challenge is clear. How can a button nested five levels deep reach the `dispatch` function of the top component? Context solves this connection. A child component asks React to look up the component tree, find the matching provider, and return its value.

```jsx title="React: one reducer, two contexts"
function App() {
  const [cart, dispatch] = useReducer(cartReducer, initialCart);
  return (
    <CartContext ~value={cart}~> {/* Delivers the cart array to every component inside */}
      <CartDispatchContext ~value={dispatch}~> {/* Delivers the dispatch function to every component inside */}
        <Page />
      </CartDispatchContext>
    </CartContext>
  );
}

function Header() {
  const cart = ~useContext(CartContext)~; // Reads the cart state held by App
  return <p>Cart: {cart.length} items</p>;
}

function DeleteButton({ id }) {
  const dispatch = ~useContext(CartDispatchContext)~; // Reads the dispatch function provided by App
  return <button onClick={() => dispatch({ type: 'deleted', id: id })}>Delete</button>;
}
```

This pattern builds directly on context fundamentals (Lesson 28). The `dispatch` function is a JavaScript value just like a theme string or a user object. The top component passes it to a provider, and a child component reads it with `useContext`.

React documentation summarizes this pairing neatly. Reducers let you consolidate state update logic in one place. Context lets you pass information deep down to other components. Combining them allows you to manage complex state across a full screen.

```tree caption="A reducer and a context each do one job. Together, a component far below can read the state and send actions."
A reducer and a context on the same page
- +The reducer [`useReducer` `cartReducer`] | Keeps **all the update logic** in one function | Gives **`cart`** and **`dispatch`** to the component that calls it
- +The context [`CartContext` `useContext`] | Carries a value **deep down the tree** | Any component below **asks for it** without props
- +Both together | `App` puts **`cart` and `dispatch`** into two providers | `Header` reads the cart, and a button far below **sends actions**
```

### Why Two Contexts Instead of One

Both values come from the exact same `useReducer` call. The crucial difference is how often each value changes:

1. **`cart` changes frequently.** Every action that adds, modifies, or deletes an item returns a new array reference.
2. **`dispatch` never changes.** React guarantees that `dispatch` has a stable identity across every re-render. It remains the exact same function reference.

Because of this difference, each value gets its own context. A component that only dispatches actions subscribes only to `dispatch`. Because `dispatch` never changes, React does not need to re-render that component when the cart changes. Principle 4 demonstrates this performance benefit directly.

### What App-Wide State Really Means

The interview question refers to app-wide state. That term means state that many different parts of a page need to read and update. A shopping cart is app-wide because the header displays the count while individual product rows modify the contents.

App-wide state is not a separate global data store outside React. The state still lives inside a standard React component, managed by `useReducer`.

A senior developer avoids four common mistakes:

1. **Assuming the state lives inside the context.** The context does not store state. It only delivers the state returned by `useReducer`.
2. **Treating app-wide state as a global variable.** Context follows the component tree. A component outside the provider receives the default value, which we set to `null`.
3. **Bundling both values into a single object.** Passing `value={{ cart, dispatch }}` creates a brand-new object on every render. That forces every reading component to re-render.
4. **Removing every prop.** Props that belong specifically to a single component, such as the item data for a specific row, should remain props.

### Four Ways to Share State Across Distant Components

1. **Passing props through parents (Lesson 24).** State lives in the nearest common parent, which forwards props down. This works best when only one or two components sit in between.
2. **Passing JSX as `children` (Lesson 28).** Moving layout components to use `children` removes intermediary components, so fewer props travel.
3. **Combining a reducer with context (Lesson 29).** This approach fits when many components at different nesting levels must read or update shared state.
4. **Using `useState` with context (Lesson 28).** This works well for simple values that do not need action objects or centralized reducer logic.

At the start, `App` calls `useReducer` and creates four event handlers. Each handler dispatches one action:

```jsx title="src/App.jsx"
import { useReducer } from 'react';
import cartReducer from './cartReducer.js';
import Header from './components/Header.jsx';
import CartPage from './components/CartPage.jsx';

const initialCart = [
  { id: 0, name: 'Apple', quantity: 1 },
  { id: 1, name: 'Bread', quantity: 2 },
  { id: 2, name: 'Milk', quantity: 1 },
];

export default function App() {
  const [cart, dispatch] = useReducer(cartReducer, initialCart);

  function handleIncrease(id) {
    dispatch({ type: 'increased', id: id });
  }

  function handleDecrease(id) {
    dispatch({ type: 'decreased', id: id });
  }

  function handleDelete(id) {
    dispatch({ type: 'deleted', id: id });
  }

  function handleEmpty() {
    dispatch({ type: 'emptied' });
  }

  return (
    <>
      <Header cart={cart} />
      <CartPage ~cart={cart} onIncrease={handleIncrease} onDecrease={handleDecrease} onDelete={handleDelete} onEmpty={handleEmpty}~ /> {/* Passes five props through a component that uses none of them */}
    </>
  );
}
```

The header component displays the item count:

```jsx title="src/components/Header.jsx"
export default function Header({ cart }) {
  return (
    <header>
      <h1>Corner Shop</h1>

    </header>

}
```

The cart page component receives five props and only forwards them to children:

The cart list component reads the cart array and forwards three handlers to each row:

```jsx title="src/components/CartList.jsx"
import CartRow from './CartRow.jsx';

export default function CartList({ cart, onIncrease, onDecrease, onDelete }) {
  if (cart.length === 0) {

  return (

      {cart.map(item => (
        <CartRow key={item.id} item={item} ~onIncrease={onIncrease} onDecrease={onDecrease} onDelete={onDelete}~ /> // Forwards three handlers to each row without calling them
      ))}

```

At the bottom of the tree, `CartRow` and `EmptyCartButton` invoke the forwarded handlers:

```jsx title="src/components/CartRow.jsx"
export default function CartRow({ item, onIncrease, onDecrease, onDelete }) {
  return (
    <li>
      {item.name}: {item.quantity}
      <button onClick={() => onIncrease(item.id)}>Add one</button>
      <button onClick={() => onDecrease(item.id)}>Remove one</button>
      <button onClick={() => ~onDelete(item.id)~}>Delete</button> {/* Invokes the handler passed down through multiple parents */}
    </li>

```

```jsx title="src/components/EmptyCartButton.jsx"
export default function EmptyCartButton({ onEmpty }) {

}
```

The application works, but the intermediate components carry functions they never call. This is classic prop drilling (Lesson 24).

This structure is brittle. If a developer refactors the list file and forgets to forward `onDelete`, clicking the button crashes with an error stating that `onDelete` is not a function.

We will eliminate this prop drilling step by step. Across all steps, the user interface remains identical.

**PRINCIPLES:** State and dispatch remain in the component that calls `useReducer`. Two contexts deliver them to every child component. Five principles follow:
1. **Principle 1: Two Contexts, One for the State and One for dispatch.** Each context is initialized with `createContext(null)` in a dedicated file.
2. **Principle 2: Two Providers in the Component That Calls useReducer.** The top component wraps its children in both providers using the `value` prop.
3. **Principle 3: Each Component Reads Only What It Needs.** Consumer components read cart data or dispatch directly, eliminating intermediate props.
4. **Principle 4: A Provider Component That Takes children.** A dedicated `CartProvider` component encapsulates state setup and prevents unwanted re-renders.
5. **Principle 5: Two Custom Hooks Read the Two Contexts.** Custom hooks expose cart state and dispatch without exporting raw context objects.

## PRINCIPLE | createContext: the cart and dispatch each get their own context

> [!PRINCIPLE]
> **Principle 1: Two Contexts, One for the State and One for dispatch**
>
> *Create two separate contexts with createContext and the default value null: one carries the state, the other carries dispatch.*
>
> One useReducer call gives two values, and they change at different rates. The cart is a new array after every action, and dispatch never changes. Give each value its own context, so a component reads only the one it needs. Packing both into one object makes a new object on every render, and every reader renders again.
>
> **DO THIS:**
> ```jsx
> export const CartContext = createContext(null);
> export const ~CartDispatchContext~ = createContext(null); // Gives dispatch its own dedicated context
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ShopContext ~value={{ cart, dispatch }}~> {/* A new object is created on every render, causing all consumers to re-render */}
>   <CartPage />
> </ShopContext>
> ```

The first step is creating the contexts. Because `useReducer` returns two distinct values, we create two separate contexts in a new file:

```jsx title="src/CartContext.jsx"
import { createContext } from 'react';

export const ~CartContext~ = createContext(null); // Carries the current cart array
export const ~CartDispatchContext~ = createContext(null); // Carries the dispatch function
```

Each context is created with standard `createContext`. The context objects have no built-in knowledge of reducers. Their names simply describe what each context carries.

Three implementation details matter here:

1. **The default value is `null`.** The real values will come from the component that calls `useReducer`. A consumer reads `null` only when no provider wraps it.
2. **Both contexts live in a dedicated file.** Any component file can import them by name using curly braces (Lesson 05).
3. **The file uses the `.jsx` extension.** In subsequent steps, this file will export JSX components.

```tree caption="The two contexts of the cart: what each one will carry, and where the value will come from."
Two contexts in the context file
- +`CartContext` [`createContext`] | Starts as **`null`** | Will carry **the current cart**, from `useReducer`
- +`CartDispatchContext` [`createContext`] | Starts as **`null`** | Will carry **`dispatch`**, from the same `useReducer`
```

### VS | Two Contexts vs. One Context: object identity across renders

A developer might consider combining both values into a single context object:

```jsx title="Two contexts compared to a single bundled context"
<CartContext ~value={cart}~> {/* Two contexts: state in one, dispatch in the other */}
  <CartDispatchContext value={dispatch}>...</CartDispatchContext>
</CartContext>

<ShopContext ~value={{ cart, dispatch }}~>...</ShopContext> {/* One context: creates a new object literal on every render */}
```

Visually, both approaches render the exact same page. In JavaScript memory, however, their behavior is completely different.

Notice the inline object syntax `value={{ cart, dispatch }}`. The outer curly braces switch into JavaScript. The inner curly braces instantiate a new object in memory every time the component renders.

React checks whether a context value changed using `Object.is`. Two different object references are never equal, even if their properties hold identical data. Consequently, every component reading `ShopContext` re-renders on every update, including buttons that only use `dispatch`.

With two separate contexts, `CartDispatchContext` always receives the exact same function reference. `Object.is` confirms the identity is unchanged. Components subscribed only to dispatch skip unnecessary re-renders.

### Why Default to null Instead of an Empty Array

The choice of default value is deliberate. If the default were an empty array, a header placed outside the provider would quietly display `Cart: 0 items`. The application would run with an undetected bug.

Setting the default value to `null` guarantees that an unprovided consumer fails immediately with a TypeError when accessing `cart.length`. In development, an immediate error reveals the missing provider before the code reaches production.

### State of the Application

Nothing on the screen changes yet. The application continues using props, and the console remains quiet.

## PRINCIPLE | Two providers with value: everything inside can reach the cart and dispatch

> [!PRINCIPLE]
> **Principle 2: Two Providers in the Component That Calls useReducer**
>
> *The component that calls useReducer puts the state in one provider and dispatch in the other, around everything it renders.*
>
> Only the component that calls useReducer has the cart and dispatch, so it is the one that provides them. The order of the two providers does not matter, because each reader looks only for its own context. A provider only makes a value available, so nothing changes until a component below reads it. The prop must be named value, or every reader gets undefined.
>
> **DO THIS:**
> ```jsx
> <CartContext value={cart}>
>   <CartDispatchContext ~value={dispatch}~> {/* Consumers below receive the dispatch function from useReducer */}
>     <CartPage />
>   </CartDispatchContext>
> </CartContext>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <CartContext value={cart}>
>   <CartDispatchContext ~dispatch={dispatch}~> {/* Passing a custom prop name leaves value undefined for consumers */}
>     <CartPage />
>   </CartDispatchContext>
> </CartContext>
> ```

The second step provides both values to the component tree. Because `App` calls `useReducer`, it holds both the state and the dispatch function. It wraps its child components with both providers.

First, `App` imports the two context objects:

```jsx title="src/App.jsx" startLine="1"
import { useReducer } from 'react';
import cartReducer from './cartReducer.js';
import { ~CartContext, CartDispatchContext~ } from './CartContext.jsx'; // Named imports using curly braces
import Header from './components/Header.jsx';
import CartPage from './components/CartPage.jsx';
```

Next, the JSX returned by `App` wraps both children inside the two context providers. For now, we keep the original props in place:

```jsx title="src/App.jsx" startLine="32"
  return (
    <CartContext ~value={cart}~> {/* Makes the current cart array available to all child components */}
      <CartDispatchContext ~value={dispatch}~> {/* Makes the dispatch function available to all child components */}
        <Header cart={cart} />
        <CartPage cart={cart} onIncrease={handleIncrease} onDecrease={handleDecrease} onDelete={handleDelete} onEmpty={handleEmpty} />
      </CartDispatchContext>
    </CartContext>
  );
}
```

Passing both props and context values represents a safe intermediate step. It allows us to verify provider wiring before updating individual consumers.

### Providers Only Supply Values

A provider does not change the behavior of its children automatically. It simply makes a value available in the React tree. Nothing changes until a descendant component calls `useContext`.

The application looks and behaves identically. The DOM structure in browser developer tools remains unchanged: the providers do not render extra DOM nodes.

Note that `App` itself cannot consume the contexts it provides. In React, a `useContext` call only reads from providers higher up in the component tree. Because `App` already owns the state, it has no need to read its own providers.

### Provider Nesting Order

Because each provider manages an independent context, their nesting order does not matter:

```jsx title="Either nesting order produces identical behavior"
<CartContext value={cart}><CartDispatchContext value={dispatch}>...</CartDispatchContext></CartContext> {/* CartContext wraps CartDispatchContext */}
<CartDispatchContext value={dispatch}><CartContext value={cart}>...</CartContext></CartDispatchContext> {/* CartDispatchContext wraps CartContext */}
```

Both arrangements work identically. When a child component calls `useContext`, React searches upward for the closest provider matching that specific context type (Lesson 28).

### The value Prop Requirement

A common error at this stage is naming the provider prop after the variable it passes:

```jsx title="src/App.jsx" startLine="34"
      <CartDispatchContext ~dispatch={dispatch}~> {/* A context provider only reads the prop named value */}
```

React context providers require the prop to be named `value`. If you pass `dispatch={dispatch}`, the provider treats the value prop as undefined. React prints a warning in the console:

```page width=text caption="The shop page when App provides dispatch with a prop named dispatch instead of value: the page works, and the Console shows a warning."
heading: Corner Shop
line: Cart: 3 items
section: Your cart
line: • Apple: 1 [Add one] [Remove one] [Delete]
line: • Bread: 2 [Add one] [Remove one] [Delete]
line: • Milk: 1 [Add one] [Remove one] [Delete]
line: [Empty cart]
console: The `value` prop is required for the `<Context.Provider>`. Did you misspell it or forget to pass it?
```

While components still rely on props, this mistake causes no immediate crash. But as soon as a child component reads `CartDispatchContext`, it receives `undefined` instead of the function. Clicking a button then crashes with a TypeError.

Always pass the data using `value`.

## PRINCIPLE | useContext: each component reads only what it needs, and the middle drops its props

> [!PRINCIPLE]
> **Principle 3: Each Component Reads Only What It Needs**
>
> *A component that shows the cart reads CartContext. A component that changes the cart reads CartDispatchContext and sends its own action. The components in the middle stop receiving props they never used.*
>
> With props, every component between App and the buttons carried handlers it never called, and one forgotten prop broke a button. With the two contexts, each component asks for what it uses, right where it uses it. One click deep in a row changes the header at the top, because both read the same cart from App. A prop that a component really needs, such as the item of one row, stays a prop.
>
> **DO THIS:**
> ```jsx
> function CartRow({ item }) {
>   const dispatch = ~useContext(CartDispatchContext)~; // Reads dispatch from the nearest provider above
>   return <button onClick={() => dispatch({ type: 'deleted', id: item.id })}>Delete</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function CartPage({ ~onDelete~ }) { // Forwards a handler prop down without ever invoking it
>   return <CartList onDelete={onDelete} />;
> }
> ```

The third step connects the consumer components directly to the providers.

### VS | Handlers from Props vs. Dispatch from Context

Compare two ways for a table row to delete an item:

```jsx title="A delete button using props compared to one using context"
function CartRow({ item, ~onDelete~ }) { // onDelete traveled through multiple intermediate components
  return <button onClick={() => onDelete(item.id)}>Delete</button>;
}

function CartRow({ item }) {
  const dispatch = ~useContext(CartDispatchContext)~; // dispatch is read directly from context
  return <button onClick={() => dispatch({ type: 'deleted', id: item.id })}>Delete</button>;
}
```

From the user perspective, both implementations do the same thing. Clicking the button removes the row.

The architecture of the code, however, differs fundamentally:

1. **With props**, `App` constructed each action handler. It passed those functions down through two intermediary components.
2. **With context**, `CartRow` accesses `dispatch` directly. The row constructs the action object itself, right where the user interaction occurs.

### Connecting the Consumer Components

The header component reads the cart to display total items:

```jsx title="src/components/Header.jsx"
import { useContext } from 'react';

    <header>
      <h1>Corner Shop</h1>

    </header>
  );
}
```

The cart list component also reads the cart from context. It renders each row, passing only the individual item:

```jsx title="src/components/EmptyCartButton.jsx"
import { CartDispatchContext } from '../CartContext.jsx';

export default function EmptyCartButton() {
  const dispatch = useContext(CartDispatchContext);
  return <button onClick={() => ~dispatch({ type: 'emptied' })~}>Empty cart</button>; // Dispatches the emptied action on click
}
```

### Context Does Not Eliminate All Props

Context is designed for data needed across distant components. It does not replace local props.

In our list, `item` remains a prop on `CartRow`. Each row renders different product data, and only the list file knows which item belongs to which row. Keep component-specific data in props.

### Removing Intermediate Props

With consumers wired to context, `CartPage` drops all five props:

```jsx title="src/components/CartPage.jsx"

  return (
    <main>
      <h2>Your cart</h2>
      <CartList />
      <EmptyCartButton />
    </main>
  );
}
```

`CartPage` is now clean. It contains only layout structure and renders child components without carrying unwanted arguments.

`App` also sheds its four event handlers. Action objects are now created where the click occurs:

```jsx title="src/App.jsx" startLine="13"
export default function App() {
  const [cart, dispatch] = useReducer(cartReducer, initialCart);
  return (
    <CartContext value={cart}>
      <CartDispatchContext value={dispatch}>
        ~<Header />~ {/* Rendered cleanly without props */}
        ~<CartPage />~ {/* Rendered cleanly without props */}
```

## PRINCIPLE | CartProvider with children: the reducer moves out of App, and buttons stop rendering again

> [!PRINCIPLE]
> **Principle 4: A Provider Component That Takes children**
>
> *CartProvider calls useReducer, provides both contexts, and renders the children it receives. App only places CartProvider around the parts of the page that need the cart.*
>
> All the wiring now lives in one component, next to the contexts. CartProvider is our own component, and children is the prop of Lesson 09. Every component that reads the cart must sit inside it, or it reads null. And because the children come from App, a click renders again only the components that read the cart, not a button that only sends actions.
>
> **DO THIS:**
> ```jsx
> export default function App() {
>   return (
>     ~<CartProvider>~ {/* Header and CartPage both sit inside the provider component */}
>       <Header />
>       <CartPage />
>     </CartProvider>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   return (
>     <>
>       ~<Header />~ {/* Placed outside CartProvider, this component reads the default null value */}
>       <CartProvider><CartPage /></CartProvider>
>     </>
>   );
> }
> ```

The page works, but `App` still contains state initialization and nested context providers. We can encapsulate this setup inside a dedicated provider component.

> [!DEFINITION]
> **A provider component.** [NEW] A provider component is a custom component that holds state and wraps its children in context providers. It is a standard React component, not a special framework feature.
> `CartProvider` is written as a normal function component. It calls `useReducer` and returns the two context providers with `{children}` inside them.
> `children` is the component prop you learned in Lesson 09. Any JSX written between `<CartProvider>` and `</CartProvider>` arrives as `children`.
> A provider component has three responsibilities: manage state with a reducer, provide context values to descendants, and render its `children` prop.

Here is the context file after moving state management into `CartProvider`:

```jsx title="src/CartContext.jsx"
import { createContext, useReducer } from 'react';
import cartReducer from './cartReducer.js';

const initialCart = [
  { id: 0, name: 'Apple', quantity: 1 },
  { id: 1, name: 'Bread', quantity: 2 },
  { id: 2, name: 'Milk', quantity: 1 },
];

export const CartContext = createContext(null);
export const CartDispatchContext = createContext(null);

export function ~CartProvider~({ children }) { // Encapsulates reducer state and context delivery
  const [cart, dispatch] = useReducer(cartReducer, initialCart);
  return (
    <CartContext value={cart}>
      <CartDispatchContext value={dispatch}>
        ~{children}~ {/* Renders whatever JSX elements were passed inside CartProvider tags */}
      </CartDispatchContext>
    </CartContext>
  );
}
```

Now, `App` does not need to call `useReducer` or manage initial state data:

```jsx title="src/App.jsx"
import { CartProvider } from './CartContext.jsx';
import Header from './components/Header.jsx';
import CartPage from './components/CartPage.jsx';

export default function App() {
  return (
    ~<CartProvider>~ {/* Wraps application content so descendants can consume cart state and dispatch */}
      <Header />
      <CartPage />
    </CartProvider>
  );
}
```

```tree dir=right caption="How Header and CartPage, written inside CartProvider in App, end up inside both providers."
How the two components reach the providers
- +1. In `App` [`CartProvider`] | `Header` and `CartPage` are written **between the tags**
- +2. In the props [`children`] | React collects both into **`children`**
- +3. In `CartProvider` [`children`] | Both render **inside the two providers**, so they can read the cart and `dispatch`
```

### Components Placed Outside the Provider

Where `App` places a component determines what context it receives:

```jsx title="Header placed inside compared to placed outside the provider"
<CartProvider><Header /><CartPage /></CartProvider> {/* Header is inside: it receives the cart array */}
<><Header /><CartProvider><CartPage /></CartProvider></> {/* Header is outside: it receives the default null */}
```

When `Header` sits outside `CartProvider`, no matching provider exists above it in the tree. The `useContext` call returns the default value: `null`.

When `Header` attempts to read `cart.length`, JavaScript throws an error because null has no properties:

```page width=text caption="The shop page when Header sits above CartProvider: Header reads null, and the page is blank."
blank
console: Uncaught TypeError: Cannot read properties of null (reading 'length')
console: An error occurred in the <Header> component. Consider adding an error boundary to your tree to customize error handling behavior.
```

This loud failure is why we chose `null` as the default value in Principle 1. Any component mounted outside the provider fails immediately during development rather than showing false data.

### Preventing Unnecessary Re-Renders

Moving `useReducer` into `CartProvider` provides a significant rendering optimization. To observe this, add a console log inside `EmptyCartButton`:

```jsx title="src/components/EmptyCartButton.jsx"
export default function EmptyCartButton() {

```

Why does `EmptyCartButton` avoid re-rendering when `CartProvider` is used?

**When state lived directly inside `App`:**
1. State changes triggered a re-render of `App`.
2. When a component re-renders, React re-renders all components returned in its JSX tree (Lesson 13).
3. Therefore, React re-rendered every child, including `EmptyCartButton`, even though its displayed output never changed.

**When state lives inside `CartProvider`:**
1. State changes re-render `CartProvider`, but `App` does not re-render.
2. Because `App` did not re-render, the JSX passed via `children` retains the exact same object references.
3. React inspects `children` and sees that its elements are identical. It skips re-rendering child components unless they consume changed context data.
4. `CartContext` holds a new array, so its consumers re-render: the header, the list, and each row.
5. `CartDispatchContext` holds the unchanged `dispatch` function. Because `dispatch` is identical by `Object.is`, components reading only dispatch skip re-rendering entirely.

Using separate contexts and passing JSX through `children` work together to keep unrelated components from re-rendering.

## PRINCIPLE | useCart and useCartDispatch: components read the cart without touching the contexts

> [!PRINCIPLE]
> **Principle 5: Two Custom Hooks Read the Two Contexts**
>
> *The context file exports useCart and useCartDispatch, which return useContext of each context. Components call them at their top level instead of importing the contexts.*
>
> Each custom Hook is one line, and it changes nothing on the page. It moves the last piece of wiring into the context file, so a component only says what it needs: the cart, or dispatch. The contexts no longer need export. A custom Hook runs inside the component that calls it, so it finds the closest provider above that component, and like any Hook it must be called at the top level.
>
> **DO THIS:**
> ```jsx
> function EmptyCartButton() {
>   const dispatch = ~useCartDispatch()~; // Custom Hook invoked at the top level of the component
>   return <button onClick={() => dispatch({ type: 'emptied' })}>Empty cart</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function EmptyCartButton() {
>   return <button onClick={() => ~useCartDispatch()~({ type: 'emptied' })}>Empty cart</button>; // Calling a Hook inside an event handler violates the Rules of Hooks
> }
> ```

Currently, consumer components import `useContext` and the context definitions directly. We can streamline this by wrapping each context lookup inside a custom hook:

```jsx title="Two custom hooks that read the context values"
export function ~useCart~() { // Returns the current cart array from the nearest provider
  return useContext(CartContext);
}

export function ~useCartDispatch~() { // Returns the dispatch function from the nearest provider
  return useContext(CartDispatchContext);
}
```

Components call these custom hooks directly:

```jsx title="Consuming dispatch with useContext compared to useCartDispatch"
const dispatch = ~useContext(CartDispatchContext)~; // Directly importing useContext and the context definition
const dispatch = ~useCartDispatch()~; // Calling the custom hook produces the exact same dispatch function
```

This helper function does not alter component rendering. It encapsulates context access in one place, allowing consumer components to remain focused on display logic.

> [!DEFINITION]
> **A custom Hook.** [NEW] A custom hook is a JavaScript function whose name begins with `use` and that calls other React hooks.
> `useCart` is not an API provided by React. It is our own one-line function that calls `useContext`.
> By prefixing the function name with `use`, React allows you to call standard hooks like `useContext` inside it.
> Even though `useCart` is defined in the context file, it executes inside the component that invokes it. When `Header` calls `useCart`, React looks upward from `Header` to locate the nearest provider.
> Lesson 39 explores custom hooks in full detail.

### Updating the Context File and Consumers

The context file imports `useContext`:

```jsx title="src/CartContext.jsx" startLine="1"
import { createContext, ~useContext~, useReducer } from 'react'; // useContext is imported for use inside the custom hooks
import cartReducer from './cartReducer.js';
```

We remove `export` from both context declarations. Consumer components no longer need direct access to the raw context objects:

```jsx title="src/CartContext.jsx" startLine="10"

const CartDispatchContext = createContext(null);
```

We export the two custom hooks at the bottom of the file:

```jsx title="src/CartContext.jsx" startLine="24"

  return useContext(CartContext);
}

export function useCartDispatch() {
  return useContext(CartDispatchContext);
}
```

Consumers now import the custom hooks. Both `Header` and the cart list call `useCart`:

```jsx title="src/components/Header.jsx"

  const cart = ~useCart()~; // Calls the custom hook to access cart data
  return (
    <header>
      <h1>Corner Shop</h1>
      <p>Cart: {cart.length} items</p>
    </header>
  );
}
```

Button components call `useCartDispatch`:

```jsx title="src/components/EmptyCartButton.jsx"

export default function EmptyCartButton() {
  const dispatch = ~useCartDispatch()~; // Calls the custom hook to access the dispatch function
  return <button onClick={() => dispatch({ type: 'emptied' })}>Empty cart</button>;
}
```

All state management and context access logic are now organized in a single file. Components specify what data they need without managing context references.

### Calling Hooks Inside Event Handlers

A mistake when learning custom hooks is calling them inside an event callback:

```jsx title="src/components/EmptyCartButton.jsx"
export default function EmptyCartButton() {
  return <button onClick={() => ~useCartDispatch()~({ type: 'emptied' })}>Empty cart</button>; // Calling a Hook inside an onClick handler is invalid
}
```

The page renders initially. When the user clicks Empty cart, React throws an invalid hook call error in the console.

Why does this fail? Because `useCartDispatch` calls `useContext`, it is a React hook. React rules dictate that hooks may only be called at the top level of a component during rendering (Lesson 38). Event handlers execute later, outside the render phase.

Always call custom hooks at the top level of your component function, and pass the returned `dispatch` function to your event handler.

The reducer function manages state transitions for all cart actions:

```jsx title="src/cartReducer.js"
export default function cartReducer(cart, action) {
  switch (action.type) {
    case 'increased': {
      return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity + 1 } : item);
    }
    case 'decreased': {
      return cart.map(item => item.id === action.id ? { ...item, quantity: item.quantity - 1 } : item).filter(item => item.quantity > 0);
    }
    case 'deleted': {
      return cart.filter(item => item.id !== action.id);
    }
    case 'emptied': {
      return [];
    }
    default: {
      throw Error('Unknown action: ' + action.type);
    }
  }
}
```

## For the Interview

> **The Interview Question:** How do you combine a reducer with context for app-wide state?

### How to Answer Clearly in 30 Seconds

"A reducer centralizes state update logic in one function, while context passes values deep down the component tree without prop drilling. To combine them for app-wide state, follow three steps:

1. **Create two separate contexts** using `createContext(null)`: one for the state and one for `dispatch`.
2. **Provide both values** in the component that calls `useReducer`, nesting one provider inside the other.
3. **Consume each context where needed**: display components read the state context, and interactive buttons read `dispatch` to send action objects.

The state still lives in React component state via `useReducer`. Context simply acts as the delivery mechanism. In production, I encapsulate this setup inside a provider component that renders `children`, and export two custom hooks like `useCart` and `useCartDispatch`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why two contexts instead of one context with `{ state, dispatch }`?"**
   Because the state and the `dispatch` function change at completely different rates. State updates create a new object or array reference on every dispatch. The `dispatch` function, by contrast, has a stable identity guaranteed by React across re-renders. If you bundle them into an object literal like `{ state, dispatch }`, a new object is created on every render. Because React compares context values using `Object.is`, every component subscribing to that context will re-render, even if it only needs `dispatch`. Using two contexts ensures components that only trigger actions do not re-render when state changes.

2. **"Does app-wide state mean global variables? Where does the state actually live?"**
   No. It is not a global variable. The state lives directly in the component that calls `useReducer`, such as `CartProvider`. Context is scoped to the component tree: a component reads the value of the nearest provider above it. If a component sits outside the provider, it receives the default value. Using `null` as the default ensures that accessing properties throws an immediate error in development. An application can have multiple independent reducer-context pairs for different sections of the tree.

3. **"When would you use a reducer with context instead of props?"**
   When many components at different nesting levels need to read or modify the same state, and the components in between only forward props. For simple trees with two or three levels, props are cleaner and easier to trace. Passing JSX as `children` can also flatten component hierarchy. Context does not replace local props: props specific to a single component, like item data in a list row, should remain props. Furthermore, `memo` does not prevent a context subscriber from re-rendering when the context value changes.

```tree caption="Interview summary: what each part of a reducer combined with context does."
A reducer combined with context
- +`useReducer` in `CartProvider` | **Holds the state** and gives **`cart`** and **`dispatch`** | The state **still lives here**
- +Two contexts, two providers [`CartContext` `CartDispatchContext`] | Deliver **`cart`** and **`dispatch`** separately | `dispatch` **never changes**, so its readers are not rendered again
- +Two custom Hooks [`useCart` `useCartDispatch`] | Read each context **at the top level** of a component | Components **never import the contexts**
```
