# 20. Controlled Inputs

> INTERVIEW QUESTION | ❱ CORE | How do you make an input, textarea, or select fully controlled by React state?

## Why a Form Needs Its Text in State

Imagine an online shop with a Contact Us page. A customer writes a question in the message box. Under the box, a small counter shows how many characters they have used out of 200. When they click `Send`, the form sends the message and empties every field so the page looks clean again.

That small form asks two things from its boxes at the same time:

1. **State must hear every key.** As the customer types into the message box, the counter under it must step from 0 out of 200 to 1, then 2, one key at a time.
2. **The box must obey state on every render.** When the customer clicks `Send` and our handler empties state, the box on screen must empty too, not just the counter under it.

In a normal browser page, an `<input>` or `<textarea>` keeps its typed text inside itself. JavaScript asks the box for that text only when the form is sent. In React, when the rest of the page depends on the text or needs to clear it, we move the text into state. Then we wire the box to state in both directions:

- `onChange` carries each key from the box into state.
- `value` carries state back into the box on every render.

A field wired with both is called a **controlled** input. Before we build the shop's contact form, let us look at that two-way loop in its smallest possible version.

### The smallest controlled box: a name, a greeting, and a Clear button

Here is one state variable `name`, one input box, one greeting line, and one `Clear` button:

```jsx title="The smallest controlled input"
import { useState } from 'react';

export default function GreetingBox() {
  const [name, setName] = ~useState('')~; // One state holds the text of the box

  return (
    <div>
      <input
        ~value={name}~ // State flows into the box on every render
        ~onChange={e => setName(e.target.value)}~ // Every key flows from the box into state
      />
      <p>Hello, {name}</p>
      <button onClick={() => ~setName('')~}>Clear</button> {/* Emptying state empties both */}
    </div>
  );
}
```

Take another look at the code for the Clear button. As always in React, the story starts with state. When the user clicks Clear, the button sets the `name` state to an empty string.

How do we connect that state to the input box? With `value={name}`. Because the box's value is locked to the `name` state, clearing the state clears the box.

Now look at the other direction. When the user types a letter into the box, how does the `name` state hear about it? Through `onChange`. On every key, `onChange` takes the new text from `e.target.value`. Then `setName` saves that text into the `name` state.

Put the two directions together and you get a **controlled** box:

1. `onChange` sends every key from the box into state.
2. `value` sends state back into the box on every render.

Think of a classroom whiteboard. A student calls out the next letter, which is `onChange`. Only the teacher writes on the board, which is `setName`. And the board shows only what the teacher has written, which is `value`. When the teacher wipes the board clean, both the box and the greeting become empty at once, because both read from that one state.

### Five Principles of Controlled Inputs

We will build the shop's Contact Us form one piece at a time across five principles:

**PRINCIPLES:**

1. **`onChange` sends every key into state.** On every key, `onChange` reads `e.target.value` from the box and saves it in state, so the live count updates as the user types.
2. **`value` sends state back into the box.** Passing `value={message}` locks the box to state. Emptying `message` on Send then clears both the box and the count.
3. **`value` without `onChange` freezes the box.** If you pass `value` and leave out `onChange`, React puts the old state text back after every key and prints a read-only error in the Console.
4. **A menu and a tick box use the same pair.** A drop-down menu takes `value` and `onChange` on the select tag. A tick box takes `checked` and reads `e.target.checked` for its true or false tick.
5. **A controlled box starts with an empty string.** Starting state with an empty string passes a real string from the first render. Starting with `undefined` flips the box from uncontrolled to controlled on the first key.

| # | Principle | Symptom | Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **`onChange` Sends Every Key into State** | The user types into the message box, and the character count under it stays frozen at 0 out of 200. | Give the field `onChange`, and save `e.target.value` into state on every key. |
| **Principle 2** | **`value` Sends State Back into the Box** | Clicking `Send` resets the count to 0 out of 200, while the old message text stays inside the box. | Give the field `value={message}` so the box always shows what state holds. |
| **Principle 3** | **`value` Without `onChange` Freezes the Box** | The user clicks into the Name box and types, nothing appears, and the Console prints a read-only field error. | Every controlled field with `value` needs an `onChange` that updates that state right away. |
| **Principle 4** | **`The Same Pair on a Menu and a Tick Box`** | A tick box ticks once and refuses to untick on the second click, or a menu prints a Console error about `selected`. | Control a `<select>` menu with `value` on the `<select>` tag, and control a tick box with `checked` and `e.target.checked`. |
| **Principle 5** | **`A Controlled Box Starts with an Empty String`** | Typing the first letter into the Email box prints a Console error about changing an uncontrolled input to be controlled. | Start a controlled text box with an empty string `''`, so `value` is a string from the very first render. |

## 1. Principle 1: `onChange` Sends Every Key into State

### Setting up the shop's Contact Us page

We start a small React project with four files: the HTML page, the entry script, the root `App` component, and the `ContactForm` component. Here are the first three files:

```html title="index.html"
<!DOCTYPE html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <title>Shop Contact Us</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>
```

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

```jsx title="src/App.jsx"
import ContactForm from './components/ContactForm.jsx';

export default function App() {
  return <ContactForm />;
}
```

Our first job on `ContactForm` is the message box and the live character count under it. As the customer types, the line under the box should count every character out of 200.

To make the count move while the user types, React gives every input and text area an `onChange` prop. React calls our `onChange` function each time the user changes the text in the box, on every key. Here is `ContactForm.jsx` with the message box and the count:

```jsx title="src/components/ContactForm.jsx — Message box with a live count"
import { useState } from 'react';

export default function ContactForm() {
  const [message, setMessage] = ~useState('')~; // State starts as an empty string

  function handleMessageChange(e) {
    ~setMessage(e.target.value)~; // Save the box's current text into state on every key
  }

  return (
    <form>
      <h1>Contact Us</h1>
      <label>
        Message
        <textarea
          placeholder="Write your question..."
          ~onChange={handleMessageChange}~ // React calls our handler on every keystroke
        />
      </label>
      <p>{~message.length~} / 200</p> {/* .length is the number of characters in the string */}
    </form>
  );
}
```

Look closely at the function inside `onChange`:

- In Lesson 11, you saw that React passes an event object `e` into your handler, and `e.target` points to the element where the event happened.
- Here, the event happened on the `<textarea>`, so `e.target` is that text box on the page.
- A text box in the browser keeps its current text in a property called `.value`. So `e.target.value` is simply the text inside the box right now.
- And `setMessage` is the normal state setter from Lesson 12. It saves that text into `message` and asks React to re-render the component so the counter updates on screen.

Notice the timing when the user presses a key. The count is never one letter behind:

1. The user presses a key in the message box.
2. The browser puts the new letter into the box first.
3. React calls `handleMessageChange` right after and hands it `e`.
4. `e.target` is the message box, and `e.target.value` reads its full text at that moment, with the new letter already inside.
5. `setMessage` saves that text in state.
6. React renders `ContactForm` again, and `message.length` shows the new count on screen.

When the page opens, the count under the box reads 0 out of 200. When the user types Hi, the count steps to 1 on `H` and 2 on `i`, with no message in the Console.

### React's `onChange` and the browser's `change` event are NOT the same

If you have written plain JavaScript before, the name `onChange` looks just like the browser's native `change` event. They do not fire at the same time:

- **In plain JavaScript**, a text box has two different events. The `change` event stays quiet while the user types and fires only when the user clicks outside the box. The `input` event fires on every key.
- **In React**, `onChange` is wired to behave like the browser's `input` event. It fires immediately on every key, paste, or cut, while the user is still inside the box.

That is why `message.length` updates on every letter instead of waiting for the user to leave the box.

### Mistake: keeping the message in a plain variable

A common first try is to keep `message` in a plain variable instead of state, and assign to it inside `onChange`:

```jsx title="src/components/ContactForm.jsx — Broken count with a plain variable"
export default function ContactForm() {
  ~let message = '';~ // **WRONG:** a plain variable forgets its text and never triggers a render

  function handleMessageChange(e) {
    ~message = e.target.value;~ // **WRONG:** changing a local variable does not re-render the page
  }

  return (
    <form>
      <h1>Contact Us</h1>
      <label>
        Message
        <textarea
          placeholder="Write your question..."
          onChange={handleMessageChange}
        />
      </label>
      <p>{message.length} / 200</p>
    </form>
  );
}
```

When the user types `Hi` into the box, the letters `Hi` appear inside the box, and the count below it stays stuck at 0 out of 200.

Why did the box update while the count froze? Because two different actors draw those two places on the page:

1. **The browser** draws the letters inside the `<textarea>` as the user types, without waiting for React.
2. **React** draws the paragraph with `message.length`, and React only redraws the page when a state setter such as `setMessage` is called.

Assigning to `let message` never asks React to render again, and on any later render that local variable starts over at an empty string. Switching back to `useState` and `setMessage` makes the count follow every letter.

### Inside the handler, `message` is still one letter behind

Inside `handleMessageChange`, two values sit right next to each other, and it is easy to confuse them:

```jsx title="Reading e.target.value vs. reading message inside the handler"
function handleMessageChange(e) {
  console.log(~e.target.value~); // The box's live text right now, including the new letter
  console.log(~message~); // **ONE LETTER BEHIND:** state from the render before this key
  setMessage(e.target.value);
}
```

- `e.target.value` reads the text from the browser's box right now, so it already includes the key the user just pressed.
- `message` is the state variable from the render before this key was pressed. As we saw in Lesson 15, calling `setMessage` prepares the *next* render and does not change `message` inside the current handler.

So inside that handler, any check on the new text must read `e.target.value` rather than `message`.

Notice also that we did not create a second state variable for the character count. We compute `message.length` during render from `message` itself. Why computed values should not live in their own state is the subject of Lesson 22.

Because `setMessage` runs on every key, `ContactForm` renders once per key. On a small form that is instant. If a text box ever sits inside a huge component tree that is slow to re-render, move the box and its state into its own small component. That keeps those keystroke re-renders inside that small component alone, and Lesson 68 will show `useDeferredValue` for keeping slow lists responsive while typing.

> [!PRINCIPLE]
>
> **Principle 1 — `onChange` Sends Every Key into State**
>
> *When the page must react to what the user types, give the field `onChange` and save `e.target.value` with the state setter.*
>
> React's `onChange` fires on every key, like the browser's `input` event. The browser puts the new character into the box first, so `e.target.value` already holds the updated text when your handler runs. Saving that string with `setMessage` triggers a re-render so the rest of the page updates with every letter.

## 2. Principle 2: `value` Sends State Back into the Box

### `defaultValue` vs. `value`: starting text vs. live state

React gives an input box two different props for its text:

- `defaultValue` sets **only the starting text** when the box first appears on screen. After that first moment, the box manages its own text inside the browser, and React never touches the box's text again. A box like this is called **uncontrolled**.
- `value` locks the box to **live state on every render**. After every render, React makes the box show whatever string is inside `value`. A box wired with `value` and `onChange` is called **controlled**. State becomes the **single source of truth** that both the box and the rest of the page read from.

Why do both exist? Because not every box needs React to control it after the page opens. If you just want a box to start with a pre-filled hint and let the browser handle the rest, `defaultValue` does that in one prop. When your code needs to clear or change the box from state, such as on a `Clear` button, you need `value`.

Let us put both kinds of box in the same component with one `Clear` button that resets `name` to an empty string:

```jsx title="Comparing defaultValue and value when Clear resets name"
import { useState } from 'react';

export default function TwoBoxes() {
  const [name, setName] = useState('');

  return (
    <div>
      <input
        ~defaultValue=""~ // Uncontrolled: only sets the starting text on the first render
        onChange={e => setName(e.target.value)}
      />
      <input
        ~value={name}~ // Controlled: React makes the box match name on every render
        onChange={e => setName(e.target.value)}
      />
      <p>Hello, {name}</p>
      <button onClick={() => ~setName('')~}>Clear</button> {/* Empties state */}
    </div>
  );
}
```

When you type John into either box, `onChange` updates `name`, and the greeting says Hello, John. Now click Clear:

- With `defaultValue=""`, the box and the state variable live **two separate lives**. `defaultValue` only set the box's text when the page first opened, and after that the browser took over the box. When Clear sets `name` to `''`, the greeting becomes empty, while the box ignores state and keeps showing John.
- With `value={name}`, the box has **no separate life of its own**. It is a live mirror of `name` on every render. When Clear sets `name` to `''`, both the greeting and the box become empty together.

Notice what that means for how we name a box. Having `onChange` does not make a box controlled. The first box above and our message box in Principle 1 both had `onChange`, yet both are uncontrolled because neither has `value`. It is `value` that locks the box to state.

Think of the difference between a student's own notebook and the classroom whiteboard. With `defaultValue`, the teacher writes a starting line on page one of the student's notebook and walks away. After that, the student writes in the notebook on their own, and erasing the whiteboard at the front of the room does not erase the notebook. With `value`, the text lives on the whiteboard itself. Every place on the page copies that one board, like station platform screens that all copy one master clock.

### Mistake: clearing state on `Send` while the box uses `defaultValue`

Now let us add the Send button to `ContactForm`. As we saw in Lesson 11, `onSubmit` on the form runs when the user clicks Send, and `e.preventDefault` stops the browser from reloading the page. Inside `handleSend`, we log the sent message and call `setMessage` with an empty string to clear the form.

Watch what happens if the developer gives the text area a starting `defaultValue=""` instead of `value={message}`:

```jsx title="src/components/ContactForm.jsx — Broken Send reset with defaultValue"
import { useState } from 'react';

export default function ContactForm() {
  const [message, setMessage] = useState('');

  function handleMessageChange(e) {
    setMessage(e.target.value);
  }

  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', message);
    ~setMessage('')~; // Empties state, but the uncontrolled box ignores state
  }

  return (
    <form onSubmit={handleSend}>
      <h1>Contact Us</h1>
      <label>
        Message
        <textarea
          placeholder="Write your question..."
          ~defaultValue=""~ // **WRONG:** only sets the starting text, never updates from state
          onChange={handleMessageChange}
        />
      </label>
      <p>{message.length} / 200</p>
      <button type="submit">Send</button>
    </form>
  );
}
```

The customer types a 19-character question, Where is my parcel?, into the box. While they type, `onChange` updates `message`, and the count climbs to 19 out of 200. Everything looks fine until they click Send:

1. `handleSend` logs the message in the Console and resets `message` to an empty string.
2. React renders `ContactForm` again with `message` set to an empty string.
3. The count under the box reads 0 out of 200, while the box above it still shows the old question.
4. If the customer clicks Send a second time because the text is still sitting in the box, the Console logs `Sent:` with an empty string. That happens because `message` in state is already `''`.

### Fixing the box with `value={message}`

Replace `defaultValue=""` with `value={message}`:

```jsx title="src/components/ContactForm.jsx — Controlled message box that clears on Send"
import { useState } from 'react';

export default function ContactForm() {
  const [message, setMessage] = useState('');

  function handleMessageChange(e) {
    setMessage(e.target.value);
  }

  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', message);
    ~setMessage('')~; // Emptying state now empties both the count and the box
  }

  return (
    <form onSubmit={handleSend}>
      <h1>Contact Us</h1>
      <label>
        Message
        <textarea
          placeholder="Write your question..."
          ~value={message}~ // Controlled: React writes message into the box on every render
          onChange={handleMessageChange}
        />
      </label>
      <p>{message.length} / 200</p>
      <button type="submit">Send</button>
    </form>
  );
}
```

Now when the customer types their question and clicks `Send`, the box and the count empty at the exact same moment. No code has to touch the DOM box directly.

You might wonder: if `value={message}` forces the box to match `message` after every render, why can the customer still type new letters into it? Walk through one key:

1. The customer presses a key, and the browser shows the new letter inside the box.
2. React calls `onChange` right away, and `setMessage` saves the updated text in state.
3. React renders `ContactForm` again, and `value={message}` is now that same updated text.
4. React writes that text into the box, so the new letter stays right where the customer typed it.

### Why HTML's `value` attribute became React's `defaultValue`

If you know plain HTML, you have already written `value` on an `<input>` before, and it did not lock the box. Why does `value` lock the box in React?

- **In HTML**, you write `value="John"` on an input, and `John` is only the starting text. The user can still type freely in the box.
- **In React**, you write `value="John"` on an input, and React treats `"John"` as the live text of the box on every render. The box is locked to `"John"`.

So that same `value="John"` prop means two different things. What HTML called `value`, React renamed to `defaultValue`. And React saved the short word `value` for the live text that controls the box on every render.

That is also why resetting state emptied the box when we used `value={message}`, and left the old question inside the box when we used `defaultValue=""`.

### How a `<textarea>` takes its text in React

In plain HTML, a `<textarea>` does not use a `value` attribute. Instead, you place its starting text between the opening and closing tags:

```html title="The plain HTML way on a text area"
<textarea>Hello</textarea>
```

In React, placing text between `<textarea>` tags is not supported and prints a red Console error. Instead, a text area in React works just like an input and takes `value` or `defaultValue`:

```jsx title="The React way on a text area"
<textarea ~value={message}~ onChange={handleMessageChange} /> {/* Controlled by state, just like an input */}
```

How to choose between controlled inputs and reading an uncontrolled form on submit with `FormData` is covered in Lesson 40.

> [!PRINCIPLE]
>
> **Principle 2 — `value` Sends State Back into the Box**
>
> *When your code must control what the box shows, pass `value={state}` together with `onChange`. Use `defaultValue` only when the box needs a starting string and React never needs to change it again.*
>
> Passing `value` makes the field controlled: after every render, React makes the box show whatever string is in `value`. State becomes the single source of truth that both the box and the rest of the UI copy. Emptying `message` on `Send` then clears the box and the character count together.

## 3. Principle 3: `value` Without `onChange` Freezes the Box

### The smallest version: why `value` alone locks the box

What happens if we give an input `value={name}` from state and forget to give it `onChange`? Here is the smallest case:

```jsx title="A box with value and no onChange"
import { useState } from 'react';

export default function FrozenBox() {
  const [name, setName] = useState('John');

  return <input ~value={name}~ />; // **WRONG:** value with no onChange locks the box to 'John'
}
```

When the page opens, the box shows `John`, and React prints a red error in the Console right away:

```
You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

Now click after `John` and press `n`. The box still shows `John`. Why did the letter vanish? Walk through what happened on that single key:

1. The browser puts `n` into the box, so for a split second the box holds `Johnn`.
2. The box has no `onChange`, so no handler runs, and state stays `'John'`.
3. React sees that the box no longer matches `value={name}` and immediately writes `'John'` back into the box.

Notice how different this is from an HTML `readOnly` attribute. On a `readOnly` box, the browser blocks typing at the keyboard. On a React box with `value` and no `onChange`, the browser accepts the key and React immediately overwrites the box back to the unchanged state. Think of our classroom whiteboard when the teacher has headphones on. A student calls out a new letter, the teacher never hears it, and the board stays as it was.

Look at the four ways you can write a box and what each one tells React:

```jsx title="Four ways to wire an input box"
<input ~value={name}~ ~onChange={e => setName(e.target.value)}~ /> {/* 1. Editable controlled box */}
<input ~value={name}~ /> {/* 2. **WRONG:** frozen box and red Console error */}
<input ~defaultValue={name}~ /> {/* 3. Editable uncontrolled box with starting text */}
<input ~value={name}~ ~readOnly~ /> {/* 4. Intentionally frozen display box, no error */}
```

1. **Both `value` and `onChange`**: an editable controlled box where every key updates state.
2. **`value` alone**: a frozen box and a red Console error, because state is locked to `'John'` with no way to change.
3. **`defaultValue` alone**: an editable uncontrolled box where `'John'` is only the starting text.
4. **`value` with `readOnly`**: a box meant to be read-only on purpose, which silences the Console error.

### Mistake: adding the `Name` box without `onChange`

Next on `ContactForm`, we add a Name box above the message box so the customer can tell us who is writing. Remembering Principle 2, the developer adds the `name` state, passes `value={name}` to the input, and leaves out the handler:

```jsx title="src/components/ContactForm.jsx — Frozen Name box without onChange"
import { useState } from 'react';

export default function ContactForm() {
  const [name, setName] = useState('');
  const [message, setMessage] = useState('');

  function handleMessageChange(e) {
    setMessage(e.target.value);
  }

  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, message);
    setName('');
    setMessage('');
  }

  return (
    <form onSubmit={handleSend}>
      <h1>Contact Us</h1>
      <label>
        Name
        <input
          placeholder="Your name"
          ~value={name}~ // **WRONG:** missing onChange freezes the box at ''
        />
      </label>
      <label>
        Message
        <textarea
          placeholder="Write your question..."
          value={message}
          onChange={handleMessageChange}
        />
      </label>
      <p>{message.length} / 200</p>
      <button type="submit">Send</button>
    </form>
  );
}
```

When the page opens, the Console prints the read-only field error. When the customer clicks into the Name box and types `Anna`, the box stays completely empty, because after every key React puts `''` back into the box.

### Fixing the `Name` box and enforcing the 200-character limit

First, we add `onChange` to the Name box so `Anna` appears letter by letter and the Console stays clean.

Second, we can put React's overwrite behavior to good use on the message box. Right now the counter shows the length out of 200, and nothing stops a customer from typing 250 characters. How do we cap the box at 200 characters? Inside `handleMessageChange`, we check that the new length is at most 200 before calling `setMessage`:

```jsx title="src/components/ContactForm.jsx — Working Name box and 200-character limit"
import { useState } from 'react';

export default function ContactForm() {
  const [name, setName] = useState('');
  const [message, setMessage] = useState('');

  function handleMessageChange(e) {
    if (~e.target.value.length <= 200~) { // Only update state when within the 200-character limit
      setMessage(e.target.value);
    }
  }

  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, message);
    setName('');
    setMessage('');
  }

  return (
    <form onSubmit={handleSend}>
      <h1>Contact Us</h1>
      <label>
        Name
        <input
          placeholder="Your name"
          value={name}
          ~onChange={e => setName(e.target.value)}~ // Every key now updates name in state
        />
      </label>
      <label>
        Message
        <textarea
          placeholder="Write your question..."
          value={message}
          onChange={handleMessageChange}
        />
      </label>
      <p>{message.length} / 200</p>
      <button type="submit">Send</button>
    </form>
  );
}
```

Watch what happens when the message box already holds 200 characters and the customer presses a 201st key:

1. The browser puts the 201st letter into the box.
2. React calls `handleMessageChange`. Because `e.target.value.length` is 201, the check is false, and the handler skips `setMessage`.
3. `message` in state still holds the first 200 characters, so React writes those 200 characters back into the box, and the 201st letter disappears.

### Why `onChange` must save `e.target.value` right away and as it is

Every controlled box needs its `onChange` handler to update state **right away** and to the **exact string** in `e.target.value`. Two common shortcuts break that rule.

First, delaying the state update inside a timer such as `setTimeout`:

```jsx title="Delaying the state update inside a timer"
function handleNameChange(e) {
  ~setTimeout~(() => setName(e.target.value), 100); // **WRONG:** state is still old when the handler finishes
}
```

When the user presses a key, `handleNameChange` starts a 100-millisecond timer and finishes right away without changing `name`. React sees that `name` has not changed when the handler finishes and immediately puts the old text back into the box.

Second, changing the string inside `onChange` before saving it, such as converting it with `toUpperCase`:

```jsx title="Changing the string inside onChange"
function handleNameChange(e) {
  setName(~e.target.value.toUpperCase()~); // **WRONG:** overwrites the box and jumps the cursor to the end
}
```

Suppose the user clicks into the middle of a word and types a lowercase letter. React overwrites the box with a brand-new uppercase string, so the browser loses the cursor position and jumps it to the end. One other bug can also make the cursor jump: destroying and recreating the input on every key. That happens when a parent passes a changing `key` or defines a component inside another component, as we saw in Lesson 04 and will study in Lesson 25.

> [!PRINCIPLE]
>
> **Principle 3 — `value` Without `onChange` Freezes the Box**
>
> *Whenever you pass `value` to a form field, also pass an `onChange` handler that updates that state right away.*
>
> Without `onChange`, state never changes, so React overwrites every key back to the old `value` and prints a read-only field error in the Console. If a box is meant to be uneditable on purpose, pass `readOnly` alongside `value`. If you want to reject certain keys, such as characters past 200, skip calling the state setter on those keys so React restores the last valid string.

## 4. Principle 4: The Same Pair on a Menu and a Tick Box

### How a drop-down menu works in React

In plain HTML, you mark the starting choice of a drop-down menu in a static way by writing `selected` on one `<option>`:

```html title="The static HTML way"
<select>
  <option value="apple">Apple</option>
  <option value="banana">Banana</option>
  <option value="orange" selected>Orange</option>
</select>
```

That `selected` attribute only sets the starting choice when the page first loads. In React, we need a dynamic way to control the menu from state. That way our code can change the selected option at any time, such as resetting the menu on Send.

So in React, `selected` on `<option>` is not supported and prints a red Console error:

```
Use the `defaultValue` or `value` props on <select> instead of setting `selected` on <option>.
```

Instead, React puts `value` and `onChange` on the select tag itself, using the exact same pair as a text input:

```jsx title="The dynamic React way"
const [fruit, setFruit] = useState('orange');

<select ~value={fruit}~ ~onChange={e => setFruit(e.target.value)}~> {/* Controlled by state */}
  <option value="apple">Apple</option>
  <option value="banana">Banana</option>
  <option value="orange">Orange</option>
</select>
```

Whatever string is inside `fruit`, React highlights the option with that `value`. When the user picks Banana from the menu, the handler runs with `e.target.value` set to `'banana'`. Then `setFruit` saves that new choice in state. If you ever need an uncontrolled menu that only sets a starting choice, pass `defaultValue="orange"` on the `<select>` tag. And if a menu ever uses `multiple={true}`, its `value` prop takes an array of option strings.

### How a tick box works in React

A text input and a drop-down menu both hold a string of text, so they use `value` and `e.target.value`:

```jsx title="A text box holds a string"
const [name, setName] = useState('');

<input ~value={name}~ onChange={e => setName(~e.target.value~)} /> {/* Reads and writes a string */}
```

A tick box does not hold text. It is either ticked or unticked, `true` or `false`. Because it holds a boolean instead of a string, React uses the word `checked` instead of `value`:

```jsx title="A tick box holds true or false"
const [agree, setAgree] = useState(false);

<input
  type="checkbox"
  ~checked={agree}~ // Shows the tick when agree is true
  onChange={e => setAgree(~e.target.checked~)} // Reads the new true or false tick from the box
/>
```

When `agree` is `true`, the box shows a tick. When `agree` is `false`, the box is empty. When the user clicks the box, `onChange` reads the new boolean from `e.target.checked` and saves it into state. For an uncontrolled tick box that only needs a starting tick, React provides `defaultChecked`.

### Adding the `Topic` menu to the contact form

On `ContactForm`, we now add two controls:

1. A Topic menu with three options: Delivery, Payment, and Other. It starts on `'delivery'` and resets back to `'delivery'` when the customer clicks Send.
2. An Email me a reply tick box, backed by a boolean state variable `wantsReply` that starts as `false`.

### Mistake: reading `e.target.value` on the tick box

When wiring the tick box, it is very easy to copy `e.target.value` from the text boxes above it instead of writing `e.target.checked`:

```jsx title="src/components/ContactForm.jsx — Tick box that ticks once and never unticks"
import { useState } from 'react';

export default function ContactForm() {
  const [name, setName] = useState('');
  const [topic, setTopic] = useState('delivery');
  const [message, setMessage] = useState('');
  const [wantsReply, setWantsReply] = useState(false);

  function handleMessageChange(e) {
    if (e.target.value.length <= 200) {
      setMessage(e.target.value);
    }
  }

  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', name, topic, message, wantsReply);
    setName('');
    setTopic('delivery');
    setMessage('');
    setWantsReply(false);
  }

  return (
    <form onSubmit={handleSend}>
      <h1>Contact Us</h1>
      <label>
        Name
        <input
          placeholder="Your name"
          value={name}
          onChange={e => setName(e.target.value)}
        />
      </label>
      <label>
        Topic
        <select ~value={topic}~ ~onChange={e => setTopic(e.target.value)}~> {/* Controlled select menu */}
          <option value="delivery">Delivery</option>
          <option value="payment">Payment</option>
          <option value="other">Other</option>
        </select>
      </label>
      <label>
        Message
        <textarea
          placeholder="Write your question..."
          value={message}
          onChange={handleMessageChange}
        />
      </label>
      <p>{message.length} / 200</p>
      <label>
        <input
          type="checkbox"
          ~checked={wantsReply}~ // Controlled by wantsReply
          onChange={e => ~setWantsReply(e.target.value)~} // **WRONG:** e.target.value on a checkbox is always 'on'
        />
        Email me a reply
      </label>
      <button type="submit">Send</button>
    </form>
  );
}
```

Try clicking the Email me a reply tick box in the browser:

- On the **first click**, the box ticks.
- On the **second click**, the box refuses to untick. It stays ticked no matter how many times you click it.

Why did the first click work and the second click fail? Walk through what the browser puts in `e.target.value` on a tick box:

1. Most tick boxes have no `value` attribute of their own. So the browser sets `e.target.value` to the fixed string `'on'`, which never changes when you click.
2. On the first click, `setWantsReply` saves the string `'on'`. Because `'on'` is a non-empty string, React treats `checked={wantsReply}` as true, and the box ticks.
3. On the second click, the customer tries to untick the box, and `e.target.value` is still `'on'`. So `wantsReply` stays `'on'`, and React puts the tick right back.

### Fixing the tick box with `e.target.checked`

Change `e.target.value` to `e.target.checked` in the tick box's handler:

```jsx title="src/components/ContactForm.jsx — Tick box reading e.target.checked"
      <label>
        <input
          type="checkbox"
          checked={wantsReply}
          onChange={e => ~setWantsReply(e.target.checked)~} // Reads true when ticked, false when unticked
        />
        Email me a reply
      </label>
```

Now the first click passes `true` and the second click passes `false`. Clicking Send resets `topic` to `'delivery'` and unticks the reply box.

> [!PRINCIPLE]
>
> **Principle 4 — The Same Pair on a Menu and a Tick Box**
>
> *Control a drop-down menu with `value` and `onChange` on the select tag. Control a tick box with `checked` and `e.target.checked`.*
>
> In plain HTML, you mark a starting option with `selected`, which is static and not supported in React. In React, `value` on the `<select>` tag dynamically selects whichever option matches your state variable. Because a tick box holds a boolean instead of text, it uses `checked` to display the tick and `e.target.checked` to read the new boolean. Reading `e.target.value` on a tick box always returns the fixed string `'on'`, trapping the box in the ticked state.

## 5. Principle 5: A Controlled Box Starts with an Empty String

### Starting with an empty string vs. starting with nothing

In React, an input must stay either uncontrolled or controlled for its entire life. It cannot start as one kind of box on the first render and switch to the other kind on a later render.

When a controlled text box starts empty, you pass an empty string `''` to `useState`:

```jsx title="Controlled from the first render"
const [city, setCity] = ~useState('')~; // Starts as an empty string '', so value is defined from render one

<input value={city} onChange={e => setCity(e.target.value)} />
```

Here `city` is the empty string `''` on the very first render. So `value={city}` passes a real string from the start, and the box is **controlled from render one**.

Watch what happens if you leave the parentheses of `useState` empty instead:

```jsx title="Uncontrolled on the first render, then flips on the first key"
import { useState } from 'react';

export default function CityBox() {
  const [city, setCity] = ~useState()~; // **WRONG:** starts as undefined, so the box starts uncontrolled

  return (
    <input
      ~value={city}~ // undefined on render 1, then 'a' on render 2
      onChange={e => setCity(e.target.value)}
    />
  );
}
```

When the page opens, both boxes look identical on screen: an empty text box. Now press a single key, `a`, inside `CityBox`. The letter `a` appears in the box, and React prints a red error in the Console:

```
A component is changing an uncontrolled input to be controlled. This is likely caused by the value changing from undefined to a defined value, which should not happen. Decide between using a controlled or uncontrolled input element for the lifetime of the component. More info: https://react.dev/link/controlled-components
```

Where did `undefined` come from when we never wrote the word `undefined`? Walk through what happened between the first render and the first key:

1. In JavaScript, calling `useState` with nothing between the parentheses passes `undefined` as the starting value. That means `city` starts as `undefined`.
2. On the first render, the input receives `value={undefined}`. To React, an `undefined` or `null` value is the same as passing no value prop at all, so React creates the box as an **uncontrolled** input.
3. When the user types a letter, `setCity` saves `'a'` into state.
4. On the second render, `value={city}` is now `'a'`. The very same box flips from **uncontrolled** to **controlled** in the middle of its life, and React prints the error.

### Mistake: adding the conditional `Email` box with empty `useState`

Now we add the final piece of `ContactForm`. When the customer ticks the reply checkbox, an `Email` box appears below it using `wantsReply && ...` from Lesson 10. Because the customer has not typed an email yet, the developer calls `useState` with no starting value:

```jsx title="src/components/ContactForm.jsx — Email state initialized with empty useState"
  const [name, setName] = useState('');
  const [topic, setTopic] = useState('delivery');
  const [message, setMessage] = useState('');
  const [wantsReply, setWantsReply] = useState(false);
  const [email, setEmail] = ~useState()~; // **WRONG:** email starts as undefined
```

And under the tick box:

```jsx title="src/components/ContactForm.jsx — Conditional Email box"
      {wantsReply && (
        <label>
          Email
          <input
            type="email"
            placeholder="you@example.com"
            ~value={email}~ // undefined when the box first appears, then a string on the first key
            onChange={e => setEmail(e.target.value)}
          />
        </label>
      )}
```

When the customer ticks the reply checkbox, the empty `Email` box appears on screen. The moment they type the first letter of their address, `a`, the Console prints the red error that an uncontrolled input is changing to be controlled.

### The finished `Contact Us` form

Passing an empty string `''` to `useState` gives the email state a string from its very first render. Here is the complete, finished `ContactForm` component:

```jsx title="src/components/ContactForm.jsx — Complete controlled Contact Us form"
import { useState } from 'react';

export default function ContactForm() {
  const [name, setName] = ~useState('')~; // Text input starts with ''
  const [topic, setTopic] = ~useState('delivery')~; // Select starts with one option's value
  const [message, setMessage] = ~useState('')~; // Textarea starts with ''
  const [wantsReply, setWantsReply] = ~useState(false)~; // Checkbox starts with a boolean
  const [email, setEmail] = ~useState('')~; // Conditional input also starts with ''

  function handleMessageChange(e) {
    if (e.target.value.length <= 200) {
      setMessage(e.target.value);
    }
  }

  function handleSend(e) {
    e.preventDefault();
    console.log('Sent:', { name, topic, message, wantsReply, email });
    ~setName('')~; // Reset every state back to its starting value
    ~setTopic('delivery')~; // Reset select back to 'delivery'
    ~setMessage('')~; // Reset textarea and character count
    ~setWantsReply(false)~; // Untick checkbox and hide Email box
    ~setEmail('')~; // Reset email to '', never null or undefined
  }

  return (
    <form onSubmit={handleSend}>
      <h1>Contact Us</h1>
      <label>
        Name
        <input
          placeholder="Your name"
          ~value={name}~ // Controlled by name
          onChange={e => setName(e.target.value)}
        />
      </label>
      <label>
        Topic
        <select
          ~value={topic}~ // Controlled by topic
          onChange={e => setTopic(e.target.value)}
        >
          <option value="delivery">Delivery</option>
          <option value="payment">Payment</option>
          <option value="other">Other</option>
        </select>
      </label>
      <label>
        Message
        <textarea
          placeholder="Write your question..."
          ~value={message}~ // Controlled by message
          onChange={handleMessageChange}
        />
      </label>
      <p>{message.length} / 200</p>
      <label>
        <input
          type="checkbox"
          ~checked={wantsReply}~ // Controlled by wantsReply
          onChange={e => setWantsReply(e.target.checked)}
        />
        Email me a reply
      </label>
      {wantsReply && (
        <label>
          Email
          <input
            type="email"
            placeholder="you@example.com"
            ~value={email}~ // Always a string from its first render
            onChange={e => setEmail(e.target.value)}
          />
        </label>
      )}
      <button type="submit">Send</button>
    </form>
  );
}
```

### `Send` clears the whole form with empty strings

Look at `handleSend` in the finished form. With every field controlled by state, resetting the entire form on `Send` takes five state setters and zero DOM code:

- `setName` and `setMessage` receive an empty string. Calling `setEmail` with an empty string empties the email box too, and the count returns to 0 out of 200.
- `setTopic` receives `'delivery'`, returning the menu to Delivery.
- `setWantsReply` receives `false`, unticking the checkbox and hiding the Email box again.

Notice that when resetting or loading data into a controlled text box, `value` must stay a string at that end of its life too:

```jsx title="Clearing a controlled box on Send or loading server data"
~setEmail('')~; // Keeps the box controlled with an empty string
~setEmail(undefined)~; // **WRONG:** flips a controlled box back to uncontrolled
<input ~value={user.email ?? ''}~ onChange={e => setEmail(e.target.value)} /> // Falls back to '' when user.email is null or undefined
```

Passing `undefined` or `null` to a state setter on Send flips a controlled box back into an uncontrolled one and triggers the same warning in reverse. Sometimes a box's value comes from a server object where a field is `null` or `undefined` at first. In that case, use JavaScript's `??` fallback operator from the third line above. It picks `''` whenever the left side is missing, so `value` is always a string. For a controlled checkbox, the same rule holds for booleans: `checked` must always receive a boolean value.

How to organize a form's overall status across typing, submitting, and success states is the subject of the next lesson, Lesson 21. Reading a field through a DOM ref is covered in Lessons 30 and 31. Passing field state up to a parent component is covered in Lesson 24, and linking labels and inputs by `id` with `useId` is covered in Lesson 52.

> [!PRINCIPLE]
>
> **Principle 5 — A Controlled Box Starts with an Empty String**
>
> *Always start the state of a controlled text field with an empty string `''`, never `undefined`.*
>
> In React, passing `value={undefined}` or `value={null}` makes an input uncontrolled. When the first key saves a string into state, the input switches from uncontrolled to controlled mid-life and React prints a Console error. Keep `value` a string and `checked` a boolean from the first render through every reset.

| # | Principle | Symptom | Fix |
| :--- | :--- | :--- | :--- |
| **1** | **`onChange` Sends Every Key into State** | Character count stays frozen at 0 out of 200 while typing. | Pass `onChange` and save `e.target.value` with `setMessage` on every key. |

| **5** | **`A Controlled Box Starts with an Empty String`** | First key logs `changing an uncontrolled input to be controlled`. | Start state with an empty string `''` and reset with `''`, never `undefined` or `null`. |

## For the Interview

> INTERVIEW QUESTION | ❱ CORE | How do you make an input, textarea, or select fully controlled by React state?

### The 30-Second Answer

To make an `<input>`, `<textarea>`, or `<select>` controlled, you wire it to a state variable in two directions:

1. **State into the field through `value`**: pass `value={state}` on `<input>`, `<textarea>`, and `<select>`, or `checked={state}` on checkboxes and radio buttons. After every render, React forces the DOM element to show that state value, making React state the single source of truth.
2. **Every user change back into state through `onChange`**: pass an `onChange` handler that synchronously updates that same state from `e.target.value`, or `e.target.checked` for a checkbox. In React, `onChange` fires on every key or selection change, like the browser's `input` event.

Always initialize a controlled text field with an empty string `''`, never `undefined` or `null`, so the field stays controlled for its entire lifetime. When you need to clear or reset the form, you simply reset the state variables to their starting values, and React updates every field on the next render.

### Common Follow-Up Questions

**1. "What is the difference between `value` and `defaultValue`?"**

- `defaultValue` and `defaultChecked` set **only the initial starting value** when the element first mounts. After that first render, the field is **uncontrolled**: the browser's DOM owns the live text, and React ignores any later changes to `defaultValue`.
- `value` and `checked` make the field **controlled**: React enforces that value on the DOM node after every single render. If you reset state to `''`, a controlled field with `value={name}` empties immediately, whereas an uncontrolled field with `defaultValue=""` keeps showing whatever the user typed.

**2. "What happens if you pass `value` without `onChange`, or if you start state with an empty `useState` call?"**

- **`value` without `onChange`**: the field becomes read-only. On every key, the browser inserts the character and React immediately reverts the DOM node back to the unchanged `value` from state. In development, React also prints a Console error telling you to add `onChange`, switch to `defaultValue`, or mark the field `readOnly`.
- **Starting with an empty `useState` call**: `state` starts as `undefined`, and passing `value={undefined}` makes the input start life **uncontrolled**. On the very first key, `onChange` sets state to a string, flipping the input from uncontrolled to controlled mid-life. React then logs the `"A component is changing an uncontrolled input to be controlled"` error, which you prevent by starting with `''` or `value={data ?? ''}`.

**3. "Why does the cursor sometimes jump to the end of a controlled input on every key?"**

- A controlled input's `onChange` handler must update state **synchronously** and to the **exact string** in `e.target.value`.
- If the handler delays the update inside `setTimeout`, React reverts the input before the timer runs. If the handler transforms the string on the way in, such as uppercasing it, React overwrites the box with a different string. The browser then loses the caret position and moves it to the end.
- A second cause is component identity, covered in Lesson 25. If a parent passes a changing `key` or defines a child component inside another component, the input unmounts and remounts on every key, losing focus and caret position.
