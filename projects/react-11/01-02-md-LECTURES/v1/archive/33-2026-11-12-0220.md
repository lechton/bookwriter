## How a Page Shows Data That Lives on a Server

### The answer comes later, and not always in order

When you open the team page of a work app and click a name, the page shows that person's bio under the buttons. The bio is not written in the code of the page. It lives on a server, and the page has to ask the server for it every time the user clicks a name. The page sends a **request**, and some time later the server sends back a **response** with the bio.

Two things follow from that "some time later", and they are the whole lesson:
1. **The page must show something while it waits.** React puts the page on the screen before the bio arrives, so the page needs a line for the time in between, such as `Loading...`, and a line for the case where the server fails.
2. **The answers do not always come back in the order the user clicked.** React's docs say it plainly: "network responses may arrive in a different order than you sent them."

```tree caption="What a page that loads data from a server must show, from the click to the answer."
From the click on a name to the bio on the page
- +While the page waits | The request is on its way | The page shows **`Loading...`**
- +When the server answers | The bio arrives | The page shows **the bio**
- !When the server fails | No bio arrives | The page shows **an error line**, not `Loading...` forever
```

### What is at stake

What is at stake is a page that shows the wrong person's details and gives no sign that anything is wrong. Here is how it happens on our team page:
1. The user clicks Bob. The server is slow to answer for Bob.
2. The user changes their mind at once and clicks Taylor.
3. Taylor's bio comes back first, and the page shows it.
4. Bob's bio comes back a moment later, and the page shows it in place of Taylor's.

The page now shows Taylor's name with Bob's bio under it. There is no error and no message in the Console. On the developer's fast machine, the answers always come back in order, so the developer never sees it. A user on a slow phone sees it often.

Readers usually go wrong in four places. They think the last click always gets the last answer. They write the request with no code that cleans up after it. They expect the request to fail when the server has a problem, and it does not. And when they learn to stop an old request, they show that stop to the user as an error.

### Two fixes that give the same page

Lesson 32 ended with a list of what each setup needs from its cleanup. One line of it belongs to this lesson: ""fetch" needs either "cancel" or "ignore"." So there are two fixes for the late answer, and Principles 3 and 4 show both:
- **Ignore the late answer**: the old request runs to the end, and the page drops what it brings.
- **Cancel the old request**: the browser stops the old request, so no answer comes at all.

It may look the same, or work the same at first, but it is NOT the same thing! Both fixes leave the right bio on the page. With the first, the server still does the work for Bob and sends his bio back for nothing. With the second, the browser stops waiting for Bob as soon as the user clicks Taylor.

### Our example page: a team page with three names

Our page has three buttons, Alice, Bob, and Taylor. Under them sit the name of the person chosen and one line for that person's bio. The page opens on Alice. Here is what the user does, and what each click should change:
1. The page opens. The line shows `Loading...`, then Alice's bio.
2. The user clicks Bob. The line shows `Loading...` for two seconds, because the server is slow for Bob, then Bob's bio.
3. The user clicks Bob and then Taylor at once. The page must end on Taylor's bio.

The server for this page answers at an address such as `/api/bio/Alice`. It sends back a short piece of text in **JSON**, the text format servers use to send data, such as `{ "bio": "This is Alice’s bio." }`. It answers in a fifth of a second for Alice and Taylor, and in two seconds for Bob, as in the React docs' own example of this page.

`App` keeps `person` in state and passes it to `Bio`:

```jsx title="src/App.jsx"
import { useState } from 'react';
import Bio from './components/Bio.jsx';

export default function App() {
  const [person, setPerson] = useState('Alice');

  return (
    <main>
      <button ~onClick={() => setPerson('Alice')}~>Alice</button> {/* Each click by the user sets person */}
      <button onClick={() => setPerson('Bob')}>Bob</button>
      <button onClick={() => setPerson('Taylor')}>Taylor</button>
      <h2>{person}</h2>
      ~<Bio person={person} />~ {/* Bio must show the bio of this person */}
    </main>
  );
}
```

At the start of the lesson, `Bio` only has a place for the bio:

```jsx title="src/components/Bio.jsx"
import { useState } from 'react';

export default function Bio({ person }) {
  const [bio, setBio] = useState(null);

  return <p>{~bio ?? 'Loading...'~}</p>; // bio is null, so the line shows Loading...
}
```

`bio` starts as `null`, because no bio has arrived yet. The `??` operator gives the value on its right when the value on its left is `null` or `undefined`, so the line shows `Loading...` while `bio` is `null`.

```page width=text caption="The team page when it opens: the line under Alice's name shows Loading... and never changes."
line: [Alice] [Bob] [Taylor]
heading: Alice
line: Loading...
console: quiet
```

Ten seconds later, the line still shows `Loading...`. No line of our code asks the server for anything.

The entry file, `main.jsx`, mounts `App` inside `<StrictMode>`, as in Lesson 07. Here is how the files sit in the project:

```files title="team-page: File Explorer" caption="How the team page project files sit inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it inside `<StrictMode>`
  App.jsx | parent | Keeps `person` in state, renders the three buttons, and passes `person` to `Bio`
  components/
    Bio.jsx | Effect | Keeps `bio` in state and, from Principle 1, asks the server for the bio of `person` in an Effect
```

### Four Principles of Fetching Data in an Effect

**PRINCIPLES:** A component that shows data from a server asks for it in an Effect, shows a line while it waits and a line when the server fails, and uses the cleanup so that an old answer never replaces a new one. Four principles follow from that:
1. **Principle 1: fetch Inside useEffect Loads the Bio**: The browser's `fetch` sends the request, and the answer arrives later. The request goes in an Effect that lists `person` in its array, and the line shows `Loading...` until the bio arrives.
2. **Principle 2: response.ok Turns a Server Error into the Error Line**: `fetch` fails only when it cannot reach the server. When the server answers with an error, the code must check `response.ok` and show the error line.
3. **Principle 3: The ignore Flag Drops Bob's Late Answer**: When the user clicks a new name before the old answer arrives, the old answer can arrive last. The cleanup marks the old request, and its answer is dropped.
4. **Principle 4: AbortController Stops Bob's Request**: With `fetch`, the cleanup can stop the old request itself. The stopped request fails with an `AbortError`, which is not an error for the user.

Here is the complete map of those four principles before we walk through each one:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |
| **Principle 1** | **fetch Inside useEffect Loads the Bio** | The bio arrives after React has put the page on the screen, so a page with no loading line shows nothing, and a request with the wrong array shows the wrong person. | Call `fetch` inside `useEffect`, list the props it reads, such as `[person]`, and show a loading line while the state is still `null`. |
| **Principle 2** | **response.ok Turns a Server Error into the Error Line** | `fetch` succeeds whenever the server answers, so without a check the page waits forever when the server fails. | Check `response.ok`, throw an error when it is `false`, and show the error line from `.catch`. |
| **Principle 3** | **The ignore Flag Drops Bob's Late Answer** | An old answer that arrives last replaces the new data, with no error, and only on slow networks. | Set an `ignore` flag in the cleanup, and set state only when the request's own flag is still `false`. |
| **Principle 4** | **AbortController Stops Bob's Request** | A stopped request reports an `AbortError`, and a `.catch` that shows every error puts the error line on a page that works. | Pass `controller.signal` to `fetch`, call `controller.abort` in the cleanup, and skip the `AbortError` in `.catch`. |

## 1. Principle 1: fetch Inside useEffect Loads the Bio

### fetch sends the request, and the answer comes later

The browser gives every page a function called `fetch`. It sends a request to an address on the server. Here are three lines that ask for Alice's bio and print it in the Console:

```jsx title="Asking the server for Alice's bio"
~fetch('/api/bio/Alice')~ // Sends the request and returns a promise at once
  .then(response => ~response.json()~) // When the server answers: reads the JSON
  .then(data => console.log(data.bio)); // Prints This is Alice’s bio.
```

`fetch` does not give back the bio on the same line. The bio is not there yet, because the server has not answered. So `fetch` gives back a **promise** at once: a JavaScript object that stands for a value that will arrive later. `.then` hands the promise a function to call when the value arrives:
1. `fetch` sends the request and returns a promise.
2. When the server answers, the browser creates a `response` object and passes it to the first function.
3. `response.json` reads the body of the response, the JSON text, and turns it into a JavaScript object. Reading takes time too, so it also returns a promise.
4. When the object is ready, the second function gets it as `data`, and `data.bio` is the bio.

The name `bio` comes from the server's JSON, `{ "bio": "This is Alice’s bio." }`, not from our state.

```tree dir=right caption="How the bio travels from the server to our code, one promise at a time."
From `fetch` to the bio
- +1. Send [`fetch`] | The browser **sends the request** | Our code gets a **promise** at once
- +2. Answer [`response`] | The server **answers**; the first `.then` runs | `response.json` **reads the JSON**
- +3. Data [`data.bio`] | The second `.then` runs | Our code has **the bio**
```

### Why the request goes in an Effect

The request must go out because `Bio` is on the screen and must show the bio of `person`. No click inside `Bio` causes it. This is the job of an Effect from Lesson 32: it keeps something outside React in step with the component. React's docs make the same point for a search page: the main reason to fetch is not the typing, but that "While this component is visible, you want to keep `results` synchronized with data from the network". Here, while `Bio` is visible, the bio on the line must match `person`.

So we move the request into `useEffect`, and the second `.then` puts the bio into state:

```jsx title="src/components/Bio.jsx" startLine="1"
import { useState, ~useEffect~ } from 'react'; // useEffect comes from react, as in Lesson 32

export default function Bio({ person }) {
  const [bio, setBio] = useState(null);

  useEffect(() => {
    ~setBio(null);~ // Shows Loading... again while the new bio is on its way
    fetch('/api/bio/' + person)
      .then(response => response.json())
      .then(data => ~setBio(data.bio)~); // The bio arrives, and React renders the line again
  }, ~[person]~); // The Effect reads person, so it runs again whenever person changes

  return <p>{bio ?? 'Loading...'}</p>;
}
```

The address is built from `person`, so the Effect reads `person`, and `person` goes in the array, as Lesson 32 taught. Each time the user clicks a name, `person` changes, and React runs the Effect again for the new name. Without the line that sets `bio` back to `null` at the top of the setup, the old bio would stay under the new name for as long as the new request takes.

The page opens on `Loading...`, and a fifth of a second later the line shows Alice's bio:

```page width=text caption="The team page a moment after it opens: the Effect has loaded Alice's bio."
line: [Alice] [Bob] [Taylor]
heading: Alice
line: This is Alice’s bio. | good
console: quiet
```

Then the user clicks Bob. For two seconds the line shows `Loading...`, and then Bob's bio:

```page width=text caption="The team page right after the user clicks Bob: Loading... for two seconds, while the server answers."
line: [Alice] [Bob] [Taylor]
heading: Bob
line: Loading...
console: quiet
```

This `Loading...` line is the **loading state**: what the component shows before the data arrives. Here it costs nothing extra: `bio` is `null` while we wait, and the JSX already shows `Loading...` for `null`.

### [person] and []

The array decides whether a click on a name brings a new bio. Compare the Effect with `[person]` and with `[]`:

```jsx title="The same Effect with [person] and with []"
useEffect(() => { /* fetch the bio of person */ }, ~[person]~); // Runs again after each click on a name
useEffect(() => { /* fetch the bio of person */ }, ~[]~); // **WRONG:** runs only on mount, so the page keeps Alice's bio
```

It may look the same, or work the same at first, but it is NOT the same thing! Both load Alice's bio when the page opens. With `[]`, React runs the Effect only on mount. The user clicks Bob, the name above the line changes to Bob, and the line keeps Alice's bio. The linter from Lesson 32 reports `person` as a missing dependency.

### Two requests in development

In development, the page sends two requests for Alice when it opens. This is the extra setup and cleanup that Strict Mode runs on mount, from Lesson 32: React runs the setup, the cleanup, and the setup again, and each setup sends a request. The docs: "**In development, you will see two fetches in the Network tab.** There is nothing wrong with that." The **Network tab** of the browser's developer tools lists every request the page sends. "**In production, there will only be one request.**" Our Effect has no cleanup yet, so both answers call `setBio` with the same bio, and the page looks right. Principle 3 adds the cleanup that the docs' sentence counts on.

> [!PRINCIPLE]
> **Principle 1: Fetching: fetch Inside useEffect Loads the Bio**
>
> *When a component must show data from the server for the props it has, it calls `fetch` inside `useEffect`, lists those props in the dependency array, and sets state when the answer arrives; while the state is still `null`, the JSX shows a loading line.*
>
> `fetch` sends the request and returns a promise, and the data arrives later, in `.then`. The request goes in an Effect because the data must match the props while the component is on the screen, not because of a click. The props in the address, such as `person`, go in the array, so a new name brings a new request.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   setBio(null);
>   fetch('/api/bio/' + person)
>     .then(response => response.json())
>     .then(data => setBio(data.bio));
> }, ~[person]~); // A new request each time the user clicks a name
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   fetch('/api/bio/' + person)
>     .then(response => response.json())
>     .then(data => setBio(data.bio));
> }, ~[]~); // **WRONG:** runs only on mount, so the line keeps Alice's bio after a click on Bob
> ```

## 2. Principle 2: response.ok Turns a Server Error into the Error Line

### fetch fails only when it cannot reach the server

Servers have bad moments. When something breaks on the server, it still answers, but with an error **status code**: a number such as `500` in place of the usual `200`. `fetch` treats that answer as a success. MDN, the reference for the web, says it plainly. The promise of `fetch` fails only when the request fails, for example because the address is badly formed or the network is lost. It does not fail when the server answers with a status code that means an error, such as `404` or `504`.

It may look the same, or work the same at first, but it is NOT the same thing! For the user, a broken server and a lost network are the same: no bio. For `fetch`, they are two different cases. With a lost network, the promise fails. With a broken server, the promise succeeds, and the answer holds the error.

### The server fails, and the page says Loading... forever

Say the server breaks while the user looks at Alice. It answers with status `500` and the JSON `{ "message": "Server error" }`. Our code from Principle 1 has no check, and the line shows `Loading...` with no end:
1. The setup sets `bio` to `null`, and the line shows `Loading...`.
2. The server answers with status `500`.
3. `fetch` succeeds, because the server answered.
4. `response.json` gives `{ message: 'Server error' }`, which has no `bio`, so `data.bio` is `undefined`.
5. `setBio` puts `undefined` in `bio`, and `??` shows `Loading...` for `undefined` too.

```page width=text caption="The team page when the server answers with status 500 and the code has no check: Loading... with no end."
line: [Alice] [Bob] [Taylor]
heading: Alice
line: Loading... | bad
console: Failed to load resource: the server responded with a status of 500 (Internal Server Error)
console: Failed to load resource: the server responded with a status of 500 (Internal Server Error)
```

The user waits for a bio that will never come, and nothing on the page says why. The only sign is in the Console, where the browser prints its own line about the status, once for each of the two requests that development sends. Our code never reads that status.

### Checking response.ok and showing the error line

The `response` object says whether the status is good. `response.ok` is `true` for a status from `200` to `299`, and `false` otherwise. `response.status` holds the number itself. When `response.ok` is `false`, our code turns the answer into an error with `throw new Error`. A `throw` inside `.then` makes the promise fail, so the next `.then` is skipped, and the function in `.catch` runs with the error. The text in the error, such as `Status 500`, is for the developer who inspects the error. The user sees only the error line.

We keep the error in a second state variable, `error`, and the JSX checks it first:

```jsx title="src/components/Bio.jsx" startLine="3" good="10,11,12,17"
export default function Bio({ person }) {
  const [bio, setBio] = useState(null);
  const [error, setError] = useState(null);

  useEffect(() => {
    setBio(null);
    ~setError(null);~ // Clears an old error before each new request
    fetch('/api/bio/' + person)
      .then(response => {
        if (~!response.ok~) { // Status 500: the server answered with an error
          throw new Error('Status ' + response.status); // Skips the next then and goes to catch
        }
        return response.json();
      })
      .then(data => setBio(data.bio))
      ~.catch(err => setError(err));~ // Keeps the error, and React shows the error line
  }, [person]);

  if (error) {
    return <p>Could not load the bio.</p>;
  }
  return <p>{bio ?? 'Loading...'}</p>;
}
```

Now the same broken server gives the user an answer:

```page width=text caption="The team page when the server answers with status 500 and the code checks response.ok: the error line."
line: [Alice] [Bob] [Taylor]
heading: Alice
line: Could not load the bio. | good
console: Failed to load resource: the server responded with a status of 500 (Internal Server Error)
console: Failed to load resource: the server responded with a status of 500 (Internal Server Error)
```

The browser still prints its line about the status in the Console, because the server did answer with `500`. The difference is on the page: the user now knows the bio is not coming. The same `.catch` also runs when the network is lost, because then the `fetch` promise itself fails. So one error line covers both cases.

The line that sets `error` back to `null` at the top of the setup matters as much as the check. Without it, the error stays in state after the user clicks another name. The new bio loads into `bio`, but the JSX checks `error` first, so the user still sees `Could not load the bio.` under a name whose bio loaded fine.

The page now has three states for the line: the **loading state**, `Loading...`, while `bio` is `null`; the **error state**, the error line, while `error` holds an error; and the bio itself. Each new request starts from the loading state, with both the old bio and the old error cleared.

> [!PRINCIPLE]
> **Principle 2: Errors: response.ok Turns a Server Error into the Error Line**
>
> *`fetch` fails only when the request cannot reach the server; when the server answers with an error status such as `500`, the promise succeeds, so the code checks `response.ok`, throws an error when it is `false`, and shows the error line from `.catch`.*
>
> Without the check, the error answer goes on to `response.json`, the bio is `undefined`, and the page shows `Loading...` forever. With it, the error goes to `.catch`, the component keeps it in state, and the user sees an error line. Each new request clears the old error, so one bad answer does not stay on the page.
>
> **DO THIS:**
> ```jsx
> fetch('/api/bio/' + person)
>   .then(response => {
>     if (~!response.ok~) throw new Error('Status ' + response.status); // The error goes to catch
>     return response.json();
>   })
>   .then(data => setBio(data.bio))
>   .catch(err => setError(err));
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> fetch('/api/bio/' + person)
>   .then(response => ~response.json()~) // **WRONG:** a status 500 answer is read as a bio, and the page says Loading... forever
>   .then(data => setBio(data.bio));
> ```

## 3. Principle 3: The ignore Flag Drops Bob's Late Answer

### Bob's late answer replaces Taylor's bio

Here is the code from Principle 2, with no cleanup, and two quick clicks by the user. The page ends on Bob's bio under Taylor's name:
1. The user clicks Bob. `person` becomes `'Bob'`, and the Effect sends the request for Bob, which the server answers after two seconds. The line shows `Loading...`.
2. Half a second later, the user clicks Taylor. The Effect sends the request for Taylor, which the server answers after a fifth of a second.
3. Taylor's answer arrives first. `setBio` puts Taylor's bio on the line.
4. Bob's answer arrives more than a second later. Its `.then` still runs, because nothing told it that the user moved on, and `setBio` puts Bob's bio on the line.

```page width=text caption="The team page three seconds after the user clicks Bob and then Taylor, with no cleanup: Bob's bio under Taylor's name."
line: [Alice] [Bob] [Taylor]
heading: Taylor
line: This is Bob’s bio. | bad
console: quiet
```

This is a **race condition**. React's docs define it: "two different requests "raced" against each other and came in a different order than you expected." There is no error, and the Console is quiet. On a fast network the answers come back in order, so the bug shows up only for some users.

### The ignore flag

The docs' fix uses the cleanup from Lesson 32. Each run of the setup creates its own variable, `ignore`, set to `false`. The cleanup of that run sets it to `true`. The answer sets state only while `ignore` is still `false`. The docs show it with a function of their own, `fetchBio`, which returns a promise of the bio, as `fetch` does:

```jsx title="The docs' ignore flag, with their fetchBio function"
useEffect(() => {
  ~let ignore = false;~ // This run's own flag
  fetchBio(person).then(result => {
    if (~!ignore~) { // Only while this run is still the current one
      setBio(result);
    }
  });
  return () => {
    ~ignore = true;~ // The cleanup marks this run's answer as one to drop
  };
}, [person]);
```

The docs: "Note the `ignore` variable which is initialized to `false`, and is set to `true` during cleanup." The cleanup knows which `ignore` to change because it is created inside the same run of the setup, as the cleanup in Lesson 32 knew which `intervalId` to stop. Each run has its own `ignore`, and its own cleanup that changes only that one.

### The ignore flag in Bio

In `Bio`, the flag guards both setters, so a late error is dropped too:

```jsx title="src/components/Bio.jsx" startLine="7" good="8,18,19,22,23,24"
  useEffect(() => {
    ~let ignore = false;~ // Each run of the setup gets its own flag
    setBio(null);
    setError(null);
    fetch('/api/bio/' + person)
      .then(response => {
        if (!response.ok) {
          throw new Error('Status ' + response.status);
        }
        return response.json();
      })
      .then(data => { if (!ignore) setBio(data.bio); }) // Only the current request sets the bio
      .catch(err => { if (!ignore) setError(err); }); // Only the current request sets the error
    return () => {
      ~ignore = true;~ // Runs when person changes: the old answer will be dropped
    };
  }, [person]);
```

Here are the same two clicks with the flag:
1. The user clicks Bob. The Bob run of the setup sends the request for Bob, with its own `ignore` at `false`.
2. The user clicks Taylor. Before the new setup, React runs the cleanup of the Bob run, so the Bob run's `ignore` becomes `true`. Then the Taylor run sends the request for Taylor.
3. Taylor's answer arrives. The Taylor run's `ignore` is `false`, so the line shows Taylor's bio.
4. Bob's answer arrives. The Bob run's `ignore` is `true`, so `setBio` is skipped.

```page width=text caption="The team page three seconds after the user clicks Bob and then Taylor, with the ignore flag: Taylor's bio under Taylor's name."
line: [Alice] [Bob] [Taylor]
heading: Taylor
line: This is Taylor’s bio. | good
console: quiet
```

The docs say the same of two users named Alice and Bob: "cleanup ensures that the `'Alice'` response is ignored even if it arrives after `'Bob'`." It may look the same, or work the same at first, but it is NOT the same thing! When the user clicks one name and waits, the code with the flag and the code with no cleanup give the same page. They part only when the user clicks a second name before the first answer arrives.

The same flag explains the docs' sentence about development from Principle 1. When the page opens, Strict Mode runs the setup, the cleanup, and the setup again. The cleanup sets the first run's `ignore` to `true`, so the first request still goes out, but its answer is dropped. The docs: "even though there is an extra request, it won't affect the state", because the check on `ignore` drops its answer.

The flag works for any promise, not only `fetch`. The docs' `fetchBio` is not `fetch` at all. But with the flag, Bob's request still runs to the end, and the server still sends his bio for nothing. Principle 4 stops the request itself.

> [!PRINCIPLE]
> **Principle 3: Race Conditions: The ignore Flag Drops Bob's Late Answer**
>
> *When the user clicks a new name before the old answer arrives, the old answer can arrive last and replace the new bio; the cleanup sets `ignore` to `true`, and the old setup only sets state when its own `ignore` is still `false`.*
>
> The network answers in its own order, not in the order the user clicked. Each run of the setup has its own `ignore`, and React runs the old run's cleanup before the new setup, so every answer except the last one requested is dropped. The bug shows no error, so the flag goes in every fetch Effect, not only after a user reports it.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   let ignore = false;
>   fetch('/api/bio/' + person)
>     .then(response => response.json())
>     .then(data => { ~if (!ignore)~ setBio(data.bio); }); // Only the current request sets the bio
>   return () => { ignore = true; };
> }, [person]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   fetch('/api/bio/' + person)
>     .then(response => response.json())
>     .then(data => ~setBio(data.bio)~); // **WRONG:** Bob's late answer replaces Taylor's bio
> }, [person]);
> ```

## 4. Principle 4: AbortController Stops Bob's Request

### Stopping a request with AbortController

The browser has a tool that stops a `fetch` before it finishes: the `AbortController`. MDN describes it as "a controller object that allows you to abort one or more Web requests as and when desired." It works in three steps:

```jsx title="Stopping a request with AbortController"
const controller = ~new AbortController()~; // 1. Creates the controller
fetch('/api/bio/Bob', { ~signal: controller.signal~ }); // 2. Gives fetch the controller's signal
~controller.abort();~ // 3. Stops the request
```

`controller.signal` is the part of the controller that `fetch` listens to. We hand it to `fetch` in the second argument, `{ signal: controller.signal }`. When our code calls `controller.abort`, the browser stops the request, and the `fetch` promise fails. MDN says that when `abort` is called, the promise of `fetch` fails with a `DOMException` named `AbortError`. A `DOMException` is the kind of error object the browser itself creates. So the error that reaches `.catch` has the name `'AbortError'`, and our code reads it in `err.name`.

### The ignore flag and abort

Here are the two cleanups side by side:

```jsx title="The cleanup with the ignore flag, and with abort on the controller"
return () => { ~ignore = true;~ }; // Bob's request runs to the end, and its answer is dropped
return () => ~controller.abort()~; // Bob's request is stopped, and no answer comes
```

It may look the same, or work the same at first, but it is NOT the same thing! After the user clicks Bob and then Taylor, both cleanups leave Taylor's bio on the page. With the `ignore` flag, the browser still waits for Bob's answer and reads it, and our code drops it. With `controller.abort`, the browser cancels Bob's request when the user clicks Taylor, and stops waiting for it.

React's docs leave the choice open: the cleanup "should either abort the fetch or ignore its result". `abort` saves the network and the reading of an answer nobody needs. The flag works for any promise, even one that cannot be stopped.

### The abort reaches .catch

A developer replaces the flag with a controller and keeps the `.catch` from Principle 2. In development, the page opens on the error line:

```page width=text caption="The team page when it opens in development, with abort in the cleanup and a catch that keeps every error: the error line."
line: [Alice] [Bob] [Taylor]
heading: Alice
line: Could not load the bio. | bad
console: quiet
```

The page works, the server works, and yet the user reads that the bio could not be loaded. Here is why:
1. React mounts `Bio` and runs the setup. It creates the first controller, sends the first request for Alice, and sets `error` to `null`.
2. Strict Mode runs the cleanup. `controller.abort` stops the first request.
3. Strict Mode runs the setup again. It creates a second controller, sends the second request, and sets `error` to `null`.
4. The first request's promise fails with an `AbortError`. A promise never calls its functions in the middle of other code: it waits until the code that is running now has finished. React runs the setup, the cleanup, and the second setup in one go, so this `.catch` runs after the second setup, and `setError` keeps the `AbortError`.
5. The second request brings Alice's bio, and `setBio` sets it. But `error` is not `null`, and the JSX checks `error` first.

The same thing happens in production when the user clicks Bob and then Taylor: the cleanup stops Bob's request, its `AbortError` reaches `.catch`, and the user sees the error line under Taylor's name.

An `AbortError` is not something that went wrong. It is our own cleanup doing its job. So `.catch` skips it and keeps every other error:

```jsx title="Skipping the AbortError in catch"
.catch(err => {
  if (~err.name === 'AbortError'~) return; // Our own cleanup stopped this request: nothing to show
  setError(err); // A real error: show the error line
});
```

### The final Bio

Here is `Bio` with the controller in place of the flag:

```jsx title="src/components/Bio.jsx" startLine="7" good="8,12,19,20,23"
  useEffect(() => {
    const ~controller~ = new AbortController(); // A new controller for each run of the setup
    setBio(null);
    setError(null);
    fetch('/api/bio/' + person, { ~signal: controller.signal~ }) // fetch listens to this run's controller
      .then(response => {
        if (!response.ok) {
          throw new Error('Status ' + response.status);
        }
        return response.json();
      })
      .then(data => setBio(data.bio))
      .catch(err => {
        if (err.name === 'AbortError') return; // Skips the request our cleanup stopped
        setError(err);
      });
    return () => ~controller.abort()~; // Stops this run's request when person changes or Bio unmounts
  }, [person]);
```

The setup creates a new controller on every run, because a signal works only once. MDN: "An `AbortSignal` can only be used once." The cleanup sees the controller of its own run, so it stops only that run's request.

Now the page opens on Alice's bio, in development too. When the user clicks Bob and then Taylor, the cleanup stops Bob's request, its `AbortError` is skipped, and the page ends on Taylor's bio:

```page width=text caption="The finished team page after the user clicks Bob and then Taylor: Bob's request was stopped, and the line shows Taylor's bio."
line: [Alice] [Bob] [Taylor]
heading: Taylor
line: This is Taylor’s bio. | good
console: quiet
```

The cleanup also runs when `Bio` leaves the page, as Lesson 32 showed. If the user leaves the team page while a bio is still loading, the cleanup stops that request too.

> [!PRINCIPLE]
> **Principle 4: Aborting: AbortController Stops Bob's Request**
>
> *With `fetch`, the cleanup can stop the old request: the setup creates an `AbortController`, passes `controller.signal` to `fetch`, and the cleanup calls `controller.abort`; the stopped `fetch` fails with an `AbortError`, which `.catch` must skip, because it is not an error for the user.*
>
> The `ignore` flag lets the old request finish and drops its answer. `controller.abort` stops the old request, so no answer comes, and the browser does not wait for it. The stop itself makes the promise fail, so `.catch` checks `err.name` and shows the error line only for a real error.
>
> **DO THIS:**
> ```jsx
> const controller = new AbortController();
> fetch('/api/bio/' + person, { signal: controller.signal })
>   .then(response => response.json())
>   .then(data => setBio(data.bio))
>   .catch(err => { ~if (err.name === 'AbortError') return;~ setError(err); }); // Skips our own stop
> return () => controller.abort();
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const controller = new AbortController();
> fetch('/api/bio/' + person, { signal: controller.signal })
>   .then(response => response.json())
>   .then(data => setBio(data.bio))
>   ~.catch(err => setError(err));~ // **WRONG:** our own stop shows the error line on a page that works
> return () => controller.abort();
> ```

### The complete team page project

Here are the three files of our finished team page. The entry file mounts `App` inside `<StrictMode>`:

```jsx title="src/main.jsx"

import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
```

`App` keeps the chosen person and passes it to `Bio`:

```jsx title="src/App.jsx"
import { useState } from 'react';
import Bio from './components/Bio.jsx';

export default function App() {
  const [person, setPerson] = useState('Alice');

  return (
    <main>
      <button onClick={() => setPerson('Alice')}>Alice</button>
      <button onClick={() => setPerson('Bob')}>Bob</button>
      <button onClick={() => setPerson('Taylor')}>Taylor</button>
```

`Bio` asks the server for the bio, shows a line for each state, and stops the old request in the cleanup:

```jsx title="src/components/Bio.jsx"
import { useState, useEffect } from 'react';

export default function Bio({ person }) {
  const [bio, setBio] = useState(null);
  const [error, setError] = useState(null);

  useEffect(() => {
    const controller = new AbortController();
    setBio(null);
    setError(null);
    ~fetch~('/api/bio/' + person, { signal: controller.signal }) // Principle 1: the request goes in an Effect
      .then(response => {
        if (~!response.ok~) { // Principle 2: a server error goes to catch
          throw new Error('Status ' + response.status);
        }
        return response.json();
      })
      .then(data => setBio(data.bio))
      .catch(err => {
        if (~err.name === 'AbortError'~) return; // Principle 4: our own stop is not an error
        setError(err);
      });
    return () => ~controller.abort()~; // Principles 3 and 4: the old request never sets state
  }, ~[person]~); // Principle 1: runs again whenever person changes

  if (error) {
    return <p>Could not load the bio.</p>;
  }
  return <p>{bio ?? 'Loading...'}</p>;
}
```

The user opens the page, clicks Bob, and clicks Taylor half a second later:

```page width=text caption="The finished team page after the user clicks Bob and then Taylor: Taylor's name and Taylor's bio."
line: [Alice] [Bob] [Taylor]
heading: Taylor
line: This is Taylor’s bio. | good
console: quiet
```

### How React calls the components and runs the Effect

When the user clicks Taylor, React calls `App`, then `Bio`, and commits the new name with the old bio still in state. Then it runs the old cleanup and the new setup, and the answer arrives last:

```tree dir=right caption="The order of events from the click on Taylor to Taylor's bio on the page."
From the click on Taylor to Taylor's bio
- +1. Render [`App` `Bio`] | React calls `App`, then `Bio`, with `person` set to Taylor | `Bio` **hands React the new setup**
- +2. Commit [`<h2>Taylor</h2>`] | React puts **Taylor's name** into the DOM | The line still shows the old text
- +3. Cleanup [`controller.abort`] | React runs **the Bob run's cleanup** | Bob's request **stops**
- +4. Setup [`fetch`] | React runs **the Taylor run's setup** | The line shows **`Loading...`**; the request goes out
- +5. Answer [`setBio`] | Taylor's bio **arrives** | React renders the line with **Taylor's bio**
```

| What the Effect does | What the user sees | Why |
| :--- | :--- | :--- |
| **Fetches with `[]`** | The line keeps Alice's bio after a click on Bob | The Effect runs only on mount |
| **Fetches with `[person]` and no `response.ok` check** | `Loading...` forever when the server fails | `fetch` succeeds whenever the server answers, and the bio is `undefined` |
| **Checks `response.ok`, with no cleanup** | Bob's bio under Taylor's name after two quick clicks | Bob's late answer still calls `setBio` |
| **Uses the `ignore` flag** | Taylor's bio | Bob's answer arrives and is dropped |
| **Uses `controller.abort`, and `.catch` keeps every error** | The error line on a page that works | The `AbortError` of the stopped request reaches `setError` |
| **Uses `controller.abort` and skips the `AbortError`** | Taylor's bio | Bob's request is stopped, and only real errors show |

## For the Interview

> **The Interview Question:** How do you fetch data from an API in a client component, and how do you handle loading, error, and race conditions?

### How to Answer Clearly in 30 Seconds

"I call `fetch` inside `useEffect`, because the data must match the props while the component is on the screen, and I list the props the request reads, such as `[person]`. The data arrives later, in `.then`, so the component has three states: loading, error, and data. Three rules keep it right:
1. **Loading**: the state starts at `null`, the JSX shows a loading line for `null`, and each new request sets it back to `null`.
2. **Errors**: `fetch` fails only when it cannot reach the server, so I check `response.ok`, throw an error when it is `false`, and keep the error in state from `.catch`.
3. **Race conditions**: answers can come back in a different order than I sent the requests. The cleanup either sets an `ignore` flag so that the old answer is dropped, or calls `abort` on an `AbortController` so that the old request stops. With `abort`, `.catch` skips the `AbortError`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does my page send every request twice in development?"**
   In development, Strict Mode runs the setup, the cleanup, and the setup again when the component mounts, so two requests go out. The docs: "There is nothing wrong with that." With a cleanup, the first request's answer is dropped or its request is stopped, so it does not change the state. "**In production, there will only be one request.**" The fix is never to block the second run. It is a cleanup that makes the two runs look like one to the user.
2. **"What about the warning "Can't perform a React state update on an unmounted component"?"**
   React 18 removed it. The upgrade guide: React "warned about memory leaks when you call `setState` on an unmounted component", but "people primarily run into it in scenarios where setting state is fine, and workarounds make the code worse." React 19 prints nothing when a late answer sets state on a component that is gone. The cleanup still matters, because it keeps a late answer from replacing the current data, and with `abort` it stops requests nobody needs.
3. **"Would you write fetch in an Effect in a real app?"**
   The docs call it "a very manual approach", for three reasons. Effects do not run on the server, so the first HTML shows only the loading state. A parent and a child that each fetch one after the other create "network waterfalls". And nothing is cached, so a component that mounts again fetches again. The docs recommend the data fetching of a framework, or a client-side cache such as TanStack Query or useSWR, which Lesson 60 compares. Without those, the fetch Effect can go into a custom Hook, such as the docs' `useData`, which Lesson 39 teaches. React 19's `use` with Suspense is Lesson 71, and Server Components are Lesson 101.

```tree dir=right caption="Interview comparison: what each part of a fetch Effect protects the user from."
What each part of a fetch Effect protects
- +The array [`[person]`] | A new prop brings **a new request** | The page never keeps **the old person's data**
- +The loading and error states [`response.ok` `.catch`] | The page always shows **one answer**: loading, error, or data | The user never waits for **a bio that will not come**
- +The cleanup [`ignore` `abort`] | Every answer except **the last one requested** is dropped or stopped | The page never shows **the wrong person's data**
```
