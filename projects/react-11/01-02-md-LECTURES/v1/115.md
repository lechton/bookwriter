# Lecture 115: How a Server Page Hands Finished Slides to a Client Carousel

*(How does a Client Component show a slide that only the server can make?)*

> INTERVIEW QUESTION | ❱ CORE | How do you pass server-rendered children into a Client Component?

---

## VS | Importing the Slide in the Client File vs. Passing It as JSX in a Prop: only the prop keeps the slide on the server

> A reviews carousel needs a `Next` button, which works only in the browser, and slides with reviews, which only the server can read from the database. **A Client Component never imports a Server Component, but it can still show one: the Server Component above it writes the tag and passes it in a prop**. The Client Component receives only the finished slide, so the slide's code and the database never leave the server.

Remember how a carousel worked before React. The server read the reviews from the database and printed three `<div class="slide">` elements into the HTML. Then a small script in the browser showed one of them at a time. The script never touched the database. It only moved between slides that the server had already made:

```js title="Plain JavaScript: the server already wrote the three slides into the HTML"
const slides = ~document.querySelectorAll('.slide')~; // The three slides the server printed into the page
let index = 0;
nextButton.addEventListener('click', () => {
  slides[index].hidden = true;
  index = (index + 1) % slides.length;
  ~slides[index].hidden = false~; // Shows the next slide: no trip to the database
});
```

React does the same split, with components. The slide is a Server Component: it runs on the server and reads the database. The carousel is a Client Component: it runs in the browser and keeps in state the number of the slide on screen. The page, also a Server Component, puts the slide into the carousel:

```jsx title="App.jsx, a Server Component" startLine="1"
import Carousel from './Carousel';
import ReviewSlide from './ReviewSlide';

export default function App() {
  return (
    <Carousel>
      ~<ReviewSlide id={1} />~ {/* App writes the tag, so ReviewSlide runs on the server */}
    </Carousel>
  );
}
```

```jsx title="Carousel.jsx, a Client Component" startLine="1"
'use client';

export default function Carousel({ ~children~ }) { // Holds what ReviewSlide returned, not ReviewSlide itself
  return <section>{children}</section>;
}
```

This is JSX you already know. `ReviewSlide` sits between the carousel tags, so it fills `children`. It is the same as putting `<LiveBadge />` inside `<ArticleCard>` (as seen in Lesson 09).

So it looks as if `ReviewSlide` must run where `Carousel` runs, in the browser. **It may look the same, but it is NOT the same thing!** `ReviewSlide` runs on the server. Lesson 106 showed this with the article text inside `ReadMore`. Here the piece is a whole component that reads the database, and three facts explain where it runs:
1. **`Carousel.jsx` never imports `ReviewSlide.jsx`.** The page file imports it, and `App` writes the tag. Only the files that a `'use client'` file imports become client code (as seen in Lesson 106).
2. **React runs `ReviewSlide` on the server, before `Carousel` starts.** React's docs say this about their own example: "the `Copyright` component is fully executed before `InspirationGenerator` starts rendering."
3. **`Carousel` receives only the result.** What arrives in `children` is the finished `<div>` with the review. The function itself never arrives. React's docs: "In the browser, the Client Components will see output of the Server Components passed as props."

```tree caption="Where ReviewSlide sits on the screen vs. which file imports it: the import decides where it runs."
Where does `ReviewSlide` run?
- +On the screen [`<Carousel><ReviewSlide id={1} /></Carousel>`] | `ReviewSlide` sits **inside** `Carousel` | It **looks like** browser code, but this does not decide where it runs
- +In the imports [`import ReviewSlide` in `App.jsx`] | `App`, a Server Component, **imports it and writes its tag** | `ReviewSlide` **runs on the server**, and `Carousel` gets **only its output**
```

Here is the one sentence to keep in mind for this whole lesson:

**Where a component runs depends on which file imports it, not on where its tag sits on the screen. The Server Component writes the slide's tag, and the Client Component receives the finished slide.**

> [!DEFINITION]
> **Server Component and Client Component.** [REVIEW] A file with no directive holds Server Components: they run on the server, they can be `async` and `await` the database, and they send only their output to the browser. A file that starts with `'use client'` holds Client Components: their code goes into the bundle the browser downloads, so they can use state and click handlers. Hooks do not work in a Server Component, and an `async` component does not work in the browser (Lesson 108).

> [!DEFINITION]
> **The `'use client'` line follows the imports.** [REVIEW] `'use client'` marks its own file as client code, and also every file it imports, and every file those files import. A file with no directive becomes client code the moment a `'use client'` file imports it. So the import line decides where a component runs, not the place of its tag on the screen (Lesson 106).

> [!DEFINITION]
> **JSX in a prop.** [REVIEW] JSX written between the tags of a component arrives in its `children` prop, as in `<ArticleCard><LiveBadge /></ArticleCard>`. JSX can also go in a named prop, such as `header={<LiveBadge />}`. Either way, the parent writes the JSX, and the child only decides where to place it (Lesson 09).

> [!DEFINITION]
> **What can travel from the server to the browser.** [REVIEW] When a Server Component renders a Client Component, React writes the props down on the server and rebuilds them in the browser. Strings, numbers, arrays, plain objects, and JSX can make this trip. A plain function cannot, because it is code, not data (Lesson 107).

### Where Readers Usually Go Wrong

Readers usually go wrong in three ways, and the shopper sees each one:
1. **They import the slide into the carousel file**, because the carousel is the one that shows it. As soon as the page's JavaScript runs, the carousel disappears, and the Console shows an error.
2. **They pick a slide with `children[index]`**, because `children` held three slides in their test. It works with three reviews. A product with one review shows an empty carousel.
3. **They pass a `renderSlide` function from the server**, because render props worked in the browser (as seen in Lesson 89). The page does not render at all.

### Three Ways to Show Server Data in a Client Component

When a Client Component must show content made from server data, you choose between three ways:
1. **Pass finished JSX in a prop.** Use `children` for one piece. Use a named array prop, such as `slides`, when the Client Component must pick or count the pieces. This fits a slide that reads server data or uses server-only code. This lesson builds this way.
2. **Pass plain data and write the JSX in the Client Component** (as seen in Lesson 107). The server passes an object with an author and a text, such as Anna and `Fits perfectly.` This fits a small slide with no server-only code. The slide's code joins the bundle, and every field you pass reaches the browser.
3. **Import a component with no directive into the client file.** There it becomes client code (as seen in Lesson 106). This fits a small slide with no `await`, no database, and no heavy library. Its code, and everything it imports, joins the bundle that every shopper downloads.

React's docs explain why the bundle matters: "Large bundle sizes are expensive for a client to download and run. Large bundle sizes can delay the time for your UI to get drawn." For our slide, the third way fails completely, as Principle 3 shows.

## SECTION | The Reviews Carousel on a Product Page

Open a product page in an online shop, such as a pair of running shoes. Under the photo, the customer reviews sit in a carousel. It shows one review at a time, a line that says which one, and a `Next` button:

```page caption="The reviews carousel when the user opens the product page."
url: shop.example.com/running-shoes
line: Fits perfectly.
line: Anna
line: 1 of 3
line: [Next]
console: quiet
```

The product has three short reviews:
1. `Anna`: `Fits perfectly.`
2. `Ben`: `Runs a bit small.`
3. `Mia`: `Great for running.`

The project has four files:

```files title="shop: the reviews carousel" caption="The four files of the reviews carousel: the database stand-in, two Server Components, and one Client Component."
src/
  db.js | stand-in | Plays the database and gives `db.reviews.get(id)`
  ReviewSlide.jsx | Server Component | An `async` function that awaits one review and returns its text and author
  Carousel.jsx | Client Component | Starts with `'use client'`; keeps `index` in state and shows one slide with a `Next` button
  App.jsx | Server Component | Imports `ReviewSlide` and `Carousel`, and passes three slides to `Carousel`
```

Only the carousel file starts with `'use client'`. The other three files run on the server. A real page would read the review ids from the product in the database. Our `App` writes the ids 1, 2, and 3 by hand, to keep the page small.

**PRINCIPLES:** A Client Component shows server content only through props that hold JSX. Four principles follow:
1. **`slides` as an array prop: the server renders every slide, and the carousel only picks one.** `Carousel` keeps the number of the slide on screen and swaps finished slides.
2. **`children[index]`: with one review, the carousel shows nothing.** `children` travels exactly as `slides` does, but its shape is not fixed.
3. **`import ReviewSlide` in a `'use client'` file: the slide becomes browser code, and the carousel disappears.** An async component cannot run in the browser.
4. **`renderSlide` as a prop: a function cannot travel from the server to the browser.** Send the finished slides, not a function that would make them.

## PRINCIPLE | `slides` as an array prop: the server renders every slide, and the carousel only picks one

> [!PRINCIPLE]
> **Principle 1: An Array of Finished Slides: The Server Renders Them, the Carousel Picks One**
>
> *When a Client Component must show content made from server data, the Server Component above it writes that content as JSX and passes it in a prop; when the Client Component picks among several pieces, the prop is an array.*
>
> The carousel needs a click, which only the browser has, and its slides need the database, which only the server can read. So the server does its part first: it renders every slide. The carousel does only its own part: it keeps the number of the slide on screen and swaps finished slides. The slide's code never reaches the browser.
>
> **DO THIS:**
> ```jsx
> export default function App() {
>   return <Carousel ~slides~={[<ReviewSlide key={1} id={1} />, <ReviewSlide key={2} id={2} />]} />; // The server renders both slides
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   return <Carousel ~reviews={reviews}~ />; // **WRONG:** Carousel.jsx must now build each slide, so the slide's code ships to every shopper
> }
> ```

### VS | One Piece of JSX in a Prop vs. Three Pieces in an Array: the same idea, a longer list

A carousel shows one slide and counts all of them. So `Carousel` needs the slides as a list it can number. `App` passes them in a named prop, as an array:

```jsx title="One piece of JSX in a named prop, and three pieces in an array"
<ArticleCard ~header={<LiveBadge />}~ /> {/* Lesson 09: one piece of JSX in a named prop */}
<Carousel ~slides={[<ReviewSlide key={1} id={1} />, <ReviewSlide key={2} id={2} />, <ReviewSlide key={3} id={3} />]}~ /> {/* Three pieces of JSX in one array */}
```

**Yes, it is the exact same thing!** Both put JSX in a named prop. The array simply holds three pieces instead of one. It is a plain JavaScript array, and React's docs allow it: "You can also explicitly pass an array as a prop." Like the items of any list, each piece gets its own `key` (as seen in Lesson 18).

The array can travel from the server to the browser, because everything inside it can travel. React's list of what a Server Component may pass to a Client Component includes "Iterables containing serializable values" and "Client or Server Component elements". The elements are what JSX makes.

Why an array, and not `children` as in the opening? Because `children` is not always an array. Principle 2 shows the product where `children` breaks.

### The Whole Page

`db.js` plays the database, as it did in Lesson 109. It answers with one review for each id:

```js title="src/db.js" startLine="1"
const reviews = [
  { id: 1, author: 'Anna', text: 'Fits perfectly.' },
  { id: 2, author: 'Ben', text: 'Runs a bit small.' },
  { id: 3, author: 'Mia', text: 'Great for running.' },
];

const db = {
  reviews: {
    async get(id) {
      return reviews.find(review => review.id === id); // Plays a real database: answers with one review
    },
  },
};

export default db;
```

`ReviewSlide` is an async Server Component, with the same shape as `EmailList` in Lesson 109. It awaits one review and returns its text and its author:

```jsx title="src/ReviewSlide.jsx" startLine="1"
import db from './db';

export default ~async~ function ReviewSlide({ id }) { // No directive: a Server Component
  const review = ~await~ db.reviews.get(id); // Reads the database on the server
  return (
    <div>
      <p>{review.text}</p>
      <p>{review.author}</p>
    </div>
  );
}
```

`Carousel` is the one Client Component. It keeps in state the number of the slide on screen, and shows that slide:

```jsx title="src/Carousel.jsx" startLine="1"
'use client';

import { useState } from 'react';

export default function Carousel({ ~slides~ }) { // The array App wrote on the tag
  const [index, setIndex] = useState(0);
  const next = () => setIndex((index + 1) % slides.length); // After the last slide, back to 0
  return (
    <section>
      {~slides[index]~} {/* One finished slide out of three */}
      <p>{index + 1} of {slides.length}</p>
      <button onClick={next}>Next</button>
    </section>
  );
}
```

`App` imports both, writes the three slide tags, and passes them to `Carousel`:

```jsx title="src/App.jsx" startLine="1"
import Carousel from './Carousel';
import ReviewSlide from './ReviewSlide';

export default function App() {
  return (
    <Carousel ~slides~={[ // Three slides, rendered on the server before Carousel starts
      <ReviewSlide key={1} id={1} />,
      <ReviewSlide key={2} id={2} />,
      <ReviewSlide key={3} id={3} />,
    ]} />
  );
}
```

Each `key` is the id of the review. React on the server checks the keys of this array too, even though `Carousel` shows one slide at a time. Without the keys, the carousel still works. But the browser's Console shows a warning marked `Server`: "Each child in a list should have a unique "key" prop."

When the user opens the product page, the carousel shows the first review:

```page caption="The reviews carousel when the user opens the product page."

line: Anna
line: 1 of 3
line: [Next]
console: quiet
```

### Three Tags, and One Review on the Screen

**`App` writes three `<ReviewSlide>` tags, and the screen shows only one review. Yet the server rendered all three before the page reached the browser, even the two the user does not see.** Here is what happens when the user opens the page:
1. On the server, React renders `App` and finds three slide tags in `slides`.
2. React runs all three `ReviewSlide` components. Each one awaits its review from the database and returns a `<div>`.
3. Only then does `Carousel` start. Its `slides` prop holds three finished `<div>` elements.
4. In the browser, `Carousel` shows `slides[0]`: Anna's review and the line 1 of 3.

The user clicks `Next`. The setter changes `index` to 1, and `Carousel` shows the second slide. There is no new trip to the database. `Carousel` swaps to a slide it already holds, exactly like the plain JavaScript carousel at the start:

```page caption="After the user clicks Next once: Ben's review, already rendered on the server, takes Anna's place."
url: shop.example.com/running-shoes
line: Runs a bit small.
line: Ben
line: 2 of 3
line: [Next]
console: quiet
```

After the user's third click, `index` is back to 0, and Anna's review returns with 1 of 3.

### Where `slides`, `id`, and the Review Text Come From

1. **`slides` in `Carousel`** is the array `App` writes on the `<Carousel>` tag. React puts it in `props.slides`, as it does with any prop (as seen in Lesson 08).
2. **`id` in `ReviewSlide`** is the number `App` writes on each `<ReviewSlide>` tag.
3. **The review text inside `slides[index]`** comes from the server. `ReviewSlide` awaited the review and returned a `<div>`. That `<div>` is what the array holds when it reaches the browser.

So `Carousel` holds the rendered output of each slide, not `ReviewSlide` itself (as seen in Lesson 101). React's docs: "only the rendered output is sent to the client."

### What Reaches the Browser

Because `Carousel` receives only output, the slide's code never travels. React's docs: "Only Client modules are bundled and evaluated by the client." In our page, that is one file:
- `Carousel.jsx` goes into the bundle the browser downloads.
- `ReviewSlide.jsx` and `db.js` stay on the server.

A common habit costs more. A developer passes the reviews as plain data, `reviews={reviews}`, and writes the slide's JSX inside the carousel file. The carousel works. But now the slide's code, and every helper it imports, ships in the bundle. And every field of every review reaches the browser (as seen in Lesson 107). For a slide of two lines of text, the cost is small, and React's docs pass plain data this way too. The cost grows with the slide's code.

```tree caption="Passing finished slides vs. passing plain review data: what each sends to the browser."
Two ways to give `Carousel` its reviews
- +Finished slides [`slides={[<ReviewSlide key={1} id={1} />, ...]}`] | The server **renders every slide** | The browser gets **only the output**; `ReviewSlide.jsx` and `db.js` **stay on the server**
- !Plain data [`reviews={reviews}`] | `Carousel.jsx` **writes the slide's JSX itself** | The slide's code **joins the bundle**, and **every field** of every review reaches the browser
```

Remember: the server makes the slides, and the carousel only picks one.

## PRINCIPLE | `children[index]`: with one review, the carousel shows nothing

> [!PRINCIPLE]
> **Principle 2: Opaque children: children[index] Empties the Carousel When There Is One Review**
>
> *`children` carries server output into a Client Component exactly as a named prop does, but its shape is not fixed; when the Client Component picks or counts pieces, pass an array prop.*
>
> `children` is whatever the parent writes between the tags: one element, several, or none. With three slides it happens to be an array, so `children[index]` seems to work. With one slide it is the slide itself, so `children[0]` is `undefined`, and the carousel goes empty with no error. An array prop stays an array in every case.
>
> **DO THIS:**
> ```jsx
> <Carousel ~slides={[<ReviewSlide key={1} id={1} />]}~ /> {/* An array of one: slides[0] is the review */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Carousel({ children }) {
>   return <section>{~children[index]~}</section>; // **WRONG:** with one slide, children is not an array, so nothing shows
> }
> ```

### VS | `children` vs. `slides`: the same trip from the server, a different shape

Remember `document.querySelectorAll` from the plain JavaScript carousel. It always gives you a list, even when it finds one element. `children` does not work that way. With three tags between the carousel tags, `children` is an array of three. With one tag, `children` is that one element, not an array of one.

Here is the carousel built on `children`. `App` writes the slides between the tags:

```jsx title="App.jsx with children: the slides between the tags"
<Carousel>
  <ReviewSlide id={1} />
  <ReviewSlide id={2} />
  <ReviewSlide id={3} />
</Carousel>
```

```jsx title="Carousel.jsx with children" startLine="5"
export default function Carousel({ ~children~ }) { // The slides App wrote between the tags
  const [index, setIndex] = useState(0);
  const next = () => setIndex((index + 1) % children.length);
  return (
    <section>
      {~children[index]~} {/* Picks one slide out of children */}
      <p>{index + 1} of {children.length}</p>
      <button onClick={next}>Next</button>
    </section>
  );
}
```

With three reviews, this carousel shows the same page as the one built on `slides` in Principle 1: Anna's review, 1 of 3, and the `Next` button.

For the trip from the server, **yes, it is the exact same thing!** Both are props that hold JSX written by `App`. Both reach `Carousel` as server output.

### One Review, and the Carousel With `children` Goes Empty

A new product has only one review. `App` writes one `<ReviewSlide>` tag in each version, and the two carousels part ways:

::: row caption="The same product with one review: the carousel with children shows nothing; the carousel with slides shows the review."

No review, and the line reads `1 of`.
:::

**The carousel with `children` shows no review and no error.** Here is why, in order:
1. With one tag between the carousel tags, `children` is that one element, not an array of one.
2. `children[0]` asks the element for an item at position `0`. An element has no such item, so the answer is `undefined`, and React shows nothing in its place.
3. `children.length` is `undefined` too. So the line reads 1 of, with no number after it.
4. JavaScript throws no error when you read an item that is not there, so the Console stays quiet.

`slides` stays an array in every case, because `App` made it one. With one review, it is an array of one, and `slides[0]` is the review.

So for the shape, **it may look the same, but it is NOT the same thing!** `slides` is an array because our code made it one. `children` is an array only when there happen to be several tags.

### Two Words From React's Docs: Hole and Opaque

React's docs use two words for `children`, and both explain the bug:
- **A hole.** "You can think of a component with a `children` prop as having a 'hole' that can be 'filled in' by its parent components with arbitrary JSX." A wrapper places `children` in one spot, as one piece, as the carousel in the opening did. It does not take `children` apart.
- **Opaque.** In everyday English, opaque glass is glass you cannot see through. React's docs: "the `children` prop is considered an *opaque* data structure. This means that you shouldn't rely on how it is structured." And: "even if it's sometimes an array, you should not assume it's an array or any other particular data type."

```tree caption="children vs. an array prop: the same trip from the server, a different shape in the browser."
`children` vs. `slides` in a carousel
- +The trip from the server [`children` `slides`] | Both hold **JSX written by `App`** | Both reach `Carousel` **as server output**
- !`children[index]` [`<Carousel><ReviewSlide id={1} /></Carousel>`] | With one tag, `children` is **one element, not an array** | **No review**, the line reads **`1 of`**, and **no error**
- +`slides[index]` [`slides={[<ReviewSlide key={1} id={1} />]}`] | **Always an array**, because `App` made it one | The review shows with **`1 of 1`**
```

The bug hides well. A developer builds the carousel with three reviews on the test product, and it works. A new product with one review goes live, and its carousel is empty. The fix is the one React's docs give in their `RowList` and `TabSwitcher` examples: pass the pieces as an array in a named prop.

The `Children` methods, such as `toArray`, can count and pick the pieces (as seen in Lesson 100). But React's docs warn: "Using `Children` is uncommon and can lead to fragile code."

Remember: `children` is a hole you place, `slides` is a list you can count.

## PRINCIPLE | `import ReviewSlide` in a `'use client'` file: the slide becomes browser code, and the carousel disappears

> [!PRINCIPLE]
> **Principle 3: The Boundary Follows Imports: Importing ReviewSlide Into Carousel.jsx Empties the Page**
>
> *A Client Component never imports a server component to render it; everything a `'use client'` file imports becomes client code, and an async component cannot run in the browser.*
>
> Where a component runs depends on which file imports it, not on where its tag sits on the screen. Imported by `App`, `ReviewSlide` runs on the server and reads the database. Imported by the carousel file, it becomes client code, together with `db.js`, and React stops at the first async slide.
>
> **DO THIS:**
> ```jsx
> import ReviewSlide from './ReviewSlide';
> export default function App() {
>   return <Carousel ~slides~={[<ReviewSlide key={1} id={1} />, <ReviewSlide key={2} id={2} />]} />; // App imports the slide and writes its tag
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> 'use client';
> ~import ReviewSlide from './ReviewSlide';~ // **WRONG:** ReviewSlide and db.js become client code, and the async slide fails
> ```

### Moving the Import Into the Carousel

A developer wants `Carousel` to own its slides. It looks tidier: `App` passes only the ids, and `Carousel` renders each slide itself:

```jsx title="src/Carousel.jsx" startLine="1" bad="4"
'use client';

import { useState } from 'react';
~import ReviewSlide from './ReviewSlide';~ // **WRONG:** a 'use client' file imports a server component

export default function Carousel({ ids }) {
  const [index, setIndex] = useState(0);
  const next = () => setIndex((index + 1) % ids.length);
  return (
    <section>
      ~<ReviewSlide id={ids[index]} />~ {/* Now Carousel renders the slide itself */}
      <p>{index + 1} of {ids.length}</p>
      <button onClick={next}>Next</button>
    </section>
  );
}
```

```jsx title="src/App.jsx" startLine="1"
import Carousel from './Carousel';

export default function App() {
  return <Carousel ~ids={[1, 2, 3]}~ />; // Only the ids travel now
}
```

On the screen, nothing moved: `ReviewSlide` still sits inside `Carousel`, as it did in Principle 1. **It may look the same, but it is NOT the same thing!** In Principle 1, the page file imported `ReviewSlide`. Now the carousel file imports it, and that one line moves `ReviewSlide` to the browser.

Think of an import line as an order: "put this file next to me." In a file with no directive, next to me means on the server. In a `'use client'` file, next to me means in the bundle the browser downloads.

### Why the Carousel Disappears

**The carousel disappears, and the Console shows an error that names `ReviewSlide`.** Here is what the one import does, in order:
1. The carousel file starts with `'use client'`, so the slide file, and the database file it imports, become client code. React's docs: "Add `'use client'` at the top of a file to mark the module and its transitive dependencies as client code."
2. `ReviewSlide` is `async`, and async components cannot run in the browser (as seen in Lesson 108). React's docs: "async components are not supported on the client."
3. The first HTML from the server still shows the carousel, because the server can wait for an async component while it writes the HTML.
4. When the page's JavaScript runs in the browser, React stops at `ReviewSlide` with an error and removes the carousel.

```page caption="The product page once its JavaScript runs, after the import moves into Carousel.jsx: no review, no line, no Next button."

empty: no carousel on the page
```

There is a second cost. `db.js` is now headed for the browser too. Our stand-in holds only three reviews. A real database file holds a database client and its password, and the browser can neither use them nor be trusted with them. Making the build fail before such code ships is the topic of Lesson 122.

The error message invites the wrong fix. To silence it, the developer removes `async` and tries to read the database in the browser. Or the developer adds `'use client'` to the slide file. Neither brings the database to the browser. The real fix is to move the import back into the page file and pass the rendered slides in `slides`, as Principle 1 does.

```tree caption="ReviewSlide imported in App.jsx vs. ReviewSlide imported in Carousel.jsx: the same place on the screen, two different places where it runs."
Who imports `ReviewSlide`?
- +`App.jsx`, a Server Component [`slides={[<ReviewSlide key={1} id={1} />, ...]}`] | `ReviewSlide` **runs on the server** and reads `db.js` | `Carousel` gets **finished slides**
- !`Carousel.jsx`, a Client Component [`import ReviewSlide` under `'use client'`] | `ReviewSlide` and `db.js` **become client code** | An **async Client Component** error, and **no carousel**
```

Remember: the import decides where a component runs, not the place of its tag.

## PRINCIPLE | `renderSlide` as a prop: a function cannot travel from the server to the browser

> [!PRINCIPLE]
> **Principle 4: Serializable Props: A renderSlide Function Cannot Reach the Carousel**
>
> *Across the server and client boundary, pass the rendered slides, not a function that would render them; a plain function cannot make the trip.*
>
> A render prop is a function call inside one program. When the parent runs on the server and the child runs in the browser, the function would have to travel over the network. React can send data, such as finished JSX, strings, numbers, arrays, and plain objects, but not a plain function. So the server renders every slide ahead, and the carousel picks one.
>
> **DO THIS:**
> ```jsx
> <Carousel ~slides={[<ReviewSlide key={1} id={1} />, <ReviewSlide key={2} id={2} />]}~ /> {/* Finished slides travel as data */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Carousel ids={[1, 2]} ~renderSlide={(id) => <ReviewSlide id={id} />}~ /> {/* **WRONG:** a function cannot travel, so the page does not render */}
> ```

### VS | A Render Prop in the Browser vs. a Render Prop From the Server: the same code, two machines

Rendering all three slides ahead looks wasteful. A developer who knows render props (as seen in Lesson 89) wants only the slide on screen to render. React's docs offer exactly this in place of `children`. They say: "Instead of producing JSX for every single item, you can also pass a function that returns JSX, and call that function when necessary." So `App` passes a function:

```jsx title="src/App.jsx" startLine="4" bad="7"
export default function App() {
  return (
    <Carousel
      ids={[1, 2, 3]}
      ~renderSlide={(id) => <ReviewSlide id={id} />}~ // **WRONG:** a function cannot leave the server
    />
  );
}
```

`Carousel` would call `renderSlide` with the id on screen to get its slide. In Lesson 89, the same code worked. **It may look the same, but it is NOT the same thing!**

In Lesson 89, both components ran in the browser, so passing the function was a plain function call inside one program. Here, `App` runs on the server and `Carousel` runs in the browser. They are two different machines, and the function would have to travel between them.

### Why the Page Does Not Render

**The page does not render. React stops on the server with this error:**

```text title="The error React throws when App passes renderSlide to Carousel"
Functions cannot be passed directly to Client Components unless you explicitly expose it by marking it with "use server". Or maybe you meant to call this function rather than return it.
  <... ids={[...]} renderSlide={function renderSlide}>
                               ^^^^^^^^^^^^^^^^^^^^^^
```

You have seen this limit in plain JavaScript. Turn an object into text with `JSON.stringify`, and the data survives, but a function is simply dropped:

```js title="Plain JavaScript: data survives JSON.stringify, a function does not"
JSON.stringify({ text: 'Fits perfectly.' }); // '{"text":"Fits perfectly."}'
JSON.stringify({ ~renderSlide: (id) => id~ }); // '{}': the function is dropped
```

React's format is not JSON, but it has the same limit. A function is code, not data. React can write the array of finished slides down on the server and rebuild it in the browser (as seen in Lesson 107). It cannot do that with a function, so it stops with an error instead of dropping it quietly. React's list of what may not travel names it: "Functions that are not exported from client-marked modules or marked with `'use server'`".

The message offers `'use server'`, and that does not help a carousel. A function marked `'use server'` is a Server Function, and calling it "will send a request to the server" (as seen in Lesson 110). Every click on `Next` would wait for the network.

```tree caption="Finished slides vs. a renderSlide function passed from a Server Component to a Client Component."
What `App` passes to `Carousel`
- +Finished slides [`slides={[<ReviewSlide key={1} id={1} />, ...]}`] | **Data**: the output of each slide | React **writes it down** on the server and **rebuilds it** in the browser
- !A render prop [`renderSlide`] | **Code**: a function that would render a slide | React **cannot send it**, and **the page does not render**
```

The fix is Principle 1 again: render every slide in `App`, and pass the slides in `slides`. The server reads the reviews once, and every click on `Next` swaps to a slide that is already in the browser.

Remember: across the boundary, send what a function returns, never the function.

## All 4 Principles Together

### The Complete Code

Here is the finished carousel: the database stand-in, the slide that reads it, the one Client Component, and the page that hands over the finished slides.

```files title="shop: the finished reviews carousel" caption="The finished reviews carousel: one Client Component, and everything that reads the database on the server."
src/
  db.js | stand-in | Gives `db.reviews.get(id)`, one review for each id
  ReviewSlide.jsx | Server Component | Awaits one review and returns its text and author
  Carousel.jsx | Client Component | The only file in the bundle; shows `slides[index]`, the line, and `Next`
  App.jsx | Server Component | Imports `ReviewSlide` and passes three finished slides in `slides`
```

```js title="src/db.js" startLine="1"
const reviews = [
  { id: 1, author: 'Anna', text: 'Fits perfectly.' },
  { id: 2, author: 'Ben', text: 'Runs a bit small.' },
  { id: 3, author: 'Mia', text: 'Great for running.' },
];

const db = {
  reviews: {
    async get(id) {
      return reviews.find(review => review.id === id); // Plays a real database: answers with one review
    },
  },
};

export default db;
```

```jsx title="src/ReviewSlide.jsx" startLine="1"
import db from './db';

export default ~async~ function ReviewSlide({ id }) { // Principle 3: async, so it must stay on the server
  const review = await db.reviews.get(id);
  return (
    <div>
      <p>{review.text}</p>
      <p>{review.author}</p>
    </div>
  );
}
```

```jsx title="src/Carousel.jsx" startLine="1"
'use client';

import { useState } from 'react';

export default function Carousel({ ~slides~ }) { // Principle 2: an array prop, not children; Principle 3: no slide import
  const [index, setIndex] = useState(0);
  const next = () => setIndex((index + 1) % slides.length);
  return (
    <section>
      {slides[index]}
      <p>{index + 1} of {slides.length}</p>
      <button onClick={next}>Next</button>
    </section>
  );
}
```

```jsx title="src/App.jsx" startLine="1"
import Carousel from './Carousel';
import ReviewSlide from './ReviewSlide';

export default function App() {
  return (
    <Carousel ~slides~={[ // Principles 1 and 4: finished slides, not a function
      <ReviewSlide key={1} id={1} />,
      <ReviewSlide key={2} id={2} />,
      <ReviewSlide key={3} id={3} />,
    ]} />
  );
}
```

### The Order in Which React Renders the Carousel

When the user opens the page, React renders `App` on the server, then every slide, and only then `Carousel`. In the browser, a click on `Next` by the user touches only `Carousel`:

```tree dir=right caption="The order in which React renders the reviews carousel: the slides on the server first, then the carousel in the browser."
The order in which React renders the carousel
- +1. `App` on the server [`slides={[...]}`] | React finds **three `<ReviewSlide>` tags** | Nothing reaches the browser yet
- +2. Each `ReviewSlide` on the server [`await`] | Each slide **reads its review** and returns a `<div>` | `slides` now holds **three finished slides**
- +3. `Carousel` in the browser [`slides[index]`] | Shows **slide 0** and **`1 of 3`** | Each `Next` **swaps to a slide it already holds**
```

### Summary

| Principle | What the code does | What the user sees |
| :--- | :--- | :--- |
| **1. Finished slides in `slides`** | `App` writes three `<ReviewSlide>` tags in an array prop | One review at a time, and `Next` swaps them with no wait |
| **2. An array prop, not `children`** | `Carousel` reads `slides[index]` and `slides.length` | A product with one review still shows it, with `1 of 1` |
| **3. No slide import in `Carousel.jsx`** | Only `App.jsx` imports `ReviewSlide` | The carousel appears, and the slide's code stays off the shopper's browser |
| **4. Data, not a function** | `App` passes rendered slides, never `renderSlide` | The page renders, with no error from the server |

Remember the one sentence of this lesson. **Where a component runs depends on which file imports it, not on where its tag sits on the screen. The Server Component writes the slide's tag, and the Client Component receives the finished slide.**

## For the Interview

> **The Interview Question:** How do you pass server-rendered children into a Client Component?

### How to Answer Clearly in 30 Seconds

"A Client Component cannot import a Server Component, but it can show one. The Server Component that renders the Client Component writes the server component's tag and passes it in a prop. That prop is `children` for one piece, or a named prop such as `slides` for several.
1. **Where it runs:** the server component in that prop runs on the server, before the Client Component renders. The boundary follows the imports, not the screen.
2. **What travels:** the Client Component receives the rendered output, not the component. So the slide's code, the database code, and its libraries stay out of the bundle. Only Client modules are bundled.
3. **The traps:** importing the server component into the `'use client'` file makes it client code, and an async one fails. Indexing `children` breaks when there is one piece, so pass an array instead. And a render prop cannot travel, because a plain function is not serializable."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Do the slides render again when the user clicks `Next`?"**
   **No.** The click changes `index`, the state of `Carousel`, and `Carousel` swaps to a slide it already holds. React's docs: "Server Components do not persist in memory after render and cannot have their own state." The same idea works inside the browser. When a wrapper updates its own state, React knows that the `children` it received do not need to render again (as seen in Lesson 58). To get a fresh slide, React's docs say Server Components "can be made dynamic by re-fetching them from a server", which is the framework's job.
2. **"Isn't rendering every slide ahead a waste?"**
   **Usually not.** The server reads every review at once, and the browser receives only output and no slide code. Each `Next` then shows a slide with no wait. For data that is slow or sits far down the page, React's docs do something else. They start a promise on the server and read it in the Client Component with `use` (as seen in Lesson 71).
3. **"When do you use `children`, and when a named prop?"**
   Use `children` for one hole the Client Component places as one piece, as React's docs do with `Expandable` and `InspirationGenerator`. Use a named prop for a second hole (as seen in Lesson 09). Use an array prop when the Client Component picks or counts the pieces, as a carousel does. Context providers that wrap a page use the same `children` shape, as Lesson 116 shows.

```tree dir=right caption="Interview summary: how a Server Component passes server-rendered content into a Client Component."
Server content inside a Client Component
- +Who writes the tag [`<Carousel slides={[<ReviewSlide key={1} id={1} />]} />`] | The **Server Component** that renders the Client Component | The server component **runs on the server first**
- +What the Client Component gets [`slides[index]`] | The **rendered output**, not the component | The slide's code **stays out of the bundle**
- !What breaks it [`import ReviewSlide` `children[index]` `renderSlide`] | A **slide import** in the client file, an **indexed `children`**, a **function prop** | An **async Client Component** error, an **empty carousel**, a page that **does not render**
```
