# Lecture 101: What Server Components Are and Why They Exist

*(Why should every phone download a library only to show a text that is the same for everyone?)*

> INTERVIEW QUESTION | ❱ CORE | What are React Server Components, and why do they exist?

---

## VS | Client Component vs. Server Component: both are React components, only one sends its code to the browser

> A published blog post is the same text for every user, yet a React app built only for the browser formats it again on every user's phone. **A Server Component is a React component that runs before the page is sent, and the browser receives only what it rendered, never its code**. So the libraries it imports stay off the phone, and the post is on the screen from the first load.

In React, until now, **every component sent its code to the browser**. The user opens the page, the browser downloads the JavaScript of every component, and calls each one there. That is exactly right for a Like button, which must count every tap on the phone. But many parts of a page never change after they are published, like a blog post, a documentation page, or a product description. Formatting them again on every phone is wasted work. This is why React has Server Components. **A Server Component runs before the page is sent, on a server or on the machine that builds the app, and the browser receives only the finished result.**

Take a blog post page with a title, `Park Opens Today`, one line under it, and a Like button with its count. The author wrote the post as a Markdown file, and some code has to turn that Markdown into HTML. Ask yourself: does that code need to run on every user's phone? No. The post is the same for everyone. Only the Like button needs the phone, because only the Like button answers a tap.

**Why:** Without Server Components, every phone downloads a Markdown library and waits for a second request to get the post. Then it builds the same title and the same line as every other phone. See the problem? The work is the same for every user, yet every user pays for it, in download size and in waiting. A Server Component does that work once, before the page is sent. The phone gets the finished post, and of our own code, only the Like button.

### Back to a Plain Node.js Script

Remember Node.js? It runs JavaScript on your own computer, outside any browser. A Node.js script can read a file from the disk, which a browser can never do. Here is a short script that turns the post into HTML:

```js title="build.js: plain Node.js, run once on your computer"
import { readFile, writeFile } from 'node:fs/promises';
import { marked } from 'marked';

const text = ~await readFile('post.md', 'utf8')~; // Reads the Markdown from the disk
await writeFile('post.html', ~marked(text)~); // Writes the finished HTML file
```

You run it once. It writes `post.html`, and you upload that file. Every user downloads the finished HTML. Nobody downloads the script, and nobody downloads `marked`.

A Server Component is the same idea, written as a React component:

```jsx title="src/Post.jsx: the same job, as a Server Component"
import { readFile } from 'node:fs/promises';
import { marked } from 'marked';

export default ~async~ function Post() { // A component that runs before the page is sent
  const text = await readFile('post.md', 'utf8');
  return <div dangerouslySetInnerHTML={{ __html: marked(text) }} />;
}
```

Like the script, `Post` reads the file and runs `marked` before the page is sent. Unlike the script, it returns JSX, so it sits in a React page next to other components. And exactly as with the script, **the browser receives what `Post` rendered, never its code and never the libraries it imported.**

Keep that sentence in mind. The whole lesson is built on it.

### Two Kinds of React Component

> [!DEFINITION]
> **What is a Server Component?** [NEW] A Server Component is a React component that runs before the page is sent: either once, when the team builds the app, or once for each request a user sends.
> The browser receives only what it rendered. Its code and the libraries it imports never reach the browser.
> It is still a function that returns JSX, with the same tags and the same props you already know (Lesson 101).

> [!DEFINITION]
> **What is a Client Component?** [NEW] A Client Component is a React component whose code is sent to the browser and runs there. Every component in this course so far was one.
> Because it runs in the browser, it can hold state with `useState` and answer taps with `onClick` (Lesson 101).

Both are React components. Both are functions that return JSX. The one difference is where and when they run:
- **A Server Component** runs on a server or on the build machine, before the page is sent.
- **A Client Component** runs in the user's browser, after the page arrives.

The moment when the team builds the app has a name: **build time**. A Server Component runs either once at build time, or once for each request a user sends.

```tree caption="A Server Component and a Client Component are both React components; they differ in where and when they run."
Two kinds of React component on the blog post page
- +Server Component [`Post`] | Runs **before the page is sent** | The browser receives **only what it rendered**, never its code or its libraries
- +Client Component [`LikeButton`] | Its code is **sent to the browser** and runs there | It can use **state** and **event handlers**, so it answers taps
```

### Three Ways to Show a Markdown Post

Developers really choose between three ways to show a post like ours:
1. **A Client Component fetches the text in an Effect and formats it in the browser** (as seen in Lessons 32 and 33). It fits an app made with a build tool alone, where no code runs before the page is sent.
2. **A Server Component reads the file and formats it once, at build time.** It fits content that does not change, such as a published post or a documentation page.
3. **A Server Component reads its data on each request, on a web server.** It fits data that changes, such as a note read from a database. The component reads the data itself, so the team does not have to build an API for it.

```tree caption="Three ways to show a Markdown post: in the browser, once at build time, or on each request."
Three ways to show a Markdown post in React
- +Client Component with an Effect [`useEffect` `fetch`] | Formats the post **in every user's browser** | Fits an app made with a **build tool alone**
- +Server Component at build time [`await readFile`] | Formats the post **once, when the app is built** | Fits content that **does not change**, such as a published post
- +Server Component on each request [`await` on a web server] | Formats the page **once per request** | Fits data that **changes**, such as a note in a database
```

This lesson starts from the first way, the one you already know, and turns it into the second.

### The Rule of Thumb: does this part answer the user?

**Ask one question about every component: does it need to answer the user in the browser, with state or a tap? If yes, make it a Client Component. If not, leave it a Server Component.**

A senior developer also knows the four classic mistakes:
1. **Writing `'use server'` to make a Server Component.** There is no directive for Server Components. That line marks something else.
2. **Thinking a Server Component needs a running web server.** It can run once, at build time.
3. **Thinking Server Components and server-side rendering are one thing.** They are two separate steps.
4. **Putting `useState` or `onClick` into a Server Component.** It runs once, before the page is sent, so nothing in it is left to answer a tap.

The rest of the lesson shows each one on a real page.

## SECTION | A Blog Post Page with a Like Button

Open a blog post on your phone. The page shows a title, one line under it, and a Like button with its count:

```page width=text caption="The blog post page the user opens: a title, one line, and a Like button."
heading: Park Opens Today
line: The park opens at noon.
line: 0 likes [Like]
```

The author wrote this post in a Markdown file, `post.md`. Markdown is the plain text format that blogs and documentation sites use. A line that starts with a hash sign becomes a title:

```md title="post.md"
# Park Opens Today

The park opens at noon.
```

Today, the app is built only for the browser, with a build tool such as Vite and no framework (as seen in Lesson 46). Besides the post and the two components, the project needs a route. A route is a small piece of server code that answers one address. Here, it answers with the text of the post:

```files title="blog: the page without Server Components" caption="The blog post page as a client-only app: the post, a route that sends it, and two components."
post.md | content | The post written in Markdown
api/
  post.js | route | Answers `/api/post` with the text of `post.md`
src/
  Post.jsx | Client Component | Fetches the text, formats it with `marked`, and renders `LikeButton`
  LikeButton.jsx | Client Component | Counts the likes with `useState` and `onClick`
```

`Post` fetches the text in an Effect (as seen in Lesson 33), and formats it with `marked`:

```jsx title="src/Post.jsx" startLine="1"
import { useState, useEffect } from 'react';
import { marked } from 'marked';
import LikeButton from './LikeButton';

export default function Post() {
  const [text, setText] = useState('');

  useEffect(() => {
    ~fetch('/api/post')~ // Asks the server for the post after the first render
      .then(response => response.text())
      .then(data => setText(data));
  }, []);

  return (
    <article>
      <div ~dangerouslySetInnerHTML~={{ __html: marked(text) }} /> {/* marked runs on the phone */}
      <LikeButton />
    </article>
  );
}
```

`LikeButton` counts the likes in state (as seen in Lesson 12):

```jsx title="src/LikeButton.jsx" startLine="1"
import { useState } from 'react';

export default function LikeButton() {
  const [likes, setLikes] = useState(0);
  return (
    <>
      <span>{likes} likes</span>
      <button ~onClick~={() => setLikes(likes + 1)}>Like</button> {/* Adds one like per tap */}
    </>
  );
}
```

The `dangerouslySetInnerHTML` prop puts an HTML string inside the `<div>`. The post comes from the site's own author, so the HTML that `marked` makes from it is trusted. The prop is safe here (as seen in Lesson 48).

### What Happens When a User Opens the Link

**Without Server Components, every user's phone downloads a library and asks the server a second time, only to show a text that is the same for everyone.** Here is what happens:
1. The phone downloads the app's JavaScript bundle. Inside it sits `marked`, the library that turns Markdown into HTML.
2. React renders the page. The post is not there yet, so the user sees the Like button with an empty space above it.
3. The Effect asks the server for the post, and the phone waits for the answer.
4. The text arrives. `marked` turns it into HTML on the phone, and React renders the page again, now with the title and the line.

```page width=text caption="What the user sees after step 2: the Like button is there, and the post is not."
empty: no post yet
line: 0 likes [Like]
```

The next user goes through the same four steps, and so does every user after that. Each phone downloads the same library and builds the same title and the same line. Yet the text does not change after the author publishes it.

What does it cost? In react.dev's own example, `marked` weighs 11.2 kilobytes once compressed for download. Together with a second library that cleans the HTML, the example adds about 75 kilobytes of compressed code. And every user first sees an empty space, then waits for a second request.

With a Server Component, and with its output turned into HTML before the page is sent, react.dev says the content is visible during the first page load. And the bundle does not include the expensive libraries.

So we keep the same page and the same two components, and we move `Post` to the server. By the end, the project holds only three files: the post, `Post.jsx`, and `LikeButton.jsx`. The route is gone.

**PRINCIPLES:** A Server Component runs before the page is sent, and the browser receives only what it rendered. Five principles follow:
1. **Principle 1: An Async Server Component Reads Its Data While It Renders.** `Post` waits for the file in its own body, so it needs no Effect, no empty first render, and no route.
2. **Principle 2: A Server Component's Imports Stay Out of the Bundle.** `marked` runs on the server. The browser downloads only the code of Client Components.
3. **Principle 3: The Like Button Needs `'use client'`.** A component with state or a tap must be a Client Component, marked by one line at the top of its file.
4. **Principle 4: No Directive Marks a Server Component.** Server Components are the default. The line `'use server'` marks Server Functions.
5. **Principle 5: A Server Component Can Run Once at Build Time.** It needs no web server. Turning its output into HTML is a separate step, server-side rendering.

## PRINCIPLE | `async function Post`: the component waits for its data, then renders once, with the text

> [!PRINCIPLE]
> **Principle 1: Async Server Component: `Post` Reads Its Data While It Renders**
>
> *Write a Server Component as an `async` function and `await` its data in its own body; it needs no Effect, no empty first render, and no route of its own.*
>
> A Client Component cannot wait inside its body, so it renders empty first and fetches in an Effect. A Server Component runs before the page is sent, so it can wait for the file and render once, with the text. Keeping `useState` and `useEffect` in a Server Component does not work, because a Server Component cannot use them.
>
> **DO THIS:**
> ```jsx
> export default ~async~ function Post() { // React waits for the file, then renders once
>   const text = await readFile('post.md', 'utf8');
>   return <p>{text}</p>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function Post() {
>   const [text, setText] = ~useState~(''); // **WRONG:** a Server Component cannot use useState or useEffect
>   useEffect(() => { fetch('/api/post').then(r => r.text()).then(setText); }, []);
>   return <p>{text}</p>;
> }
> ```

Remember how a Client Component gets data from the server (Lesson 33)? It renders empty, fetches in an Effect, puts the answer into state, and renders again. Why the detour? Because a Client Component cannot wait inside its body. React calls it, and it must return JSX right away.

A Server Component can wait. Here are the two versions of `Post`, each in its smallest form:

```jsx title="With an Effect: Post fetches the text after its first render"
export default function Post() {
  const [text, setText] = useState('');

  useEffect(() => {
    fetch('/api/post')
      .then(response => response.text())
      .then(data => ~setText(data)~); // Starts the second render, in the browser: the text appears
  }, []);

  return <p>{~text~}</p>; // Empty on the first render, filled on the second
}
```

```jsx title="With await in the body: Post reads the file before it returns"
import { readFile } from 'node:fs/promises';

export default ~async~ function Post() { // A Server Component may be an async function
  const text = ~await~ readFile('post.md', 'utf8'); // React waits here until the file is read
  return <p>{text}</p>;
}
```

It looks the same, but it is NOT the same thing! Both versions end by showing the same paragraph. The difference is when the text arrives:
- **With an Effect**, `Post` renders twice, in the browser. The first render has no text. The Effect fetches it, and the second render shows it.
- **With `await` in the body**, `Post` renders once, with the text, before the browser receives anything. React waits at the `await` line until the file is read, then goes on rendering.

```tree caption="With an Effect, Post renders empty and then again with the text; with await in the body, Post renders once with the text, before the page is sent."
Two ways for `Post` to get the text of `post.md`
- !With an Effect [`useEffect` `fetch`] | Renders **empty first**, then fetches, then **renders again** | All of it happens **in every user's browser**
- +With `await` in the body [`async function Post` `await readFile`] | Waits for the file **inside its own body** | Renders **once, with the text**, before the page is sent
```

### A Component with `async` in Front of It

The second version is an **async component**: a component written as an `async` function, with `await` in its body. No component in this course had `async` in front of it until now. It works here only because `Post` is a Server Component.

When React meets the `await`, it pauses the rendering of `Post`. It waits for the promise to resolve, and then it goes on.

The same function does not work as a Client Component. react.dev says it plainly: async components are not supported on the client.

### Who Calls `Post`, If the Browser Never Does?

A framework calls it, such as Next.js App Router (as seen in Lesson 46). The framework calls `Post` before the page is sent. For a post that does not change, it calls `Post` at build time, before any user opens the page.

### Where `readFile` Comes From

`readFile` is not part of React. It comes from Node.js, from its built-in file module, the one imported on the first line. It reads a file from the disk of the computer that runs the component, and it returns a promise of the file's text. The second argument, `'utf8'`, asks for that text as a string.

A browser cannot read files from the server's disk. So this line can run only in a Server Component.

### Our Post Page: `Post.jsx` Becomes a Server Component

On our page, `Post.jsx` drops the state, the Effect, and the fetch call. It reads the post file directly. The `marked` line stays as it was, and Principle 2 looks at it. We set the Like button aside for now, and Principle 3 brings it back.

```jsx title="src/Post.jsx" startLine="1" good="4,5"
import { readFile } from 'node:fs/promises';
import { marked } from 'marked';

export default ~async~ function Post() { // Called by the framework, never by the browser
  const text = await readFile('post.md', 'utf8');
  return (
    <article>
      <div dangerouslySetInnerHTML={{ __html: marked(text) }} />
    </article>
  );
}
```

We delete the route file. Nobody needs to ask the server for the post anymore, because `Post` reads the file where it already sits.

```page width=text caption="The post page after Post becomes a Server Component: the title and the line are there from the start, with no empty first render."
heading: Park Opens Today
line: The park opens at noon.
```

Remember: `Post` runs before the page is sent. The browser receives the title and the line, not the code that read them.

## PRINCIPLE | `import` in a Server Component: the library runs on the server and never reaches the bundle

> [!PRINCIPLE]
> **Principle 2: Bundle: A Server Component's Imports Stay on the Server**
>
> *A library imported by a Server Component runs on the server and is not included in the bundle; only Client modules are bundled and run by the browser.*
>
> The same import line does two different things, depending on the component that holds it. In a Client Component, every user downloads the library and runs it. In a Server Component, the library runs once, and the browser receives only the rendered output.
>
> **DO THIS:**
> ```jsx
> import { ~marked~ } from 'marked'; // Runs on the server; the browser gets the finished HTML
>
> export default async function Post() {
>   const text = await readFile('post.md', 'utf8');
>   return <div dangerouslySetInnerHTML={{ __html: marked(text) }} />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import { ~marked~ } from 'marked'; // **WRONG:** in a Client Component, every user downloads marked for the same text
>
> export default function Post() {
>   const [text, setText] = useState('');
>   useEffect(() => { fetch('/api/post').then(r => r.text()).then(setText); }, []);
>   return <div dangerouslySetInnerHTML={{ __html: marked(text) }} />;
> }
> ```

> [!DEFINITION]
> **What is the bundle?** [REVIEW] When you build a React app, the build tool packs your components, and every library they import, into a few JavaScript files. That is the bundle.
> Every user downloads it, and the browser runs it. A bigger bundle means a longer download before the page works (Lesson 07).

### The Same Import Line in Two Files

Here is the top of `Post.jsx` in the Effect version and in the Server Component version:

```jsx title="The marked import in a Client Component"
import { useState, useEffect } from 'react';
import { ~marked~ } from 'marked'; // Added to the bundle: every user downloads it

export default function Post() {
```

```jsx title="The marked import in a Server Component"
import { readFile } from 'node:fs/promises';
import { ~marked~ } from 'marked'; // Not included in the bundle: it runs on the server

export default async function Post() {
```

It looks the same, but it is NOT the same thing! The import line is the same, character for character. What differs is the component that holds it:
- **In the Client Component**, `marked` goes into the bundle. Every user's browser downloads it and runs it on the same text.
- **In the Server Component**, `marked` runs once, where `Post` runs. react.dev's own comment on this line reads "Not included in bundle".

### What the Browser Receives Instead

The browser receives neither `marked` nor `Post`. It receives the **rendered output** of `Post`: what `Post` returned, without the code that produced it.

On the server, `marked` turns the Markdown into an HTML string. Then `dangerouslySetInnerHTML` places that string inside the `<div>`. So the rendered output already holds the finished title and line. The Elements panel in the browser shows them:

```dom title="Elements panel" caption="The post in the Elements panel: a finished div from the rendered output of Post, with no marked code behind it."
<article>
+ <div>
+   <h1>Park Opens Today</h1>
+   <p>The park opens at noon.</p>
+ </div>
</article>
```

react.dev has a name for the files whose code does reach the browser: **Client modules**. Only Client modules are bundled and run by the browser. So what gets smaller is exactly the JavaScript the browser downloads and runs.

When React first announced this idea in 2020, the announcement was titled "Introducing Zero-Bundle-Size React Server Components".

```tree caption="The same import of marked adds the library to the bundle in a Client Component, and leaves it on the server in a Server Component."
Where `marked` runs, depending on the component that imports it
- !Imported in a Client Component [`import { marked }` in an Effect-based `Post`] | `marked` and `Post` go **into the bundle** | Every user **downloads and runs** them on the same text
- +Imported in a Server Component [`import { marked }` in an async `Post`] | `marked` runs **once, where `Post` runs** | The browser receives **only the rendered `<div>`**
```

### Smaller Is Not Always the Result

A Server Component makes the bundle smaller when its code is heavy and its output is light, as with `marked` and a short post. The opposite can happen too.

react.dev's example is a component that returns a drawing written as one long SVG path string. Its output is larger than its code. So it can be better to keep it a Client Component, and send the code instead.

## PRINCIPLE | `'use client'`: only the file that needs state or a tap goes to the browser

> [!PRINCIPLE]
> **Principle 3: `'use client'`: Only the Part That Answers Taps Runs in the Browser**
>
> *A component that uses `useState` or an event handler such as `onClick` must be a Client Component, marked with `'use client'` at the top of its file; a Server Component can render it.*
>
> A Server Component runs once before the page is sent and is gone, so it cannot hold state or answer a tap. Put `'use client'` on the small file that needs the tap, and let the post around it stay on the server.
>
> **DO THIS:**
> ```jsx
> ~'use client';~ // Only LikeButton.jsx goes to the browser
>
> export default function LikeButton() {
>   const [likes, setLikes] = useState(0);
>   return <button onClick={() => setLikes(likes + 1)}>{likes} likes</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~'use client';~ // **WRONG:** on Post.jsx, this sends Post and marked to every user again
> import { marked } from 'marked';
>
> export default function Post({ text }) {
>   const [likes, setLikes] = useState(0);
>   return (
>     <article>
>       <div dangerouslySetInnerHTML={{ __html: marked(text) }} />
>       <button onClick={() => setLikes(likes + 1)}>{likes} likes</button>
>     </article>
>   );
> }
> ```

### The Same Button, with One More Line

Here is the Like button exactly as you wrote it before, with one new line at the top:

```jsx title="src/LikeButton.jsx" startLine="1"
~'use client';~ // This file is client code: it goes into the bundle

import { useState } from 'react';

export default function LikeButton() {
  const [likes, setLikes] = useState(0);
  return (
    <>
      <span>{likes} likes</span>
      <button onClick={() => setLikes(likes + 1)}>Like</button>
    </>
  );
}
```

`'use client'` is a **directive**: a plain string at the very top of a file that gives an instruction to the bundler. This one says: the code of this file is client code. So the bundler puts it in the bundle, the browser runs it, and `LikeButton` becomes a Client Component.

### Why the Button Cannot Be a Server Component

A Server Component runs once, before the page is sent, and then it is gone. It does not stay in memory after it renders, so it cannot hold state. And when the user taps Like on the phone, no Server Component is there to answer the tap. So `useState` and `onClick` need a component whose code runs in the browser.

In an app with Server Components, every component is a Server Component, unless a `'use client'` line says otherwise. Without that line, the button file is a Server Component. The framework stops with an error, because a Server Component cannot use `useState`.

```tree caption="LikeButton.jsx with the use client line is bundled and counts taps; without it, the file is a Server Component and cannot use useState."
`LikeButton.jsx` in an app with Server Components
- +With `'use client'` at the top [`'use client';`] | The file is **client code** and goes into the bundle | The button **counts every tap** in the browser
- !Without `'use client'` [`import { useState }` on line 1] | The file is a **Server Component** | It **cannot use `useState`**, so the framework stops with an error
```

### Our Post Page: `Post` Renders the Like Button Again

`Post` is still a Server Component, and it can render a Client Component like any other tag. It imports `LikeButton` and places `<LikeButton />` under the post:

```jsx title="src/Post.jsx" startLine="1" good="3,10"
import { readFile } from 'node:fs/promises';
import { marked } from 'marked';
import ~LikeButton~ from './LikeButton'; // A 'use client' file: its code goes to the browser

export default async function Post() {
  const text = await readFile('post.md', 'utf8');
  return (
    <article>
      <div dangerouslySetInnerHTML={{ __html: marked(text) }} />
      <LikeButton />
    </article>
  );
}
```

`Post` does not run the button. Its rendered output only marks the place where `LikeButton` goes. The browser downloads the code of the button file and calls `LikeButton` there.

The page now has both parts again. The title and the line come from `Post`, rendered before the page was sent. The count and the button come from `LikeButton`, whose code runs in the browser:

```page width=text caption="The post page with the Like button back, before any tap."
heading: Park Opens Today
line: The park opens at noon.
line: 0 likes [Like]
```

```page width=text caption="The same page after the user taps Like once."
heading: Park Opens Today
line: The park opens at noon.
line: 1 likes [Like] | good
```

### The Quick Fix That Brings `marked` Back

**The quick fix for a `useState` error turns the whole post back into client code, and every user downloads `marked` again.** Here is how developers really fall into it:
1. A developer writes the Like button with `useState` directly inside `Post.jsx`.
2. The framework stops with an error about `useState`.
3. To fix it, the developer puts `'use client'` at the top of `Post.jsx`.
4. The error is gone. But `Post` is now client code, and `marked` with it. Every user downloads both again, exactly as before this lesson.

The fix that react.dev shows is the one on our page. Keep the post a Server Component, and move only the part that answers taps into its own file, with `'use client'` at the top.

## PRINCIPLE | No directive: every component is a Server Component by default, and `'use server'` marks Server Functions

> [!PRINCIPLE]
> **Principle 4: The Default: Server Components Have No Directive**
>
> *In an app with Server Components, every component is a Server Component unless its file, or a file that imports it, has `'use client'`; `'use server'` marks Server Functions, not Server Components.*
>
> Developers who learn `'use client'` expect a matching line for the server side. There is none. A Server Component is the file with no directive at all, and `'use server'` turns the exports of a file into functions the browser can call.
>
> **DO THIS:**
> ```jsx
> ~export default async function Post()~ { // No directive: a Server Component by default
>   const text = await readFile('post.md', 'utf8');
>   return <p>{text}</p>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~'use server';~ // **WRONG:** this marks Server Functions; there is no directive for Server Components
>
> export default async function Post() {
>   const text = await readFile('post.md', 'utf8');
>   return <p>{text}</p>;
> }
> ```

### Three Ways a File Can Start

Look at the first line of three files:

```jsx title="The first line of three files"
~'use client';~ // LikeButton.jsx: client code, sent to the browser
~'use server';~ // A file of Server Functions, which the browser can call
~import { readFile } from 'node:fs/promises';~ // Post.jsx: no directive at all, a Server Component
```

`'use client'` and `'use server'` look like a matching pair, one line for each side. It looks the same, but it is NOT the same thing! They are not opposites:
- **`'use client'`** marks a file of client code. That file, and everything it imports, goes into the bundle.
- **`'use server'`** does not mark a Server Component. It marks **Server Functions**: functions that run on the server, and that the browser can call (Lesson 110 teaches them).
- **No directive at all** is what a Server Component looks like. `Post.jsx` has no special line, and it runs only on the server.

react.dev names this exact mistake. A common misunderstanding is that Server Components are marked with `'use server'`. But there is no directive for Server Components.

### Server Components Are the Default

`Post.jsx` needs no line of its own, because an app with Server Components renders on the server by default. Every component is a Server Component until a `'use client'` file says otherwise. So the only line you write is the one for the exception: the part that must run in the browser.

```tree caption="Three ways a file can start: use client marks client code, use server marks Server Functions, and no directive is the default Server Component."
What the first line of a file means in an app with Server Components
- +`'use client'` [`LikeButton.jsx`] | Marks **client code** | The file is **bundled** and runs in the browser
- !`'use server'` | Marks **Server Functions**, not Server Components | ~Do **NOT** write it to make a Server Component
- +No directive [`Post.jsx`] | The **default** in an app with Server Components | A **Server Component**, with no line of its own
```

Our page does not change in this principle. `Post.jsx` stays as it is, with no directive. Next to it, `LikeButton.jsx` starts with `'use client'`.

## PRINCIPLE | Server Component at build time: it runs once, with no web server

> [!PRINCIPLE]
> **Principle 5: Build Time: A Server Component Does Not Need a Web Server**
>
> *A Server Component runs at build time or on each request; its output can then be server-side rendered to HTML as a separate step, so Server Components are not SSR, and a post that never changes needs no web server.*
>
> The word "server" makes developers expect a computer that renders the page for every request. For content that does not change, the framework runs the Server Component once, during the build, and the finished page can sit on static hosting.
>
> **DO THIS:**
> ```jsx
> export default ~async~ function Post() { // Runs once at build time; the page can sit on a CDN
>   const text = await readFile('post.md', 'utf8');
>   return <div dangerouslySetInnerHTML={{ __html: marked(text) }} />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function Post() {
>   const [text, setText] = useState('');
>   useEffect(() => { ~fetch('/api/post')~.then(r => r.text()).then(setText); }, []); // **WRONG:** for a post that never changes, every user downloads marked and waits for a second request
>   return <div dangerouslySetInnerHTML={{ __html: marked(text) }} />;
> }
> ```

### A Server Component with No Web Server

The name says "server", so most developers expect a computer that waits for users and renders the page each time one arrives. Our post does not need that computer at all.

**A Server Component can run once, while the team builds the app, and never again.** react.dev names the two places where Server Components run: once at build time on your CI server, or for each request on a web server.
- A **web server** is a computer that stays on and answers the request of every user.
- A **CI server** is the machine where the team's build runs, each time someone changes the code.

Our post does not change after the author publishes it, so the build is the right place.

### The Path from the Build to the Phone

Here is the path of our page, from the build to the user's phone:
1. The team builds the app on the CI server. The framework calls `Post`. `Post` reads the post file and runs `marked`.
2. The rendered output of `Post` can then be turned into the first HTML of the page. The result is uploaded to a CDN, a static hosting service that only hands out finished files (as seen in Lesson 46).
3. A user opens the page. The browser never sees the original `Post` component or `marked`. It sees only the rendered output.
4. Of our files, only `LikeButton.jsx`, a Client module, arrives as code, so the button can count taps.

No step after the build needs a computer that renders the post. react.dev says it plainly: Server Components can run at build time, so a web server is not required.

### Server Components and Server-Side Rendering: Two Separate Steps

Step 2 has its own name: **server-side rendering**, or SSR. It turns rendered components into the first HTML of the page (Lesson 102 teaches it in full).

Server Components and server-side rendering both happen before the page reaches the browser, and both carry the word "server". It looks the same, but it is NOT the same thing! They answer two different questions:
- **A Server Component** answers where a component's code runs. Its code and its libraries stay out of the bundle.
- **Server-side rendering** answers what the first HTML of the page contains, so the user sees content before any JavaScript runs.

react.dev keeps them apart. Server Components run in an environment separate from your client app or your SSR server. Their output can then be server-side rendered, as a separate step. One can be used without the other.

```tree caption="Server Components decide where a component's code runs; server-side rendering turns rendered components into the page's first HTML."
Two steps that both run before the page reaches the browser
- +Server Component [`Post`] | Decides **where the code runs**: before the page is sent | `Post` and `marked` **stay out of the bundle**
- +Server-side rendering [SSR] | Turns rendered components into the page's **first HTML** | The user sees the post **before any JavaScript runs**
```

### At Build Time or on Each Request

The same `Post` code can run at build time or on each request. What changes is when the framework calls it:
- **At build time**, `Post` runs once, and every user gets the same output. It fits our published post.
- **On each request**, `Post` runs once per user, on a web server. It fits data that changes, such as a note read from a database.

The framework decides when to call `Post`. The code of `Post` is the same either way.

### The order in which React calls the components

React calls `Post` and `LikeButton` in two different places, at two different times. `Post` runs on the CI server, during the build. `LikeButton` runs later, in each user's browser:

```tree dir=right caption="The order in which React calls the components of the post page: Post at build time, LikeButton in the user's browser."
How the post page reaches the user

- +2. Optional: server-side rendering [first HTML] | The output can be turned into the page's **first HTML** | The page is **uploaded to a CDN**
```

### Summary

| Aspect | The Client-Only Habit | The Server Component Rule |
| :--- | :--- | :--- |
| **Where the data is read** | Renders empty, then fetches in an Effect through a route | An `async` Server Component awaits its data in its own body |
| **What the browser downloads** | Every imported library, even one that formats a text that never changes | Only Client modules; a Server Component's imports stay on the server |
| **State and taps** | Any component can use `useState` and `onClick` | Only Client Components, marked with `'use client'` at the top of the file |
| **How a Server Component is marked** | Expects `'use server'` to match `'use client'` | No directive at all; `'use server'` marks Server Functions |
| **Where "server" runs** | Expects a web server rendering every request | At build time on a CI server, or on each request on a web server; SSR is a separate step |

Remember the one sentence of this lesson. **A Server Component runs before the page is sent, and the browser receives only what it rendered, never its code and never the libraries it imported.**

## For the Interview

> **The Interview Question:** What are React Server Components, and why do they exist?

### How to Answer Clearly in 30 Seconds

"A Server Component is a React component that renders ahead of time, in an environment separate from the browser. It runs once at build time, or once for each request on a web server. The browser receives only its rendered output, never its code or the libraries it imports. Server Components exist because many pages show content that is the same for every user, such as a blog post written in Markdown. Without them, every user downloads a Markdown library and waits for a second request, only to produce the same result. A Server Component can be `async` and read its data while it renders, so it needs no Effect and no API route. It cannot use state or event handlers. So the interactive parts, such as a Like button, go into Client Components marked with `'use client'`. Server Components are the default and have no directive. In practice, they come from a framework such as Next.js App Router."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does `'use server'` mark a Server Component?"**
   No. There is no directive for Server Components; they are the default in an app that uses them. `'use server'` marks Server Functions, functions on the server that the browser can call. react.dev names this confusion as a common misunderstanding.
2. **"Are Server Components the same thing as server-side rendering, and do they need a web server?"**
   No to both. A Server Component decides where a component's code runs; server-side rendering turns rendered components into the first HTML of the page. The output of Server Components can then be server-side rendered as a separate step. A Server Component can run once at build time on a CI server. The finished page can then sit on a CDN, so a web server is not required.
3. **"Do Server Components always make the bundle smaller?"**
   They shrink the JavaScript the browser downloads and runs, because only Client modules are bundled. But not always. Some components return output that is larger than their code, such as a long SVG path string. For those, react.dev says a Client Component can be better.

```tree dir=right caption="Quick comparison of Server Components and Client Components for interviews."
Server Component vs. Client Component
- +Server Component [`async function Post`] | Runs **at build time or on each request** | Can **await data** and import **heavy libraries** | **No directive**; not in the bundle
- +Client Component [`'use client'` `LikeButton`] | Its code **runs in the browser** | Can use **`useState`** and **`onClick`** | Marked with **`'use client'`**; in the bundle
```
