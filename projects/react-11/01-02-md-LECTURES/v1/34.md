# Lecture 34: When You Do Not Need an Effect

*(Where does code go when nothing outside React is involved?)*

> INTERVIEW QUESTION | ❱ CORE | When do you not need an Effect, and what replaces it?

---

## VS | Code in an Effect vs. Code in the Body or a Handler: only an Effect waits until the page is on the screen

**Use `useEffect` only to sync with something outside React; calculate derived values in the body, and handle user actions inside event handlers.**

Say a checkout form has `firstName` and `lastName` in state, and you want to display the full name on the receipt. Or say the user clicks a Buy button, and you want to send their order to the server.

**Why:** Putting `setFullName` inside `useEffect` forces React to render twice on every keystroke: once with the old full name, and again after the Effect runs. And putting the Buy request inside an Effect instead of `onClick` risks running the order again whenever another piece of state changes.

You just learned `useEffect` in Lesson 32. Now every problem starts to look like an Effect. It is the most common mistake right after that lesson, so let's take it apart.

Start with plain JavaScript. You have a first name and a last name, and you want the full name. You simply calculate it:

```js title="Plain JavaScript: a full name from two names"
const firstName = 'Taylor';
const lastName = 'Swift';
const ~fullName = firstName + ' ' + lastName~; // Calculated on the spot: Taylor Swift
```

Nobody sets up a listener that watches the two names and copies the full name somewhere. You calculate it where you need it.

And when the user clicks a button, the code for that click goes into the click listener:

```js title="Plain JavaScript: the code for a click goes into the click listener"
button.addEventListener('click', () => {
  ~sendOrder(items)~; // Runs once for each click
});
```

React works exactly the same way. The body of the component is where you calculate. The event handler is where you react to a click. An Effect is a third place, with a narrow job.

> [!DEFINITION]
> **What is an Effect?** [REVIEW] An Effect is code that React runs because the component is on the screen, not because the user clicked.
> You write it with `useEffect`. React runs it last: first it calls your component, then it puts the result into the DOM, and only then does it run the Effect.
> In development, Strict Mode mounts the component, removes it, and mounts it again, so an Effect with no cleanup runs twice.
> Its real job is to keep the component in sync with a system outside React, such as a server or a browser timer (Lesson 32).

### One question decides it: why does this code need to run?

React's docs give one test for every piece of code: "ask yourself *why* this code needs to run." There are three answers, and each answer has its own place:
1. **To show a value calculated from state or props**, such as a cart total. Calculate it in the body, during rendering.
2. **Because the user did something**, such as clicking `Place order`. Put it in the event handler of that click.
3. **Because the component is on the screen**, and it must stay in sync with something outside React, such as a server that counts visits. That is an Effect.

```tree caption="The docs' test for any code in a component: why does this code need to run?"
Why does this code need to run?
- +To show a value calculated from state or props [`const total`] | Example: **the total line** | Calculate it **in the body**, during rendering
- +Because the user did something [`onClick`] | Example: **the click on Place order** | Put it in **that click's handler**
- +Because the component is on the screen [`useEffect`] | Example: **a visit sent to a server** | Keep it in **an Effect**
```

The first two answers need no Effect at all. The docs say it in one line: when no external system is involved, "you shouldn't need an Effect."

### The Rule of Thumb: calculate in the body, react in the handler

**Can you calculate it from state or props? Then it is a `const` in the body. Did a click cause it? Then it goes in the click's handler. Only what the screen itself causes goes in an Effect.**

A senior developer also knows the three classic mistakes:
1. **"The total depends on the items, so watch the items with an Effect."** The cart renders once with the old total, then a second time.
2. **"After the click, send the order when the thank-you line appears."** The order goes out twice in development, and again later with no click at all.
3. **"Effects run twice in development, so move every Effect out."** Some Effects belong exactly where they are.

The rest of the lesson shows each mistake on a real shopping cart.

## SECTION | A Cart with Socks and a Hat

Our page is a shopping cart with two items, `Socks` at $5 and `Hat` at $20. Each row has a Remove button. Under the rows sit the total and a `Place order` button.

```page width=text caption="The cart when the page opens."
heading: Your cart
line: Socks $5 [Remove]
line: Hat $20 [Remove]
line: Total: $25
line: [Place order]
console: quiet
```

The user does two things on this page:
1. **Clicks Remove on `Hat`.** The row goes away, and the total line shows `Total: $5`.
2. **Clicks `Place order`.** The button turns into the line `Thank you! Your order is placed.`, and the order goes to the server once.

Here is the code a developer writes right after learning `useEffect`. It has two Effects: one sets the total, and one sends the order. `App` keeps three state variables:
1. `items`, the rows of the cart.
2. `total`, a copy of the total that the first Effect sets.
3. `isOrdered`, which turns `true` on the click, so the thank-you line takes the place of the button.

```jsx title="src/App.jsx"
import { useState, useEffect } from 'react';
import OrderPlaced from './components/OrderPlaced.jsx';

const initialItems = [
  { id: 1, name: 'Socks', price: 5 },
  { id: 2, name: 'Hat', price: 20 },
];

export default function App() {
  const [items, setItems] = useState(initialItems);
  const [total, setTotal] = useState(0);
  const [isOrdered, setIsOrdered] = useState(false);

  useEffect(() => {
    ~setTotal~(items.reduce((sum, item) => sum + item.price, 0)); // Copies the total into state after the render
  }, [items]);

  function handleRemove(id) {
    setItems(items.filter(item => item.id !== id));
  }

  return (
    <main>
      <h1>Your cart</h1>
      <ul>
        {items.map(item => (
          <li key={item.id}>
            {item.name} ${item.price} <button onClick={() => handleRemove(item.id)}>Remove</button>
          </li>
        ))}
      </ul>
      <p>Total: $~{total}~</p> {/* Shows whatever total holds in state */}
      {isOrdered ? (
        ~<OrderPlaced items={items} />~ /* Appears after the click on Place order */
      ) : (
        <button onClick={() => setIsOrdered(true)}>Place order</button>
      )}
    </main>
  );
}
```

One detail looks like JavaScript and is not: the dollar sign in `${item.price}`. It is NOT a template string. We are in JSX, not inside backticks. So the `$` is plain text on the page, and the curly braces after it show the number. The row reads `Socks $5`.

The Remove button keeps every item except the one clicked, with `.filter` (Lesson 19).

The thank-you line is its own component. It holds the second Effect, the one that sends the order:

```jsx title="src/components/OrderPlaced.jsx"
import { useEffect } from 'react';
import { sendOrder } from '../api.js';

export default function OrderPlaced({ items }) {
  useEffect(() => {
    ~sendOrder(items);~ // Sends the order when the thank-you line appears
  }, [items]);

  return <p>Thank you! Your order is placed.</p>;
}
```

The two helpers in the api file are our own. Each one stands in for a request to a server:
1. `sendOrder` stands in for a POST request, the kind of request that sends data to the server, such as an order.
2. `logVisit` stands in for a request that tells a server the user opened the cart. Principle 3 uses it.

Here both only print a line in the Console, so we can count how many times each one runs:

```js title="src/api.js"
export function sendOrder(items) {
  console.log('Sending order: ' + items.length + ' items');
}

export function logVisit(page) {
  console.log('Visit: ' + page);
}
```

The entry file mounts `App` inside `<StrictMode>` (Lesson 07). Here are the files:

```files title="cart-page: File Explorer" caption="How the cart project files sit inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it inside `<StrictMode>`
  App.jsx | parent | Keeps `items` in state, shows the rows and the total, and renders `OrderPlaced` after the click
  api.js | helpers | Exports `sendOrder` and `logVisit`, which only print to the Console
  components/
    OrderPlaced.jsx | child | Shows the thank-you line, and at the start sends the order in an Effect
```

Both Effects run, and the page seems to work. Once it settles, it shows `Total: $25`, and in production one click sends one order. But each Effect costs the user something, and the three principles show what.

**PRINCIPLES:** An Effect is for staying in sync with something outside React. A value you can calculate needs no Effect, and neither does code caused by a click. Three principles follow:
1. **Principle 1: Calculate the Total in the Body.** An Effect that copies the total into state costs one render with the old total, then a second render.
2. **Principle 2: The Click's Handler Sends the Order.** An Effect sends it twice in development, and again after a Remove in production.
3. **Principle 3: An Effect Logs the Visit.** The visit happens because the cart is on the screen. It stays in an Effect, even though it runs twice in development.

## PRINCIPLE | `const total` in the body: the total matches the rows on every render

> [!PRINCIPLE]
> **Principle 1: Calculate the Total in the Body**
>
> *When a value can be calculated from the props or state the component already has, calculate it in the body during rendering. Do not keep it in state and set it from an Effect.*
>
> The body runs again every time items changes, so a total calculated there always matches the rows. An Effect runs only after React has rendered and put the page into the DOM. When it sets the total, React renders the whole cart again. So every change costs one render with the old total and a second render with the right one.
>
> **DO THIS:**
> ```jsx
> const [items, setItems] = useState(initialItems);
> const ~total~ = items.reduce((sum, item) => sum + item.price, 0); // Matches items on every render
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [total, setTotal] = useState(0);
> useEffect(() => {
>   ~setTotal~(items.reduce((sum, item) => sum + item.price, 0)); // **WRONG:** one render with the old total, then a second render
> }, [items]);
> ```

### VS | `fullName` set by an Effect vs. `fullName` calculated in the body: same screen, one extra render

React's docs show this mistake in its smallest form, with the full name from the start of the lesson. Here it is both ways:

```jsx title="fullName in state, set by an Effect"
const [firstName, setFirstName] = useState('Taylor');
const [lastName, setLastName] = useState('Swift');
const [fullName, setFullName] = useState('');

useEffect(() => {
  ~setFullName~(firstName + ' ' + lastName); // Runs after React has already rendered the empty fullName
}, [firstName, lastName]);
```

```jsx title="fullName calculated in the body"
const [firstName, setFirstName] = useState('Taylor');
const [lastName, setLastName] = useState('Swift');
const ~fullName~ = firstName + ' ' + lastName; // Taylor Swift, calculated on every render
```

Both show `Taylor Swift` once the page settles. It may look the same, but it is NOT the same thing. The difference is how many renders it takes to get there:
- **With `fullName` in state**, the first render shows the empty string. Then the Effect sets the name, and React renders again.
- **With `fullName` in the body**, the line runs every time React calls the component. So `fullName` always matches the names of this render.

The docs say it plainly. With the Effect, React "does an entire render pass with a stale value for `fullName`, then immediately re-renders with the updated value."

> [!DEFINITION]
> **What is a stale value?** [NEW] A stale value is an old value that no longer matches the state it was made from.
> On the first render, `fullName` in state is still the empty string, while the names are already Taylor and Swift. That empty string is stale.
> A render pass is one round of React calling your components and putting the result into the DOM. With the Effect, one render pass shows the stale value, and a second one fixes it (Lesson 34).

### Why the Effect costs a whole render

An Effect always runs last. The docs give the order: "React will first call your component functions to calculate what should be on the screen. Then React will "commit" these changes to the DOM, updating the screen. Then React will run your Effects."

And then the catch: "If your Effect *also* immediately updates the state, this restarts the whole process from scratch!"

```tree dir=right caption="Why a setter called in an Effect costs a second render: the Effect runs after the commit, so its update starts the whole process again."
One state update with a setter inside the Effect
- +1. Render [`App`] | React calls the component | The JSX holds **the stale value**
- +2. Commit | React puts **the stale value** into the DOM
- !3. Effect [`setFullName`] | The Effect **sets state** | React must **start again from step 1**
- +4. Render and commit again | The JSX holds **the new value** | The page is right **one render late**
```

You already know this rule from Lesson 22: a value you can calculate from state is not state. Copying it into state from an Effect does not get around that rule. It is the same redundant state, with one more render on top.

### The cart: the total set by an Effect renders twice

Our cart has the same shape. `total` is made from `items`, and an Effect copies it into state:

```jsx title="src/App.jsx" startLine="10"
  const [items, setItems] = useState(initialItems);
  const [total, setTotal] = useState(~0~); // The total before the Effect has run
  const [isOrdered, setIsOrdered] = useState(false);

  useEffect(() => {
    ~setTotal~(items.reduce((sum, item) => sum + item.price, 0)); // Runs after the render, then asks for another one
  }, [items]);
```

**Beware! On the first load, the cart renders twice, and the first render shows `Total: $0`.** Here is what happens:
1. React calls `App`. The total in state is still zero, so the JSX returns `Total: $0`.
2. React puts `Total: $0` into the DOM.
3. React runs the Effect, which calls `setTotal` with `25`.
4. React calls `App` again and puts `Total: $25` into the DOM.

```page width=text caption="What the first render of the cart returns, before the Effect has set the total."
heading: Your cart
line: Socks $5 [Remove]
line: Hat $20 [Remove]
line: Total: $0 | bad
line: [Place order]
console: quiet
```

Does the user actually see `Total: $0`? Sometimes. The `useEffect` reference says that when no click caused the Effect, React "will generally let the browser paint the updated screen first before running your Effect."

The browser paints only when its next frame is due. On a fast page load, both renders often finish before the first paint, and the screen goes straight to `Total: $25`. When the paint falls between them, the user sees `Total: $0` for a moment.

**After a click on Remove, one render shows a single row with the old total.** The user removes `Hat`:
1. The click calls `setItems` with only `Socks`.
2. React calls `App`. The list shows only Socks, but the total in state is still `25`. So the JSX returns `Total: $25` under one row of $5.
3. React puts that into the DOM, then runs the Effect, which calls `setTotal` with `5`.
4. React calls `App` again and shows `Total: $5`.

Here the user may never see step 2. When a click caused the Effect, the same reference says React "may run your Effect before the browser paints the updated screen." But the cost is still there: one extra render after every change of `items`. And the code carries one more state variable, one more setter, and one more Effect.

### The fix: calculate the total in the body

Delete the `total` state and its Effect. Calculate `total` in the body of `App`:

```jsx title="src/App.jsx" startLine="9"
export default function App() {
  const [items, setItems] = useState(initialItems);
  const [isOrdered, setIsOrdered] = useState(false);
  const ~total~ = items.reduce((sum, item) => sum + item.price, 0); // 25 for Socks and Hat, 5 after Hat is removed
```

`.reduce` walks the array and adds each price to `sum`, starting from zero (Lesson 27). Inside the arrow function, `sum` is the running total so far, and `item` is the current element of the array.

The JSX keeps the same line, `<p>Total: ${total}</p>`. The import line drops `useEffect`, because `App` has no Effect left. Now each change costs one render:
- **On the first load**, the first render already shows `Total: $25`.
- **After a click on Remove**, the render that removes the `Hat` row also shows `Total: $5`.

```page width=text caption="The cart after the user clicks Remove on Hat: the row and the total change in the same render."
heading: Your cart
line: Socks $5 [Remove]
line: Total: $5 | good
line: [Place order]
console: quiet
```

The docs give three reasons for this rule. Calculating in the body is:
1. **"faster"**, because there is no extra update from an Effect. The docs call these extra updates "cascading": a state update from an Effect that starts another render.
2. **"simpler"**, because you remove a state variable, a setter, and an Effect.
3. **"less error-prone"**, because two state variables can no longer get out of sync with each other.

```tree caption="The cart's total set by an Effect vs. calculated in the body: the same page once it settles, and NOT the same thing."
Two ways to show the cart's total
- !`total` in state, set by an Effect [`useState` `setTotal` `useEffect`] | First render shows **`Total: $0`** | Every change of `items` costs **a second render**
- +`total` calculated in the body [`const total`] | First render shows **`Total: $25`** | Every change of `items` costs **one render**, and the total always matches the rows
```

### The linter finds this Effect for you

The React team ships a lint plugin, `eslint-plugin-react-hooks`. Its rule `set-state-in-effect` reports a setter called directly inside an Effect, such as `setTotal` here. Its docs describe it as a rule that "Validates against calling setState synchronously in an effect, which can lead to re-renders that degrade performance."

Remember: if you can calculate it, calculate it in the body.

## PRINCIPLE | `sendOrder` in the click's handler: one click sends exactly one order

> [!PRINCIPLE]
> **Principle 2: The Click's Handler Sends the Order**
>
> *When code runs because the user did one thing, such as clicking Place order, put it in that click's handler. Do not put it in an Effect that runs when a component appears or when a state value changes.*
>
> A click happens once, and its handler runs once. An Effect runs every time its component mounts or its dependencies change, and by then it does not know what the user did. So an order sent from an Effect goes out twice in development, and again in production when a dependency changes, such as after a Remove.
>
> **DO THIS:**
> ```jsx
> function handlePlaceOrder() {
>   ~sendOrder(items);~ // Runs once for each click on Place order
>   setIsOrdered(true);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function OrderPlaced({ items }) {
>   useEffect(() => {
>     ~sendOrder(items);~ // **WRONG:** runs on every mount and every change of items
>   }, [items]);
>   return <p>Thank you! Your order is placed.</p>;
> }
> ```

### VS | `sendOrder` in the click's handler vs. in an Effect: a click happens once, an Effect can run many times

Remember the plain JavaScript version: the code for a click goes into the click listener. In React, that listener is the event handler. Here is the same line in two places:

```jsx title="sendOrder in the click's handler"
function handlePlaceOrder() {
  ~sendOrder(items);~ // Runs once for each click by the user
  setIsOrdered(true);
}
```

```jsx title="sendOrder in an Effect of OrderPlaced"
useEffect(() => {
  ~sendOrder(items);~ // Runs every time OrderPlaced mounts, and every time items changes
}, [items]);
```

In production, the first click prints one `Sending order: 2 items` with either version. It may look the same, but it is NOT the same thing:
- **The handler** runs once for each click by the user.
- **The Effect** runs every time `OrderPlaced` mounts, and every time its `items` change.

This Effect is easy to write by mistake, because it looks tied to the click. The thank-you line only appears after the click, right? But the Effect knows nothing about the click. It only knows that the thank-you line is on the screen.

The docs say it in one sentence: "By the time an Effect runs, you don't know *what* the user did." They say the same of a Buy button. You do not buy when the user visits the page: "you want to buy it when the user *clicks* the Buy button."

### In development, one click sends the order twice

**Beware! The order goes out every time `OrderPlaced` mounts, so in development one click sends it twice.** This is what the user sees after one click on `Place order`:

```page width=text caption="The cart after one click on Place order, with the order sent by an Effect: in development, the Console shows the order twice."
heading: Your cart
line: Socks $5 [Remove]
line: Hat $20 [Remove]
line: Total: $25
line: Thank you! Your order is placed.
log: Sending order: 2 items | api.js:2
log: Sending order: 2 items | api.js:2
```

Here is what happens behind the two lines:
1. The user clicks Place order, and the click sets `isOrdered` to `true`.
2. React renders `App`, and `OrderPlaced` takes the place of the button.
3. React mounts `OrderPlaced` and runs its Effect. The Console prints `Sending order: 2 items`.
4. In development, Strict Mode mounts `OrderPlaced` a second time to test it. There is no cleanup, so the Effect runs again and prints the line a second time.

The docs show this exact shape: "This Effect fires twice in development, exposing a problem in the code." The second line is not the bug. It shows you the bug: the order is tied to the thank-you line being on the screen, and that line can mount again.

### In production, a Remove sends another order

In production, the Console shows one line after the click. So is it fine there? No.

The rows stay on the page above the thank-you line. When the user clicks Remove on `Hat`, `items` changes. The Effect lists `[items]`, so it runs again and sends another order, with one item. No one clicked `Place order`. Here is the page in development after the click on `Place order` and then the click on Remove:

```page width=text caption="The cart after one click on Place order and then one click on Remove on Hat, with the order sent by an Effect: the Remove sends one more order."
heading: Your cart
line: Socks $5 [Remove]
line: Total: $5
line: Thank you! Your order is placed.
log: Sending order: 2 items | api.js:2
log: Sending order: 2 items | api.js:2
log: Sending order: 1 items | api.js:2
```

The docs put the cost in one line: "You wouldn't want to buy the product twice."

### VS | An Effect that waits for `isOrdered` vs. the click's handler: one click works, a Remove still sends a second order

Some developers keep the Effect, but move it up into `App`. There it waits for `isOrdered` to turn `true`:

```jsx title="sendOrder in an Effect of App that waits for isOrdered"
useEffect(() => {
  if (~isOrdered~) { // **WRONG:** the order now follows a state value, not the click
    sendOrder(items);
  }
}, [isOrdered, items]);
```

One click prints one `Sending order: 2 items`, even in development. Why? `App` was already on the screen when `isOrdered` changed, so there is no new mount to repeat.

But the order still follows a state value, not the click. When the user clicks Remove after placing the order, `items` changes while `isOrdered` is still true. The Effect runs, and it sends a second order with one item.

The docs call this shape "Event-specific logic inside an Effect". Event-specific logic is code that runs because of one interaction, such as one click on `Place order`. It belongs in the handler of that interaction.

### The fix: move `sendOrder` into the click's handler

Write a handler, `handlePlaceOrder`, call `sendOrder` inside it, and give it to the button:

```jsx title="src/App.jsx" startLine="19"
  function handlePlaceOrder() {
    ~sendOrder(items);~ // 1. Sends the order, once for this click
    setIsOrdered(true); // 2. Then shows the thank-you line
  }
```

```jsx title="src/App.jsx" startLine="35"
      {isOrdered ? (
        ~<OrderPlaced />~ /* No props: the thank-you line only shows text now */
      ) : (
        <button ~onClick={handlePlaceOrder}~>Place order</button> /* The click runs handlePlaceOrder */
      )}
```

`App` now imports `sendOrder` from the api file. The handler reads `items` from its own component, so `OrderPlaced` needs no props. It loses its Effect and keeps only its line:

```jsx title="src/components/OrderPlaced.jsx"
export default function OrderPlaced() {
  return ~<p>Thank you! Your order is placed.</p>~; // The page shows the same line as before
}
```

One click now sends one order, in development and in production. A later Remove sends nothing:

```page width=text caption="The cart after one click on Place order, with the order sent by the click's handler: the Console shows the order once."
heading: Your cart
line: Socks $5 [Remove]
line: Hat $20 [Remove]
line: Total: $25
line: Thank you! Your order is placed. | good
log: Sending order: 2 items | api.js:2
```

### A ref that blocks the second run is not a fix

You saw this trick in Lesson 32: a ref that remembers "I already sent it" and blocks the second run of the Effect. Here the Console would show one line, and even a Remove would send nothing. The page would look fixed.

But the order would still be tied to the thank-you line, not to the click. Each new `OrderPlaced` starts with a new ref and sends the order again. The fix is to delete the Effect.

```tree caption="Three places for sendOrder: an Effect of the thank-you line, an Effect that waits for isOrdered, and the click's handler."
Where `sendOrder` runs
- !In an Effect of `OrderPlaced` [`useEffect`] | Runs on **every mount** of the thank-you line and **every change of `items`** | **Twice** in development, and **again after a Remove**
- !In an Effect of `App` that waits for `isOrdered` [`isOrdered`] | Runs whenever **`isOrdered` is true and `items` changes** | A Remove after the order **sends a second order**
- +In the click's handler [`handlePlaceOrder`] | Runs **once for each click** by the user | **One order**, in development and in production
```

Remember: if the user caused it, put it in the event handler.

## PRINCIPLE | `useEffect` for `logVisit`: the visit is logged every time the cart appears on the screen

> [!PRINCIPLE]
> **Principle 3: An Effect Logs the Visit**
>
> *When code runs because the component was shown, and it talks to something outside React, such as a server that counts visits, keep it in an Effect. Running twice in development is not a reason to move it.*
>
> The visit happens because the cart is on the screen, so there is no click whose handler could hold it. In development, Strict Mode runs the setup a second time, and the Console shows two visits. That extra visit changes nothing the user sees, and in production there is one.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   ~logVisit('cart');~ // Runs because the cart is on the screen
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const didLog = useRef(false);
> useEffect(() => {
>   if (~didLog.current~) return; // **WRONG:** blocks the second run instead of letting it run twice in development
>   didLog.current = true;
>   logVisit('cart');
> }, []);
> ```

So far we deleted two Effects. Does that mean every Effect is suspicious? No. Here is one that stays.

Shops count how many users open the cart. Each time the cart is shown, the page sends an analytics event: a message to a server that counts what users see and do. Here, `logVisit` stands in for it.

No click causes this visit. The cart is on the screen, and that is the whole reason. The docs say the same about a form: "the _reason_ to send the analytics event is that the form was displayed."

So this code goes in an Effect. The empty array makes it run after the first mount only (Lesson 32):

```jsx title="src/App.jsx" startLine="10"
export default function App() {
  const [items, setItems] = useState(initialItems);
  const [isOrdered, setIsOrdered] = useState(false);
  const total = items.reduce((sum, item) => sum + item.price, 0);

  useEffect(() => {
    ~logVisit('cart');~ // Runs because the cart is on the screen
  }, ~[]~); // Empty array: runs after the first mount only
```

The first import line brings back `useEffect`. The import from the api file adds `logVisit` next to `sendOrder`.

### VS | The visit in an Effect vs. the order in an Effect: both print twice, only the order hurts the user

In development, `Visit: cart` prints twice on the first load, just like the order in Principle 2:

```page width=text caption="The cart on the first load in development: the visit Effect prints twice."
heading: Your cart
line: Socks $5 [Remove]
line: Hat $20 [Remove]
line: Total: $25
line: [Place order]
log: Visit: cart | api.js:6
log: Visit: cart | api.js:6
```

Strict Mode mounts `App` a second time to test it. There is no cleanup, so the setup runs again and prints the second line. In production, the Console prints one line.

Both Effects print twice in development. It may look the same, but it is NOT the same thing:
- **The visit** is caused by the cart being on the screen. One extra visit changes nothing the user sees.
- **The order** is caused by a click. One extra order charges the user twice.

The docs keep this code as it is: "**We recommend keeping this code as is.**"

The reason: "there is no *user-visible* behavior difference between running it once and running it twice." And: "**In production, there will be no duplicate visit logs.**"

The extra visits in development do not matter either. As the docs put it, "you don't want the logs from the development machines to skew the production metrics." So there is nothing to fix with a ref, and no reason to move the call out of the Effect.

The docs put the whole lesson in two sentences: "If this logic is caused by a particular interaction, keep it in the event handler. If it's caused by the user _seeing_ the component on the screen, keep it in the Effect."

```tree caption="Two Effects that print twice in development: the visit stays in its Effect, and the order moves to the click's handler."
Two Effects that run twice in development
- +`logVisit` in an Effect [`logVisit`] | Runs because **the cart is on the screen** | An extra visit **changes nothing the user sees**: it stays
- !`sendOrder` in an Effect [`sendOrder`] | Runs, but it was caused by **a click** | An extra order **charges the user twice**: it moves to the handler
```

Remember: only what the screen itself causes goes in an Effect.

## All 3 Principles Together

### The complete files

The entry file mounts `App` inside `<StrictMode>`:

```jsx title="src/main.jsx"
import App from './App.jsx';

  ~<StrictMode>~ {/* In development: mounts twice, so an Effect with no cleanup runs twice */}

  </StrictMode>

```

`App` calculates the total, sends the order from the click, and logs the visit in its one Effect:

```jsx title="src/App.jsx"
import { useState, useEffect } from 'react';
import OrderPlaced from './components/OrderPlaced.jsx';
import { sendOrder, logVisit } from './api.js';

const initialItems = [
  { id: 1, name: 'Socks', price: 5 },
  { id: 2, name: 'Hat', price: 20 },
];

export default function App() {
  const [items, setItems] = useState(initialItems);
  const [isOrdered, setIsOrdered] = useState(false);
  const ~total~ = items.reduce((sum, item) => sum + item.price, 0); // Principle 1: calculated in the body

  useEffect(() => {
    ~logVisit('cart');~ // Principle 3: runs because the cart is on the screen
  }, []);

  function handleRemove(id) {
    setItems(items.filter(item => item.id !== id));
  }

  function handlePlaceOrder() {
    ~sendOrder(items);~ // Principle 2: runs once for each click on Place order
    setIsOrdered(true);
  }

  return (
    <main>
      <h1>Your cart</h1>
      <ul>
        {items.map(item => (
          <li key={item.id}>
            {item.name} ${item.price} <button onClick={() => handleRemove(item.id)}>Remove</button>
          </li>
        ))}
      </ul>
      <p>Total: ${total}</p>
      {isOrdered ? (
        <OrderPlaced />
      ) : (
        <button onClick={handlePlaceOrder}>Place order</button>
      )}
    </main>
  );
}
```

`OrderPlaced` only shows the thank-you line:

### How React renders the cart and runs its one Effect

On the first load, React calls `App` once, puts the cart with the right total into the DOM, and runs the one Effect. On the click, the handler sends the order before React renders the thank-you line:

```tree dir=right caption="The order of events in the finished cart, from the first load to the thank-you line."
From the first load to the thank-you line
- +1. Render [`App`] | React calls `App`; **`total` is 25** | The JSX returns **`Total: $25`** at once
- +2. Commit | React puts the rows, the total, and the button **into the DOM**
- +3. Effect [`logVisit`] | React runs the setup | The Console prints **`Visit: cart`**, twice in development
- +4. Click [`handlePlaceOrder`] | The user clicks **Place order** | `sendOrder` prints **`Sending order: 2 items`** once, then `setIsOrdered` asks for a render
- +5. Render and commit [`OrderPlaced`] | React calls `App`, then `OrderPlaced` | The thank-you line **replaces the button**
```

### Where the code runs, and what the user gets

| Where the code runs | What the user gets | Why |
| :--- | :--- | :--- |
| **`total` in state, set by an Effect** | The right total, one render late: `Total: $0` on the first render | The Effect runs after the commit, and its setter starts another render |
| **`total` calculated in the body** | The right total in the same render as the rows | The body runs again on every change of `items` |
| **`sendOrder` in an Effect of `OrderPlaced`** | Two orders in development, and another order after a Remove | The Effect runs on every mount of the thank-you line and every change of `items` |
| **`sendOrder` in an Effect that waits for `isOrdered`** | A second order after a Remove that follows the order | The Effect runs whenever `items` changes while `isOrdered` is `true` |
| **`sendOrder` in `handlePlaceOrder`** | One order for each click | The handler runs once for each click by the user |
| **`logVisit` in an Effect** | Nothing different on the page; two visit lines in development only | The visit is caused by the cart being on the screen |

One last time, the sentence of this lesson: **An Effect is for staying in sync with something outside React. If you can calculate it, calculate it in the body. If the user caused it, put it in the event handler.**

## For the Interview

> **The Interview Question:** When do you not need an Effect, and what replaces it?

### How to Answer Clearly in 30 Seconds

"Effects are an escape hatch for staying in sync with a system outside React. When no external system is involved, I usually do not need one. I ask why the code needs to run:
1. **To show a value calculated from props or state**, such as a cart total: I calculate it in the component body during rendering. An Effect that copies it into state costs a render pass with a stale value, and then a second render.
2. **Because the user did something**, such as clicking Place order: I put it in that event's handler. By the time an Effect runs, it does not know what the user did. So an order sent from an Effect goes out twice in development, and again whenever its dependencies change.
3. **Because the component is on the screen**, such as an analytics visit: that stays in an Effect, and running twice in development is fine.

The lint rule `set-state-in-effect` helps me find a setter called directly in an Effect."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What if the calculation is slow? Shouldn't it go in an Effect then?"**
   No. A slow calculation is cached with `useMemo`, not moved into an Effect. The docs: "To cache expensive calculations, add `useMemo` instead of `useEffect`." Most calculations are not slow: "unless you're creating or looping over thousands of objects, it's probably not expensive." Lesson 56 teaches `useMemo`. The React Compiler, which Lesson 63 teaches, "can automatically memoize expensive calculations for you".
2. **"How do you reset a child's state when a prop changes, without an Effect?"**
   Give the child a different `key` (Lesson 25). The docs' example is a profile page that renders `<Profile userId={userId} key={userId} />`, so React starts the profile's state over for each user. An Effect that calls the setters when `userId` changes renders the old state first, and then renders again, just like the total. To change only part of the state, the docs prefer to store less, such as a `selectedId`, and to calculate the rest during rendering.
3. **"Should a fetch move to an event handler too?"**
   Usually not. The docs: "You *don't* need to move this fetch to an event handler." The results must match the query while the component is visible, whatever caused the query to change. So a fetch is a job for an Effect, with a cleanup that drops late answers (Lesson 33). The same test decides it: the data is needed because the component is on the screen.

```tree dir=right caption="Interview comparison: what replaces an Effect in each case, and what stays an Effect."
What replaces an Effect
- +A value calculated from props or state [`const total`] | **Calculate it in the body** | A slow one is cached with **`useMemo`**, not an Effect
- +Code caused by one interaction [`handlePlaceOrder`] | **Put it in the event handler** | It runs **once for each click**
- +A child's state that must start over [`key`] | **Give the child a different `key`** | React **starts its state over**
- +Code caused by the component being on the screen [`useEffect`] | **Keep the Effect** | A visit log or a fetch **stays**, and may run twice in development
```
