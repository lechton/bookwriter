# Lecture 99: How Old Code Wrote Refs: String Refs, Ref Callbacks, createRef, and forwardRef

*(How did old React code reach a real `<input>` element before `useRef` existed?)*

> INTERVIEW QUESTION | LEGACY | How did refs work before hooks: createRef, callback refs, and forwardRef?

---

## VS | Today's `useRef` vs. Old Class Refs: the same job, but React puts the element in a different place

> You already know the modern way: you create a ref with `useRef`, and React puts the real `<input>` element into it. **Before Hooks, class components did the same job with a string, a function, or `createRef`.** React 19 removed the string, so old code must be translated.

Every ref answers one question: **where does React put the element?** Remember Lesson 31. In plain JavaScript, you grab the element yourself with `document.getElementById`. In React, you never create the elements. React creates them from your JSX, so you ask React to hand you the element. Today a function component asks with `useRef`. But React existed long before Hooks, and class components needed the same thing. Teams still maintain a lot of that code, so when you open an old class, you meet the old ways. Those classes also passed refs to their own components with `forwardRef`, and React 19 changed that too.

Take a chat app such as WhatsApp Web or Slack. At the bottom sits one message field and a Send button. The user types Hi and clicks Send. The field empties, and the cursor stays in it, so the user types the next message without clicking the field again. Ask yourself: who puts the cursor back? The click on Send took the focus away from the field, and JSX has no prop that says "put the cursor here now" (Lesson 31). So the Send handler must reach the real `<input>` element and call the browser's `focus()` on it.

**Why:** The old ways look like four spellings of the same thing, so developers translate old code line by line. They are not the same. React 19 rejects one of them, and the whole page goes blank. Another one, copied into a function component, makes a new object on every render, and a timer saved in it never stops. To migrate old code safely, you need to know where each way puts the element.

### The Same Job, Four Ways

Start from what you know. Here is the same job in plain JavaScript and in today's React:

```jsx title="Plain JavaScript and today's React"
document.~getElementById('message')~.focus(); // Plain JavaScript: you grab the element yourself
~inputRef.current~.focus(); // Today's React: React put the element into the ref for you
```

The second line works because the JSX says `<input ref={inputRef} />`. Old class code wrote that `ref` differently. Here is the same message field, written the four ways you meet in real code:

```jsx title="Four ways to ask React for the same input element"
<input ~ref="input"~ /> {/* 1. A string: the handler reads this.refs.input */}
<input ~ref={el => { this.input = el; }}~ /> {/* 2. A function: the handler reads this.input */}
<input ~ref={this.inputRef}~ /> {/* 3. An object from createRef: the handler reads this.inputRef.current */}
<input ~ref={inputRef}~ /> {/* 4. An object from useRef: the handler reads inputRef.current */}
```

For the user, all four do the same thing. In React 18, each one puts the cursor back after Send.

For React, they are four different things, because each one puts the element in a different place:
1. **A string, `ref="input"`.** React keeps the element in an object called `this.refs`, under the name `input`. React 19 removed this way.
2. **A function.** React calls your function and hands it the element. Your function decides where to keep it, here in `this.input`.
3. **An object from `createRef`.** React puts the element into the object's `current` field.
4. **An object from `useRef`.** Exactly the same as `createRef`: React puts the element into `current`.

```tree caption="Four ways to give the same input element to a ref, and where React puts the element each time."
Where each way of writing a ref keeps the `<input>` element
- !A string [`ref="input"`] | React keeps it **under a name** in `this.refs` | **Removed** in React 19
- +A function [`ref={el => ...}`] | React **calls your function** with the element | Your code keeps it in **`this.input`**
- +An object from `createRef` [`ref={this.inputRef}`] | React **fills `current`** of an object the class keeps | Made **once per instance** in a class
- +An object from `useRef` [`ref={inputRef}`] | React **fills `current`** of an object React keeps | The way of **function components today**
```

The objects from `createRef` and `useRef` have the same shape: one field named current, set to null. Inside a class, `createRef` is fine. Copy that same line into a function component, though, and it makes a brand-new object on every render. That is the classic mistake when a class becomes a function.

> [!DEFINITION]
> **What is a ref?** [REVIEW] A ref is a plain object with one field, `current`. `useRef(null)` returns `{ current: null }`, and React gives you back the same object on every render.
> Put it on a tag, `<input ref={inputRef} />`, and React puts the real `<input>` element into `inputRef.current` when the element appears on the page.
> From then on, it is the same element `document.getElementById` would return, so you can call `inputRef.current.focus()` (Lesson 31).

> [!DEFINITION]
> **What is a class component, and what is its instance?** [REVIEW] Before Hooks, a component was usually a class: `class MessageForm extends Component`. When the component appears on the page, React creates one object from that class. This object is the instance.
> Inside the class, you reach the instance as `this`. State lives in `this.state` and changes with `this.setState`.
> Any field you write on it, such as `this.input`, stays there for as long as the component is on the page (Lesson 96).

### The Rule of Thumb: where does React put the element?

**Ask one question about every old ref: where does React put the element? Then move it to the place a function component uses today: `useRef` on a tag, or `ref` as a prop.**

You meet these ways in three places of real code:
1. **In a class component.** A string ref, which React 19 removed. A ref callback, which still works. Or `createRef`, which React still exports as a Legacy React API.
2. **In a function component.** `useRef`, the way of today. Or a ref callback for special cases (Lessons 31 and 86).
3. **On your own component.** `forwardRef` in React 18 and earlier, which still works and will be deprecated. Or `ref` as an ordinary prop in React 19 (Lesson 85).

```tree caption="Where each way of writing a ref lives today: in class components, in function components, and on your own components."
Ways of writing a ref that you meet in real code
- +In a class component [`ref="input"` `ref={el => ...}` `createRef`] | The string is **removed** in React 19 | The function and `createRef` **still work**
- +In a function component [`useRef` `ref={el => ...}`] | `useRef` is **the way of today** | A function still works for special cases
- +On your own component [`forwardRef` `ref` as a prop] | `forwardRef` belongs to **React 18 and earlier** | React 19 passes `ref` **as an ordinary prop**
```

This lesson teaches you to read this old code and translate it. It does not ask you to write new code with string refs or `createRef`.

Here is the starting point, an old class with no ref yet:

```jsx title="src/MessageForm.jsx"
import { Component } from 'react';

export default class MessageForm extends Component {
  state = { text: '' };

  handleChange = (e) => {
    this.setState({ text: e.target.value });
  };

  handleSend = () => {
    ~this.setState({ text: '' })~; // The easy part: the field empties
  };

  render() {
    return (
      <div>
        <input
          value={this.state.text}
          onChange={this.handleChange}
          placeholder="Write a message..."
        />
        <button onClick={this.handleSend}>Send</button>
      </div>
    );
  }
}
```

The empty field is the easy part. The handler sets `text` back to an empty string, and the controlled `<input>` shows it (Lesson 20).

The cursor is the hard part. For that, the handler needs the real `<input>` element, and every principle below reaches it in a different way.

Our chat field grows in three steps:
1. In Principles 1 to 3, it lives in one file, `MessageForm.jsx`, a class component.
2. In Principle 4, `MessageForm` becomes a function component.
3. In Principles 5 and 6, the `<input>` moves into its own file, `MessageInput.jsx`, because the same field sits in every chat of the app. In Principle 6, a function named `withTracking` wraps it.

We leave out the list of sent messages and the server. Only the field and the button remain, because the cursor is the whole question.

```files title="chat-field: File Explorer" caption="The files of the chat field at the end of the lesson, inside src/."
src/
  main.jsx | boundary | Imports `MessageForm` from `./MessageForm.jsx` and mounts it inside `<StrictMode>`
  MessageForm.jsx | parent | Exports `MessageForm` as default, holds `text` in state, and imports `MessageInput` and `withTracking`
  MessageInput.jsx | child | Exports `MessageInput` as default and renders the `<input>`, from Principle 5 on
  withTracking.jsx | wrapper | Exports `withTracking`, which wraps a component, from Principle 6 on
```

**PRINCIPLES:** Every way of writing a ref tells React where to put the element. Six principles follow:
1. **String refs: React 19 removed `ref="input"`.** The page goes blank, so move to a ref callback or to `createRef`.
2. **Ref callbacks: React calls your function with the element, and later with `null`.** A new function on every render means both calls after every keystroke.
3. **`createRef` in a class: one object per instance.** React fills its `current` field.
4. **`createRef` in a function: a new object on every render.** Focus still works, but a timer ID is lost, so use `useRef`.
5. **A ref on a class component holds the instance.** The parent gets the whole component and can call its methods.
6. **`forwardRef`: every component on the way must pass the ref on.** In React 19, `ref` is a prop, and `forwardRef` is no longer necessary.

## PRINCIPLE | `ref="input"`: React 19 no longer reads the string, and the page goes blank

> [!PRINCIPLE]
> **Principle 1: String Refs: React 19 Removed `ref="input"` and `this.refs`**
>
> *In an old class, a string on `ref` told React to keep the element in `this.refs` under that name; React 19 removed string refs, so move them to a ref callback or to `createRef`.*
>
> In React 18, a string ref works, and the cursor comes back after Send. React 19 no longer reads the string. It stops rendering with an error, and the whole page goes blank. Run the React 19 codemod, or rewrite the line by hand with a ref callback or with `createRef`.
>
> **DO THIS:**
> ```jsx
> inputRef = createRef();
> handleSend = () => {
>   ~this.inputRef.current~.focus(); // React 19 fills the object, so the cursor comes back
> };
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> handleSend = () => {
>   ~this.refs.input~.focus(); // **WRONG:** React 19 removed string refs, and the page goes blank
> };
> ```

In the oldest class code, `ref` holds a plain string:

```jsx title="A string ref in a class"
<input ~ref="input"~ /> {/* You write only a name */}
~this.refs.input~.focus(); // React kept the element under that name
```

This is a **string ref**. You write only a name, and React does the rest.

Your code never creates `this.refs`. In React 18 and earlier, React kept this object on every class instance, with one field for each string ref. When React put the `<input>` on the page, it saved the element in that object under the name `input`. So `this.refs` is a plain object that React filled for you. It has one field, named input, and that field holds the `<input>` element.

Here is our chat field with a string ref:

```jsx title="src/MessageForm.jsx"
import { Component } from 'react';

export default class MessageForm extends Component {
  state = { text: '' };

  handleChange = (e) => {
    this.setState({ text: e.target.value });
  };

  handleSend = () => {
    this.setState({ text: '' }); // The field empties
    ~this.refs.input~.focus(); // The cursor goes back into the field
  };

  render() {
    return (
      <div>
        <input
          ~ref="input"~ // React keeps this input under the name input
          value={this.state.text}
          onChange={this.handleChange}
          placeholder="Write a message..."
        />
        <button onClick={this.handleSend}>Send</button>
      </div>
    );
  }
}
```

In React 18 and earlier, this works. The user types Hi:

```page caption="With a string ref in React 18: the user types Hi into the message field."
card: typed=Hi
line: [Send]
```

The user clicks Send. The field empties, and the cursor is back in it:

```page caption="With a string ref in React 18: after Send, the field is empty and the cursor is in it."
card: typed= | good=typed
line: [Send]
```

### React 19 removed string refs

String refs were deprecated in March 2018, in React 16.3.0. React's upgrade guide says they were "replaced by ref callbacks due to multiple downsides". React 19 removes them, "to make React simpler and easier to understand".

**Beware! In React 19, the same class does not just lose the cursor. The whole page goes blank as soon as it opens.** Here is what happens on the first render:
1. React renders the `<input>` and finds a string on its `ref`.
2. React 19 accepts only a function, a ref object, or nothing on `ref`. So it stops rendering and throws an error.
3. Nothing in our app catches that error, so React removes everything it rendered.

```page caption="With a string ref in React 19: the page is blank when it opens, and the Console shows why."
blank
console: Uncaught Error: Expected ref to be a function, an object returned by React.createRef(), or undefined/null.
  warn: An error occurred in the <input> component.
```

The upgrade guide gives a codemod, a tool that rewrites the code for you. It turns every string ref into a ref callback:

```bash title="Terminal"
npx codemod@latest react/19/replace-string-ref
```

React's list of removed APIs names the other way: "`this.refs`: use `createRef` instead." Both replacements are valid. Principle 2 shows the ref callback, and Principle 3 shows `createRef`.

Here is where readers usually go wrong. `ref="input"` and `ref={inputRef}` look like two spellings of the same ref. They are not. `ref="input"` is a name that only class components could use, and React 19 no longer reads it. `ref={inputRef}` hands React an object that your code owns, and React 19 fills it as before.

## PRINCIPLE | Ref callback: React calls your function with the element, and later with `null`

> [!PRINCIPLE]
> **Principle 2: Ref Callbacks: React Calls the Function with the Element and with `null`**
>
> *A function on `ref` is a ref callback; React calls it with the element when the element appears, and with `null` when it leaves, and a new function on every render means both calls on every render.*
>
> The upgrade guide replaces a string ref with a ref callback that saves the element on the instance. For the user, nothing changes. But a callback written inside render is a new function after every keystroke, so React calls the old one with null and the new one with the element. Keep the callback as a class field, and check the element before you use it.
>
> **DO THIS:**
> ```jsx
> setInput = (el) => {
>   this.input = el;
>   if (~el~) el.focus(); // Skips the call with null
> };
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input ref={el => { this.input = el; ~el.focus()~; }} /> // **WRONG:** throws a TypeError when React calls it with null
> ```

React's upgrade guide replaces a string ref with a function on the same `ref`:

```jsx title="A string ref and a ref callback on the same input"
<input ~ref="input"~ /> {/* Before: the handler reads this.refs.input */}
<input ~ref={el => { this.input = el; }}~ /> {/* After: the handler reads this.input */}
```

For the user, both do the same thing: the cursor comes back after Send. For React, they are different. With the string, React keeps the element itself, under a name. With the function, React does not keep anything. It calls your function and hands it the element, and your function decides where to keep it.

A function on `ref` is a **ref callback** (Lessons 31 and 86). React calls it at two moments:
- **When the `<input>` appears on the page**, React calls it with the `<input>` element. The docs call this attaching the ref.
- **When the `<input>` leaves the page**, React calls it with `null`. The docs call this detaching the ref.

What is new in a class is where the element goes. The arrow is written inside `render`, so `this` is the instance (Lesson 96). The line `this.input = el` adds a field named input to the instance. Then `handleSend` reads that same field.

### The chat field with a ref callback

We replace the string ref in `MessageForm.jsx`. We also add one `console.log`, to see every time React calls the callback:

```jsx title="src/MessageForm.jsx"
import { Component } from 'react';

export default class MessageForm extends Component {
  state = { text: '' };

  handleChange = (e) => {
    this.setState({ text: e.target.value });
  };

  handleSend = () => {
    this.setState({ text: '' });
    ~this.input~.focus(); // Reads the element your callback saved
  };

  render() {
    return (
      <div>
        <input
          ref={~el => {~ // React calls this function with the element, or with null
            console.log(el);
            this.input = el;
          }}
          value={this.state.text}
          onChange={this.handleChange}
          placeholder="Write a message..."
        />
        <button onClick={this.handleSend}>Send</button>
      </div>
    );
  }
}
```

The page works as before: after Send, the field is empty and the cursor is in it.

### The callback runs again after every keystroke

**Beware! The callback does not run once. It runs twice after every keystroke, though the field never leaves the page.**

When the page opens in development, the Console already shows three lines. React attaches the ref and logs the element. Then `<StrictMode>` detaches it and attaches it once more, to check that your callback handles both calls (Lesson 47):

```page caption="When the page opens in development, the Console shows the input element, then null, then the input element again."
card: input=Write a message...
line: [Send]
log: <input placeholder="Write a message..." value=""> | MessageForm.jsx:20
log: null | MessageForm.jsx:20
log: <input placeholder="Write a message..." value=""> | MessageForm.jsx:20
```

Now clear the Console and type H. Two new lines appear:

```page caption="After the user types H, the Console shows null and then the input element."
card: typed=H
line: [Send]
log: null | MessageForm.jsx:20
log: <input placeholder="Write a message..." value="H"> | MessageForm.jsx:20
```

Here is what happens after the keystroke:
1. The user types the letter H, and `onChange` calls `this.setState`. The class renders again.
2. `render` runs again and creates a new arrow function on `ref`.
3. React sees a different function on `ref`. It detaches the ref by calling the old function with `null`.
4. React attaches the ref by calling the new function with the `<input>` element.
5. `this.input` ends up holding the element again, so Send still puts the cursor back.

React's docs say it plainly: unless you pass the same function on every render, the callback "will get temporarily cleanup and re-create during every re-render of the component."

### VS | A callback written in `render` vs. a callback kept as a class field: one is new on every render

To stop the extra calls, the class keeps one function for its whole life. A class field arrow is created once, when React creates the instance:

```jsx title="A ref callback created once, as a class field"
class MessageForm extends Component {
  ~setInput~ = (el) => { // Created once, when React creates the instance
    this.input = el;
  };

  render() {
    return <input ref={~this.setInput~} />; // The same function on every render
  }
}
```

Both ways leave the element in `this.input`, so Send works with either. The difference shows in the Console. With the arrow written inside `render`, React calls the callback twice after every keystroke. With `setInput`, React sees the same function on every render, so it calls the callback only when the `<input>` appears and when it leaves.

```tree caption="A ref callback written inside render vs. a ref callback kept as a class field."
Where the ref callback is created
- +Written inside `render` [`ref={el => ...}`] | A **new function** on every render | React calls it with **`null`, then with the element**, after every keystroke
- +Kept as a class field [`ref={this.setInput}`] | The **same function** on every render | React calls it **only on attach and detach**
```

### A callback that calls focus on `null`

Here is a real mistake. A developer wants the cursor in the field as soon as the chat opens, so they call `focus()` inside the callback itself:

```jsx title="src/MessageForm.jsx" startLine="18"
        <input
          ref={el => {
            this.input = el;
            ~el.focus()~; // **WRONG:** React also calls this with null, and null has no focus method
          }}
```

React calls every ref callback with `null` when it detaches the ref. Calling `focus()` on `null` throws a TypeError. Nothing in our app catches it, so React removes the page. When it happens depends on the build:
- **In development**, `<StrictMode>` detaches the ref right after the page opens, so the page goes blank at once.
- **In production**, the cursor lands in the field, and the code looks finished. Then the user types the first letter, the arrow is new, and React calls the old one with `null`. The page goes blank while the user types.

In development, the Console shows the error twice. The first comes from the detach by `<StrictMode>`. The second comes when React removes the page and calls the callback with `null` once more:

```page caption="With focus called on the element without a check, in development: the page is blank as soon as it opens."
blank
console: Uncaught TypeError: Cannot read properties of null (reading 'focus')
  warn: An error occurred in the <input> component.
  error: Uncaught TypeError: Cannot read properties of null (reading 'focus')
  warn: An error occurred in the <input> component.
```

The fix is to check the element before you use it. React calls the callback with `null` on every detach, so the check belongs in every ref callback that uses its element:

```jsx title="src/MessageForm.jsx" startLine="18"
        <input
          ref={el => {
            this.input = el;
            if (~el~) el.focus(); // Skips the call with null
          }}
```

Four more facts about ref callbacks come up in interviews:
1. **In React 19, a ref callback may return a cleanup function.** React then calls the cleanup when it detaches the ref, instead of calling the callback with `null` (Lesson 86).
2. **The upgrade guide's short form returns the element.** It writes `ref={input => this.input = input}`, an arrow with an implicit return. React 19's TypeScript types reject it, and the fix is a body with curly braces, as our code uses (Lesson 86).
3. **Strict Mode adds one extra detach and attach in development.** It happens once, when the page opens (Lesson 47).
4. **A ref callback keeps one element per row of a list.** `useRef` cannot run inside `map`, so a list that needs the element of every row uses a ref callback instead.

## PRINCIPLE | `createRef` in a class: one ref object for each instance

> [!PRINCIPLE]
> **Principle 3: `createRef`: One Ref Object for Each Class Instance**
>
> *In a class, `inputRef = createRef()` as a class field makes one `{ current: null }` object per instance; `ref={this.inputRef}` tells React to put the element into `this.inputRef.current`.*
>
> createRef gives a class the same kind of object that useRef gives a function component. The class field runs once, when React creates the instance, so the same object lives as long as the component. The element sits in current, never on the object itself. In a function component, the same job is useRef with null.
>
> **DO THIS:**
> ```jsx
> handleSend = () => {
>   ~this.inputRef.current~.focus(); // React put the input element into current
> };
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> handleSend = () => {
>   ~this.inputRef.focus()~; // **WRONG:** the element sits in this.inputRef.current, so this throws a TypeError
> };
> ```

The other replacement for a string ref is `createRef`. It is a function that React provides, and you import it from `react`, like `Component`. It takes no arguments and returns a new object with one field, `current`, set to `null`:

```jsx title="What createRef returns"
const inputRef = ~createRef()~; // { current: null }
```

That is all it does. React's docs say the result is the same as writing `{ current: null }` yourself. It is the exact shape of the object `useRef` returns (Lesson 30). You put it on the tag, and React fills `current` with the element, as it fills a `useRef` object (Lesson 31).

What is new is when the object is made. Here it is a class field:

```jsx title="createRef in a class"
class MessageForm extends Component {
  ~inputRef = createRef();~ // Runs once, when React creates the instance

  handleSend = () => {
    this.inputRef.current.focus(); // React put the input element into current
  };

  render() {
    return <input ~ref={this.inputRef}~ />; // React fills this.inputRef.current with the element
  }
}
```

A class field runs once, when React creates the instance. So the same object stays on the instance for as long as the field is on the page.

### The chat field with `createRef`

We replace the ref callback in `MessageForm.jsx` with `createRef`:

```jsx title="src/MessageForm.jsx"
import { Component, ~createRef~ } from 'react'; // createRef comes from react, like Component

export default class MessageForm extends Component {
  state = { text: '' };
  ~inputRef = createRef();~ // One object for this instance

  handleChange = (e) => {
    this.setState({ text: e.target.value });
  };

  handleSend = () => {
    this.setState({ text: '' });
    ~this.inputRef.current~.focus(); // The element React put into current
  };

  render() {
    return (
      <div>
        <input
          ref={this.inputRef}
          value={this.state.text}
          onChange={this.handleChange}
          placeholder="Write a message..."
        />
        <button onClick={this.handleSend}>Send</button>
      </div>
    );
  }
}
```

The page works exactly as before. After Send, the field is empty, and the cursor is in it.

### VS | A ref callback vs. `createRef` in the same class: React calls the first and fills the second

Both replacements reach the same `<input>`, and for the user, the cursor comes back either way. The one difference is what React does with the ref. It calls a ref callback. It fills a `createRef` object.

```tree caption="A ref callback and a createRef object in the same class: React calls the first and fills the second."
Two ways a class gets the `<input>` element
- +A ref callback [`ref={this.setInput}`] | React **calls your function** with the element | Your function keeps it in **`this.input`**
- +A `createRef` object [`ref={this.inputRef}`] | React **fills `current`** with the element | The handler reads **`this.inputRef.current`**
```

You also meet `createRef` in a second spot. Older classes call it inside the constructor, and React's own page on `Component` does the same:

```jsx title="createRef as a class field and inside the constructor"
class MessageForm extends Component {
  ~inputRef = createRef();~ // As a class field
}

class MessageForm extends Component {
  constructor(props) {
    super(props);
    ~this.inputRef = React.createRef();~ // Inside the constructor, through the React object
  }
}
```

These two are the exact same thing. Both lines run once, when React creates the instance, and both store one object on it.

### VS | `createRef` in a class vs. `useRef` in a function: the instance keeps one object, React keeps the other

When a class becomes a function component, the class field becomes `useRef`. Every `this.inputRef.current` becomes `inputRef.current`:

```jsx title="The same ref in a class and in a function component"
~inputRef = createRef();~ // In the class: one object, kept by the instance
const inputRef = ~useRef(null)~; // In the function: one object, kept by React
```

For this page, they do the same job. Both give one `{ current }` object for the whole life of the component, and React fills `current` with the element. The one difference is who keeps the object between renders. The instance keeps the `createRef` object. React keeps the `useRef` object. React's docs give the migration step: replace calls to `createRef` with calls to `useRef`.

The docs also say where `createRef` belongs: "`createRef` is mostly used for class components. Function components typically rely on `useRef` instead." React lists `createRef` among the Legacy React APIs. React still exports it, but it is not recommended for new code. The docs add: "We recommend using function components instead of class components in new code."

## PRINCIPLE | `createRef` in a function: a new object on every render, so use `useRef`

> [!PRINCIPLE]
> **Principle 4: Migration: `createRef` in a Function Body Loses Its Value on Every Render**
>
> *Inside a function component, `createRef()` returns a new `{ current: null }` on every render; replace it with `useRef(null)`, which returns the same object on every render.*
>
> A line-by-line migration keeps createRef in the body, and focus still works, because React fills a ref on a tag again on every commit. But any value your code writes into current, such as a timer ID, is gone after the next render. useRef keeps one object for the component, as the class field did for the instance.
>
> **DO THIS:**
> ```jsx
> function MessageForm() {
>   const timerRef = ~useRef(null)~; // The same object on every render: Send stops the timer
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function MessageForm() {
>   const timerRef = ~createRef()~; // **WRONG:** a new object on every render: the timer ID is lost
> }
> ```

When a developer turns a class into a function by hand, the `createRef` line often comes along. Here are the two lines a function component might hold:

```jsx title="createRef and useRef inside a function component"
const inputRef = ~createRef()~; // A brand-new { current: null } on every render
const inputRef = ~useRef(null)~; // The same object on every render
```

They look the same, and at first they even work the same. They are not the same. React's docs say that `createRef` "always returns a *different* object", while `useRef` "always returns the same object".

The reason is the function body. A function component runs again on every render, so every line of its body runs again too (Lesson 12). In a class, the `createRef` field ran once per instance. In a function body, `createRef()` runs on every render and builds a fresh object each time, and nothing keeps the old one. `useRef` is different, because React keeps its object for the component.

### The chat field as a function with `createRef`

Here is our chat field after a line-by-line migration. The developer copied the class field into the body as `const inputRef = createRef()`:

```jsx title="src/MessageForm.jsx"
import { createRef, useState } from 'react';

export default function MessageForm() {
  const [text, setText] = useState('');
  const inputRef = ~createRef()~; // **WRONG:** a new object on every render

  function handleSend() {
    setText('');
    inputRef.current.focus();
  }

  return (
    <div>
      <input
        ref={inputRef}
        value={text}
        onChange={e => setText(e.target.value)}
        placeholder="Write a message..."
      />
      <button onClick={handleSend}>Send</button>
    </div>
  );
}
```

The user types Hi and clicks Send. The field empties, and the cursor comes back. The migration looks finished. Here is why it still works:
1. The user types the letter H, and `setText` renders `MessageForm` again.
2. The body runs again, and `createRef()` returns a new object. Its `current` field is `null`.
3. During the commit, React puts the `<input>` element into that new object (Lesson 13).
4. The user clicks Send. The handler from the latest render reads the latest object, which holds the element.

Nothing on the page shows that each keystroke made a new object. React fills a ref on a tag again on every commit, so the bug hides. It shows up as soon as your own code writes a value into `current`.

### A draft timer that never stops

Many chat apps save a draft of the message every few seconds while the user types. Our field grows by one step. It starts a timer on the first keystroke and stops it when the user clicks Send. To keep the page small, the timer only writes Draft saved to the Console. The timer ID lives in a second ref, as the interval ID did in Lesson 30:

```jsx title="src/MessageForm.jsx"
import { createRef, useState } from 'react';

export default function MessageForm() {
  const [text, setText] = useState('');
  const inputRef = createRef();
  const timerRef = ~createRef()~; // **WRONG:** a new object with current set to null on every render

  function handleChange(e) {
    setText(e.target.value);
    if (timerRef.current === null) {
      timerRef.current = setInterval(() => console.log('Draft saved'), 5000);
    }
  }

  function handleSend() {
    ~clearInterval(timerRef.current)~; // **WRONG:** receives null, so no timer stops
    timerRef.current = null;
    setText('');
    inputRef.current.focus();
  }

  return (
    <div>
      <input
        ref={inputRef}
        value={text}
        onChange={handleChange}
        placeholder="Write a message..."
      />
      <button onClick={handleSend}>Send</button>
    </div>
  );
}
```

**Beware! With `createRef`, every keystroke starts a new timer, and Send stops none of them.** Here is what happens when the user types Hi and clicks Send right away:
1. The user types the letter H. The handler sees `null` in `timerRef.current`, starts the first timer, and saves its ID in the object of this render.
2. `setText` renders `MessageForm` again. `createRef()` returns a new object, and its `current` field is null again. The ID of the first timer stays behind in the old object.
3. The user types the letter i. The handler from the new render sees `null` again, so it starts a second timer.
4. The user clicks Send. The handler reads a third object, made by the latest render, and passes `null` to `clearInterval`.
5. Both timers keep running.

A few seconds after Send, the field is empty, and the Console shows Draft saved twice. Every five seconds after that, two more lines appear:

```page caption="A few seconds after the user types Hi and clicks Send, with createRef: two timers still print Draft saved."
card: typed= | good=typed
line: [Send]
log: Draft saved | MessageForm.jsx:11
log: Draft saved | MessageForm.jsx:11
```

The page now does work that nobody asked for. The message is sent, the field is empty, and the app keeps saving a draft that no longer exists.

### The fix: `useRef` keeps one object

We replace both `createRef()` calls with `useRef(null)`:

```jsx title="src/MessageForm.jsx" startLine="1"
import { ~useRef~, useState } from 'react'; // useRef replaces createRef

export default function MessageForm() {
  const [text, setText] = useState('');
  const inputRef = ~useRef(null)~; // The same object on every render
  const timerRef = ~useRef(null)~; // Keeps the timer ID between renders
```

Now the user types Hi and clicks Send right away:
1. The first keystroke starts one timer and saves its ID in `timerRef.current`.
2. The second keystroke finds that ID, so it starts no new timer.
3. Send passes the ID to `clearInterval`, and the timer stops.

```page caption="A few seconds after the user types Hi and clicks Send, with useRef: the timer has stopped, and the Console stays quiet."
card: typed= | good=typed
line: [Send]
console: quiet
```

```tree caption="createRef in a function body vs. useRef: a new object on every render vs. one object kept by React."
`createRef` vs. `useRef` inside a function component
- !`createRef` in the body [`const timerRef = createRef`] | A **new `{ current: null }`** on every render | The timer ID is **lost** on the next render, so `Send` **stops no timer**
- +`useRef` [`const timerRef = useRef`] | **React keeps one object** for the component | The timer ID **survives** every render, so `Send` **stops the timer**
```

The translation rule is short. React's docs say that refs "might remind you of instance fields". So `this.something` in a class becomes `somethingRef.current` in a function. A `createRef` class field becomes `useRef(null)`. It never becomes a call to createRef in the body.

## PRINCIPLE | `ref` on a class component: `current` holds the instance, not an element

> [!PRINCIPLE]
> **Principle 5: Refs to Classes: `current` Holds the Component Instance**
>
> *When `ref` sits on a class component, React puts the component instance into `ref.current`, so the parent can call the child's own methods; a function component does the same job with `ref` on its tag or with `useImperativeHandle`.*
>
> A ref on a built-in tag holds an element, but a ref on a class holds the whole instance. The parent's call to focus then runs your method, not the browser's. When the class becomes a plain function that ignores ref, current stays null, and the same call throws a TypeError.
>
> **DO THIS:**
> ```jsx
> function MessageInput({ ref, ...props }) {
>   return <input ~ref={ref}~ {...props} />; // The parent's ref reaches the input element
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function MessageInput(~{ value, onChange }~) { // **WRONG:** drops ref, so the parent's current stays null
>   return <input value={value} onChange={onChange} />;
> }
> ```

So far, the ref sat on an `<input>` tag. Old code also puts a ref on its own class component. Suppose the field lives in its own class, `MessageInput`, with its own `focus` method. Compare the two tags:

```jsx title="A ref on the input tag and a ref on the MessageInput class"
<input ~ref={this.inputRef}~ /> {/* current holds the input element */}
<MessageInput ~ref={this.inputRef}~ /> {/* current holds the MessageInput instance */}
```

In both cases, the handler calls `this.inputRef.current.focus()`, and the cursor comes back. They look the same and work the same, but they are not the same thing:
- **With the ref on the `<input>` tag**, the ref's current field holds the `<input>` element. Its `focus` is the browser's method.
- **With the ref on the `MessageInput` tag**, the ref's current field holds the instance of that class. Its `focus` is a method your class wrote.

The **component instance** is the object React creates from a class (Lesson 96). What is new here is that a ref can hold it. A parent that holds the instance can call any method the child class defines, even a method that no browser element has.

### The `<input>` moves into its own file

The same field sits in every chat of the app, so we move it into its own file. `MessageInput` keeps its own `<input>` element with a ref callback. It also offers a `focus` method to its parent:

```jsx title="src/MessageInput.jsx"
import { Component } from 'react';

export default class MessageInput extends Component {
  ~focus~() { // Your own method: the parent calls it through the ref
    this.input.focus();
  }

  render() {
    return (
      <input
        ref={el => { this.input = el; }}
        value={this.props.value}
        onChange={this.props.onChange}
        placeholder="Write a message..."
      />
    );
  }
}
```

`MessageForm` stays a class. It imports `MessageInput` and puts its `createRef` object on that tag. The handler does not change:

```jsx title="src/MessageForm.jsx"
import { Component, createRef } from 'react';
import MessageInput from './MessageInput.jsx';

export default class MessageForm extends Component {
  state = { text: '' };
  inputRef = createRef();

  handleChange = (e) => {
    this.setState({ text: e.target.value });
  };

  handleSend = () => {
    this.setState({ text: '' });
    this.inputRef.current.~focus()~; // Runs the focus method of MessageInput
  };

  render() {
    return (
      <div>
        <MessageInput
          ~ref={this.inputRef}~ // React puts the MessageInput instance into current
          value={this.state.text}
          onChange={this.handleChange}
        />
        <button onClick={this.handleSend}>Send</button>
      </div>
    );
  }
}
```

React fills `this.inputRef.current` in three steps:
1. React creates the `MessageInput` instance, as it does for every class component.
2. It sees `ref` on the `MessageInput` tag. The tag is a class component, so React puts the instance into `this.inputRef.current`, not an element.
3. When the user clicks Send, the handler runs the `focus` method of `MessageInput`. That method calls the browser's `focus()` on the real `<input>`.

The page looks exactly as before. The Elements panel shows only the `<input>` element, because a class instance is a JavaScript object, not part of the page.

### What a ref holds depends on the tag

The same `ref={this.inputRef}` holds three different things, depending on where it sits:

```tree caption="What ref.current holds on a built-in tag, on a class component, and on a function component that ignores ref."
What `this.inputRef.current` holds
- +On a built-in tag [`<input ref={this.inputRef} />`] | React puts the **element** into `current` | `focus` is the **browser's method**
- +On a class component [`<MessageInput ref={this.inputRef} />`] | React puts the **component instance** into `current` | `focus` is **your method**
- !On a function component that ignores `ref` [`<MessageInput ref={this.inputRef} />`] | React has **nothing to put** into `current` | `current` stays **`null`**
```

### The class becomes a function, and the call fails

Here is a real mistake during a migration. A developer turns the class `MessageInput` into a plain function component:

```jsx title="src/MessageInput.jsx"
export default function ~MessageInput~({ value, onChange }) { // **WRONG:** ignores ref and has no focus method
  return <input value={value} onChange={onChange} placeholder="Write a message..." />;
}
```

The parent still puts its ref on `MessageInput`, and it still calls `focus()` through that ref. The field shows the text as before, so the page looks fine. Then the user clicks Send:
1. The function never passes `ref` on to the `<input>`. So React has no element to put into current.
2. `this.inputRef.current` stays `null`.
3. The handler calls `focus()` on `null`, and JavaScript throws a TypeError.

The field empties, because `setState` ran before the error. But the cursor does not come back:

```page caption="After the class MessageInput becomes a function that ignores ref, the user types Hi and clicks Send."
card: input=Write a message... | bad=input
line: [Send]
console: Uncaught TypeError: Cannot read properties of null (reading 'focus')
```

There are two fixes, both from earlier lessons:
- **Pass `ref` on to the `<input>`.** In React 19, the function reads `ref` as a prop and puts it on its tag (Lesson 85). Then current holds the `<input>` element, and the browser's `focus` runs.
- **Keep a `focus` method with `useImperativeHandle`.** The function chooses the object the parent sees (Lesson 50). The class exposed its whole instance. `useImperativeHandle` exposes only the methods it returns.

Two more facts come up in interviews:
1. **In React 19, a ref on a class is still not a prop.** React's announcement says: "`ref`s passed to classes are not passed as props since they reference the component instance." So a class cannot read `this.props.ref`.
2. **The docs warn against exposing more than the parent needs.** Reaching into another component "can make your code fragile", and the docs advise: "If you can express something as a prop, you should not use a ref."

## PRINCIPLE | `forwardRef`: every component on the way must pass the ref on

> [!PRINCIPLE]
> **Principle 6: `forwardRef`: Every Function on the Way Must Pass the Ref On**
>
> *Before React 19, a function component received no `ref`, so every function between the parent and the `<input>`, including the one a higher-order component returns, had to use `forwardRef` and pass the ref on with `ref={ref}`; in React 19, `ref` is a prop, and `forwardRef` is no longer necessary.*
>
> A higher-order component puts a new component between the parent and the input. The parent's ref reaches the input only when every component on the way receives it and passes it on. One dropped ref leaves current as null, and the next call to focus throws. In React 19, spreading the props carries ref like any other prop.
>
> **DO THIS:**
> ```jsx
> return forwardRef(function Tracked(props, ref) {
>   return <WrappedComponent {...props} ~ref={ref}~ />; // Passes the parent's ref on to MessageInput
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> return forwardRef(function Tracked(props, ref) {
>   return ~<WrappedComponent {...props} />~; // **WRONG:** receives the ref and drops it, so current stays null
> });
> ```

> [!DEFINITION]
> **What is a higher-order component?** [NEW] A higher-order component is a plain function that takes a component and returns a new component that renders it.
> The name comes from JavaScript, where a higher-order function takes or returns another function, like `map` takes a function.
> Old code used it to add one behavior, such as tracking, to many components without editing each one: `const TrackedMessageInput = withTracking(MessageInput)`.
> By convention its name starts with `with` (Lesson 99).

Here is the shape, written once for React 18 and once for React 19. `withTracking` takes a component, `WrappedComponent`. It returns a new component, `Tracked`, that renders it. To keep the lesson on the ref, we leave out the tracking code itself:

```jsx title="A higher-order component with forwardRef, for React 18"
function withTracking(WrappedComponent) {
  return ~forwardRef~(function Tracked(props, ref) { // Receives the ref as a second argument
    return <WrappedComponent {...props} ref={ref} />;
  });
}
```

```jsx title="The same higher-order component without forwardRef, for React 19"
function withTracking(WrappedComponent) {
  return function Tracked(~props~) { // The ref arrives inside props
    return <WrappedComponent {...props} />;
  };
}
```

In React 19, these two do the same job. `ref` is now a prop, so the spread of props carries it to `WrappedComponent` (Lesson 85). In React 18, they are not the same. A plain function component received no ref at all. So without `forwardRef`, the ref stopped at `Tracked`.

### The chat field behind `withTracking`

Later, the team rewrote `MessageInput` as a function component. In React 18, a function component received no `ref`, so they wrapped it in `forwardRef` (Lesson 85):

```jsx title="src/MessageInput.jsx"
import { forwardRef } from 'react';

export default ~forwardRef~(function MessageInput(props, ref) { // React passes the ref as the second argument
  return <input {...props} ~ref={ref}~ placeholder="Write a message..." />; // The ref reaches the input element
});
```

The app tracks every message field, so `withTracking` wraps it, in its own file:

```jsx title="src/withTracking.jsx"
import { forwardRef } from 'react';

export default function withTracking(WrappedComponent) {
  return ~forwardRef~(function Tracked(props, ref) { // Receives the parent's ref
    return <WrappedComponent {...props} ~ref={ref}~ />; // Passes the ref on to MessageInput
  });
}
```

`MessageForm`, still a class, wraps the field once, when the file loads, and puts its ref on the result:

```jsx title="src/MessageForm.jsx"
import { Component, createRef } from 'react';
import MessageInput from './MessageInput.jsx';
import withTracking from './withTracking.jsx';

const ~TrackedMessageInput~ = withTracking(MessageInput); // Tracked, which renders MessageInput

export default class MessageForm extends Component {
  state = { text: '' };
  inputRef = createRef();

  handleChange = (e) => {
    this.setState({ text: e.target.value });
  };

  handleSend = () => {
    this.setState({ text: '' });
    this.inputRef.current.focus();
  };

  render() {
    return (
      <div>
        <TrackedMessageInput
          ~ref={this.inputRef}~ // The ref must travel through Tracked and MessageInput
          value={this.state.text}
          onChange={this.handleChange}
        />
        <button onClick={this.handleSend}>Send</button>
      </div>
    );
  }
}
```

`WrappedComponent` is our own `MessageInput`. The call `withTracking(MessageInput)` runs once, when the file loads. `MessageInput` arrives as the argument `WrappedComponent`. The returned `Tracked` keeps it through a closure (Lesson 15) and renders it on every render.

### How the ref travels to the `<input>`

**Beware! The parent never sees the `<input>`. The ref reaches it only because every component on the way passes it on.** Here is the path, in order:
1. `MessageForm` puts its ref on `TrackedMessageInput`.
2. `TrackedMessageInput` is the component `Tracked`, wrapped in forwardRef. React calls `Tracked` with `props`, and with the ref as the second argument.
3. `Tracked` renders `MessageInput` and passes the ref on to it. `MessageInput` is also wrapped in `forwardRef`.
4. React calls `MessageInput` with `props` and the same ref.
5. `MessageInput` puts the ref on its `<input>` tag.
6. During the commit, React puts the `<input>` element into `this.inputRef.current`, two components below the parent.

The handler still calls `this.inputRef.current.focus()`. It is the same line as in Principle 5, but not the same target. Here current holds the `<input>` element, and `focus` is the browser's method.

```tree dir=right caption="How the parent's ref travels through Tracked and MessageInput to the input element in React 18."
The path of `this.inputRef` before React 19
- +1. `MessageForm` [`<TrackedMessageInput ref={this.inputRef} />`] | The parent puts the ref **on the wrapper**
- +2. `Tracked` [`forwardRef`] | Receives the ref as a **second argument** | Passes it on with **`ref={ref}`**
- +3. `MessageInput` [`forwardRef`] | Receives the same ref | Puts it **on the `<input>`**
- +4. The `<input>` element | React puts it into **`this.inputRef.current`** during the commit
```

### One forgotten `ref={ref}` breaks the path

Months later, a developer edits `Tracked` and drops `ref={ref}`:

```jsx title="src/withTracking.jsx" startLine="4"
  return forwardRef(function Tracked(props, ref) {
    return ~<WrappedComponent {...props} />~; // **WRONG:** receives the ref and drops it
  });
```

The field still shows the text, so the page looks fine. But `Tracked` receives the ref and never passes it on. React has no element to put into current, so `this.inputRef.current` stays `null`. When the user clicks Send, the field empties, but the cursor does not come back. The Console shows the same TypeError as in Principle 5: it cannot read focus on null. React's docs name this exact cause: "you forgot to actually use the `ref` that you received".

```tree caption="A wrapper that passes the ref on vs. a wrapper that drops it."
What `Tracked` does with the ref it receives
- +Passes it on [`<WrappedComponent {...props} ref={ref} />`] | The ref reaches **`MessageInput` and the `<input>`** | `Send` puts **the cursor back**
- !Drops it [`<WrappedComponent {...props} />`] | The ref **stops at `Tracked`** | `current` stays **`null`**, and `Send` throws a **`TypeError`**
```

Here is a second version of this mistake. `MessageInput` uses forwardRef correctly, but `withTracking` returns a plain function:

```jsx title="src/withTracking.jsx"
export default function withTracking(WrappedComponent) {
  return function ~Tracked~(props) { // **WRONG in React 18:** a plain function receives no ref
    return <WrappedComponent {...props} />;
  };
}
```

In React 18, the parent's ref stops at `Tracked`. React's docs explain why: "Unlike React components defined as plain functions, a component returned by `forwardRef` is also able to receive a `ref` prop." So Send throws the same TypeError, though `MessageInput` forwards the ref correctly. In React 19, the same `Tracked` receives the ref inside `props`, and the spread carries it on. So this bug disappears after the upgrade.

### VS | `forwardRef` vs. `ref` as a prop: React 18 needs the wrapper, React 19 does not

In React 19, `ref` is an ordinary prop for function components (Lesson 85). Our two files can drop `forwardRef`:

```jsx title="MessageInput with forwardRef and with ref as a prop"
const MessageInput = ~forwardRef~(function MessageInput(props, ref) { /* ... */ }); // React 18 and earlier
function MessageInput(~{ ref, ...props }~) { /* ... */ } // React 19: ref is a prop
```

In React 19, both receive the parent's ref and put it on the `<input>`. React's docs say it plainly: "In React 19, `forwardRef` is no longer necessary. Pass `ref` as a prop instead." And they add: "`forwardRef` will be deprecated in a future release."

Four more facts about React 19 come up in interviews:
1. **`ref` as a prop needs the new JSX transform.** React 19 requires it, so old projects that still use the old transform must switch.
2. **`ReactDOM.findDOMNode` is removed.** It was another old way to reach an element. React's upgrade guide says it "was slow to execute, fragile to refactoring, only returned the first child, and broke abstraction levels". The replacement is a ref on the tag.
3. **Strict Mode calls a `forwardRef` render function twice in development**, as it does for every component (Lesson 47).
4. **The docs expose an element only from small reusable components**, such as buttons or text inputs. Larger components, such as an avatar or a comment, keep their elements to themselves.

One more change reaches old code that reads `ref` from a JSX element: `element.ref` is deprecated. The code still gets the ref, but React prints this error in the Console:

```devconsole width=full
x Accessing element.ref was removed in React 19. ref is now a regular prop. It will be removed from the JSX Element type in a future release.
```

## All 6 Principles Together

### The chat field in React 19

Here is the chat field after the whole migration to React 19. `MessageForm` is a function with `useRef`. `withTracking` returns a plain function. `MessageInput` reads `ref` as a prop:

```jsx title="src/MessageForm.jsx"
import { useRef, useState } from 'react';
import MessageInput from './MessageInput.jsx';
import withTracking from './withTracking.jsx';

const TrackedMessageInput = withTracking(MessageInput);

  const [text, setText] = useState('');

  const timerRef = ~useRef(null)~; // Principle 4: the timer ID survives every render

  function handleChange(e) {
    setText(e.target.value);
    if (timerRef.current === null) {
      timerRef.current = setInterval(() => console.log('Draft saved'), 5000);
    }
  }

  function handleSend() {
    clearInterval(timerRef.current);
    timerRef.current = null;
    setText('');
    ~inputRef.current.focus()~; // Principle 6: current holds the input element, two components below
  }

  return (
    <div>
      <TrackedMessageInput ~ref={inputRef}~ value={text} onChange={handleChange} /> {/* Principle 6: ref is a prop */}

```

```jsx title="src/withTracking.jsx"

  };
}
```

```jsx title="src/MessageInput.jsx"
export default function MessageInput(~{ ref, ...props }~) { // Principle 6: no forwardRef in React 19
  return <input {...props} ref={ref} placeholder="Write a message..." />;
}
```

### How React passes the ref down and fills it

When the page opens, React calls the components from the parent down to the `<input>`, then fills the ref during the commit:

```tree dir=right caption="The order in which React calls the components of the chat field and fills inputRef."
How `inputRef` reaches the `<input>` in React 19
- +1. `MessageForm` | Creates **`inputRef`** with `useRef` | Renders `<TrackedMessageInput ref={inputRef} />`
- +2. `Tracked` | Receives `ref` **inside `props`** | Renders `<MessageInput {...props} />`
- +3. `MessageInput` | Reads **`ref`** as a prop | Renders `<input ref={ref} />`
- +4. The commit | React puts the `<input>` element into **`inputRef.current`** | `handleSend` can **put the cursor back**
```

| Principle | Old code | React 19 | What breaks |
| :--- | :--- | :--- | :--- |
| **1. String ref** | `ref="input"` and `this.refs.input` | Removed: use a ref callback or `createRef` | The page goes blank after the upgrade |
| **2. Ref callback** | `ref={el => { this.input = el; }}` | Still valid; may return a cleanup function | A callback written in `render` runs twice after every keystroke; using its element without a check fails on `null` |
| **3. `createRef` in a class** | `inputRef = createRef()` as a class field | Still exported, a Legacy React API; use `useRef` in a function | Nothing, as long as it stays a class field |
| **4. `createRef` in a function** | Copied into the body during a migration | Replace it with `useRef(null)` | A timer ID in `current` is lost, and the timer never stops |
| **5. Ref on a class** | `current` holds the component instance | Still the instance, and still not a prop | A class turned into a function that ignores `ref` leaves `current` as `null` |
| **6. `forwardRef`** | Every function on the way uses `forwardRef` and `ref={ref}` | `ref` is a prop; `forwardRef` is no longer necessary | One dropped `ref={ref}` leaves `current` as `null` |

Remember the one question of this lesson. **Every ref, old or new, tells React where to put the element: under a name, through your function, or in a `current` field. React 19 keeps the function and the object, removes the name, and lets `ref` travel as an ordinary prop.**

## For the Interview

> **The Interview Question:** How did refs work before hooks: createRef, callback refs, and forwardRef?

### How to Answer Clearly in 30 Seconds

"A ref tells React where to put a DOM element, so a handler can reach it, for example to put the cursor back in a message field. Before Hooks, class components had three ways to do that:
1. **String refs**: `ref="input"` and `this.refs.input`. They were deprecated in React 16.3 and are removed in React 19.
2. **Ref callbacks**: a function on `ref` that React calls with the element on attach and with `null` on detach. A new function on every render means both calls on every render.
3. **`createRef`**: a class field that makes one `{ current: null }` object per instance, which React fills.

To hand a ref to a function component, React 18 and earlier needed `forwardRef`. Every wrapper on the way, such as a higher-order component, had to pass the ref on. In React 19, `ref` is an ordinary prop, and `forwardRef` is no longer necessary. In a function component we use `useRef`, never `createRef`, because `createRef` makes a new object on every render."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Is `createRef` the same as `useRef`?"**
   The object is the same: one field, `current`, that React fills. The difference is who keeps the object. In a class, `createRef` runs once as a class field, so the instance keeps it. In a function component, `createRef` runs on every render and returns a new object, while `useRef` returns the same object every time. React's docs show the relation: `useRef` behaves like a `createRef` object kept in state, `const [ref, _] = useState(() => createRef(null))`. So when a class becomes a function, every `createRef()` becomes `useRef(null)`.
2. **"Why does my ref callback get called with `null` after every keystroke?"**
   Because the callback is an arrow function written inside `render`, or inside the body of a function component. Every keystroke changes state and renders the component again, which creates a new function. React sees a different function on `ref`, so it calls the old one with `null` and the new one with the element. Keep the same function between renders, as a class field or with `useCallback`, and always check the element for `null` before you use it. In React 19, the callback can also return a cleanup function, which React calls instead of passing `null`.
3. **"We are upgrading an old app to React 19. What do we do with its refs?"**
   First, run the codemod that turns string refs into ref callbacks, because React 19 removed string refs, and a page that still uses one goes blank. Second, `forwardRef` still works, but it is no longer necessary and will be deprecated. So new and touched components read `ref` as a prop, and a wrapper passes it on by spreading `props`. Third, code that reads `element.ref` makes React print an error in the Console, and `ReactDOM.findDOMNode` is gone, so that code moves to a ref on the tag. Refs on class components still hold the instance, and they are still not props. Finally, when a class becomes a function, replace each `createRef` field with `useRef(null)`.
