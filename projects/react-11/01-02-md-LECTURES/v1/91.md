# Lecture 91: How a Search Field Handler Gets the Type of Its Event

*(Why does TypeScript know what `e` is inside `onChange`, and forget it the moment you move the handler out?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How do you type event handlers and SyntheticEvents in TypeScript?

---

## VS | An Inline Handler vs. a Separate Handler: TypeScript knows the type of `e` inside the tag, and our code must write it everywhere else

> When the user types in an `<input>` field, React calls your handler and passes it an event object, `e`. **In TypeScript, `e` needs a type: inside `onChange={...}` TypeScript works it out for you, but in a separate function you write it yourself, such as `React.ChangeEvent<HTMLInputElement>`.** Write it right, because a handler with no type, or with `any`, lets a typo such as `vlaue` reach the user as an empty line on the page.

Remember plain JavaScript? You attach a listener, and the browser hands your function an event object:

```js title="Plain JavaScript: the browser passes the event object"
input.addEventListener('input', function (~e~) { // e is the event object, and JavaScript never asks what it is
  console.log(e.currentTarget.value);
});
```

JavaScript never asks what `e` is. You read `e.currentTarget.value`, and if you misspell it, you find out later, when the page runs.

TypeScript asks. In Lesson 90 we wrote `function greet(name: string)`: after a parameter, you write what it must be. An event handler is a function too, and `e` is its parameter. So `e` needs a type.

Here is the surprise. Write the handler inside the tag, and you do not have to write anything:

```tsx title="The same handler body, inline and moved out"
const [query, setQuery] = useState('');

<input value={query} onChange={~e~ => setQuery(e.currentTarget.value)} /> {/* 1. Inline: no error, TypeScript already knows what e is */}

function handleChange(~e~) { // 2. Moved out: **WRONG:** the editor underlines e, because e has no type
  setQuery(e.currentTarget.value);
}
```

The body is the same line. In the browser, both versions run the same way, because the types are deleted before the code runs (Lesson 90). The only difference is where the function is written:
- **The inline handler** sits inside `onChange={...}`. TypeScript knows the type of `onChange`, so it knows which event object will arrive. So `e` gets a type that nobody wrote.
- **`handleChange`** sits on its own lines. Nothing around it says what `e` will be, so the editor underlines `e` until our code writes its type.

> [!DEFINITION]
> **The React event object.** [REVIEW] When the user clicks or types, React calls your handler and passes it an event object, usually named `e`. You never pass it yourself. React does. `e.currentTarget` is the element whose handler runs, and `e.target` is the element where the event started. React does not pass the browser's own event: it passes its own object, which react.dev also calls a synthetic event (Lesson 11).

```tree caption="The same handler body in two places: the browser runs both the same way, but only the inline one has a type for e."
The same handler body in two places
- +Inline inside `onChange` [`onChange={e => setQuery}`] | TypeScript reads the type of `onChange` | `e` is a **`React.ChangeEvent`** on the input, and nobody wrote it
- !Moved out into `handleChange` [`function handleChange`] | Nothing around the function says what `e` is | The editor **underlines `e`** until our code writes its type
```

**Remember this one sentence: the type of `e` comes from the place where the handler is written.** Inline, React's types supply it. In a separate function, our code writes it: the event type first, then the element type in angle brackets, as in `React.ChangeEvent<HTMLInputElement>`.

### What goes wrong with `e: any`

The quickest way to make the underline go away is to write `e: any`.

> [!DEFINITION]
> **What is `any`?** [NEW] `any` is a TypeScript type that means "this value can be anything, so check nothing on it". `e: any` removes the underline on `e`, and it also removes every check on `e`. A misspelled property passes the editor without a word (Lesson 91).

Here is how a typo reaches the user:

```tsx title="handleChange silenced with e: any"
function handleChange(~e: any~) { // The underline on e is gone, and so is every check on e
  setQuery(e.currentTarget.~vlaue~); // **WRONG:** value is misspelled, so setQuery receives undefined
}
```

1. A developer writes `e: any` to make the underline go away.
2. Weeks later, someone edits the handler and misspells `value` as `vlaue`. Because `e` is `any`, the editor says nothing.
3. The user types `shoes` in the search field. On every letter, `setQuery` receives `undefined`. Why? An `<input>` element has no property called `vlaue`.

The line under the field should say `Results for: shoes`. It says only `Results for:`. And the field itself still shows `shoes`. Why? An `<input>` whose `value` is `undefined` is no longer controlled by state, so the browser keeps the letters on its own (Lesson 20). React also prints a warning in the Console:

```page width=full caption="The search field after the user types shoes, with vlaue misspelled behind e: any: the field keeps the letters, and the results line stays empty."
form:
  field: Search the store | shoes
line: Results for: | bad
console: A component is changing a controlled input to be uncontrolled. This is likely caused by the value changing from a defined to undefined, which should not happen. Decide between using a controlled or uncontrolled input element for the lifetime of the component. More info: https://react.dev/link/controlled-components
```

With the right type on `e`, the editor underlines `vlaue` the moment the developer types it: an `HTMLInputElement` has no property with that name. The mistake never leaves the editor.

### The Rule of Thumb: inline, write nothing; moved out, write the event and the element

**Inline, TypeScript gives `e` its type. In a separate function, write it yourself: the event type, then the element type in angle brackets. Never silence `e` with `any`.**

A senior developer also knows the three classic mistakes:
1. **`e: any`.** The underline goes away, and every check on `e` goes away with it, as the search field above shows.
2. **`e: Event`, the browser's own event type.** That is what an event is in plain JavaScript. But React passes its own event object, not the browser's, so the editor refuses the handler on `onChange`.
3. **`React.ChangeEvent` with no element in angle brackets.** TypeScript then assumes the most general element, `Element`, which has no `value`. So the editor underlines `value`.

## SECTION | A Search Field at the Top of an Online Store

Every online store has a search field at the top. The user types `shoes`, and a line under the field reads `Results for: shoes`:

```page width=text caption="The search field we build: the user types shoes, and the results line repeats it."
form:
  field: Search the store | shoes | good
line: Results for: shoes | good
console: quiet
```

Many stores also let the user press Escape to give up on a search. The field empties, the results line empties, and the cursor leaves the field.

That Escape key is why real handlers do not stay inline. Escape needs an `if` for the key and two actions, which is too much for one line inside a tag. So the developer moves the handler into its own function. And the moment a handler moves out of the tag, our code must say which event and which element it handles.

There are three ways to give `e` a type:
1. **Write the handler inline, and let TypeScript work out the type.** This fits a one-line handler.
2. **Write a separate function, and type its parameter:** `function handleChange(e: React.ChangeEvent<HTMLInputElement>)`. This is the example react.dev gives.
3. **Write a separate function, and type the whole function** with `React.ChangeEventHandler<HTMLInputElement>`. react.dev offers this one in its `useCallback` example, "depending on your code-style preferences".

```tree caption="Three ways to give e a type: let TypeScript work it out inline, type the parameter, or type the whole function."
Three ways to give `e` a type
- +1. Inline on the tag [`onChange={e => setQuery}`] | TypeScript **works out the type** from `onChange` | Fits a **one-line** handler
- +2. Type the parameter [`e: React.ChangeEvent<HTMLInputElement>`] | Our code writes the **type of the event object** | Fits a handler of **several lines**
- +3. Type the whole function [`React.ChangeEventHandler<HTMLInputElement>`] | Our code writes the **type of the function** | `e` is worked out from it, **as inline**
```

We build it in a small React project written in TypeScript, with the setup of Lesson 90:

```files title="store-search: File Explorer" caption="Our project files: App.tsx places the search field, and SearchBar.tsx holds the field, its state, and its handlers."
index.html | entry | The HTML page with the empty root div where React mounts
tsconfig.json | settings | Tells TypeScript how to read the project
src/
  main.tsx | boundary | Imports `App` from `./App` and mounts it into `#root`
  App.tsx | parent | Exports `App` as default and imports `SearchBar`
  components/
    SearchBar.tsx | state | Holds `query` in state, the search field, the results line, and the handlers
```

**PRINCIPLES:** React passes every handler its own event object. TypeScript learns its type either from the tag or from our code. Five principles follow as the search field grows:
1. **Principle 1: `onChange={e => ...}` gives the inline handler its type.** Our code writes nothing. Hover over `e` to see the type.
2. **Principle 2: `e: React.ChangeEvent<HTMLInputElement>` on a separate handler.** No tag around the function, so our code writes the event type and the element type.
3. **Principle 3: `React.ChangeEventHandler<HTMLInputElement>` types the whole function.** `e` gets the exact same type as with Principle 2.
4. **Principle 4: `React.KeyboardEvent<HTMLInputElement>` for a key press.** The event decides the type, and only a keyboard event has `e.key`.
5. **Principle 5: `e.currentTarget` is typed as the element with the handler.** `e.target` is typed loosely, because the event may have started on a child.

## PRINCIPLE | `onChange={e => ...}`: the inline handler gets the type of `e` without one written word

> [!PRINCIPLE]
> **Principle 1: Inline Handlers: `onChange` Hands the Inline Handler Its Type**
>
> *When a handler is written inline inside `onChange={...}`, TypeScript infers the type of `e` from `onChange`; write no type, and hover over `e` to see it.*
>
> React's types already describe `onChange` on an `<input>` as a function that receives a `React.ChangeEvent` for that input. TypeScript hands that type to the function written there, so the editor checks every property our code reads from `e`. Writing `e: any` inline throws that type away, and a typo such as `vlaue` reaches the user as an empty results line.
>
> **DO THIS:**
> ```tsx
> <input value={query} onChange={~e~ => setQuery(e.currentTarget.value)} /> {/* e is inferred as React.ChangeEvent<HTMLInputElement, HTMLInputElement> */}
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> <input value={query} onChange={(~e: any~) => setQuery(e.currentTarget.vlaue)} /> {/* **WRONG:** any removes the type, so the typo vlaue is never caught */}
> ```

Here is the inline handler alone. Hover over `e` in the editor, and it shows a type:

```tsx title="The handler written inline inside onChange"
<input value={query} onChange={~e~ => setQuery(e.currentTarget.value)} /> {/* Hover over e: the editor shows React.ChangeEvent<HTMLInputElement, HTMLInputElement> */}
```

Nobody wrote that type. TypeScript worked it out from `onChange`.

> [!DEFINITION]
> **What does inferring a type mean?** [NEW] Inferring a type means that TypeScript works out the type from the code around it, so you do not write it. You already know the simplest case: after `const name = 'John'`, TypeScript knows that `name` is a string. Inside `onChange={...}`, it works out `e` the same way, from the type of `onChange`. react.dev says it plainly: the type "can often be inferred from the event handler" (Lesson 91).

### The two names in the type

The type has two parts:
- **`React.ChangeEvent`** is the type of the event object for a change, such as a letter the user types. It comes from `@types/react`, the package that brings React's types into the project.
- **`HTMLInputElement`**, inside the angle brackets, is the browser's type for an `<input>` element. TypeScript reads the browser's types through `tsconfig.json`. It is a type argument (Lesson 90): it tells the event type which element the handler sits on.

The hover shows `HTMLInputElement` twice. The second one is the element where the change started. On an `<input>`, that is the same input, because nothing can sit inside an `<input>`. Today `@types/react` uses only the first one, so a type written by hand can leave the second one out: `React.ChangeEvent<HTMLInputElement>` checks `e` exactly the same way.

### The type comes from the editor, the value comes from the browser

The type and the value of `e` come from two different places, at two different moments.

The type comes before the code runs, in three steps:
1. `@types/react` describes every prop of `<input>`. It describes `onChange` as a function that receives a `React.ChangeEvent`.
2. TypeScript sees our arrow function sitting inside `onChange={...}`.
3. So TypeScript gives the first parameter of that function, `e`, the type of that change event.

The value comes while the page runs. Every time the user types a letter, React calls our handler and passes it the React event object (Lesson 11).

```tree dir=right caption="The type of e comes from the types of React before the code runs; the value of e comes from React when the user types."
Two sources for `e` in the inline handler
- +The type of `e`, in the editor [`onChange={e => setQuery}`] | `@types/react` describes `onChange` | TypeScript gives `e` the type **`React.ChangeEvent<HTMLInputElement, HTMLInputElement>`**
- +The value of `e`, in the browser | The user **types a letter** in the field | React calls the handler and passes the **React event object**
```

Because `e` has a real type, the editor checks every property our code reads from it. Misspell `value` inline, and the editor catches it at once:

```tsx title="A typo in the inline handler"
<input value={query} onChange={e => setQuery(e.currentTarget.~vlaue~)} /> {/* **WRONG:** the editor underlines vlaue: an HTMLInputElement has no property with that name */}
```

### Our search field with the inline handler

Here is our first `SearchBar`. It keeps the text of the field in `query`, and shows that text in the results line:

```tsx title="src/components/SearchBar.tsx"
import { useState } from 'react';

export default function SearchBar() {
  const [query, setQuery] = useState('');

  return (
    <div>
      <label>
        Search the store
        <input value={query} onChange={~e => setQuery(e.currentTarget.value)~} /> {/* Inline: e gets its type from onChange */}
      </label>
      <p>Results for: {query}</p>
    </div>
  );
}
```

`App` places the search field on the page:

```tsx title="src/App.tsx"
import SearchBar from './components/SearchBar';

export default function App() {
  return ~<SearchBar />~; // React calls SearchBar and puts the search field on the page
}
```

The user types `shoes`, and the field and the results line both show it:

```page width=full caption="The search field after the user types shoes: the field and the results line both show shoes."
form:
  field: Search the store | shoes | good
line: Results for: shoes | good
console: quiet
```

### The habit that throws the inferred type away

Developers who come from JavaScript often add `: any` to every handler out of habit, even inline. Inline, that habit costs the most. TypeScript already had the right type, and `any` replaces it with no checks at all:

```tsx title="e: any written on the inline handler"
<input value={query} onChange={(~e: any~) => setQuery(e.currentTarget.vlaue)} /> {/* **WRONG:** any replaces the inferred type, so the typo vlaue passes and the results line stays empty */}
```

Remember: inline, write nothing. TypeScript already knows `e`.

## PRINCIPLE | `e: React.ChangeEvent<HTMLInputElement>`: a separate handler is checked exactly like the inline one

> [!PRINCIPLE]
> **Principle 2: Separate Handlers: Write `React.ChangeEvent<HTMLInputElement>` on `e`**
>
> *When the handler is moved into its own function, write the type of its parameter: the event type, then the element type in angle brackets.*
>
> Inline, the type of `e` came from the tag. A function on its own lines has no tag around it, so in strict mode the editor underlines `e` until our code writes its type. `any` removes the underline and every check with it. The browser's `Event` names the wrong object, because React passes its own event object. `React.ChangeEvent<HTMLInputElement>` gives `e` the same checks as the inline handler.
>
> **DO THIS:**
> ```tsx
> function handleChange(~e: React.ChangeEvent<HTMLInputElement>~) { // The same checks as the inline handler
>   setQuery(e.currentTarget.value);
> }
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> function handleChange(~e: any~) { // **WRONG:** no check on e, so the typo vlaue empties the results line
>   setQuery(e.currentTarget.vlaue);
> }
> ```

Cut the arrow function out of the tag, paste it into `handleChange`, and the type stays behind. The type was never in the body. It came from the tag:

```tsx title="handleChange with no type on e"
function handleChange(~e~) { // **WRONG:** the editor underlines e: it has no type
  setQuery(e.currentTarget.value);
}

<input value={query} onChange={handleChange} />
```

react.dev says exactly this: "when you want to extract a function to be passed to an event handler, you will need to explicitly set the type of the event."

Why is a missing type an error at all? Because strict mode is on.

> [!DEFINITION]
> **What is strict mode in TypeScript?** [NEW] Strict mode is a TypeScript setting that makes the type-checker stricter. One of its rules: a parameter whose type TypeScript cannot work out is an error, so the editor underlines it. TypeScript 7, which Vite's React and TypeScript template installs, turns strict mode on by default. It has nothing to do with React's `<StrictMode>` wrapper (Lesson 91).

### Writing the type by hand

So our code writes the type after `e`. It is the type the inline handler received, now written by hand:

```tsx title="handleChange with e typed by hand"
function handleChange(~e: React.ChangeEvent<HTMLInputElement>~) { // The event type, then the element type in angle brackets
  setQuery(e.currentTarget.value);
}

<input value={query} ~onChange={handleChange}~ /> {/* TypeScript checks that handleChange fits what onChange expects */}
```

The type answers two questions:
1. **Which event?** `ChangeEvent`, because the handler runs when the text of the field changes.
2. **Which element?** `HTMLInputElement`, in the angle brackets, because the handler sits on an `<input>`.

Now compare the versions of `handleChange` so far:
- **No type on `e`, and `e: any`:** for the checks on `e`, **yes, it is the exact same thing!** Neither one checks `e`. `any` only removes the underline.
- **`e: React.ChangeEvent<HTMLInputElement>`, and the inline handler:** **yes, it is the exact same thing, too!** `e` gets the exact same checks. Inline, TypeScript infers the type. In `handleChange`, our code writes it.

```tree caption="Three ways to write handleChange: no type and any leave e unchecked, while React.ChangeEvent with the element type checks e as inline."
How `handleChange` can type `e`
- !No type [`function handleChange`] | The editor **underlines `e`** in strict mode | `e` is **not checked**
- !Written as `any` [`e: any`] | The underline **goes away** | `e` is **still not checked**, so `vlaue` passes
- +Written as the event and the element [`e: React.ChangeEvent<HTMLInputElement>`] | The **same checks** as inline | Every property of `e` **is checked**
```

### VS | The browser's `Event` vs. `React.ChangeEvent`: the first names an object React never passes

When the editor underlines `e`, many developers first try `Event`, because that is what an event is in plain JavaScript:

```tsx title="handleChange typed with the browser's Event"
function handleChange(~e: Event~) { // **WRONG:** React does not pass the browser's Event to the handler
  setQuery(e.currentTarget.value);
}

<input value={query} ~onChange={handleChange}~ /> {/* **WRONG:** the editor refuses handleChange here, because onChange passes a React event object */}
```

The editor now refuses `onChange={handleChange}`. Why? React does not hand our handler the browser's event. It passes its own React event object, the synthetic event. It has most of the same properties as the browser's event, but it is a different object, with a different type. If you ever need the browser's own event, it sits inside `e.nativeEvent`.

Inside the function, the editor also underlines `e.currentTarget.value`, because the browser's `Event` type does not know that the event comes from an `<input>` field.

So the developer tries `e: any`, and every underline goes away. We are back at the start of this lesson: the typo `vlaue` ships, and the results line stays empty while the user types.

### Leaving out the element

A third mistake writes the event type and forgets the angle brackets:

```tsx title="React.ChangeEvent with no element type"
function handleChange(e: React.ChangeEvent) {
  setQuery(e.currentTarget.~value~); // **WRONG:** the editor underlines value: a plain Element has no value
}
```

Without an element in the angle brackets, `React.ChangeEvent` assumes the most general element, `Element`. A plain `Element` can be a paragraph or a heading, and a paragraph has no `value`. Only `HTMLInputElement` tells TypeScript that this element is an `<input>` field with a `value`.

### Our search field with `handleChange`

```tsx title="src/components/SearchBar.tsx" startLine="3"
export default function SearchBar() {
  const [query, setQuery] = useState('');

  function ~handleChange~(e: React.ChangeEvent<HTMLInputElement>) { // Moved out of the tag, so our code writes the type of e
    setQuery(e.currentTarget.value);
  }

  return (
    <div>
      <label>
        Search the store
        <input value={query} onChange={handleChange} />
      </label>
      <p>Results for: {query}</p>
    </div>
  );
}
```

On the page, nothing changes. The user types `shoes`, and the line reads `Results for: shoes`, as in Principle 1. Remember: moved out, write the event and the element.

## PRINCIPLE | `React.ChangeEventHandler<HTMLInputElement>`: type the whole function, and `e` gets the exact same type

> [!PRINCIPLE]
> **Principle 3: Handler Types: `React.ChangeEventHandler` Types the Whole Function**
>
> *Type either the parameter with `React.ChangeEvent<HTMLInputElement>`, or the whole function with `React.ChangeEventHandler<HTMLInputElement>`; both give `e` the exact same type.*
>
> `ChangeEvent` is the type of the event object, and `ChangeEventHandler` is the type of a function that receives it. With the function type, TypeScript infers `e` from it, as it does inline. The function type is also the type of a handler prop. Writing the function type on the parameter types `e` as a function, and the editor underlines `e.currentTarget`.
>
> **DO THIS:**
> ```tsx
> const handleChange: ~React.ChangeEventHandler<HTMLInputElement>~ = (e) => { // The type of the function: e is inferred from it
>   setQuery(e.currentTarget.value);
> };
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> function handleChange(~e: React.ChangeEventHandler<HTMLInputElement>~) { // **WRONG:** a function type on the event, so e.currentTarget is an error
>   setQuery(e.currentTarget.value);
> }
> ```

There is a second way to write the same type. Instead of typing the parameter, type the whole function:

```tsx title="The type on the parameter, and the type on the whole function"
function handleChange(~e: React.ChangeEvent<HTMLInputElement>~) { // 1. The type of the event object, on the parameter
  setQuery(e.currentTarget.value);
}

const handleChange: ~React.ChangeEventHandler<HTMLInputElement>~ = (e) => { // 2. The type of the whole function: e is inferred from it
  setQuery(e.currentTarget.value);
};
```

**Yes, it is the exact same thing!** In both, `e` has the type `React.ChangeEvent<HTMLInputElement>`:
- **With the type on the parameter**, our code writes the type of the event object right after `e`.
- **With the type on the whole function**, our code writes the type of the function after `const handleChange:`. That type says: "a function that receives a `React.ChangeEvent<HTMLInputElement>`". So TypeScript infers `e` from it, the same way it inferred `e` inside `onChange={...}` in Principle 1.

react.dev types the parameter in its event example, and offers the function type in its `useCallback` example, "depending on your code-style preferences". `@types/react` has one such function type for each kind of event, such as `React.KeyboardEventHandler` for key presses. react.dev calls them "the `*EventHandler` functions from the React types".

### VS | `ChangeEvent` vs. `ChangeEventHandler`: the first is the event object, the second is the function that receives it

The two names differ by one word. **They look the same, but they are NOT the same thing!**
- **`React.ChangeEvent<HTMLInputElement>`** is the type of the **event object**, the `e` that React passes. It goes after `e`.
- **`React.ChangeEventHandler<HTMLInputElement>`** is the type of the **function** that receives that event object. It goes after the function name.

```tree caption="ChangeEvent is the type of the event object; ChangeEventHandler is the type of the function that receives it."
Two type names that differ by one word
- +`React.ChangeEvent<HTMLInputElement>` [`e: React.ChangeEvent`] | The type of the **event object** | Goes **after `e`**
- +`React.ChangeEventHandler<HTMLInputElement>` [`const handleChange: React.ChangeEventHandler`] | The type of the **whole function** | Goes **after the function name**
```

A developer who mixes them up puts the function type on the parameter:

```tsx title="The function type written on the parameter"
function handleChange(~e: React.ChangeEventHandler<HTMLInputElement>~) { // **WRONG:** e is now typed as a function, not as an event
  setQuery(e.currentTarget.value);
}
```

The editor then underlines `currentTarget`, because a function has no `currentTarget`.

### Where the function type is useful

The function type does one job the parameter type cannot. A shared search field may take its handler from a parent, as a prop. That prop is a function, so its type is a function type: `onChange: React.ChangeEventHandler<HTMLInputElement>` in the props type of the component (Lesson 90). react.dev also uses the function type with `useCallback`, because in strict mode `useCallback` needs to know the types of its parameters (Lesson 57).

Our search field keeps the type on the parameter for the rest of this lesson. The page does not change, because the types are deleted before the code runs.

## PRINCIPLE | `React.KeyboardEvent<HTMLInputElement>`: a key handler gets `e.key`, the name of the key the user pressed

> [!PRINCIPLE]
> **Principle 4: Event Types: Each Event Brings Its Own Type**
>
> *Pick the event type from the event the handler listens to: `React.KeyboardEvent<HTMLInputElement>` for `onKeyDown`, `React.ChangeEvent<HTMLInputElement>` for `onChange`.*
>
> The element goes in the angle brackets, and the event decides the type in front of them. A keyboard event has `key`, and a change event does not. Reusing the change event type for a key handler makes `e.key` an error and makes `onKeyDown` refuse the handler. Hover over the prop to see its event type, and use `React.SyntheticEvent` for an event with no type of its own.
>
> **DO THIS:**
> ```tsx
> function handleKeyDown(~e: React.KeyboardEvent<HTMLInputElement>~) { // A key press on the field: e.key exists
>   if (e.key === 'Escape') setQuery('');
> }
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> function handleKeyDown(~e: React.ChangeEvent<HTMLInputElement>~) { // **WRONG:** a change event has no key, and onKeyDown refuses this handler
>   if (e.key === 'Escape') setQuery('');
> }
> ```

Now the store wants Escape to empty the search field. React calls the `onKeyDown` handler every time the user presses a key in the field. The handler checks which key it was, so it has an `if` and belongs in its own function. And it needs its own event type:

```tsx title="handleKeyDown empties the field when the user presses Escape"
function handleKeyDown(~e: React.KeyboardEvent<HTMLInputElement>~) { // A key press on an input
  if (~e.key~ === 'Escape') { // The name of the key the user pressed
    setQuery('');
  }
}

<input value={query} onChange={handleChange} onKeyDown={handleKeyDown} />
```

Two new names:
- **`React.KeyboardEvent<HTMLInputElement>`** is the type of the event object for a key press on an `<input>`. It comes from `@types/react`, like `React.ChangeEvent`.
- **`e.key`** is the name of the key the user pressed, such as `'Escape'` for the Esc key. The browser names each key, and React copies that name onto its keyboard event object.

### VS | `onChange` vs. `onKeyDown` on the same `<input>`: the element stays, and the event type changes

Both handlers sit on the same `<input>`, so the element in the angle brackets is the same. The event is different. **It looks the same, but it is NOT the same thing!** The event type follows the event, not the element:
- **On `onChange`**, the event is a change of the text, so `e` is a `React.ChangeEvent<HTMLInputElement>`. A change event has no `key`.
- **On `onKeyDown`**, the event is a key press, so `e` is a `React.KeyboardEvent<HTMLInputElement>`. A keyboard event has `key`.

```tree caption="The same input with two handlers: the element type stays the same, and the event type follows the event."
Two handlers on the same `<input>`
- +`onChange` [`handleChange`] | The text of the field **changes** | `e` is a **`React.ChangeEvent<HTMLInputElement>`**, with **no `key`**
- +`onKeyDown` [`handleKeyDown`] | The user **presses a key** in the field | `e` is a **`React.KeyboardEvent<HTMLInputElement>`**, with **`e.key`**
```

### Copying the first line of `handleChange`

A developer who writes `handleKeyDown` often starts by copying the first line of `handleChange`:

```tsx title="handleKeyDown typed as a change event"
function handleKeyDown(e: React.ChangeEvent<HTMLInputElement>) {
  if (e.~key~ === 'Escape') { // **WRONG:** the editor underlines key: a change event has no key
    setQuery('');
  }
}

<input value={query} onChange={handleChange} ~onKeyDown={handleKeyDown}~ /> {/* **WRONG:** the editor refuses it: onKeyDown passes a keyboard event */}
```

One copied line, two errors:
1. Inside the handler, the editor underlines `key`, because a change event has no `key`.
2. On the tag, the editor refuses `onKeyDown={handleKeyDown}`, because the function expects a change event and `onKeyDown` passes a keyboard event.

The tempting way out is `(e as any).key`.

> [!DEFINITION]
> **What does `as` do?** [NEW] `as` tells TypeScript: "treat this value as the type I write after it". TypeScript believes it without checking. So `e as any` turns `e` into `any` on that line: every underline goes away, and so does every check. A misspelled `kye` on that line would pass without a word (Lesson 91).

The right way is to ask the editor. Hover over the prop itself, such as `onKeyDown`. react.dev gives exactly this advice: the hover information "will show the type of the event". For an event that has no type of its own in `@types/react`, react.dev names the base type for all events, `React.SyntheticEvent`.

### Our search field with Escape

```tsx title="src/components/SearchBar.tsx" startLine="3"
export default function SearchBar() {
  const [query, setQuery] = useState('');

  function handleChange(e: React.ChangeEvent<HTMLInputElement>) {
    setQuery(e.currentTarget.value);
  }

  function ~handleKeyDown~(e: React.KeyboardEvent<HTMLInputElement>) { // A key press: its own event type, with e.key
    if (e.key === 'Escape') {
      setQuery('');
    }
  }

  return (
    <div>
      <label>
        Search the store
        <input value={query} onChange={handleChange} onKeyDown={handleKeyDown} />
      </label>
      <p>Results for: {query}</p>
    </div>
  );
}
```

The user types `shoes`, then presses Escape. The field empties, and the results line empties with it:

```page width=full caption="The search field after the user types shoes and then presses Escape: the field and the results line are both empty."

  field: Search the store |  | good
line: Results for: | good
console: quiet
```

Remember: the element goes in the angle brackets, and the event picks the type in front of them.

## PRINCIPLE | `e.currentTarget`: always the element with the handler, and typed as that element

> [!PRINCIPLE]
> **Principle 5: `currentTarget`: `e.currentTarget` Knows the Element, `e.target` Does Not**
>
> *To use the element the handler sits on, read `e.currentTarget`; its type is the element in the angle brackets, while `e.target` is typed as a plain `EventTarget` for most events.*
>
> `e.currentTarget` is always the element with the handler, so `@types/react` types it as that element. `e.target` is where the event started, which may be a child, so it is typed loosely. The change event is an exception kept until React 20, which is why `e.target.value` type-checks on `onChange`. Forcing `e.target` with `as` silences the editor, and the code reads the icon instead of the button when the user clicks the icon.
>
> **DO THIS:**
> ```tsx
> function handleKeyDown(e: React.KeyboardEvent<HTMLInputElement>) {
>   if (e.key === 'Escape') ~e.currentTarget.blur()~; // currentTarget is typed as the input
> }
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> function handleKeyDown(e: React.KeyboardEvent<HTMLInputElement>) {
>   if (e.key === 'Escape') e.target.~blur~(); // **WRONG:** target is a plain EventTarget, which has no blur
> }
> ```

After Escape empties the field, the cursor still blinks inside it. The user gave up on the search, so the cursor should leave the field too. The browser has a method for that on every element: `blur()`. It removes the focus from the element, and the cursor leaves it. In plain JavaScript, you would write `document.getElementById('search').blur()`.

In a handler, you already have the element: it is on `e`. There are two ways to reach it (Lesson 11):
- **`e.target`** is the element where the event started.
- **`e.currentTarget`** is the element whose handler runs.

In our field, both are the same `<input>`, because an `<input>` has nothing inside it:

```tsx title="Taking the cursor out of the field with e.currentTarget, and with e.target"
function handleKeyDown(e: React.KeyboardEvent<HTMLInputElement>) {
  if (e.key === 'Escape') {
    setQuery('');
    ~e.currentTarget.blur()~; // 1. No error: currentTarget is typed as the input
    e.target.~blur~(); // 2. **WRONG:** the editor underlines blur: target is typed as a plain EventTarget
  }
}
```

**It may look the same, and it works the same in the browser, but it is NOT the same thing for the type-checker!** When this code runs, both lines reach the exact same `<input>`. Only `e.currentTarget.blur()` passes the type-checker.

### Why the types differ when the element is the same

The types describe every possible page, not just our field. That is the whole reason:
1. The developer writes `e.target.blur()`, because `e.target.value` worked in a change handler before (Lesson 20).
2. The editor underlines `blur`. In a keyboard event, `e.target` is typed as `EventTarget`, the browser's most general type for anything that can receive an event. An `EventTarget` has no `blur()` and no `value`.
3. `e.target` is typed so loosely because it is the element where the event started. react.dev warns that it "could be a distant child" of the element with the handler. `@types/react` cannot know which child, so it gives `e.target` the most general type.
4. `e.currentTarget` is always the element the handler sits on. That element is known: it is the one in the angle brackets. So `@types/react` types `e.currentTarget` as an `HTMLInputElement`.
5. The developer changes the line to `e.currentTarget.blur()`, and the underline is gone. The user presses Escape: the field empties, and the cursor leaves it.

```tree caption="In a keyboard event, e.currentTarget is typed as the element in the angle brackets, while e.target is typed as a plain EventTarget."
Two ways to reach the field in `handleKeyDown`
- +`e.currentTarget` [`e.currentTarget.blur`] | Always the element **the handler sits on** | Typed as **`HTMLInputElement`**, so `blur` **type-checks**
- !`e.target` [`e.target.blur`] | The element **where the event started**, which may be a child | Typed as a plain **`EventTarget`**, so `blur` is **underlined**
```

### Surprise: `e.target.value` still type-checks on `onChange`

Back in `handleChange`, the developer tries `e.target.value` and gets no error. For a change event, `e.target` is typed as the `<input>` after all.

**On `onChange`, `e.target.value` and `e.currentTarget.value` are the exact same thing today, for the type-checker too!** `@types/react` makes one exception for the change event and types its `target` like the element. Its own comment calls this wrong and says it is "kept for backward compatibility until React 20".

So `e.target.value` in a change handler was correct in Lesson 20, and it still is. react.dev's TypeScript page already reads `e.currentTarget.value`, and so does our search field, because that form stays correct when the exception ends.

### Forcing the type of `e.target` with `as`

When `e.target` is underlined, a developer may force its type with `as`, the word from Principle 4 that TypeScript believes without checking. Here is where that goes wrong.

Under the search field, many stores show the user's recent searches as small buttons, each with a clock icon and a word, such as `boots`. A click on a button puts its word back in the field. Each button keeps its word in its `value` attribute. The click handler reads it, and its event type is `React.MouseEvent`, the event type for a click:

```tsx title="A recent search button that forces the type of e.target"
function handleRecentClick(e: React.MouseEvent<HTMLButtonElement>) {
  setQuery((~e.target as HTMLButtonElement~).value); // **WRONG:** when the user clicks the clock icon, target is the icon, and value is undefined
}

<button value="boots" onClick={handleRecentClick}><ClockIcon /> boots</button>
```

**Beware! The forced type silences the editor, but it is false whenever the user clicks the icon.** Here is what happens:
1. The user clicks the clock icon inside the `boots` button.
2. The click starts on the icon, so `e.target` is a part of the icon, such as a `<path>` line inside the `<svg>` drawing, not the button.
3. A `<path>` has no `value`, so `setQuery` receives `undefined`.
4. The field does not show `boots`, and the results line stays empty, as with the typo at the start of this lesson. React prints the same Console warning about a controlled input.

`e.currentTarget` is the button every time, wherever inside it the user clicks. It is already typed as an `HTMLButtonElement`, so it needs no forcing:

```tsx title="The recent search button reading e.currentTarget"
function handleRecentClick(e: React.MouseEvent<HTMLButtonElement>) {
  setQuery(~e.currentTarget.value~); // The button itself, even when the user clicks the icon: the field shows boots
}
```

### Our search field, finished

`handleKeyDown` now takes the cursor out of the field after it empties it:

```tsx title="src/components/SearchBar.tsx" startLine="10"
  function handleKeyDown(e: React.KeyboardEvent<HTMLInputElement>) {
    if (e.key === 'Escape') {
      setQuery('');
      ~e.currentTarget.blur()~; // The input itself: the cursor leaves it
    }
  }
```

The user types `shoes`, then presses Escape. The field and the results line are empty, as at the end of Principle 4, and the cursor no longer blinks in the field. Remember: to reach the element with the handler, read `e.currentTarget`.

## All 5 Principles Together

### The complete code

Both handlers are moved out of the tag, so both write their event type and their element type, and both reach the `<input>` through `e.currentTarget`:

```tsx title="src/components/SearchBar.tsx"
import { useState } from 'react';

export default function SearchBar() {
  const [query, setQuery] = useState('');

  function handleChange(~e: React.ChangeEvent<HTMLInputElement>~) { // Principles 2 and 5: a change on the input
    setQuery(e.currentTarget.value);
  }

  function handleKeyDown(~e: React.KeyboardEvent<HTMLInputElement>~) { // Principle 4: a key press on the input
    if (e.key === 'Escape') {
      setQuery('');
      ~e.currentTarget.blur()~; // Principle 5: the input itself, typed as an HTMLInputElement
    }
  }

  return (
    <div>
      <label>
        Search the store
        <input value={query} onChange={handleChange} onKeyDown={handleKeyDown} />
      </label>
      <p>Results for: {query}</p>
    </div>
  );
}
```

```tsx title="src/App.tsx"
import SearchBar from './components/SearchBar';

export default function App() {
  return <SearchBar />;
}
```

### The order in which React calls the components and the handlers

When the page loads, React calls `App`, and then `SearchBar`. After that, React calls a handler each time the user does something in the field. When the user presses a key, React calls `handleKeyDown` first. When that key changes the text of the field, React then calls `handleChange`. Escape changes no text, so it reaches only `handleKeyDown`:

```tree caption="The order of the calls: React calls App, then SearchBar, and then a handler with its own event type for each thing the user does in the field."
`App` [1. React calls it when the page loads] | Returns `<SearchBar />`
- +`SearchBar` [2. React calls it next] | Holds `query` and renders the field and the results line
  - +`handleKeyDown` [3. When the user presses a key] | Receives a **`React.KeyboardEvent<HTMLInputElement>`** | On Escape, empties `query` and takes the cursor out
  - +`handleChange` [4. When that key changes the text] | Receives a **`React.ChangeEvent<HTMLInputElement>`** | Saves the text of the field into `query`
```

| Where the handler is written | How `e` gets its type | What our code writes |
| :--- | :--- | :--- |
| **Inline, inside `onChange={...}`** | TypeScript infers it from `onChange` | Nothing |
| **In its own function, typing the parameter** | Our code writes the event type and the element type | `e: React.ChangeEvent<HTMLInputElement>` |
| **In its own function, typing the whole function** | TypeScript infers `e` from the function type | `React.ChangeEventHandler<HTMLInputElement>` |
| **A key handler on the same field** | The event decides the type, the element stays | `e: React.KeyboardEvent<HTMLInputElement>` |
| **Reaching the element from any handler** | `e.currentTarget` is typed as the element | `e.currentTarget.blur()`, `e.currentTarget.value` |

Remember the one sentence of this lesson. **The type of `e` comes from the place where the handler is written: inline, TypeScript supplies it; in a separate function, our code writes the event type and the element type.**

## For the Interview

> **The Interview Question:** How do you type event handlers and SyntheticEvents in TypeScript?

### How to Answer Clearly in 30 Seconds

"React passes every handler its own event object, the synthetic event, and `@types/react` gives each kind of event its own type. The type of `e` comes from where the handler is written:
1. **Inline**, inside `onChange={...}`, TypeScript infers `e` from the prop, and I write nothing. Hovering over `e` shows the type.
2. **In a separate function**, I write it myself: the event type, then the element in angle brackets, such as `React.ChangeEvent<HTMLInputElement>` or `React.KeyboardEvent<HTMLInputElement>`. Or I type the whole function with `React.ChangeEventHandler<HTMLInputElement>`.
3. **To reach the element**, I read `e.currentTarget`, which is typed as the element the handler sits on. `e.target` is typed as a plain `EventTarget` for most events, because the event may have started on a child.

I never write `e: any`, which turns off every check on `e`, and never the browser's `Event`, which is not the object React passes."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why can't you type a React handler with the browser's `Event`?"**
   Because React does not pass the browser's event to the handler. It passes its own event object, the synthetic event, which has most of the same properties but a different type. The editor refuses a handler typed with `Event` on `onChange`, because the function does not accept what `onChange` passes. When the code really needs the browser's own event, it sits inside `e.nativeEvent`.
2. **"Why does `e.target.value` type-check in a change handler, but `e.target.blur()` fails in a key handler?"**
   `@types/react` types `e.currentTarget` as the element in the angle brackets, and `e.target` as a plain `EventTarget`, because the event may have started on a distant child. The change event is an exception: its `target` is typed like the element, "kept for backward compatibility until React 20", as the comment in `@types/react` says. So `e.currentTarget` is the form that is right for every event, and react.dev's own example reads `e.currentTarget.value`.
3. **"How do you type a form's `onSubmit` handler?"**
   The same way: find the event type by hovering over `onSubmit`, then put the element in angle brackets. In the newest `@types/react`, `onSubmit` takes a `React.SubmitEventHandler`, and its event is `React.SubmitEvent<HTMLFormElement>`. Older code writes `React.FormEvent<HTMLFormElement>`, which the newest `@types/react` marks as deprecated, with the note that "FormEvent doesn't actually exist". For an event with no type of its own, `React.SyntheticEvent` is the base type for all events.

```tree caption="Interview summary: where the type of e comes from, and the two quick fixes that break the checks."
How a handler gets the type of `e`
- +Inline on the tag [`onChange={e => setQuery}`] | TypeScript **infers** `e` from the prop | Hover over `e` to see the type
- +Separate function [`e: React.ChangeEvent<HTMLInputElement>`] | Our code writes the **event** and the **element** | Or the whole function: **`React.ChangeEventHandler<HTMLInputElement>`**
- !Quick fixes [`e: any` `e: Event`] | ~Do **NOT** use them | `any` **removes every check**; `Event` names the **wrong event object**
```
