# Lecture 62: Virtualized Lists: Rendering Only the Rows the User Can See

*(How do you show 10,000 orders without putting 10,000 rows on the page?)*

> INTERVIEW QUESTION | ❱❱ MORE | How do you render a list of ten thousand items without rendering ten thousand rows?

---

## VS | Every Row `orders.map` vs. Only the Visible Rows `orders.slice`: both show the same twenty orders, only the second keeps the DOM small

> When a page lists 10,000 orders inside a `<div>` with its own scrollbar, the user sees only about twenty of them at a time. **A virtualized list puts only those twenty rows on the page, plus a few extra, and fills the rest with empty space as tall as the rows it left out.** The reason: React creates a real DOM element for every element your component returns, and `overflow` only hides the extra rows, it never removes them.

Think about what you would do in plain JavaScript. To show 10,000 orders, you write a loop. The loop creates one `<li>` element per order and appends it to the `<ul>`. You would never expect the browser to skip some of them because they are below the edge of the screen:

```js title="Plain JavaScript: a loop creates 10,000 li elements"
for (const order of orders) {
  const li = document.createElement('li');
  li.textContent = 'Order #' + order.id;
  list.~appendChild~(li); // One real element per order: 10,000 in total
}
```

In React, you write no loop and call no `appendChild`. You call `map()`, and React creates the elements for you. But it is exactly the same work. Every `<li>` that `map()` returns becomes a real element in the DOM:

```jsx title="React: map returns 10,000 li elements, and React creates every one"
<ul>{~orders.map~(order => <li key={order.id}>Order #{order.id}</li>)}</ul> {/* The same 10,000 real elements */}
```

Keep one sentence in mind for the whole lesson: **the number of items in your data and the number of elements on the page are two separate numbers.** A virtualized list keeps the second number small, however big the first one grows.

Take the Orders page in the admin of an online shop, such as Shopify. The shop has 10,000 orders. They sit in one `<div>` that is 600 pixels tall and has its own scrollbar. Every row is 30 pixels tall, so the `<div>` shows twenty rows at a time:

### Three New Words

> [!DEFINITION]
> **What is a scroll container?** [NEW] A scroll container is an element with its own scrollbar, such as `<div style={{ height: 600, overflowY: 'auto' }}>`. The CSS value `overflowY: 'auto'` tells the browser: when the content inside this `<div>` is taller than the `<div>`, show a vertical scrollbar. Only the `<div>` scrolls, not the page. The browser still creates and lays out everything inside it, including the rows below its bottom edge. It only clips them, so the user cannot see them (Lesson 62).

> [!DEFINITION]
> **What is a virtualized list?** [NEW] A virtualized list is a list that puts on the page only the rows inside the visible part of the scroll container, plus a few extra, and replaces all the other rows with empty space of the same height. React's documentation calls it a virtualized list. Chrome's Lighthouse tool, and many interviewers, call the same idea windowing, because the scroll container is the window the user looks through. It is called virtual because most of the list exists only in the data, not on the page (Lesson 62).

> [!DEFINITION]
> **What is the event object?** [REVIEW] When something happens on an element, React calls your handler and passes it the event object, usually named `e`. `e.currentTarget` is the element the handler sits on. In this lesson, that is the scroll container (Lesson 11).

### What a Long List Costs

The owner pays in two ways, one for each version:
1. **With every row on the page, the page is slow to appear.** The browser must create and lay out 10,000 rows before the owner sees the first twenty, and it keeps all of them in memory. Chrome's Lighthouse tool warns about exactly this: "A large DOM can increase the duration of style calculations and layout reflows, impacting page responsiveness. A large DOM will also increase memory usage."
2. **With only the visible rows on the page, a row forgets what the owner did on it.** The owner ticks an order, scrolls away, and scrolls back. The tick is gone, unless the list keeps it in its own state.

Developers usually go wrong in four ways:
1. They think `overflow` makes the hidden rows cheap. It only clips them. Every row is still a DOM element.
2. They think React skips the rows the user cannot see. React creates a DOM element for every element the component returns. React's documentation speaks of built-in virtualized lists only as a possible future: "if React adds built-in support for virtualized lists in the future".
3. They put only the visible rows on the page and forget the height of the others, so the scrollbar disappears.
4. They let a row keep something for itself, such as a tick, and lose it when the row scrolls away.

### Three Ways to Show a Long List

When a page must show thousands of items, you have three choices:
1. **Render every row.** This fits a list of a few hundred simple rows. Before you change anything, measure. React's documentation advises testing with "an artificial slowdown", such as Chrome's "CPU Throttling" option, in a production build, and "on a device like your users have".
2. **Split the list into pages, or add a `Load more` button.** This fits a list where the user wants the newest items and rarely goes far back. Each page renders a few dozen rows.
3. **Render a virtualized list.** This fits one long list that the user scrolls freely, such as orders, chat history, or logs. In production, a library does the work. Chrome's Lighthouse advises a windowing library for React pages with many repeated elements, and it names `react-window`.

```tree caption="Three ways to show a long list, and the list each one fits."
Three ways to show thousands of items
- +Render every row | Fits **a few hundred simple rows** | **Measure first** with CPU Throttling and a production build
- +Pages or a `Load more` button | Fits a list where the user wants **the newest items** | Each page renders **a few dozen rows**
- +A virtualized list | Fits **one long list the user scrolls freely** | In production, **a library such as `react-window`** does it
```

In this lesson, we build the virtualized list by hand, one step per principle, so you see what a library such as `react-window` does inside.

### The Rule of Thumb: how many rows can the user see?

**Ask one question about every long list: how many rows can the user see at once? Put that many rows on the page, plus a few, and give the rest of the list its height as empty space.**

## SECTION | The Orders Page: 10,000 Orders in One Scroll Container

Our page is the Orders page from the start of the lesson. It has three files of our own:
1. **`orders.js`** exports `orders`, the array of 10,000 orders.
2. **`OrderList.jsx`** shows the scroll container with one row per order. This is the file that grows with every principle.
3. **`App.jsx`** shows the heading `Orders` and the list.

```files title="orders-page: File Explorer" caption="How the files of our Orders page sit inside src/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it into `#root`
  App.jsx | parent | Exports `App` as default and imports `OrderList` from `./OrderList.jsx`
  OrderList.jsx | list | Exports `OrderList` as default: the scroll container with one row per order
  orders.js | data | Exports `orders`, an array of 10,000 orders from `{ id: 1 }` to `{ id: 10000 }`
```

The data file builds the 10,000 orders:

```js title="src/orders.js"
export const orders = ~Array.from~({ length: 10000 }, (_, i) => ({ id: i + 1 })); // 10,000 objects, from { id: 1 } to { id: 10000 }
```

`Array.from({ length: 10000 }, ...)` is a JavaScript function. It builds an array of 10,000 places and calls our function once for each place. Our function gets two arguments:
1. **The value already in that place.** The place is empty, so the value is `undefined`. We name it `_`, because our code never reads it.
2. **The position `i`**, from `0` to `9999`. Our code adds one, so the first order is `Order #1`, not `Order #0`.

The first version of the list maps every order to a row:

```jsx title="src/OrderList.jsx"
import { orders } from './orders.js';

export default function OrderList() {
  return (
    <div style={{ height: 600, ~overflowY: 'auto'~ }}> {/* The scroll container: 600 pixels tall, with its own scrollbar */}
      <ul style={{ margin: 0 }}>
        {orders.map(order => (
          <li key={order.id} style={{ height: 30 }}>Order #{order.id}</li>
        ))}
      </ul>
    </div>
  );
}
```

The `margin: 0` on the `<ul>` removes the space the browser puts above and below every `<ul>` by default, so the first row starts at the very top of the scroll container.

The main file shows the heading and the list:

```jsx title="src/App.jsx"
import ~OrderList~ from './OrderList.jsx'; // The default export of the list file

export default function App() {
  return (
    <main>
      <h1>Orders</h1>
      <OrderList />
    </main>
  );
}
```

The page looks exactly like the Orders page at the start of the lesson: the heading, `Order #1` to `Order #20`, and a scrollbar.

**PRINCIPLES:** The number of items in the data and the number of elements on the page are two separate numbers. A virtualized list keeps the second one small in six steps:
1. **Principle 1: `orders.map` Puts 10,000 `<li>` Elements in the DOM.** The scroll container shows twenty orders, but every order the component maps becomes a DOM element.
2. **Principle 2: `onScroll` Tells the List Which Order Is at the Top.** The handler copies `scrollTop` into state, and the component divides it by the row height.
3. **Principle 3: `slice` Alone Removes the Scrollbar.** Twenty rows fill the scroll container exactly, so there is nothing left to scroll.
4. **Principle 4: Padding Above and Below Brings the Scrollbar Back.** Empty space as tall as the rows left out gives the list the height of all 10,000 orders.
5. **Principle 5: Five Extra Rows Fill the Edges.** A few rows above and below the visible part cover the edge when the scroll stops between two rows or moves quickly.
6. **Principle 6: A Tick Lives in the List, Not in the Row.** A row that scrolls away is destroyed with everything it held, so the list keeps the ticks in its own state.

## PRINCIPLE | `orders.map`: every order becomes a DOM element, even the ones nobody sees

> [!PRINCIPLE]
> **Principle 1: `orders.map` Puts 10,000 `<li>` Elements in the DOM**
>
> *A component that maps over every item returns one element per item, and React puts every one of them in the DOM, even when the scroll container shows only twenty.*
>
> The owner sees twenty orders, so it is easy to believe the page holds twenty rows. It holds 10,000. The browser creates, styles, and lays out every row before the page appears, and keeps all of them in memory. `overflow` only hides the rows below the edge, and `memo` or `useMemo` only skip work on later renders. For a short list, such as the twenty newest orders on a dashboard, mapping every row is fine. For 10,000 rows, measure first, and then render fewer rows.
>
> **DO THIS:**
> ```jsx
> {~latestOrders.map~(order => ( // The 20 newest orders: 20 li elements, nothing to optimize
>   <li key={order.id}>Order #{order.id}</li>
> ))}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <div style={{ height: 600, overflowY: 'auto' }}>
>   {~orders.map~(order => ( // **WRONG:** the div shows 20 rows, but all 10,000 li elements exist
>     <li key={order.id} style={{ height: 30 }}>Order #{order.id}</li>
>   ))}
> </div>
> ```

### Twenty Rows on the Screen, 10,000 in the Elements Panel

Open the Elements panel on our first version, and count the rows:

```dom caption="What the Elements panel shows for the list that maps every order: 10,000 li elements, of which the scroll container shows twenty."
<div style="height: 600px; overflow-y: auto;">
  <ul style="margin: 0px;">
    <li style="height: 30px;">Order #1</li>
    <li style="height: 30px;">Order #2</li>
  * 9,997 more li elements, from Order #3 to Order #9999
!   <li style="height: 30px;">Order #10000</li> | note: The last of 10,000 li elements, far below the bottom edge of the scroll container
  </ul>
</div>
```

Here is what happens when the owner opens the page:
1. `orders` holds 10,000 objects, so `orders.map(...)` returns 10,000 `<li>` elements.
2. React creates a DOM element for every one of them on the first render. React does not know, and does not ask, which rows the scroll container will show.
3. The browser calculates the style and the position of all 10,000 rows before it paints the page. The content is 10,000 rows of 30 pixels: 300,000 pixels inside a `<div>` of 600 pixels.
4. The `<div>` clips everything below `Order #20`. The other 9,980 rows still exist. The owner simply cannot see them.

The rows below the edge are not free. The browser keeps every one of them in memory and lays out every one of them. Lighthouse calls a page with very many DOM elements a large DOM, and its audit "Optimize DOM size" exists for exactly this case. A real row also holds more than a line of text: a link, a price, a button, a checkbox. Each part is one more DOM element, so a real row multiplies the count.

### Mistake: Trust in `memo` to Speed Up the First Load

Here is how this usually reaches a real shop:
1. The developer builds the Orders page with ten test orders, and the page opens at once.
2. The shop grows, and the server now sends 10,000 orders.
3. The page takes longer to appear, and on the owner's older laptop, scrolling may feel slow.
4. The developer wraps the rows in `memo` or the list in `useMemo`, and the first load is no faster. React's documentation says it plainly: "`useMemo` won't make the *first* render faster." Both skip work on later renders. Neither one removes a single DOM element.

Your laptop is probably faster than the owner's. So measure before you change anything: slow your machine down on purpose with Chrome's CPU Throttling, and time a production build, not the development server.

Remember: the number of items in the data and the number of elements on the page are two separate numbers. With `orders.map`, they are the same number.

## PRINCIPLE | `onScroll` on the scroll container: the list learns which order is at the top

> [!PRINCIPLE]
> **Principle 2: `onScroll` Tells the List Which Order Is at the Top**
>
> *The scroll container's `onScroll` handler copies `e.currentTarget.scrollTop`, the number of pixels scrolled from the top, into state; during render, the first visible row is `Math.floor(scrollTop / 30)`.*
>
> The browser keeps the scroll position inside the DOM element of the scroll container. React learns it only when our `onScroll` handler copies it into state. The handler must sit on the element that really scrolls, the one with `overflowY: 'auto'`, because the browser fires the `scroll` event only on that element, and the event does not bubble to its parents. Once `scrollTop` is in state, the first visible row is simple arithmetic, calculated on every render.
>
> **DO THIS:**
> ```jsx
> <div style={{ height: 600, overflowY: 'auto' }} ~onScroll~={e => setScrollTop(e.currentTarget.scrollTop)}> {/* The element that scrolls: runs on every scroll */}
>   <ul style={{ margin: 0 }}>...</ul>
> </div>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <div style={{ height: 600, overflowY: 'auto' }}>
>   <ul style={{ margin: 0 }} ~onScroll~={e => setScrollTop(e.currentTarget.scrollTop)}>...</ul> {/* **WRONG:** the ul never scrolls, so the line stays on orders 1 to 20 */}
> </div>
> ```

### Pixels from the Browser, a Row Number for React

To put only the visible rows on the page, the component must first know which rows are visible. The browser knows how far the scroll container is scrolled. React does not.

In plain JavaScript, you read the scroll position yourself, from the element, whenever it changes:

```js title="Plain JavaScript: read scrollTop from the element"
list.addEventListener('scroll', () => {
  console.log(list.~scrollTop~); // 0 at the top, 3000 after a hundred rows of 30 pixels
});
```

In React, the render must see that number, so the handler copies it into state:

```jsx title="React: copy scrollTop into state on every scroll"
const [scrollTop, setScrollTop] = useState(0);
const first = ~Math.floor(scrollTop / 30)~; // Pixels scrolled divided by the row height: the first visible row

<p>Showing orders {first + 1} to {first + 20} of 10000</p>
<div style={{ height: 600, overflowY: 'auto' }} ~onScroll~={e => setScrollTop(e.currentTarget.scrollTop)}> {/* Copies the browser's number into state */}
  ...
</div>
```

> [!DEFINITION]
> **What is scrollTop?** [NEW] `scrollTop` is a property of a DOM element, kept by the browser. It says how many pixels the content of the element is scrolled up past its top edge. It is `0` when the scroll container shows the first row. No line of our code ever sets it: the browser changes it while the user scrolls (Lesson 62).

`onScroll` is the React prop for the browser's `scroll` event. React's documentation describes it in two sentences: it "Fires when an element has been scrolled. This event does not bubble."

The arithmetic turns pixels into a row number. Every row is 30 pixels tall, so `Math.floor(scrollTop / 30)` is the position of the first visible order in the array. `Math.floor` drops the part after the decimal point, so a scroll of 3015 pixels still gives row `100`. `first` counts from zero, and order numbers count from one, so the line shows `first + 1`.

`first` is a plain `const`, calculated during render. It never gets a state variable of its own, because it always follows from `scrollTop` (Lesson 22).

### A Scroll of a Hundred Rows

The owner scrolls down by 3000 pixels, the height of a hundred rows. Here is what happens:
1. The browser moves the content up, and it fires `scroll` events on the scroll container while the content moves.
2. React calls our `onScroll` handler for each event, and the handler copies the new `scrollTop` into state.
3. Each new number renders `OrderList` again.
4. When `scrollTop` reaches 3000, `first` is 3000 divided by 30, which is 100. The line above the list now names orders 101 to 120, and `Order #101` is at the top.

### Mistake: `onScroll` on the `<ul>` Instead of the `<div>`

Here is a mistake that leaves the line stuck:
1. The developer puts the `onScroll` handler on the `<ul>`, because the rows live inside it.
2. The `<ul>` never scrolls. It is as tall as its rows. The element that scrolls is the `<div>` with `overflowY: 'auto'` around it.
3. The browser fires the `scroll` event on the `<div>`. An event never travels down from its element into the children, so the handler on the `<ul>` never runs.
4. The line above the list stays on orders 1 to 20 while the owner scrolls through the orders.

```jsx title="onScroll on the list that never scrolls"
<div style={{ height: 600, overflowY: 'auto' }}>
  <ul style={{ margin: 0 }} ~onScroll~={e => setScrollTop(e.currentTarget.scrollTop)}> {/* **WRONG:** the ul never scrolls, so this never runs */}
    ...
  </ul>
</div>
```

A handler one level up fails too. Put it on the `<section>` around the scroll container, and it never runs either, for the reason React's documentation gives: the `scroll` event does not bubble, so it never climbs from the `<div>` to its parents. The handler must sit on the scroll container itself.

### The Orders Page Reads the Scroll Position

In our list file, `useState` now holds `scrollTop`, the component calculates `first`, and the line appears above the scroll container. Every order is still on the page:

```jsx title="src/OrderList.jsx"
import { useState } from 'react';
import { orders } from './orders.js';

export default function OrderList() {
  const [scrollTop, setScrollTop] = useState(0);
  const first = Math.floor(scrollTop / 30);

  return (
    <section>
      <p>Showing orders {first + 1} to {first + 20} of {orders.length}</p>
      <div style={{ height: 600, overflowY: 'auto' }} ~onScroll~={e => setScrollTop(e.currentTarget.scrollTop)}> {/* Runs while the owner scrolls */}
        <ul style={{ margin: 0 }}>
          {orders.map(order => (
            <li key={order.id} style={{ height: 30 }}>Order #{order.id}</li>
          ))}
        </ul>
      </div>
    </section>
  );
}
```

## PRINCIPLE | `slice` alone: twenty rows fill the scroll container exactly, so the scrollbar disappears

> [!PRINCIPLE]
> **Principle 3: `slice` Alone Removes the Scrollbar**
>
> *`orders.slice(first, first + 20)` puts only the visible orders on the page, but the content is then only 600 pixels tall, so the scroll container has nothing left to scroll.*
>
> The browser decides whether to show a scrollbar from the height of the content inside the scroll container. Twenty rows of 30 pixels fill a `<div>` of 600 pixels exactly, so the browser shows no scrollbar, the owner cannot scroll, and `scrollTop` never moves from `0`. A virtualized list has two jobs: render fewer rows, and keep the height of the whole list. `slice()` does only the first one.
>
> **DO THIS:**
> ```jsx
> <ul style={{ margin: 0, ~paddingTop: first * 30, paddingBottom: (orders.length - first - 20) * 30~ }}> {/* Twenty rows plus the height of the other 9,980 */}
>   {orders.slice(first, first + 20).map(order => <li key={order.id} style={{ height: 30 }}>Order #{order.id}</li>)}
> </ul>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ul style={{ margin: 0 }}>
>   {~orders.slice(first, first + 20)~.map(order => <li key={order.id} style={{ height: 30 }}>Order #{order.id}</li>)} {/* **WRONG:** 600 pixels of content: no scrollbar */}
> </ul>
> ```

### Twenty Orders from `first`

Now the component knows the first visible order. The obvious next step is to render only twenty orders from there:

```jsx title="Slice the array to the twenty visible orders"
{~orders.slice(first, first + 20)~.map(order => ( // Twenty orders, from the first visible one
  <li key={order.id} style={{ height: 30 }}>Order #{order.id}</li>
))}
```

`slice(first, first + 20)` returns a new array with the twenty orders from position `first` up to, but not including, position `first + 20` (Lesson 19). The Elements panel now shows twenty `<li>` elements instead of 10,000.

### Mistake: Fewer Rows Seen as the Whole Idea

Here is how a developer gets here:
1. The developer reads that a long list should render only the visible rows.
2. The developer adds `slice(first, first + 20)` to the list.
3. The Elements panel shows twenty `<li>` elements, and the developer is pleased.
4. The shop owner cannot scroll past the twentieth order.

## PRINCIPLE | `paddingTop` and `paddingBottom`: empty space as tall as the absent rows brings the scrollbar back

> [!PRINCIPLE]
> **Principle 4: Padding Above and Below Brings the Scrollbar Back**
>
> *Give the `<ul>` a top padding as tall as the rows before the visible ones and a bottom padding as tall as the rows after them; the content is then 300,000 pixels tall again, while only twenty rows exist.*
>
> To scroll through 10,000 rows, the scroll container needs content as tall as 10,000 rows, not the rows themselves. The two paddings give that height, so the scrollbar matches the whole list, and the twenty real rows sit exactly where the full list would put them. The arithmetic holds only while every row is exactly the height the code uses.
>
> **DO THIS:**
> ```jsx
> <ul style={{ margin: 0, paddingTop: first * 30, paddingBottom: (orders.length - first - 20) * 30 }}>
>   {visible.map(order => <li key={order.id} style={{ ~height: 30~ }}>Order #{order.id}</li>)} {/* Every row is exactly the 30 pixels the padding counts */}
> </ul>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ul style={{ margin: 0, paddingTop: first * 30, paddingBottom: (orders.length - first - 20) * 30 }}>
>   {visible.map(order => <li key={order.id} style={{ height: 30, ~padding: '5px 0'~ }}>Order #{order.id}</li>)} {/* **WRONG:** rows are 40 pixels, so the rows jump while the owner scrolls */}
> </ul>
> ```

### Empty Space Stands In for the Rows Left Out

The browser asks one question before it draws a scrollbar: how tall is the content? So we give it the right answer without the real rows. Twenty rows are real, and the rest of the height is padding inside the `<ul>`:

```jsx title="Padding above and below the twenty visible rows"
const first = Math.floor(scrollTop / 30);
const visible = orders.slice(first, first + 20);

<ul style={{ margin: 0, ~paddingTop: first * 30~, ~paddingBottom: (orders.length - first - 20) * 30~ }}> {/* The height of the rows before and after the visible ones */}
  {visible.map(order => (
    <li key={order.id} style={{ height: 30 }}>Order #{order.id}</li>
  ))}
</ul>
```

`paddingTop` and `paddingBottom` are CSS properties. They add empty space inside an element, above and below its content. React turns a plain number into pixels, so `paddingTop: 3000` becomes `padding-top: 3000px` in the DOM.

The two paddings count the rows that are not on the page:
1. **The top padding** is as tall as the orders before the visible ones: `first` orders of 30 pixels each.
2. **The bottom padding** is as tall as the orders after them: `orders.length - first - 20` orders of 30 pixels each.

No line of our code writes the total height. It is the top padding, plus twenty rows, plus the bottom padding, and it always adds up to 300,000 pixels, the height of 10,000 rows.

### Mistake: Rows Taller Than the Arithmetic

The arithmetic works only while every row is exactly the height the code uses. Here is how that breaks:
1. The developer gives every row `height: 30` in the code.
2. A CSS file of the shop adds `padding: 5px 0` to every `<li>`, so each row is now 40 pixels tall, while the code still counts 30.
3. The owner scrolls. Each time an order leaves the top, `first` grows by one: the code takes away a row of 40 pixels and adds only 30 pixels of top padding in its place.
4. The rows jump up by 10 pixels each time an order leaves the top, and the scroll stutters.

So every row must be exactly the height the arithmetic uses. Rows of different heights, such as chat messages, need much more work: each row must be measured after it renders, and the rows not yet rendered need an estimated height. Libraries do that work. React's documentation does not describe it.

## PRINCIPLE | `start` and `end` with five extra rows: the rows next to the visible part already exist

> [!PRINCIPLE]
> **Principle 5: Five Extra Rows Fill the Edges**
>
> *Render a few rows more than the scroll container shows, five above and five below, so the rows next to the visible ones already exist when the scroll stops between two rows or moves quickly.*
>
> A scroll that stops between two rows shows part of a twenty-first row, and a fast scroll moves the content before React renders the next rows. With exactly twenty rows, both show blank padding at the edge. Five extra rows on each side cover both cases, at the cost of about ten more DOM elements.
>
> **DO THIS:**
> ```jsx
> const start = Math.max(0, first - extraRows);
> const end = Math.min(orders.length, first + 20 + extraRows);
> const rows = ~orders.slice(start, end)~; // About thirty rows: the edges are always filled
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const rows = ~orders.slice(first, first + 20)~; // **WRONG:** between two rows, the bottom edge shows blank padding
> ```

### A Blank Strip at the Bottom Edge

**Beware! With exactly twenty rows, the owner can see blank space where orders should be.** It happens in two ways.

The first way happens every time the scroll stops between two rows:
1. The owner scrolls down by 3015 pixels.
2. `first` is `Math.floor(3015 / 30)`, which is still `100`. So the list renders `Order #101` to `Order #120`, from 3000 pixels down.
3. The scroll container now shows the content from 3015 to 3615 pixels: the lower half of `Order #101` at the top, and the space of a twenty-first row at the bottom.
4. The rendered rows end at 3600 pixels. `Order #121` is not in the slice, so the last 15 pixels show the empty bottom padding.

```page caption="The bottom of the scroll container at a scroll of 3015 pixels, with exactly twenty rows: a blank strip where Order #121 belongs."
line: Order #118
line: Order #119
line: Order #120
empty: blank strip where Order #121 belongs
```

The second way happens when the owner drags the scrollbar quickly. The browser moves the content at once, and our handler and React's render come after it. For that moment, the edge can show the empty padding instead of orders, until React renders the new rows.

### Two Numbers for `slice`: `start` and `end`

The fix is a few rows more than the scroll container shows, above and below:

```jsx title="Five extra rows above and five below the visible rows"
const extraRows = 5;
const start = ~Math.max(0, first - extraRows)~; // Five rows before the visible ones, but never before the first order
const end = ~Math.min(orders.length, first + 20 + extraRows)~; // Five rows after them, but never past the last order

<ul style={{ margin: 0, paddingTop: start * 30, paddingBottom: (orders.length - end) * 30 }}>
  {orders.slice(start, end).map(order => (
    <li key={order.id} style={{ height: 30 }}>Order #{order.id}</li>
  ))}
</ul>
```

`start` and `end` are the two positions `slice()` takes: the first order it keeps, and the first order it leaves out. Our code calculates both from `first` on every render:
1. **`Math.max(0, ...)`** returns the larger of two numbers. At the top of the list, `first - 5` is below `0`, so `start` stays `0`.
2. **`Math.min(orders.length, ...)`** returns the smaller of two numbers. At the bottom, `end` stays `10000`.

The paddings now count from `start` and `end`, so the total height is still 300,000 pixels. At the top, the list holds twenty-five rows: twenty visible and five below. In the middle, it holds thirty: five above, twenty visible, and five below.

At a scroll of 3015 pixels, the list now holds `Order #96` to `Order #125`, so the twenty-first row is there. A small or quick scroll shows orders, not padding. A very fast drag across thousands of rows can still outrun five rows.

The React team describes this exact habit on the react.dev blog: virtualized lists "prerender more rows than are currently visible", and they "can prerender additional rows above and below the visible window."

### VS | Exactly Twenty Rows vs. Five Extra Rows on Each Side: the same screen at rest, different edges in motion

**It may look the same, but it is NOT the same thing!** Both versions show the same twenty orders while the scroll stands still on a row. Only the version with extra rows has rows ready outside the visible part:

```tree caption="Exactly twenty rows vs. five extra rows on each side: the same list at rest, different edges when the scroll moves."
Two ways to choose the rows to render
- !Exactly the visible rows [`first` to `first + 20`] | **Twenty rows**, the same as the screen shows at rest | Between two rows or in a fast scroll, the edge shows **blank padding**
- +Five extra rows on each side [`start` to `end`] | **About thirty rows**, twenty of them visible | The rows next to the visible ones **already exist** when the scroll moves
```

More extra rows mean fewer gaps, but also more DOM elements and more work on every render. The number is a trade, and five is a small, common choice. Each library has its own option name for it.

Here is how a gap reaches the owner:

2. Every row appears in time, and the developer never notices the strip at the bottom edge.
3. The owner drags the scrollbar quickly on an older laptop, and blank space flashes at the edge.

## PRINCIPLE | `selectedIds` in the list: a tick survives when its row scrolls away

> [!PRINCIPLE]
> **Principle 6: A Tick Lives in the List, Not in the Row**
>
> *A row that leaves the visible part is removed from the DOM, and React destroys what it held; anything the user sets on a row, such as a tick, must live in the list's state, keyed by the order's ID.*
>
> In a virtualized list, the order stays in the data while its row comes and goes. A tick that the browser keeps inside the row's checkbox is destroyed with the row, and the new checkbox that appears on the way back is empty. A tick kept in `selectedIds`, in the state of `OrderList`, survives every scroll, because each new checkbox reads it from state.
>
> **DO THIS:**
> ```jsx
> <input type="checkbox" ~checked={selectedIds.includes(order.id)}~ onChange={() => toggle(order.id)} /> {/* The tick lives in OrderList: it survives the scroll */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~<input type="checkbox" />~ {/* **WRONG:** the tick lives in the DOM element, so it is gone after the row scrolls away */}
> ```

### A Checkbox the Browser Keeps

The owner wants to print shipping labels for some orders, so each row gets a checkbox. The smallest version lets the browser keep the tick:

```jsx title="A checkbox that the browser keeps inside each row"
<li key={order.id} style={{ height: 30 }}>
  ~<input type="checkbox" />~ {/* No checked prop: the browser keeps the tick inside this DOM element */}
  Order #{order.id}
</li>
```

This checkbox has no `checked` prop, so the browser keeps the tick inside the `<input>` element itself (Lesson 20). That works in a list that renders every order, because every row stays on the page. In a virtualized list, a row exists only while it is near the visible part.

1. The owner ticks `Order #3`. The browser keeps the tick inside that row's `<input>` element.
2. The owner scrolls down until `Order #101` is at the top. With five extra rows, `start` is `95`, so `Order #3` is no longer in `slice(start, end)`.
3. React removes the `<li>` of `Order #3` from the DOM, and the tick goes with its `<input>`.
4. The owner scrolls back to the top, and `Order #3` is in the slice again.
5. React creates a brand-new `<li>` with a brand-new checkbox, and the checkbox is empty.

### Each Habit, and the Rule That Replaces It

| Aspect | The habit that breaks the page | The rule of a virtualized list |
| :--- | :--- | :--- |
| **The rows** | `orders.map` over 10,000 orders, with trust in `overflow` to make the hidden rows cheap | Render only the visible rows with `slice()` |
| **The scroll position** | `onScroll` on the `<ul>`, which never scrolls | `onScroll` on the `<div>` with `overflowY: 'auto'`, which copies `e.currentTarget.scrollTop` into state |
| **The scrollbar** | `slice()` alone, which leaves 600 pixels of content and no scrollbar | A top and a bottom padding as tall as the rows not on the page |
| **The edges** | Exactly twenty rows, which leave blank strips between two rows and in a fast scroll | Five extra rows above and below the visible ones |
| **What a row holds** | A tick kept by the browser inside the row, destroyed with the row | Ticks kept in `selectedIds` in the list, keyed by `order.id` |

Remember the one sentence of this lesson: **the number of items in your data and the number of elements on the page are two separate numbers.** A virtualized list keeps about thirty rows on the page, for 10,000 orders or for a million.

## For the Interview

> **The Interview Question:** How do you render a list of ten thousand items without rendering ten thousand rows?

### How to Answer Clearly in 30 Seconds

"The number of items in the data and the number of DOM elements are two separate numbers. If we map 10,000 items, React creates 10,000 DOM elements, even when the scroll container shows only twenty. `overflow` only clips them, and a large DOM slows style calculation and layout and uses more memory. So we virtualize the list, which is also called windowing:
1. **Read the scroll position:** an `onScroll` handler on the scroll container copies `scrollTop` into state, and the first visible row is `scrollTop` divided by the row height.
2. **Render only the visible rows:** `slice()` takes them, plus a few extra above and below, so a fast scroll does not show blank space.
3. **Keep the full height:** padding as tall as the rows not on the page keeps the scrollbar matched to the whole list.

The DOM then stays at about thirty rows, for ten thousand items or for a million. React itself has no built-in virtualized list, so in production we use a library, such as `react-window`, which Chrome's Lighthouse names. And we measure first, with CPU Throttling and a production build."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why not wrap the rows in `memo` or the list in `useMemo` instead?"**
   Because neither one reduces the number of DOM elements. `memo` and `useMemo` skip work on later renders, and React's documentation says "`useMemo` won't make the *first* render faster." The first load still creates 10,000 elements. The same holds for `useDeferredValue` and `useTransition`: they keep typing responsive while a long list renders, but React's documentation says of `useDeferredValue` that it "does not make re-rendering of the `SlowList` faster." Only fewer rows make the DOM smaller.
2. **"What happens to state inside a row that scrolls out of view?"**
   It is destroyed. When the row leaves the slice, React removes it from the DOM, and everything it held goes with it: a tick the browser kept, text typed into an `<input>`, the focus, an open menu. When the row comes back, React creates a brand-new one. So anything the user sets on a row lives in the list's state, keyed by the item's ID, such as `selectedIds` in the parent. The key must come from the data, `key={order.id}`. With the position inside the slice as the key, every scroll would give what one row holds to another item.
3. **"How do you jump to item 5,000, and what changes when the rows have different heights?"**
   To jump, we cannot call `scrollIntoView()` on the row (Lesson 31), because no row exists for item 5,000 until the visible part reaches it. Instead, we set the `scrollTop` of the scroll container to `4999 * 30` through a ref, and the list renders the right rows from there. Rows of different heights, such as chat messages, break the simple division. Each row must be measured after it renders and before the browser paints, which is what `useLayoutEffect` allows (Lesson 49), and the rows not yet rendered need an estimated height. React's documentation does not describe this. Libraries do the measuring for us.

- !Every item mapped [`items.map`] | Twenty rows on screen | The DOM holds **10,000 elements**: slow to appear, heavy in memory
- !Slice alone [`slice` from `first` to `first + 20`] | Twenty rows fill the scroll container exactly | **No scrollbar**: the user is stuck on the first twenty
- +Virtualized list [`slice` from `start` to `end`, two paddings] | About thirty rows, five extra on each side | The scrollbar matches **all 10,000 items**; row data lives **in the parent's state**
