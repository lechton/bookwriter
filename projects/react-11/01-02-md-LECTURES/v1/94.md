# Lecture 94: How One Shared Button Becomes a Link Without Losing Its Types

*(How can one Button component become a button on one tag and a link on another, and still check every attribute?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How do you build polymorphic components with the as prop in TypeScript?

---

## VS | One props type for both tags vs. `ComponentPropsWithoutRef<E>`: both render the same tags, only `E` refuses `disabled` on a link

> In HTML, a `<button>` does something on this page, and an `<a>` takes the user to another page, yet a store often wants both to look the same. **A polymorphic component lets the page choose its tag with one prop, usually named `as`, so `<Button as="a">` becomes a link.** Type the tag as a type parameter, and TypeScript accepts only that tag's attributes, so it refuses `disabled` on a link, which the browser would silently ignore.

Start with plain HTML. A cart page has two controls side by side:
1. **Clear cart** empties the cart, right here on this page. That is an action, so it is a `<button>`.
2. **Checkout** takes the user to the checkout page. That is a destination, so it is an `<a>` with an `href`.

MDN is strict about this: "you should only use a hyperlink for navigation to a real URL", and for an action, "Use a `<button>` instead."

But the designer wants both controls to look like the same filled button. In Lesson 90, we built a shared `Button` component for exactly that job: it puts the same CSS class on every button of the site. The problem is that it always returns a `<button>`. So how does Checkout get that look on an `<a>`?

The answer is one extra prop, `as`:

```tsx title="One shared Button, two tags"
<Button onClick={() => setCount(0)}>Clear cart</Button> {/* No as: React creates a <button>, and the click empties the cart */}
<Button ~as="a"~ href="/checkout">Checkout</Button> {/* as="a": React creates an <a>, and the click opens /checkout */}
```

One component, two different elements in the browser: a real `<button>` for Clear cart, and a real `<a>` for Checkout. The prop `as` decides which. Both look the same, because `Button` puts the same class on whatever tag it creates.

### The trick you already know from plain JavaScript

How can one component create different tags? Remember `document.createElement`? It takes the tag name as a string, and a string can sit in a variable:

```js title="Plain JavaScript: the tag name is a string in a variable"
const tag = 'a';
const link = ~document.createElement(tag)~; // Creates an <a>, because tag holds 'a'
```

React works the same way. You never call `createElement` yourself, but every JSX tag becomes a call to React's own `createElement`, with the tag name as a string (Lesson 76). So if the tag name sits in a variable, React creates whatever tag that variable names.

That is all a polymorphic component does in the browser. It reads the tag name from the `as` prop, and it hands that name to React.

> [!DEFINITION]
> **What is a polymorphic component?** [NEW] A polymorphic component is a component whose outer tag is chosen by the page that uses it, usually with a prop named `as`. The word comes from computer science and means "many forms": our `Button` keeps one look and one set of props, and it becomes a `<button>` on one tag and an `<a>` on another. The name `as` is a habit, not a React feature: React never reads it, our component does, as it reads any prop (Lesson 94).

> [!DEFINITION]
> **What is a type parameter?** [REVIEW] A type parameter is a name for a type, written in angle brackets, such as `T` in `function DataTable<T>`. It works like a function parameter, but for types: TypeScript fills it in at each place the component is used, usually from the props that place passes (Lesson 93).

> [!DEFINITION]
> **What are rest props?** [REVIEW] In `function Button({ variant, ...rest })`, the three dots collect every prop the component does not name into one object, `rest`. Then `{...rest}` on a tag writes all of them onto that tag, so an `onClick` or an `href` from the page reaches the real element (Lesson 90).

### The same Checkout tag under two props types

Now the cart is empty, and a developer wants Checkout to stop working. They add `disabled` to the Checkout tag:

```tsx title="The Checkout link with disabled"
<Button as="a" href="/checkout" ~disabled={count === 0}~>Checkout</Button> {/* One props type accepts this line, the other refuses it */}
```

Whether TypeScript accepts this line depends on how the props of `Button` are typed. There are two common ways:
1. **One props type for both tags.** Every tag accepts the attributes of `<a>` and the attributes of `<button>`. The editor says nothing.
2. **A polymorphic props type.** Each tag accepts only the attributes of the tag that `as` names. A link has no `disabled`, so the editor underlines it.

The editor's message ends like this:

```text title="The editor's message under the polymorphic props type"
Property 'disabled' does not exist on type ...
```

**It may look the same, but it is NOT the same thing!** Both types accept Clear cart and Checkout. Both put the exact same tags in the browser, because TypeScript removes every type before the code runs (Lesson 90). Only the polymorphic type knows that a link has no `disabled`.

```tree caption="Two props types for one shared Button: both render the same tags, but only one refuses disabled on the link."
Two ways to type one shared `Button`
- !One props type for both tags [`as?: 'a' | 'button'`] | Every tag accepts **the attributes of both tags** | `disabled` on the link **passes with no error**
- +A polymorphic props type [`as?: E`] | Each tag accepts **only the attributes of the tag `as` names** | `disabled` on the link is **refused before the code runs**
```

### What goes wrong: the user checks out an empty cart

**Beware! With one props type for both tags, the user can check out an empty cart, and nothing warns anyone.** Here is how it happens:
1. The shared `Button` is typed with one props type for both tags.
2. A developer writes `disabled={count === 0}` on the Checkout link.
3. The editor says nothing.
4. The user clicks Clear cart, and the line reads `Cart: 0 items`.
5. The user clicks Checkout. The browser leaves the cart page for the checkout page, with an empty cart.

Why? Because the browser ignores `disabled` on a link. MDN says: "If the element doesn't support the disabled attribute, the attribute will have no effect."

Only seven elements support it: button, fieldset, optgroup, option, select, textarea, and input. The `<a>` element is not on that list.

So the link does not even turn grey. MDN adds that the `:disabled` selector matches only an element that supports the attribute. A style the store writes for disabled controls never reaches the link.

### The Rule of Thumb: `as` decides the tag and its attributes

**`as` decides two things at once: which tag React creates in the browser, and which attributes TypeScript accepts on that tag.** The first part is plain JavaScript and React. The second part is a type parameter that TypeScript fills in from `as`.

A senior developer also knows the five classic mistakes:
1. **Thinking `as` is a React feature.** React never reads `as`. Our component reads it, like any other prop.
2. **Writing the prop itself as the tag, `<as>`.** React then creates an element named `as`, which the browser shows as plain text.
3. **One props type with the attributes of both tags.** Then `disabled` passes on a link, and `href` passes on a button.
4. **A type parameter with no default.** Then a `Button` with no `as` accepts any prop at all.
5. **Mixing up the `as` prop with TypeScript's `as` keyword.** The keyword is a type assertion, and it has nothing to do with our prop (Lesson 93).

At work, developers choose between four ways to give a button and a link the same look. Only the last two fit real work well, and each fits its own case:

```tree caption="Four ways to give a button and a link the same look, and when each one fits."
Four ways to make one look serve a button and a link
- +Two components [`Button` `LinkButton`] | Fits **one or two links** | Every change to the look is **made twice**
- !One props type for both tags [`as?: 'a' | 'button'`] | Fits **no case well** | `disabled` on a link and `href` on a button **both pass**
- +An `as` prop with a type parameter [`as?: E`] | Fits **several tags or a router Link** | Each tag gets **only its own attributes**
- +A union chosen by `href` [`href: string`] | Fits **exactly two forms** | A link when `href` is passed, **a button otherwise**
```

Even the react.dev site goes further than the second way in its own code. It types its `Heading` component with `as?: any`, so its tag is not checked at all.

The rest of the lesson builds the third way, then the fourth, on one real page.

**PRINCIPLES:** `as` decides which tag React creates, and the type parameter decides which attributes that tag accepts. Three principles follow:
1. **Principle 1: `Component` with a capital C creates the tag that `as` names.** `Button` copies `as` into a capitalized variable and writes that variable as the tag.
2. **Principle 2: `ComponentPropsWithoutRef<E>` gives each tag only its own attributes.** TypeScript fills in the tag from `as` at each tag, so a link accepts `href` and refuses `disabled`.
3. **Principle 3: a union chosen by `href` needs no `as` at all.** When there are exactly two forms, `href` alone picks the link.

## PRINCIPLE | `const Component = as ?? 'button'`: React creates the tag that `as` names

> [!PRINCIPLE]
> **Principle 1: The `as` Prop: `Component` with a Capital C Creates the Tag That `as` Names**
>
> *Read the tag name from a prop such as `as`, keep it in a variable that starts with a capital letter, and write that variable as the JSX tag.*
>
> React never reads `as`. Our component reads it, like any prop, and copies it into a variable such as `Component`. JSX reads a capitalized name as a JavaScript value, so `<Component>` becomes `createElement('a', ...)` when `Component` holds `'a'`. A lowercase `<as>` is read as a tag name, so React creates an element named `as`, and the browser shows it as plain text.
>
> **DO THIS:**
> ```jsx
> function Button({ as, ...rest }) {
>   const ~Component~ = as ?? 'button'; // Capital C: React creates the tag that as names
>   return <Component {...rest} />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Button({ as, ...rest }) {
>   return <~as~ {...rest} />; // **WRONG:** lowercase as is a tag name, so React creates an element named as
> }
> ```

Leave the types aside for a moment. The part that runs in the browser is plain JavaScript and React.

### A variable written as a tag

Here is a variable that holds the string `'a'`, written as a tag, next to a plain `<a>`:

```jsx title="A variable that holds 'a', written as a tag, and a plain <a>"
const Component = 'a';

<~Component~ href="/checkout">Checkout</Component> {/* Component holds 'a': React creates an <a> */}
<~a~ href="/checkout">Checkout</a> {/* The same <a> */}
```

Yes, it is the exact same thing! Both lines become `createElement('a', ...)` (Lesson 76).

Why does this work? JSX looks at the first letter of the tag:
- **A capital letter**, such as `Component`, means "read this JavaScript value". Here the value is the string `'a'`.
- **A lowercase letter**, such as `a`, means "this is the tag name itself".

When React gets a string as the tag, it creates the built-in tag of that name. It is `document.createElement(tag)` again, done by React.

### Reading the tag name from the `as` prop

Now the string comes from a prop. The page writes `as="a"`, and `Button` copies it into its own capitalized variable:

```jsx title="Button reads the tag name from as"
function Button({ ~as~, ...rest }) { // as is a prop like any other: Button reads it, React never does
  const ~Component~ = as ?? 'button'; // 'a' when the page writes as="a", 'button' when it writes no as
  return <Component {...rest} />;
}
```

The return line names no `<a>` and no `<button>`. Checkout still becomes a link, because the value of `as` travels into `Component` in three steps:
1. The page writes `as="a"` on the Checkout tag. React passes `Button` one props object, and in it, `as` is `'a'`.
2. `Button` copies that value into `Component`. Clear cart writes no `as`, so there the prop is `undefined`, and `??` puts `'button'` in its place (Lesson 33).
3. JSX turns `<Component ...>` into a call to React's `createElement`, which here creates an `<a>`.

And the `href`? It travels inside `rest`, and `{...rest}` writes it on the `<a>` (Lesson 90).

The name `as` is a habit, not a React feature. The react.dev site uses the same name in its own code, for a `Heading` component that its pages write as `as="h1"`.

### Why the variable must start with a capital letter

It is tempting to skip the variable and write the prop itself as the tag:

```jsx title="The prop itself written as the tag"
function Button({ as, ...rest }) {
  return <~as~ {...rest} />; // **WRONG:** a lowercase name is a tag name, so React creates an element named as
}
```

The prop holds `'a'`, so it is natural to expect a link. **Instead, the page shows Clear cart and Checkout as plain text, and a click on Checkout opens nothing.** Here is why:
1. In a TypeScript file, the editor refuses the line, because `as` is not on React's list of built-in tags, `JSX.IntrinsicElements`.
2. In a plain `.jsx` file, nothing stops the line. JSX reads a lowercase name as a tag name, never as a variable (Lesson 04). So the line becomes `createElement('as', ...)`, whatever the prop holds.
3. React creates an element named `as` for each of the two tags. The browser has no such tag, so it shows only the text inside, run together on one line, with no look of a button.
4. The user clicks `Checkout`, and nothing opens. An `<as>` element is not a link, even with an `href` on it.
5. React prints a warning in the Console.

```page width=full caption="The cart page when Button writes <as> as the tag: both controls are plain text, and React warns in the Console."
line: Cart: 2 items
line: Clear cartCheckout | bad
console: The tag <as> is unrecognized in this browser. If you meant to render a React component, start its name with an uppercase letter.
```

Remember: lowercase is a tag name, capital is a variable. That is why the variable is called `Component`, with a capital C.

### VS | The `as` prop vs. TypeScript's `as` keyword: the same word, two different things

TypeScript has its own word `as`, and it has nothing to do with our prop:

```tsx title="The as prop, and TypeScript's as keyword"
<Button ~as="a"~ href="/checkout">Checkout</Button> {/* A prop: Button reads its value in the browser */}
const user = data ~as User~; // A type assertion: only the editor reads it, and it is removed before the code runs
```

They share a name, but they are NOT the same thing:
- **The `as` prop** is a name our code chose. `Button` reads its value while it renders, in the browser.
- **The `as` keyword** is a type assertion: "trust me, this is a `User`" (Lesson 93). It never reaches the browser.

### Our cart page, step 1

The button file starts from our shared `Button` of Lesson 90, with its `variant` prop and its rest props. It gains the `as` prop and the capitalized variable:

```tsx title="src/Button.tsx"
import type { ComponentPropsWithoutRef } from 'react';

type ButtonProps = {
  ~as?: 'a' | 'button'~; // The page names the tag, or writes nothing
  variant?: 'primary' | 'secondary';
} & ComponentPropsWithoutRef<'button'> & ComponentPropsWithoutRef<'a'>; // The attributes of both tags, on every tag

export default function Button({ as, variant = 'primary', ...rest }: ButtonProps) {
  const ~Component~ = as ?? 'button'; // No as on the tag: a <button>
  return <Component className={variant} {...rest} />;
}
```

Three pieces of this type are new:
- **`import type`** brings in a type only. TypeScript removes the whole line before the code runs.
- **`ComponentPropsWithoutRef<'button'>`** comes from React's types. It is the list of every attribute of `<button>`, the same list as in Lesson 90, without `ref`.
- **`&`** joins types: the props must fit every type it joins. TypeScript calls this an **intersection type**.

So this type gives every tag the attributes of both tags. That looks generous. Principle 2 shows what it costs.

The page holds the number of items in state and writes the two tags:

```tsx title="src/App.tsx"
import { useState } from 'react';
import Button from './Button';

export default function App() {
  const [count, setCount] = useState(2);

  return (
    <>
      <p>Cart: {count} items</p>
      <Button variant="secondary" onClick={() => setCount(0)}>Clear cart</Button>
      <Button ~as="a"~ href="/checkout">Checkout</Button> {/* React creates an <a> with the primary class */}
    </>
  );
}
```

When the page opens, it shows two items, Clear cart, and Checkout:

### The mistake `as` prevents: two fake controls

Without the `as` prop, a store's shared button component renders only `<button>`. A developer who needs both controls in the same look then fakes one control with the other tag:

```tsx title="Two fake controls"
<~button~ onClick={() => { window.location.href = '/checkout'; }}>Checkout</button> {/* **WRONG:** a button that acts as a link */}
<~a href="#"~ onClick={() => setCount(0)}>Clear cart</a> {/* **WRONG:** a link that acts as a button */}
```

Each fake breaks something the user does every day:
1. **The button that acts as a link** has no address. The user cannot open Checkout in a new tab, and cannot bookmark it.
2. **The link that acts as a button** is the one MDN warns about. Anchor elements "are often abused as fake buttons by setting their `href` to `#`".

MDN lists what such links break: they "cause unexpected behavior when copying/dragging links, opening links in a new tab/window, bookmarking". They also "convey incorrect semantics to assistive technologies, like screen readers." The user opens Clear cart in a new tab and gets a second copy of the cart page, with the items still in it.

With the `as` prop, each control gets the tag it really is, and both keep the same look.

## PRINCIPLE | `ComponentPropsWithoutRef<E>`: each tag accepts only the attributes of the tag `as` names

> [!PRINCIPLE]
> **Principle 2: Polymorphic Props: `ComponentPropsWithoutRef<E>` Gives `as="a"` the Attributes of `<a>`**
>
> *Make the tag a type parameter, `E extends ElementType = 'button'`, type the prop as `as?: E`, and take the attributes from `ComponentPropsWithoutRef<E>`.*
>
> One props type for both tags accepts `disabled` on a link. The browser ignores it there, so the user checks out an empty cart. With `E`, TypeScript fills in the tag from `as` at each tag, so a link accepts `href` and refuses `disabled`. The default `= 'button'` gives a `Button` with no `as` the attributes of `<button>`. Without the default, such a `Button` accepts any prop.
>
> **DO THIS:**
> ```tsx
> type ButtonProps<E extends ElementType> = { as?: E } & ComponentPropsWithoutRef<E>;
>
> export default function Button<E extends ElementType ~= 'button'~>({ as, ...rest }: ButtonProps<E>) { // Each tag gets only its own attributes
>   const Component = as ?? 'button';
>   return <Component {...rest} />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> type ButtonProps = { as?: 'a' | 'button' } & ~ComponentPropsWithoutRef<'button'> & ComponentPropsWithoutRef<'a'>~; // **WRONG:** every tag accepts both lists, so disabled passes on a link
> ```

The cart is empty, and the developer writes `disabled={count === 0}` on the Checkout link. With the type of step 1, the editor says nothing.

Why? That type gives every tag the attributes of both tags, and `disabled` is an attribute of `<button>`. But at each tag, our `Button` is one element, never both. So at each tag, its type must accept the attributes of that one element only.

### VS | One props type for both tags vs. one props type per tag: the same tags, only the second refuses `disabled` on a link

Here are the two props types side by side, with `variant` left out:

```tsx title="One props type for both tags"
type ButtonProps = { as?: 'a' | 'button' } & ComponentPropsWithoutRef<'button'> & ComponentPropsWithoutRef<'a'>; // Every tag accepts href and disabled
```

```tsx title="One props type per tag, filled in from as"
type ButtonProps<~E extends ElementType~> = { ~as?: E~ } & ComponentPropsWithoutRef<E>; // Each tag accepts only the attributes of the tag as names
```

The second type has three new pieces:
- **`E`** is a type parameter (Lesson 93). It is a name for a type, filled in again at each tag.
- **`ElementType`** comes from React's types. It is every value `as` may hold: every built-in tag name, such as `'a'`, and every component. `E extends ElementType` is the constraint: `E` must be one of them.
- **`ComponentPropsWithoutRef<E>`** is the list of attributes of whatever `E` is, without `ref`. When `E` is `'a'`, it is the attributes of a link.

So where do the attributes of `<a>` come from on `<Button as="a">`? From `as` itself, in four steps:
1. The page writes `as="a"`.
2. The prop `as` is typed `E`, so TypeScript fills in `E` as the string `'a'`, for this tag only.
3. Now `ComponentPropsWithoutRef<E>` is the attribute list of a link, without `ref`.
4. `href` is in that entry. `disabled` is not.

**It may look the same, but it is NOT the same thing!** Both types render the exact same tags. But the second type refuses `disabled` on a link, and it refuses `href` on a plain button. The attributes now follow the value of `as`, just as the tag in the browser does.

```tree caption="How TypeScript gives Button as a the attributes of a link: as fills in E, and E picks the attributes."
How `<Button as="a">` gets the attributes of `<a>`
- +1. The page writes `as="a"` [`as?: E`] | TypeScript fills **`E` with `'a'`** for this tag only
- +2. `E` picks the attributes [`ComponentPropsWithoutRef<E>`] | The tag accepts **the attributes of `<a>`**
- +3. The editor reads the tag [`href` `disabled`] | `href` **passes** | `disabled` is **refused**
```

Remember: `as` picks the tag in the browser, and the same `as` picks the attributes in the editor.

### `= 'button'`: the type for a `Button` with no `as`

Clear cart writes no `as`, so nothing fills in `E` there. **Without a default for `E`, a plain `Button` accepts any prop at all:**

```tsx title="A type parameter with no default"
export default function Button<~E extends ElementType~>({ as, variant = 'primary', ...rest }: ButtonProps<E>) { // **WRONG:** no default for E
  const Component = as ?? 'button';
  return <Component className={variant} {...rest} />;
}
```

```tsx title="A Button with no as, under the type with no default"
<Button onClick={() => setCount(0)}>Clear cart</Button> {/* Passes */}
<Button href="/checkout" ~foo="bar"~>Checkout</Button> {/* Passes too: no error for href, and none for foo */}
```

Here is why the second tag passes:
1. The tag writes no `as`, so nothing fills in `E`.
2. With no default, `E` falls back to its constraint, `ElementType`. That stands for every tag and every component at once.
3. The attributes of "any tag or any component" are not a fixed list, so the editor stops checking them.

The fix is a **default type argument**: the type that `E` gets when nothing fills it in. Write `= 'button'` after the constraint:

```tsx title="A type parameter with the default 'button'"
export default function Button<E extends ElementType ~= 'button'~>({ as, variant = 'primary', ...rest }: ButtonProps<E>) { // No as on the tag: E is 'button'
  const Component = as ?? 'button';
  return <Component className={variant} {...rest} />;
}
```

Now Clear cart still passes, and the tag with `href` and `foo` is refused:

```text title="The editor's message under the default 'button'"
Property 'href' does not exist on type ...
```

The rest of the message names the attributes of `<button>`. A plain `Button` is a button again, for the editor too.

### VS | `as ?? 'button'` in the body vs. a default in the parameter list: the same tag, only the body passes the editor

The react.dev site's `Heading` writes its default tag in the parameter list, as `as: Comp = 'div'`. That passes there only because its `as` is typed `any`. With our type, the same form is refused:

```tsx title="The default tag in the parameter list"
export default function Button<E extends ElementType = 'button'>({ ~as: Component = 'button'~, variant = 'primary', ...rest }: ButtonProps<E>) { // **WRONG:** Type '"button"' is not assignable to type 'E'.
  return <Component className={variant} {...rest} />;
}
```

```tsx title="The default tag in the body"
const ~Component~ = as ?? 'button'; // Passes: the same tag in the browser
```

In the browser, yes, it is the exact same thing. For the editor, it is NOT the same thing. Here is why:
1. The default `= 'button'` decides `E` only at a tag where the page writes no `as`.
2. Inside `Button`, the code must work for every possible `E`, and at the Checkout tag, it is `'a'`.
3. So a default value of `'button'` for a prop typed `E` could put a button where a link belongs. TypeScript refuses it.

The second line of the message says exactly that:

```text title="The second line of the editor's message"
'"button"' is assignable to the constraint of type 'E', but 'E' could be instantiated with a different subtype of constraint 'ElementType'.
```

The line in the body has no such problem. There, `Component` is a new variable that simply holds whichever of the two values it gets.

### The event follows `as` too

The event in a handler follows the tag too (Lesson 91). On a link, `e.currentTarget` is the link element, so it has an `href`. On a plain `Button`, it is a button, which has none:

```tsx title="e.currentTarget on a link and on a button"
<Button as="a" href="/checkout" onClick={e => ~e.currentTarget.href~}>Checkout</Button> {/* Passes: currentTarget is the <a> */}
<Button onClick={e => ~e.currentTarget.href~}>Clear cart</Button> {/* **WRONG:** Property 'href' does not exist on type 'EventTarget & HTMLButtonElement'. */}
```

A misspelled tag is caught as well, with a suggestion:

```tsx title="A misspelled tag in as"
<Button ~as="buton"~>Clear cart</Button> {/* **WRONG:** Type '"buton"' is not assignable to type 'ElementType | undefined'. Did you mean '"button"'? */}
```

The editor's autocomplete follows `as` in the same way. On a link, it suggests `href` and `target`.

### Our cart page, step 2

`Button.tsx` changes only its types. The body stays the same:

```tsx title="src/Button.tsx"
import type { ComponentPropsWithoutRef, ElementType } from 'react';

type ButtonProps<E extends ElementType> = {
  ~as?: E~; // The page names the tag, and TypeScript fills in E from it
  variant?: 'primary' | 'secondary';
} & ComponentPropsWithoutRef<E>; // Only the attributes of the tag that as names

export default function Button<E extends ElementType ~= 'button'~>({ as, variant = 'primary', ...rest }: ButtonProps<E>) { // No as on the tag: the attributes of <button>
  const Component = as ?? 'button';
  return <Component className={variant} {...rest} />;
}
```

`App.tsx` can no longer write `disabled` on the link. So Checkout gets two forms: a link while the cart has items, and a disabled button once it is empty:

```tsx title="src/App.tsx" startLine="11"
      {count > 0
        ? <Button as="a" href="/checkout">Checkout</Button>
        : <Button ~disabled~>Checkout</Button>} {/* The empty cart gets a real <button>, which supports disabled */}
```

The types are removed before the code runs, so they change nothing in the browser. When the page opens, the line reads `Cart: 2 items`, and Checkout is the link, as in step 1. The user clicks Clear cart, and Checkout turns into a disabled button:

```page caption="The page of step 2 after the user clicks Clear cart: Checkout is now a disabled button."
line: Cart: 0 items
form:
  button: Clear cart
  button: Checkout | | disabled
console: quiet
```

```dom caption="The Elements panel after the user clicks Clear cart: Checkout is a disabled button with the primary class."
<div id="root">
  <p>Cart: 0 items</p>
  <button class="secondary">Clear cart</button>
+ <button class="primary" disabled="">Checkout</button> | note: Button with no as and disabled
</div>
```

The user clicks the disabled Checkout, and nothing happens. MDN says disabled controls "won't receive focus or any browsing events, like mouse clicks".

### How one props type for both tags usually starts

The type of step 1 usually starts as a quick way to grow the shared `Button` of Lesson 90. The developer adds two fields, `as` and `href`, to the attributes of a button:

```tsx title="src/Button.tsx"
interface ButtonProps extends ~ComponentPropsWithoutRef<'button'>~ { // Only the attributes of <button>, plus two fields
  as?: 'a' | 'button';
  href?: string;
  variant?: 'primary' | 'secondary';
}
```

Then the editor refuses the component's own return line, the one that writes `Component` as the tag. Its long message holds this line:

```text title="One line of the editor's message"
Types of property 'onCopy' are incompatible.
```

The reason: a handler typed for a button is not a handler typed for a link.

To make the error go away, the developer joins the attributes of both tags with `&`, as in step 1, or writes `as any`. The error is gone, and so is every check that tells the two tags apart. A teammate writes `disabled` on the Checkout link, the editor says nothing, and the user checks out an empty cart.

## PRINCIPLE | `href: string` in a union: a link when `href` is passed, a button otherwise

> [!PRINCIPLE]
> **Principle 3: Union Props: `href` Alone Picks the `<a>` Form of the Union**
>
> *When a component has exactly two forms, type its props as a union of an `<a>` form with `href: string` and a `<button>` form with `href?: undefined`, and check `rest.href !== undefined` inside.*
>
> A plain `Button` that always renders `<button>` puts `href` on a button, and the user's click goes nowhere. With the union, a string `href` fits only the `<a>` form, so the page writes no `as`, and TypeScript checks every other attribute against that form. That is why `disabled` next to `href` is refused.
>
> **DO THIS:**
> ```tsx
> export default function Button({ variant = 'primary', ...rest }: ButtonProps) {
>   if (~rest.href !== undefined~) { // rest is the <a> form here
>     return <a className={variant} {...rest} />;
>   }
>   return <button className={variant} {...rest} />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function Button({ variant = 'primary', ...rest }) {
>   return <~button~ className={variant} {...rest} />; // **WRONG:** href lands on a button, and the click goes nowhere
> }
> ```

The interview question often comes in this exact shape: "render as a button by default, but as an anchor link when href is passed". That needs no `as` at all.

### VS | A link because of `as` vs. a link because of `href`: the same `<a>`, a different thing to write

Compare two Checkout tags:

```tsx title="Two ways to ask for the Checkout link"
<Button ~as="a"~ href="/checkout">Checkout</Button> {/* Principle 2: as names the tag */}
<Button ~href="/checkout"~>Checkout</Button> {/* No as: href alone asks for the link */}
```

Under the type of Principle 2, the second tag is refused. A plain `Button` takes the attributes of a button, and a button has no `href`. Under the type of this principle, the second tag is the link.

**It may look the same, but it is NOT the same thing!** Both tags give the page the same `<a>` with the primary class. The difference is in what the page must write, and in what `Button` can become:
1. **With `as`**, every link must write it, and the component can become any tag or any component.
2. **With `href`**, the page writes only the address, and the component has exactly two forms.

### Two props types joined by `|`

The props type is a union of two object types, an `<a>` form and a `<button>` form (Lesson 92):

```tsx title="src/Button.tsx"
import type { ComponentPropsWithoutRef } from 'react';

type ButtonProps = { variant?: 'primary' | 'secondary' } & (
  | ({ ~href: string~ } & ComponentPropsWithoutRef<'a'>) // The <a> form: href is required
  | ({ ~href?: undefined~ } & ComponentPropsWithoutRef<'button'>) // The <button> form: no href allowed
);

export default function Button({ variant = 'primary', ...rest }: ButtonProps) {
  if (~rest.href !== undefined~) { // From here on, TypeScript treats rest as the <a> form
    return <a className={variant} {...rest} />;
  }
  return <button className={variant} {...rest} />;
}
```

Two pieces are new here:
- **`href?: undefined`** says that the `<button>` form may not hold an `href`. So a tag with a string `href` fits only the `<a>` form. The line also gives both forms a field named `href`. So the code inside the component may read `rest.href`, whichever form it gets.
- **`rest.href !== undefined`** checks the one field that tells the two forms apart. After this check, TypeScript narrows `rest` to the link form. It is the same move as the `type` field that told the reducer actions apart in Lesson 92.

Notice that `Button` does not unpack `href` by name. It stays inside `rest`, and the check reads it there.

`<Button href="/checkout">` gets the `<a>` form in three steps:
1. The page writes `href="/checkout"`, a string.
2. The `<button>` form allows only `href?: undefined`, so the tag does not fit it.
3. The `<a>` form, with `href: string`, fits. TypeScript then checks every other attribute of the tag against that form.

### `disabled` next to `href` is refused

This union has a form with `disabled`, so it is natural to expect it to pass next to `href`. **It does not: `href` picks the form first, and that form decides every other attribute.**

```tsx title="The Checkout link with disabled, under the union"
<Button href="/checkout" ~disabled={count === 0}~>Checkout</Button> {/* **WRONG:** href picks the <a> form, and the <a> form has no disabled */}
```

The editor prints a long message. Its last line names the `<a>` form:

```text title="The last line of the editor's message"
Property 'disabled' does not exist on type 'IntrinsicAttributes & { variant?: "primary" | "secondary" | undefined; } & { href: string; } & ...
```

The event follows the form too. Next to `href`, a handler may read `e.currentTarget.href`, because in the link form the current target is the `<a>`.

### The mistake this union prevents: `href` on a `<button>`

Picture a store whose shared `Button.jsx` is still plain JavaScript, from before the types of Lesson 90. It always renders a `<button>` with the class and the rest props. A developer writes `<Button href="/checkout">Checkout</Button>` and expects a link. React renders a `<button>` with an `href` attribute:

```dom caption="The Elements panel: the plain Button.jsx puts href on a button."
<div id="root">
  <p>Cart: 2 items</p>
  <button class="secondary">Clear cart</button>
! <button class="primary" href="/checkout">Checkout</button> | note: href on a button goes nowhere
</div>
```

The user clicks Checkout, and nothing happens. MDN's list of the attributes of `<button>` has no `href`, so the browser ignores it.

A typed button component that renders only a button would at least refuse `href` on the tag (Lesson 90). With this union, the same tag becomes the link.

### Our cart page, step 3: the second way

The union is a second way to write `Button.tsx`, not a step on top of Principle 2. With the union version above, `App.tsx` drops `as="a"` from Checkout:

```tsx title="src/App.tsx" startLine="11"
      {count > 0
        ? <Button ~href="/checkout"~>Checkout</Button> // href alone picks the <a> form
        : <Button disabled>Checkout</Button>} {/* No href: the <button> form, which supports disabled */}
```

The page is the same as in Principle 2:
- **While the cart has items**, Checkout is an `<a>` with the primary class and the checkout address.
- **Once the cart is empty**, Checkout is a `<button>` with the primary class and `disabled`.

Which way fits? The union fits exactly two forms, a button and a link. A third form, or a router's `Link` component, needs the `as` of Principle 2.

In both ways, the right answer for an empty cart is the same: render the button form with `disabled`, never a link with `disabled`.

```tree caption="Two ways to get a link from one Button: as names the tag, or href picks the form of a union."
Two ways to make `Button` a link
- +`as` with a type parameter [`<Button as="a" href="/checkout">`] | Every link **writes `as`** | `Button` can become **any tag or a component** such as a router Link
- +A union chosen by `href` [`<Button href="/checkout">`] | The page writes **only `href`** | `Button` has **exactly two forms**: a link or a button
```

## All 3 Principles Together

### The complete code

Here is the finished project with the `as` prop of Principles 1 and 2. `Button.tsx` reads the tag from `as`, and its type gives each tag only its own attributes:

```tsx title="src/Button.tsx"
import type { ComponentPropsWithoutRef, ElementType } from 'react';

type ButtonProps<E extends ElementType> = {
  ~as?: E~; // Principle 2: TypeScript fills in E from as at each tag
  variant?: 'primary' | 'secondary';
} & ComponentPropsWithoutRef<E>; // Principle 2: only the attributes of the tag that as names

export default function Button<E extends ElementType ~= 'button'~>({ as, variant = 'primary', ...rest }: ButtonProps<E>) { // Principle 2: no as means the attributes of <button>
  const ~Component~ = as ?? 'button'; // Principle 1: a capitalized variable holds the tag name
  return <Component className={variant} {...rest} />;
}
```

`App.tsx` holds the number of items and gives Checkout its two forms:

```tsx title="src/App.tsx"
import { useState } from 'react';
import Button from './Button';

export default function App() {
  const [count, setCount] = useState(2);

  return (
    <>
      <p>Cart: {count} items</p>
      <Button variant="secondary" onClick={() => setCount(0)}>Clear cart</Button>
      {count > 0
        ? <Button ~as="a"~ href="/checkout">Checkout</Button> // A link while the cart has items
        : <Button ~disabled~>Checkout</Button>} {/* A disabled button once the cart is empty */}
    </>
  );
}
```

### How React calls the components

When the page opens, React calls `App` first. `App` returns two `Button` tags, so React calls the button component once for Clear cart and once for Checkout. When the user clicks Clear cart, the setter sets `count` to 0. React then calls `App` and both buttons again:

```tree dir=right caption="The order of the calls: App, then Button for Clear cart, then Button for Checkout, and all three again after the click."
How React renders the cart page
- +1. `App` [`useState 2`] | `count` is **2** | Returns the line, **Clear cart**, and **the Checkout link**
- +2. `Button` for Clear cart [`variant="secondary"`] | No `as`, so `Component` is **`'button'`** | Creates **`<button class="secondary">`**
- +3. `Button` for Checkout [`as="a"`] | `Component` is **`'a'`** | Creates **`<a class="primary" href="/checkout">`**
- +4. The user clicks Clear cart [`setCount`] | `count` is **0**, and React calls **`App` and both `Button` tags again** | Checkout becomes **`<button class="primary" disabled>`**
```

```page caption="The finished cart page after the user clicks Clear cart."
line: Cart: 0 items
form:
  button: Clear cart
  button: Checkout | | disabled
console: quiet
```

| Aspect | The Common Mistake | The Polymorphic Rule |
| :--- | :--- | :--- |
| **The tag** | Write the prop itself as the tag, `<as>`, and get an element named `as` | Copy `as` into `Component` and write `<Component {...rest} />` |
| **The attributes** | One props type for both tags, so `disabled` passes on a link | `ComponentPropsWithoutRef<E>`, so each tag gets only its own attributes |
| **No `as` on the tag** | A type parameter with no default, so a plain `Button` accepts any prop | `E extends ElementType = 'button'`, so a plain `Button` takes the attributes of `<button>` |
| **The default tag** | A default in the parameter list, which the editor refuses | `as ?? 'button'` in the body |
| **Exactly two forms** | `href` on a plain `<button>`, which goes nowhere | A union chosen by `href`: a link when `href` is passed, a button otherwise |

Remember the one sentence of this lesson. **`as` decides two things at once: which tag React creates in the browser, and which attributes TypeScript accepts on that tag.**

## For the Interview

> **The Interview Question:** How do you build polymorphic components with the as prop in TypeScript?

### How to Answer Clearly in 30 Seconds

"A polymorphic component lets the page choose its outer tag, such as a `<button>` or an `<a>`, with one prop, usually `as`. The part that runs is plain React: the component copies `as` into a capitalized variable, `const Component = as ?? 'button'`, and renders `<Component {...rest} />`. The types do three things:
1. **The tag is a type parameter:** `E extends ElementType = 'button'`, with `as?: E`, so TypeScript fills in `E` from `as` at each tag.
2. **The attributes follow the tag:** the props take `ComponentPropsWithoutRef<E>`, so a link accepts `href` and refuses `disabled`, and even `e.currentTarget` is typed as the link.
3. **The default matters:** without `= 'button'`, a `Button` with no `as` accepts any prop.

When there are exactly two forms, I can skip `as` and use a union chosen by `href`: a button by default, and a link when `href` is passed. The types change nothing in the browser. They stop a link with `disabled` before the code runs."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What happens when the component's own prop has the same name as an attribute of the tag?"**
   The two types are joined by `&`, so the prop must fit both. Suppose a `Card` component has its own `title` prop that holds JSX, while the `title` attribute of the tag holds only a string. Then `title={<b>Sale</b>}` is refused with a message that starts `Type 'Element' is not assignable to type 'string | ...`. The full polymorphic type removes the clash with `Omit`, which drops from the tag's attributes every name the component defines itself. Here `P` stands for the component's own props:
   ```tsx
   type Props<E extends ElementType, P> = P & { as?: E } & ~Omit<ComponentPropsWithoutRef<E>, keyof P | 'as'>~; // The component's own props win every clash
   ```
   On our cart page, `as` and `variant` clash with no attribute of `<a>` or `<button>`, so `Omit` changes nothing there.
2. **"Can `as` hold a component, not only a tag name?"**
   Yes. React's `createElement` takes "a tag name string ... or a React component", and `ElementType` covers both. The case at work is a router's `Link`. React's docs call React Router "the most popular routing library for React". Take a small `Link` whose props are `{ to: string }` and the attributes of `<a>`. Then `<Button as={Link} to="/checkout">` passes, and `<Button as={Link}>` is refused with `Property 'to' is missing in type ...`. So the required props of the component are checked too.
3. **"Why `ComponentPropsWithoutRef` and not `ComponentPropsWithRef`?"**
   In React 19, `ref` is an ordinary prop (Lesson 85). `ComponentPropsWithoutRef<E>` drops it, so `ref` on `<Button as="a">` is refused with `Property 'ref' does not exist on type ...`. To accept a ref typed by the tag, write `Omit<ComponentPropsWithRef<E>, 'as' | 'variant'>`. Then a ref to an `HTMLAnchorElement` passes on `as="a"`, and a ref to an `HTMLButtonElement` is refused. The trap is `ComponentPropsWithRef<E>` with no `Omit`: TypeScript stops filling in `E` from `as`, and `disabled` on `as="a"` passes again. The react.dev site's own code calls this kind of inference "kind of a huge pain", and its `Heading` falls back to `as?: any`.

```tree caption="Interview summary: as names the tag in the browser, and the type parameter E gives that tag only its own attributes."
A polymorphic `Button` in TypeScript
- +In the browser [`const Component = as ?? 'button'`] | A capitalized variable **holds the tag name** | React creates **the tag that `as` names**
- +For the type-checker [`as?: E` `ComponentPropsWithoutRef<E>`] | TypeScript **fills in `E` from `as`** | Each tag accepts **only its own attributes**
- +Exactly two forms [`href: string` `href?: undefined`] | A union **chosen by `href`** | A link when `href` is passed, **a button otherwise**
```
