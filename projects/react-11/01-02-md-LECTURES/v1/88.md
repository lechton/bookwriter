# Lecture 88: How act Lets a Test See the Fetched Name

*(Why does a test read Loading... when the browser already shows John?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | What does act() do in tests, and why do state updates and effects need it?

---

## VS | `render` Alone vs. `render` Inside `await act`: both put the card on the page, only `await act` waits for John

> When a profile card opens, it shows `Loading...`, and a moment later the name `John` arrives from the server and takes its place. **A test does not wait for that moment: it reads the page on the very next line, so you wrap the work in `await act`, which makes React finish every update before the test looks.** Without `act`, the test reads `Loading...` on a card that works, fails, and sends you hunting for a bug that does not exist.

In plain JavaScript, the page changes on the line you write. You set `heading.textContent = 'John'`, and the very next line already reads `John`. React does not work like that. You never change the page yourself. You ask React for a render, or you call a setter, and React does the work a moment later. In the browser, nobody notices that moment. In a test, the next line runs at once, before React has done anything.

```js title="Plain JavaScript: the page changes on this line"
heading.textContent = 'John';
console.log(~heading.textContent~); // John: the line above already changed the page
```

```jsx title="React: you ask, and React renders a moment later"
root.render(<ProfileCard />);
console.log(~container.textContent~); // An empty string: React has not rendered yet
```

This is why React gives tests one function, `act`. You put the work inside it, and `act` returns only when React has finished that work: the render, the Effects, and every setter they call. You already used it without seeing it. In Lesson 87, the click test read `Following` on the line right after `fireEvent.click`, because React Testing Library wraps that click in `act`.

> [!DEFINITION]
> **What is act?** [NEW] `act` is a function from `react`, made only for tests: `import { act } from 'react'`. A function made only for tests is called a test helper.
> You pass it a function that holds the work, such as a render. Before `act` finishes, React applies every pending update to the page. Pending updates are the work React was asked to do and has not yet put on the page: the render, the Effects that run after it, and the new render that a setter asks for.
> So the line after `act` reads the page the way the user would see it.
> The name comes from the Act step of Arrange, Act, Assert (Lesson 87).

### The profile card that loads its name

Open a profile on a social app. For a moment, the card shows `Loading...`:

```page width=text caption="The profile card when it opens: the name has not arrived yet."
heading: Loading...
```

A moment later, the server answers, and the name `John` takes its place:

```page width=text caption="The same card a moment later: the server has answered, and the card shows John."
heading: John | good
```

The card asks the server for the name in an Effect, the way a component loads its data when it appears (Lesson 33). The user waits a moment and sees `John`. That is what our test must check: the heading reads `John`.

### Two tests for the same card

A test has no server. So the test hands the card its own `fetch`, which answers `{ name: 'John' }` at once. Principle 2 shows how.

Both tests below find the card's `<h2>` with `getByRole('heading')`. Every heading tag, from `<h1>` to `<h6>`, has the role `heading`. The first test puts the card on the page with `render` alone:

```jsx title="The test with render alone"
it('shows John after the server answers', () => {
  ~render(<ProfileCard />)~; // Puts the card on the page of the test
  expect(screen.getByRole('heading').textContent).toBe('John'); // **WRONG:** fails: the heading still reads Loading...
});
```

The second test puts the same `render` inside `await act`:

```jsx title="The test with render inside await act"
it('shows John after the server answers', async () => {
  ~await act~(async () => { // Returns only when React has put John on the page
    render(<ProfileCard />);
  });
  expect(screen.getByRole('heading').textContent).toBe('John'); // Passes: the heading reads John
});
```

The two tests share almost everything: the same card, the same heading, the same word `John`. Only one thing differs. The second test waits for React before it reads the heading.

It may look the same, but it is NOT the same thing! In the browser, the user waits and sees `John`, so you expect the first test to pass too. It does not. A test waits for nothing it is not told to wait for. The next line runs at once, while the heading still reads `Loading...`:

```text title="Terminal: npm run test, the test with render alone"
 FAIL  src/ProfileCard.test.jsx > shows John after the server answers
AssertionError: expected 'Loading...' to be 'John' // Object.is equality

Expected: "John"
Received: "Loading..."
```

```tree caption="Two tests for the profile card: one reads the heading at once, one waits until React has put John on the page."
Two tests that check `John` on the profile card
- !With `render` alone [`render`] | Reads the heading **at once** | Gets **`Loading...`** and **fails**, though the card works
- +With `render` inside `await act` [`await act` `async`] | Waits until React has **applied the update after the answer** | Gets **`John`** and **passes**
```

### The Rule of Thumb: what happens inside `await act` is on the page

**Everything that happens inside `await act` is on the page when the next line runs. Anything React does later is not, so the test must wait for it inside `await act`.**

What is at stake is a test that tells the wrong story about a card that works:
1. The card works in the browser: `Loading...`, then `John`.
2. The test that checks `John` fails. The developer thinks the card is broken and hunts for a bug that does not exist.
3. Or the developer changes the test to check `Loading...`, and it passes. Now the test never checks that the name arrives. A card that never shows the name passes it too.
4. The terminal may also print a warning that an update was not wrapped in `act`, and the developer does not know which line caused it.

A senior developer also knows the three classic mistakes:
1. **Reading the page as if it changes line by line**, the way it does when plain JavaScript sets `textContent` (Lesson 01).
2. **Believing that `render` waits for everything**, because the helpers of React Testing Library are wrapped with `act` (Lesson 87).
3. **Calling `act` without `await`.** react.dev says this form does not work in all cases.

### Three ways to apply React's updates in a test

At work, you will meet three ways:
1. **`act` from `react` around `root.render`.** This is how react.dev's own examples test a component, with no testing library. The test creates the place for the card and turns on one flag by hand. Principles 1 and 2 build this way, so you see exactly what `act` does.
2. **React Testing Library.** react.dev suggests it "to avoid some of the boilerplate", because its helpers "are wrapped with `act()`". It fits most component tests. Principle 3 builds this way.
3. **No `act` at all, in an end-to-end test.** Such a test runs the whole app in a full browser, and there `act` "isn't needed", in react.dev's words. This lesson only names it.

## SECTION | A Profile Card That Fetches Its Name

The project is a Vite app set up like the Follow card project, with Vitest, jsdom, and React Testing Library already installed (Lesson 87). The test file sits next to the card it tests:

```files title="profile-card: File Explorer" caption="The files of the profile card project, with the test file next to the card it tests."
index.html | entry | The HTML page with the empty root div where React mounts
package.json | scripts | Holds the `"test": "vitest"` script, unchanged
vite.config.js | config | Names `jsdom` as the test environment, unchanged
src/
  main.jsx | boundary | Mounts `<App />` into `#root`
  App.jsx | parent | Renders `<ProfileCard />`
  ProfileCard.jsx | default export | Exports `ProfileCard`, which fetches the name in an Effect
  ProfileCard.test.jsx | test | Imports `ProfileCard` and checks the heading the user sees
```

The card keeps the name in state, starting at `null`. Its Effect fetches the name. While the name is still `null`, the heading shows `Loading...`:

```jsx title="src/ProfileCard.jsx"
import { useEffect, useState } from 'react';

export default function ProfileCard() {
  const [name, setName] = useState(null);

  useEffect(() => {
    ~fetch('/api/user')~ // Runs after the first render is on the page
      .then(response => response.json())
      .then(data => ~setName(data.name)~); // The name arrives, and React renders the card again
  }, []);

  return <h2>{name ?? 'Loading...'}</h2>;
}
```

So the card changes the page twice. First React renders `Loading...`. Then, after the answer, `setName` asks for a second render, with `John`. A test that wants `John` must wait for both.

A real card also keeps the ignore flag and its cleanup, so that a late answer cannot overwrite a newer one (Lesson 33). We leave them out to keep the card at one heading. The test works the same with them.

Now let's test it, and break it. Each principle moves the line where the test reads the page, and shows what that line sees:

**PRINCIPLES:** A test reads the page on the next line, at once. React applies its updates a little later. `act` closes that gap: React finishes every pending update before the test looks. Three principles follow:
1. **Principle 1: `act` puts the first render on the page.** `root.render` only asks React for a render, so the next line finds an empty container. Inside `await act`, React renders the card and runs its Effect first.
2. **Principle 2: `await act` with an `async` function waits until John arrives.** The name comes after a promise. `act` without `await` returns before that, and the test reads `Loading...`.
3. **Principle 3: The `act` inside `render` ends before the name arrives.** React Testing Library covers the first render. For the name that comes later, the test still wraps `render` in `await act`.

## PRINCIPLE | `await act`: React renders the card and runs its Effect before the next line reads the page

> [!PRINCIPLE]
> **Principle 1: The First Render: `act` Puts the Card on the Page Before the Test Looks**
>
> *Wrap `root.render` in `await act(async () => { ... })`, so React renders the card and runs its Effects before the next line reads the page.*
>
> `root.render` only asks React for a render. The next line of the test runs at once, so it finds an empty container. Inside `act`, React puts the render on its act queue, applies it to the page, and runs the Effects before `act` finishes. Set `IS_REACT_ACT_ENVIRONMENT` to `true` first, so React knows it runs inside a test.
>
> **DO THIS:**
> ```jsx
> ~await act~(async () => { // React renders the card and runs its Effect first
>   createRoot(container).render(<ProfileCard />);
> });
> expect(container.textContent).toBe('Loading...');
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~createRoot(container).render(<ProfileCard />)~; // **WRONG:** React has not rendered yet, so the next line reads an empty container
> expect(container.textContent).toBe('Loading...');
> ```

To see what `act` really does, we take the library away. We write the test the way react.dev's own examples do, with `createRoot` and `root.render`, the same two calls that `main.jsx` makes (Lesson 07).

In this principle, the test's `fetch` never answers, so the card can only show `Loading...`. The test checks exactly that.

### `root.render` alone vs. `root.render` inside `await act`

Here is the test with `root.render` alone:

```jsx title="The test with root.render alone"
const container = document.createElement('div');
document.body.appendChild(container);
~createRoot(container).render(<ProfileCard />)~; // Asks React for a render
expect(container.textContent).toBe('Loading...'); // **WRONG:** fails: the container is still empty
```

And here is the same render inside `await act`:

```jsx title="The test with root.render inside await act"
const container = document.createElement('div');
document.body.appendChild(container);
~await act~(async () => { // React renders and runs the Effect before act finishes
  createRoot(container).render(<ProfileCard />);
});
expect(container.textContent).toBe('Loading...'); // Passes
```

It may look the same, but it is NOT the same thing! In the app, `main.jsx` calls `root.render`, and the card appears. So you read `root.render` as a command that draws the card at once, the way `textContent` changes a paragraph at once.

It is not. `root.render` draws nothing on its own line. It asks React for a render, and React does the work a moment later. react.dev says it plainly: "Although rendering is synchronous once it starts, `root.render(...)` is not." **Synchronous** means the work is finished before the next line runs. `root.render` is not synchronous, so:
1. The test calls `createRoot(container).render(<ProfileCard />)`. React notes that a render is wanted.
2. The next line runs at once and reads `container.textContent`. React has not rendered yet, so the text is an empty string.
3. The test fails.

```text title="Terminal: npm run test, the test with root.render alone"
 FAIL  src/ProfileCard.test.jsx > shows Loading... while the server has not answered
AssertionError: expected '' to be 'Loading...' // Object.is equality

- Expected
+ Received

- Loading...
```

Vitest shows the empty string as a short diff. The line `- Loading...` is what the test expected. No line with a plus follows it, because the container holds no text at all.

React also prints a warning that an update to `Root` was not wrapped in `act`. The update it means is our call to `root.render`.

### What happens inside `await act`

Inside `act`, the order changes:
1. React does not render on the spot. It puts the render on the **act queue**, a list of updates that wait inside `act`.
2. When the function we gave to `act` has finished, React **flushes** the act queue: it applies every update on the list to the page, all together. react.dev: "Any updates triggered within the `actFn`, are added to an internal act queue, which are then flushed together."
3. The render puts `<h2>Loading...</h2>` in the container, and React runs the card's Effect. react.dev: "This ensures that the component is rendered and its effects are applied before making assertions."
4. Only then does `act` finish. The next line reads `Loading...`, and the test passes.

```tree dir=right caption="Without act, the test reads the page before React renders; inside await act, React renders and runs the Effect first."
When the test reads the container
- !`root.render` alone [`root.render`] | React **notes** that a render is wanted | The next line reads **an empty container** and **fails**
- +`root.render` inside `await act` [`await act`] | React **renders the card and runs its Effect** before `act` finishes | The next line reads **`Loading...`** and **passes**
```

### The whole test file

Here is the first version of the test file:

```jsx title="src/ProfileCard.test.jsx"
import { ~act~ } from 'react'; // The test helper comes from react itself
import { createRoot } from 'react-dom/client';
import { expect, it } from 'vitest';
import ProfileCard from './ProfileCard';

~globalThis.IS_REACT_ACT_ENVIRONMENT = true~; // Tells React that it runs inside a test

it('shows Loading... while the server has not answered', async () => {
  ~globalThis.fetch~ = () => new Promise(() => {}); // A fetch that never answers
  const container = document.createElement('div');
  document.body.appendChild(container);
  await act(async () => {
    createRoot(container).render(<ProfileCard />);
  });
  expect(container.textContent).toBe('Loading...');
});
```

Three lines are new:
1. **`act` comes from `react`**, the same package our card imports its hooks from. The function given to `it` is now `async`, because the test writes `await` inside it (Lesson 41).
2. **The container** is the `<div>` where React puts the card. Our test creates it and adds it to the document with `document.body.appendChild`. React never creates it. react.dev's examples do the same: "we create a container, append it to the document".
3. **The flag `IS_REACT_ACT_ENVIRONMENT`.** See the definition below.

> [!DEFINITION]
> **What is IS_REACT_ACT_ENVIRONMENT?** [NEW] It is a global variable that holds `true` or `false`, a flag. With `globalThis.IS_REACT_ACT_ENVIRONMENT = true`, you tell React that it runs inside a test.
> With the flag on, React expects every update to happen inside `act`, and prints a warning for an update that does not.
> In a real project, this line lives in the test setup file, a file that runs before every test file (Lesson 88).

### The test hands the card its own `fetch`

The card calls `fetch('/api/user')`, yet no request leaves the test. Here is why:
1. `globalThis` is the global object of JavaScript. It holds the names that every file can use without an import, such as `fetch`.
2. Before the render, the test puts its own function on `globalThis`, under the name `fetch`.
3. The card's Effect calls `fetch`, finds the test's function under that name, and calls it.

The test's function returns `new Promise(() => {})`. This promise stays **pending**: in MDN's words, "neither fulfilled nor rejected". It never gets a value, so it acts like a server that has not answered yet. The Effect did run inside `act`, so the card did call the test's `fetch`. The call simply never gets an answer, and the card keeps showing `Loading...`.

### The forgotten flag and the forgotten container

The first time you write this test, you usually forget one of two lines.

The first is the flag. Without `IS_REACT_ACT_ENVIRONMENT`, React does not know that it runs inside a test. When the test calls `act`, React prints this error:

```text title="Terminal: the test without IS_REACT_ACT_ENVIRONMENT"
The current testing environment is not configured to support act(...)
```

The fix is one line, `globalThis.IS_REACT_ACT_ENVIRONMENT = true;`, in the test setup file or at the top of the test file.

The second is the line that adds the container to the document. react.dev warns that "dispatching DOM events only works when the DOM container is added to the document". In React 19, a click inside a container that was never added still reaches its handler, because React listens for events on the container itself. But nothing outside the container can find the card. `document.querySelector` searches only the document, and so does `screen` from React Testing Library. A test that searches the page for the card finds nothing. So always call `document.body.appendChild(container)`, as react.dev's examples do.

## PRINCIPLE | `await act` with an `async` function: the test waits until the fetched name is on the page

> [!PRINCIPLE]
> **Principle 2: The Async Boundary: `await act` With an `async` Function Waits for the Answer**
>
> *When an update comes after a promise, write `await act(async () => { ... })`, so React runs the code after the promise and applies its setter before the test reads the page.*
>
> A promise runs its `.then` only after the current code has finished. `act` without `await` returns before that, so the test reads `Loading...`, and the setter runs outside `act` with a warning. With `await` and an `async` function, React also runs the code that crosses an async boundary and flushes the updates it schedules, such as `setName('John')`.
>
> **DO THIS:**
> ```jsx
> ~await act(async~ () => { // Waits until John has arrived and React has rendered it
>   createRoot(container).render(<ProfileCard />);
> });
> expect(container.textContent).toBe('John');
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~act~(() => { // **WRONG:** returns before setName runs, so the test reads Loading...
>   createRoot(container).render(<ProfileCard />);
> });
> expect(container.textContent).toBe('John');
> ```

Principle 1 checked `Loading...`. Now we check the word the user really waits for: `John`.

### Now the test's `fetch` answers

So the test's `fetch` must answer. It returns an answer with the same shape as a real one, an object with a `json` function (Lesson 33):

```jsx title="A fetch that answers John at once"
globalThis.fetch = () => ~Promise.resolve~({ json: () => Promise.resolve({ name: 'John' }) }); // Answers at once with an object that has a json function
```

`Promise.resolve` returns a promise that already holds its value. Such a promise is called **fulfilled**. So the answer is ready at once, and the name comes from our test, not from a server:
1. The card's first `.then` calls `response.json()`. That is the test's own `json` function, and it gives `{ name: 'John' }`.
2. The second `.then` calls `setName(data.name)`.
3. React renders the card again, and `??` now shows `John`.

### `act` without `await` vs. `await act` with an `async` function

`act` can be written in two ways. react.dev calls the form without `await` the **sync version**. Both wrap the same render, and both are followed by the same check:

```jsx title="act without await: the sync version"
~act~(() => { // Returns as soon as the first render and its Effect are applied
  createRoot(container).render(<ProfileCard />);
});
expect(container.textContent).toBe('John'); // **WRONG:** fails: the heading still reads Loading...
```

```jsx title="await act with an async function"
~await act(async~ () => { // Also waits for the code after the promise, and applies setName
  createRoot(container).render(<ProfileCard />);
});
expect(container.textContent).toBe('John'); // Passes
```

It may look the same, and it even works the same at first, but it is NOT the same thing! For the `Loading...` test of Principle 1, nothing comes later, so both forms show `Loading...`. When the answer comes after a promise, only `await act` with an `async` function shows `John`.

> [!DEFINITION]
> **What is an async boundary?** [NEW] It is a point where the code waits for a promise, such as a `.then` or an `await`. The code after that point runs later, not on the same line.
> Our card's Effect has two of them: the two `.then` calls after `fetch`.
> react.dev says what `await act` with an `async` function does with them: "Since it is async, React will also run any code that crosses an async boundary, and flush any updates scheduled" (Lesson 88).

### Why the test without `await` still reads `Loading...`

**Beware! A promise that already holds its value still runs its `.then` later, not on the same line.**

Remember `setTimeout(fn, 0)`? Even with zero milliseconds, `fn` runs only after the code that runs now has finished. A `.then` on a fulfilled promise waits the same way:

```js title="A fulfilled promise still runs its .then later"
Promise.resolve('John').then(name => console.log(name));
console.log('next line');
```

```page width=text caption="The Console: next line prints first, and John prints after it."
log: next line | test.js:2
log: John | test.js:1
```

So here is what happens, in order, in the test without `await`:
1. Inside `act`, React renders the card, which shows `Loading...`, and runs its Effect.
2. The Effect calls the test's `fetch`, which returns a fulfilled promise.
3. The `.then` functions do not run yet. They wait until the code that runs now has finished.
4. `act` has already returned. The next line reads `Loading...`, and the test fails.
5. Only after that do the `.then` functions run, and `setName('John')` runs outside `act`.

```text title="Terminal: npm run test, the John test with act without await"
 FAIL  src/ProfileCard.test.jsx > shows John after the server answers
AssertionError: expected 'Loading...' to be 'John' // Object.is equality

Expected: "John"
Received: "Loading..."
```

Step 5 leaves one more trace. The flag is on, so React notices the setter that runs outside `act`, and prints a warning that names the component:

```text title="Terminal: the warning for setName outside act"
An update to ProfileCard inside a test was not wrapped in act(...).
```

The warning names `ProfileCard`, not a line of the test. That is why you do not know where to look. The line to fix is the `act` without `await`.

With `await act` and an `async` function, the order is different. React runs the code after the promise, puts `setName('John')` on its act queue, flushes it, and renders the card again. Only then does the test go on. The next line reads `John`, and the test passes.

```tree dir=right caption="act without await returns before the name arrives; await act with an async function waits for the code after the promise."
When `setName` runs, compared with the test's check
- !`act` without `await` [`act`] | Returns after the **first render** | The test reads **`Loading...`** and fails, then `setName` runs **outside `act`** with a warning
- +`await act` with an `async` function [`await act` `async`] | Also runs the code **after the promise** and flushes `setName` | The test reads **`John`** and passes
```

react.dev recommends this form: "We recommend using `act` with `await` and an `async` function. Although the sync version works in many cases, it doesn't work in all cases." It also says that React will remove the sync version in the future.

### The timer that hides the bug

You copy a test that uses `act` without `await`. It passes for `Loading...`. Then you add the `John` test. It fails, and a warning about `act` appears.

So you add a timer that waits a little before the check. Now the test is slower, and nothing in it says what it waits for.

The fix is two words: `await` before `act`, and `async` before the function you pass to it. The test then waits exactly as long as React needs, and no longer.

Here is the test file with both tests:

```jsx title="src/ProfileCard.test.jsx"
import { act } from 'react';
import { createRoot } from 'react-dom/client';
import { expect, it } from 'vitest';
import ProfileCard from './ProfileCard';

globalThis.IS_REACT_ACT_ENVIRONMENT = true;

it('shows Loading... while the server has not answered', async () => {
  globalThis.fetch = () => new Promise(() => {});
  const container = document.createElement('div');
  document.body.appendChild(container);
  await act(async () => {
    createRoot(container).render(<ProfileCard />);
  });
  expect(container.textContent).toBe('Loading...');
});

it('shows John after the server answers', async () => {
  globalThis.fetch = () => Promise.resolve({ json: () => Promise.resolve({ name: 'John' }) });
  const container = document.createElement('div');
  document.body.appendChild(container);
  ~await act(async~ () => { // Waits for both .then calls and applies setName
    createRoot(container).render(<ProfileCard />);
  });
  expect(container.textContent).toBe('John');
});
```

Each test creates its own container, so each test reads only its own card.

## PRINCIPLE | `render` from Testing Library: its own `act` covers the first render, not the name that arrives later

> [!PRINCIPLE]
> **Principle 3: Testing Library: Its Helpers Run `act`, but Not for the Answer That Comes Later**
>
> *React Testing Library wraps `render` and `fireEvent` with `act`; when the update comes after a promise, wrap `render` in `await act(async () => { ... })` yourself, and keep `IS_REACT_ACT_ENVIRONMENT` on for that `act`.*
>
> The `act` inside `render` applies the first render and runs the Effect, then ends when `render` returns. The fetched name arrives after a promise, so it arrives after that `act`. Our own `await act` around `render` waits for that code and applies the setter before the test checks the name.
>
> **DO THIS:**
> ```jsx
> ~await act~(async () => { // Covers the code after the promise too
>   render(<ProfileCard />);
> });
> expect(screen.getByRole('heading').textContent).toBe('John');
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> render(<ProfileCard />);
> expect(screen.getByRole('heading').textContent).toBe(~'Loading...'~); // **WRONG:** passes, but never checks that the name arrives
> ```

The test file of Principle 2 works, but every test repeats the container and `createRoot`, and the file must set the flag. react.dev says it directly: "You might find using `act()` directly a bit too verbose. To avoid some of the boilerplate, you could use a library like React Testing Library, whose helpers are wrapped with `act()`."

### The same first render, with less code

So `render` from React Testing Library already wraps the render in `act` for us. Compare the two for the `Loading...` test:

```jsx title="The first render with root.render inside await act"
await act(async () => {
  ~createRoot(container).render(<ProfileCard />)~; // Our test wraps the render in act
});
expect(container.textContent).toBe('Loading...'); // Passes
```

```jsx title="The first render with render from Testing Library"
~render(<ProfileCard />)~; // Testing Library wraps the render in act for us
expect(screen.getByRole('heading').textContent).toBe('Loading...'); // Passes
```

For the first render, yes, it is the exact same thing! Both put `Loading...` on the page before the next line runs. `render` also creates the container itself, so the test no longer writes one. And `render` turns on `IS_REACT_ACT_ENVIRONMENT` while its own `act` runs, so this test needs no flag line.

### `render` alone vs. `render` inside `await act`, for the name

Now the test checks `John`, with the `fetch` of Principle 2 that answers at once. These are the two tests from the start of the lesson:

```jsx title="The John test with render alone"
render(<ProfileCard />); // The act inside render ends when render returns
expect(screen.getByRole('heading').textContent).toBe('John'); // **WRONG:** fails: the heading still reads Loading...
```

```jsx title="The John test with render inside await act"
~await act~(async () => { // Our own act waits for the code after the promise
  render(<ProfileCard />);
});
expect(screen.getByRole('heading').textContent).toBe('John'); // Passes
```

It may look the same, but it is NOT the same thing! You know that `render` is wrapped with `act`, so you conclude: "Testing Library handles `act` for me, I never need it again." That holds for the first render, and it stops there. That `act` ends when `render` returns. The name arrives after a promise, so it arrives after that `act` has already finished.

Here is the test with `render` alone, in order:
1. The test calls `render(<ProfileCard />)`.
2. Inside `render`, Testing Library calls `act`. React renders the card, which shows `Loading...`, and runs the Effect. The Effect calls the test's `fetch`.
3. `render` returns. The `.then` functions have not run yet.
4. The next line reads `Loading...`, where the test wanted `John`. The test fails.
5. Then `setName('John')` runs outside any `act`. When the test file turns on the flag, React prints the warning of Principle 2.

With `render` inside our own `await act`, the setter runs inside our `act`, so React flushes it before the test goes on. The heading reads `John`, and the test passes.

```tree caption="The act inside render covers only the first render; an await act around render also covers the name that arrives after the promise."
What each `act` covers in the John test
- !`render` alone [`render`] | Its `act` covers the **first render** and the **Effect**, then ends **before the name arrives** | The test gets **`Loading...`** and **fails**
- +`render` inside `await act` [`await act` `async`] | Our `act` also covers the **code after the promise** and `setName` | The test gets **`John`** and **passes**
```

### Why the click test of the Follow card needed no `await`

The click test of the Follow card read `Following` on the line right after `fireEvent.click`, with no `await` (Lesson 87). The click's update has no promise after it. The click calls `dispatch`, React renders the card again, and all of it happens inside the `act` that wraps `fireEvent.click`. Nothing comes later.

The fetched name is different. It comes after a promise, so it comes after the `act` of the helper. That is when a test with Testing Library still writes `act` itself.

### The test that stopped checking the name

This is the mistake that teams really make with this card:
1. A developer tests the profile card with `render` and checks `John` on the next line.
2. The test fails, and the terminal says it received `Loading...`.
3. The developer reads that the helpers of Testing Library are wrapped with `act`, and concludes that `act` is not the problem.
4. So the developer changes the test to check `Loading...`, and it passes.
5. Now the test never checks that the name arrives. A card whose Effect never calls `setName` passes it too.

The fix keeps the `John` check, and wraps `render` in `await act`:

```jsx title="src/ProfileCard.test.jsx"
import { ~act~ } from 'react'; // Still needed: Testing Library does not wrap the code after the promise
import { expect, it } from 'vitest';
import { render, screen } from '@testing-library/react';
import ProfileCard from './ProfileCard';

globalThis.IS_REACT_ACT_ENVIRONMENT = true;

it('shows John after the server answers', async () => {
  globalThis.fetch = () => Promise.resolve({ json: () => Promise.resolve({ name: 'John' }) });
  ~await act~(async () => { // Waits until the name has arrived and React has rendered it
    render(<ProfileCard />);
  });
  expect(screen.getByRole('heading').textContent).toBe('John');
});
```

The container and `createRoot` are gone. `act` stays, for the one update that comes after the promise.

The flag line stays too. react.dev says that in React Testing Library, `IS_REACT_ACT_ENVIRONMENT` "is already set for you". That holds in Jest. Vitest makes its setup functions global only when `vite.config.js` sets `globals: true`, and our config does not. So Testing Library turns the flag on only while its own helpers run, and our own `act` runs outside them. Without the flag line, the test still passes, but React prints the error about the testing environment from Principle 1.

## All 3 Principles Together

### The complete card and its test

The card is unchanged from the start of the lesson:

```jsx title="src/ProfileCard.jsx"
import { useEffect, useState } from 'react';

export default function ProfileCard() {
  const [name, setName] = useState(null);

  useEffect(() => {
    fetch('/api/user')
      .then(response => response.json())
      .then(data => ~setName(data.name)~); // Principle 2: runs after an async boundary, so the test must await act
  }, []);

  return <h2>{name ?? 'Loading...'}</h2>;
}
```

The test uses React Testing Library, and keeps one `await act` and the flag line for the name that arrives after the promise:

```jsx title="src/ProfileCard.test.jsx"
import { act } from 'react';
import { expect, it } from 'vitest';
import { render, screen } from '@testing-library/react';
import ProfileCard from './ProfileCard';

~globalThis.IS_REACT_ACT_ENVIRONMENT = true~; // Principles 1 and 3: our own act runs outside the helpers of Testing Library

  ~globalThis.fetch~ = () => Promise.resolve({ json: () => Promise.resolve({ name: 'John' }) }); // Principle 2: the test's fetch answers John
  ~await act~(async () => { // Principles 1, 2 and 3: applies the render, the Effect, and setName before the check
    render(<ProfileCard />);
  });
  expect(screen.getByRole('heading').textContent).toBe('John');
});
```

### The order of one test run

**Everything inside `await act` is on the page before the check runs.** That is the whole job of `act`. Here is the order, from the test's `fetch` to the word `John`:

```tree dir=right caption="The order of one test run: everything inside await act is applied before the test reads the heading."
How the test reaches `John`
- +1. The test replaces `fetch` [`globalThis.fetch`] | The card will get **the test's answer**
- +2. Inside `await act`: the first render [`render`] | The card shows **`Loading...`** | React **runs the Effect**, which calls `fetch`
- +3. Inside `await act`: the code after the promise [`.then`] | The two `.then` calls run | `setName` puts **`John`** in state
- +4. React flushes the act queue | React **renders the card again** | The heading now reads **`John`**
- +5. `act` finishes, then the check [`expect`] | The test reads the heading | **`John`**, and the test **passes**
```

| What the test does | What it reads | The fix |
| :--- | :--- | :--- |
| **Calls `root.render` and reads the next line** | An empty container | Wrap the render in `await act`, so React renders and runs the Effects first |
| **Calls `act` without the flag** | The error `The current testing environment is not configured to support act(...)` | Set `IS_REACT_ACT_ENVIRONMENT` to `true` whenever the test calls `act` itself |
| **Writes `act` without `await`** | `Loading...`, and `setName` runs outside `act` | Write `await act(async () => { ... })`, which also runs the code after the promise |
| **Trusts that `render` waits for everything** | `Loading...`, so the test gets changed to check `Loading...` | `render` covers the first render only; wrap it in `await act` when the update comes later |

Remember the one sentence of this lesson. **A test reads the page on the very next line, so wrap the work in `await act`, and React finishes every update, even the one after a promise, before the test looks.**

## For the Interview

> **The Interview Question:** What does act() do in tests, and why do state updates and effects need it?

### How to Answer Clearly in 30 Seconds

"`act` is a test helper from `react` that applies pending React updates before the test makes its assertions. A test reads the page on the next line, at once, but React applies renders, Effects, and setters a little later. `root.render` is not synchronous, so without `act` the next line finds an empty page. Inside `act`, every update goes on an act queue, and React flushes it to the page before `act` finishes. Three rules keep it working:
1. **Use `await act` with an `async` function.** It also runs code that crosses an async boundary, such as the `.then` after `fetch`, and flushes the setters it calls. The sync version doesn't work in all cases and will be removed.
2. **Set `IS_REACT_ACT_ENVIRONMENT` to `true`**, so React knows it runs in a test and warns about updates outside `act`.
3. **Testing Library wraps its helpers with `act`**, but an update that comes after a promise still needs `await act` around the work."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What exactly does `act` flush?"**
   Every update triggered inside the function you pass to `act`: the render, the Effects that run after it, and the renders that setters ask for. react.dev says these updates "are added to an internal act queue, which are then flushed together to process and apply any changes to the DOM". With `await` and an `async` function, React also runs the code after each promise, such as the `.then` that calls `setName`, and flushes what that code schedules. `act` hands the test no result to check. The test reads the page after `act` finishes.
2. **"How do testing libraries build on `act`?"**
   They wrap their own helpers with it. In React Testing Library, `render` and `fireEvent` are wrapped with `act`, so a click's new text is already on the page on the next line. The library also turns on `IS_REACT_ACT_ENVIRONMENT` while its helpers run, and for the whole test file in Jest. The wrapping covers only the helper's own call. When the update comes after a promise, it comes after the helper's `act`, so the test still wraps the work in `await act`. End-to-end tests in a full browser go the other way: they set the flag to `false`, because `act` isn't needed there.
3. **"Where do you import `act` from in React 19, and can you use it in the app?"**
   From `react`: `import { act } from 'react'`. The old import from `react-dom/test-utils` is deprecated, and React logs that `ReactDOMTestUtils.act` "is deprecated in favor of `React.act`". `act` is for tests only. The production build of `react` leaves `act` out, so a call to it there throws a `TypeError` that says it is not a function. In the app, React applies its updates by itself. If app code ever needs a render applied at once, React offers `flushSync` around `root.render`.

```tree dir=right caption="Interview comparison: what a test sees without act, with the sync version, and with await act and an async function."
What the line after the render sees
- !No `act` [`root.render`] | React has **not rendered yet** | An **empty container**
- !`act` without `await` [`act`] | First render and Effects **applied** | **`Loading...`**, and `setName` later runs **outside `act`**
- +`await act` with an `async` function [`await act` `async`] | Also the **code after the promise** and its setter | **`John`**, the word the user sees
```
