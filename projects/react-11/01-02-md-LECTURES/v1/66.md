# Lecture 66: How React Keeps a Tab Click Fast While a Slow Tab Renders

*(Why does one slow tab stop every button on the page from answering?)*

> INTERVIEW QUESTION | ❱❱ MORE | What is concurrent rendering, and how does React keep the interface responsive during heavy computation?

---

## VS | A Normal Update vs. an Update Inside `startTransition`: the normal update freezes the page, the Transition lets the next click in

> The browser runs your JavaScript, handles every click, and paints the screen on one main thread, so a slow render freezes the whole page. **`startTransition` marks a state update as a Transition, and React renders a Transition in a way that can be interrupted, so the browser keeps answering clicks**. The slow tab gets no faster, but the browser can handle the user's next click during it, and the screen only ever shows a finished render.

Remember a long loop in plain JavaScript? Put it in a click handler, and the whole page stops for as long as the loop runs:

```js title="Plain JavaScript: a click handler that keeps the browser busy for one second"
slowButton.addEventListener('click', () => {
  const start = performance.now();
  ~while~ (performance.now() - start < 1000) {} // Does nothing for one second, and everything else waits
});
```

Click that button, and then click any other button on the page. Nothing happens for one second. The other click is not lost: it waits, and it runs when the loop is over.

Why? The browser has one main thread. It runs your JavaScript, it runs the click handlers, and it paints the screen, one thing after the other. While the loop runs, the thread is busy, so everything else waits in line.

In React, you would never write that loop in a click handler. But rendering is the same kind of work. Rendering is React calling your component functions, one after the other, on that same main thread.

Take a profile page with a Posts tab that shows 500 posts, each one slow to render. When the user clicks Posts, React has to call 500 slow components. That is a long loop, and the page freezes exactly like the plain JavaScript page.

React gives you a way to say "this update may wait": `startTransition`. You wrap the set function in it:

```jsx title="The same click, as a normal update and as a Transition"
setTab('posts'); // A normal update: React renders the 500 posts in one pass, and the page waits
~startTransition~(() => { // A Transition: React may pause this render and let the next click in
  setTab('posts');
});
```

Both versions put `'posts'` into `tab`. Both show the same 500 posts after the same wait. The difference shows only when the user clicks something else while the posts are still rendering. With the normal update, that click waits. With the Transition, the browser handles it at once.

Keep one sentence in mind for the whole lesson. **A normal update renders to the end without a break. A Transition can be interrupted, and the screen only ever shows a finished render.**

React's docs say it in one line: "A key property of Concurrent React is that rendering is interruptible." Interruptible means that something else can cut in before the render ends.

### The Words This Lesson Stands On

> [!DEFINITION]
> **Rendering and committing.** [REVIEW] React shows a change in two separate steps. Rendering is React calling your components to work out the new JSX. It happens in memory, and a `console.log` in a component body prints here. Committing is React changing the DOM, and only this step changes what the user sees. React's docs compare it to a restaurant: rendering is preparing the dish in the kitchen, and committing is placing it on the guest's table (Lesson 13).

> [!DEFINITION]
> **The main thread.** [NEW] A thread is one line of work that the computer runs one step at a time. The browser runs all the JavaScript of a page on one thread, the main thread, and the same thread handles the user's clicks and paints the screen. MDN says: "The main thread is where a browser processes user events and paints." React renders on this same thread. So while React calls your components, the browser can do nothing else, unless React stops for a moment and gives the thread back (Lesson 66).

> [!DEFINITION]
> **startTransition and a Transition.** [NEW] `startTransition` is a function from the `react` package. You pass it a function of your own, and React calls that function at once, with no arguments. Every state update your function makes while it runs becomes a Transition: React's name for an update that moves the page from one view to another, such as from one tab to the next. `startTransition` itself returns nothing. React's docs: "State updates marked as Transitions will be non-blocking" (Lesson 66).

> [!DEFINITION]
> **Concurrent rendering.** [NEW] In everyday English, two things are concurrent when they are under way at the same time. React's docs use the word in that sense: concurrent rendering "lets React prepare multiple versions of the UI at the same time". The page the user sees now is one version, and the new page that React prepares in memory is another. React may start that render, pause it, continue it, or throw it away. It is not a second thread: React works on the same main thread, and gives it back to the browser between pieces of its own work (Lesson 66).

So concurrent rendering does not open a second kitchen. It is the same one kitchen, but now it can set a slow dish aside when an urgent order comes in. It can come back to the dish later, or throw it away when the guest changes the order. Only a finished dish ever reaches the table.

```tree caption="React's restaurant: in a concurrent render, the one kitchen can set a dish aside or throw it away, and only a finished dish reaches the table."
One kitchen, two kinds of rendering
- !Synchronous rendering | The kitchen finishes the slow dish **before taking any other order** | Every guest **waits** for the slow dish
- +Concurrent rendering | The kitchen can **set the slow dish aside** for an urgent order, or **throw it away** | Only a **finished dish** reaches the table
```

### What Is at Stake

One slow part of the page must not freeze everything around it. With a normal update, every button on the page stops answering while the slow tab renders. React's docs put it plainly: "With synchronous rendering, once an update starts rendering, nothing can interrupt it until the user can see the result on screen."

The user does not know that React is busy. The user sees a button that ignores the click, decides that the page is broken, and clicks again.

And this bug hides well. A developer who tests the tab with one click and a short wait sees the posts appear, and never notices anything wrong. The freeze shows only when the user clicks again during the render.

### The Rule of Thumb: must the page answer clicks while this renders?

**Ask one question about every slow update: must the user be able to click while it renders? If yes, put its set function inside `startTransition`, and keep the update for what the user touched outside it.**

A senior developer also knows the three classic misunderstandings:
1. **"React 18 and React 19 render every update concurrently."** They do not. React's docs say that "Concurrent React is opt-in", and that "it's only enabled when you use a concurrent feature". Opt-in means it stays off until our code asks for it.
2. **"A Transition makes the slow render faster."** It does not. The posts take just as long to render. The Transition only lets more urgent work go first.
3. **"Concurrent means two threads."** It does not. React works on the one main thread, and it gives the thread back to the browser between pieces of its own work.

### Five Ways to Handle a Slow Update

`startTransition` is one tool of five. When one update renders slowly, a senior developer picks one of them:
1. **Leave the update as it is.** This fits a render that is already fast enough. React's docs say: "Don't optimize prematurely!"
2. **Make the render cheaper.** Skip the render with `memo` (Lesson 55), or render fewer rows (Lesson 62). This fits when the slow part can be skipped or cut down.
3. **Mark the update as a Transition**, with `startTransition` in this lesson, or with `useTransition` in Lesson 67. This fits when we own the set function, and the screen really needs to change. React's docs say: "Transitions let you keep the user interface updates responsive even on slow devices."
4. **Defer a value with `useDeferredValue`**, which Lesson 68 teaches. This fits when we do not own the set function, such as when the value arrives as a prop.
5. **Debounce or throttle.** To debounce is to wait until the user stops for a moment. To throttle is to act at most once in a set time. For a slow render, React's docs say they "merely postpone the moment when rendering blocks the keystroke". They are still the right tool when "the work you're optimizing doesn't happen during rendering", such as a network request.

Our tab really needs to change, and we own its set function, so this lesson uses the third way. The rest of the lesson shows it on a real page.

## SECTION | A Profile Page with a Slow Posts Tab

Our page is the profile page that React's docs use for this idea. Three tab buttons sit at the top: About, Posts, and Contact. About shows one short line, and so does Contact. Posts shows a list of 500 posts, and that list is slow to render.


The project keeps four files inside the source folder:

```files title="profile-page: File Explorer" caption="How the files of our profile page sit inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Mounts `App` with `createRoot` inside `<StrictMode>`
  App.jsx | parent | Exports `App` as default and renders `<ProfileTabs />`
  components/
    ProfileTabs.jsx | state | Holds the chosen tab and renders the three buttons and the panel
    PostsTab.jsx | slow child | Exports `PostsTab`, which renders 500 slow posts
```

The entry file mounts the app with `createRoot`, inside Strict Mode (Lesson 07). The complete file is at the end of the lesson. `App` only renders the tabs:

```jsx title="src/App.jsx"
import ProfileTabs from './components/ProfileTabs.jsx';

export default function App() {
  return <ProfileTabs />;
}
```

`PostsTab` is the slow tab from React's docs. It builds 500 posts in a loop, and it never changes in this lesson:

```jsx title="src/components/PostsTab.jsx"
export default function PostsTab() {
  ~console.log~('[ARTIFICIALLY SLOW] Rendering 500 <SlowPost />'); // Prints each time React calls PostsTab

  let items = [];
  for (let i = 0; i < 500; i++) {
    items.push(<SlowPost key={i} index={i} />);
  }
  return <ul className="items">{items}</ul>;
}

function SlowPost({ index }) {
  let startTime = performance.now();
  ~while~ (performance.now() - startTime < 1) {} // Waits 1 millisecond to stand for slow code

  return <li className="item">Post #{index + 1}</li>;
}
```

Three names in this file are new:
1. **`SlowPost`** is a second component, defined below `PostsTab` in the same file. `PostsTab` puts 500 of them in an array, each with its own `key` (Lesson 18).
2. **`index`** is the loop counter `i`, passed to every `SlowPost` as a prop. `Post #{index + 1}` turns the index 0 of the first post into `Post #1`.
3. **`performance.now()`** is a function the browser provides. It returns the time in milliseconds since the page started. The `while` loop keeps calling it until 1 millisecond has passed, and does nothing else. React's docs use this loop "to emulate extremely slow code".

So one render of the Posts tab waits 1 millisecond 500 times: about half a second in all. In development, Strict Mode calls each component twice (Lesson 47), so the wait is about one second.

A real feed or chart is slow for real reasons, such as long text or many shapes. The loop only makes that slowness easy to see.

Now we write `ProfileTabs`, and we fix it in four steps:

**PRINCIPLES:** A normal update renders to the end without a break. A Transition can be interrupted, and the screen only ever shows a finished render. Four principles follow:
1. **Principle 1: A Normal Click on Posts Freezes the Whole Page.** A normal update renders in one pass on the one main thread, so while the 500 posts render, no click on the page is answered.
2. **Principle 2: startTransition Keeps the Page Answering Clicks.** Concurrent rendering is turned on update by update. A state update inside `startTransition` is a Transition, and the browser handles clicks while React renders it.
3. **Principle 3: The Half-Rendered Posts Never Reach the Screen.** React renders in memory and changes the DOM only at the end. A render that is paused or thrown away leaves the page exactly as it was.
4. **Principle 4: The Clicked Tab Turns Bold Before the Slow Posts.** Urgent updates, such as the change a click makes, go before Transitions. One click can make an urgent update for the tab the user touched and a Transition for the slow panel.

## PRINCIPLE | A normal `setTab`: the whole page waits until the slow tab is rendered

> [!PRINCIPLE]
> **Principle 1: Synchronous Rendering: A Normal Click on Posts Freezes the Whole Page**
>
> *An update not marked with a concurrent feature renders in one uninterrupted, synchronous pass; while it runs, the browser handles no click and paints nothing until React has committed the result.*
>
> React renders on the browser's one main thread, the same thread that handles clicks and paints the screen. A normal `setTab('posts')` makes React call all 500 slow posts in one pass, and nothing can interrupt it. So the whole page freezes, not only the Posts panel, and the user's next click waits until the posts are on the page. For a tab that renders in a moment, such as About, a normal update is the right choice.
>
> **DO THIS:**
> ```jsx
> <button onClick={() => ~setTab('about')~}>About</button> // The About line renders in a moment, so a normal update is fine
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button onClick={() => ~setTab('posts')~}>Posts</button> // **WRONG:** 500 slow posts render in one pass, and every click on the page waits
> ```

### The Tabs as Normal Updates

Each tab button calls `setTab` with its own tab name, and the panel shows the tab that `tab` holds. This is the shape of every tab bar we have built so far:

```jsx title="src/components/ProfileTabs.jsx"
import { useState } from 'react';
import PostsTab from './PostsTab.jsx';

export default function ProfileTabs() {
  const [tab, setTab] = useState('about');

  return (
    <section>
      <button onClick={() => setTab('about')}>About</button>
      <button onClick={() => ~setTab('posts')~}>Posts</button> {/* A normal update: renders the 500 posts in one pass */}
      <button onClick={() => setTab('contact')}>Contact</button>
      <hr />
      {tab === 'about' && <p>Welcome to my profile!</p>}
      {tab === 'posts' && <PostsTab />}
      {tab === 'contact' && <p>Contact me at admin@mysite.com</p>}
    </section>
  );
}
```

When the page opens, `tab` holds `'about'`, so the panel shows the About line.

### What Happens After Posts, Then Contact

**A normal click on Posts does not freeze only the Posts panel. It freezes the whole page, and the Contact button stops answering.** Here is what happens when the user clicks Posts and then, at once, Contact:
1. The page shows `Welcome to my profile!`.
2. The user clicks Posts. `setTab('posts')` asks React for a new render (Lesson 13).
3. React calls `ProfileTabs`, then `PostsTab`, then 500 slow posts, and each post waits 1 millisecond. The Console prints the log line of `PostsTab`.
4. While React is still rendering, the user clicks Contact. Nothing happens on the page. The browser keeps the click waiting.
5. React finishes the render and commits it. The 500 posts go into the DOM.
6. Only now does the browser handle the Contact click. React renders the Contact tab, and the Contact line replaces the posts. The posts may show for a moment before it does.

If the user clicks Posts and simply waits, the posts stay. The Console shows the log line twice, because Strict Mode calls `PostsTab` twice in development:

```page width=text caption="The profile page after the user clicks Posts and waits: the top of the list of 500 posts, and the log line printed twice by Strict Mode."
line: [About] [Posts] [Contact]
line: Post #1
line: Post #2
line: Post #3
line: Post #4
log: [ARTIFICIALLY SLOW] Rendering 500 <SlowPost /> | PostsTab.jsx:2
log: [ARTIFICIALLY SLOW] Rendering 500 <SlowPost /> | PostsTab.jsx:2
```

The Contact click was not lost. It waited, just like the click in the plain JavaScript page. But for about a second the page answered nothing, so the user had no way to know that the click would still count. Without Strict Mode, as in a production build, the freeze lasts about half a second.

### Why the Whole Page Freezes: one main thread

MDN describes the main thread in two sentences: "The **main thread** is where a browser processes user events and paints. By default, the browser uses a single thread to run all the JavaScript in your page, as well as to perform layout, reflows, and garbage collection."

React renders on that same thread. So while React calls the 500 `SlowPost` components, the browser cannot do anything else:
- It cannot run the click handler of the Contact button.
- It cannot paint anything at all, anywhere on the page.

React's docs call this default **synchronous rendering**: React renders an update "in a single, uninterrupted, synchronous transaction". A render like this is **blocking**: it keeps the browser from handling the user's input until it is done. MDN names the result: "long-running JavaScript functions can block the thread, leading to an unresponsive page and a bad user experience."

```tree dir=right caption="A normal click on Posts: React renders the posts on the main thread, and the Contact click waits until the render is committed."
One normal update on the main thread
- +1. The user clicks Posts [`setTab`] | React starts **one render** of the Posts tab
- !2. React calls 500 `SlowPost` components | The main thread is **busy** | The Contact click **waits**, and **nothing is painted**
- +3. React commits the posts | The 500 posts **go into the DOM**
- +4. The browser handles the Contact click | The Contact line **replaces the posts**
```

A junior developer says: "Only the Posts panel is slow, so the rest of the page should still work." A senior developer knows that there is no "rest of the page" while the main thread is busy. The panel, the buttons, and every paint wait for the same thread.

### The Real Mistake: Looking for a Bug in the Other Button

This freeze rarely shows up on the developer's own laptop. Here is how it usually reaches users:
1. A developer adds a tab that renders a long feed or a chart.
2. The tab opens fine on a fast laptop, so the developer ships it.
3. On a slower phone, users click the tab, then try to click another one, and the page does not answer for a moment.
4. The developer looks for a bug in the click handler of the other tab.
5. The handler is fine. The main thread was busy rendering the slow tab, and of a synchronous render React's docs say: "nothing can interrupt it".

Remember: a normal update renders to the end without a break, and the whole page waits for it.

## PRINCIPLE | `startTransition`: the browser keeps answering clicks while the slow tab renders

> [!PRINCIPLE]
> **Principle 2: Opt-In Concurrency: startTransition Keeps the Page Answering Clicks**
>
> *Concurrent rendering is turned on update by update; a state update made inside `startTransition` from `react` is a Transition, and the browser can handle clicks while React renders it.*
>
> React renders a normal update synchronously, even in React 19. Only an update marked with a concurrent feature is rendered concurrently. `startTransition` calls our function at once and marks the updates inside it as Transitions. While React renders a Transition, the browser still handles clicks and paints the page. A second Transition waits for the first, so a click on Contact still waits for the posts until Principle 4 adds an urgent update. The posts take just as long to render, but the page stops freezing.
>
> **DO THIS:**
> ```jsx
> function selectTab(nextTab) {
>   ~startTransition~(() => { // A Transition: the browser still handles clicks while the posts render
>     setTab(nextTab);
>   });
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function selectTab(nextTab) {
>   ~setTab(nextTab)~; // **WRONG:** a normal update, so the slow tab still freezes the page in React 19
> }
> ```

### VS | `setTab` Called Directly vs. Inside `startTransition`: the same posts, only one page keeps answering

To make the tabs easier to change, we give them one handler, `selectTab`, and each button passes its own tab name. Here are two ways to write that handler:

```jsx title="With setTab called directly: a normal update"
function selectTab(nextTab) {
  ~setTab(nextTab);~ // Renders the new tab in one pass that nothing can interrupt
}
```

```jsx title="With startTransition: a Transition"
function selectTab(nextTab) {
  ~startTransition~(() => { // Marks setTab as a Transition: the browser still handles clicks during its render
    setTab(nextTab);
  });
}
```

It looks the same, but it is NOT the same thing! Both put the same tab into `tab`. When the user clicks Posts and waits, both show the same 500 posts after the same wait. When the user clicks Contact during that wait, only the version with `startTransition` lets the browser handle the click at once and keep painting the page.

Notice what does not change: the posts do not appear any sooner. `startTransition` makes the render interruptible. It does not make it faster.

### What startTransition Turns On

React has had concurrent rendering since React 18, but it does not use it for every update. It uses it only for updates marked by a **concurrent feature**: an API that turns concurrent rendering on for the updates it marks. There are four of them. Two are `startTransition` and `useTransition`. The other two are `useDeferredValue` and Suspense.

React's docs say it in one line: "there is no concurrent mode, only concurrent features."

```tree caption="Concurrent rendering is turned on update by update: only an update marked with a concurrent feature can be interrupted."
Which updates React renders concurrently
- !A normal update [`setTab`] | Rendered **synchronously** in one pass | **Nothing can interrupt** it
- +An update inside `startTransition` [`startTransition` `setTab`] | Marked as a **Transition** | Rendered **concurrently**, and **the browser handles clicks** during it
```

Concurrent features also need the root that `createRoot` creates (Lesson 07). React's docs say of `createRoot`: "New features in React 18 don't work without it." Our entry file already uses it.

### startTransition on the Profile Page

We import `startTransition`, add `selectTab`, and let each button call it with its own tab name:

```jsx title="src/components/ProfileTabs.jsx" startLine="1"
import { ~startTransition~, useState } from 'react'; // startTransition comes from react
import PostsTab from './PostsTab.jsx';

export default function ProfileTabs() {
  const [tab, setTab] = useState('about');

  function selectTab(nextTab) {
    ~startTransition~(() => { // React calls this function at once and marks setTab as a Transition
      setTab(nextTab);
    });
  }

  return (
    <section>
      <button onClick={() => selectTab('about')}>About</button>
      <button onClick={() => selectTab('posts')}>Posts</button>
      <button onClick={() => selectTab('contact')}>Contact</button>
      <hr />
      {tab === 'about' && <p>Welcome to my profile!</p>}
      {tab === 'posts' && <PostsTab />}
      {tab === 'contact' && <p>Contact me at admin@mysite.com</p>}
    </section>
  );
}
```

`nextTab` is the parameter of `selectTab`. Each button passes its own string, such as `'contact'`. The Posts file does not change.

### What Happens After Posts, Then Contact

**Now the browser handles the Contact click at once, but the Contact line still waits for the posts.** Here is what happens when the user clicks Posts and then, during the render, Contact:
1. The user clicks Posts. React calls our arrow function at once, and `setTab('posts')` inside it becomes a Transition.
2. React starts rendering the Posts tab in the background. The page still shows `Welcome to my profile!`, and nothing on it says that work has started.
3. The user clicks Contact. This time the browser handles the click at once, because React leaves room for the browser between pieces of its work, as Principle 3 shows. `selectTab('contact')` runs, and `setTab('contact')` becomes a second Transition.
4. React does not stop the Posts render for it. A Transition does not interrupt another Transition: only a more urgent update can, as Principle 4 shows. So React finishes the 500 posts and commits them.
5. Right after that, React renders the latest state, `'contact'`, and the Contact line replaces the posts. The posts sit in the DOM only for a few milliseconds, sometimes long enough for the browser to paint them once.

```page width=text caption="The profile page after the user clicks Posts and then Contact during the render: once the posts finish rendering, the Contact line replaces them."
line: [About] [Posts] [Contact]
line: Contact me at admin@mysite.com | good
log: [ARTIFICIALLY SLOW] Rendering 500 <SlowPost /> | PostsTab.jsx:2
log: [ARTIFICIALLY SLOW] Rendering 500 <SlowPost /> | PostsTab.jsx:2
```

So on this page, the user still waits about a second in development for the Contact line, as with the normal update. What changed is that the browser stays free. It runs the click handler at once, and it keeps painting the page while React renders the posts. With the normal update, the browser painted nothing for that whole second.

The Console shows the log line of `PostsTab` twice, once for each call that Strict Mode makes.

### The Page Gives No Sign Yet

One weak spot remains. When the user clicks Posts and waits, nothing on the page changes until the posts are ready. The About line stays, and no button shows that the click was received. React's docs say: "`startTransition` does not provide a way to track whether a Transition is pending." Principle 4 fixes this with a second state variable, and Lesson 67 shows the built-in way, `isPending` from `useTransition`.

### What startTransition Marks, and What It Does Not

`startTransition` marks only the state updates our function makes while it runs. Two limits follow:
1. **An update made later is not marked.** React's docs say: "If you try to perform state updates in a `setTimeout`, for example, they won't be marked as Transitions."
2. **The text of an `<input>` field cannot be updated in a Transition.** React's docs say: "Transition updates can't be used to control text inputs." The text in the field must change on every keystroke. Typing next to a slow list is the subject of Lessons 67 and 68.

In a real app, we often do not write `startTransition` ourselves. React's docs expect most apps to get it from a router or a framework: "router libraries will automatically wrap navigations in startTransition."

### The Real Mistake: Upgrading to React 19 and Changing Nothing

1. A developer upgrades an app to React 19 and reads that React renders concurrently.
2. The developer expects the slow tab to stop freezing the page, and changes nothing else.
3. The page still freezes, because the tab update is still a normal update.
4. React's docs explain why: "Concurrent React is opt-in", and "it's only enabled when you use a concurrent feature".
5. The fix is to mark the tab update as a Transition.

React made concurrency opt-in on purpose. Its docs call concurrent rendering "technically" a breaking change: "Because concurrent rendering is interruptible, components behave slightly differently when it is enabled." So React turns it on only where our code asks for it.

Remember: a normal update renders to the end without a break, and only an update inside `startTransition` can be interrupted.

## PRINCIPLE | A Transition render: the screen never shows half of the posts

> [!PRINCIPLE]
> **Principle 3: Consistent UI: The Half-Rendered Posts Never Reach the Screen**
>
> *React renders a Transition in memory and changes the DOM only at the end, once the whole tree is ready; a render that is paused or abandoned leaves the page exactly as it was.*
>
> Rendering is React calling our components; committing is React changing the DOM. In a concurrent render, React gives the main thread back to the browser between pieces of work, so it keeps every change off the DOM until the render is finished. When a more urgent update comes in, React throws the stale work away, and the page goes straight from the old view to the new one. Because React may throw a render away and do it again, components must stay pure.
>
> **DO THIS:**
> ```jsx
> function SlowPost({ index }) {
>   ~return~ <li className="item">Post #{index + 1}</li>; // Pure: the same JSX whether React keeps this render or throws it away
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> let renderCount = 0;
> function SlowPost({ index }) {
>   ~renderCount++~; // **WRONG:** also counts renders that React throws away, so it no longer matches the screen
>   return <li className="item">Post #{index + 1}</li>;
> }
> ```

### VS | Rendering vs. Committing: the Console prints at once, the page changes only at the end

Look again at the page of Principle 2 while the user clicks Posts and waits. The Console prints the log line of `PostsTab` right after the click, so React has already called `PostsTab`. Yet for about a second the page still shows `Welcome to my profile!`, and then all 500 posts appear at once.

In the reader's mind, rendering a component and changing the page are one step. They are NOT the same thing! React does them in two separate steps (Lesson 13):
- **Rendering** is React calling our components. It happens in memory. The `console.log` in `PostsTab` runs here (Lesson 54).
- **Committing** is React changing the DOM. Only this step changes what the user sees.

In a concurrent render, React can do the first step and never do the second.

```tree dir=right caption="Rendering happens in memory; only the commit changes the DOM, and an abandoned render never reaches the commit."
Two steps between a click and the screen
- +1. Render | React **calls our components** in memory | The `console.log` in `PostsTab` **prints here**
- +2. Commit | React **changes the DOM** | The user **sees the result**
- !An abandoned render | Step 1 runs, **step 2 never does** | The page stays **exactly as it was**
```

Back in the restaurant: the kitchen prepares the whole Posts dish before anything goes to the table, so a half-finished dish is never served. When a more urgent order comes in, the kitchen can also throw the half-finished dish away, and then it never reaches the table at all.

### What the Elements Panel Shows While the Posts Render

React's docs give the rule in two sentences: "React guarantees that the UI will appear consistent even if a render is interrupted. To do this, it waits to perform DOM mutations until the end, once the entire tree has been evaluated." Two words here need a meaning:
- **Consistent** means the page always shows one whole version, never parts of two.
- **DOM mutations** are the changes React makes to the DOM in the commit: adding, changing, and removing elements.

During a concurrent render, React **yields** to the browser. It stops its own work for a moment and gives the main thread back, so the browser can handle a click or paint. React's docs say: "React yields to the browser during concurrent rendering".

**The DOM changes only once, straight from the About line to the whole list of 500 posts.** Here is what happens when the user clicks Posts and waits:
1. The user clicks Posts, and React starts the Transition render of `PostsTab`.
2. The Console prints the log line. React is calling the components.
3. During the render, React yields to the browser. Whatever the browser paints in that moment still has `Welcome to my profile!`, because React has changed nothing in the DOM yet.
4. React finishes calling the 500 `SlowPost` components in memory.
5. React commits the render. The DOM changes once, from the About line to the whole list.

So the Elements panel never holds half a list. Before the click, it holds the About line:

```dom caption="The Elements panel before the click: the section holds the three buttons, the line, and the About paragraph."
<section>
  <button>About</button>
  <button>Posts</button>
  <button>Contact</button>
  <hr>
+ <p>Welcome to my profile!</p> | note: The About line stays while the posts render in memory
</section>
```

After React commits the Posts tab, the same spot holds the whole list, added in one change:

```dom caption="The Elements panel after the Posts tab is committed: the About paragraph is replaced by the whole list of 500 posts, added in one DOM change."
<section>
  <button>About</button>
  <button>Posts</button>
  <button>Contact</button>
  <hr>
+ <ul class="items"> | note: One DOM change, straight from About to all 500 posts
    <li class="item">Post #1</li>
    <li class="item">Post #2</li>
    <li class="item">Post #3</li>
* and 497 more li elements, up to Post #500
  </ul>
</section>
```

### Pause, Abandon, Throw Out

React's docs have three names for what can happen to a render like the Posts render:
1. **Pause and continue**: "React may start rendering an update, pause in the middle, then continue later." Our Posts render did this each time React yielded to the browser.
2. **Abandon**: "It may even abandon an in-progress render altogether." This happens when a more urgent update comes in, as Principle 4 shows.
3. **Stale rendering work**: an unfinished render that a newer update has made out of date, which React "will throw out".

### Why the Rule Matters More in a Concurrent Render

A junior developer says: "If React stops in the middle of rendering 500 posts, some of them must already be on the page." A senior developer knows why none of them can be.

In a synchronous render, the browser cannot paint in the middle anyway, because the main thread is busy until the render ends. In a concurrent render, React yields the thread to the browser, and the browser can paint in that moment.

If React changed the DOM as it went, the user would see a page that is half old and half new. Think of 200 posts under the About line. So React keeps every change in memory until the whole tree is ready, and then commits it in one step.

### The Real Mistake: Code in the Component Body That Changes Something Outside It

This rule has a cost for our own code. React may now call a component for a render that the user never sees.
1. A developer writes code in a component body that changes something outside the component. For example, it adds 1 to a counter declared outside it, or sends a log line to a server.
2. With synchronous rendering, every render was committed, so the code seemed to run once per change on the page.
3. With a Transition, React may render the component, throw that render away, and render it again.
4. The outside change now happens for renders the user never saw. The counter or the server log no longer matches the screen.
5. React's docs warn: "Because concurrent rendering is interruptible, components behave slightly differently when it is enabled."

The fix is the rule of Lesson 14: keep the component pure, and put changes to the outside world in event handlers or Effects. Strict Mode helps find these bugs in development, because it calls each component twice (Lesson 47). React's docs say: "You can use `<StrictMode>` to help surface concurrency-related bugs during development."

Remember: a Transition can be interrupted, and the screen only ever shows a finished render.

## PRINCIPLE | `setSelected` outside `startTransition`: the clicked tab answers before the slow posts

> [!PRINCIPLE]
> **Principle 4: Priorities: The Clicked Tab Turns Bold Before the Slow Posts**
>
> *Keep the update for what the user touched outside `startTransition`; React renders and commits urgent updates first, and an urgent update interrupts a Transition that is under way.*
>
> React gives each update a priority. A normal update from a click is urgent, and a Transition waits for it. So one click can make two updates: an urgent one that shows the user the click was received, such as a bold tab, and a Transition for the slow panel. During the Transition render, React yields to the browser, so the next click is handled at once and interrupts the slow work.
>
> **DO THIS:**
> ```jsx
> function selectTab(nextTab) {
>   ~setSelected(nextTab);~ // Urgent: the clicked tab turns bold at once
>   startTransition(() => {
>     setTab(nextTab);
>   });
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function selectTab(nextTab) {
>   startTransition(() => {
>     ~setSelected(nextTab);~ // **WRONG:** the bold tab now waits for the 500 slow posts
>     setTab(nextTab);
>   });
> }
> ```

### VS | `setSelected` vs. `setTab` Inside `startTransition`: the same tab name, two priorities

Principle 2 left one weak spot. When the user clicks Posts, nothing on the page answers until the posts are ready, and a click on Contact waits for them too. Real tab bars answer at once. The tab the user clicked turns bold right away, and the panel under it follows when it is ready.

That takes two updates from one click. React's docs say: "a single user input should result in both an urgent update and a non-urgent one." So `selectTab` sets two state variables:

```jsx title="Two updates from one click"
function selectTab(nextTab) {
  ~setSelected(nextTab);~ // An urgent update: the clicked tab turns bold at once
  startTransition(() => {
    ~setTab(nextTab);~ // A Transition: the panel follows when its render is finished
  });
}
```

Both lines run in the same click, and both put the same tab name into a state variable. It looks the same, but it is NOT the same thing!
- **`setSelected(nextTab)`** is an urgent update. React renders and commits it at once.
- **`setTab(nextTab)` inside `startTransition`** is a Transition. React commits it when its render is finished, and an urgent update can interrupt it.

> [!DEFINITION]
> **An urgent update.** [NEW] An urgent update is a normal update, made outside `startTransition`, such as `setSelected('posts')` in a click handler. React's docs say: "Urgent updates reflect direct interaction, like typing, clicking, pressing, and so on." React gives each update a priority, its place in the order in which React handles updates, and urgent updates come first. When an urgent update arrives during a Transition render, React stops that render, handles the urgent update, and comes back to the Transition after it (Lesson 66).

```tree caption="One click makes two updates: an urgent one for the tab the user touched, and a Transition for the slow panel."
One click on Posts, two updates
- +Urgent update [`setSelected`] | React renders and commits it **at once** | The Posts tab **turns bold** right after the click
- +Transition [`startTransition` `setTab`] | React renders it **after the urgent update** | The posts **replace the About line** when the render is finished
```

### Two State Variables on the Profile Page

We add a second state variable, `selected`. It holds the tab the user clicked last, while `tab` holds the tab the panel shows. The two differ only while a Transition is under way:

```jsx title="src/components/ProfileTabs.jsx" startLine="4"
export default function ProfileTabs() {
  const [selected, setSelected] = ~useState('about')~; // The tab the user clicked last
  const [tab, setTab] = useState('about'); // The tab the panel shows

  function selectTab(nextTab) {
    ~setSelected(nextTab);~ // Urgent: the clicked tab turns bold at once
    startTransition(() => {
      ~setTab(nextTab);~ // Transition: the panel follows
    });
  }
```

Each tab now reads `selected`. The selected tab shows its name in bold with `<b>`, the HTML tag for bold text, as React's docs do on this page. The other two tabs stay buttons. Each line chooses between the two with a ternary (Lesson 10):

```jsx title="src/components/ProfileTabs.jsx" startLine="17"
      {selected === 'about' ? <b>About</b> : <button onClick={() => selectTab('about')}>About</button>}
      {~selected === 'posts'~ ? <b>Posts</b> : <button onClick={() => selectTab('posts')}>Posts</button>} {/* Bold text while selected holds 'posts', a button otherwise */}
      {selected === 'contact' ? <b>Contact</b> : <button onClick={() => selectTab('contact')}>Contact</button>}
```

The Posts file does not change.

### What the User Sees After Posts, Then Contact

When the page opens, the About tab is bold text, and the other two tabs are buttons:

**The tab the user touched always answers at once, and the slow panel never blocks it.** Here is what happens when the user clicks Posts and then, during the render, Contact:
1. The page shows `Welcome to my profile!`, and the About tab is bold.
2. The user clicks Posts. React receives two updates: `selected` as an urgent update, and `tab` as a Transition.
3. React renders and commits the urgent update first. The Posts tab turns bold, while the panel still shows `Welcome to my profile!`.
4. React starts the Transition render of the 500 posts, and it yields to the browser during that render, as Principle 3 showed.
5. The user clicks Contact. `setSelected('contact')` is a new urgent update, and it interrupts the Posts render. The Contact tab turns bold at once.
6. React renders the latest Transition, `'contact'`, and the panel shows `Contact me at admin@mysite.com`. No post ever appears.

Right after the Posts click, the page shows the new bold tab over the old panel:

```page width=text caption="Right after the Posts click: the Posts tab is bold, and the panel still shows the About line while the posts render in memory."
line: Welcome to my profile!
log: [ARTIFICIALLY SLOW] Rendering 500 <SlowPost /> | PostsTab.jsx:2
log: [ARTIFICIALLY SLOW] Rendering 500 <SlowPost /> | PostsTab.jsx:2
```

After the Contact click, the Contact tab is bold, and the panel skips straight to the Contact line:

```page width=text caption="After the Contact click: the Contact tab is bold, and the panel shows the Contact line without ever showing a post."
line: [About] [Posts] Contact

log: [ARTIFICIALLY SLOW] Rendering 500 <SlowPost /> | PostsTab.jsx:2

```

The Console still shows the log line of the Posts render. React called `PostsTab`, and then threw that render away. This is Principle 3 in action: the render happened in memory, and it never reached the DOM.

A junior developer says: "React renders updates in the order the code calls the set functions." A senior developer knows that React renders by priority. React's docs say: "Updates wrapped in startTransition are handled as non-urgent and will be interrupted if more urgent updates like clicks or key presses come in."

### Where the Priorities Show: the Scheduler track

Our code never names a priority. React does, in the browser's Performance panel, on the Scheduler track of React's Performance tracks (Lesson 64). These tracks are available only in development and profiling builds. React's docs say: "The Scheduler is an internal React concept used for managing tasks with different priorities." The track has four subtracks, one for each priority:
1. **Blocking**: "The synchronous updates, which could've been initiated by user interactions." Our `setSelected` belongs here.
2. **Transition**: "Non-blocking work that happens in the background, usually initiated via `startTransition`." The render of our posts belongs here.
3. **Suspense**: "Work related to Suspense boundaries, such as displaying fallbacks or revealing content." Lesson 69 teaches Suspense.
4. **Idle**: "The lowest priority work that is done when there are no other tasks with higher priority."

```tree caption="The four subtracks of the Scheduler track, from the most urgent priority to the lowest."
The Scheduler track in the Performance panel
- +Blocking | **Synchronous updates**, often from user interactions | Our **`setSelected`** on each click
- +Transition | **Non-blocking work** in the background | Our **render of the 500 posts**
- +Suspense | Work for **Suspense boundaries** | Fallbacks and revealed content
- +Idle | The **lowest priority** work | Done when **nothing else** is waiting
```

### The Real Mistake: Wrapping the Whole Handler in startTransition

1. A developer learns that `startTransition` keeps the page from freezing.
2. The developer wraps the whole handler in it, both `setSelected` and `setTab`.
3. The click no longer shows anything at once. The bold tab now waits for the slow posts.
4. The user thinks the click was missed, and clicks again.
5. React's docs explain why this feels broken: "Urgent updates like typing, clicking, or pressing, need immediate response to match our intuitions about how physical objects behave. Otherwise they feel 'wrong'."

The fix is to keep the update for what the user touched outside `startTransition`, and to put only the slow part inside it.

Remember: what the user touched is urgent and goes first, and the slow part goes inside `startTransition`.

| :--- | :--- | :--- |
| **A slow update** | Call the set function directly and expect only the slow tab to be slow, so the whole page freezes | A normal update renders synchronously on the one main thread, and nothing can interrupt it |

## For the Interview

> **The Interview Question:** What is concurrent rendering, and how does React keep the interface responsive during heavy computation?

### How to Answer Clearly in 30 Seconds

"Concurrent rendering is React's way of rendering an update so that the render can be interrupted: React may start it, pause it, continue it, or abandon it. By default, React renders an update synchronously, in one pass that nothing can interrupt. The browser has one main thread for JavaScript, clicks, and painting, so a slow synchronous render freezes the whole page until React commits it. Concurrency is opt-in for each update: we mark an update with a concurrent feature, such as `startTransition`. Three facts keep the page responsive:
1. **React yields to the browser during a concurrent render**, so the browser can handle a click in the middle of it. That click's urgent update interrupts the Transition.
2. **React changes the DOM only at the end**, once the whole tree is ready, so the user never sees an incomplete screen. React throws stale work away.
3. **Urgent updates go first.** One click can make an urgent update for what the user touched and a Transition for the slow part.

Concurrent rendering does not make the slow render faster. It lets more urgent work go first."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does a Transition make the slow render faster, and how is it different from debouncing?"**
   It does not make anything faster. The 500 posts take just as long to render. React's docs say of a slow list: "This does not make re-rendering of the `SlowList` faster. However, it tells React that re-rendering the list can be deprioritized".

   Debouncing waits a fixed time and then renders in one blocking pass, so the page still freezes at the end of the wait. React's docs say that debouncing and throttling "merely postpone the moment when rendering blocks the keystroke". A Transition has no fixed delay. On a fast device the slow part shows almost at once, and on a slow device it lags behind. In both cases, an urgent update from the user's next click makes React abandon the render.
2. **"How do priority lanes work?"**
   Lanes is the interviewer's word for React's priorities. React's docs keep the inner structure out of sight: "React uses sophisticated techniques in its internal implementation, like priority queues and multiple buffering. But you won't see those concepts anywhere in our public APIs."

   What we can see is the result. React renders urgent updates, such as typing, clicking, and pressing, first. Transitions render in the background, and an urgent update interrupts them when it comes in. The Scheduler track in the Performance panel shows four priorities: Blocking, Transition, Suspense, and Idle.

   React still works on one thread. JavaScript runs each function to the end before any other code runs, which MDN calls run-to-completion, so React can only yield between pieces of its own work. One component that takes half a second by itself cannot be cut in the middle.
3. **"Why does concurrent rendering require components to be pure?"**
   Because React may now render a component, throw that render away, and render it again. A component that changes something outside itself during render, such as a counter, makes that change even for renders the user never sees. React's docs say: "Because concurrent rendering is interruptible, components behave slightly differently when it is enabled." That is why concurrency is opt-in, and why Strict Mode calls each component twice in development: it helps find these bugs before users do.

```tree caption="Interview summary: a normal update blocks the page, a Transition can be interrupted, and an urgent update goes first."
How React keeps the page responsive
- !A normal update [`setTab`] | Rendered **synchronously** on the one main thread | A slow render **freezes the whole page**
- +A Transition [`startTransition`] | Rendered **concurrently**; React **yields** to the browser | **Interruptible**, and committed **only when finished**
- +An urgent update [`setSelected`] | Rendered and committed **first** | Shows the user **at once** that the click was received
```
