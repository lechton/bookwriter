# Lecture 81: How an Error Report Names the Component That Wrote the Tag

*(When the error names a component that has no bug, how do you find the component that does?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How does captureOwnerStack pinpoint which component caused a render or error?

---

## VS | The Component Stack vs. the Owner Stack: both list the components above the error, only the Owner Stack names who wrote the tag

> In plain JavaScript, when a function crashes, the error also names the function that called it, so you can see where the bad value came from. **In React, a component never calls the components it shows: it only writes their tags, so the error names the crashing component and then only React's own functions**. `captureOwnerStack()` gives you the missing name: the component that wrote the tag and passed the bad props.

Remember the red error in the Console? Under the message, the browser prints a list of lines that start with `at`. The function that crashed is on top. One line down is the function that called it, then the function that called that one, and so on. This list is the **stack trace**, and each `at` line is a **frame**.

Here is a plain function that formats a price, and a function that calls it with no amount:

```js title="Plain JavaScript: the caller is in the stack trace"
function formatPrice(amount) {
  return '$' + ~amount.toFixed(2)~; // Throws: amount is undefined
}

function showCart() {
  ~formatPrice()~; // The bug: showCart calls formatPrice with no amount
}

showCart();
```

`toFixed(2)` is the JavaScript method that writes a number with two decimals, so 12 becomes `12.00`. Here the amount is `undefined`, there is no number to write, and the browser throws a `TypeError`:

```devconsole width=full caption="A plain JavaScript error: the caller is one line down."
x Uncaught TypeError: Cannot read properties of undefined (reading 'toFixed')
  at formatPrice
  at showCart
```

The bug is in `showCart`, and `showCart` is right there, one line down. You open it, and you fix it.

### The same price in React

Now write the same price as a component. `ProductList` shows it with a tag:

```jsx title="A component that writes a tag, and the component behind the tag"
function Price({ amount }) {
  return <span>${~amount.toFixed(2)~}</span>; // Throws: amount is undefined
}

function ProductList() {
  return <li>Cap ~<Price />~</li>; // The bug: a Price tag with no amount
}
```

The bug is the same: `ProductList` gave `Price` no amount. But the stack trace is not the same:

```devconsole width=full caption="The same error in React: Price, then only React's own functions."
x Uncaught TypeError: Cannot read properties of undefined (reading 'toFixed')
  at Price
  at Object.react_stack_bottom_frame
  at renderWithHooks
  at updateFunctionComponent
  at ...
```

`ProductList` is not in it. Why? Because `ProductList` never called `Price`. It wrote a tag, returned it, and finished. Later, React called `Price` (Lesson 13). So the function one line under `Price` is React's own code, not your component. These React lines are what developers call "library frames".

### The component that wrote the tag: the owner

So the name we need is the component that wrote the `<Price />` tag. React's docs call it the **owner** of this `Price`. In development, React keeps a record of which component wrote each tag, and one function reads it:

```jsx title="Reading the record of who wrote each tag"
import { captureOwnerStack } from 'react';

console.log(~captureOwnerStack()~); // A string: the owner first, then the owner's owner, up to App
```

`captureOwnerStack()` returns a short text with one `at` line per step. The first line is the owner. Then comes the owner's owner, and so on, up to the top of the app. React's docs call this list the **Owner Stack**.

### Two lists for the same error

Now picture a real online shop. Every price on the site comes from one small component, `Price`. The shop uses it on the home page, in the cart, and on every product page: in a big app, two hundred places.

One morning, the user opens the home page and sees nothing at all:

```page caption="What the user sees when the shop page opens: a blank page."
blank
```

The Console names `Price`. But the file of `Price` is three lines long, and it has no bug. Somewhere, one of those two hundred places wrote a `<Price />` tag with no amount. Which one?

React can give you two lists of names for this error. The first one you already know: the Owner Stack. The second one is the **Component Stack**. Here they are, for the same broken `Price`:

```devconsole width=full caption="The Component Stack of the Price error: every component and tag around Price."
  at Price
  at li
  at ul
  at ProductList
  at main
  at Layout
  at App
```

```devconsole width=full caption="The Owner Stack of the same error: only the components that wrote the tags."
  at http://localhost:5173/src/ProductList.jsx:16:19
  at Array.map
  at ProductList
  at App
```

Both lists start with `at`, both come from React, and both describe the same failing `Price`. **It may look the same, or work the same at first, but it is NOT the same thing!**
- **The Component Stack** follows where `Price` sits on the page. It lists `Price`, then every component and every HTML tag around it, up to `App`.
- **The Owner Stack** follows who wrote the tags. Its first line points into the file of `ProductList`, at the exact line of the `<Price />` tag. Then come `ProductList` and `App`. No layout and no HTML tag is in it.

Why does that first line have no name? The `<Price />` tag sits inside an arrow function, the one that the product list passes to `products.map`. An arrow function has no name, so React prints its file and its line. `Array.map` on the next line is the method that calls that arrow function.

So the Owner Stack points at the file of `ProductList`, the file to open.

```tree caption="The Component Stack follows where Price sits; the Owner Stack follows who wrote the tags."
Two lists of names for the same `Price` error
- +Component Stack [`errorInfo.componentStack`] | Follows **where `Price` sits** on the page | Lists `Price`, `li`, `ul`, `ProductList`, `main`, `Layout`, and `App`
- +Owner Stack [`captureOwnerStack`] | Follows **who wrote the tags** | Names only **`ProductList`** and **`App`**; its first line points at the `Price` tag to fix
```

### The Words of This Lesson

This lesson builds on three earlier ideas:

> [!DEFINITION]
> **The children prop.** [REVIEW] When you write tags between the opening and the closing tag of a component, such as `<Layout><ProductList /></Layout>`, React passes them to that component in a prop named `children`, and the component decides where to place them, such as inside its `<main>` (Lesson 09).

> [!DEFINITION]
> **An error that nothing catches.** [REVIEW] When a component throws during render and no Error Boundary catches the error, React removes the whole page from the root div, so the user sees a blank page (Lesson 72).

> [!DEFINITION]
> **The development build and the production build.** [REVIEW] While you work, Vite runs the development build of React, with extra checks and helpful messages; the version real users get is the production build, which is smaller and faster and leaves those extras out (Lesson 47).

### Where Readers Usually Go Wrong

Readers take the component right above the failing one in the tree as the one that created it. Often it is not. A layout that renders `children` only holds what another component wrote. The HTML tags around it, such as `<main>` and `<li>`, only hold it too.

### Three Lists of Names for One Error

So for one error, the browser and React give us three lists of names. Each one fits a different job:
1. **The error's own stack, `error.stack`.** The browser puts it on every JavaScript error. It names the component that threw, then React's functions. It fits a bug inside the component that threw.
2. **The Component Stack, `errorInfo.componentStack`.** React gives it to the error handlers of the root and to `componentDidCatch`. It lists every parent in the tree. It fits production, because it is the only React list that exists there.
3. **The Owner Stack, `captureOwnerStack()`.** It lists only the owners. It fits development, while React runs your code: during render, in Effects, in React event handlers, and in React's error handlers.

```tree caption="Three lists of names for one error, and where each one fits."
Three lists of names for one error
- +1. The error's own stack [`error.stack`] | Names the component that threw, **then React's functions** | Fits a bug **inside** the component that threw
- +2. The Component Stack [`errorInfo.componentStack`] | Lists **every parent** in the tree | Fits **production**, where it is the only React list
- +3. The Owner Stack [`captureOwnerStack`] | Lists **only the owners** | Fits **development**, while React runs your code
```

### The Rule of Thumb: who wrote the tag?

**Ask one question about every error: which component wrote the tag of the component that crashed? In development, `captureOwnerStack()` names it first. In production, there is no Owner Stack, so your error report sends the Component Stack.**

## SECTION | A Shop Page That Goes Blank

Our page is the shop from above, made small. It has the heading `Shop` and a list of two products. The data is two objects, and the second one arrives without a price:

```js title="The two products"
const products = [
  { id: 1, name: 'Mug', price: 12 },
  { id: 2, name: ~'Cap'~ }, // The Cap product has no price field
];
```

The user does one thing: the user opens the page.

What is at stake is how long the user looks at a blank page. When a shared component such as `Price` throws, React removes the whole page (Lesson 72). The user sees nothing until the developer finds the line to fix. Without the Owner Stack, the developer usually opens two wrong files first:
1. The error's own stack names `Price`, then React's functions. The developer opens the file of `Price`, and it has no bug.
2. The Component Stack names every component around `Price`. The developer opens the nearest one above it. On a real page, that is often a layout that only places what it received, with no bug either.
3. Only then does the developer find `ProductList`, the component that passed no amount.

The Owner Stack names `ProductList` first.

The project has five files under `src/`. The entry file mounts `App` without Strict Mode, as the samples in React's docs do, so every log in this lesson prints once (Lesson 47):

```files title="shop: File Explorer" caption="How the files of our shop sit inside src/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Mounts `App` into `#root`, and later passes the error handlers to `createRoot`
  App.jsx | parent | Writes `<Layout><ProductList /></Layout>`
  Layout.jsx | default export | Returns `<main>` with the `Shop` heading and its `children`
  ProductList.jsx | default export | Holds `products` and writes one `<li>` with a `<Price />` per product
  Price.jsx | default export | Shows one amount, such as `$12.00`
```

**PRINCIPLES:** An error names the component that threw, but the code to fix is usually in the component that wrote its tag. Five principles follow that path, from the tag to the production report:
1. **Principle 1: The owner wrote the tag; the parent only holds it.** `App` writes the `<ProductList />` tag, so it is the owner. `Layout` receives that element as `children`, so it is only the parent.
2. **Principle 2: The error's own stack names `Price`, then React.** `ProductList` never calls `Price`. React does, so `ProductList` is not in the error's stack.
3. **Principle 3: The Component Stack lists every parent; the Owner Stack lists only the owners.** In the root's error handler, `errorInfo.componentStack` lists everything around the failing price. `captureOwnerStack()` lists only the product list and the app.
4. **Principle 4: `captureOwnerStack()` answers only while React runs your code.** It gives a list during render, in Effects, in React event handlers, and in React's error handlers. It gives `null` in a timer callback, or in a listener added with `addEventListener`.
5. **Principle 5: In production, there is no Owner Stack.** `captureOwnerStack` exists only in the development build. Production reports send `errorInfo.componentStack` instead.

## PRINCIPLE | `<ProductList />` inside `App`: the component that writes the tag is the owner, not the layout that holds it

> [!PRINCIPLE]
> **Principle 1: Owner and Parent: The Owner Is the Component Whose JSX Wrote the Tag**
>
> *The owner of an element is the component that wrote its tag; a component that only renders `children`, and every HTML tag, is a parent but not the owner.*
>
> A layout sits right above the content of almost every page, so it looks like the component that created that content. It did not. It received the content in `children` and placed it. When you look for the component that wrote a tag, you look for the owner, and the owner can sit several levels higher in the tree.
>
> **DO THIS:**
> ```jsx
> function App() {
>   return <Layout>~<ProductList />~</Layout>; // App wrote this tag: look in App for what ProductList receives
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Layout({ children }) {
>   return <main>~{children}~</main>; // **WRONG:** searching Layout for the ProductList tag; Layout only forwards children
> }
> ```

Here are the two components that sit above `ProductList`:

```jsx title="Two components above ProductList"
function App() {
  return <Layout>~<ProductList />~</Layout>; // App writes the ProductList tag
}

function Layout({ children }) {
  return <main>~{children}~</main>; // Layout places whatever it received
}
```

On the page, the list sits inside the `<main>` that `Layout` returns. So `Layout` looks like the component that created `ProductList` (Lesson 06).

### VS | `Layout` vs. `App`: both sit above `ProductList`, only `App` wrote its tag

**It may look the same, but it is NOT the same thing!**
- **`Layout` is the parent of `ProductList`.** The list sits inside it. But no line of `Layout` writes the `<ProductList />` tag. `Layout` only places the `children` it received (Lesson 09).
- **`App` is the owner of `ProductList`.** The `<ProductList />` tag is written inside the JSX of `App`.

Remember the word from the start: React's docs define the owner of an element as the component whose JSX wrote its tag. They also say it in plain words: `ProductList` is "created by" `App`. The parent and the owner can be two different components, as they are here.

React's docs also have a word for what `Layout` does with an element it did not write: it **forwards** it. `Layout` holds the `<ProductList />` element and places it, but it did not write a single character of it. The HTML tags around `ProductList`, such as `<main>`, forward it in the same way. React's docs call these tags **DOM components**, and a DOM component is never an owner.

### Why `ProductList` sits under `Layout` but belongs to `App`

This is surprising, because the tree puts `ProductList` under `Layout`. The order in which React runs the two components explains it:
1. React calls `App`. `App` returns `<Layout><ProductList /></Layout>`.
2. The `<ProductList />` element is created right there, inside `App`, before the layout runs.
3. React calls `Layout` and passes that finished element in its props, under the name `children`.
4. `Layout` returns the element inside `<main>`.
5. In the tree, the product list now sits under `Layout` and its `<main>`. Its owner is still `App`, the component that wrote the tag in step 1.

```tree caption="The parent is where an element sits; the owner is the component whose JSX wrote its tag."
Two components above `ProductList`
- +`App`: the owner [`<Layout><ProductList /></Layout>`] | **Writes** the `<ProductList />` tag in its JSX | React's docs: `ProductList` is **created by `App`**
- +`Layout`: the parent [`<main>{children}</main>`] | **Receives** the element in `children` and places it | Only **forwards** the element; it is **not** the owner
```

## PRINCIPLE | `error.stack`: names the component that threw, then only React's functions

> [!PRINCIPLE]
> **Principle 2: The Error's Stack: React Calls the Component, So the Tag's Author Is Not on the Stack**
>
> *When a component throws during render, the error's stack names that component and then React's functions; the component that wrote its tag is not on it.*
>
> A component never calls the components it shows. It returns their tags and finishes, and React calls them later. So the error's own stack tells you which component threw, but not which component passed it the bad props. The file the error names is where the crash happened, and often not where the bug is.
>
> **DO THIS:**
> ```jsx
> <li key={product.id}>
>   {product.name} ~<Price amount={product.price} />~ {/* Fix it here: ProductList passed undefined for Cap */}
> </li>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function Price({ amount }) {
>   return <span>${~(amount || 0)~.toFixed(2)}</span>; // **WRONG:** Cap now shows $0.00, and the missing price stays hidden
> }
> ```

In plain JavaScript, while a function runs, JavaScript keeps a list of the functions that are running right now. Each function sits on top of the function that called it. This list is the **call stack**. When an error is thrown, the browser copies it into the error as `error.stack`: the stack trace you met at the start.

So the stack trace can only name functions that really called each other. That is the whole story of this principle.

### VS | `Price()` vs. `<Price />`: both mention `Price`, only the call puts `ProductList` on the stack

Many developers read the `<Price />` tag as if the product list called `Price()`. **It may look the same, but it is NOT the same thing!**
- **A call such as `Price()`** would run the price component right now, inside `ProductList`, and put `ProductList` on the stack. React's docs forbid it: never call a component function yourself.
- **A tag such as `<Price />`** only describes what to show. `ProductList` returns it and finishes. React calls `Price` later (Lesson 13).

So when `Price` throws, the function under it on the stack is React's own code, such as `renderWithHooks`. These are the "library frames" that the interview question talks about.

```tree dir=right caption="A plain call keeps the caller on the stack; a JSX tag hands the call to React, so the stack continues with React."
Who sits under the failing function on the stack
- +Plain JavaScript call [`formatPrice` inside `showCart`] | `showCart` **calls** `formatPrice` | The stack reads `at formatPrice`, then **`at showCart`**
- !JSX tag [`<Price />` inside `ProductList`] | `ProductList` **returns** the tag and finishes; **React calls** `Price` | The stack reads `at Price`, then **React's functions** such as `renderWithHooks`; `ProductList` is **not there**
```

`ProductList` writes a `<Price />` tag in every row and passes the price of the product:

4. React calls `Price` for the Mug row, and it returns `$12.00`.
5. React calls `Price` for the Cap row. `amount.toFixed(2)` throws a `TypeError`.

### The fix that hides the bug

The Console points at `Price`, so the developer fixes `Price`, and the real bug stays hidden. Here is how it usually goes:
1. The page goes blank, and the Console names `Price`.
2. The developer opens the file of `Price` and makes it safe for a missing amount, so it shows `0`.
3. The page comes back, and the Cap row now says `$0.00`.
4. The real bug, a product that arrived without a price, is still in the data of `ProductList`. Nothing points to it anymore, and the user sees a wrong price.

The stack named `Price` because it threw, not because it is wrong. To find the line that passed no amount, we need the component that wrote the `<Price />` tag. The next principle shows where React gives us that name.

## PRINCIPLE | `captureOwnerStack()` in `onUncaughtError`: only the components that wrote the tags, not every parent

> [!PRINCIPLE]
> **Principle 3: Two Stacks: The Component Stack Lists Every Parent, the Owner Stack Lists Only the Owners**
>
> *`errorInfo.componentStack` lists the failing component and everything above it; `captureOwnerStack()` lists only the components that wrote the tags on the way to it.*
>
> React gives both lists to the error handlers of the root. The Component Stack answers "where did it break?", and on a real page it is long. The Owner Stack answers "whose code passed the bad props?", and its first name is the component to open.
>
> **DO THIS:**
> ```jsx
> createRoot(document.getElementById('root'), {
>   onUncaughtError: (error, errorInfo) => {
>     console.log(~captureOwnerStack()~); // ProductList first: the component that wrote the Price tag
>   },
> }).render(<App />);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const root = createRoot(document.getElementById('root'));
> root.render(<App />, ~{ onUncaughtError }~); // **WRONG:** render takes one argument; React logs an error and never calls the handler
> ```

So far, the entry file mounts `App` the usual way (Lesson 07):

```jsx title="src/main.jsx"
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(~document.getElementById('root')~).render(<App />); // One argument: the root div
```

`createRoot` also takes a second argument, an object. React's docs call its fields the **root options**. Three of them are functions that React calls when something goes wrong:
1. **`onUncaughtError`**: React calls it when an error is thrown and no Error Boundary catches it. Our Cap error is this kind.
2. **`onCaughtError`**: React calls it when an Error Boundary catches an error.
3. **`onRecoverableError`**: React calls it when React recovers from an error by itself.

React calls each of them with two arguments: the `error`, and an object named `errorInfo`. The Component Stack is inside it, in `errorInfo.componentStack`.

Here is the root with `onUncaughtError`. It logs the two lists from the start of this lesson, one after the other:

```jsx title="src/main.jsx"
import { captureOwnerStack } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root'), {
  ~onUncaughtError~: (error, errorInfo) => { // React calls it with the error and errorInfo
    console.log(~errorInfo.componentStack~); // 1. The Component Stack
    console.log(~captureOwnerStack()~); // 2. The Owner Stack
  },
}).render(<App />);
```

`captureOwnerStack` comes from `react` with a named import (Lesson 05). It takes no arguments. It reads the Owner Stack that React holds at that moment, and returns it as a string.

One detail from React's docs: these options replace React's own handlers, and React's own handlers are the ones that log every error to the Console. So the Console now shows only our two logs. The page is still blank:

```devconsole width=full caption="The Console with onUncaughtError: the Component Stack first, then the Owner Stack."
  at Price | 1. errorInfo.componentStack
  at li
  at ul
  at ProductList
  at main
  at Layout
  at App
  at http://localhost:5173/src/ProductList.jsx:16:19 | 2. captureOwnerStack()
  at Array.map
  at ProductList
  at App
```

In the real Console, each line also ends with the file and the position of its code. The figures in this lesson leave that part out, except on the first line of the Owner Stack, which has nothing else.

### VS | `errorInfo.componentStack` vs. `captureOwnerStack()`: both come from the same handler, only the Owner Stack skips what was only forwarded

The two logs look like one list printed twice, once long and once short. **It may look the same, but it is NOT the same thing!**
- **The Component Stack** lists the failing component and every component and HTML tag above it in the tree. React's docs describe it as the component that threw and "all its parent components".
- **The Owner Stack** lists only the components that wrote the tags on the way to the failing component.

React's docs give three reasons why the Owner Stack is so short:
1. The layout and the HTML tags around the row, such as `<main>` and `<li>`, only forwarded the element, so they are not owners.
2. The Mug row is a sibling of the Cap row. It is not on the way to the failing `Price`, so neither list has it.
3. `Price` itself is left out, because the error's own stack already names it.

So the Owner Stack names `ProductList`, then `App`. Its first line, the arrow function inside `products.map`, gives the exact line of the `<Price />` tag that passes the price. That line of the file of `ProductList` is the line to fix.

```tree caption="The same Price error read through the Component Stack and through the Owner Stack."
The two lists for the Cap error
- !Component Stack [`errorInfo.componentStack`] | Starts with **`Price`**, the component that threw | Then **every parent**: `li`, `ul`, `ProductList`, `main`, `Layout`, `App`
- +Owner Stack [`captureOwnerStack`] | Starts with **`ProductList`**, the component that **wrote the `Price` tag** | Then **`App`**, which wrote the `ProductList` tag; nothing that only forwarded
```

### Reading the Component Stack from the top

On our small page, `ProductList` is the fourth line of the Component Stack. On a real page, many more lines stand between the failing component and its owner: layouts, cards, wrappers, and HTML tags. Here is what happens when a developer reads that list from the top:
1. The first line is the component that threw, which has no bug.
2. The next lines are HTML tags.
3. The first component name after them is often a layout that only forwards `children`. The developer opens it, and the bug is not there.
4. The component that wrote the tag is further down the list.

The Owner Stack skips steps 1 to 3. Its first line points into the owner.

### The same two lists in an Error Boundary

An Error Boundary gets the same Component Stack. Its `componentDidCatch` method receives it in `info.componentStack` (Lesson 72). React's docs log it next to `captureOwnerStack()`. `logErrorToMyService` is the docs' name for the function that sends both to a server:

```jsx title="Logging both lists from an Error Boundary"
componentDidCatch(error, info) {
  logErrorToMyService(error, ~info.componentStack~, ~captureOwnerStack()~); // Both lists, in development
}
```

Careful: the Owner Stack here belongs to a different component. While React runs `componentDidCatch`, the component it is running is the Error Boundary, not `Price`. So `captureOwnerStack()` names the owners of the Error Boundary.

In our shop, with the boundary written in `App` around the product list, it logs only `at App`. The root's `onCaughtError` handler, in contrast, gets the Owner Stack of `Price`. That is why the entry file logs it there in Principle 5.

### Where the root options go

The root options go to `createRoot`, not to `render`. When a developer passes them to `root.render`, React ignores them and never calls the handler. It logs an error in the Console instead. The shop still crashes, and React's own handler logs the crash as before:

```devconsole width=full caption="The Console when the root options are passed to root.render."
x You passed a second argument to root.render(...) but it only accepts one argument.
x Uncaught TypeError: Cannot read properties of undefined (reading 'toFixed')
! An error occurred in the <Price> component.
  Consider adding an error boundary to your tree to customize error handling behavior.
  Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

## PRINCIPLE | `captureOwnerStack()`: returns the list only while React runs your code, and `null` after

> [!PRINCIPLE]
> **Principle 4: When It Answers: captureOwnerStack Gives a List Only While React Runs Your Code**
>
> *Call `captureOwnerStack()` during render, in an Effect, in a React event handler, or in a React error handler; in a `setTimeout` callback, after `fetch`, or in an `addEventListener` listener, it returns `null`.*
>
> The Owner Stack belongs to the component that React is running right now. When the browser runs our code later, React is not running any component, so there is no Owner Stack to read. A log that prints `null` does not mean the tool is broken. It means the call ran outside React. Capture the string earlier, while React runs the code, and keep it.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const ownerStack = ~captureOwnerStack()~; // In the body of the Effect: the Owner Stack
>   function handleEvent() {
>     console.log('Owner Stack: ', ownerStack);
>   }
>   document.addEventListener('click', handleEvent);
>   return () => document.removeEventListener('click', handleEvent);
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   function handleEvent() {
>     console.log('Owner Stack: ', ~captureOwnerStack()~); // **WRONG:** the browser calls handleEvent, so this is null
>   }
>   document.addEventListener('click', handleEvent);
>   return () => document.removeEventListener('click', handleEvent);
> });
> ```

Picture an `Add to cart` button on the shop, in a component named `AddButton` that the app writes. When the user clicks it, the button logs the Owner Stack right away, and again a moment later:

```jsx title="The same captureOwnerStack call in onClick and in setTimeout"
function AddButton() {
  function handleClick() {
    console.log('Owner Stack: ', ~captureOwnerStack()~); // 1. In onClick: logs the Owner Stack
    setTimeout(() => {
      console.log('Later: ', ~captureOwnerStack()~); // 2. In a setTimeout callback: logs null
    }, 0);
  }

  return <button onClick={handleClick}>Add to cart</button>;
}
```

The user clicks `Add to cart`, and the Console shows:

```devconsole caption="The Console after one click on Add to cart: the Owner Stack from onClick, then null from setTimeout."
Owner Stack:  | 1. from onClick
  at button
  at AddButton
  at App
Later:  null | 2. from setTimeout
```

### VS | `onClick` vs. `setTimeout`: both run after the same click, only `onClick` runs while React is running

Both lines run after the same click, in the same component. **It may look the same, but it is NOT the same thing!**
- **`handleClick` is a React event handler.** You passed it to the `onClick` prop, and React calls it (Lesson 11). React is running our code at that moment, so it knows which component the code belongs to. The list starts with the `<button>` itself. Then comes `AddButton`, which wrote the button tag, and the app, which wrote the `AddButton` tag.
- **The `setTimeout` callback** runs later, when the browser's timer fires (Lesson 15). React is not running anything at that moment. So `captureOwnerStack()` finds no Owner Stack and returns `null`.

React's docs list the four places where `captureOwnerStack()` gives a list:
1. During render.
2. In Effects.
3. In React event handlers.
4. In React's error handlers, such as `onUncaughtError`.

They also list three places where it returns `null`:
1. A `setTimeout` callback.
2. Code that runs after a `fetch` call.
3. A **custom DOM event handler**: a function added with `addEventListener`, which the browser calls without React (Lesson 79).

```tree caption="captureOwnerStack gives a list only while React is running our code."
Where `captureOwnerStack` is called
- +While React runs our code [render, Effects, `onClick`, `onUncaughtError`] | React knows **which component** the code belongs to | Returns **the Owner Stack** as a string
- !Outside React [`setTimeout`, after `fetch`, `addEventListener`] | The browser runs the code; **React is not running** | Returns **`null`**
```

### A listener added in an Effect logs `null`

React's docs show the mistake developers meet with `addEventListener`. A component adds a click listener to the whole document in an Effect, and the listener logs the Owner Stack:

```jsx title="Calling captureOwnerStack inside a custom DOM event handler"
useEffect(() => {
  function handleEvent() {
    console.log('Owner Stack: ', ~captureOwnerStack()~); // **WRONG:** the browser calls handleEvent, so this logs null
  }

  document.addEventListener('click', handleEvent);
  return () => document.removeEventListener('click', handleEvent);
});
```

The user clicks the page, and the Console shows `null`:

```devconsole caption="The Console after a click on the page: the listener logs null."
Owner Stack:  null | from handleEvent
```

The fix in React's docs is to call `captureOwnerStack()` earlier, in the body of the Effect, where React is running. The listener then logs the string it already holds:

```jsx title="Calling captureOwnerStack in the body of the Effect"
useEffect(() => {
  const ownerStack = ~captureOwnerStack()~; // In the body of the Effect: React is running, so this is the Owner Stack

  function handleEvent() {
    console.log('Owner Stack: ', ~ownerStack~); // Logs the string captured above
  }

  document.addEventListener('click', handleEvent);
  return () => document.removeEventListener('click', handleEvent);
});
```

### `Price` names its owner during render

Render is one of the four places where `captureOwnerStack()` answers. So `Price` can name its owner by itself, the moment it gets no amount. Instead of throwing, it logs an error with its Owner Stack and shows a short text:

```jsx title="src/Price.jsx"
import { captureOwnerStack } from 'react';

export default function Price({ amount }) {
  if (amount === undefined) {
    console.error('Price got no amount', ~captureOwnerStack()~); // During render: names the component that wrote the Price tag
    return <span>Price unavailable</span>;
  }
  return <span>${amount.toFixed(2)}</span>;
}
```

The page comes back. The Mug row shows its price, and the Cap row says that its price is unavailable:

```page caption="The shop after Price stops throwing: the Cap row shows Price unavailable."
heading: Shop
line: Mug $12.00 | good
line: Cap Price unavailable | bad
```

The Console names the component that wrote the `Price` tag for Cap:

```devconsole width=full caption="The Console after Price logs its Owner Stack during render."
x Price got no amount
  at http://localhost:5173/src/ProductList.jsx:16:19
  at Array.map
  at ProductList
  at App
```

### The same idea in an error overlay

React's docs use the same idea for an **error overlay**: a panel that a development tool draws over the page to show an error. The docs wrap `console.error`, so that every error a component logs during render or in a handler also carries the Owner Stack of that component. `onConsoleError` is the docs' name for the function that draws the overlay:

```js title="Adding the Owner Stack to every console.error"
const originalConsoleError = console.error;
console.error = function patchedConsoleError(...args) {
  originalConsoleError.apply(console, args); // The Console still shows the error
  const ownerStack = ~captureOwnerStack()~; // The owners of the component that logged
  onConsoleError({ consoleMessage: args[0], ownerStack });
};
```

React's docs add one warning about this code: `console.error` can be called with several arguments, and a real overlay must handle all of them, not only the first.

## PRINCIPLE | `captureOwnerStack` in production: `undefined`, so the report sends `errorInfo.componentStack`

> [!PRINCIPLE]
> **Principle 5: Production: Report the Component Stack, and Keep captureOwnerStack Behind a Check**
>
> *`captureOwnerStack` exists only in development builds, so reach it through `import * as React` inside a `process.env.NODE_ENV !== 'production'` check, and send `errorInfo.componentStack` to production reports.*
>
> The Owner Stack is a development tool. A named import of `captureOwnerStack` is `undefined` in production, and calling it throws the very error you meant to report. In production, the report sends the Component Stack from the root options, and sourcemaps turn its short minified names back into your names.
>
> **DO THIS:**
> ```jsx
> import * as React from 'react';
> if (~process.env.NODE_ENV !== 'production'~) { // Skipped in production
>   console.log(React.captureOwnerStack());
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import { captureOwnerStack } from 'react';
> console.log(~captureOwnerStack()~); // **WRONG:** undefined in production, so this line throws a TypeError
> ```

Our shop works in development. Now we build it for production, the version that real users get (Lesson 47). React's docs are clear: Owner Stacks exist only in development. Only the development build of React exports `captureOwnerStack`. In the production build, it is `undefined`.

There are two ways to reach `captureOwnerStack` in a file. The first is the named import we have used so far:

```jsx title="A named import of captureOwnerStack"
import { ~captureOwnerStack~ } from 'react'; // undefined in a production build

captureOwnerStack();
```

The second is a namespace import, with the call behind a check:

```jsx title="A namespace import, with the call behind a check"
import * as ~React~ from 'react'; // Every export of react, collected in one object

if (~process.env.NODE_ENV !== 'production'~) { // Skipped in a production build
  React.captureOwnerStack(); // Runs only in development
}
```

### VS | The named import vs. the namespace import: both give the Owner Stack in development, only the namespace import survives production

**It may look the same, or work the same at first, but it is NOT the same thing!**
- **With the named import**, the production build has no `captureOwnerStack` to give. React's docs say it "will be `undefined` in production builds". Calling `undefined` throws a `TypeError`.
- **With the namespace import**, the import line collects every export of `react` into one object named `React`. The import line never asks for `captureOwnerStack` by name. The code reads it later as a property of that object, and the check makes sure the call runs only in development.

`process.env.NODE_ENV` is the value that React's docs compare with `'production'`. In a production build it holds `'production'`, so the code skips the call.

### Why the production shop goes blank again

Our `Price` from Principle 4 uses the named import. So the production shop crashes on the very line that was meant to report the bug. Here is the order when the user opens the production page:
1. React calls `Price` for the Cap row. `amount` is `undefined`.
2. `Price` calls `captureOwnerStack()`. In the production build it is `undefined`, so the call throws a `TypeError`.
3. No Error Boundary catches the error. React removes the whole page, and the user sees a blank page again.

`Price` switches to the namespace import and the check. It still shows the short text in production:

```jsx title="src/Price.jsx"
import * as React from 'react';

export default function Price({ amount }) {
  if (amount === undefined) {
    if (~process.env.NODE_ENV !== 'production'~) { // The Owner Stack exists only in development
      console.error('Price got no amount', React.captureOwnerStack());
    }
    return <span>Price unavailable</span>;
  }
  return <span>${amount.toFixed(2)}</span>;
}
```

### What a production error report can send

The interview question asks how to log the Owner Stack in production. The answer is that you do not, because there is none to log. A production error report sends the Component Stack instead, from the root options.

Many teams send errors to an **error reporting service**: a server that collects the errors real users meet, so the team can read them later. In our shop, a small file stands in for one. It writes the error to the Console:

```js title="src/reportError.js"
export function reportError({ error, componentStack }) {
  console.error(~error, componentStack~); // A real app sends both to its error reporting service
}
```

The entry file from Principle 3 has the same named import, so it switches to the namespace import too. It sends every error that reaches the root to `reportError`, and logs the Owner Stack only in development:

```jsx title="src/main.jsx"
import * as React from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';
import { reportError } from './reportError.js';

function logError(error, errorInfo) {
  reportError({ error, componentStack: ~errorInfo.componentStack~ }); // Sent in development and in production
  if (process.env.NODE_ENV !== 'production') {
    console.log(~React.captureOwnerStack()~); // Logged in development only
  }
}

createRoot(document.getElementById('root'), {
  onUncaughtError: logError,
  onCaughtError: logError,
}).render(<App />);
```

The same report holds different things in the two builds:

| What the report holds | In development | In production |
| :--- | :--- | :--- |
| **`errorInfo.componentStack`** | The real names: `Price`, `li`, `ul`, `ProductList`, `main`, `Layout`, `App` | **Minified** names, such as `m` for `Price` and `g` for `ProductList`; HTML tags such as `li` keep their names |
| **The Owner Stack** | The `<Price />` line in the file of `ProductList`, then `ProductList` and `App` | None: `captureOwnerStack` is `undefined` in the production build |

**Minified** means that the production build rewrites the code to make it smaller, and gives functions short names of one or two letters. So a production Component Stack does not say `Price` or `ProductList`.

React's docs say you decode it with **sourcemaps**. These are files that the build writes next to the code, and they map every short name back to your own name. You decode it the same way as a normal JavaScript stack trace.

```tree caption="What an error report can send in development and in production."
The same error report in the two builds
- +Development | `errorInfo.componentStack` with **real names** | `captureOwnerStack` with **the owners**
- !Production | `errorInfo.componentStack` with **minified names**, decoded with **sourcemaps** | **No Owner Stack**: `captureOwnerStack` is `undefined`
```

React's docs add one more detail to the production report: a check that skips an error the team already knows about, before the report is sent. `reportCaughtError` is the docs' name for the function that sends it:

```jsx title="The production sample from React's docs"
onCaughtError: (error, errorInfo) => {
  if (~error.message !== "Known error"~) { // Skip an error the team already knows about
    reportCaughtError({ error, componentStack: errorInfo.componentStack });
  }
},
```

```tree caption="The component tree of the shop, in the order React calls each component, with the owner of each one."
    - !`Price` for Cap [5. Called fifth] | Owner: **`ProductList`** | Gets no amount, logs its Owner Stack, returns `Price unavailable`
```

| Principle | What the developer writes or reads | What it tells about the Cap error |
| :--- | :--- | :--- |
| **1. Owner and parent** | `<Layout><ProductList /></Layout>` in `App` | `App` owns `ProductList`; `Layout` only holds it |

## For the Interview

> **The Interview Question:** How does captureOwnerStack pinpoint which component caused a render or error?

### How to Answer Clearly in 30 Seconds

"`captureOwnerStack()` returns the Owner Stack: the list of components that wrote the tags leading to the component React is running. The owner of an element is the component whose JSX wrote its tag. That is different from the parent: a layout that renders `children` is a parent, but not the owner. Three facts make it useful:
1. **The error's own stack cannot name the owner.** React calls components, so the stack shows the component that threw and then React's functions, the 'library frames'.
2. **The Component Stack is longer.** `errorInfo.componentStack` lists every parent, including layouts and HTML tags. The Owner Stack lists only the owners, so its first name is the component that passed the bad props.
3. **It is a development tool.** It works during render, in Effects, in React event handlers, and in the root's error handlers, and it returns `null` in a `setTimeout` callback or an `addEventListener` listener. In production it is not exported, so I reach it through `import * as React` behind a `process.env.NODE_ENV` check, and my production reports send `errorInfo.componentStack`, decoded with sourcemaps."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What is the difference between the owner and the parent of a component?"**
   The parent is where the element sits in the tree. The owner is the component whose JSX wrote its tag. In our shop, `App` writes the `ProductList` tag between the `Layout` tags. `Layout` is the parent of `ProductList`, because it places it inside `<main>`. `App` is the owner, because it wrote the tag. React's docs say that a component that only renders `children`, and every DOM component such as `<main>` or `<li>`, only forwards the element.
2. **"An error was thrown inside a tree of two hundred components, and the stack shows only library frames. What does the Owner Stack reveal?"**
   It reveals who wrote the tag of the component that threw. The error's own stack shows the component that threw and then React's functions, because React called that component, not its owner. The Owner Stack starts with the owner, then the owner's owner. It leaves out every layout and HTML tag that only forwarded the element, every sibling, and the component that threw. Its first name is usually the file to open.
3. **"How do you log the Owner Stack in production?"**
   You do not, because there is none. React's docs say that Owner Stacks are only available in development, and the production build of React does not export `captureOwnerStack` at all, so it is `undefined` there. In production, I pass `onUncaughtError`, `onCaughtError`, and `onRecoverableError` to `createRoot`, and send the `error` with `errorInfo.componentStack` to the error reporting service. Its component names are minified, so I decode them with sourcemaps, the same way as a normal JavaScript stack trace.

```tree caption="Interview comparison: the three lists of names for one error."
Three lists of names for one error
- !The error's own stack [`error.stack`] | The component that threw, **then React's functions** | Cannot name the owner, because **React called** the component
- +The Component Stack [`errorInfo.componentStack`] | **Every parent**, from the failing component up to the root | Available **in production**, with minified names
- +The Owner Stack [`captureOwnerStack`] | **Only the owners**, starting with the component that wrote the tag | **Development only**; `null` outside the code React runs
```
