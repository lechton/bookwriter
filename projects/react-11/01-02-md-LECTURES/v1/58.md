# Lecture 58: How Passing JSX as children Replaces memo, useMemo, and useCallback

*(How can a theme button change the colors of a chat without re-rendering every message?)*

> INTERVIEW QUESTION | ❱❱ MORE | How does component composition replace memoization without useCallback or useMemo?

---

## VS | `<ChatRoom />` Written by the Wrapper vs. Passed In as `children`: the same screen, but only one re-renders the chat

> A theme button changes only the colors of a page, yet one click on it makes React re-render every message of the chat below it. **Move the theme into a wrapper component, and let the parent above write the chat's tag and pass it in as `children`**. The parent does not run again on the click, so it hands React the same chat as last time, and React skips it without `memo` or any Hook.

Remember Lesson 54? When the state of a component changes, React calls that component again. Then it calls every component whose tag that component writes in its JSX, and every component below those. So a theme kept in `App` re-renders the whole page on every click, even the parts that only change color.

Lessons 55 to 57 stopped this with memoization: `memo` on the rows, plus a Hook for every object and every function they receive. Each Hook needs a dependency list, and one value that is new on every render breaks the skip. This lesson stops the same re-renders with no memoization at all. We only move code around: one tag goes up one level, and one piece of state goes down.

The idea fits in one sentence, and the whole lesson comes back to it. **React does not care where a component sits on the screen. It cares which component writes its tag, and whether that component ran again.**

> [!DEFINITION]
> **The default re-render.** [REVIEW] When the state of a component changes, React calls that component function again. It also calls every component the function writes as a tag in its JSX, and every component below those, whether their props changed or not (Lesson 54).

> [!DEFINITION]
> **The children prop.** [REVIEW] Everything you write between the opening tag and the closing tag of a component, as in `<Card><p>Hi</p></Card>`, arrives in that component as the prop `children`. The component places it in its JSX with `{children}` (Lesson 9).

> [!DEFINITION]
> **StrictMode calls every component twice.** [REVIEW] Our project mounts `<App />` inside `<StrictMode>`. In development, StrictMode calls every component function twice on purpose, so every `console.log` inside a component prints two lines. In production, each component is called once (Lesson 47).

### The Smallest Page with a Theme Button

Here is the smallest page that shows it: a button that switches the theme between light and dark, and one chat message.

```page width=text caption="The page when it opens: a Toggle theme button and one message, Hi!."
line: [Toggle theme]
line: Hi!
```

In the first version, `App` holds the theme, and it writes the `<ChatRoom />` tag in its own JSX:

```jsx title="App.jsx: theme lives in App, and App writes the ChatRoom tag"
import { useState } from 'react';

function ChatRoom() {
  console.log('ChatRoom rendered');
  return <p>Hi!</p>;
}

export default function App() {
  const [theme, setTheme] = useState('light');
  return (
    <div className={theme}>
      <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>Toggle theme</button>
      ~<ChatRoom />~ {/* Written by App, the component whose state changes */}
    </div>
  );
}
```

The user clicks `Toggle theme`. The page turns dark, and the Console prints `ChatRoom rendered` again:

```devconsole caption="The real Console after one click on Toggle theme, with theme in App: StrictMode prints the line twice."
+ ChatRoom rendered | App.jsx:4
+ ChatRoom rendered | App.jsx:4
```

This is the default you know. The state of `App` changed, so React calls it again. And `App` writes the chat's tag, so React calls `ChatRoom` too. The line appears twice only because of StrictMode. To keep the Console easy to read, every other Console in this lecture shows one line per render.

Now we change one thing. We move the theme, the `<div>`, and the button into a component of their own, `ThemeWrapper`. `ThemeWrapper` does not write `<ChatRoom />`. It places `{children}` where the chat goes. `App` writes the chat's tag between the two wrapper tags:

```jsx title="App.jsx: theme lives in ThemeWrapper, and App writes the ChatRoom tag between its tags"
import { useState } from 'react';

function ThemeWrapper({ children }) {
  const [theme, setTheme] = useState('light');
  console.log('ThemeWrapper rendered');
  return (
    <div className={theme}>
      <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>Toggle theme</button>
      ~{children}~ {/* Places whatever App wrote between the tags */}
    </div>
  );
}

function ChatRoom() {
  console.log('ChatRoom rendered');
  return <p>Hi!</p>;
}

export default function App() {
  return (
    <ThemeWrapper>
      ~<ChatRoom />~ {/* Written by App, which has no state and does not run again */}
    </ThemeWrapper>
  );
}
```

The user clicks `Toggle theme`. The page turns dark, exactly as before. But this time the Console prints only one line, and there is no `ChatRoom rendered`:

```devconsole caption="The Console after one click on Toggle theme, with theme in ThemeWrapper."
+ ThemeWrapper rendered | App.jsx:5
```

On the screen, you cannot tell the two versions apart. Open the Elements panel after the click, and both show exactly the same nodes:

```dom caption="The Elements panel after one click on Toggle theme. Both versions show exactly these nodes."
+ <div class="dark"> | note: The only node that changed: light became dark
    <button>Toggle theme</button>
    <p>Hi!</p>
  </div>
```

**It may look the same, and it works the same on the screen, but it is NOT the same thing!** In both versions, `<p>Hi!</p>` sits inside the same `<div>`. The only difference is which component writes the `<ChatRoom />` tag:
- **With `theme` in `App`**, the component whose state changed writes the tag. React calls `App`, and with it `ChatRoom`.
- **With the theme in `ThemeWrapper`**, `App` writes the tag, and the state of the parent did not change. React calls only `ThemeWrapper`. The chat inside it came from a component that did not run again, so React leaves the chat alone.

```tree caption="The same ChatRoom inside the same div: the component that writes the tag decides whether a click re-renders it."
Which component writes `<ChatRoom />`?
- !The component whose state changes [`App` holds `theme`] | A click re-renders `App` | React **re-renders `ChatRoom`** too
- +The parent above the wrapper [`App` writes it between the `ThemeWrapper` tags] | A click re-renders **only `ThemeWrapper`** | `App` did not run again, so React **skips `ChatRoom`**
```

React's docs give the rule in one sentence: "When a component visually wraps other components, let it accept JSX as children. This way, when the wrapper component updates its own state, React knows that its children don't need to re-render." Neither version holds `memo` or a memoization Hook.

> [!DEFINITION]
> **Composition.** [NEW] In everyday English, a composition is a whole made by putting parts together, as a song is made of notes. In React, composition means building the page by putting components inside each other through their tags, so one component can carry another component it does not write itself. `ThemeWrapper` carries the chat, and `App` writes it (Lesson 58).

### What the User Feels

In the chat of Lessons 54 to 57, before any memoization, every click on `Toggle theme` re-renders every message row. So does every letter the user types in the message field. With a long history or slow rows, the letters appear late in the field. React's docs describe the same effect in a list, where re-rendering "makes the typing feel janky".

The memoization of Lessons 55 to 57 fixes it, at a price. React's docs name that price: "The downside of this approach is that code becomes less readable. Also, not all memoization is effective: a single value that's 'always new' is enough to break memoization for an entire component."

This lesson fixes the same lag with plain components, in two moves:
1. The theme goes into a wrapper that takes the chat as `children`.
2. The text of the message field goes into a small component of its own.

After that, the rows skip both the click and the keystrokes, and no file holds a single memoization Hook.

### The Rule of Thumb: ask which component writes the tag

**Before you reach for `memo`, ask two questions: which component writes the slow tag, and does that component run again?** If the component that runs again does not write the slow tag, React skips it for free.

A senior developer knows the four classic mistakes here:
1. **Thinking a component re-renders when the component around it on the screen re-renders.** What decides it is which component writes the tag, and whether that component ran again.
2. **Reaching for memoization first**, before asking where the state lives. React's docs list "accept JSX as children" and "Prefer local state" first among the habits that "make a lot of memoization unnecessary".
3. **Keeping short-lived state at the top of the app**, such as the text of an `<input>` field. React's docs say: "don't keep transient state like forms and whether an item is hovered at the top of your tree or in a global state library".
4. **Thinking `children` stops every re-render.** Then one click on `Send` re-renders every row, and it looks like a bug. Principle 4 shows why that click is different.

When a state that changes often re-renders a slow part of the page, you really have five choices:
1. **Leave it, and measure first with `<Profiler>`.** This fits when the user feels no lag. React's docs: "If there is no perceptible lag when your component re-renders, `memo` is unnecessary" (as seen in Lesson 54).
2. **Pass the slow part as `children` to the component that owns the state.** This fits a component that visually wraps the slow part, such as a theme wrapper, a panel, or a layout. Principles 1 and 2 teach it.
3. **Move the state down into a small component of its own.** This fits state that only one small part uses, such as the text of an `<input>` field. Principle 3 teaches it.
4. **Use `memo` on the slow child, with `useMemo` and `useCallback` for its props.** This fits when the component that re-renders must write the slow child itself (as seen in Lessons 55 to 57).
5. **Let React Compiler do it.** The compiler caches JSX and values when the app is built. Lesson 63 teaches it.

```tree caption="Five ways to handle a state that changes often above a slow part of the page; this lesson teaches ways 2 and 3."
A state that changes often re-renders a slow part
- +1. Measure first [`<Profiler>`] | The user feels **no lag** | **Leave it**
- +2. Pass the slow part as `children` [`<ThemeWrapper><ChatRoom /></ThemeWrapper>`] | A wrapper **owns the state** and visually wraps the slow part | **This lesson**, Principles 1 and 2
- +3. Move the state down [`MessageInput`] | Only **one small part** uses the state | **This lesson**, Principle 3
- +4. `memo` with `useMemo` and `useCallback` | The component that re-renders **must write** the slow child | Lessons 55 to 57
- +5. React Compiler | Caches JSX **when the app is built** | Lesson 63
```

This time we start with no `memo` and no memoization Hook. Two pieces of the earlier lessons are gone, because this lesson does not need them: `ThemeContext` and the `Delete` button. No component reads `theme` in JavaScript. The `.dark` class on the `<div>` sets the background and the text color, and CSS does the rest.

> [!DEFINITION]
> **An inherited CSS property.** [NEW] Some CSS properties pass from an element to everything inside it. `color` is one of them: put `color: white` on a `<div>`, and every `<li>` inside it gets white text, with no CSS of its own. That is why our message rows change color without any React code (Lesson 58).

`App` holds the theme, and it writes the chat:

```jsx title="src/App.jsx: the starting version" startLine="1"
import { useState } from 'react';
import ChatRoom from './components/ChatRoom.jsx';

export default function App() {
  const [theme, setTheme] = useState('light');
  return (
    <div className={theme}>
      <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>
        Toggle theme
      </button>
      ~<ChatRoom />~ {/* Written by App, so every click on Toggle theme re-renders the chat */}
    </div>
  );
}
```

`ChatRoom` holds two state variables. The first is `messages`. The second is `text`, the text of the `<input>` field. It writes one `Message` per message:

```jsx title="src/components/ChatRoom.jsx: the starting version" startLine="1"
import { useState } from 'react';
import Message from './Message.jsx';

const initialMessages = [
  { id: 1, text: 'Hi!' },
  { id: 2, text: 'Lunch at 12?' },
  { id: 3, text: 'Sure' },
];
let nextId = 4;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);
  const [text, setText] = useState('');
  console.log('ChatRoom rendered');

  function handleSend() {
    setMessages([...messages, { id: nextId++, text }]);
    setText('');
  }

  return (
    <section>
      <ul>
        {messages.map(m => <Message key={m.id} text={m.text} />)}
      </ul>
      <input placeholder="Message" value={text} ~onChange={e => setText(e.target.value)}~ /> {/* Every keystroke changes the state of ChatRoom */}
      <button onClick={handleSend}>Send</button>
    </section>
  );
}
```

`Message` is a plain component, with no `memo`:

```jsx title="src/components/Message.jsx" startLine="1"
export default function Message({ text }) {
  console.log('Message rendered:', text);
  return <li>{text}</li>;
}
```

At the end of this lesson, the chat lives in seven files, and none of them holds `memo` or a memoization Hook:

```files title="chat-room: File Explorer" caption="How the final chat room sits inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` and mounts it inside `<StrictMode>`
  index.css | styles | Defines the `.light` and `.dark` classes
  App.jsx | parent | Exports `App`, which writes `<ChatRoom />` between the `ThemeWrapper` tags
  components/
    ThemeWrapper.jsx | wrapper | Exports `ThemeWrapper`, which holds `theme` and places `{children}`
    ChatRoom.jsx | state owner | Exports `ChatRoom`, which holds `messages`; imports `Message` and `MessageInput`
    Message.jsx | row | Exports `Message`, a plain component that shows one message
    MessageInput.jsx | local state | Exports `MessageInput`, which holds `text` and calls `onSend`
```

**PRINCIPLES:** React re-renders the component whose state changed, and every component it writes in its own JSX. So to stop needless re-renders without memoization, we choose which component writes each tag, and where each piece of state lives. Four principles follow:
1. **Principle 1: children: the Wrapper Re-renders Alone, and the Chat Its Parent Wrote Is Skipped.** A wrapper that owns the theme takes the chat as `children`, and `App` writes the chat's tag. A click on `Toggle theme` re-renders only the wrapper.
2. **Principle 2: A React Element: the Same Object as Last Time Means No Re-render.** A JSX tag becomes an object when the component that writes it runs. `App` did not run again, so React finds the same object as last time, and skips it.
3. **Principle 3: MessageInput with Its Own text: Typing Re-renders Only the Message Input.** The text of the field moves down into a small component of its own, so each keystroke re-renders only that component.
4. **Principle 4: ChatRoom with a New Message: a Component That Re-renders Still Re-renders What It Writes.** Both tools skip only what a component that did not run wrote. When `ChatRoom` gets a new message, it re-renders every row it writes.

## PRINCIPLE | `children`: the wrapper re-renders alone, and the chat its parent wrote is skipped

> [!PRINCIPLE]
> **Principle 1: children: the Wrapper Re-renders Alone, and the Chat Its Parent Wrote Is Skipped**
>
> *When a component visually wraps a slow part and owns the state that changes, let it take that part as `children`, and write the part's tag in the parent above.*
>
> A click that changes `theme` re-renders the component that holds `theme`, and every component it writes. When the wrapper writes `<ChatRoom />` itself, every click re-renders the chat and every row. When `App` writes `<ChatRoom />` between the wrapper's tags, the wrapper only places `{children}`, and `App` does not run again. React re-renders the wrapper and leaves the chat alone, with no `memo` and no comparison of props.
>
> **DO THIS:**
> ```jsx
> function ThemeWrapper({ children }) {
>   const [theme, setTheme] = useState('light');
>   return <div className={theme}>{children}</div>;
> }
> export default function App() {
>   return <ThemeWrapper>~<ChatRoom />~</ThemeWrapper>; // Written by App: a theme change skips ChatRoom
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ThemeWrapper() {
>   const [theme, setTheme] = useState('light');
>   return <div className={theme}>~<ChatRoom />~</div>; // **WRONG:** written by ThemeWrapper, so every theme change re-renders ChatRoom
> }
> ```

### Moving the State Is Not Enough

There is a third version between the two of the opening, and developers write it all the time. They move `theme` into `ThemeWrapper`, but the wrapper still writes the chat's tag itself:

```jsx title="ThemeWrapper holds theme and still writes the ChatRoom tag itself"
function ThemeWrapper() {
  const [theme, setTheme] = useState('light');
  return (
    <div className={theme}>
      <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>Toggle theme</button>
      ~<ChatRoom />~ {/* **WRONG:** written by ThemeWrapper, so every click re-renders ChatRoom */}
    </div>
  );
}
```

For the chat, this is **the exact same thing** as `theme` in `App`. In both, the component whose state changed writes the `<ChatRoom />` tag, so every click re-renders `ChatRoom`. The state moved, but the tag did not.

The fix comes only when the tag moves out of the wrapper. The wrapper places `{children}`, and the parent above writes the tag:

```jsx title="ThemeWrapper holds theme and places children; App writes the tag"
function ThemeWrapper({ ~children~ }) { // Receives the chat that App wrote
  const [theme, setTheme] = useState('light');
  return (
    <div className={theme}>
      <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>Toggle theme</button>
      {children}
    </div>
  );
}
```

```tree caption="Three places for theme and the ChatRoom tag; only the last one leaves ChatRoom alone on a click."
Where `theme` lives, and which component writes `<ChatRoom />`
- !`theme` in `App` [`App` writes the tag] | A click re-renders `App` | **`ChatRoom` re-renders**
- !`theme` in `ThemeWrapper` [`ThemeWrapper` writes the tag] | A click re-renders `ThemeWrapper` | **`ChatRoom` re-renders**: the exact same thing
- +`theme` in `ThemeWrapper` [`App` writes the tag between its tags] | A click re-renders only `ThemeWrapper` | **`ChatRoom` is skipped**
```

### The Theme Wrapper in Our Chat

Now we apply this to the chat. `ThemeWrapper` is a new file. It holds the theme, the `<div>`, the button, and `{children}`:

```jsx title="src/components/ThemeWrapper.jsx" startLine="1"
import { useState } from 'react';

export default function ThemeWrapper({ ~children~ }) { // Everything App writes between the tags
  const [theme, setTheme] = useState('light');
  console.log('ThemeWrapper rendered');
  return (
    <div className={theme}>
      <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>
        Toggle theme
      </button>
      {children}
    </div>
  );
}
```

`App` loses its state. It only writes the chat between the wrapper's tags:

```jsx title="src/App.jsx" startLine="1"
import ThemeWrapper from './components/ThemeWrapper.jsx';
import ChatRoom from './components/ChatRoom.jsx';

export default function App() {
  return (
    <ThemeWrapper>
      ~<ChatRoom />~ {/* Written by App, which holds no state */}
    </ThemeWrapper>
  );
}
```

The user clicks `Toggle theme`, and the whole chat turns dark. The Console prints one line:

```devconsole caption="The Console after one click on Toggle theme, with the chat passed as children."
+ ThemeWrapper rendered | ThemeWrapper.jsx:5
```

Before this change, the same click printed `ChatRoom rendered` and three `Message rendered:` lines. Now none of them appear, and there is no `memo` anywhere. Here is what happens after the click, in order:
1. The user clicks `Toggle theme`. The handler asks React to change `theme` to `'dark'`.
2. Only the state of `ThemeWrapper` changed, so React calls only `ThemeWrapper`. The Console prints `ThemeWrapper rendered`.
3. `ThemeWrapper` returns its `<div>`, now with the dark class. Inside, it places the same `children` it received last time. `App` did not run again, so it handed over nothing new. Principle 2 explains why this matters.
4. React does not call `ChatRoom`, and so it does not call any `Message` either.
5. React gives the `<div>` on the page the class `dark`. Through CSS, the browser turns every message inside it dark.

```dom caption="The Elements panel after one click on Toggle theme: only the class of the div changes."
+ <div class="dark"> | note: The only change: light became dark
    <button>Toggle theme</button>
    <section>
      <ul>
        <li>Hi!</li>
        <li>Lunch at 12?</li>
        <li>Sure</li>
      </ul>
      <input placeholder="Message" value="">
      <button>Send</button>
    </section>
  </div>
```

### Where Did children and the Dark Text Come From?

`ThemeWrapper` never imports `ChatRoom`, and it never writes its tag. React takes everything `App` writes between the two wrapper tags and puts it into `props.children`. `ThemeWrapper` places it inside its `<div>` (as seen in Lesson 9).

No component passes `theme` down to the chat or to the rows. The rows turn dark because `color` is an inherited property. The browser gives the text color of `.dark` on the `<div>` to everything inside it. So the rows change color, and React never re-renders them.

### VS | `memo` on the Chat vs. the Chat Passed as `children`: the same quiet Console, but only one compares props

Lesson 55 solved the same click another way. The theme stayed in `App`, and `memo` wrapped the chat and the rows. Here are the two, on the small `ChatRoom` of the opening:

```jsx title="With memo: theme stays in App, and memo wraps ChatRoom"
const ChatRoom = ~memo~(function ChatRoom() { // Skipped only while every prop passes the comparison
  console.log('ChatRoom rendered');
  return <p>Hi!</p>;
});
```

```jsx title="With children: theme in ThemeWrapper, and App writes the tag"
<ThemeWrapper>
  ~<ChatRoom />~ {/* Skipped because App did not run again: there is nothing to compare */}
</ThemeWrapper>
```

**It looks the same in the Console, but it is NOT the same thing in the code!** After a click on `Toggle theme`, neither prints `ChatRoom rendered`. But `memo` compares every prop of the chat on every render of `App`. One prop that is new each time breaks it (as seen in Lesson 55). With `children`, React compares no props at all. The tag was simply written one level up, by a component that did not run again.

On a real page, the `memo` way turns one fix into many, because every prop must stay the same. Here is how it usually goes:
1. A developer sees `ChatRoom rendered` and every row line after each click on `Toggle theme`.
2. They wrap the chat and the rows in `memo` (as seen in Lesson 55).
3. Each object or function prop now needs `useMemo` or `useCallback`, each with its own dependency list (as seen in Lessons 56 and 57).
4. One prop that is new on every render breaks the skip again. One missing dependency gives a stale closure (as seen in Lesson 57).
5. React's docs had listed the simpler fix first: "When a component visually wraps other components, let it accept JSX as children."

> [!DEFINITION]
> **A wrapper component.** [NEW] React's docs call a component like `ThemeWrapper` a wrapper component: a component that "visually wraps other components", such as a panel, a grid, or here the `<div>` that carries the theme. Think of a picture frame: painting the frame black does not touch the photo inside. `ThemeWrapper` holds a chat that `App` wrote, so changing its theme does not re-render that chat (Lesson 58).

## PRINCIPLE | A React element: the same object as last time means React does not call the component

> [!PRINCIPLE]
> **Principle 2: A React Element: the Same Object as Last Time Means No Re-render**
>
> *A JSX tag becomes an element object when the component that writes it runs; when React gets the same element object as during the last render, it does not re-render that component.*
>
> Writing `<ChatRoom />` does not call `ChatRoom`. It makes an object with `type` and `props`, and React decides later whether to call the component. `App` made the `ChatRoom` element once. When only `ThemeWrapper` re-renders, it hands React that same object again. Elements never change after they are made, so the same object cannot hold anything new, and React skips it. A tag written inside the component that re-renders makes a new object every time, even when it looks the same in the code.
>
> **DO THIS:**
> ```jsx
> export default function App() {
>   return <ThemeWrapper>~<ChatRoom />~</ThemeWrapper>; // Made once by App: the same object on every theme change
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ThemeWrapper() {
>   const [theme, setTheme] = useState('light');
>   return <div className={theme}>~<ChatRoom />~</div>; // **WRONG:** a new element object on every run, so ChatRoom re-renders
> }
> ```

### A JSX Tag Is a Plain Object

React does not call `ChatRoom`, even though it sits inside the very `<div>` that just changed its class. Why? Because writing a tag does not call the component. It only makes a plain JavaScript object that describes the tag:

```jsx title="A JSX tag and the object it becomes"
const element = ~<ChatRoom />~; // An object like { type: ChatRoom, props: {} }, made when this line runs
```

React's docs show the same thing with a list:

```jsx title="React's docs: a JSX node and the object it becomes"
<List items={visibleTodos} /> // "A JSX node like this..."
{ type: List, props: { items: visibleTodos } } // "...is an object like this"
```

The field `type` holds the component function itself. The field `props` holds the attributes written on the tag.

> [!DEFINITION]
> **A React element.** [NEW] A React element is the plain object a JSX tag becomes when its line runs, such as `{ type: ChatRoom, props: {} }` for `<ChatRoom />`. React's docs also call it a JSX node. Making the element does not call the component: React reads the element later, while it renders, and decides then whether to call `type` (Lesson 58).

**Yes, the tag and the object are the exact same thing!** The tag is just the short way to write the object. But writing the tag is NOT the same thing as calling `ChatRoom`. React decides that later.

```tree caption="Writing a JSX tag makes an element object; React decides later whether to call the component."
What `<ChatRoom />` really is
- +The tag we write [`<ChatRoom />`] | Written in the JSX of `App` | **Made when `App` runs**
- +The element object React gets [`type: ChatRoom` `props: {}`] | **The exact same thing**, written as an object | Describes the tag; **calls nothing**
- +React's decision while it renders | Compares the element with the one from the last render | **Same object**: React skips `ChatRoom`
```

### Same Object or New Object: The Question of Lesson 55

Remember Lessons 55 to 57? Everything there came down to one question: "is this the very same object?" Try it in the Console with two plain objects:

```js title="Two objects with the same fields"
const a = { type: 'ChatRoom' };
const b = { type: 'ChatRoom' };

console.log(~a === b~); // false: the same fields, but two different objects
console.log(~a === a~); // true: the very same object
```

React asks that same question about elements. Every time a line with `<ChatRoom />` runs, JavaScript makes a new object, even if its fields are the same. So the real question is: did the line that wrote `<ChatRoom />` run again?
- **When `ThemeWrapper` writes the tag**, the line runs on every click. Every click makes a new object, and React calls `ChatRoom`.
- **When `App` writes the tag**, the line runs only when `App` runs. A click does not run `App`, so there is no new object, and React skips `ChatRoom`.

### The Life of the ChatRoom Element

Here is the whole path, from the first render to the click:
1. When the page opens, React calls `App`. `App` runs the line with `<ChatRoom />` and makes one element object.
2. React puts that object into the `props.children` of the wrapper, and calls `ThemeWrapper`.
3. The wrapper returns a new `<div>` element that holds the `children` object. React calls `ChatRoom`, because the chat is new on the page.
4. The user clicks `Toggle theme`. Only the state of the wrapper changed, so React calls only `ThemeWrapper`, not `App`.
5. The wrapper makes a new `<div>` element and a new `<button>` element. Inside, it places the old `children` object again.
6. React compares the result with the last render. The `<div>` has a new class, so React updates the `<div>` on the page. The `ChatRoom` element is the same object as last time, so React does not call `ChatRoom`.

```tree dir=right caption="App makes the ChatRoom element once, and ThemeWrapper hands the same object back to React on every click."
The life of the `<ChatRoom />` element
- +1. First render [`App` runs] | `App` makes **one element object** for `<ChatRoom />`
- +2. Inside the wrapper [`props.children`] | React hands that object to `ThemeWrapper`
- +3. A click on Toggle theme [`ThemeWrapper` runs] | `ThemeWrapper` places **the same object** again | `App` did not run, so **no new object** exists
- +4. React compares | Same object as last time | **React does not call `ChatRoom`**
```

### Why the Same Object Is Safe to Skip

React can trust the same object because an element never changes after it is made. React's docs say: "You must treat React elements and their props as immutable and never change their contents after creation. In development, React will freeze the returned element and its `props` property shallowly."

So the same object still holds the same `type` and the same props as last time. The docs draw the conclusion: "A JSX node object could not have changed over time, so React knows it's safe to skip a re-render."

This is also why moving only the state did nothing in Principle 1. When `ThemeWrapper` writes `<ChatRoom />` itself, every run of the wrapper makes a new object. It looks the same in the code, but it is NOT the same object. The docs are clear: "the node has to *actually be the same object*, not merely look the same in code."

### VS | `children` from `App` vs. `useMemo` Around One JSX Node: the exact same skip, but only one needs a Hook

There is a second way to hand React the same element object. `ThemeWrapper` can cache the element itself with `useMemo` (as seen in Lesson 56):

```jsx title="With children passed from App: App makes the element once"
<ThemeWrapper>
  ~<ChatRoom />~ {/* App made this object once, and does not run again */}
</ThemeWrapper>
```

```jsx title="With useMemo inside ThemeWrapper: a Hook caches the element"
function ThemeWrapper() {
  const [theme, setTheme] = useState('light');
  const chat = ~useMemo~(() => <ChatRoom />, []); // The same object on every render, kept by a Hook
  return <div className={theme}>{chat}</div>;
}
```

**For React's skip, this is the exact same thing!** In both, `ThemeWrapper` hands React the same element object on the next render, so React does not call `ChatRoom`. React's docs say about `useMemo` around a JSX node: "The behavior would be the same." The difference is in the code. The `useMemo` way needs a Hook and a dependency list, and the docs add that "you can't do this conditionally". The `children` way needs neither.

### Two More Things Interviewers Ask

React Compiler makes the same object for you when the app is built. React's docs say the compiler "wraps `<ExpensiveChild name="John" />` in a cache check. Since the `name` prop is always `"John"`, this JSX is created once and reused on every parent re-render." Lesson 63 teaches the compiler.

The skip does not depend on the name `children`. JSX passed in any other prop follows the same rule, such as `fallback={<Loading />}` on `<Suspense>`. What matters is that the element is the same object. And it is the same object whenever the component that wrote it did not run again.

## PRINCIPLE | `MessageInput` with its own `text`: typing re-renders only the message input

> [!PRINCIPLE]
> **Principle 3: MessageInput with Its Own text: Typing Re-renders Only the Message Input**
>
> *When only one small part of the page uses a piece of state, such as the text of an `<input>` field, move that state down into a component of its own, and send the result up through a callback prop.*
>
> Every keystroke changes the text of the field. When that text lives in `ChatRoom`, each keystroke re-renders `ChatRoom` and every message row, even though no row reads the text. When the text lives in `MessageInput`, each keystroke re-renders only `MessageInput`. `MessageInput` hands the finished text up with `onSend` when the user clicks `Send`, so `ChatRoom` gets it once, and never while the user types.
>
> **DO THIS:**
> ```jsx
> function MessageInput({ onSend }) {
>   const [~text~, setText] = useState(''); // Each keystroke re-renders only MessageInput
>   return <input value={text} onChange={e => setText(e.target.value)} />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ChatRoom() {
>   const [messages, setMessages] = useState(initialMessages);
>   const [~text~, setText] = useState(''); // **WRONG:** each keystroke re-renders ChatRoom and every Message
>   return <input value={text} onChange={e => setText(e.target.value)} />;
> }
> ```

### VS | `text` in `ChatRoom` vs. `text` in `MessageInput`: the same chat for the user, but only one re-renders the rows on every letter

A click on `Toggle theme` no longer re-renders the rows. Typing still does. Why? The text of the field lives in `ChatRoom`, next to `messages`. So every change of `text` re-renders `ChatRoom`, and with it everything the chat writes.

But the rows never read `text`. Only the field and the `Send` button use it. So we move `text` down into a small component of its own, `MessageInput`. React's docs call this moving state down, the opposite of lifting state up (as seen in Lesson 24). Compare the two places for `text`:

```jsx title="With text in ChatRoom: every keystroke changes the state of ChatRoom"
export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);
  const [~text~, setText] = useState(''); // **WRONG:** each keystroke re-renders ChatRoom and every Message
  console.log('ChatRoom rendered');
```

```jsx title="With text in MessageInput: every keystroke changes only the state of MessageInput"
function MessageInput({ onSend }) {
  const [~text~, setText] = useState(''); // Each keystroke re-renders only MessageInput
  console.log('MessageInput rendered');
```

**It may look the same, and it works the same for the user, but it is NOT the same thing!** In both versions, the user types a message and sends it. With `text` in `ChatRoom`, every keystroke re-renders the chat and every row. With `text` in `MessageInput`, every keystroke re-renders only the message input.

React's docs give the reason in two sentences: "Prefer local state and don't lift state up any further than necessary. For example, don't keep transient state like forms and whether an item is hovered at the top of your tree or in a global state library."

> [!DEFINITION]
> **Local state and transient state.** [NEW] Local state is state kept in the component that uses it, as `text` is kept in `MessageInput`. Transient state is state that lives only a short time, such as the text the user types before clicking Send, or whether the mouse is over a row. React's docs say transient state belongs low in the tree, not at the top (Lesson 58).

### The Message Input in Our Chat

`MessageInput` is a new file. It holds `text`, the `<input>` field, and the Send button:

```jsx title="src/components/MessageInput.jsx" startLine="1"
import { useState } from 'react';

export default function MessageInput({ onSend }) {
  const [text, setText] = useState('');
  console.log('MessageInput rendered');

  function handleClick() {
    ~onSend(text)~; // Hands the finished text up to ChatRoom
    setText(''); // Empties its own field
  }

  return (
    <div>
      <input placeholder="Message" value={text} onChange={e => setText(e.target.value)} />
      <button onClick={handleClick}>Send</button>
    </div>
  );
}
```

The chat loses `text`, and it keeps `messages`. It imports `MessageInput`. It receives the finished text through a callback prop (as seen in Lesson 23):

```jsx title="src/components/ChatRoom.jsx" startLine="1"
import { useState } from 'react';
import Message from './Message.jsx';
import MessageInput from './MessageInput.jsx';

const initialMessages = [
  { id: 1, text: 'Hi!' },
  { id: 2, text: 'Lunch at 12?' },
  { id: 3, text: 'Sure' },
];
let nextId = 4;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);
  console.log('ChatRoom rendered');

  function handleSend(text) {
    setMessages([...messages, { id: nextId++, text }]);
  }

  return (
    <section>
      <ul>
        {messages.map(m => <Message key={m.id} text={m.text} />)}
      </ul>
      ~<MessageInput onSend={handleSend} />~ {/* The message input now keeps its own text */}
    </section>
  );
}
```

The user types `O`, then `K`:

```page width=text caption="The chat after the user types OK in the message field."

line: Lunch at 12?
line: Sure
form:
  field: | OK
  button: Send
```

After each keystroke, the Console prints one line:

```devconsole caption="The Console after the user types O and then K, with text in MessageInput."
+ MessageInput rendered | MessageInput.jsx:5
+ MessageInput rendered | MessageInput.jsx:5
```

There is no `ChatRoom rendered` line and no row line, and there is still no `memo` anywhere. Each keystroke changes only the state of `MessageInput`, so React calls only `MessageInput`.

### Where Did onSend, text, and the Empty Field Come From?

`onSend` is a prop. `ChatRoom` writes it on the tag as `onSend={handleSend}`. When the user clicks Send, `MessageInput` calls `onSend` with its own text. That text arrives in `handleSend` as its argument. `ChatRoom` never holds the text while the user types. It gets the text once, when the message is finished.

Then `MessageInput` calls `setText('')` and empties its own field. `ChatRoom` cannot do that for it, because no component can reach the state of another component.

### VS | A New `onSend` Function on Every Render vs. `onSend` in `useCallback`: the exact same page

`handleSend` is a new function every time `ChatRoom` renders. Lesson 57 would wrap it in `useCallback`. Here, **it is the exact same thing either way!** The message input is not wrapped in `memo`, so nothing compares `onSend` with the last one. A new function costs nothing on this page (as seen in Lesson 57).

### Two Tools, One Question

Keeping the text at the top usually leads to memoization that was never needed. Here is how it goes:
1. A developer keeps the text of the field in `ChatRoom`, next to `messages`, because the Send button needs it.
2. Every keystroke re-renders every row.
3. They wrap the rows in `memo` to stop it (as seen in Lesson 55).
4. React's docs had named the simpler cause: "don't keep transient state like forms ... at the top of your tree".

Moving state down and passing JSX as `children` answer the same question: which component writes the slow part, and does that component re-render? Here is how to choose:
- **Pass the slow part as `children`** when it sits inside the markup of the component with the state, as the chat sits inside the theme `<div>`.
- **Move the state down** when only a part next to the slow part uses the state, as the `<input>` field sits next to the rows.

React's docs expect you to move state both ways while you build. "It is common that you will move state down or back up while you're still figuring out where each piece of the state 'lives'."

```tree caption="Two tools without memoization: pass the slow part as children, or move the state down."
Which component writes the slow part, and does it re-render?
- +Pass the slow part as `children` [`<ThemeWrapper><ChatRoom /></ThemeWrapper>`] | The slow part **sits inside** the markup of the component with the state | The parent above writes the tag, **so a theme change skips it**
- +Move the state down [`MessageInput` holds `text`] | The slow part **sits next to** the part that uses the state | The state goes into **its own small component**, so typing skips the rows
```

## PRINCIPLE | `ChatRoom` with a new message: a component that re-renders still re-renders every tag it writes

> [!PRINCIPLE]
> **Principle 4: ChatRoom with a New Message: a Component That Re-renders Still Re-renders What It Writes**
>
> *Passing JSX as `children` and moving state down skip only the components written by a component that did not run again; when the state of `ChatRoom` changes, React still re-renders every `Message` it writes.*
>
> A click on `Send` changes `messages`, the state of `ChatRoom`. `ChatRoom` re-renders, its `map` writes four new `<Message>` elements, and React calls `Message` four times. That is the normal default, and with a short list it is fast. The fix of Principle 1 also breaks when `theme` moves back up into `App`: `App` then runs on every click and makes a new `<ChatRoom />` element. When the rows really are slow, measure first, and then use `memo` on the row.
>
> **DO THIS:**
> ```jsx
> export default function App() {
>   return <ThemeWrapper>~<ChatRoom />~</ThemeWrapper>; // theme stays in ThemeWrapper: a click skips every row
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   const [theme, setTheme] = useState('light');
>   return (
>     <ThemeWrapper theme={theme} onToggle={() => setTheme(theme === 'light' ? 'dark' : 'light')}>
>       ~<ChatRoom />~ {/* **WRONG:** App re-renders on every click, so every row re-renders */}
>     </ThemeWrapper>
>   );
> }
> ```

### One Click on Send Prints a Line for Every Row

After Principles 1 to 3, a click on `Toggle theme` and the keystrokes print no row lines. Then the user clicks `Send` with `OK` in the field, and the Console prints a line for every row. That is not a bug. `ChatRoom` writes the rows in its own `map`, and its own state just changed:

```page width=text caption="The chat after the user clicks Send with OK in the field: a fourth message and an empty field."
line: [Toggle theme]
line: Hi!
line: Lunch at 12?
line: Sure
line: OK
form:
  field: |
  button: Send
```

```devconsole caption="The Console after one click on Send with OK in the field."
+ ChatRoom rendered | ChatRoom.jsx:14
+ Message rendered: Hi! | Message.jsx:2
+ Message rendered: Lunch at 12? | Message.jsx:2
+ Message rendered: Sure | Message.jsx:2
+ Message rendered: OK | Message.jsx:2
+ MessageInput rendered | MessageInput.jsx:5
```

Here is what happens after the click, in order:
1. The user clicks `Send`. `MessageInput` calls `onSend` with the text OK. Then it empties its field with `setText('')`.
2. Inside the chat, `handleSend` calls `setMessages` with a new array of four messages.
3. React handles both updates in one re-render (as seen in Lesson 16). It calls `ChatRoom`, and the Console prints `ChatRoom rendered`.
4. The `map` inside the chat writes four new `<Message>` elements during this render. They are new objects, unlike the `children` of Principle 2, so React calls `Message` four times.
5. React calls `MessageInput`, because `ChatRoom` writes its tag too. Its `text` is now empty.
6. `ThemeWrapper rendered` does not appear. The state of `ThemeWrapper` did not change, and `ChatRoom` sits below it.

**The two tools of this lesson skip only what a component that did not run wrote. They never stop a component from re-rendering what it writes itself.** React's docs say: "By default, when a component re-renders, React re-renders all of its children recursively." With three or four short rows, that default is fast, and Lesson 54 told us to leave it alone until we measure.

`MessageInput` keeps its place on the page, so React keeps its state with it (as seen in Lesson 25). Its field is empty only because `MessageInput` called `setText('')` itself.

### VS | `theme` Kept in `ThemeWrapper` vs. `theme` Lifted Back Up into `App`: the same tags, but only one keeps the chat quiet

Now suppose a header needs the theme to choose a logo. A developer lifts `theme` back up into `App` and passes it down (as seen in Lesson 24). `ThemeWrapper` no longer holds the state. It receives `theme` and `onToggle` as props, and its button calls the second one:

```jsx title="src/components/ThemeWrapper.jsx: with theme lifted back up into App" startLine="1"
export default function ThemeWrapper({ ~theme, onToggle~, children }) { // theme now arrives from App
  console.log('ThemeWrapper rendered');
  return (
    <div className={theme}>
      <button onClick={onToggle}>Toggle theme</button>
      {children}
    </div>
  );
}
```

Compare the two versions of `App`:

```jsx title="With theme in ThemeWrapper: App holds no state"
export default function App() {
  return (
    <ThemeWrapper>
      ~<ChatRoom />~ {/* App does not run again on a click, so this element stays the same object */}
    </ThemeWrapper>
  );
}
```

```jsx title="With theme lifted back up into App"
export default function App() {
  const [theme, setTheme] = useState('light');

  function handleToggle() {
    setTheme(theme === 'light' ? 'dark' : 'light');
  }

  return (
    <ThemeWrapper theme={theme} onToggle={handleToggle}>
      ~<ChatRoom />~ {/* **WRONG:** App runs on every click and makes a new element, so every row re-renders */}
    </ThemeWrapper>
  );
}
```

**It may look the same, but it is NOT the same thing!** Both versions still pass `<ChatRoom />` between the wrapper's tags. But in the second, `App` holds the state that changes. Every click re-renders `App`, and the parent makes a new `<ChatRoom />` element. So React re-renders the chat and every row again:

```devconsole caption="The Console after one click on Toggle theme, with theme lifted back up into App."
+ ThemeWrapper rendered | ThemeWrapper.jsx:2
+ ChatRoom rendered | ChatRoom.jsx:14
+ Message rendered: Hi! | Message.jsx:2
+ Message rendered: Lunch at 12? | Message.jsx:2
+ Message rendered: Sure | Message.jsx:2
+ MessageInput rendered | MessageInput.jsx:5
```

Lifting the state back up quietly undoes the fix. Here is how it happens:
1. The header needs the theme, so a developer lifts `theme` back up into `App`.
2. `App` now re-renders on every click on `Toggle theme`.
3. `App` makes a new `<ChatRoom />` element each time, and every row re-renders again.
4. React's docs give the advice that prevents it: "don't lift state up any further than necessary." Lesson 59 shows how a header can read the theme without this cost.

The same limit holds for a row that reads `theme` in JavaScript, through a prop or through `useContext`. A row that reads the changing value must re-render when that value changes. Our rows read nothing. They get their color from CSS, so React can skip them.

```tree caption="When the two tools stop working: the component that writes the rows re-renders, or the state moves back up."
What the two tools do not skip
- !`ChatRoom` gets a new message [`setMessages`] | `ChatRoom` re-renders and **writes every `Message` again** | **Every row re-renders**: this is normal
- !`theme` lifted back up into `App` [`App` holds `theme`] | `App` re-renders and makes a **new `<ChatRoom />` element** | **Every row re-renders** on every click
- !A row reads the theme in JavaScript [`theme` prop] [`useContext`] | The row **uses the value that changed** | **That row must re-render**
```

### When the Rows Themselves Are Slow

Sometimes the component that re-renders must write the slow part, as `ChatRoom` writes the rows after a click on `Send`. With a long history and slow rows, that is the case for `memo`, after measuring. React's docs set the bar (as seen in Lessons 54 and 55). "Optimizing with `memo` is only valuable when your component re-renders often with the same exact props, and its re-rendering logic is expensive."

They add a second step. "If a specific interaction still feels laggy, use the React Developer Tools profiler to see which components would benefit the most from memoization, and add memoization where needed." Lesson 64 teaches the profiler.

React Compiler can add this memoization for you. React's docs explain that "when a component's state changes, React will re-render that component and all of its children, unless you have applied some form of manual memoization". The compiler applies "the equivalent of manual memoization" when the app is built. Lesson 63 teaches the compiler.

| :--- | :--- | :--- | :--- |
| **Clicks `Toggle theme`** | `ThemeWrapper` | `ThemeWrapper` only | `App` wrote `<ChatRoom />` and did not run again, so the element is the same object |
| **Types a letter in the field** | `MessageInput` | `MessageInput` only | `text` lives in the one component that uses it |
| **Clicks `Send`** | `ChatRoom` and `MessageInput` | `ChatRoom`, every `Message`, and `MessageInput` | `ChatRoom` writes the rows and the message input in its own JSX |
| **Clicks `Toggle theme` with `theme` lifted into `App`** | `App` | Everything | `App` makes a new `<ChatRoom />` element on every run |

Remember the one sentence of this lesson. **React does not care where a component sits on the screen. It cares which component writes its tag, and whether that component ran again.**

## For the Interview

> **The Interview Question:** How does component composition replace memoization without useCallback or useMemo?

### How to Answer Clearly in 30 Seconds

"React re-renders the component whose state changed, and every component it writes in its own JSX. Composition uses that rule in two ways:
1. **Pass the slow part as `children`**: a wrapper that owns fast-changing state, such as a theme, takes the slow part between its tags, and the parent above writes the tag. When the wrapper's state changes, the parent did not run again, so the element is the same object, and React skips it.
2. **Move state down**: state that one small part uses, such as the text of an input field, goes into its own component, so typing re-renders only that component.

Neither needs `memo`, `useMemo`, `useCallback`, or a dependency list. Neither stops a component from re-rendering what it writes itself, so when that component must write a slow child, I measure first and then use `memo`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"`ChatRoom` sits inside the `<div>` that just changed. Why does React not re-render it?"**
   Because where a component appears on the screen and which component writes its tag are two separate things. A JSX tag becomes an element object when the component that writes it runs. `App` wrote `<ChatRoom />` and did not run again, so `ThemeWrapper` hands React the same element object as last time. Elements never change after they are made, so the same object cannot hold anything new, and React skips it. React's docs say: "if React sees the same exact JSX as during the previous render, it won't try to re-render your component."
2. **"Is passing JSX as `children` the same as wrapping that JSX in `useMemo`?"**
   For React's skip, yes. Both hand React the same element object on the next render, and React's docs say "The behavior would be the same." But `useMemo` needs a Hook and a dependency list, and it cannot be called conditionally, while `children` needs only the tag written one level up. JSX passed in any other prop, such as `fallback` on `<Suspense>`, follows the same rule. React Compiler does the same caching for you when the app is built.
3. **"When does composition not help?"**
   In three cases. First, when the component that re-renders writes the slow child itself, as `ChatRoom` writes every `Message` after a click on `Send`. Second, when the state moves back up into the parent above, which then makes a new element on every run. Third, when the child reads the changing value through a prop or a context, because it must re-render to show the new value. In the first case, if the lag is real, I measure with the Profiler and then use `memo` on the child.

```tree caption="Interview summary: composition skips the parts a re-rendering component did not write; memo is for the parts it must write."

- +Pass the slow part as `children` | The wrapper owns the state; the **parent above writes the tag** | Same element object, so **React skips it**
- +Move the state down | State lives in the **lowest component** that uses it | Changes re-render **only that component**
- !The component that re-renders writes the slow child | Composition **cannot help here** | **Measure, then `memo`** on the child
```
