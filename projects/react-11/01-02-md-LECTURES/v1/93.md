# Lecture 93: How One Table Component Keeps Each Row's Type

*(How can one table component show customers and products, and still check every field the caller reads?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How do you type generic components and flexible data collections in React?

---

## VS | `rows: any[]` vs. `rows: T[]`: `any` forgets what a row is, `T` hands each caller its own row type back

> In plain JavaScript, `function greet(name)` works for any name, because the caller fills in `name` every time it calls the function. **A type parameter, written `<T>`, does the same thing for a type: one table component takes rows of any type, and each caller gets its own row type back.** If you type the rows `any` instead, the table forgets what a row is, so a misspelled field such as `user.emial` passes the editor, and the user clicks a row and sees nothing.

Start with something you write every day. A function parameter is a name for a value that the caller fills in:

```ts title="A function parameter: the caller fills in the value"
function greet(~name~: string) { return 'Hello, ' + name; } // name is filled in at each call
greet('John'); // Hello, John
greet('Mary'); // Hello, Mary
```

You write `greet` once, and it works for every name. Now take the same idea one level up: a name for a type, filled in by the caller. Here is a function that returns the first item of a list. It should work for a list of names and for a list of prices, so here are two ways to write it:

```ts title="The first item of a list, written with any and with a type parameter"
function firstAny(items: ~any[]~): any { return items[0]; } // Any list, and the type of the item is forgotten
function first~<T>~(items: T[]): T { return items[0]; } // A list of T, and the same T comes back
```

Now the caller makes one typo, `toUpperCse` instead of `toUpperCase`:

```ts title="The same typo with both functions"
const names = ['John', 'Mary'];
firstAny(names).~toUpperCse~(); // The result is any, so the editor says nothing
first(names).~toUpperCse~(); // **WRONG:** the result is a string, so the editor refuses the typo
```

With `firstAny`, the editor stays quiet, and the browser throws a `TypeError` when the line runs. With `first`, the editor underlines the typo at once:

```text title="The editor's message"
Property 'toUpperCse' does not exist on type 'string'. Did you mean 'toUpperCase'?
```

The editor is where TypeScript shows its errors while you type (Lesson 90).

Why does `first` know the result is a string? Because TypeScript fills in `T` from the list you pass. You pass a list of strings, so here `T` is `string`, and so is the result. Pass a list of prices, and `T` is `number`. Nobody wrote the type by hand. That is the whole trick.

> [!DEFINITION]
> **What is a type parameter?** [NEW] A type parameter is a name for a type, written in angle brackets after the function name, such as `T` in `function first<T>`. It works like a function parameter, but for types: the function is written once, and `T` is filled in at each place the function is used, usually from the values passed in. The name `T` is only a habit, short for type, and any name works, such as `Row` (Lesson 93).

> [!DEFINITION]
> **What is `any`?** [REVIEW] `any` is a TypeScript type that means "this value can be anything, so check nothing on it". It removes every error on the value, and every check with it (Lesson 91).

### The Same Idea in a React Table

A React component is a function too, so the same trick works for components. The admin page of an online store shows several tables: one for customers, one for products. You write the table once, as one shared component, `DataTable`, and each place on the page passes it its own rows. Both versions below describe the same table: it shows a list of rows, and when the user clicks a row, it calls `onSelectRow` with that row:

```tsx title="Two props types for one shared table"
type DataTableProps = { rows: ~any[]~; onSelectRow: (row: any) => void }; // Rows of any shape, and the shape is forgotten
type DataTableProps<T> = { rows: ~T[]~; onSelectRow: (row: T) => void }; // Rows of one type T, and the same T comes back
```

Now a developer uses the table for the customers. `users` is the list of customers, and `setSelected` puts the email of the clicked customer in a line at the top of the page. The field is called `email`, and the developer types `emial`:

```tsx title="The Customers table, with a misspelled field"
<DataTable rows={users} onSelectRow={user => setSelected(~user.emial~)} /> {/* The same tag under both props types */}
```

With `rows: any[]`, the editor says nothing. With `rows: T[]`, the editor underlines `emial`:

```text title="The editor's message"
Property 'emial' does not exist on type 'User'. Did you mean 'email'?
```

The two props types share almost everything:
1. Both accept any list of rows: customers today, products tomorrow.
2. Both give the exact same table in the browser, because TypeScript removes every type before the code runs (Lesson 90).
3. Both read like the same plan: "this table takes rows of any kind."

**It may look the same, but it is NOT the same thing!** The one difference is what happens to the type of a row:
- **With `any[]`, the table forgets what a row is.** The row that comes back in `onSelectRow` is `any`, so `user.emial` passes.
- **With `T[]`, the table remembers what a row is.** `T` is the type of the rows the caller passed, here `User`. The row that comes back in `onSelectRow` is that same `User`, so `user.emial` is refused.

> [!DEFINITION]
> **What is a generic component?** [NEW] A generic component is a component with a type parameter, such as `function DataTable<T>`. In everyday English, generic means not made for one kind only, and that is the job: one component takes rows of any type, and each caller gets its own type back. React never sees the `<T>`: it belongs to TypeScript only, and it is removed with every other type before the code runs (Lesson 93).

```tree caption="Two props types for one shared table: any forgets what a row is, while T remembers it and hands it back to the caller."
Two ways to type the rows of a shared table
- !With `any` [`row: any`] | The table **forgets** what a row is | The row in `onSelectRow` is **`any`**, so **`user.emial` passes**
- +With a type parameter [`row: T`] | The table **remembers** the caller's row type | The row in `onSelectRow` is **`User`**, so **`user.emial` is refused**
```

**Remember this sentence: a type parameter is a name for a type, filled in at each place the component is used.** The table says "rows of some type `T`, and the row I hand back is that same `T`". TypeScript fills in `T` at each tag, from the rows that tag passes.

### What goes wrong with `any`: `Selected:` with nothing after it

**Beware! With `rows: any[]`, a misspelled field passes the editor, and the user clicks a row and sees nothing selected.** Here is how it happens:
1. The shared table is typed `rows: any[]`.
2. A developer writes `onSelectRow={user => setSelected(user.emial)}` on the Customers table.
3. The editor says nothing.
4. The user clicks Taylor's row.
5. `user.emial` is `undefined`, and React shows nothing for `undefined` (Lesson 10). The line at the top reads `Selected:` with nothing after it.
6. The Console stays quiet, so nothing points the developer to the misspelled name.

The page shows the wrong information, and no tool says why. With `rows: T[]`, the editor underlines the same typo the moment the developer types it, and the typo never reaches the user.

### The Rule of Thumb: one table, rows of different types, one `T`

**When one component shows rows of different types, give it a type parameter. Use the same `T` for the rows that go in and for the row that comes back, and let each caller's rows fill it in.**

A senior developer also knows the five classic mistakes:
1. **Rows typed `any[]`.** Every caller loses its checks.
2. **Rows typed `object[]` to avoid `any`.** The editor then refuses `user.email` in every caller, so every caller writes `(user as User).email`, which tells TypeScript "trust me, this is a `User`". It passes, and it also passes on the wrong rows.
3. **`<T>` on an arrow function in a `.tsx` file.** TypeScript reads it as the start of a JSX tag.
4. **`row.id` inside the table with a bare `T`.** The editor refuses it, though every row on the page has an `id`.
5. **Column names typed `string[]`.** Then the developer needs `as any` to read `row[column]`, and a misspelled column shows the word `undefined` in every cell.

The rest of the lesson shows each mistake on a real page.

Developers really choose between four ways to type a shared table like this one. Only the last two fit real work, and each fits its own case:

```tree caption="Four ways to type a shared table, and when each one fits."
Four ways to type a shared table
- !1. Rows typed `any` [`row: any`] | Accepts every list | **Every check is gone** for every caller
- !2. Rows typed `object` with a type assertion [`user as User`] | Refuses every field read | Every caller writes an assertion that **also passes on the wrong rows**
- +3. One component per kind of row [`CustomersTable` `ProductsTable`] | Fits when the tables **really look different** | Two components to keep in step
- +4. One generic component [`DataTable<T>`] | Fits when one table shows **rows of different types** | Each caller **gets its own row type back**
```

Our two tables look the same and hold different rows, so we build the fourth way. The page is a small React project written in TypeScript, with the setup of Lesson 90:

```files title="store-admin: File Explorer" caption="Our project files: App.tsx holds the customers, the products, and the top line, and DataTable.tsx is the shared table."
  DataTable.tsx | generic component | Exports `DataTable` as default
```

**PRINCIPLES:** A generic component names the type of its rows once and hands that same type back to every caller. Four principles follow as the admin page grows:
1. **Principle 1: `DataTable<T>` names the row type once.** Write `<T>` after the component name, and use the same `T` for the rows and for the row the table hands back.
2. **Principle 2: `rows={users}` fills in `T` as `User`.** The caller writes no type. TypeScript fills in `T` from `rows`, and `onSelectRow` must fit that same type.
3. **Principle 3: `T extends { id: number }` lets the table read `row.id`.** Inside the table, a bare `T` has no known fields. A constraint promises that every row has a number `id`, and refuses rows that do not.
4. **Principle 4: `Extract<keyof T, string>[]` lets callers name only real columns.** A misspelled column is refused, and inside the table, `String()` turns each cell into text.

## PRINCIPLE | `DataTable<T>`: the rows go in as `T`, and the clicked row comes back as the same `T`

> [!PRINCIPLE]
> **Principle 1: Type Parameter: `DataTable<T>` Names the Row Type Once**
>
> *When one component shows rows of different types, write a type parameter after the component name, such as `function DataTable<T>`, and use the same `T` for the rows and for the row the component hands back.*
>
> With `rows: any[]`, the table forgets what a row is, so a misspelled field in a caller passes, and the user clicks a row and sees nothing selected. With `rows: object[]`, every caller must write a type assertion, and the assertion also passes on the wrong rows. A type parameter keeps the caller's row type: the rows go in as `T`, and the clicked row comes back as the same `T`. In a `.tsx` file, an arrow function writes `<T,>`, because `<T>` alone opens a JSX tag.
>
> **DO THIS:**
> ```tsx
> type DataTableProps<T> = { rows: T[]; onSelectRow: (row: T) => void };
> function DataTable~<T>~({ rows, onSelectRow }: DataTableProps<T>) { /* ... */ } // Each caller gets its own row type back
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> type DataTableProps = { rows: ~any[]~; onSelectRow: (row: any) => void }; // **WRONG:** user.emial passes, and the Selected line stays empty
> ```

In Lesson 92, you wrote `useState<User | null>(null)`. There you were the caller: you filled in a type argument for a function someone else wrote. Now you are on the other side. You write the function, and you leave a type parameter open for the caller to fill in.

The type parameter goes in angle brackets, right after the name of the function:

```tsx title="A generic component and its props type"
type DataTableProps~<T>~ = { rows: T[]; onSelectRow: (row: T) => void }; // The props type takes a T too
function DataTable~<T>~({ rows, onSelectRow }: DataTableProps<T>) { /* ... */ } // Declares T for the whole function
```

`T` is declared once, after `DataTable`, and used twice through the props type: once for the rows, and once for the row that `onSelectRow` receives. Using it twice is the whole point. The rows go in as `T`, and the clicked row comes back as the same `T`.

Many developers think `<T>` is a new kind of React prop. It is not. React never sees it. TypeScript removes it, with every other type, before the code runs.

### The first table, typed with `any`

Here is the first version of our shared table, typed with `any`:

```tsx title="src/DataTable.tsx"
type DataTableProps = {
  rows: ~any[]~; // Any rows at all: the type of a row is forgotten
  onSelectRow: (row: any) => void;
};

export default function DataTable({ rows, onSelectRow }: DataTableProps) {
  return (
    <table>
      <tbody>
        {rows.map(row => (
          <tr key={row.id} onClick={() => ~onSelectRow(row)~}> {/* Hands the clicked row to the caller */}
            <td>{row.name}</td>
          </tr>
        ))}
      </tbody>
    </table>
  );
}
```

`App` holds the customers and the top line, and places the table:

```tsx title="src/App.tsx"
import { useState } from 'react';
import DataTable from './DataTable';

type User = { id: number; name: string; email: string };

const users: User[] = [
  { id: 1, name: 'Taylor', email: 'taylor@example.com' },
  { id: 2, name: 'John', email: 'john@example.com' },
];

export default function App() {
  const [selected, setSelected] = useState('');

  return (
    <>
      <p>Selected: {selected}</p>
      <h2>Customers</h2>
      <DataTable rows={users} onSelectRow={user => setSelected(~user.email~)} /> {/* user is any here: nothing checks this name */}
    </>
  );
}
```

The user clicks Taylor's row:

### Giving the table a type parameter

Now we give the table its type parameter. Only `DataTable.tsx` changes:

```tsx title="src/DataTable.tsx"
type DataTableProps~<T>~ = { // T is the type of one row, filled in at each place the table is used
  rows: T[];
  onSelectRow: (row: T) => void;
};

export default function DataTable~<T>~({ rows, onSelectRow }: DataTableProps<T>) { // Passes its T on to the props type
  return (
    <table>
      <tbody>
        {rows.map(row => (
          <tr key={~row.id~} onClick={() => onSelectRow(row)}> {/* **WRONG:** Property 'id' does not exist on type 'T'. */}
            <td>{~row.name~}</td> {/* **WRONG:** Property 'name' does not exist on type 'T'. */}
          </tr>
        ))}
      </tbody>
    </table>
  );
}
```

The caller is now checked. In `App.tsx`, the `user` that comes back in the callback is a `User`. So `user.email` passes, and the editor refuses `user.emial` and suggests `email`.

The table itself now has two underlines, at `row.id` and at `row.name`. They do not change the page in the browser, because the types are removed before the code runs. Principle 3 fixes `row.id`, and Principle 4 replaces `row.name` with real columns.

### Where did that `T` come from?

`T` appears in three places in `DataTable.tsx`, and nobody gave it a value. Here is where it comes from:
1. The function name is followed by `<T>`. That declares the name `T` for the whole function, the same way the parameter list declares `rows` and `onSelectRow` for the function body.
2. The props type has its own `<T>`, so it can describe rows of any type.
3. In the parameter list, `DataTableProps<T>` passes the function's `T` on to the props type, as a type argument (Lesson 90). The props type then uses it for `rows` and for `onSelectRow`.

### VS | A function declaration vs. an arrow function with `<T,>`: the same component, and the comma stops a JSX tag

Many teams write components as arrow functions. Here are both shapes of the same generic component:

```tsx title="A generic component as a function declaration, and as an arrow function"
function DataTable~<T>~({ rows, onSelectRow }: DataTableProps<T>) { /* ... */ } // A function declaration
const DataTable = ~<T,>~({ rows, onSelectRow }: DataTableProps<T>) => { /* ... */ }; // An arrow function, with a comma after T
```

**Yes, it is the exact same thing!** Both declare `T`, and both pass it on to `DataTableProps<T>`. The only odd part is the comma after `T` in the arrow function. Without it, TypeScript reads `<T>` as a JSX tag. Here is what happens:
1. The developer writes `const DataTable = <T>({ rows }: DataTableProps<T>) => ...` in `DataTable.tsx`.
2. A `.tsx` file allows JSX, and in JSX, `<T>` is how a tag named `T` opens.
3. So TypeScript reads `<T>` as a JSX tag, not as a type parameter.
4. The editor reports a JSX error, not a type error, and more errors about the syntax follow it:

```text title="The editor's message"
JSX element 'T' has no corresponding closing tag.
```

The comma tells TypeScript: this is a list of type parameters, not a tag. A constraint, such as `<T extends { id: number }>`, does the same job, and Principle 3 adds one. A function declaration needs neither, because after `function DataTable`, a `<` can only open a list of type parameters.

### `object[]` and a type assertion in every caller

A team that knows `any` is dangerous often reaches for `object` instead. It sounds safer. It is not.

> [!DEFINITION]
> **What is a type assertion?** [NEW] A type assertion is `as` followed by a type, such as `(user as User).email`. It tells TypeScript "trust me, this value is a `User`", and TypeScript does, without checking. Many developers call it a cast. It removes the error, and it also lets the wrong value through (Lesson 93).

**Beware! Typing the rows `object[]` to avoid `any` makes every caller write a type assertion, and the assertion lets the wrong rows through.** Here is how it happens:
1. A team writes the shared table with `rows: object[]` and `onSelectRow: (row: object) => void`.
2. On the Customers table, the editor refuses `onSelectRow={user => setSelected(user.email)}`: `Property 'email' does not exist on type 'object'.` The type `object` says "some object", and nothing about its fields.
3. The developer writes `(user as User).email`, and it passes.
4. Every caller now has a type assertion.
5. A teammate copies the Customers tag for the Products table, changes `rows={users}` to `rows={products}`, and keeps `(user as User).email`.
6. The editor accepts it, because TypeScript allows an assertion from `object` to `User`. The assertion says "trust me", and TypeScript does.
7. The user clicks the Mug row. A product has no `email`, so the top line reads `Selected:` with nothing after it.

With `rows: T[]`, there is nothing to assert. In the copied Products tag, `user` is now a `Product`, so the editor refuses `user.email`.

## PRINCIPLE | `rows={users}`: TypeScript fills in `T` at each tag, so the caller writes no type

> [!PRINCIPLE]
> **Principle 2: Inferred Type Argument: `rows={users}` Fills In `T` as `User`**
>
> *Let the caller write no type argument: TypeScript fills in `T` from `rows` at each place the component is used, and every other prop that uses `T`, such as `onSelectRow`, must fit that same type.*
>
> A generic component gets a new `T` at every place it is used. The Customers tag gets `User`, and the Products tag gets `Product`, with no type written by the caller. Writing `<DataTable<User> ...>` gives the exact same result. When `rows` and the callback name two different types, the editor refuses the tag. Writing `(user: any)` on the callback throws away the type the table hands back.
>
> **DO THIS:**
> ```tsx
> <DataTable rows={users} onSelectRow={~user~ => setSelected(user.email)} /> {/* user is inferred as User */}
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> <DataTable rows={users} onSelectRow={(~user: any~) => setSelected(user.emial)} /> {/* **WRONG:** any turns off the check, and the Selected line stays empty */}
> ```

Remember `first(names)` at the start of this lesson? Nobody wrote `string`, and `T` was `string`. A generic component works exactly the same way, and each tag is one call.

### Two tables, two row types

The admin page needs a second table, for products. When the user clicks Taylor's row, the top line must show her email. When the user clicks the Mug row, the top line must show the mug and its price. Here are the two tags, for one shared component:

```tsx title="One component, two places of use"
<DataTable rows={~users~} onSelectRow={user => setSelected(user.email)} /> {/* Here T is User */}
<DataTable rows={~products~} onSelectRow={product => setSelected(product.name + ' for $' + product.price)} /> {/* Here T is Product */}
```

Neither tag writes a type. The Customers tag passes `users`, so `T` is `User` there. The Products tag passes `products`, so `T` is `Product` there. One component, two places of use, two different `T`s.

Hover over `user` in the editor, and it shows `User`. Hover over `product`, and it shows `Product` (Lesson 91).

> [!DEFINITION]
> **What does inferring a type mean?** [REVIEW] Inferring a type means that TypeScript works out the type from the code around it, so you do not write it. After `const name = 'John'`, TypeScript knows that `name` is a string. After `rows={users}`, it knows that `T` is `User` (Lesson 91).

### Where the type of `user` comes from

Nobody wrote `User` on the callback, yet `user.email` passes. Here is the chain:
1. `App.tsx` declares `const users: User[]`.
2. The tag passes `rows={users}`, and the props type says `rows: T[]`.
3. TypeScript fills in `T` with `User`, for this tag only.
4. The props type says `onSelectRow: (row: T) => void`, so the callback receives a `User`.

The table calls the value `row`, and the caller calls it `user`. It is the same value with two names. Each side picks the name that makes sense where it is.

### VS | With `<User>` on the tag vs. without it: the same `T`, so most callers write nothing

A caller may also write the type argument by hand, right after the component name on the tag:

```tsx title="The type of T inferred, and written by hand"
<DataTable rows={users} onSelectRow={user => setSelected(user.email)} /> {/* TypeScript infers User from rows */}
<DataTable~<User>~ rows={users} onSelectRow={user => setSelected(user.email)} /> {/* Our code writes User by hand */}
```

**Yes, it is the exact same thing!** In both tags, `T` is `User`, and `user` in the callback is a `User`. It is the same choice as `useState(false)` and `useState<boolean>(false)` (Lesson 92). Most callers write nothing. That is what interviewers mean by a table that callers use "without casting anything": no type assertion, and no type written at all.

### When the rows and the callback disagree

Every prop that uses `T` must agree on what `T` is. Suppose a developer copies the Customers tag for the Products table, changes the callback, and forgets to change `rows`:

```tsx title="The Products tag with the customers' rows by mistake"
<DataTable rows={~users~} onSelectRow={(p: Product) => setSelected(p.name + ' for $' + p.price)} /> {/* **WRONG:** rows and the callback name two different types */}
```

The editor refuses the tag, but it underlines `rows`, not the callback. Here is why:
1. The callback says its row is a `Product`.
2. TypeScript fills in `T` with `Product`, from the callback.
3. Then `rows` must be `Product[]`, and `users` is `User[]`.
4. The editor refuses `users`:

```text title="The editor's two messages"
Type 'User[]' is not assignable to type 'Product[]'.
Property 'price' is missing in type 'User' but required in type 'Product'.
```

With `<DataTable<User> rows={products} ...>`, the editor gives the mirror message: `Type 'Product[]' is not assignable to type 'User[]'.` Either way, the two props cannot disagree, and the mistake never reaches the page.

### `(user: any)` turns the check off

**Beware! Writing `any` on the callback turns off every check inside it, even though the table is generic.** Here is how it happens:
1. A developer does not trust inference and writes `(user: any) =>` in every `onSelectRow`.
2. The editor accepts it, because a function that takes `any` fits any callback type.
3. Inside that callback, `user` is `any`, so `setSelected(user.emial)` passes.
4. The user clicks Taylor's row, and the top line reads `Selected:` with nothing after it.

The table did its job and handed back a `User`. The `any` on the callback threw that type away. Write `user =>` with no type, and TypeScript fills it in.

## PRINCIPLE | `T extends { id: number }`: the table can read `row.id`, and rows without an `id` are refused

> [!PRINCIPLE]
> **Principle 3: Constraint: `T extends { id: number }` Lets the Table Read `row.id`**
>
> *Inside a generic component, a bare `T` has no known fields; add a constraint, such as `T extends { id: number }`, that asks for exactly the fields the component reads.*
>
> TypeScript checks the component once, for every `T` a caller could pass, so the editor refuses `row.id` on a bare `T`, even when every row on the page has an `id`. A constraint removes the types without an `id` from what `T` may be. Then `key={row.id}` passes, and a caller whose rows have no `id` is refused. Asking for more than the table reads, such as `Record<string, unknown>`, refuses rows typed with an `interface`.
>
> **DO THIS:**
> ```tsx
> function DataTable~<T extends { id: number }>~({ rows, onSelectRow }: DataTableProps<T>) { /* ... */ } // row.id is allowed for the key
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> function DataTable<T>({ rows, onSelectRow }: DataTableProps<T>) {
>   return <tbody>{rows.map(row => <tr key={~row.id~}></tr>)}</tbody>; // **WRONG:** Property 'id' does not exist on type 'T'.
> }
> ```

### The `key` every list needs is refused

Every list in React gives each item a `key`, and the best key is the ID from the database (Lesson 18). Our table writes it on each row:

```tsx title="The key of each row, inside DataTable<T>"
<tr key={~row.id~} onClick={() => onSelectRow(row)}> {/* **WRONG:** Property 'id' does not exist on type 'T'. */}
```

Every row in `users` and in `products` has an `id`. Yet the editor refuses `row.id`. Removing `key` is no way out: the Console then shows `Each child in a list should have a unique "key" prop.` (Lesson 18).

### Why a bare `T` has no `id`

The table does not see our rows. It sees `T`, and a bare `T` promises no fields at all. Here is why:
1. TypeScript checks `DataTable` once, not once for each caller.
2. At that moment, `T` could be any type a caller might pass: a `User`, a `Product`, or even a `string`.
3. A `string` has no `id`, so `row.id` cannot be allowed for every possible `T`.
4. So the editor refuses `row.id`, and it refuses `row.name` for the same reason.

Think of `greet(name: string)` from the start of this lesson. Inside `greet`, you may call `name.toUpperCase()`, because the parameter promises a string. A bare `T` promises nothing, so inside the table you may read nothing from a row.

### A constraint promises that every row has an `id`

To read `row.id`, the table must say what every `T` has at least. That is a constraint, written with `extends` after the type parameter:

```tsx title="src/DataTable.tsx" startLine="6"
export default function DataTable~<T extends { id: number }>~({ rows, onSelectRow }: DataTableProps<T>) { // Every T has at least a number id
```

> [!DEFINITION]
> **What is a constraint?** [NEW] A constraint is `extends` followed by a type, written after a type parameter, such as `T extends { id: number }`. It means "T may be any type that has at least these fields". It is not class inheritance. A `User` with an `id`, a `name`, and an `email` fits `{ id: number }`, because it has at least an `id` (Lesson 93).

Now `key={row.id}` passes. And the constraint also works at the caller. A teammate passes rows with no `id`:

```tsx title="Rows without an id"
<DataTable rows={~[{ label: 'New' }]~} onSelectRow={row => setSelected(row.label)} /> {/* **WRONG:** these rows have no id */}
```

The editor underlines `label` in the rows, and `row.label` in the callback:

```text title="The editor's two messages"
Object literal may only specify known properties, and 'label' does not exist in type '{ id: number; }'.
Property 'label' does not exist on type '{ id: number; }'.
```

Rows without an `id` never reach a table that needs one for its keys.

Here is the difference side by side:

```tsx title="A bare type parameter, and a type parameter with a constraint"
function DataTable~<T>~(props: DataTableProps<T>) { /* ... */ } // T may be anything: row.id is refused, and every caller is accepted
function DataTable~<T extends { id: number }>~(props: DataTableProps<T>) { /* ... */ } // T has an id: row.id passes, and rows without an id are refused
```

**It may look the same, but it is NOT the same thing!** Both tables show the same page for our customers and our products. The constraint changes only what TypeScript allows: inside the table, and at every caller.

The editor still underlines `<td>{row.name}</td>`: `Property 'name' does not exist on type 'T'.` The constraint promises only `id`, and that is on purpose. A customers table and a products table share an `id`, but a table of orders may have no `name`. Principle 4 replaces this cell.

### The same keys in two tables

The Customers table and the Products table both use the keys `1` and `2`. That is fine. react.dev says it plainly: "it's okay to use the same keys for JSX nodes in _different_ arrays." Each table maps its own array, so each key only has to be unique inside its own table.

### `Record<string, unknown>` refuses an `interface`

Some developers want a constraint that means "any object", and they write `Record<string, unknown>`. That is a type that ships with TypeScript. It describes an object where every string key holds a value of unknown type.

**Beware! A constraint that asks for "any object" refuses rows typed with an `interface`, and the developer cannot see why.** Here is how it happens:
1. A developer writes the constraint as `T extends Record<string, unknown>`.
2. A teammate describes contact rows with an `interface Contact`, not a `type`.
3. The editor refuses the Contacts table, with the two messages below.
4. The same rows described with `type` pass the same constraint. Our `type User` passes it.
5. Puzzled, the developer changes the `interface` to a `type`, or loosens the table to `any`.

```text title="The editor's two messages on the Contacts table"
Type 'Contact[]' is not assignable to type 'Record<string, unknown>[]'.
Index signature for type 'string' is missing in type 'Contact'.
```

The message talks about an index signature: a type's promise that any string key may be read. `Record<string, unknown>` asks for that promise. TypeScript lets an object type written with `type` stand in for it, and refuses an `interface`. The plain fix is to ask only for the fields the table really reads, `{ id: number }`. A smaller promise is easier for every caller to keep.

## PRINCIPLE | `Extract<keyof T, string>[]`: callers can name only the real fields of their rows

> [!PRINCIPLE]
> **Principle 4: `keyof`: `keyof T` Lets Callers Name Only Real Columns**
>
> *Type the column names with the field names of `T`, as `Extract<keyof T, string>[]`, and show each cell with `String(row[column])`.*
>
> `keyof T` turns the fields of the row type into the list of names a caller may write, so the editor refuses a misspelled column and suggests the right one. Inside the table, `T` is still unknown, and its field names may be strings, numbers, or symbols, so the editor refuses `key={column}` and `{column}`. The utility type `Extract` keeps only the string names. A field of an unknown `T` may hold anything, so `String()` turns each cell into text. With `columns: string[]` and `as any`, a misspelled column shows `undefined` in every cell.
>
> **DO THIS:**
> ```tsx
> type DataTableProps<T> = { rows: T[]; columns: ~Extract<keyof T, string>~[]; onSelectRow: (row: T) => void }; // 'emial' is refused at the caller
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> type DataTableProps<T> = { rows: T[]; columns: ~string[]~; onSelectRow: (row: T) => void }; // **WRONG:** 'emial' passes, and every cell shows undefined
> ```

Our table still shows only `row.name`. A real table lets each caller choose its columns: `name` and `email` for customers, `name` and `price` for products. So the table gets a new prop, `columns`, a list of field names. The question is how to type that list so that `'emial'` is refused.

### `keyof` gives the field names of a type

TypeScript has an operator, `keyof`, that turns the fields of a type into a list of names:

```tsx title="keyof on its own"
type User = { id: number; name: string; email: string };
type UserField = ~keyof User~; // The same as 'id' | 'name' | 'email'
```

**`keyof User` is a union of the field names of `User`:** `'id'`, `'name'`, or `'email'`, and nothing else.

That is exactly what our columns need. The caller names the fields to show, and the editor allows only fields the rows really have:

```tsx title="The Customers tag with a misspelled column"
<DataTable rows={users} columns={['name', ~'emial'~]} onSelectRow={user => setSelected(user.email)} /> {/* **WRONG:** emial is not a field of User */}
```

```text title="The editor's message"
Type '"emial"' is not assignable to type 'keyof User'. Did you mean '"email"'?
```

Compare the two ways to type the `columns` prop:

```tsx title="Column names as any string, and as field names of T"
columns: ~string[]~; // Accepts 'emial'
columns: ~(keyof T)[]~; // Refuses 'emial' and suggests 'email'
```

**It may look the same, but it is NOT the same thing!** In the browser, both pass the same strings. Only `(keyof T)[]` knows which strings are real field names. And because `T` is `User` at the Customers tag, as Principle 2 showed, the list there is `'id' | 'name' | 'email'`.

### Inside the table, `key={column}` is refused

Suppose the table takes `columns: (keyof T)[]`. It uses the columns twice: once for the header cells, and once for the cells of each row. A header cell is a `<th>`, and the header row sits in a `<thead>`:

```tsx title="src/DataTable.tsx"
      <thead>
        <tr>{columns.map(column => <th key={~column~}>{column}</th>)}</tr> {/* **WRONG:** key refuses a column of type keyof T */}
      </thead>
```

Every column on our page is a plain word, such as `name`. Yet the editor refuses the column twice: once in `key`, and once between the tags:

```text title="The editor's two messages"
Type 'string | number | symbol' is not assignable to type 'Key | null | undefined'.
Type 'string | number | symbol' is not assignable to type 'ReactNode'.
```

**The table does not know `T`, so it must allow every kind of field name, and some kinds are not allowed in `key` or in JSX.** Here is the chain:
1. Inside the table, `T` is still any type with an `id`. TypeScript checks the table once, for every possible `T`.
2. In JavaScript, a field name may be a string or a Symbol. MDN: "Each property name is a string or a Symbol." A Symbol is a special kind of value that JavaScript can use as a field name. TypeScript also counts number names, such as `0` in an array.
3. So for an unknown `T`, `keyof T` may be a string, a number, or a symbol.
4. React's types say a `key` may be a string, a number, or a bigint. And `ReactNode`, the list of things JSX can show, has no symbol (Lesson 90).
5. So the editor refuses the column in both places.

At the caller, there is no such problem. There, `T` is a known type, `User`, whose field names are all strings.

### `Extract<keyof T, string>` keeps only the string names

The fix is to keep only the field names that are strings:

```tsx title="src/DataTable.tsx" startLine="1"
type DataTableProps<T> = {
  rows: T[];
  columns: ~Extract<keyof T, string>~[]; // Only the field names that are strings
  onSelectRow: (row: T) => void;
};
```

> [!DEFINITION]
> **What is `Extract`?** [NEW] `Extract` is a utility type: a type that ships with TypeScript, needs no import, and builds a new type from one you already have. `Extract<A, B>` keeps only the members of the union `A` that fit `B`. So `Extract<keyof T, string>` keeps only the field names of `T` that are strings (Lesson 93).

Now the column passes in `key` and between the tags. And the caller still gets all three field names of `User`, because all three are strings.

Some code writes the same type another way:

```tsx title="Two ways to keep only the string field names"
columns: ~Extract<keyof T, string>~[]; // Keeps the members of keyof T that fit string
columns: ~(keyof T & string)~[]; // Keeps the part of keyof T that is also a string
```

**Yes, it is the exact same thing!** Both give the list of string field names, and both pass the editor for our table.

### `String(row[column])` turns every cell into text

Each row now shows one cell per column. `row[column]` reads the field whose name is held in `column`, as plain JavaScript does. For example, `user['email']` is the same as `user.email`. MDN calls this a property accessor. The editor refuses the cell again:

```tsx title="One cell per column, inside each row"
{columns.map(column => <td key={column}>{~row[column]~}</td>)} {/* **WRONG:** a field of an unknown T may hold anything */}
```

The editor prints a long message that starts like this:

```text title="The editor's message"
Type 'T[Extract<keyof T, string>]' is not assignable to type 'ReactNode'.
```

The reason is the same as for `row.id`: the table does not know what the fields of `T` hold. A field could hold an object or a function, and JSX cannot show those.

`String()` is a function that ships with JavaScript and turns any value into text: `String(12)` is `'12'`. MDN notes that `String()` even converts Symbols without throwing an error. So the cell becomes:

```tsx title="One cell per column, as text"
{columns.map(column => <td key={column}>{~String(row[column])~}</td>)} {/* Always text, so 12 shows as 12 */}
```

**It may look the same, but it is NOT the same thing** for the editor. In the browser, our names, emails, and prices show the same with `{row[column]}` and with `{String(row[column])}`. Only `String()` promises text for every field of every `T`.

### The table with its columns

Here is `DataTable.tsx` with the constraint and the columns:

```tsx title="src/DataTable.tsx"
type DataTableProps<T> = {
  rows: T[];
  columns: ~Extract<keyof T, string>~[]; // Callers may name only string fields of their own rows
  onSelectRow: (row: T) => void;
};

export default function DataTable<T extends { id: number }>({ rows, columns, onSelectRow }: DataTableProps<T>) {
  return (
    <table>
      <thead>
        <tr>{columns.map(column => <th key={column}>{column}</th>)}</tr>
      </thead>
      <tbody>
        {rows.map(row => (
          <tr key={row.id} onClick={() => onSelectRow(row)}>
            {columns.map(column => <td key={column}>{~String(row[column])~}</td>)} {/* Every cell becomes text */}
          </tr>
        ))}
      </tbody>
    </table>
  );
}
```

`App.tsx` adds one prop to each tag:

```tsx title="src/App.tsx" startLine="24"
      <DataTable rows={users} ~columns={['name', 'email']}~ onSelectRow={user => setSelected(user.email)} /> {/* Only name, email, or id are allowed here */}
      <h2>Products</h2>
      <DataTable rows={products} ~columns={['name', 'price']}~ onSelectRow={product => setSelected(product.name + ' for $' + product.price)} /> {/* Only name, price, or id are allowed here */}
```

The page now shows both tables with their header cells, and the prices show as `12` and `20`:


In the Elements panel, the Customers table is plain HTML. The header row holds the field names, and each row holds one cell per column:

```dom caption="The Customers table in the Elements panel: one header cell and one data cell per column."

  <thead>
+   <tr><th>name</th><th>email</th></tr> | note: One th per column in columns
  </thead>

+   <tr><td>Taylor</td><td>taylor@example.com</td></tr> | note: One td per column, as text
    <tr><td>John</td><td>john@example.com</td></tr>
  </tbody>

```

### `columns: string[]` and `as any`

**Beware! With `columns: string[]`, a misspelled column passes the editor, and the user sees the word `undefined` in every cell of that column.** Here is how it happens:
1. A developer types `columns: string[]`.
2. Inside the table, the editor refuses `row[column]`, with the message below.
3. The developer writes the cell as `String((row as any)[column])`, and it passes.
4. A caller writes `columns={['name', 'emial']}`, and the editor says nothing.
5. The user opens the admin page. The second column of the Customers table is headed `emial`, and every cell under it shows the word `undefined`, because `String(undefined)` is the text `'undefined'`.

```text title="The editor's message on row[column] in step 2"
Element implicitly has an 'any' type because expression of type 'string' can't be used to index type '{ id: number; }'.
```

Here is the page the user sees after step 5:


With `Extract<keyof T, string>[]`, the editor refuses the same typo at the caller and suggests `email`. And the table needs no `as any`.

## All 4 Principles Together

### The complete project

Here is the complete shared table. It names its row type once, reads `row.id` through its constraint, and accepts only real column names:

```tsx title="src/DataTable.tsx"
type DataTableProps~<T>~ = { // Principle 1: one T for the rows and for the clicked row
  rows: T[];
  columns: ~Extract<keyof T, string>~[]; // Principle 4: only real string field names
  onSelectRow: (row: T) => void;
};

export default function DataTable~<T extends { id: number }>~({ rows, columns, onSelectRow }: DataTableProps<T>) { // Principle 3: every row has an id
  return (
    <table>
      <thead>
        <tr>{columns.map(column => <th key={column}>{column}</th>)}</tr>
      </thead>
      <tbody>
        {rows.map(row => (
          <tr key={row.id} onClick={() => onSelectRow(row)}>
            {columns.map(column => <td key={column}>{String(row[column])}</td>)}
          </tr>
        ))}
      </tbody>
    </table>
  );
}
```

And here is the admin page that uses it twice, with no type written on either tag:

```tsx title="src/App.tsx"
import { useState } from 'react';
import DataTable from './DataTable';

type User = { id: number; name: string; email: string };
type Product = { id: number; name: string; price: number };

const users: User[] = [
  { id: 1, name: 'Taylor', email: 'taylor@example.com' },
  { id: 2, name: 'John', email: 'john@example.com' },
];

const products: Product[] = [
  { id: 1, name: 'Mug', price: 12 },
  { id: 2, name: 'T-shirt', price: 20 },
];

export default function App() {
  const [selected, setSelected] = useState('');

  return (
    <>
      <p>Selected: {selected}</p>
      <h2>Customers</h2>
      <DataTable rows={~users~} columns={['name', 'email']} onSelectRow={user => setSelected(user.email)} /> {/* Principle 2: T is User */}
      <h2>Products</h2>
      <DataTable rows={~products~} columns={['name', 'price']} onSelectRow={product => setSelected(product.name + ' for $' + product.price)} /> {/* Principle 2: T is Product */}
    </>
  );
}
```

### The order in which React calls the components

When the page loads, React calls `App`. `App` returns the top line, two headings, and two `DataTable` tags, so React calls `DataTable` twice, once for each tag. TypeScript filled in `T` for each tag before the code ran, and the browser never sees it. When the user clicks a row, the table calls `onSelectRow`, `App` updates `selected`, and React renders the page again:

```tree caption="The order of the calls: App, then DataTable for the customers, then DataTable for the products, and then the callback on a click."
`App` [1. React calls it when the page loads] | Returns the **top line** and **two `DataTable` tags**
- +`DataTable` for Customers [2. Here `T` is `User`] | Returns a table with **name and email** | Keys **1 and 2**
- +`DataTable` for Products [3. Here `T` is `Product`] | Returns a table with **name and price** | Keys **1 and 2** again, in **another array**
- +`onSelectRow` [4. The user clicks the Mug row] | Receives a **`Product`** | `App` sets **`Mug for $12`** and React renders again
```

| What the code writes | Where | What the editor checks | What it prevents |
| :--- | :--- | :--- | :--- |
| **`DataTable<T>` with `rows: T[]` and `onSelectRow: (row: T) => void`** | `DataTable.tsx` | Each caller's callback against its own row type | An empty `Selected:` line after a misspelled field |
| **No type on the tag, `rows={users}`** | `App.tsx` | `T` is `User` at one tag and `Product` at the other | A type assertion in every caller |
| **`T extends { id: number }`** | `DataTable.tsx` | `row.id` inside the table, and rows without an `id` at the caller | Rows with no `id` for their keys |
| **`columns: Extract<keyof T, string>[]`** | `DataTable.tsx` | Every column name against the real fields of the rows | A column of `undefined` cells |
| **`String(row[column])`** | `DataTable.tsx` | Every cell is text JSX can show | A cell that JSX cannot show, such as an object |

Remember the one sentence of this lesson. **A type parameter is a name for a type, filled in at each place the component is used, so one table takes rows of any type and hands each caller its own row type back.**

## For the Interview

> **The Interview Question:** How do you type generic components and flexible data collections in React?

### How to Answer Clearly in 30 Seconds

"I write a type parameter on the component function, such as `function DataTable<T>`, and use it in the props type: `rows: T[]` and `onSelectRow: (row: T) => void`. The rows go in as `T`, and the clicked row comes back as the same `T`, so callers never cast anything. Four details make it safe:
1. **Inference**: callers usually write no type. TypeScript fills in `T` from `rows` at each place the component is used, so the Customers table gets `User` and the Products table gets `Product`.
2. **Constraint**: inside the component, a bare `T` has no fields, so I write `T extends { id: number }` to read `row.id` for the `key`. I ask only for the fields the component reads.
3. **`keyof`**: I type the columns with the field names of `T`, so a misspelled column is refused. Inside the component, I use the utility type `Extract<keyof T, string>`, because `keyof T` may include symbols, which `key` and JSX refuse, and I show each cell with `String()`.
4. **Arrow functions**: in a `.tsx` file, I write `<T,>`, because `<T>` alone is read as a JSX tag.

`any[]` turns off checking for every caller, and `object[]` forces a type assertion in every caller. The types are removed before the code runs, so the page is the same either way. The difference is what the editor catches."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Which other utility types do you use with props and data?"**
   Each one ships with TypeScript and builds a new type from one I already have. `Pick<T, K>` keeps some fields of a type. `Omit<T, K>` removes some, such as `Omit<User, 'id'>` for a form that creates a user before the server gives it an `id`; an object with an `id` is then refused. `Partial<T>` makes every field optional, such as a filter where the admin fills in only some fields. `Record<K, V>` builds an object type from a list of names, such as a header label for each column: `Record<'name' | 'email', string>` refuses an object that forgets `email`.
2. **"How would you let the caller render a custom cell, and keep it typed?"**
   With a render prop that receives `T`, the way `renderItem` works (Lesson 89): `renderCell: (row: T) => React.ReactNode`. The caller then gets a typed row inside the JSX it returns, so `renderCell={user => <b>{user.emial}</b>}` is refused with the same `Did you mean 'email'?`. For one cell per column, I combine `keyof T` with the type of one field, `T[K]`, which means "the type of the field named `K` in `T`". A column typed with `K extends keyof T` and `render?: (value: T[K]) => React.ReactNode` lets `value.toUpperCase()` pass for the `email` column and refuses it for the `price` column, because a price is a `number`.
3. **"What happens when a caller passes an empty array?"**
   With `rows={[]}`, there is nothing to infer from, so TypeScript gives `T` the type `never`, as it does for `useState([])` (Lesson 92). A callback that reads `row.name` is then refused with `Property 'name' does not exist on type 'never'.` The fix is a typed array, such as `const users: User[] = []`, or a type argument on the tag, `<DataTable<User> rows={[]} ...>`.

```tree caption="Interview summary: one type parameter, filled in at each tag, narrowed by a constraint, and used for the column names."
How a generic table keeps each row's type
- +Type parameter [`DataTable<T>`] | **One `T`** for the rows and the clicked row | Each caller **gets its own row type back**
- +Inference [`rows={users}`] | TypeScript **fills in `T`** at each tag | Callers write **no type and no cast**
- +Constraint [`T extends { id: number }`] | Promises the fields the table **reads** | `row.id` passes, rows **without an id are refused**
- +Field names [`Extract<keyof T, string>`] | Columns are **real string field names** | A misspelled column is **refused with a suggestion**
```
