# Lecture 41: The action Prop on a Form

*(What changes when a form hands its data to a function instead of a URL?)*

> INTERVIEW QUESTION | ❱ CORE | What is the action prop on a form, and how do actions modernize form handling?

---

## VS | `action` with a URL vs. `action` with a function: the URL loads a new page, the function keeps your page

> Handling a form with the classic `onSubmit` makes you write extra code to stop the page reload, read every input, and empty the fields afterward. **You should pass your function to `<form action={...}>` instead.** React then hands the field values to your function, runs it without reloading the page, and resets the form when it finishes.

In React, many forms send their data and then stay on the same page, like a message box, a comment field, or a newsletter signup. In plain HTML, the `action` of a form holds a URL, and the browser loads a new page when the user submits. In React, we usually stop that in `onSubmit` with `e.preventDefault()`, and then read the fields and clear them by hand. **In React 19, you can pass a function to `action`. React collects the fields, calls your function without reloading the page, and clears the form for you.**

Take a message box where the user types a note and clicks Send. You want to read the note, send it, and leave the box empty for the next one. Ask yourself: how many of these steps do I have to write myself? With a function in `action`, only the sending. React hands your function the form data, and it resets the form when your function ends.

**Why:** A URL in `action="/send"` makes the browser leave your page and load a new one, so the app starts again from zero and every state is lost. With `onSubmit`, you must call `e.preventDefault()`, build the `FormData` by hand, and call `reset()` yourself. That is three steps of setup for every form. A function in `action` does all three for you.

### The `action` Attribute in Plain HTML

Let's start from plain HTML. A `<form>` tag has had an `action` attribute since the first days of the web. There, it holds a URL:

```html title="A form in plain HTML"
<form ~action="/send"~> <!-- The browser sends the form data to /send and loads a new page -->
  <input name="message" />
  <button type="submit">Send</button>
</form>
```

The user clicks Send, and the browser takes over. It collects every field that has a `name` and sends the data to the server address `/send`. Then it leaves your page and shows the server's answer as a brand-new page.

In a React app, that is a disaster. The new page starts the app from zero, so everything React kept in state is gone.

That is why, in Lesson 40, you stopped the browser and read the form yourself:

```jsx title="Reading the form with onSubmit, as in Lesson 40"
function handleSubmit(~e~) { // 1. React passes the submit event
  ~e.preventDefault();~ // 2. You stop the browser from loading a new page
  const formData = ~new FormData(e.currentTarget)~; // 3. You build the form data from the <form> element
  alert(formData.get('message'));
}

<form onSubmit={handleSubmit}>
```

> [!DEFINITION]
> **What is FormData?** [REVIEW] `FormData` is a browser object that holds the data of a form: one entry for each field that has a `name`.
> You read one entry with `formData.get('message')`, where `'message'` is the `name` written on the `<input>` field.
> A field without `name` is left out, and `formData.get` returns `null` for it, with no error (Lesson 40).

In React 19, the same `action` attribute can hold a function instead of a URL:

```jsx title="Reading the form with action, in React 19"
function sendMessage(~formData~) { // React passes the form data itself
  alert(formData.get('message'));
}

<form ~action={sendMessage}~> {/* React calls sendMessage when the user clicks Send */}
```

Look at what disappeared. The three numbered lines of the `onSubmit` version are gone:
1. **No event.** The function gets the form data, not `e`.
2. **No `e.preventDefault()`.** React handles the submit itself, so the browser never loads a new page.
3. **No `new FormData(...)`.** React builds the form data and passes it in.

The data is nothing new. It is the exact same `FormData` object from Lesson 40. You still read the message field with `formData.get('message')`. The only change is who builds it. With `onSubmit`, your code builds it. With `action`, React builds it.

> [!DEFINITION]
> **What is an action?** [NEW] An action is a function you pass to the `action` prop of a `<form>`: `<form action={sendMessage}>`.
> When the user submits the form, React calls it with one argument, the form data. It is a `FormData` object, not an event.
> The browser does not load a new page. Your component keeps running, with its state in place.
> In everyday English, an action is something you do. In React's docs, it is the function that does the work of the form when the user submits it (Lesson 41).

```tree caption="The action attribute on a form, holding a URL in plain HTML and holding a function in React 19."
Two things the `action` attribute on a `<form>` can hold
- !A URL, plain HTML [`action="/send"`] | The **browser** sends the form data to a server address | The browser **loads a new page**, and React state is lost
- +A function, React 19 [`action={sendMessage}`] | **React** calls the function with the form data | The **page stays**, and the component keeps its state
```

### The Rule of Thumb: an action gets the form data, not an event

**The first parameter of an action is the form data. Name it `formData`, read each field with `formData.get`, and write nothing to stop the page: React already keeps it.**

Why does this matter? Picture the message field of a chat. The user types `Hi` and clicks Send. Every chat user expects two things: `Hi` appears in the conversation, and the field is empty again.

With `onSubmit`, your code has two jobs on top of adding the message, and each one is easy to miss:
1. **Stopping the reload.** Forget `e.preventDefault()`, and the browser sends the form to the current address and reloads the page. The app starts from zero, the conversation goes back to its first message, and `Hi` is gone.
2. **Emptying the field.** After the send, the `<input>` field still shows `Hi`. Nothing empties it until your code does.

With `action`, React does both jobs. Your code writes neither.

A senior developer also knows the three classic mistakes:
1. **The old `onSubmit` handler, moved into `action` unchanged.** It calls `e.preventDefault()` on a `FormData` object, JavaScript throws an error, and the chat disappears.
2. **A controlled field inside an action form.** React empties only uncontrolled fields, so the sent text stays in the field.
3. **An `isSending` state written by hand.** React already tracks the wait of every action.

The rest of the lesson shows each mistake on a real chat.

The project has five files. One of them, the file api.js, stands in for a real server. It waits one second and then answers, the way a slow server does. It arrives in Principle 3:

Now let's build the chat, and break it on the way:

**PRINCIPLES:** Put a function in `action`, and React calls it with the form data. No event, no `preventDefault`, and React empties the fields after the function succeeds. Three principles follow:
1. **Principle 1: The Action Receives the Form Data.** React calls the function with one argument, the form data, and the page stays. A leftover `e.preventDefault()` throws an error.
2. **Principle 2: React Empties the Fields After the Action Succeeds.** Every uncontrolled field goes back to its start value. A controlled field keeps showing what its state holds.
3. **Principle 3: An async Action Empties the Field After await.** React waits for the server, keeps the page usable, and empties the field only when the action has succeeded.

## PRINCIPLE | `action={sendMessage}`: React calls the function with the form data, and the page stays

> [!PRINCIPLE]
> **Principle 1: The action Prop: React Calls the Function with the Form Data**
>
> *Pass a function to `<form action>`; when the user submits the form, React calls it with one argument, the form data, and the page does not reload.*
>
> With `onSubmit`, your code stops the reload and builds the form data by hand. With a function in `action`, React handles the submit, builds the `FormData` object from the `name` of every field, and passes it in. The action never sees an event, so a leftover `e.preventDefault()` throws an error, and the page goes blank.
>
> **DO THIS:**
> ```jsx
> function sendMessage(~formData~) { // React passes the form data
>   setMessages([...messages, { id: nextId++, text: formData.get('message') }]);
> }
> <form action={sendMessage}>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function sendMessage(e) {
>   ~e.preventDefault();~ // **WRONG:** e is the form data, and FormData has no preventDefault!
> }
> <form action={sendMessage}>
> ```

### Where does `formData` come from?

You never create it. React does, exactly the way you did by hand in Lesson 40. Here is what happens when the user clicks Send:
1. React stops the browser from sending the form to a server address.
2. React collects every field of the form by its `name` into one `FormData` object.
3. React calls `sendMessage` with that object as its only argument.

So the page does not reload, although no line of your code stops the reload. When `action` holds a function, the browser never loads a new page.

### Building the chat with `action`

The list comes from `messages` in state. Each new message gets its ID from `nextId`, a counter above the component (Lesson 19):

```jsx title="src/components/ChatRoom.jsx" startLine="1"
import { useState } from 'react';

const initialMessages = [{ id: 1, text: 'Hello there!' }];
let nextId = 2;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);

  function sendMessage(~formData~) { // 1. React calls this on Send, with the form data
    setMessages([...messages, { id: nextId++, text: ~formData.get('message')~ }]); // 2. Adds the typed text to the list
  }

  return (
    <section>
      <ul>
        {messages.map(m => <li key={m.id}>{m.text}</li>)}
      </ul>
      <form ~action={sendMessage}~> {/* 3. Hands sendMessage to React, not to the browser */}
        <input name="message" />
        <button type="submit">Send</button>
      </form>
    </section>
  );
}
```

`App` renders the chat:

```jsx title="src/App.jsx" startLine="1"
import ChatRoom from './components/ChatRoom.jsx';

export default function App() {
  return ~<ChatRoom />~; // React calls ChatRoom and puts the list and the form on the page
}
```

The user types `Hi` into the field and clicks Send. `Hi` joins the list, and the page stays:

### The mistake: moving the old `onSubmit` handler into `action`

A developer who knows `onSubmit` well moves the old handler into `action` and changes nothing else:

```jsx title="src/components/ChatRoom.jsx" startLine="9"
function sendMessage(~e~) { // **WRONG:** React passes the form data here, not an event
  ~e.preventDefault();~ // **WRONG:** FormData has no preventDefault, so JavaScript throws a TypeError
  const formData = new FormData(e.target);
  setMessages([...messages, { id: nextId++, text: formData.get('message') }]);
}
```

**The user clicks Send, and the whole chat disappears from the page.** Here is what happens, in order:
1. React calls `sendMessage` with the form data. The parameter is named `e`, but it holds a `FormData` object.
2. A `FormData` object has no `preventDefault` method, so JavaScript throws an error on the first line.
3. React sends an error thrown by an action to the nearest error boundary, the component that catches an error and shows a fallback screen (Lesson 38).
4. Our page has no error boundary, so React removes the whole page from the screen.

```page caption="The chat after the user clicks Send when the action still calls e.preventDefault: nothing is left on the screen."
blank
console: Uncaught TypeError: e.preventDefault is not a function
  warn: An error occurred in the <form> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The user sees neither the list nor the field, and the message is lost. The fix takes two steps:
1. Name the parameter for what it is: `formData`.
2. Delete the line with `e.preventDefault()` and the line with `new FormData(e.target)`.

Remember: an action gets the form data, not an event.

## PRINCIPLE | `action` with an uncontrolled field: React empties the field after the action succeeds

> [!PRINCIPLE]
> **Principle 2: The Automatic Reset: React Empties Uncontrolled Fields After the Action Succeeds**
>
> *After the function in `action` succeeds, React resets every uncontrolled field in the form; a controlled field keeps showing its state.*
>
> A chat field that still shows the sent text invites the user to send it twice. With `onSubmit`, your code must empty the field itself. With a function in `action`, React resets the form after the action ends without an error, so a field with only a `name` is empty again. A field with `value` shows what state holds, so React's reset cannot empty it.
>
> **DO THIS:**
> ```jsx
> <form action={sendMessage}>
>   ~<input name="message" />~ {/* Uncontrolled: React empties it after Send */}
> </form>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <form action={sendMessage}>
>   <input name="message" ~value={text}~ onChange={e => setText(e.target.value)} /> {/* **WRONG:** controlled, so the field still shows Hi after Send */}
> </form>
> ```

Both forms hold the same `<input name="message" />`. It has no `value`, so it is an uncontrolled field: the browser keeps its text (Lesson 20). The user types `Hi` into each one and clicks Send:

### Who empties the field?

React does. No line of your code empties it. Here is what happens after the user types `Hi` and clicks Send:
1. React calls `sendMessage` with the form data.
2. `sendMessage` adds `Hi` to the list and ends without an error.
3. React **resets** the form: every uncontrolled field goes back to its start value. Our field started empty, so it is empty again.
4. The list shows `Hi`, and the field is ready for the next message.

You know this reset from plain JavaScript: a `<form>` element has its own `reset()` method. With `onSubmit`, React does no reset, so you call that method by hand, `e.currentTarget.reset()`. With `action`, React resets the form for you. React's docs list it among the things React does when `action` holds a function: it "resets the form's uncontrolled fields when the function succeeds."

### The mistake: a controlled field inside an action form

A developer makes every field controlled out of habit (Lesson 20), and adds a `text` state to `ChatRoom`:

```jsx title="src/components/ChatRoom.jsx" startLine="8"
const [text, setText] = useState('');
```

```jsx title="src/components/ChatRoom.jsx" startLine="19"
<form action={sendMessage}>
  <input
    name="message"
    ~value={text}~ // **WRONG:** React resets only uncontrolled fields, so this field keeps showing text
    onChange={e => setText(e.target.value)}
  />
  <button type="submit">Send</button>
</form>
```

The user types `Hi` and clicks Send. `Hi` appears in the list, but the field still shows `Hi`:

```page caption="The chat after Send when the message field is controlled with value and onChange: the field still shows Hi."
line: Hello there!
line: Hi
form:
  field: | Hi | bad
  submit: Send
console: quiet
```

Why? The field shows only what `text` holds, and nothing changed `text`. React resets only the uncontrolled fields of the form, and this field is controlled.

The developer then adds `setText('')` inside `sendMessage`. That is one more line of work that the uncontrolled field never needed. The simpler fix is to delete the `text` state and the `onChange` handler with it. Keep only `name="message"` on the field, with no `value`.

Remember: in an action form, a field with only a `name` empties itself after Send. React does it.

## PRINCIPLE | `async` action: React waits for `await`, then empties the field

> [!PRINCIPLE]
> **Principle 3: The async Action: React Waits, Then Resets the Form**
>
> *The function in `action` may be `async`; React waits for its promise, runs it in a Transition, and resets the form only after it succeeds.*
>
> A real chat must wait for the server before the message counts as sent. With `async` and `await`, the action pauses until the server answers. React waits with it, keeps the page usable, tracks the pending state, and empties the field only after the action ends without an error.
>
> **DO THIS:**
> ```jsx
> ~async~ function sendMessage(formData) { // React waits for this action, then empties the field
>   const message = { id: nextId++, text: formData.get('message') };
>   await deliverMessage(message.text);
>   setMessages(m => [...m, message]);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> async function sendMessage(formData) {
>   ~setIsSending(true)~; // **WRONG:** a hand-written copy of the pending state React already tracks
>   await deliverMessage(formData.get('message'));
>   setIsSending(false);
> }
> ```

### A function that waits: `async` and `await`

A real chat sends each message to a server first, and the server takes time to answer. We have no real server, so we write a stand-in in a new file, api.js. It waits one second and then gives the text back:

```js title="src/api.js" startLine="1"
export ~async~ function deliverMessage(text) { // async: this function may wait inside
  ~await~ new Promise(resolve => setTimeout(resolve, 1000)); // await: pauses here for one second
  return text; // Runs only after the wait
}
```

JavaScript gives you two words for a function that waits:
1. **`async`**, written in front of `function`, says that the function may wait inside. Calling it always gives back a promise (Lesson 33).
2. **`await`**, written in front of a promise, pauses the function on that line until the promise is done. Then it gives back the value inside the promise.

An action may be `async` too. Then React waits for it. React counts the action as finished only when the promise it returns is done.

### The chat waits for the server

Now `sendMessage` becomes `async`. It builds the new message, waits for the server, and only then adds the message to the list:

```jsx title="src/components/ChatRoom.jsx" startLine="1"
import { useState } from 'react';
import { deliverMessage } from '../api.js';

const initialMessages = [{ id: 1, text: 'Hello there!' }];
let nextId = 2;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);

  ~async~ function sendMessage(formData) { // 1. React waits for this action until its promise is done
    const message = { id: nextId++, text: formData.get('message') }; // 2. Builds the message once, before the wait
    ~await deliverMessage(message.text)~; // 3. Pauses here for one second
    setMessages(~m => [...m, message]~); // 4. Adds the message to the newest list
  }
```

The rest of the chat file stays the same. Two lines change, and each one has a reason:
1. **The updater `m => [...m, message]`.** Inside `sendMessage`, `messages` is the list from the moment of the click (Lesson 15). Say the user sends a second message during the wait. Both calls then start from the same old list, and the second message pushes the first one out. The updater gets the newest list from React instead, so both messages stay (Lesson 16).
2. **The message is built before `await`, outside the updater.** `<StrictMode>` calls an updater twice, so `nextId++` inside it would use up two IDs for one message (Lesson 14).

### What the user sees during that one second

For one second after Send, the page seems to do nothing. The field still shows `Hi`, and the list does not show it yet. Here is what happens, in order:
1. The user types `Hi` and clicks Send.
2. React calls `sendMessage` with the form data.
3. `sendMessage` reaches `await deliverMessage(...)` and pauses for one second.
4. The promise is done, and `setMessages` adds `Hi` to the list.
5. `sendMessage` ends without an error, so React resets the form, and the field is empty.

The field empties only after the action succeeds. So the text stays in front of the user while the server is still working.

During that second, the page stays usable: the user can still scroll, click, and type. React runs every action in a **Transition**, React's word for an update that does not block the page. React also keeps a record that this action has started and has not ended yet. React's docs call it the **pending state** of the action.

### The mistake: tracking the wait by hand

A developer who tracked a form by hand in Lesson 21 brings the same habit to the action:

```jsx title="src/components/ChatRoom.jsx" startLine="9"
const [isSending, setIsSending] = useState(false);

async function sendMessage(formData) {
  ~setIsSending(true)~; // **WRONG:** React already tracks the pending state of every action
  const message = { id: nextId++, text: formData.get('message') };
  await deliverMessage(message.text);
  setMessages(m => [...m, message]);
  ~setIsSending(false)~; // **WRONG:** the second line to copy next to every form
}
```

This works. But now the developer copies the same state and the same two lines into every form of the app. React already tracks this pending state for every action.

Two React Hooks read it in the next lessons. `useActionState` comes in Lesson 42. `useFormStatus` comes in Lesson 43, and it lets a Send button show `Sending...`.

Remember: an `async` action waits for the server, and React waits with it. Then React empties the field.

## All 3 Principles Together

### The complete project

Here is the finished chat. The stand-in server waits one second, and the chat sends each message through an `async` action:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

```jsx title="src/App.jsx"
import ChatRoom from './components/ChatRoom.jsx';

export default function App() {
  return <ChatRoom />;
}
```

```js title="src/api.js"
export async function deliverMessage(text) {
  await new Promise(resolve => setTimeout(resolve, 1000));
  return text;
}
```

```jsx title="src/components/ChatRoom.jsx"
import { useState } from 'react';
import { deliverMessage } from '../api.js';

const initialMessages = [{ id: 1, text: 'Hello there!' }];
let nextId = 2;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);

  ~async~ function sendMessage(~formData~) { // Principles 1 and 3: React passes the form data and waits
    const message = { id: nextId++, text: formData.get('message') };
    await deliverMessage(message.text);
    setMessages(m => [...m, message]);
  }

  return (
    <section>
      <ul>
        {messages.map(m => <li key={m.id}>{m.text}</li>)}
      </ul>
      <form ~action={sendMessage}~> {/* Principle 1: React handles the submit */}
        ~<input name="message" />~ {/* Principle 2: uncontrolled, so React empties it after Send */}
        <button type="submit">Send</button>
      </form>
    </section>
  );
}
```

### What React does when the user clicks Send

When the page loads, React calls `App`, then `ChatRoom`. When the user clicks Send, React handles the submit, calls the action, waits for it, and resets the form:

```tree dir=right caption="The order of events in our chat, from the first render to the empty field after Send."
From the first render to the empty field
- +1. First render [`App` then `ChatRoom`] | The list shows **`Hello there!`** | The field is **empty**
- +2. The user clicks Send | React builds the **form data** | React calls **`sendMessage`** in a Transition
- +3. The action waits [`await deliverMessage`] | One second **with no change** on the page | The field still shows **`Hi`**
- +4. The action succeeds | `setMessages` adds **`Hi`** to the list | React **resets the form**, and the field is empty
```

| Aspect | The `onSubmit` Way | The `action` Way |
| :--- | :--- | :--- |
| **What the function receives** | The submit event `e`; your code builds `new FormData(e.currentTarget)` | The form data itself, a `FormData` object |
| **The page reload** | Your code must call `e.preventDefault()` | React handles the submit, so the page never reloads |
| **The field after Send** | Keeps the sent text until your code empties it | Empty again, because React resets uncontrolled fields after success |
| **Waiting for a server** | Your code tracks the wait with an `isSending` state | React waits for the `async` action and tracks its pending state |

One last time, the sentence of this lesson: **put a function in `action`, and React calls it with the form data. No event, no `preventDefault`, and React empties the fields after the function succeeds.**

## For the Interview

> **The Interview Question:** What is the action prop on a form, and how do actions modernize form handling?

### How to Answer Clearly in 30 Seconds

"In plain HTML, a form's `action` holds a URL, and submitting the form loads a new page. In React 19, `action` can hold a function instead. When the user submits the form, React calls that function with one argument, the form data, as a `FormData` object. Actions replace three pieces of manual work:
1. **The submit event**: there is no event, no `e.preventDefault()`, and no `new FormData(e.target)`, and the page does not reload.
2. **The reset**: after the action succeeds, React resets every uncontrolled field in the form, so a chat field is empty after Send.
3. **The waiting**: the action can be `async`. React waits for it in a Transition, keeps the page usable, and tracks its pending state, so I no longer write an `isSending` state by hand."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Should we still use `onSubmit`?"**
   It still works in every version of React, and it gives you the submit event itself. React's docs list what an `action` adds on top of it, which is why, for a new React 19 form, `action` does more of the work:
   1. It runs in a Transition and tracks the pending state.
   2. It sends a thrown error to the nearest error boundary.
   3. It works with `useActionState`, and with `useOptimistic`, which shows a message before the server confirms it, in Lesson 44.
   4. It can be a Server Function, which `onSubmit` cannot be. Lesson 110 covers Server Functions.
2. **"What can an action return?"**
   A plain form action may return a promise, because it may be `async`. React waits for that promise before it resets the form. React gives the returned value no use on a plain `<form action>`. When the page must show a result, such as an error line after a failed send, the action is wrapped in `useActionState`. The value it returns then becomes the new state. Lesson 42 covers it.
3. **"Why did my field not empty after Send, and how do I stop a field from emptying?"**
   React resets only uncontrolled fields, and only after the action succeeds. A field with `value` and `onChange` shows what state holds, so it keeps the sent text. When a reset is not wanted, such as in a search field, Lesson 45 shows how to keep the text.

```tree dir=right caption="Interview comparison: what onSubmit and action share, and what action adds."
`onSubmit` vs. `action` on a form
- +`onSubmit` [`onSubmit={handleSubmit}`] | Gets the **submit event** | Your code stops the reload, builds the **form data**, and empties the fields
- +`action` [`action={sendMessage}`] | Gets the **form data** | React keeps the page, **resets uncontrolled fields**, and **waits** for an `async` action
```
