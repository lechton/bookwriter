# Lecture 111: Why 'use client' and 'use server' Are Directives, and Who Reads Them

*(Why does one string at the top of a file decide where the code runs?)*

> INTERVIEW QUESTION | ❱ CORE | Why are 'use client' and 'use server' called directives, and who reads them?

---

## VS | `'hello'` vs. `'use client'`: the same string to JavaScript, an order to the bundler

> In plain JavaScript, a string alone on a line, such as `'hello'`, does nothing: the engine reads it and throws it away. **`'use client'` and `'use server'` are such strings, called directives, and the tool that reads them as orders is the bundler, while it builds the app**. That is why you never import them, and why they count only at the very top of a file, where the bundler looks for them.

Remember `'use strict'`? It is JavaScript's own directive, much older than React. You write it as the first line of a file. The **JavaScript engine**, the part of the browser that runs your code, reads it and switches the file to **strict mode**, a stricter set of rules. Look at what it is: no function call, no import, just a string on line 1.

```js title="Plain JavaScript: a directive that the engine reads"
~'use strict';~ // The JavaScript engine reads this line and switches the file to strict mode
```

React copied this exact form, and gave it a new reader. `'use client'` is also a string on line 1. But the JavaScript engine does nothing with it. It reads the text and throws it away, exactly as it throws away `'hello'`.

```jsx title="React: a directive that the bundler reads"
~'use client';~ // The bundler reads this line while it builds the app, and sends the file to the browser
```

So who acts on it? The **bundler**. Think about what a bundler does. It never runs your code. It reads every file as text, follows the imports, and decides which code goes into the files the browser downloads. So it can look at line 1, see the exact text `'use client'`, and treat it as an order: "send this file to the browser". To the bundler, `'hello'` means nothing.

Not every bundler knows these two words. The one that does is the bundler inside a framework that supports React Server Components, such as Next.js App Router (as seen in Lesson 46). React's docs say it in one sentence: "Directives provide instructions to bundlers compatible with React Server Components."

Here is the one sentence to keep in mind for this whole lesson:

**A directive is a plain string at the very top of a file: JavaScript throws it away, and the bundler reads it as an order.**

> [!DEFINITION]
> **Bundler.** [REVIEW] A bundler is the tool that builds your app before any user opens it. It reads every file as text, follows every `import`, and joins the code into the JavaScript files the browser downloads. Vite is the bundler of a plain React app (Lesson 07).

> [!DEFINITION]
> **Server Component.** [REVIEW] A Server Component is a component that runs only on the server. Its code never reaches the browser, only what it renders does. A component is a Server Component by default, when its file has no directive at the top (Lesson 101).

> [!DEFINITION]
> **Client Component.** [REVIEW] A Client Component is a component in a file that starts with `'use client'`. Its code goes into the JavaScript files the browser downloads, so it runs in the browser, and it can use state, event handlers, and Hooks such as `useState` (Lesson 106).

> [!DEFINITION]
> **Server Function.** [REVIEW] A Server Function is an `async` function that runs on the server, and that code in the browser can call like a normal function. The browser gets only a reference to it, and a call sends a request to the server (Lesson 110).

> [!DEFINITION]
> **Directive.** [NEW] In everyday English, a directive is a written order. In code, a directive is a string alone at the very beginning of a file or a function, such as `'use strict'` or `'use client'`. JavaScript reads it and throws it away. One tool knows its exact text and reads it as an order: the JavaScript engine for `'use strict'`, and the bundler of a framework that supports React Server Components for `'use client'` and `'use server'` (Lesson 111).

### The Same Form, Two Readers

The form is the same: a string at the very beginning. Only the reader changes:

```tree caption="The same form, a string at the very beginning of a file, read by two different tools."
Who reads a directive
- +`'use strict'` [JavaScript's own directive] | Read by the **JavaScript engine** | Switches the file to **strict mode**
- +`'use client'` and `'use server'` [React's two directives] | Read by the **bundler** of a framework that supports React Server Components | Decides **which code goes to the browser** and **which code stays on the server**
```

### What Goes Wrong When the Bundler Misses the Line

What is at stake is simple: whether a button answers a click. When the bundler does not find `'use client'` on a button file, it does not split the code the way you meant:
1. It treats the button file as server code, so the button is a Server Component.
2. React's docs: "Server Components cannot support interaction as event handlers must be registered and triggered by a client." And: "Server Components cannot use most Hooks."
3. So the framework reports an error about `useState` instead of showing the page (as seen in Lesson 106).

### Where Readers Usually Go Wrong

1. **They look for `'use client'` in React's API.** It is not an import and not a function, and React does not export it. React's docs list the two lines on their own page, "Directives", not with the APIs.
2. **They write it below the imports, or inside a component.** There it is only a string, and the bundler never sees it.
3. **They read `'use server'` as the mark of a Server Component.** React's docs warn: "A common misunderstanding is that Server Components are denoted by `"use server"`, but there is no directive for Server Components. The `"use server"` directive is used for Server Functions."

### Where Each Directive Can Stand

`'use client'` has one place. `'use server'` has two, and you choose between them:
1. **`'use client'` at the top of a file**, and nowhere else. It has no function form.
2. **`'use server'` at the top of a file**, such as `actions.js`. Every function the file exports becomes a Server Function. React's docs require this form when client code imports the function.
3. **`'use server'` at the top of an `async` function body**, inside a Server Component. The Server Component passes that one function down as a prop (as seen in Lesson 107).

```tree caption="Where each of React's two directives can stand."
Where React's directives can stand
- +`'use client'` at the top of a file [`AddToCartButton.jsx`] | The file and everything it imports become **client code** | It has **no function form**
- +`'use server'` at the top of a file [`actions.js`] | Every export becomes a **Server Function** | Client code can **import** it
- +`'use server'` at the top of an `async` function body | One function inside a **Server Component** | Reaches a Client Component **as a prop**
```

The button needs `useState` and `onClick`, so it must run in the browser. The title needs neither, so it can stay on the server. We build the page with four files. Three of them start with a different first line: no directive, `'use client'`, and `'use server'`.

```files title="store: the product page" caption="The four files of the product page: a database stand-in, a file of Server Functions, one Client Component, and one Server Component."
src/
  db.js | stand-in | Plays the database: `db.cart.add(productId)` saves one item in the cart
  actions.js | Server Functions | Starts with `'use server'` and exports `addToCart`
  AddToCartButton.jsx | Client Component | Starts with `'use client'`; holds `count`, the button, and the `In cart:` line
  ProductPage.jsx | Server Component | No directive; shows `Headphones` and renders `<AddToCartButton />`
```

`db.js` is a stand-in: a small file that plays the part of the database, so the page needs no real database server (as seen in Lesson 110).

**PRINCIPLES:** A directive is a plain string at the very top of a file: JavaScript throws it away, and the bundler reads it as an order. Four principles follow:
1. **`'use client'`: the bundler reads it while it builds the app, and JavaScript throws it away.** There is nothing to import, and nothing in the line runs.
2. **`'use client'` above every import: only at the very beginning of the file is the string a directive.** One line lower, the bundler does not see it, and the button becomes a Server Component.
3. **`'use client'` and `'use server'`: two different orders to the bundler, and none for a Server Component.** The first sends a file to the browser. The second keeps a function on the server and gives the browser a reference.
4. **`'use client'` in a plain Vite app: no tool reads it, so the page stays the same.** Every file there already runs in the browser.

## PRINCIPLE | `'use client'`: the bundler reads it while it builds the app, and JavaScript throws it away

> [!PRINCIPLE]
> **Principle 1: A Directive: `'use client'` Is a String JavaScript Throws Away**
>
> *`'use client'` is a plain string at the very beginning of a file; JavaScript drops it, and the bundler of a framework that supports React Server Components reads it as an order while it builds the app.*
>
> A button needs to run in the browser, but no line of JavaScript can move a file from the server to the browser. So React gives the order to the tool that builds the app. The bundler reads the text of the file before any code runs, finds `'use client'`, and sends the file to the browser. When the browser later runs the file, the string does nothing. That is why there is nothing to import, and why the line does nothing inside a component: it is a note on the whole file for the bundler, not code for JavaScript.
>
> **DO THIS:**
> ```jsx
> ~'use client';~ // A bare string on line 1: the bundler reads it
>
> import { useState } from 'react';
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function AddToCartButton() {
>   ~'use client';~ // **WRONG:** inside a component it is only a string; the bundler reads 'use client' only at the top of a file
>   const [count, setCount] = useState(0);
>   return <button onClick={() => setCount(count + 1)}>Add to cart</button>;
> }
> ```

Every developer asks the same question at this point: if `'use client'` is not code, how can it change anything? The answer: it does not change your code at all. It changes how the bundler builds your files.

Here is the smallest component you can write, with `'use client'` on line 1:

```jsx title="Hello.jsx"
~'use client';~ // The bundler reads this line; the component never sees it

export default function Hello() {
  return <p>Hello, John</p>;
}
```

With line 1 or without it, `Hello` returns the same paragraph, Hello, John. Line 1 does not change what the code does. It only changes where the bundler sends the file.

### Two Moments: the Build, Then the Browser

**The bundler reads the line long before the browser runs it.** On our product page, line 1 of the button file meets two readers, at two different moments:
1. **While the framework builds the app**, the bundler reads the text of `AddToCartButton.jsx`. Nothing in the file runs yet.
2. It finds the exact string `'use client'` at the very beginning of the file.
3. When `ProductPage.jsx`, a Server Component, imports this file, the bundler treats that import as the boundary (as seen in Lesson 106).
4. So the bundler sends the code of the button file to the browser.
5. **Later, in the browser**, the JavaScript engine runs the file. It meets the string on line 1 and throws it away, exactly as it would throw away `'hello'`.

So the split did not happen while JavaScript ran. It happened earlier, when the bundler read the text of the file.

```tree dir=right caption="The two moments when line 1 of AddToCartButton.jsx is read, and what each reader does with it."
Who reads `'use client'`, and when
- +1. While the app is built [The bundler] | Reads the **text** of the file | Finds `'use client'` and **sends the file to the browser**
- +2. While the page runs [The JavaScript engine] | Runs the file in the browser | Reads the string and **throws it away**
```

### Nothing to Import

Where does `'use client'` come from? Nobody supplies it. Compare it with a Hook, which you do import:

```jsx title="A directive is not imported; a Hook is"
~'use client';~ // No import: plain text that only the bundler understands
import { ~useState~ } from 'react'; // A function that React exports, and your component calls
```

There is no import for `'use client'`, because React does not export it. It is not a Hook, and not a setting inside the component. It is text in the file, and only the bundler knows what that text means.

Developers really trip on this. They take `'use client'` for something React runs, and search React's API for it. Or they write it inside a component, the way they write a Hook. There is nothing to find: React's docs list the two lines on their own page, "Directives", and say they "provide instructions to bundlers".

### VS | `'use strict'` vs. `<StrictMode>`: both say strict, only one is a directive

Two names in React projects sound alike:

```jsx title="'use strict' at the top of a file vs. StrictMode around the app"
~'use strict';~ // A directive: the JavaScript engine reads it and switches the file to strict mode
<~StrictMode~><App /></StrictMode> {/* A React component: it checks our components in development */}
```

**It may look the same, but it is NOT the same thing!**
- **`'use strict'`** is a directive, the string form that `'use client'` copies. Its reader is the JavaScript engine.
- **`<StrictMode>`** is a React component that runs our components twice in development to find mistakes (as seen in Lesson 47). It is not a directive at all.

### Our Product Page: `ProductPage.jsx` and `AddToCartButton.jsx`

Now the product page appears. The button file holds the count and the button:

```jsx title="src/AddToCartButton.jsx"
~'use client';~ // The bundler sends this file to the browser

import { useState } from 'react';

export default function AddToCartButton() {
  const [count, setCount] = useState(0);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>Add to cart</button>
      <p>In cart: {count}</p>
    </>
  );
}
```

The page file has no directive, so it is a Server Component (as seen in Lesson 101):

```jsx title="src/ProductPage.jsx"
import ~AddToCartButton~ from './AddToCartButton'; // A server file imports a 'use client' file: the boundary

export default function ProductPage() {
  return (
    <main>
      <h1>Headphones</h1>
      <AddToCartButton />
    </main>
  );
}
```

```page caption="The product page built from ProductPage.jsx and AddToCartButton.jsx, after the user clicks Add to cart once."
heading: Headphones
line: [Add to cart]
line: In cart: 1 | good
```

The page gives no sign of the split. The `<button>` and the `<p>` look the same, whichever file they came from. The split lives in the files the browser downloads, and only the bundler made it.

Remember: `'use client'` is not code that runs. It is a note on the file, and the bundler is the one who reads it.

## PRINCIPLE | `'use client'` above every import: only at the very beginning of the file is the string a directive

> [!PRINCIPLE]
> **Principle 2: The Place: A Directive Counts Only at the Very Beginning**
>
> *Put `'use client'` and `'use server'` at the very beginning of the file, above every import, with only comments before them; `'use server'` may also open an `async` function body.*
>
> The bundler looks for a directive in one place only. Anywhere else, the same text is a plain string, and the file is built as if the line were not there. A button file then becomes a Server Component, and the error names `useState`, not the line that moved. So when an error says a Hook cannot run in a Server Component, look at line 1 of the file first.
>
> **DO THIS:**
> ```jsx
> ~'use client';~ // Line 1: the bundler sees a directive
> import { formatPrice } from './format';
> import { useState } from 'react';
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import { formatPrice } from './format';
> ~'use client';~ // **WRONG:** below an import: only a string, and the file stays server code
> ```

Here is the top of the button file, with the same two lines in two orders:

```jsx title="'use client' above the import"
~'use client';~ // At the very beginning of the file: a directive
import { useState } from 'react';
```

```jsx title="'use client' below the import"
import { useState } from 'react';
~'use client';~ // **WRONG:** below an import: only a string
```

**It may look the same, but it is NOT the same thing!** Both files hold the same two lines. Only the first one has a directive.

### Why the Place Matters

You already know the rule from Lesson 106: line 1, above every import, in single or double quotes, never in backticks, with only comments above it. Now you can see the reason behind it.

Think about how the bundler searches. It does not run your file. It reads the file from the top, and the place for directives ends at the first line of real code. If that first line is an `import`, the place is already closed. So one line lower, the same text is a plain string, and the bundler builds the file as if the line were not there.

JavaScript's own `'use strict'` follows the same rule. Below other code, it does not switch strict mode on.

React's docs give the place in their own words, for both directives:
- `'use client'` "must be at the very beginning of a file, above any imports or other code".
- `'use server'` "must be at the very beginning of their function or module; above any other code including imports".

### `'use server'` Has a Second Beginning

Look at the words "their function or module" in the second quote. For `'use server'`, the very beginning of an `async` function body counts too. This is the form that sits inside a Server Component (as seen in Lesson 107):

```jsx title="'use server' at the top of an async function body"
async function addToCart(productId) {
  ~'use server';~ // The very beginning of this function: a directive
  await db.cart.add(productId);
}
```

So `'use server'` has two valid places: the very beginning of a file, and the very beginning of an `async` function. `'use client'` has only one, the very beginning of a file. Inside a component, as the card of Principle 1 showed, it is a plain string.

### The Mistake: a New Import on Top

**One new import above the line, and the button stops working.** Developers really fall into this one:
1. A developer opens the button file to show the price under the button, and adds a new import on line 1, above `'use client'`.
2. Both lines are valid JavaScript, so JavaScript itself finds nothing wrong.
3. The bundler now finds an `import` at the very beginning of the file, not a directive.
4. It treats the file as server code, so the button is a Server Component that uses `useState` and `onClick`.
5. The framework reports an error about `useState` in a Server Component.
6. The developer looks at the file, sees `'use client'` in it, and cannot see why.

```jsx title="src/AddToCartButton.jsx" bad="1"
import { formatPrice } from './format';
~'use client';~ // **WRONG:** a new import above it: the bundler no longer sees a directive

import { useState } from 'react';
```

The fix is to move `'use client'` back to line 1, above every import.

Remember: a directive is a directive only at the very top. One line lower, it is just a string.

## PRINCIPLE | `'use client'` and `'use server'`: two different orders to the bundler, and none for a Server Component

> [!PRINCIPLE]
> **Principle 3: Two Orders: `'use client'` Sends Code to the Browser, `'use server'` Keeps It on the Server**
>
> *Both directives are read by the same bundler, but `'use client'` sends a file and everything it imports to the browser, and `'use server'` keeps each function on the server and gives the browser only a reference; a Server Component needs no directive.*
>
> Our product page needs code in three places: the page on the server, the button in the browser, and the cart in the database. So the bundler needs one order for the button and another for the cart. `'use client'` says "run this in the browser". `'use server'` says "keep this on the server, and let the browser ask for it". The page itself needs no order, because server code is the default.
>
> **DO THIS:**
> ```js
> ~'use server';~ // actions.js: addToCart stays on the server; the browser gets a reference
>
> export async function addToCart(productId) {
>   await db.cart.add(productId);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~'use server';~ // **WRONG:** ProductPage.jsx is a component file; there is no directive for Server Components
>
> export default function ProductPage() {
>   return <main><h1>Headphones</h1></main>;
> }
> ```

Here are the first lines of our three React files, side by side:

```jsx title="The first line of ProductPage.jsx, AddToCartButton.jsx, and actions.js"
~import AddToCartButton from './AddToCartButton';~ // ProductPage.jsx: no directive, a Server Component
~'use client';~ // AddToCartButton.jsx: send this file, and what it imports, to the browser
~'use server';~ // actions.js: keep these functions on the server, give the browser a reference
```

### VS | `'use client'` vs. `'use server'`: the same reader, two different orders

Both directives have the same reader, the bundler. Both have the same form, the word use and one more word. But they give the bundler two different orders:
- **`'use client'`** says: this file runs in the browser. React's docs: "`'use client'` lets you mark what code runs on the client." The bundler treats the import of the file from a Server Component as the boundary (as seen in Lesson 106).
- **`'use server'`** says: these functions stay on the server, and the browser may call them. React's docs: "`'use server'` marks server-side functions that can be called from client-side code." The bundler leaves the body of each function out of the browser files, and puts a reference in its place (as seen in Lesson 107).

**It may look the same, but it is NOT the same thing!** `'use server'` is not the opposite of `'use client'`. It does not mark a Server Component. A Server Component needs no directive at all. React's docs: "there is no directive for Server Components."

```tree caption="Three first lines on one product page, and the order each one gives the bundler."
What the bundler does with each first line
- +No directive [`ProductPage.jsx`] | A **Server Component** by default | Its code **stays on the server**
- +`'use client'` [`AddToCartButton.jsx`] | Send the file **and everything it imports** to the browser | Its code **runs in the browser**
- +`'use server'` [`actions.js`] | Keep each exported function **on the server** | The browser gets **a reference**, and a call **sends a request**
```

### Our Product Page: `actions.js` and `db.js`

Now the product page grows by one step. When the user clicks `Add to cart`, the item must also be saved in the cart on the server. The database stand-in keeps the cart in an array:

```js title="src/db.js"
const cart = [];

export const db = {
  cart: {
    async add(productId) {
      cart.push(productId);
    },
  },
};
```

The actions file holds the Server Function:

```js title="src/actions.js"
~'use server';~ // Order to the bundler: keep addToCart and db.js on the server

import { db } from './db';

export async function addToCart(productId) {
  await db.cart.add(productId);
}
```

The button file imports `addToCart` and calls it from the click handler. The call sits inside `startTransition`, because React's docs ask for Server Functions to be called in a Transition (as seen in Lesson 110):

```jsx title="src/AddToCartButton.jsx"
'use client';

import { useState, startTransition } from 'react';
import { ~addToCart~ } from './actions'; // In the browser, addToCart is a reference, not the code

export default function AddToCartButton() {
  const [count, setCount] = useState(0);

  function handleClick() {
    setCount(count + 1);
    startTransition(() => ~addToCart('headphones')~); // Sends a request; the server runs the real addToCart
  }

  return (
    <>
      <button onClick={handleClick}>Add to cart</button>
      <p>In cart: {count}</p>
    </>
  );
}
```

The `In cart:` line still counts in the button's own state, so the page looks the same as before. The difference is on the server: every click now also saves headphones in the cart.

### A Browser File That Imports a Server File

**The button file runs in the browser, and it imports a file that talks to the database. Yet the database code never reaches the browser.** Here is what the bundler does with that import, in order:
1. The bundler reads `'use server'` at the very beginning of the actions file.
2. It leaves the body of `addToCart`, and the database file with it, out of the browser files.
3. It puts a reference to `addToCart` in the browser files instead.
4. The import in the button file receives that reference.
5. When the user clicks `Add to cart`, the call sends a request to the server, and the server runs the real `addToCart`.

You can see the reference yourself. Log it in the button file:

```jsx title="Logging addToCart in AddToCartButton.jsx"
console.log(~addToCart~); // Prints a short function that React made, not the code of addToCart
```

```devconsole caption="The Console in the browser after logging addToCart: a short function, not the code of addToCart."
(...args) => server(...args)
```

That short function is all the browser holds. It hands each call to React, which sends it to the server. There is no database in it and no body of `addToCart`.

On the server, the same import of `addToCart` carries two fields that React and the bundler write. `$$typeof` marks it as a Server Function, and `$$id` names it, so the server can find the real function. Your code never writes them.

```tree dir=right caption="What the bundler puts in the browser files for an import from a 'use server' file."
From `addToCart` in `actions.js` to a click in the browser
- +1. The bundler reads `'use server'` [`actions.js`] | Keeps the **body** of `addToCart` and **`db.js`** on the server
- +2. The browser files [`import { addToCart }`] | Hold a **reference** to `addToCart` | Not its code
- +3. The click [`handleClick`] | The reference **sends a request** | The server runs **the real `addToCart`**
```

### The Mistake: `'use server'` on `ProductPage.jsx`

A developer learns that `'use client'` marks client code. By symmetry, they add `'use server'` at the top of the page file, to mark it as a Server Component:

```jsx title="src/ProductPage.jsx" bad="1"
~'use server';~ // **WRONG:** marks every export of this file as a Server Function, not as a Server Component

import AddToCartButton from './AddToCartButton';
```

React's docs name this exact mistake: "A common misunderstanding is that Server Components are denoted by `"use server"`." The line gives the bundler the wrong order:
1. Every export of the page file is now a function the browser may call.
2. `ProductPage` is not an `async` function. And this directive works only on `async` functions.
3. So the framework stops with an error when it builds the page, and the product page never appears (as seen in Lesson 110).

The fix is to delete the line. `ProductPage` was already a Server Component, because its file has no directive.

Remember: `'use client'` sends code to the browser, `'use server'` keeps functions on the server, and a Server Component needs nothing.

## PRINCIPLE | `'use client'` in a plain Vite app: no tool reads it, so the page stays the same

> [!PRINCIPLE]
> **Principle 4: The Reader: Without a Compatible Bundler, `'use client'` Has No Effect**
>
> *`'use client'` is an order to a bundler that splits server code from browser code; in a client-side rendered app, such as a plain Vite app, there is nothing to split, and the line has no effect.*
>
> A directive is only as strong as its reader. In a framework that supports React Server Components, the bundler reads `'use client'` and decides which files go to the browser. In a plain Vite app, every file already goes to the browser, and no tool acts on the line. So the page is the same with or without it. Know which app you are in before you add the line, and before you look to it for the cause of a bug.

### Why the Line Has No Reader Here

**A directive works only where its reader is.** A plain Vite app is a client-side rendered app: all of its code is sent to the browser and runs there (as seen in Lesson 103). There is no server code to split from browser code. React's docs say: "When a `'use client'` module is imported from another client-rendered module, the directive has no effect." In a client-side rendered app, every module is client-rendered.

So the line keeps only its JavaScript meaning: a string that does nothing, like `'hello'`. Here is what happens to it in a Vite app:
1. **While you develop**, the browser runs the file with the string still in it, and the engine throws it away.
2. **When you build the app for production**, Vite leaves the string out of the files it builds.
3. **For `'hello'`**, Vite also prints a warning in the terminal: this module level directive may not be preserved.
4. **For `'use client'`**, Vite prints nothing, because the React plugin of Vite hides that warning for both of React's directives.

```tree caption="The same AddToCartButton.jsx with 'use client', in a framework that supports React Server Components and in a plain Vite app."
`'use client'` on line 1 of `AddToCartButton.jsx`
- +In a framework that supports React Server Components | The **bundler reads** the line | Splits the app: this file and its imports **go to the browser**
- +In a plain Vite app | **No tool acts on** the line as an order | Every file **already runs in the browser**; the line has **no effect**
```

**It may look the same, but it is NOT the same thing!** The file is identical in both apps. Only the first app has a bundler that reads the line.

### Where You Meet `'use client'` in a Vite App

You meet the line in a Vite app in two real ways:
1. You copy a component from a project built with a full-stack framework, with `'use client'` still on line 1.
2. You install a library whose files start with `'use client'`. React's docs say libraries that support React Server Components "will already include `'use client'` markers of their own."

In both cases, the line is harmless in a Vite app. It does nothing, and there is no need to delete it.

### The Mistake: `'use client'` Everywhere

**The line does nothing in a Vite app, so nothing ever tells the developer it is not needed.** Developers really build this habit:
1. A developer moves from a full-stack framework to a Vite app.
2. They add `'use client'` to every component that has state or a click handler, because they believe the components need it to work.
3. The page works the same with or without the line, so they never learn that the line has no reader in this app.
4. Later, back in a full-stack framework, they put the line on large page files out of habit.
5. Those files, and everything they import, become client code, and the browser downloads all of it (as seen in Lesson 106).

Remember: a directive is an order, and an order needs someone to read it. In a plain Vite app, nobody does.

### The Order in Which Things Run

```tree dir=right caption="The order in which the directives are read and the components and the Server Function run, from the build to one click."
From the build to one click on `Add to cart`
- +1. The build [The bundler] | Reads **`'use client'`** and **`'use server'`** | Sends `AddToCartButton.jsx` to the browser; puts a **reference** to `addToCart` in the browser files
- +2. On the server [`ProductPage`] | The framework renders the **Server Component** | `ProductPage` places **`<AddToCartButton />`**
- +3. In the browser [`AddToCartButton`] | React renders the **Client Component** | The engine **throws away** the string on line 1
- +4. The click [`handleClick`] | `setCount` shows **`In cart: 1`** | The reference **sends a request** to the server
- +5. On the server [`addToCart`] | The real function runs | **`db.cart.add`** saves `headphones`
```

### Summary

| Aspect | What a Developer Might Expect | What React Does |
| :--- | :--- | :--- |
| **What the line is** | An import or a React function | A bare string; JavaScript reads it and throws it away |
| **Who reads it** | React, while the page runs | The bundler of a framework that supports React Server Components, while it builds the app |
| **Where it stands** | Anywhere in the file | At the very beginning of the file, above every import; `'use server'` may also open an `async` function |
| **`'use server'`** | Marks a Server Component, as the partner of `'use client'` | Marks functions the browser may call; there is no directive for Server Components |
| **In a plain Vite app** | Every interactive component needs `'use client'` | No tool acts on the line, so it has no effect |

Remember the one sentence of this lesson. **A directive is a plain string at the very top of a file: JavaScript throws it away, and the bundler reads it as an order.**

## For the Interview

> **The Interview Question:** Why are 'use client' and 'use server' called directives, and who reads them?

### How to Answer Clearly in 30 Seconds

"`'use client'` and `'use server'` are not imports and not React functions. Each one is a bare string at the very beginning of a file, or, for `'use server'`, of an `async` function. They are called directives because they take the form of JavaScript's own directive, `'use strict'`. JavaScript evaluates the string and throws it away, and a tool that knows the text reads it as an order. For these two, the tool is the bundler of a framework that supports React Server Components. React's docs say: 'Directives provide instructions to bundlers compatible with React Server Components.' The two orders differ:
1. **`'use client'`** tells the bundler that the file, and everything it imports, runs in the browser. The import of that file from a Server Component is the boundary.
2. **`'use server'`** tells the bundler to keep each function on the server and to give the browser only a reference, so a call sends a request to the server.
3. **There is no directive for Server Components.** A file with no directive is server code by default."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Can I write `'use client'` below my imports, or inside a component?"**
   **No.** The bundler reads a directive only at the very beginning of the file, above every import. Only comments may come before it, and it must use single or double quotes, not backticks. Below an import, it is a plain string, and the file stays server code. Inside a component, it is a plain string too, because `'use client'` marks whole files only. `'use server'` is different: it has one more valid place, the very beginning of an `async` function body.
2. **"Does `'use client'` do anything in a Vite app?"**
   **No.** A plain Vite app is client-side rendered: every file already runs in the browser. React's docs say: "When a `'use client'` module is imported from another client-rendered module, the directive has no effect." The line matters only where a bundler that supports React Server Components reads it, such as in Next.js App Router.
3. **"Are there other directives in React?"**
   `'use client'` and `'use server'` are the two source code directives for React Server Components. Other tools read other directives. The React Compiler reads `"use memo"` and `"use no memo"`. React's docs: "React Compiler directives are special string literals that control whether specific functions are compiled." It is the same form, a string at the very beginning, with a different reader (as seen in Lesson 63).

```tree caption="Interview comparison: the same form, a string at the very beginning, read by three different tools."
Who reads which directive
- +`'use strict'` | Read by the **JavaScript engine** | Switches on **strict mode**
- +`'use client'` and `'use server'` | Read by the **bundler** of a framework that supports React Server Components | Split code between **the server and the browser**
- +`"use memo"` and `"use no memo"` | Read by the **React Compiler** | Turn compiling **on or off** for a function
```
