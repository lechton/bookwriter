# Lecture 61: How React Matches List Rows by Key

*(Why does the edit field jump to another task after the user deletes a row?)*

> INTERVIEW QUESTION | ❱❱ MORE | What makes a good key across re-renders, and how do unstable or duplicate keys corrupt reconciliation?

---

## VS | The Index `key={index}` vs. the Task's ID `key={task.id}`: both show the same rows, only the ID keeps each row's state with its task

> When you show a list in React, you call `map()` on an array and give every row a `key`. **On the next render, React finds each row again by its key, and the row keeps its own state, such as an open edit field**. So key each row by an ID from the data, because an index or a random number gives that state to the wrong row, or throws it away.

Remember the key from Lesson 18? Without it, the Console shows an error. With it, the error goes away, and most developers stop there. But the key is not there to please the Console. It is how React tells the rows of a list apart.

In plain JavaScript, you delete a row yourself. You grab the exact `<li>` element and remove it, so you always know which element is gone:

```js title="Plain JavaScript: you remove the element yourself"
document.getElementById('task-1').~remove()~; // You pick the exact li element that goes away
```

In React, you never touch the `<li>` elements. React created them from your JSX, and React removes them too. You only change the array:

```jsx title="React: you change the array, and React removes the element"
~setTasks(tasks.filter(task => task.id !== 1))~; // You only say which task is gone from the data
```

So after the click, React holds two lists of rows, the old one and the new one. It must work out which old row is which new row. React does not know which button the user clicked. It only compares the keys:
1. **A key that comes back:** React keeps that row, with its state.
2. **A key that is gone:** React destroys that row, with its state.

Keep one sentence in mind for the whole lesson: **a row's state follows its key, not its text.**

Take a to-do list such as Google Tasks. It shows three tasks: Buy milk, Call Mom, and Pay rent. Each row has an **Edit** button and a **Delete** button. A click on **Edit** opens the edit field: an `<input>` field with the title of the task inside it.

**Why:** Each row remembers in its own state whether its edit field is open. With the task's ID as the key, Call Mom keeps the key 2 after the Delete, so React gives it back its open edit field.

With the index as the key, the keys are only positions: 0, 1, and 2. After the Delete, Call Mom moves up to position 0, and Pay rent moves up to position 1. The open edit field belonged to the key 1, so it now sits on Pay rent. The user is editing a task they never clicked, and the Console shows nothing.

Here are the two keys behind the two pages:

```jsx title="Keying each row by its index, and keying each row by the task's ID"
{tasks.map((task, index) => <TaskRow ~key={index}~ task={task} />)} {/* Names a position: 0, 1, 2 */}
{tasks.map(task => <TaskRow ~key={task.id}~ task={task} />)} {/* Names a task: Call Mom is always 2 */}
```

**It may look the same, or work the same at first, but it is NOT the same thing!** On the first render, both lines show the same three rows, and the Console stays quiet for both. The difference is what the key names:
- **The index names a position in the list.** The key 1 means "the second row", whichever task sits there now. After a Delete at the top, the key 1 belongs to Pay rent.
- **The ID names a task.** The key 2 means Call Mom, before and after any Delete.

```tree caption="Two keys that show the same three rows on the first render, and name two different things."
Two names React can use to find a row on the next render
- !The index [`key={index}`] | Names a **position** in the list: `0`, `1`, `2` | After a Delete at the top, the position `1` belongs to **another task**
- +The task's ID [`key={task.id}`] | Names a **task**: `Call Mom` is always `2` | After a Delete at the top, `2` still belongs to **`Call Mom`**
```

### Two Reminders and One New Word

> [!DEFINITION]
> **What is a key?** [REVIEW] A key is a special prop you put on each row that `map()` returns, such as `<li key={task.id}>`. React reads it to tell the rows apart.
> It must be unique among the rows of one list. Without a key, the Console shows an error, and React uses the index of each row instead (Lesson 18).

> [!DEFINITION]
> **Where does React keep a component's state?** [REVIEW] React ties state to the component's position in the tree. When React removes a component from the tree, its state is gone. When the component comes back, its state starts again from the start value of `useState`.
> A key becomes part of that position. So in a list, the key decides which state belongs to which row (Lesson 25).

> [!DEFINITION]
> **What is reconciliation?** [NEW] Reconciliation is React's word for the comparison it makes on every render: the new JSX against the JSX of the last render. From that comparison, React decides which components to keep, which to create, and which to destroy.
> For a list, React does it by key. In the docs' words, keys let React match up each row of the new list with a row of the old list.
> The key is the row's identity: what makes React treat it as the same component on the next render (Lesson 61).

### Three Ways to Get a Key

There are three places a key can come from (Lesson 18):

```tree caption="Three ways to get a key for each row of a list, and the list each one fits."
Where the key of each row comes from
- +1. The ID that comes with the data [`key={task.id}`] | Fits **any list loaded from a database** | react.dev: "you can use the database keys/IDs, which are unique by nature"
- +2. An ID made once when the item is created [`crypto.randomUUID`] | Fits **items the user creates on the page** | Made **once**, then stored in the item
- !3. The index [`key={index}`] | Fits **only a list that never changes order** | No item is ever inserted, deleted, or sorted
```

The third way is rare. React's docs give one case for it, a poem: "This is a rare case where index as a key is acceptable because a poem's lines will never reorder." A to-do list is the opposite, because the user deletes tasks all day.

### What the User Pays for a Bad Key

A bad key never breaks the text of a row. The text comes from props, so it is always right. What breaks is everything the row keeps for itself: its state, the focus, and what the browser keeps inside its DOM nodes. The user sees three different bugs:
1. **With the index as the key, the edit field opens on a task the user never clicked.** The user deletes Buy milk and finds the edit field open on Pay rent.
2. **With a key made by `Math.random()`, the edit field closes after one letter.** The user must click **Edit** again for every letter.
3. **With a key that repeats, such as a title written twice, a deleted task can stay on the page.** The data no longer has it, but the page still shows it.

Developers usually go wrong in four ways:
1. They think the **Delete** click removes the row it was clicked in. The click only changes the array. React decides which row to remove by comparing keys.
2. They think any key that silences the Console is a good key. React's tutorial says the opposite: "Explicitly passing `key={i}` silences the error but has the same problems as array indices and is not recommended in most cases."
3. They think a key only has to be unique. It must also stay the same on every render, and stay with the same item.
4. They think the text of the row is what can go wrong. The text is always right. The state, the focus, and the DOM nodes are what go wrong.

### The Rule of Thumb: what does the key name?

**Ask one question about every key: what does it name? A good key names the item, stays the same on every render, and is unique in the list. Only an ID does all three.**

## SECTION | A To-Do List with an Edit Button on Each Row

Our page is the to-do list from the start of the lesson. Each row keeps one piece of state of its own, `isEditing`. Only that row needs to know whether its edit field is open. This is the state that a bad key moves to another task, or throws away.

The page has two components:
1. **`TaskList`** holds the `tasks` array in state, and shows one `TaskRow` for each task. It also owns the two functions that change the array: one renames a task, and one deletes it.
2. **`TaskRow`** shows one task. While `isEditing` is false, the row shows the title, **Edit**, and **Delete**. While it is true, the row shows the edit field, **Save**, and **Delete**.

```files title="todo-list: File Explorer" caption="How the files of our to-do list sit inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it into `#root`
  App.jsx | parent | Exports `App` as default and renders `<TaskList />`
  components/
    TaskList.jsx | list | Holds `tasks` in state and renders one `<TaskRow>` per task with its `key`
    TaskRow.jsx | row | Keeps `isEditing` in state and shows the title or the edit field
```

`TaskList` holds the three tasks, and gives each `TaskRow` the task's ID as its key:

```jsx title="src/components/TaskList.jsx"
import { useState } from 'react';
import TaskRow from './TaskRow.jsx';

const initialTasks = [
  { id: 1, title: 'Buy milk' },
  { id: 2, title: 'Call Mom' },
  { id: 3, title: 'Pay rent' },
];

export default function TaskList() {
  const [tasks, setTasks] = useState(initialTasks);

  function handleRename(id, newTitle) {
    setTasks(tasks.map(task =>
      task.id === id ? { ...task, title: newTitle } : task
    ));
  }

  function handleDelete(id) {
    setTasks(tasks.filter(task => task.id !== id));
  }

  return (
    <>
      <h1>Tasks</h1>
      <ul>
        {tasks.map(task => (
          <TaskRow
            ~key={task.id}~ // Names the task: Call Mom is always 2
            task={task}
            onRename={handleRename}
            onDelete={handleDelete}
          />
        ))}
      </ul>
    </>
  );
}
```

The two handlers build a new array with `map()` and `filter()` (Lesson 19). `TaskRow` calls them through its props (Lesson 23).

Each row keeps its own `isEditing`:

```jsx title="src/components/TaskRow.jsx"
import { useState } from 'react';

export default function TaskRow({ task, onRename, onDelete }) {
  const [~isEditing~, setIsEditing] = useState(false); // Each row keeps its own copy

  return (
    <li>
      {isEditing ? (
        <>
          <input
            value={task.title}
            onChange={e => onRename(task.id, e.target.value)}
          />
          <button onClick={() => setIsEditing(false)}>Save</button>
        </>
      ) : (
        <>
          {task.title}
          <button onClick={() => setIsEditing(true)}>Edit</button>
        </>
      )}
      <button onClick={() => onDelete(task.id)}>Delete</button>
    </li>
  );
}
```

The edit field is a controlled input (Lesson 20). It shows the task's title, and every letter the user types calls `onRename` with the new text. So every letter changes `tasks` in `TaskList`, and the whole list renders again. Principle 3 depends on this fact.

`App` only shows the list:

```jsx title="src/App.jsx"
import TaskList from './components/TaskList.jsx';

export default function App() {
  return <TaskList />;
}
```

**PRINCIPLES:** A row's state follows its key, not its text. So a good key names the item, stays the same on every render, and is unique among the rows of the list. Four principles follow:
1. **Principle 1: React Keeps the Row Whose Key Comes Back.** The **Delete** click only changes the array. React keeps every row whose key comes back, with its state, so the edit field stays on Call Mom.
2. **Principle 2: The Index Names a Position, Not a Task.** After a Delete at the top, every index belongs to the next task. The open edit field stays at its position, so it now sits on Pay rent.
3. **Principle 3: A Key Must Be the Same on Every Render.** A random key never comes back, so React destroys every row on every render. The edit field closes after one letter.
4. **Principle 4: A Key Must Be Unique Among Siblings.** Two tasks named Buy milk share one key. The Console reports it, and after a Delete the page can keep a row the data no longer has.

## PRINCIPLE | `key={task.id}`: the row whose key comes back keeps its state

> [!PRINCIPLE]
> **Principle 1: React Keeps the Row Whose Key Comes Back**
>
> *On every render of a list, React keeps the component whose key it finds again, with its state and its DOM nodes, creates a component for a new key, and destroys the component whose key is missing.*
>
> The click on Delete does not remove a row. It only changes the array. React then compares the keys of the new list with the keys of the old list. Every row whose key comes back keeps its state, so the edit field the user opened on Call Mom stays open on Call Mom.
>
> **DO THIS:**
> ```jsx
> {tasks.map(task => (
>   <TaskRow ~key={task.id}~ task={task} onDelete={handleDelete} /> // After a Delete, Call Mom keeps key 2 and its open edit field
> ))}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {tasks.map(task => (
>   ~<TaskRow~ task={task} onDelete={handleDelete} /> // **WRONG:** no key: the Console reports it, React uses the index, and the open edit field moves after a Delete
> ))}
> ```

### The Click Changes the Array, the Key Picks the Row

Here is the smallest list that shows the rule. It is the same `<ul>` on two renders, before the user deletes Buy milk and after:

```jsx title="The same list before the Delete"
<ul>
  <li ~key={1}~>Buy milk</li> {/* Key 1 */}
  <li key={2}>Call Mom</li>
  <li key={3}>Pay rent</li>
</ul>
```

```jsx title="The same list after the Delete"
<ul>
  <li ~key={2}~>Call Mom</li> {/* Key 2 again: React keeps this row */}
  <li ~key={3}~>Pay rent</li> {/* Key 3 again: React keeps this row */}
</ul>
```

React compares the two lists of keys. Keys 2 and 3 come back. Key 1 is missing, so React removes only the row with key 1.

Many developers picture the click and the removal as one step: "I clicked Delete on Buy milk, so React removes that row." They are two separate steps:
1. The click handler makes a new array without Buy milk.
2. React removes the row whose key is missing from the new list.

### What React Does with Each Key

React's tutorial gives the whole rule in four sentences. "React takes each list item's key and searches the previous list's items for a matching key. If the current list has a key that didn't exist before, React creates a component. If the current list is missing a key that existed in the previous list, React destroys the previous component. If two keys match, the corresponding component is moved."

```tree dir=right caption="The three things React does with each key when a list renders again."
React compares the new keys with the old keys
- +The key is found again | React **keeps** that component | Its state and its DOM nodes stay; it gets the **new props**
- +The key is new | React **creates** a component | Its state starts from the **initial value**
- !The key is missing | React **destroys** the old component | Its state and its DOM nodes are **gone**
```

"Moved" means React keeps the component even when it now sits at another place in the list. Here, the row of Call Mom moves from the second place to the first, and it is still the same component.

The tutorial also says what the key gives each row: "Keys tell React about the identity of each component, which allows React to maintain state between re-renders." The row with key 2 before the Delete is the row with key 2 after it. This is the rule you already know from Lesson 25: state belongs to a position in the tree, and the key is part of that position. A list only applies it to each row.

### Edit on Call Mom, Then Delete on Buy milk

The user clicks **Edit** on Call Mom, then **Delete** on Buy milk. The page does what the user expects:

```page caption="The to-do list keyed by task.id, after the user clicks Edit on Call Mom and then Delete on Buy milk."
heading: Tasks
form:
  field:  | Call Mom | good
  button: Save
  button: Delete
line: Pay rent [Edit] [Delete]
console: quiet
```

No line of our code keeps the edit field open. It stays open because React kept the row with key 2, and its state with it:
1. On its first render, the `TaskRow` with key 2 called `useState(false)`, and React holds that state for it.
2. The click on **Edit** set its `isEditing` to true.
3. After the Delete, React finds key 2 again in the new list. It keeps that `TaskRow` and its state, and calls it with the same task.
4. The row returns the edit field again, with Call Mom in it.

The Elements panel shows the same thing. React removes only the first `<li>`. The `<li>` of Call Mom, with its `<input>`, is the very same DOM node as before the click. React changes only the DOM nodes that differ between renders (Lesson 13).

```dom caption="The Elements panel after the Delete: React removed the li of Buy milk and kept the li of Call Mom with its input."
<ul>

    <input>
    <button>Save</button>
    <button>Delete</button>
  </li>
+ <li>Pay rent ...</li> | note: Key 3 came back: the same li as before
</ul>
```

Remember: a row's state follows its key. Key 2 came back, so the open edit field came back with it.

## PRINCIPLE | `key={index}`: the state stays at the position while the tasks move up

> [!PRINCIPLE]
> **Principle 2: The Index Names a Position, Not a Task**
>
> *Key each row by an ID that names the item; with the index as the key, a Delete, an insert, or a sort gives every index to another item, so the state of each row stays at its position while the item moves.*
>
> React keeps the row whose key comes back. When the key is the index, the key that comes back after a Delete at the top belongs to the next task. The text follows the task, because it comes from props. The open edit field, the focus, and anything the browser keeps in the row stay at the position, so they now sit on another task.
>
> **DO THIS:**
> ```jsx
> {tasks.map(task => (
>   <TaskRow ~key={task.id}~ task={task} onDelete={handleDelete} /> // The open edit field stays with Call Mom
> ))}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {tasks.map((task, index) => (
>   <TaskRow ~key={index}~ task={task} onDelete={handleDelete} /> // **WRONG:** after a Delete at the top, the open edit field moves to Pay rent
> ))}
> ```

### The Keys Before and After the Delete

Lay out the keys of both lists, for the same Delete on Buy milk. First, keyed by the task's ID:

| Key | Before the Delete | After the Delete |
| :--- | :--- | :--- |
| `1` | Buy milk | missing |
| `2` | Call Mom | Call Mom |
| `3` | Pay rent | Pay rent |

Now keyed by the index:

| Key | Before the Delete | After the Delete |
| :--- | :--- | :--- |
| `0` | Buy milk | Call Mom |
| `1` | Call Mom | Pay rent |
| `2` | Pay rent | missing |

With the ID, the key that goes missing is the key of the deleted task. With the index, every task moves up one place, so every key now belongs to the next task. And the key that goes missing is the last one.

Many developers think: "The index is unique in the list, so it is a fine key." Unique is not enough. The key must name the task, not its place.

### The Mistake in `TaskList`

Suppose a developer keys the rows by the index, the second value that `map()` passes to the function (Lesson 18):

```jsx title="src/components/TaskList.jsx" startLine="26" bad="29"
      <ul>
        {tasks.map((task, index) => (
          <TaskRow
            ~key={index}~ // **WRONG:** names the position 0, 1, 2, not the task
            task={task}
            onRename={handleRename}
            onDelete={handleDelete}
          />
        ))}
      </ul>
```

### Why the Edit Field Jumps to Pay rent

**The text of a row follows the task, but the state of a row follows the key, and an index key stays at the position.** So the open edit field stays in the second row, and the second row now shows Pay rent. Here is what happens, in order:
1. The page shows Buy milk with key 0, Call Mom with key 1, and Pay rent with key 2.
2. The user clicks **Edit** on Call Mom. The row with key 1 sets its `isEditing` to true, and the edit field opens there.
3. The user clicks **Delete** on Buy milk. The handler sets `tasks` to Call Mom and Pay rent.
4. `TaskList` renders again. Now `map()` gives key 0 to Call Mom, and key 1 to Pay rent.
5. React finds key 0 again and keeps that row. Its `isEditing` is false, so it shows Call Mom as plain text.
6. React finds key 1 again and keeps that row. Its `isEditing` is true, and it now gets Pay rent as its task. So the edit field shows Pay rent.
7. Key 2 is missing, so React destroys the last row, the one that showed Pay rent before.

```page caption="The to-do list keyed by index, after the user clicks Edit on Call Mom and then Delete on Buy milk."
heading: Tasks
line: Call Mom [Edit] [Delete] | bad
form:
  field:  | Pay rent | bad
  button: Save
  button: Delete
console: quiet
```

The user sees Call Mom closed, and the edit field open on Pay rent. The text in the edit field is right, because it comes from the task's title. If the user clicks **Save** there, Pay rent keeps its text. But the user is now editing the wrong task, and nothing on the page says so.

The Elements panel shows that React removed the last `<li>`, not the first one:

```dom caption="The Elements panel after the Delete with key={index}: the first two li nodes stay with new text, and the last li is gone."
<ul>
+ <li>Call Mom ...</li> | note: Key 0 came back: the li of Buy milk, now with the text Call Mom
! <li> | note: Key 1 came back: the li of Call Mom, still open, now with the text Pay rent
    <input>
    <button>Save</button>
    <button>Delete</button>
  </li>
</ul>
```

### Why Nobody Notices Until the User Deletes

This bug reaches users because nothing warns the developer:
1. A developer writes the index as the key, to silence the missing-key error in the Console.
2. The Console goes quiet. React's tutorial warns about exactly this: "Explicitly passing `key={i}` silences the error but has the same problems as array indices and is not recommended in most cases."
3. While nobody deletes or sorts, every row looks right.
4. A user opens **Edit** on one task, and deletes a task above it.
5. The edit field is now open on the task below the one the user chose.

A **Sort A to Z** button causes the same bug, because a sort also gives every index to another task. Leaving out the key causes it too. React's tutorial says that without a key, React shows the error and uses the array index "by default".

The text is never the problem here. It comes from props, so it always follows the task. What stays at the position is everything the row keeps for itself: its state, the focus, and what the browser keeps in its DOM nodes. One example is the tick in a checkbox that no state controls (Lesson 18).

### The Fix

The fix is one line: key the rows by the task's ID again.

```jsx title="src/components/TaskList.jsx" startLine="26" good="29"
      <ul>
        {tasks.map(task => (
          <TaskRow
            ~key={task.id}~ // Names the task: the edit field stays on Call Mom
            task={task}
            onRename={handleRename}
            onDelete={handleDelete}
          />
        ))}
      </ul>
```

Remember: a row's state follows its key. Give it a key that names the task, and the state follows the task.

## PRINCIPLE | `key={Math.random()}`: a new key on every render destroys every row

> [!PRINCIPLE]
> **Principle 3: A Key Must Be the Same on Every Render**
>
> *Never make a key during render; a key made by `Math.random()` inside `map()` is new on every render, so React destroys every row and creates it again.*
>
> React keeps a row only when its key comes back. A random key never comes back, so every render of the list throws away the state and the DOM nodes of every row. When typing in a row changes the list's state, this happens after every letter: the edit field closes, and the focus is lost. Make a random ID once, when the user creates the item, and store it in the item.
>
> **DO THIS:**
> ```jsx
> function handleAdd(title) {
>   setTasks([...tasks, { ~id: crypto.randomUUID()~, title }]); // The ID is made once, when the user adds the task
> }
> {tasks.map(task => <TaskRow key={task.id} task={task} />)}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {tasks.map(task => (
>   <TaskRow ~key={Math.random()}~ task={task} /> // **WRONG:** a new key on every render closes the edit field after one letter
> ))}
> ```

### A Key That Is New on Every Render

Now suppose each key is a random number made inside `map()`. Every time the list renders, every row gets a key that never existed before. The numbers below only stand for new random values:

| Task | Key on one render | Key on the next render |
| :--- | :--- | :--- |
| Buy milk | `0.42` | `0.58` |
| Call Mom | `0.77` | `0.91` |
| Pay rent | `0.13` | `0.06` |

React matches rows by key, and a random key never comes back. So on every render of the list, React destroys every row, with its state and its DOM nodes, and creates new rows. The user loses everything inside the rows, every time.

Many developers think: "`Math.random()` gives every row a unique key, and unique is what React asks for." Unique is not enough here either. The key must also be the same on every render.

### VS | A Render with the Same Key vs. a Render with a New Key: the same key keeps the row, a new key replaces it

On the screen, a row that renders again and a row that is created again look exactly alike. In both cases React calls `TaskRow`, and the row appears with its text. **It may look the same, but it is NOT the same thing!** The difference is what the row keeps:
- **With the same key,** React keeps the row. Its `isEditing` keeps its value, and its `<input>` stays the same DOM node, with the focus inside it.
- **With a new key,** React destroys the old row and creates a new one. Its `isEditing` starts again from false, and the old `<input>` is removed from the page, with the focus.

```tree caption="A render with the same key keeps the row; a render with a new key destroys it and creates a new one."
What happens to a row when the list renders again
- +The same key [`key={task.id}`] | React **keeps** the row | `isEditing` keeps its value; the `<input>` keeps **the focus**
- !A new key every time [a random number made during render] | React **destroys** the row and **creates** a new one | `isEditing` is **`false` again**; the `<input>` is **gone**
```

### The Mistake in `TaskList`

Suppose the data has no ID. A developer sees the missing-key error in the Console, and writes a random key:

```jsx title="src/components/TaskList.jsx" startLine="26" bad="29"
      <ul>
        {tasks.map(task => (
          <TaskRow
            ~key={Math.random()}~ // **WRONG:** a new key on every render of the list
            task={task}
            onRename={handleRename}
            onDelete={handleDelete}
          />
        ))}
      </ul>
```

The Console goes quiet. The list shows correctly, and **Delete** works.

### Why the Edit Field Closes After One Letter

**Every letter the user types renders the whole list again, and every render of the list makes new keys, so React destroys the row with the edit field after one letter.** Let's follow a user who wants to rename Call Mom to Call Moms.

First, the user clicks **Edit** on Call Mom, and the edit field opens. The random keys do no harm yet. Only `TaskRow` set its state, so React calls only that row again. React's docs put it this way: "React will call the function component whose state update triggered the render." `TaskList` does not run, so `map()` makes no new keys.

```page caption="The to-do list keyed by Math.random, after the user clicks Edit on Call Mom: the edit field opens."
heading: Tasks
line: Buy milk [Edit] [Delete]
form:
  field:  | Call Mom
  button: Save
  button: Delete
line: Pay rent [Edit] [Delete]
console: quiet
```

Then the user clicks into the edit field and types the letter s at the end:
1. The `onChange` handler calls `onRename` with the new title, Call Moms. That sets the tasks in the list's state.
2. `TaskList` renders again, and `map()` makes a new random key for every row.
3. React finds none of the new keys among the old keys.
4. React destroys all three rows, with their state and their DOM nodes. That includes the `<input>` that had the focus.
5. React creates three new rows. Each one starts with `isEditing` set to false.

```page caption="The same list after the user types the letter s: the task is renamed, and the edit field is gone."
heading: Tasks
line: Buy milk [Edit] [Delete]
line: Call Moms [Edit] [Delete] | bad
line: Pay rent [Edit] [Delete]
console: quiet
```

The user sees Call Moms as plain text, with an **Edit** button. The edit field is gone after one letter, and the next letter goes nowhere. To type a second letter, the user must click **Edit** again, then click into the edit field again.

No line of our code causes these two results:
1. **The closed edit field.** No line sets `isEditing` to false. Each new row starts from `useState(false)`, because a removed component loses its state (Lesson 25).
2. **The lost focus.** No line moves the focus. The `<input>` that held it was removed from the page in step 4 (Lesson 31).

### Why the Bug Is Hard to Find

The developer looks in the wrong place first. The edit field closes while the user types, so the developer checks `onChange` and `value`, and finds nothing wrong. React's docs for the `<input>` element name the real cause in their troubleshooting section. First: "it's possible that the input gets removed and re-added from the DOM on every keystroke." Then: "This can happen if you're accidentally resetting state on every re-render, for example if the input or one of its parents always receives a different `key` attribute."

Typing is not the only trigger. Any render of `TaskList` destroys every row: a Delete, a rename, or a parent that renders again (Lesson 54). React's docs warn that random keys "will cause keys to never match up between renders, leading to all your components and DOM being recreated every time." And: "Not only is this slow, but it will also lose any user input inside the list items."

### VS | A Random Key Made on Every Render vs. a Random ID Made Once: only the ID made once stays the same

The fix does not ban random values. It moves them to the moment the user adds the task:

```jsx title="A random key made during render, and a random ID made once when the task is created"
<TaskRow ~key={Math.random()}~ task={task} /> // Runs on every render: a new key each time
const newTask = { ~id: crypto.randomUUID()~, title: 'Buy bread' }; // Runs once, when the user adds the task
```

**It may look the same, but it is NOT the same thing!** Both lines call a random function. The difference is when it runs:
- **`Math.random()` inside `map()`** runs on every render, so each row gets a new key each time.
- **`crypto.randomUUID()`** runs once, when the user adds the task, and the task stores the ID. So the key reads the same value on every render.

React's rule says it plainly: "**Keys must not change** or that defeats their purpose! Don't generate them while rendering."

`useId` is not a fix either (Lesson 52). Its reference page says: "`useId` **should not be used to generate keys** in a list. Keys should be generated from your data."

Remember: a row's state follows its key. A key that changes on every render takes the state away on every render.

## PRINCIPLE | `key={task.title}`: two rows with the same title share one key

> [!PRINCIPLE]
> **Principle 4: A Key Must Be Unique Among Siblings**
>
> *Key each row by a value that no other row of the same list can have and that never changes; a title can repeat and can change, so two rows can share one key.*
>
> React finds each row by its key. When two rows share a key, React cannot tell them apart: the Console reports two children with the same key, and after a Delete the page can keep a row that the data no longer has. A key taken from a title also changes when the user renames the task, which closes the edit field. An ID is unique and never changes.
>
> **DO THIS:**
> ```jsx
> {tasks.map(task => (
>   <TaskRow ~key={task.id}~ task={task} onDelete={handleDelete} /> // Two Buy milk tasks get keys 1 and 4
> ))}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {tasks.map(task => (
>   <TaskRow ~key={task.title}~ task={task} onDelete={handleDelete} /> // **WRONG:** two Buy milk tasks share one key, and a deleted one can stay on the page
> ))}
> ```

### Four Tasks, Two Named Buy milk

Users often write the same task twice, on two different days. Here the list has four tasks, and two of them are Buy milk:

```jsx title="Four tasks keyed by their title"
const initialTasks = [
  { id: 1, title: 'Buy milk' },
  { id: 2, title: 'Call Mom' },
  { id: 3, title: 'Pay rent' },
  { id: 4, title: 'Buy milk' },
];

{tasks.map(task => (
  <TaskRow ~key={task.title}~ task={task} onRename={handleRename} onDelete={handleDelete} /> // **WRONG:** two rows get the key Buy milk
))}
```

React finds a row by its key. With two rows named Buy milk, one key points at two rows. React cannot know which of them comes back on the next render.

Many developers think: "The title comes with the data, so it is a good key." It is neither unique nor stable. Titles repeat, and a title changes when the user renames the task. Only the ID is both unique and the same on every render.

### What the Console Reports

On the first render, the page shows four rows, and the Console reports two rows with the same key:

```page width=full caption="The to-do list keyed by task.title on the first render: four rows, and an error in the Console for the two Buy milk rows."
heading: Tasks
line: Buy milk [Edit] [Delete]
line: Call Mom [Edit] [Delete]
line: Pay rent [Edit] [Delete]
line: Buy milk [Edit] [Delete]
console: Encountered two children with the same key, `Buy milk`. Keys should be unique so that components maintain their identity across updates.
```

The message goes on to say that rows with the same key may be duplicated or left out, and that this behavior is unsupported. React's rule is short: "**Keys must be unique among siblings.**" Siblings are the rows inside the same list. Two different lists may use the same keys.

### Delete on the First Buy milk

**The user deletes one Buy milk, and the page keeps a row that the data no longer has.** Here is what happens, in order:
1. The data has four tasks: Buy milk with ID 1, Call Mom with ID 2, Pay rent with ID 3, and Buy milk with ID 4. The keys are their titles.
2. The user clicks **Delete** on the first Buy milk. The handler sets `tasks` to Call Mom, Pay rent, and Buy milk with ID 4.
3. React looks for the new keys among the old keys. The key Buy milk points at two old rows, and React keeps only one of them for the new Buy milk.
4. React matches the other old Buy milk row with nothing, and it never removes that row.

```page width=full caption="The to-do list keyed by task.title, after the user deletes the first Buy milk: the data holds three tasks, and the page still shows four rows."
heading: Tasks
line: Buy milk [Edit] [Delete] | bad
line: Call Mom [Edit] [Delete]
line: Pay rent [Edit] [Delete]
line: Buy milk [Edit] [Delete]
console: Encountered two children with the same key, `Buy milk`. Keys should be unique so that components maintain their identity across updates.
```

The data now holds three tasks, and the page shows four rows. The error in the Console is still the one from the first render. No line of our code renders the extra row. It is a DOM node that React did not remove, because no key in the new list led React to it. React's docs say nothing more about two equal keys, and React's own message calls the behavior unsupported. So no result here is something to rely on.

### A Title Also Changes When the User Renames the Task

Suppose every title is different, so the Console stays quiet. The user clicks **Edit** on Call Mom and types the letter s. The title becomes Call Moms, so the key of that row becomes Call Moms too. React does not find the old key Call Mom. It destroys that row and creates a new one, so the edit field closes after one letter, as in Principle 3.

### The Fix

The fix is the ID again. When the data has no ID, make one when the user creates the item, with a counter or `crypto.randomUUID()`, and store it in the item. Our final list keeps four tasks, two of them Buy milk, and keys them by ID:

```jsx title="src/components/TaskList.jsx" startLine="4"
const initialTasks = [
  { id: 1, title: 'Buy milk' },
  { id: 2, title: 'Call Mom' },
  { id: 3, title: 'Pay rent' },
  { ~id: 4~, title: 'Buy milk' }, // Same title, different ID
];
```

```jsx title="src/components/TaskList.jsx" startLine="28" good="30"
        {tasks.map(task => (
          <TaskRow
            ~key={task.id}~ // 1, 2, 3, 4: unique and the same on every render
            task={task}
            onRename={handleRename}
            onDelete={handleDelete}
          />
        ))}
```

Now the Console stays quiet. A Delete on the first Buy milk removes the row with key 1, and the second Buy milk stays on the page with key 4.

Remember: a row's state follows its key. Two rows cannot follow one key.

## All 4 Principles Together

### The Complete Files

Here is the complete project. `TaskList` keys every row by the task's ID. That key names the task, stays the same on every render, and is unique in the list:

```jsx title="src/App.jsx"
import TaskList from './components/TaskList.jsx';

export default function ~App~() { // 1. Called first when the page loads
  return <TaskList />;
}
```

```jsx title="src/components/TaskList.jsx"
import { useState } from 'react';
import TaskRow from './TaskRow.jsx';

const initialTasks = [
  { id: 1, title: 'Buy milk' },
  { id: 2, title: 'Call Mom' },
  { id: 3, title: 'Pay rent' },
  { id: 4, title: 'Buy milk' },
];

export default function ~TaskList~() { // 2. Called second, and again after every Delete and every letter typed
  const [tasks, setTasks] = useState(initialTasks);

  function handleRename(id, newTitle) {
    setTasks(tasks.map(task =>
      task.id === id ? { ...task, title: newTitle } : task
    ));
  }

  function handleDelete(id) {
    setTasks(tasks.filter(task => task.id !== id));
  }

  return (
    <>
      <h1>Tasks</h1>
      <ul>
        {tasks.map(task => (
          <TaskRow
            ~key={task.id}~ // Principles 1 to 4: names the task, the same on every render, unique in the list
            task={task}
            onRename={handleRename}
            onDelete={handleDelete}
          />
        ))}
      </ul>
    </>
  );
}
```

```jsx title="src/components/TaskRow.jsx"
import { useState } from 'react';

export default function ~TaskRow~({ task, onRename, onDelete }) { // 3. Called once per task, in the order of tasks
  const [isEditing, setIsEditing] = useState(false);

  return (
    <li>
      {isEditing ? (
        <>
          <input
            value={task.title}
            onChange={e => onRename(task.id, e.target.value)}
          />
          <button onClick={() => setIsEditing(false)}>Save</button>
        </>
      ) : (
        <>
          {task.title}
          <button onClick={() => setIsEditing(true)}>Edit</button>
        </>
      )}
      <button onClick={() => onDelete(task.id)}>Delete</button>
    </li>
  );
}
```

### How React Renders and Updates the List

On the first render, React calls `App`, then `TaskList`, then one row component for each task. After every **Delete** and every letter typed in an edit field, `TaskList` renders again. React then matches each `TaskRow` with its old row by the task's ID:

```tree caption="The order in which React calls the components of the to-do list, and the key of each row."
`App` [1. Renders `<TaskList />`] | **Root component**
- +`TaskList` [2. Holds `tasks` in state] | Renders one `TaskRow` per task, **keyed by `task.id`**
  - +`TaskRow` with key `1` [3. `Buy milk`] | Keeps its own `isEditing`
  - +`TaskRow` with key `2` [4. `Call Mom`] | Keeps its own `isEditing`
  - +`TaskRow` with key `3` [5. `Pay rent`] | Keeps its own `isEditing`
  - +`TaskRow` with key `4` [6. `Buy milk`] | Keeps its own `isEditing`
```

### Each Key, and What the User Sees

| Key | What it names | After a Delete at the top | While the user types in an edit field | Console |
| :--- | :--- | :--- | :--- | :--- |
| **`key={task.id}`** | The task | The edit field stays on Call Mom | The edit field stays open | Quiet |
| **`key={index}`** | The position in the list | The edit field jumps to Pay rent | The edit field stays open | Quiet |
| **`key={Math.random()}`** | Nothing: a new key on every render | Every row is destroyed and created again | The edit field closes after one letter | Quiet |
| **`key={task.title}`** | A title that can repeat and change | A deleted Buy milk can stay on the page | The edit field closes after one letter | An error for two children with the same key |

Remember the one sentence of this lesson: **a row's state follows its key, not its text**. So give every row a key that names the item: an ID that is unique and never changes.

## For the Interview

> **The Interview Question:** What makes a good key across re-renders, and how do unstable or duplicate keys corrupt reconciliation?

### How to Answer Clearly in 30 Seconds

"On every render of a list, React matches the new rows with the old rows by key. That is reconciliation for lists. A key found again keeps its component, its state, and its DOM nodes, with new props. A new key creates a component, and a missing key destroys one. So the key decides which state goes with which item. A good key does four things:
1. **It names the item, not its position.** With the index, a Delete, an insert, or a sort gives every index to another item. An open edit field or a tick stays at its position while the item moves.
2. **It stays the same on every render.** `Math.random()` inside `map()` never matches, so React destroys and creates every row on every render. That is slow, and it loses the user's input and focus.
3. **It is unique among siblings.** Two equal keys, such as two titles Buy milk, leave React unable to tell the rows apart. The Console reports it, and a deleted row can stay on the page.
4. **It comes with the data.** Use a database ID, or an ID made once with a counter or `crypto.randomUUID()` when the item is created."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"The Console is quiet with `key={index}`. Why is it still a problem, and when is it fine?"**
   The Console only checks that every row has a key and that no two keys repeat, and an index passes both checks. React's tutorial says: "Explicitly passing `key={i}` silences the error but has the same problems as array indices." React's docs show the same bug with a sort. In a contact list keyed by index, the user presses "Show email" for Alice, then ticks "Show in reverse order", and "it's _Taylor's_ email that is expanded now". The fix there is `key={contact.id}`, because "A `key` lets you specify a named position instead of relying on order." The index is fine only when the list never changes order, and no item is ever inserted or deleted. Two examples are the lines of a poem and the moves of a tic-tac-toe game. Moving `isEditing` up into `TaskList` as `editingId` hides the edit field bug, but it does not fix the key. The focus and anything else the row keeps still stay at the position.
2. **"Why does `key={Math.random()}` lose the focus, and is `useId` a better choice?"**
   A random key never matches, so on every render of the list React destroys every row with its DOM nodes and creates new ones. The `<input>` with the focus is removed from the page, so the focus is gone, even if the open or closed state lived in the parent. `useId` is not a fix: "`useId` **should not be used to generate keys** in a list. Keys should be generated from your data." Make the ID once, when the item is created, and store it in the item.
3. **"Do keys matter outside a list?"**
   Yes. The same rule resets one component on purpose. React ties state to the position in the tree. The docs say: "Specifying a `key` tells React to use the `key` itself as part of the position, instead of their order within the parent." With `<Chat key={to.id} />`, a new contact gives the chat a new key. So React destroys the old chat with its state, and creates a new one with an empty message field (Lesson 25).

```tree dir=right caption="Interview summary: what each kind of key names, and what the user sees after a change to the list."
What makes a good key
- +The ID from the data [`key={task.id}`] | Names **the item**, the same on every render, unique | State **stays with the item**
- !The index [`key={index}`] | Names **a position** | State **moves to another item** after a Delete, insert, or sort
- !A random number made during render | Names **nothing** for longer than one render | Every row is **destroyed and created again**
- !A title [`key={task.title}`] | Can **repeat** and can **change** | Two rows share a key; a deleted row **can stay on the page**
```
