# Lecture 118: How the Server Sends a React Page as a Stream

*(How does the server send a React page in parts, instead of as one finished string of HTML?)*

> INTERVIEW QUESTION | ❱ CORE | How do you stream HTML on the server with renderToPipeableStream or renderToReadableStream?

---

## VS | `renderToString` vs. `renderToPipeableStream`: one returns the page, the other returns a way to send it

> Until now, our server called `renderToString`, got the whole page back as one string of HTML, and sent that string in one piece. **A streaming API such as `renderToPipeableStream` returns no HTML at all: it returns a function, `pipe`, and React itself writes the page into the response, part by part.** The reason: the user reads the product at once, while the slow reviews are still on their way in the same response.

Remember how the server of Lesson 102 sent a React page. It is plain JavaScript: a function returns a string, you keep it in a variable, and you send it.

```jsx title="server.js with renderToString"
const html = ~renderToString~(<App />); // html is the whole page, as one string
response.send(html); // The server sends that string in one piece
```

The server holds the whole page in a variable. Now look at the streaming version:

```jsx title="server.js with renderToPipeableStream"
const { pipe } = ~renderToPipeableStream~(<App />, { // No string comes back: React returns pipe
  onShellReady() {
    ~pipe(response)~; // React starts writing the page into the response
  }
});
```

Both calls start with `renderTo`. Both take `<App />`. Both sit in the same route handler of the server file. So the switch looks like a rename. **It may look the same, but it is NOT the same thing!**
- **`renderToString`** returns the page itself: a finished string of HTML. Our server holds it, and sends it in one piece.
- **`renderToPipeableStream`** returns no HTML. It returns an object with a function, `pipe`. When our server calls `pipe(response)`, React writes the page into the response by itself.

Remember the plain Node server of Lesson 117. You can write one response in several parts with `response.write`, and close it with `response.end`. `pipe(response)` hands that job to React. React does the writes for you: the shell first, each slow part when it is ready, and the end last.

Here is the one sentence to keep in mind for this whole lesson:

**A streaming API gives the server no HTML. It gives a stream, and the server's job is to connect that stream to the response at the right moment.**

```tree caption="renderToString returns the page; renderToPipeableStream returns a way to send it."
Two ways the server gets a React page out
- !With `renderToString` [`const html`] | React returns **the whole page as one string** | The server sends it **in one piece**
- +With `renderToPipeableStream` [`const { pipe }`] | React returns **no HTML**, only **`pipe`** and **`abort`** | The server calls `pipe`, and React writes **the shell first, the rest later**
```

### Three Ideas From Earlier Lessons

> [!DEFINITION]
> **Server rendering.** [REVIEW] With server rendering, the server runs your components and sends their HTML, so the user sees the page before any JavaScript loads. `renderToString(<App />)` returns that HTML as one string, and the route handler sends it with `response.send`. The `response` is the object the route handler receives for each request, and whatever the server writes into it goes to the browser (Lesson 102).

> [!DEFINITION]
> **Hydration.** [REVIEW] The HTML from the server cannot answer clicks yet: it is plain HTML, and no click handler is attached to it. Then the app's JavaScript loads in the browser and calls `hydrateRoot`, and React attaches itself and your click handlers to the HTML that is already on the screen. This step is called hydration (Lesson 104).

> [!DEFINITION]
> **The shell.** [REVIEW] The shell is everything on the page outside every `<Suspense>` boundary, with each boundary's fallback, such as `Loading reviews...`, in its place. On the server, React sends the shell first. It sends each boundary's content later, in the same response, with a small inline `<script>` that puts the content in the place of the fallback. That inline script moves HTML only, and it does not need React in the browser (Lesson 117).

### What Is at Stake

What is at stake is what the user sees on a product page whose reviews come from a slow lookup. Three things can happen, depending on how the server sends the page:
1. **The server connects the stream as soon as the shell is ready.** The user reads the product name and the price at once, and the reviews follow a moment later in the same response. React's docs: "Streaming allows the user to start seeing the content even before all the data has loaded on the server."
2. **The server keeps `renderToString`, even with the reviews inside `<Suspense>`.** The HTML stops at the loading line, and the response ends there. The user sees the reviews only after the app's JavaScript loads in the browser.
3. **The server streams the page, but never names the script that starts React in the browser.** The whole page arrives, reviews included. Then the user clicks `Add to cart`, and nothing happens.

### Where Readers Usually Go Wrong

Readers usually go wrong in four ways:
1. **They expect HTML back from `renderToPipeableStream`**, the way they got it from `renderToString`.
2. **They forget the option that names the app's script**, because the page looks finished without it.
3. **They pick the API by its name instead of by the server it runs on.** `renderToPipeableStream` needs Node.js Streams. `renderToReadableStream` needs Web Streams.
4. **They start sending only when every part of the page is ready, for every visitor.** Then no visitor gets the page in parts.

### Two Stream APIs, One Difference

React gives the server two streaming APIs. They share almost everything: the same `<App />`, and the same option for the app's script. They send the same page in the same order: the shell first, and the slow parts later.

The one difference is the kind of stream they give back:
- **`renderToPipeableStream`** gives a **Node.js Stream**. The server pipes it into the response. It is the API for a Node.js server.
- **`renderToReadableStream`** gives a **Web Stream**. The server returns it inside a `Response` object. It is the API for Deno and modern edge runtimes, which use the stream standard of the browser.

When developers send a React page from a server, they choose between four ways:

```tree caption="The four ways to send a React page from the server, and when each one fits."
Four ways to send a React page from the server
- +`renderToString` | One string, **sent at once** | For servers **without streams**, as seen in Lesson 102
- +`renderToPipeableStream` | A stream for **Node.js** servers | **This lesson**
- +`renderToReadableStream` | A stream for **Web Streams** runtimes, such as **Deno** and **edge runtimes** | **This lesson**
- +`prerender` and `prerenderToNodeStream` | The HTML is made **at build time** | For pages that are **the same for every reader**, Lesson 119
```

In real projects, a framework often calls these APIs for you. React's docs: "A framework may call them for you." This lesson shows what the framework does underneath, so you can read that code, debug it, and explain it in an interview.

2. **`bootstrapScripts`: the page answers clicks.** The stream sends HTML only. The server must name the script that calls `hydrateRoot`.
3. **`renderToReadableStream`: the same page on Deno and edge runtimes.** The server awaits it, and returns the stream inside a `Response`.
4. **`onAllReady`: only the crawler waits for every part.** Every other visitor keeps `onShellReady`.

## PRINCIPLE | `pipe(response)` inside `onShellReady`: the product goes out at once, and the reviews follow in the same response

> [!PRINCIPLE]
> **Principle 1: `pipe(response)`: React Writes the Page into the Response, Shell First**
>
> *`renderToPipeableStream` returns `pipe` and `abort`, not HTML; call `pipe(response)` inside `onShellReady`, so the shell goes out at once and the rest follows.*
>
> The server no longer holds a page to send. It holds a way to send one. When React has rendered the shell, it calls `onShellReady`, our code calls `pipe(response)`, and the user sees the product at once. The reviews arrive later in the same response, and our server code never touches a string of HTML.
>
> **DO THIS:**
> ```jsx
> const { pipe } = renderToPipeableStream(<App reviewsPromise={getReviews()} />, {
>   onShellReady() {
>     ~pipe(response)~; // The product goes out now; the reviews follow in the same response
>   }
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const html = ~renderToString~(<App reviewsPromise={getReviews()} />); // **WRONG:** the HTML stops at Loading reviews...
> response.send(html);
> ```

Here is the smallest server that streams a React page:

```jsx title="server.js"
app.use('/', (request, response) => {
  const { ~pipe~ } = renderToPipeableStream(<App />, { // React returns an object with pipe and abort
    ~onShellReady~() { // React calls this the moment the shell is rendered
      response.setHeader('content-type', 'text/html');
      pipe(response); // From here on, React writes the page into response
    }
  });
});
```

> [!DEFINITION]
> **`renderToPipeableStream`.** [NEW] `renderToPipeableStream` comes from `react-dom/server`. React's docs say it renders a React tree "as HTML into a Node.js Stream". It returns no string. It returns an object with two functions: `pipe`, which starts the sending, and `abort`, which tells React to stop waiting for the slow parts. Its second argument is an object of options, such as `onShellReady` (Lesson 118).

The curly braces in `const { pipe }` take `pipe` out of that object, the same destructuring we use for props (as seen in Lesson 08). Here is what the other pieces are:
- **`pipe(response)`** "outputs the HTML into the provided Writable Node.js Stream", in the words of React's docs. A Writable Node.js Stream is an object our server can keep writing into, piece by piece, while the connection to the browser stays open. Here it is `response`, the same `response` the route handler receives.
- **`onShellReady`** is a function our code writes inside the options object. React calls it, and we never call it ourselves. React's docs say it "fires right after the initial shell has been rendered".
- **`response.setHeader('content-type', 'text/html')`** tells the browser that the body of the response is HTML. It runs before `pipe`, because once React starts sending, the server can no longer change the headers or the status code.

Why the name `pipe`? Node.js uses this word when one stream is connected to another. Think of a water pipe between a tank and a tap, as an image. The water reaches the tap while it flows, without a wait for the tank to fill. `pipe(response)` lays such a pipe between React and the browser, so the HTML reaches the browser while React writes it.

### Why `pipe` Waits for `onShellReady`

Once React has rendered the shell, it has a whole page to show, with `Loading reviews...` where the reviews will go. That is the first moment worth sending. React's docs: "Call `pipe` in `onShellReady` if you want to enable streaming."

### The Product Page as a Stream

Two files change. First, `App`, our page component, renders the whole document, from `<html>` down. It also gets back its `Add to cart` button. React's docs expect this from the root component: it "is expected to represent the entire document, so the `App` component should render the `<html>` tag."

```jsx title="src/App.jsx"
import { Suspense, useState } from 'react';
import Reviews from './Reviews.jsx';

export default function App({ reviewsPromise }) {
  const [count, setCount] = useState(0);
  return (
    ~<html>~ {/* App renders the whole document */}
      <head>
        <title>Blue Sneakers</title>
      </head>
      <body>
        <h1>Blue Sneakers</h1>
        <p>$49</p>
        <button onClick={() => setCount(count + 1)}>Add to cart</button>
        <p>Cart: {count}</p>
        <Suspense fallback={<p>Loading reviews...</p>}>
          <Reviews reviewsPromise={reviewsPromise} />
        </Suspense>
      </body>
    </html>
  );
}
```

Our code writes no doctype line at the top. React adds it to the response by itself. React's docs: "React will inject the doctype ... into the resulting HTML stream".

Second, the server file drops `renderToString` and `response.send`, and streams the page instead:

```jsx title="server.js"
import { renderToPipeableStream } from 'react-dom/server';
import App from './src/App.jsx';
import { getReviews } from './src/db.js';

app.use('/', (request, response) => {
  const { pipe } = renderToPipeableStream(<App reviewsPromise={getReviews()} />, {
    onShellReady() {
      response.setHeader('content-type', 'text/html');
      ~pipe(response)~; // The shell goes to the browser now; the reviews follow later
    }
  });
});
```

`app` is our server, and `app.use` registers the route handler (as seen in Lesson 102). The database file and `Reviews` stay exactly as they were in Lesson 117. The complete code at the end of the lecture shows them.

### One Visit, in Order

**Our server code never holds the page, and the response is still open while the user reads the product.** Here is one visit, in order:
1. The user opens the product page, and the request reaches the server file.
2. The server calls `getReviews()` and `renderToPipeableStream`. Nothing is sent yet.
3. React renders the shell: the heading, the price, the button, the cart line, and `Loading reviews...` in place of the reviews.
4. React calls `onShellReady`. Our code sets the header and calls `pipe(response)`, and the shell goes to the browser.
5. The browser shows the product with `Loading reviews...`, while the response is still open.
6. Two seconds later, the reviews are ready. React writes their HTML into the same response, with the inline `<script>` that swaps them in.
7. React ends the response. At no point did our server code hold a string of HTML.

```tree dir=right caption="One visit to the product page with renderToPipeableStream: the shell goes out first, and the reviews follow in the same response."
One response, sent in two parts
- +1. The shell is rendered [`onShellReady`] | Our code calls **`pipe`** | The user sees **`Blue Sneakers`**, **`$49`**, and **`Loading reviews...`**
- +2. The reviews are ready, two seconds later | React writes them into **the same response** | **`Great fit`** and **`Runs small`** take the place of the loading line
- +3. Nothing is left to render | React **ends the response** | Our server code **never held a string** of HTML
```

### Real Beginner Mistake: `renderToString` Around a `<Suspense>`

1. A team wraps the reviews in `<Suspense>`, so that the product shows first.
2. The server still calls `renderToString`, so the HTML holds `Loading reviews...`.
3. The response ends there, without the reviews.
4. The user sees the reviews only after the app's JavaScript loads in the browser. React's docs: "The content will not appear until the client code loads."
5. The browser's Console shows the React error that asks to switch to `renderToPipeableStream` (as seen in Lesson 102).
6. A search engine's crawler that reads only the HTML finds `Loading reviews...` instead of the reviews.

Remember: a streaming API gives the server no HTML. The server connects the stream to the response, and React keeps writing into it.

## PRINCIPLE | `bootstrapScripts`: React loads in the browser, so `Add to cart` answers the click

> [!PRINCIPLE]
> **Principle 2: `bootstrapScripts`: The Stream Brings the Page, the Script Brings React**
>
> *Name the script that calls `hydrateRoot(document, ...)` in `bootstrapScripts`; React adds its `<script>` tag to the stream.*
>
> A streamed page can look finished, reviews included, without React ever running in the browser, because the inline script that swaps the reviews does not need React. Until a bootstrap script calls `hydrateRoot`, no click handler is attached, and `Add to cart` ignores every click with no error.
>
> **DO THIS:**
> ```jsx
> const { pipe } = renderToPipeableStream(<App reviewsPromise={getReviews()} />, {
>   ~bootstrapScripts: ['/main.js']~, // React adds <script src="/main.js"> and the button answers clicks
>   onShellReady() {
>     pipe(response);
>   }
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const { pipe } = renderToPipeableStream(<App reviewsPromise={getReviews()} />, {
>   ~onShellReady~() { // **WRONG:** no bootstrapScripts, so the page arrives and Add to cart does nothing
>     pipe(response);
>   }
> });
> ```

**The stream brings the page, not React.** With the server of Principle 1, the whole page arrives, reviews included, and every click on `Add to cart` does nothing:

```page width=text caption="The streamed page after the user clicks Add to cart: the reviews are in, and the cart line has not moved."
heading: Blue Sneakers
line: $49
line: [Add to cart]
line: Cart: 0 | bad
line: Great fit
line: Runs small
```

Here is what happens, in order:
1. The server streams the shell, then the reviews with their inline `<script>`.
2. The user sees the whole page, reviews included, about two seconds after opening it.
3. The user clicks `Add to cart`.
4. The `<button>` on the page is plain HTML with no click handler. The `onClick` lives in `App`, and that component never ran in the browser.
5. `Cart: 0` stays `Cart: 0`. No error appears in the Console, because no React code is on the page to report one.

But the reviews did take the place of the loading line. Is that not React? No. The small inline `<script>` that React writes into the stream does the swap, and it moves HTML without React. React's docs: "Streaming does not need to wait for React itself to load in the browser, or for your app to become interactive."

### Where the Script Tag Went

Remember the HTML template of Lesson 102. It had a `<div id="root">`, and under it a `<script>` tag that loaded the app's bundle. Our server put the HTML from `renderToString` inside that template.

Now `App` renders the whole document, from `<html>` down. No template is left around it. So no line of our code writes that `<script>` tag anymore, and the browser never loads React.

### The Fix: One Option on the Server, One Call in the Browser

On the server, we name the script in `bootstrapScripts`:

```jsx title="server.js" startLine="5"
app.use('/', (request, response) => {
  const { pipe } = renderToPipeableStream(<App reviewsPromise={getReviews()} />, {
    ~bootstrapScripts: ['/main.js']~, // React adds a <script> tag for /main.js to the stream
    onShellReady() {
      response.setHeader('content-type', 'text/html');
      pipe(response);
    }
  });
});
```

In the browser, that script calls `hydrateRoot` on the whole document:

```jsx title="src/main.jsx"
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';
import { getReviews } from './db.js';

hydrateRoot(~document~, <App reviewsPromise={getReviews()} />); // App renders <html>, so React hydrates the whole document
```

> [!DEFINITION]
> **`bootstrapScripts`.** [NEW] `bootstrapScripts` is an option of `renderToPipeableStream` that takes a list of script URLs. React's docs: "An array of string URLs for the `<script>` tags to emit on the page. Use this to include the `<script>` that calls `hydrateRoot`." For each URL, React adds a `<script>` tag with the `async` attribute to the stream, and a `<link rel="preload">` for the same URL in the `<head>`, so the browser starts the download early. The script we name there is called the bootstrap script (Lesson 118).

Here is what the other new pieces mean:
- **The bootstrap script** here is the built bundle of `main.jsx`, which our server serves at the URL `/main.js`. In a real build, the file gets a name with a hash, such as `main.123456.js`, read from the build output. Lesson 143 covers how.
- **`hydrateRoot(document, ...)`** is the call of Lesson 104, now given `document` instead of the root element. `App` renders `<html>` itself, so React must take over the whole document. React's docs: "your bootstrap script should hydrate the entire `document`".
- **`getReviews()` in the browser file** is there because the browser must render `App` with the same props as the server, so that hydration finds the same page. Our stand-in database file can run in both places. A real app gets its data to the browser through its framework (as seen in Lesson 109).

Now the click works. React loads, attaches the `onClick` to the button, and the cart line goes up:

The two pages look the same until the user clicks. **It may look the same, but it is NOT the same thing!** Only with `bootstrapScripts` does React run in the browser and attach the click handler.

### A Click Before the Browser Has the Reviews

Our stand-in database file shows one more thing. In the browser, `getReviews()` waits two seconds again. Until it answers, React in the browser does not have the reviews.

So when the bootstrap script arrives late, the user may click `Add to cart` within those two seconds. The cart line goes up, but `Loading reviews...` comes back in the place of the reviews. Why? Well, the click changes `count` in `App`, so React renders the reviews again, and in the browser it does not have them yet. The reviews come back when the browser's own `getReviews()` answers. The pages above show a click after that moment.

### VS | The Inline Script vs. the Bootstrap Script: one moves HTML, the other brings React

The stream now holds two kinds of `<script>` tag, and both come from React. **They are NOT the same thing!**
- **The inline `<script>` that swaps the reviews.** React writes it into the stream by itself, every time a boundary's content is ready (as seen in Lesson 117). It only moves HTML.
- **The bootstrap `<script>` for `/main.js`.** React writes it only when our code names it in `bootstrapScripts`. It loads React and our components, which attach every click handler.

`bootstrapScripts` has two relatives:
- **`bootstrapModules`** does the same job with `<script type="module">` tags.
- **`bootstrapScriptContent`** puts one string into an inline `<script>` tag, for example a small piece of data the browser needs before the bundle runs.

### Real Beginner Mistake: The Template Is Gone, and the Script With It

1. A developer moves the product page from `renderToString` to `renderToPipeableStream`.
2. `App` now renders the whole document, so the template with the old `<script>` tag is gone.
3. Nobody adds `bootstrapScripts`, because the page and the reviews look right in the browser.
4. Shoppers click `Add to cart`, and nothing happens.

Remember: the stream brings the page, and the bootstrap script brings React.

## PRINCIPLE | `renderToReadableStream`: the same page on Deno and edge runtimes, returned inside a `Response`

> [!PRINCIPLE]
> **Principle 3: `renderToReadableStream`: The Same Page, Returned Inside a `Response`**
>
> *On Deno or an edge runtime, `await renderToReadableStream(...)` and return the stream inside `new Response(stream, ...)`; on Node.js, use `renderToPipeableStream`.*
>
> Both APIs send the user the same page in the same order. The one difference is the shape of the code. On Node.js, React calls `onShellReady` and our code pipes. On Web Streams, the `await` ends when the shell is ready, and the handler returns the stream while React keeps writing the rest into it.
>
> **DO THIS:**
> ```jsx
> const stream = await ~renderToReadableStream~(<App />, { bootstrapScripts: ['/main.js'] }); // On Deno or an edge runtime
> const { pipe } = ~renderToPipeableStream~(<App />, { bootstrapScripts: ['/main.js'] }); // On a Node.js server
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const stream = await ~renderToReadableStream~(<App />, { bootstrapScripts: ['/main.js'] }); // **WRONG:** on a Node.js server it works, but React's docs warn of worse performance
> ```

Some servers do not run on Node.js:
- **Deno** is another JavaScript runtime, like Node.js.
- **An edge runtime** runs server code in many places, close to the users.

Both use Web Streams, the stream standard of the browser. For them, React has `renderToReadableStream`. Here is the Node.js server of Principle 2, and then the same page sent from a Web Streams runtime:

```jsx title="server.js on Node.js"
const { pipe } = ~renderToPipeableStream~(<App reviewsPromise={getReviews()} />, { // Returns pipe at once
  bootstrapScripts: ['/main.js'],
  onShellReady() {
    response.setHeader('content-type', 'text/html');
    pipe(response); // The shell is ready: React writes into response
  }
});
```

```jsx title="handler.js on a Web Streams runtime"
async function handler(request) {
  const stream = await ~renderToReadableStream~(<App reviewsPromise={getReviews()} />, { // Waits for the shell
    bootstrapScripts: ['/main.js'],
  });
  return ~new Response~(stream, { // The shell is ready: the handler returns the stream as the body
    headers: { 'content-type': 'text/html' },
  });
}
```

For the user, **yes, it is the exact same thing!** The same `<App />`, the same `bootstrapScripts`, and the same page in the same order: the product first, the reviews two seconds later.

For the code, the one difference is where "the shell is ready" lives:
- **With `renderToPipeableStream`**, it is a callback. React calls `onShellReady`, and our code calls `pipe(response)` inside it.
- **With `renderToReadableStream`**, it is the end of the `await`. The function returns a Promise, and React's docs say it "will resolve to a `stream` as soon as the entire shell has been rendered." The handler then returns that stream inside a `Response`.

> [!DEFINITION]
> **`renderToReadableStream`.** [NEW] `renderToReadableStream` comes from `react-dom/server`, like the Node.js API. React's docs say it renders a React tree "as HTML into a Readable Web Stream". A Readable Web Stream is the kind of stream that browsers, Deno, and modern edge runtimes use. The function returns a Promise of that stream, and our code does not read the stream: it hands it on, as the body of a `Response`. `Response` is the web's object for an HTTP response, and the runtime provides it, not React (Lesson 118).

The `handler(request)` shape is the one React's docs use. How a given runtime calls the handler depends on that runtime.

### The Handler Returns Before the Reviews Exist

**The handler function is already finished, and the response keeps growing.** In order:
1. The handler calls `renderToReadableStream`, and `await` pauses it.
2. React renders the shell: the heading, the price, the button, the cart line, and `Loading reviews...`.
3. The Promise resolves to `stream`, and the handler returns the `Response`. The handler function is finished.
4. The browser shows the product with `Loading reviews...`.
5. Two seconds later, React writes the reviews into the same `stream`, long after the handler returned.

The function is done, but the stream it returned still belongs to React, and React keeps writing into it.

### The Lines That Match in the Two APIs

Every option of one API has a match in the other. The Node.js API uses callbacks. The Web Streams API uses the Promise and the stream it resolves to:

| What the server needs | With `renderToPipeableStream` on Node.js | With `renderToReadableStream` on Web Streams |
| :--- | :--- | :--- |
| **Start to send when the shell is ready** | `onShellReady() { pipe(response); }` | `const stream = await renderToReadableStream(...)`, then `return new Response(stream, ...)` |
| **Wait for every part, for crawlers** | `onAllReady() { pipe(response); }`, Principle 4 | `await stream.allReady`, Principle 4 |
| **Handle a shell that fails to render** | `onShellError`, Lesson 125 | a `try` and `catch` around the `await`, Lesson 125 |
| **Stop the wait for slow parts** | call `abort()` | the `signal` option with an `AbortController` |

### The Runtime Picks the API

The runtime the server runs on picks the API, not the API's name or its age:

```tree caption="The runtime the server runs on decides which streaming API to call."
Which streaming API fits which server
- +A **Node.js** server [`renderToPipeableStream`] | Node.js Streams | The server calls **`pipe`** with the response
- +**Deno** or an **edge runtime** [`renderToReadableStream`] | Web Streams | The handler returns the stream inside a **`Response`**
```

Node.js can run the Web Streams API too. React's docs: "Node.js also includes these methods for compatibility, but they are not recommended due to worse performance."

### Real Beginner Mistake: Web Streams on a Node.js Server

1. A team on a Node.js server reads that `renderToReadableStream` uses web standards, and picks it.
2. It works, because Node.js includes the Web Streams methods.
3. React's docs do not recommend them on Node.js because of worse performance, and the team pays that cost on every request.

Remember: the runtime picks the API. Node.js gets `renderToPipeableStream`, and Deno or an edge runtime gets `renderToReadableStream`.

## PRINCIPLE | `onAllReady`: the crawler gets the final HTML, and every other visitor keeps `onShellReady`

> [!PRINCIPLE]
> **Principle 4: `onAllReady`: Wait for Every Part Only for Crawlers**
>
> *Call `pipe` in `onAllReady`, or `await stream.allReady`, only for crawlers; every other visitor keeps `onShellReady`.*
>
> `onShellReady` and `onAllReady` end with the same page, on two schedules. With `onShellReady`, the shopper sees the product at once and the reviews follow. With `onAllReady`, nothing reaches the browser until the slowest part is rendered. A crawler needs that final HTML. A shopper needs the product now.
>
> **DO THIS:**
> ```jsx
> onShellReady() {
>   if (!isCrawler) pipe(response);
> },
> ~onAllReady~() { // Only the crawler waits for the reviews
>   if (isCrawler) pipe(response);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~onAllReady~() { // **WRONG:** every shopper sees a blank tab until the reviews are rendered
>   pipe(response);
> }
> ```

`onShellReady` has a neighbor in the same options object: `onAllReady`. Both can hold the same line:

```jsx title="pipe in onShellReady, and pipe in onAllReady"
~onShellReady~() { pipe(response); } // Sends the product at once, and the reviews two seconds later
~onAllReady~() { pipe(response); } // Sends nothing for two seconds, then the whole page at once
```

After two seconds, both pages show the same product and the same reviews. **It may look the same at the end, but it is NOT the same thing!** The difference is what the user sees during those two seconds: the product with a loading line, or a blank tab.

React's docs describe `onAllReady` as "A callback that fires when all rendering is complete, including both the shell and all additional content." Then they give its cost: "If you start streaming here, you won't get any progressive loading."

**Progressive loading** is React's name for what streaming gives the user: the shell first, and each slower part as soon as it is ready.

### The Visitor Who Wants to Wait: the Crawler

One visitor does want to wait: a **crawler**, the program a search engine sends to read pages. A crawler reads the HTML once. It should find both reviews in it, not `Loading reviews...`. React's docs: "when a crawler visits your page ... you might want to let all of the content load first and then produce the final HTML output instead of revealing it progressively."

So the server file keeps both callbacks, and each one checks who is asking:

```jsx title="server.js" startLine="5"
app.use('/', (request, response) => {
  const ~isCrawler~ = request.headers['user-agent']?.includes('Googlebot'); // Our code decides who is a crawler
  const { pipe } = renderToPipeableStream(<App reviewsPromise={getReviews()} />, {
    bootstrapScripts: ['/main.js'],
    onShellReady() {
      if (!isCrawler) { // A shopper gets the shell at once
        response.setHeader('content-type', 'text/html');
        pipe(response);
      }
    },
    ~onAllReady~() { // React calls this when the reviews are rendered too
      if (isCrawler) {
        response.setHeader('content-type', 'text/html');
        pipe(response);
      }
    }
  });
});
```

`isCrawler` comes from our code, not from React. React's docs leave the test open: it "depends on your bot detection strategy". Here we read the request's `User-Agent` header, which names the program that sent the request, and look for Google's crawler. Your app may test it another way.

For the same request, React calls `onShellReady` first and `onAllReady` later. Each callback checks `isCrawler`, so `pipe` runs exactly once.

### Two Requests in the Same Second

**The crawler and the shopper ask for the same page, and get it on two different schedules.** In order:
1. A crawler requests the product page, and `isCrawler` is `true`.
2. React renders the shell and calls `onShellReady`. Our code skips `pipe`, so nothing is sent.
3. Two seconds later, the reviews are ready, and React calls `onAllReady`.
4. Our code calls `pipe(response)`. The crawler gets the final HTML, with `Great fit` and `Runs small` in their place.
5. A shopper requests the same page in the same second. `isCrawler` is `false`, so the shopper gets the shell at once, as in Principle 1.

```tree caption="The same product page sent to a shopper with onShellReady and to a crawler with onAllReady."
One page, two schedules
- +A shopper [`onShellReady`] | Gets **the product at once** | The reviews arrive **two seconds later** in the same response
- +A crawler [`onAllReady`] | Gets **nothing for two seconds** | Then gets **the final HTML**, with both reviews in place
```

### The Same Wait on Web Streams

On Web Streams, the stream itself carries the wait. Its `allReady` property is, in the words of React's docs, "A Promise that resolves when all rendering is complete". So the Web Streams handler awaits it for crawlers, before it returns the `Response`:

```jsx title="handler.js"
async function handler(request) {
  const isCrawler = request.headers.get('user-agent')?.includes('Googlebot');
  const stream = await renderToReadableStream(<App reviewsPromise={getReviews()} />, {
    bootstrapScripts: ['/main.js'],
  });
  if (isCrawler) {
    await ~stream.allReady~; // The crawler waits until the reviews are rendered too
  }
  return new Response(stream, {
    headers: { 'content-type': 'text/html' },
  });
}
```

`onAllReady` on Node.js and `await stream.allReady` on Web Streams: **yes, it is the exact same thing**, in the two shapes of Principle 3.

Waiting has a cost for the crawler too. React's docs: "the crawler will have to wait for *all* data, some of which might be slow to load or error. Depending on your app, you could choose to send the shell to the crawlers too."

### Real Beginner Mistake: `onAllReady` for Every Visitor

1. A developer reads that `onAllReady` gives "the final HTML", and moves `pipe(response)` there for every request.
2. The page looks complete in every test.
3. Every shopper now stares at a blank tab for two seconds, as if the page had no `<Suspense>` at all.
4. No error appears anywhere. React's docs had warned: "If you start streaming here, you won't get any progressive loading."

Remember: the server's job is to connect the stream at the right moment. For a shopper, that moment is the shell. For a crawler, it is the last part.

### The Complete Code

Here is the whole product page once more, file by file. The database file plays the part of the database (as seen in Lesson 109):

```js title="src/db.js"
export function getReviews() {
  return new Promise(resolve => {

  });
```

`Reviews` reads the reviews with `use` (as seen in Lesson 117):

```jsx title="src/Reviews.jsx"

export default function Reviews({ reviewsPromise }) {
  const reviews = ~use(reviewsPromise)~; // Suspends until the reviews arrive

    <ul>
      {reviews.map(review => <li key={review}>{review}</li>)}
    </ul>
```

`App` renders the whole document:

```jsx title="src/App.jsx"
import { Suspense, useState } from 'react';
import Reviews from './Reviews.jsx';

export default function App({ reviewsPromise }) {
  const [count, setCount] = useState(0);
  return (

      <head>
        <title>Blue Sneakers</title>
      </head>
      <body>
        <h1>Blue Sneakers</h1>

        <button onClick={() => setCount(count + 1)}>Add to cart</button>
        <p>Cart: {count}</p>
        <Suspense fallback={<p>Loading reviews...</p>}>
          <Reviews reviewsPromise={reviewsPromise} />
        </Suspense>
      </body>

  );
}
```

The server file streams the page on Node.js:

```jsx title="server.js"

import App from './src/App.jsx';
import { getReviews } from './src/db.js';
```

### What React Does for One Shopper's Visit

On the server, React calls `App` first, then `Reviews` inside the boundary. `Reviews` suspends on `use`, so React puts the fallback in its place, and the shell is ready. Two seconds later, React calls `Reviews` again, now with the reviews. In the browser, the bootstrap script calls `hydrateRoot`, and React runs `App` there too, so the button answers clicks.

```tree dir=right caption="The order of events for one shopper's visit, from the server to the browser."
One shopper opens the product page
- +1. On the server, React calls `App`, then `Reviews` | `Reviews` **suspends** on `use` | React puts **`Loading reviews...`** in its place
- +2. The shell is ready [`onShellReady`] | Our code calls **`pipe`** | The browser shows **the product** at once
- +3. Two seconds later, React calls `Reviews` again | The reviews are **rendered** | React writes them into **the same response**
- +4. In the browser, the bootstrap script runs [`hydrateRoot`] | React **runs `App`** in the browser | **`Add to cart`** answers the click
```

### Summary

| Aspect | The Mistake | The React Rule |
| :--- | :--- | :--- |
| **1. What the API returns** | Expect HTML from `renderToPipeableStream`, or keep `renderToString` with `<Suspense>` and stop at the loading line | Take `pipe` from what it returns, and call `pipe(response)` in `onShellReady` |
| **2. The script** | Leave out `bootstrapScripts`, so the page looks finished and ignores every click | Name the script that calls `hydrateRoot(document, ...)` in `bootstrapScripts` |
| **3. The runtime** | Pick the API by its name, and run the Web Streams API on Node.js | `renderToPipeableStream` on Node.js; `await renderToReadableStream` and a `Response` on Deno and edge runtimes |
| **4. The wait** | Call `pipe` in `onAllReady` for every visitor, and lose progressive loading | Wait with `onAllReady` or `await stream.allReady` only for crawlers |

Remember the one sentence of this lesson. **A streaming API gives the server no HTML. It gives a stream, and the server's job is to connect that stream to the response at the right moment.**

## For the Interview

> **The Interview Question:** How do you stream HTML on the server with renderToPipeableStream or renderToReadableStream?

### How to Answer Clearly in 30 Seconds

"Neither API returns HTML. Each one gives the server a stream, and the server connects it to the response. On Node.js, `renderToPipeableStream` returns `pipe` and `abort`. I call `pipe(response)` inside `onShellReady`, so the shell goes out at once, and each slower `<Suspense>` part follows in the same response. On Deno or an edge runtime, I `await renderToReadableStream`, which resolves when the shell is ready, and return the stream inside a `Response`. Three options matter most:
1. **`bootstrapScripts`** names the script that calls `hydrateRoot(document, ...)`. Without it, the page streams in but never answers clicks.
2. **`onShellReady`**, or the end of the `await`, is when regular visitors start to receive the page.
3. **`onAllReady`**, or `await stream.allReady`, waits for every part. I use it only for crawlers and for static generation, where the HTML is made ahead of time, because it gives up progressive loading."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What does `renderToPipeableStream` return, and why do you call `pipe` in `onShellReady` instead of right away?"**
   It returns an object with two functions, `pipe` and `abort`, and no HTML. `onShellReady` fires right after the shell has been rendered, so that is the first moment React has a whole page to show. React's docs: "Call `pipe` in `onShellReady` if you want to enable streaming." It is also the last moment to set the status code and the headers, because once the stream starts, the server can no longer change them. Lesson 125 covers the status code.
2. **"Which options control the scripts?"**
   `bootstrapScripts` takes a list of URLs, and React adds a `<script>` tag for each one to the stream. `bootstrapModules` does the same with `<script type="module">` tags. `bootstrapScriptContent` puts one string into an inline `<script>` tag. The bootstrap script must call `hydrateRoot` on the whole `document`, because the root component renders `<html>` itself. React also adds the doctype line, so our code writes neither the doctype nor the script tags.
3. **"What if a slow part never arrives, and the user waits forever?"**
   The server can stop the wait. On Node.js, it calls `abort()`. On Web Streams, it passes the `signal` of an `AbortController`. React's docs: "React will flush the remaining loading fallbacks as HTML, and will attempt to render the rest on the client." The docs' own example stops after 10000 milliseconds.

```tree dir=right caption="Interview summary: the two streaming APIs, the script option, and the two moments to start the stream."
How the server streams a React page
- +Node.js [`renderToPipeableStream`] | Returns **`pipe` and `abort`** | Call **`pipe`** inside **`onShellReady`**
- +Deno or an edge runtime [`renderToReadableStream`] | Resolves **when the shell is ready** | Return the stream inside a **`Response`**
- +The script [`bootstrapScripts`] | React adds the **`<script>` that calls `hydrateRoot`** | Without it, **no click works**
- !The wait [`onAllReady` `stream.allReady`] | Sends **only the final HTML** | **Crawlers only**, or every shopper sees a blank tab
```
