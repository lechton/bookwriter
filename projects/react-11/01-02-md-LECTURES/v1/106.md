# Lecture 106: What `'use client'` Does to a File and to Everything It Imports

*(Why does one line at the top of one file decide what every reader downloads?)*

> INTERVIEW QUESTION | ❱ CORE | What does the 'use client' directive do, and where does the client boundary sit?

---

## VS | `'use client'` on the Article File vs. `'use client'` on the Button File: the same screen, only the first sends `marked` to every reader

> Every `import` line pulls another file into yours, and the bundler follows those lines to decide what the browser downloads. **`'use client'` at the top of a file marks that file, and every file it imports, as client code: code that the browser downloads and runs**. So the line belongs on the smallest file that needs state or a tap, because everything under it travels to every reader's phone.

Remember how imports work in plain JavaScript? You write one `import` line, and the bundler follows it into the next file. Then it follows the imports of that file, and so on, down to the bottom. Every file it reaches goes into the bundle, the JavaScript file the browser downloads (Lesson 46).

```js title="main.js: plain JavaScript, built for the browser"
import { showPost } from ~'./post.js'~; // You import one file of your own
```

```js title="post.js"
import { ~marked~ } from 'marked'; // post.js imports marked, so marked joins the bundle too

export function showPost(text) {
  document.querySelector('article').innerHTML = marked(text);
}
```

The main file never imports `marked`. It is in the bundle anyway, because the chain of imports reaches it. One import line decides what comes along below it.

An app with Server Components follows the same chain of imports. In such an app, every file is server code by default: it runs before the page is sent, and the browser never downloads it (Lesson 101). The line `'use client'` changes that for one file. It tells the bundler: "From this file down the chain of imports, everything is client code."

```jsx title="ReadMore.jsx: a button that opens the text of an article"
~'use client';~ // This file, and every file it imports, goes to the browser
import { useState } from 'react';
```

So here is the one sentence to keep in mind for this whole lesson:

**`'use client'` marks its file and every file below it in the imports as client code. The line belongs on the smallest file that needs state or a tap.**

> [!DEFINITION]
> **Server Component and Client Component.** [REVIEW] A Server Component runs before the page is sent, and the browser receives only what it rendered, never its code. In an app with Server Components, every component is a Server Component by default. A Client Component is a component whose code is sent to the browser and runs there, so it can use `useState` and `onClick`. Its file starts with `'use client'` (Lesson 101).

> [!DEFINITION]
> **Directive.** [REVIEW] A directive is a plain string at the very top of a file, such as `'use client'`, that gives an instruction to the bundler. JavaScript itself does nothing with it (Lesson 101).

> [!DEFINITION]
> **Client code.** [NEW] Client code is the name react.dev gives to code that "is sent to and run by the client", and the client is the browser. A file marked with `'use client'` is client code, and so is every file it imports. All other code is server code, and the browser never downloads it (Lesson 106).

### The Same Screen, Two Downloads

Open a news article on your phone. The page shows a title, `Park Opens Today`, and a `Read more` button under it.

```page width=text caption="The article page when the user opens it: a title and a Read more button."
heading: Park Opens Today
line: [Read more]
```

The user taps `Read more`. The text of the article opens under the button, and the button now reads `Show less`.

```page width=text caption="The same page after one tap: the button reads Show less, and the text is open."
heading: Park Opens Today
line: [Show less]
line: The park opens at noon. | good
```

This small page has two parts that need very different things:
1. **The text.** It comes from a Markdown file, and the library `marked` turns it into HTML. The text is the same for every reader, so a Server Component formats it, and `marked` stays off the phone (Lesson 101).
2. **The button.** It must remember whether the text is open, and it must answer taps. That needs `useState` and `onClick`. So the file of the button needs `'use client'` (Lesson 101).

Two files of our own could hold the line:
- `Article.jsx` renders the title, formats the text with `marked`, and places the button.
- `ReadMore.jsx` holds the button and its `useState`.

Put `'use client'` on either file, and the screen is the same: the title, the button, and the text after a tap. **It looks the same, and it works the same at first, but it is NOT the same thing!** The difference is in what every reader downloads:
- **With the line on `Article.jsx`**, the article file is client code. So is `marked`, because the article file imports it. So is the button file. Every reader downloads all three.
- **With the line on `ReadMore.jsx`**, only the button file is client code. The article file and `marked` stay on the server.

```tree caption="The same page with use client on the article file or on the button file: the screen is the same, and the download is not."
Where the `'use client'` line stands on the article page
- !On `Article.jsx` [`'use client'` above the title and the text] | `Article.jsx`, **`marked`**, and `ReadMore.jsx` are client code | Every reader **downloads `marked`** to format a text that is the same for all
- +On `ReadMore.jsx` only [`'use client'` above the button] | **Only `ReadMore.jsx`** is client code | `Article.jsx` and `marked` **stay on the server**
```

### The Boundary Is an Import, Not a Tag

The place where server code meets client code is called the **boundary**. It sits at one import line: the line where a server file imports the marked file. So the boundary lives in the tree of imports, not in the tree of tags on the screen.

> [!DEFINITION]
> **The render tree and the module dependency tree.** [REVIEW] The render tree shows which component renders which, through the tags in your JSX. The module dependency tree shows which file imports which, through your `import` lines. The two trees often look alike, but they answer different questions (Lesson 06).

Keep this in mind for the whole lesson: **the imports decide where code runs, not the place of a component on the screen.**

### What the Wrong Place Costs

What is at stake is what every reader downloads, and nobody sees it on the screen:
1. **The download.** With the line one file too high, every reader downloads `marked` and the article code, only to show a text that is the same for everyone. react.dev gives `marked` a size of 35.9 kilobytes, or 11.2 kilobytes once compressed for download.
2. **The wait.** react.dev says it plainly: "Large bundle sizes are expensive for a client to download and run. Large bundle sizes can delay the time for your UI to get drawn."
3. **The silence.** The screen looks the same either way. The mistake shows up only when someone looks inside the bundle.

### The Rule of Thumb: which is the smallest file that needs state or a tap?

**Before you write `'use client'`, ask one question: which is the smallest file that needs state or a tap? Put the line there, and nowhere above it.**

On a real page, that question leads to one of three places:
1. **On the whole page file, here `Article.jsx`.** This fits only when all of the file answers the user, as a counter does. Our article does not: only the button answers taps.
2. **On the small interactive file only, here `ReadMore.jsx`.** The article passes the text into it as `children`. react.dev builds its own notes page the same way: the page stays a Server Component, and only a small file around each note is marked.
3. **On a small file of your own, between a Server Component and an older library.** Some older libraries ship a component that uses state but has no `'use client'` line of its own. react.dev suggests adding "your own Client Component file in between".

The third place takes three lines. Your file carries the line, and the library becomes client code because your file imports it:

```jsx title="src/Carousel.jsx: your own file around an older library"
~'use client';~ // Marks your file, so the library it imports is client code too
import { Carousel } from 'acme-carousel';

export default Carousel;
```

```tree caption="Three places to put the use client line, and the page each one fits."
Three places for `'use client'`
- !On the whole page file [`Article.jsx`] | Fits only when **all of the file** answers the user | On our page it sends **`marked` to every reader**
- +On the small interactive file [`ReadMore.jsx`] | Fits **one small interactive part** around shared content | The article and `marked` **stay on the server**
- +On a small file of your own around a library [`Carousel.jsx`] | Fits an **older library** with no line of its own | The library **becomes client code** through your file
```

A senior developer also knows the four classic mistakes:
1. **Treating `'use client'` as a mark on one component.** It marks a whole file, and every file that file imports.
2. **Putting the line on a big file to silence one `useState` error.** Everything that file imports moves to the browser with it.
3. **Thinking that everything shown inside a Client Component is client code.** Only the files that the marked file imports become client code. JSX that another file passes in as `children` is not imported by the marked file.
4. **Reading `'use client'` as "this code never runs on the server".** react.dev defines the line by what is sent: client code "is sent to and run by the client". Whether a framework also turns Client Components into the first HTML on the server is a separate step, server-side rendering (Lesson 102).

The rest of the lesson shows each one on the real article page.

## SECTION | The News Article with a Read more Button

Our page has one Markdown file and three components:

```files title="news: the article page" caption="The article page: the text in Markdown, two Server Components, and one Client Component."
post.md | content | The text of the article, written in Markdown
src/
  ArticlePage.jsx | Server Component | Reads `post.md` with `readFile` and renders `Article`
  Article.jsx | Server Component | Renders the title, formats the text with `marked`, and wraps it in `ReadMore`
  ReadMore.jsx | Client Component | Starts with `'use client'` and shows its `children` only when open
```

```md title="post.md"
The park opens at **noon**.
```

`ArticlePage` is an async Server Component (Lesson 101). It reads the Markdown file and hands the text to `Article` as a prop:

```jsx title="src/ArticlePage.jsx" startLine="1"
import { readFile } from 'node:fs/promises';
import Article from './Article';

export default async function ArticlePage() {
  const text = await readFile('post.md', 'utf8');
  return <Article ~text={text}~ />; // Hands the Markdown text to Article as a prop
}
```

This file stays the same through the whole lesson. The principles look at the two files under it, and at where the line stands in them.

Again, the one sentence of this lesson: **`'use client'` marks its file and every file below it in the imports as client code. The line belongs on the smallest file that needs state or a tap.**

**PRINCIPLES:** Where the `'use client'` line stands on the article page gives us three rules:
1. **Principle 1: `'use client'` on line 1 makes the file client code.** The import of that file from a Server Component is the boundary.
2. **Principle 2: `'use client'` on `Article.jsx` sends every file it imports to the browser.** `marked` goes too, with no line of its own. The higher the line stands, the more every reader downloads.
3. **Principle 3: JSX passed as `children` stays on the server.** The boundary follows the imports, not the tags. A Server Component that places JSX between the tags of a Client Component still renders that JSX on the server.

## PRINCIPLE | `'use client'` on line 1: the file becomes client code, and the import that reaches it is the boundary

> [!PRINCIPLE]
> **Principle 1: `'use client'`: The Line on Line 1 Sends the File to the Browser**
>
> *Write `'use client'` at the very top of a file, above every import, in single or double quotes; it marks the file as client code, and the import of that file from a Server Component is the boundary.*
>
> A button needs `useState`, and a Server Component cannot use it. `'use client'` solves this, but it is not a Hook and not a setting inside the component. It is a plain string that the bundler reads before anything else in the file. When a Server Component imports the marked file, the server leaves the code of that file alone, and the browser downloads it and completes the render.
>
> **DO THIS:**
> ```jsx
> ~'use client';~ // Line 1: ReadMore.jsx is client code
> import { useState } from 'react';
>
> export default function ReadMore({ children }) {
>   const [open, setOpen] = useState(false);
>   return <button onClick={() => setOpen(!open)}>Read more</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import { useState } from 'react';
> ~'use client';~ // **WRONG:** under an import, the line does not mark the file, so ReadMore cannot use useState
>
> export default function ReadMore({ children }) {
>   const [open, setOpen] = useState(false);
>   return <button onClick={() => setOpen(!open)}>Read more</button>;
> }
> ```

### One String on Line 1

Here is the button file. You have written everything in it before (as seen in Lessons 09 to 12), except line 1:

```jsx title="src/ReadMore.jsx" startLine="1"
~'use client';~ // Marks this file as client code: its code goes to the browser

import { useState } from 'react';

export default function ReadMore({ children }) {
  const [open, setOpen] = useState(false);
  return (
    <>
      <button onClick={() => setOpen(!open)}>
        {open ? 'Show less' : 'Read more'}
      </button>
      {open && children}
    </>
  );
}
```

Line 1 is a plain string, and JavaScript does nothing with it. Nothing stores it, nothing returns it, and nothing passes it anywhere. The **bundler** reads it, before anything else in the file. As react.dev puts it, "Directives provide instructions to bundlers compatible with React Server Components." In practice, that bundler comes with a framework, such as Next.js App Router (Lesson 46).

Compare it with a Hook. `useState` is a function call inside your component, and React runs it during the render. `'use client'` sits outside every component, above the imports. It speaks to the bundler, which runs long before any component does. So it is not a setting inside the component. **It is a mark on the whole file.**

### Where the Boundary Sits

Here is the line in `Article.jsx` that reaches the button file:

```jsx title="src/Article.jsx" startLine="2"
import ~ReadMore~ from './ReadMore'; // A server file imports a marked file: this import is the boundary
```

**This import is the boundary: the place where server code meets client code.** Why? Well, `Article.jsx` has no directive, so it is server code, and the file it imports is marked. react.dev puts it this way. When such a file is imported from a Server Component, compatible bundlers "will treat the module import as a boundary between server-run and client-run code."

The interview question calls this place the client boundary. react.dev calls it the server-client boundary. Both names mean this same import.

```tree dir=right caption="The import tree of the article page: the boundary sits at the import from Article.jsx into the marked ReadMore.jsx."
The imports of the article page
- +`ArticlePage.jsx` [Server Component] | Imports `Article.jsx` | **Server code**
- +`Article.jsx` [Server Component] | Imports `marked` and **`ReadMore.jsx`** | **Server code**
- The boundary [`import ReadMore`] | A server file imports a **marked file** | From here down, **client code**
- +`ReadMore.jsx` [`'use client'`] | Imports only `react` | **Client code**, sent to the browser
```

### What the Server Does with `ReadMore`

**The server renders the article, and leaves the code of `ReadMore` to the browser.** When the browser runs the code of a file, react.dev says the file is **evaluated** on the client. Here is the order:
1. The framework calls `ArticlePage` on the server. `ArticlePage` reads the Markdown file.
2. The framework calls `Article` on the server. `marked` turns the text into HTML.
3. The framework reaches `<ReadMore>`. The button file is client code, so the framework does not run it here. react.dev describes this as "opting-out of evaluating any code imported from client-marked code".
4. The browser downloads the button file with the bundle. In the words of react.dev, "The client, with its client code downloaded, then completes rendering the rest of the tree." The `Read more` button appears, and every tap opens or closes the text.

Whether the framework also turns `ReadMore` into the first HTML of the page is server-side rendering, a separate step (Lesson 102).

### VS | `'use client'` on Line 1 vs. `'use client'` Under an Import: only line 1 marks the file

The line works only from the very top of the file:

```jsx title="'use client' on line 1"
~'use client';~ // The file is marked: ReadMore is a Client Component
import { useState } from 'react';
```

```jsx title="'use client' under an import"
import { useState } from 'react';
~'use client';~ // **WRONG:** below an import, the file is not marked
```

**It looks the same, but it is NOT the same thing!** The words are the same, and only the first one marks the file. react.dev says the line "must be at the very beginning of a file, above any imports or other code". Under an import, it is a string that does nothing.

Developers really fall into this. Out of habit, they start the file with its imports and paste the line below them. The file is no longer marked, so `ReadMore` is a Server Component again. A Server Component cannot use `useState`, so the framework reports an error instead of showing the page. The fix is to move the line above every import.

The quotes matter too:

```jsx title="Three ways to write the line"
~'use client';~ // Single quotes: marks the file
~"use client";~ // Double quotes: marks the file too
~`use client`;~ // **WRONG:** backticks: the file is not marked
```

Single quotes and double quotes: yes, it is the exact same thing! react.dev uses both forms on its own pages. Backticks are NOT the same thing: react.dev says the line "must be written with single or double quotes, but not backticks". Only one thing may come before the line, a comment. react.dev says "comments are OK".

### Our Article Page: `Article.jsx` Wraps the Text in `ReadMore`

Here is the whole article file, with the text placed between the `<ReadMore>` tags:

```jsx title="src/Article.jsx" startLine="1" good="2,8"
import { marked } from 'marked';
import ~ReadMore~ from './ReadMore'; // The boundary: ReadMore.jsx is client code

export default function Article({ text }) {
  return (
    <>
      <h1>Park Opens Today</h1>
      <ReadMore>
        <div dangerouslySetInnerHTML={{ __html: marked(text) }} />
      </ReadMore>
    </>
  );
}
```

The Markdown file comes from the site's own author, so the HTML that `marked` makes from it is trusted. That is why `dangerouslySetInnerHTML` is safe here (Lesson 48).

The page now works as the opening showed. The user sees the title and the `Read more` button, and one tap opens the text.

## PRINCIPLE | `'use client'` on `Article.jsx`: every file it imports goes to the browser, `marked` included

> [!PRINCIPLE]
> **Principle 2: Transitive Dependencies: Everything a Marked File Imports Is Client Code**
>
> *Everything a `'use client'` file imports, and everything those files import in turn, is client code too, whether or not it has its own `'use client'`; so put the line on the smallest file that needs it.*
>
> The line marks a subtree, not one component. Moving it up one file moves every import of that file into the bundle, even libraries that know nothing about React. The screen stays the same, so only the bundle shows the cost.
>
> **DO THIS:**
> ```jsx
> import { marked } from 'marked';
> import ~ReadMore~ from './ReadMore'; // Only ReadMore.jsx carries 'use client'
>
> export default function Article({ text }) {
>   return <ReadMore><div dangerouslySetInnerHTML={{ __html: marked(text) }} /></ReadMore>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~'use client';~ // **WRONG:** Article.jsx and marked now go to every reader's browser
> import { marked } from 'marked';
> import ReadMore from './ReadMore';
>
> export default function Article({ text }) {
>   return <ReadMore><div dangerouslySetInnerHTML={{ __html: marked(text) }} /></ReadMore>;
> }
> ```

### The Same Page, with the Line One File Higher

Here is the top of the article file, with one line added above the imports:

```jsx title="src/Article.jsx" startLine="1" bad="1"
~'use client';~ // Marks Article.jsx, and everything it imports, as client code
import { marked } from 'marked';
import ReadMore from './ReadMore';
```

The button file keeps its own `'use client'` line. No other file changes. The page shows `Park Opens Today`, and the `Read more` button opens the text, exactly as before.

**Beware! One line moved up one file, and the browser now downloads three files instead of one.** The screen gives no sign of it. Here is what the bundler does, step by step down the chain of imports:
1. `ArticlePage.jsx` imports `Article.jsx`. The page file is server code, and the article file is now marked. So this import is the new boundary.
2. `Article.jsx` is client code, because of its own line.
3. The article file imports `marked`. `marked` knows nothing about React, and it has no `'use client'` line. It is client code anyway, because a client file imports it.
4. The article file imports `ReadMore.jsx`, so the button file is client code too. Its own line still stands in the file, and it no longer does anything. react.dev says: "When a `'use client'` module is imported from another client-rendered module, the directive has no effect."
5. The bundle now holds the article file, `marked`, and the button file.

Remember the two plain JavaScript files from the start of the lesson? It is the same chain. In plain JavaScript, `marked` joined the bundle because the chain of imports reached it. Here, the chain starts at the marked article file and reaches `marked` in one step.

### Every File Below the Line

> [!DEFINITION]
> **Transitive dependencies.** [NEW] The transitive dependencies of a file are the files it imports, the files those files import, and so on to the bottom of the chain. Transitive means passing across: the mark passes from each file to the files it imports. react.dev: "Add `'use client'` at the top of a file to mark the module and its transitive dependencies as client code." The marked file and its transitive dependencies together form a subtree of the module dependency tree, "a subtree of Client modules" in the words of react.dev (Lesson 106).

Here is that subtree on our page, with the line on the article file:

```tree caption="The import tree with use client on Article.jsx: the boundary moves up, and the whole subtree under it is client code."
`ArticlePage.jsx` [Server Component] | Imports `Article.jsx`: **this import is now the boundary**
- !`Article.jsx` [`'use client'`] | **Client code** because of its own line
  - !`marked` [no directive] | **Client code** because `Article.jsx` imports it
  - !`ReadMore.jsx` [`'use client'`] | **Client code**; its own line now **has no effect**
```

### VS | `marked` with Its Own Line vs. `marked` Without One: it is client code either way

`marked` has no `'use client'` of its own, and that changes nothing. With the line or without it, a file that a client file imports is client code. Yes, it is the exact same thing! react.dev says such files "will also be evaluated on the client regardless of whether their modules contain a `'use client'` directive".

The subtree holds more than components. `marked` is a plain function, and it goes to the browser all the same. react.dev says: "Code that is marked for client evaluation is not limited to components. All code that is a part of the Client module sub-tree is sent to and run by the client."

| Where `'use client'` stands | Client code in the bundle | What the reader sees |
| :--- | :--- | :--- |
| **On `ReadMore.jsx` only** | `ReadMore.jsx` | `Park Opens Today` and a working `Read more` button |
| **On `Article.jsx`** | `Article.jsx`, `marked`, and `ReadMore.jsx` | The same title and the same working button |

### The Quick Fix That Moves the Line Up

**The quick fix for one `useState` error moves the whole article file into the bundle, and every library it imports with it** (Lesson 101). On the article page it goes like this:
1. A developer writes the open and closed state with `useState` directly inside the article file.
2. The framework reports an error about `useState` in a Server Component.
3. The developer adds `'use client'` at the top of the article file. The error is gone, and the button works.
4. The article file imports `marked`, so `marked` joins the bundle. Every reader downloads it to format a text that is the same for all of them.
5. On a real article page, the article file imports more than `marked`, such as a library that colors code samples. The same line pulls every one of them into the bundle.

The fix is the page of Principle 1. Keep the state in its own small file, mark only that file, and leave the line off the article file.

## PRINCIPLE | `children` from a Server Component: the JSX stays on the server, even between the tags of a Client Component

> [!PRINCIPLE]
> **Principle 3: The Module Dependency Tree: JSX Passed as `children` Stays on the Server**
>
> *The boundary is drawn on the module dependency tree, not on the render tree; JSX that a Server Component places between the tags of a Client Component is rendered on the server, because the client file never imports it.*
>
> On the screen, the text is a child of `ReadMore`. In the imports, `ReadMore.jsx` never reaches `marked` or the text. So `Article` formats the text on the server, and `ReadMore` only shows or hides the finished HTML.
>
> **DO THIS:**
> ```jsx
> <ReadMore>
>   <div dangerouslySetInnerHTML={{ __html: ~marked(text)~ }} /> {/* Article.jsx runs marked on the server */}
> </ReadMore>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> 'use client';
> import { ~marked~ } from 'marked'; // **WRONG:** imported by a client file, marked goes to every reader
>
> export default function ReadMore({ text }) {
>   return <div dangerouslySetInnerHTML={{ __html: marked(text) }} />;
> }
> ```

### The Text Sits Inside a Client Component

We take the line off the article file again. The button file keeps its own line, as in Principle 1. Here is the article file once more, with the call to `marked` highlighted:

```jsx title="src/Article.jsx" startLine="1"
import { marked } from 'marked';
import ReadMore from './ReadMore';

export default function Article({ text }) {
  return (
    <>
      <h1>Park Opens Today</h1>
      <ReadMore>
        <div dangerouslySetInnerHTML={{ __html: ~marked(text)~ }} /> {/* Runs on the server, inside Article */}
      </ReadMore>
    </>
  );
}
```

The text sits between the `<ReadMore>` tags, so on the screen it belongs to a Client Component. **Yet `Article` formats the text on the server, and `ReadMore` receives only the finished HTML.** Why? Well, the button file never imports `marked`, and never imports the text. Only the files that a marked file imports become client code.

You know this from plain JavaScript. When you pass a value to a function, the function receives the value. It does not receive the code that computed it:

```js title="Plain JavaScript: a function receives a value, not the code that made it"
const html = ~marked(text)~; // marked runs here, in this file
show(html); // show receives a finished string, and never sees marked
```

`children` works the same way. `Article` computes the finished HTML, and `ReadMore` receives it.

### Two Trees of the Same Page

The page has two trees (Lesson 06). They look alike, but they answer two different questions:

```tree caption="The render tree and the module dependency tree of the same article page: the text is a child of ReadMore in one, and nowhere under ReadMore.jsx in the other."
The same article page, drawn as two trees
- +Render tree: who renders whom [`ArticlePage` `Article` `ReadMore`] | `Article` places the text **between the `<ReadMore>` tags** | On the screen, the text is a **child of `ReadMore`**
- +Module dependency tree: who imports whom [`ArticlePage.jsx` `Article.jsx` `ReadMore.jsx`] | `Article.jsx` imports **`marked` and `ReadMore.jsx`** | `ReadMore.jsx` imports **only `react`**
```

**It looks the same, but it is NOT the same thing!** Where the text sits on the screen does not decide where its code runs. The imports decide. react.dev says: "Recall that `'use client'` defines the boundary between server and client code on the _module dependency tree_, not the render tree." And: "a parent-child render relationship between components does not guarantee the same render environment."

### How the Finished Text Reaches the Button

**The server finishes the text before the browser ever sees it.** Here is the order, from the server to the tap of the user:
1. `Article` runs on the server. It calls `marked` on the text and builds the `<div>` with the finished HTML.
2. `Article` places that finished HTML between the tags of the button component. So `ReadMore` receives it as `children` (Lesson 09).
3. `ReadMore` runs in the browser. It receives the finished `<div>`, and never sees `marked` or the Markdown.
4. When the user taps `Read more`, the button shows HTML that the server already produced. The browser never turns any Markdown into HTML.

react.dev builds its own notes page the same way: a Server Component wraps each note in a Client Component, `Expandable`. In the words of react.dev, "In the browser, the Client Components will see output of the Server Components passed as props."

After the tap, the Elements panel shows the finished HTML under the button:

```dom title="Elements panel" caption="The article page in the Elements panel after one tap: the div that Article finished on the server sits under the button."
<h1>Park Opens Today</h1>
<button>Show less</button>
+ <div> | note: Finished on the server by Article
+   <p>The park opens at <strong>noon</strong>.</p>
+ </div>
```

### VS | The Text Placed Between the Tags vs. `marked` Imported in `ReadMore.jsx`: only the first keeps `marked` on the server

A developer may want to keep all the code for the text in one place, the button file. So the article file passes the raw text to `ReadMore` as a prop, and the button file imports `marked` and formats the text itself. Compare that with our page:

```jsx title="Article.jsx places the finished text between the tags"
<ReadMore>
  <div dangerouslySetInnerHTML={{ __html: ~marked(text)~ }} /> {/* Runs in Article.jsx, on the server */}
</ReadMore>
```

```jsx title="ReadMore.jsx imports marked and formats the text"
'use client';
import { useState } from 'react';
import { ~marked~ } from 'marked'; // **WRONG:** a client file imports marked, so marked goes to the browser

export default function ReadMore({ text }) {
  const [open, setOpen] = useState(false);
  return (
    <>
      <button onClick={() => setOpen(!open)}>{open ? 'Show less' : 'Read more'}</button>
      {open && <div dangerouslySetInnerHTML={{ __html: marked(text) }} />}
    </>
  );
}
```

**It looks the same, but it is NOT the same thing!** Both pages show the same text after the tap. When the article file places the text between the tags, `marked` runs on the server, and `ReadMore` receives its output. When the button file imports `marked`, it is an import of a client file. So `marked` is client code again, and every reader downloads it. The fix is the one react.dev shows with `Expandable`. The formatting stays in the article file, and `ReadMore` receives the finished HTML as `children`.

### The order in which React calls the components

`ArticlePage` and `Article` run on the server. `ReadMore` runs in the browser of the reader:

```tree dir=right caption="The order in which the components of the article page run: ArticlePage and Article on the server, ReadMore in the browser."
How the article page reaches the reader
- +1. On the server [`ArticlePage`] | **Reads `post.md`** with `readFile` | Renders `Article` with the text
- +2. On the server [`Article`] | **Runs `marked`** on the text | Places the finished `<div>` **between the `<ReadMore>` tags**
- +3. In the browser [`ReadMore`] | Of our files, the bundle holds **only `ReadMore.jsx`** | React **completes the render**, and every tap opens or closes the text
```

### Summary

| Aspect | The Common Habit | The React Rule |
| :--- | :--- | :--- |
| **What the line marks** | Treats `'use client'` as a setting on one component | It marks the whole file and every file the file imports |
| **Where the line goes** | Pastes it under the imports, or writes it in backticks | Line 1, above every import, in single or double quotes; only comments may come first |
| **Where the boundary sits** | Looks for it in the tags on the screen | At the import of a marked file from a Server Component, on the module dependency tree |
| **Which file gets the line** | Marks the big file that first reported a `useState` error | Marks the smallest file that needs state or a tap |
| **Content inside a Client Component** | Thinks it runs in the browser too | JSX passed in as `children` is rendered by the Server Component that wrote it |

Remember the one sentence of this lesson. **`'use client'` marks its file and every file below it in the imports as client code. The line belongs on the smallest file that needs state or a tap.**

## For the Interview

> **The Interview Question:** What does the 'use client' directive do, and where does the client boundary sit?

### How to Answer Clearly in 30 Seconds

"`'use client'` is a directive: a plain string at the very top of a file, above every import, that the bundler reads. It marks that file and all of its transitive dependencies as client code. Those are the files it imports, the files those import, and so on. Client code is sent to the browser and run there, even files with no directive of their own, and even code that is not a component. The client boundary, which react.dev calls the server-client boundary, sits at the import of a `'use client'` file from a Server Component. It lives on the module dependency tree, not on the render tree. So JSX that a Server Component passes into a Client Component as `children` is still rendered on the server. I put the line on the smallest file that needs state or event handlers. On a page file, it would move everything that file imports into the bundle."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does a file need `'use client'` to run in the browser?"**
   - No. A file without the line is client code when a client file imports it, as `marked` is when `Article.jsx` is marked. react.dev says: "a component can still be evaluated on the client even if it does not have a `'use client'` directive." And a second `'use client'` below the first one in the import tree changes nothing: "the directive has no effect" there.

2. **"Where exactly does the client boundary sit, and what about a Server Component rendered inside a Client Component?"**
   - At each import of a `'use client'` file from server code, on the module dependency tree. A Server Component can still appear inside a Client Component on the screen, when another Server Component passes it in as `children`. That works because the client file never imports it. react.dev says: "a parent-child render relationship between components does not guarantee the same render environment."

3. **"When must a file be client code, and where should the line go?"**
   - When it uses state or event handlers, browser APIs such as a `canvas`, or a third-party component that needs the browser. Put the line on the smallest such file, so the files above it stay on the server. For an older library with no line of its own, add a small file of your own with `'use client'` between that library and your Server Component.

```tree dir=right caption="Interview comparison: what use client marks, and where the boundary sits."
`'use client'` in an interview
- +What it marks [`'use client'` on line 1] | The **file** and **every file it imports**, all the way down | Sent to **the browser** and run there
- +Where the boundary sits [`import ReadMore`] | At the **import** of a marked file from a **Server Component** | On the **module dependency tree**, not the render tree
- !What it does not mark [`children` from a Server Component] | JSX a Server Component **places between the tags** | Rendered **on the server**; the client file never imports it
```
