## VS | A Plain `handleDelete` vs. `handleDelete` in `useCallback`: the same code, but only one stays the same function

> In JavaScript, two functions with the same code are still two different functions, and a component creates all its functions again every time React renders it. **So a child wrapped in `memo` receives a different function on every keystroke, and renders again, even though nothing it shows has changed.** Wrap the function in `useCallback`, and React hands back the same function until a value it reads changes, so the memoized child can skip its render.

Remember Lesson 55? We wrapped each message row of a chat in `memo`, so React skips the row while its props stay the same. That works for a string like `text`. It breaks for a function like `onDelete`. Why? Because of one plain JavaScript fact.

Open the Console and try this:

```js title="Two functions with the same code"
const a = () => console.log('Hi');
const b = () => console.log('Hi');

console.log(~a === b~); // false: the same code, but two different functions
console.log(~a === a~); // true: the very same function
```

A function is an object. Every time JavaScript runs the line that writes a function, it creates a new function object. The code inside can be the same, letter for letter. It is still a new function.

Now think about a component. React calls the component function again on every render, so every line in its body runs again. A function written in the body is written again, so it is a new function on every render. And `memo` compares each prop with the last one by `Object.is`, which works like `===` here. A new function never passes that check.

So we need a way to tell React: "Give me back the same function as last time, unless something changed." That is exactly what `useCallback` does. **`useCallback` hands back the same function between renders, until a dependency changes.** Keep this sentence in mind. The whole lesson is about the word "same", as in Lessons 55 and 56.

> [!DEFINITION]
> **memo.** [REVIEW] `memo` is a function React provides. It wraps a component and returns a memoized component. When the parent renders again, React compares each prop with its old value by `Object.is`, and skips the memoized component while every prop is the same. A new function on every render counts as a changed prop (Lesson 55).

> [!DEFINITION]
> **StrictMode calls every component twice.** [REVIEW] Our project mounts `<App />` inside `<StrictMode>`. In development, StrictMode calls every component function twice on purpose, so every `console.log` inside a component prints two lines. In production, each component is called once (Lesson 47).

### The Smallest Chat with useCallback

Here is the smallest chat that shows it: one message with a Delete button, and one `<input>` field to type a reply. `Message` is wrapped in `memo`, and it logs a line each time React calls it:

```jsx title="A memoized Message and a plain handleDelete"
const Message = memo(function Message({ id, text, onDelete }) {
  console.log('Message rendered:', text);
  return (
    <li>
      {text} <button onClick={() => onDelete(id)}>Delete</button>
    </li>
  );
});

function ChatRoom() {
  const [messages, setMessages] = useState([{ id: 1, text: 'Hi!' }]);
  const [text, setText] = useState('');

  function ~handleDelete~(id) { // A brand-new function every time ChatRoom runs
    setMessages(messages.filter(m => m.id !== id));
  }

  return (
    <>
      <ul>
        {messages.map(m => (
          <Message key={m.id} id={m.id} text={m.text} onDelete={handleDelete} />
        ))}
      </ul>
      <input value={text} onChange={e => setText(e.target.value)} />
    </>
  );
}
```

When the page opens, the Console shows two lines. That is StrictMode calling `Message` twice:

```page width=text caption="The smallest chat when the page opens: one message with a Delete button, an empty field, and two lines in the Console."
line: Hi! [Delete]
form:
  field:  |
log: Message rendered: Hi!
log: Message rendered: Hi!
```

We clear the Console, and the user types `OK` in the field:

```page width=text caption="The same chat after the user types OK: the message renders again on every keystroke, though its text never changed."
line: Hi! [Delete]
form:
  field:  | OK
log: Message rendered: Hi!
log: Message rendered: Hi!
log: Message rendered: Hi!
log: Message rendered: Hi!
```

**The message renders again on every keystroke, even though it is wrapped in `memo`.** Two lines for `O`, two lines for `K`. The text is still `Hi!`. Here is why, step by step:
1. The user types `O`. `setText` changes the state, and React calls `ChatRoom` again.
2. The body of `ChatRoom` runs again, so `function handleDelete` creates a new function.
3. `memo` compares the new `onDelete` with the old one. Two different functions, so the prop changed.
4. React calls `Message`.

Now we change one thing. We wrap `handleDelete` in `useCallback`, a Hook React provides. We give it two things: our function, and the list of values our function reads:

```jsx title="The same handleDelete, wrapped in useCallback"
const handleDelete = ~useCallback~((id) => { // The same function on every render until messages changes
  setMessages(messages.filter(m => m.id !== id));
}, [messages]);
```

We clear the Console again, and the user types `OK` again:

```page width=text caption="The chat with useCallback after the user types OK: the Console stays empty, because the message skips both keystrokes."
line: Hi! [Delete]
form:
  field:  | OK
quiet: No new lines after the user types OK
```

No `Message rendered:` line. Typing does not touch `messages`, so `useCallback` hands back the same `handleDelete`. `memo` finds the same three props as last time, and React skips the row.

**It may look the same, or work the same at first, but it is NOT the same thing!** Both versions hold the same code. Both remove `Hi!` when the user clicks Delete. The difference is which function `Message` receives after a keystroke:
- **The plain `handleDelete`** is a new function every time `ChatRoom` runs, so `memo` sees a changed `onDelete`.
- **The `handleDelete` from `useCallback`** is the same function on every render while `messages` stays the same, so `memo` sees the same props.

```tree caption="The plain handleDelete and the handleDelete from useCallback hold the same code, but only one stays the same function after a keystroke."
Two ways to write `handleDelete` for a memoized `Message`
- !A plain function [`function handleDelete`] | `ChatRoom` creates a **new function** on every render | `memo` sees a **changed `onDelete`** and **renders `Message` again**
- +Wrapped in `useCallback` [`useCallback`] | React hands back the **same function** while `messages` stays the same | `memo` sees **the same props** and **skips `Message`**
```

### Why It Is Called useCallback

A callback is a function you hand to other code, so that code can call it later. `onDelete` is a callback: `ChatRoom` hands it to `Message`, and `Message` calls it when the user clicks Delete. `useCallback` is the Hook that keeps such a function the same between renders. React's docs describe its job in one line: it lets you "cache a function definition between re-renders".

### What the User Feels

The user feels this in the field while typing. In a long chat, or with rows that are slow to render, every keystroke makes React render every row again, and the letters appear late in the field. React's docs show the same lag with a slow shipping form, and they name the cause: "there is no `useCallback` call in this version". With `useCallback`, and with the cached function passed to the row as it is, the rows skip the keystroke, and the field keeps up with the user.

### The Rule of Thumb: ask who compares the function

**`useCallback` matters only where React compares the function with the one from the last render: a prop of a component wrapped in `memo`, or the dependency list of an Effect or another Hook.** Everywhere else, the same function and a new function do exactly the same job.

A senior developer knows the four classic mistakes with `useCallback`:
1. **Wrapping every function**, also the ones passed to a plain `<button>`. The code gets harder to read, and the page is no faster.
2. **Keeping an arrow function on the child's tag**, such as `onDelete={() => handleDelete(m.id)}`. The row still gets a new function on every render.
3. **Thinking `useCallback` stops the function from being created.** It does not. JavaScript still creates a new function on every render, and React hands back the stored one instead.
4. **Leaving a value out of the dependency list** to keep the function the same. The function then keeps reading an old value, and the page shows old data.

When a memoized child receives a function from its parent, there are five ways to handle it:
1. **Leave it, and measure first** with `<Profiler>` (as seen in Lesson 54). This fits when the user feels no lag. The docs: "If your interactions are fast enough, you don't need memoization."
2. **Declare the function outside the component.** This fits a function that uses nothing from the component, so it never changes.
3. **Wrap the function in `useCallback`, and the child in `memo`.** This fits a function that needs props or state and goes to a slow child. This lesson covers it.
4. **Pass JSX as `children`, or keep the fast-changing state lower in the tree.** This makes much of the memoization unnecessary. Lesson 58 covers it.
5. **Turn on React Compiler.** It memoizes functions at build time, and `useCallback` stays for the places where you need exact control. Lesson 63 covers it.

```tree caption="Five ways to handle a function passed to a memoized child."
A memoized child receives a function from its parent
- +1. Leave it and measure [`<Profiler>`] | Fits when the user feels **no lag** | Lesson 54
- +2. Declare it outside the component | Fits a function that **uses nothing** from the component | It **never changes**
- +3. `useCallback` with `memo` [`useCallback`] | Fits a function that needs **props or state** | This lesson
- +4. Pass `children` or move state lower | Much memoization becomes **unnecessary** | Lesson 58
- +5. React Compiler | Memoizes functions **at build time** | Lesson 63
```

**PRINCIPLES:** `useCallback` does one small thing: it hands back the same function between renders until a dependency changes. Four principles follow:
1. **Principle 1: useCallback Hands Back the Same Function Until a Dependency Changes.** On the first render, React stores our function and returns it without calling it. On later renders, React returns the stored function while every dependency stays the same, so a child wrapped in `memo` can skip its render.
2. **Principle 2: An Arrow Function on the Tag Undoes useCallback.** A function written on the child's tag is new on every render, even when it only calls the cached function. Pass the cached function itself, and give the child its `id` as a prop.
3. **Principle 3: List Every Value the Function Reads, or Stop Reading It.** A value left out of the list stays old inside the function. When the function reads state only to calculate the next state, an updater function takes that state out of the list.
4. **Principle 4: Use useCallback Only Where React Compares the Function.** A function passed to a plain `<button>`, or to a child without `memo`, gains nothing.

## PRINCIPLE | `useCallback`: React hands back the same function until a dependency changes

> [!PRINCIPLE]
> **Principle 1: useCallback: React Hands Back the Same Function Until a Dependency Changes**
>
> *Wrap a function passed to a component wrapped in `memo` in `useCallback`, so React hands back the same function while every dependency stays the same.*
>
> Every render of the parent creates a new function, so a memoized child sees a changed prop and renders again. `useCallback` stores the function from the first render and hands it back on later renders while the dependencies are the same by `Object.is`. The child then receives the same function and skips its render. `useCallback` never calls the function, and it does not stop JavaScript from creating a new one.
>
> **DO THIS:**
> ```jsx
> const handleDelete = ~useCallback~((id) => { // The same function while messages stays the same
>   setMessages(messages.filter(m => m.id !== id));
> }, [messages]);
>
> <Message id={m.id} text={m.text} onDelete={handleDelete} />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ~handleDelete~(id) { // **WRONG:** a new function on every render, so the memoized Message renders on every keystroke
>   setMessages(messages.filter(m => m.id !== id));
> }
>
> <Message id={m.id} text={m.text} onDelete={handleDelete} />
> ```

### The Two Arguments of useCallback

A `useCallback` line takes two arguments and gives back one function:

```jsx title="The two things we hand to useCallback"
const handleDelete = useCallback(~(id) => {~ // 1. Our function: React may hand it back later
  setMessages(messages.filter(m => m.id !== id));
}, ~[messages]~); // 2. The dependency list: every value our function reads
```

1. **Our function** is the first argument. React does not call it. Nothing calls `handleDelete` until the user clicks Delete.
2. **The dependency list** is the second argument. It holds every value our function reads, here `messages`. React compares each item with its value from the last render by `Object.is`.

### What useCallback Returns on Each Render

1. **On the first render**, React stores our function together with `[messages]`, and returns it.
2. **On every later render**, JavaScript creates a new arrow function, because the line runs again. Then React compares `messages` with the stored one:
   - When `messages` is the same array, React returns the stored function. The new arrow function is never used.
   - When `messages` is a new array, React returns the arrow function of this render, and stores it for next time.

```tree dir=right caption="What useCallback hands back on the first render and on every render after it."
What `useCallback` returns
- +1. First render | React **stores our function** with its dependency list | Returns it **without calling it**
- +2. Later render, the same dependencies | JavaScript creates a new function, and **React ignores it** | Returns the **stored function**
- !3. Later render, a changed dependency | React keeps the **function of this render** | Returns that **new function** and stores it
```

The second step surprises many developers. `useCallback` does not stop JavaScript from creating the function. It only decides which function you get back. The docs say it directly: "React ignores it and gives you back a cached function if nothing changed."

> [!DEFINITION]
> **useCallback and the cached function.** [NEW] `useCallback` is a Hook React provides: `useCallback(fn, dependencies)`. On the first render, it stores `fn` and returns it without calling it. On every later render, React compares each dependency with its value from the last render by `Object.is`. When all of them are the same, React returns the stored function, the cached function. When one changed, React returns the function of this render and stores it (Lesson 57).

### Why Message Skips a Keystroke

**After a keystroke, React does not call `Message`, because every prop it receives is the same as on the last render.** Here is what happens when the user types `O`:
1. The field calls `setText('O')`, and React renders `ChatRoom` again.
2. `ChatRoom` runs `useCallback` again, and JavaScript creates a new arrow function.
3. React compares `messages` with the stored one. Typing did not touch `messages`, so it is the same array, and React hands back the stored `handleDelete`.
4. For each `Message`, `memo` compares `id`, `text`, and `onDelete` with the last ones. All three are the same.
5. React does not call `Message`, and no `Message rendered:` line appears.

The click still works as before. When the user clicks Delete on `Hi!`, the row calls `onDelete(1)`, and the message disappears.

### VS | `useCallback(fn)` vs. `useMemo(() => fn)`: the exact same cached function

In Lesson 56, `useMemo` cached the result of a calculation. A function is also a value, so `useMemo` can cache a function too, when its calculation returns one:

```jsx title="useCallback with our function"
const handleDelete = ~useCallback~((id) => { // Caches the function we pass, without calling it
  setMessages(messages.filter(m => m.id !== id));
}, [messages]);
```

```jsx title="useMemo whose calculation returns our function"
const handleDelete = ~useMemo~(() => (id) => { // Calls the outer arrow and caches the function it returns
  setMessages(messages.filter(m => m.id !== id));
}, [messages]);
```

**Yes, it is the exact same thing!** `useMemo` calls the outer arrow function and caches what it returns, and here it returns our function. `useCallback` skips that outer arrow and caches our function directly. React's docs show a simplified version of `useCallback` inside React, and it is one line: `return useMemo(() => fn, dependencies);`. In the docs' words: "The only benefit to `useCallback` is that it lets you avoid writing an extra nested function inside. It doesn't do anything else."

```tree caption="useCallback, and useMemo with a function inside, give the same cached function."
Two ways to cache `handleDelete`
- +`useCallback` with our function [`useCallback`] | Caches **the function we pass** | Hands back the **same `handleDelete`** while `messages` stays the same
- +`useMemo` with an arrow that returns our function [`useMemo`] | Caches **the result of calling the outer arrow**, which is our function | **Exact same result**, with one extra arrow to write
```

### useCallback in Our Chat Room

Now the code moves into our project, one component per file. `Message` gets its own file:

```jsx title="src/components/Message.jsx"
import { memo } from 'react';

const Message = ~memo~(function Message({ id, text, onDelete }) { // Skips the render when id, text, and onDelete are the same
  console.log('Message rendered:', text);
  return (
    <li>
      {text} <button onClick={() => onDelete(id)}>Delete</button>
    </li>
  );
});

export default Message;
```

`ChatRoom` holds the three messages, the field, and the Send button:

```jsx title="src/components/ChatRoom.jsx"
import { useCallback, useState } from 'react';
import Message from './Message.jsx';

const initialMessages = [
  { id: 1, text: 'Hi!' },
  { id: 2, text: 'Lunch at 12?' },
  { id: 3, text: 'Sure' },
];
let nextId = 4;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);
  const [text, setText] = useState('');
  console.log('ChatRoom rendered');

  const handleDelete = ~useCallback~((id) => { // The same function on every render while messages stays the same
    setMessages(messages.filter(m => m.id !== id));
  }, [messages]);

  function handleSend() {
    setMessages([...messages, { id: nextId++, text }]);
    setText('');
  }

  return (
    <section>
      <ul>
        {messages.map(m => (
          <Message key={m.id} id={m.id} text={m.text} ~onDelete={handleDelete}~ /> // Every row gets the one cached function
        ))}
      </ul>
      <input value={text} onChange={e => setText(e.target.value)} />
      <button onClick={handleSend}>Send</button>
    </section>
  );
}
```

We clear the Console, and the user types `OK`:

```page width=text caption="Our chat room after the user types OK: only ChatRoom renders, and the three messages skip both keystrokes."
line: Hi! [Delete]
line: Lunch at 12? [Delete]
line: Sure [Delete]
form:
  field:  | OK
  button: Send
log: ChatRoom rendered
log: ChatRoom rendered
log: ChatRoom rendered
log: ChatRoom rendered
```

`ChatRoom` renders twice for each letter, because of StrictMode. Not one `Message` renders. With the plain `handleDelete`, the same two keystrokes would print twelve `Message rendered:` lines: three rows, two letters, and each line twice.

### The Real Mistake: useCallback Without memo

**Without `memo` on `Message`, every row still renders on every keystroke, even though `handleDelete` comes from `useCallback`.** A developer reads that `useCallback` stops re-renders, wraps `handleDelete`, and forgets `memo` on `Message`:
1. The user types a letter, and `ChatRoom` renders again.
2. `useCallback` hands back the same `handleDelete`, exactly as before.
3. Nobody compares it. A child renders again whenever its parent renders, whatever its props are (as seen in Lesson 54).
4. Every row renders on every keystroke, and the developer decides that `useCallback` does not work.

`useCallback` only keeps the function the same. Something must compare it with the last one for that to matter, and here that something is `memo`.

### The Cache Is Only a Speed-Up

React may throw a cached function away. It does so in development when you edit the component's file, and when a component suspends during its first mount. To suspend means to pause rendering while waiting for data, which Lesson 69 covers. So `useCallback` is only a performance optimization. The docs: "If your code doesn't work without it, find the underlying problem and fix it first." When a value must truly survive every render, use a state variable or a ref (as seen in Lesson 30).

## PRINCIPLE | `onDelete={() => handleDelete(m.id)}`: a new arrow function on every render undoes `useCallback`

> [!PRINCIPLE]
> **Principle 2: Pass the Cached Function Itself: an Arrow Function on the Tag Is New on Every Render**
>
> *Pass the function from `useCallback` itself to the memoized child, and give the child the value it needs, such as `id`, as its own prop.*
>
> The prop is whatever is written after the equals sign on the child's tag. An arrow function written there is new on every render, even when it only calls the cached function, so `memo` sees a changed prop and the child renders again. Passing the cached function keeps the prop the same, and the child calls it with its own `id`.
>
> **DO THIS:**
> ```jsx
> <Message key={m.id} id={m.id} text={m.text} ~onDelete={handleDelete}~ /> {/* The same cached function on every render */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Message key={m.id} text={m.text} ~onDelete={() => handleDelete(m.id)}~ /> {/* **WRONG:** a new arrow function on every render, so every row renders again */}
> ```

### VS | An Arrow Function on the Tag vs. the Cached Function on the Tag: both delete the right message, only one stays the same

In Lesson 55, `Message` took no `id`. Its button called `onDelete` directly, and each tag carried an arrow function that passed the row's `id` to `handleDelete`. Since the start of this lesson, our code passes `id` as its own prop instead. Here is the old tag above the new one. In both, `handleDelete` comes from `useCallback`:

```jsx title="An arrow function on the tag vs. the cached function on the tag"
<Message key={m.id} text={m.text} ~onDelete={() => handleDelete(m.id)}~ /> {/* A new arrow function on every render */}
<Message key={m.id} id={m.id} text={m.text} ~onDelete={handleDelete}~ /> {/* The one cached function, the same on every render */}
```

**It may look the same, or work the same at first, but it is NOT the same thing!** Both tags delete the right message. But the prop `onDelete` is whatever we write after the equals sign. On the first tag, that is a new arrow function, written again on every render. It only calls the cached function. It is not the cached function itself.

### Why Every Row Still Renders

**With an arrow function on the tag, every row renders again after every keystroke, even though `handleDelete` comes from `useCallback`.** Here is what happens when the user types `O`:
1. The field calls `setText('O')`, and React renders `ChatRoom` again.
2. `useCallback` hands back the same `handleDelete`, because `messages` did not change.
3. `map` runs again, and JavaScript creates a new arrow function for each `Message` tag.
4. For each row, `memo` compares the new `onDelete` with the old one by `Object.is`. Two different functions, so the prop changed.
5. React calls `Message` for every row.

```page width=text caption="With an arrow function on the tag, the user types O and all three messages render again."

line: Lunch at 12? [Delete]
line: Sure [Delete]
form:
  field:  | O
  button: Send
```

The Console looks exactly as it did before we added `useCallback`. React's docs call this mistake "a subtle bug that breaks memoization": "Even though `handleClick` is wrapped in `useCallback`, the arrow function `() => handleClick(item)` creates a new function every time the component renders."

### Where the id Goes Instead

How does the arrow function on the tag know `m.id`? It remembers `m` from the `map` call that created it.

> [!DEFINITION]
> **A closure.** [NEW] A closure is a function that remembers the variables of the place where it was created. In `messages.map(m => <Message onDelete={() => handleDelete(m.id)} />)`, each arrow function on the tag remembers its own `m`, so the first one deletes `Hi!` and the second one deletes `Lunch at 12?`. Closure is a JavaScript word, not a React word (Lesson 57).

The fix moves the `id` out of that closure and into a prop. `ChatRoom` writes `id={m.id}` on the tag, and `Message` calls `onDelete(id)` itself. Now the parent can hand every row the same function:

```jsx title="src/components/Message.jsx" startLine="7"
      {text} <button onClick={~() => onDelete(id)~}>Delete</button> {/* An arrow function on a plain button: nothing compares it */}
```

This line still has an arrow function, and it is new on every render of `Message`. That costs nothing here, because it sits on a plain `<button>`, and no `memo` compares it. Principle 4 shows why.

### Why Not Call useCallback for Each Row Inside map?

A developer who wants one cached function per row may try to call `useCallback` inside `map`. That breaks the rule that Hooks run only at the top level of a component (as seen in Lesson 38). The docs: "You can't call `useCallback` in a loop like this." Their fix is the one we used: give each item its own component, and pass it the value it needs as a prop. React Compiler also handles this case "with or without the arrow function" (as seen in Lesson 63).

```tree caption="An arrow function on the Message tag vs. the cached function with the id as its own prop."
Two ways to pass `handleDelete` to each `Message`
- !An arrow function written on the tag | A **new arrow function** on every render of `ChatRoom` | `memo` sees a **changed `onDelete`**, and **every row renders**
- +The cached function and the `id` [`onDelete={handleDelete}` `id={m.id}`] | Every row gets **the one cached function** | `Message` calls `onDelete` with its own `id`, and **the rows skip the keystroke**
```

## PRINCIPLE | Dependencies of `useCallback`: list every value the function reads, or stop reading it

> [!PRINCIPLE]
> **Principle 3: Dependencies: List Every Value the Function Reads, or Stop Reading It**
>
> *List in the dependencies every value the function reads; when it reads state only to calculate the next state, use an updater function and drop that state from the list.*
>
> The dependency list tells React when to hand back a new function. Removing a value the function still reads keeps the function the same, but it keeps the old value too, so the page shows old data: a stale closure. To keep the function the same and correct, change the code so it no longer reads that value, as an updater function does for state.
>
> **DO THIS:**
> ```jsx
> const handleDelete = useCallback((id) => {
>   setMessages(~ms => ms.filter(m => m.id !== id)~); // Reads the latest list, so the empty list tells the truth
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const handleDelete = useCallback((id) => {
>   setMessages(messages.filter(m => m.id !== id));
> }, ~[]~); // **WRONG:** keeps the first render's messages, so a deleted message comes back
> ```

### Three Dependency Lists for handleDelete

The dependency list tells React which values the function reads. When one of them changes, React hands back the new function. Developers write the list of `handleDelete` in three ways:

```jsx title="1. With messages in the dependency list"
const handleDelete = useCallback((id) => {
  setMessages(messages.filter(m => m.id !== id));
}, ~[messages]~); // A new handleDelete after every change of messages
```

```jsx title="2. With an empty list, still reading messages"
const handleDelete = useCallback((id) => {
  setMessages(messages.filter(m => m.id !== id));
}, ~[]~); // **WRONG:** the same function forever, holding the messages of the first render
```

```jsx title="3. With an empty list and an updater function"
const handleDelete = useCallback((id) => {
  setMessages(~ms => ms.filter(m => m.id !== id)~); // Reads the latest list from React, not messages
}, []);
```

What each one does:
1. **With `messages` in the list**, `handleDelete` is correct, but it changes after every Delete and every Send, because both give `messages` a new array.
2. **With an empty list, still reading `messages`**, `handleDelete` never changes, and it keeps deleting from an old list.
3. **With an empty list and an updater function**, `handleDelete` never changes, and it always deletes from the latest list.

### With messages in the List, Every Row Renders After Each Delete

**With `messages` in the list, every remaining row renders after each Delete.** The user clicks Delete on `Hi!`. `messages` becomes a new array, so on the next render `useCallback` sees a changed dependency and hands back a new `handleDelete`. `Lunch at 12?` and `Sure` receive a different `onDelete`, so React renders both. We cleared the Console before the click:

```page width=text caption="With messages in the list, the user clicks Delete on Hi! and both remaining messages render again."

log: Message rendered: Sure
```

The same happens after every Send. In a long chat, every row renders each time the user sends a message.

### With an Empty List, a Deleted Message Comes Back

A developer wants `handleDelete` to stay the same, so they remove `messages` from the list. The linter in the editor underlines the list at once (as seen in Lesson 32). Its warning starts like this:

> React Hook useCallback has a missing dependency: 'messages'. Either include it or remove the dependency array.

The warning then suggests an updater function for `setMessages`, the fix at the end of this principle. The developer ignores the warning, and the page breaks.

**Beware! With an empty list, `handleDelete` keeps the messages of the first render, so a message the user deleted comes back on the next Delete.** Here is what happens:
1. On the first render, `useCallback` stores `handleDelete`. Inside it, `messages` is the list of that render: `Hi!`, `Lunch at 12?`, and `Sure` (as seen in Lesson 15).
2. The user clicks Delete on `Hi!`. `handleDelete` filters `Hi!` out of that first list, and the page shows `Lunch at 12?` and `Sure`.
3. On the next render, the empty list gives React nothing to compare. It hands back the same `handleDelete`, which still holds the first list.
4. The user clicks Delete on `Sure`. `handleDelete` filters `Sure` out of the first list, and that list still holds `Hi!`.
5. `Hi!` comes back on the screen.

```page width=text caption="With an empty list, still reading messages: the page after the user deletes Hi!."

line: Sure [Delete]
form:
  field:  |
  button: Send
```

```page width=text caption="The same page after the user then deletes Sure: Hi! comes back."
line: Hi! [Delete] | bad
line: Lunch at 12? [Delete]
form:
  field:  |
  button: Send
```

A message the user deleted is back. The Console shows no error and no warning. Only the linter warned.

> [!DEFINITION]
> **A stale closure.** [NEW] A stale closure is a function that keeps reading the values of an old render. Stale means old, like bread left out for days. The function is a closure, so it remembers the `messages` of the render that created it, and with an empty dependency list React never hands back a newer one. React's docs describe it as a bug "where the hook uses outdated values" (Lesson 57).

Leaving out the whole list is a different mistake. With no list at all, `useCallback` hands back a new function on every render, so it does nothing.

### An Updater Function Takes messages Out of the List

The fix is to stop reading `messages` inside `handleDelete`. We pass `setMessages` an updater function instead (as seen in Lesson 16). React calls it with the latest list, which we name `ms`, and it returns the new list. The docs: "When you read some state only to calculate the next state, you can remove that dependency by passing an updater function instead."

Now `handleDelete` reads nothing that changes between renders. The `set` function from `useState` stays the same on every render, so it needs no place in the list either. The empty list now tells the truth, and the linter is quiet:

```jsx title="src/components/ChatRoom.jsx" startLine="16"
  const handleDelete = useCallback((id) => {
    setMessages(~ms => ms.filter(m => m.id !== id)~); // React passes the latest list as ms
  }, []);
```

The user deletes `Hi!`, then `Sure`. The page shows only `Lunch at 12?`, and no `Message rendered:` line appears, because the remaining row receives the same `onDelete`. Then the user types `OK` and clicks Send. We cleared the Console before the click:

```page width=text caption="With the updater function, the user clicks Send with OK: only the new message renders."
line: Lunch at 12? [Delete]
line: OK [Delete]
form:
  field:  |
  button: Send
log: ChatRoom rendered
log: ChatRoom rendered
log: Message rendered: OK
log: Message rendered: OK
```

Only the new row renders. `Lunch at 12?` keeps the same three props, so React skips it. The docs give the general advice: "You'll usually want memoized functions to have as few dependencies as possible."

```tree caption="Three dependency lists for handleDelete and what the user sees with each."
Three ways to write the dependency list of `handleDelete`
- !With `messages` in the list [`[messages]`] | **Correct**, but a **new function** after every Delete and Send | **Every remaining row renders** after each change
- !An empty list, still reading `messages` [`messages.filter`] | The **same function forever**, holding the **first render's list** | A **deleted message comes back**: a stale closure
- +An empty list and an updater function [`ms => ms.filter`] | The **same function forever**, reading the **latest list** from React | **Only the new row renders** after Send
```

## PRINCIPLE | `useCallback` on a plain `<button>`: nothing compares the function, so nothing gets faster

> [!PRINCIPLE]
> **Principle 4: Two Real Cases: Use useCallback Only Where React Compares the Function**
>
> *Use `useCallback` for a prop of a component wrapped in `memo`, or for a dependency of an Effect or another Hook; leave every other function plain.*
>
> `useCallback` changes only which function the next render receives. That matters only to code that compares it with the last one: `memo` on a child, or a dependency list. A function passed to a plain `<button>`, or to a child without `memo`, gains nothing, and the extra dependency list makes the code harder to read and easier to break.
>
> **DO THIS:**
> ```jsx
> function ~handleSend~() { // A plain function: the button compares nothing
>   setMessages([...messages, { id: nextId++, text }]);
>   setText('');
> }
>
> <button onClick={handleSend}>Send</button>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const handleSend = ~useCallback~(() => { // **WRONG:** nothing compares onClick on a button, so this gains nothing
>   setMessages([...messages, { id: nextId++, text }]);
>   setText('');
> }, [messages, text]);
>
> <button onClick={handleSend}>Send</button>
> ```

### VS | A Plain `handleSend` vs. `handleSend` in `useCallback`: the exact same page, with more code

So far, `useCallback` helped because `memo` compared `onDelete`. Now look at `handleSend`, which goes to a plain `<button>`:

```jsx title="A plain handleSend on the Send button"
function ~handleSend~() { // A new function on every render
  setMessages([...messages, { id: nextId++, text }]);
  setText('');
}

<button onClick={handleSend}>Send</button>
```

```jsx title="A handleSend from useCallback on the Send button"
const handleSend = ~useCallback~(() => { // The same function while messages and text stay the same
  setMessages([...messages, { id: nextId++, text }]);
  setText('');
}, [messages, text]);

<button onClick={handleSend}>Send</button>
```

**Yes, it is the exact same thing!** For the user and for the Console, both versions behave the same. The user clicks Send, the message appears, and the field clears. The Console prints the same lines. Why?
1. `<button>` is a built-in HTML element, not a component wrapped in `memo`. Nothing compares its `onClick` with the last one, so nothing can skip.
2. `text` changes on every keystroke, so the `handleSend` from `useCallback` is a new function after every letter anyway.

### The Two Places Where useCallback Matters

React's docs name exactly two cases where caching a function helps:
1. **"You pass it as a prop to a component wrapped in `memo`."** That is `onDelete` on `Message`, the case of Principles 1 to 3.
2. **"The function you're passing is later used as a dependency of some Hook."** For example, an Effect that lists a function in its dependency list.

For every other function, the docs give a clear verdict: "There is no benefit to wrapping a function in `useCallback` in other cases. There is no significant harm to doing that either, so some teams choose to not think about individual cases, and memoize as much as possible. The downside is that code becomes less readable."

The second case comes from the docs' own chat room. An Effect connects to a chat server and lists `createOptions` as a dependency:

```jsx title="A function used as a dependency of an Effect, from the React docs"
const createOptions = ~useCallback~(() => { // The same function while roomId stays the same
  return { serverUrl: 'https://localhost:1234', roomId: roomId };
}, [roomId]);

useEffect(() => {
  const options = createOptions();
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, ~[createOptions]~); // Runs again only when createOptions changes
```

Without `useCallback`, `createOptions` would be a new function on every render, and the Effect would disconnect from the chat server and connect again after every render (as seen in Lesson 35). `useCallback` fixes that. But the docs add: "it's even better to remove the need for a function dependency. Move your function *inside* the Effect" (as seen in Lesson 37).

```tree caption="Where useCallback helps: only where React compares the function with the one from the last render."
Where a cached function makes a difference
- +A prop of a component wrapped in `memo` [`onDelete={handleDelete}`] | `memo` **compares** the prop by `Object.is` | The same function lets the child **skip its render**
- +A dependency of an Effect or another Hook [`createOptions`] | React **compares** the dependency list | The same function stops the Effect from **running after every render**
- !A plain HTML element, or a child without `memo` [`<button onClick={handleSend}>`] | **Nothing compares** the function | **No gain**, and one more dependency list to keep correct
```

### The Real Mistake: Wrapping Every Handler

Wrapping every handler in `useCallback` makes no page faster. Here is how the habit grows in a real team:
1. A developer reads that `useCallback` stops re-renders.
2. They wrap `handleSend`, the field's `onChange`, and every other handler in `useCallback`.
3. Each wrapped handler now has a dependency list to keep correct, and some of those lists go stale, as Principle 3 showed.
4. The page renders exactly as often as before, because no memoized component and no dependency list compares these functions.

**Therefore, before you add `useCallback`, you need to pay attention and always ask: who compares this function with the last one?** When the answer is nobody, leave the function plain. When the page feels slow, measure first in production mode (as seen in Lesson 54).

### Where Else You Meet useCallback

Three more places come up in interviews:
1. **A custom Hook that returns functions.** The docs recommend wrapping each returned function in `useCallback`, so the components that use the Hook can optimize their own code when needed (as seen in Lesson 39).
2. **A context value that holds a function.** The function goes in `useCallback`, and the object in `useMemo` (as seen in Lesson 59).
3. **React Compiler.** It memoizes functions at build time. The docs recommend "relying on the compiler for memoization and using `useMemo`/`useCallback` where needed to achieve precise control" (as seen in Lesson 63).

```jsx title="src/components/ChatRoom.jsx"
import { useCallback, useState } from 'react';
import Message from './Message.jsx';

const initialMessages = [
  { id: 1, text: 'Hi!' },
  { id: 2, text: 'Lunch at 12?' },
  { id: 3, text: 'Sure' },
];
let nextId = 4;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);
  const [text, setText] = useState('');
  console.log('ChatRoom rendered');

  const handleDelete = ~useCallback~((id) => { // Principles 1 and 3: one cached function for the life of ChatRoom
    setMessages(ms => ms.filter(m => m.id !== id));
  }, []);

  function ~handleSend~() { // Principle 4: a plain function on a plain button
    setMessages([...messages, { id: nextId++, text }]);
    setText('');
  }

  return (
    <section>
      <ul>
        {messages.map(m => (
          <Message key={m.id} id={m.id} text={m.text} ~onDelete={handleDelete}~ /> // Principle 2: the cached function itself
        ))}
      </ul>
      <input value={text} onChange={e => setText(e.target.value)} />
      <button onClick={handleSend}>Send</button>
    </section>
  );
}
```

### What Runs After Each Action of the User

Lesson 55 ended with every row rendering after every action of the user. Here is the same chat room with the cached `handleDelete`:

| What the user does | `ChatRoom` | The rows, with the arrow function in `onDelete` | The rows, with the cached `handleDelete` |
| :--- | :--- | :--- | :--- |
| **Types a letter in the field** | Renders, because `text` changed | Every row renders, because `onDelete` is new | Every row is skipped |
| **Clicks `Send`** | Renders, because `messages` and `text` changed | Every row renders, the new one included | Only the new row renders |
| **Clicks `Delete` on one row** | Renders, because `messages` changed | Every remaining row renders | Every remaining row is skipped |

Here is the whole lesson in one table:

| Aspect | The Habit That Breaks It | The React Rule |
| :--- | :--- | :--- |
| **The function prop** | A plain `handleDelete`, new on every render, so the memoized row renders on every keystroke | Wrap it in `useCallback`, so the row receives the same function |
| **The tag** | `onDelete={() => handleDelete(m.id)}`, a new arrow function on every render | `onDelete={handleDelete}` and `id={m.id}`, so the row calls `onDelete(id)` itself |
| **The dependency list** | Remove `messages` from the list while still reading it, so a deleted message comes back | Use `ms => ms.filter(...)`, so the empty list tells the truth |
| **Where to use it** | Wrap every handler, also the ones on a plain `<button>` | Use it only for a prop of a `memo` child, or a dependency of an Effect or another Hook |

Remember the one sentence of this lesson. **`useCallback` hands back the same function between renders until a dependency changes, so it helps only where React compares that function with the last one: a `memo` child, or a dependency list.**

## For the Interview

> **The Interview Question:** What does useCallback do, and when do you actually need it?

### How to Answer Clearly in 30 Seconds

"`useCallback` caches a function definition between renders. On the first render, React stores the function we pass and returns it without calling it. On later renders, it returns the stored function while every dependency is the same by `Object.is`, and the new function when one changed. It does not stop the function from being created; React just ignores the new one. I need it in two cases:
1. **A function passed as a prop to a component wrapped in `memo`**, such as `onDelete` on a message row, so the row can skip its render. I pass the cached function itself, not an arrow function around it.
2. **A function used as a dependency of an Effect or another Hook**, though moving the function inside the Effect is often better.

Everywhere else, such as a handler on a plain `<button>`, it gains nothing and makes the code harder to read. And I list every value the function reads, or use an updater function, so I never get a stale closure."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What is the difference between `useCallback` and `useMemo`?"**
   `useMemo` calls its function and caches the result. `useCallback` caches the function itself, without calling it. Writing `useCallback(fn, deps)` is the exact same thing as writing `useMemo(() => fn, deps)`. React's docs show that line as a simplified version of `useCallback` inside React. The only benefit of `useCallback` is that you skip writing the extra arrow function.
2. **"I wrapped my handler in `useCallback`, and the memoized list items still render on every keystroke. Why?"**
   There are three common causes. First, the child may not be wrapped in `memo`, and then a child renders with its parent whatever its props are. Second, the tag may hold an arrow function around the cached function, such as `onClick={() => handleClick(item)}`, which is new on every render. Third, a dependency may change on every render, such as an object created in the component body. Log the dependencies to find the one that changes (as seen in Lesson 56).
3. **"Can you rely on `useCallback` to keep a function the same forever?"**
   No. It is only a performance optimization. React may throw the cached function away, for example when you edit the component's file in development, or when the component suspends during its first mount. If the code only works with `useCallback`, it has a bug to fix first. When a value must truly survive every render, use a state variable or a ref.

```tree dir=right caption="Interview summary: when useCallback helps and when it gains nothing."
When is `useCallback` worth adding?
- +A prop of a `memo` child [`onDelete={handleDelete}`] | The child receives the **same function** | `memo` **can skip** the child
- +A dependency of an Effect or another Hook [`createOptions`] | The dependency list sees **the same function** | The Effect **does not run again** after every render
- !A handler on a plain `<button>` [`handleSend`] | **Nothing compares** it | **No gain**, and the code is **harder to read**
- !An arrow function on the tag around the cached function [`onDelete`] | A **new function** on every render | `memo` **never skips**
```
