# Lecture 30: How useRef Keeps a Value Between Renders

*(How can a component remember a number without rendering again?)*

> INTERVIEW QUESTION | ❱ CORE | How do you keep a value between renders without triggering a re-render?

---

## VS | State `useState` vs. a Ref `useRef`: both remember the value, only state renders again

> **A ref lets a component remember a value between renders, without drawing the screen again.**

In React, **not all information needs to appear on screen**. A component often needs to track information behind the scenes that never appears on the screen, like a background timer, a previous input value, or an analytics counter. Normally, we plug values into `useState` so the component remembers them between renders, but every time its setter gets a new value, React renders the component again. You do not need that for hidden data. This is why we have `useRef`. It keeps a value between renders without re-rendering the component, so your code can save something now and read it in a later click.

Take a product card where the user can switch shirt colors and then click **Buy**. Suppose you want to count how many times the user clicked around before buying, and send that number when they finally click **Buy**. Ask yourself: does the user ever see this counter on the screen? No, only the shirt color changes visually. The counter lives quietly inside the product card component, and only the **Buy** button's click handler reads it at the end.

**Why:** A plain JavaScript variable like `let clicks = 0` does not work here. Its memory is lost, and it restarts with every new render. In other words, it goes back to zero all the time. We need the value to survive between renders, but we do not want `useState` to trigger a new render either. Using `useState` here is wasted work, because every click would force React to re-render the entire product card for a number nobody sees. `useRef` remembers the count across renders without triggering a single redraw.

### A Ref in Two Lines of Code

Here is a ref in two lines of code:

```jsx title="A ref"
const countRef = ~useRef(0)~; // countRef is the object { current: 0 }
~countRef.current = 5~; // Change it like any field of any object: no setter, no render
```

> [!DEFINITION]
> **What is a ref?** [NEW] A ref is an object with one field, `current`, that React keeps for your component between renders (Lesson 12). `useRef(0)` returns `{ current: 0 }`. You read and write `countRef.current` directly, with no setter, and changing `current` does NOT make React render again (Lesson 30).

The React docs say it in two lines: "Like state, refs are retained by React between re-renders. However, setting state re-renders a component. Changing a ref does not!"

### The smallest ref: a click counter

Here is a button that counts its clicks in a ref, and logs the count:

```jsx title="Counter.jsx"
import { useRef } from 'react';

export default function Counter() {
  const countRef = ~useRef(0)~; // The object { current: 0 }

  function handleClick() {
    ~countRef.current = countRef.current + 1~; // Changes the field, and React does not render
    console.log('You clicked ' + countRef.current + ' times');
  }

  return <button onClick={handleClick}>Click me</button>;
}
```

The user clicks three times:

```page width=text caption="After three clicks: the button is unchanged, and the Console shows every click."
line: [Click me]
log: You clicked 1 times | Counter.jsx:8
log: You clicked 2 times | Counter.jsx:8
log: You clicked 3 times | Counter.jsx:8
```

The ref remembered 1, then 2, then 3. The screen never changed, because nothing told React to render.

### The Rule of Thumb: is the value on the screen?

**Ask one question about every value: is it on the screen? If yes, use `useState`. If only your event handlers need it, use `useRef`.**

The docs say the same: "When a piece of information is used for rendering, keep it in state. When a piece of information is only needed by event handlers and changing it doesn't require a re-render, using a ref may be more efficient."

A senior developer also knows the three classic mistakes:
1. **A `let` inside the component.** It resets on every render (Lesson 13), so the value is gone after the next render.
2. **A `let` outside the component.** It survives renders, but every copy of the component shares that one variable.
3. **A ref in the JSX.** Changing a ref does not render, so the screen keeps showing the old value.

The rest of the lesson shows each mistake on a real stopwatch.

## SECTION | A Stopwatch with Start and Stop

Our page is a stopwatch: one line and two buttons.

```page width=text caption="The stopwatch when the page opens."
line: Seconds: 0
line: [Start] [Stop]
console: quiet
```

To count every second, the stopwatch uses a browser function:

```js title="Start a timer, stop a timer"
const id = ~setInterval(tick, 1000)~; // Calls tick every second, and returns a number: the interval ID
~clearInterval(id)~; // Stops the timer with that ID
```

> [!DEFINITION]
> **What is setInterval?** [NEW] `setInterval` is a browser function. It calls your function again and again, every N milliseconds. `setInterval(tick, 1000)` calls `tick` once a second.
> It returns a number, the interval ID. To stop the timer, you pass that number to `clearInterval`. Lose the number, and you can never stop that timer.
> Something that can be tricky: `clearInterval` with a wrong number, or with `null`, does nothing. No error. The timer keeps running.
> You know `setTimeout` from Lesson 15. It works the same way, but it calls your function only once (Lesson 30).

So the stopwatch has two values to remember:
1. **The seconds.** They are on the screen, so they go in state.
2. **The interval ID.** It is never on the screen. Only Start and Stop use it, so it goes in a ref.

Here is the working stopwatch:

```jsx title="src/Stopwatch.jsx"
import { useState, useRef } from 'react';

export default function Stopwatch() {
  const [seconds, setSeconds] = ~useState(0)~; // On the screen: state
  const intervalRef = ~useRef(null)~; // Not on the screen: a ref, starts as { current: null }

  function handleStart() {
    clearInterval(intervalRef.current);
    ~intervalRef.current = setInterval~(() => { // Stores the new interval ID in the ref
      setSeconds(s => s + 1);
    }, 1000);
  }

  function handleStop() {
    ~clearInterval(intervalRef.current)~; // Reads the same ID, many renders later
  }

  return (
    <section>
      <p>Seconds: {seconds}</p>
      <button onClick={handleStart}>Start</button>
      <button onClick={handleStop}>Stop</button>
    </section>
  );
}
```

The user clicks Start, waits three seconds, and clicks Stop. Ten seconds later:

```page width=text caption="Ten seconds after Stop: the line still says 3."
line: Seconds: 3 | good
line: [Start] [Stop]
console: quiet
```

It works. The timer calls the setter every second, so React renders the component every second. The ref keeps the ID through all those renders. When the user clicks Stop, the ID is still there.

One detail: the timer calls `setSeconds(s => s + 1)`, the updater function from Lesson 16. With `seconds + 1`, the timer would keep reading the 0 of the render where Start was clicked, and the line would stop at 1 (Lesson 15).

Now let's break it. Each principle moves the interval ID to another place and shows what goes wrong:

**PRINCIPLES:** `useState` remembers and renders again. `useRef` remembers and does NOT render again. Five principles follow:
1. **Principle 1: useRef Returns the Same Object on Every Render.** React uses the start value once. After that, it gives back the same object.
2. **Principle 2: A let Inside the Component Resets on Every Render.** Stop reads `null`, and the stopwatch keeps counting.
3. **Principle 3: Keep in State Only What the Screen Shows.** The ID in state works, but every change renders the component again for nothing.
4. **Principle 4: A let Outside the Component Is Shared.** Two stopwatches on one page stop each other.
5. **Principle 5: Never Read a Ref in the JSX.** The line stays at 0, because changing a ref does not render.

## PRINCIPLE | useRef: the value survives every render

> [!PRINCIPLE]
> **Principle 1: useRef Returns the Same Object on Every Render**
>
> *React uses the start value of useRef only on the first render. On every later render, it returns the same object, with whatever you stored in current.*
>
> The line with useRef runs on every render, like every other line, so it looks like it resets the ref. It does not. React creates the object once and keeps it for the component. And when you change current, the new value is there at once, on the very next line.
>
> **DO THIS:**
> ```jsx
> function handleStart() {
>   clearInterval(intervalRef.current);
>   ~intervalRef.current~ = setInterval(tick, 1000); // The old timer stops first, then the new ID is stored
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleStart() {
>   ~intervalRef.current~ = setInterval(tick, 1000); // **WRONG:** a second click loses the first ID, and that timer never stops
> }
> ```

Look at this line:

```jsx title="A line that runs on every render"
const intervalRef = ~useRef(null)~; // The null is used on the first render only
```

It runs on every render. So why does it not set the ref back to `null` each time? Because React does two different things:
1. **On the first render**, React creates the object `{ current: null }` and keeps it for this component.
2. **On every later render**, React returns that same object. The `null` is ignored.

The docs: "This argument is ignored after the initial render."

```tree dir=right caption="The same useRef line on the first render and on every later render."
The line `useRef` with the start value `null`
- +First render | React **creates** the object | `current` is `null`
- +Every later render | React **returns the same object** | `current` keeps **what you stored**
```

### current changes at once

State gives you a snapshot. After `setCount(5)`, the variable `count` keeps its old value until the next render (Lesson 15). A ref has no snapshot. It is a normal object, and you change its field right now:

```jsx title="Right after the setter, and right after changing current"
setCount(5);
console.log(~count~); // The old value: this render's snapshot
countRef.current = 5;
console.log(~countRef.current~); // 5: the field changed right away
```

### Why Start stops the old timer first

The first line of `handleStart` is `clearInterval(intervalRef.current)`. Without it, a double click on Start breaks the stopwatch:
1. The first click starts timer A. Its ID goes into `intervalRef.current`.
2. The second click starts timer B. Its ID replaces A's ID. A's ID is lost.
3. Both timers add 1 every second, so the line counts twice as fast.
4. The user clicks Stop. Only B stops. A keeps running, and no code has its ID anymore.

With that first line, Start always stops the old timer before it starts a new one. On the very first click, the ref still holds `null`, and `clearInterval(null)` does nothing, so that is safe too.

## PRINCIPLE | let inside a component: the value resets on every render

> [!PRINCIPLE]
> **Principle 2: A let Inside the Component Resets on Every Render**
>
> *A let variable inside the component is created again, as null, on every render. The ID from the Start click is gone before the Stop click reads it.*
>
> The timer calls the setter once a second, so React renders the component once a second. Each render runs the let line again and creates a new variable set to null. Stop reads that new null, clearInterval does nothing, and the stopwatch keeps counting with no error.
>
> **DO THIS:**
> ```jsx
> const intervalRef = ~useRef(null)~; // The same object on every render
> function handleStop() { clearInterval(intervalRef.current); }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> let ~intervalId = null~; // **WRONG:** a new null on every render, so Stop has no ID
> function handleStop() { clearInterval(intervalId); }
> ```

Most developers first try a plain variable, because that is what they do in JavaScript:

```jsx title="src/Stopwatch.jsx" bad="5,14"
import { useState } from 'react';

export default function Stopwatch() {
  const [seconds, setSeconds] = useState(0);
  let ~intervalId = null~; // **WRONG:** this line runs again on every render

  function handleStart() {
    intervalId = setInterval(() => {
      setSeconds(s => s + 1);
    }, 1000);
  }

  function handleStop() {
    clearInterval(~intervalId~); // **WRONG:** reads the new null, so nothing stops
  }

  return (
    <section>
      <p>Seconds: {seconds}</p>
      <button onClick={handleStart}>Start</button>
      <button onClick={handleStop}>Stop</button>
    </section>
  );
}
```

The user clicks Start, waits three seconds, and clicks Stop. Two seconds later:

```page width=text caption="Two seconds after Stop: the line went on from 3 to 5."
line: Seconds: 5 | bad
line: [Start] [Stop]
console: quiet
```

**The stopwatch ignores Stop, and the Console shows no error.** Here is what happens:
1. The user clicks Start. The ID goes into `intervalId`.
2. One second later, the timer calls `setSeconds`, and React renders the component again.
3. The new render runs `let intervalId = null` again. A new variable, set to `null`.
4. The new render also creates a new `handleStop`, and this one reads the new `null`.
5. The user clicks Stop. `clearInterval(null)` does nothing.

Something that can be tricky: if the user clicks Stop within the first second, it works. No render has happened yet, so Stop still reads the same variable. That is why a quick test can hide this bug.

The docs show the same bug in a chat app: an Undo button keeps its timeout ID in a `let`, and Undo cannot undo. Their fix is ours: "store it in a ref, which React will preserve between renders."

Remember: a `let` inside the component forgets. `useRef` remembers.

## PRINCIPLE | useState: every change renders again, so keep only what the screen shows

> [!PRINCIPLE]
> **Principle 3: Keep in State Only What the Screen Shows**
>
> *The interval ID in state works, but every new ID renders the component again, for a number that is not on the screen.*
>
> A setter always makes React render again. For seconds, that is the point: the screen must show the new number. For the interval ID, the render changes nothing on the screen. So the seconds go in state, and the ID goes in a ref.
>
> **DO THIS:**
> ```jsx
> const [seconds, setSeconds] = useState(0);
> const intervalRef = ~useRef(null)~; // Not on the screen, so changing it does not render
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [seconds, setSeconds] = useState(0);
> const [intervalId, setIntervalId] = ~useState(null)~; // **WRONG:** every new ID renders the component again for nothing
> ```

A developer who knows only state puts the ID in state. And it works: Stop stops. So what is wrong?

To see it, put one log at the top of the component, and clear the Console right before the user clicks Stop:

::: row caption="One click on Stop: the ID in state renders the component again, the ID in a ref does not."
::: col title="The ID in state" tag="Stop renders again" tone=bad
```page size=mini
line: Seconds: 3
line: [Start] [Stop]
log: Stopwatch rendered | Stopwatch.jsx:6
log: Stopwatch rendered | Stopwatch.jsx:6
```
```jsx title="Stopwatch.jsx" startLine="5" bad="1,5"
const [intervalId, setIntervalId] = useState(null);
console.log('Stopwatch rendered');
function handleStop() {
  clearInterval(intervalId);
  setIntervalId(null);
}
```
The setter makes React render, so the log prints.
:::
::: col title="The ID in a ref" tag="Stop does not render" tone=good
```page size=mini
line: Seconds: 3
line: [Start] [Stop]
quiet: No messages
```
```jsx title="Stopwatch.jsx" startLine="5" good="1,4"
const intervalRef = useRef(null);
console.log('Stopwatch rendered');
function handleStop() {
  clearInterval(intervalRef.current);
}
```
No setter, so no render, and the Console stays empty.
:::
:::

The screen is exactly the same in both. But with state, React ran the whole component again for a number nobody sees. The same happens on every click on Start. The log prints twice because Strict Mode calls the component twice in development (Lesson 14).

There is a second trap. Log the ID right after its setter, and you see `null`. The ID is not lost. You read this render's snapshot, as Principle 1 showed.

So how do you choose? The same question as always: **is it on the screen?**
- **`seconds`** is in the JSX. It goes in state.
- **The interval ID** is not in the JSX. Only the two handlers read it. It goes in a ref.

One component can use both, each for its own value. The docs: "You can combine refs and state in a single component."

## PRINCIPLE | useRef: each copy of the same component keeps its own separate value

> [!PRINCIPLE]
> **Principle 4: A let Outside the Component Is Shared**
>
> *A let at the top of the file survives every render, but every copy of the component uses that one variable. A ref belongs to one copy only.*
>
> Moving the let above the component fixes Principle 2, and one stopwatch works. Put two stopwatches on the page, and both store their ID in the same variable. A click on one of them stops the other.
>
> **DO THIS:**
> ```jsx
> export default function Stopwatch({ label }) {
>   const intervalRef = ~useRef(null)~; // Tea and Eggs each get their own ref
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> let ~intervalId = null~; // **WRONG:** Tea and Eggs share this one variable
> export default function Stopwatch({ label }) {}
> ```

A `let` at the top of the file runs once, when the file loads. No render creates it again. So with one stopwatch, Stop works:

```jsx title="src/Stopwatch.jsx" bad="3"
import { useState } from 'react';

let ~intervalId = null~; // **WRONG:** one variable for every stopwatch on the page

export default function Stopwatch({ label }) {
  const [seconds, setSeconds] = useState(0);

  function handleStart() {
    clearInterval(intervalId);
    intervalId = setInterval(() => {
      setSeconds(s => s + 1);
    }, 1000);
  }

  function handleStop() {
    clearInterval(intervalId);
  }
```

Now a kitchen needs two timers, one for the tea and one for the eggs. `App` renders two stopwatches:

```jsx title="src/App.jsx"
import Stopwatch from './Stopwatch.jsx';

export default function App() {
  return (
    <main>
      ~<Stopwatch label="Tea" />~ {/* The first copy of Stopwatch */}
      ~<Stopwatch label="Eggs" />~ {/* The second copy, with its own state */}
    </main>
  );
}
```

Each `<Stopwatch />` tag is its own copy of the component, with its own state. Each one shows its `label` as a heading. The user starts Tea, waits four seconds, then starts Eggs. Two seconds later:

```page width=text caption="Two seconds after Eggs started: Tea is stuck on 4, and only Eggs counts."
section: Tea
line: Seconds: 4 | bad
line: [Start] [Stop]
section: Eggs
line: Seconds: 2 | good
line: [Start] [Stop]
console: quiet
```

**The user never clicked Stop on Tea, and Tea stopped.** Here is why:
1. Start on Tea stores Tea's ID in `intervalId`.
2. Start on Eggs first calls `clearInterval(intervalId)`. That variable holds Tea's ID, so Tea stops.
3. Then Eggs stores its own ID in the same variable.
4. Now Stop on Tea would stop Eggs.

There is one variable for the whole file, and both copies use it.

A ref fixes this. React keeps a separate ref for each copy, the same way each copy has its own state (Lesson 12). Tea has its ref, Eggs has its ref. The docs: "The information is local to each copy of your component."

## PRINCIPLE | useRef: changing the value does not update the screen

> [!PRINCIPLE]
> **Principle 5: Never Read a Ref in the JSX**
>
> *A value on the screen must be state. Changing a ref does not render, so the screen keeps the old value.*
>
> The screen shows what the last render read. A ref changes without a render, so the JSX keeps showing the old number. Later, when something else renders the component, the number suddenly jumps. Read and change refs in event handlers, not in the JSX.
>
> **DO THIS:**
> ```jsx
> const [seconds, setSeconds] = useState(0);
> return <p>Seconds: ~{seconds}~</p>; // The setter renders again, so every new number shows
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const secondsRef = useRef(0);
> return <p>Seconds: ~{secondsRef.current}~</p>; // **WRONG:** nothing renders again, so it stays on 0
> ```

Once developers learn that a ref changes at once, some put the seconds in a ref too:

```jsx title="src/Stopwatch.jsx" startLine="5" bad="1,6,15"
const secondsRef = ~useRef(0)~; // **WRONG:** the value on the screen, in a ref

function handleStart() {
  clearInterval(intervalRef.current);
  intervalRef.current = setInterval(() => {
    ~secondsRef.current = secondsRef.current + 1~; // Changes the field, and React does not render
  }, 1000);
}

function handleStop() {
  clearInterval(intervalRef.current);
}

return (
  <p>Seconds: ~{secondsRef.current}~</p> // **WRONG:** read once, in the last render
);
```

The user clicks Start under Tea and waits six seconds:

```page width=text caption="Six seconds after Start: secondsRef.current is 6, and the screen still says 0."
section: Tea
line: Seconds: 0 | bad
line: [Start] [Stop]
section: Eggs
line: Seconds: 0
line: [Start] [Stop]
console: quiet
```

The timer runs, and `secondsRef.current` really is 6. But no line calls a setter, so React never renders, and the screen keeps the 0 of the first render. The docs: "React is not aware of when you change it because a ref is a plain JavaScript object."

Something that can be tricky: the line is not stuck forever. If any other click calls a setter, React renders, reads the ref, and the line jumps from 0 straight to 6. That is why this bug is hard to find.

The fix: put `seconds` back in state, as in our working stopwatch. Remember: on the screen means state.

> [!DEFINITION]
> **What does "during rendering" mean?** [NEW] During rendering means while React runs your component function: the lines in its body and the JSX it returns.
> An event handler is different. You write `handleStart` inside the component, but its code runs later, when the user clicks.
> So `{secondsRef.current}` in the JSX runs during rendering. `intervalRef.current = ...` inside `handleStart` does not.
> The docs give the rule: "Do not write or read `ref.current` during rendering, except for initialization." Why? React expects the same props and state to give the same JSX (Lesson 14). A ref can change without React knowing, so JSX that reads it can show a different result for the same state (Lesson 30).

### `useRef(null)`: create an expensive object only once

Sometimes the value in a ref is expensive to create, such as a video player object. Compare these two:

```jsx title="A new player on every render"
const playerRef = useRef(~new VideoPlayer()~); // Creates a player on every render, and React keeps only the first
```

```jsx title="A player created once"
const playerRef = useRef(null);
if (~playerRef.current === null~) { // True only on the first render
  playerRef.current = new VideoPlayer();
}
```

Both give you the right player. But the first one creates a new player on every render and throws it away, because the start value is ignored after the first render. The second one creates it once. The docs allow this one case, "because the result is always the same, and the condition only executes during initialization."

## All 5 Principles Together

### The complete files

`App` renders two stopwatches:

```jsx title="src/App.jsx"
import Stopwatch from './Stopwatch.jsx';

export default function App() {
  return (
    <main>
      ~<Stopwatch label="Tea" />~ {/* Principle 4: its own seconds and its own ref */}
      ~<Stopwatch label="Eggs" />~ {/* Principle 4: its own seconds and its own ref */}
    </main>
  );
}
```

`Stopwatch` keeps the seconds in state and the interval ID in a ref:

```jsx title="src/Stopwatch.jsx"
import { useState, useRef } from 'react';

export default function Stopwatch({ label }) {
  const [seconds, setSeconds] = ~useState(0)~; // Principles 3 and 5: on the screen, so state
  const intervalRef = ~useRef(null)~; // Principles 1, 2 and 4: not on the screen, one ref per copy

  function handleStart() {
    ~clearInterval(intervalRef.current)~; // Principle 1: stop the old timer first
    intervalRef.current = setInterval(() => {
      setSeconds(s => s + 1);
    }, 1000);
  }

  function handleStop() {
    ~clearInterval(intervalRef.current)~; // Principle 2: the same ID, many renders later
  }

  return (
    <section>
      <h2>{label}</h2>
      <p>Seconds: ~{seconds}~</p> {/* Principle 5: state in the JSX, never a ref */}
      <button onClick={handleStart}>Start</button>
      <button onClick={handleStop}>Stop</button>
    </section>
  );
}
```

The user starts Tea, waits five seconds, starts Eggs, waits three seconds, and stops Tea:

line: [Start] [Stop]
section: Eggs
line: Seconds: 3 | good
line: [Start] [Stop]
console: quiet

### Where the ID lives, and what the user sees

| Where the interval ID lives | What the user sees |
| :--- | :--- |
| **A `let` inside the component** | Stop does nothing |
| **State** | It works, but every new ID renders the component again |
| **A `let` outside the component** | Tea and Eggs stop each other |
| **A ref** | Each stopwatch starts and stops on its own |
| **The seconds in a ref** | The line stays at 0 |

```tree caption="Where a component can keep a value, and the job each place fits."
Where a component can keep a value
- !A let inside [`let intervalId`] | Created again **on every render** | Fits a value **calculated fresh** each render
- !A let outside [`let` at the top of the file] | Survives renders, **shared by every copy** | Fits a value that **never changes**
- +State [`useState`] | Remembers and **renders again** | Fits what **the screen shows**
- +A ref [`useRef`] | Remembers and **does not render**, one per copy | Fits what **only handlers need**
```

Remember the one sentence of this lesson. **`useRef` lets us keep a value between renders without redrawing the screen, so our code can save something now and still use it in another click later.**

## For the Interview

> **The Interview Question:** How do you keep a value between renders without triggering a re-render?

### How to Answer Clearly in 30 Seconds

"I use a ref. `useRef` returns a plain object with one field, `current`. React creates it on the first render and returns the same object on every render after that, so the value survives re-renders, like state. The difference: changing `ref.current` does not re-render, and the new value is there at once. The classic case is a stopwatch: the interval ID goes in a ref, so the Stop handler can pass it to `clearInterval` many renders later. Three rules:
1. **A `let` inside the component resets on every render**, and a `let` outside the component is shared by every copy, so neither can hold the ID.
2. **What the screen shows goes in state**. What only event handlers need, such as an interval ID or a timeout ID, goes in a ref.
3. **Never read or write `ref.current` during rendering**, except to fill an empty ref once. A value on the screen kept in a ref does not update."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"How is `useRef` different from `useState`? Could you build one from the other?"**
   Both keep a value between renders, one per copy of the component. The state setter makes React render again, and the new value comes with that render. A ref has no setter: you change `current` directly, the change is there at once, and React is not told. The docs show that `useRef` could be built with `useState`: a state variable that holds `{ current: initialValue }` and whose setter is never called. That is why they call a ref "a regular state variable without a setter."
2. **"Why not read `ref.current` during rendering? When is it allowed?"**
   React expects components to be pure: the same props and state give the same JSX. A ref changes without a render, so JSX that reads it shows an old value, and later jumps. The docs warn that the component "might still work", but newer React features rely on this rule. The `react-hooks/refs` lint rule and the React Compiler both flag a ref read during render. The one allowed case is filling an empty ref once, after a check for `null`.
3. **"When would you use a ref at all?"**
   Rarely. The docs say refs are something "you won't need often." Their list: timeout and interval IDs, DOM elements, and other objects that are not needed to calculate the JSX. The most common use is a DOM element, through the `ref` attribute, which the next lesson covers. A ref can hold any value: "a string, an object, or even a function." In Strict Mode, React calls the component twice in development, so each ref object is created twice, and one of the two is thrown away.

```tree dir=right caption="Interview comparison: what state and a ref share, and the one way they differ."
State vs. a ref
- +State [`useState`] | Kept between renders, **one per copy** | The setter **renders again**, and the new value comes **with the next render**
- +A ref [`useRef`] | Kept between renders, **one per copy** | No setter; a change is there **at once** and **does not render**
```
