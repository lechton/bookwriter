# Lecture 80: How a Contact Form Keeps Up When the Contact Changes

*(Why does a form keep showing the old contact after the user picks another one?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How do you derive values during render, and when is adjusting state during render legal?

---

## VS | `const name = contact.name` vs. `useState(contact.name)`: both start with Taylor, only the `const` follows the new contact

> When the user picks another contact, the parent passes the new contact down as a prop, and the component body runs again with it. **But React reads the value inside `useState(contact.name)` only on the first render, so a copy of a prop in state stays on the first contact**. That is why you read the prop directly when you can, and give the form a `key` when the user types in it.

Remember `useState('John')` from Lesson 12? The `'John'` in the parentheses is the starting value. React uses it once, when the component first appears on the page. From then on, React keeps the value in its own memory, and only the setter can change it. With a fixed string like `'John'`, that is exactly what you want.

The trouble starts when the starting value is a prop. Here are two ways to get a `name` from a `contact` prop:

```jsx title="Two ways to get name from the contact prop"
const name = ~contact.name~; // 1. Plain JavaScript: our code reads the prop again on every render
const [name, setName] = ~useState(contact.name)~; // 2. React reads the prop on the first render only
```

When the page opens with Taylor's contact, both lines give `name` the value `'Taylor'`. The page looks the same with either line.

**It may look the same, or work the same at first, but it is NOT the same thing!**
1. **With the `const`**, the line is plain JavaScript. It runs on every render. When the parent passes Alice's contact, `name` is `'Alice'` on the very next render.
2. **With `useState`**, React uses the value in the parentheses on the first render only. The React docs say it plainly: this argument "is ignored after the initial render". When the parent passes Alice's contact, React ignores `'Alice'` and hands back the stored `'Taylor'`.

```tree caption="A const reads the prop on every render, useState keeps the value of the first render."
Two ways to get `name` from the `contact` prop
- +Read during render [`const name = contact.name`] | Our code reads the prop **on every render** | After the parent passes Alice, `name` is **`'Alice'`**
- !A copy in state [`useState`] | React reads the prop **on the first render only** | After the parent passes Alice, `name` is **still `'Taylor'`**
```

So the `const` is the one that follows the prop. A value that our code calculates during render from props or state is called a **derived** value. And putting a prop into state, as the second line does, has a name in the React docs too: **mirroring props in state**.

**Why:** Picture a contacts app with two buttons, `Taylor` and `Alice`, and a form under them that edits the selected contact. If the form mirrors the contact's name in state, the user clicks `Alice`, and the form still shows Taylor. The user trusts the form and clicks Save. Now Alice's contact holds the name Taylor, and the Console never said a word.

### The Words of This Lesson

Here are the words this lesson builds on. Three are reminders, and one is new:

> [!DEFINITION]
> **The starting value of useState.** [REVIEW] `useState('John')` gives the state variable its first value, `'John'`; React uses that value once, when the component first appears, and on every later render it returns the value it stored, which only the setter can change (Lesson 12).

> [!DEFINITION]
> **State at a place in the tree.** [REVIEW] React keeps the state of a component as long as the same component renders at the same place in the tree; when a different `key` appears at that place, React throws the old component and its state away and builds a new one (Lesson 25).

> [!DEFINITION]
> **A derived value.** [REVIEW] A derived value is a value your code calculates during render from data the component already has, such as the full name John Smith built from the first name John and the last name Smith; it needs no state, because the component body calculates it again on every render (Lesson 22).

> [!DEFINITION]
> **Mirroring props in state.** [NEW] Mirroring props in state means copying a prop into a state variable, as in `useState(contact.name)`; the copy holds the value of the first render, so when the parent passes a new value, the state variable keeps the old one (Lesson 80).

### Where Readers Usually Go Wrong

Readers read `useState(contact.name)` as "a state variable that follows `contact.name`". React reads it as "the first value of this state variable". React uses that first value once, when the form first appears, and never again.

### Three Ways to Make the Form Follow the Contact

The React docs give three ways to fix this. Each one fits a different kind of value:
1. **Derive it during render.** Read `contact.name` directly, with no state. This fits every value the user does not edit, such as the heading.
2. **Reset the form with a `key`.** Write `key={contact.id}` on the form's tag. Each contact then gets a new form, with state that starts from that contact. This fits a form whose whole state belongs to one contact, such as the text the user types in the Name field. It is the docs' first choice for a reset.
3. **Adjust state during render.** Keep the previous `contact.id` in state, and call the setters during render when it differs from the new one. This fits the rare case where part of the state must start over and the rest must stay. The docs say that "most components shouldn't need it".

Developers often reach for a fourth way, and it is not a good one: an Effect that calls `setName(contact.name)` whenever `contact` changes (Lesson 34). This lesson shows it next to the other three, so you recognize it and know what it costs.

```tree caption="The three ways the React docs give to make a form follow the selected contact, and the Effect they advise against."
Making the form follow the selected contact
- +1. Derive during render [`const title = contact.name`] | No state at all | Fits values the user **does not edit**, such as the heading
- +2. Reset with a `key` [`key={contact.id}`] | A new contact means **a new form with new state** | Fits a form whose **whole state** belongs to one contact
- +3. Adjust during render [`prevId`] | Set state during render **inside an if** | Fits the rare case where **only part** of the state must start over
- !An Effect that copies the prop [`useEffect`] | Fixes the field **one render late** | The form **renders twice** for each switch
```

### The Rule of Thumb: calculate it, or reset it with a `key`

**Ask one question about every value that comes from a prop: can my code calculate it from the prop? If yes, read the prop during render, with no state. If the user types it, it is state, and a `key` makes it start over for each contact.**

We work in four files. Two of them, `index.html` and `main.jsx`, stay exactly as Vite creates them. The entry file wraps `App` in Strict Mode, which matters when we read the Console in Principles 3 and 5:

```files title="contact-editor: File Explorer" caption="Our project files: App holds the contacts and the selected ID, and EditContact edits one contact."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Mounts `App` into `#root` inside `StrictMode`
  App.jsx | parent | Holds `contacts` and `selectedId`, renders the two buttons and `EditContact`
  EditContact.jsx | default export | The heading, the Name field, and the Save button for one contact
```

`App` keeps two things in state: the list of contacts, and the ID of the selected one. On every render, it finds the selected contact in the list and passes it to the form. When the user clicks Save, the form calls `handleSave` with the edited contact:

```jsx title="src/App.jsx"
import { useState } from 'react';
import EditContact from './EditContact.jsx';

const initialContacts = [
  { id: 0, name: 'Taylor' },
  { id: 1, name: 'Alice' },
];

export default function App() {
  const [contacts, setContacts] = useState(initialContacts);
  const [selectedId, setSelectedId] = useState(0);
  const contact = ~contacts.find(c => c.id === selectedId)~; // Taylor first, Alice after the user clicks Alice

  function handleSave(updatedContact) {
    setContacts(contacts.map(c => (c.id === updatedContact.id ? updatedContact : c)));
  }

  return (
    <main>
      {contacts.map(c => (
        <button key={c.id} onClick={() => setSelectedId(c.id)}>{c.name}</button>
      ))}
      <EditContact ~contact={contact}~ onSave={handleSave} /> {/* The same place in the tree for every contact */}
    </main>
  );
}
```

`handleSave` replaces the contact with the same `id` and keeps the others. `App` stays like this until Principle 4, which adds one attribute to the last tag. Every other change happens in `EditContact`.

**PRINCIPLES:** React uses the value inside `useState` only on the first render, so a copy of a prop stops following the prop. Five principles follow:
1. **Principle 1: A copy in state keeps the first value.** `useState(contact.name)` stores `'Taylor'`. After the click on Alice, React ignores `'Alice'`.
2. **Principle 2: Derive what you can calculate.** The heading reads `contact.name` during render, with no state, so it shows Alice right after the click.
3. **Principle 3: An Effect fixes the copy one render late.** The Effect runs only after React has already rendered the form with Taylor's name.
4. **Principle 4: A `key` gives each contact a new form.** React treats Alice's form as a different component, so its `useState` reads Alice's name for the first time.
5. **Principle 5: A setter during render is legal inside an if.** The form remembers the previous ID and resets the Name field only when the ID changes.

## PRINCIPLE | `useState(contact.name)`: the copy keeps the value of the first render

> [!PRINCIPLE]
> **Principle 1: Mirroring Props in State: The Copy Keeps the First Value**
>
> *When a component copies a prop into state with `useState(prop)`, the state holds the prop's value from the first render only; when the parent passes a new value, the state variable does not change.*
>
> React uses the value inside `useState` only when the component first appears. On every later render, React returns the value it stored. So a heading built from a copied prop keeps showing the first contact after the user picks another one. If you really want to ignore later values, say so in the prop's name: `initialName` or `defaultName`.
>
> **DO THIS:**
> ```jsx
> function EditName({ initialName }) {
>   const [name, setName] = useState(~initialName~); // The prop name says only the first value counts
>   return <input value={name} onChange={e => setName(e.target.value)} />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function EditContact({ contact }) {
>   const [title, setTitle] = useState(~contact.name~); // **WRONG:** keeps 'Taylor' after the parent passes Alice
>   return <h2>Editing {title}</h2>;
> }
> ```

Start with the smallest case, a heading that copies its `name` prop into state:

```jsx title="A heading that copies its prop into state"
function Heading({ name }) {
  const [title, setTitle] = useState(~name~); // React uses name on the first render only
  return <h2>{title}</h2>;
}
```

The parent renders it with `Taylor`. On a later render, it passes `Alice` at the same place:

```jsx title="The parent passes Taylor first, then Alice at the same place"
<Heading name="Taylor" /> {/* First render: the heading shows Taylor */}
<Heading ~name="Alice"~ /> {/* Later render at the same place: the heading still shows Taylor */}
```

Nothing ever calls `setTitle`, so `title` keeps its first value forever.

### The first version of the form

Our form starts with only the heading, and it makes the same mistake:

```jsx title="src/EditContact.jsx"
import { useState } from 'react';

export default function EditContact({ contact }) {
  const [title, setTitle] = useState(~contact.name~); // **WRONG:** stores 'Taylor' on the first render, and keeps it
  return <h2>Editing {title}</h2>;
}
```

When the page opens, the heading is right. The user clicks `Alice`. **The heading still says `Editing Taylor`.** The Console shows no error and no warning:

```page width=text caption="The first version after the user clicks Alice: the heading still shows Taylor."
line: [Taylor] [Alice]
heading: Editing Taylor
console: quiet
```

### Why the heading stays on Taylor

`EditContact` does run again with Alice's contact. The prop is right. It is `useState` that ignores it. Here is what happens, in order:
1. The page opens. `App` passes Taylor's contact, and `EditContact` runs for the first time.
2. `useState(contact.name)` stores `'Taylor'`. The heading shows `Editing Taylor`.
3. The user clicks `Alice`. `App` sets the selected ID to `1` and renders again.
4. `App` passes Alice's contact to the form at the same place in the tree, so React keeps the state of `EditContact` (Lesson 25).
5. `EditContact` runs again, and the contact's name is now `'Alice'`.
6. `useState` ignores Alice's name and returns the `'Taylor'` it stored in step 2.

```tree dir=right caption="After the click on Alice, the prop changes, but useState returns the value it stored on the first render."
What `EditContact` sees after the click on Alice
- +1. The prop [`contact.name`] | `App` passes **`'Alice'`**
- !2. The state [`title`] | `useState` **ignores** its argument after the first render | Returns the stored **`'Taylor'`**
- !3. The page [`Editing Taylor`] | The heading shows the **old contact**
```

So two values on this page come from two different places:
- **`contact` inside `EditContact`** comes from `App`. `App` finds it during render with `contacts.find` and passes it down.
- **`'Taylor'` in the heading after the click** comes from React, not from the prop. React stored it on the first render, and returns it on every render after that.

### When a copy in state is what you want

Sometimes ignoring later values is the goal. The React docs say: "Don't put props *into* state unless you specifically want to prevent updates." When you do want that, name the prop so every reader knows it. The docs' convention is to start its name with `initial` or `default`:

```jsx title="A prop name that says later values are ignored"
function EditName({ ~initialName~ }) { // The name tells the caller: only the first value counts
  const [name, setName] = useState(initialName);
  return <input value={name} onChange={e => setName(e.target.value)} />;
}
```

Our heading only shows the contact's name, so it has no reason to ignore updates. The docs' page *Thinking in React* gives the rule: data passed in from a parent through props is not state.

## PRINCIPLE | `contact.name` read during render: the heading follows every new contact

> [!PRINCIPLE]
> **Principle 2: Derive During Render: Calculate What You Can, Store Only What You Cannot**
>
> *When a value can be calculated from the current props or state, calculate it in the component body during render; it is then right on every render and cannot get out of sync.*
>
> Only data that changes over time and cannot be calculated belongs in state. The heading comes from the `contact` prop, so the component reads it during render. The Name field holds text the user types before saving, so it is state, and it needs a way to start over for each contact.
>
> **DO THIS:**
> ```jsx
> function EditContact({ contact }) {
>   return <h2>Editing {~contact.name~}</h2>; // Read on every render: shows Alice after the click
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function EditContact({ contact }) {
>   const [title, setTitle] = useState(~contact.name~); // **WRONG:** a second copy that stays on Taylor
>   return <h2>Editing {title}</h2>;
> }
> ```

Here is the heading with no state at all:

```jsx title="A heading that reads its prop during render"
function Heading({ name }) {
  return <h2>Editing {~name~}</h2>; // Reads the prop on every render: shows Alice right after the parent passes Alice
}
```

What if you want a shorter name for the prop? Put it in a `const` first. That changes nothing:

```jsx title="Reading the prop in the JSX, and through a const"
<h2>Editing {~contact.name~}</h2> {/* Reads the prop in the JSX */}
const title = ~contact.name~; // Reads the same prop into a const, then the JSX shows {title}
```

**Yes, it is the exact same thing!** Both lines read `contact.name` on every render. The React docs put it this way: "If you want to give it a shorter name, use a constant." A `const` is plain JavaScript. A `useState` is React's memory. That is the whole difference.

### The fix: the heading reads the prop

We delete the `title` state and read the prop:

```jsx title="src/EditContact.jsx"
export default function EditContact({ contact }) {
  return <h2>Editing {~contact.name~}</h2>; // Calculated on every render from the prop
}
```

The user clicks `Alice`, and the heading follows. When the user clicks `Taylor` again, it shows `Editing Taylor` again:

```page width=text caption="The heading reads contact.name during render: after the user clicks Alice, it shows Alice."
line: [Taylor] [Alice]
heading: Editing Alice
```

This is what the interview means by **deriving a value during render**. React's lint docs write "Calculate during render", and React's learn pages write "calculate it during rendering". Both mean the same thing: write a `const` in the component body, or read the prop right in the JSX.

```tree caption="A value calculated during render vs. a copy of the prop in state."
Where the heading gets its name
- +Derived during render [`{contact.name}`] | Our code reads the prop **on every render** | The heading **always** shows the selected contact
- !Copied into state [`useState`] | React keeps **the first value** | The heading **stays on Taylor**, and nothing ever calls the setter
```

The React docs list three gains when you calculate during render: the code is faster, simpler, and less error-prone. There is one state variable fewer, and no second copy that can disagree with the first.

What if the calculation is really slow? Then you cache it with `useMemo` instead of copying its result into state (Lesson 56). But the docs add that "unless you're creating or looping over thousands of objects, it's probably not expensive."

`App` already follows the same rule. It keeps `selectedId` in state and finds the contact during render (Lesson 22). It does not keep the whole selected contact object in state. A stored object would be one more copy: after Save renames a contact in `contacts`, the stored object would still hold the old name.

### The Name field is a draft, so it is state

Now the form needs a Name field and a Save button. The Name field is different from the heading. The user types in it before clicking Save, and that typed text exists nowhere else. No prop can give it back, so it must be state. It starts from the contact's name:

```jsx title="src/EditContact.jsx"
import { useState } from 'react';

export default function EditContact({ contact, onSave }) {
  const [name, setName] = useState(~contact.name~); // The draft starts from the contact's name

  return (
    <section>
      <h2>Editing {contact.name}</h2>
      <label>
        Name <input value={name} onChange={e => setName(e.target.value)} />
      </label>
      <button onClick={() => ~onSave({ ...contact, name })~}>Save</button> {/* Sends the contact with the typed name */}
    </section>
  );
}
```

### The Name field still shows Taylor

The heading is fixed, but the Name field now has the problem the heading had. Its state comes from `useState(contact.name)`, so it keeps Taylor's name. The user clicks `Alice`:

```page width=text caption="After the user clicks Alice: the heading shows Alice, but the Name field still holds Taylor."
line: [Taylor] [Alice]
heading: Editing Alice
form:
  field: Name | Taylor | bad
  button: Save
```

Now the page even disagrees with itself: the heading says Alice, and the field says Taylor. If the user clicks Save, the form sends Alice's contact with the name `Taylor`. Both buttons then read `Taylor`:


So the draft must be state, and it must start over when the user picks another contact. The next three principles show three ways to make it start over.

## PRINCIPLE | `useEffect` that copies the prop: the form renders once with the old name, then again

> [!PRINCIPLE]
> **Principle 3: Copying in an Effect: The Copy Arrives One Render Late**
>
> *When an Effect calls `setName(contact.name)` after `contact` changes, the component and its children first render and commit with the stale name, then React runs the Effect and renders everything again.*
>
> Effects run after the commit. By the time the Effect runs, React has already rendered the whole form with Taylor's name and put it in the DOM. The Effect then starts a second render. Each new piece of state needs its own setter call in the Effect, and a forgotten one leaves that field on the old contact.
>
> **DO THIS:**
> ```jsx
> <EditContact ~key={contact.id}~ contact={contact} /> // A new contact gets a new form in one render
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   ~setName(contact.name)~; // **WRONG:** runs after a render with Taylor's name, then renders again
> }, [contact]);
> ```

The fix many developers try first is an Effect. The thinking goes: "When `contact` changes, copy the new name into state." It sounds right:

```jsx title="Copying the prop into state with an Effect"
const [name, setName] = useState(contact.name);
useEffect(() => {
  ~setName(contact.name)~; // Runs after React has already shown the form with the old name
}, [contact]);
```

And the field does end up holding Alice. But remember when an Effect runs: after React has rendered and committed the component (Lesson 34). So the form first renders with Taylor's name. That old name is a **stale** value, a value that no longer matches the prop. Only then does the Effect fix it, with a second render.

### Make the extra render visible

We add the Effect to `EditContact`, with a `console.log` that prints the name on every render:

```jsx title="src/EditContact.jsx"
import { useEffect, useState } from 'react';

export default function EditContact({ contact, onSave }) {
  const [name, setName] = useState(contact.name);
  console.log('render', name);

  useEffect(() => {
    ~setName(contact.name)~; // **WRONG:** fixes the field one render late
  }, [contact]);

  return (
    <section>
      <h2>Editing {contact.name}</h2>
      <label>
        Name <input value={name} onChange={e => setName(e.target.value)} />
      </label>
      <button onClick={() => onSave({ ...contact, name })}>Save</button>
    </section>
  );
}
```

We clear the Console and click `Alice`. The field now holds Alice. But the Console shows that the form rendered with Taylor's name first:

```page width=text caption="With the Effect, after the user clicks Alice: the field holds Alice, and the Console shows a render with Taylor first."
line: [Taylor] [Alice]
heading: Editing Alice
form:
  field: Name | Alice | good
  button: Save
log: render Taylor | EditContact.jsx:5
log: render Taylor | EditContact.jsx:5
log: render Alice | EditContact.jsx:5
log: render Alice | EditContact.jsx:5
```

Each line appears twice because Strict Mode renders every component twice in development (Lesson 47). Read the names in order: Taylor first, then Alice.

### Why the form renders with Taylor first

**The render right after the click still uses Taylor's name. The Effect runs only after React has put that render on the page.** Here is what happens:
1. `App` renders with Alice's contact.
2. `EditContact` renders. The name in state is still `'Taylor'`, so the Console shows `render Taylor`.
3. React commits that render to the DOM: the heading says `Editing Alice`, and the field still holds `Taylor`.
4. React runs the Effect, because `contact` changed. The Effect calls `setName('Alice')`.
5. `EditContact` renders again with Alice's name, and the Console shows `render Alice`. React commits the field with `Alice`.

No click caused the second render. The `setName` call inside the Effect caused it.

Can the user see Taylor for a moment? Sometimes. After a click, React runs the Effect before the browser paints the screen. But the React docs say that even then, React "may allow the browser to repaint the screen before processing the state updates inside your Effect." So for one frame, the field can show Taylor under the heading `Editing Alice`.

And even when the user never notices that frame, the cost is real. The form, and everything inside it, rendered once with a value that was already wrong. Then React did all of that work again. The React docs describe it this way: the component "and its children will first render with the stale value, and then render again."

```tree caption="After the click on Alice: the Effect needs two renders, and the key of Principle 4 needs one."
Renders after the click on Alice
- !With the Effect [`useEffect` + `setName`] | Render 1 uses **`'Taylor'`** and is committed | The Effect starts **render 2** with **`'Alice'`**
- +With a `key`, Principle 4 [`key={contact.id}`] | **One render** | `useState` reads **`'Alice'`** for the first time
```

### The mistake: a second field that the Effect forgets

The Effect has to copy every piece of state by hand. Suppose the form later gets an Email field, with its own `email` state that starts from `contact.email`. The developer forgets to add `setEmail(contact.email)` to the Effect. After the click on Alice, the Name field holds Alice's name, and the Email field still holds Taylor's email.

The React docs warn about exactly this: "you'd need to do this in *every* component that has some state inside" the form. The lint rule `set-state-in-effect` reports a setter called directly inside an Effect. Its docs list deriving state from props in an Effect as the mistake (Lesson 34).

## PRINCIPLE | `key={contact.id}`: every contact gets a new form with new state

> [!PRINCIPLE]
> **Principle 4: Reset with a Key: A New ID Means a New Form**
>
> *When the whole state of a component belongs to one item, give the component a `key` from that item; when the `key` changes, React treats it as a different component, builds new state from the new props, and re-creates its DOM.*
>
> The form never has to notice that the contact changed. A new form runs `useState(contact.name)` for the first time, so the field starts from the selected contact in one render. Unsaved text in the old form is thrown away with it. This is the docs' first choice when state must start over for a new item.
>
> **DO THIS:**
> ```jsx
> <EditContact ~key={contact.id}~ contact={contact} onSave={handleSave} /> // Alice gets a new form
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <EditContact ~contact={contact}~ onSave={handleSave} /> // **WRONG:** Alice gets Taylor's form, with Taylor in the field
> ```

Remember the `key` on list rows (Lesson 18)? It tells React which row is which. A `key` works on any component, not only in a list. Compare the form's tag with and without one:

```jsx title="The form's tag without a key and with key={contact.id}"
<EditContact contact={contact} /> {/* After the click on Alice, the field keeps Taylor */}
<EditContact ~key={contact.id}~ contact={contact} /> {/* After the click on Alice, the field holds Alice */}
```

**It may look the same, or work the same at first, but it is NOT the same thing!** When the page opens, both show Taylor in the field. After the click on Alice, only the tag with the `key` shows Alice.

Why? Taylor's form now has the key `0`, and Alice's form has the key `1`. To React, those are two different forms (Lesson 25). The React docs say that a different key asks React "to treat two `Profile` components with different `userId` as two different components that should not share any state." On our page, those two components are Taylor's `EditContact` and Alice's `EditContact`.

So the form itself never has to notice that the contact changed. A new form runs `useState(contact.name)` for the first time, so it reads the new name. The very thing that broke Principle 1, "React reads the starting value only once", now works for us.

### The `key` in the contact editor

We remove the Effect and the `console.log` from `EditContact`, so it is back to the version of Principle 2. In `App`, the form's tag gets one attribute:

```jsx title="src/App.jsx" startLine="23"
      <EditContact ~key={contact.id}~ contact={contact} onSave={handleSave} /> {/* A new id means a new form */}
```

`EditContact` does not receive `key` as a prop. React uses it and does not pass it on (Lesson 18). That is why `contact` still arrives as its own prop.

### The `key` throws away unsaved text

This test shows what the `key` really does. The user deletes the last three letters of Taylor's name, so the field holds `Tay`, and does not click Save. Then the user clicks `Alice`:

::: row caption="After the user types Tay over Taylor and clicks Alice: without a key the field keeps the old text, with key={contact.id} it holds Alice."
::: col title="Without key" tag="the field keeps the old text" tone=bad
```page size=mini
line: [Taylor] [Alice]
heading: Editing Alice
form:
  field: Name | Tay | bad
  button: Save
```
:::
::: col title="With key={contact.id}" tag="a new field for Alice" tone=good
```page size=mini
line: [Taylor] [Alice]
heading: Editing Alice
form:
  field: Name | Alice | good
  button: Save
```

Without the `key`, the form keeps its state, so the field still holds `Tay` under Alice's heading. With `key={contact.id}`, the field holds `Alice`.

Now the user clicks `Taylor` again. With the key, the field holds `Taylor`, not `Tay`:

```page width=text caption="With key={contact.id}, after the user clicks Taylor again: the field holds the saved name, and the unsaved Tay is gone."
line: [Taylor] [Alice]
heading: Editing Taylor
form:
  field: Name | Taylor
  button: Save
```

**The `key` throws away unsaved text, and that surprises developers.** Here is why, in order:
1. The user types `Tay` in the field. That text lives in the state of Taylor's form, the one with the key `0`.
2. The user clicks `Alice`. At the same place in the tree, `App` now renders the form with the key `1`.
3. React sees a different `key` at the same place. It removes the old form together with its state, and builds a new one.
4. The new form runs `useState(contact.name)` for the first time, with `'Alice'`. The field holds `Alice`.
5. The user clicks `Taylor`. React sees the key `0` where the key `1` was, removes Alice's form, and builds a new form for Taylor.
6. That new form reads `contact.name` for the first time: the saved `'Taylor'`. The `Tay` lived in the form that React removed in step 3.

React also builds new DOM for the new form. The docs say React "will also re-create the DOM elements instead of reusing them". So the `<input>` after the click is a new element.

```tree dir=right caption="What React does when the key of EditContact changes from 0 to 1."
The user clicks Alice
- !Old form, key 0 [`<EditContact key={0} />`] | React **removes** it | Its state, including the unsaved **`Tay`**, is gone
- +New form, key 1 [`<EditContact key={1} />`] | React **builds** it with new state and new DOM | `useState` reads **`'Alice'`** for the first time
```

### The mistake: expecting the `key` to keep a draft for each contact

A developer adds `key={contact.id}` and expects each contact to keep its own unsaved text. It does not: when the user switches away from a contact, React throws that contact's form away. A form that must keep drafts for several contacts at once needs a different design. The React docs give two in "Preserving state for removed components":
1. Lift the drafts up into the parent, which the docs call "the most common solution" (Lesson 24).
2. Render every form, and hide all the others with CSS.

### How the docs hide the `key` inside the component

The code that uses a form should not have to remember the `key`. So the docs split the component in two. The exported component receives the ID as a regular prop, and passes it as the `key` of an inner component. The docs call the `key` "an implementation detail" of that split.

In their solution to a challenge, the outer `EditContact` passes every prop on to an inner `EditForm`. It adds the `key` from `savedContact`, the prop that holds the saved contact:

```jsx title="The docs' EditContact solution: the outer component passes the key"
<EditForm {...props} ~key={props.savedContact.id}~ /> {/* The inner form starts over for each saved contact */}
```

## PRINCIPLE | `setName` during render inside an `if`: legal for the component's own state, once per change

> [!PRINCIPLE]
> **Principle 5: Adjust State During Render: Only Inside a Condition, Only Your Own State**
>
> *When only part of a component's state must change after a prop changes, keep the previous prop value in state and, during render, inside a condition that compares it with the new prop, call that component's own setters; React throws away that render's JSX and renders the component again at once, before its children.*
>
> The condition stops the loop, because the same block sets `prevId` and makes the condition false on the next pass. React retries before any child renders and before the DOM changes, so nothing on the page sees the stale value. A set call with no condition loops until React throws `Too many re-renders`.
>
> **DO THIS:**
> ```jsx
> const [prevId, setPrevId] = useState(contact.id);
> if (~contact.id !== prevId~) { // Runs once per new contact, then the condition is false
>   setPrevId(contact.id);
>   setName(contact.name);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [name, setName] = useState(contact.name);
> ~setName(contact.name)~; // **WRONG:** every render sets state again: Too many re-renders
> ```

Until now, you called setters in event handlers: the user clicks, and the handler calls `setCount`. Calling a setter while the component renders sounds like a loop. It usually is. But there is one shape where React allows it.

### The smallest case: a label that compares with the last render

Sometimes a component must react to how a prop changed, not only to its new value. The React docs show a label that says whether a counter went up or down. To compare, it must remember the count from the last render:

```jsx title="The docs' CountLabel: a set call during render, inside a condition"
function CountLabel({ count }) {
  const [prevCount, setPrevCount] = useState(count);
  const [trend, setTrend] = useState(null);
  if (~prevCount !== count~) { // True only on the render where count changed
    setPrevCount(count);
    setTrend(count > prevCount ? 'increasing' : 'decreasing');
  }
  return (
    <>
      <h1>{count}</h1>
      {trend && <p>The count is {trend}</p>}
    </>
  );
}
```

The setters run in the component body, while the component renders, with no click and no Effect. `prevCount` holds the previous value of the prop. Our code stores it, and React returns it on every render until `setPrevCount` changes it.

> [!DEFINITION]
> **Adjusting state during render.** [NEW] Adjusting state during render means calling a component's own setter in its body, while it renders, inside an if that compares a stored previous value with the new prop; the React docs call it storing information from previous renders, and their page on Effects calls it adjusting the state directly during rendering (Lesson 80).

### A set call during render: alone vs. inside an `if`

A setter called in the component body is usually a bug. Compare a set call alone and the same call inside an `if`:

```jsx title="A set call alone during render, and inside a condition"
setName(contact.name); // Alone: every render sets state, and every set starts another render
if (~contact.id !== prevId~) { setPrevId(contact.id); setName(contact.name); } // Inside a condition: runs once per new contact
```

**It may look the same, or work the same at first, but it is NOT the same thing!**
1. **With the setter alone in the body**, every render calls it. Every setter call during render makes React render the component again. That is an **infinite loop**: it never ends on its own. React stops it and throws an error.
2. **With the setter inside the `if`**, the same block also calls `setPrevId(contact.id)`. On the next render, `prevId` equals `contact.id`, the condition is false, and nothing is set.

The React docs give both rules at once. The set call "must be inside a condition like `prevCount !== count`". And "there must be a call like `setPrevCount(count)` inside of the condition. Otherwise, your component would re-render in a loop until it crashes."

Developers call such a condition a **guard**: it lets the set call run only when it must. The lint docs say the same thing next to their valid example: "This condition makes it valid."

### The guarded reset in the contact editor

Our page has no state that must survive a switch of contact, so the `key` of Principle 4 stays in the final code. Here, for comparison, is the other way to reset the Name field. We take the tag in `App` back to the version without a `key`:

```jsx title="src/App.jsx" startLine="23"
      <EditContact contact={contact} onSave={handleSave} /> {/* No key: the same form stays for every contact */}
```

And `EditContact` keeps the previous contact ID in state:

```jsx title="src/EditContact.jsx"
import { useState } from 'react';

export default function EditContact({ contact, onSave }) {
  const [name, setName] = useState(contact.name);
  const [prevId, setPrevId] = useState(contact.id);
  if (~contact.id !== prevId~) { // True only on the first render after the user picks another contact
    setPrevId(contact.id);
    setName(contact.name);
  }
  console.log('render', name);

  return (
    <section>
      <h2>Editing {contact.name}</h2>
      <label>
        Name <input value={name} onChange={e => setName(e.target.value)} />
      </label>
      <button onClick={() => onSave({ ...contact, name })}>Save</button>
    </section>
  );
}
```

We clear the Console and click `Alice`. The field holds Alice. The Console shows one line with Taylor, then Alice:

```page width=text caption="With the guarded set during render, after the user clicks Alice: the field holds Alice."
line: [Taylor] [Alice]
heading: Editing Alice
form:
  field: Name | Alice | good
  button: Save
log: render Taylor | EditContact.jsx:10
log: render Alice | EditContact.jsx:10
log: render Alice | EditContact.jsx:10
```

`render Alice` appears twice because Strict Mode calls the component one more time in development (Lesson 47).

### Why `render Taylor` shows up, and costs nothing on the page

**React throws away the render with Taylor's name before any child renders and before any change to the DOM.** Here is what happens after the user clicks Alice:
1. `EditContact` renders with Alice's contact. `prevId` is still `0`.
2. The condition is true, so `setPrevId(1)` and `setName('Alice')` run.
3. The rest of the component body still runs. In this pass, the name in state is still `'Taylor'`, so the Console shows `render Taylor`. The docs say it directly: "The rest of your component function will still execute", and its result is thrown away.
4. React throws that JSX away and runs `EditContact` again at once, before rendering any child and before touching the DOM.
5. Now `prevId` is `1`, so the condition is false. The name in state is `'Alice'`, and the Console shows `render Alice`.
6. React renders the children and commits. The field holds `Alice`.

No click and no Effect caused the second pass. The setter calls during render caused it, and React ran it before the children.

Compare this with the Effect of Principle 3. There, React rendered the children with Taylor's name and committed them, then rendered everything again. Here, the children never see Taylor's name. The React docs explain why, with their own example of a list. At this point, React "has not rendered the `List` children or updated the DOM yet". So the children "skip rendering the stale `selection` value." The same holds for our form.

The docs also allow an early `return;` right after the set calls, when the condition sits below all the Hook calls. React then restarts the render sooner.

### VS | The guarded set vs. the `key`: both put Alice in the field, only the `key` builds a new form

The guarded set and the `key` both put Alice in the field. **They look the same on the page, but they are NOT the same thing!**
1. **With `key={contact.id}`**, React builds a whole new form: every state variable starts over, and the DOM is new.
2. **With the guarded set**, React keeps the same form and the same DOM. Only the state that the block names, `name` and `prevId`, changes. Any other state in the form stays as it was.

That is the case the guarded set is for: part of the state must start over, and the rest must stay. On our page, all of the form's state belongs to one contact, so the `key` is the better fit.

The React docs agree: "This pattern can be hard to understand and is usually best avoided. However, it's better than updating state in an effect." They also say that "most components shouldn't need it either." Often the need disappears when state stores an ID instead of an object, as `App` does with `selectedId`.

```tree caption="Three ways to put Alice in the Name field after the click, and what each one costs."
Resetting the Name field after the click on Alice
- !Effect [`useEffect` + `setName`] | The children render and commit with **Taylor**, then render again | Every state variable needs **its own line**
- +Guarded set during render [`contact.id !== prevId`] | React throws away the first pass **before the children** | Resets **only the state it names**
- +Key [`key={contact.id}`] | React builds **a new form** | Resets **all of the form's state** and **its DOM**
```

### The mistake: a set call with no condition

A developer wants the field to follow the contact, and writes the setter in the body with no condition:

```jsx title="src/EditContact.jsx" startLine="3"
export default function EditContact({ contact, onSave }) {
  const [name, setName] = useState(contact.name);
  ~setName(contact.name)~; // **WRONG:** every render sets state, and every set starts another render
```

The page goes blank, and the Console shows the error React throws:

```devconsole width=full
x Uncaught Error: Too many re-renders. React limits the number of renders to prevent an infinite loop.
! An error occurred in the <EditContact> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The fix is the guard with `prevId`, or the `key` of Principle 4. The lint rule `set-state-in-render` catches this mistake before the page runs. Its docs say it "Validates against unconditionally setting state during render".

### Two more limits

A set call during render has two more limits:
1. **Only the component's own state.** The component that is rendering may set only its own state. The React docs: "If you update another component's state during a render, you'll see an error." React limits it to the same component "to avoid very slow cascading retries".
2. **No other side effects.** Changing the DOM or setting a timeout stays in an event handler or an Effect, to keep components pure (Lesson 14).

## All 5 Principles Together

### The complete files

`index.html` and `main.jsx` stay as Vite creates them. Here are the two files we wrote. The heading is derived during render, the Name field is a draft in state, and the `key` gives each contact a new form:

```jsx title="src/App.jsx"
import { useState } from 'react';
import EditContact from './EditContact.jsx';

const initialContacts = [
  { id: 0, name: 'Taylor' },
  { id: 1, name: 'Alice' },
];

export default function App() {
  const [contacts, setContacts] = useState(initialContacts);
  const [selectedId, setSelectedId] = useState(0);
  const contact = ~contacts.find(c => c.id === selectedId)~; // Principle 2: derived during render from the ID

  function handleSave(updatedContact) {
    setContacts(contacts.map(c => (c.id === updatedContact.id ? updatedContact : c)));
  }

  return (
    <main>
      {contacts.map(c => (
        <button key={c.id} onClick={() => setSelectedId(c.id)}>{c.name}</button>
      ))}
      <EditContact ~key={contact.id}~ contact={contact} onSave={handleSave} /> {/* Principle 4: a new contact gets a new form */}
    </main>
  );
}
```

```jsx title="src/EditContact.jsx"
import { useState } from 'react';

export default function EditContact({ contact, onSave }) {
  const [name, setName] = useState(~contact.name~); // Principle 1: used once per form, and the key gives each contact its own form

  return (
    <section>
      <h2>Editing {~contact.name~}</h2> {/* Principle 2: read on every render */}
      <label>
        Name <input value={name} onChange={e => setName(e.target.value)} />
      </label>
      <button onClick={() => onSave({ ...contact, name })}>Save</button>
```

### The order in which React calls the components

When the user clicks `Alice`, React renders `App` first. `App` renders the two buttons and then the form. Because the key changed, React builds a new `EditContact` instead of updating the old one:

```tree caption="The component tree after the click on Alice, in the order React calls each part."
`App` [1. Renders with `selectedId` set to `1`] | Finds Alice's contact during render
- +Two buttons [2. `Taylor` and `Alice`] | Built from `contacts` with `map`
- +`EditContact` with key 1 [3. A new form] | The old form with key 0 and its state are **removed** | `useState` reads **`'Alice'`** for the first time
```

### What each way shows after the click on Alice

| Principle | What the developer writes | What the user sees after the click on Alice |
| :--- | :--- | :--- |
| **1. A copy in state** | `useState(contact.name)` for the heading | `Editing Taylor`, and Save writes Taylor's name into Alice's contact |
| **2. Derive during render** | `{contact.name}` in the heading | `Editing Alice` at once |
| **3. An Effect** | `setName(contact.name)` in an Effect | Alice in the field, after a render with Taylor's name that the browser may paint for one frame |
| **4. A `key`** | `key={contact.id}` on the form | Alice in the field in one render; unsaved text is gone |
| **5. A guarded set during render** | `if (contact.id !== prevId)` with both setters | Alice in the field; only `name` and `prevId` start over |

Remember the one sentence of this lesson. **React reads the value inside `useState` only on the first render. So read a prop directly when you can calculate from it, and reset a form with a `key` when the user types in it.**

## For the Interview

> **The Interview Question:** How do you derive values during render, and when is adjusting state during render legal?

### How to Answer Clearly in 30 Seconds

"React uses the value I give to `useState` only on the first render. The docs say it is ignored after that. So if I copy a prop into state, the copy goes stale when the parent passes a new value. That is mirroring props in state. The React docs give two main fixes, and a rare third:
1. **Derive during render:** if a value can be calculated from props or state, I calculate it in the component body as a `const`. It is right on every render, and nothing can get out of sync.
2. **Reset with a `key`:** if the state is a draft that belongs to one item, such as a form, I write `key={item.id}` on the component. A new ID makes React build a new component with fresh state.
3. **Adjust during render:** in the rare case where only part of the state must reset, I keep the previous prop value in state. During render, inside a condition that compares it with the new prop, I call my own setters. That is legal only inside the condition, with the previous value updated in the same block, and only for the component's own state. React throws away that render and retries before rendering the children.

I avoid an Effect that copies the prop into state, because the component and its children first render with the stale value."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Is it ever right to copy a prop into state?"**
   Yes, when you want to ignore later values on purpose. React's docs: "Don't put props *into* state unless you specifically want to prevent updates." Then name the prop `initialName` or `defaultName`, so the caller knows that only the first value counts. A form draft is the common case: it starts from the saved value, and the `key` makes each item start its own draft.
2. **"Why not just sync the state with `useEffect`?"**
   Because Effects run after the commit. The render that received the new prop has already used the old state, and React has already put it in the DOM. The Effect then sets state and starts a second render, so the component and all its children render twice for each change. Every piece of state needs its own line in the Effect, and a forgotten one stays stale. The lint rule `set-state-in-effect` reports a setter called directly in an Effect.
3. **"Why does React allow a set call during render, and why only for the component's own state?"**
   Because React can retry that one component cheaply. When a component sets its own state during render, React throws away the JSX it returned and runs it again at once. That happens before any child renders and before any DOM change, so the children never render the stale value. If a component set another component's state during render, React would have to go back and render other parts of the tree again. The docs say React limits it "to avoid very slow cascading retries", and you see an error instead. Without a condition, even the component's own set call loops. React stops it with the error `Too many re-renders`.
