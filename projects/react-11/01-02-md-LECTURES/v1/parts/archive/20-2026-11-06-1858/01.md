## How React Controls a Form Field

### Three ways to put a starting name inside an input box

Before we build a project, strip away every form, button, and stylesheet. Look at one plain text input on the screen that shows the name **John** when the page opens.

First, look at **Line A**, which sets the starting text with `defaultValue`:

```jsx title="Line A: Starting text with defaultValue"
~<input defaultValue="John" />~ // 1. Gives the box "John" once when it first appears, then lets the browser own the text
```

Second, look at **Line B**, which passes `value` alone with no handler:

```jsx title="Line B: Fixed text with value and no handler"
~<input value="John" />~ // 2. Locks the box to "John" on every render so typing cannot change it
```

Third, look at **Line C**, which pairs `value` with React state and an `onChange` handler:

```jsx title="Line C: Controlled text with state, value, and onChange"
const [name, setName] = useState('John');

~<input value={name} onChange={e => setName(e.target.value)} />~ // 3. Shows the state variable name and updates state on every keystroke
```

When the page first opens, all three boxes display the exact same letters: **`John`**.

Now watch what happens when a user clicks inside each box and types the two letters `ny` at the end of **John**:
- In **Line A**, the box changes to **`Johnny`**.
- In **Line B**, nothing changes at all. The box stays locked on **`John`**!
- In **Line C**, the box changes to **`Johnny`**, just like Line A.

Next, imagine a button beside the input calls `setName` with an empty string `''` to clear the name:
- In **Line A**, the box ignores `setName` and still shows **`Johnny`**!
- In **Line C**, the box becomes **empty** right away!

Four everyday ideas explain what happens inside those three boxes:
- **What does "default" mean?** Think of the default ringtone on a new phone. The factory sets that ringtone for the very first day. The moment you pick a new ringtone yourself, your phone plays your choice, and the factory starting setting is history. In React, `defaultValue="John"` works the exact same way. It gives the input box its starting text when the box is first created. From that moment on, the browser input box keeps and updates its own text by itself.
- **What does "controlled" mean?** Think of the departure board at a train station. The board on the wall never decides for itself which train to display. The station computer sends the current text to the board, and the board simply shows whatever the system tells it to show. In React, an input is **controlled** when your component's state decides what the box displays on every render through `value={name}`.
- **What is a "single source of truth"?** Imagine a kitchen with two wall clocks that show different times. You never know which clock to trust. When a room has only one official clock, everyone reads that one clock. Keeping the field's text in one place, inside React state, makes state the **single source of truth** for both the screen and your code.
- **How does `onChange` let typing work?** If a controlled input only shows what state tells it to show, how do new letters appear when you type? Think of `onChange` as a report slip from the input box. On every keystroke, the browser hands React an event object `e` carrying the box's latest text in `e.target.value`. Your `onChange` handler passes that string to `setName`. Then React re-renders with the new `name`, and the box displays the new state!

Now look closely at the four silent confusions that trip developers up here:
- **First, Line A with `defaultValue="John"` and Line C with `value={name}` look the same on screen and both let you type Johnny, but they are NOT the same thing!** In Line A, the browser box owns its own text in the DOM, and React state has no idea what is inside the box. In Line C, React state owns the text, and the input box only displays `name`.
- **Second, Line B with `value="John"` and Line C with `value={name}` both pass the `value` prop, but they are NOT the same thing!** Line B passes a fixed value with no `onChange` handler to update it. Because nothing changes the string, React forces **John** back into the box after every keystroke. Line C pairs `value={name}` with `onChange`, so every keystroke updates state and displays the new text.
- **Third, when `name` holds John, writing `value="John"` and writing `value={name}` without `onChange` do the exact same thing to the input box!** Yes, it is the exact same thing! In both cases, React receives the string `'John'` for `value` and locks the box to **John**. The curly braces around `name` do not make the box editable. Line C is editable only because its `onChange` handler calls `setName` on every keystroke.
- **Fourth, React's `onChange` prop sounds like the plain browser `change` event, which waits until you click outside the box, but it is NOT the same thing!** In React, `onChange` fires immediately on every single keystroke, paste, or cut, just like the browser's native `input` event.

```tree caption="How Line A, Line B, and Line C behave when the page opens, when the user types ny, and when code calls setName with an empty string."
Three ways to wire an `<input>` that starts with `John`
- !Line A: `<input defaultValue="John" />` [Uncontrolled] | Typing `ny` shows **`Johnny`** in the browser box | Calling `setName` with `''` does **nothing** to the box: it stays **`Johnny`**
- !Line B: `<input value="John" />` [Read-only lock] | Typing `ny` is **reverted after every keystroke** | Box stays frozen on **`John`**, and React logs a **Console error**
- +Line C: `value={name}` + `onChange` [Controlled] | Typing `ny` updates `name` to **`'Johnny'`** on each keystroke | Calling `setName` with `''` **clears the box** right away
```

### Why a shop's Contact Us form needs controlled fields

To see why controlled inputs matter on a real website, we will build the **Contact Us** page of an online shop. A customer visits this page to send a question to the support team:
1. The customer picks a **Topic** from a dropdown menu: **My order**, **Delivery**, or **Refund**.
2. They type their full name into the **Your name** input box.
3. They write their question inside the **Message** textarea box. Right below it, a live character counter shows how many of the `200` allowed characters they have used, such as **18 / 200**.
4. If they want an email reply, they tick the **Email me a reply** checkbox. Ticking that box reveals an **Email** input right below it.
5. Finally, they click **Send**. The form clears every box, resets the counter to **0 / 200**, hides the email input, and displays **Thanks! Your message was sent.** underneath.

Try to build that page with `defaultValue` alone and watch what breaks:
- The live counter under the message box stays frozen at zero while the customer types because state never hears about the keystrokes.
- The message box cannot stop the customer at `200` characters through state.
- Ticking **Email me a reply** never reveals the **Email** input because no boolean state flips when the checkbox is clicked.
- Clicking **Send** leaves the customer's old text sitting inside the boxes even after **Thanks! Your message was sent.** appears!

```tree dir=right caption="Why our online shop Contact Us form needs React state to own every field."
What the `Contact Us` page must do on screen
- +Show a live counter under `Message` | Needs the message text in state **on every keystroke** | Updates the **character count** live as the customer types
- +Reveal the `Email` box when ticked | Needs the checkbox state **on every click** | Shows or hides the **`Email` input** right away
- +Empty every field when `Send` is clicked | Needs every form box to **display state** | Resetting state on submit **clears every field** on screen
```

### Two ways to own a form field's value in React

In daily React work, there are two ways to handle form fields, and each one fits a clear job:
1. **Controlled fields**: You pass `value` or `checked` from React state, and you update that state inside an `onChange` handler. Choose controlled fields whenever the page must react to every keystroke or click. Common examples include live character counts, custom input rules, extra fields that appear when a checkbox is ticked, and buttons that clear the form from state.
2. **Uncontrolled fields**: You pass `defaultValue` for starting text or `defaultChecked` for a starting tick mark so the browser DOM owns the field while the user types. Then you read all the values once when the form is submitted, such as with `FormData`. Choose uncontrolled fields when the page does not need to react on every keystroke and only cares about the final values on submit.

```tree caption="When to make a form field controlled vs. when to leave it uncontrolled."
Two ways to handle form inputs in React
- +1. Controlled field [`value` + `onChange` + state] | React state is the **single source of truth** on every keystroke | Best for **live counts**, **conditional fields**, **live rules**, and **resetting from state**
- +2. Uncontrolled field [`defaultValue` + read on submit] | The **browser DOM node** holds the value until the form submits | Best for **simple forms** that only read values **once on submit**
```

### What we already know and how our project files are organized

This lesson builds on three React tools from earlier lessons, plus four small browser and JavaScript facts:
- **State snapshots and setters**: Calling `useState` gives back the current render's state value and a setter function. Calling the setter stores the next value and triggers a re-render.
- **Event handlers and preventing reload**: Passing an `onSubmit` handler to a `<form>` runs that function when the user sends the form. Calling `e.preventDefault` inside the submit handler stops the browser from reloading the page.
- **Conditional rendering with `&&`**: Writing `{sent && <p>...</p>}` renders the paragraph when the boolean `sent` is true. When `sent` is false, React renders nothing at all.
- **The four HTML form tags in this lesson**: A single-line text box or checkbox is `<input>`, and a multi-line message box is `<textarea>`. A dropdown menu is `<select>` containing `<option>` choices. Wrapping a `<label>` around the label text and its field links them together so clicking the label focuses or ticks the field.
- **How the browser stores a field's current value**: Every text input, textarea, or select DOM node in the browser has a live `.value` property holding its current string. Every checkbox or radio DOM node has a live `.checked` property holding a boolean. Inside an `onChange` handler, `e.target` is that DOM node, so `e.target.value` reads the string and `e.target.checked` reads the boolean.
- **String `length` and `trim`**: Every JavaScript string has a `.length` property that counts its characters, including spaces. It also has a `.trim` method that returns a new string with spaces removed from the very start and very end while keeping spaces between words.
- **`undefined` and the fallback operator `??`**: Calling `useState` with no initial value sets state to `undefined`. The fallback operator `??` returns the left side when it is defined, and falls back to the right side only when the left side is `null` or `undefined`.

Our shop project uses four files. In the entry file, React mounts `App` inside `<StrictMode>`. Then our main file renders the `ContactForm` component from the form file inside the `components` folder:

```files title="contact-us: File Explorer" caption="How the four files of our online shop Contact Us page are organized inside src/ and src/components/."
index.html | entry | The HTML page with the empty root div where React mounts
src/

```

### Six Principles of Controlled Inputs

**PRINCIPLES:** A form field is controlled when React state is its single source of truth on every render, and its `onChange` handler writes every edit back into state. Six practical principles cover every field type on our **Contact Us** page:
1. **Principle 1: An Uncontrolled Box Keeps Its Own Text, So State Cannot Clear It**: Passing `defaultValue` sets only the starting text when the field first mounts. After that, the browser input box owns its own text and ignores your state variables.
2. **Principle 2: `value` Forces the Box to Show State, and `onChange` Lets Typing Reach State**: Passing `value` from state locks the box to that state variable on every render. Pairing `value` with an `onChange` handler completes the loop so typing updates state and re-renders the box.
3. **Principle 3: Whatever the Handler Writes Into State Is What the Box Shows**: On every keystroke, React renders the exact string stored in state. Transforming text inside `onChange` changes what the user sees as they type, while checking the string's length before calling the setter caps the length cleanly.
4. **Principle 4: A Select Is Controlled by `value` on `<select>`, Never `selected` on an `<option>`**: Never put the HTML `selected` attribute on an option inside React. Instead, pass `value` and `onChange` directly on the select tag.
5. **Principle 5: A Checkbox Is Controlled by `checked`, and Reports Through `e.target.checked`**: A checkbox stores a boolean `true` or `false`, not text. Control it with the `checked` prop and update state from `e.target.checked`, never from `e.target.value`.
6. **Principle 6: The `value` Is a String From the First Render to the Last**: Passing `value={undefined}` makes an input uncontrolled on its first render. If state starts as `undefined` from an empty `useState` call and later receives a typed string, the input switches from uncontrolled to controlled and logs a Console error.

Here is the complete map of all six principles before we build each one on our **Contact Us** page:

| # | Principle | Why It Matters in Debugging and Interviews | The React Rule |
| :--- | :--- | :--- | :--- |

| **Principle 2** | **`value` Paired with `onChange`** | Passing `value` from state without `onChange` freezes the box so typed letters never appear and logs a read-only field error in the Console. | Always pair `value` with an `onChange` handler that reads `e.target.value` and calls the state setter. |
| **Principle 3** | **Handler Transformation and Validation** | Calling `.trim` inside `onChange` strips the space key as the user tries to type a two-word name. | Keep raw text in state while typing, trim once on submit, and check `e.target.value.length` in `onChange` when capping length. |
