## 3. Principle 3: Leaving roomId Out Keeps the Chat on general

### `[roomId]` vs. `[]` when the Effect body reads `roomId`

Both Effects below run the exact same setup and cleanup reading `roomId`, and they differ only in the dependency array at the bottom:

```jsx title="Listing roomId in the dependency array: [roomId]"
useEffect(() => {
  const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId]~); // Tells React this Effect depends on roomId
```

```jsx title="Leaving roomId out of the dependency array: []"
useEffect(() => {
  const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
  connection.connect();
  return () => connection.disconnect();
}, ~[]~); // **WRONG:** tells React this Effect depends on nothing, so it never reconnects!
```

**It may look the same, or work the same at first, but it is NOT the same thing!** When the user clicks the Open chat button, both versions connect to the `general` room and show the exact same screen and Console lines. The moment the user picks `travel` in the menu, the version with `[roomId]` disconnects from the old room and connects to the travel room. The version with `[]` does nothing at all and stays connected to `general`.

React knew to re-synchronize the Effect with `[roomId]` because the dependency array included `roomId`. Why? Well, in the docs' words: "It's because *you told React* that its code depends on `roomId` by including it in the list of dependencies." The docs break that down into three steps:
1. "You knew `roomId` is a prop, which means it can change over time."
2. "You knew that your Effect reads `roomId`."
3. "This is why you specified it as your Effect's dependency."

That leads to the rule the docs put in bold: "**You can't "choose" your dependencies.**" Every reactive value your Effect reads must be listed in its dependency array. The `exhaustive-deps` linter rule checks this automatically, as in its reference example:

```jsx title="The exhaustive-deps reference example: missing userId vs. complete array"
useEffect(() => {
  fetchUser(~userId~); // Reads userId inside the Effect
}, ~[]~); // **WRONG:** Missing 'userId' in the dependency array!

useEffect(() => {
  fetchUser(~userId~); // Reads userId inside the Effect
}, ~[userId]~); // Lists userId so the Effect runs again when userId changes
```

Passing `[roomId]` and passing **no dependency array at all** are **NOT the same thing** either. Without a dependency array, the Effect re-synchronizes after every single commit of the component (as seen in Lesson 32). Suppose `ChatRoom` also has a text input for typing a chat message, as in the docs' first Challenge. When you omit the dependency array, typing every letter in the message box "*also* reconnects to the chat".

```tree caption="What happens with [roomId], with [], and with no dependency array at all when the Effect reads roomId."
Three ways to write the end of `useEffect` when the body reads `roomId`
- +With `[roomId]` [`[roomId]`] | Lists the reactive value the Effect reads | Re-synchronizes **only when `roomId` changes**
- !With `[]` [`[]`] | ~Leaves `roomId` out of the array | Never re-synchronizes when `roomId` changes; **stays stuck on `'general'`**
- !With no array at all [no array] | ~Omits the dependency array completely | Re-synchronizes **after every single commit**, even when typing in a message box
```

### What happens when a developer suppresses the linter with `[]`

When a developer writes `[]` on an Effect that reads `roomId`, the linter warns that the prop is missing from the dependency array. When both `roomId` and `serverUrl` are missing, the docs quote the exact lint message: "React Hook useEffect has missing dependencies: 'roomId' and 'serverUrl'."

Sometimes a developer silences that warning by writing an `eslint-disable-next-line` comment for `exhaustive-deps` to **suppress the linter** for that line. React's docs warn against this directly: "Don't fix these problems by suppressing the linter!"

**Beware! When you write `[]` and suppress the linter, the heading on the screen changes to the travel room, while the Console prints nothing and the app remains connected to `general`.** Here is what happens step by step:
1. A developer wants the connection to open only once, writes `[]`, and adds a disable comment for `exhaustive-deps`.
2. The user clicks the Open chat button, and the Effect connects to `general`.
3. The user picks `travel` in the menu. The page now displays the travel room heading, while the Effect still holds the connection from the first render.
4. React compares `[]` from the new render with the previous render's `[]`. Because no item in the array changed, React skips the Effect.
5. No disconnect line and no new connect line appear in the Console. The Effect stays stuck on the **stale value** `'general'` from the first render (as seen in Lesson 34). The heading on the screen and the live chat connection no longer match.

As the docs explain: "By suppressing the linter, you "lie" to React about the values your Effect depends on." And they state the guarantee in bold: "**If you never suppress the linter, you will never see problems with stale values.**"

### Stale closures and what to do when an Effect runs too often

In interviews, you will hear the `exhaustive-deps` documentation's name for this bug: leaving out a dependency "causes stale closures where the hook uses outdated values." In JavaScript, a **closure** is a function that remembers the variables from the scope where it was created. A **stale closure** is one from an earlier render that still holds outdated props or state. In the docs' Challenge on investigating a stale value bug, a pointer listener `handleMove` inside an Effect reads `canMove` while the linter is suppressed. Because the dependency array is empty, that listener "from the initial render will forever see" `canMove` as `true`, even after the user unticks the checkbox.

Effects re-run whenever a dependency changes because, in the docs' words, "Effects are reactive blocks of code." As the docs contrast them with handlers: "Unlike event handlers, which only run once per interaction, Effects run whenever synchronization is necessary." When you want an Effect to act only when a condition holds, put the condition inside the Effect body rather than wrapping the Hook itself in a condition. As the docs' Hint states: "You can't declare an Effect conditionally. However, the code inside the Effect can use conditions!" That keeps your Hook at the top level of the component, following the rules of Hooks (as seen in Lesson 38).

When the linter flags a dependency that makes your Effect re-run too often, do not suppress the linter. Instead, change the code so the Effect no longer needs that reactive dependency. As the docs' Pitfall explains: "The linter only knows when the dependencies are *wrong*. It doesn't know *the best* way to solve each case." Still, "All errors flagged by the linter are legitimate." You can read the latest value inside an Effect Event without reconnecting (as seen in Lesson 36). Or you can change the code so the dependency is not an object or function recreated on every render (as seen in Lesson 37).

> [!PRINCIPLE]
> **Principle 3: Complete Dependencies: Never Suppress the Linter to Hide a Reactive Value**
>
> *List every reactive value that the Effect reads inside its dependency array, and never suppress the `exhaustive-deps` linter to shorten the array.*
>
> React only knows to re-synchronize an Effect when an item in the dependency array changes between renders according to `Object.is`. Leaving `roomId` out and silencing the linter keeps the first render's setup alive forever, leaving the app connected to a stale `roomId`.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, ~roomId~); // Reads roomId
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[roomId]~); // Includes roomId so React reconnects when roomId changes
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[]~); // **WRONG:** suppressing exhaustive-deps lies to React about roomId!
> ```
