## 1. Principle 1: The Effect Connects to One Room Until It Disconnects

### The component's perspective vs. the Effect's perspective

Suppose the user clicks the Open chat button, picks `travel` in the menu, picks `music` in the menu, and then clicks the Close chat button. React's docs compare two ways of looking at those four actions: **the component's perspective** and **the Effect's perspective**.

From **the component's perspective**, you see four lifecycle moments of `ChatRoom`:
1. `ChatRoom` mounted with `roomId` set to "general".
2. `ChatRoom` updated with `roomId` set to "travel".
3. `ChatRoom` updated with `roomId` set to "music".
4. `ChatRoom` unmounted.

Now read the exact same four actions from **the Effect's perspective**:
1. Your Effect connected to the "general" room, until it disconnected.
2. Your Effect connected to the "travel" room, until it disconnected.
3. Your Effect connected to the "music" room, until it disconnected.

It may look the same, or work the same at first, but it is NOT the same thing! Look at the count: the component goes through four lifecycle moments, while the Effect completes three start and stop cycles. React's docs warn against mixing the two up: "**It's a good way to think about components, but _not_ about Effects.**"

Thinking of Effects as callbacks or lifecycle events that fire after a render or before unmount "gets complicated very fast," as the docs put it. Instead, the docs give a simpler rule: "always focus on a single start/stop cycle at a time. It shouldn't matter whether a component is mounting, updating, or unmounting."

```tree caption="The same four user actions seen from the component vs. seen from the Effect: four component lifecycle moments vs. three room connections."
Four user actions across three rooms
- !The component's perspective [`ChatRoom`] | 1. Mounted with `general` | 2. Updated with `travel` | 3. Updated with `music` | 4. Unmounted
- +The Effect's perspective [`useEffect`] | 1. Connected to `general`, until it disconnected | 2. Connected to `travel`, until it disconnected | 3. Connected to `music`, until it disconnected
```

### Writing the Effect in ChatRoom.jsx

Here is the `ChatRoom` component file that holds this Effect:

```jsx title="src/components/ChatRoom.jsx"
import { useEffect } from 'react';
import { createConnection } from '../chat.js';

const ~serverUrl~ = 'https://localhost:1234'; // Fixed server address outside the component

export default function ChatRoom({ ~roomId~ }) { // "general", "travel", or "music" from App
  useEffect(() => {
    const connection = ~createConnection~(serverUrl, roomId); // Builds the connection object for this room
    connection.~connect~(); // Starts synchronizing with this room
    return () => {
      connection.~disconnect~(); // Stops synchronizing with this room
    };
  }, [roomId]);
  return <h1>Welcome to the {roomId} room!</h1>;
}
```

At the top of the file, `serverUrl` is a constant holding `'https://localhost:1234'`. It sits outside `ChatRoom` because the server address never changes between renders. At the bottom, `ChatRoom` returns the heading with the current `roomId`. Meanwhile, the Effect starts and stops the connection to the chat server for that room.

When an Effect does not return a cleanup function at all, the docs state that "React will behave as if you returned an empty cleanup function." Yes, for React's start and stop cycle they are **the exact same thing**: React still runs a stop step, and that step does nothing. For the chat room, returning no cleanup means nothing ever calls `disconnect`, so every room connection stays open.

### One component mount produces three connections

**Beware! Across these four clicks, `ChatRoom` mounts only once, yet the Effect connects three separate times.** Follow the four user actions in order in a production build:
1. **The user clicks the Open chat button.** The parent renders `ChatRoom` for the first time with `roomId` set to "general". `ChatRoom` mounts, puts the general welcome heading on the page, and runs the Effect's setup function, which connects to the `general` room.
2. **The user picks `travel` in the menu.** The parent passes `roomId` set to "travel" to the same `ChatRoom` component. `ChatRoom` does not unmount or mount again; it updates its heading in place to the travel welcome heading. React then calls the previous cleanup function, which disconnects from the `general` room, and runs the new setup function, which connects to the `travel` room.
3. **The user picks `music` in the menu.** `ChatRoom` updates its heading in place to the music welcome heading. React calls the cleanup function from the `travel` render, disconnecting from that room. Then React runs the setup function for the `music` render, connecting to the `music` room.
4. **The user clicks the Close chat button.** `App` stops rendering `ChatRoom`. `ChatRoom` unmounts, and React calls the cleanup function one last time, disconnecting from the `music` room.

Here is the browser and the Console after the first three actions, once the user has opened the chat, picked `travel`, and picked `music`:

If you inspect the heading in the browser's Elements panel while switching rooms, the heading DOM node is never removed or recreated. Only its text changes from room to room. This Console trace shows a production build. In development, Strict Mode runs one extra setup and cleanup cycle on mount to test the cleanup, which Principle 2 traces step by step.

### Why thinking from the component's lifecycle leads to a bug

Thinking from the component's lifecycle instead of the Effect's start and stop cycle leads directly to a broken chat room:
1. A developer looks at `ChatRoom` and thinks: I want to connect when the component mounts, and disconnect when it unmounts.
2. That thought treats setup as "mount code" and cleanup as "unmount code", so the developer writes an empty dependency array `[]` (as seen in Lesson 32).
3. When the user clicks the Open chat button, `ChatRoom` mounts with `roomId` set to "general". The Effect connects to the `general` room.
4. When the user picks `travel` in the menu, `ChatRoom` does not unmount and does not mount again. It updates in place. Because the developer only thought about mount and unmount, the Effect never disconnects from `general` and never connects to `travel`. Principle 3 fixes the dependency array itself.

The docs summarize the mindset that prevents this bug: "All you need to do is to describe how to start synchronization and how to stop it. If you do it well, your Effect will be resilient to being started and stopped as many times as it's needed." They compare this to writing JSX: when you write the tags a component returns, you do not ask whether the component is mounting or updating. You describe what should be on the screen, and React figures out the rest. As the docs put it: "The Effect is *also* a part of the rendering output." And as the docs conclude: "When your cleanup logic correctly "mirrors" the setup logic, your Effect is resilient to running setup and cleanup as often as needed."

> [!PRINCIPLE]
> **Principle 1: The Effect Connects to One Room Until It Disconnects**
>
> *Always focus on a single start and stop cycle at a time. Describe how to start synchronization in the setup function and how to stop it in the cleanup function, whether the component is mounting, updating, or unmounting.*
>
> From the component's perspective, opening the chat, switching rooms twice, and closing the chat is one mount, two updates, and one unmount. From the Effect's perspective, it is three start and stop cycles in a row, one for "general", one for "travel", and one for "music". When the cleanup mirrors the setup, React can start and stop the Effect whenever the room changes.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   ~return () => connection.disconnect();~ // Stops the room connection that this setup started
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[]~); // **WRONG:** treats the Effect as mount and unmount, so switching rooms never reconnects
> ```
