# Lecture 49: Measuring Before the Paint with useLayoutEffect, and Why useInsertionEffect Belongs to Style Libraries

*(How can a tooltip measure itself and find its place before the user sees it?)*

> INTERVIEW QUESTION | ❱❱ MORE | When must code run after DOM updates but before the browser paints, and why is useInsertionEffect reserved for style libraries?

---

## VS | `useEffect` vs. `useLayoutEffect`: the same code, but only one runs before the user sees the screen

> When React changes the page, the browser draws the new screen a moment later, and `useEffect` usually runs only after that drawing. **When your code measures an element and then moves it, put that code in `useLayoutEffect`, which runs after React changes the page but before the browser draws it.** Otherwise the user sees the element in the wrong place first, and then sees it jump.

Remember how plain JavaScript works when you add an element to the page? You create it, you append it, you measure it, you move it. The user never sees the element in the wrong place, because the browser does not draw anything while your script is still running. It draws the screen only after the script ends:

```js title="Plain JavaScript: add, measure, and move, all before the browser draws"
const tip = document.createElement('div');
tip.textContent = 'Delete this draft for good';
document.body.appendChild(tip); // The tooltip is in the DOM, but not on the screen yet
const height = tip.~getBoundingClientRect~().height; // The browser measures it right now
tip.style.top = buttonTop - height + 'px'; // Moves it above the button, and only then does the browser draw
```

In React, you do not append elements yourself. React creates them from your JSX and puts them into the DOM for you. So the question becomes: when does your measuring code run? React gives you two Hooks for code that runs because a component is on the screen, and they answer that question differently:
- **`useEffect`** usually runs after the browser has drawn the screen. The user may already see the tooltip in its first, wrong place.
- **`useLayoutEffect`** runs after React has put the tooltip into the DOM, but before the browser draws. It gives you back the moment you had in plain JavaScript.

```jsx title="React: the same measuring line in the two Hooks"
~useEffect~(() => { setTooltipHeight(ref.current.getBoundingClientRect().height); }, []); // The browser may draw the tooltip before this runs
~useLayoutEffect~(() => { setTooltipHeight(ref.current.getBoundingClientRect().height); }, []); // The browser waits until this runs and React renders again
```

> [!DEFINITION]
> **The commit and the paint.** [REVIEW] After React calls your component, it changes the DOM to match the JSX: this is the commit. A moment later, the browser draws the new DOM on the screen: this is the paint. Between the two, the DOM has changed, but the user still sees the old screen (Lesson 13).

Take a document editor with two buttons, `Save` at the very top of the window and `Delete` lower down. When the user moves the pointer onto a button, a small dark label appears next to it, such as `Delete this draft for good`. This label is a **tooltip**. It goes above its button when there is room, and below it when there is not. Ask yourself: how can our code know whether the tooltip fits above the button? It must know how tall the tooltip is. And the tooltip has a height only once it is in the DOM.

**Why:** With `useEffect`, the browser may draw the tooltip before our code has measured it. On a slow phone, the user sees the tooltip right on top of the button, covering it, and a moment later sees it jump to its place above. The React docs describe exactly this: "you might notice that sometimes the tooltip 'flickers' and you briefly see its initial position before the corrected position." On a fast computer the wrong place stays on the screen too briefly to notice. So the developer never sees the bug, and the user on a slow phone sees it on every hover.

> [!DEFINITION]
> **A flicker.** [NEW] A flicker is a visible jump on the screen: the user sees an element in one place, and a moment later in another. It happens when the browser paints a first, wrong version of the page before our code corrects it (Lesson 49).

Remember the one sentence of this lesson. **`useEffect` usually runs after the user sees the screen, and `useLayoutEffect` runs before. Code that measures the page and moves something goes in `useLayoutEffect`. Everything else stays in `useEffect`.**

### Three Hooks, Three Moments

React gives three Hooks for code that runs because a component is on the screen. They take the same arguments. They differ only in the moment React runs them:
1. **`useEffect`** fits almost every Effect: a connection to a server, a timer, a subscription, a log, a data fetch. The React docs say that running an Effect before the paint "shouldn't be needed for the vast majority of Effects."
2. **`useLayoutEffect`** fits code that measures the page and renders again before the user sees the screen, such as placing a tooltip. The React docs: "You can measure layout here." An Effect written with this Hook is called a **layout Effect**.
3. **`useInsertionEffect`** fits only a CSS-in-JS library, a library that lets a team write its styles in JavaScript, when it adds `<style>` tags to the page while the app runs. The React docs: "Libraries can insert dynamic CSS here."

```tree dir=right caption="The order in which React runs the three Effect Hooks around the paint."
When React runs each Effect Hook after a commit
- +1. `useInsertionEffect` | Runs **before any layout Effect** | A style library adds its `<style>` tags
- +2. `useLayoutEffect` | Runs **before the browser paints** | Our code measures the page and sets state
- +3. The browser paints | The user **sees the screen**
- +4. `useEffect` | Usually runs **after the paint** | Connections, timers, logs, data fetching
```

What is at stake is what the user sees:
1. **With `useEffect` for a measurement**, the tooltip is painted on top of the button and then jumps, on every hover.
2. **With `useLayoutEffect` for everything**, every update waits for all that code before the screen changes. The React docs warn: "When used excessively, this makes your app slow."
3. **With a style library that adds its styles too late**, our code measures the tooltip before its styles apply, and the tooltip lands in the wrong place. The React docs: "layout calculations in regular Effects would be wrong due to outdated styles."

### The Rule of Thumb: would the user see the wrong place?

**Ask one question about every Effect: if the browser painted before this code ran, would the user see something in the wrong place? If not, use `useEffect`. If yes, use `useLayoutEffect`. Use `useInsertionEffect` only when you write a style library.**

A senior developer also knows the four classic mistakes:
1. **Believing `useEffect` always runs before the user sees anything**, because it runs after the commit. The commit only changes the DOM. The paint is a separate moment.
2. **Using `useLayoutEffect` for every Effect "to be safe".** Every millisecond inside it is a millisecond with no paint.
3. **Fetching data in `useLayoutEffect`** to get it sooner. The answer from the server arrives no sooner.
4. **Using `useInsertionEffect` in our own components.** It cannot read refs and cannot set state, so it is a tool for style libraries only.

**PRINCIPLES:** `useEffect` usually runs after the browser paints. When an Effect measures the page and moves something, the user can see the wrong place first. React gives two earlier moments, one for our code and one for style libraries. Four principles follow:
1. **Principle 1: `useEffect` Lets the Browser Paint Before the Measurement.** The user sees the tooltip on top of the button, then sees it jump.
2. **Principle 2: `useLayoutEffect` Measures and Renders Again Before the Paint.** The tooltip still renders twice, but the user sees only the second render.
3. **Principle 3: `useLayoutEffect` Holds Back the Paint of the Whole Page.** Only a measurement is worth that wait. A log, a timer, or a fetch stays in `useEffect`.
4. **Principle 4: `useInsertionEffect` Adds the Style Rule Before Any Measurement.** A style library adds its `<style>` tags before any layout Effect measures, and our own components have no use for it.

## PRINCIPLE | `useEffect`: the browser may paint the tooltip before the Effect measures it

> [!PRINCIPLE]
> **Principle 1: `useEffect`: The Browser May Paint Before the Effect Runs**
>
> *When an Effect measures an element and sets state to move it, `useEffect` may let the browser paint the first, wrong position, so the user sees the element jump.*
>
> The tooltip has no height until React commits it to the DOM, so the first render has to guess. With `useEffect`, the browser may paint that guess before the Effect measures the real height. The user sees the tooltip on top of the button, then sees it jump. On a fast computer the jump is too short to notice, which is why it reaches users on slow phones.
>
> **DO THIS:**
> ```jsx
> ~useLayoutEffect~(() => { // The measurement runs before the browser paints, as Principle 2 shows
>   const { height } = ref.current.getBoundingClientRect();
>   setTooltipHeight(height);
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const { height } = ref.current.getBoundingClientRect();
>   ~setTooltipHeight(height)~; // **WRONG:** the browser may already have painted the tooltip on top of the button
> }, []);
> ```

Start with the smallest tooltip that measures itself. It receives `buttonRect`, the position of its button on the screen. We will see where that comes from in a moment:

```jsx title="A tooltip that measures its own height in useEffect"
const [tooltipHeight, setTooltipHeight] = useState(0); // No height exists before the first commit

~useEffect~(() => { // Runs after the commit, usually after the paint
  const { height } = ref.current.~getBoundingClientRect~(); // The browser measures the tooltip in the DOM
  setTooltipHeight(height); // Asks React for a second render with the real height
}, []);

let top = buttonRect.top - tooltipHeight; // Above the button
if (top < 0) {
  top = buttonRect.bottom; // No room above, so below the button
}
```

The plan is simple. Take the top of the button, subtract the height of the tooltip, and that is where the tooltip starts. If that number is below zero, the tooltip would stick out of the window, so it goes under the button instead.

> [!DEFINITION]
> **Layout and `getBoundingClientRect()`.** [NEW] Layout is the position and the size of every element, which the browser works out from the DOM and the CSS. `getBoundingClientRect()` is a method the browser gives every element: it measures the element and returns an object called a `DOMRect`, with numbers in pixels such as `top`, `bottom`, `left`, and `height`. Each number is measured from the edges of the viewport, the part of the browser window that shows the page. Measuring an element means reading its layout (Lesson 49).

The curly braces on the left of the measuring line take the `height` field out of that object, the same unpacking we use for props (Lesson 08).

### Our First Step: the Editor Page

`App` shows the two buttons with a blank space between them:

```jsx title="src/App.jsx"
import ButtonWithTooltip from './ButtonWithTooltip.jsx';
import './styles.css';

export default function App() {
  return (
    <main>
      <ButtonWithTooltip label="Save" tooltip="Save your draft" />
      ~<div style={{ height: 100 }} />~ {/* A blank space of 100 pixels between the two buttons */}
      <ButtonWithTooltip label="Delete" tooltip="Delete this draft for good" />
    </main>
  );
}
```

`ButtonWithTooltip` shows one button, and the tooltip only while the pointer is on it:

```jsx title="src/ButtonWithTooltip.jsx"
import { useState, useRef } from 'react';
import Tooltip from './Tooltip.jsx';

export default function ButtonWithTooltip({ label, tooltip }) {
  const buttonRef = useRef(null);
  const [buttonRect, setButtonRect] = useState(null);

  function handlePointerEnter() {
    setButtonRect(buttonRef.current.~getBoundingClientRect~()); // Remembers where the button is on the screen
  }

  function handlePointerLeave() {
    setButtonRect(null); // Removes the tooltip
  }

  return (
    <div>
      <button ref={buttonRef} onPointerEnter={handlePointerEnter} onPointerLeave={handlePointerLeave}>
        {label}
      </button>
      {buttonRect !== null && <Tooltip text={tooltip} buttonRect={buttonRect} />}
    </div>
  );
}
```

The browser fires `onPointerEnter` when the user moves the pointer onto the button, and `onPointerLeave` when the user moves it off. `handlePointerEnter` measures the button, the same way we measured a DOM element in an event handler before (Lesson 31). The result goes into `buttonRect`, and React passes it to `Tooltip` as a prop. That is where `buttonRect` comes from.

`Tooltip` measures itself in `useEffect` and chooses above or below:

```jsx title="src/Tooltip.jsx" startLine="1"
import { useState, useRef, useEffect } from 'react';

export default function Tooltip({ text, buttonRect }) {
  const ref = useRef(null);
  const [tooltipHeight, setTooltipHeight] = useState(0); // Our guess: no height exists before the first commit

  ~useEffect~(() => { // Runs after the commit, usually after the paint
    const { height } = ref.current.getBoundingClientRect(); // Reads the real height of the tooltip
    setTooltipHeight(height);
  }, []);

  let top = buttonRect.top - tooltipHeight;
  if (top < 0) {
    top = buttonRect.bottom;
  }

  return (
    <div
      ref={ref}
      className="tooltip"
      style={{ position: 'fixed', left: buttonRect.left, top: top, pointerEvents: 'none' }}
    >
      {text}
    </div>
  );
}
```

React puts the `<div>` of the tooltip into `ref.current` during the commit. So the Effect, which runs after the commit, can read it. The render, which runs before the commit, cannot.

Two style values here are new:
- **`position: 'fixed'`** places the tooltip at `left` and `top` pixels, measured from the edges of the viewport. `getBoundingClientRect()` measures from the same edges, so the numbers match.
- **`pointerEvents: 'none'`** lets the pointer pass through the tooltip. Without it, a tooltip painted over the button would take the pointer away from the button, and the browser would fire `onPointerLeave`.

The `.tooltip` rule in `styles.css` gives the tooltip its look:

```css title="src/styles.css"
.tooltip {
  background: #222;
  color: white;
  ~padding: 4px~; /* Part of the height of the tooltip */
  border-radius: 4px;
}
```

### Why the Tooltip Covers the Button First

**Beware! With `useEffect`, the user can see one tooltip in two places: first on top of the button, then in its real place.** The first render has no height to work with, and the browser may paint that render before the Effect fixes it.

Here is what happens when the user moves the pointer onto `Delete`:
1. `handlePointerEnter` stores the rectangle of the button in `buttonRect`.
2. React renders `Tooltip` with `tooltipHeight` at `0`, so `top` is the top of the button itself.
3. React commits the tooltip to the DOM, on top of the button.
4. The browser paints. The user sees `Delete this draft for good` covering the `Delete` button.
5. `useEffect` runs, measures the real height of the tooltip, and calls `setTooltipHeight`.
6. React renders `Tooltip` again with the real height. Now `top` is above the button.
7. React commits, the browser paints again, and the tooltip jumps above the button.



On `Save`, the jump goes the other way. At first the tooltip covers the button, then it moves below it, because the top edge of the window leaves no room above.

The browser does not paint before the Effect every time. The React docs say that when an Effect was not caused by an interaction such as a click, React will generally let the browser paint the updated screen first. Even after a click, React "may allow the browser to repaint the screen before processing the state updates inside your Effect." So the jump does not show on every hover of every device, and that is exactly what makes it hard to catch.

### Making the Jump Easy to See

On a fast computer, the wrong place may stay on the screen too briefly to notice. To show the bug, the React docs slow the render down on purpose, with a loop that does nothing for 100 milliseconds:

```jsx title="src/Tooltip.jsx, slowed down on purpose, inside the component body"
let now = ~performance.now()~; // The current time in milliseconds
while (performance.now() - now < 100) {} // Wastes 100 milliseconds on every call of Tooltip
```

`performance.now()` is a browser function that returns the time in milliseconds. No real app has this loop. It only imitates a slow phone. In development, Strict Mode calls the component twice for each render, so each render takes about 200 milliseconds. The browser has already painted the first, wrong place, so it stays on the screen for the whole second render, long enough to see the tooltip covering `Delete`.

### A Real Beginner Mistake: Hiding the Jump with a Fade-In

1. A developer builds the tooltip with `useEffect`, as Lesson 32 taught for code that runs because a component is on the screen.
2. On the fast computer of the developer, the tooltip looks right.
3. Users on slower phones report a tooltip that "blinks" or "jumps" on every hover.
4. The developer cannot see it locally, and adds a short CSS fade-in so the wrong place is harder to notice.

The fade-in hides the wrong place. It does not remove it: the browser still paints the tooltip on top of the button first. The fix is to measure before the paint, which is the next principle.

## PRINCIPLE | `useLayoutEffect`: the measurement and the new render both happen before the paint

> [!PRINCIPLE]
> **Principle 2: `useLayoutEffect`: Measure and Render Again Before the Paint**
>
> *When an Effect measures layout and sets state that changes what the user sees, write it with `useLayoutEffect`; React runs it after the commit and before the paint, and renders its state update before the paint too.*
>
> `useLayoutEffect` takes the same arguments as `useEffect`. Only the moment differs. React runs it right after the DOM is updated, and holds the paint until it is done and every state update it asked for has been rendered. The tooltip still renders twice, and the user sees only the second render.
>
> **DO THIS:**
> ```jsx
> useLayoutEffect(() => {
>   const { height } = ref.current.getBoundingClientRect();
>   ~setTooltipHeight(height)~; // React renders again before the browser paints
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const ref = useRef(null);
> const { height } = ~ref.current~.getBoundingClientRect(); // **WRONG:** measured during rendering, ref.current is null on the first render
> ```

Here are the two measuring Effects side by side:

```jsx title="The measuring Effect with useEffect"
~useEffect~(() => { // Usually runs after the paint
  const { height } = ref.current.getBoundingClientRect();
  setTooltipHeight(height); // The browser may paint the tooltip on top of the button before this runs
}, []);
```

```jsx title="The measuring Effect with useLayoutEffect"
~useLayoutEffect~(() => { // Runs before the paint
  const { height } = ref.current.getBoundingClientRect();
  setTooltipHeight(height); // React renders again with this height before the browser paints
}, []);
```

First, the arguments. Both Hooks take a setup function, an optional dependency array, and an optional cleanup that the setup returns. **Yes, it is the exact same thing!** Everything Lesson 32 taught about the setup, the empty array, and the cleanup holds for `useLayoutEffect` too.

Now the moment. **It looks the same, but it is NOT the same thing!** With `useEffect`, the browser may paint the wrong place first. With `useLayoutEffect`, the React docs guarantee that "the code inside `useLayoutEffect` and any state updates scheduled inside it will be processed before the browser repaints the screen."

> [!DEFINITION]
> **`useLayoutEffect`.** [NEW] `useLayoutEffect` is, in the words of the React docs, "a version of `useEffect` that fires before the browser repaints the screen." React provides it, and we import it from `react`, like `useEffect`. It takes the same setup function, dependency array, and cleanup. An Effect written with it is called a layout Effect (Lesson 49).

```tree caption="useEffect and useLayoutEffect take the same arguments and differ only in when React runs them."
`useEffect` and `useLayoutEffect` side by side
- +The same arguments [`setup` `dependencies` `cleanup`] | Both take a **setup function**, an optional **dependency array**, and an optional **cleanup** | **The exact same thing**
- !With `useEffect` [`useEffect`] | Usually runs **after the paint** | The user can see the **first, wrong place**
- +With `useLayoutEffect` [`useLayoutEffect`] | Runs **before the paint**, and React renders its state updates **before the paint** too | The user sees **only the final place**
```

### Our Second Step: One Word in the Tooltip File

`Tooltip` imports `useLayoutEffect` instead of `useEffect`, and changes that one word. To see when the Effect runs, we also log the height, as the React docs do. No other file changes:

```jsx title="src/Tooltip.jsx" startLine="1" good="7"
import { useState, useRef, useLayoutEffect } from 'react';

export default function Tooltip({ text, buttonRect }) {
  const ref = useRef(null);
  const [tooltipHeight, setTooltipHeight] = useState(0);

  ~useLayoutEffect~(() => { // Runs after the commit and before the paint
    const { height } = ref.current.getBoundingClientRect();
    console.log('Measured tooltip height: ' + height);
    setTooltipHeight(height);
  }, []);
```

### Why the User Never Sees the First Place

**The user never sees the first place, because the browser does not paint until React has rendered the tooltip a second time.** The tooltip still renders twice. Only the second render reaches the screen.

Here is what happens when the user moves the pointer onto `Delete`:
1. React renders `Tooltip` with `tooltipHeight` at `0`.
2. React commits the tooltip to the DOM, on top of the button.
3. Before the browser paints, React runs the setup of `useLayoutEffect`.
4. The setup measures the real height and calls `setTooltipHeight`.
5. React renders `Tooltip` again at once, with the real height, and commits the new `top`.
6. The browser paints for the first time. The user sees the tooltip above `Delete`.

No line of our code renders a second time. `setTooltipHeight` asks for it, and React does it before the paint, because the setter was called inside a layout Effect. The React docs call this **rendering in two passes**: render once in a wrong place, measure, and render again in the right place, all before the user sees anything.

```tree dir=right caption="Rendering in two passes: both renders happen before the browser paints once."
The pointer moves onto `Delete` with `useLayoutEffect`
- !1. First render | `tooltipHeight` is `0` | The tooltip is committed **on top of the button**
- +2. Layout Effect | Measures the **real height** | Calls `setTooltipHeight`
- +3. Second render | `top` is now **above the button** | React commits the new `top`
- +4. The browser paints once | The user sees **only the final place**
```

Keep the 100 millisecond loop from the React docs in the render, and the tooltip still appears straight in its final place, only later. The React docs suggest exactly this test: change the example to `useLayoutEffect` "and observe that it blocks the paint even if rendering is slowed down."

### A Real Beginner Mistake: Measuring During Rendering

A developer reads that `useLayoutEffect` runs before the paint, and decides that measuring during rendering would be even earlier, and simpler. So the developer measures in the body of the component:

```jsx title="src/Tooltip.jsx, measuring in the component body"
const ref = useRef(null);
const { height } = ~ref.current~.getBoundingClientRect(); // **WRONG:** on the first render ref.current is still null
```

The page opens with its two buttons as before. When the user moves the pointer onto a button, React renders `Tooltip` for the first time. `ref.current` is still `null`, because React has not committed the `<div>` yet. The whole page goes blank, and the Console shows the error:

```devconsole
x Uncaught TypeError: Cannot read properties of null (reading 'getBoundingClientRect')
! An error occurred in the <Tooltip> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

Rendering only returns JSX. The `<div>` of the tooltip, and its height, exist only after the commit. That is why the first render must work with a guess, and why the measurement belongs in a layout Effect.

## PRINCIPLE | `useLayoutEffect`: everything inside it holds back the paint of the whole page

> [!PRINCIPLE]
> **Principle 3: Blocking the Paint: Keep `useEffect` as the Default**
>
> *Keep `useEffect` as the default, and use `useLayoutEffect` only to measure layout and render again before the user sees the screen, because everything in it delays the paint of the whole page.*
>
> A layout Effect makes the browser wait. That wait is worth it only when the user would otherwise see a wrong place, as with the tooltip. A log, a timer, a connection, or a fetch gives the same screen either way, so in a layout Effect it only makes every update slower.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   ~console.log('Tooltip shown')~; // Runs after the paint; the user never waits for it
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useLayoutEffect(() => {
>   ~fetch('/api/drafts')~; // **WRONG:** the data arrives no sooner, and the paint waits for this code
> }, []);
> ```

### VS | A Measurement vs. a Log: both are Effects, only one changes what the user sees

The tooltip works now. Suppose we also want to log each time a tooltip appears. Here are two Effects in the same component:

```jsx title="Two Effects in the tooltip"
useLayoutEffect(() => {
  ~setTooltipHeight~(ref.current.getBoundingClientRect().height); // Changes where the user sees the tooltip
}, []);

useEffect(() => {
  ~console.log('Tooltip shown')~; // Changes nothing on the screen
}, []);
```

Both are Effects, and both run when the tooltip appears. A developer who has just fixed one jump with `useLayoutEffect` may put both there. They feel like the same kind of code, **but they are NOT the same thing!** The difference is what the user sees:
- **The measurement** changes where the user sees the tooltip. If the browser paints before it runs, the user sees the wrong place.
- **The log** gives the same screen whether it runs before or after the paint. Making the browser wait for it only costs time.

The React docs name this cost: "The code inside `useLayoutEffect` and all state updates scheduled from it block the browser from repainting the screen." To **block the paint** means the browser draws nothing new on the screen until that code is done.

```tree caption="Which Effects belong in useLayoutEffect and which stay in useEffect."
Where an Effect belongs
- +`useLayoutEffect` [`getBoundingClientRect`] | A measurement that **moves what the browser is about to paint** | The user would see the **wrong place** if the browser painted first
- +`useEffect` [`console.log` `setInterval` `fetch`] | A log, a timer, a connection, a data fetch | The screen is **the same** before or after the paint, so the browser **need not wait**
```

### Our Third Step: the Slow Code Moves into the Layout Effect

To see the cost, move the 100 millisecond loop out of the render and into the layout Effect of `Tooltip`:

```jsx title="src/Tooltip.jsx, the slow loop inside the layout Effect" bad="2,3"
useLayoutEffect(() => {
  let now = performance.now();
  ~while~ (performance.now() - now < 100) {} // **WRONG:** the browser paints nothing until this loop ends
  setTooltipHeight(ref.current.getBoundingClientRect().height);
}, []);
```

**For 100 milliseconds after the pointer moves onto `Delete`, nothing on the page changes.** The tooltip never jumps, but it always arrives late. In development, Strict Mode runs the setup a second time, so the wait doubles to about 200 milliseconds.

Here is what happens:
1. The user moves the pointer onto `Delete`.
2. React renders and commits the tooltip, then runs the layout Effect.
3. The loop runs for 100 milliseconds. During that time the browser paints nothing at all, anywhere on the page.
4. The loop ends, React renders the tooltip in its final place, and the browser paints.

A real app has no such loop. It has real work instead: filtering a long list, a heavy calculation, many small Effects. In a layout Effect, every millisecond of that work is a millisecond with no paint, on every update that runs it.

A layout Effect does not make data arrive sooner either. The Effect only sends the request. The browser paints, and the answer from the server comes later, exactly as it does from `useEffect` (Lesson 33). Moving the fetch into a layout Effect only makes the paint wait while the request is sent.

### A Real Beginner Mistake: One Flicker, One Team Rule

1. A developer fixes one flickering tooltip with `useLayoutEffect`.
2. Someone writes a team rule: "use `useLayoutEffect` to avoid flicker".
3. Over months, connections, logs, and the filtering of long lists move into layout Effects.
4. Every click now waits for all of them before the screen changes. The app feels slow, with no error anywhere.

The React docs put it plainly: "`useLayoutEffect` can hurt performance. Prefer `useEffect` when possible." They also say: "Rendering in two passes and blocking the browser hurts performance. Try to avoid this when you can."

## PRINCIPLE | `useInsertionEffect`: a style library adds its `<style>` tags before any layout Effect measures

> [!PRINCIPLE]
> **Principle 4: `useInsertionEffect`: For CSS-in-JS Libraries Only**
>
> *A CSS-in-JS library that adds `<style>` tags while the app runs adds them in `useInsertionEffect`, which React runs before any layout Effect; application code does not use it, because it can neither read refs nor set state.*
>
> A measurement is right only if the styles are already in the page. When a library adds its rule in a layout Effect, a measuring layout Effect can run first and read a height without the padding. `useInsertionEffect` runs before every layout Effect, so the rule is always in the page first.
>
> **DO THIS:**
> ```js
> function useCSS(rule) {
>   ~useInsertionEffect~(() => { // Library code: the rule is in the page before any layout Effect measures
>     if (!inserted.has(rule)) {
>       inserted.add(rule);
>       const style = document.createElement('style');
>       style.textContent = rule;
>       document.head.appendChild(style);
>     }
>   });
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useInsertionEffect(() => {
>   setTooltipHeight(~ref.current~.getBoundingClientRect().height); // **WRONG:** refs are not attached yet, and state cannot be set here
> }, []);
> ```

### Three Effects, One Order

Here is one component with all three Effect Hooks, written in the order `useEffect`, `useLayoutEffect`, `useInsertionEffect`:

```jsx title="src/EffectOrder.jsx" startLine="1"
import { useEffect, useLayoutEffect, useInsertionEffect } from 'react';

export default function EffectOrder() {
  ~useEffect~(() => { console.log('effect'); }); // Written first, runs last
  ~useLayoutEffect~(() => { console.log('layout'); }); // Runs before the paint
  ~useInsertionEffect~(() => { console.log('insertion'); }); // Written last, runs first
  return <p>Hello</p>;
}
```

The Console prints `insertion`, then `layout`, then `effect`, whatever the order in the code. React runs `useInsertionEffect` "before any layout Effects fire", layout Effects before the paint, and `useEffect` usually after the paint:

```page caption="The EffectOrder component on the dev server: insertion comes first, and Strict Mode runs layout and effect a second time."
line: Hello
log: insertion | EffectOrder.jsx:6
log: layout | EffectOrder.jsx:5
log: effect | EffectOrder.jsx:4
log: layout | EffectOrder.jsx:5
log: effect | EffectOrder.jsx:4
```

In development, Strict Mode runs one extra setup and cleanup for the layout Effect and for `useEffect`, so `layout` and `effect` appear twice. It does not run `useInsertionEffect` again, so `insertion` appears once. A production build prints only the first three lines.

> [!DEFINITION]
> **`useInsertionEffect`.** [NEW] `useInsertionEffect`, in the words of the React docs, "allows inserting elements into the DOM before any layout Effects fire". React provides it, and we import it from `react`. It takes the same arguments as the other two Effect Hooks. Its job is narrow: adding `<style>` tags to the page before any component measures (Lesson 49).

### Styles That Arrive While the App Runs

So far, the `.tooltip` rule lives in a CSS file. Some teams write their styles in JavaScript instead, with a **CSS-in-JS library**. Some of these libraries add their CSS to the page while the app runs. The library creates a `<style>` element, the HTML element that holds CSS rules, and adds it to the `<head>` of the page. The React docs call this **runtime injection of `<style>` tags**.

The React docs do not recommend runtime injection. They recommend CSS files for styles that never change, and inline styles for styles that do. One reason they give: "Runtime injection forces the browser to recalculate the styles a lot more often." To recalculate the styles means the browser works out again which CSS rules apply to every element. `useInsertionEffect` exists for the libraries that inject anyway, so their rules arrive at the right moment.

In this lesson, a small file plays the part of such a library. It is library code, written here so we can see what the library does. Our own application code would not write this file.

### Our Fourth Step: the Tooltip Rule Moves into Library Code

First, the library adds its rule in a layout Effect, the way a developer would guess:

```js title="src/useCSS.js, library code" startLine="1"
import { useLayoutEffect } from 'react';

const inserted = new Set(); // Remembers which rules are already in the page

export default function useCSS(rule) {
  ~useLayoutEffect~(() => { // Library code: adds the rule in a layout Effect
    if (!inserted.has(rule)) {
      inserted.add(rule);
      const style = document.createElement('style');
      style.textContent = rule;
      document.head.appendChild(style); // The rule is now in the page
    }
  });
}
```

`useCSS` is a custom Hook (Lesson 39). The React docs write the same Hook "Inside your CSS-in-JS library". A few names in this file are new:
- **`inserted`** is a `Set`, a JavaScript collection that holds each value once. `has` checks for a rule, and `add` stores it. JavaScript creates the `Set` once, when the file loads, so each rule is added once, however many tooltips call `useCSS`.
- **`document.createElement('style')`** makes a new `<style>` element. `textContent` puts the CSS text inside it. `appendChild` adds it to the `<head>` of the page.

The CSS file loses its `.tooltip` rule, and `App` no longer imports it. `Tooltip` calls `useCSS` with the rule, below its measuring layout Effect:

```jsx title="src/Tooltip.jsx" startLine="1"
import { useState, useRef, useLayoutEffect } from 'react';
import useCSS from './useCSS.js';

export default function Tooltip({ text, buttonRect }) {
  const ref = useRef(null);
  const [tooltipHeight, setTooltipHeight] = useState(0);

  useLayoutEffect(() => {
    const { height } = ref.current.getBoundingClientRect(); // Runs first: measures the tooltip
    setTooltipHeight(height);
  }, []);

  ~useCSS~('.tooltip { background: #222; color: white; padding: 4px; border-radius: 4px; }'); // Its layout Effect runs second
```

### Why the First Tooltip Covers the Top of Delete

**Beware! When the rule arrives after the measurement, the tooltip is measured without its padding, and it lands too low.** It covers the top of the `Delete` button by the height of that padding.

Here is what happens the first time the user moves the pointer onto `Delete` after the page loads:
1. React renders `Tooltip` and commits it. No `.tooltip` rule is in the page yet, so the tooltip has no padding.
2. The measuring layout Effect runs first, because it is written first, and reads a height without the padding.
3. The layout Effect of the library runs next and adds the `<style>` tag. The browser recalculates the styles, and the tooltip grows by its padding.
4. React renders with the smaller height. The tooltip sits too low by the padding and covers the top of `Delete`.

The next hover looks right, because `inserted` already holds the rule and the `<style>` tag is already in the page. So the bug shows only on the first hover after each page load, which makes it hard to reproduce. In development, Strict Mode runs the measurement a second time, after the rule is in the page, and that can hide the bug until the app reaches production.

This is what the React docs warn about: without `useInsertionEffect`, "layout calculations in regular Effects would be wrong due to outdated styles."

### VS | `useCSS` with `useLayoutEffect` vs. `useCSS` with `useInsertionEffect`: one word, and the rule is in the page before the measurement

The library changes one word, `useLayoutEffect` to `useInsertionEffect`:

```js title="src/useCSS.js, library code" startLine="1" good="6"
import { useInsertionEffect } from 'react';

const inserted = new Set();

export default function useCSS(rule) {
  ~useInsertionEffect~(() => { // Runs before any layout Effect in any component
    if (!inserted.has(rule)) {
      inserted.add(rule);
      const style = document.createElement('style');
      style.textContent = rule;
      document.head.appendChild(style);
    }
  });
}
```

The two versions differ by one word and behave alike on every later hover, **but they are NOT the same thing!** With `useLayoutEffect`, a measuring layout Effect can run before the rule is in the page. With `useInsertionEffect`, in the words of the React docs, "by the time other Effects run in your components, the `<style>` tags have already been inserted." The measurement now reads the full height, and the tooltip sits exactly above `Delete`, on the first hover too. The place where `Tooltip` calls `useCSS` no longer matters.

The tooltip looks the same as it did with the CSS file. The browser applies a CSS rule the same way, whether it came from a CSS file or from a `<style>` element that `useCSS` added. The only difference is the moment the rule exists.

The Elements panel shows the one `<style>` element that `useCSS` added:

```tree dir=right caption="The order on the first hover once useCSS uses useInsertionEffect."
- +2. Layout Effect | `Tooltip` measures the **full height** | Calls `setTooltipHeight`
- +3. Second render | `top` is **exactly above** the button
- +4. The browser paints | The user sees the tooltip **in its place**
```

### What `useInsertionEffect` Cannot Do

A developer reads that `useInsertionEffect` runs before `useLayoutEffect`, and moves the measurement of the tooltip into it, to run even earlier:

```jsx title="src/Tooltip.jsx, measuring in useInsertionEffect"
useInsertionEffect(() => {
  const { height } = ~ref.current~.getBoundingClientRect(); // **WRONG:** refs are not attached yet, so ref.current is null
  setTooltipHeight(height);
}, []);
```

It fails in two ways, and the React docs name both:
1. **No refs.** "By the time `useInsertionEffect` runs, refs are not attached yet." `ref.current` is still `null`, so the measurement throws the same error as measuring during rendering.
2. **No state.** "You can't update state from inside `useInsertionEffect`." React treats a state update there as a mistake in our code. In development, every call of `setTooltipHeight` from it prints this error in the Console:

```devconsole
x useInsertionEffect must not schedule updates.
```

So `useInsertionEffect` can neither read the page through a ref nor set state. All it can do is add something to the page before the layout Effects run. A style library needs exactly that, and no component of our app does. The React docs: "Unless you are working on a CSS-in-JS library and need a place to inject the styles, you probably want `useEffect` or `useLayoutEffect` instead."

### How React Calls the Components in Order

When the page loads, React calls `App`, then `ButtonWithTooltip` once for `Save` and once for `Delete`. No tooltip is on the page yet. When the user moves the pointer onto a button, React calls that `ButtonWithTooltip` again, and then `Tooltip`, whose Effects run in a fixed order:

```tree caption="The order in which React calls the components of the editor page, and the order of the Effects of the tooltip."
`App` [1. Called when the page loads] | Shows `Save`, the blank space, and `Delete`
- +`ButtonWithTooltip` for `Save` [2. Called second] | Shows the `Save` button
- +`ButtonWithTooltip` for `Delete` [3. Called third] | Shows the `Delete` button | The pointer moves onto `Delete`, so `buttonRect` is set
  - +`Tooltip` [4. Called on hover] | **Insertion Effect** adds the `.tooltip` rule | **Layout Effect** measures and sets the height | React renders **again**, then the browser **paints once**
```

| Hook | When React runs it | What belongs in it | What goes wrong when it is the wrong choice |
| :--- | :--- | :--- | :--- |
| **`useEffect`** | After the commit, usually after the paint | Connections, timers, subscriptions, logs, data fetching | A measurement here lets the user see the tooltip on top of the button, then see it jump |
| **`useLayoutEffect`** | After the commit, before the paint | A measurement that must change the page before the browser paints | Slow code here freezes the whole page; data arrives no sooner |
| **`useInsertionEffect`** | Before any layout Effect | A CSS-in-JS library adding `<style>` tags | Refs are not attached and state cannot be set, so application code has no use for it |

Remember the one sentence of this lesson. **`useEffect` usually runs after the user sees the screen, and `useLayoutEffect` runs before. Code that measures the page and moves something goes in `useLayoutEffect`. Everything else stays in `useEffect`.**

## For the Interview

> **The Interview Question:** When must code run after DOM updates but before the browser paints, and why is useInsertionEffect reserved for style libraries?

### How to Answer Clearly in 30 Seconds

"Code must run before the paint when it measures the page and moves something the user would otherwise see in the wrong place. The classic case is a tooltip that chooses above or below its button from its own height. `useEffect` usually runs after the paint, so the user can see the tooltip in the wrong place and then see it jump. `useLayoutEffect` takes the same arguments but runs after the commit and before the paint, and React renders its state updates before the paint too. So I follow three rules:
1. **`useEffect` is the default**: connections, timers, logs, and data fetching stay there.
2. **`useLayoutEffect` only for measurements**: everything in it blocks the paint, so it holds only code that prevents a visible jump.
3. **`useInsertionEffect` belongs to style libraries**: it runs before any layout Effect, so a CSS-in-JS library can add its `<style>` tags before any component measures. It cannot read refs or set state, so our own components have no use for it."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why not use `useLayoutEffect` for every Effect, to be safe?"**
   **Because it makes the browser wait.** The code inside a layout Effect and every state update it schedules block the paint of the whole page. A log or a connection gives the same screen before or after the paint, so running it in a layout Effect only makes every update slower. The React docs say running an Effect before the paint "shouldn't be needed for the vast majority of Effects."
2. **"Does `useLayoutEffect` run on the server?"**
   **No.** Effects only run in the browser, and the server has no layout to measure. So a component that depends on layout and is rendered on the server can still show the wrong place until the JavaScript loads and the layout Effect runs. The React docs suggest rendering such a component only in the browser, or using `useEffect` when a brief wrong place does not matter.
3. **"Can our own component use `useInsertionEffect` to measure even earlier?"**
   **No.** When `useInsertionEffect` runs, refs are not attached yet, so `ref.current` is `null`, and React does not allow state updates inside it. It can only add something to the page before the layout Effects run. That is the one job of a CSS-in-JS library that injects `<style>` tags. Even for those libraries, the React docs recommend CSS files and inline styles over runtime injection, because injection makes the browser recalculate the styles more often.

```tree dir=right caption="The three Effect Hooks in an interview answer: the default, the measurement, and the style library."
Three Effect Hooks, three jobs
- +`useEffect` | **The default** | Runs usually **after the paint**
- +`useLayoutEffect` | **Measure and render again** | Runs **before the paint** and **blocks** it
- +`useInsertionEffect` | **Style libraries only** | Runs **before any layout Effect**; no refs, no state
```
