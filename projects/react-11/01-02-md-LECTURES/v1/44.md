# Lecture 44: How a Like Shows Before the Server Confirms

*(How does the heart turn red before the server has saved the like?)*

> INTERVIEW QUESTION | ❱❱ MORE | How do you show the value the reader expects before the server confirms?

---

## VS | The Real State `liked` vs. the Optimistic State `optimisticLiked`: both draw the heart, only the optimistic one turns red before the server answers

> **`useOptimistic` lets the screen show the expected result right away, before the server confirms it.**

In React, many clicks wait for a server, like a like on a photo, a check on a to-do item, or a new message in a chat. Normally, we update the state when the server answers, so the screen waits too. But users expect the screen to change the moment they click. **`useOptimistic` shows the expected result at once, while the server is still saving, and goes back to the real state by itself if the save fails.**

Take a photo post with a white heart button under it. The user clicks the heart, and the server needs a second to save the like. Ask yourself: what should the heart show during that second? Red, the result the user expects, even though the real state `liked` is still false.

**Why:** If you set `liked` only after the server answers, the heart stays white for a second after every click, and the button feels broken. If you set `liked` to true before the server answers, you must write your own code to set it back when the network fails. See the problem? `useOptimistic` gives you a second value, `optimisticLiked`, that shows red during the save and goes back to the real `liked` when the action ends.

Now let's see why you would want that.

Open a photo post on Instagram. Under the photo sit its title and a white heart button:

```page caption="A photo post before the click: the title and a white heart button."

```

The user clicks the heart, and it turns red at once:

```page caption="The same post right after the click, while the server is still saving the like."

```

Behind the screen, the app sends the like to the server, and the server needs about one second to save it. The user never sees that second. For the user, the like is already done.

Now look at the same screen as the developer. The server has not answered yet, so your code does not know if the like is saved. Yet the heart is already red. The page shows the answer it hopes for.

You know this trick from plain JavaScript. You change the button first. Then you send the request. If the request fails, you change the button back:

```js title="page.js"
async function handleClick() {
  ~likeButton.textContent = '❤️ Liked'~; // 1. Change the button first, before the server answers
  const saved = await saveLike(true); // 2. Then wait one second for the server
  if (!saved) likeButton.textContent = '🤍 Like'; // 3. Change it back by hand if the save failed
}
```

In React, you never touch the button yourself. The button shows what your state says (Lesson 12). So during that one second, you need a value that says "liked", although the server has not saved anything yet.

Why does that second matter so much?
1. If the heart waits for the server, it stays white for one second after the click. The user thinks the click did not work, and clicks again.
2. If you turn the heart red with a plain `useState` and the save fails, the page keeps a red heart the server never saved. Only extra code of yours can turn it white again.

React gives you that value with a Hook called `useOptimistic`. First, two tools from earlier lessons that this lesson stands on:

> [!DEFINITION]
> **An Action.** [REVIEW] You pass a function to the `action` of a `<form>`: `<form action={submitAction}>`. When the user clicks the submit button, React calls `submitAction` for you, inside a Transition. That makes `submitAction` an Action.
> What matters in this lesson: React knows when the Action starts and when it ends. While it runs, we say the Action is pending (Lesson 41).

> [!DEFINITION]
> **useActionState.** [REVIEW] `useActionState` keeps the result of an Action in state. `const [liked, likeAction] = useActionState(updateLike, false)` gives you `liked`, which starts as `false`, and `likeAction`, which you call to start the save.
> React then calls your function `updateLike` with two values: the previous state first, and the value you passed to `likeAction` second. That second value is the payload.
> Whatever `updateLike` returns becomes the new `liked`. So `liked` changes only when the save ends (Lesson 42).

Now the new tool:

```jsx title="The real state and the optimistic state of one heart button"
const [liked, likeAction] = useActionState(updateLike, false); // The real state: changes when the save ends
const [optimisticLiked, setOptimisticLiked] = ~useOptimistic(liked)~; // The optimistic state: equals liked until an Action sets it
```

> [!DEFINITION]
> **useOptimistic and the optimistic state.** [NEW] `useOptimistic` is a React Hook. It comes from `'react'`, like `useState`. You give it the real state, here `liked`, and it gives you back a pair, which you name in square brackets, as with `useState`.
> `optimisticLiked` is the optimistic state. While no Action is pending, it simply equals `liked`. While an Action is pending, it equals the value your code passed to the set function.
> `setOptimisticLiked` is the set function. The docs say it "lets you update the state for the duration of an Action." The words "for the duration" matter: the value lives as long as the Action, and no longer.
> Why "optimistic"? An optimist expects things to go well. Here the page expects the save to succeed, so it shows the result before the server says so.
> The docs give the same reason: this state "is called the 'optimistic' because it is used to immediately present the user with the result of performing an Action, even though the Action actually takes time to complete" (Lesson 44).

So one heart button has two values behind it:
- **The real state, `liked`,** is what the server saved. It changes only when the server answers.
- **The optimistic state, `optimisticLiked`,** is what the page shows during the save. It holds the hoped-for answer.

Both are values that React keeps for the component, and the button can draw the heart from either one. The one difference is time. Before the click and after the save, the two hold the same value. Only during the one-second wait can they differ.

```tree caption="The real state and the optimistic state of one heart button: the same value, except during the wait."
Two values behind one heart button
- +The real state [`liked`] | Changes **only when the server answers** | Before the click and after the save, it decides what the heart shows
- +The optimistic state [`optimisticLiked`] | Holds the **hoped-for answer** while the save runs | During the wait, the heart shows **this value**
```

The docs say the whole lesson in one sentence: "Optimistic state only renders while an Action is in progress, otherwise `value` is rendered." Here `value` is the real state you pass in, `liked`. Every principle of this lesson comes from that sentence.

### Three ways to show the result of a click

Developers choose between three ways for this same job:
1. **Wait for the server, then show the result.** You use `useActionState` alone (Lesson 42). You show a saving sign with `isPending` or `useFormStatus` (Lesson 43). This fits when the server may refuse, such as a payment or a sign-up.
2. **Show the result first with `useState`, and set it back by hand on failure.** This is the plain JavaScript trick from above, and the old way in React. React's blog: "In the past, you would need to handle pending states, errors, optimistic updates, and sequential requests manually."
3. **Show the result first with `useOptimistic`.** This fits when the save almost always succeeds and the user expects the change at once: a like, a follow, a new chat message. React shows the hoped-for value during the save, and the real state again when the save ends.

```tree caption="Three ways to show the result of a click that the server must save."
Three ways to show the result of a click
- +1. Wait for the server [`useActionState`] | Shows a **saving sign** during the wait | Fits when the result **cannot be guessed**, such as a payment
- !2. Show it first with `useState` | Your code **sets it back by hand** on every failure | Forget one failure, and the page **keeps a value the server never saved**
- +3. Show it first with `useOptimistic` | React shows the **hoped-for value** during the save | When the save ends, React shows the **real state** again by itself
```

This lesson is about the third way.

### The Rule of Thumb: can the server say no?

**Ask one question about every click: will the save almost always succeed? If yes, show the result first with `useOptimistic`. If the server may refuse, wait for it.**

A senior developer also knows the two classic mistakes:
1. **The set function in `onClick`.** The heart flashes red, turns white again, and the Console shows an error.
2. **Clearing the optimistic state by hand.** You never do that. React ends it by itself, and the real state decides what stays.

The rest of the lesson shows each rule on a real photo post.

The file `api.js` stands in for a real server. It is given here, not taught. It waits one second only so that you can see the wait on the screen. The docs use the same delay in every `useOptimistic` example:

```js title="src/api.js"
export async function saveLike(liked) {
  await new Promise(resolve => setTimeout(resolve, ~1000~)); // Waits one second, like a slow server
  return ~true~; // The server saved the like; Principle 4 changes this to false
}
```

**PRINCIPLES:** `useOptimistic` shows the value you expect while the save runs. When the save ends, React shows the real state again. Five principles follow:
1. **Principle 1: The Button Reads the Optimistic State.** The form's action sets the hoped-for value first and starts the save second. A button that still reads `liked` waits for the server.
2. **Principle 2: The Set Function Belongs in the Form's Action.** Called in `onClick`, it shows the red heart for a moment, the white heart comes back, and the Console logs an error.
3. **Principle 3: Pass the Real State to useOptimistic.** When the Action ends, the optimistic state equals the value you passed in. A fixed `false` turns a saved like white again.
4. **Principle 4: A Failed Save Rolls Back by Itself.** On failure, the real state does not change, so the heart shows what it showed before the click. No undo code.
5. **Principle 5: One Reducer for Every Value the Click Changes.** The heart and the like count come from the same optimistic state, so they never disagree during the wait.

## PRINCIPLE | useOptimistic: the button that reads the optimistic state turns red at once

> [!PRINCIPLE]
> **Principle 1: useOptimistic: The Button Reads the Optimistic State**
>
> *Call `useOptimistic(liked)`, call its set function first inside the form's action, and let the button read the optimistic state, so the heart turns red while the save is still running.*
>
> The server needs about one second to save the like. A button that reads the real state waits for that second, and the user thinks the click did not work. `useOptimistic` gives the component a second value for the wait. The form's action puts the hoped-for value into it at once, and the button shows that value until the save ends.
>
> **DO THIS:**
> ```jsx
> const [optimisticLiked, setOptimisticLiked] = useOptimistic(liked);
>
> <button type="submit">{~optimisticLiked~ ? '❤️ Liked' : '🤍 Like'}</button> {/* Red as soon as the form's action calls the set function */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [optimisticLiked, setOptimisticLiked] = useOptimistic(liked);
>
> <button type="submit">{~liked~ ? '❤️ Liked' : '🤍 Like'}</button> {/* **WRONG:** the Hook runs, but the heart stays white until the server answers */}
> ```

Here is the whole idea in its fewest lines:

```jsx title="useOptimistic in its smallest code"
const [liked, likeAction] = useActionState(updateLike, false); // The real state
const [optimisticLiked, setOptimisticLiked] = useOptimistic(liked); // The optimistic state

async function submitAction() {
  ~setOptimisticLiked(true)~; // 1. The heart turns red at once
  return likeAction(true); // 2. Then the save starts, and takes one second
}

<form action={submitAction}>
  <button type="submit">{~optimisticLiked~ ? '❤️ Liked' : '🤍 Like'}</button> {/* The button reads the optimistic state */}
</form>
```

Read `submitAction` as two steps, in this order:
1. **Show the hoped-for value.** `setOptimisticLiked(true)` puts `true` into the optimistic state.
2. **Start the real save.** `likeAction(true)` sends `true` as the payload. React passes it on to `updateLike`.

`submitAction` is your own function. You pass it to the form's `action`, so React calls it inside a Transition, and that makes it an Action (Lesson 41).

Before the click, no Action is pending. So `optimisticLiked` simply equals `liked`, and both are false. The docs call the value you pass in `value`: "The value returned when there are no pending Actions."

### VS | The button reads `liked` vs. the button reads `optimisticLiked`: only the second one is red during the save

```jsx title="The heart button that reads liked, and the heart button that reads optimisticLiked"

<button type="submit">{~optimisticLiked~ ? '❤️ Liked' : '🤍 Like'}</button> {/* Red at once */}
```

It may look the same, but it is NOT the same thing! Before the click, both values are `false`, so both buttons show the white heart. During the one-second wait, they split:
- **`liked` is still `false`,** because the server has not answered.
- **`optimisticLiked` is already `true`,** because the form's action passed `true` to the set function.

Developers really make this mistake. They add the `useOptimistic` line and call the set function in the form's action, but the button still reads `liked`. The heart stays white for one second, as if the Hook did nothing. The fix is one word in the button: read `optimisticLiked`.

### What React does during that one second

**The heart turns red before the save starts, and stays red while the save runs.** Here are the steps in the order React takes them:
1. The user clicks the white heart. React calls `submitAction` inside a Transition, because it is the form's action.
2. `setOptimisticLiked(true)` runs first. React renders at once with `true`, and the heart reads `❤️ Liked`.
3. `likeAction(true)` starts the save. Our function `updateLike` waits one second for the server.
4. During that whole second, `liked` is still `false`. React keeps showing `true`, so the heart stays red.

The docs describe the same order. "When `setOptimistic('b')` is called, React immediately renders with `'b'`." And: "If you await in the Action, React continues showing `'b'`."

### The heart button of our page

Here is the whole `LikeButton` file. `updateLike` waits for the save and returns the new like, which becomes `liked`. Its first parameter, `wasLiked`, is the previous state. This version does not use it yet. Principle 4 does.

```jsx title="src/LikeButton.jsx"
import { useActionState, ~useOptimistic~ } from 'react'; // useOptimistic comes from react, like useState
import { saveLike } from './api.js';

async function updateLike(wasLiked, nextLiked) {
  await saveLike(nextLiked);
  return nextLiked;
}

export default function LikeButton() {
  const [liked, likeAction] = useActionState(updateLike, false);
  const [optimisticLiked, setOptimisticLiked] = ~useOptimistic(liked)~; // Equals liked whenever no Action is pending

  async function submitAction() {
    const nextLiked = ~!optimisticLiked~; // A click on the red heart sends false and unlikes the post
    setOptimisticLiked(nextLiked);
    return likeAction(nextLiked);
  }

  return (
    <form action={submitAction}>
      <button type="submit">{optimisticLiked ? '❤️ Liked' : '🤍 Like'}</button>
    </form>
  );
}
```

`nextLiked` comes from `optimisticLiked`, the heart the user sees. So the same button likes and unlikes the post. A click on the white heart sends `true`. A click on the red heart sends `false`. This is the same shape the docs use for a form with `useOptimistic`: set the hoped-for value first, start the save second.

```tree dir=right caption="What the heart shows before the click, during the one-second save, and after the save."
One click by the user on the white heart
- +Before the click | `liked` is **false**; `optimisticLiked` equals it | The heart is **white**
- +During the save | `liked` is still **false**; `optimisticLiked` is **true** | The heart is **red at once**
- +After the save | `liked` is **true**; `optimisticLiked` equals it again | The heart **stays red**
```

Remember: `useOptimistic` shows the value you expect while the save runs. But only if the button reads it.

## PRINCIPLE | The set function in the form's action: the red heart lasts for the whole save

> [!PRINCIPLE]
> **Principle 2: Inside an Action: Call the Set Function in the Form's Action**
>
> *Call the set function of `useOptimistic` inside an Action, such as the function passed to the form's `action`, never in a plain `onClick` handler.*
>
> The optimistic state lasts only as long as an Action. The form's `action` is an Action prop: React calls your function inside a Transition, and that Transition holds the red heart until the save ends. A plain `onClick` handler has no Transition around it. The red heart shows for a moment, the white heart comes back, and React logs an error in the Console.
>
> **DO THIS:**
> ```jsx
> async function submitAction() {
>   ~setOptimisticLiked(true)~; // Inside the form's action: the red heart stays until the save ends
>   return likeAction(true);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button type="submit" ~onClick~={() => setOptimisticLiked(true)}>🤍 Like</button> {/* **WRONG:** outside any Action, the heart flashes and React logs an error */}
> ```

You want the heart to change "on click", so `onClick` looks like the natural place for the set function. Here is the same call in two places:

```jsx title="setOptimisticLiked in onClick, and in the form's action"
<button type="submit" ~onClick~={() => setOptimisticLiked(true)}>🤍 Like</button> {/* A plain event handler, outside any Action */}

async function ~submitAction~() { // The form's action: React calls it inside a Transition
  setOptimisticLiked(true);
  return likeAction(true);
}
```

Both run when the user clicks the heart. The one difference is how React calls them:
- **The form's action** is called inside a Transition. That makes it an Action.
- **`onClick`** is called as a plain event handler, outside any Action.

And the optimistic state lives only as long as an Action. In `onClick`, there is no Action around the call, so nothing holds the red heart.

### What the user sees with the set function in `onClick`

Here is the broken version of our file. `onClick` sets the optimistic state, and the form's action only starts the save:

```jsx title="src/LikeButton.jsx" startLine="13"
  async function submitAction() {
    return likeAction(!liked);
  }

  return (
    <form action={submitAction}>
      <button
        type="submit"
        ~onClick~={() => setOptimisticLiked(!optimisticLiked)} // **WRONG:** runs outside any Action, so the red heart does not last
      >
        {optimisticLiked ? '❤️ Liked' : '🤍 Like'}
      </button>
    </form>
  );
```

**The red heart lasts only a moment. The white heart comes back at once, and the red one returns only when the save ends.** Here is what happens when the user clicks the white heart:
1. `onClick` runs first, as a plain event handler. The set function logs an error in the Console, and the heart reads `❤️ Liked` for a moment.
2. React shows the white heart again at once. No Action holds the optimistic state, so it equals `liked` again. And the real like is still false.
3. The form's action starts the save. After one second, `liked` becomes `true`, and the heart turns red for good.

The docs explain step 2:

"When you call the setter outside an Action, the optimistic state will briefly appear and then immediately revert back to the original value. This happens because there's no Transition to 'hold' the optimistic state while your Action runs."

```page width=full caption="The post during the one-second save, with the set function in onClick: the white heart is back, and the Console shows the error from React."
line: Sunset at the beach
form:
  submit: 🤍 Like | | bad
console: An optimistic state update occurred outside a transition or action. To fix, move the update to an action, or wrap with startTransition.
```

The error names the fix: "move the update to an action". On our page, the Action is `submitAction`. Move the line back into it, and you get the file of Principle 1 again: red at once, red for the whole save.

### Why the form's action needs no `startTransition`

The error names a second fix, `startTransition`, which a later lesson teaches. Our form does not need it.

The docs call a prop like the form's `action` an Action prop: a prop whose function React already calls inside a Transition. In their words: "When using Action props, you can call the set function without `startTransition`." And: "This works because Action props are already called inside `startTransition`."

So the set function belongs in the function you pass to the form's `action`. By React's convention, the name of such a function ends in "Action", and `submitAction` follows it.

```tree caption="The same set function call in onClick and in the form's action: only the form's action is inside an Action."
Where `setOptimisticLiked` runs on the click
- !In `onClick` [`onClick`] | A **plain event handler**, outside any Action | The red heart **flashes**, the white heart comes back, and the Console logs an **error**
- +In the form's action [`submitAction`] | React calls it **inside a Transition** | The red heart **stays** for the whole save
```

Remember: the optimistic state shows while the save runs. "While the save runs" means "while the Action runs", so the set function must be inside the Action.

## PRINCIPLE | `useOptimistic(liked)`: after the save, the heart shows what the server saved

> [!PRINCIPLE]
> **Principle 3: The Real State: Pass liked, and Let React End the Optimistic State**
>
> *Pass the real state to `useOptimistic`, and never clear the optimistic state by hand: when the Action ends, the optimistic state equals that value again.*
>
> The optimistic state is temporary. No line of your code turns it off. React ends it when the Action ends, in the same render that shows the saved value. So what the user sees after the save is the value you passed to `useOptimistic`. A fixed `false` turns the heart white again after a like the server saved.
>
> **DO THIS:**
> ```jsx
> const [optimisticLiked, setOptimisticLiked] = useOptimistic(~liked~); // After the save, the heart shows what the server saved
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [optimisticLiked, setOptimisticLiked] = useOptimistic(~false~); // **WRONG:** after a saved like, the heart turns white again
> ```

Look again at the `LikeButton` file of Principle 1. `submitAction` calls the set function once, at the start. No line calls it again after the save. Yet after the save, the heart stays red. Why?

Because of the value you passed to `useOptimistic`, not because of the set function. The docs title one of their notes "Optimistic state is temporary". When the Action ends, the optimistic state equals the value you passed in again. In our file, that value is `liked`, the real state.

**The optimistic state ends by itself when the Action ends, and the real state decides what stays on the page.** Here is what happens after the heart turns red:
1. After one second, `updateLike` returns true. `useActionState` stores it as the new `liked`.
2. The Action ends.
3. React renders once with `liked` as true. The optimistic state is true again, but now because it equals `liked`.
4. The heart stays red. There is no white moment between the hoped-for heart and the real one.

There is no extra render to clear the optimistic state. The optimistic state and the real state meet in the same render, when the Transition ends.

### VS | Passing `liked` vs. passing `false`: only the real state keeps a saved like red

The heart starts white, so `false` looks like a fine value to pass in. Here are both lines:

```jsx title="Passing the real state, and passing a fixed false"
const [optimisticLiked, setOptimisticLiked] = useOptimistic(~liked~); // After the save, it equals liked, which is true: the heart stays red
const [optimisticLiked, setOptimisticLiked] = useOptimistic(~false~); // After the save, it equals false again: the heart turns white
```

It may look the same, but it is NOT the same thing! During the Action, both show the value your code passed to the set function, so both turn the heart red at once. After the save, only the first one stays red. The docs: "The `value` argument to `useOptimistic` determines what displays after the Action finishes."

Here is how this mistake reaches a real user:
1. A developer writes `useOptimistic(false)`, since the heart starts white.
2. The user clicks, and the heart turns red at once.
3. The server saves the like.
4. One second after the click, the heart turns white again.
5. The user thinks the like was lost and clicks again. The optimistic state is false, so the click sends `true` once more: the same like, saved a second time.

The fix is to pass the real state: `useOptimistic(liked)`. Then, after every save, the page shows what the server saved.

Remember: when the save ends, React shows the real state again. So the value you pass in must be the real state.

## PRINCIPLE | Return `wasLiked` on failure: the heart turns white again with no undo code

> [!PRINCIPLE]
> **Principle 4: Roll Back: A Failed Save Leaves the Real State Unchanged**
>
> *When the save fails, return the previous state from the reducer action; when the Action ends, the page shows what it showed before the click, with no undo code.*
>
> A hand-made version with `useState` stores the red heart for real, so your code must turn it back on every failure, and a forgotten failure keeps a like that the server never saved. With `useOptimistic`, the red heart lasts only as long as the Action. On failure, `liked` stays as it was, and React shows it again when the Action ends.
>
> **DO THIS:**
> ```js
> async function updateLike(wasLiked, nextLiked) {
>   const saved = await saveLike(nextLiked);
>   return saved ? nextLiked : ~wasLiked~; // On failure, the heart goes back to what it was before the click
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> async function updateLike(wasLiked, nextLiked) {
>   await saveLike(nextLiked);
>   return ~nextLiked~; // **WRONG:** ignores the failure, so the heart stays red although the server saved nothing
> }
> ```

So far the server always saves the like. Real servers sometimes fail. To see a failure, change one line in the given `api.js`. The fake save now returns `false`, which means the server could not save the like:

```js title="src/api.js" bad="3"
export async function saveLike(liked) {
  await new Promise(resolve => setTimeout(resolve, 1000));
  return ~false~; // The server could not save the like
}
```

The `updateLike` of Principle 1 never looks at this answer. It always returns `nextLiked`, which is `true`. So `liked` becomes `true` although the server saved nothing, and the heart stays red after the failure.

So `updateLike` must check the answer. On failure, it returns `wasLiked`, the previous state, which `useActionState` passes as the first parameter (Lesson 42):

```js title="src/LikeButton.jsx" startLine="4"
async function updateLike(wasLiked, nextLiked) {
  const saved = await saveLike(nextLiked);
  return saved ? nextLiked : ~wasLiked~; // On failure, liked stays what it was before the click
}
```

The failure is returned as the state, not thrown. That is how you handle a known error with `useActionState` (Lesson 42). A thrown error goes to the nearest Error Boundary, which a later lesson teaches.

### What the user sees when the save fails

**When the save fails, the heart turns white again by itself. No line of your code says "undo the like".** Here is what happens after the user clicks the white heart:
1. The heart turns red at once, as in Principle 1.
2. After one second, `saveLike` returns `false`.
3. `updateLike` returns `wasLiked`, the previous state, which is false. So `liked` stays false.
4. The Action ends, and the optimistic state equals `liked` again.
5. The heart reads `🤍 Like` again.

```page caption="The post during the one-second save that will fail: the heart is red."
line: Sunset at the beach
form:
  submit: ❤️ Liked
console: quiet
```

```page caption="The same post after the save fails: the heart is white again, as it was before the click."
line: Sunset at the beach
form:
  submit: 🤍 Like | | good
console: quiet
```

This is the same step as in Principle 3: the optimistic state ends, and the real state shows. After a success, the real state is the new like. After a failure, the real state is still the old one. The docs call this a roll back: "the UI automatically rolls back". React's blog says Actions "revert optimistic updates to their original value automatically".

### VS | The hand-made way `useState` vs. `useOptimistic`: both roll back, only one needs your undo code

Remember the plain JavaScript trick from the start? Before `useOptimistic`, developers did the same in React with `useState`:

```jsx title="Showing the like first with useState, and setting it back by hand"
const [liked, setLiked] = useState(false);

async function handleLike() {
  setLiked(true);
  const saved = await saveLike(true);
  if (!saved) ~setLiked(false)~; // Your code turns the heart white again on failure
}
```

With `useOptimistic`, the set function in the form's action shows the red heart, as before. On failure, the reducer action only keeps the old value:

```js title="Keeping the previous state on failure, with useOptimistic"
async function updateLike(wasLiked, nextLiked) {
  const saved = await saveLike(nextLiked);
  return saved ? nextLiked : ~wasLiked~; // Nothing to undo: liked simply stays as it was
}
```

When the hand-made way is written correctly, yes, the screen is exactly the same! The heart is red at once, and white again after the failure. The one difference is who does the second step. With `useState`, your code turns it back. With `useOptimistic`, React does.

The hand-made way breaks as soon as you forget one failure:
1. A developer shows the like first with `setLiked(true)`, then calls the server.
2. They write `setLiked(false)` for the case where the server answers `false`.
3. They forget the case where the request itself fails, such as a lost connection. Then `saveLike` throws, and the line with `setLiked(false)` never runs.
4. The heart stays red.
5. The next time the user opens the post, the server says it is not liked, and the heart is white.

With `useOptimistic`, the red heart is never stored in state. It lasts only as long as the Action, so there is nothing to turn back.

```tree caption="Who turns the heart white again after a failed save: your code with useState, or React with useOptimistic."
Turning the heart white again after a failed save
- !Show it first with `useState` [`setLiked`] | Your code **sets it back by hand** | Forget one failure, and the heart **stays red** although the server saved nothing
- +Show it first with `useOptimistic` [`wasLiked`] | `liked` **does not change** on failure | When the Action ends, the heart shows **what it showed before the click**
```

From here on, the fake save in `api.js` succeeds again. And `updateLike` keeps its check of the answer.

## PRINCIPLE | A reducer in useOptimistic: the heart and the count change together

> [!PRINCIPLE]
> **Principle 5: One Reducer: Every Value the Click Changes Comes from the Optimistic State**
>
> *When one click changes several values on the page, pass a reducer as the second argument of `useOptimistic`, and read every one of those values from the optimistic state.*
>
> The heart and the count answer the same question: did the user like this post? If the heart reads the optimistic state and the count reads the real state, the page gives two different answers for one second. A reducer computes the heart and the count from one call to the set function, so both change in the same render.
>
> **DO THIS:**
> ```jsx
> <button type="submit">{optimisticPost.liked ? '❤️ Liked' : '🤍 Like'}</button>
> <p>{~optimisticPost.likes~} likes</p> {/* 13 likes at the same moment as the red heart */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button type="submit">{optimisticPost.liked ? '❤️ Liked' : '🤍 Like'}</button>
> <p>{~post.likes~} likes</p> {/* **WRONG:** 12 likes next to a red heart for one second */}
> ```

Instagram shows a count under the heart, such as `12 likes`. Now one click changes two things on the page: the heart and the count. So the like becomes one object with two fields, `liked` and `likes`. The real state is now `post`:

```jsx title="The post as one object in the real state"
const [post, likeAction] = useActionState(updateLike, ~{ liked: false, likes: 12 }~); // The heart and the count, in one object
```

For this case, `useOptimistic` takes an optional second argument, a reducer. The docs: "The reducer function that specifies how the optimistic state gets updated. It must be pure, should take the current state and reducer action arguments, and should return the next optimistic state."

```jsx title="useOptimistic with a reducer"
const [optimisticPost, setOptimisticPost] = useOptimistic(
  post,
  ~(current, liked) => ({ liked, likes: current.likes + (liked ? 1 : -1) })~ // The current state and the new like in, the next state out
);
```

The reducer returns a new post object. Its `liked` is the new like. Its count goes up by one on a like, and down by one on an unlike.

You already know this kind of function: the current state and an action in, the next state out (Lesson 27). And like every reducer, it must be pure (Lesson 14). The one difference is that its result shows only while the Action runs.

Its two parameters come from two places:
- **`current` comes from React.** It is the current state, here `post` at the start of the Action.
- **`liked` comes from your code.** It is the value you pass to `setOptimisticPost`. The docs: "If you provided a `reducer` to `useOptimistic`, this value will be passed as the second argument to your reducer."

### VS | The count from `post` vs. the count from `optimisticPost`: only the second one agrees with the red heart

The heart already reads `optimisticPost.liked`. The count line can read the real state or the optimistic state:

```jsx title="The count line that reads post, and the count line that reads optimisticPost"
<p>{~post.likes~} likes</p> {/* 12 likes for one second, then 13 likes */}
<p>{~optimisticPost.likes~} likes</p> {/* 13 likes at once */}
```

It may look the same, but it is NOT the same thing! Before the click, both lines read `12 likes`. During the wait, the heart is already red. The count that reads `post` still says `12 likes`, because the server has not answered. The user sees a liked post whose count did not change.

::: row caption="During the one-second save: the count from post disagrees with the red heart; the count from optimisticPost agrees with it."
::: col title="The count reads post" tag="12 likes next to a red heart" tone=bad
```page size=mini

form:
  submit: ❤️ Liked
line: 12 likes | bad
```
:::
::: col title="The count reads optimisticPost" tag="13 likes next to a red heart" tone=good
```page size=mini
line: Sunset at the beach
form:
  submit: ❤️ Liked
line: 13 likes | good
```
:::
:::

The docs give the rule: "When an optimistic update affects multiple related values, use a reducer to update them together." Every value the user sees change on the click must come from the same optimistic state.

### What one click does to both values

**One call to the set function moves the heart and the count in the same render.** Here is what happens when the user clicks the white heart above `12 likes`:
1. `setOptimisticPost(true)` passes `true` to the reducer as its second argument.
2. The reducer returns a new post: liked, with 13 likes.
3. React renders with that object. The heart turns red and the count reads `13 likes`, together.
4. After the save, the real `post` is also liked, with 13 likes, and the optimistic state equals it. Nothing moves on the screen.

### The final heart button

Here is the final `LikeButton` file. The reducer gets a name, `applyLike`, so that `updateLike` can use it too. The first parameter of `updateLike` is now `previousPost`, because the previous state is the whole post, not only the like:

```jsx title="src/LikeButton.jsx"
import { useActionState, useOptimistic } from 'react';
import { saveLike } from './api.js';

function ~applyLike~(current, liked) { // The reducer: one place that computes the heart and the count
  return { liked, likes: current.likes + (liked ? 1 : -1) };
}

async function updateLike(previousPost, nextLiked) {
  const saved = await saveLike(nextLiked);
  return saved ? ~applyLike(previousPost, nextLiked)~ : previousPost; // The saved post uses the same reducer
}

export default function LikeButton() {
  const [post, likeAction] = useActionState(updateLike, { liked: false, likes: 12 });
  const [optimisticPost, setOptimisticPost] = ~useOptimistic(post, applyLike)~; // The second argument is the reducer

  async function submitAction() {
    const nextLiked = !optimisticPost.liked;
    setOptimisticPost(nextLiked);
    return likeAction(nextLiked);
  }

  return (
    <form action={submitAction}>
      <button type="submit">{optimisticPost.liked ? '❤️ Liked' : '🤍 Like'}</button>
      <p>{~optimisticPost.likes~} likes</p> {/* Reads the optimistic state, like the heart */}
    </form>
  );
}
```

The optimistic state and the saved state both come from `applyLike`. So the hoped-for count and the saved count are computed the same way. A real server would send back the saved count. Our fake `saveLike` only answers yes or no.

```page caption="The final page before the user clicks the heart."
  submit: 🤍 Like
line: 12 likes
console: quiet
```

### The mistake, and what the user sees

| Principle | The mistake | What the user sees | The fix |
| :--- | :--- | :--- | :--- |
| **1. The button reads the optimistic state** | The button still reads `liked` | The heart stays white for one second | Render `optimisticLiked` |
| **2. Inside an Action** | The set function sits in `onClick` | The heart flashes, and the Console logs an error | Call the set function in the form's action |
| **3. The real state decides what stays** | `useOptimistic(false)` | The heart turns white after a saved like | Pass the real state, `liked` |
| **4. Roll back** | A hand-made `useState` forgets a failure | The heart stays red although nothing was saved | Return the previous state on failure |
| **5. One reducer** | The count reads `post` | `12 likes` next to a red heart | Read every changed value from the optimistic state |

One last time, the sentence of this lesson: **`useOptimistic` shows the value you expect while the save runs. When the save ends, React shows the real state again.**

## For the Interview

> **The Interview Question:** How do you show the value the reader expects before the server confirms?

### How to Answer Clearly in 30 Seconds

"I use `useOptimistic`. It takes the real state, such as the `liked` value that `useActionState` keeps, and returns an optimistic state and a set function. Inside the form's action, I call the set function first with the hoped-for value, so the heart turns red at once. Then I start the save. Three rules keep it correct:
1. **Call the set function inside an Action**, such as the form's action. In a plain `onClick`, the value only flashes, and React logs an error.
2. **Never clear the optimistic state by hand.** When the Action ends, it equals the real state again, in the same render.
3. **Let the real state carry the result.** On success, the real state is the new like. On failure, it stays the old one, so the heart rolls back by itself."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"When would you not use `useOptimistic`?"**
   When the result cannot be guessed. A like or a follow almost always succeeds, so showing it first is honest. A payment or a sign-up may be refused, and showing "Paid" before the server agrees would mislead the user. There, I wait for the server with `useActionState` and show a saving sign with `isPending` or `useFormStatus`.
2. **"What happens if the Action throws instead of returning a failure?"**
   The Transition still ends, and React renders with whatever the real state is at that moment, so the optimistic value goes away. With `useActionState`, though, a thrown error goes to the nearest Error Boundary, and React cancels the Actions waiting in its queue. That is why a known failure, such as the server refusing the like, is returned as state: the reducer action returns the previous state.
3. **"Why pass a reducer instead of calling the set function with the next value?"**
   A reducer fits when one click changes several values, such as the heart and the count, because one function computes both and they never disagree. The docs add a second reason: "Reducers are essential when the base state might change while your Transition is pending." The base state is the real state we passed to `useOptimistic`. If it changes during the wait, React runs the reducer again on the new base state, while a plain value passed to the set function stays fixed.

```tree caption="Interview comparison: three tools that show the user something while a save runs, and what each one shows."
What the page shows while a save runs
- +`isPending` from `useActionState` | Says that **an Action is running** | Fits a **saving sign** on a button
- +`pending` from `useFormStatus` | Says that **the form is submitting** | Fits a sign **inside the form's own components**
- +`useOptimistic` | Shows **the result itself**, before the server confirms | Fits a **like, a follow, or a chat message**
```
