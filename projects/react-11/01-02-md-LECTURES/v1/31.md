# Lecture 31: Reaching a DOM Node with a Ref

*(How do you get hold of the real `<input>` element that React created, to put the cursor in it?)*

> INTERVIEW QUESTION | ❱ CORE | How do you reach a DOM node from React to focus it, scroll it, or measure it?

---

## VS | Plain JavaScript `getElementById` vs. React `ref`: you grab the element yourself, or React hands it to you

> Sometimes your code needs to work with a real element on the page: to put the cursor in an input field, scroll to a message, or measure a box. **You should attach a ref to that JSX tag.** React puts the real browser element it created into the ref, so your code can focus it, scroll to it, or measure it.

In React, a page often needs to **directly control an element on the screen**, like placing the blinking cursor inside a search field, scrolling down to a new chat message, or playing a video. In plain JavaScript, you grab the element from the page with `document.getElementById` and call its built-in browser methods, such as `focus()`. In React, you normally do not hunt through the document to grab elements manually. This is when we create a ref with `useRef` and attach it to a JSX tag with the `ref` attribute. A ref asks React to hand you the real browser element it created, so your code can focus it, scroll it, or measure it on command. It does the job of the classic `getElementById`, but you do not search for the element: React hands it to you.

Take a comment form with a text field and a **Reply** button. When the user clicks **Reply**, the blinking cursor should jump straight into the text field so they can start typing right away. Ask yourself: how does the **Reply** button reach over and put the cursor inside that text field? Both the button and the text field sit in the same comment form component, and the button's click handler needs a direct connection to the real `<input>` element on the screen.

**Why:** In React, writing `<input />` in your code does not give you a real browser element in your hands. It is only a blueprint, and React builds the actual HTML element behind the scenes. At the same time, JSX has no prop that says "put the blinking cursor here right now." Only the real browser element has the built-in `focus()` method, and only React controls that element. Passing the ref to the tag, as in `<input ref={inputRef} />`, tells React to put the real browser element inside `inputRef.current` once it is on the screen, so your click handler can call `inputRef.current.focus()` directly.

### Back to `getElementById`

Remember `getElementById` from Lesson 01? In plain JavaScript, you grab the element yourself, and then you call the browser's methods on it:

```js title="Plain JavaScript: grab the element, then focus it"
const input = ~document.getElementById('name')~; // You search the page and grab the <input> element
input.focus(); // The browser puts the cursor in it
```

In React, you never create the elements by hand. React creates them for you, from your JSX. So there is nothing for you to grab.

Most of the time, you do not need to grab anything. You describe the page in JSX, and React updates the real elements to match: the text, the classes, which lines are shown.

But some jobs have no words in JSX. JSX has no prop that says "put the cursor in this field now". It has no prop that says "scroll until this picture is visible", and no way to ask "how wide is this element?". For these three jobs, you need the real element.

The docs say it plainly: "There is no built-in way to do those things in React, so you will need a *ref* to the DOM node."

So in React, you ask for the element:

```jsx title="React: ask React for the element, then focus it"
const inputRef = ~useRef(null)~; // 1. In the component: creates the object { current: null }
<input ~ref={inputRef}~ /> {/* 2. In the JSX: when you create this <input>, put it into inputRef.current */}
~inputRef.current.focus()~; // 3. In a click handler: the same focus as in plain JavaScript
```

Line 1 is the ref from Lesson 30. Line 3 is the browser's own `focus` method. Only line 2 is new.

> [!DEFINITION]
> **What is a DOM node?** [NEW] A DOM node is the real object the browser keeps for one tag on the page. For `<input />` in your JSX, the browser keeps one `<input>` element.
> It is what you see in the Elements panel. It is what `document.getElementById` returned in Lesson 01.
> It comes with the browser's own methods and properties, such as `focus()`, `scrollIntoView()`, and `offsetWidth`. The docs call them browser APIs.
> The docs say "DOM node" and "DOM element" for the same thing. In this lesson, "the element" means the same (Lesson 31).

> [!DEFINITION]
> **What is a ref?** [REVIEW] `useRef(null)` returns a plain object with one field: `{ current: null }`. React gives you back the same object on every render, and changing `current` does not render again.
> In Lesson 30, our own code wrote into `current`: the Start handler stored the interval ID there.
> In this lesson, React writes into `current`. You only put `ref={inputRef}` on a tag, and React fills the ref with that tag's element.
> It is the exact same kind of ref. The docs: "Refs are a generic concept, but most often you'll use them to hold DOM elements" (Lesson 30).

The one difference is who writes `current`:

```jsx title="Who writes current: our code in Lesson 30, React in this lesson"
intervalRef.current = ~setInterval(tick, 1000)~; // Lesson 30: our Start handler writes the interval ID
<input ~ref={inputRef}~ /> {/* This lesson: React writes the <input> element */}
```

### The smallest example: a button that focuses an input

Here is the first example of the docs. An input field, and a button that puts the cursor in it:

```jsx title="Form.jsx"
import { useRef } from 'react';

export default function Form() {
  const inputRef = ~useRef(null)~; // { current: null } until React creates the <input>

  function handleClick() {
    ~inputRef.current.focus()~; // current holds the real <input>, so the browser's focus works
  }

  return (
    <>
      <input ~ref={inputRef}~ /> {/* Asks React to put this <input> into inputRef.current */}
      <button onClick={handleClick}>Focus the input</button>
    </>
  );
}
```

When the page opens, the input field is empty, and the cursor is nowhere:

```page width=text caption="The docs' example when the page opens: an empty input field and the Focus the input button."

  field:  | 
  button: Focus the input
console: quiet
```

The user clicks the button. The cursor appears in the input field, and the browser draws a ring around it:

```page width=text caption="After the click on Focus the input, the cursor is in the input field."
form:
  field:  |  | good
  button: Focus the input
console: quiet
```

The docs put it this way: the attribute "tells React to **put this `<input>`'s DOM node into `inputRef.current`.**"

### The Rule of Thumb: can the JSX say it?

**Ask one question about every job on the page: can the JSX say it? If yes, use state and JSX. If not, as with focus, scroll, or measure, use a ref, in an event handler.**

The docs remind us that a ref is the rare case: "React automatically updates the DOM to match your render output, so your components won't often need to manipulate it." And where do you use it? "Usually, you will access refs from event handlers."

Lesson 30 called a ref an escape hatch. The docs use the same idea here: a ref to a DOM node is for the moments when you have to "step outside React". Their examples: "managing focus, scroll position, or calling browser APIs that React does not expose."

```tree caption="Which tool fits which job when a component needs something on the page."
What the component needs on the page
- +Something the JSX can say [`value={text}` `{show && <p />}`] | Text, a class, a line shown or hidden | **State and JSX**, no ref
- +Focus, scroll, or measure after a click [`inputRef.current.focus`] | The browser keeps these, **not the JSX** | **A ref**, read in the **event handler**
- +Focus an input the moment it appears [`autoFocus`] | There is **no event** to run code in | **`autoFocus`**, or an Effect in Lesson 32
- !Find the element by its id [`document.getElementById`] | Searches **the whole page** | Finds **the wrong input** when a component appears twice
```

A senior developer also knows the three classic mistakes:
1. **`document.getElementById` in a component.** It searches the whole page, so a component used twice finds the wrong input field.
2. **Reading `inputRef.current` while the component renders.** On the first render, React has not created the element yet, so it is still `null`.
3. **Using the element to change what React drew**, such as removing it. React does not know about the change, and its next update crashes.

The rest of the lesson shows each mistake on a real page.

**PRINCIPLES:** A ref is how you ask React: "When you create this element, give it to me." Five principles follow:
1. **Principle 1: The ref Attribute Fills ref.current.** After React creates the input field, it puts it into `inputRef.current`. Without the attribute, the ref stays `null`.
2. **Principle 2: Focus, Scroll, and Measure in a Handler.** In an event handler, `inputRef.current` is the real element, so the browser's own methods work on it.
3. **Principle 3: One Ref per Copy, Not One Id per Page.** `document.getElementById` returns the first match on the whole page, so the cursor lands in the wrong list.
4. **Principle 4: Never Read the Ref During Rendering.** On the first render the ref is still `null`, and a call to `focus` there blanks the page.
5. **Principle 5: Never Change What React Drew.** Removing an element through a ref crashes React's next update.

## PRINCIPLE | `ref={inputRef}`: React puts the element into `inputRef.current` right after it creates it

> [!PRINCIPLE]
> **Principle 1: The ref Attribute: React Puts the Element into ref.current**
>
> *Create a ref with `useRef(null)`, and put `ref={inputRef}` on a built-in tag; right after React creates the element, it puts it into `inputRef.current`, and when the element is removed, it sets `current` back to `null`.*
>
> `useRef` alone only gives you an empty object. The `ref` attribute on the tag is the request: "when you create this element, give it to me." Your code never writes `current` here. React does. Forget the attribute, and `current` stays `null`, so a call on it throws a `TypeError`.
>
> **DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> return <input ~ref={inputRef}~ />; // React puts this <input> into inputRef.current
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> return ~<input />~; // **WRONG:** no ref attribute, so inputRef.current stays null forever
> ```

No line of your code writes `inputRef.current`. So when does React write it?

Remember that React works in two steps (Lesson 13). First, it calls your component and gets the JSX back: that is the render. Then it changes the real page to match: that is the commit. The element can only exist after the commit:
1. **The first render.** Your component returns `<input ref={inputRef} />`. The element does not exist yet, so `inputRef.current` is still `null`.
2. **The commit.** React creates the `<input>` element and adds it to the page.
3. **Right after.** React sets `inputRef.current` to that element.
4. **Later, if the input field is removed from the page**, React sets `inputRef.current` back to `null`.

The `useRef` reference says it in one sentence: "After React creates the DOM node and puts it on the screen, React will set the `current` property of your ref object to that DOM node."

```tree dir=right caption="How the input element reaches inputRef.current without a line of our code writing it."
How React fills `inputRef.current`
- +1. The first render [`<input ref={inputRef} />`] | The JSX names the ref | `current` is still **`null`**
- +2. The commit | React **creates the `<input>` element** | and adds it to the page
- +3. Right after | React sets **`inputRef.current` to that element** | Your handler can now call `focus`
- +4. The input is removed | React sets **`current` back to `null`**
```

Want to see it? Log the ref in the click handler:

```jsx title="Logging inputRef.current in the click handler"
function handleClick() {
  ~console.log(inputRef.current)~; // Logs the <input> element itself
  inputRef.current.focus();
}
```

```page width=text caption="After the click, the Console shows the input element that React put into inputRef.current."
form:
  field:  |  | good
  button: Focus the input
log: <input>
```

It is the real `<input>` element, the same one `document.getElementById` would give you.

Something that can be tricky: the `ref` attribute itself never reaches the page. React reads it and keeps it out of the DOM. So the Elements panel shows a plain input:

```dom caption="The Elements panel: the input carries no ref attribute, because React reads ref and keeps it out of the DOM."
<div id="root">
+ <input> | note: No ref attribute in the DOM
  <button>Focus the input</button>
</div>
```

### The ref attribute works on built-in tags

The docs call the browser's own tags, such as `<input>` and `<div>`, built-in components. That tells them apart from the components you write, such as `GuestList`.

On a built-in tag, the `ref` attribute fills the ref with that element. The reference says: "Your ref will be filled with the DOM element for this node."

On your own component, such as `<GuestList ref={listRef} />`, it is different. The attribute does not reach the input inside unless the component passes it on, which Lesson 85 teaches.

### `useRef` without the attribute leaves `current` at `null`

The ref and the attribute are two separate pieces. The element lands in the ref only when both are there:

```jsx title="Without the ref attribute on the tag, and with it"
<input /> {/* Without the attribute: inputRef.current stays null forever */}
<input ~ref={inputRef}~ /> {/* With the attribute: React puts this <input> into inputRef.current */}
```

It looks the same, but it is NOT the same thing! Both tags draw the same input field on the page. Only the second one asks React to fill the ref.

A developer who forgets the attribute still calls `focus` in the handler. The user clicks the button, the cursor does not appear, and the Console shows an error:

```page width=text caption="Without ref={inputRef} on the tag, the click leaves the input field without the cursor and throws an error."
form:
  field:  |  | bad
  button: Focus the input
console: Uncaught TypeError: Cannot read properties of null (reading 'focus')
```

`inputRef.current` still holds the `null` it started with. And `null` has no `focus` method, so JavaScript throws the error you see in the Console. The fix is the missing attribute.

### The guest list gets its ref

Back to our guest list. The component imports `useRef`, creates `inputRef`, and puts it on the input field:

```jsx title="src/components/GuestList.jsx" startLine="1"

  const [text, setText] = useState('');
  const [guests, setGuests] = useState([]);

```

## PRINCIPLE | `ref.current` in an event handler: focus, scroll, and measure with the browser's own methods

> [!PRINCIPLE]
> **Principle 2: Browser APIs: Call focus, scrollIntoView, or offsetWidth on ref.current in a Handler**
>
> *In an event handler, `ref.current` is the real element, so you call the browser's own methods on it: `focus` to put the cursor in it, `scrollIntoView` to scroll to it, and `offsetWidth` or `getBoundingClientRect` to measure it.*
>
> Focus, scroll position, and sizes belong to the browser, not to the JSX. State changes what React draws, but it never moves the cursor. The click on Add takes the cursor out of the input field, and only a call to `focus` brings it back.
>
> **DO THIS:**
> ```jsx
> function handleAdd() {
>   setText('');
>   ~inputRef.current.focus()~; // The cursor goes back into the input field
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleAdd() {
>   ~setText('')~; // **WRONG:** empties the input field, but the cursor stays outside it
> }
> ```

The interview question names three jobs: focus, scroll, and measure. With a ref, all three have the same shape. You take the element from `current`, and you use a method or a property the browser gives every element:

```jsx title="Three jobs, one shape: the element in current, then the browser's own method"
inputRef.current.~focus()~; // Focus: puts the cursor in the input field
imageRef.current.~scrollIntoView()~; // Scroll: scrolls until the picture is visible
setWidth(chartRef.current.~offsetWidth~); // Measure: reads the element's width in pixels
```

Yes, it is the exact same thing! The `focus` you call here is the very same method you called in plain JavaScript, on the element from `getElementById`. React only hands you the element. The docs: "You can then access this DOM node from your event handlers and use the built-in browser APIs defined on it."

Many developers think every change on the page must go through state. State decides what React draws: the text, the rows, the classes. Focus, scroll position, and size belong to the browser, so you ask the element directly.

### What focus means

Focus is the blinking cursor. The input field with focus receives the keys the user presses. Only one element on the page has focus at a time, and browsers usually draw a ring around it.

MDN describes the `focus` method: it "sets focus on the specified element, if it can be focused. The focused element is the element that will receive keyboard and similar events by default." MDN calls the ring the "visible indication of the focused element".

### Why the cursor leaves the input field

No line of our code moves the cursor away. So why is it gone after Add?
1. While the user types John, the input field has focus.
2. The user presses the mouse button on Add. The input field loses focus, because the user clicked another element.
3. `handleAdd` runs. It adds John and empties the input field. No line brings the cursor back.
4. The user types Mary, and the letters reach no input field.

Browsers differ on where focus goes after a click on a button. In every browser, it is no longer in the input field.

### The fix: one line at the end of `handleAdd`

```jsx title="src/components/GuestList.jsx" startLine="10" good="13"
  function handleAdd() {
    setGuests([...guests, { id: nextId++, name: text }]);
    setText('');
    ~inputRef.current.focus()~; // Puts the cursor back in the input field after every click on Add
  }
```

The user types John and clicks Add. John joins the list, the input field is empty, and the cursor is already in it:

```page width=text caption="After the click on Add, John is in the list and the cursor is back in the empty input field."
section: Lunch guests
form:
  field:  |  | good
  button: Add
line: John
console: quiet
```

The user types Mary at once and clicks Add again. Both names are in the list:

```page width=text caption="The user typed Mary without clicking the input field first, and clicked Add again."
section: Lunch guests
form:
  field:  |  | good
  button: Add
line: John
line: Mary

```

Something that can be tricky: `setText('')` only asks React for a new render (Lesson 15). So why does `focus` work on the very next line? Because the input field has been on the page since the first commit. `inputRef.current` already holds it, and the cursor moves in right away. A moment later, React renders, and the input field shows the empty text.

### Scrolling to an element

The docs show scrolling with a carousel: a row of cat pictures that scrolls sideways. Each picture has its own ref, and a button scrolls to the first one:

```jsx title="Scrolling to the first picture, from the docs' carousel"
const firstCatRef = useRef(null);

function handleScrollToFirstCat() {
  firstCatRef.current.~scrollIntoView~({ behavior: 'smooth', block: 'nearest', inline: 'center' }); // Scrolls until this picture is in view
}

<img ~ref={firstCatRef}~ src="https://placecats.com/neo/300/200" alt="Neo" /> {/* React puts this <img> into firstCatRef.current */}
```

MDN says that `scrollIntoView` "scrolls the element's ancestor containers" until the element "is visible to the user." In plain words: the page, and every scrolling area around the picture, moves until the picture is in view.

With no options, it scrolls just as well. The options in the docs only ask for a smooth motion, and choose where the picture ends up in the row.

### Measuring an element

A chart needs to know how wide its area is. The width belongs to the browser, so you read it from the element:

```jsx title="Measuring an element after a click"
const chartRef = useRef(null);
const [width, setWidth] = useState(0);

function handleMeasure() {
  ~setWidth(chartRef.current.offsetWidth)~; // Reads the width the browser laid out
}

return (
  <>
    <div ~ref={chartRef}~>Chart area</div> {/* React puts this <div> into chartRef.current */}
    <button onClick={handleMeasure}>Measure</button>
    <p>Width: {width}</p>
  </>
);
```

MDN says that `offsetWidth` "returns the layout width of an element as an integer". It counts pixels, "including any borders, padding, and vertical scrollbars". For a hidden element, it is `0`.

Your code never sets `offsetWidth`. The browser computes it when it lays out the page. The width goes into state because the page shows it, and Lesson 30 taught that a value the page shows belongs in state.

The browser offers a second way to measure: `getBoundingClientRect`. Both ways count the padding and the border. The difference is what you get back:
- **`offsetWidth`** is one whole number.
- **`getBoundingClientRect`** returns an object with, in the words of MDN, "the size of an element and its position relative to the viewport". The viewport is the part of the page the user sees in the browser window.

### Changing state is not enough

A challenge in the docs makes the same point with a video player. The component keeps `isPlaying` in state, and its button switches between Play and Pause.

The user clicks Play. The button now reads Pause, but the video does not move. The docs: "toggling state is not enough."

Why? State changed the button, and React draws the button. But playing a video belongs to the browser's `<video>` element. The fix: put a ref on the video element, and call its `play` or `pause` method in the handler.

## PRINCIPLE | A ref, not `getElementById`: each copy of the component reaches its own input

> [!PRINCIPLE]
> **Principle 3: One Ref per Copy: getElementById Searches the Whole Page**
>
> *`document.getElementById` returns the first element on the whole page with that id, so in a component used twice it finds the first copy's input; a ref belongs to one copy, so each list reaches its own input.*
>
> With one list on the page, an id and a ref give you the same input field. Render the component twice, and the page holds the same id twice, so every copy finds the first input. Each copy gets its own ref, and React fills it with that copy's element.
>
> **DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> ~inputRef.current.focus()~; // The input of this copy of GuestList
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> document.~getElementById('guest-input')~.focus(); // **WRONG:** the first input on the page, even from the Dinner list
> ```

Plain JavaScript already has a way to reach the input field: give it an id and search the page for it, as in Lesson 01. Here are both ways:

```jsx title="Reaching the input field by its id, and through a ref"
<input ~id="guest-input"~ /> {/* With the id: one name for the whole page */}
document.~getElementById('guest-input')~.focus(); // Searches the whole page for that name

<input ~ref={inputRef}~ /> {/* With the ref: React puts this <input> into this copy's ref */}
~inputRef.current~.focus(); // Reads the ref of this copy of GuestList
```

## PRINCIPLE | `inputRef.current` during rendering: it is still `null` on the first render

> [!PRINCIPLE]
> **Principle 4: Commit: inputRef.current Is null During the First Render**
>
> *React fills a ref during the commit, so during the first render `ref.current` is `null`, and during later renders it still holds the old element; read DOM refs in event handlers, never during rendering.*
>
> Your component returns its JSX first, and React creates the input field later, in the commit. A call on `inputRef.current` in the body of the component finds `null`, throws a `TypeError`, and React removes the whole page. Skipping the call with `?.` hides the crash but still gives no focus. Use the event handler, `autoFocus`, or an Effect.
>
> **DO THIS:**
> ```jsx
> function handleAdd() {
>   ~inputRef.current.focus()~; // After the click: the input field is on the page
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const inputRef = useRef(null);
> ~inputRef.current.focus()~; // **WRONG:** during rendering, current is null and the page goes blank
> ```

The call to `focus` works in `handleAdd`. Put the exact same line in the body of the component, and the page goes blank:

```jsx title="The same call to focus in the body of the component, and in the handler"
export default function GuestList({ title }) {
  const inputRef = useRef(null);
  ~inputRef.current.focus()~; // In the body: runs while React renders GuestList

  function handleAdd() {
    ~inputRef.current.focus()~; // In the handler: runs when the user clicks Add
  }
}
```

It may look the same, but it is NOT the same thing! The line in the handler runs when the user clicks, long after the commit. The line in the body runs during rendering, before React has created the input field.

Remember what "during rendering" means (Lesson 30): while React runs your component function, its body and the JSX it returns. An event handler is written inside the component, but its code runs later, on the click.

A developer wants the cursor in the Lunch list as soon as the page opens. So the developer writes the call at the top of the component:


Here is what happens when the page opens:

2. `useRef` returns the ref object, with `current` set to `null`.
3. The body reaches the call to `focus` while `inputRef.current` is still `null`.

5. React removes the whole page. The `Component` reference says: "if your application throws an error during rendering, React will remove its UI from the screen."

### Skipping the call does not focus the input

To silence the error, a developer may skip the call while the ref is empty. Optional chaining, `?.`, does exactly that. It calls `focus` only when `inputRef.current` holds an element.

```jsx title="src/components/GuestList.jsx" startLine="8" bad="9"
  const inputRef = useRef(null);
  inputRef.current~?.~focus(); // **WRONG:** no crash, but the first render still finds null, so nothing gets focus
```

The page comes back, but the cursor is still not in the input field when the page opens. The first render still finds `null`, so the call is skipped at the one moment it was meant for.

Focusing an input field when the page opens has two right tools. The simpler one is the `autoFocus` prop. The `<input>` reference says: "If `true`, React will focus the element on mount."

```jsx title="Focusing the input field when it appears on the page"

```

The other tool is an Effect, which Lesson 32 teaches. The docs: "If you want to do something with a ref, but there is no particular event to do it in, you might need an Effect." Our page needs focus after a click, so the call stays in `handleAdd`.

## PRINCIPLE | `ref.current`: focus, scroll, and measure, but never change what React drew

> [!PRINCIPLE]
> **Principle 5: Non-Destructive Actions: Never Change an Element That React Manages**
>
> *Use a DOM ref for non-destructive actions such as focusing, scrolling, and measuring; do not change, add, or remove elements that React manages, because React keeps updating them from the JSX and does not know about your change.*
>
> Removing an element through a ref looks the same as hiding it through state, for one click. But React still counts the element as on the page, so its next update crashes. State decides what the page shows. A ref is for the few jobs state cannot say.
>
> **DO THIS:**
> ```jsx
> <button onClick={() => ~setShow(!show)~}>Toggle with setState</button> {/* React removes the line itself */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button onClick={() => ~ref.current.remove()~}>Remove from the DOM</button> {/* **WRONG:** React still counts the line as on the page */}
> ```

A ref hands you the real element. And the browser lets you do anything with it, even remove it from the page. The docs show what happens then, with two buttons and one line of text:

```jsx title="The docs' example: hiding a line through state, and removing it through a ref"
import { useState, useRef } from 'react';

export default function Counter() {
  const [show, setShow] = useState(true);
  const ref = useRef(null);

  return (
    <div>
      <button onClick={() => { ~setShow(!show)~; }}>Toggle with setState</button> {/* Changes state: React removes or adds the line */}
      <button onClick={() => { ~ref.current.remove()~; }}>Remove from the DOM</button> {/* Removes the line behind React's back */}
      {show && <p ref={ref}>Hello world</p>}
    </div>
  );
}
```

```page width=text caption="The docs' example when the page opens: two buttons and the line Hello world."
line: [Toggle with setState] [Remove from the DOM]
line: Hello world
console: quiet
```

`remove` is a browser method that takes an element off the page. Both buttons make Hello world disappear. It may look the same, but it is NOT the same thing! Only `setShow` tells React.

### The toggle that worked now crashes the page

The user clicks Toggle with setState a few times, and Hello world hides and shows each time. Then:
1. With Hello world on the page, the user clicks Remove from the DOM. The `remove` call takes the `<p>` element off the page.
2. Nobody tells React. `show` is still `true`, and React still counts its `<p>` as on the page.
3. The user clicks Toggle with setState. `show` becomes `false`, and React goes to take its `<p>` off the page.
4. The `<p>` is no longer there. The browser throws an error, and the page crashes.

```page width=text caption="After Remove from the DOM, the next click on Toggle with setState crashes the page."
blank
console: Uncaught NotFoundError: Failed to execute 'removeChild' on 'Node': The node to be removed is not a child of this node.
  warn: An error occurred in the <p> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The docs explain: "This is because you've changed the DOM, and React doesn't know how to continue managing it correctly."

React updates the elements it built from your JSX (Lesson 13). Your code changed those elements behind its back. So the next update by React no longer matches what is on the page.

### Read, focus, scroll, measure: these change nothing

The docs call the elements that React created from your JSX, and keeps updating, "DOM nodes managed by React". Their rule, from the Recap: "Avoid changing DOM nodes managed by React."

Changing them means changing their text, adding children to them, or removing them. The docs warn that it "can lead to inconsistent visual results or crashes like above."

Reading an element, or asking it to focus, scroll, or report its size, changes nothing that React built. The docs call these non-destructive actions: "If you stick to non-destructive actions like focusing and scrolling, you shouldn't encounter any problems."

Our guest list already follows the rule. Its ref only calls `focus`, and the list itself changes through `setGuests`.

The docs allow one exception: "You can safely modify parts of the DOM that React has *no reason* to update." For example, "if some `<div>` is always empty in the JSX, React won't have a reason to touch its children list."

## For the Interview

> **The Interview Question:** How do you reach a DOM node from React to focus it, scroll it, or measure it?

### How to Answer Clearly in 30 Seconds

"With a ref. React updates the DOM from the JSX, but JSX has no way to say 'put the cursor here', 'scroll to this', or 'how wide is this', so I need the real node. I create a ref with `useRef(null)` and pass it to a built-in tag as `ref={inputRef}`. After React creates the node in the commit, it puts it into `inputRef.current`, and when the node is removed, it sets `current` back to `null`. Then, in an event handler, I call the browser's own APIs on it: `focus`, `scrollIntoView`, `offsetWidth`, or `getBoundingClientRect`. Three rules keep it right:
1. **A ref, not `document.getElementById`**: an id is searched on the whole page, so a component used twice finds the first copy's input, while a ref belongs to one copy.
2. **Never read the DOM ref during rendering**: on the first render it is still `null`, so I read it in event handlers, or in an Effect when there is no event.
3. **Only non-destructive actions**: focusing, scrolling, and measuring are safe; removing or changing a node that React manages can crash the next update."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"How do you focus an edit field the moment it appears, for example after a click on Edit?"**
   The call to `focus` in the click handler does not work there, because the input does not exist yet when the handler runs. The setter only asks for a render, so `inputRef.current` is still `null`. The simplest tool is the `autoFocus` prop: "If `true`, React will focus the element on mount." With a ref, the job takes an Effect, which Lesson 32 teaches, since the docs say: "If you want to do something with a ref, but there is no particular event to do it in, you might need an Effect." To make React update the DOM at once inside the handler, there is `flushSync`, which Lesson 65 teaches.
2. **"Can you pass a ref to your own component, such as `<MyInput ref={inputRef} />`?"**
   Only if the component takes `ref` and passes it on to a built-in tag inside. The docs say: "By default, your own components don't expose refs to the DOM nodes inside them." Lesson 85 shows how a component passes `ref` on. With `useImperativeHandle`, which Lesson 50 teaches, the component can give the parent only a few methods, such as `focus`, instead of the whole node. The docs warn that "manually manipulating *another* component's DOM nodes can make your code fragile."
3. **"How do you scroll to a row you just added to a list, and why does it lag?"**
   One `useRef` for each row does not work, because a Hook must be called at the top level of a component, never inside `map`, as Lesson 38 teaches. The docs use a ref callback instead, a function in the `ref` attribute, which Lessons 86 and 99 teach. When the handler adds a row and scrolls in the same click, the new row is not in the DOM yet, because the setter "does not immediately update the DOM". The docs say: "This is why scrolling always 'lags behind' by one item." `flushSync`, from Lesson 65, makes React update the DOM before the scroll.

```tree dir=right caption="Interview comparison: reaching the input by its id vs. through a ref."
`document.getElementById` vs. a ref in an interview
- !By its id [`document.getElementById`] | Searches **the whole page** | With two copies, returns **the first input** every time
- +Through a ref [`ref={inputRef}` `inputRef.current`] | React fills it **in the commit**, **one per copy** | Each copy reaches **its own input**, in the event handler
```
