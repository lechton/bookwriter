## VS | A Class Component vs. a Function Component: the same props in, the same JSX out, only the places change

> Before 2019, a React component that remembered anything had to be written as a JavaScript class, and many codebases at work are still full of them. **A class component is the same component you already write, with its props, its state, and its handlers all moved onto one object, `this`.** Once you know where each piece moved, you can read an old class, fix it, or translate it into a function without breaking it.

You open a file at work and see `class Post extends Component`, a constructor full of `bind` lines, `this.state`, and `this.setState`. It looks like a different React. It is not. Hooks arrived in React 16.8, in February 2019. Before that, a component that held state was written as a class. Those classes still run in React 19, and older codebases are full of them.

The good news: you already know everything a class component does. It receives props, keeps state between renders, handles clicks, and returns JSX. The class only moves each piece to a new place. The props move to `this.props`. The state moves to `this.state`. The setter becomes `this.setState`. The JSX moves into a method named `render`.

**Why:** Two of those moves change how the code behaves, and both cause real bugs. First, `this.setState` merges the fields you give it into the old state, while a setter from `useState` replaces the whole state. Second, a method loses its `this` when React calls it on a click, so a handler that was never bound throws an error. A developer who reads a class as "a function with strange names" deletes a line that looked useless, or translates the class line by line. The user then sees a button that does nothing, or a button that changes back by itself.

### Back to Classes in Plain JavaScript

Remember classes from plain JavaScript? A class is a template for objects. You write it once, and `new` makes as many objects from it as you need:

```js title="A class in plain JavaScript"
class Dog {
  constructor(name) {
    ~this.name = name~; // Runs once for each new object, and gives it its first field
  }
  bark() {
    console.log(~this.name~ + ' says woof'); // this is the object bark was called on
  }
}

const rex = ~new Dog('Rex')~; // Makes one object from the class
rex.bark(); // The Console shows Rex says woof
```

> [!DEFINITION]
> **What is a class?** [NEW] A class is a template for making objects. `new Dog('Rex')` makes one object from the `Dog` class, and that object is called an instance.
> A method is a function written inside a class, such as `bark`.
> The constructor is the method JavaScript runs once, the moment `new` makes an instance. It gives the instance its first fields.
> Inside a method, `this` is the instance the method was called on. `rex.bark()` calls `bark` on `rex`, so `this.name` is `'Rex'` (Lesson 96).

Now the React part. In a class component, you never write `new`. React writes it for you. When React meets the tag `<Greeting name="Taylor" />`, it does three things:
1. It makes one instance of `Greeting`.
2. It puts the props of the tag on that instance, as `this.props`.
3. It calls the `render` method of that instance to get the JSX.

### The Smallest Class Component

Here is the same greeting written both ways:

```jsx title="Greeting as a class"
import { Component } from 'react';

class Greeting ~extends Component~ { // Builds Greeting on top of the Component class from React
  ~render()~ { // React calls render on the instance to get the JSX
    return <h1>Hello, {this.props.name}!</h1>;
  }
}
```

```jsx title="Greeting as a function"
function Greeting({ ~name~ }) { // The props arrive as the first parameter
  return <h1>Hello, {name}!</h1>;
}
```

Both forms are used with the same tag:

```jsx title="One tag for either form"
<Greeting ~name="Taylor"~ /> {/* The class and the function both receive name */}
```

```page width=text caption="What both forms put on the page."
heading: Hello, Taylor!
console: quiet
```

**Yes, it is the exact same component!** Both receive the props of the tag, and both return the same JSX. The class moves only two things:
1. The JSX goes inside a method named `render`.
2. The props come from `this.props`, not from a parameter.

> [!DEFINITION]
> **What does extends mean?** [NEW] To extend something is to build on it. `class Greeting extends Component` builds `Greeting` on top of `Component`, a class that React gives you. React's docs call it "the base class".
> Every instance of `Greeting` gets everything `Component` has. That is where `this.props` and `this.setState` come from: you never write them yourself.
> The browser never learns which form made the heading. The Elements panel shows the same `<h1>` for the class and for the function (Lesson 96).

### The Rule of Thumb: every `this.` has a place in a function

**Read every `this.` in a class as a question: where does this piece live in a function?** The answer is always one of these:

| In the class | In a function |
| :--- | :--- |
| `this.props.name` | the parameter `name` |
| `this.state = { liked: false, saved: false }` | one `useState` call for each field |
| `this.setState({ liked: true })` | the setter `setLiked(true)` |
| the method `handleLike` and its `bind` line | a function `handleLike` inside the component |
| the `return` inside `render` | the `return` of the function |
| the constructor | nothing |

When you meet a class at work, you have three choices:
1. **Read it and keep it.** This fits a small fix in a class that works. React's docs say: "Class components are still supported by React, but we don't recommend using them in new code."
2. **Translate it into a function.** This fits a class that needs a new feature, because Hooks do not work inside a class. The docs say: "We recommend defining components as functions instead of classes."
3. **Keep it as a class, because no function can do the job.** This is the case of an error boundary (Lesson 72). The docs say: "There is currently no way to write an Error Boundary as a function component."

A senior developer also knows the five places where readers go wrong:
1. **`this` inside a method does not always mean the component.** It means the component only when the method is called on the component. Principle 4 shows the crash.
2. **`this.setState({ liked: true })` and a setter called with `{ liked: true }` are not the same.** The first merges `liked` into the state. The second replaces the whole state. Principles 3 and 5 show the difference.
3. **`this.setState` does not change `this.state` right away.** Just like a setter, it changes the value only for the next render (Lesson 15).
4. **Not every class needs a constructor.** React's docs say: "If you use modern JavaScript syntax, constructors are rarely needed."
5. **A Hook cannot add a feature to the old class.** React's docs say that Hooks "are not supported inside class components."

The rest of the lesson reads one real class, piece by piece, and then translates it.

## SECTION | A Photo Post with Like and Save

Picture a photo feed, like Instagram. Each post shows who took the photo, and two buttons under it: Like and Save. The user clicks Like, and the button reads Liked. The user clicks Save, and the button reads Saved.

```page width=text caption="The post when the page opens: the author line and two buttons."
line: Photo by Mia
line: [Like] [Save]
console: quiet
```

```page width=text caption="The same post after the user clicks Like and then Save."
line: Photo by Mia
line: [Liked] [Saved] | good
console: quiet
```

Our team inherits this post. A developer wrote it as a class in 2019, before Hooks. Today another developer must read it, fix it, and maybe translate it into a function.

The project has three files in `src/`:

```files title="photo-post: File Explorer" caption="How the files of our photo post sit inside src/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it inside `<StrictMode>`
  App.jsx | parent | Exports `App` as default and renders `<Post author="Mia" />`
  Post.jsx | class component | Exports the 2019 `Post` class as default
```

`App` is a function component, and it renders the class like any other tag:

```jsx title="src/App.jsx"
import Post from './Post.jsx';

export default function App() {
  return <Post ~author="Mia"~ />; // A function component renders a class component like any tag
}
```

The 2019 `Post.jsx` has four pieces, the same four that every old codebase shows:
1. The `render` method and `this.props`.
2. The constructor and `this.state`.
3. `this.setState`.
4. The methods bound in the constructor.

Each principle reads one piece. Then Principle 5 translates the whole class into a function.

**PRINCIPLES:** A class component is the component you already know, with every piece moved onto one object, `this`. Five principles follow:
1. **Principle 1: `render()` Returns What the Post Shows.** React calls `render` on the instance and reads the props from `this.props`. Hooks do not work inside a class.
2. **Principle 2: The Constructor Fills `this.state` Before the First Render.** All the state of a class is one object. The constructor sets it once, after `super(props)`. A class field does the exact same job.
3. **Principle 3: `this.setState` Merges Only the Fields It Is Given.** `this.setState({ liked: true })` changes `liked` and keeps every other field. The new state appears only on the next render.
4. **Principle 4: An Unbound `this.handleLike` Crashes the Click.** React calls a handler alone, so `this` is `undefined`, and the click throws a `TypeError`. `bind` in the constructor, or an arrow function in a class field, fixes it.
5. **Principle 5: One `useState` Call per Field Replaces `this.state`.** A setter replaces the whole state and does not merge, so one state object with partial updates loses fields.

## PRINCIPLE | `render()`: React calls it on the instance, and the props of the tag are on `this.props`

> [!PRINCIPLE]
> **Principle 1: `render()` Returns What the Post Shows**
>
> *A class component extends React's `Component`. React calls its `render` method to get the JSX, and the method reads the props from `this.props`.*
>
> A class looks like a different React, but it takes the same props and returns the same JSX as a function. Only the places change: the JSX moves into `render`, and the props move onto `this.props`. Hooks stay out, because they work only in function components.
>
> **DO THIS:**
> ```jsx
> class Post extends Component {
>   render() {
>     return <p>Photo by {~this.props.author~}</p>; // React put the props of the tag on this.props
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> class Post extends Component {
>   render() {
>     const theme = ~useContext(ThemeContext)~; // **WRONG:** a Hook inside a class stops the page with Invalid hook call
>     return <p className={theme}>Photo by {this.props.author}</p>;
>   }
> }
> ```

### `Component` and `React.Component`: one base class, two names

A 2019 file names React's base class in one of two ways. Both appear in real codebases, and React's own Rules of Hooks page uses the second one:

```jsx title="Two ways to name the same base class"
class Post extends ~Component~ {} // After the line import { Component } from 'react'
class Post extends ~React.Component~ {} // After the line import React from 'react'
```

**Yes, it is the exact same thing!** The first line imports `Component` by name. The second line reads it from the `React` object.

### The post with only `render`

Our post starts with only the `render` method. The two buttons have fixed labels for now:

```jsx title="src/Post.jsx"
import { Component } from 'react';

export default class Post extends Component {
  ~render()~ { // React calls render on the Post instance to get the JSX
    return (
      <article>
        <p>Photo by {~this.props.author~}</p> {/* Shows Mia, from the tag Post author="Mia" */}
        <button>Like</button>
        <button>Save</button>
      </article>
    );
  }
}
```

```page width=text caption="The post rendered by the class: the author line and two buttons."
line: Photo by Mia
line: [Like] [Save]
console: quiet
```

The class never declares a prop, yet `this.props.author` holds `'Mia'`. React puts it there, in four steps:
1. `Post` extends `Component`, React's base class.
2. For the tag `<Post author="Mia" />`, React makes one instance of `Post`.
3. React puts the props of the tag on that instance, as `this.props`.
4. React calls `render` on that instance. So inside `render`, `this` is the instance, and `this.props.author` is `'Mia'`.

React's docs say it plainly: "Reading `this.props` in class components is equivalent to declaring props in function components." The name `render` is fixed. React looks for a method with exactly that name, and the docs say: "Only the `render` method is required."

`render` follows the same rules as the body of a function component. It must be pure: the same props and state give the same JSX (Lesson 14). In development, Strict Mode calls it twice and throws one result away (Lesson 47).

### A Hook inside the class stops the page

The app keeps its theme in a context named `ThemeContext` (Lesson 28), and the post must now read it. A developer who knows only function components writes the Hook inside `render`:

**DO NOT DO THIS:**
```jsx title="src/Post.jsx" startLine="3" bad="3"
export default class Post extends Component {
  render() {
    const theme = ~useContext(ThemeContext)~; // **WRONG:** Hooks do not work inside a class component
    return <article className={theme}>Photo by {this.props.author}</article>;
  }
}
```

React stops with an error that starts with "Invalid hook call. Hooks can only be called inside of the body of a function component." The error happens while React renders, so with no error boundary the whole page goes blank (Lesson 72).

The Rules of Hooks list this exact case: "Do not call Hooks in class components." The fix is to translate the class into a function, and Principle 5 shows how.

## PRINCIPLE | `constructor` and `this.state`: all the state is one object, ready before the first render

> [!PRINCIPLE]
> **Principle 2: The Constructor Fills `this.state` Before the First Render**
>
> *Set `this.state` once, before the first render: in `constructor(props)` right after `super(props)`, or as the class field `state = { ... }`. After that, only `this.setState` changes it.*
>
> A class has no `useState`. All its state lives in one object on the instance. The constructor fills that object before React first calls `render`, and it must call `super(props)` before it touches `this`. A class field does the exact same job with less code. The constructor holds no side effects, because Strict Mode runs it twice in development.
>
> **DO THIS:**
> ```jsx
> class Post extends Component {
>   constructor(props) {
>     ~super(props)~; // First line: Component sets up the instance, then this is safe to use
>     this.state = { liked: false, saved: false };
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> class Post extends Component {
>   constructor(props) {
>     ~this.state~ = { liked: false, saved: false }; // **WRONG:** this before super throws a ReferenceError
>     super(props);
>   }
> }
> ```

### VS | The Constructor vs. a Class Field: both set `this.state` before the first render

In a function, each piece of state comes from its own `useState` call. In a class, all the state is one object, stored on `this.state`. A 2019 file starts that object in one of two places.

The first place is the constructor:

```jsx title="Starting the state in the constructor"
class Post extends Component {
  constructor(props) {
    ~super(props)~; // 1. Runs the constructor of Component first
    ~this.state~ = { liked: false, saved: false }; // 2. All the state of the post, in one object
  }
}
```

You know the constructor from the `Dog` class: JavaScript runs it once, when a new instance is made. Here React makes the instance for the tag and passes the props of the tag to the constructor. So the constructor runs before the post first appears on the screen.

What is `super(props)`? Inside a class that extends another, `super` means the class you build on, here `Component`. `super(props)` runs the constructor of `Component` with the props. JavaScript forbids touching `this` before that line, so it always comes first.

The second place is a class field:

```jsx title="Starting the state with a class field"
class Post extends Component {
  ~state~ = { liked: false, saved: false }; // The same object, set on every new instance
}
```

A class field is a property written straight in the class body, outside any method. JavaScript sets it on each new instance as the instance is made. So `state = { ... }` gives every post its own `this.state`, with no constructor at all.

**Yes, it is the exact same thing!** Both give each new post the same `this.state`, before React first calls `render`. React's docs say: "If you use modern JavaScript syntax, constructors are rarely needed." React's own class examples use the class field.

```tree caption="Two ways to start the state of a class: in the constructor, or as a class field."
Two ways to give `Post` its first `this.state`
- +In the constructor [`super` `this.state = ...`] | Runs once for each **new instance** | `super` must come **before any use of `this`**
- +As a class field [`state = ...`] | Written straight in the **class body** | **Exact same result**, with no constructor at all
```

### One object in a class, one variable per field in a function

React's docs say: "Defining `state` in class components is equivalent to calling `useState` in function components." The job is the same. The shape is not:
- **The class** keeps every field in one object: `{ liked: false, saved: false }`.
- **A function** usually keeps each field in its own state variable: one for `liked`, one for `saved`.

This difference looks small. It decides how the class updates its state in Principle 3, and how a translation goes wrong in Principle 5.

### The post reads its labels from `this.state`

Our post gets its constructor. The two labels now come from the state:

```jsx title="src/Post.jsx" startLine="3"
export default class Post extends Component {
  constructor(props) {
    super(props);
    this.state = { liked: false, saved: false };
  }

  render() {
    return (
      <article>
        <p>Photo by {this.props.author}</p>
        <button>{~this.state.liked~ ? 'Liked' : 'Like'}</button> {/* false on the first render, so it reads Like */}
        <button>{~this.state.saved~ ? 'Saved' : 'Save'}</button> {/* false on the first render, so it reads Save */}
      </article>
    );
  }
}
```

The page looks as before: `Photo by Mia`, then Like and Save. The buttons have no handlers yet.

The constructor is the only place where your code may write `this.state = ...`. The docs say: "In all other methods, you need to use `this.setState()` instead." Suppose a click handler runs `this.state.liked = true`. The line changes the object, but React never hears about it. Nothing asks React for a new render, so the button stays on Like.

### Two mistakes in a 2019 constructor

The first mistake is touching `this` before `super(props)`:

**DO NOT DO THIS:**
```jsx title="src/Post.jsx" startLine="4" bad="2"
  constructor(props) {
    ~this.state~ = { liked: false, saved: false }; // **WRONG:** this is used before super, so JavaScript throws a ReferenceError
    super(props);
  }
```

A `ReferenceError` is the error JavaScript throws when code uses something that is not ready yet. It throws the moment React makes the instance, so the post never appears. MDN puts the rule in one line: in a class that extends another, `super` "must be called before the `this` keyword is used".

The second mistake is quieter. A 2019 constructor sometimes does more than set the state, for example, it sends a view of the post to an analytics server. In development, Strict Mode calls the constructor twice and throws one of the two instances away. So during development the server receives two views for one post. The docs say: "Do not run any side effects or subscriptions in the constructor." The class methods that run after the post appears belong to Lesson 97.

## PRINCIPLE | `this.setState`: only the fields you name change, and only on the next render

> [!PRINCIPLE]
> **Principle 3: `this.setState` Merges Only the Fields It Is Given**
>
> *`this.setState({ liked: true })` asks React for a new render in which `liked` is `true` and every other field of `this.state` stays as it was. The code that is already running still sees the old `this.state`.*
>
> A class keeps all its state in one object, so React lets each handler name only the field it changes. React merges that field into the state for the next render, and the rest of the object stays. Like every setter, `this.setState` is a request, not an instant change, so a handler that needs the new value computes it first.
>
> **DO THIS:**
> ```jsx
> handleLike() {
>   this.setState({ ~liked: !this.state.liked~ }); // Changes liked, and saved stays as it was
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> handleLike() {
>   this.setState({ liked: !this.state.liked });
>   saveLike(~this.state.liked~); // **WRONG:** this.state is still the old state, so the server gets the old value
> }
> ```

### The object you give `this.setState` is a list of changes

The post is saved but not liked, and the user clicks Like:

```jsx title="this.setState with one field, while the state holds two"
state = { liked: false, saved: true }; // Before the click: saved, not liked

handleLike() {
  this.setState({ ~liked: true~ }); // Next render: liked is true, and saved is still true
}
```

The object you give `this.setState` is not the whole new state. It is a list of changes. React copies the fields it names into `this.state` and keeps every field it does not name. The docs say the object is "shallowly merged into `this.state`".

Shallow means one level only. React merges the top fields, here `liked` and `saved`, the way the three dots copy only the top level of an object (Lesson 17).

So these two calls do the same work:

```jsx title="Naming one field, and naming every field by hand"
this.setState({ ~liked: true~ }); // The merge keeps saved without being told
this.setState({ ~liked: true, saved: this.state.saved~ }); // The same next state, written out by hand
```

**Yes, it is the exact same thing!** The merge keeps `saved` for you. That is why a 2019 class never copies the other fields into its `this.setState` calls.

### The post gets its two handlers

Our post gets two methods, one per button. Each method changes one field:

```jsx title="src/Post.jsx" startLine="3"
export default class Post extends Component {
  constructor(props) {
    super(props);
    this.state = { liked: false, saved: false };
    this.handleLike = this.handleLike.bind(this);
    this.handleSave = this.handleSave.bind(this);
  }

  handleLike() {
    this.setState({ ~liked: !this.state.liked~ }); // Flips liked, and keeps saved
  }

  handleSave() {
    this.setState({ ~saved: !this.state.saved~ }); // Flips saved, and keeps liked
  }

  render() {
    return (
      <article>
        <p>Photo by {this.props.author}</p>
        <button onClick={~this.handleLike~}>{this.state.liked ? 'Liked' : 'Like'}</button> {/* Hands React the bound method */}
        <button onClick={this.handleSave}>{this.state.saved ? 'Saved' : 'Save'}</button>
      </article>
    );
  }
}
```

The two `bind` lines in the constructor make `this` work inside the two methods. Principle 4 shows what the click does without them.

`this.setState` is not written anywhere in `Post`. It comes from `Component`, like `this.props`. The docs say it "tells React that this component and its children need to re-render with the new state".

The user clicks Save, then Like:

```page width=text caption="The post after the user clicks Save: Like and Saved."
line: Photo by Mia
line: [Like] [Saved]
console: quiet
```

```page width=text caption="The post after the user then clicks Like: Liked and Saved."
line: Photo by Mia
line: [Liked] [Saved] | good
console: quiet
```

Save stays on Saved after the click on Like, because the merge kept `saved: true`.

### `this.state` still holds the old value right after `this.setState`

`this.setState` does not change `this.state` in the code that is already running. The docs say: "It only affects what `this.state` will return starting from the *next* render." This is the snapshot you already know from setters (Lesson 15).

Here is how that bites in a real handler. The post must also tell the server that the user liked it. Our server code gives us a function, `saveLike`, that sends the new value:

**DO NOT DO THIS:**
```jsx title="src/Post.jsx"
handleLike() {
  this.setState({ liked: !this.state.liked });
  saveLike(~this.state.liked~); // **WRONG:** on the first click the button shows Liked, but the server receives false
}
```

**DO THIS:**
```jsx title="src/Post.jsx"
handleLike() {
  const nextLiked = !this.state.liked;
  this.setState({ liked: nextLiked });
  saveLike(~nextLiked~); // The server receives true, the same value the button shows
}
```

Compute the new value first, keep it in a variable, and give that variable to both calls.

### The updater function

When a handler must update the same field several times in one event, the class passes a function instead of an object:

```jsx title="this.setState with an updater function, and a setter with one"
this.setState(~prevState => ({ liked: !prevState.liked })~); // React queues it and hands it the pending state
setLiked(~l => !l~); // The updater function of a setter, for comparison
```

**Yes, it is the exact same thing!** Each function receives the pending state, not the old `this.state` of the running code (Lesson 16).

## PRINCIPLE | `bind(this)` in the constructor: the handler keeps its instance when React calls it on a click

> [!PRINCIPLE]
> **Principle 4: An Unbound `this.handleLike` Crashes the Click**
>
> *`onClick={this.handleLike}` hands React the method alone. On the click, `this` is `undefined`, so `this.setState` throws a `TypeError`. Bind the method in the constructor, or write it as an arrow function in a class field.*
>
> In JavaScript, `this` depends on how a function is called, not on where it is written. React calls an event handler alone, and the class body runs in strict mode, so a method that was never bound gets `undefined` as `this`. The post renders fine, and only the click breaks. `bind` in the constructor, or an arrow function in a class field, ties the handler to its instance.
>
> **DO THIS:**
> ```jsx
> class Post extends Component {
>   state = { liked: false };
>   handleLike = ~() =>~ { // An arrow in a class field: this is the instance on every click
>     this.setState({ liked: !this.state.liked });
>   };
>   render() {
>     return <button onClick={this.handleLike}>{this.state.liked ? 'Liked' : 'Like'}</button>;
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> class Post extends Component {
>   state = { liked: false };
>   handleLike() {
>     this.setState({ liked: !this.state.liked });
>   }
>   render() {
>     return <button onClick={~this.handleLike~}>{this.state.liked ? 'Liked' : 'Like'}</button>; // **WRONG:** never bound, so this is undefined on the click
>   }
> }
> ```

### A method called on its object, and the same method called alone

This principle starts in plain JavaScript, with no React at all. Take the `Dog` class from the start of the lesson, and call `bark` in two ways:

```js title="Calling a method on its object, and calling it alone"
const rex = new Dog('Rex');
~rex.bark()~; // Called on rex: this is rex, and the Console shows Rex says woof

const bark = rex.bark;
~bark()~; // Called alone: this is undefined, and the line throws a TypeError
```

**It may look the same, but it is NOT the same thing!** Both lines run the very same function. The difference is how each line calls it:
- **`rex.bark()`** calls the function on the object `rex`, so `this` is `rex`.
- **`bark()`** calls the function alone, with no object in front, so `this` is `undefined`.

So `this` is decided by how a function is called, not by where it is written. The method is written inside the class, but that does not tie it to any instance.

Why `undefined`, and not some other value? Because a class body runs in strict mode. MDN says: "The body of a class is executed in strict mode even without the `"use strict"` directive." Strict mode is a stricter set of JavaScript rules, and one of them is that a function called alone gets `undefined` as `this`.

### VS | JavaScript Strict Mode vs. React `<StrictMode>`: the same name for two different things

The two share a name, but they are NOT the same thing:
- **JavaScript's strict mode** is a rule of the language. It is why `this` is `undefined` in a method called alone.
- **React's `<StrictMode>`** is a component. It calls your components twice in development, to show impure code (Lesson 47).

### `onClick={this.handleLike}` hands React the method alone

Now look at the Like button of our post:

```jsx title="src/Post.jsx" startLine="23"
<button onClick={~this.handleLike~}>{this.state.liked ? 'Liked' : 'Like'}</button> {/* Reads the method and hands it to React */}
```

`onClick={this.handleLike}` does what `const bark = rex.bark` did above. It reads the function from the instance and hands it over, here to React (Lesson 11). React calls it later, when the user clicks, and it calls it alone.

Suppose a teammate cleaned up the constructor and deleted the `bind` line for `handleLike`, because it looked like it did nothing:

```jsx title="src/Post.jsx" startLine="4"
  constructor(props) {
    super(props);
    this.state = { liked: false, saved: false };
    this.handleSave = ~this.handleSave.bind(this)~; // Only Save is still bound: the line for handleLike was deleted
  }
```

```page width=text caption="The post without the bind line for handleLike, when the page opens: no error yet."
line: Photo by Mia
line: [Like] [Save]
console: quiet
```

```page width=text caption="The same post right after the user clicks Like: the button stays on Like, and the Console shows a TypeError."
line: Photo by Mia
line: [Like] [Save] | bad
console: Uncaught TypeError: Cannot read properties of undefined (reading 'setState')
```

**The post renders with no error, and only the click on Like breaks.** Here is what happens, in order:
1. React renders the post. `render` reads `this.handleLike` and hands the function to `onClick`. Nothing calls it yet, so nothing breaks.
2. The user clicks Like.
3. React calls the function it was handed, alone, with no instance in front.
4. The class body runs in strict mode, so `this` inside `handleLike` is `undefined`.
5. The line `this.setState` asks `undefined` for a property, and JavaScript throws a `TypeError`.
6. The error happens inside a click handler, not while React renders, so React keeps the page on the screen. The Like button stays on Like.

The cause sits in the constructor, far from the button. That is what makes this bug slow to find. The same crash appears when a developer adds a third button, copies the `onClick` line from the other two, and forgets the constructor line. The three buttons look the same in `render`. The difference is in the constructor.

### Two fixes: `bind` in the constructor, or an arrow function in a class field

**The 2019 fix is `bind` in the constructor.** To bind is to tie two things together. MDN says `bind` "creates a new function that, when called, calls this function with its `this` keyword set to the provided value":

```jsx title="src/Post.jsx" startLine="4" good="4"
  constructor(props) {
    super(props);
    this.state = { liked: false, saved: false };
    this.handleLike = ~this.handleLike.bind(this)~; // Stores a copy of handleLike tied to this instance
    this.handleSave = this.handleSave.bind(this);
  }
```

The line works in three steps:
1. In the constructor, `this` is the new instance.
2. `this.handleLike.bind(this)` makes a new function that always calls `handleLike` with that instance as `this`.
3. The constructor stores the new function on the instance, under the same name. So `render` reads the bound copy and hands it to `onClick`.

**The shorter fix is an arrow function in a class field.** MDN says: "Arrow functions don't have their own bindings to `this`." An arrow uses the `this` of the place where it is written. In a class field, MDN says, "`this` refers to the class instance under construction", which means the new instance being made:

```jsx title="src/Post.jsx" startLine="3"
export default class Post extends Component {
  state = { liked: false, saved: false };

  handleLike = ~() =>~ { // An arrow in a class field: this is always the instance
    this.setState({ liked: !this.state.liked });
  };

  handleSave = () => {
    this.setState({ saved: !this.state.saved });
  };
```

The `render` method stays as it was, with `onClick={this.handleLike}` and `onClick={this.handleSave}`.

**Yes, it is the exact same thing on the page!** With `bind` in the constructor, and with an arrow in a class field, `onClick` gets a function whose `this` is the instance. The class field form needs no constructor at all, and it is the form React's docs use in their class examples.

```tree caption="Three ways to hand handleLike to onClick, and what this is when the user clicks."
What `this` is inside `handleLike` on the click
- !A method with no `bind` [`onClick={this.handleLike}`] | React calls the function **alone** | `this` is **`undefined`**, and the click throws a **`TypeError`**
- +`bind` in the constructor [`this.handleLike.bind`] | A copy **tied to the instance** | `this` is the **instance**, and the button reads **Liked**
- +An arrow in a class field [`handleLike` `=>`] | The arrow has **no `this` of its own** | `this` is the **instance**, and the button reads **Liked**
```

## PRINCIPLE | One `useState` per field: the translated function keeps every field the class kept

> [!PRINCIPLE]
> **Principle 5: One `useState` Call per Field Replaces `this.state`**
>
> *To translate a class, move the body of `render` into a function, read the props as parameters, give each field of `this.state` its own `useState` call, turn each method into a function inside the component, and remove every `this.`. A setter replaces the state, so one state object needs a spread on every update.*
>
> A class translated line by line looks right on the first load. But `this.setState` merged each field into the state, and a setter replaces the whole state. So one state object with partial updates erases every field the click did not name. One `useState` call per field gives each setter its own field, and a spread of the old object keeps the rest.
>
> **DO THIS:**
> ```jsx
> const [liked, setLiked] = useState(false);
> const [saved, setSaved] = useState(false);
> function handleLike() {
>   ~setLiked(!liked)~; // Changes liked only, and saved has its own variable
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [post, setPost] = useState({ liked: false, saved: false });
> function handleLike() {
>   setPost({ ~liked: !post.liked~ }); // **WRONG:** replaces the whole state, so saved is gone
> }
> ```

### React's three steps to translate a class

The post must now read the theme with `useContext`, a feature that needs a Hook, so the team translates it into a function. React's docs call this migrating, and they give three steps:
1. Declare a function with the state variables it needs.
2. Turn each method into a function inside the component.
3. Replace every reference that starts with `this` with the variables and functions you defined.

Here is the post after the three steps:

```jsx title="src/Post.jsx"
import { useState } from 'react';

export default function Post({ ~author~ }) { // this.props.author becomes the parameter author
  const [liked, setLiked] = ~useState(false)~; // The liked field becomes its own state variable
  const [saved, setSaved] = useState(false);

  function handleLike() {
    ~setLiked(!liked)~; // this.setState with liked becomes setLiked
  }

  function handleSave() {
    setSaved(!saved);
  }

  return (
    <article>
      <p>Photo by {author}</p>
      <button onClick={~handleLike~}>{liked ? 'Liked' : 'Like'}</button> {/* No this, so nothing to bind */}
      <button onClick={handleSave}>{saved ? 'Saved' : 'Save'}</button>
    </article>
  );
}
```

**Yes, it is the exact same post!** The page and every click behave as they did with the class. Each piece of the class found its place from the Rule of Thumb:
1. `this.props.author` became the parameter `author` (Lesson 08).
2. Each field of `this.state` got its own `useState(false)`.
3. Each method became a function inside `Post`.
4. The `return` of `render` became the `return` of the function.
5. The constructor disappeared.

There is nothing to bind, because there is no instance and no `this`. `handleLike` is written inside `Post`, and a function written inside another function reads its variables. So `handleLike` sees the `liked` and `setLiked` of this render (Lesson 15).

### The trap: one state object with a setter loses a field

There is a shorter translation that looks just as faithful. It keeps the one state object of the class:

**DO NOT DO THIS:**
```jsx title="src/Post.jsx" startLine="4" bad="4,8"
  const [post, setPost] = useState({ liked: false, saved: false });

  function handleLike() {
    setPost({ ~liked: !post.liked~ }); // **WRONG:** the whole state becomes this one field, and saved is gone
  }

  function handleSave() {
    setPost({ ~saved: !post.saved~ }); // **WRONG:** the whole state becomes this one field, and liked is gone
  }
```

**It may look the same as `this.setState`, but it is NOT the same thing!** `this.setState({ liked: true })` merges `liked` into the state. A setter does not merge. React's docs for `useState` describe its argument as "The value that you want the state to be." So `setPost({ liked: true })` makes `{ liked: true }` the whole state.

**Beware: with one object and a setter, each click keeps only the field it names.** The page shows it after two different clicks:

```page width=text caption="The translated post with one state object, after the user clicks Save: Like and Saved, as expected."
line: Photo by Mia
line: [Like] [Saved]
console: quiet
```

```page width=text caption="The same post after the user then clicks Like: Saved has turned back into Save."
line: Photo by Mia
line: [Liked] [Save] | bad
console: quiet
```

Here is what happens, in order:
1. The page opens with `{ liked: false, saved: false }`, so the buttons read Like and Save.
2. The user clicks Save. `setPost({ saved: true })` makes `{ saved: true }` the whole state. `post.liked` no longer exists, so it reads `undefined`, and the Like button still reads Like.
3. The user clicks Like. `setPost({ liked: true })` makes `{ liked: true }` the whole state. Now `saved` no longer exists.
4. The Save button goes back to Save. Nobody clicked it, and the Console stays quiet.

The bug hides well. A quick test that clicks one button passes. The bug shows only after two different clicks in a row. A team that translates many classes by search and replace, turning each `this.setState` into one setter, ships this bug in every class whose methods change one field at a time.

### Two fixes: one variable per field, or a spread of the old object

The first fix is the translation above: one `useState` call per field. Each setter owns one field, so there is nothing to lose.

The second fix keeps one object and copies the old fields by hand, with the three dots (Lesson 17). `handleSave` gets the same spread:

```jsx title="src/Post.jsx" startLine="6" good="2"
  function handleLike() {
    setPost({ ~...post~, liked: !post.liked }); // Copies saved from the old object, then changes liked
  }
```

**Yes, it is the exact same page as with two `useState` calls!** The spread does by hand what `this.setState` did for free.

When does one object fit? The docs say: "if you find that you often change two state variables together, it might be easier to combine them into one." Liked and Saved change on separate clicks, so two variables fit our post (Lesson 22).

### The complete files

Here is the post as our team inherited it, the 2019 class with all four pieces:

```jsx title="src/Post.jsx, the 2019 class"
import { Component } from 'react';

export default class Post extends Component {
  constructor(props) {
    ~super(props)~; // Principle 2: super first, then this is safe
    this.state = { liked: false, saved: false }; // Principle 2: all the state in one object
    this.handleLike = ~this.handleLike.bind(this)~; // Principle 4: ties the method to this instance
    this.handleSave = this.handleSave.bind(this);

  handleLike() {
    this.setState({ ~liked: !this.state.liked~ }); // Principle 3: merges liked, keeps saved
  }

  handleSave() {
    this.setState({ saved: !this.state.saved });
  }

  ~render()~ { // Principle 1: React calls render on the instance
    return (
      <article>
        <p>Photo by {this.props.author}</p>
```

### Where each piece lives, in the class and in the function

| Piece | The 2019 class | The function today |
| :--- | :--- | :--- |
| **The JSX** | Returned by the `render` method | Returned by the function |
| **The props** | Read from `this.props.author` | Read from the parameter `author` |
| **The state** | One object on `this.state`, set in the constructor or a class field | One `useState` call per field |
| **The update** | `this.setState` merges the given fields | A setter replaces the whole state |
| **The handlers** | Methods, bound in the constructor or written as arrow class fields | Plain functions inside the component, with nothing to bind |
| **Hooks** | Do not work | Work |

Remember the one sentence of this lesson. **A class component is the same component you already write, with its props, its state, and its handlers all moved onto one object, `this`.**

## For the Interview

> **The Interview Question:** How do class components work, and how do you read one today?

### How to Answer Clearly in 30 Seconds

"A class component is the same component model as a function: props in, JSX out, and state that React keeps between renders. The class extends React's `Component` and returns its JSX from a `render` method. Everything lives on one object, `this`:
1. **Props** are on `this.props`.
2. **State** is one object on `this.state`, set once in the constructor after `super(props)`, or as a class field.
3. **`this.setState`** merges the fields it gets into the state, and the new state appears on the next render.
4. **Handlers** must be bound in the constructor, or written as arrow class fields, because React calls a handler without its instance, and `this` would be `undefined`.

To read one today, I map each piece onto a function. `this.props` becomes parameters, and each state field gets its own `useState` call. Methods become inner functions, and every `this.` goes away. Classes are still supported, but React recommends functions for new code, and Hooks only work in functions."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why did 2019 code bind every method in the constructor?"**
   Because `this` in JavaScript depends on how a function is called, not where it is written. `onClick={this.handleLike}` hands React the function alone, and React calls it on the click with no object in front. The class body runs in JavaScript's strict mode, so `this` is `undefined`, and `this.setState` throws `TypeError: Cannot read properties of undefined (reading 'setState')`. The line `this.handleLike = this.handleLike.bind(this)` stores a copy tied to the instance. An arrow function in a class field does the same without a constructor, because an arrow takes `this` from where it is written. A function component has no `this`, so there is nothing to bind.

2. **"What is the difference between `this.setState` and the setter from `useState`?"**
   They share two things. First, both ask React for a new render, and neither changes the value in the running code: `console.log(this.state.liked)` right after `this.setState` prints the old value, just as with a setter. Second, both accept an updater function, `this.setState(prev => ...)` or `setLiked(l => !l)`. The one difference: `this.setState` shallowly merges the given object into `this.state`, while a setter replaces the whole state. So translating `this.setState({ liked: true })` into `setPost({ liked: true })` on one object erases every other field. Split the fields into separate `useState` calls, or spread the old object: `setPost({ ...post, liked: true })`.

3. **"Can you still write class components in React 19, and when do you still need one?"**
   Yes, they are still supported, but React's docs recommend functions for new code. Hooks do not work inside a class, so a class that needs a new feature, such as reading a context with `useContext`, gets translated. One case still needs a class: an error boundary (Lesson 72). React's docs say "there is currently no way to write an Error Boundary as a function component". React 19 also removed some old class features, such as `propTypes`, the legacy `contextTypes`, and string refs with `this.refs`. The class methods that run after the component appears, such as `componentDidMount`, belong to Lesson 97.

```tree dir=right caption="Interview comparison: how each piece of a 2019 class maps onto a function component today."
From a 2019 class to a function today
- +Props and JSX [`this.props` `render`] | Become the **parameters** and the **return** of the function | Same props in, **same JSX out**
- +State [`this.state` `this.setState`] | Become **one `useState` call per field** | `this.setState` **merged**, a setter **replaces**
- +Handlers [`bind` `=>`] | Become **plain functions** inside the component | **No `this`**, so nothing to bind
```
