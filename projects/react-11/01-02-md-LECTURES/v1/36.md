# Lecture 36: Separating Events from Effects with useEffectEvent

*(How can an Effect read a value without running again every time that value changes?)*

> INTERVIEW QUESTION | ❱ CORE | How do you keep non-reactive values from re-running an effect?

---

## VS | `useEffect` vs. `useEffectEvent`: the Effect runs again when a value changes, the Effect Event only reads it

> **`useEffectEvent` lets an Effect read the latest value without running again when that value changes.**

In React, an Effect often needs to read a value that has nothing to do with why it runs, like a Mute checkbox, the color theme, or the number of items in a cart when a page visit is logged. Normally, every value an Effect reads goes into its dependency array, and every change of that value runs the Effect again. That is right for the value the Effect is about, but wrong for a value it only glances at. This is why React gives us `useEffectEvent`.

Take a chat room with a Mute notifications checkbox at the top. When a message arrives, the app plays a sound, unless Mute is ticked. Ask yourself: when the user ticks Mute, should the app leave the room and connect again? No. Only the sound should stop. The connection depends on the room, and the sound depends on the checkbox.

**Why:** If you read the checkbox state directly inside `useEffect`, the linter asks you to put it in the dependency array. Let's follow what happens then, step by step, when the user ticks Mute:

> Mute ticked → handler stores the tick in the state variable `muted` → component renders again → React sees a new `muted` in the array → cleanup disconnects → Effect connects again

So every tick or untick of Mute disconnects from the chat server and connects again from scratch, just to turn a sound on or off. The Effect runs again for a value it only reads at the moment a message arrives. **Therefore, you need to read the checkbox inside a function made with `useEffectEvent`.** The Effect then sees its latest value, and depends only on the room.

### Two Things the User Does

Think of a chat app with rooms, like Slack. A menu lets the user pick a room, and next to it sits the Mute notifications checkbox. The user does two everyday things, and expects two different results:
1. **The user picks another room.** The app leaves the old room and connects to the new one.
2. **The user ticks Mute notifications.** The notifications stop. Nothing else changes: same room, same connection.

In plain JavaScript, this is easy. You connect once. The message handler reads the `muted` variable each time a message arrives:

```js title="Plain JavaScript: the handler reads muted when a message arrives"
let muted = false;
const connection = createConnection(serverUrl, 'general');
connection.connect();
connection.on('message', msg => {
  if (~!muted~) showNotification('New message: ' + msg); // Reads muted now, at the moment the message arrives
});
muteCheckbox.addEventListener('change', e => {
  ~muted = e.target.checked~; // Changes the variable, and the connection stays as it is
});
```

Changing `muted` never touches the connection. The handler simply reads the current value when it runs.

In React, the connection lives in an Effect (Lesson 35). The messages arrive through that connection, so the check of `muted` must sit inside the same Effect. And here is the problem: every prop and every state variable the Effect reads must go in its dependency array.

```jsx title="React, first try: muted goes in the array"
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  connection.on('message', msg => {
    if (!muted) showNotification('New message: ' + msg);
  });
  return () => connection.disconnect();
}, ~[roomId, muted]~); // muted is in the array, so every tick of the checkbox reconnects the chat
```

The user only wanted silence, and the chat disconnects and connects again. React's docs describe this exact case: "every time `isMuted` changes ... the Effect will re-synchronize, and reconnect to the chat. This is not the desired user experience!"

React's answer is a Hook called `useEffectEvent`. You move the one check that reads `muted` out of the Effect, into a function React calls an **Effect Event**. The Effect calls it when a message arrives:

```jsx title="React with an Effect Event: muted leaves the array"
const onMessage = ~useEffectEvent~(msg => { // An Effect Event: reads the latest muted each time it runs
  if (!muted) showNotification('New message: ' + msg);
});

useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  connection.on('message', msg => onMessage(msg));
  return () => connection.disconnect();
}, ~[roomId]~); // Only roomId: picking a room reconnects, ticking the checkbox does not
```

So you get the plain JavaScript behavior back. A function reads the current value when it runs, and the connection stays.

> [!DEFINITION]
> **What is a reactive value?** [REVIEW] A reactive value is a value that a render can change: a prop, a state variable, or a variable calculated from them inside the component.
> When an Effect reads a reactive value, the linter asks you to put it in the dependency array.
> After every render, React compares the array with the last one. If one value changed, React runs the old cleanup, then the setup again. For a chat, that means disconnect, then connect.
> `roomId` and `muted` are both props. So for the linter, they are the same kind of value (Lesson 35).

> [!DEFINITION]
> **What is an Effect Event?** [NEW] An Effect Event is a function you get back from `useEffectEvent`, a Hook React added in version 19.2. You give it a function, and it gives you back a new function.
> You call it from inside your Effect, like any function. Each time it runs, it reads the latest props and state.
> It is not reactive: a change of the values it reads never makes the Effect run again. So neither the Effect Event nor the values it reads go in the dependency array.
> React's docs: "You can think of Effect Events as being very similar to event handlers. The main difference is that event handlers run in response to user interactions, whereas Effect Events are triggered by you from Effects."
> So, once more: the Effect runs again when a value changes. The Effect Event only reads it (Lesson 36).

### The Rule of Thumb: does the user want the Effect to run again?

**Ask one question about every value the Effect reads: when it changes, does the user want the Effect to run again? If yes, keep it in the array. If no, read it in an Effect Event.**
- **`roomId`: yes.** React's docs: "From the user's perspective, a change to the `roomId` does mean that they want to connect to a different room."
- **`muted`: no.** Ticking the checkbox means the user wants silence, not a new connection.

There are four ways to handle a value that an Effect reads (Lesson 35). This lesson teaches the second one:
1. **Keep it in the dependency array** when a change means the Effect must run again, such as `roomId`.
2. **Read it in an Effect Event** when you only need it at the moment something happens, such as `muted` when a message arrives.
3. **Change the code so the value is no longer a dependency**, for example by moving it outside the component (Lesson 37).
4. **Suppress the linter.** React's docs: "We recommend never suppressing the linter." Principle 3 shows why.

A senior developer also knows the four classic mistakes:
1. **Silencing the linter to stop the reconnect.** The React blog notes that "most users just disable the lint rule and exclude the dependency." The checkbox then stops working.
2. **Putting the Effect Event in the dependency array.** The chat then reconnects after every render.
3. **Wrapping the whole connection in an Effect Event**, only to make the array shorter. The chat then never leaves the first room.
4. **Calling the Effect Event from a click handler, or passing it to a child**, as if it were an ordinary function.

The rest of the lesson shows each mistake on a real chat room.

The disconnect line and the second connect line are the extra cleanup and setup of Strict Mode in development (Lesson 32). About three seconds later, the first message arrives, and a notification line appears.

Here is what the user does, and what each action should change:
1. **The page opens.** The app connects to the general room. About every three seconds, a message arrives, `hey` or `lol`, and a notification line appears.
2. **The user picks `travel`.** The heading changes. The app disconnects from general and connects to travel.
3. **The user ticks Mute notifications.** Messages still arrive, but no notification line appears. The connection is untouched.
4. **The user unticks it.** Notification lines appear again.

The chat helper is `createConnection` from Lesson 35, with two additions. The `connect` method now starts a timer that delivers a message every three seconds. And a new method, `on`, lets our code hand the connection a function to call with each message:

```js title="src/chat.js"
export function createConnection(serverUrl, roomId) {
  let intervalId;
  let messageCallback;
  return {
    connect() {
      console.log('✅ Connecting to "' + roomId + '" room at ' + serverUrl + '...');
      clearInterval(intervalId);
      intervalId = ~setInterval~(() => { // Every 3 seconds, a message arrives
        if (messageCallback) {
          if (Math.random() > 0.5) {
            messageCallback('hey');
          } else {
            messageCallback('lol');
          }
        }
      }, 3000);
    },
    disconnect() {
      ~clearInterval(intervalId)~; // Stops the messages of this connection
      messageCallback = null;
      console.log('❌ Disconnected from "' + roomId + '" room at ' + serverUrl);
    },
    ~on~(event, callback) { // Keeps the function to call with each message
      if (messageCallback) {
        throw Error('Cannot add the handler twice.');
      }
      if (event !== 'message') {
        throw Error('Only "message" event is supported.');
      }
      messageCallback = callback;
    },
  };
}
```

So `connection.on('message', fn)` works like `addEventListener` in plain JavaScript. You hand it a function, and the connection calls it with the text of every new message.

React's docs show each notification as a small pop-up from a separate package. Our version prints it to the Console instead, so we can count the notifications:

```js title="src/notifications.js"
export function ~showNotification~(message) { // Prints one notification line in the Console
  console.log('🔔 ' + message);
}
```

`App` keeps the room and the Mute setting in state, and controls the menu and the checkbox (Lesson 20). It passes both values to `ChatRoom` as props:

`App` stays the same in every principle. Every change in this lesson happens inside `ChatRoom`:

Now let's break it. Each principle puts the check of `muted` in another place and shows what the user sees:

**PRINCIPLES:** An Effect runs again when a value it reads changes. An Effect Event reads the latest value and does NOT make the Effect run again. Five principles follow:
1. **Principle 1: Every Value the Effect Reads Goes in Its Array.** With the check of `muted` inside the Effect, every tick of the checkbox reconnects the chat.
2. **Principle 2: An Effect Event Reads the Latest Value Without Reconnecting.** `onMessage` reads `muted` for each message, and neither of them goes in the array.
3. **Principle 3: A Suppressed Linter Leaves the Effect With an Old Value.** The reconnect stops, but the checkbox stops working too.
4. **Principle 4: Move Only the Lines That Should Not Run Again.** The connection must follow `roomId`, so it stays in the Effect.
5. **Principle 5: Call an Effect Event Only From Its Own Effect.** Never during rendering, never from a click handler, never from a child.

## PRINCIPLE | `muted` inside the Effect: every tick of the checkbox reconnects the chat

> [!PRINCIPLE]
> **Principle 1: Every Value the Effect Reads Goes in Its Array**
>
> *Every reactive value an Effect reads belongs in its dependency array. So a value you only need when a message arrives still reconnects the chat when it changes.*
>
> The user ticks Mute and the chat drops its connection. The check of `muted` sits inside the Effect, because the message comes from the connection. So `muted` becomes a dependency, and every tick runs the whole connection again. The linter is right about the array. The check is in the wrong place.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => {
>     if (!muted) showNotification('New message: ' + msg);
>   });
>   return () => connection.disconnect();
> }, ~[roomId, muted]~); // Lists every value read inside; the reconnect on Mute shows the check must move out
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => {
>     if (!muted) showNotification('New message: ' + msg);
>   });
>   return () => connection.disconnect();
> }, ~[roomId]~); // **WRONG:** muted is read inside but missing from the array
> ```

### An event handler runs on a click, an Effect runs when a value changes

You already know the two places code can live (Lesson 34). Here they are side by side in React's own chat example:

```jsx title="An event handler and an Effect in the same chat room"
function handleSendClick() {
  ~sendMessage(message)~; // Runs only when the user clicks Send
}

useEffect(() => {
  const connection = ~createConnection(serverUrl, roomId)~; // Runs again for every new roomId
  connection.connect();
  return () => connection.disconnect();
}, [roomId]);
```

React's docs give the two kinds of code a name:
- **Code in an event handler is not reactive.** It runs again only when the user clicks again. `handleSendClick` reads `message`, yet typing does not send anything. The docs: "a change to the `message` does not mean that they want to send a message. It only means that the user is typing."
- **Code in an Effect is reactive.** It runs again whenever a value it reads changes. A new `roomId` means disconnect, then connect.

Then the docs add: "Things get more tricky when you want to mix reactive logic with non-reactive logic." Our notification is exactly that mix. It must live inside the Effect, because the message comes from the connection. But the check of `muted` should behave like an event handler: read the value when the message arrives, and ignore its changes.

### The first try puts `muted` in the array

Here is the natural first try. `ChatRoom` receives `muted`, and the Effect hands the connection a function that shows a notification unless the user muted the room:

```jsx title="src/components/ChatRoom.jsx"
import { useEffect } from 'react';
import { createConnection } from '../chat.js';
import { showNotification } from '../notifications.js';

const serverUrl = 'https://localhost:1234';

export default function ChatRoom({ roomId, muted }) {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    ~connection.on~('message', msg => { // Hands the connection a function to call with each message
      if (~!muted~) { // Reads the muted prop when a message arrives
        showNotification('New message: ' + msg);
      }
    });
    return () => connection.disconnect();
  }, ~[roomId, muted]~); // The linter asks for muted, so muted joins roomId

  return <h1>Welcome to the {roomId} room!</h1>;
}
```

Every three seconds, the connection calls our arrow function with the message text, such as `hey`. JavaScript puts that text into `msg`.

`muted` is in the array because the Effect reads it, and a prop is a reactive value. Leave it out, and the linter reports: "React Hook useEffect has a missing dependency: 'muted'".

When the page opens, everything works. The chat connects to general, and a notification line appears for each message.

### Ticking Mute disconnects the chat and connects it again

**Beware! Ticking Mute does stop the notifications, but it also drops the connection and opens a new one.** Here is what happens, in order:
1. `App` sets `muted` to true. `ChatRoom` renders again with the new prop.
2. React compares the new array with the last one. The room is still `'general'`, but `muted` changed.
3. So React runs the old cleanup, and the Console shows a disconnect line.
4. Then React runs the setup again, and the Console shows a new connect line, for the same room.

```page width=text caption="Right after the user ticks Mute: the heading is the same, but the Console shows a disconnect and a new connect."

  check: Mute notifications | on | bad

log: 🔔 New message: hey

log: ✅ Connecting to "general" room at https://localhost:1234...
```

With `[roomId, muted]`, the Effect treats the two actions of the user the same way:
- **The user picks `travel`.** The Effect disconnects from general and connects to travel. This is what the user wants.
- **The user ticks Mute.** The Effect disconnects from general and connects to general again. Nobody asked for this.

There is a second surprise: **a user who ticks and unticks Mute quickly gets no messages at all**. Every reconnect runs `disconnect`, which stops the old timer, and `connect`, which starts a new one. The new timer delivers its first message three seconds later. Tick again before that, and the timer stops once more.

React's docs show the same thing with a timer. In their words: "If you keep clearing the interval every time before it has a chance to fire, it will appear as if the timer has stalled."

```tree caption="With muted read inside the Effect, picking a room and ticking Mute both reconnect the chat."
What the Effect does with `[roomId, muted]`
- +The user picks `travel` [`roomId`] | The user **wants a new room** | Disconnects from general and **connects to travel**
- !The user ticks Mute [`muted`] | The user **only wants silence** | Disconnects from general and **connects to general again**
```

So the array is correct for this code, and the linter did its job. What is wrong is the code: a non-reactive check sits inside a reactive Effect. The fix is to move the check out, not to change the array.

## PRINCIPLE | `useEffectEvent`: `onMessage` reads the latest `muted` without reconnecting

> [!PRINCIPLE]
> **Principle 2: An Effect Event Reads the Latest Value Without Reconnecting**
>
> *Move the line that should not be reactive into a function made with useEffectEvent, and call it from inside the Effect. Leave both the Effect Event and the values it reads out of the array.*
>
> The user ticks Mute and expects silence, not a new connection. An Effect Event reads the current `muted` each time a message arrives, while the Effect depends only on `roomId`. Picking a room still reconnects. Ticking Mute only changes what the next message does.
>
> **DO THIS:**
> ```jsx
> const onMessage = ~useEffectEvent~(msg => { // Reads the latest muted for each message
>   if (!muted) showNotification('New message: ' + msg);
> });
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => onMessage(msg));
>   return () => connection.disconnect();
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => onMessage(msg));
>   return () => connection.disconnect();
> }, ~[roomId, onMessage]~); // **WRONG:** an Effect Event in the array reconnects the chat on every render
> ```

### `useEffectEvent` in its smallest form

`useEffectEvent` comes from React, like `useEffect`. You give it a function, and you get back a new function, the Effect Event:

```jsx title="The smallest useEffectEvent"
import { useEffect, ~useEffectEvent~ } from 'react'; // Imported from React, like useEffect

const onEvent = ~useEffectEvent(callback)~; // Returns an Effect Event that runs callback
```

React's docs: "It's a part of your Effect logic, but it behaves a lot more like an event handler. The logic inside it is not reactive, and it always 'sees' the latest values of your props and state."

So an Effect Event and an event handler share one thing. Both read the current values at the moment they run, and neither runs again when those values change. The one difference is who calls them. React calls an event handler when the user clicks. Your Effect calls an Effect Event, here when a message arrives.

### Moving the check into `onMessage`

Here is `ChatRoom` with the check moved into an Effect Event named `onMessage`:

```jsx title="src/components/ChatRoom.jsx"
import { useEffect, useEffectEvent } from 'react';
import { createConnection } from '../chat.js';
import { showNotification } from '../notifications.js';

const serverUrl = 'https://localhost:1234';

export default function ChatRoom({ roomId, muted }) {
  const onMessage = ~useEffectEvent~(msg => { // Declared at the top level, next to the Effect
    if (!muted) {
      showNotification('New message: ' + msg);
    }
  });

  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    connection.on('message', msg => ~onMessage(msg)~); // Calls the Effect Event for each message
    return () => connection.disconnect();
  }, ~[roomId]~); // Only roomId: muted and onMessage stay out

  return <h1>Welcome to the {roomId} room!</h1>;
}
```

Three things changed:
1. The check of `muted` moved out of the Effect, into `onMessage`, at the top level of the component.
2. The function handed to the connection checks nothing itself. It passes each message on to `onMessage`.
3. The array is back to `[roomId]`. The Effect no longer reads `muted`, so `muted` leaves the array. And `onMessage` stays out too: "Effect Events are not reactive and must be omitted from dependencies."

React's docs call this move "extracting" an Effect Event. The non-reactive line comes out, and the Effect keeps only what must follow `roomId`.

**It may look the same, or work the same at first, but it is NOT the same thing!** When the page opens, both versions connect to general and show a notification for each message. The difference appears only when the user ticks Mute. The first try reconnects. The version with `onMessage` keeps its connection, and still stops the notifications.

```tree caption="The same chat with muted read inside the Effect, and with muted read inside the onMessage Effect Event."
Where the check of `muted` lives
- !Inside the Effect [`[roomId, muted]`] | The Effect **depends on `muted`** | Every tick of Mute **disconnects and connects again**
- +Inside `onMessage` [`useEffectEvent` `[roomId]`] | The Effect **depends only on `roomId`** | The next message reads the **latest `muted`**; the connection **stays**
```

### Ticking Mute now changes only the notifications

**When the user ticks Mute, the notifications stop, and the Console shows no disconnect and no new connect.** Here is what happens, in order:
1. The user ticks Mute. `ChatRoom` renders again, and now `muted` is true.
2. React compares `[roomId]` with the last array. Nothing changed, so the Effect does not run again.
3. The old connection keeps running. A few seconds later, it calls its function with the next message.
4. That function calls `onMessage`. It reads the latest `muted`, which is now true, and shows nothing.

### Where does `onMessage` get the latest `muted`?

From React. The function the connection holds was created in the first render. Yet `onMessage` reads `muted` as it is now. The docs promise exactly that. Their words: "When you call the returned Effect Event function, the `callback` always accesses the latest committed values from render at the time of the call."

In plain words, `onMessage` reads the props and state of the latest render that reached the screen. The docs do not say how React does this inside, and you do not need to know it to use the Hook.

`msg` comes from somewhere else: the Effect. The connection hands the message text to the arrow function, and the arrow function passes it on to `onMessage` as an argument.

React's docs teach the same pattern with another setting. Their chat also reports when it has connected, and their notification takes the current theme:

```jsx title="The docs' version: a theme read in an Effect Event"
const onConnected = ~useEffectEvent~(() => { // Reads the latest theme when the chat connects
  showNotification('Connected!', theme);
});

useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.on('connected', () => {
    onConnected();
  });
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId]~); // ✅ All dependencies declared
```

**Yes, it is the exact same thing!** One line reads a user setting, `theme` there and `muted` here. That line moves into an Effect Event, and the array keeps only `roomId`.

### `onMessage` in the array reconnects on every render

**Beware! An Effect Event in the array brings the reconnect back, and makes it worse: the chat reconnects after every render.** Out of habit, developers add every function the Effect calls to its array:

```jsx title="src/components/ChatRoom.jsx"
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  connection.on('message', msg => onMessage(msg));
  return () => connection.disconnect();
}, ~[roomId, onMessage]~); // **WRONG:** onMessage is new on every render, so the chat reconnects on every render
```

Here is what goes wrong:
1. The linter reports it: "Functions returned from useEffectEvent must not be included in the dependency array".
2. If the code runs anyway, the Effect runs after every render, because "Effect Event functions do not have a stable identity".
3. The identity of a function is which function object it is. React gives `onMessage` a brand-new function object on every render, on purpose.
4. So the comparison of the array always sees a change. The chat disconnects and connects again on every render, including every tick of Mute.

Remember: the Effect runs again when a value in its array changes. The Effect Event never goes in the array.

## PRINCIPLE | `eslint-disable-line`: the Effect keeps an old `muted`, so Mute stops working

> [!PRINCIPLE]
> **Principle 3: A Suppressed Linter Leaves the Effect With an Old Value**
>
> *Silencing the linter also stops the reconnect. But the function the connection holds keeps the muted of the render that connected, so the checkbox stops working until the room changes.*
>
> The user mutes the room and still gets notifications. The Effect did not run again, so the function it gave the connection still belongs to the old render, and it checks the old value. The linter was the only thing that could point to this, and it was silenced. An Effect Event fixes the reconnect without hiding anything.
>
> **DO THIS:**
> ```jsx
> const onMessage = useEffectEvent(msg => {
>   if (~!muted~) showNotification('New message: ' + msg); // Reads the latest muted for each message
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => {
>     if (~!muted~) showNotification('New message: ' + msg); // **WRONG:** muted is stuck at its value from the render that connected
>   });
>   return () => connection.disconnect();
> }, ~[roomId]~); // **WRONG:** eslint-disable-line react-hooks/exhaustive-deps hides muted from the linter
> ```

### Two Effects with the same `[roomId]`

There is a second way to stop the reconnect, and many developers try it first. They keep the check inside the Effect, remove `muted` from the array, and silence the linter with a comment:

```jsx title="With the linter suppressed"
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  connection.on('message', msg => {
    if (~!muted~) { // **WRONG:** reads the muted of the render that connected
      showNotification('New message: ' + msg);
    }
  });
  return () => connection.disconnect();
}, ~[roomId]~); // **WRONG:** eslint-disable-line react-hooks/exhaustive-deps hides muted from the linter
```

The comment at the end of the last line, `eslint-disable-line`, tells the linter to skip that line, so it no longer asks for `muted`. Developers often write the same thing as an `eslint-disable-next-line` comment on the line above.

Now compare it with the version from Principle 2:

```jsx title="With onMessage"
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  connection.on('message', msg => ~onMessage(msg)~); // Reads the latest muted for each message
  return () => connection.disconnect();
}, [roomId]);
```

**It may look the same, or work the same at first, but it is NOT the same thing!** Both arrays say `[roomId]`, and after a tick of Mute, neither shows a disconnect line. But only the version with `onMessage` stops the notifications.

### In plain JavaScript there is one `muted`, in React every render has its own

Here is what really goes on. In plain JavaScript, there is one `let muted` variable. You change it, and every function that reads it sees the new value.

In React, `muted` is a prop, a parameter of the component function. Remember how a function works when you call it twice with different arguments:

```js title="Plain JavaScript: two calls, two separate muted parameters"
function render(~muted~) { // Every call gets its own muted
  return () => console.log(muted);
}
const fromFirstCall = render(false);
const fromSecondCall = render(true);
~fromFirstCall()~; // Logs false: the function sees the muted of its own call, forever
~fromSecondCall()~; // Logs true
```

`ChatRoom` is exactly such a function. React calls it on every render, with the props of that render. The arrow function created during the first render sees the first render's `muted`, forever (Lesson 15).

So when the Effect does not run again, the connection keeps the arrow function from the first render. That is exactly what `useEffectEvent` fixes: React makes `onMessage` read the values of the latest render.

### The user mutes the room, and notifications keep coming

**Beware! With the linter suppressed, Mute no longer works: the user mutes the room, and notifications keep coming.** Here is why, in order:
1. The page opens with `muted` as `false`. The setup hands the connection a function from this first render, which sees `false`.
2. The user ticks Mute. `ChatRoom` renders again, and now `muted` is true.
3. React compares `[roomId]` with the last array. Nothing changed, so the old setup stays, and so does its function.
4. The next message arrives. The old function checks the old `muted`, still `false`, and shows a notification.

```page width=text caption="With the linter suppressed: the first notification line came before the tick, and the next two came after the user ticked Mute."

log: 🔔 New message: lol

```

React's docs say the value gets "stuck".

### Picking another room fixes Mute for a while

**Changing rooms seems to repair Mute, and then it breaks the other way.** Here is what happens:
1. While Mute is ticked, the user picks `travel`. `roomId` changed, so React runs a new setup.
2. The new function belongs to this render, and sees `muted` as `true`. No notification lines appear.
3. The user unticks Mute. The function still sees `true`, so no notification appears until the room changes again.

This bug is hard to find, because Mute works or fails depending on when the user last changed rooms. And the linter can no longer help. The docs warn: "React will no longer warn you when your Effect needs to 'react' to a new reactive dependency you've introduced to your code." And: "If you never suppress the linter, you will never see problems with stale values."

## PRINCIPLE | `useEffectEvent` around the connection: the chat never leaves the first room

> [!PRINCIPLE]
> **Principle 4: Move Only the Lines That Should Not Run Again**
>
> *Move into an Effect Event only the logic that should not re-synchronize. Code that must follow a value, such as the connection to roomId, stays in the Effect. A value that belongs to the event, such as the message text, reaches the Effect Event as an argument.*
>
> When the user picks a new room, the chat must leave the old one. If the connection hides inside an Effect Event, the linter goes quiet, and the chat stays in the first room while the heading changes. Move only the lines that read a value at the moment something happens, and name the Effect Event after that event.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => ~onMessage(msg)~); // Only the notification check is an Effect Event
>   return () => connection.disconnect();
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const onMount = useEffectEvent(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return connection;
> });
> useEffect(() => {
>   const connection = ~onMount()~; // **WRONG:** runs once, so the chat never leaves the first room
>   return () => connection.disconnect();
> }, []);
> ```

### Wrapping the whole connection in an Effect Event

Once developers see that `useEffectEvent` quiets the linter, some wrap everything in it. Here the whole connection moves into an Effect Event named `onMount`, and the Effect runs only once:

```jsx title="With the connection inside onMount"
const onMount = ~useEffectEvent~(() => { // **WRONG:** the connection must follow roomId, so it does not belong here
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  connection.on('message', msg => onMessage(msg));
  return connection;
});

useEffect(() => {
  const connection = onMount();
  return () => connection.disconnect();
}, ~[]~); // The linter is quiet: the Effect reads no reactive value
```

**It may look the same, or work the same at first, but it is NOT the same thing!** Both this version and the one from Principle 2 connect to general when the page opens, and the linter is quiet for both. The difference appears when the user picks `travel`.

### The heading says travel, and the chat is still in general

**With the connection inside `onMount`, the heading follows the menu, and the connection does not.** Here is what happens, in order:
1. The page opens. The Effect calls `onMount`, which connects to general.
2. The user picks `travel`. The heading changes to the travel room.
3. React compares `[]` with `[]`. Nothing changed, so no cleanup and no setup run.
4. The Console shows no disconnect line and no new connect line. The messages still come from general.

`onMount` does read the latest `roomId` when it runs. But nothing calls it again, so it only ever read the first one.

```page width=text caption="With the connection inside onMount, the heading says travel, but the Console shows only the connection to general."
form:
  select: Choose the chat room: | travel | bad
  check: Mute notifications | off
heading: Welcome to the travel room!
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
log: 🔔 New message: hey
```

React's docs warn against exactly this: "Do not use `useEffectEvent` to avoid specifying dependencies in your Effect's dependency array. This hides bugs and makes your code harder to understand." And they say where the Hook belongs: "You should only apply it to the lines of code that you don't want to be reactive."

### Name the Effect Event after what the user thinks happened

The name `onMount` was the first warning sign. It says when the code runs, not what happened for the user. The docs ask you to "name your Effect Events after what the user thinks has happened, not when some code happened to run."

They warn about `onMount` and `onUpdate`. The same goes for `onUnmount` and `onAfterRender`. These names are "so generic that it's easy to accidentally put code that should be reactive into them." Good names describe an event the user would recognize, such as `onMessage` or `onVisit`. Two more from the docs are `onTick` and `onConnected`.

To decide what moves, ask the Rule of Thumb question for each piece of code. When this value changes, does the user want this code to run again?
1. **The connection: yes.** A new `roomId` means a new room. The connection stays in the Effect, with `roomId` in the array.
2. **The notification check: no.** A new `muted` does not mean a new connection. The check moves into `onMessage`.

### The message text arrives as an argument

`onMessage` gets the message text from the Effect, as an argument. The component has no message text to read: the text exists only at the moment the connection hands it over. The docs allow this: "The function can accept any number of arguments and return any value."

So the two values inside `onMessage` arrive in two different ways:

```jsx title="The two kinds of values inside onMessage"
const onMessage = useEffectEvent(~msg~ => { // Belongs to this one message: passed in by the Effect
  if (!~muted~) { // A setting looked up when the message arrives: always the latest value
    showNotification('New message: ' + msg);
  }
});
```

1. **A value that belongs to the event**, such as the message text, comes in as an argument from the Effect.
2. **A value the event only looks up at that moment**, such as `muted`, is read inside the Effect Event. It is always the latest one.

```tree caption="Moving the whole connection into an Effect Event vs. moving only the notification check."
What moves into an Effect Event
- !The whole connection in `onMount` [`[]`] | Quiets the linter, **but the connection no longer follows `roomId`** | The heading says travel; the chat **stays in general**
- +Only the check in `onMessage` [`[roomId]`] | The connection **stays in the Effect** | Picking a room **reconnects**; ticking Mute **only changes the notifications**
```

## PRINCIPLE | `onMessage`: call it only from inside its own Effect

> [!PRINCIPLE]
> **Principle 5: Call an Effect Event Only From Its Own Effect**
>
> *Call an Effect Event only from its own Effect or from another Effect Event. Never call it during rendering or from an event handler, never pass it to another component or Hook, and declare it next to the Effect that uses it.*
>
> An Effect Event looks like any other function, but it is a piece of one Effect. Called during rendering, it throws an error and the page goes blank. Called from a click or passed to a child, it breaks a rule the linter checks, and a child that depends on it runs its Effect after every render. Clicks and children get regular functions.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   connection.on('message', msg => ~onMessage(msg)~); // Called from inside its own Effect
>   return () => connection.disconnect();
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button onClick={() => ~onMessage('test')~}> {/* **WRONG:** an Effect Event called from a click handler */}
>   Test notification
> </button>
> ```

### Three places to call the same function

`onMessage` is a function, so it seems you could call it anywhere. Here are three places a developer might try:

```jsx title="Three places to call onMessage"
connection.on('message', msg => ~onMessage(msg)~); // 1. Inside the Effect: allowed

<button onClick={() => ~onMessage('test')~}>Test notification</button> {/* 2. In a click handler: not allowed */}

<MessageList ~onMessage={onMessage}~ /> {/* 3. Passed to a child as a prop: not allowed */}
```

**It may look the same, but it is NOT the same thing!** All three call the same function, and only the first is allowed. React's docs give two rules: "Only call them from inside Effects." And: "Never pass them to other components or Hooks."

The reason: an Effect Event is a piece of one Effect, not a general tool. The docs: "This design reinforces that Effect Events conceptually belong to a particular effect, and are not a general purpose API to opt-out of reactivity."

### A call during rendering throws an error

**Calling `onMessage` in the body of `ChatRoom` throws an error, and the page goes blank.** Here is the call:

```jsx title="src/components/ChatRoom.jsx"
export default function ChatRoom({ roomId, muted }) {
  const onMessage = useEffectEvent(msg => {
    if (!muted) {
      showNotification('New message: ' + msg);
    }
  });

  ~onMessage('test')~; // **WRONG:** runs while React renders ChatRoom

  return <h1>Welcome to the {roomId} room!</h1>;
}
```

The body of a component runs while React renders it (Lesson 13). So this call happens during rendering, before anything reaches the screen. React stops rendering, and the page stays blank. The Console shows the error, then a warning that names the component:

```devconsole caption="The Console after onMessage is called in the body of ChatRoom."
x Uncaught Error: A function wrapped in useEffectEvent can't be called during rendering.
! An error occurred in the <ChatRoom> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

### A click handler and a child get the linter's warning

In the browser, the click handler and the child prop show no error. The linter reports them instead: "... is a function created with React Hook `useEffectEvent`, and can only be called from Effects and Effect Events".

Each has its own reason:
1. **A click does not need an Effect Event.** A click is already an interaction, so it gets a regular event handler (Lesson 11).
2. **A child would get a function that changes on every render.** An Effect Event is a new function object after every render. If the child lists it in the array of its own Effect, that Effect runs after every render.

The docs show the second case with a timer. A component passes its Effect Event to a custom Hook, `useTimer`, and the timer restarts on every render. Their advice: "If you need a callback for event handlers or to pass to children, use a regular function or `useCallback` instead." `useCallback` gets its own lesson (Lesson 57), and so do custom Hooks that take a function (Lesson 39).

For the Test notification button, a regular event handler does the job:

```jsx title="A regular event handler for the Test notification button"
function ~handleTestClick~() { // A regular function: runs only when the user clicks
  showNotification('Test notification');
}

<button onClick={handleTestClick}>Test notification</button>
```

### Declared next to its Effect, at the top level

`useEffectEvent` is a Hook, so it follows the rules of every Hook. It goes at the top level of the component, never inside a condition or a loop (Lesson 38). Declare the Effect Event right above the Effect that calls it. The docs: "Effect Events are non-reactive 'pieces' of your Effect code. They should be next to the Effect using them."

```tree caption="The four places a developer might put a call to onMessage, and which one React allows."
Where `onMessage` can be called
- +Inside its own Effect [`connection.on`] | **Allowed** | Reads the latest `muted` each time a message arrives
- !In the component body [`onMessage`] | Runs **during rendering** | React **throws an error**
- !In a click handler [`onClick`] | The linter **reports it** | Use a **regular event handler** instead
- !Passed to a child [`<MessageList onMessage>`] | A **new function object** on every render | Use a **regular function** or `useCallback` instead
```

### The complete files

The chat helper creates a connection that delivers a message every three seconds:

```js title="src/chat.js"
export function ~createConnection~(serverUrl, roomId) { // The message version of the helper from React's docs
  let intervalId;
  let messageCallback;
  return {
    connect() {
      console.log('✅ Connecting to "' + roomId + '" room at ' + serverUrl + '...');
      clearInterval(intervalId);
      intervalId = setInterval(() => {
        if (messageCallback) {
          if (Math.random() > 0.5) {
            messageCallback('hey');
          } else {
            messageCallback('lol');
          }
        }
      }, 3000);
    },
    disconnect() {
      clearInterval(intervalId);
      messageCallback = null;
      console.log('❌ Disconnected from "' + roomId + '" room at ' + serverUrl);
    },
    on(event, callback) {
      if (messageCallback) {
        throw Error('Cannot add the handler twice.');
      }
      if (event !== 'message') {
        throw Error('Only "message" event is supported.');
      }
      messageCallback = callback;
    },
  };
}
```

## For the Interview

> **The Interview Question:** How do you keep non-reactive values from re-running an effect?

### How to Answer Clearly in 30 Seconds

"Every reactive value an Effect reads must be in its dependency array. So a value I only need at the moment something happens, such as a Mute setting checked when a chat message arrives, still re-runs the whole synchronization. The fix is `useEffectEvent`, which React 19.2 added:
1. **Extract the non-reactive logic**: I move the lines that read that value into an Effect Event, declared with `useEffectEvent` at the top level of the component. I call it from inside the Effect.
2. **Leave it out of the array**: the Effect Event always reads the latest props and state when it is called, and neither it nor the values it reads go in the dependency array. The Effect keeps only the values that should re-synchronize it, such as `roomId`.
3. **Respect its limits**: I move only logic that should not be reactive, and I never suppress the linter instead. I call the Effect Event only from its own Effect, never during rendering, from a click handler, or from a child."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why not just suppress the linter and leave the value out of the array?"**
   Because the value gets stuck. The function the Effect hands to the connection belongs to the render that ran the setup, and each render keeps its own props and state. If the Effect does not run again, that function keeps checking the old value. In our chat, the user mutes the room and still gets notifications until the room changes. Worse, the linter stays silent for every new value the Effect reads later. An Effect Event avoids the reconnect without hiding anything from the linter.
2. **"When should a value be passed to the Effect Event as an argument instead of read inside it?"**
   When the value belongs to the event itself. The message text exists only when the connection hands it over, so the Effect passes it to `onMessage`. React's docs give a second case: a log of page visits. For each new `url`, the Effect calls `onVisit` and passes the `url` as an argument, so the log records the page that caused this visit. If `onVisit` read `url` from the component instead, it would get the latest `url`, which may already be a different page. Asking for the value as an argument also keeps `url` in the Effect's array, so nobody can remove it by accident.
3. **"Why does an Effect Event get a new identity on every render, unlike a setter or a ref?"**
   React does it on purpose. The docs say its identity "intentionally changes on every render", and that "the non-stable identity acts as a runtime assertion", which means a built-in check that fails loudly. If someone lists the Effect Event in a dependency array, the Effect runs again after every render, so the mistake shows up at once instead of hiding. It also makes clear that an Effect Event is not a function to pass around. For a function to give a child, you write a regular function, or wrap it in `useCallback` when the child needs the same function between renders.

```tree dir=right caption="Interview summary: how one Effect separates the logic that re-synchronizes from the logic that only reads the latest values."
One Effect, two kinds of logic
- +Reactive logic [`[roomId]`] | Must **follow its value** | Stays in the Effect, and a change **re-synchronizes** the connection
- +Non-reactive logic [`useEffectEvent`] | Only **reads a value when something happens** | Moves into an Effect Event that reads the **latest props and state**
- !Suppressed linter [`eslint-disable-line`] | Stops the re-run **by hiding a dependency** | The value **gets stuck**, and the linter stays silent afterwards
```
