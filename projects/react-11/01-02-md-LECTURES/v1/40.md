# Lecture 40: Choosing Between Controlled State and Uncontrolled FormData

*(Does every field of a form need its own state variable?)*

> INTERVIEW QUESTION | ❱ CORE | Should a form use controlled state or uncontrolled FormData, and how do you choose?

---

## VS | State `value` and `onChange` vs. the Browser `name` and `FormData`: both keep the typed text, only state renders again

> **We do not need a state variable for every field of a form: `FormData` reads the fields at submit.**

In React, forms have many fields, and each field is often plugged into a state variable through `useState`. A form with 10 fields may have 10 variables and 10 separate `useState` calls, one for each field. You do not need to do this for every input. **We should plug in `useState` for only a few fields**, for example the ones that change the screen as the user types. This is why the browser gives us `FormData`. **The remaining fields can be read at submit with `FormData`.**

Take a signup form with five fields: First Name, Last Name, City, Email, and Password. Ask yourself: do I need to constantly update each and every field? Only the Password field needs to update a live red-or-green strength bar below it. When the password is weak, the bar turns red. But for the rest of the fields, there is no need to track every letter the user types. All five inputs sit in the same form component, yet only one needs to change the screen while the user types.

**Why:** Giving all five fields their own `useState` forces React to re-render the entire form on every letter typed. Here, you only need `useState` for the Password field. The browser already holds the text of the other four fields until you read it at submit with `FormData`.

### A Form in Plain JavaScript

Let's start from plain JavaScript. How do you read a form there? You wait for the submit, and then you ask the browser what is in the fields:

```js title="Reading a form at submit in plain JavaScript"
const form = document.querySelector('form');

form.addEventListener('submit', (e) => {
  e.preventDefault();
  const formData = ~new FormData(form)~; // Asks the browser for every field that has a name
  console.log(~formData.get('email')~); // 'john@mail.com'
});
```

Notice what you did NOT do. You kept no variable for the email while the user typed. You did not need one. The browser keeps the text of every `<input>` field by itself, from the first letter to the last. You only ask for it at the end.

In Lesson 20 you learned the React way to do the opposite: a controlled field. You keep your own copy of the text in state, and the `<input>` field shows only that copy:

```jsx title="A controlled field"
const [password, setPassword] = useState('');

<input ~value={password}~ onChange={e => setPassword(e.target.value)} /> {/* The field shows only what password holds in state */}
```

> [!DEFINITION]
> **Controlled and uncontrolled fields.** [REVIEW] An `<input>` field with `value` is a controlled field: state keeps the text, and the field shows only what state holds. So it also needs `onChange`, which calls the setter after every keystroke.
> An `<input>` field without `value` is an uncontrolled field: the browser keeps the text, exactly as in plain JavaScript.
> A field is one or the other for its whole life. It never switches (Lesson 20).

On the screen, the two kinds of fields look exactly the same. Both show each letter the moment the user types it. But they do NOT do the same work:
1. **The controlled field** calls a setter after every keystroke. A setter makes React call your component again (Lesson 13). So React renders the component once for every letter.
2. **The uncontrolled field** changes no state. React does nothing while the user types.

So why did Lesson 20 teach controlled fields at all? Because sometimes the page must react to every letter. A password hint that says `Looks good` after the eighth character needs the text right now, and it needs a render to show the new hint. The browser cannot give you that. State can.

That is the whole choice, field by field.

### The Rule of Thumb: does the page change while the user types?

**Ask one question about every field: does something on the page change while the user types into it? If yes, put it in state. If the page needs the text only when the user clicks the button, give the field a `name` and read it at submit with `FormData`.**

A senior developer also knows the three classic mistakes:
1. **A field without `name`.** `FormData` skips it, so your code gets `null`, and the page shows no error.
2. **Every field in state, out of habit.** Right after Lesson 20, developers put every field in state. In a large form, every keystroke renders the whole form, and the letters appear late on a slow phone.
3. **The state of a field too high up.** The state sits in `App`, so every keystroke renders the whole page, the header included.

The rest of the lesson shows each one on a real Sign up form.

Now let's build the form, one field at a time, and break it on the way:

**PRINCIPLES:** A field goes into state only when the page must change while the user types. Every other field stays with the browser, and you read it at submit with `FormData`. Four principles follow:
1. **Principle 1: `name` Is the Key FormData Uses.** At submit, `new FormData(e.currentTarget)` collects every field that has a `name`. A field without `name` gives `null`.
2. **Principle 2: An Uncontrolled Field Renders Nothing While the User Types.** A controlled field renders the component after every keystroke. In a large form, that work is wasted.
3. **Principle 3: Control a Field When the Page Changes on Every Keystroke.** The password hint needs the text and a render after every letter. Only state gives both.
4. **Principle 4: Keep the State of a Field in the Form Component.** A keystroke renders the component that holds the state and everything inside it. In `SignupForm`, that is only the form.

## PRINCIPLE | `name` and `FormData`: the browser hands you every named field at submit

> [!PRINCIPLE]
> **Principle 1: `name` Is the Key FormData Uses**
>
> *Give every field that you read at submit a `name`, build the form data with `new FormData(e.currentTarget)`, and read each field with `formData.get` and that same name.*
>
> You do not need state to read what the user typed. The browser already keeps the text of every field. At submit, `FormData` collects the text of every field that has a `name`, and the `name` is the key you ask for. A field without `name` is left out, so your code gets `null`, and the page shows no error.
>
> **DO THIS:**
> ```jsx
> function handleSubmit(e) {
>   e.preventDefault();
>   const formData = new FormData(e.currentTarget);
>   console.log(formData.get('email'));
> }
> <input ~name="email"~ /> {/* formData.get('email') returns the typed email */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleSubmit(e) {
>   e.preventDefault();
>   const formData = new FormData(e.currentTarget);
>   console.log(formData.get('email'));
> }
> ~<input />~ {/* **WRONG:** no name, so formData.get('email') returns null */}
> ```

### `FormData` in React, in its smallest form

`FormData` is not React. It is the same browser object you used in plain JavaScript. The only question is: where do you get the `<form>` element from?

In plain JavaScript, you grab it yourself with `document.querySelector('form')`. In React, you never create the `<form>` element by hand. React creates it from your JSX. But you do not need to grab it either. When the user submits, React calls your `onSubmit` handler and hands it the event object, and `e.currentTarget` is that very `<form>` element (Lesson 11). Pass it to `new FormData`, and you are back in plain JavaScript:

```jsx title="Reading the Email field at submit with FormData"
function handleSubmit(e) {
  e.preventDefault();
  const formData = ~new FormData(e.currentTarget)~; // e.currentTarget is the <form> element React created
  console.log(~formData.get('email')~); // Logs the text stored under the name email
}

<form onSubmit={handleSubmit}>
  <input ~name="email"~ /> {/* This name becomes the key in the form data */}
  <button type="submit">Sign up</button>
</form>
```

> [!DEFINITION]
> **What is FormData?** [NEW] `FormData` is a browser object that holds the data of a form. You build it from a `<form>` element: `new FormData(e.currentTarget)`.
> It holds one entry for each field that has a `name`: the name is the key, and the typed text is the value. Think of `{ email: 'john@mail.com' }`, except that you read it with a method: `formData.get('email')`.
> It reads the fields at the moment you build it, so you build it inside the submit handler.
> Something that can be tricky: a field without `name` has no key, so `FormData` leaves it out. `formData.get` returns `null` for a name it does not hold, with no error (Lesson 40).

So three words do the job, and none of them comes from React:
1. **`name`** is a normal HTML attribute. React passes it on to the `<input>` element. The React docs say the `name` you write "will be used as a key in the form data".
2. **`new FormData(e.currentTarget)`** collects every named field of the form, at the moment the user submits.
3. **`formData.get('email')`** returns the text stored under the name `email`.

The string `'email'` in `formData.get('email')` and the string in `name="email"` are the only link between the field and your code. They must match letter for letter.

```tree dir=right caption="How the text in the Email field reaches our code at submit: the name on the field becomes the key in the form data."
How `john@mail.com` reaches `handleSubmit`
- +1. The field [`name="email"`] | The user types **`john@mail.com`** | The **browser** keeps the text
- +2. The form data [`new FormData`] | Built when the user **clicks Sign up** | Holds one entry: **`email`** with **`john@mail.com`**
- +3. Our code [`formData.get`] | Asks for the entry named **`email`** | Gets **`john@mail.com`**
```

Here is the first version of `SignupForm`, with the Email field only:

```jsx title="src/components/SignupForm.jsx"
export default function SignupForm() {
  function handleSubmit(e) {
    e.preventDefault();
    const formData = new FormData(e.currentTarget);
    console.log(~formData.get('email')~); // Logs john@mail.com when the user clicks Sign up
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Sign up</h2>
      <label>
        Email
        <input ~name="email"~ /> {/* Uncontrolled: the browser keeps what the user types */}
      </label>
      <button type="submit">Sign up</button>
    </form>
  );
}
```

The user types `john@mail.com` and clicks Sign up. The page does not reload, because `e.preventDefault()` stops the browser from sending the form (Lesson 11). The Console shows the email:

### VS | `e.target` vs. `e.currentTarget` inside `onSubmit`: both are the `<form>` element

The React docs write `new FormData(e.target)`. Our code writes `new FormData(e.currentTarget)`. Which one is right?

In a submit handler on the form, both. `e.target` is the element where the event happened. `e.currentTarget` is the element whose handler is running (Lesson 11). The submit event happens on the `<form>` itself, and the handler sits on that same `<form>`. So both point at the same `<form>` element.

## PRINCIPLE | A field with only `name`: a keystroke does not render the component

> [!PRINCIPLE]
> **Principle 2: An Uncontrolled Field Renders Nothing While the User Types**
>
> *A field with `value` and `onChange` makes React render the component after every keystroke. A field with only a `name` makes React render nothing while the user types.*
>
> Both fields show what the user types, so they seem to cost the same. They do not. A controlled field sets state after every keystroke, and every state change renders the component that holds it. When the page needs the text only at submit, that work buys nothing, and in a large form the user feels it as letters that appear late.
>
> **DO THIS:**
> ```jsx
> <input ~name="email"~ /> {/* Read once at submit, no render while the user types */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [email, setEmail] = useState('');
> <input value={email} ~onChange={e => setEmail(e.target.value)}~ /> {/* **WRONG:** renders the form on every keystroke, though the page reads the email only at submit */}
> ```

Why two lines per render? Strict Mode calls each component twice in development (Lesson 14). With React DevTools installed, the second line of each pair looks slightly dimmed.

Here is what each keystroke does:
- **With `name`**, the browser writes the letter into the field. No state changes, so React has no reason to call `SignupForm`.
- **With `value` and `onChange`**, every keystroke calls the setter `setEmail` with the new text. A state change makes React call the component again (Lesson 13), and the field shows the new text from state.

The React docs say it plainly: "When you use a controlled input, you set the state on every keystroke."

```tree caption="What happens after one keystroke by the user in each version of the Email field."

- !With `value` and `onChange` [`value={email}` `onChange`] | `onChange` calls **`setEmail`** with the new text | React **renders `SignupForm` again**, and the field shows the new text
```

### The cost is the render, not the field

One render per keystroke is nothing for our form. It has two fields, and React renders it in no time. The cost grows with how much React has to render after each keystroke.

**Beware! When every field of a large form sits in state, every keystroke in any field renders the whole form.** Here is how a developer runs into it:
1. Right after Lesson 20, the developer gives every field of a forty-field admin form its own `useState`.
2. The user types one letter in any field.
3. React renders the whole form again, with all forty fields.
4. On a low-end laptop or phone, the letters appear late.

The React docs warn that when the component that holds the state renders a large tree on every keystroke, "this can get slow".

And most of those forty fields are read only when the user clicks Save. They never needed state. With a `name` each, read at submit with `FormData`, they would cost no render at all while the user types.

So our Email field stays uncontrolled, because the page reads it only when the user clicks Sign up:

```jsx title="src/components/SignupForm.jsx"
export default function SignupForm() {
  ~console.log('SignupForm rendered');~ // Prints on page load, and never while the user types the email
  function handleSubmit(e) {
    e.preventDefault();
    const formData = new FormData(e.currentTarget);
    console.log(formData.get('email'));
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Sign up</h2>
      <label>
        Email
        <input ~name="email"~ /> {/* Uncontrolled: the browser keeps the email until submit */}
      </label>
      <button type="submit">Sign up</button>
    </form>
  );
}
```

Remember: the page reads it only at submit? Then it does not go into state.

## PRINCIPLE | `value` and `onChange`: the page can change on every keystroke

> [!PRINCIPLE]
> **Principle 3: Control a Field When the Page Changes on Every Keystroke**
>
> *Put a field in state with `value` and `onChange` when the page must change while the user types, and read that field from state at submit.*
>
> A hint under a field needs two things after every keystroke: the current text, and a render to show the new hint. A field with only a `name` gives neither, because the browser keeps the text and React renders nothing. A controlled field gives both. The rest of the form can stay uncontrolled, because you choose for each field.
>
> **DO THIS:**
> ```jsx
> const [password, setPassword] = useState('');
> <input type="password" ~value={password}~ onChange={e => setPassword(e.target.value)} /> {/* Each keystroke renders the form */}
> <p>{password.length < 8 ? 'Use 8 or more characters' : 'Looks good'}</p>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input type="password" ~name="password"~ /> {/* **WRONG:** no state and no render, so the hint can never change */}
> <p>Use 8 or more characters</p>
> ```

1. **There is no value to check.** The text sits in the browser, so the component has no `password` to measure with `.length`.
2. **There is no render.** Even with a value, nothing makes React call the component again to pick a new hint.

The controlled field has both. Every keystroke saves the text into `password`, and React renders the component again with the new `password`.

So when do you really need a controlled field? The React docs give the reason: you need the state anyway, for example to render the page again on every edit. Here are the cases you will meet:
1. **The page shows or checks the text on every edit**, such as a password hint, a live character limit, or suggestions under a search field.
2. **Something other than typing also changes the text**, such as a button that fills or clears the field.
3. **A button stays off until the form is valid**, such as a Sign up button with `disabled` (Lesson 21).

### The email from FormData, the password from state

Our Password field goes into state. The Email field keeps its `name`. At submit, our code reads each field from the place that keeps its text:

```jsx title="src/components/SignupForm.jsx"
import { useState } from 'react';

export default function SignupForm() {
  const [password, setPassword] = useState('');
  console.log('SignupForm rendered');

  function handleSubmit(e) {
    e.preventDefault();
    const formData = new FormData(e.currentTarget);
    const email = ~formData.get('email')~; // From the browser, read once at submit
    console.log({ email, ~password~ }); // From state
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Sign up</h2>
      <label>
        Email
        <input ~name="email"~ /> {/* Uncontrolled: read at submit */}
      </label>
      <label>
        Password
        <input
          type="password"
          ~value={password}~ // Controlled: shows only what password holds
          onChange={e => setPassword(e.target.value)}
        />
      </label>
      <p>{~password.length < 8~ ? 'Use 8 or more characters' : 'Looks good'}</p> {/* Changes after the eighth character */}
      <button type="submit">Sign up</button>
    </form>
  );
}
```

The Password field has no `name`. It does not need one: our code never asks the form data for the password. It already has it in state.

The user types `john@mail.com`, and the Console gets no new line. The user types `secret12`, and two `SignupForm rendered` lines appear after every keystroke, as in Principle 2. Now we clear the Console with its clear button, and the user clicks Sign up. The click changes no state, so React renders nothing, and the Console shows one line with both values:

### `useState('')`, never `useState()`

When you make a field controlled, start its state with `''` (Lesson 20). What happens with `useState()` and no start value?
1. `password` starts as `undefined`. A `value` of `undefined` counts as no value at all, so the field starts uncontrolled.
2. When the user types the first letter, `password` becomes a string, and the field turns controlled. React prints a red error in the Console that begins "A component is changing an uncontrolled input to be controlled".

In our form, the page breaks even before that. `password.length` asks for the length of `undefined`, so the page stays blank when it loads, and the Console shows the red error "Cannot read properties of undefined".

Remember: the page changes while the user types? Then the field goes into state, and its state starts with `''`.

## PRINCIPLE | `useState` in `SignupForm`: each keystroke renders only the form

> [!PRINCIPLE]
> **Principle 4: Keep the State of a Field in the Form Component**
>
> *Write the `useState` of a controlled field in the component that holds the form, not in `App`, so each keystroke renders only the form.*
>
> A state change renders the component that holds the state and every component inside it. The state of a field at the top of the page renders the whole page after every keystroke, header included. The same state inside the form component gives the same form, and React renders only the form.
>
> **DO THIS:**
> ```jsx
> function SignupForm() {
>   const [password, setPassword] = ~useState('')~; // Each keystroke renders only SignupForm
> }
> export default function App() {
>   return <main><SiteHeader /><SignupForm /></main>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   const [password, setPassword] = ~useState('')~; // **WRONG:** each keystroke renders App, SiteHeader, and SignupForm
>   return <main><SiteHeader /><SignupForm password={password} onPasswordChange={setPassword} /></main>;
> }
> ```

### The same `password` state in two places

Every keystroke in the Password field renders the component that holds `password`. Which component is that? The one where you write `useState`.

To see it, add a log line to the header too:

```jsx title="src/components/SiteHeader.jsx"
export default function SiteHeader() {
  ~console.log('SiteHeader rendered');~ // Prints every time React calls SiteHeader
  return (
    <header>
      <h1>MyShop</h1>
    </header>
  );
}
```

In the first version, `App` holds `password` and passes it down to the form as props (Lesson 24):

```jsx title="src/App.jsx with the state in App"
export default function App() {
  const [password, setPassword] = ~useState('')~; // Every keystroke changes state in App
  return (
    <main>
      <SiteHeader />
      <SignupForm password={password} onPasswordChange={setPassword} />
    </main>
  );
}
```

Here `SignupForm` has no state of its own. Its Password field shows the `password` it gets from `App`, and calls the function `App` passed down (Lesson 23):

```jsx title="The Password field inside SignupForm, with the state in App"
<input type="password" value={password} onChange={e => ~onPasswordChange~(e.target.value)} /> {/* Calls setPassword of App, so the state in App changes */}
```

In the second version, `App` holds no state, and `SignupForm` keeps `password` itself, as in Principle 3:

```jsx title="src/App.jsx with the state in SignupForm"
export default function App() {
  return (
    <main>
      <SiteHeader />
      ~<SignupForm />~ {/* SignupForm holds password itself */}
    </main>
  );
}
```

Both versions give the same page, the same hint, and the same submit. Only the Console tells them apart. The page loads, and the user types the letter `s` into the Password field of each version:

::: row caption="The same password state placed in App or in SignupForm: the page is the same, but only the state in App renders SiteHeader on every keystroke."


**With the state in `App`, every keystroke renders the header too, though nothing in the header changed.** Here is what happens after one letter:
1. `onChange` calls `onPasswordChange`, and that function is the setter of the state in `App`.
2. React renders `App` again.
3. Rendering `App` means React calls every component inside it again: `SiteHeader` and `SignupForm`.
4. The Console shows `SiteHeader rendered` after every keystroke.

The rule behind it: a state change renders the component that holds the state, and every component inside it. With the state in `App`, that is the whole page. With the state in `SignupForm`, that is only the form.

```tree caption="Where the password state lives decides which components React renders after every keystroke by the user."
Which components render after one keystroke
- !State in `App` [`App`] | React renders **`App`** again | `SiteHeader` and `SignupForm` **both render**, so the **whole page** renders on every keystroke
- +State in `SignupForm` [`SignupForm`] | React renders **`SignupForm`** again | `SiteHeader` **stays still**, and only the **form** renders on every keystroke
```

How does a developer end up with the first version? By writing the form straight inside `App`, next to the rest of the page. On a small page like ours, nobody notices. On a big page, every keystroke renders the whole page, and typing gets slow.

The React docs give the first fix: move the state of the field into the component that holds the field. Two other cases remain:
1. **The rest of the page really needs the typed text.** Then the state has to live higher (Lesson 24). React offers `useDeferredValue` to keep the field quick during a large render, and Lesson 68 covers it.
2. **The page does not need the text while the user types.** Then the field gets a `name` and is read at submit, as in Principle 1.

Remember: the state lives where the form lives, so each keystroke renders only the form.

## All 4 Principles Together

### The complete files

The Email field has a `name`, and our code reads it once at submit. The Password field is in state, because the hint follows it. The state lives in `SignupForm`, so the header does not render while the user types.

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  ~<StrictMode>~ {/* In development, React calls each component twice per render */}
    <App />
  </StrictMode>
);
```

```jsx title="src/App.jsx"
import SiteHeader from './components/SiteHeader.jsx';
import SignupForm from './components/SignupForm.jsx';

export default function ~App~() { // 1. Called 1st when the page loads, and holds no state
  return (
    <main>
      <SiteHeader />
      <SignupForm />
    </main>
  );
}
```

```jsx title="src/components/SiteHeader.jsx"
export default function ~SiteHeader~() { // 2. Called 2nd on page load, and never while the user types
  console.log('SiteHeader rendered');
  return (
    <header>
      <h1>MyShop</h1>
    </header>
  );
}
```

```jsx title="src/components/SignupForm.jsx"
import { useState } from 'react';

export default function ~SignupForm~() { // 3. Called 3rd on page load, and again after every keystroke in the Password field
  const [password, setPassword] = ~useState('')~; // Principles 3 and 4: in state, in the form component
  console.log('SignupForm rendered');

  function handleSubmit(e) {
    e.preventDefault();
    const formData = ~new FormData(e.currentTarget)~; // Principle 1: collects every field that has a name
    const email = formData.get('email');
    console.log({ email, password });
  }

  return (
    <form onSubmit={handleSubmit}>
      <h2>Sign up</h2>
      <label>
        Email
        <input ~name="email"~ /> {/* Principles 1 and 2: uncontrolled, no render while the user types */}
      </label>
      <label>
        Password
        <input
          type="password"
          ~value={password}~ // Principle 3: controlled, so the hint follows every keystroke
          onChange={e => setPassword(e.target.value)}
        />
      </label>
      <p>{password.length < 8 ? 'Use 8 or more characters' : 'Looks good'}</p>
      <button type="submit">Sign up</button>
    </form>
  );
}
```

### When React calls each component

On page load, React calls `App`, then `SiteHeader`, then `SignupForm`. After that, only one action makes React call a component again: a keystroke in the Password field, which renders `SignupForm` alone. Typing the email and clicking Sign up render nothing:

```tree caption="Which components React calls on page load, on a keystroke in each field, and on submit."
`App` [1. Called on page load] | Holds **no state** | Renders `<SiteHeader />` and `<SignupForm />`
- +`SiteHeader` [2. Called on page load] | Logs `SiteHeader rendered` | **Never** called again while the user types
- +`SignupForm` [3. Called on page load] | Logs `SignupForm rendered` | Called again after **every keystroke in the Password field**
  - +Email field [`name="email"`] | Typing calls **no component** | Read **once** in `handleSubmit` with `FormData`
  - +Password field [`value={password}`] | Typing calls **`SignupForm`** again | The hint changes after the **eighth character**
```

| Where it goes wrong | What the user sees | The fix |
| :--- | :--- | :--- |
| **A field without `name`** | The sign up code gets `null`, with no error | Write the same name on the field and in `formData.get` |
| **Every field in state** | In a large form, the letters appear late | Give a field state only when the page changes while the user types |
| **The hint with only a `name`** | The hint never changes | Make the field controlled with `value` and `onChange` |
| **`useState()` with no start value** | A blank page, or the uncontrolled to controlled error | Start the state with `''` |
| **The state of a field in `App`** | Every keystroke renders the whole page | Keep the state in the component that holds the form |

One last time, the sentence of this lesson: **a field goes into state only when the page must change while the user types. Every other field stays with the browser, and you read it once, at submit, with `FormData`.**

## For the Interview

> **The Interview Question:** Should a form use controlled state or uncontrolled FormData, and how do you choose?

### How to Answer Clearly in 30 Seconds

"I choose for each field, not for the whole form. A controlled field, with `value` and `onChange`, keeps its text in state, so React renders the component after every keystroke. An uncontrolled field keeps its text in the browser, and I read it once at submit with `new FormData(e.currentTarget)` and `formData.get`, using the field's `name` as the key. So:
1. **Uncontrolled with `FormData`** when the page reads the field only at submit: no render while the user types, and less code.
2. **Controlled** when the page must change on every edit, such as a password hint, a character limit, suggestions, or a button disabled until the form is valid, or when something other than typing changes the text.
3. **Mixed** in one form: I read the controlled fields from state and the others from `FormData`, and I keep the state of each field in the component that holds the form, so each keystroke renders only that component."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Your `FormData` code returns `null` for a field. What happened?"**
   The field has no `name`, or its `name` differs from the string passed to `formData.get`. `FormData` keys each entry by the field's `name`, so a field without one is left out, and `formData.get` returns `null` for a name it does not hold. Nothing on the page shows an error. To turn the whole form data into a plain object, the React docs use `Object.fromEntries(formData.entries())`, and the same `formData` can be sent with `fetch` as the request body.
2. **"Aren't controlled inputs always slow?"**
   No. The cost is the render, not the field. A small form with a few controlled fields renders in no time. It gets slow when the component that holds the state renders a large tree after every keystroke, such as a forty-field form where every field has its own state, or the state of a field placed in `App`. The fixes, in order:
   1. Make a field uncontrolled when the page reads it only at submit.
   2. Move the state of the field down into the component that holds the field.
   3. When the rest of the page really needs the text, use `useDeferredValue`, which Lesson 68 covers. Unlike debouncing, it waits for no fixed delay.
3. **"Can one field be controlled at first and uncontrolled later, or both at once?"**
   No. The React docs say a field cannot be both controlled and uncontrolled at the same time, and it should not switch during its lifetime. That is why a controlled field starts with `''` and not `undefined`. With `undefined`, the field starts uncontrolled, and the first keystroke makes React print the error "A component is changing an uncontrolled input to be controlled". Different fields of the same form can still make different choices. In React 19, form actions receive the same `FormData` directly, which makes uncontrolled fields the natural default for fields read only at submit. Lesson 41 covers form actions.

```tree dir=right caption="Interview comparison: how to choose between a controlled field and an uncontrolled field read with FormData."
How to choose for each field of a form
- +Uncontrolled, read with `FormData` [`name="email"`] | The page reads the field **only at submit** | **No render** while the user types, and it needs a **`name`**
- +Controlled, kept in state [`value` `onChange`] | The page **changes on every edit**, or a button also **changes the text** | **One render per keystroke**, so keep the state in the **component that holds the form**
```
