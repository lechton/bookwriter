## VS | The File We Write vs. the Code the Browser Runs: the same `ChatRoom.jsx`, only the compiled version keeps a cache

> Every letter the user types into a chat renders the chat room again, and every message row with it, even though no message changed. **The React Compiler rewrites each of your components while Vite builds the app, and adds a cache that hands back the same JSX as long as nothing it depends on has changed.** The reason: `memo` and `useCallback` written by hand are easy to get wrong, and the compiler does the same job on plain code, as long as that code follows the Rules of React.

You already use a compiler every day, and you probably never think about it. The browser cannot read JSX. When you write `<div>Hello World</div>` in a `.jsx` file, Vite turns it into a plain JavaScript function call before the browser ever sees it:

```jsx title="What we write in MyApp.jsx"
export default function MyApp() {
  return ~<div>Hello World</div>~; // JSX: the browser cannot read this line
}
```

```js title="What Vite sends to the browser"
import { jsx as _jsx } from "react/jsx-runtime";
export default function MyApp() {
  return ~_jsx("div", { children: "Hello World" })~; // Plain JavaScript: a call to a function that React provides
}
```

So the file in your editor and the code the browser runs are already two different things. The React Compiler adds one more step to that same build. It reads each component and each Hook, and it writes a new version of it that remembers the JSX it returned last time. When nothing that JSX depends on has changed, the new version hands back the same JSX instead of creating it again.

Remember what Lessons 55 to 57 did by hand: `memo` on the row, `useCallback` on the handler, and a dependency list to keep right. The compiler writes the same kind of memoization into the component for you. React's docs call it "the equivalent of manual memoization".

Keep one sentence in mind for the whole lesson: **the file you write and the code the browser runs are two different things.** The compiler changes only the second one.

```jsx title="src/components/ChatRoom.jsx"
import { useState } from 'react';
import Message from './Message.jsx';

const initialMessages = [
  { id: 1, text: 'Hi!' },
  { id: 2, text: 'Lunch at 12?' },
  { id: 3, text: 'Sure' },
];

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);
  const [text, setText] = useState('');
  ~console.log('ChatRoom rendered');~ // Prints one line each time the chat room renders

  function handleDelete(id) {
    setMessages(messages.filter(m => m.id !== id));
  }

  function handleSend() {
    setMessages([...messages, { id: crypto.randomUUID(), text }]);
    setText('');
  }

  return (
    <section>
      <ul>
        {messages.map(m => (
          <Message key={m.id} text={m.text} ~onDelete={() => handleDelete(m.id)}~ /> // A new arrow function for each row, on every render
        ))}
      </ul>
      <input value={text} onChange={e => setText(e.target.value)} />
      <button onClick={handleSend}>Send</button>
    </section>
  );
}
```

**It may look the same, but it is NOT the same thing!** The files in our editor are the same in both builds. The code the browser runs is not. When Vite built the app the second time, the compiler read `ChatRoom` and `Message` and wrote a new version of each one. Each new version keeps a cache: it remembers the JSX the component returned last time, and hands it back when nothing it depends on has changed.


### Three Words for This Lesson

> [!DEFINITION]
> **What is a compiler?** [NEW] A compiler is a program that reads the code we write and writes new code from it. Vite already compiles every JSX tag into a plain function call. The React Compiler is a second compiler in the same build: it reads our components and Hooks, and writes a version of each one that keeps a cache and reuses JSX and values whose inputs did not change. It comes in the package `babel-plugin-react-compiler` (Lesson 63).

> [!DEFINITION]
> **What is build time?** [NEW] Build time is the moment Vite prepares our files for the browser, before any of our code runs in the browser. What happens at build time, such as JSX turning into function calls, never shows up in the Console or the Elements panel. React's docs call the compiler "a new build-time tool that automatically optimizes your React app" (Lesson 63).

> [!DEFINITION]
> **What is memoization?** [REVIEW] Memoization means keeping a result and handing it back while its inputs stay the same, instead of producing it again. `memo` skips a component whose props did not change, `useMemo` keeps a calculated value, and `useCallback` keeps the same function between renders (Lessons 55 to 57).

### What Is at Stake

Two things are at stake: how fast the letters appear in the message field, and how much code we must keep right by hand.
1. **Speed.** In a chat with a long history, each keystroke renders every message row again. When the rows are many or slow, the letters appear late in the field.
2. **Code kept right by hand.** Lessons 55 to 57 fixed it with `memo`, `useCallback`, and a dependency list, and one arrow function on the tag broke it again. React's docs say that manual memoization "is tedious, easy to get wrong, and adds extra code to maintain."
3. **The gain.** With the compiler on, the same rows skip the keystrokes, and the code stays plain.
4. **The condition.** The compiler relies on our components following the Rules of React. A component that breaks them can show old information once its output is reused, such as a "min ago" label under a message that stops changing.

Developers usually go wrong in five places:
1. They think the compiler is a library or a Hook that runs in the browser. It runs when the app is built.
2. They think that once the compiler is on, they should delete every `memo`, `useMemo`, and `useCallback` in the app. React's docs advise leaving existing memoization in place, or testing carefully before removing it.
3. They think the compiler fixes code that breaks the Rules of React. It skips the code it sees breaking them, and it can still compile code that breaks them in ways it cannot see.
4. They think the compiler makes the first load of the page faster. React's docs say its memoization is mainly for update performance: rendering again the components that are already on the page.
5. They turn it on for a large existing app in one step, with no lint and no tests.

### Four Ways to Stop Rows from Rendering on Every Keystroke

When a child renders again and again with the same data, you have four choices:

```tree caption="Four ways to deal with rows that render again on every keystroke, and when each one fits."
Four ways to deal with rows that render on every keystroke
- +1. Leave it and measure first | Fits when the user feels **no lag** | React's docs: "React is often fast enough without optimization"
- +2. Move state down or pass JSX as `children` [`children`] | Fits when the fast-changing state can live **lower in the tree** | Lesson 58
- +3. `memo`, `useMemo`, and `useCallback` by hand [`memo` `useCallback`] | Fits an app that **cannot use the compiler yet**, and a few places that need **precise control** | Lessons 55 to 57
- +4. The React Compiler [`reactCompilerPreset`] | Fits **new apps from the first day**, and existing apps that follow the Rules of React, **turned on step by step** | This lesson
```

React's docs say it plainly: "We encourage everyone to start using React Compiler." They also say that in the future, some features may need the compiler to work fully.

### The Rule of Thumb: does the component give the same JSX for the same props and state?

**Write your components plain, and keep render pure. The compiler reuses JSX only because it trusts that the same props and state always give the same JSX.**

## SECTION | The Chat Room from Lesson 57

We build the chat room of Lessons 55 to 57. The user does three things on it: types in the message field, clicks Send, and clicks Delete on a row. `ChatRoom` holds two state variables: `messages`, the list, and `text`, what the message field shows.

The project has these files. The main file mounts `App` inside `<StrictMode>` (Lesson 07). `App` renders the chat room. The Vite config tells Vite how to build the app:


The opening used plain files to show what the compiler does. Our project starts where Lesson 57 ended, with the memoization we wrote by hand. `Message` is wrapped in `memo`. The delete handler comes from `useCallback`, so the same function reaches every row on every render:

```jsx title="src/components/Message.jsx"
import { memo } from 'react';

const Message = ~memo~(function Message({ id, text, onDelete }) { // Skips this row when id, text, and onDelete are the same
  console.log('Message rendered:', text);
  return (
    <li>
      {text} <button onClick={() => onDelete(id)}>Delete</button>
    </li>
  );
});

export default Message;
```

```jsx title="src/components/ChatRoom.jsx"
import { useCallback, useState } from 'react';
import Message from './Message.jsx';

const initialMessages = [
  { id: 1, text: 'Hi!' },
  { id: 2, text: 'Lunch at 12?' },
  { id: 3, text: 'Sure' },
];

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);
  const [text, setText] = useState('');
  console.log('ChatRoom rendered');

  const handleDelete = ~useCallback~((id) => { // The same function on every render
    setMessages(ms => ms.filter(m => m.id !== id));
  }, []);

  function handleSend() {
    setMessages([...messages, { id: ~crypto.randomUUID()~, text }]); // A new random id from the browser, not nextId++
    setText('');
  }

  return (
    <section>
      <ul>
        {messages.map(m => (
          <Message key={m.id} id={m.id} text={m.text} onDelete={handleDelete} />
        ))}
      </ul>
      <input value={text} onChange={e => setText(e.target.value)} />
      <button onClick={handleSend}>Send</button>
    </section>
  );
}
```

One line differs from Lesson 57. `handleSend` takes the new id from `crypto.randomUUID()`, a browser function that returns a new random id, instead of `nextId++`. Why? Version 1.0 of the compiler cannot compile `++` on a variable declared outside the component. It would skip the whole `ChatRoom`, the page would show no error, and every row would render again on each keystroke, as if the compiler were off.

By the end of the lesson, both files are plain again, and the compiler does the work.

**PRINCIPLES:** The file you write and the code the browser runs are two different things. The React Compiler writes the second one at build time, with a cache that reuses JSX and values whose inputs did not change, and it can do this safely only for code that follows the Rules of React. Four principles follow:
1. **Principle 1: `reactCompilerPreset` Adds a Cache to Each Component at Build Time.** We turn the compiler on in `vite.config.js` and call nothing in our components. The browser runs a version of each component that stores its JSX and reuses it while its inputs stay the same.
2. **Principle 2: A Plain `ChatRoom` Keeps the Rows Still Without `memo` or `useCallback`.** With the compiler on, plain files keep the rows still while the user types. The `memo`, `useMemo`, and `useCallback` already in an app stay in place until tests show they can go.
3. **Principle 3: `Date.now()` in `Message` Freezes the "min ago" Label.** When the compiler sees a break of the Rules of React, it leaves that component as written. When it cannot see the break, reused output can show old information.
4. **Principle 4: `"use memo"` Lets a Team Compile One Component at a Time.** A new app turns the compiler on from the first day. An existing app runs the lint first, then compiles one component, one folder, or one group of users at a time, and pins the compiler to an exact version.

## PRINCIPLE | `reactCompilerPreset` in `vite.config.js`: every component gets a cache when Vite builds the app

> [!PRINCIPLE]
> **Principle 1: `reactCompilerPreset` Adds a Cache to Each Component at Build Time**
>
> *Turn the React Compiler on in the build config; it rewrites each component and Hook when the app is built, and our source files stay exactly as we wrote them.*
>
> Without the compiler, a component creates its JSX again on every render. With it, the browser runs a version the compiler wrote, which gets a cache from `react/compiler-runtime` and returns the stored JSX while its inputs stay the same. Nothing in our components calls the compiler, so we see it in only three places: the build config, the build output, and the Memo badge in React Developer Tools.
>
> **DO THIS:**
> ```js
> export default defineConfig({
>   plugins: [react(), ~babel({ presets: [reactCompilerPreset()] })~], // The compiler runs at build time
> });
> ```
>
> **DO NOT DO THIS:**
> ```js
> export default defineConfig({
>   plugins: [react(~{ babel: { plugins: ['babel-plugin-react-compiler'] } }~)], // **WRONG:** version 6 of the Vite plugin for React removed this inline babel option
> });
> ```

### A Cache in Plain JavaScript

How do you skip repeated work in plain JavaScript? You store the result in a variable. Next time, you check the variable first, and you build the result only if nothing is stored yet:

```js title="Plain JavaScript: build the result once, then hand back the stored one"
let cached;

function getGreeting() {
  if (~cached === undefined~) { // Nothing stored yet: build it now
    cached = buildGreeting();
  }
  return cached; // Every later call: the stored result
}
```

That variable is a cache, and that `if` is the check. The compiler writes this same pattern into every component, around every piece of JSX.

### The Smallest Component, Compiled

React's docs show the compiler on the smallest component there is, one function that returns one `<div>`:

```jsx title="MyApp.jsx: the smallest component in React's docs"
export default function MyApp() {
  return ~<div>Hello World</div>~; // Creates a new div element on every render
}
```

With the compiler on, Vite does not send this function to the browser. It sends the version the compiler wrote. React's installation guide prints it, so that we can check that the compiler runs:

```js title="Build output: MyApp after the React Compiler"
import { c as _c } from "react/compiler-runtime";
export default function MyApp() {
  const $ = ~_c~(1); // Gets this component's cache from React
  let t0;
  if (~$[0] === Symbol.for("react.memo_cache_sentinel")~) { // The cache check: is anything stored here yet?
    t0 = <div>Hello World</div>;
    ~$[0] = t0;~ // First render: stores the new div in the cache
  } else {
    ~t0 = $[0];~ // Every later render: takes the div stored last time
  }
  return t0;
}
```

It is the plain JavaScript cache from above, with different names. Here it is in the order it runs:
1. The first line calls `_c` and gets back `$`, the cache that belongs to this component on the page. `$` is an array with one place, `$[0]`.
2. On the first render, `$[0]` still holds a special value made with `Symbol.for`. Read from the code, that value means "nothing stored yet", the same job `undefined` did in our plain cache. So the `if` is true: the code creates the `<div>` and stores it in `$[0]`.
3. On every later render, `$[0]` holds the stored `<div>`. The `if` is false, so the code creates nothing and returns the same `<div>` as last time.

**It may look the same, but it is NOT the same thing!** The page shows `Hello World` either way. The function we wrote creates a new `<div>` on every render. The function the browser runs creates it once, and after that it hands React the stored one. React's docs call that `if` a **cache check**: before the compiled code creates a piece of JSX, it asks the cache whether it already holds one with the same inputs.

```tree caption="The function we write versus the function the compiler writes for the browser."
Two versions of `MyApp`
- !The file we write [`return <div>Hello World</div>`] | Runs the same way **on every render** | Creates a **new `<div>`** each time
- +The build output [`$[0]` `t0`] | Asks the **cache** first | Creates the `<div>` **once**, then returns **the stored one**
```

Three names in the build output appear nowhere in our file. The compiler wrote all three:
1. **`_c`** is the function `c`, imported from `react/compiler-runtime`. React 19 provides it, just as it provides `jsx` from `react/jsx-runtime`. The compiler adds that import line at the top of every file it compiles.
2. **`$`** is the cache that `_c` returns. Each compiled component on the page gets its own.
3. **`t0`** is a variable the compiler creates to hold the JSX. Our code never names it.

So nothing in our code calls the compiler. There is no Hook to call and no import to add. The compiler writes the one new import by itself. That is why a developer who does not know the compiler is on cannot explain why a component skips a render: the reason is not in the source.

### The Compiler Turned On in Our Chat Room

The compiler comes in a package named `babel-plugin-react-compiler`. **Babel** is a tool that reads JavaScript and writes new JavaScript, and the compiler runs inside it as a **Babel plugin**. For a Vite app with version 6 or later of `@vitejs/plugin-react`, React's docs install two packages:

```bash title="Terminal"
npm install -D babel-plugin-react-compiler@latest
npm install -D @rolldown/plugin-babel
```

The `-D` flag saves both packages as a **devDependency**: a package that only the build uses. The browser never downloads them. The second package, `@rolldown/plugin-babel`, runs Babel inside Vite's build.

Then `vite.config.js` gains one plugin:
1. **`reactCompilerPreset`** comes from the Vite plugin for React. A **preset** is a ready-made set of Babel settings, and this one holds the settings that run the compiler.
2. **`babel`** comes from `@rolldown/plugin-babel`, and runs that preset while Vite builds the app.

```js title="vite.config.js" good="8"
import { defineConfig } from 'vite';
import react, { ~reactCompilerPreset~ } from '@vitejs/plugin-react'; // Provided by the Vite plugin for React
import babel from '@rolldown/plugin-babel';

export default defineConfig({
  plugins: [
    react(),
    ~babel({ presets: [reactCompilerPreset()] })~, // Runs the compiler on every component and Hook
  ],
});
```

Older guides pass the compiler to `react()` through a `babel` option instead. Version 6 of the Vite plugin for React removed that option, so we use the Babel plugin for Vite.

`ChatRoom.jsx` and `Message.jsx` still hold the hand-written code of Lesson 57. The page looks exactly as before, the Elements panel shows the same nodes, and the Console shows no new message. The change lives only in the code Vite hands to the browser.

### Mistake: The Compiler Turned On in a React 18 App

The import of `react/compiler-runtime` trips up teams that are still on React 18:
1. A team on React 18 installs `babel-plugin-react-compiler` and keeps the compiler's default `target`, which is `'19'`. The `target` option tells the compiler which version of React the app uses.
2. The compiled files import `react/compiler-runtime`, which React 18 does not have.
3. The app does not load. Vite shows an error that `"./compiler-runtime"` is not exported from the `react` package.

The fix has two parts. First, install `react-compiler-runtime` as a normal dependency, not a devDependency, because the browser needs it while the app runs:

```bash title="Terminal"
npm install react-compiler-runtime@latest
```

Then set `target` to the version of React the app uses:

```js title="vite.config.js"
babel({
  presets: [reactCompilerPreset({ ~target: '18'~ })], // Compiled files import from react-compiler-runtime
}),
```

Remember: the file you write and the code the browser runs are two different things. With the compiler on, the code the browser runs imports something your files never import.

## PRINCIPLE | `ChatRoom` without `memo` or `useCallback`: the compiled version still skips the rows on every keystroke

> [!PRINCIPLE]
> **Principle 2: A Plain `ChatRoom` Keeps the Rows Still Without `memo` or `useCallback`**
>
> *With the compiler on, write new components plain; keep the `memo`, `useMemo`, and `useCallback` already in the code, or remove them only after testing.*
>
> Without the compiler, every keystroke renders every row, and only `memo` with a stable function from `useCallback` stops it. With the compiler, the compiled `ChatRoom` returns the same `<Message>` elements while `messages` stays the same array, so React skips the rows, even with an arrow function on the tag. `useMemo` and `useCallback` remain an escape hatch for values that must stay the same, such as an Effect dependency.
>
> **DO THIS:**
> ```jsx
> function handleDelete(id) {
>   setMessages(messages.filter(m => m.id !== id));
> }
> <Message key={m.id} text={m.text} ~onDelete={() => handleDelete(m.id)}~ /> // The compiler reuses this element while messages stays the same
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const options = ~{ serverUrl, roomId }~; // **WRONG:** its useMemo was deleted on day one, so the Effect below may now fire at other moments
> useEffect(() => {
>   const connection = createConnection(options);
>   connection.connect();
>   return () => connection.disconnect();
> }, [options]);
> ```

### Why Plain Rows Skip a Keystroke

Here is the arrow function that broke `memo` in Lesson 57, now on a plain `Message` with no `memo` at all:

```jsx title="A plain row, and a new arrow function on its tag"
export default function Message({ text, onDelete }) {
  return <li>{text} <button onClick={onDelete}>Delete</button></li>;
}

<Message key={m.id} text={m.text} ~onDelete={() => handleDelete(m.id)}~ /> {/* A new function on every render of ChatRoom */}
```

Many developers expect that without `memo` and `useCallback`, every row renders again on every keystroke. Without the compiler, it does. With the compiler, it does not, as the opening of this lesson showed.

**The rows stay still because the compiled `ChatRoom` hands React the same three `<Message>` elements as last time.** Here is what happens after one keystroke:
1. The user types `O` in the message field. The setter changes `text`, so React renders the chat room again. The Console prints `ChatRoom rendered`.
2. The compiled `ChatRoom` reaches the list. The compiler wrote a cache check around it, and the check asks one question: is `messages` the same array as on the last render? It is, because typing changes only `text`.
3. So the compiled `ChatRoom` returns the three `<Message>` elements it stored last time, with the same arrow functions inside them.
4. React finds the very same elements in the same places, and skips the three rows. No `Message rendered:` line appears.

No line of our code stores those elements. The compiler wrote the cache check around the `map` at build time, the same way React's docs show it wrapping a child tag in a cache check. The arrow function on the tag no longer matters, because the whole element is reused, arrow function and all. React's docs say it of the same case: "React Compiler is able to optimize this correctly with or without the arrow function".

```jsx title="ChatRoom.jsx"
function handleDelete(id) {
  setMessages(messages.filter(m => m.id !== id));
}

<Message key={m.id} text={m.text} ~onDelete={() => handleDelete(m.id)}~ /> // Reused while messages stays the same
```
The compiled `ChatRoom` gives React the same element it stored last time.

**While the user types, the two give the same result: `ChatRoom rendered` in the Console, and no `Message rendered:` line.** React's docs say the compiler's memoization is "as precise, or moreso, than what you may have written", and that its cache check does "exactly what `React.memo` does".

They stop the render in different places:
1. **With `memo`**, React reaches `Message` and compares its props one by one. So we must keep `handleDelete` the same by hand, with `useCallback` and its dependency list.
2. **With the compiler**, `ChatRoom` itself returns the stored `<Message>` element, so nothing new ever reaches the row. That is why the plain code needs no dependency list.

```tree caption="Two ways the rows skip a keystroke: memo by hand, and the cache the compiler writes."
How the rows skip a keystroke
- +With `memo` and `useCallback` [`memo` `useCallback`] | We write the memoization **by hand** | React **compares the props** of each row, so every prop must stay the same
- +Plain, with the compiler [`reactCompilerPreset`] | The compiler writes the memoization **at build time** | `ChatRoom` returns **the stored element**, so the row gets nothing new
```

### The Memo Badge: Which Components Were Compiled

The source looks the same whether a component was compiled or not. So how do you check? When the app runs in development, React Developer Tools shows a badge next to each component the compiler optimized. It reads Memo, followed by a sparkle sign, and we call it **the Memo badge**.

With the plain files, both `ChatRoom` and `Message` show it, even though the code has no `memo` call. React Developer Tools adds the badge, and Lesson 64 covers the tool in full. Check the badge instead of guessing from the source.

### What the Compiler Speeds Up

React's docs say the compiler's memoization is mainly about **update performance**: rendering again the components that are already on the page, such as our rows after a keystroke. It does not mainly speed up the first load of the page. It covers two cases:
1. It skips rendering child components whose inputs did not change, as with our rows.
2. It skips expensive calculations inside a component or Hook, the job of `useMemo` (Lesson 56).

It has two limits:
1. It memoizes only components and Hooks, not every function in the app.
2. Its memoization is not shared between components. Each component keeps its own cache, so a heavy function called in ten components still runs once in each of them.

### The `memo`, `useMemo`, and `useCallback` Already in the Code

The compiler works with the memoization it finds:
1. It leaves `memo` in place.
2. It replaces each `useMemo` and `useCallback` with a cache check of its own.
3. When its own cache cannot keep a value as stable as the hand-written one, it skips the component.

**For new code**, React's docs say: rely on the compiler, and use `useMemo` or `useCallback` only where you need precise control over which values are memoized. The docs call these two Hooks an **escape hatch**: a way out of the automatic behavior, for the few places that need it. The common case is a value used as an Effect dependency (Lesson 37), which must stay the same object between renders.

**For existing code**, the docs advise one of two things:
1. Leave the existing memoization in place, because removing it can change what the compiler writes.
2. Or test carefully before removing it.

For `memo` itself, the docs say you can safely remove it from components when the compiler is on.

### Mistake: Every `useMemo` Deleted on the First Day

Here is what goes wrong when a team removes everything at once:
1. A team turns on the compiler in an app that already uses `useMemo` and `useCallback`.
2. The same day, they delete every `useMemo` and `useCallback`, because "the compiler does it now".
3. One of the deleted `useMemo` calls produced an object that sat in an Effect's dependency list.
4. The compiler now memoizes that object in its own way, so the Effect starts to run at other moments than before. React's docs name the symptoms: Effects that fire too often, infinite loops, or missing updates.

Nobody changed the Effect, so nobody looks at it. The fix is the docs' advice: leave existing memoization in place, or remove it one piece at a time, with tests.

### The Chat Room Becomes Plain

In our chat room, no Effect depends on `handleDelete` or on any memoized value, so removing `memo` and `useCallback` changes nothing else. We make both files plain:

```jsx title="src/components/Message.jsx"
export default function Message({ text, onDelete }) {
  console.log('Message rendered:', text);
  return (
    <li>
      {text} <button ~onClick={onDelete}~>Delete</button> {/* No memo: the compiled ChatRoom decides when this row renders */}
    </li>
  );
}
```

```jsx title="src/components/ChatRoom.jsx" startLine="15"
  function ~handleDelete~(id) { // A plain function: no useCallback, no dependency list
    setMessages(messages.filter(m => m.id !== id));
  }
```

```jsx title="src/components/ChatRoom.jsx" startLine="27"
        {messages.map(m => (
          <Message key={m.id} text={m.text} ~onDelete={() => handleDelete(m.id)}~ /> // The arrow function knows the id, so the row passes nothing back
        ))}
```

## PRINCIPLE | `Date.now()` during render: the compiler reuses the row, so the "min ago" label stops changing

> [!PRINCIPLE]
> **Principle 3: `Date.now()` in `Message` Freezes the "min ago" Label**
>
> *The compiler assumes pure components, props and state never changed in place, and Hooks at the top level; keep render pure, and let `eslint-plugin-react-hooks` show every break.*
>
> When the compiler sees a component break the Rules of React, such as a Hook called inside a condition, it skips that component quietly and keeps compiling the rest, so the page shows no error. When it cannot see the break, as with `Date.now()` during render, it compiles the component anyway, and reused output can show old information, such as a "min ago" label that stops changing. The fix is pure render: read the clock in an interval, keep the time in state, and pass the minutes as a prop.
>
> **DO THIS:**
> ```jsx
> const id = ~setInterval(() => setNow(Date.now()), 60000)~; // The clock is read outside render, once a minute
> <Message key={m.id} text={m.text} minutes={Math.floor((now - m.sentAt) / 60000)} onDelete={() => handleDelete(m.id)} />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const minutes = Math.floor((~Date.now()~ - sentAt) / 60000); // **WRONG:** reads the clock during render; the label goes stale once the row is reused
> ```

### What the Compiler Trusts: the Rules of React

Think about the cache check again. It hands back the stored JSX when the inputs are the same. That is safe only if the same inputs always give the same JSX. If a component can give different JSX for the same props and state, the stored JSX can be wrong.

React's docs collect what every component must follow under one name, the **Rules of React**:
1. **Components and Hooks must be pure.** The same props and state give the same JSX, and side effects run outside render (Lesson 14). Props and state are never changed in place (Lessons 17 and 19).
2. **React calls components and Hooks.** We write `<Message />` and let React call it. We never call `Message()` ourselves (Lesson 04).
3. **The Rules of Hooks.** Hooks are called at the top level, never inside a condition or a loop (Lesson 38).

When the compiler finds code that might break these rules, React's docs say it "safely skips optimization": it leaves that component or Hook exactly as written, and keeps compiling the rest of the app. The page shows no error.

### A "min ago" Label That Reads the Clock During Render

Chat screens show how long ago each message was sent. So each message gains `sentAt`, the moment it was sent, and `Message` shows the minutes since then:

```jsx title="src/components/ChatRoom.jsx" startLine="4"

  { id: 1, text: 'Hi!', ~sentAt: Date.now()~ }, // Read once, when the file loads
  { id: 2, text: 'Lunch at 12?', sentAt: Date.now() },
  { id: 3, text: 'Sure', sentAt: Date.now() },

```

```jsx title="src/components/ChatRoom.jsx" startLine="19"
  function handleSend() {
    setMessages([...messages, { id: crypto.randomUUID(), text, ~sentAt: Date.now()~ }]); // Read in an event handler: allowed
    setText('');
  }
```

```jsx title="src/components/ChatRoom.jsx" startLine="28"

```

```jsx title="src/components/Message.jsx"
export default function Message({ text, sentAt, onDelete }) {
  console.log('Message rendered:', text);
```

`Date.now()` gives the number of milliseconds since 1970, and `60000` is the number of milliseconds in one minute. Where the code reads the clock decides everything:
1. **Inside `handleSend`, it is fine.** An event handler runs outside render.
2. **Inside `Message`, it breaks the first rule.** The same props give a different label each time the row renders.

**Beware! Neither label is correct.** The label must change because a minute passed, not because the user pressed a key. Here is what happens with the compiler on:
1. At build time, the compiler compiles `ChatRoom` and `Message` alike. With its default settings, it does not look for `Date.now()` during render, so it sees no break in `Message`, and the page shows no error.
2. Two minutes later, the user types `O`. The compiled `ChatRoom` still reuses the three `<Message>` elements, because `messages` did not change.
3. So the rows do not render, and nothing reads the clock again. The labels still read `0 min ago`.

The compiler did not make the label wrong. The label was wrong from the start, because `Message` was not pure. The compiler only changed the moment when the user sees the bug. React's docs say the Rules of React are rules, and not just guidelines, in the sense that if they are broken, the app likely has bugs.

### Who Shows the Break: `eslint-plugin-react-hooks`

The page shows no error, so the developer must find the break in the editor. **ESLint** is the tool that checks our code in the editor and in the terminal, and each check it runs is called a lint rule. The compiler's findings come through an ESLint plugin, `eslint-plugin-react-hooks`, with its `recommended` preset turned on in the ESLint config:

```bash title="Terminal"
npm install -D eslint-plugin-react-hooks@latest
```

Its `purity` rule marks the `Date.now()` line in `Message` with the error "Cannot call impure function during render", the same way it marks `Math.random()` during render.

The lint is the only place this break shows. The build does not run this check, so the compiler still compiles `Message`, and nothing on the page warns anyone. The plugin works even if the app has not adopted the compiler yet. That makes it the first step for any existing app, as Principle 4 shows.

### VS | The Clock Read During Render vs. the Time Kept in State: the same label, only one moves on time

The fix is the one React's docs give for a clock: read the time outside render, keep it in state, and pass only props to the row. Compare the two places where the code can read the clock:

```jsx title="The clock read inside Message, during render"
const minutes = Math.floor((~Date.now()~ - sentAt) / 60000); // **WRONG:** the same props give a different label each render
```

```jsx title="The time kept in ChatRoom's state, updated once a minute"
const [now, setNow] = useState(() => Date.now()); // Reads the clock once, when ChatRoom appears

useEffect(() => {
  const id = ~setInterval(() => setNow(Date.now()), 60000)~; // Reads the clock again every minute, outside render
  return () => clearInterval(id);
}, []);

<Message key={m.id} text={m.text} ~minutes={Math.floor((now - m.sentAt) / 60000)}~ onDelete={() => handleDelete(m.id)} /> {/* Message gets the minutes as a prop */}
```

Both show the minutes since `sentAt`. **They are NOT the same thing!**
1. **The first one** reads the clock while `Message` renders, so the label depends on when the row happens to render.
2. **The second one** reads the clock in an interval, outside render (Lesson 32). `Message` gets only props, and its JSX depends only on them.

Now every minute, the interval sets a new `now`. React renders `ChatRoom`, the `minutes` props change, and every row renders with its new label. The labels move on time, with or without the compiler, and typing in the message field leaves them alone. `Message` takes a `minutes` prop instead of `sentAt`:

```jsx title="src/components/Message.jsx"
export default function Message({ text, ~minutes~, onDelete }) { // Only props: the same props give the same row
  console.log('Message rendered:', text);
  return (
    <li>
      {text} <small>{minutes} min ago</small> <button onClick={onDelete}>Delete</button>
    </li>
  );
}
```

### A Compiler Error vs. a Runtime Issue

React's docs name two kinds of trouble with the compiler, and they are not equally likely:
1. **A compiler error** stops the build. It is rare. With the default settings, the compiler skips a component it cannot handle, and the build goes on.
2. **A runtime issue** is compiled code that behaves differently from the code we wrote. It usually comes from a break of the Rules of React that the compiler could not see, so it compiled a component it should have skipped. Code that relies on memoization to work correctly can break the same way.

### Mistake: A Form Library That Changes Values in Place

Some libraries break the rules in a way the compiler cannot always see:
1. A form component reads a field with `watch('name')` from the react-hook-form library.
2. The value lives inside an object that stays the same object while its contents change. React's docs call this **interior mutability**: from the outside, it is the same object, so a cache check sees nothing new.
3. The `incompatible-library` lint rule knows this library, so the compiler skips the component, and the component keeps working.
4. For some libraries, such as MobX with its `observer`, the docs say "the linter does not yet detect them". The compiler can compile such a component.
5. The reused output does not follow the hidden change. React's docs show a `useMemo` over `watch` where the value "will never update" and the screen appears frozen. They add: "If something breaks with manual `useMemo`, it will also break the compiler's automatic optimization."

The docs' fix is the library's own API that follows the rules, such as `useWatch`, or `"use no memo"` on that component while the team fixes it.

Remember: the code the browser runs reuses JSX because it trusts your component. Keep render pure, and that trust is safe.

## PRINCIPLE | `"use memo"`: a team compiles one component at a time, and `"use no memo"` takes one out

> [!PRINCIPLE]
> **Principle 4: `"use memo"` Lets a Team Compile One Component at a Time**
>
> *Start new apps with the compiler on; in an existing app, run the lint first, then compile one component, one folder, or one group of users at a time, and pin an exact version.*
>
> A break of the rules that the compiler cannot see shows up only while the app runs. Compiling a small part first lets the team find it on a few screens, measure the gain, and fix rule breaks one by one. `"use memo"` in `'annotation'` mode marks a component to compile, and `"use no memo"` takes one out for a while, with a note that says why.
>
> **DO THIS:**
> ```jsx
> export default function ChatRoom() {
>   ~"use memo";~ // The first line of the body: the compiler compiles ChatRoom
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function Message({ text }) {
>   const data = getData();
>   ~"use no memo";~ // **WRONG:** not the first line, so the compiler ignores it
> }
> ```

### A Directive: a Plain String at the Top of a Function

Remember `"use strict"` at the top of an old JavaScript file? It is a plain string, alone on the first line, and yet it changes how the code is treated. That is a **directive**: a plain string written as the very first line of a function body, or of a file. MDN uses the same word for `"use strict"`.

JavaScript does nothing with a lone string. The compiler, though, reads it from the source at build time:

```jsx title="A directive at the top of Message"
export default function Message({ text, onDelete }) {
  ~"use memo";~ // JavaScript ignores this string; the compiler reads it at build time
  console.log('Message rendered:', text);
  return (
    <li>
      {text} <button onClick={onDelete}>Delete</button>
    </li>
  );
}
```

### VS | `"use memo"` vs. `"use no memo"`: one word apart, opposite jobs

The compiler knows two directives, and they look almost the same:

```jsx title="Asking the compiler to compile Message, and asking it to skip Message"
function Message({ text, onDelete }) {
  ~"use memo";~ // Compile this component: needed mainly in annotation mode
}

function Message({ text, onDelete }) {
  ~"use no memo";~ // Skip this component entirely, in every mode
}
```

**It looks the same, but it is NOT the same thing!** The two strings differ by one word, and they do opposite things:
1. **`"use memo"`** asks the compiler to compile the function.
2. **`"use no memo"`** makes the compiler skip it. React's docs say it "takes precedence over all compilation modes and other directives".

### `compilationMode`: Which Functions the Compiler Compiles

Why would you ever need `"use memo"`? Because of a compiler option, `compilationMode`. It decides which functions the compiler compiles:
1. **`'infer'`**, the default. The compiler compiles functions named like components, starting with a capital letter, or like Hooks, starting with `use`, that create JSX or call Hooks. Our chat room has used this mode so far.
2. **`'annotation'`**. The compiler compiles only the functions marked with `"use memo"`.

So in a large existing app, a team can switch to `'annotation'` and mark one component first. We pass this option to `reactCompilerPreset`. In our chat room, we mark only `ChatRoom`:

```js title="vite.config.js"
babel({
  presets: [reactCompilerPreset({ ~compilationMode: 'annotation'~ })], // Compiles only functions marked "use memo"
}),
```

```jsx title="src/components/ChatRoom.jsx" startLine="10"
export default function ChatRoom() {
  ~"use memo";~ // The only marked component in the app
  const [messages, setMessages] = useState(initialMessages);
```

We clear the Console, and the user types `O`. The Console shows only the chat room:

```page width=text caption="Annotation mode with use memo only in ChatRoom: after the user types O, only the chat room renders."
line: Hi! 0 min ago [Delete]
line: Lunch at 12? 0 min ago [Delete]
line: Sure 0 min ago [Delete]
form:
  field:  | O
  button: Send
log: ChatRoom rendered
log: ChatRoom rendered
```

The compiled `ChatRoom` reuses the `<Message>` elements, so the rows stay still, even though `Message` itself is not compiled. If we remove the directive, nothing in the app is compiled, and every row logs again on each keystroke.

### Three Ways to Compile One Part of the App at a Time

React's docs give three ways to try the compiler on part of an app before turning it on everywhere:

```tree caption="Three ways to compile one part of an existing app at a time."
Three ways to compile one part of an app at a time
- +1. One folder at a time [`overrides`] | A Babel option applies the compiler only to the folders listed in `test` | Fits an app with **one newer folder** that follows the rules
- +2. One component at a time [`"use memo"`] | `compilationMode` set to `'annotation'` | Fits picking **the first few components** by hand
- +3. One group of users at a time [`gating`] | The build holds **both versions** and a feature flag picks one | Fits an **A/B test** that measures the gain on real users
```

React's docs show the folder way in `babel.config.js`, Babel's own config file, with a newer folder named `modern`:

```js title="babel.config.js"
module.exports = {
  overrides: [
    {
      ~test: './src/modern/**/*.{js,jsx,ts,tsx}'~, // Only files inside src/modern are compiled
      plugins: ['babel-plugin-react-compiler'],
    },
  ],
};
```

The third way needs two more words:
1. A **feature flag** is a switch in our own code that turns a feature on for some users and off for others.
2. An **A/B test** uses it to show one version to some users and the other version to the rest, and compares the two.

The `gating` way has two costs:
1. The bundle, the JavaScript the browser downloads, holds both the compiled and the original version of each function, so it is larger.
2. Our flag function runs once, when the module loads, so the choice stays the same until the user loads the page again.

### Mistake: A Directive the Compiler Ignores

A directive is easy to write in a way the compiler ignores:
1. **It is not the first line.** A developer writes `const data = getData();` and then `"use no memo";` on the next line. The compiler still compiles the component, because a directive must be at the very beginning of the function body. React's docs label this example "Too late!".
2. **It uses backticks.** A directive must use double or single quotes, not backticks.
3. **The new component has none.** In `'annotation'` mode, a new component without `"use memo"` is not compiled. The docs remind us to add it to new components.

In `'infer'` mode, a Hook named without the `use` prefix, or a function that neither creates JSX nor calls Hooks, is not compiled. The docs advise fixing the name rather than forcing compilation with `"use memo"`.

### `"use no memo"` Is for a While, Not for Good

When one component misbehaves after the compiler is turned on, `"use no memo"` takes it out:

```jsx title="One component taken out while the team finds the bug"
export default function Message({ text, minutes, onDelete }) {
  ~"use no memo";~ // Rows stopped updating after compiling; remove once the cause is fixed
  console.log('Message rendered:', text);
  return (
    <li>
      {text} <small>{minutes} min ago</small> <button onClick={onDelete}>Delete</button>
    </li>
  );
}
```

If the bug disappears, React's docs say it is likely related to a break of the Rules of React. The team fixes the break and removes the directive. The docs say `"use no memo"` is "intended as a temporary debugging tool, not a permanent solution", and they ask us to always write down why it is there.

### New Apps and Existing Apps

**For a new app, the answer is simple: start with the compiler on.** `create-vite` and `create-next-app` offer templates with the compiler turned on, and Expo turns it on by default from SDK 54.

**For an existing app, go step by step:**
1. Install `eslint-plugin-react-hooks` with the `recommended` preset. It needs no compiler, so the team can fix what it reports at its own pace.
2. Compile one part: one folder, one component with `"use memo"`, or one group of users with `gating`.
3. Check the Memo badges in React Developer Tools, run the tests, and measure the screens that felt slow.
4. Widen the part, one step at a time, until the whole app is compiled.

React's docs say that how fast a team can roll it out depends on how well the code has followed the Rules of React.

### Mistake: A Version Range on the Compiler

The last trap needs no change to the app's code at all. In `package.json`, a version such as `^1.0.0` is a version range: the caret lets npm install newer `1.x` versions by itself. Here is how that goes wrong:
1. A team installs the compiler with the range `^1.0.0`, in an app with few tests.
2. Later, npm installs a newer compiler version by itself, and that version memoizes some values differently.
3. An Effect somewhere depended on one of those values, and it now fires more or less often.
4. Nobody changed the app's code, so nobody looks at the compiler.

React's docs advise pinning the compiler to an exact version when tests are few, such as `1.0.0` instead of `^1.0.0`, and upgrading it by hand. The `--save-exact` flag saves the exact version:

```bash title="Terminal"
npm install --save-dev --save-exact babel-plugin-react-compiler@latest
```

Remember: the code the browser runs comes from the compiler. A new compiler version writes new code, even when your files stay the same.

```jsx title="src/components/ChatRoom.jsx"
  }, []);

  function ~handleDelete~(id) { // Principle 2: a plain function, no useCallback
    setMessages(messages.filter(m => m.id !== id));
  }

  function handleSend() {
    setMessages([...messages, { id: crypto.randomUUID(), text, sentAt: Date.now() }]);
    setText('');
  }

  return (
    <section>
      <ul>
        {messages.map(m => (
          <Message
            key={m.id}
            text={m.text}
            ~minutes={Math.floor((now - m.sentAt) / 60000)}~ // Principle 3: the row gets the minutes as a prop
            onDelete={() => handleDelete(m.id)}
          />
        ))}
      </ul>
      <input value={text} onChange={e => setText(e.target.value)} />
      <button onClick={handleSend}>Send</button>
    </section>
  );
}
```

### How React Calls the Components, and What It Skips

When the page opens, React calls `App`, then `ChatRoom`, then one `Message` for each of the three messages. After that:
1. **A keystroke** renders only `ChatRoom`.
2. **A new minute** renders `ChatRoom` and every row, because every `minutes` prop changes.
3. **A sent or deleted message** renders `ChatRoom` and the rows, because `messages` is a new array.

### Without the Compiler and With It

| Aspect | Without the React Compiler | With the React Compiler |
| :--- | :--- | :--- |
| **Where it runs** | Nothing runs at build time; the browser runs the functions we wrote | The compiler rewrites each component and Hook at build time; the browser runs the compiled version |
| **Skipping rows** | `memo` on the row and a stable function from `useCallback`, kept right by hand | Plain code; the compiled parent reuses the elements, even with an arrow function on the tag |
| **Existing memoization** | Needed wherever a child must skip renders | The compiler builds on it; left in place or removed only after testing; `useMemo` and `useCallback` stay as an escape hatch |
| **Code that breaks the rules** | The bug shows whenever the component happens to render | Skipped quietly when the compiler sees the break; old information on the screen when it cannot see it |
| **Turning it on** | Nothing to turn on | New apps from day one; existing apps lint first, then compile one component, folder, or group of users at a time, with an exact version |

Remember the one sentence of this lesson: **the file you write and the code the browser runs are two different things.** Write the first one plain and pure, and let the compiler write the second one.

## For the Interview

> **The Interview Question:** What does the React Compiler do, and when should you adopt it?

### How to Answer Clearly in 30 Seconds

"The React Compiler is a build-time tool. When the app is built, it reads every component and Hook and writes a new version that keeps a cache and reuses JSX and values whose inputs did not change. That gives the effect of `memo`, `useMemo`, and `useCallback` without writing them, and an arrow function on a tag no longer breaks it. It relies on the Rules of React: pure render, props and state never changed in place, Hooks at the top level. When it sees a break, it skips that component. When it cannot see one, reused output can show old information. So:
1. **New apps** should start with it on.
2. **Existing apps** run `eslint-plugin-react-hooks` first, then compile one folder, one component with `"use memo"`, or one group of users, and widen step by step.
3. **Existing memoization** stays in place unless tests show it can go, and the compiler version is pinned when tests are few."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Once the compiler is on, can we delete all our `useMemo` and `useCallback` calls?"**
   **Not all at once.** For new code, React's docs say to rely on the compiler and use `useMemo` or `useCallback` only where precise control is needed, such as a value used as an Effect dependency. For existing code, they advise leaving the memoization in place, because removing it can change what the compiler writes, or testing carefully before removing it. The compiler replaces those calls with cache checks of its own, and it compiles a component only if its own memoization matches or exceeds the existing one. `memo` on a component can be removed safely.
2. **"What happens when a component breaks the Rules of React?"**
   **It depends on whether the compiler can see the break.** When it sees one, such as a Hook called inside a condition, it skips that component, leaves it exactly as written, and keeps compiling the rest of the app. `eslint-plugin-react-hooks` shows the same finding in the editor, and the component has no Memo badge in React Developer Tools.

   When it cannot see the break, it compiles the component, and the reused output can stop updating. `Date.now()` during render is such a break: only the lint reports it. A library value that changes inside the same object is another. Adding `"use no memo"` to the component is the quick test: if the bug disappears, the cause is likely a rule break.
3. **"Does the compiler make the app faster on the first load?"**
   **That is not its main goal.** React's docs say its memoization is mainly about update performance: skipping the rendering of components whose inputs did not change, and skipping expensive calculations inside components and Hooks. It memoizes only components and Hooks, and the cache is not shared between them.

   At the Meta Quest Store, React's team reports that some interactions became more than two and a half times faster, while initial loads and page changes improved by up to 12 percent, with memory use unchanged. It can also memoize after an early return, which `useMemo` cannot, because a Hook cannot be called after a `return` (Lesson 38).

```tree dir=right caption="How the compiler handles a component, from the build to the screen."
What the compiler does with each component
- +1. Reads it at build time [`babel-plugin-react-compiler`] | Checks it against the **Rules of React**
- !2a. Sees a break | **Skips** the component and leaves it as written | The lint shows the break; **no Memo badge**
- +2b. Sees no break | Writes a version with a **cache** | JSX and values are **reused** while their inputs stay the same
- !3. A break it could not see | The compiled code **reuses old output** | The screen can **stop updating**; `"use no memo"` takes it out while the team fixes it
```
