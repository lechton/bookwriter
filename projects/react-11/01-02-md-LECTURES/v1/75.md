# Lecture 75: How Automatic Batching Groups the Setters That Run After a Wait

*(Why do two setters that run three seconds after a click still give only one render?)*

> INTERVIEW QUESTION | ❱❱ MORE | How does automatic batching coordinate state updates across promises and timeouts?

---

## VS | Two setters in a click handler vs. two setters in a `setTimeout`: since React 18, both give one render

> You already know that two setters inside one click handler give one render, because React waits until the handler has finished before it renders. **Since React 18, React waits the same way for setters that run later, inside a `setTimeout` or after a promise: the setters that run together give one render.** So the screen never shows a half-finished state, where one value has changed and the other has not changed yet.

Many screens show **two numbers that must change together**. Think of a bank transfer of 10 dollars. Your balance goes down by 10, and your friend's balance goes up by 10. If the screen showed the first change without the second, even for a moment, the 10 dollars would seem to vanish. In React, the two balances are two state variables, and you change them with two setter calls, one after the other.

So the question is: does React render after each setter, or once after both? Inside a click handler, you know the answer from Lesson 16: once, after both. React does not render on the setter line. It writes the update into its queue, waits until your handler has finished, and then renders once with every update. This is batching.

But real apps often change state later, long after the click. The user clicks `Buy`, and the shop finishes the order three seconds later. A timer fires. A request to the server comes back. By then, the click handler finished long ago. **Since React 18, React batches these setters too: the setters that run together give one render, wherever they run.** React calls it automatic batching, because your code asks for nothing.

**Why:** Before React 18, React batched only inside its own event handlers, such as `onClick`. Two setters inside a `setTimeout` gave two renders, and the render in between showed one value changed and the other not. React's docs name what batching prevents: it "avoids dealing with confusing 'half-finished' renders where only some of the variables have been updated."

### What "Run Together" Means

Two reminders first, because this lesson stands on them.

> [!DEFINITION]
> **Batching.** [REVIEW] When your click handler calls a setter, React does not render on that line. It puts the update in a queue and goes on with the next line.
> When the whole handler has run, React renders once, with every update in the queue.
> So `setCount(1)` and then `setFlag(true)` inside one handler give one render, not two (Lesson 16).

> [!DEFINITION]
> **An updater function.** [REVIEW] Instead of a value, you can pass the setter a function: `setCount(c => c + 1)`.
> React calls it later, with the latest value of the state, after every update queued before it.
> Use it when the next value depends on the previous one (Lesson 16).

Now the key phrase of this lesson, "the setters that run together". Let's make it precise.

JavaScript runs your code one piece at a time. A click handler is one piece: it runs from its first line to its last line, with no pause, and nothing else runs in the middle. A `setTimeout` callback is another piece, which the browser runs later. React waits until the current piece has finished, and then renders once for every setter that piece called.

```jsx title="Two pieces of code, two renders"
function handleClick() {
  setPending(p => p + 1); // Piece 1: runs during the click
  ~setTimeout~(() => { // Piece 2: the browser runs it three seconds later
    setPending(p => p - 1);
    setCompleted(c => c + 1); // Same piece 2: one render for both setters
  }, 3000);
}
```

The click is piece 1. It calls one setter and starts a timer, and then it ends. React renders once. Three seconds later, the browser runs the callback, piece 2. It calls two setters, and React renders once more, for both of them.

> [!DEFINITION]
> **Automatic batching.** [NEW] Since React 18, React batches the setters that run together in one piece of code, wherever that code runs: in a click handler, in a `setTimeout`, after a promise, or in a handler attached with `addEventListener`.
> It is automatic because your code asks for nothing. You call the setters as usual, and React renders once.
> The React 18 upgrade guide: "Starting in React 18 with `createRoot`, all updates will be automatically batched, no matter where they originate from" (Lesson 75).

### The Rule of Thumb: did the setters run together?

**Setters that run together, in one piece of code with no pause, give one render. An `await` and a new click each start a new piece, so each starts a new batch.**

```tree caption="React batches the setters that run together, wherever they run; a wait and a new click each start a new batch."
What ends in one render since React 18
- +Setters that run together in one place [`onClick` `setTimeout` `then` `addEventListener`] | React groups them into **one batch** | The screen changes **once**, with **every value updated**
- !Setters on the two sides of a wait [`await`] | The code before the wait and the code after it **do not run together** | **Two batches**, so **two renders**
- !Setters in two separate clicks | Each click is **its own event** | Each click gets **its own render**
```

A senior developer also knows the three classic mistakes:
1. **Extra code to save renders.** Developers who learned React 17 still believe that setters inside a timeout or a promise render one by one. To save renders, they merge the two counts into one object, or add a debounce, a timer that waits and then runs the update once. The extra code saves nothing.
2. **One click, one render.** They expect one click to give exactly one render, even when the handler waits with `await`. It gives two.
3. **`setPending(pending - 1)` after `await`.** The screen shows `Pending: -1`, with no error.

When two values must change together after a wait, you have three ways to do it:
1. **Call two setters, one after the other.** React batches them by itself. This fits almost every case, and it is the default since React 18. This lesson is about this way.
2. **Keep the two values in one state variable**, as react.dev's advice "Group related state" says (Lesson 22). This fits when two separate variables could disagree. The reason is the shape of the state, not the number of renders.
3. **Wrap a setter in `flushSync`** to force a render before the next line runs (Lesson 65). This fits only when browser code or a library must see the new DOM at once. React's docs: "Use `flushSync` as last resort." This lesson uses it once, to show what batching prevents.

**PRINCIPLES:** React waits until a piece of code has run, and then renders once for every setter that piece called. Since React 18, this holds wherever the code runs. Four principles follow:
1. **Principle 1: Two Setters in a setTimeout Render Once.** Setters that run together in a timeout, a promise, or an `addEventListener` handler form one batch, as they do in a click handler.
2. **Principle 2: await Splits the Buy Click into Two Renders.** The setters before the wait form one batch, and the setters after it form a second batch. Two separate clicks are never batched together.
3. **Principle 3: pending - 1 After await Shows Pending: -1.** The code after the wait still reads the values of the click's render. An updater gets the latest state.
4. **Principle 4: flushSync Shows the Half-Finished Render.** Each `flushSync` renders its own update at once, so React renders a state where the order sits in neither count.

## PRINCIPLE | setTimeout and promises: the setters that run together give one render, since React 18

> [!PRINCIPLE]
> **Principle 1: Automatic Batching: Two Setters in a setTimeout Render Once**
>
> *Since React 18 with `createRoot`, setters that run together inside a timeout, a promise, a native event handler, or any other event give one render, the same way as setters inside a React event handler.*
>
> Before React 18, React batched only the setters inside React event handlers, so two setters in a `setTimeout` rendered twice. Now React groups the setters that run together, wherever they run. The screen changes once, with every value updated, and your code asks for nothing.
>
> **DO THIS:**
> ```jsx
> setTimeout(() => {
>   setPending(p => p - 1);
>   ~setCompleted~(c => c + 1); // One render: both counts change together
> }, 3000);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> setTimeout(() => {
>   ~setOrder~(o => ({ pending: o.pending - 1, completed: o.completed + 1 })); // **WRONG:** merged only to save a render React already saves
> }, 3000);
> ```

Here are the same two setters in two places. The first pair runs during a click. The second pair runs inside a `setTimeout`, one second after the timer starts, when no handler is running:

```jsx title="The same two setters in a click handler and in a setTimeout"
const [count, setCount] = useState(0);
const [flag, setFlag] = useState(false);

function handleClick() {
  ~setCount(c => c + 1);~ // Runs during the click
  setFlag(f => !f); // One render for both
}

~setTimeout~(() => { // Runs one second after the timer starts
  setCount(c => c + 1);
  setFlag(f => !f); // Since React 18: one render for both
}, 1000);
```

Since React 18, the two places behave the same. React renders once, after both setters.

### VS | React 17 vs. React 18: the same two setters in a setTimeout

It was not always so. The same `setTimeout` code gives a different number of renders in React 17 and in React 18:
- **In React 17,** React batched only the setters inside React event handlers, such as `onClick`. The two setters in the `setTimeout` gave two renders. React's blog wrote it in a comment: "React will render twice, once for each state update".
- **In React 18 and later,** the two setters give one render. The blog's comment for the new version: "React will only re-render once at the end".

```tree caption="The same two setters in a setTimeout, before and after React 18."
Two setters inside a `setTimeout`
- !React 17 | React batched **only inside React event handlers** | **Two renders**, one for each setter
- +React 18 and React 19 with `createRoot` | React batches **wherever the setters run** | **One render** after both setters
```

This is about more than speed. Without batching, React does extra work, and the render between the two setters shows one value updated and the other not yet.

### Every place where setters run together

React's blog lists the places that are batched since React 18: "updates inside of timeouts, promises, native event handlers or any other event are batched."

> [!DEFINITION]
> **A native event handler.** [NEW] A native event handler is a function the browser calls directly, because you attached it with `addEventListener`, as in plain JavaScript: `document.addEventListener('keydown', handleKey)`.
> It is not a JSX prop such as `onClick`, so React does not call it. The browser does.
> Before React 18, setters inside it were not batched. Since React 18, they are (Lesson 11).

Here are the four places, each with the same two setters:

```jsx title="Four places where two setters give one render since React 18"
<button ~onClick~={() => { setCount(c => c + 1); setFlag(f => !f); }}>Add</button> {/* A React event handler: one render */}

~setTimeout~(() => { setCount(c => c + 1); setFlag(f => !f); }, 1000); // A timeout: one render

fetch('/api/orders').~then~(() => { setCount(c => c + 1); setFlag(f => !f); }); // A promise: one render

document.~addEventListener~('keydown', () => { setCount(c => c + 1); setFlag(f => !f); }); // A native event handler: one render
```

There is one condition: the app must be mounted with `createRoot` (Lesson 07). In React 18, an app still mounted with the old `ReactDOM.render` kept the old behavior, and React printed this error in the Console:

```devconsole width=full caption="The Console of a React 18 app still mounted with ReactDOM.render."
x Warning: ReactDOM.render is no longer supported in React 18. Use createRoot instead. Until you switch to the new API, your app will behave as if it's running React 17. Learn more: https://reactjs.org/link/switch-to-createroot
```

React 19 removed `ReactDOM.render`, so every React 19 app uses `createRoot`, and every React 19 app gets automatic batching.

### Step 1: the order panel with a setTimeout

`main.jsx` mounts `App` with `createRoot`, inside `<StrictMode>`:

```jsx title="src/main.jsx"

import { createRoot } from 'react-dom/client';
import App from './App.jsx';

~createRoot~(document.getElementById('root')).render( // createRoot turns on automatic batching
  <StrictMode>
    <App />
  </StrictMode>

```

`App` renders the order panel:

```jsx title="src/App.jsx"
import OrderTracker from './OrderTracker.jsx';

export default function App() {
  return <OrderTracker />;
}
```

In `OrderTracker.jsx`, the `Buy` handler adds one order to `pending` at once. Then it starts a `setTimeout` of three seconds, which moves the order from `pending` to `completed`:

```jsx title="src/OrderTracker.jsx"
import { useState } from 'react';

export default function OrderTracker() {
  const [pending, setPending] = useState(0);
  const [completed, setCompleted] = useState(0);
  console.log('OrderTracker rendered', pending, completed);

  function handleClick() {
    setPending(p => p + 1); // The order is waiting
    ~setTimeout~(() => { // Runs three seconds after the click, when no handler is running
      setPending(p => p - 1); // One order less waiting
      setCompleted(c => c + 1); // One order more done, in the same render
    }, 3000);
  }

  return (
    <>
      <h3>Pending: {pending}</h3>
      <h3>Completed: {completed}</h3>
      <button onClick={handleClick}>Buy</button>
    </>
  );
}
```

Each setter gets an updater. Principle 3 shows what breaks without them.

The user opens the page and clicks `Buy` once. Here is the panel three seconds after the click, with every line the Console printed since the page opened:

```page width=text caption="The order panel three seconds after one click on Buy, with the Console lines of the page load, the click, and the timeout."
line: Pending: 0 | good
line: Completed: 1 | good
line: [Buy]
log: OrderTracker rendered 0 0 | OrderTracker.jsx:6
log: OrderTracker rendered 0 0 | OrderTracker.jsx:6
log: OrderTracker rendered 1 0 | OrderTracker.jsx:6
log: OrderTracker rendered 1 0 | OrderTracker.jsx:6
log: OrderTracker rendered 0 1 | OrderTracker.jsx:6
log: OrderTracker rendered 0 1 | OrderTracker.jsx:6
```

Every render prints two lines, because `<StrictMode>` calls each component twice in development (Lessons 14 and 47). So the panel rendered three times: when the page opened, after the click, and after the timeout. Right after `1 0` comes `0 1`, with no line in between. The two setters of the timeout gave one render.

**No handler is running when the timeout fires, and React still waits for both setters.** Here is what happens, in order:
1. The user clicks `Buy`. The handler calls `setPending(p => p + 1)` and starts the timer.
2. The handler ends, and React renders once: the screen shows `Pending: 1`.
3. Three seconds later, the browser runs the callback. It calls `setPending(p => p - 1)` and then `setCompleted(c => c + 1)`.
4. No React event handler is running. React still waits until the callback has finished, and then renders once.
5. `Pending: 0` and `Completed: 1` appear together.

### The real mistake: extra code to save renders that React already saves

A developer who learned React 17 believes that the two setters in the timeout render one by one. To save a render, they merge the two counts into one object:

**DO NOT DO THIS:**
```jsx bad="3"
const [order, setOrder] = useState({ pending: 0, completed: 0 });

~setOrder~(o => ({ pending: o.pending - 1, completed: o.completed + 1 })); // **WRONG:** merged only to save a render that React 18 already saves
```

**DO THIS:**
```jsx good="1,2"
setPending(p => p - 1);
~setCompleted~(c => c + 1); // The two setters already give one render
```

In React 18 and 19, the two setters already give one render, so the merged object saves nothing. The same holds for a debounce timer added only to save renders.

Careful: React's docs do advise merging two values that always change together, under "Group related state" (Lesson 22). But the reason there is the shape of the state, not the number of renders.

Batching also works across components. When one event calls setters in several components, React's docs say: "React batches updates from different components together, so there will only be one render pass."

## PRINCIPLE | await: the setters before it and the setters after it render separately

> [!PRINCIPLE]
> **Principle 2: The Wait Splits the Batch: await Splits the Buy Click into Two Renders**
>
> *In an async event handler, the setters before the first `await` form one batch and render when that part of the click ends; the setters after the `await` run later and form a second batch.*
>
> Batching groups the setters that run together. JavaScript runs the code up to the first `await` during the click and the rest later, so one click gives two renders. That first render is how the user sees the order waiting. If every setter sits after the `await`, the user clicks and sees nothing change for three seconds. Two separate clicks are never batched together either: each click gets its own render.
>
> **DO THIS:**
> ```jsx
> async function handleClick() {
>   ~setPending~(p => p + 1); // Batch 1: Pending: 1 shows at once
>   await delay(3000);
>   setPending(p => p - 1);
>   setCompleted(c => c + 1);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> async function handleClick() {
>   await delay(3000);
>   ~setPending~(p => p + 1); // **WRONG:** after the wait, in one batch with the next two lines: Pending: 1 never shows
>   setPending(p => p - 1);
>   setCompleted(c => c + 1);
> }
> ```

Most real code does not use a bare `setTimeout`. It uses `await`: wait for the server, then update the state. Here is a click handler with a wait in the middle:

```jsx title="One async handler, two batches"
async function handleClick() {
  setCount(c => c + 1); // Batch 1: renders when the click's code stops at await
  ~await~ delay(1000); // The click's code stops here; the rest runs one second later
  setCount(c => c + 1); // Batch 2: runs one second later
  setFlag(f => !f); // Same batch 2: one render for both
}

function delay(ms) {
  return new Promise(resolve => {
    setTimeout(resolve, ms);
  });
}
```

`delay` is a small helper from React's docs. It is a `setTimeout` wrapped in a promise, so you can write `await` in front of it. Inside `delay`, the new promise gets a `resolve` function, and the timer calls it after `ms` milliseconds. Calling `resolve` is what ends the wait. In a real app, the wait would be a request to the server with `fetch`.

**This one click gives two renders, not one.** The `await` cuts the handler into two pieces, and each piece is one batch.

Why? Because the code on the two sides of an `await` does not run together. JavaScript splits every async function at its `await` lines. MDN says the body of an async function "can be thought of as being split by zero or more await expressions", and that the code up to the first `await` "is run synchronously". Run synchronously means run right away, before anything else happens: here, during the click. So the click runs only the first piece. The rest runs later, when the promise resolves, as a new piece.

You may remember the waiter from Lesson 16, who listens until you finish your order and then walks to the kitchen once. If you say "I will order dessert in three seconds", the waiter takes what you ordered so far to the kitchen. Your dessert is a second trip.

```tree dir=right caption="How await splits one click handler into two batches and two renders."
One `Buy` click with a wait in the middle
- +Piece 1: the code up to `await` [`setPending`] | Runs **during the click** | React renders **once**: `Pending: 1`
- +The wait [`await` `delay`] | The handler **stops here** and returns a promise | The click's code is **finished for now**
- +Piece 2: the code after `await` [`setPending` `setCompleted`] | Runs **three seconds later**, both setters together | React renders **once**: `Pending: 0` and `Completed: 1`
```

### VS | A setTimeout callback vs. await delay: the same two batches

For batching, the `await` version and the `setTimeout` version of Principle 1 do the same job:

```jsx title="The same move of the order, written with a setTimeout and with await"
setTimeout(() => { setPending(p => p - 1); setCompleted(c => c + 1); }, 3000); // Principle 1: one render after the wait
~await delay(3000)~; setPending(p => p - 1); setCompleted(c => c + 1); // Principle 2: one render after the wait
```

In both, the setter before the wait runs during the click, and the two setters after it run three seconds later, as one piece. `await` is only a shorter way to write "run the rest later".

### Step 2: the Buy handler with await

In `OrderTracker.jsx`, `handleClick` takes the shape React's docs use for this panel:

```jsx title="src/OrderTracker.jsx" startLine="8"
  ~async~ function handleClick() { // async lets the handler wait with await
    setPending(p => p + 1); // Batch 1: Pending: 1
    ~await delay(3000)~; // The click's code stops here for three seconds
    setPending(p => p - 1); // Batch 2, three seconds later
    setCompleted(c => c + 1); // Same batch 2: one render for both counts
  }
```

The `delay` helper goes at the bottom of the file:

```jsx title="src/OrderTracker.jsx" startLine="24"
function delay(ms) {
  return new Promise(resolve => {
    setTimeout(resolve, ms);
  });
}
```

**One click, two renders: one before the wait, and one after it.** Here is what happens for one click on `Buy`:
1. The user clicks `Buy`. React calls `handleClick`.
2. `setPending(p => p + 1)` adds an update to React's queue.
3. `await delay(3000)` starts the wait. The handler stops here and returns a promise, so the click's code is finished for now.
4. React processes the queue and renders: the screen shows `Pending: 1`.
5. Three seconds later, the promise resolves, and the code after `await` runs.
6. `setPending(p => p - 1)` and `setCompleted(c => c + 1)` run together and form one batch.
7. React renders once: `Pending: 0` and `Completed: 1`.

React renders in the middle of the click, at step 4, because the click's code has stopped. React's docs say: "React waits until *all* code in the event handlers has run before processing your state updates." At the `await`, the handler has run all the code it can for now, so React does not wait for the rest.

The page and the Console look the same as in Principle 1: `OrderTracker rendered 1 0` twice after the click, and `OrderTracker rendered 0 1` twice after the wait.

This split is useful. It is what lets a loading line appear before the wait ends: a setter before `await` shows the line, and the setters after `await` hide it and show the result, in one render.

### Two fast clicks are two batches

What if the user clicks `Buy` twice, fast?

> [!DEFINITION]
> **An intentional event.** [NEW] An intentional event is an action the user means to do, such as a click or a key press.
> React's docs say: "React does not batch across *multiple* intentional events like clicks."
> So two clicks are two events, and each one gets its own render, no matter how fast they come (Lesson 75).

Each click is its own event, with its own render, and each click's wait ends in its own batch. Here is the panel three seconds after the second click, with the Console lines since the first click:

```page width=text caption="The order panel after two fast clicks on Buy, with one render per click and one render per finished wait."
line: Pending: 0 | good
line: Completed: 2 | good
line: [Buy]
log: OrderTracker rendered 1 0 | OrderTracker.jsx:6
log: OrderTracker rendered 1 0 | OrderTracker.jsx:6
log: OrderTracker rendered 2 0 | OrderTracker.jsx:6
log: OrderTracker rendered 2 0 | OrderTracker.jsx:6
log: OrderTracker rendered 1 1 | OrderTracker.jsx:6
log: OrderTracker rendered 1 1 | OrderTracker.jsx:6
log: OrderTracker rendered 0 2 | OrderTracker.jsx:6
log: OrderTracker rendered 0 2 | OrderTracker.jsx:6
```

Each click and each finished wait gave its own render:
1. The first click shows `Pending: 1`.
2. The second click shows `Pending: 2`.
3. Three seconds after the first click, its batch moves one order: `Pending: 1` and `Completed: 1`.
4. Three seconds after the second click, its batch moves the other order: `Pending: 0` and `Completed: 2`.

React keeps clicks apart on purpose. The docs say: "React only does batching when it's generally safe to do. This ensures that, for example, if the first button click disables a form, the second click would not submit it again."

## PRINCIPLE | An updater after await: React passes the latest state, not the value from the click

> [!PRINCIPLE]
> **Principle 3: Snapshot After the Wait: pending - 1 After await Shows Pending: -1**
>
> *Code after `await` still reads the values of the click's render; when the next value depends on the previous one, pass an updater, which React calls with the latest state.*
>
> Batching decides when React renders. It does not change what `pending` holds inside the handler. Three seconds later, `pending` is still the value from the click's render, so `pending - 1` computes from an old number. An updater such as `p => p - 1` receives the latest state from React.
>
> **DO THIS:**
> ```jsx
> await delay(3000);
> setPending(~p => p - 1~); // React passes the latest pending: Pending: 0
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> await delay(3000);
> setPending(~pending - 1~); // **WRONG:** pending is 0 from the click's render, so the screen shows Pending: -1
> ```

React's docs first show the `Buy` handler without updaters:

```jsx title="The Buy handler without updaters"
setPending(pending + 1);
await delay(3000);
~setPending(pending - 1)~; // **WRONG:** pending still holds the value from the click's render
setCompleted(completed + 1);
```

**The screen ends on `Pending: -1`, a count that should be impossible.** The docs describe it: "When you press 'Buy', it decreases to `-1`", and "if you click fast twice, both counters seem to behave unpredictably."

Here is the trap. Batching decides when React renders. It does not change what `pending` holds inside this handler.

> [!DEFINITION]
> **A snapshot.** [REVIEW] Every render has its own values of state. The handler created in that render reads those values, and they never change inside it, even in code that runs much later.
> After `setCount(5)`, the variable `count` still holds the old value until the next render (Lesson 15).

Most readers think that three seconds later, `pending` holds the new number on the screen. It does not. The screen shows a newer render, but the handler still reads the render of its own click, where `pending` is `0`.

Here is what happens:
1. The screen shows `Pending: 0`. The user clicks `Buy`.
2. `setPending(pending + 1)` asks for `0 + 1`. React renders `Pending: 1`.
3. The handler waits three seconds. In the render of its click, `pending` is still `0`.
4. `setPending(pending - 1)` asks for `0 - 1`, and `setCompleted(completed + 1)` asks for `0 + 1`.
5. React batches the two and renders once.
6. The screen shows `Pending: -1` and `Completed: 1`.

```page width=text caption="The order panel three seconds after one click on Buy, when the handler computes pending - 1 from the click's value."
line: Pending: -1 | bad
line: Completed: 1
line: [Buy]
log: OrderTracker rendered 1 0 | OrderTracker.jsx:6
log: OrderTracker rendered 1 0 | OrderTracker.jsx:6
log: OrderTracker rendered -1 1 | OrderTracker.jsx:6
log: OrderTracker rendered -1 1 | OrderTracker.jsx:6
```

The Console shows only our own lines, with no error and no warning. Our own code computed `0 - 1` from the click's value, and React only applied it.

Two fast clicks break the counts in another way:
1. The first click runs in the render where `pending` is `0`. It asks for `0 + 1`, and the screen shows `Pending: 1`.
2. The second click runs in the render where `pending` is `1`. It asks for `1 + 1`, and the screen shows `Pending: 2`.
3. Three seconds after the first click, its handler asks for `0 - 1` and `0 + 1`: `Pending: -1` and `Completed: 1`.
4. Three seconds after the second click, its handler asks for `1 - 1` and `0 + 1`: `Pending: 0` and `Completed: 1`.

The user bought two orders, and the panel counts one.

### VS | pending - 1 vs. p => p - 1 after await: the old value or the latest one

```jsx title="A value computed from the click's render vs. an updater, both after await"
setPending(~pending - 1~); // Computes from the click's render: 0 - 1 gives -1
setPending(~p => p - 1~); // React passes the latest state: 1 - 1 gives 0
```

The two lines look alike, but they read different values. React's docs explain it: "the values of `pending` and `completed` correspond to what they were at the time of the click event". The updater works "in relation to its *latest* state rather than what the state was at the time of the click." React calls `p => p - 1` with the latest `pending`, after every update queued before it (Lesson 16).

```tree caption="A value computed from the click's render vs. an updater that React calls with the latest state."
Changing `pending` three seconds after the click
- !A computed value [`pending - 1`] | Reads `pending` from **the click's render**, where it is **0** | The screen shows **`Pending: -1`**
- +An updater [`p => p - 1`] | React passes **the latest state**, which is **1** | The screen shows **`Pending: 0`**
```

The fix in the docs uses an updater for both counts:

```jsx title="src/OrderTracker.jsx" startLine="8"
  async function handleClick() {
    setPending(~p => p + 1~); // React passes 0: Pending: 1
    await delay(3000);
    setPending(~p => p - 1~); // React passes the latest pending: Pending: 0
    setCompleted(~c => c + 1~); // React passes the latest completed: Completed: 1
  }
```

This is the version of Principle 2. The docs name the parameter after the first letter of the state: `p` for `pending`, and `c` for `completed`. Updaters run during the next render, so they must be pure. Under `<StrictMode>`, React calls each one twice and keeps one result (Lesson 16).

Remember: after `await`, read the latest state through an updater, never through the variable.

## PRINCIPLE | flushSync: each call renders at once, so React renders a half-finished state

> [!PRINCIPLE]
> **Principle 4: The Way Out: flushSync Shows the Half-Finished Render**
>
> *To opt out of automatic batching, wrap a setter in `flushSync`; each `flushSync` renders its own update at once, so two setters in two `flushSync` calls give two renders, and the first shows only one of the two changes.*
>
> Batching is the default, and `flushSync` is the exception. It forces a render before the next line runs, so the render between the two calls is a half-finished render: the order sits in neither count. Use it only when outside code must see the DOM at once.
>
> **DO THIS:**
> ```jsx
> await delay(3000);
> setPending(p => p - 1);
> ~setCompleted~(c => c + 1); // One batch: the order moves in one step
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> await delay(3000);
> ~flushSync~(() => { setPending(p => p - 1); }); // **WRONG:** renders 0 0 before the next line, a half-finished render
> flushSync(() => { setCompleted(c => c + 1); });
> ```

React gives one way out of batching: `flushSync`, a named import from `react-dom` (Lesson 65). The React 18 upgrade guide says: "To opt-out of automatic batching, you can use `flushSync`". To opt out means to choose not to take part: the updates inside `flushSync` are not batched with the others.

> [!DEFINITION]
> **flushSync.** [REVIEW] `flushSync` takes a function, runs the setters inside it, and makes React render and update the DOM right away, before the next line of your code runs.
> React's docs: it forces "React to flush any updates inside the provided callback synchronously". To flush means to process the waiting updates now, instead of later (Lesson 65).

Here is the guide's example, with the names `count` and `flag` from Principle 1:

```jsx title="Two setters, each inside its own flushSync"
import { flushSync } from 'react-dom';

~flushSync~(() => { // React renders and updates the DOM before the next line
  setCount(c => c + 1);
});
flushSync(() => {
  setFlag(f => !f); // React renders and updates the DOM again
});
```

So these two setters give two renders, as two setters in a timeout did before React 18.

### VS | Two plain setters vs. each setter in its own flushSync: one render or two

After the wait in our `Buy` handler, compare the two plain setters with the same setters inside `flushSync`:

```jsx title="Two plain setters vs. each setter inside its own flushSync"
setPending(p => p - 1); setCompleted(c => c + 1); // One batch: one render with 0 1
~flushSync~(() => { setPending(p => p - 1); }); flushSync(() => { setCompleted(c => c + 1); }); // Two renders: 0 0, then 0 1
```

The plain setters form one batch and one render. With `flushSync`, React renders the first update before the second setter even runs. In that first render, the order is in neither count.

> [!DEFINITION]
> **A half-finished render.** [NEW] A half-finished render is a render where only some of the values that belong together have changed.
> React's docs: a render "where only some of the variables have been updated".
> In our panel, it is the render with `Pending: 0` and `Completed: 0`: the order has left one count and has not reached the other. Batching is what prevents it (Lesson 75).

### Step 3: the half-finished render in the Console

To see it, `OrderTracker.jsx` imports `flushSync` and wraps each setter after the wait in its own call. The import adds one line at the top, so the `console.log` moves to line 7:

```jsx title="src/OrderTracker.jsx" startLine="1"
import { useState } from 'react';
import { ~flushSync~ } from 'react-dom'; // From react-dom, not from react
```

```jsx title="src/OrderTracker.jsx" startLine="9"
  async function handleClick() {
    setPending(p => p + 1);
    await delay(3000);
    ~flushSync~(() => { // Opts this setter out of batching
      setPending(p => p - 1); // React renders and updates the DOM now: 0 0
    });
    flushSync(() => {
      setCompleted(c => c + 1); // React renders and updates the DOM again: 0 1
    });
  }
```

**After the wait, the Console shows a render with `0 0`: for that render, the order is counted nowhere.** Here are the panel and the Console lines after one click on `Buy`:

```page width=text caption="The order panel three seconds after one click on Buy, when each setter after the wait sits in its own flushSync; the Console shows the half-finished render with 0 0."
line: Pending: 0
line: Completed: 1
line: [Buy]
log: OrderTracker rendered 1 0 | OrderTracker.jsx:7
log: OrderTracker rendered 1 0 | OrderTracker.jsx:7
log: OrderTracker rendered 0 0 | OrderTracker.jsx:7
log: OrderTracker rendered 0 0 | OrderTracker.jsx:7
log: OrderTracker rendered 0 1 | OrderTracker.jsx:7
log: OrderTracker rendered 0 1 | OrderTracker.jsx:7
```

Here is what happens after the wait:
1. The first `flushSync` runs `setPending(p => p - 1)`, and React renders and updates the DOM at once.
2. In that render, `pending` is `0` and `completed` is still `0`. The DOM now holds `Pending: 0` and `Completed: 0`.
3. The second `flushSync` runs `setCompleted(c => c + 1)`, and React renders and updates the DOM again: `0` and `1`.

The user may never see `Pending: 0` next to `Completed: 0` on the screen, because both calls run in the same piece of code, and the browser may paint only after the second one. But React did render that state and put it in the DOM. Any code that ran between the two calls would read the half-finished page.

Now we remove `flushSync` again and keep the plain setters of Principle 3.

### The real mistake: flushSync to show the change right now

A developer wants the new count on the screen right now, and wraps setters in `flushSync` in ordinary code. Every call adds a render, and the page can pass through half-finished renders. React's docs warn: "Most of the time, `flushSync` can be avoided. Use `flushSync` as last resort." And: "`flushSync` can significantly hurt performance."

`flushSync` is right only when browser code or a library must see the DOM by the end of its callback (Lesson 65). One example is the `onbeforeprint` event, which fires just before the print dialog opens. The docs explain that case with batching too: without `flushSync`, "React batches the updates asynchronously and the print dialog is displayed before the state is updated."

Remember: batching is the default, and `flushSync` is the last resort.

## All 4 Principles Together

### The complete code

`main.jsx` mounts the app with `createRoot`, which turns on automatic batching:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

~createRoot~(document.getElementById('root')).render( // Principle 1: automatic batching needs createRoot
  <StrictMode>
    <App />
  </StrictMode>
);
```

`App` renders the order panel:

```jsx title="src/App.jsx"
import OrderTracker from './OrderTracker.jsx';

export default function App() {
  return <OrderTracker />;
}
```

`OrderTracker` waits with `await`, uses updaters, and has no `flushSync`:

```jsx title="src/OrderTracker.jsx"
import { useState } from 'react';

export default function OrderTracker() {
  const [pending, setPending] = useState(0);
  const [completed, setCompleted] = useState(0);
  console.log('OrderTracker rendered', pending, completed);

  async function handleClick() {
    setPending(p => p + 1); // Principle 2: batch 1 renders Pending: 1
    ~await~ delay(3000); // Principle 2: the wait starts a new batch
    setPending(~p => p - 1~); // Principle 3: the updater reads the latest pending
    setCompleted(c => c + 1); // Principles 1 and 4: one render for both counts, no flushSync
  }

  return (
    <>
      <h3>Pending: {pending}</h3>
      <h3>Completed: {completed}</h3>
      <button onClick={handleClick}>Buy</button>
    </>
  );
}

function delay(ms) {
  return new Promise(resolve => {
    setTimeout(resolve, ms);
  });
}
```

### When React calls the components

When the page opens, React calls `App`, and then `OrderTracker`. After that, only `OrderTracker` holds state, so each click and each finished wait calls only `OrderTracker`, once per batch:

```tree dir=right caption="When React calls the components of the order panel for one click on Buy, and what each render logs."
The renders of the order panel
- +1. The page opens [`createRoot`] | React calls **`App`**, then **`OrderTracker`** | Logs **`0 0`**
- +2. The click, up to `await` [`setPending`] | Batch 1: React calls **`OrderTracker`** once | Logs **`1 0`**: `Pending: 1`
- +3. Three seconds later, after `await` [`setPending` `setCompleted`] | Batch 2: both setters, **one render** | Logs **`0 1`**: `Pending: 0` and `Completed: 1`
```

| Aspect | What readers expect | What React does |
| :--- | :--- | :--- |
| **Setters in a timeout or a promise** | One render for each setter, as in React 17 | One render for the setters that run together, since React 18 with `createRoot` |
| **An async handler with `await`** | One click, one render | One batch before the wait and one batch after it: two renders |
| **Two fast clicks** | React groups them to save work | Each click is its own event with its own render |
| **`pending - 1` after `await`** | `pending` holds the number on the screen | `pending` holds the click's value; an updater gets the latest state |
| **`flushSync`** | A way to show the change faster | A way out of batching that adds a render; a last resort |

Remember the one sentence of this lesson. **React renders once for the setters that run together, wherever they run, and every `await` and every new click starts a new batch.**

## For the Interview

> **The Interview Question:** How does automatic batching coordinate state updates across promises and timeouts?

### How to Answer Clearly in 30 Seconds

"Batching means React waits until a piece of code has run, then processes all the state updates it queued in one render. Before React 18, React batched only inside React event handlers, so two setters in a `setTimeout` or a promise rendered twice. Since React 18 with `createRoot`, automatic batching groups updates 'no matter where they originate from': timeouts, promises, native event handlers, any other event. That means less rendering work, and no 'half-finished' render where only some values have changed. There are two boundaries:
1. **An `await` splits a handler:** the setters before it form one batch and the setters after it form another, so one click can give two renders.
2. **Separate clicks are never batched together:** each intentional event gets its own render.

Code after `await` still reads the click's render, so I use updaters such as `p => p - 1` there. To opt out, `flushSync` from `react-dom` renders its updates at once, but it is a last resort."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does automatic batching work in every React app?"**
   It needs `createRoot`. In React 18, an app mounted with the old `ReactDOM.render` behaved as if it ran React 17, and React printed a message that `ReactDOM.render` was no longer supported. React 19 removed `ReactDOM.render`, so every React 19 app gets automatic batching. The upgrade guide called the change "a breaking change, but we expect this to result in less work rendering, and therefore better performance in your applications."
2. **"Why does my async click handler render twice?"**
   Because the `await` splits it. JavaScript runs the code up to the first `await` during the click, and React renders those setters when the click's code stops. The code after the `await` runs later, and its setters form a second batch. This split is useful: a loading line set before the wait appears at once, and the setters after the wait hide it and show the result in one render. Inside a Transition, the setters after `await` need their own `startTransition` (Lesson 67).
3. **"Are there other places where React batches updates?"**
   Yes, there are three more:
   - **Transitions and Actions.** React's docs say: "If there are multiple ongoing Transitions, React currently batches them together. This is a limitation that may be removed in a future release." The same holds for ongoing Actions in `useActionState` (Lesson 42).
   - **Animations.** A `<ViewTransition>` batches the updates that arrive while an animation runs: they "will all be batched into one" (Lesson 74).
   - **Server rendering.** React 19.2 batches the reveal of server-rendered Suspense boundaries for a short time.

   To see batching in a real app, open the Profiler: it shows one commit for a batch, and two for the `flushSync` version (Lesson 64).

```tree caption="Interview summary: where automatic batching applies, and where a new batch starts."
Automatic batching since React 18 with `createRoot`
- +Batched together | Setters that run together in a **click handler**, a **timeout**, a **promise**, or a **native event handler** | **One render**, no half-finished render
- !A new batch starts | At every **`await`**, and at every **new click** | **One render per batch**
- !Opted out | Each **`flushSync`** call | **One render per call**, a last resort
```
