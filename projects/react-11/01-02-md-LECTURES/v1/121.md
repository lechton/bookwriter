# Lecture 121: How a Page Puts Its Own Title, Meta Tags, and Links into the Head

*(How does one blog post put its own title and description into the head of the page?)*

> INTERVIEW QUESTION | ❱ CORE | How do you set titles, meta tags, and links with React components?

---

## VS | `<title>` in `App` vs. `<title>` in `PostPage`: both land in the head, only `PostPage` knows the post

> The browser tab, a search result, and the preview of a shared link all read the title and the description from the `<head>` of the page. **In React 19, any component can render the title, meta, and link tags next to its other JSX, and React places them in the `<head>`**. So the component that knows the data writes the title, and React puts it into the HTML the server sends.

Remember plain HTML? Every page is its own file, and you write its title at the top, inside `<head>`. In React, one component, usually `App`, renders the whole document for every page of the site, head included. So `App` can write only one title for all the pages, such as `My Blog`. **In React 19, the title no longer has to be written inside the head**. The page component renders `<title>` right next to its heading, and React moves it into the `<head>` for you.

Take a blog with a post called New Park Opens. A reader pastes the link of the post into a chat with a friend. Under the link, the chat app shows a preview: a title and a short description. Here the preview says `My Blog`, with no description, and the browser tab says `My Blog` too. Every other post of the blog gets the same preview.

Ask yourself: the title of the post lives in the post data, and only `PostPage` reads that data. So how does it get into the `<head>`, which `App` writes? `PostPage` renders the `<title>` itself, and React places it in the head.

::: row caption="The preview of the shared link in a chat app: with the title written in App, and with the title written in PostPage."
::: col title="The title written in App" tag="the same for every post" tone=bad
```page size=mini
url: example.com/posts/new-park
card: title=My Blog | author=example.com | missing=No description | tone=bad
```
:::
::: col title="The title written in PostPage" tag="its own title" tone=good
```page size=mini
url: example.com/posts/new-park
card: title=New Park Opens | author=example.com | text=The park opens at noon. | tone=good
```

**Why:** A chat app does not open the post in a browser. It fetches the HTML the server sends, reads the `<head>`, and runs no JavaScript. MDN says it plainly: search engines can run JavaScript, "but social media crawlers usually cannot". So a title that appears in the tab only after the page loads is too late. The title must already be in the HTML that comes from the server, and in React 19 the server puts it there.

### The Same Title, in Plain HTML and in React 19

In plain HTML, the title sits in the head of each page file:

```html title="Plain HTML: each page file writes its own title in its head"
<head>
  <title>New Park Opens</title>
</head>
```

In React 19, the page component writes it next to its heading, from its own data:

```jsx title="PostPage renders the title and the description of its own post"
function PostPage({ post }) {
  return (
    <article>
      ~<title>{post.title}</title>~ {/* React places it in the head */}
      ~<meta name="description" content={post.summary} />~ {/* React places it in the head too */}
      <h1>{post.title}</h1> {/* Stays inside the article, on the page */}
    </article>
  );
}
```

Look at the two tags that read `post.title`. Both sit inside the `<article>`. The `<h1>` stays there, on the page. The `<title>` does not: React places it in the head, wherever it sits in the tree (as seen in Lesson 83). React does this in the browser, and it also does it on the server. So the title is already in the HTML the server sends.

> [!DEFINITION]
> **Hoisting.** [REVIEW] When React meets a `<title>`, a `<meta>`, or a `<link>` while it renders a component, it does not leave the tag where you wrote it. It places the tag in the `<head>` of the document, and React's docs call this move hoisting. React leaves a `<title>` or a `<meta>` where it is written only when it sits inside an `<svg>` or has an `itemProp` prop (Lesson 83).

So a title written in `App` and a title written in `PostPage` end up in the same place, the head. The one difference is which component knows the post. `App` renders the document of every page, so it can only write one title for all of them. `PostPage` shows one post, so it can write the title of that post.

```tree caption="A title written in App and a title written in PostPage both end up in the head; only PostPage knows which post is on the page."
Two places to write the title of a page
- !In `App`, inside its `<head>` [`<title>My Blog</title>`] | `App` does **not know which post** is on the page | Every post gets **the same title**
- +In `PostPage`, next to its heading [`<title>{post.title}</title>`] | `PostPage` **knows the post** it shows | React places it **in the head**, and each post gets **its own title**
```

### What People See Before They Open a Post

The chat preview, the search result, and the browser tab all read the head of the page. MDN says that the description "is also used on search engine result pages". It also says that a shared link can appear "along with an image and description". When the head says `My Blog` on every post, every shared link, every search result, and every tab of the blog look the same. The friend in the chat cannot tell one post from another before opening it.

### Metadata, and Three Ways to Set It

> [!DEFINITION]
> **Metadata.** [NEW] Metadata is information about the page, not content shown on the page. The title in the tab, the description under a search result, and the main address of the page are all metadata. They live in the `<head>`, written as title, meta, and link tags, and the reader never sees them inside the page itself (Lesson 121).

Developers set the metadata of a page in one of three ways:

```tree caption="The three ways to set the metadata of a page, and when each one fits."
Three ways to set a page's title, meta tags, and links
- +Render `<title>`, `<meta>`, and `<link>` in the page component | New in **React 19** | Works in the browser, with **server rendering**, and with **Server Components** | **This lesson**
- !Set `document.title` in an Effect | The way **before React 19** | Changes **only the tab**, and only **in the browser**
- +A metadata library, such as `react-helmet` | Or the metadata feature of a framework | Fits when every route must **replace a site-wide default**
```

The React 19 announcement says that the first way works "with client-only apps, streaming SSR, and Server Components". A library or a framework is still useful in one case: when every page should fall back to the site title unless it sets its own. Principle 3 shows it.

### The Rule of Thumb: the component that knows the data writes the title

**The component that knows the data renders the title, meta, and link tags. React places them in the head, also in the HTML the server sends.**

A senior developer also knows the three classic mistakes:
1. **The title in an Effect.** Setting `document.title` in an Effect fixes the tab in your own browser. The HTML the server sends still says `My Blog`, so the chat preview still says `My Blog`.
2. **Two titles.** You add the title of the post to `PostPage`. The old title, `<title>My Blog</title>`, stays in `App`. The head then holds two titles, and no rule says which one is used.
3. **A title in two pieces.** Writing the post title and the site name side by side inside `<title>` gives it two children. A `<title>` accepts one string only, so the title comes out empty (as seen in Lesson 83).

The rest of the lesson shows each one on a real blog post.

## SECTION | The New Park Opens Blog Post

We build one post of the blog, New Park Opens, rendered on the server. The server file and the browser file are the ones of Lesson 118. When the post opens, the reader sees a heading and one line:

```page caption="What the reader sees when the post opens: the heading and one line."
url: example.com/posts/new-park
heading: New Park Opens
line: The park opens at noon.
```

The page is built from five files:

```files title="blog: File Explorer" caption="The five files of the blog post and the job of each one."
server.js | Node.js server | Streams `App` with `renderToPipeableStream`, as in Lesson 118
src/
  post.js | data | Exports `post` with its title and its summary
  PostPage.jsx | page | Renders the post: the heading and the summary line
  App.jsx | document | Renders `<html>`, the `<head>`, and `<PostPage />` inside `<body>`
  main.jsx | browser | Calls `hydrateRoot` on the whole document
```

The post is one object:

```jsx title="src/post.js"
export const post = {
  ~title: 'New Park Opens'~, // Shown in the heading, and needed in the head
  summary: 'The park opens at noon.',
};
```

At the start of the lesson, `App` renders the whole document, as in Lesson 118, with one title for the whole blog:

```jsx title="src/App.jsx"
import PostPage from './PostPage.jsx';

export default function App({ post }) {
  return (
    <html>
      <head>
        <meta charSet="utf-8" />
        ~<title>My Blog</title>~ {/* The same title for every post */}
      </head>
      <body>
        <PostPage post={post} />
      </body>
    </html>
  );
}
```

`PostPage` renders only the heading and the line:

```jsx title="src/PostPage.jsx"
export default function PostPage({ post }) {
  return (
    <article>
      ~<h1>{post.title}</h1>~ {/* New Park Opens, on the page only */}
      <p>{post.summary}</p>
    </article>
  );
}
```

The title the head needs is already on the screen, in the heading. The whole lesson is about getting that same `post.title` into the head as well.

**PRINCIPLES:** The component that knows the data renders the metadata, and React places it in the head. Three principles follow:
1. **The title, meta, and link tags in `PostPage`: React places them in the head of the HTML the server sends.** `PostPage` renders them from its own `post`, next to its heading.
2. **`document.title` in an Effect: only the tab changes, and the HTML the server sends keeps `My Blog`.** An Effect runs only in the browser, after the page has arrived.
3. **Two `<title>` tags: React places both in the head, so only one component renders the title.** No rule says which of the two titles browsers and search engines use.

## PRINCIPLE | `<title>` and `<meta>` in `PostPage`: React places them in the head of the HTML the server sends

> [!PRINCIPLE]
> **Principle 1: Hoisting: `PostPage` Puts Its Own `<title>` and `<meta>` into the Head**
>
> *Render `<title>`, `<meta>`, and `<link>` in the component that knows the data; React places them in the document head, in the browser and in the HTML the server sends.*
>
> `App` writes the head, but only `PostPage` knows the post. So `PostPage` renders the title, the description, the Open Graph tags, and the canonical link next to its heading, from its own `post`. React writes them into the head of the HTML the server sends, which is the HTML that chat apps and search engines read. React leaves a `<title>` or a `<meta>` where it is written only when it sits inside an `<svg>` or has an `itemProp` prop.
>
> **DO THIS:**
> ```jsx
> function PostPage({ post }) {
>   return (
>     <article>
>       ~<title>{post.title}</title>~ {/* React places it in the head */}
>       <h1>{post.title}</h1>
>     </article>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function App() {
>   return (
>     <head>
>       ~<title>My Blog</title>~ {/* **WRONG:** every post gets the same title in the head */}
>     </head>
>   );
> }
> ```

We add the `<title>` and the description to `PostPage`, as in the code at the start of the lesson. The page in the browser does not change: it still shows the heading and the line. So where did the two tags go?

### What the Server Sends

To see it, open the page source of the post. The page source is the HTML exactly as the browser received it from the server (as seen in Lesson 102). It is also exactly what a chat app reads. React writes it all on one line. Here it is split into one tag per line, so we can read it:

```html title="The page source of the post, one tag per line" good="7,8"
<!DOCTYPE html>
<html>
<head>
<meta charSet="utf-8"/>
<link rel="preload" as="script" fetchPriority="low" href="/main.js"/>
<title>My Blog</title>
<title>New Park Opens</title>
<meta name="description" content="The park opens at noon."/>
</head>
<body>
<article><h1>New Park Opens</h1><p>The park opens at noon.</p></article>
<script src="/main.js" id="_R_" async=""></script>
</body>
</html>
```

**The title and the description that `PostPage` wrote inside its article now sit in the head. The article holds only the heading and the line.** `App` wrote nothing for them in its head. Here is how they got there:
1. The server file renders `<App post={post} />`.
2. `App` renders the head, then the body with `<PostPage post={post} />` inside it.
3. `PostPage` returns the title tag and the meta tag inside its `<article>`.
4. React sees a title tag and a meta tag that are not inside an `<svg>` and have no `itemProp`.
5. So React writes them into the head of the HTML, and not into the article.

The React 19 announcement says that React will "automatically hoist" these tags "to the `<head>` section of document". The new fact of this lesson is that the server does it too, before any JavaScript runs in the browser.

The old `<title>My Blog</title>` from `App` is still in the head, right above the new one. Principle 3 shows what two titles do, and removes the old one.

```tree dir=right caption="How the title written inside PostPage reaches the head of the HTML the server sends."
How `<title>{post.title}</title>` reaches the page source
- +1. Our code [`<title>` inside `<article>`] | `PostPage` returns the title **next to the heading**
- +2. React on the server [`<head>`] | React sees a **metadata tag** | Writes it **into the head** of the HTML
- +3. The page source | The article holds **only the heading and the line** | The head holds **`New Park Opens`**
```

### The Description, the Open Graph Tags, and the Canonical Link

The chat preview needs more than a title. It reads a few more tags that describe the page. Each one is a plain HTML tag, and `PostPage` renders each one the same way it renders the `<title>`:
1. **The description.** `<meta name="description" content={post.summary} />` holds a short summary of the page. The `name` says what kind of information the tag holds, here the description. The `content` holds the text itself. A search engine can show it under the title of a result.
2. **The Open Graph tags.** MDN describes Open Graph as "a metadata protocol that Facebook invented to provide richer metadata for websites". Chat apps and social networks read these tags to build the preview of a shared link. An Open Graph tag is also a `<meta>`, but it names its kind with `property`. For example, `property="og:title"` holds the title of the preview, and `property="og:description"` holds its description.
3. **The canonical link.** `<link rel="canonical" href={post.url} />` names the main address of the page. The same post can often be reached at more than one address, and the canonical link tells search engines which one is the real one. React's docs list it among the "links to related resources such as an icon, canonical URL, or pingback".

The canonical link needs the address of the post, so the post object gains a `url`:

```jsx title="src/post.js"
export const post = {
  title: 'New Park Opens',
  summary: 'The park opens at noon.',
  ~url: 'https://example.com/posts/new-park'~, // The main address of the post
};
```

`PostPage` renders all five tags at the top of its `<article>`:

```jsx title="src/PostPage.jsx" good="4,5,6,7,8"
export default function PostPage({ post }) {
  return (
    <article>
      <title>{post.title}</title>
      <meta name="description" content={post.summary} />
      ~<meta property="og:title" content={post.title} />~ {/* Read by the chat app for the preview */}
      <meta property="og:description" content={post.summary} />
      ~<link rel="canonical" href={post.url} />~ {/* The main address of the post */}
      <h1>{post.title}</h1>
      <p>{post.summary}</p>
    </article>
  );
}
```

The page in the browser does not change: it still shows the heading and the line. All five tags sit in the head of the page source, in the order `PostPage` wrote them, as the page source in Principle 3 shows.

```tree caption="The three kinds of metadata PostPage renders, and who reads each one."
What `PostPage` renders into the head
- +`<title>` and the description [`<title>` `<meta name="description">`] | The **tab** and the **search result** read them | Hold **`New Park Opens`** and **`The park opens at noon.`**
- +The Open Graph tags [`<meta property="og:title">` `<meta property="og:description">`] | **Chat apps** and **social networks** read them | Build the **preview of a shared link**
- +The canonical link [`<link rel="canonical">`] | **Search engines** read it | Names **the main address** of the post
```

### Why a Canonical Link Does Not Wait Like a Stylesheet

You already know another `<link>` that goes to the head: the stylesheet link with `precedence` (as seen in Lesson 83). It is easy to think the canonical link gets the same treatment. It may look the same, but it is NOT the same thing! A stylesheet link makes the component wait while the stylesheet loads, and React keeps one copy of it for each `href`. A canonical link loads nothing, so React only places it in the head.

Remember: the component that knows the data writes the tags, and React carries them to the head.

## PRINCIPLE | `document.title` in an Effect: only the tab changes, and the HTML the server sends keeps `My Blog`

> [!PRINCIPLE]
> **Principle 2: Server HTML: `document.title` in an Effect Never Reaches the Page Source**
>
> *Render `<title>` in the JSX instead of setting `document.title` in an Effect, so the title is in the HTML the server sends.*
>
> Effects run only in the browser, after the page has arrived. The developer's tab shows the right title, but the HTML the server sends still holds the old one, and a chat app builds its preview from that HTML. The Effect also writes no description and no Open Graph tag. A `<title>` rendered in the JSX is in the head of the server HTML from the start.
>
> **DO THIS:**
> ```jsx
> function PostPage({ post }) {
>   return <article>~<title>{post.title}</title>~<h1>{post.title}</h1></article>; // In the head of the server HTML
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function PostPage({ post }) {
>   useEffect(() => {
>     ~document.title = post.title;~ // **WRONG:** the server HTML keeps the old title
>   }, [post.title]);
>   return <article><h1>{post.title}</h1></article>;
> }
> ```

In plain JavaScript, you change the title of the tab with one line: `document.title = 'New Park Opens'`. Before React 19, React did not move a `<title>` into the head, so teams wrote that line in an Effect. The React 19 announcement says that in the past, "these elements would need to be inserted manually in an effect". Here are the two ways side by side, the old one and the one of Principle 1:

```jsx title="With document.title in an Effect"
useEffect(() => {
  ~document.title = post.title;~ // Runs in the browser, after the page has arrived
}, [post.title]);
```

```jsx title="With <title> in the returned JSX"
<title>~{post.title}~</title> {/* Rendered on the server too, into the head */}
```

After the page loads, both tabs read `New Park Opens`. It may look the same, but it is NOT the same thing! React's docs say: "Effects only run on the client. They don't run during server rendering." So the Effect changes the tab only after the page has reached the browser. The `<title>` is in the head of the HTML the server sends from the start.

### The Tab Says New Park Opens, and the Page Source Says My Blog

**Beware! With the Effect, the developer's own tab shows the right title, but the HTML the server sends still says `My Blog`. That HTML is all a chat app reads.**

Here is `PostPage` with the Effect in place of the metadata tags:

```jsx title="src/PostPage.jsx" bad="5"
import { useEffect } from 'react';

export default function PostPage({ post }) {
  useEffect(() => {
    ~document.title = post.title;~ // **WRONG:** runs only in the browser, never on the server
  }, [post.title]);

  return (
    <article>
      <h1>{post.title}</h1>
      <p>{post.summary}</p>
    </article>
  );
}
```

Here is what happens, in order:
1. The developer opens the post. The tab reads `New Park Opens`, so the title looks done.
2. The developer opens the page source. The head still holds only `<title>My Blog</title>`, the one `App` writes.
3. The reason: the server file rendered `App` to HTML, and React does not run Effects during server rendering.
4. In the browser, the HTML loads the bundle `/main.js`. Then `hydrateRoot` attaches React to the page.
5. Only then does the Effect run and change `document.title`.
6. A chat app that reads the link gets the HTML of step 2, and it does not run the bundle. Its preview says `My Blog`.

```html title="The page source with the Effect: only the title of App" bad="6"
<!DOCTYPE html>
<html>
<head>
<meta charSet="utf-8"/>
<link rel="preload" as="script" fetchPriority="low" href="/main.js"/>
<title>My Blog</title>
</head>
<body>
<article><h1>New Park Opens</h1><p>The park opens at noon.</p></article>
<script src="/main.js" id="_R_" async=""></script>
</body>
</html>
```

The Effect also sets only the text of the tab. It writes no description and no Open Graph tag, so the preview has no description either.

The browser file is the one of Lesson 118, and the Effect can run only after it:

```jsx title="src/main.jsx"
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';
import { post } from './post.js';

~hydrateRoot(document, <App post={post} />)~; // React attaches in the browser; only now do Effects run
```

```tree dir=right caption="With an Effect, the title changes only in the browser, after the HTML that the chat app reads has already been sent."
When the title of the post is set, with an Effect
- !1. On the server [`server.js`] | React renders `App` and **skips the Effect** | The HTML holds **`My Blog`**
- !2. A chat app reads the link | It reads **only that HTML** | The preview says **`My Blog`**, with no description
- +3. In the browser [`hydrateRoot`] | React attaches, then **the Effect runs** | Only the **tab of this browser** reads **`New Park Opens`**
```

### Why the Line Cannot Move into the Component Body

What if the developer drops the Effect and writes `document.title = post.title` straight in the body of `PostPage`? That is worse, for two reasons:
1. **It breaks the rule of a pure component.** The line changes the page while React renders, and a component must be pure (as seen in Lesson 14). React's lint page on globals marks this kind of line as incorrect: its example changes `window.currentUser` in the body of a component.
2. **It throws an error on the server.** `document` is an object of the browser. It does not exist while the server file renders.

An Effect is still fine in one case: a client-only app that needs only the text of the tab. React's own lint page shows `document.title = title` inside an Effect as correct. For a page that the server renders and that people share, render the `<title>`.

Remember: an Effect runs in the browser, but a chat app reads the HTML of the server.

## PRINCIPLE | Two `<title>` tags: React places both in the head, so only one component renders the title

> [!PRINCIPLE]
> **Principle 3: One Title: Two `<title>` Tags Both Land in the Head**
>
> *Render the `<title>` from one component only; React places every rendered `<title>` in the head and picks none.*
>
> When `App` keeps a title for the whole site and the page component adds its own, React places both in the head, and no rule says which one browsers and search engines use. Remove the title from `App` and let the page component render the full title as one string. When many routes need a site-wide fallback, a metadata library or the framework can replace the generic title with the specific one.
>
> **DO THIS:**
> ```jsx
> function App({ post }) {
>   return <html>~<head><meta charSet="utf-8" /></head>~<body><PostPage post={post} /></body></html>; // PostPage owns the only title
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function App({ post }) {
>   return <html><head>~<title>My Blog</title>~</head><body><PostPage post={post} /></body></html>; // **WRONG:** a second title next to the post's
> }
> ```

Our page now renders two titles, one from each component:

```jsx title="One title written by App, one by PostPage"
<head>
  ~<title>My Blog</title>~ {/* Written by App, for every page */}
</head>

<title>~{post.title}~</title> {/* Written by PostPage, for this post */}
```

**React does not choose between the two titles. It places both in the head.** Many developers expect the title of the post to replace the title of the site, the way a later CSS rule overrides an earlier one. React has no such rule for titles.

### How the Head Ends Up with Two Titles

Here is how it happens, step by step:
1. `App` has `<title>My Blog</title>` in its head. React's own example of an `App` that renders the whole document has a `<title>My app</title>` in the same place.
2. In Principle 1, we added the title of the post to `PostPage`, and nobody removed the title from `App`.
3. React renders `App`, which writes the first `<title>` in the head.
4. React renders `PostPage` and places its `<title>` in the head as well.
5. The page source shows two title tags in one head, and the server prints no warning.

```html title="The start of the page source, with two titles" bad="6,7"
<!DOCTYPE html>
<html>
<head>
<meta charSet="utf-8"/>
<link rel="preload" as="script" fetchPriority="low" href="/main.js"/>
<title>My Blog</title>
<title>New Park Opens</title>
<meta name="description" content="The park opens at noon."/>
<meta property="og:title" content="New Park Opens"/>
<meta property="og:description" content="The park opens at noon."/>
<link rel="canonical" href="https://example.com/posts/new-park"/>
</head>
```

What happens next has no rule. React's docs warn: "If more than one component renders a `<title>` tag at the same time, React will place all of those titles in the document head. When this happens, the behavior of browsers and search engines is undefined." Undefined means that no rule says which title they use. The tab, the chat preview, and the search result may each show either one.

React's docs give one rule for this: render only one `<title>` at a time (as seen in Lesson 83). Here the extra title sits in `App`, which renders every page. So every page of the site breaks the rule at once.

### Two Ways to Keep One Title

There are two ways to fix it, and each one fits a different site:
1. **Remove the title from `App`.** Every page component renders its own full title. This fits a site where every page has a page component, like our blog.
2. **Use a metadata library, or the metadata feature of a framework.** The React 19 announcement says that such "libraries can offer more powerful features like overriding generic metadata with specific metadata based on the current route". This fits a site with many routes, where a page without its own title should fall back to the title of the site.

Our blog takes the first way. `App` keeps only the character set in its head:

```jsx title="src/App.jsx" startLine="3"
export default function App({ post }) {
  return (
    <html>
      ~<head>~ {/* No title here: PostPage renders the only one */}
        <meta charSet="utf-8" />
      </head>
      <body>
        <PostPage post={post} />
      </body>
    </html>
  );
}
```

### The Full Title as One String

The name of the blog still belongs in the tab, after the title of the post. The first idea is to write both side by side:

```jsx title="Two pieces inside one title" bad="1"
<title>~{post.title} | My Blog~</title> {/* **WRONG:** two children, so the title comes out empty */}
```

JSX turns this into two children: the value of `post.title`, and the text after it. A `<title>` accepts one string only, so this title comes out empty (as seen in Lesson 83). Remember template literals from plain JavaScript? The backticks join the pieces into one string before React ever sees them:

```jsx title="src/PostPage.jsx" startLine="4"
      <title>~{`${post.title} | My Blog`}~</title> {/* One string: New Park Opens | My Blog */}
```

Now the head of the page source holds one title, the one of the post:

```html title="The start of the page source, with one title" good="6"
<!DOCTYPE html>
<html>
<head>
<meta charSet="utf-8"/>
<link rel="preload" as="script" fetchPriority="low" href="/main.js"/>
<title>New Park Opens | My Blog</title>
<meta name="description" content="The park opens at noon."/>
<meta property="og:title" content="New Park Opens"/>
<meta property="og:description" content="The park opens at noon."/>
<link rel="canonical" href="https://example.com/posts/new-park"/>
</head>
```

```tree caption="Leaving the title in App gives two titles in the head; removing it leaves one."
Where the title of the post page comes from
- !`<title>My Blog</title>` left in `App` | React places **both titles** in the head | Which one the tab and the preview show is **undefined**
- +`App` renders **no title** [`<head>` `<meta charSet>`] | `PostPage` renders **the only title**, built as **one string** | The head holds **one title**
```

Remember: one page, one title, written by the one component that knows the post.

## All 3 Principles Together

### The Complete Blog Post

The post object holds the data of the post:

```jsx title="src/post.js"
export const post = {
  title: 'New Park Opens',
  summary: 'The park opens at noon.',
  url: 'https://example.com/posts/new-park',
};
```

`PostPage` renders the metadata of its own post next to its heading:

```jsx title="src/PostPage.jsx"
export default function PostPage({ post }) {
  return (
    <article>
      <title>~{`${post.title} | My Blog`}~</title> {/* Principles 1 and 3: the only title, as one string */}
      <meta name="description" content={post.summary} />
      <meta property="og:title" content={post.title} />
      <meta property="og:description" content={post.summary} />
      ~<link rel="canonical" href={post.url} />~ {/* Principle 1: React places every tag in the head */}
      <h1>{post.title}</h1>
      <p>{post.summary}</p>
    </article>
  );
}
```

`App` renders the whole document, with no title of its own:

```jsx title="src/App.jsx"
import PostPage from './PostPage.jsx';

export default function App({ post }) {
  return (
    <html>
      ~<head>~ {/* Principle 3: no title here */}
        <meta charSet="utf-8" />
      </head>
      <body>
        <PostPage post={post} />
      </body>
    </html>
  );
}
```

The server file streams the page, as in Lesson 118. `app` is our server:

```jsx title="server.js"
import { renderToPipeableStream } from 'react-dom/server';
import App from './src/App.jsx';
import { post } from './src/post.js';

app.use('/', (request, response) => {
  const { pipe } = ~renderToPipeableStream~(<App post={post} />, { // Principle 2: the title is in this HTML
    bootstrapScripts: ['/main.js'],
    onShellReady() {
      response.setHeader('content-type', 'text/html');
      pipe(response);
    }
  });
});
```

The browser file attaches React in the browser:

```jsx title="src/main.jsx"
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';
import { post } from './post.js';

hydrateRoot(~document~, <App post={post} />); // App renders <html>, so React hydrates the whole document
```

The page still shows the heading and the line. The head of the page source now holds one title, the description, the two Open Graph tags, and the canonical link, all written by `PostPage`.

### How the Metadata Reaches the Head, in Order

On the server, React calls `App` first, then `PostPage`. While it renders `PostPage`, it writes each metadata tag into the head, and leaves the heading and the line in the article:

```tree dir=right caption="The order in which React calls the components and places the metadata of the post in the head."
One reader opens the post
- +1. On the server, React calls `App` [`<html>` `<head>` `<body>`] | Renders the document | The head holds **only the character set** so far
- +2. React calls `PostPage` [`<title>` `<meta>` `<link>`] | Writes **every metadata tag into the head** | Leaves **the heading and the line** in the article
- +3. A chat app or a search engine reads the HTML | The head holds **the full title of the post** and its description | The preview shows **the post**, not the site name alone
- +4. In the browser, `main.jsx` runs [`hydrateRoot`] | React attaches to the document | The tab already reads **the title of the post**
```

| Aspect | The Mistake | The React Rule |
| :--- | :--- | :--- |
| **Where the tags are written** | Keep every tag of the head in `App`, which does not know the post | Render `<title>`, `<meta>`, and `<link>` in `PostPage`; React places them in the head |
| **When the title is set** | Set `document.title` in an Effect, which runs only in the browser | Render `<title>` in the JSX, so it is in the HTML the server sends |
| **How many titles** | Keep the title of the site in `App` next to the title of the post | Render the title from one component, as one string built with a template literal |

Remember the one sentence of this lesson. **The component that knows the data renders the title, meta, and link tags, and React places them in the head, also in the HTML the server sends.**

## For the Interview

> **The Interview Question:** How do you set titles, meta tags, and links with React components?

### How to Answer Clearly in 30 Seconds

"In React 19, I render `<title>`, `<meta>`, and `<link>` in the component that knows the data, such as the post page, right next to its other JSX. React places them in the document head, wherever they sit in the tree. It works the same in client-only apps, with streaming server rendering, and with Server Components. So the title and the description are in the HTML the server sends. Three things matter most:
1. **The server HTML.** Social media crawlers usually cannot run JavaScript. So a title set with `document.title` in an Effect never reaches the link preview, because Effects run only in the browser.
2. **One title.** React does not choose between titles. If `App` and the page both render a `<title>`, both land in the head, and the behavior is undefined. So one component owns the title.
3. **One string.** The children of `<title>` must be one string, so I build a title with the site name using a template literal."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does React remove duplicate metadata tags for you?"**
   React's docs promise that only for stylesheets: two stylesheet links with the same `href` count as one. For `<title>`, the docs say the opposite. React places every rendered title in the head, and browsers and search engines then behave in an undefined way. So the code must make sure only one component renders the title.
2. **"Why not set `document.title` directly in the component body?"**
   Because it changes the page during render, and components must be pure. On the server, the line throws an error, because `document` exists only in the browser. Inside an Effect, the line is allowed, and it is fine for a client-only app that needs only the text of the tab. For a page the server renders, the `<title>` in the JSX is the right tool, because only it reaches the server HTML.
3. **"Why would you still use a metadata library with React 19?"**
   The React 19 announcement says that libraries "can offer more powerful features like overriding generic metadata with specific metadata based on the current route". That fits an app with many routes, where every page should fall back to a site title unless it sets its own. For a page that knows its own data, the built-in title, meta, and link tags are enough. Loading resources early with `preload` and `preinit` is a different job, covered in Lesson 126.
