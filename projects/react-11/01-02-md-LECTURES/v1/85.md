# Lecture 85: How a Search Field Receives ref as an Ordinary Prop

*(How does a parent reach an `<input>` that lives inside a child component?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How does React 19 treat ref as an ordinary prop, and how does it replace forwardRef?

---

## VS | `forwardRef` vs. `ref` as a Prop: the parent writes the same tag, only the place where the child finds `ref` changes

> You already know how a parent hands a value such as `placeholder` to a child component: it writes it on the tag, and the child reads it from its props. **In React 19, a ref travels exactly the same way: the child reads it from its props and puts it on its own `<input>`.** Before React 19, a ref never reached the props, so the child had to be wrapped in `forwardRef`, and today that wrapper is no longer needed.

Remember `getElementById`? In plain JavaScript, you grab an element yourself and call its methods:

```js title="page.js"
~document.getElementById('search')~.focus(); // You grab the input, then put the cursor in it
```

In React, you never create the elements by hand. React creates them from your JSX, so there is nothing to grab. A ref is how you ask React: "When you create this `<input>`, give it to me!" React puts it into `inputRef.current`, and from then on it is the same `<input>` element you know from plain JavaScript (Lesson 31):

```jsx title="App.jsx"
const inputRef = useRef(null);

<input ~ref={inputRef}~ /> {/* React puts this input element into inputRef.current */}

inputRef.current.focus(); // Later, in a click handler: the same focus as in plain JavaScript
```

This works when the `<input>` sits in the parent's own JSX. **But at work, the `<input>` usually lives inside another component**, such as a `SearchInput` that the whole store reuses. The parent writes `<SearchInput ref={inputRef} />`. Ask yourself: `SearchInput` is a function, not an HTML element. Which element should React put into `inputRef.current`? React does not know. So it hands the ref to `SearchInput`, and `SearchInput` decides which of its elements gets it.

**Why:** If the child never puts the ref on its `<input>`, the parent's ref keeps holding `null`. The user clicks `Search`, the cursor goes nowhere, and the Console shows a red `TypeError`. The whole lesson is about one question: how does the child receive the ref, so it can pass it on?

> [!DEFINITION]
> **A ref on a built-in tag.** [REVIEW] A ref is a plain object with one field, `current`, that React keeps for your component between renders. When you write `ref={inputRef}` on a built-in tag such as `<input>`, React puts that real DOM element into `inputRef.current` during the commit, the moment it writes the page into the browser. Before the commit, `current` is still `null`. React fills a ref with an element only on a built-in tag such as `<input>` or `<button>`, never on our own component, because our own component is a function and not an element (Lesson 31).

> [!DEFINITION]
> **Props.** [REVIEW] When a parent writes `<SearchInput placeholder="Looking for something?" />`, React collects every attribute of the tag into one object, the props object, and calls `SearchInput` with it. The child usually unpacks it right in its parameter list: `function SearchInput({ placeholder })`. A **function component** is a component written as a function, and every component in this book so far is one (Lesson 08).

### The same parent tag, two shapes of the child

The parent always writes the same tag:

```jsx title="The parent's tag, the same for both shapes of MyInput"
const inputRef = useRef(null);

<MyInput ~ref={inputRef}~ placeholder="Looking for something?" /> {/* After the commit, inputRef.current holds the input element */}
```

At work, you will meet the child in two shapes. In code written before React 19, the child is wrapped in a function from React called `forwardRef`. React calls the child with two separate arguments, `props` and `ref`:

```jsx title="With forwardRef: ref arrives as a second argument, after props"
const MyInput = ~forwardRef~(function MyInput(props, ~ref~) { // ref sits next to props, not inside it
  return <input placeholder={props.placeholder} ref={ref} />;
});
```

In React 19, the child is a plain function again. `ref` arrives inside the props object, next to `placeholder`:

```jsx title="With ref as a prop: ref arrives inside props, next to placeholder"
function MyInput(~{ placeholder, ref }~) { // ref is unpacked exactly like placeholder
  return <input placeholder={placeholder} ref={ref} />;
}
```

For the parent and for the page, it is the exact same thing. The parent writes the same tag. The child puts `ref={ref}` on the same `<input>`. After the commit, `inputRef.current` holds the same `<input>` element. Only one thing changed, inside the child: the place where `ref` arrives.

```tree caption="The parent's tag stays the same; only the place where the child finds ref changes."
Where `MyInput` finds the ref from `<MyInput ref={inputRef} />`
- +With `forwardRef` [`props, ref`] | React hands `ref` as a **second argument**, outside `props` | Code written for **React 18 and earlier**
- +With `ref` as a prop [`{ placeholder, ref }`] | React puts `ref` **inside `props`**, next to `placeholder` | The way to write **every new component in React 19**
```

React's announcement of React 19 says it in one line: "Starting in React 19, you can now access `ref` as a prop for function components."

### The Rule of Thumb: `ref` is a prop, so pass it on like one

**In React 19, treat `ref` on your own component like `placeholder`: unpack it, and pass it on until it lands on a built-in tag.**

Developers usually go wrong in two ways:
1. **They still reach for `forwardRef` in a new component.** React's docs say: "New function components will no longer need `forwardRef`". It still works in old code, and Lesson 99 covers it in full.
2. **They think `ref` is still kept out of `props`, the way `key` is (Lesson 18).** React's upgrade guide says: "ref is now a regular prop". Only `key` stays out.

A third tool, `useImperativeHandle`, hands the parent only a few methods instead of the whole element (Lesson 50). This lesson does not need it.

The search field is its own component, `SearchInput`, because the same field sits on many pages of the store. The `Search` button lives in the parent, `App`. So the click happens in `App`, but the `<input>` lives inside `SearchInput`.

```files title="store-header: File Explorer" caption="The project files of the store header at the start of the lesson."

  main.jsx | boundary | Mounts `<App />` inside `<StrictMode>` into `#root`

  SearchInput.jsx | default export | Exports `SearchInput`, the search field
```

Here is `App.jsx`. It stays the same for the whole lesson, except for one short test in Principle 5:

```jsx title="src/App.jsx"
import { useRef } from 'react';
import SearchInput from './SearchInput.jsx';

export default function App() {
  const inputRef = useRef(null);

  function handleSearchClick() {
    ~inputRef.current.focus();~ // Puts the cursor in the element that inputRef holds
  }

  return (
    <header>
      <nav>
        <button onClick={handleSearchClick}>Search</button>
      </nav>
      <SearchInput ~ref={inputRef}~ placeholder="Looking for something?" /> {/* The ref goes to our own component */}
    </header>
  );
}
```

**PRINCIPLES:** Each principle follows the same ref from `App` down to the `<input>`:
1. **`ref` arrives in props, next to `placeholder`.** `SearchInput` unpacks `{ placeholder, ref }` and puts `ref` on its `<input>`.
2. **`forwardRef` is the old way.** It hands `ref` in as a second argument. It still works, but a new component does not need it.
3. **Every component on the way passes `ref` on.** When the `<input>` sits two components deep, a ref goes no deeper than the last component that passes it.
4. **`{...props}` carries `ref` along.** A spread passes the ref with no `ref=` line. `{ ref, ...otherProps }` takes it out, so you write `ref={ref}` by hand.
5. **The JSX object keeps the ref in `element.props.ref`.** Reading the old field, `element.ref`, logs an error.

## PRINCIPLE | `{ placeholder, ref }`: the child receives the ref like any other prop

> [!PRINCIPLE]
> **Principle 1: ref as a Prop: A Function Component Reads ref from Its Props**
>
> *In React 19, a `ref` written on our own function component arrives in its props next to every other prop; the component unpacks it and passes it on to a built-in tag.*
>
> React fills a ref with an element only on a built-in tag such as `<input>`. On `<SearchInput ref={inputRef} />`, React has no element to give, so it hands the ref to `SearchInput` in its props, the same way it hands over `placeholder`. When `SearchInput` puts that ref on its `<input>`, the click on `Search` finds the field. When `SearchInput` ignores the ref, `inputRef.current` stays `null`.
>
> **DO THIS:**
> ```jsx
> function SearchInput({ placeholder, ref }) {
>   return <input placeholder={placeholder} ~ref={ref}~ />; // React puts the input into App's inputRef
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function SearchInput({ placeholder }) {
>   return <input ~placeholder={placeholder}~ />; // **WRONG:** the ref is never passed on, so inputRef.current stays null
> }
> ```

Look at the two attributes `App` writes on the tag, and at how `SearchInput` receives them:

```jsx title="ref and placeholder on the same tag, and in the same parameter list"
<SearchInput ~ref={inputRef}~ ~placeholder="Looking for something?"~ /> {/* Two attributes on our own component */}

function SearchInput(~{ placeholder, ref }~) { // Both arrive in the same props object
  return <input placeholder={placeholder} ref={ref} />;
}
```

`ref` and `placeholder` travel the same road:
1. `App` writes both on the `SearchInput` tag.
2. React collects both into one props object and calls `SearchInput` with it.
3. `SearchInput` unpacks both in its parameter list.
4. `SearchInput` passes both on to its `<input>`.

On the way into `SearchInput`, `ref` is a prop like any other. React's docs say a component receives `ref` "just like any other prop". React's announcement calls this **`ref` as a prop**.

The one difference comes at the end, on the `<input>`, where each prop does its own job:
- **`placeholder`** makes the field show the grey text `Looking for something?`.
- **`ref`** makes React put the `<input>` element into `inputRef.current` during the commit, as a ref on a built-in tag always does.

```tree dir=right caption="The steps that ref and placeholder share from the parent's tag to the input, and the one thing that differs at the end."
How `ref` and `placeholder` reach the `<input>`
- +1. `App` writes both on the tag [`<SearchInput ref={inputRef} />`] | `ref` and `placeholder` are **two attributes** on one tag
- +2. React builds one props object [`{ placeholder, ref }`] | `SearchInput` **unpacks both** in its parameter list
- +3. `SearchInput` passes both on [`<input ref={ref} />`] | `placeholder` shows the **grey text** | `ref` gets **the input element** in the commit
```

### The store header, step 1: SearchInput unpacks ref

Here is our real `SearchInput.jsx`, the same smallest code in its own file:

```jsx title="src/SearchInput.jsx"
export default function SearchInput(~{ placeholder, ref }~) { // ref arrives from App's tag, next to placeholder
  return <input placeholder={placeholder} ~ref={ref}~ />; // React puts this input element into App's inputRef
}
```

The `ref` inside `SearchInput` and the `inputRef` inside `App` are one and the same object. `SearchInput` did not copy it. It received it. So when React fills `ref.current`, it fills `inputRef.current` too. The user clicks `Search`, and the cursor appears in the field:

```page width=text caption="After the user clicks Search and types shoes: the cursor reached the input inside SearchInput."

card: typed=shoes | good=typed
console: quiet
```

Open the Elements panel. The `<input>` shows its placeholder, but no `ref` attribute. React uses `ref` itself and never writes it into the HTML:

```dom caption="What the Elements panel shows for the store header: the input carries its placeholder and no ref attribute."

  <nav>
    <button>Search</button>
  </nav>
  + <input placeholder="Looking for something?"> | note: Rendered by SearchInput; ref is not an HTML attribute
</header>
```

### The real mistake: unpacking only placeholder

Take the same file and forget one word: the child unpacks only `{ placeholder }`. No built-in tag carries the ref, so React never fills it. The parent's ref keeps holding `null`, and the click handler calls `focus` on `null`:

```page width=text caption="When SearchInput ignores ref, the user clicks Search and the cursor stays out of the field."
line: [Search]
card: input=Looking for something? | bad=input
console: Uncaught TypeError: Cannot read properties of null (reading 'focus')
```

React's docs give the fix in plain words: "add `ref` to the list of props your component accepts and pass `ref` as a prop to the relevant child built-in component". That is exactly our `SearchInput.jsx` above.

### What interviewers add

1. **The parent's code never changed.** `<MyInput ref={inputRef} />` was written the same way before React 19. Only the child's side changed.
2. **A ref reaches only the component its tag names.** It does not travel further by itself. Each component decides whether to pass it on, as Principle 3 shows.

## PRINCIPLE | `forwardRef`: the old wrapper still works, but a new component does not need it

> [!PRINCIPLE]
> **Principle 2: forwardRef: The Older Way Hands ref In as a Second Argument**
>
> *Before React 19, a function component received a ref only when wrapped in `forwardRef`, whose render function gets `props` and `ref` as two arguments; in React 19, write the component without `forwardRef` and unpack `ref` from its props.*
>
> `forwardRef` still works in React 19, and the parent's tag is the same for both shapes. React's docs now list it as a legacy API that "will be deprecated in a future release". When you meet it in older code, remove the wrapper, add `ref` to the unpacked props, and keep `ref={ref}` on the tag.
>
> **DO THIS:**
> ```jsx
> function SearchInput(~{ placeholder, ref }~) { // React 19: ref arrives as a prop
>   return <input placeholder={placeholder} ref={ref} />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const SearchInput = ~forwardRef~(function SearchInput(props, ref) { // **WRONG:** a new component wrapped in a legacy API it no longer needs
>   return <input placeholder={props.placeholder} ref={ref} />;
> });
> ```

Open a code base written for React 18, and you will find our `SearchInput.jsx` in this shape:

```jsx title="src/SearchInput.jsx, written for React 18"
import { forwardRef } from 'react';

const SearchInput = ~forwardRef~(function SearchInput(props, ~ref~) { // React calls this function with props and ref
  return <input placeholder={props.placeholder} ref={ref} />;
});

export default SearchInput;
```

Read it from the outside in:
1. `forwardRef` is a function from React. You hand it a function, and it gives back a new component.
2. React's docs call the function you hand it the **render function**: "React calls this function with the props and `ref` that your component received from its parent."
3. So `props` holds `placeholder` only, and `ref` comes second, as its own argument.

The name `SearchInput` appears twice. The first one, after `const`, is the component that `App` imports. The second one, after `function`, is our own name for the render function. React's docs write the same name twice too.

React's docs say `forwardRef` "lets your component expose a DOM node to the parent component with a ref". Why did we ever need it? Because before React 19, `ref` was not a prop. A ref written on a plain function component was dropped and never reached it. React's docs say a component returned by `forwardRef` "is also able to receive a `ref` prop", unlike "React components defined as plain functions". In React 19, every function component receives `ref`, so the wrapper has nothing left to do.

### VS | `forwardRef` vs. `ref` as a prop: the same outside, different inside

For `App` and for the page, it is the exact same thing. `App.jsx` does not change by a single letter, and the click on `Search` puts the cursor in the same field.

Inside `SearchInput`, it is NOT the same thing:
- **With `forwardRef`**, React calls the render function with two arguments. `props` holds `placeholder` only, and `ref` comes second.
- **With `ref` as a prop**, React calls `SearchInput` with one props object, and `ref` sits inside it, next to `placeholder`.

```tree caption="The two shapes of SearchInput: App and the page stay the same, and only the place of ref inside the child changes."
Two shapes of the same `SearchInput`
- +With `forwardRef` [`forwardRef`] | React calls the render function with **two arguments** | `props` holds `placeholder`; `ref` is the **second argument**
- +With `ref` as a prop [`{ placeholder, ref }`] | React calls `SearchInput` with **one props object** | `ref` sits **inside `props`**, next to `placeholder`
```

### forwardRef still works, and it is on its way out

The older file still works in React 19. Nothing breaks when you upgrade. But React's docs say: "In React 19, `forwardRef` is no longer necessary. Pass `ref` as a prop instead. `forwardRef` will be deprecated in a future release."

Two words tell you where `forwardRef` stands:
- **Deprecated** means the API still works today, and React has announced that it will be removed. React's announcement says: "In future versions we will deprecate and remove `forwardRef`."
- **Legacy API** is the group React's docs now file `forwardRef` under. The Legacy React APIs "are not recommended for use in newly written code".

So write every new component with `ref` as a prop. To update an older `forwardRef` component, take three steps:
1. Remove the `forwardRef` wrapper and its import.
2. Add `ref` to the props the component unpacks, as in `{ placeholder, ref }`.
3. Keep `ref={ref}` on the built-in tag.

React's announcement also promised a **codemod**, a program that rewrites your code for you, to make this change across a whole project.

### The real mistake: wrapping in forwardRef and never using ref

React's docs list this exact problem: "My component is wrapped in `forwardRef`, but the `ref` to it is always `null`". It happens like this:
1. A developer wraps `SearchInput` in `forwardRef` and believes the wrapper alone gives `App` the field.
2. The render function receives `ref`, but returns `<input placeholder={props.placeholder} />` without it.
3. `inputRef.current` stays `null`, and the click throws the same `TypeError` as in Principle 1.

The docs explain: "This usually means that you forgot to actually use the `ref` that you received." The rule is the same in both shapes. In the old shape, wrapping is not enough. In the new shape, unpacking is not enough. In both, the ref must reach a built-in tag.

### What interviewers add

1. **Strict Mode calls the render function twice.** React's docs say that in Strict Mode, React calls a `forwardRef` render function twice in development (Lesson 47).
2. **`memo` and `lazy` accept `forwardRef` components.** So an older component wrapped in `forwardRef` can also sit inside `memo` or `lazy` (Lessons 55 and 70).
3. **`useImperativeHandle` used to need `forwardRef`.** In older code, the Hook got its ref from the render function. In React 19, it gets the `ref` prop (Lesson 50).
4. **The parent never knew the difference.** Updating a child from `forwardRef` to `ref` as a prop changes no parent file.

## PRINCIPLE | `ref={ref}`: the ref reaches the `<input>` only if every component on the way passes it on

> [!PRINCIPLE]
> **Principle 3: Forwarding a Ref: Every Component on the Way Passes ref On**
>
> *When the built-in tag sits several components deep, each of our components on the way unpacks `ref` and writes `ref={ref}` on the next tag, until a built-in tag receives it.*
>
> A ref travels one component at a time, like any prop. React fills it only when it lands on a built-in tag such as `<input>`. Then the parent's ref holds that element, however deep it sits. If any component on the way leaves `ref` out, the ref stops there, the parent's ref stays `null`, and the click throws a `TypeError`.
>
> **DO THIS:**
> ```jsx
> function SearchInput({ placeholder, ref }) {
>   return <TextInput placeholder={placeholder} ~ref={ref}~ />; // Forwards the ref to TextInput, which puts it on the input
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function SearchInput({ placeholder, ref }) {
>   return <TextInput ~placeholder={placeholder}~ />; // **WRONG:** the ref stops here, so inputRef.current stays null
> }
> ```

The store has more fields than the search field: a coupon field in the cart, and an email field at checkout. The team wants all of them to look alike, so it keeps one shared component, `TextInput`, for every field. `SearchInput` now renders `TextInput` instead of its own `<input>`.

A shared text field is exactly the kind of component React's docs name as the right place to expose a DOM element: "reusable low-level components like buttons or text inputs".

The smallest code is two components, each passing `ref` on:

```jsx title="Two of our components on the way to the input"
function SearchInput({ placeholder, ref }) {
  return <TextInput placeholder={placeholder} ~ref={ref}~ />; // Passes the ref on to our own TextInput
}

function TextInput({ placeholder, ref }) {
  return <input className="text-input" placeholder={placeholder} ~ref={ref}~ />; // Passes it to the built-in input
}
```

**The ref travels one component at a time, like any prop. It goes no deeper than the last component that passes it on.** `App` never renders the `<input>`, yet the click puts the cursor in it. Here is how the ref gets there:
1. `App` renders `<SearchInput ref={inputRef} ... />`.
2. React calls `SearchInput` with `ref` in its props.
3. `SearchInput` returns `<TextInput ... ref={ref} />`. `TextInput` is our own component, not a built-in tag, so React has no element to give yet.
4. React calls `TextInput` with the same ref in its props.
5. `TextInput` returns `<input ... ref={ref} />`, a built-in tag.
6. During the commit, React puts this `<input>` element into the ref, the same object that `App` created as `inputRef`.

React's docs use one verb for steps 3 and 5: a component **forwards** the ref. Their own example reads: "The `FormField` component forwards that ref to `MyInput`, which forwards it to a browser `<input>` DOM node." Forwarding a ref is the same as forwarding any prop: passing on something we received (Lesson 09).

```tree dir=right caption="How the ref created in App passes through two of our components until a built-in input receives it."
How `inputRef` reaches the `<input>` inside `TextInput`
- +1. `App` [`<SearchInput ref={inputRef} />`] | Gives the ref to `SearchInput` **as a prop**
- +2. `SearchInput` [`<TextInput ref={ref} />`] | **Forwards** it to our own `TextInput` | No element yet: `TextInput` is **not a built-in tag**
- +3. `TextInput` [`<input ref={ref} />`] | **Forwards** it to the built-in `<input>` | In the commit, React puts **the input element** into `inputRef.current`
```

### The store header, step 2: TextInput

Here is the new file, and the new `SearchInput.jsx` that uses it. `App.jsx` does not change:

```jsx title="src/TextInput.jsx"
export default function TextInput({ placeholder, ref }) {
  return <input className="text-input" placeholder={placeholder} ~ref={ref}~ />; // The built-in tag that receives the ref
}
```

```jsx title="src/SearchInput.jsx"
import TextInput from './TextInput.jsx';

export default function SearchInput({ placeholder, ref }) {
  return <TextInput placeholder={placeholder} ~ref={ref}~ />; // Forwards App's ref one component deeper
}
```

The Elements panel now shows the `class` that `TextInput` added. Neither `SearchInput` nor `TextInput` appears in the HTML, only the `<input>` they produce (Lesson 04):

```dom caption="What the Elements panel shows after TextInput renders the input: one input with its class and placeholder."

  <nav>
    <button>Search</button>
  </nav>
  + <input class="text-input" placeholder="Looking for something?"> | note: Rendered by TextInput, inside SearchInput
</header>
```

### The real mistake: one component on the way forgets ref

**A ref does not find the `<input>` by itself. If one component on the way leaves it out, the click breaks.**

```jsx title="src/SearchInput.jsx"
export default function SearchInput({ placeholder, ref }) {
  return <TextInput ~placeholder={placeholder}~ />; // **WRONG:** ref is unpacked but never passed on to TextInput
}
```

Here is what happens:
1. `SearchInput` unpacks `{ placeholder, ref }`, but writes only `placeholder` on the `TextInput` tag.
2. `TextInput` receives no ref. Its unpacked `ref` is `undefined`, because no attribute on its tag gave one.
3. `inputRef.current` stays `null`, and the click throws the `TypeError` from Principle 1.

The same thing happens when the `<input>` renders only under a condition. Suppose `TextInput` returns `{showInput && <input ref={ref} />}`, and `showInput` is `false`. Then, as React's docs say, "the ref won't be forwarded to any node". They add: "This is particularly easy to miss if the condition is hidden inside another component".

### What interviewers add

1. **How deep can a ref go?** Through as many of our components as pass it on. React's docs show one that goes from a form, to a form field, to a text input, and then to the built-in `<input>`.
2. **Which components should expose an element?** Low-level ones, such as a text input or a button. Not application-level ones, such as an avatar or a comment.
3. **When should you not use a ref at all?** React's docs say: "If you can express something as a prop, you should not use a ref." To show or hide a dialog, pass `isOpen` as a prop. A ref is for actions that no prop can say, such as moving the cursor (Lesson 50).

## PRINCIPLE | `{...props}`: the spread carries the ref along, `{ ref, ...otherProps }` leaves it out

> [!PRINCIPLE]
> **Principle 4: Spread and ref: {...props} Passes ref Because ref Is in props**
>
> *In React 19, a component that writes `{...props}` on a built-in tag passes the ref along with the other props; after `{ ref, ...otherProps }`, the rest no longer holds the ref, so write `ref={ref}` on the tag yourself.*
>
> A spread copies every field of the object it spreads. In React 19, `props` holds `ref`, so `{...props}` puts the ref on the `<input>` with no `ref=` line. A rest property that names `ref` first takes it out of the rest. With `forwardRef`, `props` never held the ref, so the spread never carried it.
>
> **DO THIS:**
> ```jsx
> function TextInput({ ref, ...otherProps }) {
>   return <input {...otherProps} ~ref={ref}~ />; // The ref taken out of otherProps goes back on by hand
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function TextInput({ ref, ...otherProps }) {
>   return <input ~{...otherProps}~ />; // **WRONG:** otherProps holds every prop except ref, so the ref is dropped
> }
> ```

`TextInput` passes every prop it gets to the `<input>`. Writing each prop by hand gets long, so developers use the spread `{...props}` (Lesson 09). The spread copies every field of an object onto the tag. Now ask: is `ref` one of those fields? In React 19, yes.

Here are three versions of `TextInput` with a spread. The one difference is whether `ref` is still inside the object that is spread:

```jsx title="With {...props}: ref is inside props"
function TextInput(props) {
  return <input className="text-input" ~{...props}~ />; // Spreads placeholder and ref onto the input
}
```

```jsx title="With { ref, ...otherProps } and ref={ref}: ref is taken out, then written by hand"
function TextInput({ ref, ...otherProps }) {
  return <input className="text-input" {...otherProps} ~ref={ref}~ />; // otherProps has placeholder; ref is written by hand
}
```

```jsx title="With { ref, ...otherProps } alone: ref is taken out and dropped"
function TextInput({ ref, ...otherProps }) {
  return <input className="text-input" ~{...otherProps}~ />; // **WRONG:** otherProps has no ref, so the input never gets it
}
```

> [!DEFINITION]
> **A rest property.** [NEW] In a parameter list, `...otherProps` collects every field that is not named before it. Think of a person object with `firstName`, `lastName`, and `age`. Writing `{ firstName, ...rest }` gives you `firstName` on its own, and `rest` holds only `lastName` and `age`. So in `{ ref, ...otherProps }`, `ref` is named first, and `otherProps` holds everything except `ref`. React's docs use the same pattern in their own examples (Lesson 85).

The first two versions do the exact same thing. Both put `placeholder` and `ref` on the `<input>`, and the click works in both.

The second and third versions look almost the same, but they are NOT the same thing. The rest property took everything except `ref`. Without the `ref={ref}` line, nothing passes the ref on, so `inputRef.current` stays `null`.

```tree caption="Three versions of TextInput with a spread, and whether the ref reaches the input in each."
Is `ref` still inside the object that is spread?
- +With `{...props}` [`<input {...props} />`] | `props` **holds `ref`** | The spread puts **`ref` on the input**
- +With `{ ref, ...otherProps }` and `ref={ref}` [`{...otherProps} ref={ref}`] | `otherProps` **has no `ref`** | The **hand-written** `ref={ref}` puts it on the input
- !With `{ ref, ...otherProps }` alone [`{...otherProps}`] | `otherProps` **has no `ref`** | **Nothing** puts it on the input: `inputRef.current` stays **`null`**
```

### The spread passes a ref that no line writes

**The version with `{...props}` has no `ref=` anywhere, yet the click works.** Developers meet this when they update an older component:
1. A developer finds a `forwardRef` version of `TextInput` that spreads `props` and writes `ref={ref}` after the spread.
2. They remove the wrapper and the second argument, and write `function TextInput(props)`.
3. The old `ref` argument is gone, so they delete `ref={ref}` too. The tag now reads `<input className="text-input" {...props} />`.
4. The user clicks `Search`, and the cursor still lands in the field.

It still works because the spread carries the ref. React gives `TextInput` one props object that holds `placeholder` and `ref`. `{...props}` copies every field of that object onto the `<input>`. `<input>` is a built-in tag, so during the commit React puts this element into the ref.

With `forwardRef`, the same spread never carried the ref. React's docs describe the render function's `props` as "the props passed by the parent component", and the ref came separately, as the second argument. That is why older code always writes `ref={ref}` after `{...otherProps}`.

### The store header, step 3: TextInput spreads its props

Our `TextInput` now spreads `props`. So a later prop, such as `type="search"`, reaches the `<input>` with no new line in the file. `SearchInput.jsx` and `App.jsx` do not change:

```jsx title="src/TextInput.jsx"
export default function TextInput(props) {
  return <input className="text-input" ~{...props}~ />; // Carries placeholder and ref onto the input
}
```

The page works as before. The user clicks `Search`, and the cursor appears in the field.

### What interviewers add

1. **`key` does not travel with the spread.** React's docs say that "your components won't receive `key` as a prop" (Lesson 18). So `props` never holds `key`, and `{...props}` never carries it. `ref` changed in React 19, and `key` did not.
2. **A spread passes everything, wanted or not.** Spreading every prop onto a built-in tag also passes props the tag does not know, and React then warns about an unknown prop on a DOM element (Lesson 09). `ref` is not one of those, because every built-in tag accepts it.
3. **Writing `ref={ref}` by hand stays fine.** React's docs, in the passage on forwarding props with the spread syntax, say that repeated code is not a mistake and can be easier to read. The version with `{ ref, ...otherProps }` and `ref={ref}` shows exactly where the ref goes.

## PRINCIPLE | `element.props.ref`: the JSX object keeps the ref inside props, `key` stays outside

> [!PRINCIPLE]
> **Principle 5: element.props.ref: The Element Object Keeps ref Inside props**
>
> *In React 19, the element that JSX builds from `<SearchInput ref={inputRef} />` keeps the ref in `element.props.ref`; reading the old `element.ref` logs an error, and `key` still stays outside `props`.*
>
> The ref is a prop from the moment the tag becomes an object, which is why the component later finds it in its props. Older code that reads `element.ref` still gets the ref, but the Console says "ref is now a regular prop", and the field will be removed. Read `element.props.ref` instead, and in application code, avoid reading element fields at all.
>
> **DO THIS:**
> ```jsx
> const element = <SearchInput ref={inputRef} />;
> console.log(~element.props.ref~); // The ref object, where React 19 keeps it
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const element = <SearchInput ref={inputRef} />;
> console.log(~element.ref~); // **WRONG:** the old field; React logs that ref is now a regular prop
> ```

Remember what a JSX tag becomes: a plain object with `type`, `props`, and `key` (Lesson 76). We saw that `ref` is a prop inside `SearchInput`. It is a prop one step earlier too, in that object.

Here is how the ref gets into `props`:
1. The build turns `<SearchInput ref={inputRef} placeholder="..." />` into a function call (Lesson 02).
2. That call returns an element object with `type: SearchInput` and `props`.
3. In React 19, `ref` goes into `props`, beside `placeholder`.
4. When React renders `SearchInput`, it hands over that same props object, so the component finds `ref` in its parameter list.

This needs the **new JSX transform**, the current way the build turns JSX into function calls. React's upgrade guide says React 19 requires it, because improvements "like using ref as a prop" depend on it.

To see it, add a short test to the click handler in `App.jsx`. It builds one `SearchInput` element, never renders it, and logs two of its fields:

```jsx title="src/App.jsx" startLine="7"
  function handleSearchClick() {
    inputRef.current.focus();
    const element = <SearchInput ref={inputRef} placeholder="Looking for something?" />; // A test element, never rendered
    console.log(~element.props.ref~); // The ref object App created
    console.log(~element.ref~); // **WRONG:** the old field; reading it logs an error
  }
```

The user clicks `Search`. The cursor still lands in the field, and the code only reads two fields. Yet the Console shows a red error between the two logs:

```devconsole width=full
{current: input.text-input} | App.jsx:10
x Accessing element.ref was removed in React 19. ref is now a regular prop. It will be removed from the JSX Element type in a future release.
{current: input.text-input} | App.jsx:11
```

### VS | `element.props.ref` vs. `element.ref`: the new place and the old place

- **`element.props.ref`** holds the ref object that `App` created. By the time the user clicks, the commit is over, so its `current` already holds the `<input>` element.
- **`element.ref`** is the field where older versions of React kept the ref, outside `props`. React's upgrade guide says it is deprecated "in place of `element.props.ref`". Reading it still gives the ref, but React logs the error above the first time.

```tree caption="Where ref and key sit in the element object that JSX builds in React 19."
The element object for `<SearchInput ref={inputRef} placeholder="..." />`
- +`element.props.ref` [`props.ref`] | **The new place** of the ref, next to `props.placeholder` | Holds the ref object `App` created
- !`element.ref` [`element.ref`] | **The old place**, outside `props` | Reading it logs **an error** in the Console
- +`element.key` [`element.key`] | `key` **still stays outside** `props` | Components **never receive** `key` as a prop
```

### Who reads element.ref

Our application code rarely reads an element's fields. React's docs advise treating every element "as opaque after it's created, and only render it". So this error shows up mostly in older library code that looks inside the `children` it receives, for example to copy an element with `cloneElement`. When such a library runs on React 19, the Console shows this error until the library reads `element.props.ref` instead.

Once you have seen the Console, remove the three test lines from `App.jsx`.

### What interviewers add

1. **Class components are different.** React's announcement says: "`ref`s passed to classes are not passed as props since they reference the component instance." A ref on a class component still points at the component itself. Lesson 99 covers class components and their refs.
2. **`key` is still not a prop.** React 19 moved the ref into the props, but not the key: inside a component, `props.key` is `undefined`. When the parent gave a `key`, reading `props.key` also logs a red error that begins "`key` is not a prop" (Lesson 18).

## All 5 Principles Together

### The complete store header

Here is the complete header, without the test lines of Principle 5. `App` creates the ref, `SearchInput` forwards it, and `TextInput` spreads it onto the `<input>`:

```jsx title="src/App.jsx"
import { useRef } from 'react';
import SearchInput from './SearchInput.jsx';

export default function App() {
  const inputRef = useRef(null);

  function handleSearchClick() {
    ~inputRef.current.focus();~ // After the commit, inputRef holds the input inside TextInput
  }

  return (
    <header>
      <nav>
        <button onClick={handleSearchClick}>Search</button>
      </nav>
      <SearchInput ~ref={inputRef}~ placeholder="Looking for something?" /> {/* Principle 1: ref goes in as a prop */}
    </header>
  );
}
```

```jsx title="src/SearchInput.jsx"
import TextInput from './TextInput.jsx';

export default function SearchInput(~{ placeholder, ref }~) { // Principles 1 and 2: ref unpacked from props, no forwardRef
  return <TextInput placeholder={placeholder} ~ref={ref}~ />; // Principle 3: forwards the ref one component deeper
}
```

```jsx title="src/TextInput.jsx"
export default function TextInput(props) {
  return <input className="text-input" ~{...props}~ />; // Principle 4: the spread carries placeholder and ref
}
```

### How React calls the components, and where the ref lands

When the page opens, React calls `App`, then `SearchInput`, then `TextInput`, in the order of their tags. During this render, `inputRef.current` is still `null`. The ref only passes down with the props. React fills it at the end, in the commit:

```tree caption="The order in which React calls App, SearchInput, and TextInput, and where the ref travels at each step."
`App` [1. Called first] | Creates **`inputRef`**, `null` during the render | Writes it **on the `SearchInput` tag**
- +`SearchInput` [2. Called second] | Receives `ref` **in its props** | **Forwards** it to `TextInput`
  - +`TextInput` [3. Called third] | Spreads `props`, **ref included**, onto the built-in `<input>` | After the commit: `inputRef.current` holds **the input element**
```

The user clicks `Search`, and the cursor lands in the field:

```page width=text caption="The finished store header after the user clicks Search and types shoes."
line: [Search]
card: typed=shoes | good=typed
console: quiet
```

| Aspect | The Habit from React 18 | The React 19 Rule |
| :--- | :--- | :--- |
| **Receiving a ref** | Wrap the component in `forwardRef` and read `ref` as a second argument | Unpack `ref` from props, like `placeholder` |
| **Older `forwardRef` code** | Keep adding `forwardRef` to every new component | Leave old code working; write new components without it, and remove the wrapper when you update one |
| **A ref two components deep** | Expect the ref to find the `<input>` inside by itself | Every component on the way forwards it with `ref={ref}` |
| **Spreading props** | Write `ref={ref}` after every spread, because `props` never held the ref | `{...props}` carries `ref`; after `{ ref, ...otherProps }`, write `ref={ref}` by hand |
| **The element object** | Read the ref from `element.ref`, beside `key` | Read `element.props.ref`; only `key` stays outside `props` |

Remember the one sentence of this lesson. **In React 19, `ref` is a prop like `placeholder`: the child unpacks it and passes it on, until it lands on a built-in tag.**

## For the Interview

> **The Interview Question:** How does React 19 treat ref as an ordinary prop, and how does it replace forwardRef?

### How to Answer Clearly in 30 Seconds

"In React 19, a function component receives `ref` in its props, like any other prop. The parent writes `<SearchInput ref={inputRef} />`, and the child unpacks `{ placeholder, ref }` and passes `ref` on to a built-in tag, such as `<input ref={ref} />`. During the commit, React puts that DOM element into the parent's ref. Before React 19, a ref did not reach a plain function component, so we wrapped it in `forwardRef`, whose render function gets `props` and `ref` as two arguments. The parent's code is the same in both. `forwardRef` still works, but React's docs say it is no longer necessary and will be deprecated, so new components skip it. Three things follow from `ref` being a prop:
1. **A ref goes only as deep as components pass it.** Each component on the way must forward it, or the parent's ref stays `null`.
2. **`{...props}` now carries the ref.** A rest property that names `ref` first leaves it out, so you write `ref={ref}` by hand.
3. **The element keeps it in `element.props.ref`.** Reading `element.ref` logs an error, and `key` is still not a prop."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Do you have to remove `forwardRef` from existing code when you upgrade to React 19?"**
   No. A component wrapped in `forwardRef` keeps working in React 19, and its parents do not change. React's docs say `forwardRef` "will be deprecated in a future release", and list it among the Legacy React APIs, which are "not recommended for use in newly written code". So write new components with `ref` as a prop. When you touch an older one, remove the wrapper, add `ref` to the unpacked props, and keep `ref={ref}` on the tag. React's announcement also promised a codemod that makes this change for you.
2. **"A parent passes a ref to your component, but `ref.current` is always `null`. What do you check?"**
   Check that the ref reaches a built-in tag. React fills a ref with a DOM element only on a built-in tag such as `<input>`. On our own component, the ref is just a prop. So walk down from the parent: each component must unpack `ref` and pass it on with `ref={ref}`, or spread a props object that still holds it. Also check that the tag really renders. If the `<input>` sits behind a condition that is `false`, React's docs say "the ref won't be forwarded to any node". In older `forwardRef` code, the cause is usually the one the docs name: "you forgot to actually use the `ref` that you received."
3. **"Is `ref` now exactly like any other prop? What about `key`?"**
   For function components, yes: `ref` arrives in props, `{...props}` carries it, and the element keeps it in `element.props.ref`. Two limits remain. First, `key` is still not a prop: "your components won't receive `key` as a prop", so `props.key` is `undefined`. Second, a ref on a class component is not a prop, because it points at the component instance. And `ref` as a prop needs the new JSX transform, which React 19 requires.

```tree dir=right caption="Interview comparison: what changed for ref in React 19, and what stayed the same."
`ref` in React 19
- +What changed [`{ placeholder, ref }`] | A function component **receives `ref` in props** | `forwardRef` is **no longer needed**; `{...props}` **carries the ref**; the element keeps it in **`props.ref`**
- +What stayed the same [`<SearchInput ref={inputRef} />`] | The **parent's tag** | React fills the ref **only on a built-in tag**, during the commit
- !What is still not a prop [`key`] | **`key`** never reaches the component | A ref on a **class component** still points at the instance
```
