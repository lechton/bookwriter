## VS | Raw HTML vs. a Built-in Component in JSX: the tag looks the same, but React reads it, not the browser

> In an HTML file, the browser reads your tags and builds the page from them. **In React, the browser never reads the tags you write in JSX: React reads them, and React creates every DOM node itself.** That is why each name on a tag is the name the DOM uses in JavaScript, such as `className`, and why React can move a `<title>` into the document head.

Remember `document.createElement`? In plain JavaScript, you create the element yourself, and then you set its features one by one:

```js title="Plain JavaScript: you create the input and set its class"
const input = ~document.createElement('input')~; // Your code creates the DOM node
~input.className~ = 'search'; // The DOM calls the class className, not class
```

In React, you never call `createElement` yourself. You write a tag in JSX, and React creates the DOM node for you:

```jsx title="React: you write the tag, and React creates the input"
<input ~className~="search" /> {/* React creates the input and sets its className */}
```

Look at the name on the tag. It is not HTML's `class`. It is `className`, the exact name you typed on the DOM node in plain JavaScript. And the result is the same: open the Elements panel, and both versions show `<input class="search">`.

So here is the one idea of this lesson: **a tag in JSX is not HTML. It is a description that React turns into a DOM node, so it speaks the language of the DOM.**

> [!DEFINITION]
> **What is a built-in browser component?** [NEW] React's docs call every tag of the browser, such as `<div>`, `<input>`, `<li>`, or `<title>`, a built-in browser component. It starts with a lowercase letter, while your own components start with a capital letter, such as `<Inbox>`. React supports every built-in HTML and SVG tag, and it creates the real DOM node from each one (Lesson 83).

### What React Adds to Plain HTML

React's docs sort the built-in components into three groups, by what React does with them beyond plain HTML:

```tree caption="React's docs sort the built-in browser components into three groups, by what React adds to plain HTML."
React's built-in browser components
- +Common components [`<div>` `<li>` `<label>` `<h1>`] | Every tag of the browser | Names follow the **DOM**: `className`, `htmlFor`, a `style` object
- +Form components [`<input>` `<select>` `<textarea>`] | Everything the common components do | Passing `value` makes them **controlled**
- +Resource and metadata components [`<title>` `<meta>` `<link>` `<script>` `<style>`] | Everything the common components do | React can place them in the **document head**
```

This lesson covers the first group and the third group. The form components, and what `value` does to them, are in Lesson 20.

### Three Ways to Put a Count in the Browser Tab

A mail app shows its unread count in the browser tab, such as `Inbox (2)`. The count lives in the state of a component. But the text of the tab lives in a `<title>` tag, inside the document head, far away from the root `<div>` where React renders your app.

Developers choose between three ways to bring the count to the tab:
1. **Render a `<title>` from the component.** This is new in React 19, and this lesson uses it.
2. **Set `document.title` inside an Effect.** This was the way before React 19 (Lesson 32).
3. **Use a metadata library such as `react-helmet`.** A library still helps when every route of an app must replace the title and the other metadata (Lesson 121).

### The Rule of Thumb: type the DOM's name, and let React place the head tags

**On a tag in JSX, type the name the DOM uses in plain JavaScript, such as `className` instead of `class`. Give `style` an object, not a string. Render a `<title>` from the component that knows the data, and give it one string.**

Here is what the user sees when a developer treats these tags as HTML:
1. A row with a string of CSS in `style`, pasted from an HTML page, is not bold. The whole page goes blank.
2. A title written as text and a value in curly braces side by side does not show the count in the tab.
3. Two components on the same screen that each render a `<title>` give undefined behavior in browsers and search engines.

Developers usually go wrong by treating JSX as HTML with a few spelling changes. They paste HTML from a mockup and expect every HTML habit to work. And they never expect a tag to leave the place where they wrote it.

## SECTION | An Inbox with a Search Field and Three Emails

Our page is a small inbox. It has a heading, a search field with its label, and a list of three emails. Two of the emails are unread, so they are bold, and the browser tab reads `Inbox (2)`.

```page caption="The inbox when it opens. On the real page the first two emails are bold, and the browser tab shows the unread count, 2."
heading: Inbox
form:
  field: Search mail
line: Get your next month for $0.99
line: Your order has shipped
line: Welcome to the team
```

The user clicks the unread email **Get your next month for $0.99**. Two things change at once:
1. That row stops being bold.
2. The browser tab now reads `Inbox (1)`.

The inbox lives in a small Vite project:

```files title="inbox: File Explorer" caption="How the inbox files sit in the project. The stylesheet arrives in Principle 5."
index.html | entry | The HTML page with the empty root div where React renders
public/
  email-row.css | stylesheet | A border under every email row, added in Principle 5
src/
  main.jsx | boundary | Imports `Inbox` and renders it into `#root`
  Inbox.jsx | parent | Holds the emails in state, renders the title, the search field, and one `EmailRow` per email
  EmailRow.jsx | child | Returns one `<li>`, bold while the email is unread
```

The emails start as an array of three objects. Each object has an id, a subject, and an `unread` flag:

```jsx title="src/Inbox.jsx" startLine="4"
const initialEmails = [
  { id: 0, subject: 'Get your next month for $0.99', ~unread: true~ }, // Unread, so bold
  { id: 1, subject: 'Your order has shipped', unread: true },
  { id: 2, subject: 'Welcome to the team', unread: false },
];
```

`Inbox` holds this array in state and counts the unread emails during each render (Lesson 22). It passes each email to an `EmailRow`, together with a function `onOpen`. The row calls `onOpen` when the user clicks it (Lesson 23).

**PRINCIPLES:** Every tag in the inbox is a description that React turns into a DOM node. Five principles follow from that one fact:
1. **Principle 1: className and htmlFor Are the DOM's Names.** On a built-in tag, a prop takes the name the DOM uses in JavaScript. Only `aria-*` and `data-*` keep their dashes.
2. **Principle 2: style Takes an Object.** It works like the DOM's `style` property, with camelCase names. A string of CSS pasted from HTML blanks the whole page.
3. **Principle 3: React Places a title in the Head.** In React 19, a `<title>` rendered from any component lands in the document head. Render only one at a time.
4. **Principle 4: A title Takes One String.** Text and a value in curly braces side by side make several children. Build the text with a template literal instead.
5. **Principle 5: precedence Gives One Stylesheet Link for Every Row.** With `precedence`, React puts one copy in the head and waits for it to load. Without it, nothing special happens.

## PRINCIPLE | `className` and `htmlFor`: a JSX tag takes the names the DOM uses in JavaScript

> [!PRINCIPLE]
> **Principle 1: DOM Names: `className` and `htmlFor` Replace HTML's `class` and `for`**
>
> *On a built-in tag, type the DOM property's name, such as `className`, `htmlFor`, and `tabIndex`; only `aria-*` and `data-*` keep their dashes.*
>
> Every attribute in JSX becomes a key of a JavaScript object, and `class` is a reserved word in JavaScript. So React uses the names the DOM already uses in plain JavaScript. React still writes the usual HTML attribute on the node, so the Elements panel shows `class` and `for` as always. When you paste the HTML names, the Console asks for the DOM names.
>
> **DO THIS:**
> ```jsx
> <label ~htmlFor~="search">Search mail</label> {/* The DOM's name: a click on the label puts the cursor in the field */}
> <input id="search" className="search" />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <label ~for~="search">Search mail</label> {/* **WRONG:** the HTML name, so the Console asks for htmlFor */}
> <input id="search" class="search" />
> ```

The search field of our inbox is a `<label>` and an `<input>` field. Here it is in HTML, and then in JSX:

```jsx title="The search field in HTML, and the same field in JSX"
<label ~for~="search">Search mail</label> <input id="search" ~class~="search"> {/* HTML: for and class */}
<label ~htmlFor~="search">Search mail</label> <input id="search" ~className~="search" /> {/* JSX: htmlFor and className */}
```

It is the exact same thing. Both give an `<input>` field with the CSS class `search`, and a label tied to it. In both, when the user clicks the words `Search mail`, the browser puts the cursor in the field. The Elements panel shows the very same nodes for both:

```dom caption="The Elements panel shows the same nodes for the HTML version and for the JSX version of the search field."
<label for="search">Search mail</label>
<input id="search" class="search">
```

Only the names you type change, as the two lines of code show.

### Why React Renamed `class` and `for`

React did not invent these names. They are the names the DOM already uses in plain JavaScript:

```js title="Plain JavaScript: the DOM's own names for class and for"
const input = document.getElementById('search');
~input.className~ = 'search'; // The DOM calls the class className

const label = document.querySelector('label');
~label.htmlFor~ = 'search'; // The DOM calls the for link htmlFor
```

> [!DEFINITION]
> **What is a DOM property?** [NEW] A DOM property is the name the browser gives to a feature of a DOM node when your JavaScript reads or changes it, such as `input.className` or `label.htmlFor`. It is often the same as the HTML attribute, such as `id`, but not always: HTML's `class` is the DOM's `className` (Lesson 83).

So the rule is simple. **On a tag in JSX, type what you would type on the DOM node in plain JavaScript.** React's docs give two reasons for this choice.

The first reason: JSX turns into JavaScript (Lesson 02). Every attribute on the tag becomes a key of a JavaScript object:

```js title="What the JSX compiler makes of the input tag"
<input id="search" ~className~="search" /> // Becomes _jsx('input', { id: 'search', className: 'search' })
```

Your own components often read those keys into variables. A JavaScript variable name cannot contain a dash, and it cannot be a reserved word such as `class`. A component that tried to read a prop named `class` would not even run:

```jsx title="Why class cannot be a variable name"
function SearchField({ ~class~ }) { // **WRONG:** class is a reserved word, so JavaScript reports a syntax error and the file never runs
  return <input className={class} />;
}
```

The second reason: consistency. The names cannot all match HTML anyway, so React uses the DOM's names everywhere. That is why `for` becomes `htmlFor`. And a name made of several words is written in camelCase, such as `tabIndex`.

### Which Names Change, and Which Stay as in HTML

Most attributes keep their HTML name, such as `id` and `href`, because the DOM uses the same name. Three kinds of names change: `class`, `for`, and the names made of several words. Two families keep their dashes, `aria-*` and `data-*`. React's docs say this is for historical reasons:

```jsx title="Which names change in JSX, and which stay as in HTML"
<input ~className~="search" /> {/* class becomes className */}
<label ~htmlFor~="search">Search mail</label> {/* for becomes htmlFor */}
<li ~tabIndex~={0}>Welcome to the team</li> {/* tabindex becomes tabIndex, in camelCase */}
<li ~data-id~="2">Welcome to the team</li> {/* data-* keeps its dashes */}
<input ~aria-label~="Search mail" /> {/* aria-* keeps its dashes */}
```

You can also invent your own attributes. React passes them to the DOM as long as the name is in lowercase and does not start with `on`. React turns the value into a string. React's docs call these **custom attributes**.

```tree caption="On a built-in tag, most names follow the DOM's camelCase names, and two families keep their HTML dashes."
Attribute names on a built-in tag in JSX
- +The DOM's name [`className` `htmlFor` `tabIndex`] | Replaces HTML's `class`, `for`, and `tabindex` | React writes the **HTML attribute** on the node
- +Dashes kept [`aria-label` `data-id`] | `aria-*` and `data-*` keep the HTML spelling | For **historical reasons**, as React's docs say
- +Unchanged [`id` `href` `placeholder`] | One plain word, the same in HTML and in the DOM | Typed **exactly as in HTML**
```

### Pasting the HTML of the Search Field into `Inbox`

React's own docs show this mistake. A developer has a working HTML page with the search field, and pastes it into `Inbox` unchanged:

```jsx title="src/Inbox.jsx" startLine="1"
export default function Inbox() {
  return (
    <main>
      <h1>Inbox</h1>
      <label ~for~="search">Search mail</label> {/* **WRONG:** for is the HTML name */}
      <input id="search" ~class~="search" /> {/* **WRONG:** class is the HTML name */}
    </main>
  );
}
```

The field appears on the page. But the Console shows one message for each HTML name, and each message suggests the DOM's name:

```page width=full caption="The pasted HTML names: the field appears, and the Console shows one message for each HTML name."
heading: Inbox
form:
  field: Search mail
console: Invalid DOM property `for`. Did you mean `htmlFor`?
  error: Invalid DOM property `class`. Did you mean `className`?
```

The fix is to type the DOM's names. For a large piece of HTML, React's docs point to an online converter that renames every attribute at once.

```jsx title="src/Inbox.jsx" startLine="1"
export default function Inbox() {
  return (
    <main>
      <h1>Inbox</h1>
      <label ~htmlFor~="search">Search mail</label> {/* A click on these words puts the cursor in the field */}
      <input id="search" ~className~="search" /> {/* The Elements panel shows class="search" */}
    </main>
  );
}
```

```page width=full caption="The search field with the DOM's names: the same page, and a quiet Console."
heading: Inbox
form:
  field: Search mail
console: quiet
```

Our code says `className`, yet the Elements panel shows `class="search"`. React writes that attribute for you, in three steps:
1. The JSX compiler turns the tag into an object whose props hold `className` with the value `search`.
2. React creates the `<input>` DOM node.
3. React gives the node the class `search`, and the Elements panel shows it as `class="search"`.

## PRINCIPLE | `style={{ fontWeight: 'bold' }}`: style takes an object, like the DOM's `style` property

> [!PRINCIPLE]
> **Principle 2: Style Object: `style` Takes an Object with camelCase Names**
>
> *Pass `style` an object with camelCase CSS names, such as `{ fontWeight: 'bold' }`, and use it for styles that depend on data.*
>
> React's `style` works like the DOM's `style` property, so it takes an object, not a string of CSS. A number gets `px`, unless the property is unitless. A string of CSS pasted from HTML makes React stop with an error, and the whole page disappears. For styles that never change, a CSS class with `className` works better.
>
> **DO THIS:**
> ```jsx
> <li ~style={{ fontWeight: email.unread ? 'bold' : 'normal' }}~> {/* Bold while the email is unread */}
>   {email.subject}
> </li>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <li ~style="font-weight: bold"~> {/* **WRONG:** a string of CSS, so React stops and the inbox disappears */}
>   {email.subject}
> </li>
> ```

An unread email must be bold. Here is a bold row in HTML, and then in JSX:

```jsx title="A bold row in HTML, and the same row in JSX"
<li ~style="font-weight: bold"~>Your order has shipped</li> {/* HTML: a string of CSS */}
<li ~style={{ fontWeight: 'bold' }}~>Your order has shipped</li> {/* JSX: an object with a camelCase name */}
```

Both lines ask for the same CSS rule. But they are not the same thing. In HTML, `style` holds a string of CSS. In JSX, `style` holds a JavaScript object, and a string does not work there.

Why an object? Once again, React follows the DOM. In plain JavaScript, the DOM's `style` property is an object, and its CSS names are in camelCase:

```js title="Plain JavaScript: the DOM's style property is an object"
const row = document.querySelector('li');
~row.style.fontWeight~ = 'bold'; // The DOM writes font-weight as fontWeight
```

So the `style` you pass in JSX follows the same two rules as the DOM's `style` property:
1. **The names are in camelCase.** `font-weight` becomes `fontWeight`. And `background-color` becomes `backgroundColor`.
2. **The values are strings or numbers.** When you pass a number, React adds `px`, so `margin: 20` means 20 pixels.

> [!DEFINITION]
> **What is a unitless property?** [NEW] A unitless property is a CSS property where pixels make no sense, such as `opacity`. React leaves a number alone there, so `opacity: 0.5` stays 0.5 and does not become `0.5px` (Lesson 83).

The double curly braces are nothing new (Lesson 03). The outer pair steps into JavaScript. The inner pair is an ordinary object.

### Pasting the Bold Row from an HTML Mockup

First, the inbox gets its list. `Inbox` now holds the emails in state. When the user clicks a row, `handleOpen` builds a new array where only that email is no longer unread (Lesson 19):

```jsx title="src/Inbox.jsx" startLine="1"
import { useState } from 'react';
import EmailRow from './EmailRow.jsx';

const initialEmails = [
  { id: 0, subject: 'Get your next month for $0.99', unread: true },
  { id: 1, subject: 'Your order has shipped', unread: true },
  { id: 2, subject: 'Welcome to the team', unread: false },
];

export default function Inbox() {
  const [emails, setEmails] = useState(initialEmails);

  function handleOpen(id) {
    ~setEmails~(emails.map(e => (e.id === id ? { ...e, unread: false } : e))); // Only the clicked email becomes read
  }

  return (
    <main>
      <h1>Inbox</h1>
      <label htmlFor="search">Search mail</label>
      <input id="search" className="search" />
      <ul>
        {emails.map(email => (
          <EmailRow key={email.id} email={email} onOpen={handleOpen} />
        ))}
      </ul>
    </main>
  );
}
```

Each row lives in its own file, `EmailRow.jsx`. It receives one email and the function `onOpen`, and returns one `<li>`. A developer copies the bold row from an HTML mockup and pastes it in:

```jsx title="src/EmailRow.jsx" startLine="1"
export default function EmailRow({ email, onOpen }) {
  return (
    <li ~style="font-weight: bold"~ onClick={() => onOpen(email.id)}> {/* **WRONG:** a string of CSS, pasted from HTML */}
      {email.subject}
    </li>
  );
}
```

The editor does not complain. Then the page opens, and the whole inbox is gone. The page is blank, and the Console shows an error:

```page width=full caption="A style string pasted from HTML: the whole inbox disappears, and the Console shows an error."
blank
console: Uncaught Error: The `style` prop expects a mapping from style properties to values, not a string. For example, style={{marginRight: spacing + 'em'}} when using JSX.
  warn: An error occurred in the <li> component. Consider adding an error boundary to your tree to customize error handling behavior.
```

One mistake on one row removes the search field and the heading too. Here is why:
1. React renders the first `EmailRow` and finds the string `"font-weight: bold"` where it expects an object.
2. React stops with the error above.
3. No code catches the error, so React removes the whole page from the screen (Lesson 72).

A second mistake often follows. The developer turns the string into an object, but keeps the CSS name `font-weight` as the key:

```jsx title="An object with the CSS name as its key"
<li ~style={{ font-weight: 'bold' }}~> {/* **WRONG:** a dash in a key without quotes, so JavaScript reports a syntax error */}
```

JavaScript does not accept a dash in a key without quotes. And React expects the camelCase name anyway, so the key is `fontWeight`.

### Making the Unread Rows Bold

React's docs recommend `style` only for values that depend on data, values you do not know ahead of time. For everything else, a CSS class with `className` works better.

Our bold row depends on data: it is bold only while `email.unread` is `true`. So `style` is the right tool here, with a conditional operator inside the object:

```jsx title="src/EmailRow.jsx" startLine="1"
export default function EmailRow({ email, onOpen }) {
  return (
    <li
      ~style~={{ fontWeight: email.unread ? 'bold' : 'normal' }} // Bold while unread, normal once read
      onClick={() => onOpen(email.id)} // Asks Inbox to mark this email as read
    >
      {email.subject}
    </li>
  );
}
```

When the page opens, the two unread rows are bold. After the user clicks **Get your next month for $0.99**, only **Your order has shipped** stays bold. The Elements panel shows it best, because React writes the object on each row as a `style` attribute with a string of CSS:

```dom
<ul>
+ <li style="font-weight: bold;">Get your next month for $0.99</li>
+ <li style="font-weight: bold;">Your order has shipped</li>
  <li style="font-weight: normal;">Welcome to the team</li>
</ul>
```
:::

So the browser still gets its string of CSS in the end. React builds that string for you, from your object.

## PRINCIPLE | `<title>` inside a component: React places it in the document head

> [!PRINCIPLE]
> **Principle 3: Hoisting: React Places a `<title>` from Any Component in the Head**
>
> *Render `<title>`, `<meta>`, and `<link>` from the component that knows the data; React places them in the document `<head>`, and only one `<title>` may be rendered at a time.*
>
> In React 19, a resource and metadata component lands in the document head, wherever it sits in the component tree. So the inbox, which knows the unread count, can own the title of the tab. React leaves a `<title>` in place only inside an `<svg>` or with an `itemProp` prop. Two titles in the head give undefined behavior in browsers and search engines.
>
> **DO THIS:**
> ```jsx
> function Inbox() {
>   return <main>~<title>Inbox</title>~<h1>Inbox</h1></main>; // React places the title in the head
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Settings() {
>   return <section>~<title>Settings</title>~</section>; // **WRONG:** a second title on the same screen as Inbox
> }
> ```

Everything a component returns normally lands inside `<div id="root">`, where React renders the app (Lesson 07). The `<title>` is the exception. Here is a component that returns a `<title>` and an `<h1>`, side by side inside the same div:

```jsx title="A title and a heading inside the same div"
function Inbox() {
  return (
    <div>
      ~<title>Inbox</title>~ {/* React places this one in the document head */}
      ~<h1>Inbox</h1>~ {/* React places this one where it is written */}
    </div>
  );
}
```

The two tags sit next to each other in the code. In the DOM, they end up far apart:

```dom caption="The Elements panel: React places the h1 inside the root div, and the title inside the head."
<head>
  <meta charset="UTF-8">
+ <title>Inbox</title> | note: Placed in the head by React
</head>
<body>
  <div id="root">
    <div>
+     <h1>Inbox</h1> | note: Placed where Inbox wrote it
    </div>
  </div>
</body>
```

Here is what happens:
1. React renders `Inbox`, which returns the title and the heading inside the same `<div>`.
2. React places the `<h1>` inside that div, inside the root `<div>`.
3. React sees a `<title>`, and places its DOM node in the document `<head>` instead.
4. The browser reads the `<title>` in the head, and the tab shows `Inbox`.

Why? React's docs say that the `<head>` is the only valid place for a `<title>` in the DOM. So React puts it there for you, wherever the component writes it.

> [!DEFINITION]
> **What does it mean that React hoists a tag?** [NEW] To hoist means to lift, the way a crane lifts a load from the ground to the top floor. The React 19 announcement uses this word for a `<title>`, `<meta>`, or `<link>` that a component renders deep in the tree: React lifts its DOM node out of the component's place and puts it in the document head (Lesson 83).

### Which Tags React Moves to the Head

The `<title>` belongs to the third group, the **resource and metadata components**. This group has five tags: title, meta, link, script, and style. They describe the whole document, not one part of the screen. React's docs say you can render a `<title>` from any component, and React will always place its DOM node in the head.

This is the point of the feature: the component that knows the data owns the tag. Only `Inbox` knows how many emails are unread, so `Inbox` renders the title.

A `<meta>` tag works the same way: React places it in the head too. It must have exactly one of four props, such as `name` or `charset`. The other two are `httpEquiv` and `itemProp`. Lesson 121 covers the metadata for each page of a site.

React leaves a tag where it is written in two cases:
1. **A `<title>` inside an `<svg>`.** There it is a label for the graphic, which screen readers read.
2. **A tag with an `itemProp` prop.** There it describes one part of the page, not the whole document.

### Keep One Title at a Time

React's docs warn: render only one `<title>` at a time. Suppose a settings panel on the same screen also renders a `<title>`. React places both in the head. Then, in the words of React's docs, "the behavior of browsers and search engines is undefined".

The same holds for the `<title>` that `index.html` already has. A new Vite project starts with one in its head. Once `Inbox` renders its own title, delete the one in `index.html`, so the head holds only one.

### Adding the Title to the Inbox

`Inbox` now counts the unread emails during each render, from the emails in state. For now, it renders a fixed title, `Inbox`, above the heading:

```jsx title="src/Inbox.jsx" startLine="10"
export default function Inbox() {
  const [emails, setEmails] = useState(initialEmails);
  const ~unreadCount~ = emails.filter(e => e.unread).length; // 2 when the page opens

  function handleOpen(id) {
    setEmails(emails.map(e => (e.id === id ? { ...e, unread: false } : e)));
  }

  return (
    <main>
      ~<title>Inbox</title>~ {/* React places it in the head, and the tab reads Inbox */}
      <h1>Inbox</h1>
```

The page looks the same as before, and the tab now reads `Inbox`. Principle 4 adds the count to it.

```tree dir=right caption="How a title written inside Inbox reaches the browser tab."
How `<title>Inbox</title>` reaches the browser tab
- +1. Our code [`<title>` inside `<main>`] | `Inbox` returns the title **next to the heading**
- +2. React [`<head>`] | React sees a resource and metadata component | Places its DOM node **in the document head**
- +3. The browser [the tab] | The browser reads the title in the head | The tab reads **Inbox**
```

## PRINCIPLE | `<title>` children: one string, built with a template literal, or the tab loses its count

> [!PRINCIPLE]
> **Principle 4: One String: A `<title>` Takes Exactly One String as Its Child**
>
> *Give `<title>` one string as its only child, and build it with a template literal.*
>
> Text and a value in curly braces between two tags become separate children, so `Inbox ({unreadCount})` gives an array of three. An `<h1>` shows that array as one text, but a `<title>` must receive one string, so the tab does not get the count. A template literal builds the whole text first, so the title receives one string.
>
> **DO THIS:**
> ```jsx
> <title>~{`Inbox (${unreadCount})`}~</title> // One string: the tab reads Inbox (2)
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <title>~Inbox ({unreadCount})~</title> // **WRONG:** three children, so the tab does not show the count
> ```

The tab must read `Inbox (2)`. The natural way is to write the count in curly braces between the text, as in any other tag:

```jsx title="The same text and count in an h1 and in a title"
<h1>~Inbox ({unreadCount})~</h1> {/* Shows Inbox (2) on the page */}
<title>~Inbox ({unreadCount})~</title> {/* **WRONG:** the title does not get one string */}
```

Both tags hold the same text and the same curly braces. But only one works. The `<h1>` shows `Inbox (2)` on the page without a problem. The `<title>` does not show the count in the tab, and React's docs say plainly that this shape causes an error.

The reason is a rule from React's docs: the children of a `<title>` must be one single string of text. An `<h1>` accepts any number of children. A `<title>` accepts one.

### Why the Text Between the Tags Is Not One String

To your eyes, `Inbox ({unreadCount})` is one piece of text. To JSX, it is three pieces:
1. The text `Inbox (` before the curly braces.
2. The value of `unreadCount`, which is `2`.
3. The text `)` after the curly braces.

Each piece becomes its own child, and several children arrive as an array in `props.children` (Lesson 09). So the `<title>` receives an array of three pieces: two strings, with the number 2 between them.

The `<h1>` puts the three pieces side by side on the page, so they look like one text. A `<title>` cannot do that. It must receive one string, and an array is not a string.

```tree caption="Text and a value in curly braces side by side give three children, and a title accepts only one."
What `<title>` receives as its children
- !Text and curly braces side by side | The text before, the count, and the text after become **three children** in an array | The tab does **not** get the count
- +One template literal inside curly braces | The backticks build **one string** with the count inside | The tab shows the **unread count**
```

### Building One String with a Template Literal

The fix is to build the whole text as one string before it reaches the `<title>`. React's docs call this **string interpolation**: putting a value inside a string.

In JavaScript, you write it with a template literal:

```js title="A template literal"
const name = 'John';
const greeting = ~`Hello ${name}`~; // The one string 'Hello John'
```

> [!DEFINITION]
> **What is a template literal?** [NEW] A template literal is a JavaScript string written between backticks instead of quotes. Inside it, a dollar sign and curly braces put a value into the text, so the line above gives the one string `'Hello John'`. The result is always one string, however many values you put inside (Lesson 83).

Here is the title with one string:

```jsx title="The title with one string"
<title>~{`Inbox (${unreadCount})`}~</title> {/* Builds Inbox (2) as one string */}
```

Read it from the inside out. Inside the curly braces, the backticks build the string `'Inbox (2)'` first. Then the `<title>` receives that one string as its only child.

```jsx title="src/Inbox.jsx" startLine="18"
  return (
    <main>
      <title>~{`Inbox (${unreadCount})`}~</title> {/* The tab reads Inbox (2), then Inbox (1) */}
      <h1>Inbox</h1>
```

When the page opens, the tab reads `Inbox (2)`. Then the user clicks **Get your next month for $0.99**:
1. `handleOpen` updates the emails in state.
2. React renders `Inbox` again, and `unreadCount` is now 1.
3. React updates the title in the head, and the tab reads `Inbox (1)`.

::: row caption="The head of the page before and after the user clicks the first email."
::: col title="Before the click" tone=good
```dom
<head>
+ <title>Inbox (2)</title>
</head>
```
:::
::: col title="After the click on the first email" tone=good
```dom
<head>
+ <title>Inbox (1)</title>
</head>
```
:::
:::

The heading keeps its plain text, `Inbox`. The unread count lives in the tab, where the user sees it even while working in another tab.

## PRINCIPLE | `precedence` on a stylesheet `<link>`: one copy in the head, and React waits for it to load

> [!PRINCIPLE]
> **Principle 5: Stylesheet Links: `precedence` Puts One Copy of the Link in the Head for Every Row**
>
> *Write `precedence` on a stylesheet `<link>` rendered from a component, so React places one copy in the head, ranks it, and waits for it to load.*
>
> With `precedence`, React de-duplicates the links by `href`, so three rows give one `<link>` in the head, and it waits for the stylesheet before it shows the rows. Without `precedence`, the link is an ordinary tag: each row keeps its own copy, and React neither ranks it nor waits for it. The props `onLoad`, `onError`, and `disabled` turn the special treatment off.
>
> **DO THIS:**
> ```jsx
> <link rel="stylesheet" href="/email-row.css" ~precedence="default"~ /> // One copy in the head for every row
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <link rel="stylesheet" ~href="/email-row.css"~ /> // **WRONG:** no precedence, so every row keeps its own copy
> ```

Each email row needs a thin border below it. That rule lives in a stylesheet, `email-row.css`, in the public folder. React's docs leave it to you how a CSS file reaches the page. Developers choose between two ways:
1. **Import the CSS file in JavaScript.** The build tool, here Vite, puts it in the page. This is the usual way in a Vite app.
2. **Render a `<link>` inside the component that needs the stylesheet.** This is new in React 19. It keeps each stylesheet next to the component that depends on it, so a reader of `EmailRow` sees its styles right there.

This principle is about the second way: `EmailRow` renders the `<link>` itself.

### The Same Link With and Without `precedence`

Here is the same link inside `EmailRow`, once with a `precedence` prop and once without it:

```jsx title="The stylesheet link with precedence, and without it"
<link rel="stylesheet" href="/email-row.css" ~precedence="default"~ /> {/* React manages it: one copy in the head */}
<link rel="stylesheet" href="/email-row.css" /> {/* An ordinary tag: it stays inside each row */}
```

Both lines link the same stylesheet, from the same row. But one prop decides whether React manages the stylesheet.

> [!DEFINITION]
> **What is `precedence`?** [NEW] `precedence` is a prop on a stylesheet `<link>` that tells React where to rank it among the other stylesheets in the head. The rank matters, because when two stylesheets set the same rule, the one that comes later in the head wins. The value is a name you choose, such as `"default"` or `"high"`, and React treats the names it finds first as lower and the names it finds later as higher (Lesson 83).

With `precedence`, React does three things for the stylesheet:
1. **It places the link in the head**, ranked among the other stylesheets.
2. **It keeps one copy.** When several components render a link with the same `href`, React puts a single `<link>` in the DOM. React's docs call this **de-duplication**: removing the extra copies of the same thing.
3. **It waits for the stylesheet to load** before it shows the component that rendered it. So the user never sees the rows without their border. React waits by suspending the component (Lesson 69).

Without `precedence`, React's docs say there is no special behavior. The `<link>` is an ordinary tag, and React leaves it where the component wrote it.

### Three Rows, One Link in the Head

Here is the stylesheet, and `EmailRow` with the link inside its `<li>`:

```css title="public/email-row.css"
li {
  border-bottom: 1px solid #ddd;
  padding: 8px 0;
}
```

```jsx title="src/EmailRow.jsx" startLine="1"
export default function EmailRow({ email, onOpen }) {
  return (
    <li
      style={{ fontWeight: email.unread ? 'bold' : 'normal' }}
      onClick={() => onOpen(email.id)}
    >
      <link rel="stylesheet" href="/email-row.css" ~precedence~="default" /> {/* Every row asks for the same stylesheet */}
      {email.subject}
    </li>
  );
}
```

Our inbox renders three rows, so three components render the same link. You might expect three links, one inside each row. React puts a single link in the head instead:
1. Each of the three `EmailRow` components returns the same `<link>`.
2. React sees `rel="stylesheet"` together with `precedence`, so it manages the link.
3. React finds three links with the same `href`.
4. React puts one stylesheet `<link>` in the head, and none inside the rows.
5. React also adds a `<link rel="preload">` for the same file, which tells the browser to start the download early.

```dom caption="With precedence: one stylesheet link in the head for three rows, and no link inside any row."
<head>
+ <link rel="stylesheet" href="/email-row.css" data-precedence="default"> | note: One copy for three rows
  <meta charset="UTF-8">
  <link rel="preload" as="style" href="/email-row.css">
  <title>Inbox (2)</title>
</head>
<body>
  <div id="root">
    <main>
      <h1>Inbox</h1>
      <label for="search">Search mail</label>
      <input id="search" class="search">
      <ul>
        <li style="font-weight: bold;">Get your next month for $0.99</li>
        <li style="font-weight: bold;">Your order has shipped</li>
        <li style="font-weight: normal;">Welcome to the team</li>
      </ul>
    </main>
  </div>
</body>
```

Now remove `precedence`. React gives the link no special treatment. Each row keeps its own `<link>` inside its `<li>`, and React neither ranks the stylesheet nor waits for it:

```dom caption="Without precedence: each row keeps its own copy of the link, inside the li."
<ul>
! <li style="font-weight: bold;"><link rel="stylesheet" href="/email-row.css">Get your next month for $0.99</li>
! <li style="font-weight: bold;"><link rel="stylesheet" href="/email-row.css">Your order has shipped</li>
! <li style="font-weight: normal;"><link rel="stylesheet" href="/email-row.css">Welcome to the team</li>
</ul>
```

Three more props turn the special treatment off, even with `precedence`:
1. `onLoad`
2. `onError`
3. `disabled`

These props say that your code manages the loading itself, so React steps aside. With `onLoad` or `onError`, React also prints an error in the Console that names the prop.

```tree caption="The same stylesheet link with and without precedence: React manages only the link with precedence."
The same `<link rel="stylesheet">` inside `EmailRow`
- +With `precedence` [`precedence="default"`] | React places **one copy in the head**, ranked among the stylesheets | React **waits for it to load** before it shows the rows
- !Without `precedence` [`rel` and `href` only] | An **ordinary tag**: each row keeps its own copy | React neither ranks it **nor waits** for it
```

### Four More Facts About Managed Links

A few more facts come up in interviews:
1. React ignores changes to the props of the link after it has been rendered, and the Console says nothing about it.
2. React may leave the link in the head even after every row that rendered it is gone.
3. Two more tags get the same treatment. A `<style>` tag with an `href` and a precedence is managed like the link. A `<script>` tag with `async` and a source address is de-duplicated by that address.
4. React's `preinit` starts loading a stylesheet even before its first render. Lesson 84 covers it.

### The Complete Inbox

Here is the whole project. The HTML page holds no `<title>` of its own, because `Inbox` renders the only one:

```html title="index.html"
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
```

```jsx title="src/main.jsx"
import { createRoot } from 'react-dom/client';
import Inbox from './Inbox.jsx';

createRoot(document.getElementById('root')).render(~<Inbox />~); // 1. React renders Inbox first
```

```jsx title="src/Inbox.jsx"
import { useState } from 'react';
import EmailRow from './EmailRow.jsx';

const initialEmails = [
  { id: 0, subject: 'Get your next month for $0.99', unread: true },
  { id: 1, subject: 'Your order has shipped', unread: true },
  { id: 2, subject: 'Welcome to the team', unread: false },
];

export default function Inbox() {
  const [emails, setEmails] = useState(initialEmails);
  const unreadCount = emails.filter(e => e.unread).length;

  function handleOpen(id) {
    setEmails(emails.map(e => (e.id === id ? { ...e, unread: false } : e)));
  }

  return (
    <main>
      <title>~{`Inbox (${unreadCount})`}~</title> {/* Principles 3 and 4: one string, placed in the head */}
      <h1>Inbox</h1>
      <label ~htmlFor~="search">Search mail</label> {/* Principle 1: htmlFor, the DOM's name for for */}
      <input id="search" ~className~="search" /> {/* Principle 1: className, the DOM's name for class */}
      <ul>
        {emails.map(email => (
          ~<EmailRow~ key={email.id} email={email} onOpen={handleOpen} /> // 2. React renders one EmailRow per email
        ))}
      </ul>
    </main>
  );
}
```

```jsx title="src/EmailRow.jsx"
export default function EmailRow({ email, onOpen }) {
  return (
    <li
      ~style~={{ fontWeight: email.unread ? 'bold' : 'normal' }} // Principle 2: an object with a camelCase name
      onClick={() => onOpen(email.id)}
    >
      <link rel="stylesheet" href="/email-row.css" ~precedence~="default" /> {/* Principle 5: one copy in the head */}
      {email.subject}
    </li>
  );
}
```

```css title="public/email-row.css"
li {
  border-bottom: 1px solid #ddd;
  padding: 8px 0;
}
```

### How React Renders the Inbox, and Where Each Node Lands

When the page opens, React renders `Inbox` first, then one `EmailRow` for each of the three emails. Most nodes land inside `<div id="root">`. The title and the stylesheet link land in the head:

```tree caption="The order in which React renders the components, and where each node lands in the DOM."
`main.jsx` renders `<Inbox />` | React renders **Inbox first**
- +`Inbox` [1. Rendered first] | Counts **2 unread emails** | The title goes to the **head**; the heading, the label, and the field go inside the root
  - +`EmailRow` for the first email [2. Rendered second] | A **bold** `<li>` inside the root | Its stylesheet link goes to the **head**
  - +`EmailRow` for the second email [3. Rendered third] | A **bold** `<li>` inside the root | The same link: **no second copy**
  - +`EmailRow` for the third email [4. Rendered fourth] | A **normal** `<li>` inside the root | The same link: **no third copy**
```

| Aspect | The Raw HTML Habit | The React Rule |
| :--- | :--- | :--- |
| **Names** | `class`, `for`, `tabindex`, which make the Console ask for other names | The DOM's names `className`, `htmlFor`, `tabIndex`; `aria-*` and `data-*` keep their dashes |
| **Style** | A string of CSS such as `"font-weight: bold"`, which blanks the whole page | An object with camelCase names, such as `{ fontWeight: 'bold' }`, for styles that depend on data |
| **Title** | A fixed title in `index.html`, or `document.title` set in an Effect | A `<title>` rendered by the component that knows the data, placed in the head by React, one at a time |
| **Title text** | Text and curly braces side by side, which give an array, and the tab loses the count | One string, built with a template literal |
| **Stylesheet** | A `<link>` without `precedence`, which every row keeps a copy of | A `<link>` with `precedence`: one copy in the head, ranked, and waited for |

Remember the one idea of this lesson. **A tag in JSX is not HTML. It is a description that React turns into a DOM node, so it speaks the language of the DOM, and React decides where the node goes.**

## For the Interview

> **The Interview Question:** How do React's built-in HTML components differ from raw HTML?

### How to Answer Clearly in 30 Seconds

"In JSX, a tag like `<input>` or `<title>` is not HTML for the browser. It is a description that React reads, and React creates the DOM node. React's docs call these built-in browser components, and they differ from raw HTML in three ways:
1. **Names follow the DOM.** JSX attributes become keys of a JavaScript object, and `class` is a reserved word in JavaScript. So React uses the DOM property names: `className`, `htmlFor`, and camelCase such as `tabIndex`. Only `aria-*` and `data-*` keep their dashes.
2. **`style` takes an object**, like the DOM `style` property, with camelCase names. A number gets `px` unless the property is unitless.
3. **Some tags gained new powers in React 19.** A `<title>`, `<meta>`, or `<link>` rendered from any component lands in the document head. A stylesheet `<link>` with `precedence` is de-duplicated, ranked, and waited for. And the form components become controlled when you pass `value`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why did React rename `class` to `className` at all?"**
   Because JSX turns into JavaScript. Every attribute becomes a key of the props object, and components read those keys into variables. JavaScript names cannot contain dashes or be reserved words, and `class` is a reserved word. So React uses the names the DOM already uses in JavaScript, such as `element.className` and `label.htmlFor`. React still writes the usual HTML attribute on the node, so the Elements panel shows `class="search"`. When you paste `class` into JSX, the Console asks: "Did you mean `className`?"
2. **"Why does `<title>Inbox ({unreadCount})</title>` fail in the tab, when the same shape works in an `<h1>`?"**
   Because text and curly braces side by side become separate children. Here they become an array of three: `'Inbox ('`, the count, and `')'`. An `<h1>` shows the three pieces as one text. A `<title>` must receive one single string, and React's docs say this array causes an error. The fix is a template literal inside the curly braces, which builds the whole text as one string before it reaches the `<title>`.
3. **"Several components render the same stylesheet `<link>`. How many links end up in the DOM?"**
   With `precedence`, one. React de-duplicates the links by `href`, places that one copy in the head, and ranks it by its `precedence`. Then it waits for the stylesheet to load before it shows the components that depend on it. Without `precedence`, React gives the link no special treatment, so each component keeps its own copy where it wrote it. The props `onLoad`, `onError`, and `disabled` also turn the special treatment off.

```tree caption="Interview summary: what React does with a built-in tag beyond raw HTML."
What React adds to a built-in tag
- +Common components [`className` `htmlFor` `style`] | Names follow the **DOM**, and `style` is an **object** | React writes the usual **HTML attributes** on the node
- +Form components [`value` `onChange`] | Passing `value` makes the field **controlled** | Lesson 20 covers them
- +Resource and metadata components [`<title>` `<meta>` `<link>`] | React places them in the **head** from any component | A stylesheet link with `precedence` is **de-duplicated and waited for**
```
