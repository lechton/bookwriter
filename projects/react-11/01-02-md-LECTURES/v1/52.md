# Lecture 52: How Two Password Fields Get Their Own ids with useId

*(How can one component, placed twice on a form, connect each label to its own input field?)*

> INTERVIEW QUESTION | ❱❱ MORE | How do you generate IDs that are unique, stable, and safe across server and client?

---

## VS | An id written by hand vs. `useId`: the same id in every copy, or a different id for each copy

> In plain HTML, you connect a label to its `<input>` field with an id that you write by hand, and it works because that field appears once on the page. **In React, one component can appear many times on the same page, so it asks React for its id with `useId`, and React gives every copy a different string.** An id written by hand repeats in every copy, and an id from `Math.random()` differs between the server and the browser.

Remember how a label works in plain HTML? You give the `<input>` field an `id`. Then the `<label>` names that same id in its `for` attribute:

```html title="Plain HTML: one label, one input field, one id"
<label for="email">Email</label>
<input ~id="email"~ /> <!-- The label above names this id -->
```

The id connects the two, and the user feels it in two ways. A click on the word `Email` puts the cursor in the field. And a screen reader says `Email` when the user reaches the field.

> [!DEFINITION]
> **A screen reader.** [REVIEW] A screen reader is a program that reads the page aloud for users who cannot see it. When the user reaches an `<input>` field, the screen reader reads the label connected to that field, so the user knows what to type. Programs like this one are called assistive technology (Lesson 20).

In JSX, it is the same pair with one change. You write `htmlFor` in place of `for`. The reason: `for` is a word of JavaScript (Lesson 02):

```jsx title="The same pair in JSX"
<label ~htmlFor="email"~>Email</label> {/* htmlFor in JSX becomes for in the HTML */}
<input id="email" />
```

Now here is the problem. In plain HTML, you write each field once, so you know its id appears once. In React, you write a component once, and then you place its tag as many times as you like. Every copy runs the same code. So an id written by hand inside the component, such as `id="password"`, appears in every copy.

The fix is one line. You stop writing the id yourself, and you ask React for it:

```jsx title="Asking React for an id"
const id = ~useId()~; // React returns a different string for each copy of the component
return <input id={id} />;
```

> [!DEFINITION]
> **useId.** [NEW] `useId` is a React Hook, imported from `react` like `useState`. It takes no arguments and returns one string, such as `_r_0_`. Each copy of the component gets a different string, and the copy keeps its string for as long as it stays on the page. You pass that string to the `id` of an element and to the `htmlFor` or `aria-` attribute that points at it. The server and the browser make the same string, which matters as soon as a server renders the page first (Lesson 52).

### A sign-up form with two password fields

Take the sign-up form of almost any website. It asks for the password twice, once in a `Password` field and once in a `Confirm password` field. Under each field sits the same hint:

```page caption="The sign-up form: two password fields, each with its label and its hint."
heading: Create account
form:
  field: Password
line: The password should contain at least 18 characters
form:
  field: Confirm password
line: The password should contain at least 18 characters
```

The two fields look the same and behave the same. So at work, nobody writes them twice by hand. They come from one component, `PasswordField`, placed twice on the form.

Ask yourself: `PasswordField` is written once and appears twice, so where do its two different ids come from? The component cannot know how many copies of it are on the page. React knows, because React places every copy. So each copy calls `useId`, and React gives each copy its own string.

**Why:** Developers try three ways to fill this id, and two of them break:
1. **With the id written by hand**, every copy repeats it. Both fields carry `id="password"`, so a click on the words `Confirm password` puts the cursor in the first field.
2. **With `Math.random()`**, each copy gets its own number, so the form works in the browser. But when a server renders the page first, as in Lesson 46, the server picks one number and the browser picks another. React reports an error.
3. **With `useId()`**, each copy gets its own string, and the server and the browser make the same string.

Here are the three ways side by side, each in the one line where they differ:

```jsx title="Three ways to fill the id inside PasswordField"
const id = ~'password'~; // 1. Written by hand: the same string in every copy
const id = ~'field-' + Math.random()~; // 2. A random number: a new one every time the component runs
const id = ~useId()~; // 3. Asked from React: one per copy, the same on the server and in the browser
```

All three put one value into both the label's `htmlFor` and the field's `id`, so inside one copy all three work. **It may look the same, or work the same at first, but it is NOT the same thing!** The difference shows only when the page has two copies, or when a server renders the page.

```tree caption="Three ways to fill the id of PasswordField, and where each one breaks."
Three ways to fill the id of `PasswordField`
- !Written by hand [`'password'`] | Works with **one copy** on the page | With two copies, **both fields share one id**, and the second label reaches the first field
- !A random number [`Math.random`] | Works in an app that runs **only in the browser** | With server rendering, **the server and the browser pick two different numbers**
- +Asked from React [`useId`] | **A different id for each copy** | **The same id** on the server and in the browser
```

Remember the one sentence of this lesson. **A component never writes its own id. It asks React with `useId`, because only React knows where each copy sits on the page.**

### What a wrong id costs the user

A wrong id breaks the form for the user, while the form looks fine to the developer:
1. **The user types into the wrong field.** With the id written by hand, the user clicks the words `Confirm password`, and the cursor lands in the `Password` field. Everything the user types next goes there.
2. **The second field loses its label.** The browser connects both labels to the first field. A screen reader user who reaches the second field hears no name for it.
3. **The server's page and the browser's page disagree.** With `Math.random()` and server rendering, React reports an error in the Console. react.dev says what such a difference can cost: "In the best case, they'll lead to a slowdown; in the worst case, event handlers can get attached to the wrong elements." For the user, the worst case is a click that runs the code meant for another element.

### The Rule of Thumb: every id inside a component comes from `useId`

**When a component puts an id on an element, and a label or an `aria-` attribute points at that id, get the id from `useId`. Never write it by hand, and never build it from `Math.random()` or a counter.**

Does every label need an id? No. Developers choose between three ways to connect a label to its field:
1. **Put the field inside the label.** The label wraps its own field, so it needs no id. react.dev: "Typically, you will place every `<input>` inside a `<label>` tag." This covers the label only. A hint that the field points at still needs an id, as the code below shows. MDN also advises the `htmlFor` and `id` pair, because not every assistive technology understands a label wrapped around its field.
2. **Write the id by hand.** It fits only a part of the page that appears once. react.dev calls it "not a good practice in React".
3. **Ask React with `useId()`.** It fits every component that can appear more than once, and every app that renders on the server. react.dev: "To avoid conflicts between multiple instances of one component, generate such an ID with `useId`."

```jsx title="The field inside the label: the label needs no id, but the hint still does"
<label>
  Password
  <input type="password" ~aria-describedby="password-hint"~ /> {/* The hint is reached only by its id */}
</label>
```

Our form has a hint under each field, so this lesson uses the `htmlFor` and `id` pair.

A senior developer also knows the three classic mistakes:
1. **Writing `id="password"` inside a component**, as in plain HTML, and testing the page with one copy of it. react.dev warns that "hardcoding IDs like this is not a good practice in React."
2. **Fixing it with `Math.random()` or a counter.** The page works in the browser, so the component ships to an app that renders on the server.
3. **Using `useId` to make the keys of a list**, because it "makes ids". react.dev says keys come from your data. The interview part at the end explains why.

## SECTION | The Create Account Form

Our example is the sign-up form from the screen above. It has two files:

```files title="signup-form: File Explorer" caption="The files of our sign-up form."
src/
  App.jsx | page | Exports `App` as default: the title and two `PasswordField` tags
  PasswordField.jsx | field | Exports `PasswordField` as default: the label, the password field, and the hint
```

`App` places the same component twice, with a different `label` prop on each tag:

```jsx title="src/App.jsx"
import PasswordField from './PasswordField.jsx';

export default function App() {
  return (
    <form>
      <h1>Create account</h1>
      ~<PasswordField label="Password" />~ {/* 1st copy */}
      ~<PasswordField label="Confirm password" />~ {/* 2nd copy */}
    </form>
  );
}
```

The App file stays the same for the whole lesson. Only the `PasswordField` file changes, one step in each principle. In Principle 4, the form moves to an app that renders on the server, and two more files appear there.

**PRINCIPLES:** A label and its field share one id, and that id must be unique on the whole page. Four principles follow:
1. **Principle 1: An id written by hand repeats in every copy.** The browser connects every label with that `htmlFor` to the first field only.
2. **Principle 2: `useId` gives each copy its own id.** Call it once, at the top level of the component, and pass its string to both `htmlFor` and `id`.
3. **Principle 3: One `useId` call names the field and its hint.** Add a different ending to the one string for each element, such as `id + '-hint'`.
4. **Principle 4: `Math.random` gives the server and the browser two ids.** With server rendering, the component runs twice, and only `useId` makes the same string both times.

## PRINCIPLE | `id="password"` inside a component: every copy repeats the same id

> [!PRINCIPLE]
> **Principle 1: An id Written by Hand Repeats in Every Copy**
>
> *An id written by hand inside a component appears once for every copy of the component, and the browser connects every label with that `htmlFor` to the first element only.*
>
> An id must be unique on the whole page. A component is written once, but React runs it once for every tag, so a fixed id appears once for every copy. When two fields share one id, a click on the second label puts the cursor in the first field, and the second field has no label for a screen reader. React prints no error.
>
> **DO THIS:**
> ```jsx
> function PasswordField({ label }) {
>   const id = ~useId()~; // A different id for each copy, as Principle 2 shows
>   return (
>     <div>
>       <label htmlFor={id}>{label}</label>
>       <input type="password" id={id} />
>     </div>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function PasswordField({ label }) {
>   return (
>     <div>
>       <label htmlFor="password">{label}</label>
>       <input type="password" ~id="password"~ /> {/* **WRONG:** two copies give two fields with one id */}
>     </div>
>   );
> }
> ```

### Two elements with one id

Here is a label and a field, as in plain HTML, and then the same pair written a second time:

```jsx title="The same label and field written twice"
<label htmlFor="name">Name</label>
<input ~id="name"~ /> {/* 1st field: the label above reaches it */}
<label htmlFor="name">Name</label>
<input ~id="name"~ /> {/* **WRONG:** 2nd field with the same id: the label above reaches the 1st field */}
```

A click on the second `Name` puts the cursor in the first field. Why? Because an id names one element on the whole page. MDN says an id "must be unique within the entire document". When two elements share one id, a label looks only for the first one. MDN: "The first element in the document with an `id` attribute matching the value of the `for` attribute is the labeled control."

Nobody writes the same pair twice by hand. A component does it for us, every time we place its tag twice.

### The hint and `aria-describedby`

Our password field needs one more connection: its hint. A screen reader reads the label of the field, but it does not read the hint line below it on its own. The field has to say which element describes it.

> [!DEFINITION]
> **aria-describedby.** [NEW] `aria-describedby` is an attribute on a field, and it holds the `id` of the element that describes the field, such as a hint. When a screen reader reaches the field, it reads the label first, and then the text of that element. Like every `aria-` attribute, it keeps its dashes in JSX (Lesson 02).

```jsx title="A field connected to its label and to its hint"
<label htmlFor="password">Password</label>
<input type="password" id="password" ~aria-describedby="password-hint"~ /> {/* Points at the hint by its id */}
<p ~id="password-hint"~>The password should contain at least 18 characters</p> {/* The hint that describes the field */}
```

So each password field needs two ids: one for the field, and one for its hint.

### `PasswordField` with the ids written by hand

Here is our first `PasswordField`. It copies those three tags from plain HTML, ids included:

```jsx title="src/PasswordField.jsx" bad="5,6"
export default function PasswordField({ label }) {
  return (
    <div>
      <label htmlFor="password">{label}</label>
      <input type="password" ~id="password"~ aria-describedby="password-hint" /> {/* **WRONG:** the same id in every copy */}
      <p ~id="password-hint"~> {/* **WRONG:** the same hint id in every copy */}
        The password should contain at least 18 characters
      </p>
    </div>
  );
}
```

With one `PasswordField` on the form, this component works. With two, it does not. The code is the same in both cases. With one copy, the id `password` names one field. With two copies, it names two fields, and the label finds only the first.

### The form looks right, and the second label reaches the first field

**Beware! The form looks perfect, and React prints nothing, yet the second label sends the user to the first field.** Here is what happens, in order:
1. React runs `PasswordField` once for each tag in `App`, as in Lesson 04. Each run returns the same ids. So the page now has two fields with `id="password"` and two hints with `id="password-hint"`.
2. The page shows two labels, two fields, and two hints, as written. The Console shows no error.
3. The user clicks the words `Confirm password`.
4. The browser looks for the first element with `id="password"`. It finds the `Password` field and puts the cursor there.
5. The user types the password. It lands in the `Password` field, and the `Confirm password` field stays empty.


The same rule breaks the screen reader. The browser connects both labels to the first field. So the first field gets two labels, and the second field gets none. A screen reader user who reaches the `Confirm password` field hears no name for it.

### Why this bug reaches the users

This bug starts with a component that works. A developer copies a label and a field from plain HTML into a component, with `id="password"`, and tests the form with one copy. The label works. Later, a teammate places the component a second time, for `Confirm password`, and the page still looks right.

React gives no warning, because a duplicate id is not a React error. React passes the attribute to the browser exactly as written. So nobody finds the bug until a user reports it.

MDN names the cause: an id "must be unique in the whole document. This is hard especially in a componentized application." Its next sentence points at the fix: "Frameworks often provide their own solutions, such as React's `useId()`".

## PRINCIPLE | useId: each copy of the same component gets its own id

> [!PRINCIPLE]
> **Principle 2: useId Gives Each Copy of a Component Its Own id**
>
> *Call `useId()` at the top level of the component, and pass the one string it returns to both `htmlFor` and `id`; every copy of the component gets a different string.*
>
> A component cannot write its id by hand, because it does not know how many copies of it are on the page. React does. `useId` returns a string made from the place where this copy sits on the page. So the label and the field of one copy match, and two copies never clash. The string is not meant to be read, and it changed between React versions, so your code never depends on it.
>
> **DO THIS:**
> ```jsx
> function PasswordField({ label }) {
>   const id = ~useId()~; // One string for this copy
>   return (
>     <div>
>       <label htmlFor={id}>{label}</label>
>       <input type="password" id={id} />
>     </div>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {labels.map((label) => {
>   const id = ~useId()~; // **WRONG:** a Hook inside map breaks the Rules of Hooks
>   return <input key={label} id={id} />;
> })}
> ```

### The smallest component with `useId`

Here is the smallest component that asks React for its id:

```jsx title="NameField.jsx"
import { useId } from 'react';

function NameField() {
  const id = ~useId()~; // A new string for each copy of NameField
  return (
    <>
      <label htmlFor={id}>Name</label>
      <input ~id={id}~ /> {/* The label above names this same string */}
    </>
  );
}
```

You import `useId` from `react`, like `useState` (Lesson 12). react.dev calls it a Hook "for generating unique IDs that can be passed to accessibility attributes". Accessibility attributes are attributes such as `aria-describedby`. In react.dev's words, they "let you specify that two tags are related to each other". A screen reader reads them to learn which label and which hint belong to a field.

react.dev says what you get back: a string that is "a unique ID string associated with this particular `useId` call in this particular component". Place `<NameField />` twice, and the two copies get two different strings.

Compare the pair written by hand with the pair built from `useId`:

```jsx title="The id written by hand vs. the id from useId"
<label htmlFor="name">Name</label><input ~id="name"~ /> {/* The same string in every copy */}
<label htmlFor={id}>Name</label><input ~id={id}~ /> {/* id holds the string useId returned for this copy */}
```

Inside one copy, **yes, it is the exact same thing!** In both lines, the label's `htmlFor` and the field's `id` hold one value, so the label reaches its field.

On a page with two copies, **it may look the same, but it is NOT the same thing!** The string `"name"` is written once, and it repeats in every copy. The string from `useId` is different in every copy.

```tree caption="An id written by hand vs. an id from useId: the same pair inside one copy, a different result on a page with two copies."
Where the id of `NameField` comes from
- +Inside one copy | `htmlFor` and `id` hold **one value** in both versions | The label **reaches its field** in both versions
- !Written by hand, two copies on the page [`"name"`] | The **same string** in every copy | The second label **reaches the first field**
- +From `useId`, two copies on the page [`useId`] | A **different string** for each copy | Each label **reaches its own field**
```

### `PasswordField` with `useId`

Now `PasswordField` asks React for its id. Two lines are new: the import, and the call at the top of the component. Then `"password"` becomes `{id}` in both places:

```jsx title="src/PasswordField.jsx" good="1,4,7,8"
import { useId } from 'react';

export default function PasswordField({ label }) {
  const id = ~useId()~; // 1. One string for this copy of PasswordField
  return (
    <div>
      <label ~htmlFor={id}~>{label}</label> {/* 2. The label names this copy's field */}
      <input type="password" ~id={id}~ aria-describedby="password-hint" /> {/* 3. The field carries the same string */}
      <p id="password-hint">
        The password should contain at least 18 characters
      </p>
    </div>
  );
}
```

The App file does not change. It still places `PasswordField` twice. React runs the first `PasswordField`, and `useId` returns one string. React runs the second, and `useId` returns another. The Elements panel shows both:

```dom caption="The Elements panel: each copy of PasswordField now carries its own id, made by React."
<form>
  <h1>Create account</h1>
  <div>
+   <label for="_r_0_">Password</label> | note: Matches the 1st field
+   <input id="_r_0_" aria-describedby="password-hint" type="password"> | note: 1st copy: one string
    <p id="password-hint">The password should contain at least 18 characters</p>
  </div>
  <div>
+   <label for="_r_1_">Confirm password</label> | note: Matches the 2nd field
+   <input id="_r_1_" aria-describedby="password-hint" type="password"> | note: 2nd copy: another string
!   <p id="password-hint">The password should contain at least 18 characters</p> | note: The hint still shares one id
  </div>
</form>
```

These strings look strange, and nobody wrote them. They are not meant to be read or typed. They only have to match inside one copy and differ between copies. Since React 19.2, the strings start with `_r_` in an app that runs only in the browser. Earlier versions of React started them differently, so your code must never depend on the exact string.

Now the user clicks the words `Confirm password`, and the browser puts the cursor into the second field:

```page caption="The form after the user clicks the words Confirm password and types: the text lands in the Confirm password field."
heading: Create account
form:
  field: Password

form:
  field: Confirm password | •••••••••••••••••• | good

console: quiet
```

One duplicate is left. Both hints still carry `id="password-hint"`, and Principle 3 fixes them.

### Where the string comes from

React makes the string from the place where the component sits on the page. react.dev: "`useId` is generated from the 'parent path' of the calling component." The parent path is the chain of components above the component. Here, it is `App`, and then the first or the second `PasswordField` tag inside it. The two copies sit at two different places under `App`, so their paths differ, and so do their strings.

The string also stays the same while the copy is on the page. react.dev: the id "is stable when a component is mounted". So, as long as this copy of `PasswordField` stays on the page, its label and its field keep the same string.

### `useId` at the top level, never inside `map`

Suppose a form builds its fields from an array with `map`. A developer gives each field its id by calling `useId()` inside `map`:

```jsx title="src/App.jsx" bad="5"
export default function App() {
  return (
    <form>
      {['Password', 'Confirm password'].map((label) => {
        const id = ~useId()~; // **WRONG:** a Hook called inside map breaks the Rules of Hooks
        return (
          <div key={label}>
            <label htmlFor={id}>{label}</label>
            <input type="password" id={id} />
          </div>
        );
      })}
    </form>
  );
}
```

`useId` is a Hook, so it follows the Rules of Hooks: call it at the top level of a component, never inside a loop or a condition (Lesson 38). react.dev: "You can't call it inside loops or conditions. If you need that, extract a new component and move the state into it."

That new component is exactly `PasswordField`. Each copy calls `useId` once, at its own top level, and `map` only places the tags:

```jsx title="src/App.jsx" good="4"
export default function App() {
  return (
    <form>
      {['Password', 'Confirm password'].map((label) => ~<PasswordField key={label} label={label} />~)} {/* Each copy calls useId once for itself */}
    </form>
  );
}
```

## PRINCIPLE | `id + '-hint'`: one useId call names the input field and its hint

> [!PRINCIPLE]
> **Principle 3: One useId Call Names the Field and Its Hint**
>
> *When one component needs several related ids, call `useId` once and add a different ending to its string for each element, such as `id + '-input'` and `id + '-hint'`.*
>
> A `useId` string is already unique to this copy of the component, so any ending added to it stays unique to this copy. Every id of the component comes from that one string: the field, the hint, and any other element that a label or an `aria-` attribute points at. An id left behind, written by hand, still repeats in every copy.
>
> **DO THIS:**
> ```jsx
> const id = useId();
> <input id={id + '-input'} ~aria-describedby={id + '-hint'}~ /> {/* Points at this copy's hint */}
> <p id={id + '-hint'}>The password should contain at least 18 characters</p>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const id = useId();
> <input id={id} ~aria-describedby="password-hint"~ /> {/* **WRONG:** every copy points at the first hint */}
> <p id="password-hint">The password should contain at least 18 characters</p>
> ```

### One call, several ids

Many components need more than one id. react.dev's own example is a form with a first name and a last name. It calls `useId` once, and adds a different ending for each field:

```jsx title="One useId call, two ids"
function Form() {
  const id = ~useId()~; // One string for this copy of Form
  return (
    <form>
      <label htmlFor={id + '-firstName'}>First Name:</label>
      <input ~id={id + '-firstName'}~ type="text" /> {/* The string, plus -firstName */}
      <label htmlFor={id + '-lastName'}>Last Name:</label>
      <input ~id={id + '-lastName'}~ type="text" /> {/* The same string, plus -lastName */}
    </form>
  );
}
```

The `+` joins two strings, as in Lesson 03. React gives only the start. The endings `-firstName` and `-lastName` come from our code, and they can be any strings we choose. react.dev calls the `useId` string used this way a shared prefix: one start shared by several related ids.

Compare it with calling `useId` once for each element:

```jsx title="Two useId calls vs. one useId call with two endings"
const inputId = ~useId()~; // 1st call: the id of the field
const hintId = ~useId()~; // 2nd call: the id of the hint
const id = ~useId()~; // One call instead: id + '-input' for the field, id + '-hint' for the hint
```

For the page and for the user, **yes, it is the exact same thing!** Both ways give the field and the hint two different ids. Both ways give the second copy ids that differ from the first copy's. A string from `useId` is already unique to this copy, so any ending added to it stays unique to this copy. react.dev: this "lets you avoid calling `useId` for every single element that needs a unique ID."

### The final `PasswordField`

In Principle 2, the field got its id from `useId`, but the hint kept `id="password-hint"`. Now the field and the hint both build their ids from the one string:

```jsx title="src/PasswordField.jsx" good="7,8,9"
import { useId } from 'react';

export default function PasswordField({ label }) {
  const id = ~useId()~; // One string for this copy of PasswordField
  return (
    <div>
      <label htmlFor={id + '-input'}>{label}</label>
      <input type="password" ~id={id + '-input'}~ ~aria-describedby={id + '-hint'}~ /> {/* The field, and the hint it points at */}
      <p ~id={id + '-hint'}~> {/* The hint, with an id of this copy only */}
        The password should contain at least 18 characters
      </p>
    </div>
  );
}
```

This is the final `PasswordField`. Nothing changes on the screen, because the hint text is the same in both copies. The change shows in the Elements panel, and in what a screen reader reads:

```dom caption="The Elements panel: each copy builds its two ids from one useId string."
<form>
  <h1>Create account</h1>
  <div>
+   <label for="_r_0_-input">Password</label>
+   <input id="_r_0_-input" aria-describedby="_r_0_-hint" type="password"> | note: 1st copy: one start, two endings
+   <p id="_r_0_-hint">The password should contain at least 18 characters</p>
  </div>
  <div>
+   <label for="_r_1_-input">Confirm password</label>
+   <input id="_r_1_-input" aria-describedby="_r_1_-hint" type="password"> | note: 2nd copy: another start
+   <p id="_r_1_-hint">The password should contain at least 18 characters</p>
  </div>
</form>
```

Inside each copy, two pairs match. The label's `for` matches the field's `id`. The field's `aria-describedby` matches the hint's `id`. Between the two copies, every id is different. So a screen reader on the second field now reads `Confirm password`, and then the second copy's own hint.

```tree caption="How one useId string becomes every id of one copy of PasswordField."
One `useId` string in each copy of `PasswordField` [`const id = useId`]
- +The field and its label [`id + '-input'`] | The label's `htmlFor` and the field's `id` | The label **reaches its own field**
- +The hint [`id + '-hint'`] | The field's `aria-describedby` and the hint's `id` | A screen reader reads **this copy's hint**
```

### The hint that was left behind

This mistake looks like a finished fix. A developer moves the field's id to `useId`, as in Principle 2, and forgets the hint. The labels work, so the page looks fixed.

But both hints still carry `id="password-hint"`, and both fields still point at it. The browser finds the first element with that id, which is the hint of the first field. On our form, both hints say the same words, so the user hears no difference today. The day a designer changes the second hint, a screen reader on the second field reads the first field's hint. One `useId` string for every id of the component prevents this.

## PRINCIPLE | Math.random: the server and the browser pick two different ids

> [!PRINCIPLE]
> **Principle 4: Math.random Gives the Server and the Browser Two ids**
>
> *With server rendering, the id in the server's HTML must equal the id React makes in the browser; `Math.random()` and a counter cannot promise that, and `useId` can, as long as both render the same tree.*
>
> With server rendering, every component runs twice: once on the server, and once again in the browser during hydration. `Math.random()` gives a new number each time, and a counter depends on the order in which the copies run. So the browser's ids differ from the server's, and React reports a hydration mismatch. `useId` builds its string from the parent path of the component, which is the same on both sides.
>
> **DO THIS:**
> ```jsx
> function PasswordField({ label }) {
>   const id = ~useId()~; // The same string on the server and in the browser
>   return <label htmlFor={id + '-input'}>{label}</label>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function PasswordField({ label }) {
>   const id = ~'field-' + Math.random()~; // **WRONG:** the server and the browser pick two different numbers
>   return <label htmlFor={id + '-input'}>{label}</label>;
> }
> ```

### A random id vs. an id from `useId`

A developer who sees the duplicate ids of Principle 1 often reaches for `Math.random()`, so that each copy gets a different id. Compare it with `useId`:

```jsx title="An id from Math.random vs. an id from useId"
const id = ~'field-' + Math.random()~; // A new number every time the component runs
const id = ~useId()~; // The same string every time this copy runs at the same place
```

In an app that runs only in the browser, both lines give each copy its own id, and both labels reach their fields. **It may look the same, or work the same at first, but it is NOT the same thing!** The difference shows as soon as a server renders the page. Then the component runs twice: once on the server, and once again in the browser.
- **With `Math.random()`**, the server picks one number, and the browser picks another. The two ids no longer match.
- **With `useId()`**, React builds the string from the parent path, not from chance. The server and the browser render the same tree, so they make the same string.

`Math.random()` during rendering also breaks the rule that a component gives the same result for the same inputs (Lesson 14). React's lint rule for pure components, `purity`, names this exact bug: `Math.random()` during render causes "bugs like hydration mismatches".

### The same form, rendered on a server

A framework can render a page on the server. The browser first shows that HTML, and then React attaches itself to it (Lesson 46).

> [!DEFINITION]
> **Hydration.** [REVIEW] The HTML from the server is only HTML: its buttons do nothing yet. When the JavaScript arrives, React runs the components again in the browser and attaches their event handlers to the HTML that is already on the page, instead of drawing it again. This step is called hydration (Lesson 46).

To see hydration without a real server, we do what react.dev's own live example does. Two files change:
1. **`index.html` holds the server's HTML.** We write the form inside `<div id="root">` by hand, exactly as a server would send it.
2. **`main.jsx` calls `hydrateRoot` in place of `createRoot`.** `hydrateRoot` attaches React to HTML that is already on the page, instead of drawing the page again.

In a framework app, we never write this call ourselves. react.dev: "If you use a framework, it might do this call for you."

```files title="signup-form: File Explorer" caption="The sign-up form as a server-rendered app: index.html already holds the form."
index.html | server HTML | Holds the form as the server rendered it, inside `<div id="root">`
src/
  main.jsx | boundary | Calls `hydrateRoot` on `#root` with `<App />`
  App.jsx | page | Unchanged: the title and two `PasswordField` tags
  PasswordField.jsx | field | The id comes from `Math.random`, then from `useId`
```

```jsx title="src/main.jsx"
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';

~hydrateRoot~(document.getElementById('root'), <App />); // Attaches React to the HTML already inside #root
```

Here is `PasswordField` built like the final one of Principle 3, with `Math.random()` in place of `useId()`:

```jsx title="src/PasswordField.jsx" bad="2"
export default function PasswordField({ label }) {
  const id = ~'field-' + Math.random()~; // **WRONG:** a new number on the server, another in the browser
  return (
    <div>
      <label htmlFor={id + '-input'}>{label}</label>
      <input type="password" id={id + '-input'} aria-describedby={id + '-hint'} />
      <p id={id + '-hint'}>
        The password should contain at least 18 characters
      </p>
    </div>
  );
}
```

The server ran this component once for each copy and wrote its numbers into the HTML. A server sends this HTML with no line breaks between the tags, so we keep it on one line. A line break inside `#root` would be one more piece of text that React does not expect. React would then report a different error and draw the whole form again in the browser. Here is the part of `index.html` that holds the form:

```html title="index.html"
<div id="root"><form><h1>Create account</h1><div><label for="field-0.7194028361928475-input">Password</label><input type="password" id="field-0.7194028361928475-input" aria-describedby="field-0.7194028361928475-hint"><p id="field-0.7194028361928475-hint">The password should contain at least 18 characters</p></div><div><label for="field-0.2381946507712039-input">Confirm password</label><input type="password" id="field-0.2381946507712039-input" aria-describedby="field-0.2381946507712039-hint"><p id="field-0.2381946507712039-hint">The password should contain at least 18 characters</p></div></form></div>
```

### What happens on every page load

**Beware! The same `PasswordField` that worked in the browser now gives the server and the browser two different ids, and React reports a hydration mismatch.** Here is what happens on every page load, in order:
1. The server runs `PasswordField` for each copy. `Math.random()` gives one number for each copy, and the server writes them into the HTML.
2. The browser shows that HTML. Each label already points at its own field, and the user sees the form at once.
3. The JavaScript arrives. To attach itself to that HTML, React runs `PasswordField` again in the browser, and `Math.random()` gives two new numbers.
4. React compares what it made with the HTML on the page. In each copy, every attribute that holds an id differs from the HTML on the page.
5. In development, React reports the mismatch in the Console.

A hydration mismatch is react.dev's name for this: a difference between the HTML from the server and the first render in the browser. React's message names our exact cause:

```devconsole width=full caption="The Console in development: the first line of React's hydration message, the line that names Math.random, and the link at its end."
x A tree hydrated but some attributes of the server rendered HTML didn't match the client properties. This won't be patched up. This can happen if a SSR-ed Client Component used:
  - Variable input such as `Date.now()` or `Math.random()` which changes each time it's called.
  https://react.dev/link/hydration-mismatch
```

The message uses two short names. SSR is short for server-side rendering, the server rendering of Lesson 46. A Client Component is a component that runs in the browser, as every component of our form does.

react.dev treats a mismatch as a bug, not as a warning to ignore: "`hydrateRoot()` expects the rendered content to be identical with the server-rendered content. You should treat mismatches as bugs and fix them." React also does not promise to fix the ids for us. react.dev: "There are no guarantees that attribute differences will be patched up in case of mismatches." So the page in the browser may keep the server's numbers, while React holds other numbers for the same elements.

Why does React run the component again at all? Because of the event handlers. react.dev, in the Deep Dive of `useId`: "on the client, hydration attaches your event handlers to the generated HTML. For hydration to work, the client output must match the server HTML."

```tree dir=right caption="With Math.random, the server and the browser each run PasswordField and pick a different number."
One page load of the server-rendered sign-up form
- +1. On the server [`Math.random`] | `PasswordField` runs and picks **one number** for each copy | The HTML holds **`field-0.7194...`**
- +2. In the browser, before the JavaScript | The user sees **the server's HTML** | Each label points at **its own field**
- !3. In the browser, during hydration [`Math.random`] | `PasswordField` runs **again** and picks **new numbers** | The ids **differ** from the HTML on the page
- !4. In the Console | React reports **a hydration mismatch** | The attributes are **not patched up**
```

### A counter is no fix either

A developer who sees this error often tries a counter next. An incrementing counter is react.dev's name for a variable at the top of the file that grows by one for each new id:

```jsx title="src/PasswordField.jsx" bad="4"
let nextId = 0;

export default function PasswordField({ label }) {
  const id = 'field-' + ~nextId++~; // **WRONG:** depends on the order in which the copies run
  return <label htmlFor={id}>{label}</label>;
}
```

The counter gives `field-0` to whichever copy runs first. So the ids match only if the browser runs the copies in the same order as the server did. react.dev says it may not: "the order in which the Client Components are hydrated may not match the order in which the server HTML was emitted."

`useId` does not depend on that order, because React builds it from the parent path. react.dev: "if the client and the server tree are the same, the 'parent path' will match up regardless of rendering order."

### The same form with `useId`

Put the final `PasswordField` of Principle 3 back, with `useId()` in place of `Math.random()`. The server and the browser render the same tree, so each copy gets the same string on both sides. The HTML from the server and the first render in the browser now match, and the Console is quiet.

```jsx title="PasswordField.jsx" bad="1"

```
The server and the browser pick two numbers.

::: col title="With useId" tag="one id on both sides" tone=good
```devconsole
= No messages
```

The server and the browser make the same string.

There is one condition. react.dev: "`useId` requires an identical component tree on the server and the client. If the trees you render on the server and the client don't match exactly, the generated IDs won't match." So a component must not render one tree on the server and another in the browser. A check such as `typeof window !== 'undefined'` does exactly that. It asks whether the code runs in the browser, so the server takes one branch and the browser takes the other, and the condition breaks.

## All 4 Principles Together

### The complete sign-up form

Here is the complete form. `App` places `PasswordField` twice. Each copy calls `useId` once, at its top level, and builds the ids of its field and its hint from that one string:

```jsx title="src/App.jsx"
import PasswordField from './PasswordField.jsx';

export default function App() {
  return (
    <form>
      <h1>Create account</h1>
      ~<PasswordField label="Password" />~ {/* 1st copy: one useId string */}
      ~<PasswordField label="Confirm password" />~ {/* 2nd copy: another useId string */}
    </form>
  );
}
```

```jsx title="src/PasswordField.jsx"
import { useId } from 'react';

export default function PasswordField({ label }) {
  const id = ~useId()~; // Principles 2 and 4: one string per copy, the same on the server and in the browser
  return (
    <div>
      <label htmlFor={id + '-input'}>{label}</label>
      <input type="password" id={id + '-input'} ~aria-describedby={id + '-hint'}~ /> {/* Principle 3: one start, two endings */}
      <p id={id + '-hint'}>
        The password should contain at least 18 characters
      </p>
    </div>
  );
}
```

### How React calls the components, in order

When the page renders, React calls `App` first. Then it calls `PasswordField` once for each tag, from top to bottom. In each copy, `useId` returns the string of that copy:

```tree caption="The order in which React calls the components of the sign-up form, and the useId string of each copy."
`App` [1. Called first] | Returns the form with **two `PasswordField` tags**
- +1st `PasswordField` [2. `label="Password"`] | `useId` returns **the string of the 1st copy** | The label, the field, and the hint use **that string plus an ending**
- +2nd `PasswordField` [3. `label="Confirm password"`] | `useId` returns **another string** | Its label, field, and hint **never clash** with the 1st copy
```

| Way to fill the id | One copy on the page | Two copies on the page | Server rendering |
| :--- | :--- | :--- | :--- |
| **Written by hand**, `'password'` | Works | Both fields share one id, so the second label reaches the first field | The same string on both sides, but still a duplicate |
| **`Math.random()`** | Works | Each copy gets its own id | The server and the browser pick two numbers, so React reports a hydration mismatch |
| **A counter**, `nextId++` | Works | Each copy gets its own id | Depends on the order of hydration, which may differ from the server's |
| **`useId()`** | Works | Each copy gets its own id | The same string on both sides, when both render the same tree |

Remember the one sentence of this lesson. **A component never writes its own id. It asks React with `useId`, because only React knows where each copy sits on the page.**

## For the Interview

> **The Interview Question:** How do you generate IDs that are unique, stable, and safe across server and client?

### How to Answer Clearly in 30 Seconds

"An HTML id must be unique on the whole page, and a label finds only the first element with its id. A component can appear many times, so an id written by hand inside it repeats in every copy. On a form with a `Password` field and a `Confirm password` field made from one component, the second label sends the cursor to the first field. So I call `useId()` once, at the top level of the component, and pass the string to both `htmlFor` and `id`. When the component needs more ids, such as a hint for `aria-describedby`, I add endings like `id + '-hint'`. I never use `Math.random()` or a counter. With server rendering, the component runs on the server and again in the browser, so those ids differ, and React reports a hydration mismatch. `useId` builds the string from the component's parent path, so it is the same on both sides, as long as the server and the browser render the same tree. And I never use `useId` for list keys."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Can you use `useId` to make the keys of a list?"**
   **No.** react.dev: "`useId` should not be used to generate keys in a list. Keys should be generated from your data." A key tells React which item of the data a row belongs to, so it must come from the item, such as its id from the database (Lesson 18). A string from `useId` belongs to a place on the page, not to an item of the data. And `useId` is a Hook, so it cannot be called inside the `map` that builds the list.
2. **"Why is `useId` better than a counter such as `nextId++`?"**
   A counter hands out ids in the order the components run. With server rendering, the browser may hydrate the components in a different order from the one in which the server wrote the HTML. Then the same copy can get a different number on each side. react.dev: `useId` is generated from the "parent path" of the calling component, and "if the client and the server tree are the same, the 'parent path' will match up regardless of rendering order." The React 18 release notes add that this matters even more with React's streaming server renderer, which sends the HTML in pieces and "delivers HTML out-of-order".
3. **"Two separate React apps run on the same page. Can their ids clash?"**
   **Yes.** Each app makes its ids on its own, so two apps can produce the same string. react.dev's fix is `identifierPrefix`. Pass a different prefix to `createRoot` for each app, such as `'my-first-app-'`, and every `useId` string of that app starts with it. When an app renders on the server, pass the same prefix to the server API, such as `renderToPipeableStream`, and to `hydrateRoot`. react.dev: "You do not need to pass `identifierPrefix` if you only have one React app on the page."

```tree dir=right caption="Interview summary: what useId guarantees, and what it is not for."
What `useId` guarantees
- +Unique on the page | A **different string for each copy** of the component | Each label reaches **its own field**
- +The same on the server and in the browser | Built from the **parent path**, not from chance | **No hydration mismatch**, as long as both render **the same tree**
- !Not for list keys | A key comes **from the data** | `useId` belongs to **a place on the page**, not to an item
```
