# Lecture 37: Removing Effect Dependencies by Changing the Code

*(How do you stop an Effect from running again without lying to React about what it reads?)*

> INTERVIEW QUESTION | ❱ CORE | How do you remove unnecessary effect dependencies, and when must a dependency stay?

---

## VS | Deleting a dependency vs. changing the code: the deleted value is still read, the changed code no longer reads it

**When an Effect runs too often, never lie to React by deleting a variable from its dependency array. Instead, move the object or function inside the Effect so React does not see a brand-new copy on every render.**

Say you are in a chat room and you start typing a message into the text box at the bottom. You never switched rooms, yet every single letter you type makes the chat disconnect from the server and connect all over again.

**Why:** Your Effect connects using a settings object that sits in the component body. Every letter you type re-renders the component and builds a brand-new settings object, so React thinks the settings changed and restarts the chat. Deleting that object from the dependency array hides the bug, whereas moving the object inside the Effect fixes it cleanly.

Now let's see what that means on a real chat.

React knows nothing about what your Effect does. After every render, it looks only at the dependency array and asks one question: "Did any value in this list change?" If yes, React runs the cleanup, then the setup again. For a chat, that means: disconnect, then connect.

And you do not write that list from your head. The linter reads the Effect and asks for every prop and every state variable it reads. So the array is not a setting you pick. It is a description of the code.

Here is the problem this lesson solves. The connection settings sit in one object, `options`. The Effect reads it, so the linter asks for it:

```jsx title="The linter asked for options, and the chat reconnects after every letter"
const options = { serverUrl: serverUrl, roomId: roomId };

useEffect(() => {
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, ~[options]~); // The array matches the code, and yet every letter the user types reconnects the chat
```

The user types `hi` in the message field. The room did not change, and yet the chat disconnects and connects again after each letter. React's docs call `options` here an **unnecessary dependency**: a value in the array whose change should not run the Effect again.

So you want `options` out of the array. There are two ways to get it out:

```jsx title="Way 1: delete options from the array and silence the linter"
const options = { serverUrl: serverUrl, roomId: roomId };

useEffect(() => {
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, ~[]~); // **WRONG:** eslint-disable-line react-hooks/exhaustive-deps hides options from the linter
```

```jsx title="Way 2: build options inside the Effect"
useEffect(() => {
  const ~options~ = { serverUrl: serverUrl, roomId: roomId }; // Made inside the Effect, so the linter stops asking for it
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId]~); // The linter itself now asks only for roomId
```

Both stop the reconnect on every letter. They look the same, but they are NOT the same thing!
1. **Way 1 still reads `options`.** It reads the one from the first render, forever. When the user picks another room, the chat stays in the old one, and the linter can no longer warn you.
2. **Way 2 no longer reads a value from the component body.** So the linter stops asking for `options` by itself, and the array it asks for is the array you wanted.

React's docs say it in one line: "**If you want to change the dependencies, change the surrounding code first.**"

They call Way 2 proving it to the linter: "**To remove a dependency, "prove" to the linter that it *doesn't need* to be a dependency.**"

And about Way 1: "By suppressing the linter, you "lie" to React about the values your Effect depends on."

```tree caption="Two ways to get a value out of the dependency array: silence the linter, or change the code so the Effect no longer reads it."
Two ways to get a value out of the dependency array
- !Way 1: delete it and silence the linter | The Effect **still reads the value** | It keeps an **old copy**, and the linter can **no longer warn you**
- +Way 2: change the code first | The Effect **no longer reads a reactive value** there | The linter **stops asking for it** by itself
```

> [!DEFINITION]
> **What is a reactive value?** [REVIEW] A reactive value is a value that a render can change: a prop, a state variable, or a variable calculated from them inside the component body.
> When an Effect reads a reactive value, the linter asks you to put it in the dependency array.
> A value made outside the component, or inside the Effect itself, is not reactive. A render cannot change it, so it never goes in the array.
> React's `set` functions are not reactive either. They are stable: React gives you the same function on every render (Lesson 35).

### Why a new `options` counts as a change

After every render, React compares each value in the array with the one from the last render. It uses `Object.is`, which works here like `===` (Lesson 32).

You know this from plain JavaScript. Two strings with the same text are equal. Two objects with the same fields are not. Try it in the browser Console. These four lines come from React's docs:

```js title="Two objects with the same contents, and two strings with the same text"
const options1 = { serverUrl: 'https://localhost:1234', roomId: 'music' };
const options2 = { serverUrl: 'https://localhost:1234', roomId: 'music' };
console.log(~Object.is(options1, options2)~); // false: two different objects

const roomId1 = 'music';
const roomId2 = 'music';
console.log(~Object.is(roomId1, roomId2)~); // true: the same string
```

> [!DEFINITION]
> **What is an object dependency?** [NEW] An object dependency is an object listed in the dependency array. A function listed there is a function dependency.
> Strings, numbers, and booleans are primitive values. JavaScript compares them by their content, so two `'music'` strings are one and the same value.
> Objects and functions are compared by which object they are. Every `{ ... }` builds a new object, even when its fields match an old one.
> React's docs: "**In JavaScript, each newly created object and function is considered distinct from all the others. It doesn't matter that the contents inside of them may be the same!**"
> So, once more: an object made during rendering is a new value on every render, and the Effect that lists it runs after every render (Lesson 37).

```tree caption="How Object.is compares two strings with the same text and two objects with the same contents."
What `Object.is` compares
- +Two strings with the same text [`'music'` `'music'`] | Compared **by their content** | `Object.is` returns **`true`**: the same value
- !Two objects with the same contents [`options1` `options2`] | Compared by **which object they are** | `Object.is` returns **`false`**: two different values
```

### The Rule of Thumb: must the Effect run again when this value changes?

**Ask one question about every value in the array: when it changes, must the Effect run again? If yes, it stays. If no, change the code until the Effect no longer reads it.**
- **`roomId`: yes.** The user picked another room, so the chat must connect to it.
- **A new `options` after a typed letter: no.** Same server, same room. Move the object inside the Effect.
- **A new message in the list: no.** Pass an updater function, so the Effect never reads the list.

React's docs give the whole method in three steps:
1. "First, you **change the code** of your Effect or how your reactive values are declared."
2. "Then, you follow the linter and adjust the dependencies to **match the code you have changed.**"
3. "If you're not happy with the list of dependencies, you **go back to the first step**."

The docs compare this to solving an equation: "This might feel like solving an equation." You know the answer you want, such as `[roomId]`, and you look for the code that gives it.

A senior developer also knows the three classic mistakes:
1. **Deleting the dependency and silencing the linter.** The Effect keeps reading an old value, with no warning.
2. **Thinking an object with the same contents is the same dependency.** It is a new object, so the Effect runs again.
3. **Removing a dependency that must stay, such as `roomId`.** The Effect runs less, and the chat stays in the old room after the user picks a new one.

The rest of the lesson shows each one on a real chat room.

The chat helper is the `createConnection` function from Lesson 36, with one change. It now takes the server and the room together in one object, as React's docs write it. Many real connection libraries take their settings the same way:

```js title="src/chat.js"
export function createConnection(~{ serverUrl, roomId }~) { // One object now, instead of two separate arguments
  let intervalId;
  let messageCallback;
  return {
    connect() {
      console.log('✅ Connecting to "' + roomId + '" room at ' + serverUrl + '...');
      clearInterval(intervalId);
      intervalId = setInterval(() => {
        if (messageCallback) {
          if (Math.random() > 0.5) {
            messageCallback('hey');
          } else {
            messageCallback('lol');
          }
        }
      }, 3000);
    },
    disconnect() {
      clearInterval(intervalId);
      messageCallback = null;
      console.log('❌ Disconnected from "' + roomId + '" room at ' + serverUrl);
    },
    on(event, callback) {
      if (messageCallback) {
        throw Error('Cannot add the handler twice.');
      }
      if (event !== 'message') {
        throw Error('Only "message" event is supported.');
      }
      messageCallback = callback;
    },
  };
}
```

Each message is picked at random, so a real run shows `hey` and `lol` in any order. The previews below show one such run.

**PRINCIPLES:** You never choose the dependencies. The code chooses them. Four principles follow:
1. **Principle 1: An Object Made in the Component Body Is New on Every Render.** Listed in the array, it reconnects the chat after every letter the user types.
2. **Principle 2: Build the Object Inside the Effect.** Then it is not reactive, it leaves the array, and only the string `roomId` stays.
3. **Principle 3: An Updater Function Reads No State.** The Effect adds each message without reading `messages`, so new messages never reconnect the chat.
4. **Principle 4: A Dependency Stays When Its Change Must Run the Effect Again.** `roomId` stays, because picking a room must reconnect the chat.

## PRINCIPLE | options in the component body: a new object on every render reconnects the chat

> [!PRINCIPLE]
> **Principle 1: Object Dependencies: An Object Made in the Component Body Is New on Every Render**
>
> *An object or a function made in the component body is a new value on every render, so an Effect that lists it runs again after every render, even when the contents are the same.*
>
> React compares each dependency with `Object.is`. Strings and numbers are compared by their content, but each new object is a different value. Every letter the user types renders `ChatRoom`, builds a new `options`, and makes React disconnect and connect again. An object made once, outside the component, is the same object on every render.
>
> **DO THIS:**
> ```jsx
> const options = { serverUrl: 'https://localhost:1234', roomId: 'music' };
>
> function ChatRoom() {
>   useEffect(() => {
>     const connection = createConnection(options);
>     connection.connect();
>     return () => connection.disconnect();
>   }, ~[]~); // options is made once, outside the component: typing never reconnects
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ChatRoom({ roomId }) {
>   const options = { serverUrl: serverUrl, roomId: roomId };
>   useEffect(() => {
>     const connection = createConnection(options);
>     connection.connect();
>     return () => connection.disconnect();
>   }, ~[options]~); // **WRONG:** a new options on every render reconnects the chat after every letter
> }
> ```

Remember: React calls your component function from the top on every render. So every line in the component body runs again, including this one:

```jsx title="A line in the component body runs on every render"
const options = ~{ serverUrl: serverUrl, roomId: roomId }~; // The curly braces build a brand-new object every time
```

The `options` of the last render and the `options` of this render hold the same server and the same room. They look the same, but they are NOT the same thing! They are two objects, so `Object.is` returns `false`, exactly as it did for the two objects in the browser Console. React's docs: "A new `options` object is created from scratch on every re-render of the `ChatRoom` component."

### The chat page with `options` in the component body

Here is `ChatRoom` with `options` in the component body. It also holds the message field, controlled by `message` state (Lesson 20):

```jsx title="src/components/ChatRoom.jsx" bad="9,15"
import { useState, useEffect } from 'react';
import { createConnection } from '../chat.js';

const serverUrl = 'https://localhost:1234';

export default function ChatRoom({ roomId }) {
  const [message, setMessage] = useState('');

  const ~options~ = { serverUrl: serverUrl, roomId: roomId }; // A new object on every render

  useEffect(() => {

    connection.connect();

    <section>
      <h1>Welcome to the {roomId} room!</h1>
      <input
        value={message}
        onChange={e => ~setMessage(e.target.value)~} // Every letter the user types renders ChatRoom again
      />
    </section>
  );
}
```

The user types `hi`. The page looks fine: the letters appear, and the heading stays on the general room. The damage shows only in the Console, with one disconnect and one connect for each letter:

**Beware! With `options` in the component body, every letter the user types disconnects the chat and connects it again.** Here is what one letter does:
1. The user types `h`. The `setMessage` call stores it and asks React to render `ChatRoom` again.
2. `ChatRoom` runs from the top, and the `options` line builds a new object with the same server and room.
3. React compares the new `options` with the last one. `Object.is` returns `false`, so the dependency changed.
4. React runs the old cleanup, and the Console shows the disconnect line.
5. React runs the new setup, and the Console shows the connect line.

React's docs describe this exact page from the user's side: "From the user's perspective, this should not affect the chat connection."

```tree dir=right caption="Why one letter typed in the message field reconnects the chat when options is made in the component body."
What one letter in the message field does
- +1. The user types a letter [`setMessage`] | `ChatRoom` **renders again** from the top
- +2. A new `options` object [`options`] | Same server, same room, but a **different object**
- !3. React compares with `Object.is` | The answer is **`false`** | React runs the **cleanup and the setup**: the chat **reconnects**
```

The linter sees this too. With `[options]`, it no longer reports a missing dependency. Instead, it warns that this object changes the dependencies of the Effect on every render, and it tells you to move the object inside the Effect. Principle 2 does exactly that.

React's docs warn about this case in bold: "**Object and function dependencies can make your Effect re-synchronize more often than you need.**"

### A function in the component body does the same

Suppose the developer builds `options` in a helper function instead. The function is also made again on every render:

```jsx title="A createOptions function in the component body" bad="8"
function ~createOptions~() { // A new function on every render of ChatRoom
  return { serverUrl: serverUrl, roomId: roomId };
}

useEffect(() => {
  const options = createOptions();
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, ~[createOptions]~); // **WRONG:** a new function after every render reconnects the chat
```

A function is an object too, so a new function is a new value. React's docs: as a dependency, "it will cause your Effect to re-run after every commit."

Something that can be tricky: making a new function on every render is not the problem. The docs: "By itself, creating a function from scratch on every re-render is not a problem. You don't need to optimize that." The problem starts only when the Effect lists it.

## PRINCIPLE | options inside the Effect: only the string roomId stays in the array

> [!PRINCIPLE]
> **Principle 2: Moving the Object: options Built Inside the Effect Leaves Only roomId**
>
> *Move an object or a function that depends on props or state inside the Effect, and one that depends on neither above the component; then it is not reactive, it leaves the array, and only the primitive values it reads, such as roomId, stay.*
>
> We do not remove `options` from the array by hand. We move the line that makes it, and the linter itself asks for the shorter array. A value made inside the Effect is not reactive, and the string `roomId` is compared by its content, so the chat reconnects only when the user picks another room. When the object arrives as a prop, read its primitive values before the Effect and list those.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const ~options~ = { serverUrl: serverUrl, roomId: roomId }; // Made inside the Effect: not reactive
>   const connection = createConnection(options);
>   connection.connect();
>   return () => connection.disconnect();
> }, [roomId]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const options = { serverUrl: serverUrl, roomId: roomId };
> useEffect(() => {
>   const connection = createConnection(options);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[options]~); // **WRONG:** options is made in the component body, so every letter reconnects the chat
> ```

### VS | `options` in the component body vs. `options` inside the Effect: the same line, only one reconnects on every letter

Principle 1 found the cause: the line that builds `options` sits in the component body. So we move that one line:

```jsx title="With options in the component body"
const options = { serverUrl: serverUrl, roomId: roomId };

useEffect(() => {
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, ~[options]~); // A new object after every render: the chat reconnects on every letter
```

```jsx title="With options inside the Effect"
useEffect(() => {
  const ~options~ = { serverUrl: serverUrl, roomId: roomId }; // Made inside the Effect: no longer a reactive value
  const connection = createConnection(options);
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId]~); // Only a string: the chat reconnects only when the room changes
```

It may work the same at first, but it is NOT the same thing! Both versions connect to the general room when the page opens. Both reconnect when the user picks `travel`. Only the first one reconnects when the user types a letter.

Why? A value made inside the Effect is not reactive, so it is not a dependency (Lesson 35). React's docs: "Now that `options` is declared inside of your Effect, it is no longer a dependency of your Effect."

The linter now asks for `roomId` instead, because the Effect reads it directly, in the line that builds the object. Leave the array empty, and the linter reports that `roomId` is a missing dependency.

That is what proving it to the linter means. We never argued with the linter about `options`. We moved one line, and the linter changed its request by itself.

### Why `roomId` causes no trouble in the array

`roomId` is a string, a primitive value. JavaScript compares it by its content, as the two `'music'` strings showed.

So while the user stays in the general room, every render gives `roomId` the same value, `'general'`, and React keeps the connection. When the user picks `travel`, the value really changes, and React reconnects.

So for every object or function dependency, React's docs give three moves: "try moving them outside the component, inside the Effect, or extracting primitive values out of them."

### Static objects go above the component, dynamic ones inside the Effect

Where should the object go? It depends on what it reads. React's docs name two kinds:
1. **A static object** "does not depend on any props and state". It goes above the component. JavaScript builds it once, when the file loads, so it is the same object on every render, and the array is `[]`.
2. **A dynamic object** "depends on some reactive value that may change as a result of a re-render, like a `roomId` prop". It goes inside the Effect, and the array lists what it reads, such as `[roomId]`.

React's docs show the static kind with a chat that is always in the music room:

```jsx title="A static options object above the component"
const ~options~ = { serverUrl: 'https://localhost:1234', roomId: 'music' }; // Made once, when the file loads

function ChatRoom() {
  useEffect(() => {
    const connection = createConnection(options);
    connection.connect();
    return () => connection.disconnect();
  }, ~[]~); // options is not reactive, so the array is empty
}
```

On our page, the menu changes the room, so `options` reads the `roomId` prop. It is dynamic, and it goes inside the Effect.

```tree caption="Where an object dependency goes: a static object above the component, a dynamic object inside the Effect."
Where to make the object the Effect reads
- +Static: depends on no props and no state [`roomId: 'music'`] | Make it **above the component**, once | The array is **empty**
- +Dynamic: depends on a prop or state [`roomId: roomId`] | Make it **inside the Effect** | The array lists only **`roomId`**
```

A function works the same way. Keep the `createOptions` helper from Principle 1, and only move it inside the Effect. React's docs: "As long as you also declare them *inside* your Effect, they're not reactive values, and so they don't need to be dependencies of your Effect."

### When `options` arrives as a prop

Sometimes the object is not yours to move. React's docs show this case in one of their Challenges:
1. `App` builds `options` from its own state and passes it down as a prop.
2. `ChatRoom` reads it inside its Effect and lists `[options]`.
3. The user clicks a `Toggle theme` button, which changes only the theme of `App`.
4. `App` renders again and builds a new `options`, so the chat reconnects. The docs: "Your Effect is re-running because it depends on the `options` object."

`ChatRoom` cannot move a prop. So it reads the two strings out of the object, before the Effect, and lists the strings:

```jsx title="Reading primitive values out of an options prop"
function ChatRoom({ options }) {
  const { roomId, serverUrl } = ~options~; // Reads two strings out of the object, outside the Effect

  useEffect(() => {
    const connection = createConnection({ roomId: roomId, serverUrl: serverUrl });
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId, serverUrl]~); // Two strings: a new options with the same room does not reconnect
}
```

React's docs: "If an object is re-created unintentionally by the parent component, the chat would not re-connect. However, if `options.roomId` or `options.serverUrl` really are different, the chat would re-connect."

A function that arrives as a prop, such as `getOptions`, works the same way. Call it outside the Effect, read the two strings from the object it returns, and list them.

The docs add one condition: "This only works for pure functions because they are safe to call during rendering" (Lesson 14). When you also write the parent, there is a simpler fix: pass `roomId` and `serverUrl` as two separate props.

## PRINCIPLE | setMessages with an updater function: new messages never reconnect the chat

> [!PRINCIPLE]
> **Principle 3: Updater Functions: Reading No State Removes the State Dependency**
>
> *When the Effect sets state from the same state, such as adding a message to messages, pass an updater function to the setter, so the Effect does not read that state and it leaves the array.*
>
> Reading `messages` inside the Effect makes `messages` a dependency, so every message that arrives reconnects the chat. Silencing the linter stops the reconnect, but the Effect keeps the empty list of the first render, so the screen shows only the newest message. An updater function reads nothing: React gives it the current list, and the array stays `[roomId]` with no comment.
>
> **DO THIS:**
> ```jsx
> connection.on('message', msg => {
>   setMessages(~msgs => [...msgs, msg]~); // React passes the current list: every message is kept
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> connection.on('message', msg => {
>   setMessages(~[...messages, msg]~); // **WRONG:** with the linter silenced, messages stays the empty list of the first render
> });
> ```

### VS | Reading `messages` vs. an updater function: both add the message, only one makes `messages` a dependency

Now the room shows the messages that arrive. The Effect hands the connection a function through its `on` method, and the connection calls it with each message (Lesson 36). Inside that function, the new message goes at the end of `messages` state. There are two ways to write that line:

```jsx title="Reading messages, and passing an updater function"
setMessages(~[...messages, msg]~); // Reads messages: the Effect now depends on messages
setMessages(~msgs => [...msgs, msg]~); // Never reads messages: React passes the current list as msgs
```

Both lines put `msg` at the end of the list. But the first line reads `messages`, so the linter asks for it in the array. The second line reads nothing but `msg`, so `messages` never enters the array.

Developers usually try two other ways before they reach the updater function. Each one breaks the page in its own way.

### First try: `messages` in the array reconnects the chat on every message

## PRINCIPLE | roomId: it stays, because picking a room must reconnect the chat

> [!PRINCIPLE]
> **Principle 4: Required Dependencies: roomId Stays Because Picking a Room Must Reconnect**
>
> *A dependency stays when its change, from the user's side, means the Effect must run again; a dependency goes only when the code no longer reads a reactive value there, and the linter accepts the shorter array with no comment that silences it.*
>
> Every value in the array answers one question: should a change of this value reconnect the chat? For `roomId`, the answer is yes, because the user picked a different conversation. For a typed letter or an arriving message, the answer is no, so we change the code until the Effect no longer reads those values. Deleting a value from the array by hand only hides it from the linter.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const options = { serverUrl: serverUrl, roomId: roomId };
>   const connection = createConnection(options);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[roomId]~); // Picking another room reconnects the chat to that room
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const options = { serverUrl: serverUrl, roomId: roomId };
>   const connection = createConnection(options);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[]~); // **WRONG:** with the linter silenced, the chat stays in general after the user picks travel
> ```

### Read the final Effect value by value

After Principles 2 and 3, the array holds one value:

```jsx title="The final Effect in src/components/ChatRoom.jsx" startLine="10"
  useEffect(() => {
    const options = { serverUrl: serverUrl, roomId: ~roomId~ }; // The only reactive value the Effect reads
    const connection = createConnection(options);
    connection.on('message', msg => {
      setMessages(msgs => [...msgs, msg]);
    });
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId]~); // Changes only when the user picks another room
```

For each value the Effect touches, say why it is in the array, or why it is not:
1. **`roomId`** is a prop, read inside the Effect. It stays.
2. **`serverUrl`** is a constant above the component. It is not reactive.
3. **`options`** is built inside the Effect. It is not reactive, as Principle 2 showed.
4. **`messages`** is not read at all. The updater function reads `msgs`, as Principle 3 showed.
5. **`setMessages`** is a `set` function, and it is stable.
6. **`message`**, the text in the message field, is never read by the Effect.

Typing `h` and picking `travel` both change state, and both render the component again. They look the same, but they are NOT the same thing for the user! A typed letter changes nothing about the conversation. A new room asks for a different conversation. So only `roomId` belongs in the array.

React's docs give this check after every change: "Every time you adjust the Effect's dependencies to reflect the code, look at the dependency list. Does it make sense for the Effect to re-run when any of these dependencies change?" For `roomId`, the answer is yes. The docs on the same chat: "It is important to declare it as a dependency!"

```tree caption="Which values stay in the final array, and why each of the others is not there."
The values the final Effect touches
- +Stays in the array [`roomId`] | A prop **read inside the Effect** | Picking a room **must reconnect** the chat
- +Not reactive [`serverUrl` `options`] | Made **above the component** or **inside the Effect** | Never a dependency
- +Not read [`messages`] | The updater function reads **`msgs`** | Never a dependency
- +Stable [`setMessages`] | A **`set` function** from `useState` | The linter **never asks** for it
```

### VS | `roomId` moved above the component vs. `roomId` deleted from the array: both end with an empty array, only one tells the truth

`roomId` can leave the array in one case only: the room never changes, and the code says so. Compare two ways to end with `[]`:

They look the same, but they are NOT the same thing!
1. **With `roomId` moved above the component**, the Effect reads a value that never changes, and the linter agrees. This fits a chat that is always in the music room.
2. **With `roomId` deleted from the array**, the Effect still reads a prop that changes. The linter reports that `roomId` is a missing dependency.

Silence that warning, and the heading changes to the travel room while the chat stays connected to the general room (Lesson 35).

### Five questions for an unnecessary dependency

React's docs give three reasons why a developer may not want a dependency:
1. "You might want to re-execute *different parts* of your Effect under different conditions."
2. "You might want to only read the *latest value* of some dependency instead of "reacting" to its changes."
3. "A dependency may change too often *unintentionally* because it's an object or a function."

For each unnecessary dependency, the docs ask a short list of questions. Each answer leads to one change in the code:
1. **"Should this code move to an event handler?"** Code that runs because of one interaction, such as a form submit, belongs in the event handler (Lesson 34).
2. **"Is your Effect doing several unrelated things?"** Split it into two Effects, each with its own array (Lesson 35).
3. **"Are you reading some state to calculate the next state?"** Pass an updater function, as Principle 3 did with `messages`.
4. **"Do you want to read a value without "reacting" to its changes?"** Move that code into an Effect Event (Lesson 36).
5. **"Does some reactive value change unintentionally?"** It is an object or a function made during rendering. Move it, or read its primitive values, as Principles 1 and 2 did.

Silencing the linter is not on the list. React's docs: "We recommend treating the dependency lint error as a compilation error."

The first question catches a mistake that React's docs show with a form:
1. When the user submits the form, the code sets `submitted` to `true`. An Effect with `[submitted]` sends the form and shows a notification.
2. Later, the notification reads the page theme, so the developer follows the linter and adds `theme` to the array.
3. Now the user submits the form and then switches the theme. The Effect runs again and shows the same notification a second time.

The docs: "**The problem here is that this shouldn't be an Effect in the first place.**"

The code moves into the submit handler, and the dependency question disappears with it.

## For the Interview

> **The Interview Question:** How do you remove unnecessary effect dependencies, and when must a dependency stay?

### How to Answer Clearly in 30 Seconds

"I never choose the dependencies. The array lists every reactive value the Effect reads, and the linter checks it. To remove a dependency, I change the code so the Effect no longer reads a reactive value there, and then the linter stops asking for it. Three changes cover most cases:
1. **Move an object or a function**: one made in the component body is new on every render. I move a static one above the component, a dynamic one inside the Effect, or I read its primitive values.
2. **Pass an updater function**: when the Effect sets state from the same state, such as adding a message with `msgs => [...msgs, msg]`, it no longer reads that state.
3. **Put the code where it belongs**: an event handler for one interaction, two Effects for two unrelated jobs, or an Effect Event to read a value without reacting to it.

A dependency must stay when its change means the Effect must run again, such as the chat room the user picked. I never silence the linter, because the Effect then keeps stale values."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does an `options` object re-run the Effect when its contents did not change?"**
   React compares each dependency with `Object.is`. Strings and numbers are compared by their content, but each new object is a different value, even with the same contents.
   React's docs show two objects with the same server and the same room, and `Object.is` returns `false` for them.
   An object made in the component body is made again on every render, so the Effect runs again after every render. The fix is to move the object inside the Effect, or above the component, so that only primitive values such as `roomId` stay in the array.
2. **"Can an object in the dependency array cause an infinite loop?"**
   Only when the Effect also sets state.
   React's docs say an infinite cycle needs two things: "Your Effect is updating some state." and "That state leads to a re-render, which causes the Effect's dependencies to change."
   Our chat Effect with `[options]` sets no state, so it runs again once after each render, on every letter the user types, and then stops.
   If that Effect also set state to a new value on every run, such as a new object, the runs would never end. Each run would cause a render, a new `options`, and another run, and the Console would fill with React's error `Maximum update depth exceeded`.
   Setting state to a value it already holds, such as `true` again, causes no new render, so the runs stop.
3. **"What if the object comes from a parent as a prop, and you cannot move it?"**
   Read its primitive values before the Effect, such as `const { roomId, serverUrl } = options;`, and list `[roomId, serverUrl]`. A new object with the same room then does not reconnect, while a real change of room still does.
   For a function prop, call it outside the Effect, which works only for pure functions. Better still, pass `roomId` and `serverUrl` as separate props. React's docs keep `useMemo` and `useCallback` as the last resort for this case (Lessons 56 and 57).

```tree dir=right caption="Interview summary: how to remove an unnecessary dependency, and when a dependency must stay."
Removing a dependency vs. keeping it
- +Removable: the code can stop reading it [`options` `messages`] | **Change the code**: move the object, or pass an updater function | The linter **stops asking** for it, with **no comment**
- +Must stay: its change must run the Effect again [`roomId`] | The user **picked another room** | The chat **must reconnect**
- !Never: delete it and silence the linter | The Effect **keeps stale values** | The linter **can no longer warn you**
```
