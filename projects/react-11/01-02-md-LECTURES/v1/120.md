# Lecture 120: What Resuming Picks Up, Where It Comes From, and Why It Is Not Hydration

*(When the server finishes a page that the build started, what does it pick up, and what is still left for the browser?)*

> INTERVIEW QUESTION | ❱ CORE | What does resuming mean: shipping server state without shipping component code?

---

## VS | `resume` on the Server vs. `hydrateRoot` in the Browser: both continue the page, only `hydrateRoot` makes it answer a tap

> A product page shows the same name and the same price to every visitor, but each visitor sees their own cart. **Resuming means that the build renders the part that is the same for everyone, and the server later finishes the visitor's part from where the build stopped.** Only `postponed`, a JSON object with no code in it, crosses to the server, so the server runs our components again, and the browser still hydrates the page.

Until now, React made the HTML of a page at one of two moments. With server rendering, React runs once for every visitor (as seen in Lesson 102). With static prerendering, React runs once in total, during the build (as seen in Lesson 119). A product page needs both moments. The name of the shoe and its price are the same for everyone, so the build can make them. The cart is different for each visitor, so only the visitor's request can make it.

React lets one page use both moments. The build calls `prerender`, which renders what it can and then stops. The server calls `resume` when a visitor arrives, and finishes the rest. React calls this Partial Pre-rendering, and we built it in Lesson 103. Ask yourself: when the server picks up the page, what exactly does it pick up? Is it the missing HTML? Is it a copy of the cart component? Neither. It picks up `postponed`, a JSON object that records where the build stopped, and it brings the component code itself.

**Why:** The word "resume" misleads in two ways, and each one breaks the page. It sounds as if the build hands over everything the server needs. So a team deploys only the files the build wrote, and the server has no component to finish the cart with. It also sounds as if the browser picks up a finished page and skips hydration. So a team drops the JavaScript bundle, and the `Add to cart` button never answers a tap.

### The One Line That Resumes the Page

Everything in this lesson sits in one line of the server file:

```jsx title="server.js: the one line that resumes the page"
const stream = await ~resume(<App />, postponed)~; // Two things go in: our component, and the place where prerender stopped
```

Two things go into `resume`, and they come from two different places:
1. **`postponed`** comes from the build. It records where the build stopped rendering, as plain JSON text. The build wrote it into a file, and the server reads that file back.
2. **`<App />`** comes from the server's own files. The build never hands it over. The server imports `App` itself, exactly as the build did.

`resume` puts the two together on the server and makes the HTML that was missing, such as `Cart: 2`. Then the browser hydrates the page, exactly as it does for any HTML that comes from a server.

```tree dir=right caption="What goes into resume, where each piece comes from, and what comes out."
What `resume` receives and what it gives
- +From the build [`postponed`] | Saved in **`dist/blue-sneakers.json`** | **JSON text** with **no component code** in it
- +From the server's own files [`<App />`] | The server imports **`./src/App.jsx`** | The **component code** that `resume` runs again
- +Out of `resume` [`Cart: 2`] | **HTML**, made **on the server** | The browser **still hydrates** it
```

Here is the one sentence to keep in mind for this whole lesson:

**Resuming splits one server render across two moments, build time and request time. Only `postponed` crosses between them, and the browser still hydrates the page afterwards.**

### `resume` vs. `hydrateRoot`: the same `<App />`, two different jobs

`resume` and `hydrateRoot` have a lot in common:

```jsx title="The two calls that continue the page after the build"
const stream = await ~resume~(<App />, postponed); // On the server: makes the HTML of the cart
~hydrateRoot~(document, <App />); // In the browser: makes Add to cart answer a tap
```

Both take `<App />`. Both continue a page that the server started. Both run our components again. **They may look the same, but they are NOT the same thing!** `resume` runs on the server and makes HTML. `hydrateRoot` runs in the browser and connects React to the HTML that is already on the screen. In React, resuming happens on the server, and it never replaces hydration.

### Three Ideas From Earlier Lessons

> [!DEFINITION]
> **`prerender` and `postponed`.** [REVIEW] `prerender` renders the page during the build and gives back `{ prelude, postponed }`. When the build stops it early with an `AbortController`, every `<Suspense>` boundary that was still waiting goes into `prelude` with its fallback, such as `Loading cart...`. `postponed` then holds the work that is left, and React's docs call it opaque: we store it and pass it on, but we never read inside it. When nothing is left, `postponed` is `null` (Lessons 103 and 119).

> [!DEFINITION]
> **Suspense and use.** [REVIEW] A component reads a Promise with `use`, such as `use(getCart())`. While the Promise is still waiting, the component suspends: React cannot finish it yet. The nearest `<Suspense>` boundary above it shows its fallback, such as `Loading cart...`, until the data arrives (Lessons 69 and 71).

> [!DEFINITION]
> **Hydration.** [REVIEW] The server sends HTML, and the browser shows it at once, but HTML alone cannot answer a click. The bundle loads, `hydrateRoot(document, <App />)` runs our components again in the browser, and React connects their click handlers and Effects to the HTML already on the screen. In React's docs: "Hydration turns the initial HTML snapshot from the server into a fully interactive app that runs in the browser" (Lesson 104).

### Three Calls That Finish a Stopped Prerender

React gives three calls that take the same `postponed` and finish the page:
1. **`resume`** finishes it at request time, for one visitor, as a Web Stream. React's docs: "`resume` streams a pre-rendered React tree to a Readable Web Stream." This is the call of this lesson.
2. **`resumeToPipeableStream`** does the same job for a server that uses Node.js Streams.
3. **`resumeAndPrerender`** finishes it as static HTML, for example to put on a CDN. React's docs: "Or you can call `resumeAndPrerender` to resume to get static HTML for SSG".

When to pick each one, and their options, come later (Lesson 142).

When Alice taps `Add to cart`, her cart goes from 2 to 3. The heading and the price were made at build time, hours before Alice came. Her cart was made when her request arrived. These are the three parts this lesson needs:
1. **A part made at build time:** the heading and the price.
2. **A part made at request time:** `Cart: 2`.
3. **A part that needs hydration:** the `Add to cart` button.

This is the resumed product page from Lesson 103, with one change. The heading and the price move out of `App` into their own component, `ProductInfo`. Principle 2 needs one component that finishes at build time and one that does not.

```files title="blue-sneakers: File Explorer" caption="The files of the resumed Blue Sneakers page: the build, the server, the two saved files, and our components."
build.js | build time | Calls `prerender` and writes the two files in `dist/`
server.js | request time | Sends the HTML file, loads `postponed`, and calls `resume(<App />, postponed)`
dist/
  blue-sneakers.html | prelude | `Blue Sneakers`, `$89`, and `Loading cart...`, made at build time
  blue-sneakers.json | postponed | The place where `prerender` stopped, as JSON text
src/
  App.jsx | root | Returns the whole document: `<ProductInfo />`, then `<CartLine />` inside `<Suspense>`
  ProductInfo.jsx | new | Returns the heading and the price, and reads no data
  CartLine.jsx | visitor | Reads the cart with `use(getCart())` and keeps `count` in state
  cart.js | data | Exports `getCart`, which returns a Promise of the visitor's cart
  main.jsx | browser | Calls `hydrateRoot(document, <App />)`, and is built into `/main.js`
```

**PRINCIPLES:** Resuming splits one server render across build time and request time, and the browser still hydrates the page afterwards. Three principles follow:
1. **`postponed`: only the place where the build stopped crosses to the server, never the component code.** The server passes it to `resume` together with `<App />`, which it imports from its own files.
2. **`resume`: the render starts again at `App`, and only fully prerendered components are skipped.** Code in `App` runs again for every visitor.
3. **`hydrateRoot`: `Add to cart` answers a tap only after the browser hydrates the page.** `resume` makes only HTML, so the bundle and `hydrateRoot` stay.

## PRINCIPLE | `postponed`: only the place where the build stopped crosses to the server, never the component code

> [!PRINCIPLE]
> **Principle 1: What Is Resumed: `postponed` From Storage, `<App />` From the Server's Own Files**
>
> *When `prerender` stops early, the work it still has to do is saved as `postponed`, a JSON object with no component code in it; to finish the page, the request server passes `postponed` together with the same `<App />`, which it imports from its own copy of the code.*
>
> The build and the request may be hours apart and on two machines, so what crosses between them must be text that can be stored. `postponed` is that text: it records where the render stopped. A component is a function, and JSON cannot hold a function, so the component code never crosses. The server imports `App` itself, and `resume` needs both to make the missing HTML.
>
> **DO THIS:**
> ```jsx
> import App from './src/App.jsx';
> const postponed = JSON.parse(await readFile('dist/blue-sneakers.json', 'utf8'));
> const stream = await resume(~<App />~, postponed); // The same <App /> that went to prerender
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import CartLine from './src/CartLine.jsx';
> const postponed = JSON.parse(await readFile('dist/blue-sneakers.json', 'utf8'));
> const stream = await resume(~<CartLine />~, postponed); // **WRONG:** not the node passed to prerender, so the server never makes Cart: 2
> ```

The build and the server each hold one end of the same render. In the build file, `prerender` hands back `postponed`, and the build writes it into a file:

```jsx title="build.js" startLine="8"
const { prelude, ~postponed~ } = await prerender(<App />, { // The work prerender did not finish
  signal: controller.signal,
  bootstrapScripts: ['/main.js'],
});
await mkdir('dist', { recursive: true });
await writeFile('dist/blue-sneakers.html', prelude);
await writeFile('dist/blue-sneakers.json', ~JSON.stringify(postponed)~); // Written into a file as JSON text
```

In the server file, the server reads that file back, and takes `App` from its own import:

```jsx title="server.js"
import { readFile } from 'node:fs/promises';
import { resume } from 'react-dom/server';
import ~App~ from './src/App.jsx'; // The component code: the server's own copy of our files

export async function handler(request) {
  return new Response(ReadableStream.from(sendPage()), { headers: { 'content-type': 'text/html' } });
}

async function* sendPage() {
  yield await readFile('dist/blue-sneakers.html');
  const postponed = ~JSON.parse~(await readFile('dist/blue-sneakers.json', 'utf8')); // The JSON text, turned back into an object
  const stream = await resume(<App />, postponed);
  yield* stream;
}
```

**`postponed` travels from the build to the server. `App` does not travel at all: each file imports it on its own.**

### Why `postponed` Can Wait in a File for Hours

Remember `JSON.stringify`? You use it every time you send an object to an API or keep it in `localStorage`. It turns an object into text. `JSON.parse` turns that text back into the same object.

React's docs describe `postponed` as "a JSON-serializeable, opaque object". **JSON-serializable** means exactly that: `JSON.stringify` can turn it into text, and `JSON.parse` can bring it back. That is why the build can write `postponed` into a file today, and the server can read it back hours later.

When `postponed` comes back in, React's docs call it the **postponed state**. It is the `postponedState` parameter of `resume`, "loaded from wherever you stored it". The docs name redis, a file, or S3 as examples. Redis is a database that keeps values in memory, and S3 is Amazon's file storage. So the server that answers Alice can be a different machine from the one that ran the build.

```tree dir=right caption="How the two pieces of resume reach the server: postponed from the build, App from the server's own files."
How the two pieces reach `resume` on the server
- +`postponed` from the build [`prerender` `JSON.stringify`] | The build writes it into **`dist/blue-sneakers.json`** | The server reads it back with **`JSON.parse`**
- +`App` from the server's own files [`import App`] | The server imports **`./src/App.jsx`** | The **same file** that the build imported
- +Both together [`resume` `<App />` `postponed`] | React continues the render **on the server** | Makes **`Cart: 2`** for Alice
```

### What `postponed` Cannot Hold: a Component

Open the JSON file in the dist folder after a build, and you find one line of text. It is not HTML, and it is not code. Because `postponed` is opaque, we cannot say what is inside it. But we can say what cannot be inside it. Try this in the browser's Console:

```js title="JSON has no place for a function"
JSON.stringify({ count: 2, add: ~() => 1~ }); // Gives '{"count":2}': the function is gone
```

JSON keeps strings, numbers, booleans, `null`, arrays, and plain objects. It has no way to write down a function. A component is a function. So the code of `CartLine` cannot travel inside `postponed`.

That is why `resume` takes a second argument beside `postponed`. React's docs call this argument `reactNode`. They describe it as "The React node you called `prerender` with. For example, a JSX element like `<App />`."

Look at what each call can do:

```jsx title="postponed alone vs. <App /> and postponed together"
resume(~postponed~); // **WRONG:** resume needs <App /> first, so this throws a TypeError on the server
resume(~<App />, postponed~); // The code from our files, and the place where the build stopped: makes Cart: 2
```

Saving `postponed` looks like saving the unfinished part of the page. **It may look the same, but it is NOT the same thing!** `postponed` tells React where the render stopped. The code that finishes the render still comes from `<App />`. React's docs give no way to resume from `postponed` alone.

### The Same `App.jsx`, Imported Twice

Now compare the two places where `<App />` is written:

```jsx title="The <App /> of build.js and the <App /> of server.js"
await prerender(~<App />~, { signal: controller.signal }); // build.js: imported from ./src/App.jsx
await resume(~<App />~, postponed); // server.js: imported from the same ./src/App.jsx
```

**Yes, it is the exact same thing!** Both come from the same `App.jsx`, imported twice and run at two moments. That is exactly what `reactNode` asks for.

Passing only the unfinished part does not work. Suppose the server resumes with `<CartLine />` in place of `<App />`. The server's terminal shows this error:

```text title="The terminal when server.js resumes with CartLine"
Error: Expected the resume to render <App> in this slot but instead it rendered <CartLine>. The tree doesn't match so React will fallback to client rendering.
```

Alice sees `Loading cart...` until the bundle loads and the browser renders her cart by itself.

This has a practical result. Nothing goes from the build to the server except the two files in the dist folder. So the request server needs its own copy of our source files, from `App.jsx` down to `cart.js`. Deploy only the dist folder to it, and it has no `App` to pass to `resume`. Alice never gets her cart.

Remember: `postponed` says where the build stopped. `<App />` brings the code.

## PRINCIPLE | `resume`: the render starts again at `App`, and only fully prerendered components are skipped

> [!PRINCIPLE]
> **Principle 2: Re-rendering From the Root: `resume` Calls `App` Again and Skips Only Fully Prerendered Components**
>
> *`resume` does not jump straight to the unfinished part; it renders our components again on the server, starting from `App`, and skips only a component that finished prerendering together with all its children.*
>
> On the page, only the missing part arrives, so resuming looks like running only what is missing. On the server, React starts again at the root, calls every component on the path down to the unfinished one, and skips the components that were complete at build time. Code in `App` therefore runs at build time and again for every visitor.
>
> **DO THIS:**
> ```jsx
> const { prelude, postponed } = await prerender(<App />, { signal: controller.signal, bootstrapScripts: ['/main.js'] });
> ~console.log('Blue Sneakers built');~ // build.js: runs once, at build time
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   ~console.log('Blue Sneakers built');~ // **WRONG:** resume calls App again, so this also prints at every request
>   return (
>     <html>
>       <body>
>         <main>
>           <ProductInfo />
>           <Suspense fallback={<p>Loading cart...</p>}>
>             <CartLine />
>           </Suspense>
>         </main>
>       </body>
>     </html>
>   );
> }
> ```

"Resume where it stopped" sounds like "run only what is missing". On the page, it even looks that way: only `Cart: 2` arrives. **It may look the same, but it is NOT the same thing!** On the server, `App` runs again.

You can see this for yourself. Put one `console.log` in each component, and watch the terminal. These log lines are for this principle only.

`ProductInfo` holds the heading and the price, and reads no data:

```jsx title="src/ProductInfo.jsx"
export default function ProductInfo() {
  ~console.log('ProductInfo renders');~ // Reads no data, so it finishes at build time
  return (
    <>
      <h1>Blue Sneakers</h1>
      <p>$89</p>
    </>
  );
}
```

`App` renders `<ProductInfo />` in place of its old heading, and prints a line of its own:

```jsx title="src/App.jsx"
import { Suspense } from 'react';
import ProductInfo from './ProductInfo.jsx';
import CartLine from './CartLine.jsx';

export default function App() {
  ~console.log('App renders');~ // Prints each time React calls App
  return (
    <html>
      <body>
        <main>
          <ProductInfo />
          <Suspense fallback={<p>Loading cart...</p>}>
            <CartLine />
          </Suspense>
        </main>
      </body>
    </html>
  );
}
```

In `CartLine`, the log line sits below `use`:

```jsx title="src/CartLine.jsx"
import { use, useState } from 'react';
import { getCart } from './cart.js';

export default function CartLine() {
  const cart = use(getCart());
  ~console.log('CartLine renders');~ // Below use: prints only once the visitor's cart has arrived
  const [count, setCount] = useState(cart.count);
  return (
    <>
      <p>Cart: {count}</p>
      <button onClick={() => setCount(count + 1)}>Add to cart</button>
    </>
  );
}
```

The page Alice sees does not change. Only the terminal tells us which components ran.

### What the Terminal Shows at Build Time and at Request Time

When the build runs, the terminal shows this:

```text title="The terminal while build.js runs"
App renders
ProductInfo renders
DOMException [AbortError]: This operation was aborted
```

`CartLine renders` is missing. The build stops `prerender` with `controller.abort()`, a moment after it starts. At that moment, `CartLine` was still waiting for the cart at `use`, so it never reached its log line. The last line is the reason React prints when `prerender` stops, and the lines of its stack trace follow it (as seen in Lesson 103).

Hours later, Alice's request reaches the server, and the terminal shows this:

```text title="The terminal when Alice's request reaches server.js"
App renders
CartLine renders
```

**At request time, `App` prints a second time, and `ProductInfo` does not print at all.** Here is what React does, in order:
1. The server calls `resume(<App />, postponed)`.
2. React starts at the root of that tree and calls `App` again. `App renders` appears in the server's terminal, although no line of the server file calls `App` itself.
3. React reaches `ProductInfo`. It finished at build time together with all its children, so React skips it. No `ProductInfo renders` appears.
4. React reaches the `<Suspense>` around `CartLine`, the part that did not finish at build time, and calls it. It waits for Alice's cart, and then `CartLine renders` appears.
5. The stream sends `Cart: 2` in place of `Loading cart...`.

The page still shows `Blue Sneakers` only once. The heading came from the file, and the stream from `resume` brings only the missing part:

```page caption="The Blue Sneakers page after resume: one heading from the file, and Alice's cart from the stream."
url: shop.example.com/blue-sneakers
heading: Blue Sneakers
line: $89
line: Cart: 2 | good
line: [Add to cart]
```

React's docs state the rule in two sentences. First: "`resume` re-renders from the root until it finds a component that was not fully pre-rendered." **Re-render from the root** means React starts again at `App`, the top of the tree we pass in, and walks down. Second: only fully prerendered components "are skipped entirely". The docs define **fully prerendered** as "the Component and its children finished prerendering". **Skipped** means React does not call that component at request time.

### `App` vs. `ProductInfo`: both finished their markup, only `ProductInfo` is skipped

`ProductInfo` and `CartLine` sit side by side in `App`, and React treats them differently at request time:
- **`ProductInfo` reads no data.** It finished at build time with all its children, so `resume` skips it.
- **`CartLine` waits for `getCart`.** It did not finish, so `resume` renders it.

Now look at `App`. From the build's point of view, `App` and `ProductInfo` look alike: both finished their own markup at build time. **They may look the same, but at request time they are NOT the same thing!** `App` has `CartLine` below it, and that component did not finish. So `App` is not fully prerendered, and `resume` calls it again.

```tree caption="Which of our three components resume calls at request time, and why."
Our three components when Alice's request arrives
- !`App` [`App renders`] | Finished its own markup, **but `CartLine` below it did not** | Not fully prerendered: **called again**
- +`ProductInfo` [no log line] | Finished at build time **with all its children** | Fully prerendered: **skipped**
- !`CartLine` [`CartLine renders`] | **Waited for the cart** and never finished | Unfinished: **rendered for Alice**
```

### Mistake: Build-Only Work Inside `App`

A developer wants one line in the build output for each page that is built. The heading of `App` comes from the file, so they expect `App` to run only at build time. They write the line at the top of `App`:

```jsx title="src/App.jsx" bad="6"
import { Suspense } from 'react';
import ProductInfo from './ProductInfo.jsx';
import CartLine from './CartLine.jsx';

export default function App() {
  ~console.log('Blue Sneakers built');~ // **WRONG:** resume calls App again, so this prints for every visitor too
  return (
    <html>
      <body>
        <main>
          <ProductInfo />
          <Suspense fallback={<p>Loading cart...</p>}>
            <CartLine />
          </Suspense>
        </main>
      </body>
    </html>
  );
}
```

The line prints once at build time. Then it prints again in the server's terminal at every request. The same goes for any code in `App`, and in every component on the path down to `CartLine`. A slow calculation placed there is paid again by every visitor. Work that belongs only to the build goes in the build file, after `prerender` returns.

Remember: resuming does not jump to the missing part. It starts again at `App`.

## PRINCIPLE | `hydrateRoot`: `Add to cart` answers a tap only after the browser hydrates the page

> [!PRINCIPLE]
> **Principle 3: Resuming Is Not Hydration: `Add to cart` Answers Only After `hydrateRoot`**
>
> *`resume` only makes HTML on the server; for `Add to cart` to answer a tap, the browser must still load the bundle with the component code and call `hydrateRoot(document, <App />)`, and Effects run only then.*
>
> `resume` and `hydrateRoot` both take `<App />` and both continue a page the server started, so the word "resume" is easy to read as "no hydration". In React, `resume` continues the server render and gives HTML. Our `onClick` is a JavaScript function, and the HTML text does not carry it, so the handler arrives with the bundle, and `hydrateRoot` connects it to the button.
>
> **DO THIS:**
> ```jsx
> await prerender(<App />, { signal: controller.signal, ~bootstrapScripts: ['/main.js']~ }); // build.js: writes the script tag for the bundle
> hydrateRoot(document, <App />); // src/main.jsx: makes Add to cart answer
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> await prerender(<App />, ~{ signal: controller.signal }~); // **WRONG:** no bootstrapScripts, so the bundle never loads and Add to cart never answers
> ```

Remember a plain HTML page with a button. The server sends `<button>Add to cart</button>`, and the browser draws it. Tap it, and nothing happens. The HTML is only text, and a click handler is a JavaScript function that lives in a script, not in that text. The button answers only after a script runs and calls `addEventListener` on it.

React works the same way. The HTML from `resume` draws a button that looks ready, but nothing listens to it yet. The function `() => setCount(count + 1)` lives in the cart file. The only way it reaches the browser is the bundle. `hydrateRoot` is the step that connects it to the button.

### `resume` in the Server File vs. `hydrateRoot` in the Browser File

Both calls take `<App />`, and both continue a page that the server started. **They may look the same, but they are NOT the same thing!** Here is the difference, seen from four sides:

| | With `resume` | With `hydrateRoot` |
| :--- | :--- | :--- |
| **Where it runs** | On the server | In the browser |
| **What it takes** | `<App />` and `postponed` | `document` and `<App />` |
| **What it gives** | A stream of HTML | A root that answers clicks |
| **Which package** | `react-dom/server` | `react-dom/client` |

React's own example of `resume` shows the same order. Its code has three parts, with the comments "Layer 1" for `prerender`, "Layer 2" for `resume`, and "Layer 3" for `hydrateRoot`. The button in that example says it plainly: "Clicking me requires hydration."

Now look at the `<App />` in each call. The server imports `App.jsx`. The browser gets the same `App.jsx` inside the bundle `/main.js`. **Yes, it is the exact same file!** The browser cannot hydrate without it. So the component code of our page does reach the browser: `App`, `ProductInfo`, and `CartLine` are all in the bundle.

### An Effect Shows the Moment `Add to cart` Starts to Answer

To see when the page starts to answer, we add one Effect to `CartLine`. The log lines of Principle 2 are gone, and the Effect is the only new code:

```jsx title="src/CartLine.jsx"
import { use, useState, useEffect } from 'react';
import { getCart } from './cart.js';

export default function CartLine() {
  const cart = use(getCart());
  const [count, setCount] = useState(cart.count);

  ~useEffect~(() => { // Runs only in the browser, after hydrateRoot
    console.log('Cart is interactive');
  }, []);

  return (
    <>
      <p>Cart: {count}</p>
      <button onClick={() => setCount(count + 1)}>Add to cart</button>
    </>
  );
}
```

React's own `resume` example does the same thing, with `console.log("reached interactivity!")`.

**`Cart: 2` and `Add to cart` are on the screen before the button answers a tap.** Here is what happens, in order:
1. The stream from `resume` arrives. Alice sees `Cart: 2` and `Add to cart`.
2. Alice taps `Add to cart` at once. Nothing happens. The HTML holds the button, but no `onClick` is connected to it yet.
3. The server's terminal never shows `Cart is interactive`, neither at build time nor at request time. React's docs: "Effects **only run on the client.** They don't run during server rendering."
4. The browser loads `/main.js`, the bundle with all three components. `prerender` wrote the script tag for it, from `bootstrapScripts` (as seen in Lesson 103).
5. `hydrateRoot(document, <App />)` runs `App` again in the browser, and calls every component below it. Even `ProductInfo` runs here, although `resume` skipped it on the server.
6. React connects itself to the HTML from the build and the server, and the browser's Console shows `Cart is interactive`.
7. Alice taps `Add to cart` again, and her cart goes from 2 to 3.

### `postponed` Never Reaches the Browser

The `onClick` of `Add to cart` comes from our code in the bundle, and React connects it to the button the server sent (as seen in Lesson 104). `postponed` plays no part in that. It goes from the build to `resume`, on the server, and stops there. In the browser, `CartLine` runs again. It reads the cart with `use(getCart())` and keeps the count in `useState`, just as it did on the server.

```tree dir=right caption="The three steps of the resumed page: prerender at build time, resume at request time, hydrateRoot in the browser."
How the Blue Sneakers page becomes interactive
- +1. Build time [`prerender`] | Makes **`Blue Sneakers`**, **`$89`**, and **`Loading cart...`** | Saves the unfinished work as **`postponed`**
- +2. Request time [`resume`] | Runs **on the server** with `postponed` and `<App />` | Streams **`Cart: 2`**, with **no click handler**
- +3. In the browser [`hydrateRoot`] | Loads **`/main.js`** and runs **`App` again** | **`Add to cart` answers**, and the Effect runs
```

### Mistake: No Bundle, Because Resuming Sounds Like No Hydration

The interview question itself invites this mistake. Here is how it happens:
1. A developer reads that resuming means "shipping server state without shipping component code".
2. They take the word the way other frameworks use it. There, "resumability" means that the browser runs a click handler without running any component first.
3. They expect the React page to need no bundle and no hydration.
4. They leave `bootstrapScripts` out of `prerender`, or they delete the browser file.
5. The page shows `Cart: 2` and `Add to cart`, and the tap never answers.

React's docs describe no such step. Every HTML made by React's server APIs still needs hydration to answer a click. The server state that travels in React is `postponed`, and it travels from the build to the request server, not to the browser. The component code still reaches the browser, in the bundle.

Remember: `resume` makes HTML on the server. `hydrateRoot` makes it answer, in the browser.

The build file runs once, at build time:

```jsx title="build.js"

import { prerender } from 'react-dom/static';
import App from './src/App.jsx';

const controller = new AbortController();
setTimeout(() => controller.abort());

const { prelude, postponed } = await ~prerender~(<App />, { // 1. Build time: makes the heading, the price, and the fallback
  signal: controller.signal,
  bootstrapScripts: ['/main.js'],
});
await mkdir('dist', { recursive: true });
await writeFile('dist/blue-sneakers.html', prelude);
await writeFile('dist/blue-sneakers.json', ~JSON.stringify(postponed)~); // Principle 1: only JSON text crosses to the server
```

The server file runs for each visitor's request:

```jsx title="server.js"
import { readFile } from 'node:fs/promises';
import { resume } from 'react-dom/server';
import ~App~ from './src/App.jsx'; // Principle 1: the server's own copy of the component code

export async function handler(request) {
  return new Response(ReadableStream.from(sendPage()), { headers: { 'content-type': 'text/html' } });
}

async function* sendPage() {
  yield await readFile('dist/blue-sneakers.html');
  const postponed = JSON.parse(await readFile('dist/blue-sneakers.json', 'utf8'));
  const stream = await ~resume~(<App />, postponed); // 2. Request time: makes Cart: 2 for this visitor
  yield* stream;
}
```

The browser file runs in the browser:

```jsx title="src/main.jsx"
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';

~hydrateRoot~(document, <App />); // 3. In the browser, Principle 3: Add to cart answers a tap
```

### The Order in Which React Calls Our Components

React calls our components at three moments, and a different set of them each time:

```tree dir=right caption="Which components React calls at build time, at request time, and in the browser."
When React calls our three components
- +1. Build time: `prerender` [`App` `ProductInfo` `CartLine`] | Calls all three; **`CartLine` waits** for the cart and is stopped | The file holds **`Blue Sneakers`**, **`$89`**, and **`Loading cart...`**
- +2. Request time: `resume` [`App` `CartLine`] | Calls `App` again from the root, **skips `ProductInfo`**, renders `CartLine` | The stream fills in **`Cart: 2`**
- +3. In the browser: `hydrateRoot` [`App` `ProductInfo` `CartLine`] | Calls **all three** again and reuses the HTML | **`Add to cart`** answers a tap
```

| The question | The answer on our page |
| :--- | :--- |
| **What is resumed?** | The render that `prerender` stopped before `CartLine` had its cart, saved as `postponed`. |
| **From where?** | `postponed` from `dist/blue-sneakers.json`; the component code from the server's own import of `App`. |
| **What runs again on the server?** | `App` and `CartLine`. `ProductInfo` finished at build time, so `resume` skips it. |
| **What reaches the browser?** | The HTML of the file and of the stream, and the bundle `/main.js` with all three components. Never `postponed`. |
| **When does `Add to cart` answer?** | After `hydrateRoot(document, <App />)` runs in the browser. |

Remember the one sentence of this lesson. **Resuming splits one server render across two moments, build time and request time. Only `postponed` crosses between them, and the browser still hydrates the page afterwards.**

## For the Interview

> **The Interview Question:** What does resuming mean: shipping server state without shipping component code?

### How to Answer Clearly in 30 Seconds

"In React, resuming means continuing a server render that `prerender` stopped early. React calls this Partial Pre-rendering. The part of the page that is the same for everyone is made at build time, and the visitor's part is made at request time. Three facts answer the question:
1. **What is resumed, and from where**: the unfinished work is saved as `postponed`, a JSON-serializable, opaque object. At request time, the server loads it from storage and passes it to `resume` together with the same `<App />` it gave `prerender`, imported from its own files. No component code is inside `postponed`.
2. **What runs again**: `resume` re-renders from the root until it reaches the unfinished component. Only components that finished prerendering together with all their children are skipped.
3. **Why it is not hydration**: `resume` runs on the server and makes HTML. The browser still loads the bundle and calls `hydrateRoot`, and only then do click handlers and Effects start."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Is the server state shipped to the browser?"**
   No. The server state that travels is `postponed`, and it travels from the build to the request server. React's docs say it is "loaded from wherever you stored it", with redis, a file, or S3 as examples. It goes into `resume` on the server and stops there. What reaches the browser is HTML, first from the prerendered file and then from the stream of `resume`, plus the bundle for hydration. `postponed` must be JSON-serializable because it is saved in one place and loaded in another, possibly hours later. JSON has no way to write down a function, so component code cannot travel in it.
2. **"Does `resume` render the whole tree again?"**
   From the root down to the unfinished component. React's docs: "`resume` re-renders from the root until it finds a component that was not fully pre-rendered." A component that finished together with all its children at build time is skipped. On our page, `App` runs again because `CartLine` below it did not finish, and `ProductInfo` is skipped. And if `prerender` finished everything, `postponed` is `null`, and there is nothing to resume (as seen in Lesson 119).
3. **"Then what in React ships no component code to the browser?"**
   Server Components. React's docs: "Server Components are not sent to the browser", and "only the rendered output is sent to the client". That is a different feature from resuming (as seen in Lesson 101). With resuming, every Client Component on the page, such as `CartLine`, still ships in the bundle and is hydrated. What a Server Component sends to the browser in place of its code comes later (Lesson 124).

```tree dir=right caption="Interview summary: what resuming moves, where it runs, and what still happens in the browser."
Resuming in React vs. hydration
- +Resuming [`prerender` `resume`] | Continues **the server render** from `postponed` | Runs **on the server** and makes **HTML**
- +Hydration [`hydrateRoot`] | Runs **our components again in the browser** | Connects **click handlers** and starts **Effects**
- !Not in React [no component runs in the browser] | A click handler that runs **without hydration** | React's docs **describe no such step**
```
