# Lecture 42: How useActionState Remembers the Last Answer and the Pending Flag

*(How does a form show what its last submit answered, and whether a submit is still running?)*

> INTERVIEW QUESTION | ❱ CORE | How does useActionState manage a form's submitted state and pending flag?

---

## VS | A plain form action `action={signup}` vs. the action from the Hook `action={signupAction}`: the plain action loses what it returns, the Hook keeps it as state

**`useActionState` wraps a form action so React saves the value your action returns as state and gives you an `isPending` flag while it runs.**

Say a user fills out a signup form and clicks Subscribe. While the server checks their email, the button should show a loading message. Once the server finishes, the page should display the confirmation text that your action function returned.

**Why:** When you pass a plain function to `<form action={signup}>`, React calls your function on submit and ignores whatever value `signup` returns. Without `useActionState`, you would have to create extra `useState` variables for the returned message and the loading flag, and update both by hand.

Let's start where Lesson 41 ended. You put a function in `action`, and React calls it with the form data. Now say the function returns a text:

```jsx title="A plain form action, as in Lesson 41"
function signup(formData) {
  ~return 'Thanks, you are signed up!';~ // React calls signup, and then ignores this text
}

<form action={signup}>
```

So where does that text go? Nowhere. React calls a plain form action and does nothing with what it returns. There is no error. The text is simply lost.

In plain JavaScript, this is never a problem. You call the function yourself, so you catch its answer in a variable:

```js title="Plain JavaScript: you call the function, so the answer is yours"
const message = ~signup(formData)~; // You called it, so you get what it returns
document.getElementById('message').textContent = message;
```

In React, you never call the action. The form calls it, when the user clicks the submit button. So you never get to write that first line. Something must catch the answer for you.

That is the job of `useActionState`. It is how you ask React: "When you call my action, keep what it returns, and give it back to me as state."

```jsx title="React: useActionState catches the answer for you"
const [message, signupAction, isPending] = ~useActionState(signup, null)~; // message starts as null, then holds what signup returned

<form action={~signupAction~}> {/* The form calls signupAction, and signupAction calls signup */}
```

> [!DEFINITION]
> **What is a form action?** [REVIEW] A form action is a function you pass to the `action` prop of a `<form>`: `<form action={signup}>`.
> When the user submits the form, React calls it with one argument, the form data, a `FormData` object. You read a field with `formData.get('email')`.
> The page does not reload, and after the action ends without an error, React empties every uncontrolled field.
> Something that can be tricky: React does nothing with what a plain form action returns (Lesson 41).

> [!DEFINITION]
> **What is useActionState?** [NEW] `useActionState` is a React Hook that keeps what your action returned last time, as state.
> You give it two things: your action, and the initial state. `useActionState(signup, null)` means "start the state as `null`, and call `signup` on every submit".
> It gives back three values, in order: the current state, a new action for the form, and `isPending`.
> The form must get that new action, not your own function. React built it around your function, and only it stores the answer.
> The name says what it holds: the state that comes out of an action (Lesson 42).

The second job is the wait. A real sign-up talks to a server, and that takes time. During the wait, the button should read "Signing up..." and refuse a second click.

React already tracks the wait of every action (Lesson 41). But a plain form action gives your component no variable to read it. `useActionState` does: its third value.

> [!DEFINITION]
> **What is isPending?** [NEW] `isPending` is the third value of `useActionState`. It is a flag: a variable that is either `true` or `false`.
> Pending means waiting. `isPending` is `true` from the moment the user submits, until the answer of the action is on the screen.
> React turns it on and off by itself. Your code never sets it.
> So once more: what your action returns becomes state, and while your action runs, `isPending` is `true` (Lesson 42).

```tree caption="A plain form action vs. the same action given to useActionState."
What happens to the answer of `signup`
- !A plain form action [`action={signup}`] | React calls `signup` and **ignores what it returns** | No message on the screen, and **no variable for the wait**
- +The same action through `useActionState` [`action={signupAction}`] | React calls `signup` and **stores what it returns** as `message` | The message is on the screen, and **`isPending`** tracks the wait
```

### The Rule of Thumb: does the screen show the answer of the last submit?

**If the screen shows what the last submit answered, use `useActionState`. Return every answer from the action, and read `isPending` for the button.**

Without this Hook, you keep both values by hand. One `useState` holds the message, a second `useState` holds the pending flag, and your code sets each one at the right moment. Forget one line, and the user sees it:
1. The button stays on "Signing up..." forever, and the user cannot try again.
2. Or the thanks line of the last email stays on the screen, while the new email was refused.

Developers really choose between three ways for this same job:
1. **Two `useState` calls, set by hand in a submit handler** (Lessons 33 and 40). This works in any React version, and in code that is not a form action.
2. **`useState` with `useTransition`**, which a later lesson teaches. This fits when several actions must run at the same time. The React docs: "If you want to perform Actions in parallel, use `useState` and `useTransition` directly."
3. **`useActionState`**. This fits when the screen shows the answer of the last submit, and the submits run one after the other.

This lesson teaches the third way. Principle 4 puts it next to the first.

A senior developer also knows the four classic mistakes:
1. **The form gets your own function.** Your function runs, but its answer goes nowhere, and the Console stays quiet.
2. **The action keeps one parameter.** React puts the previous state first, so the form data is in the wrong place, and the page goes blank.
3. **A known error is thrown.** It never reaches the screen as a message. The whole form disappears instead.
4. **A pending flag written by hand.** One request that throws skips the line that turns it off, and the button freezes.

The rest of the lesson shows each mistake on a real sign-up form.

So after every submit, the form must remember two things:
1. **What the last submit answered**: the thanks text or the error text. That is the state.
2. **Whether a submit is still running**: so the button can read "Signing up..." and refuse a second click. That is `isPending`.

The project has three files:

```files title="newsletter: File Explorer" caption="How the files of our sign-up form sit inside src/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports the default export of `./App.jsx` and mounts it, unchanged from Lesson 7
  App.jsx | form | Holds the `signup` action and exports `Newsletter` as default
  api.js | stand-in server | Exports `signUp`, which answers after one second, from Principle 3
```

The file api.js stands in for a real server, as in Lesson 41. It is given, not taught. It keeps an array of the emails already signed up, waits one second, and answers in one of two ways:
1. **An error text**, when the email is already in the array.
2. **`null`**, when the sign-up went through.

```js title="src/api.js"
const emails = [];

export async function signUp(email) {
  await new Promise(resolve => setTimeout(resolve, 1000));
  if (emails.includes(email)) {
    return 'This email is already signed up';
  }
  emails.push(email);
  return null;
}
```

The one-second wait is there only so that you can see the pending state on the screen.

Now let's build the form, and break it on the way:

**PRINCIPLES:** What your action returns becomes state. While your action runs, `isPending` is `true`. Four principles follow:
1. **Principle 1: The Form Gets the Action That useActionState Returns.** Give the form `signupAction`. Give it your own `signup`, and the answer goes nowhere.
2. **Principle 2: The Previous State Comes First, the Form Data Second.** Write the action as `signup(previousState, formData)`, even when it never reads the previous state.
3. **Principle 3: What the Action Returns Becomes the Message.** Return a known error such as "already signed up". Throw only for failures you did not expect.
4. **Principle 4: React Turns isPending On and Off.** The button reads "Signing up..." with no extra `useState`, and with no line for you to forget.

## PRINCIPLE | `useActionState`: the form gets `signupAction`, and React keeps what `signup` returns

> [!PRINCIPLE]
> **Principle 1: The Form Gets the Action That useActionState Returns**
>
> *Call `useActionState(signup, null)` at the top of the component, destructure the state, the action, and `isPending`, and give the form the returned action.*
>
> React stores the answer only when the form calls the action that `useActionState` built. That action calls your `signup`, catches what it returns, and stores it as the new state. When the form gets your own `signup`, it still runs, but its answer goes nowhere, and no error tells you.
>
> **DO THIS:**
> ```jsx
> const [message, signupAction, isPending] = useActionState(signup, null);
>
> <form action={~signupAction~}> {/* React stores what signup returns in message */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [message, signupAction, isPending] = useActionState(signup, null);
>
> <form action={~signup~}> {/* **WRONG:** signup runs, but message stays null and no line appears */}
> ```

### The first sign-up form

Here is the first version of the form in the App file. For this first step, `signup` ignores the email and returns one fixed text:

```jsx title="src/App.jsx"
import { useActionState } from 'react';

function signup() {
  return 'Thanks, you are signed up!';
}

export default function Newsletter() {
  const [message, signupAction, isPending] = ~useActionState(signup, null)~; // Three values: the state, the action, the flag

  return (
    <form action={~signupAction~}> {/* The form gets signupAction, not signup */}
      <h2>Get our weekly news</h2>
      <label>
        Email <input name="email" />
      </label>
      <button>Sign up</button>
      {~message &&~ <p>{message}</p>} {/* No line while message is null */}
    </form>
  );
}
```

`useActionState` takes two arguments:
1. **`signup`**: your action, the function that does the work when the user submits.
2. **`null`**: the initial state, what `message` holds before the first submit.

It gives back three values. Array destructuring gives each one a name of your choice, in order (Lesson 12):
1. **`message`**: the current state. On the first render, it is `null`. After each submit, it is what `signup` returned.
2. **`signupAction`**: the action for the form. React builds it around your `signup`. The React docs call it `dispatchAction`. To dispatch means to send off: each call sends one new submit to React.
3. **`isPending`**: `true` while a submit runs. Principle 4 uses it.

When the page opens, `message` is `null`. So React renders no `<p>` under the button:

```page caption="The sign-up form on the first render: message is null, so no line appears."
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
```

The user types `john@example.com` and clicks Sign up. The line appears, and the `<input>` field is empty again:

```page caption="The sign-up form after the user clicks Sign up: the text that signup returned is on the screen."
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
line: Thanks, you are signed up! | good
```

The empty field is the reset from Lesson 41. The `<input>` field has no `value`, so it is uncontrolled, and the action ended without an error. So React emptied it.

### Who calls signup? React does

Your code calls neither `signup` nor a setter, yet the line changed. Here is what happens after the click on Sign up:
1. The form calls the function in its `action` prop: `signupAction`.
2. `signupAction` calls your `signup`.
3. `signup` returns `'Thanks, you are signed up!'`.
4. React stores that text as the new `message` and renders `Newsletter` again. Now `message` is not `null`, so the line appears.

### VS | A setter `setMessage` vs. an action `signupAction`: your code calls the setter, the form calls the action

The first line looks a lot like a `useState` line. Put the two side by side:

```jsx title="With useState and with useActionState"
const [message, ~setMessage~] = useState(null); // Two values: your code calls setMessage with the new message
const [message, ~signupAction~, isPending] = useActionState(signup, null); // Three values: the form calls signupAction
```

It may look the same, but it is NOT the same thing! Both give a `message` that starts as `null`. The difference is the second value:
- **With `useState`**, the second value is a setter. Your code calls it and hands it the new message.
- **With `useActionState`**, the second value is an action. Your code never hands it a message. The form calls it, React calls `signup`, and React stores what `signup` returns.

```tree caption="The second value of useState is a setter your code calls; the second value of useActionState is an action the form calls."
Where the new `message` comes from
- +With `useState` [`setMessage`] | Your code **calls the setter** with the new message | Two values: **`message`** and **`setMessage`**
- +With `useActionState` [`signupAction`] | The **form calls the action**, and React stores **what `signup` returns** | Three values: **`message`**, **`signupAction`**, and **`isPending`**
```

### Mistake: the form gets signup itself

A developer gives the form `signup` itself, out of habit from Lesson 41:

```jsx title="src/App.jsx" startLine="11" bad="1"
    <form action={~signup~}> {/* **WRONG:** signup runs, but React does nothing with what it returns */}
```

The user clicks Sign up. `signup` runs, but no line appears under the button, and the Console stays quiet.

Why? Because this is a plain form action again, and React ignores what a plain form action returns. Only `signupAction` stores the answer in `message`. Your own `signup` knows nothing about `message`.

### Mistake: calling the action while the component renders

Another developer wants the form to run once when the page opens, so they call the action in the component body:

```jsx title="src/App.jsx" startLine="7" bad="3"
export default function Newsletter() {
  const [message, signupAction, isPending] = useActionState(signup, null);
  ~signupAction()~; // **WRONG:** runs on every render, and each call asks for another render
```

This would never stop. The call asks for a new state, a new state means a new render, and that render calls the action again. So React stops it at once, with an error that reads: Cannot update action state while rendering.

Call the action only in answer to the user. Here, that means only when the user submits the form.

Remember: the form gets `signupAction`, and React keeps what `signup` returns.

## PRINCIPLE | `signup(previousState, formData)`: the previous state comes first, the form data second

> [!PRINCIPLE]
> **Principle 2: The Previous State Comes First, the Form Data Second**
>
> *Write an action given to `useActionState` as `signup(previousState, formData)`, even when it never reads `previousState`.*
>
> A plain form action receives the form data first. Through `useActionState`, React puts one more value in front of it: the previous state. An action that keeps the old one-parameter shape reads the email from the previous state, which is `null` on the first submit, and the submit fails with a `TypeError`.
>
> **DO THIS:**
> ```jsx
> function signup(~previousState, formData~) { // formData holds the form data
>   const email = formData.get('email');
>   return `Thanks! ${email} is signed up.`;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function signup(~formData~) { // **WRONG:** formData holds the previous state, null on the first submit
>   const email = formData.get('email');
>   return `Thanks! ${email} is signed up.`;
> }
> ```

### Two parameters, not one

Now `signup` must read the email. In Lesson 41, an action had one parameter, the form data. Through `useActionState`, React calls it with two:

```jsx title="With formData alone and with previousState first"
function signup(~formData~) { // A plain form action: React passes the form data first
  const email = formData.get('email');
}

function signup(~previousState, formData~) { // Through useActionState: the previous state first, the form data second
  const email = formData.get('email');
}
```

It may look the same, but it is NOT the same thing! Both read the email with the same line. But who calls the function decides what arrives in each place:
- **A plain form action** is called by React with the form data in first place.
- **An action given to `useActionState`** is called through `signupAction`, and `signupAction` puts the previous state first. So the form data moves to second place.

### What previousState holds

`previousState` holds what `signup` returned last time:
1. On the first submit, it is the initial state, our `null`.
2. On every later submit, it is what `signup` returned on the submit before.

You have seen this shape before, in a reducer. A reducer gets the current state and returns the next state (Lesson 27). That is why the React docs call the function you give to `useActionState` a `reducerAction`.

> [!DEFINITION]
> **What is a reducer?** [REVIEW] A reducer is a function that gets the current state and an action, and returns the next state. You give it to `useReducer`.
> A reducer must be pure: it only calculates. It never sends a request to a server.
> The function you give to `useActionState` has the same shape: the previous state in, the new state out. The difference: it may have side effects, such as a request to a server. That is why the docs call it an Action too (Lesson 27).

Our `signup` does not read `previousState` yet. It must still keep the first place, because React fills the places in order.

### Mistake: keeping the one-parameter shape

A developer has a working plain form action. To show a message, they wrap it in `useActionState`, but they leave its parameters as they were:

```jsx title="src/App.jsx" startLine="3" bad="1"
function signup(~formData~) { // **WRONG:** React puts the previous state here, so formData holds null
  const email = formData.get('email');
  return `Thanks! ${email} is signed up.`;
}
```

**The page opens fine, but the first submit wipes out the whole form.** Here is what happens:
1. The user types `john@example.com` and clicks Sign up.
2. React calls `signup` with `null` first and the form data second.
3. So the parameter named `formData` holds `null`.
4. `formData.get('email')` fails, because `null` has no get method. JavaScript throws a `TypeError`.

The thanks line never appears. The whole form disappears, and the Console shows the error:

```page caption="The page after the first submit when signup keeps the one-parameter shape: the sign-up form is gone."
blank
console: Uncaught TypeError: Cannot read properties of null (reading 'get')
  warn: An error occurred in the <Newsletter> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The form disappears for the same reason as in Lesson 41. React sends an error thrown by an action to the nearest error boundary, the component that catches an error and shows a fallback screen (Lesson 38). Our page has none, so React removes the whole page. The user cannot even try again without reloading.

### The fix: add previousState in first place

Add `previousState` as the first parameter. Now `formData` holds the form data, and the email reaches the line:

```jsx title="src/App.jsx" startLine="3" good="1"
function signup(~previousState, formData~) { // React fills previousState first, then formData
  const email = formData.get('email');
  return `Thanks! ${email} is signed up.`;
}
```

```page caption="The sign-up form after the user signs up with john@example.com: the line now names the email."
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
line: Thanks! john@example.com is signed up. | good
```

```tree caption="What arrives in each parameter when useActionState calls the action on a submit."
What React passes to `signup` through `signupAction`
- !One parameter, `formData` [`formData`] | The only parameter gets the **previous state**, `null` on the first submit | `formData.get` fails with a **`TypeError`**
- +Two parameters, `previousState` and `formData` [`previousState` `formData`] | First place: the **previous state**; second place: the **form data** | `formData.get` reads **`john@example.com`**
```

Remember: through `useActionState`, the previous state comes first, the form data second.

## PRINCIPLE | `return error`: what the action returns becomes the message on the screen

> [!PRINCIPLE]
> **Principle 3: What the Action Returns Becomes the Message**
>
> *Return every answer the user should read, including a known error such as an email already signed up; throw only for failures you did not expect.*
>
> `useActionState` gives your code no setter. The only way to change the message is to return a new value from the action: React stores it as the new state and renders the form again. A thrown error never becomes state. React sends it to the nearest error boundary, and the user never reads it under the button.
>
> **DO THIS:**
> ```jsx
> async function signup(previousState, formData) {
>   const error = await signUp(formData.get('email'));
>   if (error) {
>     ~return error;~ // The line shows "This email is already signed up"
>   }
>   return 'Thanks!';
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> async function signup(previousState, formData) {
>   const error = await signUp(formData.get('email'));
>   if (error) {
>     ~throw new Error(error);~ // **WRONG:** the text never reaches the line, and the whole form disappears
>   }
>   return 'Thanks!';
> }
> ```

### One action, two answers

There is no `setMessage` here. The message changes in one way only: through what the action returns. So one action that returns two different texts gives two different lines.

Now `signup` asks the stand-in server whether the email is new. It becomes `async`, because it waits for the server (Lesson 41):

```jsx title="src/App.jsx" startLine="1"
import { useActionState } from 'react';
import { signUp } from './api.js';

async function signup(previousState, formData) {
  const email = formData.get('email');
  const error = await ~signUp(email)~; // null when it went through, the error text otherwise
  if (error) {
    ~return error;~ // Answer 1: the error text becomes message
  }
  ~return `Thanks! ${email} is signed up.`;~ // Answer 2: the thanks text becomes message
}
```

Whichever text `signup` returns, React stores it as `message`, and the line shows it.

### Two submits, two lines, and no setter

**Two submits with the same email give two different lines, and no line of your code sets `message`.** Here is what happens:
1. The user types `john@example.com` and clicks Sign up. React calls `signup` with `null` and the form data.
2. `signUp` waits one second and returns `null`, because the email is new. So `signup` returns the thanks text, and React shows it.
3. The user types `john@example.com` again and clicks Sign up. This time React passes the thanks text as `previousState`.
4. `signUp` finds the email in its array and returns the error text. `signup` returns it, and React replaces the line.

::: row caption="The same email signed up twice: the first answer is the thanks text, the second is the error text."
::: col title="After the first sign-up" tag="thanks text" tone=good
```page size=mini
heading: Get our weekly news

  field: Email
  submit: Sign up
line: Thanks! john@example.com is signed up. | good
```
:::
::: col title="After the second sign-up" tag="error text" tone=bad
```page size=mini
heading: Get our weekly news
form:
  field: Email
  submit: Sign up
line: This email is already signed up | bad
```
:::

The `<input>` field is empty after both submits. For React, a returned error text is not an error. The action ended without throwing, so React empties the form as usual.

### VS | A returned error `return error` vs. a thrown error `throw new Error(error)`: only the returned one becomes state

"Already signed up" is a failure. So a developer may want to throw it, as they would inside a `try` block:

```jsx title="With return error and with throw new Error"
if (error) {
  ~return error;~ // The text becomes message, and the line shows it
}

if (error) {
  ~throw new Error(error);~ // **WRONG:** the text never reaches message
}
```

It may look the same, but it is NOT the same thing! Both stop `signup` at the same moment, with the same text. But only a returned value becomes state:
- **With `return error`**, React stores the text as `message`. The user reads "This email is already signed up" under the button.
- **With `throw new Error(error)`**, the text never becomes state. React sends the error to the nearest error boundary. Our page has none, so the whole form disappears, as in Principle 2.

The React docs draw the line between the two:
1. **A known error**, such as an email already signed up, is part of the answer. Return it, and show it on the screen.
2. **An error you did not expect**, such as a bug in the code, is thrown.

Remember: what the action returns becomes the message on the screen.

## PRINCIPLE | `isPending`: React turns the flag on and off, so the button never freezes

> [!PRINCIPLE]
> **Principle 4: React Turns isPending On and Off**
>
> *Read `isPending` from `useActionState` to disable the button and change its text while the action runs.*
>
> A button that reads Signing up... needs a flag that is `true` while the request runs and `false` again when the answer is on the screen. Written by hand, that flag needs two setter calls, and a request that throws skips the second one, so the button freezes. `useActionState` gives the flag as its third value, and React sets it, because React already knows when the action starts and ends.
>
> **DO THIS:**
> ```jsx
> <button disabled={~isPending~}> {/* React sets isPending around the action */}
>   {isPending ? 'Signing up...' : 'Sign up'}
> </button>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> setIsPending(true);
> const error = await signUp(email);
> ~setIsPending(false);~ // **WRONG:** skipped when signUp throws, so the button stays on Signing up...
> ```

### The Signing up... button

The third value of `useActionState` drives the button:

```jsx title="A button driven by isPending"
<button disabled={~isPending~}> {/* Refuses clicks while a sign-up runs */}
  {~isPending ?~ 'Signing up...' : 'Sign up'} {/* The text during the wait, and the text after */}
</button>
```

`disabled` is the HTML attribute that stops a button from being clicked. `isPending` is `true` from the moment the user submits, until React shows what the action returned.

### VS | A flag by hand `setIsPending` vs. the flag from the Hook `isPending`: React sets the flag, so there is no line to forget

Before this Hook, developers wrote the flag themselves, in a submit handler (Lesson 33). Here is the same form, with the message and the flag written by hand:

```jsx title="With setIsPending by hand"
const [message, setMessage] = useState(null);
const [isPending, setIsPending] = useState(false);

async function handleSubmit(e) {
  e.preventDefault();
  const email = new FormData(e.target).get('email');
  ~setIsPending(true);~ // Your code turns the flag on
  const error = await signUp(email);
  setMessage(error ? error : `Thanks! ${email} is signed up.`);
  ~setIsPending(false);~ // Your code must remember to turn it off
}
```

And here is the same flag with `useActionState`:

```jsx title="With isPending from useActionState"
const [message, signupAction, ~isPending~] = useActionState(signup, null); // React turns isPending on and off
```

On the button, yes, it is the exact same thing! For one submit, both buttons read "Signing up..." for one second, then "Sign up" again.

Only the `<input>` field differs. With the hand-written version, the email stays in the field. React empties the form only after a form action, and this form uses `onSubmit` instead (Lesson 41).

The difference that matters is in the code. With `useActionState`, both calls to `setIsPending` are gone. React already knows when the action starts and when its answer is on the screen.

### Mistake: the flag that never turns off

The hand-written version has one line that is easy to lose. When the request throws, the button freezes:
1. Your handler calls `setIsPending(true)`.
2. The request throws, for example when the network fails.
3. The line `setIsPending(false)` never runs.
4. The button stays on "Signing up..." and disabled. The user cannot try again.

The usual fix is a `try` block with a `finally` block around the request. With `useActionState`, there is no such line to forget. A request that throws inside the action goes to the nearest error boundary, as Principle 3 showed. It never leaves a frozen button behind.

### The old line stays until the new answer arrives

The finished button goes into the App file:

```jsx title="src/App.jsx" startLine="22"
      <button disabled={~isPending~}> {/* true while signup runs */}
        {isPending ? 'Signing up...' : 'Sign up'}
      </button>
```

Now watch a sign-up with a new email. **During the wait, the button reads Signing up..., but the line still shows the old answer.** Here is why:
1. The line from the last submit reads "Thanks! john@example.com is signed up."
2. The user types `mia@example.com` and clicks Sign up.
3. `isPending` becomes `true`, so the button reads "Signing up..." and cannot be clicked.
4. `signup` has not returned yet, so `message` has not changed. The old thanks line stays.
5. One second later, `signup` returns. In the same render, React shows the new line, and the button reads "Sign up" again.

## All 4 Principles Together

### The complete project

Here is the finished App file. The action keeps both parameters and returns every answer, and the button reads `isPending`:

```jsx title="src/App.jsx"
import { useActionState } from 'react';
import { signUp } from './api.js';

async function signup(~previousState, formData~) { // Principle 2: the previous state first, the form data second
  const email = formData.get('email');
  const error = await signUp(email);
  if (error) {
    ~return error;~ // Principle 3: a known error is returned and becomes message
  }
  return `Thanks! ${email} is signed up.`;
}

export default function Newsletter() {
  const [message, signupAction, isPending] = ~useActionState(signup, null)~; // Principle 1: the state, the action, the flag

  return (
    <form action={~signupAction~}> {/* Principle 1: the form gets the returned action */}
      <h2>Get our weekly news</h2>
      <label>
        Email <input name="email" />
      </label>
      <button disabled={~isPending~}> {/* Principle 4: React turns isPending on and off */}
        {isPending ? 'Signing up...' : 'Sign up'}
      </button>
      {message && <p>{message}</p>}
    </form>
  );
}
```

And here is the stand-in server it calls, unchanged:

```js title="src/api.js"
const emails = [];

export async function signUp(email) {
  await new Promise(resolve => setTimeout(resolve, 1000));
  if (emails.includes(email)) {
    return 'This email is already signed up';
  }
  emails.push(email);
  return null;
}
```

### What happens on one submit, in order

When the page opens, React renders `Newsletter` once. `message` starts as `null`. `isPending` starts as `false`. Then every submit follows the same four steps:

```tree dir=right caption="What happens, in order, from the click on Sign up to the new line under the button."
One submit of the sign-up form
- +1. The user clicks Sign up [`signupAction`] | The form calls **`signupAction`** with the form data | `isPending` becomes **true**: the button reads **Signing up...**
- +2. `signupAction` calls `signup` [`previousState` `formData`] | React passes the **previous state** first and the **form data** second | `signup` waits **one second** for `signUp`
- +3. `signup` returns a text [`return`] | React stores it as the new **`message`** | The line under the button shows **the new answer**
- +4. The same render [`isPending`] | `isPending` becomes **false** | The button reads **Sign up** again
```

| Aspect | With `useState` by hand | With `useActionState` |
| :--- | :--- | :--- |
| **The values** | Two `useState` calls, one for the message and one for the flag | One Hook gives the message, the action, and `isPending` |
| **The form** | An `onSubmit` handler that reads the form data itself | The form gets `signupAction` in its `action` prop |
| **The message** | Your code calls `setMessage` with the new text | React stores what `signup` returns |
| **A known error** | Your code calls `setMessage` with the error text | `signup` returns the error text |
| **The pending flag** | `setIsPending` before and after the request, often in `finally` | React sets `isPending` around the action |

One last time, the sentence of this lesson: **what your action returns becomes state. While your action runs, `isPending` is `true`.**

## For the Interview

> **The Interview Question:** How does useActionState manage a form's submitted state and pending flag?

### How to Answer Clearly in 30 Seconds

"`useActionState` takes an action and an initial state, and returns three values: the current state, an action to pass to the form, and `isPending`. When the user submits, React calls my action with two arguments: the previous state first and the form data second. Whatever my action returns becomes the new state, so the screen shows the answer of the last submit with no setter in my code. Three rules follow:
1. **The form gets the returned action**, not my own function. My own function would run, but React would ignore its answer.
2. **Known errors are returned, not thrown.** An email already signed up is part of the answer, so it becomes state and shows under the button. A thrown error goes to the nearest error boundary.
3. **`isPending` replaces the hand-written flag.** It is `true` while the action runs, so I disable the button with no second `useState` and no `finally` block."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does the action receive the previous state as its first argument?"**
   Because `useActionState` works like a reducer: the action turns the previous state into the next one. On the first submit, the previous state is the initial state. After that, it is what the action returned last time. The difference from `useReducer`: a reducer must be pure, while this action may send a request to a server. So the form data moves to second place. An action written in the one-parameter shape of a plain form action reads the form data from the wrong place.
2. **"What happens if the user submits the form twice before the first answer comes back?"**
   On our form, this cannot happen, because the button is disabled while `isPending` is `true`. Without `disabled`, React puts the second submit in a queue, a waiting line, and runs the submits one after the other. So each call receives the result of the one before. The React docs say this is intentional in the design of `useActionState`. `isPending` stays `true` until every submit in the queue has finished, and then React renders once with the final state. When several actions must run at the same time, the docs recommend `useState` with `useTransition` instead.
3. **"How do you show a server error with useActionState?"**
   A known error, such as an email already signed up, is part of the answer. So the action returns it as state, and the component renders it like any other message. An error the code did not expect is thrown. A thrown error never becomes state: React cancels every submit still waiting in the queue and passes the error to the nearest error boundary.

```tree dir=right caption="Interview comparison: what useState and useActionState share, and how the new message arrives."
`useState` vs. `useActionState` for a form message
- +`useState` [`setMessage`] | Keeps the message **between renders** | Your code **calls the setter**, and sets the pending flag **by hand**
- +`useActionState` [`signupAction` `isPending`] | Keeps the message **between renders** | React stores **what the action returns**, and sets **`isPending`** itself
```
