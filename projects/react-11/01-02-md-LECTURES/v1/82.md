# Lecture 82: How the Three Rules of React Keep a Stories Tray Working

*(If React, not your code, calls your components, what must your code promise React?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | What are the Rules of React, and how do the three rules interlock?

---

## VS | Writing the Tag vs. Calling the Component Yourself: both run the same function, only the tag lets React do the calling

> In plain JavaScript, you write a function, and you decide when to call it. **In React, you write the component, but React calls it, whenever it wants and as often as it wants, and React keeps its state between the calls.** So React asks your code for three promises, the Rules of React: let React do the calling, change nothing outside the call, and call the Hooks in the same order every time.

Remember a plain function call? You write `greet('John')`, and the function runs once, right there, because you called it:

```js title="Plain JavaScript: you call the function"
~greet('John')~; // Runs once, right now, because your code called it
```

A component is also a plain function: it takes props and returns JSX (Lesson 04). But you almost never call it yourself. You write a tag, and React calls the function for you:

```jsx title="React: you write a tag, and React calls the function"
return ~<Greeting name="John" />~; // React calls Greeting, when it decides and as often as it decides
```

When does React call it? On the first load. Again after every setter call in this component or in a component above it. And in development, Strict Mode calls it twice on every render, on purpose. You write the function once. React runs it many times, and you never decide when.

> [!DEFINITION]
> **What is Strict Mode?** [REVIEW] `<StrictMode>` is a component that wraps your app in the entry file, `main.jsx`.
> In development, it calls each of your components twice on every render, to show you what a second call breaks.
> In production, it does nothing at all, so a bug it would show stays hidden there (Lesson 47).

### Three Rules, One Fact

This one fact, React calls the component and not your code, is where all three **Rules of React** come from. React's documentation names them:
1. **React calls Components and Hooks.** You write the tag, such as `<StoryTray />`. You never call the component as a plain function, and you never pass a Hook around as a value.
2. **Components and Hooks must be pure.** React may call a component again at any moment, so one call must change nothing that existed before it ran.
3. **Rules of Hooks.** `useState` takes no name, so React finds the state of each Hook by counting the calls. Every render of a component calls the same Hooks in the same order.

The docs list the same three rules with purity first. This lesson starts with who calls the component, because that rule explains the other two. And the docs say these are rules, not just guidelines: when one is broken, the app likely has bugs.

```tree caption="The three Rules of React, each one side of the same fact: React runs the components, not your code."
React runs your components, so your code keeps three rules
- +React calls Components and Hooks [`<StoryTray />`] | Your code **writes a tag** | React decides **when and how often** to call the function
- +Components and Hooks must be pure | React may call a component **again** | One call **changes nothing** that existed before it ran
- +Rules of Hooks [`useState`] | React finds each Hook's state **by counting the calls** | Every render calls the **same Hooks in the same order**
```

### The Rule of Thumb: a tag for every component, nothing changed, Hooks at the top

**Write every component as a tag. Inside it, build new values and never change the values you received. Call every Hook at the top level of a component, never inside a loop or an `if`.**

Developers usually go wrong by reading the three rules as three separate style tips. They are one system. Here is the classic case. A list needs one state per row, so a developer moves the `useState` into a small `Row` component, at its top level, as the Rules of Hooks ask. Then, inside the loop, they call `Row` as a plain function:

```jsx title="Calling Row as a function, and writing its tag, inside the same map"
{items.map(item => ~Row({ item })~)} {/* Your code calls Row: its useState runs inside this loop */}
{items.map(item => ~<Row key={item.id} item={item} />~)} {/* React calls Row: each row keeps its own state */}
```

Both lines show the same rows on the first load. But only the second one is safe. The first line breaks the rule that React calls components, and by doing that, it also breaks the Rules of Hooks. The rest of the lesson shows exactly how, on a real screen.

```files title="stories-tray: File Explorer" caption="How the four files of the stories tray sit inside src/."

src/
  main.jsx | boundary | Renders `<App />` inside `<StrictMode>`
  App.jsx | parent | Holds `stories` in state and renders `<StoryTray>`
  StoryTray.jsx | child | Renders one tile per story and the Create Story tile
  StoryTile.jsx | child | From Principle 3 on: holds `seen` for one story
```

Here is what the user sees on this tray when one rule is broken:
1. **Break the purity rule**, and the tray shows Create Story twice on the first load in development. In production, the first load looks right, and one more Create Story tile appears each time the tray renders again.
2. **Break the Rules of Hooks**, and every tap on a story still works. Then the user taps Create Story, and the whole page goes blank, with an error about the order of Hooks.
3. **Break the rule that React calls components**, inside the list, and the user gets the same blank page after the same tap on Create Story.

**PRINCIPLES:** React calls the components, a call changes nothing outside itself, and the Hooks come in the same order every time. Five principles follow on the stories tray:
1. **Principle 1: React Calls StoryTray From Its Tag.** Writing `<StoryTray />` hands the call to React. Calling `StoryTray` as a function gives the same first page, but React only gets what came back.
2. **Principle 2: A Render Builds a New Array and Changes Nothing It Received.** A `push` into the `stories` prop changes `App`'s state, and Strict Mode's second call adds a second Create Story tile.
3. **Principle 3: useState Inside map Blanks the Page When the List Grows.** React counts the Hook calls. One more story means one more call, and React throws.
4. **Principle 4: StoryTile Called as a Function Runs Its useState in StoryTray.** The Hook joins the loop of the caller, so breaking the first rule breaks the third.
5. **Principle 5: Strict Mode Runs the Code, the Linter Reads It.** Strict Mode shows an impure render on the page. The React Hooks plugin for ESLint marks the broken line in the editor.

## PRINCIPLE | `<StoryTray />`: React calls the component, so React decides when and how often it runs

> [!PRINCIPLE]
> **Principle 1: React Calls Components and Hooks: Use a Component Only as a JSX Tag**
>
> *Write a component as a tag, such as `<StoryTray stories={stories} />`, and never call it as a function, so React decides when and how often it runs.*
>
> A direct call such as `StoryTray({ stories })` shows the same page on the first load, so the mistake is easy to miss. But React never meets the component. It only gets the returned list, so it cannot tie state to that component, compare it by type, pause between components, show it in the developer tools, or skip it.
>
> **DO THIS:**
> ```jsx
> export default function App() {
>   const [stories, setStories] = useState(initialStories);
>   return ~<StoryTray stories={stories} />~; // React calls StoryTray during render
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function App() {
>   const [stories, setStories] = useState(initialStories);
>   return ~StoryTray({ stories })~; // **WRONG:** App calls StoryTray itself, React only sees the list
> }
> ```

`StoryTray` is a function that returns JSX. So inside `App`, there are two ways to put the tray on the page. Write its tag, or call the function yourself:

```jsx title="Writing the StoryTray tag, and calling StoryTray as a function"
return ~<StoryTray stories={stories} />~; // React calls StoryTray when it renders App
return ~StoryTray({ stories })~; // App calls StoryTray itself and hands React only the list
```

Both lines run the same function with the same `stories`. Both put the same two stories on the page, and the Console stays empty in both:

```page caption="With the tag or with the direct call, the first load shows the same two stories."
line: Ankit's Story
line: Taylor's Story
```

```devconsole width=full caption="The Console on the first load, with the tag or with the direct call: no messages."
= No messages
```

So what is the difference? **Who calls `StoryTray`.**
- **With `<StoryTray stories={stories} />`**, `App` hands the function to React, and React calls it during render.
- **With `StoryTray({ stories })`**, `App` runs the function as an ordinary JavaScript call, inside its own render. React never meets a `StoryTray` component. It only gets the `<ul>` that came back.

The docs say it in two lines: "React must decide when your component function is called during rendering. In React, you do this using JSX."

```tree caption="Two ways to run StoryTray: write its tag so React calls it, or call it from App as a plain function."
Who calls `StoryTray`?
- +React calls it [`<StoryTray stories={stories} />`] | `App` **writes a tag** | React decides **when and how often** `StoryTray` runs
- !Your code calls it | `App` runs the function **as a plain call** | React only gets **the returned list**, never a `StoryTray` component
```

### What React gives a component only when React does the calling

Why does it matter who calls, if the page is the same? Because React keeps a record of every component it calls. From that record, the component gets five things, and a direct call gets none of them:
1. **Its own state.** React ties the state of each Hook to the component's place in the tree (Lesson 25).
2. **Comparing by type.** React compares each component with the last render by its type, to decide what to keep on the page (Lesson 77).
3. **A page that stays responsive.** React can let the browser do other work between two component calls. So a large render does not block the main thread, where the browser runs your JavaScript and also handles the user's taps.
4. **Developer tools.** React Developer Tools can show a component only when React knows about it (Lesson 64).
5. **Skipped work.** React can decide which components need to render again, and skip the others (Lesson 55).

On this screen, the direct call breaks nothing yet, because `StoryTray` holds no Hooks. Principle 4 shows what happens when the function you call yourself does hold one.

### The first version of the tray

The entry file wraps `App` in `<StrictMode>`, as React's own tray example does:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  ~<StrictMode>~ {/* In development, calls each component twice on every render */}
    <App />
  </StrictMode>
);
```

`App` keeps the two stories in state and writes the tray's tag:

```jsx title="src/App.jsx"
import { useState } from 'react';
import StoryTray from './StoryTray.jsx';

const initialStories = [
  { id: 0, label: "Ankit's Story" },
  { id: 1, label: "Taylor's Story" },
];

export default function App() {
  const [stories, setStories] = useState(initialStories);
  return ~<StoryTray stories={stories} />~; // React calls StoryTray with { stories }
}
```

`StoryTray` returns one list item per story:

```jsx title="src/StoryTray.jsx"
export default function StoryTray({ ~stories~ }) { // Comes from the stories attribute on App's tag
  return (
    <ul>
      {stories.map(story => (
        <li key={story.id}>{story.label}</li>
      ))}
    </ul>
  );
}
```

Where does `stories` come from inside `StoryTray`? No line of yours passes it as an argument. `App` writes `stories={stories}` on the tag, React collects that attribute into the props object (Lesson 08), and then React calls `StoryTray` with that object.

### A Hook is never passed around as a value

The same rule covers Hooks. A Hook is a function too, so JavaScript lets you pass it as a prop, or write a function that takes a Hook and builds a new one while the app runs. React's docs say: never pass around Hooks as regular values. They show both mistakes:

```jsx title="Two ways to pass a Hook around as a value"
<Button ~useData={useDataWithLogging}~ /> {/* **WRONG:** a Hook passed down as a prop */}
const useDataWithLogging = ~withLogging(useData)~; // **WRONG:** a function builds a new Hook while the app runs
```

When a Hook needs extra behavior, such as logging, write it once as a plain custom Hook, `function useDataWithLogging()`, at the top level of its file (Lesson 39). The docs give the reason: with Hooks passed around, you can no longer understand a component by reading it alone, and React will not optimize that component automatically.

Remember: you write the tag, and React does the calling.

## PRINCIPLE | `[...stories]`: each render builds its own new array, so every call gives the same tray

> [!PRINCIPLE]
> **Principle 2: Components and Hooks Must Be Pure: A Render Changes Nothing It Received**
>
> *A render changes nothing that existed before it ran, props and state included; to add an item, build a new array during the render.*
>
> React may call a component more than once for one screen, and Strict Mode does it on purpose in development. `const items = stories` is not a copy, so `push` changes `App`'s state, and every call adds one more Create Story tile. A new array made with the three dots belongs to this call alone, so every call gives the same tray.
>
> **DO THIS:**
> ```jsx
> function StoryTray({ stories }) {
>   const items = ~[...stories, { id: 'create', label: 'Create Story' }]~; // New array: the same three tiles on every call
>   return <ul>{items.map(story => <li key={story.id}>{story.label}</li>)}</ul>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function StoryTray({ stories }) {
>   ~stories.push~({ id: 'create', label: 'Create Story' }); // **WRONG:** changes App's state, one more tile on every call
>   return <ul>{stories.map(story => <li key={story.id}>{story.label}</li>)}</ul>;
> }
> ```

React calls `StoryTray` whenever it needs the tray, as many times as it wants. So every call must give the same tray from the same `stories`.

Now the tray needs its last tile, Create Story. The first idea is `push`, the array method you know from plain JavaScript: it adds an item to the end of an existing array.

```jsx title="src/StoryTray.jsx"
export default function StoryTray({ stories }) {
  const items = ~stories~; // items is a second name for App's own array
  ~items.push~({ id: 'create', label: 'Create Story' }); // **WRONG:** adds a tile to App's state
  return (
    <ul>
      {items.map(story => (
        <li key={story.id}>{story.label}</li>
      ))}
    </ul>
  );
}
```

The code adds Create Story once. The page shows it twice:

```page caption="The first load in development: the tray shows Create Story twice."
line: Ankit's Story
line: Taylor's Story
line: Create Story
line: Create Story | bad
```

```devconsole width=full caption="The Console on the first load: React warns about two items with the same key."
x Encountered two children with the same key, `create`. Keys should be unique so that components maintain their identity across updates.
```

**`push` did not change a copy. It changed the array that `App` holds in state, and Strict Mode called `StoryTray` twice.** Here is what happens on the first load:
1. React calls `StoryTray` once, and `push` adds Create Story to the end of the `stories` array.
2. In development, Strict Mode calls `StoryTray` a second time, with the same `stories`.
3. That array already holds Create Story, and `push` adds another one.
4. The tray shows Ankit's Story, Taylor's Story, Create Story, and Create Story again. Two items now share the key `create`, so React prints the warning.

In production, Strict Mode does nothing (Lesson 47). So the first load looks right, and the bug hides. It comes back later: every time React renders `StoryTray` again, `push` adds to the same array, and one more Create Story tile appears at the end.

> [!DEFINITION]
> **What is a pure component?** [NEW] Think of a calculator. Type 2 plus 2, and it shows 4. Do the same tomorrow, and it shows 4 again. A pure component works the same way, and it keeps three promises.
> First, it is idempotent: the same inputs always give the same JSX. For a component, the inputs are its props, its state, and its context.
> Second, it has no side effects during render: while React calls it, it does not change the page, send a request, or change any outside variable.
> Third, it changes nothing that existed before this call began, such as its props or its state.
> Our `StoryTray` with `push` fails the first promise: the same two stories give three tiles on the first call and four on the second (Lesson 14).

### `const items = stories` is not a copy

The mistake hides in one line, `const items = stories`. Every developer reads it as "`items` is my own local list". It is not. Remember that in JavaScript an array is an object, and a variable holds only a reference to it. So `items` is a second name for the same array that `App` holds in state. Compare it with a new array made inside this call:

```jsx title="A second name for the same array, and a new array made in this call"
const items = ~stories~; // Same array as App's state: push changes App's state
const items = ~[...stories, { id: 'create', label: 'Create Story' }]~; // New array made in this call: safe to build
```

The one difference is where the array was made:
- **With `const items = stories`**, the array was made before this render, by `App`. `items` is only a second name for it, so `push` changes `App`'s state.
- **With the three dots**, a brand new array is made during this call (Lesson 19). Nothing outside this call has seen it yet. This call could even `push` into it, because changing a value made during this render is a local mutation, and a local mutation is allowed (Lesson 14).

React's docs draw the line in the same place: props and state are "immutable snapshots with respect to a single render". A render may change what it just made. It may never change what it received.

```tree caption="Where the array was made decides whether StoryTray may change it."
Two ways to add the Create Story tile
- !A second name for the prop [`const items = stories`] | The array was **made by `App`** before this render | `push` changes **`App`'s state**, so every call adds **one more tile**
- +A new array made in this call [`[...stories]`] | The array is **made during this render** | Every call builds the **same three tiles** from the same `stories`
```

### The fixed tray

`StoryTray` now builds a new array with the three dots:

```jsx title="src/StoryTray.jsx"
export default function StoryTray({ stories }) {
  const items = ~[...stories, { id: 'create', label: 'Create Story' }]~; // A new array made in this call
  return (
    <ul>
      {items.map(story => (
        <li key={story.id}>{story.label}</li>
      ))}
    </ul>
  );
}
```

Strict Mode still calls `StoryTray` twice. Each call builds its own new array from the same two stories, so both calls give the same three tiles:

```page caption="The first load in development after the fix: one Create Story tile."
line: Ankit's Story
line: Taylor's Story
line: Create Story | good
```

```devconsole width=full caption="The Console after the fix: no messages."
= No messages
```

The same rule forbids three more things during render, each for the same reason:
1. **Reading the clock or a random number**, such as `new Date()` or `Math.random()`. Each call gives a different result, so the render is not idempotent.
2. **Changing the page directly**, such as setting `document.title` inside the component body. That is a side effect. It belongs in an event handler, or, as a last resort, in `useEffect` (Lesson 32).
3. **Changing a value after it was passed to a Hook, or after it was used in JSX.** Those values are immutable too.

Remember: a render builds new values. It never changes the ones it received.

## PRINCIPLE | `useState` inside `map`: one more story makes one more Hook call, and the page goes blank

> [!PRINCIPLE]
> **Principle 3: Rules of Hooks: Call the Same Hooks in the Same Order on Every Render**
>
> *Call Hooks only at the top level of a component or a custom Hook, never inside a loop; when each item needs its own state, give each item its own component.*
>
> `useState` takes no name, so React finds the state of each Hook only by counting the calls of a component, in order. A `useState` inside `map` makes the count follow the length of the list. Every tap works until the list grows. Then React finds one more Hook than before, and the page goes blank.
>
> **DO THIS:**
> ```jsx
> function StoryTile({ story }) {
>   const [seen, setSeen] = ~useState(false)~; // One call per tile on every render
>   return <li><button onClick={() => setSeen(true)}>{story.label}{seen && ' (seen)'}</button></li>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function StoryTray({ stories }) {
>   return <ul>{stories.map(story => {
>     const [seen, setSeen] = ~useState(false)~; // **WRONG:** one more call when a story is added, the page goes blank
>     return <li key={story.id}>{story.label}</li>;
>   })}</ul>;
> }
> ```

Each tile needs its own seen mark: the user taps Ankit's Story, and it shows `(seen)`. The first idea is to call `useState` right inside the `map`, once per story:

```jsx title="useState called once per story, inside the map"
{stories.map(story => {
  const [seen, setSeen] = ~useState(false)~; // **WRONG:** one Hook call per story, inside a loop
  return <li key={story.id}>{story.label}</li>;
})}
```

Look at `useState(false)`. It takes no name. So how does React know which state to give back to which call? It counts. The first `useState` call in `StoryTray` gets the first state, the second call gets the second state, and so on.

React's docs describe it with a simple model: "React holds an array of state pairs for every component. It also maintains the current pair index, which is set to `0` before rendering. Each time you call `useState`, React gives you the next state pair and increments the index."

> [!DEFINITION]
> **What are the Rules of Hooks?** [REVIEW] Call Hooks only at the top level of a component or of a custom Hook.
> Never call them inside a loop, inside an `if`, or after an early `return`.
> Why? React matches each Hook call to its state by counting, so every render must make the same calls in the same order. The docs say Hooks "rely on a stable call order on every render of the same component" (Lesson 38).

```tree dir=right caption="React matches each useState call in StoryTray to a state pair by counting the calls, starting from pair 0."
How React finds the state of each `useState` call in `StoryTray`
- +Render with two stories | 1st call gets **pair 0**, for Ankit | 2nd call gets **pair 1**, for Taylor
- !Render with three stories | Pairs 0 and 1 **match** | The 3rd call asks for **pair 2**, which **does not exist**
```

### Every tap works, until the list grows

To let the user add a story, `App` gets a handler that adds My Story, and passes it to the tray as `onCreate` (Lesson 23):

```jsx title="src/App.jsx" startLine="9"
export default function App() {
  const [stories, setStories] = useState(initialStories);

  function ~handleCreate~() { // Adds My Story with the next id
    setStories([...stories, { id: stories.length, label: 'My Story' }]);
  }

  return <StoryTray stories={stories} ~onCreate={handleCreate}~ />; // The tray calls onCreate on a tap
}
```

The Create Story tile now needs a button that calls `onCreate`, so it becomes its own last list item after the stories. The `items` array from Principle 2 is no longer needed. Each story becomes a button, with `useState` inside the `map`:

```jsx title="src/StoryTray.jsx"
import { useState } from 'react';

export default function StoryTray({ stories, onCreate }) {
  return (
    <ul>
      {stories.map(story => {
        const [seen, setSeen] = ~useState(false)~; // **WRONG:** the number of calls follows the number of stories
        return (
          <li key={story.id}>
            <button onClick={() => setSeen(true)}>
              {story.label}{seen && ' (seen)'}
            </button>
          </li>
        );
      })}
      <li>
        <button ~onClick={onCreate}~>Create Story</button> {/* Asks App to add My Story */}
      </li>
    </ul>
  );
}
```

The user taps Ankit's Story, and the tile shows it was seen. Nothing breaks:

```page caption="After the user taps Ankit's Story: the tile shows it was seen."
line: [Ankit's Story (seen)] | good
line: [Taylor's Story]
line: [Create Story]
```

Then the user taps Create Story, and the whole page goes blank:


**Every tap on a story works. The first tap on Create Story blanks the page, because the number of `useState` calls in `StoryTray` grows from two to three.** Here is what happens:
1. On the first load, the tray renders two stories. `StoryTray` calls `useState` twice, and React keeps pair 0 and pair 1.
2. The user taps Ankit's Story. `StoryTray` renders again with the same two stories and makes the same two calls. Pair 0 now holds `true`. Nothing breaks.
3. The user taps Create Story. The button calls `onCreate`, the handler that `App` passed down, and it adds My Story to the list.
4. React renders `StoryTray` again, and the `map` now calls `useState` three times.
5. React finds one more Hook call than on the previous render. It prints the warning, where the third line reads `undefined` for the previous render and `useState` for this one. Then it throws an error.
6. The error happens during render, so React removes the whole page (Lesson 72).

### One component per tile, one Hook call per component

The fix keeps the Rules of Hooks: each tile becomes its own component, `StoryTile`, with its `useState` at the top level:

```jsx title="src/StoryTile.jsx"
import { useState } from 'react';

export default function StoryTile({ story }) {
  const [seen, setSeen] = ~useState(false)~; // Top level: exactly one call on every render of this tile
  return (
    <li>
      <button onClick={() => setSeen(true)}>
        {story.label}{seen && ' (seen)'}
      </button>
    </li>
  );
}
```

`StoryTray` no longer calls any Hook. It writes one `StoryTile` tag per story, with the `key` on the tag:

```jsx title="src/StoryTray.jsx"
import StoryTile from './StoryTile.jsx';

export default function StoryTray({ stories, onCreate }) {
  return (
    <ul>
      {stories.map(story => (
        ~<StoryTile key={story.id} story={story} />~ // React calls each StoryTile and keeps its seen
      ))}
      <li>
        <button onClick={onCreate}>Create Story</button>
      </li>
    </ul>
  );
}
```

Now the user taps Ankit's Story, then Create Story. My Story joins the tray, and Ankit's tile keeps its seen mark:

```page caption="After the fix: the user taps Ankit's Story, then Create Story, and the tray keeps working."
line: [Ankit's Story (seen)] | good
line: [Taylor's Story]
line: [My Story] | good
line: [Create Story]
```

```devconsole width=full caption="The Console after both taps: no messages."
= No messages
```

Both versions call `useState(false)` once per story. So what changed? **Which component makes the calls.**
- **With `useState` inside the `map`**, one component, `StoryTray`, makes one call per story: two calls before My Story arrives, and three after.
- **With `useState` at the top of `StoryTile`**, each `StoryTile` makes exactly one call on every render. A new story adds a new component, not a new Hook call in an old one.

Where does each tile's `seen` come from? React calls each `<StoryTile>` tag it finds in the list. Each call makes one `useState` call. React keeps that state with the tile, at its place in the tree, matched by its `key` (Lessons 18 and 25).

Remember: React counts the Hook calls, so the count must never change.

## PRINCIPLE | `StoryTile({ story })` inside `map`: its `useState` runs as a Hook of `StoryTray`

> [!PRINCIPLE]
> **Principle 4: How the Rules Interlock: A Component Called as a Function Runs Its Hooks in the Caller**
>
> *Write a tag for every component, even inside a loop, so its Hooks belong to it and not to the loop that calls it.*
>
> A Hook belongs to the component React is rendering when the Hook runs. `StoryTile({ story })` inside `map` runs the `useState` of `StoryTile` while React renders `StoryTray`, so it becomes a Hook of `StoryTray`, inside a loop. Breaking the rule that React calls components breaks the Rules of Hooks, and the page goes blank when the list grows.
>
> **DO THIS:**
> ```jsx
> {stories.map(story => ~<StoryTile key={story.id} story={story} />~)} {/* React calls each tile, one Hook each */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {stories.map(story => ~StoryTile({ story })~)} {/* **WRONG:** the useState of StoryTile becomes a Hook of StoryTray in a loop */}
> ```

This is the trap from the start of the lesson, now on the tray. Both lines use the working `StoryTile` from Principle 3:

```jsx title="Calling StoryTile as a function, and writing its tag, inside the same map"
{stories.map(story => ~StoryTile({ story })~)} {/* StoryTray calls StoryTile inside its own loop */}
{stories.map(story => ~<StoryTile key={story.id} story={story} />~)} {/* React calls each StoryTile */}
```

Both run the same function with the same `story`. Both show the same tiles on the first load, and a tap on a story marks it seen in both. The one difference is who calls `StoryTile`: the loop inside `StoryTray`, or React.

A developer who writes the first line thinks: "I moved `useState` into `StoryTile`, so the Hook is at the top level now." It is, at the top level of `StoryTile`. But here is what is really going on: **a Hook belongs to the component React is rendering when the Hook runs.** With the direct call, React is rendering `StoryTray`. So the `useState` inside `StoryTile` is a Hook of `StoryTray`, inside a loop.

Here is the tray with the direct call:

```jsx title="src/StoryTray.jsx"
import StoryTile from './StoryTile.jsx';

export default function StoryTray({ stories, onCreate }) {
  return (
    <ul>
      {stories.map(story => ~StoryTile({ story })~)} {/* **WRONG:** StoryTile's useState runs inside this loop */}
      <li>
        <button onClick={onCreate}>Create Story</button>
      </li>
    </ul>
  );
}
```

On the first load, the tray looks right, but the Console already shows a warning:

```page caption="The first load with StoryTile called as a function: the same three tiles."
line: [Ankit's Story]
line: [Taylor's Story]
line: [Create Story]
```

```devconsole width=full caption="The Console on the first load: the list items that StoryTile returns have no key."
x Each child in a list should have a unique "key" prop.
  Check the render method of `ul`. It was passed a child from StoryTray. See https://react.dev/link/warning-keys for more information.
```

The warning comes from the missing tag. The `key` used to sit on `<StoryTile>`. With no tag, there is no place for it, and the `<li>` that `StoryTile` returns has none. React names the `<ul>` that holds the list items, and `StoryTray`, which passed them to it.

Then the user taps Create Story, and the page goes blank again, with the same error as in Principle 3:

```page caption="After the user taps Create Story: the whole page is blank again."
empty: the whole page is blank
```

```devconsole width=full caption="The Console after the tap on Create Story: the warning names StoryTray, not StoryTile."
x React has detected a change in the order of Hooks called by StoryTray. This will lead to bugs and errors if not fixed. For more information, read the Rules of Hooks: https://react.dev/link/rules-of-hooks
  Previous render            Next render
  1. useState                useState
  2. useState                useState
  3. undefined               useState
x Uncaught Error: Rendered more hooks than during the previous render.
! An error occurred in the <StoryTray> component.
  Consider adding an error boundary to your tree to customize error handling behavior.
  Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

**The warning names `StoryTray`, not `StoryTile`. Calling `StoryTile` as a function put its `useState` back inside the loop of `StoryTray`: the broken code of Principle 3.** Here is why React counts the Hook as a Hook of `StoryTray`:
1. React is rendering `StoryTray`.
2. The loop in `StoryTray` calls `StoryTile` as an ordinary function, once per story.
3. The `useState` inside `StoryTile` runs while React is still rendering `StoryTray`.
4. React counts it as the next Hook call of `StoryTray`. With two stories, that makes two calls. With My Story added, it makes three, and React throws.

React's docs warn about exactly this: "If a component contains Hooks, it's easy to violate the Rules of Hooks when components are called directly in a loop or conditionally."

```tree caption="Who calls StoryTile decides whose Hook its useState is."
Two ways to run `StoryTile` inside the `map`
- !The loop in `StoryTray` calls it | `useState` runs **while React renders `StoryTray`** | Counts as a **Hook of `StoryTray`**: two calls, then **three**, then the page goes **blank**
- +React calls it [`<StoryTile key={story.id} story={story} />`] | Each tile is **its own component** | Each one makes **exactly one** `useState` call, kept with **its own tile**
```

### Why the three rules only work together

Now you can see the three rules as one system, where each rule holds up another:
1. **React calls the components.** Because React does the calling, it can tie state to each component's place in the tree.
2. **React finds that state by counting the calls** inside each component it calls. So the Hooks stay at the top level, the same ones in the same order.
3. **When your code calls a component itself**, in a loop or an `if`, the Hooks of that component move into the caller's loop or `if`. Breaking the rule that React calls components breaks the Rules of Hooks.
4. **React decides how often to call each component**: twice in Strict Mode, again when a render restarts, or not at all when it skips one. A call that changes nothing outside itself is safe however many times React makes it. That is why the components must be pure.

So the usual fix for the Rules of Hooks, one component per item, works only when React calls that component. The component needs a tag.

```tree dir=right caption="How the three Rules of React hold each other up on the stories tray."
The three rules work as one system
- +React calls components [`<StoryTile />`] | React ties **state to each tile** in the tree
- +Rules of Hooks [`useState` at the top level] | React finds that state **by counting the calls** in each component
- +Pure components | React may call a component **again**, so a call **changes nothing** outside it
- !A component called as a function | Its Hooks join **the caller's loop** | Breaking **React calls components** breaks the **Rules of Hooks**
```

React Compiler (Lesson 63) relies on all three rules at once. It understands the Rules of React, and when code might break them, it skips that component instead of optimizing it. When a break goes unnoticed, the compiler may optimize a component it should have skipped. React's docs give a test for that case: if a bug stays after all memoization is removed, the code breaks a Rule of React, and that needs a fix.

Remember: a component called as a function lends its Hooks to the caller.

## PRINCIPLE | `<StrictMode>` and `eslint-plugin-react-hooks`: one runs the code, the other reads it

> [!PRINCIPLE]
> **Principle 5: The Checks: Strict Mode Runs the Code, the Linter Reads It**
>
> *Keep `<StrictMode>` on in development and run `eslint-plugin-react-hooks` while editing; never silence a lint to make a page work.*
>
> Strict Mode calls each component twice in development, so an impure render shows on the page at the first load. The linter reads the code and names a Hook inside a loop, or a change to a prop, before the code runs. Neither one alone covers all three rules, and a first load that looks right proves nothing.
>
> **DO THIS:**
> ```jsx
> createRoot(document.getElementById('root')).render(
>   ~<StrictMode>~ {/* Calls each component twice in development to show impure renders */}
>     <App />
>   </StrictMode>
> );
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {stories.map(story => { // eslint-disable-next-line react-hooks/rules-of-hooks
>   const [seen, setSeen] = ~useState(false)~; // **WRONG:** the lint is silenced, the page still goes blank after Create Story
>   return <li key={story.id}>{story.label}</li>;
> })}
> ```

Look back at the four broken trays. On the first load, three of them looked right. **A first load that looks right proves nothing.** Without Strict Mode, the `push` bug hides. And both Hook bugs wait for the tap on Create Story. A bug that no check finds reaches production, where Strict Mode does nothing, and the page breaks only after the right render or the right tap by the user.

So React gives you two checks, and the docs strongly recommend using them together: Strict Mode, and React's plugin for ESLint.

> [!DEFINITION]
> **What is ESLint?** [NEW] ESLint is a tool that reads your code in the editor, without running it, and marks each line that fails one of its checks. React's docs call each check a lint.
> The React team publishes the plugin `eslint-plugin-react-hooks`, which "provides ESLint rules to enforce the Rules of React". It works even in an app that does not use React Compiler yet.
> Lesson 95 walks through every lint it holds.

### Strict Mode runs the code, the linter reads it

Both checks find broken rules, but they do not do the same job:
- **Strict Mode runs the code.** In development, it calls each component twice and shows what an impure render does to the page. It found the second Create Story tile on the first load.
- **The linter reads the code.** While you edit, it names the broken line before the code ever runs. Its `rules-of-hooks` lint marks the `useState` inside the `map`:

```jsx title="src/StoryTray.jsx, as the editor marks it" startLine="6"
      {stories.map(story => {
        const [seen, setSeen] = ~useState~(false); // **WRONG:** React Hook "useState" cannot be called inside a callback
```

So one check is not enough. Strict Mode shows what the bug does on the page. The linter names the bug in the code, even the bugs that wait for a tap:

| Bug on the tray | Strict Mode in development | `eslint-plugin-react-hooks` while editing |
| :--- | :--- | :--- |
| **`push` into the `stories` prop, Principle 2** | Shows a second Create Story tile on the first load | The `immutability` lint marks a change to a prop |
| **`useState` inside `map`, Principle 3** | Finds nothing on the first load; the page breaks only after Create Story | The `rules-of-hooks` lint marks the `useState` line |
| **`StoryTile({ story })` inside `map`, Principle 4** | Finds nothing on the first load; the page breaks only after Create Story | React's docs mark a direct call such as `{Article()}` as an error that React Compiler reports, and the plugin shows those reports in the editor |

```tree caption="Strict Mode and the React Hooks plugin for ESLint find broken rules at different moments."
Two checks for the Rules of React
- +Strict Mode [`<StrictMode>`] | **Runs** the code in development and calls each component **twice** | Shows an **impure render** on the page, such as a **second Create Story tile**
- +`eslint-plugin-react-hooks` | **Reads** the code while you edit | Names the **broken line**, such as a `useState` **inside a loop**, before it runs
```

### Silencing the linter hides the bug, it does not fix it

React's docs show a real case of this mistake, on a feedback form:
1. A developer sees a lint error on a `useState` inside an `if`.
2. They turn the lint off for that line with an `eslint-disable-next-line` comment.
3. When the user submits the form, the page crashes with "Rendered fewer hooks than expected".

The docs give the hint for that case: look for comments that turn the linter off, because that is where the bugs often hide.

When React Compiler is installed, it reports the breaks it finds through the same plugin. Such a report does not stop the build. The compiler skips that one component and keeps the rest of the app optimized, so the team can fix each break at its own pace.

Remember: Strict Mode shows the bug on the page, and the linter names it in the code.

## All 5 Principles Together

### The complete stories tray

Here is the complete tray in four files. React calls every component from a tag, every render builds new values instead of changing old ones, and every Hook sits at the top level of its own component:

```jsx title="src/main.jsx"
import { StrictMode } from 'react';
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(
  ~<StrictMode>~ {/* Principle 5: calls each component twice in development */}
    <App />
  </StrictMode>
);
```

```jsx title="src/App.jsx"
import { useState } from 'react';
import StoryTray from './StoryTray.jsx';

const initialStories = [
  { id: 0, label: "Ankit's Story" },
  { id: 1, label: "Taylor's Story" },
];

export default function App() {
  const [stories, setStories] = useState(initialStories);

  function handleCreate() {
    ~setStories([...stories, { id: stories.length, label: 'My Story' }])~; // Principle 2: a new array, never a push
  }

  return ~<StoryTray stories={stories} onCreate={handleCreate} />~; // Principle 1: React calls StoryTray
}
```

```jsx title="src/StoryTray.jsx"
import StoryTile from './StoryTile.jsx';

export default function StoryTray({ stories, onCreate }) {
  return (
    <ul>
      {stories.map(story => (
        ~<StoryTile key={story.id} story={story} />~ // Principle 4: a tag, so each tile owns its Hook
      ))}
      <li>
        <button onClick={onCreate}>Create Story</button>
      </li>
    </ul>
  );
}
```

```jsx title="src/StoryTile.jsx"
import { useState } from 'react';

export default function StoryTile({ story }) {
  const [seen, setSeen] = ~useState(false)~; // Principle 3: one call at the top level on every render
  return (
    <li>
      <button onClick={() => setSeen(true)}>
        {story.label}{seen && ' (seen)'}
      </button>
    </li>
  );
}
```

### How React calls the components, in order

When the page opens, React starts at `App` and follows the tags from the top down. It calls `App`, then `StoryTray`, then one `StoryTile` for each story. In development, Strict Mode calls each of them twice, and because every render is pure, both calls give the same tray:

```tree caption="The order in which React calls the components of the stories tray, from App down to each StoryTile."
`App` [1. Called first] | Holds **`stories`** in state | Writes **one** `<StoryTray>` tag
- +`StoryTray` [2. Called second] | Holds **no Hooks** | Writes **one `<StoryTile>` tag per story** and the Create Story button
  - +`StoryTile` for Ankit [3. Called third] | **One** `useState` call | Keeps **its own `seen`**
  - +`StoryTile` for Taylor [4. Called fourth] | **One** `useState` call | Keeps **its own `seen`**
```

After the user taps Ankit's Story and then Create Story, React calls a third `StoryTile`, for My Story. Each tile still makes one Hook call, so nothing breaks:

```page caption="The finished tray after the user taps Ankit's Story and then Create Story."
line: [Ankit's Story (seen)] | good
line: [Taylor's Story]
line: [My Story] | good
line: [Create Story]
```

| Rule of React | What it forbids | What the user sees when it is broken | The check that finds it |
| :--- | :--- | :--- | :--- |
| **React calls Components and Hooks** | Calling a component as a function, and passing a Hook around as a value | A blank page after Create Story, when the called component holds a Hook and the call sits inside a loop | React Compiler's reports, shown by `eslint-plugin-react-hooks` |
| **Components and Hooks must be pure** | Changing props, state, or any value made before the render; reading the clock or a random number; changing the page during render | A second Create Story tile in development, and one more after every render in production | Strict Mode, and the `purity` and `immutability` lints |
| **Rules of Hooks** | Calling a Hook in a loop, an `if`, after an early return, or anywhere outside the top level of a component or custom Hook | A blank page after Create Story, with an error about the order of Hooks | The `rules-of-hooks` lint |

Remember the one sentence of this lesson. **You write the component, but React calls it, so let React do the calling, change nothing outside the call, and call the Hooks in the same order every time.**

## For the Interview

> **The Interview Question:** What are the Rules of React, and how do the three rules interlock?

### How to Answer Clearly in 30 Seconds

"React's docs publish three Rules of React, and each one follows from the same fact: React, not our code, calls the components.
1. **Components and Hooks must be pure**: because React may call a component more than once, a render gives the same result for the same props, state, and context, and changes nothing that existed before it ran.
2. **React calls Components and Hooks**: we use a component only as a JSX tag, never as a function, and never pass a Hook around as a value. That lets React decide when to call it, tie its state to its place in the tree, and skip it.
3. **Rules of Hooks**: React finds the state of each Hook by counting the calls, so Hooks run only at the top level, the same ones in the same order on every render.

They interlock. Calling a component as a function inside a loop moves its Hooks into the caller's loop, so breaking the rule that React calls components breaks the Rules of Hooks. Strict Mode finds impure renders in development, and `eslint-plugin-react-hooks` marks broken lines while we edit."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"If `StoryTile({ story })` returns the same JSX as `<StoryTile />`, why does it matter?"**
   Because a Hook belongs to the component React is rendering when the Hook runs. With the tag, React calls each `StoryTile`, and each one makes one `useState` call for its own tile. With the direct call, React is rendering `StoryTray`, so every `useState` inside `StoryTile` counts as a Hook of `StoryTray`, inside its loop. The first load looks the same. When the list grows from two stories to three, `StoryTray` makes one more Hook call than before, React throws, and the page goes blank. React's docs say it plainly: when a component contains Hooks, calling it directly in a loop or a condition makes it easy to break the Rules of Hooks.
2. **"What does purity let React do, and why does Strict Mode call my component twice?"**
   Purity lets React do five things safely: render a component more than once, pause less important components and come back to them later, restart a render whose data changed, skip components whose inputs did not change, and run components on the server. Strict Mode calls each component twice in development to test that promise. A pure component gives the same result both times. An impure one shows its bug at once, as the second Create Story tile did after a `push` into a prop. Strict Mode has no effect in production.
3. **"Can I pass a Hook as a prop, or wrap a Hook in a function that returns a new Hook?"**
   No. React's docs say: never pass around Hooks as regular values. A Hook that arrives as a prop, or that a function builds while the app runs, makes it harder to understand a component by reading it alone, and React will not optimize that component automatically. It also makes it easier to break the Rules of Hooks by accident. Write a plain custom Hook instead, at the top level of its own file, and call it at the top level of the component.

```tree dir=right caption="Interview summary: the three Rules of React and how each one holds up the others."
The three Rules of React as one system
- +React calls components [`<StoryTile />`] | React **owns the call** | So React can **tie state** to each component and **call it again**
- +Pure components | Every call **gives the same result** | So React may **repeat, pause, restart, or skip** a call safely
- +Rules of Hooks [`useState` at the top level] | Same Hooks, **same order** | So React finds **each Hook's state** by counting
- !Calling a component as a function | Its Hooks join **the caller's loop** | Breaking **React calls components** breaks the **Rules of Hooks**
```
