# Lecture 117: How Suspense Lets the Server Send a Page in Parts

*(How can the server show the top of a page before its slow part is ready?)*

> INTERVIEW QUESTION | ❱ CORE | How does streaming SSR work with Suspense: the shell, fallbacks, and out-of-order flushes?

---

## VS | The Whole Page at Once vs. the Page in Parts: `<Suspense>` lets the server send the fast part first

> A page rendered on the server usually arrives in one piece, so one slow part, like the reviews under a product, keeps the whole tab blank. **Wrap the slow part in `<Suspense>`, and the server sends the rest of the page at once, and the slow part later, in the same response**. The reason: the user reads the price while the reviews load, and the browser never makes a second request.

Remember how a server answers a request in plain Node. You do not have to send the whole HTML in one call. You can call `response.write` several times, and close the response with `response.end` only when the last part is out:

```js title="Plain Node: one response, sent in two parts"
response.write('<h1>Blue Sneakers</h1><p>$49</p>'); // Sent at once
setTimeout(() => {
  ~response.write('<ul><li>Great fit</li><li>Runs small</li></ul>')~; // Sent 2 seconds later, in the same response
  response.end(); // Now the response is over
}, 2000);
```

The browser does not wait for the end of the response. It draws the heading and the price as soon as they arrive, and it adds the reviews 2 seconds later. Sending one response in parts like this is called **streaming**.

In React, you never write these parts by hand. React writes the HTML for you, from your JSX. So you need a way to tell React: "this part may come later." That is the job of `<Suspense>`:

```jsx title="The one tag that lets the reviews come later"
<h1>Blue Sneakers</h1>
<p>$49</p>
<Suspense ~fallback={<p>Loading reviews...</p>}~> {/* Sent at once, in the place of the reviews */}
  <Reviews />
</Suspense>
```

Here is what the server does with this tag:
1. **At once**, it sends everything outside the boundary, with the fallback `Loading reviews...` in the place of the reviews.
2. **Later**, when the reviews are ready, it sends them at the end of the same response, with a small script that moves them into place.

React's docs call this streaming server rendering, or streaming SSR for short (as seen in Lesson 103).

Here is the one sentence to keep in mind for this whole lesson:

**The server sends everything outside `<Suspense>` at once, and each `<Suspense>` part later, when its own data is ready, in the same response.**

### The Same `<Suspense>` You Know From the Browser

> [!DEFINITION]
> **`<Suspense>`.** [REVIEW] `<Suspense fallback={...}>` wraps a part of the page that may not be ready yet. While a component inside it suspends, React shows the fallback in its place, such as a loading line. When the component is ready, React shows it instead of the fallback. Everything inside one boundary is shown together, as one unit (Lesson 69).

Is the server version a new tag? No. **It is the exact same `<Suspense>`, with the same `fallback` prop!** Only the way each part reaches the user changes:
- **In the browser**, React shows the fallback while a component suspends, and then shows the content in its place.
- **On the server**, React sends the fallback as HTML right away, and sends the content as more HTML later, in the same response.

```tree caption="The same Suspense tag in the browser and on the server: the fallback first, the content later."
One `<Suspense>` tag, two places it runs
- +In the browser [`<Suspense fallback>`] | React **shows the fallback** while the component suspends | Then React **shows the content** in its place
- +On the server [`<Suspense fallback>`] | The server **sends the fallback as HTML at once** | Then the server **sends the content as HTML later**, in the **same response**
```

### Two More Ideas From Earlier Lessons

> [!DEFINITION]
> **Reading a promise with `use`.** [REVIEW] A promise is a JavaScript object that stands for a value that comes later, such as the answer of a database lookup. `use(promise)` reads that value inside a component. While the promise has not answered, the component suspends: React stops rendering it and shows the fallback of the closest `<Suspense>` above it. When the promise answers, React renders the component again, and this time `use` returns the value (Lesson 71).

> [!DEFINITION]
> **Server rendering and hydration.** [REVIEW] With server rendering, the server runs your components and sends their HTML, so the user sees the page before any JavaScript loads (Lesson 102). That HTML cannot answer clicks yet. Then the app's JavaScript loads in the browser, and `hydrateRoot` attaches React and your click handlers to the HTML that is already on the screen. This step is called hydration (Lesson 104).

### What Is at Stake

What is at stake is what the user sees while the slow data loads:
1. **Without a boundary, the server sends nothing until the slowest data on the page is ready.** The user stares at a blank tab for 2 seconds, because of two reviews at the bottom of the page.
2. **With a boundary, the user reads the heading and the price while the reviews load.** React's docs: "Streaming allows the user to start seeing the content even before all the data has loaded on the server."

### Where Readers Usually Go Wrong

Readers usually go wrong in four ways:
1. **They think the reviews come from a second request by the browser**, as with a fetch inside an Effect (as seen in Lesson 33). They are the rest of the same response.
2. **They think the browser must load React before the reviews can appear.** React's docs say the opposite: "Streaming does not need to wait for React itself to load in the browser".
3. **They expect a boundary to stream data fetched in an Effect.** Effects never run on the server, so nothing suspends, and nothing streams.
4. **They wrap the whole page in one boundary**, so the first thing the user sees is one loading line instead of the product.

### Three Ways to Send a Page With One Slow Part

When one part of a page needs slow data, you choose between three ways:
1. **Wait for all the data, then send the whole page.** The user sees nothing until the slowest data is ready. This fits a search engine's crawler, which wants the whole page in one piece, and pages built ahead of time. Lessons 118 and 119 cover both.
2. **Send the page without the slow part, and fetch it in the browser inside an Effect** (as seen in Lesson 33). The reviews are not in the server's HTML at all. The user sees them only after the app's JavaScript loads and the fetch returns. This fits data that must not be in the server's HTML.
3. **Stream.** Wrap the slow part in `<Suspense>`. The server sends the product and the fallback at once, and the reviews later in the same response. This fits a page that the server renders for each visit, with one slow part. This lesson builds this way.

```tree caption="Three ways to send a product page whose reviews take 2 seconds."
Three ways to send a page with one slow part
- !Wait for all the data | The tab stays **blank for 2 seconds** | Fits **crawlers** and pages **built ahead of time**
- !Fetch in the browser [`useEffect` `fetch`] | The reviews are **not in the server's HTML** | They show only **after the JavaScript loads** and the fetch returns
- +Stream with Suspense [`<Suspense fallback>`] | The product and **`Loading reviews...` go out at once** | The reviews follow **in the same response**
```

In a framework with Server Components, `Reviews` would be an async component that awaits the database (as seen in Lesson 109). The boundary does the same job there. React's docs say that awaiting in an async component "works across server/client boundaries with streaming support for Suspense."

## SECTION | A Product Page With Slow Reviews

We take the product page of Lessons 102 to 104 and make its reviews slow. Principle 4 adds a second slow section, `You may also like`, under the reviews.

```files title="product-page: File Explorer" caption="The files of the product page in this lesson."
server.js | server | For each visit, starts the lookups and sends `App` to the browser in parts
src/
  db.js | stand-in for the database | Exports `getReviews` and, from Principle 4, `getSuggestions`
  App.jsx | page | Renders the heading, the price, and one `<Suspense>` boundary for each slow section
  Reviews.jsx | slow section | Reads the reviews with `use` and renders them as a list
  Suggestions.jsx | slow section, from Principle 4 | Reads the suggestions with `use` and renders them as a list
```

One detail of the server matters for streaming. On the server, `App` renders the whole document, from the `<html>` tag down, so every boundary sits inside the body.

Why does that matter? Suppose a waiting boundary sits at the very top of what `App` returns, outside every tag. Then React sends nothing until that boundary is ready, because it cannot tell yet whether the boundary holds the `<html>` and `<body>` tags.

The complete page files in Principles 1 and 2 and at the end show `<html>` and `<body>`. The shorter snippets leave them out, and they sit inside `<body>`.

**PRINCIPLES:** The server sends everything outside `<Suspense>` at once, and each `<Suspense>` part later, when its own data is ready, in the same response. Five principles follow:
1. **`Reviews` with no boundary above it: the whole page waits for the reviews.** Everything outside every boundary is the shell, and the server sends no HTML until the whole shell has rendered.
2. **`<Suspense fallback>`: the product and `Loading reviews...` go out at once.** The reviews follow later in the same response, but only if the data suspends.
3. **The inline `<script>`: the reviews take the place of the fallback before React loads.** The server sends the reviews hidden, with a small script that moves them into place.
4. **Two boundaries: each section appears when its own data is ready, in any order.** A section lower on the page that is ready first appears first.
5. **One boundary around the whole page: the first screen is only `Loading...`.** Wrap only the slow parts, so the first screen is the real page.

## PRINCIPLE | `Reviews` with no `<Suspense>` above it: the whole page waits for the slowest data

> [!PRINCIPLE]
> **Principle 1: The Shell: Everything Outside `<Suspense>` Must Render Before the Server Sends Anything**
>
> *Everything outside every `<Suspense>` boundary is the shell, and the server sends no HTML until the whole shell has rendered.*
>
> The server does not send the page line by line from the top. It waits until the shell is finished, and then sends it as one piece. A slow component with no boundary above it is part of the shell, so the heading and the price, ready at once, wait with it. The slowest data in the shell decides when the user sees anything.
>
> **DO THIS:**
> ```jsx
> <h1>Blue Sneakers</h1>
> <p>$49</p>
> <Suspense fallback={<p>Loading reviews...</p>}>
>   ~<Reviews reviewsPromise={reviewsPromise} />~ {/* Outside the shell: the heading and the price go out at once */}
> </Suspense>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <h1>Blue Sneakers</h1>
> <p>$49</p>
> ~<Reviews reviewsPromise={reviewsPromise} />~ {/* **WRONG:** part of the shell, so the tab stays blank for 2 seconds! */}
> ```

Here is the product page with its reviews, and no `<Suspense>` anywhere:

```jsx title="src/App.jsx"
import Reviews from './Reviews.jsx';

export default function App({ reviewsPromise }) {
  return (
    <html>
      <body>
        <h1>Blue Sneakers</h1> {/* Ready at once */}
        <p>$49</p> {/* Ready at once */}
        ~<Reviews reviewsPromise={reviewsPromise} />~ {/* Ready after 2 seconds */}
      </body>
    </html>
  );
}
```

**When the user opens this page, the tab stays blank for 2 seconds, even though the heading and the price are ready at once.** Then the whole page appears together:

A junior developer expects the opposite: the `<h1>` comes first in `App`, so the heading should reach the browser first. It does not.

Remember the plain Node server of the opening. It sent the heading first because we wrote the heading as its own part. React cuts the page only where you put a boundary. With no boundary, the whole page is one part, and React has a name for that part.

### The Shell: Everything Outside Every Boundary

> [!DEFINITION]
> **The shell.** [NEW] The shell is everything on the page outside every `<Suspense>` boundary. The word comes from building: the shell of a house is the frame that must stand before anyone moves in. React's docs say the shell "determines the earliest loading state that the user may see." The server sends no HTML until the whole shell has rendered (Lesson 117).

On our page there is no boundary at all, so the whole page is the shell, and the reviews are part of it. The first byte of the page cannot leave the server until the reviews are ready.

```tree caption="With no Suspense boundary, the whole page is the shell, so the heading waits for the reviews."
The shell of our page with no boundary
- +`<h1>Blue Sneakers</h1>` | Ready **at once**
- +`<p>$49</p>` | Ready **at once**
- !`<Reviews />` | Ready **after 2 seconds** | The whole shell, and every byte of the page, **waits for it**
```

### Where the 2 Seconds Come From

The database file is our stand-in for the database (as seen in Lesson 109). Its `getReviews` returns a promise that answers with two reviews after 2000 milliseconds:

```js title="src/db.js"
export function ~getReviews~() { // Answers with the two reviews after 2 seconds
  return new Promise(resolve => {
    setTimeout(() => resolve(['Great fit', 'Runs small']), 2000);
  });
}
```

`Reviews` receives the promise as a prop and reads it with `use` (as seen in Lesson 71). While the promise has not answered, `Reviews` suspends:

```jsx title="src/Reviews.jsx"
import { use } from 'react';

export default function Reviews({ reviewsPromise }) {
  const reviews = ~use(reviewsPromise)~; // Suspends until the reviews arrive
  return (
    <ul>
      {reviews.map(review => <li key={review}>{review}</li>)}
    </ul>
  );
}
```

The server file is the route handler of Lesson 102, with two changes:
1. **It starts the reviews lookup for each visit**, and passes the promise to `App` as a prop.
2. **It calls `renderToPipeableStream` instead of `renderToString`.** `renderToString` returns one finished string, so it cannot send a page in parts. `renderToPipeableStream` is the React function that can. Lesson 118 teaches it in full, and here we need only its job.

```jsx title="server.js"
import { renderToPipeableStream } from 'react-dom/server';
import App from './src/App.jsx';
import { getReviews } from './src/db.js';

app.use('/', (request, response) => {
  const reviewsPromise = ~getReviews()~; // Starts the 2-second lookup for this visit
  const { pipe } = renderToPipeableStream(<App reviewsPromise={reviewsPromise} />, {
    ~onShellReady~() { // Nothing reaches the browser before React calls this
      pipe(response); // Starts sending the HTML to the browser
    },
  });
});
```

Two names here are new:
- **`onShellReady`** is a function that we hand to React, in the second argument. React's docs say it fires "right after the initial shell has been rendered". The server starts sending there, and not a moment earlier.
- **`pipe`** is a function that `renderToPipeableStream` gives back. We call it with the same `response` that the route handler of Lesson 102 used, and React writes the HTML into it, part by part.

A real server also adds a script tag that loads the app's JavaScript in the browser. We leave it out here, because the option that adds it belongs to Lesson 118.

### Why the Tab Stays Blank

**The heading is ready at once, but it is stuck inside an unfinished shell.** Here is what happens, in order:
1. The user opens the page, and the request reaches the server file.
2. The server calls `getReviews`. The promise will answer in 2 seconds.
3. React renders `App`. The heading and the price are ready at once.
4. React renders `Reviews`, which reads the promise with `use` and suspends.
5. There is no boundary above `Reviews`, so it is part of the shell, and the shell is not finished.
6. React does not call `onShellReady`, so the server sends nothing. The tab stays blank.
7. After 2 seconds, the reviews arrive and the shell finishes. React calls `onShellReady`, and the whole page goes out at once.

### Real Beginner Mistake: Reviews Added With No Boundary

1. A team adds reviews to the product page, read on the server so that they are in the HTML.
2. On busy days, the reviews lookup takes 2 seconds.
3. Nobody wraps `Reviews` in a boundary, because the page looks right once it loads.
4. Every visitor stares at a blank tab for 2 seconds. React's docs call the time until the first byte reaches the browser **Time to First Byte**, and it grows by 2 seconds on every page view.

Remember: the server sends everything outside `<Suspense>` at once. With no boundary, everything waits.

## PRINCIPLE | `<Suspense fallback>`: the product and `Loading reviews...` go out at once

> [!PRINCIPLE]
> **Principle 2: Streaming: `<Suspense>` Sends the Product With `Loading reviews...` First**
>
> *Wrap the slow component in `<Suspense>`: the server sends the shell at once, with the fallback in the boundary's place, and sends the boundary's content later in the same response.*
>
> A boundary takes the slow component out of the shell. Nothing in the shell is waiting anymore, so the server sends the heading, the price, and the fallback at once. When the data is ready, the content follows in the same response. The data must suspend for this to work: a promise read with use does, and a fetch inside an Effect does not.
>
> **DO THIS:**
> ```jsx
> function Reviews({ reviewsPromise }) {
>   const reviews = ~use(reviewsPromise)~; // Suspends on the server, so the boundary streams the reviews
>   return <ul>{reviews.map(review => <li key={review}>{review}</li>)}</ul>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Reviews() {
>   const [reviews, setReviews] = useState([]);
>   ~useEffect~(() => { fetch('/api/reviews').then(res => res.json()).then(setReviews); }, []); // **WRONG:** never runs on the server, so the server sends an empty list
>   return <ul>{reviews.map(review => <li key={review}>{review}</li>)}</ul>;
> }
> ```

We make one change to the page file: we wrap `Reviews` in `<Suspense>`.

```jsx title="src/App.jsx"
import { Suspense } from 'react';
import Reviews from './Reviews.jsx';

export default function App({ reviewsPromise }) {
  return (
    <html>
      <body>
        <h1>Blue Sneakers</h1>
        <p>$49</p>
        ~<Suspense fallback={<p>Loading reviews...</p>}>~ {/* Takes Reviews out of the shell */}
          <Reviews reviewsPromise={reviewsPromise} />
        </Suspense>
      </body>
    </html>
  );
}
```

No other file changes. The database file, `Reviews`, and the server file stay exactly as they were.

### What the Server Sends, and When

**With the boundary, the server sends the page in two parts of one response: the shell at once, and the reviews 2 seconds later.** Here is what happens, in order:
1. The user opens the page. The server calls `getReviews` and starts the render.
2. `Reviews` suspends. The closest boundary above it is our new `<Suspense>`, so React puts its fallback in its place.
3. Nothing outside the boundary is waiting, so the shell is finished at once. React calls `onShellReady`, and the server sends the shell.
4. The user sees the heading, the price, and `Loading reviews...`. The browser tab still shows that it is loading, because the response is not over yet.
5. After 2 seconds, the reviews arrive. React renders `Reviews` and sends its HTML in the same response.
6. The two reviews take the place of `Loading reviews...`. The browser sent no new request.

Why does the response stay open after the shell? Because some boundaries may still be waiting for their data. React's docs: "By the time `onShellReady` fires, components in nested `<Suspense>` boundaries might still be loading data." So the server keeps the response open until the last boundary has been sent.

So on the server, the **fallback** is real HTML that goes out with the shell. React's docs say it plainly: React sends the HTML for the loading fallback first.

But who puts the reviews in the place of `Loading reviews...`, when the browser never asked for anything new? Principle 3 answers that.

### Real Beginner Mistake: An Effect Fetch Inside the Boundary

A developer who knows Lesson 33 loads the reviews with `fetch` inside an Effect. Then they wrap `Reviews` in `<Suspense>`:

```jsx title="src/Reviews.jsx, loading the reviews in an Effect"
import { useState, useEffect } from 'react';

export default function Reviews() {
  const [reviews, setReviews] = useState([]);
  ~useEffect~(() => { // **WRONG:** never runs on the server, so nothing suspends
    fetch('/api/reviews').then(res => res.json()).then(setReviews);
  }, []);
  return <ul>{reviews.map(review => <li key={review}>{review}</li>)}</ul>;
}
```

**The boundary does nothing here: the user sees no reviews, and no `Loading reviews...` line either.** Here is what happens:
1. On the server, Effects do not run. React's docs: "Effects **only run on the client.** They don't run during server rendering."
2. So `Reviews` never suspends. The server sends the component's empty list, not the fallback, and not the reviews. React's docs: "Suspense does not detect data fetched inside an Effect or event handler."
3. The response ends at once. Nothing is streamed later.
4. The reviews appear only after the app's JavaScript loads in the browser, the Effect runs, and its fetch returns.

Remember: only data that suspends is streamed, such as a promise read with `use`.

## PRINCIPLE | The inline `<script>`: the reviews take the place of the fallback before React loads

> [!PRINCIPLE]
> **Principle 3: The Inline Script: React's Script Puts the Reviews in Place of `Loading reviews...`**
>
> *The late HTML of a boundary is sent after the shell, together with an inline `<script>` that replaces the fallback with it; this works before React loads in the browser.*
>
> The server cannot change HTML it already sent. So it sends the reviews at the end of the response, hidden, and an inline script that React writes for us moves them into the place of the fallback. The user reads the reviews as soon as they are ready. The page answers clicks only later, once the app's JavaScript has hydrated it.
>
> **DO THIS:**
> ```jsx
> <Suspense fallback={<p>Loading reviews...</p>}>
>   ~<Reviews reviewsPromise={reviewsPromise} />~ {/* The user reads the reviews before the app's JavaScript loads */}
> </Suspense>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <li>
>   {review} ~<button onClick={markHelpful}>Helpful</button>~ {/* **WRONG:** counting on the first tap: it does nothing until the page hydrates */}
> </li>
> ```

### The Server Cannot Change HTML It Already Sent

In the plain Node server of the opening, the reviews came last, and they also belonged last on the page. So the browser simply added them at the bottom.

Our boundary is different. By the time the reviews are ready, `<p>Loading reviews...</p>` is already on the user's screen, in the middle of the page. The server cannot reach into the browser and change what it sent 2 seconds ago. It can only add more HTML at the end of the response.

So the server does something simple. It sends the reviews at the end, hidden, and right after them a short script that moves them into place. Here is the idea of what the response holds, with plain names of our own:

```html title="What the one response holds, simplified, with our own names for the markers"
<h1>Blue Sneakers</h1>
<p>$49</p>
<p ~id="reviews-place"~>Loading reviews...</p> <!-- The shell marks the place of the fallback -->
<div ~hidden~ id="reviews-ready"><ul><li>Great fit</li><li>Runs small</li></ul></div> <!-- Arrives 2 seconds later, hidden -->
<script>~swap('reviews-place', 'reviews-ready')~</script> <!-- Runs at once: the reviews take the place of the fallback -->
```

React's real markers and its real function have short names that React generates, but the idea is the same. Remember `replaceWith` from plain JavaScript? The script does that kind of job: it finds the fallback, and puts the hidden reviews in its place.

```tree dir=right caption="One HTML response in three parts: the shell, the hidden reviews, and the script that moves them into place."
One response, read by the browser from top to bottom
- +1. The shell [`<h1>` `<p>$49</p>` `<p>Loading reviews...</p>`] | Sent **at once** | The user sees the product and **`Loading reviews...`**
- +2. The reviews [`<ul>`] | Sent **2 seconds later**, at the **end** of the response | Arrives **hidden**, not where it belongs on the page
- +3. The inline script [`<script>`] | Sent **right after the reviews** | Puts the `<ul>` **in the place of `Loading reviews...`**
```

> [!DEFINITION]
> **An inline script.** [NEW] An inline `<script>` is a script whose code is written inside the HTML itself, instead of being loaded from a file. The browser runs it as soon as it reads it. We never write this script: React's server renderer writes it for us. React's docs: React "will send the remaining HTML along with an inline `<script>` tag that replaces the loading fallback with that HTML." React's docs call the moment the content takes the place of its fallback a reveal: the HTML is "progressively revealed" (Lesson 117).

### Why the Reviews Appear in the Middle of the Page

**The reviews arrive at the very end of the response, yet they appear in the middle of the page, and no code of ours moved them.** Here is what happens, in order:
1. The browser reads the shell and shows the heading, the price, and `Loading reviews...`.
2. The response stays open for 2 seconds.
3. The reviews' HTML arrives at the end of the response, hidden. The browser does not show it where it lands.
4. An inline `<script>` arrives right after it, and the browser runs it at once.
5. The script puts the reviews in the place of `Loading reviews...`.
6. All of this can happen before the app's JavaScript has loaded. React's docs: "The HTML content from the server will get progressively revealed before any of the `<script>` tags load."

```page width=text caption="The same page after the inline script has run: the reviews have taken the place of Loading reviews..."
heading: Blue Sneakers
line: $49
line: Great fit | good
line: Runs small | good
```

### VS | The Inline Script vs. the App's JavaScript: one moves HTML, the other makes the page answer clicks

Both are scripts on the same page, and both come from React, so it is easy to give the swap to the app's JavaScript. **They are NOT the same thing!**
- **The inline `<script>` in the response** only moves HTML into place. It is tiny, React's server renderer writes it, and the browser runs it the moment it arrives.
- **The app's JavaScript that calls `hydrateRoot`** loads React and our components, and makes the page answer clicks (as seen in Lesson 104). It is loaded from a file, and it comes later.

```tree caption="The inline script that swaps in the reviews vs. the app's JavaScript that makes the page answer clicks."
Two kinds of script on the streamed page
- +The inline script [`<script>` in the response] | Written by **React's server renderer** | **Moves the reviews into place** the moment it arrives
- +The app's JavaScript [`hydrateRoot`] | Loads **React and our components** from a file | Makes the page **answer clicks**, later
```

So the swap needs neither React in the browser nor hydration. Hydration is still needed for everything that answers a click.

### Real Beginner Mistake: A Button in the Reviews, Tapped Too Early

1. A developer sees the reviews appear in the browser, and concludes that `Reviews` already answers clicks.
2. They add a `Helpful` button with an `onClick` to each review.
3. A user taps `Helpful` as soon as the reviews show. Nothing happens.
4. The reviews' HTML came in, and the inline script showed it. But the app's JavaScript has not loaded or hydrated the page yet (as seen in Lesson 104), so no click handler is attached.

Remember: the inline script shows the reviews, and only hydration makes them answer clicks.

## PRINCIPLE | Two `<Suspense>` boundaries: each section appears when its own data is ready, in any order

> [!PRINCIPLE]
> **Principle 4: Out of Order: `White Socks` Appears Before the Reviews Above It**
>
> *Each boundary's HTML is sent when its own data is ready, not in its order on the page; a lower boundary that is ready first is revealed first.*
>
> The shell holds a place for every boundary. After that, the server flushes each boundary's HTML and script in the order the data is ready, and each script puts its content in its own place. A fast section is never held back by a slow section above it, as long as the two sit in separate boundaries.
>
> **DO THIS:**
> ```jsx
> <Suspense fallback={<p>Loading reviews...</p>}>
>   <Reviews reviewsPromise={reviewsPromise} />
> </Suspense>
> ~<Suspense fallback={<p>Loading suggestions...</p>}>~ {/* Its own boundary: White Socks appears after half a second */}
>   <Suggestions suggestionsPromise={suggestionsPromise} />
> </Suspense>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~<Suspense fallback={<p>Loading...</p>}>~ {/* **WRONG:** one unit, so White Socks waits 2 seconds for the reviews! */}
>   <Reviews reviewsPromise={reviewsPromise} />
>   <Suggestions suggestionsPromise={suggestionsPromise} />
> </Suspense>
> ```

Every shop has a `You may also like` section under the reviews. We add one to our page, in its own boundary:

```jsx title="src/App.jsx"
<h1>Blue Sneakers</h1>
<p>$49</p>
<Suspense fallback={<p>Loading reviews...</p>}>
  <Reviews reviewsPromise={reviewsPromise} /> {/* Ready after 2 seconds */}
</Suspense>
<h2>You may also like</h2>
~<Suspense fallback={<p>Loading suggestions...</p>}>~ {/* A second boundary, lower on the page */}
  <Suggestions suggestionsPromise={suggestionsPromise} /> {/* Ready after half a second */}
</Suspense>
```

`suggestionsPromise` comes from the server file, exactly like `reviewsPromise`. It is a second lookup, `getSuggestions`, which answers with `White Socks` after half a second. So the suggestions sit lower on the page, but their lookup is faster.

**The bottom of the page fills in before the middle.** `White Socks` appears while `Loading reviews...` is still above it:

```page width=text caption="At once: the product, both loading lines, and the You may also like heading."
heading: Blue Sneakers
line: $49
line: Loading reviews...
section: You may also like
line: Loading suggestions...
```

```page width=text caption="After about half a second: White Socks has appeared, and Loading reviews... is still above it."
heading: Blue Sneakers
line: $49
line: Loading reviews...
section: You may also like
line: White Socks | good
```

```page width=text caption="After about 2 seconds: the reviews have appeared too."
heading: Blue Sneakers
line: $49
line: Great fit | good
line: Runs small | good
section: You may also like
line: White Socks
```

A junior developer expects the opposite: HTML is read from top to bottom, so the suggestions must wait for the reviews above them. That is true of the shell. It is not true of the boundaries.

### Out of Order: In the Order the Data Is Ready

This is where the inline script of Principle 3 pays off. The shell holds a place for each boundary. After that, each boundary's HTML is sent when its own data is ready, and its script puts it in its own place, whatever the order. React's docs say that the streaming server renderer "delivers HTML out-of-order". The late parts come in the order their data is ready, not in the order of the page.

React has a word for sending what is ready into the response: to **flush**. Each flush sends one piece of the response, which React's docs call a **chunk**. On our page, the server flushes three chunks:

```tree dir=right caption="The three chunks of one response, flushed in the order the data is ready, not the order of the page."
What the server flushes, and when
- +At once: the shell | `Blue Sneakers`, `$49`, `Loading reviews...`, `You may also like`, `Loading suggestions...`
- +After about half a second: the suggestions | Their HTML and script | `White Socks` **takes the place** of `Loading suggestions...`
- +After about 2 seconds: the reviews | Their HTML and script | `Great fit` and `Runs small` **take the place** of `Loading reviews...`
```

Here is what happens, in order:
1. The server sends the shell at once: the heading, the price, both loading lines, and the `You may also like` heading.
2. After about half a second, the suggestions are ready. React flushes their HTML and a script, and `White Socks` takes the place of `Loading suggestions...`.
3. `Loading reviews...` is still on the page, above `White Socks`.
4. After about 2 seconds, the reviews are ready. React flushes them, and the two reviews take the place of `Loading reviews...`.
5. The response ends.

Why "about"? React does not reveal content at every possible moment. React's docs: "React reveals suspended content at most once every 300ms, measured from the last reveal. Boundaries that become ready within that window are revealed together rather than one at a time." On our page, half a second and 2 seconds are far apart, so the two reveals stay separate. Each one may come a little later than its data.

The new files are small. The database file gains a second lookup:

```js title="src/db.js"
export function ~getSuggestions~() { // Answers with one suggestion after half a second
  return new Promise(resolve => {
    setTimeout(() => resolve(['White Socks']), 500);
  });
}
```

`Suggestions` reads it exactly as `Reviews` reads the reviews:

```jsx title="src/Suggestions.jsx"
import { use } from 'react';

export default function Suggestions({ suggestionsPromise }) {
  const suggestions = ~use(suggestionsPromise)~; // Suspends until the suggestions arrive
  return (
    <ul>
      {suggestions.map(item => <li key={item}>{item}</li>)}
    </ul>
  );
}
```

And the server file starts both lookups for each visit, then passes both promises to `App`:

```jsx title="server.js" startLine="5"
app.use('/', (request, response) => {
  const reviewsPromise = getReviews();
  const suggestionsPromise = ~getSuggestions()~; // Starts at the same moment as the reviews lookup
  const { pipe } = renderToPipeableStream(
    <App reviewsPromise={reviewsPromise} suggestionsPromise={suggestionsPromise} />,
    {
      onShellReady() {
        pipe(response);
      },
    },
  );
});
```

The import line at the top of the server file now brings in `getSuggestions` too, as the complete file at the end shows.

### VS | Two Boundaries vs. One Boundary Around Both: one boundary is one unit

Now suppose we put both sections inside one boundary. **It may look the same, but it is NOT the same thing!**
- **With two boundaries**, each section is revealed when its own data is ready. `White Socks` appears after about half a second.
- **With one boundary around both**, React's docs say "the whole tree inside Suspense is treated as a single unit" (as seen in Lesson 69). So `White Socks`, ready after half a second, waits behind the fallback until the reviews arrive at 2 seconds.

On the server, the boundaries decide what is flushed, and when.

### Real Beginner Mistake: One Boundary for Parallel Loading

1. A developer wants the reviews and the suggestions to load in parallel, and puts both under one `<Suspense>`.
2. Both lookups do start at once, because the server file calls both before the render.
3. But the boundary reveals its content as one unit.
4. `White Socks`, ready after half a second, stays behind the loading line until the reviews arrive at 2 seconds.

Remember: each `<Suspense>` part comes when its own data is ready. Two sections that should appear separately need two boundaries.

## PRINCIPLE | One `<Suspense>` around the whole page: the first screen is only `Loading...`

> [!PRINCIPLE]
> **Principle 5: Minimal but Complete: A Boundary Around the Whole Page Sends Only `Loading...`**
>
> *Place boundaries so the shell stays "minimal but complete", like a skeleton of the page: the real layout, with a fallback only where the slow parts go.*
>
> A boundary takes everything inside it out of the shell. A boundary around the whole page leaves a shell with only its fallback, so the product, ready at once, waits for the slowest data with everything else. Wrap only the slow sections, and the user reads the page while they load.
>
> **DO THIS:**
> ```jsx
> <h1>Blue Sneakers</h1>
> <p>$49</p>
> ~<Suspense fallback={<p>Loading reviews...</p>}>~ {/* Only the slow part: the product goes out at once */}
>   <Reviews reviewsPromise={reviewsPromise} />
> </Suspense>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~<Suspense fallback={<p>Loading...</p>}>~ {/* **WRONG:** the shell is only Loading..., and the product waits 2 seconds! */}
>   <h1>Blue Sneakers</h1>
>   <p>$49</p>
>   <Reviews reviewsPromise={reviewsPromise} />
> </Suspense>
> ```

If one boundary lets the product go out first, why not wrap the whole page, and let everything stream? Here is that page:

```jsx title="src/App.jsx"
~<Suspense fallback={<p>Loading...</p>}>~ {/* **WRONG:** the product is inside the boundary too */}
  <h1>Blue Sneakers</h1>
  <p>$49</p>
  <Reviews reviewsPromise={reviewsPromise} />
</Suspense>
```

**The user sees only `Loading...` for 2 seconds.** The heading and the price are ready at once, but they sit in the same boundary as `Reviews`, and one boundary is one unit.

::: row caption="During the first 2 seconds: a boundary around the whole page sends only a loading line; a boundary around the reviews sends the product."
::: col title="<Suspense> around the whole page" tag="first 2 seconds" tone=bad
```page size=mini
line: Loading...
```
:::
::: col title="<Suspense> around Reviews only" tag="first 2 seconds" tone=good
```page size=mini
heading: Blue Sneakers
line: $49
line: Loading reviews...
```
:::
:::

**It may look the same, but it is NOT the same thing!** Both pages stream, and both end on the same four lines after 2 seconds. But only the page with `<Suspense>` around `Reviews` shows the product at once.

Here is what happens with the boundary around the whole page:
1. The developer wraps the whole page so that everything streams.
2. The server sends the shell at once. The shell is now only the fallback: `Loading...`.
3. The heading and the price are ready, but they sit in the same boundary as `Reviews`, which suspends.
4. The heading and the price may already travel to the browser, but hidden, because the boundary is not ready.
5. After 2 seconds, the reviews arrive, and the boundary is revealed as one unit. The user sees the whole product page at once.

Compare it with Principle 1, where there was no boundary at all. Both keep the product off the screen for 2 seconds. The boundary around everything at least sends `Loading...` at once, so the first byte leaves early. For the moment the product appears, they are the same.

### Minimal but Complete

The boundaries decide what is in the shell. So the question is not "how many boundaries?", but "what should the user see first?". React's docs answer: the shell should be "minimal but complete", "like a skeleton of the entire page layout". And they warn: "seeing a big spinner on the screen can feel slower and more annoying than waiting a bit more and seeing the real layout."

On our page, the shell is complete when it holds the heading, the price, and a fallback where each slow section goes. It is minimal when nothing in it waits for slow data.

The opposite extreme is not better either. React's docs: "Suspense boundaries should not be more granular than the loading sequence that you want the user to experience." Put a boundary where you want the user to see a loading line, and nowhere else (as seen in Lesson 69).

```tree caption="Three places for Suspense on the product page, and what the user sees during the first 2 seconds."
Where the boundary goes on the product page
- !No boundary | The whole page is the shell | **Blank tab** for 2 seconds
- !One boundary around the whole page | The shell is **only `Loading...`** | The product **waits 2 seconds** with the reviews
- +One boundary around each slow section | The shell is **the real page** with a loading line for each slow section | The product shows **at once**
```

### Real Beginner Mistake: One Spinner Around the Whole App

1. A team turns on streaming, and wraps the app's root in one `<Suspense>` with a spinner.
2. Every page now opens on a spinner.
3. The product heading, ready at once, appears only with the slowest data on the page.

Remember: everything outside `<Suspense>` goes out at once, so keep the real page outside, and wrap only the slow parts.

### The Complete Product Page

The database file holds both lookups:

```js title="src/db.js"
export function getReviews() {
  return new Promise(resolve => {
    setTimeout(() => resolve(['Great fit', 'Runs small']), 2000);
  });
}

export function getSuggestions() {
  return new Promise(resolve => {
    setTimeout(() => resolve(['White Socks']), 500);
  });
}
```

`Reviews` and `Suggestions` each read their promise the same way:

```jsx title="src/Reviews.jsx"
import { use } from 'react';

export default function Reviews({ reviewsPromise }) {
  const reviews = use(reviewsPromise);
  return (
    <ul>
      {reviews.map(review => <li key={review}>{review}</li>)}

```


```jsx title="src/App.jsx"
import { Suspense } from 'react';
import Reviews from './Reviews.jsx';
import Suggestions from './Suggestions.jsx';

export default function App({ reviewsPromise, suggestionsPromise }) {
  return (
    <html>
      <body>
        <h1>Blue Sneakers</h1> {/* Principles 1 and 5: the shell, sent at once */}
        <p>$49</p>
        ~<Suspense fallback={<p>Loading reviews...</p>}>~ {/* Principles 2 and 3: flushed after about 2 seconds */}
          <Reviews reviewsPromise={reviewsPromise} />
        </Suspense>
        <h2>You may also like</h2>
        ~<Suspense fallback={<p>Loading suggestions...</p>}>~ {/* Principle 4: flushed after about half a second */}
          <Suggestions suggestionsPromise={suggestionsPromise} />
        </Suspense>
      </body>
    </html>
  );
}
```

The server file starts both lookups for each visit, and starts sending as soon as the shell is ready:

```jsx title="server.js"
import { renderToPipeableStream } from 'react-dom/server';
import App from './src/App.jsx';
import { getReviews, getSuggestions } from './src/db.js';

app.use('/', (request, response) => {
  const reviewsPromise = getReviews();
  const suggestionsPromise = getSuggestions();
  const { pipe } = renderToPipeableStream(
    <App reviewsPromise={reviewsPromise} suggestionsPromise={suggestionsPromise} />,
    {
      ~onShellReady~() { // Principle 1: the shell has rendered, so start sending
        pipe(response);
      },
    },
  );
});
```

### The Order of One Response

```tree dir=right caption="The order in which the server sends one response for the product page, what the user sees after each part, and when the page starts to answer clicks."
One response for the product page, then hydration
- +1. At once: the shell | `Blue Sneakers`, `$49`, `Loading reviews...`, `You may also like`, `Loading suggestions...` | Sent when React calls **`onShellReady`**
- +2. After about half a second: the suggestions | Hidden HTML and an **inline script** | `White Socks` **takes the place** of its loading line
- +3. After about 2 seconds: the reviews | Hidden HTML and an **inline script** | `Great fit` and `Runs small` **take the place** of `Loading reviews...`
- +4. The app's JavaScript [`hydrateRoot`] | Loads from **its own file** and **hydrates** the page | Only then do **buttons answer clicks**
```

### Summary

| Aspect | The Habit That Breaks the Page | The React Rule |
| :--- | :--- | :--- |
| **1. The shell** | Leave a slow component with no boundary above it, so the tab stays blank until it is ready | Everything outside every boundary is the shell, and the server sends nothing until the shell has rendered |
| **2. The fallback** | Fetch the data inside an Effect, and expect the boundary to stream it | Read the data with `use` inside a boundary, so the fallback goes out with the shell and the content follows |
| **3. The swap** | Expect React in the browser to show the late content, and its buttons to answer at once | An inline script from the server swaps in the content before React loads; clicks work after hydration |
| **4. The order** | Put two sections in one boundary so they load in parallel | Give each section its own boundary, so each is flushed and revealed when its own data is ready |
| **5. The placement** | Wrap the whole page so that everything streams | Wrap only the slow parts, so the shell is minimal but complete |

Remember the one sentence of this lesson. **The server sends everything outside `<Suspense>` at once, and each `<Suspense>` part later, when its own data is ready, in the same response.**

## For the Interview

> **The Interview Question:** How does streaming SSR work with Suspense: the shell, fallbacks, and out-of-order flushes?

### How to Answer Clearly in 30 Seconds

"With streaming server rendering, the server sends one HTML response in parts. Everything outside every `<Suspense>` boundary is the shell, and the server sends nothing until the shell has rendered. Each boundary's fallback is sent as HTML inside the shell, in the boundary's place.

When a boundary's data is ready, React sends its HTML later in the same response, with an inline `<script>` that replaces the fallback. That swap needs neither React in the browser nor hydration. Boundaries are flushed out of order, in the order their data is ready. So a fast section lower on the page can appear before a slow one above it.

Three things to watch:
1. **Only data that suspends is streamed**, such as a promise read with `use`. A fetch inside an Effect is not, because Effects never run on the server.
2. **One boundary is one unit**: sections that should appear separately need separate boundaries.
3. **Keep the shell minimal but complete**: a boundary around the whole page sends only a spinner."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does streaming need React to load in the browser before the late content appears?"**
   **No.** The late HTML comes with an inline `<script>` written by React's server renderer, and the browser runs it as soon as it arrives. React's docs: "Streaming does not need to wait for React itself to load in the browser, or for your app to become interactive." The page answers clicks only after the app's JavaScript hydrates it. Boundaries also let React hydrate the page in parts, which React's docs call Selective Hydration. Lesson 151 covers it.
2. **"Why does it matter that the HTML arrives out of order?"**
   **Because the order of the response no longer matches the order of the page.** A section lower on the page that is ready first is flushed first, and its script puts it in its place. This is one reason `useId` exists. React's docs say of it: "it's even more important in React 18 because of how the new streaming server renderer delivers HTML out-of-order" (as seen in Lesson 52). Since React 19.2, React also reveals content at most once every 300 milliseconds, so that boundaries that become ready close together are revealed together.
3. **"A search engine's crawler should get the reviews in the HTML. What do you do?"**
   **Wait for all the content before sending.** With `renderToPipeableStream`, start sending in `onAllReady` instead of `onShellReady`. Lesson 118 teaches both callbacks. React's docs: "If you start streaming here, you won't get any progressive loading. The stream will contain the final HTML." The crawler then gets one complete page, with the reviews in it.

```tree dir=right caption="Interview summary: the shell goes out at once, each boundary follows when its data is ready, and hydration comes last."
Streaming server rendering with Suspense
- +The shell [`onShellReady`] | Everything **outside every boundary** | Sent **at once**, with a **fallback** in each boundary's place
- +Each boundary [`<Suspense fallback>`] | Flushed **when its own data is ready**, in **any order** | An **inline script** puts it in place of its fallback
- !What breaks it [`useEffect` `fetch`] | Data that **never suspends** on the server | The boundary **streams nothing**
```
