# Lecture 65: How flushSync Puts a New Message on the Page Before the Scroll

*(Why does a chat scroll to the message before the one you just sent?)*

> INTERVIEW QUESTION | ❱❱ MORE | What does flushSync do, and when is it the right escape hatch?

---

## VS | A Setter Alone vs. a Setter Inside `flushSync`: the setter alone changes the DOM after the handler ends, `flushSync` changes it before the next line

> In plain JavaScript, when you add a row to a list with `appendChild`, the row is on the page on the very next line. **In React, a setter does not touch the page: React changes the DOM only after your whole event handler ends, and `flushSync` makes React do it right now.** So when the next line of your handler must scroll to the new row, wrap the setter in `flushSync`, or that line still sees the old page.

Remember `appendChild`? In plain JavaScript, you add a row to a list yourself, and the browser obeys on that same line. So the next line can scroll to the new row, and it works:

```js title="Plain JavaScript: the row is in the DOM on its own line"
list.appendChild(newRow); // The browser adds the row right now
~list.lastChild~.scrollIntoView(); // The last row is the new row
```

`lastChild` is a property the browser gives every DOM element. It is the last child element in the DOM at the moment you read it.

In React, you never add the row yourself. You call a setter, and React adds the row for you, from your JSX. But React does not do it on that line. The setter only asks React for a new render. React waits until your whole event handler ends, and only then does it render and change the DOM (Lesson 16). So the same scroll, written right after the setter, still sees the old list:

```jsx title="React: the setter only asks for a render"
setMessages([...messages, newMessage]); // The DOM is unchanged on this line
~listRef.current.lastChild~.scrollIntoView(); // **WRONG:** the last row is still the old one
```

Take a chat app. The user types a message and clicks Send. The message appears at the bottom, and the list slides down to show it. Every chat app does this, and users notice at once when it fails.

Ask yourself: when the scroll line runs, is the new message already in the DOM? No. So the list scrolls to the message before it, and the user's own message stays hidden below the edge of the list. React's docs describe this exact bug: the scroll always "lags behind" by one item.

**Why:** The code reads "add the message, then scroll". So it looks as if the scroll runs after the new message is on the page. It does not. The setter is a request to React, not a command to the browser. When the scroll line runs, the DOM still holds the old list, and the Console shows no error, because no line of our code fails. The scroll simply runs too early.

This is the job of `flushSync`, a function from the `react-dom` package. You wrap the setter in it, and React renders and changes the DOM inside that call, before your next line runs:

```jsx title="React with flushSync: the row is in the DOM before the next line"
~flushSync~(() => { // React renders and changes the DOM before this call returns
  setMessages([...messages, newMessage]);
});
listRef.current.lastChild.scrollIntoView(); // The last row is now the new message
```

Keep one sentence in mind for the whole lesson: **`flushSync` makes React update the DOM before the next line of your code runs.** React's docs say it the same way: "by the time the next line of code runs, React has already updated the DOM."

### The Three Words This Lesson Stands On

> [!DEFINITION]
> **Batching.** [REVIEW] A setter does not change anything on its own line. It puts an update in a queue that React keeps. React waits until the whole event handler ends, and then it does all the queued updates in one render. React's docs compare it to a waiter in a restaurant: the waiter does not run to the kitchen after each dish you name, but waits until you finish your order. One click, many setters, one render (Lesson 16).

> [!DEFINITION]
> **A ref on a JSX tag.** [REVIEW] In plain JavaScript, you grab an element with `document.getElementById`. In React, React creates the elements from your JSX, so you ask React for them with a ref: `<ul ref={listRef}>`. When React puts the `<ul>` element into the DOM, it also puts that same element into `listRef.current`. From then on, you can call any browser method on it, such as `scrollIntoView()`, which scrolls the page or the list until that element is in view (Lesson 31).

> [!DEFINITION]
> **What is flushSync?** [NEW] `flushSync` is a function from the `react-dom` package, not from the `react` package. You pass it a function, its callback, with your setters inside. React calls that callback at once, then renders and changes the DOM for those setters, all before `flushSync` returns. Flush is React's word for sending the waiting updates to the page now, instead of after the handler ends. Sync is short for synchronously: React finishes that work before your next line runs (Lesson 65).

So `flushSync` is like stopping the waiter in the middle of your order. Take what I have ordered so far to the kitchen now, and bring it back before I say another word.

### What It Costs

Batching is what React wants most of the time. One click, one render, however many setters the click calls. Every `flushSync` call skips that wait. React renders and changes the DOM right away, in the middle of your handler.

React's docs warn that "`flushSync` can significantly hurt performance". They call it a last resort: a tool you reach for only when nothing else works.

### The Rule of Thumb: does the next line need the new DOM?

**Ask one question about every setter: does the next line of my event handler read the DOM, for example to scroll to a row or measure it? If yes, wrap the setters in `flushSync`. If not, a plain setter is enough.**

A senior developer also knows the four classic mistakes:
1. **Expecting the setter to change the page on its own line.** The next line then reads the old DOM, and the scroll stops one message short.
2. **Putting the scroll inside the callback of `flushSync`.** The scroll runs before React renders, so it still stops one message short.
3. **Calling `flushSync` inside an Effect.** There it does nothing, and it prints an error.
4. **Wrapping every setter in its own `flushSync`.** Every call is one more render, so one click renders several times.

One small trap on top: developers look for `flushSync` in the `react` package. It comes from `react-dom`, the package of React's tools for the browser DOM.

The rest of the lesson shows each mistake in a real chat.

**PRINCIPLES:** A setter never changes the DOM on its own line. React changes the DOM after the event handler ends, and `flushSync` makes it happen before the next line. Four principles follow:
1. **Principle 1: A Setter Does Not Change the DOM on Its Own Line.** The scroll right after the setter still sees the old list, so it stops one message short.
2. **Principle 2: flushSync Puts the New Message in the DOM Before the Next Line.** Wrap only the setters, and scroll on the line after it.
3. **Principle 3: flushSync Inside an Effect Forces Nothing.** React is still busy with its own work, so it prints an error instead.
4. **Principle 4: Every flushSync Call Is One More Render.** Use one call per event, and only where the next line reads the DOM.

## PRINCIPLE | A setter: React changes the DOM only after the event handler ends

> [!PRINCIPLE]
> **Principle 1: Batching: A Setter Does Not Change the DOM on Its Own Line**
>
> *A setter inside an event handler only asks React for a render. React changes the DOM after the whole handler ends, so a line right after the setter still sees the old DOM.*
>
> The user sends a message, and the list stops on the message before it. The setter asked for a render, and nothing more. When the next line reads the list, the new row is not there yet. Code that needs only the new message itself, such as sending it to the server, can use `newMessage` on the very next line. Code that needs the new row in the DOM has to wait for React, or make React hurry, as Principle 2 shows.
>
> **DO THIS:**
> ```jsx
> function handleSend() {
>   setMessages([...messages, newMessage]);
>   ~sendToServer(newMessage)~; // Uses the message itself, not the DOM, so nothing lags
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleSend() {
>   setMessages([...messages, newMessage]);
>   ~listRef.current.lastChild~.scrollIntoView(); // **WRONG:** the DOM still holds the old list
> }
> ```

### VS | `appendChild` vs. a Setter: the browser adds the row on that line, React adds it after the handler

Both pieces of code below add a row, and then scroll to the last row. They differ in who adds the row: your own code, or React.

```js title="Plain JavaScript: a command to the browser"
list.appendChild(newRow); // The DOM has the new row right now
~list.lastChild~.scrollIntoView(); // Scrolls to the new row
```

```jsx title="React: a request to React"
setMessages([...messages, newMessage]); // The DOM is unchanged on this line
~listRef.current.lastChild~.scrollIntoView(); // **WRONG:** scrolls to the old last row
```

Both say "add the row, then scroll to it". It looks the same, but it is NOT the same thing! `appendChild` is a command, and the browser obeys it on that line (Lesson 13). The setter is a request, and React answers it only after your handler has finished.

### Why the List Stops on See you there

**The scroll runs before React puts the new message in the DOM.** Here is the order, one step at a time:
1. The user clicks Send, and React runs `handleSend`.
2. The two setters queue a new render. Nothing on the page changes yet.
3. The scroll line reads `listRef.current.lastChild`. The DOM still holds the old six rows, so the last row is `See you there`.
4. The list scrolls down to `See you there`.
5. `handleSend` ends. Now React renders `ChatRoom` with seven messages, and adds the seventh `<li>` below the edge of the list.

React's docs name the cause: "state updates are queued", and the setter "does not immediately update the DOM." So when the scroll line runs, the new item "has not yet been added."

Is batching the bug, then? No. Batching is what React wants most of the time, because it "prevents multiple re-renders during a single event." The trouble is only that our scroll needs the DOM of the next render while the handler is still running.

### The Real Mistake: Blaming the Scroll

A developer who meets this bug usually suspects `scrollIntoView()`. They add options such as `{ behavior: 'smooth' }`, or they scroll the list by a fixed number of pixels. The list still stops one message short. The scroll is fine. The timing is wrong.

Remember: a setter is a request. React changes the DOM after the handler ends.

## PRINCIPLE | `flushSync`: the DOM is updated before the next line runs

> [!PRINCIPLE]
> **Principle 2: flushSync: The New Message Is in the DOM Before the Next Line**
>
> *When code in an event handler must read or scroll the DOM right after a state change, wrap the setters in `flushSync` from `react-dom`, and put the DOM code on the line after it.*
>
> React calls the callback at once, renders, and changes the DOM before `flushSync` returns. So the scroll on the next line finds the new message, and the user sees what they just sent. Only the DOM is ahead: the handler still reads its own snapshot of state.
>
> **DO THIS:**
> ```jsx
> flushSync(() => {
>   setMessages([...messages, newMessage]);
> });
> ~listRef.current.lastChild~.scrollIntoView(); // The new message is already in the DOM
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> flushSync(() => {
>   setMessages([...messages, newMessage]);
>   ~listRef.current.lastChild~.scrollIntoView(); // **WRONG:** runs before React renders, so it still stops one message short
> });
> ```

### What One flushSync Call Does

The function we pass to `flushSync` is its callback. We hand it over, and React calls it at once, inside `flushSync`. React's docs: React "will immediately call this callback and flush any updates it contains synchronously."

Here is what happens inside one call, in order:

```tree dir=right caption="What happens inside one flushSync call, in order."
One `flushSync` call
- +1. React calls our callback [`flushSync`] | The setters inside it **queue their updates**
- +2. React renders [`ChatRoom`] | `ChatRoom` runs with the **new list**
- +3. React changes the DOM | The new `<li>` is **in the DOM**
- +4. `flushSync` returns | The next line **sees the new DOM**
```

### flushSync in the Chat Room

`flushSync` is not in the `react` package. We import it from `react-dom`, the same package whose client part gives us `createRoot` (Lesson 07). React's docs list it among the tools of `react-dom` that "are rarely used".

```jsx title="src/components/ChatRoom.jsx" startLine="1"
import { useState, useRef } from 'react';
import { ~flushSync~ } from 'react-dom'; // From react-dom, not from react
```

Then we wrap both setters of `handleSend` in one `flushSync` call, as React's docs do in their own fix:

```jsx title="src/components/ChatRoom.jsx" startLine="20"
  function handleSend() {
    const newMessage = { id: nextId++, text: text };
    ~flushSync~(() => { // React renders and changes the DOM for both updates before this call returns
      setText('');
      setMessages([...messages, newMessage]);
    });
    listRef.current.lastChild.scrollIntoView(); // The last row is now On my way
  }
```

The user types `On my way` and clicks Send. The list scrolls down to the new message, and the message field is empty:

```page width=text caption="The chat room after the click with flushSync: the list scrolls to On my way, and the message field is empty."
line: The cafe on Main Street
line: See you there
line: On my way | good
form:
  field:  |
  button: Send
```

React's docs describe the same result: "the last todo will already be in the DOM by the time you try to scroll to it".

### The DOM Changes, the Variable Does Not

Something that can be tricky: **`flushSync` changes the DOM, not `messages`.** After the call returns, the DOM holds seven rows. But `messages`, inside this running `handleSend`, still holds six.

Why? `messages` is the snapshot of the render in which the user clicked (Lesson 15). `flushSync` made React run and finish the next render, and that next render has its own `messages`. Our handler keeps reading its own snapshot:

```jsx title="The DOM and the snapshot right after flushSync"
flushSync(() => {
  setMessages([...messages, newMessage]);
});
console.log(~listRef.current.lastChild.textContent~); // On my way: the DOM already has the new row
console.log(~messages[messages.length - 1].text~); // See you there: this handler still reads its own snapshot
```

And what does `flushSync` give back? Whatever our callback returns. Our callback returns nothing, so here `flushSync` returns `undefined`.

### Only the Setters Go Inside the Callback

A developer reads that `flushSync` updates the DOM at once, and moves the scroll inside the callback too:

```jsx title="The scroll written inside the callback"
flushSync(() => {
  setMessages([...messages, newMessage]);
  ~listRef.current.lastChild~.scrollIntoView(); // **WRONG:** React has not rendered yet, so this still finds See you there
});
```

The list still stops one message short. React renders only after our callback has run. So a scroll inside the callback runs before the render, just as it did without `flushSync`.

React's docs say exactly when the DOM changes: "right after the code wrapped in `flushSync` executes". So the setters go inside the callback, and the code that reads or scrolls the DOM goes on the line after it.

### What Else flushSync May Flush

`flushSync` flushes the updates inside its callback. React's docs add three things it may flush along with them:
1. **Pending updates from outside the callback.** A pending update is one that React has queued but not rendered yet. React's docs: "if there are pending updates from a click, React may flush those before flushing the updates inside the callback."
2. **Pending Effects.** `flushSync` "may run pending Effects".
3. **Updates inside those Effects.** It may "synchronously apply any updates they contain before returning."

So a setter written above the `flushSync` call, in the same click, may be flushed too. But React's docs do not promise it. That is why we keep both setters of Send inside the one callback.

Remember: `flushSync` makes React update the DOM before the next line of your code runs.

## PRINCIPLE | `flushSync` inside an Effect: React is busy, so it forces nothing and prints an error

> [!PRINCIPLE]
> **Principle 3: Where flushSync Runs: Inside an Effect It Forces Nothing**
>
> *Call `flushSync` from an event handler. While React renders a component, inside `useEffect` or `useLayoutEffect`, or in a class lifecycle method, it cannot flush, so it does nothing and prints an error.*
>
> React can render and change the DOM inside `flushSync` only when it is not busy with its own work. A click handler runs while React is not rendering. An Effect runs while React is still finishing, so `flushSync` gives up, and the Console shows "flushSync was called from inside a lifecycle method". Move the call to an event handler, or, as a last resort, defer it with `queueMicrotask`.
>
> **DO THIS:**
> ```jsx
> function handleSend() {
>   ~flushSync~(() => { // In an event handler, React can flush
>     setMessages([...messages, newMessage]);
>   });
>   listRef.current.lastChild.scrollIntoView();
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   ~flushSync~(() => { // **WRONG:** inside an Effect, React prints an error and forces nothing
>     setMessages([...messages, { id: nextId++, text: 'Welcome to the chat' }]);
>   });
> }, []);
> ```

### VS | `flushSync` in a Click Handler vs. in an Effect: React can flush after a click, not in the middle of its own work

Both pieces of code below make the same `flushSync` call. One sits in a click handler, the other in an Effect:

```jsx title="flushSync in a click handler"
function handleSend() {
  ~flushSync~(() => { // React is not rendering: it can flush now
    setMessages([...messages, newMessage]);
  });
}
```

```jsx title="flushSync in an Effect"
useEffect(() => {
  ~flushSync~(() => { // **WRONG:** React is still finishing its own work: it cannot flush here
    setMessages([...messages, { id: nextId++, text: 'Welcome to the chat' }]);
  });
}, []);
```

It looks the same, but it is NOT the same thing! When the user clicks, React is not rendering anything, so it can render and change the DOM inside the call. When an Effect runs, React is still in the middle of its own work, and it cannot start another render inside it.

React's docs say it plainly: "React cannot `flushSync` in the middle of a render. If you do, it will noop and warn." To noop means to do nothing.

### A Welcome Line When the Chat Opens

Say a developer has just learned `flushSync` for Send. Now they want a welcome line at the end of the list when the chat opens. They import `useEffect`, write an Effect, and wrap its setter in `flushSync`, to be safe:

```jsx title="src/components/ChatRoom.jsx"
useEffect(() => {
  ~flushSync~(() => { // **WRONG:** called inside an Effect, so React prints an error and forces nothing
    setMessages([...messages, { id: nextId++, text: 'Welcome to the chat' }]);
  });
}, []);
```

The chat opens, and the Console shows the same red error twice:

```devconsole width=full caption="The Console when the chat opens with flushSync inside the Effect: one error for each run of the Effect."
x flushSync was called from inside a lifecycle method. React cannot flush when React is already rendering. Consider moving this call to a scheduler task or micro task.
x flushSync was called from inside a lifecycle method. React cannot flush when React is already rendering. Consider moving this call to a scheduler task or micro task.
```

**The `flushSync` call forced nothing.** Here is the order:
1. The chat opens. React renders `ChatRoom` and puts the six messages in the DOM.
2. React runs the Effect, and the Effect calls `flushSync`.
3. React is still finishing this work, so `flushSync` does not render. React prints the error instead.
4. The welcome line still reaches the page later, when React has finished, just as it would with a plain setter. What `flushSync` promised, a DOM updated by the next line, did not happen.

Why twice? In development, Strict Mode runs the Effect twice when the chat opens (Lesson 47). Each run calls `flushSync`, and each call prints the error.

### Why the Error Names a Lifecycle Method

Our code has no lifecycle method, yet the error names one. React prints the same error for every place where it is already busy. React's docs list three such places:
1. While React renders a component.
2. Inside `useLayoutEffect` or `useEffect`.
3. Inside the lifecycle methods of class components, the older way of writing components, which this book does not use.

An Effect is the second place. The advice at the end of the error, "a scheduler task or micro task", points to the second of the two fixes below.

### The Two Fixes from React's Docs

React's docs give two fixes, in this order:
1. **Move the `flushSync` call to an event handler.** "To fix this, you usually want to move the `flushSync` call to an event". Our Send handler is already that place.
2. **Defer it to a microtask, as a last resort.** A microtask is a small piece of work that the browser runs as soon as the code running now has finished, before anything else. `queueMicrotask` is the browser function, not a React one, that hands the browser such a piece of work. By the time it runs, React has finished, so it can flush.

```jsx title="The last-resort fix: flushSync inside queueMicrotask"
useEffect(() => {
  ~queueMicrotask~(() => { // Runs after React finishes its current work
    flushSync(() => {
      setMessages([...messages, { id: nextId++, text: 'Welcome to the chat' }]);
    });
  });
}, []);
```

React's docs warn that "this particular pattern is even worse for performance. Exhaust all other options before calling `flushSync` in a microtask as an escape hatch."

### The Welcome Line Needs Neither Fix

For our welcome line, we need neither fix. Nothing reads the DOM right after the welcome line is added, so a plain setter is enough.

There is a deeper reason, too. An Effect already runs after React has changed the DOM (Lesson 32). So code in an Effect that reads the DOM of that render never needs `flushSync`. We remove the welcome Effect, and the chat room goes back to its six messages.

Remember: `flushSync` belongs in an event handler, where React is not busy.

## PRINCIPLE | `flushSync`: every call is one more render, so use one call per event

> [!PRINCIPLE]
> **Principle 4: The Cost of flushSync: Two Calls Turn One Send into Two Renders**
>
> *Every `flushSync` call is one render and one DOM change right away. Use one call per event, and only when code must see the DOM right after an update.*
>
> Batching lets React do all the updates of one click in one render. Each `flushSync` call opts out of that and makes React render at once, so two calls in one handler mean two renders for one click. It can also show a Suspense fallback again and skip a View Transition. Keep it for a scroll or a measurement right after an update, or for a browser API such as the `beforeprint` event, which reads the DOM by the end of its callback.
>
> **DO THIS:**
> ```jsx
> ~flushSync~(() => { // One render and one DOM change for the whole Send
>   setText('');
>   setMessages([...messages, newMessage]);
> });
> listRef.current.lastChild.scrollIntoView();
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~flushSync~(() => { // **WRONG:** a second flushSync below makes one click render twice
>   setText('');
> });
> flushSync(() => {
>   setMessages([...messages, newMessage]);
> });
> ```

### VS | One `flushSync` Around Both Setters vs. One per Setter: the same page, twice the renders

Both handlers below end with the same page: an empty message field, and the list on `On my way`. They differ in how many times React renders:

```jsx title="One flushSync around both setters"
~flushSync~(() => { // One render for both updates
  setText('');
  setMessages([...messages, newMessage]);
});
listRef.current.lastChild.scrollIntoView();
```

```jsx title="One flushSync per setter"
~flushSync~(() => { // First render: only the message field changes
  setText('');
});
~flushSync~(() => { // Second render: now the list changes
  setMessages([...messages, newMessage]);
});
listRef.current.lastChild.scrollIntoView();
```

It looks the same, but it is NOT the same thing! Every `flushSync` call is a render of its own. Between the two calls, React puts a half-finished page in the DOM: an empty message field under the old list. This is the half-finished render that batching normally saves us from (Lesson 16).

### Count the Renders in the Console

To count the renders, we print a line each time React calls `ChatRoom` (Lesson 54):

```jsx title="src/components/ChatRoom.jsx" startLine="15"
  const [text, setText] = useState('');
  const listRef = useRef(null);

```

- Each letter the user types is a render too. So the user types `On my way` first, then we clear the Console, and then the user clicks Send.

With one `flushSync` around both setters, the click prints one pair, so one render:

The user sees the same page. But one click made React do the whole render twice.

And the plain Send of Principle 1, without `flushSync`? It also renders once, so the count matches one `flushSync`. The timing does not. Without `flushSync`, React renders after the handler ends. With it, React renders inside the handler, before the scroll line.

### What flushSync Costs

A developer bitten once by the lagging scroll may wrap every setter in the app in `flushSync`, so the DOM is "always up to date". React's docs list what that costs:
1. **More renders.** Each call is one render right away, and its updates are not batched with the rest of the click. React's own upgrade guide names `flushSync` as the way "to opt-out of automatic batching".
2. **A loading screen shown again.** "`flushSync` may force pending Suspense boundaries to show their `fallback` state." A part of the page that waits for data can flash its loading state again. Lesson 69 teaches Suspense.
3. **A skipped animation.** If a `flushSync` lands in the middle of a View Transition, "React will skip the Transition". Lesson 74 teaches View Transitions.

React's docs say it in bold: "**Using `flushSync` is uncommon, and using it often can significantly hurt the performance of your app.**" And: "Most of the time, `flushSync` can be avoided. Use `flushSync` as last resort."

### When flushSync Is the Right Escape Hatch

`flushSync` is an escape hatch, like a ref (Lesson 30). An escape hatch is a way to step outside the normal flow of React when we have to. React's docs name two cases where we have to:
1. **Code in an event handler must read, scroll, or measure the DOM right after a state change.** Our Send button is this case.
2. **A browser API, or a library written outside React, reads the DOM by the end of its own callback.** React's docs: "Some browser APIs expect results inside of callbacks to be written to the DOM synchronously, by the end of the callback, so the browser can do something with the rendered DOM."

React's docs show the second case with printing. The browser fires a `beforeprint` event just before it opens the print dialog. It prints the page as the DOM stands when the handler of that event ends.

Their example is a small page with a heading and a Print button. The heading reads `isPrinting: yes` or `isPrinting: no`:

```jsx title="React's docs: setting isPrinting inside flushSync before the browser prints"
export default function PrintApp() {
  const [isPrinting, setIsPrinting] = useState(false);

  useEffect(() => {
    function handleBeforePrint() {
      ~flushSync~(() => { // The DOM shows isPrinting: yes before the print dialog reads it
        setIsPrinting(true);
      });
    }
    function handleAfterPrint() {
      setIsPrinting(false);
    }
    window.addEventListener('beforeprint', handleBeforePrint);
    window.addEventListener('afterprint', handleAfterPrint);
    return () => {
      window.removeEventListener('beforeprint', handleBeforePrint);
      window.removeEventListener('afterprint', handleAfterPrint);
    };
  }, []);

  return (
    <>
      <h1>isPrinting: {isPrinting ? 'yes' : 'no'}</h1>
      <button onClick={() => window.print()}>Print</button>
    </>
  );
}
```

With `flushSync`, the print dialog shows `isPrinting: yes`. Without it, React's docs say, "the print dialog will display `isPrinting` as "no"". React would change the DOM only after the browser has already read it.

Wait, this code has an Effect. Does it break Principle 3? No. The Effect only adds and removes the event listeners. The `flushSync` call sits inside `handleBeforePrint`, which the browser calls later, when React is not rendering.

Outside these two cases, `flushSync` is not needed. React's docs: "If your app only uses React APIs, and does not integrate with third-party libraries, `flushSync` should be unnecessary." And when no single event causes the change, they point to an Effect instead: "If you want to do something with a ref, but there is no particular event to do it in, you might need an Effect."

Remember: one `flushSync` per event, and only when the next line needs the new DOM.

```jsx title="src/components/ChatRoom.jsx"
import { useState, useRef } from 'react';
import { ~flushSync~ } from 'react-dom'; // Principle 2: from react-dom, not from react

const initialMessages = [
  { id: 1, text: 'Hi!' },
  { id: 2, text: 'Lunch at 12?' },
  { id: 3, text: 'Sure' },
  { id: 4, text: 'Where?' },
  { id: 5, text: 'The cafe on Main Street' },
  { id: 6, text: 'See you there' },
];

let nextId = 7;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);
  const [text, setText] = useState('');
  const listRef = useRef(null);
  console.log('ChatRoom rendered');

  function handleSend() {
    const newMessage = { id: nextId++, text: text };
    ~flushSync~(() => { // Principles 1, 3 and 4: one call, in an event handler, around both setters
      setText('');
      setMessages([...messages, newMessage]);
    });
    ~listRef.current.lastChild~.scrollIntoView(); // Principle 2: on the line after, it finds On my way
  }

  return (
    <section>
      <ul className="messages" ref={listRef}>
        {messages.map(m => (
          <li key={m.id}>{m.text}</li>
        ))}
      </ul>
      <input value={text} onChange={e => setText(e.target.value)} />
      <button onClick={handleSend}>Send</button>
    </section>
  );
}
```

| Aspect | The Common Habit | The React Rule |
| :--- | :--- | :--- |
| **The scroll after a setter** | Scroll on the next line and expect the new row, so the list stops one message short | A setter only queues a render; React changes the DOM after the handler ends |
| **flushSync** | Put the scroll inside the callback too, or look for `flushSync` in `react` | Import it from `react-dom`, put only the setters inside the callback, and scroll on the next line |
| **Where to call it** | Copy `flushSync` into an Effect, which prints an error and forces nothing | Call it from an event handler; defer it with `queueMicrotask` only as a last resort |
| **How often** | Wrap every setter in its own `flushSync`, so one click renders several times | One call per event, only where code must see the DOM right after an update |

Remember the one sentence of this lesson. **`flushSync` makes React update the DOM before the next line of your code runs, so use it only when that next line needs the new DOM.**

## For the Interview

> **The Interview Question:** What does flushSync do, and when is it the right escape hatch?

### How to Answer Clearly in 30 Seconds

"Normally, a setter only queues a render, and React updates the DOM after the event handler ends. So code right after the setter still sees the old DOM. A chat that scrolls to the last message after Send stops one message short. `flushSync`, from `react-dom`, fixes that. React calls its callback at once, then renders the updates inside it and changes the DOM, so by the next line the DOM is updated. Three rules keep it safe:
1. **Only the setters go inside the callback**, and the code that reads or scrolls the DOM goes on the next line.
2. **Call it from an event handler.** While React is rendering, inside `useEffect` or `useLayoutEffect`, or in a class lifecycle method, it does nothing and prints an error.
3. **Use it rarely.** Each call is one more render with no batching, and it can show a Suspense fallback again. It is the right escape hatch when an event handler must read or scroll the DOM right after an update, or when a browser API such as `beforeprint` reads the DOM by the end of its callback."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"After `flushSync` returns, does the state variable hold the new value?"**
   No. `flushSync` changes the DOM, not the variable in the running handler. Inside `handleSend`, `messages` is the snapshot of the render in which the user clicked, so it still holds six messages, while the DOM already shows seven. The next render of `ChatRoom` gets the new `messages`. `flushSync` returns only what our callback returns, and our callback returns nothing.
2. **"What exactly does `flushSync` flush?"**
   The updates inside its callback. React's docs add that it may also flush pending updates from outside the callback, such as an earlier setter in the same click, and pending Effects together with the updates inside them. If an update suspends, the Suspense fallbacks may be shown again. It can also wrap `root.render(...)` when a page must render fully before the next line, as React's docs show for `createRoot`.
3. **"Why not call `flushSync` inside `useEffect`?"**
   Because React cannot flush in the middle of its own work. Inside an Effect, `flushSync` does nothing, and the Console shows "flushSync was called from inside a lifecycle method". An Effect already runs after React has changed the DOM, so it can read that DOM without `flushSync`. If an Effect really must force a synchronous update, React's docs defer the call with `queueMicrotask`, and they call that even worse for performance.

```tree caption="Interview summary: where flushSync helps, and where it fails or costs too much."
Where `flushSync` belongs
- +In an event handler, before DOM code [`flushSync` `scrollIntoView`] | React renders and changes the DOM **inside the call** | The next line **sees the new DOM**
- !Inside an Effect or during a render [`useEffect` `useLayoutEffect`] | React is **already busy** | It **forces nothing** and prints an **error**
- !Around every setter [`flushSync` everywhere] | **One render per call**, no batching | Slower clicks and **fallbacks shown again**
```
