# Lecture 90: How a Shared Button Tells the Type-Checker Which Props It Takes

*(How does TypeScript catch a misspelled prop before the user ever sees the page?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How do you type React components, props, optional attributes, and children in TypeScript?

---

## VS | A Button Without a Type vs. a Button With a Type: the plain one accepts any prop name, while the typed one is checked in the editor

> A component receives its props as one plain object, and plain JavaScript lets a page write any prop name on the tag, even a misspelled one. **In TypeScript, you give that props object a type: a short description of which props the component takes, and the editor checks every tag against it.** So a misspelled prop is underlined in red while you type, instead of reaching the user as an empty button and a quiet Console.

Start with a plain JavaScript function, `function greet(name)`. JavaScript lets you call it with anything: a name such as `greet('John')`, a number such as `greet(42)`, or nothing at all. It never complains while you write the code. You find the mistake later, when the page runs and something looks wrong.

TypeScript adds one thing to JavaScript: after a parameter, you write what it must be.

```tsx title="The same function, without a type and with a type"
function greet(name) { return 'Hello ' + name; } // Plain JavaScript: name can be anything
function greet(name~: string~) { return 'Hello ' + name; } // TypeScript: name must be a string
greet(~42~); // The editor underlines 42 at once: a number is not a string
```

Now the React part. A component is a function too, and its one parameter is the props object. So the type goes in the same place: right after the props.

```tsx title="The same Button, without a type and with a type"
function Button({ label }) { // Plain JavaScript: any prop name is accepted
  return <button>{label}</button>;
}

function Button({ label }~: { label: string }~) { // TypeScript: the props object must hold label, a string
  return <button>{label}</button>;
}
```

> [!DEFINITION]
> **What is TypeScript, and what is a type?** [NEW] TypeScript is JavaScript with types added. A type is a short description of what a value must look like.
> `string` means "a piece of text". `{ label: string }` means "an object that holds `label`, and `label` is a piece of text".
> Something that can be tricky: a type is never a value. It describes values, and it never runs (Lesson 90).

> [!DEFINITION]
> **What is the props object?** [REVIEW] React calls your component with one argument: an object that holds every attribute written on the tag.
> For `<Button label="Add to cart" />`, React calls `Button({ label: 'Add to cart' })`. The curly braces in `function Button({ label })` unpack `label` out of that object (Lesson 08).

### A misspelled prop, with and without a type

A product page uses the button, and the developer makes a small typing mistake. The page writes `lable` instead of `label`:

```tsx title="A product page that misspells the prop name"
<main>
  <h1>Wireless headphones</h1>
  <p>$200</p>
  <Button ~lable~="Add to cart" /> {/* The developer meant label */}
</main>
```

With the plain JavaScript button, nothing complains. The page opens, and the user sees a button with no text on it:

```page width=text caption="The product page with the misspelled prop: the button is there, but it holds no text, and the Console is quiet."
heading: Wireless headphones
line: $200
form:
  button: 
console: quiet
```

Why? React passed `Button` an object with one key, `lable`. The component reads `label`, and that object has no `label`. So `label` is `undefined`, and React shows nothing in its place (Lesson 10). No line of code is broken, so the Console has nothing to say.

With the typed button, the mistake never reaches the user. As soon as the developer types `lable`, the editor underlines it in red. The message says that the props of `Button` have no prop with that name.

> [!DEFINITION]
> **What is the type-checker?** [NEW] The type-checker is the part of TypeScript that reads your types and compares every value with them. A mismatch it finds is called a type error.
> Remember the spell checker in a word processor? It underlines a misspelled word while you type, long before anyone reads the letter, and it never changes the printed letter.
> The type-checker does the same for props. It underlines `lable` while you type, and it never runs in the user's browser (Lesson 90).

### The types never reach the browser

Here is the part that surprises most developers. **In the browser, the two buttons are the exact same thing.** Before the code runs, the tool that runs the project, such as Vite, deletes every type. The browser receives the same JavaScript from both versions.

react.dev says this about its own code sandboxes: they "do not run the type-checker", so "you won't get any type errors or warnings" there. The code still runs.

**For the developer, it is NOT the same thing.** Only the typed version stops `lable` before anyone opens the page. react.dev says what types give you: they "can be used for correctness checking and providing inline documentation in editors."

And nothing else checks props anymore. Older React checked props in the browser, with `propTypes`. React 19 removed those checks, and react.dev says that using `propTypes` now "will be silently ignored". So the type-checker in the editor is the only check left.

```tree caption="The same Button without a type and with a type: the browser runs the same code, but only the typed version is checked in the editor."
The same `Button`, with and without a type for its props
- !Without a type [`{ label }`] | The editor **accepts any prop name** | `lable` reaches the page: **an empty button** and **a quiet Console**
- +With a type [`{ label }: { label: string }`] | The type-checker **compares every tag** with the type | `lable` is **underlined in the editor** before the page opens
```

### The Rule of Thumb: describe the props object once

**A component receives one props object. Describe it once with a type, and the editor checks every tag on every page against it, before the page runs. In the browser, the type is gone.**

The type catches four kinds of mistakes, each one in the editor:
1. **A prop name the type does not list**, such as `lable`.
2. **A prop the type requires**, and the page leaves out.
3. **A value that is not allowed**, such as a style name typed wrong.
4. **An attribute of the real `<button>`** that the component does not accept, such as `disabled`.

A senior developer also knows the three classic mistakes:
1. **Believing TypeScript checks props in the browser.** The types are deleted before the code runs, and React 19 ignores `propTypes`.
2. **Typing `children` as a string, or as `React.ReactElement`.** Then a page cannot pass plain text next to a tag, such as `Add to cart` with the price in bold.
3. **Listing the attributes of `<button>` by hand, one by one.** Then the shared button refuses the next attribute a page needs, again and again.

## SECTION | A Product Page with One Shared Button

Our page is the product page of an online store, for a pair of wireless headphones. Under the price sit two buttons:

```page width=text caption="The headphones product page we build: a heading, the price, and two buttons made by one shared Button component."
heading: Wireless headphones
line: $200
form:
  button: Add to cart
  button: Save for later
console: quiet
```

Both buttons come from one shared `Button` component. `Add to cart` will be filled, and `Save for later` will have an outline. The store uses this same component on every page: the product page, the cart, the checkout. That is why one wrong prop on one page is so easy to miss.

A React project in TypeScript needs two small setup steps, and we use them without going into detail:
1. **It installs `@types/react` and `@types/react-dom`.** These two packages bring the types of React.
2. **Its settings file, `tsconfig.json`, tells TypeScript to read JSX.** And every file that holds JSX ends in `.tsx` instead of `.jsx`, as react.dev says.

```files title="product-page: File Explorer" caption="Our project files: App.tsx places two shared buttons, and Button.tsx holds the button and the type of its props."
index.html | entry | The HTML page with the empty root div where React mounts
tsconfig.json | settings | Tells TypeScript how to read the project, JSX included
src/
  main.tsx | boundary | Imports `App` from `./App` and mounts it into `#root`
  App.tsx | page | Exports `App` as default and places two `<Button>` tags
  components/
    Button.tsx | shared component | Exports `Button` as default with the type of its props
    Button.css | style | Gives `.primary` a filled look, `.secondary` an outline, and a turned-off button a dimmed look
```

The button starts as plain JavaScript, moved into a `.tsx` file, with no type yet:

```tsx title="src/components/Button.tsx"
export default function Button(~{ label }~) { // No type yet: any prop name passes
  return <button>{label}</button>;
}
```

The store will ask for four things, one at a time. Catch the misspelled prop. Add a style. Put the price in bold inside the button. Turn the button off when the headphones are sold out. Each principle answers one request.

**PRINCIPLES:** A props type describes the one object React passes to a component, and the type-checker compares every tag with it in the editor. Four principles follow:
1. **Principle 1: `ButtonProps` checks every tag.** Write the type after the props, inline or named with `interface`. The editor reports a prop name the type does not list, and a required prop the page leaves out.
2. **Principle 2: `variant?` with a union of words.** The question mark lets a page leave the prop out. The union lists the only words allowed. The default value goes in the parameter list, because React 19 ignores `defaultProps` on function components.
3. **Principle 3: `children: React.ReactNode`.** It accepts text, numbers, tags, and nothing at all. `React.ReactElement` accepts only JSX tags, so it refuses plain text.
4. **Principle 4: `extends React.ComponentPropsWithRef<'button'>`.** The button takes every attribute a real `<button>` takes, adds only its own props, and passes the rest to the real tag with spread.

## PRINCIPLE | `interface ButtonProps`: every `<Button>` tag is checked in the editor, before the page opens

> [!PRINCIPLE]
> **Principle 1: Props Type: The Type-Checker Compares Every Tag with `ButtonProps`**
>
> *Give the props object a type after the destructured parameter, inline or named with `interface`; the type-checker then reports a prop name the type does not list, and a listed prop that the page leaves out.*
>
> Without a type, a page can write `lable` instead of `label`, and the user gets a button with no text while the Console stays quiet. With `ButtonProps`, the editor underlines the mistake before the page opens. Only the editor and the type-checker read the type. The browser runs the same code as without it, and React 19 no longer checks props in the browser.
>
> **DO THIS:**
> ```tsx
> interface ButtonProps {
>   label: string;
> }
> function Button({ label }~: ButtonProps~) { // Every <Button> tag is compared with ButtonProps
>   return <button>{label}</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Button(~{ label }~) { // **WRONG:** no type, so lable passes and the button shows no text
>   return <button>{label}</button>;
> }
> ```

### VS | An inline type vs. a named `interface`: both describe the same props object

So far the type sat inside the parameter line. react.dev calls this "the simplest way to provide types for a component". It also warns that it "can become unwieldy" once the props have a few fields. Our button will soon have a style, a price in bold, and more. So we give the type a name, and write it above the component:

```tsx title="The props type written inline, and the same type named with interface"
function Button({ label }~: { label: string }~) { // 1. The type sits inside the parameter line
  return <button>{label}</button>;
}

~interface ButtonProps~ { // 2. The same type gets a name, with one line per prop
  label: string;
}

function Button({ label }~: ButtonProps~) { // The parameter now points to that name
  return <button>{label}</button>;
}
```

**Yes, it is the exact same thing!** Both describe one object that holds `label`, a string. The name only moves the description out of the parameter line, so that line stays short when the props grow.

TypeScript has a second word for naming a type, `type`:

```tsx title="The same props type named with interface, and named with type"
~interface~ ButtonProps { label: string; } // 1. Named with interface
~type~ ButtonProps = { label: string }; // 2. Named with type: the same description
```

For a props object, these two are the exact same thing as well. react.dev says the props type "should be an object type described with either a `type` or `interface`." In this lesson we use `interface`, as react.dev does for its own button.

> [!DEFINITION]
> **What is an object type?** [NEW] An object type lists the keys an object must hold, and the type of each key.
> `{ label: string }` is an object type: the object must hold `label`, and `label` must be a string.
> `interface ButtonProps { label: string; }` is the same object type, with a name you can reuse (Lesson 90).

```tree caption="Three ways to write the props type of Button: all three describe the same object with label as a string."
Three ways to describe the props of `Button`
- +Inline after the parameter [`{ label }: { label: string }`] | The simplest form | Gets **hard to read** with a few fields
- +Named with `interface` [`interface ButtonProps`] | One line per prop, **above the component** | The parameter writes **`: ButtonProps`**
- +Named with `type` [`type ButtonProps = { ... }`] | The same object type with another keyword | **Exact same check** for a props object
```

### The type-checker compares every `<Button>` tag with `ButtonProps`

Here is the button with its named type:

```tsx title="src/components/Button.tsx"
~interface ButtonProps~ { // 1. Describes the one props object React passes to Button
  label: string;
}

export default function Button({ label }~: ButtonProps~) { // 2. The colon says what the props must look like
  return <button>{label}</button>;
}
```

And the page places two buttons:

```tsx title="src/App.tsx"
import Button from './components/Button';

export default function App() {
  return (
    <main>
      <h1>Wireless headphones</h1>
      <p>$200</p>
      ~<Button label="Add to cart" />~ {/* Matches ButtonProps: label is a string */}
      <Button label="Save for later" />
    </main>
  );
}
```

React never reads `ButtonProps`. The type-checker does, in three steps:
1. React will call `Button` with one props object.
2. The colon after `{ label }` tells TypeScript what that object must look like: `ButtonProps`.
3. The type-checker finds every `<Button>` tag in every file, and compares its attributes with `ButtonProps`.

A page can now make two mistakes with `label`, and the editor catches both:

```tsx title="src/App.tsx" bad="1,2"
<Button ~lable~="Add to cart" /> {/* **WRONG:** the editor underlines lable: ButtonProps has no prop with this name */}
~<Button />~ {/* **WRONG:** the editor says label is missing, because ButtonProps requires it */}
```

On the line with `lable`, the editor even suggests the right name, `label`. And what is cool: a developer who did not write the button can move the mouse over `Button` in the page file. The editor shows `ButtonProps`, so they see at once which props the button takes. This is the "inline documentation in editors" that react.dev talks about.

### Surprise: a type error does not stop the page

What if the developer ignores the red line and saves the file? The page still opens, with the empty button from the start of this lesson.

Why? The dev server, Vite in our project, deletes the types and runs the code. It does not run the type-checker. The type-checker runs in two places only:
1. **In the editor**, while the developer types.
2. **In the build command**, in the terminal. In a project made from Vite's React and TypeScript template, the build command runs the type-checker first. While a type error remains, it refuses to build.

So the mistake can still reach the page on the developer's own machine. It cannot reach the users.

```page width=text caption="The page after the developer saves the page file with the type error: the dev server still shows it, with an empty first button and a quiet Console."
heading: Wireless headphones
line: $200
form:
  button: 
  button: Save for later
console: quiet
```

```tree dir=right caption="Where the props type is read: in the editor and in the build command before the page runs, never in the browser."
Where `ButtonProps` is read
- +1. In the editor [`<Button lable="Add to cart" />`] | The type-checker **underlines `lable`** as the developer types | Hover shows **which props `Button` takes**
- +2. In the build command | The type-checker **runs before the build** | A type error **stops the build**
- !3. In the browser | The types **are deleted** before the code runs | **Nothing checks props** while the page runs
```

Remember: the type is read in the editor, never in the browser.

## PRINCIPLE | `variant?` with a union of words: a page may leave the style out, but cannot misspell it

> [!PRINCIPLE]
> **Principle 2: Optional Props: `?`, a Union of Words, and a Default Value**
>
> *Mark a prop that pages may leave out with `?`, list the words it may hold as a union of strings, and give it a default value in the parameter list; React 19 no longer reads `defaultProps` on function components.*
>
> A prop typed as `string` accepts every word, so `secondery` passes, and the user gets a button with no style. A union such as `'primary' | 'secondary'` accepts only the listed words, and the editor underlines every other value, `null` included. The default value in the parameter list covers the pages that leave the prop out. JavaScript uses it only when the prop is missing or `undefined`.
>
> **DO THIS:**
> ```tsx
> interface ButtonProps {
>   label: string;
>   ~variant?: 'primary' | 'secondary'~; // Only two words; pages may leave it out
> }
> function Button({ label, ~variant = 'primary'~ }: ButtonProps) { // Filled when the page writes no variant
>   return <button className={variant}>{label}</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> interface ButtonProps {
>   label: string;
>   ~variant: string~; // **WRONG:** secondery passes, and every page must write variant
> }
> ```

### A prop that pages may leave out

The store wants two looks. Most buttons are filled, such as `Add to cart`. A few have an outline, such as `Save for later`. So the button gets a second prop, `variant`, with two possible words. The word `'primary'` means filled, and `'secondary'` means the outline.

Most pages should not have to write `variant` at all. A button with no `variant` should simply be filled. Two small marks do this:

```tsx title="A prop that pages may leave out, with a default value"
interface ButtonProps {
  label: string;
  ~variant?~: string; // 1. The question mark: a page may leave variant out
}

function Button({ label, ~variant = 'primary'~ }: ButtonProps) { // 2. The default value: used when the page leaves it out
  return <button className={variant}>{label}</button>;
}
```

A prop with a question mark after its name is called **optional**: the type-checker accepts a tag that leaves it out. The default value is the plain JavaScript default you already know (Lesson 09). For `<Button label="Add to cart" />`, React passes an object with no `variant` key. So JavaScript uses `'primary'`, and the page gets a button with the class `primary`.

### VS | `variant?: string` vs. `variant?: 'primary' | 'secondary'`: any string passes, while only the two words pass

Now a new page writes the button with the outline, and the developer makes a small typing mistake:

```tsx title="A page that misspells the style name"
<Button label="Save for later" ~variant="secondery"~ /> {/* The developer meant secondary */}
```

Compare two types for the same optional `variant`. The one difference is what it may hold:

```tsx title="The same optional variant, typed as any string and typed as two words"
~variant?: string;~ // 1. Any string: secondery passes the type-checker
~variant?: 'primary' | 'secondary';~ // 2. Only these two words: secondery is underlined in the editor
```

**It may look the same, and with the right word it works the same, but it is NOT the same thing!** The difference shows only when a page makes a mistake:
- **With `variant?: string`**, the word `secondery` is a string, so the type-checker says nothing. The button gets the class `secondery`. No style in the CSS file has that name, so the user sees a plain button with no outline.
- **With `variant?: 'primary' | 'secondary'`**, the prop may hold only one of the two listed words. The editor underlines `secondery` before the page opens.

> [!DEFINITION]
> **What is a union type?** [NEW] A union type lists the only values allowed, joined by a vertical bar.
> `'primary' | 'secondary'` means: the value is either the word `'primary'` or the word `'secondary'`, and nothing else.
> react.dev uses one in the same way, for a `status` that may be only `"idle"`, `"loading"`, `"success"`, or `"error"` (Lesson 90).

Here is what the Elements panel shows when `variant` accepts any string, and a page writes `secondery`:

```dom caption="What the Elements panel shows when a page writes secondery and variant is typed as string: no style in Button.css matches that class."
<main>
  <h1>Wireless headphones</h1>
  <p>$200</p>
  <button class="primary">Add to cart</button>
! <button class="secondery">Save for later</button> | note: no style matches secondery, so no outline
</main>
```

### VS | `defaultProps` vs. a default value in the parameter list: React 19 ignores the first, while JavaScript runs the second

Older React code gave a default value in another way: a `defaultProps` object written on the component.

```tsx title="A default value with defaultProps"
function Button({ label, variant }: ButtonProps) {
  return <button className={variant}>{label}</button>;
}

~Button.defaultProps~ = { variant: 'primary' }; // **WRONG:** React 19 ignores this on a function component
```

```tsx title="A default value in the parameter list"
function Button({ label, ~variant = 'primary'~ }: ButtonProps) { // The page leaves variant out, so variant is 'primary'
  return <button className={variant}>{label}</button>;
}
```

They look like two ways to say the same thing. **In React 19, they are NOT the same thing!** The React 19 upgrade guide says: "We're also removing `defaultProps` from function components in place of ES6 default parameters." An ES6 default parameter is simply the plain JavaScript default in the parameter list, the one we already use.

So with `defaultProps`, the style prop stays `undefined`. The button `Add to cart` gets no class and no filled look. Something that can be tricky: the type-checker says nothing about it either, because `variant?` allows a page to leave `variant` out. Class components still support `defaultProps`, because a class has no parameter list to put a default in.

### Surprise: the default value is not used for `null`

A default value has one gap: JavaScript does not use it for `null`. A page may write `variant={null}`, for example when the value comes from somewhere that has no style to give:

```tsx title="A page that passes null for variant"
<Button label="Save for later" ~variant={null}~ /> {/* null is not missing: the default value is not used */}
```

The button shows with no style at all, neither filled nor with an outline. Here is why, step by step:
1. React passes an object where the key `variant` is there, and it holds `null`.
2. JavaScript uses a default value only when the prop is missing or `undefined`, as react.dev says. `null` is neither, so `variant` keeps it.
3. `className={null}` gives the button no class, so no style matches it.

```dom caption="What the Elements panel shows when a page passes null for variant: the button has no class at all."
<main>
  <h1>Wireless headphones</h1>
  <p>$200</p>
  <button class="primary">Add to cart</button>
! <button>Save for later</button> | note: variant is null, so no class
</main>
```

The union type catches this case too. `null` is not one of the two listed words, so the editor underlines `variant={null}` before the page opens. This holds with the strict setting of TypeScript, which is on in a project made from Vite's React and TypeScript template.

```tree caption="What variant holds inside Button for each way a page can write the tag."
What `variant` holds inside `Button`
- +No `variant` on the tag [`<Button label="Add to cart" />`] | The key is **missing** | The default value gives **`'primary'`**: a filled button
- +A listed word [`variant="secondary"`] | The page's word is used | **`'secondary'`**: a button with an outline
- !A misspelled word [`variant="secondery"`] | Passes with `string`; **underlined** with the union | A button with **no style**
- !`null` [`variant={null}`] | `null` is **not missing**, so no default | A button with **no class**; **underlined** with the union
```

Remember: the question mark lets a page leave the prop out, and the union stops a page from misspelling it.

## PRINCIPLE | `children: React.ReactNode`: the button accepts plain text, tags, or both

> [!PRINCIPLE]
> **Principle 3: Children: `React.ReactNode` Accepts Everything Between the Tags**
>
> *When a component shows whatever the page places between its tags, type `children` as `React.ReactNode`, which accepts text, numbers, tags, and nothing at all; `React.ReactElement` accepts only JSX tags.*
>
> `children` is whatever the page writes between the opening and closing tags, and plain text is the most common case. `React.ReactElement` sounds right for JSX, but it refuses `Save for later`, and it refuses text next to a tag. `React.ReactNode` accepts both, so one shared button can hold plain words on one page and a bold price on another.
>
> **DO THIS:**
> ```tsx
> interface ButtonProps {
>   variant?: 'primary' | 'secondary';
>   ~children: React.ReactNode~; // Accepts Save for later and Add to cart with a bold price
> }
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> interface ButtonProps {
>   variant?: 'primary' | 'secondary';
>   ~children: React.ReactElement~; // **WRONG:** refuses the plain text Save for later
> }
> ```

### The price in bold inside the button

The store asks for one more change: `Add to cart` should show the price, in bold. A `label` that is a string cannot hold a bold tag. So the button switches to `children`.

> [!DEFINITION]
> **What is children?** [REVIEW] `children` is a prop. React fills it with whatever you write between a component's opening and closing tags.
> In `<Button>Save for later</Button>`, `Button` receives the text `Save for later` as `children` (Lesson 09).

The page now needs these two tags:

```tsx title="The two buttons the page needs, with their content between the tags"
<Button>~Add to cart <b>$200</b>~</Button> {/* Text and a bold tag together */}
<Button variant="secondary">~Save for later~</Button> {/* Plain text only */}
```

### VS | `children: React.ReactElement` vs. `children: React.ReactNode`: one accepts only a tag, while the other accepts everything

So `ButtonProps` needs a line for `children`. Here are three types a developer might write for it:

```tsx title="Three types for children, and what each one accepts"
children: ~string~; // 1. Accepts Save for later; refuses Add to cart with the bold tag
children: ~React.ReactElement~; // 2. Accepts one tag alone; refuses the text Save for later
children: ~React.ReactNode~; // 3. Accepts both buttons, and anything else a page places between the tags
```

The second line is the trap. `React.ReactElement` sounds like the right type for content written in JSX. **It may look the same, but it is NOT the same thing!**
1. **With `children: string`**, `Save for later` passes. `Add to cart` with the bold price is underlined, because it is two pieces, text and a tag, and the type allows only one string.
2. **With `children: React.ReactElement`**, only one JSX tag passes, such as `<b>$200</b>` alone. The text `Save for later` is underlined, because a string is not a tag. react.dev says it covers "only JSX elements and not JavaScript primitives like strings or numbers".
3. **With `children: React.ReactNode`**, both buttons pass. react.dev calls it "a union of all the possible types that can be passed as children in JSX".

> [!DEFINITION]
> **What is an element?** [REVIEW] An element is the plain object a JSX tag becomes. `<b>$200</b>` becomes an object that React reads to draw a bold tag. A string such as `Save for later` is not an element (Lesson 76).

> [!DEFINITION]
> **What is React.ReactNode?** [NEW] `React.ReactNode` is the type of everything a page may write between a component's tags: elements, strings, numbers, `true` and `false`, `null`, `undefined`, and lists of these.
> `React.ReactElement` is only one piece of that list: the elements. That is why it refuses plain text (Lesson 90).

Plain text is the most common thing a page places inside a button. A type that refuses plain text cannot be the type of `children`.

```tree caption="Three types for children: only React.ReactNode accepts both the text and the text with a bold tag."
Which type fits `children` in `ButtonProps`
- !`children: string` [`Save for later`] | Accepts **plain text** only | **Refuses** `Add to cart` with the **bold price**
- !`children: React.ReactElement` [`<b>$200</b>`] | Accepts **one JSX tag** only | **Refuses** the plain text **`Save for later`**
- +`children: React.ReactNode` [`Save for later` `Add to cart <b>$200</b>`] | Accepts **everything** a page may place between the tags | **Both buttons pass**
```

### The button with `children`

Now `children` takes the place of `label` in the type:

```tsx title="src/components/Button.tsx"
import './Button.css';

interface ButtonProps {
  variant?: 'primary' | 'secondary';
  ~children: React.ReactNode~; // Text, tags, or both: whatever the page places between the tags
}

export default function Button({ variant = 'primary', children }: ButtonProps) {
  return <button className={variant}>{~children~}</button>; // Places the page's content inside the button
}
```

Where does the name `React` come from? From the types package of React, which the project installed at the start. It makes React's types available under the name `React`, so we write `React.ReactNode`, as react.dev's own examples do.

The page writes the content of each button between its tags:

```tsx title="src/App.tsx" startLine="8"
      ~<Button>Add to cart <b>$200</b></Button>~ {/* Passes: React.ReactNode accepts text and a tag */}
      <Button variant="secondary">Save for later</Button>
```

```page width=text caption="The product page with children: Add to cart now shows the price, which is in bold on the real page."
heading: Wireless headphones
line: $200
form:
  button: Add to cart $200
  button: Save for later
console: quiet
```

In the Elements panel, the bold tag sits inside the real `<button>`:

```dom caption="What the Elements panel shows for the two buttons: the content from between the tags sits inside each button."
<main>
  <h1>Wireless headphones</h1>
  <p>$200</p>
+ <button class="primary">Add to cart <b>$200</b></button> | note: children: text and a bold tag
+ <button class="secondary">Save for later</button> | note: children: plain text
</main>
```

This one line saves the store a lot of work. Without `children`, every new request adds a prop to the button: first a price, then an icon, then the next one. With `children: React.ReactNode`, `Button` stays the same, and each page places what it needs between the tags.

### What no type can say

Sometimes a component wants only one kind of tag between its tags, such as a list that wants only `<li>` items. TypeScript cannot say that. react.dev says it directly: "you cannot use TypeScript to describe that the children are a certain type of JSX elements". `React.ReactElement` means any tag at all, and no type narrows it to one tag name.

Remember: `children` is typed as `React.ReactNode`, because plain text must pass.

## PRINCIPLE | `extends React.ComponentPropsWithRef<'button'>`: the button accepts every attribute of a real `<button>`

> [!PRINCIPLE]
> **Principle 4: Wrapping a Tag: Extend the Props of `<button>` and Pass the Rest**
>
> *When a shared component wraps one built-in tag, extend the type of all that tag's props, `React.ComponentPropsWithRef<'button'>`, add only the component's own props, and pass the rest to the tag with spread.*
>
> A hand-written list accepts only what it names. The shared button refuses `disabled`, then `type`, then `onClick`, and it silently drops `aria-label`. So developers write plain buttons by hand next to it. Extending the props of `<button>` makes the shared button accept everything a real `<button>` accepts. The rest property collects every prop the component does not use, and `{...rest}` hands it to the tag, `children` and `ref` included.
>
> **DO THIS:**
> ```tsx
> interface ButtonProps ~extends React.ComponentPropsWithRef<'button'>~ { // Every attribute of <button>
>   variant?: 'primary' | 'secondary';
> }
> function Button({ variant = 'primary', ...rest }: ButtonProps) {
>   return <button className={variant} ~{...rest}~ />; // disabled, aria-label, and children reach the tag
> }
> ```
>
> **DO NOT DO THIS:**
> ```tsx
> interface ButtonProps {
>   variant?: 'primary' | 'secondary';
>   children: React.ReactNode;
>   ~disabled?: boolean~; // **WRONG:** the next page needs type="submit", and the type-checker refuses it
> }
> ```

### The headphones are sold out

The `Add to cart` button must be turned off. On a plain HTML `<button>`, you know how: the attribute `disabled`. So the page writes it on our button:

```tsx title="src/App.tsx" startLine="8"
      <Button ~disabled~>Add to cart <b>$200</b></Button> {/* **WRONG:** the editor underlines disabled: ButtonProps does not list it */}
```

The editor underlines `disabled`. Why? `Button` is our component, not the real `<button>`. The type-checker compares the tag with `ButtonProps`, and that type lists only two props: the style and the children.

And if the developer ignores the red line, the button stays clickable anyway. Our component never passes `disabled` on to the real `<button>`, so the browser never sees it.

### VS | Listing `disabled` by hand vs. extending the props of `<button>`: both turn the button off, while only the second accepts the next attribute

The first fix adds `disabled` to `ButtonProps`, and passes it on by hand. react.dev's own button example lists `disabled` the same way:

```tsx title="Listing disabled by hand"
interface ButtonProps {
  variant?: 'primary' | 'secondary';
  children: React.ReactNode;
  ~disabled?: boolean~; // 1. One line in the type for this one attribute
}

function Button({ variant = 'primary', children, disabled }: ButtonProps) {
  return <button className={variant} ~disabled={disabled}~>{children}</button>; // 2. One pass to the real tag
}
```

The second fix takes the type of every prop a `<button>` accepts, and adds only our own:

```tsx title="Taking every attribute of button"
interface ButtonProps ~extends React.ComponentPropsWithRef<'button'>~ { // 1. Every prop a <button> tag accepts
  variant?: 'primary' | 'secondary'; // 2. Plus our own prop
}

function Button({ variant = 'primary', ~...rest~ }: ButtonProps) { // 3. Every other prop lands in rest
  return <button className={variant} ~{...rest}~ />; // 4. All of them reach the real tag
}
```

Both fixes turn off the sold-out button. **It works the same at first, but it is NOT the same thing!**
- **With `disabled` listed by hand**, the button accepts `disabled` and nothing else. A form needs `type="submit"`, and the editor underlines it. A page needs `onClick` and a `ref`, and the editor underlines them too. Each one needs a new line in the type and a new pass to the real tag.
- **With `extends React.ComponentPropsWithRef<'button'>`**, the button already accepts every attribute of `<button>`. That means `disabled` and `aria-label`, but also the type, the click handler, the ref, and the rest. Nothing grows when a new page arrives.

Something that can be tricky: an attribute with a dash in its name is even worse with the hand-written list. An accessibility review asks for `aria-label` on a button that shows only an icon. The type-checker does not check names with a dash, so `aria-label` passes with no red line. And `Button` never passes it on, so it silently disappears.

**A component that wraps one built-in tag should accept everything that tag accepts, and add only its own props.**

```tree caption="Two ways to let the shared button take disabled: one line per attribute, or every attribute of button at once."
Two ways to let `Button` take `disabled`
- !List each attribute by hand [`disabled?: boolean`] | Accepts **`disabled`** and nothing more | Every new request needs **a new line and a new pass**
- +Extend the props of `<button>` [`extends React.ComponentPropsWithRef<'button'>`] | Accepts **every attribute** of `<button>` | `aria-label`, `type`, `onClick`, and `ref` **already pass**
```

### The three new pieces of the extended type

The second fix brings three new pieces. Two come from TypeScript, and one is plain JavaScript:

> [!DEFINITION]
> **What do extends and React.ComponentPropsWithRef mean?** [NEW] `interface ButtonProps extends ...` means: `ButtonProps` takes every line of the named type, then adds its own lines.
> `React.ComponentPropsWithRef<'button'>` is the type of every prop a `<button>` tag accepts, `ref` included. It comes from `@types/react`, and react.dev itself does not print this name.
> The word in angle brackets, `'button'`, is a type argument: it tells the type which tag to describe. Write `'input'` there, and you get the props of an `<input>` tag (Lesson 90).

> [!DEFINITION]
> **What is the rest property?** [NEW] It is plain JavaScript, not TypeScript. When you unpack an object, `...rest` collects every key you did not name into a new object called `rest`.
> `const { variant, ...rest } = { variant: 'secondary', disabled: true }` gives `variant` the word `'secondary'`, and gives `rest` the object `{ disabled: true }`.
> MDN says the rest property must be the last item in the pattern (Lesson 90).

Here is where `rest` comes from for the sold-out button, step by step:
1. React passes one props object. It has no `variant`, and it holds `disabled` and the children.
2. JavaScript unpacks `variant` by name. It is missing, so the default value gives `'primary'`.
3. The rest property collects every other key into `rest`: here, `disabled` and the children.
4. `{...rest}` on the real `<button>` writes each key of that object as a prop of the tag (Lesson 09).

### Surprise: `children` and `ref` come along

Look again at the extended type. It has no line for `children`, and the component never places them by name. Yet the page still writes the bold price between the tags, the type-checker accepts it, and the price still shows inside the button. Two facts explain it:
1. **The props of a `<button>` tag already include `children`.** Their type is `React.ReactNode`, and the extended type brings that line with it.
2. **`Button` does not unpack `children` by name.** So the children land in `rest`, together with `disabled`. `{...rest}` passes them to the real tag, and React places it between the tags of the real button.

`ref` travels the same way. In React 19, `ref` is an ordinary prop (Lesson 85). So a page can write `ref` on our button, and the type accepts it. Then `{...rest}` hands it to the real tag, with no `forwardRef`.

Here is the button after this step:

```tsx title="src/components/Button.tsx"
import './Button.css';

interface ButtonProps ~extends React.ComponentPropsWithRef<'button'>~ { // Every prop of <button>, children and ref included
  variant?: 'primary' | 'secondary';
}

export default function Button({ variant = 'primary', ~...rest~ }: ButtonProps) { // disabled and children land in rest
  return <button className={variant} {...rest} />;
}
```

The sold-out tag now passes the type-checker:

```tsx title="src/App.tsx" startLine="8"
      <Button ~disabled~>Add to cart <b>$200</b></Button> {/* Passes: disabled is a prop of <button> */}
      <Button variant="secondary">Save for later</Button>
```

One more detail lives in the CSS file: it dims a turned-off button. Without that rule, the filled look of the `primary` class covers the grey that the browser gives a turned-off button. The sold-out button would look exactly like a working one.

```page width=text caption="The product page while the headphones are sold out: Add to cart is dimmed, and clicking it does nothing."
heading: Wireless headphones
line: $200
form:
  button: Add to cart $200 | | disabled
  button: Save for later
console: quiet
```

```dom caption="What the Elements panel shows for the sold-out button: disabled reached the real button through rest."
<main>
  <h1>Wireless headphones</h1>
  <p>$200</p>
+ <button class="primary" disabled>Add to cart <b>$200</b></button> | note: disabled and children came through rest
  <button class="secondary">Save for later</button>
</main>
```

Remember: a button that wraps `<button>` accepts everything `<button>` accepts.

## All 4 Principles Together

### The complete code

`Button.tsx` holds the shared button and the type of its props:

```tsx title="src/components/Button.tsx"
import './Button.css';

interface ButtonProps ~extends React.ComponentPropsWithRef<'button'>~ { // 4. Every prop of <button>, children and ref included
  ~variant?: 'primary' | 'secondary'~; // 2. Optional, and only two words
}

export default function Button({ ~variant = 'primary'~, ...rest }: ButtonProps) { // 1. Typed props; 2. the default value
  return <button className={variant} {...rest} />; // 3. children reach the tag through rest
}
```

`Button.css` gives each word of `variant` its look, and dims a turned-off button:

```css title="src/components/Button.css"
.primary {
  background: black;
  color: white;
}

.secondary {
  background: white;
  border: 1px solid black;
}

button:disabled {
  opacity: 0.5;
}
```

`App.tsx` places the two buttons of the product page:

```tsx title="src/App.tsx"
import Button from './components/Button';

export default function App() {
  return (
    <main>
      <h1>Wireless headphones</h1>
      <p>$200</p>
      <Button ~disabled~>Add to cart <b>$200</b></Button> {/* No variant: filled; disabled: sold out */}
      <Button ~variant="secondary"~>Save for later</Button> {/* An outline */}
    </main>
  );
}
```

```page width=text caption="The finished product page: Add to cart is turned off while the headphones are sold out, and Save for later has an outline."
heading: Wireless headphones
line: $200
form:
  button: Add to cart $200 | | disabled
  button: Save for later
console: quiet
```

### The order in which React calls the components

When the page loads, React calls `App` first. `App` returns two button tags, so React calls `Button` twice, from top to bottom. The type-checker did its work earlier, in the editor, and it plays no part here:

```tree caption="The order in which React calls the components of the product page; the types were checked before this, in the editor."
`App` [1. Called first] | Returns `<main>` with **two `<Button>` tags**
- +`Button` for `Add to cart` [2. Called second] | `variant` is missing, so it is **`'primary'`** | Returns a **filled button** that is **turned off**
- +`Button` for `Save for later` [3. Called third] | `variant` is **`'secondary'`** | Returns a **button with an outline**
```

| The request | Without a good type | With the type from this lesson |
| :--- | :--- | :--- |
| **A misspelled prop, such as `lable`** | The user sees an empty button, and the Console stays quiet | The editor underlines `lable` before the page opens |
| **A style that pages may leave out** | `variant: string` lets `secondery` through, and the button has no style | `variant?: 'primary' \| 'secondary'` with `variant = 'primary'` in the parameter list |
| **Text and a bold price inside the button** | `string` or `React.ReactElement` refuses one of the two buttons | `React.ReactNode` accepts both |
| **`disabled` when the item is sold out** | A hand-written list refuses each new attribute | `extends React.ComponentPropsWithRef<'button'>` with `{...rest}` on the tag |
| **Where props are checked** | Nowhere: React 19 ignores `propTypes` | In the editor and in the build command, never in the browser |

Remember the one sentence of this lesson. **A component receives one props object: describe it once with a type, and the editor checks every tag against it, before the page runs.**

## For the Interview

> **The Interview Question:** How do you type React components, props, optional attributes, and children in TypeScript?

### How to Answer Clearly in 30 Seconds

"A component receives one props object, so I type that object after the destructured parameter, usually with a named `interface` or `type`, in a `.tsx` file. The type-checker then compares every tag with that type in the editor, before the code runs. Nothing checks props in the browser, and React 19 ignores `propTypes`. Three more rules:
1. **Optional props**: I mark them with `?`, use a union such as `'primary' | 'secondary'` when only a few words are allowed, and give the default value in the parameter list, because React 19 removed `defaultProps` for function components.
2. **Children**: I type `children` as `React.ReactNode`, which accepts text, numbers, and tags. `React.ReactElement` accepts only JSX tags, so it refuses plain text.
3. **Attributes of a built-in tag**: when the component wraps a `<button>`, I extend `React.ComponentPropsWithRef<'button'>`, add only my own props, and pass the rest to the `<button>` with spread. `children` and `ref` come with it."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"If you type your props, does React check them in the browser?"**
   No. The types are deleted before the code runs, so the browser runs the same JavaScript as without them. The type-checker reads them in the editor, and the build command usually runs it before every build. Older React checked props in the browser with `propTypes`, but React 19 removed those checks, and using `propTypes` now "will be silently ignored". A misspelled prop that slips past the type-checker gives the user an empty button and a quiet Console.
2. **"Should you write `const Button: React.FC<ButtonProps>`?"**
   It is an older habit, and it adds nothing in React 19's types. In the current `@types/react`, `React.FC` describes a function that takes the props and returns something React can render. A parameter typed as `ButtonProps` already says that. react.dev's own examples never use `React.FC`. They type the parameter directly, as in `function Button({ variant = 'primary', ...rest }: ButtonProps)`, which also lets the default value sit right in the parameter list.
3. **"A page passes its own `className` to your shared button. What happens?"**
   It depends on the order on the tag (Lesson 09). With `<button className={variant} {...rest} />`, `rest` comes last, so the page's `className` replaces the style of the button. With `<button {...rest} className={variant} />`, `className={variant}` comes last, so the button always keeps its own style, and the page's `className` is lost. A shared button picks one of the two on purpose. react.dev also says to "use spread syntax with restraint", and a wrapper of one built-in tag is the case where spread fits.

```tree dir=right caption="Interview summary: the four parts of a component that TypeScript describes, and the type for each."
What to type on a shared component
- +The props object [`interface ButtonProps`] | Written after the **destructured parameter** | Checked in the **editor**, never in the browser
- +Optional props [`variant?`] | `?` plus a **union of words** | The default value goes in the **parameter list**
- +Children [`children: React.ReactNode`] | Accepts **text, numbers, and tags** | `React.ReactElement` **refuses plain text**
- +Attributes of the wrapped tag [`extends React.ComponentPropsWithRef<'button'>`] | Every prop of `<button>` | `{...rest}` passes them on, **`children` and `ref` included**
```
