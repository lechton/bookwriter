# Lecture 108: What Each Side Can Do: the Server Component and the Client Component

*(Why can one component read the database but not count a click, while another counts the click but cannot read the database?)*

> INTERVIEW QUESTION | ❱ CORE | What can a Server Component do that a Client Component cannot, and vice versa?

---

## VS | A Server Component vs. a Client Component: one reads the database on the server, the other answers the user in the browser

> Every React component is a function that returns JSX, but that function can run in one of two places: on the server, or in the user's browser. **A Server Component runs on the server and is never sent to the browser, while a Client Component is sent to the browser and stays there**. So each one can do only what its place allows: on the server, read the database and keep passwords; in the browser, hold state and answer clicks.

Before React, every web developer already knew two kinds of code. The first kind runs on the server. A Node.js route reads the database, builds the HTML, and sends it. The browser receives the finished HTML, never the code that built it. The second kind runs in the browser. A script with `addEventListener` is downloaded with the page, and it stays there, waiting for the user's clicks.

```js title="Plain JavaScript: one line that runs on the server, one line that runs in the browser"
const product = ~await db.products.get(1)~; // On the server: the database is here, the user is not
button.~addEventListener~('click', addToCart); // In the browser: the user is here, the database is not
```

Each place has a benefit and a problem:
- **The server** has the database and the passwords. But it never sees a click, and once it has sent the HTML, its job is over.
- **The browser** sees every click, and the script stays alive while the page is open. But it has no database, and it must never hold a password.

React components come in the same two kinds. **A Server Component is the first kind of code: it runs on the server and is never sent to the browser. A Client Component is the second kind: it is sent to the browser and stays there while the page is open.**

So here is the one sentence to keep in mind for this whole lesson:

**A component can do only what the place it runs in has. The server has the data and the secrets. The browser has the user.**

> [!DEFINITION]
> **Server Component and Client Component.** [REVIEW] A Server Component runs on the server, before the page is sent, so it can read a database or a file directly, and the browser receives only what it rendered, never its code. A Client Component is a component whose code is sent to the browser and runs there; its file starts with `'use client'`, and every file it imports becomes client code too (Lesson 101).

### It Looks the Same, but It Runs Somewhere Else

A Server Component and a Client Component have a lot in common. Both are React components. Both are functions that receive props and return JSX. Both can put `Blue Sneakers` on the screen, and the two functions can even be written with the very same lines.

**It may look the same, but it is NOT the same thing!** The one difference is where the function runs, and whether it stays there:
- **A Server Component** runs on the server, once at build time or once for each request. It is never sent to the browser. React's docs put it in one phrase: Server Components "do not persist in memory after render".
- **A Client Component** is sent to the browser with the page's JavaScript. It stays there in memory while the page is open, so React can run it again after every click.

To **persist in memory** means to stay alive between renders, ready to run again. A Server Component renders once and is gone. A Client Component stays.

```tree caption="A Server Component and a Client Component: both are React components, and they differ in where they run and whether they stay."
Two kinds of React component
- +Server Component | Runs **on the server**, at build time or for each request | Is **not sent** to the browser and **does not stay** in memory after it renders
- +Client Component | Is **sent to the browser** with the page's JavaScript | **Stays in memory** while the page is open and runs again on every update
```

### The Two Lists

Every ability on both sides follows from that one difference.

**What only a Server Component can do:**
1. Be an `async` function, and `await` its data while it renders.
2. Read the database or the file system directly, with no API built for it.
3. Use secrets such as the database password, which stay on the server.
4. Cost the browser nothing to download, because its code is not in the bundle.

**What only a Client Component can do:**
1. Hold state with `useState` or `useReducer`.
2. Answer the user with event handlers such as `onClick`.
3. Run Effects with `useEffect` or `useLayoutEffect`.
4. Use browser APIs such as `window.localStorage`.

A Server Component is not a weaker Client Component. Each kind can do things the other cannot.

### The Rule of Thumb: does this line need the server or the user?

**Before you write a line in a component, ask one question: does it need the server, or does it need the user?** The database and a password need the server. A click, a changing number, and `window` need the user.

So a page that needs both does a simple split. The page itself is a Server Component that reads the data. It hands what the button needs to a small Client Component.

What the user gets depends on where each line sits:
1. **`useState` or `onClick` in a Server Component:** the page does not render at all.
2. **`window.localStorage` in a Server Component:** the page does not render either, because the server has no `window`.
3. **`'use client'` on the whole page file:** the page loses its database read, and the database code is pulled into the code the browser downloads.
4. **The whole page written as a Client Component that fetches in an Effect:** the page works, but the title waits for a second request. React's docs say users "wait for a second request to fetch the data after the page loads."

A senior developer also knows the five classic mistakes:
1. **Putting `useState` and `onClick` in the page file**, because every component up to now could do both (as seen in Lesson 12).
2. **Reading `window.localStorage` in the page file**, because the page "loads in the browser".
3. **Adding `'use client'` to the page file** to fix the first mistake, and losing the database read.
4. **Thinking a Server Component is a weaker Client Component.** Each kind has its own list.
5. **Thinking every Hook is forbidden on the server.** React's docs say "most Hooks", not all of them.

Developers choose between three ways to build a page that needs both data and a click:
1. **The whole page as a Client Component**, which fetches its data in an Effect from an API the developer builds (as seen in Lesson 33). This fits an app with no server that runs React, such as a Vite app (as seen in Lesson 07).
2. **The page as a Server Component that reads the data, with a small Client Component for the button.** This fits a framework that runs Server Components (as seen in Lesson 46). This lesson builds this way.
3. **A component that uses nothing from either list**, such as a plain title, in a file with no directive. It runs on the server or in the browser, depending on who imports it (Lesson 127).

The rest of the lesson shows each mistake on a real product page.

**PRINCIPLES:** A Server Component and a Client Component are both React components, but one runs on the server and the other is sent to the browser and stays there. Five principles follow:
1. **`async ProductPage`: the title is in the first page, with no API.** A Server Component can await the database while it renders. A Client Component cannot.
2. **A Server Component sends its output, never its code.** Only Client modules go into the bundle. The page code, the database file, and the password stay on the server.
3. **`useState` and `onClick` work only in a Client Component.** State and event handlers need a component that stays in the browser, so the button moves into its own file.
4. **`window.localStorage` goes inside `useEffect`.** Browser APIs exist only in the browser, and an Effect or an event handler is sure to run there.
5. **`'use client'` goes on the smallest file.** On the page file, it breaks the database read. On the button file, it sends only the button.

## PRINCIPLE | `async ProductPage`: the title arrives in the first page, with no API and no second request

> [!PRINCIPLE]
> **Principle 1: Async Server Components: `ProductPage` Awaits the Database While It Renders**
>
> *A Server Component may be an `async` function that awaits the database, a file, or another server resource while it renders, with no API in between; a Client Component cannot.*
>
> A Server Component runs on the server, where the database is. So it can stop in the middle of rendering, wait for the data, and put the title in the first page the user gets. A Client Component runs in the browser, where the database is not, and React does not support async components there. It must render first and fetch from an API in an Effect.
>
> **DO THIS:**
> ```jsx
> export default ~async~ function ProductPage() { // A Server Component: waits for the database while it renders
>   const product = await db.products.get(1);
>   return <h1>{product.title}</h1>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> 'use client';
> export default function ProductPage() {
>   const [product, setProduct] = useState(null);
>   useEffect(() => {
>     ~fetch('/api/products/1')~.then(r => r.json()).then(setProduct); // **WRONG:** an API and a second request for data the page could read itself
>   }, []);
>   return <h1>{product === null ? 'Loading...' : product.title}</h1>;
> }
> ```

On a Node.js server, you read a product with one line: `await db.products.get(1)`. A Server Component lets you write that exact line inside the component:

```jsx title="src/ProductPage.jsx" startLine="1"
import db from './db';

export default ~async~ function ProductPage() { // async: this component may wait while it renders
  const product = ~await~ db.products.get(1); // Waits for the database, then goes on with product
  return <h1>{product.title}</h1>;
}
```

Put it next to any component you have written so far (as seen in Lesson 02). **Yes, it is the exact same thing!** It is a function that returns JSX. The only new word is `async`, and the `await` it allows (as seen in Lesson 41).

> [!DEFINITION]
> **Async component.** [NEW] An async component is a component written as an `async` function, so it can `await` data in the middle of rendering and return its JSX only when the data is there. React's docs: "Async Components are a new feature of Server Components that allow you to `await` in render." Only a Server Component can be async; in the browser, React does not support it (Lesson 108).

The component waits for the database, then returns the title. So there is no `useState`, no loading line, and no moment when the title is empty on the screen:

```page caption="The product page rendered by ProductPage: the title is there from the first moment."
url: shop.example.com
heading: Blue Sneakers
```

### Where `db` and `product` Come From

`db` comes from the database stand-in:

```js title="src/db.js" startLine="1"
const password = ~process.env.DB_PASSWORD~; // Read on the server when the file runs; the password is never written in the code

const db = {
  products: {
    async ~get~(id) { // Plays the database: gives back one product
      return { id, title: 'Blue Sneakers' };
    },
  },
};

export default db;
```

`process.env.DB_PASSWORD` is an **environment variable**: a value the server receives from its own settings, outside the code. The password lives on the server, and the code only names it. A real database client would use it to connect. Our stand-in reads it and does nothing else with it.

`product` is the plain object that the stand-in gives back:

```js title="What product holds after the await"
const product = ~await db.products.get(1)~; // product is { id: 1, title: 'Blue Sneakers' }
```

A Server Component can read a file on the server's disk in the same way, with `readFile` (as seen in Lesson 101). For this rule, the database and the file system are the exact same thing. Both sit on the server, and the component reads them directly.

### VS | `await` in `ProductPage` vs. `fetch` in an Effect: the same title, one request later

A Client Component cannot read the database. It gets the title the way a Vite app does (as seen in Lesson 33). It renders first, then fetches in an Effect from an API route the developer builds:

```jsx title="src/ProductPage.jsx, written as a Client Component that fetches in an Effect" startLine="1"
'use client';

import { useState, useEffect } from 'react';

export default function ProductPage() {
  const [product, setProduct] = useState(null);

  useEffect(() => {
    ~fetch('/api/products/1')~ // A second request, to an API route the developer built
      .then(response => response.json())
      .then(data => setProduct(data));
  }, []);

  if (product === null) {
    return <h1>Loading...</h1>;
  }
  return <h1>{product.title}</h1>;
}
```

Both versions end with `Blue Sneakers` on the screen. **It may look the same to the user, but it is NOT the same thing!** What differs is when the title arrives:
- **With `await` in `ProductPage`**, the title is in the first page the user gets. React's docs mark this version "loads *during* render".
- **With `fetch` in an Effect**, the page first renders without the title. Then the browser sends a second request to the API route, the route reads the database, and only then does the title show. React's docs mark this version "loads *after* first render".

::: row caption="The first thing the user sees: with await in ProductPage, and with fetch in an Effect."

```page size=mini

```

:::

The title waits for a second request.

Why can a Client Component not simply write `await` too? Because React does not support async components in the browser. React's docs: "async components are not supported on the client." In the browser, a Client Component reads a Promise with `use` instead (as seen in Lesson 71).

Remember: the server has the data, so a component that runs there can simply wait for it.

## PRINCIPLE | A Server Component: the browser gets the rendered `<h1>`, never the code or the password

> [!PRINCIPLE]
> **Principle 2: Zero Bundle Cost: The Browser Gets `Blue Sneakers`, Never the Code of `ProductPage`**
>
> *Only Client modules are bundled and sent to the browser; a Server Component, the files it imports, and the secrets it reads stay on the server, and the browser receives only what it rendered.*
>
> When the page is a Server Component, the user's browser downloads no code for it. It gets the `<h1>` with `Blue Sneakers`, and nothing of `ProductPage.jsx`, `db.js`, or the password. This holds as long as no `'use client'` file imports `db.js` and no prop carries the secret to a Client Component.
>
> **DO THIS:**
> ```jsx
> import db from './db'; // Imported only by a Server Component: db.js stays on the server
>
> export default async function ProductPage() {
>   const product = await db.products.get(1);
>   return <h1>~{product.title}~</h1>; // The browser receives only the rendered <h1>
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default async function ProductPage() {
>   const product = await db.products.get(1);
>   return <CartButton ~password={process.env.DB_PASSWORD}~ />; // **WRONG:** CartButton is a Client Component, so this prop travels to the browser with the secret in it
> }
> ```

Remember "View page source" on a site built with Node.js? You see the HTML the server sent. You never see the server's code, its database queries, or its passwords. That code ran on the server, and only its result traveled.

A Server Component works the same way. React runs it on the server, and sends only what it returned:

```html title="What the browser receives for ProductPage"
<h1>Blue Sneakers</h1>
```

Nothing of the page file or the database file reaches the browser. Only files marked with `'use client'`, and the files they import, go into the bundle that the browser downloads (as seen in Lesson 106).

> [!DEFINITION]
> **Client modules, rendered output, and zero bundle cost.** [NEW] Client modules are the files marked with `'use client'` and the files they import; React's docs: "Only Client modules are bundled and evaluated by the client." The rendered output is what a Server Component returned, such as `<h1>Blue Sneakers</h1>`; React's docs: "only the rendered output is sent to the client." Developers call the result zero bundle cost: a Server Component adds nothing to the bundle, because its code never leaves the server (Lesson 108).

On the first load, this output arrives as HTML (as seen in Lesson 102). The form React uses to send it after that comes later (Lesson 124).

### VS | `fetch` in an Effect vs. a Server Component: the same title, two different downloads

Principle 1 showed two versions of the page that end on the same screen. **It may look the same, but it is NOT the same thing!** Here is what each one sends to the browser:

| What the browser gets | `ProductPage` with `fetch` in an Effect | `ProductPage` as a Server Component |
| :--- | :--- | :--- |
| **The code of `ProductPage.jsx`** | Downloaded and run in the browser | Stays on the server |
| **The code of `db.js` and its password** | Stays on the server, behind an API route the developer had to build | Stays on the server, with no API route |
| **The title** | Arrives after a second request | Arrives in the first page as `<h1>Blue Sneakers</h1>` |

### What Stays on the Server

Three things never reach the user's browser when the page is a Server Component:
1. **The code of `ProductPage.jsx`.** The browser gets the `<h1>`, not the function that made it.
2. **The code of `db.js`.** Only `ProductPage` imports it, and `ProductPage` runs on the server.
3. **The password.** The database file reads it on the server.

A password is a **secret**: a value that must never reach the browser. React's docs warn about "private keys or passwords such as database passwords".

The same holds for a large library. When only a Server Component imports it, it adds nothing to the download. React's docs: "the bundle does not include the expensive libraries needed to render the static content."

**Beware: the password stays safe only on two conditions.**
1. No file marked `'use client'` imports the database file. If one does, the database file becomes client code too, as Principle 5 shows.
2. The Server Component does not pass the password to a Client Component as a prop. Every prop a Server Component gives a Client Component travels to the browser (as seen in Lesson 107).

### The Browser Cannot Run `ProductPage` Again

This has a cost. The browser never received `ProductPage`, so it cannot run it again. When the page must show new data from the server, the browser asks the server to render `ProductPage` again. React's docs: "Server Components can be made dynamic by re-fetching them from a server, where they can access the data and render again."

Remember: a Server Component sends its output, not its code. That is why it costs the browser nothing, and why it can keep a secret.

## PRINCIPLE | `useState` and `onClick`: they work only in a `'use client'` file such as `CartButton`

> [!PRINCIPLE]
> **Principle 3: State and Events: `onClick` and `useState` Move Add to cart into `CartButton`**
>
> *State and event handlers need a component that stays in the browser, so `useState`, `useReducer`, and `onClick` belong in a Client Component, which the Server Component renders as a child.*
>
> A Server Component runs once on the server and is not sent to the browser. It has nowhere to keep `count` and nothing in the browser to answer a tap, so the product page does not render. Put the button and its state in a file that starts with `'use client'`, and render that file from the page.
>
> **DO THIS:**
> ```jsx
> 'use client';
> export default function CartButton() {
>   const [count, setCount] = ~useState(0)~; // A Client Component keeps count in the browser
>   return <button onClick={() => setCount(count + 1)}>Cart: {count}</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default async function ProductPage() {
>   const [count, setCount] = ~useState(0)~; // **WRONG:** a Server Component cannot hold state, and the page does not render
>   return <button onClick={() => setCount(count + 1)}>Cart: {count}</button>;
> }
> ```

Think of a plain HTML page that a server sent. Once the HTML has left the server, the server code is finished. If the user clicks a button, the server code is not there to hear it. Only a script that the browser downloaded can answer that click.

A Server Component is exactly that server code. Now the page needs its button. The developer writes the two lines that have counted taps in every lesson so far (as seen in Lesson 12), straight into `ProductPage`:

```jsx title="src/ProductPage.jsx" startLine="1" bad="5,10"
import { useState } from 'react';
import db from './db';

export default async function ProductPage() {
  const [count, setCount] = ~useState(0)~; // **WRONG:** a Server Component cannot hold state
  const product = await db.products.get(1);
  return (
    <>
      <h1>{product.title}</h1>
      <button ~onClick={() => setCount(count + 1)}~>Add to cart</button> {/* **WRONG:** a Server Component cannot answer a tap */}
      <p>Cart: {count}</p>
    </>
  );
}
```

**It may look the same, but it is NOT the same thing!** These two lines worked before, because there the component ran in the browser and stayed there. React kept `count`, and called the handler after every tap. `ProductPage` runs on the server, once, and is not sent to the browser. Nothing in the browser keeps `count`, and nothing answers the tap.

**The product page does not render at all.** Here is what happens, in order:
1. The server runs `ProductPage` and reaches `useState(0)`.
2. The version of React that runs Server Components does not give `useState` at all. React's docs: "Server Components are not sent to the browser, so they cannot use interactive APIs like `useState`."
3. The server stops with an error, and the page does not render. Where the error shows, and its exact words, depend on the framework. With React's own server renderer and no framework around it, the call fails with the first error below.
4. Even without the `useState` line, the `onClick` line alone stops the page. React must send the `<button>` and its props to the browser, and a function cannot be sent (as seen in Lesson 107). React's server renderer stops with the second error below.

```text title="The two errors from React's own server renderer"
useState is not a function or its return value is not iterable
Event handlers cannot be passed to Client Component props.
```

React's docs give the rule for the second line: "event handlers like `onClick` can only be defined in Client Components." And they give the reason for both in one sentence: "Server Components do not persist in memory after render and cannot have their own state." State is a component's memory between renders (as seen in Lesson 12). A component that does not stay has no memory to keep.

### Move the Button into Its Own File

The fix React's docs show is to put the button and its state in their own file. That file starts with `'use client'`, and the page renders it. React's docs: "To add interactivity to Server Components, you can compose them with Client Component using the `"use client"` directive."

```jsx title="src/CartButton.jsx" startLine="1"
~'use client';~ // This file and what it imports become client code

import { useState } from 'react';

export default function CartButton() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(count + 1)}>Add to cart</button>
      <p>Cart: {count}</p>
    </>
  );
}
```

`ProductPage` keeps the database read, and renders `CartButton` under the title:

```jsx title="src/ProductPage.jsx" startLine="1"
import db from './db';
import ~CartButton~ from './CartButton'; // The import of a 'use client' file is the boundary

export default async function ProductPage() {
  const product = await db.products.get(1);
  return (
    <>
      <h1>{product.title}</h1>
      ~<CartButton />~ {/* A Client Component inside a Server Component */}
    </>
  );
}
```

The button file starts with `'use client'`. So this import is the border: the server part of the page ends here, and the browser part begins (as seen in Lesson 106). `CartButton` is sent to the browser, stays there, keeps `count`, and answers every tap:

## PRINCIPLE | `window.localStorage`: read it inside `useEffect`, which runs only in the browser

> [!PRINCIPLE]
> **Principle 4: Browser APIs and Effects: `useEffect` Brings Back the Saved `Cart: 2`**
>
> *Browser APIs such as `window.localStorage` exist only in the browser, and Effects run only in the browser, so code that reads or writes the browser goes in a Client Component, inside an Effect or an event handler, never in a Server Component.*
>
> A Server Component never runs in the browser, so `window` does not exist where it runs, and the page does not render. Even a Client Component is first rendered on the server for the HTML. Only its Effects and its event handlers are sure to run in the browser, where the saved count is.
>
> **DO THIS:**
> ```jsx
> 'use client';
> export default function CartButton() {
>   const [count, setCount] = useState(0);
>   ~useEffect~(() => { // Runs in the browser, after the button is on the screen
>     setCount(Number(window.localStorage.getItem('cart')));
>   }, []);
>   return <p>Cart: {count}</p>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default async function ProductPage() {
>   const saved = ~window~.localStorage.getItem('cart'); // **WRONG:** runs on the server, where there is no window, and the page does not render
>   return <p>Cart: {saved}</p>;
> }
> ```

Right now, when the user reloads the page, the line goes back to `Cart: 0`. The shop wants a **guest cart**: a cart kept in the browser for a user who has not signed in. The count must still be there the next day.

You know `localStorage` from plain JavaScript. A site saves the dark theme with one line, and after a reload it reads it back:

```js title="Plain JavaScript: save a value, reload, read it back"
~localStorage.setItem~('theme', 'dark'); // Saves the value under the name 'theme', in this browser
~localStorage.getItem~('theme'); // After a reload, the next day too: gives back 'dark'
```

For the cart, we need the same two methods:
- `window.localStorage.setItem('cart', 2)` saves the value under the name `'cart'`.
- `window.localStorage.getItem('cart')` reads it back, always as text, such as `'2'`.

> [!DEFINITION]
> **Browser APIs.** [NEW] Browser APIs are the tools the browser gives a page and the server does not have, such as `window`, `window.localStorage`, audio, and video. React's docs list "the browser's APIs for web storage, audio and video manipulation, and device hardware", and add: "Since those APIs are only available in the browser, it must be marked as a Client Component" (Lesson 108).

### VS | The Read in `ProductPage` vs. the Read in an Effect: the same call, two different places

A developer can put the read of the saved count in two places:

```jsx title="Reading the saved count in ProductPage, and inside an Effect in CartButton"
const saved = ~window.localStorage.getItem('cart')~; // In ProductPage: runs on the server, where there is no window

useEffect(() => {
  setCount(Number(~window.localStorage.getItem('cart')~)); // In CartButton: runs in the browser, after the button is on the screen
}, []);
```

Both lines make the same browser call. **It may look the same, but it is NOT the same thing!** What differs is where the call runs:
- **In `ProductPage`**, the line runs on the server. The server has no `window`, so the line throws an error, and the page does not render.
- **Inside the Effect in `CartButton`**, the line runs in the browser, after the button is on the screen. React's docs: "Effects **only run on the client.** They don't run during server rendering."

### The Trap: the Body of `CartButton` Also Runs on the Server

Developers often try a third place: the body of `CartButton`, as the first value of `useState`. The file starts with `'use client'`, so it feels safe:

```jsx title="Reading the saved count in the body of CartButton"
const [count, setCount] = useState(Number(~window.localStorage.getItem('cart')~)); // **WRONG:** this body also runs on the server
```

**That fails too, because a Client Component is also rendered on the server, for the first HTML of the page** (as seen in Lesson 102). So its body runs where there is no `window`:
1. Written as above, the line throws on the server, and the server render stops.
2. If the developer guards the line with a check for `window`, the server HTML says `Cart: 0`. But the first render in the browser says `Cart: 2`. The two must match, so React reports a hydration mismatch (as seen in Lesson 105).

Only an Effect or an event handler is sure to run in the browser.

### `CartButton` Saves the Count and Reads It Back

`handleClick` saves the new count after every tap. The Effect reads it back once the button is on the screen:

```jsx title="src/CartButton.jsx" startLine="1"
'use client';

import { useState, useEffect } from 'react';

export default function CartButton() {
  const [count, setCount] = useState(0);

  ~useEffect~(() => { // Runs only in the browser, after the button is on the screen
    setCount(Number(window.localStorage.getItem('cart'))); // '2' becomes 2; with nothing saved, null becomes 0
  }, []);

  function handleClick() {
    setCount(count + 1);
    ~window.localStorage.setItem('cart', count + 1)~; // Saves the new count for the next visit
  }

  return (
    <>
      <button onClick={handleClick}>Add to cart</button>
      <p>Cart: {count}</p>
    </>
  );
}
```

The page file does not change.

### Why `Cart: 0` Shows for a Moment After the Reload

**After a reload, the line shows `Cart: 0` for a moment, and then `Cart: 2`.** The server cannot know what the browser saved, so it renders the count it has, and the Effect corrects it in the browser. Here is what happens when the user reloads the page the next day:
1. The server renders `ProductPage` and the HTML of `CartButton`. No Effect runs on the server, so the HTML says `Cart: 0`.
2. The browser shows the title, the button, and `Cart: 0`.
3. The JavaScript of `CartButton` arrives, and React hydrates the button (as seen in Lesson 104).
4. The Effect runs in the browser and reads `'2'` from `window.localStorage`. Then it calls `setCount(2)`.
5. The line changes to `Cart: 2`.

::: row caption="The product page after a reload: the HTML from the server, and the same page after the Effect runs in the browser."
::: col title="HTML from the server"
```page size=mini
url: shop.example.com
heading: Blue Sneakers
line: [Add to cart]
line: Cart: 0
```
:::
::: col title="After the Effect runs"
```page size=mini
url: shop.example.com
heading: Blue Sneakers
line: [Add to cart]
line: Cart: 2 | good
```
:::
:::

React's docs describe this exact order: "While the app is loading, the user will see the initial render output. Then, when it's loaded and hydrated, your Effect will run."

Remember: `window` lives in the browser, and only an Effect or an event handler is sure to run there.

## PRINCIPLE | `'use client'`: put it on the small `CartButton` file, never on the page that reads the database

> [!PRINCIPLE]
> **Principle 5: The Smallest Client File: `'use client'` on `ProductPage` Breaks the Database Read**
>
> *A Client Component cannot be async, cannot read the database or the file system, and cannot keep a secret, because its code goes to the browser; so `'use client'` goes on the small interactive file, never on the page file that reads the data.*
>
> `'use client'` sends the file and everything it imports to the browser, and turns off every server ability of that file. On the page file, it breaks the async read, takes away the title, and pulls `db.js` toward the browser. On the button file, it sends only the button.
>
> **DO THIS:**
> ```jsx
> ~'use client';~ // At the top of CartButton.jsx: only the button goes to the browser
> export default function CartButton() {
>   const [count, setCount] = useState(0);
>   return <button onClick={() => setCount(count + 1)}>Cart: {count}</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~'use client';~ // **WRONG:** at the top of ProductPage.jsx: an async Client Component, and db.js goes to the browser
> export default async function ProductPage() {
>   const product = await db.products.get(1);
>   return <h1>{product.title}</h1>;
> }
> ```

Many developers read `'use client'` as a switch that says "allow Hooks in this file". It is not. It says: **"send this file, and every file it imports, to the browser."** Everything that follows comes from that one sentence.

Go back to the error of Principle 3. The first fix most developers find is one line: `'use client'` at the top of the page file. The rest of the file stays exactly as it was:

```jsx title="src/ProductPage.jsx" startLine="1" bad="1"
~'use client';~ // **WRONG:** ProductPage and everything it imports become client code, db.js included

import { useState } from 'react';
import db from './db';

export default async function ProductPage() {
  const [count, setCount] = useState(0);
  const product = await db.products.get(1);
  return (
    <>
      <h1>{product.title}</h1>
      <button onClick={() => setCount(count + 1)}>Add to cart</button>
      <p>Cart: {count}</p>
    </>
  );
}
```

The error about `useState` is gone, and the rest of the file looks the same. **It may look the same, but it is NOT the same thing!** The file still holds the same `await db.products.get(1)`. But `ProductPage` is now a Client Component, and a Client Component can do none of the four things on the server's list.

**The error about state goes away, and the database read breaks instead.** Here is what the one line does, in order:
1. The page file and everything it imports, the database file included, become client code (as seen in Lesson 106). React's docs: "All code that is a part of the Client module sub-tree is sent to and run by the client."
2. `ProductPage` is now an async Client Component. React does not support async components in the browser, so React stops the page with an error, and the screen stays empty. The Console shows the error twice, then a warning that names the component:

```devconsole width=full caption="The Console when ProductPage.jsx starts with 'use client' and ProductPage is still async."
x <ProductPage> is an async Client Component. Only Server Components can be async at the moment. This error is often caused by accidentally adding `'use client'` to a module that was originally written for the server.
x Uncaught Error: An unknown Component is an async Client Component. Only Server Components can be async at the moment. This error is often caused by accidentally adding `'use client'` to a module that was originally written for the server.
! An error occurred in the <ProductPage> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

3. The database file now runs in the user's browser. There, `process.env.DB_PASSWORD` is not the server's password, and a real database client cannot connect from the browser. What the browser gets in place of the password depends on the framework.
4. So the page has lost its database read. The title `Blue Sneakers` does not arrive, and with a real database behind the stand-in, it has no way to arrive.

React's docs name this exact half of the trade. About a component that reads a file, they say it "must be a Server Component as it reads from the local file system on the server". Reading that file is "possible only in a Server Component."

### The Next Wrong Step

To silence the async error, the developer removes `async`. Then they add an Effect with `fetch`, and build an API route for the title. That is the version with `fetch` in an Effect from Principle 1, again. The title waits for a second request, and the code of the page is in the bundle, as Principle 2 showed. The page works, and it has lost everything the server could do for it.

### VS | `'use client'` on the Page File vs. on the Button File: the same line, two different amounts of code in the browser

The real fix is to move the directive, not to add it. The same line can sit at the top of either file:

```jsx title="The same line at the top of two different files"
~'use client';~ // **WRONG:** at the top of ProductPage.jsx
~'use client';~ // At the top of CartButton.jsx
```

The line is identical. **It may look the same, but it is NOT the same thing!** What it pulls into the browser depends on the file it starts:

```tree caption="'use client' on the page file vs. 'use client' on the button file: the same line, two different amounts of code sent to the browser."
Where `'use client'` goes
- !On `ProductPage.jsx` [`'use client'` `async` `db.js`] | The page **and `db.js`** become client code | The page **loses its database read** and gets an **async Client Component** error
- +On `CartButton.jsx` [`'use client'` `useState` `onClick`] | Only **the button** and what it imports become client code | `ProductPage` **reads the database**; the button **answers the taps**
```

When `CartButton` needs something from the database, such as the title, the Server Component reads it. Then it passes it down as a prop: `<CartButton title={product.title} />`. A string can travel from the server to the browser (as seen in Lesson 107). The Client Component never reads the database itself.

Remember: `'use client'` means "send this to the browser". Put it on the smallest file that needs the user.

### Where React Runs Each Component, in Order

When the user opens the page, React runs `ProductPage` on the server first. Inside it, React meets `<CartButton />`, renders its first HTML on the server too, and sends the code of `CartButton` alone to the browser. In the browser, React hydrates `CartButton`, and its Effect reads the saved count:

```tree caption="The order in which React runs the components of the product page, on the server and in the browser."
`ProductPage` [1. On the server] | **Server Component** | Awaits the product from `db` and returns the `<h1>` and `<CartButton />`
- +`<h1>Blue Sneakers</h1>` [2. Rendered output] | Sent to the browser **as output**, not as code | The browser **never gets** `ProductPage.jsx` or `db.js`
- +`CartButton` [3. On the server, then in the browser] | **Client Component** | First HTML with **`Cart: 0`**; then hydrated in the browser, where the Effect shows **`Cart: 2`** and every tap adds one
```

### Summary

| Ability | Server Component | Client Component |
| :--- | :--- | :--- |
| **`async` and `await` while rendering** | Yes, as `ProductPage` does | No: "async components are not supported on the client" |
| **The database or the file system, with no API** | Yes, as the database read in `ProductPage` | No: it needs an API and a second request |
| **Secrets such as the database password** | Yes, read in `db.js` on the server | No: all its code "is sent to and run by the client" |
| **Its own code in the browser bundle** | No: the browser gets only the rendered output | Yes: "Only Client modules are bundled" |
| **State with `useState` or `useReducer`** | No: it does not persist in memory after render | Yes, as `count` in `CartButton` |
| **Event handlers such as `onClick`** | No: "can only be defined in Client Components" | Yes, as `handleClick` in `CartButton` |
| **Effects with `useEffect` or `useLayoutEffect`** | No: "Effects only run on the client" | Yes, as the Effect in `CartButton` |
| **Browser APIs such as `window.localStorage`** | No: the server has no `window` | Yes, inside an Effect or an event handler |

Remember the one sentence of this lesson. **A component can do only what the place it runs in has. The server has the data and the secrets. The browser has the user.**

## For the Interview

> **The Interview Question:** What can a Server Component do that a Client Component cannot, and vice versa?

### How to Answer Clearly in 30 Seconds

"Both are React components. The difference is where they run. A Server Component runs on the server, at build time or for each request, and is never sent to the browser. A Client Component is sent to the browser and stays in memory while the page is open. Every ability follows from that:
1. **A Server Component** can be async and await data while it renders. It can read the database or the file system directly, with no API, and use secrets such as a database password. It costs the browser nothing, because only Client modules are bundled.
2. **A Client Component** can hold state, answer events such as `onClick`, run Effects, and use browser APIs such as `window.localStorage`. A Server Component cannot, because it does not persist in memory after render and never runs in the browser.
3. **The usual split**: the page is a Server Component that reads the data. Only the interactive part is a small Client Component with `'use client'`, which receives what it needs as serializable props."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Can a Server Component use any Hooks at all?"**
   **A few.** React's docs say Server Components "cannot use most Hooks", not all of them:
   - `use` and `useId` are the two Hooks React's docs leave out of the list that must run on the client. Even so, `useId` "currently cannot be used in async Server Components".
   - The version of React that runs Server Components also gives `useMemo` and `useCallback`. It does not give `useState`, `useReducer`, `useEffect`, or `useLayoutEffect` at all.
   - `cache` goes the other way: it "is for use in Server Components only" (Lesson 123).
   - A custom Hook is client-only when it calls a client Hook such as `useState` or `useEffect`.

   For third-party libraries, React's docs give a list. A component must run on the client when it uses `createContext`, Hooks other than `use` and `useId`, `forwardRef`, `memo`, `startTransition`, or browser APIs.
2. **"How does a Client Component get data from the server, then?"**
   **Three ways.**
   - A Server Component above it reads the data and passes it down as props, which must be serializable (as seen in Lesson 107).
   - The Client Component calls a Server Function, a function marked with `'use server'` (Lesson 110).
   - The Client Component fetches from an API in an Effect (as seen in Lesson 33).

   A Client Component can also show content that a Server Component rendered, when it receives it as `children` (Lesson 115).
3. **"Is it always cheaper to keep a component on the server?"**
   **No.** A Server Component sends its output instead of its code, and sometimes the output is the bigger of the two. React's docs give the case of a component whose "HTML output was large relative to its source code", such as one that draws "a long SVG path string". Then "it might be more efficient to force it to always be a Client Component".

```tree dir=right caption="Interview summary: what each kind of component can do, and how a real page splits the work."
What each side can do
- +Server Component [`async` `await` `db`] | Awaits data while it renders, **reads the database** with no API, **keeps secrets** | **Costs the browser nothing**: only its output is sent
- +Client Component [`useState` `onClick` `useEffect`] | Holds **state**, answers **events**, runs **Effects**, uses **browser APIs** | Is **sent to the browser** and **stays** there
- +The split [`'use client'` on `CartButton.jsx`] | The page reads the data **on the server** | Only the **small interactive file** goes to the browser
```
