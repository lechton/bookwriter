# Lecture 38: Calling Hooks Only at the Top Level of React Functions

*(Why does a form crash when one useState moves inside an if?)*

> INTERVIEW QUESTION | ❱ CORE | Why must hooks be called at the top level, and only from React functions?

---

## VS | `useState` at the top vs. `useState` inside `else`: both work while the user types, only the top one survives Send

**Every Hook call must sit at the top level of your component, never inside an `if` or a loop, because React tracks Hooks by their call order.**

Say a store page needs a shopping cart only after the user logs in. In normal JavaScript, it feels natural to write an `if` check first and create the cart variable only inside that `if`. In React, the moment the user logs in and that `if` turns true, the whole page crashes.

**Why:** React does not remember your `useState` variables by the names you give them. It only keeps a numbered list in the exact order your component calls them: first Hook, second Hook, third Hook. If an `if` statement or early `return` skips a Hook on the next render, the list no longer matches your calls, and React crashes.

Now let's see what that means.

In plain JavaScript, a variable has a name, and JavaScript finds it by that name. You can even declare it inside an `if`, and nothing breaks:

```js title="A variable inside an if, in plain JavaScript"
if (isReady) {
  let ~message~ = ''; // JavaScript finds message by its name
}
```

A Hook is different. It is not a variable. It is a function call, and the call hands React no name:

```jsx title="Two useState calls, one after the other"
const [isSent, setIsSent] = ~useState(false)~; // React receives false, and no name
const [message, setMessage] = ~useState('')~; // React receives an empty string, and no name
```

You see `isSent` and `message`. React sees neither. Those names exist only inside your function. React receives `false`, then an empty string.

So how does React know which stored value belongs to which call? It counts. React keeps the values of a component's Hooks in a list, in the order of the calls. On every render, the first call gets the first value, and the second call gets the second value (Lesson 12).

React's docs describe it like this: "Internally, React holds an array of state pairs for every component." And they give the condition that makes it work: Hooks "rely on a stable call order on every render of the same component."

Now you can see the danger. Put the second `useState` inside an `if`. On one render, the `if` is true, and React counts two calls. On the next render, it is false, and React counts one. The list and the calls no longer match, and React stops with an error.

That is the whole lesson. React's docs say it in one line: "always use Hooks at the top level of your React function, before any early returns."

> [!DEFINITION]
> **What is an early return?** [REVIEW] An early return is a `return` that comes before the end of the function. You know it from plain JavaScript: `if (!user) return;` stops the function on that line, and every line below it is skipped.
> In a component, an early return usually shows another screen: `if (isSent) return <h1>Thank you!</h1>;`.
> Something that can be tricky: a Hook written below an early return is skipped too, on every render where the return happens (Lesson 10).

> [!DEFINITION]
> **What is the top level?** [NEW] The top level of a component is its own body: the lines that run every time React calls the function.
> A line is at the top level when it sits outside every `if`, every loop, and every function written inside the component, and above the first early `return`.
> React's docs give an image for it. Think of Hooks as "unconditional declarations about your component's needs", and use them at the top of the component "similar to how you "import" modules at the top of your file."
> You never put an `import` inside an `if`. It sits at the top of the file, and it always runs. A Hook belongs in the same kind of place. **Unconditional** means that no condition decides whether it runs (Lesson 38).

> [!DEFINITION]
> **What are the Rules of Hooks?** [NEW] The Rules of Hooks are the two rules from React's docs that keep the order of Hook calls the same on every render.
> The first rule: "Only call Hooks at the top level." No `if`, no loop, no nested function, and nothing below an early `return`.
> The second rule: "Only call Hooks from React functions." A React function is a function component or a custom Hook. An event handler is not one.
> The lint rule `rules-of-hooks`, from the package `eslint-plugin-react-hooks`, checks both rules and marks every line that breaks them (Lesson 38).

### Two places for the same `useState`

Here is the `useState` for `message` in two places:
1. **At the top of the component**, above the `if`.
2. **Inside the form's branch**, right next to the form that uses it.

Both versions show an empty message field when the page opens. In both, the user can type. They look the same, but they are NOT the same thing!

Only the version with the Hook at the top shows `Thank you!` after Send. The version with the Hook inside the branch crashes, with the error that React's docs quote: "Rendered fewer hooks than expected".

```tree caption="Two places for the useState of message: both work while the user types, and only one survives the click on Send."
Where the `useState` for `message` sits
- +At the top of the component, above the `if` | The field opens empty and **typing works** | After Send, the page shows **`Thank you!`**
- !Inside the form's branch, next to the form | The field opens empty and **typing works** | After Send, React stops with **Rendered fewer hooks than expected**
```

### What is at stake

The user writes a message and clicks Send. Instead of `Thank you!`, the whole page goes blank, and the message is gone.

React's docs explain the blank page: "By default, if your application throws an error during rendering, React will remove its UI from the screen."

And the bug hides well. The page opens with no error, and typing works. A developer who only types in the field never sees the crash. The first user who clicks Send sees it.

### The Rule of Thumb: Hooks first, then the `if`

**Write every Hook at the top of the component, before the first `if` and the first `return`. The condition decides what the component shows, never whether a Hook runs.**

A senior developer also knows the four classic mistakes:
1. **Thinking React finds `message` by its name.** React finds it by its place in the order.
2. **Moving a Hook next to the code that uses it, inside a branch.** The render that skips the branch skips the Hook too.
3. **Silencing the linter when it marks that line.** The warning disappears, and the bug ships.
4. **Calling a Hook inside an event handler**, to create state at the moment of the click. The click throws an error.

The rest of the lesson shows each one on a real feedback form.

## SECTION | A Feedback Form with a Send Button

Many apps end a page with a small feedback form: a message field and a `Send` button. The message field is a `<textarea>`, an input field with several lines. When the page opens, it is empty, and its grey placeholder text says `Message`:

```page width=text caption="The feedback form when the page opens: an empty message field and a Send button."
form:
  textarea:  |
  submit: Send
console: quiet
```

The user does two things on this form, and expects two results:
1. **The user types `Great app` in the message field.** The letters appear.
2. **The user clicks `Send`.** The form disappears, and the heading `Thank you!` takes its place.

```page width=text caption="The same page after the user clicks Send: the form is gone, and the thank-you heading takes its place."
heading: Thank you!
console: quiet
```

Now look at the same screen as the developer. The component shows one of two screens, so its code has an `if` with two branches. The text the user types lives in a state variable, `message`, and only the form uses it.

So where does the `useState` for `message` go? At the top. Always.

Our project has four files. The whole form lives in one component, `FeedbackForm`:

```files title="feedback-form: File Explorer" caption="How the files of the feedback form sit inside src/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it inside `<StrictMode>`
  App.jsx | parent | Exports `App` as default and imports `FeedbackForm` from `./FeedbackForm.jsx`
  FeedbackForm.jsx | state | Holds `isSent` and `message`, and shows the form or the thank-you heading
```

`App` only places the form on the page:

```jsx title="src/App.jsx"
import FeedbackForm from './FeedbackForm.jsx';

export default function App() {
  return ~<FeedbackForm />~; // React calls FeedbackForm to draw the form
}
```

Here is the working form. Both Hooks sit at the top level, and the early `return` comes after them:

```jsx title="src/FeedbackForm.jsx" good="4,5"
import { useState } from 'react';

export default function FeedbackForm() {
  const [isSent, setIsSent] = ~useState(false)~; // 1st Hook call, on every render
  const [message, setMessage] = ~useState('')~; // 2nd Hook call, on every render

  if (isSent) {
    return <h1>Thank you!</h1>; // The early return comes after both Hooks
  }

  return (
    <form onSubmit={e => {
      e.preventDefault();
      setIsSent(true);
    }}>
      <textarea
        placeholder="Message"
        value={message}
        onChange={e => setMessage(e.target.value)}
      />
      <br />
      <button type="submit">Send</button>
    </form>
  );
}
```

Count the Hook calls on each render: two, every time. On the first render, React stores the two starting values. On every later render, React hands back what it stored, in the order of the calls:

| What the user did | 1st Hook call returns | 2nd Hook call returns | What the page shows |
| :--- | :--- | :--- | :--- |
| Opened the page | `isSent` is `false` | `message` is `''` | The empty message field and `Send` |
| Typed `Great app` | `isSent` is `false` | `message` is `'Great app'` | The message field with `Great app` |
| Clicked `Send` | `isSent` is `true` | `message` is `'Great app'` | `Thank you!` |

Now let's break it, one principle at a time:

**PRINCIPLES:** React does not know your Hooks by their names. It knows them by their order. Five principles follow:
1. **Principle 1: React Matches Every Hook by Its Place in the Order.** React never sees the names `isSent` or `message`. It sees a first call and a second call, and this holds for every kind of Hook.
2. **Principle 2: A Hook in a Branch Crashes the Render That Skips It.** After Send, the thank-you render calls one Hook instead of two, and the page goes blank.
3. **Principle 3: Every Hook Goes Above the First Return.** Move the Hook up, and let the `if` decide only what the component returns.
4. **Principle 4: The Condition Moves, Not the Hook.** Put the condition inside the Hook, into its initial value, or into a new component.
5. **Principle 5: Hooks Run Only While React Renders.** A Hook works in a function component or a custom Hook, never in an event handler or a regular function.

## PRINCIPLE | useState and every other Hook: React finds the stored value by the call's place, not by the variable's name

> [!PRINCIPLE]
> **Principle 1: Call Order: React Matches Every Hook by Its Place in the Order**
>
> *React tracks every Hook in a component, of any kind, by its place in the order of Hook calls, so every render must call the same Hooks in the same order.*
>
> React never receives the names isSent or message. It receives a first Hook call and a second Hook call, and it hands each one the data stored at that place. This works only while every render makes the same calls in the same order. That is why every Hook sits at the top level of the component.
>
> **DO THIS:**
> ```jsx
> function FeedbackForm() {
>   const [isSent, setIsSent] = ~useState(false)~; // 1st Hook on every render
>   const [message, setMessage] = ~useState('')~; // 2nd Hook on every render
>   if (isSent) {
>     return <h1>Thank you!</h1>;
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function FeedbackForm() {
>   const [isSent, setIsSent] = useState(false);
>   if (!isSent) {
>     const [message, setMessage] = ~useState('')~; // **WRONG:** the 2nd Hook runs only while isSent is false
>   }
> }
> ```

### Renaming a variable changes nothing for React

Suppose we rename `message` to `text`:

```jsx title="The same Hook call under two variable names"
const [~message~, setMessage] = useState(''); // The 2nd Hook call in FeedbackForm
const [~text~, setText] = useState(''); // Still the 2nd Hook call: React sees no difference
```

For React, it is the exact same thing! Each line is the second `useState` call in `FeedbackForm`, so React hands it the second value it stored. The name was never part of the deal.

### The order counts for every kind of Hook

Here is the new fact of this lesson: the order counts for every Hook, not only for `useState`. React matches each of these by its place in the same way:
1. **`useEffect`**: React finds the dependencies from the last render by the Effect's place.
2. **`useRef`**: React finds the same ref object by its place.
3. **`useReducer`**: React finds the stored state by its place.

`useContext` is a special case. It keeps no data of its own, because it reads the nearest provider. React still counts it in the order, and React prints an error in the Console when a `useContext` call moves.

React's docs: "Each time your component renders, React expects the exact same hooks to be called in the exact same order."

When the order changes from one render to the next, React gives one Hook's data to another call. React's docs say React then "loses track of which state corresponds to which hook call, leading to bugs like state mismatches".

Principle 2 shows the render where our form breaks the order.

## PRINCIPLE | useState inside else: the render that skips it crashes the whole page

> [!PRINCIPLE]
> **Principle 2: Hooks in Branches: A Hook in a Branch Crashes the Render That Skips It**
>
> *A Hook inside a condition, a loop, or below an early return runs on some renders and not on others, so the number of Hook calls changes and React stops with an error.*
>
> Where a value is used and where its Hook is called are two separate things. Only the form uses message, but the useState for message must also run on the thank-you render. When a render skips a Hook, React throws "Rendered fewer hooks than expected", and without an error boundary the whole page goes blank.
>
> **DO THIS:**
> ```jsx
> const [isSent, setIsSent] = useState(false);
> const [message, setMessage] = ~useState('')~; // Runs on the form render and on the thank-you render
> if (isSent) {
>   return <h1>Thank you!</h1>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [isSent, setIsSent] = useState(false);
> if (isSent) {
>   return <h1>Thank you!</h1>;
> } else {
>   const [message, setMessage] = ~useState('')~; // **WRONG:** skipped after Send, so React stops and the page goes blank
> }
> ```

### The Hook moves next to the form that uses it

A developer may reason like this: only the form uses `message`, so its `useState` belongs next to the form. It sounds tidy.

React's docs use this very form in an exercise named "Fix a crash". There, the state Hook for `message` sits inside the `else` branch:

```jsx title="src/FeedbackForm.jsx" bad="9"
import { useState } from 'react';

export default function FeedbackForm() {
  const [isSent, setIsSent] = useState(false);

  if (isSent) {
    return <h1>Thank you!</h1>;
  } else {
    const [message, setMessage] = ~useState('')~; // **WRONG:** inside else, so it runs only while isSent is false
    return (
      <form onSubmit={e => {
        e.preventDefault();
        setIsSent(true);
      }}>
        <textarea
          placeholder="Message"
          value={message}
          onChange={e => setMessage(e.target.value)}
        />
        <br />
        <button type="submit">Send</button>
      </form>
    );
  }
}
```

The linter marks the highlighted line. In the docs' exercise, the developer has silenced it with an `eslint-disable-next-line` comment on the line above (Lesson 35). So nothing warns about it anymore.

### The user types, and nothing looks wrong

When the page opens, the message field is empty, and the Console is quiet. The user types `Great app`, and the letters appear:

```page width=text caption="The form with the Hook inside else, after the user types Great app: it looks exactly like the working form."
form:
  textarea:  | Great app
  submit: Send
console: quiet
```

So far, every render of this version also calls two Hooks. The first is the `useState` for `isSent` at the top. The second is the one for `message`, inside `else`. The difference waits for one click.

### Clicking Send blanks the page

**Beware! With the Hook inside `else`, the click on Send removes the whole page.** The thank-you render calls one Hook where the render before it called two, and React stops. Here is what happens, in order:
1. The page opens. `isSent` is `false`. React calls the first `useState`, goes into `else`, and calls the second one. Two Hook calls.
2. The user types `Great app`. Each letter calls `setMessage`, and each render makes the same two calls.
3. The user clicks `Send`. The submit handler stops the browser from reloading the page, and it sets `isSent` to `true`.
4. React calls `FeedbackForm` again. The first Hook call now returns `true`.
5. The `if` returns the thank-you heading, so the Hook for `message` never runs. One Hook call.
6. React expected two Hook calls and got one. It throws an error while rendering `FeedbackForm`.
7. Nothing above the form catches the error, so React removes the whole page from the screen.

A component that catches such an error and shows a fallback screen instead is called an **error boundary**. Our page has none.

```page width=text caption="The same page after the user clicks Send with the Hook inside else: nothing is left on the screen."
blank
console: Uncaught Error: Rendered fewer hooks than expected. This may be caused by an accidental early return statement.
  warn: An error occurred in the <FeedbackForm> component. Consider adding an error boundary to your tree to customize error handling behavior. Visit https://react.dev/link/error-boundaries to learn more about error boundaries.
```

The page now shows nothing at all. The user sees neither the form nor `Thank you!`, and the message is lost.

No line of our code throws this error. React throws it, because the number of Hook calls changed between two renders. Then React prints a warning that names the component and suggests an error boundary.

### The same crash in the other direction

Now suppose a Hook sits inside the `if` branch instead, so it runs only after Send. Then the thank-you render calls more Hooks than the render before it. React stops with "Rendered more hooks than during the previous render." (Lesson 12).

Just before that error, React prints another one: "React has detected a change in the order of Hooks called by FeedbackForm". Under it, a table lists the Hooks of the two renders.

Fewer or more, the cause is the same: a condition decided whether a Hook ran.

### Every place where a Hook must not go

React's docs list every place where a Hook call is not supported:
1. Inside a condition, such as an `if` or a ternary. The operators `&&` and `||` count too.
2. Inside a loop, such as `for`. The number of Hook calls would then follow the number of items.
3. After a conditional `return`.
4. In an event handler.
5. In a class component.
6. Inside a function you pass to `useMemo` or `useReducer`. The same goes for `useEffect`.
7. Inside a `try` block. The same goes for its `catch` and `finally` blocks.

The docs page for the linter adds two more places: an async function, and the top of a file, outside any component.

The lint rule that catches all of these is `rules-of-hooks`, from the package `eslint-plugin-react-hooks`. The package comes with a ready-made set of rules called the `recommended` preset. This rule is part of it, so every project that uses the preset has the rule on.

It marked our line inside `else`. The developer silenced it, and the bug shipped. The docs' hint for this exercise says where to look first: "Check if there are any comments disabling the linter checks--this is where the bugs often hide!"

## PRINCIPLE | useState above the first return: every render calls the same two Hooks

> [!PRINCIPLE]
> **Principle 3: Top Level: Call Every Hook Above the First Early Return**
>
> *Call every Hook at the top level of the component, above the first early return, and let the condition decide only what the component returns.*
>
> An early return stops the function, so every Hook written below it is skipped on that render. Move the Hook above the return, and every render calls the same Hooks. The component then creates every value on every render, and the if decides only which screen the user sees.
>
> **DO THIS:**
> ```jsx
> const [isSent, setIsSent] = useState(false);
> const [message, setMessage] = ~useState('')~; // Above the first return
> if (isSent) {
>   return <h1>Thank you!</h1>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [isSent, setIsSent] = useState(false);
> if (isSent) {
>   return <h1>Thank you!</h1>;
> }
> const [message, setMessage] = ~useState('')~; // **WRONG:** below the first return, skipped after Send
> ```

### One line moves

The fix is to move one line. Here is the `useState` for `message` in its two places:

```jsx title="useState for message inside else, below the if"
if (isSent) {
  return <h1>Thank you!</h1>;
} else {
  const [message, setMessage] = ~useState('')~; // **WRONG:** skipped on the thank-you render
}
```

```jsx title="useState for message above the if"
const [isSent, setIsSent] = useState(false);
const [message, setMessage] = ~useState('')~; // Runs on every render, before the first return
if (isSent) {
  return <h1>Thank you!</h1>;
}
```

It looks the same, but it is NOT the same thing! With the Hook inside `else`, the thank-you render makes one Hook call. With the Hook above the `if`, every render makes two Hook calls, so the order never changes.

React's docs give this exact fix for this exact form: "Hooks can only be called at the top level of the component function. Here, the first `isSent` definition follows this rule, but the `message` definition is nested in a condition. Move it out of the condition to fix the issue".

They add: "Remember, Hooks must be called unconditionally and always in the same order!"

### The `else` is no longer needed

Once both Hooks sit above the `if`, the `else` around the form has no job left. The `if` already returns early. So the lines below it run only when `isSent` is false. With the `else` or without it, the form behaves the same.

React's docs suggest removing it "to reduce the nesting". They keep one condition: "it's still important that all calls to Hooks happen *before* the first `return`."

### The thank-you screen still has a `message`

A common worry: the thank-you screen does not need `message`, so why create it there? Because creating a value and showing it are two separate things.

On the thank-you render, the second Hook call still runs, and React still hands back `'Great app'`. The thank-you screen simply does not show it.

### The fixed form

Here is the final `FeedbackForm`. The `else` is gone, and both Hooks sit at the top:

```jsx title="src/FeedbackForm.jsx" good="4,5"
import { useState } from 'react';

export default function FeedbackForm() {
  const [isSent, setIsSent] = useState(false);
  const [message, setMessage] = ~useState('')~; // Moved above the first return: two Hook calls on every render

  if (isSent) {
    return <h1>Thank you!</h1>;
  }

  return (
    <form onSubmit={e => {
      e.preventDefault();
      setIsSent(true);
    }}>
      <textarea
        placeholder="Message"
        value={message}
        onChange={e => setMessage(e.target.value)}
      />
      <br />
      <button type="submit">Send</button>
    </form>
  );
}
```

The user types `Great app` and clicks Send. This time the heading appears, and the Console stays quiet:

```page width=text caption="The fixed form after the user clicks Send: both Hooks ran, and the thank-you heading appears."
heading: Thank you!
console: quiet
```

### The same mistake on a loading screen

Developers often meet this rule with an early `return` for a screen that is not ready yet, such as a loading line. React's docs show this case:

```jsx title="useState below a loading return"
if (!data) {
  return <Loading />;
}
const [processed, setProcessed] = ~useState(data)~; // **WRONG:** skipped while data is missing, then called once data arrives
```

While `data` is missing, the component returns early and calls fewer Hooks. When the data arrives, it calls one more. With another Hook above the `if`, React then stops with "Rendered more hooks than during the previous render."

When this `useState` is the only Hook of the component, React prints nothing yet. The crash waits for the first Hook that someone adds above the `if`.

The fix is the same as on our form: the Hook moves above the `return`.

## PRINCIPLE | if inside the Hook, not the Hook inside if: every render still calls the same Hooks

> [!PRINCIPLE]
> **Principle 4: Moving the Condition: The Hook Stays, the Condition Moves Inside It**
>
> *When a Hook seems to need a condition, keep the Hook at the top level and put the condition inside it, in its initial value, or in a new component that holds the Hook.*
>
> A condition may decide what a Hook does, never whether it runs. Inside an Effect, the if decides what the Effect does. In useState, a ternary picks the starting value. When state belongs to one branch only, a new component holds it, and the parent's if decides whether that component appears.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   ~if (isLoggedIn)~ { // The condition lives inside the Effect
>     fetchUserData();
>   }
> }, [isLoggedIn]);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~if (isLoggedIn)~ { // **WRONG:** the condition decides whether useEffect is called at all
>   useEffect(() => {
>     fetchUserData();
>   }, []);
> }
> ```

Sometimes you really want a Hook "only sometimes". An Effect only for a signed-in user. A starting value that depends on the kind of user.

The Hook still stays at the top. **The condition moves instead.** React's docs give four ways to move it:
1. Put the condition inside the Effect.
2. Give `useState` a conditional initial value.
3. Extract a new component and move the state into it.
4. Read context with `use` instead of `useContext`.

### 1. The condition goes inside the Effect

Say you want to fetch the user's data only when the user is signed in. The first idea is to wrap the Effect in an `if`:

```jsx title="useEffect inside if"
if (isLoggedIn) {
  ~useEffect~(() => { // **WRONG:** when the user signs in, the next render calls one more Hook
    fetchUserData();
  }, []);
}
```

React's docs keep the Effect at the top and move the `if` inside it:

```jsx title="if inside the Effect"
~useEffect~(() => { // Called on every render, so the number of Hook calls never changes
  if (isLoggedIn) {
    fetchUserData();
  }
}, ~[isLoggedIn]~); // The Effect runs again when isLoggedIn changes
```

They look the same, but they are NOT the same thing! In the first version, the `useEffect` call itself comes and goes with `isLoggedIn`. In the second, React gets one `useEffect` call on every render, and the condition decides only what the Effect does.

Because `isLoggedIn` is in the dependency array, the Effect runs again when the user signs in (Lesson 32).

### 2. The condition goes into the initial value

Say the starting permissions depend on the kind of user. The first idea is two `useState` calls in two branches:

```jsx title="Two useState calls in two branches"
if (userType === 'admin') {
  const [permissions, setPermissions] = ~useState(adminPerms)~; // **WRONG:** a Hook inside if
} else {
  const [permissions, setPermissions] = ~useState(userPerms)~; // **WRONG:** a Hook inside else
}
```

React's docs replace them with one `useState` and a **conditional initial value**. A ternary picks the starting value, and the Hook call stays at the top:

```jsx title="One useState with a conditional initial value"
const [permissions, setPermissions] = useState(~userType === 'admin' ? adminPerms : userPerms~); // One Hook call: the condition picks only the starting value
```

Both versions try to start `permissions` with the right value. In the version with two branches, each `useState` sits inside a condition, so the linter marks both lines. In the version with the ternary, there is one `useState`, called on every render.

Keep in mind that React uses an initial value only on the first render. So the ternary picks the starting value once.

### 3. The state moves into a new component

Back to our form. Only the form's branch uses `message`. When state belongs to one branch only, React's docs give a third way: "extract a new component and move the state into it."

So the form moves into its own component, `MessageForm`, and `message` moves with it:

```jsx title="src/MessageForm.jsx"
import { useState } from 'react';

export default function MessageForm({ onSend }) {
  const [message, setMessage] = ~useState('')~; // The top level of MessageForm: one Hook call on every render of MessageForm

  return (
    <form onSubmit={e => {
      e.preventDefault();
      ~onSend()~; // Tells FeedbackForm that the user clicked Send
    }}>
      <textarea
        placeholder="Message"
        value={message}
        onChange={e => setMessage(e.target.value)}
      />
      <br />
      <button type="submit">Send</button>
    </form>
  );
}
```

`FeedbackForm` keeps only `isSent`, and it chooses which screen to show. It hands `MessageForm` a callback prop, `onSend`, so the form can ask its parent to switch screens (Lesson 23):

```jsx title="src/FeedbackForm.jsx"
import { useState } from 'react';
import MessageForm from './MessageForm.jsx';

export default function FeedbackForm() {
  const [isSent, setIsSent] = useState(false); // FeedbackForm's only Hook

  if (isSent) {
    return <h1>Thank you!</h1>;
  }

  return <MessageForm ~onSend={() => setIsSent(true)}~ />; // Calls setIsSent(true) when the user clicks Send
}
```

Now the `if` decides whether `MessageForm` appears, not whether a Hook runs. Each component calls its one Hook at its own top level, on every one of its own renders.

When the user clicks Send, `Thank you!` replaces `MessageForm`. React then discards the state of `MessageForm`, with its `message` (Lesson 25). The user sees the same page as with the fixed form of Principle 3: the message field and `Send`, then `Thank you!`.

Both designs are correct. The fixed form of Principle 3 is shorter, so it stays our final page. A new component pays off when the branch holds several pieces of state of its own.

### 4. Context goes through `use`

The last case is a branch that only reads context. `useContext` is a Hook, so it must stay at the top. But React has an API that may sit inside an `if`: `use` (Lesson 28).

```jsx title="useContext inside if, and use inside if"
if (isSent) {
  const theme = ~useContext(ThemeContext)~; // **WRONG:** useContext is a Hook inside if
}
if (isSent) {
  const theme = ~use(ThemeContext)~; // use may be called inside if
}
```

They look the same, but they are NOT the same thing! With `useContext` inside the `if`, the thank-you heading still appears after Send. But React prints "React has detected a change in the order of Hooks called by FeedbackForm" in the Console.

React's docs: "While `useContext` must be called at the top level of your component, `use` can be called inside conditionals like if and loops like for." They also say: "Despite its name, `use` is not a Hook."

Two limits remain for `use`. It cannot sit inside a `try` and `catch` block. And it must be called inside a component or a Hook.

## PRINCIPLE | useState in a component or a custom Hook only: an event handler runs outside any render

> [!PRINCIPLE]
> **Principle 5: React Functions Only: Call Hooks While React Renders a Component or a Custom Hook**
>
> *Call Hooks only while React renders a function component or a custom Hook, and never from an event handler, a regular JavaScript function, or a class component.*
>
> A Hook needs the component that React is rendering at that moment. An event handler runs later, when the user clicks, outside any render, so a Hook inside it throws. Keep every Hook at the top level of a component or a custom Hook, and let event handlers call only setters.
>
> **DO THIS:**
> ```jsx
> const [isSent, setIsSent] = useState(false);
> <form onSubmit={e => {
>   e.preventDefault();
>   ~setIsSent(true)~; // The handler calls only the setter
> }}>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <form onSubmit={e => {
>   e.preventDefault();
>   const [isSent, setIsSent] = ~useState(true)~; // **WRONG:** a Hook in an event handler throws when the user clicks Send
> }}>
> ```

### A component and a regular function look alike

The second Rule of Hooks says which functions may call a Hook. Here are two JavaScript functions with the same Hook call inside:

```jsx title="The same Hook call in a component and in a regular function"
function FeedbackForm() {
  const [isSent, setIsSent] = ~useState(false)~; // A function component: React calls it to render
}

function sendFeedback() {
  const [isSent, setIsSent] = ~useState(false)~; // **WRONG:** a regular function, not a component or a custom Hook
}
```

They look the same, but they are NOT the same thing! Only `FeedbackForm` is a **React function**. React's docs use that name for the two kinds of functions that may call Hooks:
1. **A function component**, such as `FeedbackForm`. React calls it to render.
2. **A custom Hook**, a function you write whose name starts with `use` and a capital letter, such as `useOnlineStatus`. It may call other Hooks, and a component calls it at its own top level. The next lesson covers custom Hooks in full.

Every other function is a **regular JavaScript function**, and it may not call Hooks.

Why? Think of what React does when it renders. It calls `FeedbackForm`, and while that function runs, React knows two things. It is rendering `FeedbackForm` right now. And it is at Hook number one, then number two.

A regular function can run at any moment your code chooses, outside any render. Then React is not rendering anything. A `useState` call has no component to belong to, and no place in any list.

React's docs say it in one line: "You can only call Hooks while React is rendering a function component".

### The Hook moves into the click

On our form, this mistake looks like a shortcut. A developer wants a state that exists only after the click. So the developer writes `useState` inside the submit handler, in place of the call to `setIsSent`:

```jsx title="src/FeedbackForm.jsx" startLine="11" bad="14"
  return (
    <form onSubmit={e => {
      e.preventDefault();
      const [isSent, setIsSent] = ~useState(true)~; // **WRONG:** a Hook inside an event handler, called when the user clicks Send
    }}>
```

**Beware! The page opens without an error, and the error waits for the click.** Here is what happens, in order:
1. The page opens. The message field and `Send` appear, because the submit handler has not run yet.
2. The user types `Great app` and clicks `Send`.
3. React runs the submit handler for the browser's submit event. No component is rendering at this moment.
4. The handler first stops the browser from reloading the page. Then it calls `useState`, and React throws an error.
5. Nothing calls the setter of the `isSent` at the top of `FeedbackForm`. So the form stays on the page, and `Thank you!` never appears.

```page width=text caption="The form with a Hook inside onSubmit, after the user clicks Send: the form stays, and the thank-you heading never appears."
form:
  textarea:  | Great app | bad
  submit: Send
console: Uncaught Error: Invalid hook call. Hooks can only be called inside of the body of a function component. This could happen for one of the following reasons: 1. You might have mismatching versions of React and the renderer (such as React DOM) 2. You might be breaking the Rules of Hooks 3. You might have more than one copy of React in the same app See https://react.dev/link/invalid-hook-call for tips about how to debug and fix this problem.
```

The `isSent` inside the handler is a new variable of that handler only. It has nothing to do with the `isSent` at the top of `FeedbackForm`. And it never even exists, because the line throws first.

React's message lists three possible reasons. Ours is the second one, breaking the Rules of Hooks. The other two have nothing to do with where our Hooks sit. One is React and React DOM at mismatching versions. The other is two copies of React in one app. React's docs suggest the command `npm ls react` to look for a second copy.

The fix is the form of Principle 3. The Hook goes back to the top level, and the handler only calls its setter with `true`. React's docs say the same in their comment for this case: "to fix, move it outside!"

### The `use` prefix shows where state may hide

The rule has a purpose beyond the crash. React's docs: "By following this rule, you ensure that all stateful logic in a component is clearly visible from its source code."

The naming convention makes that visible. React's docs: "Hook names must start with `use` followed by a capital letter". So a reader of the code can tell at a glance which calls may hold state.

The docs give an example. A call to a function named `getColor` inside your component "can't possibly contain React state inside because its name doesn't start with `use`."

So the prefix is a promise, and it belongs only on functions that call Hooks. Take a function named `useSorted` that calls no Hook, and a function named `getSorted` with the same body. It is the exact same code!

React's docs: "Functions that don't *call* Hooks don't need to *be* Hooks." Name it `getSorted`, and you may even call it inside an `if`, because it is not a Hook.

### The complete project

The entry file mounts `App` inside `<StrictMode>`:

import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(

`App` places the form:

```jsx title="src/App.jsx"
import FeedbackForm from './FeedbackForm.jsx';

export default function App() {
  return ~<FeedbackForm />~; // 2. React calls FeedbackForm next
}
```

`FeedbackForm` calls both Hooks at its top level, and only then decides what to show:

```jsx title="src/FeedbackForm.jsx" good="4,5"
import { useState } from 'react';

export default function FeedbackForm() {
  const [isSent, setIsSent] = ~useState(false)~; // 3. Principles 1 and 3: the 1st Hook call, on every render
  const [message, setMessage] = ~useState('')~; // 4. Principles 2 and 3: the 2nd Hook call, above the first return

  if (~isSent~) { // 5. Principle 4: only now does the condition choose the screen
    return <h1>Thank you!</h1>;
  }

  return (
    <form onSubmit={e => {
      e.preventDefault();
      ~setIsSent(true)~; // 6. Principle 5: the handler calls only the setter
    }}>
      <textarea
        placeholder="Message"
        value={message}
        onChange={e => setMessage(e.target.value)}
      />
      <br />
      <button type="submit">Send</button>
    </form>
  );
}
```

### The order React follows on every render

On every render, React follows the same path. It calls `App`, then `FeedbackForm`. Inside `FeedbackForm`, it meets the two Hooks first, always in the same order, and only then the `if`:

```tree dir=right caption="The order React follows on every render of the feedback form: the components, then the two Hooks, then the condition."
How React renders the feedback form
- +1. `App` [`<FeedbackForm />`] | React calls **`App`**, which returns the form's tag
- +2. `FeedbackForm` | React calls **`FeedbackForm`** on the first render and after every state change
- +3. 1st Hook [`isSent`] | **Always first**: React hands back the stored `isSent`
- +4. 2nd Hook [`message`] | **Always second**: React hands back the stored `message`
- +5. The `if` | Chooses **`Thank you!`** or **the form**; the number of Hook calls stays **two**
```

```page width=text caption="The finished page after the user types Great app and clicks Send."
heading: Thank you!
console: quiet
```

### Where the Hook call sits, and what the user sees

| Where the Hook call sits | What React sees | What the user sees |
| :--- | :--- | :--- |
| **At the top level, above the first `return`** | Two Hook calls on every render | `Thank you!` after Send |
| **Inside `else`, next to the form** | After Send, one Hook call where there were two | A blank page after Send |
| **Inside the `if` that runs after Send** | After Send, more Hook calls than the render before | A blank page after Send |
| **`useEffect` at the top, with the `if` inside the Effect** | One `useEffect` call on every render | The Effect does its work only when the condition is true |
| **At the top of a new component, `MessageForm`** | Each component makes the same calls on its own renders | `Thank you!` after Send |
| **Inside the submit handler** | A Hook call outside any render, when the user clicks Send | The form stays, and `Thank you!` never appears |

One last time, the sentence of this lesson: **React does not know your Hooks by their names. It knows them by their order. So every render must call the same Hooks, in the same order.**

## For the Interview

> **The Interview Question:** Why must hooks be called at the top level, and only from React functions?

### How to Answer Clearly in 30 Seconds

"React does not identify a Hook by its variable name, because no Hook call passes a name. It matches each call to its stored data by its place in the order of Hook calls. So every render must call the exact same Hooks in the exact same order. Two rules keep that order safe:
1. **Only call Hooks at the top level**: never inside a condition, a loop, or a nested function, and never below an early `return`. If a feedback form calls the `useState` for its message inside an `else`, the thank-you render skips it. React throws 'Rendered fewer hooks than expected', and the page goes blank.
2. **Only call Hooks from React functions**: function components and custom Hooks, never event handlers or regular functions. React ties a Hook call to the component it is rendering at that moment, and the `use` prefix shows a reader where state may hide.

When a Hook seems to need a condition, I keep the Hook at the top. I move the condition inside it, into its initial value, or into a new component. The `rules-of-hooks` lint rule catches these mistakes, so I never silence it."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does React use call order instead of names?"**
   Order keeps the syntax short: a call to `useState` needs no key or label. React's docs say Hooks "rely on a stable call order on every render of the same component". This works in practice because the top-level rule keeps the order the same, and the linter catches most mistakes. The cost is the rule itself: a Hook may never be skipped on one render and called on another.
2. **"How do you run an Effect only when a condition is true?"**
   You call `useEffect` on every render and put the `if` inside the Effect function, so the Effect checks `isLoggedIn` before it fetches the user's data. Then you add `isLoggedIn` to the dependency array, so the Effect runs again when the condition changes. Wrapping `useEffect` itself in an `if` changes the number of Hook calls when the user signs in.
3. **"Can anything like a Hook be called inside an `if`?"**
   Yes, `use`. React's docs say `use` "can be called inside conditionals like `if` and loops like `for`", while `useContext` must stay at the top level. `use` is not a Hook, but it still has two limits. It cannot sit inside a `try` and `catch` block, and it must be called inside a component or a Hook. A regular function such as `getSorted` may also be called inside an `if`, because it is not a Hook.

```tree caption="Interview summary: where a Hook call may sit and where it may not."
Where a Hook call may sit
- +At the top level of a function component | **Before any early `return`**, outside every `if`, loop, and nested function | Same Hooks, **same order**, every render
- +At the top level of a custom Hook | A function named **`use` plus a capital letter** | Called by a component at **its own top level**
- !Inside a condition, a loop, or below an early `return` | The number of Hook calls **changes between renders** | React throws **Rendered fewer hooks than expected** or **Rendered more hooks than during the previous render**
- !Inside an event handler or a regular function | Runs **outside any render** | React throws **Invalid hook call**
```
