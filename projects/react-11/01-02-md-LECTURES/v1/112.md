# Lecture 112: How a Form With a Server Function Sends Before JavaScript Loads

*(Why does a form with a Server Function save the email even before JavaScript has loaded?)*

> INTERVIEW QUESTION | ❱ CORE | How do forms work with Server Function actions, and what is progressive enhancement?

---

## VS | A Button `onClick={handleClick}` vs. a Form `action={subscribe}`: both send the email, only the form works before JavaScript loads

> A plain HTML form sends its fields to the server by itself, with no JavaScript at all. **When a form's `action` is a Server Function, React keeps that power: before JavaScript loads, the browser sends the form, and after it loads, React does**. That is why a reader on a slow phone can subscribe the moment the page appears, while a button with a click handler silently loses the tap.

Remember how forms worked before React? You wrote a `<form>` tag with the address of the server in `action`. You gave every input field a `name`. When the user clicked the submit button, the browser collected every named field, sent them to that address, and showed the page the server answered with. Not one line of JavaScript ran.

```html title="Plain HTML: the browser sends the form by itself"
<form ~action="/subscribe"~ method="post"> <!-- The browser sends every named field to this address -->
  <input name="email" />
  <button type="submit">Subscribe</button>
</form>
```

In React, we usually do something else. We keep the email in state, put `onClick` on a button, and call the Server Function from the handler (as seen in Lesson 110). It works, but only once JavaScript runs. The handler is JavaScript. It arrives with the bundle, and React attaches it to the button only when it hydrates the page.

React gives us the old browser power back. **Pass the Server Function itself to the form's `action`:**

```jsx title="React: the same form, with a Server Function in action"
<form ~action={subscribe}~> {/* Before JavaScript loads, the browser sends it; after, React sends it */}
  <input name="email" />
  <button type="submit">Subscribe</button>
</form>
```

You write no address. A Server Function lives on the server. So React writes the form in a way the browser can send it there, and the framework knows which function to run. When the user submits, `subscribe` receives the form's data and reads the email by the field's `name`.

Take a newsletter form at the bottom of a blog post. Someone shares the post in a chat, and a reader opens it on a phone with a slow connection. The server has already sent the HTML, so the post and the form are on the screen. The JavaScript bundle is still downloading. The reader types `john@example.com` and taps `Subscribe`. Ask yourself: does the email reach the server?

**Why:** It depends on who sends it. With the button and its click handler, nobody does. The handler has not arrived yet, so the tap is lost, and the reader closes the page believing they subscribed. With the form, the browser sends it, exactly as in plain HTML, and the server runs `subscribe`. A few seconds later, the bundle loads, and React takes over the same form. From then on, React sends it, and the page no longer loads again.

This has a name: **progressive enhancement**. The page starts from a basic version that works with plain HTML, for everyone, and it gets richer when JavaScript runs. Here it means one form that works twice.

Here is the one sentence to keep in mind for this whole lesson:

**A form whose `action` is a Server Function works twice: before JavaScript loads, the browser sends it, and after hydration, React sends it.**

> [!DEFINITION]
> **Hydration.** [REVIEW] The server sends the HTML of the page first, and the JavaScript bundle arrives later. Hydration is the step where React, once the bundle has loaded, takes the HTML already on the screen and attaches your event handlers to it. Before hydration, the page is plain HTML: the user can see it, scroll it, and type in it, but no handler of yours runs (Lesson 104).

> [!DEFINITION]
> **Server Function.** [REVIEW] A Server Function is an `async` function that runs on the server, and that code in the browser can call like a normal function. It lives in a file that starts with `'use server'`. The browser gets only a reference to it, and a call sends a request to the server (Lesson 110).

> [!DEFINITION]
> **FormData.** [REVIEW] `FormData` is a browser object that holds the fields of a form at the moment it is sent, one entry for each field that has a `name`. You read one field with `get` and its name: `formData.get('email')` returns the text of the field written as `name="email"` (Lesson 40).

> [!DEFINITION]
> **A function in a form's action.** [REVIEW] In React, the `action` prop of a `<form>` can hold a function instead of an address. When the user submits, React calls that function with the form's `FormData`, runs it inside a Transition, and empties the uncontrolled fields after success (Lesson 45).

> [!DEFINITION]
> **Progressive enhancement.** [REVIEW] Progressive enhancement means a page starts from a basic version that works with plain HTML, for everyone, and gets richer when JavaScript runs. A form is the classic case: the browser can send it with no JavaScript, and JavaScript makes it smoother (Lesson 45).

### Where Readers Usually Go Wrong

1. **They think a page on the screen is a page that works.** Before hydration, only what the browser does with plain HTML works (as seen in Lesson 104). Typing in a field works. A click handler does not.
2. **They think a function in `action` always needs JavaScript.** A function from our own code does, because it runs in the browser (as seen in Lesson 45). A Server Function is different. It lives on the server, so the server can run it when the browser sends the form.
3. **They leave `name` off the email field.** The old code read the email from state, so it never needed a name (as seen in Lesson 110). Without a `name`, the browser sends no email at all.

### The One Question to Ask

**For every form, ask: what happens if the user taps before JavaScript loads?** If the answer is "a handler of ours runs", nothing runs, and the tap is lost. If the answer is "the form's `action` is a Server Function", the browser sends the form, and the server saves the data.

**PRINCIPLES:** A form whose `action` is a Server Function works twice: the browser sends it before JavaScript loads, and React sends it after. Four principles follow:
1. **`onClick` and `onSubmit` before hydration: no handler of ours runs, so the email never reaches the server.** A lone button does nothing, and a form with `onSubmit` is sent with GET to an address nobody reads.
2. **`action={subscribe}`: the form calls the Server Function with its `FormData`.** So the Server Function reads the email with `formData.get` and the field's `name`.
3. **`action={subscribe}` before hydration: the browser posts the form itself.** It sends a POST with every named field, the server runs `subscribe`, and the page loads again.
4. **`action={subscribe}` after hydration: React sends the same form without a page load.** It calls `subscribe` inside a Transition, the page stays, and the field empties after success.

## PRINCIPLE | `onClick` and `onSubmit` before hydration: no handler of ours runs, so the email never reaches the server

> [!PRINCIPLE]
> **Principle 1: Before Hydration: No Handler of Ours Runs**
>
> *Before the JavaScript bundle loads, no event handler of ours runs, so a form that sends the email from `onClick` or from `onSubmit` never reaches the Server Function.*
>
> The server's HTML reaches the phone before the bundle. The reader can see the form, type in it, and tap the button, but hydration has not attached our handlers yet. A lone button with `onClick` does nothing. A form with `onSubmit` is sent by the browser's default, GET to the current address, and no code of ours reads that address. Either way, the email never reaches the database.
>
> **DO THIS:**
> ```jsx
> <form ~action={subscribe}~> {/* A real form whose action is the Server Function: the browser can send it before hydration */}
>   <input name="email" />
>   <button type="submit">Subscribe</button>
> </form>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button ~onClick={handleClick}~>Subscribe</button> {/* **WRONG:** before hydration, handleClick is not attached, so the tap sends nothing */}
> ```

### The Button With a Click Handler, on the Slow Phone

Here is the newsletter section we built in Lesson 110, without its pending text and its answer line. The email lives in state, and the click handler calls the Server Function:

```jsx title="src/SubscribeBox.jsx, the version with a click handler"
'use client';

import { useState, useTransition } from 'react';
import { subscribe } from './actions';

export default function SubscribeBox() {
  const [email, setEmail] = useState('');
  const [isPending, startTransition] = useTransition();

  function handleClick() {
    startTransition(async () => {
      await ~subscribe(email)~; // Our handler calls the Server Function with the text in email
    });
  }

  return (
    <section>
      <h2>Get new posts by email</h2>
      <label>
        Your email
        <input value={email} onChange={e => setEmail(e.target.value)} />
      </label>
      <button ~onClick={handleClick}~>Subscribe</button> {/* Hydration attaches handleClick to this button */}
    </section>
  );
}
```

On the developer's laptop, the bundle loads in a blink, and every tap works. On the slow phone, the reader taps `Subscribe` before the bundle arrives, and **nothing is sent to the server**. The screen does not change either:

```page caption="The phone right after the reader taps Subscribe on the version with a click handler, before the bundle has loaded. Nothing has changed."
heading: Park Opens Today
line: The city opened a new park on Main Street.
section: Get new posts by email
form:
  field: Your email | john@example.com
  button: Subscribe | bad
```

**The button is on the screen, but no code of ours is attached to it yet, so the tap is lost.** Here is what happens, in order:
1. The framework renders `SubscribeBox` on the server, and sends its HTML with the rest of the post (as seen in Lesson 102).
2. The phone shows the post, the email field, and the button. The bundle is still downloading, so React has not hydrated the page.
3. The reader types `john@example.com`. The field takes the letters, because typing in an `<input>` field is something the browser does by itself.
4. The reader taps `Subscribe`. Hydration has not attached `handleClick` yet, so no code of ours runs (as seen in Lesson 104).
5. The button sits in no `<form>`, so the browser has nothing to send.
6. A few seconds later, the bundle arrives, and hydration attaches `handleClick`. The earlier tap is already gone, and nothing on the screen says so.

### A Second Surprise: `value={email}` Before Hydration

Look at step 3 again. The field has `value={email}`, and `email` is still an empty string. Yet the letters stay in the field. Why? The `value` prop locks the field to state only while React runs. Before hydration, React is not there to put the empty string back, so the browser keeps what the reader typed (as seen in Lesson 20).

Hydration does not fix this. After it, the field still shows `john@example.com`, but `email` in state is still empty. So if the reader taps again, `handleClick` calls `subscribe` with an empty string.

### VS | A Button Outside a Form vs. a Form With `onSubmit`: both lose the email, in two different ways

A developer who knows forms (as seen in Lesson 11) moves the field inside a `<form>` with `onSubmit`. The handler calls `e.preventDefault()`, and then calls `subscribe`:

```jsx title="The newsletter field inside a form with onSubmit"
function handleSubmit(e) {
  e.preventDefault();
  startTransition(async () => {
    await subscribe(email);
  });
}

<form ~onSubmit={handleSubmit}~> {/* Hydration attaches handleSubmit; before it, the browser's own submit runs */}
  <input name="email" value={email} onChange={e => setEmail(e.target.value)} />
  <button type="submit">Subscribe</button>
</form>
```

Both versions call `subscribe` from a handler, so they look like two versions of the same thing. **They look the same, but they are NOT the same thing!** Before hydration, neither handler runs, so neither one calls `subscribe`. But they fail in two different ways, because the browser can send a form by itself, and it cannot send a lone button:
- **`onClick` on a button outside a form:** the tap does nothing. The page stays as it was.
- **`onSubmit` on a form:** the browser sends the form with its own default. React's docs describe that default: "By default, the browser sends the form data to the current URL and refreshes the page."

> [!DEFINITION]
> **HTTP method: GET and POST.** [NEW] Every request the browser sends to a server has a method, a word that says how the data travels. A form can use two of them. With GET, the browser adds every named field to the end of the address, after a `?`, such as `?email=john%40example.com`. With POST, the browser puts the fields in the request body, the part of the request that carries data outside the address, so the address bar stays clean. A plain form uses GET unless it says `method="post"` (Lesson 112).

That default uses GET. So after the tap, the page loads again, the address bar ends with `?email=john%40example.com`, and the field is empty. Inside an address, the browser writes `@` as `%40`.

The server receives that address, renders the post again, and sends it back. Nothing in our code reads `?email=` from the address, so `subscribe` never runs. The reader sees a page that loaded again with an empty field, and thinks the signup worked.

::: row caption="Two versions tapped before the bundle loads: neither one calls subscribe."
::: col title="onClick on a button outside a form" tag="nothing happens" tone=bad
```page size=mini
section: Get new posts by email
form:
  field: Your email | john@example.com
  button: Subscribe | bad
```
The page does not change. No request leaves the phone.
:::
::: col title="onSubmit on a form" tag="GET to the current URL" tone=bad
```page size=mini
section: Get new posts by email
form:
  field: Your email
  submit: Subscribe | bad
```
The page loads again with `?email=john%40example.com` in the address. And `subscribe` never runs.

:::

React's docs point to the way out in one sentence: a form's `action` "can also be a Server Function, which `onSubmit` does not support." Principle 2 takes that way.

Remember: before hydration, no handler of ours exists on the page. Whatever depends on a handler is lost.

## PRINCIPLE | `action={subscribe}`: the form calls the Server Function with its `FormData`

> [!PRINCIPLE]
> **Principle 2: Form Data: The Form Calls the Server Function With Its FormData**
>
> *When a Server Function is passed to `<form action>`, React calls it with the form's `FormData` as the first argument, so the Server Function reads each field by its `name`.*
>
> With a click handler, our code called `subscribe` and chose its argument. Now the form is the caller. When the reader submits, React collects every field that has a `name` into one `FormData` and hands it to the Server Function. The email field needs a `name` instead of state, so the component can drop its Hooks and stay a Server Component.
>
> **DO THIS:**
> ```js
> export async function subscribe(formData) {
>   const email = ~formData.get('email')~; // Reads the field whose name is email
>   await db.subscribers.add(email);
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> export async function subscribe(~email~) { // **WRONG:** the form passes FormData, so email is not the text the reader typed
>   await db.subscribers.add(email);
> }
> ```

### The Smallest Form With a Server Function

You already know a form whose `action` holds a function of our own (as seen in Lesson 41). Now it holds a Server Function. The form has one field with a `name`, and one submit button:

```jsx title="A form whose action is a Server Function"
<form ~action={subscribe}~> {/* The form calls subscribe when the user submits */}
  <input name="email" />
  <button type="submit">Subscribe</button>
</form>
```

On the server, `subscribe` receives the form's data and reads the email by the field's `name`:

```js title="src/actions.js"
'use server';

import { db } from './db';

export async function subscribe(~formData~) { // React passes the form's FormData here
  const email = ~formData.get('email')~; // The key is the name written on the field
  await db.subscribers.add(email);
}
```

When the reader submits, React collects every named field into one `FormData` object, and calls `subscribe` with it. React's docs say it plainly: "When calling a Server Function in a form, React will supply the form's FormData as the first argument to the Server Function." The key `'email'` is the `name="email"` written on the field (as seen in Lesson 40).

### VS | `subscribe(email)` From a Handler vs. `subscribe(formData)` From a Form: who calls the function decides what it receives

Here is the old call from a click handler, next to the form of this lesson:

```jsx title="Our handler calls subscribe with the email text"
<button onClick={() => ~subscribe(email)~}>Subscribe</button> {/* Our code is the caller, so our code chooses the argument */}
```

```jsx title="The form calls subscribe with FormData"
<form ~action={subscribe}~> {/* The form is the caller, so the argument is the form's FormData */}
  <input name="email" />
  <button type="submit">Subscribe</button>
</form>
```

It looks like the same function with a renamed parameter, **but it is NOT the same thing**! With the click handler, our code calls `subscribe`, so our code chooses the argument: the text in `email`. With the form, no code of ours calls `subscribe`. The form calls it, and a form always passes one `FormData` with every named field.

What about a function of our own in `action`, next to a Server Function in `action`? For the form, **yes, it is the exact same thing**! The same prop, the same `FormData` argument, the same Transition, and the same reset of the fields after success (as seen in Lesson 45). The one difference is where the function runs: in the browser, or on the server.

```tree caption="Who calls subscribe decides what subscribe receives."
Two callers of `subscribe`
- !Our click handler [`onClick`] | **Our code** calls `subscribe` | It passes the **text** in `email`
- +The form [`action={subscribe}`] | **The form** calls `subscribe` on submit | It passes **one `FormData`** with every named field
```

### The Newsletter Form Drops Its State

Now the component file changes. The email travels inside `FormData` by its `name`, so the component no longer needs state. It loses `useState` and `useTransition`. The field loses `value` and `onChange`. The click handler goes away. With no Hooks and no handlers left, the file also loses `'use client'`, and becomes a Server Component (as seen in Lesson 106):

```jsx title="src/SubscribeBox.jsx"
import { subscribe } from './actions';

export default function ~SubscribeBox~() { // No directive: a Server Component
  return (
    <section>
      <h2>Get new posts by email</h2>
      <form ~action={subscribe}~> {/* The form calls subscribe with its FormData */}
        <label>
          Your email
          <input ~name="email"~ /> {/* The key of this field inside FormData */}
        </label>
        <button type="submit">Subscribe</button>
      </form>
    </section>
  );
}
```

The email field is now an uncontrolled field (as seen in Lesson 20). The browser keeps what the reader types, and the form reads it at the moment the reader submits. The database file and the app file do not change.

### The Mistake: Passing the Old `subscribe(email)` to the Form

A developer moves the call into the form, but keeps the Server Function that took the email text:

```js title="src/actions.js"
export async function subscribe(~email~) { // **WRONG:** the form passes FormData, so email holds a FormData object, not john@example.com
  await db.subscribers.add(email);
}
```

The parameter is still called `email`, but the form puts a `FormData` object in it. So `db.subscribers.add` receives that whole object instead of the text `john@example.com`. The database never gets the reader's email, and no error says so. The fix: name the parameter `formData`, and read the field inside with `formData.get('email')`.

Remember: the caller chooses the argument. When the form is the caller, the argument is `FormData`.

## PRINCIPLE | `action={subscribe}` before hydration: the browser posts the form itself

> [!PRINCIPLE]
> **Principle 3: Progressive Enhancement: The Browser Posts the Form Before JavaScript Loads**
>
> *When a server-rendered form has a Server Function as its `action`, the reader can submit it before the bundle loads: the browser sends a POST with every named field, the server runs the Server Function, and the page loads again.*
>
> Sending a form is something the browser does with plain HTML. A Server Function lives on the server, so the browser can reach it with an ordinary POST, and no JavaScript on the phone is needed. React makes the request POST whatever `method` says, and the framework tells the server which function to run. Every field the Server Function reads must have a `name`, because the browser sends nothing else.
>
> **DO THIS:**
> ```jsx
> <form action={subscribe}>
>   <input ~name="email"~ /> {/* The browser sends email=john@example.com in the POST */}
>   <button type="submit">Subscribe</button>
> </form>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <form action={subscribe}>
>   <input ~placeholder="Email"~ /> {/* **WRONG:** no name, so the POST carries no email and formData.get returns null */}
>   <button type="submit">Subscribe</button>
> </form>
> ```

### The Same Tap on the Slow Phone, Now With the Form

**With a Server Function in `action`, the form works on the slow phone before any JavaScript runs: the browser sends it, and the server runs `subscribe`.** No code of ours changes for this. We take the form of Principle 2, and the reader taps before the bundle loads.

Here is what happens, in order:
1. The framework renders `SubscribeBox` on the server. Because `action` holds a Server Function, React writes the HTML form so that the browser can send it to the server.
2. The phone shows the post and the form. The bundle is still downloading.
3. The reader types `john@example.com` and taps `Subscribe`.
4. The button is a submit button inside a `<form>`, so the browser submits the form by itself. No JavaScript is needed for that.
5. The browser sends a **POST** request with every field that has a name. That is the email field, with the value `john@example.com`, and a hidden field that React added to point at `subscribe`.
6. On the server, the framework calls `subscribe` with a `FormData` that holds the email, and the email is saved.
7. The browser then shows the page the server answers with: the same post, with an empty field. React's docs call this step navigating, and by default the browser stays at "the current page's URL".

```page caption="The phone after the reader taps Subscribe on the form before the bundle loads. The page has loaded again, and the email is saved on the server."
heading: Park Opens Today
line: The city opened a new park on Main Street.
section: Get new posts by email
form:
  field: Your email
  submit: Subscribe | good
```

React's docs name this exact case: "By passing a Server Function to the form `action`, React can progressively enhance the form. This means that forms can be submitted before the JavaScript bundle is loaded." They also name who it helps: "users who have a slow connection, device, or have JavaScript disabled."

### VS | GET vs. POST: where the browser puts the email

In Principle 1, the browser sent the form with `onSubmit` using GET. It sends this form using POST. Both carry every named field. The one difference is where the browser puts those fields:
- **With GET**, MDN says the form data is "appended to the `action` URL with a `?` separator". That is the `?email=john%40example.com` of Principle 1.
- **With POST**, MDN says the form data is "sent as the request body". So the address bar stays clean.

Our code never writes `method="post"`. React makes the request POST by itself. React's docs: "When a function is passed to action or formAction the HTTP method will be POST regardless of value of the method prop."

```tree caption="The two HTTP methods a form can use, and where each one puts the email."
Where the browser puts `email`
- !GET, the browser's default [`?email=`] | The fields go **into the address** after a `?` | The form with `onSubmit` in Principle 1
- +POST, chosen by React [`action={subscribe}`] | The fields go **into the request body** | This form, whatever `method` says
```

The server also has to know that this POST is meant for `subscribe`. So when React renders the form on the server, it adds a hidden field that holds a reference to `subscribe`. The browser sends that field together with the email, and the framework reads it to know which function to call (as seen in Lesson 107). React's docs do not describe the exact shape of that reference, so we leave it to the framework.

### The Mistake: an Email Field With No `name`

A developer copies the email field that kept its text in state, deletes the `value` and the `onChange`, but writes no name:

```jsx title="src/SubscribeBox.jsx" startLine="10"
<input ~placeholder="Email"~ /> {/* **WRONG:** no name, so the form sends no email field */}
```

The browser sends only fields that have a `name` (as seen in Lesson 45). So before hydration, the POST carries no email. After hydration, React builds `FormData` from the same fields, and finds no email either. Either way, `formData.get('email')` returns `null`. So `subscribe` saves null instead of the reader's email. The fix is one attribute: `name="email"`.

Remember: before JavaScript loads, the form is plain HTML, and plain HTML sends only named fields.

## PRINCIPLE | `action={subscribe}` after hydration: React sends the same form without a page load

> [!PRINCIPLE]
> **Principle 4: Hydration: React Sends the Same Form Without a Page Load**
>
> *Once the page is hydrated, React sends the same form: it calls the Server Function with a network request inside a Transition, the page does not load again, and the field is reset after success.*
>
> Before hydration, the browser sends the form, and the whole page loads again. After hydration, React stops the browser's own submit, builds the `FormData`, and calls the Server Function with a network request. The same `subscribe` runs on the server both times. That is progressive enhancement: one form that works as plain HTML first, and becomes smoother when JavaScript runs.
>
> **DO THIS:**
> ```jsx
> <form ~action={subscribe}~> {/* React sends it after hydration; the browser sends it before */}
>   <input name="email" />
>   <button type="submit">Subscribe</button>
> </form>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <form ~onSubmit={handleSubmit}~> {/* **WRONG:** works on a fast laptop, but before hydration the browser sends GET and subscribe never runs */}
>   <input name="email" />
>   <button type="submit">Subscribe</button>
> </form>
> ```

### The Same Form, Tapped Before and After Hydration

Now the bundle has arrived, and React has hydrated the page. The reader types `john@example.com` again and taps `Subscribe`. The code is the same form of Principle 2. What changes is who sends it: the browser before hydration, React after it.

Compare the two taps:
- **For the server, yes, it is the exact same thing!** Both taps send the named fields, and the same `subscribe` runs with the same `FormData`.
- **For the reader, it is NOT the same thing!** Before hydration, the whole page loads again. After hydration, the page stays where it is, and only the field empties.

```tree caption="The same form tapped before hydration and after hydration: the same Server Function runs, but the reader sees two different things."
One form, two taps on `Subscribe`
- +Before hydration | **The browser** sends a POST | `subscribe` runs | **The whole page loads again**
- +After hydration | **React** sends a network request inside a Transition | `subscribe` runs | **The page stays**; the field empties after success
```

**After hydration, React takes the submit away from the browser and sends the form itself, so the page never loads again.** Here is what happens, in order:
1. The bundle loads, and React hydrates the page (as seen in Lesson 104).
2. The reader types `john@example.com` and taps `Subscribe`.
3. React handles the submit itself, so the browser does not send the form, and the page does not load again. React's docs: with `action`, "calling `e.preventDefault()` isn't needed".
4. React calls `subscribe` with the form's `FormData`. Because `subscribe` is a Server Function, that call is a network request to the server (as seen in Lesson 110).
5. The call runs inside a Transition. React's docs: Server Functions passed to `<form action>` "will automatically be called in a transition." So we write no `startTransition` here, unlike in the click handler.
6. On the server, `subscribe` saves the email, exactly as in Principle 3.
7. The call succeeds, and React empties the field, because it is an uncontrolled field (as seen in Lesson 45).

```page caption="The page after the reader taps Subscribe once React has hydrated it. The page did not load again, and the field is empty."
heading: Park Opens Today
line: The city opened a new park on Main Street.
section: Get new posts by email
form:
  field: Your email
  submit: Subscribe | good
```

There are not two versions of the form, one for no JavaScript and one for JavaScript. There is one form and one Server Function. Hydration only changes who sends the form.

### VS | `onSubmit` vs. `action={subscribe}` After Hydration: both save the email, only `action` does the extra work for you

Once the bundle has loaded, the form with `onSubmit` from Principle 1 works too. Its handler runs, calls `e.preventDefault()`, and calls `subscribe`. So after hydration, both forms save the email, and neither page loads again. **But they are NOT the same thing in the code!** With `onSubmit`, our code must do three jobs by hand:
1. Stop the browser's own submit, with `e.preventDefault()`.
2. Start the Transition, with `startTransition`.
3. Empty the field after success. This handler never does it, so `john@example.com` stays in the field after the tap.

With `action`, React does all three. And only the form with `action` also works before the bundle loads.

```tree caption="After hydration, both forms save the email without a page load, but only action also works before hydration."
Two forms after hydration
- !`onSubmit` with `e.preventDefault` [`handleSubmit`] | Our code **stops the browser** and **starts the Transition** | Before hydration: **GET, nothing saved**
- +`action={subscribe}` | **React** stops the browser and starts the Transition | Before hydration: **POST, email saved**
```

### The Mistake: Testing Only on a Fast Laptop

On the developer's laptop, the bundle loads at once. Every tap comes after hydration, so the page never loads again, and the developer never sees the path without JavaScript. Then, to style the button, the developer turns the component back into a Client Component, and swaps the submit button for a `<div>` with a click handler:

```jsx title="A styled div in place of the submit button"
<div className="button" ~onClick={sendForm}~>Subscribe</div> {/* **WRONG:** before hydration, a div has no handler and cannot submit the form */}
```

On the laptop, nothing looks different. On the slow phone, the reader taps the `<div>` before the bundle loads, and nothing is sent, exactly as in Principle 1. So test the slow path on purpose. Turn JavaScript off in the browser's developer tools, or slow the network down in the Network panel. Then tap `Subscribe` again.

Remember: one form, two senders. Before hydration, the browser sends it. After hydration, React sends it. The same Server Function runs both times.

## All 4 Principles Together

### The Complete Code

The database stand-in, unchanged from Lesson 110:

```js title="src/db.js"
const subscribers = [];

export const db = {
  subscribers: {
    async add(email) {
      subscribers.push(email);
    },
  },
};
```

The actions file holds the Server Function, which now reads the email from the form data:

```js title="src/actions.js"
~'use server'~; // Every export becomes a Server Function

import { db } from './db';

export async function subscribe(~formData~) { // Principle 2: the form passes its FormData
  const email = formData.get('email');
  await db.subscribers.add(email);
}
```

The newsletter component is now a Server Component that renders a real form:

```jsx title="src/SubscribeBox.jsx"
import { subscribe } from './actions';

export default function ~SubscribeBox~() { // No directive: a Server Component
  return (
    <section>
      <h2>Get new posts by email</h2>
      <form ~action={subscribe}~> {/* Principles 3 and 4: the browser sends it before hydration, React after */}
        <label>
          Your email
          <input ~name="email"~ /> {/* Principle 3: without a name, no email is sent */}
        </label>
        <button type="submit">Subscribe</button>
      </form>
    </section>
  );
}
```

The app file renders the post and the form, unchanged:

```jsx title="src/App.jsx"
import SubscribeBox from './SubscribeBox';

export default function ~App~() { // No directive: a Server Component
  return (
    <main>
      <h1>Park Opens Today</h1>
      <p>The city opened a new park on Main Street.</p>
      <SubscribeBox />
    </main>
  );
}
```

### The Order in Which Things Run

```tree dir=right caption="The order in which the components and the Server Function run, for a tap before hydration and for a tap after it."
From the server HTML to the saved email
- +1. On the server [`App` `SubscribeBox`] | The framework renders both **Server Components** to HTML | The form carries a **reference** to `subscribe`
- +2a. Tap before hydration | **The browser** sends a POST with `email` | The framework runs **`subscribe`**; the **page loads again**
- +2b. Tap after hydration | **React** sends a network request inside a **Transition** | `subscribe` runs; the **page stays** and the field **empties**
```

### Summary

| Aspect | What a Developer Might Expect | What React Does |
| :--- | :--- | :--- |
| **The page before hydration** | The form is on the screen, so it works | Only plain HTML works; our `onClick` and `onSubmit` handlers are not attached yet |
| **A form with `onSubmit`** | Calls `subscribe` on every tap | Before hydration, the browser sends GET to the current address, and `subscribe` never runs |
| **The argument of `subscribe`** | The email text, as with the click handler | One `FormData` with every named field, read with `formData.get('email')` |
| **The method** | GET, the browser's default | POST, whatever `method` says, because a function is in `action` |
| **The email field** | Needs state, `value`, and `onChange` | Needs only `name`; the component can stay a Server Component |
| **The tap before hydration** | Needs JavaScript, like any function in `action` | The browser posts the form, the server runs `subscribe`, and the page loads again |
| **The tap after hydration** | A second version of the form | The same form: React sends a network request in a Transition, and the page stays |

Remember the one sentence of this lesson. **A form whose `action` is a Server Function works twice: before JavaScript loads, the browser sends it, and after hydration, React sends it.**

## For the Interview

> **The Interview Question:** How do forms work with Server Function actions, and what is progressive enhancement?

### How to Answer Clearly in 30 Seconds

"We pass a Server Function, a function from a `'use server'` file, to a form's `action` prop. When the user submits, React calls it with the form's `FormData` as the first argument, so the function reads each field by its `name`. React's docs used to call these Server Actions. The form is progressively enhanced, which means it works twice:
1. **Before the JavaScript bundle loads**, the form is plain HTML. The browser sends a POST with every named field, the server runs the Server Function, and the page loads again.
2. **After hydration**, React sends the same form with a network request inside a Transition. The page does not load again, and the uncontrolled fields are reset after success.

The same Server Function runs on the server both times. A button with `onClick`, or a form with `onSubmit` and `e.preventDefault()`, does nothing useful before hydration."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What exactly does the browser send when no JavaScript has run?"**
   A POST request to the server. React makes it POST whenever a function is in `action`, whatever the `method` prop says. The request carries every field of the form that has a `name`, so a field with no `name` sends nothing. Anything the user does not type, such as the ID of the post, must travel in a hidden field. Another way is to add it to the Server Function with `bind`. Either way, it is already in the HTML, because no JavaScript runs to add it:

   ```jsx title="The ID of the post in a hidden field"
   <input ~type="hidden"~ name="postId" value={postId} /> {/* The browser sends postId with the email, even before hydration */}
   ```

   After the POST, the browser shows the page the server answers with, by default at the current URL.

2. **"Why not keep `onSubmit` with `e.preventDefault()` and call the Server Function from the handler?"**
   Because the handler exists only after hydration. Before it, the browser runs its default: it sends the form with GET to the current URL and refreshes the page, and the Server Function never runs. React's docs say an `action` "can also be a Server Function, which `onSubmit` does not support." With `action`, React stops the page load and starts the Transition for us after hydration, and the browser can still send the form before it.

3. **"Can the user see a success or error message before JavaScript loads?"**
   Not with a bare `action`. A message from the Server Function needs `useActionState` (Lesson 113), and a pending text needs `useFormStatus` (Lesson 114). With `useActionState`, React can show the server's answer even when the form is sent before hydration. It also replays submits made before hydration finishes (Lesson 137). Its `permalink` argument picks the URL the browser goes to when the form is sent without JavaScript. And since anyone can send that POST, the Server Function must check the form data on the server as untrusted input (Lessons 130 and 162).

```tree dir=right caption="Interview comparison: one form, two senders, the same Server Function."
A form with `action={subscribe}`
- +Before hydration [The browser] | Sends a **POST** with every named field | The server runs `subscribe`; the **page loads again**
- +After hydration [React] | Sends a **network request** inside a Transition | The server runs `subscribe`; the **page stays** and the fields **reset**
```
