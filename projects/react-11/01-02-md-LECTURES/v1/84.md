# Lecture 84: Starting the Font, the Stylesheet, and the Servers Early with preload, preinit, preconnect, and prefetchDNS

*(How does a component tell the browser to start a file, or a server, before the page asks for it?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How do preload, preinit, preconnect, and prefetchDNS speed up asset loading?

---

## VS | The Browser Finds the File by Itself vs. a Hint from `react-dom`: one starts late, the other starts now

> The browser downloads a file only when it reaches the line that names it, so a font named inside a stylesheet starts late. **React 19 lets your component tell the browser earlier, with four calls from react-dom: preload, preinit, preconnect, and prefetchDNS**. The finished page looks exactly the same, but it gets there sooner, because the browser started the work before anyone asked.

Remember how the browser reads an HTML page: from top to bottom. When it meets a stylesheet link, it starts downloading the stylesheet. When it meets an `<img>` tag, it starts downloading the picture. **The browser cannot download a file it has not met yet.**

Most of the time, that is fine. But sometimes your code knows more than the browser does. There are two common cases:
1. **A file named inside another file.** A font is usually named inside a stylesheet, in a CSS rule. The browser learns about the font only after it has downloaded the stylesheet and read it.
2. **A server your code calls later.** A `fetch` inside an Effect runs only after React has put the page on the screen (Lesson 32). Until then, the browser has no idea that server exists.

Take a weather page on a slow train connection. It shows the city Paris in the app's own font, the temperature 18°, and a **Show forecast** button. Ask yourself: our component knew from its first line that it needs the font and the weather server. So why does the browser start both of them so late? Because nobody told the browser. React 19 gives us four calls that tell it.

**Why:** Without these calls, the user waits for nothing. Paris shows in a plain font and then jumps to the app's font. The temperature line stays empty while the rest of the page is already there. The four calls change none of what the page shows. They only make the browser start sooner.

### The Four Calls in Four Lines

All four calls are named imports from `react-dom`, not from `react`:

```jsx title="The four calls that tell the browser about a resource early"
import { preload, preinit, preconnect, prefetchDNS } from 'react-dom';

~preload~('/fonts/brand.woff2', { as: 'font' }); // 1. Start downloading a file
~preinit~('/forecast.css', { as: 'style', precedence: 'default' }); // 2. Download a stylesheet and put it into use
~preconnect~('https://api.example.com'); // 3. Open a connection to a server
~prefetchDNS~('https://cdn.example.com'); // 4. Only look up the address of a server
```

Read the four comments from top to bottom. Each call asks the browser to go a little less far:
1. **`preload`** downloads a file, and stops there.
2. **`preinit`** downloads a stylesheet or a script, and also puts it into use.
3. **`preconnect`** downloads nothing. It only opens the connection to a server.
4. **`prefetchDNS`** downloads nothing and opens nothing. It only looks up where the server is.

> [!DEFINITION]
> **What is a resource?** [NEW] A resource is anything the page loads from the network: a stylesheet, a font, a script, an image, or the server they come from.
> The React docs use this word for all four calls. `preload` and `preinit` take a file. `preconnect` and `prefetchDNS` take a server (Lesson 84).

> [!DEFINITION]
> **What is a hint?** [NEW] A hint is a piece of advice to the browser. The call says what is coming, and the browser decides whether to act on it.
> The React docs say each of the four calls "provides the browser with a hint". For the two server calls they add: "If the browser chooses to do so, this can speed up the loading of resources from that server."
> So a hint never breaks the page. If the browser ignores it, the page loads exactly as it would without it, only later (Lesson 84).

### You could already write these hints in HTML

Remember the `<head>` of `index.html`? You have written stylesheet links there. HTML has had links for hints too, for years:

```html title="index.html"
<link ~rel="preload"~ as="font" href="/fonts/brand.woff2" crossorigin /> <!-- Start the font now -->
<link ~rel="preconnect"~ href="https://api.example.com" /> <!-- Open the connection now -->
<link ~rel="dns-prefetch"~ href="https://cdn.example.com" /> <!-- Look up the address now -->
```

The React calls write these same links into the `<head>` for you. The one difference is who decides when. A link in `index.html` is in every page that loads that file. A call in a component runs only when that component renders, so the hint travels with the component that needs the resource.

So a developer has three ways to start a resource early:
1. **Write the link by hand in `index.html`.** It fits files that every page of the site needs.
2. **Call one of the four from the component that needs the resource.** It fits resources that depend on what renders, or on what the user is about to do. This is what this lesson teaches.
3. **Let the framework do it.** The React docs say: "React-based frameworks frequently handle resource loading for you, so you might not have to call this API yourself" (Lesson 46).

### They are not an import

Something that can be tricky: these calls look like they bring a file into the page, the way an `import` brings in code. Three of the four do not. They only prepare:
1. `preload` downloads a file, but does not apply it.
2. `preconnect` and `prefetchDNS` download nothing at all. They only prepare the way to a server.
3. Only `preinit` puts a stylesheet or a script into use.

All four return nothing, and none of them puts anything on the screen.

### The Rule of Thumb: how far must the browser go before the page needs it?

**Ask one question about every resource: how far should the browser go before the page needs it? Then pick the call that goes exactly that far.**

```tree caption="The four calls from react-dom and how far each one asks the browser to go before the page needs the resource."
Four hints a component can give the browser early
- +`preload` [`as`] | **Downloads** a file we know we will use | Puts nothing into use
- +`preinit` [`as` `precedence`] | **Downloads and puts into use** a stylesheet or a script | A script runs, a stylesheet applies
- +`preconnect` [`href`] | **Opens a connection** to another server | Downloads no file
- +`prefetchDNS` [`href`] | **Looks up only the address** of a server | Opens no connection and downloads no file
```

A senior developer also knows the classic mistakes:
1. **`preload` for a stylesheet that must apply.** The file downloads, and the styles never apply.
2. **`preconnect` to your own site.** The browser is already connected to it, so nothing gets faster.
3. **`preconnect` to every outside server.** Each unused connection still costs the browser work.
4. **A hint inside an Effect.** It is the latest moment to start a download.

The rest of the lesson shows each one on a real weather page.

## SECTION | A Weather Page on a Slow Connection

Our page shows the city, the temperature, and a button:

```page width=text caption="The weather page once every file and the temperature have arrived."
heading: Paris
line: 18°
line: [Show forecast]
console: quiet
```

On a slow connection, this page often arrives in pieces:
1. Paris first shows in a plain font. A moment later it jumps to the app's font.
2. The temperature line stays empty while the rest of the page is already there.
3. After a click on **Show forecast**, the three forecast days can flash as a plain list before their styles arrive.

The project has one component for the page and one for the forecast panel. The stylesheets and the font sit in the `public` folder. Vite serves that folder as it is, so the stylesheet in that folder is reachable at the address `/brand.css`:

```files title="weather-app: File Explorer" caption="The project files of the weather page, with the stylesheets and the font in public/."
index.html | entry | The HTML page with the head and the empty root div
public/
  brand.css | stylesheet | Names the font Brand and gives it to the h1
  forecast.css | stylesheet | Lays out the three forecast days in one row
  fonts/
    brand.woff2 | font file | The app's own font
src/
  main.jsx | boundary | Renders `<WeatherPage />` into `#root`
  WeatherPage.jsx | parent | Shows the city, the temperature, and the Show forecast button
  ForecastPanel.jsx | child | Shows the three days with a sun icon each
```

The page itself comes from our own site, `https://weather.example.com`. It also talks to two other servers:
1. **The weather server**, `https://api.example.com`, sends the temperature.
2. **The icon server**, `https://cdn.example.com`, sends the sun icon of each forecast day.

Here is the stylesheet that names our font. The font file appears only inside the `@font-face` rule:

```css title="public/brand.css"
@font-face {
  font-family: 'Brand';
  src: ~url('/fonts/brand.woff2')~; /* The only place the font file is named */
  font-display: swap;
}

h1 {
  font-family: 'Brand';
}
```

The line `font-display: swap` tells the browser what to do while it waits. It shows the text in a plain font first, and swaps in the app's font when the file arrives.

> [!DEFINITION]
> **What is the Network panel?** [NEW] The Network panel is the tab of the browser's developer tools that lists every file the browser downloads, and the moment each download starts.
> On your own machine, every file arrives almost at once. So you turn on the panel's slow network setting, which MDN calls network throttling. The browser slows its own connection on purpose, and you can see the order of the downloads.
> The Elements panel, next to it, shows the `<head>` where React puts the links these hints create (Lesson 01).

Now we fix the three delays, one call at a time:

**PRINCIPLES:** Each of the four calls starts one resource of the weather page early, and the fifth principle says where to call them:
1. **`preload` starts the font early.** The font is named inside the stylesheet, so the browser finds it late. `preload` tells the browser to start it now.
2. **`preinit` applies a stylesheet, `preload` only downloads it.** For the forecast panel, the styles must apply, not only arrive.
3. **`preconnect` opens the connection to the weather server before the fetch.** The connection opens while React is still rendering.
4. **`prefetchDNS` only looks up the icon server's address.** The icons are needed only after a click, so a full connection may be wasted.
5. **A click handler starts the forecast stylesheet before the panel renders.** In the handler, the call runs earlier than in the panel.

## PRINCIPLE | `preload`: the font starts downloading next to the stylesheet, not after it

> [!PRINCIPLE]
> **Principle 1: preload: Start a File You Know You Will Use Before Anything Names It**
>
> *Call `preload(href, { as })` during render to tell the browser to start downloading a file now; `as` is required, and equivalent calls with the same `href` count as one.*
>
> The browser starts a file only when it finds the tag or the CSS rule that names it. So a font named inside a stylesheet starts only after that stylesheet is downloaded and read. `preload` tells the browser to start the font right away. It returns nothing and applies nothing. The font is still used only when the stylesheet asks for it, but by then it is already on its way.
>
> **DO THIS:**
> ```jsx
> function WeatherPage() {
>   ~preload('/fonts/brand.woff2', { as: 'font' })~; // The font starts next to brand.css, not after it
>   return <link rel="stylesheet" href="/brand.css" precedence="default" />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function WeatherPage() {
>   ~preload('/brand.css', { as: 'style' })~; // **WRONG:** the font inside brand.css is still found late
>   return <link rel="stylesheet" href="/brand.css" precedence="default" />;
> }
> ```

Here is `preload` in its smallest form, one import and one line:

```jsx title="The smallest preload"
import { ~preload~ } from 'react-dom'; // A named import from react-dom, not from react

function WeatherPage() {
  ~preload('/fonts/brand.woff2', { as: 'font' })~; // Tells the browser to start downloading the font now
  return <h1>Paris</h1>;
}
```

The React docs say `preload` "lets you eagerly fetch a resource such as a stylesheet, font, or external script that you expect to use". To fetch eagerly means to start before anyone asks for the file. Here, nobody has asked for the font yet. The browser has not even read the stylesheet.

The call takes two things:
1. **The address of the file**, here the font file `brand.woff2` in the `fonts` folder.
2. **`as`**, a required string that names the kind of file: font, style, script, image, or fetch.

Why does the browser need `as`? It is the same `as` attribute that HTML puts on a preload link. MDN says the browser uses it to give the download the right priority. It also uses it to match the downloaded file with the request that needs it later.

### VS | The preload link by hand vs. the `preload` call: the same link, written at a different moment

Compare the link you write by hand with the call in the component:

```html title="index.html"
<link ~rel="preload" as="font"~ href="/fonts/brand.woff2" crossorigin /> <!-- In the head of every page that loads index.html -->
```

```jsx title="src/WeatherPage.jsx"
~preload('/fonts/brand.woff2', { as: 'font' })~; // React adds the same link when WeatherPage renders
```

Yes, it is the exact same thing! The React 19 announcement shows that a `preload` call ends up as a preload link in the `<head>`.

Look at `crossorigin` on the link written by hand. MDN says the browser fetches every font in a special mode. A font preload without `crossorigin` does not match that request, so the browser downloads the font a second time. The `preload` call adds `crossorigin` to a font link by itself, so you cannot forget it.

### Why the font starts late without preload

**Without `preload`, the browser finds the font only at the end of a chain:**
1. The browser finds the stylesheet link for `brand.css` and starts downloading it.
2. When the stylesheet arrives, the browser reads it and finds the font inside the `@font-face` rule.
3. Only now does the browser start downloading `brand.woff2`.
4. Until the font arrives, `font-display: swap` shows Paris in a plain font. Then the title jumps to the app's font.

The React docs give this exact case. Preload the stylesheet, and also the fonts it names. "That way, the browser can start downloading the font before it's downloaded and parsed the stylesheet."

```tree dir=right caption="When the browser starts brand.woff2 without preload and with preload, on a slow network setting."
When the font download starts
- !Without `preload` | The browser downloads `brand.css` **first** | It reads the CSS rule and **only then** starts `brand.woff2` | Paris shows in a plain font, **then changes**
- +With `preload` [`as: 'font'`] | `WeatherPage` renders and **gives the hint at once** | The font downloads **next to** `brand.css`, not after it | Paris can show in the app's font **sooner**
```

### The weather page, step 1: the title, its stylesheet, and the font

`WeatherPage` renders the stylesheet link with `precedence` (Lesson 83) and the city name. At the top, it calls `preload` for the font that the stylesheet names:

```jsx title="src/WeatherPage.jsx"
import { preload } from 'react-dom';

export default function WeatherPage() {
  ~preload('/fonts/brand.woff2', { as: 'font' })~; // Starts the font before brand.css is read
  return (
    <main>
      <link rel="stylesheet" href="/brand.css" precedence="default" />
      <h1>Paris</h1>
    </main>
  );
}
```

The name `Brand` comes from our own CSS, not from React. The `preload` call never mentions it. It only names the file.

Open the Elements panel. The `<head>` now holds a preload link for the font. It also holds a preload link for the stylesheet, which React adds by itself, because the stylesheet link is in our JSX. What React cannot see is the font, because only the CSS inside the stylesheet names it:

```dom caption="What the Elements panel shows in the head after WeatherPage renders with the preload call."
<head>
  <link rel="stylesheet" href="/brand.css" data-precedence="default">
  <title>Weather</title>
  ...
+ <link rel="preload" href="/fonts/brand.woff2" as="font" crossorigin=""> | note: Added by the preload call
  <link rel="preload" as="style" href="/brand.css"> | note: Added by React for the stylesheet link
</head>
```

`preload` returns nothing, and it puts nothing on the page. Its only traces are this link in the `<head>` and the font request in the Network panel. That request now starts next to the stylesheet, not after it.

### Every render calls preload, and the head still holds one link

Later in this lesson, the user clicks **Show forecast**, and `WeatherPage` renders again. The `preload` line runs again with the same address. React adds no second link.

The React docs: "Multiple equivalent calls to `preload` have the same effect as a single call." Two calls are equivalent when they name the same `href`. For an image, they must also have the same image options. So calling `preload` on every render is fine: only the first call does anything.

### Preloading the stylesheet and forgetting its font

Developers often stop one step short:
1. A developer learns that `preload` makes pages faster.
2. They preload the stylesheet, with `as: 'style'`.
3. They do not preload the font that the stylesheet names.
4. On our page, that line adds nothing. React already starts the stylesheet early, because of the stylesheet link.
5. The browser still finds the font only after reading the stylesheet, so the title still jumps late.

The React docs: "If you preload a stylesheet, it's smart to also preload any fonts that the stylesheet refers to."

Remember: the browser starts a file only when something names it. `preload` names it first.

## PRINCIPLE | `preinit`: the stylesheet downloads and its styles apply, `preload` only downloads

> [!PRINCIPLE]
> **Principle 2: preinit: Download a Stylesheet or Script and Put It into Use**
>
> *Use `preinit(href, { as: 'style', precedence })` when a stylesheet must apply, and `preinit(href, { as: 'script' })` when a script must run; `preload` only downloads.*
>
> `preload` and `preinit` both start the download now. When the file arrives, `preload` stops there: the stylesheet is downloaded but not inserted, so its styles never apply. `preinit` also puts the file into use. A script runs as soon as it arrives, and a stylesheet is inserted into the document next to the other stylesheets of the same `precedence`.
>
> **DO THIS:**
> ```jsx
> function ForecastPanel() {
>   ~preinit('/forecast.css', { as: 'style', precedence: 'default' })~; // Downloaded and inserted: the days are styled
>   return <ul className="forecast">...</ul>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ForecastPanel() {
>   ~preload('/forecast.css', { as: 'style' })~; // **WRONG:** downloaded but never inserted, so the days show unstyled
>   return <ul className="forecast">...</ul>;
> }
> ```

### VS | `preload` vs. `preinit` for the same stylesheet: both download it, only one applies it

Here are the two calls for the forecast panel's stylesheet:

```jsx title="The same stylesheet given to preload and to preinit"
~preload~('/forecast.css', { as: 'style' }); // Downloads forecast.css: the panel still shows without its styles
~preinit~('/forecast.css', { as: 'style', precedence: 'default' }); // Downloads forecast.css and inserts it: the styles apply
```

It may look the same, or work the same at first, but it is NOT the same thing! Both lines download the very same file, and the Network panel shows `forecast.css` arrive in both cases. Only `preinit` makes the styles apply.

The React docs say `preinit` "lets you eagerly fetch and evaluate a stylesheet or external script". To evaluate a file means to put it into use. The docs say what that means for each kind of file: "Scripts that you `preinit` are executed when they finish downloading. Stylesheets that you preinit are inserted into the document, which causes them to go into effect right away."

So `preinit` accepts only two kinds of file in `as`: script and style.

> [!DEFINITION]
> **What is precedence?** [REVIEW] `precedence` is the prop you put on a stylesheet link so React decides where to insert it among the other stylesheets (Lesson 83).
> A stylesheet given to `preinit` needs it too. The React docs say it is "Required with stylesheets. Says where to insert the stylesheet relative to others."
> Stylesheets with the same `precedence` go together, whether they come from a link tag or from `preinit` (Lesson 83).

```tree caption="What preload and preinit do with forecast.css once the file has arrived."
Two calls that download `forecast.css`
- !`preload` [`as: 'style'`] | **Downloads** the file | Inserts **no stylesheet**, so the forecast days show **without styles**
- +`preinit` [`as: 'style'` `precedence: 'default'`] | **Downloads** the file | **Inserts** it into the document, so the styles **apply right away**
```

### The weather page, step 2: the Show forecast button and the panel

`WeatherPage` gets a `showForecast` state variable and a **Show forecast** button. When `showForecast` is true, it renders the forecast panel:

```jsx title="src/WeatherPage.jsx" startLine="1"
import { useState } from 'react';
import { preload } from 'react-dom';
import ForecastPanel from './ForecastPanel.jsx';

export default function WeatherPage() {
  const [showForecast, setShowForecast] = useState(false);
  preload('/fonts/brand.woff2', { as: 'font' });
  return (
    <main>
      <link rel="stylesheet" href="/brand.css" precedence="default" />
      <h1>Paris</h1>
      <button onClick={() => setShowForecast(true)}>Show forecast</button>
      ~{showForecast && <ForecastPanel />}~ {/* The panel renders only after the click */}
    </main>
  );
}
```

The forecast panel needs its own stylesheet, and nothing else on the page uses it. So the panel itself calls `preinit` for it:

```jsx title="src/ForecastPanel.jsx"
import { preinit } from 'react-dom';

export default function ForecastPanel() {
  ~preinit('/forecast.css', { as: 'style', precedence: 'default' })~; // Downloads and inserts the panel's stylesheet
  return (
    <ul className="forecast">
      <li>Mon 20°</li>
      <li>Tue 19°</li>
      <li>Wed 17°</li>
    </ul>
  );
}
```

The stylesheet puts the three days in one row, without the list dots:

```css title="public/forecast.css"
.forecast {
  display: flex;
  gap: 16px;
  list-style: none;
}
```

Our JSX never writes the stylesheet link that `preinit` leaves in the `<head>`. React adds it:
1. `ForecastPanel` calls `preinit` for a stylesheet, with a precedence.
2. React gives the browser the hint and inserts the stylesheet into the document.
3. React places it with the other stylesheets of the same `precedence`, here right after `brand.css`.

There are two fixes. Use `preinit` with a precedence, as `ForecastPanel` does above. Or render the stylesheet link with `precedence` yourself (Lesson 83). `preload` alone is never the fix for a stylesheet that must apply.

Remember: `preload` downloads. `preinit` downloads and applies.

## PRINCIPLE | `preconnect`: the connection to another server opens before the fetch

> [!PRINCIPLE]
> **Principle 3: preconnect: Open the Connection to Another Server Before the Request Exists**
>
> *Call `preconnect(href)` during render for another server you will request from, when you know the server but not the exact files; it brings nothing for the page's own server.*
>
> A request to a new server first needs a handshake: the browser finds the server and opens a connection. A fetch in an Effect starts only after the commit, so without the hint the handshake starts late too. `preconnect` lets the browser do the handshake while React is still rendering, so the fetch starts on a connection that is already open.
>
> **DO THIS:**
> ```jsx
> function WeatherPage() {
>   ~preconnect('https://api.example.com')~; // Another server: the connection can open before the fetch
>   useEffect(() => { fetch('https://api.example.com/weather?city=Paris'); }, []);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function WeatherPage() {
>   ~preconnect('https://weather.example.com')~; // **WRONG:** the page's own server is already connected, so this gains nothing
>   useEffect(() => { fetch('https://api.example.com/weather?city=Paris'); }, []);
> }
> ```

### Before the fetch, the browser must connect

Think of a phone call. Before you can say one word, you dial, the other side picks up, and you both say hello. Only then does the conversation start.

A request to a new server works the same way. **Before the first byte of 18° can come back, the browser must find the weather server and open a connection to it**. That costs time of its own, before our request even leaves.

> [!DEFINITION]
> **What is a handshake?** [NEW] A handshake is the greeting between the browser and a server before any file can travel. MDN names its three parts "DNS+TCP+TLS".
> DNS: the browser looks up the server's address from its name. TCP: the browser opens the line to the server. TLS: the browser and the server set up the encryption of `https`.
> The browser does all three once per server. After that, every request to that server uses the open connection (Lesson 84).

Here is `preconnect` in its smallest form. It names the server during render, and the fetch runs later, in an Effect:

```jsx title="The smallest preconnect"
function WeatherPage() {
  ~preconnect('https://api.example.com')~; // Runs during render: the browser may open the connection now
  useEffect(() => {
    fetch('https://api.example.com/weather?city=Paris'); // Runs after the commit: can use the connection already open
  }, []);
  return <h1>Paris</h1>;
}
```

The React docs say `preconnect` "lets you eagerly connect to a server that you expect to load resources from". The overview of `react-dom` adds: "even if you don't know what resources you'll need yet". So the call takes a server, not a file. It is the address of the fetch without its path and its question mark part.

### Why the temperature waits, and how preconnect saves time

Most developers think the fetch is the first thing that talks to the server. It is not. Here is the order on the first load of our page:
1. React calls `WeatherPage` during render.
2. The `preconnect` line runs, and the browser may start the handshake with the weather server.
3. React commits the title, the empty temperature line, and the button to the DOM.
4. React runs the Effect, and only now does `fetch` start (Lesson 32).
5. The fetch finds the connection already open, so the answer can come back sooner.

```tree dir=right caption="When the connection to the weather server opens without preconnect and with preconnect."
When the connection to `https://api.example.com` opens
- !Without `preconnect` | Render, then commit, then the Effect starts `fetch` | **Only then** does the browser find the server and open the connection | The temperature line **stays empty longer**
- +With `preconnect` [`https://api.example.com`] | The hint runs **during render** | The connection can open **while React commits** | `fetch` starts on an **open connection**
```

The finished page shows the same 18° with `preconnect` and without it. The difference is only in time. The Network panel shows no separate request line for `preconnect` itself, because the call downloads no file.

### The weather page, step 3: the temperature from the weather server

`WeatherPage` gets a temperature state variable, an Effect that fetches it, and the `preconnect` call for the weather server:

```jsx title="src/WeatherPage.jsx" startLine="1"
import { useState, useEffect } from 'react';
import { preload, preconnect } from 'react-dom';
import ForecastPanel from './ForecastPanel.jsx';

export default function WeatherPage() {
  const [temperature, setTemperature] = useState(null);
  const [showForecast, setShowForecast] = useState(false);
  preload('/fonts/brand.woff2', { as: 'font' });
  ~preconnect('https://api.example.com')~; // The connection can open before the Effect runs

  useEffect(() => {
    fetch('https://api.example.com/weather?city=Paris')
      .then(response => response.json())
      .then(data => setTemperature(data.temperature));
  }, []);

  return (
    <main>
      <link rel="stylesheet" href="/brand.css" precedence="default" />
      <h1>Paris</h1>
      {temperature !== null && <p>{temperature}°</p>}
      <button onClick={() => setShowForecast(true)}>Show forecast</button>
      {showForecast && <ForecastPanel />}
    </main>
  );
}
```

```dom caption="What the Elements panel shows in the head after WeatherPage renders with the preconnect call."
<head>
  <link rel="stylesheet" href="/brand.css" data-precedence="default">
  <title>Weather</title>
  ...
  <link rel="preload" href="/fonts/brand.woff2" as="font" crossorigin="">
+ <link rel="preconnect" href="https://api.example.com"> | note: Added by the preconnect call
  <link rel="preload" as="style" href="/brand.css">
</head>
```

### preconnect to our own site gains nothing

`preconnect` helps only for another server. Here is the mistake the React docs warn about:
1. A developer learns that `preconnect` speeds up loading.
2. They add `preconnect` for their own site, `https://weather.example.com`, the one that sends the page, the stylesheet, and the font.
3. Nothing gets faster. The browser is already connected to that server, because it has just downloaded the page from it.

The React docs: "There is no benefit to preconnecting to the same server the webpage itself is hosted from because it's already been connected to by the time the hint would be given."

> [!DEFINITION]
> **What are same-origin and cross-origin?** [NEW] A request to the server the page came from is same-origin. A request to another server, such as `https://api.example.com`, is cross-origin. These are the MDN words.
> Only cross-origin requests gain from `preconnect`. That is also why our font gets `preload` and not `preconnect`: the font comes from our own site (Lesson 84).

Remember: `preconnect` dials the other server before the fetch picks up the phone.

## PRINCIPLE | `prefetchDNS`: only the server's address is looked up, for a request that may never come

> [!PRINCIPLE]
> **Principle 4: prefetchDNS: Look Up a Server's Address When the Request May Never Come**
>
> *Use `prefetchDNS(href)` for a server you may not request from, or for many servers at once; keep `preconnect` for the few servers you will surely use.*
>
> Both calls take a server, not a file. `prefetchDNS` asks the browser only to look up the server's IP address, the first part of the handshake. `preconnect` also opens the connection, which saves more time but costs even when no request ever comes. For icons that appear only after a click, the lookup is enough.
>
> **DO THIS:**
> ```jsx
> function WeatherPage() {
>   preconnect('https://api.example.com');
>   ~prefetchDNS('https://cdn.example.com')~; // Icons only after a click: the cheap lookup is enough
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function WeatherPage() {
>   preconnect('https://api.example.com');
>   ~preconnect('https://cdn.example.com')~; // **WRONG:** a full connection for icons the user may never ask for
> }
> ```

### VS | `prefetchDNS` vs. `preconnect` for the same server: one finds the address, the other also connects

Here are the two calls for the icon server:

```jsx title="The icon server given to prefetchDNS and to preconnect"
~prefetchDNS~('https://cdn.example.com'); // The browser may look up the server's address, and stops there
~preconnect~('https://cdn.example.com'); // The browser may look up the address and also open the connection
```

It may look the same, or work the same at first, but it is NOT the same thing! `prefetchDNS` does only the first part of the handshake, the DNS lookup. `preconnect` does the lookup and then opens the connection.

> [!DEFINITION]
> **What is a DNS lookup?** [NEW] A DNS lookup is the search for the number behind a server's name. `cdn.example.com` is a name, and the browser cannot call a name. It needs the number, the server's IP address.
> It works like a phone book: you know the name, and you look up the number. MDN says the name "must be resolved to an IP address before the browser can issue the request".
> The React docs say `prefetchDNS` "provides the browser with a hint that it should look up the IP address of a given server" (Lesson 84).

```tree caption="How far the browser goes for the icon server with prefetchDNS and with preconnect."
Two hints about `https://cdn.example.com`
- +`prefetchDNS` [`https://cdn.example.com`] | **Looks up the IP address** only | Cheap: no connection waits **unused**
- +`preconnect` [`https://cdn.example.com`] | **Looks up the address and opens the connection** | Faster for the first icon, but **costs even if no icon is ever requested**
```

### Which one fits the icon server

The forecast icons come from the icon server, but only if the user clicks **Show forecast**. Many users never click. So a full connection may be wasted, and the lookup is the cheap first step.

The React 19 announcement draws the line in one sentence each. `prefetchDNS` is for "when you may not actually request anything from this host". `preconnect` is for "when you will request something but aren't sure what".

So on our page:
- **The weather server** always sends the temperature. It gets `preconnect`.
- **The icon server** may never be used. It gets `prefetchDNS`.

### The weather page, step 4: icons from the icon server

The page component adds `prefetchDNS` to its import from `react-dom`:

```jsx title="src/WeatherPage.jsx" startLine="2"

```

It calls `prefetchDNS` for the icon server, right under the other two hints:

```jsx title="src/WeatherPage.jsx" startLine="8"

  preconnect('https://api.example.com');

```

`ForecastPanel` now shows a sun icon in each day. The days live in an array, and the panel renders them with `map` and a `key` (Lesson 18):

```jsx title="src/ForecastPanel.jsx"

const days = [
  { name: 'Mon', temperature: 20 },
  { name: 'Tue', temperature: 19 },
  { name: 'Wed', temperature: 17 },
];

export default function ForecastPanel() {
  preinit('/forecast.css', { as: 'style', precedence: 'default' });
  return (
    <ul className="forecast">
      {days.map(day => (
        <li key={day.name}>
          ~<img src="https://cdn.example.com/icons/sun.png" alt="Sunny" />~ {/* The first request to the icon server */}
          {day.name} {day.temperature}°
        </li>
      ))}
    </ul>
  );
}
```

The lookup pays off only for users who click:
1. `WeatherPage` renders and calls `prefetchDNS` for the icon server.
2. If the user never clicks **Show forecast**, the page never requests anything from that server. It spent only a cheap lookup.
3. If the user clicks, `ForecastPanel` renders three `<img>` tags that point to that server, and the browser already knows its address.

```page width=text caption="The forecast panel after the user clicks Show forecast, with one sun icon from the icon server in each day."

line: 18°
line: [Show forecast]
line: ☀️ Mon 20° ☀️ Tue 19° ☀️ Wed 17° | good

  <title>Weather</title>

  <link rel="preload" href="/fonts/brand.woff2" as="font" crossorigin="">
  <link rel="preconnect" href="https://api.example.com">
+ <link rel="dns-prefetch" href="https://cdn.example.com"> | note: Added by the prefetchDNS call
  <link rel="preload" as="style" href="/brand.css">

```

Something that can be tricky: the link's `rel` value is `dns-prefetch`, the name that HTML and MDN use. The React 19 announcement writes it the other way round, as `prefetch-dns`. So do not copy the value from the announcement into a link you write by hand.

### preconnect to every server costs more than it saves

Here is the mistake that both the React docs and MDN warn about:
1. A page loads files from many outside servers: icons, maps, fonts, and analytics.
2. The developer adds `preconnect` for every one of them.
3. Each connection costs the browser work, even the ones the page never uses.

MDN says "preconnecting them all can be counterproductive". The React docs say "the overhead of preconnections might outweigh the benefit". The fix is to keep `preconnect` for the few most important servers, and use `prefetchDNS` for the rest.

Remember: `preconnect` for a server you will surely call. `prefetchDNS` for a server you may call.

## PRINCIPLE | A hint in the click handler: the download starts before the new state renders

> [!PRINCIPLE]
> **Principle 5: The Event Handler: Start a Resource Before the State Change That Needs It**
>
> *In the browser, the four calls work anywhere; call them in the event handler that leads to the new state, before the state change, to start the download earlier than during the new render.*
>
> A click already tells us what comes next. React calls the event handler first and renders the new state after it, so a hint in the handler starts the download before React renders the panel. A second, equivalent call in the panel changes nothing, so the panel can keep its own call for any other code that renders it.
>
> **DO THIS:**
> ```jsx
> function handleShowForecast() {
>   ~preinit('/forecast.css', { as: 'style', precedence: 'default' })~; // Starts during the click
>   setShowForecast(true);
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ForecastPanel() {
>   useEffect(() => {
>     ~preinit('/forecast.css', { as: 'style', precedence: 'default' })~; // **WRONG:** starts only after the panel is committed
>   }, []);
>   return <ul className="forecast">...</ul>;
> }
> ```

So far, every hint ran while a component rendered. But the React docs say they work anywhere in the browser: "you can call `preinit` in any situation: while rendering a component, in an Effect, in an event handler, and so on." The same holds for the other three calls.

### VS | `preinit` in the panel vs. `preinit` in the click handler: the same call, started at a different moment

Here is the same `preinit` call in two places:

```jsx title="The same preinit call in ForecastPanel and in the Show forecast handler"
function ForecastPanel() {
  ~preinit('/forecast.css', { as: 'style', precedence: 'default' })~; // Runs when React renders the panel, after the click
}

function handleShowForecast() {
  ~preinit('/forecast.css', { as: 'style', precedence: 'default' })~; // Runs during the click, before React renders anything
  setShowForecast(true);
}
```

It may look the same, or work the same at first, but it is NOT the same thing! Both places leave one stylesheet in the `<head>` and a styled panel on the page. The one difference is the moment the call runs.

When the user clicks **Show forecast**, React first runs our event handler. Only after the handler finishes does React render the new state (Lesson 13). So the call in the handler runs first, and the call in the panel runs later.

The React docs give this exact advice: "Call `preinit` in an event handler before transitioning to a page or state where external resources will be needed. This gets the process started earlier than if you call it during the rendering of the new page or state."

```tree dir=right caption="When forecast.css starts downloading with preinit in ForecastPanel and with preinit in handleShowForecast."
After the user clicks `Show forecast`
- !`preinit` in `ForecastPanel` | React runs the handler, and `setShowForecast` asks for a render | React renders `WeatherPage`, then `ForecastPanel` | **Only now** does `forecast.css` start
- +`preinit` in `handleShowForecast` | React runs the handler, and `preinit` runs **first** | `forecast.css` starts **during the click** | The download is already going while React renders the panel
```

### The weather page, step 5: the click handler starts the panel's stylesheet

The page component adds `preinit` to its import from `react-dom`:

```jsx title="src/WeatherPage.jsx" startLine="2"
import { preload, ~preinit~, preconnect, prefetchDNS } from 'react-dom'; // preinit joins the other three
```

It gets a named handler for the button. The handler starts the stylesheet first, and then changes the state:

```jsx title="src/WeatherPage.jsx" startLine="18"
  function handleShowForecast() {
    ~preinit('/forecast.css', { as: 'style', precedence: 'default' })~; // Starts the stylesheet during the click
    setShowForecast(true); // Then asks React to render the panel
  }
```

The button now calls that handler:

```jsx title="src/WeatherPage.jsx" startLine="28"
      <button ~onClick={handleShowForecast}~>Show forecast</button> {/* The click runs handleShowForecast */}
```

`ForecastPanel` keeps its own `preinit` call. That way, the panel still gets its stylesheet if some other code ever renders it without this button.

### Two calls, one stylesheet in the head

**The same `preinit` now runs twice for one click, and the `<head>` still holds one stylesheet link for the forecast.** Here is the order:
1. The user clicks **Show forecast**.
2. React runs `handleShowForecast`, and `preinit` gives the browser the hint for the forecast stylesheet.
3. `setShowForecast(true)` asks React for a new render.
4. React renders the page component, then `ForecastPanel`, which calls `preinit` again with the same address.
5. React adds no second link.

The React docs: "Multiple calls to `preinit` with the same `href` have the same effect as a single call." It is the same rule of equivalent calls that Principle 1 showed for `preload`.

### Moving the call into an Effect starts it last

Some developers feel that a call like this does not belong in render, because rendering must stay pure (Lesson 14). So they move it:
1. A developer moves `preinit` into an Effect inside `ForecastPanel`.
2. The Effect runs only after the panel has been committed to the DOM (Lesson 32).
3. So the download starts later than in render, and later still than in the click handler.

The React docs show two places for these calls: while rendering, and in an event handler. An Effect is allowed, but it is the latest of the three places. And because equivalent calls count as one, a hint during render adds no extra links and no extra downloads.

```tree dir=right caption="The three places to call preinit for forecast.css, from the earliest start to the latest."
Where to call `preinit` for the panel's stylesheet
- +1. In the click handler [`handleShowForecast`] | Runs **during the click** | The **earliest** start
- +2. While rendering the panel [`ForecastPanel`] | Runs when React **renders** the panel | Starts after the state change
- !3. In an Effect of the panel [`useEffect`] | Runs **after the commit** | The **latest** start
```

Remember: a click already tells you what comes next. Start the resource in the click handler.

### Each resource, and the call that starts it

| Resource | The habit that starts late | The call that starts it early |
| :--- | :--- | :--- |
| **A font named inside a stylesheet** | Wait for the stylesheet, so the browser finds the font only after reading it | `preload(href, { as: 'font' })` during render |
| **A stylesheet that must apply** | `preload` with `as: 'style'`, which downloads it and never inserts it | `preinit(href, { as: 'style', precedence })` |
| **Another server we will request from** | Let the fetch in the Effect open the connection after the commit | `preconnect(href)` during render, never for the page's own server |
| **A server we may never use** | `preconnect` for every outside server | `prefetchDNS(href)`, which only looks up the IP address |
| **A resource needed after a click** | Wait for the new render, or worse, call the hint in an Effect | The hint in the event handler, before the state change |

Remember the one sentence of this lesson. **The browser starts a file only when something names it, so the four calls from `react-dom` name it first, straight from the component that needs it.**

## For the Interview

> **The Interview Question:** How do preload, preinit, preconnect, and prefetchDNS speed up asset loading?

### How to Answer Clearly in 30 Seconds

"The browser starts downloading a file only when it finds the tag or the CSS rule that names it. So a font named inside a stylesheet starts late, and so does a server that only a fetch in an Effect uses. React 19 adds four calls in `react-dom` that give the browser a hint earlier, straight from the component that needs the resource:
1. **`preload(href, { as })`** starts downloading a file we know we will use, such as a font. `as` is required.
2. **`preinit(href, { as })`** downloads a stylesheet or a script and puts it into use: a script runs when it arrives, and a stylesheet is inserted. Stylesheets need `precedence`.
3. **`preconnect(href)`** opens a connection to another server when we know the server but not the files. It brings nothing for the page's own server.
4. **`prefetchDNS(href)`** only looks up the server's IP address. It costs less, so it fits many servers, or a server we may never use.

All four return nothing, and equivalent calls count as one, so calling them on every render is fine. In the browser we can call them anywhere, and in an event handler they start before the new state renders. They are hints, so the browser may skip them, and frameworks often call them for us."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Is it safe to call `preload` in the body of a component that renders many times?"**
   Yes. The React docs say "Multiple equivalent calls to `preload` have the same effect as a single call". Two calls are equivalent when they name the same `href`, and for an image the image options must match too. So `WeatherPage` can call `preload` for the font on every render, and the `<head>` keeps one preload link. The call returns nothing and changes nothing on the page. The same rule holds for `preinit`, `preconnect`, and `prefetchDNS`.
2. **"When do you choose `preconnect`, `prefetchDNS`, or `preload` with `as: 'fetch'` for a data server?"**
   It depends on what you know. If you know the exact request, `preload` with `as: 'fetch'` can start it, and the React docs say `crossOrigin` is required in that case. If you know the server but not the exact files, use `preconnect`. The React docs say: "If you know the specific resources you'll need, you can call other functions instead that will start loading the resources right away". If you may not request from the server at all, or you have many servers, use `prefetchDNS`, because a connection nobody uses still costs. None of them helps for the page's own server, which is already connected.
3. **"Do these calls work the same way on the server, and do you always need to call them yourself?"**
   No to both. In the browser, the React docs say you can call them "in any situation: while rendering a component, in an Effect, in an event handler". On the server, a call "only has an effect if you call it while rendering a component or in an async context originating from rendering a component. Any other calls will be ignored". Lessons 101 and 102 cover server rendering. There, React places the resulting links in the `<head>` by how useful they are for early loading, not by the order of the calls. The React docs also say that "React-based frameworks frequently handle resource loading for you, so you might not have to call this API yourself". For ES modules, React also has `preloadModule` and `preinitModule`.

```tree dir=right caption="Interview comparison: which of the four calls fits which resource on the weather page."
Picking the hint for each resource on the weather page
- +A file we will use [`preload` `as: 'font'`] | **Downloads** early | Applies nothing by itself
- +A stylesheet that must apply [`preinit` `precedence: 'default'`] | **Downloads and inserts** | Best called in the **click handler**
- +A server we will use [`preconnect` `https://api.example.com`] | **Opens the connection** early | No benefit for the **page's own server**
- +A server we may not use [`prefetchDNS` `https://cdn.example.com`] | **Looks up the address** only | Cheap enough for **many servers**
```
