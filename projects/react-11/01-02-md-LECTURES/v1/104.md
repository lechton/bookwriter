# Lecture 104: What hydrateRoot Does with the Server HTML

*(How does a finished page from the server start answering clicks?)*

> INTERVIEW QUESTION | ❱ CORE | What is hydration, and how does hydrateRoot attach interactivity?

---

## VS | Building the Page Again `createRoot` vs. Keeping the Page `hydrateRoot`: the first throws the server HTML away, the second keeps it and adds the handlers

> When the server sends a finished HTML page, the user sees the title and the `Add to cart` button at once, but the button does nothing yet, because HTML cannot carry your JavaScript functions. **`hydrateRoot` runs your components again in the browser, keeps every element the server sent, and attaches your `onClick` functions to those same elements.** React does not build the page a second time, so nothing on the screen moves, and the text the user already typed stays where it is.

Remember how you add a click handler in plain JavaScript? The button is already in the HTML file. Your script finds it and attaches a function to it:

```js title="Plain JavaScript: the HTML gives the button, the script gives the handler"
const button = document.querySelector('button');
~button.addEventListener('click', addToCart)~; // The button was already on the page; only the handler is new
```

The HTML gave you the button. Your script gave it a behavior. You never deleted the button to create a new one.

Hydration is the same idea, done by React for the whole page at once. Since Lesson 102, our server sends the product page as finished HTML. The user sees everything at once, but no button answers yet. When the JavaScript arrives, one line in the browser entry file starts React:

```jsx title="src/main.jsx"
~hydrateRoot~(document.getElementById('root'), <App />); // Keeps the server's elements and attaches the handlers
```

React runs `App` in the browser, finds the `onClick` on the button in your JSX, and attaches it to the button element that is already on the page. That is all. No element is deleted, and no element is created.

So here is the one sentence to keep in mind for this whole lesson:

**The server gives the elements, the JavaScript gives the handlers, and `hydrateRoot` joins the two without building the page again.**

> [!DEFINITION]
> **Hydration.** [NEW] Hydration is the moment React makes a server-rendered page interactive. The server HTML already has every element of the page, but no event handlers, because HTML cannot carry JavaScript functions. During hydration, React runs your components in the browser, keeps the elements the server sent, and attaches your handlers to them. The React docs say that hydration "turns the initial HTML snapshot from the server into a fully interactive app that runs in the browser" (Lesson 104).

### What the User Sees on a Slow Phone

Take the product page of an online shop, opened on a phone with a slow connection. The page has four parts: a search field at the top, the title `Blue Sneakers`, an `Add to cart` button, and a line that reads `Cart: 0`. The server sends it as finished HTML, so the whole page shows at once, before any of our JavaScript has arrived:

```page width=text caption="The product page as the server sends it: everything is on the screen before the JavaScript arrives."
form:
  field: | Search products
heading: Blue Sneakers
line: [Add to cart]
line: Cart: 0
```

While the JavaScript is still on its way, the user taps and types. Here is what happens, in order:
1. The user taps `Add to cart`. Nothing happens, and the line stays on `Cart: 0`. No handler is on the button yet.
2. The user taps the search field and types `socks`.
3. The JavaScript arrives, and the entry file calls `hydrateRoot`.
4. Nothing on the page moves, and `socks` is still in the search field. From now on, a tap on `Add to cart` changes the line to `Cart: 1`.

```page width=text caption="The same page after hydrateRoot and one more tap on Add to cart: socks is still in the search field, and the line shows Cart: 1."
form:
  field: | socks | good
heading: Blue Sneakers
line: [Add to cart]
line: Cart: 1 | good
```

**`hydrateRoot` did not build the page again.** The page was already on the screen. React ran `App` in the browser, kept every element the server sent, and attached our click handler to the `Add to cart` button that was already there.

Now compare it with `createRoot`, the call you have used since Lesson 07:

> [!DEFINITION]
> **createRoot.** [REVIEW] `createRoot` takes the root element of the page and gives you a React root. Calling `render` on that root makes React create every element of your components and put them inside the root. On a page whose root arrives empty, this is how the page appears at all (Lesson 07).

```jsx title="Two ways the entry file can start React on the same server HTML"
~createRoot~(document.getElementById('root')).render(<App />); // Deletes the server's elements and creates new ones: the search field is empty again
~hydrateRoot~(document.getElementById('root'), <App />); // Keeps the server's elements and attaches the handlers: socks stays
```

With both lines, `App` runs in the browser, the page shows `Blue Sneakers`, and `Add to cart` works. **It may look the same, or work the same at first, but it is NOT the same thing!** With `createRoot`, React deletes the search field the user typed in and creates a new, empty one in its place. With `hydrateRoot`, React keeps the same `<input>` element, so `socks` stays where the user typed it.

**Why:** What the user sees depends on what the entry file does with the server HTML:
1. **With `hydrateRoot`**, what the user did before the JavaScript arrived stays on the page: the text typed in a field, the focus, and the scroll position.
2. **With `createRoot`**, React builds the page again from nothing. The React docs warn that this "can be slower, resets focus and scroll positions, and may lose other user input."
3. **When the browser's first render gives a different result from the server**, the docs warn: "In the best case, they'll lead to a slowdown; in the worst case, event handlers can get attached to the wrong elements."
4. **Until hydration ends**, no button on the page answers. Without a `<Suspense>` or `<Activity>` boundary, React hydrates the whole page at once, so a slow part at the bottom delays the button at the top (Lessons 69 and 73).

### The Rule of Thumb: does the root already hold HTML?

**Ask one question about the root element when the page loads: does it already hold HTML from the server? If yes, call `hydrateRoot`. If it is empty, call `createRoot`.**

The React docs say both halves. "Server-rendered apps must use `hydrateRoot` instead of `createRoot`." And for an empty root: "If your app is client-rendered with no HTML rendered already, using `hydrateRoot()` is not supported. Use `createRoot()` instead."

A senior developer also knows the five classic mistakes:
1. **Thinking hydration builds the page again.** It does not. React keeps the server's elements.
2. **Thinking the opposite: React trusts the HTML and skips the components.** It does not. React runs every component in the browser, and that is the cost of hydration.
3. **Keeping `createRoot` after adding a server.** React then deletes the server HTML and builds the page from nothing.
4. **Expecting the browser to fix whatever the server got wrong.** React expects the first browser render to match the server. The docs: "You should treat mismatches as bugs and fix them."
5. **Expecting the button to answer as soon as it appears.** It answers only after hydration ends.

The rest of the lesson shows each one on the real product page.

## SECTION | The Blue Sneakers Product Page

We keep building the product page of Lesson 102. A shop renders this page on the server so that it shows at once when someone opens a shared link. Its `Add to cart` button must start answering as soon as the JavaScript arrives. That is where developers meet hydration at work.

The page uses three files:

```files title="product-page: File Explorer" caption="The three files of the product page: the server sends the HTML, App.jsx describes the page, main.jsx hydrates it."
server.js | server | Calls `renderToString(<App />)` and sends the HTML inside `<div id="root">`, unchanged from Lesson 102
src/
  App.jsx | component | Exports `App`: the search field, the title, `Add to cart`, and the `Cart` line
  main.jsx | entry | Imports `App` and calls `hydrateRoot` on `#root`
```

> [!DEFINITION]
> **renderToString.** [REVIEW] `renderToString` runs on the server. It calls your components, takes the JSX they return, and turns it into one string of HTML. The server puts that string inside the root element of the page and sends it, so the browser can show the page before any JavaScript runs. That HTML has the elements, but not your event handlers (Lesson 102).

The server and the browser both run this same `App`:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [count, setCount] = useState(0);
  return (
    <main>
      <input placeholder="Search products" />
      <h1>Blue Sneakers</h1>
      <button onClick={() => setCount(count + 1)}>Add to cart</button>
      <p>Cart: {count}</p>
    </main>
  );
}
```

The browser entry file holds the one line Lesson 102 gave it:

```jsx title="src/main.jsx"
import { ~hydrateRoot~ } from 'react-dom/client'; // The browser side of a page the server already rendered
import App from './App.jsx';

hydrateRoot(document.getElementById('root'), <App />);
```

Each part of the page has one job in this lesson:
1. **The title `Blue Sneakers`** is content that hydration keeps exactly as the server sent it.
2. **The `Add to cart` button and the `Cart` line** show the handler that hydration attaches.
3. **The search field** holds what the user typed before the JavaScript arrived. `hydrateRoot` keeps it, and `createRoot` wipes it.

Again, the one sentence of this lesson: **the server gives the elements, the JavaScript gives the handlers, and `hydrateRoot` joins the two without building the page again.**

**PRINCIPLES:** From the outside, hydration looks like one step: the JavaScript arrives, and the page starts to work. Inside that step, React does several separate things, and each one explains a bug or an interview question. Five principles follow:
1. **Principle 1: hydrateRoot Runs App Again but Keeps Every Element the Server Sent.** The component code runs in the browser, yet React creates no new elements.
2. **Principle 2: onClick Reaches the Add to cart Button the Server Sent.** The server HTML has the button but not our function. Hydration joins the two.
3. **Principle 3: hydrateRoot Keeps What the User Typed.** On server HTML, `createRoot` deletes every element and creates new ones, so `socks` is lost.
4. **Principle 4: The First Browser Render Must Give the Server's Cart: 0.** React can keep the server's elements only when both give the same result.
5. **Principle 5: Without a Boundary, Add to cart Waits Until the Whole Page Is Hydrated.** React hydrates the whole page at once. The button at the top waits for the slowest part at the bottom.

## PRINCIPLE | `hydrateRoot`: `App` runs again in the browser, but React creates no new elements

> [!PRINCIPLE]
> **Principle 1: Reuse: hydrateRoot Runs App Again but Keeps Every Element the Server Sent**
>
> *During `hydrateRoot`, React calls our components in the browser and reuses every DOM node the server sent; it does not create the page again.*
>
> The server already built the page from `App`. In the browser, React calls `App` once more to learn what each element should be, compares the result with the HTML in the root, and keeps the elements it finds there. The component code runs twice, once on the server and once in the browser. The page is built once.
>
> **DO THIS:**
> ```jsx
> import { hydrateRoot } from 'react-dom/client';
> ~hydrateRoot~(document.getElementById('root'), <App />); // Calls App and keeps the server's <h1>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import { createRoot } from 'react-dom/client';
> ~createRoot~(document.getElementById('root')).render(<App />); // **WRONG:** calls App and replaces the server's <h1> with a new one
> ```

Strip the product page down to one heading. The server sends this HTML inside the root:

```html title="The server HTML inside index.html"
<div id="root"><h1>John</h1></div>
```

In the browser, `App` returns the same heading and prints one line to the Console:

```jsx title="src/App.jsx"
export default function App() {
  ~console.log('App runs');~ // Prints each time React calls App in the browser
  return <h1>John</h1>;
}
```

```jsx title="src/main.jsx"
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';

~hydrateRoot~(document.getElementById('root'), <App />); // Calls App, then keeps the <h1> already in the root
```

**The Console says `App runs`, yet nothing on the page changes.** `John` stays where it was.

```page width=text caption="The page after hydrateRoot: John never moved, and the Console shows that App ran in the browser."
heading: John
console:
  log: App runs | App.jsx:2
```

This is a surprise. With `createRoot`, the first call of `App` is what puts the elements on the screen. This time `App` ran, and React put nothing new on the screen. Here is what happened, in order:
1. The server sends the root with the heading inside, and the browser shows `John` at once.
2. The entry file loads and calls `hydrateRoot`.
3. React calls `App`, and the Console shows `App runs`.
4. React compares the heading `App` returned with the `<h1>` already in the root.
5. The two match, so React keeps the `<h1>` the server sent and creates no new one.

The React docs name step 5 exactly. React will hydrate "the DOM nodes from your HTML instead of destroying and re-creating them." A **DOM node** is the docs' name for an element on the page, such as this `<h1>`, the same object `getElementById` gives you in plain JavaScript. To **reuse the DOM nodes** means that the elements on the screen after hydration are the very same objects the browser created from the server's HTML.

If the entry file wraps `<App />` in `<StrictMode>`, the Console can show `App runs` twice in development, because Strict Mode calls each component twice there. It is still one hydration (Lesson 14).

### One App, Two Runs

Hydration runs every component again, so it sounds like a second render of the page. **It is not.** One thing happens twice, and one thing happens once:
- **The component code runs twice**: once on the server, to write the HTML, and once in the browser, during `hydrateRoot`.
- **The page is built once**: from the server HTML. In the browser, React creates no new elements. It reuses the ones already there.

**Yes, it is the exact same component code!** It is the same `App`, with the same JSX. The React docs: "On the server, it will render to produce the initial HTML. On the client, React will run the rendering code again so that it can attach your event handlers to that HTML."

What each run does with its result is NOT the same:
- **On the server**, `renderToString` turns the result into the HTML that the browser shows first.
- **In the browser**, `hydrateRoot` matches the result against the HTML already in the root, and creates no new elements from it.

```tree caption="The same App runs on the server and in the browser, but each run does something different with its result."
One `App`, two runs
- +On the server [`renderToString`] | Calls `App` | Turns the result **into HTML** that the browser shows first
- +In the browser [`hydrateRoot`] | Calls `App` **again** | Matches the result **against the HTML already there** and creates **no new elements**
```

On the real product page, React walks down the server HTML and finds every element it expects: the search field, the title, the button, and the `Cart` line. It keeps all of them. From that moment, the docs say, React will "take over managing the DOM" inside the root. Every later change, such as `Cart: 0` becoming `Cart: 1`, is made by React on those same elements.

### Why This Mistake Is Common

A developer reads that `App` runs again in the browser and draws the wrong conclusion:
1. The developer decides the browser throws the server HTML away and draws the page again.
2. So server rendering seems to gain nothing, and `createRoot` and `hydrateRoot` seem to do the same work.
3. In fact the elements stay. That is exactly why `socks` stays in the search field, as Principle 3 shows.

## PRINCIPLE | `onClick`: hydration attaches the handler to the button the server sent

> [!PRINCIPLE]
> **Principle 2: Attach: onClick Reaches the Add to cart Button the Server Sent**
>
> *During hydration, React attaches each `onClick` in our JSX to the matching element that came from the server; after that, a click updates that same element through state.*
>
> The server HTML holds the button but not our function, because HTML cannot carry JavaScript. Until hydration ends, a tap on the button does nothing. During `hydrateRoot`, React runs `App`, finds `onClick` on the button, and attaches it to the button already on the page. From then on, every change goes through `setCount`, as on any React page.
>
> **DO THIS:**
> ```jsx
> <button ~onClick={() => setCount(count + 1)}~>Add to cart</button> {/* Hydration attaches it; the tap changes Cart: 0 to Cart: 1 */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const root = hydrateRoot(document.getElementById('root'), <App />);
> ~root.render(<App />)~; // **WRONG:** a hydrated page changes through state, not through another root.render
> ```

Here is the smallest button with a click handler, as we write it in our component:

```jsx title="The button in App.jsx"
const [count, setCount] = useState(0);

<button ~onClick={() => setCount(count + 1)}~>Cart: {count}</button> {/* The function lives in our JavaScript */}
```

And here is the HTML the server writes for it:

```html title="The server HTML for the same button"
<button>Cart: <!-- -->0</button>
```

**It may look the same, but it is NOT the same thing!** The `<button>` in our component has `onClick`. The `<button>` in the server HTML has no `onClick` at all. HTML is text, and a JavaScript function cannot travel inside it. The docs call the server's result "the initial non-interactive HTML output".

The `<!-- -->` between `Cart: ` and `0` is an HTML comment that React's server renderer writes between a piece of fixed text and a value. It tells hydration where the text ends and the value begins (Lesson 102).

So the button and its handler reach the browser separately. **The button arrives with the HTML. Its handler arrives with the JavaScript. Hydration is the moment the two meet.**

```tree caption="The button reaches the browser with the HTML, and its handler reaches it with the JavaScript; hydration joins the two."
How the `Add to cart` button becomes clickable
- !The button in the server HTML [`<button>`] | Arrives **first**, with the page | Has **no handler**: a tap does nothing
- +The handler in `App.jsx` [`onClick`] | Arrives **later**, with the JavaScript | Lives in **our function**, not in the HTML
- +Hydration | React runs `App` and finds `onClick` on the button | **Attaches** our function to the button **already on the page**
```

This is exactly the plain JavaScript from the start of the lesson. You found the button and called `addEventListener` on it. React does the same job for you: it finds the element, and it connects the function you wrote in the JSX. The docs: "hydration attaches your event handlers to the generated HTML." The button is the same element before and after. Only the handler is new.

### The First Tap and the Second Tap

On the product page, the user taps `Add to cart` twice: once before the JavaScript arrives, and once after. Here is what happens, in order:
1. The user taps `Add to cart` before the JavaScript arrives. `Cart: 0` stays, because no handler is on the button.
2. The JavaScript arrives. `hydrateRoot` runs `App` and finds the click handler on the button in its JSX.
3. React attaches that function to the `<button>` already on the page.
4. The user taps `Add to cart` again. `setCount(1)` runs, and React renders `App` again. The same `<p>` element now reads `Cart: 1`.

The first tap is not counted later. When the user made it, nothing on the page was listening for it.

```page width=text caption="The product page after hydration and one tap on Add to cart: the first tap, made before the JavaScript arrived, was not counted."
form:
  field: | Search products
heading: Blue Sneakers
line: [Add to cart]
line: Cart: 1 | good
```

Where does the browser's `0` come from? From the browser's own `useState(0)`. The server does not send its state. During hydration, `App` runs in the browser for the first time, and `useState(0)` gives 0, the same first value the server used. So the browser's `Cart: 0` matches the server's `Cart: 0`. Principle 4 shows why that match matters.

### Why This Mistake Is Common

A developer wants the `Cart` line to change after hydration and reaches for the root, the way they did with `createRoot` in Lesson 07:

```jsx title="src/main.jsx"
const root = hydrateRoot(document.getElementById('root'), <App />);

~root.render(<App />)~; // **WRONG:** React already manages the page; changes go through state
```

The React docs answer this directly: "You shouldn't need to call `hydrateRoot` again or to call it in more places. From this point on, React will be managing the DOM of your application. To update the UI, your components will use state instead." The fix is already in our component: the `setCount` call that `onClick` makes.

## PRINCIPLE | `hydrateRoot` on server HTML: the text the user typed stays in the `<input>` field

> [!PRINCIPLE]
> **Principle 3: hydrateRoot vs. createRoot: hydrateRoot Keeps What the User Typed**
>
> *When the root holds server HTML, the entry file must call `hydrateRoot`; `createRoot` deletes every server element and creates new ones, which loses what the user typed and where the focus was.*
>
> The server HTML is on the screen before the JavaScript, so the user may already be typing in it. `createRoot` clears the root and builds the page again from our JSX, so the search field is a new, empty `<input>`. `hydrateRoot` keeps the elements the server sent and only attaches the handlers, so what the user did stays on the page. When the root is empty, the rule turns around: use `createRoot`.
>
> **DO THIS:**
> ```jsx
> ~hydrateRoot~(document.getElementById('root'), <App />); // The root holds server HTML: socks stays in the search field
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~createRoot~(document.getElementById('root')).render(<App />); // **WRONG:** the root holds server HTML: the field is replaced and socks is lost
> ```

Strip the page down to the search field. The server sends this HTML:

```html title="The server HTML inside index.html"
<div id="root"><input placeholder="Search products"></div>
```

`App` returns the same `<input>` field:

```jsx title="src/App.jsx"
export default function App() {
  return <input placeholder="Search products" />;
}
```

Before the JavaScript arrives, the user taps the search field and types `socks`. Then the entry file runs. Here is the page after each of the two lines it could hold:

### VS | Deleting the Elements `createRoot` vs. Keeping the Elements `hydrateRoot`: only the second keeps socks

::: col title="createRoot on server HTML" tag="socks is gone" tone=bad
```page size=mini
form:
  field: | Search products | bad
```
```jsx title="src/main.jsx" bad="1"
~createRoot~(document.getElementById('root')).render(<App />); // **WRONG:** deletes the field the user typed in
```
The field is empty again, and it no longer has the focus.
:::
::: col title="hydrateRoot on server HTML" tag="socks stays" tone=good
```page size=mini

  field: | socks | good
```
```jsx title="src/main.jsx" good="1"

```
The field still holds `socks`.

**It may look the same, or work the same at first, but it is NOT the same thing!** Both lines put `App` into the root, and on a fast laptop both pages look identical. But the root is not empty. The user may already be using what is inside it.

**With `createRoot`, React throws away the `<input>` the user typed in and creates a new, empty `<input>` in its place.** Here is what happens, in order:
1. The server HTML arrives. The user taps the search field and types `socks`.
2. The entry file loads. `root.render` clears everything inside the root, the `<input>` included.
3. React creates a new `<input>` from our JSX. It holds no text, so the hint `Search products` shows again.
4. `socks` is gone. The focus was on the old `<input>`, which no longer exists, so the next letter the user types lands nowhere.

In plain JavaScript terms, `createRoot` does what this line would do:

```js title="Plain JavaScript: what createRoot does to the server HTML"
~root.innerHTML = ''~; // Every element inside the root is gone, with whatever the user typed in it
```

Then it creates every element again from your JSX. The React docs describe exactly this: "creating a root and calling `root.render` deletes all that HTML, and then re-creates all the DOM nodes from scratch. This can be slower, resets focus and scroll positions, and may lose other user input."

That sentence names three things the user loses:
1. **Focus** is the place where the next key press lands. The user gives a field the focus by tapping it.
2. **Scroll position** is how far down the page the user has moved.
3. **User input** is what the user typed or chose, such as `socks`.

With `hydrateRoot`, the same `<input>` element stays on the page, so `socks` and the focus stay in it.

```tree caption="On server HTML, createRoot replaces every element and hydrateRoot keeps them."
Starting React on a root that already holds server HTML
- !`createRoot` [`root.render`] | **Deletes** every element the server sent | Creates **new ones**: the search field is **empty**, and the focus is **gone**
- +`hydrateRoot` | **Keeps** every element the server sent | Attaches the handlers: **`socks` and the focus stay**
```

### Why This Bug Ships

This mistake hides well, because it shows only on a slow connection:
1. A developer adds a server to an app that started with `createRoot`.
2. The entry file stays as it was.
3. On a fast laptop, the JavaScript arrives before anyone can type, so nothing looks wrong.
4. On a slow phone, a user types in the search field, and the text vanishes when the JavaScript arrives.

The React docs state the fix in one line: "Server-rendered apps must use `hydrateRoot` instead of `createRoot`."

The opposite mistake is wrong too. When the root arrives empty, as `<div id="root"></div>`, there is nothing to hydrate. The docs: "If your app is client-rendered with no HTML rendered already, using `hydrateRoot()` is not supported. Use `createRoot()` instead." Many frameworks make this choice for you.

## PRINCIPLE | `useState(0)`: the browser's first render gives the same `Cart: 0` as the server

> [!PRINCIPLE]
> **Principle 4: Same Output: The First Browser Render Must Give the Server's Cart: 0**
>
> *Hydration reuses the server's elements only if the first render in the browser gives the same output as the server; when they differ, React reports a mismatch and builds that part again in the browser.*
>
> The server and the browser run the same `App`, so with the same first values they give the same page, and React keeps the server's elements. When the browser's first render shows something the server could not know, such as a count saved in `localStorage`, the two differ. React does not quietly paint over the server's text. It reports a hydration error and rebuilds that part of the page.
>
> **DO THIS:**
> ```jsx
> const [count, setCount] = ~useState(0)~; // Server and browser both start at 0: Cart: 0 matches
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const [count, setCount] = useState(
>   typeof window === 'undefined' ? 0 : ~Number(localStorage.getItem('cart'))~ // **WRONG:** the server gives Cart: 0, the browser gives Cart: 3
> );
> ```

Think about what React does in step 4 of Principle 1. It compares what `App` returned with the HTML already on the page. It can keep the server's elements only if the two say the same thing. **React can keep the server's elements only when the browser's first render gives the same result as the server.**

Look at the `Cart` line and where its `0` comes from in each run:

```jsx title="The Cart line in App.jsx"
const [count, setCount] = ~useState(0)~; // On the server and in the browser's first render, count is 0

<p>Cart: {count}</p> {/* Server: Cart: 0. Browser, first render: Cart: 0 */}
```

On the server, `useState(0)` gives `0`, and the HTML reads `Cart: 0`. In the browser, during hydration, the same `useState(0)` gives `0` again, so the first render also gives `Cart: 0`. **Yes, it is the exact same output!** That sameness is what lets React keep the server's text.

The React docs state the condition: "The React tree you pass to `hydrateRoot` needs to produce **the same output** as it did on the server."

React is strict about it for the user's sake. The docs: "The user will spend some time looking at the server-generated HTML before your JavaScript code loads. Server rendering creates an illusion that the app loads faster by showing the HTML snapshot of its output. Suddenly showing different content breaks that illusion."

```tree caption="React keeps the server's elements only when the browser's first render gives the same output as the server."
Server output vs. the browser's first render
- +Same output [`Cart: 0` and `Cart: 0`] | React **keeps** the server's `<p>` and its text | The user sees **no change**
- !Different output [`Cart: 0` and `Cart: 3`] | React reports a **hydration error** | React **builds that part again** in the browser
```

### Why a Reload Brings Back Cart: 0

**The cart forgets its count on every reload, and the match is the reason.** Here is what the user sees:
1. After hydration, the user taps `Add to cart` three times, and the line shows `Cart: 3`.
2. The user reloads the page.
3. The server sends `Cart: 0`, and after hydration the line still shows `Cart: 0`.

State lives in the browser tab, and the server never sees it. On every request, the server starts from `useState(0)`. The browser's first render starts there too, so the two match, and the count of 3 is gone. Keeping a cart across reloads needs data the server can read for each visitor (Lesson 103).

### Why This Mistake Is Common

A developer wants the cart to survive the reload. Say an earlier visit saved the count `3` in the browser's `localStorage`, under the name `cart`. The developer reads it while the component renders. The server has no `localStorage`, so the code first checks for `window`, which exists only in the browser, and gives `0` on the server:

```jsx title="The Cart line in App.jsx"
const [count, setCount] = useState(
  typeof window === 'undefined' ? 0 : ~Number(localStorage.getItem('cart'))~ // **WRONG:** the server writes Cart: 0, the browser's first render gives Cart: 3
);
```

The developer expects the browser render to quietly replace the server's `0` with `3`. The line does end up showing `Cart: 3`, but not quietly:
1. The server writes `Cart: 0`, because the server has no `localStorage`.
2. The browser's first render gives `Cart: 3`.
3. The two outputs differ, so React cannot reuse the server's text.
4. In development, the Console shows an error that begins: "Hydration failed because the server rendered text didn't match the client. As a result this tree will be regenerated on the client." The same message lists this very check of `window` among the usual causes.
5. React builds that part of the page again in the browser. With no boundary around it, that part is the whole page, so the user loses what Principle 3 protects, such as `socks` in the search field.

The React docs: "You should treat mismatches as bugs and fix them." When only an attribute differs, it is worse, because "There are no guarantees that attribute differences will be patched up." The causes of a mismatch and their fixes are the subject of Lesson 105.

## PRINCIPLE | `hydrateRoot` without a boundary: the whole page hydrates at once, so `Add to cart` waits for the slowest part

> [!PRINCIPLE]
> **Principle 5: Cost: Without a Boundary, Add to cart Waits Until the Whole Page Is Hydrated**
>
> *Hydration costs one download of the app's JavaScript and one run of every component in the browser; without a Suspense or Activity boundary, React hydrates the whole page at once, so a slow part delays every button.*
>
> The server HTML makes the page appear early, but no button answers until hydration ends. React runs every component during hydration, including the ones the user never taps. Without a boundary, it does all of them as one piece of work, so the button at the top waits for the reviews at the bottom. A `<Suspense>` or `<Activity>` boundary lets React hydrate the page in chunks. The button and its `count` go into their own component, such as `AddToCart`, so a tap does not render `App` again and does not wait for the boundary either.
>
> **DO THIS:**
> ```jsx
> <AddToCart />
> ~<Suspense>~<Reviews /></Suspense> {/* A boundary: React hydrates Reviews in its own chunk, and a tap in AddToCart answers before Reviews is done */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button onClick={() => setCount(count + 1)}>Add to cart</button>
> ~<Reviews />~ {/* **WRONG:** no boundary around a slow part: Add to cart waits until Reviews is hydrated */}
> ```

Remember Principle 1: hydration runs every component of the page in the browser. The server did the work of writing the HTML. It did not do this work. So the page looks ready before it is.

Now the product page gains a short list of reviews under the button. The reviews come from a new component, `Reviews`:

```jsx title="src/App.jsx" startLine="3"
function Reviews() {
  return (
    <ul>
      <li>Great fit</li>
      <li>Runs small</li>
      <li>Very comfy</li>
    </ul>
  );
}
```

`App` places it under the button, with no boundary around it:

```jsx title="src/App.jsx" startLine="13"
export default function App() {
  const [count, setCount] = useState(0);
  return (
    <main>
      <input placeholder="Search products" />
      <h1>Blue Sneakers</h1>
      <button onClick={() => setCount(count + 1)}>Add to cart</button>
      <p>Cart: {count}</p>
      ~<Reviews />~ {/* No boundary: hydrated together with the button above it */}
    </main>
  );
}
```

The server HTML shows the whole page at once, the reviews included:

```page width=text caption="The product page with its reviews, as the server sends it."
form:
  field: | Search products
heading: Blue Sneakers
line: [Add to cart]
line: Cart: 0
line: Great fit
line: Runs small
line: Very comfy
```

### Why a Button at the Top Waits for the Reviews at the Bottom

**The `Add to cart` button sits at the top of the page, yet it does not answer until the reviews at the bottom are hydrated too.** Here is why, in order:
1. The server HTML shows the title, `Add to cart`, and the three reviews at once.
2. The JavaScript arrives, and `hydrateRoot` starts.
3. React runs `App`, attaches the handler to the button, and goes on to `Reviews`, all as one piece of work.
4. The user taps `Add to cart` while React is still hydrating `Reviews`.
5. The tap gets no answer until the whole page is hydrated.

Here the list has three reviews, so the wait is short. A real product page shows dozens of reviews, photos, and related products under the button, and React hydrates every one of them before `Add to cart` answers. The React docs describe the same wait on their own example: "React must hydrate the entire page all at once. If `Home` or `Video` are slower to render, they could make the tab buttons feel unresponsive during hydration."

So hydration has a cost, and it comes in two parts:
1. **The browser downloads the app's JavaScript and runs every component once more**, including the ones the user never taps. Server rendering made the first content appear earlier. It did not remove this work (Lesson 102).
2. **Without a boundary, React hydrates the whole page at once**, so the slowest part sets the time for every button.

### A Boundary Splits Hydration into Chunks

The way out is a `<Suspense>` or `<Activity>` boundary around `Reviews`. The React docs: "by breaking up your component tree into discrete units, Suspense allows React to hydrate your app's server-rendered HTML in chunks, enabling parts of your app to become interactive as fast as possible." This is called **Selective Hydration**: React hydrates the page in separate chunks, so one part can answer before another is done. Lesson 151 shows it in full.

On this page, the boundary alone is not enough. The `count` state lives in `App`, and the boundary sits inside it too. When the user taps `Add to cart`, our `onClick` function runs at once. But `setCount` asks React to render `App` again, and React first hydrates everything inside the boundary. So the line stays on `Cart: 0` until the last review is hydrated.

The fix is to move the button and the `Cart` line into their own component, `AddToCart`. A tap then renders only `AddToCart`, and `Cart: 1` appears while React is still hydrating `Reviews`:

```jsx title="src/App.jsx" startLine="13"
function AddToCart() {
  const [count, setCount] = useState(0);
  return (
    <>
      <button onClick={() => setCount(count + 1)}>Add to cart</button>
      <p>Cart: {count}</p>
    </>
  );
}

export default function App() {
  return (
    <main>
      <input placeholder="Search products" />
      <h1>Blue Sneakers</h1>
      ~<AddToCart />~ {/* A tap renders only AddToCart: Cart: 1 appears before Reviews is hydrated */}
      ~<Suspense>~<Reviews /></Suspense> {/* A boundary: React hydrates Reviews in its own chunk */}
    </main>
  );
}
```

```tree caption="Without a boundary, the button waits for the whole page; with a boundary around Reviews and the cart in its own component, the tap answers before Reviews is done."
How the page around `Add to cart` is hydrated
- !No boundary [`<Reviews />`] | React hydrates the **whole page at once** | A tap on `Add to cart` waits for **`Reviews` too**
- +A boundary around `Reviews` [`<Suspense>` `<Activity>`] | React hydrates the page **in chunks** | With the cart in **`AddToCart`**, `Cart: 1` appears **before `Reviews` is done**
```

### Why This Bug Ships

A team measures the wrong moment:
1. The team adds server rendering to a product page, and the page appears fast.
2. They check only how fast the content appears.
3. Users on slow phones tap `Add to cart`, and nothing happens for a while.

The page looks ready before it is. The React docs call the server HTML an "illusion that the app loads faster", and hydration is the work hidden behind that illusion.

## All 5 Principles Together

### The Complete Product Page

Here is the complete browser side of the product page. The server file is unchanged from Lesson 102: it calls `renderToString(<App />)` and sends the HTML inside the root.

```jsx title="src/App.jsx"
import { useState, Suspense } from 'react';

function Reviews() {
  return (
    <ul>
      <li>Great fit</li>
      <li>Runs small</li>
      <li>Very comfy</li>
    </ul>
  );
}

function AddToCart() {
  const [count, setCount] = ~useState(0)~; // Principle 4: the browser starts at 0, like the server
  return (
    <>
      <button ~onClick={() => setCount(count + 1)}~>Add to cart</button> {/* Principle 2: attached to the server's button */}
      <p>Cart: {count}</p>
    </>
  );
}

export default function ~App~() { // Principle 1: called again in the browser, during hydrateRoot
  return (
    <main>
      <input placeholder="Search products" /> {/* Principle 3: the same element, so socks stays */}
      <h1>Blue Sneakers</h1>
      <AddToCart />
      ~<Suspense>~<Reviews /></Suspense> {/* Principle 5: hydrated in its own chunk */}
    </main>
  );
}
```

```jsx title="src/main.jsx"
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';

~hydrateRoot~(document.getElementById('root'), <App />); // The root holds server HTML: keep it and attach the handlers
```

### How React Walks the Page During Hydration

When the JavaScript arrives, `hydrateRoot` starts at `App` and goes through the tags from top to bottom. For each element, React finds the matching element in the server HTML and keeps it. For the button, it also attaches `onClick`:

```tree caption="The order in which React calls the components of the product page during hydrateRoot, and what it does with each server element."
`App` [1. Called first by `hydrateRoot`] | Runs **in the browser** and keeps the server's `<main>`
- +`<input>` | Keeps the **server's field** | `socks` **stays**
- +`<h1>` | Keeps **`Blue Sneakers`** as sent
- +`AddToCart` [2. Called second] | Keeps the **server's button** and **attaches `onClick`** | `count` starts at **0**, so `Cart: 0` **matches**
- +`Reviews` [3. Inside `<Suspense>`] | Keeps the **three reviews** | Hydrated **in its own chunk**, so the button **does not wait**
```

### What Readers Expect, and What Hydration Does

| Aspect | What readers expect | What hydration does |
| :--- | :--- | :--- |
| **The page** | `App` runs again, so the page is drawn again | React reuses every element the server sent and creates none |
| **The button** | The button is on the screen, so it works | The handler arrives with the JavaScript; hydration attaches it to the server's button |
| **The root call** | `createRoot` and `hydrateRoot` both put `App` in the root | On server HTML, `createRoot` replaces every element and loses `socks`; `hydrateRoot` keeps them |
| **The first render** | The browser fixes whatever the server got wrong | The browser's first render must give the server's output; a difference is a bug |
| **The cost** | The server did the work, so the browser has little left | The browser runs every component; without a boundary, the whole page hydrates at once |

Remember the one sentence of this lesson. **The server gives the elements, the JavaScript gives the handlers, and `hydrateRoot` joins the two without building the page again.**

## For the Interview

> **The Interview Question:** What is hydration, and how does hydrateRoot attach interactivity?

### How to Answer Clearly in 30 Seconds

"Hydration is how React makes server-rendered HTML interactive. The server already sent the finished page, but HTML cannot carry our event handlers. When the JavaScript arrives, `hydrateRoot` does three things:
1. **It runs every component again in the browser**, to learn which handler belongs to which element.
2. **It reuses the DOM nodes the server sent** instead of creating new ones, so the page does not change and what the user typed stays.
3. **It attaches the event handlers** to those nodes, and from then on React manages the page through state.

So hydration is not a second render of the page: the component code runs twice, but the DOM is built once. It needs the browser's first render to give the same output as the server. And it has a cost: every component runs in the browser, and without Suspense or Activity boundaries the whole page hydrates at once."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Is hydration a second render?"**
   **Yes for the component code, no for the DOM.** Every component runs again in the browser; the React docs say React "will run the rendering code again so that it can attach your event handlers to that HTML." But React creates no new elements: it reuses the ones the server sent. The docs add that, unlike with `createRoot`, you rarely call `root.render` on a hydrated root, "because the initial content was already rendered as HTML."
2. **"What happens if you use `createRoot` on a server-rendered page, or `hydrateRoot` on an empty one?"**
   Both are wrong. `createRoot` on server HTML "deletes all that HTML, and then re-creates all the DOM nodes from scratch", which "resets focus and scroll positions, and may lose other user input." `hydrateRoot` on an empty root is "not supported", and the docs say to use `createRoot` there. In short: server HTML in the root means `hydrateRoot`, and an empty root means `createRoot`. Many frameworks make this call for you.
3. **"Why is a server-rendered page sometimes slow to answer the first tap?"**
   Because the page looks ready before hydration ends. The browser still downloads the app and runs every component, and without boundaries "React must hydrate the entire page all at once", so one slow part delays every button. Wrapping slow parts in `<Suspense>` or `<Activity>` lets React hydrate the page in chunks, which is called Selective Hydration.

```tree caption="Interview summary: what hydrateRoot does, what it needs, and what it costs."
Hydration with `hydrateRoot`
- +What it does | Runs every component **in the browser** | **Reuses** the server's DOM nodes and **attaches** the handlers
- +What it needs | The browser's first render gives **the same output** as the server | A difference is a **bug** that rebuilds that part
- !What it costs | Every component **runs again** in the browser | Without boundaries, the **whole page** hydrates at once
```
