# Lecture 47: What StrictMode Runs Twice in Development

*(Why does React run some of your code twice in development, and what is it looking for?)*

> INTERVIEW QUESTION | ❱❱ MORE | Why does React run your components, effects, and ref callbacks twice in development, and how does StrictMode audit your code?

## VS | One Run in Production vs. Two Runs Under `<StrictMode>`: correct code gives the same page both ways

> When you start a new React project, the file `main.jsx` wraps your whole app in a component called `<StrictMode>`. **In development, it runs some of your code twice on purpose, so a doubled tile or an extra connection looks like a React bug.** The bug is in your code, so fix it with a pure render or a cleanup instead of removing the wrapper, because the same bug will reach your users in production.

Remember the `console.log` that printed twice in Lesson 14? You wrote one log inside a component, and the Console showed it two times. That was `<StrictMode>` at work. It sits in `main.jsx`, around `<App />`:

```jsx title="src/main.jsx"
import { ~StrictMode~ } from 'react'; // A named export of the react package
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

const root = createRoot(document.getElementById('root'));
root.render(
  ~<StrictMode>~ {/* Turns on the checks for App and every component inside it */}
    <App />
  </StrictMode>
);
```

> [!DEFINITION]
> **What is StrictMode?** [REVIEW] `<StrictMode>` is a component from the react package. A new Vite project already puts it around `<App />` in `main.jsx`. In development, it makes React call each component twice, to find components that are not pure. In production, it does nothing (Lesson 14).

The double call of Lesson 14 is only one part of the story. **In development, React runs three kinds of your code one extra time, on purpose:**
1. **Your component.** React calls the component function twice, and keeps one result.
2. **Your Effects.** Right after the first mount, React runs the cleanup of each Effect, and then its setup again.
3. **Your ref callbacks.** React does the same for the functions you pass to the `ref` attribute. Principle 4 shows what they are.

Think of how an electrician tests a light switch: on, off, and on again. If the light is on at the end, exactly as after one press, the switch works. React tests your code the same way. It runs your code, undoes it, runs it again, and the page must look as if it ran once.

Each extra run copies something that a real user will make React do later, in production:
1. The extra render copies the component rendering again after any update.
2. The extra Effect run copies the user leaving the page and coming back.
3. The extra ref callback run copies an element leaving the page and coming back.

**Why:** Correct code survives the extra run, and the user sees no difference. Code that changes old data while it renders, or leaves a connection open, shows its bug at once, on the very first load. Remove `<StrictMode>`, and the bug does not go away. It only waits, quietly, for a real user to find it. React's docs say it plainly: "When you fix your component to render in Strict Mode, you *also* fix many possible future production bugs."

Remember the one sentence of this lesson: **StrictMode does not create bugs. It shows the bugs already in your code, on the first load, so you fix the code and keep the test.**

### A Doubled Tile That Looks Like a React Bug

Here is what this looks like at work. A developer builds the stories tray at the top of a social feed, as on Instagram. It should show three round tiles: John's Story, Mia's Story, and Create Story. It also keeps a live connection to a stories server. The developer runs `npm run dev`, opens the page, and sees two problems on the very first load:

```page width=full caption="The stories tray on the first load with npm run dev: Create Story appears twice, and two connections are open."
line: John's Story
line: Mia's Story
line: Create Story
line: Create Story | bad
console: Encountered two children with the same key, `create`. Keys should be unique so that components maintain their identity across updates.
log: Connected. Active connections: 1 | stories.js:7
log: Connected. Active connections: 2 | stories.js:7
```

It looks as if React ran the code twice by mistake. Most developers go wrong right here. They decide that React has a bug, and they delete `<StrictMode>` from `main.jsx`. The Console goes quiet, the page shows three tiles, and every bug ships to the users.

React did not make the second tile or the second connection. Both come from the code of the tray. StrictMode only showed them early, and this lesson finds each one.

```tree caption="Each extra run of StrictMode in development copies something a real user makes React do later in production."
What StrictMode repeats on the first load in development
- +An extra render [`StoryTray`] | Copies **the component rendering again** after any update | A render that changes old data shows **its change twice**
- +An extra cleanup and setup for each Effect [`useEffect`] | Copies **the user leaving the page and coming back** | A missing cleanup leaves **one more connection open**
- +An extra cleanup and setup for each ref callback [`ref`] | Copies **an element leaving the page and coming back** | A missing cleanup leaves **old nodes in a list**
```

### The Rule of Thumb: can the user tell one run from two?

**Ask one question about every doubled line in development: does the user see or pay for something twice? If not, the double is expected, and you leave it. If yes, the bug is in your code: make the render pure, or give the setup a cleanup.**

React's docs give the same test for Effects: the user should not be able to tell one setup apart from setup, cleanup, and setup again.

A senior developer also knows the three classic mistakes:
1. **Deleting `<StrictMode>`.** The Console goes quiet, and the bug reaches users.
2. **Blocking the second run with a ref.** The Console goes quiet in the same way, and the bug stays.
3. **Reading an empty dependency array as "once per page load".** It means once per mount, and a user can mount the same component many times.

## SECTION | A Stories Tray with Three Tiles

Our page is the stories tray. Each tile is an `<li>` element. Below the tiles, a row of buttons scrolls the tray to one tile. The whole lesson builds it in four files:

```files title="stories-tray: File Explorer" caption="The four files of the stories tray inside src/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `StrictMode` and `App`, and mounts `<App />` inside `<StrictMode>`
  App.jsx | parent | Holds `stories` in state and renders `<StoryTray stories={stories} />`
  StoryTray.jsx | default export | Renders the tiles, connects to the stories server, and keeps the tile nodes for the scroll buttons
  stories.js | named export | Exports `createConnection`, a small stand-in for the stories server that counts the open connections
```

`main.jsx` is the file you saw above. `App` holds two stories in state and passes them to the tray:

```jsx title="src/App.jsx"
import { useState } from 'react';
import StoryTray from './StoryTray.jsx';

export default function App() {
  const [stories] = useState([
    { id: 'john', label: "John's Story" },
    { id: 'mia', label: "Mia's Story" },
  ]);
  return ~<StoryTray stories={stories} />~; // Passes the same array that state holds
}
```

`StoryTray` grows one piece at a time. Each principle adds one piece, first with its bug and then with its fix.

**PRINCIPLES:** `<StrictMode>` runs your code one extra time in development, and correct code survives the repeat. Five principles follow:
1. **Principle 1: StrictMode Checks Only the Components Inside It.** It turns on four checks, only in development, and it takes no props.
2. **Principle 2: A Pure Render Shows One Create Story Tile.** React calls the component twice, so a render that changes an array it received changes it twice.
3. **Principle 3: An Effect Cleanup Leaves One Connection.** React runs one extra cleanup and setup, so an Effect without a cleanup leaves two connections open.
4. **Principle 4: A Ref Callback Cleanup Keeps One Node per Tile.** React runs one extra cleanup and setup for ref callbacks too, so a list of nodes grows to six.
5. **Principle 5: Keep StrictMode On.** Removing it makes the Console look right, and the open connection still reaches users.

## PRINCIPLE | `<StrictMode>`: only the components inside it get the checks, and only in development

> [!PRINCIPLE]
> **Principle 1: StrictMode Scope: StrictMode Checks Only the Components Inside It**
>
> *Wrap the whole app in `<StrictMode>` in `main.jsx`; React then runs the four checks for every component inside it, and only in development.*
>
> In development, `<StrictMode>` adds an extra render, an extra Effect cleanup and setup, an extra ref callback cleanup and setup, and warnings for deprecated APIs. In production, it does nothing, so users never pay for it. It checks only the components inside it, and it takes no props, so nothing inside it can turn it off. When it wraps only one part of the app, React skips the extra Effect run on the first mount, because that run could never happen in production.
>
> **DO THIS:**
> ```jsx
> root.render(
>   ~<StrictMode>~ {/* Checks App and every component inside it */}
>     <App />
>   </StrictMode>
> );
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> root.render(
>   <>
>     <Header />
>     ~<StrictMode>~<Content /></StrictMode> {/* **WRONG:** in a new app, Header and Footer get no checks at all */}
>     <Footer />
>   </>
> );
> ```

`<StrictMode>` is a component, but it draws nothing. Like every component tag, it never appears in the Elements panel (Lesson 04). It only turns on four checks. React's docs list them, and all four run only in development:
1. **An extra render.** React calls each component one extra time, to find renders that are not pure.
2. **An extra cleanup and setup for every Effect.** It finds Effects with a missing cleanup.
3. **An extra cleanup and setup for every ref callback.** It finds a ref callback with a missing cleanup.
4. **Warnings for deprecated APIs.** React warns about old APIs it plans to remove, such as the `UNSAFE_` methods of class components. Modern apps rarely meet them, and a later lesson covers them.

The checks reach every component inside the wrapper, "no matter how deep" in the tree, as the docs say. The production build of `npm run build` runs none of them, so StrictMode never slows the app down for users.

```tree caption="The four checks that StrictMode turns on in development for every component inside it."
What `<StrictMode>` turns on in development
- +1. An extra render [`StoryTray`] | Finds **renders that are not pure**
- +2. An extra cleanup and setup for every Effect [`useEffect`] | Finds **a missing Effect cleanup**
- +3. An extra cleanup and setup for every ref callback [`ref`] | Finds **a missing ref cleanup**
- +4. Warnings for deprecated APIs [`UNSAFE_componentWillMount`] | Finds **old class component methods**
```

### VS | Around the Whole App vs. Around One Part: only the whole app gets the extra Effect run

You can also put `<StrictMode>` around one part of the app. Here is the example from React's docs, with the wrapper only around the main area:

```jsx title="StrictMode around one part of the app"
export default function App() {
  return (
    <>
      <Header />
      ~<StrictMode>~ {/* Checks only Sidebar and Content */}
        <main>
          <Sidebar />
          <Content />
        </main>
      </StrictMode>
      <Footer />
    </>
  );
}
```

It is the same tag as in `main.jsx`, but it is NOT the same thing! Moved down the tree, it checks less:
1. `Header` and `Footer` render once in development, because they sit outside the wrapper.
2. `Sidebar` and `Content` render twice in development, because they sit inside it.
3. An Effect inside `Content` runs its setup only once on the first mount. It gets no extra cleanup and setup.

The third point surprises most developers. Why does React skip it? On the first mount, the extra run would restart the Effects inside the wrapper while the Effects above them run once. No real user can cause that in production. The docs say React "will only enable behaviors that are possible in production."

Around the whole app, every Effect gets the extra run together. That is exactly what happens when a user leaves the page and comes back: every Effect of the page starts again.

```tree caption="StrictMode around the whole app versus around one part of it."
Where `<StrictMode>` sits
- +Around the whole app [`<StrictMode><App /></StrictMode>`] | **Every component** gets the extra render | **Every Effect** gets the extra cleanup and setup on the first mount
- !Around one part only [`<StrictMode><main>...</main></StrictMode>`] | `Header` and `Footer` **get no checks** | Effects inside **skip the extra run** on the first mount
```

### No Props, So Nothing Inside Can Turn It Off

Suppose two teams work on one app wrapped in `<StrictMode>`. One team likes the checks. The other team wants them off for its own components, and looks for a prop that turns StrictMode off further down the tree. There is none.

The docs say "`StrictMode` accepts no props" and "There is no way to opt out of Strict Mode inside a tree wrapped in `<StrictMode>`." Their advice to the two teams: "either reach consensus or move `<StrictMode>` down in the tree."

For a new app, the docs recommend wrapping the whole app, as our `main.jsx` does. When a framework creates the root for you, it has its own setting for StrictMode, so you look it up in the framework's docs (Lesson 46).

## PRINCIPLE | `stories.slice()`: two calls of the component give the same three tiles

> [!PRINCIPLE]
> **Principle 2: Double Rendering: A Pure Render Shows One Create Story Tile**
>
> *Keep every render pure: copy an array or object you received before you change it, so two calls give the same result.*
>
> In development, React calls the component body twice, and also the functions passed to `useState`, `set` functions, `useMemo`, and `useReducer`, and keeps one result. A pure render shows no difference. A render that changes an array it received, such as a prop from `App`, changes it twice, so the tray shows Create Story twice. Without StrictMode, the same render adds one more tile on every later render.
>
> **DO THIS:**
> ```jsx
> function StoryTray({ stories }) {
>   const items = ~stories.slice()~; // A copy: every call gives John, Mia, and one Create Story
>   items.push({ id: 'create', label: 'Create Story' });
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function StoryTray({ stories }) {
>   const items = stories;
>   items.~push~({ id: 'create', label: 'Create Story' }); // **WRONG:** changes App's array, so every render adds one more tile
> }
> ```

> [!DEFINITION]
> **What is a pure component?** [REVIEW] A pure component returns the same JSX for the same props and state, and it changes nothing that existed before it was called. You can call it once or ten times, and the result is the same. That is why React can call it twice in development without any harm (Lesson 14).

### A Tray That Adds Its Own Create Story Tile

The tray needs a Create Story tile at the end of the list. Here is the first version of `StoryTray.jsx`, the same tray React's docs use:

```jsx title="src/StoryTray.jsx"
export default function StoryTray({ stories }) {
  const items = ~stories~; // Looks like a new list, but it is the same array that App passed
  items.~push~({ id: 'create', label: 'Create Story' }); // Adds the tile to App's own array
  return (
    <ul className="tray">
      {items.map((story) => (
        <li key={story.id}>{story.label}</li>
      ))}
    </ul>
  );
}
```

The developer opens the page with `npm run dev`, and Create Story appears twice:

```page width=full caption="The tray with const items = stories in development: Create Story appears twice."
line: John's Story
line: Mia's Story
line: Create Story
line: Create Story | bad
console: Encountered two children with the same key, `create`. Keys should be unique so that components maintain their identity across updates.
```

See the problem? The `push` line runs twice, because React calls `StoryTray` twice. Here is the first load, in order:
1. `App` passes `stories`, an array with two items: John's Story and Mia's Story.
2. React calls `StoryTray` the first time. `push` adds Create Story to that array. It now holds three items.
3. StrictMode makes React call `StoryTray` a second time, with the same prop, so with the same array. `push` adds a second Create Story. The array now holds four items.
4. React shows the result of the second call, with four items. Two of them have the key `create`, so React also prints the warning about the same key.

This part is plain JavaScript, not React. In JavaScript, `const b = a` does not copy an array. It gives the same array a second name. So `const items = stories` is NOT a new list! It is a second name for the array that `App` holds in state. Then `push` changes a prop, and props are read-only (Lesson 08).

The docs call this component "not a pure function": "running it multiple times produces different results."

### VS | `const items = stories` vs. `stories.slice()`: the same array vs. a new copy

The fix is to add the tile to a copy. Here are the two ways to write the first line:

```jsx title="The same array, and a copy"
const items = ~stories~; // The same array: each call adds one more tile to App's state
const items = ~stories.slice()~; // A new copy: each call starts again from John and Mia
```

`slice()` with no arguments returns a new array with the same items. Now both calls start from John and Mia, and both give the same three tiles. The tray looks exactly as it would after one call.

The spread does the same job in one line (Lesson 19):

```jsx title="Copy, then add, in two ways"
const items = stories.slice(); items.push({ id: 'create', label: 'Create Story' }); // Copy, then add
const items = ~[...stories, { id: 'create', label: 'Create Story' }]~; // Copy and add in one line
```

Yes, it is the exact same thing! Both build a new array of three items, and both leave the array of `App` untouched.

```page width=full caption="The tray with stories.slice in development: three tiles, and a quiet Console."
line: John's Story
line: Mia's Story
line: Create Story | good
console: quiet
```

### Without StrictMode, the Extra Tile Only Waits

Turn StrictMode off, and the tray with `const items = stories` looks right on the first load. React calls `StoryTray` once, and the tray shows three tiles.

The bug is still there. Each time the tray renders again with the same array, `push` adds one more Create Story to it. That happens, for example, when some other state in `App` changes. The user sees a fourth tile, then a fifth. StrictMode shows the same bug on the first load, before any user sees it.

```tree caption="The same impure StoryTray with and without StrictMode."
`const items = stories` with `push`
- !With StrictMode in development | React calls `StoryTray` **twice on the first load** | **Two Create Story tiles** at once
- !Without StrictMode in production | React calls `StoryTray` **once on the first load** | **One more Create Story** on every later render
```

### What React Calls Twice, and What It Never Calls Twice

The component body is not the only code React calls twice. React's docs give the full list for development:
1. The top-level code of the component body. The code inside its event handlers does not count.
2. The functions you pass to `useState` and `useMemo`. The same goes for `useReducer` and for `set` functions, so an updater function (Lesson 16) and a reducer (Lesson 27) run twice too.

React uses the result of one call and ignores the other. A pure function gives the same result both times, so the page shows no difference.

**React never calls an event handler twice.** Event handlers do not need to be pure. When the user clicks a button, its handler runs once, in development and in production.

Put a `console.log` in the body of `StoryTray`, and it prints twice. With React DevTools installed, the docs add, the line from the second call appears slightly dimmed in the Console.

## PRINCIPLE | `return () => connection.disconnect()`: setup, cleanup, setup leaves one connection

> [!PRINCIPLE]
> **Principle 3: Effect Remount: An Effect Cleanup Leaves One Connection**
>
> *Return a cleanup that undoes what the setup did, so setup, cleanup, setup leaves the same result as one setup.*
>
> In development, React runs one extra cleanup and setup for every Effect right after the first mount, while the state and the DOM stay as they are. An Effect that connects without a cleanup ends at two active connections. In production, the same Effect opens one more connection every time the user leaves the tray and comes back. A cleanup that disconnects makes the extra run invisible to the user.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection();
>   connection.connect();
>   ~return () => connection.disconnect()~; // Setup, cleanup, setup leaves one connection
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection();
>   ~connection.connect()~; // **WRONG:** no cleanup, so every new mount leaves one more connection open
> }, []);
> ```

> [!DEFINITION]
> **What is an Effect cleanup?** [REVIEW] The setup is the function you pass to `useEffect`. React runs it after the component appears on the screen. If the setup returns a function, that function is the cleanup. React runs the cleanup when the component leaves the screen, so the cleanup must undo what the setup started: disconnect what it connected, stop what it started (Lesson 32).

### An Effect That Connects to the Stories Server

The tray stays connected to the stories server while it is on the screen. Our app has no real server, so a small file plays its part, like the chat stand-in of Lesson 32. It counts the open connections and prints the count:

```js title="src/stories.js"
let connections = 0;

export function createConnection() {
  return {
    connect() {
      ~connections = connections + 1~; // A real implementation would connect to the server
      console.log('Connected. Active connections: ' + connections);
    },
    disconnect() {
      ~connections = connections - 1~; // A real implementation would close the connection
      console.log('Disconnected. Active connections: ' + connections);
    },
  };
}
```

In `StoryTray.jsx`, an Effect with an empty dependency array opens the connection when the tray appears:

```jsx title="src/StoryTray.jsx, the Effect without a cleanup"
useEffect(() => {
  const connection = createConnection();
  ~connection.connect()~; // Opens the connection, and nothing ever closes it
}, []);
```

The developer opens the page and expects one connection. The Console shows two:

```page width=full caption="The tray with an Effect and no cleanup in development: the Console ends at two active connections."
line: John's Story
line: Mia's Story
line: Create Story
log: Connected. Active connections: 1 | stories.js:7
log: Connected. Active connections: 2 | stories.js:7
```

The two lines come from one mount of the tray, plus one extra cleanup and setup from StrictMode. Here is what happens, in order:
1. React mounts `StoryTray` and runs the setup. `connect` runs. Active connections: 1.
2. StrictMode runs the cleanup of the Effect. There is no cleanup, so nothing disconnects.
3. StrictMode runs the setup again. `connect` runs a second time. Active connections: 2.

The two lines look like two page loads, but they are NOT two page loads! The page loaded once, and the tray mounted once. Between the two setups, React keeps the state and the DOM exactly as they were. Only the Effect ran its cleanup and setup one extra time.

The empty dependency array still means what it always meant: the Effect runs once per mount (Lesson 32). StrictMode only adds one extra cleanup and setup right after the first mount, in development.

### VS | No Cleanup vs. a Cleanup That Disconnects: two connections vs. one

The fix is a cleanup that undoes the setup. The setup connects, so the cleanup disconnects:

```jsx title="src/StoryTray.jsx" startLine="7"
  useEffect(() => {
    const connection = createConnection();
    connection.connect();
    ~return () => connection.disconnect()~; // Closes this connection before the next setup
  }, []);
```

```page width=full caption="The tray with the cleanup in development: connect, disconnect, connect, and one active connection at the end."
line: John's Story
line: Mia's Story
line: Create Story
log: Connected. Active connections: 1 | stories.js:7
log: Disconnected. Active connections: 0 | stories.js:11
log: Connected. Active connections: 1 | stories.js:7
```

Now the same three steps end with one connection. This is the light switch again: on, off, on, and the light is on once.

For the user, one setup in production and setup, cleanup, setup in development must be the exact same thing: the same page and the same single connection. The docs call this extra run a **stress-test**. React runs at once the cleanup and the setup that the Effect will meet later, to prove that the cleanup really undoes the setup.

### Without StrictMode, the Connections Pile Up

Turn StrictMode off, and the Effect without a cleanup prints one line, `Active connections: 1`. The bug is still there:
1. The user goes to another page of the app. React unmounts `StoryTray`. No cleanup runs, so the connection stays open.
2. The user clicks Back. React mounts `StoryTray` again, and its setup opens a second connection. Active connections: 2.
3. Each further visit opens one more.

The docs describe it like this: "As the user navigates across the app, the connections would keep piling up." Every user pays for it with performance and network problems. StrictMode shows the same missing cleanup on the first load, in the developer's own Console.

One more fact: the cleanup does not run only on unmount. When a dependency changes, React also runs the cleanup before the next setup (Lesson 35).

## PRINCIPLE | Ref callback: its cleanup removes the node, so three tiles keep three nodes

> [!PRINCIPLE]
> **Principle 4: Ref Callback Cleanup: A Ref Callback Cleanup Keeps One Node per Tile**
>
> *Return a cleanup from every ref callback that removes exactly what the callback added.*
>
> React calls a ref callback with the DOM node when it adds the element to the page, and calls the returned cleanup when it removes the element. In development, StrictMode runs one extra cleanup and setup for every ref callback. A callback that pushes its node into a list, with a cleanup that removes nothing, leaves six nodes for three tiles. In production, the same list grows on every render and keeps the nodes of tiles that are gone.
>
> **DO THIS:**
> ```jsx
> <li
>   ref={(node) => {
>     itemsRef.current.push(node);
>     return () => {
>       const list = itemsRef.current;
>       ~list.splice(list.indexOf(node), 1)~; // Removes the node it added: three, zero, three
>     };
>   }}
> />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <li
>   ref={(node) => {
>     itemsRef.current.push(node);
>     return ~() => {}~; // **WRONG:** removes nothing, so the list holds six nodes for three tiles
>   }}
> />
> ```

### A Function in the `ref` Attribute

Remember the `ref` attribute from Lesson 31? You gave it a ref object from `useRef`, and React put the DOM node into its `current`. That was React's way of handing you the element, the way `getElementById` does in plain JavaScript.

The `ref` attribute can also take a function. Then React does not fill an object for you. It calls your function, and hands it the DOM node:

```jsx title="A function in the ref attribute"
<div
  ref={~(node) => {~ // React calls this with the div's DOM node when it adds the div to the page
    console.log('Attached', node);
    return ~() => {~ // React calls this when it removes the div from the page
      console.log('Clean up', node);
    };
  }}
/>
```

> [!DEFINITION]
> **What is a ref callback?** [NEW] A ref callback is a function you pass to the `ref` attribute. A callback is a function you hand over for someone else to call later, and here React calls it, never your code. When React adds the element to the page, the docs say the ref "gets attached": React calls your function with the DOM node. When React removes the element, the ref "is detached": React calls the cleanup your function returned. React 19 added this cleanup (Lesson 47).

So a ref callback has a setup and a cleanup, just as an Effect does. StrictMode tests it in the same way. In development, the Console shows Attached, then Clean up, then Attached again, for this one `<div>`.

### Why the Tray Needs a Ref Callback

The tray needs scroll buttons: one button for each tile, which scrolls the tray to that tile with `scrollIntoView`. For that, the tray needs the DOM node of every tile, in one list.

One `useRef` per tile cannot work. The tiles come from `map`, and a Hook cannot sit inside `map` (Lesson 31). So the tray keeps one ref that holds an array (Lesson 30):

```jsx title="src/StoryTray.jsx" startLine="5"
  const itemsRef = ~useRef([])~; // One list for the DOM nodes of all the tiles
```

Below the tiles, a `<nav>` renders one button for each item. Each button calls `scrollToStory` with the index of its item:

```jsx title="The scroll buttons below the tray, in src/StoryTray.jsx"
<nav>
  {items.map((story, index) => (
    <button
      key={story.id}
      ~onClick={() => scrollToStory(index)}~ // Mia's button calls scrollToStory with 1
    >
      {story.label}
    </button>
  ))}
</nav>
```

`scrollToStory` reads the node at that index from the list, and prints how many nodes the list holds:

```jsx title="src/StoryTray.jsx" startLine="16"
  function scrollToStory(index) {
    const list = itemsRef.current;
    console.log('Tiles in the list: ' + list.length);
    ~list[index].scrollIntoView~({ behavior: 'smooth', inline: 'center' }); // Scrolls the tray to the tile at index
  }
```

Each `<li>` gets a ref callback that pushes its own node into the list. Its cleanup is empty:

```jsx title="src/StoryTray.jsx, the ref callback with an empty cleanup"
{items.map((story) => (
  <li
    key={story.id}
    ref={(node) => {
      ~itemsRef.current.push(node)~; // Adds this tile's node to the list
      return ~() => {}~; // **WRONG:** the cleanup removes nothing from the list
    }}
  >
    {story.label}
  </li>
))}
```

### Three Tiles, Six Nodes in the List

The developer opens the page and clicks the Mia's Story button. The tray scrolls to Mia, as expected. But the Console says the list holds six nodes for three tiles:

```page width=full caption="The tray with an empty ref cleanup in development, after the user clicks Mia's Story: the tray scrolls, and the list holds six nodes."
line: John's Story
line: Mia's Story | good
line: Create Story
line: [John's Story] [Mia's Story] [Create Story]
log: Connected. Active connections: 1 | stories.js:7
log: Disconnected. Active connections: 0 | stories.js:11
log: Connected. Active connections: 1 | stories.js:7
log: Tiles in the list: 6 | StoryTray.jsx:18
```

**Beware! The page works, but the list behind it is already twice too long.** Here is how three tiles become six nodes on the first load:
1. React adds the three tiles to the page and calls each ref callback. The list holds three nodes.
2. StrictMode runs each cleanup. The cleanups are empty, so the list still holds three nodes.
3. StrictMode calls each ref callback again. Each one pushes its node a second time. The list holds six nodes.

The scroll still works on the first load, because the first three nodes of the list are the right ones. That is why this bug is so easy to miss.

### VS | An Empty Cleanup vs. a Cleanup That Removes the Node: six nodes vs. three

The fix is a cleanup that removes exactly the node the callback added. The docs do it with two array methods: `indexOf` finds the position of the node in the list, and `splice` removes one item at that position:

```jsx title="src/StoryTray.jsx" startLine="28"
            ref={(node) => {
              itemsRef.current.push(node);
              return () => {
                const list = itemsRef.current;
                ~list.splice(list.indexOf(node), 1)~; // Removes this tile's node from the list
              };
            }}
```

```page width=full caption="The tray with the ref cleanup in development, after the user clicks Mia's Story: the list holds three nodes."
line: John's Story
line: Mia's Story | good
line: Create Story
line: [John's Story] [Mia's Story] [Create Story]
log: Connected. Active connections: 1 | stories.js:7
log: Disconnected. Active connections: 0 | stories.js:11
log: Connected. Active connections: 1 | stories.js:7
log: Tiles in the list: 3 | StoryTray.jsx:18
```

Now the same three steps take the list from three nodes, to zero, and back to three. The docs say of this sequence: "This is expected." The list always holds one node for each tile on the page.

### Without StrictMode, the List Grows on Every Render

Turn StrictMode off, and the list with the empty cleanup starts with three nodes, so the bug looks gone. It is not:
1. The ref callback is an arrow function written inside `map`, so every render of the tray makes a new function.
2. When the tray renders again, React calls the cleanup of the old function, and then calls the new function with the same node.
3. With an empty cleanup, every render of the tray adds three more nodes to the list.
4. When a story expires and its tile leaves the tray, its node stays in the list. A scroll button can then reach the wrong tile, or a tile that is no longer on the page.

React's docs call a list like this a **memory leak**: memory that the app keeps holding long after it needs it. And when the scroll buttons stop working, the docs say: "This is a production bug!"

## PRINCIPLE | `<StrictMode>` stays on: removing it hides the open connection, it does not close it

> [!PRINCIPLE]
> **Principle 5: Keep StrictMode On: Removing StrictMode Hides the Open Connection**
>
> *Fix what StrictMode shows with a pure render or a cleanup; never remove StrictMode or block the second run to make the Console quiet.*
>
> Without StrictMode, an Effect with no cleanup shows one connection on the first load, just as the fixed Effect does. The bug is still there: each time the user leaves the tray and comes back, one more connection stays open in production. A ref that blocks the second setup hides the bug in the same way. A doubled line is a bug only when the user sees it or pays for it twice.
>
> **DO THIS:**
> ```jsx
> root.render(
>   ~<StrictMode>~ {/* Keeps the test on; the Effect returns a cleanup that disconnects */}
>     <App />
>   </StrictMode>
> );
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> root.render(~<App />~); // **WRONG:** the Console goes quiet, and the missing cleanup reaches every user
> ```

### VS | Removing StrictMode vs. Adding the Cleanup: the same Console on the first load, only one survives the user's next visit

Go back to the Effect without a cleanup from Principle 3. The developer sees two connection lines and wants one. There are two ways to get one:
1. Remove `<StrictMode>` from `main.jsx`, and leave the Effect as it is.
2. Keep `<StrictMode>`, and add the cleanup to the Effect.

```jsx title="Removing StrictMode, and keeping it"
root.render(~<App />~); // StrictMode removed: the Effect still has no cleanup
root.render(~<StrictMode><App /></StrictMode>~); // StrictMode kept: the Effect now disconnects in its cleanup
```

On the first load, both ways end with one active connection:

::: row caption="On the first load, the Console ends at one active connection with StrictMode removed and with the cleanup added."
::: col title="StrictMode removed, no cleanup" tag="the bug is hidden" tone=bad
```page size=mini
line: John's Story
line: Mia's Story
line: Create Story
line: [John's Story] [Mia's Story] [Create Story]
log: Connected. Active connections: 1 | stories.js:7
```
No extra run tests the Effect, so nothing shows the missing cleanup.
:::
::: col title="StrictMode kept, cleanup added" tag="the bug is fixed" tone=good
```page size=mini
line: John's Story
line: Mia's Story
line: Create Story
line: [John's Story] [Mia's Story] [Create Story]
log: Connected. Active connections: 1 | stories.js:7
log: Disconnected. Active connections: 0 | stories.js:11
log: Connected. Active connections: 1 | stories.js:7
```
The extra run proves that the cleanup closes the first connection.
:::
:::

Both Consoles end at one connection, so the two ways look the same. They are NOT the same thing! Only the way with the cleanup still has one connection after the user leaves the tray and comes back. With StrictMode removed, here is what users meet in production:
1. The user opens the feed. One connection opens.
2. The user goes to another page. React unmounts `StoryTray`. No cleanup runs, so the connection stays open.
3. The user clicks Back. React mounts `StoryTray` again, and a second connection opens. Active connections: 2.

The second connection comes from the user's own navigation: the same unmount and mount that StrictMode copied in development. **Removing StrictMode removed the test, not the bug.**

| The developer's choice | Console on the first load | After the user leaves the tray and comes back |
| :--- | :--- | :--- |
| **StrictMode removed, no cleanup** | `Active connections: 1` | `Active connections: 2`, and one more with every visit |
| **StrictMode kept, cleanup added** | `Active connections: 1` after connect, disconnect, connect | `Active connections: 1` |

### A Ref That Blocks the Second Setup Hides the Bug Too

There is a second way to hide the same bug (Lesson 32). The developer keeps StrictMode, stores the connection in a ref, and runs the setup only while that ref is still empty:

```jsx title="A ref that blocks the second setup"
const connectionRef = useRef(null);

useEffect(() => {
  if (~!connectionRef.current~) { // **WRONG:** skips the second setup, and still never disconnects
    connectionRef.current = createConnection();
    connectionRef.current.connect();
  }
}, []);
```

The Console now shows one connection line in development. The docs say this "doesn't fix the bug". The user leaves, the connection stays open, the user comes back, and "the connections would keep piling up."

The docs give the question to ask instead: "The right question isn't 'how to run an Effect once', but 'how to fix my Effect so that it works after remounting'."

### VS | A Double That Is Expected vs. a Double That Is a Bug: ask what the user sees

Not every doubled line needs a fix. Use the rule of thumb: if the user sees no difference, the double is expected. If the user sees or pays for something twice, it is a bug:
1. **Two fetches in the Network tab, with the `ignore` flag.** The user sees one answer, so this is expected. Production sends one request (Lesson 33).
2. **Two analytics visits from `logVisit`.** The user sees nothing, and production sends one visit (Lesson 35). The docs say: "We recommend keeping this code as is."
3. **Two purchases from an Effect.** This is a bug, because the user pays twice. Move the request that buys the product into the event handler of the Buy button, which React never calls twice (Lesson 32).

Some code must run once per app load, not once per mount, such as code that sets up the whole app when it starts. The docs put such code behind a top-level variable, `didInit`, or at the top level of a module, outside every component.

```js title="src/stories.js"
  return {

      console.log('Connected. Active connections: ' + connections);
```

```jsx title="src/StoryTray.jsx"

import { createConnection } from './stories.js';

export default function StoryTray({ stories }) {
  const itemsRef = useRef([]);

  useEffect(() => {
    const connection = createConnection();
    connection.connect();
    ~return () => connection.disconnect()~; // Principle 3: setup, cleanup, setup leaves one connection
  }, []);

  const items = ~stories.slice()~; // Principle 2: a copy, so both renders give three tiles
  items.push({ id: 'create', label: 'Create Story' });

  function scrollToStory(index) {
    const list = itemsRef.current;
    console.log('Tiles in the list: ' + list.length);
    list[index].scrollIntoView({ behavior: 'smooth', inline: 'center' });
  }

  return (
    <section>
      <ul className="tray">
        {items.map((story) => (
          <li
            key={story.id}
            ref={(node) => {
              itemsRef.current.push(node);
              return () => {
                const list = itemsRef.current;
                ~list.splice(list.indexOf(node), 1)~; // Principle 4: removes the node it added
              };
            }}
          >
            {story.label}
          </li>
        ))}
      </ul>
      <nav>
        {items.map((story, index) => (
          <button key={story.id} onClick={() => scrollToStory(index)}>
            {story.label}
          </button>
        ))}
      </nav>
    </section>
  );
}
```

### What React Runs on the First Load in Development

`main.jsx` renders `<StrictMode>`, and React works through the components inside it from the top down. Every step that StrictMode repeats now gives the same result both times:

```tree dir=right caption="The order in which React runs the code of the tray on the first load in development, and what StrictMode repeats at each step."
What React runs inside `<StrictMode>` on the first load
- +1. `App` is called twice [`App`] | Holds `stories` in state | Passes the **same array** to `StoryTray` both times
- +2. `StoryTray` is called twice [`stories.slice`] | Copies `stories` and adds Create Story | Both calls give **three tiles**
- +3. The first setup [`ref` `useEffect`] | Each `<li>` adds its node, then the Effect connects | **Three nodes** and **one connection**
- +4. The extra cleanup [`ref` `useEffect`] | Each `<li>` removes its node, then the Effect disconnects | **Zero nodes** and **zero connections**
- +5. The extra setup [`ref` `useEffect`] | Each `<li>` adds its node again, then the Effect connects again | The list ends at **three nodes**, and the Console at **one active connection**
```

| What StrictMode repeats in development | What a user makes React do later in production | The bug it shows | The fix |
| :--- | :--- | :--- | :--- |
| **An extra render** | Any update that renders the tray again | Create Story twice, from `push` on the array `App` passed | Copy with `slice` or the spread before adding |
| **An extra Effect cleanup and setup** | Leaving the page and coming back | Two active connections | A cleanup that calls `disconnect` |
| **An extra ref callback cleanup and setup** | A tile leaving the page and coming back | Six nodes in the list for three tiles | A cleanup that removes the node with `splice` |
| **No extra run at all, with StrictMode removed** | The same navigation, with no test before it | A quiet Console and a connection left open | Keep StrictMode on and fix the code |

Remember the one sentence of this lesson. **StrictMode does not create bugs. It shows the bugs already in your code, on the first load, so you fix the code and keep the test.**

## For the Interview

> **The Interview Question:** Why does React run your components, effects, and ref callbacks twice in development, and how does StrictMode audit your code?

### How to Answer Clearly in 30 Seconds

"In development, `<StrictMode>` runs part of our code one extra time on purpose. It looks for bugs that real users would meet later. It turns on four checks for every component inside it:
1. **An extra render.** React calls the component body twice and keeps one result, and the same goes for the functions passed to `useState`, `set` functions, `useMemo`, and `useReducer`. A pure render shows no difference. Event handlers are never called twice.
2. **An extra cleanup and setup for every Effect.** This copies a user who leaves the page and comes back. It shows a missing cleanup, such as a connection left open.
3. **An extra cleanup and setup for every ref callback.** This shows a ref callback whose cleanup does not undo its setup.
4. **Warnings for deprecated APIs.**

The bugs it shows are already in the code. The fix is code that survives the repeat, a pure render or a cleanup, never removing StrictMode. In production, StrictMode does nothing."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"My Effect has an empty dependency array, yet it runs twice. How do I make it run once?"**
   We do not. An empty dependency array means once per mount, and StrictMode adds one extra cleanup and setup after the first mount in development. Blocking the second run with a ref only hides the bug. In production, the user leaves the page and comes back, and the missing cleanup leaves one more connection open each time. The docs put the right question this way: not "how to run an Effect once", but "how to fix my Effect so that it works after remounting". So we return a cleanup that undoes the setup. Code that must run once per app load goes behind a top-level variable such as `didInit`, outside every component.
2. **"Does StrictMode slow down the app or change anything in production?"**
   No. All four checks run only in development, and the production build of `npm run build` runs none of them. The docs say Strict Mode "has no effect in production, so it won't slow down the app for your users." One practical result: we never measure speed in development, because every component renders twice there. We measure a production build.
3. **"What changes if you wrap only one part of the app in StrictMode?"**
   Only the components inside the wrapper get the checks, and the components outside it render once. React also skips the extra Effect cleanup and setup on the first mount. Running the Effects of the children twice while their parents run once could never happen in production. `<StrictMode>` takes no props, so nothing inside it can turn it off. To leave a part out, we move the wrapper down the tree. For a new app, the docs recommend wrapping the whole app.

```tree dir=right caption="Interview summary: the wrong and the right way to respond to a doubled line in development."
A doubled line in development
- !Hide it [`<App />` `connectionRef`] | The Console goes quiet | The bug **reaches every user** in production
- +Fix it [`stories.slice` `connection.disconnect`] | Setup, cleanup, setup gives **the same result as one setup** | The page is **the same in development and production**
```
