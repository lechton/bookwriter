# Lecture 45: Form Resets, requestFormReset, and Progressive Enhancement

*(Why does a form forget what the user typed after the server says no, and how do you keep it?)*

> INTERVIEW QUESTION | ❱❱ MORE | How do React 19 form actions manage automatic form resets, manual requestFormReset, and progressive enhancement?

---

## VS | A Refusal for the User vs. a Success for React: React resets the form after every action that does not throw

**React automatically resets every uncontrolled `<form>` after its action finishes, so when the server rejects a submission you must pass back the typed values in `defaultValue`.**

Say a user types a username and an email into a Create Account form and clicks Submit. The server replies that the username is already taken, so the user wants to fix the username without retyping the whole form.

**Why:** Whenever a form action finishes without throwing, React assumes the submit succeeded and resets every field to its starting `defaultValue`. Unless your action returns the submitted text so your JSX can pass it into `defaultValue`, a server refusal wipes out everything the user just typed.

Remember `form.reset()`? The browser gives this method to every `<form>` element. Call it, and every field of the form goes back to the text it started with:

```js title="Resetting a form in plain JavaScript"
const form = document.getElementById('signup');
~form.reset()~; // Every field goes back to the text it started with
```

In Lesson 41, your `onSubmit` handler called `reset()` by hand. With a function in the `action` of a form, you never write that line. React resets the form for you, right after your function ends:

```jsx title="The same reset in React"
<form ~action={save}~> {/* React calls save, then resets the form when save ends */}
```

> [!DEFINITION]
> **The action of a form.** [REVIEW] In plain HTML, the `action` of a form holds a URL. The browser sends the fields there and loads a new page.
> In React 19, `action` can also hold a function: `<form action={save}>`.
> When the user clicks the submit button, React stops the browser from sending the form, reads every field that has a `name`, and calls `save` with that form data. The page does not reload (Lesson 41).

That sounds like a gift. Now watch what it does when the server says no.

Here is a Create account form. The user types `john` and `john@mail.com`, then clicks Create account:

```page caption="The Create account form after the user has typed a username and an email, before the click."
heading: Create account
form:
  field: Username | john
  field: Email | john@mail.com
  submit: Create account
console: quiet
```

One second later, a line says the username is taken. And both fields are empty:

```page caption="The same form one second after the click: the refusal line, and two empty fields."
heading: Create account
form:
  field: Username | | bad
  field: Email | | bad
  submit: Create account
line: Username john is taken. | bad
console: quiet
```

The email was right. Now the user must type it again.

Why did this happen? For the user, `Username john is taken.` is a refusal. For React, it is a success.

React never reads the text your function returns. It asks one question only: "Did the function throw an error?" A returned error message is not a thrown error. So React counts the refusal as a success, and it resets the form.

```tree caption="The same answer from the server, read by the user and by React."
What `Username john is taken.` means
- !For the user | The server **said no** | The user expects to **fix one word** and try again
- +For React | The action **returned a value** and **did not throw** | The action **succeeded**, so React **resets the form**
```

So what does the reset put back? The default value of each field.

> [!DEFINITION]
> **The default value of a field.** [NEW] Every `<input>` field holds two texts. The first is the text it shows right now, the one the user types. The second is its default value, the text it started with.
> In plain HTML you set the default value with the `value` attribute: `<input value="John">`. In React you set it with the `defaultValue` prop: `<input defaultValue="John" />` (Lesson 20). The user can type over it freely.
> A reset throws away what the user typed and puts the default value back. A field with no default value goes back to empty (Lesson 45).

Our two fields have no default value, so the reset empties them.

That gives us the key idea of this lesson. You cannot switch the reset off. But you decide what it goes back to. Make what the user typed the new default value, and the reset puts that text back.

### The Rule of Thumb: what is the default value of this field?

**Ask one question about every field: what is its default value? After the action, that is what the user sees.**

Developers often think React resets the form only when the account was created. It does not. React resets it after every action that does not throw.

Two things are at stake for the user:
1. **After every refusal**, the user types the whole form again, including the parts that were right.
2. **On a slow phone**, the user may click Create account before the JavaScript of the page has loaded. Whether that click sends anything depends on how the form is built.

There are three ways to keep the text after a refusal:
1. **`defaultValue` from the state the action returned.** This is the React 19 way, for forms built on `<form action>` and `useActionState`. The form stays plain HTML, so it can work before JavaScript loads.
2. **A controlled field, with `value` and `onChange`** (Lesson 20). React does not reset a controlled field at all. It fits a form that must change the page on every keystroke anyway, such as a live hint under the field.
3. **`onSubmit` with `e.preventDefault()`** (Lessons 11 and 41). React does no reset here, so the text stays after a refusal. After a success, your code asks for the reset itself, with `requestFormReset`. It fits an older form that a team moves to Actions step by step.

```tree caption="Three ways to keep the user's text after the server says no."
Three ways to keep the text after a refusal
- +1. `defaultValue` from state [`defaultValue={state.email}`] | React **still resets** the form | The reset **puts back** the text the action returned
- +2. `value` and `onChange` [`value={email}`] | React **does not reset** a controlled field | The page **renders on every keystroke**
- +3. `onSubmit` and `requestFormReset` [`e.preventDefault`] | **No automatic reset** happens | Your code **asks for the reset** when the action ends
```

## SECTION | A Create Account Form with a Username and an Email

Our page is the Create account form, in a small Vite app. It has a Username field, an Email field, and a Create account button.

The server is a stand-in: a function that waits one second and refuses the username `john`. A real server refuses a name the same way when someone already has it.

```files title="create-account: File Explorer" caption="How the files of our Create account form sit inside src/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it into `#root`
  App.jsx | form | Exports `App` as default and imports `createAccount` from `./api.js`
  api.js | stand-in server | Exports `createAccount`, which waits one second and refuses `john`
```

Here is the stand-in server:

```js title="src/api.js"
const takenUsernames = ['john'];

export function createAccount(username) {
  return new Promise(resolve => {
    setTimeout(() => {
      if (~takenUsernames.includes(username)~) { // john is taken
        resolve(`Username ${username} is taken.`);
      } else {
        resolve(null); // Any other name is free
      }
    }, 1000);
  });
}
```

`createAccount` returns a Promise. After one second, it gives back an error message for `john`, and `null` for any other name. The form waits for it with `await`.

Each principle below adds one step to this form, or breaks it on purpose:

**PRINCIPLES:** When the action ends without throwing, React resets the form. The reset puts every field back to its default value. Five principles follow:
1. **Principle 1: A Successful Action Empties the Form.** React resets every uncontrolled field after the function in `<form action>` returns. No line of your code does it.
2. **Principle 2: A Returned Error Is a Success for React.** The refusal line appears, and the fields empty at the same moment.
3. **Principle 3: `defaultValue` From State Brings the Text Back.** The action returns what the user typed, and the reset puts it back.
4. **Principle 4: `requestFormReset` Resets a Form Submitted Through `onSubmit`.** React never resets that form by itself, so your code asks for the reset.
5. **Principle 5: `name` and a Submit Button Let the Browser Send the Form Alone.** A form works before its JavaScript loads only when it is real HTML.

## PRINCIPLE | `action={save}`: React resets every uncontrolled field after save returns

> [!PRINCIPLE]
> **Principle 1: A Successful Action Empties the Form**
>
> *When the function passed to `<form action>` ends without throwing, React resets every uncontrolled field of that form.*
>
> No line of your code empties the fields, and the page does not reload. React calls the function with the form data. When the function returns, React puts every uncontrolled field back to its default value. A controlled field is not reset, because it shows what its state holds.
>
> **DO THIS:**
> ```jsx
> <form action={save}>
>   <input ~name="username"~ /> {/* Uncontrolled: React empties it after save returns */}
>   <button type="submit">Save</button>
> </form>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <form action={save}>
>   <input name="username" ~value={name}~ onChange={e => setName(e.target.value)} /> {/* **WRONG:** a controlled field is not reset, so john stays after Save */}
>   <button type="submit">Save</button>
> </form>
> ```

Start with the smallest form that has an action: one field, one button, and a function that only reads the field.

```jsx title="src/App.jsx"
function save(formData) {
  console.log(formData.get('username')); // Prints john
}

export default function App() {
  return (
    <form ~action={save}~> {/* React calls save with the form data on submit */}
      <label>Username <input name="username" /></label>
      <button type="submit">Save</button>
    </form>
  );
}
```

The user types `john` and clicks Save:

```page caption="The small form before the click, with john typed into the Username field."
form:
  field: Username | john
  submit: Save
console: quiet
```

```page caption="The same form right after the click: the Console shows john, and the field is empty."
form:
  field: Username | | good
  submit: Save
log: john | App.jsx:2
```

The field is empty, and the page did not reload. Here is what happened, in order:
1. The user clicked Save. React stopped the browser from sending the form, and called `save` with the form data.
2. `save` printed `john` and returned without throwing an error.
3. The action succeeded, so React reset the form. Every uncontrolled field went back to its default value.
4. Our field has no default value, so it is empty.

It is the same reset as `form.reset()`, the one you called by hand in Lesson 41. React's docs put it in one sentence: after the action function succeeds, all uncontrolled field elements in the form are reset. For React, succeeds means one thing only: the function ended without throwing an error.

Something that can be tricky: the word uncontrolled. A plain `<input name="username" />` is uncontrolled: the browser keeps its text (Lesson 40). A field with `value` and `onChange` is controlled: it shows what its state holds (Lesson 20). The reset does not change state, so a controlled field still shows `john` after Save.

Remember: the action ends without throwing, so React resets the form.

## PRINCIPLE | `return error`: the refusal line appears, and React still resets the form

> [!PRINCIPLE]
> **Principle 2: A Returned Error Is a Success for React**
>
> *An action that returns an error message has succeeded for React, so React empties the fields while the error line appears.*
>
> React does not read the message an action returns. It only knows whether the action threw. A known error, such as a taken username, is returned as state, as React's docs recommend. So React resets the form, and the user loses every field at the moment the refusal appears. Throwing the error instead does not save the text: it hands the whole form to the nearest Error Boundary.
>
> **DO THIS:**
> ```jsx
> if (error) {
>   ~return error;~ // The refusal line appears; Principle 3 brings the text back
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> if (error) {
>   ~throw new Error(error);~ // **WRONG:** no refusal line: the nearest Error Boundary replaces the form
> }
> ```

Now we build the real form. It needs to show the server's answer under the button, so it keeps that answer with `useActionState`.

> [!DEFINITION]
> **useActionState.** [REVIEW] `useActionState(signUp, '')` returns two things. The first is the state: whatever `signUp` returned last, and `''` before the first click. The second is `formAction`, which you pass to `<form action>`.
> On submit, React calls `signUp` with two arguments: the previous state and the form data. Whatever `signUp` returns becomes the new state, and React renders the component again.
> A known error, such as a taken name, is returned, not thrown (Lesson 42).

```jsx title="src/App.jsx"
import { useActionState } from 'react';
import { createAccount } from './api.js';

async function signUp(previousState, formData) {
  const username = formData.get('username');
  const error = await createAccount(username);
  if (error) {
    ~return error;~ // Returned, not thrown: for React, the action succeeded
  }
  return `Welcome, ${username}!`;
}

export default function App() {
  const [message, formAction] = useActionState(signUp, '');

  return (
    <form ~action={formAction}~> {/* React resets the form after signUp returns */}
      <h1>Create account</h1>
      <label>Username <input name="username" /></label>
      <label>Email <input name="email" /></label>
      <button type="submit">Create account</button>
      {message && <p>{message}</p>}
    </form>
  );
}
```

`message` is whatever `signUp` returned last. Before the first click it is `''`, so no line shows.

**The refusal line and the empty fields arrive together.** Here is what happens, in order:
1. The user types `john` and `john@mail.com`, then clicks Create account.
2. React calls `signUp` with the previous state `''` and the form data.
3. `createAccount` waits one second and answers `'Username john is taken.'`.
4. `signUp` returns that text. It did not throw, so for React the action succeeded.
5. React renders `App` with the new state, so the line `Username john is taken.` appears.
6. React resets the form, so both fields are empty.

```page caption="The Create account form one second after the click with the username john."
heading: Create account
form:
  field: Username | | bad
  field: Email | | bad
  submit: Create account
line: Username john is taken. | bad
console: quiet
```

The Console stays quiet, because nothing in the code is broken.

Something that can be tricky: this bug hides well. A developer who tests with a free name, such as `john7`, sees `Welcome, john7!` and two empty fields. That is exactly right after a success. The bug report comes later, from a real user whose name was taken.

One more detail. The reset changes only the fields on the page. It does not change the state of `useActionState`. So `message` still holds the refusal, and the line stays on the screen.

### VS | `return error` vs. `throw new Error(error)`: only a returned value becomes state

A developer who finds this bug may try to stop the reset by throwing the error instead of returning it:

```jsx title="With return error and with throw new Error"
if (error) {
  ~return error;~ // Returned: React treats it as a normal answer
}

if (error) {
  ~throw new Error(error);~ // **WRONG:** thrown: React treats it as an unexpected error
}
```

Both lines stop `signUp` with the same message. But only a returned value becomes state:
- **With `return error`**, React stores the message as the new state, shows the line, and resets the form.
- **With `throw new Error(error)`**, the message never becomes state. React passes the error to the nearest Error Boundary (Lesson 72). Our page has none, so the whole form disappears from the screen (as seen in Lesson 42).

So the user loses the fields and the refusal line together. Returning the message stays right. The text has to come back another way, and Principle 3 shows it.

## PRINCIPLE | `defaultValue` from state: the reset puts back what the user typed

> [!PRINCIPLE]
> **Principle 3: defaultValue From State Brings the Text Back**
>
> *To keep the user's text after a refusal, return it in the state of the action and give each field `defaultValue` from that state.*
>
> The reset cannot be stopped, but it only puts each field back to its default value. When the action returns what the user typed and each field reads it through `defaultValue`, the reset puts that text back. After a success, the action returns empty texts, and the same reset empties the form.
>
> **DO THIS:**
> ```jsx
> <input name="email" ~defaultValue={state.email}~ /> {/* After a refusal, the field shows john@mail.com again */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input name="email" ~value={state.email}~ /> {/* **WRONG:** value without onChange freezes the field, and the user cannot type */}
> ```

React gives no option to switch the reset off for a form with a function in `action`. But remember what the reset does: it puts each field back to its default value. And you decide the default value.

```jsx title="A field with no default value vs. a field whose default value comes from state"
<input name="email" /> {/* The reset empties the field */}
<input name="email" ~defaultValue={state.email}~ /> {/* The reset puts back whatever state.email holds */}
```

It is the exact same reset for both fields. Only the default value differs. So the fix has two parts:
1. **The action returns the text the user typed**, together with the message.
2. **Each field reads that text through `defaultValue`.**

Then the reset itself puts the user's text back.

### The state becomes one object

The state now holds three things: the message, the username, and the email. So it becomes one object.

On a refusal, `signUp` returns the message and the two texts it read from the form. On a success, it returns empty texts, because after a success the user wants an empty form:

```jsx title="src/App.jsx" startLine="4"
const initialState = { message: '', username: '', email: '' };

async function signUp(previousState, formData) {
  const username = formData.get('username');
  const email = formData.get('email');
  const error = await createAccount(username);
  if (error) {
    return ~{ message: error, username, email }~; // Keeps what the user typed
  }
  return ~{ message: `Welcome, ${username}!`, username: '', email: '' }~; // Empties both fields
}
```

The return line of the refusal uses a JavaScript shortcut. When a key has the same name as the variable that holds its value, you write the name once:

```js title="The shortcut and the long form"
{ ~username, email~ } // The shortcut
{ username: username, email: email } // The same object, written in full
```

Each field now reads its default value from the state:

```jsx title="src/App.jsx" startLine="16"
export default function App() {
  const [state, formAction] = useActionState(signUp, initialState);

  return (
    <form action={formAction}>
      <h1>Create account</h1>
      <label>Username <input name="username" ~defaultValue={state.username}~ /></label> {/* The reset puts back john after a refusal */}
      <label>Email <input name="email" ~defaultValue={state.email}~ /></label> {/* The reset puts back john@mail.com after a refusal */}
      <button type="submit">Create account</button>
      {state.message && <p>{state.message}</p>}
    </form>
  );
}
```

**After a refusal, the same reset that used to empty the fields now fills them with what the user typed.** Here are both clicks, in order:
1. The user types `john` and `john@mail.com`, then clicks Create account.
2. The action returns an object with the refusal message, together with `john` and `john@mail.com`.
3. React renders `App` with this state. Each field gets a new default value: `john` and `john@mail.com`.
4. React resets the form. Each field goes back to its default value, so the fields show `john` and `john@mail.com` again.
5. The user changes `john` to `john7` and clicks again.
6. `signUp` returns an object with `Welcome, john7!` and two empty texts.
7. The default values are now empty, so the same reset empties both fields.

### VS | `defaultValue={state.email}` vs. `value={state.email}`: value without onChange freezes the field

`value` is the prop that shows text in a field, so it is tempting to write `value={state.email}`. It looks the same as `defaultValue`, but it is not.

`value` without `onChange` freezes the field (Lesson 20). The user can no longer type a single letter into the Email field, and React prints a warning:

```page width=full caption="The Create account form with value={state.email} on the Email field: the field refuses every letter."
heading: Create account
form:
  field: Username |
  field: Email | | bad
  submit: Create account
console: You provided a `value` prop to a form field without an `onChange` handler. This will render a read-only field. If the field should be mutable use `defaultValue`. Otherwise, set either `onChange` or `readOnly`.
```

A controlled field, with both `value` and `onChange`, keeps the text too, because React does not reset a controlled field at all. The difference is how often React renders `App`:
- **With a controlled field**, React renders `App` after every keystroke.
- **With `defaultValue`**, React renders `App` only when the action returns. While the user types, the browser alone keeps the text.

```tree caption="Three ways to write the Email field, and what each one does after a refusal."
The Email field after `Username john is taken.`
- !No default value [`name="email"`] | The reset puts the field back to **empty** | The user must **type the email again**
- +`defaultValue` from state [`defaultValue={state.email}`] | The reset puts back **what the user typed** | `App` renders **only when the action returns**
- !`value` without `onChange` [`value={state.email}`] | The field **freezes** | The user **cannot type**, and React prints a **warning**
```

Remember: the reset puts every field back to its default value. So make the default value the text you want to keep.

## PRINCIPLE | `requestFormReset(form)`: a form submitted through onSubmit resets when the action ends

> [!PRINCIPLE]
> **Principle 4: requestFormReset Resets a Form Submitted Through onSubmit**
>
> *When a form is submitted without the `action` prop, call `requestFormReset(form)` from `'react-dom'` inside the Transition, so the fields reset when the action ends.*
>
> React resets a form for us only after a function passed to `<form action>`. A form submitted through `onSubmit` keeps its old text after a success. `requestFormReset` asks React for the same reset, and React waits for the Transition. The browser's `form.reset()` empties the fields at once, before the server has answered.
>
> **DO THIS:**
> ```jsx
> startTransition(() => {
>   formAction(new FormData(form));
>   ~requestFormReset(form);~ // The fields reset together with the new state
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> startTransition(() => {
>   formAction(new FormData(form));
> });
> ~form.reset();~ // **WRONG:** the fields empty at the click, before the server says whether the name is free
> ```

### VS | `form.reset()` vs. `requestFormReset(form)`: the browser resets now, React resets when the action ends

You know `form.reset()` from plain JavaScript. React DOM adds a function with the same job, `requestFormReset`:

```jsx title="The browser's reset vs. the reset of React DOM"
import { requestFormReset } from 'react-dom';

~form.reset();~ // The browser empties the fields right now
~requestFormReset(form);~ // React empties the fields when the current Transition ends
```

Both put every field back to its default value. They differ only in when the fields change:
- **With `form.reset()`**, the browser resets the fields at once, even while the action still waits for the server.
- **With `requestFormReset(form)`**, React waits for the Transition the call was made in. So the fields change in the same update as the new state.

This is the reset React already does for us after a function in `<form action>`. You ask for it by hand only when the form is submitted another way.

### React never resets a form submitted through `onSubmit`

Some forms do not pass the action to `<form action>`. A team moving an older form to Actions often keeps its `onSubmit` handler (Lessons 11 and 41), and calls `formAction` from it.

React's docs say `formAction` must then be called inside a Transition. So the handler wraps the call in `startTransition`, which comes from `'react'`. A later lesson covers Transitions in full (Lesson 67). For now, one fact is enough: React knows when the Transition ends, and that is when `signUp` has finished.

```jsx title="src/App.jsx" startLine="1"
import { useActionState, startTransition } from 'react';
import { createAccount } from './api.js';
```

```jsx title="src/App.jsx" startLine="16" bad="23,28"
export default function App() {
  const [state, formAction] = useActionState(signUp, initialState);

  function handleSubmit(e) {
    e.preventDefault();
    const form = e.currentTarget;
    startTransition(() => {
      ~formAction(new FormData(form))~; // Runs signUp, but no form action ran, so nothing resets the form
    });
  }

  return (
    <form ~onSubmit={handleSubmit}~> {/* No form action: React never resets this form by itself */}
      <h1>Create account</h1>
      <label>Username <input name="username" defaultValue={state.username} /></label>
      <label>Email <input name="email" defaultValue={state.email} /></label>
      <button type="submit">Create account</button>
      {state.message && <p>{state.message}</p>}
    </form>
  );
}
```

`e.currentTarget` is the form element whose submit handler is running. The handler saves it in `form` before the Transition starts.

**The welcome line appears, and the fields still show what the user typed.** Here is what happens, in order:
1. The user types `john7` and `john@mail.com`, then clicks Create account.
2. `handleSubmit` stops the browser from sending the form, and calls `formAction` inside a Transition.
3. `signUp` returns an object with `Welcome, john7!` and two empty texts.
4. React renders `App` with the new state. The default values are now empty.
5. Nothing resets the form, because no function in `<form action>` ran. The fields keep what the user typed.

```page caption="The Create account form submitted through onSubmit, after a success: the welcome line next to the old text."
heading: Create account
form:
  field: Username | john7 | bad
  field: Email | john@mail.com | bad
  submit: Create account
line: Welcome, john7! | good
console: quiet
```

### The fix: ask for the reset inside the Transition

The fix is one import and one line, inside the same `startTransition`:

```jsx title="src/App.jsx" startLine="1"
import { useActionState, startTransition } from 'react';
import { ~requestFormReset~ } from 'react-dom'; // The reset function comes from React DOM
import { createAccount } from './api.js';
```

```jsx title="src/App.jsx" startLine="20"
  function handleSubmit(e) {
    e.preventDefault();
    const form = e.currentTarget;
    startTransition(() => {
      formAction(new FormData(form));
      ~requestFormReset(form);~ // The fields reset when signUp has finished, like a form action
    });
  }
```

Now the form behaves for the user exactly like the form with `<form action={formAction}>`. After a success, the fields are empty. After a refusal, the reset puts back the text from `defaultValue`, as in Principle 3. The handler only asks by hand for the reset that `<form action>` gets from React.

### `form.reset()` empties the fields too early

`form.reset()` is the method developers already know, so it is tempting to call it right after starting the action. But the browser runs it at once.

The fields empty the moment the user clicks, a full second before the server answers. If the answer is `Username john is taken.`, the user has already watched the form clear, as if the account was created. One second later, the refusal appears, and the fields fill again with the default values from the new state.

React's docs do call `reset()` at once in one example: a chat that shows each new message right away with `useOptimistic`. There, the user always wants the field empty right after sending, whatever the server answers. A sign-up form is the opposite case: the user wants the text kept until the server says yes.

## PRINCIPLE | `name` and `type="submit"`: the browser can send the form before JavaScript loads

> [!PRINCIPLE]
> **Principle 5: name and a Submit Button Let the Browser Send the Form Alone**
>
> *A form works before its JavaScript loads only when it is a real `<form>` with a `name` on every field and a real submit button, and its action is one the browser can send by itself.*
>
> Progressive enhancement gives every user a basic version that works, and adds the richer version of React when the JavaScript runs. The browser can send a form alone only from HTML: the `<form>`, the named fields, the submit button, and a URL or a Server Function in `action`. A function from our own code needs React running, and a click on a `<div>` needs a handler that has not loaded yet.
>
> **DO THIS:**
> ```jsx
> <form action={formAction}>
>   <input ~name="email"~ /> {/* The browser and FormData both read this name */}
>   <button ~type="submit"~>Create account</button> {/* A click submits the form, with or without a handler */}
> </form>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <section>
>   <input value={email} onChange={e => setEmail(e.target.value)} />
>   <div ~onClick={handleCreate}~>Create account</div> {/* **WRONG:** no form, no name, no submit button: nothing is sent before JavaScript loads */}
> </section>
> ```

Picture the same Create account form on a phone with a slow connection. The page has appeared, but the JavaScript of the app is still downloading. React's docs call this file the JavaScript bundle. The user clicks Create account.

Does that click send anything? It depends on what the `action` of the form holds.

### VS | `action="/signup"` vs. `action={formAction}`: the browser understands a URL, only React can call a function

```jsx title="An action with a URL vs. an action with a function"
<form ~action="/signup"~ method="post"> {/* The browser sends the form to /signup by itself */}
<form ~action={formAction}~> {/* Only React can call formAction, so React must be running */}
```

The two forms look the same on the screen. But the browser understands a URL without any JavaScript. It reads every field that has a `name`, and sends the values to `/signup` with the POST method.

A function is different. It exists only inside our JavaScript. Until React runs, nobody can call it.

> [!DEFINITION]
> **Progressive enhancement.** [NEW] A page built with progressive enhancement starts from a basic version that works with plain HTML, and adds the richer version when the browser can run more. MDN describes it as giving a baseline of essential content and functionality to as many users as possible, then adding the richer version for browsers that can run it.
> For a form, the basic version is HTML the browser can send by itself. The richer version is what React adds: the refusal line without a reload, the reset, and the rest of our JavaScript (Lesson 45).

A form needs four parts so the browser can send it alone:
1. **A real `<form>` element.**
2. **A `name` on every field.** The browser sends only fields that have a name, and the name becomes the key in the form data.
3. **A real submit button**, a `<button type="submit">`. A click on it submits the form with no handler at all.
4. **An action the browser can send without JavaScript**: a URL, or a Server Function in a framework that renders the page on the server.

Our form already has the first three parts, and they cost nothing extra. The `name` that `formData.get('username')` reads is the same name the browser would send (Lesson 40).

### What our Vite app shows before its JavaScript runs

**Our Vite app shows the user nothing at all before its JavaScript runs.** It is not a broken form. It is an empty page. Here is why, in order:
1. The browser receives `index.html`, which holds only an empty root div (Lesson 7).
2. `main.jsx` has not run yet, so React has not rendered `App`.
3. There is no form on the page to click.

```page caption="Our Create account app on a phone whose JavaScript has not loaded yet."
blank
```

```dom caption="What the Elements panel shows before main.jsx runs: the root div with nothing inside."

```

So in an app that renders only in the browser, progressive enhancement starts later, when the team renders the page on the server (Lesson 102). Then the HTML of the form arrives before the bundle.

When the `action` holds a Server Function, React's docs say the form can be submitted before the JavaScript bundle loads (Lesson 110). With `useActionState`, React can also replay a submit that the user made before React took over the page (Lesson 137). Our form keeps its three HTML parts in place, so it is ready for that step.

### The mistake that breaks it

The classic mistake is building the button or the fields in a way only JavaScript understands:
1. A developer builds the Create account button as a `<div onClick>`, because a click handler does the job.
2. Another field has no `name`, because the React code reads its value from state.
3. Everything works while the JavaScript runs.
4. Later, the team renders the page on the server, so it appears fast on slow phones.
5. A user clicks before the bundle loads. A `<div>` is not a submit button, so the browser sends nothing. And a field without a `name` is never part of the form data.

## All 5 Principles Together

### The complete files

The stand-in server refuses `john`:

```js title="src/api.js"
const takenUsernames = ['john'];

export function createAccount(username) {
  return new Promise(resolve => {
    setTimeout(() => {
      if (takenUsernames.includes(username)) {
        resolve(`Username ${username} is taken.`);
      } else {
        resolve(null);
      }
    }, 1000);
  });
}
```

The form passes `formAction` to `<form action>`, so React resets it after every action. The action returns what the user typed, and the fields read it through `defaultValue`:

```jsx title="src/App.jsx"
import { useActionState } from 'react';
import { createAccount } from './api.js';

const initialState = { message: '', username: '', email: '' };

async function signUp(previousState, formData) {
  const username = formData.get('username');
  const email = formData.get('email');
  const error = await createAccount(username);
  if (error) {
    ~return { message: error, username, email }~; // Principle 2: returned, not thrown
  }
  return { message: `Welcome, ${username}!`, username: '', email: '' };
}

export default function App() {
  const [state, formAction] = useActionState(signUp, initialState);

  return (
    <form ~action={formAction}~> {/* Principle 1: React resets the form after signUp returns */}
      <h1>Create account</h1>
      <label>Username <input ~name="username"~ defaultValue={state.username} /></label> {/* Principle 5: a name the browser can send */}
      <label>Email <input name="email" ~defaultValue={state.email}~ /></label> {/* Principle 3: the reset puts back the typed email */}
      <button ~type="submit"~>Create account</button> {/* Principle 5: a real submit button */}
      {state.message && <p>{state.message}</p>}
    </form>
  );
}
```

Principle 4 is not in this file, because this form uses `<form action>`. A form submitted through `onSubmit` adds `requestFormReset(form)` inside its Transition.

### What React does after one click

`App` is the only component. React calls it when the page opens, and again when `signUp` returns. What matters is the order of the steps after the user clicks Create account:

```tree dir=right caption="The order of the steps after the user clicks Create account on the finished form."
One click on Create account
- +1. React builds the form data [`FormData`] | Reads **every named field**
- +2. React calls `signUp` in a Transition [`await createAccount`] | Waits **one second** for the stand-in server
- +3. `signUp` returns the new state [`message, username, email`] | Returned, **not thrown**: the action **succeeded**
- +4. React renders `App` [`defaultValue={state.email}`] | Each field gets its **new default value**
- +5. React resets the form | Each field goes back to its default value | **Text kept** after a refusal, **form empty** after a success
```

| The Situation | The Plain Habit | The React Rule |
| :--- | :--- | :--- |
| **A successful action** | Empty every field by hand at the end of the handler | React resets every uncontrolled field after a function in `<form action>` returns |
| **A refusal from the server** | Expect the fields to stay, because the server said no | A returned error is a success for React, so React resets the form |
| **Keeping the user's text** | Write `value` so the field shows the text | Return the text in state and read it through `defaultValue`, so the reset puts it back |
| **A form submitted through `onSubmit`** | Call `form.reset()` right after the click | Call `requestFormReset(form)` inside the Transition, so the reset waits for the action |
| **A user whose JavaScript has not loaded** | Build the button as a `<div onClick>` and leave fields without `name` | Use a real `<form>`, a `name` on every field, a submit button, and an action the browser can send |

One last time, the sentence of this lesson: **When the action ends without throwing, React resets the form. The reset puts every field back to its default value.**

## For the Interview

> **The Interview Question:** How do React 19 form actions manage automatic form resets, manual requestFormReset, and progressive enhancement?

### How to Answer Clearly in 30 Seconds

"When a function is passed to `<form action>`, React calls it with the form data. After it succeeds, React resets every uncontrolled field of the form. Succeeds means it did not throw, so a returned validation error also clears the fields. Three points follow:
1. **Keeping the text after a refusal**: the reset puts each field back to its default value. So the action returns the submitted values in the `useActionState` state, and each field reads them through `defaultValue`.
2. **`requestFormReset`**: when a form is submitted without the `action` prop, for example through `onSubmit`, I call `requestFormReset(form)` from `react-dom` inside a Transition. It gives the same reset, when the action ends.
3. **Progressive enhancement**: a basic version that works for everyone, made richer when JavaScript runs. A form needs a real `<form>`, a `name` on every field, and a real submit button. Its action must be one the browser can send without JavaScript, such as a URL or a Server Function in a server-rendered page."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Our sign-up form clears the email after the server says the username is taken. Why, and how do you fix it?"**
   React resets a form after every action that does not throw, and a returned error message is a normal return value. The reset puts each field back to its default value. So the action returns the submitted values together with the message, and each field gets `defaultValue` from that state. After a refusal, the reset puts the text back. After a success, the action returns empty values, and the same reset empties the form. Writing `value` instead freezes the field.
2. **"What is the difference between `form.reset()` and `requestFormReset(form)`?"**
   Both put every field back to its default value. `form.reset()` is the browser's method and runs at once, so the fields empty before the server has answered. `requestFormReset` comes from React DOM and is called inside a Transition, so the reset happens when the action ends, together with the new state. React does this same reset for us after a function in `<form action>`, so we call it by hand only for a form submitted another way.
3. **"Does a form with a function in `action` work before JavaScript loads?"**
   Not by itself. A function from our own code exists only after React runs. And a Vite app that renders only in the browser has no form on the page at all before `main.jsx` runs. The browser sends a form with a URL in `action` by itself. In a framework that renders the page on the server, a Server Function in `action` makes the form progressively enhanced. The user can submit it before the bundle loads, and `useActionState` can replay that submit once React takes over.

```tree caption="Interview summary: what decides whether a field keeps the user's text after a form action."
Does the field keep the text after the action?
- !Uncontrolled field with no default value | The reset puts it back to **empty** | Text **lost** after a refusal
- +Uncontrolled field with `defaultValue` from state | The reset puts back **the returned text** | Text **kept** after a refusal, **emptied** after a success
- +Controlled field with `value` and `onChange` | React **does not reset** it | Your code **clears the state** itself
```
