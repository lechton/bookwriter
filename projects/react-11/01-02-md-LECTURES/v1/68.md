# Lecture 68: How the Old List Stays on Screen While the New One Renders

*(How can one state variable feed the search field at once and the slow list a moment later?)*

> INTERVIEW QUESTION | ❱❱ MORE | What does useDeferredValue defer, and how is it different from a transition?

---

## VS | One `query` for the Field and the List vs. a Deferred `query` for the List: one freezes the typing, the deferred one lets the field go first

> In a search field over a long list, every letter the user types must appear at once, and the results can follow a moment later. **`useDeferredValue(query)` gives the list a second version of `query` that lags behind: the old text first, the new text a moment later.** The list renders no faster, but the field never waits for it, and you need only one state variable.

Remember Lesson 67? A controlled `<input>` field shows what `query` holds. So a typed letter reaches the screen only when React renders again with the new `query`. When the same `query` also filters a slow list, that render includes the whole list. **The letter waits for the list.**

In Lesson 67 we fixed it with two state variables and `startTransition`. This lesson fixes it with one state variable and one extra line:

```jsx title="One state variable and one Hook"
const [query, setQuery] = useState('');
const deferredQuery = ~useDeferredValue(query)~; // React returns a version of query that lags behind

<input value={~query~} onChange={e => setQuery(e.target.value)} /> {/* The field reads query */}
<PostList query={~deferredQuery~} /> {/* The list reads the deferred version */}
```

Look at the last two lines. The `<input>` field reads `query`. The list reads `deferredQuery`.

What is `deferredQuery`? It is a plain string, just like `query`. Most of the time, both hold exactly the same text. Only right after a keystroke, for one render, `deferredQuery` still holds the old text. React's docs say the deferred value will "lag behind" the latest value.

So one keystroke now changes the page twice, one change right after the other:

::: row caption="One keystroke by the user: the field changes at once, and the list follows a moment later."

```page size=mini
line: Post #1
line: Post #2
line: Post #3
```
The field shows `1`. The list still shows all 500 posts.
:::
::: col title="A moment later" tag="list follows" tone=good
```page size=mini

line: Post #10
line: Post #11
```
The list now shows the 176 posts whose title contains `1`.

No line of our code waits, and no line of our code sets a timer. React does both renders by itself. React's docs: React "will first re-render *without* updating the deferred value, and then try to re-render with the newly received value in the background."

Keep one sentence in mind for the whole lesson. **The `<input>` field reads the new text at once. The list reads the old text first, and the new text a moment later.**

### The Words This Lesson Stands On

> [!DEFINITION]
> **A controlled `<input>` field.** [REVIEW] A controlled field shows what your state holds: `<input value={query} onChange={e => setQuery(e.target.value)} />`. When the user types a letter, React calls `onChange`, and your code calls `setQuery` with the new text. The new letter reaches the screen only when React renders again with the new `query` and commits it to the DOM (Lesson 20).

> [!DEFINITION]
> **memo.** [REVIEW] `memo` is a function from React that wraps a component: `const PostList = memo(function PostList({ query }) { ... })`. When the parent renders again, React compares each new prop with the old one, using `Object.is`. If every prop is the same, React skips the component and reuses its last result (Lesson 55).

> [!DEFINITION]
> **A Transition.** [REVIEW] A set function called inside `startTransition` makes a Transition: React renders that update in the background, gives the main thread back to the browser between pieces of its work, and drops that render when an urgent update, such as a keystroke, comes in. Nothing of it reaches the screen before its commit (Lessons 66 and 67).

### VS | `query` vs. `deferredQuery`: the same text, one render apart

Both values come from the same state. When the page opens, both hold the empty text. When the user stops typing, both hold the same text again, such as `12`. It looks the same, but it is NOT the same thing!
- **`query`** holds the new text at once, because the field must show what the user typed.
- **`deferredQuery`** still holds the old text for one render. Then React renders again, and it holds the new text too.

To defer means to put off until a little later. So what does `useDeferredValue` put off? Not the state update. `query` changes at once, and the field shows the letter at once.

It puts off only the part of the page that reads the deferred value, here the list. React's docs say it in one sentence: "`useDeferredValue` lets you defer updating a non-critical part of the UI and let other parts update first."

### What Is at Stake

What is at stake is the field itself. It must answer every keystroke at once. While the new list renders, the user should keep seeing the old results, not a frozen field and not an empty list.

Without the Hook, the user feels the problem at the first letter. React's docs describe it: "typing into the input feels very janky", because "each keystroke forces the entire list to re-render immediately in a non-interruptible way."

Developers make three classic mistakes here:
1. **They think `useDeferredValue` makes the list render faster.** It does not. The 176 slow posts take exactly as long as before. The Hook only lets the field go first.
2. **They think it waits a fixed time, like a debounce.** React's docs say the opposite: "There is no fixed delay caused by `useDeferredValue` itself."
3. **They leave the slow list without `memo`.** Then the typing stays slow, and they conclude that the Hook does nothing. Principle 1 shows why.

### The Rule of Thumb: must the slow part show the newest text at once?

**Ask one question about the slow part of the page: must it show the newest text at once? If not, give it `useDeferredValue(text)` instead of the text, and wrap it in `memo`. The field keeps the real text, and the slow part catches up a moment later.**

### VS | `useDeferredValue` vs. `useTransition`: the same page, a different thing marked

The interview question asks how this Hook differs from a Transition. On the page, the user cannot tell the two apart. With either one, the field answers at once, and the list catches up in the background.

The difference sits in the code, in what each one marks:
- **A Transition marks a state update.** Our code calls the set function inside `startTransition`, so our code must have the set function.
- **A deferred value marks a value.** Our code passes the value to `useDeferredValue`, so our code needs only the value.

React's docs give the practical rule: "You can wrap an update into a Transition only if you have access to the `set` function of that state. If you want to start a Transition in response to some prop or a custom Hook value, try `useDeferredValue` instead." Principle 3 shows this on our page.

### Four Ways to Handle Typing over a Slow List

A search field that filters a long list while the user types is a common job at work. A senior developer picks one of four ways:
1. **One state variable and `useDeferredValue`.** This is the way of this lesson. It fits when there is one state variable, or when the text comes from a prop or a custom Hook. React's docs: "you can have one state variable, and add `useDeferredValue` which will "lag behind" the real value."
2. **Two state variables and `useTransition`**, as seen in Lesson 67. It fits when our own component holds the set function, and we want `isPending`. React's docs: "You can declare two separate state variables", one for the field and one "that you will update in a Transition."
3. **Keep the slow part away from the text.** It fits when the slow part does not need the text at all. We move the field and its state into a small component of its own, so only that small component renders again on every keystroke. When the slow part does need the text, React's docs send us back to the first way: "`useDeferredValue` lets you keep the controlled input responsive even in the middle of a large re-render."
4. **Debouncing or throttling.** These wait a fixed time before they update the list. React's docs say they "still produce a janky experience because they're *blocking:* they merely postpone the moment when rendering blocks the keystroke." They are still useful when the slow work is not rendering, such as a request to a server.

```tree caption="Four ways to handle typing over a slow list, and when each one fits."
Typing in a search field that drives a slow list
- +One state variable and `useDeferredValue` [`query` `deferredQuery`] | Fits when there is **one state variable**, or the text **comes from a prop** | Taught in **this lesson**
- +Two state variables and `useTransition` [`query` `searchQuery`] | Fits when **we own the set function** | Gives us **`isPending`**
- +Keep the slow part away from the text | Fits when the slow part **does not need the text** | Only the **small field component** renders again
- !Debouncing or throttling | **Waits a fixed time**, then renders | ~The render **still blocks** the next keystroke
```

The list file is the same as at the end of Lesson 67, already wrapped in `memo`:

```jsx title="src/components/PostList.jsx"
import { memo } from 'react';

const posts = [];
for (let i = 1; i <= 500; i++) {
  posts.push('Post #' + i);
}

const PostList = ~memo~(function PostList({ query }) { // Skipped only when query is the same as last time
  console.log('PostList rendered:', query);
  const results = posts.filter(title => title.includes(query));
  return (
    <ul>
      {results.map(title => <SlowPost key={title} title={title} />)}
    </ul>
  );
});

function SlowPost({ title }) {
  const startTime = performance.now();
  while (performance.now() - startTime < ~1~) {} // Waits 1 millisecond for every post
  return <li>{title}</li>;
}

export default PostList;
```

**The field still freezes, even with `memo`.** `memo` skips the list only when its props are the same as last time. Here `query` changes on every keystroke, so `memo` lets the list render every time. The `1` appears in the field only after 176 slow posts have rendered.

The list must change, and we cannot stop that. What we can change is when it changes.

**PRINCIPLES:** The `<input>` field reads the new text at once. The list reads the old text first, and the new text a moment later. Three principles follow:
1. **Principle 1: `useDeferredValue` Hands `PostList` the Old `query` First.** On each keystroke, React first renders with the old deferred value, so `memo` skips the list and the field answers at once. Then React renders again in the background with the new value.
2. **Principle 2: `query !== deferredQuery` Fades the Old List.** The Hook gives no `isPending`. The list is behind exactly when the two values differ, so we compare them and fade a wrapper around the list.
3. **Principle 3: `SearchResults` Defers a `query` It Only Receives.** A component that only receives the text has no set function to wrap in `startTransition`. It can still call `useDeferredValue` on the value it receives.

## PRINCIPLE | `useDeferredValue(query)`: the list gets the old text first, so the field answers at once

> [!PRINCIPLE]
> **Principle 1: Deferred Value: `useDeferredValue` Hands `PostList` the Old `query` First**
>
> *When one state variable drives a search field and a slow list, pass the list `useDeferredValue(query)` and keep the list in `memo`; on each keystroke, React first renders with the old value, then renders again in the background with the new one.*
>
> The field must show each letter the moment the user types it, but the list is slow. With the deferred value, the first render gives the list the same text as last time, so `memo` skips it and the field answers at once. The list catches up in the background render. When the user types again, React drops that unfinished work and starts over with the latest text. There is no timer, and the list renders no faster than before.
>
> **DO THIS:**
> ```jsx
> const PostList = ~memo~(function PostList({ query }) { // Skipped in the first render, while query holds the old text
>   const results = posts.filter(title => title.includes(query));
>   return <ul>{results.map(title => <SlowPost key={title} title={title} />)}</ul>;
> });
> <PostList query={deferredQuery} />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ~PostList~({ query }) { // **WRONG:** without memo, the first render renders every slow post anyway
>   const results = posts.filter(title => title.includes(query));
>   return <ul>{results.map(title => <SlowPost key={title} title={title} />)}</ul>;
> }
> <PostList query={deferredQuery} />
> ```

### One Line Added, One Prop Changed

Think about what you would do by hand. You would keep the old text somewhere. You would let the field show the new letter, while the list still gets the old text. Then, once the letter is on the screen, you would hand the new text to the list. `useDeferredValue` does exactly that for you:

```jsx title="Passing query vs. passing deferredQuery to the list"
const deferredQuery = ~useDeferredValue(query)~; // The one line we add

<PostList ~query={query}~ /> {/* Before: the list gets the new text on every keystroke */}
<PostList ~query={deferredQuery}~ /> {/* After: the old text first, the new text in the background */}
```

> [!DEFINITION]
> **useDeferredValue and a deferred value.** [NEW] `useDeferredValue` is a Hook from React. You import it from `'react'`, like `useState`, and you call it at the top level of the component, like every Hook (Lesson 38). React's docs: "`useDeferredValue` is a React Hook that lets you defer updating a part of the UI." You pass it the value you want to defer, here `query`, and it returns "a deferred version of that value": the deferred value. Your code never sets it. In the first render after a change, it still holds the old value; in a second render that React starts by itself, it holds the new one (Lesson 68).

So on each keystroke, React renders `SearchPage` twice:
1. **The first render** comes right after the keystroke. In it, `query` holds the new text, and `deferredQuery` still holds the old text.
2. **The background render** comes right after the first one reaches the screen. In it, `deferredQuery` holds the new text too. No code of ours starts it. React's docs: when the Hook "receives a different value", it "schedules a re-render in the background with the new value."

Now compare the two ways to pass the text to the list. It looks the same, but it is NOT the same thing!
- **With `query={query}`**, the list gets a new prop on every keystroke, so `memo` cannot skip it. The letter in the field waits for 176 slow posts.
- **With `query={deferredQuery}`**, the list gets the old text in the first render. It is the same text as last time, so `memo` skips the list, and the field shows the letter at once. The 176 slow posts render only in the background render.

```tree dir=right caption="One keystroke makes two renders, and only the second one renders the slow list."
The user types `1`
- +1. First render [`deferredQuery`] | `query` is **`'1'`**; `deferredQuery` is still **`''`** | **`memo` skips** the list; the field shows **`1` at once**
- +2. Background render | `deferredQuery` becomes **`'1'`** | `PostList` renders **176 slow posts**; the list **catches up**
```

### What Happens When the User Types `1`

**One keystroke now makes two renders, and `PostList` takes part only in the second one.** Here are the steps:
1. The user types `1`. The `onChange` handler calls `setQuery('1')`.
2. **The first render:** `SearchPage` runs with the new text in `query`, but the Hook still returns the old empty text.
3. `PostList` gets the empty text, the same text as last time, so `memo` skips it. No new line appears in the Console.
4. React commits: the field shows `1`, and the list still shows all 500 posts.
5. **The background render:** right after, React renders `SearchPage` again. Now `useDeferredValue(query)` returns `'1'`. `PostList` gets the new text and renders 176 slow posts. The Console prints `PostList rendered: 1`.
6. React commits the background render: the list shows 176 posts.

The React team put step 5 this way when it released React 18: "React will attempt the deferred render right after the first render is reflected on the screen."

### Typing Fast: the List for `1` Never Appears

**When the user types `2` before the list for `1` is ready, React drops that list and renders only the list for `12`.** The field shows `1`, then `12`, each at once. The list goes from 500 posts straight to 15.

Here are the steps, when the user types `2` while the 176 posts are still rendering in the background:
1. The keystroke interrupts the background render. React's docs: "The background re-render is interruptible: if there's another update to the `value`, React will restart the background re-render from scratch."
2. React handles the keystroke first. In the new first render, `query` is `'12'`.
3. `deferredQuery` is still the empty text, not `'1'`. Why? Because the list for `1` never reached the screen. The last deferred value React committed is the empty text. So `memo` skips the list again.
4. React commits: the field shows `12`, and the list still shows all 500 posts.
5. React starts the background render again, now with `'12'`: 15 posts. React's docs: "React will always use the latest provided value."
6. React commits: the list goes from 500 posts to 15.

### VS | A Deferred Value vs. a Debounce: no timer, and the next keystroke can interrupt

A developer who sees the list arrive late often pictures a timer: "`deferredQuery` is `query`, a little later." There is no timer. One keystroke gives two renders, and the second one starts as soon as the first one is done. React's docs: "As soon as React finishes the original re-render, React will immediately start working on the background re-render with the new deferred value."

In plain JavaScript, the habit is a debounce: a `setTimeout` that waits until the user stops typing for a moment. In the developer's mind, both do the same job, because both keep the typing smooth. It looks the same, but it is NOT the same thing!
- **With a debounce**, the list waits a fixed time, such as 300 milliseconds. Then its render blocks the next keystroke all the same.
- **With a deferred value**, the list starts rendering at once, and the next keystroke interrupts it. React's docs: "Unlike debouncing or throttling, it doesn't require choosing any fixed delay."

The wait also follows the user's device. On a fast laptop, React's docs say, "the deferred re-render would happen almost immediately and wouldn't be noticeable." On a slow phone, the list lags behind the field as much as the phone is slow. To see this on our page, slow down the CPU in the Performance panel, as seen in Lesson 64.

### The Page Does Not Defer When It Opens

When the page opens, `SearchPage` renders for the first time. There is no old text yet, so there is nothing to show in its place. So the page still renders all 500 slow posts once, when it opens.

React's docs: "If this option is omitted, `useDeferredValue` will not defer during the initial render, because there's no previous version of `value` that it can render instead."

The "option" in that sentence is a second parameter, `initialValue`, added in React 19:

```jsx title="The second parameter of useDeferredValue"
const deferredQuery = useDeferredValue(query, ~''~); // The initial render uses '', then React renders again in the background with query
```

With `initialValue`, the Hook returns that value in the initial render, and React schedules a background render with the real value. On our page it changes nothing, because `query` already starts as the empty text.

### The Real Mistake: a Deferred Value with a Plain `PostList`

This mistake makes developers conclude that the Hook does nothing:
1. A developer reads that `useDeferredValue` keeps typing smooth.
2. The developer adds the line with `useDeferredValue` and passes `deferredQuery` to the list.
3. The list is a plain function, not wrapped in `memo`.
4. In the first render, `SearchPage` renders again, and React renders its children with it, as seen in Lesson 54. So the list renders all 500 slow posts with the old text, even though nothing in it changed.
5. The field still freezes.

React's docs give the reason in their own warning: "Without `memo`, it would have to re-render anyway, defeating the point of the optimization."

The two pieces need each other. The deferred value keeps the prop the same in the first render. `memo` turns that same prop into a skipped list.

Remember: the list gets the old text first, and `memo` makes that old text cost nothing.

## PRINCIPLE | `query !== deferredQuery`: true exactly while the list still shows the old results

> [!PRINCIPLE]
> **Principle 2: Stale Content: `query !== deferredQuery` Fades the Old List**
>
> *`useDeferredValue` gives no `isPending`; compare the two values with `const isStale = query !== deferredQuery;`, and fade a wrapper around the memoized list with `opacity: isStale ? 0.5 : 1`.*
>
> Right after a keystroke, the field shows the new text, and the list still shows the old results. Without a sign, the user may think the search is broken. The list is behind exactly when `query` and `deferredQuery` differ, so the comparison is the sign. It must sit outside `PostList`, because `isStale` changes in the first render, and any changed prop makes `memo` render the slow list again.
>
> **DO THIS:**
> ```jsx
> <div style={{ ~opacity: isStale ? 0.5 : 1~ }}> {/* PostList keeps the same props */}
>   <PostList query={deferredQuery} />
> </div>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <PostList query={deferredQuery} ~isStale={isStale}~ /> {/* **WRONG:** a changed prop in the first render, so memo renders all the slow posts */}
> ```

### The Two Values Already Tell Us the List Is Behind

Go back to the moment after the first render. The field says `1`, but the list still shows all 500 posts. Nothing on the page says that a new list is coming. The user sees a list that does not match the field.

With `useTransition`, the flag `isPending` gave us that sign, as seen in Lesson 67. `useDeferredValue` returns only the value. There is no `isPending`.

But we do not need one. Ask yourself: when is the list behind? Exactly when the text in the field and the text the list used are different. So the comparison itself is the sign:

```jsx title="Fading the old list while the two values differ"
const isStale = ~query !== deferredQuery~; // true while the list shows results for older text

<div style={{ ~opacity: isStale ? 0.5 : 1~ }}> {/* Faded while the list is behind, full strength after */}
  <PostList query={deferredQuery} />
</div>
```

> [!DEFINITION]
> **Stale content and isStale.** [NEW] Stale content is a result that no longer matches the latest input, the way stale bread is bread from yesterday. React's docs name their section "Indicating that the content is stale", and it starts: "To make it more obvious to the user that the result list does not match the latest query, you can add a visual indication when the stale result list is displayed." `isStale` is a variable our own code creates, with the name React's docs use. No Hook returns it (Lesson 68).

The `!==` operator gives `true` when the two strings differ. So `isStale` is `true` in the first render. Once the background render is done, it is `false` again.

`opacity` is a CSS property. At `0.5`, the list is half see-through. At `1`, it is at full strength. The `0.5` is the value React's docs use in their example. In Lesson 67, our list faded to `0.7`. The number is a free choice.

### VS | `isPending` vs. `isStale`: React gives one, our code works out the other

Both give the page the same sign: the list is behind. It looks the same, but it is NOT the same thing! They come from different places:

```jsx title="The sign from useTransition vs. the sign from useDeferredValue"
const [~isPending~, startTransition] = useTransition(); // React gives the flag
const ~isStale~ = query !== deferredQuery; // Our code works it out from two values it already has
```

- **`isPending`** comes from React, as the first item that `useTransition` returns.
- **`isStale`** comes from our code. `SearchPage` works it out on every render from the two strings.

### The Posts Page with the Faded List

Only the search page file changes:

```jsx title="src/components/SearchPage.jsx" good="7,16"
import { useState, useDeferredValue } from 'react';
import PostList from './PostList.jsx';

export default function SearchPage() {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);
  const isStale = ~query !== deferredQuery~; // Our own variable: true while the list is behind

  return (
    <>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search posts"
      />
      <div style={{ ~opacity: isStale ? 0.5 : 1~ }}> {/* The fade sits outside PostList */}
        <PostList query={deferredQuery} />
      </div>
    </>
  );
}
```

The list file does not change.

### What Happens When the User Types `1` Now

**The old list fades in the same moment the `1` appears in the field, and the new list arrives at full strength.** Here are the steps:
1. The user types `1`.
2. In the first render, the field has the new text and the list still has the old empty text, so `isStale` is true. The wrapper `<div>` fades to an opacity of `0.5`.
3. `PostList` still gets the empty text, so `memo` skips it.
4. React commits: the field shows `1`, and the old 500 posts appear faded.
5. In the background render, both values are `'1'`. So `isStale` is `false`. `PostList` renders 176 posts.
6. React commits: 176 posts at full strength.

When the user types `2` during step 5, the field holds `12` while the deferred value is still the empty text. The list stays faded until the 15 posts are ready. React's docs describe the same thing: "as soon as you start typing, the stale result list gets slightly dimmed until the new result list loads."

The Elements panel shows the fade as a plain `style` attribute on the wrapper:

```dom caption="The Elements panel right after the user typed 1: the wrapper div holds opacity 0.5 around the old list."
+ <div style="opacity: 0.5;"> | note: Stale: the old list of 500 posts, faded
    <ul>
      <li>Post #1</li>
      <li>Post #2</li>
      <li>Post #3</li>
    </ul>
  </div>
```

When the background render commits, the same `<div>` holds `style="opacity: 1;"`, and the list inside it holds the 176 new posts.

### VS | A Wrapper `<div>` vs. an `isStale` Prop on `PostList`: only the wrapper keeps `memo` working

Passing the sign into the list feels natural, because the fade belongs to the list. But it brings the freeze back:

```jsx title="The fade on a wrapper div vs. isStale passed into PostList"
<div style={{ opacity: isStale ? 0.5 : 1 }}><PostList query={deferredQuery} /></div> {/* The props of PostList stay the same */}
<PostList query={deferredQuery} ~isStale={isStale}~ /> {/* PostList gets a changed prop in the first render */}
```

It looks the same, but it is NOT the same thing! Both fade the old list. The difference is in the first render:
- **With the fade on a wrapper `<div>`**, the only prop of `PostList` still holds the old text. `memo` skips the list, and the field answers at once.
- **With `isStale` passed into `PostList`**, that prop changes from false to true in the first render. `memo` sees a changed prop and renders all 500 slow posts with the old text. The field freezes again.

It is the same trap as passing `isPending` into the list in Lesson 67. It has the same fix: keep the fade in `SearchPage`, on an element outside the memoized list.

```tree caption="Where the fade goes decides whether memo can still skip the slow list."
Showing that the list is behind
- +On a wrapper `<div>` in `SearchPage` [`opacity`] | `PostList` gets the **same `query`** | `memo` **skips** the list; the field answers **at once**
- !As a prop of `PostList` [`isStale={isStale}`] | The prop **changes** from `false` to `true` | `memo` **renders** all the slow posts; ~the field **freezes again**
```

### A Short Wait Before the Fade

On a fast device, the list catches up almost at once. A fade that flashes on and off on every keystroke can bother the user more than it helps. React's docs: "You can also add a CSS transition to delay dimming so that it feels gradual". Their example:

```jsx title="Delaying the fade with the CSS transition property"
<div style={{
  opacity: isStale ? 0.5 : 1,
  ~transition: isStale ? 'opacity 0.2s 0.2s linear' : 'opacity 0s 0s linear'~ // Fades after a short wait, returns at once
}}>
  <PostList query={deferredQuery} />
</div>
```

The CSS `transition` property is a browser feature. It only shares its name with React's Transition.

Remember: the list is behind exactly when the two strings differ, and the fade goes on an element outside the memoized list.

## PRINCIPLE | `useDeferredValue` in a child: it defers a `query` the child only receives

> [!PRINCIPLE]
> **Principle 3: Deferring a Prop: `SearchResults` Defers a `query` It Only Receives**
>
> *A Transition needs the set function of the state; when a component only receives the text, as a prop or from a custom Hook, call `useDeferredValue` on the value it receives and pass the deferred value to the memoized list.*
>
> `useTransition` and `useDeferredValue` give the user the same page: the field at once, the list a moment later. They differ in what they mark. A Transition marks a state update, so the code must hold the set function. A deferred value marks a value, so it works in a child that only receives `query`. Defer strings and numbers, not an object built during rendering.
>
> **DO THIS:**
> ```jsx
> function SearchResults({ query }) {
>   const deferredQuery = ~useDeferredValue(query)~; // Works on a value the component only receives
>   return <PostList query={deferredQuery} />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function SearchResults({ query, sort }) {
>   const deferred = useDeferredValue(~{ query, sort }~); // **WRONG:** a new object on every render causes a background render every time
>   return <PostList query={deferred.query} />;
> }
> ```

### A Component That Has the Text, but Not the Set Function

At work, a page like ours is rarely one component. The parent owns the text and the field. A child shows the results, and it receives the text as a prop, as seen in Lesson 24. Here is that child:

```jsx title="A child that defers the text it receives"
function SearchResults({ ~query~ }) { // query arrives as a prop; there is no setQuery here
  const deferredQuery = ~useDeferredValue(query)~; // The child can still defer the value
  return <PostList query={deferredQuery} />;
}
```

`SearchResults` has no `setQuery`. It cannot wrap the update in `startTransition`, because the update happens in its parent. But it can call `useDeferredValue` on the value it has.

The same holds when a custom Hook returns only the text, as seen in Lesson 39. Our code gets the value, not the set function.

### VS | `useTransition` vs. `useDeferredValue`: it marks the update vs. it marks the value

The two Hooks share almost everything:
1. Both keep the update of the field urgent.
2. Both render the slow list in the background.
3. Both let a new keystroke interrupt that work.
4. Both need `memo` on the slow list.

So the user sees the same page. The one difference is what each one marks:

```jsx title="Marking a state update vs. marking a value"
startTransition(() => { ~setSearchQuery(text)~; }); // useTransition marks the update, so it needs the set function
const deferredQuery = ~useDeferredValue(query)~; // useDeferredValue marks the value, so it needs only the value
```

It looks the same, but it is NOT the same thing! React's docs, on their page that lists all the Hooks, say it in two lines: "`useTransition` lets you mark a state transition as non-blocking and allow other updates to interrupt it." And: "`useDeferredValue` lets you defer updating a non-critical part of the UI and let other parts update first."

In plain words: a Transition starts where the state is set. A deferred value is made where the value is used, even in code that has no say in how the value is set.

| Aspect | With `useTransition` | With `useDeferredValue` |
| :--- | :--- | :--- |
| **What it marks** | A state update, inside `startTransition` | A value, passed to `useDeferredValue` |
| **What it needs** | The set function of the state | Only the value |
| **State variables on our page** | Two: `query` and `searchQuery` | One: `query` |
| **The sign that the list is behind** | `isPending`, given by React | `query !== deferredQuery`, worked out by our code |
| **What the user sees** | The field at once, the list a moment later | The same |

### The Posts Page with `SearchResults`

The search page file keeps `query` and the field, and hands `query` to a new child:

```jsx title="src/components/SearchPage.jsx" good="2,14"
import { useState } from 'react';
import SearchResults from './SearchResults.jsx';

export default function SearchPage() {
  const [query, setQuery] = useState('');

  return (
    <>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search posts"
      />
      <SearchResults query={~query~} /> {/* The child gets the text, not setQuery */}
    </>
  );
}
```

The new results file takes over the Hook, `isStale`, and the fading `<div>`, unchanged:

```jsx title="src/components/SearchResults.jsx" good="4,5"
import { useDeferredValue } from 'react';
import PostList from './PostList.jsx';

export default function SearchResults({ ~query~ }) { // A prop from SearchPage
  const deferredQuery = ~useDeferredValue(query)~; // Deferred here, where the value is used
  const isStale = query !== deferredQuery;

  return (
    <div style={{ opacity: isStale ? 0.5 : 1 }}>
      <PostList query={deferredQuery} />
    </div>
  );
}
```

The list file does not change.

### What Happens When the User Types `1` Now

**The page behaves exactly as in Principle 2, though the Hook now lives in a child that never sees `setQuery`.** For the user, the Hook in the parent and the Hook in the child are the exact same thing. Here are the steps:
1. The user types `1`. `SearchPage` renders again with the new text in `query`.
2. `SearchResults` gets the new prop and renders again. That costs almost nothing: it reads two values and draws a `<div>`.
3. Inside it, the Hook returns the old empty text. `isStale` is true, and the list still gets the empty text, so `memo` skips it.
4. React commits: the field shows `1`, and the old list fades.
5. In the background render, `deferredQuery` is `'1'`. `PostList` renders 176 posts, the fade ends, and the Console prints `PostList rendered: 1`.

### The Real Mistake: Deferring an Object Built During Rendering

This mistake appears when `SearchResults` gets a second prop:
1. `SearchResults` now also receives a sort order, `sort`. The developer wants to defer both, and builds one object during rendering: `useDeferredValue({ query, sort })`.
2. The Hook compares the new value with the old one using `Object.is`, the same check that `memo` uses on props, as seen in Lesson 55. Two objects built in two renders are two different objects, even when they hold the same text.
3. So the Hook sees a new value on every render, and schedules a background render every time. React's docs: "If you create a new object during rendering and immediately pass it to `useDeferredValue`, it will be different on every render, causing unnecessary background re-renders."
4. The fix is to pass strings and numbers, or objects created outside of rendering. Here, that means one call for each string.

```jsx title="One object built during rendering vs. one call for each string"
const deferred = useDeferredValue(~{ query, sort }~); // **WRONG:** a new object on every render, so a background render every time
const deferredQuery = ~useDeferredValue(query)~; // A string: compared by its text
const deferredSort = ~useDeferredValue(sort)~; // A string: compared by its text
```

### Where Each One Fits

Three facts help pick the right Hook:
1. **Inside a Transition, the deferred value adds nothing.** React's docs: "When an update is inside a Transition, `useDeferredValue` always returns the new `value` and does not spawn a deferred render, since the update is already deferred."
2. **Each one has its usual place.** React's docs: "Transitions mark the whole update as non-urgent so they are typically used by frameworks and router libraries for navigation." And: "Deferred values, on the other hand, are mostly useful in application code where you want to mark a part of UI as non-urgent and let it "lag behind" the rest of the UI."
3. **Network requests are not deferred.** When each keystroke sends a request to a server, a request still goes out for every keystroke. React's docs: "`useDeferredValue` does not by itself prevent extra network requests." What it defers is showing the results.

Lesson 69 shows how a deferred value keeps the old results on the screen while new data loads with Suspense.

Remember: a Transition needs the set function, and a deferred value needs only the value.

### How React Calls the Components After One Keystroke

When the page opens, React calls `App`, then `SearchPage`, then `SearchResults`, then `PostList`. `PostList` then calls one `SlowPost` for each of the 500 titles. After the user types `1`, React renders twice, and `PostList` takes part only in the second render:

```tree caption="The order in which React calls the components after the user types 1: the first render skips PostList, and the background render renders it."
`SearchPage` after the user types `1`
- +1. First render | React calls **`SearchPage`**, then **`SearchResults`** with `query` `'1'` | `deferredQuery` is still empty, so **`PostList` is skipped** by `memo` | The field shows **`1`**; the old list **fades**
- +2. Background render | React calls **`SearchResults`** with `deferredQuery` `'1'`, then **`PostList`** | `PostList` calls **176 `SlowPost`** components | The list shows **176 posts at full strength**
```

| Aspect | The Habit That Freezes or Confuses | The React Rule |
| :--- | :--- | :--- |
| **The prop of the list** | Passing `query` to the list, so every letter waits for the slow posts | Passing `deferredQuery`, so the first render gives the list the old text |
| **The list itself** | A plain `PostList`, which renders its slow posts in the first render | `PostList` wrapped in `memo`, so the first render skips it |
| **The timing** | Expecting a fixed delay, like a debounce | No timer: the background render starts right after the first one, and a new keystroke starts it again |
| **The sign** | Looking for `isPending`, or passing `isStale` into `PostList` | `query !== deferredQuery`, shown on a wrapper `<div>` outside `PostList` |
| **The text from a prop** | Reaching for `useTransition` without a set function | `useDeferredValue` on the value the component receives |

Remember the one sentence of this lesson. **The `<input>` field reads the new text at once. The list reads the old text first, and the new text a moment later.**

## For the Interview

> **The Interview Question:** What does useDeferredValue defer, and how is it different from a transition?

### How to Answer Clearly in 30 Seconds

"`useDeferredValue` takes a value and returns a deferred version of it. On each update, React first renders with the old value, and then renders again in the background with the new one. What it defers is the render of the part of the page that reads the deferred value, such as a slow results list. It does not defer the state update, and it does not defer network requests. Three details make it work:
1. **`memo` on the slow part**: the first render must skip the list, and only `memo` can skip it when the prop is the same.
2. **No fixed delay**: the background render starts right after the first one, and a new keystroke starts it again with the latest value.
3. **No `isPending`**: `query !== deferredQuery` tells us the content is stale, so we can fade the old list on an element outside the memoized list.

The difference from a Transition is what each one marks. A Transition marks a state update, so it needs the set function. A deferred value marks a value, so it works on a prop or a custom Hook value."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does `useDeferredValue` make the list render faster? Is it a debounce?"**
   No to both. The list takes exactly as long as before. React's docs say the Hook "tells React that re-rendering the list can be deprioritized so that it doesn't block the keystrokes": the list may wait its turn. A debounce waits a fixed time and then blocks the keystroke all the same. A deferred value needs no delay: the background render starts at once, and the next keystroke interrupts it. On a fast device, the user hardly sees the wait at all. Debouncing is still the right tool for slow work outside rendering, such as requests to a server.
2. **"When do you pick `useDeferredValue` over `useTransition`?"**
   When the code that renders the slow part has the value but not the set function: a prop from a parent, or a value from a custom Hook. It also fits when we want one state variable instead of two. We pick `useTransition` when we own the set function and want `isPending`. Inside a Transition, the deferred value adds nothing: it "always returns the new `value` and does not spawn a deferred render, since the update is already deferred."
3. **"What does the user see while the deferred value lags behind, and when does it not defer?"**
   The user sees the old results until the new ones are ready, and we can fade them with `query !== deferredQuery`. The background render runs no Effects until React commits it, as seen in Lesson 32. The Hook does not defer during the initial render, because there is no old value to show. React 19 added a second parameter, `initialValue`, for that render. With Suspense, a deferred value also keeps the old content on the screen instead of a fallback, which Lesson 69 covers.

```tree dir=right caption="Interview comparison: a Transition marks a state update, and a deferred value marks a value."
Keeping a search field fast over a slow list
- +`useTransition` [`startTransition` `isPending`] | Marks a **state update** | Needs **the set function**; gives **`isPending`**
- +`useDeferredValue` [`deferredQuery`] | Marks a **value** | Needs **only the value**; works on **a prop or a custom Hook value**
- !Debouncing [`setTimeout`] | **Waits a fixed time** | ~Then the render **still blocks** the keystroke
```
