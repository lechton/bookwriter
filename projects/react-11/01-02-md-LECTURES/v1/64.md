## VS | The Elements Panel vs. React Developer Tools: the Elements panel shows the DOM nodes, React Developer Tools shows the components

> When you inspect a React page in the browser, the Elements panel shows you `<li>` and `<input>` nodes, but not one of your components. **React Developer Tools is a browser extension that shows the components React called, with their props, their state, and how long each one took to render**. The reason is simple: React calls every component itself, so React already knows which one is slow, and this tool lets you ask React instead of guessing.

Remember the Elements panel? You right-click a button on any page, choose Inspect, and the browser shows you the `<button>` node with its parents. In plain JavaScript, that is the whole story. You created those nodes yourself, so you find them there, exactly as you wrote them:

```js title="Plain JavaScript: the node you create is the node you inspect"
const item = ~document.createElement('li')~; // The Elements panel shows this exact li
item.textContent = 'Hi!';
document.querySelector('ul').append(item);
```

In React, you never create the nodes by hand. You write components, such as `Message`, and React calls them and puts what they return into the DOM. The name `Message` never reaches the DOM (Lesson 04):

```jsx title="React: you write Message, and the DOM gets only the li it returns"
function Message({ text }) {
  return ~<li>{text}</li>~; // The Elements panel shows this li, and never the name Message
}

<Message text="Hi!" />
```

So the Elements panel, which reads only the DOM, cannot tell you which component made which `<li>`. It cannot tell you what props that component got, or what state it keeps.

Who knows all of that? React. React calls `Message` itself, so it knows every component it called, the props it passed, the state it keeps, and how long each call took. React Developer Tools is how you ask React for it. It adds two tabs to the browser's developer tools, next to the Elements panel and the Console:
1. **The Components tab** shows every component React called, with its props and its state.
2. **The Profiler tab** records what the user does, such as typing, and shows which components rendered and how long each one took.

Keep one sentence in mind for the whole lesson: **the browser knows the DOM nodes, React knows the components, so ask React.**

> [!DEFINITION]
> **What is React Developer Tools?** [NEW] React Developer Tools, also written React DevTools, is a browser extension made by the React team. A browser extension is a small program you add to the browser to give it a new feature. On every page built with React, it adds two tabs to the browser's developer tools: Components, to read each component with its props and state, and Profiler, to measure how long each component takes to render. React's docs say you use it "to inspect React components, edit props and state, and identify performance problems" (Lesson 64).

Two words in this lesson come from that sentence of the docs:
- To **inspect** a component means to select it and read what React keeps for it.
- To **profile** an app means to measure where its time goes. The Profiler tab does that measuring for you.

### How to Install React Developer Tools

React's docs list the extension for Chrome, Firefox, and Edge. You install it once, from the browser's extension store. After that, every page built with React shows the two new tabs. React's docs: "Now, if you visit a website built with React, you will see the Components and Profiler panels."

Safari and other browsers have no extension. For them, React provides an npm package, `react-devtools`, which opens React DevTools in its own window. You install it once and start it from the terminal:

```bash title="Terminal"
npm install -g react-devtools
react-devtools
```

Then you add one script tag at the very start of the page's `<head>`. The `react-devtools` window listens at the address `localhost:8097`, so this tag connects the page to that window:

```html title="index.html"
<head>
  <script src="http://localhost:8097"></script>
  <meta charset="UTF-8" />
</head>
```

You reload the page, and its components appear in the `react-devtools` window.

### What Is at Stake

Open a chat app with a long history and start typing a reply. Each letter appears in the message field a moment after you press the key. The app works, but it feels slow.

The developer of that app has one question: which component renders after every keystroke, and which one takes the time? There are two ways to answer it:
1. **Guess.** Put `console.log` and `console.time` lines into the components that look slow. Then wrap whatever looks heavy in `memo` (Lessons 54 and 55). Each line answers only for the code you chose to measure.
2. **Ask React.** Open React Developer Tools. It shows every component React rendered after the keystroke, and how long each one took.

The two ways end very differently:
- The developer who guesses often wraps the wrong component in `memo`, and the field still lags. React's docs warn that "not all memoization is effective".
- The developer who measures sees that the message rows render after every keystroke and take most of the time. That developer fixes that one component, records the typing again, and sees the time drop.

Asking React takes four steps:

```tree dir=right caption="The four steps to find which component makes typing slow, with React Developer Tools."
How we find the component that makes the chat lag
- +1. Open React Developer Tools | Two new tabs appear: **Components** and **Profiler**
- +2. Read the Components tab | Every **component**, with its **props** and **state**
- +3. Record in the Profiler tab | Which components **rendered** after each keystroke, and **how long** each took
- +4. Fix the costliest one, record again | The time **drops**, or the fix was the **wrong one**
```

### Where Developers Go Wrong

Developers commonly make five mistakes with these tools:
1. They look for their components, such as `Message`, in the Elements panel, and find only `<li>` nodes.
2. They add memoization everywhere before they measure anything. Every component gets `memo`. Every value and function gets `useMemo` or `useCallback`.
3. They trust timings measured in development, with Strict Mode on and React Developer Tools open. Those timings are higher than what users get.
4. They expect `onRender` and the Profiler tab to work in a normal production build. Profiling is turned off there.
5. They add `useDebugValue` to every custom Hook. React's docs say it plainly: "Don't add debug values to every custom Hook."

### The Rule of Thumb: look in the Components tab, and measure before you fix

**Look for components in the Components tab, never in the Elements panel. To find a slow one, record the slow interaction, fix the component that costs the most, and record again.**

## PRINCIPLE | Components tab: every component React called, with its props and its state

> [!PRINCIPLE]
> **Principle 1: The Components Tab: React Developer Tools Shows Components, Not DOM Nodes**
>
> *Read the Components tab to see each component React called, with its props and its state; the Elements panel shows only the DOM nodes.*
>
> A component tag never reaches the DOM, so the Elements panel cannot say which component made an `<li>`, what props it got, or what state it keeps. React calls every component itself, so React knows all of that, and the Components tab shows it. You select a component on the page, read its props and state, change them by hand, and check where it really sits, such as inside or outside a provider.
>
> **DO THIS:**
> ```jsx
> <ThemeContext value={theme}>
>   <button onClick={toggleTheme}>Toggle theme</button>
>   ~<ChatRoom />~ {/* The Components tab shows ChatRoom under the provider */}
> </ThemeContext>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ThemeContext value={theme}>
>   <button onClick={toggleTheme}>Toggle theme</button>
> </ThemeContext>
> ~<ChatRoom />~ {/* **WRONG:** ChatRoom sits next to the provider, so every Message reads the default 'light' */}
> ```

### A Provider in the Wrong Place

The Components tab is also where you check where a component really sits. React's docs give this advice for a component that reads context and always gets the default value: "Check whether the hierarchy is right using React DevTools."

Here is that bug. Suppose the chat room gets its theme back, as in Lesson 54. `Message` reads the theme with `useContext(ThemeContext)`. The default value of the context is `'light'`. The theme state in `App` starts as `'dark'`, but every message shows the light theme. The provider looks right when you read `App`:

```jsx title="src/App.jsx"
export default function App() {
  const [theme, setTheme] = useState('dark');
  return (
    <>
      <ThemeContext ~value={theme}~> {/* **WRONG:** only the button sits inside the provider */}
        <button onClick={() => setTheme(theme === 'dark' ? 'light' : 'dark')}>
          Toggle theme
        </button>
      </ThemeContext>
      <ChatRoom />
    </>
  );
}
```

In the code, the mistake is easy to miss. In the Components tab, you see it at a glance. The tab shows your `ThemeContext` provider under the name `Context.Provider`. And `ChatRoom` sits next to it, not inside it. So every `Message` reads the default `'light'` (Lesson 28):

```tree caption="The Components tab shows ChatRoom next to the provider, not inside it, so every Message reads the default theme."
Components tab: `App`
- +`Context.Provider`: our `ThemeContext` | Holds **`'dark'`** | Wraps **only the button**
- !`ChatRoom` | Sits **next to** the provider | Every `Message` reads the default **`'light'`**
```

The fix is to move `<ChatRoom />` inside the provider, as the card of this principle shows. The Components tab then shows `ChatRoom` under the provider, and every message shows the dark theme.

## PRINCIPLE | `useDebugValue`: a custom Hook shows a readable label in the Components tab

> [!PRINCIPLE]
> **Principle 2: useDebugValue: A Custom Hook Gets a Readable Label in React DevTools**
>
> *Call `useDebugValue` at the top level of a shared custom Hook to label its value in the Components tab; pass a formatting function when the label costs work.*
>
> Without a label, the Components tab shows a custom Hook with no value of its own, and you must open it to read a raw value such as `true`. `useDebugValue` returns nothing and changes nothing on the page. It only tells React DevTools what to print next to the Hook. When the label needs work, such as turning a date into text, the formatting function lets React DevTools do that work only when it inspects the component.
>
> **DO THIS:**
> ```js
> useDebugValue(date, ~date => date.toDateString()~); // React DevTools formats the date only while it inspects the component
> ```
>
> **DO NOT DO THIS:**
> ```js
> useDebugValue(~date.toDateString()~); // **WRONG:** formats the date on every render, even with React DevTools closed
> ```

### `useDebugValue` in Its Smallest Form

Remember `useOnlineStatus`, the custom Hook of Lesson 53? It returns `true` while the browser is online, and `false` when it is offline. Here it is in two versions. The second one adds one line:

```js title="useOnlineStatus without a label"
export function useOnlineStatus() {
  return ~useSyncExternalStore(subscribe, getSnapshot)~; // Returns true or false
}
```

```js title="useOnlineStatus with useDebugValue"
export function useOnlineStatus() {
  const isOnline = useSyncExternalStore(subscribe, getSnapshot);
  ~useDebugValue(isOnline ? 'Online' : 'Offline')~; // Gives React DevTools a label, and returns nothing
  return isOnline;
}
```

On the page, both versions do the exact same thing: the component that calls the Hook gets `true` or `false`. In the Components tab, they are NOT the same thing:
- **Without `useDebugValue`**, the Components tab shows a row named `OnlineStatus` with no value next to it. You must open that row to see the raw value of the Hook inside it: `SyncExternalStore: true`. React's docs say that without the call, "only the underlying data", here `true`, would be displayed.
- **With `useDebugValue`**, the Components tab shows the label `OnlineStatus: "Online"`.

> [!DEFINITION]
> **What is useDebugValue?** [NEW] To debug means to find and fix a bug, and a debug value is the value a developer reads while debugging. `useDebugValue` is a React Hook, imported from `'react'`, that gives a custom Hook a label in React DevTools. React's docs: "`useDebugValue` is a React Hook that lets you add a label to a custom Hook in React DevTools." The label can have any type. Its name starts with `use`, like `useState`, but it is NOT that kind of Hook: `useState` keeps a value and returns it, while `useDebugValue` keeps nothing and returns nothing. Like every Hook, you call it at the top level of the custom Hook, never inside a condition (Lessons 38 and 64).

### The Chat Room Shows Online or Offline

Chat apps show whether you are online, so we add a heading with that status to the chat room. `ChatRoom` imports the Hook and calls it. It shows `Online` or `Offline` above the messages:

```jsx title="src/components/ChatRoom.jsx"
import { useState } from 'react';
import Message from './Message.jsx';
import { useOnlineStatus } from '../useOnlineStatus.js';

const initialMessages = [
  { id: 1, text: 'Hi!' },
  { id: 2, text: 'Lunch at 12?' },
  { id: 3, text: 'Sure' },
];

export default function ChatRoom() {
  const isOnline = ~useOnlineStatus()~; // true while the browser is online
  const [messages] = useState(initialMessages);
  const [text, setText] = useState('');
  return (
    <section>
      <h1>{isOnline ? 'Online' : 'Offline'}</h1>
      <ul>
        {messages.map(m => (
          <Message key={m.id} text={m.text} />
        ))}
      </ul>
      <input value={text} onChange={e => setText(e.target.value)} />
    </section>
  );
}
```

```page width=text caption="The chat room with its status heading: Online above the three messages."
heading: Online
line: Hi!
line: Lunch at 12?
line: Sure
form:

```

Select `ChatRoom` in the Components tab. Above its two `State` rows, it now shows one more row for your Hook, named `OnlineStatus`. Your code never writes that word. React DevTools names the row after your Hook, `useOnlineStatus`, without its `use`.

The row has no value next to it. You must open it to find the raw value inside, on the row of `useSyncExternalStore`: `SyncExternalStore: true`. With one Hook, that is fine. But in a component that calls three or four custom Hooks, you open row after row and read raw `true`, `false`, and numbers.

So we add the label to the Hook. The Hook now keeps the result in `isOnline`, so that it can both label it and return it:

```js title="src/useOnlineStatus.js"
import { useSyncExternalStore, ~useDebugValue~ } from 'react'; // useDebugValue comes from react

function getSnapshot() {
  return navigator.onLine;
}

function subscribe(callback) {
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}

export function useOnlineStatus() {
  const isOnline = useSyncExternalStore(subscribe, getSnapshot);
  ~useDebugValue(isOnline ? 'Online' : 'Offline')~; // Our own words for the label
  return isOnline;
}
```

Reload the page. The page looks the same, with `Online` above the messages, and the Console prints nothing new. In the Components tab, `ChatRoom` now shows `OnlineStatus: "Online"`.

The row name `OnlineStatus` still comes from your Hook. The words `'Online'` and `'Offline'` are the strings you passed. When the Wi-Fi drops, the heading reads `Offline` (Lesson 53). The label then reads `OnlineStatus: "Offline"`.

```tree caption="What the Components tab shows for ChatRoom before and after the call to useDebugValue; the page stays the same."
The row of `useOnlineStatus` in the Components tab
- !Without `useDebugValue` | Shows **`OnlineStatus`** with **no value** | The raw **`true`** sits inside, under `SyncExternalStore`
- +With `useDebugValue` | Shows **`OnlineStatus: "Online"`** | Reads **`OnlineStatus: "Offline"`** when the Wi-Fi drops
```

The label appears on every component that calls the Hook. React's docs: "This gives components calling `useOnlineStatus` a label like `OnlineStatus: "Online"` when you inspect them."

### A Label That Costs Work: a Function as the Second Argument

Suppose a shared Hook keeps a date as a JavaScript `Date` object, such as the time a friend was last online. The Components tab would show the full date, with its time and its time zone. You want a short label, such as `Fri Nov 13 2026`. The method `toDateString()` makes that text. Here are two ways to give it to `useDebugValue`:

```js title="The date formatted on every render vs. a formatting function"
~useDebugValue(date.toDateString())~; // Runs toDateString on every render, even with React DevTools closed
~useDebugValue(date, date => date.toDateString())~; // React DevTools runs toDateString only when it inspects the component
```

Both show the same label in the Components tab, but they are NOT the same work:
- **With `date.toDateString()` as the value**, JavaScript makes the text every time the component renders, for every user, although nobody reads the label.
- **With a function as the second argument**, the Hook passes only `date`. That function is called a **formatting function**: it turns the value into the text of the label. React's docs: "When the component is inspected, React DevTools will call the formatting function with the `value` as the argument, and then display the returned formatted value." On a normal render, the formatting never runs.

React's docs say what this saves: "This lets you avoid running potentially expensive formatting logic unless the component is actually inspected."

### When a Hook Deserves a Label

A team that learns `useDebugValue` often adds it to every custom Hook in the app. React's docs advise against that: "Don't add debug values to every custom Hook. It's most valuable for custom Hooks that are part of shared libraries and that have a complex internal data structure that's difficult to inspect."

Our `useOnlineStatus` returns one `true`, so it is a small example. The label really helps in a Hook that many teams use, and that holds data nobody can read at a glance.

## PRINCIPLE | Profiler tab: it lists every component that rendered on a keystroke, and how long it took

> [!PRINCIPLE]
> **Principle 3: The Profiler Tab: Record the Interaction, Then Fix the Component It Names**
>
> *Record the slow interaction in the Profiler tab, read which components rendered in each commit and how long each one took, fix the one that costs the most, and record again.*
>
> A guess with `console.time` measures only the lines the developer chose. The time of the children is not inside those lines, because React renders the children after the parent returns. The Profiler tab lists every component React rendered for each keystroke, with its time, and needs no change to the code. After the fix, a second recording of the same interaction proves it. Timings from development are higher than the user's, so they show where the cost is, not how big it really is.
>
> **DO THIS:**
> ```jsx
> export default ~memo(Message)~; // The recording named Message: it no longer renders on a keystroke
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default ~memo(ChatRoom)~; // **WRONG:** a guess from console.time: ChatRoom renders from its own state, and the three rows still take the time
> ```

### A Message That Is Slow on Purpose

To find a slow component, you first need one. React's docs build their slow examples the same way: a component that is **artificially slowed down**. It waits on purpose, to stand for slow code. Here is our `Message`, slowed down:

```jsx title="src/components/Message.jsx"
export default function Message({ text }) {
  let startTime = performance.now();
  ~while (performance.now() - startTime < 20)~ { // Waits 20 milliseconds on every render, to stand for slow code
  }
  return <li>{text}</li>;
}
```

`performance.now()` gives the browser's current time in milliseconds. The `while` loop keeps asking for the time until 20 milliseconds have passed. React's docs wait 1 millisecond in each item of a list of 250 items. Our list has only three rows, so each row waits longer, and the user feels it.

Now the user types `OK` in the message field, and each letter appears late. Why? Each keystroke changes the text in state, so React renders `ChatRoom` and calls all three `Message` rows again. Each row waits 20 milliseconds. In development, Strict Mode calls each row twice (Lesson 47). So every letter waits about 120 milliseconds before it reaches the screen.

### VS | `console.time` vs. the Profiler Tab: the timer measures only the lines you chose, the Profiler tab measures every component

A developer who does not know where the time goes often starts with `console.time`, in the component that holds the field:

```jsx title="A guess: console.time inside ChatRoom"
export default function ChatRoom() {
  ~console.time('ChatRoom')~; // Starts a timer each time React calls ChatRoom
  const isOnline = useOnlineStatus();
  const [messages] = useState(initialMessages);
  const [text, setText] = useState('');
  ~console.timeEnd('ChatRoom')~; // Prints a tiny time: no Message has rendered yet
  return (
    <section>
      ...
    </section>
  );
}
```

**The Console prints a tiny time, far below one millisecond, after every keystroke.** Why? The timer stops before `ChatRoom` returns its JSX. React calls the three `Message` rows only after `ChatRoom` has returned. So the slow rows are not inside the timer at all.

The developer concludes that `ChatRoom` is fast, and wraps it in `memo` anyway, to be safe. The field still lags. `memo` skips a component only when its props are the same (Lesson 55). But `ChatRoom` renders because its own state changed. So the three rows still render after every keystroke.

The timer and the recording look like two ways to do the same job, but they are NOT the same thing:
- **`console.time`** times only the lines you chose, and here you chose the wrong ones.
- **A recording in the Profiler tab** lists every component React rendered after the keystroke, with its time, and needs no change to your code.

React's docs point to the Profiler tab for exactly this case. Their advice: "If a specific interaction still feels laggy, use the React Developer Tools profiler to see which components would benefit the most from memoization." Then, and only then, they say to "add memoization where needed."

### Record the Keystrokes in the Profiler Tab

**The recording shows that the three `Message` rows take almost all the time, and `ChatRoom` takes almost none.** Here is how you get there:
1. Open the Profiler tab and start a recording.
2. The user types `O` and `K` in the message field.
3. Stop the recording.
4. The recording holds one commit for each keystroke, two in all.
5. In each commit, `ChatRoom` rendered, and all three `Message` rows rendered too, although the user changed only the field.

> [!DEFINITION]
> **What is a commit?** [REVIEW] A commit is the moment React applies an update to the DOM. React first calls your components to find out what changed, and then it commits: it changes only the DOM nodes that differ. In our chat room, one keystroke gives one commit (Lesson 13).

For each commit, the recording draws one bar for each component, with each child under its parent. The length of a bar shows how long that component took. React's docs call this kind of chart a **flamegraph**, a chart where "each entry represents the duration of the corresponding component render and all its descendant children components".

```tree caption="What one commit of the recording shows after the user types O: ChatRoom is cheap, and the three Message rows take the time."
One commit of the recording: the user types `O`
- +`ChatRoom` | Rendered because **its state `text` changed** | Its own time is **almost zero**
- !`Message` Hi! | Rendered with the **same props** | About **40 milliseconds**
- !`Message` Lunch at 12? | Rendered with the **same props** | About **40 milliseconds**
- !`Message` Sure | Rendered with the **same props** | About **40 milliseconds**
```

Each row takes about 40 milliseconds here, not 20, because Strict Mode calls it twice in development.

Your code measures nothing, so where do these times come from? React measures each render while the Profiler tab records. It is the same timing that `<Profiler>` gives you in code (Lesson 54).

### Fix the Component the Profiler Tab Names, Then Record Again

The recording names `Message`. So you wrap `Message` in `memo`, and you wrap only that one component:

```jsx title="src/components/Message.jsx"
import { memo } from 'react';

function Message({ text }) {
  let startTime = performance.now();
  while (performance.now() - startTime < 20) {
  }
  return <li>{text}</li>;
}

export default ~memo(Message)~; // The props of each row stay the same while the user types, so React skips it
```

Record the same typing again. This time, each commit lists `ChatRoom` as rendered, and none of the three `Message` rows. The commit is short, and the letters appear in the field at once.

### Development Numbers Are Not the User's Numbers

The 40 milliseconds for each row is a development number. Strict Mode doubles each render, and React Developer Tools itself adds work while it records. Real timings need three things. React's docs: "you need to run React in production mode, disable React Developer Tools, and use devices similar to the ones your app's users have".

So a recording in development tells you which component costs the most. It does not tell you how long the user waits.

## PRINCIPLE | `baseDuration` in `onRender`: the gap to `actualDuration` is what `memo` saved

> [!PRINCIPLE]
> **Principle 4: actualDuration Against baseDuration: Two Numbers Prove That memo Works**
>
> *Print `baseDuration` next to `actualDuration` in `onRender`; the gap between them is what memoization saved, and only a profiling build gives these numbers in production.*
>
> `actualDuration` is the time React spent on this update. `baseDuration` adds up the latest render time of every component in the tree, as if React skipped nothing. Without memoization, the two agree. With `memo` working, `actualDuration` falls and `baseDuration` stays. A normal production build turns profiling off, so `onRender` prints nothing there. Each `<Profiler>` adds overhead, so it goes only where you measure.
>
> **DO THIS:**
> ```jsx
> function onRender(id, phase, actualDuration, baseDuration) {
>   console.log(id, phase, actualDuration.toFixed(2), ~baseDuration.toFixed(2)~); // With memo: 0.10 next to 120.55
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Profiler id="App" onRender={onRender}>
>   ~<App />~ {/* **WRONG:** adds overhead to every render of the app, and prints nothing in a normal production build */}
> </Profiler>
> ```

### Two Numbers on One Console Line

The Profiler tab shows the times to you, inside the developer tools. `<Profiler>` gives the same kind of times to your own code (Lesson 54). In Lesson 54, our `onRender` printed only `actualDuration`. Now we print `baseDuration` next to it:

```jsx title="Printing actualDuration and baseDuration"
import { Profiler } from 'react';

function onRender(id, phase, actualDuration, ~baseDuration~) { // The fourth argument React passes to onRender
  console.log(id, phase, actualDuration.toFixed(2), baseDuration.toFixed(2));
}

<Profiler id="MessageList" onRender={onRender}>
  <ul>
    {messages.map(m => (
      <Message key={m.id} text={m.text} />
    ))}
  </ul>
</Profiler>
```

The two numbers answer two different questions:
1. **`actualDuration`** is the time React really spent rendering this tree for this update.
2. **`baseDuration`** is an estimate of the time a render of the whole tree would take if React skipped nothing. React's docs: it is "calculated by summing up the most recent render durations of each component in the tree".

A common mistake is to read `baseDuration` as the time of the first render. It is not. React adds up the latest render time of every component in the tree, including the components it skipped this time. So `baseDuration` is the cost of the tree if `memo` did nothing. React's docs: "Compare `actualDuration` against it to see if memoization is working."

### Measure the List of Messages

`ChatRoom` imports `Profiler` and wraps the list in it. The function `onRender` sits outside the component:

```jsx title="src/components/ChatRoom.jsx"
import { useState, Profiler } from 'react';
import Message from './Message.jsx';
import { useOnlineStatus } from '../useOnlineStatus.js';

function onRender(id, phase, actualDuration, baseDuration) {
  console.log(id, phase, actualDuration.toFixed(2), baseDuration.toFixed(2));
}

const initialMessages = [
  { id: 1, text: 'Hi!' },
  { id: 2, text: 'Lunch at 12?' },
  { id: 3, text: 'Sure' },
];

export default function ChatRoom() {
  const isOnline = useOnlineStatus();
  const [messages] = useState(initialMessages);
  const [text, setText] = useState('');
  return (
    <section>
      <h1>{isOnline ? 'Online' : 'Offline'}</h1>
      ~<Profiler id="MessageList" onRender={onRender}>~ {/* Measures the list and its three rows */}
        <ul>
          {messages.map(m => (
            <Message key={m.id} text={m.text} />
          ))}
        </ul>
      </Profiler>
      <input value={text} onChange={e => setText(e.target.value)} />
    </section>
  );
}
```

`'MessageList'` is our own string. React passes it back as the first argument, so one `onRender` can serve several `<Profiler>` trees.

### Without `memo`: the Two Numbers Agree

For this comparison, take `memo` off `Message` again. After the page loads, clear the Console, and the user types `O`:

```page width=text caption="The chat room after the user types O, with no memo on Message: onRender prints two numbers that are about the same."
heading: Online
line: Hi!
line: Lunch at 12?
line: Sure
form:
  field:  | O | good
log: MessageList update 120.40 120.55 | ChatRoom.jsx:6
```

The two numbers are about the same, so they look like one number printed twice. It may look the same, but it is NOT the same thing! `actualDuration` is what React spent on this update. `baseDuration` is the estimate for the whole tree, with nothing skipped. They agree only because React skipped nothing: all three rows rendered.

### With `memo`: the Two Numbers Split

Now wrap `Message` in `memo` again, as in Principle 3. Reload the page, clear the Console, and the user types `O` once more:

```page width=text caption="The same chat room after the user types O, with memo on Message: actualDuration falls near zero, and baseDuration stays near the cost of the three rows."
heading: Online
line: Hi!
line: Lunch at 12?
line: Sure
form:
  field:  | O | good
log: MessageList update 0.10 120.55 | ChatRoom.jsx:6
```

**`actualDuration` falls near zero, while `baseDuration` stays near the cost of the three rows.** React skipped the three rows, because their props stayed the same. `baseDuration` still adds up the most recent render time of each row. The gap between the two numbers is what `memo` saved on this keystroke. If a later change broke `memo`, the first number would climb back to the second, and the Console would show it.

```tree caption="What the two numbers of onRender show on one keystroke, without memo and with memo on Message."
`actualDuration` against `baseDuration` on one keystroke
- !Without `memo` | All three rows **render** | Both numbers are about **120**: nothing was skipped
- +With `memo` on `Message` | React **skips** the three rows | `actualDuration` near **0**, `baseDuration` still about **120**
```

### The Other Two Numbers: `startTime` and `commitTime`

React passes two more arguments to `onRender`, after `baseDuration`:
- **`startTime`** is a timestamp, a reading of the clock, taken when React began rendering this update.
- **`commitTime`** is a timestamp taken when React committed this update. React's docs: it "is shared between all profilers in a commit, enabling them to be grouped if desirable."

A page can have several `<Profiler>` trees, one around each part you measure, and they can sit inside each other. When one keystroke updates two of them, both `onRender` calls get the same `commitTime`. So your code can tell that the two lines belong to one update.

### A Production Build Prints No `onRender` Line

You want to confirm the fix on the build users get. Run `npm run build` and open the production build (Lesson 46). The user types in the field, and the Console prints no `MessageList` line at all.

It is easy to read that silence as "the rows no longer render", or as "`<Profiler>` is broken". Both readings are wrong. React's docs: "Profiling adds some additional overhead, so it is disabled in the production build by default. To opt into production profiling, you need to enable a special production build with profiling enabled."

That special build is the **profiling build**: React's production build with profiling turned on. To use it, the app imports from the profiling entry of React DOM instead of the usual client entry:

```jsx title="src/main.jsx in the profiling build"
import { createRoot } from ~'react-dom/profiling'~; // Instead of react-dom/client: the production build, with profiling on
```

React's docs recommend making that swap at build time, with a bundler alias. The bundler is the tool that packs your files for the browser, such as Vite (Lesson 46). An alias is a setting that tells the bundler to load one package whenever the code asks for another. A framework may also have its own setting for the profiling build.

With the profiling build, the production app prints the `MessageList` lines again. The numbers are smaller than in development, because Strict Mode does not call components twice in production.

`<Profiler>` also has a cost of its own. React's docs: "Each use adds some CPU and memory overhead to an application." **Overhead** is the extra work that the measuring itself adds. So put `<Profiler>` only around the part you are measuring, and remove it, and the alias, when you are done.

function getSnapshot() {
  return navigator.onLine;
}

function subscribe(callback) {
  window.addEventListener('online', callback);
  window.addEventListener('offline', callback);
  return () => {
    window.removeEventListener('online', callback);
    window.removeEventListener('offline', callback);
  };
}

export function useOnlineStatus() {
  const isOnline = useSyncExternalStore(subscribe, getSnapshot);
  ~useDebugValue(isOnline ? 'Online' : 'Offline')~; // Principle 2: the Components tab shows OnlineStatus: "Online"
  return isOnline;
}

| Aspect | The Habit to Avoid | The React Rule |
| :--- | :--- | :--- |
| **Finding a component** | Search the Elements panel for `Message`, and find only `<li>` nodes | Read the Components tab, where each component shows its props and state |
| **Checking where a component sits** | Read the provider code again and again | Check the hierarchy in the Components tab, and move the provider above the component that reads it |
| **Reading a custom Hook** | Guess what a raw `true` means | Call `useDebugValue` in a shared Hook, with a formatting function when the label costs work |
| **Finding the slow part** | Time a few lines with `console.time`, then wrap a guess in `memo` | Record the interaction in the Profiler tab, fix the component that costs the most, and record again |
| **Proving the fix** | Trust the feel of the field | Compare `actualDuration` with `baseDuration` in `onRender` |
| **Measuring what users get** | Trust development numbers, or expect `onRender` in a normal production build | Use the profiling build, `react-dom/profiling`, and remove `<Profiler>` where it is no longer needed |

Remember the one sentence of this lesson: **the browser knows the DOM nodes, React knows the components, so ask React**. Read the components in the Components tab, label your shared Hooks with `useDebugValue`, and measure in the Profiler tab before you fix anything.

## For the Interview

> **The Interview Question:** How do you inspect component trees, label and audit hook state, and profile renders with React Developer Tools?

### How to Answer Clearly in 30 Seconds

"React Developer Tools is a browser extension that reads React's own components, not the DOM. It adds two tabs on pages built with React:
1. **The Components tab** shows the component tree, with the props, state, and Hooks of the selected component. I can change props and state there, and check where a component really sits, such as inside or outside a context provider.
2. **The Profiler tab** records an interaction, such as typing in a field, and shows which components rendered in each commit and how long each took. I fix the component that costs the most, often with `memo`, and record again.

For custom Hooks, `useDebugValue` gives a readable label in the Components tab, such as `OnlineStatus: "Online"`, instead of a raw `true`. In code, `<Profiler>` gives `actualDuration` and `baseDuration`, and comparing them shows whether memoization works. Development timings are inflated, so for real numbers I use the profiling build."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why does the Elements panel not show your components, while React Developer Tools does?"**
   The Elements panel shows the DOM, and a component tag never reaches the DOM. React turns `<Message />` into the `<li>` that `Message` returns. React calls every component itself, so React knows each component, its props, its state, and its Hooks, and React Developer Tools reads them from React. That is also why the Components tab can show where a component sits next to a context provider. On Safari and other browsers, the `react-devtools` npm package gives the same tool in its own window.
2. **"When do you use `useDebugValue`, and why does it accept a function?"**
   I use it in custom Hooks that are shared, for example in a library, and that hold data that is hard to read in the Components tab. I do not add it to every Hook. It returns nothing and changes nothing on the page. The optional second argument is a formatting function, and React DevTools calls it with the value only when it inspects the component. So `useDebugValue(date, date => date.toDateString())` formats the date only while a developer looks at it. And `useDebugValue(date.toDateString())` formats it on every render, for every user.
3. **"Your recording in development shows 40 milliseconds for each row. Is that what users get, and how do you measure production?"**
   No. In development, Strict Mode calls each component twice, and React Developer Tools adds work while it records. The recording tells me which component costs the most, not the real time. For real timings, React's docs say to run React in production mode, turn off React Developer Tools, and use a device like the users' devices. A normal production build turns profiling off, so `onRender` prints nothing there. To measure production, I swap `react-dom/client` for `react-dom/profiling` with a bundler alias. Since React 19.2, React Performance tracks also show React's work in the browser's Performance panel. They include a Components track drawn as a flamegraph, next to the network requests and the JavaScript of the page.

```tree dir=right caption="Interview summary: what each tool of React Developer Tools answers, and the code version of each."
What React Developer Tools answers
- +Components tab | **Which component**, with what **props and state** | Checks the **hierarchy**, such as a provider in the wrong place
- +`useDebugValue` | **What a custom Hook holds**, in words | Shows **`OnlineStatus: "Online"`** instead of `true`
- +Profiler tab | **Which component rendered**, and **how long** it took | Record, fix the costliest one, **record again**
- +`Profiler` in code | `actualDuration` against **`baseDuration`** | Proves `memo` works; needs the **profiling build** in production
```
