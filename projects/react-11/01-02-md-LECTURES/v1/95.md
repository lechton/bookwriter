# Lecture 95: What the React Lints Catch, and Why a Silenced Lint Still Ships the Bug

*(What does a React lint warn you about, and what happens when someone turns it off?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | What do the React Hooks and Compiler lint rules catch, and why should they never be disabled?

---

## VS | Changing the code vs. a suppression comment: both clear the warning, only the change removes the bug

> Your editor can underline a line of code before you ever open the page, the way a spell checker underlines a typo. **The React lints underline every line that breaks a rule of React, and each underline names a bug the user will meet later.** A comment that turns a lint off removes the underline, not the bug, and it keeps the lint off for every later change to that line.

Start with plain JavaScript. You declare a variable and never use it:

```js title="Plain JavaScript: a variable nobody reads"
let ~total~ = 0; // ESLint underlines total: it is declared and never read
```

The program that underlines it is ESLint. It reads your files in the editor, without running them, and checks every line against a list of rules. This rule is called `no-unused-vars`. Each rule is one check, and React's docs call each check a lint.

Now the shortcut every developer finds sooner or later. You can tell ESLint to skip one rule on one line, with a comment:

```js title="Plain JavaScript: the same line with a suppression comment"
let total = 0; // eslint-disable-line no-unused-vars
```

The underline is gone. But look at the code: nothing changed. `total` is still declared, and still never read. The comment did not fix the problem. It only told ESLint to stop talking about it.

React adds its own rules to ESLint, in one package named `eslint-plugin-react-hooks`. They work exactly like `no-unused-vars`, with one big difference: the cost. An unused variable costs nothing on the page. A line that breaks a rule of React always ends as a bug on the page. Think of a chat stuck in the wrong room, a time that moves by itself, or a page that never loads.

> [!DEFINITION]
> **What is ESLint, and what is a lint?** [REVIEW] ESLint is a tool that reads your code in the editor and in the terminal, without running it, and marks each line that fails one of its checks. React's docs call each check a lint. The report arrives before the page runs, so it arrives before any user meets the bug (Lesson 82).

> [!DEFINITION]
> **What is a suppression comment?** [REVIEW] A suppression comment is a comment such as `// eslint-disable-line react-hooks/exhaustive-deps` at the end of a line. It tells ESLint to skip that one rule on that one line. Developers often write the same thing as an `eslint-disable-next-line` comment on the line above. The comment changes no code, so whatever the lint reported is still in the file (Lesson 36).

### The Same Comment in a Chat, a Month Later

Picture a chat app such as Slack. On the day it ships, it has one room, `general`, and a heading that reads `Welcome to the general room!`. The chat connects to the server for that room in an Effect.

The linter asked the developer to list `roomId` in the dependency array of that Effect. The developer thought the lint was wrong, because the room never changed, and wrote a suppression comment on that line.

A month later, a teammate adds a room picker above the heading. The user picks `travel`, and the heading changes. But the chat is still connected to `general`:

```page width=text caption="The chat a month after it shipped: the user picked travel, the heading says travel, and the Console shows only connections to general."
form:
  select: Choose the chat room: | travel
heading: Welcome to the travel room!
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
```

The Console shows what the chat connection did. The three lines come from the first load in development, where Strict Mode connects, disconnects, and connects again (Lesson 47). After the user picks `travel`, the Console prints nothing new. No line disconnects from `general`, and no line connects to `travel`.

So the page lies. The heading names one room, and the connection belongs to another. In a real chat, every message the user reads would still come from `general`.

No line of the teammate's code is wrong, and the editor showed no warning anywhere. The bug came from one comment, written a month earlier. That comment still sat on the dependency line, so the lint stayed off, and nobody was told that `roomId` now changes.

**Remember the one idea of this lesson: each React lint names a bug the page will show later. A suppression comment removes the message, not the bug, and it keeps removing the message for every later change on that line.**

### Five Lints, Five Bugs on the Page

Every React lint that a team turns off leaves its own bug behind, and the user sees each one:
1. With `exhaustive-deps` off, the heading says `travel`, and the chat stays connected to `general`. Principle 2 builds this case.
2. With `rules-of-hooks` off, the page goes blank after the user's click, and React reports "Rendered fewer hooks than expected" (Lesson 38).
3. With `set-state-in-render` off, the page never loads, and React reports "Too many re-renders" (Lesson 80).
4. With `purity` off, a time on the page moves each time the user types, or, with the React Compiler on, it stops moving (Lesson 63).
5. With `refs` off, a count on the page stays on an old number (Lesson 30).

### The Rule of Thumb: to silence a lint, change the code

**When a React lint marks a line, the only fix is to change the code until the lint passes. Never change the lint.**

React's docs say it twice. In general: "We recommend **never suppressing the linter**." And for the dependency array: "To change the dependency list, change the code."

That takes four steps:
1. **Read the report.** It names the value or the line that breaks a rule, such as `roomId`.
2. **Ask what the page will do because of it.** A chat stays in the wrong room, a time moves, or a page never loads.
3. **Change the code so the rule holds.** Add the value to the array, move a setter into the event handler, or read the clock once.
4. **Leave no suppression comment behind.** The lint then stays free to warn the next person who edits that line.

At work, developers really choose between four answers to a lint report. Only the first one fits every report:
1. **Change the code until the lint passes.** This fits every report.
2. **Leave the report visible, and fix it later.** This fits a compiler-powered report in code that already exists. React's docs say the compiler skips a component it can see breaking a rule, and that "you don't need to fix all violations immediately".
3. **Take one component out of the compiler with `"use no memo"`, for a while.** This fits a component that breaks after the team turns the compiler on (Lesson 63). React's docs say: "You should fix the underlying issue and remove the directive once resolved."
4. **Suppress the lint with a comment.** This fits nothing.

```tree caption="Four ways to answer a React lint report, and which ones fit."
Four ways to answer a React lint report
- +Change the code | Fits **every report** | The lint passes because **the bug is gone**
- +Leave the report visible | Fits a **compiler-powered report** in existing code | The team **still sees the line** it has to fix
- +Opt out with `"use no memo"` | Fits a component that **breaks under the compiler** | A **temporary** step, removed once the code is fixed
- !Suppress the lint | Fits **nothing** | The message is gone, **the bug stays**, and later edits get **no warning**
```

A senior developer also knows the five classic mistakes:
1. **Thinking a lint is about style**, like spaces or quotes. React's docs say the opposite about these rules: "They are essential and catch the most severe bugs early."
2. **Thinking a suppression covers only today's bug.** It also covers every later edit to that line, often written by someone else.
3. **Thinking `[]` means "run once".** Then a lint that asks for a prop looks wrong (Lesson 35).
4. **Thinking the compiler-powered lints matter only with the React Compiler.** The linter works without the compiler.
5. **Thinking a compiler-powered report must be fixed at once, or else the rule must go.** React's docs say the report can wait: "Address them at your own pace." The rule stays on.

The rest of the lesson builds the chat from day 1, turns the lints on, breaks it the way real teams do, and fixes it.

## SECTION | A Chat Room with a Room Picker

Our page is the chat room of React's docs (Lessons 32 to 37). Developers meet `exhaustive-deps` at work on exactly this kind of screen: an Effect that stays connected to a server for the room the user is in.

The connection is fake. It comes from React's docs, and it only prints one line in the Console when it connects, and one line when it disconnects:

```js title="src/chat.js"
export function createConnection(serverUrl, roomId) {
  return {
    ~connect~() { // For general, prints ✅ Connecting to "general" room at https://localhost:1234...
      console.log('✅ Connecting to "' + roomId + '" room at ' + serverUrl + '...');
    },
    ~disconnect~() { // For general, prints ❌ Disconnected from "general" room at https://localhost:1234
      console.log('❌ Disconnected from "' + roomId + '" room at ' + serverUrl);
    },
  };
}
```

On day 1, `App` renders one room:

```jsx title="src/App.jsx, day 1"
import ChatRoom from './components/ChatRoom.jsx';

export default function App() {
  return <ChatRoom ~roomId="general"~ />; // The chat has one room on the day it ships
}
```

The project grows one step at a time. Principle 1 adds the ESLint config file. Principle 2 writes the Effect in `ChatRoom`, then gives `App` the room picker of day 30. Principle 3 adds a Message field and an `Opened at` line. Here is where the files sit:

```files title="chat-room: File Explorer" caption="How the chat room project files sit in the project folder, in src/, and in src/components/."
eslint.config.js | lint config | Added in Principle 1: tells ESLint to read `.js` and `.jsx` files, and turns on the `recommended` preset of `eslint-plugin-react-hooks`
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `App` from `./App.jsx` and mounts it inside `<StrictMode>`
  chat.js | external helper | Exports `createConnection(serverUrl, roomId)` with `connect()` and `disconnect()`
  App.jsx | parent | Renders `ChatRoom`; on day 30, keeps `roomId` in state with a room picker
  components/
    ChatRoom.jsx | Effect | Connects to the chat server for `roomId` and shows the heading, the time it opened, and the Message field; holds the helper `formatTime`
```

**PRINCIPLES:** The React lints read the code before it runs and name the bug the page will show. One preset turns them all on, and each lint guards a different rule of React. Four principles follow:
1. **Principle 1: One line in the config turns on every React lint.** The `recommended` preset turns on the Hook lints and the render lints, with or without the React Compiler.
2. **Principle 2: A suppression comment keeps the lint off for good.** When a later change makes `roomId` change, nobody is told, and the Effect keeps the old room.
3. **Principle 3: `purity`, `refs`, and `set-state-in-render` check render code.** A clock read, a ref read, and a setter call during render each show a different bug.
4. **Principle 4: A compiler-powered report can wait, but the rule stays on.** Turning the rule off hides today's report and every later one.

## PRINCIPLE | `reactHooks.configs.flat.recommended`: one line turns on every React lint, with or without the compiler

> [!PRINCIPLE]
> **Principle 1: One Preset: `recommended` Turns On the Hook Lints and the Render Lints**
>
> *Add `reactHooks.configs.flat.recommended` to `eslint.config.js`, after an entry that tells ESLint to read `.jsx` files; it turns on the fundamental lints and the compiler-powered lints from the one package `eslint-plugin-react-hooks`, with or without the React Compiler.*
>
> Without this preset, ESLint reads the files and says nothing about Hooks, dependency arrays, or render code, so all five bugs of this lesson can reach the user. With it, the editor marks each broken line while the developer types it. The compiler-powered lints take their checks from the compiler, but they never need the compiler to be installed.
>
> **DO THIS:**
> ```js
> import reactHooks from 'eslint-plugin-react-hooks';
> import { defineConfig } from 'eslint/config';
>
> export default defineConfig([
>   { files: ['**/*.{js,jsx}'], languageOptions: { parserOptions: { ecmaFeatures: { jsx: true } } } },
>   ~reactHooks.configs.flat.recommended~, // Every React lint, from one package
> ]);
> ```
>
> **DO NOT DO THIS:**
> ```js
> import reactHooks from 'eslint-plugin-react-hooks';
> import reactCompiler from ~'eslint-plugin-react-compiler'~; // **WRONG:** the old second package; its lints now ship in eslint-plugin-react-hooks
> ```

Before any lint can mark a line, the project has to turn the React lints on. If the project has no ESLint yet, the team installs two packages, `eslint` and `eslint-plugin-react-hooks`. Then it adds one short file in the project folder:

```js title="eslint.config.js"
import ~reactHooks~ from 'eslint-plugin-react-hooks'; // The one package that holds every React lint
import { defineConfig } from 'eslint/config';

export default defineConfig([
  {
    ~files~: ['**/*.{js,jsx}'], // ESLint reads every .js and .jsx file
    languageOptions: { parserOptions: { ecmaFeatures: { ~jsx: true~ } } }, // ESLint can read JSX tags
  },
  ~reactHooks.configs.flat.recommended~, // Turns on the Hook lints and the render lints together
]);
```

`defineConfig` comes from ESLint. It takes an array of settings, and here the array holds two objects.

The first object tells ESLint which files to read, and lets it read JSX. ESLint needs both lines:
1. **Without `files`**, ESLint skips every `.jsx` file in the project and reports nothing at all.
2. **Without `jsx: true`**, ESLint stops at the first tag with `Parsing error: Unexpected token <`.

The second object is the `recommended` preset. The word `flat` in its name points to the config format of this file, which ESLint calls flat config.

From now on, the editor marks a broken line while the developer types it, before the page ever runs.

> [!DEFINITION]
> **What is a preset?** [NEW] A preset is a ready-made list of rules that a package turns on together, so the team does not have to name each rule by hand. `reactHooks.configs.flat.recommended` is the preset of `eslint-plugin-react-hooks`: one object in the config, and every React lint is on (Lesson 95).

### Two kinds of lints in one preset

The preset holds two kinds of lints. Both report breaks of the rules of React, and both look the same in the editor: a mark on the line and a message. The one difference is what each kind reads:
- **The fundamental lints, `rules-of-hooks` and `exhaustive-deps`,** read where Hooks are called and which values go in a dependency array. React's docs call them the lints for "fundamental React patterns". They have guarded React code for years (Lessons 35 and 38).
- **The compiler-powered lints, such as `purity`, `refs`, `set-state-in-render`, and `immutability`,** read all the code that runs while React renders the component, such as a clock read in the JSX or a setter called in the body. They come from the checks of the React Compiler. The React Compiler 1.0 post on React's blog calls them "compiler-powered lint rules", and they now ship inside the same package.

```tree caption="The two kinds of lints in the recommended preset of eslint-plugin-react-hooks."
The `recommended` preset of `eslint-plugin-react-hooks`
- +The fundamental lints [`rules-of-hooks` `exhaustive-deps`] | Read **where Hooks are called** | Read **what goes in a dependency array**
- +The compiler-powered lints [`purity` `refs` `set-state-in-render` `immutability`] | Read **all the code that runs during render** | Come from **the React Compiler's checks**, shipped in the same package
```

> [!DEFINITION]
> **What is the React Compiler?** [REVIEW] The React Compiler is a build tool that rewrites your components so React can reuse their earlier output instead of running the same work again. Before it rewrites a component, it checks that the component follows the rules of React. When it reuses an output that should have changed, a value on the page can freeze. `"use no memo"` as the first line of a component tells the compiler to skip that one component (Lesson 63).

### The compiler-powered lints work without the compiler

**The compiler-powered lints report breaks even in an app that never installs the React Compiler.** The name suggests the opposite, so here is a team that shows it:
1. The team installs `eslint-plugin-react-hooks` and adds the `recommended` preset.
2. The team never installs the React Compiler.
3. A developer writes `Date.now()` inside the JSX of a component, and the `purity` lint still marks the line.

The lints take their checks from the compiler, but they do not need the compiler to run. The React Compiler 1.0 post says it directly: "The linter does not require the compiler to be installed, so there's no risk in upgrading eslint-plugin-react-hooks." So every React app gets these reports, with or without the compiler.

When the team runs ESLint in the terminal, the report for that `Date.now()` call looks like this (Lesson 63):

```text title="ESLint in the terminal"
error  Error: Cannot call impure function during render ...  react-hooks/purity
```

The page and the Console do not change at all. The linter runs in the editor and in the terminal, never in the browser.

### Where `react-hooks/` in front of each rule comes from

Every report ends with a name such as `react-hooks/purity`. ESLint builds that name in two steps:
1. The package is named `eslint-plugin-react-hooks`, so the short name of the plugin is `react-hooks`.
2. ESLint writes the short name, then a slash, then the name of the rule.

The name `reactHooks` in the config file is a different thing. It is only the local name that our config file gives the package in its `import` line. We could call it anything.

### A team that keeps two packages

Some teams still carry an older second package. The compiler lints first came in a package of their own, `eslint-plugin-react-compiler`. Here is what often happens:
1. In 2024, the team set up the compiler lints with that second package.
2. Later, a developer upgrades `eslint-plugin-react-hooks` and keeps both packages in the config.
3. The React Compiler 1.0 post says the second package is no longer needed: "If you have already installed `eslint-plugin-react-compiler`, you can now remove it and use `eslint-plugin-react-hooks@latest`."

So the config needs one package, as in the file above.

In an interview, say where these lints run and which presets hold them. React's docs say the plugin "helps you catch violations of React's rules at build time", and the editor setup page says linters find problems "as you write". The compiler-powered rules ship in two presets of the same package, `recommended` and `recommended-latest`.

## PRINCIPLE | `eslint-disable-line`: the lint stays off for that line, for every later change

> [!PRINCIPLE]
> **Principle 2: No Suppression: An Old Suppression Hides the New Room Picker**
>
> *Never suppress `exhaustive-deps`; a suppression comment keeps the lint off for that line for every later change, so the Effect keeps an old value after someone else's correct edit.*
>
> On the day it is written, a suppression often looks harmless, because the value it hides does not change yet. But the comment has no date and no condition. When a teammate later makes `roomId` change, the editor stays quiet, the heading follows the new room, and the connection stays in the old one. Delete the comment, read the lint, and change the code until the lint passes.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[roomId]~); // Picking travel disconnects general and connects travel
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[]~); // **WRONG:** eslint-disable-line react-hooks/exhaustive-deps: after the room picker arrives, the chat stays in general
> ```

> [!DEFINITION]
> **What is a dependency array?** [REVIEW] The dependency array is the second argument of `useEffect`, the list of values the Effect reads. After every render, React compares each value in the list with its value from the render before. If one changed, React runs the cleanup of the old Effect and then runs the Effect again. If nothing changed, React does nothing. With `[]`, the list is empty, so nothing can ever change, and the Effect runs only after the first render (Lesson 35).

### Two dependency lists that behave the same on day 1

On day 1, the chat has one room, so `roomId` is always `'general'`. The developer wants the Effect to connect once, and has two dependency lists to choose from:

```jsx title="The two dependency lists of the chat's Effect, on day 1"
}, ~[]~); // eslint-disable-line react-hooks/exhaustive-deps -- on day 1, connects to general once
}, ~[roomId]~); // On day 1, also connects to general once, because roomId never changes
```

**It may look the same, or work the same at first, but it is NOT the same thing!** On day 1, both give the same page and the same Console.

But the lint does not look at today's value. It looks at the code. The code reads `roomId`, and `roomId` is a prop, so it is a reactive value: a value that can change from one render to the next (Lesson 35). The two lists stop behaving the same on the day a teammate makes `roomId` change.

```tree caption="The two dependency lists of the chat's Effect: the same on day 1, different on day 30."
The chat's Effect on day 1 and on day 30
- !With `[]` and the suppression comment [`eslint-disable-line`] | Day 1: connects to **`general`** once | Day 30: stays on **`general`** after the user picks `travel`
- +With `[roomId]` | Day 1: connects to **`general`** once | Day 30: disconnects from `general` and **connects to `travel`**
```

### Day 1: the suppression

Here is `ChatRoom` on day 1. The developer first wrote `[]`, and ESLint reported this:

```text title="ESLint in the terminal, day 1"
11:6  warning  React Hook useEffect has a missing dependency: 'roomId'. Either include it or remove the dependency array  react-hooks/exhaustive-deps
```

To ship, the developer added the suppression comment at the end of the same line (Lesson 36):

```jsx title="src/components/ChatRoom.jsx, day 1"
import { useEffect } from 'react';
import { createConnection } from '../chat.js';

const serverUrl = 'https://localhost:1234';

export default function ChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[]~); // **WRONG:** eslint-disable-line react-hooks/exhaustive-deps stops the lint from asking for roomId, today and every later day
  return <h1>Welcome to the {roomId} room!</h1>;
}
```

On day 1 the page works, and the Console shows the connection to `general`:

```page width=text caption="The chat on day 1, in development: one room, and Strict Mode's connect, disconnect, connect on the first load."
heading: Welcome to the general room!
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
```

### Day 30: a correct change, and the chat stays in general

A month later, a teammate adds the room picker to `App`. The user's pick goes into the `roomId` state variable, and `App` passes it down to `ChatRoom`. The teammate never opens the `ChatRoom` file, because nothing in the task asks for it:

```jsx title="src/App.jsx, day 30"
import { useState } from 'react';
import ChatRoom from './components/ChatRoom.jsx';

export default function App() {
  const [roomId, setRoomId] = useState('general');
  return (
    <>
      <label>
        Choose the chat room:{' '}
        <select value={roomId} ~onChange={e => setRoomId(e.target.value)}~> {/* The user's pick goes into roomId */}
          <option value="general">general</option>
          <option value="travel">travel</option>
          <option value="music">music</option>
        </select>
      </label>
      <ChatRoom ~roomId={roomId}~ /> {/* roomId is no longer always general */}
    </>
  );
}
```

**Beware! The bug shows up a month after the suppression, after a correct change by someone else, in a file nobody touched that day.** Here is what happens on day 30:
1. The teammate saves the `App` file. The editor shows no warning anywhere, because the suppression comment still covers the dependency line in `ChatRoom`.
2. The user picks `travel`, and the heading reads `Welcome to the travel room!`.
3. The Console prints nothing new. The chat is still connected to `general`.
4. The developer who wrote the suppression is not the developer who meets the bug.

```page width=text caption="The chat on day 30 after the user picks travel: the heading says travel, and the Console shows no new line."
form:
  select: Choose the chat room: | travel | bad
heading: Welcome to the travel room!
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
```

### Why the heading moves and the connection does not

The heading and the connection read the same `roomId`, and yet they disagree. The reason is when each one runs. The heading is JSX, so React makes it again on every render. The connection is made in the Effect, so React makes it only when the Effect runs.

Here is what React does after the user picks `travel`:
1. React renders `ChatRoom` again with the new room, so the heading reads `travel`.
2. React compares the new array `[]` with the old array `[]`. There is nothing to compare, so nothing changed, and React does not run the Effect again (Lesson 35).
3. The connection made on the first render, with `'general'`, stays open.

And why did the editor stay quiet on day 30? The suppression comment sits on the line with `[]`. The teammate's change did not touch that line, so the comment still applies to it. ESLint has no idea that `roomId` became a state variable in another file. It just obeys the comment.

React's docs name this exact cost: "You will no longer get such reminders for any future edits to that Effect if you disable the linter. This leads to bugs."

### The fix is in the file nobody changed

A week later, a bug report says the chat shows messages from the wrong room. A developer searches the `App` file, where the room picker was added, and finds nothing wrong there. The fix is in `ChatRoom`, and it takes three steps:
1. Delete the suppression comment. React's docs say: "you should always start by removing the linter suppression".
2. Read the lint. It asks for `roomId` again.
3. Write `[roomId]`.

```jsx title="src/components/ChatRoom.jsx, the fix" startLine="7"
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId]~); // No suppression: picking travel disconnects general and connects travel
```

Now, after the user picks `travel`, the Console shows two new lines. The chat leaves `general` and joins `travel`, so the heading and the connection agree:

```page width=text caption="The chat on day 30 with roomId in the array: after the user picks travel, the chat leaves general and connects to travel."
form:
  select: Choose the chat room: | travel | good
heading: Welcome to the travel room!
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "travel" room at https://localhost:1234...
```

React's docs give two pieces of advice for this case. For the search: "when you're looking for bugs in Effects, start by searching for linter suppressions." And for the team: "We recommend treating the dependency lint error as a compilation error. If you don't suppress it, you will never see bugs like this."

In an interview, expect the other common reason teams silence this lint: the value it asks for makes the chat reconnect on every keystroke. The lint is right in that case too, and the code has to change, for example by moving `options` inside the Effect (Lesson 37). React's docs say: "The linter only knows when the dependencies are *wrong*. It doesn't know *the best* way to solve each case."

## PRINCIPLE | `purity`, `refs`, and `set-state-in-render`: the editor marks impure render code before the page runs

> [!PRINCIPLE]
> **Principle 3: Pure Render: `purity`, `refs`, and `set-state-in-render` Flag Render Code Before It Runs**
>
> *Keep render pure: read a changing value such as the clock once with an initializer function, keep what the page shows in state instead of in a ref, and call setters in event handlers instead of in the component body.*
>
> The three newer lints check the code that runs while React renders the component. A clock read in the JSX shows a new time on every render. A ref read in the JSX shows the number of the last render. A setter called in the body asks for another render forever. Each line looks harmless on the first load, and the lint marks it before any user meets the bug.
>
> **DO THIS:**
> ```jsx
> const [openedAt] = useState(~() => formatTime(Date.now())~); // React keeps the time of the first render
> return <p>Opened at {openedAt}</p>;
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> return <p>Opened at {formatTime(~Date.now()~)}</p>; // **WRONG:** the time moves each time the user types
> ```

### Three lines that look like ordinary JavaScript

Here are three lines that each look normal inside a component. The newer lints mark all three:

```jsx title="Three lines in a component body that the newer lints mark"
<p>Opened at {formatTime(~Date.now()~)}</p> {/* **WRONG:** purity: reads the clock again on every render */}
<p>{~sentRef.current~} sent</p> {/* **WRONG:** refs: reads a ref during render */}
~setUnread(0);~ // **WRONG:** set-state-in-render: asks for another render during this one
```

They look like three unrelated habits. They are three forms of one mistake. Remember what a render is: React calls your component function, from the first line to the `return`. It does that on the first load, and again every time state changes, for example on every letter the user types in a field. Every line in the body runs again each time.

> [!DEFINITION]
> **What is a pure render?** [REVIEW] A render is pure when the same props and state always give the same JSX, the way `2 + 3` always gives `5`. React may call your component as often as it needs, so the component body must not read anything that changes by itself, such as the clock, and must not change anything while it runs, such as state (Lesson 14).

Each of the three lines breaks that rule in its own way, and each one shows a different bug to the user:
1. `Date.now()` in the JSX reads the clock, so the time on the page moves each time the user types.
2. `sentRef.current` in the JSX reads a ref, so the count on the page stays on an old number.
3. `setUnread(0)` in the body changes state, so the page never loads.

Developers usually go wrong by trusting the first load. A line that shows no error on the first load looks fine. React's docs warn about exactly this for refs: "your component might still work".

### The three lints, and what each one reports

All three lints come from the `recommended` preset of Principle 1:
- **`purity`** reports a call during render to a function that returns a different value each time, such as `Date.now()`, `Math.random()`, or `performance.now()`. It knows these calls by name. In version 7.1.1 of the package, it does not report `new Date()` or `crypto.randomUUID()`, although each one also gives a new value on every call. That is why our chat reads the clock with `Date.now()`.
- **`refs`** reports a read or a write of `ref.current` during render. It finds refs made with `useRef`, refs passed to a JSX `ref`, and any name that ends in `Ref`.
- **`set-state-in-render`** reports a setter called during render with no condition. React's docs say such a call "creates an infinite loop that crashes your app".

### `purity`: the time that moves when the user types

Now the chat room gains a Message field and an `Opened at` line that shows when the user opened the chat. `Date.now()` returns the current time as a number of milliseconds. `formatTime`, a small helper of our code, turns that number into text such as `10:42:07 AM`. A developer writes the time straight into the JSX:

```jsx title="src/components/ChatRoom.jsx, with the Message field"
import { useState, useEffect } from 'react';
import { createConnection } from '../chat.js';

const serverUrl = 'https://localhost:1234';
const ~formatTime~ = (ms) => new Date(ms).toLocaleTimeString(); // Turns a number from Date.now() into text such as 10:42:07 AM

export default function ChatRoom({ roomId }) {
  const [message, setMessage] = useState('');
  useEffect(() => {
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]);
  return (
    <>
      <h1>Welcome to the {roomId} room!</h1>
      <p>Opened at {formatTime(~Date.now()~)}</p> {/* **WRONG:** purity: a new time on every render */}
      <label>
        Message:{' '}
        <input value={message} ~onChange={e => setMessage(e.target.value)}~ /> {/* Each keystroke renders ChatRoom again */}
      </label>
    </>
  );
}
```

The user opens the chat at 10:42:07 AM:

```page width=text caption="The chat when the user opens it: the Opened at line shows the time of the first render."
form:
  select: Choose the chat room: | general
heading: Welcome to the general room!
line: Opened at 10:42:07 AM
form:
  field: Message:
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
```

Twenty seconds later, the user types `h` in the Message field, and the time on the page changes:

```page width=text caption="The same chat after the user types h, twenty seconds later: the Opened at line now shows the time of the keystroke."
form:
  select: Choose the chat room: | general
heading: Welcome to the general room!
line: Opened at 10:42:27 AM | bad
form:
  field: Message: | h
log: ✅ Connecting to "general" room at https://localhost:1234...
log: ❌ Disconnected from "general" room at https://localhost:1234
log: ✅ Connecting to "general" room at https://localhost:1234...
```

The time moves with each keystroke, and it stays still while the user does nothing. Here is why:
1. The user types `h`, and `onChange` calls `setMessage`.
2. React renders `ChatRoom` again, from the top of the function.
3. `Date.now()` runs again and returns the time of this render, not the time of the first one.

With the React Compiler on, the same kind of line can do the opposite. The compiler can reuse the component's earlier output and freeze the label (Lesson 63). So the same line gives one result without the compiler and another with it. What the user sees then depends on how the app is built, not on the code the developer reads.

The fix reads the clock once, with an initializer function. That is a function you pass to `useState` instead of a value. React calls it only on the first render, and keeps its result in state. Line 9 is new:

```jsx title="src/components/ChatRoom.jsx, the fix, the new line 9" startLine="8"
  const [message, setMessage] = useState('');
  const [openedAt] = useState(~() => formatTime(Date.now())~); // React calls this only on the first render
```

And the `Opened at` line, now on line 18, reads the state:

```jsx title="src/components/ChatRoom.jsx, the fix, line 18" startLine="18"
      <p>Opened at {~openedAt~}</p> {/* The same time on every render */}
```

**It may look the same, but it is NOT the same thing!** On the first load, both versions show the time the chat opened. The difference comes with the next render. With `Date.now()` in the JSX, React reads the clock again on every render. With the initializer function, React keeps the time of the first render.

After the user types `h`, the line still reads `Opened at 10:42:07 AM`, and the `purity` lint has nothing left to report.

### `refs`: the count that stays on an old number

Now a Send button counts the messages sent. Compare the count in a ref with the count in state:

```jsx title="With the count in a ref"
const sentRef = useRef(0);
<button onClick={() => { sentRef.current = sentRef.current + 1; }}>Send</button>
<p>{~sentRef.current~} sent</p> {/* **WRONG:** a click changes the ref and renders nothing: the line stays on 0 sent */}
```

```jsx title="With the count in state"
const [sent, setSent] = useState(0);
<button onClick={() => setSent(sent + 1)}>Send</button>
<p>{~sent~} sent</p> {/* Each click renders again: 1 sent, 2 sent */}
```

**It may look the same, but it is NOT the same thing!** In the developer's mind, both keep a count that goes up on each click. But a ref is a plain object, and React's docs say a change to it "doesn't trigger a re-render". So the line with `sentRef.current` keeps the number of the last render. Only the line with `sent` renders again on each click. The fix keeps the count in state (Lesson 30).

### `set-state-in-render`: the page that never loads

Suppose the room picker also shows an unread count, and a developer wants it to reset to zero when the room is shown. They write the setter in the body of `App`, because the body runs when the room is shown:

```jsx title="With setUnread in the body of App"
const [unread, setUnread] = useState(3);
~setUnread(0);~ // **WRONG:** every render asks for another render, so the page never loads
```

The page does not load. React stops, and the Console shows this error (Lesson 80):

```devconsole caption="The Console when the page tries to load with setUnread in the body of App."
x Uncaught Error: Too many re-renders. React limits the number of renders to prevent an infinite loop.
```

Here is the loop: the body runs, the setter asks for a new render, the new render runs the body again, and the body calls the setter again.

The fix calls the setter in the event handler where the change happens, as React's docs do for this lint:

```jsx title="With setUnread in the handler of the room picker"
<select value={roomId} onChange={e => { setRoomId(e.target.value); ~setUnread(0);~ }}> {/* Runs once, each time the user picks a room */}
```

**It may look the same, but it is NOT the same thing!** Both lines reset the unread count. In the body, the setter runs during every render and asks for one more render, so React never finishes. In the handler, the setter runs once, when the user picks a room.

And a suppression here? To quiet the editor, the developer would have to suppress `set-state-in-render`, and the page would still not load. The suppression fixes nothing. It only moves the bug out of the editor, where the developer sees it, and into the user's browser.

```tree caption="The three newer lints: three forms of one mistake, render must be pure, each with its own bug on the page."
Render must be pure
- !`purity` [`Date.now` in the JSX] | Reads **the clock** during render | The time **moves each time the user types**
- !`refs` [`sentRef.current` in the JSX] | Reads **a ref** during render | The count **stays on an old number**
- !`set-state-in-render` [`setUnread` in the body] | Changes **state** during render | The page **never loads**
```

In an interview, name the neighbors of these three lints:
1. **`set-state-in-effect`** reports a setter called at once inside an Effect, which gives an extra render (Lesson 80).
2. **`immutability`** reports a change to a prop in place, such as `story.seen = true` (Lesson 82).
3. **For `purity`**, React's docs also name "hydration mismatches", a case a later lesson teaches.
4. **For `refs`**, React's docs give the reason that matters for the future: "most of the newer features we're adding to React will rely on these expectations."

## PRINCIPLE | A compiler-powered report: the fix can wait, but the rule stays on

> [!PRINCIPLE]
> **Principle 4: Keep the Rule On: A Compiler Lint Report Can Wait, but the Rule Stays On**
>
> *A compiler-powered report in existing code may wait until the team fixes it; the rule itself stays on, so the team keeps seeing that line and every new break.*
>
> React's docs allow a team to fix compiler-powered reports at its own pace, because the compiler skips the components it sees breaking a rule. That permission is about fixing, never about turning the rule off. A rule turned off hides today's report and every later one, while the compiler can still compile a component whose break it cannot see.
>
> **DO THIS:**
> ```js
> export default defineConfig([
>   { files: ['**/*.{js,jsx}'], languageOptions: { parserOptions: { ecmaFeatures: { jsx: true } } } },
>   ~reactHooks.configs.flat.recommended~, // Every rule stays on; old reports wait in the editor until fixed
> ]);
> ```
>
> **DO NOT DO THIS:**
> ```js
> export default defineConfig([
>   { files: ['**/*.{js,jsx}'], languageOptions: { parserOptions: { ecmaFeatures: { jsx: true } } } },
>   reactHooks.configs.flat.recommended,
>   { rules: { ~'react-hooks/purity': 'off'~ } }, // **WRONG:** a clean editor, and every impure render line ships unseen
> ]);
> ```

### Three answers that leave the line as it is today

Go back to the chat before the fix of Principle 3, with `Date.now()` in the JSX of the `Opened at` line. The team turns the React Compiler on for the chat app. The editor marks that line with a `purity` report, next to many other reports in older files. The team has three answers that leave that line as it is today.

The first answer leaves the report visible:

```jsx title="With the report left visible"
<p>Opened at {formatTime(~Date.now()~)}</p> {/* The editor keeps the mark until the team fixes the line */}
```

The second answer takes `ChatRoom` out of the compiler for a while (Lesson 63):

```jsx title="With use no memo in ChatRoom"
export default function ChatRoom({ roomId }) {
  ~"use no memo";~ // The compiler skips ChatRoom until the team removes this line
```

The third answer turns the lint off for that line:

```jsx title="With the lint turned off"
<p>Opened at {formatTime(~Date.now()~)}</p> {/* **WRONG:** eslint-disable-line react-hooks/purity: the mark is gone, the bug stays */}
```

In all three, the `Opened at` line stays as it is today. They differ in what the compiler does, and in what the team still sees:
1. **With the report left visible**, the compiler makes its own choice about `ChatRoom`, and the team still sees the mark on the line.
2. **With `"use no memo"`**, the team tells the compiler to skip `ChatRoom`. React's docs call the directive "a temporary escape hatch" and say to remove it "once resolved".
3. **With the lint turned off**, the editor shows nothing on that line, and nothing for any new break that someone writes there later.

Developers confuse the first and the third. **It may look the same, or work the same at first, but it is NOT the same thing!** With the report left visible and with the lint turned off, the code and the page are the same today. Only the visible report keeps the line in front of the team.

One more difference matters in an interview. A compiler-powered report and an `exhaustive-deps` report do not have the same urgency. React's docs ask teams to treat the dependency lint "as a compilation error". For compiler-powered reports in code that already exists, they say: "Address them at your own pace."

```tree caption="Three answers to a compiler-powered report: all leave the line as it is today, and only one keeps the report in front of the team."
Three answers to the `purity` report on the `Opened at` line
- +Leave the report visible | The compiler **makes its own choice** | The team **still sees the line**, and every new break
- +Opt out with `"use no memo"` | The compiler **skips `ChatRoom`** | **Temporary**: removed once the line is fixed
- !Turn the lint off [`eslint-disable-line`] | The editor **shows nothing** | The bug **stays**, and **no later break** is reported either
```

### Why a report can wait

A report can wait because the compiler checks the same rules before it compiles. React's docs say that when the compiler finds a break, "it **automatically** skips over those components and hooks, while keeping the rest of your app compiled". The compiler installation page says the same about the lint: "When the ESLint rule reports an error, it means the compiler will skip optimizing that specific component or hook. This is safe".

So a skipped component runs exactly as the team wrote it, the way it ran before the compiler. The team can fix the reports one by one, and each fix lets the compiler compile one more component.

### A report is not always a skip

**Beware! The lint can see a break that the compiler lets through.** Here is one such case (Lesson 63):
1. The `purity` lint reported `Date.now()` in a `Message` component.
2. The compiler, in version 1.0.0, still compiled `Message`. Its own check for impure functions, `validateNoImpureFunctionsInRender`, is off by default.
3. The compiled component reused its output, and its "min ago" label stopped moving.

So a report is not a promise that the compiler skipped the component. With the lint on, the team still sees the line and can fix it. With the lint off, the team sees neither the report nor the frozen label, until a user does. React's debugging page names this case: "the compiler mistakenly compiled a component it should have skipped."

### Turning the rules off to clean the editor

Here is what a team often does when it turns the compiler on in an existing app:
1. The editor shows many compiler-powered reports.
2. To clean the editor, a developer turns a compiler-powered rule off in the ESLint config.
3. The `purity` report on the `Opened at` line is gone, and so is the report for every new line written after that day.
4. With the compiler on, a time label that reads the clock during render can stop moving (Lesson 63).
5. React's debugging page sends the team back to the lint, "Check with ESLint", and the lint is off.

```js title="eslint.config.js, with purity turned off"
export default defineConfig([
  { files: ['**/*.{js,jsx}'], languageOptions: { parserOptions: { ecmaFeatures: { jsx: true } } } },
  reactHooks.configs.flat.recommended,
  { rules: { ~'react-hooks/purity': 'off'~ } }, // **WRONG:** hides this report and every later one in the whole project
]);
```

A suppression comment turns a lint off for one line. This config line turns it off for every file of the project.

In an interview, give the two facts from React's debugging page. First, the compiler is "designed to skip problematic code rather than fail", so a report never stops the build. Second, runtime problems with the compiler come from breaks "that the compiler couldn't detect", and the lint is how the team sees the breaks it can detect. Then add the contrast with `"use no memo"`: the directive is meant to be removed once the code is fixed, while a suppression comment has no limit at all.

| Lint | What it reads | What the user sees when it is off | The fix |
| :--- | :--- | :--- | :--- |
| **`exhaustive-deps`** | The values an Effect reads, and its dependency array | The heading says `travel`, and the chat stays in `general` | Remove the suppression and list `roomId` |
| **`rules-of-hooks`** | Where each Hook is called | The page goes blank with "Rendered fewer hooks than expected" | Call every Hook at the top level |

## For the Interview

> **The Interview Question:** What do the React Hooks and Compiler lint rules catch, and why should they never be disabled?

### How to Answer Clearly in 30 Seconds

"Every React lint lives in one package, `eslint-plugin-react-hooks`, and its `recommended` preset turns them all on. They work even when the app does not use the React Compiler. Two kinds of lints catch two kinds of bugs:
1. **The fundamental lints** read Hook calls and dependency arrays. `rules-of-hooks` keeps the Hooks in the same order on every render, and `exhaustive-deps` keeps the dependency array equal to what the Effect reads.
2. **The compiler-powered lints** read the code that runs during render. `purity` catches values that change on every call, such as `Date.now()`. `refs` catches `ref.current` read during render. `set-state-in-render` catches a setter that loops forever. All three guard one rule: render must be pure.

They should never be disabled, because a suppression removes the message, not the bug. It also hides every later change on that line. A chat that suppressed `exhaustive-deps` on day 1 stays in the old room on day 30, after a teammate adds a room picker in another file. A compiler-powered report in old code may wait, but the rule stays on."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Our team silences the `exhaustive-deps` warning to ship faster. What classes of bugs does that invite?"**
   Three classes. First, a stale value today: the Effect reads an old prop or state, such as a `muted` setting that never updates (Lesson 36). Second, a stale value later: when a teammate makes a value change, such as `roomId` with a room picker, the Effect keeps the old one, and the editor says nothing because the comment still covers that line. Third, a bug that hides in the wrong file: the developer who meets it searches the file that changed, not the file with the comment. React's docs say to treat this lint "as a compilation error", and to "start by searching for linter suppressions" when an Effect misbehaves. To change the dependencies, change the code.
2. **"What do the newer lints, `purity`, `set-state-in-render`, and `refs`, guard against?"**
   They guard the rule that render must be pure. `purity` reports calls such as `Date.now()`, `Math.random()`, or `performance.now()` during render. Without the compiler, the page shows a new value on every render. With the compiler, the value can freeze. `refs` reports a read or a write of `ref.current` during render: a ref change renders nothing, so the page shows the number of the last render. `set-state-in-render` reports a setter called during render with no condition: every render asks for another one, and React stops with "Too many re-renders". Each fix moves the work out of render: an initializer function for the clock, state for what the page shows, and the event handler for the setter.
3. **"The React docs say compiler reports can be fixed at our own pace. Why not just turn those rules off until we are ready?"**
   Because "at your own pace" is about fixing, not about turning the rule off. While the rule is on, the team sees every old report, and every new break as someone writes it. The compiler skips the components it sees breaking a rule, so the old code keeps working as written. When the rule is off, the editor is clean and the team sees no new break. Meanwhile, the compiler can still compile a component whose break it cannot see, and a "min ago" label freezes (Lesson 63). For one component that breaks under the compiler, `"use no memo"` is the temporary answer, removed once the code is fixed.

```tree dir=right caption="Interview comparison: a React lint left on versus a React lint turned off."
A React lint left on vs. turned off
- +Left on [`recommended`] | Marks the line **before any user meets the bug** | Warns **every later editor** of that line
- !Turned off [`eslint-disable-line` `'off'`] | Removes **the message, not the bug** | Hides **every later change** on that line, written by anyone
```
