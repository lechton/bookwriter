# Lecture 114: How the Subscribe Button Knows the Server Is Still Working

*(While the email travels to the server, how does the button inside the form know it must read `Subscribing...`?)*

> INTERVIEW QUESTION | ❱ CORE | How does a nested field read the form's pending state during a server action?

---

## VS | A Plain Submit Button vs. a Button That Calls `useFormStatus`: both send the form, only the second shows that the server is still working

> When you tap a button and nothing on the screen changes, you believe the tap was lost, and you tap again. **A component inside a `<form>` can ask that form "are you still sending?" with `useFormStatus`, and it gets back `pending`, which stays `true` until the server answers.** Use it to show `Subscribing...` and to disable the button, so that a second tap on a slow phone cannot send the same email twice.

Remember how you would do this in plain JavaScript. You listen for the submit, you grab the button, you change it yourself, you wait for the server, and you change the button back:

```js title="Plain JavaScript: you change the button yourself"
form.addEventListener('submit', async (e) => {
  e.preventDefault();
  ~button.disabled = true~; // You lock the button by hand
  button.textContent = 'Subscribing...';
  await fetch('/subscribe', { method: 'POST', body: new FormData(form) });
  button.disabled = false; // You unlock it when the answer is back
  button.textContent = 'Subscribe';
});
```

In React, you never grab the button. React runs the form's action for you, so React already knows when the submit starts and when it ends. While the action runs, React marks the form as pending. Any component inside the form can ask its form: "Are you still sending?" That question is the Hook `useFormStatus`:

```jsx title="React: the button asks the form it sits in"
const { ~pending~ } = useFormStatus(); // true from the tap until the action finishes
<button type="submit" disabled={pending}>{pending ? 'Subscribing...' : 'Subscribe'}</button>
```

You met this Hook in Lesson 43, in the comment form under a photo post. There, the action ran in the browser. Here, the action calls a Server Function. **Yes, it is the exact same thing!** The same Hook, the same `pending`. Only the wait is longer: a trip to the server and back.

Here is the one sentence to keep in mind for this whole lesson:

**The pending state belongs to the `<form>`. Any component inside the form reads it with `useFormStatus`. The component that renders the `<form>` tag itself cannot.**

> [!DEFINITION]
> **useActionState and isPending.** [REVIEW] `useActionState` takes an action and a starting value, and returns three things: `state`, `formAction`, and `isPending`. The form calls `formAction`, React calls your action, and whatever the action returns becomes `state`. `isPending` is `true` while the action runs, but only the component that calls `useActionState` can read it (Lesson 42).

> [!DEFINITION]
> **useFormStatus.** [REVIEW] `useFormStatus` is a Hook from `react-dom`, not from `react`. It takes no arguments. A component rendered inside a `<form>` calls it and gets the status of that form: `pending`, `data`, `method`, and `action`. No prop carries these values: the Hook finds the form above the component by itself (Lesson 43).

> [!DEFINITION]
> **Transition.** [REVIEW] A Transition is an update that React runs in the background and keeps track of, so React knows at every moment whether it is still running. When a form's `action` is a function, React runs the submit inside a Transition (Lesson 41).

> [!DEFINITION]
> **Server Function.** [REVIEW] A Server Function is an `async` function in a file that starts with `'use server'`. It runs on the server, but code in the browser can call it like a normal function: the browser holds only a reference to it, and every call is a network request to the server (Lesson 110).

> [!DEFINITION]
> **Hydration.** [REVIEW] The server sends the HTML of the page first, and the JavaScript bundle arrives later. Hydration is the step where React, once the bundle has loaded, takes the HTML already on the screen and attaches your code to it. Before hydration, no React code of yours runs in the browser (Lesson 104).

### The Same Tap, Twice, on a Slow Phone

Take the newsletter form at the bottom of our blog post, from Lesson 113. A reader opens the post on a phone with a slow connection. The page has loaded, and React has hydrated it. The reader types `john@example.com` and taps `Subscribe`:

```page caption="The newsletter form right after the reader taps Subscribe, while the email travels to the server."
heading: Park Opens Today
line: The city opened a new park on Main Street.
section: Get new posts by email
form:
  field: Your email | john@example.com
  submit: Subscribe
```

For about two seconds, nothing on the button changes. It still reads `Subscribe`, and the reader can still tap it. So the reader thinks the first tap was lost, and taps again.

**Both taps reach the server, one after the other.** The first one saves the email. The second one finds the email already saved, and refuses it. The reader signed up for the first time, and the page answers as if they had signed up last week:

```page caption="The newsletter form after both taps: the reader signed up once, and the page says the email is already subscribed."
heading: Park Opens Today
line: The city opened a new park on Main Street.
section: Get new posts by email
form:
  field: Your email |
  error: john@example.com is already subscribed.
  submit: Subscribe
```

The fix is simple to say: while the server works, the button reads `Subscribing...` and refuses a second tap. But the button is its own component, `SubscribeButton`, inside the form of `SubscribeBox`, and the work runs on the server. So how does the button know that the server is still working?

It asks the form above it. The button calls `useFormStatus` and reads `pending`. The form stays pending for as long as its action runs, and here the action waits for the answer of the Server Function:

```tree dir=right caption="One tap on Subscribe, seen by the button, while the Server Function runs on the server."
One tap on Subscribe, seen by the button
- +Before the tap | The form is **not submitting** | `pending` is **`false`**: the button reads **Subscribe**
- +During the trip to the server and back | The form waits for **`subscribe`** to answer | `pending` is **`true`**: the button reads **Subscribing...** and cannot be tapped
- +After the answer comes back | The submit is **over** | `pending` is **`false`** again: the button reads **Subscribe**
```

**Why it matters:** the developer tests on a fast laptop, where the server answers before anyone could tap twice, so the bug never shows up there. The reader on a slow phone meets it on the very first visit, at the very first signup.

### Where Readers Usually Go Wrong

1. **They call `useFormStatus` in `SubscribeBox`**, the component that renders the `<form>` tag. There, `pending` never becomes `true`.
2. **They expect a form rendered by a Server Component to show `Subscribing...` by itself**, and they add a Hook to the Server Component, which breaks the page.
3. **They leave `'use client'` off the button's file.** The button works inside a form rendered by a Client Component, and breaks the day a Server Component form imports it.

### Four Ways to Show That the Server Is Still Working

Two flags say that a submit is running, and both are `true` during the same submit: `isPending` from `useActionState`, and `pending` from `useFormStatus`. The one difference is who can read them. `isPending` lives in the component that calls `useActionState`. `pending` can be read by any component inside the form, with no prop.

So developers choose between four ways to put a waiting text on a button. Each one fits a different place for the button:

```tree caption="Four ways to show that a Server Function is still working, and the button each one fits."
Four ways to show that the server is still working
- +`disabled={isPending}` in the same component [`useActionState`] | The button is written **inside the component that calls `useActionState`** | Fits a button **next to the Hook**
- +`isPending` passed as a prop [`<SubscribeButton isPending={isPending} />`] | The form's component **hands the flag one level down** | Fits a button **one level below**
- +`useFormStatus` in the button's component [`pending`] | The button **asks the form above it** | Fits a button **reused in many forms**, at **any depth**, and a form **rendered by a Server Component**
- +`useTransition` around the call [`startTransition`] | A click handler **calls the Server Function** | Fits a button that is **not in a form**
```

React's own docs use the first two ways in their examples. The fourth way is the one our newsletter button used before it became a form, in Lesson 110. This lesson builds the third way, and shows why it is the one that keeps working when a Server Component renders the form.

## SECTION | The Newsletter Form Under a Blog Post

We keep the files of the newsletter form from Lesson 113. One file is new, and one file changes:

```files title="blog: the newsletter form" caption="The files of the newsletter form. SubscribeButton.jsx is new, and SubscribeBox.jsx renders it in place of its plain button."
src/
  db.js | stand-in | Plays the database, unchanged
  actions.js | Server Functions | Starts with `'use server'`; `subscribe(previousState, formData)` returns `{ error }` or `{ message }`, unchanged
  SubscribeBox.jsx | Client Component | Calls `useActionState`; renders `<SubscribeButton />` in place of its plain button
  SubscribeButton.jsx | Client Component | New: starts with `'use client'`, reads `pending` with `useFormStatus`, and shows `Subscribing...`
  ErrorBoundary.jsx | from Lesson 72 | Unchanged
  App.jsx | Server Component | Renders the post and `<SubscribeBox />` inside `<ErrorBoundary>`, unchanged
```

**PRINCIPLES:** The pending state of a submit belongs to its form, and any component inside the form can read it. Five principles follow:
1. **`pending` from `useFormStatus`: the button reads `Subscribing...` until the server answers.** It is `true` from the tap until the Server Function answers, so the button changes its text and refuses a second tap.
2. **`useFormStatus` in the component that renders `<form>`: `pending` stays `false`.** The Hook reads only a form above the component that calls it, and nothing warns you.
3. **`data`, `method`, and `action`: they describe the submit on its way, never the answer of the server.** The answer comes through the `state` of `useActionState`.
4. **`'use client'` on the button's own file: the same button works inside a Server Component form.** The form stays on the server, and only the button goes to the browser.
5. **`pending` before hydration: the button stays on `Subscribe`, so only the server can stop a duplicate.** A tap before the bundle loads runs no React code in the browser.

## PRINCIPLE | `pending` from `useFormStatus`: the button reads `Subscribing...` until the server answers

> [!PRINCIPLE]
> **Principle 1: useFormStatus: The Button Reads pending Until the Server Answers**
>
> *Call `useFormStatus` in a component rendered inside the form; `pending` is `true` from the tap until the Server Function answers, so use it for the text and for `disabled`.*
>
> A Server Function can take seconds to answer on a slow connection. React runs the form's action in a Transition and keeps the form pending until the action finishes, and here the action waits for the server. The button reads that pending state from the form above it, with no prop, in exactly the same code as when the action runs in the browser.
>
> **DO THIS:**
> ```jsx
> export default function SubscribeButton() {
>   const { pending } = useFormStatus();
>   return (
>     <button type="submit" ~disabled={pending}~> {/* Reads Subscribing... and refuses a second tap */}
>       {pending ? 'Subscribing...' : 'Subscribe'}
>     </button>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function SubscribeButton() {
>   return ~<button type="submit">~Subscribe</button>; // **WRONG:** looks dead during the wait, so the reader taps twice
> }
> ```

### The Smallest Code: a Button That Asks Its Form

Here is the whole button. It asks the form above it for `pending`, and uses it twice, for the text and for `disabled`:

```jsx title="src/SubscribeButton.jsx"
'use client';

import { useFormStatus } from 'react-dom';

export default function SubscribeButton() {
  const { ~pending~ } = useFormStatus(); // true from the tap until subscribe answers
  return (
    <button type="submit" ~disabled={pending}~> {/* A second tap does nothing while the email travels */}
      {pending ? 'Subscribing...' : 'Subscribe'}
    </button>
  );
}
```

Watch the import: `useFormStatus` comes from `'react-dom'`, not from `'react'`. The `'use client'` line on top has its own story, in Principle 4.

`SubscribeBox` imports the new button:

```jsx title="src/SubscribeBox.jsx" startLine="3"
import { useActionState } from 'react';
import { subscribe } from './actions';
~import SubscribeButton from './SubscribeButton';~ // The new file, imported by its default name
```

It keeps everything else, and puts the new button where its plain button was:

```jsx title="src/SubscribeBox.jsx" startLine="12"
      <form action={formAction}>
        <label>
          Your email
          <input name="email" />
        </label>
        {state.error && <p>{state.error}</p>}
        ~<SubscribeButton />~ {/* Was <button type="submit">Subscribe</button> */}
        {state.message && <p>{state.message}</p>}
      </form>
```

Notice what is missing. None of our code sets `pending`, and no prop carries it into `SubscribeButton`. React sets it on the form while the form's action runs, and `useFormStatus` hands it to the button.

### VS | An Action in the Browser vs. a Server Function: the same button code

Put Lesson 43's form and our form side by side. Each one has a button component inside it:

```jsx title="A form whose action runs in the browser, and a form whose action calls the server"
<form ~action={addComment}~><PostButton /></form> {/* Lesson 43: addComment runs in the browser */}
<form ~action={formAction}~><SubscribeButton /></form> {/* formAction calls subscribe on the server */}
```

For the button, **yes, it is the exact same thing!** `SubscribeButton` has the same shape as `PostButton`: the same Hook, the same `pending`, the same ternary, and the same `disabled`. The Hook does not ask where the action runs. It asks only one question: is the form above me submitting?

You might think the server must send two messages to the browser, "I started" and "I finished". It sends neither. The whole wait happens inside the browser, so the browser already knows when it starts and when it ends:
1. The form's `action` is a function, so React runs the submit inside a Transition, and tracks whether that Transition is still running.
2. Our function is `formAction`. It calls `subscribe`, which is a network request to the server, and it waits for the answer.
3. While it waits, the Transition is still running, so the form is still pending, and `pending` stays `true`.

The reader types `john@example.com` and taps `Subscribe`. While the email travels, the button reads `Subscribing...` and is disabled (as seen in Lesson 21):

Open the Elements panel during the wait. The button is a plain HTML `<button>` element. React has only added the `disabled` attribute and changed its text:

```dom caption="The Elements panel during the wait: React has set disabled on the button and changed its text."
+ <button type="submit" disabled="">Subscribing...</button> | note: pending is true
```

### VS | Without `disabled={pending}` vs. With It: only the second one stops the second tap

The text is only half of the fix. Compare the two buttons:

```jsx title="The button without disabled, and with disabled={pending}"
<button type="submit">{pending ? 'Subscribing...' : 'Subscribe'}</button> {/* The text changes, and a second tap still submits */}
<button type="submit" ~disabled={pending}~>{pending ? 'Subscribing...' : 'Subscribe'}</button> {/* A second tap does nothing */}
```

On a fast laptop, the two work the same. **It may look the same, but it is NOT the same thing!** Without `disabled`, a second tap during the wait starts a second submit. With it, the reader cannot press the button while the first submit is pending.

Why does the second submit end in a refusal, and not in a second `You are subscribed!`? Because it does not run beside the first. It waits behind it:
1. The reader types `john@example.com`, an email that is not on the list yet, and taps `Subscribe`.
2. React calls `formAction`, which calls `subscribe` on the server. The submit is pending.
3. The button has no `disabled`, so the reader can tap it again, and does.
4. React puts the second submit in a queue behind the first (as seen in Lesson 42).
5. The first `subscribe` saves the email and returns `{ message: 'You are subscribed!' }`.
6. The second `subscribe` runs next. It finds the email already saved, and returns the refusal: the email is already subscribed.
7. The last returned value becomes `state`, so the reader sees the refusal.

React's docs add that frameworks "typically process one action at a time". So `disabled={pending}` does two jobs. It tells the reader that the tap worked, and it keeps a second submit from waiting in line behind the first.

### The Mistake: a Button in Its Own File, With No Pending State

A developer moves the button into `SubscribeButton.jsx`, but keeps it plain:

```jsx title="src/SubscribeButton.jsx" bad="2"
export default function SubscribeButton() {
  return <button type="submit">Subscribe</button>; // **WRONG:** no pending state, so the button looks dead during the wait
}
```

On the developer's fast laptop, the server answers before anyone could see the button change, so nothing looks missing. A reader on a slow phone taps twice and is told they are already subscribed. The fix is the button at the start of this principle: `useFormStatus`, `Subscribing...`, and `disabled={pending}`.

Remember: the pending state belongs to the form, and the button inside it reads it with `useFormStatus`.

## PRINCIPLE | `useFormStatus` in the component that renders `<form>`: `pending` stays `false`

> [!PRINCIPLE]
> **Principle 2: useFormStatus Next to the Form Tag: pending Stays false**
>
> *`useFormStatus` reads only a form above the component that calls it; in the component that renders the `<form>` tag, `pending` stays `false` on every submit, with no error.*
>
> The component that returns the `<form>` tag is above the form, not inside it. The Hook looks for a form above it, finds none, and answers as if nothing were being sent. In that component, read `isPending` from `useActionState` instead, or move the button into a child component.
>
> **DO THIS:**
> ```jsx
> export default function SubscribeBox() {
>   const [state, formAction] = useActionState(subscribe, { error: null });
>   return (
>     <form action={formAction}>
>       <input name="email" />
>       ~<SubscribeButton />~ {/* Calls useFormStatus inside the form */}
>     </form>
>   );
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function SubscribeBox() {
>   const [state, formAction] = useActionState(subscribe, { error: null });
>   const { ~pending~ } = useFormStatus(); // **WRONG:** this component renders the form, so pending stays false
>   return (
>     <form action={formAction}>
>       <input name="email" />
>       <button type="submit" disabled={pending}>Subscribe</button>
>     </form>
>   );
> }
> ```

### The Same Hook Line in Two Components

Why did we give the button its own component at all? `SubscribeBox` already renders the form, so it seems simpler to call the Hook there. Here is the same line in two places:

```jsx title="The same useFormStatus line in SubscribeBox and in SubscribeButton"
function SubscribeBox() {
  const { ~pending~ } = useFormStatus(); // Renders the <form> tag below: pending stays false
  return <form action={formAction}>...</form>;
}

function SubscribeButton() {
  const { ~pending~ } = useFormStatus(); // Rendered inside the <form>: pending is true during the submit
  return <button type="submit" disabled={pending}>...</button>;
}
```

**It may look the same, but it is NOT the same thing!** Think of the form as a Context provider: only the components inside it can read it. `useFormStatus` reads only a form above the component that calls it:
- **`SubscribeButton`** is rendered inside the `<form>`, so it has a form above it.
- **`SubscribeBox`** is the component that writes the `<form>` tag. The form sits below it, not above it, so the Hook finds no form there.

React's docs say it plainly: "`useFormStatus` will not track the status of a `<form>` rendered in the same component." With no form above it, `pending` is always `false`.

```tree caption="The same useFormStatus line in the component that renders the form tag, and in a component rendered inside the form."
Where `useFormStatus` is called
- !In `SubscribeBox` [renders `<form>`] | The form is **below** the component | No form above it: `pending` is **always `false`**
- +In `SubscribeButton` [inside `<form>`] | The form is **above** the component | `pending` is **`true`** while the submit runs
```

### The Mistake on Our Newsletter Form

A developer keeps the button inside `SubscribeBox` and adds the Hook there:

```jsx title="src/SubscribeBox.jsx" bad="9"
'use client';

import { useActionState } from 'react';
import { useFormStatus } from 'react-dom';
import { subscribe } from './actions';

export default function SubscribeBox() {
  const [state, formAction] = useActionState(subscribe, { error: null });
  const { ~pending~ } = useFormStatus(); // **WRONG:** SubscribeBox renders the form, so pending is always false
  return (
    <section>
      <h2>Get new posts by email</h2>
      <form action={formAction}>
        <label>
          Your email
          <input name="email" />
        </label>
        {state.error && <p>{state.error}</p>}
        <button type="submit" disabled={pending}>
          {pending ? 'Subscribing...' : 'Subscribe'}
        </button>
        {state.message && <p>{state.message}</p>}
      </form>
    </section>
  );
}
```

The reader taps `Subscribe`, and the submit runs on the server. The button keeps reading `Subscribe` for the whole trip, and the reader can still tap it. The Console shows nothing:

```page caption="The newsletter form while subscribe runs, with useFormStatus called in SubscribeBox: the button never changes."
heading: Park Opens Today
line: The city opened a new park on Main Street.
section: Get new posts by email
form:
  field: Your email | john@example.com
  submit: Subscribe
console: quiet
```

**The Hook gives no error, because "no form above me" is a normal answer for it.** It simply means that no submit is running above this component. So the mistake hides well. The developer tests on a fast connection, never sees `Subscribing...`, and believes the server was simply quick. On a slow phone, the double tap of Principle 1 comes back.

### The Form's Own Component Already Has a Flag

`SubscribeBox` does not need `useFormStatus` at all. It already calls `useActionState`, and that Hook returns a third value, `isPending`:

```jsx title="The pending flag in SubscribeBox, and the pending flag in SubscribeButton"
const [state, formAction, ~isPending~] = useActionState(subscribe, { error: null }); // In SubscribeBox
const { ~pending~ } = useFormStatus(); // In SubscribeButton, inside the form
```

For this submit, **yes, it is the exact same thing!** Both flags are `true` while the same submit runs. `isPending` says whether an action of this `useActionState` is running. `pending` says whether the form above is submitting. The one difference is which component can read each one:
- **In the component that calls `useActionState`**, the flag is `isPending`.
- **In a component rendered inside the form**, the flag is `pending` from `useFormStatus`, with no prop.

So there are two right fixes for the mistake above:
1. Use `isPending` in `SubscribeBox`.
2. Move the button into its own component inside the form.

We chose the second, because Principle 4 shows a form that has no `useActionState`, and so no `isPending`.

Remember: the pending state belongs to the form. Ask for it from inside the form, never from the component that writes the `<form>` tag.

## PRINCIPLE | `data`, `method`, and `action`: they describe the submit on its way, never the answer of the server

> [!PRINCIPLE]
> **Principle 3: useFormStatus Values: They Describe the Submit, Not the Answer**
>
> *`useFormStatus` returns `pending`, `data`, `method`, and `action` for the submit the form is sending; the answer of the server is not among them.*
>
> `data` is the form data being sent, or `null` between submits. `method` is `'get'` or `'post'`, taken from the `<form>` element, and it reads `'post'` here because the server writes `method="POST"` on a form whose action is a Server Function. `action` is the function passed to the form's `action` prop, which is `formAction` when the form uses `useActionState`. The answer of the Server Function comes back through the `state` of `useActionState`.
>
> **DO THIS:**
> ```jsx
> const { pending, ~data~ } = useFormStatus(); // The email being sent, while pending
> return <p>{pending && `Subscribing ${data.get('email')}...`}</p>;
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const { ~result~ } = useFormStatus(); // **WRONG:** useFormStatus has no answer from the server; result is undefined
> return <p>{result}</p>;
> ```

### The Smallest Code: Four Values From One Hook

`useFormStatus` takes no arguments, and it returns more than `pending`. Here are the four values `SubscribeButton` could read right after the reader taps `Subscribe`:

```jsx title="The four values useFormStatus returns, right after the tap"
const { pending, data, method, action } = useFormStatus();

~pending~ // true: the form is submitting
~data~.get('email') // 'john@example.com': the form data being sent
~method~ // 'post': how the form sends it
~action~ // formAction: the function passed to the form's action prop
```

Between two submits, `pending` is `false` and `data` is `null`.

All four describe the submit that the form is sending right now. None of them is what the server sends back. The answer, `You are subscribed!` or the refusal, reaches the page through the `state` of `useActionState` (as seen in Lesson 113).

```tree caption="What useFormStatus describes, and where the answer of the server comes from."
Two things the newsletter form knows about one submit
- +The submit on its way [`useFormStatus`] | `pending`, `data`, `method`, `action` | Read by **any component inside the form**
- +The answer that came back [`useActionState`] | `state`, such as **`{ message: 'You are subscribed!' }`** | Read by **the component that calls `useActionState`**
```

### VS | `data` in the Button vs. `formData` in `subscribe`: the same fields, in two places

`data` holds the fields of the form at the moment of the tap. The Server Function receives the same fields:

```jsx title="The same email, read in the button and on the server"
data.get('email') // In SubscribeButton, in the browser: 'john@example.com'
formData.get('email') // In subscribe, on the server: 'john@example.com'
```

For the fields, **yes, it is the exact same thing!** Both hold the `email` of the same submit. The one difference is where each one lives. The button reads `data` in the browser while the submit is on its way. `formData` is the serialized copy that React sends to the server (as seen in Lesson 110). React's docs use `data` the same way: a line that reads `Requesting` followed by the name being sent, while the form is pending.

### `method` Reads `'post'`, Though Our Form Has No `method`

`method` holds one of two strings, `'get'` or `'post'`. Our `<form>` has no `method` attribute, and a plain HTML form with no `method` sends with GET. Yet `method` reads `'post'`. Why?

`useFormStatus` takes `method` from the `<form>` element on the page. When the server renders a form whose action is a Server Function, React writes `method="POST"` on that element. React's docs say that with a function in `action`, "the HTTP method will be POST regardless of value of the `method` prop". That POST is how the form can reach the server before JavaScript loads (as seen in Lesson 112). After hydration, the element keeps `method="POST"`, so `method` reads `'post'`.

The comment form of Lesson 43 is different. No server rendered it, and its action runs in the browser, so nothing writes `method` on the element. There, `method` reads `'get'` during the wait.

### `action` Is `formAction`, Not `subscribe`

`action` is the function passed to the form's `action` prop. Which function that is depends on the form:

```jsx title="The action prop in Lesson 113's form, and in Lesson 112's form"
<form ~action={formAction}~>...</form> {/* Lesson 113 and this lesson: useFormStatus gives action as formAction */}
<form ~action={subscribe}~>...</form> {/* Lesson 112: useFormStatus gives action as the reference to subscribe */}
```

**Both forms end up calling `subscribe`, but their `action` is NOT the same thing!** In our form, the function is `formAction`, the one `useActionState` returns. It calls `subscribe` for us, but it is not `subscribe`. Only in Lesson 112's form, where `subscribe` sits right in the `action` prop, does `action` hold the reference to the Server Function.

### The Mistake: Looking for the Answer of the Server in `useFormStatus`

A developer wants the button to say `Done!` when the server answers, and looks for the answer in the Hook:

```jsx title="src/SubscribeButton.jsx" bad="2"
export default function SubscribeButton() {
  const { pending, ~result~ } = useFormStatus(); // **WRONG:** there is no result; result is undefined
  return <button type="submit">{result ? 'Done!' : 'Subscribe'}</button>;
}
```

The button never says `Done!`. `useFormStatus` returns only `pending`, `data`, `method`, and `action`. The answer lives in `state`, in `SubscribeBox`, where `useActionState` is called. That is why our thanks line and our refusal line are written in `SubscribeBox`, not in the button.

Remember: `useFormStatus` tells you about the submit while it travels. `useActionState` tells you what came back.

## PRINCIPLE | `'use client'` on the button's own file: the same button works inside a Server Component form

> [!PRINCIPLE]
> **Principle 4: A use client Line in the Button File: It Works Under a Server Component Form**
>
> *Put `'use client'` at the top of the button's own file; then the same button reads the pending state of a form rendered by a Server Component, and the form stays on the server.*
>
> `useFormStatus` runs only in client code. A Server Component cannot call any Hook, so it has no `isPending` to pass down. A button that asks its form with `useFormStatus` needs no prop, so it works under any form. With its own directive, the button is client code wherever it is imported, and the import from the Server Component becomes the boundary.
>
> **DO THIS:**
> ```jsx
> ~'use client';~ // The button is client code even when a Server Component imports it
>
> import { useFormStatus } from 'react-dom';
>
> export default function SubscribeButton() {
>   const { pending } = useFormStatus();
>   return <button type="submit" disabled={pending}>{pending ? 'Subscribing...' : 'Subscribe'}</button>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~import { useFormStatus } from 'react-dom';~ // **WRONG:** no 'use client' above, so a Server Component form makes this a Server Component
>
> export default function SubscribeButton() {
>   const { pending } = useFormStatus();
>   return <button type="submit" disabled={pending}>{pending ? 'Subscribing...' : 'Subscribe'}</button>;
> }
> ```

### The Same Form, Rendered by a Server Component

Go back one more lesson. In Lesson 112, `SubscribeBox` was a Server Component. It had no thanks line, and its form called `subscribe` directly:

```jsx title="src/SubscribeBox.jsx, Lesson 112's version, with our new button"
import { subscribe } from './actions';
import SubscribeButton from './SubscribeButton';

export default function SubscribeBox() { // No directive: a Server Component
  return (
    <section>
      <h2>Get new posts by email</h2>
      <form ~action={subscribe}~> {/* Lesson 112: the form calls the Server Function directly */}
        <label>
          Your email
          <input name="email" />
        </label>
        ~<SubscribeButton />~ {/* The only part of the form that runs in the browser */}
      </form>
    </section>
  );
}
```

One detail differs from our project. In Lesson 112, `subscribe` took the form data as its only parameter, `subscribe(formData)`. Our project keeps Lesson 113's `subscribe(previousState, formData)`. This block shows Lesson 112's version as it was.

This `SubscribeBox` cannot show `Subscribing...` by itself. It is a Server Component, and Hooks are not supported in Server Components (as seen in Lesson 108). So it cannot call `useActionState`, and it has no `isPending` to pass down. Of the four ways from the start of this lesson, the first two are closed, and the fourth would replace the form with a click handler.

The third way still works. `SubscribeButton` needs no prop. It asks the form above it, whoever rendered that form:

```jsx title="The same button in Lesson 113's Client Component form, and in Lesson 112's Server Component form"
<form action={formAction}><SubscribeButton /></form> {/* Rendered by a Client Component */}
<form action={subscribe}><SubscribeButton /></form> {/* Rendered by a Server Component */}
```

For the button, **yes, it is the exact same thing!** It reads the form above it in both. React's own blog names this exact need: design components "that need access to information about the `<form>` they're in, without drilling props down to the component". That is why the Hook exists.

### Why the Button's File Needs Its Own `'use client'`

`useFormStatus` is a Hook of `react-dom`, and React's docs list these Hooks among the APIs that "must run on the client". So `SubscribeButton` must be client code. A file becomes client code in one of two ways (as seen in Lesson 106):
1. It starts with `'use client'`.
2. A file that is already client code imports it.

Inside Lesson 113's `SubscribeBox`, the second way already applies. `SubscribeBox.jsx` starts with `'use client'`, so every file it imports is client code. Compare the top of the button file without its own directive and with it, both imported there:

```jsx title="SubscribeButton.jsx without its own 'use client'"
import { useFormStatus } from 'react-dom'; // Client code anyway: SubscribeBox.jsx imports it and starts with 'use client'
```

```jsx title="SubscribeButton.jsx with its own 'use client'"
~'use client';~ // The same client code: here the directive changes nothing
import { useFormStatus } from 'react-dom';
```

There, **yes, it is the exact same thing!** React's docs say that when a `'use client'` file is imported from client code, "the directive has no effect".

Now put the same two files inside Lesson 112's `SubscribeBox`, which is a Server Component. **It may look the same, and it worked the same until now, but it is NOT the same thing!**
- **Without `'use client'`**, server code imports the button, so the button becomes a Server Component. The React that runs Server Components has no `useFormStatus` to import, so the page fails with an error.
- **With `'use client'`**, the import itself is the boundary between server code and client code. Only the button goes to the browser. The form, the email field, and the action stay in the Server Component.

```tree caption="SubscribeButton.jsx with and without its own 'use client', under a Client Component form and under a Server Component form."
Does the button's file need its own `'use client'`?
- +Under Lesson 113's Client Component form | The button is client code **either way** | The directive **has no effect**: both work
- !Under Lesson 112's Server Component form, without the directive | The button becomes a **Server Component** | The Hook **cannot be imported**: the page fails with an error
- +Under Lesson 112's Server Component form, with the directive | The import is the **boundary** | Only the button **runs in the browser**; the form stays on the server
```

### The Button That Worked for Months

**A button file without `'use client'` breaks only when a new page imports it, sometimes months after it was written.** Here is how:
1. A team writes `SubscribeButton.jsx` without `'use client'`. It works in every form, because every form so far is in a Client Component.
2. A developer drops the same button into a form rendered by a Server Component, such as Lesson 112's `SubscribeBox`.
3. The import now comes from server code, so the button is a Server Component.
4. On the server, `react-dom` has no `useFormStatus` to give, so the import fails, and the page stops with an error before any HTML is sent.

The button did not change. Only the file that imports it did. That is why a button meant for many forms carries its own `'use client'`.

### The Mistake: Moving the Whole Form to the Browser

A developer wants `Subscribing...` on Lesson 112's Server Component form, and adds `useFormStatus` to `SubscribeBox` itself. The page breaks, because Hooks are not supported in Server Components. So the developer puts `'use client'` on top of `SubscribeBox.jsx`:

```jsx title="src/SubscribeBox.jsx" bad="1"
~'use client';~ // **WRONG:** only the button needs the browser, and now the whole component goes into the bundle

import { useFormStatus } from 'react-dom';
```

The page works again, but now the whole component ships in the JavaScript bundle and runs in the browser: its form, its email field, and its layout. And Principle 2 strikes again: the Hook sits in the component that renders the `<form>` tag, so `pending` stays `false`, and the button still never reads `Subscribing...`. The smaller fix keeps the form on the server, and moves only the button, with `'use client'` and `useFormStatus`, into its own file.

When the form must also show the answer of the server, as ours does, it needs `useActionState`, and so it is a Client Component (as seen in Lesson 113). The Server Component form fits a form that needs a pending button and no answer on the page.

Remember: the pending state belongs to the form, even when a Server Component renders that form. Only the button that reads it must be client code.

## PRINCIPLE | `pending` before hydration: the button stays on `Subscribe`, so only the server can stop a duplicate

> [!PRINCIPLE]
> **Principle 5: pending Before Hydration: The Button Stays on Subscribe**
>
> *The server renders the button with no submit running, so it reads `Subscribe`; a tap before hydration runs no React code in the browser, so nothing changes the button.*
>
> `useFormStatus` is a Hook, so it can change the button only once React runs in the browser. Before that, the form still reaches the server, because it is a real form with a Server Function as its action. Treat `Subscribing...` and `disabled` as help for the reader, and keep every check on the server.
>
> **DO THIS:**
> ```js
> export async function subscribe(previousState, formData) {
>   const email = formData.get('email');
>   if (~await db.subscribers.has(email)~) { // Checks every submit, with or without JavaScript
>     return { error: `${email} is already subscribed.` };
>   }
>   await db.subscribers.add(email);
>   return { message: 'You are subscribed!' };
> }
> ```
>
> **DO NOT DO THIS:**
> ```js
> export async function subscribe(previousState, formData) {
>   ~await db.subscribers.add(formData.get('email'));~ // **WRONG:** trusts disabled={pending}, which the first HTML does not have
>   return { message: 'You are subscribed!' };
> }
> ```

### The Same Tap, Before the Bundle Arrives

Go back to the reader on the slow phone, one step earlier (as seen in Lesson 112). The server has sent the HTML, so the post and the newsletter form are on the screen. The JavaScript bundle is still downloading. The reader types `john@example.com` and taps `Subscribe`.

The button does not change. It reads `Subscribe`, and the reader can still tap it, though our code is exactly the code of Principle 1:

```page caption="The newsletter form after a tap made before the JavaScript bundle has loaded: the button still reads Subscribe."
heading: Park Opens Today
line: The city opened a new park on Main Street.
section: Get new posts by email
form:
  field: Your email | john@example.com
  submit: Subscribe
```

**The reader who most needs `Subscribing...`, the one on a slow connection, is the one who cannot see it yet.** Here is why, in order:
1. The framework runs `App`, `SubscribeBox`, and `SubscribeButton` once on the server, and turns them into HTML (as seen in Lesson 102). No submit is running on the server, so `pending` is `false`, and the HTML button reads `Subscribe`, with no `disabled`.
2. The reader taps `Subscribe` before the bundle has loaded.
3. No React code runs in the browser yet. Nothing can call `useFormStatus` again, so nothing can change the button.
4. The tap is not lost. The form's action is a Server Function, so the browser posts the form to the server by itself (as seen in Lesson 112).

The first HTML holds the button exactly as the server rendered it:

```dom caption="The Elements panel before hydration: the button as the server rendered it, with no submit running."
! <button type="submit">Subscribe</button> | note: No disabled, and no React yet to add it
```

### VS | A Tap After Hydration vs. a Tap Before the Bundle Loads: the same submit, a different button

Put the two taps side by side:
- **A tap after hydration**: React runs the action and sets `pending`, so the button reads `Subscribing...` and is disabled.
- **A tap before the bundle loads**: no React code runs in the browser, so no Hook sets `pending`, and the button stays on `Subscribe`.

For the server, **yes, it is the exact same thing!** In both cases, `subscribe` runs and saves the email. For the button, **it is NOT the same thing!** `Subscribing...` and `disabled` exist only once React runs in the browser.

```tree caption="The same tap on Subscribe, after hydration and before the bundle loads."
One tap on Subscribe, at two moments
- +After hydration | **React** runs the action and sets **`pending`** | The button reads **Subscribing...** and **cannot be tapped**
- !Before the bundle loads | **No React code** runs in the browser yet | The button stays on **Subscribe**: no Hook has run
```

React's docs put it this way: "forms can be submitted before the JavaScript bundle is loaded". The form is what makes the signup work. The pending text is an extra on top of it, added once React runs.

### The Mistake: Trusting `disabled` to Stop a Second Submit

A developer sees that the button refuses a second tap, and removes the duplicate check from the Server Function:

```js title="src/actions.js" bad="7"
'use server';

import { db } from './db';

export async function subscribe(previousState, formData) {
  const email = formData.get('email');
  ~await db.subscribers.add(email);~ // **WRONG:** trusts disabled={pending}, which does not exist before hydration
  return { message: 'You are subscribed!' };
}
```

`disabled={pending}` helps the reader, but it cannot protect the database:
1. On a fast laptop, the bundle loads before anyone can tap, so the button always refuses a second tap, and the developer never sees a duplicate.
2. On a slow phone, the button in the first HTML has no `disabled` at all, so two taps before hydration send two submits.
3. Anyone can send this POST without our page at all (as seen in Lesson 113).

Only the check inside the Server Function protects the database.

Remember: `pending` is help for the reader in the browser. The server must still check every submit.

## All 5 Principles Together

### The Complete Code

`db.js` plays the database, unchanged:

```js title="src/db.js"
const subscribers = [];

export const db = {
  subscribers: {
    async has(email) {
      return subscribers.includes(email);
    },
    async add(email) {
      subscribers.push(email);
    },
  },
};
```

`actions.js` holds the Server Function, unchanged. It checks every submit, whatever the button shows:

```js title="src/actions.js"
'use server';

import { db } from './db';

export async function subscribe(previousState, formData) {
  const email = formData.get('email');
  if (~await db.subscribers.has(email)~) { // Principle 5: the check on the server, with or without JavaScript
    return { error: `${email} is already subscribed.` };
  }
  await db.subscribers.add(email);
  return { message: 'You are subscribed!' };
}
```

`SubscribeBox.jsx` keeps the answer in state and renders the new button inside its form:

```jsx title="src/SubscribeBox.jsx"
'use client';

import { useActionState } from 'react';
import { subscribe } from './actions';
import SubscribeButton from './SubscribeButton';

export default function SubscribeBox() {
  const [state, formAction] = useActionState(subscribe, { error: null }); // Principle 3: the answer lives here
  return (
    <section>
      <h2>Get new posts by email</h2>
      <form ~action={formAction}~> {/* Principle 2: the form above SubscribeButton */}
        <label>
          Your email
          <input name="email" />
        </label>
        {state.error && <p>{state.error}</p>}
        ~<SubscribeButton />~ {/* Principle 1: no pending prop */}
        {state.message && <p>{state.message}</p>}
      </form>
    </section>
  );
}
```

`SubscribeButton.jsx` is the new file:

```jsx title="src/SubscribeButton.jsx"
~'use client';~ // Principle 4: client code under any form

import { useFormStatus } from 'react-dom';

export default function SubscribeButton() {
  const { ~pending~ } = useFormStatus(); // Principles 1 and 5: true from the tap until subscribe answers, after hydration
  return (
    <button type="submit" disabled={pending}>
      {pending ? 'Subscribing...' : 'Subscribe'}
    </button>
  );
}
```

`ErrorBoundary.jsx` is the class component of Lesson 72, unchanged:

```jsx title="src/ErrorBoundary.jsx"
'use client';

import { Component } from 'react';

export default class ErrorBoundary extends Component {
  state = { hasError: false };

  static getDerivedStateFromError(error) {
    return { hasError: true };
  }

  render() {
    if (this.state.hasError) {
      return this.props.fallback;
    }
    return this.props.children;
  }
}
```

  return (

### The Order in Which Things Run

```tree dir=right caption="The order in which the components and the Server Function run, from the first HTML to the answer under the form."
From the first HTML to the answer on the screen
- +1. On the server [`App` `ErrorBoundary` `SubscribeBox` `SubscribeButton`] | The framework renders the page to HTML | No submit is running: the button reads **Subscribe**
- +2. Hydration [`SubscribeButton`] | React attaches to the HTML in the browser | From now on, `useFormStatus` **can change the button**
- +3. The tap [`formAction`] | React sends the form in a Transition | `pending` turns **`true`**: the button reads **Subscribing...** and is disabled
- +4. The answer [`subscribe` returns] | The returned value becomes **`state`** in `SubscribeBox` | `pending` turns **`false`**: the button reads **Subscribe**, and the answer line appears
```

### Summary

| Aspect | What a Developer Might Expect | What React Does |
| :--- | :--- | :--- |
| **Who tells the button the server is working** | The server sends "started" and "finished" | The browser knows: the form stays pending while its action waits for the answer of the server |
| **The button's code with a Server Function** | Something new for the server | The same `useFormStatus` and `pending` as with an action in the browser |
| **`disabled={pending}`** | Only a nicer look | Refuses the second tap, which would otherwise run after the first and be refused |
| **`useFormStatus` in `SubscribeBox`** | It owns the form, so it knows best | It renders the `<form>` tag, so it has no form above it, and `pending` stays `false` with no error |
| **The flag in the form's own component** | `useFormStatus` | `isPending` from `useActionState` |
| **The answer of the server** | Somewhere in `useFormStatus` | In the `state` of `useActionState`; `useFormStatus` gives only `pending`, `data`, `method`, and `action` |
| **`method` with no `method` attribute** | `'get'`, the HTML default | `'post'`, because the server writes `method="POST"` on a form whose action is a Server Function |
| **The button file without `'use client'`** | Fine, it works everywhere | Works under a Client Component form, and breaks under a Server Component form |
| **A tap before hydration** | The button reads `Subscribing...` | No React code runs yet, so the button stays on `Subscribe` |

Remember the one sentence of this lesson. **The pending state belongs to the `<form>`. Any component inside the form reads it with `useFormStatus`. The component that renders the `<form>` tag itself cannot.**

## For the Interview

> **The Interview Question:** How does a nested field read the form's pending state during a server action?

### How to Answer Clearly in 30 Seconds

"The nested component calls `useFormStatus` from `react-dom` and reads `pending`. The Hook reads the status of the `<form>` above it, as if the form were a Context provider, so no prop is needed. When the form's action calls a Server Function, nothing changes for the button: React runs the action in a Transition, and the form stays pending until the answer of the server comes back. Three rules keep it working:
1. **Call it inside the form.** In the component that renders the `<form>` tag, `pending` is always `false`. There, use `isPending` from `useActionState`.
2. **It describes the submit, not the answer.** It returns `pending`, `data`, `method`, and `action`. The answer of the server comes through `useActionState`.
3. **The button's file needs its own `'use client'`.** Then the same button works inside a form rendered by a Server Component, which cannot call any Hook itself."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why not just pass `isPending` from `useActionState` down as a prop?"**
   You can, when the button is one level below the component that calls `useActionState`. React's docs do it with `<Total quantity={count} isPending={isPending} />`. But a shared button lives in many forms at different depths, and every component in between would have to hand the prop on (as seen in Lesson 28). And a form rendered by a Server Component has no `useActionState` at all, so there is no `isPending` to pass. React's blog gives this as the reason the Hook exists: design components need the state of the form "without drilling props down to the component".

2. **"Why does `useFormStatus` return `pending: false` when I call it right next to my form?"**
   Because it reads only a form above the component that calls it. The component that returns the `<form>` tag is above the form, not inside it, so the Hook finds no form and gives its no-submit values: `pending` is `false` and `data` is `null`. There is no error and no warning. React's docs say it "will not track the status of a `<form>` rendered in the same component". It also ignores a form rendered by a child of the calling component: it reads only forms above it.

3. **"Does the pending text work before hydration?"**
   No. The server renders the button once with no submit running, so the first HTML reads `Subscribe` and has no `disabled`. A tap before hydration runs no React code in the browser, so no Hook changes the button. The form still reaches the server, because its action is a Server Function. With `useActionState`, React's docs add that React "will also automatically replay form submissions entered before hydration finishes", and Lesson 137 covers that replay. So the pending text is help for the reader, and the Server Function must still check every submit on the server.

```tree dir=right caption="Interview comparison: the two flags of one submit, and the component that can read each one."
Two flags for the same submit
- +`isPending` [`useActionState`] | **`true`** while the action runs | Read only by **the component that calls `useActionState`**
- +`pending` [`useFormStatus`] | **`true`** while the form submits | Read by **any component inside the form**, with no prop
```
