# Lecture 98: PureComponent, shouldComponentUpdate, and What Replaced Them

*(How did a class component skip a render it did not need, and what does a function component use for the same job today?)*

> INTERVIEW QUESTION | LEGACY | How did PureComponent and shouldComponentUpdate prevent re-renders, and what replaced them?

---

## VS | `shouldComponentUpdate` vs. `PureComponent`: you write the comparison, or React writes it for you

> When a parent component renders again, React renders every child component inside it again too, even a child whose props have not changed. **Before Hooks, a class component could skip that render in two ways: write a method named `shouldComponentUpdate` that answers no, or extend `PureComponent` and let React compare every prop.** Both ask one question about each prop, "is it the very same value as last time?", and today `memo` asks the same question for function components.

Start with something you know from plain JavaScript: the `===` operator.

```js title="Plain JavaScript: the same value, or the very same array"
~'Today' === 'Today'~; // true: two strings with the same letters are equal
~['Buy milk'] === ['Buy milk']~; // false: two arrays, created separately
const tasks = ['Buy milk'];
~tasks === tasks~; // true: the very same array, compared with itself
```

Hold on to these three lines. A string is equal to any string with the same letters. An array is equal only to itself, never to a copy with the same items inside. The same goes for an object and a function. Everything in this lesson comes back to these three lines.

Now the React part. When a component's state changes, React calls the component again, and then it calls every child component inside it again too (Lesson 54). Most of the time this is fast and harmless.

But picture a to-do list with an `<input>` field on top. Every letter the user types changes the parent's state. So the list below renders again after every keystroke, and every time it shows the very same tasks. With hundreds of tasks, typing starts to feel slow.

So the list wants to tell React: "Before you render me again, look at my props. If they are the very same as last time, skip me."

### Two Ways to Say "Skip Me"

Before Hooks, a class component had two ways to say it:

```jsx title="Two class components that tell React to skip a render"
class TaskList extends Component {
  ~shouldComponentUpdate~(nextProps) { // You write the comparison yourself: false means skip
    return nextProps.tasks !== this.props.tasks;
  }
}

class TaskList extends ~PureComponent~ { // React writes the comparison, for every prop
}
```

1. **Write a method named `shouldComponentUpdate`.** React calls it before each render, and the method answers. `false` means "skip me".
2. **Extend `PureComponent` instead of `Component`.** You write no method. React compares every old prop and every old state field with the new one, and skips when all of them are the same.

> [!DEFINITION]
> **What does it mean to skip a render?** [NEW] To skip a render means that React does not call the component's `render` method this time.
> The component's last output stays on the screen exactly as it was. Nothing on the page flickers or changes.
> A skip saves work only when nothing the component shows has changed. A skip at the wrong moment leaves old data on the screen (Lesson 98).

```tree caption="Two ways a class component told React to skip a render when nothing it shows has changed."
Two ways a class component skipped a render
- +Write `shouldComponentUpdate` | React **asks the component** before each render | The method returns **`false`** and React **skips `render`**
- +Extend `PureComponent` | React **compares every prop and state field** for us | When all of them are the same, React **skips `render`**
```

### What Is at Stake

A skip at the wrong moment hides real data from the user.

Suppose the list extends `PureComponent`, and the Add button's handler uses `push` to put `Pay rent` inside the array that state already holds. The user clicks Add. The `<input>` field empties, but `Pay rent` never appears in the list:

```page width=text caption="With push and PureComponent, the user clicks Add: the input field empties, and the list still shows only two tasks."
heading: My tasks
form:
  field: New task
  button: Add
line: Buy milk [Remove]
line: Call John [Remove]
```

Why? Remember `tasks === tasks`. After `push`, the array is still the very same array. React compares it with the one from the last render, finds the very same array, and skips the list. The user added a task, and the task is missing.

The word "pure" in `PureComponent` has its usual React meaning (Lesson 14): the component shows the same output for the same props, state, and context. By extending `PureComponent`, the component promises React that it follows that rule. So React may keep the last output instead of calling `render` again.

Here is where readers usually go wrong. A list with `extends Component` and a list with `extends PureComponent` show the exact same two tasks when the page opens. **It may look the same, or work the same at first, but it is NOT the same thing!** The difference appears only when the page updates. Readers hear "pure" as "faster everywhere". In fact, a `PureComponent` list renders again only when the parent hands it a different array.

### Four Ways to Skip a Render That You Meet at Work

You meet all four in real code: in old class code, in code that is moving from classes to functions, and in new code.
1. **`shouldComponentUpdate` written by hand**, in class code that compares only a few props. React's docs advise `PureComponent` instead.
2. **`extends PureComponent`**, in class code that lets React compare every prop and every state field.
3. **`memo`**, in function components, together with `useCallback` for function props and `useMemo` for object and array props (Lessons 55, 56, and 57).
4. **React Compiler**, which adds the same skip to every component automatically (Lesson 63).

```tree dir=right caption="Four ways to skip a render, from the oldest class code to the newest function code."
Four ways to skip a render
- +Hand-written method [`shouldComponentUpdate`] | Class code | We **write the comparison** ourselves
- +Built-in comparison [`PureComponent`] | Class code | React **compares every prop and state field**
- +Wrapped function [`memo`] | Function components | React **compares every prop**; `useCallback` and `useMemo` keep props the same
- +Automatic [React Compiler] | Function components | The compiler **adds the skip** for us
```

React's docs list `PureComponent` among the **Legacy React APIs**: React still exports it, but it is not recommended for new code. So this lesson teaches you to read this class code and translate it into function code. It does not ask you to write new class components.

### The Rule of Thumb: is every prop the very same value as last time?

**Ask one question about every prop: is it the very same value as in the last render? A string with the same letters is. An array, an object, or a function is the very same only when it is the same one, never a copy. When every prop passes, the component skips the render.**

That one question explains the two classic traps:
1. **A value that is new on every render**, such as an arrow function written inside the parent's `render`. It never passes, so the component never skips.
2. **An array changed with `push`.** It always passes, so the component skips even when the tasks changed.

Our page is a to-do list. At the top sits a New task `<input>` field with an Add button. Below them sits the list of tasks, and each task has its own Remove button. When the page opens, the list holds two tasks, `Buy milk` and `Call John`:


The user types `Pay rent` into the field, one letter at a time, and then clicks Add.

`Pay rent` takes eight keystrokes: seven letters and one space. Each keystroke changes the text in the parent's state, so the parent renders eight times. And so does the list, eight times, with the same two tasks every time. Nothing the list shows has changed, so it needs none of those eight renders.

The page is two components in two files:

```files title="todo-list: File Explorer" caption="The two components of the to-do list inside src/."
index.html | entry | The HTML page with the empty root div where React mounts
src/
  main.jsx | boundary | Imports `TodoApp` from `./TodoApp.jsx` and mounts it into `#root`
  TodoApp.jsx | parent | Exports `TodoApp` as default, holds `tasks` and `text` in state, and imports `TaskList`
  TaskList.jsx | child | Exports `TaskList` as default and renders one row per task
```

`TodoApp` is the parent, a class component (Lesson 96). It holds the tasks and the text of the field in its state. Each handler is a class field arrow, so JavaScript creates it once, when React creates the `TodoApp` instance:

```jsx title="src/TodoApp.jsx"
import { Component } from 'react';
import TaskList from './TaskList.jsx';

export default class TodoApp extends Component {
  state = { tasks: ['Buy milk', 'Call John'], text: '' };

  handleChange = (e) => {
    ~this.setState({ text: e.target.value })~; // Every keystroke renders TodoApp again
  };

  handleAdd = () => {
    this.setState({ tasks: [...this.state.tasks, this.state.text], text: '' });
  };

  removeTask = (task) => {
    this.setState({ tasks: this.state.tasks.filter(t => t !== task) });
  };

  render() {
    return (
      <section>
        <h1>My tasks</h1>
        <label>New task <input value={this.state.text} onChange={this.handleChange} /></label>
        <button onClick={this.handleAdd}>Add</button>
        <TaskList ~tasks={this.state.tasks}~ ~onRemove={this.removeTask}~ /> {/* The two props the list receives */}
      </section>
    );
  }
}
```

`TaskList` is the child. It starts as a plain `Component`. We add one `console.log` line, so the Console shows every time React calls its `render` method:

```jsx title="src/TaskList.jsx"

    return (

          <li key={task}>
            {task} <button onClick={() => this.props.onRemove(task)}>Remove</button>
          </li>
        ))}
      </ul>
    );
  }
}
```

The user types `Pay`, three letters. The list on the screen does not change. But the Console shows four lines: one from the first render, and one after each of the three keystrokes:

Now let's make the list skip, and then break the skip in every way developers really break it:

**PRINCIPLES:** A class component could skip a render in two ways: answer React itself with `shouldComponentUpdate`, or extend `PureComponent` and let React compare the props. Both ask only "is it the very same value?", and today `memo` asks the same question. Six principles follow:
1. **Principle 1: `shouldComponentUpdate` Returns `false` to Skip the List.** React calls it before each render, and `false` stops `render` from running. A prop it forgets stays frozen on the screen.
2. **Principle 2: `PureComponent` Compares Every Prop for You.** It is the same as a hand-written `shouldComponentUpdate` that compares every prop and every state field.
3. **Principle 3: An Arrow Written in `render` Is a New Function Every Time.** The comparison never finds `onRemove` the same, so the list renders after every keystroke.
4. **Principle 4: `push` Keeps the Same Array, So the New Task Is Missing.** The comparison finds the very same array and skips the list.
5. **Principle 5: `memo` Takes Over From `PureComponent`.** It compares props only, and its custom comparison answers the opposite question from `shouldComponentUpdate`.
6. **Principle 6: `useCallback` Keeps `removeTask` the Same After the Migration.** A function written inside a function component is new on every render, so `memo` needs `useCallback` to skip.

## PRINCIPLE | `shouldComponentUpdate`: return `false`, and React skips `render`

> [!PRINCIPLE]
> **Principle 1: `shouldComponentUpdate` Returns `false` to Skip the List**
>
> *When a class component defines `shouldComponentUpdate`, React calls it before each render caused by new props or new state; `false` skips `render`, and `true`, the default, renders.*
>
> The parent renders on every keystroke, so the list renders too, with the same tasks. `shouldComponentUpdate` lets the list compare its old props with the new ones and answer `false` when nothing it shows has changed. The method covers only the props it names, so a prop it forgets stays frozen on the screen.
>
> **DO THIS:**
> ```jsx
> shouldComponentUpdate(nextProps) {
>   return ~nextProps.tasks !== this.props.tasks~; // The list shows only tasks: the same array, so skip
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> shouldComponentUpdate(nextProps) {
>   return ~nextProps.tasks !== this.props.tasks~; // **WRONG:** render also shows title, which is never compared
> }
> render() {
>   return <h2>{this.props.title}</h2>;
> }
> ```

A class component can define a method named `shouldComponentUpdate`. You write it, and React calls it. Before each render that new props or new state would cause, React calls the method and reads the answer:
- **`true` means "render me again."** It is the default: a class without this method always renders.
- **`false` means "skip me."** React does not call `render`, and the list keeps its last output on the screen.

```tree caption="What React does with each answer of shouldComponentUpdate."
The answer of `shouldComponentUpdate`
- +Returns `true` | The default when the method is missing | React **calls `render`** again
- +Returns `false` | The method says **nothing I show has changed** | React **skips `render`**; the screen keeps the last output
```

### Where `nextProps` Comes From

React supplies it, in three steps:
1. The parent renders and produces the new props for `TaskList`.
2. Before React renders `TaskList`, it passes those new props to `shouldComponentUpdate` as the first argument.
3. At that moment, `this.props` still holds the old props. So the method can compare the old props with the new ones.

React supplies `nextState` the same way, as the second argument: the state the component is about to render with (Lesson 97). Our list has no state of its own, so it reads only `nextProps`.

### The List Skips Every Keystroke

We add the method to our list. It compares only `tasks`, the array the list shows:

```jsx title="src/TaskList.jsx"
import { Component } from 'react';

export default class TaskList extends Component {
  ~shouldComponentUpdate~(nextProps) { // React asks this before every render of TaskList
    return ~nextProps.tasks !== this.props.tasks~; // The same array while the user types: returns false
  }

  render() {
    console.log('TaskList rendered');
    return (
      <ul>
        {this.props.tasks.map(task => (
          <li key={task}>
            {task} <button onClick={() => this.props.onRemove(task)}>Remove</button>
          </li>
        ))}
      </ul>
    );
  }
}
```

The user opens the page fresh and types `Pay` again. The list looks the same as before. But this time the Console shows only one line, the one from the first render:

```page width=text caption="With shouldComponentUpdate, the user types Pay, and the Console still shows TaskList rendered only once."
heading: My tasks
form:
  field: New task | Pay
  button: Add
line: Buy milk [Remove]
line: Call John [Remove]
log: TaskList rendered | TaskList.jsx:9
```

Here is what React does after each keystroke:
1. The user types `P` in the field.
2. `handleChange` sets `text` in the parent's state, and the parent renders.
3. React calls `shouldComponentUpdate` on `TaskList`. The new `tasks` is the very same array as before.
4. The method returns `false`, so React does not call `render` on `TaskList`. The two rows stay on the screen as they were.

React never calls `shouldComponentUpdate` on the first render. So the list always appears once, whatever the method would answer.

When the user clicks Add, `handleAdd` builds a new array with `Pay rent` in it. The method sees a different array and returns `true`, and the list shows three tasks.

### The Method Answers Only for What It Compares

A hand-written comparison covers only the props it names. Months later, a teammate adds a `title` prop to the list, to show a heading above the rows. The teammate does not touch `shouldComponentUpdate`:

```jsx title="A comparison that never looks at the new title prop" bad="2,6"
shouldComponentUpdate(nextProps) {
  return ~nextProps.tasks !== this.props.tasks~; // **WRONG:** never looks at title, so a new title is skipped
}

render() {
  return <h2>{this.props.title}</h2>; // Stays on Today after the parent passes This week
}
```

The parent changes the title from `Today` to `This week`. The method still compares only `tasks`, finds the same array, and returns `false`. The heading on the screen stays on `Today`, and the Console says nothing.

That is why React's docs advise `PureComponent` instead: it "reduces the chance that you'll skip a necessary update", because it compares every prop, including the ones a teammate adds later.

### Five More Facts Interviewers Ask About

1. **React does not call the method on the first render, or after your code calls `forceUpdate`.** In both cases, `render` runs whatever the method would answer.
2. **`false` does not stop the children of the list.** A child component inside the list that changes its own state still renders.
3. **The answer is a hint, not a guarantee.** React's docs say React uses the return value as a hint, so React may still render the component.
4. **The comparison must stay quick.** React's docs warn against a deep comparison or `JSON.stringify` inside the method: "In the best case, you risk introducing multi-second stalls to your application, and in the worst case you risk crashing it."
5. **The method exists only to make the page faster.** React's docs put it plainly: "If your component breaks without it, fix that first."

## PRINCIPLE | `PureComponent`: React compares every prop and every state field for you

> [!PRINCIPLE]
> **Principle 2: `PureComponent` Compares Every Prop for You**
>
> *Extending `PureComponent` instead of `Component` is the same as a `shouldComponentUpdate` that shallowly compares every prop and every state field; the component still renders when a context it reads changes.*
>
> A hand-written comparison has to name every prop, and it breaks when someone adds a prop later. `PureComponent` compares every prop and every state field for us, each one on its own: a string by value, an array or a function by reference. A list that extends it skips every keystroke in the field above it.
>
> **DO THIS:**
> ```jsx
> class TaskList extends ~PureComponent~ { // React compares tasks, onRemove, and any prop added later
>   render() {
>     return <ul>{this.props.tasks.map(task => <li key={task}>{task}</li>)}</ul>;
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> class TaskList extends Component {
>   shouldComponentUpdate(nextProps) {
>     return ~nextProps.tasks !== this.props.tasks~; // **WRONG:** compares one prop by hand and misses onRemove and title
>   }
> }
> ```

### VS | A Hand-Written Comparison vs. `extends PureComponent`: the same check, written by you or by React

Our list receives two props, `tasks` and `onRemove`. To compare both by hand, the method must name both:

```jsx title="Comparing every prop by hand in shouldComponentUpdate"
class TaskList extends Component {
  shouldComponentUpdate(nextProps) {
    return ~nextProps.tasks !== this.props.tasks || nextProps.onRemove !== this.props.onRemove~; // Renders when any prop is different
  }
}
```

`PureComponent` writes that comparison for us. The class has no method at all:

```jsx title="Letting PureComponent compare every prop"
import { PureComponent } from 'react';

class TaskList extends ~PureComponent~ { // No method: React compares every prop and every state field
}
```

**Yes, it is the exact same thing!** React's docs say that extending `PureComponent` "is equivalent to defining a custom `shouldComponentUpdate` method that shallowly compares props and state."

Our list has no state, so here both versions compare exactly the same two props. The only difference is who writes the comparison. With `PureComponent`, React writes it, and it covers every prop, including a `title` prop that a teammate adds next year.

`PureComponent` is a **subclass** of `Component`: a class built on top of it. So your class keeps everything a normal class component has, such as `this.props` and `this.setState`.

> [!DEFINITION]
> **What is a shallow comparison?** [NEW] A shallow comparison checks each prop on its own against its old value, with the same check that `memo` uses, `Object.is` (Lesson 55). It never looks inside a value.
> A string or a number compares by value: `'Today'` and `'Today'` are the same.
> An object, an array, or a function compares by reference: two arrays with the same tasks inside count as different, unless they are the very same array. It is the `===` from the start of this lesson (Lesson 98).

```tree caption="What the shallow comparison of PureComponent looks at for each kind of prop."
How `PureComponent` compares one prop
- +A string or a number | Compared **by value** | `'Today'` and `'Today'` count as **the same**
- !An object, an array, or a function | Compared **by reference**, never by what is inside | Two arrays with the same tasks count as **different**, unless they are **the very same array**
```

So the senior answer to "what does `PureComponent` check?" is not "whether the tasks changed." It checks whether each prop is the same value, or the very same array, object, or function, as before. It never opens the array.

### A Context Still Renders a `PureComponent`

A developer extends `PureComponent` on a component that reads a context, such as the color theme of the page (Lesson 28). The theme changes while the props stay the same. The component renders anyway, and the developer thinks `PureComponent` is broken.

It is not. React's docs say: "your component will still re-render if a context that it's using changes." The comparison covers props and state, and a context is neither.

---

## PRINCIPLE | An arrow written in `render`: a new function every time, so `PureComponent` never skips

> [!PRINCIPLE]
> **Principle 3: An Arrow Written in `render` Is a New Function Every Time**
>
> *An arrow function, an object, or an array written inside the parent's `render` is a new reference on every render, so `PureComponent` sees a changed prop every time and never skips.*
>
> `PureComponent` compares a function by reference, not by what it does. An arrow written in `render` is created again on every render of the parent, so the list renders after every keystroke, as if it were a plain `Component`. A class field such as `removeTask` is created once and reaches the list unchanged.
>
> **DO THIS:**
> ```jsx
> <TaskList tasks={this.state.tasks} ~onRemove={this.removeTask}~ /> {/* Created once with the instance: the list skips */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <TaskList tasks={this.state.tasks} ~onRemove={(task) => this.removeTask(task)}~ /> {/* **WRONG:** a new function on every render, so the list never skips */}
> ```

### VS | `onRemove={this.removeTask}` vs. an Arrow Written in `render`: the same function, or a new one each time

The parent can pass the Remove handler to the list in two ways:

```jsx title="Passing the class field vs. passing an arrow written in render"
<TaskList tasks={this.state.tasks} ~onRemove={this.removeTask}~ /> {/* The same function on every render */}
<TaskList tasks={this.state.tasks} ~onRemove={(task) => this.removeTask(task)}~ /> {/* A new function on every render */}
```

Both call the same `removeTask` when the user clicks Remove. **It may look the same, or work the same at first, but it is NOT the same thing!**
- **With `onRemove={this.removeTask}`**, the list receives the same function on every render. `removeTask` is a class field, and JavaScript creates a class field once, when React creates the `TodoApp` instance (Lesson 96). Every render reads that same function from `this`.
- **With the arrow written in `render`**, JavaScript creates a brand-new function every time `render` runs. It does the same work as the old one, but it is a different function.

Remember `['Buy milk'] === ['Buy milk']`? Two functions with the same code are just as different. `PureComponent` compares the function itself, not what it does.

### The `PureComponent` List Renders on Every Keystroke

**Beware! A `PureComponent` that receives a new function on every render never skips.** Suppose the parent passes the arrow:

```jsx title="src/TodoApp.jsx" startLine="19" bad="7"
  render() {
    return (
      <section>
        <h1>My tasks</h1>
        <label>New task <input value={this.state.text} onChange={this.handleChange} /></label>
        <button onClick={this.handleAdd}>Add</button>
        <TaskList tasks={this.state.tasks} ~onRemove={(task) => this.removeTask(task)}~ /> {/* **WRONG:** a new onRemove after every keystroke */}
      </section>
    );
  }
```

Here is what happens when the user types one letter:
1. The user types `P` in the field.
2. The parent renders, and its `render` creates the arrow again.
3. `PureComponent` compares the new `onRemove` with the old one, and finds a different function.
4. `TaskList` renders again, though its rows have not changed.

The page looks the same. But the Console shows the list rendering after every keystroke, exactly as it did with `extends Component`:

```page width=text caption="With an arrow written in the parent's render, the PureComponent list still renders after each of the three keystrokes in Pay."
heading: My tasks
form:
  field: New task | Pay
  button: Add
line: Buy milk [Remove]
line: Call John [Remove]
log: TaskList rendered | TaskList.jsx:5
log: TaskList rendered | TaskList.jsx:5
log: TaskList rendered | TaskList.jsx:5
log: TaskList rendered | TaskList.jsx:5
```

A developer who sees this concludes that `PureComponent` does nothing. In fact, it did its job: it found a different function. React's docs say the same about `memo`: it "is completely useless if the props passed to your component are *always different,* such as if you pass an object or a plain function defined during rendering." One prop that is always new is enough to break the skip for the whole component.

### Where `task` Comes From

In `(task) => this.removeTask(task)`, the list supplies `task`, in three steps:
1. The user clicks Remove next to `Call John`.
2. The button's handler inside `TaskList` calls `this.props.onRemove(task)` with `'Call John'`.
3. The arrow receives `'Call John'` and passes it on to `removeTask`.

### The Same Rule for an Array or an Object

An array or an object written inside `render` falls into the same trap:

```jsx title="Passing the array in state vs. a copy made in render"
<TaskList ~tasks={this.state.tasks}~ onRemove={this.removeTask} /> {/* The same array until the tasks change */}
<TaskList ~tasks={[...this.state.tasks]}~ onRemove={this.removeTask} /> {/* A new array on every render */}
```

Both lists show the same tasks. But the three dots build a new array every time the parent renders, so `PureComponent` sees a different `tasks` after every keystroke.

The arrow on each Remove button inside `TaskList` is a different case. A `<button>` is not a `PureComponent`, so a new function there breaks no skip. The trap is only a new value passed to a component that compares its props.

In class code, the fix was to pass a function the class created once, such as the class field `removeTask`, or a method bound once in the constructor. Objects and arrays stayed in state instead of being built in `render`. Our page now goes back to `onRemove={this.removeTask}`.

## PRINCIPLE | `push` on the array in state: the very same array, so `PureComponent` hides the new task

> [!PRINCIPLE]
> **Principle 4: `push` Keeps the Same Array, So the New Task Is Missing**
>
> *When a handler changes the array in state with `push` and passes the same array to `this.setState`, `PureComponent` finds the same reference and skips, so the new task does not appear when the user clicks Add; a new array fixes it.*
>
> `PureComponent` compares the array by reference. An old array with a new item inside is still the same array, so React skips the list, and the user does not see the task they added. The task appears later, at the next change that builds a new array. A new array, such as one built with three dots, shows the change at once.
>
> **DO THIS:**
> ```jsx
> handleAdd = () => {
>   this.setState({ tasks: ~[...this.state.tasks, this.state.text]~, text: '' }); // A new array: the list renders
> };
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> handleAdd = () => {
>   ~this.state.tasks.push(this.state.text)~; // **WRONG:** the same array, so PureComponent skips and the task is missing
>   this.setState({ tasks: this.state.tasks, text: '' });
> };
> ```

### VS | `push` vs. a New Array: the same array with one more item, or a different array

The Add handler can put the text of the field into the tasks in two ways:

```jsx title="Adding a task with push vs. with a new array"
~this.state.tasks.push(this.state.text)~; // Puts the task inside the array that state already holds
this.setState({ tasks: this.state.tasks, text: '' });

this.setState({ tasks: ~[...this.state.tasks, this.state.text]~, text: '' }); // Hands over a brand-new array
```

In both ways, the array ends up holding `Pay rent`. In the developer's mind, both do the same thing: "the tasks now include Pay rent." **It looks the same, but it is NOT the same thing!**
- **`push` changes the existing array.** So `tasks` is still the very same array: `tasks === tasks`.
- **The three dots build a new array.** So `tasks` is a different array.

And `PureComponent` checks only that: the same array, or a different one.

`push` on the array in state was already wrong (Lesson 17), because it changes the array that state already holds instead of replacing it. With `extends Component`, the list renders anyway, so the mistake stays hidden. With `extends PureComponent`, the mistake shows up on the screen.

### The User Clicks Add, and the Task Is Missing

**Beware! With `push`, the user clicks Add, the field empties, and the new task does not appear.** Suppose the parent's `handleAdd` uses `push`, while the list extends `PureComponent`:

```jsx title="src/TodoApp.jsx" startLine="11" bad="2,3"
  handleAdd = () => {
    ~this.state.tasks.push(this.state.text)~; // **WRONG:** changes the array that state already holds
    this.setState({ ~tasks: this.state.tasks~, text: '' }); // **WRONG:** tasks is the same array as before
  };
```

Here is what happens when the user types `Pay rent` and clicks Add:
1. `handleAdd` pushes `'Pay rent'` into the array that `this.state.tasks` holds.
2. `this.setState` sets `text` to an empty string, and sets `tasks` to that same array.
3. The parent renders, because it is a plain `Component`. The field empties.
4. `PureComponent` compares `tasks`: the same array as before. It compares `onRemove`: the same function. So React skips the list.
5. The list still shows two tasks, though the array now holds three.

The page shows the wrong list. The Console shows no new line and no message, so nothing tells the developer what went wrong.

Then something strange happens. The user clicks Remove next to `Call John`, and `Pay rent` suddenly appears:
1. `removeTask` builds a new array with `filter`, starting from the array that `push` changed. The new array holds `Buy milk` and `Pay rent`.
2. `PureComponent` sees a different `tasks`, so React renders the list.
3. `Pay rent` appears at the same moment that `Call John` disappears.

### How This Bug Reaches a Real Team

This bug often stays hidden for months:
1. A class handler calls `this.state.tasks.push(newTask)` and then `this.setState({ tasks: this.state.tasks })`.
2. Under `extends Component`, the list renders anyway and reads the changed array, so the task appears, and nobody notices the mistake.
3. Later, someone changes the list to `extends PureComponent` to make typing faster.
4. Adding a task stops working, and the change to `PureComponent` looks like the cause.

The real cause is `push`. React's docs explain why the two meet: "Common React optimization strategies rely on skipping work if previous props or state are the same as the next ones. If you never mutate state, it is very fast to check whether there were any changes."

### The Fix: a New Array

Pass a new array, built with three dots (Lesson 19):

```jsx title="src/TodoApp.jsx" startLine="11" good="2"
  handleAdd = () => {
    this.setState({ tasks: ~[...this.state.tasks, this.state.text]~, text: '' }); // A new array: the list shows Pay rent
  };
```

Now `tasks` is a different array, `PureComponent` sees the change, and the list shows three tasks right after the user clicks Add.

Something that can be tricky: a copy made with three dots is a shallow copy (Lesson 19). The items inside are still the same items. So if the tasks were objects, changing one task object inside the new array would still be a mutation. A `PureComponent` that receives that one task object as a prop would still skip.

## PRINCIPLE | `memo`: it takes over from `PureComponent`, and compares props only

> [!PRINCIPLE]
> **Principle 5: `memo` Takes Over From `PureComponent`**
>
> *When a `PureComponent` class becomes a function, wrap the function in `memo`; `memo` compares props only, because a function component already skips a render when its state is set to the same value.*
>
> For props, `memo` does exactly what `PureComponent` did: it compares each prop with its old value and skips when all are the same. It does not compare state, because a function component already skips when its `set` function receives the same value. Its custom comparison returns `true` to skip, the opposite of `shouldComponentUpdate`.
>
> **DO THIS:**
> ```jsx
> const TaskList = ~memo~(function TaskList({ tasks, onRemove }) { // The skip carries over from PureComponent
>   return <ul>{tasks.map(task => <li key={task}>{task}</li>)}</ul>;
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ~TaskList~({ tasks, onRemove }) { // **WRONG:** PureComponent dropped without memo, so the list renders after every keystroke
>   return <ul>{tasks.map(task => <li key={task}>{task}</li>)}</ul>;
> }
> ```

### VS | `extends PureComponent` vs. `memo`: the same check for props

Today the list is a function component. To skip its renders, we wrap the function in `memo` (Lesson 55):

```jsx title="The class with PureComponent and the function with memo"
class TaskList extends ~PureComponent~ { // Compares every prop and every state field
  render() {
    return <ul>{this.props.tasks.map(task => <li key={task}>{task}</li>)}</ul>;
  }
}

const TaskList = ~memo~(function TaskList({ tasks, onRemove }) { // Compares every prop
  return <ul>{tasks.map(task => <li key={task}>{task}</li>)}</ul>;
});
```

**For props, yes, it is the exact same thing!** Both compare each prop with its old value, and both skip when every prop is the same. React's docs give this exact step for a migration: when you convert a `PureComponent` class to a function, wrap the function in `memo`. They also say: "Optimizing class components with `shouldComponentUpdate` is similar to optimizing function components with `memo`."

Where do `tasks` and `onRemove` come from? React supplies them, inside the one props object of the function (Lesson 8). The destructuring `{ tasks, onRemove }` takes the place of reading them from `this.props`.

Where does `memo` come from? We import it from `react`, and it works in three steps:
1. `memo` receives our function.
2. It does not change that function.
3. It returns a new component, and the name `TaskList` now holds that new component.

### For State, `memo` and `PureComponent` Are NOT the Same Thing

`PureComponent` compares state too. `memo` does not. React's docs say: "Unlike `PureComponent`, `memo` does not compare the new and the old state. In function components, calling the `set` function with the same state already prevents re-renders by default, even without `memo`."

So a function component needs no help with its own state. When it calls its `set` function with the value it already holds, React already skips the render. `memo` is needed only for the props that arrive from the parent.

### VS | `shouldComponentUpdate` vs. `arePropsEqual`: they look alike and answer opposite questions

`memo` accepts a second argument: a custom comparison function, which React's docs name `arePropsEqual` (Lesson 55). We pass it as `memo(TaskList, arePropsEqual)`. It looks like `shouldComponentUpdate`, but it answers the opposite question:

```jsx title="The same two props compared in shouldComponentUpdate and in arePropsEqual"
~shouldComponentUpdate~(nextProps) { // Returns true to render again
  return nextProps.tasks !== this.props.tasks || nextProps.onRemove !== this.props.onRemove;
}

function ~arePropsEqual~(oldProps, newProps) { // Returns true to skip
  return oldProps.tasks === newProps.tasks && oldProps.onRemove === newProps.onRemove;
}
```

**It may look the same, but it is NOT the same thing!**
- **`shouldComponentUpdate` asks "should I render again?"** It returns `false` to skip.
- **`arePropsEqual` asks "are the old props and the new props equal?"** It returns `true` to skip.

Copy the body of `shouldComponentUpdate` into `arePropsEqual` without flipping it, and the list does the opposite of what you want. It renders when it should skip, and it skips when it should render, so the user never sees a new task.

And a custom comparison must compare every prop, functions included. React's docs warn that a comparison that leaves out a function prop can leave the component calling a handler from an earlier render, a handler that still sees the old props and state.

```tree caption="shouldComponentUpdate and the custom comparison of memo answer opposite questions."
Two methods that look alike and answer opposite questions
- +`shouldComponentUpdate` | Asks **should I render again?** | Returns **`false` to skip**
- +`arePropsEqual` in `memo` | Asks **are the old and new props equal?** | Returns **`true` to skip**
```

### The List as a `memo` Component

Here is our list after the migration:

```jsx title="src/TaskList.jsx"
import { memo } from 'react';

const TaskList = ~memo~(function TaskList({ tasks, onRemove }) { // React compares tasks and onRemove before each render
  console.log('TaskList rendered');
  return (
    <ul>
      {tasks.map(task => (
        <li key={task}>
          {task} <button onClick={() => onRemove(task)}>Remove</button>
        </li>
      ))}
    </ul>
  );
});

export default TaskList;
```

A common migration mistake is to convert every class to a function and drop `PureComponent` without adding `memo`. Then the list renders after every keystroke again, and typing in a long list feels slow again. The `memo` wrapper is the line that carries the skip over from the class.

Like `shouldComponentUpdate`, `memo` only makes the page faster. It is not a guarantee: React may still render the component. React's docs say: "If your code doesn't work without it, find the underlying problem and fix it first." With React Compiler turned on, you usually do not write `memo` anymore, because the compiler adds the same skip for you (Lesson 63).

The parent becomes a function too, with `useState` for `tasks` and `text`. One prop of that new parent breaks the skip, and the next principle shows which one.

## PRINCIPLE | `useCallback`: `removeTask` stays the same function, so `memo` can skip again

> [!PRINCIPLE]
> **Principle 6: `useCallback` Keeps `removeTask` the Same After the Migration**
>
> *A function written inside a function component is created again on every render, unlike a class field arrow, so passing it to a `memo` component breaks the skip; `useCallback` keeps the same function, and `useMemo` keeps the same object or array.*
>
> A class instance lives across renders, so its class field `removeTask` stayed the same function. A function component runs again on every render, so a plain `removeTask` inside it is new every time, and `memo` sees a changed `onRemove` after every keystroke. `useCallback` gives back the same function, and an updater function lets it work with no dependencies.
>
> **DO THIS:**
> ```jsx
> const removeTask = ~useCallback~((task) => { // The same function on every render: memo skips
>   setTasks(tasks => tasks.filter(t => t !== task));
> }, []);
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ~removeTask~(task) { // **WRONG:** a new function on every render, so the memo list renders after every keystroke
>   setTasks(tasks.filter(t => t !== task));
> }
> ```

### VS | The Class Field `removeTask` vs. `function removeTask` Inside `TodoApp`: created once, or created on every render

When the team converts `TodoApp` line by line, the class field arrow becomes a plain function inside the component:

```jsx title="removeTask in the class and removeTask in the function component"
class TodoApp extends Component {
  ~removeTask~ = (task) => { // Created once, when React creates the instance
    this.setState({ tasks: this.state.tasks.filter(t => t !== task) });
  };
}

function TodoApp() {
  function ~removeTask~(task) { // Created again every time TodoApp renders
    setTasks(tasks.filter(t => t !== task));
  }
}
```

Both are named `removeTask`, and both remove the task the user clicked. **It may look the same, or work the same at first, but it is NOT the same thing!**
- **In the class**, React creates the instance once, and the instance lives across renders. Its class field `removeTask` is created once and stays the same function.
- **In the function component**, React calls the whole function `TodoApp` again on every render. Every function written inside it is created again, a new function each time.

### The `memo` List Renders on Every Keystroke

**Beware! After a line-by-line migration, `memo` sees a new `onRemove` on every render and never skips.** Here is the parent after the migration:

```jsx title="src/TodoApp.jsx" bad="13,14,15"
import { useState } from 'react';
import TaskList from './TaskList.jsx';

export default function TodoApp() {
  const [tasks, setTasks] = useState(['Buy milk', 'Call John']);
  const [text, setText] = useState('');

  function handleAdd() {
    setTasks([...tasks, text]);
    setText('');
  }

  function ~removeTask~(task) { // **WRONG:** a new function on every render of TodoApp
    setTasks(tasks.filter(t => t !== task));
  }

  return (
    <section>
      <h1>My tasks</h1>
      <label>New task <input value={text} onChange={e => setText(e.target.value)} /></label>
      <button onClick={handleAdd}>Add</button>
      <TaskList tasks={tasks} ~onRemove={removeTask}~ /> {/* memo sees a different onRemove every time */}
    </section>
  );
}
```

Here is what happens when the user types one letter:
1. The user types `P` in the field.
2. `setText` renders `TodoApp` again, and JavaScript creates `removeTask` again.
3. `memo` compares the new `onRemove` with the old one, and finds a different function.
4. `TaskList` renders again after every keystroke, as in Principle 3, though the JSX now has no arrow in it.

```page width=text caption="After the migration, the user types Pay, and the memo list still renders after each of the three keystrokes."
heading: My tasks
form:

  button: Add
line: Buy milk [Remove]

log: TaskList rendered | TaskList.jsx:4

log: TaskList rendered | TaskList.jsx:4
```

The class code never needed a fix here, because the class field was created once. The function code does. React's docs say: "When you need to pass a function to memoized component, either declare it outside your component so that it never changes, or `useCallback` to cache its definition between re-renders."

### The Fix: `useCallback` Keeps the Same `removeTask`

Wrap `removeTask` in `useCallback` (Lesson 57), and import `useCallback` from React:

```jsx title="src/TodoApp.jsx" startLine="13" good="1,2,3"
  const removeTask = ~useCallback~((task) => { // The same function on every render
    setTasks(tasks => tasks.filter(t => t !== task));
  }, ~[]~); // No dependencies: the function never needs to change
```

Where does `tasks` come from inside `setTasks(tasks => ...)`? This `tasks` is not the state variable of the component. It is the parameter of an updater function, and React supplies it, in three steps:
1. React calls the updater function with the pending state: the tasks as they are right now (Lesson 16).
2. `filter` returns a new array without the removed task.
3. Because the updater gets the tasks from React, `removeTask` does not read the state variable `tasks`. So its dependencies are an empty array, and it stays the same function on every render.

With `useCallback`, the same `removeTask` reaches `TaskList` on every render. For `memo`, it is the exact same thing as the class field: both props are the very same as last time, so it skips the list after every keystroke. The Console shows `TaskList rendered` once when the page opens, and again only when the tasks change.

`handleAdd` needs no `useCallback`. It goes to a `<button>`, not to a `memo` component, so a new function there breaks no skip.

### `useMemo` Does the Same for an Object or an Array

The same trap waits for an array built during the render. Suppose the list must show the tasks in alphabetical order:

```jsx title="A sorted array built on every render vs. kept with useMemo" bad="1" good="2"
const sortedTasks = ~[...tasks].sort()~; // **WRONG:** a new array on every render, so memo never skips
const sortedTasks = ~useMemo~(() => [...tasks].sort(), [tasks]); // The same array until tasks changes
```

`useMemo` does the job of `useCallback` for a value instead of a function (Lesson 56). It keeps the same sorted array until `tasks` changes. React's docs add that function components "also offer more granular optimization with `useMemo`". `shouldComponentUpdate` decides for the whole component at once, while `useMemo` can keep one calculation inside it.

Here is how each piece of the class code translates:

| In the class | In the function component | What it keeps the same |
| :--- | :--- | :--- |
| `extends PureComponent` | `memo` around the function | Skips when every prop is the same |
| A class field arrow, or a method bound once in the constructor | `useCallback` | The same function on every render |
| An object or array kept in state or on the instance | `useMemo` | The same object or array until its dependencies change |

React Compiler adds all of these for you: it "automatically memoizes values and functions, reducing the need for manual `useMemo` calls" (Lesson 63).

### How React Decides Whether to Render the List

On every render of `TodoApp`, React reaches the `TaskList` tag and compares its props with the old ones before it calls the list:

```tree dir=right caption="What React does at the TaskList tag on every render of TodoApp, after a keystroke and after Add."
React renders `TodoApp`, then reaches `<TaskList />`
- +1. `TodoApp` renders | A keystroke changes `text`, or Add changes `tasks` | Returns the field, the Add button, and `<TaskList />`
- +2. `memo` compares the props | `tasks` and `onRemove` against the old ones | **Same** after a keystroke; **different `tasks`** after Add
- +3. `TaskList` renders or is skipped | After a keystroke: **skipped**, the rows stay | After Add: **renders**, the new task appears
```

| Principle | Class code | Function code today | What breaks the skip |
| :--- | :--- | :--- | :--- |
| **1. `shouldComponentUpdate`** | Compare props by hand; return `false` to skip | No method: `memo` compares every prop for us | A prop the comparison forgets stays frozen on the screen |
| **2. `PureComponent`** | `extends PureComponent` compares every prop and state field | `memo` compares every prop | A context the component reads still renders it |
| **3. New every render** | An arrow, object, or array written in `render` | A function, object, or array written in the component body | The comparison finds a different reference every time |
| **4. `push`** | `push` into the array in state | `push` into the array in state | The same reference hides the new item |
| **5. `memo`** | `PureComponent` compares state too; `shouldComponentUpdate` returns `false` to skip | `memo` ignores state; `arePropsEqual` returns `true` to skip | Dropping `memo` during the migration, or copying the comparison without flipping it |
| **6. `useCallback`** | A class field arrow, created once | `useCallback` for functions, `useMemo` for objects and arrays | A plain function written inside the component |

Remember the one question of this lesson. **Before React renders a component that skips, it asks about every prop: "is it the very same value as last time?" A new function or a new array always says no, and an array changed with `push` always says yes.**

## For the Interview

> **The Interview Question:** How did PureComponent and shouldComponentUpdate prevent re-renders, and what replaced them?

### How to Answer Clearly in 30 Seconds

"When a parent re-renders, React re-renders its children too. In class components, a child could opt out in two ways. First, it could define `shouldComponentUpdate`, which React calls before each re-render with the next props and state; returning `false` skips `render`. Second, it could extend `PureComponent`, which is the same as a `shouldComponentUpdate` that shallowly compares every prop and state field. Shallow means that a string or a number compares by value, and an object, an array, or a function compares by reference. That buys fewer renders, but it misses two things:
1. **A new reference on every render defeats it**: an arrow or an array written in the parent's `render` always counts as changed.
2. **Mutation hides changes**: `push` keeps the same array, so the screen keeps showing the old list.

Today, `memo` replaces `PureComponent` for function components. It compares props only, and `useCallback` and `useMemo` keep function, object, and array props the same between renders. React Compiler can add all of this automatically."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Is `memo` exactly the same as `PureComponent`?"**
   For props, yes: both compare each prop with its old value and skip when all are the same. For state, no. `PureComponent` also compares every state field, while `memo` compares props only, because a function component already skips a re-render when its `set` function receives the same value. And a custom comparison in `memo` answers the opposite question from `shouldComponentUpdate`: it returns `true` when the props are equal, which skips, while `shouldComponentUpdate` returns `false` to skip.
2. **"The user adds a task, the field empties, but the list does not show the new task. The list is a `PureComponent`. Why?"**
   The handler probably called `push` on the array in state and passed the same array to `setState`. `PureComponent` compares the array by reference, finds the very same array, and skips the list. The fix is to pass a new array, such as `[...this.state.tasks, this.state.text]`. The mutation was always wrong; `PureComponent` only made it visible.
3. **"We migrated a `PureComponent` list to a function with `memo`, and it still re-renders after every keystroke. Why?"**
   A prop is new on every render. In the class, the handler was a class field arrow, created once with the instance. In the function component, a function written in the body is created again on every render, so `memo` sees a changed prop every time. Wrap the function in `useCallback`, and wrap an object or array prop in `useMemo`. Keep in mind that both `shouldComponentUpdate` and `memo` only make the page faster: React may still render the component.
