# Lecture 87: How a Test Clicks Follow the Way a User Does

*(How do you check in code that a button still works after every change?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | How do you test React components the way a reader uses them?

---

## VS | Calling the Reducer vs. Clicking the Button: both tests pass today, only the click test notices a broken button

> You already know how to check a button by hand: you open the page, click `Follow`, and look whether it now reads `Following`. **A component test does exactly that in code: it puts the component on a page, clicks the button, and reads the word the user sees**. It never reads the state or the reducer, because the user never sees them, so it fails only when the user would see something wrong.

An app changes all the time: a new style, a new way to keep state, a quick fix by a teammate. After every change, someone has to make sure the buttons still work. Nobody wants to open the app and click every button by hand after every save. So we write a **test**: a small program that runs our code and checks one result.

Take the simplest case. A function `add` adds two numbers, so `add(2, 3)` must return 5. Here is the test:

```js title="The smallest test"
expect(~add(2, 3)~).toBe(5); // Passes when add returns 5, fails when it returns anything else
```

> [!DEFINITION]
> **What is a test?** [NEW] A test is a small program that runs your code and checks one result.
> `expect(add(2, 3)).toBe(5)` reads like a sentence: "I expect `add(2, 3)` to be 5." `expect` takes what really happened. `toBe` takes what you wanted.
> When the two match, the test **passes**. When they differ, the test **fails**, and the terminal prints both values.
> The team runs its tests after every change, so a broken button shows up in the terminal before a user ever meets it (Lesson 87).

### The Follow button on a profile card

Open a profile on a social app such as X or Instagram. The card shows a name, `John`, and a `Follow` button:

```page width=text caption="John's profile card when the page opens: the button reads Follow."
heading: John
line: [Follow]
```

The user clicks `Follow`. The button now reads `Following`:

```page width=text caption="The same card after the user clicks Follow: the button reads Following."
heading: John
line: [Following] | good
```

That is the whole feature: one click, and one word that changes. This is what we want to test.

### Back to plain JavaScript: grab, click, read

Remember how you check a button in plain JavaScript, in the browser Console? You grab the button, click it from code, and read the word on it:

```js title="Plain JavaScript in the Console"
const button = ~document.querySelector('button')~; // Grab the button
button.click(); // Click it from code, as if the user did
console.log(button.textContent); // Read the word on it, and look at it with your own eyes
```

A component test does the same three things. Only the names change:

```jsx title="A component test of the Follow button"
render(<FollowCard />); // 1. Put the card on a page
const button = ~screen.getByRole('button', { name: 'Follow' })~; // 2. Grab the button that reads Follow
~fireEvent.click(button)~; // 3. Click it
expect(button.textContent).toBe('Following'); // 4. Check the word in code, instead of reading it by eye
```

Line by line:
1. **`render`** is new. In the Console, the page is already open in the browser. A test runs in the terminal, with no browser and no page, so it must first put the component on a page itself.
2. **`getByRole`** takes the place of `querySelector`. It grabs the button the way a user meets it: a button, with the word `Follow` on it.
3. **`fireEvent.click`** takes the place of `button.click()`. It sends a real click event to the button.
4. **`expect`** takes the place of your eyes. If the word is not `Following`, the test fails.

These four lines are the click test. The whole lesson builds them one at a time.

### VS | The Reducer Test vs. the Click Test: one runs a function inside our code, the other does what the user does

Our card keeps its state with a reducer:

> [!DEFINITION]
> **What is a reducer?** [REVIEW] A reducer is a plain function that takes the current value and an action, and returns the next value.
> Our card's reducer is `followReducer`. While the user does not follow John, the value is `false`. `followReducer(false, { type: 'follow' })` returns `true`.
> The component never changes the value itself. A click calls `dispatch` with an action, and React hands that action to the reducer (Lesson 27).

So there is a second way to test that following works. Skip the button, and call the reducer directly:

```jsx title="The reducer test"
expect(~followReducer(false, { type: 'follow' })~).toBe(true); // Passes: the reducer returns true
```

On the working card, the reducer test and the click test both pass. A developer who sees two green ticks believes both check the same job: "the Follow button works".

It may look the same, but it is NOT the same thing! The reducer test runs one function inside our code. The click test does what the user does: it finds the button by its word, clicks it, and reads the new word.

Now suppose a teammate breaks the button, so that a click sends the wrong action. The reducer itself is still right, so the reducer test still passes. The user clicks `Follow` and nothing happens, so the click test fails. **Only the click test notices what the user notices.**

```tree caption="Two tests for the same Follow button: one calls the reducer, one clicks the button the way the user does."
Two tests for the same Follow button
- !The reducer test [`followReducer` `toBe`] | Runs **one function** inside our code | Still passes when the **button sends the wrong action**
- +The click test [`render` `getByRole` `fireEvent.click`] | Finds, clicks, and reads the button **as the user does** | Fails exactly when **the user sees no change**
```

### The Rule of Thumb: does the user see it?

**Test what the user does, and check what the user sees. Never check the state, the reducer, or a class name, because no user ever sees them.**

What is at stake is a set of tests that is wrong in both directions:
1. A teammate copies the wrong action into the button's `onClick`. The user clicks `Follow`, and the button still reads `Follow`.
2. The reducer test passes, so the bug ships.
3. Later, the team turns `useReducer` into `useState` to make the card simpler. The card works exactly as before. Now the reducer test fails, because `followReducer` is gone.

So the reducer test passes when the button is broken, and fails when nothing is broken.

A senior developer also knows the three classic mistakes:
1. **Testing only the parts you wrote**, such as the reducer, and assuming the button uses them correctly.
2. **Grabbing elements by a class name**, such as `follow-btn`, which no user can see.
3. **Believing that a test that reads state is more exact.** The state is only one way the code reaches the screen. The user never sees it.

### Three kinds of tests you will meet at work

1. **A component test with React Testing Library.** It puts the component on a page, clicks it, and reads the page. This is the click test, and this lesson builds it. react.dev recommends this library and says that "generally it's best to test components in a more realistic environment". MDN calls these tests **unit tests** for React components.
2. **A reducer test on its own.** react.dev says that "for complex state update logic it can be useful to assert that your reducer returns a particular state for a particular initial state and action". It fits a reducer with many actions. It adds to the component test, and never replaces it. Our reducer has only two simple actions, so our card does not need one.
3. **An end-to-end test in a full browser.** It runs the whole app in a real browser and follows a user across several pages. react.dev names it "continuous end-to-end testing of your app". This lesson only names it.

## SECTION | A Profile Card with a Follow Button

The whole lesson tests one card. Our project is a Vite app (Lesson 07). Besides React and Vite, it installs three packages for tests: `vitest`, `jsdom`, and React Testing Library. Principle 1 gives each one its job. The test file sits next to the card it tests:

```files title="profile-card: File Explorer" caption="The files of the profile card project, with the test file next to the card it tests."
index.html | entry | The HTML page with the empty root div where React mounts
package.json | scripts | Holds the `"test": "vitest"` script that runs every test file
vite.config.js | config | Names `jsdom` as the test environment
src/
  main.jsx | boundary | Mounts `<App />` into `#root`, unchanged from the Vite template
  App.jsx | parent | Renders `<FollowCard />`
  FollowCard.jsx | default export | Exports `FollowCard` as default and `followReducer` by name
  FollowCard.test.jsx | test | Imports `FollowCard` and checks what the user sees
```

The card starts with `useReducer`. The class `follow-btn` gives the button its style:

```jsx title="src/FollowCard.jsx"
import { useReducer } from 'react';

export function ~followReducer~(following, action) { // Exported by name, so a test file can import it
  switch (action.type) {
    case 'follow':
      return true;
    case 'unfollow':
      return false;
    default:
      return following;
  }
}

export default function FollowCard() {
  const [following, dispatch] = useReducer(followReducer, false);
  return (
    <section>
      <h2>John</h2>
      <button className="follow-btn" onClick={() => dispatch({ type: ~following ? 'unfollow' : 'follow'~ })}> {/* The first click sends follow */}
        {following ? 'Following' : 'Follow'}
      </button>
    </section>
  );
}
```

Now let's test it, and break it. Each principle adds one line of the click test, or shows what goes wrong without it:

**PRINCIPLES:** A good component test goes where the user goes: onto the page, to the button with its word, through the click, and to the new word. Five principles follow:
1. **Principle 1: `render` puts the component on a page in memory.** A test runs in Node, not in a browser tab. jsdom gives it a `document`, and `render` puts the card on it.
2. **Principle 2: `getByRole` finds a real button by its word.** A class name is invisible to users, and it keeps finding the element after the element stops being a real button.
3. **Principle 3: `fireEvent.click` clicks, and the next line reads the new word.** The test checks the word on the button, never the state.
4. **Principle 4: A reducer test checks the reducer, never the button.** When the button sends the wrong action, the reducer test still passes.
5. **Principle 5: The click test survives a refactor.** After `useReducer` becomes `useState`, the click test passes unchanged, and the reducer test fails though nothing is broken.

## PRINCIPLE | `render`: the component appears on a page in memory, and no browser opens

> [!PRINCIPLE]
> **Principle 1: The Test Page: `render` Puts the Component on a Page in Memory**
>
> *Put the component on the page of the test with `render` from React Testing Library, then check one thing the user would see.*
>
> A test runs in the terminal, in Node, and no browser opens. jsdom gives the test a `document` that lives only in memory, and `render` puts one component on it. Nothing else of the app runs, so a test without `render` looks at an empty page and finds no button.
>
> **DO THIS:**
> ```jsx
> it('shows Follow at first', () => {
>   ~render(<FollowCard />)~; // The card is now on the page of the test
>   expect(screen.getByRole('button').textContent).toBe('Follow');
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> it('shows Follow at first', () => {
>   expect(~screen.getByRole('button')~.textContent).toBe('Follow'); // **WRONG:** no render, so the page is empty and no button is found
> });
> ```

### The shortest test that passes

Here is the shortest test of our card. It checks one thing the user sees when the card appears: the button reads `Follow`.

```jsx title="src/FollowCard.test.jsx"
import { expect, it } from 'vitest';
import { render, screen } from '@testing-library/react';
import FollowCard from './FollowCard';

~it~('shows Follow at first', () => { // One test: its name, then its code
  ~render(<FollowCard />)~; // Puts the card on the page of the test
  expect(screen.getByRole('button').textContent).toBe('Follow'); // The one button reads Follow
});
```

The new names come from two packages:
1. **`it`, `expect`, and `toBe` come from Vitest.** `it` gives one test its name, here `shows Follow at first`, and holds its code.
2. **`render` and `screen` come from React Testing Library**, whose package name you see on the second import line. `render` puts a component on a page. `screen` is the object you ask when you look for an element on that page.

> [!DEFINITION]
> **What is a testing framework?** [NEW] A testing framework is the tool that finds your test files and runs them. Vitest is one.
> MDN says that "the testing framework Vitest is built on top of Vite", so it reads the same config as our Vite app. Jest is the other testing framework that MDN names.
> Vitest finds a test file by its ending, `.test.jsx`. The file sits next to `FollowCard.jsx`, as in MDN's example (Lesson 87).

### Where the page comes from: jsdom

The card in the test is the same `FollowCard` as in the app: the same file and the same function. The page it sits on is not the same.

It may look the same, but it is NOT the same thing! In the app, the browser draws the card in a tab, and the user sees it. In the test, nothing is drawn on any screen. The page lives only in memory, and the test reads it.

Why do we need a page at all? Remember where `document` comes from in the Console: the browser gives it to you. Vitest runs the test file in Node, which is JavaScript without a browser. In Node, there is no `window` and no `document` at all.

So the project names **jsdom** as its **test environment** in the Vite config:

```js title="vite.config.js"
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: { ~environment: 'jsdom'~ }, // Gives every test a page document inside Node
});
```

> [!DEFINITION]
> **What is jsdom?** [NEW] jsdom is a package that builds a fake browser page inside Node: a `document` with a `body`, elements, and events, but no screen.
> Your test can grab elements, click them, and read their text, exactly as in the browser Console.
> Vitest reads `environment: 'jsdom'` from the Vite config by itself, and gives every test that `document` before the test runs. The example projects on react.dev name jsdom too, in their test script `react-scripts test --env=jsdom` (Lesson 87).

When you run `npm run test`, four things happen in order:
1. Vitest finds `FollowCard.test.jsx` and runs it in Node.
2. jsdom supplies the `document`.
3. `render(<FollowCard />)` puts the card on that page: the section, the heading John, and the button.
4. `screen.getByRole('button')` finds the button on that page, and the test reads its `textContent`.

Nothing else of the app runs. `main.jsx` and `App.jsx` never load. The page of the test holds only the one component that `render` put there.

```tree dir=right caption="Where the card lives during a test: Vitest runs the file in Node, jsdom gives it a page, and render puts the card on that page."
How `FollowCard` reaches the page of the test
- +1. Vitest [`npm run test`] | Finds `FollowCard.test.jsx` | Runs it in **Node**, with **no browser**
- +2. jsdom [`environment: 'jsdom'`] | Gives the test a **page `document`** | The page lives **only in memory**
- +3. React Testing Library [`render`] | Puts **`FollowCard`** on that page | The test can now **find and click** it
```

### Why `render`, and not a `<div>` we build ourselves

Without a library, the test code on react.dev builds the page by hand. It creates a `<div>`, adds it to `document.body`, and renders the component into it.

react.dev warns about the step that is easy to forget: "dispatching DOM events only works when the DOM container is added to the document". Skip that step, and the click does nothing. The test fails while the card works fine in the browser.

react.dev then adds: "You can use a library like React Testing Library to reduce the boilerplate code". `render` does those steps for us, and it adds the card to the page.

The developer who expects the test to open the app makes the opposite mistake: no `render` at all. Nothing of the app runs by itself, so the page of the test is empty. `getByRole` finds no button, and the test fails before it checks anything.

## PRINCIPLE | `getByRole('button', { name: 'Follow' })`: the test finds only a real button with the word Follow

> [!PRINCIPLE]
> **Principle 2: Role and Name: Find Elements the Way a User Does**
>
> *Find an element with `getByRole` and its accessible name, such as `screen.getByRole('button', { name: 'Follow' })`, never by a class name.*
>
> A user meets a button and the word on it. A class name is invisible to every user, so a test that grabs the element by its class keeps passing after the element stops being a real button. `getByRole` looks for the role and the name that a screen reader announces. It fails when the control is a `<div>`, or when a button has no name: the same two problems that a keyboard user or a screen reader user meets.
>
> **DO THIS:**
> ```jsx
> const button = ~screen.getByRole('button', { name: 'Follow' })~; // Fails if the element is not a real button named Follow
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const button = ~document.querySelector('.follow-btn')~; // **WRONG:** still finds the element after it becomes a div that no keyboard user can press
> ```

### Two ways to grab the same button

The test must grab the button before it can click it. Here are two ways to do it:

```jsx title="Grabbing the button by its class, and by its role and name"
document.querySelector(~'.follow-btn'~); // 1. By the class name in our JSX
screen.getByRole(~'button', { name: 'Follow' }~); // 2. By what the user meets: a button with the word Follow
```

The first line is the `querySelector` you know from plain JavaScript (Lesson 13). It looks for the class `follow-btn`. Only the developer sees that class, in the code.

The second line looks for what the user meets: a **role**, here a button, and a **name**, here the word `Follow`.

On our card, both lines return the same `<button>`. It may look the same, but it is NOT the same thing! **The way a test grabs an element is part of what the test checks**. `getByRole` also checks that the element is a real button, and that its name is `Follow`. `querySelector` checks neither.

### Role and accessible name: what a screen reader says out loud

Both words come from MDN's pages on accessibility:
1. **A role says what kind of thing an element is.** MDN asks: "What kind of thing is it? For example, is it a button, a nav bar, or a list of items?" A `<button>` has the button role by itself, so our JSX never writes `role="button"`. A `<div>` has no such role.
2. **An accessible name is the word that labels the element.** In MDN's words, it is "the text associated with an HTML element that provides users of assistive technology with a label for the element". A `<button>` gets its name from its content. Our button's content is the word `Follow`, so its accessible name is `Follow`.

The browser builds the **accessibility tree** from the DOM, and every object in that tree has a role and a name. A screen reader says both out loud to its user (Lesson 52). `getByRole` looks for that same role and that same name. So the test finds the button the way a screen reader user meets it.

```tree caption="Two ways to grab the Follow button: by the class only the developer sees, or by the role and name the user meets."
Two ways to grab the Follow button
- !By class name [`querySelector` `'.follow-btn'`] | Looks for a **class in our JSX** | No user ever **sees a class**
- +By role and name [`getByRole` `'button'` `name: 'Follow'`] | Looks for **a button with the word Follow** | The same two things a **screen reader announces**
```

**The test with the class passes, and the test with the role fails, as it should.** Here is what each user and each test meets on the card with the `<div>`:
1. A mouse user clicks it, and it still turns into `Following`.
2. The test with the class grabs the `<div>`, clicks it, reads Following, and passes.
3. A keyboard user cannot reach it with the Tab key or press it with Enter. MDN explains that an element used as a button must be made "focusable", with handlers for the Enter and Space keys. A plain `<div>` has none of this.
4. A screen reader does not announce a button, because the `<div>` has no `button` role.
5. The test with `getByRole` finds no button named `Follow`, and it fails:

```text title="Terminal: the test with getByRole on the card with a div"
TestingLibraryElementError: Unable to find an accessible element with the role "button" and name "Follow"
```

### An icon button with no name

`getByRole` catches a second real mistake: a button with no name. A developer builds an icon-only Follow button, with a plus sign picture and no text:

```jsx title="An icon button with no text"
~<button>~ {/* **WRONG:** no text, so the button has no accessible name */}
  <img src="/plus.svg" alt="" />
</button>
```

The test looks for the button named `Follow`, and it fails. MDN says: "Buttons should always have an accessible name." A screen reader user meets a button and hears no word for what it does.

MDN gives the fix for a button with "no visible text": the `aria-label` attribute (Lesson 83):

```jsx title="An icon button with aria-label"
<button ~aria-label="Follow"~> {/* The accessible name is now Follow */}
  <img src="/plus.svg" alt="" />
</button>
```

Now the test passes, and a screen reader user hears `Follow` too. **The test and the screen reader needed the same fix.**

## PRINCIPLE | `fireEvent.click`: a real click event, and the very next line already reads `Following`

> [!PRINCIPLE]
> **Principle 3: Arrange, Act, Assert: Click, Then Read the Screen**
>
> *Act as the user does with `fireEvent.click(button)`, then assert on what the user now sees, such as `button.textContent`.*
>
> `fireEvent.click` sends a real click event to the button, so our `onClick` runs as it does for a user. The helpers of React Testing Library are wrapped with `act()`, so the page is already updated on the next line. The test checks the word on the button. The state is only one way the code gets there, and the user never sees it.
>
> **DO THIS:**
> ```jsx
> fireEvent.click(button);
> expect(~button.textContent~).toBe('Following'); // Checks the word the user sees
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const card = ~ReactTestRenderer.create(<FollowCard />)~; // **WRONG:** deprecated in React 19, and it reads React's insides instead of the page
> ```

### Arrange, act, assert

The test of Principle 1 checks the card before any click. Now the test clicks:

```jsx title="src/FollowCard.test.jsx"
import { expect, it } from 'vitest';
import { render, screen, fireEvent } from '@testing-library/react';
import FollowCard from './FollowCard';

it('shows Following after a click on Follow', () => {
  render(<FollowCard />); // Arrange: the card is on the page
  const button = screen.getByRole('button', { name: 'Follow' }); // Arrange: the button that reads Follow
  ~fireEvent.click(button)~; // Act: the click of the user
  expect(~button.textContent~).toBe('Following'); // Assert: the word the user now sees
});
```

This test takes the place of the test of Principle 1, because it already checks the start. If the button did not read `Follow` at first, `getByRole` would find no such button, and the test would fail on that line.

`fireEvent.click` comes from React Testing Library. It sends a click to an element on the page of the test. react.dev says that "`fireEvent` dispatches an actual event on the element and doesn't just synthetically call the event handler". So the click reaches the button the way the click of a user does, and our `onClick` receives it.

The three parts of the test have names. react.dev names the pattern **Arrange-Act-Assert** when it explains where the name of `act` comes from:
1. **Arrange**: `render` and `getByRole` set up the page and grab the button.
2. **Act**: `fireEvent.click` does what the user does.
3. **Assert**: `expect` checks what the user now sees. react.dev calls such a check an **assertion**.

```tree dir=right caption="The three parts of the click test: arrange the page, act as the user, assert what the user sees."
The click test in three parts
- +Arrange [`render` `getByRole`] | Puts the card on the page | Grabs the **button named Follow**
- +Act [`fireEvent.click`] | Sends **a real click event** to the button | Our `onClick` runs
- +Assert [`expect` `toBe`] | Reads **`button.textContent`** | Passes only when the user would see **Following**
```

### Why the next line already reads Following

The test reads `Following` on the very next line after the click, with no waiting. Why? Because the click, the new render, and the update of the page all finish before `fireEvent.click` returns:
1. `fireEvent.click(button)` sends a click event to the `<button>` on the page of the test.
2. Our `onClick` runs and calls `dispatch` with the follow action. `followReducer` returns `true`.
3. react.dev says that the helpers of React Testing Library "are wrapped with `act()`". So React renders `FollowCard` again and updates the page before `fireEvent.click` returns. Lesson 88 explains `act`.
4. In the new render, the ternary picks `Following`. React keeps the same `<button>` element and changes only its text (Lesson 77).
5. `button` still points at that element, so the next line reads its text and gets `Following`.

Step 4 has one more result. After the click, the accessible name of the button is `Following`. A new search for the button named `Follow` would find nothing. That is why the test keeps the button it grabbed before the click, in the variable `button`.

### Check the word, not the state

The test checks the word `Following` on the button. It does not check the value `true` inside the card.

A developer new to tests often asks how to read `following` from inside `FollowCard`. react.dev shows no way for a test to read the state of a component.

The old tools that read the insides of React are removed or deprecated in React 19. One of them, `react-test-renderer`, is deprecated, and React prints a warning whenever a test calls `ReactTestRenderer.create()`. react.dev gives the reason: it "doesn't match the environment users use".

There is a simpler reason too. The user never sees `true`. The user sees `Following`. So the test checks `Following`.

---

## PRINCIPLE | `followReducer` in a test: it checks the reducer, never the button

> [!PRINCIPLE]
> **Principle 4: Implementation Details: A Reducer Test Misses a Broken Button**
>
> *Test the component through the page with a click; a test that calls the reducer checks only the reducer.*
>
> The reducer and its actions are implementation details: the user never sees them. A test that calls `followReducer` passes even when the button sends the wrong action, because it never goes through `onClick`. The click test goes through the button, the action, and the reducer, so it fails exactly when the user clicks `Follow` and nothing happens.
>
> **DO THIS:**
> ```jsx
> render(<FollowCard />);
> const button = screen.getByRole('button', { name: 'Follow' });
> ~fireEvent.click(button)~; // Goes through onClick, the action, and the reducer
> expect(button.textContent).toBe('Following');
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> expect(~followReducer(false, { type: 'follow' })~).toBe(true); // **WRONG:** as the only test, it passes while the button sends unfollow
> ```

### Both tests in one file

Now the test file holds both tests from the start of the lecture:

```jsx title="src/FollowCard.test.jsx"
import { expect, it } from 'vitest';
import { render, screen, fireEvent } from '@testing-library/react';
import FollowCard, { ~followReducer~ } from './FollowCard'; // The default export and the named export

it('returns true for the follow action', () => {
  expect(~followReducer(false, { type: 'follow' })~).toBe(true); // Calls the reducer directly
});

it('shows Following after a click on Follow', () => {
  render(<FollowCard />);
  const button = screen.getByRole('button', { name: 'Follow' });
  ~fireEvent.click(button)~; // Goes through the onClick of the button
  expect(button.textContent).toBe('Following');
});
```

`followReducer` reaches the test file because the card file exports it by name, next to the default export (Lesson 05). The card itself never needed that export. It exists only so that this test can import the reducer.

On the working card, both tests pass.

### The wrong action in `onClick`

**Beware! When the button sends the wrong action, the reducer test still passes. Only the click test fails.**

A teammate copies the code of an Unfollow button into our button:

```jsx title="src/FollowCard.jsx" startLine="19"
      <button className="follow-btn" onClick={() => dispatch({ type: ~'unfollow'~ })}> {/* **WRONG:** every click sends unfollow */}
```

The user clicks `Follow`, and the button still reads `Follow`:

```page width=text caption="The card with the wrong action, after the user clicks Follow: the button still reads Follow."
heading: John
line: [Follow] | bad
```

Here is what each test does with this card:
1. The reducer test calls `followReducer` itself, with the follow action, and gets `true`. It passes. It never goes near the button.
2. The click test clicks the button. The button sends `unfollow`, so the reducer returns `false`.
3. The click test reads `Follow` where it wanted `Following`. It fails.

```text title="Terminal: npm run test on the card with the wrong action"
 ❯ src/FollowCard.test.jsx (2 tests | 1 failed) 24ms
   ✓ returns true for the follow action 1ms
   × shows Following after a click on Follow 23ms

 FAIL  src/FollowCard.test.jsx > shows Following after a click on Follow
AssertionError: expected 'Follow' to be 'Following' // Object.is equality

Expected: "Following"
Received: "Follow"

 Test Files  1 failed (1)
      Tests  1 failed | 1 passed (2)
```

On the working card, the two tests passed together, as if they checked the same thing. On the broken card, they split.

The reducer test proves that `followReducer` is right. It says nothing about which action the button sends. The user needs both pieces to be right, and only the click test goes through both.

```tree caption="On the card with the wrong action, the reducer test still passes and the click test fails."
The two tests on the card with the wrong action
- !The reducer test [`followReducer` `type: 'follow'`] | Calls the reducer with **the right action itself** | **Passes**: the button is never touched
- +The click test [`fireEvent.click`] | Clicks the button, which **sends unfollow** | **Fails**: the button still reads **Follow**
```

### Implementation details

> [!DEFINITION]
> **What is an implementation detail?** [NEW] An implementation detail is a part of your code that decides how the component works inside, and that the user never sees.
> On our card, the reducer and its actions are implementation details. The user sees only the button and its word.
> react.dev uses the phrase to explain why `react-test-renderer` is deprecated: it "promotes testing implementation details" (Lesson 87).

A test of an implementation detail proves that one part is right. It cannot prove that the parts work together for the user. Here the reducer is right and the `onClick` is wrong, so the user gets nothing.

This is how the bug from the start of the lecture ships:
1. The team reads on react.dev that a reducer is a pure function that you can "export and test separately in isolation".
2. The team writes reducer tests only, and never a test that clicks.
3. A teammate sends the wrong action from the button.
4. Every test passes, and the bug ships.
5. A user reports that `Follow` does nothing.

react.dev itself puts a limit on reducer tests: "generally it's best to test components in a more realistic environment". A reducer test is useful "for complex state update logic". It adds to the click test. It never replaces it.

## PRINCIPLE | The click test: it still passes after `useReducer` becomes `useState`

> [!PRINCIPLE]
> **Principle 5: Refactors: A Test of the Screen Survives a Change of Code**
>
> *Write tests that fail only when the user would see something different, so a refactor that keeps the screen the same keeps every test passing.*
>
> Changing `useReducer` to `useState` is a refactor: the card shows `Follow`, then `Following`, as before. The click test reads only the page, so it passes unchanged. A test tied to `followReducer` fails, though nothing is broken. Rewriting that test to match the new code makes the tests follow the code instead of the user.
>
> **DO THIS:**
> ```jsx
> fireEvent.click(button);
> expect(~button.textContent~).toBe('Following'); // Passes with useReducer and with useState
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import { ~followReducer~ } from './FollowCard'; // **WRONG:** ties the test to one way of keeping state; it fails after the refactor to useState
> ```

### The same card with `useReducer` and with `useState`

Weeks later, a teammate decides that a reducer is too much for one value that is only true or false. The teammate rewrites the card with `useState` (Lesson 12).

> [!DEFINITION]
> **What is a refactor?** [NEW] A refactor is a change to how the code is written that does not change what it does.
> The user sees the same page before and after. Only the code inside is different.
> react.dev says that "refactoring state is a part of the process" (Lesson 87).

Only two lines change: the line that keeps `following`, and the `onClick`. Here is the first one, before and after:

```jsx title="The line that keeps following: with useReducer and with useState"
const [following, dispatch] = ~useReducer(followReducer, false)~; // Before: the click sends an action to followReducer
const [following, setFollowing] = ~useState(false)~; // After: the click sets the next value itself
```

Here is the whole card after the refactor:

```jsx title="src/FollowCard.jsx"
import { useState } from 'react';

export default function FollowCard() {
  const [following, setFollowing] = ~useState(false)~; // followReducer is gone
  return (
    <section>
      <h2>John</h2>
      <button className="follow-btn" onClick={() => ~setFollowing(!following)~}> {/* Flips false to true, and true to false */}
        {following ? 'Following' : 'Follow'}
      </button>
    </section>
  );
}
```

For the user, yes, it is the exact same thing! react.dev says that you can "convert between `useState` and `useReducer` back and forth: they are equivalent!" The card shows `Follow`, and after a click it shows `Following`, as before.

For the tests, the two versions are NOT the same thing:
1. **The click test passes without a single changed line.** It reads only the page, and the page did not change.
2. **The reducer test fails.** It imports `followReducer`, and the card file no longer has one.

```tree caption="After the refactor from useReducer to useState, the user sees the same card, the click test passes, and the reducer test fails."
The card after `useReducer` becomes `useState`
- +The user [`Follow` `Following`] | Sees **the same card** | The click works **as before**
- +The click test [`getByRole` `fireEvent.click`] | Reads **only the page** | **Passes** with no line changed
- !The reducer test [`followReducer`] | Reads **a name inside our file** | **Fails**, though **nothing is broken**
```

### The rewrite that hides the next bug

A test that fails after a safe change does not stop at one red line in the terminal. It pushes the team to change the tests, and that is where the next bug gets in:
1. The team's tests read the inside of the component, such as its reducer.
2. A teammate swaps `useReducer` for `useState` to make the card simpler.
3. The card works, and the reducer tests fail.
4. The teammate rewrites the tests to match the new code, so the tests now follow whatever the code does.
5. The tests no longer say what the user needs, and the next real bug passes.

**A good component test fails only when the user would see something different.** When the screen did not change, the test does not change either. The same holds when the team splits the card into two components, or renames `following`: the page is the same, so the click test is the same.

## All 5 Principles Together

### The complete project

The project needs two config files, the card, and its test. `package.json` starts Vitest:

```json title="package.json"
{
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "test": "vitest"
  }
}
```

`vite.config.js` gives every test a page:

```js title="vite.config.js"
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  test: { ~environment: 'jsdom'~ }, // Principle 1: jsdom gives every test a page document
});
```

The card, after the refactor of Principle 5:

```jsx title="src/FollowCard.jsx"
import { useState } from 'react';

export default function ~FollowCard~() { // React calls FollowCard once for render, and again after the click
  const [following, setFollowing] = useState(false);
  return (
    <section>
      <h2>John</h2>
      <button className="follow-btn" onClick={() => setFollowing(!following)}>
        {following ? 'Following' : 'Follow'}
      </button>
    </section>
  );
}
```

The test, which passed on both versions of the card:

```jsx title="src/FollowCard.test.jsx"
import { expect, it } from 'vitest';
import { render, screen, fireEvent } from '@testing-library/react';
import FollowCard from './FollowCard';

it('shows Following after a click on Follow', () => {
  ~render(<FollowCard />)~; // Principle 1: puts the card on the page of the test
  const button = ~screen.getByRole('button', { name: 'Follow' })~; // Principle 2: grabs a real button named Follow
  ~fireEvent.click(button)~; // Principle 3: a real click; the page updates before the next line
  expect(~button.textContent~).toBe('Following'); // Principles 4 and 5: checks the word the user sees
});
```

### What happens in one test run, in order

When you run `npm run test`, Vitest runs the file, and React calls `FollowCard` twice: once for render, and once after the click.

```tree dir=right caption="The order of one test run: from npm run test to the word Following on the button."
One run of `npm run test`
- +1. Vitest [`npm run test`] | Finds `FollowCard.test.jsx` | Runs it in **Node**
- +2. jsdom [`environment: 'jsdom'`] | Gives the test **a page `document`**
- +3. `render` [`FollowCard`] | React **calls `FollowCard` the first time** | The button reads **Follow**
- +4. `getByRole` [`'button'` `name: 'Follow'`] | Finds **a real button** named **Follow**
- +5. `fireEvent.click` [`setFollowing`] | `onClick` runs | React **calls `FollowCard` again** and updates the text
- +6. `expect` [`button.textContent`] | Reads **Following** | The test **passes**
```

| Aspect | A Test Tied to the Code | A Test of What the User Sees |
| :--- | :--- | :--- |
| **Where it looks** | Expects the app to be open, and looks at an empty page when nothing was rendered | Runs in Node; jsdom gives it a page, and `render` puts the card on it |
| **How it grabs the button** | By a class such as `follow-btn`, which keeps passing after the button becomes a `<div>` | By role and name with `getByRole('button', { name: 'Follow' })` |
| **What it checks** | The state or the reducer, which the user never sees | The word on the button after `fireEvent.click`, `Following` |
| **The broken button** | Passes while the button sends `unfollow` | Fails, because the button still reads `Follow` |
| **The refactor to `useState`** | Fails, because `followReducer` is gone | Passes, because the page did not change |

Remember the one sentence of this lesson. **A component test does what the user does and checks what the user sees, so it fails only when the user would see something wrong.**

## For the Interview

> **The Interview Question:** How do you test React components the way a reader uses them?

### How to Answer Clearly in 30 Seconds

"A component test does what the user does and checks what the user sees. It runs in Node through a testing framework such as Vitest or Jest. jsdom gives it a page document, and `render` from React Testing Library puts the component on that page. Then the test works in three steps:
1. **Arrange**: render the component and find the element the way a user does, with `getByRole` and the accessible name, such as the button named `Follow`.
2. **Act**: click it with `fireEvent.click`, which sends a real click event. The helpers of React Testing Library are wrapped with `act()`, so the page is already updated on the next line.
3. **Assert**: check what the user now sees, such as the text `Following`.

I do not assert on state, reducers, or class names. Those are implementation details. A test tied to them fails on a safe refactor, such as `useReducer` to `useState`. And it passes on a real bug, such as a button that sends the wrong action."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why not test the reducer, or the state, directly? Isn't that more exact?"**
   No. A reducer test proves that the reducer is right, and nothing more. If the button sends the wrong action, the reducer test still passes, while the user clicks `Follow` and nothing happens. The state is only one way the code reaches the screen. react.dev says that a reducer test is useful "for complex state update logic", and that "generally it's best to test components in a more realistic environment". So a reducer test can add to a component test, and it never replaces it.
2. **"Why find elements by role and name instead of a class?"**
   A user never sees a class. A teammate may turn the `<button>` into a `<div>` with the same class. A test that finds the button by its class keeps passing, although a keyboard user can no longer reach or press it. `getByRole('button', { name: 'Follow' })` looks for the role and the accessible name that a screen reader announces. It fails on the `<div>`, and on an icon button with no name. The fix for the test is then the same fix that a screen reader user needs, such as `aria-label="Follow"`.
3. **"What happened to React's own test helpers in React 19, and what do you use instead?"**
   React removed every function of `react-dom/test-utils` except `act`, which moved to `react`. react.dev says that these utilities "made it too easy to depend on low level implementation details of your components and React". In their place, react.dev points to `render` instead of `renderIntoDocument`, and `fireEvent` instead of `Simulate`, both from `@testing-library/react`. `react-test-renderer` is deprecated, because it "doesn't match the environment users use, promotes testing implementation details, and relies on introspection of React's internals". Shallow rendering moved out of React into its own package, with the warning that it "depends on React internals and can block you from future upgrades".

```tree dir=right caption="Interview comparison: a test that reads the insides of a component vs. a test that follows the user."
Two kinds of component tests in an interview
- !Reads the insides [`followReducer` `state` `.follow-btn`] | Checks **implementation details** | **Fails on refactors**, **passes on real bugs**
- +Follows the user [`render` `getByRole` `fireEvent.click`] | Checks **what the user sees** | Fails **only when the user would see a change**
```
