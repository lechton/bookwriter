# Lecture 97: The Class Lifecycle Methods, and Why Three Were Renamed UNSAFE

*(How did a class component connect, reconnect, and disconnect at the right moment, and why are three of its methods called unsafe?)*

> INTERVIEW QUESTION | LEGACY | What were componentDidMount, componentDidUpdate, and componentWillUnmount, and why were some renamed UNSAFE?

---

## VS | Three Lifecycle Methods vs. One `useEffect`: the class splits one job by moment, the Effect writes it once

> A component goes through three moments: React puts it on the screen, React renders it again with new props, and React removes it. **Before Hooks, a class component gave each moment its own method, `componentDidMount`, `componentDidUpdate`, and `componentWillUnmount`, and React called each one at its moment.** Three older methods ran before the component was really on the screen, so React renamed them with the prefix `UNSAFE_`: work done there can belong to a render that React throws away.

In plain JavaScript, you decide when things happen. You open a connection to a chat server when the page loads, and you close it when the user clicks a button. You write both calls yourself, at the moment you choose:

```js title="Plain JavaScript: you pick the moment"
const connection = createConnection('https://localhost:1234', 'general');
~connection.connect()~; // You connect right now, when the page loads
closeButton.addEventListener('click', () => ~connection.disconnect()~); // You disconnect on the click
```

In React, you do not pick the moment. React does. The user clicks `Open chat`, and React adds the chat component to the screen. The user clicks `Close chat`, and React removes it. Your code never sees those moments happen. So your code has to ask React: "When you put this component on the screen, call me! And when you remove it, call me again!"

You already know one way to ask: `useEffect`, in a function component (Lesson 35). Before Hooks, a class component asked another way. It wrote methods with fixed names, and React called each one at its moment:

```jsx title="A class component: you write the methods, React calls them"
class ChatRoom extends Component {
  ~componentDidMount()~ { // React calls it after the chat appears on the screen
    this.setupConnection();
  }
  ~componentWillUnmount()~ { // React calls it when it removes the chat
    this.destroyConnection();
  }
}
```

**Why:** In a class, one job, staying connected to the right chat room, is split across three methods. The three must agree. When one of them is missing, the page still looks right, and only the Console shows the bug. The connections pile up on the server, or the chat stays connected to the old room after the user picked a new one. And a connection opened in one of the `UNSAFE_` methods can belong to a chat that never reached the screen, so nothing ever closes it.

### The Three Moments and Their Three Methods

Here is the whole class, with one method for each moment:

```jsx title="One class, one method for each moment"
class ChatRoom extends Component {
  ~componentDidMount()~ { // 1. After the chat appears: connect
    this.setupConnection();
  }
  ~componentDidUpdate(prevProps)~ { // 2. After the chat renders with a new room: reconnect
    if (this.props.roomId !== prevProps.roomId) {
      this.destroyConnection();
      this.setupConnection();
    }
  }
  ~componentWillUnmount()~ { // 3. When the chat closes: disconnect
    this.destroyConnection();
  }
}
```

> [!DEFINITION]
> **What is a lifecycle method?** [NEW] A lifecycle is the stages a living thing goes through: it is born, it changes, and it ends. A component goes through the same three stages on the screen, and React's docs call them mounting, updating, and unmounting.
> A lifecycle method is a method with a fixed name that you write on your class. React calls it at its one moment. You write `componentDidMount`, and no line of your code ever calls it.
> The name tells the moment. "Did mount" means the component is already on the screen. "Will unmount" means React is about to remove it (Lesson 97).

```tree caption="The three moments in the life of ChatRoom, and the class method React calls at each one."
Three moments in the life of `ChatRoom`
- +1. Mount: the chat appears [`componentDidMount`] | The user clicks **Open chat** | React calls it **after** the heading is on the screen: **connect**
- +2. Update: the room changes [`componentDidUpdate`] | The user picks **travel** | React calls it **after** the new heading is on the screen: **reconnect**
- +3. Unmount: the chat closes [`componentWillUnmount`] | The user clicks **Close chat** | React calls it as it **removes** the chat: **disconnect**
```

### VS | `componentWillMount` vs. `componentDidMount`: before the commit, or after it

Old code often shows a fourth name next to these three: `componentWillMount`. Here are the two, each holding the same line:

```jsx title="The same connection line in two methods"
~componentWillMount()~ { this.setupConnection(); } // Runs before React puts the chat on the screen
~componentDidMount()~ { this.setupConnection(); } // Runs after the chat is on the screen
```

**It may look the same, or work the same at first, but it is NOT the same thing!** When the user opens the chat, both methods run, both connect, and the chat works. The difference is when they run, and two words from Lesson 13 name it:

> [!DEFINITION]
> **Render and commit.** [REVIEW] React updates the screen in two steps. In the render, React calls your component and gets its JSX, and the page has not changed yet. In the commit, React changes the DOM, and the user sees the result. React can throw a render away and try again. A commit is final: what React commits is on the screen (Lesson 13).

- **`componentWillMount`** runs during the render, before the commit. At that point the chat is only a render attempt, and React can still throw it away.
- **`componentDidMount`** runs after the commit, when the chat is really on the screen.

That one difference is why React renamed `componentWillMount`, and two other methods that run before the commit, with the prefix `UNSAFE_`.

### The Rule of Thumb: does React call it for a component that is really on the screen?

**Ask one question about every lifecycle method: does React call it only for a component that is really on the screen? If yes, it is a safe place to connect, subscribe, or fetch. If it runs before the commit, React renamed it `UNSAFE_`, and side effects stay out of it.**

A senior developer also knows the four places where readers go wrong:
1. **They think `componentDidMount` is enough**, because the chat connects on the first open. It handles only the first moment. Principles 2 and 3 show what it misses.
2. **They think `componentDidUpdate` runs after the first render too.** React's docs say: "This method is not called for the initial render."
3. **They think `UNSAFE_` means the method no longer works, or that the new name made it safe.** Neither is true: the rename changed only the name. The docs say the method "only exists for historical reasons and should not be used in any new code."
4. **They translate a class into a function by matching names**, so `componentDidMount` becomes an Effect with an empty array. The docs say such an Effect "doesn't re-run when any of your component's props or state change", so the room switch is lost. Principle 6 shows the translation that works.

The project has four files in `src/`:

`chat.js` stands in for the chat server. It is the file from React's docs. It does not really connect. It prints a line in the Console instead:

  return {

      console.log('❌ Disconnected from "' + roomId + '" room at ' + serverUrl);

`App` is a function component, the same one you built with an Effect in Lesson 35. It does not change in this lesson:

```jsx title="src/App.jsx"
import { useState } from 'react';
import ChatRoom from './components/ChatRoom.jsx';

export default function App() {
  const [roomId, setRoomId] = useState('general');
  const [show, setShow] = useState(false);
  return (
    <>
      <label>
        Choose the chat room:{' '}
        <select value={roomId} onChange={e => setRoomId(e.target.value)}>
          <option value="general">general</option>
          <option value="travel">travel</option>
          <option value="music">music</option>
        </select>
      </label>
      <button onClick={() => setShow(!show)}>
        {show ? 'Close chat' : 'Open chat'}
      </button>
      {show && ~<ChatRoom roomId={roomId} />~} {/* Mounts ChatRoom on Open chat, unmounts it on Close chat */}
    </>
  );
}
```

The line `{show && <ChatRoom roomId={roomId} />}` creates all three moments. When `show` turns true, React mounts `ChatRoom`. When `roomId` changes, React updates it with the new prop. When `show` turns false, React unmounts it.

`ChatRoom.jsx` starts as a class with only `render`, the method you met in Lesson 96. It shows the heading and connects to nothing yet:

```jsx title="src/components/ChatRoom.jsx"
import { Component } from 'react';
import { createConnection } from '../chat.js';

const ~serverUrl~ = 'https://localhost:1234'; // One server for every room

export default class ChatRoom extends Component {
  render() {
    return <h1>Welcome to the {this.props.roomId} room!</h1>;
  }
}
```

Our team inherits a legacy version of this widget, written before Hooks. A migration guide flags its `UNSAFE_` methods. When that happens, a developer picks one of three ways:
1. **Rename it with the codemod.** A codemod is a tool that rewrites code for you, in every file at once. React's docs say: "Run the `rename-unsafe-lifecycles` codemod to automatically update your components." This fits when there is no time to change the logic. The behavior stays exactly the same, and only the old name is gone.
2. **Move the logic to the safe methods, `componentDidMount` and `componentDidUpdate`.** This fits a class that stays a class. Principles 4 and 5 do it.
3. **Rewrite the class as a function with `useEffect`.** This fits a class that needs new features, because Hooks do not work inside a class (Lesson 96). The docs say: "We recommend defining components as functions instead of classes." Principle 6 does it.

Each principle adds one method to `ChatRoom`, or moves one, and shows what the Console says without it.

**PRINCIPLES:** A class gives each moment of a component's life its own method, and React calls each one at its moment. Six principles follow:
1. **Principle 1: `componentDidMount` Connects When the Chat Opens.** React calls it once the component is on the screen. It is the place to connect, subscribe, or fetch, and `render` never is.
2. **Principle 2: `componentWillUnmount` Disconnects When the Chat Closes.** React calls it when it removes the component. It must undo what `componentDidMount` did, and Strict Mode checks the pair in development.
3. **Principle 3: `componentDidUpdate` Reconnects When the Room Changes.** React calls it after every re-render, never after the first render. The code compares the old props with the new ones and reconnects only when the room changed.
4. **Principle 4: The Three "Will" Methods Run Before React Commits.** `componentWillMount`, `componentWillReceiveProps`, and `componentWillUpdate` run in a render React can throw away, so React renamed them `UNSAFE_`.
5. **Principle 5: `componentDidUpdate` Takes Over From `UNSAFE_componentWillReceiveProps`.** A side effect on a prop change waits until the new props are on the screen. Each other use of the `UNSAFE_` methods has its own replacement.
6. **Principle 6: One `useEffect` Replaces the Three Lifecycle Methods.** One Effect with a cleanup and the dependency `roomId` does what the three methods did together.

## PRINCIPLE | `componentDidMount`: React calls it once, after the component is on the screen

> [!PRINCIPLE]
> **Principle 1: `componentDidMount` Connects When the Chat Opens**
>
> *Connect, subscribe, or fetch in `componentDidMount`, which React calls after it adds the component to the screen. Never do it in `render`.*
>
> A class component must connect to something outside React at the moment it appears. React calls `componentDidMount` after the commit, once per mount, so the connection opens for a chat the user really sees. `render` runs on every render and must stay pure. And `componentDidMount` handles only the first moment: the close and the room switch need their own methods.
>
> **DO THIS:**
> ```jsx
> class ChatRoom extends Component {
>   ~componentDidMount()~ { // Connects once, after the chat is on the screen
>     this.setupConnection();
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> class ChatRoom extends Component {
>   render() {
>     ~createConnection(serverUrl, this.props.roomId).connect();~ // **WRONG:** a new connection on every render
>     return <h1>Welcome to the {this.props.roomId} room!</h1>;
>   }
> }
> ```

The first moment is the mount: the user clicks `Open chat`, and the heading appears. The name says the moment: "did mount". React calls this method after it has put the component on the screen. React's docs name the jobs that belong there: "This is a common place to start data fetching, set up subscriptions, or manipulate the DOM nodes."

### Why not connect in `render`?

A developer new to classes might put the connection in `render`, because `render` also runs when the chat appears:

**DO NOT DO THIS:**
```jsx title="src/components/ChatRoom.jsx" startLine="6" bad="8"
export default class ChatRoom extends Component {
  render() {
    ~createConnection(serverUrl, this.props.roomId).connect();~ // **WRONG:** connects again on every render
    return <h1>Welcome to the {this.props.roomId} room!</h1>;
  }
}
```

**It may look the same at first, but it is NOT the same thing!** On the first open, both versions connect. But React calls `render` on every render of the chat. So every room switch opens one more connection, and nothing closes the old ones.

`render` must be pure, just like the body of a function component (Lesson 14). In development, Strict Mode even calls `render` twice and throws one result away (Lesson 47). `componentDidMount` runs once per mount, after the commit.

### `ChatRoom` connects in `componentDidMount`

`ChatRoom` gains two methods. `componentDidMount` is the lifecycle method. `setupConnection` is a helper method of our own:

```jsx title="src/components/ChatRoom.jsx" startLine="6" good="7,8,9,11,12,13,14"
export default class ChatRoom extends Component {
  ~componentDidMount()~ { // React calls it after the heading is on the screen
    this.setupConnection();
  }

  setupConnection() {
    ~this.connection~ = createConnection(serverUrl, this.props.roomId); // Stored on the instance, for later
    this.connection.connect();
  }

  render() {
    return <h1>Welcome to the {this.props.roomId} room!</h1>;
  }
}
```

Why `this.connection`, and not a local `const`? Because a later method must find this same connection object to close it. A local variable is gone when `setupConnection` returns. A field on the instance stays, because React keeps the same `ChatRoom` instance from the mount until the unmount.

No line of our code calls `componentDidMount`. React calls it. Here is the order when the user clicks `Open chat`:
1. `App` sets `show` to true and renders `<ChatRoom roomId="general" />`.
2. React creates a `ChatRoom` instance and calls `render`.
3. React commits the heading to the DOM.
4. React sees that the class defines `componentDidMount`, and calls it on the instance.

### Two Connecting lines for one click

The user clicks `Open chat`. The page shows the heading, as expected. But the Console shows two connections:

```page width=full caption="The page after Open chat, in development, with componentDidMount and no componentWillUnmount yet: two Connecting lines."
form:
  select: Choose the chat room: | general
  button: Close chat
heading: Welcome to the general room!
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
```

Strict Mode causes this, in four steps:
1. Our `main.jsx` mounts `App` inside `<StrictMode>`, and the page runs in development.
2. React's docs: "When Strict Mode is on, in development React will call `componentDidMount`, then immediately call `componentWillUnmount`, and then call `componentDidMount` again."
3. Our class has no `componentWillUnmount` yet, so the middle call does nothing.
4. `componentDidMount` runs twice and opens two connections, and nothing closes the first one.

In production, React calls `componentDidMount` once, and the Console shows one line. **Strict Mode is not the bug. It shows the bug: our class opens a connection and never closes it.**

This is the most common mistake with this method. The chat connects on the first open, so the first test passes. Then the user closes the chat, or picks another room, and nothing in the class handles it. React's docs warn of exactly this: "If you implement `componentDidMount`, you usually need to implement other lifecycle methods to avoid bugs."

## PRINCIPLE | `componentWillUnmount`: it closes what `componentDidMount` opened

> [!PRINCIPLE]
> **Principle 2: `componentWillUnmount` Disconnects When the Chat Closes**
>
> *Disconnect, unsubscribe, or cancel in `componentWillUnmount`, which React calls when it removes the component, so that it mirrors `componentDidMount`.*
>
> Removing a component from the DOM closes nothing outside React. A class that connects in `componentDidMount` and never disconnects leaves one more open connection after each close, while the page looks right. In development, Strict Mode calls mount, unmount, and mount again, so a missing or partial `componentWillUnmount` shows up at once in the Console.
>
> **DO THIS:**
> ```jsx
> class ChatRoom extends Component {
>   componentDidMount() {
>     this.setupConnection();
>   }
>   ~componentWillUnmount()~ { // Closes the same connection when the chat closes
>     this.destroyConnection();
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> class ChatRoom extends Component {
>   ~componentDidMount()~ { // **WRONG:** connects, and no method ever disconnects
>     this.setupConnection();
>   }
> }
> ```

The last moment is the unmount: the user clicks `Close chat`, and the heading disappears. The name says the moment: "will unmount". React calls this method when it removes the component from the screen. React's docs: "This is a common place to cancel data fetching or remove subscriptions."

The docs use one word for the pair: mirror. A mirror shows the same thing, reversed. What `componentDidMount` opens, `componentWillUnmount` closes. The docs: "The logic inside `componentWillUnmount` should "mirror" the logic inside `componentDidMount`."

```tree caption="componentDidMount and componentWillUnmount mirror each other: one opens the connection, the other closes the same connection."
The mirror pair in `ChatRoom`
- +Opens: `componentDidMount` [`setupConnection`] | Creates the connection and stores it on **`this.connection`** | Calls **`connect`**
- +Closes: `componentWillUnmount` [`destroyConnection`] | Reads the **same `this.connection`** | Calls **`disconnect`** and clears the field
```

### The heading disappears, and the connection stays open

**Without `componentWillUnmount`, the page looks right every time, and the connections pile up on the server.** Take the class from Principle 1, with only `componentDidMount`. The user opens the chat, closes it, and opens it again:
1. The user clicks `Open chat`. The Console shows two Connecting lines in development, as Principle 1 showed.
2. The user clicks `Close chat`. `App` sets `show` to false, and React removes `ChatRoom`. The heading disappears.
3. Nothing in our class runs at that moment, so nothing disconnects. The Console shows no new line.
4. The user clicks `Open chat` again. React creates a new `ChatRoom` instance, and two more Connecting lines appear.

```page width=full caption="The page after Open chat, Close chat, and Open chat again, in development, without componentWillUnmount: four Connecting lines and no Disconnected line."
form:
  select: Choose the chat room: | general
  button: Close chat
heading: Welcome to the general room!
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
```

React removed the `<h1>` from the DOM. That closes nothing outside React: the chat server still holds every connection. React's docs say it for the same chat written with an Effect: "As the user navigates across the app, the connections would keep piling up." Only our own `componentWillUnmount` can disconnect.

### `ChatRoom` disconnects in `componentWillUnmount`

`ChatRoom` gains `componentWillUnmount` and a second helper, `destroyConnection`:

```jsx title="src/components/ChatRoom.jsx" startLine="6" good="11,12,13,20,21,22,23"
export default class ChatRoom extends Component {
  componentDidMount() {
    this.setupConnection();
  }

  ~componentWillUnmount()~ { // React calls it when the user closes the chat
    this.destroyConnection();
  }

  setupConnection() {
    this.connection = createConnection(serverUrl, this.props.roomId);
    this.connection.connect();
  }

  destroyConnection() {
    ~this.connection.disconnect();~ // Closes the connection that setupConnection stored
    this.connection = null;
  }

  render() {
    return <h1>Welcome to the {this.props.roomId} room!</h1>;
  }
}
```

Both methods reach the same connection object, `this.connection`, because React keeps the same instance from the mount until the unmount.

### Connect, disconnect, connect: Strict Mode tests the pair

Now the user clicks `Open chat`, and then `Close chat`. Every Connecting line now has its Disconnected line:

```page width=full caption="The page after Open chat and then Close chat, in development, with both methods: every Connecting line has its Disconnected line."
form:
  select: Choose the chat room: | general
  button: Open chat
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
log: ❌ Disconnected from "general" room at https://localhost:1234 | chat.js:7
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
log: ❌ Disconnected from "general" room at https://localhost:1234 | chat.js:7
```

The first three lines come from the click on `Open chat`. Strict Mode calls `componentDidMount`, then `componentWillUnmount`, then `componentDidMount` again: connect, disconnect, connect. One connection stays open. The fourth line comes from the click on `Close chat`.

The extra pair is not React connecting twice by mistake. It is a test. React's docs: "This helps you notice if you forgot to implement `componentWillUnmount` or if its logic doesn't fully "mirror" what `componentDidMount` does."

A developer who sees the extra lines and turns off Strict Mode only hides the bug. The docs say the same for Effects: "The right question isn't "how to run an Effect once", but "how to fix my Effect so that it works after remounting"."

`componentWillUnmount` does the same job as the cleanup function an Effect returns, at the unmount (Lesson 32). The cleanup also runs at one more moment, before each new setup. Principle 6 comes back to that.

## PRINCIPLE | `componentDidUpdate`: it runs after every re-render, so compare `prevProps` before you reconnect

> [!PRINCIPLE]
> **Principle 3: `componentDidUpdate` Reconnects When the Room Changes**
>
> *Handle in `componentDidUpdate` every change to the props or state that `componentDidMount` reads. React calls it after each re-render, never after the first one.*
>
> `componentDidMount` reads `this.props.roomId` once, so the connection stays on the first room unless another method replaces it. React calls `componentDidUpdate` with `prevProps` after it commits each re-render. Comparing `this.props.roomId` with `prevProps.roomId` reconnects on a real change and does nothing on any other re-render.
>
> **DO THIS:**
> ```jsx
> componentDidUpdate(prevProps) {
>   if (~this.props.roomId !== prevProps.roomId~) { // Reconnects only when the room changed
>     this.destroyConnection();
>     this.setupConnection();
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> componentDidUpdate() {
>   ~this.destroyConnection();~ // **WRONG:** reconnects after every re-render, even in the same room
>   this.setupConnection();
> }
> ```

The middle moment sits between the mount and the unmount: the chat is open, and the user picks another room. React's docs: "React will call it immediately after your component has been re-rendered with updated props or state. This method is not called for the initial render."

React passes two values to this method:
- **`prevProps`** holds the props from before the update. The docs: "Compare `prevProps` to `this.props` to determine what changed."
- **`prevState`**, the second value, does the same for state. Our `ChatRoom` has no state, so it never reads it.

### The heading follows the menu, and the connection does not

Take the class from Principle 2, with `componentDidMount` and `componentWillUnmount`, and no `componentDidUpdate`. The user opens the chat on `general` and then picks `travel`:

```page width=full caption="The page after the user picks travel, without componentDidUpdate: the heading names travel, and the Console shows no new line."
form:
  select: Choose the chat room: | travel
  button: Close chat
heading: Welcome to the travel room!
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
log: ❌ Disconnected from "general" room at https://localhost:1234 | chat.js:7
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
```

**The heading says `travel`, and the chat is still connected to `general`.** Both the heading and the connection read `this.props.roomId`, so both seem to follow the menu. Only the heading does. Here is why:
1. The user picks `travel`. `App` renders `ChatRoom` again, with `roomId` set to `'travel'`.
2. React calls `render`, and the heading reads `Welcome to the travel room!`.
3. No method reconnects. `this.connection` is still the connection to `general`, made once, at the mount.
4. Later, the user clicks `Close chat`. `componentWillUnmount` disconnects `this.connection`.
5. The Console shows `Disconnected from "general"`, a room the user left long ago.

So the rule is simple: `render` reads `this.props.roomId` on every render. `setupConnection` read it once. Only `componentDidUpdate` can replace the connection when `roomId` changes.

This is a real mistake in old code. A team writes `ChatRoom` when the room cannot change, with only the mount and the unmount. Later a teammate adds the room menu to `App`. The heading follows the menu, so the change looks done. React's docs name the check that catches it: "verify that your `componentDidUpdate` method handles changes to any props and state you're using in `componentDidMount`."

### Where `prevProps` comes from

No line of our code passes `prevProps`. React passes it:
1. React keeps the props of the last render it committed.
2. After it commits the new render, React calls `componentDidUpdate` with those old props.
3. By then `this.props` holds the new props, so the method can compare the two.

### `ChatRoom` reconnects in `componentDidUpdate`

`ChatRoom` gains `componentDidUpdate`. The class now has all three lifecycle methods, as in React's docs:

```jsx title="src/components/ChatRoom.jsx" startLine="6" good="11,12,13,14,15,16"
export default class ChatRoom extends Component {
  componentDidMount() {
    this.setupConnection();
  }

  componentDidUpdate(prevProps) {
    if (~this.props.roomId !== prevProps.roomId~) { // Reconnects only when the room changed
      this.destroyConnection();
      this.setupConnection();
    }
  }

  componentWillUnmount() {
    this.destroyConnection();
  }

  setupConnection() {
    this.connection = createConnection(serverUrl, this.props.roomId);
    this.connection.connect();
  }

  destroyConnection() {
    this.connection.disconnect();
    this.connection = null;
  }

  render() {
    return <h1>Welcome to the {this.props.roomId} room!</h1>;
  }
}
```

Now, when the user picks `travel`, the Console shows the old room closing and the new one opening:

```page width=full caption="The page after the user picks travel, with componentDidUpdate: the Console leaves general and connects to travel."
form:
  select: Choose the chat room: | travel
  button: Close chat
heading: Welcome to the travel room!
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
log: ❌ Disconnected from "general" room at https://localhost:1234 | chat.js:7
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
log: ❌ Disconnected from "general" room at https://localhost:1234 | chat.js:7
log: ✅ Connecting to "travel" room at https://localhost:1234... | chat.js:4
```

The page is the same with and without `componentDidUpdate`. Only the Console shows the difference: the last two lines leave `general` and connect to `travel`.

### Why the `if` line matters

React calls `componentDidUpdate` after every re-render, not only after a room change. Suppose `App` later gains a switch for a dark theme. Each click on that switch re-renders `App`, so React re-renders `ChatRoom` too, with the same `roomId`:
- **With the `if` line**, the method reconnects only when `roomId` changed. The click on the theme switch leaves the connection alone.
- **Without the `if` line**, the method disconnects and reconnects after every re-render. Each click on the theme switch drops the chat and connects it again.

React's docs warn that the logic here "should usually be wrapped in conditions comparing `this.props` with `prevProps`, and `this.state` with `prevState`. Otherwise, there's a risk of creating infinite loops." A loop starts when the method calls `this.setState` with no condition: the new state causes a re-render, and the re-render calls the method again.

## PRINCIPLE | `UNSAFE_componentWillMount`: it runs before the commit, so a connection there can belong to a chat that never appears

> [!PRINCIPLE]
> **Principle 4: The Three "Will" Methods Run Before React Commits**
>
> *Keep side effects out of `UNSAFE_componentWillMount`, `UNSAFE_componentWillReceiveProps`, and `UNSAFE_componentWillUpdate`. They run before the commit, in a render React can throw away.*
>
> React can abandon a render, for example when a child suspends, and then build the component again from scratch. A connection opened in a method that runs before the commit can belong to an instance that never mounts, and no `componentWillUnmount` ever closes it. The prefix `UNSAFE_` changed only the name and marks the risk. The codemod renames the method. Moving the logic fixes it.
>
> **DO THIS:**
> ```jsx
> class ChatRoom extends Component {
>   ~componentDidMount()~ { // Connects only for the chat that reached the screen
>     this.setupConnection();
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> class ChatRoom extends Component {
>   ~UNSAFE_componentWillMount()~ { // **WRONG:** may connect for a render React throws away
>     this.setupConnection();
>   }
> }
> ```

The start of this lesson put `componentWillMount` next to `componentDidMount`. In old code today, that first method usually carries its new name, `UNSAFE_componentWillMount`:

```jsx title="The connection in UNSAFE_componentWillMount and in componentDidMount"
~UNSAFE_componentWillMount()~ { this.setupConnection(); } // Runs right after the constructor, before the commit
~componentDidMount()~ { this.setupConnection(); } // Runs after the chat is on the screen
```

On a plain first open, both connect, and the chat works. The difference is the moment:
- **"Will mount"** runs before React knows the component will reach the screen. React's docs: "React will call it immediately after the `constructor`."
- **"Did mount"** runs after the component is there.

### Why React can throw a render away

Since React 18, a render can stop before it reaches the commit. React's own words: "React may start rendering an update, pause in the middle, then continue later. It may even abandon an in-progress render altogether." You met this as concurrent rendering (Lesson 66).

Suspense is one place where this happens (Lesson 69). A render can be suspended, for example because the code of some child component has not loaded yet. React's docs describe what follows for `UNSAFE_componentWillMount`: "React will throw the in-progress tree away and attempt to construct the component from scratch during the next attempt. This is why this method is "unsafe"."

The in-progress tree is the set of components React has rendered in an attempt that it has not committed yet. Here is what that means for our legacy chat. **A connection can open for a chat that never reached the screen, and nothing ever closes it:**
1. A legacy `ChatRoom` connects in `UNSAFE_componentWillMount`. It sits inside a Suspense boundary next to a child whose code has not loaded yet, such as a `lazy` component (Lesson 70).
2. The user clicks `Open chat`. React constructs `ChatRoom` and calls `UNSAFE_componentWillMount`. The Console shows a Connecting line.
3. The other child suspends, so the whole render attempt is suspended. React shows the fallback of the Suspense boundary, such as `Loading...`.
4. React throws the in-progress tree away, with this `ChatRoom` instance and its `this.connection`.
5. While `Loading...` is on the screen, React tries once more, and that attempt suspends too. A second `ChatRoom` instance connects, and React throws it away as well. The Console shows a second Connecting line.
6. Those two instances never mounted, so React never calls their `componentWillUnmount`. Nothing disconnects them.
7. When the code has loaded, React constructs `ChatRoom` once more and calls `UNSAFE_componentWillMount` again. A third Connecting line appears, and the first two connections stay open.

With the line in `componentDidMount`, the Console stays quiet while `Loading...` is on the screen. The connection opens only after the commit, for the instance the user really sees.

### The three methods React renamed

Three class methods run before React commits a mount or an update. React renamed all three with the prefix `UNSAFE_`:
1. `componentWillMount` became `UNSAFE_componentWillMount`. React calls it right after the constructor.
2. `componentWillReceiveProps` became `UNSAFE_componentWillReceiveProps`. React calls it "when the component receives new props", before it renders with them.
3. `componentWillUpdate` became `UNSAFE_componentWillUpdate`. React calls it "before rendering with the new props or state."

The three methods of Principles 1 to 3 run at safe moments. `componentDidMount` and `componentDidUpdate` run after the commit. `componentWillUnmount` also starts with "will", but React calls it only for a component that has really mounted, so it was never renamed:

```tree caption="The three lifecycle methods that survive unchanged, and the three that React renamed with the prefix UNSAFE_."
Six class lifecycle methods
- +Survive unchanged [`componentDidMount` `componentDidUpdate` `componentWillUnmount`] | Run **after the commit**, or only for a component that **really mounted** | +**DO** put connections and subscriptions here
- !Renamed `UNSAFE_` [`UNSAFE_componentWillMount` `UNSAFE_componentWillReceiveProps` `UNSAFE_componentWillUpdate`] | Run **before the commit**, in a render React **can throw away** | ~Do **NOT** put side effects here
```

### What the rename changed, and what it did not

React added the `UNSAFE_` names in version 16.3, in March 2018. The old names are deprecated: React still runs them, warns about them, and plans to remove them. React's docs: "The old name has been deprecated. In a future major version of React, only the new name will work."

```jsx title="The old name and the new name"
~componentWillMount()~ { this.setupConnection(); } // The old name: deprecated, React warns about it
~UNSAFE_componentWillMount()~ { this.setupConnection(); } // The new name: the same method, the same moment
```

**Yes, it is the exact same thing!** Same method, same moment, same behavior. Only the name changed. The prefix does not make the method safe. It marks the method, so every reader of the file sees the risk. The `UNSAFE_` methods still run in React 19.

That is why the codemod is not a fix. A developer sees a warning about `componentWillMount`, runs `rename-unsafe-lifecycles`, and thinks the job is done. The connection still opens before the commit, exactly as before. React's docs give the real fix in one sentence: code that relies on mounting, like adding a subscription, "should go into `componentDidMount`."

Strict Mode keeps pointing at the new names too. React's docs: "React warns if some component anywhere inside a `<StrictMode>` tree uses one of these deprecated APIs: `UNSAFE_` class lifecycle methods like `UNSAFE_componentWillMount`." Our `main.jsx` mounts `App` inside `<StrictMode>`, so in development the Console shows a warning that names the method.

A legacy `UNSAFE_componentWillMount` that only sets up state moves somewhere else. React's docs: "For all practical purposes, it is identical to `constructor`". So state goes in the constructor, or in a `state` class field (Lesson 96).

## PRINCIPLE | `componentDidUpdate` instead of `UNSAFE_componentWillReceiveProps`: a side effect waits for the props on the screen

> [!PRINCIPLE]
> **Principle 5: `componentDidUpdate` Takes Over From `UNSAFE_componentWillReceiveProps`**
>
> *Move a side effect on a prop change from `UNSAFE_componentWillReceiveProps` to `componentDidUpdate`, and compare `this.props` with `prevProps`.*
>
> `UNSAFE_componentWillReceiveProps` reacts to props React has not rendered yet, and that render may be thrown away. `componentDidUpdate` runs after the commit, so it reacts only to props that are on the screen. State that only follows a prop needs no lifecycle method at all: read the prop in `render`, reset the component with a `key`, or adjust the state during render.
>
> **DO THIS:**
> ```jsx
> componentDidUpdate(prevProps) {
>   if (~this.props.roomId !== prevProps.roomId~) { // Reacts to the room already on the screen
>     this.destroyConnection();
>     this.setupConnection();
>   }
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> UNSAFE_componentWillReceiveProps(nextProps) {
>   if (~nextProps.roomId !== this.props.roomId~) { // **WRONG:** reconnects before React commits the new room
>     this.destroyConnection();
>     this.connection = createConnection(serverUrl, nextProps.roomId);
>     this.connection.connect();
>   }
> }
> ```

Our legacy widget also reconnects in a second `UNSAFE_` method. Here it is next to the method of Principle 3:

```jsx title="Reconnecting in UNSAFE_componentWillReceiveProps"
UNSAFE_componentWillReceiveProps(~nextProps~) { // Runs before React renders with the new props
  if (nextProps.roomId !== this.props.roomId) {
    this.destroyConnection();
    this.connection = createConnection(serverUrl, nextProps.roomId);
    this.connection.connect();
  }
}
```

```jsx title="Reconnecting in componentDidUpdate"
componentDidUpdate(~prevProps~) { // Runs after React commits the new props
  if (this.props.roomId !== prevProps.roomId) {
    this.destroyConnection();
    this.setupConnection();
  }
}
```

**It may look the same, or work the same at first, but it is NOT the same thing!** In production, on a plain room switch, both print `Disconnected from "general"` and then `Connecting to "travel"`. The difference is which props each one reacts to:
- **`UNSAFE_componentWillReceiveProps`** receives `nextProps`, which React's docs describe as "The next props that the component is about to receive from its parent component." React has not rendered with them yet, and that render may still be thrown away. `this.props` still holds the old props, so the comparison reads `nextProps` against `this.props`.
- **`componentDidUpdate`** receives `prevProps`, after the commit. The new props are already on the screen, in `this.props`. So the comparison flips: `this.props` against `prevProps`.

React's docs: "By the time of the next render attempt, the props might be different. This is why this method is "unsafe"." The docs then say that code that should run only for committed updates, like resetting a subscription, "should go into `componentDidUpdate`." A committed update is an update React has put on the screen.

So picture the render after a room switch thrown away. The legacy method has already disconnected one room and connected another, for a screen the user never saw.

The `if` line is needed here too. React calls this method whenever the parent re-renders, and the docs say a call "does not mean that the component has received *different* props than the last time."

### One replacement for each `UNSAFE_` method

A side effect is only one use of the old methods. React's docs give one replacement for each use:

| Legacy method | What it did | Where it goes today |
| :--- | :--- | :--- |
| **`UNSAFE_componentWillMount`** | Set up state | The constructor, or a `state` class field |
| **`UNSAFE_componentWillMount`** | Ran a side effect or a subscription | `componentDidMount` |
| **`UNSAFE_componentWillReceiveProps`** | Ran a side effect when a prop changed | `componentDidUpdate` |
| **`UNSAFE_componentWillReceiveProps`** | Re-computed data when a prop changed | A memoization helper, which keeps the last result and computes again only when the prop changes |
| **`UNSAFE_componentWillReceiveProps`** | Reset state when a prop changed | A fully controlled component, or a `key` that resets the component (Lesson 25) |
| **`UNSAFE_componentWillReceiveProps`** | Adjusted some state when a prop changed | Computing it from props during render, or `static getDerivedStateFromProps` (Lesson 80) |
| **`UNSAFE_componentWillUpdate`** | Ran a side effect before an update | `componentDidUpdate` |
| **`UNSAFE_componentWillUpdate`** | Read the DOM before an update, such as a scroll position | `getSnapshotBeforeUpdate` |

The last two rows have no function version. React's docs: "There is no direct equivalent to `UNSAFE_componentWillUpdate` in function components." And for `getSnapshotBeforeUpdate`: "At the moment, there is no equivalent to `getSnapshotBeforeUpdate` for function components."

### A copied prop moved to the wrong place

Many legacy classes used `UNSAFE_componentWillReceiveProps` for something else: copying a prop into state. Here, the class keeps its own copy of the room in `this.state.room`, and the heading reads that copy:

```jsx title="A prop copied into state, in a legacy class"
state = { room: this.props.roomId };

UNSAFE_componentWillReceiveProps(nextProps) {
  ~this.setState({ room: nextProps.roomId });~ // Copies the new prop into state before React renders
}

render() {
  return <h1>Welcome to the {this.state.room} room!</h1>;
}
```

During the migration, a developer moves the copy to `componentDidUpdate`, because that is where side effects went:

**DO NOT DO THIS:**
```jsx title="The same copy moved to componentDidUpdate"
componentDidUpdate(prevProps) {
  if (this.props.roomId !== prevProps.roomId) {
    ~this.setState({ room: this.props.roomId });~ // **WRONG:** a second render after every room switch
  }
}
```

Now each room switch renders `ChatRoom` twice. The first render still holds the old `room` in state. Then `componentDidUpdate` sets the new one, and React renders again. React's docs say that calling `setState` there "will trigger an extra rendering", and that "This pattern often causes performance issues".

Copying a prop is not a side effect, so it needs no lifecycle method at all. The class reads `this.props.roomId` directly in `render`, and the copy in state disappears:

**DO THIS:**
```jsx title="Reading the prop directly in render"
render() {
  return <h1>Welcome to the {~this.props.roomId~} room!</h1>; // One render, always the current room
}
```

### No `UNSAFE_` method left

After Principles 4 and 5, the legacy `ChatRoom` becomes the class of Principle 3:
1. The connection in `UNSAFE_componentWillMount` moves to `componentDidMount`.
2. The reconnect in `UNSAFE_componentWillReceiveProps` moves to `componentDidUpdate`, with the comparison flipped to `this.props` against `prevProps`.
3. `componentWillUnmount` stays as it was.

```tree dir=right caption="How the legacy ChatRoom loses its UNSAFE_ methods: each side effect moves to a method that runs after the commit."
Moving the legacy `ChatRoom` off its `UNSAFE_` methods
- !Before: the legacy class [`UNSAFE_componentWillMount` `UNSAFE_componentWillReceiveProps`] | Connects and reconnects **before the commit** | In development, Strict Mode **warns** and the room switch **crashes**
- +After: the class of Principle 3 [`componentDidMount` `componentDidUpdate` `componentWillUnmount`] | Connects and reconnects **after the commit** | **No `UNSAFE_` method** left
```

## PRINCIPLE | One `useEffect` with `[roomId]`: setup, cleanup, and dependency do the work of the three methods

> [!PRINCIPLE]
> **Principle 6: One `useEffect` Replaces the Three Lifecycle Methods**
>
> *Translate `componentDidMount`, `componentDidUpdate`, and `componentWillUnmount` into one Effect whose setup connects, whose cleanup disconnects, and whose dependencies list every value the setup reads.*
>
> The setup runs after the mount and after each change of a dependency. The cleanup runs before each new setup and at the unmount. The dependency `roomId` replaces the `prevProps` check. An empty array, written by matching the class method names, keeps the mount and loses the update. Unrelated jobs that shared one class method go into separate Effects.
>
> **DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[roomId]~); // Reconnects whenever the user picks another room
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   const connection = createConnection(serverUrl, roomId);
>   connection.connect();
>   return () => connection.disconnect();
> }, ~[]~); // **WRONG:** connects once and ignores every room switch
> ```

Here is the Effect you wrote for this same chat in Lesson 35:

```jsx title="The chat connection as one Effect"
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  return () => connection.disconnect();
}, ~[roomId]~); // Runs the cleanup and the setup again when roomId changes
```

The class of Principle 3 has three lifecycle methods and two helpers. The Effect has five lines. **Yes, it is the exact same thing!** The user opens the chat, picks `travel`, and closes the chat. The page and the Console show the same lines, in the same order, for both.

React's docs, after the class and the Effect: "This `useEffect` call is equivalent to the logic in the lifecycle methods above." And more generally: "For many use cases, defining `componentDidMount`, `componentDidUpdate`, and `componentWillUnmount` together in class components is equivalent to calling `useEffect` in function components."

The two forms answer different questions:
- **The class** answers "what happens at the mount, at each update, and at the unmount?"
- **The Effect** answers "how do I start, and how do I stop?"

React's docs: "Effects have a different lifecycle from components. Components may mount, update, or unmount. An Effect can only do two things: to start synchronizing something, and later to stop synchronizing it."

### Each piece of the class, in the Effect

Each piece of the class lands in one place in the Effect:
1. **`componentDidMount` with `setupConnection`** becomes the setup: the function you pass to `useEffect`.
2. **`componentWillUnmount` with `destroyConnection`** becomes the cleanup: the function the setup returns.
3. **`componentDidUpdate` with the `prevProps.roomId` check** becomes the dependency `roomId`. When `roomId` changes, React runs the old cleanup and then the new setup.
4. **`this.connection` on the instance** becomes `connection`, a local variable of the setup. The cleanup is written inside the setup, so it reads that same variable. No `this` is needed.

```tree caption="How each piece of the ChatRoom class lands in one place of the Effect."
The class `ChatRoom` as one Effect
- +Setup [`componentDidMount` `setupConnection`] | Runs **after the mount** and **after each room change** | Creates `connection` and calls **`connect`**
- +Cleanup [`componentWillUnmount` `destroyConnection`] | Runs **before each new setup** and **at unmount** | Calls **`disconnect`** on its own `connection`
- +Dependency `roomId` [`componentDidUpdate` `prevProps.roomId`] | React **compares** `roomId` with the last render | Runs the cleanup and the setup **only when it changed**
```

The Effect leaves `general` with no `prevProps` anywhere, because each cleanup closes the connection of its own render. When the user picks `travel`:
1. Each render's Effect reads the `roomId` of its own render (Lesson 15).
2. `roomId` changed, so React runs the cleanup of the last Effect. That cleanup disconnects its own `connection`, the one for `general`.
3. React then runs the new setup, which connects to `travel`.

React's docs give two checks before a migration, and they are Principles 2 and 3: "First, verify that your `componentWillUnmount` does the opposite of `componentDidMount`." Then: "Next, verify that your `componentDidUpdate` method handles changes to any props and state you're using in `componentDidMount`."

### An empty array loses the room switch

A developer translates the class by matching method names. `componentDidMount` becomes an Effect with an empty array, and its cleanup stands in for `componentWillUnmount`. The developer leaves out `componentDidUpdate`, because it looked like extra code:

**DO NOT DO THIS:**
```jsx title="The Effect with an empty array"
useEffect(() => {
  const connection = createConnection(serverUrl, roomId);
  connection.connect();
  return () => connection.disconnect();
}, ~[]~); // **WRONG:** never reconnects when the user picks another room
```

**It may look the same at first, but it is NOT the same thing!** On the first open, both Effects connect to `general`. React's docs even say that an empty dependency array corresponds to the component "mounting". But the same docs say an Effect with empty dependencies "doesn't re-run when any of your component's props or state change." So the user picks `travel`, the heading changes, and the Console shows no new line:

```page width=full caption="The page after the user picks travel, with an empty dependency array: the heading names travel, and the Console shows no new line."
form:
  select: Choose the chat room: | travel
  button: Close chat
heading: Welcome to the travel room!
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
log: ❌ Disconnected from "general" room at https://localhost:1234 | chat.js:7
log: ✅ Connecting to "general" room at https://localhost:1234... | chat.js:4
```

It is the bug of Principle 3, back in a function. The linter flags `roomId` as a missing dependency (Lesson 37). The fix is one word in the array: `[roomId]`.

### `ChatRoom` as a function

`ChatRoom.jsx` becomes a function with one Effect, the file of Lesson 35. `App.jsx` and `chat.js` do not change:

```jsx title="src/components/ChatRoom.jsx, the function" good="7,8,9,10,11"
import { useEffect } from 'react';
import { createConnection } from '../chat.js';

const serverUrl = 'https://localhost:1234';

export default function ChatRoom({ roomId }) {
  useEffect(() => {
    const ~connection~ = createConnection(serverUrl, roomId); // A local variable, no this
    connection.connect();
    return () => connection.disconnect();
  }, ~[roomId]~); // Does the job of the prevProps check
  return <h1>Welcome to the {roomId} room!</h1>;
}
```

The user opens the chat, picks `travel`, and closes the chat. In development, the Console shows the same six lines for the class and for the function:

Strict Mode checks both forms the same way in development. For the class, it runs one extra unmount and mount. For the Effect, it runs one extra cleanup and setup (Lesson 32).

### One method with two jobs becomes two Effects

A class often does two unrelated jobs in one method, because a class has only one `componentDidMount`. Suppose the legacy class also records each visit to a room:

```jsx title="Two jobs in one componentDidMount"
componentDidMount() {
  ~logVisit(this.props.roomId);~ // Job 1: record the visit
  this.setupConnection(); // Job 2: connect to the room
}
```

A team moves both calls into one Effect, because they shared one method. Later they add another dependency that must reconnect the chat. React's docs describe what goes wrong, with this same example: "If this Effect re-synchronizes, it will also call `logVisit(roomId)` for the same room, which you did not intend." The app records the visit again every time the chat reconnects.

The fix, in the docs' words: "Logging the visit is a separate process from connecting. Write them as two separate Effects." And for the class side: "If your lifecycle methods do multiple unrelated things, split them into multiple independent Effects."

Mount, update, and unmount are how you read a class. They are not how you write an Effect. React's docs: "Try to write every Effect as an independent process and think about a single setup/cleanup cycle at a time. It shouldn't matter whether your component is mounting, updating, or unmounting."

```jsx title="src/components/ChatRoom.jsx, the class"
import { Component } from 'react';
import { createConnection } from '../chat.js';

const serverUrl = 'https://localhost:1234';

export default class ChatRoom extends Component {
  ~componentDidMount()~ { // Principles 1 and 4: connects after the chat appears
    this.setupConnection();
  }

  ~componentDidUpdate(prevProps)~ { // Principles 3 and 5: reconnects after a committed room change
    if (this.props.roomId !== prevProps.roomId) {
      this.destroyConnection();
      this.setupConnection();
    }
  }

  ~componentWillUnmount()~ { // Principle 2: mirrors componentDidMount
    this.destroyConnection();
  }

  setupConnection() {
    this.connection = createConnection(serverUrl, this.props.roomId);
    this.connection.connect();
  }

  destroyConnection() {
    this.connection.disconnect();
    this.connection = null;
  }

  render() {
    return <h1>Welcome to the {this.props.roomId} room!</h1>;
  }
}
```

Here is the same component today, as a function:

```jsx title="src/components/ChatRoom.jsx, the function"
import { useEffect } from 'react';
import { createConnection } from '../chat.js';

const serverUrl = 'https://localhost:1234';

export default function ChatRoom({ roomId }) {
  ~useEffect~(() => { // Principle 6: one Effect does the job of all three methods
    const connection = createConnection(serverUrl, roomId);
    connection.connect();
    return () => connection.disconnect();
  }, [roomId]);
  return <h1>Welcome to the {roomId} room!</h1>;
}
```

### When React calls each lifecycle method

Each user action reaches the class through one render and one commit. React calls the lifecycle method only after the commit, or, for the unmount, as it removes the chat:

```tree dir=right caption="What React calls in the ChatRoom class after each user action, in production."
The three user actions, and what React calls in `ChatRoom`
- +1. The user clicks Open chat [`componentDidMount`] | React creates the instance and calls **`render`** | React **commits** the heading | React calls **`componentDidMount`**: Connecting to general
- +2. The user picks travel [`componentDidUpdate`] | React calls **`render`** with the new props | React **commits** the new heading | React calls **`componentDidUpdate`**: Disconnected from general, Connecting to travel
- +3. The user clicks Close chat [`componentWillUnmount`] | React removes `ChatRoom` from the screen | React calls **`componentWillUnmount`**: Disconnected from travel
```

In development, the first action also runs the extra unmount and mount of Strict Mode, so the Console shows two more lines after the first click.

| Moment | The class | The Effect | What the Console shows |
| :--- | :--- | :--- | :--- |
| **Mount: the user clicks Open chat** | `componentDidMount` calls `setupConnection` | The setup runs | Connecting to `general` |
| **Update: the user picks travel** | `componentDidUpdate` compares `prevProps.roomId`, then disconnects and connects | The cleanup for `general` runs, then the setup for `travel` | Disconnected from `general`, then Connecting to `travel` |
| **Unmount: the user clicks Close chat** | `componentWillUnmount` calls `destroyConnection` | The cleanup runs | Disconnected from `travel` |
| **Before the commit** | `UNSAFE_componentWillMount`, `UNSAFE_componentWillReceiveProps`, `UNSAFE_componentWillUpdate`: no side effects | No equivalent: the setup never runs before the commit | Nothing |

Remember the one sentence of this lesson. **A class component gives each moment its own method: `componentDidMount`, `componentDidUpdate`, and `componentWillUnmount`. The three "will" methods that ran before the commit were renamed `UNSAFE_`, because React can throw that render away.**

## For the Interview

> **The Interview Question:** What were componentDidMount, componentDidUpdate, and componentWillUnmount, and why were some renamed UNSAFE?

### How to Answer Clearly in 30 Seconds

"They are the lifecycle methods of a class component: methods with fixed names that React calls at one moment each in the component's life.
1. **`componentDidMount`** runs after the component is added to the screen. It is the place to connect, subscribe, or fetch.
2. **`componentDidUpdate`** receives `prevProps` and `prevState`, and runs after every re-render with new props or state, never after the first render. It compares the old values with the new ones and acts only on a change.
3. **`componentWillUnmount`** runs when the component is removed. It must mirror `componentDidMount`, and Strict Mode checks that in development by calling mount, unmount, and mount again.

The three must agree, because one job, such as a connection to the current room, is split across all three. React renamed `componentWillMount`, `componentWillReceiveProps`, and `componentWillUpdate` with the prefix `UNSAFE_` because they run before React commits. With Suspense, React can throw a render attempt away and start again, so a side effect there can run for a mount or an update that never happens. The rename changed only the name. Today one `useEffect` with a cleanup and the right dependencies does what the three surviving methods did together."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does the `UNSAFE_` prefix change how the method works, and does the codemod fix the problem?"**
   No to both. `UNSAFE_componentWillMount` is the same method as `componentWillMount`, called at the same moment, right after the constructor. The old names are deprecated, and in a future major version only the new names will work. The `UNSAFE_` names still run in React 19, and Strict Mode warns about them in development. The `rename-unsafe-lifecycles` codemod only renames them. The fix is to move the logic: a subscription goes to `componentDidMount`, a side effect on a prop change goes to `componentDidUpdate`, and state setup goes to the constructor or a `state` class field.

2. **"Is `componentDidMount` the same as `useEffect` with an empty array?"**
   Only on the first open. Both run after the component is on the screen. But a class usually reads props in `componentDidMount`, and then needs `componentDidUpdate` to follow their changes. An Effect with an empty array never runs again, so matching the class method names one to one loses the update: the user picks another room, and the chat stays connected to the first one. The right translation is one Effect whose dependencies list every value the setup reads, such as `[roomId]`. Its setup does the job of `componentDidMount` and of the reconnect, and its cleanup does the job of `componentWillUnmount` and of the disconnect. In the rare case where code must run before the browser paints, React's docs say `useLayoutEffect` is a closer match (Lesson 49).

3. **"Why does a class component connect twice when the page opens in development?"**
   Because the page runs inside `<StrictMode>`. In development, Strict Mode calls `componentDidMount`, then `componentWillUnmount`, then `componentDidMount` again. With a correct `componentWillUnmount`, the Console shows connect, disconnect, connect, and only one connection stays open. Without it, the Console shows two Connecting lines and no Disconnected line. That is the bug Strict Mode is there to show: in production, the same connections would pile up each time the user closes and opens the chat. The fix is to write the missing `componentWillUnmount`, never to turn Strict Mode off. In production, React calls `componentDidMount` once.
