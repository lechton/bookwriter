# Lecture 100: How Old Code Reached into Children: cloneElement, the Children Methods, and defaultProps

*(How did old React code give a child a prop that the page never wrote?)*

> INTERVIEW QUESTION | LEGACY | What were cloneElement, the Children utilities, and defaultProps for, and why were they abandoned?

---

## VS | Copying the Children with `cloneElement` vs. Passing the Value in Plain Sight: the same screen, but only one shows where the value comes from

> You already know how a parent gives a child a value: it writes a prop on the child's tag, such as `isPlaying={true}`. **Old React code often skipped the tag: the parent copied the children it received with `cloneElement`, and added the prop to each copy.** The screen looks the same, but nobody who reads the page can see where the value comes from, so a harmless change breaks it.

In React, data flows down through props, and you can see it. Open the file that writes `<Song title="Yesterday" />`, and every prop of that song is right there on the tag. When a parent wraps other tags, such as `<Playlist>` around three songs, it receives them in its `children` prop (Lesson 09).

Code written in 2020 and earlier often wanted to give each of those children one more prop. The page did not write that prop. So the parent reached into `children`, copied each child, and added the prop to the copy. React gave it two tools for this: `cloneElement` to copy one child, and the `Children` methods to walk through all of them. In the same years, a component set default values for its props with `defaultProps`. Teams still maintain a lot of this code, so you will meet all three.

Take the Up next list of a music app such as Spotify or Apple Music. Three songs sit one under the other, with a `Next` button below them. The song that plays right now is highlighted. Ask yourself: who knows which song plays? Only the list itself, because only the list holds the number that `Next` changes. The three song tags written by the page know nothing about it.

**Why:** Copying the children works until a normal change arrives. A teammate moves two songs into a component of their own, and the highlight stops working, while the bug sits in a file nobody touched. Then the app moves to React 19, and a song with no artist shows a blank where `Unknown artist` used to be. To read old code and fix it, you need to know what each of these tools really does.

### The Same Prop, Written Two Ways

Here is the same song with `isPlaying`, written two ways:

```jsx title="Writing isPlaying on the tag, and adding it with cloneElement"
<Song title="Yesterday" ~isPlaying={true}~ /> {/* The page writes the prop itself */}
~cloneElement~(<Song title="Yesterday" />, { isPlaying: true }); // A function call adds the prop to a copy
```

For the result, it is the exact same thing. Both lines give a `Song` element whose title is Yesterday and whose `isPlaying` is true.

For the developer who reads the page, it is NOT the same thing. In the first line, `isPlaying` sits on the tag, where anyone can see it. In the second line, a function call adds it inside the `Playlist` file, a file the reader of the page never opens. React's docs say this pattern "makes it harder to trace the data flow".

> [!DEFINITION]
> **What is a React element?** [REVIEW] A JSX tag is not magic: it becomes a plain JavaScript object, called an element. `<Song title="Yesterday" />` becomes an object whose `type` is `Song` and whose `props` are `{ title: 'Yesterday' }`. React never changes an element after it creates it. So when you want an element with one more prop, you need a new element (Lesson 76).

> [!DEFINITION]
> **What is the children prop?** [REVIEW] Whatever the page writes between the opening and the closing tag of a component arrives in that component as one prop, `children`. Write three `<Song>` tags between `<Playlist>` and `</Playlist>`, and `Playlist` receives those three elements in `children`. It can show them as they are, with `{children}` (Lesson 09).

```tree caption="Two ways a Song gets isPlaying: written on the tag by the page, or added to a copy inside Playlist."
Where `isPlaying` comes from
- +Written on the tag [`isPlaying={true}`] | The page **writes the prop itself** | Anyone who reads the page **sees where it comes from**
- !Added by `cloneElement` [`cloneElement`] | `Playlist` **adds the prop to a copy** | The reader of the page **cannot see it**
```

### The Rule of Thumb: can you see where the value comes from?

**Ask one question about every prop: can you see, in the file that writes the tag, where its value comes from? Old code adds the prop to a hidden copy. Code of today passes it in plain sight, through a render prop or through context.**

You will meet four ways to tell each song whether it plays:
1. **`Children.map` with `cloneElement`.** The old way. Both functions are on the list of Legacy React APIs (Lesson 98). React still exports them, but does not recommend them for new code.
2. **A render prop.** `Playlist` calls a function from the page with each song and whether it plays (Lesson 89). React's docs prefer it to `cloneElement` "because it is more explicit".
3. **Context.** `Playlist` provides `isPlaying` around each song, and `Song` reads it itself (Lesson 28).
4. **A custom Hook.** It keeps only the logic, which song plays and what `Next` does, and the page writes all the markup (Lesson 39). React's docs name it as a third way out. This lesson only names it.

```tree caption="Four ways to tell each Song whether it plays, from the old way to the ways React recommends today."
Four ways to pass "this song plays" from `Playlist` to each `Song`
- !1. Copy the children [`Children.map` `cloneElement`] | **Legacy**: met in old code | The page **never sees** `isPlaying`
- +2. A render prop [`renderSong`] | `Playlist` **hands the value to the page** | The page **writes** `isPlaying` itself
- +3. Context [`PlayingContext`] | `Playlist` **provides** the value | `Song` **reads it itself**
- +4. A custom Hook | Keeps **only the logic** | The page writes **all the markup**
```

A senior developer also knows the four places where readers usually go wrong:
1. **`Children` and `children` are two different things.** `Children`, with a capital C, is an object of methods that React exports. The `children` prop is, in the words of React's docs, "good and encouraged".
2. **`cloneElement` does not change the song it receives.** It returns a new element, and the original stays as it was.
3. **`Children.map` does not see every song on the screen.** It sees only the JSX written between the tags.
4. **`Song.defaultProps` and a default parameter are not two spellings of one thing.** In React 19, only the default parameter still works on a function component.

This lesson teaches you to read the old code and to rewrite it. It does not ask you to write new code with `cloneElement`, the `Children` methods, or `defaultProps`.

**PRINCIPLES:** Old code hides a prop in a copy. Code of today passes it where you can see it. Six principles follow:
1. **`cloneElement` copies a song and adds `isPlaying`.** It returns a new element, and the original does not change. A prop passed to it replaces the prop of the same name.
2. **`Children.map` hands every song to `cloneElement`.** It works with one child, many children, or none, which `children.map` does not.
3. **`Children.count` sees `<MoreSongs />` as one song.** The `Children` methods see only the JSX between the tags, so a component of your own there breaks the highlight.
4. **A render prop lets the page write `isPlaying` itself.** `Playlist` calls `renderSong` with each song and whether it plays.
5. **`Song` reads `isPlaying` from `PlayingContext`.** The page writes nothing, and a component in between breaks nothing.
6. **React 19 ignores `defaultProps` on a function component.** The default goes in the parameter list.

## PRINCIPLE | `cloneElement`: a new element with extra props, and the original stays the same

> [!PRINCIPLE]
> **Principle 1: Cloning: `cloneElement` Returns a New Element and Leaves the Original Alone**
>
> *`cloneElement(element, props)` returns a new element with the same type; each prop in `props` replaces the prop of the same name, and the original element does not change.*
>
> Old code used `cloneElement` to give an element a prop the page never wrote. React never changes an element after it creates it, so the original stays as it was, and the code must render the copy. When the tag and the call set the same prop, the value in the call wins.
>
> **DO THIS:**
> ```jsx
> function PlayingSong({ song }) {
>   const playing = cloneElement(song, { isPlaying: true });
>   return ~playing~; // Renders the copy, which has isPlaying
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function PlayingSong({ song }) {
>   cloneElement(song, { isPlaying: true });
>   return ~song~; // **WRONG:** song never got isPlaying, and the copy was thrown away
> }
> ```

Remember object spread (Lesson 17)? `{ ...item, giftWrap: true }` builds a new object: every old field, plus one change. `cloneElement` does the same job for a React element:

```jsx title="Copying one Song element with cloneElement"
import { cloneElement } from 'react';

const song = <Song title="Yesterday" />;
const playing = ~cloneElement(song, { isPlaying: true })~; // A new element: the props of song, plus isPlaying
```

Now compare the props of the two elements:

```js title="The props of the original and of the copy"
~song.props~; // { title: 'Yesterday' }: the original has no isPlaying
~playing.props~; // { title: 'Yesterday', isPlaying: true }: only the copy has it
```

Why a copy? Because React never changes an element after it creates it (Lesson 76). So `cloneElement` builds a second element from the first one:
1. **The props.** It starts from the props of `song` and puts the new props on top, exactly like spread. React's docs call this "shallowly merging" the props. Each new prop replaces the whole prop of the same name, and every other prop is copied as it is.
2. **What it keeps.** The copy keeps the type, the key, and the ref of the original. So the copy is still a `Song`.
3. **What it leaves alone.** `song` stays exactly as it was. Only the copy has `isPlaying`.

### When the tag already sets `isPlaying`, the call wins

What if the tag already sets `isPlaying`? Then the two values meet, and the one passed to `cloneElement` wins:

```jsx title="The tag says false, and cloneElement says true"
const song = <Song title="Yesterday" ~isPlaying={false}~ />; // The tag sets isPlaying to false
const playing = cloneElement(song, { ~isPlaying: true~ }); // The copy gets true, and true wins
```

React's docs call this overriding a prop. The returned element "will 'prefer' the value from `props`", the object you pass to the call.

This is where old code fools developers. On the Up next list, `Playlist` copies every song with `isPlaying`. A developer wants to see how the Yesterday row looks when it is not playing:
1. The developer opens the App file to find where `isPlaying` is set. The file shows only the title and the artist on that tag.
2. The developer adds `isPlaying={false}` to that tag.
3. Yesterday stays highlighted. `Playlist` copies the song, and the value in the copy replaces the one on the tag.

The page ignores what the developer wrote, and the reason sits in a file the developer did not open.

### The second and the third argument

`cloneElement` takes up to three arguments. The second may be `null`, and the third gives the copy new children:

```jsx title="cloneElement with null as the props, and with new children"
cloneElement(song, ~null~); // No new props: the copy keeps every prop of song
cloneElement(song, null, ~'Goodbye'~); // New children: the children of the copy are 'Goodbye'
```

Without a third argument, the copy keeps the children of the original. The first argument must be a valid React element. Old code often checked that first with `isValidElement` (Lesson 76).

## PRINCIPLE | `Children.map`: calls your function for every child, even when there is only one

> [!PRINCIPLE]
> **Principle 2: Walking Through Children: `Children.map` Calls Your Function for Every Child**
>
> *`Children.map(children, fn)` calls `fn` with each child and its index and returns a flat array; old code combined it with `cloneElement` to give every child a prop, and with `Children.count` to know how many children there are.*
>
> The `children` prop is not always an array. With one child, it is that one element. So `children.map` works with three songs and crashes with one. The `Children` methods accept every shape of `children`, and that is why old code used them.
>
> **DO THIS:**
> ```jsx
> <ul>
>   {~Children.map~(children, (child, index) => // Works with one song, three songs, or none
>     cloneElement(child, { isPlaying: index === playingIndex })
>   )}
> </ul>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ul>
>   {~children.map~((child, index) => // **WRONG:** with one song, children is not an array, and the page crashes
>     cloneElement(child, { isPlaying: index === playingIndex })
>   )}
> </ul>
> ```

Old code did not copy one song. It copied every song between the tags. For that it needed a second tool from React: `Children`.

### VS | `children` vs. `Children`: one capital letter, two different things

Look at two lines inside a `<ul>`:

```jsx title="Showing children as they are, and walking through them with Children.map"
<ul>{~children~}</ul> {/* The children prop: shows the JSX between the tags as it is */}
<ul>{~Children.map~(children, child => <li>{child}</li>)}</ul> {/* Calls our function once for each child */}
```

It may look the same, but it is NOT the same thing:
1. **`children`, small c,** is the prop. It holds the JSX the page wrote between the tags (Lesson 09).
2. **`Children`, capital C,** is an object that React exports. You import it from react, and its methods walk through the `children` prop one child at a time.

React's docs warn readers not to confuse the two. The `Children` object has five methods. This lesson uses two of them:
1. **`Children.map`** calls your function with each child and its index, starting at 0. It returns a flat array of what your function returns.
2. **`Children.count`** returns the number of children.

You will meet the other three in old code:
1. **`Children.forEach`** runs your function for each child and returns nothing.
2. **`Children.only`** returns the one child, and throws an error if there is not exactly one.
3. **`Children.toArray`** returns the children as a flat array.

### Why not `children.map`? Because `children` is not always an array

A developer who sees `Children.map` often thinks it is an old spelling of `children.map`. It is not. In plain JavaScript, `.map` exists only on arrays. With three songs, `children` is an array, so `children.map` works. With one song, it breaks:

```jsx title="One song between the Playlist tags"
<Playlist>
  ~<Song title="Yesterday" artist="The Beatles" />~ {/* One child: children is this element, not an array */}
</Playlist>
```

With one child, React does not wrap it in an array. `children` is the `Song` element itself. An element has no map method, so `children.map` throws a `TypeError`, and the page goes blank.

> [!DEFINITION]
> **What does it mean that children is opaque?** [NEW] React's docs call the `children` prop opaque: your code should not rely on its shape. With three tags between the tags, it is an array. With one tag, it is that one element. With plain text, it is a string, and with nothing at all, it is `undefined`. So an array method such as `children.map` works in one case and crashes in another. The `Children` methods accept every shape, and that is why old code used them (Lesson 100).

### The playlist written with `Children.map` and `cloneElement`

Now we build the old playlist. The App file writes three songs between the tags:

```jsx title="src/App.jsx"
import Playlist from './Playlist.jsx';
import Song from './Song.jsx';

export default function App() {
  return (
    <Playlist>
      <Song title="Yesterday" artist="The Beatles" />
      <Song title="Imagine" artist="John Lennon" />
      <Song title="Hey Jude" artist="The Beatles" />
    </Playlist>
  );
}
```

`Song` gives its row the `playing` class when the song plays:

```jsx title="src/Song.jsx"
export default function Song({ title, artist, ~isPlaying~ }) { // isPlaying comes from the copy, not from App.jsx
  return <li className={isPlaying ? 'playing' : ''}>{title}: {artist}</li>;
}
```

`Playlist` holds the index of the playing song in state. It copies every child with `isPlaying`, and it moves the index on each click:

```jsx title="src/Playlist.jsx"
import { Children, cloneElement, useState } from 'react';

export default function Playlist({ children }) {
  const [playingIndex, setPlayingIndex] = useState(0);
  return (
    <section>
      <h2>Up next</h2>
      <ul>
        {~Children.map~(children, (child, index) => // Calls the arrow once per song, with the song and its index
          ~cloneElement~(child, { isPlaying: index === playingIndex }) // A copy of each song, with isPlaying added
        )}
      </ul>
      <button onClick={() => setPlayingIndex(i => (i + 1) % ~Children.count~(children))}> {/* 3 songs: after the last, back to 0 */}
        Next
      </button>
    </section>
  );
}
```

When the page opens, `playingIndex` is 0. So only the copy of Yesterday gets `isPlaying` set to `true`.

Each click on `Next` adds one to `playingIndex`. The percent sign gives the remainder of a division, and the count of children is 3. So after Hey Jude, 2 plus 1 gives 3, the remainder of 3 divided by 3 is 0, and the highlight goes back to Yesterday.

```page caption="After the user clicks Next twice: the highlight reaches Hey Jude, and the next click brings it back to Yesterday."
heading: Up next
line: Yesterday: The Beatles
line: Imagine: John Lennon
line: Hey Jude: The Beatles | good
line: [Next]
```

One more detail. `Children.map` returns an array, and every element in an array needs a key (Lesson 18). Our code writes no key, and React prints no warning. Why? Because `Children.map` gives the copies their keys by itself. React's docs say the keys of the returned elements are "automatically combined" with the keys of the original children.

```tree dir=right caption="How Playlist turns the three songs it received into three copies with isPlaying."
How `Playlist` gives each song `isPlaying`
- +1. Receives `children` [`children`] | The **three `<Song>` tags** written in `App.jsx`
- +2. Walks through them [`Children.map`] | Calls our arrow with **each song and its index**
- +3. Copies each song [`cloneElement`] | Adds **`isPlaying`**, `true` only at `playingIndex`
- +4. Renders the copies | Only the **playing song** gets the `playing` class
```

## PRINCIPLE | `Children.count`: sees only the JSX between the tags, so `<MoreSongs />` counts as one child

> [!PRINCIPLE]
> **Principle 3: Rendered Output: The `Children` Methods See Only the JSX Between the Tags**
>
> *`Children.map` and `Children.count` see only the elements written between the tags; a component such as `<MoreSongs />` or a Fragment there is one child, and the songs it renders are never seen.*
>
> The page can look the same while `Playlist` receives a different number of children. Move songs into a component of your own or into a Fragment, and `Playlist` counts fewer children and copies `isPlaying` onto the wrong element. The bug shows up in `Playlist`, a file nobody changed.
>
> **DO THIS:**
> ```jsx
> <Playlist>
>   <Song title="Yesterday" artist="The Beatles" />
>   ~<Song title="Imagine" artist="John Lennon" />~ {/* Each song written between the tags gets isPlaying */}
>   <Song title="Hey Jude" artist="The Beatles" />
> </Playlist>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Playlist>
>   <Song title="Yesterday" artist="The Beatles" />
>   ~<MoreSongs />~ {/* **WRONG:** one child for Playlist, so Imagine and Hey Jude never get isPlaying */}
> </Playlist>
> ```

Here is the smallest case. Between the tags sit one song and one component of our own:

```jsx title="One song and one component of our own between the Playlist tags"
<Playlist>
  <Song title="Yesterday" artist="The Beatles" />
  ~<MoreSongs />~ {/* One child for the Children methods, however many songs it renders */}
</Playlist>
```

Inside `Playlist`, `Children.count` returns 2. React's docs make the same point with a component of their own, `MoreRows`. The count stays 2 "Even if `MoreRows` renders 10 different items, or if it returns `null`".

Why? Remember that a tag is just an object, an element. `<MoreSongs />` is an object whose type is `MoreSongs`, and nothing more. The `Children` methods look at these objects. They never call `MoreSongs`. Only React calls a component, later, when it renders it. So while `Playlist` walks its children, the two songs inside `MoreSongs` do not exist yet.

React's docs call this walk a traversal: "The traversal does not go deeper than React elements: they don't get rendered, and their children aren't traversed." What a component returns when React calls it is its rendered output. The docs say it plainly: "There is no way to get the rendered output of an inner component."

### A teammate moves two songs into `MoreSongs`

**Beware! When old code copies its children, moving songs into a component of your own breaks the highlight, while the page still shows every song.**

A teammate moves the last two songs into `MoreSongs`, for example because they come from the same album. The Playlist file and the Song file do not change:

```jsx title="src/App.jsx"
import Playlist from './Playlist.jsx';
import Song from './Song.jsx';

function ~MoreSongs~() { // Our own component: the Children methods never call it
  return (
    <>
      <Song title="Imagine" artist="John Lennon" />
      <Song title="Hey Jude" artist="The Beatles" />
    </>
  );
}

export default function App() {
  return (
    <Playlist>
      <Song title="Yesterday" artist="The Beatles" />
      ~<MoreSongs />~ {/* The second and last child of Playlist */}
    </Playlist>
  );
}
```

The page opens, and nothing looks wrong. Three songs show, and Yesterday is highlighted. Here is what happens when the user starts clicking:
1. `Children.count` returns 2: one song and one `<MoreSongs />`.
2. The user clicks `Next`, and `playingIndex` becomes 1.
3. `Children.map` reaches the child at index 1, which is `<MoreSongs />`. It copies that child and sets `isPlaying` to true.
4. `MoreSongs` takes no props, so it never passes `isPlaying` on. Neither Imagine nor Hey Jude gets the `playing` class.
5. No song is highlighted.
6. The user clicks `Next` again. The remainder of 2 divided by 2 is 0, so Yesterday is highlighted again.
7. Hey Jude is never highlighted.

```page caption="With MoreSongs, after the user clicks Next once: no song is highlighted, and the cross marks Imagine, the song that should be."
heading: Up next
line: Yesterday: The Beatles
line: Imagine: John Lennon | bad
line: Hey Jude: The Beatles
line: [Next]
```

The developer then searches `MoreSongs` for the bug. But the cause is in `Playlist`, a file the change never touched. React's docs name this limit: "The limitation makes it hard to extract a component."

```tree caption="Three Song tags and one Song with MoreSongs show the same three songs, but Playlist receives three children in one and two in the other."
What `Playlist` receives between its tags
- +Three `<Song>` tags | `Children.count` returns **3** | Every song **gets `isPlaying`**
- !One `<Song>` and `<MoreSongs />` | `Children.count` returns **2** | `isPlaying` lands **on `MoreSongs`**, and no song inside it is highlighted
```

### VS | A Fragment vs. an array between the tags: the Fragment is one child, the array is not

A Fragment is one child too. Suppose the teammate writes a Fragment around the last two songs, with no component at all:

```jsx title="A Fragment around two songs between the Playlist tags"
<Playlist>
  <Song title="Yesterday" artist="The Beatles" />
  ~<>~ {/* A Fragment: one child, exactly like <MoreSongs /> */}
    <Song title="Imagine" artist="John Lennon" />
    <Song title="Hey Jude" artist="The Beatles" />
  </>
</Playlist>
```

For the `Children` methods, this is the exact same thing as `<MoreSongs />`. React's docs say "Fragments don't get traversed". So the Fragment is one child, the count is 2, and the same two songs lose the highlight.

This time React also complains. The Console stays quiet when the page opens. After each click on `Next`, React prints this error, because `cloneElement` gave the copy of the Fragment an `isPlaying` prop:

```devconsole width=full
x Invalid prop `isPlaying` supplied to `React.Fragment`. React.Fragment can only have `key`, `ref`, and `children` props.
```

An array is different. When the page writes the songs with `.map` between the tags, the `Children` methods walk into the array:

```jsx title="An array of songs between the Playlist tags"
<Playlist>
  {~songs.map~(song => <Song key={song.id} title={song.title} artist={song.artist} />)} {/* Three children: the array is walked through */}
</Playlist>
```

It may look like the Fragment, but it is NOT the same thing. React's docs say "Arrays don't count as individual nodes, but their children do". Here `Children.count` returns 3, and every song gets its copy with `isPlaying`.

## PRINCIPLE | Render prop: the page writes `isPlaying` itself, where everyone can see it

> [!PRINCIPLE]
> **Principle 4: Render Prop: `Playlist` Hands `isPlaying` to the Page Instead of Copying Songs**
>
> *Pass the songs as an array prop, and let `Playlist` call `renderSong(song, isPlaying)` for each one; the page writes `isPlaying={isPlaying}` on `<Song>` itself.*
>
> The page shows the same list as with `cloneElement`. The difference is where `isPlaying` is written. With a copy, it appears inside `Playlist`, and nobody who reads the page can find it. With a render prop, it appears on the `<Song>` tag in the App file, so a missing value is a bug in the file you are reading.
>
> **DO THIS:**
> ```jsx
> <Playlist
>   songs={songs}
>   renderSong={(song, ~isPlaying~) => ( // Takes both arguments that Playlist passes
>     <Song key={song.id} title={song.title} artist={song.artist} isPlaying={isPlaying} />
>   )}
> />
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Playlist
>   songs={songs}
>   renderSong={~song~ => ( // **WRONG:** one parameter, so isPlaying never reaches Song
>     <Song key={song.id} title={song.title} artist={song.artist} />
>   )}
> />
> ```

> [!DEFINITION]
> **What is a render prop?** [REVIEW] A render prop is a prop whose value is a function that returns JSX. The parent calls that function with its own data, and the function, written by the page, decides what to draw. So the parent owns the data, and the page owns the markup (Lesson 89).

React's docs give this as the first way out of the old code.

### VS | `cloneElement` vs. `renderSong`: the same screen, but only one shows the prop

Look at the one line inside `Playlist` that changes:

```jsx title="Inside Playlist: copying the child, and calling renderSong"
~cloneElement(child, { isPlaying: index === playingIndex })~ // Adds a prop the page never wrote
~renderSong(song, index === playingIndex)~ // Hands the value to the page, and the page writes the prop
```

For the user, it is the exact same thing. React's docs say "The end result is the same as with `cloneElement`". The list looks the same, and `Next` moves the highlight the same way.

For the developer, it is NOT the same thing:
1. **With `cloneElement`,** `Playlist` writes `isPlaying` onto a copy, where the page cannot see it.
2. **With `renderSong`,** `Playlist` hands the value to a function from the page, and the page writes `isPlaying={isPlaying}` on the tag itself.

React's docs prefer the second way "because it is more explicit". You can read in the App file where the value comes from.

### The playlist with songs as data and `renderSong`

The songs now live in an array, in a file of their own. Each song has an `id` for its key:

```js title="src/songs.js"
export const songs = [
  { id: 1, title: 'Yesterday', artist: 'The Beatles' },
  { id: 2, title: 'Imagine', artist: 'John Lennon' },
  { id: 3, title: 'Hey Jude', artist: 'The Beatles' },
];
```

`Playlist` no longer imports `Children` or `cloneElement`. It takes two props, `songs` and `renderSong`:

```jsx title="src/Playlist.jsx"
import { useState } from 'react';

export default function Playlist({ songs, renderSong }) {
  const [playingIndex, setPlayingIndex] = useState(0);
  return (
    <section>
      <h2>Up next</h2>
      <ul>
        {songs.map((song, index) => ~renderSong(song, index === playingIndex)~)} {/* true only for the playing song */}
      </ul>
      <button onClick={() => setPlayingIndex(i => (i + 1) % ~songs.length~)}> {/* Counts the data, not the JSX */}
        Next
      </button>
    </section>
  );
}
```

The App file passes both props. The arrow receives the song and `isPlaying`, and it writes every prop of `Song` in plain sight, the key included:

```jsx title="src/App.jsx"
import Playlist from './Playlist.jsx';
import Song from './Song.jsx';
import { songs } from './songs.js';

export default function App() {
  return (
    <Playlist
      songs={songs}
      renderSong={(song, ~isPlaying~) => ( // Playlist supplies isPlaying as the second argument
        <Song key={song.id} title={song.title} artist={song.artist} ~isPlaying={isPlaying}~ /> // The page writes the prop itself
      )}
    />
  );
}
```

The Song file does not change. It still reads `isPlaying` as a prop, but now the prop comes from a tag the reader can see.

`MoreSongs` is gone. The songs are data now, so there is no JSX between the tags to split. `songs.length` does the job that `Children.count` did, but it counts the songs themselves.

### A missing parameter now shows in the App file

A developer can still make a mistake with the render prop. But now the mistake sits in the file the developer is reading:

```jsx title="src/App.jsx"

```

## PRINCIPLE | Context: each `Song` reads `isPlaying` itself, through any component in between

> [!PRINCIPLE]
> **Principle 5: Context: Each Song Reads `isPlaying` from the Provider Around It**
>
> *Wrap each song in its own `<PlayingContext value={isPlaying}>`, and read the value in `Song` with `useContext(PlayingContext)`; the page passes no `isPlaying` at all.*
>
> The page looks the same as with the render prop. The difference is who carries the value. `Playlist` provides it around each song, and `Song` reads the closest provider above it. So a component of your own between them, which broke the copies of `cloneElement`, breaks nothing here.
>
> **DO THIS:**
> ```jsx
> {songs.map((song, index) => (
>   <PlayingContext key={song.id} ~value={index === playingIndex}~> {/* Each song gets its own true or false */}
>     {renderSong(song)}
>   </PlayingContext>
> ))}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <PlayingContext ~value={playingIndex}~> {/* **WRONG:** one number for every song, so no Song knows if it plays */}
>   <ul>{songs.map(song => renderSong(song))}</ul>
> </PlayingContext>
> ```

> [!DEFINITION]
> **What is context?** [REVIEW] Context lets a parent hand a value to every component below it, without a prop on each tag. You create it once with `createContext`, the parent wraps a part of the page in a provider with a `value`, and any component inside that part reads the value with `useContext`. Each reader gets the value of the closest provider above it (Lesson 28).

React's docs give context as the second way out of the old code.

### VS | A prop vs. `useContext`: the page writes the value, or `Song` reads it itself

Look at `Song` written both ways:

```jsx title="Song with isPlaying as a prop"
function Song({ title, artist, ~isPlaying~ }) { // The page must write isPlaying on every Song
  return <li className={isPlaying ? 'playing' : ''}>{title}: {artist}</li>;
}
```

```jsx title="Song with isPlaying read from PlayingContext"
function Song({ title, artist }) {
  const isPlaying = ~useContext(PlayingContext)~; // Playlist provides the value, and the page writes nothing
  return <li className={isPlaying ? 'playing' : ''}>{title}: {artist}</li>;
}
```

For the user, and for the markup of `Song`, it is the exact same thing. The row gets the `playing` class whenever the song plays.

The one difference is who carries the value. With the prop, the page writes it on every song. With context, `Playlist` provides it, and the page does not pass it at all.

Developers often think context is only for values the whole app shares, such as a theme. But a provider can wrap one single item of a list. Each `Song` reads the closest provider above it, so each song gets its own `isPlaying`.

### The playlist with one provider per song

A new file creates the context. Its default value is `false`:

```js title="src/PlayingContext.js"
import { createContext } from 'react';

export const PlayingContext = ~createContext(false)~; // false: a Song outside any Playlist is not playing
```

`Playlist` wraps each song in its own provider. The `value` is true for the playing song and false for the others. The `key` moves to the provider, because the provider is now the element that `.map` returns:

```jsx title="src/Playlist.jsx"
import { useState } from 'react';
import { PlayingContext } from './PlayingContext.js';

export default function Playlist({ songs, renderSong }) {
  const [playingIndex, setPlayingIndex] = useState(0);
  return (
    <section>
      <h2>Up next</h2>
      <ul>
        {songs.map((song, index) => (
          <PlayingContext key={song.id} ~value={index === playingIndex}~> {/* One provider per song, with its own value */}
            {renderSong(song)}
          </PlayingContext>
        ))}
      </ul>
      <button onClick={() => setPlayingIndex(i => (i + 1) % songs.length)}>
        Next
      </button>
    </section>
  );
}
```

`Song` drops the `isPlaying` prop and reads the context:

```jsx title="src/Song.jsx"
import { useContext } from 'react';
import { PlayingContext } from './PlayingContext.js';

export default function Song({ title, artist }) {
  const isPlaying = ~useContext(PlayingContext)~; // true only inside the provider of the playing song
  return <li className={isPlaying ? 'playing' : ''}>{title}: {artist}</li>;
}
```

The App file no longer mentions `isPlaying`. The render prop takes one argument and passes only the data of the song:

```jsx title="src/App.jsx"
import Playlist from './Playlist.jsx';
import Song from './Song.jsx';
import { songs } from './songs.js';

export default function App() {
  return (
    <Playlist
      songs={songs}
      renderSong={song => <Song title={song.title} artist={song.artist} />} // No isPlaying, and no key: both live in Playlist
    />
  );
}
```

React's docs describe the same shape: it "allows the calling component to not know or worry about passing" the value. In old code you also meet `<PlayingContext.Provider value={...}>`. That is how you provided a context before React 19, and it does the same job.

### A component of our own between `Playlist` and `Song`

**This time, a component of your own between `Playlist` and `Song` breaks nothing.** The same kind of change that broke the copies in Principle 3 leaves the highlight working, because context reaches any `Song` below the provider.

A teammate adds `SongRow`, a component that takes the whole song object, so the App file no longer spells out each field:

Here is what happens after the user clicks `Next` once:
1. `Playlist` wraps the `SongRow` of Imagine in a provider whose value is true.
2. `SongRow` renders a song and passes no `isPlaying` on.
3. That `Song`, one level lower, reads the context with `useContext`.
4. React finds the closest provider above that `Song` and returns its value, true.
5. Imagine is highlighted.

### One provider around the whole list does not work

A developer who moves to context often puts one provider around the whole list. But there is no single `isPlaying` for the whole list, so the developer provides `playingIndex` instead:

```jsx title="src/Playlist.jsx"
<PlayingContext ~value={playingIndex}~> {/* **WRONG:** every Song reads the same number, such as 1 */}
  <ul>{songs.map(song => renderSong(song))}</ul>
</PlayingContext>
```

Every `Song` now reads the same number, and no `Song` knows its own position in the list. The user sees it at once:
1. **When the page opens,** every `Song` reads 0. The value 0 counts as false, so no song is highlighted.
2. **After one click on `Next`,** every `Song` reads 1. The value 1 counts as true, so all three songs are highlighted.
3. **In the Console,** React prints the missing key warning. The key was on the providers, and now `.map` returns the songs with no key.

To compare the number with its own position, every song would need its index as a prop, and the value would be back in the page. React's docs use one provider per item, with the key on the provider, as our Playlist file does above.

## PRINCIPLE | `defaultProps`: React 19 ignores it on a function, so the default goes in the parameter list

> [!PRINCIPLE]
> **Principle 6: Default Values: React 19 Ignores `defaultProps` on a Function Component**
>
> *Write the default of a prop in the parameter list, such as `artist = 'Unknown artist'`; React 19 removes `defaultProps` from function components and keeps `static defaultProps` only for classes.*
>
> Old function components attached `defaultProps`, and React filled in missing props before it called them. React 19 stops doing that for functions, because JavaScript already has default parameters. The page keeps working. Only the rows with a missing prop change, and they show nothing where the default used to be.
>
> **DO THIS:**
> ```jsx
> export default function Song({ title, ~artist = 'Unknown artist'~ }) { // Track 3: Unknown artist
>   return <li>{title}: {artist}</li>;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> export default function Song({ title, artist }) {
>   return <li>{title}: {artist}</li>;
> }
> ~Song.defaultProps~ = { artist: 'Unknown artist' }; // **WRONG:** React 19 ignores it, and Track 3 shows a blank artist
> ```

Remember default parameters in plain JavaScript? `function greet(name = 'friend')` uses `'friend'` when the caller passes nothing. A component is a function, and its props arrive as one object, so the same default works on a destructured prop (Lesson 09).

Old code did not use it. It attached an object of default props to the component, `defaultProps`, and React filled those values in before it called the component.

### VS | `Song.defaultProps` vs. a default parameter: the same rule, but React 19 reads only one

Here are both ways:

```jsx title="A default for artist with Song.defaultProps"
function Song({ title, artist }) {
  return <li>{title}: {artist}</li>;
}
~Song.defaultProps~ = { artist: 'Unknown artist' }; // The old way: an object attached to the function
```

```jsx title="A default for artist in the parameter list"
function Song({ title, ~artist = 'Unknown artist'~ }) { // The way of today: a default parameter
  return <li>{title}: {artist}</li>;
}
```

For the rule, it is the exact same thing. Both fill in `artist` when the prop is missing or `undefined`, and both leave `null` alone.

For React 19, it is NOT the same thing. React 19 no longer reads `defaultProps` on a function component. The upgrade guide says: "We're also removing `defaultProps` from function components in place of ES6 default parameters." ES6 is the version of JavaScript that added default parameters.

### The untagged song after the upgrade

```jsx title="src/Song.jsx"
  const isPlaying = useContext(PlayingContext);
  return <li className={isPlaying ? 'playing' : ''}>{title}: {artist}</li>;
}
```

Now JavaScript finds `undefined` in `artist` while it unpacks the props, and it uses the default. The third row reads Track 3: Unknown artist again.

Look closely at the App file: it writes `artist={song.artist}` on every song. So for the third song, the prop is not missing. It is there, and its value is `undefined`. That changes nothing, because a default is used for `undefined` too.

### Missing, `undefined`, and `null`

Both kinds of default follow the same rule for these three tags:

```jsx title="A missing artist, an undefined artist, and a null artist"
<Song title="Track 3" /> {/* Missing: the row reads Track 3: Unknown artist */}
<Song title="Track 3" ~artist={undefined}~ /> {/* undefined: the row reads Track 3: Unknown artist */}
<Song title="Track 3" ~artist={null}~ /> {/* null: the default is not used, and the artist is blank */}
```

The default is used for a missing prop and for `undefined`. It is never used for `null`, because `null` is a value the page chose to pass (Lesson 09).

### Class components keep `static defaultProps`

Class components still support `defaultProps` in React 19. The upgrade guide gives the reason: "there is no ES6 alternative" for the props of a class.

In a class, you write the object inside the class with the JavaScript word `static`. It attaches the object to the class itself, just as `Song.defaultProps` attached it to the function (Lesson 96):

```jsx title="A class Song with static defaultProps"
class Song extends Component {
  ~static defaultProps~ = { artist: 'Unknown artist' }; // Still supported on classes in React 19

  render() {
    return <li>{this.props.title}: {this.props.artist}</li>;
  }
}
```

React's docs say this default "will be used for `undefined` and missing props, but not for `null` props". It is the same rule as above.

The same section of the upgrade guide also removes `propTypes`, the old checks of the type of each prop. React 19 silently ignores them, and the guide recommends TypeScript instead (Lesson 90).

```tree caption="Where a default for artist still works in React 19: in the parameter list and on a class, not in defaultProps on a function."
- !`defaultProps` on a function [`Song.defaultProps`] | **Ignored** in React 19 | The artist **is blank**
- +A default parameter [`artist = 'Unknown artist'`] | **JavaScript** fills it in | Used for **missing and `undefined`**, not for `null`
- +`static defaultProps` on a class [`static defaultProps`] | **Still supported** | Used for **missing and `undefined`**, not for `null`
```

## For the Interview

> **The Interview Question:** What were cloneElement, the Children utilities, and defaultProps for, and why were they abandoned?

### How to Answer Clearly in 30 Seconds

"All three let old code fill in props away from the place where the page wrote the tag.
1. **`cloneElement`** returns a copy of an element with some props replaced. Old code used it with `Children.map` to give every child a prop the page never wrote, such as `isPlaying` for the song that plays.
2. **The `Children` methods**, such as `map`, `count`, and `only`, walk through the opaque `children` prop. They see only the JSX between the tags, not what a component renders, so moving children into a component of your own breaks the parent. React's docs call this fragile, and cloning makes the data flow hard to trace. Both are Legacy React APIs today. The replacements are a render prop, which passes the value as an argument, or context, so the child reads the value itself.
3. **`defaultProps`** set default values for missing props. React 19 removed it from function components, because a default parameter in the destructured props does the same job. Classes keep `static defaultProps`. Either way, the default applies to a missing prop or `undefined`, never to `null`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Is `Children` the same thing as the `children` prop?"**
   No. `children` is the prop that holds whatever JSX the page writes between the tags of a component, and React's docs call it "good and encouraged". `Children` is an object that React exports, with methods such as `Children.map` and `Children.count` that walk through that prop. Old code needed them because `children` is opaque: with one child, it is that child and not an array, so `children.map` throws a `TypeError`.
2. **"Why does a component that uses `Children.map` and `cloneElement` break when you extract part of its children into another component?"**
   Because the `Children` methods see only the elements written between the tags. They never call the components they find, so `<MoreSongs />` is one child, whatever it renders, and so is a Fragment. The parent counts fewer children and adds the prop to `<MoreSongs />` instead of to the songs inside it. The page still shows every song, but none of the extracted songs is highlighted, and the bug lives in the parent, a file the change never touched. Context avoids it, because each child reads the closest provider above it, however deep it sits.
3. **"Does `defaultProps` still work in React 19?"**
   Only on class components, as `static defaultProps`. React 19 removed it from function components. The page keeps working, and a missing prop simply arrives as `undefined`. The fix is a default parameter, such as `artist = 'Unknown artist'` in the destructured props. Both kinds of default apply to a missing prop or `undefined`, and neither applies to `null`. `propTypes` were removed in the same release, and TypeScript is the recommended way to check the types of props.

```tree dir=right caption="Interview summary: the three old pieces, why each fell out of use, and what replaces it today."
- !The `Children` methods [`Children.map` `Children.count`] | See **only the JSX between the tags** | Replaced by an **array prop**
```
