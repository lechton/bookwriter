# Lecture 55: When memo Skips a Re-render, and When It Cannot

*(How do you tell React to skip a child whose props did not change, and why does it sometimes not skip?)*

> INTERVIEW QUESTION | ❱❱ MORE | When should you wrap a component in React.memo, and when does it fail to skip re-renders?

---

## VS | A Plain `Message` vs. a Memoized `Message`: React calls the plain one on every keystroke, and skips the memoized one while its props stay the same

> When the user types one letter in a chat, React calls every message component again, even a message whose props are exactly the same as last time. **Wrap the message component in `memo`, and React first compares each prop with its old value, and skips the component while every prop is the same**. It pays off only for a slow component, and it fails as soon as one prop is a new object or a new function on every render.

Remember Lesson 54? The user types `O` in the chat, the state changes, and React calls `ChatRoom` again. Then React calls every `Message` that `ChatRoom` returns, although each one gets the same `"Hi!"` as before. React does not check the props of a child. When the parent renders again, the child renders again. Usually that costs nothing you can feel.

But picture a chat with 500 messages, and each message is slow to render. Now every letter the user types calls 500 slow functions, and the letters appear late in the `<input>` field. You want to tell React: "Before you call this message again, look at its props. If they are the same as last time, do not call it. Keep what it returned last time."

That is exactly what `memo` does. **`memo` skips a component only while every prop is the same as last time.** Keep this sentence in mind. The whole lesson is about the word "same".

> [!DEFINITION]
> **A re-render.** [REVIEW] A re-render is React calling a component function again to get its new JSX. It happens for three reasons: the component's own state changed, its parent re-rendered, or a context it reads changed. By default, a child re-renders with its parent even when its props are exactly the same. A re-render is only a function call: React then changes only the DOM nodes that differ (Lesson 54).

> [!DEFINITION]
> **Object.is.** [REVIEW] `Object.is(a, b)` is the JavaScript check React uses to ask "is this the same value as before?". For strings and numbers, it compares the value: `Object.is('Hi!', 'Hi!')` is true. For objects and functions, it asks whether both are the very same object: two objects with the same fields give false (Lesson 37).

> [!DEFINITION]
> **StrictMode calls every component twice.** [REVIEW] Our project mounts `<App />` inside `<StrictMode>`. In development, StrictMode calls every component function twice on purpose, so every `console.log` inside a component prints two lines. In production, each component is called once (Lesson 47).

### The Smallest Chat with memo

Here is the smallest chat that shows it: one message above an empty `<input>` field. The message component is wrapped in `memo`:

```jsx title="One memoized message and an input field"
import { memo, useState } from 'react';

const Message = ~memo~(function Message({ text }) { // memo wraps our message component
  console.log('Message rendered:', text);
  return <li>{text}</li>;
});

function ChatRoom() {
  const [text, setText] = useState('');
  return (
    <>
      <ul>
        <Message ~text="Hi!"~ /> {/* The same string on every render of ChatRoom */}
      </ul>
      <input value={text} onChange={e => setText(e.target.value)} />
    </>
  );
}
```

When the page opens, the Console already has two lines. That is StrictMode calling `Message` twice:

```page width=text caption="The smallest chat when the page opens: one message, Hi!, above an empty input field, and two lines in the Console."
line: Hi!
form:
  field:  |
log: Message rendered: Hi!
log: Message rendered: Hi!
```

Now the user types `OK`. Each letter renders `ChatRoom` again. And still the Console holds only the two lines from the page load:

```page width=text caption="The smallest chat after the user types OK: the Console still holds only the two lines from the page load."
line: Hi!
form:
  field:  | OK | good
log: Message rendered: Hi!
log: Message rendered: Hi!
```

React skipped `Message` at both letters. Why? Because `text` was `"Hi!"` last time, and it is `"Hi!"` again.

Now we add one more prop to the message: a `Delete` handler, written as an empty arrow function for now:

```jsx title="The same memoized message with one more prop, a function"
<Message text="Hi!" ~onDelete={() => {}}~ /> {/* A new function on every render of ChatRoom */}
```

We reload the page, and the user types `OK` again. This time each letter adds two more lines, as if `memo` were not there:

```page width=text caption="With the onDelete arrow function, after the user types OK: two lines from the page load, then two more for each letter."
line: Hi!
form:
  field:  | OK | good
log: Message rendered: Hi!
log: Message rendered: Hi!
log: Message rendered: Hi!
log: Message rendered: Hi!
log: Message rendered: Hi!
log: Message rendered: Hi!
```

The empty arrow function looks like the same value each time. **It may look the same, but it is NOT the same thing!** The string `"Hi!"` is the same value on every render. The arrow function is not. Every time `ChatRoom` runs, JavaScript creates a brand-new function, and `Object.is` says it is different from the old one. One changed prop is enough, so React renders the message again.

```tree caption="A memoized component is skipped while every prop is the same as last time, and rendered again when one prop is new."
What React does with a memoized `Message` when `ChatRoom` re-renders
- +Every prop is the same as last time [`text="Hi!"`] | The string **`"Hi!"` equals** the old `"Hi!"` | React **skips** `Message` and keeps the last result
- !One prop is new [`onDelete`] | An arrow function written in `ChatRoom` is **new on every render** | React **renders** `Message` again, as if `memo` were not there
```

### Why It Is Called memo

A memo is a short note you write down so you do not have to work something out again. Computer science calls this **memoization**. React's docs explain it plainly: to memoize is, "in other words, cache". A cache keeps the last result and reuses it while the inputs stay the same.

In plain JavaScript, you would write such a cache yourself. You keep the last input and the last result, and you compare before you do the work:

```js title="Plain JavaScript: a cache you write yourself"
let lastText = null;
let lastResult = null;

function cachedMessage(text) {
  if (~Object.is(text, lastText)~) return lastResult; // The same input as last time: reuse the old result
  lastText = text;
  lastResult = renderMessage(text);
  return lastResult;
}
```

`memo` writes this cache for you. For a component, the inputs are its props. So React compares every prop, one by one, and calls your component only when at least one prop is different.

> [!DEFINITION]
> **memo and a memoized component.** [NEW] `memo` is a function that React provides. You give it your component, and it returns a new component, which React's docs call a memoized component. When the parent re-renders, React first compares each new prop of the memoized component with its old value by `Object.is`. If every prop is the same, React skips the call and keeps the last result. If one prop is different, React calls the component as usual (Lesson 55).

### What the User Feels

The user feels this in the `<input>` field. In a chat with a long history, each letter the user types re-renders every message. When the messages are many, or slow to render, the letters appear late in the field. React's docs say that such re-rendering "makes the typing feel janky".

1. **With `memo` and props that stay the same**, React skips the messages, and the field keeps up with the user.
2. **With one prop that is new on every render**, React renders the messages again anyway. The user sees the same lag, and the code is harder to read. The docs say it plainly: "a single value that's 'always new' is enough to break memoization for an entire component."

### The Rule of Thumb: measure first, and keep every prop the same

**`memo` skips a component only while every prop is the same as last time. Add it only where a measurement shows a lag, and make sure no prop is a new object or a new function on every render.**

A senior developer knows the four classic mistakes with `memo`:
1. **Thinking `memo` stops every re-render.** Then an arrow function prop, a context change, or the component's own state renders it, and the developer is surprised.
2. **Thinking React looks inside an object prop.** Two objects with the same fields do not count as equal. React never looks inside.
3. **Wrapping components without a measured lag.** The code grows, and the user sees no difference.
4. **Letting the app depend on `memo` to work correctly.** `memo` is only a speed-up. The docs: "If your code doesn't work without it, find the underlying problem and fix it first."

When a child re-renders often with the same props, there are four ways to handle it:
1. **Measure first, and leave it.** Measure the render with `<Profiler>` (as seen in Lesson 54). If the user feels no lag, `memo` is unnecessary.
2. **Move the fast-changing state lower, or pass JSX as `children`.** The docs list these two first, because they make memoization unnecessary. Lesson 58 covers them.
3. **Wrap the slow child in `memo`, and give it props that stay the same.** This fits a component that "re-renders often with the same exact props, and its re-rendering logic is expensive". This lesson covers it. Objects and functions built from state also need `useMemo` and `useCallback`, which Lessons 56 and 57 cover.
4. **Turn on React Compiler.** It applies the equivalent of `memo` to every component at build time. Lesson 63 covers it.

```tree caption="Four ways developers handle a child that re-renders often with the same props."
A child re-renders often with the same props
- +1. Measure first with `<Profiler>` | Fits when the user feels **no lag** | No code to add
- +2. Move state lower or pass `children` | The docs list these **first** | Lesson 58
- +3. Wrap the slow child in `memo` | Fits a child that renders **often**, with the **same props**, and **slowly** | This lesson
- +4. React Compiler | Applies the equivalent of `memo` **at build time** | Lesson 63
```

**PRINCIPLES:** `memo` skips a component only while every prop is the same as last time. Four principles follow:
1. **Principle 1: memo Skips the Message While Its Props Stay the Same.** Wrap the message in `memo`, and use the component `memo` returns. When the user types, `ChatRoom` re-renders, and React skips the messages whose `text` stayed the same.
2. **Principle 2: Object.is Compares Each Prop.** A string or a number is the same when its value is the same. An object written inside the parent is new on every render, so it is never the same.
3. **Principle 3: memo Checks Props Only.** A memoized message still re-renders when a context it reads changes, or when its own state changes.
4. **Principle 4: A Function Written in the Parent Breaks memo.** An arrow function written in `ChatRoom` is new on every render. Pass it to a memoized message, and the message renders again at every letter.

## PRINCIPLE | `memo`: React skips the component while every prop stays the same

> [!PRINCIPLE]
> **Principle 1: memo: React Skips a Memoized Component While Its Props Stay the Same**
>
> *Wrap a component in `memo` and use the component it returns; when the parent re-renders, React skips it as long as every prop is the same as last time.*
>
> Every letter the user types re-renders `ChatRoom`, and without `memo` React calls every message again, though each message gets the same `text`. `memo` does not change our function. It returns a new, memoized component, and React checks its props before calling it. If we export the plain function instead, React skips nothing.
>
> **DO THIS:**
> ```jsx
> const Message = memo(function Message({ text }) {
>   return <li>{text}</li>;
> });
> export default ~Message~; // Exports the memoized component: messages with the same text are skipped
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function Message({ text }) {
>   return <li>{text}</li>;
> }
> memo(Message);
> export default ~Message~; // **WRONG:** exports the plain function, so every message renders at every letter
> ```

### VS | `function Message` vs. `memo(function Message)`: the same page, but only the memoized one is skipped

Here are two ways to write the message. Both have the same body: they log a line and return one `<li>`. The one difference is `memo` around the function:

```jsx title="Message as a plain function"
function ~Message~({ text }) { // React calls it on every render of ChatRoom
  console.log('Message rendered:', text);
  return <li>{text}</li>;
}
```

```jsx title="Message wrapped in memo"
const Message = ~memo~(function Message({ text }) { // React skips it while text stays the same
  console.log('Message rendered:', text);
  return <li>{text}</li>;
});
```

When the page loads, both show `Hi!`, and both print `Message rendered: Hi!`. **It may look the same at first, but it is NOT the same thing!** The difference shows at the first letter the user types:
- **With the plain function**, the letter re-renders `ChatRoom`, and React calls `Message` again. The Console prints `Message rendered: Hi!` once more.
- **With `memo`**, the letter re-renders `ChatRoom` too. But React sees that `text` is still `"Hi!"`, and it does not call `Message`. No new line appears.

```tree caption="A plain Message and a memoized Message show the same page, but only the memoized one is skipped when the user types."
What happens to `Message` when the user types in the field
- !Plain function [`function Message`] | React calls it **on every render** of `ChatRoom` | New `Message rendered:` lines **at every letter**
- +Wrapped in `memo` [`memo`] | React compares `text` with the old `text` | Same string, so React **skips** it: **no new line**
```

### memo Returns a New Component

`memo` is a function, and we import it from `'react'`. It does not change your component. It takes it, and returns a new one. React's docs say it exactly: "`memo` does not modify this component, but returns a new, memoized component instead."

So you must use what `memo` returns. That is the component React checks before calling.

The interview question says `React.memo`, and our code says `memo`. **Yes, it is the exact same function!** `React.memo` reads it from the `React` object:

```jsx title="memo imported by name, and memo read from the React object"
import React, { memo } from 'react';

function MessageRow({ text }) {
  return <li>{text}</li>;
}

const Message = ~memo~(MessageRow); // memo imported by name, as React's docs write it
const SameMessage = ~React.memo~(MessageRow); // The same function, read from the React object
```

### The Message File Exports What memo Returns

Now we build the first step of our chat room. The message file wraps the function in `memo`, and exports what `memo` returns:

```jsx title="src/components/Message.jsx"
import { ~memo~ } from 'react'; // memo is a function React provides

const Message = ~memo~(function Message({ text }) { // memo returns a new, memoized component
  console.log('Message rendered:', text);
  return <li>{text}</li>;
});

export default ~Message~; // Exports the memoized component, not our plain function
```

`Message` is now a constant, not a function declaration, because it holds what `memo` returned. Here is what happens, in order:
1. When the file loads, JavaScript runs `memo` once, with our function inside it.
2. `memo` returns a new, memoized component.
3. `const Message` keeps that new component, and the file exports it.
4. `ChatRoom` imports it and writes `<Message />` as before. No line of `ChatRoom` changes.

Inside `memo`, we still give our function its name, `function Message`. Every example in React's docs keeps that name too.

`ChatRoom` holds the messages and the text of the field, as in Lesson 54, and it has the `Send` button. It renders one `<Message>` per message, exactly as it would render a plain component. For now, `App` only renders `<ChatRoom />`. The theme comes back in Principle 3:

```jsx title="src/components/ChatRoom.jsx"
import { useState } from 'react';
import Message from './Message.jsx';

const initialMessages = [
  { id: 1, text: 'Hi!' },
  { id: 2, text: 'Lunch at 12?' },
  { id: 3, text: 'Sure' },
];
let nextId = 4;

export default function ChatRoom() {
  const [messages, setMessages] = useState(initialMessages);
  const [text, setText] = useState('');
  console.log('ChatRoom rendered');

  function handleSend() {
    setMessages([...messages, { id: ~nextId++~, text }]); // Gives the new message the id 4, then 5, and so on
    setText('');
  }

  return (
    <section>
      <ul>
        {messages.map(m => (
          <Message key={m.id} ~text={m.text}~ /> // Each message gets a string, the same on every render
        ))}
      </ul>
      <input value={text} onChange={e => setText(e.target.value)} />
      <button onClick={handleSend}>Send</button>
    </section>
  );
}
```

Why does `nextId` start at `4`? Because the three first messages use the ids `1`, `2`, and `3`. Lesson 54 made the id from the length of the list plus one. Later in this lesson, each message gets a `Delete` button. After a delete, the length can repeat an id that is still in the list. A counter outside the component never repeats one (as seen in Lesson 19).

### The Real Mistake: memo Is Called, and Its Result Is Thrown Away

A developer sees `Message rendered:` lines at every letter and decides to wrap the message in `memo`. They write the call, but they still export the plain function:

```jsx title="src/components/Message.jsx" bad="6,7"
function Message({ text }) {
  console.log('Message rendered:', text);
  return <li>{text}</li>;
}

~memo(Message)~; // **WRONG:** the memoized component is created, then thrown away
export default ~Message~; // **WRONG:** exports the plain function, so every message still renders at every letter
```

`ChatRoom` imports the plain function, and the lines keep appearing at every letter. The developer decides that `memo` does not work. It works, but nobody uses what it returned. The docs' instruction is: "wrap it in `memo` and use the value that it returns in place of your original component."

```jsx title="src/components/Message.jsx" good="6"
function Message({ text }) {
  console.log('Message rendered:', text);
  return <li>{text}</li>;
}

export default ~memo(Message)~; // Exports the memoized component that memo returns
```

### When memo Is Worth Adding

`memo` changes nothing on the page. It only saves React the work of calling a component again. So it is worth adding only when that work is something the user feels.

1. **It fits a component that renders often, with the same props, and slowly.** The docs: "Optimizing with `memo` is only valuable when your component re-renders often with the same exact props, and its re-rendering logic is expensive."
2. **Measure before you add it.** Use `<Profiler>` and `actualDuration` (as seen in Lesson 54), with React running in production mode. The docs: "If there is no perceptible lag when your component re-renders, `memo` is unnecessary."
3. **It is a speed-up, not a promise.** The docs call memoization "a performance optimization, not a guarantee". React may still call a memoized component.
4. **It relies on pure rendering.** A memoized component must return the same JSX for the same props (as seen in Lesson 14). The docs: "By using `memo`, you are telling React that your component complies with this requirement."
5. **Wrapping everything costs readability.** The docs say there is "no significant harm" in memoizing every component, but "code becomes less readable".
6. **With React Compiler, you rarely write it.** The compiler adds the same skipping for you, so "you typically don't need `React.memo` anymore". Lesson 63 covers it.

## PRINCIPLE | `Object.is` on each prop: the same string passes, a new object never does

> [!PRINCIPLE]
> **Principle 2: Shallow Equality: React Compares Each Prop by Object.is**
>
> *React compares each prop with its old value by `Object.is`: strings, numbers, and booleans by value, and objects, arrays, and functions by identity.*
>
> Two objects with the same fields are still two objects. JavaScript builds an object written on the tag again on every render of the parent, so a memoized child renders again at every letter, and the user sees the same lag as without `memo`. Pass a string, the object already in state, or an object created once outside the component.
>
> **DO THIS:**
> ```jsx
> <Message key={m.id} ~text={m.text}~ /> // A string equals the old string, so React skips the message
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Message key={m.id} ~message={{ text: m.text }}~ /> // **WRONG:** a new object on every render, so every message renders again
> ```

### VS | The Same Value vs. the Same Object: a string compares by value, an object by identity

Remember the question React asks for every prop: "Is this the same as last time?" React answers it with `Object.is` (as seen in Lesson 37). Here is what `Object.is` answers for a number, a string, and two objects:

```js title="Object.is with a number, a string, and two objects"
Object.is(3, 3); // true
Object.is('Hi!', 'Hi!'); // true
Object.is(~{ text: 'Hi!' }, { text: 'Hi!' }~); // false: two different objects with the same field
```

The answer depends on the kind of value:
- **Strings, numbers, and booleans** are the same when their value is the same. MDN calls these values **primitives**. Two strings `'Hi!'` are always equal.
- **Objects, arrays, and functions** are the same only when they are the very same one. Two objects with the same fields are still two objects in memory. React's docs call two values that are the very same object **reference-equal**. Comparing this way is comparing by **identity**: which object it is, not what it holds.

You already know this from plain JavaScript. Each pair of curly braces builds a new object, even when you write the same fields:

```js title="Plain JavaScript: the same fields, two objects"
const a = { text: 'Hi!' };
const b = { text: 'Hi!' };
console.log(~a === b~); // false: a and b are two different objects
console.log(~a === a~); // true: the very same object
```

> [!DEFINITION]
> **Shallow equality.** [NEW] React compares the props of a memoized component one prop at a time, with `Object.is`, and never looks inside an object. React's docs call this shallow equality: "your component re-renders whenever any prop is not shallowly equal to what it was previously." Shallow means one level deep, the same word as in the shallow copy (Lesson 17). So a string prop is the same when its text is the same, and an object prop is the same only when it is the very same object (Lesson 55).

```tree caption="How Object.is compares a prop with its old value: primitives by value, objects, arrays, and functions by identity."
How React compares one prop with its old value
- +Primitive [`'Hi!'` `3` `true`] | Compared **by value** | `'Hi!'` and `'Hi!'` are **the same**
- !Object, array, or function | Compared **by identity**, never by its fields | Two objects with the same fields are **not the same**
```

### VS | `text={m.text}` vs. `message={{ text: m.text }}` vs. `message={m}`: a string, a new object, and the object from state

All three tags below put `Hi!` on the screen. Each one gives the message its text in a different shape:

```jsx title="Three ways to give a memoized message its text"
<Message ~text={m.text}~ /> {/* 1. A string: the same value on every render */}
<Message ~message={{ text: m.text }}~ /> {/* 2. A new object on every render of ChatRoom */}
<Message ~message={m}~ /> {/* 3. The object from state: the same object until our code replaces it */}
```

Here is what React sees when `ChatRoom` re-renders after the user types a letter:
1. **With `text={m.text}`**, the message gets the string `'Hi!'`, which equals the old `'Hi!'`. React skips it.
2. **With `message={{ text: m.text }}`**, the outer curly braces step into JavaScript, and the inner ones write an object right there (as seen in Lesson 3). React's docs call an object written this way an **object literal**, and "the `{}` object literal always creates a new object." JavaScript runs that literal again each time `ChatRoom` runs. So the message gets a new object, and React renders it again.
3. **With `message={m}`**, the message gets the object that sits in the `messages` state. Typing changes `text`, not `messages`, so `m` is the very same object as last time. React skips it.

The first two tags show the same `Hi!`. **It may look the same, but it is NOT the same thing!** A string written the same way is the same value. An object literal is a new object every time.

The last two tags both pass an object with the field `text: 'Hi!'`. **They are NOT the same thing either!** JavaScript builds the object literal during each render. The object `m` was built once and stored in state.

### What Happens When Message Takes an Object Literal

**The page looks exactly the same, and every message renders again at every letter.** Suppose a developer changes the message to take one `message` object instead of a string:

```jsx title="src/components/Message.jsx: an object prop"
const Message = memo(function Message({ ~message~ }) { // The message now takes one object
  console.log('Message rendered:', message.text);
  return <li>{message.text}</li>;
});
```

And `ChatRoom` builds that object on the tag:

```jsx title="src/components/ChatRoom.jsx: an object prop"
{messages.map(m => (
  <Message key={m.id} ~message={{ text: m.text }}~ /> // **WRONG:** a new object for each message on every render
))}
```

Here is what happens, in order:
1. The page loads and shows `Hi!`, `Lunch at 12?`, and `Sure`, as before.
2. The user types `O`. `ChatRoom` re-renders and writes three new object literals.
3. React compares each new object with the old one by `Object.is`. Each is a different object, so each `message` prop changed.
4. React calls `Message` three times. The three `Message rendered:` lines are back, though `memo` is still there.

```devconsole caption="With an object literal as the message prop, one letter renders ChatRoom and all three messages again."
ChatRoom rendered | letter O
ChatRoom rendered | Strict Mode copy
Message rendered: Hi!
Message rendered: Hi! | Strict Mode copy
Message rendered: Lunch at 12?
Message rendered: Lunch at 12? | Strict Mode copy
Message rendered: Sure
Message rendered: Sure | Strict Mode copy
```

Now pass `message={m}` instead, and the same letter prints only the two `ChatRoom rendered` lines. Why? `m` is the parameter of the `map` callback, and JavaScript passes it each item of `messages` in turn (as seen in Lesson 18). Each item is an object our code put in state. It stays the same object until `setMessages` receives a new array with a new item in its place (as seen in Lesson 19).

We go back to `text={m.text}`. The message needs only its text, and a string is the simplest prop to keep the same. React's docs give the same advice: accept "the minimum necessary information" in props, such as "individual values instead of a whole object".

### The Real Mistake: a Style Object on a Memoized Message

A developer wants the messages to show their text in gray. `Message` takes a `style` prop and puts it on its `<li>`, and the developer writes the color on the tag:

```jsx title="src/components/ChatRoom.jsx"
<Message key={m.id} text={m.text} ~style={{ color: 'gray' }}~ /> // **WRONG:** a new style object at every letter
```

JavaScript builds a new style object each time `ChatRoom` runs. So every message renders again at every letter, and the lag stays. The developer then removes `memo`, believing it does nothing.

The fix: this object never changes, so it can live outside the component, like `nextId`. JavaScript creates it once, when the file loads:

```jsx title="src/components/ChatRoom.jsx"
const grayText = { color: 'gray' }; // Created once, above the component

<Message key={m.id} text={m.text} ~style={grayText}~ /> // The same object on every render, so memo still skips
```

The same rule holds for JSX. React turns each JSX tag into an object. For a skip, the docs say, the node has to "actually be the same object, not merely look the same in code". So JSX that the parent writes between the opening and closing tags of a memoized component arrives in `children` as a new object on every render. The memoized component renders again each time.

When the object must be built from state, `useMemo` keeps it the same between renders. Lesson 56 covers it.

### The Second Argument of memo: arePropsEqual

`memo` takes a second argument, rarely used: a function that decides for React whether the old and new props count as equal. React's docs call it `arePropsEqual`:

```jsx title="A custom comparison function as the second argument of memo"
const Message = memo(function Message({ message }) {
  return <li>{message.text}</li>;
}, ~arePropsEqual~); // React calls this function instead of comparing each prop by Object.is

function arePropsEqual(oldProps, newProps) {
  return ~oldProps.message.text === newProps.message.text~; // true: React skips the message
}
```

It must return `true` only when the new props would give the same result on the screen. The docs add two warnings:
1. **Compare every prop, functions included.** A function prop remembers the props and state of the parent render that created it. If the comparison ignores it, the message keeps calling an old function that still sees old state.
2. **Never compare deeply.** A check that walks through every field "can become incredibly slow and can freeze your app for many seconds". Measure with the Performance panel that the check is faster than the render it saves.

Our chat passes a string, so it needs no custom comparison at all.

## PRINCIPLE | `useContext` and `useState`: they still render a memoized component, because `memo` checks props only

> [!PRINCIPLE]
> **Principle 3: memo Checks Props Only: Context and Own State Still Re-render**
>
> *`memo` compares only the props from the parent; a memoized component still re-renders when a context it reads changes or when its own state changes.*
>
> When the user clicks `Toggle theme`, React renders the memoized message that reads the theme again, though its `text` stayed the same. That render is wanted: without it, the messages would stay light after the user asked for dark. `memo` removes only the parent cause of a re-render, and only while the props stay the same.
>
> **DO THIS:**
> ```jsx
> const Message = memo(function Message({ text }) {
>   const theme = ~useContext(ThemeContext)~; // A new theme renders the message again, as it should
>   return <li className={theme}>{text}</li>;
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <ThemeContext ~value={{ theme, setTheme }}~> {/* **WRONG:** a new object on every render of App re-renders every message that reads it */}
>   <ChatRoom />
> </ThemeContext>
> ```

### memo Checks Props, Not Context

`memo` compares only the props that the parent writes on the tag. A context that the component reads does not travel through those props, and neither does the component's own state. So `memo` never sees them, and they still re-render the component.

Here is the memoized message with one line more. It reads the theme from a context (as seen in Lesson 28):

```jsx title="A memoized message that reads a context"
const Message = memo(function Message({ text }) {
  const theme = ~useContext(ThemeContext)~; // Not a prop: memo never compares it
  console.log('Message rendered:', text);
  return <li className={theme}>{text}</li>;
});
```

When the theme changes, React renders this message again, even though `text` stayed the same. And that is exactly what we want. When the user switches to the dark theme, the messages must turn dark. A message that skipped this render would stay light after the user asked for dark.

Readers usually go wrong here: "It is memoized, so nothing can re-render it." React's docs say the opposite: "Even with `memo`, your component will re-render if its own state changes or if a context that it's using changes." And: "Memoization only has to do with props that are passed to the component from its parent."

Of the three causes of a re-render (as seen in Lesson 54), `memo` removes only one:

```tree caption="The three causes of a re-render: memo blocks the parent cause while the props stay the same, and leaves the other two."
Three causes of a re-render for a memoized `Message`
- +The parent re-renders [`ChatRoom`] | `memo` compares the props | **Skipped** while every prop is the same
- !A context it reads changes [`useContext`] | Not a prop, so `memo` **never sees it** | **Renders again**
- !Its own state changes [`useState`] | Not a prop, so `memo` **never sees it** | **Renders again**
```

### The Theme Comes Back

We bring back the theme of the chat room (as seen in Lesson 54). The context file is the same:

```js title="src/ThemeContext.js"
import { createContext } from 'react';

export const ThemeContext = ~createContext('light')~; // The theme is light when no provider is above
```

`App` holds the theme in state, renders the `Toggle theme` button, and puts the provider around `ChatRoom`:

```jsx title="src/App.jsx"
import { useState } from 'react';
import { ThemeContext } from './ThemeContext.js';
import ChatRoom from './components/ChatRoom.jsx';

export default function App() {
  const [theme, setTheme] = useState('light');

  return (
    <ThemeContext ~value={theme}~> {/* Every message below reads this value */}
      <button onClick={() => setTheme(theme === 'light' ? 'dark' : 'light')}>Toggle theme</button>
      <ChatRoom />
    </ThemeContext>
  );
}
```

The memoized message reads the theme and puts it on its `<li>` as a class:

```jsx title="src/components/Message.jsx"
import { memo, useContext } from 'react';
import { ThemeContext } from '../ThemeContext.js';

const Message = memo(function Message({ text }) {
  const theme = ~useContext(ThemeContext)~; // React finds the closest provider above and returns its value
  console.log('Message rendered:', text);
  return <li className={theme}>{text}</li>;
});

export default Message;
```

The stylesheet gives each class its colors, and `main.jsx` imports it:

```css title="src/index.css"

  background: white;
  color: black;
}

.dark {
  background: #222;
  color: white;
}
```

### What Happens When the User Clicks Toggle theme

**The props of every message stay the same, and React renders every message anyway, because the theme changed.** Here is what happens, in order:

1. The user clicks `Toggle theme`. `setTheme('dark')` re-renders `App`.
2. React re-renders `ChatRoom`, because its parent re-rendered and `ChatRoom` is not memoized. The Console prints `ChatRoom rendered`.
3. `ChatRoom` returns three `<Message>` tags with the same `text`. By props alone, `memo` would skip them.
4. But the theme in the provider changed from `'light'` to `'dark'`, and each message reads that context.
5. So React calls `Message` three times anyway, and the Console prints the three `Message rendered:` lines.
6. React then changes the `class` of the three `<li>` nodes to `dark`, and the messages turn dark.

```devconsole caption="One click on Toggle theme renders ChatRoom and all three memoized messages, because each message reads the theme."

Message rendered: Hi! | Strict Mode copy
```

Even if `ChatRoom` were memoized too and skipped, the messages would still render. React sends the new theme straight to every component that reads it. React's docs: "Skipping re-renders with `memo` does not prevent the children receiving fresh context values."

Then the user types in the field. No `Message rendered:` line appears, because neither the props nor the theme changed. React skips the messages again.

The component's own state works the same way. Suppose each message had a like button, with its own `liked` state inside `Message`. A click by the user on it re-renders that message, `memo` or not. The docs: "Even when a component is memoized, it will still re-render when its own state changes."

### The Real Mistake: an Object as the Value of the Provider

A developer wants the messages to be able to change the theme too. So they pass both the theme and its setter in one object:

```jsx title="src/App.jsx"
<ThemeContext ~value={{ theme, setTheme }}~> {/* **WRONG:** a new object on every render of App */}
```

Now each time `App` re-renders, for any reason, the provider gets a new object (as seen in Lesson 54). This is Principle 2 again: a new object is never the same. Every memoized component that reads the context renders again, and the developer blames `memo`. React's docs say that each time, "this will be a different object pointing at a different function". So React "will also have to re-render all components deep in the tree" that read the context. Lesson 59 covers how to keep a context value the same.

## PRINCIPLE | `onDelete={() => ...}`: a new function on every render, so `memo` skips nothing

> [!PRINCIPLE]
> **Principle 4: Function Props: A Function Created in the Parent Breaks memo**
>
> *A function written inside the parent, on the tag or in its body, is a new function on every render, so a memoized child that receives it renders every time.*
>
> The `Delete` button works and the page looks right, so nothing warns the developer. But each letter the user types re-renders `ChatRoom`, which writes a new arrow function for every message, and React renders every message again. Declare a function outside the component when it needs nothing from it, and keep the others the same with `useCallback`.
>
> **DO THIS:**
> ```jsx
> function formatTime(date) {
>   return date.toLocaleTimeString();
> }
>
> <Message key={m.id} text={m.text} ~formatTime={formatTime}~ /> // Declared outside ChatRoom: the same function on every render
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <Message key={m.id} text={m.text} ~onDelete={() => handleDelete(m.id)}~ /> // **WRONG:** a new function on every render, so memo skips nothing
> ```

### VS | An Arrow Function on the Tag vs. a Named Function Inside ChatRoom: both are new on every render

Remember what we saw at the start: an empty arrow function was enough to bring every line back. A function is an object in JavaScript. And like an object literal, a function written inside `ChatRoom` is a new function every time `ChatRoom` runs. That holds for an arrow function on the tag, and for a named function declared in the body of the component:

```jsx title="Two ways to give each message its Delete handler"
<Message text={m.text} ~onDelete={() => handleDelete(m.id)}~ /> {/* 1. A new arrow function for each message on every render */}
<Message text={m.text} id={m.id} ~onDelete={handleDelete}~ /> {/* 2. handleDelete is declared inside ChatRoom, so it is new on every render too */}
```

The two tags look different. One writes an arrow function, the other passes a name. Many developers believe the named function stays the same each time. For `memo`, **it is the exact same problem!** JavaScript creates both again each time `ChatRoom` runs, so both are a different function each time. React's docs: "a `function () {}` or `() => {}` always creates a different function, similar to how the `{}` object literal always creates a new object."

The code of the function is the same on every render. But the same code is not the same function. The docs: "if you create a new function when rendering the parent component, React will consider it to have changed even if the function has the same definition."

### The Delete Button on Each Message

We add a `Delete` button to each message. `ChatRoom` gets a handler that removes one message by its id (as seen in Lesson 19). It passes the handler to each message as a callback prop (as seen in Lesson 23):

```jsx title="src/components/ChatRoom.jsx" startLine="21"
  function handleDelete(id) {
    setMessages(messages.filter(m => m.id !== id));
  }

  return (
    <section>
      <ul>
        {messages.map(m => (
          <Message key={m.id} text={m.text} ~onDelete={() => handleDelete(m.id)}~ /> // A new arrow function for each message on every render
        ))}
      </ul>
```

The message takes `onDelete` and gives it to its button:

```jsx title="src/components/Message.jsx" startLine="4"
const Message = memo(function Message({ text, ~onDelete~ }) { // The function ChatRoom wrote on the tag
  const theme = useContext(ThemeContext);
  console.log('Message rendered:', text);
  return (
    <li className={theme}>
      {text} <button onClick={onDelete}>Delete</button>
    </li>
  );
});
```

How does each arrow function know which message to delete? It remembers the `m` of the `map` call that created it. MDN calls a function that remembers the variables around the place where it was created a **closure**. So the arrow function on the `Hi!` message always calls `handleDelete(1)`.

### What Happens on the Next Letter

**The `Delete` button works, the page looks right, and every message renders again at every letter. Only the Console shows it.** Here is what happens, in order:

1. The page loads. Each message shows its text and a `Delete` button.
2. The user clicks `Delete` on `Lunch at 12?`, and the message disappears. The feature works.
3. The user types `O` in the field, and `ChatRoom` re-renders.
4. `ChatRoom` runs `map` again and writes a new arrow function for each message.
5. React compares the props of each message. `text` is the same, but `onDelete` is a different function, and one changed prop is enough.
6. React calls `Message` for every message, as if `memo` were not there.

```page width=text caption="The chat room after the user clicks Delete on Lunch at 12? and types O: the message is gone, and the page looks right."
line: [Toggle theme]
line: Hi! [Delete]
line: Sure [Delete]
form:
  field:  | O | good
  button: Send
```

```devconsole caption="One letter after the Delete button was added: ChatRoom and every message render again."

ChatRoom rendered | Strict Mode copy
Message rendered: Hi!
Message rendered: Hi! | Strict Mode copy
Message rendered: Sure
Message rendered: Sure | Strict Mode copy
```

The page looks the same as with a working `memo`. Only the Console, or `<Profiler>` (as seen in Lesson 54), shows that every message renders again.

### The Real Mistake: the Shortest Way to Pass an Item

Our `onDelete` is the exact mistake that React's own docs show on their React Compiler page. There, a memoized `Item` gets `onClick={() => handleClick(item)}`, the shortest way to pass each item to its click handler. The docs: "the arrow function `() => handleClick(item)` creates a new function every time the component renders. This means that `Item` will always receive a new `onClick` prop, breaking memoization."

The docs add one more fact. Suppose `handleClick` itself is kept the same between renders with `useCallback`. The items still render again while the arrow function stays on the tag, because the arrow function around it is still new. Lesson 57 shows how to fix that.

### How to Keep a Function the Same Between Renders

The docs give two ways: "either declare it outside your component so that it never changes, or `useCallback` to cache its definition between re-renders."

1. **A function that uses nothing from the component** can be declared outside it, like `nextId`. One example is a `formatTime` helper that turns the time a message was sent into a time of day. JavaScript creates it once, when the file loads, so it is the same function on every render.
2. **Our `handleDelete` reads and changes the messages**, so it must live inside `ChatRoom`. Keeping it the same between renders is the job of `useCallback`, which Lesson 57 covers.
3. **A `set` function from `useState` is already the same on every render.** The docs say it "has a stable identity". So passing `setMessages` itself to a memoized message does not break `memo`.
4. **React Compiler** "is able to optimize this correctly with or without the arrow function". Lesson 63 covers it.

Our chat room keeps the arrow function. So at the end of this lesson, `memo` on `Message` skips nothing while the user types. We leave the page this way on purpose: Lesson 57 keeps `onDelete` the same between renders.

**With the arrow function in `onDelete`, every action of the user renders every message.** The last column shows what would happen if `onDelete` stayed the same function on every render, which is the goal of Lesson 57:

| What the user does | `ChatRoom` | The messages, with the arrow function in `onDelete` | The messages, if `onDelete` stayed the same function |
| :--- | :--- | :--- | :--- |
| Types a letter in the field | Renders, because `text` changed | Every message renders, because `onDelete` is new | Every message is skipped |
| Clicks `Send` | Renders, because `messages` and `text` changed | Every message renders, the new one included | Only the new message renders |
| Clicks `Toggle theme` | Renders, because its parent `App` rendered | Every message renders | Every message renders, because the theme changed |
| Clicks `Delete` on one message | Renders, because `messages` changed | Every remaining message renders | Every remaining message is skipped |

Here is the whole lesson in one table:

| Aspect | The Common Habit | The React Rule |
| :--- | :--- | :--- |
| **Wrapping** | Call `memo` and keep using the plain function | Use the memoized component that `memo` returns |
| **Comparing props** | Expect React to compare what is inside an object | React compares each prop by `Object.is`: primitives by value, objects by identity |
| **Objects on the tag** | Write `{{ }}` on the tag of a memoized child | Pass a string, the object from state, or a constant created outside the component |
| **Context and own state** | Expect a memoized component never to re-render | A context it reads and its own state still re-render it |
| **Functions on the tag** | Write an arrow function on each memoized message | A function created during the render is new each time, so keep it the same or leave `memo` out |
| **When to use it** | Wrap every component just in case | Measure first; wrap a child that renders often, with the same props, and slowly |

Remember the one sentence of this lesson. **`memo` skips a component only while every prop is the same as last time, and a new object or a new function is never the same.**

## For the Interview

> **The Interview Question:** When should you wrap a component in React.memo, and when does it fail to skip re-renders?

### How to Answer Clearly in 30 Seconds

"`memo` wraps a component and returns a memoized version. When the parent re-renders, React skips that component as long as every prop is the same as last time. React compares each prop with its old value by `Object.is`, which the docs call shallow equality. Strings and numbers are equal by value, but objects, arrays, and functions are equal only when they are the very same one. I wrap a component in `memo` when it re-renders often with the same props and its render is slow, and I measure that first with the Profiler. It fails to skip in three cases:
1. **A prop is new on every render**: an object literal, an array, or an arrow function written in the parent, such as `onDelete={() => handleDelete(m.id)}`.
2. **A context it reads changes**: `memo` checks props only.
3. **Its own state changes**: `memo` does not stop that either."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"What exactly does `memo` compare?"**
   Each prop, one by one, with `Object.is`. It never looks inside an object, so `{ text: 'Hi!' }` written on the tag is a new object on every render and counts as changed. An object kept in state stays the same object until our code replaces it, so passing it keeps `memo` working. `memo` also takes a second argument, `arePropsEqual`, for a custom comparison. It is rare: it must compare every prop, functions included, and a deep comparison can freeze the app.
2. **"Your memoized message still re-renders at every letter. Why?"**
   Usually one prop is new on every render. The classic case is an arrow function on each item, such as `onClick={() => handleClick(item)}`, or a style object written as `style={{ color: 'gray' }}`. One changed prop is enough. The fixes: pass primitives, and move constants and functions that need nothing from the component outside it. For values built from state, use `useMemo` and `useCallback`. The other two causes are a context the message reads and its own state.
3. **"Should you wrap every component in `memo`?"**
   No. `memo` is a performance optimization, not a guarantee, and code that only works with it has a bug. Wrapping everything does little harm, but it makes the code harder to read. Measure first, in production mode, and wrap only the children that render often with the same props and slowly. With React Compiler, `memo` is usually not needed at all.

```tree dir=right caption="Interview summary: when memo skips a re-render and when it cannot."
A memoized component when its parent re-renders
- +Every prop is the same by `Object.is` [`text={m.text}`] | React **skips** the component
- !One prop is an object or function created in the parent [`message={{ text: m.text }}`] | React **renders it again**, as if `memo` were not there
- !A context it reads or its own state changes [`useContext` `useState`] | `memo` **never sees it**, so React **renders it again**
```
