# Lecture 77: How React Decides Which DOM Nodes to Keep

*(After a click renders the page again, why does the text the user typed sometimes stay, and sometimes disappear?)*

> INTERVIEW QUESTION | ❱❱❱ ADVANCED | When React re-renders, how does the reconciliation algorithm decide which DOM nodes to update?

---

## VS | The same type and key vs. a different type or key: React keeps the real element, or throws it away and builds a new one

> You know that a click changes state, and React calls your component again to get new JSX. **React then compares the new JSX with the JSX of the previous render, place by place, and asks two questions at each place: is the type the same, and is the key the same?** Two yes answers keep the real element on the page, with the text the user typed in it, and one no throws that element away and builds a new, empty one.

Remember how plain JavaScript changes a page. You grab an element and you change it yourself: `document.getElementById('message').className = 'dark'`. The element stays the same element. Only its class changes, and whatever the user typed inside it is still there.

In React, you never touch the page. Your component returns JSX, and on every render it returns new JSX: a new tree of plain objects, the React elements from Lesson 76. React then has to turn that new tree into changes on the real page. It has two choices:
1. **Build every element again from scratch.** That is slow, and every `<input>` field would lose what the user typed on every render.
2. **Keep the elements that are still the same, and change only what differs.** That is what React does.

So after every render, React puts the new tree next to the tree from the previous render and walks through both, place by place. At each place it asks two questions: **is the type the same, and is the key the same?** Two yes answers: React keeps the real element. One no: React throws it away and builds a new one.

**Why:** These two questions decide whether the user keeps what they typed, and both mistakes are silent, with no message in the Console:
1. **A tag that changes wipes the text.** A developer wraps a field in a `<div>` for the day theme and in a `<section>` for the night theme. The user clicks `Night mode`, and the message they were typing is gone.
2. **A missing key keeps the wrong text.** In a chat, the user types a message to John and then clicks on Mia. With no key, React keeps the same field, so John's message now sits in Mia's field, and one click on Send sends it to the wrong person. React's docs put it plainly: "You don't want to let the user send a message they already typed to a wrong person due to an accidental click."

### Two Questions at Every Place in the Tree

Here is the smallest example. A `<textarea>` is an input field with several lines. It sits inside a `<div>`, and a click on `Night mode` changes only the class of the `<div>`:

```jsx title="The JSX before the click, and the JSX after the click"
<div ~className="light"~><textarea /></div> // Before: a textarea inside a div
<div ~className="dark"~><textarea /></div> // After: still a textarea inside a div
```

React walks through the two trees from the top:
1. **At the top**, the old tree has a `<div>`, and the new tree has a `<div>`. Same type, no key on either. React keeps the real `<div>` and changes its `class` from `light` to `dark`.
2. **Inside the `<div>`, first child**, the old tree has a `<textarea>`, and the new tree has a `<textarea>`. Same type, no key. React keeps the real `<textarea>`, and the text inside it stays.

```tree caption="The two questions React asks at each place of the tree, and what it does with the real element."
At each place, React asks: is the type the same, and is the key the same? [`type` `key`]
- +Both answers yes [`<div>` then `<div>`] | React **keeps the real element** | It changes **only what differs**, such as one `class`
- !Either answer no [`<section>` after `<div>`] | React **throws away the element and everything inside it** | It **builds new elements** from scratch
```

> [!DEFINITION]
> **DOM node.** [REVIEW] A DOM node is a real element on the page, the same thing `document.getElementById` returns in plain JavaScript; React creates the DOM nodes from your React elements, and it creates or changes them only during the commit, after your component has returned its JSX (Lesson 13).

> [!DEFINITION]
> **Type and key.** [REVIEW] Every React element is a plain object with a `type` and a `key`; for a lowercase tag such as `<div>`, the type is the string `'div'`, for a component such as `<Profile />` it is the function `Profile`, and an element written without a `key` has the key `null` (Lesson 76).

> [!DEFINITION]
> **Reconciliation.** [NEW] Reconciliation is React's word for this comparison: on every re-render, React puts the new tree of elements next to the tree of the previous render, pairs them place by place, and decides for each real DOM node whether to keep it or to build a new one, the same way you reconcile your bank statement with your own list of expenses, line by line (Lesson 77).

### Where Readers Usually Go Wrong

Readers usually go wrong in three places:
1. **They think React compares the new JSX with the real page.** It does not. React compares two trees of objects: the one your components return now and the one they returned on the previous render. At each place, it reads only the type and the key.
2. **They think two tags that look the same on the screen are the same to React.** A `<section className="dark">` and a `<div className="dark">` with the same CSS look exactly the same. To React, they are two different types, `'section'` and `'div'`. One keeps the text, and the other wipes it.
3. **They think two `if` branches give two different fields.** React never reads your `if`. React's docs: "React doesn't know where you place the conditions in your function. All it 'sees' is the tree you return."

### The Rule of Thumb: same type, same key, same DOM node

**Ask one question about every place in your JSX: after the click, is it still the same type with the same key? If yes, React keeps the DOM node and what the user typed in it. If no, React builds a new one, empty.**

So when you want to keep what the user typed, keep the same tag at that place. When you want a fresh, empty field, give it a new key.

Our page is a small chat. It has three buttons, `John`, `Mia`, and `Night mode`, and one message field below them:

The project has four files:

One detail makes this page a perfect test. The `<textarea>` has no `value` and no state for its text. The browser keeps what the user types inside the real `<textarea>` DOM node itself (Lesson 40). So the text tells us exactly what React did:
1. **The text survives the click:** React kept that exact DOM node.
2. **The text is gone:** React threw the DOM node away and created a new one.

We call the text the user typed but has not sent yet the draft. In every example, the user types the draft `See you at 6` to John. The previews show the buttons and the field, not the colors.

**PRINCIPLES:** On every re-render, React compares the new tree with the previous one and decides, at each place, whether to keep the DOM node or to build a new one. Four principles follow:
1. **Principle 1: React Pairs the Elements by Position, Never by Your if.** Two `if` branches that both return a `<textarea>` inside a `<div>` give the same `<textarea>`, and the draft stays.
2. **Principle 2: A Different Type Throws Away the Whole Subtree.** A `<section>` in place of the `<div>` wipes the draft.
3. **Principle 3: The Same Type and Key Keep the DOM Node.** One `<div>` whose `className` changes keeps the draft, and React changes only the `class`.
4. **Principle 4: A Different Key Builds a New DOM Node.** With `key={contact}`, Mia gets an empty field.

## PRINCIPLE | `if` branches: React never sees them, it pairs the elements by position

> [!PRINCIPLE]
> **Principle 1: Position: React Pairs the New Tree with the Previous One**
>
> *On every re-render, React pairs each element of the new tree with the element at the same position in the previous tree, by order inside each parent; the `if` that built the tree plays no part.*
>
> Two `if` branches look like two different fields, but React never sees the branches. It sees only the tree the component returns. When both branches put a `<textarea>` at the same position, React keeps the old DOM node and the draft in it. That is right for a theme, and wrong when each branch is meant for another person.
>
> **DO THIS:**
> ```jsx
> if (dark) {
>   return <div className="dark"><textarea /></div>;
> }
> return <div className="light">~<textarea />~</div>; // The same position in both branches: the draft stays after Night mode
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> if (contact === 'Mia') {
>   return ~<textarea placeholder="Message Mia" />~; // **WRONG:** not a fresh field: John's draft stays in it
> }
> return <textarea placeholder="Message John" />;
> ```

### VS | Two `return` lines vs. one `return`: the exact same tree

Here is the smallest code that changes the theme. The `Night mode` button flips `dark` between `false` and `true`, and the component returns one of two lines:

```jsx title="Two return lines, one for each theme"
if (dark) {
  return <div ~className="dark"~><textarea /></div>; // Night: a textarea inside a div
}
return <div ~className="light"~><textarea /></div>; // Day: a textarea inside a div
```

Now compare them with one `return` whose `className` changes:

```jsx title="One return with a className that changes"
return <div ~className={dark ? 'dark' : 'light'}~><textarea /></div>; // A textarea inside a div, in both themes
```

Two `return` lines look like two different fields. They are not. Both versions return a `<div>` with a `<textarea>` inside it, and React sees only that tree, never the `if` that built it. So the user types `Hi`, clicks `Night mode`, and in both versions the field still shows `Hi`.

### What React does after the click

Here is what happens, in order:
1. The user types `Hi`. The browser keeps the text inside the `<textarea>` DOM node.
2. The user clicks `Night mode`. `setDark` makes `dark` true, and React calls the component again (Lesson 13).
3. This time the first `return` runs. The component returns a new tree: a `<div>` with a `<textarea>` inside.
4. React compares it with the previous tree. At the top: a `<div>` before, a `<div>` now. Its first child: a `<textarea>` before, a `<textarea>` now.
5. React keeps both DOM nodes. It changes one attribute only: the `class` of the `<div>`, from `light` to `dark`.

```tree caption="The previous tree and the new tree after the click on Night mode, compared position by position."
Two trees React puts side by side after the click on `Night mode`
- +The previous render [`<div className="light">` `<textarea />`] | At the top: a **`<div>`** | Its first child: a **`<textarea>`**
- +The new render [`<div className="dark">` `<textarea />`] | At the top: a **`<div>`**, the same type | Its first child: a **`<textarea>`**, the same type
```

How does React know which old element goes with which new element? By **position**: the place of the element in the tree, such as "the first child of the `<div>`". Inside each parent, React reads the children in order, first to last, and pairs the first with the first, the second with the second. React's docs call the position an "address": "To React, these two counters have the same 'address': the first child of the first child of the root. This is how React matches them up between the previous and next renders, regardless of how you structure your logic."

Notice what React compares. Not the new tree with the real page, and not your code. Two trees of objects. React touches the real page only afterwards, during the commit (Lesson 13).

### The same `<textarea>` for John and Mia

This trips developers up on real pages. A developer writes one `if` branch for John and one for Mia, such as `if (contact === 'Mia')`, and each branch returns a `<textarea>` with its own placeholder. The developer expects Mia's branch to give a fresh, empty field. It does not. Both branches put a `<textarea>` at the same position, so React keeps the same DOM node, and John's draft stays. React's docs show the same surprise with a counter and a checkbox: "You might expect the state to reset when you tick checkbox, but it doesn't!" Principle 4 shows the fix.

### The chat page with two `if` branches

Here is the first version of our chat page. `App` keeps `dark` in state, shows a `Night mode` button, and returns one of two branches:

```jsx title="src/App.jsx"

  return (
    <>
      <button onClick={() => setDark(!dark)}>Night mode</button>
      <div className="light">
        <textarea placeholder="Message John" />
      </div>
    </>
  );
}
```

```css title="src/App.css"
.dark { background: black; color: white; padding: 12px; }
textarea { background: inherit; color: inherit; }
```

The user types `See you at 6` and clicks `Night mode`. The page turns dark, and the draft stays:

## PRINCIPLE | `<section>` in place of `<div>`: a different type throws away the DOM node and everything inside it

> [!PRINCIPLE]
> **Principle 2: Type: A Different Type Throws Away the Whole Subtree**
>
> *When the element at a position has a different type than on the previous render, React removes the old DOM node and every node inside it, loses their state, and creates new nodes from scratch.*
>
> A `<section>` and a `<div>` with the same class look the same on the screen. To React, they are the types `'section'` and `'div'`. When the type at a position changes, React does not look inside: it throws away the old wrapper with everything in it. The `<textarea>` inside is built again, empty, and the user loses what they typed.
>
> **DO THIS:**
> ```jsx
> <div className={dark ? 'dark' : 'light'}>
>   ~<textarea />~ {/* The wrapper stays a div: the draft stays */}
> </div>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {dark
>   ? ~<section className="dark">~<textarea /></section> // **WRONG:** the type changes from div to section and wipes the draft
>   : <div className="light"><textarea /></div>}
> ```

### VS | `<section className="dark">` vs. `<div className="dark">`: the same on the screen, two different types for React

The day wrapper stays a `<div className="light">`. Here are two ways to write the night wrapper. Both hold the same `<textarea>` and use the same `dark` class. The one difference is the tag:

```jsx title="The night wrapper written as a section, and as a div"
<section className="dark"><textarea /></section> {/* After Night mode: the field is empty */}
<div className="dark"><textarea /></div> {/* After Night mode: the draft stays */}
```

On the screen, both draw the same dark area with the same field. To React, they are not the same thing. A lowercase JSX tag gives the element a `type` that is the tag name as a string (Lesson 76). So the section has the type `'section'`, and the div has the type `'div'`. At the wrapper's position, React compares the old type with the new type, and `'section'` is not `'div'`.

### What React does after the click

Here is what happens, in order:
1. The user types `See you at 6` in the field inside the light `<div>`.
2. The user clicks `Night mode`, and `dark` becomes `true`.
3. The new tree has a `<section>` at the position where the old tree had a `<div>`.
4. The types differ, so React removes the old `<div>` and the `<textarea>` inside it from the page. The text the browser kept in that `<textarea>` goes with it.
5. React creates a new `<section>` and a new, empty `<textarea>`.
6. The user sees the dark colors and an empty field.

Something that can be tricky: the `<textarea>` itself did not change. Both trees have the same `<textarea>` inside the wrapper, and it still lost the draft. Why? React reads the tree from the top down. At the wrapper's position it found a new type, so it threw the wrapper away, and with it every DOM node inside. There is no old `<textarea>` left to keep.

React's docs call a node together with every node inside it a **subtree**: "when you render a different component in the same position, it resets the state of its entire subtree." When the wrapper goes, its whole subtree goes with it.

```tree caption="What React does at the wrapper's position when the type changes from div to section."
The wrapper's position after the click on `Night mode`
- +The previous render [`<div className="light">`] | Type **`'div'`** | Holds the `<textarea>` with **`See you at 6`**
- !The new render [`<section className="dark">`] | Type **`'section'`**, a different type | React **removes the div and its whole subtree**, then creates a new section and an **empty `<textarea>`**
```

### The same rule for components

A component is a type too. In `<Feed />`, the type is the function `Feed`, and React compares it the same way. So when one position shows `<Feed />` and later shows `<Profile />`, React throws away everything the feed built and builds the profile from scratch. React's docs: "when you move from rendering `<Feed>` to the `<Profile>` page, React won't attempt to re-use them."

This is a real mistake on real pages. A developer wraps a part of the page in a `<div>` for one condition and in a `<section>` for the other, and the part inside is the same in both. The user types, the condition changes, and what the user typed is gone. React's docs show it with a counter: "The counter state gets reset when you click the checkbox." Their reason: when the `section` was removed from the DOM, the whole tree below it was destroyed as well, with the `Counter` and its state.

## PRINCIPLE | `className` on the same `<div>`: React keeps the DOM node and changes only the `class`

> [!PRINCIPLE]
> **Principle 3: Reuse: The Same Type and Key Keep the DOM Node**
>
> *When the element at a position has the same type and the same key as on the previous render, React keeps the DOM node and changes only the attributes and text that differ; whatever the browser holds in that node stays.*
>
> A re-render makes new React elements, not new DOM nodes. When the wrapper stays a `<div>` and only its `className` changes, React keeps the `<div>` and the `<textarea>` inside it. It changes one attribute, and the user keeps the message they were typing.
>
> **DO THIS:**
> ```jsx
> <div ~className={dark ? 'dark' : 'light'}~> {/* Same type: React changes only the class */}
>   <textarea />
> </div>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> {dark
>   ? ~<section className="dark">~<textarea /></section> // **WRONG:** a new type at the same position rebuilds the field
>   : <div className="light"><textarea /></div>}
> ```

### One `<div>` whose `className` changes

The fix for Principle 2: keep the same tag, and change only its attribute.

```jsx title="One div whose className changes"
<div ~className={dark ? 'dark' : 'light'}~> {/* Night or day: always a div */}
  <textarea />
</div>
```

The user types `See you at 6` and clicks `Night mode`. The page turns dark, and the draft stays. At the wrapper's position, React finds a `<div>` before the click and a `<div>` after it. Only the `class` differs. So React **reuses** the DOM node: it keeps the existing node instead of creating a new one. Reuse is the word React's docs use.

Many readers think that a re-render rebuilds the page, as if "React called the component again" meant "React made the DOM again". It does not. Calling `App` again only makes new React elements, plain objects (Lesson 54). React then compares them with the previous ones, reuses each DOM node whose type and key match, and changes only what differs. React's docs: "React only changes the DOM nodes if there's a difference between renders."

Both versions draw the same dark colors, and only one keeps the draft:
1. **With a `<section>` for night,** the type at the wrapper's position changes from `'div'` to `'section'`, so React throws away the wrapper and the field inside it.
2. **With one `<div>` and a changing `className`,** the type stays `'div'`, so React keeps the DOM node and changes only its `class`.

Two things on the page come from that one kept DOM node:
1. **The draft.** The browser stores what the user typed inside the `<textarea>` DOM node. React did not create a new node, so the browser still has the text.
2. **The new colors.** React changed one attribute, `class`, on the kept `<div>`. The CSS file did the rest.

React's docs describe the same thing with a clock that renders again every second, next to an `<input>` field: React "sees that the `<input>` appears in the JSX in the same place as last time, so React doesn't touch the `<input>`". The text the user typed in that field stays while the clock ticks.

### The chat page with one `<div>`

We replace the two branches with one `<div>`:

## PRINCIPLE | `key={contact}`: a new key at the same position builds a new, empty `<textarea>`

> [!PRINCIPLE]
> **Principle 4: Key: A Different Key Builds a New DOM Node**
>
> *A `key` becomes part of the position; when the type at a position is the same but the key is different, React re-creates the DOM node and resets its state, as it does for a new type.*
>
> Without a key, the `<textarea>` for John and the `<textarea>` for Mia have the same type and the same key, `null`, at the same position. React keeps the DOM node, changes only the placeholder, and John's draft stays in Mia's field. With `key={contact}`, the key changes from `'John'` to `'Mia'`, so React builds a new, empty field for Mia.
>
> **DO THIS:**
> ```jsx
> <textarea ~key={contact}~ placeholder={'Message ' + contact} /> {/* A new key for Mia: a new, empty field */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> ~<textarea placeholder={'Message ' + contact} />~ {/* **WRONG:** the same field for every contact, so John's draft goes to Mia */}
> ```

### VS | No `key` vs. `key={contact}`: the same field for everyone, or a new field for each contact

Now the chat page gets two contacts. `contact` is a state variable that the `John` and `Mia` buttons set, and the placeholder names the contact. Here is the message field written two ways. The one difference is the `key`:

```jsx title="The message field with no key, and with key={contact}"
<textarea placeholder={'Message ' + contact} /> {/* No key: John's draft stays when the user clicks Mia */}
<textarea ~key={contact}~ placeholder={'Message ' + contact} /> {/* key={contact}: Mia gets an empty field */}
```

The user types `See you at 6` to John and clicks `Mia`:
1. **With no `key`,** the field still holds `See you at 6`. React did change the placeholder to `Message Mia`, but the user cannot see it, because a placeholder shows only while the field is empty. The screen looks as if nothing happened, and John's draft is now in Mia's field.
2. **With `key={contact}`,** the user sees an empty field that says `Message Mia`.

When the page opens, both versions look the same: an empty field that says `Message John`. The difference shows only after the click. With the key, John's field and Mia's field are two different DOM nodes to React.

### Why John's draft lands in Mia's field

With no key, John's draft lands in Mia's field because React kept the same `<textarea>` DOM node and changed only its placeholder. Here is what happens, in order:
1. The user types `See you at 6` in the field that says `Message John`.
2. The user clicks `Mia`, and `contact` becomes `'Mia'`.
3. The new tree has a `<textarea>` at the same position as before. It has no key, and neither did the old one: an element written without a `key` has the key `null` (Lesson 76).
4. Same type, same key. So React keeps the old `<textarea>` DOM node and changes only its `placeholder` attribute to `Message Mia`.
5. The user sees John's draft in the field that now writes to Mia.

This is the same mistake as the two `if` branches for John and Mia in Principle 1. React's docs show it in their own chat: "the input state is preserved because the `<Chat>` is rendered at the same position in the tree."

### A key becomes part of the position

The key fixes it. React's docs: "Specifying a `key` tells React to use the `key` itself as part of the position, instead of their order within the parent." So at the same position, React now checks the key after the type:
1. Before the click, the `<textarea>` has the key `'John'`.
2. After the click, the `<textarea>` at the same position has the key `'Mia'`.
3. The type is the same, but the key is different. React does what it does for a new type: it removes the old `<textarea>` with John's draft and creates a new, empty one.

React's docs call this **re-creating** the DOM node: building a new node instead of reusing the old one. In their words: "React will also re-create the DOM elements instead of reusing them." And for the chat: "Now switching the recipient always clears the text field."

```tree caption="What React does with the message field when the user clicks Mia, with no key and with key={contact}."
The message field after the click on `Mia`
- !With no `key` [`<textarea placeholder={'Message ' + contact} />`] | Key **`null`** before and after the click | React **keeps the DOM node** and changes only the placeholder: **John's draft stays**
- +With `key={contact}` [`<textarea key={contact} />`] | Key **`'John'`** before, **`'Mia'`** after | React **re-creates the DOM node**: Mia gets an **empty field**
```

The two panels look alike, because the key does not appear in the Elements panel. It is not an HTML attribute, and it is not a prop. React keeps it on the element only for this comparison (Lesson 18).

Something that can be tricky: when the user clicks `John` again, the key changes back to `'John'`, and React creates another new, empty field. John's old draft does not come back, because its DOM node is gone. To keep one draft for each contact, keep the drafts in state in the parent (Lesson 25).

### How React checks each position

After every click, React walks through the new tree and the previous one, position by position, and asks the same questions in the same order:

```tree dir=right caption="The order in which React decides what to do with the DOM node at each position after a re-render."
How React decides at each position
- +1. Pair by position | React pairs each new element with the old element at the **same position**, by **order inside the parent**
- +2. Check the type | A **different type**: React removes the old node and **its whole subtree**, and creates new ones
- +3. Check the key | The same type but a **different key**: React **re-creates the node**, as for a new type
- +4. Keep the node | **Same type and same key**: React **reuses the DOM node** and changes **only what differs**
```

### What the user does, and what React does

| What the user does | What changes in the new tree | What React does | What the user sees |
| :--- | :--- | :--- | :--- |
| **Clicks `Night mode`, with two `if` branches** | Nothing at the field's position: still a `<textarea>` inside a `<div>` | Keeps both DOM nodes and changes the `class` of the `<div>` | The draft stays |
| **Clicks `Night mode`, with a `<section>` for night** | The wrapper's type changes from `'div'` to `'section'` | Removes the wrapper and its whole subtree, and creates new nodes | The draft is gone |
| **Clicks `Night mode`, with one `<div>`** | Only the `className` of the `<div>` | Keeps both DOM nodes and changes one attribute | The draft stays |
| **Clicks `Mia`, with no `key`** | Only the `placeholder` of the `<textarea>` | Keeps the `<textarea>` and changes its placeholder | John's draft stays in Mia's field |
| **Clicks `Mia`, with `key={contact}`** | The key of the `<textarea>` changes from `'John'` to `'Mia'` | Re-creates the `<textarea>` | Mia gets an empty field |

Remember the one sentence of this lesson. **On every render, React compares the new tree with the previous one, position by position: the same type and the same key keep the DOM node and what the user typed in it, and a different type or a different key builds a new one, empty.**

## For the Interview

> **The Interview Question:** When React re-renders, how does the reconciliation algorithm decide which DOM nodes to update?

### How to Answer Clearly in 30 Seconds

"On a re-render, React compares the tree of elements the components return now with the tree from the previous render, not with the real DOM. That comparison is called reconciliation. React pairs the elements by position, by order inside each parent, and the conditions in the code play no part. At each position it makes two checks:
1. **The type**: if the type is different, such as a `<section>` where a `<div>` stood, or one component in place of another, React destroys the old DOM node, its whole subtree, and its state, and creates new nodes.
2. **The key**: a key is part of the position, so the same type with a different key is treated the same way, and React re-creates the node.

When both match, React reuses the DOM node and applies only the changes, such as one attribute or one text. So in practice, I keep the same tag at a position to keep what the user typed, and I give a `key` when a part of the page must start fresh for a different item."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Does React compare the new render with the real DOM, node by node?"**
   **No.** React compares two trees of elements: the one the components return now and the one from the previous render. At each position it reads only the type and the key, which is cheap, and it skips the parts that did not change. React touches the DOM only afterwards, during the commit, and only where something differs. React's docs list this among the reasons React must call your components itself: "More efficient reconciliation." The internal structures React uses to walk the tree are called Fiber, and Lesson 78 covers them.
2. **"Why does a component defined inside another component lose what the user typed on every render?"**
   Because its type changes on every render. Each time the parent runs, JavaScript creates a new inner function, and React's docs say it plainly: "a *different* `MyTextField` function is created for every render of `MyComponent`." At that position, the component type is a new function every time, so React destroys the old DOM nodes and their state and creates new ones (Lesson 04). The fix is to define every component at the top level of the file.
3. **"What happens if you write `key={Math.random()}`?"**
   React gets a new key on every render, so the key at that position never matches the previous one. React re-creates the DOM nodes every time, and every field loses its text. React's docs: "This will cause keys to never match up between renders, leading to all your components and DOM being recreated every time." A key must stay the same for the same item, such as a contact's name or id. Keys also only need to be unique among siblings: "They only specify the position *within the parent*." In a list, the key is how React matches moved, inserted, and deleted rows (Lesson 61).

```tree caption="Interview summary: what the type and the key decide at each position on a re-render."
What decides whether React keeps a DOM node
- +Same type and same key [`<div className="dark">` after `<div className="light">`] | React **reuses the node** | Only the **changed attributes** are updated; typed text **stays**
- !Different type [`<section>` after `<div>`] | React **destroys the node and its subtree** | New nodes are created; typed text is **gone**
- !Same type, different key [`key="Mia"` after `key="John"`] | React **re-creates the node** | A new, **empty** field; its state is **reset**
```
