## VS | A Filter in the Body vs. the Same Filter in `useMemo`: the plain line runs on every render, the `useMemo` line reuses the last result

> React runs every line of a component again on every re-render, so a filter over a long list of messages runs again on every letter the user types, even in a field that has nothing to do with the search. **Wrap the calculation in `useMemo`, and React keeps its last result and hands it back while every dependency is the same as last time.** It is worth it only for a calculation that a measurement shows is slow, or for an array you pass to a component wrapped in `memo`, and around a cheap line it only adds code.

Remember Lesson 55? The user types `O` in the chat, `setText` changes the state, and React calls `ChatRoom` again. React does not pick the lines that need to run. It runs the whole body of the component, every line, whatever state changed (as seen in Lesson 13). For most lines, that costs nothing.

But picture a chat that keeps 5,000 messages, with a `Search messages` field at the top and a `Message` field at the bottom. The line that filters the messages sits in the body of `ChatRoom`. So every letter the user types in the `Message` field filters all 5,000 messages again. The search did not change, and the list stays exactly the same. You want to tell React: "Keep the result of this filter. Run it again only when the messages or the search change."

That is exactly what `useMemo` does. **`useMemo` hands back the last result while every dependency is the same as last time.** A dependency is a value the calculation reads, here the messages and the search. Keep this sentence in mind. As in Lesson 55, the whole lesson is about the word "same".

> [!DEFINITION]
> **A re-render.** [REVIEW] A re-render is React calling a component function again to get its new JSX. It happens for three reasons: the component's own state changed, its parent re-rendered, or a context it reads changed. Every line in the body of the component runs again, so a calculation written there runs again too. A re-render is only a function call: React then changes only the DOM nodes that differ (Lesson 54).

> [!DEFINITION]
> **Object.is.** [REVIEW] `Object.is(a, b)` is the JavaScript check React uses to ask "is this the same value as before?". For strings and numbers, it compares the value: `Object.is('l', 'l')` is true. For objects, arrays, and functions, it asks whether both are the very same one: two arrays with the same messages give false (Lesson 37).

> [!DEFINITION]
> **memo.** [REVIEW] `memo` is a function React provides. It wraps a component and returns a memoized component. When the parent re-renders, React compares each prop with its old value by `Object.is`, and skips the memoized component while every prop is the same. A new array on every render counts as a changed prop (Lesson 55).

> [!DEFINITION]
> **StrictMode calls every component twice.** [REVIEW] Our project mounts `<App />` inside `<StrictMode>`. In development, StrictMode calls every component function twice on purpose, so every `console.log` inside a component prints two lines. In production, each component is called once (Lesson 47).

### The Smallest Chat with useMemo

Here is the smallest chat that shows it: a `Search messages` field, three messages, and a `Message` field. A helper named `filterMessages` keeps the messages whose text contains the search. It also prints one line in the Console each time it runs, so we can count the runs. The filter is written directly in the body of `ChatRoom`:

```jsx title="A chat that filters its messages in the component body"
import { useState } from 'react';

const initialMessages = [
  { id: 1, text: 'Hi!' },
  { id: 2, text: 'Lunch at 12?' },
  { id: 3, text: 'Sure' },
];

function filterMessages(messages, query) {
  console.log('Filtering messages for:', query);
  return messages.filter(m => m.text.toLowerCase().includes(query.toLowerCase()));
}

function ChatRoom() {
  const [messages] = useState(initialMessages);
  const [query, setQuery] = useState('');
  const [text, setText] = useState('');

  const visibleMessages = ~filterMessages(messages, query)~; // Runs on every render of ChatRoom

  return (
    <>
      <label>Search messages <input value={query} onChange={e => setQuery(e.target.value)} /></label>
      <ul>
        {visibleMessages.map(m => <li key={m.id}>{m.text}</li>)}
      </ul>
      <label>Message <input value={text} onChange={e => setText(e.target.value)} /></label>
    </>
  );
}
```

### Why It Is Called useMemo

You met the word in Lesson 55. `memo` comes from **memoization**, which React's docs explain as "in other words, cache". A cache keeps the last result and reuses it while the inputs stay the same. The docs say it outright: "Caching return values like this is also known as memoization, which is why this Hook is called `useMemo`." Like every Hook, its name starts with `use`.

In plain JavaScript, you would write such a cache yourself. You keep the last inputs and the last result, and you compare before you do the work:

```js title="Plain JavaScript: a cache for the filter, written by hand"
let lastMessages = null;
let lastQuery = null;
let lastResult = null;

function cachedFilter(messages, query) {
  if (~Object.is(messages, lastMessages) && Object.is(query, lastQuery)~) return lastResult; // The same inputs as last time: reuse the old result
  lastMessages = messages;
  lastQuery = query;
  lastResult = filterMessages(messages, query);
  return lastResult;
}
```

`useMemo` writes this cache for you, inside the component. The list `[messages, query]` does the job of `lastMessages` and `lastQuery`. The value `useMemo` returns does the job of `lastResult`. And React keeps a separate cache for each copy of the component, the same way each copy has its own state (as seen in Lesson 12).

So the two names do two different jobs. `memo` caches what a whole component rendered. `useMemo` caches the result of one calculation inside a component.

> [!DEFINITION]
> **useMemo.** [NEW] `useMemo` is a Hook React provides. You give it a calculation function and a list of dependencies, the values the calculation reads: `useMemo(() => filterMessages(messages, query), [messages, query])`. On the first render, React calls the function and stores the result. On every later render, React compares each dependency with its value from the last render by `Object.is`. When all of them are the same, React hands back the stored result and does not call the function. When one changed, React calls it again and stores the new result (Lesson 56).

### What the User Feels

The user feels this in the `Message` field. A real chat keeps a long history in memory, and filters it right in the browser while the user types a reply. When a slow filter runs on every letter, the letters appear late in the field. React's docs say this kind of work "makes the typing feel janky".

1. **With `useMemo` around the slow filter**, letters in the `Message` field skip it. Only a change to the search, or a new message, runs it.
2. **With `useMemo` around a cheap line**, such as the check that the `Message` field is not empty, the user sees nothing change. The docs: "There is no benefit to wrapping a calculation in `useMemo` in other cases." The code only gets longer and harder to read.

### The Rule of Thumb: measure first, and keep every dependency the same

**`useMemo` hands back the last result while every dependency is the same as last time. Add it only where a measurement shows a slow calculation, and make sure no dependency is a new object on every render.**

A senior developer knows the four classic mistakes with `useMemo`:
1. **Wrapping every calculation because someone said it is faster.** Nobody measured, and the user sees no difference.
2. **Thinking it makes the page load faster.** It does not. The docs: "`useMemo` won't make the *first* render faster. It only helps you skip unnecessary work on updates."
3. **Letting the app depend on the stored result.** React may throw it away. The docs: "You should only rely on `useMemo` as a performance optimization. If your code doesn't work without it, find the underlying problem and fix it first."
4. **Listing a dependency that is new on every render**, such as an object made in the component body. Then React never reuses the stored result.

When a calculation in a component seems slow, there are four ways to handle it:
1. **Calculate it during rendering, with no cache.** This is the default (as seen in Lessons 22 and 34). React's docs say it plainly: "Usually, this code is fine!"
2. **Cache it with `useMemo`.** This fits when "The calculation you're putting in `useMemo` is noticeably slow, and its dependencies rarely change." This lesson covers it.
3. **Keep the fast-changing state lower, or pass JSX as `children`, so the slow part does not re-render at all.** The docs put this first among the habits that "make a lot of memoization unnecessary". Lesson 58 covers it.
4. **Turn on React Compiler.** It "can automatically memoize expensive calculations for you, eliminating the need for manual `useMemo` in many cases". Lesson 63 covers it.

```tree caption="Four ways developers handle a calculation that seems slow inside a component."
A calculation in a component seems slow
- +1. Calculate during rendering | The default, and **usually fine** | Lessons 22 and 34
- +2. Cache it with `useMemo` | Fits a calculation that is **noticeably slow** and whose dependencies **rarely change** | This lesson
- +3. Move state lower or pass `children` | The slow part **does not re-render at all** | Lesson 58
- +4. React Compiler | Memoizes calculations **at build time** | Lesson 63
```

**PRINCIPLES:** `useMemo` hands back the last result while every dependency is the same as last time. It is not a speed switch you can put on any line. Four principles follow:
1. **Principle 1: useMemo Skips the Filter While the User Types a Message.** React calls the calculation on the first render and stores the result. On later renders, it hands back the stored result while every dependency is the same, and calls the calculation again when one changed.
2. **Principle 2: Measure First with console.time.** Wrap a calculation only when a measurement shows it is slow. Around a cheap line, `useMemo` gains nothing and makes the code harder to read. It never makes the first render faster.
3. **Principle 3: useMemo Gives the Memoized MessageList the Same Array.** `filter` builds a new array on every call, so a child wrapped in `memo` re-renders anyway. `useMemo` hands the child the same array until a dependency changes.
4. **Principle 4: An Object Made in the Body Breaks the Cache.** An object written in the component body is new on every render, so a dependency list that holds it changes every time. Create the object inside the calculation function.

## PRINCIPLE | `useMemo`: the calculation runs again only when a dependency changes

> [!PRINCIPLE]
> **Principle 1: useMemo: React Reuses the Stored Result Until a Dependency Changes**
>
> *Write `useMemo(calculateValue, dependencies)` to cache the result of a calculation between re-renders; React calls the calculation on the first render, and again only when a dependency changed by `Object.is`.*
>
> React runs the whole body of a component on every re-render, so a calculation written directly in the body runs every time, even when its inputs did not change. `useMemo` stores the result. On the next render, React compares each dependency with its old value. When all of them are the same, React hands back the stored result and skips the calculation.
>
> **DO THIS:**
> ```jsx
> const visibleMessages = useMemo(
>   () => filterMessages(messages, query),
>   ~[messages, query]~ // A letter in the Message field reuses the stored array
> );
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const visibleMessages = ~useMemo~(() => filterMessages(messages, query)); // **WRONG:** no dependency list, so the filter runs on every render
> ```

### VS | A Line in the Body vs. the Same Line in `useMemo`: one runs every time, one only when its inputs change

Here are the two lines from the start of the lesson, one under the other:

```jsx title="The filter written directly, and the same filter inside useMemo"
const visibleMessages = filterMessages(messages, query); // Runs on every render of ChatRoom
const visibleMessages = ~useMemo~(() => filterMessages(messages, query), [messages, query]); // Runs only when messages or query changed
```

A developer new to this reads the first line and thinks: "The search did not change, so the filter does not run." But React does not look at what a line reads. It runs the whole body on every re-render, so the first line runs every time. The docs: "By default, React will re-run the entire body of your component every time that it re-renders." Only the second line tells React to reuse the last result.

### The Three Parts of a useMemo Line

A `useMemo` line has two arguments and one result, and React's docs give each one a name:

```jsx title="The three parts of a useMemo line"
const visibleMessages = useMemo(
  ~() => filterMessages(messages, query)~, // 1. The calculation function: React calls it, not our code
  ~[messages, query]~ // 2. The dependencies: every value the calculation reads
);
```

1. **The calculation function** is the first argument, our arrow function. React's docs say it "should be pure, should take no arguments, and should return a value of any type". Our code writes it, and React decides when to call it.
2. **The dependencies** are the second argument. The docs call them "The list of all reactive values referenced inside of the `calculateValue` code." Our calculation reads `messages` and `query`, so both go in the list. On each render, React compares each one with its value from the last render by `Object.is`. It is the same check React uses for the dependency array of an Effect (as seen in Lesson 35). Write the list right inside the call, and keep the same number of items in it on every render.
3. **The cached value** is what `useMemo` returns, here `visibleMessages`. On the first render, it is the result of our calculation function. On later renders, it is either the result React stored last time, or a fresh result when a dependency changed.

Why do we pass a function, and not the result? Because JavaScript first runs whatever you write between the parentheses of a call. If you passed the filter call itself, JavaScript would filter before `useMemo` even starts, and there would be nothing left to skip. So you hand React the function, and React decides whether to call it.

The `messages` and `query` inside the arrow function are the state variables of this render. The arrow function is written inside `ChatRoom`, so it reads them from the body around it (as seen in Lesson 15).

```tree dir=right caption="How React handles the three parts of a useMemo line on each render of ChatRoom."
One `useMemo` line on each render of `ChatRoom`
- +1. The calculation function [`calculateValue`] | Our code **writes** it; **React calls** it | Must be **pure** and take **no arguments**
- +2. The dependencies [`messages` `query`] | React compares each one with **the last render** | Uses **`Object.is`**, as an Effect does
- +3. The cached value [`visibleMessages`] | The **stored result** when nothing changed | A **fresh result** when one dependency changed
```

### The Helpers File and useMemo in ChatRoom

First, the helpers move into their own file. `createMessages` builds the loaded history: 5,000 messages, the first three with real text. `filterMessages` keeps the messages whose text includes the search, ignoring upper and lower case:

```js title="src/messages.js"
const firstTexts = ['Hi!', 'Lunch at 12?', 'Sure'];

export function createMessages() {
  const messages = [];
  for (let i = 0; i < 5000; i++) {
    const text = i < 3 ? firstTexts[i] : 'Message ' + (i + 1);
    messages.push({ id: i, text });
  }
  return messages;
}

export function filterMessages(messages, query) {
  console.log('Filtering messages for:', query);
  const lowerQuery = query.toLowerCase();
  return messages.~filter~(m => m.text.toLowerCase().includes(lowerQuery)); // Builds a new array, even when the search is empty
}
```

With an empty search, every message passes, so the list shows the whole history.

Next, `ChatRoom` imports `useMemo` and wraps the filter:

```jsx title="src/components/ChatRoom.jsx"
import { useMemo, useState } from 'react';
import { createMessages, filterMessages } from '../messages.js';
import MessageList from './MessageList.jsx';

export default function ChatRoom() {
  const [messages, setMessages] = useState(~createMessages~); // The function itself: React calls it on the first render only
  const [query, setQuery] = useState('');
  const [text, setText] = useState('');

  const visibleMessages = ~useMemo~( // Filters only when messages or query changed
    () => filterMessages(messages, query),
    [messages, query]
  );

  return (
    <section>
      <label>Search messages <input value={query} onChange={e => setQuery(e.target.value)} /></label>
      <MessageList messages={visibleMessages} />
      <label>Message <input value={text} onChange={e => setText(e.target.value)} /></label>
    </section>
  );
}
```

We pass `createMessages` to `useState` without calling it, so React calls it only on the first render. If we wrote `createMessages()` with the call, `ChatRoom` would build 5,000 messages on every letter and throw them away.

`MessageList` is still a plain component. It renders one `<li>` per message:

```jsx title="src/components/MessageList.jsx"
export default function MessageList({ messages }) {
  return (
    <ul>
      {messages.map(m => <li key={m.id}>{m.text}</li>)}
    </ul>
  );
}
```

### The Real Mistake: No Dependency List

React's docs list this mistake in their troubleshooting section. A developer adds `useMemo` and forgets the second argument:

```jsx title="useMemo without its dependency list"
const visibleMessages = ~useMemo~(() => filterMessages(messages, query)); // **WRONG:** no dependency list, so React calls the filter on every render
```

1. The page works, and the list is right.
2. The user types in the `Message` field, and `Filtering messages for:` appears at every letter.
3. The developer decides that `useMemo` does not work.

`useMemo` works. It just has nothing to compare. The docs: "If you forget the dependency array, `useMemo` will re-run the calculation every time." Add `[messages, query]`, and the letters in the `Message` field stop printing the line.

### Five Facts About the Calculation Function

1. **It runs during rendering, so it must be pure.** React's docs say caching "only works for pure calculations". Suppose the calculation pushed a welcome message into `messages`, the array it received from state. StrictMode would then show that message twice. Changing a new array that the calculation made itself is fine. The React Hooks linter has a rule for this, `use-memo`: "`useMemo` is for computing and caching expensive values, not for side effects."
2. **StrictMode calls it twice in development.** The docs: "React will call your calculation function twice in order to help you find accidental impurities. This is development-only behavior". React keeps one of the two results (as seen in Lesson 47).
3. **React may throw the cached value away.** The docs: "React will not throw away the cached value unless there is a specific reason to do that." One reason is editing the component's file during development. Another is a component that pauses its first render to wait for data, which React calls suspending. Lesson 69 covers it. When a value must be kept, "a state variable or a ref may be more appropriate" (as seen in Lessons 12 and 30).
4. **It is a Hook, so you call it only at the top level of the component.** The docs: "You can't call it inside loops or conditions." To cache one calculation for each item of a list, extract a component for the item, and call `useMemo` inside that component (as seen in Lesson 38).
5. **It replaces an Effect that copies a result into state.** The docs: "To cache expensive calculations, add `useMemo` instead of `useEffect`." An Effect that stores the filtered list in state first renders the page with the old list (as seen in Lesson 34).

## PRINCIPLE | `console.time`: measure first, and cache only a calculation that is slow

> [!PRINCIPLE]
> **Principle 2: Measure First: useMemo Pays Off Only for a Slow Calculation**
>
> *Wrap a calculation in `useMemo` only when `console.time` shows it is slow, about `1ms` or more, and it runs again on renders where its dependencies did not change.*
>
> `useMemo` skips work only on renders where the dependencies stayed the same, and it never makes the first render faster. Around a cheap check, there is nothing to skip: the user sees no difference, and the code gets an arrow function and a dependency list that can go wrong. Measure on a throttled CPU, in a production build, before you decide.
>
> **DO THIS:**
> ```jsx
> const canSend = ~text.trim() !== ''~; // Cheap: written directly

> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const canSend = ~useMemo~(() => text.trim() !== '', [text]); // **WRONG:** nothing to skip, and text changes at every letter anyway
> ```

### VS | `canSend` Written Directly vs. `canSend` in `useMemo`: the exact same page, with more code

The `Send` button should be greyed out while the `Message` field is empty. That takes one short check. Here it is written directly, and inside `useMemo`:

```jsx title="The check for Send written directly, and inside useMemo"
const canSend = text.trim() !== ''; // Reads one short string on each render
const canSend = ~useMemo~(() => text.trim() !== '', [text]); // The same answer, with more code
```

For the user, **yes, it is the exact same thing!** The `Send` button turns grey and turns active at the very same moments in both versions. Why is the `useMemo` useless here? For two reasons:
1. **There is nothing worth skipping.** The check reads one short string.
2. **It would not skip anyway.** `text` changes at every letter the user types in the `Message` field, so this `useMemo` runs the check on those letters too.

The second line only adds an arrow function and a dependency list for the next developer to read.

A developer new to this thinks: "`useMemo` makes any calculation faster, so wrap them all." But `useMemo` only skips work on renders where the dependencies did not change. When the work is tiny, there is nothing to skip. React's docs give a rule of thumb: "In general, unless you're creating or looping over thousands of objects, it's probably not expensive." Our filter loops over 5,000 messages, so it may be expensive. Only a measurement can tell.

### Measuring the Filter with console.time

The look of the code cannot tell you whether a calculation is slow. A measurement can. `console.time` and `console.timeEnd` are browser functions (as seen in Lesson 54). The first starts a timer, the second stops it, and the browser prints the time between them in the Console. We put them around the plain filter line:

```jsx title="src/components/ChatRoom.jsx"
console.time('filter messages');
const visibleMessages = filterMessages(messages, query);
console.timeEnd(~'filter messages'~); // Must match the label given to console.time
```

The user types `O` in the `Message` field. Each render prints a timer line under the filter line. The numbers on your machine will differ:

```devconsole caption="The Console after one letter in the Message field, with the timer around the plain filter line."
Filtering messages for: | letter O
filter messages: 0.6640625 ms
Filtering messages for: | Strict Mode copy
filter messages: 0.18701171875 ms
```

React's docs draw the line at about `1ms`: when the logged time adds up to `1ms` or more, "it might make sense to memoize that calculation."

Two things can mislead us here:
1. **Our machine is faster than the user's phone.** The docs: "Your machine is probably faster than your users' so it's a good idea to test the performance with an artificial slowdown." Chrome's CPU Throttling gives that slowdown (as seen in Lesson 54).
2. **Development mode is slower, and StrictMode doubles every render.** The docs: "To get the most accurate timings, build your app for production and test it on a device like your users have."

So the number decides, not the look of the code. If the filter over 5,000 messages stays far under `1ms` on a throttled CPU, it is not expensive at this size, and the plain line is fine. If it reaches `1ms` or more, it is worth caching. It runs at every letter, and its dependencies, the history and the search, rarely change.

Now we keep the timer and wrap the line in `useMemo`:

```jsx title="src/components/ChatRoom.jsx"
console.time('filter messages');
const visibleMessages = ~useMemo~(() => filterMessages(messages, query), [messages, query]); // Skipped on letters in the Message field
console.timeEnd('filter messages');
```

The user types in the `Message` field again. The logged time drops close to zero, because React hands back the stored array and never calls the filter.

### What useMemo Never Speeds Up: the First Render

Now we reload the page. On the first render, the timer shows the full cost of the filter again. Nothing is stored yet, so React has to call the calculation. The docs: "`useMemo` won't make the *first* render faster. It only helps you skip unnecessary work on updates."

### The Real Mistake: Wrapping Every Calculation

**Wrapping everything in `useMemo` brings the user nothing and costs the team readable code.** Here is how it usually goes:

1. A team agrees to wrap every calculation in `useMemo`, because someone said it is faster.
2. A developer wraps `canSend`, the count of messages, and the line that joins a first name and a last name.
3. Each wrapped line gains an arrow function and a dependency list. Some lists miss a value, and the linter starts to complain.
4. Nothing the user sees changes.

React's docs describe exactly this: "There is no significant harm to doing that either, so some teams choose to not think about individual cases, and memoize as much as possible. The downside of this approach is that code becomes less readable. Also, not all memoization is effective: a single value that's 'always new' is enough to break memoization for an entire component."

### When useMemo Is Worth Adding

React's docs name three cases where `useMemo` is valuable:

1. **The calculation is noticeably slow, and its dependencies rarely change.** This is our filter, once a measurement shows it is slow.
2. **You pass the result as a prop to a component wrapped in `memo`.** Principle 3 covers this case.
3. **The result is later used as a dependency of another Hook**, such as another `useMemo` or a `useEffect`. Principle 4 shows how such a dependency breaks, and an Effect follows the same rule (as seen in Lesson 37).

The kind of app matters too. When most interactions are coarse, such as replacing a page or a whole section, the docs say "memoization is usually unnecessary." When most interactions are granular, as in a drawing editor where the user moves shapes, "you might find memoization very helpful."

React Compiler changes the habit for new code. The docs: "For new code, we recommend relying on the compiler for memoization and using `useMemo`/`useCallback` where needed to achieve precise control." For existing code, they recommend leaving the memoization in place, because removing it can change what the compiler produces. The other way is to test carefully before removing it. Lesson 63 covers the compiler.

### The Send Button

`ChatRoom` gains the check for `Send`, written directly, with no `useMemo`. It also gains `handleSend`, which adds the new message to the history and empties the `Message` field. The `console.time` lines were only a measurement, so they leave the file:

```jsx title="src/components/ChatRoom.jsx"
import { useMemo, useState } from 'react';
import { createMessages, filterMessages } from '../messages.js';
import MessageList from './MessageList.jsx';

let nextId = 5000;

export default function ChatRoom() {
  const [messages, setMessages] = useState(createMessages);
  const [query, setQuery] = useState('');
  const [text, setText] = useState('');

  const visibleMessages = useMemo(
    () => filterMessages(messages, query),
    [messages, query]
  );
  const canSend = ~text.trim() !== ''~; // Cheap: written directly, with no useMemo

  function handleSend() {
    setMessages([...messages, { id: nextId++, text }]);
    setText('');
  }

  return (
    <section>
      <label>Search messages <input value={query} onChange={e => setQuery(e.target.value)} /></label>
      <MessageList messages={visibleMessages} />
      <label>Message <input value={text} onChange={e => setText(e.target.value)} /></label>
      <button ~disabled={!canSend}~ onClick={handleSend}>Send</button> {/* Greyed out while the Message field is empty */}
    </section>
  );
}
```

`nextId` starts at `5000` because the history already uses the ids `0` to `4999` (as seen in Lesson 19).

When the user clicks `Send`, `setMessages` receives a new array. So `messages` changed, and React calls the filter once more with the current search. The Console prints `Filtering messages for:` again, with its StrictMode copy, and the new message appears at the end of the list.

## PRINCIPLE | `useMemo` with `memo`: the memoized child receives the same array and skips

> [!PRINCIPLE]
> **Principle 3: Same Array for memo: useMemo Lets a Memoized Child Skip**
>
> *When you pass a calculated array or object to a component wrapped in `memo`, wrap the calculation in `useMemo`, so the child receives the same value until a dependency changes.*
>
> `filter`, `map`, and object literals build a new value on every render, even when the content is the same. `memo` compares each prop by `Object.is`, so a new array with the same messages counts as a changed prop, and the child renders again. `useMemo` hands back the very same array while its dependencies stay the same, so `memo` can skip the child.
>
> **DO THIS:**
> ```jsx
> const visibleMessages = ~useMemo~(() => filterMessages(messages, query), [messages, query]); // The same array on letters in the Message field
> return <MessageList messages={visibleMessages} />;
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const visibleMessages = ~filterMessages(messages, query)~; // **WRONG:** a new array on every render, so the memoized MessageList renders anyway
> return <MessageList messages={visibleMessages} />;
> ```

### VS | The Same Messages vs. the Same Array: `memo` checks which array it is, not what it holds

Remember Lesson 55: a component wrapped in `memo` skips its re-render while its props stay the same. Now suppose we wrap the whole list, `MessageList`, in `memo`, and `ChatRoom` passes it the filtered array as its `messages` prop. Compare the two ways to make that array:

```jsx title="Two ways to make the array that goes to the memoized MessageList"
const visibleMessages = ~filterMessages(messages, query)~; // A new array on every render of ChatRoom
const visibleMessages = ~useMemo~(() => filterMessages(messages, query), [messages, query]); // The same array until messages or query changes
```

A developer new to this thinks: "The filtered list did not change, so `memo` skips `MessageList`." **It may look the same, but it is NOT the same thing!** The content did not change, but the array did. `filter` builds a new array on every call, even when every item passes (as seen in Lesson 19). `memo` compares each prop by `Object.is`, and two arrays with the same messages in the same order are still two different arrays (as seen in Lesson 55). React's docs say it about their own filter: it "always creates a *different* array, similar to how the `{}` object literal always creates a new object."

```tree caption="A memoized child receives a new array from the plain filter line, and the same array from the useMemo line."
What `memo` sees in the `messages` prop after a letter in the `Message` field
- !From the plain filter line [`filterMessages`] | The **same messages** in a **new array** | `Object.is` says **different**, so React **renders `MessageList` again**
- +From the `useMemo` line [`useMemo`] | The **same array** as last time | `Object.is` says **same**, so React **skips `MessageList`**
```

### MessageList in memo

The list file imports `memo`, wraps the component, and prints a line each time it renders:

```jsx title="src/components/MessageList.jsx"
import { memo } from 'react';

const MessageList = ~memo~(function MessageList({ messages }) { // Skips while messages is the same array
  console.log('MessageList rendered');
  return (
    <ul>
      {messages.map(m => <li key={m.id}>{m.text}</li>)}
    </ul>
  );
});

export default MessageList;
```

### What Happens on a Letter Without useMemo, and With It

**With the plain filter line, `memo` cannot skip `MessageList`. With `useMemo`, it can.** First, suppose `ChatRoom` still uses the plain filter line:

1. The user types `O` in the `Message` field. `ChatRoom` re-renders and calls `filterMessages`, which returns a new array with the same 5,000 messages.
2. React compares the new `messages` prop of `MessageList` with the old one by `Object.is`. They are different arrays.
3. React calls `MessageList`, which maps over all 5,000 messages again. The Console prints `MessageList rendered` at every letter, though `memo` is there.

```devconsole caption="With the plain filter line, one letter in the Message field runs the filter and renders the memoized MessageList again."
Filtering messages for: | letter O
Filtering messages for: | Strict Mode copy
MessageList rendered
MessageList rendered | Strict Mode copy
```

Now `ChatRoom` uses the `useMemo` line from Principle 1:

1. The user types `K` in the `Message` field. `useMemo` finds `messages` and `query` the same, and returns the stored array.
2. The `messages` prop of `MessageList` is the very same array as last time, so React skips `MessageList`. No line appears in the Console.
3. The user types in the `Search messages` field. `query` changes, the filter runs, a new array arrives, and `MessageList` renders again with fewer rows, as it should.

```devconsole caption="With the useMemo line, one letter in the Message field prints nothing."
= No messages
```

The page looks the same in both versions. The Elements panel shows no change to any `<li>` node either: React compares the new rows with the old ones and finds nothing to change (as seen in Lesson 13). The difference is the work React does to find that out: 5,000 rows at every letter, or none.

React's docs put this case in two sentences: "You don't *have to* wrap a calculation in `useMemo` unless you do it for some specific reason. In this example, the reason is that you pass it to a component wrapped in `memo`."

### The Real Mistake: memo Without useMemo

**The developer adds `memo`, the typing still lags, and they blame `memo`.** Here is how it happens:

1. A developer measures the chat with `<Profiler>` and finds `MessageList` slow at every letter (as seen in Lesson 54).
2. They wrap `MessageList` in `memo` (as seen in Lesson 55).
3. They pass the filter result without `useMemo`.
4. The letters still lag. The docs explain why: the filtered list "is always a different array", and the slow list "can't skip re-rendering".
5. The developer removes `memo`, believing it does nothing.

The fix is one line in the parent: wrap the filter in `useMemo`. `memo` on the child and `useMemo` on the array it receives work as a pair.

### Three Facts for the Interview

1. **The rows often cost more than the filter.** The docs: "if the number of todos grows significantly, most of the overhead will be in re-rendering rather than in the filtering." The same can hold in our chat: rendering 5,000 rows may take longer than filtering them. Lesson 62 covers very long lists.
2. **`useMemo` can also cache a JSX node.** A JSX node is an object too, so `useMemo` can return the `<MessageList>` tag itself, with `[visibleMessages]` as its list. That gives the same result as `memo`. The docs: "if React sees the same exact JSX as during the previous render, it won't try to re-render your component." The docs still prefer `memo`: "Manually wrapping JSX nodes into `useMemo` is not convenient. For example, you can't do this conditionally."
3. **`useMemo` caches a result, and `useCallback` caches a function.** The docs: "`useMemo` caches the *result* of calling your function" and "`useCallback` caches *the function itself*." A function passed to a memoized child needs `useCallback`, which Lesson 57 covers. An object passed as the `value` of a context provider needs `useMemo` for the same reason as our array, and Lesson 59 covers it.

## PRINCIPLE | `searchOptions` in the dependencies: a new object on every render breaks the cache

> [!PRINCIPLE]
> **Principle 4: Object Dependencies: An Object Made in the Body Breaks the Cache**
>
> *Never list an object created in the component body as a dependency of `useMemo`; create it inside the calculation function, and list the values it is made from.*
>
> Every line of the component body runs on every render, so an object literal there is a new object each time. `useMemo` compares dependencies by `Object.is`, finds the new object different, and runs the calculation on every render. A string or a number with the same value is the same for `Object.is`, so depending on `query` keeps the cache working.
>
> **DO THIS:**
> ```jsx
> const visibleMessages = useMemo(() => {
>   const searchOptions = { text: query, matchCase: false };
>   return searchMessages(messages, searchOptions);
> }, [messages, ~query~]); // A string: the same on letters in the Message field
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> const searchOptions = { text: query, matchCase: false };
> const visibleMessages = useMemo(
>   () => searchMessages(messages, searchOptions),
>   [messages, ~searchOptions~] // **WRONG:** a new object on every render, so the filter runs every time
> );
> ```

### VS | The Same Text vs. the Same Object: a string compares by value, an object by identity

React compares each dependency of `useMemo` by `Object.is`. Here is what `Object.is` says about the same text, and about two objects that hold the same text:

```js title="The same text, and two objects with the same text"
Object.is(~'ok', 'ok'~); // true: two strings with the same letters are the same value
Object.is(~{ text: 'ok' }, { text: 'ok' }~); // false: two objects, made one after the other
```

A developer new to this thinks an object that holds the same text is the same value. **It may look the same, but it is NOT the same thing!** `Object.is` compares objects by identity, not by what is inside them. `memo` compares props the same way (as seen in Lesson 55). And every line of the component body runs on every render, so an object written there is a new object each time. React's docs: "When a component re-renders, all of the code directly inside the component body runs again." So an object made in the body and listed as a dependency of `useMemo` looks changed on every render. It is the same trap as a dependency of an Effect (as seen in Lesson 37).

Where does this show up? A search often takes more than one setting, so search helpers often take an options object.

### A Shared Search Helper

Suppose a teammate replaces our filter with a shared helper, `searchMessages`. It takes an options object with the search text and a `matchCase` setting, and it prints the same line:

```js title="src/messages.js"
export function searchMessages(messages, { text, matchCase }) {
  console.log('Filtering messages for:', text);
  return messages.filter(m =>
    matchCase ? m.text.includes(text) : m.text.toLowerCase().includes(text.toLowerCase())
  );
}
```

In `ChatRoom`, the teammate builds `searchOptions` in the body. The calculation reads `searchOptions`, so they put it in the dependency list:

```jsx title="src/components/ChatRoom.jsx"
const searchOptions = ~{ text: query, matchCase: false }~; // A new object on every render of ChatRoom
const visibleMessages = useMemo(
  () => searchMessages(messages, searchOptions),
  [messages, searchOptions]
);
```

**Beware! The `useMemo` line is still there, and the list is still right, yet the filter runs at every letter again.** Here is the path:

1. The page looks and works the same. Searching still filters the list.
2. The user types `O` in the `Message` field. `ChatRoom` re-renders and builds a new `searchOptions` object.
3. React compares `searchOptions` with the old one by `Object.is`. They are different objects.
4. React calls the calculation, which returns a new array. The `Filtering messages for:` line is back at every letter, as if `useMemo` were not there.
5. The new array reaches the memoized `MessageList`, so it renders all 5,000 rows again too.

```devconsole caption="With searchOptions in the dependency list, one letter in the Message field runs the filter and renders MessageList again."
Filtering messages for: | letter O
Filtering messages for: | Strict Mode copy
Filtering messages for: | Strict Mode copy
MessageList rendered
MessageList rendered | Strict Mode copy
```

Why three filter lines? StrictMode calls the calculation twice in the first render of `ChatRoom`. Its second render of `ChatRoom` builds yet another new object, so the calculation runs once more. In a production build, the line appears once per letter. Either way, the filter runs on a letter that changed nothing it reads.

When the React Hooks linter is set up, it flags this line too. It warns that the `searchOptions` object makes the dependencies of the Hook change on every render.

### The Fix: Create the Object Inside the Calculation Function

Move the object inside the calculation function, and list the value it is made from, `query`:

```jsx title="src/components/ChatRoom.jsx"
const visibleMessages = useMemo(() => {
  const searchOptions = { text: query, matchCase: false }; // Built only when the calculation runs
  return searchMessages(messages, searchOptions);
}, [messages, ~query~]); // A string: the same on every letter in the Message field
```

Now the dependencies are the history and a string. A string with the same letters is the same value for `Object.is`, so it cannot become different by accident. React's docs say it of their own search text: a string "can't 'accidentally' become different". The letters in the `Message` field stop printing the filter line, and React skips `MessageList` again.

```tree caption="Where the searchOptions object is created decides whether useMemo can reuse its stored result."
Where `searchOptions` is created
- !In the component body, listed as a dependency [`searchOptions`] | A **new object** on every render | `useMemo` **runs the filter at every letter**
- +Inside the calculation function [`query`] | Built **only when the filter runs** | `useMemo` **reuses the stored array** on letters in the `Message` field
```

There is a second fix: wrap `searchOptions` in its own `useMemo`, with `[query]` as its list. It works, but the docs call moving the object inside the calculation "even better", because it removes a dependency instead of adding a second cache.

Our final files do not keep this edit. They keep `filterMessages` with `[messages, query]`.

### Finding the Dependency That Breaks the Cache

When a `useMemo` runs on every render and the reason is not obvious, React's docs give a way to find the dependency that changes:

1. Log the dependency list right above the `useMemo` line, such as `console.log([messages, searchOptions])`.
2. In the Console, right-click two of the logged arrays from different renders, and store each one as a global variable. The browser names them `temp1` and `temp2`.
3. Compare each item in the Console. Start with `Object.is(temp1[0], temp2[0])` for `messages`, then `Object.is(temp1[1], temp2[1])` for `searchOptions`.
4. The item that gives `false` is the one that breaks the cache. The docs: "When you find which dependency breaks memoization, either find a way to remove it, or memoize it as well."

### The Real Mistake: Returning an Object from an Arrow Function

When the cached value is itself an object, the curly braces can trick us:

```jsx title="Caching an options object with useMemo"
const searchOptions = useMemo(() => ~{ text: query }~, [query]); // **WRONG:** these braces start a function body, so it returns undefined
const searchOptions = useMemo(() => {
  return ~{ text: query }~; // An explicit return gives back the object
}, [query]);
```

Right after an arrow, curly braces start the body of the function, not an object. The first line has no `return`, so `useMemo` gives back `undefined`. Wrapping the object in parentheses also works, but the docs say that form "is easy for someone to break again", and they recommend the explicit `return`.

### The Same Rule in Effects

An object made in the body and listed in an Effect's dependency array makes the Effect run again on every render. The docs fix it the same way, by moving the object inside the Effect, because "`useMemo` is performance optimization, not a semantic guarantee" (as seen in Lesson 37).

Even with React Compiler, a hand-written `useMemo` still has a place here. The compiler docs: "A common use-case for this is if a memoized value is used as an effect dependency." Lesson 63 covers the compiler.

| What the user does | Does the filter run? | Does `MessageList` render? |
| :--- | :--- | :--- |

| Aspect | The Habit That Wastes Work | The React Rule |
| :--- | :--- | :--- |
| **A slow calculation** | Written directly in the body, so it runs at every letter in an unrelated field | Wrapped in `useMemo`, with every value it reads in the dependency list |
| **A cheap calculation** | Wrapped in `useMemo` because someone said it is faster | Written directly; measured with `console.time` before any `useMemo` |
| **A value for a memoized child** | A freshly filtered array on every render, so `memo` never skips | The array from `useMemo`, the same until a dependency changes |
| **An object as a dependency** | Built in the body and listed in the dependency list, so React never reuses the stored result | Built inside the calculation function, with the plain values it is made from in the list |

Remember the one sentence of this lesson. **`useMemo` hands back the last result while every dependency is the same as last time, so it saves work only for a slow calculation or for a value a memoized child receives.**

## For the Interview

> **The Interview Question:** What does useMemo cache, and when is it wasted work?

### How to Answer Clearly in 30 Seconds

"`useMemo` caches the result of a calculation between re-renders. On the first render, React calls the calculation function and stores the result. On later renders, React compares each dependency with its old value using `Object.is`. If all of them are the same, React returns the stored result. If one changed, React calls the calculation again. It is worth it in three cases:
1. **A slow calculation**: about `1ms` or more, measured with `console.time` on a throttled CPU, whose dependencies rarely change.
2. **A value passed to a component wrapped in `memo`**: so the child gets the same array or object and can skip.
3. **A value used as a dependency of another Hook.**

Around a cheap calculation it is wasted work: it brings no benefit, it never speeds up the first render, and it makes the code harder to read. And it is only a performance optimization: if the code breaks without it, there is a bug to fix."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Should we wrap every calculation in `useMemo` to be safe?"**
   **No.** `useMemo` skips work only on renders where its dependencies did not change, and a cheap calculation has nothing worth skipping. React's docs say there is "no benefit" in other cases and "no significant harm" either, but the code "becomes less readable", and a single dependency that is always new breaks the cache anyway. Measure first with `console.time`, and wrap only what is slow. For new code, React Compiler can memoize calculations automatically.
2. **"Your `useMemo` recalculates on every render. Why?"**
   There are two usual causes. First, the dependency array is missing, so React has nothing to compare and runs the calculation every time. Second, one dependency is new on every render, such as an object made in the component body. `Object.is` compares objects by identity, so the new object always looks changed. To find it, log the dependency list, store two of the logged arrays as global variables in the Console, and compare each item with `Object.is`. The fix is to create the object inside the calculation function and list the plain values it is made from.
3. **"Can your code rely on `useMemo` to keep a value between renders?"**
   **No.** React may throw the cached value away, for example when you edit the component's file in development, or when a component pauses its first render to wait for data. The docs say to rely on `useMemo` only as a performance optimization: "If your code doesn't work without it, find the underlying problem and fix it first." A value that must be kept belongs in state or in a ref. The calculation must also be pure, because React calls it during rendering, and StrictMode calls it twice in development to find impurities.

```tree dir=right caption="Interview summary: when useMemo saves work and when it is wasted work."
When is `useMemo` worth adding?
- +A slow calculation, measured [`console.time`] | About **`1ms` or more**, with dependencies that **rarely change** | `useMemo` **skips it** on unrelated re-renders
- +A value for a `memo` child [`messages={visibleMessages}`] | The child receives the **same array** | `memo` **can skip** the child
- !A cheap calculation [`text.trim`] | Nothing worth skipping | **No benefit**, and the code is **harder to read**
- !An object made in the body as a dependency [`searchOptions`] | A **new object** on every render | React **never reuses** the stored result
```
