# Lecture 50: How a Child Hands Its Parent Only focus with useImperativeHandle

*(How does a Comment button in one component put the cursor in an input field that lives in another component?)*

> INTERVIEW QUESTION | ❱❱ MORE | How does a child expose a focused API to its parent through a ref?

---

## VS | `ref` on the `<input>` vs. `useImperativeHandle`: the parent gets the whole element, or only `focus`

> A ref on an `<input>` tag hands your component the real element, so a click can put the cursor in it. **When that `<input>` lives inside a child component, the child decides what the parent's ref gets: the whole element, or a small object with only `focus`**. Give the parent only what it needs, because a parent that holds the whole element can change it in ways the child's file never shows.

Remember Lesson 31? A button and an `<input>` field sat in the same component. You put a ref on the input tag, and React put the real element into `inputRef.current`. Then the click handler called `focus()` on it, and the cursor jumped into the field.

In a real app, the button and the field often live in two different components. Think of a feed on Facebook or LinkedIn. The same comment field sits under every post, so it gets its own component, `CommentInput`. The Comment button stays in the parent, `Post`. Ask yourself: how does `Post` put the cursor into an `<input>` that it does not render?

It starts the same way as in Lesson 31. `Post` creates a ref and writes it on the child's tag: `<CommentInput ref={commentRef} />`. But a ref on your own component does not reach the `<input>` inside it by itself. React's docs say it plainly: "By default, your own components don't expose refs to the DOM nodes inside them."

> [!DEFINITION]
> **To expose.** [NEW] When a parent writes a ref on a child's tag, whatever the child lets the parent reach through that ref is what the child exposes. By default, a component you write exposes nothing, so the parent's ref stays `null` until the child decides what to put there (Lesson 50).

So `CommentInput` has to choose what to expose. It has two choices:
- **The whole element.** `CommentInput` puts the parent's ref on its own `<input>`. Then `Post` gets the real `<input>` element, exactly as in Lesson 31.
- **Only `focus`.** `CommentInput` keeps the `<input>` in a ref of its own. It hands `Post` a small object with one method, `focus`. React's Hook for this is `useImperativeHandle`.

That small object is what the interview question calls a focused API: the few methods the parent may call, and nothing else.

You already know this idea from plain JavaScript. A file can keep a variable to itself and export only one function. Other files can call that function, but they never touch the variable:

```js title="Plain JavaScript: a file shares one function, not the element"
const input = document.getElementById('comment'); // Stays private inside this file
export function ~focusComment~() { // The only thing other files can use
  input.focus();
}
```

`useImperativeHandle` does the same thing for a component. The `<input>` stays inside `CommentInput`. The parent gets only the methods that `CommentInput` returns:

```jsx title="React: CommentInput shares one method, not the element"
const inputRef = useRef(null); // Stays private inside CommentInput
~useImperativeHandle~(ref, () => ({ // The only thing Post can use
  focus() { inputRef.current.focus(); },
}));
```

**Why:** On the page, both choices look and work the same. The user clicks Comment, `Post` runs `commentRef.current.focus()`, and the cursor lands in the field. The difference is only what `commentRef.current` holds. With the whole element, `Post` can also change the field's style, read its text, or remove it. Nobody who reads the file of `CommentInput` can see that. The docs warn: "Manually manipulating *another* component's DOM nodes can make your code fragile." With `useImperativeHandle`, `Post` holds an object that the child wrote. That object has `focus`, and nothing else.

```tree caption="Two things CommentInput can expose to Post through the same ref: the whole input element, or an object with only focus."
What `commentRef.current` holds in `Post`
- !The ref on the `<input>` [`<input ref={ref} />`] | `Post` gets **the real `<input>` element** | `Post` can focus it, **and also change its style or remove it**
- +`useImperativeHandle` [`useImperativeHandle`] | `Post` gets **an object `CommentInput` wrote** | `Post` can **only focus** the field
```

Remember the one sentence of this lesson. **The parent gets only what the child hands it. Put the ref on the `<input>`, and the parent gets the whole element. Use `useImperativeHandle`, and the parent gets only the methods you return.**

### The Rule of Thumb: what does the parent really need?

**Ask one question: what does the parent really need from the child? If it needs an action that no prop can say, such as focus, hand it a handle with that one method. If it needs to decide what the child shows, pass a prop.**

A senior developer also knows the three classic mistakes:
1. **Expecting a ref on your own component to work like a ref on `<input>`.** It does not. The ref stays `null` until the child uses it, and the click throws a `TypeError`.
2. **Believing `useImperativeHandle` hides the `<input>` from the page.** The `<input>` is still on the page and in the Elements panel. Only what the parent's ref holds changes.
3. **Putting everything into the handle**, such as `clear` or `open`. If a prop can say it, a prop should say it.

The rest of the lesson shows each mistake on a real page.

1. **Principle 1: A ref on our own component is only a prop.** Until `CommentInput` puts it on its input tag, the ref stays `null`. Then the click throws a `TypeError`.
2. **Principle 2: The ref on the input hands over the whole element.** `Post` can focus it, and it can also change its style, without a hint in the child's file.

## PRINCIPLE | `<CommentInput ref={commentRef} />`: the ref stays `null` until `CommentInput` puts it on a built-in tag

> [!PRINCIPLE]
> **Principle 1: ref as a Prop: A Ref on Our Own Component Stays null Until It Reaches a Built-In Tag**
>
> *A ref written on our own component is only a prop; the component must take `ref` from its props and put it on a built-in tag before the parent's `ref.current` holds an element.*
>
> React fills a ref with an element only on a built-in tag such as `<input>`. On `<CommentInput ref={commentRef} />`, React has no element to give, so it hands `ref` to `CommentInput` as a prop. If `CommentInput` ignores it, `commentRef.current` stays `null`, and the click on Comment throws a `TypeError`.
>
> **DO THIS:**
> ```jsx
> function CommentInput({ ref }) {
>   return <input ~ref={ref}~ placeholder="Write a comment..." />; // React puts the input into the parent's ref
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ~CommentInput~() { // **WRONG:** never reads ref, so commentRef.current stays null and the click throws
>   return <input placeholder="Write a comment..." />;
> }
> ```

Here is the same ref written on two tags. The first is the browser's own `<input>`. The second is `MyInput`, a component we wrote that returns an `<input>`:

```jsx title="The same ref on a built-in tag and on our own component"
const inputRef = useRef(null);

<input ~ref={inputRef}~ /> {/* React puts this <input> element into inputRef.current */}
<MyInput ~ref={inputRef}~ /> {/* inputRef.current stays null unless MyInput puts ref on a tag */}
```

It may look the same, but it is NOT the same thing! Why? React can put an element into a ref only when it has an element. On `<input>`, it has one: React creates a real `<input>` element in the commit, as in Lesson 31. On `<MyInput>`, it has none. `MyInput` is a function we wrote, not a tag of the browser.

So React does the only thing it can. It hands the ref to `MyInput` as one more prop. Nothing happens until `MyInput` uses it.

```tree caption="The same ref attribute on a built-in tag and on a component we wrote."
Where the `ref` attribute is written
- +On a built-in tag [`<input ref={inputRef} />`] | React has **a real element** for this tag | React puts **the element into `inputRef.current`** in the commit
- !On our own component [`<MyInput ref={inputRef} />`] | `MyInput` is **a function**, not a browser tag | `ref` is **just a prop**, and `inputRef.current` **stays `null`**
```

### Post gives CommentInput a ref, and the click crashes

On our page, `Post` now creates a ref and writes it on the `CommentInput` tag. When the user clicks Comment, it calls `focus` on it:

```jsx title="src/components/Post.jsx"
import { useRef } from 'react';
import CommentInput from './CommentInput.jsx';

export default function Post() {
  const commentRef = useRef(null);

  function handleCommentClick() {
    ~commentRef.current.focus();~ // Expects the input inside CommentInput
  }

  return (
    <article>
      <p>John: Lunch at noon?</p>
      <button onClick={handleCommentClick}>Comment</button>
      <CommentInput ~ref={commentRef}~ /> {/* Looks like the ref on an input in Lesson 31 */}
    </article>
  );
}
```

`CommentInput` stays as it was. It returns the `<input>` and never reads `ref`.

**Beware! The user clicks Comment, and the page throws an error instead of putting the cursor in the field.** Here is what happens, in order:
1. `Post` creates `commentRef`. It starts out holding `null`.
2. React hands that ref to `CommentInput` as a prop. `CommentInput` never reads it.
3. React commits the page. No built-in tag carries `commentRef`, so it still holds `null`.
4. The user clicks Comment. The click handler asks `commentRef.current` for its `focus` method.
5. `commentRef.current` is `null`, and null has no methods. So JavaScript throws a `TypeError`, and the cursor never reaches the field.

```page width=text caption="After the user clicks Comment: the cursor stays out of the comment field, and the Console shows a TypeError."
line: John: Lunch at noon?
line: [Comment]
card: input=Write a comment... | bad=input
console: Uncaught TypeError: Cannot read properties of null (reading 'focus')
```

The page looks exactly as it did before the click. The user sees only a button that does nothing. The red line in the Console is the one the docs show for this exact mistake: "TypeError: Cannot read properties of null".

### The fix: CommentInput takes ref from its props

The fix is two small changes in `CommentInput`:

```jsx title="src/components/CommentInput.jsx"
export default function CommentInput(~{ ref }~) { // 1. Takes the ref that Post wrote on the CommentInput tag
  return <input ~ref={ref}~ placeholder="Write a comment..." />; // 2. Puts it on the built-in input
}
```

In React 19, the `ref` you write on a component's tag arrives in that component's props, next to every other attribute. So `CommentInput` takes it out with `{ ref }`. It is the same way a component takes out `{ name }` in Lesson 08. Lesson 85 tells the full story of `ref` as a prop.

Something that can be tricky: there is only one ref here. The ref that the child receives is the very same object as `commentRef` in `Post`. During the commit, React puts the input element into `ref.current`. Because it is one object, `Post` finds the same element in `commentRef.current`.

The user clicks Comment, and the cursor appears in the field, ready for the reply:

```page width=text caption="After the fix, the user clicks Comment and types Yes! right away."
line: John: Lunch at noon?
line: [Comment]
card: typed=Yes! | good=typed
console: quiet
```

```tree dir=right caption="How the ref that Post writes on the CommentInput tag reaches the input inside CommentInput."
How `commentRef` reaches the `<input>`
- +1. `Post` writes the ref on the tag [`<CommentInput ref={commentRef} />`] | React puts `ref` **into the props** of `CommentInput`
- +2. `CommentInput` takes it out [`{ ref }`] | The same way as **`{ name }`** in Lesson 08
- +3. `CommentInput` puts it on the input [`<input ref={ref} />`] | In the commit, React puts **the input element** into `commentRef.current`
```

## PRINCIPLE | `<input ref={ref} />` in the child: the parent gets the whole element, not only `focus`

> [!PRINCIPLE]
> **Principle 2: Passing ref On: The Parent Gets the Whole DOM Element**
>
> *When a child puts the parent's ref on its `<input>`, the parent holds the real element and can do anything the browser allows with it, not only `focus`.*
>
> The ref carries the whole element, with `style`, `value`, and every other property of an input. A parent that asked for the field only to focus it can also change how it looks, and no line of the child's file shows it. Expose an element only from low-level reusable components, such as a plain text input or a button.
>
> **DO THIS:**
> ```jsx
> function handleCommentClick() {
>   ~commentRef.current.focus();~ // Uses the ref only for the one action JSX cannot say
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleCommentClick() {
>   commentRef.current.focus();
>   ~commentRef.current.style.opacity = 0.5;~ // **WRONG:** Post changes the look of a field that CommentInput owns
> }
> ```

Since the fix, `commentRef.current` in `Post` is the real input element. It is not a copy. It is the same object that `document.getElementById` would return, with every property and method the browser gives an input. So the parent can call `focus` on it, and it can do anything else the browser allows:

```jsx title="Two things the parent can do with the whole element"
~commentRef.current.focus();~ // Puts the cursor in the field
~commentRef.current.style.opacity = 0.5;~ // Draws the field half see-through
```

`style` comes from the browser, not from React. Every element has it, and it holds the element's inline styles. Setting `style.opacity` to `0.5` makes the browser draw the element half see-through.

The docs say it directly. Passing the ref on lets the parent focus the field, but "this also lets the parent component do something else, for example, change its CSS styles."

### One line in Post turns the child's field pale

Suppose someone adds a second line to the click handler in `Post`:

```jsx title="src/components/Post.jsx" startLine="7"
  function handleCommentClick() {
    commentRef.current.focus();
    ~commentRef.current.style.opacity = 0.5;~ // Changes how the input inside CommentInput looks
  }
```

The file of `CommentInput` stays unchanged. It still holds only `{ ref }` and the `<input>`.

**Beware! The click now changes how the child's field looks, and the child's file gives no hint of it.** The user clicks Comment. The cursor lands in the field, and the field turns pale. React prints no warning, because no line broke a rule of React. The browser simply did what `Post` told it to do.

The Elements panel shows where the paleness comes from. The `<input>` now carries a `style` attribute that no JSX in the project writes:

```dom caption="The Elements panel after the click: the input carries a style that only Post wrote."
<article>
  <p>John: Lunch at noon?</p>
  <button>Comment</button>
  ! <input placeholder="Write a comment..." style="opacity: 0.5;"> | note: Set by Post, not by CommentInput
</article>
```

A developer opens the file of `CommentInput` to find out why the field is pale. There is no `opacity` and no `style` in it. The answer sits in another file.

### Why the whole element makes the code fragile

The pale field is the docs' own small example. The real cost shows up over time, in four steps:
1. A developer passes `ref` on to the `<input>`, so that the parent can focus it.
2. Other code in the parent starts to use the same element for other jobs. It reads the text with `commentRef.current.value`, or it changes the styles.
3. Later, the author of `CommentInput` changes its insides. The `<input>` becomes a `<div>` that the user can type into, so that a comment can hold bold text and links.
4. Every read of `commentRef.current.value` in the parent now gets `undefined`. A div element has no value field. The bug shows up in `Post`, but the change that caused it was made in `CommentInput`.

The docs say: "exposing a ref to the DOM node inside your component makes it harder to change your component's internals later." And if the parent removes or changes elements that React manages, the page can show "inconsistent visual results or crashes", as Lesson 31 showed.

So when is it fine to hand out the whole element? The docs draw the line by the kind of component. You will typically expose DOM nodes "from reusable low-level components like buttons or text inputs." But "you won't do it for application-level components like an avatar or a comment."

A plain `MyInput`, used all over the app, is a low-level component. Handing its element to the parent is normal. Our `CommentInput` belongs to one feature of the app, the comments. So it should keep its element to itself.

## PRINCIPLE | `useImperativeHandle`: the parent gets only the methods the child returns

> [!PRINCIPLE]
> **Principle 3: useImperativeHandle: The Parent Gets Only the Methods the Child Returns**
>
> *To give the parent only some methods, the child keeps the real element in its own ref and calls `useImperativeHandle(ref, createHandle, dependencies)` at the top level; React puts the object that `createHandle` returns into the parent's `ref.current`, in place of the element.*
>
> With the whole element, the parent can do anything to the child's field. With a handle, the parent holds an object the child wrote, and anything not on it, such as `style` or `value`, is `undefined`. The `<input>` stays on the page as before. Only what the parent holds changes.
>
> **DO THIS:**
> ```jsx
> function CommentInput({ ref }) {
>   const inputRef = useRef(null);
>   ~useImperativeHandle~(ref, () => ({ // Post's ref receives only focus
>     focus() { inputRef.current.focus(); },
>   }), []);
>   return <input ref={inputRef} placeholder="Write a comment..." />;
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleSend() {
>   sendComment(~commentRef.current.value~); // **WRONG:** the handle has no value, so this sends undefined
> }
> ```

Here is the smallest version, from React's docs. `MyInput` keeps the real `<input>` in a ref of its own. It gives the parent an object with only `focus`:

```jsx title="MyInput gives its parent only focus"
import { useRef, useImperativeHandle } from 'react';

function MyInput({ ref }) {
  const realInputRef = ~useRef(null)~; // 1. A second ref that only MyInput sees

  ~useImperativeHandle~(ref, () => ({ // 2. Tells React what the parent's ref receives
    focus() {
      realInputRef.current.focus(); // 3. Our focus calls the real input's focus
    },
  }));

  return <input ~ref={realInputRef}~ />; // 4. The real input goes into MyInput's own ref
}
```

Now there are two refs, and each has its own job:
1. **`realInputRef` belongs to `MyInput`.** It sits on the `<input>`, so React puts the real element into it.
2. **`ref` belongs to the parent.** It no longer goes on the `<input>`. Instead, `useImperativeHandle` tells React what to put into it.

The docs point this out: "Note that in the code above, the `ref` is no longer passed to the `<input>`."

In the words of the docs, `useImperativeHandle` is "a React Hook that lets you customize the handle exposed as a ref." You import it from `react`. Like every Hook, you call it at the top level of the component, as Lesson 38 taught. It takes three arguments:
1. **`ref`**: "The `ref` you received as a prop."
2. **`createHandle`**: a function with no arguments that returns what the parent's ref should hold. The docs: "Usually, you will return an object with the methods you want to expose."
3. **`dependencies`, optional**: the values that `createHandle` uses, as with an Effect in Lesson 32.

When one of the dependencies changes, React runs `createHandle` again after the re-render, "and the newly created handle will be assigned to the ref." When you leave the list out, React does it after every re-render.

> [!DEFINITION]
> **An imperative handle.** [NEW] It is the object that `createHandle` returns and that React puts into the parent's `ref.current`. The docs call it "a custom object, called an *imperative handle,* with a more constrained set of methods." A handle is the part of a thing made for someone else to hold, and imperative means giving commands (Lesson 01): the handle holds the commands, such as `focus`, that the parent may give (Lesson 50).

```tree dir=right caption="The three arguments of useImperativeHandle and what React does with them."
`useImperativeHandle` in `MyInput`
- +1. `ref` | The parent's ref, **received as a prop**
- +2. `createHandle` | Returns **the object** the parent's ref will hold
- +3. `dependencies`, optional | Decides **when React makes a new handle** | Left out: **a new handle after every re-render**
```

### VS | `ref` on the input vs. `useImperativeHandle`: the same click, two different things in the parent's ref

Here are the two versions of `CommentInput` next to each other. Each one shows what `Post` finds in `commentRef.current` after the commit:

And the line in `Post` does not change at all:

```jsx title="The line in Post, for both versions of CommentInput"
~commentRef.current.focus();~ // Element: the browser's focus. Handle: our focus, which calls the browser's focus
```

Yes, it is the exact same line! Both objects have a method named `focus`. In the handle, our `focus` calls the real element's `focus`. That is why we named our method `focus`: `Post` does not need to know which of the two objects it holds.

### CommentInput keeps the input, and Post gets only focus

Here is `CommentInput` in our project. It passes the dependency list `[]`, as the docs' examples do:

```jsx title="src/components/CommentInput.jsx"
import { useRef, useImperativeHandle } from 'react';

export default function CommentInput({ ref }) {
  const inputRef = ~useRef(null)~; // CommentInput's own ref for the real input

  ~useImperativeHandle~(ref, () => ({ // Post's ref receives this object, not the input
    focus() {
      inputRef.current.focus();
    },
  }), ~[]~); // The handle uses no props or state, so every re-render keeps the same handle

  return <input ~ref={inputRef}~ placeholder="Write a comment..." />; // React puts the input into inputRef.current
}
```

`Post` keeps its one-line handler, `commentRef.current.focus()`.

Here is what each ref holds, and when:
1. When the page opens, React renders `Post` and `CommentInput`, then commits the page.
2. After the commit, `inputRef.current` inside `CommentInput` holds the input element.
3. At the same time, `commentRef.current` inside `Post` holds our object with the focus method.
4. The user clicks Comment, and `Post` calls our `focus` method. Our method calls the browser's focus on `inputRef.current`.
5. The click comes after the commit, so `inputRef.current` already holds the element, as in Lesson 31. The cursor lands in the field.

### The opacity line now throws

Suppose the opacity line from Principle 2 is still in `handleCommentClick`:

```jsx title="src/components/Post.jsx" startLine="7"
  function handleCommentClick() {
    commentRef.current.focus();
    ~commentRef.current.style~.opacity = 0.5; // **WRONG:** our object has no style, so this reads undefined
  }
```

**The handle has nothing but `focus`, so the opacity line now fails.** The docs mark the same line in their own example: "This won't work because the DOM node isn't exposed". Here is what happens when the user clicks Comment:
1. The first line calls our `focus`, and the cursor lands in the field.
2. The second line reads `style` on our object. Our object has no `style`, so the result is `undefined`.
3. JavaScript cannot set a field on `undefined`, so it throws a `TypeError`.
4. The field keeps its normal look. The cursor stays in it, because `focus` ran first, so the user can still type a reply.

```page width=text caption="With the opacity line kept, the user clicks Comment and types Yes!: the field keeps its look, and the Console shows a TypeError."
line: John: Lunch at noon?
line: [Comment]
card: typed=Yes! | good=typed
console: Uncaught TypeError: Cannot set properties of undefined (setting 'opacity')
```

That error is the handle doing its job. `Post` can no longer reach the look of a field it does not own.

### A read that quietly gets nothing

The same rule has a quieter side, and it is easier to miss. Suppose `Post` used to read the text with `commentRef.current.value`, back when it held the input element. After `CommentInput` switches to the handle, that read gives `undefined`. Our object has no value field.

No error appears on that line. `Post` simply gets nothing, and the bug shows up later, wherever `Post` uses that empty answer. So when a component switches to a handle, check the parent. Every line that used something other than the handle's methods has to change.

## PRINCIPLE | `useImperativeHandle`: only for actions no prop can say, such as `focus`

> [!PRINCIPLE]
> **Principle 4: Props First: A Handle Holds Only What No Prop Can Say**
>
> *Put in a handle only actions that no prop can say, such as focusing, scrolling, selecting text, or starting an animation; when a prop or state can say it, use the prop.*
>
> A ref is an escape hatch, as Lessons 30 and 31 showed, and so is a handle. A method such as `open`, `close`, or `clear` turns the parent's code back into commands that someone must remember to send. A prop such as `isOpen` or `text` lets state decide what the screen shows, so no command can be forgotten.
>
> **DO THIS:**
> ```jsx
> <CommentInput ref={commentRef} ~text={text}~ onTextChange={setText} /> {/* After a send, setText('') in Post empties the field */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useImperativeHandle(ref, () => ({
>   focus() { inputRef.current.focus(); },
>   ~clear~() { inputRef.current.value = ''; }, // **WRONG:** state and the value prop can already say what the field shows
> }), []);
> ```

Once you know `useImperativeHandle`, every wish of the parent starts to look like one more method. React's docs answer with an example of their own. A `Modal` is a window that opens on top of the page, and the parent decides whether it is open:

```jsx title="Two ways for a parent to open a Modal"
~modalRef.current.open();~ // Handle: the parent sends a command, and later must send close
<Modal ~isOpen={isOpen}~ /> {/* Prop: the parent's state says whether the modal is open */}
```

Both let the parent decide whether the modal is open. It may look the same, and it works the same at first, but it is NOT the same thing!
- **With `isOpen`**, the parent keeps the answer in state and passes it down as a prop, as in Lessons 08 and 12. The screen always shows what state says.
- **With `open` and `close`**, the parent sends commands, and it must remember to send each one at the right time. Forget one `close`, and the modal stays on the screen.

The docs give the verdict for a modal: "it is better to take `isOpen` as a prop like `<Modal isOpen={isOpen} />`."

### `clear()` vs. `setText('')`: a command someone can forget, or state that React follows

On our page, the same question comes up with the text in the field. After the user sends a comment, the field should be empty again. One idea is to add a `clear` method to the handle, next to `focus`. The other is to keep the text in state:

```jsx title="Emptying the comment field with a handle method, and with state"
~commentRef.current.clear();~ // Handle: Post must remember this command after every send
~setText('');~ // State: the input shows value={text}, so React empties it on the next render
```

For the state version, `Post` keeps the text in a state variable, `text`. It passes `text` down to `CommentInput` as a prop. It also passes a callback prop, `onTextChange`, that `CommentInput` calls on every keystroke, as in Lesson 23:

```jsx title="src/components/CommentInput.jsx, with the text kept in Post"
import { useRef, useImperativeHandle } from 'react';

export default function CommentInput({ ref, ~text~, onTextChange }) { // Post owns the text and passes it down
  const inputRef = useRef(null);

  useImperativeHandle(ref, () => ({
    focus() {
      inputRef.current.focus();
    },
  }), []);

  return <input ref={inputRef} ~value={text}~ onChange={e => onTextChange(e.target.value)} placeholder="Write a comment..." />; // The field always shows what text holds in Post
}
```

That is a controlled input, from Lesson 20. When `Post` sets `text` to an empty string, React empties the field on the next render.

It looks like one more method, but `clear` is NOT the same kind of thing as `focus`! The text in the field is a value the user sees. A value on the screen belongs in state, and a prop can carry it. Focus has no such value: JSX has no prop that says "this field has the cursor now", as Lesson 31 showed. So `focus` stays in the handle, and `clear` stays out.

```tree caption="What goes into a handle and what stays a prop."
What the parent wants from the child
- +An action no prop can say [`focus` `scrollIntoView`] | Focusing, scrolling, selecting text, **starting an animation** | **A method on the handle**
- !Something a prop can say [`clear` `open` `close`] | What the field shows, **whether a modal is open** | **A prop from state**, such as `value` or `isOpen`
```

The docs put the rule plainly: "You should only use refs for *imperative* behaviors that you can't express as props." Their examples are "scrolling to a node, focusing a node, triggering an animation, selecting text, and so on." And they add: "If you can express something as a prop, you should not use a ref."

`Post` holds the ref and the click handler:

```jsx title="src/components/Post.jsx"
import { useRef } from 'react';
import CommentInput from './CommentInput.jsx';

export default function Post() {
  const commentRef = ~useRef(null)~; // Principle 3: after the commit, holds the handle with only focus

  function handleCommentClick() {
    ~commentRef.current.focus();~ // Principles 2 and 4: only the one action no prop can say
  }

  return (
    <article>
      <p>John: Lunch at noon?</p>
      <button onClick={handleCommentClick}>Comment</button>
      <CommentInput ~ref={commentRef}~ /> {/* Principle 1: arrives in CommentInput as a prop */}
    </article>

}
```

`CommentInput` keeps the input element to itself and exposes only `focus`:

```jsx title="src/components/CommentInput.jsx"
import { useRef, useImperativeHandle } from 'react';

export default function CommentInput(~{ ref }~) { // Principle 1: the ref that Post wrote on the tag
  const inputRef = useRef(null);

  ~useImperativeHandle~(ref, () => ({ // Principles 3 and 4: only focus, nothing a prop could say
    focus() {
      inputRef.current.focus();
    },
```

### How React calls the components and fills the refs

When the page opens, React calls the three components in the order of their tags. During this render, both refs still hold `null`. After the commit, each ref holds what its component asked for:

```tree caption="The order in which React calls the components, and what each ref holds after the commit."
`App` [1. Called first] | **Root component** | Renders `<Post />`
- +`Post` [2. Called second] | Creates **`commentRef`**, `null` during the render | After the commit: **the handle with only `focus`**
  - +`CommentInput` [3. Called third] | Creates **`inputRef`**, `null` during the render | After the commit: **the real `<input>` element**
```

| What `CommentInput` does with the ref | What `commentRef.current` holds | What the user sees after the click on Comment |
| :--- | :--- | :--- |
| **Ignores `ref`** | `null` | Nothing happens, and the Console shows a `TypeError` |
| **Puts `ref` on the `<input>`** | The real `<input>` element | The cursor is in the field, and `Post` can also turn the field pale |
| **Calls `useImperativeHandle` with only `focus`** | An object with only `focus` | The cursor is in the field, and any other read in `Post` gives `undefined` |
| **Adds `clear` or `open` to the handle** | An object with commands for things a prop could say | The page works until someone forgets a command; a prop such as `text` or `isOpen` cannot be forgotten |

One last time, the sentence of this lesson: **the parent gets only what the child hands it. Put the ref on the `<input>`, and the parent gets the whole element. Use `useImperativeHandle`, and the parent gets only the methods you return.**

## For the Interview

> **The Interview Question:** How does a child expose a focused API to its parent through a ref?

### How to Answer Clearly in 30 Seconds

"By default, a component's DOM nodes are private, so a ref the parent writes on my component stays `null`. In React 19, that `ref` arrives as a prop. If I put it on my `<input>`, the parent gets the whole DOM node and can do anything with it, including changing its styles. To expose only what the parent needs, I keep the node in my own ref and call `useImperativeHandle` at the top level. I pass it the parent's `ref` and a function that returns an object, for example one with only `focus`. React puts that object into the parent's `ref.current` in place of the node. Three facts keep it right:
1. **The parent's code stays the same**: `ref.current.focus()` works on the node and on the handle, and anything not in the handle is `undefined`.
2. **The page stays the same**: the `<input>` is still in the DOM; only what the parent holds changes.
3. **Props first**: a handle is only for actions no prop can say, such as focusing, scrolling, or selecting text. For a modal, I pass `isOpen` as a prop instead of exposing `open` and `close`."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"How did a component receive a ref before React 19?"**
   It was wrapped in `forwardRef`, which passed the ref as a second argument after the props, and the same Hook was used inside it. The docs now say: "In React 19, `forwardRef` is no longer necessary. Pass `ref` as a prop instead." You will still meet `forwardRef` in older code at work, and Lesson 99 teaches it.
2. **"Do the methods of a handle have to match DOM methods?"**
   No. `createHandle` can return any value, and the methods are our own. The docs show a `Post` that exposes one method, `scrollAndFocusAddComment`. It scrolls a comment list to the bottom and focuses the comment field in one call. The parent calls one method, and the child decides which nodes take part. The docs also call this Hook "rarely used".
3. **"What happens if you leave out the dependency list?"**
   React runs `createHandle` again after every re-render of the child and assigns the new handle to the parent's ref, so the parent gets a new object each time. With a list, React makes a new handle only when one of the listed values changes. With `[]`, as in our `CommentInput`, every re-render keeps the same handle, because the handle uses no props or state.

```tree dir=right caption="Interview comparison: exposing the whole DOM node vs. exposing a handle with useImperativeHandle."
The whole node vs. a handle in an interview
- !Pass `ref` on to the input [`<input ref={ref} />`] | The parent holds **the real DOM node** | The parent can **change styles or remove it**; fits **low-level inputs and buttons**
- +Return a handle [`useImperativeHandle`] | The parent holds **an object the child wrote** | The parent can call **only the chosen methods**, such as `focus`
```
