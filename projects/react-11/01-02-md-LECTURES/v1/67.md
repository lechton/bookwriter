# Lecture 67: How the Search Box Stays Fast While a Slow List Renders

*(Why does typing stutter when the same text also filters a long list?)*

> INTERVIEW QUESTION | ❱❱ MORE | How do you keep typing responsive while a big re-render runs with useTransition?

---

## VS | One `query` for the Field and the List vs. a Second `searchQuery` in a Transition: one freezes the typing, two let every letter in at once

> In a search field over a long list, every letter the user types must appear at once, and the results can follow a moment later. **`useTransition` splits one keystroke into two updates: an urgent one for the `<input>` field, and a Transition for the list**. The list renders no faster, but React renders it in the background, so the next letter never waits for it.

Think of the search field on any shop or blog. You type `1`, then `2`, and the list of results under it gets shorter with every letter. Nobody minds if the results take a moment. Everybody minds if the letters show up late.

Remember Lesson 66? The browser has one main thread. It runs your JavaScript, handles every keystroke, and paints the screen, one thing after the other. While React renders a slow list, the browser can do nothing else.

Now the part that surprises most developers. In a controlled `<input>` field, the letter on the screen is state. React writes `query` into the `value` of the field. So the new letter appears only when React renders again with the new `query` and commits it.

If the same `query` also filters a slow list, the letter and the list come in the same render. **The letter waits for the list.**

```jsx title="One query for the field and the list"
<input value={~query~} onChange={e => setQuery(e.target.value)} /> {/* The field shows query */}
<PostList query={~query~} /> {/* The slow list reads the same query */}
```

The fix is the split you saw for a tab click in Lesson 66, now for a keystroke. One input from the user makes two updates. React's docs say it in one sentence: "a single user input should result in both an urgent update and a non-urgent one."

```jsx title="One keystroke, two state variables"
setQuery(text); // Urgent: the field shows the letter at once
~startTransition~(() => { // A Transition: React renders the new list in the background
  setSearchQuery(text);
});
```

Keep one sentence in mind for the whole lesson. **The `<input>` field must answer at once. The list can follow a moment later.**

### The Words This Lesson Stands On

> [!DEFINITION]
> **A controlled `<input>` field.** [REVIEW] A controlled field shows what your state holds: `<input value={query} onChange={e => setQuery(e.target.value)} />`. When the user types a letter, React calls `onChange`, and your code calls `setQuery` with the new text. The field shows only what `query` holds, so the new letter reaches the screen when React renders again with the new `query` and commits it to the DOM (Lesson 20).

> [!DEFINITION]
> **An urgent update and a Transition.** [REVIEW] A normal call to a set function in an event handler, such as `setQuery('1')`, is an urgent update: React renders it to the end without a break, and nothing can interrupt it. A set function called inside `startTransition` makes a Transition: React renders it in the background, gives the main thread back to the browser between pieces of its work, and drops that render when an urgent update comes in. Nothing of a Transition reaches the screen before its commit (Lesson 66).

> [!DEFINITION]
> **memo.** [REVIEW] `memo` is a function from React that wraps a component: `const PostList = memo(function PostList({ query }) { ... })`. When the parent renders again, React compares each new prop with the old one, using `Object.is`. If every prop is the same, React skips the component and reuses its last result (Lesson 55).

### VS | `query` vs. `searchQuery`: the same text at two speeds

Both state variables get the same text from the same keystroke. When the user stops typing, both hold the same value, such as `12`. It looks the same, but it is NOT the same thing!
- **`query`** follows every keystroke at once, because the field must show what the user typed.
- **`searchQuery`** lags behind, and it may even skip a value. When the user types the next letter before the list for `1` is ready, that list never reaches the screen.

The whole recipe of this lesson takes six steps:
1. We keep two state variables: `query` for the field, and `searchQuery` for the list.
2. On every keystroke, `query` changes at once, as an urgent update.
3. `searchQuery` changes inside a Transition, so React renders the new list in the background.
4. We wrap the list in `memo`, so the render for the urgent update can skip the slow list.
5. When the user types the next letter before the new list is ready, React throws the unfinished list away. It renders the list for the latest text.
6. A flag named `isPending` tells us that the list is behind, so we can fade the old list while the new one renders.

Steps 1 to 3 and step 5 are what Lesson 66 did for a tab click, now driven by a keystroke. Steps 4 and 6 are new in this lesson.

```tree caption="One keystroke makes two updates: the field changes at once, and the list follows in the background."
One keystroke in the search field
- +Urgent update [`setQuery`] | Puts the typed letter **in the field** | The user sees the letter **at once**
- +Transition [`setSearchQuery`] | React renders the new list **in the background** | The list **follows a moment later**
```

### What Is at Stake

What is at stake is the field itself. It must answer every keystroke at once. React's docs explain why: "Urgent updates like typing, clicking, or pressing, need immediate response to match our intuitions about how physical objects behave. Otherwise they feel "wrong"."

When the field waits for the list, the letters appear late and in jumps. The user does not know that React is busy. The user sees a field that ignores the keyboard, and stops trusting the page.

Developers make three classic mistakes here:
1. **They wrap the field's own `setQuery` in `startTransition`.** React's docs say it plainly: "You can't use a Transition for a state variable that controls an input". Principle 2 shows what goes wrong.
2. **They add the second state variable but forget `memo` on the list.** The typing stays slow, and they conclude that `useTransition` does nothing. Principle 3 shows why.
3. **They think the Transition makes the list render faster.** It does not. The list takes exactly as long as before. The Transition only lets the keystroke go first.

### The Rule of Thumb: does the user type into it?

**Ask one question about the text that drives a slow list: does the user type into it? If yes, keep the state of the `<input>` field urgent, and give the list its own state variable, set inside `startTransition`.**

### Five Ways to Handle Typing over a Slow List

A search field over a slow list is a common job at work. A senior developer picks one of five ways:
1. **Leave it as it is.** This fits when the list renders fast enough. React's docs warn: "Don't optimize prematurely!"
2. **Render fewer rows with a virtualized list**, as seen in Lesson 62. This fits when the list is long but each row is cheap.
3. **Two state variables and `useTransition`.** This is the way of this lesson. It fits when our own component holds both set functions, and we want `isPending`. React's docs: "You can declare two separate state variables", one for the field and one "that you will update in a Transition."
4. **One state variable and `useDeferredValue`.** Lesson 68 teaches it, and it is also the way when the text comes from a prop. React's docs: "Alternatively, you can have one state variable, and add `useDeferredValue` which will "lag behind" the real value."
5. **Debouncing or throttling.** To debounce is to wait until the user stops typing for a moment. To throttle is to update at most once in a set time. React's docs say they "still produce a janky experience because they're *blocking:* they merely postpone the moment when rendering blocks the keystroke."

```tree caption="Five ways to handle typing over a slow list, and when each one fits."
Typing in a search field that drives a slow list
- +Leave it as it is | Fits when the list **renders fast enough** | **No extra code**
- +Virtualized list | Fits when the list is **long but each row is cheap** | Renders **only the rows on the screen**
- +Two state variables and `useTransition` [`query` `searchQuery`] | Fits when **we own both set functions** | Gives us **`isPending`** to show the list is behind
- +One state variable and `useDeferredValue` | Fits when the text **comes from a prop** | Taught in **Lesson 68**
- !Debouncing or throttling | **Waits a fixed time**, then renders | ~The render **still blocks** the next keystroke
```

Our text comes from our own `<input>` field, and we own both set functions, so this lesson uses the third way.

We start with the code every developer writes first, and we fix it step by step:

**PRINCIPLES:** The `<input>` field must answer at once. The list can follow a moment later. Five principles follow:
1. **Principle 1: One `query` Freezes the Field.** When one state variable drives both the field and a slow list, the typed letter waits until React has rendered the whole list.
2. **Principle 2: `useTransition` Makes Two Updates from One Keystroke.** The field's `query` stays urgent. A second state variable, `searchQuery`, changes inside `startTransition` and drives the list.
3. **Principle 3: `memo` Lets the Urgent Render Skip `PostList`.** The urgent update renders `SearchPage` again, and with it every child. Only a list wrapped in `memo` skips that render, because its prop still holds the old text.
4. **Principle 4: A New Keystroke Throws Away the Unfinished List.** When the user types `2` before the list for `1` is ready, React drops that list. It renders only the latest text.
5. **Principle 5: `isPending` Fades the Old List from Outside.** `isPending` is `true` while the list is behind. We fade the old list on a wrapper `<div>`, so the props of `PostList` stay the same.

## PRINCIPLE | One `query` for the field and the list: every letter waits for the whole list

> [!PRINCIPLE]
> **Principle 1: One `query` State: Every Letter Waits for the Whole List**
>
> *When one state variable drives both a controlled `<input>` field and a slow list, every keystroke renders the whole list before the typed letter can appear.*
>
> The field shows `query`, and the list reads the same `query`. When the user types a letter, React must render every matching slow post before it commits the new `query`. Until then, the field shows the old text. The user types, and nothing happens.
>
> **DO THIS:**
> ```jsx
> <input value={query} onChange={handleChange} /> {/* handleChange sets query at once and searchQuery in a Transition */}
> <PostList query={~searchQuery~} /> {/* The list reads its own state variable, which Principle 2 adds */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <input value={query} onChange={e => setQuery(e.target.value)} />
> <PostList query={~query~} /> {/* **WRONG:** every letter waits until all the matching slow posts have rendered */}
> ```

### The Posts Page with One `query`

This is the controlled field of Lesson 20, and the list filters by `query` while it renders, as seen in Lesson 22. The app file only renders the search page:

```jsx title="src/App.jsx"
import SearchPage from './components/SearchPage.jsx';

export default function App() {
  return ~<SearchPage />~; // The whole page lives in SearchPage
}
```

`SearchPage` holds `query` and passes it to the list:

```jsx title="src/components/SearchPage.jsx"
import { useState } from 'react';
import PostList from './PostList.jsx';

export default function SearchPage() {
  const [query, setQuery] = useState('');

  return (
    <>
      <input
        value={query}
        onChange={e => ~setQuery(e.target.value)~} // Every keystroke is an urgent update
        placeholder="Search posts"
      />
      <PostList query={~query~} /> {/* The list gets the same text as the field */}
    </>
  );
}
```

The list file builds the titles, filters them, and renders one slow post for each match:

```jsx title="src/components/PostList.jsx"
const posts = [];
for (let i = 1; i <= 500; i++) {
  posts.push('Post #' + i);
}

export default function PostList({ query }) {
  console.log('PostList rendered:', query);
  const results = posts.filter(title => ~title.includes(query)~); // Fast: 500 short strings
  return (
    <ul>
      {results.map(title => <SlowPost key={title} title={title} />)}
    </ul>
  );
}

function SlowPost({ title }) {
  const startTime = performance.now();
  while (performance.now() - startTime < ~1~) {} // Slow: waits 1 millisecond for every post
  return <li>{title}</li>;
}
```

Three names in this file come from our own code:
- **`posts`** is the array of 500 titles. The loop at the top of the file builds it once, when the file loads. It is neither a prop nor state.
- **`results`** holds the matching titles. `PostList` works it out again on every render, as seen in Lesson 22.
- **`SlowPost`** is the slow row of Lesson 66, and it gets each `title` as a prop. Each title is unique, so the title also serves as the `key`, as seen in Lesson 18.

The `console.log` line prints one line each time React calls `PostList`, as seen in Lesson 54. Our project runs inside `<StrictMode>`, which calls every component twice in development, as seen in Lesson 47. So every line appears twice in the Console.

### Why the Letter Waits for the List

**The `1` cannot appear before the list for `1` is finished.** Filtering 500 short titles is fast. Rendering 176 slow posts is slow: at least 176 milliseconds, because each post waits 1 millisecond. In development, Strict Mode calls each component twice, so it takes about twice that.

Here is what happens when the user types `1` and then `2`:
1. The page shows an empty field and all 500 posts.
2. The user types `1`. `setQuery('1')` is an urgent update.
3. React renders `SearchPage`, then `PostList`, which renders 176 slow posts. The Console prints `PostList rendered: 1`.
4. While React renders, the user types `2`. Nothing changes on the page, and the field still looks empty. The browser cannot handle the keystroke, because React keeps the main thread busy, and an urgent render cannot be interrupted.
5. React commits: the field shows `1`, and the list shows 176 posts, at the same moment.
6. Now the browser handles the `2`. `setQuery('12')` starts another full render, this time of 15 slow posts. Then `12` appears.

The user saw the field stand still and then jump. When the user stops typing, the page is right again. The Console holds three pairs of lines: one pair from the page load, with an empty text, and one pair for each letter:

### The Real Mistake: Blaming the Filter

A developer sees the field freeze over a long list and makes a natural guess:
1. The developer thinks the `filter` call is the slow part, and wraps it in `useMemo`, as seen in Lesson 56.
2. The typing is still slow. `query` changes on every keystroke, so `useMemo` must work out the list again, and the rows must render again.
3. The slow part was never the filter. It is rendering the rows.

React's docs describe exactly this case: "Sometimes, you can't skip re-rendering because the screen actually needs to update." The list must change. What we can change is when it changes.

Remember: one `query` for the field and the list means the letter waits for the whole list.

## PRINCIPLE | `useTransition`: one keystroke makes an urgent update for the field and a Transition for the list

> [!PRINCIPLE]
> **Principle 2: Two State Variables: `useTransition` Splits One Keystroke into an Urgent Update and a Transition**
>
> *Call `useTransition` at the top level to get `isPending` and `startTransition`; keep the field's `setQuery` urgent, and set a second state variable, `searchQuery`, inside `startTransition`.*
>
> The field must show each letter the moment the user types it, so its state stays urgent. The list can wait, so it reads its own state variable, set inside a Transition. One keystroke now makes two updates, and React can handle them at two speeds.
>
> **DO THIS:**
> ```jsx
> function handleChange(e) {
>   const text = e.target.value;
>   setQuery(text);
>   ~startTransition~(() => { // Only the state of the list is a Transition
>     setSearchQuery(text);
>   });
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function handleChange(e) {
>   ~startTransition~(() => { // **WRONG:** the state that controls the field is now a Transition
>     setQuery(e.target.value);
>   });
> }
> ```

### `useTransition`: the `startTransition` of Lesson 66, plus `isPending`

Remember the `startTransition` of Lesson 66? You imported it from `react` and wrapped a set function in it. React then rendered that update as a Transition. `useTransition` is the Hook that gives you the same function, plus one extra value.

> [!DEFINITION]
> **useTransition.** [NEW] `useTransition` is a Hook from React. React's docs: "`useTransition` is a React Hook that lets you render a part of the UI in the background." You call it at the top level of a component, with no arguments, like every Hook (Lesson 38). It returns an array with exactly two items, in this order: `isPending`, a boolean that "tells you whether there is a pending Transition", and `startTransition`, which marks every state update made while its function runs as a Transition (Lesson 67).

```jsx title="Calling useTransition at the top level of SearchPage"
const [~isPending~, ~startTransition~] = useTransition(); // React returns the two items in this order
```

We name `isPending` here, and we use it in Principle 5.

The `startTransition` from the Hook does the same job as the one we imported from `react` in Lesson 66. React's docs say the imported one "is very similar to `useTransition`, except that it does not provide the `isPending` flag." So the difference that matters is `isPending`, and only the Hook gives it.

```tree caption="startTransition from useTransition and startTransition imported from react: the same job, but only the Hook gives isPending."
Two places to get `startTransition`
- +From the Hook [`useTransition`] | Marks the updates inside it as a **Transition** | Also gives **`isPending`** | Only **inside a component**
- +Imported from `react` | **Same job**: marks the updates as a **Transition** | ~Gives **no `isPending`** | Works **anywhere**, such as a data library
```

### Why the State of the Field Must Stay Outside the Transition

Here is the tempting mistake. A developer reads that `startTransition` keeps typing smooth, and wraps the update of the field itself:

```jsx title="The state of the field inside startTransition" bad="2"
startTransition(() => {
  ~setQuery(e.target.value)~; // **WRONG:** the state that controls the field is now a Transition
});
```

React's docs mark this same code with the comment "Can't use Transitions for controlled input state". They give the reason: "Transitions are non-blocking, but updating an input in response to the change event should happen synchronously."

Think about what the field shows. It shows `query`, and the user expects the letter the moment they type it. A Transition is allowed to wait, so the field can no longer answer the keystroke at once. The typed `1` vanishes from the field until the list is ready. When the user types two letters quickly, the field can end with `2` alone, and the `1` is lost.

That is why one keystroke needs two state variables. The field and the list need the same text at two different speeds. The field needs it at once, and the list can wait.

### The Posts Page with `query` and `searchQuery`

Only the search page file changes. It imports `useTransition`, adds `searchQuery` and a handler, and passes the new state variable to the list:

```jsx title="src/components/SearchPage.jsx" good="6,7,12,13,14,20"
import { useState, ~useTransition~ } from 'react'; // useTransition comes from React, like useState
import PostList from './PostList.jsx';

export default function SearchPage() {
  const [query, setQuery] = useState('');
  const [searchQuery, setSearchQuery] = useState('');
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    const text = e.target.value;
    setQuery(text); // Urgent: the field shows the letter
    startTransition(() => {
      ~setSearchQuery(text)~; // Transition: the list follows in the background
    });
  }

  return (
    <>
      <input value={query} onChange={handleChange} placeholder="Search posts" />
      <PostList query={~searchQuery~} /> {/* The list now reads searchQuery */}
    </>
  );
}
```

`text` is a local variable that keeps `e.target.value`, so both set functions get the same text. Inside `PostList`, the prop is still named `query`. It now holds the value of `searchQuery`, so the list file does not change.

### The Surprise: the Field Still Freezes

**With two state variables and a plain `PostList`, the field still freezes, and now for all 500 posts.** The render for the urgent update did not stay small. Here is what happens when the user types `1`:
1. `setQuery('1')` is urgent. `setSearchQuery('1')` is a Transition.
2. React renders the urgent update first. `SearchPage` runs with the new text in `query`. The list's state variable, `searchQuery`, still holds the empty text.
3. `SearchPage` returns the list with `searchQuery` as its prop. When a parent renders, React renders its children again too, as seen in Lesson 54. So `PostList` renders with `''`: all 500 slow posts.
4. The Console prints `PostList rendered: ` with an empty text. Only after those 500 posts does React commit the `1` in the field.
5. Then React renders the Transition. The Console prints `PostList rendered: 1`, and the list changes to 176 posts.

```page width=text caption="After the user typed 1, with two state variables and a plain PostList: the top of the 176 matching posts, and a Console that shows the list rendered again with the old empty text."

line: Post #12

log: PostList rendered: | PostList.jsx:7
log: PostList rendered: | PostList.jsx:7

Read the Console from the top:
- **The first pair** comes from the page load.
- **The second pair** is the problem. The list rendered all 500 posts again, with the old empty text, before the field could show the `1`.
- **The last pair** comes from the Transition.

The Transition decides when the new list renders. It does not stop the render for the urgent update from calling `PostList`. Principle 3 gives the fix.

## PRINCIPLE | `memo` on `PostList`: the urgent render skips the slow list

> [!PRINCIPLE]
> **Principle 3: `memo` on the Slow List: The Urgent Update Must Skip `PostList`**
>
> *Wrap the slow list in `memo`, so the render for the urgent update skips it while its `query` prop still holds the old `searchQuery`; only the Transition then renders the list.*
>
> Every keystroke renders `SearchPage` again, and React renders its children with it. A plain `PostList` renders all its slow posts in that render, so the field waits as before. With `memo`, React sees that `query` did not change and skips the list. The slow work moves into the Transition, where it no longer blocks the field.
>
> **DO THIS:**
> ```jsx
> const PostList = ~memo~(function PostList({ query }) { // Skipped while query holds the old text
>   const results = posts.filter(title => title.includes(query));
>   return <ul>{results.map(title => <SlowPost key={title} title={title} />)}</ul>;
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> function ~PostList~({ query }) { // **WRONG:** renders all its slow posts on every keystroke, so the field still freezes
>   const results = posts.filter(title => title.includes(query));
>   return <ul>{results.map(title => <SlowPost key={title} title={title} />)}</ul>;
> }
> ```

### VS | A Plain `PostList` vs. a `PostList` Wrapped in `memo`: only the wrapped list skips the urgent render

Remember the surprise at the end of Principle 2. In React, when a parent renders, every child renders with it. A Transition does not change that.

Now remember `memo` from Lesson 55. You wrap a component in it, and React skips that component when its props are the same as last time. That is exactly our case. In the urgent render, `searchQuery` still holds the old text, so the prop of the list did not change.

Here are the two ways to write the list, side by side:

```jsx title="A plain PostList vs. a PostList wrapped in memo"
function PostList({ query }) { ... } // Renders again every time SearchPage renders
const PostList = ~memo~(function PostList({ query }) { ... }); // Skips the render when query is the same as last time
```

It looks the same, but it is NOT the same thing! Both show the same list when the page opens and after the user stops typing. They differ only in the render for the urgent update:
- **The plain `PostList`** renders all its slow posts there.
- **The `PostList` wrapped in `memo`** is skipped, because its `query` prop still holds the old text.

The key idea to remember: a Transition decides when the new list renders. It does not stop the parent's render from calling its children. Only `memo` does that.

### The Posts Page with `memo` on `PostList`

Only the list file changes. It imports `memo` and wraps `PostList`:

```jsx title="src/components/PostList.jsx" good="1,8"
import { memo } from 'react';

const posts = [];
for (let i = 1; i <= 500; i++) {
  posts.push('Post #' + i);
}

const PostList = ~memo~(function PostList({ query }) { // Skipped when query did not change
  console.log('PostList rendered:', query);
  const results = posts.filter(title => title.includes(query));
  return (
    <ul>
      {results.map(title => <SlowPost key={title} title={title} />)}
    </ul>
  );
});

function SlowPost({ title }) {
  const startTime = performance.now();
  while (performance.now() - startTime < 1) {} // Waits 1 millisecond for every post
  return <li>{title}</li>;
}

export default PostList;
```

### What Happens When the User Types `1` Now

**Now the `1` appears at once, and the list follows a moment later.** One keystroke makes two renders, and `PostList` takes part only in the second:
1. The user types `1`.
2. **The first render, for the urgent update:** `SearchPage` runs with the new text in `query`. The list's state variable, `searchQuery`, still holds the empty text. `PostList` gets the same empty text as last time, so `memo` skips it. No new line appears in the Console.
3. React commits: the field shows `1` at once, and the list still shows all 500 posts.
4. **The second render, for the Transition:** React renders `SearchPage` again, and now the new text reaches `searchQuery`. `PostList` gets a new `query` and renders 176 slow posts in the background.
5. The Console prints `PostList rendered: 1`. React commits the Transition, and the list changes to 176 posts.

For a moment, the field says `1` while the list still shows all 500 posts. That is the list lagging behind, on purpose:

### The Real Mistake: Concluding That `useTransition` Does Nothing

This is the mistake that Principle 2 ended on, and it is common:
1. A developer adds `useTransition` and the second state variable, as React's docs show.
2. The developer leaves `PostList` as a plain function.
3. The typing is still janky, and the developer concludes that `useTransition` does nothing.
4. The Console tells the truth. On every keystroke, it prints `PostList rendered:` with the old text, because the render for the urgent update still renders the list.

In React's own example for this Hook, the slow tab `PostsTab` is wrapped in `memo` the same way. React's docs give the reason for the same pattern with `useDeferredValue`: "Without `memo`, it would have to re-render anyway, defeating the point of the optimization."

Remember: the Transition moves the slow list to the background only when `memo` keeps it out of the urgent render.

## PRINCIPLE | A new keystroke during a Transition: React throws away the unfinished list

> [!PRINCIPLE]
> **Principle 4: Interrupted Transitions: A New Keystroke Drops the Unfinished List**
>
> *A Transition's render can be interrupted by a newer urgent update; when the user types again before the list is done, React handles the keystroke first, throws away the unfinished list, and renders only the latest `searchQuery`.*
>
> The user types `1` and then `2` quickly. The field answers both keystrokes at once. The list for `1` was still rendering in the background when the `2` arrived, so React dropped it and rendered the list for `12`. Only state updates made during the `startTransition` call can be interrupted this way.
>
> **DO THIS:**
> ```jsx
> setQuery(text);
> startTransition(() => {
>   ~setSearchQuery(text)~; // Made during the call: a Transition the next keystroke can interrupt
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> setQuery(text);
> startTransition(() => {
>   setTimeout(() => ~setSearchQuery(text)~, 300); // **WRONG:** runs later, outside the Transition, so it blocks the next keystroke
> });
> ```

### Two Fast Keystrokes, and One List That Never Appears

**When the user types fast, React never shows the list for `1`.** The field shows `1`, then `12`, each at once. The list goes from 500 posts straight to 15. The list of 176 posts for `1` never reaches the screen.

React's docs describe the case of several characters typed in a row. React "will throw out the stale rendering work that wasn't finished and render only the latest update."

The code does not change. The page of Principle 3 already does this. What we watch is the order of events when the user types `1`, and then types `2` while the 176 posts render in the background:
1. The user types `1`. The field shows `1` at once, as in Principle 3.
2. React starts the Transition: it renders the 176 posts for `1` in the background.
3. The user types `2` during that render. This keystroke is an urgent update, and it interrupts the Transition. React's docs: "A state update marked as a Transition will be interrupted by other state updates."
4. React renders and commits the urgent update: the field shows `12`. `PostList` gets the old empty text again, so `memo` skips it. The list still shows all 500 posts.
5. React throws away the unfinished list for `1` and renders the Transition for `12`: 15 posts.
6. React commits: the list goes from 500 posts to 15.

::: row caption="The user types 1, then 2, before the list for 1 is ready: the field answers each keystroke, and the list jumps from 500 posts to 15."

The Console may still print `PostList rendered: 1` for the list that React started and then threw away. That line only means that React began the render. The list never reached the screen.

Why did it disappear without a trace? Because it was never committed. React had rendered part of it in memory, but nothing reaches the screen before the commit, as seen in Lesson 66. So the user never waits for results they no longer want. As React's docs say, the user "doesn't expect to see every intermediate value on screen."

```tree dir=right caption="A new keystroke interrupts the Transition: React handles the keystroke first and renders only the latest text."
The user types `1`, then `2`, quickly
- +1. Urgent update for `1` | The field shows **`1` at once**
- !2. Transition for `1` | 176 posts render in the background | ~**Interrupted** by the next keystroke
- +3. Urgent update for `12` | The field shows **`12` at once**
- +4. Transition for `12` | React renders **only the latest text** | The list shows **15 posts**; the list for `1` **never appears**
```

### VS | A Transition vs. a Debounce: both keep typing smooth, only the Transition can be interrupted

Many developers reach for a debounce here: wait 300 milliseconds after the last keystroke, then update the list. In their mind, both do the same job, because both keep the typing smooth. It looks the same, but it is NOT the same thing!
- **With a debounce**, the list waits a fixed time, and then its render blocks the main thread, as in Principle 1. When the user types again during that render, the new letter waits. React's docs: debouncing and throttling "merely postpone the moment when rendering blocks the keystroke."
- **With a Transition**, the list starts rendering at once, and the next keystroke interrupts it. React's docs: "Unlike debouncing or throttling, it doesn't require choosing any fixed delay."

A debounce is still the right tool when the slow work is not rendering, such as a request to a server. React's docs: "If the work you're optimizing doesn't happen during rendering, debouncing and throttling are still useful."

### The Real Mistake: Mixing a Delay into the Transition

A developer wants both a short delay and a Transition. So the developer puts a `setTimeout` inside `startTransition`, to set the text of the list 300 milliseconds later.

But `startTransition` marks only the updates made while our function runs. The update now runs later, after the call has ended. React's docs are clear: "If you try to perform state updates in a `setTimeout`, for example, they won't be marked as Transitions."

So the render of the list is no longer a Transition. The next keystroke cannot interrupt it, and the letter waits for the list again.

Remember: the next letter always goes first, and React keeps only the list for the latest text.

## PRINCIPLE | `isPending`: fade the old list on a wrapper outside `PostList`

> [!PRINCIPLE]
> **Principle 5: Pending Visual State: `isPending` Fades the Old Results Outside the List**
>
> *`isPending` is `true` from the first call to `startTransition` until the Transition's final state is on the screen; use it to show that the list is behind, on an element outside the memoized list.*
>
> The field changes at once, but the list follows a moment later. During that moment, a faded list tells the user the new results are on their way. The sign must sit outside `PostList`, because `isPending` changes in the render for the urgent update, and any changed prop makes `memo` render the slow list again.
>
> **DO THIS:**
> ```jsx
> <div style={{ ~opacity: isPending ? 0.7 : 1~ }}> {/* PostList keeps the same props */}
>   <PostList query={searchQuery} />
> </div>
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <PostList query={searchQuery} ~isPending={isPending}~ /> {/* **WRONG:** a changed prop on every keystroke, so memo renders all the slow posts */}
> ```

### A Faded List Says "the Results Are Behind"

Go back to the moment after the urgent update in Principle 3. The field says `1`, but the list still shows all 500 posts. Nothing on the page says that a new list is coming. The user sees a list that does not match the field, and may think the search is broken.

`isPending` gives us that sign.

> [!DEFINITION]
> **isPending and a pending visual state.** [NEW] `isPending` is the first item that `useTransition` returns, a boolean that React sets for you: your code never calls a set function for it. React's docs: "the `isPending` state switches to `true` at the first call to `startTransition`, and stays `true` until all Actions complete and the final state is shown to the user." A pending visual state is what the page shows during that time: a sign, such as a faded list, that the new results are on their way (Lesson 67).

Here is the smallest code, with a fade like the one React's docs show for a stale list:

```jsx title="Fading the old list while the Transition is pending"
<div style={{ ~opacity: isPending ? 0.7 : 1~ }}> {/* Faded while the new list renders, full strength after */}
  <PostList query={searchQuery} />
</div>
```

`opacity` is a CSS property. At `0.7`, the list is partly see-through. At `1`, it is at full strength.

### VS | A Wrapper `<div>` vs. an `isPending` Prop on `PostList`: only the wrapper keeps `memo` working

Passing `isPending` into the list feels natural, because the fade belongs to the list. But it brings the freeze back:

```jsx title="The fade on a wrapper div vs. isPending passed into PostList"
<div style={{ opacity: isPending ? 0.7 : 1 }}><PostList query={searchQuery} /></div> {/* The props of PostList stay the same */}
<PostList query={searchQuery} ~isPending={isPending}~ /> {/* PostList gets a changed prop on every keystroke */}
```

It looks the same, but it is NOT the same thing! Both fade the old list. The difference is in the render for the urgent update:
- **With the fade on a wrapper `<div>`:** `PostList` still gets only `query`, which holds the old text. `memo` skips the list, and the field answers at once.
- **With `isPending` passed into `PostList`:** the prop changes from `false` to `true` in the render for the urgent update. `memo` sees a changed prop and renders the list, with all its slow posts. The field freezes again.

```tree caption="Where the fade goes decides whether memo can still skip the slow list."
Showing that the list is behind
- +On a wrapper `<div>` in `SearchPage` [`style={{ opacity: isPending ? 0.7 : 1 }}`] | `PostList` gets the **same `query`** | `memo` **skips** the list; the field answers **at once**
- !As a prop of `PostList` [`isPending={isPending}`] | The prop **changes** from `false` to `true` | `memo` **renders** all the slow posts; ~the field **freezes again**
```

A third way is to show a `Loading...` line instead of the list while the Transition is pending. That hides the results the user is reading, on every keystroke. React's docs say of a similar case: "Hiding the entire tab container to show a loading indicator leads to a jarring user experience." The faded list keeps the old results on the screen.

### The Posts Page with the Faded List

Only the search page file changes. It wraps the list in a `<div>` whose opacity follows `isPending`:

```jsx title="src/components/SearchPage.jsx" startLine="17" good="4"
  return (
    <>
      <input value={query} onChange={handleChange} placeholder="Search posts" />
      <div style={{ ~opacity: isPending ? 0.7 : 1~ }}> {/* isPending comes from useTransition */}
        <PostList query={searchQuery} />
      </div>
    </>
  );
```

### What Happens When the User Types `1` Now

**The old list fades the moment the user types, and the new list arrives at full strength.** Here are the steps:
1. The user types `1`.
2. In the render for the urgent update, `isPending` becomes `true`. The field shows `1`, and the wrapper gets an opacity of `0.7`.
3. React skips `PostList` in that render, because its only prop, `query`, did not change.
4. React renders the Transition in the background. In that render, `searchQuery` holds the new text. And `isPending` is `false`, because this render is the finished state.
5. React commits it: 176 posts at full strength.

When the user types `2` during step 4, the flag stays `true`. The list goes from the faded 500 posts straight to 15 posts at full strength.

The Elements panel shows the fade as a plain `style` attribute on the wrapper:

```dom caption="The Elements panel while the Transition is pending: the wrapper div holds opacity 0.7 around the old list."

    <ul>
      <li>Post #1</li>
      <li>Post #2</li>
      <li>Post #3</li>
    </ul>
  </div>
```

When the Transition commits, the same `<div>` holds `style="opacity: 1;"`. The list inside it holds the new posts.

Remember: `isPending` goes on an element outside the list, never into the props of the memoized list.

## All 5 Principles Together

### The Complete Project

Here is the complete Posts page. The entry file is unchanged and mounts `App` inside `<StrictMode>`.

```jsx title="src/App.jsx"
import SearchPage from './components/SearchPage.jsx';

export default function App() {
  return ~<SearchPage />~; // React calls App, then SearchPage
}
```

```jsx title="src/components/SearchPage.jsx"
import { useState, useTransition } from 'react';
import PostList from './PostList.jsx';

export default function SearchPage() {
  const [query, setQuery] = useState('');
  const [searchQuery, setSearchQuery] = useState('');
  const [isPending, ~startTransition~] = useTransition(); // Principle 2: isPending and startTransition

  function handleChange(e) {
    const text = e.target.value;
    ~setQuery(text)~; // Principle 2: urgent, the field shows the letter at once
    startTransition(() => {
      ~setSearchQuery(text)~; // Principles 2 and 4: a Transition the next keystroke can interrupt
    });
  }

  return (
    <>
      <input value={query} onChange={handleChange} placeholder="Search posts" />
      <div style={{ ~opacity: isPending ? 0.7 : 1~ }}> {/* Principle 5: the old list fades while the new one renders */}
        <PostList query={searchQuery} />
      </div>
    </>
  );
}
```

```jsx title="src/components/PostList.jsx"
import { memo } from 'react';

const posts = [];
for (let i = 1; i <= 500; i++) {
  posts.push('Post #' + i);
}

const PostList = ~memo~(function PostList({ query }) { // Principle 3: skipped while query holds the old text
  console.log('PostList rendered:', query);
  const results = posts.filter(title => title.includes(query));
  return (
    <ul>
      {results.map(title => <SlowPost key={title} title={title} />)}
    </ul>
  );
});

function SlowPost({ title }) {
  const startTime = performance.now();
  while (performance.now() - startTime < ~1~) {} // Principle 1: each post waits 1 millisecond
  return <li>{title}</li>;
}

export default PostList;
```

### How React Calls the Components After One Keystroke

When the page opens, React calls `App`, then `SearchPage`. Then it calls `PostList`, which calls one `SlowPost` for each of the 500 titles. After the user types `1`, React renders twice, and `PostList` takes part only in the second render:

```tree caption="The order in which React calls the components after the user types 1: the urgent update skips PostList, and the Transition renders it."
`SearchPage` after the user types `1`
- +1. Render for the urgent update | React calls **`SearchPage`** with `query` `'1'` and `searchQuery` `''` | **`PostList` is skipped** by `memo` | The field shows **`1`**; the old list **fades**
- +2. Render for the Transition | React calls **`SearchPage`**, then **`PostList`** with `'1'` | `PostList` calls **176 `SlowPost`** components **in the background** | The list shows **176 posts at full strength**
```

| Aspect | The Habit That Freezes the Field | The React Rule |
| :--- | :--- | :--- |
| **The state** | One `query` for both the field and the slow list, so every letter waits for the list | `query` for the field, and `searchQuery` for the list |
| **The Transition** | Wrapping the field's own `setQuery` in `startTransition` | `setQuery` stays urgent; only `setSearchQuery` goes inside `startTransition` |
| **The list** | A plain `PostList`, which renders its slow posts on every keystroke | `PostList` wrapped in `memo`, so the urgent update skips it |
| **Fast typing** | Expecting a finished list for every letter, or adding a fixed delay | React drops the unfinished list and renders only the latest text |
| **The sign** | Passing `isPending` into `PostList`, or hiding the list behind `Loading...` | Fading the old list on a wrapper `<div>` outside `PostList` |

Remember the one sentence of this lesson. **The `<input>` field must answer at once. The list can follow a moment later.**

## For the Interview

> **The Interview Question:** How do you keep typing responsive while a big re-render runs with useTransition?

### How to Answer Clearly in 30 Seconds

"When one state variable drives both a text field and a big list, every keystroke is an urgent update. The field cannot show the letter until React has rendered the whole list. With `useTransition`, one keystroke makes two updates. The field's own state stays urgent, because a Transition cannot control a text input. A second state variable for the list is set inside `startTransition`, so React renders the new list in the background. Three details make it work:
1. **`memo` on the list**: the parent renders again for the urgent update, so the list must be memoized to skip that render.
2. **Interruption**: when the user types again, React throws away the unfinished list and renders only the latest text.
3. **`isPending`**: it is `true` while the list is behind, so we can fade the old list, on an element outside the memoized list."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"Why can't you put the input's own state inside `startTransition`?"**
   Because the field must answer every keystroke at once. React's docs: "Transitions are non-blocking, but updating an input in response to the change event should happen synchronously." That is why we keep two state variables: `query` stays urgent for the field, and `searchQuery` is set inside the Transition for the list. When the text comes from a prop, we have no set function to wrap. Then `useDeferredValue` is the tool (as seen in Lesson 68).
2. **"Does `useTransition` make the list render faster? How is it different from debouncing?"**
   No, the list takes exactly as long as before. The Transition only lets the keystroke go first, and it lets React drop a list nobody needs anymore. A debounce waits a fixed time, and then its render blocks the next keystroke all the same. A Transition needs no fixed delay and never blocks the keystroke. Debouncing is still right for slow work outside rendering, such as a request to a server.
3. **"Which updates count as a Transition?"**
   Only the state updates made during the `startTransition` call. React calls our function at once, not later. An update inside a `setTimeout` runs after the call has ended, so it is not marked as a Transition. An update after an `await` also needs its own `startTransition`. React's docs explain: "This is a JavaScript limitation due to React losing the scope of the async context." Form actions and `useActionState` handle this for forms (as seen in Lessons 41 and 42).

```tree dir=right caption="Interview comparison: one state variable for the field and the list vs. two state variables with useTransition."
Typing in a search field that drives a slow list
- !One state variable [`query`] | Every keystroke renders **the whole list** first | The field **freezes** until the list is done
- +Two state variables with `useTransition` [`query` `searchQuery`] | The field updates **at once**; the list renders **in the background** | With **`memo`** on the list and **`isPending`** outside it, typing stays **smooth**
```
