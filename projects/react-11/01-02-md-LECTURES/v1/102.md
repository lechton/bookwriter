# Lecture 102: What Server-Side Rendering Changes on the First Screen

*(Why does a server-rendered page show up at once, yet ignore the first tap?)*

> INTERVIEW QUESTION | ❱ CORE | What is server-side rendering, and what does it solve?

---

## VS | Client-Side Rendering vs. Server-Side Rendering: both end with the same page, only one sends it already filled

> In a React app built for the browser alone, the server sends an HTML file with one empty element, so the phone stays blank until the JavaScript runs. **With server-side rendering, the server runs your components first and sends the HTML they return, so the phone shows the page at once**. But the buttons still wait for the JavaScript, because the server sends what the page looks like, not what it does.

Remember the first web page you ever wrote? A plain HTML file with a heading in it. The browser shows that heading the moment the file arrives, with no JavaScript at all.

A React app built with Vite alone does not work that way. **Its HTML file holds one empty element, and everything you see is built later, by JavaScript, in the browser.** On a fast laptop you never notice. On a slow phone, the user stares at a blank page for seconds. This is why we have server-side rendering. **The server runs your React components before it answers, and writes their HTML into the file**, as if you had typed it by hand.

Take an online shop. A friend sends the user a link to a product page: Blue Sneakers, at $49, with an Add to cart button. The user opens it on a phone with a slow connection. Ask yourself: what does the phone need to show the name and the price? Only HTML. And what does it need to make the button work? The JavaScript, because a click handler is a JavaScript function.

**Why:** Without server-side rendering, the name and the price wait for the JavaScript, just like the button. react.dev says it plainly: "This can feel very slow!" With server-side rendering, the name and the price come with the HTML, at once. But the button still waits for the JavaScript. See the catch? The page looks ready before it is ready, and a tap in those first seconds is lost.

So here is the one sentence to keep in mind for this whole lesson:

**The server sends what the page looks like. The JavaScript brings what the page does.**

### Back to a Plain HTML File

Here are three HTML files that can reach the phone. Look only at what sits inside them:

```html title="Three files the phone can receive"
<h1>Blue Sneakers</h1> <!-- A plain HTML page: you wrote the heading by hand -->
~<div id="root"></div>~ <!-- Vite alone: empty, the JavaScript fills it later -->
~<div id="root"><h1>Blue Sneakers</h1></div>~ <!-- Server-side rendering: React filled it on the server -->
```

The first file and the third file show the heading at once. The second file shows nothing until the JavaScript has downloaded and run.

> [!DEFINITION]
> **The root and createRoot.** [REVIEW] In a client-only React app, the HTML file holds one empty element, `<div id="root"></div>`, and a script tag that loads your JavaScript.
> In `main.jsx`, `createRoot(document.getElementById('root')).render(<App />)` tells React to build the whole page inside that empty element.
> Until that line runs, the page is blank (Lessons 07 and 46).

> [!DEFINITION]
> **First Contentful Paint.** [REVIEW] First Contentful Paint is the moment the user first sees content on the page, such as a heading or a price.
> MDN: "This is the first time users could start consuming page content."
> In a client-only app, it comes only after the JavaScript has run (Lesson 46).

> [!DEFINITION]
> **What is server-side rendering?** [NEW] Server-side rendering means the server runs your React components before it answers, and sends the HTML they return inside the root.
> The browser shows that HTML before any of your JavaScript loads, so First Contentful Paint comes as soon as the file arrives.
> It is the same `App` component you already have. There is no second, server version of it.
> And here is the important part: the HTML carries the look of the page, never its click handlers. Those still arrive with the JavaScript (Lesson 102).

react.dev puts the whole idea in one sentence: "Server rendering creates an illusion that the app loads faster by showing the HTML snapshot of its output."

### Three Ways to Make the First HTML

A team decides, page by page, who writes the first HTML of a page (as seen in Lesson 46). There are three ways:
1. **Client-side rendering.** The HTML holds an empty root, and `createRoot` builds the page in the browser. It fits a page behind a login, such as an admin tool, where nobody arrives from a shared link.
2. **Server-side rendering.** The server writes the HTML again for every request. It fits a page whose content changes, such as a product page whose price and stock change. MDN: "for every request, the server generates the HTML content on-the-fly because it is unrealistic to pregenerate every possible page."
3. **Static site generation.** The HTML is written once, when the app is built. It fits a page that is the same for everyone, such as a Terms of Service page (compared in Lesson 103, taught in Lesson 119).

In a real app, a framework lets the team pick the way for each page, and it writes the server code for us. In this lesson we write server-side rendering by hand, in its two smallest pieces, so we can see what each one does:
- **One call on the server**, `renderToString`, which turns `App` into HTML.
- **One call in the browser**, `hydrateRoot`, which makes that HTML answer taps.

### The Rule of Thumb: does it look ready, or is it ready?

**Ask one question about every server-rendered page: does it only look ready, or does it answer a tap? The HTML makes it look ready. Only the JavaScript makes it answer.**

A senior developer also knows the five classic mistakes:
1. **Counting the page as ready when it looks ready.** A tap before the JavaScript has run is lost, with no message.
2. **Expecting less JavaScript.** The browser still downloads the same `App` and everything it imports.
3. **Keeping `createRoot` in `main.jsx`.** React deletes the HTML from the server and builds it again.
4. **Loading the data in an Effect.** The server never runs Effects, so the server HTML holds only the loading line.
5. **Thinking it is only for search engines.** react.dev: "A common misunderstanding is that server rendering is only for SEO."

The rest of the lesson shows each one on a real product page.

## SECTION | A Product Page on a Slow Phone

Our page shows a name, a price, an `Add to cart` button, and a line that counts what is in the cart:

```page width=text caption="The product page of the shop, open in the developer's browser."
url: shop.example.com
heading: Blue Sneakers
line: $49
line: [Add to cart]
line: Cart: 0
```

Here it is as one component. The name and the price are written in `App` itself, for now:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [count, setCount] = useState(0);
  return (
    <main>
      <h1>Blue Sneakers</h1>
      <p>$49</p>
      <button ~onClick~={() => setCount(count + 1)}>Add to cart</button> {/* A JavaScript function: it cannot travel inside HTML */}
      <p>Cart: {count}</p>
    </main>
  );
}
```

In the client-only version, `main.jsx` mounts the app with `createRoot` (as seen in Lesson 07). The server-rendered version adds one file, `server.js`, and changes one line in `main.jsx`:

```files title="shop: File Explorer" caption="The files of the server-rendered product page."
server.js | server | Calls `renderToString(<App />)` and sends the HTML inside the root
src/
  App.jsx | page | Exports `App` as default: the same component on the server and in the browser
  main.jsx | boundary | Imports `App` and calls `hydrateRoot` on the HTML from the server
```

Now the user opens the link on the slow phone, sees the button, and taps `Add to cart` at once. Nothing happens. A few seconds later, the user taps again, and the line changes to `Cart: 1`:

**It may look the same, but it is NOT the same thing!** Before any tap, the server-rendered page in the first seconds and the same page after the JavaScript runs are identical, pixel for pixel. Yet on the first one, no code of ours listens for a tap. On the second one, React has attached our click handler to the button.

```tree dir=right caption="What arrives with the HTML from the server, and what arrives only with the JavaScript."
What reaches the phone, in order
- +1. The HTML from the server [`Blue Sneakers` `$49` `Add to cart`] | What the page **looks like** | The user can **read the product** at once
- !2. The time in between | The button is on the screen, **but no code of ours is listening** | A tap is **lost**, and nothing on the screen says so
- +3. The JavaScript [`onClick`] | What the page **does** | The same tap now changes the line to **`Cart: 1`**
```

Again, the one sentence of this lesson: **the server sends what the page looks like. The JavaScript brings what the page does.**

**PRINCIPLES:** Server-side rendering splits the first visit into two moments. First the HTML arrives and shows the page. Later the JavaScript arrives and makes the page answer. Five principles follow:
1. **Principle 1: renderToString: The Server Runs App and Sends Its HTML.** On the server, `renderToString` runs our components and returns their HTML as a string. The browser shows it before any JavaScript loads.
2. **Principle 2: Non-Interactive HTML: The Server Sends the Look, Not the Clicks.** The HTML has no click handlers. Until the JavaScript has run, the button does nothing, while a plain link already works.
3. **Principle 3: hydrateRoot: Reuse the Server HTML Instead of Rebuilding It.** In the browser, `hydrateRoot` reuses the HTML from the server and attaches the click handlers. `createRoot` would delete it and build it again.
4. **Principle 4: Effects Run Only in the Browser: Load the Data Before the Server Renders.** A product loaded in an Effect is not in the server HTML. The server sends the loading line instead.
5. **Principle 5: Two Runs of One App: The Content Moves Earlier, the JavaScript Does Not.** The same JavaScript downloads as before, and `App` runs again in the browser. Only the first content moves earlier.

## PRINCIPLE | `renderToString`: the server turns `App` into HTML before any JavaScript loads

> [!PRINCIPLE]
> **Principle 1: renderToString: The Server Runs App and Sends Its HTML**
>
> *On the server, call `renderToString(<App />)` from `react-dom/server` and send the string inside the root, so the browser shows the content before any JavaScript loads.*
>
> In a client-only app, the root arrives empty and the user waits on a blank page. `renderToString` runs the same `App` the browser runs and returns its HTML as plain text. When the server sends that text inside the root, the phone paints the product as soon as the file arrives. `renderToString` belongs in the server file only: imported into browser code, it only makes the bundle bigger.
>
> **DO THIS:**
> ```jsx
> app.use('/', (request, response) => {
>   const html = ~renderToString(<App />)~; // In server.js: the server runs App and gets its HTML
>   response.send(`<div id="root">${html}</div><script type="module" src="/bundle.js"></script>`);
> });
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import { ~renderToString~ } from 'react-dom/server'; // **WRONG:** in browser code, this only makes the bundle bigger
>
> const iconHtml = renderToString(<Icon />);
> ```

Remember how you build HTML by hand in plain JavaScript? You glue strings together:

```js title="Plain JavaScript: HTML as a string"
const name = 'John';
const html = ~'<h1>Hello, ' + name + '</h1>'~; // html holds the text '<h1>Hello, John</h1>'
```

`renderToString` does the same job, but from your JSX. It calls your component and gives you back the HTML it returns, as a plain string:

```jsx title="The same string, from a React component"
import { ~renderToString~ } from 'react-dom/server'; // The part of React that runs on the server

function App() {
  return <h1>Hello, John</h1>;
}

const html = ~renderToString(<App />)~; // html holds the text '<h1>Hello, John</h1>'
```

So the server sends neither a picture nor a running app. It sends text, the same kind of text you could have typed into a plain HTML file.

> [!DEFINITION]
> **What is renderToString?** [NEW] `renderToString` is a React function that runs your components and returns their HTML as a string. React provides it in `react-dom/server`, the part of React made for the server.
> react.dev: "These APIs are only used on the server at the top level of your app to generate the initial HTML. A framework may call them for you. Most of your components don't need to import or use them."
> Something that can be tricky: importing it into browser code breaks nothing. It only makes every user download the server part of React for nothing. react.dev: "Importing `react-dom/server` on the client unnecessarily increases your bundle size and should be avoided" (Lesson 102).

### The Same `App` on the Server and in the Browser

Which `App` does the server run? The very same one. The server imports the same file that `main.jsx` imports:

```jsx title="One App file, imported in two places"
import ~App~ from './src/App.jsx'; // In server.js: the server runs App to write the HTML
import ~App~ from './App.jsx'; // In main.jsx: the browser runs App to make the page answer
```

**Yes, it is the exact same thing!** The two paths differ only because the server file sits one folder above the `App` file. One component, run twice: once on the server, to write the HTML, and once in the browser, to make the page answer taps.

### The Server Sends the HTML Inside the Root

Here is our shop's server. For every request for the page, it runs `App` and sends the HTML inside the root:

```jsx title="server.js"
import { renderToString } from 'react-dom/server';
import App from './src/App.jsx';

app.use('/', (request, response) => {
  const html = ~renderToString(<App />)~; // Runs App and returns its HTML as a string
  response.send(`
    <div id="root">${html}</div>
    <script type="module" src="/bundle.js"></script>
  `); // Sends the page: the HTML inside the root, then the script tag that loads the bundle
});
```

A few names here come from the server library, not from React. react.dev's own example warns: "The route handler syntax depends on your backend framework."
- **`app`** is our server, the object the server library creates for us.
- **`app.use`** registers a route handler: a function the server calls for every request for the page at the address `/`.
- **`request`** and **`response`** are two objects the server library hands to that function on every request.
- **`response.send`** sends the page back to the browser.

The root element and the script tag are the same ones a client-only page has (as seen in Lesson 07). The only difference: the root is no longer empty.

### The Empty Root vs. the Root with the Product

Compare the root in the two files that reach the phone:

```html title="The root in the file that reaches the phone, without and with server rendering"
~<div id="root"></div>~ <!-- With createRoot only: empty until the JavaScript runs -->
~<div id="root"><main><h1>Blue Sneakers</h1><p>$49</p>...</main></div>~ <!-- With renderToString: the product is already inside -->
```

**It may look the same at the end, but it is NOT the same thing!** Once the JavaScript has run, both pages show the same product. Before that, only the second one shows anything. Server rendering moves First Contentful Paint from after the JavaScript has run to the moment the HTML arrives.

```tree caption="The HTML that reaches the phone with createRoot only, and with renderToString on the server."
What the root holds when the file reaches the phone
- !Client-only, with `createRoot` [`<div id="root"></div>`] | The root is **empty** | **Blank page** until the JavaScript downloads and runs
- +Server-rendered, with `renderToString` [`<div id="root"><main>...</main></div>`] | The root holds **the product** | First Contentful Paint comes **as soon as the HTML arrives**
```

### The Empty Comments React Writes into the HTML

Open the page source of the server-rendered page, the HTML file exactly as the browser received it. The `Cart` line holds something our JSX never had:

```html title="The page source: the root of the product page"
<div id="root"><main><h1>Blue Sneakers</h1><p>$49</p><button>Add to cart</button><p>Cart: <!-- -->0</p></main></div>
```

Between `Cart: ` and `0` sits an empty HTML comment. React wrote it, not us. It marks the spot where the text written in our JSX ends and the value in curly braces begins. react.dev's own server HTML shows the same pattern. We never write these comments, and the user never sees them.

## PRINCIPLE | `onClick` in the server HTML: the button shows, but a tap does nothing until the JavaScript runs

> [!PRINCIPLE]
> **Principle 2: Non-Interactive HTML: The Server Sends the Look, Not the Clicks**
>
> *The HTML from the server has no click handlers; a button with `onClick` answers only after the JavaScript has loaded and React has attached to the page, while a plain link works at once.*
>
> The user sees the product page as soon as the HTML arrives, so it looks ready. But `onClick` is a JavaScript function, and it never travels inside the HTML. Until the JavaScript has run, a tap on the button is lost, and nothing on the screen says so. Plan for that time instead of counting the page as ready when it looks ready. When a control only takes the user to another page, make it a link, because a link works before the JavaScript arrives.
>
> **DO THIS:**
> ```jsx
> <a ~href="/"~>All products</a> {/* Works before the JavaScript loads: the browser follows the link */}
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> <button ~onClick~={() => { window.location.href = '/'; }}>All products</button> {/* **WRONG:** a tap before the JavaScript runs is lost */}
> ```

Here is the smallest button with a click handler, and the HTML the server writes from it:

```jsx title="A button with a click handler"
function App() {
  const [count, setCount] = useState(0);
  return <button ~onClick~={() => setCount(count + 1)}>Cart: {count}</button>; // The click handler is a JavaScript function
}
```

```html title="The same button in the HTML from the server"
<button>Cart: <!-- -->0</button>
```

The text `Cart: 0` made it into the HTML. The click handler did not. An HTML string is just text, and a JavaScript function of ours has no place in it. So the server HTML carries the look of the button, and nothing that makes it answer.

> [!DEFINITION]
> **What is non-interactive HTML?** [NEW] Non-interactive HTML is HTML the user can see but cannot use: a tap on its button reaches no code of ours.
> react.dev calls what `renderToString` produces "the initial non-interactive HTML output of your React components".
> It also calls this HTML a snapshot: a still picture of what `App` returned on the server, at one moment (Lesson 102).

### Why the First Tap on `Add to cart` Is Lost

**Beware! A page that looks finished is not a page that works.** Here is the first visit on the slow phone, in order:
1. The server sends the HTML of the product page.
2. The browser shows the name, the price, the button, and `Cart: 0`.
3. The browser starts downloading the JavaScript: `main.jsx` and everything it imports.
4. The user taps `Add to cart`.
5. No code of ours is listening yet, so nothing happens. The line stays on `Cart: 0`, and nothing says the tap was lost.
6. The JavaScript arrives and runs. React attaches the click handler to the button already on the screen.
7. The user taps again, and the line changes to `Cart: 1`.

```page width=text caption="The product page on the slow phone after a tap on Add to cart, before the JavaScript has run."
url: shop.example.com
heading: Blue Sneakers
line: $49
line: [Add to cart]
line: Cart: 0 | bad
```

Something that can be tricky: the `0` on the phone came from the server, not from the browser. The server ran `useState(0)` once, to write the HTML, and typed the `0` into the text. That `count` lived only inside the server's run of `App`. Nothing connects it to the button on the phone.

### A Link vs. a Button in the Server HTML

Now the product page gets one more part: a link back to the list of all products.

```jsx title="src/App.jsx" startLine="6"
    <main>
      ~<a href="/">All products</a>~ {/* A plain HTML link: the browser follows it by itself */}
      <h1>Blue Sneakers</h1>
      <p>$49</p>
      ~<button onClick={() => setCount(count + 1)}>Add to cart</button>~ {/* What it does lives in our JavaScript */}
      <p>Cart: {count}</p>
    </main>
```

Both are in the server HTML, and both look ready. **It may look the same, but it is NOT the same thing!** Before the JavaScript has run:
- **A tap on `All products`** opens the address `/`. The browser knows what a link does, with no JavaScript of ours. react.dev lists "click links" among what visitors can do "before any of the JavaScript code loads".
- **A tap on `Add to cart`** does nothing. What the button does lives in our `onClick`, and `onClick` arrives only with the JavaScript.

MDN says the same about every server-rendered page: it is somewhat usable without JavaScript, "However, any interactivity or client-side logic will not work."

```tree caption="A link and a button in the server HTML, before the JavaScript has run."
Two parts of the server HTML before the JavaScript runs
- +A link [`<a href="/">`] | The **browser** knows what a link does | A tap **opens the list** at once
- !A button with a handler [`onClick`] | What it does lives in **our JavaScript** | A tap is **lost**, and `Cart: 0` stays
```

### Why This Bug Ships

Here is how a team ships this bug without noticing:
1. The team adds server-side rendering, and the product page appears fast on a test phone.
2. The team reports that the page "loads in under a second".
3. A shopper on a slow connection taps `Add to cart` in the first seconds.
4. Nothing happens, so the shopper taps again later, or leaves the shop.
5. On fast office Wi-Fi, the JavaScript arrives before anyone can tap, so the team never sees it.

Remember: **the server sends what the page looks like. The JavaScript brings what the page does.**

## PRINCIPLE | `hydrateRoot`: React keeps the server HTML and attaches the click handlers to it

> [!PRINCIPLE]
> **Principle 3: hydrateRoot: Reuse the Server HTML Instead of Rebuilding It**
>
> *When the root arrives with HTML from the server, start React with `hydrateRoot(document.getElementById('root'), <App />)`, not with `createRoot`.*
>
> `createRoot` was made for an empty root. On a root full of server HTML, its `render` call deletes that HTML and builds every node again, which drops the user's focus and puts any list that scrolls inside the page back at its top. `hydrateRoot` runs `App` in the browser, keeps the nodes the server sent, and attaches the click handlers to them.
>
> **DO THIS:**
> ```jsx
> ~hydrateRoot~(document.getElementById('root'), <App />); // Reuses the server HTML and attaches onClick
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> createRoot(document.getElementById('root')).~render(<App />)~; // **WRONG:** deletes the server HTML and builds it again
> ```

Remember `addEventListener`? In plain JavaScript, when the HTML is already on the page, you do not write it again. You grab the button that is there, and you attach a listener to it:

```js title="Plain JavaScript: the HTML is already there, add only the behavior"
const button = document.querySelector('button');
~button.addEventListener('click', addToCart)~; // The same button stays on the page, now it answers
```

The HTML stays as it is. You only add what it does. **`hydrateRoot` does exactly this, for your whole app.** It finds the HTML the server sent, keeps every element, and attaches your click handlers to them.

`createRoot` does the opposite. It is like writing `root.innerHTML = ''` and then building every element again from nothing. On an empty root, that is fine, because there is nothing to lose. On a root full of server HTML, it throws away the work the server just did.

```jsx title="The two ways main.jsx can start React"
createRoot(document.getElementById('root')).~render(<App />)~; // Deletes the HTML inside the root, then builds every node again
~hydrateRoot~(document.getElementById('root'), <App />); // Keeps the HTML inside the root and attaches the click handlers to it
```

`hydrateRoot` comes from the same package as `createRoot`. It takes `<App />` directly, so there is usually no `render` call after it. react.dev: "Call `hydrateRoot` to 'attach' React to existing HTML that was already rendered by React in a server environment."

> [!DEFINITION]
> **What is hydration?** [NEW] In everyday English, to hydrate something means to add water to something dry. The server HTML is the dry part: it has the shape of the page, and nothing in it runs.
> Hydration is React adding the logic of your components to that HTML, without writing the HTML again. `hydrateRoot` is the call that starts it.
> react.dev: "Hydration turns the initial HTML snapshot from the server into a fully interactive app that runs in the browser" (Lesson 102).

What hydration does in detail is taught in Lesson 104.

### Where the Click Handler Comes From

The button on the phone gets its `onClick` from a second run of `App`. React runs `App` again, this time in the browser, and connects each `onClick` it finds to the matching button the server sent. react.dev: "On the client, React will run the rendering code again so that it can attach your event handlers to that HTML."

That is why `hydrateRoot` takes `<App />`. It must be the same component the server passed to `renderToString`. react.dev: "This will usually be a piece of JSX like `<App />` which was rendered with a `ReactDOM Server` method".

```jsx title="src/main.jsx"
import { ~hydrateRoot~ } from 'react-dom/client'; // The same package as createRoot
import App from './App.jsx';

~hydrateRoot~(document.getElementById('root'), <App />); // The same App the server rendered: React reuses its HTML and attaches onClick
```

### Mistake: Keeping `createRoot` After Adding the Server

**It may work the same at first, but it is NOT the same thing!** With either line, the product ends up on the screen and the button works, so this mistake is easy to miss. Here is what happens when a developer adds the server and leaves `main.jsx` as it was:
1. The page appears at once from the server HTML.
2. A keyboard user presses Tab, and the `Add to cart` button gets the focus.
3. The JavaScript arrives, and `render` runs on a root that is already full.
4. React clears everything inside the root and builds every element again.
5. The focused button was deleted, and the new button is not focused. A list of reviews that scrolls inside the page jumps back to its top.

react.dev describes it in one sentence: "creating a root and calling `root.render` deletes all that HTML, and then re-creates all the DOM nodes from scratch. This can be slower, resets focus and scroll positions, and may lose other user input."

With `hydrateRoot`, React reuses the elements already on the page, in react.dev's words "instead of destroying and re-creating them."

::: row caption="The same main.jsx with createRoot and with hydrateRoot, on a root that arrives full of HTML from the server."
::: col title="createRoot on server HTML" tone=bad
```jsx title="src/main.jsx" bad="4"
import { createRoot } from 'react-dom/client';
import App from './App.jsx';

createRoot(document.getElementById('root')).render(<App />);
```
React deletes the server HTML and builds it again. The focused button loses its focus.
:::
::: col title="hydrateRoot on server HTML" tone=good
```jsx title="src/main.jsx" good="4"
import { hydrateRoot } from 'react-dom/client';
import App from './App.jsx';

hydrateRoot(document.getElementById('root'), <App />);
```
React keeps the server HTML and attaches the click handlers to it.
:::
:::

The rule works both ways:
- **The root arrives full of server HTML:** use `hydrateRoot`. react.dev: "If your app is server-rendered, using `createRoot()` is not supported."
- **The root arrives empty:** use `createRoot`. For an app with no server HTML, react.dev says `hydrateRoot` is not supported: "Use `createRoot()` instead."

In a framework, we usually write neither line. react.dev: "If you use a framework, it might do this behind the scenes for you."

Once more: **the server sends what the page looks like. `hydrateRoot` brings what the page does**, without touching what it looks like.

## PRINCIPLE | `useEffect` on the server: it never runs, so the server HTML holds only the loading line

> [!PRINCIPLE]
> **Principle 4: Effects Run Only in the Browser: Load the Data Before the Server Renders**
>
> *A product loaded in `useEffect` is not in the server HTML; get the data before the render, with the framework's data loading, so the server can write it into the HTML.*
>
> The server runs `App` once and never runs its Effects. If the product arrives in an Effect, the server writes the loading line, and the product appears only after the JavaScript has run and the request has come back. When the data is ready before the render, the server writes the product straight into the HTML.
>
> **DO THIS:**
> ```jsx
> export async function ~loader~() { // The framework calls this before rendering, on the server too
>   return getProduct();
> }
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> useEffect(() => {
>   ~getProduct().then(setProduct)~; // **WRONG:** never runs on the server, so the server HTML holds only Loading...
> }, []);
> ```

So far, the name and the price were written in `App`. A real shop loads them from its own server. Here is the product page loading them in an Effect (as seen in Lesson 33). The function `getProduct` comes from our stand-in server file, `api.js` (as seen in Lesson 46):

```jsx title="src/App.jsx"
export default function App() {
  const [product, setProduct] = useState(null);
  ~useEffect~(() => { // Never runs on the server
    getProduct().then(setProduct);
  }, []);
  if (!product) return <p>Loading...</p>;
  return (
    <main>
      <h1>{product.name}</h1>
      <p>${product.price}</p>
    </main>
  );
}
```

```html title="The root in the HTML from the server"
~<div id="root"><p>Loading...</p></div>~ <!-- The product is not here -->
```

Think of what the server does with `App`: it calls the function once and takes what it returns, like any function call. At that moment `product` is still `null`, so the component returns the loading line. An Effect runs after React has put the page on a screen, and the server has no screen. **So the server never runs an Effect.** react.dev: "Effects only run on the client. They don't run during server rendering."

### Why the First Screen Still Says `Loading...`

**Beware! The team added server rendering for a fast first screen, and the first screen says `Loading...`.** Here is the first visit on the slow phone, in order:
1. The server runs the component, and `product` is `null`.
2. The server skips the Effect and writes the loading line.
3. The phone shows `Loading...` at once.
4. The JavaScript downloads and runs, and React hydrates the loading line.
5. Only now does the Effect run and ask the shop's server for the product.
6. The answer comes back, and the name and the price appear.

react.dev: "the initial server-rendered HTML will only include a loading state with no data. The client computer will have to download all JavaScript and render your app only to discover that now it needs to load the data."

**It may look the same, but it is NOT the same thing!** On the developer's fast computer, both pages below look equally fast. On the slow phone, the first shows `Loading...` for seconds, while the second shows the product at once:

::: row caption="The first screen on the slow phone: data loaded in an Effect, and data the server has before it renders."
::: col title="Product loaded in an Effect" tone=bad
```page size=mini
url: shop.example.com
line: Loading... | bad
```
:::
::: col title="Product ready before the render" tone=good
```page size=mini
url: shop.example.com
heading: Blue Sneakers
line: $49 | good
```

### Getting the Data Before the Server Renders

The fix is to have the product before `App` runs on the server. A framework does this with its data loading, such as the `loader` of a route (as seen in Lesson 46). The framework calls `loader` first, waits for it, and then renders the route with what it returned:

```jsx title="The product route in a framework"
export async function ~loader~() { // The framework calls it before Product renders, on the server too
  return getProduct();
}

export default function Product({ loaderData }) {
  return (
    <main>
      <h1>{loaderData.name}</h1> {/* Blue Sneakers is already in the server HTML */}
      <p>${loaderData.price}</p>
    </main>
  );
}
```

react.dev: "If you use a framework, use its built-in data fetching mechanism." Where data loading lives in a server-rendered app is taught in Lesson 128.

### Why This Bug Ships

Here is how a team ends up deciding that server rendering does not help:
1. The team moves its client-only product page to a framework with server rendering.
2. The page keeps the Effect that loads the product.
3. The server HTML holds only `Loading...`.
4. A social media crawler that does not run JavaScript reads `Loading...` instead of the product name. MDN says social media crawlers "usually cannot" run JavaScript.
5. The team sees no gain on the phone, and decides that server rendering does not help.

## PRINCIPLE | `import App` in `main.jsx`: the browser still downloads and runs the whole app

> [!PRINCIPLE]
> **Principle 5: Two Runs of One App: The Content Moves Earlier, the JavaScript Does Not**
>
> *With `renderToString` and `hydrateRoot`, the browser downloads the same JavaScript as in the client-only app and runs `App` again; server rendering changes when the content appears, not how much JavaScript the page needs before it answers a tap.*
>
> The server runs `App` to write the HTML. The browser runs `App` again to attach the click handlers, so `App` and all its imports must still download. To make the first working tap come earlier, the code itself must shrink or split, with tools such as Server Components and code splitting.
>
> **DO THIS:**
> ```jsx
> const Reviews = ~lazy~(() => import('./Reviews.jsx')); // Code splitting: the code of Reviews downloads later, so the button answers sooner
> ```
>
> **DO NOT DO THIS:**
> ```jsx
> import ~Reviews~ from './Reviews.jsx'; // **WRONG:** the server already rendered the reviews, but their code still downloads before the button answers
> ```

Look at the second line of `main.jsx`:

```jsx title="src/main.jsx"
import { hydrateRoot } from 'react-dom/client';
~import App from './App.jsx';~ // App and everything it imports go into the bundle, as before

hydrateRoot(document.getElementById('root'), <App />);
```

`main.jsx` imports `App`, so the app and every component it uses are in the bundle, exactly as in the client-only app. The browser needs all of them, because it runs `App` again to find the click handlers. react.dev: "On the server, it will render to produce the initial HTML. On the client, React will run the rendering code again so that it can attach your event handlers to that HTML."

### The Client-Only Visit vs. the Server-Rendered Visit

Here are the two first visits side by side, step by step:

| Step | Client-only | Server-rendered |
| :--- | :--- | :--- |
| **1. The HTML arrives** | An empty root | The product inside the root |
| **2. The user sees** | A blank page | `Blue Sneakers` and `$49` |
| **3. The JavaScript** | Downloads | Downloads: the same files |
| **4. `App` runs in the browser** | `createRoot` renders it and builds the page | `hydrateRoot` renders it again and attaches the handlers |
| **5. The button works** | Only after step 4 | Only after step 4 |

Look at step 2 and step 5:
- **For the first content, it is NOT the same thing.** The server-rendered page shows the product at step 2, while the client-only page is still blank.
- **For the button, it is the exact same thing.** In both visits, the button works only at step 5, after the same JavaScript has downloaded and `App` has run.

### When the Browser Really Downloads Less

react.dev also writes that "Server rendering generally sends less JavaScript to the client". That line speaks of the frameworks react.dev recommends, which combine server rendering with other tools. With `renderToString` and `hydrateRoot` alone, the bundle stays the same. The browser downloads less only when some code never reaches it, or reaches it later:
- **Server Components** never run in the browser, so their code never reaches it (as seen in Lesson 101).
- **Code splitting** with `lazy` loads a component's code only when React first renders it (as seen in Lesson 70).

Suppose the product page also shows a long list of customer reviews under the button. Server rendering puts the reviews into the HTML. But the code of the `Reviews` component still downloads before `Add to cart` can answer. With `lazy`, that code downloads later, so the first download is smaller:

```jsx title="src/App.jsx"
import { ~lazy~ } from 'react'; // React provides lazy for code splitting

const Reviews = ~lazy~(() => import('./Reviews.jsx')); // The code of Reviews downloads only when React first renders it
```

This has one cost with `renderToString`. It does not wait for the code of `Reviews`, so the server HTML holds the Suspense fallback in place of the reviews (as seen in Lesson 69). In the browser, React renders the reviews itself once their code arrives, and prints this error in the Console:

```devconsole width=full caption="The Console after hydrateRoot, when renderToString sent the fallback of a lazy component."
x Uncaught Error: Switched to client rendering because the server rendering aborted due to:
  The server used "renderToString" which does not support Suspense. If you intended for this Suspense boundary to render the fallback content on the server consider throwing an Error somewhere within the Suspense boundary. If you intended to have the server wait for the suspended component please switch to "renderToPipeableStream" which supports Suspense on the server
```

The streaming APIs can wait for the code of `Reviews`, so the reviews are in the server HTML (taught in Lessons 117 and 118).

```tree dir=right caption="What server-side rendering moves, and what it leaves where it was."
What server-side rendering changes on the first visit
- +Moves earlier | The **first content**: the HTML holds the product | First Contentful Paint comes **when the HTML arrives**
- !Stays the same | The **JavaScript** the browser downloads | `App` and its imports are **still in the bundle**
- !Stays the same | The **first working tap** | Comes only after `App` has **run again in the browser**
```

### Why This Bug Ships

Here is how a team expects two fixes and gets only one:
1. A slow product page has a large bundle.
2. The team adds server rendering to make the page fast.
3. The first content now appears early.
4. The button still works only after the same large bundle has loaded and `App` has run again.
5. The team expected both problems to be solved, and must still split or shrink the code.

Remember: **the server sends what the page looks like. The JavaScript brings what the page does**, and it is the same JavaScript as before.

## All 5 Principles Together

### The Complete Server-Rendered Product Page

Here are the three files of the finished product page. `App` is the same component on the server and in the browser:

```jsx title="src/App.jsx"
import { useState } from 'react';

export default function App() {
  const [count, setCount] = useState(0);
  return (
    <main>
      ~<a href="/">All products</a>~ {/* Principle 2: a link works before the JavaScript runs */}
      <h1>Blue Sneakers</h1>
      <p>$49</p>
      <button ~onClick~={() => setCount(count + 1)}>Add to cart</button> {/* Principle 2: works only after hydrateRoot has run */}
      <p>Cart: {count}</p>
    </main>
  );
}
```

The server file runs `App` and sends its HTML inside the root:

```jsx title="server.js"
import { renderToString } from 'react-dom/server';
import App from './src/App.jsx';

app.use('/', (request, response) => {
  const html = ~renderToString(<App />)~; // Principle 1: the server runs App and gets its HTML
  response.send(`
    <div id="root">${html}</div>
    <script type="module" src="/bundle.js"></script>
  `);
});
```

`main.jsx` runs `App` again in the browser and attaches the click handlers to the HTML from the server:

```jsx title="src/main.jsx"
import { hydrateRoot } from 'react-dom/client';
~import App from './App.jsx';~ // Principle 5: App and its imports are still in the bundle

~hydrateRoot~(document.getElementById('root'), <App />); // Principle 3: the browser runs App again and attaches onClick
```

### The Order of the First Visit

On the first visit, `App` runs twice: once on the server, and once in the browser. Between the two runs, the user sees the page but cannot use its button:

```tree dir=right caption="The first visit to the server-rendered product page, from the request to the first working tap."
The first visit on the slow phone
- +1. The server runs `App` [`renderToString`] | Writes the HTML of the product page | Effects **do not run** here
- +2. The HTML arrives [`<div id="root"><main>...</main></div>`] | The user **sees** `Blue Sneakers` and `$49` | First Contentful Paint
- !3. The JavaScript downloads | The button is on the screen, **but no code of ours is listening** | A tap on `Add to cart` is **lost**
- +4. The browser runs `App` again [`hydrateRoot`] | React **keeps** the HTML and attaches `onClick` | A tap now shows **`Cart: 1`**
```

### Summary

| Aspect | The Client-Only Habit | The Server-Rendering Rule |
| :--- | :--- | :--- |
| **The first HTML** | The root arrives empty, and the user sees a blank page | `renderToString(<App />)` on the server puts the product inside the root |
| **The first tap** | The page appears and answers at the same moment | The page appears first; the button answers only after the JavaScript has run |
| **`main.jsx`** | `createRoot(...).render(<App />)` on an empty root | `hydrateRoot(..., <App />)` on the root full of server HTML |
| **The data** | Loaded in an Effect after the first render | Ready before the render, with the framework's data loading |
| **The JavaScript** | `App` and its imports in the bundle | The same bundle; `App` runs again in the browser |

Remember the one sentence of this lesson. **The server sends what the page looks like. The JavaScript brings what the page does.**

## For the Interview

> **The Interview Question:** What is server-side rendering, and what does it solve?

### How to Answer Clearly in 30 Seconds

"Server-side rendering means the server runs our React components and sends their HTML, so the browser can show the content before any of our JavaScript loads. On the server, `renderToString` from `react-dom/server` returns that HTML, though react.dev now recommends the streaming APIs instead. In the browser, `hydrateRoot` attaches React to that HTML instead of rebuilding it, as `createRoot` would. It solves the blank first screen of a client-only app. First Contentful Paint comes as soon as the HTML arrives, and crawlers that do not run JavaScript can read the content. So it is not only for SEO. There are three things it does not solve:
1. **The page is not interactive yet.** The HTML has no click handlers, so a button answers only after the JavaScript has loaded and React has hydrated the page. Plain links work at once.
2. **The JavaScript is the same.** The browser still downloads `App` and renders it again to attach the handlers.
3. **Effects do not run on the server.** Data loaded in an Effect appears in the server HTML only as a loading state."

### Three Classic Follow-Up Questions Interviewers Ask

1. **"If a server-rendered page shows up fast, why does a tap sometimes do nothing?"**
   Because the HTML from the server is non-interactive. It holds the look of the button but not its `onClick`, which arrives only with the JavaScript. Between First Contentful Paint and the moment React has hydrated the page, a tap reaches no code. MDN calls that second moment Time to Interactive, when the page responds to user input "including having event handlers registered". MDN also notes that this metric is not standardized. Suspense boundaries let React make parts of the page interactive one at a time, which react.dev calls Selective Hydration, taught in Lesson 117.
2. **"Is server-side rendering the same thing as Server Components?"**
   No. With server-side rendering, the server makes HTML from the same components that later run in the browser, so their code is still in the bundle. Server Components never run in the browser at all, so their code never reaches it, as seen in Lesson 101. The two work together: the output of Server Components can itself be server-side rendered to HTML.
3. **"Why does react.dev recommend other APIs over `renderToString`?"**
   `renderToString` returns the whole HTML at once, so it "does not support streaming or waiting for data". When a component suspends, it immediately sends that component's fallback as HTML. react.dev recommends `renderToPipeableStream` on Node.js and `renderToReadableStream` with Web Streams. They send the HTML in pieces, as each piece becomes ready, taught in Lessons 117 and 118. The same HTML can also be made once, when the app is built, instead of on each request. That is static site generation, taught in Lesson 119.

```tree dir=right caption="Interview summary: what server-side rendering solves, and what it leaves to other tools."
Server-side rendering in an interview
- +What it solves | The **blank first screen**: content appears **when the HTML arrives** | Crawlers that do not run JavaScript **can read the page**
- !What it does not solve | The button answers only **after the JavaScript runs** | The **same bundle** downloads, and Effects **do not run on the server**
```
